### Title
Certificate verification trusts the self-declared, unsigned-at-lookup-time `Issuer` field to select the signing CA - ([File: cert/ca_pool.go])

### Summary
In the Foundation report, `_getCreatorPaymentInfo` decided who counts as the "creator" (and thus who gets 100% of the sale revenue) by matching an attacker-influenceable field (a royalty-registry recipient address) against the seller, rather than binding that decision to a value that was cryptographically tied to the real creator identity. The closest reachable analog in `nebula--017` is `CAPool.GetCAForCert`, which selects the CA used to validate a certificate's signature purely by reading the certificate's own self-declared `Issuer` field and doing a map lookup — before any signature check has occurred.

### Finding Description
`CAPool.verify` (called from `VerifyCertificate`/`VerifyCachedCertificate`, which back `HandshakeManager.certVerifier`) resolves the signer as follows: [1](#0-0) 

```go
func (ncp *CAPool) verify(c Certificate, now time.Time, certFp string, signerFp string) (*CachedCertificate, error) {
	...
	signer, err := ncp.GetCAForCert(c)
	...
	if signer.Certificate.Curve() != c.Curve() {
		return nil, ErrCurveMismatch
	}
```

`GetCAForCert` itself: [2](#0-1) 

The `issuer` value used for the map lookup comes directly from the wire bytes of the *unverified* certificate the peer supplied during the handshake (`c.Issuer()`), which is populated during ASN.1/protobuf unmarshalling before any cryptographic check occurs: [3](#0-2) [4](#0-3) 

This mirrors the underlying pattern in H-02: a downstream authorization/trust decision ("which CA governs this certificate, and by extension what group/network constraints apply") is derived from a field the *presenter* controls and declares, and is only *later* validated by checking `c.CheckSignature(signer.Certificate.PublicKey())` and `CheckCAConstraints`. If the fingerprint used for lookup happens to collide with, or if an attacker submits a certificate whose `Issuer` matches a legitimately-trusted CA fingerprint but whose actual signing key differs, the signature check does catch the mismatch (`ErrSignatureMismatch`) — so the ultimate cryptographic guarantee holds. However, this is exactly the fragile pattern flagged in H-02: the "who signed / who owns this" determination is read from self-declared data rather than being intrinsically bound to the verification result, and any code path that consults `signer`/`Issuer()` for a policy decision *before* the signature check completes (as `verify()` does when computing curve/expiry checks against `signer` before calling `CheckSignature`) is operating on a lookup keyed by unverified attacker input.

### Impact Explanation
If exploitable, this pattern would let an attacker present a certificate whose self-declared `Issuer` fingerprint spoofs a legitimate CA to influence pre-signature-check control flow (e.g., which CA's expiry/curve is consulted for early rejection decisions), analogous to how the Foundation bug let a self-declared royalty recipient override the true creator's payout rights. In nebula's case the final `CheckSignature`/`CheckCAConstraints` gate prevents a full authentication bypass, so the exploitable impact is limited to information/behavioral differences based on an unverified `Issuer` lookup rather than fund theft or auth bypass — this is a structural code-smell match to H-02's root cause (deciding based on attacker-declared identity field before verification), not a proven, standalone exploitable vulnerability in this codebase.

### Likelihood Explanation
Low-to-moderate. The dangerous "use before verify" ordering is real and structurally identical to the reported bug class, but the actual cryptographic check (`CheckSignature`) still gates final trust, so a concrete authentication bypass was not demonstrated in the available code; this could not be fully confirmed without deeper tracing of every caller that consults `signer` fields ahead of `CheckSignature` (e.g., `signer.Certificate.Curve()`/`Expired()` checks at ca_pool.go:220-226, which run on the "signer" object resolved purely from the unverified `Issuer` value, before the signature is validated at line 240).

### Recommendation
Reorder `verify()` so that no property of `signer` (curve, expiry) is consulted for a security decision until after `c.CheckSignature(signer.Certificate.PublicKey())` succeeds, or ensure every consumer of `GetCAForCert`'s result treats it as provisional/unverified until the signature check passes — mirroring the Foundation fix of computing the "is this really the creator" fact from an authenticated source (`ITokenCreator.tokenCreator`) rather than from the self-declared royalty override.

### Proof of Concept
Not independently reproduced against a running nebula instance in this session — this assessment is based on static code review of `cert/ca_pool.go`, `cert/cert_v1.go`, and `cert/cert_v2.go`. Confirming actual exploitability would require constructing a certificate with a forged `Issuer` fingerprint colliding with a real trusted CA's fingerprint and observing whether any decision taken between `GetCAForCert` and `CheckSignature` (e.g., curve/expiry-based early rejection) can be abused to affect behavior — this was not verified end-to-end due to tool/time constraints.

```go
// GetCAForCert attempts to return the signing certificate for the provided certificate.
// No signature validation is performed
func (ncp *CAPool) GetCAForCert(c Certificate) (*CachedCertificate, error) {
	issuer := c.Issuer()
	if issuer == "" {
		return nil, fmt.Errorf("no issuer in certificate")
	}

	signer, ok := ncp.CAs[issuer]
	if ok {
		return signer, nil
	}

	return nil, ErrCaNotFound
}
```
