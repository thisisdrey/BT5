### Title
Liquidation deadlock: positions with debt in `[debtFloorInUsd, 2 * debtFloorInUsd)` can never be liquidated - (contracts/Pool.sol)

### Summary
`Pool.liquidate` combines the `maxLiquidable` close-factor cap with the `debtFloorInUsd` check in a way that creates a dead zone: for any account whose debt in USD is between `debtFloorInUsd` and `2 * debtFloorInUsd` (given the deployed `maxLiquidable = 0.5e18`), every possible `amountToRepay_` reverts. This is the analog of the reported null-deref DoS class — a crafted state makes a core code path permanently unreachable — and it lets an attacker deliberately park an underwater position that no liquidator can touch, forcing the pool to absorb bad debt.

### Finding Description
In `Pool.liquidate` (contracts/Pool.sol:537-596) two sequential checks constrain `amountToRepay_`:

1. Close factor: `amountToRepay_.wadDiv(_debtTokenBalance) > maxLiquidable` reverts. With `maxLiquidable = 0.5e18` (set in `initialize`, contracts/Pool.sol:181), `amountToRepay_ ≤ 0.5 * debt`.
2. Debt floor: if `debtFloorInUsd > 0`, then `_newDebtInUsd = debt − amountToRepay_` must be `0` or `≥ debtFloorInUsd`, else `RemainingDebtIsLowerThanTheFloor` reverts (contracts/Pool.sol:571-579).

Let `D` be the position's debt in USD. For a successful liquidation we need either `repay == D` (full repay, requires `D ≤ 0.5·D` — impossible) or `D − repay ≥ floor` with `repay ≤ 0.5·D`, i.e. `0.5·D ≥ floor`, i.e. `D ≥ 2·floor`.

Therefore any position with `floor ≤ D < 2·floor` is completely unliquidatable:
- Partial repay (`repay < D`) → remaining debt `∈ (0, floor)` → `RemainingDebtIsLowerThanTheFloor`.
- Full repay (`repay == D`) → `repay/D = 1e18 > maxLiquidable` → `AmountGreaterThanMaxLiquidable`.

The attacker path: deposit collateral, `DebtToken.issue`/`mint` a synthetic so the position's debt sits inside `(floor, 2·floor)`, then let the collateral price decline (or manipulate it in the same block via an AMM-backed oracle path) until `debtPositionOf` reports unhealthy. Every `liquidate` call reverts. Repayment of one's own debt via `DebtToken.repay` is unaffected, but the attacker simply doesn't repay — the pool cannot force-exit the position.

The checks that exist (`whenNotShutdown`, `nonReentrant`, `onlyIfSyntheticTokenExists`, `PositionIsHealthy`, `AmountIsZero`, `CanNotLiquidateOwnPosition`) do not cover this case. `quoteLiquidateMax` (contracts/Pool.sol:419-440) correctly returns `min(maxLiquidable·debt, collateral-bound amount)` as the "max repayable", yet passing exactly that value still hits the floor revert — the quote path itself confirms the contradiction.

### Impact Explanation
Permanent liquidation liveness failure on a targeted, attacker-created position → protocol insolvency. The attacker deposits the minimum collateral that supports `D ∈ (floor, 2·floor)`, waits for (or induces) undercollateralization, and the pool accrues unliquidatable bad debt with no recourse; seizure via `DepositToken.seize` is only reachable through `liquidate`. Repeated across accounts/synths, losses scale linearly at negligible cost. This meets the "permanent freezing / insolvency" impact bar.

### Likelihood Explanation
Requires `debtFloorInUsd > 0` (a deployed configuration the protocol itself intends for liquidator incentives) and `maxLiquidable < 1e18` (deployed as 50%). Both are the configured state. The attacker only needs public entry points (`deposit` via gateway/`DepositToken`, `DebtToken.issue`) and a price move — achievable via waiting for volatility or same-transaction oracle-manipulable collateral. No privileged role needed. The dead-zone width is `floor` USD, which is designed to be non-trivial (it exists to cover liquidator gas+profit).

### Recommendation
In `liquidate`, permit a full repay to bypass the close-factor cap, e.g. skip the `maxLiquidable` check when `amountToRepay_ == _debtTokenBalance` (or when the remaining debt would otherwise drop below the floor). Alternatively, treat `D − repay < floor` as an instruction to repay all rather than reverting. `quoteLiquidateMax` should be updated consistently so the quoter never returns an amount that necessarily reverts.

### Proof of Concept
Hardhat/fork sketch (fork a chain where the pool has `debtFloorInUsd = F > 0`, `maxLiquidable = 0.5e18`):

```ts
// 1. Attacker deposits collateral worth ~2.4 * F and mints synth so
//    debtUsd = 1.5 * F  (i.e. F < D < 2F)
await depositToken.connect(attacker).deposit(amount);
await debtToken.connect(attacker).issue(mintAmount, attacker.address);

// 2. Push position underwater: drop collateral price via oracle's
//    manipulable feed or wait for market move.
//    assert((await pool.debtPositionOf(attacker.address))._isHealthy == false)

const debt = await debtToken.balanceOf(attacker.address);

// 3a. Any partial repay reverts on the floor
await expect(
  pool.connect(liquidator).liquidate(synth.address, attacker.address, debt.div(2), depositToken.address)
).to.be.revertedWithCustomError(pool, 'RemainingDebtIsLowerThanTheFloor');

// 3b. Full repay reverts on maxLiquidable
await expect(
  pool.connect(liquidator).liquidate(synth.address, attacker.address, debt, depositToken.address)
).to.be.revertedWithCustomError(pool, 'AmountGreaterThanMaxLiquidable');

// 4. The "max liquidatable" quote itself is unusable
const maxRepay = await pool.quoteLiquidateMax(synth.address, attacker.address, depositToken.address);
await expect(
  pool.connect(liquidator).liquidate(synth.address, attacker.address, maxRepay, depositToken.address)
).to.be.reverted; // RemainingDebtIsLowerThanTheFloor
```

One caveat I could not fully verify within the search budget: whether `DebtToken.issue` additionally enforces `debtFloorInUsd` as a mint minimum. The result is unaffected either way — if issue enforces `debt ≥ floor`, debt in `[floor, 2·floor)` is still reachable and unliquidatable; if it doesn't, the dead zone only widens.
