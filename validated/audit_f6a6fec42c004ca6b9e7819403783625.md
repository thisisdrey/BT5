### Title
`liquidate-multi` Batch Size Can Exceed Per-Transaction Cost Limits, Defeating Its Front-Running Protection for Bad-Debt Socialization - ([File: mainnet/contracts/market/v0-4-market.clar])

### Summary
`liquidate-multi` is designed to atomically liquidate up to 64 positions in a single transaction specifically to "prevent front-running attacks that prevent bad debt socialization." Each of the 64 positions it processes internally triggers the full `liquidate` code path — multiple cross-contract calls to `.v0-market-vault`, index-cache refreshes, and a further nested `fold` over `socialize-debt-asset` when a borrower's collateral is fully exhausted. This is structurally the same class of bug as the reported issue: a caller-controlled batch size multiplies per-unit cost until a single transaction's required runtime/read/write cost can exceed what the Stacks network allows in a block, making the transaction permanently un-mineable and silently defeating the atomicity guarantee the function was built to provide.

### Finding Description
`liquidate-multi` simply maps `call-liquidate` over a caller-supplied list of up to 64 positions: [1](#0-0) 

Each element of that list invokes the full `liquidate` function via `call-liquidate`: [2](#0-1) 

Every single `liquidate` invocation already performs several nested cross-contract calls (`get-cached-indexes`, `vault-system-repay`, `.v0-market-vault debt-remove-scaled`, `.v0-market-vault collateral-remove`), and — when the borrower's collateral is fully drained by the liquidation — additionally runs `fold socialize-debt-asset` over the borrower's remaining debt list, where each entry does its own `vault-socialize-debt` call, `map-set index-cache` write, and `.v0-market-vault debt-remove-scaled` call: [3](#0-2) [4](#0-3) 

Because the batch length (up to 64) is multiplied by this already-heavy per-position cost (multiple contract-calls, map reads/writes, and a further inner loop for socialization), a caller (or an attacker who deliberately arranges many simultaneously-liquidatable, fully-collateral-exhausted positions, e.g. during a market downturn) can construct a `liquidate-multi` call whose aggregate runtime/read-count/write-count cost approaches or exceeds the cost limits enforceable within a single Stacks block. Unlike a normal DoS where the caller simply pays more, on Stacks a transaction whose cost exceeds the network's per-block cost limits can never be included by any miner, regardless of fee — the transaction is permanently unmineable, exactly the scenario the external report describes for `finalizeBlocks`.

### Impact Explanation
The comment on `liquidate-multi` explicitly states its purpose is to prevent front-running attacks that would otherwise block bad-debt socialization. If the worst-case cost of a full 64-position batch (each potentially triggering its own bad-debt socialization sub-loop) exceeds network cost limits, then during the exact high-stress conditions (mass under-collateralization from a price crash) when this atomic protection is most needed, liquidators are forced to fall back to sequential, non-atomic single-position `liquidate` calls — reintroducing the very front-running window the batch function was built to close. This increases the likelihood that bad debt escapes socialization or that liquidations are delayed, contributing to protocol insolvency risk, which falls under the in-scope "protocol insolvency" impact category.

### Likelihood Explanation
This requires no special privilege — any ordinary user (a liquidator, or an attacker crafting many simultaneously-liquidatable positions) can call the public `liquidate-multi` entry point with a maximal-size positions list. The likelihood of hitting the worst case scales with market volatility (many underwater positions with fully drained collateral simultaneously), which is precisely the scenario in which this batch function is intended to be relied upon.

### Recommendation
Benchmark the actual runtime/read/write cost of `liquidate` in its worst case (full collateral list length, full debt list requiring socialization) and cap `liquidate-multi`'s list length (or reduce it from 64) so that the aggregate worst-case cost of a full batch stays safely under the network's per-block cost limits. Alternatively, require batches to be split client-side and document/enforce a safe maximum, and add on-chain guards (e.g., limiting number of positions that can trigger socialization within one call) so the function cannot silently become unmineable.

### Proof of Concept
1. Note that `liquidate-multi` accepts up to 64 `positions` and maps `call-liquidate` (→ `liquidate`) over each: [1](#0-0) .
2. Observe that each `liquidate` call, when the borrower's collateral is fully removed, performs an additional inner `fold socialize-debt-asset` over the borrower's debt list, each entry issuing 3 further contract-calls/map-writes: [5](#0-4) , [3](#0-2) .
3. Construct (or wait for market conditions to naturally produce) 64 positions that are all simultaneously liquidatable and each fully drain the borrower's collateral, forcing socialization for each. Submit them together via `liquidate-multi`.
4. If the combined runtime/read/write cost of processing all 64 positions (each with its own nested socialization loop) exceeds the Stacks network's per-block cost limits, the transaction cannot be mined by any node regardless of fee, and the atomic batch-liquidation protection becomes permanently unusable for large-enough legitimate use cases — forcing fallback to non-atomic sequential `liquidate` calls that reopen the front-running window the function claims to close.

(define-private (socialize-debt-asset
                (debt-entry { aid: uint, scaled: uint })
                (acc { borrower: principal, success: bool }))
  ;; Early return if previous socialization failed
  (if (not (get success acc))
      acc
      (let ((borrower (get borrower acc))
            (failed-status { borrower: borrower, success: false })
            (asset-id (get aid debt-entry))
            (scaled-debt (get scaled debt-entry)))

            ;; Socialize in vault - pass scaled directly to avoid rounding
            (unwrap! (vault-socialize-debt asset-id scaled-debt) failed-status)
            ;; Refresh cache with new indexes post-write-down (lindex decreased)
            (map-set index-cache
                     { timestamp: stacks-block-time, aid: asset-id }
                     (unwrap! (vault-accrue asset-id) failed-status))
            ;; Remove from obligation
            (unwrap! (contract-call? .v0-market-vault
                                      debt-remove-scaled
                                      borrower
                                      scaled-debt
                                      asset-id) failed-status)
          acc)
        ))
