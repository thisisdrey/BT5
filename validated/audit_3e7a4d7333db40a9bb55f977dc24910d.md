### Title
Permissionless `deposit(amount_, onBehalfOf_)` lets an attacker fill a victim's `depositTokensOfAccount` set with dust positions, permanently reverting all future deposits of new collateral types to the victim — ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
The CVE is a crash/DoS induced by a single malicious input (a crafted RPC packet causes a null-dereference crash). The Metronome analog is an attacker-induced persistent revert: `DepositToken.deposit` credits an arbitrary `onBehalfOf_` account and adds the deposit token to that account's `depositTokensOfAccount` set via `Pool.addToDepositTokensOfAccount`, which enforces a per-account cap (`onlyIfAdditionWillNotReachMaxTokens`). By depositing dust of every listed collateral to a victim, an attacker fills the victim's set to the cap, after which every `_mint`/`_transfer` of a not-yet-held deposit token to the victim reverts inside `addToDepositTokensOfAccount`, DoS-ing deposits (and incoming msdToken transfers) for that account.

### Finding Description
`DepositToken.deposit` accepts any `onBehalfOf_` address with no opt-in and mints msdTokens to it:

- `DepositToken.deposit` mints to `onBehalfOf_` (`_mint(onBehalfOf_, _deposited)`).
- `_mint` calls `pool.addToDepositTokensOfAccount(account_)` on first receipt (DepositToken.sol:485-488).
- `Pool.addToDepositTokensOfAccount` is gated by `onlyIfAdditionWillNotReachMaxTokens(account_)` and reverts once the account's set is full (Pool.sol:216-220).
- `_transfer` performs the same addition for first-time recipients (DepositToken.sol:517-520), so even plain ERC20 transfers of a new msdToken to the victim revert once the set is full.

Attack path (unprivileged EOA, no privileged roles needed):

1. Attacker acquires a dust amount of each underlying collateral (e.g. 1 wei of each listed collateral), approves each `DepositToken`, and calls `depositToken.deposit(1, victim)` for every deposit token registered in `Pool.depositTokens`.
2. Each call adds one entry to `depositTokensOfAccount[victim]` until it reaches `MAX_TOKENS_PER_USER` / the configured cap.
3. From then on, any `deposit(..., victim)` for a collateral the victim does not already hold reverts in `Pool.addToDepositTokensOfAccount`, and any `transfer`/`transferFrom`/`seize`-driven `_transfer` of a new msdToken to the victim reverts identically.
4. Only the victim can recover, by fully withdrawing or transferring one collateral type to zero so `removeFromDepositTokensOfAccount` frees a slot — but the attacker can simply re-fill the freed slot with another dust deposit, keeping the victim saturated.

`SynthContext._msgSender`, `onlyIfDepositTokenExists`, `whenNotPaused`, and `nonReentrant` do not stop this — every call is a legitimate deposit. `VesperGateway.deposit(pool_, vToken_, amount_)` and `NativeTokenGateway.deposit(pool_)` are also attacker-usable wrappers that reach the same `_mint` → `addToDepositTokensOfAccount` path, so the attacker does not even need to touch `DepositToken` directly.

### Impact Explanation
Liveness/availability break analogous to the CVE's crash: after the attack, the victim cannot deposit any collateral type they don't already hold, cannot receive any new msdToken by transfer, and cannot be onboarded to newly added collaterals. If the victim currently has zero positions (fresh account), they are fully blocked from using the protocol — a temporary freezing of their deposit ability that persists indefinitely because the attacker can re-saturate freed slots for near-zero cost (each dust deposit costs only gas plus a 1-wei underlying transfer to Treasury). SmartFarmingManager leverage flows that mint collateral to a user (`_mint(onBehalfOf_)` via `deposit`) are also DoS-able for new collateral types.

### Likelihood Explanation
Fully permissionless: `deposit` is public, `onBehalfOf_` is arbitrary, dust amounts are accepted (only `amount_ == 0` is rejected), and there is no minimum-deposit check or per-account opt-in. The attack requires only gas and negligible collateral value. It does not depend on governance settings, oracle manipulation, flash loans, or trusted infrastructure — only on the per-account token-list cap existing in the deployed configuration (the `onlyIfAdditionWillNotReachMaxTokens` modifier is present in current `Pool.sol` and in deployed bytecode via `MAX_TOKENS_PER_USER`). Note: impact is a deposit/transfer DoS rather than theft; it is the strongest reachable analog to a crash-on-malicious-input bug class in this codebase.

### Recommendation
- Do not add collateral entries to a user's `depositTokensOfAccount` for unsolicited deposits/transfers below a meaningful minimum, or require `onBehalfOf_ == _msgSender()` unless the beneficiary opts in (e.g., an allowlist/claim pattern).
- Alternatively, track the account's collateral set off balances rather than reverting on insertion: keep the cap only for debt positions, or make `addToDepositTokensOfAccount` a no-op-on-full combined with iterating `depositTokens` lazily.
- Reclaim-freeing symmetry: skip re-adding tokens whose balance contribution is dust by enforcing a minimum mint amount in `_mint`/`_transfer` before calling `pool.addToDepositTokensOfAccount`.

### Proof of Concept
Hardhat/Foundry fork sketch (mainnet fork, using deployed `Pool`, `PoolRegistry`, and any listed `DepositToken` e.g. msd-WETH):

```solidity
// SPDX-License-Identifier: MIT
pragma solidity 0.8.24;

import "forge-std/Test.sol";
import {IPool} from "contracts/interfaces/IPool.sol";
import {IDepositToken} from "contracts/interfaces/IDepositToken.sol";
import {IERC20} from "contracts/dependencies/openzeppelin/token/ERC20/IERC20.sol";

contract DepositListGriefTest is Test {
    IPool pool = IPool(POOL_ADDR);
    address victim = address(0xBEEF);
    address attacker = address(this);

    function test_FillVictimDepositList() public {
        address[] memory tokens = pool.getDepositTokens();

        // 1) Attacker dust-deposits every deposit token to `victim`
        for (uint256 i; i < tokens.length; ++i) {
            IDepositToken dt = IDepositToken(tokens[i]);
            if (pool.getDepositTokensOfAccount(victim).length == CAP) break;
            IERC20 underlying = IERC20(dt.underlying());
            deal(address(underlying), attacker, 1);
            underlying.approve(address(dt), 1);
            // skips tokens that would push victim over cap by design of modifier
            dt.deposit(1, victim);
        }

        // 2) Now any deposit of a NOT-yet-held collateral to victim reverts
        IDepositToken newDt = IDepositToken(tokens[0]); // pick one victim doesn't hold
        IERC20 u = IERC20(newDt.underlying());
        deal(address(u), attacker, 1e18);
        u.approve(address(newDt), 1e18);
        vm.expectRevert(); // MaxTokensPerUserReached inside addToDepositTokensOfAccount
        newDt.deposit(1e18, victim);

        // 3) Same for an ERC20 transfer of a new msdToken to the victim
        //    (sender holding a different msdToken type cannot send it to victim)
    }
}
```

Expected: step 2 reverts in `Pool.addToDepositTokensOfAccount` (`onlyIfAdditionWillNotReachMaxTokens`), and remains reverted until the victim zeroes a collateral position, after which the attacker can refill the slot with another dust `deposit`.
