### Title
NullPointerException on delegated-resource capsule with no backing store during UnDelegateResource execution - (File: actuator/src/main/java/org/tron/core/actuator/UnDelegateResourceActuator.java)

### Summary
`UnDelegateResourceActuator.execute()` fetches the "unlock" `DelegatedResourceCapsule` from `DelegatedResourceStore` and immediately dereferences it without a null check, exactly mirroring the kernel bug class in CVE‑2025‑21990 where a BO's backing store (`bo->tbo.resource`) can legitimately be `NULL` (PRT/sparse BOs) yet is dereferenced unconditionally when computing PTE flags. Here the "resource" object (`unlockResource`) can legitimately be absent for a delegation relationship even though `validate()` allows the transaction to proceed based on a *different* capsule (`lockResourceCapsule`).

### Finding Description
In `execute()`: [1](#0-0) 

```
delegatedResourceStore.unLockExpireResource(ownerAddress, receiverAddress,
    dynamicStore.getLatestBlockHeaderTimestamp());

byte[] unlockKey = DelegatedResourceCapsule
    .createDbKeyV2(ownerAddress, receiverAddress, false);
DelegatedResourceCapsule unlockResource = delegatedResourceStore
    .get(unlockKey);

// modify owner Account
AccountCapsule ownerCapsule = accountStore.get(ownerAddress);
switch (unDelegateResourceContract.getResource()) {
  case BANDWIDTH: {
    unlockResource.addFrozenBalanceForBandwidth(-unDelegateBalance, 0);
```

`unlockResource` is fetched via `delegatedResourceStore.get(unlockKey)` — a store lookup that returns `null` when no such key exists — and is dereferenced immediately in both the `BANDWIDTH` and `ENERGY` branches (`unlockResource.addFrozenBalanceForBandwidth(...)`, `unlockResource.addFrozenBalanceForEnergy(...)`) with no null guard.

Crucially, `validate()` does not guarantee `unlockResource` will exist. It only requires that *either* the unlock capsule *or* the lock capsule is present: [2](#0-1) 

An owner who only ever delegated resources with `lock = true` (never with `lock = false`) will have `unlockResourceCapsule == null` and only `lockResourceCapsule` populated. If that lock has since expired (`lockResourceCapsule.getExpireTimeForBandwidth() < now`), `validate()` happily accepts the transaction using the *locked* capsule's balance, while `execute()` still unconditionally does `delegatedResourceStore.get(unlockKey)` and dereferences the result. Whether `unLockExpireResource()` (in `chainbase/src/main/java/org/tron/core/store/DelegatedResourceStore.java`) is guaranteed to materialize an unlock-side capsule in every such case could not be fully confirmed within the available tooling — this is the one open question in this analysis — but the `execute()` code as written performs the dereference with no defensive null check, which is itself the structural analog of the reported bug class (an "optional/absent backing object" dereferenced without verification).

### Impact Explanation
If `unlockResource` is `null` at this point, the actuator throws an unhandled `NullPointerException` while executing a broadcast transaction (`UnDelegateResourceContract`) inside block/transaction application (`Manager`/`RuntimeImpl` → `ActuatorCreator` → `Actuator.execute`). An uncaught NPE during transaction execution is not converted to a `ContractExeException` here (unlike the try/catch used for `InvalidProtocolBufferException`), so it can propagate up and crash or halt block processing on every node that must replay/apply the same block, matching the "node crash or halt" impact accepted by this analog process.

### Likelihood Explanation
An unprivileged account can construct the required on-chain state (delegate only with `lock=true`, wait for the lock to expire, then unDelegate) purely through public, unprivileged `DelegateResourceContract`/`UnDelegateResourceContract` transactions — no special privileges, SR/witness status, or peer access are required, satisfying the "single signed transaction" reachability bar for this analog process. The exact triggering condition (whether `unLockExpireResource` always creates the unlock capsule) is unverified due to index limitations, which lowers confidence but does not eliminate the structural absence of a null check at the dereference site.

### Recommendation
Add a null check for `unlockResource` (and mirror it for the analogous `DelegateResourceActuator`/`UnDelegateResourceProcessor` VM native-contract paths) before calling `addFrozenBalanceForBandwidth`/`addFrozenBalanceForEnergy`, e.g. lazily construct a new `DelegatedResourceCapsule` when the store lookup returns `null`, consistent with how `DelegateResourceProcessor.delegateResource()` already guards this same scenario.

### Proof of Concept
1. Account A calls `DelegateResourceContract` with `lock=true` to delegate BANDWIDTH to account B (never issues a `lock=false` delegation to B).
2. Wait until `lockPeriod` expires so `lockResourceCapsule.getExpireTimeForBandwidth() < now`.
3. Account A calls `UnDelegateResourceContract` to un-delegate from B for BANDWIDTH. `validate()` passes because `lockResourceCapsule` alone satisfies the balance check.
4. In `execute()`, `delegatedResourceStore.get(unlockKey)` returns `null` (no prior `lock=false` delegation ever created that key) and `unlockResource.addFrozenBalanceForBandwidth(...)` throws `NullPointerException`, aborting/crashing transaction execution for any node applying this transaction.

Note: full confirmation that `unLockExpireResource()` does not itself create the missing unlock-side capsule under this specific condition requires reading `chainbase/src/main/java/org/tron/core/store/DelegatedResourceStore.java`, which was not fully retrievable within tool limits — a Devin session with full repository access should verify this method before treating the PoC as conclusively reproducible.
