### Title
No slippage protection on `ExchangeWithdrawContract` liquidity withdrawal, enabling sandwich extraction of the exchange creator's funds - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
`ExchangeWithdrawContract` lets an exchange (bancor-style TRC10 AMM pool) creator withdraw `tokenQuant` of one side of the pool and receive a proportional amount of the other side, computed from the *current* pool ratio at execution time. Unlike `ExchangeTransactionContract`, which carries an `expected` field enforced in `doValidate()`, `ExchangeWithdrawContract` has no minimum-output parameter at all, so the creator has no way to bound how much of the paired token they will actually receive.

### Finding Description
`ExchangeWithdrawContract` only carries `owner_address`, `exchange_id`, `token_id`, and `quant` — there is no `expected`/minimum field, in contrast to `ExchangeTransactionContract` which explicitly has `expected` for this exact purpose. [1](#0-0) 

In `ExchangeWithdrawActuator.execute`, `anotherTokenQuant` (the amount of the other token returned to the creator) is derived purely from the pool's live `firstTokenBalance`/`secondTokenBalance` ratio at the moment of execution: [2](#0-1) 

`doValidate()` recomputes the same ratio-based `anotherTokenQuant` and only checks pool sufficiency and a fixed precision-rounding bound (`0.0001` relative tolerance) — never a user-specified minimum: [3](#0-2) 

This is the same root cause class as the referenced Dopex report: the amount a user receives for a fixed input depends on mutable on-chain state (pool balances) that can shift between transaction submission and block inclusion, and the contract provides no parameter to cap the acceptable slippage. Any other account can call `ExchangeTransactionContract` against the same `exchange_id` to move `firstTokenBalance`/`secondTokenBalance` before the withdraw transaction lands (front-run), altering the ratio the withdrawer will receive, and then trade back afterward (back-run) to restore price and capture the difference — a classic sandwich against the withdrawal, since `ExchangeTransactionActuator.execute` mutates the same shared `ExchangeCapsule` balances used by the withdraw calculation: [4](#0-3) 

### Impact Explanation
The exchange creator withdrawing liquidity can receive materially less of the paired token than the pool ratio implied when they built/signed the transaction, because an attacker can manipulate the pool ratio via ordinary, permissionless `ExchangeTransactionContract` calls immediately before the withdrawal is packed into a block, and reverse the trade afterward. This is a direct, unauthorized value-extraction path (sandwich) against a signed transaction with no way for the victim to protect themselves, matching the "unbacked/loss of funds" impact bar via a single crafted pair of `ExchangeTransactionContract` transactions surrounding the victim's `ExchangeWithdrawContract`.

### Likelihood Explanation
Both the manipulating trade and the reversing trade use the standard, unprivileged `ExchangeTransactionContract` path, callable by any account holding the relevant TRC10/TRX balance, with no special permission needed beyond being the pool creator for the withdraw side. Ordering within a block (transaction position) is attacker-influenced in practice (fee/witness inclusion ordering), making the sandwich practically constructible whenever a withdraw is broadcast to the mempool.

### Recommendation
Add a `expected`/minimum-output field to `ExchangeWithdrawContract` (mirroring `ExchangeTransactionContract.expected`) and enforce it in `ExchangeWithdrawActuator.doValidate()`/`execute()` so the withdrawer can bound the minimum amount of the paired token they are willing to accept, rejecting the transaction if the computed `anotherTokenQuant` falls below that bound.

### Proof of Concept
1. Attacker observes a pending `ExchangeWithdrawContract` from the pool creator withdrawing `tokenQuant` of `firstTokenID` from exchange `X`.
2. Attacker submits an `ExchangeTransactionContract` selling a large amount of `secondTokenID` into exchange `X`, executed via `ExchangeTransactionActuator.execute`, shifting `firstTokenBalance`/`secondTokenBalance` unfavorably for the pending withdrawal's implied ratio. [5](#0-4) 
3. The victim's withdrawal executes next, computing `anotherTokenQuant` from the now-skewed ratio via the unchanged formula in `ExchangeWithdrawActuator.execute`, with no `expected` guard to reject an unfavorable result. [6](#0-5) 
4. Attacker submits a reversing `ExchangeTransactionContract` trade to restore the pool ratio, having profited from the price impact captured out of the victim's withdrawal.
