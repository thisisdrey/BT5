### Title
Blacklisted account cannot claim accrued rewards via permissionless `claimRewards`, reverting the push transfer - (File: contracts/RewardsDistributor.sol)

### Summary
`RewardsDistributor.claimRewards` is permissionless — anyone can trigger a claim for any account, and the function pushes `rewardToken` directly to the target account via `safeTransfer`. If the configured `rewardToken` is a blacklistable ERC20 (e.g., USDC) and the account is blacklisted, the transfer reverts and the claim can never complete while the account is blacklisted — mirroring the Notional `settleVaultAccount` bug where a push transfer inside a permissionless flow is bricked by a token blacklist.

### Finding Description
`claimRewards(address[] accounts_, IERC20[] tokens_)` at `contracts/RewardsDistributor.sol:150` iterates over accounts and calls `_transferRewardIfEnoughTokens(account_, tokensAccruedOf[account_])` for each. That function executes:

```solidity
// contracts/RewardsDistributor.sol:248
tokensAccruedOf[account_] = 0;
_rewardToken.safeTransfer(account_, amount_);
```

There is no recipient parameter — the reward token is always pushed to `account_`. The `rewardToken` is set once in `initialize` (`contracts/RewardsDistributor.sol:103`) and can be any ERC20 the governor chooses, including blacklistable tokens such as USDC.

When `account_` is on the reward token's blacklist:
- The `safeTransfer` reverts, reverting the entire call (including all index/accrual state updates for every account in the batch, since it's one transaction).
- Because `claimRewards` pushes to the account rather than letting the account specify a fresh, non-blacklisted recipient, the account has no way to route around the blacklist — unlike `DepositToken.withdraw(uint256,address to_)` (`contracts/DepositToken.sol:406`), which lets the caller choose a recipient.

The same push-pattern does not exist in liquidation: `Pool.liquidate` (`contracts/Pool.sol:543`) seizes `DepositToken` shares (internal accounting, not blacklistable) to the liquidator and pulls the synthetic repayment from the liquidator, so it is not affected. `RewardsDistributor.claimRewards` is the reachable surface for this bug class.

### Impact Explanation
Temporary freezing of unclaimed yield: a blacklisted user's accrued rewards (`tokensAccruedOf[account]` plus index accrual) become unclaimable for as long as the account remains blacklisted. Nobody — not the user, not a keeper, not a relayer — can complete the claim, because the recipient is hardcoded to the blacklisted account. Rewards are not lost (state updates revert atomically), but they are frozen. If the reward token blacklist is never lifted, the freeze is effectively permanent for that account.

### Likelihood Explanation
Requires the pool to run a `RewardsDistributor` whose `rewardToken` is a blacklistable asset (USDC is a realistic reward token) and a depositor/borrower to be blacklisted by the token issuer. Both conditions are external to the attacker but are plausible in production, matching the Notional report's premise. No privileged role is needed to observe the failure — any caller invoking `claimRewards` for the account hits the revert.

### Recommendation
Let the reward recipient be specified, or accrue-and-let-pull: add a `claimRewards(address account_, address to_)` variant, or allow the account (or an authorized party) to redirect the payout. Alternatively, wrap the `safeTransfer` in a try/catch so a failed transfer leaves `tokensAccruedOf` intact but does not revert the rest of the batch — at minimum preventing one blacklisted account from reverting claims for other accounts batched in the same `claimRewards(address[],IERC20[])` call.

### Proof of Concept
Hardhat fork sketch:

1. Deploy/attach `RewardsDistributor` initialized with USDC as `rewardToken`; register a `DepositToken` via `updateTokenSpeed` so index accrual runs.
2. Alice deposits, accrues rewards (advance time; `claimable(alice)` > 0).
3. On the fork, use the USDC master-minter/blacklister slot to add Alice to the blacklist (or impersonate Circle's `blacklister` role and call `blacklist(alice)`).
4. Call `rewardsDistributor.claimRewards(alice.address)` from any EOA → reverts inside `_rewardToken.safeTransfer(account_, amount_)` at `contracts/RewardsDistributor.sol:253`.
5. Assert `claimable(alice)` remains > 0 and all claims revert, demonstrating the yield freeze.

Caveat: the impact is limited to the blacklisted account's own unclaimed yield — unlike Notional, Metronome has no settlement step that gates protocol-critical actions like liquidation, so there is no cross-user or protocol-liveness impact.
