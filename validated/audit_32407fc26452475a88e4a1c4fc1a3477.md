### Title
Relayed-handshake path bypasses `remote_allow_list` enforcement before any certificate is verified - (File: `handshake_manager.go`)

### Summary
Nebula's `lighthouse.remote_allow_list` is meant to restrict which underlay (UDP) source addresses may initiate a handshake toward a node, independent of any certificate content. In `HandleIncoming`, `beginHandshake`, and `continueHandshake`, this check is guarded by `if !via.IsRelayed`, so any packet path that sets `ViaSender.IsRelayed = true` skips the allow-list check entirely, at the exact point in the code before a certificate has been reconstructed or verified.

### Finding Description
The remote_allow_list check exists specifically to gate handshake initiation on the physical/underlay source address, as the very first line of defense in `HandleIncoming`: [1](#0-0) 

This is enforced again at continuation and post-verification stages: [2](#0-1) [3](#0-2) 

In every one of these three call sites, the check is entirely skipped — not weakened, but bypassed — whenever `via.IsRelayed` is true. This mirrors the ENS `wrapETH2LD` pattern precisely: a permission/trust mechanism scoped for one purpose (the `IsRelayed` flag exists so relay-forwarded traffic, whose `via.UdpAddr` is the relay's address rather than the true originator, isn't checked against the wrong address) is used as a blanket bypass of an unrelated authorization gate (the operator's configured IP allow-list for handshake initiation), rather than being scoped to only skip the specific check that no longer makes sense (comparing the wrong address) while still enforcing the policy's intent through another means (e.g., checking the relay's own address, or the ultimate claimed VPN address's applicability).

`ViaSender.IsRelayed` is attacker-influenced in the sense that it is set purely from packet routing metadata (`outside.go`), not from anything cryptographically tied to the peer's identity at the point these checks run: [4](#0-3) 

Since `beginHandshake` is where a *brand new, unauthenticated* handshake (stage-0) is first processed — before `validatePeerCert` or `certVerifier` have run to trust anything about the sender — the `IsRelayed`-gated skip at `HandleIncoming` line 165 operates purely on unauthenticated routing metadata, exactly analogous to the ENS bug where a permission granted for one narrow purpose (wrapper-level approval / relay-forwarding routing) was allowed to satisfy a broader, unrelated authorization check (arbitrary domain wrapping / IP-based handshake admission).

### Impact Explanation
An operator who configures `lighthouse.remote_allow_list` to restrict handshake-initiating source IPs (e.g., to block untrusted networks or enforce network segmentation) loses that protection for any handshake or roaming update that arrives tagged as relayed. Because the relayed path is reachable by any node that can get itself treated as "am_relay" traffic in the local routing metadata before certificate verification occurs, this weakens a firewall/handshake-authentication control that the ENS-style report class targets: a broad, unintended extension of one trust scope (relay routing) into another (source-IP admission control), with no compensating check that the *effective* source is still covered by the intended policy.

### Likelihood Explanation
The bypass is unconditional and triggers on every packet where `via.IsRelayed` is set, which happens on every relay-routed message by design (`outside.go`, `handleOutsideRelayPacket`). Any environment using `use_relays`/`am_relay` and simultaneously depending on `remote_allow_list` for handshake admission control is affected without any special conditions or timing needed — this is a systemic condition, not a race.

### Recommendation
Do not use `via.IsRelayed` as a blanket exemption from `remote_allow_list`. Instead, either: (1) apply the allow-list check against the relay's own verified address/VPN identity when relayed, so the policy intent ("who may cause a handshake to be admitted") is still enforced through the relay's own trust relationship, or (2) explicitly document and gate this behavior behind an operator-opt-in setting (e.g., `relay.trust_relayed_handshakes`) rather than making it implicit and unconditional, mirroring the ENS recommendation to remove the over-broad permission clause rather than leave two independent trust paths silently OR'd together.

### Proof of Concept
1. Configure a node `me` with `lighthouse.remote_allow_list` denying all source IPs except a narrow allowed range (as in `TestHandshakeRemoteAllowList`, `e2e/handshake_manager_test.go` lines 351–408) — confirming the non-relayed path is enforced.
2. Establish `me` as reachable through a relay node with `relay.am_relay: true` (as in `TestHandshakeRelayComplete`, `e2e/handshake_manager_test.go` lines 521–568).
3. Have a third node send a handshake through the relay from a source address that would be denied by `remote_allow_list` if received directly.
4. Because `readOutsidePackets` sets `via.IsRelayed = true` for the inner packet before invoking `f.handshakeManager.HandleIncoming` (see `outside.go` lines 195–205), the `HandleIncoming` remote_allow_list gate at `handshake_manager.go` lines 165–170 is skipped, and the handshake proceeds to `beginHandshake`/`continueHandshake` despite the underlying policy intent to block it.
