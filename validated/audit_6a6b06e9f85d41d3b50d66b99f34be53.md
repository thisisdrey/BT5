Based on the investigation, I found a concrete analog in java-tron: an unbounded list-growth pattern with no cap enforcement, directly comparable to the Sherlock report's core issue (a hard cap that the code assumes is enforced elsewhere but never actually is, allowing repeated legitimate transactions to blow past it and create unrecoverable growth that later breaks a downstream operation).

### Title
Unbounded growth of `DelegatedResourceAccountIndexCapsule.toAccounts`/`fromAccounts` lists with no maximum-size check - (File: `actuator/src/main/java/org/tron/core/actuator/FreezeBalanceActuator.java`)

### Summary
`FreezeBalanceActuator.delegateResource()` appends a new receiver/owner address into the `toAccountsList`/`fromAccountsList` of a single `DelegatedResourceAccountIndexCapsule` protobuf record every time an account delegates bandwidth/energy to a *new* address, and this happens with **no check on the resulting list size**. Just as the Sherlock report's `depositETHIntoMultipleRounds` never verifies that appending to the *next* round's deposit count stays within `MAXIMUM_NUMBER_OF_DEPOSITS_PER_ROUND`, this code never verifies that appending to the index list stays within any bound before writing it back to the store.

### Finding Description
In the legacy (non-optimized) delegation-index path, `delegateResource()` reads the owner's `DelegatedResourceAccountIndexCapsule`, checks only whether the specific receiver address is *already* present, and if not, unconditionally appends it: [1](#0-0) 

There is no maximum count enforced anywhere in `FreezeBalanceActuator.validate()` (lines 187-241) or in `delegateResource()` on the size of `toAccountsList` / `fromAccountsList`. The capsule itself provides only unconditional `addToAccount`/`addFromAccount` methods with no bound check: [2](#0-1) 

The corresponding existing test confirms the list is allowed to grow arbitrarily (100+ entries added with no error), proving there is no validation gate preventing unbounded growth, exactly as in the reported bug where the "current round" cap check never protects the "future round" state that eventually becomes current: [3](#0-2) 

This differs qualitatively from `UnfreezeBalanceV2Actuator`, which *does* correctly bound its analogous list (`UnFreezeV2`) via an explicit `UNFREEZE_MAX_TIMES` check before insertion: [4](#0-3) 
That contrast highlights that the pattern used for `DelegatedResourceAccountIndexCapsule` omits the bound check that the analogous, newer code path considers mandatory — precisely the class of bug flagged in the report (a hard cap assumed but not actually enforced on a per-entity cumulative list).

### Impact Explanation
Every `FreezeBalanceContract` transaction delegating resources to a new, distinct receiver address permanently grows the owner's (and the receiver's) `DelegatedResourceAccountIndexCapsule` record by one entry, with the entire record read and rewritten (`get`/`put`) as a whole on every subsequent freeze/unfreeze/delegate call touching that account: [5](#0-4) 
Because the fee for this operation is fixed at 0 (`calcFee()` returns 0) and does not scale with list size, an attacker can cheaply grow this record to an arbitrarily large size across many transactions. Once large enough, any operation touching that account (including read paths that serialize/deserialize the whole capsule, or RPC/API calls that expose `DelegatedResourceAccountIndex`) becomes increasingly expensive, ultimately risking degraded processing time or an inability of the node to serve requests involving that account/list — a resource-exhaustion condition on a widely-reachable, unprivileged transaction path.

### Likelihood Explanation
This path exists only when `DynamicPropertiesStore.supportAllowDelegateOptimization()` is false, i.e. the legacy (pre-optimization) delegated-resource-index mode is still active on the given network/config. On networks/config where this optimization has not been activated, the path is fully reachable by any account with a minimal frozen balance issuing repeated `FreezeBalanceContract` transactions to many distinct receiver addresses — no special privileges are required.

### Recommendation
Enforce an explicit maximum size on `toAccountsList`/`fromAccountsList` in `DelegatedResourceAccountIndexCapsule.addToAccount`/`addFromAccount` (or in `FreezeBalanceActuator.validate()`/`delegateResource()`), analogous to the `UNFREEZE_MAX_TIMES` bound already used for `UnFreezeV2`, and reject transactions that would cause the list to exceed that bound before writing it back to the store.

    AccountStore accountStore = chainBaseManager.getAccountStore();

    DelegatedResourceStore delegatedResourceStore = chainBaseManager.getDelegatedResourceStore();

    DelegatedResourceCapsule delegatedResourceCapsule = delegatedResourceStore
        .get(key);
    if (delegatedResourceCapsule != null) {
      if (isBandwidth) {
        delegatedResourceCapsule.addFrozenBalanceForBandwidth(balance, expireTime);
      } else {
        delegatedResourceCapsule.addFrozenBalanceForEnergy(balance, expireTime);
      }

      delegatedResourceCapsule = new DelegatedResourceCapsule(
          ByteString.copyFrom(ownerAddress),

      } else {
        delegatedResourceCapsule.setFrozenBalanceForEnergy(balance, expireTime);
      }

    delegatedResourceStore.put(key, delegatedResourceCapsule);

    //modify DelegatedResourceAccountIndexStore
    if (!dynamicPropertiesStore.supportAllowDelegateOptimization()) {

      DelegatedResourceAccountIndexCapsule ownerIndexCapsule =
          delegatedResourceAccountIndexStore.get(ownerAddress);

            ByteString.copyFrom(ownerAddress));
      }
      List<ByteString> toAccountsList = ownerIndexCapsule.getToAccountsList();

            ByteString.copyFrom(receiverAddress));
      }

          .getFromAccountsList();
      if (!fromAccountsList.contains(ByteString.copyFrom(ownerAddress))) {
        receiverIndexCapsule.addFromAccount(ByteString.copyFrom(ownerAddress));
      }
      delegatedResourceAccountIndexStore.put(receiverAddress, receiverIndexCapsule);

      delegatedResourceAccountIndexStore.convert(ownerAddress);

      delegatedResourceAccountIndexStore.delegate(ownerAddress, receiverAddress,

  public void addFromAccount(ByteString fromAccount) {
    this.delegatedResourceAccountIndex = this.delegatedResourceAccountIndex.toBuilder()
        .addFromAccounts(fromAccount)
        .build();
  }

  public void removeFromAccount(ByteString fromAccount) {
    if (getFromAccountsList().contains(fromAccount)) {
      List<ByteString> fromList = new ArrayList<>(getFromAccountsList());
      fromList.remove(fromAccount);
      setAllFromAccounts(fromList);
    }
  }

  public List<ByteString> getToAccountsList() {
    return this.delegatedResourceAccountIndex.getToAccountsList();
  }

  public void setAllToAccounts(List<ByteString> toAccounts) {
    this.delegatedResourceAccountIndex = this.delegatedResourceAccountIndex.toBuilder()
        .clearToAccounts()
        .addAllToAccounts(toAccounts)
        .build();
  }

  public void addToAccount(ByteString toAccount) {
    this.delegatedResourceAccountIndex = this.delegatedResourceAccountIndex.toBuilder()
        .addToAccounts(toAccount)
        .build();
  }
