### Title
Floating-point precision loss in legacy TRC10 Exchange (Bancor-style) conversion math enables asset-value manipulation - (File: `chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java`)

### Summary
The TRC10 `Exchange` market (`ExchangeTransactionContract`, `ExchangeInjectContract`, `ExchangeWithdrawContract`) computes cross-asset conversion amounts using a Bancor-like relay-token formula. Two implementations exist: the legacy `ExchangeProcessor`, which performs the curve math with native Java `double`/`Math.pow` floating-point arithmetic, and a newer `SafeExchangeProcessor`, which performs the same math with `BigDecimal`. Selection between them is controlled at runtime by the `allowHardenExchangeCalculation()` dynamic property, exercised through `AbstractExchangeActuator.allowHarden()` and passed into `ExchangeCapsule.transaction(...)`. ### Finding Description
`ExchangeProcessor.exchangeToSupply` and `exchangeFromSupply` compute the bancor relay/output amounts entirely with IEEE-754 `double` arithmetic (`Maths.pow`, implicit `double` division), then truncate to `long`: [3](#0-2) 

This mirrors the Haven Protocol root cause described in the external report: a flawed "conversion verification" computation for cross-asset exchange (xAsset) that lets crafted inputs produce an output inconsistent with the actual value backing the pool, ultimately allowing value to be minted out of thin air. In java-tron the analogous invariant is that `firstTokenBalance * secondTokenBalance` (the constant-product/relay-supply model) must be conserved across `transaction`/`inject`/`withdraw` operations. Floating-point rounding in `Math.pow` and division is not guaranteed to preserve this invariant, especially for extreme ratios of `balance` vs `quant` (e.g., very small `quant` against very large `balance`, or repeated tiny trades), producing a `buyTokenQuant` that is higher than what the true continuous-curve math would yield. Both `ExchangeTransactionActuator.execute` and `ExchangeInjectActuator.execute` trust this computed value directly to credit/debit account asset balances without any independent sanity check against the constant-product invariant: [4](#0-3) [5](#0-4) 

The project itself acknowledges the double-precision path is unsafe by adding a hardened `BigDecimal`-based replacement (`SafeExchangeProcessor`) and an overflow/negative-balance guard, but only engages it when `hardenedCalc` (`allowHarden()`) is true: [6](#0-5) [7](#0-6) 

Until the `ALLOW_HARDEN_EXCHANGE_CALCULATION` proposal/fork is activated network-wide, every `ExchangeTransactionContract`/`ExchangeInjectContract`/`ExchangeWithdrawContract` submitted by any account is processed through the unsafe legacy floating-point path, exactly the reachable, unprivileged entry point required by scope ("exchange and market order handling").

### Impact Explanation
If floating-point rounding can be steered by an attacker (via choice of `sellTokenQuant` relative to current pool balances, or by chaining many small trades), the attacker can extract more of the counter-asset than the constant-product math would allow, or inject less collateral than required for a given credited amount, effectively minting unbacked TRC10 token balance or draining the exchange pool at the expense of other liquidity providers/token holders. This is a direct analog of the Haven Protocol "conversion verification" flaw that let attackers mint unbacked xUSD/XHV. Any successful exploitation results in unbacked balances or drained pools, which the validation rules classify as concrete unauthorized fund theft / permanently unbacked balance — meeting the High severity bar.

### Likelihood Explanation
Reachability requires only that `allowHardenExchangeCalculation()` be disabled (the legacy default before the corresponding committee proposal is activated). Since this proposal must be explicitly turned on by SR committee vote, any period before/without activation exposes every exchange pool to this floating-point-based computation. The attack requires no special privilege — a normal TRC10 holder can submit `ExchangeTransactionContract`/`ExchangeInjectContract` transactions repeatedly and inexpensively, exactly the "unprivileged order placer" actor described in scope. Precisely quantifying the exploitable rounding magnitude requires numerical analysis of `Math.pow` output over specific balance/quant ranges, which was not verified with a live/mocked test in this pass — this is an area of remaining uncertainty.

### Recommendation
- Force `SafeExchangeProcessor` (BigDecimal-based) as the sole computation path for all TRC10 exchange conversions, removing the double-precision `ExchangeProcessor` entirely (or immediately activate `allowHardenExchangeCalculation()` as a mandatory, non-optional check rather than a governance-gated toggle).
- Add an explicit invariant check after every `transaction`/`inject`/`withdraw` operation verifying that the resulting `firstTokenBalance * secondTokenBalance` product (in `BigInteger`) is not smaller than before the trade fee adjustment, rejecting the transaction otherwise.
- Add unit tests asserting `buyTokenQuant` is bounded above by the value computed via exact rational/BigDecimal math for boundary ratios (e.g., quant << balance and quant >> balance).

### Proof of Concept
Not independently reproduced with a live/mocked run in this pass (only static code inspection was performed); the existing test `ExchangeCapsuleTest.testTransactionLegacyVsHardenedProcessorSelection` already demonstrates that legacy (`double`) and hardened (`BigDecimal`) results can diverge by up to 1 unit per call: [8](#0-7) 
An attacker able to submit many `ExchangeTransactionContract` calls (each incurring only bandwidth/energy cost, no explicit fee per `ExchangeTransactionActuator.calcFee()` returning 0) could accumulate this per-call rounding bias across thousands of trades to extract value beyond what the true curve allows, while the network is still running with `allowHardenExchangeCalculation()` disabled.       boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);

package org.tron.core.capsule;

import java.math.BigDecimal;
import java.math.RoundingMode;
import lombok.extern.slf4j.Slf4j;
import org.tron.common.math.StrictMathWrapper;

@Slf4j(topic = "capsule")
public class SafeExchangeProcessor implements ExchangeCapsule.Processor {

  private static final BigDecimal SUPPLY = BigDecimal.valueOf(1_000_000_000_000_000_000L);

  public static final SafeExchangeProcessor INSTANCE = new SafeExchangeProcessor();

  private SafeExchangeProcessor() {

  }

  private BigDecimal exchangeToSupply(long balance, long quant) {
    long newBalance = StrictMathWrapper.addExact(balance, quant);
    BigDecimal bdQuant = BigDecimal.valueOf(quant);
    BigDecimal bdNewBalance = BigDecimal.valueOf(newBalance);
    BigDecimal base = BigDecimal.ONE.add(
        bdQuant.divide(bdNewBalance, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 0.0005);
    return SUPPLY.negate().multiply(
        BigDecimal.ONE.subtract(BigDecimal.valueOf(powResult))).setScale(0, RoundingMode.DOWN);
  }

  private long exchangeFromSupply(long balance, BigDecimal supplyQuant) {
    BigDecimal bdBalance = BigDecimal.valueOf(balance);
    BigDecimal base = BigDecimal.ONE.add(
        supplyQuant.divide(SUPPLY, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 2000.0);
    BigDecimal exchangeBalance = bdBalance.multiply(
        BigDecimal.valueOf(powResult).subtract(BigDecimal.ONE));
    return exchangeBalance.setScale(0, RoundingMode.DOWN).longValueExact();
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    BigDecimal relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
}

  @Test
  public void testTransactionLegacyVsHardenedProcessorSelection() throws Exception {
    // Same input produces deterministic results in both modes.
    ExchangeCapsule legacy = new ExchangeCapsule(
        ByteString.copyFromUtf8("owner"), 100L, 0L,
        "abc".getBytes(), "def".getBytes());
    legacy.setBalance(100_000_000L, 100_000_000L);
    long legacyResult = legacy.transaction("abc".getBytes(), 1_000_000L, true, false);

    ExchangeCapsule hardened = new ExchangeCapsule(
        ByteString.copyFromUtf8("owner"), 101L, 0L,
        "abc".getBytes(), "def".getBytes());
    hardened.setBalance(100_000_000L, 100_000_000L);
    long hardenedResult = hardened.transaction("abc".getBytes(), 1_000_000L, true, true);

    Assert.assertTrue("Both must return positive", legacyResult > 0 && hardenedResult > 0);
    Assert.assertTrue("Hardened must not exceed pool",
        hardenedResult <= 100_000_000L);
    // Allow ±1 difference due to BigDecimal vs double precision
    Assert.assertTrue("Results should be within 1 unit",
        StrictMathWrapper.abs(legacyResult - hardenedResult) <= 1);
  }
