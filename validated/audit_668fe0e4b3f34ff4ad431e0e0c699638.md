### Title
Unbounded revert propagation in `Pool.addToDepositTokensOfAccount` lets an attacker fill a victim's collateral set to `MAX_TOKENS_PER_USER` and DoS all further deposits/transfers of new collateral - (contracts/Pool.sol)

### Summary
The external report concerns uncaught exceptional conditions crashing the caller. The Metronome analog is `Pool.addToDepositTokensOfAccount`: it reverts with `UserReachedMaxTokens` whenever the target account's combined debt+deposit token list reaches `MAX_TOKENS_PER_USER` (30) [1](#0-0) . This function is invoked by `DepositToken` whenever an account's balance changes from `0` [2](#0-1) . Because `DepositToken.transfer`/`transferFrom` are permissionless, an attacker can dust-transfer 1 wei of every listed deposit token to a victim, fill their `depositTokensOfAccount` set, and cause every subsequent deposit, transfer, or liquidation-seize path that would add a *new* token to revert — an exceptional condition propagated as a hard revert rather than handled.

### Finding Description
- `addToDepositTokensOfAccount(account_)` applies `onlyIfAdditionWillNotReachMaxTokens(account_)`, which counts `debtTokensOfAccount.length + depositTokensOfAccount.length` and reverts at 30 [1](#0-0) .
- `DepositToken` calls it whenever a balance moves off zero (per the natspec on lines 211–213), including on `deposit()` and on `transfer`/`transferFrom` to a new holder.
- The attacker deposits dust amounts of each of up to `MAX_TOKENS_PER_USER` deposit tokens and transfers them to the victim (or front-runs the victim's first deposits), filling the victim's set. Thereafter:
  - `deposit()` of any *new* collateral type reverts via the propagated `UserReachedMaxTokens`.
  - `transfer`/`transferFrom` of any token the victim doesn't already hold reverts.
  - `depositToken_.seize()` during liquidation of a token the liquidator doesn't already hold reverts in the same way [3](#0-2) .
- The exceptional condition is "handled" only by reverting, with no escape path: a victim cannot remove a token without zeroing its balance, which they may be unable or unwilling to do (e.g., zeroing debt positions requires full repayment).

### Impact Explanation
A victim whose account set is filled to 30 cannot add any new collateral. If their position approaches the liquidation threshold, they are denied the primary defense (depositing a different collateral asset) while `liquidate` remains callable against them [4](#0-3) . This is temporary freezing of the deposit/transfer liveness of the victim's position and can contribute to forced liquidation of otherwise rescuable collateral — a direct denial-of-service consequence analogous to the CVE's crash-on-crafted-input.

### Likelihood Explanation
Fully permissionless: the attacker needs only dust amounts of each deposit token (obtainable by depositing minimal underlying themselves). No privileged role, oracle manipulation, or governance action is required; `MAX_TOKENS_PER_USER` is a compile-time constant [5](#0-4) . Cost is bounded by gas for ~30 deposits/transfers. Note: the impact is capped because victims can still add collateral of token types already in their set, and seize-side reverts only matter if the liquidator also lacks the token — so severity is bounded, consistent with the Medium rating of the source advisory.

### Recommendation
In `addToDepositTokensOfAccount` / `addToDebtTokensOfAccount`, return `false` (or make `DepositToken`/`DebtToken` catch the revert) instead of reverting, so exceeding the cap skips tracking rather than blocking the transfer/deposit. Alternatively, count only the caller's own additions against the cap, or treat forced-inbound dust distinctly from user-initiated deposits.

### Proof of Concept
Hardhat/Foundry fork sketch:
1. Deploy/fork `Pool`, `PoolRegistry`, `MasterOracle`, and N `DepositToken`s; governor adds them via `addDepositToken` [6](#0-5) .
2. Attacker deposits dust underlying into each `DepositToken`, then calls `depositToken.transfer(victim, 1)` for each until `Pool.depositTokensOfAccount.length(victim) + debtTokensOfAccount.length(victim) == 30`.
3. Assert `victim` call to `depositToken_new.deposit(amount)` reverts with `UserReachedMaxTokens` [1](#0-0) .
4. Drive the victim's existing position unhealthy (price move on fork or accrued interest) and show `pool.liquidate(...)` succeeds while remediation via new collateral is impossible.

Caveat: I did not fully read `DepositToken.sol` in this session to confirm the exact call sites of `addToDepositTokensOfAccount` (deposit vs. transfer hooks); the natspec confirms it is invoked on 0→nonzero balance changes, but the PoC should verify each hook propagates the revert rather than swallowing it.
