## Analysis

**Binding under test:** `FEE_owed(single diff, amount=N) == FEE_collected(N split diffs, amount=1 each)`, where `FEE_owed = TokenDiff::token_fee(token_id, N, protocol_fee).fee_ceil(N)` and `FEE_collected = Σ_{i=1}^{N} TokenDiff::token_fee(token_id, 1, protocol_fee).fee_ceil(1)`.

Tracing `TokenDiff::token_fee`, for `TokenIdType::Nep245 | TokenIdType::Imt`, the fee is only applied `if amount > 1`; otherwise `Pips::ZERO` is returned unconditionally: [1](#0-0) 

This is invoked inside `TokenDiff::execute_intent`, where fee is computed and accumulated **per intent, per negative delta**, with no memory of prior intents in the same batch: [2](#0-1) 

Because the fee check only looks at `amount.unsigned_abs()` of a *single intent's* delta on that token, an attacker can split any bulk NEP-245/Imt transfer into N intents each with `delta = -1`, and each individually satisfies `amount == 1`, so `token_fee` returns `Pips::ZERO` for every one of them. The aggregate `fees_collected` across the batch is `0`, whereas a single `TokenDiff` with `delta = -N` (N > 1) would have paid `fee.fee_ceil(N) > 0` for nonzero `protocol_fee`.

There is no batch-level aggregation preventing this: `Engine::execute_signed_intents` processes each signed intent's `TokenDiff::execute_intent` independently, and the only cross-intent invariant enforced is the zero-sum balancing done by `TransferMatcher::finalize` — which checks that deltas net to zero across the batch, but has no visibility into or influence on fee computation: [3](#0-2) 

The counterparty side (whoever provides the balancing positive delta) only pays fees according to *their own* negative deltas on whatever token they give up — unrelated to the attacker's token_C fee, and if the counterparty's own token happens to be Nep141 there's no such `amount > 1` exemption (`TokenIdType::Nep141 => {}` always yields the full `fee` regardless of amount). But this does not remedy the attacker-side bypass on the NEP-245/Imt token being unit-split.

This matches the description in the code comment "do not take fees on NFTs and MTs with `|delta| <= 1`" — an intentional exemption meant for genuinely atomic NFTs/unique-MT items whose quantity can never exceed 1 in a single transfer. However, `TokenIdType::Nep245`/`Imt` can represent fungible-like multi-token balances with arbitrary integer amounts, so nothing prevents an attacker from repeatedly triggering the `amount == 1` exemption across N intents in one `MultiPayload` batch to move an arbitrarily large aggregate amount of that token while the total fee collected remains `0`.

### Title
Protocol fee on NEP-245/Imt tokens bypassed by splitting a bulk transfer into unit-amount `TokenDiff` intents - (`contracts/defuse/core/src/intents/token_diff.rs`)

### Summary
`TokenDiff::token_fee` waives protocol fees for `TokenIdType::Nep245`/`Imt` tokens whenever the per-intent delta magnitude is `<= 1`, and `TokenDiff::execute_intent` computes/collects fees independently per intent with no cross-intent tracking of cumulative amounts moved for the same token within a batch. An attacker can split a large NEP-245/Imt transfer into N separate unit-amount `TokenDiff` intents inside one `execute_signed_intents` batch, each individually qualifying for the `amount <= 1` fee exemption, causing the total protocol fee collected to be `0` instead of `fee_ceil(N) * protocol_fee` that a single equivalent diff of amount N would incur.

### Finding Description
The broken binding: `Σ_{i=1}^{N} TokenDiff::token_fee(token_C, 1, fee).fee_ceil(1) = 0`, while `TokenDiff::token_fee(token_C, N, fee).fee_ceil(N) > 0` for `N > 1` and nonzero `fee`. These should be economically equivalent (same aggregate quantity of token_C leaves the attacker's balance and enters the counterparty side) but the collected fee differs.

The relevant guard is at [4](#0-3)  — the `amount > 1` check operates purely on the per-intent delta magnitude, and `execute_intent` at [5](#0-4)  computes and collects fee independently for each intent it processes, with each call to `internal_add_balance(fee_collector, fees_collected)` at [6](#0-5)  credited per-intent.

Attacker's payload: N signed `TokenDiff{diff: {token_C: -1, token_D: +k}}` intents (each below/at the exemption threshold on token_C), packaged together with N matching counterparty intents in one `MultiPayload` batch passed to `execute_intents`/`simulate_intents`. `TransferMatcher::finalize` only checks that deltas net to zero across the batch — it does not recompute or enforce fees — so the batch settles successfully with zero fee collected on token_C.

Existing guards do not prevent this: `verify_intent_nonce`, signature verification, and `Lock` checks are orthogonal to fee computation; there is no aggregation of "total amount moved per token per signer per batch" anywhere in `Engine::execute_signed_intents` or `TransferMatcher`.

### Impact Explanation
Protocol fee revenue is under-collected/bypassed for any NEP-245 or Imt token whose owner is willing to split trades into unit-sized legs, matching the "protocol fees bypassed" Critical category. This is repeatable indefinitely by any unprivileged account, across any NEP-245/Imt token, up to gas/batch-size limits, at zero marginal cost beyond ordinary transaction overhead. It does not move funds away from another party without authorization, but it does deprive the fee collector of fees it is otherwise entitled to on the exact same economic transfer.

### Likelihood Explanation
The attacker only needs to hold N units of a NEP-245/Imt token they wish to trade and a counterparty (a solver, or their own second account) willing to fill the N unit-sized legs — the same requirement as any normal swap, just split into more, smaller intents. No special role, relayer key, or privileged access is needed; this is directly reachable via `execute_intents`/`simulate_intents` with an ordinary signed `MultiPayload`. The only cost is additional gas for N intents in a batch instead of 1, which is proportional and bounded by block gas limits, not a meaningful deterrent for high-value transfers.

### Recommendation
Compute `TokenDiff` fees based on the cumulative negative delta per `(signer_id, token_id)` accumulated across the *entire batch* (or at minimum, remove/restrict the `amount <= 1` exemption to `TokenIdType::Nep171` only, since true NFTs are inherently quantity-1 and cannot be split further, whereas `Nep245`/`Imt` balances can be freely divided into repeated unit transfers to exploit the exemption).

    // Finalizes all transfers, or returns unmatched deltas.
    // If unmatched deltas overflow, then Err(None) is returned.
    pub fn finalize(self) -> Result<Transfers, InvariantViolated> {
        let mut transfers = Transfers::default();
        let mut deltas = TokenDeltas::default();
        for (token_id, transfer_matcher) in self.0 {
            if let Err(unmatched) = transfer_matcher.finalize_into(&token_id, &mut transfers)
                && (unmatched == 0 || deltas.apply_delta(token_id, unmatched).is_none())
            {
                return Err(InvariantViolated::Overflow);
            }
        }
        if !deltas.is_empty() {
            return Err(InvariantViolated::UnmatchedDeltas {
                unmatched_deltas: deltas,
            });
        }
        Ok(transfers)
    }
