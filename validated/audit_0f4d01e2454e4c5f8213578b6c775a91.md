### Title
Dust deposit-token transfers permanently fill a victim's token list and DoS deposits, borrows, and inbound transfers - ([File: contracts/Pool.sol])

### Summary
`DepositToken._transfer` unconditionally registers the recipient in `Pool.depositTokensOfAccount` the first time they receive a deposit token. `Pool.addToDepositTokensOfAccount` reverts with `UserReachedMaxTokens` once `debtTokensOfAccount + depositTokensOfAccount` reaches `MAX_TOKENS_PER_USER = 30`. Any unprivileged EOA can dust-transfer deposit tokens to a victim (or front-run their deposit) to fill this list, after which every code path that would add a new token entry for that account reverts — the same crash-on-untrusted-input shape as CVE-2024-28577, where a malformed object reaches an unchecked dereference.

### Finding Description
When a `DepositToken` transfer lands on an account with zero prior balance, `_transfer` calls `pool.addToDepositTokensOfAccount(recipient_)`. [1](#0-0) 

The pool-side hook enforces a hard cap and reverts instead of allowing the accounting to degrade gracefully. [2](#0-1) [3](#0-2) 

The same hook fires on `_mint`, so `deposit()` reverts for any collateral type the victim does not already hold once the list is full. [4](#0-3) 

`DebtToken.issue/mint` has the symmetric hook via `addToDebtTokensOfAccount` (same `onlyIfAdditionWillNotReachMaxTokens` modifier), so new borrows are also blocked.

Attack path:
1. Attacker deposits 1-wei-scale amounts of each listed collateral via `DepositToken.deposit(1, attacker)` (fee-free or near-free depending on `depositFee`), obtaining dust msdTOKEN balances.
2. Attacker calls `DepositToken.transfer(victim, 1)` for enough distinct deposit tokens to push `debtTokensOfAccount.length(victim) + depositTokensOfAccount.length(victim)` to 30. If the pool has fewer than 30 deposit tokens, the attacker combines this with the debt side or targets accounts already near the cap; the grief is strongest when the pool lists close to 30 collaterals.
3. Afterwards, for the victim:
   - `deposit(amount, victim)` for any collateral not already in the victim's list reverts inside `_mint → addToDepositTokensOfAccount`.
   - Any `transfer`/`transferFrom`/`seize` crediting the victim a new deposit token reverts.
   - `DebtToken` issuance of a new synthetic reverts via the debt-list hook.
4. The victim can only recover by fully zeroing a dust balance (`transfer` of the entire 1-wei balance to another account whose list is not full), which is itself hampered by `_revertIfLocked` if the victim has open debt — `unlockedBalanceOf` returns 0 for an unhealthy or fully-utilized position, so a victim with locked collateral cannot even eject the dust entries. [5](#0-4) [6](#0-5) 

### Impact Explanation
- **Temporary freezing of funds / position management**: the victim cannot deposit additional collateral types. If their position drifts toward the liquidation threshold, they cannot add a *new* collateral to restore health — only top up existing types — and in the worst case (debt present, dust locked) they cannot clear the attacker-inserted entries at all, leaving them exposed to liquidation they could otherwise have prevented.
- **Blocked inbound value**: seizure proceeds, OTC transfers, or smart-farming deposits directed at the victim for a not-yet-held token revert.
- **Low cost, repeatable**: the attacker only forfeits dust; they can re-fill the slot immediately after the victim clears it.

### Likelihood Explanation
Reachable by any unprivileged account through public `deposit` + `transfer` entry points; no privileged role, oracle manipulation, or malicious relayer required. Effectiveness depends on the deployed pool listing enough deposit/debt tokens to reach the 30-entry cap, which needs to be confirmed against the target chain's configuration — on pools with few listed tokens the cap is unreachable and the attack degrades to no-impact. The mitigating factor is that a debt-free victim can always eject dust by transferring the full balance away, so the freeze is temporary rather than permanent in most configurations.

### Recommendation
- Do not revert in `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` when the cap is hit; either silently skip registration for *unsolicited* transfers (track "user-initiated deposit" vs "received" separately), or raise/decouple the cap.
- Restrict the cap check to mint/deposit paths and exempt `_transfer` recipients, e.g. pass a flag through `_transfer(sender, recipient, amount, /*isSeizeOrDeposit*/)` so that only the originating action enforces `MAX_TOKENS_PER_USER`.
- Alternatively let `debtPositionOf` iterate a bounded merged view so that unregistered dust balances are simply ignored for accounting instead of bricking the account.

### Proof of Concept
Hardhat/Foundry fork sketch against a deployed pool:

```solidity
// Assume pool has >= K deposit tokens such that attacker can fill victim to 30.
// vm.createSelectFork(<chain rpc>)

for (uint i; i < needed; ++i) {
    IDepositToken dt = IDepositToken(pool.getDepositTokens()[i]);
    if (dt.balanceOf(victim) == 0 && pool.depositTokensOfAccount.length(victim) < 30) {
        dt.underlying().approve(address(dt), 1);
        // attacker deposits dust for itself
        dt.deposit(1, attacker);
        // then dusts the victim
        dt.transfer(victim, dt.balanceOf(attacker) > 1 ? 1 : dt.balanceOf(attacker));
    }
}

// Now victim's token count == 30
// Any deposit of a collateral type the victim doesn't hold reverts:
vm.expectRevert(UserReachedMaxTokens.selector);
vm.prank(victim);
newDepositToken.deposit(100e18, victim); // reverts inside _mint -> addToDepositTokensOfAccount

// Inbound transfer of a new deposit token to victim reverts:
vm.expectRevert(UserReachedMaxTokens.selector);
vm.prank(attacker);
newDepositToken.transfer(victim, 1); // reverts inside _transfer -> addToDepositTokensOfAccount

// If victim has debt and dust is locked, they cannot clear the entries either:
vm.expectRevert(NotEnoughFreeBalance.selector);
vm.prank(victim);
dustToken.transfer(attacker, 1); // _revertIfLocked blocks if unlockedBalanceOf(victim) == 0
```

Note: whether the cap is reachable depends on the number of listed deposit/debt tokens in the deployed configuration (`depositTokens.length` is itself capped at 30 via `ReachedMaxDepositTokens`), and the "permanent" leg requires the victim to carry enough debt that the dust balances are locked — both should be validated on a mainnet fork before claiming severity.
