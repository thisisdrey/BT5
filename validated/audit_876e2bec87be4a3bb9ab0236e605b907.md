### Title
`action_delete_account` fails to purge `PromiseYieldReceipt`/`PromiseYieldStatus` (and yield-id mappings), allowing a re-created account to inherit and execute a parked yield receipt - (File: `runtime/runtime/src/actions.rs`, `core/store/src/utils/mod.rs`)

### Summary
`action_delete_account` (`runtime/runtime/src/actions.rs:314-390`) deletes an account by calling `remove_account` (`core/store/src/utils/mod.rs:505-575`), which only removes `TrieKey::Account`, `TrieKey::ContractCode`, access keys/gas-key nonces, and `TrieKey::ContractData`. It never removes `TrieKey::PromiseYieldReceipt`, `TrieKey::PromiseYieldStatus`, `TrieKey::PromiseYieldTimeout`, or the `YieldIdToDataId`/`DataIdToYieldId` mappings that were written by `create_promise_yield_receipt`/`create_promise_yield_receipt_with_id` (`runtime/runtime/src/ext.rs:353-400`). If the account is deleted while it has a self-targeted yield still parked (`receiver_id == account_id`), the parked receipt survives account deletion and remains keyed to that account name.

### Finding Description
`create_promise_yield_receipt` writes `TrieKey::PromiseYieldReceipt{receiver_id, data_id}` (via `set_promise_yield_receipt`) and `TrieKey::PromiseYieldStatus{receiver_id, data_id}` (via `set_promise_yield_status`) — see [1](#0-0) . These keys are namespaced by `receiver_id` (the account name), not by any per-account incarnation/generation counter.

When the account is later deleted through `DeleteAccount`, `action_delete_account` calls `remove_account`, which purges the account record, contract code, access keys, gas-key nonces and contract data [2](#0-1) , but the removal routine itself never touches promise-yield trie keys: [3](#0-2) . The functions `remove_promise_yield_receipt`, `remove_promise_yield_status`, and `remove_yield_id_mappings` exist elsewhere in the same module [4](#0-3) [5](#0-4)  but are not invoked from `remove_account`/`action_delete_account`.

Because the trie key namespace is purely `AccountId`-based, once account `A` is re-created (a plain `CreateAccount` action succeeds because the account no longer exists after deletion), the residual `PromiseYieldReceipt`/`PromiseYieldStatus` rows are still addressable under the new account `A`. When the resume path eventually fires — either a genuine `promise_yield_resume` host call from the original caller, or the protocol's timeout-driven resume queued via `TrieKey::PromiseYieldTimeout` — the runtime will look up the receipt by `(receiver_id, data_id)`, find it still present, and dispatch/execute the parked action receipt against whatever account now occupies name `A`. That parked receipt's `predecessor_id` is the original `receiver_id` (== `A`), so the resulting action receipt executes with `predecessor_id == receiver_id == A`, i.e., it looks self-invoked/owner-privileged from the perspective of the new contract, even though the new account's owner/deployer never initiated the yield.

No existing check re-validates that the account instance targeted by the resume is the same instance that created the yield (there is no account "epoch"/nonce embedded in the trie key or in the receipt), and none of the delete-account safety checks (storage-usage cap, gas-key balance cap) inspect or account for outstanding promise-yield state.

### Impact Explanation
This is an authorization-escalation bug: a resumed/timeout receipt with `predecessor_id == receiver_id` (normally only achievable by the account itself, e.g., for privileged/owner-gated `FunctionCall` logic) can be made to execute against an account that a *different, unrelated* party created and funded after the original account was deleted. If the new contract at `A` contains any logic gated on "caller is myself" (a common pattern for internal callback/owner-only entry points), an attacker (the original account owner who set up the yield before deleting the account) can trigger execution of that gated logic against the victim's newly deployed contract, potentially draining funds or corrupting contract state. This matches the "authorization escalation across accounts or promises" bounty category.

### Likelihood Explanation
Preconditions are fully within reach of an unprivileged account: (1) call `promise_yield_create` targeting itself (self-receiver) — a standard, permissionless host function; (2) submit a `DeleteAccount` action on the same account, which is unconditionally available to the account owner and only gated by storage-usage/gas-key-balance caps that a lean account trivially satisfies; (3) wait for a *different* party to independently create a new account with the exact same name and deploy a contract there (this requires the attacker to predict/target a specific account name being reused, e.g., through a naming convention, marketplace, or squatting scheme) or, more directly, the attacker can immediately re-register account `A` themselves and observe whether the eventual timeout/resume receipt executes against it. The attack is fully repeatable and costs only the gas/storage fees for the yield-create and delete-account transactions.

### Recommendation
`remove_account` (or `action_delete_account`) should also purge all promise-yield state scoped to the account being deleted before finalizing deletion: call `remove_promise_yield_status`/`remove_promise_yield_receipt` for any outstanding `data_id`s under `receiver_id == account_id`, and `remove_yield_id_mappings` for any `YieldIdToDataId`/`DataIdToYieldId` entries. Alternatively (and more robust against iteration cost), reject/queue `DeleteAccount` while the account has any outstanding parked yield receipts, or bind promise-yield trie keys to an account "incarnation" identifier that changes on every `CreateAccount` so that a residual receipt from a deleted account can never resolve against a newly created account of the same name.

### Proof of Concept
Unit/integration test (runtime-level, e.g. added to `runtime/runtime/src/tests/apply.rs` or `test-loop-tests/src/tests/yield_resume.rs`):
1. Deploy a contract on account `A` with a `FunctionCall` entry point that behaves as owner-only for calls where `predecessor_id == current_account_id`, mutating some observable state (e.g., writing a "privileged executed" flag or transferring balance).
2. From `A`, invoke a host function that calls `promise_yield_create` targeting `A` itself (self-receiver yield), producing `data_id` and writing `TrieKey::PromiseYieldReceipt{receiver_id:A, data_id}` and `TrieKey::PromiseYieldStatus{receiver_id:A, data_id}`.
3. Submit `DeleteAccount` for `A` with a beneficiary; assert `get_account(A)` returns `None`, but `get_promise_yield_receipt(trie, A, data_id)` and `get_promise_yield_status(trie, A, data_id)` still return `Some(..)`.
4. Submit `CreateAccount` for `A` funded by a distinct party `B`, deploy a fresh (victim) contract with its own owner-only entry point guarded by `predecessor_id == current_account_id`.
5. Deliver the `PromiseResume` (either directly via `promise_yield_resume` targeting the original `data_id`, or by advancing blocks until the `PromiseYieldTimeout` queue entry fires).
6. Assert the parked receipt's action executes against the *new* account `A`'s state (owner-only mutation observed) despite `B` never authorizing it — demonstrating cross-account authorization escalation via un-purged promise-yield trie state.

/// Removes account, code and all access keys and gas keys associated to it.
pub fn remove_account(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
) -> Result<RemoveAccountResult, StorageError> {
    state_update.remove(TrieKey::Account { account_id: account_id.clone() });
    state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });

    let mut gas_key_nonce_count: usize = 0;
    let mut gas_key_nonce_total_key_bytes: usize = 0;

    // Removing access keys and gas key nonces
    let lock = state_update.trie().lock_for_iter();
    let mut keys_to_remove: Vec<TrieKey> = Vec::new();
    for raw_key in state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_access_keys(account_id), &lock)?
    {
        let raw_key = raw_key?;
        let key_handle = trie_key_parsers::parse_key_handle_from_access_key_key(
            &raw_key, account_id,
        )
        .map_err(|_e| {
            StorageError::StorageInconsistentState(
                "Can't parse key handle from raw key for AccessKey".to_string(),
            )
        })?;
        let nonce_index =
            trie_key_parsers::parse_nonce_index_from_gas_key_key(&raw_key, account_id, &key_handle)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse nonce index from raw key for AccessKey".to_string(),
                    )
                })?;
        if let Some(index) = nonce_index {
            gas_key_nonce_count += 1;
            gas_key_nonce_total_key_bytes += raw_key.len();
            keys_to_remove.push(TrieKey::gas_key_nonce(
                account_id.clone(),
                key_handle.clone(),
                index,
            ));
        } else {
            keys_to_remove.push(TrieKey::access_key(account_id.clone(), key_handle.clone()));
        }
    }
    drop(lock);

    for trie_key in keys_to_remove {
        state_update.remove(trie_key);
    }

    // Removing contract data
    let lock = state_update.trie().lock_for_iter();
    let data_keys = state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_contract_data(account_id, &[]), &lock)?
        .map(|raw_key| {
            trie_key_parsers::parse_data_key_from_contract_data_key(&raw_key?, account_id)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse data key from raw key for ContractData".to_string(),
                    )
                })
                .map(Vec::from)
        })
        .collect::<Result<Vec<_>, _>>()?;
    drop(lock);

    for key in data_keys {
        state_update.remove(TrieKey::ContractData { account_id: account_id.clone(), key });
    }
    Ok(RemoveAccountResult { gas_key_nonce_count, gas_key_nonce_total_key_bytes })
}
