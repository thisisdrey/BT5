### Title
Dust-transfer griefing fills a victim's `MAX_TOKENS_PER_USER` slots, DoS-ing new deposits and debt issuance — (File: contracts/DepositToken.sol)

### Summary
`DepositToken._transfer` registers the recipient in the Pool's per-account token list whenever their balance goes 0 → non-zero, and `Pool.addToDepositTokensOfAccount` reverts once `debtTokensOfAccount + depositTokensOfAccount` reaches `MAX_TOKENS_PER_USER` (30). An unprivileged attacker can cheaply dust-transfer every whitelisted deposit token to a victim, permanently filling their slots and making any subsequent `deposit` of a not-yet-held collateral or `issue`/`mint` of a not-yet-held debt token revert with `UserReachedMaxTokens`.

### Finding Description
Like CVE-2018-25098 (`executeUcacTx` DoS via a manipulated state-changing handler), this is a state-manipulation denial of service reachable by any EOA:

1. `DepositToken._transfer` (contracts/DepositToken.sol, lines 498–526) calls `pool.addToDepositTokensOfAccount(recipient_)` whenever `_recipientBalanceBefore == 0 && amount_ > 0`.
2. `Pool.addToDepositTokensOfAccount` is gated by `onlyIfAdditionWillNotReachMaxTokens` (contracts/Pool.sol, lines 143–148), which reverts `UserReachedMaxTokens` once the combined list hits 30, and by `_revertIfSenderIsNotDepositToken`, which accepts any *whitelisted* deposit token — not just ones the victim chose.
3. The same cap guards `addToDebtTokensOfAccount` (contracts/Pool.sol, lines 204–208), which is called from `DebtToken._mint` (contracts/DebtToken.sol, lines 597–600) inside `issue()` and `SmartFarmingManager`-driven `mint()`.

Attack: the attacker deposits 1 wei of each underlying to obtain each whitelisted msdTOKEN, then calls `transfer(victim, 1)` on each deposit token. Each first-time receipt appends an entry to `depositTokensOfAccount[victim]`. If the pool has ≥30 deposit/debt tokens the victim hasn't touched, the victim's list is filled. Thereafter:
- `deposit()` into any new collateral reverts (inside `_mint` → `addToDepositTokensOfAccount`),
- `issue()`/`DebtToken.mint()` into any new synthetic reverts (inside `_mint` → `addToDebtTokensOfAccount`).

No modifier stops this: `transfer` only checks the *sender's* unlocked balance (`_revertIfLocked(_msgSender, amount_)`), `nonReentrant` doesn't apply to plain `transfer`, and there is no opt-in/opt-out on receiving.

### Impact Explanation
Denial of service of position management. A victim who is approaching liquidation and needs to add a *new* collateral type (e.g., a freshly onboarded deposit token, or simply one they hadn't used) is blocked; `deposit` reverts and they can be liquidated — indirect loss of funds. New users can be pre-griefed before their first deposit, and `SmartFarmingManager.leverage` flows (which deposit + mint) also revert. Recovery requires the victim to locate the dust tokens and transfer each full balance out to free a slot — possible but unbounded in UX/gas and unusable inside a single transaction (e.g., mid-leverage or mid-liquidation-defense), so funds/positions are at least temporarily frozen.

### Likelihood Explanation
Fully unprivileged: only public `deposit` + `transfer` calls on whitelisted tokens. Cost is ~1 wei of each underlying per token plus gas. Limitation: the pool's whitelist caps the number of fillable slots (also `MAX_TOKENS_PER_USER` in `addDepositToken`), so the attack is most effective on fresh accounts or pools with many collaterals, and the victim can eventually clear slots themselves. Severity is therefore closer to Medium than the CVE's High.

### Recommendation
- Only add to `depositTokensOfAccount`/`debtTokensOfAccount` on protocol-initiated mints (`_mint`), not on user-initiated `_transfer`, or maintain a separate "received dust" set that does not count against `MAX_TOKENS_PER_USER`.
- Alternatively, let the cap check apply only to *locked/health-relevant* balances above a dust threshold.
- Provide a `sweepDust`/self-service removal so an account can force-remove tokens it never deposited.

### Proof of Concept
Hardhat (repo test stack):

```ts
// test/Pool.test.ts style — real DepositToken instances, not mocks
it('grief: dust transfers fill MAX_TOKENS_PER_USER and block new deposits/issues', async () => {
  // setup: pool with N whitelisted deposit tokens dt[i] (N = MAX_TOKENS_PER_USER)
  const max = (await pool.MAX_TOKENS_PER_USER()).toNumber();

  for (let i = 0; i < max; i++) {
    // attacker deposits 1 wei underlying and transfers the msdTOKEN dust to victim
    await underlying[i].approve(dt[i].address, 1);
    await dt[i].deposit(1, attacker.address);
    await dt[i].transfer(victim.address, 1); // adds dt[i] to depositTokensOfAccount[victim]
  }
  expect(await pool.getDepositTokensOfAccount(victim.address)).to.have.length(max);

  // victim tries to deposit a collateral they don't hold yet -> reverts inside _mint
  await expect(dtNew.connect(victim).deposit(1e18, victim.address))
    .revertedWithCustomError(pool, 'UserReachedMaxTokens');

  // victim tries to issue a new synthetic -> reverts inside DebtToken._mint
  await expect(debtToken.connect(victim).issue(1, victim.address))
    .revertedWithCustomError(pool, 'UserReachedMaxTokens');
});
