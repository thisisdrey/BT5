### Title
Missing staleness check on the external stSTX/STX ratio price component used in oracle callcode transformation - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`price-resolve` in `v0-4-market.clar` validates freshness only for the timestamp returned by the primary Pyth/DIA feed. The secondary price component used for `stSTX`/`zstSTX` valuation — the stSTX/STX exchange ratio fetched from an external contract via `call-ststx-ratio` — carries no timestamp at all and is never checked for staleness before being multiplied into the final price, mirroring the missing second-oracle staleness check in the referenced BendDAO finding.

### Finding Description
`price-resolve` computes the final asset price as follows: [1](#0-0) 

It calls `resolve-price-feed` to get `{value, timestamp}` from Pyth or DIA, then applies `resolve-callcode` to transform the base price, and finally validates freshness only against the timestamp obtained from the *primary* feed: [2](#0-1) 

For `stSTX`/`zstSTX`, `resolve-callcode` invokes `resolve-ststx`, which multiplies the base STX price by a ratio obtained from a second, independent external oracle: [3](#0-2) [4](#0-3) 

`call-ststx-ratio` calls out to `'SP4SZE494VC2YC5JYG7AYFQ44F5Q4PYV7DVMDPBG.block-info-nakamoto-ststx-ratio-v2 get-ststx-ratio-v3`, an external contract that this repository does not control, and this call returns only a `uint` ratio value — no timestamp/publish-time metadata is returned at all. Because `resolve-ststx`/`resolve-ztoken` only return the transformed numeric price (see `resolve-callcode`), and `price-resolve`'s only freshness check (`oracle-timestamp-fresh`) operates exclusively on the timestamp coming from `resolve-price-feed` (Pyth/DIA), the ststx-ratio component is composited into the final price with zero staleness validation — structurally identical to the BendDAO `WEETH_AGGREGATOR` finding where one of two price sources composed into a single answer bypassed the staleness check entirely.

This is directly analogous to and stronger than the reported bug class, because in the reference case at least a `latestAnswer()` call was made (no metadata by design of the interface); here the ratio oracle is called but any staleness information it might expose is simply discarded/never checked in `price-resolve`, so a frozen, outdated, or otherwise stale stSTX ratio silently propagates into every collateral/debt valuation, health check, and liquidation decision that touches `stSTX` or `zstSTX` (e.g. via `collateral-add`, borrow/health checks, and `write-feeds`/`price-multi-resolve` batch resolution used across market entry points).

### Impact Explanation
If the external ststx-ratio oracle stalls, is paused, or otherwise stops updating while continuing to answer with an old value, `resolve-ststx` will keep using that stale ratio indefinitely — `price-resolve`'s freshness gate cannot detect this because it never inspects the ratio oracle's own timestamp. An attacker (or unfavorable market conditions) could exploit a stale (favorably inflated) stSTX/STX ratio to:
- Over-value `stSTX`/`zstSTX` collateral in health checks, allowing under-collateralized borrowing (theft of user funds/protocol insolvency), or
- Prevent legitimate liquidations from triggering when the real ratio has dropped, causing bad debt to accumulate (protocol insolvency), or
- Block legitimate liquidations of otherwise-unhealthy positions valued using stale/inflated collateral, temporarily freezing funds recoverable via liquidation.

This lands squarely in the **Critical** impact category (protocol insolvency / theft of user funds via mispriced collateral) since `stSTX`/`zstSTX` valuations feed directly into borrowing capacity and liquidation health checks reachable by any ordinary principal's `collateral-add`, borrow, and liquidation calls.

### Likelihood Explanation
Likelihood depends on the external ratio oracle (`block-info-nakamoto-ststx-ratio-v2`) actually stalling or being manipulated — this is an external dependency risk, but the root-cause bug is squarely inside Zest's own `price-resolve`/`resolve-ststx` composition logic, which fails to defend against it, unlike the primary Pyth/DIA leg which is explicitly protected by `oracle-timestamp-fresh`. Any temporary outage, congestion, or bug in the external ratio contract translates directly into an unguarded price defect in Zest with no fallback or bound.

### Recommendation
Extend `call-ststx-ratio`/`get-ststx-ratio-v3` integration to also return (or independently query) a timestamp for the ratio value, and apply the same `oracle-timestamp-fresh` (or an equivalent, ratio-specific staleness bound) check to that timestamp inside `resolve-ststx` before it is composed into the final price returned by `resolve-callcode`. If the ratio oracle contract does not expose a timestamp, add a protocol-side heartbeat (e.g., record last-successful-ratio-update time and cap staleness) so a frozen ratio cannot be used indefinitely.

### Proof of Concept
1. External contract `block-info-nakamoto-ststx-ratio-v2` stops updating `get-ststx-ratio-v3` (e.g. due to congestion, a bug, or a stuck oracle) but continues returning its last-known ratio value with no error.
2. A user calls `collateral-add`/`supply-collateral-add` with `stSTX` or `zstSTX` collateral, or triggers a health check/liquidation flow that resolves prices via `price-multi-resolve` → `price-resolve` → `resolve-callcode` → `resolve-ststx`. [1](#0-0) 
3. `resolve-price-feed` returns a fresh Pyth/DIA STX/USD price and timestamp, which passes `oracle-timestamp-fresh`.
4. `resolve-callcode`→`resolve-ststx` multiplies that fresh STX price by the stale ratio from `call-ststx-ratio`, producing a stale/incorrect `stSTX` (or `zstSTX`) USD price.
5. `price-resolve`'s single freshness assertion only checks the Pyth/DIA timestamp, which is fresh, so the whole (partially stale) composite price passes validation.
6. The resulting mispriced collateral is then used unchecked in health/LTV calculations and liquidation eligibility, enabling under-collateralized borrowing or blocking legitimate liquidations.

```text
(define-private (price-resolve
  (data { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint }))
  (let ((type (get type data))
        (ident (get ident data))
        (key { type: type, ident: ident })
        (resolution (try! (resolve-price-feed type ident)))
        (price (get value resolution))
        (callcode (get callcode data))
        (final-price (try! (resolve-callcode price callcode)))
        (last-update-time (oracle-last-update key))
        (timestamp (get timestamp resolution))
        (max-staleness (get max-staleness data)))

    ;; validate price and timestamp using max-staleness from oracle data
    (asserts! (and (oracle-price-legal final-price) (oracle-timestamp-fresh timestamp last-update-time max-staleness))
              ERR-ORACLE-INVARIANT)

    ;; update timestamp if newer
    (if (> timestamp last-update-time)
        (map-set last-update key timestamp)
        false)

    (ok final-price)))
```
