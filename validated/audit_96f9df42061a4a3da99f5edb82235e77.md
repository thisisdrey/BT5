### Title
Unbounded array allocation from unvalidated ABI-encoded length in TVM precompiles - ([File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java])

### Summary
The `BatchValidateSign` and `ValidateMultiSign` precompiled contracts, reachable from any smart-contract call (`STATICCALL`/`CALL` to precompile addresses `0x66`/similar) with attacker-controlled ABI-encoded `data`, extract an array length directly from the calldata and allocate a Java array of that size before any bound is enforced, when the `allowTvmSelfdestructRestriction` feature switch is disabled.

### Finding Description
`extractBytes32Array` and `extractBytesArray` in `PrecompiledContracts.java` read a length word from the caller-supplied ABI data and immediately allocate an array of that length: [1](#0-0) 

In `BatchValidateSign.doExecute` and `ValidateMultiSign.execute`, the `MAX_SIZE` bound check on the array-length word (`sigArraySize`/`addrArraySize`) is only performed `if (VMConfig.allowTvmSelfdestructRestriction())`; when that flag is false, `extractBytesArray`/`extractSigArray`/`extractBytes32Array` are invoked with the raw, attacker-controlled `intValueSafe()` length taken straight from calldata, with no upper bound check before the `new byte[len][]` allocation: [2](#0-1) [3](#0-2) 

`intValueSafe()` clamps to `Integer.MAX_VALUE` (per `DataWord`'s design for safe int extraction), so a single crafted 32-byte length word can request an array of up to ~2^31 element references, i.e. up to ~16 GB of pointer memory (`byte[][]` of `Integer.MAX_VALUE` entries) allocated eagerly, before any of the downstream length/other consistency checks (`cnt == 0 || cnt > MAX_SIZE`) are reached — those checks only run *after* the array is already allocated.

This mirrors the CVE-2021-36373 bug class: a small, cheaply-crafted input causes the target to eagerly allocate an amount of memory disproportionate to the actual (or even declared) payload size, before any validation of that size against real content bounds.

### Impact Explanation
A successful trigger causes an `OutOfMemoryError` in the node's JVM during TVM execution of an ordinary contract call. This can crash or destabilize the executing full node/SR node process (denial of service), since large heap allocations of this scale during transaction execution are not bounded by energy/CPU limits in the way execution time is. Because the call path is `execute()` of a `PrecompiledContract` invoked during normal contract execution (not merely during static analysis), it is reachable by any account able to broadcast a signed transaction that calls a contract invoking the precompile with crafted data.

### Likelihood Explanation
Reachability depends on `VMConfig.allowTvmSelfdestructRestriction()` being disabled. This is a `ChainParameter`-controlled feature switch; on networks/deployments where it has not been activated (e.g., older/private chains, or before mainnet activation), the vulnerable path is directly reachable by an unprivileged caller with a single transaction encoding a large length word into the appropriate offset slot — no special privileges are required, only calldata construction.

### Recommendation
Move the `MAX_SIZE` bound check (and any other sanity bound) so it applies unconditionally, before calling `extractBytesArray`/`extractSigArray`/`extractBytes32Array`, regardless of `allowTvmSelfdestructRestriction`. Additionally, harden `extractBytes32Array`/`extractBytesArray`/`extractSigArray` themselves to reject/clamp `len` derived from `intValueSafe()` against a small sane upper bound (or against `words.length`) before allocating `new byte[len][]`.

### Proof of Concept
1. Deploy or call an existing contract that invokes the `BatchValidateSign` (or `ValidateMultiSign`) precompile with `STATICCALL`, passing raw ABI-encoded bytes.
2. Craft the `data` payload so that the word at the offset used for `words[2].intValueSafe() / WORD_SIZE]` (the addresses-array-length slot, for `extractBytes32Array`) resolves to a large value (e.g., `0x7fffffff`), while `VMConfig.allowTvmSelfdestructRestriction()` is disabled on the target chain.
3. Broadcast the transaction; on execution, `extractBytes32Array` performs `new byte[Integer.MAX_VALUE][]`, forcing a multi-gigabyte allocation attempt and triggering `OutOfMemoryError` in the node process before the subsequent `MAX_SIZE` bound check is ever reached.

    int len = words[offset].intValueSafe();
    byte[][] bytes32Array = new byte[len][];
    for (int i = 0; i < len; i++) {
      bytes32Array[i] = words[offset + i + 1].getData();
    }
    return bytes32Array;
  }

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
