### Title
Unbounded array-length field in TVM precompile ABI decoding causes uncontrolled memory/CPU allocation - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The internal helpers `extractBytesArray`, `extractBytes32Array`, and `extractSigArray` in `PrecompiledContracts.java` read a "count" field directly from attacker-controlled precompile call data and use it to allocate a Java array and drive a loop, with no upper-bound or EOF-style check against the actual size of the input words/data before the allocation happens.

### Finding Description
`extractBytesArray` reads `len` from `words[offset].intValueSafe()` — a `DataWord` decoded straight from the raw call data passed to a precompiled contract — and immediately does `byte[][] bytesArray = new byte[len][];` before any validation that `len` is consistent with the size of `words` or `data`: [1](#0-0) 

The sibling helpers `extractBytes32Array` and `extractSigArray` follow the identical pattern — attacker-controlled `len` used to size an array and drive a loop with no sanity check against remaining data length: [2](#0-1) 

This mirrors the FFmpeg `rl2_read_header()` bug class: a size/count field taken from untrusted input (`frame_count` in the RL2 header vs. `len` in the precompile call data) is used to allocate memory and iterate a loop without first checking that the input actually contains enough backing data (an "EOF check"). In FFmpeg this caused huge CPU/memory consumption; here, a sufficiently large `len` value (e.g., derived from the low 32 bits of a 256-bit word, up to `Integer.MAX_VALUE`) causes an immediate huge/failed allocation (`new byte[len][]`), which can throw `OutOfMemoryError` or otherwise consume excessive heap before any per-item energy/gas accounting for the loop body occurs.

There is a separate validator, `isValidAbiEncoding`, that checks overall data length divisibility and tail consistency: [3](#0-2) 
However, I was not able to confirm from the available index whether every call site of `extractBytesArray`/`extractBytes32Array`/`extractSigArray` (e.g. batch signature validation precompiles) invokes `isValidAbiEncoding` or otherwise bounds `len` before calling these helpers — this could not be fully verified due to index truncation of the surrounding precompile classes (e.g. `BatchValidateSign`, `ValidateMultiSign`) that consume these helpers.

### Impact Explanation
If `len` is not bounds-checked before reaching these helpers, a caller invoking the affected precompiled contract (reachable by any contract deployer/caller via a normal TVM `CALL`/`STATICCALL` to the precompile address, i.e., an unprivileged transaction) can supply a crafted large "array length" word to force a large/failing allocation (`new byte[len][]`), producing `OutOfMemoryError` inside the TVM execution path. Depending on how that error propagates through `Program`/`Runtime` exception handling, this could crash the node process or halt processing of that node's TVM executions, denying transaction execution service — consistent with the "node crash or halt" / "API the node can no longer serve" impact bar.

### Likelihood Explanation
Exploitability depends entirely on whether the call sites of these helpers validate `len` against `words.length`/`data.length` before invoking them. I could not fully confirm this from the indexed code (the precompile classes that consume `extractBytesArray`/`extractSigArray` were only partially visible). If such validation exists at every call site, the loop would fail fast via `ArrayIndexOutOfBoundsException` on `words[offset + i + 1]` rather than causing meaningful resource exhaustion, which would significantly reduce or eliminate the practical impact.

### Recommendation
Add an explicit upper-bound check on `len` (e.g., `len <= (words.length - offset - 1)` or a hard cap consistent with `MAX_ABI_ARRAY_LENGTH`) in `extractBytesArray`, `extractBytes32Array`, and `extractSigArray` before allocating the output arrays, mirroring the `verifyLength` pattern already used in `RLP.calcLength`/`RLP.decode`: [4](#0-3) 

### Proof of Concept
Not fully constructible from the available index: a concrete PoC requires the precompile address and calldata layout that leads into `extractBytesArray`/`extractSigArray` (e.g., the `BatchValidateSign`/`ValidateMultiSign` precompile input encoding), which was not retrievable from the indexed portions of `PrecompiledContracts.java`. In principle, the PoC is: craft calldata to the affected precompile where the length word for a dynamic array field is set to a very large 32-bit value (e.g., `0x7FFFFFFF`), triggering `new byte[len][]` in `extractBytesArray`/`extractBytes32Array`/`extractSigArray` before any bound check, and observe `OutOfMemoryError`/excessive GC pressure during that single contract call.

    int len = words[offset].intValueSafe();
    byte[][] bytes32Array = new byte[len][];
    for (int i = 0; i < len; i++) {
      bytes32Array[i] = words[offset + i + 1].getData();

    return bytes32Array;
  }

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;

    }

  }
