### Title
Debt floor + `maxLiquidable` cap permanently brick liquidation of small unhealthy positions — ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
In Undertow's AJP bug, a request exceeding a size limit leaves the backend worker stuck in an error state, producing a DoS window. The closest Metronome analog is `Pool.liquidate`: a position whose debt is at or below `debtFloorInUsd` can never be liquidated, because any partial repayment permitted by `maxLiquidable` either leaves a positive remainder below the floor (revert `RemainingDebtIsLowerThanTheFloor`) or requires repaying more than `maxLiquidable` of the balance (revert `AmountGreaterThanMaxLiquidable`). An unprivileged attacker can mass-produce such positions, each permanently stuck as unliquidatable bad debt.

### Finding Description
`Pool.liquidate` enforces two limits in sequence [1](#0-0) :

```solidity
if (amountToRepay_.wadDiv(_debtTokenBalance) > maxLiquidable) {
    revert AmountGreaterThanMaxLiquidable();
}
if (debtFloorInUsd > 0) {
    uint256 _newDebtInUsd = masterOracle().quoteTokenToUsd(..., _debtTokenBalance - amountToRepay_);
    if (_newDebtInUsd > 0 && _newDebtInUsd < debtFloorInUsd) {
        revert RemainingDebtIsLowerThanTheFloor();
    }
}
```

Because `maxLiquidable` is initialized to `0.5e18` (50%) [2](#0-1) , a full repayment is impossible. Once an unhealthy position's debt (in USD) reaches `debtFloorInUsd`, every allowed repayment leaves a remainder in `(0, debtFloorInUsd)` and reverts. The floor is denominated in USD while repayment is bounded as a fraction of token balance, so accrued interest does not rescue the position — repaying the excess above the floor lands exactly on the boundary case again.

Anyone can reach this state through public entry points: open a position via `DebtToken.issue`/`SmartFarmingManager.leverage` with debt only slightly above `debtFloorInUsd`, then let price movement or interest accrual make it unhealthy. Even honest users' decaying positions eventually converge to the stuck state, since liquidation can only reduce debt down to the floor, never below or to zero.

### Impact Explanation
Each stuck position permanently holds ≈`debtFloorInUsd` of unbacked synthetic debt that no liquidator can clear — a per-position liveness failure directly mirroring the reference bug's "worker marked in error state." Repeating across many accounts and synthetic tokens converts this into accumulating protocol insolvency: bad debt grows linearly with attacker capital (~floor value per position, requiring only modest over-collateralization). Accepted impact class: protocol insolvency via permanently unliquidatable debt.

### Likelihood Explanation
Requires `debtFloorInUsd > 0`, a governor-set parameter (config-dependent; cannot be confirmed for every deployment from the repo alone), and a position reaching both unhealthy status and the floor boundary — which occurs naturally via interest accrual and can be engineered deliberately by any EOA. No privileged actor, oracle manipulation beyond normal price movement, or mock-only path is needed. `liquidate` is permissionless [3](#0-2)  and no guard, cap, or pause flag mitigates it; `shutdown` would freeze *all* liquidations anyway, which is out of scope.

### Recommendation
Allow a closing repayment when the remaining debt would fall below the floor — e.g., exempt the floor check when `amountToRepay_ == _debtTokenBalance` and lift/bypass the `maxLiquidable` fraction for full-close liquidations of near-floor positions, or have the last liquidator repay in full by treating `remaining <= debtFloorInUsd` as fully liquidatable. Alternatively, enforce a *minimum* debt at issuance so positions cannot be opened within the unliquidatable band, though this does not fix positions that decay into it via interest.

### Proof of Concept
Hardhat fork sketch (mainnet fork with a deployed Pool where `debtFloorInUsd > 0`, e.g. 100 USD):

```ts
// Attacker deposits collateral via DepositToken.deposit(amount, attacker)
// and issues synthetic debt worth ~1.5 * debtFloorInUsd via DebtToken.issue.
// Collateral price drops / interest accrues until debtPositionOf(attacker)._isHealthy == false
// and debtInUsd is driven to <= debtFloorInUsd by earlier legitimate partial liquidations
// (or attacker opens debt just above floor and interest drags it down in USD terms... see note).

// Now every liquidation call reverts:
const debtBal = await debtToken.balanceOf(attacker.address);        // ~ floor worth
await expect(
  pool.connect(liquidator).liquidate(synth, attacker.address, debtBal, depositToken)
).to.be.revertedWithCustomError(pool, 'AmountGreaterThanMaxLiquidable'); // 100% > 50% cap

await expect(
  pool.connect(liquidator).liquidate(synth, attacker.address, debtBal.div(2), depositToken)
).to.be.revertedWithCustomError(pool, 'RemainingDebtIsLowerThanTheFloor'); // remainder < floor
```

Concrete path to the stuck state: attacker opens debt of `floor + ε` USD across N fresh accounts (Sybil of EOAs, not contracts, so allowed). Price decline makes positions unhealthy; a first liquidation repays `debt - floor` (permitted, since remainder equals the floor and the check is strict `<`). Thereafter all further `liquidate` calls revert as shown above — N × `floor` USD of permanent bad debt. Note: the exact stuck-state entry requires the deployed `debtFloorInUsd` value and a pool configuration where small positions can become unhealthy; I could not confirm live deployment values from the indexed sources, so magnitude should be verified against target-chain config in a fork test.
