### Title
Unsolicited StackerDB push handler advertises a chunk version in its inventory reply before the chunk is actually persisted, allowing false/non-canonical inventory to be served - (File: `stackslib/src/net/stackerdb/mod.rs`)

### Summary
`PeerNetwork::handle_unsolicited_StackerDBPushChunk` patches an in-memory `StackerDBChunkInv` reply to claim the local replica now holds the pushed chunk's `slot_version`, and immediately signs and sends that reply back to the peer, before the chunk itself is ever written to the on-disk StackerDB. The actual write only happens later, out-of-band, when the message is forwarded to the relayer (`process_stacker_db_chunks` → `StackerDBTx::try_replace_chunk`). This is the same class of bug as the reported `_buyToken` issue: a state value (`ftReserve` / here, the slot's advertised version) is treated as authoritative and used to answer/emit before the underlying mutation (`market.mint` / here, the actual chunk `INSERT`) has occurred, so the value reported can diverge from ground truth.

### Finding Description
In `handle_unsolicited_StackerDBPushChunk`:
1. `make_StackerDBChunksInv_or_Nack` builds an inventory reply (`data.slot_versions`) reflecting the *currently stored* versions [1](#0-0) .
2. The incoming chunk is validated with `validate_received_chunk`, which checks size, signer, and freshness against the just-fetched `data.slot_versions` [2](#0-1) .
3. The in-memory `data.slot_versions[slot_id]` is then patched to the new (higher) version to represent that "we'll accept this chunk," and this patched inventory is what gets signed and sent back to the peer as the reply [3](#0-2) [4](#0-3) .
4. The function itself never calls `try_replace_chunk` / never writes to the `StackerDBs` sqlite store. It merely returns `Ok((false, true))`, meaning "forward to the relayer to actually process" [4](#0-3) .
5. The actual persistence happens later and independently in `Relayer::process_stacker_db_chunks`, which re-validates and calls `StackerDBTx::try_replace_chunk` [5](#0-4) . That function does its own signer/staleness checks against the DB state *at that later point in time* and can fail with `StaleChunk` or other errors, in which case the chunk is simply dropped with a log message and never stored [6](#0-5) [7](#0-6) .

Because step 3 happens strictly before step 4/5, and step 4/5 can fail or be delayed/reordered (e.g., a race where another valid chunk for the same slot arrives and is committed first via the relayer, causing this chunk to be rejected as `StaleChunk`), the signed `StackerDBChunkInv` already sent to the remote peer in step 3 asserts a version that was never actually written to the local replica. This breaks the equality that should always hold: "advertised slot version == version actually stored," exactly analogous to the report's `ftReserve` (claimed balance) diverging from `ft.balanceOf(address(this))` (actual balance) because the reserve was read/used before the state-changing `market.mint` call completed.

### Impact Explanation
This causes the node to serve non-canonical inventory as canonical to its peers. Downstream consumers of `StackerDBChunkInv` (peer StackerDB sync schedulers) use the advertised version to decide what to request/skip and to prioritize downloads (rarest-first, newest-first) as documented in `stackslib/src/net/stackerdb/mod.rs` [8](#0-7) . A peer that trusts this inventory will believe the node already has the newer chunk and will not re-fetch/re-serve it, and a subsequent `StackerDBGetChunkData` for that slot/version against this node will not find the data it claimed to have, stalling replication of that slot's data across the network. Since a remote, unprivileged peer can trigger this simply by pushing an unsolicited `StackerDBPushChunk` (racing with another push, or crafting a chunk that is valid at inventory-build time but rejected by the time the relayer processes it, e.g. by exploiting the `TooManySlotWrites`/`StaleChunk` window), this fits the "serving non-canonical state as canonical" / "steering a node off the tip via false inventory" High-impact category.

### Likelihood Explanation
The condition requires only two unsolicited `StackerDBPushChunk` messages to the same slot arriving in quick succession from different unprivileged peers (or one peer sending two versions rapidly), which is entirely within a remote attacker's control given no authentication is needed to send push messages — only a valid StackerDB slot signature is needed to pass `validate_received_chunk`, and an attacker who controls (or has previously observed) any single legitimate slot signer's chunk can replay this race deterministically by controlling message timing/ordering across two connections.

### Recommendation
Do not patch/sign and send the `StackerDBChunkInv` reply claiming a version until after the chunk has actually been durably written via `StackerDBTx::try_replace_chunk`. Either move the actual persistence into `handle_unsolicited_StackerDBPushChunk` itself (so the ack reflects only what was truly stored), or defer sending any inventory acknowledgment until the relayer confirms successful storage, mirroring the recommended fix in the referenced report of performing the mutating operation before relying on its resulting state.

### Proof of Concept
1. Configure a StackerDB slot with a signer key `sk`.
2. From peer A, send `StackerDBPushChunk` for `slot_id=0, slot_version=2` signed by `sk`. This causes `handle_unsolicited_StackerDBPushChunk` to compute an inventory with `slot_versions[0] = 2` and sign/send it back immediately, then return `(false, true)` to forward to the relayer [9](#0-8) .
3. Before the relayer processes that forwarded message, from peer B send another `StackerDBPushChunk` for the same slot with `slot_version=3` signed by `sk`, which gets forwarded and committed first via `Relayer::process_stacker_db_chunks` → `try_replace_chunk`, advancing the stored version to 3 [5](#0-4) .
4. When the relayer finally processes A's version-2 chunk, `try_replace_chunk` now sees `slot_version (2) <= slot_validation.version (3)` and returns `Error::StaleChunk`, so the chunk is dropped and never stored [10](#0-9) .
5. Peer A, however, already received a signed `StackerDBChunkInv` from this node claiming `slot_versions[0] = 2` was accepted — a version that was never persisted, and which is now also stale relative to the real stored version 3, demonstrating the inventory/state mismatch.
