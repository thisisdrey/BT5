### Title
Unauthenticated MARF trie key enumeration bypasses contract-level access control on private Clarity state - ([File: stackslib/src/net/api/getclaritymarfvalue.rs])

### Summary
The `/v2/clarity/marf/:marf_key_hash` endpoint accepts an arbitrary 64-hex-character MARF key hash and a caller-chosen tip (including historical, still-indexed tips via `TipRequest::SpecificTip`), and returns whatever value is stored at that raw MARF trie key with no check that the corresponding Clarity variable/map is exposed by any contract's public read-only interface. This lets a remote, unauthenticated caller who can compute or guess a `marf_key_hash` (these are deterministic hashes derived from known/guessable inputs: contract identifier + variable/map name) read private (non-`define-read-only`, non-public) contract state directly, bypassing Clarity's own access-control semantics.

### Finding Description
`path_regex` at [1](#0-0)  only validates that `marf_key_hash` is a 64-char hex string; it performs no check that the hash belongs to a key the caller is entitled to view. `try_handle_request` then resolves the `tip` via `node.load_stacks_chain_tip` (which itself permits `TipRequest::SpecificTip` for any block ID matching `^(latest|[0-9a-f]{64})?$`) and directly calls `clarity_db.get_data_by_hash(&marf_key_hash)` / `get_data_with_proof_by_hash` inside a read-only Clarity transaction at that tip [2](#0-1) . This is a raw, hash-keyed lookup into the MARF trie's key/value space — it is not routed through any contract's public/read-only ABI, and it is not restricted to a specific contract identifier the caller has demonstrated the right to query (unlike `getclarityvalue`/`callreadonly`, which take an explicit `contract_addr`/`contract_name`/function or variable name and are scoped to a single named entity). Because Clarity's `marf_key_hash` for a data-var or map entry is a deterministic hash of well-known inputs (contract principal, var/map name, and for maps, the serialized key), an attacker with knowledge of a deployed contract's source (or even just the ability to enumerate common variable names) can compute candidate hashes off-chain and query them here, retrieving values a contract intentionally kept private (never exposed via `define-read-only`).

### Impact Explanation
This exposes contract-internal state (private data-vars/maps) that a contract's own author never intended to be publicly readable, to any unauthenticated remote party — an unauthenticated information disclosure of Clarity contract state, keyed directly into the MARF rather than gated by contract ABI. It affects any node exposing this RPC endpoint (default `/v2/` API) and is fully repeatable/enumerable per query, with no rate limiting beyond generic HTTP throttling.

### Likelihood Explanation
The endpoint is unauthenticated and reachable on the standard RPC port with no special privileges, secret, or peer relationship required. The only "cost" to the attacker is knowing or deriving the MARF key hash for the variable/map entry of interest, which is a deterministic, documented hashing scheme (contract identifier + var/map name, i.e., not a secret) — this is a low-cost, purely computational step, not a brute force over the full 256-bit space. Historical/non-canonical but still-materialized tips can be targeted via the standard `tip` query parameter mechanism shared by all RPC endpoints.

### Recommendation
Either remove/restrict `/v2/clarity/marf/:marf_key_hash` from being reachable without authentication (e.g., gate behind the RPC secret / admin-only), or change the endpoint's semantics so lookups are scoped to a specific contract identifier and only expose values for keys the contract has designated public/read-only (mirroring `callreadonly.rs`/`getclarityvalue.rs`), rather than allowing arbitrary raw MARF key hash lookups.

### Proof of Concept
Add a `stackslib::net` test that: (1) deploys a contract with a private (non-`define-read-only`) `define-data-var`, (2) computes the contract's data-var MARF key and its hash using the same hashing routine used internally by `ClarityDatabase`/`MarfedKV` (`clarity_db`'s key hashing for data-vars, e.g. via `ClarityDatabase::make_key_for_trip`/`Hash160`/`TrieHash` helper used by `get_data_by_hash`), (3) issues `GET /v2/clarity/marf/{hash}` via `RPCGetClarityMarfRequestHandler`/`StacksHttpRequest::new_getclaritymarf`, and (4) asserts the HTTP 200 response's `ClarityMarfResponse.data` equals the private var's serialized Clarity value — demonstrating disclosure with no contract-level read-only exposure involved, at `stackslib/src/net/api/getclaritymarfvalue.rs:123-148`.
