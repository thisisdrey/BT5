Based on my research, I found a strong analog in the ijar zip parser: `InputZipFile::ProcessCentralDirEntry` in `third_party/ijar/zip.cc` performs unbounded pointer arithmetic when parsing central-directory extra fields.

### Title
Out-of-bounds read parsing Zip64 extra fields in central directory entries - (`third_party/ijar/zip.cc`)

### Summary
`ProcessCentralDirEntry` reads a JAR/ZIP's central directory to extract per-entry metadata used by `ijar`/`singlejar` when building interface jars from untrusted archives. The extra-field parsing loop advances a raw pointer using attacker-controlled 16-bit length fields without validating those lengths against the actual bounds of the central directory buffer, unlike the sibling local-header parser which uses `EnsureRemaining()` checks before every read.

### Finding Description
`ProcessCentralDirEntry` reads `file_name_length`, `extra_field_length`, and `file_comment_length` directly from the input bytes with no bounds validation against the mapped file/central-directory buffer [1](#0-0) . It then loops over the extra field region using `header_id`/`data_size` read via `get_u2le`, advancing `extra_p` by the attacker-supplied `data_size` and, if the tag matches `ZIP64_EXTRA_FIELD_TAG`, calling `get_u8le(extra)` to read three 8-byte fields, all without checking that `extra_p + data_size` (or `extra + 8`) actually stays within the `extra_field_length` region or the mapped file bounds [2](#0-1) . Contrast this with `ProcessLocalFileEntry`, which calls `EnsureRemaining()` before every field read against `input_file_->Length()` [3](#0-2) , and with `ExtraField::find` in the singlejar zip header parser, which explicitly checks `byte_ptr(start) + extra_field->size() > byte_ptr(end)` before dereferencing [4](#0-3) . `ProcessCentralDirEntry` has no equivalent containment check — an attacker-crafted central directory entry with a mismatched or oversized `extra_field_length`/`data_size` can cause `get_u2le`/`get_u8le` to read past the end of the mapped input file into unrelated memory. This is structurally the same class of bug as CVE-2024-47249: attacker-controlled length/index fields consumed without validation before being used to index into a buffer.

### Impact Explanation
This affects `ijar`, which is used by Bazel's Java toolchain to build interface jars from arbitrary input jars (including third-party dependency jars fetched over the network) — i.e., it operates on attacker-influenced content (a hostile or compromised jar/archive served as a dependency). An out-of-bounds read can leak adjacent process memory into the derived output/interface jar (via the malformed `data_size` causing extra bytes belonging to other regions of the mapped file to be copied out as attribute values) or crash the process. It does not currently intersect a checksum/integrity boundary — it's a memory-safety flaw in a native parser fed by content that a build already trusted, similar in nature to the reported NimBLE class ("lack of input validation for [structured input] could result in out-of-bound memory corruption").

### Likelihood Explanation
Reaching this code merely requires building a `java_import`/`ijar` target (or `singlejar` merge) against a maliciously crafted `.jar`/`.zip` file, something achievable by an unprivileged party who can influence which jar is fetched/built (e.g., publishing a malicious dependency, or supplying such a file on an untrusted CI branch). The lack of any bounds check on `data_size` and `extra_field_length` in `ProcessCentralDirEntry` makes triggering an out-of-bounds pointer walk straightforward with a hand-crafted archive.

### Recommendation
Add explicit bounds checks in `ProcessCentralDirEntry`'s extra field loop, mirroring `EnsureRemaining()`/`ExtraField::find`'s containment checks: validate that `extra_p + 4 <= p` before reading the tag/size header, that `extra_p + data_size <= p` before advancing, and that `extra + 8 <= extra_p` before each `get_u8le` call reading Zip64 attributes. Also validate `file_name_length`, `extra_field_length`, and `file_comment_length` against the remaining bytes in the mapped central directory buffer before advancing `p`, consistent with the containment checks already used elsewhere in the same file.

### Proof of Concept
A concrete PoC would need a `BuildIntegrationTestCase`/unit test (e.g., extending `third_party/ijar/zip_test.cc` or `output_jar_simple_test.cc`, which already contains a similar `MalformedExtraField` regression test pattern for the local header path [5](#0-4) ) that crafts a central directory entry with `extra_field_length` set large but containing a Zip64 extra field whose `data_size` exceeds the remaining bytes in the mapped file, then invokes `ijar`/`ProcessNext()` on it and asserts a sanitizer (ASan) failure or crash, analogous to `MalformedExtraField` but targeting `ProcessCentralDirEntry` instead of the singlejar `LH`/`CDH` parser (which already has containment checks). I was not able to directly execute or fuzz this PoC — this description is based on static code review of the parsing logic differences within the same file.

        break;

      if (extra_field->is(tag)) {
        return extra_field;
      }
      start = ziph::byte_ptr(start) + extra_field->size();
    }
