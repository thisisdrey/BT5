### Title
Gas Under-Accounting in `bls12381_impl!` via Register-Sentinel `value_len`/`value_ptr` Mismatch - ([File: runtime/near-vm-runner/src/logic/bls12381.rs])

### Finding Description
The `bls12381_impl!` macro computes the per-element gas charge from the raw, attacker-supplied `value_len` argument **before** the actual payload is resolved: [1](#0-0) 

```
self.result_state.gas_counter.pay_base($bls12381_base)?;
let elements_count = value_len / $ITEM_SIZE;
self.result_state.gas_counter.pay_per($bls12381_element, elements_count as u64)?;
let data = get_memory_or_register!(self, value_ptr, value_len)?;
```

`get_memory_or_register!` supports a register-read sentinel path (`value_ptr == u64::MAX`), in which `value_len` is not used as a byte length at all but is re-interpreted as a *register id* whose stored content (populated by a prior `write_register` call under a completely independent gas context) is returned verbatim, with a size determined solely by whatever was previously written to that register. This is the standard convention used across other host functions in this file (e.g. `sha256`, `keccak256`) — but in every other such function, the per-byte/per-element gas charge is computed *after* the data is retrieved, using `data.len()`, precisely to avoid this mismatch. `bls12381_impl!` deviates from that safe pattern by charging `pay_per` from the raw `value_len` parameter first and only then dereferencing it through `get_memory_or_register!`.

This lets a contract: (1) call `write_register` with a large buffer (up to the configured max register size) into some register, (2) call e.g. `bls12381_p1_sum` with `value_ptr = u64::MAX` (register sentinel) and `value_len` set to a small register-id integer (e.g. `0`), and `register_id` pointing at a different output register. `elements_count = value_len / ITEM_SIZE` evaluates to a tiny or zero value based on the register-id integer rather than the real payload size, so `pay_per($bls12381_element, ...)` charges almost no gas for the expensive elliptic-curve computation, while `data` returned by `get_memory_or_register!` is the full, large register content that is then fully parsed and processed by the BLS12-381 point-summation logic.

I was not able to directly inspect the exact body of the `get_memory_or_register!` macro in this pass (index/tool limitations prevented fetching `logic.rs` contents for this symbol), so the register-sentinel reinterpretation of `value_len` as a register id is based on the well-established NEAR host-function convention used elsewhere in this codebase and the strong circumstantial evidence of the reversed pay_per/read ordering in this macro specifically (unlike sibling functions such as `sha256` which charge after resolving the actual data length). This should be independently confirmed by reading the macro definition directly before treating this as fully verified.

### Impact Explanation
If confirmed, this allows an unprivileged contract to trigger CPU-expensive BLS12-381 point parsing/aggregation (proportional to a large register payload, up to the configured max register size) while paying gas proportional only to a small, attacker-chosen `value_len`/register-id value. This breaks the METERING_TOTALITY invariant (gas charged must reflect gas-equivalent work performed) and enables cheap, repeatable CPU amplification during chunk application — a liveness/DoS risk against chunk producers under NEAR's bug-bounty "shard-halting/DoS" category.

### Likelihood Explanation
Preconditions are trivial and fully within reach of an unprivileged account: deploy a wasm contract, call `write_register` with a large blob, then invoke a `bls12381_*` host function with `value_ptr` set to the register sentinel and a small `value_len`. No special permissions, keys, or validator access needed; the attack is a single `FunctionCall` action and is fully repeatable at low cost per invocation.

### Recommendation
Reorder the macro to compute `elements_count`/`pay_per` from the actual resolved data length after `get_memory_or_register!` returns, mirroring the pattern used by `sha256`/`keccak256` in this codebase:
```rust
pay_base(...)?;
let data = get_memory_or_register!(self, value_ptr, value_len)?;
let elements_count = data.len() as u64 / ITEM_SIZE;
pay_per(bls12381_element, elements_count)?;
```
This ensures the per-element gas charge always reflects the true byte length actually processed, regardless of whether the register or direct-memory path was taken.

### Proof of Concept
1. Unit test in `runtime/near-vm-runner/src/logic/tests` (or equivalent bls12381 test module): call `write_register(register_id=0, large_buf)` where `large_buf.len()` is a multiple of `BLS_P1_SIZE` far exceeding a small `value_len`.
2. Call `bls12381_p1_sum(value_len=<small integer>, value_ptr=u64::MAX, register_id=1)`.
3. Assert: (a) the gas consumed after the call is only `pay_base + pay_per(elements_count computed from small value_len)`, i.e. far less than `pay_per` scaled to `large_buf.len() / BLS_P1_SIZE`; (b) the function nonetheless successfully processes/parses the full `large_buf` content (verify via the returned result or by observing wall-time/CPU proportional to `large_buf.len()`).
4. Fuzz combinations of declared `value_len` vs. actual register content length to confirm charged gas never tracks actual bytes processed in the register-sentinel path, in contrast to the direct-memory path where `value_len` correctly bounds both.
