### Title
Front-running the per-block vault accrual lets an attacker manipulate the interest rate/index applied retroactively to a victim's borrow, repay, or liquidation - (File: mainnet/contracts/vault/v0-vault-stx.clar, mainnet/contracts/market/v0-4-market.clar)

### Summary
The report describes AlgebraPool's dynamic fee being fixed by whichever swap happens first in a block, letting an attacker front-run a flashloan to force a worse fee on the victim. Zest has a structurally identical pattern: the vault's borrow/liquidity index for an entire elapsed period is computed using the **instantaneous utilization measured only at the moment `accrue` is called**, and the result is cached per-block (per `stacks-block-time`) in `market.clar` so every later operation in the same block reuses that first-caller's value. Any ordinary principal can front-run a victim's borrow/repay/liquidation with a utilization-shifting transaction to change the rate that gets retroactively applied to the whole stale time-delta, and everyone else's same-block operations are then priced off that manipulated, cached index.

### Finding Description
Each vault computes interest with `next-index` / `next-liquidity-index`, which take the **current** utilization via `interest-rate` and apply it over `time-delta = stacks-block-time - last-update` — i.e., the entire unaccrued period since the last accrual, however long that is: [1](#0-0) 

`utilization` is a pure function of the vault's current `available-assets` and `total-debt`, both of which are directly moved by ordinary `system-borrow`/repay calls in the same transaction that immediately precedes the accrual: [2](#0-1) 

Whoever's transaction is the first in a block to trigger accrual for a given asset determines the index for the *rest of the block*: `market.clar`'s `accrue-and-cache` keys the vault's index by `{ timestamp: stacks-block-time, aid }` and simply returns the cached value on any subsequent call within the same block/timestamp, without recomputing: [3](#0-2) 

This cache is read by both the debt-accrual and collateral-accrual paths used before health checks, borrows, repayments, and liquidations: [4](#0-3) 

Critically, the underlying vault call (`vault-accrue`) is not a read-only preview — it is the vault's real `accrue` public function, which *persists* the computed index/lindex on-chain (`var-set index next`, `var-set lindex nliq`) and mints treasury LP shares based on the same manipulated debt-delta: [5](#0-4) 

So an attacker who is the first to touch a given vault's accrual in a block can, by first submitting a large borrow (or repay) to spike (or depress) utilization, cause `interest-rate`/`next-index` to be computed with that manipulated utilization and have it applied over the *entire* elapsed `time-delta` since the last update — not just the current instant. That manipulated index is then both permanently persisted to the vault and cached for the rest of the block, so a victim's borrow, repay, or liquidation transaction that follows in the same block is charged debt/collateral valuations derived from the attacker-manipulated index, exactly mirroring the flashloan-fee report's root cause (first mover in the block fixes a rate that later movers are forced to accept).

### Impact Explanation
Because the retroactively-applied rate compounds over the full stale `time-delta` (which can be large if a vault has gone unaccrued for some time), and because a share of any interest delta is minted as treasury LP to `dao-treasury` and the remainder accrues to suppliers, an attacker who is also a supplier of the vault can force a spike in the accrued-interest delta at the exact moment of accrual to redirect a disproportionate share of retroactive interest to current suppliers (including themselves) at the expense of borrowers being liquidated or transacting in the same block, or vice versa (suppressing the rate to reduce collateral valuation/liquidation, denying yield to suppliers for that period). This is theft/misallocation of unclaimed yield between borrowers and suppliers caused by a manipulable shared per-block state, landing on the in-scope High impact class ("theft of unclaimed yield").

### Likelihood Explanation
No privileged role is required — utilization can be moved by any account issuing an ordinary borrow or repay through the public market entry points, and the timing/front-running window only requires ordering within a single block, which is achievable by any user submitting a transaction ahead of a known pending one (e.g., a visible liquidation or large borrow/repay in the mempool). The vulnerability is systemic across every vault (`v0-vault-stx`, `v0-vault-sbtc`, `v0-vault-ststx`, `v0-vault-usdc`, `v0-vault-usdh`, `v0-vault-ststxbtc`), all sharing the identical `next-index`/`next-liquidity-index`/`accrue-and-cache` pattern.

### Recommendation
Avoid deriving a full-period interest multiplier from a single point-in-time utilization sample taken opportunistically by whichever transaction happens to trigger accrual first. Consider tracking a time-weighted/twap-style utilization, or splitting accrual into smaller windows keyed to when utilization actually changed rather than only to `stacks-block-time`/on-demand caller triggering, so that a single manipulable instant cannot retroactively re-price an entire stale accrual period for every other party acting in the same block.

### Proof of Concept
1. Vault `V` (e.g., `vault-stx`) has not been accrued for a long stale period; `last-update` is far behind `stacks-block-time`.
2. Attacker observes a pending victim transaction (e.g., a large repay, borrow, or a liquidation) that will implicitly trigger `market.clar`'s `accrue-and-cache` for `V` in the upcoming block.
3. Attacker front-runs with a transaction that first calls `system-borrow` (or repay) on `V` to sharply move `utilization`, then immediately (in the same call chain) triggers `accrue`. Because `next-index`/`next-liquidity-index` compute the rate from this manipulated `utilization` and apply it over the full stale `time-delta` since `last-update` (`mainnet/contracts/vault/v0-vault-stx.clar:368-404`), the persisted `index`/`lindex` jump by an attacker-chosen amount, and treasury LP is minted off the resulting `debt-delta` (`mainnet/contracts/vault/v0-vault-stx.clar:841-863`).
4. `market.clar`'s `index-cache` now holds this manipulated index for `{ timestamp: stacks-block-time, aid: V }` (`mainnet/contracts/market/v0-4-market.clar:245-257`).
5. The victim's transaction executes later in the same block; its debt/collateral accrual calls hit the cache (`mainnet/contracts/market/v0-4-market.clar:259-293`) and use the attacker-set index, causing the victim to be charged (or credited) an amount that differs from what they would have gotten absent the attacker's front-run — identical in structure to the flashloan-fee report's front-run of a swap to fix the block's fee.

```text
(define-private (accrue-and-cache (aid uint))
  (let ((cache-key { timestamp: stacks-block-time, aid: aid })
        (cached? (map-get? index-cache cache-key)))

    (match cached?
      ;; cache HIT: return cached value (1 read only)
      cached-indexes (ok cached-indexes)

      ;; cache MISS: accrue and cache (vault-accrue now returns indexes)
      (let ((indexes (try! (vault-accrue aid))))
        ;; store in cache
        (map-set index-cache cache-key indexes)
        (ok indexes)))))
```
