### Title
Unbounded nested-loop growth in `Transaction.UpdateReferences` allows push-triggered quadratic-time reference staging - ([File: internal/gitaly/storage/storagemgr/partition/transaction_manager.go])

### Summary
`Transaction.UpdateReferences` is invoked once per reference-transaction hook cycle during a git write (push, fetch, replication, etc.), and each call re-scans *every previously staged batch* of reference updates in the same transaction for every reference in the new batch. Git itself splits a single push into multiple reference-transaction hook invocations when it needs to resolve directory-file ref-name conflicts sequentially. An attacker who submits a push containing a chain of nested/conflicting reference names (`refs/heads/a`, `refs/heads/a/b`, `refs/heads/a/b/c`, ...) can force many hook invocations within one Gitaly transaction, each carrying references that must be checked against all prior batches — producing the same "nested-loop over user-controlled N" pattern as the Renzo `calculateTVLs` finding, but here reachable directly from an ordinary user's push.

### Finding Description
`Transaction.UpdateReferences` accumulates one map of updates (`u`) per invocation into `txn.referenceUpdates`. For every reference present in a newly submitted `updates` map, it iterates the *entire* `txn.referenceUpdates` slice built up so far to look up whether that reference was already staged in an earlier batch: [1](#0-0) 

The doc comment explicitly acknowledges the reason multiple calls happen within one transaction — Git needs separate reference-transaction segments to handle directory-file conflicting ref updates: [2](#0-1) 

Each call originates from the `ReferenceTransactionHook`, fired by git itself during `update-ref`/`receive-pack` execution and routed straight into the storage-layer transaction: [3](#0-2) 

Because git invokes the reference-transaction hook once per conflict-resolution segment, and an attacker fully controls the set and names of references pushed (e.g. via `git push` with refspecs like `refs/heads/a`, `refs/heads/a/b`, `refs/heads/a/b/c`, …, each superseding the previous one to force a directory/file conflict split), the number of hook invocations (`k`) and the number of references per invocation both scale with the attacker-supplied ref count `N`. The inner loop over `txn.referenceUpdates` thus performs work proportional to `k` (up to `N`) for every reference in every batch, yielding up to `O(N^2)` map-membership work purely in Gitaly's Go transaction-manager code, on top of Git's own per-segment cost.

### Impact Explanation
This nested-loop scan sits on the hot path of the WAL-based transaction manager that backs every reference-modifying RPC (pushes via SSH/HTTP, `UpdateReferences`, replication, mirroring, etc.). A crafted push with a large, deliberately conflict-chained set of reference names can inflate the per-transaction CPU cost superlinearly, degrading or blocking the write path for the affected repository/partition, mirroring the DoS impact described in the source report (unusable protocol/handler under modest attacker-controlled input size).

### Likelihood Explanation
The reachability path — an ordinary user pushing references with attacker-chosen names — requires only standard push access to a repository (no privileged actor, no leaked token, no malicious peer/MITM required). The exact number of hook invocations git will emit for a given conflict chain and any other internal Git-side batching limits were not fully verified from the available code (this depends on git's own reference-transaction implementation, which is outside this repo), so the practical achievable exponent/scale of `N` should be validated empirically (e.g. with a PoC push containing many nested conflicting ref names) before treating this as a fully confirmed high-severity DoS.

### Recommendation
Replace the linear rescans of `txn.referenceUpdates` with an aggregate map keyed by reference name, updated in O(1) per reference as new batches arrive, instead of iterating the full history of prior batches inside `UpdateReferences`. This removes the quadratic term while preserving the "first old OID / last new OID" semantics described in the function's documentation.

### Proof of Concept
1. As a normal user with push access to a repository, construct a push with a chain of conflicting reference updates, e.g. sequentially:
   - `refs/heads/r1`
   - delete `refs/heads/r1`, create `refs/heads/r1/r2`
   - delete `refs/heads/r1/r2`, create `refs/heads/r1/r2/r3`
   - … repeated `N` times.
2. Push this in a single `git push` so Git must resolve each directory-file conflict as a separate reference-transaction segment, invoking the `ReferenceTransactionHook` (and thus `Transaction.UpdateReferences`) once per segment within the same Gitaly transaction.
3. Observe CPU/time cost of the push scaling superlinearly with `N` due to the nested loop in `transaction_manager.go` lines 731-741, versus linear cost for an equivalent non-conflicting set of `N` reference updates.

// UpdateReferences updates the given references as part of the transaction. Each call is treated as
// a different reference transaction. This allows for performing directory-file conflict inducing
// changes in a transaction. For example:
//
// - First call  - delete 'refs/heads/parent'
// - Second call - create 'refs/heads/parent/child'
//
// If a reference is updated multiple times during a transaction, its first recorded old OID used as

// OID in the final commit. This means updates like 'oid-1 -> oid-2 -> oid-3' will ultimately be
// committed as 'oid-1 -> oid-3'. The old OIDs of the intermediate states are not verified when

func (txn *Transaction) UpdateReferences(ctx context.Context, updates git.ReferenceUpdates) error {
	u := git.ReferenceUpdates{}

	for reference, update := range updates {
		// Transactions should only stage references with valid names as otherwise Git would already
		// fail when they try to stage them against their snapshot. `update-ref` happily accepts references
		// outside of `refs` directory so such references could theoretically arrive here. We thus sanity
		// check that all references modified are within the refs directory.
		//
		// HEAD is a special case and refers to a default branch update.
		if !strings.HasPrefix(reference.String(), "refs/") && reference != "HEAD" {
			return InvalidReferenceFormatError{ReferenceName: reference}
		}

		oldOID := update.OldOID
		oldTarget := update.OldTarget

		if initialValue, ok := txn.initialReferenceValues[reference]; ok {
			if !initialValue.IsSymbolic {
				oldOID = git.ObjectID(initialValue.Target)
			} else {
				oldTarget = git.ReferenceName(initialValue.Target)
			}
		}

		if oldOID == update.NewOID && oldTarget == update.NewTarget {
			// This was a no-op.
			continue
		}

		for _, updates := range txn.referenceUpdates {
			if txUpdate, ok := updates[reference]; ok {
				if txUpdate.NewOID != "" {
					oldOID = txUpdate.NewOID
				}

				if txUpdate.NewTarget != "" {
					oldTarget = txUpdate.NewTarget
				}
			}
		}
