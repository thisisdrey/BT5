## Analysis

The relevant code path is `run_server` in `streamer/src/nonblocking/quic.rs`, which gates each incoming connection through:
1. `overall_connection_rate_limiter.current_tokens() == 0` check
2. `rate_limiter.is_allowed(&ip)` per-IP check
3. `ClientConnectionTracker::new(stats.clone(), qos.max_concurrent_connections())` — a **global** atomic counter check [1](#0-0) 

Critically, both rate limiters at steps 1 and 2 only *peek* at token counts (`current_tokens`) rather than consuming them [2](#0-1) . Actual token consumption (`register_connection` and `overall_connection_rate_limiter.consume_tokens(1)`) only happens later in `setup_connection`, **after** the QUIC handshake successfully completes [3](#0-2) . The `ClientConnectionTracker` itself is created and increments the *global* `stats.open_connections` counter immediately, before the handshake even begins, and is only decremented on `Drop` (which happens when the handshake times out via `QUIC_CONNECTION_HANDSHAKE_TIMEOUT` or the connection is later closed) [4](#0-3) .

This means: an attacker who opens connection attempts but deliberately stalls/never completes the QUIC handshake never triggers `register_connection` or `consume_tokens`, so `is_allowed` (which returns `true` when no tokens have ever been consumed for that IP) keeps admitting new attempts from the same IP indefinitely. Each such attempt still increments the *global* `stats.open_connections` counter via `ClientConnectionTracker::new`, gated only by the shared `max_concurrent_connections()` limit — not a per-IP limit.

However, this attack is fundamentally bounded by `QUIC_CONNECTION_HANDSHAKE_TIMEOUT`: each stalled `connecting` future is wrapped in `timeout(QUIC_CONNECTION_HANDSHAKE_TIMEOUT, connecting)` in `setup_connection`, and when it expires the `client_connection_tracker` is dropped, decrementing `open_connections` [5](#0-4) . So a single IP can only hold slots open for the duration of `QUIC_CONNECTION_HANDSHAKE_TIMEOUT`, and would need to continuously re-establish new stalled connections faster than the timeout window to sustain a persistent DoS. I could not verify the exact numeric value of `QUIC_CONNECTION_HANDSHAKE_TIMEOUT` in this indexed snapshot of the codebase, which limits precise quantification of the attack window, but its existence and role are confirmed by the code and by the module comment explicitly describing this mitigation strategy: "limit duration of in-flight connection attempts with a timeout" [6](#0-5) .

This is a real, narrow gap: the documented defense-in-depth comment states four bullet points including "cap total connections per-peer/ip", but that per-peer/IP cap (`max_connections_per_peer`, enforced in `ConnectionTable::try_add_connection`) is only applied **after** handshake success, inside `try_add_connection`/`cache_new_connection` in `swqos.rs`/`simple_qos.rs` [7](#0-6) . Before handshake completion, the only global admission gate is `ClientConnectionTracker`, which has no per-IP dimension — confirming the premise of the question that global slot exhaustion by unauthenticated pre-handshake connections from a single IP is architecturally possible, bounded only by the handshake timeout and the peek-only (non-consuming) per-IP/overall rate limiters.

### Title
Global `ClientConnectionTracker` slot exhaustion via stalled/never-completed QUIC handshakes from a single IP - (streamer/src/nonblocking/quic.rs)

### Summary
The connection admission gate in `run_server` increments a single, IP-agnostic `open_connections` counter (`ClientConnectionTracker::new`) immediately upon accepting a `Incoming`, before the QUIC handshake is verified, while the per-IP (`rate_limiter.is_allowed`) and overall (`overall_connection_rate_limiter.current_tokens`) rate limiters only *peek* and are not consumed until handshake success. An unstaked attacker can therefore repeatedly initiate handshakes it never completes, filling the shared `max_concurrent_connections()` slot pool and causing `incoming.refuse()` for legitimate connections from any IP, for the duration bounded by `QUIC_CONNECTION_HANDSHAKE_TIMEOUT` per attempt cycle.

### Finding Description
In `run_server`, incoming connections pass three checks before a task is spawned to complete the handshake: (1) `overall_connection_rate_limiter.current_tokens() == 0`, (2) `rate_limiter.is_allowed(&ip)`, (3) `ClientConnectionTracker::new(stats, qos.max_concurrent_connections())` [8](#0-7) . Checks (1) and (2) are non-mutating "peek" checks; the actual token consumption (`register_connection`, `consume_tokens(1)`) only occurs in `setup_connection` after a successful handshake [9](#0-8) . Check (3), however, unconditionally increments a process-global atomic `stats.open_connections` regardless of source IP, and is only decremented when the `ClientConnectionTracker` is dropped — which occurs either on handshake failure/timeout or later connection teardown [10](#0-9) .

Because the per-IP and global rate limiters never consume tokens for connections that don't complete the handshake, an attacker can repeatedly open new QUIC connection attempts and stall the handshake (e.g., withhold the final handshake packet) without ever being throttled by `is_allowed`/`current_tokens`, since those never see a corresponding `register_connection`/`consume_tokens` call for the stalled attempts. Each stalled attempt occupies one slot of the shared `max_concurrent_connections()` budget — `(max_staked_connections + max_unstaked_connections) * 5/4` in `SwQos::max_concurrent_connections` [11](#0-10)  (or `max_staked_connections * 5/4` in `SimpleQos` [12](#0-11) ). Once this global counter reaches the limit, subsequent legitimate connections from *any* IP fail `ClientConnectionTracker::new` and are refused via `incoming.refuse()` [13](#0-12) .

The per-peer/IP connection cap (`max_connections_per_peer`) enforced in `ConnectionTable::try_add_connection` does not help here because it is only applied after the handshake succeeds and the connection reaches `try_add_connection` in `SwQos`/`SimpleQos` [14](#0-13) ; pre-handshake stalled attempts never reach this stage.

### Impact Explanation
This is a QoS/availability degradation: a single unstaked, unauthenticated attacker can consume the entire shared `open_connections` budget with pre-handshake stalled connections, causing the TPU QUIC server to reject all subsequent connection attempts (staked and unstaked alike) via `incoming.refuse()`. This violates the intended invariant (documented in the code's own comment block) that limits should be enforced per-IP/peer, not globally exhausted by one source. This matches the Agave bounty category of QoS evasion / node resource-exhaustion DoS affecting legitimate leader ingress.

### Likelihood Explanation
Preconditions are minimal: the attacker needs only to be an unprivileged remote client capable of initiating QUIC handshakes to the TPU port and choosing not to complete them. The attack is repeatable in cycles bounded by `QUIC_CONNECTION_HANDSHAKE_TIMEOUT`; sustaining the exhaustion requires the attacker to relaunch stalled attempts faster than the timeout window releases prior slots, which is feasible for a single high-bandwidth attacker given no other per-IP throttle applies to non-consuming "peek" checks.

### Recommendation
Consume (rather than merely peek) per-IP and overall rate-limiter tokens at the time of `Incoming` acceptance/tracker-creation (before handshake), not after handshake success, so that stalled/abandoned handshakes are properly charged against the initiating IP's budget. Additionally, consider tracking `open_connections`/in-flight pre-handshake attempts per-IP (or reuse the existing per-IP token bucket to bound `outstanding_incoming_connection_attempts`) so that global slot exhaustion cannot be caused by a single source IP.

### Proof of Concept
Integration test plan (using existing `setup_quic_server` test harness in `streamer/src/nonblocking/quic.rs`):
1. Configure `SwQosConfig` with small `max_staked_connections`/`max_unstaked_connections` so `max_concurrent_connections()` is a small deterministic number `N`.
2. From a single client IP, open `N` QUIC connections but withhold the final handshake step (e.g., use a raw UDP socket / custom quinn client config that sends only the Initial packet and never completes handshake, or drop the client endpoint before `await`ing the connect future) so `setup_connection`'s `connecting.await` stays pending.
3. Assert `stats.open_connections.load(Ordering::Relaxed) == N` while stalled connections remain outstanding (before `QUIC_CONNECTION_HANDSHAKE_TIMEOUT` elapses).
4. From a second, distinct client IP, attempt a normal legitimate connection and assert it is refused (`stats.refused_connections_too_many_open_connections` increments) despite never having made a prior attempt from that IP — demonstrating cross-IP denial caused by single-IP global slot exhaustion.
5. Additionally assert that `stats.connection_rate_limited_per_ipaddr` and `stats.connection_rate_limited_across_all` remain unincremented for the attacker's IP during the stalled attempts, confirming the rate limiters never charged the attacker because tokens are only consumed post-handshake.

impl Drop for ClientConnectionTracker {
    /// When this is dropped, reduce the open connection count.
    fn drop(&mut self) {
        self.stats.open_connections.fetch_sub(1, Ordering::Relaxed);
    }
}

impl ClientConnectionTracker {
    /// Check the max_concurrent_connections limit and if it is within the limit
    /// create ClientConnectionTracker and increment open connection count. Otherwise returns Err
    fn new(stats: Arc<StreamerStats>, max_concurrent_connections: usize) -> Result<Self, ()> {
        let open_connections = stats.open_connections.fetch_add(1, Ordering::Relaxed);
        if open_connections >= max_concurrent_connections {
            stats.open_connections.fetch_sub(1, Ordering::Relaxed);
            debug!(
                "There are too many concurrent connections opened already: open: \
                 {open_connections}, max: {max_concurrent_connections}"
            );
            return Err(());
        }

        Ok(Self { stats })
    }
}
