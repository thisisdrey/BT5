### Title
Unbounded/negative Exchange pool balance in legacy Bancor-formula path allows draining more tokens than the pool holds - ([File: chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java])

### Summary
TRON's on-chain TRC10↔TRX/TRC10↔TRC10 AMM ("Exchange") uses a Bancor-style bonding-curve formula computed with floating-point `Math.pow` in `ExchangeProcessor`. The resulting `buyTokenQuant` is subtracted from the pool's balance without any check that the pool actually has enough tokens to pay it out, **unless** a dynamic-property flag (`allowHardenExchangeCalculation`) is enabled. This is directly analogous to the PLTD incident, where an attacker skewed an AMM pool's reserve ratio to an extreme and then extracted more value than the pool could legitimately back.

### Finding Description
`ExchangeCapsule.transaction()` computes `buyTokenQuant` via the legacy `ExchangeProcessor` (double-precision `Math.pow`) and then updates the pool balances: [1](#0-0) 

Crucially, the negative-balance guard is only applied when `hardenedCalc` (i.e. `allowHarden()`) is true: [2](#0-1) 

`allowHarden()` is gated behind a dynamic property that must be turned on by proposal: [3](#0-2) 

When this flag is not enabled (its legacy/default state on the affected chain), `ExchangeTransactionActuator.execute()` calls `exchangeCapsule.transaction()` with `hardenedCalc=false`, and then unconditionally credits the trader with `anotherTokenQuant` regardless of whether it exceeds the pool's real reserve, while the pool's stored balance (`newSecondTokenBalance`/`newFirstTokenBalance`) can silently go negative and get persisted: [4](#0-3) 

Validation only checks that quantities are positive, that neither pool side is currently `0`, and that the resulting counter-quantity meets the caller-specified `expected` minimum — it never checks that the computed `anotherTokenQuant` is `<=` the pool's actual counter-token balance: [5](#0-4) 

Because the Bancor curve here is recomputed from scratch on every call with a fixed virtual `supply = 1_000_000_000_000_000_000L` (not persisted state) using floating-point exponentiation (`Math.pow(x, 0.0005)` / `Math.pow(x, 2000.0)`), an attacker can (a) execute a very large trade that skews the pool ratio to an extreme (analogous to reducing the PLTD reserve to `1`), and (b) exploit the resulting floating-point precision error in the un-hardened formula to make `exchangeFromSupply()` return a `buyTokenQuant` larger than the actual reserve of the counter token, since nothing prevents that: [6](#0-5) 

This lets an unprivileged transaction broadcaster mint an unbacked balance of TRX/TRC10 out of the exchange pool (the pool balance capsule can go negative while the trader's account is credited real, spendable tokens), functionally equivalent to draining "all BUSD" from the PLTD pool in the cited incident.

### Impact Explanation
An attacker who can drive an Exchange pool's reserve ratio to an extreme (via one or a sequence of `ExchangeTransactionContract`/`ExchangeInjectContract`/`ExchangeWithdrawContract` calls, all broadcastable by anyone) can obtain more counter-tokens than the pool's true reserve while the pool's on-chain reported balance is allowed to go negative in the non-hardened path. This is unbacked-balance creation / permanent fund drain from other liquidity participants — a Medium/High-severity issue depending on how much TRX/TRC10 value is locked in affected Exchange pools.

### Likelihood Explanation
Exploitability depends entirely on whether `allowHardenExchangeCalculation` is enabled on the target network. If disabled (its legacy/default state), the vulnerable, unguarded code path in `ExchangeCapsule.transaction()` is live and reachable by any account with sufficient TRX/TRC10 to execute `ExchangeTransactionContract` calls — no special privilege, precompile, or smart-contract access is required, only standard signed transactions. I could not verify from the available index what value `allowHardenExchangeCalculation` currently defaults to in `DynamicPropertiesStore`/genesis config, which is the key open question determining whether this is live-exploitable today or already mitigated by a hardening proposal.

### Recommendation
- Always enforce the `newFirstTokenBalance < 0 || newSecondTokenBalance < 0` guard in `ExchangeCapsule.transaction()`, independent of the `hardenedCalc`/`allowHardenExchangeCalculation` flag, so the legacy path cannot pay out more than the pool holds.
- Additionally bound `anotherTokenQuant` in `ExchangeTransactionActuator.doValidate()`/`execute()` to be `<=` the exchange's current counter-token balance before crediting the trader.
- Consider replacing the floating-point Bancor computation (`ExchangeProcessor`) entirely with the fixed-point `SafeExchangeProcessor` (BigDecimal-based) unconditionally, removing the legacy double-based formula.

### Proof of Concept
Conceptual (cannot be fully validated without confirming the current default of `allowHardenExchangeCalculation`):
1. Attacker (or two colluding accounts) locates/creates an `Exchange` pool with a small counter-token balance.
2. Attacker submits an `ExchangeTransactionContract` selling a very large amount of the other token, driving the counter-token reserve toward an extreme skew via `ExchangeCapsule.transaction()` (`hardenedCalc=false` path).
3. Attacker submits a follow-up `ExchangeTransactionContract` trading back; because `ExchangeProcessor.exchange()` uses double-precision `Math.pow` and no post-hoc balance check exists in the non-hardened branch (`chainbase/.../ExchangeCapsule.java:160-162`), `buyTokenQuant` can exceed the pool's actual counter-token balance, letting the attacker walk away with more tokens than the pool held while `secondTokenBalance`/`firstTokenBalance` is persisted as a negative or otherwise unbacked value.

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
