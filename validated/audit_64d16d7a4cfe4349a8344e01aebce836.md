### Title
Unbounded array preallocation from attacker-controlled length header in TVM precompiled contract ABI decoding - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
`PrecompiledContracts.extractBytes32Array`, `extractBytesArray`, and `extractSigArray` read a "length" word directly from precompile call data and use it, unchecked, to preallocate a Java array (`new byte[len][]`) before validating that the call data actually contains that many entries. This mirrors the go-ipld-prime advisory pattern: a length/size header taken from untrusted input is used as an allocation hint with no upper bound and no accounting against the transaction's energy/resource budget at the point of allocation.

### Finding Description
In `PrecompiledContracts.java`: [1](#0-0) [2](#0-1) [3](#0-2) 

All three helpers do:
```
int len = words[offset].intValueSafe();
byte[][] bytesArray = new byte[len][];   // allocated before any bound check on data.length
for (int i = 0; i < len; i++) { ... }
```
`len` comes from `DataWord.intValueSafe()`, applied to a 256-bit word taken verbatim from the smart-contract call data (`words` is the ABI-decoded word array of the precompile's input). Unlike `isValidAbiEncoding` (used elsewhere in the same file to sanity-check header/tail sizing before touching data), these three extraction helpers perform **no comparison of `len` against the actual size of `data`/`words`** before allocating the `byte[len][]` backing array. This is structurally identical to the CBOR bug: the "declared collection size" is trusted as a preallocation hint, is not capped, and is not charged against any budget (the TVM's energy metering for these opcodes accounts for memory expansion and word-count-based CALLDATA costs, not for the array-length header value itself) before the allocation happens.

Because `len` is an `int` derived from a 256-bit value (clamped only to `Integer.MAX_VALUE`/`Integer.MIN_VALUE` by `intValueSafe()`), an attacker can supply a small calldata payload (just enough bytes to satisfy `words[offset]`) that declares an enormous entry count, causing the JVM to attempt to allocate an array of up to `Integer.MAX_VALUE` object-array slots (~16GB for `byte[Integer.MAX_VALUE][]` header alone) synchronously, before the loop even reaches array-index bounds errors on `data`.

### Impact Explanation
A single unprivileged, signed transaction (or an internal CALL from any deployed contract) invoking one of the precompiled contracts that use `extractBytes32Array`/`extractBytesArray`/`extractSigArray` with crafted calldata can force the node executing/validating that transaction to attempt a massive heap allocation. This can throw `OutOfMemoryError` inside VM execution, and depending on where the OOM is caught (or not), can degrade or crash the node process executing the transaction — a node crash/DoS impact, consistent with the CWE-770 classification and CVSS `A:H` in the source advisory. Because all full nodes must execute the same transaction identically during block application, this could affect multiple nodes simultaneously if the transaction reaches consensus execution.

### Likelihood Explanation
Reachable directly by any address able to send a TVM transaction (TriggerSmartContract) that calls a precompiled-contract address using one of the affected helper functions, or via any deployed contract that internally calls into that precompile. No special privileges are required — this matches the "unprivileged transaction broadcaster / contract deployer / order placer" reachability requirement. The exact precompile(s) wired to these helpers were not conclusively identified in the available index (naming and adjacent test files such as `BatchValidateSignContractTest.java` and `ValidateMultiSignContractTest.java` strongly suggest `BatchValidateSign`/`ValidateMultiSign`-style precompiles), so full end-to-end confirmation of the calling precompile's `execute()` wiring is not verified against the search results and should be confirmed directly in the repository before remediation.

### Recommendation
Before allocating `new byte[len][]` (or similar) in `extractBytes32Array`, `extractBytesArray`, and `extractSigArray`, validate `len` against the actual size of `words`/`data` (similar to the bound check already used in `isValidAbiEncoding`), and/or cap `len` to a small sane maximum (e.g., matching the maximum number of signatures/hashes the calling precompile logically supports) before allocation. Reject with an early `false`/empty result when the declared length is inconsistent with the available call data, rather than trusting the header value as a preallocation size.

### Proof of Concept
1. Craft a `TriggerSmartContract` transaction that calls a precompiled contract whose `execute()` invokes `extractBytesArray`/`extractBytes32Array`/`extractSigArray` (e.g., a batch-signature-validation precompile).
2. Set the ABI-encoded "array length" word at the expected `offset` to a very large value (e.g., `0x7FFFFFFF`), while keeping the rest of the calldata minimal/short.
3. Submit the transaction; on execution, `words[offset].intValueSafe()` returns the large `len`, and `new byte[len][]` is allocated immediately, before any check that `data`/`words` actually contains `len` entries, causing excessive memory allocation / `OutOfMemoryError` on the executing node.
