### Title
DeleteAccount permits removal of an account with outstanding PostponedReceipt/PendingDataCount rows, letting a stale self-authorized action later execute against a recreated account - (File: `runtime/runtime/src/actions.rs`)

### Finding Description
`check_actor_permissions` for `Action::DeleteAccount` only verifies `actor_id == account_id` and `account.locked().is_zero()`; it never inspects `TrieKey::PostponedReceiptId`, `TrieKey::PendingDataCount`, or `TrieKey::PostponedReceipt` rows keyed by the account being deleted. [1](#0-0) 
`remove_account`, invoked from `action_delete_account`, only clears `Account`, `ContractCode`, `AccessKey`/gas-key rows and `ContractData`; it does not remove any `PostponedReceipt`, `PendingDataCount`, `PostponedReceiptId`, `PromiseYieldReceipt`, `PromiseYieldStatus`, `YieldIdToDataId`, or `DataIdToYieldId` rows for the account. [2](#0-1) [3](#0-2) 

A postponed action receipt is created whenever an account issues a callback (`promise_then`) whose `input_data_ids` are not yet satisfied: `process_action_receipt` stores `PendingDataCount`/`PostponedReceiptId` and the serialized `Receipt` itself, keyed by `(receiver_id, receipt_id)`. [4](#0-3) 
When the missing `DataReceipt` eventually arrives, `process_receipt` looks the postponed receipt up purely by `receiver_id`/`receipt_id`, and hands it to `apply_action_receipt`, which loads the account fresh from state at that time via `get_account(state_update, account_id)` — not the account as it existed when the receipt was postponed. [5](#0-4) [6](#0-5) 
The `actor_id` used for `check_actor_permissions` on the postponed receipt is `receipt.predecessor_id()`, fixed at receipt-creation time. [7](#0-6) 

Combining these facts: if an account self-schedules a postponed callback whose action list contains a self-authorized privileged action (`DeployContract`, `AddKey`, `DeleteKey`, `Stake`, `DeleteAccount`, `UseGlobalContract`, `WithdrawFromGasKey` — all gated only by `actor_id == account_id` in `check_actor_permissions`), and the account is deleted via `DeleteAccount` while that receipt is still pending, the stale `PostponedReceipt`/`PendingDataCount` rows survive the deletion. If the same `account_id` string is later recreated (e.g., a subaccount name released and re-issued to a different key set), the stale receipt will still pass `check_actor_permissions` (since it only compares account-id strings, with no notion of "account generation"/incarnation) and will execute its privileged self-action against whatever account currently occupies that name once the outstanding data arrives.

### Impact Explanation
This is an authorization-escalation primitive: a privileged, self-authorized action (e.g. `DeleteAccount` with `beneficiary_id` chosen by the original attacker, or `AddKey` installing a backdoor key) queued by one incarnation of an account can fire later against a different incarnation of the same `account_id`, without the current owner's key ever countersigning the action. In the `DeleteAccount` sub-case this directly maps to theft/loss of the recreated account's balance, sent to a beneficiary chosen before the account was ever re-created.

However, exploiting this for actual cross-party fund theft requires that a *different* party gain control of the exact same `account_id` after deletion. Under nearcore's account-creation model, only the direct parent (`CreateAccount` restricted to the immediate parent for named subaccounts, or the same public key for implicit/deterministic accounts) can "recreate" a given `account_id`. This means the same attacker who deleted the account is also the only party who can recreate it (or reassign keys on it) under stock protocol rules — a purely self-inflicted scenario provides no attacker gain. Turning this into third-party fund loss requires an external mechanism (e.g., a subaccount-name marketplace/registrar dApp reissuing "expired"/released subaccount names to new owners) that is outside nearcore's own code and outside the "no misconfiguration/external-app dependency" scope of this audit.

### Likelihood Explanation
The underlying code gap is real and cheaply reproducible by an unprivileged user: deploy a contract, self-call with `promise_then` (creating a postponed receipt with `input_data_ids`), self-delete the account while the postponed row is still outstanding (which today succeeds because no precondition checks `PostponedReceiptId`/`PendingDataCount`/`PostponedReceipt` for the account), then let the missing data arrive. But turning this into "theft of another party's funds" or "authorization escalation across accounts" (as scoped) additionally requires a way for a *different* party to legitimately take over the exact deleted `account_id`, which is not achievable purely through protocol-level actions available to an unprivileged attacker without an external, non-protocol mechanism (name marketplace, custom registrar contract, etc.).

### Recommendation
If closing this class of bug is desired, `action_delete_account` (or `check_actor_permissions`/`check_account_existence` ahead of it) should reject deletion when any `TrieKey::PostponedReceiptId`, `TrieKey::PendingDataCount`, or `TrieKey::PostponedReceipt` row exists for the account (and, for completeness, also `PromiseYieldReceipt`/`PromiseYieldStatus`/`YieldIdToDataId`/`DataIdToYieldId` rows, since yielded promises have the same "recreated account executes stale privileged action" shape). This precondition — "no in-flight postponed/yielded work referencing this account" — would fully close the specific bug class described here (a stale self-authorized privileged action firing against a differently-owned recreated account), since it removes the possibility of the account being deleted (and later recreated under new ownership) while such a stale reference exists. It would not by itself need to address the broader, separate question of whether NEAR's account-naming/reuse model should prevent third parties from ever taking over a previously-used `account_id`.

### Proof of Concept
Unit test in `runtime/runtime/src/actions.rs` (or `actions_test_utils.rs`) style:
1. Set up a `TrieUpdate` with an account `alice` (locked = 0).
2. Manually write `TrieKey::PostponedReceiptId { receiver_id: alice, data_id }`, `TrieKey::PendingDataCount { receiver_id: alice, receipt_id }`, and a serialized postponed `Receipt` (containing, e.g., `Action::DeleteAccount { beneficiary_id: attacker }` with `predecessor_id == alice`) via `set`/`set_postponed_receipt`, simulating an in-flight postponed callback.
3. Call `action_delete_account` (or run a `DeleteAccount` receipt through `apply_action`) for `alice`.
4. **Current behavior (finding):** the call succeeds (`result.result.is_ok()`), the `Account`/`ContractCode`/`AccessKey` rows are removed, but the `PostponedReceiptId`/`PendingDataCount`/`PostponedReceipt` rows remain in the trie.
5. **Expected behavior (if precondition existed):** `action_delete_account` should fail with a new `ActionErrorKind` (e.g., `DeleteAccountHasPendingReceipts`) and leave the account untouched, mirroring how `DeleteAccountStaking` already rejects deletion when `locked() != 0`.

pub(crate) fn action_delete_account(
    state_update: &mut TrieUpdate,
    account: &mut Option<Account>,
    actor_id: &mut AccountId,
    receipt: &Receipt,
    result: &mut ActionResult,
    account_id: &AccountId,

    config: &RuntimeConfig,
    current_protocol_version: ProtocolVersion,
) -> Result<(), StorageError> {
    let account_ref = account.as_ref().unwrap();
    let account_storage_usage = if ProtocolFeature::FixDeleteAccountGlobalContractStorageUsage
        .enabled(current_protocol_version)
    {
        let contract_storage = get_contract_storage_usage(state_update, account_id, account_ref)?;
        account_ref.storage_usage().saturating_sub(contract_storage)
    } else {
        // Legacy behavior: only subtracts local contract code, misses the
        // global contract identifier overhead.
        let account_storage_usage = account_ref.storage_usage();
        let code_len = get_code_len_or_default(
            state_update,
            account_id.clone(),
            account_ref.local_contract_hash().unwrap_or_default(),
        )?;
        debug_assert!(
            code_len == 0 || account_storage_usage > code_len,
            "account storage usage should be larger than code size. storage usage: {}, code size: {}",
            account_storage_usage,
            code_len
        );
        account_storage_usage.saturating_sub(code_len)
    };
    if account_storage_usage > Account::MAX_ACCOUNT_DELETION_STORAGE_USAGE {
        result.result =
            Err(ActionErrorKind::DeleteAccountWithLargeState { account_id: account_id.clone() }
                .into());
        return Ok(());
    }
    let gas_key_balance_to_burn = compute_gas_key_balance_sum(state_update, account_id)?;
    if gas_key_balance_to_burn > GasKeyInfo::MAX_BALANCE_TO_BURN {
        result.result = Err(ActionErrorKind::GasKeyBalanceTooHigh {
            account_id: account_id.clone(),
            public_key: None,
            balance: gas_key_balance_to_burn,
        }
        .into());
        return Ok(());
    }
    // We use current amount as a pay out to beneficiary.
    let account_balance = account_ref.amount();
    if account_balance > Balance::ZERO {
        result
            .new_receipts
            .push(Receipt::new_balance_refund(&delete_account.beneficiary_id, account_balance));
    }
    let remove_result = remove_account(state_update, account_id)?;
    result.tokens_burnt =
        result.tokens_burnt.checked_add(gas_key_balance_to_burn).ok_or_else(|| {
            StorageError::StorageInconsistentState("tokens_burnt overflow".to_string())
        })?;
    if remove_result.gas_key_nonce_count > 0 {
        let compute = storage_removes_compute(
            &config.wasm_config.ext_costs,
            remove_result.gas_key_nonce_count,
            remove_result.gas_key_nonce_total_key_bytes,
            AccessKey::NONCE_VALUE_LEN * remove_result.gas_key_nonce_count,
        );
        result.compute_usage = safe_add_compute(result.compute_usage, compute).map_err(|_| {
            StorageError::StorageInconsistentState("compute_usage overflow".to_string())
        })?;
    }
    *actor_id = receipt.predecessor_id().clone();
    *account = None;
    Ok(())
}

pub fn remove_account(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
) -> Result<RemoveAccountResult, StorageError> {
    state_update.remove(TrieKey::Account { account_id: account_id.clone() });
    state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });

    let mut gas_key_nonce_count: usize = 0;
    let mut gas_key_nonce_total_key_bytes: usize = 0;

    // Removing access keys and gas key nonces
    let lock = state_update.trie().lock_for_iter();
    let mut keys_to_remove: Vec<TrieKey> = Vec::new();
    for raw_key in state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_access_keys(account_id), &lock)?
    {
        let raw_key = raw_key?;
        let key_handle = trie_key_parsers::parse_key_handle_from_access_key_key(
            &raw_key, account_id,
        )
        .map_err(|_e| {
            StorageError::StorageInconsistentState(
                "Can't parse key handle from raw key for AccessKey".to_string(),
            )
        })?;
        let nonce_index =
            trie_key_parsers::parse_nonce_index_from_gas_key_key(&raw_key, account_id, &key_handle)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse nonce index from raw key for AccessKey".to_string(),
                    )
                })?;
        if let Some(index) = nonce_index {
            gas_key_nonce_count += 1;
            gas_key_nonce_total_key_bytes += raw_key.len();
            keys_to_remove.push(TrieKey::gas_key_nonce(
                account_id.clone(),
                key_handle.clone(),
                index,
            ));
        } else {
            keys_to_remove.push(TrieKey::access_key(account_id.clone(), key_handle.clone()));
        }
    }
    drop(lock);

    for trie_key in keys_to_remove {
        state_update.remove(trie_key);
    }

    // Removing contract data
    let lock = state_update.trie().lock_for_iter();
    let data_keys = state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_contract_data(account_id, &[]), &lock)?
        .map(|raw_key| {
            trie_key_parsers::parse_data_key_from_contract_data_key(&raw_key?, account_id)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse data key from raw key for ContractData".to_string(),
                    )
                })
                .map(Vec::from)
        })
        .collect::<Result<Vec<_>, _>>()?;
    drop(lock);

    for key in data_keys {
        state_update.remove(TrieKey::ContractData { account_id: account_id.clone(), key });
    }
    Ok(RemoveAccountResult { gas_key_nonce_count, gas_key_nonce_total_key_bytes })
}
