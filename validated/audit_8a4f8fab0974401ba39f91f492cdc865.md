### Title
Cross-Contract StackerDB Chunk Signature Replay (Signature Reuse Via Front-Running Analog) - (File: libstackerdb/src/libstackerdb.rs)

### Summary
`SlotMetadata::sign`/`verify` (the signature scheme that authenticates every StackerDB chunk write) only commits to `slot_id`, `slot_version`, and `data_hash` — it never binds the signature to the specific StackerDB smart contract (application/message type) the chunk is destined for. Because the Stacks signer-set boot contracts (`.signers-0-*` / `.signers-1-*`) all derive their slot-to-address mapping from the *same* underlying `.signers` list for a given signer set, the same signer address occupies the same `slot_id` across every message-type contract in that set (e.g. `BlockResponse`, `Transactions`, `StateMachineUpdate`). This lets an unprivileged network peer capture a legitimately-signed chunk from one StackerDB contract and replay it, unmodified, into a *different* StackerDB contract that shares the same signer/slot mapping — exactly analogous to the reported "signature reuse via front-running" bug class where a signature lacks binding to the intended usage context and can be stolen/replayed elsewhere.

### Finding Description
`SlotMetadata::auth_digest()` computes the signed digest as: [1](#0-0) 
This digest — and therefore the signature produced by `sign()` and checked by `verify()` — never includes the StackerDB's `QualifiedContractIdentifier`: [2](#0-1) 

Both write paths validate a chunk purely against the *target* contract's own slot-owner table, independent of where the chunk actually originated:
- HTTP POST path: `StackerDBTx::try_replace_chunk` looks up `slot_validation.signer` for the given `smart_contract` and then calls `slot_desc.verify(&slot_validation.signer)`, which recomputes the digest from `slot_id`/`slot_version`/`data_hash` alone: [3](#0-2) 
- P2P push/sync path: `validate_received_chunk` similarly resolves `get_slot_signer` for the given `smart_contract_id` and calls `slot_metadata.verify(&addr)`: [4](#0-3) 

Critically, the signer-to-slot mapping is identical across every message-type contract within a signer set, because each per-message contract simply forwards to the shared `.signers` boot contract page: [5](#0-4) [6](#0-5) 

So a chunk signed by signer `S` for slot `5` in `.signers-0-2` (e.g. `BlockResponse`) is a byte-for-byte valid signature for slot `5` in `.signers-0-5` (e.g. `Transactions`) or `.signers-0-<StateMachineUpdate>`, since `S` occupies slot `5` in all of them and the signature never says which contract it was meant for. Successfully-stored chunks are then rebroadcast network-wide via `process_stacker_db_chunks`: [7](#0-6) 

### Impact Explanation
An unprivileged remote peer who has observed (via normal, permissionless StackerDB replication) any signer's legitimately-signed chunk can replay it into a *different* StackerDB message-type replica for the same signer, as long as the replayed `slot_version` exceeds the current version in the target slot (trivial, since each per-contract version counter advances independently). This is an unauthorized write into StackerDB state that the true signer never intended for that contract, and it propagates automatically to the rest of the network via `broadcast_message`. Depending on which message-type contract is targeted, this misattributed data can corrupt signer-message consumers that deserialize slot contents expecting a specific `SignerMessageV0` variant (e.g. `StackerDBListener`/`GlobalStateEvaluator`), producing bogus/garbage "signer state" entries network-wide without ever needing the signer's private key.

### Likelihood Explanation
No secrets are required — the attacker only needs a chunk that was legitimately broadcast at some point (StackerDB chunks are, by design, publicly replicated/downloadable) and a target contract/slot combination with a lower version, which is readily achievable given independent version counters per message type. The write is exposed both over the authenticated-free `/v2/stackerdb/*/chunks` HTTP RPC and the P2P `StackerDBPushChunk`/inventory sync paths, so the vulnerability is reachable by any peer without privileges.

### Recommendation
Bind the StackerDB write signature to the specific application/contract it is intended for by including the `QualifiedContractIdentifier` (and ideally the intended `MessageSlotID`/message type) inside `SlotMetadata::auth_digest()`, so a signature produced for one StackerDB contract can never validate against another. This mirrors the report's remediation of adding a nonce/context binding to prevent a signed artifact from being replayed outside its intended scope.

### Proof of Concept
1. Observe (via normal StackerDB chunk download/sync — no privileges needed) a validly-signed `StackerDBChunkData { slot_id: 5, slot_version: V, sig, data }` written by signer `S` into `.signers-0-2` (message type A).
2. Confirm that `.signers-0-5` (a different message type B) assigns the same slot `5` to the same signer `S` (guaranteed, since both contracts read the identical page from `.signers`), and that its current stored slot version for slot `5` is `< V`.
3. Submit an HTTP `POST /v2/stackerdb/<signers-0-5 contract>/chunks` (or a P2P `StackerDBPushChunk`) with the identical `(slot_id=5, slot_version=V, sig, data)` but the contract identifier of message type B.
4. `try_replace_chunk`/`validate_received_chunk` for contract B resolve `S` as the slot-5 owner, recompute `auth_digest()` from the untouched `(slot_id, slot_version, data_hash)`, and accept the signature as valid — even though `S` never signed anything intended for contract B.
5. The chunk is stored and then rebroadcast network-wide via `process_stacker_db_chunks`, propagating message-A payload data as forged content inside message-B's StackerDB replica across the network.

    /// Get the digest to sign that authenticates this chunk data and metadata
    fn auth_digest(&self) -> Sha512Trunc256Sum {
        let mut hasher = Sha512_256::new();
        hasher.update(self.slot_id.to_be_bytes());
        hasher.update(self.slot_version.to_be_bytes());
        hasher.update(self.data_hash.0);
        Sha512Trunc256Sum::from_hasher(hasher)
    }

    /// Verify that a given principal signed this chunk metadata.
    /// Note that the address version is ignored.
    pub fn verify(&self, principal: &StacksAddress) -> Result<bool, Error> {
        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )
        .map_err(|ve| Error::VerifyingError(ve.to_string()))?;

        let pubkh = Hash160::from_node_public_key(&pubk);
        Ok(pubkh == *principal.bytes())
    }

    /// Otherwise, this errors out with Error::StaleChunk
    pub fn try_replace_chunk(
        &self,
        smart_contract: &QualifiedContractIdentifier,
        slot_desc: &SlotMetadata,
        chunk: &[u8],
    ) -> Result<(), net_error> {
        // Check per-replica chunk-size cap.
        if (chunk.len() as u64) > self.config.chunk_size {
            return Err(net_error::StackerDBChunkTooBig(chunk.len()));
        }

        let slot_validation = self
            .get_slot_validation(smart_contract, slot_desc.slot_id)?
            .ok_or(net_error::NoSuchSlot(
                smart_contract.clone(),
                slot_desc.slot_id,
            ))?;

        if !slot_desc.verify(&slot_validation.signer)? {
            return Err(net_error::BadSlotSigner(
                slot_validation.signer,
                slot_desc.slot_id,
            ));
        }
