## Finding: TRX/TRC10 Exchange (Bancor-style AMM) spot price is manipulable and can be sandwiched

### Title
Sandwich-attack on `ExchangeTransactionActuator` spot price due to reliance on instantaneous `ExchangeCapsule` reserve balances - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeTransactionActuator.java`)

### Summary
java-tron implements an on-chain constant-relay-supply AMM ("Exchange") for trading TRX against TRC10 tokens. The exchange rate for every trade is derived purely from the *current* on-chain reserve balances (`firstTokenBalance` / `secondTokenBalance`) stored in `ExchangeCapsule`, with no time-weighted average or external oracle input, analogous to the reported Uniswap V3 `slot0`/`sqrtPriceX96` spot-price read. Because any account can submit an `ExchangeTransactionContract` to trade against the pool, an attacker can manipulate the spot price immediately before a victim's trade and reverse it immediately after (sandwich attack), extracting value from the victim exactly as described in the external report.

### Finding Description
`ExchangeCapsule.transaction()` computes the output amount solely from the pool's current reserves at call time: [1](#0-0) 

`ExchangeTransactionActuator.execute()`/`doValidate()` calls this same instantaneous-reserve calculation to determine `anotherTokenQuant`, the amount the trader receives: [2](#0-1) 

The only protection against price manipulation is a caller-supplied `expected` (minimum-output) field, checked in `doValidate()`: [3](#0-2) 

This is functionally identical to an `amountOutMin` slippage check in a Uniswap-style swap, and like Uniswap's slippage guard, it is opt-in and set by the *caller*, not enforced with any minimum bound by the protocol. Any account can freely trade against the exchange (there is no permission check on the trader in `ExchangeTransactionActuator`, unlike `ExchangeInjectActuator`/`ExchangeWithdrawActuator` which are creator-only), so the reserves — and thus the "spot price" — can be moved arbitrarily by anyone within the same block ordering window that a validator/attacker controls.

### Impact Explanation
An attacker (e.g., a block-producing SR or any actor able to order transactions favorably, or simply a fast trader observing a pending victim transaction) can:
1. Submit an `ExchangeTransactionContract` trade that shifts the pool ratio unfavorably against the victim's intended trade.
2. Let the victim's `ExchangeTransactionContract` execute at the now-skewed price (if the victim used a loose or zero `expected` value, or the manipulation stays within their slippage tolerance).
3. Submit a reverse trade to restore the pool and capture the difference.

This results in a direct, unauthorized value transfer from the victim to the attacker — an "unauthorized account operation"/theft-of-funds outcome reachable purely by broadcasting ordinary signed `ExchangeTransactionContract` transactions, matching the impact class required.

### Likelihood Explanation
Likelihood is moderate: it requires the victim to either omit a tight `expected` bound or accept some slippage, and it is easiest for an entity with transaction-ordering power (e.g., an SR packing the block) but is also exploitable by any user who can race transactions into the same block via mempool observation, mirroring the exact "sandwich" scenario in the original report. The Exchange feature set is a first-class, reachable actuator with no special privilege requirement.

### Recommendation
Introduce manipulation resistance for the Exchange price, e.g.:
- Enforce a mandatory, protocol-level maximum single-trade price-impact bound instead of relying solely on an optional client-supplied `expected` value.
- Consider a TWAP-style cumulative price accumulator over the `ExchangeCapsule` reserves (analogous to Uniswap V2 TWAP) so that dependent computations (or third-party contracts reading exchange state) aren't forced to trust the instantaneous spot ratio.
- Rate-limit or cap intra-block reserve movement per exchange pool.

### Proof of Concept
1. Attacker observes a pending `ExchangeTransactionContract` from victim V trading `tokenA -> tokenB` against exchange `E` (via `ExchangeTransactionActuator`, calling `ExchangeCapsule.transaction()`) with `expected` set loosely or to `0`.
2. Attacker submits `ExchangeTransactionContract` A1: sell a large amount of `tokenA` into `E`, moving `firstTokenBalance`/`secondTokenBalance` unfavorably (see `ExchangeCapsule.transaction`, lines 124-158).
3. Validator orders A1 before V's transaction in the same block (or attacker simply wins the race in mempool propagation).
4. V's trade executes via `ExchangeTransactionActuator.execute()` at the skewed reserves, receiving less `tokenB` than the pre-manipulation rate would have given, while still passing V's loose `expected` check (line 219-221).
5. Attacker submits `ExchangeTransactionContract` A2 reversing the initial trade, restoring the pool and net profiting the difference extracted from V. [4](#0-3) [5](#0-4)

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
  }

@Slf4j(topic = "actuator")
public class ExchangeTransactionActuator extends AbstractExchangeActuator {

  public ExchangeTransactionActuator() {
    super(ContractType.ExchangeTransactionContract, ExchangeTransactionContract.class);
  }

  @Override
  public boolean execute(Object object) throws ContractExeException {
    TransactionResultCapsule ret = (TransactionResultCapsule) object;
    if (Objects.isNull(ret)) {
      throw new RuntimeException(ActuatorConstant.TX_RESULT_NULL);
    }

    long fee = calcFee();
    AccountStore accountStore = chainBaseManager.getAccountStore();
    DynamicPropertiesStore dynamicStore = chainBaseManager.getDynamicPropertiesStore();
    ExchangeStore exchangeStore = chainBaseManager.getExchangeStore();
    ExchangeV2Store exchangeV2Store = chainBaseManager.getExchangeV2Store();
    AssetIssueStore assetIssueStore = chainBaseManager.getAssetIssueStore();
    try {
      final ExchangeTransactionContract exchangeTransactionContract = this.any
          .unpack(ExchangeTransactionContract.class);
      AccountCapsule accountCapsule = accountStore
          .get(exchangeTransactionContract.getOwnerAddress().toByteArray());

      ExchangeCapsule exchangeCapsule = Commons
          .getExchangeStoreFinal(dynamicStore, exchangeStore, exchangeV2Store)
          .get(ByteArray.fromLong(exchangeTransactionContract.getExchangeId()));

      byte[] firstTokenID = exchangeCapsule.getFirstTokenId();
      byte[] secondTokenID = exchangeCapsule.getSecondTokenId();

      byte[] tokenID = exchangeTransactionContract.getTokenId().toByteArray();
      long tokenQuant = exchangeTransactionContract.getQuant();

      byte[] anotherTokenID;
      long anotherTokenQuant = exchangeCapsule.transaction(tokenID, tokenQuant,
          dynamicStore.allowStrictMath(), allowHarden());

      if (Arrays.equals(tokenID, firstTokenID)) {
        anotherTokenID = secondTokenID;
      } else {
        anotherTokenID = firstTokenID;
      }

      long newBalance = subtractExact(accountCapsule.getBalance(), calcFee());
      accountCapsule.setBalance(newBalance);

      if (Arrays.equals(tokenID, TRX_SYMBOL_BYTES)) {
        accountCapsule.setBalance(subtractExact(newBalance, tokenQuant));
      } else {
        accountCapsule.reduceAssetAmountV2(tokenID, tokenQuant, dynamicStore, assetIssueStore);
      }

      if (Arrays.equals(anotherTokenID, TRX_SYMBOL_BYTES)) {
        accountCapsule.setBalance(addExact(newBalance, anotherTokenQuant));
      } else {
        accountCapsule
            .addAssetAmountV2(anotherTokenID, anotherTokenQuant, dynamicStore, assetIssueStore);
      }

      accountStore.put(accountCapsule.createDbKey(), accountCapsule);

      Commons.putExchangeCapsule(exchangeCapsule, dynamicStore, exchangeStore, exchangeV2Store,
          assetIssueStore);

      ret.setExchangeReceivedAmount(anotherTokenQuant);
      ret.setStatus(fee, code.SUCESS);
    } catch (ItemNotFoundException | InvalidProtocolBufferException
        | ContractValidateException | ArithmeticException e) {
      logger.debug(e.getMessage(), e);
      ret.setStatus(fee, code.FAILED);
      throw new ContractExeException(e.getMessage());
    }
    return true;
  }
