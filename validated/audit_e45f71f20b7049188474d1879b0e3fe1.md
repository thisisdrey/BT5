### Title
Peer-controlled `AttachmentPage.inventory` bits combined with a `ReliabilityReport::score()` that is dominated by request *count* rather than success *rate* lets an attacker permanently monopolize download attempts for an attachment it never delivers - (`stackslib/src/net/atlas/download.rs`, `stackslib/src/net/api/getattachmentsinv.rs`)

### Summary
`RPCGetAttachmentsInvRequestHandler::try_handle_request` returns whatever `AtlasDB.get_attachments_available_at_page_index` reports for the *responding node's own* database, so a malicious peer can trivially claim `inventory[position_in_page] == 1` for a `content_hash` it never actually holds. `AttachmentsBatchStateContext::get_prioritized_attachments_requests` then adds that peer to `sources` for the corresponding `AttachmentRequest`, and `get_most_reliable_source`/`Ord for AttachmentRequest`/`Ord for ReliabilityReport` pick a single URL to actually query. Because `ReliabilityReport::score()` is effectively `n + (1 if all requests ever succeeded else 0)` (an integer-truncation bug), any peer that simply answers more requests - truthfully or not - out-scores a peer with fewer but all-successful requests, so a lying, high-volume peer can durably win the "most reliable source" selection and be the only one ever queried for the real attachment bytes.

### Finding Description
The chain of relevant code:

1. `RPCGetAttachmentsInvRequestHandler::try_handle_request` builds the response purely from the local `AtlasDB`, with no cross-check against actual attachment content: [1](#0-0) . `AtlasDB::get_attachments_available_at_page_index` simply reads the `is_available` column the *responding* peer controls in its own DB: [2](#0-1) . A remote, unprivileged peer can freely misreport this since it is unauthenticated content about its own local state.

2. `AttachmentsBatchStateContext::get_prioritized_attachments_requests` builds `sources` for a `content_hash` from every peer whose response claims bit `1` at `position_in_page`, without any independent verification: [3](#0-2) . If `sources` is non-empty, an `AttachmentRequest` is enqueued once per `content_hash` (`enqueued.insert`), [4](#0-3) .

3. `AttachmentRequest::get_most_reliable_source` / `Requestable::get_url` picks a **single** URL (max score) to actually issue the HTTP GET to - not all listed sources: [5](#0-4) . Only that one URL is contacted for the round; other listed "sources" (including a genuinely-holding honest peer) are never queried for this content_hash in this round.

4. `ReliabilityReport::score()` has an integer-truncation bug: since `total_requests_success <= total_requests_sent = n`, the term `total_requests_success * 1000 / (n * 1000)` evaluates to `1` only when `success == n` and to `0` otherwise, so `score = n + (0 or 1)`. This means the score is dominated by the sheer count of requests answered, not by the fraction that were true/successful: [6](#0-5) . Crucially, `bump_failed_requests` still increments `total_requests_sent` (`n`), so *every* response - success or failure - increases score: [7](#0-6) .

5. When the actual attachment fetch to the "most reliable" attacker URL fails or returns garbage, `extend_with_attachments` only bumps that peer's failed-request counter and moves on - it does not retry against another listed source in the same round: [8](#0-7) . The batch is then requeued and retried up to `max_attachment_retry_count`, after which it is dropped entirely: [9](#0-8) . Reliability reports persist across retries in `AttachmentsDownloader.reliability_reports`, so a peer that answers many (cheap, unauthenticated) inventory queries - lying or not - keeps accumulating `n`, keeping its score high round after round.

The broken equality: the intended invariant "peer's `inventory` bit `== 1` at index `i`" implies "the peer's `AtlasDB.get_attachments_available_at_page_index` at `attachment_index=i` truthfully reflects `is_available`" is not verified anywhere on the requester side, and the score-based selection mechanism meant to mitigate exactly this kind of lying peer is itself broken by the integer-truncation bug, so the mitigation does not actually deprioritize a lying/failing peer relative to one that simply answers fewer, honest requests.

### Impact Explanation
An attacker peer can cause a specific `content_hash` (and therefore the on-chain-committed BNS/name-related attachment tied to it) to never be fetched by a victim node, because the victim's downloader keeps selecting the attacker as the sole download source for that content across retries, exhausting `max_attachment_retry_count` and dropping the batch. This is a High-severity "attachment/BNS mismatch"-class denial: the victim node never resolves an attachment that a confirmed on-chain operation committed to, even though another peer genuinely has the bytes, because only the attacker's URL is queried per round (the honest peer, even if listed in `sources`, is never itself contacted for that `content_hash` in that round). This is repeatable per attachment/content-hash and requires no privileged access - it only requires operating an ordinary P2P/RPC-reachable node peer.

### Likelihood Explanation
- The attacker needs only to run an ordinary, unprivileged Stacks peer reachable by the victim's outbound sync peer set (`network.get_outbound_sync_peers()`), and to answer `/v2/attachments/inv` requests with forged `inventory` bits and cheaply/quickly answer many such requests to accumulate `total_requests_sent`.
- No secret, no StackerDB slot, no signature bypass is required - the RPC endpoint requires no auth and the response is trusted at face value.
- The outcome depends on the attacker's score consistently beating any genuinely-holding peer's score, which per the broken `score()` formula favors sheer request volume over correctness; this is easy for an attacker to arrange by responding fast to every query (including forged ones) since even attachment-fetch failures increment `n`.
- Because the AttachmentsDownloader FSM retries with fresh DNS/inventory rounds but persists `reliability_reports` across retries, the attacker's inflated score compounds across retries rather than resetting, increasing the likelihood of durable capture of the "most reliable source" slot over time.

### Recommendation
- Fix `ReliabilityReport::score()` to genuinely reward success *rate* (e.g., compute `success as f64 / n as f64` scaled properly, or use `success.saturating_mul(SCALE) / n` with `SCALE` large enough that partial success ratios are distinguishable, and weight failures negatively rather than letting `n` alone dominate).
- When an `AttachmentRequest`'s chosen "most reliable source" fails to deliver, fall back within the same round to the next-best source in `sources` rather than waiting for a full batch retry.
- Consider requiring actual verification of delivered attachment bytes against `content_hash` before crediting `bump_successful_requests` (already implicitly done via hash check elsewhere) and penalizing/evicting peers whose claimed inventory repeatedly does not match delivered content (e.g., tracking a separate "inventory-lie" counter distinct from generic request success/failure).

### Proof of Concept
In `stackslib/src/net/atlas/download.rs` tests (or a new test module alongside `stackslib/src/net/atlas/tests.rs`):
1. Construct an `AttachmentsBatch` with one `AttachmentInstance` at a known `attachment_index`/`content_hash`.
2. Create two `ReliabilityReport`s: `attacker_report` with a growing `total_requests_sent` (e.g., 50) and `total_requests_success` slightly less than that (simulating many prior forged-but-well-formed inv responses plus some failed attachment fetches), and `honest_report` with fewer but all-successful requests (e.g., `total_requests_sent=5, total_requests_success=5`).
3. Assert via `ReliabilityReport::score()` that `attacker_report.score() > honest_report.score()` despite the honest peer having a perfect success rate - demonstrating the scoring bug directly: `assert!(attacker_report.score() > honest_report.score())`.
4. Seed `AttachmentsBatchStateContext.inventories` with a `GetAttachmentsInvResponse` from both the attacker URL (bit=1, forged) and the honest URL (bit=1, real) for the same page/position.
5. Call `get_prioritized_attachments_requests()` and assert `request.get_url()` (via `get_most_reliable_source`) resolves to the attacker's URL even though the honest peer's data is genuine.
6. Simulate `extend_with_attachments` with a failed/garbage response from the attacker URL, and drive `AttachmentsDownloader::run`/`try_proceed` through `max_attachment_retry_count` retries, asserting `AttachmentsBatch::has_fully_succeed()` remains `false` and the batch is eventually dropped, while the honest peer's URL is never chosen as `get_url()` in any round.

    pub fn extend_with_attachments(
        mut self,
        results: &mut BatchedRequestsResult<AttachmentRequest>,
    ) -> AttachmentsBatchStateContext {
        for (request, response) in results.succeeded.drain() {
            let report = self
                .peers
                .get_mut(request.get_url())
                .expect("Atlas: unable to retrieve reliability report for peer");

            let response = if let Some(r) = response {
                r
            } else {
                report.bump_failed_requests();
                continue;
            };

            if let Ok(response) = response.decode_atlas_get_attachment() {
                self.attachments.insert(response.attachment);
                report.bump_successful_requests();
            } else {
                report.bump_failed_requests();
            }
        }
        let mut events_ids = results.faulty_peers.keys().copied().collect::<Vec<usize>>();
        self.events_to_deregister.append(&mut events_ids);

        self
    }

impl AttachmentRequest {
    pub fn get_most_reliable_source(&self) -> (&UrlString, &ReliabilityReport) {
        self.sources
            .iter()
            .max_by_key(|(_, v)| v.score())
            .expect("Atlas: trying to select an Url out of an empty set")
    }
}

impl Hash for AttachmentRequest {
    fn hash<H: Hasher>(&self, state: &mut H) {
        self.content_hash.hash(state)
    }
}

impl Ord for AttachmentRequest {
    fn cmp(&self, other: &AttachmentRequest) -> Ordering {
        other.sources.len().cmp(&self.sources.len()).then_with(|| {
            let (_, report) = self.get_most_reliable_source();
            let (_, other_report) = other.get_most_reliable_source();
            report.cmp(other_report)
        })
    }
}

impl PartialOrd for AttachmentRequest {
    fn partial_cmp(&self, other: &AttachmentRequest) -> Option<Ordering> {
        Some(self.cmp(other))
    }
}

impl Requestable for AttachmentRequest {
    fn get_url(&self) -> &UrlString {
        let (url, _) = self.get_most_reliable_source();
        url
    }

    fn make_request_type(&self, peer_host: PeerHost) -> StacksHttpRequest {
        StacksHttpRequest::new_for_peer(
            peer_host,
            "GET".to_string(),
            format!("/v2/attachments/{}", &self.content_hash),
            HttpRequestContents::new(),
        )
        .expect("FATAL: failed to create an HTTP request for infallible data")
    }
}
