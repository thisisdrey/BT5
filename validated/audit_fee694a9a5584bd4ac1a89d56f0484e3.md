### Title
Auth-gated broadcast flag is bypassed — unauthenticated block upload still triggers network relay - (File: stackslib/src/net/api/postblock_v3.rs)

### Summary
The `/v3/blocks/upload/` endpoint (`RPCPostBlockRequestHandler`) requires a matching `authorization` header only when the caller explicitly sets `broadcast=1`; a plain POST without that query parameter needs no authentication at all. However, the handler's `try_handle_request` unconditionally calls `node.set_relay_message(...)` whenever the uploaded block is "accepted," regardless of whether `self.broadcast` was true/authenticated. This means the auth gate that is supposed to control network-wide propagation of an uploaded block does not actually gate that side effect.

### Finding Description
`try_parse_request` in [1](#0-0)  only requires the `authorization` header to match `self.auth` when `broadcast=1` is present in the query string; a request with no `broadcast` parameter (or `broadcast=0`) is processed with `authenticated = false` and is accepted without any credential.

In `try_handle_request`, the block is passed to `Relayer::process_new_nakamoto_block_ext` with `self.broadcast.unwrap_or(false)` [2](#0-1) , which presumably uses this flag to decide whether to actively push the block outward. Immediately afterward, though:

```rust
if data_resp.accepted {
    node.set_relay_message(StacksMessageType::NakamotoBlocks(NakamotoBlocksData {
        blocks: vec![block],
    }));
}
``` [3](#0-2) 

This call is gated only on `data_resp.accepted`, not on `self.broadcast`/`authenticated`. `set_relay_message` queues the block as a relay message for the P2P thread, which broadcasts it to peers. As a result, the intended equality — "network broadcast requires authentication" — is broken: an unauthenticated request that omits `broadcast=1` can still cause the node to relay the block to the network as long as `data_resp.accepted` is true, defeating the purpose of the `broadcast` authorization gate documented in the node's config (`connection_options.auth_token`, `docs/rpc/openapi.yaml`).

I was not able to fully verify, within the available context, whether `Relayer::process_new_nakamoto_block_ext`'s internal handling of the `broadcast` flag has some other gate that prevents `data_resp.accepted` from becoming true in the non-broadcast case, or whether `set_relay_message` has additional downstream checks that neutralize this. The `process_new_nakamoto_block_ext` definition in `stackslib/src/net/relay.rs` was located but not read in full before running out of iterations, so the exact semantics of its `broadcast` parameter (whether it only affects immediate advertisement vs. also affecting whether the block is queued at all) could not be confirmed with certainty.

### Impact Explanation
If confirmed, this allows any remote, unauthenticated peer with RPC access to force a stacks-node to relay/rebroadcast a Nakamoto block to the P2P network without holding the node's `auth_token`, which is explicitly documented as required "to receive block proposals... via the `/v3/block_proposal` endpoint" and to authenticate `/v2/blocks?broadcast=1` [4](#0-3) . This could be used to propagate blocks the operator did not intend to broadcast (e.g., ones obtained by non-network means), matching the "network-wide propagation of forged/unauthorized data" impact category.

### Likelihood Explanation
Likelihood is uncertain without confirming the exact behavior of `process_new_nakamoto_block_ext`'s `broadcast` argument and whether `data_resp.accepted` can be true when `broadcast` was false. If it can (which the code as read suggests, since acceptance appears to depend on chainstate validation rather than the broadcast flag), the bug is trivially reachable by any client that can reach the node's RPC endpoint.

### Recommendation
Gate the `node.set_relay_message(...)` call in `stackslib/src/net/api/postblock_v3.rs` on `self.broadcast == Some(true)` (i.e., only relay when the caller was authenticated for `broadcast=1`), matching the intent of the existing auth check in `try_parse_request`.

### Proof of Concept
Not independently confirmed end-to-end due to tool-call exhaustion. Conceptually: POST a valid, chainstate-acceptable Nakamoto block to `/v3/blocks/upload/` with no `authorization` header and no `broadcast` query parameter; if the node accepts the block (`data_resp.accepted == true`), observe (via network capture or a peer's chain tip) that the node still relays `NakamotoBlocksData` to its P2P peers despite the unauthenticated, non-broadcast request.
