### Title
Unvalidated raw `ContractType` value used as unchecked array/bit index in permission-operations check causes uncaught `IndexOutOfBoundsException` during signature/permission validation — (File: `chainbase/src/main/java/org/tron/common/utils/WalletUtil.java`)

### Summary
The polkit CVE-2018-19788 bug class is: an attacker-controlled numeric identity value that exceeds the range the code implicitly assumes (`uid` > `INT_MAX`) is used unchecked in a downstream authorization decision, causing incorrect/undefined behavior. The structurally analogous pattern in java-tron is `WalletUtil.checkPermissionOperations()` / `TransactionUtil.checkPermissionOperations()`, which take the *raw* wire value of the `Contract.type` field (`contract.getTypeValue()`, an `int32`) and use it directly as a bit index into a fixed 32-byte `operations` bitmap without validating that the value is a legitimate, in-range `ContractType` enum member.

### Finding Description
Multi-sig "Active" permissions store an authorized-contract-type bitmap in `Permission.operations` (32 bytes = 256 bits, one bit per `ContractType`). When a transaction is signed under a non-owner permission (`permissionId != 0`), `TransactionCapsule.checkPermission()` calls `checkPermissionOperations()` to verify the transaction's contract type is allowed by that permission: [1](#0-0) 

```java
public static boolean checkPermissionOperations(Permission permission, Contract contract)
    throws PermissionException {
  ByteString operations = permission.getOperations();
  if (operations.size() != 32) {
    throw new PermissionException(...);
  }
  int contractType = contract.getTypeValue();
  boolean b = (operations.byteAt(contractType / 8) & (1 << (contractType % 8))) != 0;
  return b;
}
```

`contract.getTypeValue()` (protobuf enum accessor) returns whatever raw `int32` was placed on the wire for the `type` field, **regardless of whether it corresponds to a known `ContractType` enum value**. Protobuf enum fields do not reject unknown/out-of-range integers when read via the `*Value()` accessor — only `getType()` would map unknown values to `UNRECOGNIZED`. There is no bounds check on `contractType` before it is used to compute `operations.byteAt(contractType / 8)`. If `contractType` is negative or larger than `256` (e.g. `Integer.MAX_VALUE`, or a small negative number), `contractType / 8` produces an index outside `[0, 31]`, and `ByteString.byteAt()` throws an unchecked `IndexOutOfBoundsException`.

Reachability: this same helper (and its duplicate in `TransactionUtil.checkPermissionOperations`) is invoked from `TransactionCapsule.checkPermission()`: [2](#0-1) 

which is called from `validateSignature()`/`addSign()` — i.e. from the core signature/permission verification path executed for **every broadcast transaction** that uses `permissionId != 0`: [3](#0-2) 

`Manager.pushTransaction()` invokes `trx.validateSignature(...)` *before* the contract's actuator dispatch/type validation occurs, so the raw, unvalidated `type` field is consumed at signature-verification time: [4](#0-3) 

and the same call occurs again inside `processTransaction()` used both for pending-tx execution and for block application: [5](#0-4) 

Neither `pushTransaction()`'s declared throws list nor `processTransaction()`'s catches an `IndexOutOfBoundsException`/generic `RuntimeException` around this call, so the exception propagates uncaught out of these methods.

### Impact Explanation
An attacker who controls any account with a multi-sig **Active** permission (any account can self-configure this via `AccountPermissionUpdateActuator`, which any unprivileged account can call) can craft a raw transaction whose `Transaction.Contract.type` field is set to an out-of-range `int32` (e.g., a negative value or one ≥ 256), sign it with a key present in that Active permission, and set `permission_id` to that permission's id. Broadcasting or otherwise injecting this transaction drives execution into `checkPermissionOperations`, producing an unchecked `IndexOutOfBoundsException` deep inside the shared signature/permission-verification path used both for mempool transaction admission and for block application (`processTransaction`). Because this is an unchecked exception not declared/caught at the relevant call sites, it can propagate out of transaction/block processing code that only anticipates the enumerated checked exceptions, resulting in inconsistent handling across different call paths (e.g., during block application versus at the API broadcast layer, which happens to have a catch-all). This can cause a node to fail to correctly process a block/transaction that other nodes process differently (or crash a worker thread), i.e., an availability/consensus-consistency issue.

### Likelihood Explanation
The path requires only: (1) a self-created account with a multi-sig Active permission (trivial, achievable by anyone via `AccountPermissionUpdateContract`), and (2) crafting a raw serialized `Transaction.Contract` with an out-of-range `type` value — trivial with direct protobuf serialization, bypassing SDK-level enum restrictions. No special privilege, witness/SR role, or node-internal access is needed; a single crafted signed transaction from an ordinary account is sufficient to reach the vulnerable code on every node that validates it.

### Recommendation
Validate `contractType` bounds before using it as a bitmap index in `checkPermissionOperations` (both in `WalletUtil` and `TransactionUtil`): reject (throw `PermissionException`) if `contractType < 0 || contractType >= operations.size() * 8` (i.e., `>= 256`) before computing `operations.byteAt(contractType / 8)`. Additionally, consider rejecting contracts whose `type` is not a recognized `ContractType` (`contract.getType() == ContractType.UNRECOGNIZED`) earlier in the signature-validation pipeline.

### Proof of Concept
1. Attacker account `A` calls `AccountPermissionUpdateContract` to set an Active permission with `id=2`, some `operations` bitmap, and a key `A` controls (multi-sign must be enabled, which is the default in current java-tron networks).
2. Attacker constructs a `Transaction` whose `raw_data.contract[0]` is built directly via protobuf serialization (not through standard SDK enum setters) with:
   - `parameter`: any valid `Any`-packed contract message (e.g. a `TransferContract`),
   - `type`: an out-of-range raw enum value, e.g. `-8` or `2000` (values with no corresponding `ContractType` constant),
   - `Permission_id = 2`.
3. Attacker signs the transaction with the key belonging to permission id `2`.
4. Attacker broadcasts the transaction (or it is included by a witness in a block).
5. During `TransactionCapsule.validateSignature()` → `checkPermission()` → `WalletUtil.checkPermissionOperations()`/`TransactionUtil.checkPermissionOperations()`, `contractType / 8` evaluates outside `[0,31]`, and `operations.byteAt(...)` throws an uncaught `IndexOutOfBoundsException`, propagating out of `Manager.pushTransaction()`/`Manager.processTransaction()` uncontrolled by the declared exception set.

Note: I was not able to fully trace every downstream caller of `Manager.processTransaction()` during block-application (`pushBlock`) to confirm the exact crash-vs-swallow behavior in that specific call chain within the available index; this would need direct code execution/testing (e.g., via a Devin session) to confirm whether it manifests as a node crash, a rejected block, or a swallowed exception in production, and to determine the precise severity (crash vs. inconsistent validation) with certainty.
