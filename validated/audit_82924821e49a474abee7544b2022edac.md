### Title
Unvalidated array-length allocation in `ValidateMultiSign`/`extractBytesArray` allows attacker-controlled unbounded memory allocation - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The bug class in the external report (Xen XSA-222) is "does not validate memory allocations during certain operations," letting an unprivileged actor trigger unchecked allocation. In java-tron, `extractBytesArray`/`extractBytes32Array` read an attacker-supplied `len` word from calldata and immediately do `new byte[len][]` with no upper bound before the `MAX_SIZE`/`sigArraySize` guard is applied [1](#0-0) .

### Finding Description
`ValidateMultiSign.execute` parses the ABI-encoded input into `DataWord[] words` and, when `VMConfig.allowTvmSelfdestructRestriction()` is disabled (or on older/alternate code paths), calls `extractBytesArray(words, words[3].intValueSafe() / WORD_SIZE, rawData)` directly, without first checking `sigArraySize` against `MAX_SIZE` [2](#0-1) . Inside `extractBytesArray`, `len` is taken straight from `words[offset].intValueSafe()` and used to allocate `byte[len][]` before any bound is enforced:
```java
int len = words[offset].intValueSafe();
byte[][] bytesArray = new byte[len][];
```
`extractBytes32Array` has the identical unguarded pattern [3](#0-2) . `intValueSafe()` clamps a `DataWord` (a 256-bit value fully attacker-controlled via calldata) to the `int` range, so a crafted transaction can set this length word to `Integer.MAX_VALUE` (or any large value up to the int range) with a tiny `rawData` payload. Energy for `ValidateMultiSign` is charged only based on `rawData.length / WORD_SIZE`, i.e. on the size of the raw calldata bytes actually supplied — not on the value encoded inside a length word [4](#0-3) . This means an attacker can pay for a small amount of calldata/energy while forcing the JVM to allocate an enormous `byte[Integer.MAX_VALUE][]` array reference table (and subsequently iterate/copy into it) before the code ever reaches the `sigArraySize > MAX_SIZE` bail-out — because that bail-out check itself is only performed on the `VMConfig.allowTvmSelfdestructRestriction()` path prior to calling `extractSigArray`, while the plain `extractBytesArray` path performs no pre-check at all.

This mirrors the CVE-2017-10918 root cause exactly: a size value taken from an untrusted, attacker-influenced input is used to drive a memory allocation without validating it is within sane bounds first.

### Impact Explanation
An attacker can submit a single smart-contract-call transaction (any account, no special permission required, using the `ValidateMultiSign` precompile at TVM address `0x2b`) that triggers a multi-gigabyte array allocation attempt on every full node/validator that executes the transaction during block validation. This can throw `OutOfMemoryError` inside the JVM, crashing or destabilizing the node process, or at minimum consuming a disproportionate amount of memory/CPU relative to the energy paid — a node crash/halt condition, which is in the accepted-impact list (node crash or halt).

### Likelihood Explanation
Likelihood is high: no privileged role, no witness/committee/SR access, and no special network conditions are needed — a normal user can construct the calldata and broadcast a contract-call transaction invoking the `validatemultisign` precompile with a manipulated length word. The check that would normally cap the array size (`sigArraySize > MAX_SIZE`) is gated behind `VMConfig.allowTvmSelfdestructRestriction()` and applies only to the `extractSigArray` call path, leaving the `extractBytesArray`/`extractBytes32Array` path unguarded.

### Recommendation
Validate the decoded `len` in `extractBytesArray` and `extractBytes32Array` against a strict upper bound (e.g. `MAX_SIZE` or the maximum number of words plausible given `rawData.length`) before allocating `byte[len][]`, and ensure the `sigArraySize`/length checks are applied unconditionally (not only when `allowTvmSelfdestructRestriction()` is enabled) prior to calling either extraction helper.

### Proof of Concept
1. Deploy or reuse any contract, or call directly via a raw contract-call transaction targeting the precompiled contract address for `ValidateMultiSign` (address `0x2b`).
2. Encode `rawData` per the expected ABI layout: `words[0]` = target address, `words[1]` = permissionId, `words[2]` = message data word, `words[3]` = offset pointing to the array-length word.
3. At the offset pointed to by `words[3]`, place a length word encoding a very large value (e.g. `0x7fffffff`), while keeping the actual `rawData` payload small (just enough words to pass `words[offset]` bounds).
4. Broadcast the transaction with `allowTvmSelfdestructRestriction` disabled (or on a network configuration where the guarded `sigArraySize` check is not active) so execution proceeds to `extractBytesArray(words, offset, rawData)` and attempts `new byte[len][]`, causing excessive allocation/OOM relative to the small energy fee charged.

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
