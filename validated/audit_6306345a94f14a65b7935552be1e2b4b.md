Based on my analysis, this describes an EVM-style reentrancy pattern that does not apply to NEAR's execution model, so the claimed vulnerability does not hold.

**The binding:** the question claims that the set of balance changes committed by the outer `execute_intents` receipt can be observed as "debited but not yet settled" by a re-entrant callee before `Engine::finalize` runs, allowing the same wNEAR balance to be spent twice. Tracing the code shows this binding never breaks.

`Engine::execute_signed_intents` processes all `MultiPayload`s in the batch synchronously, in-memory, inside a single WASM execution of `execute_intents`, then calls `self.finalize()` [1](#0-0)  . The `AuthCall` intent invokes `engine.state.auth_call(...)`, which flows through `Deltas::auth_call` straight to `Contract`'s `State::auth_call` [2](#0-1) [3](#0-2) . That implementation calls `self.withdraw(...)`, which synchronously mutates the real, persistent `Contract.accounts` field (not a buffer that is applied later at `finalize`) via `Deltas::internal_sub_balance` → `self.state.internal_sub_balance` [4](#0-3) . `Deltas`/`TransferMatcher` only accumulates bookkeeping deltas used to validate that `TokenDiff`-style transfers net to zero at `finalize`; it does not defer the actual balance write itself [5](#0-4) .

Crucially, the `near_withdraw` → `do_auth_call` → `on_auth` call chain is only *scheduled* as a `Promise` inside `auth_call` (via `.then(...)` and `.detach()`) [6](#0-5) . On NEAR, a scheduled `Promise` does not execute synchronously within the current function call; it becomes a new outgoing receipt that is only processed by the runtime after the current receipt's WASM execution returns and its resulting state changes are committed to the account's persistent storage. This means by the time `do_auth_call` (in `contracts/defuse/src/contract/intents/auth_call.rs`) and then the attacker's `on_auth` actually execute, the balance debit from `auth_call` and any other intents in the same `DefuseIntents` batch (e.g., the `Transfer`) have already been durably committed — there is no window where the callee observes "debited-but-not-yet-settled" in-memory state, because there is no shared call stack between the outer `execute_intents` receipt and the promise-driven `on_auth` receipt. Any re-entrant call the attacker's contract makes to `execute_intents` from within `on_auth` is a brand-new receipt that reads the already-updated persistent balance.

The premise also conflates `Engine::finalize` (an in-memory invariant check over `TransferMatcher` deltas within a single receipt, used to ensure `TokenDiff` transfers balance to zero) with storage commitment. `finalize` is not what "settles" balances to persistent state — `internal_sub_balance`/`internal_add_balance` already wrote to `Contract.accounts` before `finalize` is even reached [7](#0-6) . There is no code path by which a second, concurrently-dispatched `execute_intents` call (whether from the attacker directly or triggered via a promise callback) can observe stale/unsettled balances, since NEAR receipts execute atomically and sequentially per contract account, and cross-contract promises never share execution context with the caller.

I was unable to find any deferred-commit mechanism, shared mutable state across receipts, or any place where `auth_call`'s balance mutation is buffered until an asynchronous callback — everything points to synchronous, immediate persistence within the single receipt, which forecloses the described reentrancy window.

### No vulnerability found for this question.
