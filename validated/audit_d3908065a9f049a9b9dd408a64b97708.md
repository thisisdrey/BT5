## Title
`DelegateAction`/`SignedDelegateAction` in meta transactions omit any chain-binding data, enabling cross-chain replay of a signed authorization - (File: `core/primitives/src/action/delegate.rs`)

### Summary
NEP-366 meta transactions let a user (Alice) sign a `DelegateAction` off-chain and hand it to a relayer, who wraps it in a transaction on her behalf. The signed payload that authorizes the relayer to act contains no field that binds it to a specific chain/network — only `sender_id`, `receiver_id`, `actions`, `nonce`, `max_block_height`, and `public_key`. [1](#0-0) 

### Finding Description
`SignedDelegateAction::verify()` (and `VersionedSignedDelegateAction::verify()`) checks the ed25519 signature against `get_nep461_hash()`, which is just a `SignableMessage` wrapping a fixed NEP discriminant and the `DelegateAction` fields — no genesis hash, chain id, or `block_hash` is included anywhere in the signed bytes. [2](#0-1) [3](#0-2) 

This is in contrast to ordinary `SignedTransaction`s, which include a recent `block_hash` in the signed payload — a value that is chain-specific (different chains/forks have entirely different block hashes) and thus provides implicit chain-binding/replay protection across networks. `DelegateAction` deliberately replaces that binding with `nonce` + `max_block_height`, both of which are meaningful only relative to on-chain state (the access key's nonce counter and the current block height) and carry no information distinguishing one chain from another.

On the receiving side, `apply_delegate_action` / `validate_delegate_action_key` only check: signature validity, `max_block_height` vs current block height, `sender_id` match, and that the nonce in the `DelegateAction` is greater than the access key's stored nonce (and below an upper bound) — none of which reference chain identity. [4](#0-3) [5](#0-4) 

Because `SignedDelegateAction`s are explicitly designed to be transmitted off-chain to a relayer before being included in any transaction (per the meta-tx design), and because NEAR's account model allows the same `AccountId`/`PublicKey`/access-key-nonce state to exist independently on multiple nearcore-based networks (mainnet, testnet, sandbox, or any other chain instantiated from nearcore with the same genesis/account scheme — most directly, implicit accounts whose ID is derived purely from the public key), a `SignedDelegateAction` captured on one such chain can be resubmitted verbatim by a relayer/attacker on a different chain where the same sender account, public key, and a nonce/height window still validate. [6](#0-5) 

### Impact Explanation
An attacker (or a relayer acting maliciously, or anyone who intercepts the off-chain `SignedDelegateAction`) can replay Alice's meta-transaction authorization on a different NEAR-protocol network/chain that shares her account and access-key state, causing the delegated actions (fungible-token transfers, function calls, etc.) to execute a second time on a chain she never intended — a direct double-spend/replay of an authorization, potentially resulting in theft of funds or unauthorized state changes on the unintended chain.

### Likelihood Explanation
Likelihood is bounded by the requirement that the same `sender_id`/`public_key`/nonce state exist on two chains simultaneously — true by construction for NEAR implicit accounts (derived solely from the public key, commonly created identically on mainnet/testnet/sandbox by wallets and SDKs) and plausible for any nearcore-derived network sharing genesis account state. The relayer/off-chain transport step required by the NEP-366 design is the exact channel through which the signed payload becomes exposed and replayable.

### Recommendation
Bind the signed message to the target network, e.g. include the genesis hash / chain id (or the destination `NetworkId`) inside `DelegateAction`/`SignableMessage` so `get_nep461_hash()` differs across chains, and reject verification if it doesn't match the local chain's identifier — mirroring how `SignedTransaction.block_hash` implicitly ties ordinary transactions to a specific chain.

### Proof of Concept
1. Alice creates an implicit account (public key = account id) that exists identically on Chain A and Chain B (e.g., testnet and a sandbox/fork sharing the same key-derivation scheme).
2. Alice signs a `DelegateAction` (via `SignedDelegateAction::sign`) intending it for Chain A only, with `nonce`/`max_block_height` valid there.
3. Attacker observes the off-chain `SignedDelegateAction` (sent to a relayer per the NEP-366 flow) and resubmits it, wrapped in a transaction, to Chain B, where Alice's account has the same access key with a nonce still below `delegate_action.nonce` and current block height below `max_block_height`.
4. `SignedDelegateAction::verify()` succeeds (nothing in the hash references chain identity) and `apply_delegate_action`/`validate_delegate_action_key` accept it, executing Alice's actions on Chain B without her consent. [7](#0-6)

impl SignedDelegateAction {
    pub fn verify(&self) -> bool {
        let delegate_action = &self.delegate_action;
        let hash = delegate_action.get_nep461_hash();
        let public_key = &delegate_action.public_key;

        self.signature.verify(hash.as_ref(), public_key)
    }

    pub fn sign(singer: &Signer, delegate_action: DelegateAction) -> Self {
        let signature = singer.sign(delegate_action.get_nep461_hash().as_bytes());
        Self { delegate_action, signature }
    }
}

**File:** docs/architecture/how/meta-tx.md (L40-52)
```markdown
With meta transactions, Alice can create a `DelegateAction`, which is very
similar to a transaction. It also contains a list of actions to execute and a
single receiver for those actions. She signs the `DelegateAction` and forwards
it (off-chain) to a relayer. The relayer wraps it in a transaction, of which the
relayer is the signer and therefore pays the gas costs. If the inner actions
have an attached token balance, this is also paid for by the relayer.

On chain, the `SignedDelegateAction` inside the transaction is converted to an
action receipt with the same `SignedDelegateAction` on the relayer's shard. The
receipt is forwarded to the account from `Alice`, which will unpacked the
`SignedDelegateAction` and verify that it is signed by Alice with a valid Nonce
etc. If all checks are successful, a new action receipt with the inner actions
as body is sent to `FT`. There, the `ft_transfer` call finally executes.
```
