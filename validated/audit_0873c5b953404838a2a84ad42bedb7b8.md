## Analog Vulnerability Found

### Title
Remote panic via off-by-one payload-length boundary check in `validate_blocks_push` - (File: `stackslib/src/net/chat.rs`)

### Summary
The TensorFlow advisory describes a `CHECK` failure (process crash) caused by an insufficiently validated size parameter (`ksize`) that a later assumption in the code relies on being positive/bounded. The stacks-core P2P message pipeline has an analogous boundary-check mismatch: the `Preamble.payload_len` field is validated as "not `< 5`" during deserialization, but a downstream `assert!` in the Blocks-push handler assumes the strictly stronger invariant "`> 5`". A remote, unauthenticated (only handshake-completed) peer can supply `payload_len == 5` and trigger the failed assertion, causing a process panic.

### Finding Description
`Preamble::consensus_deserialize` only rejects lengths strictly less than 5: [1](#0-0) 

This means `payload_len == 5` is accepted as a valid preamble value and propagates into the rest of the message-processing pipeline.

When a framed message is later reassembled, `consume_payload_known_length` only checks that the buffer *contains at least* `payload_len` bytes before invoking the protocol's `read_payload`; it passes the entire remaining buffer (not a slice truncated to exactly `payload_len` bytes) to the decoder, and the decoder consumes as many bytes as its own `StacksMessageCodec` implementation needs, independent of the declared `payload_len`: [2](#0-1) 

This means a peer can declare `payload_len = 5` in the (signed) preamble while actually supplying a full, well-formed `StacksMessageType::Blocks` payload (relayers vector + type tag + a real, decodable `BlocksData`) in the rest of the connection buffer. The message decodes successfully because decoding is driven by the codec's own internal length fields, not by the preamble's declared `payload_len`.

Once decoded, the message is routed to `validate_blocks_push`, which asserts the *stronger* invariant that was never actually guaranteed: [3](#0-2) 

Since the codec only rejects `payload_len < 5` (not `<= 5`), a preamble with `payload_len == 5` passes all upstream checks, the message still decodes (because decoding isn't gated on `payload_len` matching the actual encoded size), and `assert!(preamble.payload_len > 5)` then fails and panics.

### Impact Explanation
This is a remote, unauthenticated (any peer that can complete a P2P handshake, which requires no privileged key or admin role) crash vector reachable with a single crafted message. A Rust `assert!` failure aborts the process/thread; in a P2P server context this constitutes a remote unauthenticated DoS, matching the "Critical - remote crash/unauthenticated DoS from few messages" impact bucket in the rules.

### Likelihood Explanation
The trigger requires only:
1. A registered/handshaked P2P conversation (a routine, unprivileged step available to any peer).
2. A single `Blocks` push message whose preamble declares `payload_len = 5` while the actual message bytes following it still form a valid, decodable `BlocksData` payload.

No node secret, signer key, or elevated role is needed, and the boundary condition (`payload_len == 5`) is trivial to construct deterministically. This is a low-effort, high-reliability crash.

### Recommendation
Change the assertion in `validate_blocks_push` (and any sibling code with the same assumption, e.g. `validate_microblocks_push`) to return a graceful `net_error` instead of panicking, and/or tighten the codec-level validation in `Preamble::consensus_deserialize` to reject `payload_len <= 5` for message types that structurally require more than the bare minimum. More robustly, `consume_payload_known_length` should enforce that the actual number of bytes consumed by `read_payload` matches the declared `payload_len` exactly (or bound decoding to a slice of exactly `payload_len` bytes), removing the discrepancy between the framing length and the real decoded size.

### Proof of Concept
1. Establish a normal P2P handshake with the target node as any peer.
2. Send a `StacksMessage` whose `Preamble.payload_len = 5`, with a signature computed correctly over the actual message bytes (an attacker fully controls their own outbound message and its signature).
3. Follow the preamble with real message bytes encoding: an empty `relayers` vector (4 zero bytes) + the `Blocks` type-tag byte (satisfying the declared `payload_len = 5`), then continue the buffer immediately with a valid, fully-encoded `BlocksData` structure (nonzero-length blocks vector) so that `read_payload`'s internal codec successfully decodes a complete `BlocksData` regardless of the mismatched `payload_len`.
4. The decoded message is dispatched to `validate_blocks_push`, where `assert!(preamble.payload_len > 5)` evaluates `5 > 5 == false` and panics, crashing the handling thread/process.

Note: I was not able to directly locate (within the indexed context available) the exact call site that dispatches an incoming `StacksMessageType::Blocks` to `validate_blocks_push`; this was inferred from the function's documentation and naming pattern alongside sibling handlers (`validate_microblocks_push`). Confirming the exact dispatch path would benefit from a full-repository review in a Devin session, since index size limits may have excluded some `chat.rs`/`relay.rs` dispatch code from search results.
