### Title
Instant Timelock Removal/Reduction Bypasses Pending-Transaction Protection in `multisig_account` — (File: `aptos-move/framework/aptos-framework/sources/multisig_account.move`)

---

### Summary

`remove_timelock` and `upsert_timelock` in `multisig_account.move` take effect **immediately** on all already-queued pending transactions. Because `can_execute_with_timelock` measures elapsed time from a transaction's `creation_time_secs` (not from when the new timelock was activated), a malicious majority of owners can queue a timelock-removal/reduction transaction followed by a fund-draining transaction. Once the first transaction executes and removes/shortens the timelock, the second transaction — which was created long before the change — satisfies the new (shorter or zero) timelock immediately and can be executed without any additional waiting period. The minority owners who relied on the timelock to react have no extra time to respond.

---

### Finding Description

`MultisigAccountTimeLock` stores a `timelock_period` that is checked in `can_execute_with_timelock`:

```move
let elapsed = now_seconds() - pending_transaction.creation_time_secs;
(override_threshold.is_some() && &num_approvals >= override_threshold.borrow()) || elapsed >= timelock
``` [1](#0-0) 

`elapsed` is computed from the transaction's `creation_time_secs`, not from when the timelock was set. When `remove_timelock` executes, `MultisigAccountTimeLock` is destroyed:

```move
move_from<MultisigAccountTimeLock>(multisig_address);
``` [2](#0-1) 

After removal, `can_execute_with_timelock` returns `true` unconditionally for all pending transactions:

```move
} else {
    true
}
``` [3](#0-2) 

Similarly, `upsert_timelock` immediately overwrites `timelock_period` with no delay:

```move
multisig_account_resource.timelock_period = timelock_period;
``` [4](#0-3) 

The code comment at lines 910–918 explicitly acknowledges this behavior and labels it "an acceptable, operator-visible risk," but this characterization is incorrect from a security standpoint: the timelock's entire purpose is to protect minority owners against a malicious majority, and this path defeats that protection. [5](#0-4) 

---

### Impact Explanation

**Concrete attack sequence** (multisig with 14-day timelock, 2-of-3 owners, two malicious owners):

1. Malicious owners create **TX1** (sequence 1): payload = `remove_timelock()`, created at time `T`.
2. Malicious owners create **TX2** (sequence 2): payload = drain all APT from the multisig, created at time `T + 1 second`.
3. Both transactions are approved by the 2-of-3 malicious majority.
4. Minority owner observes TX1 and TX2 in the queue. They have 14 days to react (e.g., alert community, seek governance intervention). They cannot execute TX2 yet because TX1 must execute first.
5. After 14 days, TX1 becomes executable. Malicious owner executes TX1 → `remove_timelock()` fires, `MultisigAccountTimeLock` is destroyed.
6. TX2 now has `elapsed = 14 days - 1 second`. With no timelock resource, `can_execute_with_timelock` returns `true`. TX2 is **immediately executable**.
7. Malicious owner executes TX2 in the same block → all APT/fungible assets are drained.

The minority owner had 14 days to react to TX1 but **zero additional time** to react to TX2 after the timelock was removed. The invariant "each pending transaction is protected by the full timelock period" is broken.

The same attack works with `upsert_timelock` reducing the period from 14 days to `MIN_TIMELOCK_PERIOD` (1 hour): after TX1 executes and sets the period to 1 hour, TX2 (created 14 days ago) has `elapsed >> 1 hour` and is immediately executable. [6](#0-5) 

---

### Likelihood Explanation

- Any multisig account that holds APT or fungible assets and has enabled the `MULTISIG_TIMELOCK` feature flag is affected.
- The attack requires a malicious majority of owners (e.g., 2-of-3), which is the exact threat model the timelock is designed to defend against.
- The attack is fully on-chain, requires no privileged framework access, and is reachable through normal multisig transaction submission.
- `validate_multisig_transaction` (called by the VM prologue) enforces `can_execute_with_timelock`, so the bypass is enforced at the VM level. [7](#0-6) 

---

### Recommendation

When `remove_timelock` or `upsert_timelock` executes, it must **not** retroactively shorten the effective protection for already-queued pending transactions. Two complementary fixes:

1. **Record a `timelock_activated_secs` timestamp** in `MultisigAccountTimeLock`. In `can_execute_with_timelock`, compute elapsed time as `now_seconds() - max(creation_time_secs, timelock_activated_secs)`. This ensures that even if a transaction was created before the timelock was set, it still waits the full `timelock_period` from the moment the timelock became active.

2. **For `remove_timelock`**: instead of immediately destroying the resource, record a `removal_scheduled_at` timestamp and only allow removal to take effect after the current `timelock_period` has elapsed (i.e., apply the timelock to the timelock-removal itself, separately from the multisig proposal queue). [8](#0-7)

### Proof of Concept

The existing test `test_remove_timelock_allows_immediate_execution` already demonstrates the instant effect:

```move
// Configure then remove timelock.
upsert_timelock(multisig_signer, 3600, option::some(3));
remove_timelock(multisig_signer);

// Create and approve a transaction.
create_transaction(owner_1, multisig_account, PAYLOAD);
approve_transaction(owner_2, multisig_account, 1);

// No timelock — immediately executable.
assert!(can_be_executed(multisig_account, 1), 0);
``` [9](#0-8) 

The attack-specific PoC extends this: create TX1 (`remove_timelock`) and TX2 (drain) before removing the timelock, advance time by 14 days, execute TX1, then assert TX2 is immediately executable without any additional time advance. The `can_execute_with_timelock` inline function will return `true` for TX2 because `MultisigAccountTimeLock` no longer exists, regardless of TX2's `creation_time_secs`. [10](#0-9)

    inline fun can_execute_with_timelock(multisig_account: address, sequence_number: u64, num_approvals: u64): bool {
        if (exists<MultisigAccountTimeLock>(multisig_account)) {
            let multisig_account_resource = &MultisigAccountTimeLock[multisig_account];
            let timelock = multisig_account_resource.timelock_period;
            let override_threshold = multisig_account_resource.override_threshold;

            // Get the pending transaction to check if the timelock has expired
            // Assume that the transaction has already been checked to exist and is valid
            let pending_transaction = get_transaction(multisig_account, sequence_number);

            // Use subtraction to avoid overflow (now_seconds() >= creation_time_secs is always true)
            let elapsed = now_seconds() - pending_transaction.creation_time_secs;

            // If the number of approvals meets the override threshold, or the timelock has expired, allow execution
            (override_threshold.is_some() && &num_approvals >= override_threshold.borrow()) || elapsed >= timelock
        } else {
            true
        }
    }
