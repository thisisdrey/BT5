### Title
Witness rewards permanently locked when a witness has zero votes during a maintenance cycle, analogous to `totalSupply()==0` locking rewards - ([File: chainbase/src/main/java/org/tron/core/store/DelegationStore.java])

### Summary
java-tron's DPoS reward-accumulation mechanism (the "Vi" — value-per-vote index algorithm) has the same class of bug as the reported Tokemak issue: when the divisor of the reward-rate calculation (here, a witness's `voteCount`, analogous to `totalSupply()`) is zero for a given cycle, the reward accrued during that cycle is silently dropped instead of being carried forward or redistributed, and is permanently unrecoverable.

### Finding Description
Block and transaction-fee rewards for a witness are accumulated per cycle via `MortgageService.payReward()`, which calls `delegationStore.addReward(cycle, witnessAddress, value)`: [1](#0-0) 

At the end of each maintenance cycle, `MaintenanceManager.doMaintenance()` converts that cycle's accumulated reward into a per-vote reward index ("Vi") for every active witness: [2](#0-1) 

The actual accumulation logic is in `DelegationStore.accumulateWitnessVi` (duplicated in `RewardViCalService.accumulateWitnessVi`): [3](#0-2) 

If `voteCount == 0` for that witness in that cycle (the direct analog of `totalSupply() == 0` in the Tokemak `rewardPerToken()` function), the code takes the `if (reward == 0 || voteCount == 0)` branch: it only forwards the previous Vi value and **never divides the cycle's reward by voteCount to add a delta**. The `reward` value that was already recorded via `addReward()` for that cycle is read exactly once here (`getReward(cycle, address)`), and after this call it is never consulted again — there is no retry, redistribution, or refund mechanism. Once this happens, the funds recorded in the `reward` DB entry for that (cycle, witness) pair become permanently stranded: they were already implicitly reserved (the block reward / TX-fee split logic already computed and stored this amount as belonging to voters of this witness), but no voter's Vi is ever incremented to reflect it, so no account can ever claim it via `MortgageService.withdrawReward()`/`computeReward()`: [4](#0-3) 

This is structurally identical to the reported vulnerability: `rewardPerTokenStored` is not incremented when `totalSupply()==0`, so rewards accrued during that period are never distributed and are locked forever, with no sweep/recompute mechanism.

A witness can have `voteCount == 0` in a live cycle for entirely permissionless reasons: any voter can withdraw/unfreeze their stake or re-vote to change allocations via ordinary vote/freeze actuators reachable by any signed transaction. If a witness's electors withdraw all votes (or a witness is newly promoted with 0 votes recorded for a cycle boundary) while the witness is still active and producing blocks for part of that cycle, block/TX-fee rewards keep flowing into `addReward()` for that witness/cycle, but at cycle-end `accumulateWitnessVi` discards the reward contribution because `voteCount==0`.

### Impact Explanation
Funds already reserved as staking rewards (from block rewards and transaction fee splits) become permanently frozen/unbacked in the `DelegationStore` reward records — no account can ever withdraw them via `MortgageService`, and there is no compensating mechanism elsewhere in the codebase that reclaims or redistributes them. This is a permanent freezing-of-funds condition on legitimately-earned protocol rewards, satisfying "permanent freezing of funds" impact criteria. It does not require any privileged actor — normal vote/unfreeze transactions from ordinary accounts can create the zero-vote condition.

### Likelihood Explanation
This requires a witness's `voteCount` (as recorded at a given cycle boundary via `setWitnessVote`) to be `0` while the witness still earns block/tx-fee rewards for part of that cycle — e.g., transient states around witness promotion/demotion, or all voters unfreezing/re-delegating away from a witness near a cycle boundary. This is a normal, permissionless sequence of votes/freezes reachable by any account, though it depends on specific vote-distribution timing, so likelihood is moderate rather than trivial to trigger at will.

### Recommendation
When `voteCount == 0` for a cycle in `DelegationStore.accumulateWitnessVi` / `RewardViCalService.accumulateWitnessVi`, do not silently discard the cycle's `reward`; either (a) roll the un-distributable reward forward into the next cycle's reward pool for that witness so it can be distributed once `voteCount > 0` again, or (b) return the amount to the witness's own allowance/brokerage rather than leaving it permanently orphaned in the `reward` store.

### Proof of Concept
1. Witness `W` is active and, over the course of cycle `C`, produces blocks, so `MortgageService.payBlockReward`/`payTransactionFeeReward` repeatedly call `delegationStore.addReward(C, W, value)`, accumulating a nonzero `reward` for `(C, W)`.
2. Before/at the maintenance boundary that finalizes cycle `C`, all voters for `W` withdraw their votes (via standard freeze/vote actuators), so `setWitnessVote(C, W, 0)` (or votes drop to 0 by that point via `countVote`) results in `getWitnessVote(C, W) == 0`.
3. At `MaintenanceManager.doMaintenance()`, `delegationStore.accumulateWitnessVi(C, W, 0)` is invoked: `voteCount == 0` is true, so the branch that would add `deltaVi = reward * DECIMAL / voteCount` is skipped; only the previous Vi is forwarded.
4. The `reward` value stored at key `(C, W, "reward")` is never read again by any other code path (confirmed: `getReward` is only called from `accumulateWitnessVi`), so those tokens are permanently unclaimable by any voter, mirroring the Tokemak `rewardPerTokenStored` stagnation bug.   private long computeReward(long beginCycle, long endCycle, AccountCapsule accountCapsule) {
    if (beginCycle >= endCycle) {
      return 0;
    }

    long reward = 0;
    long newAlgorithmCycle = dynamicPropertiesStore.getNewRewardAlgorithmEffectiveCycle();
    List<Pair<byte[], Long>> srAddresses = accountCapsule.getVotesList().stream()
        .map(vote -> new Pair<>(vote.getVoteAddress().toByteArray(), vote.getVoteCount()))
        .collect(Collectors.toList());
    if (beginCycle < newAlgorithmCycle) {
      long oldEndCycle = min(endCycle, newAlgorithmCycle,
          dynamicPropertiesStore.disableJavaLangMath());
      reward = getOldReward(beginCycle, oldEndCycle, srAddresses);
      beginCycle = oldEndCycle;
    }
    if (beginCycle < endCycle) {
      for (Pair<byte[], Long>  vote : srAddresses) {
        byte[] srAddress = vote.getKey();
        BigInteger beginVi = delegationStore.getWitnessVi(beginCycle - 1, srAddress);
        BigInteger endVi = delegationStore.getWitnessVi(endCycle - 1, srAddress);
        BigInteger deltaVi = endVi.subtract(beginVi);
        if (deltaVi.signum() <= 0) {
          continue;
        }
        long userVote = vote.getValue();
        reward += deltaVi.multiply(BigInteger.valueOf(userVote))
            .divide(DelegationStore.DECIMAL_OF_VI_REWARD).longValue();
      }
    }
    return reward;
  }

  public void accumulateWitnessVi(long cycle, byte[] address, long voteCount) {
    BigInteger preVi = getWitnessVi(cycle - 1, address);
    long reward = getReward(cycle, address);
    if (reward == 0 || voteCount == 0) { // Just forward pre vi
      if (!BigInteger.ZERO.equals(preVi)) { // Zero vi will not be record
        setWitnessVi(cycle, address, preVi);
      }
    } else { // Accumulate delta vi
      BigInteger deltaVi = BigInteger.valueOf(reward)
          .multiply(DECIMAL_OF_VI_REWARD)
          .divide(BigInteger.valueOf(voteCount));
      setWitnessVi(cycle, address, preVi.add(deltaVi));
    }
  }
