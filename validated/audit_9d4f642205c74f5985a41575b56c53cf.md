Confirmed: six separate HTTP RPC handlers across `stackslib/src/net/api/` all implement the `auth_token` check using a plain `!=` comparison on `String`, which is not constant-time.### Title
Non-constant-time `auth_token` comparison in signer/RPC HTTP endpoints enables remote timing side-channel authentication bypass - (File: `stackslib/src/net/api/postblock_proposal.rs`, `postblock_v3.rs`, `fastcallreadonly.rs`, `blockreplay.rs`, `blocksimulate.rs`, `txsimulate.rs`)

### Summary
Six privileged HTTP RPC handlers authenticate the `Authorization` header by comparing it against the node's configured `connection_options.auth_token` using Rust's default `String` `PartialEq` (`!=`), which is a byte-by-byte, early-exit comparison rather than a constant-time comparison. A remote, unauthenticated attacker can exploit response-time differences to recover the secret token byte-by-byte and then submit privileged requests (e.g., block proposals) as an authenticated signer.

### Finding Description
The Jenkins Xooa advisory (GHSA-56h7-r62c-83qp) concerns a secret token whose confidentiality guarantee is broken because the equality between "the stored secret" and "what's exposed" fails. The analogous fault class here is a broken authentication equality check: the comparison between the caller-supplied token and the node's configured secret is done with a non-constant-time string comparison.

Every one of these handlers implements the identical pattern:
```rust
let Some(password) = &self.auth else { return Err(Error::Http(400, "Bad Request.".into())); };
let Some(auth_header) = preamble.headers.get("authorization") else { return Err(Error::Http(401, "Unauthorized".into())); };
if auth_header != password {
    return Err(Error::Http(401, "Unauthorized".into()));
}
``` [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) 

`str`/`String` equality in Rust compares byte-by-byte and returns as soon as a mismatch is found — it is explicitly documented as not constant-time. This repo has no `subtle`/`ct_eq`/constant-time comparison utility anywhere (confirmed by search), and `connection_options.auth_token` is a plain `Option<String>` loaded from the node config with no special handling. [5](#0-4) 

The "equality" being broken is the fundamental authentication invariant: "supplied credential equals the stored secret" should be indistinguishable in timing from "supplied credential mismatches the stored secret at position N." Because the comparison leaks the position of the first mismatched byte via response latency, this converts a brute-force search of complexity O(256^N) into roughly O(256×N) queries over the network — the classic remote timing side-channel against token-based auth.

### Impact Explanation
This auth token protects some of the most privileged endpoints in the node:
- `/v3/block_proposal` — accepts a signer's block proposal for validation [6](#0-5) 
- `/v3/blocks/upload/` with `broadcast=1` — allows broadcasting an uploaded Nakamoto block network-wide once "authenticated" [7](#0-6) 
- `/v3/contracts/fast-call-read/...` — privileged read-only contract-call endpoint
- block/tx simulation and replay endpoints

Per `stackslib/src/config/mod.rs`, this token is explicitly documented as securing the channel between the node and its `stacks-signer`, and as being required to authenticate `/v2/blocks?broadcast=1` requests. [5](#0-4)  An attacker who recovers the token via timing analysis gains unauthorized write access to block-proposal/broadcast endpoints — matching the "Critical: unauthenticated/unauthorized write to state... auth bypass" category from the validation rules, since it results in a genuine remote authentication bypass rather than mere traffic-volume abuse.

### Likelihood Explanation
Exploitability depends on network jitter and how measurable the per-byte timing difference is over the specific transport (localhost vs. WAN); it typically requires many repeated samples (statistical averaging) to overcome network noise, which is a real but non-trivial engineering effort for an attacker. The endpoints are usually bound to a private network (signer/miner coordination channel) rather than public 0.0.0.0 in the default config, but the sample configs (`mainnet-signer.toml`, `mainnet-miner-conf.toml`) show these ports are commonly bound on `0.0.0.0:20443`, and the endpoint is reachable by anyone who can route to that port. [8](#0-7)  Given six independent handlers share the identical flawed pattern, this is a systemic issue rather than an isolated bug, increasing confidence that it is a genuine design gap rather than an incidental defect.

### Recommendation
Replace the `!=`/`==` string comparisons in all six handlers with a constant-time comparison (e.g., using the `subtle` crate's `ConstantTimeEq`, or comparing SHA-256 digests of both values with a constant-time equality check) so that comparison time is independent of where the first mismatching byte occurs. Centralize this into one shared helper (e.g., in `stackslib/src/net/http.rs` or `httpcore.rs`) so future handlers that read `connection_options.auth_token` inherit the safe comparison instead of re-implementing the check ad hoc, as currently done six separate times.

### Proof of Concept
1. Configure a node with `connection_options.auth_token = "S3CR3T-LONG-TOKEN"`.
2. From a remote host, repeatedly send POST requests to `/v3/block_proposal` (or any of the other five endpoints) with an `Authorization` header consisting of a candidate prefix followed by all 256 possible next-byte values (e.g., `"A"`, `"B"`, ... for byte 1), each candidate sent many times to average out network jitter.
3. Measure round-trip time to the point where the 401 response is generated. Because `auth_header != password` returns as soon as a mismatch is found, candidates that share a longer correct prefix with the real token take marginally longer to reject (extra byte comparisons before divergence, and CPU cache/branch behavior differences).
4. Select the byte value with the highest average response time as the next correct byte of the token; repeat until the whole token is recovered.
5. Use the recovered token in the `Authorization` header to issue unauthorized privileged requests (e.g., submit a signed block proposal or broadcast a block via `/v3/blocks/upload/?broadcast=1`).

Note: I was not able to fully verify the exact network exposure/binding defaults in a production deployment (i.e., whether `rpc_bind` is realistically reachable by a remote, non-privileged attacker in all supported deployment topologies), since this depends on operator-specific firewall/network configuration outside this repository's control — this affects the practical likelihood but not the underlying code-level equality-check defect, which is confirmed by direct code inspection across all six files.
