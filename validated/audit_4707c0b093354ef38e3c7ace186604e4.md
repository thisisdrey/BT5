### Title
Unbounded array allocation in `extractBytes32Array` reachable via `BatchValidateSign` TVM precompile - allows attacker-triggered `OutOfMemoryError` / node resource exhaustion (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The CVE-2025-29366 bug class is an array-overflow caused by writing/allocating memory using an attacker-controlled length/index without validating it against a fixed bound. The closest reachable analog in java-tron is `extractBytes32Array`, a helper used by the `BatchValidateSign` TVM precompiled contract, which allocates a `byte[len][]` array where `len` is taken directly from calldata (`words[offset].intValueSafe()`) with **no upper-bound check**, unlike its sibling `extractBytesArray`, which explicitly guards the offset. [1](#0-0) 

### Finding Description
`BatchValidateSign.doExecute()` parses calldata into 32-byte `DataWord[] words` and computes an address-array offset directly from attacker-supplied words: [2](#0-1) 

It calls `extractBytes32Array(words, words[2].intValueSafe() / WORD_SIZE)`, whose implementation is:
```java
private static byte[][] extractBytes32Array(DataWord[] words, int offset) {
  int len = words[offset].intValueSafe();
  byte[][] bytes32Array = new byte[len][];
  for (int i = 0; i < len; i++) {
    bytes32Array[i] = words[offset + i + 1].getData();
  }
  return bytes32Array;
}
``` [3](#0-2) 

Unlike `extractBytesArray`, which contains an explicit `if (offset > words.length - 1) return new byte[0][];` bound check before indexing, `extractBytes32Array` has no such guard, and — more importantly — `len` is unbounded up to `Integer.MAX_VALUE` (since `DataWord.intValueSafe()` clamps negative/overflow values to `Integer.MAX_VALUE` rather than rejecting them): [4](#0-3) 

The size cap (`MAX_SIZE = 16`) that would otherwise bound `sigArraySize`/`addrArraySize` is only enforced conditionally, behind the `VMConfig.allowTvmSelfdestructRestriction()` feature flag: [5](#0-4) 

This means an attacker who supplies a crafted `words[2]` value (e.g., a large word decoding to a large `len`) can force `new byte[len][]` to attempt allocating an array of up to ~2^31 references (~16GB of reference-array memory alone), independent of the small, real calldata size that determines the `getEnergyForData` cost: [6](#0-5) 

The resulting `OutOfMemoryError` is technically caught by `execute()`'s `catch (Throwable t)` wrapper, but the JVM's attempt to satisfy the huge allocation before throwing can still stress heap/GC across the running node process — this is analogous to the CVE's "array overflow" root cause (attacker-controlled index/length used unchecked to size or index an array), just manifesting as memory-exhaustion DoS in java-tron's managed-memory context instead of the native buffer overflow/RCE in mupen64plus.

### Impact Explanation
An unprivileged caller can invoke this precompile from any smart contract (via `TriggerSmartContract`), paying only nominal, attacker-chosen energy (decoupled from the actual attempted allocation size), and force the executing full node to attempt a huge array allocation. Repeated/parallel invocation across blocks or within a single block's multiple internal calls could cause sustained heap pressure/GC pauses that degrade or halt block processing on validating/witness nodes — a resource-exhaustion / node-availability impact.

### Likelihood Explanation
Reaching this code only requires constructing calldata for the `BatchValidateSign` builtin precompile address with a crafted `words[2]` value; no special permission or high fee is needed since energy cost is based on actual calldata length, not on the attacker-controlled `len` used for allocation. The bound-check inconsistency between `extractBytesArray` (guarded) and `extractBytes32Array` (unguarded) and the conditional nature of the `MAX_SIZE` check (gated by `allowTvmSelfdestructRestriction`) make this readily reachable unless that feature flag is always active in the deployed configuration — this dependency on the flag's runtime status was not fully verifiable within available context.

### Recommendation
Add an explicit, unconditional bound check in `extractBytes32Array` (mirroring `extractBytesArray`'s `offset` guard) and cap `len` to a small constant (e.g., `MAX_SIZE`) before allocating `bytes32Array`, regardless of `VMConfig.allowTvmSelfdestructRestriction()`. Reject with `Pair.of(true, DATA_FALSE)` (or similar) instead of allocating when `len` exceeds the safe bound or `offset`/`len` would run past `words.length`.

### Proof of Concept
Craft a `TriggerSmartContract` call to the `BatchValidateSign` precompiled address with calldata where the 3rd 32-byte word (`words[2]`, the "addresses" array offset) points to a word decoding to a very large integer (close to `Integer.MAX_VALUE / 32`), while leaving `VMConfig.allowTvmSelfdestructRestriction()` in its default/disabled state so the `MAX_SIZE` guard at line 1167 is skipped. This drives execution into `extractBytes32Array(words, largeOffset)` at line 1176, causing `new byte[len][]` with `len` derived from attacker data, independent of the actual (small) energy-charged calldata size.

**Uncertainty / unverified aspects:** I could not fully confirm from indexed content whether `VMConfig.allowTvmSelfdestructRestriction()` is enabled by default in the current mainnet configuration (only that it is a `ProposalUtil`/`DynamicPropertiesStore`-controlled feature flag), nor whether the JVM's `OutOfMemoryError` handling elsewhere in the node (e.g., watchdogs, heap sizing) mitigates the practical severity of this specific allocation size. A Devin session with full repo/config access would be needed to confirm the flag's deployed default and to build/run an end-to-end PoC transaction against a test node.
