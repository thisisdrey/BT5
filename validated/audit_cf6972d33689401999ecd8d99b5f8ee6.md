### Title
`remove_account` fails to purge `TrieKey::PostponedReceipt` and `ReceivedData` rows, allowing a stale postponed `ActionReceipt` (e.g. containing `AddKey(FullAccess)`) to execute against a re-created account - ([File: core/store/src/utils/mod.rs])

### Summary
`remove_account` (core/store/src/utils/mod.rs:505-575) clears the `Account`, `ContractCode`, `AccessKey`/gas-key, and `ContractData` trie subranges for a deleted account, but never iterates or removes `TrieKey::PostponedReceipt{receiver_id, receipt_id}` (or the corresponding `ReceivedData` rows). Because a postponed `ActionReceipt` is stored under the *receiver's* account id and that state is never scrubbed on `DeleteAccount`, an attacker can pre-stage a self-privileging receipt, delete their account, have it re-created, and then later resolve the pending data dependency to have the stale receipt executed against the fresh account.

### Finding Description
When a receipt has unresolved `input_data_ids`, the runtime persists the `ActionReceipt` via `set_postponed_receipt` under the trie key `TrieKey::PostponedReceipt{receiver_id, receipt_id}` (as defined in `core/primitives/src/trie_key.rs`) and only fetches/executes it later, via `get_postponed_receipt`, once all `ReceivedData` for its `input_data_ids` arrive (handled in the `Data` arm of `process_receipt` in `runtime/runtime/src/lib.rs`). This postponed state is addressed purely by `(receiver_id, receipt_id)` — it is *not* tied to any specific account "incarnation" or nonce.

`remove_account` (core/store/src/utils/mod.rs:505-575) is invoked by `action_delete_account` (`runtime/runtime/src/actions.rs`, which imports `remove_account` from `near_store` at line 38) when a `DeleteAccount` action executes. It removes:
- `TrieKey::Account`
- `TrieKey::ContractCode`
- All `AccessKey`/gas-key rows (via the access-key prefix iteration)
- All `ContractData` rows

but the function contains no iteration over the `PostponedReceipt` or `ReceivedData` prefixes for that account. As a result, any postponed `ActionReceipt` created before the deletion — including one embedding privileged self-actions such as `AddKey(FullAccess, attacker_pubkey)` (valid at creation time because `predecessor_id == receiver_id == X` satisfies `check_actor_permissions`) — remains durably stored in the trie under the deleted account's namespace.

Exploit flow:
1. Attacker's contract on account `X` issues a receipt to itself with an `ActionReceipt` containing two `input_data_ids` and an `AddKey(FullAccess, attacker_pubkey)` action. Since it has unresolved data dependencies, it is persisted via `set_postponed_receipt` under `PostponedReceipt{receiver_id: X, receipt_id}`.
2. Before supplying the missing `DataReceipt`s, attacker submits `DeleteAccount(X)` in a separate receipt/transaction — this succeeds and calls `remove_account`, which leaves the postponed receipt row untouched.
3. Attacker (or a parent contract they control) re-creates account `X` (fresh `Account` state, no keys, no code).
4. Attacker now supplies the previously withheld `DataReceipt`(s) targeting the original `receipt_id`. The `Data` arm of `process_receipt` finds `pending_data_count` satisfied, calls `get_postponed_receipt`, retrieves the untouched stale `ActionReceipt`, and executes it against account `X` — now the newly re-created account — running `AddKey(FullAccess, attacker_pubkey)` successfully, since `check_actor_permissions` re-validates `predecessor_id == receiver_id == X`, which still holds.

No existing check (signature, nonce, access-key permission, or account-existence check on postponed-receipt resolution) stops this because the postponed-receipt mechanism does not track account-incarnation identity, and `remove_account` does not invalidate pending postponed state tied to the account it deletes.

### Impact Explanation
This is an authorization-escalation-across-account-recreation bug: an attacker obtains a durable `FullAccess` key injected via a receipt that was authorized under the *old* incarnation of the account but executes against the *new* one. While in this specific scenario `X` is the attacker's own account (so the "escalation" nets the attacker a key on an account they already control freshly), the same primitive generalizes to a shared/managed account pattern (e.g., factory-created sub-accounts, DAO-controlled accounts) where a delegated/limited actor could stage a postponed self-receipt, have the account deleted and later re-created by a different, trusted flow, and have the escalation apply to the new owner's account — corresponding to the "authorization escalation across accounts or promises" bounty category.

### Likelihood Explanation
The preconditions are fully within attacker capability using only standard, unprivileged transactions: deploying a contract, issuing promises with data dependencies, and controlling the timing of `DataReceipt` delivery (attacker can withhold/delay supplying `PromiseResults`/data until after re-creation). No validator or node-level access is required, and the exploit is repeatable at will since it only depends on the general absence of postponed-receipt cleanup in `remove_account`.

### Recommendation
Extend `remove_account` in core/store/src/utils/mod.rs to also iterate and remove all `TrieKey::PostponedReceipt{receiver_id, ..}` and `TrieKey::ReceivedData{receiver_id, ..}` rows for the account being deleted (mirroring the existing access-key/contract-data prefix-iteration pattern), so that any pending postponed receipts and their data dependencies are invalidated when the account is deleted, preventing later resolution from re-executing against a re-created account.

### Proof of Concept
Integration test plan (runtime/runtime/src/tests or apply.rs style test-loop):
1. Deploy a contract to account `X` that, in one function call, creates an `ActionReceipt` to `X` itself with two `input_data_ids` and an `AddKey(FullAccess, attacker_pubkey)` action; assert via `get_postponed_receipt` that the row is persisted under `PostponedReceipt{X, receipt_id}`.
2. Submit `DeleteAccount(X)` receipt; call `remove_account`/apply it; assert `TrieKey::Account{X}` is gone but `get_postponed_receipt(state_update, &X, receipt_id)` still returns `Some(..)`.
3. Re-create account `X` via a `CreateAccount` action from a funding account.
4. Deliver both `DataReceipt`s targeting `receipt_id`; drive `process_receipt`'s `Data` arm; assert the postponed `ActionReceipt` executes (`get_postponed_receipt` fetched then cleared) and that `check_actor_permissions` allows the `AddKey` action.
5. Assert final state: `X`'s access keys now include `attacker_pubkey` with `FullAccess` — confirming the escalation. A fixed version of `remove_account` should cause the postponed receipt to be absent after deletion, and the `AddKey` should never execute (either the receipt is dropped or fails to resolve).
