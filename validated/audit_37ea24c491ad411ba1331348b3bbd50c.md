### Title
`ValidateMultiSign` precompile allows same signer to double-count weight via duplicate/malleable signatures - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `ValidateMultiSign` precompiled contract (used by the `validatemultisign` TVM opcode/precompile reachable from any smart contract call) aggregates signature weight to check a multisig `Permission` threshold, but its duplicate-signer detection logic is flawed: when the same recovered address appears more than once with *different* raw signature bytes, the code does not skip it — it falls through and adds that signer's weight to `totalWeight` again. This is analogous to the `VetoProposal.voteToVeto` bug where the same voter could push a vote twice to cross a threshold; here the same key's "vote" (signature weight) can be counted multiple times to cross the multisig `threshold`.

### Finding Description
`TransactionCapsule.checkWeight` (used for real transaction signature validation, e.g. `chainbase/src/main/java/org/tron/core/capsule/TransactionCapsule.java:233-270`) correctly deduplicates by recovered address using a `HashMap` and throws `"has signed twice!"` if the same address appears twice: [1](#0-0) .

However, the separate implementation in the `ValidateMultiSign` precompile does not use this safe path. It maintains its own `executedSignList` and dedupe logic: [2](#0-1) 

The relevant loop:
```java
for (byte[] sign : signatures) {
  byte[] recoveredAddr = recoverAddrBySign(sign, hash);
  sign = merge(recoveredAddr, sign);
  if (ByteArray.matrixContains(executedSignList, recoveredAddr)) {
    if (ByteArray.matrixContains(executedSignList, sign)) {
      continue;
    }
    MUtil.checkCPUTime();
  }
  long weight = TransactionCapsule.getWeight(permission, recoveredAddr);
  ...
  totalWeight += weight;
  executedSignList.add(sign);
  executedSignList.add(recoveredAddr);
}
```
The only case that is actually skipped (`continue`) is when the *exact* merged `(recoveredAddr, sign)` pair has been seen before — i.e. the identical signature bytes are repeated. If the same private key produces a *different* valid signature over the same `hash` (e.g. via ECDSA signature malleability, using `(r, n-s)` with the corresponding flipped recovery id, or simply generating a new nondeterministic ECDSA signature using a different `k` nonce), `recoveredAddr` will be identical but `sign` will differ, so `matrixContains(executedSignList, sign)` is `false`, the `continue` is skipped, and execution falls through to add `weight` for that same address again. The `MUtil.checkCPUTime()` call is unrelated to correctness — it is a CPU-throttling/DoS guard, not a duplicate-vote rejection.

### Impact Explanation
Any account calling a smart contract that invokes the `validatemultisign`/`ValidateMultiSign` precompile (a caller-supplied signature array, permission id, and address, fully controllable from an unprivileged transaction) can supply multiple distinct valid signatures produced with a single private key to inflate `totalWeight` past `permission.getThreshold()`. This lets a party holding a single key (with weight less than the threshold) satisfy a multisig `Permission` check that was intended to require several independent co-signers — enabling unauthorized authorization/approval decisions for any contract-side logic relying on this precompile's result (e.g. gating asset transfers, contract execution paths, or governance-style approvals implemented in Solidity using `validatemultisign`). This matches the "concrete unauthorized account operation" impact bar, directly analogous to the veto proposal's double-vote threshold bypass.

### Likelihood Explanation
High reachability: the precompile is invoked purely through an unprivileged TVM contract call (`TriggerSmartContract`) with attacker-controlled `signatures` array; no special privilege is required. Producing a second, distinct valid ECDSA signature over the same hash from one private key is trivial (e.g. compute `s' = n - s` and flip the recovery id `v`, or simply re-sign with a different nonce for non-deterministic ECDSA). The only defense (`matrixContains(executedSignList, sign)`) checks for byte-exact signature repetition, not signer-address repetition, so it does not block this.

### Recommendation
Deduplicate by `recoveredAddr` only (not by the full merged `sign` bytes), mirroring the correct logic already used in `TransactionCapsule.checkWeight`: once an address has contributed weight, any further signature recovering to that same address must be skipped entirely (do not add weight again), e.g.:
```java
if (ByteArray.matrixContains(executedSignList, recoveredAddr)) {
    continue; // address already counted; ignore any further signature from it
}
```
and remove the fallthrough path that increments `totalWeight` for a previously-seen address.

### Proof of Concept
1. Create an account with an `Active` permission of `threshold = 2` containing a single key `K` with `weight = 1` (or, more generally, any permission where one key's weight alone is `< threshold` but appears sufficient once "doubled").
2. Deploy/call a contract that invokes the `validatemultisign(address, permissionId, data, sig[])` precompile with a `signatures` array containing two different valid signatures from `K` over the same `hash` (e.g., one signature and its malleable variant `(r, n-s)` with corrected recovery id, or two independently-generated ECDSA signatures using different nonces).
3. In `ValidateMultiSign.execute`: both entries recover to the same `recoveredAddr` but differ in raw `sign` bytes, so `matrixContains(executedSignList, sign)` is `false` for the second entry; the loop does not `continue`, and `totalWeight` accumulates `weight` twice (`totalWeight = 2`), reaching `permission.getThreshold() == 2`.
4. The precompile returns `dataOne()` (success), even though only one distinct signer actually participated — bypassing the intended 2-of-N multisig requirement.

Existing tests (`framework/src/test/java/org/tron/common/runtime/vm/ValidateMultiSignContractTest.java:117-121`) only test *exact byte-identical* duplicate signatures being rejected/ignored — they do not cover the case of two distinct valid signatures from the same key, so this gap is not exercised by current test coverage: [3](#0-2)
