### Title
`lighthouse.am_lighthouse` cannot be updated on config reload, leaving stale lighthouse-authorization state after SIGHUP - (File: lighthouse.go)

### Summary
`LightHouse.amLighthouse` is a boolean gate that determines whether this node accepts and stores `HostUpdateNotification` messages from arbitrary peers (i.e., acts as an address-authority for the mesh). It is set once from `lighthouse.am_lighthouse` in `NewLightHouseFromConfig` and stored in the unexported field `h.amLighthouse` [1](#0-0) . Unlike every other `lighthouse.*` setting (`advertise_addrs`, `interval`, `remote_allow_list`/`remote_allow_ranges`, `local_allow_list`, `calculated_remotes`, `hosts`, `static_host_map`, `relay.relays`), `lighthouse.am_lighthouse` is never re-read inside `LightHouse.reload()`, which is the function invoked on every config reload/SIGHUP [2](#0-1) [3](#0-2) . This is the same bug class as the reported `wheelOfGuantuneNft` finding: a config field that has update paths for its siblings but no update function of its own.

### Finding Description
`reload()` walks through every `lighthouse.*` and `static_host_map`/`relay.*` key with `c.HasChanged(...)` checks to decide whether to rebuild derived state, e.g. `lighthouse.advertise_addrs`, `lighthouse.interval`, `lighthouse.remote_allow_list`/`remote_allow_ranges`, `lighthouse.local_allow_list`, `lighthouse.calculated_remotes`, `lighthouse.hosts`, `static_host_map`, and `relay.relays` [2](#0-1) [4](#0-3) [5](#0-4) . `lighthouse.am_lighthouse` is conspicuously absent from this list, and the private `amLighthouse` field is never written anywhere outside the constructor [6](#0-5) [7](#0-6) .

`amLighthouse` directly gates a security-relevant decision in `handleHostUpdateNotification`, the handler for unauthenticated-content but tunnel-encrypted `HostUpdateNotification` packets that any peer with a valid tunnel can send:
```go
func (lhh *LightHouseHandler) handleHostUpdateNotification(n *NebulaMeta, fromVpnAddrs []netip.Addr, w EncWriter) {
	if !lhh.lh.amLighthouse {
		...
		return
	}
	...
}
``` [8](#0-7) 

Because the field is frozen at process start, changing `lighthouse.am_lighthouse` in the config file and sending SIGHUP (or the SSH `reload` command) has no effect on this gate for the life of the process, even though the docs/CHANGELOG state that "`punchy` and most `lighthouse` config options now support hot reloading" (#649) [9](#0-8) , implying an operator expectation that this flag is reloadable along with the rest of the `lighthouse` block.

### Impact Explanation
If an operator demotes a host from lighthouse to a regular client (`am_lighthouse: true -> false`) via a reload — expecting it to stop authoritatively accepting/serving address information — the running process keeps `amLighthouse == true` and continues to accept `HostUpdateNotification` records and answer `HostQuery` requests as if it were still an authorized lighthouse, poisoning the address-cache/hostmap state (`RemoteList`/`addrMap`) that other peers rely on to establish handshakes. Conversely, promoting a node to a lighthouse via reload will not enable it to accept host updates until a full process restart, causing a silent, hard-to-diagnose availability/trust gap. This falls into the "remote state poisoning" / "hostmap and lighthouse address trust" bug class explicitly in scope, and is reachable by any peer that can reach the tunnel (no CA-signed cert needed to trigger the stale-trust condition itself — the stale gate persists regardless of who talks to the node).

### Likelihood Explanation
This will manifest any time an admin relies on SIGHUP/`reload`/`ReloadConfigString` to flip `lighthouse.am_lighthouse`, which the project's own documentation and CHANGELOG imply is supported behavior for the `lighthouse` config stanza. No attacker action is required to trigger the staleness — it is a deterministic consequence of the missing reload wiring — but its security effect (accepting/serving address updates as an unintended lighthouse, or failing to as an intended one) is exercised by ordinary peer traffic once triggered.

### Recommendation
Add `lighthouse.am_lighthouse` handling to `LightHouse.reload()`, mirroring the pattern already used for the other lighthouse fields, e.g.:
```diff
 func (lh *LightHouse) reload(c *config.C, initial bool) error {
+	if initial || c.HasChanged("lighthouse.am_lighthouse") {
+		newAmLighthouse := c.GetBool("lighthouse.am_lighthouse", false)
+		if !initial && newAmLighthouse != lh.amLighthouse {
+			lh.l.Info("lighthouse.am_lighthouse has changed", "value", newAmLighthouse)
+		}
+		lh.amLighthouse = newAmLighthouse
+	}
 	if initial || c.HasChanged("lighthouse.advertise_addrs") {
```
Convert `amLighthouse` to an `atomic.Bool` (it is read concurrently from the packet-handling goroutines) so the update is safe under concurrent access, and validate at reload time (as is already done at construction) that `am_lighthouse` cannot be enabled without `listen.port` set.

### Proof of Concept
1. Start a nebula node with `lighthouse.am_lighthouse: true` and `listen.port` set; confirm it accepts `HostUpdateNotification` packets from peers (verified by `TestLighthouse_Memory`/`newLHHostUpdate` helpers) [10](#0-9) .
2. Edit the running config on disk to set `lighthouse.am_lighthouse: false` and send SIGHUP (or run the SSH `reload` command).
3. Send another `HostUpdateNotification` from a peer to the node; observe that it is still accepted and stored (because `lh.amLighthouse` was never re-read), whereas a fresh process start with the same config would reject it via the early return in `handleHostUpdateNotification` [8](#0-7) .

Note: I was unable to fully verify from the index alone whether any other code path (outside `lighthouse.go`) re-derives `amLighthouse` on reload — the searches performed did not surface one, and `LightHouse.reload()` is the only registered reload callback for this struct [11](#0-10) . If a Devin session with full repo access is available, it would be worth grepping the entire codebase once more for `.amLighthouse =` assignments to rule out a reload path I may have missed.

	if initial || c.HasChanged("lighthouse.advertise_addrs") {
		rawAdvAddrs := c.GetStringSlice("lighthouse.advertise_addrs", []string{})
		advAddrs := make([]netip.AddrPort, 0)

		for i, rawAddr := range rawAdvAddrs {
			host, sport, err := net.SplitHostPort(rawAddr)
			if err != nil {
				return util.NewContextualError("Unable to parse lighthouse.advertise_addrs entry", m{"addr": rawAddr, "entry": i + 1}, err)
			}

			addrs, err := net.DefaultResolver.LookupNetIP(context.Background(), "ip", host)
			if err != nil {
				return util.NewContextualError("Unable to lookup lighthouse.advertise_addrs entry", m{"addr": rawAddr, "entry": i + 1}, err)
			}
			if len(addrs) == 0 {
				return util.NewContextualError("Unable to lookup lighthouse.advertise_addrs entry", m{"addr": rawAddr, "entry": i + 1}, nil)
			}

			port, err := strconv.Atoi(sport)
			if err != nil {
				return util.NewContextualError("Unable to parse port in lighthouse.advertise_addrs entry", m{"addr": rawAddr, "entry": i + 1}, err)
			}

			if port == 0 {
				port = int(lh.nebulaPort)
			}

			//TODO: we could technically insert all returned addrs instead of just the first one if a dns lookup was used
			addr := addrs[0].Unmap()
			if lh.myVpnNetworksTable.Contains(addr) {
				lh.l.Warn("Ignoring lighthouse.advertise_addrs report because it is within the nebula network range",
					"addr", rawAddr,
					"entry", i+1,

				continue
			}

			advAddrs = append(advAddrs, netip.AddrPortFrom(addr, uint16(port)))

			lh.l.Info("lighthouse.advertise_addrs has changed")
