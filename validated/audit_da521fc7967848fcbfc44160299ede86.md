### Title
Missing deadline parameter allows pending `leverage`/`flashRepay` transactions to be executed later at stale slippage bounds - (File: contracts/SmartFarmingManager.sol)

### Summary
`SmartFarmingManager.leverage()` and `SmartFarmingManager.flashRepay()` let users delegate AMM swaps to the `ISwapper` contract, but neither the entry points nor `ISwapper.swapExactInput()` accept a deadline. The only protection is a user-supplied `amountOutMin`/`depositAmountMin`/`swapAmountOutMin` value fixed at signing time. If the transaction sits pending and prices move, it still executes with the now-stale slippage bound, enabling the same sandwich/MEV loss as the reported Derby finding.

### Finding Description
`leverage()` performs up to two external swaps through `_swap(...)`, which calls `swapper_.swapExactInput(tokenIn, tokenOut, amountIn, amountOutMin, to)` with no deadline argument [1](#0-0) . The intermediate synth→collateral swap is executed with `amountOutMin_ = 0` and relies solely on the final `depositAmountMin_` check [2](#0-1) . `flashRepay()` similarly swaps the withdrawn collateral with `amountOutMin_ = 0` and checks only `swapAmountOutMin_` afterward [3](#0-2) . The `ISwapper` interface itself has no deadline field [4](#0-3) . Neither function accepts a user deadline, and both are unprivileged external entry points guarded only by `whenNotShutdown`/`nonReentrant` [5](#0-4) .

### Impact Explanation
Direct theft of user funds via MEV sandwich: a pending `leverage` or `flashRepay` transaction whose slippage bound was reasonable at signing time becomes exploitable after price movement. A bot can push the AMM price so the executed swap output is just above the stale minimum — the user absorbs the full slippage while the tx still succeeds, since the final `debtPositionOf` health check only validates post-trade solvency, not execution price [6](#0-5) .

### Likelihood Explanation
Requires the victim's transaction to remain pending (low gas) or be delayed — a common mempool condition, and an unprivileged EOA/bot can perform the sandwich with ordinary AMM trades. All parameters (`tokenIn_`, amounts, min-out) are attacker-agnostic user inputs; no privileged role or oracle manipulation is needed.

### Recommendation
Add a `deadline` parameter to `leverage()`, `flashRepay()`, the cross-chain variants, and `ISwapper.swapExactInput()`, reverting when `block.timestamp > deadline` so stale transactions expire instead of executing at outdated slippage bounds.

### Proof of Concept
Hardhat fork sketch:
1. Fork mainnet; impersonate a user holding collateral; deploy/attach real `SmartFarmingManager` and `Swapper`.
2. User signs `leverage(tokenIn, depositToken, msUSD, amountIn, 2e18, depositAmountMin)` with `depositAmountMin` computed from current prices, broadcast with low gas price — tx stays pending.
3. Advance time / move AMM price so tokenIn↔collateral rate shifts in the user's apparent favor, making the stale min loose.
4. Attacker sandwiches: dumps collateral on the AMM, lets the pending tx mine (still passes `depositAmountMin_` and the health check), then buys back — profit equals slippage extracted from the user.
5. Assert user's `deposited` is materially below the fair-value deposit, and that a hypothetical `block.timestamp > deadline` check would have reverted it.

        ISwapper swapper_,
        IERC20 tokenIn_,
        IERC20 tokenOut_,
        uint256 amountIn_,
        uint256 amountOutMin_,
        address to_
    ) private returns (uint256 _amountOut) {
        if (tokenIn_ != tokenOut_) {
            tokenIn_.safeApprove(address(swapper_), 0);
            tokenIn_.safeApprove(address(swapper_), amountIn_);
            uint256 _tokenOutBefore = tokenOut_.balanceOf(to_);
