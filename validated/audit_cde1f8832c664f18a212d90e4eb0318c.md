### Title
Reward accounting split across two disjoint VI stores causes permanent loss of pre-migration witness voting rewards when claimed via the TVM `withdrawReward`/`WithdrawRewardProcessor` path - (File: actuator/src/main/java/org/tron/core/vm/utils/VoteRewardUtil.java)

### Summary
Analogous to the reported discrepancy where a staking wrapper (`AbstractStakingAM`) computes accrued position rewards with a formula that diverges from the formula the underlying protocol used to actually deliver rewards, java-tron maintains **two independent "reward-per-vote" (`Vi`) accumulators** for the same underlying witness reward pool, and only one of them is consulted by the TVM-facing reward-withdraw code path. This produces a real accounting mismatch that permanently strands legitimate reward funds for accounts whose vote history spans the "old" (pre-VI) reward algorithm era and who withdraw via the TVM native contract path.

### Finding Description
Witness voting rewards in java-tron are computed via a per-witness "value-per-vote" accumulator (`Vi`), and a user's reward for a cycle range is `deltaVi * userVote / DECIMAL`, exactly analogous to the audit report's "rewardPerToken" accounting.

There are two call sites that compute this reward for a user, and they consult **two different data stores**:

1. `MortgageService.computeReward(beginCycle, endCycle, accountCapsule)` (native `WithdrawBalanceContract` path) explicitly splits the range at `newRewardAlgorithmEffectiveCycle`: for cycles *before* the new algorithm went live, it falls back to `getOldReward(...)`, which (when `allowOldRewardOpt()`), delegates to `RewardViCalService.getNewRewardAlgorithmReward(...)`. That service reads `Vi` values it back-computed and stored in a **separate `RewardViStore`** DB (`rewardViStore.get(buildViKey(cycle,address))`), populated once by `RewardViCalService.startRewardCal()`/`accumulateWitnessVi` replaying historical `reward`/`vote` records up to `newRewardCalStartCycle`. [1](#0-0) [2](#0-1) [3](#0-2) 

2. `VoteRewardUtil.withdrawReward`/`queryReward` (the TVM `withdrawReward` opcode path, reached from `WithdrawRewardProcessor.execute` and `Program.withdrawReward`) does **not** perform this split at all. `computeReward` in `VoteRewardUtil` unconditionally reads `repository.getDelegationStore().getWitnessVi(cycle, srAddress)` for the *entire* `[beginCycle, endCycle)` range, i.e. only `DelegationStore`'s own `Vi` keys. [4](#0-3) [5](#0-4) 

`DelegationStore`'s own `Vi` keys are only ever populated going forward from the cycle the new algorithm becomes active — `MaintenanceManager.doMaintenance()` only calls `delegationStore.accumulateWitnessVi(...)` when `dynamicPropertiesStore.useNewRewardAlgorithm()` is true: [6](#0-5) [7](#0-6) 

The pre-migration reward history is backfilled *only* into the separate `RewardViStore`, never into `DelegationStore`'s own `Vi` keyspace. Consequently, for any voting cycles that predate `newRewardAlgorithmEffectiveCycle`, `DelegationStore.getWitnessVi(cycle, address)` returns `BigInteger.ZERO` (no record exists), so `beginVi`/`endVi` in `VoteRewardUtil.computeReward` are both zero and `deltaVi.signum() <= 0` causes that reward segment to be silently skipped — not underpaid-and-recoverable-later, but dropped entirely, because the same call also advances `beginCycle`/`endCycle` bookkeeping in the shared `DelegationStore`/`Repository` state (`repository.updateBeginCycle`, `repository.updateEndCycle`, `repository.updateAccountVote`), which is the **same underlying store and same per-address keys** that `MortgageService.withdrawReward` reads (`delegationStore.getBeginCycle(address)` / `setBeginCycle`). [8](#0-7) [9](#0-8) 

Once a user (or a smart-contract-controlled account that has previously voted for a witness before the algorithm switch) triggers the TVM `withdrawReward` opcode, `beginCycle` is advanced past the un-rewarded old-era cycles for that address, and any subsequent call — whether via the TVM path again or via the native `WithdrawBalanceContract`/`MortgageService.withdrawReward` — can no longer recompute or reclaim the skipped pre-migration reward, because `beginCycle` no longer covers that range. The funds are permanently lost to the user, while `RewardViStore`'s independently-computed value for the same period is never consulted or reconciled by this code path.

### Impact Explanation
This is a concrete, permanent loss-of-funds bug rather than a theoretical rounding difference: any account that (a) had votes recorded prior to the new-reward-algorithm activation cycle and (b) calls the TVM `withdrawReward` precompiled path (reachable by any unprivileged smart contract or EOA via a signed transaction invoking a contract that calls the vote/withdraw opcode) will have its pre-migration reward silently zeroed and its cycle bookkeeping advanced, making that reward permanently unclaimable through any subsequent path. This matches the accepted "permanent freezing/loss of funds" impact category.

### Likelihood Explanation
Likelihood is bounded by how many addresses still have unresolved reward ranges spanning the pre-migration era and have not yet triggered a TVM-side withdraw. Since `allowTvmVote()`/TVM voting has been enabled for a considerable time on live networks, and any address with `beginCycle < newRewardAlgorithmEffectiveCycle` that never withdrew via the TVM path is exposed the first time it does so (or any contract account programmed to vote/withdraw via TVM), this is realistically triggerable by an ordinary unprivileged transaction, not merely a privileged actor.

### Recommendation
Make `VoteRewardUtil.computeReward` mirror `MortgageService.computeReward`'s split logic: for the portion of `[beginCycle, endCycle)` prior to `newRewardAlgorithmEffectiveCycle`, consult the same old-algorithm reward source (`RewardViCalService`/`RewardViStore` or the legacy per-cycle vote-rate computation) instead of unconditionally reading `DelegationStore`'s VI, which is empty for that range. Alternatively, unify the two VI stores so both code paths read from a single, consistently populated source of truth.

### Proof of Concept
1. Prior to `newRewardAlgorithmEffectiveCycle`, an account casts votes for a witness and rewards accumulate in `delegationStore` (`addReward`) and legacy per-cycle vote counts (`setWitnessVote`), with `beginCycle` left unclaimed (e.g. `beginCycle = 1`).
2. The network activates the new reward algorithm at cycle N (`useNewRewardAlgorithm()` becomes true); `MaintenanceManager` begins populating `DelegationStore`'s own `Vi` only from cycle N onward. `RewardViCalService` separately backfills cycles `1..N-1` into `RewardViStore` only.
3. The account (or a contract it controls) calls the TVM `withdrawReward` opcode (`Program.withdrawReward` → `WithdrawRewardProcessor.execute` → `VoteRewardUtil.withdrawReward`).
4. `VoteRewardUtil.computeReward(1, currentCycle, ...)` reads `DelegationStore.getWitnessVi(0, sr)` and `getWitnessVi(N-1, sr)`, both `BigInteger.ZERO` since `DelegationStore` never recorded VI for cycles `<N`; `deltaVi<=0` for that segment, contributing `0` reward for cycles `1..N-1`.
5. `repository.updateBeginCycle(address, currentCycle)` is executed regardless, permanently moving the address's `beginCycle` past the unrewarded range.
6. A later call to `MortgageService.withdrawReward` (native path) for the same address now computes reward only from the already-advanced `beginCycle`, so the pre-migration reward is unrecoverable — the funds are permanently lost.

Note: I could not fully verify (due to remaining tool budget) whether `RepositoryImpl.getBeginCycle`/`updateBeginCycle` truly write to the identical `DelegationStore` key namespace as `MortgageService`'s calls (this is the load-bearing assumption for "same underlying store"); confirming this wiring in `actuator/src/main/java/org/tron/core/vm/repository/RepositoryImpl.java` would be the key remaining verification step.

  private long computeReward(long beginCycle, long endCycle, AccountCapsule accountCapsule) {
    if (beginCycle >= endCycle) {
      return 0;
    }

    long reward = 0;
    long newAlgorithmCycle = dynamicPropertiesStore.getNewRewardAlgorithmEffectiveCycle();
    List<Pair<byte[], Long>> srAddresses = accountCapsule.getVotesList().stream()
        .map(vote -> new Pair<>(vote.getVoteAddress().toByteArray(), vote.getVoteCount()))
        .collect(Collectors.toList());
    if (beginCycle < newAlgorithmCycle) {
      long oldEndCycle = min(endCycle, newAlgorithmCycle,
          dynamicPropertiesStore.disableJavaLangMath());
      reward = getOldReward(beginCycle, oldEndCycle, srAddresses);
      beginCycle = oldEndCycle;
    }
    if (beginCycle < endCycle) {
      for (Pair<byte[], Long>  vote : srAddresses) {
        byte[] srAddress = vote.getKey();
        BigInteger beginVi = delegationStore.getWitnessVi(beginCycle - 1, srAddress);
        BigInteger endVi = delegationStore.getWitnessVi(endCycle - 1, srAddress);
        BigInteger deltaVi = endVi.subtract(beginVi);
        if (deltaVi.signum() <= 0) {
          continue;
        }
        long userVote = vote.getValue();
        reward += deltaVi.multiply(BigInteger.valueOf(userVote))
            .divide(DelegationStore.DECIMAL_OF_VI_REWARD).longValue();
      }
    }
    return reward;
  }

  private void accumulateWitnessReward(byte[] witness) {
    long startCycle = 1;
    LongStream.range(startCycle, newRewardCalStartCycle)
        .forEach(cycle -> accumulateWitnessVi(cycle, witness));
  }

  private void accumulateWitnessVi(long cycle, byte[] address) {
    BigInteger preVi = getWitnessVi(cycle - 1, address);
    long voteCount = getWitnessVote(cycle, address);
    long reward = getReward(cycle, address);
    if (reward == 0 || voteCount == 0) { // Just forward pre vi
      if (!BigInteger.ZERO.equals(preVi)) { // Zero vi will not be record
        setWitnessVi(cycle, address, preVi);
      }
    } else { // Accumulate delta vi
      BigInteger deltaVi = BigInteger.valueOf(reward)
          .multiply(DECIMAL_OF_VI_REWARD)
          .divide(BigInteger.valueOf(voteCount));
      setWitnessVi(cycle, address, preVi.add(deltaVi));
    }
  }

  private void setWitnessVi(long cycle, byte[] address, BigInteger value) {
    byte[] k = buildViKey(cycle, address);
    byte[] v = value.toByteArray();
    rewardViStore.put(k, v);
  }

  private BigInteger getWitnessVi(long cycle, byte[] address) {

    byte[] v = rewardViStore.get(buildViKey(cycle, address));
    if (v == null) {
      return BigInteger.ZERO;
    } else {
      return new BigInteger(v);
    }
  }

  private static long computeReward(long beginCycle, long endCycle,
                                    AccountCapsule accountCapsule, Repository repository) {
    if (beginCycle >= endCycle) {
      return 0;
    }

    long reward = 0;
    for (Protocol.Vote vote : accountCapsule.getVotesList()) {
      byte[] srAddress = vote.getVoteAddress().toByteArray();
      BigInteger beginVi = repository.getDelegationStore().getWitnessVi(beginCycle - 1, srAddress);
      BigInteger endVi = repository.getDelegationStore().getWitnessVi(endCycle - 1, srAddress);
      BigInteger deltaVi = endVi.subtract(beginVi);
      if (deltaVi.signum() <= 0) {
        continue;
      }
      long userVote = vote.getVoteCount();
      reward += deltaVi.multiply(BigInteger.valueOf(userVote))
          .divide(DelegationStore.DECIMAL_OF_VI_REWARD).longValue();
    }
    return reward;
  }
