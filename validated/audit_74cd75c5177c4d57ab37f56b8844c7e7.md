## Analysis

The reported bug class (missing zero-address check before a token transfer, causing permanent loss/lock-up of funds) has a direct analog in java-tron's `TransferActuator` and `TransferAssetActuator`.

Both actuators validate `toAddress` using `DecodeUtil.addressValid()`, but this function only checks the address length and the network prefix byte — it never checks whether the address bytes are all-zero: [1](#0-0) 

Because of this, `TransferActuator.validate()` accepts an all-zero `to_address` (i.e. `0x41` followed by 20 zero bytes) as valid and proceeds to move TRX to it, silently creating a new account there if it doesn't exist: [2](#0-1) [3](#0-2) 

The same missing check exists in `TransferAssetActuator.validate()`/`execute()` for TRC10 asset transfers, and in the TVM's internal-transfer validation helper `VMUtils.validateForSmartContract`, all of which call `DecodeUtil.addressValid` without any additional check against the zero address: [4](#0-3) [5](#0-4) 

### Title
Missing zero-address validation in `TransferActuator`/`TransferAssetActuator` allows funds to be sent to an unrecoverable all-zero address - (File: `actuator/src/main/java/org/tron/core/actuator/TransferActuator.java`, `actuator/src/main/java/org/tron/core/actuator/TransferAssetActuator.java`)

### Summary
`TransferActuator` and `TransferAssetActuator` (reachable by any unprivileged account that broadcasts a `TransferContract` or `TransferAssetContract` transaction) validate the destination address solely via `DecodeUtil.addressValid()`, which only checks address length and the chain's address prefix byte. It does not reject the all-zero address body (prefix + 20 zero bytes), so TRX or TRC10 tokens can be sent to that address.

### Finding Description
`DecodeUtil.addressValid` at `common/src/main/java/org/tron/common/utils/DecodeUtil.java:15-33` performs no value-based sanity check — it never rejects an address whose 20-byte body is all zeros. Both `TransferActuator.validate()` (`actuator/src/main/java/org/tron/core/actuator/TransferActuator.java:104-109`) and `TransferAssetActuator.validate()` (`actuator/src/main/java/org/tron/core/actuator/TransferAssetActuator.java:136-141`) rely exclusively on this function for `toAddress` validation, then in `execute()` create a fresh `AccountCapsule` at that address and credit it with the transferred amount (`TransferActuator.java:48-66`, `TransferAssetActuator.java:62-84`). The same gap exists in the TVM's internal transfer validation helper `VMUtils.validateForSmartContract` (`actuator/src/main/java/org/tron/core/vm/VMUtils.java:137-148`), reachable from smart-contract `transfer`/`transferToken` opcodes triggered by any contract-calling transaction.

### Impact Explanation
No private key is known to correspond to the all-zero address; funds sent there are effectively permanently frozen/unrecoverable, matching a "permanent freezing of funds" outcome. This is directly analogous to the reported YoloV2 issue where missing zero-address checks before a transfer could lock up funds.

### Likelihood Explanation
The path is trivially reachable — any account holder can construct and broadcast a normal `TransferContract` or `TransferAssetContract` with `to_address` set to the all-zero address, or trigger a smart contract that performs an internal TRX/TRC10 transfer to that address. No special privilege is required, only accidental or malicious misuse of the destination field.

### Recommendation
Add an explicit check in `DecodeUtil.addressValid` (or separately in each actuator's `validate()` and in `VMUtils.validateForSmartContract`) to reject addresses whose 20-byte body is all zero, in addition to the existing length/prefix checks.

### Proof of Concept
1. Craft a `TransferContract` with `owner_address` = a funded account and `to_address` = `0x41` + 20 zero bytes.
2. Broadcast the transaction; `TransferActuator.validate()` passes because `DecodeUtil.addressValid` only checks length/prefix (`common/src/main/java/org/tron/common/utils/DecodeUtil.java:15-33`).
3. `TransferActuator.execute()` creates a new `AccountCapsule` at the zero address and credits it with the transferred amount (`actuator/src/main/java/org/tron/core/actuator/TransferActuator.java:48-66`), permanently locking those funds since no key controls that address.

      return false;

      return false;
    }
    return true;
