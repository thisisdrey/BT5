This is confirmed as an intentional but exploitable QoS design flaw: `max_concurrent_uni_streams` is derived from client-influenceable QUIC RTT measurements, and separately, actual stream throughput is gated by `max_unstaked_load_in_throttling_window` (a fixed value like 20 per 100ms window, independent of RTT). The RTT-based scaling only affects how many streams may be concurrently *open* on a connection, not the sustained throughput rate, which limits (but does not eliminate) the practical impact.

### Title
Unstaked client can inflate QUIC-measured RTT to gain a disproportionately larger `max_concurrent_uni_streams` quota - (File: streamer/src/nonblocking/swqos.rs)

### Summary
`compute_max_allowed_uni_streams_with_rtt` scales the number of concurrent uni-streams a connection is allowed by its measured `connection.rtt()`, clamped between `REFERENCE_RTT_MS` (50ms) and `MAX_RTT_MS` (350ms). Since QUIC RTT estimation is derived from ACK timing that the remote peer controls (e.g., by delaying ACKs), an unstaked, unprivileged client can artificially inflate its own RTT sample and be granted up to 7x more concurrent uni-streams (`QUIC_MAX_UNSTAKED_CONCURRENT_STREAMS` scaled from 128 to 896) than an honest low-latency peer of the identical `peer_type`.

### Finding Description
In `cache_new_connection` [1](#0-0) , the server reads `connection.rtt()` directly from the quinn QUIC connection state and feeds it uncorrected into `compute_max_allowed_uni_streams_with_rtt`, which multiplies the base per-peer-type stream allotment by `rtt_millis.clamp(REFERENCE_RTT_MS, MAX_RTT_MS) / REFERENCE_RTT_MS` [2](#0-1) . Quinn's RTT estimator (like most QUIC/TCP RTT estimators) is derived from the time between sending a packet and receiving its ACK — a value the receiving/ACKing peer partially controls by delaying acknowledgments (or by taking a deliberately circuitous network path). A remote unstaked client can therefore induce the server to observe an RTT near `MAX_RTT_MS` regardless of true network proximity, causing `set_max_concurrent_uni_streams` to be set to the maximum scaled value (`QUIC_MAX_UNSTAKED_CONCURRENT_STREAMS * 350 / 50 = 896`) instead of the baseline 128 given to an honest low-RTT peer of the same `ConnectionPeerType::Unstaked` classification [3](#0-2) . There is no independent corroboration of RTT (e.g., via server-side path/geolocation heuristics or minimum-RTT filtering resistant to deliberate delay) before this value is trusted.

However, the actual sustained processing rate of streams is separately capped by `throttle_stream`/`StakedStreamLoadEMA::available_load_capacity_in_throttling_duration`, which for unstaked peers returns a fixed `max_unstaked_load_in_throttling_window` value independent of RTT or `max_concurrent_uni_streams` [4](#0-3) . This means the RTT-inflation only increases the number of streams that may be concurrently *outstanding/opened* on a single connection (and associated per-stream buffer/state), not the throughput rate enforced over each 100ms window.

### Impact Explanation
The impact is a bounded QoS-fairness violation: an attacker-controlled unstaked connection can obtain a `max_concurrent_uni_streams` value up to 7x larger than an honest low-RTT peer, allowing it to hold more concurrent streams open and consume more per-connection buffer/state resources on the leader's TPU relative to compliant peers. This does not bypass the independent per-window stream-rate throttle (`available_load_capacity_in_throttling_duration`), the per-IP connection cap (`max_connections_per_unstaked_peer`), or the global unstaked connection table cap, so it does not translate into unbounded resource exhaustion or a full TPU-capacity-starvation DoS — it results in unfair capture of concurrent-stream capacity rather than uncapped throughput advantage.

### Likelihood Explanation
Feasibility is high and requires no special privileges: any remote unstaked client can delay ACKs on its own QUIC connection to influence quinn's RTT estimate, and this is done purely client-side with standard socket/packet-timing control, with no interaction from the validator needed. It is fully repeatable per-connection.

### Recommendation
Do not trust raw `connection.rtt()` for QoS-elevating decisions from unstaked/untrusted peers. Options: (1) only apply RTT-based BDP scaling to staked peers whose identity is cryptographically verified and whose behavior carries reputational/stake cost; (2) use quinn's minimum observed RTT over the connection lifetime combined with a smoothing/min-filter resistant to deliberate delay, and/or cross-check with independent server-side timing (e.g., handshake completion latency) before granting scaling; (3) cap the RTT-based multiplier bonus for `ConnectionPeerType::Unstaked` to a much smaller ceiling or remove RTT scaling entirely for unstaked connections since they have no accountability mechanism.

### Proof of Concept
Unit test extending the existing `test_max_allowed_uni_streams_with_rtt` in `streamer/src/nonblocking/swqos.rs` [5](#0-4)  to sweep the full domain and assert the ratio scales linearly and unboundedly by attacker-controlled RTT:
```rust
#[test]
fn test_unstaked_rtt_gaming_grants_disproportionate_streams() {
    let honest = compute_max_allowed_uni_streams_with_rtt(
        REFERENCE_RTT_MS, ConnectionPeerType::Unstaked, 10000);
    let attacker = compute_max_allowed_uni_streams_with_rtt(
        MAX_RTT_MS, ConnectionPeerType::Unstaked, 10000);
    assert_eq!(honest, QUIC_MAX_UNSTAKED_CONCURRENT_STREAMS); // 128
    assert_eq!(attacker, QUIC_MAX_UNSTAKED_CONCURRENT_STREAMS * (MAX_RTT_MS / REFERENCE_RTT_MS)); // 896
    assert!(attacker > honest * 6); // same peer_type, 7x quota via RTT manipulation alone
}
```
An integration-level PoC would use quinn's test harness to establish two unstaked connections to a `SwQos`-governed endpoint, artificially delaying ACK packets on one connection (e.g., via a custom `UdpSocket`/pacing wrapper that withholds ACK datagrams until `MAX_RTT_MS` has elapsed) and asserting that `connection.set_max_concurrent_uni_streams` was invoked with a materially larger value for the delayed-ACK connection versus the immediate-ACK connection, both classified identically as `ConnectionPeerType::Unstaked`.

    pub(crate) fn available_load_capacity_in_throttling_duration(
        &self,
        peer_type: ConnectionPeerType,
        total_stake: u64,
    ) -> u64 {
        match peer_type {
            ConnectionPeerType::Unstaked => self.max_unstaked_load_in_throttling_window,
            ConnectionPeerType::Staked(stake) => {
                if self.staked_throttling_enabled.load(Ordering::Relaxed) {
                    // 1 is added to `max_unstaked_load_in_throttling_window` to guarantee that staked
                    // clients get at least 1 more number of streams than unstaked connections.
                    self.max_staked_load_in_throttling_window
                        .saturating_mul(stake)
                        .checked_div(total_stake)
                        .unwrap_or(self.max_unstaked_load_in_throttling_window + 1)
                        .max(self.max_unstaked_load_in_throttling_window + 1)
                } else {
                    self.max_staked_load_in_throttling_window
                }
            }
        }
    }
