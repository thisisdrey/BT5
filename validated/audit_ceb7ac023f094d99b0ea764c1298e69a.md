Based on my investigation, I found a genuine analog of the reported bug class in java-tron: two independent implementations of the vote-reward "rate" (the delegation-reward VI accounting) that are supposed to compute the same conceptual value but diverge in behavior, reachable by any account through a smart-contract call (TVM precompile) versus the standard witness/vote actuator path.

### Title
Inconsistent vote-reward computation between `VoteRewardUtil` (TVM path) and `MortgageService` (native path) - ([File: actuator/src/main/java/org/tron/core/vm/utils/VoteRewardUtil.java])

### Summary
`VoteRewardUtil.computeReward` (used by the TVM `vote reward` precompile, reachable from any deployed smart contract) always computes reward purely via the "new algorithm" VI-delta method for the *entire* `[beginCycle, endCycle)` range. In contrast, `MortgageService.computeReward` (used by the native reward query/withdraw path invoked from block reward payment and wallet-level withdraw/query) splits the range at `dynamicPropertiesStore.getNewRewardAlgorithmEffectiveCycle()`, using the legacy per-cycle `totalReward/totalVote` ratio calculation (`getOldReward`) for cycles before that boundary and the VI-delta method only for cycles after it.

### Finding Description

`MortgageService.computeReward` (the "system"/native path), which explicitly branches on the new-algorithm effective cycle and falls back to `getOldReward` for cycles before it: [2](#0-1) [3](#0-2) 

The two reward-computation code paths both read from the same `DelegationStore`/VI data (`getWitnessVi`, `getReward`, `getWitnessVote`), but `VoteRewardUtil` has no equivalent branch for pre-`newRewardAlgorithmEffectiveCycle` cycles — it assumes VI values were populated for the entire cycle range. If a smart-contract voter's `beginCycle` for the TVM-vote precompile predates the new-reward-algorithm effective cycle (i.e., VI accounting was only backfilled via `RewardViCalService`/`accumulateWitnessVi` up to `newRewardCalStartCycle`, and legacy cycles rely on `getOldReward`'s per-cycle ratio, not VI), `VoteRewardUtil.computeReward` will compute a different (potentially wrong or zero) reward than `MortgageService.computeReward` would for the identical vote/cycle data — exactly mirroring the `accrueRate` vs `getTRate` inconsistency in the original report (same underlying "rate"/value computed two different ways in two different code paths that are relied upon interchangeably for the same accounting).

### Impact Explanation
An unprivileged user who deploys a contract and votes via `TvmVote`-related precompiles (`withdrawReward`/`queryReward` in `VoteRewardUtil`) could receive a reward amount inconsistent with what the native `MortgageService` accounting would produce for equivalent vote/cycle data, because `RewardViCalService` populates VI retroactively via `accumulateWitnessVi` only up to the effective cycle boundary using the *reward/voteCount* ratio recorded per cycle — but `VoteRewardUtil` unconditionally trusts VI for the whole range while `MortgageService` explicitly protects pre-boundary cycles with the legacy ratio method. This can lead to under- or over-crediting of allowance (`accountCapsule.setAllowance`), i.e., unbacked balance or permanently lost reward funds for TVM-vote users, depending on which side of the discrepancy manifests.

### Likelihood Explanation
This requires TVM voting (`VMConfig.allowTvmVote()`) to be enabled, and a contract's vote `beginCycle` to precede `newRewardCalStartCycle`. I could not fully verify from the indexed code whether `ALLOW_TVM_VOTE` is gated (via `ForkBlockVersionConsts`/proposal ordering in `ProposalUtil.java`) to only activate after the new reward algorithm is already fully effective network-wide, which would reduce or eliminate the practical reachability of the discrepancy. This is a material open question that limits confidence in exploitability, and would need to be confirmed by checking the hard-fork/feature activation ordering for `ALLOW_TVM_VOTE` versus the reward-algorithm switch on mainnet.

### Recommendation
Align `VoteRewardUtil.computeReward` with `MortgageService.computeReward`: add the same `newRewardAlgorithmEffectiveCycle`-based branch (delegating pre-boundary cycles to the same "old reward" ratio calculation, e.g., via `RewardViCalService.getNewRewardAlgorithmReward` or an equivalent shared utility) so that both the TVM precompile path and the native wallet/withdraw path compute rewards using a single, consistent algorithm for any given cycle range.

### Proof of Concept
Not independently reproducible from the indexed code alone — would require constructing a scenario where a contract begins voting before `newRewardCalStartCycle` (or before `RewardViStore`/`RewardViCalService` finishes backfilling), then compares `VoteRewardUtil.queryReward` output against `MortgageService.queryReward` output for the same address/cycle data to demonstrate the divergence. I could not confirm this end-to-end within the available tool budget; a Devin session with full repo/test access would be needed to write and run such a differential test.

  private static long computeReward(long beginCycle, long endCycle,
                                    AccountCapsule accountCapsule, Repository repository) {
    if (beginCycle >= endCycle) {
      return 0;
    }

    long reward = 0;
    for (Protocol.Vote vote : accountCapsule.getVotesList()) {
      byte[] srAddress = vote.getVoteAddress().toByteArray();
      BigInteger beginVi = repository.getDelegationStore().getWitnessVi(beginCycle - 1, srAddress);
      BigInteger endVi = repository.getDelegationStore().getWitnessVi(endCycle - 1, srAddress);
      BigInteger deltaVi = endVi.subtract(beginVi);
      if (deltaVi.signum() <= 0) {
        continue;
      }
      long userVote = vote.getVoteCount();
      reward += deltaVi.multiply(BigInteger.valueOf(userVote))
          .divide(DelegationStore.DECIMAL_OF_VI_REWARD).longValue();
    }
    return reward;
  }

  private long computeReward(long beginCycle, long endCycle, AccountCapsule accountCapsule) {
    if (beginCycle >= endCycle) {
      return 0;
    }

    long reward = 0;
    long newAlgorithmCycle = dynamicPropertiesStore.getNewRewardAlgorithmEffectiveCycle();
    List<Pair<byte[], Long>> srAddresses = accountCapsule.getVotesList().stream()
        .map(vote -> new Pair<>(vote.getVoteAddress().toByteArray(), vote.getVoteCount()))
        .collect(Collectors.toList());
    if (beginCycle < newAlgorithmCycle) {
      long oldEndCycle = min(endCycle, newAlgorithmCycle,
          dynamicPropertiesStore.disableJavaLangMath());
      reward = getOldReward(beginCycle, oldEndCycle, srAddresses);
      beginCycle = oldEndCycle;
    }
    if (beginCycle < endCycle) {
      for (Pair<byte[], Long>  vote : srAddresses) {
        byte[] srAddress = vote.getKey();
        BigInteger beginVi = delegationStore.getWitnessVi(beginCycle - 1, srAddress);
        BigInteger endVi = delegationStore.getWitnessVi(endCycle - 1, srAddress);
        BigInteger deltaVi = endVi.subtract(beginVi);
        if (deltaVi.signum() <= 0) {
          continue;
        }
        long userVote = vote.getValue();
        reward += deltaVi.multiply(BigInteger.valueOf(userVote))
            .divide(DelegationStore.DECIMAL_OF_VI_REWARD).longValue();
      }
    }
    return reward;
  }

  private long getOldReward(long begin, long end, List<Pair<byte[], Long>> votes) {
    if (dynamicPropertiesStore.allowOldRewardOpt()) {
      return rewardViCalService.getNewRewardAlgorithmReward(begin, end, votes);
    }
    long reward = 0;
    for (long cycle = begin; cycle < end; cycle++) {
      reward += computeReward(cycle, votes);
    }
    return reward;
  }
