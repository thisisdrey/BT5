### Title
`http_archive`'s `remote_file_urls`/`remote_file_integrity` map lets an attacker-controlled overlay file bypass integrity verification when a path key is omitted - (File: `tools/build_defs/repo/utils.bzl`)

### Summary
`download_remote_files` in `tools/build_defs/repo/utils.bzl` iterates over the attacker-influenceable `remote_file_urls` dict (a `path -> [urls]` mapping) and looks up a matching integrity value from `remote_file_integrity` via `.get(path, "")` [1](#0-0) . If a `path` key present in `remote_file_urls` has no corresponding entry in `remote_file_integrity`, the lookup silently defaults to the empty string, and `ctx.download()` is invoked with `integrity=""`, which disables hash verification for that specific overlay file [2](#0-1) .

### Finding Description
This is structurally the same class of bug as `MatchOneToManyOrders`: a batch of N declared sub-items (sell orders / overlay files) is processed in a loop, and the code assumes every item is individually validated (non-empty NFT transfer / non-empty integrity hash), but a single crafted item can silently omit the validation data and still be accepted and "paid out" (extracted/committed to the repo) as if it had been checked.

Concretely, `_http_archive_impl` calls `download_remote_files(ctx)` unconditionally as part of fetching every `http_archive` [3](#0-2) . The `remote_file_urls`/`remote_file_integrity` attribute pair is explicitly documented as a mechanism to overlay files (e.g. `BUILD.bazel`/`REPO.bazel`) on top of an already-fetched archive [4](#0-3) , and this same attribute pair is populated by Bzlmod itself when generating repos with registry patches/overlays — it shows up as a `STRING_LIST_DICT`/`STRING_DICT` attribute pair recorded for `bar+` `http_archive` repos in the module resolution graph [5](#0-4) , and is consumed by tooling that expects every artifact to carry a matching `sha256`/`integrity` value [6](#0-5) .

Because `download_remote_files` keys the integrity lookup by iterating `remote_file_urls.items()` and defaulting missing entries to `""` rather than failing loudly, any caller (a registry entry, a lockfile-driven module extension, or a hand-written `MODULE.bazel`/`.bzl` overlay list) that supplies a `remote_file_urls` map with more path keys than `remote_file_integrity` keys will silently fetch that specific file with no checksum enforcement — mirroring the "empty NFT sell order that still gets paid" pattern: the aggregate operation (fetching N declared overlay files) succeeds even though one member of the batch carries no enforceable commitment.

### Impact Explanation
An attacker who controls the origin server/mirror for one of the URLs in `remote_file_urls` (e.g. a stale mirror, a hijacked or lapsed domain used in one of several listed mirror URLs) can serve arbitrary content for that path with no cryptographic check, because the loop treats the missing integrity entry as "no verification requested" rather than as a fetch error. The forged content is written into the repository directory and used to build BUILD/REPO overlay files or other referenced content for the repo, which can influence what gets compiled or how the repo behaves downstream — a direct integrity-bypass of the fetch/verification invariant that `sha256`/`integrity` is supposed to enforce for every fetched artifact, analogous to the "empty sell order still gets paid" theft primitive in the original report.

### Likelihood Explanation
This requires: (1) a `remote_file_urls` map with more keys than `remote_file_integrity` (a benign mismatch is plausible in hand-authored `.bzl` module extensions or a buggy registry-generated overlay list, since nothing in `_http_archive_attrs` or `download_remote_files` requires the two dicts' key sets to match) [4](#0-3) , and (2) attacker control of the corresponding URL's origin. Given that this attribute pair is exercised by Bzlmod's own machinery for registry-provided overlays, the likelihood that some registry entries or module extensions populate these dicts asymmetrically is non-trivial, though I was not able to locate the exact Java-side code that populates `remote_file_urls`/`remote_file_integrity` from registry JSON to confirm whether the registry format itself guarantees 1:1 correspondence — this is a gap in verification given tool limitations in this pass.

### Recommendation
In `download_remote_files` (`tools/build_defs/repo/utils.bzl`), fail (`fail(...)`) if any `path` key in `ctx.attr.remote_file_urls` is missing from `ctx.attr.remote_file_integrity`, rather than defaulting the lookup to `""`. This mirrors the original report's mitigation of "ban empty/uncommitted entries in a batch" — require that every declared item in the batch carry an explicit, non-empty commitment before it is processed.

### Proof of Concept
Not executed — no sandbox/build environment access in this pass. A `BuildIntegrationTestCase`/`src/test/shell/bazel` reproduction would:
1. Define an `http_archive` with `remote_file_urls = {"BUILD.bazel": ["http://attacker/BUILD.bazel"], "REPO.bazel": ["http://good/REPO.bazel"]}` and `remote_file_integrity = {"REPO.bazel": "<valid sha>"}` (omitting the `BUILD.bazel` entry).
2. Serve mismatched/malicious content for `BUILD.bazel` from the attacker-controlled URL.
3. Assert that `bazel build` succeeds and the malicious `BUILD.bazel` content is materialized in the repo directory without any checksum-mismatch error being raised — analogous in structure to the existing `test_remote_patch_integrity_empty` test that exercises the sibling `remote_patches` empty-integrity path and confirms fetch succeeds without a checksum [7](#0-6) .
