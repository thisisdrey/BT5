### Title
`RewardsDistributor._calculateTokenDelta` credits a full deposit balance as rewards when `tokenIndex == INITIAL_INDEX` — the `> INITIAL_INDEX` boundary check fails to zero the delta - ([File: contracts/RewardsDistributor.sol](contracts/RewardsDistributor.sol))

### Summary
The FFmpeg EXR bug is an out-of-bounds write caused by miscalculating the range over which a memset-zero should be applied — an edge-case error in deciding *when* to zero. The Metronome analog is in `RewardsDistributor._calculateTokenDelta`: when an account has no stored `accountIndexOf`, the code must zero its reward delta for indices that have not grown, but the guard uses a strict `>` comparison against `INITIAL_INDEX`. When `tokenStates[token].index == INITIAL_INDEX` (i.e., rewards were just enabled and no accrual time has elapsed), the fallback is skipped and the raw delta `INITIAL_INDEX - 0 = 1e18` is applied to the account's full balance. [1](#0-0) 

### Finding Description
`_calculateTokenDelta` computes:

```solidity
_tokenIndex = _tokenState.index;
uint256 _accountIndex = accountIndexOf[token_][account_];

if (_accountIndex == 0 && _tokenIndex > INITIAL_INDEX) {
    _accountIndex = INITIAL_INDEX;
}

uint256 _deltaIndex = _tokenIndex - _accountIndex;
_tokensDelta = token_.balanceOf(account_).wadMul(_deltaIndex);
```

The intent: a new account should only earn rewards accrued *after* it started holding. When the account index is unset (`0`), it is backfilled to `INITIAL_INDEX` so `_deltaIndex` becomes `index - 1e18` — correct only when `index > 1e18`. When `index == INITIAL_INDEX`, the backfill is skipped, `_accountIndex` remains `0`, and `_deltaIndex = 1e18`, yielding `_tokensDelta = balance * wadMul(1e18) = balance` — the account's entire balance is credited as claimable rewards.

A token state with `index == INITIAL_INDEX` exists exactly during the window between `updateTokenSpeed`/`syncTokenSpeed` initializing `tokenStates[token_]` (line 298) and the first successful `_calculateTokenIndex` update where `deltaTimestamps > 0 && speed > 0`. Any `updateBeforeMintOrBurn`/`updateBeforeTransfer`/`claimRewards` call inside that window (same block) hits the flawed branch. [2](#0-1) [3](#0-2) 

Attack trace (all public, unprivileged):
1. Before rewards are enabled, attacker deposits collateral via `DepositToken.deposit` (`onlyIfDepositTokenExists`, no lock check on deposit). `updateBeforeMintOrBurn` skips because `tokenStates[token].index == 0`, leaving `accountIndexOf` at 0.
2. Attacker monitors mempool for the governor's `updateTokenSpeed(depositToken, speed > 0)` (or the keeper's routine `syncTokenSpeed` — a normal, benign operation).
3. In the same block, attacker calls `DepositToken.transfer(attacker2, 1)` or a dust `withdraw`/`deposit`. `updateBeforeTransfer` → `updateBeforeMintOrBurn`-equivalent path: `_updateTokenIndex` is a no-op (`deltaTimestamps == 0`), then `_updateTokensAccruedOf` writes `tokensAccruedOf[attacker] += balance` for both sender and recipient.
4. Attacker calls `claimRewards(attacker)`; `_transferRewardIfEnoughTokens` pays out `min(accrued, distributorBalance)` — draining the distributor's entire reward-token holdings if the attacker's deposit balance ≥ distributor balance. [4](#0-3) 

`DepositToken._transfer` and `_mint`/`_burn` invoke the distributor hooks unconditionally when `index > 0` (line 176), so any transfer-sized trigger works. No modifier stops this: `nonReentrant` doesn't help, pause doesn't block `transfer`/`claimRewards`, and `onlyIfDistributorExists`/`onlyIfTokenExists` are satisfied in production.

### Impact Explanation
Theft of unclaimed yield: the attacker is credited `tokensAccruedOf ≈ depositToken balance` without any reward time elapsing, and immediately claims the distributor's reward token balance. With a large deposit (attacker's own funds or a flash-loaned position opened before the speed-set tx), the entire reward reserve for all honest users can be extracted in one block. The invariant broken is reward accrual conservation — rewards are emitted proportional to index growth, and here a phantom delta of `1e18` is emitted at zero growth.

### Likelihood Explanation
Requires same-block execution with a routine governor `updateTokenSpeed` (or keeper `syncTokenSpeed`) transaction — achievable via public-mempool front-running on L2 deployments (base/optimism/hemi/swell are deployed). The pre-positioned deposit can be held indefinitely while waiting, costing only gas. No privileged or malicious role is needed; the flaw triggers on ordinary admin activity. The window is narrow (one timestamp), which lowers likelihood but the payoff is bounded only by distributor balance.

### Recommendation
Change the fallback condition to `>=` or restructure so unset account indices are always backfilled:

```solidity
if (_accountIndex == 0) {
    _accountIndex = _tokenIndex > INITIAL_INDEX ? INITIAL_INDEX : _tokenIndex;
}
```

Equivalently, short-circuit `_tokensDelta` to 0 when `_accountIndex == 0 && _tokenIndex <= INITIAL_INDEX`. Alternatively, eagerly write `accountIndexOf` at index-initialization time for existing holders is impractical — the `>=` boundary fix plus a regression test covering the same-block speed-enable + transfer path is the minimal correct fix.

### Proof of Concept
Foundry fork test sketch:

```solidity
// 1. Attacker deposits before rewards exist
depositToken.deposit(1_000_000e18, attacker);          // accountIndexOf == 0, index == 0

// 2. Governor enables rewards (same block as step 3)
vm.prank(governor);
rewardsDistributor.updateTokenSpeed(IERC20(address(depositToken)), 1e18); // index = 1e18, ts = now

// 3. Same-block trigger: any balance-change touch
vm.prank(attacker);
depositToken.transfer(attacker, 0); // or transfer dust to attacker2

// 4. Delta bug credited
uint256 accrued = rewardsDistributor.claimable(attacker);
assertEq(accrued, depositToken.balanceOf(attacker)); // full balance credited

// 5. Drain reward reserve
uint256 bal = rewardToken.balanceOf(address(rewardsDistributor));
vm.prank(attacker);
rewardsDistributor.claimRewards(attacker);
assertEq(rewardToken.balanceOf(attacker), Math.min(accrued, bal));
```

Key assertion demonstrating the bug-class analog: `_calculateTokenDelta` returns `_tokensDelta == balance` when `tokenStates.index == INITIAL_INDEX` and `accountIndexOf == 0`, because the `> INITIAL_INDEX` guard (line 225) fails to zero the delta at the boundary — the same "wrong condition for applying the zero" error as the EXR memset bug.
