### Title
StackerDB `write-freq` rate limit is never enforced on chunk storage, letting a valid slot signer flood writes/gossip - ([File: stackslib/src/net/stackerdb/db.rs])

### Summary
The FEI `UniswapIncentive` report describes a cost/penalty control (a quadratic sell-penalty) that only works if it is applied to an operation as a whole; splitting the operation into many small pieces defeats the intended cost model. `stacks-core` has a structurally identical control: each StackerDB slot has a configured `write_freq`, "the minimum wall-clock time between writes to the same slot" [1](#0-0) . This is meant to bound how often any given signer can write/broadcast a chunk. However, the actual chunk-acceptance path never checks it.

### Finding Description
`StackerDBTx::try_replace_chunk`, the authoritative function that commits a chunk to the local StackerDB replica, only checks chunk size, staleness, and `max_writes` — it never checks `write_freq` or the slot's last `write_time`: [2](#0-1) 

`PeerNetwork::validate_received_chunk`, used both for chunks fetched during sync and for chunks pushed unsolicited by a peer, explicitly documents that it does **not** check write frequency, deferring that responsibility to "the caller": [3](#0-2) 

But the actual "caller" enforcement never materializes as a per-write gate:
- For solicited chunks fetched by our own sync state machine, `write_freq` is only used to decide whether *we* should bother re-fetching a slot that a remote peer already reports as being written too recently — it is a scheduling optimization, not an acceptance check, and it only applies to the requester's own throttling of its sync loop: [4](#0-3) [5](#0-4) 
- For unsolicited pushed chunks, the comment in `handle_unsolicited_StackerDBPushChunk` states plainly that write frequency is "not checked for this chunk," relying instead on `ConversationP2P`'s generic bytes/sec bandwidth throttle: [6](#0-5) [7](#0-6) 

The bandwidth throttle in `validate_stackerdb_push` only measures aggregate bytes/sec of the whole StackerDB push channel, not per-slot write cadence. It caps only `max_stackerdb_push_bandwidth` bytes/sec (default-configurable), and is checked purely on message-byte accounting: [8](#0-7) 

The HTTP `POST /v2/stackerdb/:principal/:contract/chunks` endpoint (`RPCPostStackerDBChunkRequestHandler`) accepts any well-formed, appropriately-sized JSON body and hands the chunk directly to storage; it has no size/time throttling beyond `MAX_MESSAGE_LEN`: [9](#0-8) 

This exactly mirrors the FEI bug class: the protocol design assumes a rate/cost control ("write-freq", analogous to the quadratic sell penalty) applies per logical write, but a legitimate holder of a slot signing key can split their activity into many small, cheap, individually-valid writes (each with a strictly increasing `slot_version`, well within `max_writes` and under the byte-based bandwidth cap) and bypass the intended cooldown entirely — because the cooldown is never actually consulted at the point a chunk is authenticated and persisted. Just as splitting a FEI sell into many small sells defeats a control meant to scale with aggregate size, splitting StackerDB writes into many small, frequent version bumps defeats a control (`write-freq`) meant to scale with aggregate frequency.

### Impact Explanation
Any StackerDB signer who legitimately owns a slot (as declared by the contract's `stackerdb-get-config`, e.g. a member of the signer set or other application-defined principal) can write new chunk versions far more often than the contract's `write-freq` stipulates. Each accepted write causes `StackerDBChunkInv` state to update and triggers wake-ups of the sync state machine across all connected peers, and each write is a candidate for further gossip/relay via `StackerDBPushChunk`. Because this bypasses a designed rate control at the authoritative storage layer, an attacker holding one slot key can force excessive relay/storage churn network-wide, well beyond what the contract-configured `write-freq` was meant to permit — matching a "High" bounded-compute/bandwidth-amplification style DoS impact on a legitimate write path, since the enforcement gap exists in `stackslib/src/net/stackerdb/db.rs` and `stackslib/src/net/stackerdb/mod.rs`, which are both in scope.

### Likelihood Explanation
This requires only a valid slot signing key for some StackerDB contract (something legitimately held by many non-privileged participants, e.g. signers), no special network position, and no cryptographic break — the attacker just increments `slot_version` and resubmits repeatedly through the standard `POST /v2/stackerdb/.../chunks` endpoint or `StackerDBPushChunkData` gossip message, both of which are unauthenticated at the network layer (protected only by the chunk's own valid signature, which the attacker legitimately possesses for their own slot). The absence of any `write_freq`/timestamp check in `try_replace_chunk` and `validate_received_chunk` is unconditional and easily verified by code inspection, making this a high-likelihood, low-effort abuse path.

### Recommendation
Enforce `write_freq` at the point of chunk acceptance, not just at fetch-scheduling time. Concretely: track `write_time` per slot in `StackerDBs` (already stored per `SlotValidation`), and have `StackerDBTx::try_replace_chunk` (and/or `validate_received_chunk`) reject writes where `now < previous_write_time + config.write_freq`, returning a dedicated `net_error::TooFrequentSlotWrites` (which already exists as a defined error variant but is apparently unused on this path) instead of relying solely on aggregate byte-based bandwidth throttling.

### Proof of Concept
1. Configure or select an existing StackerDB contract with a non-trivial `write-freq` (e.g. 300 seconds) and `max-writes` large enough to allow many writes (e.g. 4096, as in the test fixtures).
2. As the holder of a valid slot signing key for that contract, repeatedly:
   - Construct a `StackerDBChunkData` with monotonically increasing `slot_version` and small `data`.
   - Sign it with the slot's private key (`StackerDBChunkData::sign`).
   - Submit it via `POST /v2/stackerdb/:address/:contract/chunks` (handled by `RPCPostStackerDBChunkRequestHandler`) or via an unsolicited `StackerDBPushChunkData` P2P message.
3. Observe that each submission with a strictly higher `slot_version` and a valid signature is accepted by `StackerDBTx::try_replace_chunk` / `validate_received_chunk` immediately, with no delay enforced relative to `config.write_freq`, as confirmed by the code paths cited above (`stackslib/src/net/stackerdb/db.rs:398-438`, `stackslib/src/net/stackerdb/mod.rs:641-741`) — well before the configured `write-freq` interval has elapsed, and constrained only by the unrelated, aggregate, byte-based `max_stackerdb_push_bandwidth`/HTTP content-length limits.

    /// Add or replace a chunk for a given reward cycle, if it is valid
    /// Otherwise, this errors out with Error::StaleChunk
    pub fn try_replace_chunk(
        &self,
        smart_contract: &QualifiedContractIdentifier,
        slot_desc: &SlotMetadata,
        chunk: &[u8],
    ) -> Result<(), net_error> {
        // Check per-replica chunk-size cap.
        if (chunk.len() as u64) > self.config.chunk_size {
            return Err(net_error::StackerDBChunkTooBig(chunk.len()));
        }

        let slot_validation = self
            .get_slot_validation(smart_contract, slot_desc.slot_id)?
            .ok_or(net_error::NoSuchSlot(
                smart_contract.clone(),
                slot_desc.slot_id,
            ))?;

        if !slot_desc.verify(&slot_validation.signer)? {
            return Err(net_error::BadSlotSigner(
                slot_validation.signer,
                slot_desc.slot_id,
            ));
        }
        if slot_desc.slot_version <= slot_validation.version {
            return Err(net_error::StaleChunk {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
            });
        }
        if slot_desc.slot_version > self.config.max_writes {
            return Err(net_error::TooManySlotWrites {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
                max_writes: self.config.max_writes,
            });
        }
        self.insert_chunk(smart_contract, slot_desc, chunk)
    }

    /// Validate a pushed stackerdb chunk.
    /// Update bandwidth accounting, but forward the stackerdb chunk along if we can accept it.
    /// Possibly return a reply handle for a NACK if we throttle the remote sender
    fn validate_stackerdb_push(
        &mut self,
        network: &PeerNetwork,
        preamble: &Preamble,
        relayers: Vec<RelayData>,
    ) -> Result<Option<ReplyHandleP2P>, net_error> {
        assert!(preamble.payload_len > 1); // don't count 1-byte type prefix

        let local_peer = network.get_local_peer();
        let chain_view = network.get_chain_view();

        if !self.process_relayers(local_peer, preamble, &relayers) {
            warn!(
                "Drop pushed stackerdb chunk -- invalid relayers {:?}",
                &relayers
            );
            self.stats.msgs_err += 1;
            return Err(net_error::InvalidMessage);
        }

        self.stats
            .add_stackerdb_push((preamble.payload_len as u64) - 1);

        if self.connection.options.max_stackerdb_push_bandwidth > 0
            && self.stats.get_stackerdb_push_bandwidth()
                > (self.connection.options.max_stackerdb_push_bandwidth as f64)
        {
            debug!("{:?}: Neighbor {:?} exceeded max stackerdb-push bandwidth of {} bytes/sec (currently at {})", self, &self.to_neighbor_key(), self.connection.options.max_stackerdb_push_bandwidth, self.stats.get_stackerdb_push_bandwidth());
            return self
                .reply_nack(local_peer, chain_view, preamble, NackErrorCodes::Throttled)
                .map(Some);
        }

        Ok(None)
    }
