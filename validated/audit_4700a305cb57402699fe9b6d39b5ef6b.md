## Title
Path Traversal / Arbitrary File Write via Symlinks in `CreateRepositoryFromSnapshot`'s raw `tar` extraction - (File: `internal/gitaly/service/repository/create_repository_from_snapshot.go`)

### Summary
`CreateRepositoryFromSnapshot` is a `MUTATOR` RPC that any client authorized to talk to Gitaly can invoke, supplying an arbitrary, fully attacker-controlled `http_url` (and optional `http_auth`/`resolved_address`). Gitaly fetches whatever bytes that URL returns and pipes them directly into the system `tar` binary for extraction into the newly created repository directory, with no archive content validation whatsoever. This is the same trust model that produced CVE-2019-8320: extraction is delegated to a general-purpose tar implementation that will happily create symlinks and then write/overwrite through them, allowing the archive itself to escape the intended extraction root.

### Finding Description
The RPC handler builds an HTTP request to `in.GetHttpUrl()`, streams the response body straight into `tar -C path -xvf -`: [1](#0-0) 

and then invokes it from the RPC entrypoint: [2](#0-1) 

The code even documents that this is dangerous by design:
> "NOTE: The received archive is trusted *a lot*. Before pointing this RPC at endpoints not under our control, it should undergo a lot of hardening." [3](#0-2) 

Because extraction is delegated to the system `tar` command with no `--no-same-owner`/anchoring/symlink restrictions and no post-extraction validation of the resulting file tree, a malicious archive can:
1. Create a symlink entry (e.g. `hooks -> /etc/cron.d` or `hooks -> ../../../other-repo`).
2. Follow it with regular-file entries whose names are relative to that symlink (e.g. `hooks/evil`), which `tar` will write through the symlink to a location entirely outside the intended repository directory — exactly the "create symlink, then write/delete through it" primitive described in the HackerOne report (CVE-2019-8320), just realized through the OS `tar` binary rather than RubyGems' `mkdir_p_safe`/`rm_rf` sequence.

This is in stark contrast to the sibling code path `extractTarToDirectory` used for `ReplicateRepository`'s snapshot extraction, which explicitly re-implements tar extraction in Go and validates that every regular/dir target and every symlink/hardlink target resolves within the destination boundary before writing: [4](#0-3) 

No equivalent boundary check exists for the `CreateRepositoryFromSnapshot` path, since extraction is fully delegated to the untrusted-input-following external `tar` process.

### Impact Explanation
An ordinary authenticated user who can call `CreateRepositoryFromSnapshot` (and control or influence `http_url`, e.g. by hosting the tar on infrastructure they control, or by causing Gitaly to fetch from a URL under their influence) can craft a tar archive that writes or overwrites arbitrary files on the Gitaly node's filesystem, outside the intended repository path — including into other repositories under the same storage root, or system paths writable by the Gitaly process user. This can lead to cross-repository object/content injection, repository corruption of unrelated repos, or arbitrary file write within the Gitaly process's file permissions.

### Likelihood Explanation
The RPC is directly exposed (`MUTATOR`) and takes `http_url`/`http_auth`/`resolved_address` directly from the caller-supplied request; there is no allowlisting of the URL destination beyond the DNS-rebinding mitigation via `resolved_address`. Any caller able to issue gRPC calls to Gitaly (e.g., via GitLab's internal API on behalf of project import/fork/geo-replication flows) that reaches this RPC and can point it at attacker-influenced content can trigger the issue. The in-code comment acknowledges the trust assumption is fragile.

### Recommendation
- Replace the raw `tar -xvf -` shell-out in `untar` with a hardened Go-based extractor (mirroring `extractTarToDirectory` in `replicate.go`) that validates every entry's resolved path — including symlink/hardlink targets — stays within the destination directory before any filesystem operation, and rejects absolute or path-escaping entries.
- Alternatively, invoke system `tar` with strict, symlink-safe extraction flags (e.g., refusing to follow/create symlinks that point outside the extraction root) and validate the resulting tree afterward.
- Restrict/validate `http_url` destinations where feasible, independent of the extraction hardening.

### Proof of Concept
1. Host an HTTP endpoint serving a tar archive containing:
   - `hooks` as a symlink entry pointing to `../../other-repo-relative-path` (or an absolute path outside the storage root, subject to whatever the underlying `tar` binary permits).
   - A subsequent regular file entry `hooks/malicious-file` with attacker content.
2. Call `CreateRepositoryFromSnapshot` with `http_url` pointing at that endpoint and a `repository` target under the attacker's control.
3. Gitaly's `untar` pipes the archive into `tar -C <repoPath> -xvf -`; the system tar creates the symlink then writes `malicious-file` through it, landing outside `<repoPath>` at the symlink's target location — demonstrating write access outside the intended repository boundary.

func (s *server) untar(ctx context.Context, path string, in *gitalypb.CreateRepositoryFromSnapshotRequest) error {
	req, err := http.NewRequestWithContext(ctx, "GET", in.GetHttpUrl(), nil)
	if err != nil {
		return structerr.NewInvalidArgument("Bad HTTP URL: %w", err)
	}

	client := httpClient
	if resolvedAddress := in.GetResolvedAddress(); resolvedAddress != "" {
		client, err = newResolvedHTTPClient(in.GetHttpUrl(), resolvedAddress)
		if err != nil {
			return structerr.NewInvalidArgument("creating resolved HTTP client: %w", err)
		}
	}

	if in.GetHttpAuth() != "" {
		req.Header.Set("Authorization", in.GetHttpAuth())
	}

	rsp, err := client.Do(req)
	if err != nil {
		return structerr.NewInternal("HTTP request failed: %w", err)
	}
	defer rsp.Body.Close()

	if rsp.StatusCode < http.StatusOK || rsp.StatusCode >= http.StatusMultipleChoices {
		return structerr.NewInternal("HTTP server: %s", rsp.Status)
	}

	cmd, err := command.New(ctx, s.logger, []string{"tar", "-C", path, "-xvf", "-"}, command.WithStdin(rsp.Body))
	if err != nil {
		return err
	}

	return cmd.Wait()
}

func (s *server) CreateRepositoryFromSnapshot(ctx context.Context, in *gitalypb.CreateRepositoryFromSnapshotRequest) (*gitalypb.CreateRepositoryFromSnapshotResponse, error) {
	repository := in.GetRepository()
	if err := s.locator.ValidateRepository(ctx, repository, storage.WithSkipRepositoryExistenceCheck()); err != nil {
		return nil, structerr.NewInvalidArgument("%w", err)
	}

	if err := repoutil.Create(ctx, s.logger, s.locator, s.gitCmdFactory, s.catfileCache, s.txManager, s.repositoryCounter, repository, func(repo *gitalypb.Repository) error {
		path, err := s.locator.GetRepoPath(ctx, repo, storage.WithRepositoryVerificationSkipped())
		if err != nil {
			return structerr.NewInternal("getting repo path: %w", err)
		}

		// The archive contains a partial git repository, missing a config file and
		// other important items. Initializing a new bare one and extracting the
		// archive on top of it ensures the created git repository has everything
		// it needs (especially, the config file and hooks directory).
		//
		// NOTE: The received archive is trusted *a lot*. Before pointing this RPC
		// at endpoints not under our control, it should undergo a lot of hardening.
		if err := s.untar(ctx, path, in); err != nil {
			return structerr.NewInternal("extracting snapshot: %w", err)
		}

		return nil
	}); err != nil {
		return nil, structerr.NewInternal("creating repository: %w", err)
	}
