Audit Report

## Title
Reward-per-token computation in `pallet-asset-rewards` can permanently round to zero, silently withholding staker rewards when stake or reward-rate has low precision - (File: `substrate/frame/asset-rewards/src/lib.rs`)

## Summary
`Pallet::reward_per_token` computes `reward_rate_per_block * blocks_elapsed * PRECISION_SCALING_FACTOR / total_tokens_staked` using a fixed scaling constant of only `4096`, which is far too small relative to realistic on-chain balance precision. [1](#0-0)  Whenever the numerator is smaller than `total_tokens_staked`, integer division truncates the increment to `0`, and `update_pool_rewards` unconditionally advances `last_update_block` to the current block regardless of whether the reward increment was truncated, permanently discarding that window's reward accrual with no remainder-carry mechanism. [2](#0-1) 

## Finding Description
`reward_per_token` is called from `update_pool_and_staker_rewards`, which is invoked on every unprivileged staker action (`stake`, `unstake`, `harvest_rewards`). It computes:

```rust
pool_info.reward_rate_per_block
    .ensure_mul(rewardable_blocks_elapsed.into())?
    .ensure_mul(PRECISION_SCALING_FACTOR.into())?
    .ensure_div(pool_info.total_tokens_staked)?
``` [3](#0-2) 

`PRECISION_SCALING_FACTOR` is a fixed `u16` constant equal to `4096`, not derived from asset decimals or otherwise configurable. [1](#0-0)  The result is immediately committed via `update_pool_rewards`, which sets `new_pool_info.last_update_block = T::BlockNumberProvider::current_block_number()` and `new_pool_info.reward_per_token_stored = reward_per_token` unconditionally — there is no check for whether the computed increment was zero, and no accumulator retains the truncated remainder for the next call. [4](#0-3)  Because `total_tokens_staked` changes via the public, unprivileged `stake`/`unstake` extrinsics, and because every staker action resets `last_update_block` (shrinking the `rewardable_blocks_elapsed` window used in the next computation), the pallet can be kept in a regime where `reward_rate_per_block * blocks_elapsed * 4096 < total_tokens_staked` indefinitely, causing `reward_per_token_stored` to never increase and `derive_rewards` to always return the previously accrued (frozen) reward amount. [5](#0-4) [6](#0-5) 

## Impact Explanation
This is a genuine arithmetic-precision bug in unprivileged, publicly reachable pallet logic that can cause real, non-zero intended reward accrual to be silently and permanently lost, leaving reward-asset funds stranded in the pool account (`Pools::<T>::get(pool_id).account`) with no code path to recover the truncated portion. This matches the "runtime bugs that compromise intended behavior" / "permanent user-fund lock" impact class, since stakers are entitled to real yield that is never distributed and cannot be reclaimed through any exposed mechanism.

## Likelihood Explanation
The vulnerable path is exercised by every ordinary `stake`, `unstake`, and `harvest_rewards` call, all unprivileged public extrinsics. `total_tokens_staked` is directly attacker/user-influenceable via public staking, and repeated interactions reset `last_update_block`, keeping the elapsed-block window small and the truncation condition persistent. No privileged action, governance misuse, or off-chain compromise is required — only a pool with a reward-rate-to-stake ratio common in realistic deployments (e.g., large staked amounts relative to per-block reward rate), which is a foreseeable, not contrived, configuration.

## Recommendation
Increase `PRECISION_SCALING_FACTOR` to a fixed-point base consistent with typical Substrate balance precision (e.g., `1e18`), and/or track an explicit remainder in `PoolInfo` (analogous to `rational_mul_correction` in `substrate/primitives/arithmetic/src/per_things.rs`) that carries forward the truncated fractional reward from `reward_rate_per_block * blocks_elapsed * PRECISION_SCALING_FACTOR % total_tokens_staked` into the next `update_pool_rewards` call, ensuring conservation of reward tokens regardless of pool size or asset decimals.

## Proof of Concept
1. Create a pool via `create_pool` with a 6-decimal reward asset and `reward_rate_per_block = 10`.
2. Have unprivileged accounts call `stake` to bring `total_tokens_staked` to `1_000_000_000`.
3. Advance 1 block and call `harvest_rewards`, triggering `update_pool_and_staker_rewards` → `reward_per_token`.
4. Observe `10 * 1 * 4096 = 40_960`, and `40_960 / 1_000_000_000 = 0` under integer division; `reward_per_token_stored` stays unchanged while `last_update_block` advances to the current block. [7](#0-6) 
5. Repeat step 3 every block via routine staker activity: `reward_per_token_stored` never increases, and `derive_rewards` returns `0` additional reward indefinitely, even though the pool's reward asset continues to sit unused in the pool account. [8](#0-7)

		pub fn update_pool_rewards(
			pool_info: &PoolInfoFor<T>,
			reward_per_token: T::Balance,
		) -> Result<PoolInfoFor<T>, DispatchError> {
			let mut new_pool_info = pool_info.clone();
			new_pool_info.last_update_block = T::BlockNumberProvider::current_block_number();
			new_pool_info.reward_per_token_stored = reward_per_token;

			Ok(new_pool_info)
		}

		/// Derives the current reward per token for this pool.
		pub(super) fn reward_per_token(
			pool_info: &PoolInfoFor<T>,
		) -> Result<T::Balance, DispatchError> {
			if pool_info.total_tokens_staked.is_zero() {
				return Ok(pool_info.reward_per_token_stored);
			}

			let rewardable_blocks_elapsed: u32 =
				match Self::last_block_reward_applicable(pool_info.expiry_block)
					.ensure_sub(pool_info.last_update_block)?
					.try_into()
				{
					Ok(b) => b,
					Err(_) => return Err(Error::<T>::BlockNumberConversionError.into()),
				};

			Ok(pool_info.reward_per_token_stored.ensure_add(
				pool_info
					.reward_rate_per_block
					.ensure_mul(rewardable_blocks_elapsed.into())?
					.ensure_mul(PRECISION_SCALING_FACTOR.into())?
					.ensure_div(pool_info.total_tokens_staked)?,
			)?)
		}

			reward_per_token: &T::Balance,
		) -> Result<T::Balance, DispatchError> {
			Ok(staker_info

				.ensure_mul(reward_per_token.ensure_sub(staker_info.reward_per_token_paid)?)?
				.ensure_div(PRECISION_SCALING_FACTOR.into())?
				.ensure_add(staker_info.rewards)?)
		}
