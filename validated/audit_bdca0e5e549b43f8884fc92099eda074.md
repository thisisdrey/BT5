### Title
Exchange (bancor-style TRC10 AMM) pool math ignores per-asset `precision`, letting mismatched-decimal token pairs corrupt swap/inject/withdraw pricing - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeCreateActuator.java`)

### Summary
`ExchangeCreateActuator`, `ExchangeInjectActuator`, `ExchangeWithdrawActuator` and `ExchangeTransactionActuator` build and operate a bancor-style constant-relay AMM pool (`ExchangeCapsule`/`ExchangeProcessor`/`SafeExchangeProcessor`) over pairs of TRC10 tokens. The pool math treats `firstTokenBalance`/`secondTokenBalance` as raw, directly-comparable `long` magnitudes and never consults each token's `AssetIssueContract.precision` field. Exactly like the ClearingHouse report — which mixed AMM position/margin values implicitly assumed to be 6-decimals scaled with VAMMs that could return arbitrary decimals — java-tron's Exchange lets an owner pair two TRC10 assets with different `precision` (0–6, per `AssetIssueActuator` validation) into one pool, after which the AMM's constant-product-like pricing curve treats 1 unit of a 0-decimal token as equal in "scale" to 1 unit of a 6-decimal token.

### Finding Description
`ExchangeCreateActuator.doValidate()` validates token existence, balances, and that the two token IDs differ, but never checks that `firstTokenID` and `secondTokenID` have equal `precision`: [1](#0-0) 

The `precision` field is only validated locally (0–6) inside `AssetIssueActuator`, unrelated to Exchange pairing, and note that the actual V2 asset store (used by `ExchangeV2Store`) resets precision to `0` on issuance for pre-SameTokenName assets and only honors the requested precision for post-fork asset issuance, showing the field is inconsistently applied even for a single token, let alone enforced across a pool pair: [2](#0-1) 

The pool balances set at creation, and later mutated by inject/withdraw/swap, are plain `long` quantities with no decimal normalization: [3](#0-2) 

The core AMM pricing function `ExchangeCapsule.transaction()` feeds these raw balances directly into `ExchangeProcessor`/`SafeExchangeProcessor.exchange()`, which computes `issuedSupply`/`exchangeBalance` purely as ratios of the two raw balances — there is no scaling factor derived from either token's declared precision: [4](#0-3) [5](#0-4) 

This mirrors the ClearingHouse root cause precisely: linear (decimals-preserving) balance bookkeeping is combined with a pricing formula that implicitly assumes both sides share one common unit scale, without any per-asset decimals rescaling.

### Impact Explanation
If a pool is created (or exists) pairing a 0-decimal TRC10 token with a 6-decimal TRC10 token (or TRX, which is fixed at 6 decimals), the bancor curve will price 1 raw unit of each token as equivalent economic weight, when in reality 1 raw unit of the 0-decimal token is worth 1,000,000x more (or less) in real terms than 1 raw unit of the 6-decimal token. Any party aware of the mismatch can drain the mispriced side of the pool via `ExchangeTransactionActuator` swaps, or extract disproportionate value via `ExchangeInjectActuator`/`ExchangeWithdrawActuator`, causing theft of pool funds from other liquidity participants. This is a fund-theft/mispricing issue reachable purely by a normal signed transaction from any account (issue two TRC10 assets with different precision, create an exchange pairing them, then swap).

### Likelihood Explanation
Any unprivileged account can issue TRC10 tokens with any allowed precision (0–6) via `AssetIssueActuator`, and any account can create an `Exchange` pool pairing any two token IDs via `ExchangeCreateActuator` — there is no on-chain restriction requiring equal precision between the two assets in a pool. Because token issuance and pool creation are both permissionless single-transaction operations, an attacker (or an unaware token issuer) can trivially create such a mismatched pool, matching the "Medium" severity judged for the analogous Hubble finding (requires a specific/unusual configuration to be exploitable, but is fully reachable without special privilege).

### Recommendation
When creating (`ExchangeCreateActuator`) or injecting into (`ExchangeInjectActuator`) an Exchange pool, fetch the `precision` of both `firstTokenID` and `secondTokenID` from the asset store and either (a) reject pairs with differing precision, or (b) explicitly normalize all pool balances and swap math in `ExchangeCapsule`/`ExchangeProcessor`/`SafeExchangeProcessor` to a common internal decimal scale before applying the bancor formula, converting back to native units on output.

### Proof of Concept
1. Issue TRC10 token A with `precision = 0` via `AssetIssueActuator` (`setPrecision(0)`), and TRC10 token B with `precision = 6` via `AssetIssueActuator` (`setPrecision(6)`), both permitted by the precision validation at `AssetIssueActuator.java:176-181`.
2. Call `ExchangeCreateActuator` with `firstTokenId = A`, `secondTokenId = B`, `firstTokenBalance = 1_000_000`, `secondTokenBalance = 1_000_000` — this succeeds since `doValidate()` (lines 183-203) never compares precision.
3. Because `ExchangeCapsule.transaction()` and `ExchangeProcessor.exchange()` treat both balances as equal-scale raw longs (`ExchangeCapsule.java:124-158`, `ExchangeProcessor.java:17-45`), swapping token A (whose raw unit represents a much larger real value than token B's raw unit) via `ExchangeTransactionActuator` yields a distorted exchange rate that does not reflect the tokens' true relative value, allowing an attacker to extract token B (or A) from the pool at a favorable, mispriced rate.

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
