### Title
Missing zero-address (burn) check in address validation allows permanent loss of TRX/TRC10 funds - (File: common/src/main/java/org/tron/common/utils/DecodeUtil.java)

### Summary
`DecodeUtil.addressValid()`, which every fund-moving actuator (`TransferActuator`, `TransferAssetActuator`, `DelegateResourceActuator`, `WithdrawBalanceActuator`, etc.) relies on to validate `toAddress`/`receiverAddress` fields, only checks the byte-array length and the network prefix byte. It never rejects an address whose remaining 20 payload bytes are all zero (i.e. the "null"/zero address `0x41` + 20×`0x00`). This is the java-tron analog of the reported FarmingPool constructor issue: a security-critical address parameter is accepted from an unprivileged, single-signed transaction without a non-zero check, letting funds be sent to an address nobody controls a private key for.

### Finding Description
`DecodeUtil.addressValid()` performs exactly three checks: not empty, correct length (21 bytes), and correct prefix byte: [1](#0-0) 

It never verifies that the payload (bytes 1–20) is non-zero. Every actuator that moves value trusts this function as the sole address-format guard, e.g.: [2](#0-1) 
and [3](#0-2) 

Because `toAddress = 0x41 0000000000000000000000000000000000000000` passes `addressValid`, `TransferActuator.execute()` will happily auto-create an `AccountCapsule` for it and move the sender's TRX there: [4](#0-3) 

The same applies to `TransferAssetActuator.execute()` for TRC10 tokens: [5](#0-4) 

This zero-payload address is distinct from the protocol's designated black-hole/burn address used for fee burning (`accountStore.getBlackhole()`), which is a deliberate, tracked system sink. The all-zero address is not that sink — it is simply an address with no known private key, so any TRX or TRC10 balance sent there is permanently unrecoverable, exactly the "send funds to a zero address, which would be lost" scenario described in the original report.

### Impact Explanation
Any unprivileged transaction broadcaster can construct a `TransferContract` or `TransferAssetContract` (or use `DelegateResourceActuator`, etc., where the same `addressValid` gap applies to `receiverAddress`) with a zero-payload destination address. Funds transferred this way become permanently and irrecoverably locked, meeting the "permanent freezing of funds" impact bar. Because these are core, frequently-used, unprivileged transaction paths (simple TRX/TRC10 transfers), the blast radius is any account that mistakenly or maliciously targets a zero-payload address — including potential loss from client-side bugs that fail to properly randomize/derive a real address and instead pass zero bytes.

### Likelihood Explanation
High reachability: `TransferContract` and `TransferAssetContract` are the most basic, unprivileged, single-signed transaction types in java-tron, reachable directly via any wallet/gRPC/HTTP client. No special permission, contract deployment, or SR/witness status is required — only a normal signed transaction. The only barrier is that a client must intentionally or accidentally construct a zero-payload address, which is trivial to do.

### Recommendation
Add an explicit check in `DecodeUtil.addressValid()` (or in each actuator's `validate()`, alongside the existing `DecodeUtil.addressValid()` calls) that rejects addresses whose 20-byte payload is all zero, in addition to the existing length/prefix checks. This mirrors the recommended fix for the original FarmingPool report: validate that address parameters are non-zero before they are persisted or used to move value.

### Proof of Concept
1. Construct a `TransferContract` with `ownerAddress` = a funded, valid account and `toAddress` = `ByteArray.fromHexString("410000000000000000000000000000000000000000")` (prefix `0x41` + 20 zero bytes).
2. Submit via any client (broadcast transaction / gRPC / HTTP API) — `TransferActuator.validate()` passes because `DecodeUtil.addressValid(toAddress)` only checks length and prefix, per `common/src/main/java/org/tron/common/utils/DecodeUtil.java:15-33`.
3. `TransferActuator.execute()` creates a fresh `AccountCapsule` for the zero-payload address and credits it with the transferred amount, per `actuator/src/main/java/org/tron/core/actuator/TransferActuator.java:49-66`.
4. The transferred TRX is now held by an account with no corresponding private key, permanently unrecoverable. The identical PoC applies to `TransferAssetActuator` for TRC10 token transfers.

  public static boolean addressValid(byte[] address) {
    if (ArrayUtils.isEmpty(address)) {
      logger.warn("Warning: Address is empty !!");
      return false;
    }
    if (address.length != ADDRESS_SIZE / 2) {
      logger.warn(
          "Warning: Address length need " + ADDRESS_SIZE + " but " + address.length
              + " !!");
      return false;
    }

    if (address[0] != addressPreFixByte) {
      logger.warn("Warning: Address need prefix with " + addressPreFixByte + " but "
          + address[0] + " !!");
      return false;
    }
    return true;
  }
