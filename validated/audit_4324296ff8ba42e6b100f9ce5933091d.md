### Title
Unchecked multiplication `estimated_len * MINIMUM_TX_FEE_RATE_PER_BYTE` with caller-controlled `estimated_len` causes integer overflow/panic or fee-estimate desync - (File: stackslib/src/net/api/postfeerate.rs)

### Summary
`RPCPostFeeRateRequestHandler::try_parse_request` only bounds the raw HTTP `content_len` against `MAX_PAYLOAD_LEN`; it never validates the JSON field `estimated_len` supplied by the client. That value flows unchecked into `estimate_tx_fee_from_cost_and_length`, where `estimated_len * MINIMUM_TX_FEE_RATE_PER_BYTE` is computed with a plain `*` operator, letting a remote unauthenticated caller pick `estimated_len` completely decoupled from the actual `payload_data.len()`.

### Finding Description
In `try_parse_request` (stackslib/src/net/api/postfeerate.rs lines 145-186), the request body is deserialized into `FeeRateEstimateRequestBody { estimated_len: Option<u64>, transaction_payload: String }`. The handler computes: [1](#0-0) 
`estimated_len = max(body.estimated_len.unwrap_or(0), payload_data.len() as u64)`. This `max()` only enforces a *lower* bound of the real payload length — it does not cap the *upper* bound at all. `body.estimated_len` is attacker-supplied via JSON and can legally be any `u64`, including `u64::MAX`, while `payload_data` (the actual `TransactionPayload` bytes) can be a handful of bytes. The only size gate applied earlier, `content_len < MAX_PAYLOAD_LEN`, bounds the *HTTP body* size (the JSON text), not the numeric value of the `estimated_len` field embedded in that JSON — a small JSON body can trivially contain the literal `18446744073709551615`.

That unchecked value is stored in `self.estimated_len` and later passed into `estimate_tx_fee_from_cost_and_length`: [2](#0-1) 
`let minimum_fee = estimated_len * MINIMUM_TX_FEE_RATE_PER_BYTE;` uses the default `*` operator with no `checked_mul`/`saturating_mul`. With `estimated_len = u64::MAX` and `MINIMUM_TX_FEE_RATE_PER_BYTE` being a non-zero constant multiplier, this multiplication overflows `u64`.

No existing guard catches this: `content_len < MAX_PAYLOAD_LEN` only limits the HTTP body byte size, not the numeric field value; there is no explicit range check on `body.estimated_len`; and `estimate_tx_fee_from_cost_and_length` performs no bounds check before the multiply.

### Impact Explanation
The workspace `Cargo.toml` does not set `overflow-checks` explicitly for `[profile.release]` [3](#0-2) , so release builds use Rust's default `overflow-checks = false`, meaning the multiply silently wraps rather than panics in production binaries. This means:
- In debug/test builds (`overflow-checks` defaults to `true` for `[profile.dev]`, and this repo's dev profile does not override it) [4](#0-3) , the multiplication panics, crashing the thread handling the request — a remote, unauthenticated, single-request DoS against any node run in a debug configuration.
- In release builds, the multiplication silently wraps, producing a `minimum_fee` value with no relation to `estimated_len`'s intended magnitude, meaning the returned `RPCFeeEstimateResponse.estimations[].fee` values are decoupled from the actual transaction size — a caller-steerable, misleading fee-rate estimate served to any wallet/bridge/client relying on `/v2/fees/transaction`.

Given release builds do not panic (wrapping is the default), the realistic impact is the High-severity case: a caller-controlled, non-length-derived fee estimate served from a read endpoint, not a remote crash. The debug-build panic is a real code defect but does not affect production nodes built in the standard release profile.

### Likelihood Explanation
`/v2/fees/transaction` is an unauthenticated public RPC read endpoint reachable by any remote peer able to reach the node's RPC port — no secret, session, or privileged role is required. Constructing the malicious request costs nothing: a single POST with a tiny valid hex-encoded `transaction_payload` and `"estimated_len": 18446744073709551615` in the JSON body. This is trivially repeatable on every request.

### Recommendation
Clamp or reject `body.estimated_len` in `try_parse_request` to a sane bound (e.g., `MAX_PAYLOAD_LEN` or the maximum permitted transaction size) before storing it, and/or use `checked_mul`/`saturating_mul` in `estimate_tx_fee_from_cost_and_length` when computing `minimum_fee`, returning an `HttpBadRequest` if `estimated_len` exceeds a reasonable protocol maximum.

### Proof of Concept
Add a test under `stackslib/src/net/api/tests/postfeerate.rs` (or extend it) that:
1. Constructs an `HttpRequestPreamble` and JSON body: `{"estimated_len": 18446744073709551615, "transaction_payload": "0x<small valid TransactionPayload hex>"}`.
2. Calls `RPCPostFeeRateRequestHandler::try_parse_request` — expect it currently succeeds, setting `self.estimated_len = Some(u64::MAX)`.
3. Calls `RPCPostFeeRateRequestHandler::estimate_tx_fee_from_cost_and_length` with `estimated_len = u64::MAX` — in a `cargo test` (dev/debug) build, assert this panics with "attempt to multiply with overflow" at `postfeerate.rs:112`; in a release build, assert `minimum_fee` wraps to a value unrelated to `payload_data.len() * MINIMUM_TX_FEE_RATE_PER_BYTE`, demonstrating the fee decoupling.
