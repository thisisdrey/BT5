### Title
Missing static-call value-transfer check in the `CALLCODE` opcode handler allows a `view`/`STATICCALL`-protected TVM contract to bypass the read-only invariant enforced on its sibling opcodes - (`File: actuator/src/main/java/org/tron/core/vm/OperationActions.java`)

### Summary
`CALL` and `CALLTOKEN` both reject a value-carrying call while executing inside a static context by throwing `Program.StaticCallModificationException`. `CALLCODE`, which pops the exact same `value` operand from the stack and feeds it into the same `exeCall`/`callToAddress` path, omits this check entirely, letting attacker/contract-controlled bytecode issue a nonzero-value `CALLCODE` from within a `STATICCALL` sandbox.

### Finding Description
In `OperationActions.java`, `callAction` and `callTokenAction` both guard against value transfer while `isStaticCall()` is true: [1](#0-0) 

`callCodeAction` pops the identical `value` operand and calls the same `exeCall` helper, but never checks `program.isStaticCall()`: [2](#0-1) 

`delegateCallAction`/`staticCallAction` are exempt from the check by construction (their `value` is hard-coded to `DataWord.ZERO`), so the omission in `callCodeAction` is the outlier among the four "call-family" opcodes that share `exeCall`.

Downstream, `Program.callToAddress` propagates the endowment as the callee's `CALLVALUE` regardless of the static-call state of the *current* frame: [3](#0-2) 

Specifically, for `CALLCODE` the `contextAddress` is forced to equal `senderAddress` (same contract), so the endowment bookkeeping branch that mutates balances is skipped only because `senderAddress != contextAddress` evaluates false — but `callValue` (the fabricated nonzero endowment) is still handed to the freshly created `Program` as its `CALLVALUE`, and the invoked code executes with `msg.value != 0` even though the outer frame is a supposedly read-only `STATICCALL` context. The invariant that "no state-changing, value-carrying call can originate from a static context" — which `CALL`/`CALLTOKEN` uphold — is silently violated for `CALLCODE`.

### Impact Explanation
`STATICCALL` is the TVM's only guaranteed read-only execution mode; downstream contracts (multisig/oracle/proxy patterns, DeFi contracts gating logic on "is this call read-only") rely on the assumption that no value-carrying operation can be triggered underneath a `STATICCALL`. A malicious or compromised contract that is invoked via `STATICCALL` can issue `CALLCODE` with a nonzero value to itself (or to a helper library executing in its own storage context) and have the callee observe a nonzero `CALLVALUE`, even though no actual TRX moves and no signed transaction should have permitted a state-changing/value-bearing operation at that call site. Contracts that key business logic (e.g., "record deposit" accounting, fee logic, replay/reentrancy guards) off `msg.value` rather than off actual balance deltas can be tricked into crediting phantom deposits or executing value-gated branches inside what should be an inert, read-only call — corrupting internal accounting state (unbacked ledger balances) invoked purely through a contract call reachable by any transaction sender via `TriggerSmartContract`.

### Likelihood Explanation
This is trivially reachable: any account can deploy or call a contract that issues `STATICCALL` into attacker-controlled bytecode, and the attacker bytecode simply needs to execute `CALLCODE` with a nonzero value operand — no special permission, precompile access, or committee proposal gating is required. The check that's missing is a single, cheap, always-available comparison (`program.isStaticCall() && !value.isZero()`), identical to the one already present two opcodes above it.

### Recommendation
Add the same static-call guard used by `callAction`/`callTokenAction` to `callCodeAction` in `actuator/src/main/java/org/tron/core/vm/OperationActions.java`:
```java
public static void callCodeAction(Program program) {
  program.stackPop();
  DataWord codeAddress = program.stackPop();
  DataWord value = program.stackPop();

  if (program.isStaticCall() && !value.isZero()) {
    throw new Program.StaticCallModificationException();
  }
  DataWord adjustedCallEnergy = program.getAdjustedCallEnergy();
  if (!value.isZero()) {
    adjustedCallEnergy.add(new DataWord(EnergyCost.getStipendCallCost()));
  }
  exeCall(program, adjustedCallEnergy, codeAddress, value, DataWord.ZERO(), false);
}
```
This should be gated behind a hard fork / feature flag (similar to `VMConfig.allowTvmVote()` used elsewhere for retroactive opcode-behavior changes) to avoid breaking consensus on already-deployed contract bytecode.

### Proof of Concept
1. Deploy contract `V` (the "victim"/oracle-like contract) that a third party invokes via `STATICCALL` (e.g., through a `view`-declared Solidity function compiled to `STATICCALL`).
2. Inside `V`, include bytecode that executes:
   ```
   PUSH <outSize> PUSH <outOffs> PUSH <inSize> PUSH <inOffs> PUSH <value != 0> PUSH <codeAddress> PUSH <gas> CALLCODE
   ```
   targeting a helper contract `H` whose logic checks `CALLVALUE` to decide whether to mutate `H`'s own storage state (which is `V`'s storage, since `CALLCODE` runs in the caller's context) or emit a "deposit received" style log/state update.
3. Because `callCodeAction` never calls `program.isStaticCall()`, execution proceeds; `Program.callToAddress` sets `callValue = msg.getEndowment()` (nonzero) for the newly created `Program` regardless of `isStaticCall()` on the current frame, so `H`'s `CALLVALUE` opcode returns the nonzero value.
4. Compare against `CALL`/`CALLTOKEN` with the same nonzero value under `STATICCALL`: those revert immediately with `Program.StaticCallModificationException` (per `OperationActions.callAction`/`callTokenAction`), proving the differential — only `CALLCODE` allows this "value" leak-through under a read-only call.
