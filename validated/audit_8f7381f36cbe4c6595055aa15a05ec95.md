### Title
Uncaught array-index exception in `ValidateMultiSign` precompile via unvalidated calldata length - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
`PrecompiledContracts.ValidateMultiSign.execute()` parses raw TVM calldata into a `DataWord[]` and immediately indexes `words[0]`, `words[1]`, `words[2]`, `words[3]` without first checking that the array is long enough, unless TIP-854 (`VMConfig.allowTvmOsaka()`) has been activated. This mirrors the reported TensorFlow bug class: an op consumes attacker-controlled, insufficiently-validated shape/length data and dereferences into it, causing an unhandled crash instead of a graceful validation error.

### Finding Description
`ValidateMultiSign.execute(byte[] rawData)` only performs the ABI-shape guard `isValidAbiEncoding(rawData, ABI_HEADER_WORDS, ABI_ITEM_WORDS)` when `VMConfig.allowTvmOsaka()` is true: [1](#0-0) 

When that guard is not applied, `DataWord.parseArray(rawData)` produces a `DataWord[]` whose length is simply `rawData.length / WORD_SIZE`, and the method unconditionally accesses `words[0]`, `words[1]`, `words[2]`, and later `words[3]`: [2](#0-1) 

If a contract calls this precompile address with fewer than 4 words of calldata (e.g. an empty call or a short byte string), this throws an uncaught `ArrayIndexOutOfBoundsException`. Unlike `BatchValidateSign`, which wraps its entire body in `try { return doExecute(data); } catch (Throwable t) { ... return safe default ... }`, `ValidateMultiSign.execute()` has no such wrapper at all: [3](#0-2) 

This exact behavioral gap is documented and reproduced by the project's own regression test, which explicitly states that pre-activation malformed calldata is **not** contained: [4](#0-3) 

The companion test for outer-frame containment further confirms that TIP-854 was introduced specifically to prevent a malformed CALL to `validateMultiSign`/`batchValidateSign` from propagating an exception into the outer VM frame — implying that before its activation this containment does not exist: [5](#0-4) 

### Impact Explanation
`ValidateMultiSign` is a TVM precompiled contract, reachable by any address via a plain `CALL`/`STATICCALL` from a smart contract, with completely attacker-controlled calldata and no special privileges required. An uncaught `RuntimeException` thrown out of `PrecompiledContract.execute()` during transaction/block execution is a violation of the fundamental TVM invariant that all execution paths (however malformed the input) must resolve to a revert/false result, not an unhandled Java exception. Depending on how far up the call stack this exception is allowed to propagate before being caught (transaction execution, `RuntimeImpl.execute`, or block application in `Manager`), this can manifest as a failed/aborted transaction at best, or an uncontained exception during block application at worst — a node crash / processing halt for that block, which is explicitly an in-scope, high-impact class per the assessment rules.

### Likelihood Explanation
Likelihood is high: triggering the bug requires only deploying a trivial contract that performs a `CALL` to the `ValidateMultiSign` precompile address with a calldata payload shorter than 4 EVM words (128 bytes) and then calling that contract — no special permissions, signatures, or state setup are needed. The condition is gated solely on whether TIP-854 (`allowTvmOsaka`) is active on the target network; on any network where that upgrade has not yet been activated, the vulnerable code path is live by default, and the project's own tests document this as the current, un-mitigated pre-activation behavior.

### Recommendation
Apply the same `isValidAbiEncoding` header/length check unconditionally (not gated behind `allowTvmOsaka()`), or add explicit bounds checks on `words.length` before indexing `words[0..3]` in `ValidateMultiSign.execute()`. Alternatively, wrap the entire body of `execute()` in a `try/catch(Throwable)` returning the standard `Pair.of(true, DATA_FALSE)` failure result, mirroring the pattern already used in `BatchValidateSign.execute()`.

### Proof of Concept
1. Deploy a Solidity/TVM contract that issues a low-level `call` to the `ValidateMultiSign` precompiled contract address with calldata shorter than 128 bytes (e.g., an empty `bytes` payload or a single 32-byte word).
2. Invoke that contract's function via a normal `TriggerSmartContract` transaction, on a network/chain where TIP-854 (`allowTvmOsaka`) has not been activated (default state prior to that hard fork).
3. `ValidateMultiSign.execute()` executes `DataWord.parseArray(rawData)` and then accesses `words[3]`, throwing `ArrayIndexOutOfBoundsException`, uncaught by this method (contrast with `BatchValidateSign`, which is explicitly wrapped) — confirmed by `ValidateMultiSignContractTest.testTip854PreActivationNoOp` which reproduces this exact "no outer catch" behavior for short calldata.
