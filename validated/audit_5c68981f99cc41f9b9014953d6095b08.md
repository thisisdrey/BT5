The code in `Lauraivanka/go--010` is Go's standard library `image/jpeg`, `image/png`, and `image/gif` decoders, not the vulnerable ImageWorsener C library. The reported CVE-2017-9093 is an infinite loop in ImageWorsener's `my_skip_input_data_fn` in `imagew-jpeg.c`, caused by a skip-bytes callback that fails to make forward progress on a crafted image, hanging libjpeg's `jpeg_skip_input_data`.

The closest analogous logic in this repo is `decoder.ignore` (skip n bytes) and `decoder.fill` (refill buffer) in `src/image/jpeg/reader.go`. Both are structured to guarantee forward progress or return an error:

- `fill` explicitly converts a zero-byte read into an error (`io.ErrUnexpectedEOF` on EOF, or the underlying error) rather than looping silently: [1](#0-0) 
- `ignore` calls `fill` and propagates any error immediately, so it cannot spin forever on a reader that stops producing bytes: [2](#0-1) 
- `readFull`, which `ignore`/segment-skipping logic depends on, has the same error-propagation structure: [3](#0-2) 
- The marker-scanning loop in `decode` and the RST-marker resync loop `findRST` also read via `d.readByte`/`d.readFull` and return on any I/O error rather than looping unconditionally: [4](#0-3) [5](#0-4) 

There is also an explicit regression test guarding exactly this bug class (crafted short/truncated JPEGs causing pathological or unbounded looping), which asserts `Decode` terminates with an error within a bounded time: [6](#0-5) 

Unlike ImageWorsener's `my_skip_input_data_fn`, none of Go's `ignore`/`fill`/`readByte`/`readFull` functions can be induced into a no-progress infinite loop by attacker-controlled JPEG bytes — every code path that loops on I/O checks and returns the error from the underlying `io.Reader` (including converting `n==0`/EOF into an explicit error). No matching root cause exists in this codebase, so I'm not reporting a speculative match to the CVE.

func (d *decoder) findRST(expectedRST uint8) error {
	for {
		// i is the index such that, at the bottom of the loop, we read 2-i
		// bytes into d.tmp[i:2], maintaining the invariant that d.tmp[:2]
		// holds the next two bytes of JPEG-encoded input. It is either 0 or 1,
		// so that each iteration advances by 1 or 2 bytes (or returns).
		i := 0

		if d.tmp[0] == 0xff {
			if d.tmp[1] == expectedRST {
				return nil
			} else if d.tmp[1] == 0xff {
				i = 1
			} else if d.tmp[1] != 0x00 {
				// libjpeg's jdmarker.c's jpeg_resync_to_restart does something
				// fancy here, treating RST markers within two (modulo 8) of
				// expectedRST differently from RST markers that are 'more
				// distant'. Until we see evidence that recovering from such
				// cases is frequent enough to be worth the complexity, we take
				// a simpler approach for now. Any marker that's not 0x00, 0xff
				// or expectedRST is a fatal FormatError.
				return FormatError("bad RST marker")
			}

		} else if d.tmp[1] == 0xff {
			d.tmp[0] = 0xff
			i = 1
		}

		if err := d.readFull(d.tmp[i:2]); err != nil {
			return err
		}
	}
