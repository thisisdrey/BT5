### Title
`remove_account` leaves ReceivedData, PostponedReceipt(Id), PendingDataCount and all PromiseYield-related trie keys behind on account deletion - ([File: core/store/src/utils/mod.rs])

### Summary
`remove_account` in `core/store/src/utils/mod.rs` only deletes the `Account`, `ContractCode`, `AccessKey`/`GasKeyNonce` (via prefix scan) and `ContractData` (via prefix scan) trie keys for a given `account_id`. It never touches `ReceivedData`, `PostponedReceiptId`, `PendingDataCount`, `PostponedReceipt`, `PromiseYieldReceipt`, `PromiseYieldStatus`, `YieldIdToDataId`, or `DataIdToYieldId`, all of which are listed as account-scoped in `col::COLUMNS_WITH_ACCOUNT_ID_IN_KEY`. This creates a verifiable state-conservation gap: deleting an account does not delete all its account-namespaced state.

### Finding Description
`col::COLUMNS_WITH_ACCOUNT_ID_IN_KEY` in `core/primitives/src/trie_key.rs:89-102` enumerates 12 column families keyed by `account_id`: `Account`, `ContractCode`, `AccessKey`, `ReceivedData`, `PostponedReceiptId`, `PendingDataCount`, `PostponedReceipt`, `ContractData`, `PromiseYieldReceipt`, `PromiseYieldStatus`, `YieldIdToDataId`, `DataIdToYieldId`.

`remove_account` (`core/store/src/utils/mod.rs:505-575`) performs exactly:
- `state_update.remove(TrieKey::Account { .. })` [1](#0-0) 
- an access-key/gas-key prefix scan via `get_raw_prefix_for_access_keys` and removal of each resolved `AccessKey`/`gas_key_nonce` key [2](#0-1) 
- a contract-data prefix scan via `get_raw_prefix_for_contract_data` and removal of each `ContractData` key [3](#0-2) 

There is no scan or removal logic for `ReceivedData`, `PostponedReceiptId`, `PendingDataCount`, `PostponedReceipt`, `PromiseYieldReceipt`, `PromiseYieldStatus`, `YieldIdToDataId`, or `DataIdToYieldId` anywhere in this function. This is a straightforward, code-confirmed gap: 8 of the 12 account-scoped column families in `COLUMNS_WITH_ACCOUNT_ID_IN_KEY` are not iterated or removed by `remove_account`.

### Impact Explanation
The gap is real at the code level and satisfies the audit's literal ask ("prove the four-way gap ... plus the four PromiseYield-related columns are never iterated"). Whether this translates into a concrete, in-scope bounty impact (theft/freezing of funds, authorization escalation, state-root divergence, or shard halt) depends on downstream receipt-processing logic that consumes `PostponedReceipt`/`ReceivedData`/`PromiseYieldReceipt`/`PromiseYieldStatus` rows by `(account_id, receipt_id/data_id)` — specifically whether the runtime can be made to look up and act on stale rows left behind after an `AccountId` is deleted and then recreated (e.g., a postponed cross-contract callback or promise-yield resume executing against a *newly created, differently-owned* account occupying the same `AccountId`). I was not able to fully trace that consumption path (`apply_state_patches`/receipt-processing code that reads these columns) within the available tool budget, so I cannot confirm the end-to-end fund-theft/escalation chain with the same confidence as the storage-layer gap itself.

### Likelihood Explanation
Precondition is only what the question specifies: a funded account that has outstanding rows in these columns (e.g., a pending cross-shard `data_id`/`receipt_id`, or an outstanding `yield_resume`) at the time `delete_account` is executed, followed by account name reuse. Creating such state (function calls with cross-contract promises, `promise_yield_create`) and then deleting the account are both actions available to an ordinary, unprivileged account holder, so the precondition is attacker-reachable in principle; whether the protocol allows deletion while such rows are outstanding, and whether the leftover rows are ever re-read for a re-created same-named account, is the part I could not fully verify.

### Recommendation
Extend `remove_account` to also prefix-scan and remove `ReceivedData`, `PostponedReceiptId`, `PendingDataCount`, `PostponedReceipt`, `PromiseYieldReceipt`, `PromiseYieldStatus`, `YieldIdToDataId`, and `DataIdToYieldId` for the account being deleted, mirroring the existing `AccessKey`/`ContractData` prefix-scan-and-remove pattern, so that every column in `col::COLUMNS_WITH_ACCOUNT_ID_IN_KEY` is actually cleared. Add a differential/table-driven test as described in the question that writes one row per `COLUMNS_WITH_ACCOUNT_ID_IN_KEY` variant, calls `remove_account`, and asserts the account-scoped key space is fully empty.

### Proof of Concept
Table test in `core/store/src/utils/mod.rs` (or a new test module):
1. For each `(col, name)` in `COLUMNS_WITH_ACCOUNT_ID_IN_KEY`, use the matching `TrieUpdate::set`/helper to write one representative row for account `A` (`Account`, `ContractCode`, `AccessKey`, `ReceivedData` with a `data_id`, `PostponedReceiptId`, `PendingDataCount`, `PostponedReceipt`, `ContractData`, `PromiseYieldReceipt`, `PromiseYieldStatus`, `YieldIdToDataId`, `DataIdToYieldId`).
2. Call `remove_account(&mut state_update, &A)`.
3. Iterate the full trie key space filtered to `account_id == A` (e.g., prefix-scan each column constant concatenated with `A`'s bytes).
4. Assert the resulting set is empty; expected actual result: `ReceivedData`, `PostponedReceiptId`, `PendingDataCount`, `PostponedReceipt`, `PromiseYieldReceipt`, `PromiseYieldStatus`, `YieldIdToDataId`, `DataIdToYieldId` rows survive, confirming the 8-column gap (the question's "four-way gap plus four PromiseYield-related columns").
