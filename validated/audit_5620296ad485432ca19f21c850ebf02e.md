Based on my investigation, I found a concrete analog: an attacker-controlled array-length field used to allocate huge arrays before any bound is enforced, in the `ValidateMultiSign` and `BatchValidateSign` TVM precompiled contracts — directly reachable by any address that issues a `TriggerSmartContract` (or an internal `CALL`) to precompile addresses `0x9`/`0xa`.

### Title
Unbounded array allocation from attacker-controlled length field in `ValidateMultiSign`/`BatchValidateSign` precompiles causes out-of-memory node crash - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
`extractBytesArray`, `extractBytes32Array`, and `extractSigArray` read a 32-byte "array length" word straight out of attacker-supplied calldata and immediately allocate a Java array of that size, with no upper bound check on the legacy code path. [1](#0-0) 

### Finding Description
`extractBytes32Array` and `extractBytesArray` both do `int len = words[offset].intValueSafe(); byte[][] arr = new byte[len][];` where `len` comes directly from an attacker-controlled word in the calldata, independent of the actual calldata size. [2](#0-1) 

In `ValidateMultiSign.execute`, the number of signatures (`sigArraySize`) is only bounded to `MAX_SIZE` (5) *before* extraction when `VMConfig.allowTvmSelfdestructRestriction()` is enabled; on the legacy path (flag disabled) `extractBytesArray` is invoked unconditionally with the unchecked `len`, and the `signatures.length > MAX_SIZE` guard only runs *after* the (potentially huge) allocation has already happened. [3](#0-2) 

`BatchValidateSign.doExecute` has the identical pattern for both `signatures` and `addresses`, gated by the same feature flag, and calls `extractBytes32Array` for `addresses` with no size guard at all when reached. [4](#0-3) 

The only other guard, `isValidAbiEncoding` (itself gated behind `VMConfig.allowTvmOsaka()`), merely checks that the total calldata length is 32-byte aligned and consistent with a fixed header/item word shape — it does not correlate the embedded length field with the true remaining payload size, so an attacker can supply minimal calldata that satisfies the alignment check while embedding an arbitrarily large integer (up to `Integer.MAX_VALUE`) as the length word. [5](#0-4) 

This is directly analogous to CVE-2022-41999's bug class: a crafted, small input file encodes a large internal dimension/tile-count field that the parser trusts and uses to drive an allocation before validating it against the actual available data, causing a crash. Here, the "file" is TVM calldata and the "tile count" is the ABI array-length word.

### Impact Explanation
`new byte[len][]` with `len` near `Integer.MAX_VALUE` attempts to allocate an array of billions of null references (~8 bytes each on 64-bit HotSpot, i.e. multi-gigabyte), which throws `OutOfMemoryError` or induces heavy GC pressure on the executing full node. Because `BatchValidateSign`/`ValidateMultiSign` run inside transaction execution (including during block application by every node replaying the chain), a single malicious transaction can crash or stall every validating/syncing node that processes it — a chain-wide denial of service, not merely a local resource exhaustion of the attacker's own call.

### Likelihood Explanation
Reachability depends on the state of the `allowTvmSelfdestructRestriction` VM config flag. I was unable to conclusively confirm from the indexed code whether this flag is unconditionally activated on current TRON mainnet (the corresponding on-chain parameter setter was not found via search, unlike other `Allow*` flags in `DynamicPropertiesStore`), so I cannot fully rule out that this path is already closed by a prior hard fork. If the flag is disabled (e.g., on networks/forks where the hard fork enabling it has not been proposed/activated, or during any window before its activation), the vulnerable legacy path in `extractBytesArray`/`extractBytes32Array` is directly reachable by any unprivileged account able to submit a `TriggerSmartContract` transaction or by any contract performing an internal `CALL` to address `0x9`/`0xa`.

### Recommendation
Validate the extracted `len` against a hard maximum (e.g., `MAX_SIZE`) and against the actual bounds of the remaining calldata *before* allocating `new byte[len][]` in `extractBytesArray`, `extractBytes32Array`, and `extractSigArray`, regardless of the `allowTvmSelfdestructRestriction` flag state, so the bound check can never be bypassed on any code path.

### Proof of Concept
Craft calldata for `validatemultisign(address,uint256,bytes32,bytes[])` (precompile `0xa`) where the dynamic `bytes[]` offset word points to a length word set to a large value (e.g., `0x7FFFFFFF`) while the actual calldata remains only a few words long (still passing the 32-byte-alignment check in `isValidAbiEncoding` since alignment doesn't depend on that particular word's value). When `VMConfig.allowTvmSelfdestructRestriction()` is false, `execute()` calls `extractBytesArray(words, offset, rawData)`, which executes `new byte[0x7FFFFFFF][]`, forcing a multi-gigabyte allocation attempt and triggering `OutOfMemoryError` in the node process handling the transaction/block.   private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
