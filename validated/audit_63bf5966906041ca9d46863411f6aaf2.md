### Title
`ERC20Transactor` XCM asset transactor trusts the ERC20 `transfer()` boolean return value instead of verifying real balance movement - ([File: cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs])

### Summary
`ERC20Transactor::withdraw_asset_with_surplus` and `deposit_asset_with_surplus` implement the XCM `TransactAsset` trait for assets that are backed by arbitrary ERC20 contracts executed through `pallet-revive`. Both functions move value by invoking the target contract's `IERC20::transfer` function and then trust the ABI-decoded boolean return value (`true`/`false`) as proof that exactly `amount` was moved, crediting or debiting the XCM holding register with that nominal `amount` regardless of what the contract actually did. This is the same broken invariant as the ERC4626 report: the contract call's *declared* outcome, not the *observed* balance delta, drives runtime accounting.

### Finding Description
In `withdraw_asset_with_surplus` (used when XCM withdraws an ERC20-backed asset from a user into holding): [1](#0-0) 
the code calls `IERC20::transferCall { to: checking_address, value: EU256::from(amount) }` on the user-supplied/arbitrary `asset_id` contract, then does:
```
let is_success = IERC20::transferCall::abi_decode_returns_validate(&return_value.data)...;
if is_success {
    Ok((AssetsInHolding::new_from_fungible_credit(what.id.clone(), Box::new(Erc20Credit(amount))), surplus))
}
```
The holding is credited with the full requested `amount` purely because the contract returned `true` — there is no `balanceOf` check before/after the call to confirm that `amount` (or any amount) was actually transferred to the checking account.

Symmetrically, `deposit_asset_with_surplus` transfers from the checking account to the beneficiary and again trusts the boolean return: [2](#0-1) 

`Erc20Credit` is explicitly documented as bypassing runtime-level balance enforcement: [3](#0-2) 
"the actual balance constraints are enforced by the ERC20 smart contract itself rather than the runtime" — i.e., the runtime has no independent verification mechanism at all, unlike `pallet_assets`'s `do_transfer` (which enforces exact conservation) or the fungible `Balanced` trait's `deposit`/`withdraw` which return the actually-moved amount.

Because `asset_id` in `Matcher::matches_fungibles(what)` is attacker-influenced (any deployed contract can be registered/foreign-asset-mapped as an ERC20-backed XCM asset on chains such as `asset-hub-westend` where `ERC20Transactor` is wired via `pallet_revive::Config::Precompiles`/XCM asset transactors), a malicious or non-standard ERC20 implementation can:
- Return `true` from `transfer()` while moving 0 tokens, a partial amount (fee-on-transfer tokens), or applying internal logic unrelated to `amount` (rebasing tokens, tokens with hooks that revert-then-catch, or tokens deliberately crafted to always return `true`).
- This is functionally identical to the reported ERC4626 issue: a contract's return value is taken as ground truth for accounting instead of the observable balance state.

### Impact Explanation
If `withdraw_asset_with_surplus` credits XCM holding with `amount` while the checking account received less (or nothing), the XCM executor can subsequently `DepositAsset` that phantom `amount` to any destination (including cross-chain via teleport/reserve-transfer semantics for other assets in the same message), effectively minting value that is not backed by any real ERC20 balance held by the chain's checking account. Conversely, in `deposit_asset_with_surplus`, if the ERC20 contract's `transfer` to the beneficiary reports success without moving full value, the checking account balance is depleted while the beneficiary receives less than accounted for — a permanent value loss/lock, and repeated calls could let an attacker drain the checking account while only ever crediting fractional real value to legitimate depositors (or the reverse: extract more from the checking account than XCM holding logically represents, if the "unlock more than deposited" direction is exploited by a colluding/malicious ERC20 contract). This directly violates the required invariant that "contract-held value must conserve value and settle exactly once to the rightful beneficiary and amount," and can produce unbacked mint/unlock or duplicate/inflated settlement of a bridge- or XCM-routed asset.

### Likelihood Explanation
The precondition is that an ERC20-backed asset handled by `ERC20Transactor` is not a fully-trusted, audited token — i.e., any chain configuration that permits registering foreign/permissionless ERC20 contracts (via `ForeignIdConfig`/`AssetIdExtractor`, or any XCM asset registration flow that maps a `Location` to an arbitrary `H160` contract address) as a `Matcher`-matched fungible asset. No malicious relayer, validator, or privileged actor is required — only a non-standard, permissionlessly deployed ERC20 contract at the mapped address, controlled by an ordinary user who then initiates an XCM transfer of that asset. This matches the "public underpriced/mis-accounted work by an unprivileged actor" profile the Impact Gate accepts, while requiring nothing on the "malicious peer/validator/relayer" excluded list.

### Recommendation
Do not trust the boolean return of `transfer()`. Read `IERC20::balanceOf` for the checking account (and/or beneficiary) before and after the call and use the observed delta as the credited/debited `amount`, mirroring the audit's ERC4626 recommendation:
```rust
let balance_before = Self::erc20_balance_of(asset_id, &checking_account_id)?;
// perform transfer
let balance_after = Self::erc20_balance_of(asset_id, &checking_account_id)?;
let actual = balance_after.saturating_sub(balance_before);
// use `actual` (require actual == amount, or credit `actual` and error/refund the difference)
```
Additionally, consider restricting `ERC20Transactor` to a governance-curated allowlist of ERC20 contracts known to be standard-compliant, since fully permissionless arbitrary-contract accounting can never be made fully safe purely by balance-diffing (reentrancy, rebasing, and pausable tokens still introduce edge cases), but balance-diffing at minimum closes the exact bug class reported.

### Proof of Concept
1. Deploy a malicious/non-standard ERC20 contract whose `transfer(address,uint256)` always returns `true` but performs a no-op (or transfers less than `value`, e.g. a fee-on-transfer token).
2. Register/map this contract as a foreign asset location usable by `ERC20Transactor::Matcher` on a chain such as `asset-hub-westend` (where `pallet_revive` precompiles and asset registration flows for ERC20-backed assets exist, per `cumulus/parachains/runtimes/assets/asset-hub-westend/src/lib.rs` `pallet_revive::Config::Precompiles` wiring).
3. Send an XCM message that performs `WithdrawAsset` for `amount` of this "asset" from the attacker's own account, invoking `ERC20Transactor::withdraw_asset_with_surplus`.
4. Because `transfer()` returns `true`, the code path at `erc20_transactor.rs` lines 185–207 credits `AssetsInHolding` with the full nominal `amount`, even though the checking account's real ERC20 balance did not increase by `amount` (or at all).
5. Follow with `DepositAsset`/`InitiateReserveWithdraw`/cross-chain transfer instructions in the same XCM program to move the phantom credited `amount` to an attacker-controlled destination or another chain, realizing unbacked value that has no corresponding real ERC20 balance backing it in the checking account. /// A minimal imbalance tracking type that holds an ERC20 token amount.
///
/// This type implements the necessary imbalance accounting traits but does not perform
/// runtime-level balance enforcement. It's used to track ERC20 token amounts within XCM
/// asset holdings, where the actual balance constraints are enforced by the ERC20 smart
/// contract itself rather than the runtime.
struct Erc20Credit(u128);
impl UnsafeConstructorDestructor<u128> for Erc20Credit {
	fn unsafe_clone(&self) -> Box<dyn ImbalanceAccounting<u128>> {
		Box::new(Erc20Credit(self.0))
	}
	fn forget_imbalance(&mut self) -> u128 {
		let amount = self.0;
		self.0 = 0;
		amount
	}
}

	fn withdraw_asset_with_surplus(
		what: &Asset,
		who: &Location,
		_context: Option<&XcmContext>,
	) -> Result<(AssetsInHolding, Weight), XcmError> {
		tracing::trace!(
			target: "xcm::transactor::erc20::withdraw",
			?what, ?who,
		);
		let (asset_id, amount) = Matcher::matches_fungibles(what)?;
		let who = AccountIdConverter::convert_location(who)
			.ok_or(MatchError::AccountIdConversionFailed)?;
		// We need to map the 32 byte checking account to a 20 byte account.
		let checking_account_eth = T::AddressMapper::to_address(&TransfersCheckingAccount::get());
		let checking_address = Address::from(Into::<[u8; 20]>::into(checking_account_eth));
		let weight_limit = WeightLimit::get();
		// To withdraw, we actually transfer to the checking account.
		// We do this using the solidity ERC20 interface.
		let data =
			IERC20::transferCall { to: checking_address, value: EU256::from(amount) }.abi_encode();
		let ContractResult { result, weight_consumed, storage_deposit, .. } =
			pallet_revive::Pallet::<T>::bare_call(
				OriginFor::<T>::signed(who.clone()),
				asset_id,
				U256::zero(),
				TransactionLimits::WeightAndDeposit {
					weight_limit,
					deposit_limit: StorageDepositLimit::get(),
				},
				data,
				&ExecConfig::new_substrate_tx(),
			);
		// We need to return this surplus for the executor to allow refunding it.
		let surplus = weight_limit.saturating_sub(weight_consumed);
		tracing::trace!(target: "xcm::transactor::erc20::withdraw", ?weight_consumed, ?surplus, ?storage_deposit);
		if let Ok(return_value) = result {
			tracing::trace!(target: "xcm::transactor::erc20::withdraw", ?return_value, "Return value by withdraw_asset");
			if return_value.did_revert() {
				tracing::debug!(target: "xcm::transactor::erc20::withdraw", "ERC20 contract reverted");
				Err(XcmError::FailedToTransactAsset("ERC20 contract reverted"))
			} else {
				let is_success = IERC20::transferCall::abi_decode_returns_validate(&return_value.data).map_err(|error| {
					tracing::debug!(target: "xcm::transactor::erc20::withdraw", ?error, "ERC20 contract result couldn't decode");
					XcmError::FailedToTransactAsset("ERC20 contract result couldn't decode")
				})?;
				if is_success {
					tracing::trace!(target: "xcm::transactor::erc20::withdraw", "ERC20 contract was successful");
					Ok((
						AssetsInHolding::new_from_fungible_credit(
							what.id.clone(),
							Box::new(Erc20Credit(amount)),
						),
						surplus,
					))
				} else {
					tracing::debug!(target: "xcm::transactor::erc20::withdraw", "contract transfer failed");
					Err(XcmError::FailedToTransactAsset("ERC20 contract transfer failed"))
				}
			}
		} else {
			tracing::debug!(target: "xcm::transactor::erc20::withdraw", ?result, "Error");
			// This error could've been duplicate smart contract, out of gas, etc.
			// If the issue is gas, there's nothing the user can change in the XCM
			// that will make this work since there's a hardcoded gas limit.
			Err(XcmError::FailedToTransactAsset("ERC20 contract execution errored"))
		}
	}

	fn deposit_asset_with_surplus(
		what: AssetsInHolding,
		who: &Location,
		_context: Option<&XcmContext>,
	) -> Result<Weight, (AssetsInHolding, XcmError)> {
		tracing::trace!(
			target: "xcm::transactor::erc20::deposit",
			?what, ?who,
		);
		defensive_assert!(what.len() == 1, "Trying to deposit more than one asset!");
		// Check we handle this asset.
		let maybe = what
			.fungible_assets_iter()
			.next()
			.and_then(|asset| Matcher::matches_fungibles(&asset).ok());
		let (asset_contract_id, amount) = match maybe {
			Some(inner) => inner,
			None => return Err((what, MatchError::AssetNotHandled.into())),
		};
		let who = match AccountIdConverter::convert_location(who) {
			Some(inner) => inner,
			None => return Err((what, MatchError::AccountIdConversionFailed.into())),
		};
		// We need to map the 32 byte beneficiary account to a 20 byte account.
		let eth_address = T::AddressMapper::to_address(&who);
		let address = Address::from(Into::<[u8; 20]>::into(eth_address));
		// To deposit, we actually transfer from the checking account to the beneficiary.
		// We do this using the solidity ERC20 interface.
		let data = IERC20::transferCall { to: address, value: EU256::from(amount) }.abi_encode();
		let weight_limit = WeightLimit::get();
		let ContractResult { result, weight_consumed, storage_deposit, .. } =
			pallet_revive::Pallet::<T>::bare_call(
				OriginFor::<T>::signed(TransfersCheckingAccount::get()),
				asset_contract_id,
				U256::zero(),
				TransactionLimits::WeightAndDeposit {
					weight_limit,
					deposit_limit: StorageDepositLimit::get(),
				},
				data,
				&ExecConfig::new_substrate_tx(),
			);
		// We need to return this surplus for the executor to allow refunding it.
		let surplus = weight_limit.saturating_sub(weight_consumed);
		tracing::trace!(target: "xcm::transactor::erc20::deposit", ?weight_consumed, ?surplus, ?storage_deposit);
		if let Ok(return_value) = result {
			tracing::trace!(target: "xcm::transactor::erc20::deposit", ?return_value, "Return value");
			if return_value.did_revert() {
				tracing::debug!(target: "xcm::transactor::erc20::deposit", "Contract reverted");
				Err((what, XcmError::FailedToTransactAsset("ERC20 contract reverted")))
			} else {
				match IERC20::transferCall::abi_decode_returns_validate(&return_value.data) {
					Ok(true) => {
						tracing::trace!(target: "xcm::transactor::erc20::deposit", "ERC20 contract was successful");
						Ok(surplus)
					},
					Ok(false) => {
						tracing::debug!(target: "xcm::transactor::erc20::deposit", "contract transfer failed");
						Err((
							what,
							XcmError::FailedToTransactAsset("ERC20 contract transfer failed"),
						))
					},
					Err(error) => {
						tracing::debug!(target: "xcm::transactor::erc20::deposit", ?error, "ERC20 contract result couldn't decode");
						Err((
							what,
							XcmError::FailedToTransactAsset(
								"ERC20 contract result couldn't decode",
							),
						))
					},
				}
			}
		} else {
			tracing::debug!(target: "xcm::transactor::erc20::deposit", ?result, "Error");
			// This error could've been duplicate smart contract, out of gas, etc.
			// If the issue is gas, there's nothing the user can change in the XCM
			// that will make this work since there's a hardcoded gas limit.
			Err((what, XcmError::FailedToTransactAsset("ERC20 contract execution errored")))
		}
	}
