### Title
Unvalidated attachment content lets a peer poison AtlasDB with data never committed on-chain - ([File: stackslib/src/net/atlas/download.rs])

### Summary
`AttachmentsDownloader::run`'s `Done` branch iterates `context.attachments.drain()` and directly calls `AtlasDB::insert_instantiated_attachment(&attachment)` without ever checking that `attachment.hash()` equals the `content_hash` of the `AttachmentRequest` that was originally sent to the peer. Any peer selected as a download source for `GET /v2/attachments/{content_hash}` can return an arbitrary blob and have it permanently written into the node's `attachments` table.

### Finding Description
The response-decoding path `StacksHttpResponse::decode_atlas_get_attachment` in `stackslib/src/net/api/getattachment.rs` (lines 158-165) simply JSON-deserializes the response body into a `GetAttachmentResponse { attachment }` — it performs no hash check against the request that was made. This decoded `Attachment` is then inserted into `context.attachments: HashSet<Attachment>` in `AttachmentsBatchStateContext::extend_with_attachments` (`download.rs` lines 530-558), again with no comparison to `request.content_hash` (the `AttachmentRequest` that triggered the fetch is available in scope as `request`, but only `request.get_url()` is used — `request.content_hash` is never consulted).

Finally, in `AttachmentsDownloader::run`'s `Done` arm (`download.rs` lines 153-169), every attachment collected in the set is looked up by its *own* self-reported hash (`attachment.hash()`) via `find_all_attachment_instances`, and then unconditionally persisted with `network.atlasdb.insert_instantiated_attachment(&attachment)` — before any `AttachmentInstance` pairing/verification occurs. Because the hash used for both the DB lookup and the store is derived from the attacker-controlled payload itself, an attacker can send *any* bytes; `insert_instantiated_attachment` will just store `Hash160::from_data(bytes) -> bytes` as a valid, "instantiated" attachment, regardless of whether it matches the `content_hash` that was actually requested (which came from an on-chain `AttachmentInstance.content_hash`).

Attack flow:
1. Node has an unresolved `AttachmentInstance` with `content_hash = H` on-chain.
2. `AttachmentsDownloader` builds an `AttachmentRequest { content_hash: H, sources, .. }` and issues `GET /v2/attachments/{H}` to one of the selected peer sources.
3. Malicious peer responds `200 OK` with `GetAttachmentResponse { attachment: Attachment { content: b"evil" } }`, where `Hash160::from_data(b"evil") = H' != H`.
4. `decode_atlas_get_attachment` accepts it purely on JSON well-formedness; `extend_with_attachments` inserts it into `context.attachments`.
5. `Done` branch calls `insert_instantiated_attachment(&attachment)`, storing `H' -> b"evil"` in `atlasdb`, even though no `AttachmentInstance` with `content_hash = H'` exists anywhere on-chain.

No guard anywhere in this call chain enforces `attachment.hash() == request.content_hash`.

### Impact Explanation
This is an unauthenticated write to persistent node state (the AtlasDB `attachments` table) by any peer that is selected as an inventory source — no signature, secret, or consensus commitment is checked. The attacker can plant arbitrary content under a hash of their choosing that has no relationship to any real `AttachmentInstance.content_hash` committed on-chain, corrupting the attachments store ("storage poisoning"). This matches the Critical category: unauthenticated/unauthorized write to node state, repeatable across many requests/peers.

### Likelihood Explanation
Preconditions are modest and attacker-controllable: the node just needs an unresolved `AttachmentInstance` queued (a normal, frequent condition during BNS/Atlas sync) and the attacker peer must appear as one of the `sources` in an `AttachmentRequest` (i.e., be an outbound sync peer whose inventory claims to have the attachment — trivially achievable by responding "1" in the attachments-inventory bitmap). No RPC secret, private key, or privileged role is required; the attacker only needs to run a normal P2P peer and answer the plaintext HTTP GET.

### Recommendation
In `AttachmentsBatchStateContext::extend_with_attachments` (or in the `Done` branch of `AttachmentsDownloader::run`), verify `response.attachment.hash() == request.content_hash` before inserting into `self.attachments`; discard/penalize (bump `report.bump_failed_requests()`, and optionally add to `faulty_peers`) any response that fails this check instead of storing it.

### Proof of Concept
Rust test in `stackslib::net::atlas` (module `download`):
1. Build an `AttachmentsBatchStateContext` with one peer.
2. Construct an `AttachmentRequest { content_hash: H, .. }` and a fake `StacksHttpResponse` for `GET /v2/attachments/{H}` whose JSON body is `GetAttachmentResponse { attachment: Attachment { content: b"evil".to_vec() } }`, where `Hash160::from_data(b"evil") != H`.
3. Insert this pair into `BatchedRequestsResult::succeeded` and call `context.extend_with_attachments(&mut results)`.
4. Drive `AttachmentsBatchStateMachine::Done` handling logic (or directly replicate `AttachmentsDownloader::run`'s `Done` arm) on the resulting context against a test `AtlasDB`.
5. Assert `atlasdb.find_attachment(&Hash160::from_data(b"evil")).unwrap().is_some()` succeeds, while no `AttachmentInstance` with `content_hash == Hash160::from_data(b"evil")` was ever inserted — proving unauthorized content was durably stored.
