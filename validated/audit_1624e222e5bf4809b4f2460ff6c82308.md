### Title
Unbounded array allocation from attacker-controlled length in `ValidateMultiSign`/`BatchValidateSign` precompile signature-array decoding - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The CVE describes a heap-based overflow in `pdf_load_mesh_params` caused by trusting an attacker-supplied "decode array" length without validating it before allocation/copy. The analogous pattern in java-tron is the helper methods that turn ABI-encoded call data into Java arrays for the `ValidateMultiSign` and `BatchValidateSign` TVM precompiled contracts: `extractBytesArray`, `extractSigArray`, and `extractBytes32Array`. All three read an unbounded 32-byte length word straight out of caller-supplied calldata and use it to size a Java array before any calling code has verified it is reasonable.

### Finding Description
`extractBytes32Array` computes `len` directly from calldata and immediately allocates: [1](#0-0) 
Unlike its siblings, it has no `offset` bounds check at all. `extractBytesArray` and `extractSigArray` do check `offset > words.length - 1`, but neither bounds-checks the derived `len` itself before allocating `new byte[len][]`: [2](#0-1) 

In `ValidateMultiSign.execute`, the size check on the extracted array (`sigArraySize > MAX_SIZE`) is only performed when the chain parameter `allowTvmSelfdestructRestriction()` is enabled; if it is not, execution falls straight into `extractBytesArray`/`extractSigArray` with the raw, attacker-controlled `len`: [3](#0-2) 
This call happens before the method's only `try`/`catch` block (which starts at line 1082 and only wraps signature-recovery/weight logic), so any exception or error thrown while extracting the array is not caught here.

`BatchValidateSign` has the same conditional gate for `sigArraySize`/`addrArraySize`, and calls `extractBytes32Array` for the address array unconditionally without any prior bound check: [4](#0-3) 
Here the whole `doExecute` is wrapped by a `catch (Throwable t)` in `execute`, so an `OutOfMemoryError` thrown while allocating an oversized array is caught locally: [5](#0-4) 

### Impact Explanation
Because `intValueSafe()` on a 32-byte word can return up to `Integer.MAX_VALUE` from data fully controlled by the transaction sender, an attacker can construct calldata to a `CALL` targeting the `ValidateMultiSign` or `BatchValidateSign` precompile addresses whose length field triggers `new byte[Integer.MAX_VALUE][]` (roughly tens of GB depending on element type/JVM). This can exhaust heap and raise `OutOfMemoryError`. For `ValidateMultiSign`, this happens outside any local try/catch, so if no higher-level exception handler in the TVM/actuator execution path tolerates `Error` (as opposed to `Exception`), it can abort or crash the executing node process rather than simply failing the single transaction — this is the direct analog of the CVE's "large decode array" causing a crash/DoS. For `BatchValidateSign`, the allocation is caught locally, but attempting the huge allocation can still stress/exhaust the JVM heap for the whole node process before the `OutOfMemoryError` is thrown and caught, since heap pressure is global, not per-thread.

### Likelihood Explanation
This is reachable by any unprivileged account: simply deploying or calling a contract that issues a `CALL`/`STATICCALL` to the `ValidateMultiSign`/`BatchValidateSign` precompile address with crafted calldata is sufficient — no special permission is required. The severity of impact is conditional on the current on-chain value of the `allowTvmSelfdestructRestriction` hardfork parameter: if it is already activated on the target network, the `MAX_SIZE` checks at lines 1066-1071 / 1165-1171 mitigate this for the guarded branches, but `extractBytes32Array`'s missing bounds check and the general pattern of trusting attacker-controlled lengths before allocation remain present in the code regardless of that flag. I was not able to confirm from the index whether `allowTvmSelfdestructRestriction` defaults to enabled at genesis on the target chain configuration; this should be verified in `chainbase/src/main/java/org/tron/core/store/DynamicPropertiesStore.java` and `common/src/main/java/org/tron/core/vm/config/VMConfig.java` before relying on this as a live, unmitigated bug.

### Recommendation
- Add an explicit upper bound check (e.g., `len < 0 || len > MAX_SIZE`) inside `extractBytesArray`, `extractSigArray`, and `extractBytes32Array` themselves, unconditional on any hardfork flag, before allocating the result array.
- Add the missing `offset > words.length - 1` guard to `extractBytes32Array` to match its sibling methods.
- Ensure `ValidateMultiSign.execute` cannot throw an uncaught `Error`/`RuntimeException` from array extraction; wrap the extraction calls in the same defensive try/catch used later in the method, or perform validation before calling the extraction helpers unconditionally (not gated by `allowTvmSelfdestructRestriction`).

### Proof of Concept
Construct calldata for a `CALL` to the `ValidateMultiSign` precompile address (per `PrecompiledContracts.getContractForAddress`) with the ABI-encoded `bytes[]` "signatures" parameter's length word set to a very large value (e.g., `0x7fffffff`) while `allowTvmSelfdestructRestriction` is not yet activated on the target chain. Deploy and invoke a contract making this call; observe the node attempting `new byte[0x7fffffff][]` inside `extractBytesArray`/`extractSigArray` at [6](#0-5)  outside of the method's guarding `try`/`catch`, exhausting heap.

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
