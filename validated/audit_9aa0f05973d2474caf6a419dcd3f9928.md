### Title
Unrestricted `TransferToGasKey` lets any account permanently block a victim's key deletion and account deletion via `GasKeyBalanceTooHigh` - (File: `runtime/runtime/src/actions.rs`)

### Summary
`Action::TransferToGasKey` is one of the few actions explicitly exempted from actor-identity checks in `check_actor_permissions`, meaning *any* signer/predecessor can fund *any* account's gas key with an arbitrary deposit. Because gas-key deletion and full account deletion both hard-fail once a gas key's balance exceeds `GasKeyInfo::MAX_BALANCE_TO_BURN`, an attacker can grief a target by inflating that balance past the threshold, permanently blocking the owner from deleting that key or the account — the same "attacker deposits a token into the victim contract to trip an unconditional balance precondition and block a subsequent privileged/self-operation" pattern described in the PirexGmx `initiateMigration`/`signalTransfer` report.

### Finding Description
`check_actor_permissions` requires `actor_id == account_id` for most self-mutating actions (`DeployContract`, `Stake`, `AddKey`, `DeleteKey`, `DeployGlobalContract`, `UseGlobalContract`, `WithdrawFromGasKey`, `DeleteAccount`), but `Action::TransferToGasKey` is grouped with `CreateAccount`/`FunctionCall`/`Transfer` as requiring no actor check at all: [1](#0-0) 

The corresponding execution handler `action_transfer_to_gas_key` only checks that the target gas key exists; it never checks that the predecessor equals the account owner, and it happily accumulates the deposit into `gas_key_info.balance`: [2](#0-1) 

This means anyone who knows a victim account's public gas key (gas keys are visible on-chain, e.g. via RPC/view calls) can send a `TransferToGasKeyAction` receipt to that account with any deposit amount and repeatedly top it up, since balances are additive across calls (see `test_transfer_to_gas_key_success`, which shows repeated calls accumulate).

Once a gas key's balance exceeds `GasKeyInfo::MAX_BALANCE_TO_BURN` (1 NEAR), two owner-only operations become permanently unusable for that key/account:

1. **Key deletion is blocked.** `delete_gas_key` rejects deletion with `GasKeyBalanceTooHigh` whenever `gas_key_info.balance > GasKeyInfo::MAX_BALANCE_TO_BURN`: [3](#0-2) 

2. **Full account deletion is blocked.** `action_delete_account` sums the balances of all gas keys on the account (`compute_gas_key_balance_sum`) and fails the entire `DeleteAccount` action with the same `GasKeyBalanceTooHigh` error if that sum exceeds the threshold — even if the owner never wanted to burn that balance and only wants to close the account: [4](#0-3) 

Since `WithdrawFromGasKey` (the only way to move balance *out* of a gas key) is actor-restricted to `actor_id == account_id` in the same `check_actor_permissions` match, the account owner is the only one who can reduce this balance back down — but nothing stops the attacker from repeating the deposit in a subsequent block to re-trip the threshold, creating a persistent race the victim cannot reliably win, similar to how the PirexGmx attacker repeatedly acquires and transfers vGMX/vGLP to re-block `signalTransfer`.

### Impact Explanation
This is a griefing/permanent-freezing vector: it does not let the attacker steal funds directly, but it lets an unprivileged party permanently prevent an account from deleting a gas key or deleting the account entirely, freezing the account's storage-staked balance and gas-key balance in a state the owner cannot resolve without racing withdrawals against attacker deposits every block. This maps to the "permanent freezing of funds" acceptance criterion — the account's beneficiary payout on deletion, and the value locked in the gas key, become inaccessible as long as the attacker keeps re-funding above the threshold.

### Likelihood Explanation
The attack requires no privilege: any signer, knowing (or brute-forcing/observing) a target's gas-key public key, can send a plain `TransferToGasKeyAction` transaction with a `>1 NEAR` (or repeated smaller) deposit to any account. `TransferToGasKey`'s inclusion in the unrestricted-actor group in `check_actor_permissions` appears intentional (to let contracts fund gas keys for others, e.g. relayer patterns), but this legitimate design choice directly enables the griefing path once combined with the hard `GasKeyBalanceTooHigh` gate on deletion.

### Recommendation
Decouple "gas key has residual balance" from "cannot delete." Options:
- Instead of rejecting deletion outright when balance exceeds `MAX_BALANCE_TO_BURN`, refund the excess to the beneficiary/owner (as is already done for the account's own NEAR balance in `action_delete_account`) rather than requiring the caller to manually withdraw first.
- Alternatively, restrict `TransferToGasKey` (or at least allow an owner-only "cap"/"reject" mechanism) so unsolicited large deposits from third parties cannot silently push a key over the burn-prevention threshold, e.g., require explicit owner opt-in for deposits above a configurable cap, or let the owner unilaterally force-burn/delete regardless of balance (only they should bear that cost).
- At minimum, document/require that any account relying on gas keys for self-deletion must proactively monitor and withdraw gas-key balances, since third parties can inflate them at will.

### Proof of Concept
1. Attacker observes victim account `victim.near` has a gas key `pk_gas` (visible via `view_access_key`).
2. Attacker sends `SignedTransaction::from_actions(nonce, attacker.near, victim.near, attacker_signer, vec![Action::TransferToGasKey(TransferToGasKeyAction{ public_key: pk_gas, deposit: 2_NEAR })], block_hash)`. This succeeds because `check_actor_permissions` does not restrict `TransferToGasKey` to `actor_id == account_id`: [5](#0-4) 
3. `victim.near`'s gas key `pk_gas` now has `gas_key_info.balance = 2 NEAR > GasKeyInfo::MAX_BALANCE_TO_BURN`.
4. Victim submits `DeleteKey(pk_gas)` as themselves (`actor_id == account_id`, passes the permission check) but execution fails in `delete_gas_key` with `ActionErrorKind::GasKeyBalanceTooHigh`: [6](#0-5) 
5. Victim instead tries `DeleteAccount` to close and reclaim funds; `action_delete_account` sums all gas-key balances (including the attacker-funded one) and again fails with `GasKeyBalanceTooHigh`, leaving the account permanently undeletable unless the victim first calls `WithdrawFromGasKey` — which the attacker can immediately counter by repeating step 2 in a later block.

pub(crate) fn check_actor_permissions(
    action: &Action,
    account: &Option<Account>,
    actor_id: &AccountId,
    account_id: &AccountId,
) -> Result<(), ActionError> {
    match action {
        Action::DeployContract(_)
        | Action::Stake(_)
        | Action::AddKey(_)
        | Action::DeleteKey(_)
        | Action::DeployGlobalContract(_)
        | Action::UseGlobalContract(_)
        | Action::WithdrawFromGasKey(_) => {
            if actor_id != account_id {
                return Err(ActionErrorKind::ActorNoPermission {
                    account_id: account_id.clone(),
                    actor_id: actor_id.clone(),
                }
                .into());
            }
        }
        Action::DeleteAccount(_) => {
            if actor_id != account_id {
                return Err(ActionErrorKind::ActorNoPermission {
                    account_id: account_id.clone(),
                    actor_id: actor_id.clone(),
                }
                .into());
            }
            let account = account.as_ref().unwrap();
            if !account.locked().is_zero() {
                return Err(ActionErrorKind::DeleteAccountStaking {
                    account_id: account_id.clone(),
                }
                .into());
            }
        }
        Action::CreateAccount(_)
        | Action::FunctionCall(_)
        | Action::Transfer(_)
        | Action::TransferToGasKey(_) => (),
        Action::Delegate(_) | Action::DelegateV2(_) => (),
        Action::DeterministicStateInit(_) => (),
    };
    Ok(())

pub(crate) fn action_transfer_to_gas_key(
    state_update: &mut TrieUpdate,
    result: &mut ActionResult,
    account_id: &AccountId,
    action: &TransferToGasKeyAction,
) -> Result<(), RuntimeError> {
    let Some(mut access_key) = get_access_key(state_update, account_id, &action.public_key)? else {
        result.result = Err(ActionErrorKind::GasKeyDoesNotExist {
            account_id: account_id.clone(),
            public_key: Box::new(action.public_key.clone()),
        }
        .into());
        return Ok(());
    };
    let Some(gas_key_info) = access_key.gas_key_info_mut() else {
        // Key exists but is not a gas key
        result.result = Err(ActionErrorKind::GasKeyDoesNotExist {
            account_id: account_id.clone(),
            public_key: Box::new(action.public_key.clone()),
        }
        .into());
        return Ok(());
    };

    gas_key_info.balance = gas_key_info.balance.checked_add(action.deposit).ok_or_else(|| {
        RuntimeError::StorageError(StorageError::StorageInconsistentState(
            "gas key balance integer overflow".to_string(),
        ))
    })?;
    set_access_key(state_update, account_id.clone(), action.public_key.clone(), &access_key);
    Ok(())
}
