### Title
Unsanitized `git_object_directory` / `git_alternate_object_directories` fields bypass quarantine-ownership validation in git command construction - ([File: internal/git/gitcmd/command_factory.go])

### Summary
The `Repository` protobuf message exposes two client-settable fields, `git_object_directory` and `git_alternate_object_directories`, which are supposed to only ever reference the repository's own object quarantine directory. Gitaly has dedicated logic (`(*Repo).ObjectDirectoryPath` in `internal/git/localrepo/paths.go`) that strictly validates these fields never escape the repository's storage and, when not equal to the well-known transaction quarantine name, must match a `QuarantineDirectoryPrefix` derived from the target repository's own relative path — this is the mechanism that prevents one repository's caller from pointing at another repository's (or an arbitrary) directory. However, the code path that actually spawns git subprocesses, `ExecCommandFactory.newCommand` in `internal/git/gitcmd/command_factory.go`, never calls this validated accessor. Instead it builds the `GIT_OBJECT_DIRECTORY`/`GIT_ALTERNATE_OBJECT_DIRECTORIES` environment variables directly from the raw, unvalidated field values via `alternates.Env(repoPath, repo.GetGitObjectDirectory(), repo.GetGitAlternateObjectDirectories())`, which performs nothing more than a `filepath.Join`.

`QuarantineDirectoryPrefix` explicitly states its purpose is to let Gitaly "verify that a given quarantine object directory indeed belongs to the repository at hand" — i.e., it is the analog of verifying that the caller is the legitimate/authorized quarantine directory for *this* repository, just as the external report's root cause was failing to verify that `msg.sender` is the legitimate `aToken` for the accounting it is trying to mutate. [4](#0-3) 

The `Repository` protobuf explicitly documents these fields as directly controlling the git object directory environment variables for every git command:
```
// git_object_directory sets the GIT_OBJECT_DIRECTORY envvar on git commands to the value of this field.
...
// git_alternate_object_directories sets the GIT_ALTERNATE_OBJECT_DIRECTORIES envvar on git commands to
// the values of this field.
``` [5](#0-4) 

Because `newCommand` is the universal path through which essentially all Git subprocesses are spawned by Gitaly (used for every RPC that executes a git command against a repository), any RPC that lets a caller populate a `Repository` message with attacker-influenced `git_object_directory`/`git_alternate_object_directories` values (this is exactly how the object-quarantine feature works end-to-end — GitLab's `pre-receive` hook environment is round-tripped back into a `Repository` message and passed back into subsequent Gitaly RPCs, as documented in `doc/object_quarantine.md`) can cause Gitaly to search for (and, for write operations, potentially create/rely on) objects from an attacker-chosen directory instead of a directory validated to belong to that repository. [6](#0-5) 

### Impact Explanation
By supplying a crafted `git_object_directory`/`git_alternate_object_directories` value (e.g. a relative path traversal like `../../other-repo/objects`, or a path to another repository's genuine quarantine directory), a caller can cause Gitaly's git subprocesses to read objects from, and search for objects within, a directory outside the scope the validated `ObjectDirectoryPath` logic intends to allow. This is a cross-repository object access / storage-isolation escape: the ownership check that exists specifically to prevent one repository from being pointed at another repository's (or an arbitrary) object directory is not applied on the command-execution path. Depending on which RPC surfaces this field to an untrusted caller and how permissive access control is around it, this could disclose objects from other repositories (unauthorized read across repository boundaries) or corrupt assumptions made by the quarantine/pre-receive hook workflow.

### Likelihood Explanation
The trigger requires only setting two plain string/array fields on a `Repository` protobuf message that is a normal part of nearly every Gitaly RPC request, and no additional privilege beyond whatever level of Gitaly access the caller already has (e.g. having gone through the standard git push / hook round-trip, or crafting an RPC request with these fields populated). Given that Gitaly's own documentation and the parallel, carefully-written validation function in `paths.go` demonstrate that this class of input is explicitly recognized as security sensitive, but the actual command-spawning path (`command_factory.go`) does not invoke that validation, this is a straightforward, reachable code path for any caller able to set these fields in a request.

### Recommendation
Route the `GIT_OBJECT_DIRECTORY` / `GIT_ALTERNATE_OBJECT_DIRECTORIES` environment construction in `ExecCommandFactory.newCommand` (and any other code path building these variables directly from `repo.GetGitObjectDirectory()`/`repo.GetGitAlternateObjectDirectories()`, such as `internal/gitaly/hook/custom.go`) through the same validation performed by `(*Repo).ObjectDirectoryPath`, so that every git subprocess launch enforces the storage-containment and quarantine-prefix ownership check before honoring these fields, rather than only enforcing it in one accessor that isn't used on the hot path.

### Proof of Concept
Not independently executable from static analysis alone — a concrete PoC would require confirming, at runtime, which specific externally-reachable RPC populates `Repository.git_object_directory`/`git_alternate_object_directories` from caller-influenced input reaching `ExecCommandFactory.newCommand` without prior sanitization, and then supplying a path such as `../<other-repo-relative-path>/objects` (or a valid quarantine directory that does not match `QuarantineDirectoryPrefix` for the requested repo) to observe that Gitaly's spawned git process resolves objects from outside the caller's own repository. This should be validated in a live Devin session against the actual RPC surface and access-control configuration, since static review cannot fully confirm which callers are able to set these fields.

// Env returns the alternate object directory environment variables.
func Env(repoPath, objectDirectory string, alternateObjectDirectories []string) []string {
	var env []string
	if objectDirectory != "" {
		env = append(env, fmt.Sprintf("GIT_OBJECT_DIRECTORY=%s", filepath.Join(repoPath, objectDirectory)))
	}

	if len(alternateObjectDirectories) > 0 {
		var dirsList []string

		for _, dir := range alternateObjectDirectories {
			dirsList = append(dirsList, filepath.Join(repoPath, dir))
		}

		env = append(env, fmt.Sprintf("GIT_ALTERNATE_OBJECT_DIRECTORIES=%s", strings.Join(dirsList, ":")))
	}

// QuarantineDirectoryPrefix returns a prefix for use in the temporary directory. The prefix is
// based on the relative repository path and will stay stable for any given repository. This allows
// us to verify that a given quarantine object directory indeed belongs to the repository at hand.
// Ideally, this function would directly be located in the quarantine module, but this is not
// possible due to cyclic dependencies.
func QuarantineDirectoryPrefix(repo Repository) string {
	hash := [20]byte{}
	if repo != nil {
		hash = sha1.Sum([]byte(repo.GetRelativePath()))
	}
	return fmt.Sprintf("quarantine-%x-", hash[:8])
}
