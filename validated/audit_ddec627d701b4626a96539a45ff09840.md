## Answer

The Dopex `reLP()` bug is a **missing slippage/minimum-output protection** on an AMM liquidity operation, allowing the operation to execute against a manipulated pool ratio. The reachable analog in java-tron is in the TRC10 "Exchange" (Bancor-style AMM) actuators. [1](#0-0) 

### Title
Missing minimum-output (slippage) protection in `ExchangeInjectContract`/`ExchangeWithdrawContract` allows sandwich extraction of liquidity providers - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`, `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
`ExchangeTransactionContract` (a swap against the TRC10 bonding-curve exchange) carries an `expected` field that lets the caller bound the minimum amount received, protecting against price movement between broadcast and execution. [1](#0-0)  `ExchangeInjectContract` and `ExchangeWithdrawContract`, which add/remove liquidity from the same pool, have no analogous minimum/maximum bound on the "other token" amount computed from the live pool ratio — the exact class of bug reported for Uniswap's `addLiquidity()` in the external report (missing `amountAMin`/`amountBMin`).

### Finding Description
`ExchangeInjectContract` only carries `owner_address`, `exchange_id`, `token_id`, `quant` — no slippage bound. [2](#0-1)  In `ExchangeInjectActuator.execute()`, the counter-token amount `anotherTokenQuant` the caller must pay in is computed at execution time directly from the exchange's *current* `firstTokenBalance`/`secondTokenBalance` ratio: [3](#0-2) 
The same pattern (no caller-specified min/max) exists in `ExchangeWithdrawActuator.execute()`, where `anotherTokenQuant` — the amount of the counter-token paid *out* to the withdrawing liquidity provider — is likewise derived from the pool ratio read at execution time: [4](#0-3) 
`doValidate()` in both actuators re-derives `anotherTokenQuant` from the pool state present when the block-applying node runs validation (immediately before `execute()`), not from the state at the time the caller signed the transaction — there is no user-supplied bound comparable to Uniswap's `amountAMin`/`amountBMin` or the `expected` field already used by `ExchangeTransactionContract`. [5](#0-4) 

Any account can permissionlessly create an exchange pair via `ExchangeCreateContract` and become its "creator", the only role allowed to call inject/withdraw: [6](#0-5) 
so this is reachable by an ordinary, unprivileged account acting as a liquidity/pool operator, exactly like the `reLP()` caller in the report — no SR/witness/committee privilege is required.

Because pending transactions are visible in the p2p mempool before being packed, an anonymous broadcaster can observe a pending `ExchangeInjectContract`/`ExchangeWithdrawContract` and submit a swap (`ExchangeTransactionContract`, itself protected by `expected` so the attacker bears no slippage risk) that shifts `firstTokenBalance`/`secondTokenBalance` immediately before the victim's transaction is applied, then reverse the swap afterward — a classic sandwich. The victim's inject/withdraw executes against the manipulated ratio with no floor/ceiling to reject it.

### Impact Explanation
An attacker can sandwich a liquidity inject or withdraw to extract value from the pool creator: on inject, the victim is forced to contribute more of the counter-token than the fair-value ratio implies; on withdraw, the victim receives less of the counter-token than fair value. This is a concrete, reproducible loss of funds for any account performing exchange-pool liquidity operations, directly analogous to the "less LP tokens than expected" impact described in the reference finding.

### Likelihood Explanation
Requires no special privilege — any account that created an `Exchange` pair (permissionless via `ExchangeCreateContract`) and later injects/withdraws liquidity is exposed. The attack only needs an anonymous actor able to broadcast an ordinary `ExchangeTransactionContract` swap ahead of the victim's transaction, which is a normal, unprivileged capability (not a malicious-SR/witness scenario), and TRC10 exchanges/pools with meaningful liquidity make the ratio move economically worthwhile to manipulate.

### Recommendation
Add a slippage-bound field to `ExchangeInjectContract`/`ExchangeWithdrawContract` (e.g., `another_token_expected_min`/`_max`, mirroring the `expected` field on `ExchangeTransactionContract`) and enforce it in `ExchangeInjectActuator`/`ExchangeWithdrawActuator`'s `doValidate()`/`execute()` so the transaction fails rather than executing against an unfavorable, manipulated ratio.

### Proof of Concept
1. Attacker monitors mempool for a pending `ExchangeInjectContract` (or `ExchangeWithdrawContract`) targeting exchange `E`.
2. Attacker broadcasts an `ExchangeTransactionContract` swap against `E` with `expected` set favorably to the attacker, shifting `firstTokenBalance`/`secondTokenBalance`, and ensures it is applied before the victim's transaction in the same or an earlier block.
3. Victim's `ExchangeInjectContract`/`ExchangeWithdrawContract` executes: `anotherTokenQuant` in `ExchangeInjectActuator.execute()`/`ExchangeWithdrawActuator.execute()` is computed from the now-skewed ratio, causing the victim to pay in more (inject) or receive less (withdraw) of the counter-token than fair value.
4. Attacker reverses the swap afterward, pocketing the difference extracted from the victim's liquidity operation. No validation in either actuator's `doValidate()` rejects this because no minimum/maximum bound exists for `anotherTokenQuant`.
