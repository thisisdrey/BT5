### Title
Empty configured broadcast-auth password is treated as a valid password, allowing unauthenticated broadcast when `authorization: ` header is empty - (File: stackslib/src/net/api/postblock_v3.rs)

### Summary
`RPCPostBlockRequestHandler::try_parse_request` authenticates a `POST /v3/blocks/upload/?broadcast=1` request by comparing the `authorization` header value against the configured secret with a plain `!=` string comparison. If the operator configures an empty secret (`Some(String::new())`), an attacker who sends an empty `authorization` header (`authorization: `) satisfies `auth_header != password` as `"" != ""` → `false`, so `authenticated` is set to `true`, bypassing the intended broadcast gate.

### Finding Description
The relevant logic is:
```rust
if let Some(password) = &self.auth {
    if let Some(auth_header) = preamble.headers.get("authorization") {
        if auth_header != password {
            return Err(Error::Http(401, "Unauthorized".into()));
        }
        authenticated = true;
    }
}
``` [1](#0-0) 

The equality guard is purely lexical: it does not distinguish "no auth configured" (`self.auth == None`) from "auth configured but empty" (`self.auth == Some(String::new())`). In the `None` case, the outer `if let Some(password)` is never entered, so `authenticated` stays `false` and any `broadcast=1` request without an authenticated grant is rejected later at the `broadcast && !authenticated` check. In the `Some(String::new())` case, the branch is entered, and an attacker-supplied empty `authorization` header (`auth_header == ""`) matches the empty configured `password`, flipping `authenticated` to `true` and passing the `broadcast && !authenticated` gate:
```rust
if broadcast && !authenticated {
    return Err(Error::Http(401, "Unauthorized".into()));
}
``` [2](#0-1) 

This lets the attacker's POSTed Nakamoto block go through `try_handle_request`, which calls `Relayer::process_new_nakamoto_block_ext` with `self.broadcast.unwrap_or(false) == true`, and on acceptance queues the block via `node.set_relay_message(StacksMessageType::NakamotoBlocks(...))` for network-wide relay. [3](#0-2) 

The root cause is that an empty configured secret is not rejected/normalized as "auth disabled" (which would deny broadcast, matching the `None` behavior) nor is it treated as invalid configuration — it degenerates into a trivially satisfiable equality (`"" == ""`).

### Impact Explanation
Under this specific misconfiguration (operator sets an empty broadcast-auth secret), any remote unauthenticated attacker can force the node to accept-and-relay attacker-submitted Nakamoto blocks through the intended-to-be-gated broadcast path by simply sending an empty `authorization` header — no credential guessing needed. This is a genuine authentication-bypass logic flaw (auth-gate degeneration), matching the "unauthenticated ... auth bypass" Critical category, but it is strictly conditioned on the empty-secret misconfiguration; it does not affect deployments where `self.auth` is `None` or a non-empty secret.

### Likelihood Explanation
Preconditions: the node operator must have explicitly configured the broadcast-auth token as an empty string (`Some(String::new())`) rather than leaving it unset (`None`) or non-empty. This is a misconfiguration, not the default/typical state — I could not confirm from the indexed config code whether the node's config loader (`stackslib/src/config/mod.rs`, `auth_token` field) can actually produce `Some(String::new())` from a plausible TOML input (e.g., an explicitly empty `auth_token = ""` line) versus normalizing empty strings to `None`; this could not be fully verified with the available tools. If such a config value is reachable, exploitation is trivial and remote (a bare HTTP POST with an empty header, no privileged role or secret needed), and repeatable per block.

### Recommendation
Treat an empty configured secret the same as "no secret configured" (i.e., never set `authenticated = true` when `password.is_empty()`), or reject empty-string secrets at config-load time with a hard error, so operators cannot silently disable the broadcast-auth gate.
