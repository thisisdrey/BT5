## Analysis

The seed bug (H‑1) is: **a value/redemption path is assumed to be a fair, direct 1:1 (or otherwise "safe") conversion, but the actual conversion is executed through an external market (AMM/DEX) that can be manipulated, and no slippage/minimum-output bound is enforced before that value is used to drive further protocol accounting.**

The local analog is in the Snowbridge **system-frontend** pallet, which lets any signed AssetHub user swap an arbitrary "tip" asset for Ether through a public `pallet_asset_conversion` pool and then forwards the resulting Ether amount to BridgeHub as a **relayer reward tip / registration fee**, with **no minimum-output check on the swap**. ### Title
Unbounded AMM swap output used to fund relayer reward tips/registration fees enables inflated, unbacked reward credit - (File: bridges/snowbridge/pallets/system-frontend/src/lib.rs)

### Summary
`swap_and_burn` in the Snowbridge `system-frontend` pallet swaps an arbitrary attacker-chosen "tip" asset for Ether via `pallet_asset_conversion::Swap::swap_exact_tokens_for_tokens`, explicitly passing `None` as the minimum-amount-out parameter. The resulting `ether_gained` — an amount entirely determined by the current spot price of a permissionless, user-creatable AMM pool — is burned/teleported and forwarded verbatim as the `amount` field of `EthereumSystemCall::AddTip`/`RegisterToken`, which BridgeHub accepts and adds directly to a relayer's payable reward (`order.fee`) or to the token-registration fee accounting.

### Finding Description
Like `OraclePendlePT` assuming a PT always redeems 1:1 for its underlying without validating the real market/execution path, this code assumes that "amount of Ether obtained from an AMM swap" is a trustworthy, fair value to forward on-chain as a reward/fee amount, without validating market depth or bounding slippage/price impact.

Anyone can create an asset-conversion pool for `(tip_asset, Ether)` and be the sole liquidity provider, choosing an arbitrarily skewed initial ratio (e.g., depositing a tiny amount of Ether against a large amount of a low-value asset). Because `swap_exact_tokens_for_tokens` is called with `min_amount_out = None`, the swap always succeeds and returns whatever amount the (attacker-controlled) pool's current price dictates — there is no guard rejecting economically implausible or manipulated outputs before that number is trusted as the reward "amount" sent to BridgeHub.

BridgeHub's `add_tip`/`RegisterToken` handlers do not re-derive or sanity-check this amount against any oracle or independent price feed — they simply add it to `PendingOrders[nonce].fee` (outbound queue) or use it for registration fee accounting, both of which are eventually settled/paid from the bridge's reward pot to relayers.

### Impact Explanation
An attacker can inflate the on-chain-recorded relayer reward/registration fee for a message using a self-created, thinly-liquid pool, then extract that value later as an (over-)paid relayer reward, effectively minting unbacked reward credit against the bridge's payout pot — matching the "theft or unbacked mint" / "duplicate or incorrect settlement" impact class for Snowbridge bridge processing.

### Likelihood Explanation
Requires only a normal signed AssetHub account and the ability to create/fund an asset-conversion pool — both are unprivileged, permissionless actions available to any user, not a malicious validator/relayer/governance actor.

### Recommendation
Require a caller-supplied `min_amount_out` (or an oracle-derived floor) for the tip/fee swap in `swap_and_burn`, and/or cap the credited `amount` forwarded to BridgeHub by an independently verified maximum, rather than trusting the raw AMM swap output.

### Proof of Concept
1. Attacker creates a new `pallet_asset_conversion` pool for `(SomeCheapAsset, Ether)` and seeds it alone with a heavily skewed ratio (e.g., 1 unit `SomeCheapAsset` : 1000 units Ether).
2. Attacker calls `EthereumSystemFrontend::add_tip` with `asset = (SomeCheapAsset, small_amount)`.
3. `swap_and_burn` executes `swap_exact_tokens_for_tokens(.., small_amount, None, ..)` against the attacker's own pool, returning a large `ether_gained` due to the skewed price and no minimum-output check.
4. This inflated `ether_gained` is burned/teleported and forwarded as `amount` in `EthereumSystemCall::AddTip` to BridgeHub, which credits `PendingOrders[nonce].fee` with the inflated value, to be later paid to relayers from the bridge's reward funds. [5](#0-4) [4](#0-3)

		/// Swaps a specified tip asset to Ether and then burns the resulting ether for
		/// teleportation. Returns the amount of Ether gained if successful, or a DispatchError if
		/// any step fails.
		fn swap_and_burn(
			origin: Location,
			tip_asset_location: Location,
			ether_location: Location,
			tip_amount: u128,
		) -> Result<u128, DispatchError> {
			// Swap tip asset to ether
			let swap_path = vec![tip_asset_location.clone(), ether_location.clone()];
			let who = T::AccountIdConverter::convert_location(&origin)
				.ok_or(Error::<T>::LocationConversionFailed)?;

			let ether_gained = T::Swap::swap_exact_tokens_for_tokens(
				who.clone(),
				swap_path,
				tip_amount,
				None, // No minimum amount required
				who,
				true,
			)?;

			// Burn the ether
			let ether_asset = Asset::from((ether_location.clone(), ether_gained));

			burn_for_teleport::<T::AssetTransactor>(&origin, &ether_asset)
				.map_err(|_| Error::<T>::BurnError)?;

			Ok(ether_gained)
		}
