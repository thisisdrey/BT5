### Title
Signature-malleability duplicate-weight bypass in `ValidateMultiSign` precompile lets a single key satisfy a multisig threshold - ([File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java])

### Summary
The CVE describes an authentication bypass caused by a verification loop that mishandles a chain of repeated/duplicate entries (many intermediates), letting an attacker satisfy a check that should require independent trust anchors. The closest reachable analog in java-tron is the `ValidateMultiSign` TVM precompile's signature-aggregation loop, which can be tricked into counting the *same* authorized key's weight more than once by supplying multiple distinct (malleable) ECDSA byte-encodings that all recover to the same address, letting a caller reach a permission's weight threshold with fewer real distinct signers than intended.

### Finding Description
`ValidateMultiSign.execute` iterates over an attacker-supplied array of raw signature bytes (max 5), recovers an address for each, and is only supposed to add a key's weight once per unique signer: [1](#0-0) 

The de-duplication logic tracks previously-seen `(address, exact-signature-bytes)` pairs via `ByteArray.matrixContains`. If the recovered address was already seen but the *exact signature bytes* differ, the code only calls `MUtil.checkCPUTime()` and falls through to add the key's weight **again**, instead of rejecting/skip. Because ECDSA is malleable (a signature `(r, s)` and `(r, n-s)` with an adjusted recovery id `v` both verify and recover the same address), a caller can submit two or more distinct signature encodings produced from a single private key. Each one increases `totalWeight` by the full weight of that one key, since the exact-bytes match fails and the loop does not `continue`.

This mirrors the CVE-2017-14032 bug class exactly: a verification routine intended to require multiple independent trust anchors (multiple distinct authorized keys / certificates) can be satisfied by repeating a single trusted identity in different byte forms, because the loop's duplicate-detection is keyed on the wrong granularity (exact bytes rather than logical identity), allowing bypass of the intended threshold.

`TransactionCapsule.checkWeight`, used for top-level transaction signature verification, defends against this by keying its de-duplication map on the recovered `address` (post fork `VERSION_4_7_1`) rather than the raw signature bytes: [2](#0-1) 
but the TVM-reachable `ValidateMultiSign` precompile does not apply the same address-keyed uniqueness guarantee — it only skips when both address *and* the specific signature bytes match: [3](#0-2) 

### Impact Explanation
`ValidateMultiSign` is a public TVM precompile (address `0x0…09` family) directly reachable by any smart-contract call (`address.validatemultisign(...)` style ABI). Contracts that use this precompile to gate privileged operations (custody/escrow release, multisig wallet approvals, DAO/committee-style authorization implemented on-chain) rely on it to enforce that a threshold of *independent* keys approved an action. If a single compromised or colluding key can synthesize multiple malleable signatures to satisfy the threshold alone, this is a concrete unauthorized-operation / theft-of-funds primitive for any contract built on top of `ValidateMultiSign`, i.e. a single signer can impersonate a quorum.

### Likelihood Explanation
Exploitation only requires: (1) a target account/permission with `threshold` reachable by summing one key's weight multiple times (e.g., weight 2, threshold 2, with only one authorized key that has weight ≥ threshold/2, or weight 1 key repeated ≥2 times to reach threshold 2), and (2) the ability to derive a second valid, malleable signature from the same private key over the same message hash (trivial: negate `s` mod curve order and flip `v`). No special privileges, no consensus/node control needed — a normal contract-calling account can trigger this via any contract invoking the precompile. This is fully within the "unprivileged transaction broadcaster / contract deployer" reach specified by the scan rules.

### Recommendation
In `ValidateMultiSign.execute` (and equally review `BatchValidateSign`), change the duplicate-detection to be keyed solely by the recovered `address` (as `TransactionCapsule.checkWeight` does post-fork), rejecting or skipping weight-accrual whenever an address has already contributed weight regardless of the specific signature bytes supplied for it. Concretely: maintain a `Set<address>` of already-credited signers and refuse to add weight again for a repeated address, independent of whether the raw signature bytes differ.

### Proof of Concept
1. Create/permission an account with an `Active` permission containing a single key `K` with `weight = 1` and `threshold = 2` (multi-sign enabled).
2. Compute `hash = sha256(address || permissionId || data)` as required by `ValidateMultiSign`'s ABI.
3. Using `K`'s private key, produce signature `sig1 = sign(hash)` and derive a malleable variant `sig2` by substituting `s' = n - s` and flipping the recovery id `v` (both are valid ECDSA signatures for `hash` recoverable to the same address `K`).
4. Call the TVM precompile with `signatures = [sig1, sig2]`.
5. Observe: `recoverAddrBySign` returns `K`'s address for both; the first call adds `weight=1`; the second call finds `matrixContains(executedSignList, recoveredAddr)==true` but `matrixContains(executedSignList, sign)==false` (different bytes), so it does **not** `continue` and adds `weight=1` again. `totalWeight` becomes `2 >= threshold(2)`, and the precompile returns "true" (`dataOne()`) despite only one real signer having ever approved.
