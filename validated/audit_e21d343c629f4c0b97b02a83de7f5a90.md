### Title
Unbounded array-length parameter in TVM precompiled-contract ABI decoders leads to OOM/crash - ([File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java])

### Summary
`PrecompiledContracts.extractBytes32Array`, `extractBytesArray`, and `extractSigArray` read an array-length value directly from attacker-controlled EVM calldata and use it, unbounded, to allocate a Java array (`new byte[len][]`). Unlike other precompiles in the same file (e.g. `ModExp`, which enforces `UPPER_BOUND = 1024` on `baseLen/expLen/modLen`), these helpers impose no upper bound on `len` before allocation. This mirrors the root cause of CVE-2025-0838 in Abseil: a caller-supplied size value is used to size a backing store without an upper-bound check, enabling an oversized/overflowing allocation.

`len` comes directly from a `DataWord` decoded out of the precompile call's `data` payload — i.e., fully attacker-controlled ABI-encoded input supplied by whoever calls the precompiled contract from a TVM `CALL`. `intValueSafe()` on `DataWord` clamps/converts a 256-bit word to a Java `int`, but nothing in these three helper methods further bounds `len` to a sane size relative to the actual `data` array length. Contrast this with the `ModExp` precompile in the same file, which explicitly validates `baseLen`, `expLen`, and `modLen` against an `UPPER_BOUND` before use: [2](#0-1) 

No equivalent bound exists for `extractBytes32Array`/`extractBytesArray`/`extractSigArray`. A caller can therefore supply a `len` close to `Integer.MAX_VALUE`, which is used directly as the size of a newly allocated `byte[][]`, requesting the JVM to allocate an array of object references sized to `len * 8` bytes (roughly) before any subsequent bounds checking against `data.length` occurs in the loop body.

### Impact Explanation
Allocating a `byte[len][]` with an attacker-chosen `len` near `Integer.MAX_VALUE` (or any value large enough to exceed available heap) throws `OutOfMemoryError` inside TVM execution triggered by a normal, non-privileged smart-contract call to the precompiled contract that uses one of these decoders. Because block/transaction validation in java-tron runs this precompile logic as part of ordinary transaction execution (any full node/witness executing the block), a crafted transaction can cause the executing node to throw an unhandled `OutOfMemoryError`/allocate excessive memory, resulting in a node crash or halt during block processing — matching the "node crash or halt" impact class permitted by the rules. This is directly analogous to the Abseil CVE where an unvalidated size argument led to an oversized allocation/overflow.

### Likelihood Explanation
Reachability requires only that a contract can invoke the specific precompiled-contract address(es) that route calldata into `extractBytes32Array`/`extractBytesArray`/`extractSigArray` (these are internal helpers used by one or more `PrecompiledContract.execute()` implementations in the same file, confirmed by additional call sites inside `PrecompiledContracts.java`). Any account that can deploy or call a contract performing a `CALL`/`STATICCALL` to that precompile address with crafted calldata can trigger the path. I was not able to fully enumerate, within the available index, exactly which precompile(s) call each helper or to confirm `intValueSafe()`'s exact clamping behavior for negative/overflowing 256-bit inputs — this should be verified against the full source before treating the likelihood as certain. If `intValueSafe()` already clamps to a small/safe range (e.g., always non-negative and bounded by `Integer.MAX_VALUE` only), the allocation-size risk described above still holds since no additional application-level cap is applied in these three methods.

### Recommendation
Add an explicit upper bound (analogous to `ModExp.UPPER_BOUND`) on `len` in `extractBytes32Array`, `extractBytesArray`, and `extractSigArray` before allocating the output array — e.g., reject/short-circuit if `len` is negative or exceeds what is structurally possible given `data.length`/`words.length` (each array element requires at least one additional 32-byte word), mirroring the fix direction taken upstream in Abseil (impose an upper bound on the size argument prior to computing/allocating the backing store).

### Proof of Concept
1. Identify the precompiled-contract address in java-tron that dispatches into `extractBytesArray`/`extractSigArray`/`extractBytes32Array` (call sites exist elsewhere in `PrecompiledContracts.java` beyond the definitions shown).
2. Deploy a trivial contract that performs a low-level `CALL` (or have a broadcast transaction directly target the precompile address) with ABI-encoded calldata where the length word at the expected `offset` is set to a very large value (e.g., `0x7fffffff`).
3. Submit the transaction; when the node executes it, `extract*Array` allocates `new byte[len][]` with the attacker-supplied `len`, causing excessive memory allocation / `OutOfMemoryError` during transaction execution on every node that processes the block, resulting in a crash or degraded availability.

Note: I could not confirm from the indexed code alone (a) the exact precompile address(es)/opcode dispatch that reach each helper, or (b) the precise numeric behavior of `DataWord.intValueSafe()` for out-of-range inputs. A Devin session with full repository access should verify these two points to finalize severity/exploitability before remediation.
