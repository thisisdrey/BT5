### Title
FetchIntoObjectPool fetches objects from an arbitrary, unrelated "origin" repository into an object pool without verifying membership - (File: internal/gitaly/service/objectpool/fetch_into_object_pool.go)

### Summary
`FetchIntoObjectPool` performs an unconditional local `git fetch` of the `Origin` repository into the target `ObjectPool` repository. The only check applied to `Origin` is that it resides on the same storage as the pool ` [1](#0-0) `; there is no verification that `Origin` is actually a member of (i.e. linked to / created from) the target pool, unlike the general design intent described in the docs that housekeeping/fetch is "typically only executed with the original object pool member from which the pool has been seeded" ` [2](#0-1) `.

### Finding Description
This is the same class of bug as the reported analog: a privileged/state-changing operation (pulling data from a caller-supplied source into a shared, deduplicated store) is gated by a consistency/relationship check in one code path but not in the sibling path that performs the actual write.

- `LinkRepositoryToObjectPool` establishes the pool-membership relationship by writing the repository's `objects/info/alternates` file to point at the pool ` [3](#0-2) `, and `objectpool.FromRepo` / `linkedToRepository` are the mechanisms that determine and validate this membership relationship by reading `alternates` ` [4](#0-3) `, ` [5](#0-4) `.
- `FetchIntoObjectPool`, however, never consults this alternates-based membership relationship for the `Origin` parameter. It only validates that the pool itself is a legitimate object pool via `objectpool.FromProto` ` [6](#0-5) `, and validates `Origin` merely by checking it shares the same storage name as the pool ` [7](#0-6) `. It then directly executes `objectPool.FetchFromOrigin(ctx, origin, ...)`, which does a local `git fetch <originPath> "+refs/*:refs/remotes/origin/*"` from `Origin` into the pool with no membership check ` [8](#0-7) `.

Because Gitaly's `ObjectPoolService` is invoked directly by Rails/GitLab-Workhorse on behalf of end-user operations (e.g., during fork housekeeping), and `Origin`/`ObjectPool` are caller-supplied repository identifiers validated only for path well-formedness and matching storage name, an attacker capable of triggering this RPC (or a confused/compromised caller) can request a fetch from any repository on the same storage into any object pool they can reference, without that origin repository ever having been linked to (i.e., being a genuine member of) that pool.

### Impact Explanation
Successfully fetching an unrelated repository's refs/objects into an object pool causes **cross-repository object exposure**: any objects pulled into the pool become available via git's alternates mechanism to *every other repository already linked to that pool* (since alternates act as a search path for objects). This can leak private/proprietary commit content, blobs, or trees from `Origin` into repositories that never had a relationship to it, and it can corrupt the pool's intended 1:1 relationship with its member repositories (documented invariant that only the "original object pool member" should fetch into the pool). This mirrors the medium-severity impact of the referenced report: privileged data flow is executed based on caller-supplied identifiers without validating the required relationship/state that the surrounding design assumes is enforced.

### Likelihood Explanation
Reachability requires only the ability to invoke the `ObjectPoolService/FetchIntoObjectPool` RPC with attacker-influenced `Origin` and `ObjectPool` fields — no privileged administrative access, no hook bypass, and no leaked token is needed beyond what is already required to call this RPC in normal fork/housekeeping flows. The only gating check (`GetStorageName()` equality) is trivially satisfiable in any single-storage deployment, and multi-tenant deployments frequently share a storage across many customers/projects, so likelihood is not negligible.

### Recommendation
Before calling `objectPool.FetchFromOrigin`, verify that `Origin` is genuinely linked to `ObjectPool` — e.g., by deriving the pool from the origin repository's `objects/info/alternates` via `objectpool.FromRepo` (as already used elsewhere, ` [9](#0-8) `) and asserting that the resulting pool identity matches `req.GetObjectPool()`, rejecting the RPC with `FailedPrecondition`/`InvalidArgument` if `Origin` is not a member of the specified pool.

### Proof of Concept
1. Create repository `A` and object pool `P1` seeded from `A` (`CreateObjectPool`); link `A` to `P1` via `LinkRepositoryToObjectPool`.
2. Create an unrelated repository `B` on the same storage (never linked to `P1`, containing private commits).
3. Call `FetchIntoObjectPool` with `{ Origin: B, ObjectPool: P1 }`. `validateFetchIntoObjectPoolRequest` only checks that `B` and `P1` share the same `StorageName` — this passes.
4. `objectPool.FetchFromOrigin` performs `git fetch <path-to-B> "+refs/*:refs/remotes/origin/*"` directly into `P1`'s object database.
5. Any repository already linked to `P1` (a pool member other than `B`) can now resolve/read `B`'s objects via the `objects/info/alternates` mechanism, e.g., via `IsAncestor`/`GetBlob`/`GetCommit`-style RPCs referencing `B`'s object IDs, despite never having a relationship with `B`.

```go
func validateFetchIntoObjectPoolRequest(req *gitalypb.FetchIntoObjectPoolRequest) error {
	if req.GetOrigin() == nil {
		return errors.New("origin is empty")
	}

	if req.GetObjectPool() == nil {
		return errors.New("object pool is empty")
	}

	originRepository, poolRepository := req.GetOrigin(), req.GetObjectPool().GetRepository()

	if originRepository.GetStorageName() != poolRepository.GetStorageName() {
		return errors.New("origin has different storage than object pool")
	}

	return nil
```

```go
// linkedToRepository tests if a repository is linked to an object pool
func linkedToRepository(ctx context.Context, pool, repo *localrepo.Repo) (bool, error) {
	poolPath, err := pool.Path(ctx)
	if err != nil {
		return false, fmt.Errorf("getting object pool path: %w", err)
	}

	repoPath, err := repo.Path(ctx)
	if err != nil {
		return false, fmt.Errorf("getting repo path: %w", err)
	}

	altInfo, err := stats.AlternatesInfoForRepository(repoPath)
	if err != nil {
		return false, fmt.Errorf("getting alternates info: %w", err)
	}

	if !altInfo.Exists || len(altInfo.ObjectDirectories) == 0 {
		return false, nil
	}

	relPath := altInfo.ObjectDirectories[0]
	expectedRelPath, err := getRelativeObjectPath(ctx, pool, repo)
	if err != nil {
		return false, err
	}

	if relPath == expectedRelPath {
		return true, nil
	}

	if filepath.Clean(relPath) != filepath.Join(poolPath, "objects") {
		return false, fmt.Errorf("unexpected alternates content: %q", relPath)
	}

	return false, nil
```

```go
// FromRepo returns an instance of ObjectPool that the repository points to
func FromRepo(
	ctx context.Context,
	logger log.Logger,
	locator storage.Locator,
	gitCmdFactory gitcmd.CommandFactory,
	catfileCache catfile.Cache,
	txManager transaction.Manager,
	housekeepingManager housekeepingmgr.Manager,
	repo *localrepo.Repo,
) (*ObjectPool, error) {
	storagePath, err := locator.GetStorageByName(ctx, repo.GetStorageName())
	if err != nil {
		return nil, err
	}

	repoPath, err := repo.Path(ctx)
	if err != nil {
		return nil, err
	}

	altInfo, err := stats.AlternatesInfoForRepository(repoPath)
	if err != nil {
		return nil, fmt.Errorf("getting alternates info: %w", err)
	}

	if !altInfo.Exists || len(altInfo.ObjectDirectories) == 0 {
		return nil, ErrAlternateObjectDirNotExist
	}

	absolutePoolObjectDirPath := altInfo.AbsoluteObjectDirectories()[0]
	relativePoolObjectDirPath, err := filepath.Rel(storagePath, absolutePoolObjectDirPath)
	if err != nil {
		return nil, err
	}

	objectPoolProto := &gitalypb.ObjectPool{
		Repository: &gitalypb.Repository{
			StorageName:  repo.GetStorageName(),
			RelativePath: filepath.Dir(relativePoolObjectDirPath),
		},
	}

	if locator.ValidateRepository(ctx, objectPoolProto.GetRepository()) != nil {
		return nil, ErrInvalidPoolRepository
	}

	return FromProto(ctx, logger, locator, gitCmdFactory, catfileCache, txManager, housekeepingManager, objectPoolProto)
```

```go
// FetchFromOrigin initializes the pool and fetches the objects from its origin repository
func (o *ObjectPool) FetchFromOrigin(ctx context.Context, origin *localrepo.Repo, newLocalRepo LocalRepoFactory) error {
	if !o.Exists(ctx) {
		return structerr.NewInvalidArgument("object pool does not exist")
	}

	originPath, err := origin.Path(ctx)
	if err != nil {
		return fmt.Errorf("computing origin repo's path: %w", err)
	}

	if err := o.housekeepingManager.CleanStaleData(ctx, o.Repo, housekeeping.DefaultStaleDataCleanup()); err != nil {
		return fmt.Errorf("cleaning stale data: %w", err)
	}

	if err := o.logStats(ctx, "before fetch"); err != nil {
		return fmt.Errorf("computing stats before fetch: %w", err)
	}

	// Ideally we wouldn't want to prune old references at all so that we can keep alive all
	// objects without having to create loads of dangling references. But unfortunately keeping
	// around old refs can lead to D/F conflicts between old references that have since
	// been deleted in the pool and new references that have been added in the pool member we're
	// fetching from. E.g. if we have the old reference `refs/heads/branch` and the pool member
	// has replaced that since with a new reference `refs/heads/branch/conflict` then
	// the fetch would now always fail because of that conflict.
	//
	// Due to the lack of an alternative to resolve that conflict we are thus forced to enable
	// pruning. This isn't too bad given that we know to keep alive the old objects via dangling
	// refs anyway, but I'd sleep easier if we didn't have to do this.
	//
	// Note that we need to perform the pruning separately from the fetch: if the fetch is using
	// `--atomic` and `--prune` together then it still wouldn't be able to recover from the D/F
	// conflict. So we first to a preliminary prune that only prunes refs without fetching
	// objects yet to avoid that scenario.
	if err := o.pruneReferences(ctx, origin); err != nil {
		return fmt.Errorf("pruning references: %w", err)
	}

	objectHash, err := o.Repo.ObjectHash(ctx)
	if err != nil {
		return fmt.Errorf("detecting object hash: %w", err)
	}

	var stderr bytes.Buffer
	if err := o.Repo.ExecAndWait(ctx,
		gitcmd.Command{
			Name: "fetch",
			Flags: []gitcmd.Option{
				gitcmd.Flag{Name: "--quiet"},
				gitcmd.Flag{Name: "--atomic"},
				// We already fetch tags via our refspec, so we don't
				// want to fetch them a second time via Git's default
				// tag refspec.
				gitcmd.Flag{Name: "--no-tags"},
				// We don't need FETCH_HEAD, and it can potentially be hundreds of
				// megabytes when doing a mirror-sync of repos with huge numbers of
				// references.
				gitcmd.Flag{Name: "--no-write-fetch-head"},
				// Disable showing forced updates, which may take a considerable
				// amount of time to compute. We don't display any output anyway,
				// which makes this computation kind of moot.
				gitcmd.Flag{Name: "--no-show-forced-updates"},
			},
			Args: []string{originPath, objectPoolRefspec},
		},
		gitcmd.WithRefTxHook(objectHash, o.Repo),
		gitcmd.WithStderr(&stderr),
		gitcmd.WithConfig(gitcmd.ConfigPair{
			// Git is so kind to point out that we asked it to not show forced updates
			// by default, so we need to ask it not to do that.
			Key: "advice.fetchShowForcedUpdates", Value: "false",
		}),
	); err != nil {
		return fmt.Errorf("fetch into object pool: %w, stderr: %q", err,
			stderr.String())
	}
```
