### Title
Underwater positions can become permanently unliquidatable when the debt floor and collateral-seizure bounds conflict - ([File: contracts/Pool.sol])

### Summary
`Pool.liquidate()` can enter an unsatisfiable state for a severely undercollateralized account: every liquidation small enough to satisfy `maxLiquidable` leaves positive debt, every liquidation that leaves nonzero debt below `debtFloorInUsd` reverts, and every liquidation large enough to clear the floor requires more collateral than the account owns. The result is a permanently unliquidatable bad-debt position.

### Finding Description
The liquidation path performs three competing checks:

1. `amountToRepay_.wadDiv(_debtTokenBalance) > maxLiquidable` rejects repayments above the configured liquidation fraction.
2. When `debtFloorInUsd > 0`, a liquidation that leaves `_debtTokenBalance - amountToRepay_` with a positive USD value below the floor reverts with `RemainingDebtIsLowerThanTheFloor`.
3. `quoteLiquidateOut()` computes the collateral to seize, and `_totalSeized > depositToken_.balanceOf(account_)` reverts with `AmountIsTooHigh`.

For an underwater account, let:

- `D` be the account's debt balance,
- `B` be the account's collateral balance,
- `F` be `debtFloorInUsd`,
- `p` be the synth-to-collateral liquidation quote, including fees and incentive,
- `m` be `maxLiquidable`.

The liquidation must satisfy:

```text
A <= m * D
A = D || (D - A) * synthUsdPrice >= F
A * p <= B
```

If the collateral is insufficient to cover the smallest repayment that leaves at least `F` debt, and also insufficient to repay all debt, no value of `A` satisfies all conditions. The existing test suite already demonstrates both halves of the failure independently: a full repayment reverts as `AmountIsTooHigh` for an underwater account, while a partial repayment that drops below the configured floor reverts as `RemainingDebtIsLowerThanTheFloor`.

Because liquidation is the only protocol path that burns another account's debt and seizes its collateral, the bad debt cannot be cleared through the public liquidation mechanism.

### Impact Explanation
A severely underwater account can remain permanently unhealthy and unliquidatable. Neither partial liquidation nor full liquidation can succeed:

- Partial liquidation either violates `maxLiquidable`, leaves debt below `debtFloorInUsd`, or both.
- Full repayment avoids the floor check only by reducing debt to zero, but it requires seizing more collateral than the borrower owns and reverts as `AmountIsTooHigh`.

This leaves bad debt in the protocol indefinitely and breaks the liquidation/liveness invariant. Other users bear the resulting insolvency because debt remains recorded while its collateral backing cannot be collected through `liquidate()`.

### Likelihood Explanation
The issue requires an underwater position whose collateral is below the amount needed to reduce debt to at least the configured floor, plus liquidation fees/incentive. This can arise from collateral-price declines, debt-interest accrual, sharp synthetic-collateral price movement, or a liquidation cap below 100%. No privileged call is needed to trigger the failed liquidation: any liquidator can call `Pool.liquidate()` and hit the contradiction.

The deployed impact depends on the live `debtFloorInUsd` and `maxLiquidable` values and whether sufficiently underwater positions exist. The code makes the state possible because the bad-debt path intentionally supports partial liquidation when collateral is worth less than debt, but the debt-floor check was added without an exception for bad-debt cleanup.

### Recommendation
Handle bad-debt liquidation before enforcing the debt floor. For example:

- Skip `RemainingDebtIsLowerThanTheFloor` when the requested liquidation is the maximum collateral-covered repayment.
- Add a dedicated bad-debt liquidation path that permits seizing the account's full collateral balance and burning the corresponding debt, even when residual debt remains below the floor.
- Compute the maximum repayable amount from collateral and floor constraints atomically, rather than rejecting all candidates independently.
- Consider allowing liquidators to repay the amount that exactly seizes `depositToken_.balanceOf(account_)`, even if that leaves residual bad debt for explicit socialization/write-off accounting.

The floor should constrain normal partial liquidations, not make the final available collateral unrecoverable.

### Proof of Concept
A Foundry fork test can reproduce the contradiction by placing an account into the undercollateralized regime and then trying both boundary liquidations.

```solidity
// test/fork/PoolBadDebtDoS.t.sol
// SPDX-License-Identifier: MIT
pragma solidity 0.8.24;

import "forge-std/Test.sol";

interface IPool {
    function liquidate(
        address syntheticToken,
        address account,
        uint256 amountToRepay,
        address depositToken
    ) external returns (uint256, uint256, uint256);

    function quoteLiquidateMax(
        address syntheticToken,
        address account,
        address depositToken
    ) external view returns (uint256);

    function debtPositionOf(address account)
        external
        view
        returns (bool, uint256, uint256, uint256, uint256);
}

interface IDebtToken {
    function balanceOf(address account) external view returns (uint256);
}

interface IDepositToken {
    function balanceOf(address account) external view returns (uint256);
}

interface IPartialPriceOracle {
    function quoteTokenToUsd(address token, uint256 amount)
        external
        view
        returns (uint256);
}

contract PoolBadDebtDoSTest is Test {
    IPool pool;
    IDebtToken debtToken;
    IDepositToken depositToken;
    IPartialPriceOracle oracle;

    address syntheticToken;
    address victim;

    function testUnderwaterLiquidationHasNoValidRepayAmount() public {
        // Fork a supported deployment and initialize these addresses from
        // deployments/<chain>/Pool1_Proxy.json, the selected debt token,
        // the selected deposit token, and PoolRegistry.masterOracle().

        uint256 debt = debtToken.balanceOf(victim);
        uint256 collateral = depositToken.balanceOf(victim);
        assertGt(debt, 0);
        assertGt(collateral, 0);

        (bool healthy, uint256 depositUsd, uint256 debtUsd,,) =
            pool.debtPositionOf(victim);
        assertFalse(healthy);
        assertGt(debtUsd, depositUsd);

        // Repaying all debt requires more collateral than exists.
        vm.expectRevert(bytes4(keccak256("AmountIsTooHigh()")));
        pool.liquidate(syntheticToken, victim, debt, address(depositToken));

        // The maximum collateral-covered liquidation leaves residual debt.
        uint256 maxRepay =
            pool.quoteLiquidateMax(syntheticToken, victim, address(depositToken));
        assertGt(maxRepay, 0);
        assertLt(maxRepay, debt);

        uint256 residualDebt = debt - maxRepay;
        uint256 residualUsd =
            oracle.quoteTokenToUsd(syntheticToken, residualDebt);

        // On a fork where debtFloorInUsd > residualUsd, liquidation reverts.
        // The mock below can pin the exact quote while preserving the call shape.
        vm.mockCall(
            address(oracle),
            abi.encodeWithSelector(
                IPartialPriceOracle.quoteTokenToUsd.selector,
                syntheticToken,
                residualDebt
            ),
            abi.encode(uint256(1))
        );

        vm.expectRevert(
            bytes4(keccak256("RemainingDebtIsLowerThanTheFloor()"))
        );
        pool.liquidate(syntheticToken, victim, maxRepay, address(depositToken));
    }
}
```

The two reverts establish the invariant failure: the only repayment that avoids the debt-floor check exceeds available collateral, while the maximum collateral-covered repayment leaves forbidden residual debt.
