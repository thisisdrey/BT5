Audit Report

## Title
Integer-division rounding in `calculate_fee` can silently zero-out the Ethereum-side relayer reward for a "valid" `PricingParameters` set - (File: `bridges/snowbridge/pallets/outbound-queue/src/lib.rs`)

## Summary
`PricingParameters::validate()` only rejects individually zero-valued fields, but never checks the resulting `remote` fee after the decimal conversion performed in `calculate_fee`. Because `convert_from_ether_decimals` performs a truncating integer division, small (but individually non-zero) `fee_per_gas`/`rewards.remote` values relative to the ETH→native decimals gap collapse the computed `Fee.remote` to `0`, meaning a message can be accepted into the outbound queue while contributing nothing toward the Ethereum-side relayer reward.

## Finding Description
`PricingParameters::validate()` in `bridges/snowbridge/primitives/core/src/pricing.rs` only checks `exchange_rate`, `fee_per_gas`, `rewards.local`, `rewards.remote`, and `multiplier` for being non-zero individually: [1](#0-0) 

`Pallet::calculate_fee` computes the remote fee, converts to fixed point, and then calls `convert_from_ether_decimals`, which performs a `checked_div` (truncating integer division) by `10^(ETHER_DECIMALS - Decimals)`: [2](#0-1) 

This is directly reproduced by the pallet's own regression test, which asserts `fee.remote == 0` for a `PricingParameters` set that is fully "valid" per `validate()` (`fee_per_gas = 1`, `rewards.remote = 1`, `multiplier = 1`, `exchange_rate = 1`), with a comment acknowledging "the remote fee calculated here is invalid which should be avoided": [3](#0-2) 

`set_pricing_parameters` in `bridges/snowbridge/pallets/system/src/lib.rs` is the only gate on this stored data; it calls only `params.validate()` and never simulates `calculate_fee` to confirm the derived `remote` component stays non-zero: [4](#0-3) 

The public, permissionless `SendMessage::validate` entrypoint (used whenever a user routes an XCM message to Ethereum) reads the stored `PricingParameters` and calls `calculate_fee` without any additional floor/guard on the result: [5](#0-4) 

`do_process_message`/`commit` subsequently take `pricing_params.rewards.remote` from the same stored parameters to build the `CommittedMessage.reward` field sent to Ethereum — if the derived `Fee.remote` charged to the sender is zero while a nonzero `reward` is still promised on the Ethereum side (or vice versa depending on parameter combination), the value collected from the sender and the value promised to the relayer can diverge from what `calculate_fee` intends. [6](#0-5) 

## Impact Explanation
The corrupted value is the `remote` field of the `Fee<Balance>` struct returned by `calculate_fee`/`SendMessage::validate` — it can be silently rounded to `0` instead of rejected, even though every individual `PricingParameters` field passed `validate()` as non-zero. This does not itself let an unprivileged attacker steal funds or forge proofs; it depends on governance having set `PricingParameters` (via the privileged, root-only `set_pricing_parameters` extrinsic) such that the derived remote fee lands in the truncation range for the specific runtime's decimals configuration. Once such parameters are live, any unprivileged user calling the public `send`/`validate` path can enqueue messages that are accepted and committed with `Fee.remote == 0`, undercharging the Ethereum-side relayer reward. However, whether this is realistically reachable depends entirely on the concrete `PricingParameters` values configured on live BridgeHub runtimes (Rococo/Westend), and the parameter values referenced in the PoC (`fee_per_gas = 1`, `rewards.remote = 1`) are far below anything a rational governance body would configure for a chain with 10-12 decimals of precision — this makes the finding a real but low-probability arithmetic edge case rather than a readily-triggerable live vulnerability under realistic parameter ranges. I was unable to fully verify the exact production `PricingParameters` values configured in `bridge_to_ethereum_config.rs` for bridge-hub-rococo/westend due to tool-call limits, so I cannot confirm whether current live parameters are anywhere near the truncation boundary.

## Likelihood Explanation
Likelihood is low-to-moderate in practice: it requires governance to have set (or migrate to) a `PricingParameters` combination whose derived remote fee is small enough to truncate to zero under the runtime's specific decimals gap — this is a plausible misconfiguration risk (the pallet's own test demonstrates it with unrealistically minimal values), but is not something an unprivileged attacker can trigger unilaterally; they can only exploit it after such parameters already exist in storage. This weakens the "public underpriced work" framing, since the root cause requires a specific privileged parameter state to first exist, and the severity of the resulting economic impact (unrewarded but still-processed messages) is bounded by `MaxMessagesPerBlock` and does not create fund theft, forged proofs, or duplicate settlement.

## Recommendation
- Have `set_pricing_parameters` simulate `calculate_fee` (e.g., for `gas_used_at_most = 0` or the minimum expected gas) and reject the update if the resulting `Fee.remote == 0`, rather than relying solely on per-field non-zero checks in `validate()`.
- Alternatively, switch `convert_from_ether_decimals` to rounding-up division (`div_ceil`) so a non-zero pre-conversion value never truncates to exactly zero.

## Proof of Concept [3](#0-2) 

1. Governance calls `set_pricing_parameters` with `fee_per_gas = 1`, `rewards.remote = 1`, `multiplier = 1`, `exchange_rate = 1` — all individually non-zero, so `validate()` passes.
2. Any unprivileged user sends an XCM message routed to the Snowbridge exporter, invoking `SendMessage::validate` → `calculate_fee`.
3. `convert_from_ether_decimals`'s truncating division yields `fee.remote == 0`, as demonstrated by the existing unit test.
4. The message is queued/committed with a zero remote fee reserved, while the message is still processed on-chain.

		pub(crate) fn do_process_message(
			_: ProcessMessageOriginOf<T>,
			mut message: &[u8],
		) -> Result<bool, ProcessMessageError> {
			use ProcessMessageError::*;

			// Yield if the maximum number of messages has been processed this block.
			// This ensures that the weight of `on_finalize` has a known maximum bound.
			ensure!(
				MessageLeaves::<T>::decode_len().unwrap_or(0) <
					T::MaxMessagesPerBlock::get() as usize,
				Yield
			);

			// Decode bytes into versioned message
			let versioned_queued_message: VersionedQueuedMessage =
				VersionedQueuedMessage::decode(&mut message).map_err(|_| Corrupt)?;

			// Convert versioned message into latest supported message version
			let queued_message: QueuedMessage =
				versioned_queued_message.try_into().map_err(|_| Unsupported)?;

			// Obtain next nonce
			let nonce = <Nonce<T>>::try_mutate(
				queued_message.channel_id,
				|nonce| -> Result<u64, ProcessMessageError> {
					*nonce = nonce.checked_add(1).ok_or(Unsupported)?;
					Ok(*nonce)
				},
			)?;

			let pricing_params = T::PricingParameters::get();
			let command = queued_message.command.index();
			let params = queued_message.command.abi_encode();
			let max_dispatch_gas =
				T::GasMeter::maximum_dispatch_gas_used_at_most(&queued_message.command);
			let reward = pricing_params.rewards.remote;

			// Construct the final committed message
			let message = CommittedMessage {
				channel_id: queued_message.channel_id,
				nonce,
				command,
				params,
				max_dispatch_gas,
				max_fee_per_gas: pricing_params
					.fee_per_gas
					.try_into()
					.defensive_unwrap_or(u128::MAX),
				reward: reward.try_into().defensive_unwrap_or(u128::MAX),
				id: queued_message.id,
			};

			// ABI-encode and hash the prepared message
			let message_abi_encoded = ethabi::encode(&[message.clone().into()]);
			let message_abi_encoded_hash = <T as Config>::Hashing::hash(&message_abi_encoded);

			Messages::<T>::append(Box::new(message));
			MessageLeaves::<T>::append(message_abi_encoded_hash);

			Self::deposit_event(Event::MessageAccepted { id: queued_message.id, nonce });

			Ok(true)
		}

		/// Calculate total fee in native currency to cover all costs of delivering a message to the
		/// remote destination. See module-level documentation for more details.
		pub(crate) fn calculate_fee(
			gas_used_at_most: u64,
			params: PricingParameters<T::Balance>,
		) -> Fee<T::Balance> {
			// Remote fee in ether
			let fee = Self::calculate_remote_fee(
				gas_used_at_most,
				params.fee_per_gas,
				params.rewards.remote,
			);

			// downcast to u128
			let fee: u128 = fee.try_into().defensive_unwrap_or(u128::MAX);

			// multiply by multiplier and convert to local currency
			let fee = FixedU128::from_inner(fee)
				.saturating_mul(params.multiplier)
				.checked_div(&params.exchange_rate)
				.expect("exchange rate is not zero; qed")
				.into_inner();

			// adjust fixed point to match local currency
			let fee = Self::convert_from_ether_decimals(fee);

			Fee::from((Self::calculate_local_fee(), fee))
		}

		/// Calculate fee in remote currency for dispatching a message on Ethereum
		pub(crate) fn calculate_remote_fee(
			gas_used_at_most: u64,
			fee_per_gas: U256,
			reward: U256,
		) -> U256 {
			fee_per_gas.saturating_mul(gas_used_at_most.into()).saturating_add(reward)
		}

		/// The local component of the message processing fees in native currency
		pub(crate) fn calculate_local_fee() -> T::Balance {
			T::WeightToFee::weight_to_fee(
				&T::WeightInfo::do_process_message().saturating_add(T::WeightInfo::commit_single()),
			)
		}

		// 1 DOT has 10 digits of precision
		// 1 KSM has 12 digits of precision
		// 1 ETH has 18 digits of precision
		pub(crate) fn convert_from_ether_decimals(value: u128) -> T::Balance {
			let decimals = ETHER_DECIMALS.saturating_sub(T::Decimals::get()) as u32;
			let denom = 10u128.saturating_pow(decimals);
			value.checked_div(denom).expect("divisor is non-zero; qed").into()
		}

fn test_calculate_fees_with_valid_exchange_rate_but_remote_fee_calculated_as_zero() {
	new_tester().execute_with(|| {
		let gas_used: u64 = 250000;
		let price_params: PricingParameters<<Test as Config>::Balance> = PricingParameters {
			exchange_rate: FixedU128::from_rational(1, 1),
			fee_per_gas: 1_u32.into(),
			rewards: Rewards { local: 1_u32.into(), remote: 1_u32.into() },
			multiplier: FixedU128::from_rational(1, 1),
		};
		let fee = OutboundQueue::calculate_fee(gas_used, price_params.clone());
		assert_eq!(fee.local, 698000000);
		// Though none zero pricing params the remote fee calculated here is invalid
		// which should be avoided
		assert_eq!(fee.remote, 0);
	});
}

	fn validate(
		message: &Message,
	) -> Result<(Self::Ticket, Fee<<Self as SendMessageFeeProvider>::Balance>), SendError> {
		// The inner payload should not be too large
		let payload = message.command.abi_encode();
		ensure!(
			payload.len() < T::MaxMessagePayloadSize::get() as usize,
			SendError::MessageTooLarge
		);

		// Ensure there is a registered channel we can transmit this message on
		ensure!(T::Channels::contains(&message.channel_id), SendError::InvalidChannel);

		// Generate a unique message id unless one is provided
		let message_id: H256 = message
			.id
			.unwrap_or_else(|| unique((message.channel_id, &message.command)).into());

		let gas_used_at_most = T::GasMeter::maximum_gas_used_at_most(&message.command);
		let fee = Self::calculate_fee(gas_used_at_most, T::PricingParameters::get());

		let queued_message: VersionedQueuedMessage = QueuedMessage {
			id: message_id,
			channel_id: message.channel_id,
			command: message.command.clone(),
		}
		.into();
		// The whole message should not be too large
		let encoded = queued_message.encode().try_into().map_err(|_| SendError::MessageTooLarge)?;

		let ticket = Ticket { message_id, channel_id: message.channel_id, message: encoded };

		Ok((ticket, fee))
	}
