### Title
Expired CA certificates are added to the trust pool before the expiry check, leaving stale state in `CAPool.CAs` despite an error being returned - (File: `cert/ca_pool.go`)

### Summary
`CAPool.AddCA` writes the new CA into `ncp.CAs[sum]` before checking whether the certificate is expired, so callers who add an expired CA still get it inserted into the trust map even though `AddCA` returns `ErrExpired`. This mirrors the reported bug class: a value (collateral/fee accounting in the original report) is accumulated unconditionally before the operation that could invalidate it (a reverted transfer / an expired cert) is checked, so the failure path leaves partial, inconsistent state behind.

### Finding Description
`AddCA` performs the self-signature check, computes the fingerprint, builds a `CachedCertificate`, and unconditionally stores it into the pool map: [1](#0-0) 

The expiry check happens *after* the map write, on line 127-129. If the certificate is expired, the function returns `ErrExpired`, but `ncp.CAs[sum] = cc` at line 125 has already executed — the entry is not rolled back.

`NewCAPoolFromPEMReader` explicitly treats `ErrExpired` as a soft, ignorable condition and `continue`s the scan loop, under the apparent assumption that an expired CA was *not* added: [2](#0-1) 

In reality the CA was already committed to `ncp.CAs` before the function returned the error, so the "skip" is illusory from the state's perspective — only the caller's control flow skips it, the data does not roll back.

Downstream, `verify()` re-checks `signer.Certificate.Expired(now)` at verification time and returns `ErrRootExpired` if the stored CA is expired, so leaf-certificate verification is not silently bypassed today: [3](#0-2) 

However, this defense-in-depth check is the *only* thing preventing exploitation — the root cause (committing state for an operation that later reports failure) is present exactly as described in the external report, and any code path that trusts `CAPool.CAs` membership directly (e.g., iterating `ncp.CAs` for UI/config display, counting trusted CAs, or any future code that treats presence in the map as "this CA was successfully added") would be poisoned by an entry that should not exist per the function's own contract.

### Impact Explanation
Today, the only user-visible effect is that `len(ncp.CAs)` / iteration over the CA pool includes CAs that `AddCA` reported as rejected (expired), which is a state-consistency/API-contract violation, not by itself a break of certificate verification (that is caught by the redundant `Expired(now)` check inside `verify`). If any consumer of `CAPool` (current or future) relies on map membership as a proxy for "successfully added and currently trusted," rather than always re-deriving trust via `verify`, that consumer would incorrectly trust or count an expired CA. This is a remote state poisoning class bug rooted in the same "accumulate before checking success" pattern as the external report, but its current exploitability is limited by a working secondary revert check elsewhere.

### Likelihood Explanation
Reaching this code requires only supplying an expired CA certificate to `AddCA`/`AddCAFromPEM`/`NewCAPoolFromPEMReader` (i.e., loading a CA bundle with an expired cert), which is a normal, remotely-influenceable configuration/PKI-bundle-loading path (no valid-certificate-holder or malicious-peer prerequisite beyond supplying/rotating CA material). The bug always triggers on any expired-CA input; it's deterministic, not a race.

### Recommendation
Move the expiry check in `AddCA` before the `ncp.CAs[sum] = cc` assignment, so an expired CA is never inserted into the pool when `ErrExpired` is returned — mirroring the audit recommendation to not accumulate state (`tv`/`tvw` in the original report) when the guarded operation is going to be rejected. Concretely: check `c.Expired(time.Now())` immediately after fingerprinting and return `ErrExpired` before constructing/storing `cc`, or only perform the assignment after the expiry check succeeds.

### Proof of Concept
1. Construct a self-signed CA certificate (`IsCA() == true`, valid self-signature) whose `NotAfter` is in the past.
2. Call `pool := cert.NewCAPool(); err := pool.AddCA(expiredCA)`.
3. Observe `err == cert.ErrExpired`, but `pool.CAs[fingerprint]` is non-nil and present — the CA was inserted despite the reported failure.
4. Equivalent effect via `cert.NewCAPoolFromPEMReader` with a bundle containing only an expired CA: the returned `pool.CAs` map still contains the expired CA entry even though the reader treats `ErrExpired` as "skip and continue." [4](#0-3)

// AddCA verifies a Nebula CA certificate and adds it to the pool.
func (ncp *CAPool) AddCA(c Certificate) error {
	if !c.IsCA() {
		return fmt.Errorf("%s: %w", c.Name(), ErrNotCA)
	}

	if !c.CheckSignature(c.PublicKey()) {
		return fmt.Errorf("%s: %w", c.Name(), ErrNotSelfSigned)
	}

	sum, err := c.Fingerprint()
	if err != nil {
		return fmt.Errorf("could not calculate fingerprint for provided CA; error: %w; %s", err, c.Name())
	}

	cc := &CachedCertificate{
		Certificate:    c,
		Fingerprint:    sum,
		InvertedGroups: make(map[string]struct{}),
	}

	for _, g := range c.Groups() {
		cc.InvertedGroups[g] = struct{}{}
	}

	ncp.CAs[sum] = cc

	if c.Expired(time.Now()) {
		return fmt.Errorf("%s: %w", c.Name(), ErrExpired)
	}

	return nil
```

func (ncp *CAPool) verify(c Certificate, now time.Time, certFp string, signerFp string) (*CachedCertificate, error) {
	if ncp.IsBlocklisted(certFp) {
		return nil, ErrBlockListed
	}

	signer, err := ncp.GetCAForCert(c)
	if err != nil {
		return nil, err
	}

	if signer.Certificate.Curve() != c.Curve() {
		return nil, ErrCurveMismatch
	}

	if signer.Certificate.Expired(now) {
		return nil, ErrRootExpired
	}

	if c.Expired(now) {
		return nil, ErrExpired
	}
```
