### Title
`socialize-debt` computes bad-debt write-down using stale, un-accrued vault state - ([File: mainnet/contracts/vault/v0-vault-stx.clar])

### Summary
Every state-mutating vault entrypoint (`deposit`, `redeem`, `system-borrow`, `system-repay`) begins by calling `(try! (accrue))` to bring `index`/`lindex`/accrued interest up to date before doing any calculation. `socialize-debt` is the one exception: it reads `principal-scaled`, `total-borrowed`, `index`, `assets`, `lindex` and computes `old-total-assets` via `(total-assets)` directly from data-vars, without calling `accrue` first. This mirrors the reported bug class of "getting reserves before applying new rewards" — a downstream computation is performed on state that has not yet been brought current.

### Finding Description
In `mainnet/contracts/vault/v0-vault-stx.clar` (and the equivalent sBTC/stSTX/USDC/USDH/stSTXbtc vaults), `socialize-debt` is defined as: [1](#0-0) 

Unlike `system-repay`/`system-borrow`, which start their `let` bindings with `(u (try! (accrue)))` before reading `index`, `total-debt`, or `assets`: [2](#0-1) 

`socialize-debt` reads `idx`, `current-lindex`, `current-assets`, and `old-total-assets` (`(total-assets)` uses the cached `index`/`principal-scaled` to compute cumulative debt) with no preceding accrual call. If time has elapsed since the vault's `last-update`, `index` understates the true accrued debt, so `total-assets` (and hence `old-total-assets`) omits interest that has accrued but not yet been posted.

The caller in `market.clar`'s `socialize-debt-asset` confirms this is a known asymmetry: it calls `vault-socialize-debt` first, and only *afterward* refreshes the market's index cache by explicitly calling `vault-accrue`, with the comment "Refresh cache with new indexes post-write-down (lindex decreased)": [3](#0-2) 

Because the vault-side write-down ratio (`new-lindex`) is computed from `old-total-assets` before interest is accrued, the socialized-loss ratio applied to `lindex` is calculated against an understated total-assets base. `debt-reduction = scaled-amount * idx / INDEX-PRECISION` also uses the stale `idx`, further compounding the mismatch between the amount being written off (in market-vault's scaled-debt units, computed by the caller against the up-to-date cached index) and the amount the vault vault itself believes is being written off.

### Impact Explanation
`lindex` directly determines the exchange rate between vault shares (`zft`) and underlying assets for every supplier (`convert-to-assets-preview`/`convert-to-shares-preview` in the same vault use `total-assets`/`total-supply`, which depend on the liquidity index chain). A write-down computed against a stale, under-accrued `old-total-assets` produces an incorrect `new-lindex`, permanently distorting the share price used by all subsequent `deposit`/`redeem` calls. This causes suppliers to receive an incorrect (too high or too low) share of remaining vault assets after a bad-debt socialization event — a permanent misallocation/freezing of a portion of supplier funds, since the erroneous `lindex` is written to storage and never independently corrected. This lands in the "vault share math and interest accrual" / "socialize-debt" impact category explicitly in scope, and the resulting fund misallocation constitutes permanent freezing/loss of a portion of user funds at rest (High/Critical depending on the magnitude of unaccrued interest at socialization time).

### Likelihood Explanation
`socialize-debt` is only invoked from `market.clar`'s liquidation-driven bad-debt socialization path when a borrower has no collateral left; this is a normal, permissionless path triggered by an ordinary liquidator completing a liquidation that leaves bad debt (not a privileged/DAO action). The magnitude of the discrepancy scales with how much interest has accrued since the vault's `last-update` before socialization — for vaults with any nonzero time gap since the last accrual-triggering operation, the bug is deterministically triggered on every socialization event, making likelihood high.

### Recommendation
Call `(try! (accrue))` at the start of `socialize-debt`'s `let` bindings, exactly as done in `system-borrow`/`system-repay`, before reading `index`, `lindex`, `principal-scaled`, `total-borrowed`, or `assets`, so that `old-total-assets` and `debt-reduction` reflect fully accrued interest prior to computing the write-down ratio.

### Proof of Concept
1. Vault's `last-update` is set at time T0; no accrue-triggering call occurs afterward.
2. Time passes; unrealized interest accrues (vault's stored `index` is stale relative to `next-index`).
3. A borrower with debt in this vault becomes fully liquidated with remaining bad debt and no collateral; `market.clar`'s `liquidate` path calls `socialize-debt-asset`, which calls `vault-socialize-debt` (i.e., the vault's `socialize-debt`) directly, without first accruing the vault. [4](#0-3) 
4. `socialize-debt` computes `old-total-assets` from `(total-assets)`, which uses the pre-accrual `index`, omitting interest earned between T0 and the current block.
5. `new-lindex` is computed as `current-lindex * (old-total-assets - debt-reduction) / old-total-assets` using this understated `old-total-assets`, producing a `lindex` that does not correctly reflect the real loss ratio relative to true (accrued) total assets.
6. All subsequent `deposit`/`redeem` calls compute share conversions using this incorrect `lindex`, permanently mis-pricing supplier shares. [1](#0-0)

  (let ((scaled-principal (var-get principal-scaled))
        (borrowed (var-get total-borrowed))
        (idx (var-get index))
        (current-assets (var-get assets))
        (current-lindex (var-get lindex))
        (old-total-assets (total-assets))
        (debt-reduction (mul-div-down scaled-amount idx INDEX-PRECISION))
        (principal-reduction (if (> scaled-principal u0)
                                (mul-div-down scaled-amount borrowed scaled-principal)

        (new-lindex (if (and (> old-total-assets u0) (> old-total-assets debt-reduction))
