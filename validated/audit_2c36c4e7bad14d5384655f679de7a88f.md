### Title
Missing zero-address validation in `TransferToNewAccount`/`TransferToNewAccountPda` permanently locks migrated accounts and their funds - ([File: programs/marginfi/src/instructions/marginfi_account/transfer_account.rs])

### Summary
The `transfer_to_new_account` and `transfer_to_new_account_pda` instructions let an unprivileged marginfi account authority migrate all their lending positions to a brand-new `MarginfiAccount`, assigning it a caller-supplied `new_authority`. Neither instruction validates that `new_authority` is non-default (non-zero), matching the CoinFabrik "Ownable's `transferOwnership` fails silently" bug class where a missing `newOwner != 0x0` check let ownership silently transfer to an unrecoverable address.

### Finding Description
Both account structs mark `new_authority` explicitly as unchecked: [1](#0-0) [2](#0-1) 

The on-chain handlers `transfer_to_new_account` and `transfer_to_new_account_pda` pass `ctx.accounts.new_authority.key()` directly into `initialize_migrated_account` without any check against `Pubkey::default()`: [3](#0-2) [4](#0-3) 

Simultaneously, the old account is irreversibly disabled and marked as migrated to the new account, with no way to reverse the process: [5](#0-4) [6](#0-5) 

By contrast, the off-chain CLI client independently performs this exact check before submitting the same instruction, confirming the omission on-chain is a genuine gap rather than intentional design: [7](#0-6) 

Because `Pubkey::default()` (the all-zero pubkey) has no known private key, if `new_authority` is ever set to it — whether by a user's tooling bug, a malicious frontend, or an errant integrator building the instruction — the resulting new account becomes permanently uncontrollable by anyone, while the old account is disabled and cannot be recovered (`AccountAlreadyMigrated` blocks retry). The on-chain protocol relies solely on `is_signer_authorized`/`account_not_frozen_for_authority` constraints on the *old* account's current authority to gate the migration, and performs no sanity check on the *new* authority value itself.

### Impact Explanation
If `new_authority` is the zero pubkey, all lending/collateral positions moved into the new `MarginfiAccount` (deposits, borrows, isolated positions) become permanently frozen: no signer can ever satisfy the `authority` `has_one`/signer constraints used by every subsequent user-facing instruction (deposit, withdraw, borrow, repay, close, liquidate calls gated by account authority), since no keypair corresponds to the default pubkey. This is a permanent lock/freeze of user funds, not merely a "no impact" issue — meeting the bar of "permanent lock/freeze" required by the validation rules.

### Likelihood Explanation
The instruction is reachable by any account authority without special privileges — it is a normal user action (`transfer_to_new_account` / `transfer_to_new_account_pda`), not an admin-only path. `new_authority` is an `UncheckedAccount`, so any pubkey, including `Pubkey::default()`, passes account-level validation. This can occur via a buggy or malicious client/integrator (the marginfi test suite itself notes "WARN: User picks the new authority with no restrictions!"): [8](#0-7) 

The existence of a matching manual guard in the CLI confirms the developers recognized the risk but only enforced it client-side, which does not protect against direct instruction construction (e.g., via SDK, other CLIs, or a compromised frontend).

### Recommendation
Add an on-chain check analogous to `require(newOwner != 0x0)` in both `transfer_to_new_account` and `transfer_to_new_account_pda`, e.g.:
```rust
check!(
    ctx.accounts.new_authority.key() != Pubkey::default(),
    MarginfiError::InvalidAuthority // or a new dedicated error
);
```
placed before `initialize_migrated_account` is called in both handlers (`programs/marginfi/src/instructions/marginfi_account/transfer_account.rs`, lines ~91-99 and ~233-244), so the transfer instruction fails safely on-chain instead of silently creating a permanently inaccessible account.

### Proof of Concept
1. Attacker/careless integrator crafts a `TransferToNewAccount` (or `TransferToNewAccountPda`) instruction directly (bypassing the CLI's client-side check) with `new_authority = Pubkey::default()`.
2. The current account authority signs the transaction (this could be the victim themselves, tricked by a malicious dApp/frontend that fills in the zero address, or a bug in third-party tooling).
3. The instruction succeeds: `old_account` is disabled and its `migrated_to` set to `new_marginfi_account`; `new_account.authority` is set to `Pubkey::default()`.
4. All positions (deposits/collateral) are now owned by `new_account`, which requires a signer matching the default pubkey — impossible to produce.
5. Funds in `new_account` (and, since `old_account` is disabled, the entire position history) are permanently locked with no recovery path, since `AccountAlreadyMigrated` blocks any further migration of `old_account`.
