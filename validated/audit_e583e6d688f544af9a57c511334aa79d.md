### Title
Fee-charging in `pallet-outbound-queue::calculate_fee` can silently round the remote/relayer fee component to zero despite non-zero, validated `PricingParameters`, letting messages be delivered without covering the Ethereum-side gas refund and relayer reward - ([File: bridges/snowbridge/pallets/outbound-queue/src/lib.rs])

### Summary
`PricingParameters::validate()` [1](#0-0)  guards the *inputs* (`exchange_rate`, `fee_per_gas`, `rewards.local`, `rewards.remote`, `multiplier`) against being zero before `set_pricing_parameters` stores them [2](#0-1) . However, the *derived* fee that is actually charged to whoever sends an outbound message is computed later in `Pallet::calculate_fee`, and integer-division/decimal-rescaling there can produce a `remote` fee of exactly `0` even though every input parameter is non-zero — exactly mirroring the GMX bug class where an "impossible" (guarded-against) zero value still becomes reachable through a downstream code path that the guard doesn't cover.

### Finding Description
`calculate_fee` computes the Ether-denominated cost, converts it through `FixedU128`, and finally rescales from Ether's 18 decimals down to the local chain's currency decimals: [3](#0-2) 

The final step, `convert_from_ether_decimals`, does a plain integer division: [4](#0-3) 

Because `decimals = ETHER_DECIMALS (18) - T::Decimals` (e.g. 8 for DOT with 10 decimals, or 6 for KSM with 12 decimals), `denom` is `10^8` or `10^6`. Any wei-denominated intermediate value smaller than `denom` truncates to `0` in `checked_div`. The existing unit test in the repository itself documents this exact outcome with fully non-zero, `validate()`-passing pricing parameters: [5](#0-4) 

The test comment even states: *"Though none zero pricing params the remote fee calculated here is invalid which should be avoided"* — i.e. the maintainers are aware the guard in `validate()` does not prevent the derived charge from collapsing to zero.

This differs from the GMX report only in polarity: GMX's oracle *reverts* on zero and blocks a critical operation (liquidation) that must succeed; here the pipeline does the opposite — it *silently succeeds* with an effectively-zero charge for a component that is economically critical (the cost that is supposed to reimburse Ethereum-side relayers/gas). Both bugs share the same root cause: validating only the raw inputs is not sufficient once the invariant that matters ("this quantity must never be zero/must always be paid") is enforced several transformation steps downstream, where rounding/precision can defeat the check.

`calculate_fee`'s result becomes the fee actually withdrawn from the sender when delivering a message through the outbound queue (`OutboundQueue::validate`/`deliver`, used by `send_message_impl.rs` and by `EthereumBlobExporter`, which every parachain-originated XCM message to Ethereum goes through). If `fee.remote` (the local-currency equivalent of the Ethereum gas-refund + relayer-reward budget) rounds to zero, the message is still accepted, queued and eventually dispatched to the Gateway contract by `do_process_message`, which happily uses `pricing_params.rewards.remote` for the `reward` field committed to Ethereum [6](#0-5)  — meaning Ethereum-side relayers are still promised/paid a reward funded from the bridge's sovereign/treasury account, but the parachain side collected zero DOT/KSM to back that payout.

### Impact Explanation
This is public underpriced work with direct bridge-processing/economic impact:
- Any account able to send an outbound message (via XCM export to Ethereum, e.g. asset transfers) that falls into the parameter regime where `convert_from_ether_decimals` truncates to zero pays nothing for the remote/relayer-reward component of the fee, while the protocol still commits to reward relayers on the Ethereum side out of the bridge's own funds.
- Repeated exploitation (spamming messages under such parameters) drains the bridge's backing funds without matching fee collection — an unbacked-payout / value-non-conservation condition, directly matching the "theft or unbacked mint or unlock" / "public underpriced work that … stalls bridge processing" criteria in the impact gate.
- Unlike the GMX case (which needs a market crash to reach price zero), this requires no external price collapse — it is a pure arithmetic property of `calculate_fee`, reachable purely by choosing/hitting message-size/gas and pricing-parameter combinations, some of which are demonstrably reachable with realistic-looking values as the shipped test shows.

### Likelihood Explanation
The exact reproduction the codebase’s own test hits (`exchange_rate=1`, `fee_per_gas=1`, `rewards=1`, `gas_used=250000`) is somewhat contrived relative to the production constants used on Bridge Hub Rococo/Westend (`exchange_rate = 1/400`, `fee_per_gas = 20 gwei`, `rewards.remote = 1 milli-ether`) [7](#0-6) , so whether the truncation is trivially triggerable in the *current* live parameter set could not be fully confirmed from the index alone (would require recomputing `calculate_remote_fee`/`FixedU128` arithmetic against every `Command` variant's `max_dispatch_gas_used_at_most`). What is confirmed directly from repository evidence is that (a) the rounding-to-zero behavior exists in the shipped code, (b) it is reachable with fully-valid, `validate()`-passing `PricingParameters`, and (c) the project's own test explicitly flags it as an "invalid" result "which should be avoided," i.e. a known-but-unfixed gap between input validation and the actual invariant needed (non-zero delivered fee).

### Recommendation
- After computing `fee.remote` in `calculate_fee`, enforce a floor: reject or bump to a minimum non-zero value (e.g. `ensure!(!fee.remote.is_zero(), Error::FeeRoundedToZero)` or round up via `checked_div` with ceiling semantics) so messages can never be queued/dispatched while paying zero for the remote/reward component.
- Alternatively, validate at `set_pricing_parameters` time that for the pallet's realistic gas-usage range, `calculate_fee` never yields a zero `remote` component (i.e. validate the *derived* invariant, not just the raw parameters), similar to how the GMX escalation concluded oracles should never emit a price that collapses downstream calculations to a non-functional value.

### Proof of Concept
The existing repository test is itself the proof of concept, demonstrating the invariant break with parameters that pass `PricingParameters::validate()`: [5](#0-4) 
To weaponize this against the production parameter set, an attacker would need to identify a `Command`/message whose `max_dispatch_gas_used_at_most` (from `T::GasMeter`), combined with the live `PricingParameters`, drives the wei-denominated `calculate_remote_fee` output below the `10^(18 - T::Decimals)` truncation threshold in `convert_from_ether_decimals`; this combination could not be fully enumerated from the indexed code and would need direct on-chain/mock-runtime experimentation to confirm exploitability against current live Bridge Hub configuration.

```rust
		/// Calculate total fee in native currency to cover all costs of delivering a message to the
		/// remote destination. See module-level documentation for more details.
		pub(crate) fn calculate_fee(
			gas_used_at_most: u64,
			params: PricingParameters<T::Balance>,
		) -> Fee<T::Balance> {
			// Remote fee in ether
			let fee = Self::calculate_remote_fee(
				gas_used_at_most,
				params.fee_per_gas,
				params.rewards.remote,
			);

			// downcast to u128
			let fee: u128 = fee.try_into().defensive_unwrap_or(u128::MAX);

			// multiply by multiplier and convert to local currency
			let fee = FixedU128::from_inner(fee)
				.saturating_mul(params.multiplier)
				.checked_div(&params.exchange_rate)
				.expect("exchange rate is not zero; qed")
				.into_inner();

			// adjust fixed point to match local currency
			let fee = Self::convert_from_ether_decimals(fee);

			Fee::from((Self::calculate_local_fee(), fee))
		}
```

```rust
#[test]
fn test_calculate_fees_with_valid_exchange_rate_but_remote_fee_calculated_as_zero() {
	new_tester().execute_with(|| {
		let gas_used: u64 = 250000;
		let price_params: PricingParameters<<Test as Config>::Balance> = PricingParameters {
			exchange_rate: FixedU128::from_rational(1, 1),
			fee_per_gas: 1_u32.into(),
			rewards: Rewards { local: 1_u32.into(), remote: 1_u32.into() },
			multiplier: FixedU128::from_rational(1, 1),
		};
		let fee = OutboundQueue::calculate_fee(gas_used, price_params.clone());
		assert_eq!(fee.local, 698000000);
		// Though none zero pricing params the remote fee calculated here is invalid
		// which should be avoided
		assert_eq!(fee.remote, 0);
	});
}
```
