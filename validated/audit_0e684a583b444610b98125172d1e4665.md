### Title
Account deletion does not purge pending `ReceivedData`/`PostponedReceipt` trie entries, allowing stale cross-shard receipts to execute against a re-created account - (File: core/store/src/utils/mod.rs)

### Summary
`remove_account` in `core/store/src/utils/mod.rs` only clears the `Account`, `ContractCode`, `AccessKey`/`GasKeyNonce`, and `ContractData` trie keys for a deleted account, but never touches `TrieKey::ReceivedData` or `TrieKey::PostponedReceipt` entries keyed by that `receiver_id`. If account `A` has an outstanding cross-shard data dependency at the moment it is deleted, the pending `ReceivedData` (and the associated `PostponedReceipt`) survive under `A`'s account-id prefix in the trie and can later be completed against a freshly re-created account with the same id.

### Finding Description
`remove_account` is implemented as: [1](#0-0) 
and only removes `Account`, `ContractCode`, the access-key/gas-key set (lines 515-553), and `ContractData` (lines 555-573). There is no call to `remove_postponed_receipt` or any removal of `TrieKey::ReceivedData` for the account being deleted.

`ReceivedData` and `PostponedReceipt` are keyed by `receiver_id` (see `set_received_data` / `set_postponed_receipt` in the same file, lines 76-83 and 120-127), i.e. they live in the trie namespace of the account, but they are populated as part of processing incoming `DataReceipt`s and `ActionReceipt`s with unresolved input data — not as part of the `Account` object itself.

Exploit flow:
1. Attacker funds account `A` and sends a self-targeting `ActionReceipt` (predecessor_id == receiver_id == A) that has an unresolved `input_data_id`. This receipt is stored under `TrieKey::PostponedReceipt{receiver_id: A, ...}` while runtime awaits the corresponding `DataReceipt`.
2. Attacker submits `DeleteAccountAction` for `A`. `remove_account` runs, but as shown above, the pending `PostponedReceipt`/any already-arrived `ReceivedData` rows under `A`'s prefix are not removed.
3. Attacker (or anyone) submits `CreateAccount` for the same account id `A`, establishing a new account with new access keys.
4. The still-pending `DataReceipt` (already in flight / delayed queue) is finally delivered. The runtime looks up the `PostponedReceipt`/`ReceivedData` keyed by `receiver_id = A`, finds the stale entries still present in the trie, and completes/executes the postponed `ActionReceipt`.
5. Because the completed receipt still has `predecessor_id == receiver_id == A`, `check_actor_permissions` (`runtime/runtime/src/actions.rs`) grants it "owner" (full-access) permission on the current incarnation of `A`, even though the *current* owner of `A` (the new key holder) never authorized those actions.

### Impact Explanation
This is an authorization-boundary violation on the account-lifecycle level: actions signed/queued under an old incarnation of an account can execute with full owner privileges against a newly created, differently-owned incarnation of the same account id. Because the affected actions are still scoped to `receiver_id == A` (self-receipts only), the blast radius is limited to state/keys/contract of account `A` itself rather than arbitrary cross-account fund theft — the new owner's account, not third parties, absorbs unauthorized privileged actions (e.g. `DeployContract`, `AddKey`, `DeleteKey`, or self-fund-affecting function calls) queued by the prior owner.

### Likelihood Explanation
Preconditions are attacker-controlled and cheap: creating/deleting/recreating a NEAR account and crafting a self-receipt with an unresolved data dependency all require only ordinary transaction signing rights, no special privilege. The only external dependency is timing — the attacker (or any relayer) needs the recreation of `A` to occur, and the stale `DataReceipt` to be delivered, before the trie garbage is otherwise touched. This is plausible but requires precise choreography across at least 3 transactions/blocks and depends on cross-shard receipt timing, making it non-trivial but repeatable in a controlled test/reproduction.

### Recommendation
Extend `remove_account` in `core/store/src/utils/mod.rs` to also enumerate and remove all `TrieKey::ReceivedData`, `TrieKey::PostponedReceipt`, `TrieKey::PromiseYieldReceipt`, `TrieKey::PromiseYieldStatus`, and related yield/data-id mapping keys scoped to `account_id`, mirroring the iteration-and-remove pattern already used for access keys and contract data. Alternatively/additionally, disallow account deletion (or defer it) while any `PostponedReceipt`/pending input data exists for the account, so that `DeleteAccountAction` cannot be finalized until all outstanding receipts targeting the account have resolved.

### Proof of Concept
Runtime integration test (test-loop or `runtime/runtime/tests`):
1. Create account `A` with an initial balance and access key `K1`.
2. Submit a `FunctionCall` from `A` to itself that issues a promise depending on unresolved input data (e.g., via `promise_then`/cross-shard call construction) so a `PostponedReceipt{receiver_id: A}` and pending input data id are recorded, without the corresponding `DataReceipt` yet delivered.
3. In the same or next block, submit `DeleteAccountAction` for `A` (beneficiary = some other account). Assert `get_account(A)` is `None` post-apply, but assert `get_postponed_receipt`/`has_received_data` for `A`'s old `receipt_id`/`data_id` still return `Some`/`true` (demonstrating the leak).
4. Submit `CreateAccount` + `AddKey` for `A` with a brand-new key `K2`, unrelated to `K1`.
5. Deliver the stale `DataReceipt` (from step 2) that resolves the pending input data.
6. Assert the previously postponed `ActionReceipt` executes against the new `A`, with `actor_id == A`, granting full-access execution of actions the new key `K2` never signed — e.g. assert an `AddKey`/`DeployContract` action in that stale receipt succeeds and mutates the new account's state/keys without `K2`'s authorization.
