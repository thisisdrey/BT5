## Title
`process_delivery_receipt` pays relayer reward regardless of on-chain delivery outcome (`success` flag ignored) - ([File: bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs])

### Summary
`snowbridge-pallet-outbound-queue-v2`'s `submit_delivery_receipt` decodes an Ethereum `InboundMessageDispatched` event (the `DeliveryReceipt`) into a struct that carries a `success: bool` field, then calls `process_delivery_receipt`. That function verifies the gateway address and looks up the `PendingOrder` by nonce, but it never inspects `receipt.success` before releasing the relayer reward.

### Finding Description
The `DeliveryReceipt` primitive explicitly decodes and stores a `success` field from the Ethereum event: [1](#0-0) 

`process_delivery_receipt` fetches the `PendingOrder` for the receipt's nonce and unconditionally pays out `order.fee` if it is greater than zero — it checks `receipt.gateway` and the existence of the order, but at no point reads or branches on `receipt.success`: [2](#0-1) 

The doc comment for the flow even states the intent is "when the message has been verified and executed, the relayer will call `submit_delivery_receipt`... to pay reward" — implying reward is meant to be conditioned on successful execution on Ethereum, yet the code pays the fee purely based on the nonce matching a `PendingOrder`, irrespective of whether the Gateway actually executed the commands successfully: [3](#0-2) 

This is the same broken invariant as the external report: a public-facing "claim/settlement" entrypoint (`mint` in the BitVM case, `submit_delivery_receipt` here) trusts that a validly-proven external transaction occurred, but never checks the semantic outcome/destination encoded in that transaction (Bitcoin destination address vs. Ethereum dispatch `success`) before releasing value. The `Verifier::verify` call only proves that the *event log* was included in a finalized Ethereum block; it says nothing about whether the underlying command execution on the Gateway contract actually succeeded. Since `success` is decoded but discarded, an event log reporting `success: false` still results in a full reward payout, identical in effect to accepting any well-formed but semantically-invalid proof.

### Impact Explanation
This allows relayer rewards to be paid out for message deliveries that failed on the Ethereum side (e.g., out-of-gas execution, reverted commands). This breaks the "settle exactly once to the rightful beneficiary and amount" invariant for bridge reward payouts: rewards should only be paid for messages that were verifiably executed, not merely relayed with a failure receipt. Over time this drains the reward budget by paying for failed deliveries, and removes economic accountability for relayers who submit failing transactions, degrading the operational security assumption that reward = successful, correct delivery.

### Likelihood Explanation
Likelihood is high given that this requires no privileged access: any signed account can call `submit_delivery_receipt` with a legitimate, correctly-verified proof of an Ethereum event whose `success` field happens to be `false` (a normal occurrence, e.g. if gas metering underestimates or the Gateway command reverts). No malicious relayer/validator/prover collusion is needed — a relayer simply submits the true receipt of a failed delivery and still collects the fee.

### Recommendation
In `process_delivery_receipt`, branch on `receipt.success`: only call `T::RewardPayment::register_reward` when `receipt.success == true`. For failed deliveries, the pending order should still be removed (to avoid replay/DoS) but the fee should be forfeited, refunded to the message sender, or handled via a separate policy — but it must not be paid to the relayer as if delivery succeeded.

### Proof of Concept
1. A message is queued via `do_process_message`, creating `PendingOrders[nonce] = { fee: F, .. }`.
2. On Ethereum, the Gateway processes the message but the command execution reverts/fails, emitting `InboundMessageDispatched(nonce, topic, success=false, reward_address)`.
3. A relayer obtains a valid receipt proof for this real (failed) event and calls `submit_delivery_receipt(origin, event)`.
4. `T::Verifier::verify` succeeds (the event genuinely happened and is included in a finalized block).
5. `DeliveryReceipt::try_from` decodes `success = false` correctly.
6. `process_delivery_receipt` ignores `success`, finds `order.fee = F > 0`, and calls `T::RewardPayment::register_reward(&reward_account, .., F)` — paying the reward exactly as if delivery had succeeded. [4](#0-3)

```rust
		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}
```
