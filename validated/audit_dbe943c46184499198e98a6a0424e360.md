### Title
`StacksMessage::consensus_deserialize` never validates that relayers+payload bytes consumed equal `Preamble.payload_len`, enabling P2P stream desync/message smuggling - ([File: stackslib/src/net/codec.rs])

### Summary
`StacksMessage::consensus_deserialize` (stackslib/src/net/codec.rs:1346-1363) checks that `preamble.payload_len` does not exceed `MAX_MESSAGE_LEN - PREAMBLE_ENCODED_SIZE`, but it never checks that the number of bytes actually consumed while parsing `relayers` and `payload` matches the declared `payload_len`. Because the relayer vector is parsed with `read_next_at_most(fd, MAX_RELAYERS_LEN)` (stacks-common/src/codec/mod.rs:192-197, 153-190) directly against the shared connection reader `fd` with no `BoundReader` restricting reads to `payload_len` bytes, a message can declare a small `payload_len` while its relayer-count prefix claims up to `MAX_RELAYERS_LEN` entries, causing the parser to read past the boundary the sender declared.

### Finding Description
The broken equality is: *bytes consumed by relayers+payload parsing == `preamble.payload_len`*. This equality is never enforced anywhere in the code:
- `Preamble::consensus_deserialize` (codec.rs:158-211) only bounds `payload_len` against `MAX_MESSAGE_LEN` (line 179-185) and checks `payload_len >= 5`, but this is purely a self-declared value with no cryptographic or structural tie to what follows.
- `StacksMessage::consensus_deserialize` (codec.rs:1346-1363) re-checks the `MAX_MESSAGE_LEN - PREAMBLE_ENCODED_SIZE` bound, then calls `read_next_at_most::<_, RelayData>(fd, MAX_RELAYERS_LEN)` (line 1354) and `read_next::<StacksMessageType>(fd)` (line 1355) directly on `fd`. Nowhere is `fd` wrapped in a `stacks_common::util::retry::BoundReader` (which is imported into this file but not applied in this function) to cap it at `payload_len` bytes, and nowhere afterward is a check like `bytes_consumed == payload_len` performed.
- `read_next_vec` (stacks-common/src/codec/mod.rs:153-190) only bounds the *count* of relayer entries against `MAX_RELAYERS_LEN`; it has no knowledge of, or relation to, `payload_len`. It simply keeps calling `RelayData::consensus_deserialize(fd)` in a loop until it has read `len` entries, consuming whatever bytes are available in the underlying reader.

Attack: an attacker who has completed a handshake sends a `StacksMessage` whose preamble declares `payload_len = MAX_MESSAGE_LEN - PREAMBLE_ENCODED_SIZE - 1` bytes (just under the cap), but whose relayer-count prefix (a `u32`) is set to `MAX_RELAYERS_LEN` while only a few bytes of actual relayer data are appended before the attacker's next legitimate-looking message is placed on the wire. If the node's connection-level buffering (which accumulates raw TCP bytes and repeatedly attempts `StacksMessage::consensus_deserialize` over the buffered cursor) already has bytes belonging to whatever comes next on the same connection buffered by the time this parse is attempted, `read_next_at_most`/`RelayData::consensus_deserialize` will happily consume those subsequent bytes as fabricated `RelayData` fields, and the parse will "succeed" having consumed more bytes than `payload_len` declared. The connection layer then advances its read cursor by however many bytes the parser actually consumed (not by `PREAMBLE_ENCODED_SIZE + payload_len`), so the stream position is now desynchronized: the next bytes the connection layer feeds to the parser are a truncated/misaligned remainder of what was meant to be the next legitimate message, which gets misparsed as attacker-influenced content (smuggled/forged fields, or a spurious parse error that silently drops/corrupts a legitimate message).

The existing guards (`payload_len < MAX_MESSAGE_LEN` check, `MAX_RELAYERS_LEN` cap on relayer count) only bound the *maximum* size of an individual field; they do nothing to bind the *actual* number of bytes consumed to the *declared* `payload_len`, so they do not prevent this desync.

### Impact Explanation
This allows an attacker with an open, handshaked P2P connection to desynchronize the byte-stream framing on that connection, causing the receiving node to misinterpret bytes belonging to a subsequent legitimate message as attacker-supplied `RelayData`/message fields (message smuggling), or to corrupt/drop legitimate messages from other peers relayed over the same connection. This matches the "request smuggling" Critical-impact category in scope. The attack is repeatable per-message and requires only a single crafted packet per occurrence.

### Likelihood Explanation
Precondition is limited to completing a normal P2P handshake, which any remote unprivileged party can do by connecting to the node's P2P port. No secret, privileged role, or special peer/config state is needed. The attacker fully controls the malformed message's byte layout (payload_len value, relayer count prefix, relayer bytes), making this a low-cost, deterministic, and repeatable attack once a connection is established.

### Recommendation
In `StacksMessage::consensus_deserialize` (codec.rs:1346-1363), wrap `fd` in a `BoundReader` limited to exactly `preamble.payload_len` bytes before parsing `relayers` and `payload`, and after parsing, explicitly verify that the bound reader was fully (and exactly) consumed (i.e., that the total bytes read for relayers+payload equals `payload_len`), returning a `DeserializeError` otherwise. This ties the parser's actual consumption to the declared length and prevents any possibility of reading into subsequent buffered stream data.

### Proof of Concept
Rust test plan (to be added under `stackslib/src/net/codec.rs` tests):
1. Construct two valid serialized `StacksMessage`s, `msg_a` (malicious) and `msg_b` (legitimate, e.g. a `Ping`).
2. In `msg_a`'s preamble, set `payload_len` to a small value that only covers a truncated relayers section (a `u32` relayer count of `MAX_RELAYERS_LEN` followed by only 1-2 real `RelayData` entries' worth of bytes, i.e., fewer than `MAX_RELAYERS_LEN * RELAY_DATA_ENCODED_SIZE` bytes).
3. Concatenate `msg_a`'s truncated bytes directly followed by `msg_b`'s full serialized bytes into one buffer, simulating two back-to-back messages on the same TCP stream.
4. Call `StacksMessage::consensus_deserialize(&mut &buf[..])` and assert the following: either (a) it returns a clean `DeserializeError`/`ReadError(UnexpectedEof)` without consuming any of `msg_b`'s bytes (expected/fixed behavior), or (b) — demonstrating the bug — it returns `Ok(message)` where `message.relayers` contains entries whose byte content was actually drawn from `msg_b`'s serialized preamble/payload, proving cross-message field smuggling and cursor/position desync (measured via `Read::read` call counts or by wrapping the buffer in a `Cursor` and checking `cursor.position()` does not equal `PREAMBLE_ENCODED_SIZE + payload_len` from `msg_a`).
