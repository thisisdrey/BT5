### Title
Oversized-receipt bandwidth under-metering via `try_forward` size clamp - (File: `runtime/runtime/src/congestion_control.rs`)

### Summary
`try_forward` clamps a receipt's `size` to `max_receipt_size` only for the admission comparison and for decrementing `forward_limit.size`, while `buffer_receipt`/`own_congestion_info.add_receipt_bytes` and the shard's own congestion accounting use the real, unclamped size. An unprivileged contract deployer can create receipts whose true borsh size exceeds `max_receipt_size` via the already-documented issue #12606 bypass (post-validation growth from `output_data_receivers` or oversized value/data returns), causing more real bytes to be forwarded to a receiving shard than the bandwidth scheduler granted.

### Finding Description
In `try_forward`, when `size > max_receipt_size`, the code deliberately sets `size = max_receipt_size` "to avoid receipts getting stuck," citing https://github.com/near/nearcore/issues/12606: [1](#0-0) 
The admission check `forward_limit.size >= size` and the deduction `forward_limit.size -= size` both use this clamped value: [2](#0-1) 
Meanwhile, `buffer_receipt` (used when a receipt is *not* forwarded immediately) adds the real, unclamped `size` to `own_congestion_info.add_receipt_bytes`: [3](#0-2) 
The `size` passed into both `try_forward` and `buffer_receipt` is computed once via `compute_receipt_size(&receipt)` (or `receipt_size(&receipt)` when replaying from the buffer) and is the true, real, unclamped size: [4](#0-3) [5](#0-4) 

The precondition — an unprivileged account producing a receipt whose real size exceeds `max_receipt_size` — is achievable and is explicitly acknowledged in the codebase's own regression tests, which construct exactly this scenario through normal transaction/contract-call paths (deploy a contract, call a method) rather than any privileged or node-level access:
- `test_max_receipt_size_promise_return`: a function call receipt passes the initial size check exactly at `max_receipt_size`, then `output_data_receivers` is appended afterward, pushing the real size above the limit without re-validation. [6](#0-5) 
- `test_max_receipt_size_value_return`: a returned value as large as `max_receipt_size` is wrapped in a data receipt, growing the receipt above the limit. [7](#0-6) 

Both tests confirm the resulting oversized receipt is *not* rejected and does propagate through the shard (`assert_oversized_receipt_occurred`), i.e. the size-limit check that normally stops oversized receipts (`ReceiptValidationError::ReceiptSizeExceeded`, as validated in `test_max_receipt_size`) does not fire for these code paths.

Given such an oversized receipt, when it cannot be forwarded immediately it is buffered via `buffer_receipt` with the real size charged to `own_congestion_info`. When later forwarded from the buffer through `forward_from_buffer_to_shard` → `try_forward`, the comparison and deduction against the *receiver's* granted bandwidth (`forward_limit.size`) use the clamped `max_receipt_size` value instead of the real size, so `forward_limit.size` is decremented by less than the number of bytes actually placed into `outgoing_receipts` and physically transmitted to the receiving shard.

### Impact Explanation
This breaks the metering invariant that every forwarded byte must be charged against the sending shard's bandwidth grant to a given receiver shard. The result is that a sending shard can push more real bytes to a receiver than the bandwidth scheduler allotted for that shard-pair, consuming receiver-side capacity/memory headroom intended for other senders. This is a scoped congestion/availability degradation (denial-of-service style resource contention against other senders to the same receiver), not a direct fund theft or consensus-divergence bug — it falls into the resource-exhaustion/availability bounty category rather than fund loss or chain split. Because the discrepancy per receipt is capped by `receipt_size - max_receipt_size`, the over-grant per receipt is finite, but it is repeatable across many receipts.

### Likelihood Explanation
The precondition (creating a receipt whose true size exceeds `max_receipt_size` while bypassing the receipt-creation-time size check) is a pre-existing, documented, and reachable issue (#12606) via ordinary contract deployment and calls — no privileged node/validator access is required, matching the "unprivileged sender" threat model. The clamp-based under-metering is a direct, deterministic consequence of the current code whenever such a receipt is buffered-then-forwarded. However, this specific under-metering behavior is intentionally coded as a stated workaround (with an explicit code comment linking to the tracked issue) rather than a hidden logic slip — it is a known, accepted trade-off to avoid permanent stalls of oversized receipts, and its scoped effect (some extra bytes forwarded beyond the strict per-shard-pair grant) has bounded magnitude per receipt and requires the attacker to repeatedly trigger #12606-style oversized receipts to accumulate meaningful bandwidth over-grant.

### Recommendation
Use the real, unclamped `size` for the `forward_limit.size -= size` deduction (and for stats/metering), while only using the clamped value for the *admission comparison* (`forward_limit.size >= size`) to decide whether to allow the oversized receipt through. This preserves the anti-stall behavior (oversized receipts are not perpetually stuck) while ensuring the receiver's granted bandwidth is decremented by the true number of bytes sent, preventing under-metering. Longer-term, the root cause (issue #12606 — receipts growing past `max_receipt_size` after the size check, e.g. via `output_data_receivers` mutation or oversized return values) should be fixed by re-validating receipt size after all such mutations.

### Proof of Concept
Unit test in `runtime/runtime/src/congestion_control.rs` (or a new test module):
1. Construct an `ApplyState` with `wasm_config.limit_config.max_receipt_size = N`.
2. Construct a `Receipt` whose borsh-encoded size is `N + M` (e.g., by giving it large `output_data_receivers`, mirroring the pattern in `test_max_receipt_size_promise_return`).
3. Call `ReceiptSinkV2::try_forward(receipt, gas, size = N + M, shard, outgoing_limit, outgoing_receipts, apply_state, stats)` with `outgoing_limit` pre-populated with `OutgoingLimit { gas: Gas::MAX, size: N }`.
4. Assert the function returns `ReceiptForwarding::Forwarded` and the receipt is pushed into `outgoing_receipts`.
5. Assert `outgoing_limit[shard].size == 0` (decremented only by the clamped `N`) while the real receipt encoded via `borsh::object_length(&receipt)` is `N + M`, demonstrating `M` bytes were forwarded without being charged against the grant.
6. (Integration-level) Extend `test_max_receipt_size_promise_return`/`test_max_receipt_size_value_return` in `test-loop-tests/src/tests/max_receipt_size.rs` to additionally assert on the sending shard's post-chunk `own_congestion_info`/bandwidth-request bytes versus the actual bytes present in `outgoing_receipts`, showing the mismatch across a chunk boundary.

// A function call will generate a new receipt. Size of this receipt will be equal to
// `max_receipt_size`, it'll pass validation, but then `output_data_receivers` will be modified and
// the receipt's size will go above max_receipt_size. The receipt should be rejected, but currently
// isn't because of a bug (See https://github.com/near/nearcore/issues/12606)
// Runtime shouldn't die when it encounters a receipt with size above `max_receipt_size`.
#[test]
fn test_max_receipt_size_promise_return() {
    init_test_logger();

    let account = create_account_id("account0");
    let account_signer = create_user_test_signer(&account);
    let mut env = TestLoopBuilder::new()
        .enable_rpc()
        .add_user_account(&account, Balance::from_near(10_000))
        .build();

    // Deploy the test contract
    let deploy_contract_tx = SignedTransaction::deploy_contract(
        101,
        &account,
        near_test_contracts::rs_contract().into(),
        &account_signer,
        env.rpc_node().head().last_block_hash,
    );
    env.rpc_runner().run_tx(deploy_contract_tx, Duration::seconds(5));

    // User calls a contract method
    // Contract method creates a DAG with two promises: [A -then-> B]
    // When promise A is executed, it creates a third promise - `C` and does a `promise_return`.
    // The DAG changes to: [C ->then-> B]
    // The receipt for promise C is a maximum size receipt.
    // Adding the `output_data_receivers` to C's receipt makes it go over the size limit.
    let base_receipt_template = Receipt::V0(ReceiptV0 {
        predecessor_id: account.clone(),
        receiver_id: account.clone(),
        receipt_id: CryptoHash::default(),
        receipt: ReceiptEnum::Action(ActionReceipt {
            signer_id: account.clone(),
            signer_public_key: account_signer.public_key().into(),
            gas_price: Balance::ZERO,
            output_data_receivers: vec![],
            input_data_ids: vec![],
            actions: vec![Action::FunctionCall(Box::new(FunctionCallAction {
                method_name: "noop".into(),
                args: vec![],
                gas: Gas::ZERO,
                deposit: Balance::ZERO,
            }))],
        }),
    });
    let base_receipt_template = action_receipt_v1_to_latest(&base_receipt_template);
    let base_receipt_size = borsh::object_length(&base_receipt_template).unwrap();
    let max_receipt_size = 4_194_304;
    let args_size = max_receipt_size - base_receipt_size;

    // Call the contract
    let large_receipt_tx = SignedTransaction::call(
        102,
        account.clone(),
        account.clone(),
        &account_signer,
        Balance::ZERO,
        "max_receipt_size_promise_return_method1".into(),
        format!("{{\"args_size\": {}}}", args_size).into(),
        Gas::from_teragas(300),
        env.rpc_node().head().last_block_hash,
    );
    env.rpc_runner().run_tx(large_receipt_tx, Duration::seconds(5));

    // Make sure that the last promise in the DAG was called
    let assert_test_completed = SignedTransaction::call(
        103,
        account.clone(),
        account,
        &account_signer,
        Balance::ZERO,
        "assert_test_completed".into(),
        "".into(),
        Gas::from_teragas(300),
        env.rpc_node().head().last_block_hash,
    );
    env.rpc_runner().run_tx(assert_test_completed, Duration::seconds(5));

    assert_oversized_receipt_occurred(&env.validator());
}
