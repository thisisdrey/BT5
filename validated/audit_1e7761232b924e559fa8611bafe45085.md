### Title
Prefix-only containment check in ijar's zip extractor (`zipper x`) allows path-traversal via sibling-directory name collision, bypassing zip-slip protection - (File: `third_party/ijar/zip_main.cc`)

### Summary
The zip-slip protection added to Bazel's `ijar`-based `zipper` extraction tool (`UnzipProcessor::Process`) validates that an extracted file stays inside the requested output directory using a plain string-prefix comparison instead of a boundary-aware "is-ancestor" check. Because the check never verifies that the character immediately following the matched prefix is a path separator (or that the strings are equal), a zip entry can traverse ("..") into a sibling directory whose name merely shares the same leading characters as the output directory's basename, and the check will incorrectly treat it as "inside" the output directory.

### Finding Description
`UnzipProcessor::Process` builds the destination path by concatenating the requested output root with the entry's filename, normalizes both paths, and then performs the following containment check: [1](#0-0) 

```cpp
std::string normalized_root = normalize_path(output_root_);
std::string normalized = normalize_path(path);
if (normalized.compare(0, normalized_root.size(), normalized_root) != 0) {
  fprintf(stderr, "paths in the zip may not end up outside of the output directory: ...");
  abort();
}
```

This is a `std::string::compare` prefix comparison: it only checks that `normalized` starts with the same bytes as `normalized_root`, exactly the length of `normalized_root`. It never checks that the next character in `normalized` (at index `normalized_root.size()`) is `/` or that the lengths are equal. This is the same class of bug as the reported Munchables issue: an invalid/incomplete boundary condition where a "less-than-or-equal" (or "is-strict-ancestor") relationship is approximated by a check that is satisfied by values that should be rejected — here, `normalized_root` being a literal string-prefix of `normalized` is treated as equivalent to `normalized_root` being a directory ancestor of `normalized`, which is false whenever the next path component only shares a prefix (e.g. `out` vs `out_evil`).

Concretely, if the tool is invoked to extract to `output_root = "/work/proj/out"`, and the archive contains an entry named:
```
../out_evil/pwned.txt
```
then `concat_path` produces `/work/proj/out/../out_evil/pwned.txt`, which `normalize_path` collapses to `/work/proj/out_evil/pwned.txt`. Since `"/work/proj/out_evil/pwned.txt"` and `"/work/proj/out"` share the first `len("/work/proj/out")` characters (`"...out"` is a literal prefix of `"...out_evil"`), the `compare()` call returns `0` and the check passes, even though `/work/proj/out_evil` is a sibling of, not a descendant of, `/work/proj/out`. The file is written outside the intended output directory.

An existing regression test, `test_no_path_traversal` in `third_party/ijar/test/zip_test.sh`, only exercises straightforward `..`-escape cases and does not cover this sibling-name-collision variant, so it does not catch this specific bypass: [2](#0-1) 

### Impact Explanation
This tool (`zipper`) is used by Bazel's build machinery to extract zip archives whose contents can originate from build-time-produced or downloaded artifacts consumed by build/genrules (e.g., archive extraction actions built on `third_party/ijar`). An attacker who controls the contents of a zip archive that ends up being extracted by this tool (e.g., a hostile archive served from a dependency URL or otherwise supplied as a build input) can use this boundary-check flaw to write files to directories outside the intended, sandboxed extraction target as long as they can arrange (or predict) a sibling directory name that shares the output directory's name as a literal prefix. This is a concrete containment-check bypass leading to writes outside the intended extraction root, which is one of the accepted impact classes (write outside the repository/exec root/output base).

### Likelihood Explanation
Exploitation requires the attacker to control zip entry names (trivial — the attacker fully controls the archive) and to be able to predict or influence the output directory's name well enough to name a sibling directory that shares its prefix (e.g. guessing a commonly used output dir name like `out`, `dist`, `tmp`, `repo`, etc., then naming the colliding sibling `outXXXXX`). Because output directory names used by build actions are often fixed, short, and predictable (e.g., "out", "external", "repo"), constructing a colliding sibling name is straightforward, making this a realistic, low-complexity bypass of an intended security control rather than a purely theoretical one.

### Recommendation
Replace the prefix-only `compare()` check with a proper ancestor-of-path check that requires either exact equality or that the character following the matched prefix in `normalized` is the path separator:

```cpp
bool is_within = normalized == normalized_root ||
    (normalized.size() > normalized_root.size() &&
     normalized.compare(0, normalized_root.size(), normalized_root) == 0 &&
     normalized[normalized_root.size()] == '/');
if (!is_within) {
  ...
  abort();
}
```

### Proof of Concept
Extend `third_party/ijar/test/zip_test.sh` (alongside the existing `test_no_path_traversal`) with a new case that builds a zip containing an entry `../<output_dir>_evil/pwned.txt` and extracts it with `zipper x archive.zip -d <output_dir>`, then asserts that no file was created outside `<output_dir>` (i.e., that `<output_dir>_evil/pwned.txt` does not exist next to `<output_dir>`). With the current code, the file is written outside `<output_dir>`, demonstrating the bypass; after applying the fix above, `zipper` aborts with the "paths in the zip may not end up outside of the output directory" error as intended.
