### Title
Loss/invalidation of in-flight multi-signature transactions due to unchecked `AccountPermissionUpdateContract` execution - (File: actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java)

### Summary
`AccountPermissionUpdateActuator.execute` unconditionally overwrites an account's `owner`/`witness`/`active` permission structures (keys, weights, thresholds) as soon as a single `AccountPermissionUpdateContract` transaction is confirmed, with no check for whether other transactions signed under the old permission set are still pending in the network/mempool. This mirrors the `MessageProxy.removeConnectedChain` bug class: state that other in-flight, already-broadcast operations depend on is deleted/replaced atomically, with no coordination, pause, or pending-operation check, silently invalidating or corrupting the semantics of those pending operations.

### Finding Description
`AccountPermissionUpdateActuator.execute` directly calls `account.updatePermissions(...)` and persists the new `Permission` set with no validation against transactions that are already signed/broadcast and sitting in `Manager.pendingTransactions`, expecting the old permission/threshold/weight configuration. [4](#0-3) 

A multi-signature transaction is validated against whatever `Permission` (keys/weights/threshold) is stored on the account **at the time it is finally packed into a block** — via `TransactionCapsule.checkWeight`/`validateSignature`, which look up `account.getPermissionById(permissionId)` freshly each time. [5](#0-4) 

If the permission set (keys, weights, or threshold) is changed while a partially-collected multi-sig transaction is still pending co-signature/broadcast, the transaction's weight is recomputed against the *new* permission. Depending on the change:
- Signers who previously had weight can be silently dropped from the new key set, causing the transaction to never reach threshold even though every original signer already approved it and reasonably expects it to execute — the multi-sig "message" is permanently stuck/lost, exactly analogous to messages orphaned by `removeConnectedChain`.
- Alternatively, a threshold lowered or keys reweighted after signatures were already collected can cause a transaction to unexpectedly reach/exceed threshold and execute with fewer/different real approvals than the original signers intended, i.e. an unintended state transition executed on stale approvals.

There is no `revert`/pending-check analogous to the report's mitigation suggestion ("check if there are any pending or unprocessed messages... and revert"), nor any local pause mechanism before the permission change is committed. `Manager.getVerifyTxs` even has to special-case permission-change transactions precisely because pending signed transactions can become stale/invalid once an `AccountPermissionUpdateContract` is processed, illustrating that the systemic risk is acknowledged but not prevented at the actuator layer. [3](#0-2) 

### Impact Explanation
An account owner (or an attacker who compromises just one signer with sufficient weight under the old permission set) can submit `AccountPermissionUpdateContract` to change keys/weights/threshold while other, already fully-negotiated-off-chain multi-sig transactions (e.g., large asset transfers requiring multiple co-signers) are waiting for broadcast/inclusion. Depending on the direction of the change, co-signers can:
1. Lose the ability to ever execute a transaction they already approved (their signature weight is silently discounted against the new permission set) — a denial of a legitimate operation and freezing of intended fund movement.
2. Have a transaction that was only partially approved execute against the new (weaker) threshold, effectively bypassing the multi-sig protection the co-signers relied on when signing offline.

This can result in permanent freezing of an intended transfer, or execution of a transfer without the originally-required quorum of approvals — both fall within "permanent freezing of funds" / "unauthorized account operation" impact categories.

### Likelihood Explanation
Any account holder can trigger this by simply submitting an `AccountPermissionUpdateContract` transaction — no special privilege beyond being the account owner is required, matching the "single signed transaction" reachability bar. Multi-sig wallets that collect approvals asynchronously/off-chain before broadcasting (a common pattern) are naturally exposed to a race between permission updates and pending signature collection.

### Recommendation
Before committing a permission change in `AccountPermissionUpdateActuator.execute`, check whether there are pending transactions in `Manager.pendingTransactions` (or a mempool) signed by the affected account under the old permission, and either reject the update, require those pending transactions be cleared/re-signed first, or version the permission set so in-flight transactions are validated against the permission version active when they were signed rather than the latest one.

### Proof of Concept
1. Account `A` has `Active` permission with keys `[K1: weight 3, K2: weight 2]`, threshold `4`.
2. Off-chain, `K1` and `K2` both sign a `TransferContract` intending to move a large balance (combined weight `5 ≥ 4`), but the transaction has not yet been broadcast/included in a block.
3. Account `A`'s owner (or `K1` alone, if it also controls Owner permission) submits `AccountPermissionUpdateContract` removing `K2` from the Active permission, changing weights to `[K1: weight 3]` and threshold to `3`.
4. `AccountPermissionUpdateActuator.execute` commits this immediately with no pending-transaction check.
5. The previously-collected transfer transaction from step 2, when finally broadcast, is now checked with `TransactionCapsule.checkWeight` against the *new* permission — `K2`'s signature yields weight `0` (key no longer present), and depending on the exact scenario the transaction either fails permanently (funds/transfer "lost") or, in the inverse scenario (threshold lowered), executes despite the original quorum requirement no longer being met by the actual current signer set.

  @Override
  public boolean execute(Object object) throws ContractExeException {
    TransactionResultCapsule result = (TransactionResultCapsule) object;
    if (Objects.isNull(result)) {
      throw new RuntimeException(ActuatorConstant.TX_RESULT_NULL);
    }

    AccountStore accountStore = chainBaseManager.getAccountStore();
    long fee = calcFee();
    final AccountPermissionUpdateContract accountPermissionUpdateContract;
    try {
      accountPermissionUpdateContract = any.unpack(AccountPermissionUpdateContract.class);

      byte[] ownerAddress = accountPermissionUpdateContract.getOwnerAddress().toByteArray();
      AccountCapsule account = accountStore.get(ownerAddress);
      account.updatePermissions(accountPermissionUpdateContract.getOwner(),
          accountPermissionUpdateContract.getWitness(),
          accountPermissionUpdateContract.getActivesList());
      accountStore.put(ownerAddress, account);

      adjustBalance(accountStore, ownerAddress, -fee);
      if (chainBaseManager.getDynamicPropertiesStore().supportBlackHoleOptimization()) {
        chainBaseManager.getDynamicPropertiesStore().burnTrx(fee);
      } else {
        adjustBalance(accountStore, accountStore.getBlackhole(), fee);
      }

      result.setStatus(fee, code.SUCESS);
    } catch (BalanceInsufficientException | InvalidProtocolBufferException e) {
      logger.debug(e.getMessage(), e);
      result.setStatus(fee, code.FAILED);
      throw new ContractExeException(e.getMessage());
    }

    return true;
  }

  public static boolean validateSignature(Transaction transaction,
      byte[] hash, AccountStore accountStore, DynamicPropertiesStore dynamicPropertiesStore)
      throws PermissionException, SignatureException, SignatureFormatException {
    Transaction.Contract contract = transaction.getRawData().getContractList().get(0);
    int permissionId = contract.getPermissionId();
    byte[] owner = getOwner(contract);
    AccountCapsule account = accountStore.get(owner);
    Permission permission = null;
    if (account == null) {
      if (permissionId == 0) {
        permission = AccountCapsule.getDefaultPermission(ByteString.copyFrom(owner));
      }
      if (permissionId == 2) {
        permission = AccountCapsule
            .createDefaultActivePermission(ByteString.copyFrom(owner), dynamicPropertiesStore);
      }
    } else {
      permission = account.getPermissionById(permissionId);
    }
    if (permission == null) {
      throw new PermissionException("permission isn't exit");
    }
    checkPermission(permissionId, permission, contract);
    long weight = checkWeight(permission, transaction.getSignatureList(), hash, null);
    if (weight >= permission.getThreshold()) {
      return true;
    }
    return false;
  }

  public void addSign(byte[] privateKey, AccountStore accountStore)
      throws PermissionException, SignatureException, SignatureFormatException {
    Transaction.Contract contract = this.transaction.getRawData().getContract(0);
    int permissionId = contract.getPermissionId();
    byte[] owner = getOwnerAddress();
    AccountCapsule account = accountStore.get(owner);
    if (account == null) {
      throw new PermissionException("Account is not exist!");
    }
    Permission permission = account.getPermissionById(permissionId);
    if (permission == null) {
      throw new PermissionException("permission isn't exit");
    }
    checkPermission(permissionId, permission, contract);
    List<ByteString> approveList = new ArrayList<>();
    SignInterface cryptoEngine = SignUtils
        .fromPrivate(privateKey, CommonParameter.getInstance().isECKeyCryptoEngine());
    byte[] address = cryptoEngine.getAddress();
    if (this.transaction.getSignatureCount() > 0) {
      checkWeight(permission, this.transaction.getSignatureList(),
          this.getTransactionId().getBytes(),
          approveList);
      if (approveList.contains(ByteString.copyFrom(address))) {
        throw new PermissionException(encode58Check(address) + " had signed!");
      }
    }

    long weight = getWeight(permission, address);
    if (weight == 0) {
      throw new PermissionException(
          ByteArray.toHexString(privateKey) + "'s address is " + encode58Check(address)
              + " but it is not contained of permission.");
    }
    ByteString sig = ByteString.copyFrom(cryptoEngine.Base64toBytes(cryptoEngine
        .signHash(getTransactionId().getBytes())));
    this.transaction = this.transaction.toBuilder().addSignature(sig).build();
  }

  public List<TransactionCapsule> getVerifyTxs(BlockCapsule block) {

    if (pendingTransactions.size() == 0) {
      return block.getTransactions();
    }

    List<TransactionCapsule> txs = new ArrayList<>();
    Map<String, TransactionCapsule> txMap = new HashMap<>();
    Set<String> multiAddresses = new HashSet<>(ownerAddressSet);

    pendingTransactions.forEach(capsule -> {
      String txId = Hex.toHexString(capsule.getTransactionId().getBytes());
      if (isMultiSignTransaction(capsule.getInstance())) {
        String address = Hex.toHexString(capsule.getOwnerAddress());
        multiAddresses.add(address);
      } else {
        txMap.put(txId, capsule);
      }
    });

    block.getTransactions().forEach(capsule -> {
      String address = Hex.toHexString(capsule.getOwnerAddress());
      String txId = Hex.toHexString(capsule.getTransactionId().getBytes());
      if (multiAddresses.contains(address) || !isSameSig(capsule, txMap.get(txId))) {
        txs.add(capsule);
      } else {
        capsule.setVerified(true);
      }
    });

    return txs;
  }
