## Title
Heap buffer over-read in `Zip64ExtraField::attr64` reachable via crafted CDH/LH zip64 extra field size flags — ([File: src/tools/singlejar/zip_headers.h])

### Summary
`singlejar`'s ZIP header classes (`LH`, `CDH`) compute an index into the fixed-format `Zip64ExtraField::attr_` array from the *32-bit size sentinel flags* of an untrusted CDH/LH entry, without validating that index against the extra field's actual `attr_count()`. This mirrors the reported TensorFlow bug class: a value derived from attacker-controlled input is used as a raw array index with a double indirection (`zip64_extra_field()` lookup, then `attr64(index)`), and the bound check that should gate the index (the true number of stored attributes) is never applied.

### Finding Description
`Zip64ExtraField::attr64(int index)` directly indexes the flexible array member `attr_[]` with no bounds check: [1](#0-0) 

The actual number of valid attributes is `attr_count()`, derived from the extra field's own declared `payload_size()` — fully attacker-controlled (bounded only to fit inside `extra_fields_length()`, not to match the number of 0xFFFFFFFF sentinels used elsewhere in the header).

Multiple call sites compute the array index purely from the 32-bit-field-is-sentinel checks (`ziph::zfield_has_ext64`) on `compressed_file_size32()` / `uncompressed_file_size32()`, and pass that computed index straight to `attr64()` with no check that `zip64_extra_field()->attr_count()` is large enough:

- `CDH::compressed_file_size()` computes the index as `zfield_has_ext64(uncompressed_file_size32())` (0 or 1): [2](#0-1) 

- `CDH::local_header_offset()` computes an index that can be 0, 1, or 2 depending on independent sentinel bits from two different fields: [3](#0-2) 

- `LH::compressed_file_size()` / `LH::uncompressed_file_size()` use hard-coded indices 1 and 0 respectively, with the same missing validation: [4](#0-3) 

An attacker who controls the bytes of a ZIP/JAR file that becomes a build input (e.g. served from a hostile HTTP origin for an `http_jar`/`http_archive` with no `sha256`/`integrity` pinned, or supplied via an untrusted branch/CI-produced artifact) can craft a `CDH`/`LH` entry where:
- `compressed_file_size32_` and/or `uncompressed_file_size32_` are set to `0xFFFFFFFF` (forcing use of the Zip64 extra field), and/or `local_header_offset32_` is also `0xFFFFFFFF`, while
- the accompanying `Zip64ExtraField`'s `payload_size` declares fewer 8-byte attributes than the number of sentinel flags set (e.g. only one `uint64` attribute present, but both size fields *and* the offset field are marked `0xFFFFFFFF`).

This causes `attr64(1)` or `attr64(2)` to read 8/16 bytes past the extra field's actual payload — i.e., past what `Zip64ExtraField::find` validated to be inside `extra_fields_length()` for the *declared* payload, but into adjacent header bytes, the comment field, the next CDH entry, or (if this is the last entry) unmapped/heap memory beyond the input buffer.

The out-of-bounds bytes are then used as the returned `size_t` (a garbage/attacker-adjacent value), which propagates into size-driven memory operations, e.g.: [5](#0-4) 
which does `Append(lh->data(), uncompressed_file_size)` — if `uncompressed_file_size` is corrupted to a large bogus value, this becomes a much larger heap over-read that gets copied into the growing output buffer (i.e., into the produced merged jar), and `DecompressEntryContents` similarly trusts `in_bytes`/`out_bytes` derived the same way: [6](#0-5) 

### Impact Explanation
This is a genuine heap buffer over-read triggered purely by attacker-controlled archive bytes, with no cooperation needed from the victim beyond building against the malicious jar. Because the resulting corrupted size value flows into `memcpy`-style `Append`/`DecompressEntryContents` calls that read from `lh->data()` for `uncompressed_file_size`/`in_bytes` bytes, the impact goes beyond a simple crash: adjacent heap memory can be read past the true entry boundary and copied into the output artifact (`output_jar`), constituting a heap over-read with potential information disclosure into build outputs, not merely a crash/DoS.

### Likelihood Explanation
Reachable whenever `singlejar` processes a JAR whose CDH/LH bytes are not cryptographically verified against the specific header field combination (checksum/`sha256` on `http_jar`/`http_archive` only protects the overall archive bytes as downloaded — if omitted, or if the archive is sourced from a distdir/cache-less first fetch from a hostile mirror, the bytes are attacker-controlled). No Starlark or root-repo BUILD file cooperation is required; a single crafted JAR dependency is sufficient. It requires deliberately-malformed metadata (inconsistent 0xFFFFFFFF sentinels vs. `Zip64ExtraField` attribute count), which is easy to construct with any hex editor.

### Recommendation
In `Zip64ExtraField::attr64` (or at each call site in `LH`/`CDH`), validate `index < attr_count()` before dereferencing `attr_[index]`; on failure, treat the entry as corrupt and fail the parse (as is already done elsewhere in this file for malformed extra fields, e.g. the bounds check in `ExtraField::find`). Apply this consistently to `LH::compressed_file_size`/`uncompressed_file_size`, `CDH::compressed_file_size`/`uncompressed_file_size`/`local_header_offset`.

### Proof of Concept
A `BuildIntegrationTestCase`/`src/test/shell/bazel` style reproduction:
1. Hand-craft a minimal ZIP with one entry whose Central Directory Header sets `compressed_file_size32_ = uncompressed_file_size32_ = local_header_offset32_ = 0xFFFFFFFF`.
2. Attach a `Zip64ExtraField` extra field to that CDH with `payload_size = 8` (i.e., only one 64-bit attribute present, `attr_count() == 1`), placing the entry at the very end of the central directory buffer (immediately followed by the End-Of-Central-Directory record, which is a separate/adjacent heap allocation boundary in the mmap'd file).
3. Run `singlejar --output out.jar --sources crafted.jar` (or feed it through `OutputJar::AddJar`).
4. Observe that `CDH::local_header_offset()` computes `attr_no = 2` and calls `z64->attr64(2)`, reading 16 bytes past the declared single-attribute payload — verifiable under ASan as a heap-buffer-overflow (read), and further observe corrupted `uncompressed_file_size()`/`compressed_file_size()` values causing `AddJar`'s entry-copy logic to over-read `lh->data()`.
