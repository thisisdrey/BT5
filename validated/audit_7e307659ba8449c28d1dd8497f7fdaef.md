Based on my research, I found a legitimate analog in Bazel's ijar tool, which parses ZIP/JAR central directory records without validating declared field lengths against the actual mapped file bounds — the same bug class as CVE-2021-40716 (parser trusts an attacker-controlled length field and reads past the buffer it describes).

### Title
Out-of-bounds heap read when parsing malicious JAR/ZIP central-directory extra fields in ijar - (File: `third_party/ijar/zip.cc`)

### Summary
`InputZipFile::ProcessCentralDirEntry` in ijar parses the ZIP64 extra field of a central directory entry using attacker-controlled `data_size`/`header_id` values without ever validating that the declared extra-field bytes actually exist within the mapped input file or within the entry's own `extra_field_length`. A JAR fetched via `http_jar`/`http_archive`/Maven coordinates that a victim's build consumes can therefore trigger reads past the mmap'd file buffer, echoing adjacent heap memory into fields consumed by later stages of the build (ijar output / size fields), analogous to the OOB-read/memory-disclosure pattern in CVE-2021-40716.

### Finding Description
`ProcessCentralDirEntry` reads the central directory header for each entry and then walks its "extra fields" region: [1](#0-0) 

The loop condition is only `while (extra_p != p)`, where `p` was advanced by the untrusted 16-bit `extra_field_length` taken directly from the file. Inside the loop, `header_id` and `data_size` are also read directly from attacker bytes, and `extra_p` is advanced by `data_size` with no check that `extra_p + data_size <= p` (end of the declared extra region) — let alone any check against the end of the mmap'd file. If `header_id == ZIP64_EXTRA_FIELD_TAG` but the crafted `data_size` is smaller than 8/16/24, `get_u8le(extra)` is still called unconditionally up to three times, reading bytes beyond the declared extra field, and potentially beyond the file mapping's actual `in_length`.

The low-level readers (`get_u2le`, `get_u4le`, `get_u8le`) themselves perform no bounds checking — they are raw pointer dereferences: [2](#0-1) 

There is no enclosing bounds check elsewhere in the file that validates `p`/`extra_p` against `zipdata_in_ + in_length` before these reads; `FindZipCentralDirectory`/`FindZip64CentralDirectory` only establish where the central directory *starts*, not a per-entry upper bound tied to the mapped buffer end.

### Impact Explanation
An attacker who publishes a crafted `.jar`/`.zip` (e.g. a dependency fetched via `http_jar`, `http_archive`, or a Maven/http-served artifact that a victim's `MODULE.bazel`/`WORKSPACE` references) can cause the ijar tool — invoked as a build action on that artifact — to read past its mmap'd input buffer. This is a heap out-of-bounds read: the leaked bytes influence `*compressed_size`/`*uncompressed_size`/`*offset`, which flow into `CalculateOutputLength` and the extraction/copy logic that produces the ijar (interface jar) output consumed by the rest of the build graph. Depending on process layout, the OOB bytes can also cause a segfault (crash) reading unmapped guard pages beyond the file mapping. This mirrors the CVE-2021-40716 bug class: a parser trusts a declared length field from untrusted content and reads adjacent memory it should not, with observable effects (corrupted/incorrect size fields, potential crash, and memory content leaking into artifact-affecting values).

### Likelihood Explanation
Any dependency consumed as a JAR (very common in Bazel Java/Android builds via `http_jar`, `http_archive` unpacking jars, or a maven/http-served coordinate) goes through ijar during compilation. No sha256/integrity check on the JAR contents' internal structure prevents a validly-checksummed-but-maliciously-structured ZIP from reaching this parser — checksum verification (if present) only guarantees the bytes match what was pinned, not that the internal ZIP structure is well-formed, so a pinned malicious JAR published by the attacker (and the checksum recorded for it) still reaches this vulnerable code path.

### Recommendation
In `ExtraField`/`ProcessCentralDirEntry` style parsing, bound every `extra_p` advance and every subsequent field read against both (a) the end of the declared extra-field region (`p`) and (b) the end of the mapped input file (`zipdata_in_ + in_length`), rejecting/erroring on any entry whose extra field claims a `data_size` that doesn't fit, before dereferencing `get_u8le`/`get_u4le` on it — mirroring the bounds checks already present in `third_party/ijar/zip.cc`'s sibling implementation `ExtraField::find` in `src/tools/singlejar/zip_headers.h` (lines 99–115), which explicitly checks `start + extra_field->size() > end` before proceeding.

### Proof of Concept
1. Construct a minimal ZIP with one central directory entry.
2. Set the entry's `extra_field_length` to 4, containing only `header_id=0x0001` (ZIP64 tag) and `data_size=0` (i.e., no payload bytes at all).
3. Feed this file to ijar (`ijar input.jar output-interface.jar`), which calls `ProcessCentralDirEntry`.
4. Because `header_id == ZIP64_EXTRA_FIELD_TAG` is matched, the code unconditionally calls `get_u8le(extra)` (and up to two more times) starting right after the 4-byte extra field header — reading 8–24 bytes that were never declared as present, extending past the declared extra-field boundary and potentially past the mmap'd file buffer.
5. A JUnit/`gtest`-style test analogous to `src/tools/singlejar/zip_headers_test.cc`'s `TEST(ZipHeadersTest, Zip64ExtraFieldTest)` pattern, but targeting `InputZipFile::ProcessCentralDirEntry`, can assert that parsing such a truncated ZIP64 extra field does not read outside the buffer bounds (currently it does).
