### Title
Non-standard ERC20 tokens (no boolean return, e.g. USDT-style) that succeed on `transfer()` are treated as failed by `ERC20Transactor`, permanently stranding user funds - (File: `cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs`)

### Summary
`ERC20Transactor::withdraw_asset_with_surplus` and `deposit_asset_with_surplus`, used by the asset-hub `AssetTransactors` XCM executor configuration, assume every registered ERC20 contract strictly follows the "always revert on failure, always return `bool` on success" convention. When the underlying ERC20 contract belongs to the well-known category of tokens that perform the transfer successfully but return no ABI-encoded boolean (the exact USDT-style pattern from the referenced report), the code treats a successful, state-mutating transfer as a failed XCM operation, even though the token balance has already moved on-chain. This reproduces the "successful transfer treated as failed" impact from the external report inside a production Polkadot SDK code path.

### Finding Description
`withdraw_asset_with_surplus` performs the withdrawal by calling `IERC20::transferCall` on the registered ERC20 contract from the user's account to the checking account: [1](#0-0) 

It then interprets the outcome strictly as: [2](#0-1) 

If `return_value.did_revert()` is false (the call executed to completion — meaning the transfer logic ran and the tokens were moved), the code calls `IERC20::transferCall::abi_decode_returns_validate(&return_value.data)`. For a contract that performs the transfer but returns no data at all (like Tether USD's `transferFrom`/`transfer`, which have no `returns (bool)` in their ABI), this decode call returns `Err`, which is mapped to `XcmError::FailedToTransactAsset("ERC20 contract result couldn't decode")`.

The critical flaw: by the time this error is produced, the ERC20 contract has *already executed and mutated its own storage* — the tokens have already left the user's balance and arrived at `TransfersCheckingAccount`. The `bare_call` to `pallet_revive::Pallet::<T>::bare_call` is not able to be "undone" from the XCM executor's point of view merely by returning an `Err` from `withdraw_asset_with_surplus`; that state transition inside the target contract's storage is already committed once `did_revert()` is false. The XCM executor, upon receiving `Err`, aborts holding-asset creation for this leg of the program and does not proceed to credit the corresponding `AssetsInHolding` — meaning no compensating mechanism exists to return the value to the user or to the intended beneficiary. The user's tokens are now sitting in the `TransfersCheckingAccount` with no XCM-visible receipt and no automatic refund path.

The same "successful call with no verifiable return value" ambiguity exists symmetrically in `deposit_asset_with_surplus`, where a successful-but-undecodable `transfer()` from the checking account to a beneficiary is treated as `Err`, again after the ERC20 balance has already moved: [3](#0-2) 

This directly matches Impact type 2 from the referenced report: tokens like USDT that don't return a boolean cause on-chain state to diverge from what the calling protocol (XCM here, the Buffer contracts there) believes happened.

### Impact Explanation
Any foreign ERC20 asset registered via `ERC20Matcher`/`ERC20Transactor` (e.g., on Asset Hub, wired via `AssetTransactors` in `xcm_config.rs`) that does not strictly return a `bool` on `transfer`/`transferFrom` success will cause XCM withdraw/deposit legs to report failure to the executor while the ERC20 balance has already moved. This is a permanent fund-lock class bug: user assets get transferred into `TransfersCheckingAccount` (on withdraw) or fail to reach the beneficiary (on deposit) with no compensating credit, no error surfaced to the token owner in a recoverable way, and no automatic retry/refund. This satisfies the "permanent user-fund or bridge-state lock" impact class in the gate. [4](#0-3) 

### Likelihood Explanation
The trigger requires only that a non-privileged party register (or that the runtime already registers) a legitimate, unmodified, well-known ERC20 token whose ABI omits the boolean return value on `transfer`/`transferFrom` — the exact real-world pattern of USDT and several other production ERC20 tokens. No malicious relayer, validator, collator, or admin action is required; any ordinary user attempting a normal XCM asset transfer of such a token triggers the divergence deterministically on the very first transfer.

### Recommendation
Distinguish "call reverted" from "call succeeded with empty/undecodable return data" before deciding failure. Per EIP behavior for tokens omitting the boolean return, treat `did_revert() == false && return_value.data.is_empty()` (and the target address has contract code) as success, mirroring the recommended pattern from the referenced report (check `success`/revert first, then only require boolean decoding when return data is non-empty). Apply this uniformly to both `withdraw_asset_with_surplus` and `deposit_asset_with_surplus` in `erc20_transactor.rs`.

### Proof of Concept
1. Deploy (or point `ERC20Matcher` at) an ERC20 contract implementing `transfer`/`transferFrom` without a `returns (bool)` clause (functionally identical to USDT's `transferFrom`).
2. Register it as a foreign asset matched by `assets_common::ERC20Matcher` so `ERC20Transactor` is used as its `TransactAsset`.
3. Initiate an XCM program that performs `WithdrawAsset` on this token from a user account.
4. Observe: `pallet_revive::Pallet::<T>::bare_call` executes the token's `transfer`, moving the balance from the user to `TransfersCheckingAccount`; `return_value.did_revert()` is `false`; `return_value.data` is empty; `IERC20::transferCall::abi_decode_returns_validate` returns `Err`; `withdraw_asset_with_surplus` returns `Err(XcmError::FailedToTransactAsset(...))`.
5. The XCM executor aborts the program without creating the corresponding `AssetsInHolding` credit, leaving the user's tokens inside `TransfersCheckingAccount` with no path back to the user — funds are permanently stuck.
