### Title
Non-atomic proc-receive reference updates abort the entire batch on non-hook errors instead of isolating per-reference failures - ([File: internal/gitaly/hook/receivepack/receive_pack.go])

### Summary
In `procReceiveHook`'s non-atomic branch, Gitaly intends to process each reference update independently so that one rejected update does not affect the others in the same push. However, the error-classification logic only treats `hook.CustomHookError` and the internal `updateError` type as "safe, per-reference" failures; any other error type returned from `receivePackReferenceUpdates` causes the whole loop to `return` immediately, aborting processing of all remaining reference updates in the batch — even though those other updates are entirely legitimate and unrelated to the failure.

### Finding Description
`procReceiveHook` in `internal/gitaly/hook/receivepack/receive_pack.go` iterates over each reference update in non-atomic mode: [1](#0-0) 

For each update it calls `receivePackReferenceUpdates` and classifies the resulting error:
- `hook.CustomHookError` → recorded as a per-ref rejection, loop continues.
- `updateError` (returned only when `updater.Commit()` fails) → recorded as a per-ref rejection, loop continues.
- Any other error → `return fmt.Errorf("updating reference: %w", err)`, which aborts the entire function and, by extension, processing of every subsequent reference in the batch.

`receivePackReferenceUpdates` calls `hookManager.UpdateHook` for each reference before queuing the update: [2](#0-1) 

`UpdateHook`/`updateHook` (`internal/gitaly/hook/update.go`) can return errors that are **not** `hook.CustomHookError`:
- `structerr.NewInternal(...)` for invalid old/new object IDs, missing user details, or missing reference (validation errors).
- Errors from `m.stopTransaction` / `m.synchronizeHookExecution`, which coordinate voting across Gitaly nodes and can fail for reasons unrelated to any specific custom hook (e.g., transient synchronization/voting issues). [3](#0-2) 

Only errors originating from the custom hook script itself (wrapped as `hook.CustomHookError`) are safely isolated; other failure modes surfacing from the same call path are not distinguished from a hard failure and propagate up, causing `procReceiveHook`'s default case to short-circuit the whole non-atomic loop.

This mirrors the reported bug class: a loop processing multiple independent items where one item's failure — if not safely and specifically caught — aborts processing of the remaining, legitimate items in the same call.

### Impact Explanation
An ordinary user pushing multiple references in a single non-atomic proc-receive push can have all of their other, valid reference updates silently dropped/denied whenever one reference update encounters a non-hook-classified error (e.g., a transient inter-node synchronization failure during `synchronizeHookExecution`, or a validation edge case in `updateHook`). This is a denial-of-service of the RPC handler for legitimate reference updates that should otherwise succeed independently, contrary to the documented "single ref failures should not block others" behavior for non-atomic mode. [4](#0-3) 

### Likelihood Explanation
The proc-receive path is reachable directly from a normal client push (`git push` with multiple ref updates, non-atomic mode). Triggering the non-`CustomHookError`/non-`updateError` branch requires an internal/synchronization failure or a validation edge case rather than attacker-crafted input, so likelihood is moderate — it depends on operational conditions (e.g., replication/voting hiccups) rather than being trivially reproducible by any user on every push, but it is within reach of a normal, unprivileged push flow with multiple refs.

### Recommendation
Broaden the error classification in `procReceiveHook`'s non-atomic branch so that only errors that must abort the whole transaction (e.g., unrecoverable process/plumbing failures) do so, while all per-reference failures — including internal validation errors and hook-synchronization errors tied to a specific reference — are captured as a per-reference rejection (similar to `rejectedUpdates[update.Ref] = reason`) so unrelated, valid reference updates in the same non-atomic batch continue to be processed.

### Proof of Concept
1. Push multiple reference updates (e.g., `refs/heads/a` and `refs/heads/b`) with proc-receive in non-atomic mode.
2. Cause `updateHook`/`synchronizeHookExecution` to fail for `refs/heads/a` via a non-custom-hook error path (e.g., an internal validation error or induced synchronization failure) rather than a custom pre-receive/update hook rejection.
3. Observe that `procReceiveHook`'s `default` branch triggers `return fmt.Errorf("updating reference: %w", err)` at [5](#0-4) , terminating the loop before `refs/heads/b` is ever processed, denying an otherwise valid, unrelated reference update.

func (m *GitLabHookManager) UpdateHook(ctx context.Context, repo *gitalypb.Repository, ref, oldValue, newValue string, env []string, stdout, stderr io.Writer) error {
	payload, err := gitcmd.HooksPayloadFromEnv(env)
	if err != nil {
		return structerr.NewInternal("extracting hooks payload: %w", err)
	}

	if isPrimary(payload) {
		if err := m.updateHook(ctx, payload, repo, ref, oldValue, newValue, env, stdout, stderr); err != nil {
			m.logger.WithError(err).WarnContext(ctx, "stopping transaction because update hook failed")

			// If the update hook declines the push, then we need
			// to stop any secondaries voting on the transaction.
			if err := m.stopTransaction(ctx, payload); err != nil {
				m.logger.WithError(err).ErrorContext(ctx, "failed stopping transaction in update hook")
			}

			return err
		}
	}

	if err := m.synchronizeHookExecution(ctx, payload, "update"); err != nil {
		return fmt.Errorf("synchronizing update hook: %w", err)
	}

	return nil
}
