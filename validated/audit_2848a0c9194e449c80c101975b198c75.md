### Title
Unauthenticated forgery of `BlockValidationResponse`/`NewBurnBlock` signer events via the signer's event-observer HTTP listener - (File: libsigner/src/events.rs)

### Summary
The signer's `SignerEventReceiver` binds a plain, unauthenticated `tiny_http` server (sample configs bind it to `0.0.0.0:<port>`) and accepts POSTs to `/proposal_response` and `/new_burn_block`, decoding the JSON body with `serde_json::from_slice` and converting it directly into a trusted `SignerEvent` via `TryFrom<BlockValidateResponse>`/`TryFrom<BurnBlockEvent>`, neither of which performs any cryptographic or origin check. Any TCP client that can reach the bound port can therefore inject forged validation verdicts or burn-block notifications into the signer runloop as if they came from the node.

### Finding Description
`SignerEventReceiver::next_event` (`libsigner/src/events.rs:413-459`) dispatches based solely on URL path, routing `/proposal_response` to `process_event::<T, BlockValidateResponse>` and `/new_burn_block` to `process_event::<T, BurnBlockEvent>`. `process_event` (`libsigner/src/events.rs:519-542`) reads the raw body, deserializes it via `serde_json::from_slice::<E>`, and calls `.try_into()`. `TryFrom<BlockValidateResponse>` (`events.rs:627-635`) and `TryFrom<BurnBlockEvent>` (`events.rs:637-649`) both unconditionally wrap the parsed struct into `SignerEvent::BlockValidationResponse`/`SignerEvent::NewBurnBlock` — no signature, slot ownership, or peer-identity check exists anywhere in this call path (unlike `TryFrom<StackerDBChunksEvent>`, which at least recovers a public key from chunk signatures for the signer-message lane, `events.rs:596-611`).

On the sending side, `EventDispatcherWorker::make_http_request` (`stacks-node/src/event_dispatcher/worker.rs:325-397`) sends the event payload as a plain POST with no `Authorization` header or shared secret — the `auth_token`/`auth_password` pair documented in `docs/signing.md` and the sample configs is only used by the node's own RPC/block-proposal endpoint, not by this node→signer push channel. The reference deployment configs (`sample/conf/signer/mainnet-signer-conf.toml:39`, `sample/conf/mainnet-signer.toml:27`) even show the signer's own listener endpoint bound to `0.0.0.0:30000`, i.e., all interfaces, not loopback-only, making the port remotely reachable if the host firewall does not additionally restrict it. `stacks-signer/src/lib.rs:125-132` contains an explicit runtime warning acknowledging this exposure risk without providing a code-level mitigation.

### Impact Explanation
An attacker who can reach the signer's event-listener port can POST a crafted JSON body to `/proposal_response` or `/new_burn_block` and have it accepted as `Ok(SignerEvent::BlockValidationResponse(..))` or `Ok(SignerEvent::NewBurnBlock{..})`, forwarded straight into the signer's runloop channel (`forward_event`, `events.rs:469-490`) with zero verification that the node actually produced it. This is an unauthenticated write into signer decision-making state: a forged "valid"/"invalid" block-validation verdict or a forged burn-block notification can influence what the signer signs or how it tracks tenure/burn-height state, which is a Critical-severity unauthenticated-write finding per the stated impact taxonomy.

### Likelihood Explanation
No secret, signature, or privileged role is required — only network reachability to the bound event-listener port, which per the reference deployment configs is bound to `0.0.0.0`. The attack is a single crafted HTTP POST and is fully repeatable at will as long as the port stays reachable.

### Recommendation
Require the same shared-secret/`Authorization` check on inbound event-observer POSTs that is already used for the signer→node direction (validate a bearer token against `auth_password`/`auth_token`), or bind the listener to loopback by default and document/enforce that it must never be exposed beyond a trusted node-to-signer link (e.g., mutual TLS or a local Unix socket). At minimum, verify request origin/authenticity before calling `TryInto<SignerEvent<T>>` in `process_event`.

        self.with_server(|event_receiver, http_server, _is_mainnet| {
            // were we asked to terminate?
            if event_receiver.is_stopped() {

            }
            debug!("Request handling");
            let request = http_server.recv()?;
            debug!("Got request"; "method" => %request.method(), "path" => request.url());

            if request.url() == "/status" {
                request
                .respond(HttpResponse::from_string("OK"))
                .expect("response failed");
                return Ok(SignerEvent::StatusCheck);
            }

            if request.method() != &HttpMethod::Post {
                return Err(EventError::MalformedRequest(format!(
                    "Unrecognized method '{}'",
                    request.method(),
                )));
            }
            debug!("Processing {} event", request.url());

                process_event::<T, StackerDBChunksEvent>(request)

            } else if request.url() == "/new_burn_block" {
                process_event::<T, BurnBlockEvent>(request)

fn process_event<T, E>(mut request: HttpRequest) -> Result<SignerEvent<T>, EventError>
where
    T: SignerEventTrait,
    E: serde::de::DeserializeOwned + TryInto<SignerEvent<T>, Error = EventError>,
{
    let mut body = String::new();

    if let Err(e) = request.as_reader().read_to_string(&mut body) {
        error!("Failed to read body: {:?}", &e);
        ack_dispatcher(request);
        return Err(EventError::MalformedRequest(format!(
            "Failed to read body: {:?}",
            e
        )));
    }
    // Regardless of whether we successfully deserialize, we should ack the dispatcher so they don't keep resending it
    ack_dispatcher(request);
    let json_event: E = serde_json::from_slice(body.as_bytes())
        .map_err(|e| EventError::Deserialize(format!("Could not decode body to JSON: {:?}", e)))?;

    let signer_event: SignerEvent<T> = json_event.try_into()?;

    Ok(signer_event)
}
