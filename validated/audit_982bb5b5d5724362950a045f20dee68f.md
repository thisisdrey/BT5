### Title
Legacy (default) Exchange pool transaction path lacks negative-balance validation, enabling floating-point price-manipulation drain of TRC10 AMM pools - ([File: chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java])

### Summary
`ExchangeCapsule.transaction()` computes the counter-token amount for a Bancor-relay AMM swap using either a legacy double-precision `ExchangeProcessor` or, only when the `ALLOW_HARDEN_EXCHANGE_CALCULATION` chain proposal is active, the fixed-point `SafeExchangeProcessor`. The post-swap "pool balance must remain non-negative" invariant is only enforced in the hardened branch, leaving the default/legacy path — reachable by any account via `ExchangeTransactionContract` — without protection against floating-point precision divergence that can yield a counter-token payout larger than the pool actually holds. This is analogous to the Sovryn incident, where price-manipulation of an under-protected pricing/interest calculation let the attacker withdraw more value than the pool legitimately backed.

### Finding Description
`ExchangeCapsule.transaction()` selects the processor and only guards against a negative resulting balance when `hardenedCalc` is true: [1](#0-0) 

Note line 160: `if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) { throw ... }`. When `hardenedCalc` is `false` (the default state of a chain unless the community committee has activated `ALLOW_HARDEN_EXCHANGE_CALCULATION` via proposal), this check is skipped entirely, so `newFirstTokenBalance`/`newSecondTokenBalance` can go negative and are written straight into the persisted `ExchangeCapsule` state without any exception.

The legacy `ExchangeProcessor` computes the swap output entirely with `double` arithmetic and `Math.pow`: [2](#0-1) 

Because the relay/Bancor formula is evaluated with IEEE-754 doubles rather than exact fixed-point math, extreme or specially-crafted pool ratios (e.g. one side of the pool set very small relative to the sell quantity, achievable by anyone through `ExchangeCreateActuator`/`ExchangeInjectActuator`/`ExchangeWithdrawActuator`) can push `exchangeFromSupply`'s `Math.pow(1 + supplyQuant/supply, 2000.0)` term into a region where floating-point rounding causes the computed `buyTokenQuant` to exceed the pool's actual counter-token reserve. `ExchangeTransactionActuator.execute()` then unconditionally credits the caller with that amount: [3](#0-2) 

Because the balance-sign check that would catch this (line 160 of `ExchangeCapsule.java`) is gated behind `hardenedCalc`, the legacy path silently accepts a negative pool balance and the actuator still adds the (unbacked) counter-token/TRX amount to the caller's account via `addAssetAmountV2`/`setBalance`. The existence of `SafeExchangeProcessor` and the `hardenedCalc` guard demonstrates the project itself recognizes the legacy double-math path as unsafe, but the fix is opt-in via governance proposal rather than default-enforced, so any chain/network that has not yet activated `ALLOW_HARDEN_EXCHANGE_CALCULATION` remains exposed to this class of price-manipulation/precision-drain bug reachable purely from a signed `ExchangeTransactionContract` transaction.

### Impact Explanation
An attacker able to create or find an `Exchange`/`ExchangeV2` pool with a favorable imbalance can drain more of the counter token/TRX than the pool holds, producing an unbacked balance credited to the attacker's account and a negative (or artificially decremented) balance recorded for the pool — a direct theft-of-funds / unbacked-asset condition equivalent in kind to the Sovryn price-manipulation withdrawal, since funds are extracted beyond what legitimate collateral/liquidity in the pool supports.

### Likelihood Explanation
Reachable via a single unprivileged `ExchangeTransactionContract` broadcast; the attacker only needs to control (or influence via `ExchangeInjectActuator`/`ExchangeWithdrawActuator`) the pool's reserve ratio and issue a sell quantity chosen to maximize floating-point drift, which requires no special privileges — but it requires that `ALLOW_HARDEN_EXCHANGE_CALCULATION` has not been activated on the target network and requires finding/crafting specific balance ratios where `Math.pow` divergence becomes large enough to be economically meaningful, which is a non-trivial but automatable numerical search.

### Recommendation
Enforce the non-negative-balance invariant unconditionally in `ExchangeCapsule.transaction()` regardless of `hardenedCalc`, and/or make `SafeExchangeProcessor` (BigDecimal-based) the sole processor for `ExchangeTransactionActuator`, removing the double-math `ExchangeProcessor` path entirely rather than leaving it gated behind an optional governance proposal.

### Proof of Concept
1. Create (or locate) a TRC10 `Exchange` pool with a highly imbalanced ratio between `firstTokenBalance` and `secondTokenBalance` via `ExchangeCreateActuator`/`ExchangeInjectActuator`.
2. On a network where `ALLOW_HARDEN_EXCHANGE_CALCULATION` has not been activated (`hardenedCalc == false`), broadcast an `ExchangeTransactionContract` with a `sellTokenQuant` chosen so that `ExchangeProcessor.exchange()`'s double-precision `Math.pow` computation returns a `buyTokenQuant` exceeding the counter-token pool balance.
3. Because `ExchangeCapsule.transaction()` (chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java:160) skips the `< 0` balance check when `hardenedCalc` is false, the swap succeeds, the pool balance is persisted as negative/insufficiently backed, and `ExchangeTransactionActuator.execute()` (actuator/src/main/java/org/tron/core/actuator/ExchangeTransactionActuator.java:86-91) credits the attacker's account with the excess amount.

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
  }

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
