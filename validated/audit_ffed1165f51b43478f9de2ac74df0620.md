### Title
ModExp Precompile Unbounded Length Fields Cause Disproportionate Memory Allocation and Node OOM Crash - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
`PrecompiledContracts.ModExp.execute()` reads `baseLen`, `expLen`, `modLen` from three 32-byte header words in the call data via `parseLen()`, which converts each word to an `int` using `DataWord.intValueSafe()` [2](#0-1)  and [3](#0-2) . These values can be up to `Integer.MAX_VALUE` (~2^31-1) merely by encoding a large 32-byte word. The upper-bound rejection of `baseLen/expLen/modLen > 1024` is gated behind `VMConfig.allowTvmOsaka()` [4](#0-3) . When Osaka is not active, execution proceeds directly to `parseArg()` → `parseBytes()`, which allocates `new byte[len]` sized purely by the attacker-supplied length field, regardless of how much actual call data was provided [1](#0-0) . This is called three times (for base, exp, mod) in `execute()` [5](#0-4) , so a single call with three ~2GB length fields can trigger up to ~6GB of transient byte-array allocation from a tiny (96-byte header) call-data payload.

### Finding Description
The MongoDB advisory describes a data-type conversion operation in an aggregation stage causing disproportionate memory use versus the actual data size, leading to OOM termination. The ModExp precompile exhibits the analogous pattern: a length field is converted (`DataWord` → `int` via `intValueSafe()`) and then used directly as an array allocation size in `parseBytes`, without validating it against the true size of the supplied `data` (call data). Unlike the pre-Osaka energy accounting, which does bound the numeric *cost* of the exponentiation loosely via `getMultComplexity`/`getAdjustedExponentLength`, it does not bound the actual heap allocation performed by `parseBytes`/`parseArg` prior to (or independent of) `modPow` execution. The Osaka fork (`VMConfig.allowTvmOsaka()`) added a `UPPER_BOUND` (1024-byte) length check exactly to fix this class of issue — but only in the `execute()` gate for the non-zero base/mod path, and only when the fork is active on the network. On any deployment/testnet/private chain where TIP-7823/Osaka has not activated (or during the period before mainnet activation), this bound does not apply, and the described unbounded allocation remains reachable by any account with enough energy to make the call (energy for `ModExp` pre-Osaka is not proportional to the raw byte length in the way needed to prevent allocation of huge zero-padded arrays for a small `multComplexity`, since `baseLen`/`modLen` directly drive both the energy formula and allocation size but a moderate combination of large `modLen` with small effective exponent can still allow a large but not-infeasible energy cost while allocating gigabyte-scale arrays).

### Impact Explanation
Repeated or single such calls (from a plain, unprivileged contract call — any account able to invoke the precompiled contract address for ModExp) can force the `mod` byte array allocation (`new byte[modLen]` at line 723 for the zero-modulus path, or the full `parseArg`-driven `BigInteger` construction) to be gigabyte-scale, causing significant JVM heap pressure. Under memory pressure this can cause the `FullNodeApplication`/witness node process to be OOM-killed by the OS, resulting in denial of service / node crash — matching the "node crash or halt" acceptance criterion.

### Likelihood Explanation
Reachable from a single signed transaction that invokes the ModExp precompile (address `0x05`) with a crafted `data` payload containing large length words; no special privileges beyond enough energy for the call are required. Likelihood depends on whether the target network has activated the Osaka fork (`allowTvmOsaka`) — pre-Osaka networks/private chains remain exposed. I could not verify with certainty whether TIP-7823 (Osaka) is already activated on TRON mainnet as of the current chain state; that would need to be confirmed against live `ForkController` state before treating this as exploitable on mainnet today.

### Recommendation
Enforce the `UPPER_BOUND` (or an equivalent memory-safety bound) on `baseLen`, `expLen`, and `modLen` unconditionally in `ModExp.execute()` (and consistently in `getEnergyForData()`), independent of the `allowTvmOsaka()` fork gate, so that pre-fork or non-upgraded deployments are also protected. Additionally, harden `ByteUtil.parseBytes()` (or its ModExp-specific callers) to cap `len` against a sane absolute limit before allocation, rather than trusting a fully attacker-controlled `int`.

### Proof of Concept
Construct call data to the ModExp precompiled contract address with:
```
baseLen = 0x7FFFFFFF (32-byte word)
expLen  = 0x00000001
modLen  = 0x7FFFFFFF
[minimal trailing bytes]
```
Under non-Osaka configuration (`VMConfig.allowTvmOsaka() == false`), `execute()` skips the `UPPER_BOUND` check at [4](#0-3)  and calls `parseArg(data, ARGS_OFFSET, baseLen)` and `parseArg(data, ..., modLen)`, each internally allocating a `byte[0x7FFFFFFF]` (~2GB) array via `parseBytes` [1](#0-0) , from a payload only slightly larger than 96 bytes. This is analogous to the test harness pattern already present in the repo for boundary testing of ModExp lengths [6](#0-5) , but with `VMConfig.initAllowTvmOsaka(0)` (or the fork inactive) to bypass the `UPPER_BOUND` guard.

  public static byte[] parseBytes(byte[] input, int offset, int len) {

    if (offset >= input.length || len == 0) {
      return EMPTY_BYTE_ARRAY;
    }

    byte[] bytes = new byte[len];
    System.arraycopy(input, offset, bytes, 0, min(input.length - offset, len, true));
    return bytes;
  }
