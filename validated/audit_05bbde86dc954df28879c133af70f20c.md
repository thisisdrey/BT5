### Title
`nft_resolve_withdraw` re-credits `sender_id` on any non-void `nft_transfer` success, letting an attacker double-claim a withdrawn NFT - (File: `contracts/defuse/src/contract/tokens/nep171/withdraw.rs`)

### Summary
`nft_resolve_withdraw` treats *any* non-empty successful `nft_transfer` result as a failed transfer and refunds the withdrawn `Nep171TokenId` unit back to `sender_id`, because `promise_result_checked_void` rejects non-zero-length payloads regardless of whether the underlying transfer actually completed. Since `token` is fully attacker-controlled in the unprivileged threat model, the attacker can make `nft_transfer` succeed with a non-void return value, so the Verifier both (a) lets the transfer go through in the external NFT contract and (b) restores the debited internal balance.

### Finding Description
The broken binding: for a non-`is_call` withdraw, the invariant should be
`balance_debited_at_withdraw(1) == amount_transferred_externally(1) XOR amount_refunded_internally(1)`
i.e. exactly one of "transfer happened" or "refund happened" should be true.

Code path:
- `internal_nft_withdraw` (`contracts/defuse/src/contract/tokens/nep171/withdraw.rs:57-110`) debits 1 unit of `Nep171TokenId::new(token, token_id)` from `owner_id` via `self.withdraw(...)`, then schedules `do_nft_withdraw` → `nft_transfer` (void-returning per NEP-171), followed by `nft_resolve_withdraw`.
- `nft_resolve_withdraw` (lines 159-195) determines success for the non-call branch purely via:
```
promise_result_checked_void(0).is_ok()
```
- `promise_result_checked_void` (`crates/near/utils/src/promise.rs:64-72`) calls `env::promise_result_checked(result_idx, 0)`, i.e. it budgets **zero bytes** for the expected return value. Any promise that succeeds but returns a *non-empty* payload — even a single byte — causes `env::promise_result_checked` to return `Err`, not because the underlying call failed, but purely due to the length check. The `debug_assert!(data.is_empty())` after the `?` is compiled out in release builds and never actually validates emptiness on a successful, small, non-empty result — it can't be reached in that case anyway since the `?` already returns before it if length exceeds the budget, but conversely if `promise_result_checked` does NOT enforce the bound and instead just reads and truncates, the function still treats non-empty data as `Ok`, and `debug_assert!` would be the only check, compiled away in release. In either interpretation, a token contract that violates the NEP-171 void-return convention on `nft_transfer` cannot be distinguished from a genuinely failed transfer by this code.

Because `token` is an attacker-deployed and attacker-controlled contract (allowed in the threat model: "deploy and control their own... NFT... contracts"), the attacker implements `nft_transfer` to actually move the token to `receiver_id` internally while returning a small non-empty successful value (e.g. `true` or any JSON scalar) instead of the NEP-171-mandated void result. `nft_resolve_withdraw` then sees `used = false` and calls `self.deposit(sender_id, [(Nep171TokenId::new(token, token_id).into(), 1)], ...)`, restoring the exact unit that was already debited and already transferred out — while the transfer to `receiver_id` genuinely succeeded in the external contract's own storage.

No existing guard catches this: `#[private]` only restricts who may call the resolver, not the semantics of the promise result; there is no NEP-171 compliance/interface check; `promise_result_checked_json` is only used on the `is_call=true` branch, not here.

### Impact Explanation
The attacker's own withdrawn NFT unit is simultaneously (1) transferred out to `receiver_id` in the external (attacker-controlled) contract and (2) re-credited as `Nep171TokenId` balance inside the Verifier for `sender_id`. This is a resolver credit that does not match what actually failed to settle (the transfer did *not* fail), matching the Critical category "a refund or resolver credit that does not match what failed to settle." Because both the depositing token contract and the withdrawing account are attacker-controlled, the practical blast radius is limited to Verifier-internal balances of the attacker's *own* custom `Nep171TokenId`; genuine loss to third parties only materializes if that same `TokenId` balance is later used against another counterparty (e.g. traded in an intent, used as collateral) who is unaware the "recredited" unit no longer has a corresponding real asset. The bug is repeatable indefinitely per withdraw call on any token_id from any NFT contract the attacker deploys.

### Likelihood Explanation
Preconditions: attacker must deploy their own NFT contract with a non-compliant `nft_transfer` (returns a small non-empty successful value), deposit at least one unit of that `Nep171TokenId` into the Verifier (standard deposit flow), and call `nft_withdraw` with `msg=None` (`is_call=false`). No privileged role, relayer key, or victim signature is required — fully reachable by an ordinary account. Cost is minimal (one contract deployment + standard gas). Repeatable without limit across token_ids and withdraw calls.

### Recommendation
Do not rely on a strict zero-length budget to infer success/failure. Instead: 
1. Distinguish a promise `Err` (execution failure) from `Ok` with unexpected non-empty data — treat unexpected non-empty-but-successful results as `used = true` (transfer happened, do not refund) rather than `used = false`, since a non-panicking cross-contract call means the call executed.
2. Alternatively, bound `promise_result_checked` with a generous max length and explicitly check `data.is_empty()` in production code (not only via `debug_assert!`), returning success only when the panic actually occurred (`PromiseError`), never when data merely didn't match the expected void shape.

### Proof of Concept
`cargo test` (near-workspaces sandbox) plan:
1. Deploy a custom NFT contract `FakeNft` whose `nft_transfer` performs an internal ownership change to `receiver_id` but returns `Ok(true)` (non-void) via a raw JSON return instead of unit.
2. As `attacker`, mint a token in `FakeNft`, deposit it into the Defuse Verifier (standard `nft_transfer_call` deposit flow), asserting `token_balances[Nep171TokenId::new(fake_nft, token_id)] == 1` for `attacker`.
3. Call `nft_withdraw(token=fake_nft, receiver_id=attacker_wallet2, token_id, memo=None, msg=None)` with 1 yoctoNEAR attached.
4. Assert on both sides of the equality:
   - In `FakeNft`'s own storage, `owner_of(token_id) == attacker_wallet2` (the transfer genuinely happened).
   - In the Verifier, `token_balances[Nep171TokenId::new(fake_nft, token_id)]` for `attacker` is restored to `1` (the refund/re-credit fired).
5. Assert both are true simultaneously, proving the double-claim: one copy externally at `attacker_wallet2`, one balance unit still owned inside the Verifier by `attacker`. [1](#0-0) [2](#0-1) [3](#0-2)

#[near]
impl NonFungibleTokenWithdrawResolver for Contract {
    #[private]
    fn nft_resolve_withdraw(
        &mut self,
        token: AccountId,
        sender_id: AccountId,
        token_id: non_fungible_token::TokenId,
        is_call: bool,
    ) -> bool {
        let used = if is_call {
            // `nft_transfer_call` returns true if token was successfully transferred
            match promise_result_checked_json::<bool>(0) {
                Ok(Ok(used)) => used,
                Ok(Err(_deserialization_err)) => false,
                // do not refund on failed `nft_transfer_call` due to
                // NEP-141 vulnerability: `nft_resolve_transfer` fails to
                // read result of `nft_on_transfer` due to insufficient gas
                Err(_) => true,
            }
        } else {
            // `nft_transfer` returns empty result on success
            promise_result_checked_void(0).is_ok()
        };

        if !used {
            self.deposit(
                sender_id,
                [(Nep171TokenId::new(token, token_id).into(), 1)],
                Some(REFUND_MEMO),
            )
            .unwrap_or_else(|err| err.panic());
        }

        used
    }
}

/// Returns `Ok(())` if the promise at `result_idx` succeeded with an empty result.
/// This is the expected outcome for void-returning cross-contract calls
/// (e.g. `ft_transfer`, `nft_transfer`, `mt_batch_transfer`).
#[inline]
pub fn promise_result_checked_void(result_idx: u64) -> PromiseResult<()> {
    let data = env::promise_result_checked(result_idx, 0)?;
    debug_assert!(data.is_empty());
    Ok(())
}
