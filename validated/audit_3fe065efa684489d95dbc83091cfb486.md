### Title
Attacker fills a victim's `depositTokensOfAccount` list to `MAX_TOKENS_PER_USER` via dust deposits/transfers, blocking the victim from depositing new collateral - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
`Pool` keeps a per-account set of deposit/debt tokens capped at `MAX_TOKENS_PER_USER = 30`. Whenever a `DepositToken` balance goes from `0` to non-zero — via `deposit(..., onBehalfOf_)` or via a plain ERC20 `transfer`/`transferFrom`/`seize` — `Pool.addToDepositTokensOfAccount(recipient)` is invoked, and it reverts with `UserReachedMaxTokens` once the combined list length hits 30. Because the revert happens inside `_mint`/`_transfer`, the entire deposit/transfer transaction reverts. An unprivileged attacker can permissionlessly push dust amounts of every registered `DepositToken` into a victim's account, exhausting the cap and preventing the victim from adding any *new* collateral type.

### Finding Description
- `Pool.addToDepositTokensOfAccount` enforces the cap in `onlyIfAdditionWillNotReachMaxTokens`: `debtTokensOfAccount.length(account_) + depositTokensOfAccount.length(account_) >= MAX_TOKENS_PER_USER` reverts. [1](#0-0) 
- It is called with the *recipient* as `account_`, with no opt-in from the recipient, from `DepositToken._mint` and `DepositToken._transfer` whenever `balanceOf[recipient]` was previously `0`. [2](#0-1) [3](#0-2) 
- `DepositToken.transfer` only checks the *sender's* unlocked balance (`_revertIfLocked(_msgSender, amount_)`); the recipient is fully attacker-chosen. [4](#0-3) 
- `DepositToken.deposit(amount_, onBehalfOf_)` lets anyone mint shares to an arbitrary `onBehalfOf_` beneficiary — the attacker does not even need to hold shares first. [5](#0-4) 

Attack path (all public entry points, no privileged role):
1. For each `DepositToken` registered in the pool (`depositTokens` set), the attacker calls `depositToken.deposit(1 wei-equivalent, victim)` or buys dust and calls `depositToken.transfer(victim, 1)`.
2. Each first-time balance triggers `addToDepositTokensOfAccount(victim)`, growing the victim's list. This costs the attacker only dust of each underlying (recoverable later by withdrawing).
3. Once `debtTokens + depositTokens` for the victim reaches 30, any subsequent `deposit` of a new collateral type, `transfer`/`transferFrom` of a token the victim doesn't hold, or `seize` to a fresh liquidator account with a full list reverts in `Pool` and rolls back.

This is the direct analog of the Dovecot memory leak: repeated attacker-controlled allocations (per-account set entries instead of heap objects) accumulate in a long-lived process/account until the account hits a hard resource limit and further legitimate operations abort.

### Impact Explanation
- A victim whose list is filled cannot deposit any additional collateral types. If their position is near the liquidation threshold, they cannot add a new collateral to restore health — their existing position can be liquidated while the remediation path reverts.
- The victim also cannot receive airdropped/transferred `msdTOKEN` shares of a new type, and liquidation proceeds cannot be seized into a fresh liquidator account that is itself at the cap.
- Recovery requires the victim to transfer away the dust shares to free slots (each transfer calls `removeFromDepositTokensOfAccount` when the balance reaches zero), so funds are temporarily, not permanently, frozen — but only after the victim notices and pays gas per slot, and any liquidation occurring in the meantime is irreversible.
- Effectiveness depends on the pool having enough registered deposit tokens (the combined deposit+debt list must be fillable to 30); in pools with fewer collateral types the attack is proportionally weaker, and entries the victim already holds do not consume new slots.

### Likelihood Explanation
- Fully unprivileged: `deposit` and `transfer` are public, need no role, and `SynthContext`/reentrancy guards/pause flags do not restrict the recipient.
- Cost is bounded: dust amounts of each underlying plus gas; the underlying dust is recoverable afterward via `withdraw`.
- Limiting factor: the number of registered `DepositToken`s in the target pool must be large enough (together with the victim's debt tokens) to reach the 30-entry cap. On pools with few collaterals, or victims already holding many tokens, the attacker can only partially fill the list.
- Victims can self-mitigate by shedding dust balances, so sustained blocking requires the victim to remain unaware; the one-shot blocking of a rescue deposit before liquidation is the realistic exploit window.

### Recommendation
- Require recipient consent before adding to `depositTokensOfAccount`, or exempt `transfer` recipients from counting until they actively deposit (e.g., only `deposit` adds to the list, and `transfer` to a list-full account reverts *for the sender* rather than the recipient being unable to act).
- Alternatively, make `addToDepositTokensOfAccount` failure non-fatal inside `_transfer` (skip the accounting entry instead of reverting) so unsolicited dust cannot brick an account, and derive positions from balances rather than a capped list.
- As a lightweight mitigation, disallow `onBehalfOf_` deposits to accounts that did not opt in, or add a per-account allowlist toggle.

### Proof of Concept
Hardhat-style fork test sketch against a deployed `Pool` with ≥30 registered deposit tokens:

```ts
// Arrange: victim holds some collateral and an unhealthy-adjacent position.
const victim = victimSigner.address;
const depositTokens: DepositToken[] = await getAllDepositTokens(pool); // pool.getDepositTokens()

// Act: attacker deposits 1 unit of each underlying on behalf of the victim.
for (const dt of depositTokens) {
  const underlying = await ethers.getContractAt('IERC20', await dt.underlying());
  await underlying.connect(attacker).approve(dt.address, 1);
  await dt.connect(attacker).deposit(1, victim); // fills victim's depositTokensOfAccount
}

// Assert cap reached
const tokensOfVictim = await pool.getDepositTokensOfAccount(victim);
expect(tokensOfVictim.length + (await pool.getDebtTokensOfAccount(victim)).length)
  .to.be.gte(await pool.MAX_TOKENS_PER_USER());

// Victim tries to deposit a collateral type they don't yet hold -> reverts
const newDt = depositTokens.find(dt => !tokensOfVictim.includes(dt.address));
await expect(newDt.connect(victim).deposit(amount, victim))
  .revertedWithCustomError(pool, 'UserReachedMaxTokens');

// Consequently victim cannot top-up collateral; price move -> liquidate succeeds
await pool.connect(liquidator).liquidate(synthetic, victim, repayAmount, collateralDt);
```

If the pool has fewer than 30 deposit tokens, combine with the victim's existing debt tokens (each counts toward the same cap) to demonstrate the threshold.
