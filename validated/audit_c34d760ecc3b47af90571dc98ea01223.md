Based on the investigation, the KintoID bug class — a stale, unrefreshed piece of global state that a security check depends on, where refresh only happens on one code path but not on other paths that mutate the relevant underlying data — has a concrete structural analog in Nebula's firewall reload logic.

### Title
Firewall reload misses certificate `Networks()` changes, leaving `routableNetworks` stale after cert rotation - (File: interface.go)

### Summary
`Interface.reloadFirewall` decides whether to rebuild the firewall's certificate-derived state (`routableNetworks`/`assignedNetworks`) only by checking whether `firewall.*` config keys changed, or whether the certificate's `UnsafeNetworks()` changed. It never checks whether the certificate's `Networks()` (the VPN addresses assigned to this host) changed, even though `NewFirewall` builds `routableNetworks` from **both** fields.

### Finding Description
`NewFirewall` builds `f.routableNetworks` from the union of the certificate's `Networks()` and `UnsafeNetworks()`: [1](#0-0) 

On config/cert reload, `reloadFirewall` only compares the previous vs. new certificate's `UnsafeNetworks()` to decide whether a rebuild is warranted, and otherwise short-circuits if the `firewall` config section itself hasn't changed: [2](#0-1) 

There is no equivalent comparison for `curCert.Networks()`. If an operator rotates the node's own certificate to change its assigned `Networks()` (e.g., a new/removed VPN address) without also touching a `firewall.*` config key, `certUnsafeChanged` is `false`, `c.HasChanged("firewall")` is `false`, and the function returns early — the old `Firewall` object (with the old `routableNetworks`/`assignedNetworks` built from the stale `Networks()`) stays installed. This is structurally the same class of bug as `KintoID.lastMonitoredAt`: a security-relevant state derivation is refreshed on only one trigger path (`firewall config change` or `UnsafeNetworks change`) while another legitimate mutation path (`Networks()` change via cert rotation) silently bypasses the refresh.

### Impact Explanation
`f.routableNetworks` gates every single packet on the data path via the check in `Firewall.Drop`: [3](#0-2) 

If this set is stale after a legitimate cert rotation, the node will incorrectly enforce local-address routability decisions for all inbound/outbound packets — either dropping legitimate traffic to/from a newly assigned VPN address (denial of service for that host), or continuing to treat an address that is no longer assigned to this host as routable, depending on how the rotation changed the address set. Because `Drop()` runs on every packet for every peer, this silently affects the entire tunnel's traffic until an unrelated `firewall.*` config change happens to trigger a rebuild.

### Likelihood Explanation
This requires an operator-driven certificate rotation that changes `Networks()` without simultaneously changing `firewall.*` config and without changing `UnsafeNetworks()` — a plausible, ordinary maintenance operation (e.g., re-issuing a host cert with an additional VPN address) rather than a contrived edge case, making it a real-world-reachable staleness condition, not a purely theoretical one.

### Recommendation
Extend the staleness check in `reloadFirewall` to also compare `curCert.Networks()` against the firewall's currently tracked `assignedNetworks`, mirroring the existing `UnsafeNetworks()` comparison, so any change to the certificate's assigned networks also triggers a firewall rebuild — analogous to the report's recommendation to update `lastMonitoredAt` in every function that can invalidate the state, not just one.

### Proof of Concept
1. Start a node with a certificate whose `Networks()` = `[10.0.0.1/24]` and `UnsafeNetworks()` = `[]`.
2. Rotate the on-disk certificate to one with `Networks()` = `[10.0.0.1/24, 10.0.0.2/24]`, same `UnsafeNetworks()` = `[]`, and do not modify any `firewall.*` config key.
3. Trigger a config/cert reload (`SIGHUP`).
4. Observe `f.l.Debug("No firewall config change detected")` is logged (from [4](#0-3) ) and the firewall is not rebuilt — `routableNetworks` still lacks `10.0.0.2/24`, so all traffic addressed to/from the newly assigned network is dropped by [3](#0-2)  despite the certificate now legitimately authorizing it.

```go
func (f *Interface) reloadFirewall(c *config.C) {
	cs := f.pki.getCertState()
	curCert := cs.getCertificate(cert.Version2)
	if curCert == nil {
		curCert = cs.getCertificate(cert.Version1)
	}

	// The firewall builds its routableNetworks set from the certificate's UnsafeNetworks at construction.
	// Check to see if that set has changed, and if so, rebuild the firewall.
	certUnsafeChanged := curCert != nil && !slices.Equal(curCert.UnsafeNetworks(), f.firewall.unsafeNetworks)

	if !c.HasChanged("firewall") && !certUnsafeChanged {
		f.l.Debug("No firewall config change detected")
		return
	}
```
