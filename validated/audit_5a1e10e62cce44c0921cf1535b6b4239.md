### Title
Unprivileged front-running of vault `initialize()` permanently DoSes DAO protocol launch finalization - (File: `mainnet/contracts/vault/v0-vault-stx.clar` and sibling vault contracts)

### Summary
Each vault contract (`v0-vault-stx.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`, `v0-vault-ststxbtc.clar`) exposes a public `initialize` function that is gated only by an `initialized` flag, with no DAO/authorization check, mirroring the reported `UniswapV3Pool.initialize()` pattern where a permissionless initializer can be called ahead of the intended orchestrated setup, permanently breaking the finalization flow.

### Finding Description
`initialize` in the vault contracts only checks that it hasn't run yet before flipping the flag and performing the minimum-liquidity seed deposit: [1](#0-0) 

There is no `check-dao-auth`/`check-caller-auth` call in this function, unlike essentially every other privileged setter in the same contract (`set-cap-supply`, `set-authorized-contract`, `set-pause-states`, etc., which all call `(try! (check-dao-auth))`), e.g.: [2](#0-1) 

The intended launch flow is for the DAO proposal to set supply/debt caps, then call `initialize` on each vault as part of one atomic transaction, followed by authorizing the market contract: [3](#0-2) 

Because `initialize` is a standalone public function reachable by any principal, an attacker can call it directly on a freshly deployed vault before the DAO's launch-finalization proposal executes. `initialize` sets `var-set initialized true` unconditionally on success and then performs `(deposit MINIMUM-LIQUIDITY u0 NULL-ADDRESS)`, using `MINIMUM-LIQUIDITY` (u1000) as the seed amount: [4](#0-3) 

If the attacker holds (or, for `.wstx`, can wrap) at least `MINIMUM-LIQUIDITY` units of the underlying and the supply cap at that moment permits it, they can front-run and complete this call themselves. Once `initialized` is `true`, the subsequent DAO proposal call to the same `initialize` function will unconditionally hit `(asserts! (not (var-get initialized)) ERR-ALREADY-INITIALIZED)` and abort — reverting the entire proposal transaction (since it's wrapped in `try!` inside `execute`), including the cap-setting and market-authorization steps bundled with it. This is the exact analog of the reported bug: a permissionless call to an initializer that is supposed to run only as part of an orchestrated finalization sequence can be front-run to deny that finalization.

### Impact Explanation
A successful front-run permanently prevents the DAO's one-shot `proposal-init-vaults`/`v0-init` proposal from succeeding as written, since it will always revert at the `initialize` call for the targeted vault. Until the DAO redeploys a corrected initializer or a patched proposal, the affected vault cannot be authorized for the market and caps cannot be applied via that bundled proposal, freezing the ability of ordinary users to supply/borrow against that asset — a temporary freezing of funds for that market until governance intervenes with a new proposal, which lands in the in-scope High impact category.

### Likelihood Explanation
Likelihood is moderate: the attacker needs no privileged access, only enough of the underlying token (as little as `MINIMUM-LIQUIDITY` = 1000 base units) and knowledge of the deployment address before the DAO's finalization proposal is submitted/executed — deployment addresses and contract code are public once deployed, and the window between vault deployment and DAO proposal execution is exactly the race window exploited in the original Trugly report.

### Recommendation
Restrict `initialize` to be callable only by the DAO/authorized executor context (e.g., require `check-dao-auth` or an equivalent as-contract/executor check), matching the pattern already used by other privileged setters in the same file, or fold the seed-liquidity deposit into vault deployment/contract construction so it cannot be triggered as an independent public call.

### Proof of Concept
1. Vault contract (e.g. `vault-stx`) is deployed on mainnet but the DAO's launch proposal (`proposal-init-vaults`/`v0-init`) has not yet been executed.
2. Attacker acquires `MINIMUM-LIQUIDITY` (1000) units of the underlying token (`.wstx`).
3. Attacker calls `vault-stx.initialize` directly; the function passes the `not initialized` check, sets `initialized` to `true`, and performs the seed deposit to `NULL-ADDRESS`.
4. The DAO subsequently submits and executes its launch-finalization proposal, which internally calls `(contract-call? .vault-stx initialize)`; this now returns `ERR-ALREADY-INITIALIZED`, causing the wrapped `try!` to abort the whole proposal transaction, blocking cap configuration and market authorization for that vault.
