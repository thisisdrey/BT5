## Finding

`ExchangeWithdrawActuator` reproduces the exact bug class from the Vader report: a fund-receiving operation whose output amount is computed from *live* pool state at execution time, with **no user-supplied minimum-received parameter** to protect against front-running/sandwich manipulation of that pool state — unlike its sibling `ExchangeTransactionActuator`, which does implement this protection via an `expected` field.

### Title
Missing minimum-received (slippage) protection in `ExchangeWithdrawContract` allows front-running of exchange liquidity withdrawals - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
`ExchangeWithdrawContract`/`ExchangeWithdrawActuator` lets the creator of a Bancor-style `Exchange` pool withdraw one side of the pool's reserves and receive a proportional amount of the other token, computed from the pool's current `firstTokenBalance`/`secondTokenBalance` ratio at execution time. Unlike `ExchangeTransactionContract`, which carries an `expected` field enforced at [1](#0-0) , the withdraw contract has no such field, so the withdrawer cannot bound the minimum amount of the paired token they are willing to accept.

### Finding Description
The protobuf definition of `ExchangeWithdrawContract` only carries `owner_address`, `exchange_id`, `token_id`, and `quant` — no `expected`/minimum-amount field: [2](#0-1) 

In `ExchangeWithdrawActuator.execute`, the amount of the counter-token (`anotherTokenQuant`) returned to the caller is computed purely from the exchange pool's live balances at the moment the transaction is applied: [3](#0-2) 

`doValidate` only checks that the computed ratio is "precise enough" relative to itself (a rounding-tolerance check, not a user-specified floor), and that the amount is `> 0`: [4](#0-3) 

Because pool balances (`firstTokenBalance`/`secondTokenBalance`) can be shifted by any unprivileged account broadcasting `ExchangeTransactionContract` trades against the same `exchange_id` immediately before the withdraw transaction is applied in `Manager`'s block-application/transaction-processing loop, an attacker observing a pending `ExchangeWithdrawContract` in the mempool can submit a trade to skew the ratio, causing the withdrawer to receive materially less of the paired asset than the pool state implied when they signed their transaction — with no on-chain mechanism to reject the unfavorable outcome.

This is the same root cause as the referenced Vader finding: a value-returning operation determined by mutable pooled reserves, reachable by any transaction submitter, with no caller-specified minimum-received guard.

### Impact Explanation
The exchange creator (the only account authorized to call withdraw, per the creator check at [5](#0-4) ) can be sandwiched by any unprivileged party broadcasting an `ExchangeTransactionContract` against the same pool, resulting in the withdrawer permanently receiving fewer paired tokens than the pool ratio warranted when the withdrawal was authorized. This is a concrete loss of funds for the withdrawing party, reachable purely through normal transaction broadcast — no privileged role required by the attacker.

### Likelihood Explanation
Any account can call `ExchangeTransactionActuator` to move `firstTokenBalance`/`secondTokenBalance` in an `Exchange`/`ExchangeV2` pool right before a known pending `ExchangeWithdrawContract` executes (classic mempool front-running), since transaction contents are visible before inclusion. No malicious-SR, malicious-witness, or privileged assumption is needed — a plain unprivileged transaction broadcaster suffices, matching the scope constraints of this scan.

### Recommendation
Add a `expected` (or `min_another_token`) field to `ExchangeWithdrawContract`, and in `ExchangeWithdrawActuator.doValidate`/`execute`, require that the computed `anotherTokenQuant` be `>= expected`, mirroring the check already present in `ExchangeTransactionActuator` (`anotherTokenQuant < tokenExpected` → revert). This closes the same class of MEV/front-running exposure the external Vader report describes.

### Proof of Concept
1. Exchange creator submits `ExchangeWithdrawContract{exchange_id=X, token_id=firstToken, quant=Q}`, expecting `anotherTokenQuant = secondBalance*Q/firstBalance` based on current pool state.
2. Before this transaction is applied, an attacker broadcasts `ExchangeTransactionContract` trading against pool `X`, shifting `firstTokenBalance`/`secondTokenBalance` (e.g., dumping `secondToken` into the pool to depress its relative value).
3. When the withdraw transaction executes, `ExchangeWithdrawActuator.execute` recomputes `anotherTokenQuant` from the now-skewed balances [6](#0-5) , yielding a smaller payout than the creator anticipated, with no field available in the contract to reject this outcome.
