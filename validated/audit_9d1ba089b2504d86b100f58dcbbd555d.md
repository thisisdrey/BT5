### Title
Unbounded growth of `committedEntries` causes O(n) conflict-check scans under a partition-wide lock, enabling a low-cost DoS of Gitaly's transaction commit path - (File: internal/gitaly/storage/storagemgr/partition/transaction_manager.go)

### Summary
`TransactionManager` keeps every committed write-ahead-log entry that a still-active snapshot reader might need in an in-memory linked list, `committedEntries` [1](#0-0) . On every transaction commit that has a KV read-set or a housekeeping operation, the manager calls `walkCommittedEntries`, which iterates the **entire** list front-to-back while holding `mgr.mutex` [2](#0-1) . This mirrors the Nomad `Queue.contains()` pattern flagged in the external report: an attacker-influenceable, ever-growing list is linearly scanned by a hot-path integrity check, and the scan happens under a lock that also serializes other manager-critical sections (`appendLogEntry`, `applyLogEntry`, snapshot bookkeeping) [3](#0-2) .

### Finding Description
`committedEntries` entries are only evicted "when there are no active readers accessing the corresponding snapshots" [1](#0-0) , i.e. they are pinned by any transaction (read or write) whose snapshot LSN predates the entry. `TransactionManager` is a **single-writer per partition/repository** that processes the admission queue serially in `run()` [4](#0-3) , so any slow-down in `processTransaction` throttles every subsequent write to that repository.

`verifyKeyValueOperations` walks `committedEntries` whenever the committing transaction has a non-empty KV read-set [5](#0-4) , and `verifyHousekeeping`/`verifyRepacking` walk it on every housekeeping commit (pack-refs, repack) to check for concurrent housekeeping conflicts and pruned-object dependencies [6](#0-5) [7](#0-6) . Both housekeeping and ordinary pushes (which internally use KV metadata) are triggerable by any ordinary, unprivileged user via normal push/fetch traffic — Gitaly automatically schedules housekeeping after pushes, and each RPC that opens a transaction (`Begin`) takes a snapshot that can pin the list open if the RPC is long-running (e.g., a slow clone/fetch/blame holding a repository snapshot).

Because entries are only appended (`PushBack`) and never bounded in size except by eviction tied to reader lifetime [8](#0-7) , an unprivileged actor who (a) keeps several long-lived read snapshots open against a repository (via ordinary slow RPCs) and (b) concurrently drives many small commits/housekeeping runs against the same repository can grow `committedEntries` without bound. Every subsequent commit that needs conflict checking then pays an O(n) cost under `mgr.mutex`, and since the manager is single-writer, this degrades or stalls all writes to the affected repository/partition — directly analogous to the reachable, unprivileged, costly-but-real availability attack described for Nomad's `improperUpdate`/`Queue.contains()`.

### Impact Explanation
This is a genuine availability risk scoped to a repository/partition: growth of `committedEntries` inflates the cost of every subsequent commit's conflict check, and because `mgr.mutex` also guards `appendLogEntry`/`applyLogEntry`/snapshot-lock bookkeeping, contention here can serialize and slow down all write traffic to the partition, not just the specific transaction performing the scan. This matches the "DoS of a handler" acceptance criterion — RPC handlers backed by this `TransactionManager` (writes/pushes/housekeeping) can be starved.

### Likelihood Explanation
Reaching this condition requires an attacker to be able to (1) keep multiple concurrent, long-running read transactions open against a targeted repository via normal RPCs, and (2) generate a sustained stream of commits with KV read-sets or housekeeping operations against that same repository — both achievable by an ordinary authenticated Git user without any special privileges, though it does require sustained/concurrent traffic (higher cost than a single request, similar to the "costly to perform" characterization Connext gave the analogous Nomad issue). I was not able to fully trace the exact eviction trigger function (`updateCommittedEntry`) or confirm precise numeric thresholds within the given iteration budget, so the magnitude of achievable list growth and the resulting latency impact are not fully quantified from the code alone.

### Recommendation
Bound the growth of `committedEntries` independently of reader pinning — e.g., cap the number of retained entries or the retention window, and/or replace the linear `list.List` scan in `walkCommittedEntries` with an index keyed by LSN so lookups/conflict checks are O(log n) or O(1) rather than O(n). Consider narrowing the critical section so the list traversal in `verifyKeyValueOperations`/`verifyHousekeeping` does not hold `mgr.mutex` for its full duration, and add metrics/alerts on `committedEntries` length so operators can detect abnormal growth.

### Proof of Concept
Conceptual (not executed): 
1. Open several long-lived RPCs against a target repository that create read-only transactions with old snapshot LSNs (e.g., slow `GetBlob`/blame/streaming clone) and keep them open.
2. Concurrently issue many small pushes and/or rely on Gitaly's automatic post-push housekeeping against the same repository so that `appendLogEntry` keeps appending to `committedEntries` [8](#0-7) .
3. Because the RPCs from step 1 keep snapshot readers open, entries are not evicted, so `committedEntries` grows unbounded.
4. Every subsequent commit against the repository that has a KV read-set or triggers housekeeping now calls `walkCommittedEntries`, scanning the full (growing) list under `mgr.mutex` [2](#0-1) , increasing per-commit latency and — since the manager is single-writer per partition — throttling all writers to that repository.

// verifyKeyValueOperations checks the key-value operations of the transaction for conflicts and includes
// them in the log entry. The conflict checking ensures serializability. Transaction is considered to
// conflict if it read a key a concurrently committed transaction set or deleted. Iterated key prefixes
// are predicate locked.
func (mgr *TransactionManager) verifyKeyValueOperations(ctx context.Context, tx *Transaction) error {
	defer trace.StartRegion(ctx, "verifyKeyValueOperations").End()

	if readSet := tx.recordingReadWriter.ReadSet(); len(readSet) > 0 {
		if err := mgr.walkCommittedEntries(tx, func(entry *gitalypb.LogEntry, _ map[git.ObjectID]struct{}) error {
			for _, op := range entry.GetOperations() {
				var key []byte
				switch op := op.GetOperation().(type) {
				case *gitalypb.LogEntry_Operation_SetKey_:
					key = op.SetKey.GetKey()
				case *gitalypb.LogEntry_Operation_DeleteKey_:
					key = op.DeleteKey.GetKey()
				}

				stringKey := string(key)
				if _, ok := readSet[stringKey]; ok {
					return newConflictingKeyValueOperationError(stringKey)
				}

				for prefix := range tx.recordingReadWriter.PrefixesRead() {
					if bytes.HasPrefix(key, []byte(prefix)) {
						return newConflictingKeyValueOperationError(stringKey)
					}
				}
			}

			return nil
		}); err != nil {
			return fmt.Errorf("walking committed entries: %w", err)
		}
	}

// appendLogEntry appends a log entry of a transaction to the write-ahead log. After the log entry is appended to WAL,
// the corresponding snapshot lock and in-memory reference for the latest appended LSN is created.
func (mgr *TransactionManager) appendLogEntry(ctx context.Context, objectDependencies map[git.ObjectID]struct{}, logEntry *gitalypb.LogEntry, logEntryPath string) error {
	defer trace.StartRegion(ctx, "appendLogEntry").End()

	// After this latch block, the transaction is committed and all subsequent transactions
	// are guaranteed to read it.
	appendedLSN, err := mgr.logManager.AppendLogEntry(logEntryPath)
	if err != nil {
		return fmt.Errorf("append log entry: %w", err)
	}

	mgr.mutex.Lock()
	mgr.committedEntries.PushBack(&committedEntry{
		lsn:                appendedLSN,
		entry:              logEntry,
		objectDependencies: objectDependencies,
	})
	mgr.mutex.Unlock()

	return nil
}

// walkCommittedEntries walks all committed entries after input transaction's snapshot LSN. It loads the content of the
// entry from disk and triggers the callback with entry content.
func (mgr *TransactionManager) walkCommittedEntries(transaction *Transaction, callback func(*gitalypb.LogEntry, map[git.ObjectID]struct{}) error) error {
	mgr.mutex.Lock()
	defer mgr.mutex.Unlock()

	for elm := mgr.committedEntries.Front(); elm != nil; elm = elm.Next() {
		committed := elm.Value.(*committedEntry)
		if committed.lsn <= transaction.snapshotLSN {
			continue
		}

		if committed.entry == nil {
			return errCommittedEntryGone
		}
		// Transaction manager works on the partition level, including a repository and all of its pool
		// member repositories (if any). We need to filter log entries of the repository this
		// transaction targets.
		if committed.entry.GetRelativePath() != transaction.relativePath {
			continue
		}
		if err := callback(committed.entry, committed.objectDependencies); err != nil {
			return fmt.Errorf("callback: %w", err)
		}
	}
	return nil
}
