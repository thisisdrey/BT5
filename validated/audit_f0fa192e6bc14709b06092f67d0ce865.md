## Title
Donation attack on `pallet-asset-conversion` pools: raw token balance used as pool reserve for pricing and LP-share math - (File: `substrate/frame/asset-conversion/src/lib.rs`)

## Summary
`pallet-asset-conversion` computes pool "reserves" by directly reading the token balance held at the pool's derived account (`Self::get_balance(&pool_account, asset)` / `Self::get_reserves(...)`), the same broken pattern flagged in the Connext report: any account can transfer tokens directly to the pool account (bypassing `add_liquidity`) and inflate the balance the pallet treats as authoritative reserve data, exactly as anyone could inflate Connext's custodied amount by sending tokens straight to the Diamond contract.

## Finding Description
`get_reserves` reads reserve amounts purely from the pool account's on-chain balance: [1](#0-0) 

`do_add_liquidity` also pulls `reserve1`/`reserve2` from `Self::get_balance(&pool_account, ...)` before computing the optimal deposit ratio and, for non-empty pools, the LP token mint amount via `mul_div(&amount1, &total_supply, &reserve1)`: [2](#0-1) 

`do_remove_liquidity` uses the same balance-derived reserves to compute withdrawal amounts: [3](#0-2) 

Swap quoting (`quote_price_exact_tokens_for_tokens`, `quote_price_tokens_for_exact_tokens`) and the actual swap execution path (`get_amount_out`/`get_amount_in`, via `balance_path_from_amount_in`) likewise consume `get_reserves`, which is nothing more than the pool account's ERC20/`pallet-assets`-style balance: [4](#0-3) [5](#0-4) 

There is no internally tracked reserve counter analogous to Connext's recommended fix (maintaining custodied amount on `handleIncomingAsset`/`handleOutgoingAsset` rather than trusting `balanceOf`). A recent fix (`prdoc/pr_12408.prdoc`) shows the maintainers already touched this exact code path to switch from reducible to full balances for "pool prices," confirming the reserve calculation is balance-based and has known fragility around what balance is trusted: [6](#0-5) 

An attacker (any unprivileged account holding either pool asset) can call a plain `transfer` of `asset1` or `asset2` directly to the pool's derived account (obtainable via the public `PoolLocator`/`pool_address`), without going through `add_liquidity`. This silently changes `reserve1`/`reserve2` read by `get_reserves`/`get_balance` on the very next block, without any corresponding LP token mint and without the constant-product invariant being consciously updated by the pallet's own bookkeeping — the pallet has no bookkeeping other than "whatever tokens sit in the account."

## Impact Explanation
Because reserves are the sole inputs to `quote`, `get_amount_out`, `get_amount_in`, and LP-mint/burn math, an attacker can:
- Distort the AMM price used for swaps (`swap_exact_tokens_for_tokens`, `swap_tokens_for_exact_tokens`) immediately before another user's swap, worsening execution price for victims or enabling classic front/back-running-independent price skew.
- Manipulate the LP token mint ratio on `add_liquidity` (`side1 = amount1*total_supply/reserve1`, `side2 = amount2*total_supply/reserve2`, `lp_token_amount = side1.min(side2)`) by donating one asset right before another user's `add_liquidity` call, causing that user to receive fewer LP tokens than their contribution warrants, or causing the attacker's own subsequent LP mint calculation to be skewed.
- Distort `remove_liquidity` payouts (`amount1 = lp_redeem_amount * reserve1 / total_supply`) since `reserve1`/`reserve2` are balance-derived and can be inflated/deflated by direct donation between calls, changing the amount any LP token holder can redeem.

This falls squarely in the "Balances, assets, NFTs, staking, pools, treasury spends... must conserve value and settle exactly once to the rightful beneficiary and amount" impact category, and is a genuine implementation bug reachable by any unprivileged user with no need for a malicious validator, collator, or governance actor.

## Likelihood Explanation
The pool's account address is derivable by anyone via the public `PoolLocator`, and any account holding either underlying asset can execute a normal `transfer` to that address — this requires no special privilege, front-running infrastructure, or validator collusion. The attack is directly analogous in mechanics to the reported Connext issue (which was rated **Medium** and fixed) and to the well-known "donation attack" class against constant-product AMMs that read reserves from raw balance rather than internally tracked state.

## Recommendation
Do not derive `reserve1`/`reserve2` purely from `T::Assets::balance`/`get_balance` of the pool account. Maintain explicit, pallet-storage-tracked reserve counters per pool (updated only inside `do_add_liquidity`, `do_remove_liquidity`, and the swap execution path) and use those tracked values for all pricing/quoting/LP-mint math, exactly as recommended for Connext's `AssetLogic.handleIncomingAsset()`/`handleOutgoingAsset()` pattern. If donated dust must be reconciled, expose an explicit, permissioned "skim" operation rather than silently folding arbitrary incoming transfers into the reserve used for pricing.

## Proof of Concept
1. Create a pool for `(asset1, asset2)` via `create_pool`, and have user A call `add_liquidity` to seed it with `reserve1_before`, `reserve2_before`, obtaining LP tokens by the standard `calc_lp_amount_for_zero_supply` formula.
2. Attacker (any account holding `asset2`) calls the plain `pallet_assets::transfer` (or native `Balances::transfer` for the native asset) directly to `T::PoolLocator::pool_address(&asset1, &asset2)`, sending a large amount of `asset2` without calling `add_liquidity`.
3. `Self::get_reserves(asset1, asset2)` (and therefore `get_balance`) now reports an inflated `reserve2` because it just reads the pool account's raw balance: [1](#0-0) 
4. User B calls `add_liquidity` for `(asset1, asset2)`; `do_add_liquidity` computes `amount2_optimal = quote(amount1_desired, reserve1, reserve2)` and the LP mint via `side1/side2 = amount*total_supply/reserveX` using the attacker-skewed `reserve2`, minting B a distorted (generally smaller) LP token amount relative to the value they deposited: [7](#0-6) 
5. Alternatively, a swap executed against the skewed reserves via `quote_price_exact_tokens_for_tokens`/`get_amount_out` settles at a materially worse price than the true pre-donation market price, all without any privileged action — only two plain token transfers.

		pub fn quote_price_exact_tokens_for_tokens(
			asset1: T::AssetKind,
			asset2: T::AssetKind,
			amount: T::Balance,
			include_fee: bool,
		) -> Option<T::Balance> {
			// Swaps reject zero amounts, match that behavior.
			if amount.is_zero() {
				return None;
			}

			let pool_account = T::PoolLocator::pool_address(&asset1, &asset2).ok()?;

			let (balance1, balance2) = Self::get_reserves(asset1.clone(), asset2.clone()).ok()?;

			if balance1.is_zero() {
				return None;
			}

			let amount_out = if include_fee {
				let fee = Self::pool_fee_for(&asset1, &asset2).ok()?;
				Self::get_amount_out(fee, &amount, &balance1, &balance2).ok()?
			} else {
				Self::quote(&amount, &balance1, &balance2).ok()?
			};

			// Small inputs can round output to zero due to integer division.
			if amount_out.is_zero() {
				return None;
			}

			// Swap withdrawals from pools use `keep_alive=true` (Preserve). Use the same
			// preservation level to determine the actual withdrawable amount.
			let max_output = T::Assets::reducible_balance(asset2, &pool_account, Preserve, Polite);
			if amount_out > max_output {
				return None;
			}

			Some(amount_out)
		}
