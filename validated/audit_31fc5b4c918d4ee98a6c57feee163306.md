### Title
Residual SSRF via dumb-HTTP `http-alternates` bypasses the `transfer.bundleURI=false` mitigation - ([File: internal/gitaly/service/repository/create_repository_from_url.go])

### Summary
`cloneFromURLCommand` explicitly disables `transfer.bundleURI` to prevent the remote server from directing Gitaly's git process to fetch a bundle from an attacker-chosen (e.g. internal) URL, but this only closes one specific redirection mechanism. Git's legacy "dumb HTTP" transport supports an equivalent, in-band redirection primitive — `objects/info/http-alternates` — which is not restricted by `transfer.bundleURI`, by Git's `GIT_ALLOW_PROTOCOL` allowlist (http/https are always permitted), or by Gitaly's DNS-rebinding pinning (`http.curloptResolve`), because that pinning only fixes the IP for the originally-requested host, not for any additional host the attacker's response references.

### Finding Description
`CreateRepositoryFromURL` → `cloneFromURLCommand` builds a plain `git clone --bare|--mirror <url>` invocation, only ever hardening against bundle URIs: [1](#0-0) 

The only anti-SSRF measure for the URL itself is `GetURLAndResolveConfig`, which pins `http.curloptResolve` to the resolved IP that GitLab Rails already vetted for the *original* hostname: [2](#0-1) 

Both mitigations operate purely on the *outer* remote URL. Neither one inspects or constrains what the attacker's git server serves once the clone begins. If the attacker-controlled server does not answer the smart-HTTP `service=git-upload-pack` probe, `git clone` falls back to the legacy dumb-HTTP protocol, in which the client fetches loose objects/packs directly over plain HTTP GET requests, including honoring an `objects/info/http-alternates` (or `objects/info/alternates`) file that lists *additional* base URLs to pull objects from. Git's built-in `GIT_ALLOW_PROTOCOL` restriction (meant to stop `ext::`/arbitrary-command alternates) does not block `http://`/`https://` alternates, since HTTP is treated as a safe transport — it is exactly this class of "fetch from an attacker-chosen URL" behavior that the code comment says bundle-URI must guard against, but the guard is scoped only to `transfer.bundleURI` and does not touch the dumb-HTTP alternates mechanism.

Because the alternate URL is entirely attacker-supplied server-side content (not the `Url` field validated by GitLab Rails or by `http.curloptResolve`), Gitaly's git subprocess will issue an outbound HTTP request to whatever host the attacker lists (e.g. `http://169.254.169.254/latest/meta-data/` or `http://internal-service.local/`) as part of normal object retrieval during the clone, independent of the `transfer.bundleURI=false` setting.

### Impact Explanation
This is a Server-Side Request Forgery from Gitaly's network context, reachable by any unprivileged user who can trigger `CreateRepositoryFromURL` (e.g. via project import from a URL they control). It can be used to probe/read metadata endpoints such as cloud instance metadata services, internal-only HTTP services, or perform network reconnaissance from Gitaly's host/network — matching GitLab's SSRF bounty impact class.

### Likelihood Explanation
Preconditions are minimal and fully within the described unprivileged threat model: the attacker only needs to run a git server that they fully control and have GitLab import/clone from its URL, which is a normal supported feature (`CreateRepositoryFromURL` / project import by URL). No additional privilege, secret, or misconfiguration is required, and the attack is deterministic/repeatable since the attacker fully controls the server's protocol negotiation and response content.

### Recommendation
Do not rely solely on the `transfer.bundleURI=false` mitigation. Explicitly disable dumb-HTTP object retrieval and alternates-following for `CreateRepositoryFromURL` clones, e.g. by setting `http.protocolVersion` and using `-c http.allowReachableSHA1InWant=false` plus explicitly forcing smart-only transport, or setting `GIT_ALLOW_PROTOCOL` to a minimal safe set that also excludes alternates fetching, and/or configuring `protocol.version=2` with `uploadpack.allowFilter`/`http.followRedirects=false`. More robustly, apply the same egress/network isolation (e.g., outbound network allowlisting/proxy pinning per-request) at the process/network layer so that *any* additional outbound connection opened by the git subprocess during the clone — regardless of which git feature triggers it — is constrained to the pre-validated resolved address, rather than trying to enumerate and disable each individual git redirection feature (bundle URI, http-alternates, submodules, etc.) one at a time.

### Proof of Concept
1. Stand up an attacker HTTP server that:
   - Does *not* respond to `GET /info/refs?service=git-upload-pack` with the smart-HTTP content-type, forcing git to fall back to dumb-HTTP.
   - Serves a minimal dumb-HTTP repository layout under `/repo.git/`, including `objects/info/http-alternates` containing `http://169.254.169.254/latest/meta-data/` (or a local test HTTP listener representing an "internal" host).
2. Call `CreateRepositoryFromURL` with `Url: "http://attacker-server/repo.git"`.
3. Observe that during the clone, Gitaly's git subprocess issues an HTTP GET to the internal target URL listed in `http-alternates`, despite `transfer.bundleURI=false` being set — confirmed via request logging on the "internal" test listener.
4. Expected (secure) behavior: the clone should fail or refuse to contact any host other than the resolved/pinned original remote address; observed (vulnerable) behavior: outbound request reaches the attacker-chosen internal host.

func getURLAndResolveConfigForURL(remoteURL, resolvedAddress string) (string, []ConfigPair, error) {
	u, err := url.ParseRequestURI(remoteURL)
	if err != nil {
		return "", nil, fmt.Errorf("couldn't parse remoteURL: %w", err)
	}

	port := u.Port()

	if port == "" {
		switch u.Scheme {
		case "http":
			port = "80"
		case "https":
			port = "443"
		case "git":
			port = "9418"
		default:
			return "", nil, fmt.Errorf("unknown schema provided: %s", u.Scheme)
		}
	}

	return remoteURL, []ConfigPair{
		{Key: "http.curloptResolve", Value: fmt.Sprintf("%s:%s:%s", u.Hostname(), port, resolvedAddress)},
	}, nil
}
