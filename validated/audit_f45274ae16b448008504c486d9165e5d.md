### Title
Unbounded growth of `attachments` table via unchecked `insert_instantiated_attachment` with no size cap or hash verification - (File: stackslib/src/net/atlas/db.rs, stackslib/src/net/atlas/download.rs)

### Summary
`AtlasDB::insert_instantiated_attachment` has no capacity/eviction logic, unlike `insert_uninstantiated_attachment`, which enforces `max_uninstantiated_attachments` via `evict_k_oldest_uninstantiated_attachments`. Worse, `AttachmentsDownloader::run` calls `insert_instantiated_attachment` on every attachment byte-blob a peer returns for an `AttachmentRequest` without first checking that `attachment.hash()` equals the content hash that was actually requested, letting a malicious peer stuff the DB with unbounded attacker-chosen content while also improving its own "reliability" score for being repeatedly selected as the source.

### Finding Description
`insert_instantiated_attachment` (db.rs:576-592) unconditionally inserts into `attachments` with `was_instantiated = 1` and has no analog to the `max_uninstantiated_attachments`/`evict_k_oldest_uninstantiated_attachments` cap enforced in `insert_uninstantiated_attachment` (db.rs:511-521). No eviction function in this file ever targets `was_instantiated = 1` rows — `evict_k_oldest_uninstantiated_attachments` and `evict_expired_uninstantiated_attachments` both filter `WHERE was_instantiated = 0` (db.rs:538-560). [1](#0-0) [2](#0-1) 

More importantly, in `AttachmentsDownloader::run`, when a batch finishes, the code iterates every attachment collected from peer responses and calls `insert_instantiated_attachment(&attachment)` **before** verifying the returned content actually resolves any tracked instance — `resolve_attachment(&attachment.hash())` is only called afterward and is a no-op if the hash doesn't match anything tracked: [3](#0-2) 

The response collection step (`extend_with_attachments`) accepts and stores any successfully-decoded `GetAttachmentResponse` payload into `context.attachments` — there is no check there either that `response.attachment.hash()` equals the `content_hash` of the `AttachmentRequest` that was sent: [4](#0-3) 

Because `decode_atlas_get_attachment` only needs to hex-decode successfully to be treated as a "successful request" (`report.bump_successful_requests()` fires regardless of hash correctness), a malicious peer can return arbitrary, unique bytes (up to `attachments_max_size`, default 1MiB per `ATTACHMENTS_MAX_SIZE_MIN`) for every `AttachmentRequest` it is selected to answer, each time producing a new `hash(garbage)` row permanently stored via `insert_instantiated_attachment`, while simultaneously boosting its own reliability score, making it more likely to be picked again on retries. [5](#0-4) 

### Impact Explanation
Every accepted (but mismatched) attachment response permanently grows the `attachments` SQLite table with `was_instantiated = 1`, and this table has zero eviction/cap logic. This is disk exhaustion of the target node, driven by a remote peer that the node has chosen to sync attachments with (an outbound sync peer or inbound peer serving `/v2/attachments/{hash}` responses), repeatable across every unresolved attachment instance and every retry attempt (bounded by `max_attachment_retry_count` per batch, but each batch retry can inject a fresh unique blob). The attacker also gains an unintended advantage: bogus responses count as "successful" for reliability scoring, biasing future request routing toward the attacker.

### Likelihood Explanation
The attacker needs no privileged role — only to be selected as one of `network.get_outbound_sync_peers()` sources for a batch of `AttachmentRequest`s (reachable by any node willing to peer and respond to Atlas HTTP endpoints), and to serve fabricated inventory bits (already assumed reachable per the question) or simply be present among sources when the node's own legitimate `AttachmentInstance` queue (created from real, block-committed BNS/contract events) has entries. The requested `content_hash` values themselves are not attacker-forgeable (they derive from actual committed attachment instances), which caps the growth rate by the number of legitimate pending instances × retry count per batch rather than being instantaneously infinite; nonetheless, this is still unmitigated unbounded accumulation over time with no corresponding cap, unlike the uninstantiated-attachment path, and the attacker's cost is a handful of HTTP responses, not raw bandwidth flooding.

### Recommendation
1. In `AttachmentsDownloader::extend_with_attachments` (or immediately before `insert_instantiated_attachment` in `AttachmentsDownloader::run`), verify `attachment.hash() == request.content_hash` before accepting/storing the response; discard and penalize (bump failed, not successful) mismatched responses.
2. Add a capacity/eviction mechanism to `insert_instantiated_attachment` analogous to `insert_uninstantiated_attachment`/`evict_k_oldest_uninstantiated_attachments`, e.g. enforce a `max_instantiated_attachments` bound with LRU eviction, independent of the hash-check fix, as defense-in-depth against disk exhaustion.

### Proof of Concept
Rust test plan in `stackslib::net::atlas::download` (or an integration test driving `AttachmentsDownloader::run`):
1. Build an `AtlasDB` with a small `AtlasConfig` and one queued `AttachmentInstance` with a known `content_hash`.
2. Simulate `AttachmentsBatchStateMachine::try_proceed` → `extend_with_attachments` being fed a crafted `StacksHttpResponse` containing a `GetAttachmentResponse` whose `attachment.content` hashes to something other than `content_hash` (i.e., unrelated/garbage bytes), repeated N times with distinct content each time.
3. Assert that after each call, `atlas_db.find_attachment(&garbage_hash)` returns `Some(..)` (i.e., stored with `was_instantiated=1`), that the count of rows with `was_instantiated=1` grows by N, and that no eviction call is ever invoked (no function analogous to `evict_k_oldest_uninstantiated_attachments` exists for `was_instantiated=1` rows in `stackslib/src/net/atlas/db.rs`), confirming unbounded growth path via `insert_instantiated_attachment` (db.rs:576-592).

    pub fn insert_uninstantiated_attachment(
        &mut self,
        attachment: &Attachment,
    ) -> Result<(), db_error> {
        // Insert the new attachment
        let uninstantiated_attachments = self.count_uninstantiated_attachments()?;
        if uninstantiated_attachments >= self.atlas_config.max_uninstantiated_attachments {
            let to_delete =
                1 + uninstantiated_attachments - self.atlas_config.max_uninstantiated_attachments;
            self.evict_k_oldest_uninstantiated_attachments(to_delete)?;
        }

        let tx = self.tx_begin()?;
        let now = util::get_epoch_time_secs() as i64;
        let res = tx.execute(
            "INSERT OR REPLACE INTO attachments (hash, content, was_instantiated, created_at) VALUES (?, ?, 0, ?)",
            params![
                attachment.hash(),
                attachment.content,
                now,
            ],
        );
        res.map_err(db_error::SqliteError)?;
        tx.commit().map_err(db_error::SqliteError)?;
        Ok(())
    }

    pub fn evict_k_oldest_uninstantiated_attachments(&mut self, k: u32) -> Result<(), db_error> {
        let tx = self.tx_begin()?;
        let res = tx.execute(
            "DELETE FROM attachments WHERE hash IN (SELECT hash FROM attachments WHERE was_instantiated = 0 ORDER BY created_at ASC LIMIT ?)",
            params![k],
        );
        res.map_err(db_error::SqliteError)?;
        tx.commit().map_err(db_error::SqliteError)?;
        Ok(())
    }

    pub fn extend_with_attachments(
        mut self,
        results: &mut BatchedRequestsResult<AttachmentRequest>,
    ) -> AttachmentsBatchStateContext {
        for (request, response) in results.succeeded.drain() {
            let report = self
                .peers
                .get_mut(request.get_url())
                .expect("Atlas: unable to retrieve reliability report for peer");

            let response = if let Some(r) = response {
                r
            } else {
                report.bump_failed_requests();
                continue;
            };

            if let Ok(response) = response.decode_atlas_get_attachment() {
                self.attachments.insert(response.attachment);
                report.bump_successful_requests();
            } else {
                report.bump_failed_requests();
            }
        }
        let mut events_ids = results.faulty_peers.keys().copied().collect::<Vec<usize>>();
        self.events_to_deregister.append(&mut events_ids);

        self
    }
