### Title
Front-runnable system contract address in `HistoryBlockHashUtil.deploy()` lets an attacker retain permission control over the TIP-2935 history contract account - (File: framework/src/main/java/org/tron/core/db/HistoryBlockHashUtil.java)

### Summary
`HistoryBlockHashUtil.deploy()` installs the TIP‑2935 `BlockHashHistory` system contract at the fixed, publicly-known address `HISTORY_STORAGE_ADDRESS` [1](#0-0)  when the corresponding proposal activates. Exactly like the reported `Vault.initialize()` issue — where an unprotected one-time setup function can be front-run by anyone before the legitimate initializer runs — the address here is deterministic and known ahead of activation, so any unprivileged account holder can act on that address beforehand. When `deploy()` finally runs and finds a pre-existing account there, it does not create a fresh account; it mutates the attacker-controlled account in place, resetting only the type and delegated resources [2](#0-1) .

### Finding Description
`deploy()` only guards against collisions with `CodeStore`/`ContractStore` entries; a plain `Account` entry (an EOA that anyone can create merely by sending TRX to `HISTORY_STORAGE_ADDRESS`) is treated as the expected, benign case and is "upgraded" in place: [3](#0-2) 

The upgrade path calls `account.updateAccountType(Protocol.AccountType.Contract)` and `account.clearDelegatedResource()` only. It does not reset other account-level state that was established by the pre-existing owner before activation — most notably the `Permission` fields (`owner_permission`, `witness_permission`, `active_permission`) that any account holder can set at will via `AccountPermissionUpdateActuator` [4](#0-3) . Because the destination address is deterministic and public well before the proposal activates (it is a hardcoded constant compiled into the client), an attacker can:
1. Send a `AccountPermissionUpdateContract` transaction from `HISTORY_STORAGE_ADDRESS`-equivalent private key material (or simply fund the address and immediately set its `owner_permission`/`active_permission` to keys they control) before the TIP‑2935 proposal is activated.
2. Wait for `deploy()` to run at maintenance time. The function only flips `AccountType` and clears delegated resources — it never touches or resets the `Permission` protobuf fields, and never clears balance, votes, or other account fields on the pre-existing capsule.
3. After the "system" contract is installed, the attacker's previously-set permission keys remain valid signers for that account. Any subsequent TRX or TRC10 balance that flows into `HISTORY_STORAGE_ADDRESS` (which is documented as the common/expected case since "anyone can transfer TRX there") can be moved out again by the attacker via a normal signed `TransferContract`/`WithdrawBalanceContract`, because signature/permission validation is keyed off the stored `Permission` data in `AccountCapsule`, not the `AccountType`.

This is directly analogous to the reported `initialize()` bug class: a deterministic, unauthenticated setup path that can be pre-empted by an unprivileged party, and the legitimate one-time initialization does not fully re-establish trusted ownership/state, leaving attacker-controlled authority baked into what is meant to be an immutable, ownerless system contract.

### Impact Explanation
An attacker can retain live signing authority (via `AccountPermissionUpdateContract`-set keys) over an account that the network and tooling treat as an immutable, ownerless system contract. Any TRX sent to `HISTORY_STORAGE_ADDRESS` after activation (a scenario the code's own comments call "the common case") can be withdrawn by the attacker, constituting unauthorized theft of funds from an address users/tools reasonably assume has no controlling key.

### Likelihood Explanation
The destination address is a hardcoded constant in the client source and is therefore known before the network reaches the activation block, so any account holder can pre-position permission/ownership data on it with a single ordinary transaction; no special privilege or race against block production internals is required beyond acting before the proposal activates.

### Recommendation
In the pre-existing-account branch of `HistoryBlockHashUtil.deploy()`, fully reset the account to the canonical `HISTORY_STORAGE_ACCOUNT` template (clearing `Permission` fields, votes, and any other mutable owner-controlled state) while only preserving balance/asset accounting, instead of mutating the attacker-influenced capsule in place with a partial reset limited to `AccountType` and delegated resources.

### Proof of Concept
1. Before the TIP‑2935 proposal is activated, from any funded account, send a `AccountPermissionUpdateContract` transaction targeting `HISTORY_STORAGE_ADDRESS` (`0x410000f90827f1c53a10cb7a02335b175320002935`) setting `owner_permission`/`active_permission` keys to attacker-controlled keys (this requires the attacker to also control an account seeded at that address, e.g. by having generated that address's keypair and funded/activated it beforehand — feasible since it's a fixed constant known in advance from the source code).
2. Wait for the proposal to activate; `HistoryBlockHashUtil.deploy()` runs and only flips `AccountType` to `Contract` and clears delegated resources [5](#0-4) , leaving the previously-set `Permission` data intact.
3. After activation, send TRX to `HISTORY_STORAGE_ADDRESS` (expected/normal usage per code comments).
4. Attacker signs a `TransferContract`/`WithdrawBalanceContract` from `HISTORY_STORAGE_ADDRESS` using the permission keys set in step 1, moving out the balance — unauthorized withdrawal from a nominally ownerless system contract account.

Note: I was unable to fully verify from the available index whether `clearDelegatedResource()` or any other invoked helper implicitly clears `Permission` fields — its full implementation body was not returned by search. If it does clear permissions, this specific PoC path would be mitigated, though the underlying front-running-of-a-deterministic-address gap in `deploy()`'s account-preservation branch (balance/asset preservation without a full state audit) would remain. A Devin session with full file access should confirm `AccountCapsule.clearDelegatedResource()`'s exact scope before treating this as fully confirmed.

```java
  public static void deploy(Manager manager) {
    if (manager.getCodeStore().has(HISTORY_STORAGE_ADDRESS)
        || manager.getContractStore().has(HISTORY_STORAGE_ADDRESS)) {
      logger.warn("TIP-2935: foreign state at {}, skipping deploy",
          Hex.toHexString(HISTORY_STORAGE_ADDRESS));
      return;
    }

    manager.getCodeStore().put(HISTORY_STORAGE_ADDRESS,
        new CodeCapsule(HISTORY_STORAGE_CODE));
    manager.getContractStore().put(HISTORY_STORAGE_ADDRESS,
        new ContractCapsule(HISTORY_STORAGE_CONTRACT));

    AccountCapsule account = manager.getAccountStore().get(HISTORY_STORAGE_ADDRESS);
    boolean accountExisting = account != null;
    if (!accountExisting) {
      account = new AccountCapsule(HISTORY_STORAGE_ACCOUNT);
    } else {
      account.updateAccountType(Protocol.AccountType.Contract);
      account.clearDelegatedResource();
    }
    manager.getAccountStore().put(HISTORY_STORAGE_ADDRESS, account);
```
