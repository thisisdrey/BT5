### Title
Exchange pool creator funds become permanently frozen once either token reserve hits zero - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
The Bancor-style relay exchange (`ExchangeCapsule`/`ExchangeTransactionActuator`/`ExchangeWithdrawActuator`/`ExchangeInjectActuator`) treats an exchange whose `firstTokenBalance` or `secondTokenBalance` reaches exactly `0` as permanently "closed," rejecting *every* subsequent operation on that exchange — including the creator's own `ExchangeWithdrawContract` used to reclaim the remaining reserve. This mirrors the reported StRSR issue: a legitimate operation (a trade) can drive an internal pool value to zero, and the code has no analog of `beginEra()` to reset/recover the pool, so the non-zero side of the reserve becomes unrecoverable by any actuator.

### Finding Description
`ExchangeCapsule.transaction()` computes new token balances via the pluggable `Processor.exchange()` implementations (`ExchangeProcessor` for the legacy path, `SafeExchangeProcessor`/`SafeExchangeProcessor` for the hardened path): [1](#0-0) 

The legacy `ExchangeProcessor` performs the bancor relay math in `double` and truncates to `long` with `(long) exchangeBalance`, so the resulting `buyTokenQuant` is attacker-influenced and can be tuned (by choosing `sellTokenQuant`) to equal the full remaining `buyTokenBalance`: [2](#0-1) 

`ExchangeTransactionActuator.execute()` applies this result directly to the pool balances with no post-trade check that either side stays non-zero: [3](#0-2) 

Once a trade drives `firstTokenBalance` or `secondTokenBalance` to exactly `0`, every actuator that touches this exchange — `ExchangeTransactionActuator`, `ExchangeInjectActuator`, and critically `ExchangeWithdrawActuator` — rejects the transaction in `doValidate()` with the same guard: [4](#0-3) [5](#0-4) [6](#0-5) 

This is structurally identical to the StRSR report: the system enters a state (`stakeRSR == 0` / here `tokenBalance == 0`) that should trigger a "reset" (`beginEra()` in StRSR) but instead there is no reset path at all — the guard exists only to *reject* future operations, not to recover or redistribute the remaining reserve. Because `ExchangeWithdrawActuator` is blocked by the exact same zero-balance check, the creator has no way to withdraw the non-zero side of the pool (e.g., if `firstTokenBalance` hits `0` while `secondTokenBalance` is still large, that `secondTokenBalance` is permanently stuck in the exchange, since there is no other actuator or path that can move tokens out of `ExchangeCapsule`).

### Impact Explanation
This causes permanent freezing of funds: the exchange creator's remaining, legitimately-owned token reserve on the non-zeroed side becomes irretrievable once the other side hits `0`. There is no admin/governance/reset actuator for exchanges (unlike `StRSR.beginEra()`), so the loss is total and permanent for that exchange instance.

### Likelihood Explanation
The path is reachable by any unprivileged account via a normal `ExchangeTransactionContract` (market order) — no special privileges are required to trigger a trade that could reduce a balance to `0`. Reaching *exact* zero requires the attacker (or even the pool creator innocently) to select `sellTokenQuant` such that the floor-truncated bancor output in `ExchangeProcessor` equals the full remaining `buyTokenBalance`; since `sellTokenQuant` is a free long-integer input and the output is truncated downward, an attacker can iterate/binary-search values to hit this exact condition, making it a High-difficulty but concretely reachable edge case, consistent with the "High" difficulty rating in the referenced report.

### Recommendation
- **Short term:** When a trade, injection, or withdrawal would reduce `firstTokenBalance` or `secondTokenBalance` to exactly `0`, either reject the operation before committing state changes, or provide a dedicated "close exchange" path that atomically returns 100% of both remaining reserves to the creator instead of freezing them. Ensure `ExchangeWithdrawActuator` is never blocked from returning the creator's remaining balance once the pool is in a terminal state.
- **Long term:** Add fuzz/property tests around `ExchangeCapsule.transaction()` and the legacy `ExchangeProcessor` double-precision math to enumerate inputs that drive a reserve to `0`, and add an explicit safe-shutdown/reset mechanism for exchanges analogous to `StRSR.beginEra()`.

### Proof of Concept
1. Attacker or creator creates an exchange pool with `firstTokenBalance = A`, `secondTokenBalance = B` via `ExchangeCreateContract`.
2. Attacker (or any account with the sell-side token) submits repeated `ExchangeTransactionContract` trades selling `firstToken`, choosing `sellTokenQuant` values and observing the resulting `anotherTokenQuant` returned by `ExchangeCapsule.transaction()`/`ExchangeProcessor.exchange()`, iterating to find a value where the computed `buyTokenQuant` exactly equals the current `secondTokenBalance`.
3. Submit that trade; `ExchangeTransactionActuator.execute()` sets `secondTokenBalance = 0` while `firstTokenBalance` remains large and non-zero.
4. Creator now calls `ExchangeWithdrawContract` to recover the remaining `firstTokenBalance`; `ExchangeWithdrawActuator.doValidate()` throws `"Token balance in exchange is equal with 0, the exchange has been closed"` and the withdrawal is rejected.
5. No other actuator can move value out of `ExchangeCapsule`, so the remaining `firstTokenBalance` reserve is permanently frozen.
