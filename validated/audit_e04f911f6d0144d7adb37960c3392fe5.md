## Title
Rounding-down in `ExchangeInjectActuator`'s proportional-deposit calculation lets a pool creator systematically underpay the paired token, draining exchange reserves at zero fee - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`)

### Summary
`ExchangeInjectActuator` computes the amount of the paired token (`anotherTokenQuant`) a user must deposit alongside `tokenQuant` using integer/`BigInteger` division that truncates toward zero, exactly the rounding-truncation bug class described in the Catalyst-Exchange report (multiply-then-divide truncating instead of rounding up before pulling funds into the pool). Because the fee for this actuator is hard-coded to `0`, and the truncation always favors the caller (never rejected unless it rounds to `0`), the exchange creator can inject liquidity while paying strictly less of the paired token than the pool's price ratio requires, on every call, at no cost.

### Finding Description
In `ExchangeInjectActuator.execute()`: [1](#0-0) 

`anotherTokenQuant` is derived via `floorDiv(multiplyExact(secondTokenBalance, tokenQuant), firstTokenBalance)` (or the symmetric branch), i.e. `secondTokenBalance * tokenQuant / firstTokenBalance` using floor/truncating division. The identical truncating computation (`BigInteger.divide()`, which truncates toward zero) is repeated in `doValidate()`: [2](#0-1) 

The only guard on the result is `anotherTokenQuant <= 0` being rejected; there is no upper-bound "precision" check comparable to the one implemented for withdrawals in `ExchangeWithdrawActuator`, which explicitly re-derives the exact (non-truncated) ratio and rejects the operation when the truncation error exceeds 0.01%: [3](#0-2) 

`ExchangeInjectActuator` has no such "Not precise enough" check at all, so every inject silently rounds `anotherTokenQuant` down, favoring the depositor. In addition, `calcFee()` for this actuator returns `0`: [4](#0-3) 

so the truncation can be repeated an unlimited number of times without any TRX cost, other than ordinary bandwidth/energy, unlike the underwriting example in the report, which at least pays gas per call.

### Impact Explanation
Each `ExchangeInjectContract` call moves `tokenQuant` of one token and `anotherTokenQuant` (rounded down) of the paired token into the exchange's reserves (`exchangeCapsule.setBalance(...)`), while crediting the creator with a proportional increase of pool "ownership" (their own exchange). Because `anotherTokenQuant` is always truncated down and never re-topped-up, the actual paired-token contribution is systematically smaller than the price-ratio-implied amount. Repeated over many low-value injections (each losing up to 1 unit of the paired asset), an attacker who is (or creates, since anyone can call `ExchangeCreateContract`) the exchange creator can accumulate reserve balance/exchange-rate distortion cheaply, shifting the AMM's effective price against counterparties who subsequently trade against the same pool via `ExchangeTransactionActuator`, and can be exploited without paying any actuator fee. This mirrors the reported bug class: truncating multiply-then-divide rounding on the side of value flowing into the protocol causes an under-collateralization/loss of value relative to the intended invariant.

### Likelihood Explanation
Reachable directly and repeatedly by any account via a signed `ExchangeInjectContract` transaction (after self-issuing an `ExchangeCreateContract`, which is also open to any account). No special privilege beyond owning/creating the exchange is required, the fee is zero, and the rounding behavior is deterministic and always favors the caller, making the attack trivially and cheaply repeatable.

### Recommendation
Mirror the precision-check pattern already used in `ExchangeWithdrawActuator`: after computing `anotherTokenQuant` via truncating division, recompute the exact ratio with `BigDecimal`/`RoundingMode.HALF_UP` (or `CEILING`) and reject (or round up) when the truncation error is non-trivial, ensuring the paired-token deposit is never less than the price-ratio-implied amount. Consider also charging a nonzero `calcFee()` for `ExchangeInjectContract` to bound the number of free rounding-abuse iterations, consistent with other exchange operations.

### Proof of Concept
1. Attacker calls `ExchangeCreateContract` to create a new exchange with `firstTokenBalance = F`, `secondTokenBalance = S`, choosing `F` such that `S * tokenQuant` is not evenly divisible by `F` for small `tokenQuant`.
2. Attacker repeatedly submits `ExchangeInjectContract(exchangeId, tokenId=firstTokenID, quant=tokenQuant)` transactions with `calcFee()==0`.
3. Each call computes `anotherTokenQuant = floorDiv(S * tokenQuant, F)` in `ExchangeInjectActuator.execute()` (`actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java:73-74`), truncating the fractional remainder in the attacker's favor, with no "Not precise enough" check to catch it (contrast with `ExchangeWithdrawActuator.java:228-243`).
4. Repeating step 2 lets the attacker grow the pool's `firstTokenBalance` share while contributing less than proportional `secondTokenBalance`, shifting the exchange price to their advantage at zero actuator fee.
