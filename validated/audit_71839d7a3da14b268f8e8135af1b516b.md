### Title
Non-atomic replay-window check-then-decrypt-then-update race enables concurrent-replay decrypt amplification - (File: connection_state.go)

### Summary
`ConnectionState.Decrypt` and `ConnectionState.VerifyRelay` both consult the anti-replay window with `window.Check()`, drop the lock, perform an expensive AEAD decrypt, and only then re-acquire the lock to actually record the counter with `window.Update()`. Because the "is this a replay?" read and the "commit that we accepted this counter" write are not atomic with respect to each other, an attacker who merely captures one legitimate ciphertext packet off the wire (no CA-signed certificate of their own required) can resend many copies of it concurrently and force the victim to perform a full AEAD decrypt for every copy before the duplicate is finally rejected. This mirrors the GlpStrategy finding's root cause: a value used to authorize an action (`_currentBalance`, here `window.Check`) is read and trusted before the authoritative state mutation (`Update`) that should have prevented the duplicate work/benefit.

### Finding Description
The replay window `Bits` exposes two separate operations:
- `Check(l, i)` — read-only test of whether counter `i` looks unseen [1](#0-0) 
- `Update(l, i)` — the operation that actually marks `i` as seen and is the sole gate that can return `false` for a genuine duplicate [2](#0-1) 

`ConnectionState.Decrypt` calls these two operations across the *outside* of the actual decryption, releasing `decryptLock` in between: [3](#0-2) 

The same pattern exists in `VerifyRelay`, used for relay-forwarded packets which do not require the sender to hold a certificate trusted by the relay node itself: [4](#0-3) 

Because `decryptLock` is released between `Check` and the AEAD call, and `Check` does not itself mutate any state, two or more copies of the exact same on-the-wire ciphertext (same `messageCounter`) delivered to the UDP socket concurrently will each independently observe `Check(i) == true` before either has run `Update(i)`. Each copy therefore proceeds to the full `DecryptDanger` AEAD operation. Only after decryption does the code re-lock and call `Update`, at which point only the first caller wins; every other concurrent copy gets `ErrAlreadySeen` from `Update`, but has already paid the full decryption cost. The check that is supposed to gate expensive/authoritative work does not reflect the true, up-to-date "already accepted" state at the moment the expensive work is performed — exactly the accounting-timing gap described in the source report (an authorization decision made against a value that has not yet been updated to reflect the real, current state).

### Impact Explanation
An unauthenticated remote attacker who can observe (or otherwise obtain) a single legitimate Nebula UDP data packet — no certificate signed by the network's trusted CA is required, since the attacker is only replaying bytes, not participating in the handshake — can flood the target's socket with N concurrent duplicates of that one captured packet. Each copy forces a full AEAD decrypt (`DecryptDanger`) on the victim before being discarded, multiplying the attacker's minimal bandwidth cost into real CPU cost on the receiver. Because `readOutsidePackets`/`handleOutsideRelayPacket` route through this same `Decrypt`/`VerifyRelay` path for every inbound message and relay frame, this can be used to degrade Nebula node performance or attempt denial-of-service, i.e., a "sustained resource usage" impact from replayed/duplicate traffic.

### Likelihood Explanation
Likelihood is high in adversarial network conditions: any passive observer on a shared/untrusted network segment (Wi-Fi, cloud provider network, transit ISP) can capture one Nebula UDP frame and resend it many times in parallel without needing to complete a handshake or hold any certificate. The race window is real because the code explicitly documents and intends `decryptLock` to be released around the expensive `DecryptDanger` call, meaning the check-then-act gap is a designed property of the code, not an incidental timing fluke.

### Recommendation
Make replay acceptance atomic with the decision to spend decrypt work, or cheaply reject duplicates before doing the expensive operation on a per-attempt basis:
- Reserve the counter (tentatively mark it "in flight") under the same lock that performed `Check`, before releasing the lock for decryption, and roll back the reservation only on decrypt failure; or
- Track "counter currently being processed" state so that concurrent duplicates of the same `messageCounter` are rejected immediately rather than each independently reaching `DecryptDanger`.

### Proof of Concept
1. Establish a tunnel between two Nebula nodes and capture one outbound UDP `header.Message` frame (e.g., as done in `TestRelayReplayProtection`, which already demonstrates single-frame capture and replay injection). [5](#0-4) 
2. Instead of replaying the frame sequentially (as the existing regression test does [6](#0-5) ), replay dozens of copies of the exact same captured frame to the victim's UDP socket essentially simultaneously from multiple goroutines/sockets.
3. Because `Check` and `Update` are separated by the AEAD decrypt call with the lock released in between [3](#0-2) , every concurrently-delivered copy passes `Check` and performs a full `DecryptDanger` call; only after that does `Update` correctly reject all but one as a duplicate. Measuring CPU/decrypt-call counts under concurrent replay versus sequential replay will show each duplicate still incurs full decrypt cost, confirming the amplification.

func (b *Bits) Check(l *slog.Logger, i uint64) bool {
	// If i is the next number, return true.
	if i > b.current {
		return true
	}

	if b.strictlyWithinWindow(i) {
		return !b.get(i)
	}

	// Not within the window
	if l.Enabled(context.Background(), slog.LevelDebug) {
		l.Debug("rejected a packet (top)", "current", b.current, "incoming", i)
	}
	return false
}

func (b *Bits) Update(l *slog.Logger, i uint64) bool {
	// Fast path: i is the next expected counter. Split out so the function
	// stays small and avoids paying for the slow paths' slog argument-build
	// stack frame on every call. The bit read/test/write is inlined to
	// touch the backing word once.
	if i == b.current+1 {
		pos := i & b.lengthMask
		word := pos >> 6
		mask := uint64(1) << (pos & 63)
		w := b.bits[word]
		if i > b.length && w&mask == 0 {
			b.lostCounter.Inc(1)
		}
		b.bits[word] = w | mask
		b.current = i
		return true
	}
	return b.updateSlow(l, i)
}

func (cs *ConnectionState) Decrypt(l *slog.Logger, messageCounter uint64, out []byte, packet []byte, nb []byte) ([]byte, error) {
	var err error
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}

	out, err = cs.dKey.DecryptDanger(out, packet[:header.Len], packet[header.Len:], messageCounter, nb)
	if err != nil {
		return nil, err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}
	return out, nil
}

// VerifyRelay verifies AEAD protected (but not encrypted) relay frames. packet must be length-checked by the caller.
func (cs *ConnectionState) VerifyRelay(l *slog.Logger, messageCounter uint64, packet []byte, nb []byte) error {
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	signedPayload := packet[:len(packet)-cs.dKey.Overhead()]
	signatureValue := packet[len(packet)-cs.dKey.Overhead():]
	_, err := cs.dKey.DecryptDanger(nil, signedPayload, signatureValue, messageCounter, nb)
	if err != nil {
		return err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	return nil
}
