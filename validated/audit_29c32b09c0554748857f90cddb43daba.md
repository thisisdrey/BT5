### Title
Front-runnable global fee state initialization allows attacker to seize `global_fee_admin` and redirect protocol fees - ([File: programs/marginfi/src/instructions/marginfi_group/init_global_fee_state.rs])

### Summary
`init_global_fee_state` (and its v2 counterpart `init_global_fee_state_v2`) initializes the single, PDA-seeded `FeeState`/`FeeStateV2` account that is meant to be created exactly once, immediately after program deployment. Neither instruction verifies that the caller is the program's upgrade authority or any other known/trusted address — any signer able to pay rent can call it first and set the `global_fee_admin` and `global_fee_wallet` to their own keys.

### Finding Description
`InitFeeState` only requires a generic `payer: Signer<'info>` and creates the `fee_state` PDA via `init`, `seeds = [FEE_STATE_SEED]`: [1](#0-0) 

The handler sets `fee_state.global_fee_admin = admin_key` and `fee_state.global_fee_wallet = fee_wallet` directly from caller-supplied instruction arguments, with no check that `payer` (or `admin_key`) matches the program's upgrade authority or any pre-agreed governance key: [2](#0-1) 

Because `FeeState` is a PDA with a fixed seed (`FEE_STATE_SEED`), only one instance can ever exist — whichever transaction lands first "wins" the singleton. The corresponding `InitFeeStateV2` account struct has the identical pattern: [3](#0-2) 

This is functionally identical to the report's `ULN::init_uln` example: a permissionless `init` instruction that sets an "admin" field with no deployer/upgrade-authority check, exploitable via a race between the legitimate deployer's initialization transaction and an attacker's front-run transaction (e.g., by monitoring the mempool/validator for the program's deployment or upgrade).

`global_fee_admin` is a powerful, program-wide role. It exclusively controls `edit_global_fee_state` (which can change `fee_wallet`, all protocol fee rates, liquidation/order fee caps, and the `pause_delegate_admin`) via a `has_one = global_fee_admin` check on the FeeState PDA: [4](#0-3) 

and it gates `panic_pause`/pause-authority logic and `config_group_fee` (toggling protocol fees on any group), as documented: [5](#0-4) 

### Impact Explanation
Every newly created `MarginfiGroup` reads `fee_state.global_fee_wallet`/fee rates at init time and caches them: [6](#0-5) 

If an attacker wins the race to call `init_global_fee_state`, they become the sole `global_fee_admin` and can set `global_fee_wallet` to an address they control. All protocol fees generated across every group on the deployment (bank init fees, liquidation flat fees, order fees, and ongoing program fee revenue) would subsequently accrue to the attacker's wallet instead of the legitimate protocol treasury — a direct, concrete theft of protocol revenue. The attacker-controlled admin can also arbitrarily raise fee parameters (up to protocol-enforced caps) and control the pause/panic mechanism. This is a program-wide, un-recoverable takeover of the fee treasury (the PDA cannot be reinitialized once set), forcing a costly redeploy under a new program ID if discovered.

### Likelihood Explanation
Likelihood is Medium: this requires the attacker to race the legitimate deployer's post-deployment setup transaction. On Solana this is a known, credible risk — an attacker can observe program deployment/upgrade transactions and submit a competing `init_global_fee_state` call before the deployer's initialization script executes (especially given deployment and follow-up initialization are typically separate, sequential steps rather than atomic).

### Recommendation
Restrict `InitFeeState`/`InitFeeStateV2` (and `MarginfiGroupInitialize`'s fee-state coupling, if applicable) to a known, trusted address — e.g., verify `payer.key()` against the program's `upgrade_authority_address` (per the Anchor docs pattern referenced in the original report), or require a hardcoded/config-supplied deployer pubkey. Alternatively, bundle the deployment and fee-state initialization into a single atomic transaction signed by the deployer so no window for front-running exists.

### Proof of Concept
1. Deployer publishes/upgrades the `marginfi` program.
2. Before the deployer submits their `init_global_fee_state` transaction, an attacker submits their own transaction calling `init_global_fee_state(admin_key = attacker, fee_wallet = attacker_wallet, ...)` with the correctly derived `fee_state` PDA (`seeds = [FEE_STATE_SEED]`) and themselves as `payer`.
3. Because `InitFeeState` has no constraint on `payer` or `admin_key` besides being a signer, the transaction succeeds and creates the singleton `FeeState` PDA with the attacker as `global_fee_admin` and `global_fee_wallet`.
4. The deployer's subsequent `init_global_fee_state` call fails (PDA already initialized) — the attacker now permanently controls global fee configuration and destination wallet for the whole protocol deployment, as shown by the unrestricted `Accounts` struct at [1](#0-0) .

pub fn initialize_fee_state(
    ctx: Context<InitFeeState>,
    admin_key: Pubkey,
    fee_wallet: Pubkey,
    bank_init_flat_sol_fee: u32,
    liquidation_flat_sol_fee: u32,
    order_init_flat_sol_fee: u32,
    program_fee_fixed: WrappedI80F48,
    program_fee_rate: WrappedI80F48,
    liquidation_max_fee: WrappedI80F48,
    order_execution_max_fee: WrappedI80F48,
) -> Result<()> {
    let mut fee_state = ctx.accounts.fee_state.load_init()?;
    fee_state.global_fee_admin = admin_key;
    fee_state.global_fee_wallet = fee_wallet;
    fee_state.key = ctx.accounts.fee_state.key();
    fee_state.bank_init_flat_sol_fee = bank_init_flat_sol_fee;
    fee_state.bump_seed = ctx.bumps.fee_state;
    fee_state.program_fee_fixed = program_fee_fixed;
    fee_state.program_fee_rate = program_fee_rate;
    fee_state.liquidation_max_fee = liquidation_max_fee;
    fee_state.liquidation_flat_sol_fee = liquidation_flat_sol_fee;
    fee_state.order_execution_max_fee = order_execution_max_fee;
    fee_state.order_init_flat_sol_fee = order_init_flat_sol_fee;

    Ok(())
}
