### Title
Division-before-multiplication in standby-witness reward payout causes precision loss / vote-value–dependent under/over-payment - (File: `chainbase/src/main/java/org/tron/core/service/MortgageService.java`)

### Summary
`MortgageService.payStandbyWitness()`, the routine that pays block-reward TRX to the 127 standby witnesses every block, computes each witness's share by first dividing `totalPay` by `voteSum` (producing a `double`), and only then multiplying by each witness's individual `voteCount`. This is the same anti-pattern flagged in the referenced report (`Pool.sol` dividing before multiplying), and it is exercised on every single block via `Manager`'s block-application flow.

### Finding Description
The payout loop is:
```java
long totalPay = dynamicPropertiesStore.getWitness127PayPerBlock();
double eachVotePay = (double) totalPay / voteSum;
for (WitnessCapsule w : witnessStandbys) {
  long pay = (long) (w.getVoteCount() * eachVotePay);
  payReward(w.getAddress().toByteArray(), pay);
}
``` [1](#0-0) 

`totalPay / voteSum` is computed once as a `double` ratio and then multiplied per witness — dividing before multiplying, exactly the pattern the report calls out. Because `voteCount` values differ by orders of magnitude across the 127 standby witnesses, the pre-computed ratio's rounding error is amplified differently for each witness, and the final `(long)` cast truncates independently per witness rather than after a single combined multiply/divide. The mathematically equivalent, precision-preserving form would be `pay = (voteCount * totalPay) / voteSum` computed with a wide integer type (or `BigInteger`) so multiplication happens before division, exactly as the report recommends for `Pool.sol`.

The same defective pattern is duplicated in the analogous standby-reward path `IncentiveManager.reward()`:
```java
long pay = (long) (consensusDelegate.getWitness(address).getVoteCount()
    * ((double) totalPay / voteSum));
``` [2](#0-1) 

and in the vote-reward computation `MortgageService.computeReward(long cycle, ...)` used by the legacy reward algorithm:
```java
double voteRate = (double) userVote / totalVote;
reward += voteRate * totalReward;
``` [3](#0-2) 

Both `payStandbyWitness()` and `IncentiveManager.reward()` are invoked unconditionally from `MaintenanceManager.doMaintenance()` / block-application logic driven by `Manager`, i.e. they run on ordinary chain progression once vote thresholds trigger a maintenance cycle — reachable purely by normal, unprivileged `VoteWitnessContract` transactions accumulating votes, with no privileged actor required. [4](#0-3) 

### Impact Explanation
Because the ratio is rounded before being scaled per-witness, individual witnesses can receive slightly more or less TRX than their exact proportional entitlement `voteCount * totalPay / voteSum`. Since `payReward()`/`adjustAllowance()` directly credits `AccountCapsule` allowance (i.e., mints spendable balance into the account) without any invariant check that the sum of all payouts equals `totalPay`, systematic rounding bias across 127 witnesses each block can produce a persistent net over- or under-issuance of TRX relative to the intended block-reward budget. This is a fund-accounting correctness issue (unbacked-balance class) rather than a one-shot theft, but it accumulates over every block since the code path executes continuously as part of normal chain operation.

### Likelihood Explanation
High reachability: this code executes on essentially every maintenance cycle as soon as there are standby witnesses with non-zero votes, which is guaranteed on any live network — no special privilege, malicious actor, or unusual configuration is required. The precision-loss trigger (non-integer `totalPay/voteSum` ratio) is the common case, since vote counts are essentially arbitrary user-controlled amounts (unprivileged `VoteWitnessContract`), and `totalPay` is a fixed protocol constant, so an exact division is the exception rather than the rule.

### Recommendation
Refactor `payStandbyWitness()` (and the structurally identical `IncentiveManager.reward()` and `computeReward(long cycle, ...)`) to multiply before dividing, using `BigInteger` or `Math.multiplyHigh`/wide arithmetic to avoid `long` overflow:
```java
long pay = BigInteger.valueOf(w.getVoteCount())
    .multiply(BigInteger.valueOf(totalPay))
    .divide(BigInteger.valueOf(voteSum))
    .longValueExact();
```
This mirrors the hardened pattern already used elsewhere in the codebase (e.g. `RepositoryImpl.usageToBalance`/`calculateGlobalEnergyLimit`, `ResourceProcessor.calculateGlobalLimitV2`) which perform multiply-then-divide via `BigInteger` specifically to avoid this class of precision loss. [5](#0-4) 

### Proof of Concept
1. Configure a network with `Witness127PayPerBlock` = a fixed value (e.g., 16,000,000 sun) and 127 standby witnesses with varied, non-uniform `voteCount`s (as already exercised in `DelegationServiceTest.testPay`, which computes `long expect = (long) (d * 100000026)` with `d = (double) 16000000 / tmp` — the same divide-then-multiply shape). [6](#0-5) 
2. Sum `payReward` amounts distributed to all 127 standby witnesses over one maintenance cycle and compare to `totalPay`.
3. Observe that, due to per-witness independent truncation of `(long) (voteCount * eachVotePay)`, the aggregate paid amount deviates from the exact `totalPay` figure that would result from `(voteCount * totalPay) / voteSum` computed in exact integer arithmetic — demonstrating the same rounding-loss class described in the external report, occurring automatically on every qualifying block/maintenance cycle without any attacker action.
