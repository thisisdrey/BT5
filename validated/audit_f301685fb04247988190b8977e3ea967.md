## Title
Missing zero-address check in `TransferActuator`/`TransferAssetActuator` allows accidental permanent burn of TRX/TRC10 - (File: `actuator/src/main/java/org/tron/core/actuator/TransferActuator.java`, `actuator/src/main/java/org/tron/core/actuator/TransferAssetActuator.java`)

### Summary
`TransferActuator.validate()` and `TransferAssetActuator.validate()` validate the `toAddress` field only through `DecodeUtil.addressValid()`, which checks length and the network prefix byte but never rejects the all-zero address body (i.e., prefix byte + 20 zero bytes). As a result, a single signed `TransferContract`/`TransferAssetContract` transaction can move TRX or TRC10 tokens to an address that corresponds to no real key pair, permanently and irrecoverably freezing those funds — the same bug class as the referenced Bond report, where sending value to `address(0)` effectively burns it.

### Finding Description
`DecodeUtil.addressValid()` only checks that the address is 21 bytes long and starts with the correct prefix byte; it performs no check that the remaining 20 bytes are non-zero: [1](#0-0) 

`TransferActuator.validate()` uses exactly this check for `toAddress`, and only additionally guards against self-transfer (`toAddress == ownerAddress`), not against the zero address: [2](#0-1) 

In `execute()`, if no account exists at `toAddress` (which is guaranteed for the all-zero address, since no private key can ever produce it), a brand-new `AccountCapsule` is silently created and the transferred amount is credited to it: [3](#0-2) 

The same pattern exists in `TransferAssetActuator`, which validates `toAddress` identically and auto-creates the account before crediting TRC10 asset balance: [4](#0-3) [5](#0-4) 

Notably, the codebase already recognizes a distinct, intentional black-hole address (`accountStore.getBlackhole()`) used for burning transaction fees, showing that the protocol has a concept of "funds destined nowhere" but does not apply the same protection to arbitrary user-supplied recipient addresses that happen to be all-zero.

### Impact Explanation
Any TRX or TRC10 token sent to the zero-body address becomes permanently unrecoverable, since no private key can ever derive that address to sign a subsequent transfer out of it. This is a permanent freezing/loss of user funds — reachable directly by any unprivileged transaction broadcaster via a single signed `TransferContract` or `TransferAssetContract`, with no special privilege required. Wallet or dApp integration bugs that leave a recipient field defaulted/uninitialized (mirroring exactly the "recipient set to address 0" root cause in the referenced report) would trigger this silently, since the actuator's `validate()` step accepts the transaction as fully valid.

### Likelihood Explanation
Likelihood is driven by client/integration error rather than by an on-chain attacker economically benefiting, matching the pattern in the original report (accidental zero recipient rather than malicious exploitation). Because `validate()` provides no defense-in-depth against this well-known foot-gun class of address, any wallet, exchange integration, or smart-contract-triggered transfer flow that fails to sanitize a default/zero recipient will result in an on-chain, irreversible loss.

### Recommendation
Add an explicit rejection of the network's zero-body address (prefix byte followed by 20 zero bytes) in `TransferActuator.validate()` and `TransferAssetActuator.validate()`, alongside the existing self-transfer check, e.g.:
```java
if (Arrays.equals(toAddress, ZERO_ADDRESS)) {
  throw new ContractValidateException("Cannot transfer to the zero address.");
}
```
Consider centralizing this check inside `DecodeUtil.addressValid()` (or a new helper) so all actuators/native contracts that accept a caller-supplied recipient benefit uniformly.

### Proof of Concept
1. Construct and sign a `TransferContract` (or `TransferAssetContract`) with `toAddress` = `0x41` + 20 zero bytes (a syntactically valid but keyless address) and any positive `amount`.
2. Broadcast the transaction; `TransferActuator.validate()` passes since `DecodeUtil.addressValid()` only checks length/prefix, and `toAddress != ownerAddress`.
3. `TransferActuator.execute()` auto-creates the account at the zero-body address and credits it with `amount`.
4. Because no key pair can generate a signature for that address, the credited TRX/TRC10 balance can never be spent, effectively burning it.

  public static boolean addressValid(byte[] address) {
    if (ArrayUtils.isEmpty(address)) {
      logger.warn("Warning: Address is empty !!");
      return false;
    }
    if (address.length != ADDRESS_SIZE / 2) {
      logger.warn(
          "Warning: Address length need " + ADDRESS_SIZE + " but " + address.length
              + " !!");
      return false;
    }

    if (address[0] != addressPreFixByte) {
      logger.warn("Warning: Address need prefix with " + addressPreFixByte + " but "
          + address[0] + " !!");
      return false;
    }
    return true;
  }
