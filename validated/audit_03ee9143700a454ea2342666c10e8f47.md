### Title
Committee can disable market transactions via `ALLOW_MARKET_TRANSACTION` proposal while active TRC10 market orders remain open, permanently locking trader funds - (File: actuator/src/main/java/org/tron/core/actuator/MarketCancelOrderActuator.java)

### Summary
Both `MarketSellAssetActuator` (create/open an order) and `MarketCancelOrderActuator` (cancel/close an order) gate their `validate()` on the same global switch, `dynamicStore.supportAllowMarketTransaction()`, which is backed by the `ALLOW_MARKET_TRANSACTION` chain parameter controlled by committee proposal. If this parameter is toggled off after users already have open TRC10 market orders resting in the order book, those users can never cancel/close their existing orders again, permanently locking their escrowed sell-token balance, mirroring the reported Zaros bug class: a privileged operator disables a market without checking for open positions, and users can no longer close what they already opened.

### Finding Description
`MarketSellAssetActuator.validate()` requires `dynamicStore.supportAllowMarketTransaction()` to be true before a `MarketSellAssetContract` is accepted, throwing `"Not support Market Transaction, need to be opened by the committee"` otherwise: [1](#0-0) 

The exact same gate is enforced in `MarketCancelOrderActuator.validate()`: [2](#0-1) 

When a user creates a sell order via `MarketSellAssetActuator.execute()`, the sell-token quantity (or TRX) is immediately debited from the trader's account and escrowed as an active order in `MarketOrderStore`/`MarketPairPriceToOrderStore` (see `transferBalanceOrToken` and `createAndSaveOrder`): [3](#0-2) [4](#0-3) 

The only way for the trader to reclaim that escrowed balance for an order that hasn't fully matched is `MarketCancelOrderActuator`, which returns the remaining sell-token amount via `MarketUtils.returnSellTokenRemain` and marks the order `CANCELED`: [5](#0-4) 

Because both the "open" and "close" (cancel) paths share the identical `supportAllowMarketTransaction()` check with no exception carved out for existing/active orders, once the committee flips `ALLOW_MARKET_TRANSACTION` off (via a proposal, analogous to the "protocol operator" in the report), every user who has an outstanding, unmatched market order is permanently unable to submit `MarketCancelOrderContract` to reclaim their escrowed tokens. There is no other actuator or path that releases the escrowed balance for an active order — order matching in `matchOrder`/`matchSingleOrder` only runs as part of a *new* incoming `MarketSellAssetContract`, which is itself blocked by the same disabled flag, so existing resting orders can neither be matched nor canceled.

### Impact Explanation
This results in permanent freezing of user funds: TRC10 tokens or TRX that a trader escrowed into an open market order become permanently inaccessible for as long as `ALLOW_MARKET_TRANSACTION` stays disabled, with no fallback mechanism (unlike, for example, the perpetuals report's liquidation path which still functioned). Since `MarketCancelOrderActuator` is the sole avenue to unwind an order and reclaim escrowed balance, and it checks the very same flag used to shut markets off, a governance action intended to pause new trading activity has the unintended side effect of trapping capital already committed by users, exactly the bug class described (operator/governance disables the trading venue without accounting for already-open positions/orders).

### Likelihood Explanation
Triggering this requires: (1) at least one unprivileged account issuing a `MarketSellAssetContract` transaction that does not fully match and remains resting in the order book (a completely normal, expected trading activity), and (2) the committee subsequently disabling `ALLOW_MARKET_TRANSACTION` via the standard proposal mechanism (a supported, documented, non-malicious governance operation used e.g. to pause the market feature). Because disabling the market feature is a normal governance capability with no safeguard checking for outstanding orders, this can be reached without any malicious actor — it is a straightforward operational sequence, making the likelihood significant whenever the committee legitimately wants to pause the market feature while user orders are outstanding.

### Recommendation
Decouple the cancel path from the same on/off switch that gates opening new orders: `MarketCancelOrderActuator.validate()` should not require `supportAllowMarketTransaction()` to be true, or should have a dedicated exemption. This mirrors the original report's recommended fix of always allowing users to unwind/close existing positions regardless of whether new order creation is disabled. Alternatively, require the committee/proposal logic to verify there are no active resting orders before allowing `ALLOW_MARKET_TRANSACTION` to be turned off, though this is likely impractical at the proposal-processing layer, making the actuator-level exemption the more practical fix.

### Proof of Concept
1. Committee enables the market feature: set dynamic property `ALLOW_MARKET_TRANSACTION = 1` (as done in test setup, `dbManager.getDynamicPropertiesStore().saveAllowMarketTransaction(1L)`), matching normal test initialization: [6](#0-5) 
2. An unprivileged user broadcasts a `MarketSellAssetContract` (e.g., sell 100 TOKEN_ID_ONE for 300 TOKEN_ID_TWO with no immediate counter-order), which is accepted by `MarketSellAssetActuator`, debits the user's balance and creates an active order (as shown by `addOrder` helper calls building up `State`-active orders): [7](#0-6) 
3. Committee (via governance proposal) sets `ALLOW_MARKET_TRANSACTION = 0`.
4. The user broadcasts a `MarketCancelOrderContract` for their still-active order id. `MarketCancelOrderActuator.validate()` now throws `"Not support Market Transaction, need to be opened by the committee"` before reaching the ownership/state checks, because the check happens unconditionally early in validation: [8](#0-7) 
5. The user's escrowed sell-token balance remains locked in the order (`MarketOrderStore`) indefinitely, with no other actuator available to release it while the flag stays disabled.
