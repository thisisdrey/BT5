Audit Report

## Title
Relayer reward paid regardless of on-chain execution outcome (`success` field ignored) - (File: `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs`)

## Summary
The `DeliveryReceipt` struct decodes the Ethereum `InboundMessageDispatched(nonce, topic, success, reward_address)` event and carries a `success: bool` field indicating whether the message actually executed successfully on the Gateway contract on Ethereum. `Pallet::process_delivery_receipt`, invoked from the public, unprivileged `submit_delivery_receipt` extrinsic, never reads or checks `receipt.success` before paying the relayer reward and clearing the pending order, so a relayer is paid in full even for messages that failed execution on Ethereum.

## Finding Description
`submit_delivery_receipt` is a signed, unprivileged extrinsic: it verifies the Ethereum log proof via `T::Verifier::verify`, decodes it into a `DeliveryReceipt` (which includes `success`), then calls `Self::process_delivery_receipt(relayer, receipt)` [1](#0-0) . `DeliveryReceipt` is decoded straight from the Ethereum event log and explicitly preserves the on-chain `success` flag emitted by `InboundMessageDispatched` [2](#0-1) .

However, `process_delivery_receipt` only checks the gateway address and looks up the `PendingOrder` by nonce; it never inspects `receipt.success` before unconditionally calling `T::RewardPayment::register_reward` (when `order.fee > 0`) and removing the pending order [3](#0-2) . Proof verification (`T::Verifier::verify`) only attests that the log was genuinely emitted and included on Ethereum — it says nothing about whether the referenced message dispatch was successful; that information is carried purely in the `success` boolean of the decoded event, which is discarded by the payout logic.

## Impact Explanation
Any ordinary signed relayer account can call `submit_delivery_receipt` with a legitimately verified `InboundMessageDispatched` log where `success = false` (a normal outcome of e.g. a reverting/failing downstream call in the Gateway contract) and still receive the full `order.fee` reward via `T::RewardPayment::register_reward`, while the `PendingOrder` is removed as if delivery succeeded. This is an unbacked/duplicate-style payout — value transferred to a relayer for work that did not complete — falling under "theft or unbacked mint" / "duplicate settlement or payout" in the impact gate, and it requires no privileged or malicious-peer behavior, only the normal permissionless relaying flow.

## Likelihood Explanation
This requires no adversarial infrastructure, compromised keys, or governance action — just a signed account submitting a real, verifier-accepted proof for a message whose execution genuinely failed on Ethereum, which is an expected occurrence in production (gas exhaustion, reverting calls, etc.). Since `success` is already present in the decoded struct and simply unused, this is a straightforward missing-check defect rather than a complex multi-step exploit, making it highly reproducible.

## Recommendation
In `process_delivery_receipt`, branch on `receipt.success`: only invoke `T::RewardPayment::register_reward` when `receipt.success == true`. For `success == false`, still resolve/remove the `PendingOrder` (or mark it distinctly) but withhold the reward, and emit a separate event (e.g. `MessageDeliveryFailed`) so downstream systems can react (retry, refund, etc.).

## Proof of Concept
Using the pallet's test harness (`bridges/snowbridge/pallets/outbound-queue-v2/src/test.rs`), insert a `PendingOrder { nonce, fee: 1_000_000, .. }` into `PendingOrders`, construct a `DeliveryReceipt` (or an event log that decodes to one via `DeliveryReceipt::try_from`) with `success: false` for that `nonce`, and call `Pallet::<Test>::process_delivery_receipt(relayer, receipt)` (or `OutboundQueue::submit_delivery_receipt` with a corresponding mocked/verified event proof). Assert the call returns `Ok(())`, the relayer's registered reward increases by `order.fee`, and `PendingOrders::<Test>::get(nonce)` becomes `None` — confirming full reward payout despite `success == false`, per the unconditional payout path at [4](#0-3) .

		/// Process a delivery receipt from a relayer, to allocate the relayer reward.
		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}
