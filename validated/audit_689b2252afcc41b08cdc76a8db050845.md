### Title
Unauthenticated `recv_error` packets let an attacker tear down (or repeatedly re-trigger teardown of) another host's tunnel by spoofing the last-known remote address - (File: outside.go)

### Summary
`handleRecvError` accepts a bare, unencrypted `RecvError` header packet and uses it to immediately tear down an active tunnel and its handshake state, gated only by a comparison against the currently cached UDP remote address (`hostinfo.GetRemote()`), not by any cryptographic authentication of the sender.

### Finding Description
`readOutsidePackets` dispatches `header.RecvError` packets straight to `f.handleRecvError(via.UdpAddr, h)` before any AEAD decryption/verification step — this is one of the two "Unencrypted packets" cases in the switch, alongside `header.Handshake`: [1](#0-0) 

`handleRecvError` then:
1. Optionally checks a config gate (`acceptRecvErrorConfig`), which defaults to accepting `recv_error` "always" per the changelog note on `listen.send_recv_error`/`accept_recv_error`.
2. Looks up the hostinfo by `h.RemoteIndex` via `QueryReverseIndex`.
3. Compares the *source UDP address of the incoming packet* against the hostinfo's currently cached remote address (`hostinfo.GetRemote()`), and if they differ, logs "Someone spoofing recv_errors?" and bails.
4. If they match (or if roaming previously updated the cached remote to an address an attacker can also reach/spoof, e.g., over the public internet using an unauthenticated UDP source), it calls `f.closeTunnel(hostinfo)` and `hm.DeleteHostInfo(hostinfo)`, destroying the tunnel state entirely — no MAC, no handshake, no certificate check of any kind: [2](#0-1) 

This mirrors the bug class in the referenced report: a low-cost, unauthenticated action (sending a forged `RecvError` header) mutates protected connection state (tearing down the tunnel / clearing pending handshake) that a privileged/legitimate flow depends on remaining stable, purely by satisfying a weak, spoofable condition (source `UdpAddr` equality) rather than a cryptographic proof. Just as the Solidity bug let an attacker abuse `stake(1)` to flip a `blockNumber` checkpoint and block `slash`, an attacker here can forge `RecvError` packets (source-spoofed UDP, no cert needed) to flip tunnel/hostinfo state and disrupt the legitimate connection lifecycle — and can repeat this indefinitely to keep knocking down re-established tunnels, since nothing about sending a `RecvError` packet requires holding a CA-signed certificate.

`maybeSendRecvError`/`RecvError`'s only remaining defense is UDP source-address equality to `hostinfo.GetRemote()`, which is not authenticated and can be spoofed on many networks (UDP source IP spoofing) or trivially satisfied by an on-path/NAT-adjacent attacker who can observe the current remote endpoint. [3](#0-2) 

### Impact Explanation
An attacker who can spoof UDP source address/port (or is on-path/observes the current remote endpoint) can repeatedly force `closeTunnel` + `DeleteHostInfo` on a victim's tunnel with zero cryptographic material — no valid CA-signed certificate is required at any point in this code path. This is a remote state-poisoning / denial-of-tunnel-continuity impact: it can be abused to continuously disrupt tunnel establishment/maintenance for a target host, analogous to how the slashing bypass let an attacker indefinitely block a security-relevant operation via low-cost, repeatable self-triggered state changes.

### Likelihood Explanation
Medium: exploitation requires either the ability to spoof UDP source IP/port toward the victim's listener, or (post-roam) knowledge of the victim's currently negotiated remote endpoint. Both are plausible on many network paths without needing to complete a handshake or hold any certificate, matching the "no CA-signed certificate" reachability constraint.

### Recommendation
Require `RecvError` handling to be tied to an authenticated signal (e.g., derive the teardown trigger from AEAD-protected traffic, or require a valid MAC binding the message to the session keys) rather than relying solely on UDP source-address equality to the cached remote. At minimum, rate-limit and require additional confirmation (e.g., a subsequent failed decrypt) before tearing down an active hostinfo based on an unauthenticated `RecvError`.

### Proof of Concept
1. Establish a legitimate tunnel between "me" and "them"; note "me"'s currently negotiated remote `UdpAddr` for "them" (obtainable by an on-path observer, or guessable/reused after roam).
2. Craft a raw UDP packet with `header.RecvError` type and `RemoteIndex` set to the victim's known `localIndexId`/index for that hostinfo (indexes are exchanged in the clear during handshake, so also observable).
3. Send this unencrypted packet, spoofing the source address to match the victim's cached remote (or send from that exact source if on-path/NAT-shared).
4. Observe `handleRecvError` accept it (`hr == addr`), call `f.closeTunnel(hostinfo)` and `hm.DeleteHostInfo(hostinfo)`, destroying the tunnel without ever presenting a certificate or completing a handshake — repeatable indefinitely to keep disrupting the tunnel, directly analogous to the repeatable `stake(1)` frontrunning in the referenced report.

func (f *Interface) handleRecvError(addr netip.AddrPort, h *header.H) {
	if !f.acceptRecvErrorConfig.ShouldRecvError(addr) {
		f.l.Debug("Recv error received, ignoring",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
		return
	}

	if f.l.Enabled(context.Background(), slog.LevelDebug) {
		f.l.Debug("Recv error received",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
	}

	hostinfo := f.hostMap.QueryReverseIndex(h.RemoteIndex)
	if hostinfo == nil {
		f.l.Debug("Did not find remote index in main hostmap", "remoteIndex", h.RemoteIndex)
		return
	}

	hr := hostinfo.GetRemote()
	if hr.IsValid() && hr != addr {
		f.l.Info("Someone spoofing recv_errors?",
			"addr", addr,
			"hostinfoRemote", hr,
		)
		return
	}

	f.closeTunnel(hostinfo)
	// We also delete it from pending hostmap to allow for fast reconnect.
	f.handshakeManager.DeleteHostInfo(hostinfo)
}
