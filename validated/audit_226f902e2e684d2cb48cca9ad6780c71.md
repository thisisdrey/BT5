Based on my investigation, the strongest analog to CVE-2017-16831 in java-tron is the unvalidated count fields used to size arrays in the TVM precompiled-contract ABI decoders `extractBytesArray` and `extractSigArray`.

### Title
Unvalidated attacker-controlled array-length field in TVM precompile ABI decoding causes uncontrolled memory allocation / crash - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
`PrecompiledContracts.extractBytesArray` and `PrecompiledContracts.extractSigArray` read a "count" word directly out of attacker-supplied EVM call data and use it, unvalidated, to size a Java array before any bounds check is performed — the same root-cause pattern as CVE-2017-16831, where `coffgen.c` trusted a symbol count from a crafted PE file and allocated memory for it without validation. [1](#0-0) [2](#0-1) 

### Finding Description
`extractBytesArray(DataWord[] words, int offset, byte[] data)` computes `int len = words[offset].intValueSafe();` and immediately allocates `byte[][] bytesArray = new byte[len][];`, then loops `for (int i = 0; i < len; i++)` reading further offset/length words from the same attacker-controlled `data` buffer to slice out each element via `extractBytes`. [1](#0-0) 

`extractSigArray` follows the identical pattern for signature arrays: `int len = words[offset].intValueSafe(); byte[][] bytesArray = new byte[len][];` followed by an unbounded loop that reads `SIG_LENGTH`-byte chunks per element. [2](#0-1) 

In both functions, `len` is a raw 256-bit word taken from the caller-supplied `data`/`words` array (the ABI-encoded input to a TVM `CALL`/`STATICCALL` to the precompile), and there is no upper bound comparison against a sane maximum (e.g., number of remaining words in `data`) before the array is allocated. This mirrors the CVE's flaw: "does not validate the symbol count... allows... integer overflow and application crash, or excessive memory allocation."

The companion helper `extractBytes32Array` has the same issue: `int len = words[offset].intValueSafe(); byte[][] bytes32Array = new byte[len][];` with no validation before allocation. [3](#0-2) 

These decoders are used by the `BatchValidateSign` and `ValidateMultiSign` precompiled contracts, which are exposed at fixed TVM addresses (`0x...09` and `0x...0a`) reachable by any deployed contract via a normal `CALL` opcode — i.e., from any unprivileged transaction sender who deploys or invokes a contract that performs this call. [4](#0-3) [5](#0-4) 

### Impact Explanation
If `len` can be driven to a large positive value (bounded by `intValueSafe()`'s clamp to `Integer.MAX_VALUE`), `new byte[len][]` allocates an array of `len` object references (4–8 bytes each) before any subsequent index is validated against the actual data length — this can trigger an immediate `OutOfMemoryError`/JVM-level allocation spike or an `ArrayIndexOutOfBoundsException` while iterating (since `words[offset + i + 1]` will run past the real word array). Either outcome can abort execution of the node while validating/executing the transaction, and because the allocation happens inside the energy-metered VM execution path, a crafted low-cost call can attempt a disproportionately large allocation before failing — a resource-exhaustion / crash primitive reachable by any contract caller, consistent with the CVE's "denial of service (integer overflow and application crash, or excessive memory allocation)" impact.

### Likelihood Explanation
Reaching this code requires only deploying or calling a contract that issues a `CALL` to the `BatchValidateSign` (`0x9`) or `ValidateMultiSign` (`0xa`) precompile address with a crafted ABI payload containing an oversized count word at the expected offset — something any address holding minimal TRX for energy/bandwidth fees can do without special privileges.

### Recommendation
Before allocating `bytesArray`/`bytes32Array`, validate `len` against a sane maximum derived from the actual size of `words`/`data` (e.g., `len <= (data.length - headerBytes) / itemSize` and `len >= 0`), rejecting the call (returning a failure pair) rather than allocating, mirroring the bounds checks already used elsewhere in this file (e.g., `isValidAbiEncoding`). [6](#0-5) 

### Proof of Concept
Construct a contract that calls `BatchValidateSign`/`ValidateMultiSign` at their fixed precompile addresses with ABI-encoded input where the "array length" word (read via `words[offset].intValueSafe()` in `extractBytesArray`/`extractSigArray`) is set to a very large value (close to `Integer.MAX_VALUE`) while the remaining `data` buffer is much shorter than what that length implies. Executing this call causes `new byte[len][]` to attempt a large allocation and/or the subsequent loop to read past the actual `words`/`data` bounds, crashing the precompile execution.

**Note on verification limits:** I could not fully trace the exact clamping behavior of `DataWord.intValueSafe()` (whether it caps to `Integer.MAX_VALUE`, throws, or truncates) nor confirm whether `BatchValidateSign.execute`/`ValidateMultiSign.execute` perform any additional length pre-check before calling `extractBytesArray`/`extractSigArray`, due to tool-call limits. Confirming those two points would be necessary to fully validate exploitability versus a caught/handled exception.
