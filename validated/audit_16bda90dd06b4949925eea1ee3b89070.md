### Title
`LinkRepositoryToObjectPool` allows linking any repository to any pre-existing object pool without an ownership/relationship check, enabling cross-repository object disclosure via alternates - (File: `internal/gitaly/service/objectpool/link.go`)

### Summary
Gitaly's `ObjectPoolService.LinkRepositoryToObjectPool` RPC accepts an arbitrary `Repository` and an arbitrary `ObjectPool` and links them by writing the pool's path into the repository's `objects/info/alternates` file. Neither the RPC handler nor the underlying `Link` implementation verifies that the two are actually related (e.g., that the repository is a fork/descendant of the pool, or belongs to the same project/namespace). This mirrors the "any user can attach any existing Staking contract to their own Vault" root cause in the reference report: a shared resource (the object pool, analogous to the Staking contract) can be attached to an attacker-controlled object (the repository, analogous to the Vault) purely by naming its coordinates, with no relationship/ownership validation.

### Finding Description
The handler simply validates that the target repository is well-formed and that the named object pool exists and is a valid Git repository, then performs the link: [1](#0-0) 

Pool resolution (`poolForRequest` → `objectpool.FromProto`) only checks that the pool path resolves to a real, structurally valid pool repository — it does not check that it is the pool associated with the requesting repository's fork lineage: [2](#0-1) 

The actual linking logic in `internal/git/objectpool/link.go` writes the pool's relative object path into the repository's alternates file unconditionally, again with no check that `repo` is an authorized member of `pool`: [3](#0-2) 

Once linked, Git treats every object in the pool as locally available to the linked repository via the alternates mechanism, exactly as documented: [4](#0-3) 

Object pools intentionally retain unreferenced ("dangling") objects from *any* current or former member indefinitely, because Gitaly cannot know which repositories may still depend on them: [5](#0-4) 

This means an attacker who can name an existing pool (pools are addressed only by `storage_name` + `relative_path`, both low-entropy/guessable or discoverable via other RPCs such as `GetObjectPool`) and who controls any repository, can link that repository to a pool it has no legitimate relationship to, and thereby read every object — including dangling objects that are otherwise unreachable through any legitimate ref — ever pushed into that pool by unrelated repositories.

### Impact Explanation
This is a cross-repository object disclosure: an attacker gains read access to Git objects (blobs, commits, trees) belonging to a project/pool they are not authorized to access, including objects that were force-pushed away and are no longer reachable from any live branch but are kept alive as "dangling" in the pool for deduplication purposes. This is comparable in class to the reference report's core issue — an unprivileged actor attaching to a shared resource it does not own and thereby extracting value/data that should be isolated to legitimate members.

### Likelihood Explanation
Exploitability depends on the attacker being able to invoke `LinkRepositoryToObjectPool` directly with a `Repository` they control and an `ObjectPool` they do not own. Whether an ordinary GitLab user can reach this RPC directly (bypassing Rails-level authorization that normally derives the pool from a fork relationship) is not verifiable from the indexed Gitaly code alone, since authorization for this RPC is expected to be enforced by the calling layer (Rails/Workhorse) rather than by Gitaly itself. Within Gitaly's own trust boundary, however, there is no defense-in-depth check tying the `Repository` and `ObjectPool` fields together, so any caller capable of reaching this RPC (including a compromised or logic-flawed upstream caller) can perform the attack.

### Recommendation
- Enforce that the `Repository` and `ObjectPool` in `LinkRepositoryToObjectPoolRequest` have an established relationship before linking — e.g., require that the pool was created from (or the repository was forked from) that specific repository, tracked via persisted pool-membership metadata rather than trusting caller-supplied paths.
- Add an authorization/ownership check in `internal/gitaly/service/objectpool/link.go` and `internal/git/objectpool/link.go::Link` that rejects linking when the repository has no verified lineage to the pool.
- Consider not relying purely on upstream (Rails) authorization for this RPC given the significant blast radius (full object disclosure) if that check is ever bypassed or misconfigured.

### Proof of Concept
Conceptual reproduction using the existing test harness pattern from `internal/gitaly/service/objectpool/link_test.go`:
1. Create object pool `pool-A` seeded from victim repository `victim-repo`, and write a commit into `pool-A` that is later force-pushed away in `victim-repo` (making it "dangling" but still present in the pool per `doc/object_pools.md`).
2. As attacker, create an unrelated repository `attacker-repo` with no relationship to `pool-A`.
3. Call `LinkRepositoryToObjectPool(Repository: attacker-repo, ObjectPool: pool-A)`.
4. Observe (as shown by the existing `TestLink` test pattern) that the dangling/unreferenced commit from `victim-repo` is now readable from `attacker-repo` via `CommitService`, e.g. `gittest.RequireObjectExistsAPI(t, ctx, commitClient, attackerRepo, danglingCommitID)`, demonstrating cross-repository object disclosure: [6](#0-5)

```go
func (s *server) LinkRepositoryToObjectPool(ctx context.Context, req *gitalypb.LinkRepositoryToObjectPoolRequest) (*gitalypb.LinkRepositoryToObjectPoolResponse, error) {
	repository := req.GetRepository()
	if err := s.locator.ValidateRepository(ctx, repository); err != nil {
		return nil, structerr.NewInvalidArgument("%w", err)
	}

	pool, err := s.poolForRequest(ctx, req)
	if err != nil {
		return nil, err
	}

	repo := s.localRepoFactory.Build(repository)

	if err := pool.Link(ctx, repo); err != nil {
		return nil, structerr.NewInternal("%w", err)
	}

	return &gitalypb.LinkRepositoryToObjectPoolResponse{}, nil
}
```

```go
// FromProto returns an object pool object from its Protobuf representation. This function verifies
// that the object pool exists and is a valid pool repository.
func FromProto(
	ctx context.Context,
	logger log.Logger,
	locator storage.Locator,
	gitCmdFactory gitcmd.CommandFactory,
	catfileCache catfile.Cache,
	txManager transaction.Manager,
	housekeepingManager housekeepingmgr.Manager,
	proto *gitalypb.ObjectPool,
) (*ObjectPool, error) {
	poolPath, err := locator.GetRepoPath(ctx, proto.GetRepository(), storage.WithRepositoryVerificationSkipped())
	if err != nil {
		return nil, err
	}

	if !storage.IsPoolRepository(proto.GetRepository()) {
		// When creating repositories in the ObjectPool service we will first create the
		// repository in a temporary directory. So we need to check whether the path we see
		// here is in such a temporary directory and let it pass.
		tempDir, err := locator.TempDir(proto.GetRepository().GetStorageName())
		if err != nil {
			return nil, fmt.Errorf("getting temporary storage directory: %w", err)
		}

		if !strings.HasPrefix(poolPath, tempDir) {
			return nil, ErrInvalidPoolDir
		}
	}
```

```go
// Link will link the given repository to the object pool. This is done by writing the object pool's
// path relative to the repository into the repository's "alternates" file. This does not trigger
// deduplication, which is the responsibility of the caller.
func Link(ctx context.Context, pool, repo *localrepo.Repo, txManager transaction.Manager) (returnedErr error) {
	altPath, err := repo.InfoAlternatesPath(ctx)
	if err != nil {
		return err
	}

	expectedRelPath, err := getRelativeObjectPath(ctx, pool, repo)
	if err != nil {
		return err
	}

	linked, err := linkedToRepository(ctx, pool, repo)
	if err != nil {
		return err
	}

	if linked {
		// When the repository is already linked to the repository, cast a vote to ensure the
		// repository is consistent with the other replicas.
		if err := transaction.VoteOnContext(ctx, txManager, voting.VoteFromData([]byte("repository linked")), voting.Synchronized); err != nil {
			return fmt.Errorf("vote on linked repository: %w", err)
		}

		return nil
	}
```

```markdown

This issue is kind of unsolvable: there is no point in time where it's safe to
delete objects from the object pool, as we do not know which repositories may be
linked to it. And even if we knew, we cannot determine all references of all
repositories at once in a race-free manner. We thus must consider each object to
still be referenced somewhere.

As a safeguard to not lose any objects by accident, we thus create dangling
references in the object pool after the fetch in `FetchIntoObjectPool`. For each
dangling object, a reference `refs/dangling/$OID` is created which points into
the object. This assures that each object is still referenced.
```

```go
func TestLink(t *testing.T) {
	t.Parallel()

	ctx := testhelper.Context(t)

	cfg, repo, _, _, client := setup(t, ctx, testserver.WithDisablePraefect())

	localRepo := localrepo.NewTestRepo(t, cfg, repo)
	poolProto, _, poolPath := createObjectPool(t, ctx, cfg, repo)

	// Mock object in the pool, which should be available to the pool members
	// after linking
	poolCommitID := gittest.WriteCommit(t, cfg, poolPath,
		gittest.WithBranch("pool-test-branch"))

	for _, tc := range []struct {
		desc        string
		request     *gitalypb.LinkRepositoryToObjectPoolRequest
		expectedErr error
	}{
		{
			desc: "unset repository",
			request: &gitalypb.LinkRepositoryToObjectPoolRequest{
				Repository: nil,
				ObjectPool: poolProto,
			},
			expectedErr: structerr.NewInvalidArgument("%w", storage.ErrRepositoryNotSet),
		},
		{
			desc: "unset object pool",
			request: &gitalypb.LinkRepositoryToObjectPoolRequest{
				Repository: repo,
				ObjectPool: nil,
			},
			expectedErr: structerr.NewInvalidArgument("%w", storage.ErrRepositoryNotSet),
		},
		{
			desc: "successful",
			request: &gitalypb.LinkRepositoryToObjectPoolRequest{
				Repository: repo,
				ObjectPool: poolProto,
			},
		},
	} {
		t.Run(tc.desc, func(t *testing.T) {
			_, err := client.LinkRepositoryToObjectPool(ctx, tc.request)
			testhelper.RequireGrpcError(t, tc.expectedErr, err)

				return
			}

			commitClient := gitalypb.NewCommitServiceClient(gittest.DialService(t, ctx, cfg))
			gittest.RequireObjectExistsAPI(t, ctx, commitClient, repo, poolCommitID)

			require.NoError(t, err)
			require.NotNil(t, commit)
			require.Equal(t, poolCommitID.String(), commit.GetId())
		})
	}
```
