### Title
Unbounded storage of attacker-supplied content via unverified `AttachmentRequest` responses - ([File: stackslib/src/net/atlas/download.rs])

### Summary
`AttachmentsBatchStateContext::extend_with_attachments` stores whatever `Attachment` a remote peer returns for a solicited `AttachmentRequest` without checking that `attachment.hash()` matches the `content_hash` that was actually requested. `AttachmentsDownloader::run` then unconditionally calls `AtlasDB::insert_instantiated_attachment` on every such attachment, permanently marking it `was_instantiated = 1` in the `attachments` table even when zero `attachment_instances` rows match its hash.

### Finding Description
The intended equality is: every row in `attachments` with `was_instantiated = 1` corresponds to content whose `Hash160` was actually committed on-chain via a confirmed `AttachmentInstance.content_hash`. This equality is broken because the response-processing path never checks that the returned content's hash equals the hash that was requested.

- `AttachmentsBatchStateContext::extend_with_attachments` (`stackslib/src/net/atlas/download.rs:530-558`) takes `results.succeeded` for `AttachmentRequest`s, decodes each response via `decode_atlas_get_attachment()`, and does `self.attachments.insert(response.attachment)` — with **no comparison** between `response.attachment.hash()` and the `content_hash` field of the `AttachmentRequest` that was sent out.
- In `AttachmentsDownloader::run` (`stackslib/src/net/atlas/download.rs:153-169`), for every `attachment` drained from `context.attachments`, the code calls `network.atlasdb.find_all_attachment_instances(&attachment.hash())` to find matching instances, but then calls `network.atlasdb.insert_instantiated_attachment(&attachment)` **unconditionally**, regardless of whether `attachments_instances` came back empty.
- `AtlasDB::insert_instantiated_attachment` (`stackslib/src/net/atlas/db.rs:576-592`) does `INSERT OR REPLACE INTO attachments (hash, content, was_instantiated, created_at) VALUES (Hash160::from_data(&Y), Y, 1, now)` for the supplied content `Y`, with no check that any `attachment_instances` row references `Hash160::from_data(&Y)`.
- On the server side, `RPCGetAttachmentRequestHandler` (`stackslib/src/net/api/getattachment.rs:93-130`) only serves attachments the responding node already has stored — but a malicious/compromised or attacker-run peer being queried can serve arbitrary bytes for any hash, since the HTTP GET handler is on the requester's side, not a shared verification.
- Crucially, `evict_expired_uninstantiated_attachments` (`db.rs:549-560`) only deletes rows with `was_instantiated = 0`; there is no eviction routine for `was_instantiated = 1` rows, so once a row is marked instantiated (via this unverified path) it is retained forever.

Attack flow: node A tracks a legitimate `AttachmentInstance` with `content_hash = H1` (from a confirmed on-chain event) and issues an `AttachmentRequest` to an attacker-controlled peer B for `H1`. B replies with an HTTP 200 body containing `GetAttachmentResponse { attachment: Attachment { content: Y } }` for arbitrary `Y` where `Hash160::from_data(&Y) != H1`. A's `extend_with_attachments` accepts this into `context.attachments` unchecked. `run()` finds `find_all_attachment_instances(&Y.hash())` returns empty (since no instance references `Y`'s hash), yet still calls `insert_instantiated_attachment(&Attachment{content: Y})`, permanently storing arbitrary attacker content as `was_instantiated = 1`. B can repeat this with a fresh random `Y` on every response to a fresh `AttachmentRequest`, and each accepted batch round adds another permanent, unbounded row.

### Impact Explanation
Each malicious response the attacker peer sends causes one arbitrary-content row to be permanently written into the requesting node's `attachments` SQLite table with `was_instantiated = 1`, disassociated from any confirmed on-chain commitment. Because no eviction ever targets `was_instantiated = 1` rows, and content size is otherwise only bounded by whatever length limits exist on HTTP responses/serialization, a single malicious or compromised peer that a victim node solicits attachments from can grow the victim's Atlas database without bound over repeated download rounds — a High-severity storage-exhaustion/state-corruption issue matching "serving non-canonical state as canonical" in spirit, since these rows are indistinguishable in the schema from genuinely validated, consensus-committed attachments (`find_attachment` will return them as validated data for `content_hash` lookups matching `Y.hash()`, e.g. if any future or same-node instance's `content_hash` happens to equal `Y.hash()` it would be considered pre-validated).

### Likelihood Explanation
The precondition is that the victim node's `AttachmentsDownloader` selects the attacker's peer among `network.get_outbound_sync_peers()` and issues it an `AttachmentRequest` — a standard, unprivileged outbound-sync interaction that any peer offering itself as a data-URL peer can be selected for. No secrets, keys, or elevated roles are needed; the attacker only needs to run a normal peer that responds to `GET /v2/attachments/<hash>`-style solicitations with fabricated content instead of correct data. This is fully repeatable across every batch/retry cycle, so cost to the attacker is minimal (one HTTP-like response per requested hash) relative to the persistent storage cost imposed on the victim.

### Recommendation
In `AttachmentsBatchStateContext::extend_with_attachments`, verify `response.attachment.hash()` equals the `content_hash` of the corresponding `AttachmentRequest` before inserting into `self.attachments`; discard/penalize (mark peer as faulty) otherwise. Additionally, in `AttachmentsDownloader::run`, only call `insert_instantiated_attachment` when `find_all_attachment_instances(&attachment.hash())` returns a non-empty result (i.e., only store content that is actually referenced by a tracked `AttachmentInstance`), and consider adding a bound/eviction policy for `was_instantiated = 1` rows that are no longer referenced by any `attachment_instances` row.

### Proof of Concept
Rust test plan in `stackslib/src/net/atlas/tests.rs` (or `download.rs` test module):
1. Construct an `AttachmentsBatchStateContext` with a tracked `AttachmentInstance` whose `content_hash = H1`.
2. Simulate `results.succeeded` for the corresponding `AttachmentRequest` containing a `GetAttachmentResponse { attachment: Attachment { content: Y } }` where `Hash160::from_data(&Y) != H1`.
3. Call `context.extend_with_attachments(&mut results)` and assert `context.attachments` now contains the unrelated attachment (demonstrating the missing hash check).
4. Drive `AttachmentsDownloader::run`-equivalent logic (or directly call `atlasdb.find_all_attachment_instances(&Y.hash())` then `atlasdb.insert_instantiated_attachment(&Attachment{content: Y})`) and assert `find_all_attachment_instances(&Y.hash())` is empty while `SELECT COUNT(*) FROM attachments WHERE hash = ?1 AND was_instantiated = 1` for `Y.hash()` returns 1 — proving unverified content was persisted as "instantiated" with no backing on-chain commitment. Repeating with N distinct random `Y` values shows `SELECT COUNT(*) FROM attachments WHERE was_instantiated=1` grows to N while `count_uninstantiated_attachments()` stays 0.
