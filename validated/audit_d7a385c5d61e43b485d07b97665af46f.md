### Title
Division-before-multiplication precision loss in legacy vote-reward calculation - (File: `chainbase/src/main/java/org/tron/core/service/MortgageService.java`)

### Summary
`MortgageService.computeReward(long cycle, List<Pair<byte[], Long>> votes)` — the "old reward algorithm" path still used for cycles prior to `newRewardAlgorithmEffectiveCycle` — computes a voter's share of a witness's total reward by first dividing `userVote / totalVote` into a `double` and only then multiplying by `totalReward`. This is the same "division before multiplication" pattern flagged in the external GMX report: performing the division first truncates/rounds the ratio before the multiplication is applied, producing a result that differs from (and is systematically less precise than) computing `userVote * totalReward / totalVote` in one step.

### Finding Description [1](#0-0) 

```java
private long computeReward(long cycle, List<Pair<byte[], Long>> votes) {
  long reward = 0;
  for (Pair<byte[], Long> vote : votes) {
    ...
    long userVote = vote.getValue();
    double voteRate = (double) userVote / totalVote;
    reward += voteRate * totalReward;
  }
  return reward;
}
```

`voteRate` is computed as a division first (`userVote / totalVote`, stored as a lossy `double`), and only afterward multiplied by `totalReward`. The mathematically equivalent, precision-preserving order would be `userVote * totalReward / totalVote` (multiply before divide), exactly the fix recommended in the referenced report. Because `double` has only 53 bits of mantissa, both the initial division and the subsequent multiplication introduce rounding error that would not occur (or would be much smaller) if multiplication preceded division, or if integer/BigDecimal arithmetic were used as is done in the newer reward algorithm (`RewardViCalService`/`DelegationStore.accumulateWitnessVi`, which correctly multiply by `DECIMAL_OF_VI_REWARD` before dividing, using `BigInteger`).

This legacy path is exercised whenever a voter's `beginCycle` predates `newRewardAlgorithmEffectiveCycle`, via `MortgageService.computeReward(long beginCycle, long endCycle, AccountCapsule accountCapsule)`: [2](#0-1) 

### Impact Explanation
This computation directly determines the TRX amount credited to a voter's `allowance` via `adjustAllowance`, which is then withdrawn to the account's spendable balance in `WithdrawBalanceActuator.execute()`: [3](#0-2) 

Any unprivileged account holding votes cast before the new-reward-algorithm cutover can trigger this rounding-lossy path simply by broadcasting a `WithdrawBalanceContract` transaction. Because the division happens before the multiplication, the computed reward can deviate from the "true" proportional share of `totalReward`, causing systematic under- or over-crediting of allowance across the affected voter population — a fund-accounting correctness issue in the staking reward distribution, matching the "stake/delegation/reward math" domain called out as in-scope.

### Likelihood Explanation
This path only affects cycles prior to `newRewardAlgorithmEffectiveCycle` (i.e., networks that have already switched to the new Vi-based algorithm are unaffected for new cycles), but any account whose `beginCycle` still falls before that boundary — including all accounts that have not withdrawn/updated since — will exercise this code on their next `WithdrawBalanceContract` call, making it trivially and repeatedly reachable by any voter without special privileges.

### Recommendation
Reorder the arithmetic to multiply before dividing, matching the pattern already used correctly elsewhere in the codebase (e.g. `RewardViCalService.accumulateWitnessVi`, `DelegationStore.accumulateWitnessVi`, which use `BigInteger.multiply(...).divide(...)`):

```java
long userVote = vote.getValue();
reward += totalReward * userVote / totalVote; // use BigInteger/long to avoid overflow
```

Ideally replace the `double`-based computation entirely with `BigInteger` (or `Math.multiplyHigh`/`long` with overflow checks) arithmetic, consistent with the newer Vi-based reward algorithm, to eliminate both the precision loss and the division-before-multiplication ordering issue.

### Proof of Concept
Given `userVote = 1`, `totalVote = 3`, `totalReward = 10`:
- Current code: `voteRate = (double)1/3 = 0.3333333333333333`; `reward = (long)(0.3333333333333333 * 10) = 3` (via `+=` truncation to `long`).
- Correct order: `10 * 1 / 3 = 3` (same here by coincidence).

With larger, non-evenly-divisible values (e.g. `userVote = 1_000_000_000_000L`, `totalVote = 3_000_000_000_001L`, `totalReward = 999_999_999_999L`), the `double` division loses bits of precision in the intermediate ratio before multiplication, producing a result that diverges from the exact integer computation `totalReward * userVote / totalVote`, analogous to the precision-loss magnitudes demonstrated by the fuzzing harness in the referenced GMX report.
