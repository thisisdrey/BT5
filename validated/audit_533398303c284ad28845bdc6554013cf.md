### Title
Unbounded attacker-controlled length field used for object-array allocation in `PrecompiledContracts.extractBytesArray`/`extractSigArray`/`extractBytes32Array` enables heap-exhaustion DoS via `ValidateMultiSign`/`BatchValidateSign` precompiles - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `ValidateMultiSign` and `BatchValidateSign` TVM precompiled contracts decode a "length" word directly from attacker-supplied `CALL` data and use it, unchecked against the actual size of the supplied data, to allocate a Java object array (`new byte[len][]`). Because `intValueSafe()` can return values up to `Integer.MAX_VALUE`, a contract call with a tiny calldata payload but one crafted 32-byte word can trigger an attempted allocation of a multi-gigabyte array, independent of the (low) energy actually charged for that call. This mirrors the CVE-2016-6296 bug class: a length value taken from attacker input is used for a memory allocation/copy operation without validating it is consistent with the amount of actual data provided, producing a heap-based resource-exhaustion condition.

### Finding Description
`extractBytesArray` and `extractSigArray` read the array length purely from the decoded word at `offset`, with no check that `len` is bounded by the actual number of remaining `words`: [1](#0-0) 
`extractBytes32Array` has the identical pattern: [2](#0-1) 

These are invoked from `ValidateMultiSign.execute` and `BatchValidateSign.doExecute`. The `MAX_SIZE`/`sigArraySize` bound is only enforced when `VMConfig.allowTvmSelfdestructRestriction()` is active; the legacy `extractBytesArray` branch (still reachable when that hard-fork flag is off, or via the underlying helper logic itself) performs no length sanity check before allocation: [3](#0-2) [4](#0-3) 

The energy charged for the call is derived from `data.length` (the actual byte-array size of the calldata), not from the decoded length field: [5](#0-4) [6](#0-5) 

This decouples the metered cost from the actual resource consumption: a caller can submit a small calldata buffer (few words) but set one word to a very large value (e.g. `0x7fffffff`), causing `new byte[len][]` to attempt to allocate up to ~2^31 array-reference slots (multiple GB) while the transaction is only charged the tiny energy amount computed from the small `data.length`.

`BatchValidateSign.execute` wraps `doExecute` in a `catch (Throwable t)`, which may absorb the resulting `OutOfMemoryError` on the *calling* thread, but this does not undo the JVM-wide heap pressure/GC pause the failed allocation attempt causes: [7](#0-6) 
`ValidateMultiSign.execute`, however, calls `extractSigArray`/`extractBytesArray` (line 1072-1074) *before* entering its `try`/`catch(Throwable t)` block (which only wraps the signature-processing loop later in the method), so an `OutOfMemoryError` thrown during array allocation there propagates uncaught out of `execute()`.

I was not able to fully confirm, within the tool budget available, whether some outer layer in the TVM execution loop (e.g., `Program.callToPrecompiledAddress`, `VM`, or `Runtime`) has a blanket `catch (Throwable)`/`catch (Error)` that would contain this uncaught `OutOfMemoryError` before it can affect block processing; this should be verified before treating the "node crash/halt" outcome as certain rather than a heap-exhaustion/DoS risk.

### Impact Explanation
An `OutOfMemoryError` triggered mid-block-processing on a full node can destabilize or crash the JVM process (or leave it in a degraded state due to major GC thrashing), affecting the node's ability to continue validating/serving the chain — a node-crash/halt class impact reachable by any account that can deploy a contract and issue a single `CALL` to the `ValidateMultiSign` (or `BatchValidateSign`) precompile address with crafted calldata. This requires no special privileges beyond broadcasting an ordinary smart-contract transaction.

### Likelihood Explanation
Likelihood is high for the resource-mismatch condition itself: any unprivileged contract deployer/caller can construct the malicious calldata trivially (a handful of ABI words), and the required energy is minimal because it's computed from `data.length`, not the crafted length field. Whether this escalates all the way to a node crash/halt depends on unconfirmed upstream exception handling around precompile execution in the TVM interpreter loop, which limits full certainty of the worst-case impact.

### Recommendation
- In `extractBytesArray`, `extractSigArray`, and `extractBytes32Array`, validate the decoded `len` against the actual bounds of `words`/`data` (e.g., `len <= (words.length - offset - 1)`) before allocating, rejecting with `(false, EMPTY_BYTE_ARRAY)` on inconsistency, mirroring the `isValidAbiEncoding` check already gated behind `VMConfig.allowTvmOsaka()`.
- Make the `MAX_SIZE` bound checks in `ValidateMultiSign`/`BatchValidateSign` unconditional (not gated behind `allowTvmSelfdestructRestriction()`), and perform them before calling `extractBytesArray`/`extractSigArray`/`extractBytes32Array`.
- Move the `extractSigArray`/`extractBytesArray`/`extractBytes32Array` calls inside `ValidateMultiSign.execute`'s existing `try`/`catch(Throwable)` block so allocation failures are handled consistently with `BatchValidateSign`.
- Confirm and, if absent, add a top-level `catch (Throwable)` around precompile invocation in `Program.callToPrecompiledAddress` so a single malformed precompile call cannot escape as an uncaught `Error` during block application.

### Proof of Concept
1. Deploy a trivial contract that performs a low-level `CALL` (or use `staticcall`) to the `ValidateMultiSign` precompile address (`0000...01000c` per `VMConfig.allowTvmFreezeV2()`-style tables in `PrecompiledContracts`), or directly craft a transaction invoking it if permitted by the harness under test.
2. Build calldata as: word0 = target address, word1 = permissionId, word2 = signed data hash word, word3 = offset pointer chosen so the addressed length word equals `0x7fffffff`, followed by only a few real trailing words (so `data.length` remains small, e.g., 6-7 words = ~192-224 bytes).
3. Ensure `VMConfig.allowTvmSelfdestructRestriction()`/`allowTvmOsaka()` hard-fork flags are not both active (or craft input that still slips past the `isValidAbiEncoding`/`MAX_SIZE` guard if active) so the length-bound check is skipped.
4. Submit/execute the call: `extractBytesArray`/`extractSigArray` computes `len = 0x7fffffff` and executes `new byte[len][]`, attempting a multi-gigabyte allocation while `getEnergyForData` only charges energy proportional to the small `data.length`, demonstrating the metering/allocation mismatch.

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
