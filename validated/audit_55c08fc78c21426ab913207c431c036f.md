Audit Report

## Title
Outbound queue v2 pays relayer reward and settles pending orders while ignoring the delivery receipt's `success` flag - (File: `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs`)

## Summary
The `DeliveryReceipt` type decoded from the Ethereum `InboundMessageDispatched` event contains an explicit `success: bool` field indicating whether the referenced command actually executed successfully on the Gateway contract. `Pallet::process_delivery_receipt` never reads this field before paying the relayer reward via `T::RewardPayment::register_reward` and permanently removing the `PendingOrders` entry, meaning a relayer can collect a reward and cause the chain to forget about the pending order even when the underlying dispatch failed on Ethereum.

## Finding Description
`submit_delivery_receipt` verifies the event log/proof pair, decodes it into a `DeliveryReceipt`, and calls `process_delivery_receipt` [4](#0-3) . The `TryFrom<&Log>` implementation for `DeliveryReceipt` decodes the Solidity event `InboundMessageDispatched(uint64 nonce, bytes32 topic, bool success, bytes32 reward_address)` and correctly populates `receipt.success` from the on-chain event [5](#0-4) .

In `process_delivery_receipt`, the code checks `receipt.gateway`, resolves `reward_account`, fetches the `PendingOrder` for `receipt.nonce`, and — if `order.fee > 0` — pays the reward via `register_reward`, then unconditionally removes the `PendingOrders` entry and emits `MessageDelivered` [3](#0-2) . The `receipt.success` field is never referenced anywhere in this function or in `submit_delivery_receipt`. Since the Gateway contract emits `InboundMessageDispatched` regardless of whether the dispatched command succeeded or reverted (the event's whole purpose, per its signature, is to report both outcomes via the `success` flag), a relayer holding proof of a *failed* dispatch's event log can submit it and still receive the full reward while the chain's only record of the pending obligation (`PendingOrders[nonce]`) is deleted forever.

## Impact Explanation
This breaks the "duplicate settlement / payout must match actual execution outcome" invariant: reward payout and pending-order removal must only happen after successful execution. Because `PendingOrders` is the sole bookkeeping mechanism reconciling outbound message delivery, once removed there is no path to retry or refund a failed command — this permanently loses the associated fee to a relayer for work that did not actually deliver value, and permanently discards the chain's record of an outstanding cross-chain obligation. This matches the allowed impact category of duplicate/incorrect settlement and bridge-state loss.

## Likelihood Explanation
`submit_delivery_receipt` requires only `ensure_signed(origin)` — any unprivileged account can call it [6](#0-5) . A relayer performing legitimate work already needs to construct proofs for Gateway-emitted logs; the exact same tooling suffices to submit a proof for a log where `success == false`, since `T::Verifier::verify` only checks proof/log authenticity, not the semantic outcome encoded in `success`.

## Recommendation
In `process_delivery_receipt`, branch explicitly on `receipt.success`: only call `T::RewardPayment::register_reward` and `<PendingOrders<T>>::remove(nonce)` when `receipt.success` is `true`. On `false`, route to a distinct failure-handling path (e.g., retry, refund to the original sender, or an explicit non-rewarded settlement) that does not pay the relayer and documents the failed delivery rather than silently discarding `PendingOrders[nonce]`.

## Proof of Concept
1. A message is queued via `do_process_message`, creating `PendingOrders[nonce]` with `fee > 0` [7](#0-6) .
2. The corresponding command is dispatched on the Ethereum Gateway and fails/reverts, but the Gateway still emits `InboundMessageDispatched(nonce, topic, success=false, reward_address)` for the nonce (per the event's own definition, it exists to report both success and failure).
3. A relayer obtains proof for this log and calls `submit_delivery_receipt`; `T::Verifier::verify` succeeds and `DeliveryReceipt::try_from` decodes `success: false` correctly.
4. `process_delivery_receipt` proceeds without checking `receipt.success`, calls `register_reward` for the relayer, and removes `PendingOrders[nonce]` — rewarding the relayer and erasing the record of a failed delivery, as shown in `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs` lines 446-480 where `receipt.success` is never read.

		where

			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
