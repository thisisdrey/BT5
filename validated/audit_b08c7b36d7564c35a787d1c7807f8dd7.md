### Title
Unbounded uninstantiated-attachment ingestion via `/v2/transactions` evicts legitimate inboxed BNS attachments before instance resolution - (File: stackslib/src/net/atlas/db.rs)

### Summary
`AtlasDB::insert_uninstantiated_attachment` (db.rs:511-536) stores any attachment content submitted alongside a contract-call transaction without verifying that its `Hash160` matches any `attachment_instances.content_hash` row from a confirmed on-chain commitment. Because eviction (`evict_k_oldest_uninstantiated_attachments`, db.rs:538-547) is oldest-first once `count_uninstantiated_attachments() >= max_uninstantiated_attachments` (db.rs:517), an attacker who repeatedly submits contract-call transactions to the configured BNS contract with distinct garbage attachment payloads can churn the uninstantiated-attachment table and evict real attachments that are awaiting resolution by `check_attachment_instances` (download.rs:227-286).

### Finding Description
The reachable path is `RPCPostTransactionRequestHandler::try_handle_request` (posttransaction.rs:169-254), which, for a `TransactionPayload::ContractCall` whose contract matches `AtlasConfig.contracts` (i.e., the boot `bns` contract) and passes `AtlasDB::should_keep_attachment`, unconditionally calls `network.get_atlasdb_mut().insert_uninstantiated_attachment(attachment)` (posttransaction.rs:231-249). This gate checks only the target contract identity and attachment size constraints — it does not require the attachment's `Hash160::from_data(content)` (mod.rs:158-160) to correspond to any row already present in `attachment_instances`.

`insert_uninstantiated_attachment` (db.rs:511-536) therefore accepts and stores content whose hash has zero matching `attachment_instances.content_hash` rows, i.e., content with no on-chain commitment. Once `count_uninstantiated_attachments()` reaches `max_uninstantiated_attachments` (default `MAX_UNINSTANTIATED_ATTACHMENTS_MIN = 50_000`, mod.rs:53/108), each further insert evicts the single oldest unresolved attachment row via `evict_k_oldest_uninstantiated_attachments` (db.rs:538-547), which deletes purely by `created_at ASC` with no regard to whether a real `attachment_instances` row is waiting on that content (`find_uninstantiated_attachment`, db.rs:594-604, is used later by `check_attachment_instances`, download.rs:255-262, to resolve instances against inboxed content). A sustained flood of distinct-content, hash-mismatched attachments can therefore push a legitimately-inboxed attachment (matching a real, confirmed BNS `content_hash`) out of the table before the corresponding `AttachmentInstance` is processed, breaking the intended invariant that every stored `attachments.hash` value eventually corresponds to a `attachment_instances.content_hash` committed by a confirmed transaction.

The transaction is accepted into the node's mempool via `mempool.submit` (posttransaction.rs:214-223) and is also broadcast further via `node.set_relay_message(StacksMessageType::Transaction(tx))` (posttransaction.rs:264-266), which propagates the same attack to every peer that relays/accepts the transaction, amplifying the effect network-wide.

### Impact Explanation
Repeated submissions evict oldest-inserted uninstantiated attachments, which can include real BNS attachment content gossiped/POSTed shortly before resolution. This causes real attachment content that would otherwise be validated against an on-chain `attachment_instances` commitment to be silently dropped, delaying or preventing correct instance resolution (attachment/BNS mismatch impact). This is a storage/eviction-churn DoS scoped to the Atlas subsystem, not a crash or unauthenticated write of forged state.

### Likelihood Explanation
The attacker must submit well-formed, signed transactions that pass `mempool.submit` (valid signature, sufficient fee, valid nonce) targeting the configured BNS contract with a `ContractCall` payload plus an attached payload accepted by `should_keep_attachment`. This requires a funded account and per-transaction fee/nonce cost — it is not free traffic volume, but it does not require any privileged role, secret, or admin access; it only requires the ability to submit RPC transactions, which any remote unprivileged party can do. Reaching `max_uninstantiated_attachments` (50,000 by default) requires many distinct submissions, making the attack economically bounded but feasible for a motivated attacker with a funded key and low per-tx fees, since submission to `/v2/transactions` does not require the transaction to be mined — only accepted by mempool.

### Recommendation
Gate `insert_uninstantiated_attachment` (or `should_keep_attachment`) so that inboxed attachment content is only persisted if its hash matches an existing (even unresolved) `attachment_instances.content_hash` row, or track provenance so eviction prioritizes content with no matching pending instance over content that is actively awaited by a known `AttachmentInstance`. Alternatively, change `evict_k_oldest_uninstantiated_attachments`'s ordering/selection to exclude/deprioritize rows whose hash currently matches a row in `attachment_instances` with `is_available = 0`.

### Proof of Concept
Rust unit test in `stackslib/src/net/atlas/tests.rs`:
1. Configure `AtlasConfig` with a small `max_uninstantiated_attachments` (e.g., 10, honoring `MAX_UNINSTANTIATED_ATTACHMENTS_MIN` bypass via `connect_memory`/direct config in test).
2. Insert one real attachment instance row into `attachment_instances` (simulating a confirmed BNS commitment) via the instance-insertion API, leaving it `is_available = 0`.
3. Call `atlas_db.insert_uninstantiated_attachment(&legit_attachment)` where `legit_attachment.hash()` equals that instance's `content_hash`.
4. Loop calling `atlas_db.insert_uninstantiated_attachment(&garbage_attachment_i)` with `max_uninstantiated_attachments` distinct-content attachments whose hashes match none of `attachment_instances`.
5. Assert `atlas_db.find_uninstantiated_attachment(&legit_attachment.hash())` returns `None` (evicted) even though the corresponding `attachment_instances` row is still unresolved — demonstrating the eviction of legitimate content ahead of resolution, following the same pattern already exercised in `test_evict_k_oldest_uninstantiated_attachments` (tests.rs:889-1017).     pub fn insert_uninstantiated_attachment(
        &mut self,
        attachment: &Attachment,
    ) -> Result<(), db_error> {
        // Insert the new attachment
        let uninstantiated_attachments = self.count_uninstantiated_attachments()?;
        if uninstantiated_attachments >= self.atlas_config.max_uninstantiated_attachments {
            let to_delete =
                1 + uninstantiated_attachments - self.atlas_config.max_uninstantiated_attachments;
            self.evict_k_oldest_uninstantiated_attachments(to_delete)?;
        }

        let tx = self.tx_begin()?;
        let now = util::get_epoch_time_secs() as i64;
        let res = tx.execute(
            "INSERT OR REPLACE INTO attachments (hash, content, was_instantiated, created_at) VALUES (?, ?, 0, ?)",
            params![
                attachment.hash(),
                attachment.content,
                now,
            ],
        );
        res.map_err(db_error::SqliteError)?;
        tx.commit().map_err(db_error::SqliteError)?;
        Ok(())
    }

    pub fn evict_k_oldest_uninstantiated_attachments(&mut self, k: u32) -> Result<(), db_error> {
        let tx = self.tx_begin()?;
        let res = tx.execute(
            "DELETE FROM attachments WHERE hash IN (SELECT hash FROM attachments WHERE was_instantiated = 0 ORDER BY created_at ASC LIMIT ?)",
            params![k],
        );
        res.map_err(db_error::SqliteError)?;
        tx.commit().map_err(db_error::SqliteError)?;
        Ok(())
    }
