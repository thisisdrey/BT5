### Title
Unbounded array allocation from attacker-controlled length field in TVM precompiled-contract calldata parsing causes OutOfMemoryError node crash - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
`PrecompiledContracts.extractBytesArray`, `extractBytes32Array` and `extractSigArray` read a "length" word directly from attacker-supplied precompile calldata and immediately allocate a Java array sized by that length, without validating it against the actual size of the input buffer first, mirroring the CVE-2017-12944 pattern (a length field parsed from a header/short input is used to size an allocation before the real available data size is checked, causing an allocation failure / crash).

### Finding Description
`extractBytes32Array` and `extractBytesArray`/`extractSigArray` take the array length straight from the decoded word stream: [1](#0-0) 

`len` comes from `words[offset].intValueSafe()`. `intValueSafe()` does not clamp to a value related to the actual calldata size — it only clamps to `Integer.MAX_VALUE` when the raw 256-bit word occupies more than 4 bytes or decodes negative: [2](#0-1) 

Because a caller can put an arbitrary 32-byte word (e.g. `0x00000000...7fffffff`) at the length position, `len` can reach `Integer.MAX_VALUE` (2,147,483,647). `new byte[len][]` (an array of ~2.1 billion object references, ~17 GB on a 64-bit JVM) or `new byte[len][]`/`new byte[len]` variants in these helpers is attempted immediately, before any bound check against `words.length` or `data.length`. This is the same root-cause shape as `TIFFReadDirEntryArray`/`TIFFFetchStripThing` in the CVE: a length taken from attacker-controlled input drives a memory allocation before the code has confirmed the input actually contains that much data.

The only bound check performed (`offset > words.length - 1`) protects against an out-of-range *offset*, not against an oversized *length* value used for the allocation itself.

### Impact Explanation
An oversized allocation attempt of this size will typically throw `OutOfMemoryError`. `OutOfMemoryError` is an `Error`, not an `Exception`; unless every call frame in the TVM execution/precompile dispatch path specifically catches `Throwable`/`Error` (not just `Exception`), this will propagate out of contract execution and crash or destabilize the node process handling the transaction, meeting the "node crash or halt" impact bar for this analog scan. This is reachable by any account that can invoke a smart contract making a `CALL`/`STATICCALL` to the precompiled-contract address handling this calldata format — no elevated privileges are required.

### Likelihood Explanation
Any transaction broadcaster can construct calldata to the affected precompiled contract with a manipulated length word; this requires no special permissions, only a normal signed transaction invoking a contract that calls the precompile (or a contract deployed by the attacker themselves that performs the call). The trigger is a single crafted transaction.

### Recommendation
In `extractBytesArray`, `extractBytes32Array`, and `extractSigArray`, validate `len` against the remaining size of `words`/`data` (e.g., `len <= (words.length - offset - 1)`) before allocating any array, and reject/return empty on mismatch, analogous to how `RLP.verifyLength` bounds lengths against `msgData.length - pos` elsewhere in the codebase: [3](#0-2) 

### Proof of Concept
1. Deploy or use any contract that performs a `CALL`/`STATICCALL` to the affected precompiled contract address whose execute() path uses `extractBytesArray`/`extractBytes32Array`/`extractSigArray`.
2. Craft the calldata so the word at the "array length" offset is set to `0x000000000000000000000000000000000000000000000000000000007fffffff` (or similar large value) while the surrounding words array is otherwise short/valid enough to reach the extraction call.
3. Broadcast the transaction; the precompile execution attempts `new byte[len][]` with `len` near `Integer.MAX_VALUE`, triggering `OutOfMemoryError` during transaction processing on the executing node.

Note: I was not able to conclusively identify, within the available tool budget, exactly which specific precompiled contract (address/name) invokes each of these three helper methods — this would need direct confirmation by reading the surrounding precompile classes in `PrecompiledContracts.java` in full via a Devin session, since the index only returned the helper definitions themselves.

    int len = words[offset].intValueSafe();

  /**
   * In case of int overflow returns Integer.MAX_VALUE otherwise works as #intValue()
   */
  public int intValueSafe() {
    int bytesOccupied = bytesOccupied();
    int intValue = intValue();
    if (bytesOccupied > 4 || intValue < 0) {
      return Integer.MAX_VALUE;
    }
    return intValue;
  }
