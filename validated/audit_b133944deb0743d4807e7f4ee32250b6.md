### Title
Optimistic StackerDB inventory update before chunk commit allows serving non-canonical (false) inventory to peers - ([File: stackslib/src/net/stackerdb/mod.rs])

### Summary
`PeerNetwork::handle_unsolicited_StackerDBPushChunk` validates a pushed chunk against an in-memory/point-in-time view of expected chunk versions, then immediately patches the outgoing `StackerDBChunkInv` reply to claim the new (higher) version is now held, and signs and sends that reply back to the peer — all *before* the chunk is actually durably committed via `StackerDBTx::try_replace_chunk`. The real, authoritative commit happens later (asynchronously, via the relayer), and that authoritative check can fail (`StaleChunk`, `TooManySlotWrites`, or a DB error), in which case the chunk is silently dropped. This mirrors the reported bug class: an equality/state check is answered based on a value taken before the state-changing operation is actually applied, so the "served" state and the "committed" state can diverge.

### Finding Description
`validate_received_chunk` (`stackslib/src/net/stackerdb/mod.rs:649-718`) checks the pushed chunk's signature and version against an `expected_versions` slice that is a snapshot taken either from the just-built `StackerDBChunkInv` (`data.slot_versions`) or, on the `FutureView` buffering path, from `self.stackerdbs.get_slot_versions(...)` read at that instant.

Immediately after this snapshot-based check passes, `handle_unsolicited_StackerDBPushChunk` (`stackslib/src/net/stackerdb/mod.rs:742-871`) does the following, in order:
1. Patches the in-memory `StackerDBChunkInv.slot_versions[slot_id]` to the new chunk's version — i.e., declares the chunk "accepted" (lines 794-807, "patch inventory -- we'll accept this chunk").
2. Wakes up the sync state machine (lines 809-814).
3. Signs and sends this patched inventory back to the remote peer as the reply (lines 858-870), with the misleading comment "this is a reply to the pushed chunk, and we can store it right now (so don't buffer it)" — note that no store actually occurs here.
4. Returns `(false, true)`, meaning "forward to relayer," which performs the actual write.

The actual, authoritative write validation/commit happens in `StackerDBTx::try_replace_chunk` (`stackslib/src/net/stackerdb/db.rs:400-438`), which re-checks the chunk's signature against the *current* `SlotValidation` and re-checks the version against the *current* stored version — and can fail with `Error::StaleChunk`, `Error::TooManySlotWrites`, or a generic DB error. When invoked from the relayer's bulk chunk-processing path (`stackslib/src/net/relay.rs:2406-2437`), any such failure is only logged (`debug!`/`warn!`) and the chunk is dropped via `continue` — it is never stored.

This creates exactly the sequencing fault described in the external report: a value is read/reported (the "accepted" inventory) using a pre-write snapshot, and the actual state-mutating operation (commit) is performed afterward and independently, using a fresh/authoritative check that can disagree with the earlier snapshot. The equality broken is: *served inventory (StackerDBChunkInv reported to peers) == actually-stored chunk state*. The `chat.rs::make_stacker_db_getchunk_response` code even carries a `// TODO: this is racey` comment (`stackslib/src/net/chat.rs:1974`) acknowledging that a later `StackerDBGetChunk` request for the "advertised" version can legitimately race with real storage state and produce a stale/future-version NACK.

### Impact Explanation
StackerDB inventory (`StackerDBChunkInv`) is the mechanism peers use to decide what to fetch and from whom, using rarest-first/newest-first scheduling (`stackslib/src/net/stackerdb/sync.rs::make_chunk_request_schedule`). If a node signs and broadcasts/replies with an inventory claiming it holds a chunk version it does not actually have committed, remote peers relying on that inventory can:
- Deprioritize or skip fetching that chunk version from other legitimate replicas, believing this node already propagated it, delaying/stalling real propagation of StackerDB data (used for signer messages, etc.) across the network.
- Get a NACK / stale-version mismatch when they subsequently request the "advertised" chunk, since `get_chunk`/`get_slot_version` reflect the real (unwritten) state.

This matches the High-severity category in the rules: "steering a node off the tip via false inventory" through non-canonical state (an unwritten chunk) being served as canonical (falsely-advertised committed inventory).

### Likelihood Explanation
Any authenticated remote peer can trigger this by pushing `StackerDBPushChunk` messages. The signature/version checks that gate the optimistic inventory patch are a point-in-time snapshot distinct from the authoritative check performed at actual commit time, so any legitimate race (concurrent chunk writes hitting `max_writes`, a concurrently-inserted higher version causing `StaleChunk`, or a transient DB error) will reproduce the divergence without requiring any privileged access — the attack only needs normal, valid signer credentials for the given slot (which are permitted to push chunks at will) and a benign race condition, which is easy to induce by pushing chunks close to configured `max_writes`/`write_freq` boundaries.

### Recommendation
Do not patch/sign/send the "accepted" `StackerDBChunkInv` reply until after the chunk has actually been durably committed via `StackerDBTx::try_replace_chunk` (or equivalent authoritative check). If the design requires an immediate ack for latency reasons, the reply should reflect the *actual* result of the commit attempt (including falling back to reporting the pre-existing version on failure), not an optimistic pre-commit value. Alternatively, re-query the authoritative slot version right before constructing the outgoing inventory reply.

### Proof of Concept
1. Configure a StackerDB slot with a low `max_writes` (or exercise `write_freq`/version races) for a given signer.
2. As an authenticated peer, push a `StackerDBPushChunk` message with `slot_version = expected_version + 1`, signed correctly, but crafted (or timed) so that by the time the relayer processes it for actual storage, `try_replace_chunk` rejects it with `TooManySlotWrites` or `StaleChunk` (e.g., by racing two pushes for the same slot in quick succession, or exceeding `config.max_writes`).
3. Observe that `handle_unsolicited_StackerDBPushChunk` still validates via `validate_received_chunk` against the stale/point-in-time `expected_versions`, patches `data.slot_versions[slot_id]` to the new version, and sends back a signed `StackerDBChunkInv` claiming that version is now held — this reply is generated deterministically before the relayer's `try_replace_chunk` call runs (`stackslib/src/net/relay.rs:2412-2437`), and can be sent even in cases the later write is dropped.
4. A subsequent `StackerDBGetChunk` for that slot/version from a third peer that trusted the advertised inventory receives a NACK (`NackErrorCodes::StaleVersion`/`FutureVersion`) from `make_stacker_db_getchunk_response` (`stackslib/src/net/chat.rs:1975-1988`), confirming the inventory-vs-storage mismatch that was propagated to the network.

**Note on confidence**: I was unable to fully trace, within the available search iterations, the exact code path that performs the final commit for chunks arriving via the *unsolicited push* path specifically (as opposed to the sync-driven `chunks_to_store` path in `relay.rs::process_stacker_db_chunks`, which I confirmed handles `StackerDBSyncResult`s from active sync, not necessarily unsolicited pushes). The core sequencing fault — optimistic inventory patch/sign/send occurring before any confirmed commit, based only on a point-in-time `validate_received_chunk` check — is solidly supported by the cited code, but the precise plumbing from `handle_unsolicited_StackerDBPushChunk`'s `(false, true)` return value to the actual storage call site should be verified directly in the repository (e.g., via a Devin session with full file access) before treating this as fully proven end-to-end.
