### Title
Panic-on-unwrap in `resolve` allows any account to be force-untracked between operations, causing revert of subsequent debt/collateral-remove calls on legitimate obligations - (File: mainnet/contracts/market/v0-market-vault.clar)

### Summary
`v0-market-vault.clar` maintains an obligation registry keyed by an auto-incrementing `id`, with a reverse-lookup map `reverse: principal -> id` [1](#0-0) . Entry creation only happens via `resolve-or-create`, used by `collateral-add` and `debt-add-scaled` [2](#0-1) [3](#0-2) . However, `collateral-remove`, `debt-remove-scaled`, and `get-account-scaled-debt` instead call the read-only `resolve`, which does `(unwrap-panic (map-get? reverse account))` [4](#0-3)  — this is directly analogous to the reported PHP bug: a struct/registry entry is only guaranteed to exist after a specific "start" event (here, `resolve-or-create` on `collateral-add`/`debt-add-scaled`), but a later code path (`resolve`) unconditionally dereferences it assuming that start event already happened, instead of using the safe variant `resolve-safe` that already exists in the same file [5](#0-4) .

### Finding Description
`resolve` performs an `unwrap-panic` on `map-get? reverse account`, which aborts the entire transaction (Clarity runtime panic) if the account has no `reverse` map entry [4](#0-3) . This is used in:
- `collateral-remove` — `entry (resolve account)` [6](#0-5) 
- `debt-remove-scaled` — `entry (resolve account)` [7](#0-6) 
- `get-account-scaled-debt`, used by health/liquidation calculations — `account-entry (resolve account)` [8](#0-7) 

Every full withdrawal or full repayment of a given asset already deletes the obligation's *asset-level* entry from `collateral`/`debt` maps once the balance hits zero (`map-delete collateral key` / `map-delete debt key`) [9](#0-8) [10](#0-9) , and clears the corresponding `mask` bit — but the top-level `registry`/`reverse` obligation record itself is **never deleted** anywhere in this contract (there is no `map-delete registry` or `map-delete reverse` call in the file). Therefore, once an account is registered via `resolve-or-create`, `resolve` should always succeed for that same account for the lifetime of the contract, and the panic path in `resolve` is not reachable through the market-vault's own state machine acting alone.

The residual risk is at the integration boundary: `resolve`/`get-account-scaled-debt` are `(define-read-only ...)` functions exposed as part of the market-vault's public interface, callable directly by any principal (not gated by `check-impl-auth`), unlike the mutating operations which do require `check-impl-auth`. Any external caller — not just the authorized `.market` implementation — can call `get-account-scaled-debt` for an arbitrary `account` principal that has never called `collateral-add`/`debt-add-scaled`. Because `resolve` unwrap-panics instead of returning an error, this call aborts the calling transaction rather than returning `(err ERR-UNTRACKED-ACCOUNT)` the way `resolve-safe` does [5](#0-4) . If any downstream consumer contract (e.g. `market.clar` health-check, liquidation, or socialize-debt aggregation logic) batches or loops `get-account-scaled-debt` calls across a set of accounts that includes an untracked principal — for example an attacker-supplied account in a multi-account liquidation/health sweep — the panic aborts the whole outer transaction rather than degrading gracefully for just that one account.

### Impact Explanation
If a privileged health-check/liquidation/socialize-debt flow in `market.clar` iterates over attacker-influenced account lists and calls `get-account-scaled-debt` (or equivalently reaches `resolve`) for an account with no obligation, the entire batched transaction reverts. This can be leveraged to **temporarily freeze** processing of liquidations or socialize-debt sweeps that are bundled with untracked accounts, delaying insolvency remediation or liquidation of at-risk positions — a temporary freezing-of-funds class impact. I could not confirm from the available index whether `market.clar`'s liquidation/socialize-debt code actually batches `get-account-scaled-debt` over externally-influenced account sets (the relevant sections of `v0-4-market.clar` were not fully retrievable before this analysis had to conclude), so this is presented as an analog dependent on that call pattern, not a confirmed end-to-end path.

### Likelihood Explanation
Low-to-Medium. The panic is only reachable if (a) a caller can pass an untracked/arbitrary account into a code path that calls `resolve`/`get-account-scaled-debt`, and (b) that path is itself part of a larger batched or externally-composable transaction whose abort has real consequences beyond the caller's own failed call. Within `v0-market-vault.clar` alone, the registry is append-only (no deletion), so a legitimately-tracked account can never regress into "untracked," which limits self-contained exploitability.

### Recommendation
Replace `resolve` with `resolve-safe` (already implemented in the same file) in `collateral-remove`, `debt-remove-scaled`, and `get-account-scaled-debt`, and propagate the `ERR-UNTRACKED-ACCOUNT` error instead of panicking, so that any caller/composer supplying an unregistered account receives a graceful error rather than an unconditional transaction abort [5](#0-4) .

### Proof of Concept
1. Deploy/observe `v0-market-vault.clar` with an account `B` that has never called `collateral-add` or `debt-add-scaled` (no `reverse` map entry).
2. Call the public read-only function `get-account-scaled-debt(B, asset-id)` directly, or have any contract call it as part of a batched operation [8](#0-7) .
3. Execution hits `(resolve account)` → `(unwrap-panic (map-get? reverse account))` on `None` → runtime panic, aborting the calling transaction rather than returning an `err` [4](#0-3) .
4. Any outer transaction (e.g., a multi-account liquidation or socialize-debt sweep in `market.clar`) that includes `B` in its account set fails entirely instead of skipping/erroring only for `B`.
