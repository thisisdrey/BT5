### Title
Protocol fees on NEP-245/IMT multi-tokens can be bypassed by splitting a trade into many `delta = ±1` `TokenDiff` intents - ([File: contracts/defuse/core/src/intents/token_diff.rs])

### Summary
`TokenDiff::token_fee` returns `Pips::ZERO` for `TokenIdType::Nep245 | TokenIdType::Imt` whenever the per-intent `amount <= 1`, regardless of the cumulative value moved across separate `execute_intents` calls. Because the fee decision is made purely from the `amount` argument of a single `TokenDiff` intent and there is no aggregation across batches/accounts, an attacker who defines (or already holds) a NEP-245/IMT token whose real value is concentrated in unit-sized balances can move arbitrarily large value fee-free by submitting many `delta.unsigned_abs() == 1` intents instead of one intent with `amount = N`.

### Finding Description
The binding that should hold is: `fee_owed(single TokenDiff with |delta|=N) == Σ fee_owed(N TokenDiff intents with |delta|=1 each)`. Tracing `TokenDiff::execute_intent` in [1](#0-0) , the fee for a negative delta is computed as `Self::token_fee(token_id, amount, protocol_fee).fee_ceil(amount)`, and `token_fee` explicitly exempts `Nep245`/`Imt` tokens whenever `amount <= 1`: [2](#0-1) 

For a single intent with `amount = N > 1`, the `if amount > 1 => {}` arm falls through to `fee` (nonzero). For N separate intents each with `amount = 1`, every one hits the `Pips::ZERO` arm. Each `execute_intents` call is processed independently by `Engine::execute_signed_intents`, which only enforces a zero-sum invariant *within* that call's batch via `finalize()` [3](#0-2) ; there is no cross-batch or cross-account aggregation of `amount` for fee purposes anywhere in `Engine`, `Deltas`, or `TokenDiff`.

Exploit flow: attacker deploys/controls a NEP-245 contract that defines a sub-token id whose economically meaningful unit is `1` (e.g., a coarse-granularity token where 1 unit == large real value). Attacker (optionally colluding with a counterparty account they also control) submits N separate `MultiPayload`s, each containing a matched pair of `TokenDiff` intents that trade `1` unit of the high-value token for some other asset. Each call is fee-exempt via the `amount <= 1` branch. Repeating this N times moves the same aggregate value that a single `TokenDiff` with `amount = N` would have moved, but the latter would incur `protocol_fee` via `fee_ceil` on the whole `N`.

None of the existing guards (`MultiPayload::verify`, nonce/salt checks, `finalize`'s zero-sum invariant, `assert_one_yocto`, access-control) address this because they operate correctly and are unrelated to the fee-threshold logic; the flaw is purely in `token_fee`'s per-call, per-amount exemption rule for `Nep245`/`Imt`.

### Impact Explanation
Protocol fees that should be credited to `fee_collector` via `internal_add_balance` [4](#0-3)  are never collected when the trade is split into unit-sized legs, even though the equivalent single-shot trade would owe fees. This matches the Critical category "protocol fees bypassed" — no unauthorized token movement occurs and no user's signature is misused, but the protocol systematically under-collects its designed revenue, repeatably, across any account and any NEP-245/IMT token the attacker controls, with attacker "profit" equal to the avoided fee amount.

### Likelihood Explanation
Preconditions are entirely within an unprivileged attacker's control: they only need to deploy or use a NEP-245/IMT contract with a token id at unit granularity representing high value, and sign and submit N `execute_intents` calls (self-trading between two accounts they control, or trading with any willing counterparty). No role, relayer key, or DAO action is required. The only cost is N transactions' worth of gas, which scales linearly but is not a barrier to a determined actor extracting an unbounded amount of value fee-free.

### Recommendation
Base the `Nep245`/`Imt` fee exemption on an intrinsic token property (e.g., a per-token `decimals`/`supply == 1` marker registered at token-id definition time, similar to how NEP-171 NFTs are structurally single-unit) rather than on the transient `amount` of an individual `TokenDiff` delta, so the exemption cannot be gamed by choosing token granularity or by splitting a trade into many unit-sized intents.

### Proof of Concept
`cargo test` plan (unit test in `contracts/defuse/core/src/intents/token_diff.rs` or an integration test using the `Engine`/`Deltas` test harness):
1. Construct a `Nep245TokenId` sub-token `X` and two accounts A and B holding balances that let them trade `X` for another asset `Y`.
2. Case 1 (single intent): sign one `MultiPayload` with paired `TokenDiff` intents `{X: -N, Y: +k}` (A) and `{X: +N, Y: -k}` (B), `N > 1`, protocol `fee = Pips::ONE_PERCENT`. Execute via `Engine::execute_signed_intents`. Assert `fee_collector` balance of `X` equals `fee.fee_ceil(N)` (nonzero).
3. Case 2 (split): sign N separate `MultiPayload`s, each with paired `TokenDiff` intents `{X: -1, Y: +k/N}` / `{X: +1, Y: -k/N}`, same `fee`. Execute all N via N calls to `execute_signed_intents`. Assert `fee_collector`'s cumulative balance of `X` is `0`, despite moving the same total `N` units of `X`.
4. Assert the two `fee_collector` totals differ (`N * fee.fee(1) == 0 != fee.fee_ceil(N) > 0`), proving the bypass.
