### Title
Repeated fee drain from an ETH-implicit wallet via replay of the unvalidated `EOABaseTokenTransfer` address-check path - ([File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs])

### Summary
The Wallet Contract (`WalletContract::rlp_execute`) fires an unconditional relayer-fee `Transfer` promise as soon as an Ethereum-emulated base-token transfer is parsed, *before* the asynchronous registrar check that determines whether the transaction is actually valid completes. When that check later determines the relayer supplied an invalid target (`address_check_callback`, target resolves to an already-registered Near account), the code deliberately does **not** advance the on-chain replay-prevention `nonce`, on the stated assumption that "an honest relayer may still be able to successfully send the user's intended transaction" later. Because the fee-refund promise was already dispatched (and is *not* conditioned on, or rolled back by, the later-failing check), a relayer can resubmit the exact same signed payload indefinitely, draining `fee` from the wallet on every call without the user's intended action ever completing — mirroring the Saffron pattern of a step 2 (fee-bearing) action being reachable before/without step 1 (validation) actually gating it.

### Finding Description
In `inner_rlp_execute` (`runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs:330`), once `parse_rlp_tx_to_action` succeeds, the code decides whether to advance the replay-prevention `nonce`: [1](#0-0) 

For the `EOABaseTokenTransfer { address_check: Some(_), .. }` variant — i.e. when the target looks like another eth-implicit wallet and must first be checked against the address registrar to make sure it isn't actually a real, already-registered Near account — the nonce is intentionally **not** incremented yet. Immediately after that branch, however, the fee-refund promise to the relayer (`predecessor_account_id`) is created unconditionally for *any* `EOABaseTokenTransfer`, including this not-yet-validated one: [2](#0-1) 

The actual registrar validation only happens later, asynchronously, in the callback: [3](#0-2) 

If the registrar lookup returns `Some(account_id)` (the target really is a registered named account, i.e. the relayer's chosen target was invalid), the callback returns an error result (`"Invalid target: ..."`) and resets `has_in_flight_tx = false`, but — as noted in the code comment — the nonce was never advanced, specifically so the same underlying user-signed Ethereum transaction can be retried by another relayer.

The flaw is that the fee-refund promise (`env::promise_batch_action_transfer(refund_promise, *fee)`, `lib.rs:383`) already executed unconditionally in the first call, *before* the registrar validation outcome was known, and is not tied to or reversible based on the callback's success/failure. Since the nonce is not advanced when the callback determines the target was invalid, nothing stops the *same* relayer (or any account controlling `predecessor_account_id`) from calling `rlp_execute` again with the identical `target`/`tx_bytes_b64`. The registrar lookup result is deterministic (the target account either exists or doesn't), so every such replay reaches `inner_rlp_execute`, re-parses the same fixed nonce, and re-fires a new fee-refund `Transfer` promise to the caller — before the (always-failing, for this target) callback runs again. The `has_in_flight_tx` guard only prevents *concurrent* in-flight calls, not this kind of *sequential* replay once each call's promise chain resolves.

Because `fee` is taken from the immutable, user-signed Ethereum transaction (`tx.max_fee_per_gas * tx.gas_limit`, capped by `VALUE_MAX`, see `runtime/near-wallet-contract/implementation/wallet-contract/src/internal.rs:59-64`), the amount per drain is bounded per call but the number of calls is unbounded — an attacker-controlled relayer account can loop `rlp_execute` calls, each draining `fee` yoctoNEAR from the wallet, without the corresponding "step 2" (successful transfer/action) ever completing, since the target will always resolve as invalid.

### Impact Explanation
This is a concrete fund-theft vector against ETH-implicit wallet-contract holders: an unprivileged relayer (any account, no special permission needed beyond being allowed to call the public `rlp_execute` method — which is open to any predecessor per NEP-518's design) can repeatedly drain the wallet's balance in `fee`-sized increments by resubmitting a single previously-signed, still-fresh-nonce Ethereum transaction that targets an already-registered account. Given enough repetitions this can exhaust the wallet's entire balance. This satisfies the "concrete theft ... of funds" bar for validity, reachable purely through a normal deployed-contract interaction (calling `rlp_execute`), matching the report's bug class of a value-moving step firing ahead of / independent from the validation step meant to gate it.

### Likelihood Explanation
Likelihood is Medium: it requires (a) a user constructing/signing an Ethereum-style base-token-transfer transaction whose `to` address happens to collide with (or be deliberately crafted by a colluding "honest-looking" relayer to point at) an account that is registered in the address registrar, and (b) a relayer willing to replay the same call repeatedly instead of behaving honestly. Because relayers are explicitly untrusted third parties in this design (the whole point of "ban_relayer" logic), and the replay only needs the relayer to resend an identical payload it already possesses, this is straightforward for a malicious/economically-motivated relayer to execute against any wallet using this flow, and does not require the user to make any additional mistake beyond using this particular targeting path.

### Recommendation
Do not fire the relayer fee-refund promise until the transaction is known to be valid. Specifically:
- Move the fee-refund promise for `EOABaseTokenTransfer { address_check: Some(_), .. }` out of `inner_rlp_execute`'s eager dispatch and into `address_check_callback`, only after confirming `maybe_account_id.is_none()` (i.e., the target is confirmed to genuinely be an eth-implicit account and the transaction will proceed).
- Alternatively, advance/reserve the nonce (or otherwise mark the specific `(target, tx_bytes_b64)` pair as consumed) as soon as the fee-refund promise is dispatched, so that a failing registrar check cannot be paired with an unbounded number of repeat fee payouts for the same nonce.

### Proof of Concept
1. Deploy the Wallet Contract to an ETH-implicit account `W` funded with `N` NEAR, and register a relayer's access key on `W` as in `test_register_relayer` (`runtime/near-wallet-contract/implementation/wallet-contract/src/tests/relayer.rs:26`).
2. Have the wallet owner sign one Ethereum-style transaction (nonce `k`) whose calldata is unparsable and whose `to` address happens to correspond to a Near account ID that is registered in the address registrar (so `TargetKind::EthImplicit(address)` is used and `address_check_callback` will resolve `maybe_account_id.is_some() == true`), with a non-zero `max_fee_per_gas * gas_limit` (`fee > 0`), per the parsing logic in `runtime/near-wallet-contract/implementation/wallet-contract/src/internal.rs:43-77` and `runtime/near-wallet-contract/implementation/wallet-contract/src/internal.rs:107-122`.
3. As the (malicious) relayer, call `rlp_execute(target, tx_bytes_b64)` on `W` (`runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs:89-128`). Observe:
   - `inner_rlp_execute` parses the payload, does **not** advance `nonce` (`lib.rs:358-365`), and unconditionally schedules the fee-refund `Transfer` of `fee` to the relayer (`lib.rs:374-385`).
   - The address-registrar lookup + `address_check_callback` subsequently return `"Invalid target: ..."` and reset `has_in_flight_tx` (`lib.rs:161-173`), with `nonce` still at `k`.
4. Repeat step 3 with the identical `target`/`tx_bytes_b64` any number of times. Each call again passes nonce validation (still `k`), again unconditionally dispatches a `fee` transfer to the relayer, and again fails the registrar check — verify via `view_account` on `W` that its balance decreases by `fee` (plus gas) on every iteration with no bound other than `W`'s remaining balance.

Note: full end-to-end confirmation of the exact registrar contract's `lookup` semantics and the wasm-level test harness could not be independently executed in this analysis (index limits); the logical replay path is established directly from the cited source, but a live sandbox run (as in the existing `wallet-contract` `near-workspaces` test suite, e.g. `runtime/near-wallet-contract/implementation/wallet-contract/src/tests/relayer.rs`) would be needed to fully confirm the observable balance drain end-to-end.

    /// Callback after checking if an address is contained in the registrar.
    /// This check happens when the target is another eth implicit account to
    /// confirm that the relayer really did check for a named account with that address.
    #[private]
    pub fn address_check_callback(
        &mut self,
        target: AccountId,
        action: near_action::Action,
        caller_deposit: Option<CallerDeposit>,
    ) -> PromiseOrValue<ExecuteResponse> {
        self.has_in_flight_tx = false;
        let maybe_account_id: Option<AccountId> = match env::promise_result(0) {
            PromiseResult::Failed => {
                return PromiseOrValue::Value(ExecuteResponse {
                    success: false,
                    success_value: None,
                    error: Some("Call to Address Registrar contract failed".into()),
                });
            }
            PromiseResult::Successful(value) => match serde_json::from_slice(&value) {
                Ok(x) => x,
                Err(_) => {
                    return PromiseOrValue::Value(ExecuteResponse {
                        success: false,
                        success_value: None,
                        error: Some("Unexpected response from account registrar".into()),
                    });
                }
            },
        };
        let current_account_id = env::current_account_id();
        let promise = if maybe_account_id.is_some() {
            // We intentionally do not increment the nonce in this case because the
            // error is caused by a faulty relayer, not the user. An honest relayer
            // may still be able to successfully send the user's intended transaction.
            if env::signer_account_id() == current_account_id {
                create_ban_relayer_promise(current_account_id)
            } else {
                return PromiseOrValue::Value(ExecuteResponse {
                    success: false,
                    success_value: None,
                    error: Some("Invalid target: target is address corresponding to existing named account_id".into()),
                });
            }
        } else {
            // We must increment the nonce at this point to prevent replay of the transaction.
            // Recall that the nonce was not incremented in `inner_rlp_execute` in the case that
            // the registrar contract was called (i.e. in the case we end up inside this callback).
            self.nonce = self.nonce.saturating_add(1);
            let ext =
                WalletContract::ext(current_account_id).with_static_gas(RLP_EXECUTE_CALLBACK_GAS);
            match action_to_promise(target, action)
                .map(|p| p.then(ext.rlp_execute_callback(caller_deposit)))
            {
                Ok(p) => p,
                Err(e) => {
                    return PromiseOrValue::Value(e.into());
                }
            }
        };
        self.has_in_flight_tx = true;
        PromiseOrValue::Promise(promise)
    }
