### Title
Unbounded `GetFileAttributesRequest.Paths` causes synchronous DoS of RPC handler goroutine - (File: internal/gitaly/service/repository/file_attributes.go)

### Summary
`validateGetFileAttributesRequest` only checks that `Paths`, `Attributes`, and `Revision` are non-empty, with no upper bound on the number or total size of `Paths`/`Attributes`. `GetFileAttributes` then iterates every path synchronously against a spawned `git check-attr` subprocess, so an attacker-controlled request can force the handler goroutine into a very long, allocation-heavy loop.

### Finding Description
`validateGetFileAttributesRequest` (internal/gitaly/service/repository/file_attributes.go:44-61) enforces only non-emptiness of `in.GetPaths()`, `in.GetAttributes()`, and `in.GetRevision()` — no maximum count or byte-size limit exists.
`GetFileAttributes` (internal/gitaly/service/repository/file_attributes.go:14-42) then calls `gitattributes.CheckAttr` once (spawning a `git check-attr --stdin -z` subprocess) and loops synchronously over every entry in `in.GetPaths()`, calling `checkAttrCmd.Check(path)` for each one [1](#0-0) . Each `Check` call does a full synchronous write-to-stdin + read-from-stdout round trip with the subprocess and appends results to an in-memory, unbounded-growth `attrValues` slice [2](#0-1) . The number of attributes (`in.GetAttributes()`) is also unbounded and is passed as command-line `Args` to `check-attr`, and the response can accumulate `len(Paths) * len(Attributes)` entries.

Any authenticated user with read access to a repository they control (including their own fork) can invoke `GetFileAttributes` directly and supply arbitrarily large `Paths`/`Attributes` lists. Because this is a unary (non-streaming) RPC, request size is nevertheless bounded by gRPC's default max receive message size (4 MiB, since no explicit `grpc.MaxRecvMsgSize` override was found in `internal/gitaly/server/server_factory.go` or elsewhere in the server setup). Within that 4 MiB budget an attacker can still fit on the order of hundreds of thousands of short path strings (e.g. `"a"`), which is enough to drive the handler through hundreds of thousands of synchronous pipe round-trips to a single `check-attr` subprocess, and to build a correspondingly large response slice.

### Impact Explanation
This causes CPU and memory consumption and elongated latency of a single RPC handler goroutine, scoped to the process running the target repository's Gitaly node. Because subprocess I/O is fully synchronous per path (write, flush, blocking read), a request with a very large `Paths` count will occupy the handler for a long time and materialize a proportionally large response in memory before returning. Repeated concurrent requests of this kind can degrade the whole Gitaly instance (matches GitLab's "Denial of Service" bounty impact class for a single unauthenticated/low-privilege RPC handler), though the practical scale of the attack is capped by gRPC's default 4 MiB message size rather than being literally unbounded ("millions" of paths would not fit in a single unary request without an explicit `MaxRecvMsgSize` increase).

### Likelihood Explanation
Precondition is only read access to any repository, including one the attacker owns or forks — no special privilege is required, and `GetFileAttributes` is reachable directly via gRPC by any authenticated client. The request is trivial to construct and fully repeatable. The only mitigating factor is the default gRPC unary message-size cap, which limits (but does not eliminate) the achievable path count per request; an attacker can still send many such requests in parallel or in sequence.

### Recommendation
Add explicit upper bounds in `validateGetFileAttributesRequest` on `len(in.GetPaths())` and `len(in.GetAttributes())` (and/or total serialized size), rejecting oversized requests with `InvalidArgument` before invoking `check-attr`. Consider also capping per-request processing time/CPU via context deadlines and avoiding unbounded growth of `attrValues` (e.g., streaming the response or capping total AttributeInfo entries).

```go
func TestGetFileAttributes_LargePaths(t *testing.T) {
    ctx := testhelper.Context(t)
    cfg, client := setupRepositoryService(t)
    repoProto, repoPath := gittest.CreateRepository(t, ctx, cfg)

    gittest.WriteCommit(t, cfg, repoPath,
        gittest.WithBranch("main"),
        gittest.WithTreeEntries(
            gittest.TreeEntry{Path: ".gitattributes", Mode: "100644", Content: "* diff=go"},
            gittest.TreeEntry{Path: "a", Mode: "100644", Content: "x"},
        ))

    // Build a request with a very large number of short paths, staying
    // under the default 4MiB unary gRPC message limit.
    paths := make([]string, 500_000)
    for i := range paths {
        paths[i] = "a"
    }

    req := &gitalypb.GetFileAttributesRequest{
        Repository: repoProto,
        Revision:   []byte("main"),
        Attributes: []string{"diff"},
        Paths:      paths,
    }

    start := time.Now()
    resp, err := client.GetFileAttributes(ctx, req)
    elapsed := time.Since(start)

    require.NoError(t, err)
    require.NotNil(t, resp)
    // Assert the handler is not allowed to spend excessive time/memory —
    // this should fail today because no bound exists, demonstrating the gap.
    require.Less(t, elapsed, 200*time.Millisecond, "handler took too long for oversized Paths list")
}
```
Expected today: the test observes handler latency scaling linearly (and non-trivially) with the number of paths, and no validation error is returned regardless of how large `Paths` is — confirming the missing size/count guard in `validateGetFileAttributesRequest`.

```go
func (c CheckAttrCmd) Check(path string) (Attributes, error) {
	if strings.Contains(path, "\000") {
		return nil, fmt.Errorf("path with NUL byte not allowed")
	}

	c.m.Lock()
	defer c.m.Unlock()

	if _, err := c.stdin.WriteString(path + "\000"); err != nil {
		return nil, fmt.Errorf("write path: %w", err)
	}
	if err := c.stdin.Flush(); err != nil {
		return nil, fmt.Errorf("flush: %w", err)
	}

	attrs := Attributes{}
	buf := make([]string, 0, 3)

	// Using git-check-attr(1) with -z will return data in the format:
	// <path> NUL <attribute> NUL <info> NUL ...
	for i := 0; i < c.count; {
		word, err := c.stdout.ReadBytes('\000')
		if err != nil {
			return nil, fmt.Errorf("read line: %w", err)
		}

		buf = append(buf, string(bytes.TrimSuffix(word, []byte{0})))

		if len(buf) < 3 {
			continue // Keep going until we have 3 words
		}

		if buf[0] != path {
			return nil, fmt.Errorf("wrong path name detected, expected %q, got %q", path, buf[0])
		}
		if buf[2] != Unspecified {
			attrs = append(attrs, Attribute{Name: buf[1], State: buf[2]})
		}

		i++
		buf = buf[:0]
	}

	return attrs, nil
}
```
