### Title
Uninitialized `accountIndexOf` fallback lets holders claim rewards equal to their entire token balance - (File: contracts/RewardsDistributor.sol)

### Summary
`RewardsDistributor._calculateTokenDelta` treats `accountIndexOf[token][account] == 0` as "account never checkpointed" and only substitutes `INITIAL_INDEX` when the global index is strictly greater than `INITIAL_INDEX`. While the global index still equals `INITIAL_INDEX` (e.g., the block in which a reward speed is first set, or while accrual has not yet moved the index), the zero account index is used verbatim, producing `_deltaIndex = INITIAL_INDEX` and crediting the account `balance * 1e18` (wadMul ≈ balance) worth of reward tokens. This is the on-chain analog of an out-of-bounds/uninitialized write: attacker-controlled input causes a corrupt value to be written into `tokensAccruedOf`.

### Finding Description
- `tokenStates[token_]` is initialized to `index = INITIAL_INDEX` (1e18) when the governor first sets a positive speed via `_updateTokenSpeed` (`RewardsDistributor.sol:296-299`).
- Any account that minted/received `DepositToken` or `DebtToken` *before* the token was registered has `accountIndexOf[token][account] == 0`, because `updateBeforeMintOrBurn`/`updateBeforeTransfer` no-op while `tokenStates[token_].index == 0` (`RewardsDistributor.sol:175-192`).
- In `_calculateTokenDelta`, the fallback only applies when `_tokenIndex > INITIAL_INDEX` (`RewardsDistributor.sol:225-227`). When `_tokenIndex == INITIAL_INDEX` and `_accountIndex == 0`, `_deltaIndex = 1e18` and `_tokensDelta = balanceOf(account).wadMul(1e18) = balance` (`RewardsDistributor.sol:229-230`).
- `claimRewards` is public and callable for the caller's own account; `_updateTokenIndex` does not advance the index when `block.timestamp == state.timestamp` (same block), so the corrupted delta survives into `_transferRewardIfEnoughTokens`, which pays out up to the distributor's whole reward-token balance (`RewardsDistributor.sol:150-168`, `248-255`).
- The window is wider than one block whenever `speed > 0` but index updates are delayed, and it reopens logically for any account whose index was never written.

### Impact Explanation
An attacker who holds (or held pre-registration) deposit/debt token balance can claim reward tokens equal to their entire token balance — orders of magnitude more than legitimate accrual. With a large pre-existing position (obtainable via a flash-loan-free deposit held ahead of a known governance speed update, or by claiming for many dust accounts), the attacker drains the RewardsDistributor's reward token balance, stealing yield owed to all other users. Broken invariant: reward accrual correctness.

### Likelihood Explanation
Requires: (a) a token whose `tokenStates.index == INITIAL_INDEX` at claim time — guaranteed in the same block as `updateTokenSpeed` registration, and persistent if speed accrual hasn't ticked; (b) the attacker holds balance with `accountIndexOf == 0`, which is automatic for anyone who deposited before registration. No privileged role needed; `claimRewards` is permissionless. Claiming on behalf of others doesn't help since rewards pay the account itself, but the attacker's own pre-positioned balance suffices.

### Recommendation
Change the fallback to apply whenever the stored index is zero and the token is initialized, e.g. `if (_accountIndex == 0 && _tokenIndex >= INITIAL_INDEX) _accountIndex = INITIAL_INDEX;`, or initialize `accountIndexOf` to `INITIAL_INDEX` lazily for all accounts. Alternatively, record `timestamp`/`index` at registration and treat `accountIndexOf == 0` as `INITIAL_INDEX` unconditionally.

### Proof of Concept
Hardhat fork sketch:

```solidity
// Setup: pool, depositToken (msX), rewardsDistributor with rewardToken funded
// 1. Attacker deposits underlying and holds depositToken BEFORE any speed is set
depositTokenUnderlying.approve(address(pool), amount);
pool.deposit(address(depositToken), amount); // accountIndexOf[token][attacker] stays 0

// 2. Governor registers reward speed for depositToken (tokenStates.index = INITIAL_INDEX)
vm.prank(governor);
rewardsDistributor.updateTokenSpeed(IERC20(address(depositToken)), speed);

// 3. Same block (or before index advances): attacker claims
IERC20[] memory t = new IERC20[](1);
t[0] = IERC20(address(depositToken));
rewardsDistributor.claimRewards(attacker, t);

// Assert: attacker received rewardToken ~= depositToken.balanceOf(attacker)
// i.e., deltaIndex = INITIAL_INDEX produced tokensDelta = balance * 1e18 wadMul
assertApproxEqAbs(rewardToken.balanceOf(attacker), depositToken.balanceOf(attacker), 1);
```

Caveat: I could not fully trace `DepositToken`/`DebtToken` hook calls in the remaining iterations; the exploit assumes `updateBeforeMintOrBurn`/`updateBeforeTransfer` are invoked on mint/transfer as documented (`RewardsDistributor.sol:170-184`), which the interface comments confirm.
