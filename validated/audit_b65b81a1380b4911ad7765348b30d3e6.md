### Title
Dust transfers fill the fee collector's token list, permanently DoSing withdrawals and liquidations for any collateral not already in its set - ([File: contracts/Pool.sol, contracts/DepositToken.sol])

### Summary
`Pool.addToDepositTokensOfAccount` enforces a shared cap of `MAX_TOKENS_PER_USER = 30` across deposit + debt tokens per account, and it is invoked unconditionally whenever a `DepositToken` balance of a recipient goes from `0` to nonzero — including recipients that never asked for the tokens. An unprivileged attacker can grief the protocol `feeCollector` by transferring dust amounts (even 1 wei) of 30 distinct deposit tokens to it. Afterwards, any `_transfer`/`_mint` that would add a *new* deposit-token type to the fee collector reverts with `UserReachedMaxTokens`. Because the fee-collector transfer happens inside `DepositToken._withdraw` (fee cut) and inside `Pool.liquidate` (`depositToken_.seize(account_, feeCollector, _fee)`), every withdrawal and every liquidation of a collateral type not already in the fee collector's set reverts.

### Finding Description
- `Pool.onlyIfAdditionWillNotReachMaxTokens` reverts when `debtTokensOfAccount.length + depositTokensOfAccount.length >= 30` [1](#0-0) .
- `DepositToken._transfer` pushes the token onto the *recipient's* list whenever their prior balance was `0`, with no opt-in [2](#0-1) .
- `DepositToken._withdraw` first transfers `_fee` to `pool.feeCollector()`, so the whole withdrawal reverts if adding that token for the collector fails [3](#0-2) .
- `Pool.liquidate` calls `depositToken_.seize(account_, _poolRegistry.feeCollector(), _fee)` whenever the protocol fee is nonzero, so liquidation reverts identically [4](#0-3) .

Attack path (all public, no privilege):
1. Attacker deposits a minimal amount into 30 distinct pool deposit tokens (each `deposit(1 wei, attacker)`), or acquires dust via `transfer`.
2. Attacker calls `depositToken_i.transfer(feeCollector, 1)` for 30 distinct tokens. Each succeeds, filling `depositTokensOfAccount[feeCollector]` to 30.
3. From then on, for any collateral `X` not yet in the fee collector's set: `x.withdraw(...)` reverts (fee transfer would add `X` to a full set) and `pool.liquidate(...)` against `X` reverts at the fee `seize`.
4. If the fee collector contract/EOA ever frees a slot, the attacker re-sends dust in the same block (frontrunning), so the DoS is persistent for as long as the attacker maintains the cap. A brand-new collateral type added by governance can also be permanently kept out of the collector's set in the same way.

### Impact Explanation
- **Temporary/permanent freezing of user funds**: all holders of an affected collateral `X` cannot `withdraw` (the fee transfer reverts before `_burn`), so their underlying collateral is locked in `Treasury` for the duration of the attack.
- **Blocked liquidations → insolvency risk**: positions whose only collateral is `X` cannot be liquidated at all while fees are configured nonzero, allowing bad debt to accrue — a solvency invariant break, not just a liveness nuisance.
- No privileged action, oracle manipulation, or malicious endpoint is required; the attacker only needs dust of each deposit token, obtainable via the public `deposit`.

### Likelihood Explanation
Requires the pool to offer more than 30 deposit tokens (or a newly added collateral type after the collector is capped) and `protocolFee > 0` / `withdrawFee > 0`. The cost is bounded — 30 minimal deposits plus 30 transfers. Modifiers do not stop it: `transfer` only checks the *sender's* unlocked balance via `_revertIfLocked` [5](#0-4) , and the recipient cap check applies to the victim (fee collector), not the attacker.

### Recommendation
- Do not enforce `MAX_TOKENS_PER_USER` on privileged/system recipients such as `feeCollector`, `treasury`, and `address(0)`; e.g., skip `addToDepositTokensOfAccount` (and the revert) for the fee collector in `DepositToken._transfer`/`_mint`, or exempt that address in `Pool.addToDepositTokensOfAccount`.
- Alternatively, make fee collection a `mint`/`seize` path that tolerates the cap, or accumulate fees per-token and let the collector claim them on demand.
- As defense-in-depth, track a per-account boolean whitelist instead of reverting the entire transfer when the cap is hit (i.e., skip list insertion but still allow the balance change), since the list is only an enumeration convenience for `depositOf`/`debtOf` and `debtPositionOf` — though for the fee collector that trade-off must be evaluated since skipping insertion would exclude its balance from `depositOf`.

### Proof of Concept
```solidity
// test/foundry/poc/FeeCollectorGrief.t.sol — Foundry fork PoC (sketch)
function test_FeeCollectorCapBlocksWithdrawAndLiquidate() public {
    // pool, treasury, feeProvider with protocolFee/withdrawFee > 0, >=31 deposit tokens
    address feeCollector = poolRegistry.feeCollector();

    // 1) Attacker deposits dust into 30 deposit tokens and transfers 1 wei each
    for (uint i; i < 30; ++i) {
        IDepositToken dt = depositTokens[i];
        deal(address(dt.underlying()), attacker, 1);
        vm.startPrank(attacker);
        dt.underlying().approve(address(dt), 1);
        dt.deposit(1, attacker);            // mints dust to attacker
        dt.transfer(feeCollector, 1);       // adds dt to collector's set
        vm.stopPrank();
    }
    assertEq(pool.getDepositTokensOfAccount(feeCollector).length, 30);

    // 2) depositToken[30] (never sent to collector) now DoSes:
    IDepositToken x = depositTokens[30];
    vm.expectRevert(Pool.UserReachedMaxTokens.selector);
    victim.withdraw(amount, victim);        // reverts at fee _transfer to collector

    // 3) liquidation of a position collateralized only in x also reverts
    vm.expectRevert(Pool.UserReachedMaxTokens.selector);
    liquidator.liquidate(synth, victim, repayAmt, x); // reverts at fee seize
}
```
The revert propagates from `pool.addToDepositTokensOfAccount(feeCollector)` inside `DepositToken._transfer`/`seize`, confirmed by `onlyIfAdditionWillNotReachMaxTokens` reverting at count ≥ 30.
