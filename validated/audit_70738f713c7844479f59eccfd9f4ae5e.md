### Title
QUIC stream-throttle token bucket resets to full capacity on reconnect, enabling per-peer QoS evasion - (File: streamer/src/nonblocking/quic.rs, streamer/src/nonblocking/simple_qos.rs)

### Summary
The `SimpleQos` (stake-weighted single-connection QoS) stream rate limiter state (`TokenBucket`) is keyed to the connection-table entry for a peer, not to a value that persists independently of connection lifetime. Because `ConnectionTable::remove_connection` deletes the map entry once its connection list becomes empty [1](#0-0) , and `try_add_connection` only reuses an existing `stream_counter` if one is already present in the (non-empty) entry, otherwise constructing a brand-new one via the caller-supplied factory [2](#0-1) , a staked peer can trivially reset its own per-connection stream quota to full by disconnecting and reconnecting.

### Finding Description
In `SimpleQos::cache_new_connection`, the per-connection `TokenBucket` is created with `initial_tokens = max_streams_per_second` — i.e. fully charged at creation, not empty [3](#0-2) . This bucket is intended to bound how many QUIC uni-streams (transactions) a peer can push per second. However, its lifetime is tied 1:1 to the connection-table entry for that peer's key (IP or pubkey), and that entry is deleted as soon as the peer's last connection closes [4](#0-3) . When the peer reconnects, `try_add_connection` sees an empty/absent entry and mints a brand-new, fully-topped-off bucket rather than continuing to draw down the old one [2](#0-1) .

This is directly analogous to the report's bug class: a cheap, repeatable, permissionless action (open/close a connection, analogous to deposit/withdraw liquidity) resets state that is supposed to accrue a cost/limit over time, letting an attacker "mint" far more of a bounded resource (here, allowed stream/transaction throughput) than the QoS budget intends, at near-zero cost.

### Impact Explanation
An attacker with even minimal stake can repeatedly close and reopen a QUIC connection to the TPU to keep resetting their stream-throttle token bucket to full capacity, sending bursts of `max_streams_per_second` transactions each time instead of being smoothly rate-limited to that steady-state rate. This lets a single peer push a disproportionate share of transactions into the streamer/sigverify/banking pipeline relative to their stake, defeating the purpose of stake-weighted QoS and potentially crowding out well-behaved peers' streams — a QoS evasion. The severity is bounded by the outer connection-rate limiters (`ConnectionRateLimiter`, `overall_connection_rate_limiter`, and `max_connections_per_ipaddr_per_min`) [5](#0-4) , which cap how frequently a given IP can establish new connections, somewhat limiting exploitation frequency, but the per-peer/pubkey stream-quota model is still effectively bypassable rather than smoothly enforced over time.

### Likelihood Explanation
Reconnecting is a cheap, unprivileged client-side operation requiring no special stake beyond whatever minimum is needed to be treated as staked, and no protocol-level cost is charged for it. The exploit only requires disconnect/reconnect cycles staying under the outer connection-rate limiter's burst allowance (10x `max_connections_per_ipaddr_per_min`, default burst up to 80) [5](#0-4) , which is plausible to abuse periodically rather than continuously.

### Recommendation
Persist the per-peer stream-rate-limiting state independently of the connection-table entry lifetime (e.g., keep a separate keyed store of `TokenBucket`s per pubkey/IP that survives connection close, similar to the `KeyedRateLimiter` pattern already used for `ConnectionRateLimiter`), rather than deriving it solely from `connection_entry.first()` in `ConnectionTable::try_add_connection`. Alternatively, only reset the bucket after a minimum idle/cooldown period since the peer's last connection closed.

### Proof of Concept
Not independently executable from this review (no test harness run); the logical PoC is: (1) a staked peer opens a QUIC connection and consumes its full `max_streams_per_second` token allotment; (2) peer disconnects (calling `SwQos`/`SimpleQos::remove_connection`, which empties the connection-table entry and triggers `swap_remove_entry`) [1](#0-0) ; (3) peer immediately reconnects; `try_add_connection` finds no existing entry and calls the `stream_counter_factory`, producing a token bucket initialized at full capacity again [6](#0-5) ; (4) peer bursts another full `max_streams_per_second` streams immediately, well above the intended sustained per-second rate.

    pub(crate) fn remove_connection(
        &mut self,
        key: ConnectionTableKey,
        port: u16,
        stable_id: usize,
    ) -> usize {
        if let Entry::Occupied(mut e) = self.table.entry(key) {
            let e_ref = e.get_mut();
            let old_size = e_ref.len();

            e_ref.retain(|connection_entry| {
                // Retain the connection entry if the port is different, or if the connection's
                // stable_id doesn't match the provided stable_id.
                // (Some unit tests do not fill in a valid connection in the table. To support that,
                // if the connection is none, the stable_id check is ignored. i.e. if the port matches,
                // the connection gets removed)
                connection_entry.port != port
                    || connection_entry
                        .connection
                        .as_ref()
                        .and_then(|connection| (connection.stable_id() != stable_id).then_some(0))
                        .is_some()
            });
            let new_size = e_ref.len();
            if e_ref.is_empty() {
                e.swap_remove_entry();
            }
            let connections_removed = old_size.saturating_sub(new_size);
            self.total_size = self.total_size.saturating_sub(connections_removed);
            connections_removed
        } else {
            0
        }
    }
