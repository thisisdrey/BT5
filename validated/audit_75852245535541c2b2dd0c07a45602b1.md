### Title
Cache-coherency TOCTOU race in `SnapshotRoot` allows stale/deleted account or contract state to be served after concurrent delete - (File: `chainbase/src/main/java/org/tron/core/db2/core/SnapshotRoot.java`)

### Summary
`SnapshotRoot` is the root, DB-backed layer of every `TronStoreWithRevoking`-based store (e.g. `AccountStore`, `ContractStore`, `CodeStore`, `AccountAssetStore`) and, for the DB names listed in `getCacheDbs()`, is fronted by a shared, globally-reachable `TronCache` (Guava `Cache`) instance obtained from `CacheManager.allocate(...)`. Its `get`/`put`/`remove` methods perform a classic check-then-act sequence against this cache without any synchronization guaranteeing ordering between the underlying store mutation and the cache write, which is architecturally the same bug class as the reported `cls_route` fastmap issue: a reader can repopulate a shared cache with a value that a concurrent writer has just invalidated, so subsequent lookups return stale data even though the authoritative store has already been changed/deleted.

### Finding Description
`SnapshotRoot.get()`:
```java
public byte[] get(byte[] key) {
  WrappedByteArray cache = getCache(key);
  if (cache != null) { return cache.getBytes(); }
  byte[] value = db.get(key);
  putCache(key, value);
  return value;
}
``` [1](#0-0) 

and `SnapshotRoot.remove()`:
```java
public void remove(byte[] key) {
  if (needOptAsset()) { ... }
  db.remove(key);
  putCache(key, null);
}
``` [2](#0-1) 

There is no lock coupling the `db.get`/`db.remove` step to the `putCache` step, and no per-key "in-flight deletion" marker (the analog of the kernel's proposed `dying` flag). This reproduces the same race shape as CVE-2026-74583:

1. Thread A (e.g. block-application/flush thread, via `merge`/`remove` when a store entry is deleted — e.g. an account self-destructs, a contract is removed, an asset-issue record is deleted) calls `remove(key)`: `db.remove(key)` executes, but `putCache(key, null)` has not yet run.
2. Thread B (a concurrent reader — e.g. an HTTP/gRPC/JSON-RPC request thread calling into `Wallet`/`TronJsonRpcImpl`, which reads through `AccountStore`/`ContractStore` down to this same shared `SnapshotRoot`) calls `get(key)`: cache miss, so it reads `db.get(key)`. If this executes before A's `db.remove(key)` (or reads a still-stale on-disk value depending on timing), it obtains the old value.
3. Thread B then executes `putCache(key, value)` (or thread A's `putCache(key, null)` executes first and B's stale write lands after it), so the shared cache ends up holding the pre-deletion value even though the store has already recorded the deletion.
4. Every subsequent `get(key)` call — including calls made from the transaction-execution path (`RepositoryImpl` → `AccountStore`/`ContractStore` → revoking DB chain → `SnapshotRoot`) and from the public query APIs (`Wallet`, `TronJsonRpcImpl`) — now returns the stale, already-deleted value from the cache instead of the correct (deleted/updated) state, until the cache entry happens to be evicted or overwritten.

This is architecturally identical to the reported bug: a shared cache keyed by an identifier, populated by readers walking the "real" store, and invalidated by a writer via a bare "reset" write — with no mechanism to suppress a reader's stale republish that races the writer's invalidation.

The affected stores are exactly those enumerated in the storage configuration's cache DB list, consumed via `CACHE_DBS = CommonParameter.getInstance().getStorage().getCacheDbs()` and gated by `CacheType.findByType(...)`, which per the constructor includes account-related data (`isAccountDB` check) among others. [3](#0-2) 

### Impact Explanation
If a stale (pre-deletion) account or contract snapshot is served from this shared cache:
- Read-side impact: `Wallet`/`TronJsonRpcImpl` and other query paths can report an incorrect/unbacked balance or contract existence for an address whose state was actually deleted (e.g., after a `suicide`/self-destruct via a TVM contract execution, or an asset-issue/contract removal), misleading any client or downstream service relying on the RPC/API result — an "unbacked balance" / stale-state exposure class of issue.
- Write-side risk: because `AccountStore`/`ContractStore` (and other `TronStoreWithRevoking` implementations) resolve down to this same `SnapshotRoot` instance when a key is absent from in-memory snapshot layers, any actuator or `RepositoryImpl` read that happens to race with a concurrent flush/removal at this root layer could also observe the stale entry, potentially feeding incorrect account/contract state into transaction validation/execution logic.

This satisfies the "unbacked balance" / incorrect-state class of impact called out in the validation rules, reachable purely via ordinary API read requests racing with normal chain state deletions (self-destruct, contract/asset cleanup) — no privileged access, malicious SR, or p2p component required.

### Likelihood Explanation
Likelihood is Medium-High to trigger the race window in principle (any concurrent read while a delete/flush is in flight on the same key), but I was not able to fully confirm within available tool budget:
- Whether `SnapshotRoot.remove()`/`merge()` on the account/contract DBs is actually invoked concurrently with API read threads in this codebase's threading model, i.e., whether `Wallet.getAccount()` bypasses the `Manager`'s `synchronized(this)` block used during `pushBlock`/`applyBlock`, and whether flush-to-root (`SnapshotManager`/`Chainbase` merge into `SnapshotRoot`) runs on a separate thread from block application.
- I confirmed `pushBlock` executes under `synchronized(this)` on `Manager`, but read paths through `Wallet`/`TronJsonRpcImpl` calling directly into `AccountStore.get()` do not appear to acquire this same lock, which is the structural precondition for the race, though I could not fully trace the flush/merge call chain to `SnapshotRoot` under the remaining iteration budget.

Given this uncertainty, this should be treated as a plausible but not fully proven concurrency bug requiring further investigation.

### Recommendation
- Serialize the "check store / write cache" sequence in `SnapshotRoot.get()`, `put()`, `remove()` and `merge()` under a per-key or per-store lock (or use a cache implementation that supports atomic "invalidate-then-load-guard" semantics), so a delete cannot be raced by a stale re-populate.
- Alternatively, introduce a generation/version counter or "tombstone" marker per key (the direct analog of the kernel fix's `dying` flag) so that any in-flight `get()` load started before a `remove()`/`merge()` cannot overwrite the newer tombstone/value once the writer completes.
- Audit all call sites that reach `SnapshotRoot` (`AccountStore`, `ContractStore`, `AccountAssetStore`, etc.) to confirm which are exercised by unsynchronized reader threads (Wallet/gRPC/HTTP/JSON-RPC) concurrently with block-application/flush writers, and add the necessary locking at the `TronStoreWithRevoking`/`Chainbase` layer if confirmed.

### Proof of Concept
Conceptual reproduction (mirrors the kernel PoC's "accelerator + concurrent add/delete stress test" approach):
1. Insert an artificial delay between `db.remove(key)` and `putCache(key, null)` in `SnapshotRoot.remove()` (as the kernel report did with `mdelay(100)` in `route4_set_fastmap()`).
2. From one thread, delete an account/contract entry that is backed by a cache-enabled DB (triggering `remove()`/`merge()` on `SnapshotRoot`).
3. From a concurrent thread, immediately call the corresponding `Wallet`/`TronJsonRpcImpl` query (e.g., `getAccount`) for the same address during the delay window.
4. Observe that the cache is repopulated with the pre-deletion value, and subsequent queries via the same API return the deleted account's stale data even though the underlying RocksDB/LevelDB store no longer has the record.

public class SnapshotRoot extends AbstractSnapshot<byte[], byte[]> {

  @Getter
  private Snapshot solidity;
  private boolean isAccountDB;

  private TronCache<WrappedByteArray, WrappedByteArray> cache;
  private static final List<String> CACHE_DBS = CommonParameter.getInstance()
      .getStorage().getCacheDbs();

  public SnapshotRoot(DB<byte[], byte[]> db) {
    this.db = db;
    solidity = this;
    isAccountDB = "account".equalsIgnoreCase(db.getDbName());
    if (CACHE_DBS.contains(this.db.getDbName())) {
      this.cache = CacheManager.allocate(CacheType.findByType(this.db.getDbName()));
    }
    isOptimized = "properties".equalsIgnoreCase(db.getDbName());
  }
