Based on the investigation of the `TransferToNewAccount`/`TransferToNewAccountPda` instructions in this codebase, I found a concrete structural analog of the AddressWhitelist bug class: a security state that is supposed to lock an account out of normal operations is not re-checked at the exact point where account migration happens, allowing the restricted state to be silently discarded.

### Title
Forced-deleverage lockout is not enforced by `transfer_to_new_account`/`transfer_to_new_account_pda`, allowing an unhealthy account's authority to escape an in-progress risk-admin deleverage - (File: `programs/marginfi/src/instructions/marginfi_account/transfer_account.rs`)

### Summary
`transfer_to_new_account` and `transfer_to_new_account_pda` explicitly re-check a whitelist of "locked" account flags before allowing migration (`ACCOUNT_IN_FLASHLOAN`, `ACCOUNT_IN_RECEIVERSHIP`, `ACCOUNT_IN_ORDER_EXECUTION`, plus `active_orders == 0` and `migrated_to == default`), but omits `ACCOUNT_IN_DELEVERAGE`, the flag set when the risk admin has begun a forced-deleverage liquidation on the account.

### Finding Description
The `TransferToNewAccount`/`TransferToNewAccountPda` account-validation constraint only blocks the transfer when the account is frozen (`account_not_frozen_for_authority`) and requires the caller be an authorized signer (`is_signer_authorized`) [1](#0-0) . Inside the instruction body, an explicit set of additional state checks are performed against `old_account`'s flags before allowing the migration to proceed: flashloan, receivership, and order-execution locks, plus a "no active orders" and "not already migrated" check [2](#0-1) . The identical set of checks is duplicated in `transfer_to_new_account_pda` [3](#0-2) .

Per the project's own documentation, `ACCOUNT_IN_DELEVERAGE` (bit 5) is described as "similar to receivership, but specifically for forced deleverage scenarios where the risk admin is unwinding positions" [4](#0-3) . Unlike receivership (where control shifts to `liquidation_receiver` and any signer is authorized only for allowed operations), deleverage does not appear to strip the original authority's signing rights or set the frozen flag — nothing in `transfer_account.rs` checks for `ACCOUNT_IN_DELEVERAGE`.

This mirrors the AddressWhitelist bug class: a protective invariant (an address/account being restricted — whitelist membership tied to the owner address in the original report; a deleverage lock tied to the account here) is enforced in one code path (deposit/withdraw/borrow/repay, which do check the flag per the flag list in `finalize_migrated_old_account`/checks above) but is bypassable via a side-door state transition (ownership transfer in the original bug; account migration here) that the developers apparently did not intend to be exempt from the restriction.

`finalize_migrated_old_account` then zeroes the old account's `lending_account` and marks it `ACCOUNT_DISABLED` [5](#0-4) , meaning if this transfer succeeds while a forced deleverage is mid-flight, the old account's position data referenced by the risk admin's in-progress deleverage instructions is wiped and the position is moved intact to a brand-new account that carries no `ACCOUNT_IN_DELEVERAGE` flag.

### Impact Explanation
If confirmed exploitable (i.e., if `is_signer_authorized` does not separately reject a normal-authority signature while `ACCOUNT_IN_DELEVERAGE` is set — a detail I was not able to fully verify from the available `is_signer_authorized` source before running out of investigation budget), this would let the authority of an unhealthy account under active forced deleverage unilaterally migrate all balances to a fresh, unflagged account mid-liquidation, evading the risk admin's unwind and potentially leaving the protocol with unresolved bad debt or an inconsistent liquidation state (the old account is zeroed/disabled underneath the in-flight deleverage instruction).

### Likelihood Explanation
Low-to-moderate: it requires a permissionless-but-precisely-timed race — the account authority must submit `TransferToNewAccount`/`TransferToNewAccountPda` after the risk admin sets `ACCOUNT_IN_DELEVERAGE` but before the admin's deleverage instructions complete against that same account. This is plausible since setting the flag and taking action on it are typically separate transactions.

### Recommendation
Add an explicit `check!(!old_account.get_flag(ACCOUNT_IN_DELEVERAGE), MarginfiError::ForbiddenIx)` to both `transfer_to_new_account` and `transfer_to_new_account_pda`, consistent with the existing flashloan/receivership/order-execution checks, so an in-progress forced deleverage cannot be evaded via account migration.

### Proof of Concept
Not able to be conclusively demonstrated from static review alone: this requires confirming, via `is_signer_authorized`'s full implementation (which I could not fully retrieve in the available iterations), whether the normal account authority retains signing rights while `ACCOUNT_IN_DELEVERAGE` is set. If it does, the following sequence would demonstrate the issue:
1. Risk admin calls `StartLiquidation` in deleverage mode on a user's unhealthy account, setting `ACCOUNT_IN_DELEVERAGE`.
2. Before the risk admin completes the unwind, the account authority calls `transfer_to_new_account` (or the PDA variant) — none of the explicit checks in `transfer_account.rs` reference `ACCOUNT_IN_DELEVERAGE`, so the transaction should succeed if `is_signer_authorized` still permits the authority to sign.
3. The old account's `lending_account` is zeroed and marked `ACCOUNT_DISABLED`; the position is now on a new account with no deleverage flag, leaving the admin's pending deleverage instructions to fail or operate against stale/emptied state.

I was unable to fully verify step 2's precondition (whether `is_signer_authorized` blocks the authority during deleverage) within the available investigation scope — starting a Devin session with terminal/code access would allow tracing `is_signer_authorized`'s full body and writing an integration test to confirm or refute exploitability.

```rust
fn finalize_migrated_old_account(
    old_account: &mut MarginfiAccount,
    new_account_key: Pubkey,
    current_timestamp: u64,
) {
    old_account.migrated_to = new_account_key;
    old_account.last_update = current_timestamp;
    old_account.lending_account = LendingAccount::zeroed();
    old_account.set_flag(ACCOUNT_DISABLED, true);
    old_account.sync_indexer_flags();
}
```
