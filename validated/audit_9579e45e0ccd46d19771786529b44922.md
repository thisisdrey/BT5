### Title
`submit_delivery_receipt` pays the full relayer fee regardless of message delivery outcome - (File: `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs`)

### Summary
The Snowbridge V2 outbound queue rewards relayers for submitting a delivery receipt based purely on the existence of a `PendingOrder` for the nonce, never checking the `success` field of the decoded `DeliveryReceipt`. This mirrors the `gib()` pattern from the external report: a state-changing payout path releases the full pre-committed value ("safe") unconditionally, without verifying the invariant (here: that the message was actually executed successfully on Ethereum) that is supposed to gate the payment.

### Finding Description
`process_delivery_receipt` decodes an Ethereum `InboundMessageDispatched` event into a `DeliveryReceipt` that explicitly carries a `success: bool` field: [1](#0-0) 

The dispatchable `submit_delivery_receipt` verifies only that the event log is included in a valid Ethereum receipt (i.e. that the event genuinely happened), then forwards the decoded receipt straight into `process_delivery_receipt`: [2](#0-1) 

`process_delivery_receipt` then looks up the `PendingOrder` by nonce and, if `order.fee > 0`, unconditionally calls `T::RewardPayment::register_reward` for the full fee, before removing the order — the `receipt.success` value is never read or checked anywhere in this function: [3](#0-2) 

The module doc explicitly states the intended flow is "When the message has been verified **and executed**... fetch the pending order... pay reward", implying reward should be conditioned on successful execution: [4](#0-3) 

Because the on-chain logic ignores `success`, any account that relays a message and can obtain (or cause) a real Ethereum log with `success = false` — for example a relayer who deliberately supplies insufficient gas or triggers a revertible failure path on the destination command execution — still walks away with `order.fee` credited via `register_reward`, and the corresponding `PendingOrder` is removed from `PendingOrders`, closing the book on that nonce as if delivery had succeeded. This is a public, unprivileged entry point (`ensure_signed` only — no relayer allowlist), so no admin, governance, or validator/collator privilege is required to trigger it.

### Impact Explanation
This breaks the "message queues, bridge markers, receipts, and payout state must only advance after decode, dispatch, execution, and settlement succeed atomically" invariant. A relayer can be paid the full committed fee for messages that failed to execute on Ethereum, causing the reward pot (funded by users' message fees) to be drained for work that was not actually completed, and permanently discards the pending order (so there is no path to retry or reconcile a failed delivery). This is a value-conservation/duplicate-settlement-class bug: the fee is settled to the relayer without the corresponding successful delivery ever having occurred.

### Likelihood Explanation
Likelihood is moderate-to-high: `submit_delivery_receipt` is a completely public, permissionless extrinsic, and the exploiting party only needs a genuine (verifiable) `InboundMessageDispatched` event with `success = false`, which is a normal outcome any relayer can encounter or potentially induce (e.g., by controlling gas parameters or targeting failure-prone commands) without colluding with governance, validators, or the bridge operator.

### Recommendation
Check `receipt.success` in `process_delivery_receipt` before crediting the reward. On `success == false`, either withhold/reduce the reward, or route the order to a distinct failure-handling path (e.g. re-queue for retry, or only refund the base delivery cost rather than the full fee), rather than paying the full fee and silently removing the order as if delivery succeeded.

### Proof of Concept
1. A message is enqueued via `do_process_message`, creating `PendingOrders[nonce] = { fee, block_number }`.
2. On Ethereum, the corresponding command execution reverts/fails, so the Gateway contract emits `InboundMessageDispatched(nonce, topic, success=false, reward_address)`.
3. Any account (attacker or complicit relayer) submits `submit_delivery_receipt` with a valid Merkle/receipt proof for this real (but `success=false`) event.
4. `T::Verifier::verify` succeeds (the event genuinely occurred), `DeliveryReceipt::try_from` decodes `success = false`, but `process_delivery_receipt` never inspects it.
5. `order.fee > 0` still triggers `T::RewardPayment::register_reward(&reward_account, ..., order.fee)`, and `PendingOrders::remove(nonce)` deletes the order — the relayer is fully paid despite the failed delivery. [5](#0-4)

		/// Process a delivery receipt from a relayer, to allocate the relayer reward.
		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}
