### Title
Unchecked binary offsets/lengths in reftable parser cause out-of-bounds panics on attacker-influenced reftable data - (File: internal/git/reftable/reftable.go)

### Summary
`internal/git/reftable/reftable.go` parses the binary `.ref` reftable format byte-by-byte using raw, unchecked slice arithmetic. Several fields taken from the reftable block header (block length, restart count, varint-encoded prefix/suffix lengths) are used directly to compute slice offsets without validating them against the length of the in-memory buffer, mirroring the Firedancer pattern of trusting an untrusted length/offset field (`shred34->offset`/`shred_sz`) from one component and using it to index memory in a downstream parser (`fd_ext_blockstore_insert_shreds`).

### Finding Description
The reftable parser performs multiple unchecked memory accesses derived from file-controlled integers:

- `extractBlockLen` reads `src[blockStart+1:blockStart+4]` with no bound check against `len(src)`. [1](#0-0) 

- `getVarInt` dereferences `src[start]` before any bounds check, and only checks `start > blockEnd` after incrementing — it never checks against `len(src)`, so a crafted `blockEnd` value larger than the buffer (which is itself derived from unchecked arithmetic, see below) lets the loop walk off the end of the slice. [2](#0-1) 

- `parseRefBlock` computes `b.RestartStart = blockStart + currentBS - 2 - 3*uint(b.RestartCount)` using unsigned (`uint`) arithmetic. If `currentBS` (from `extractBlockLen`, attacker/file controlled) or `RestartCount` (read directly from file bytes via `binary.Read`) are inconsistent, this subtraction underflows to a huge value, producing a `RestartStart` far outside the buffer. [3](#0-2) 

- `getRefsFromBlock` then loops `for idx < b.RestartStart` and repeatedly slices `src[idx:idx+suffixLength]`, `prefix[:prefixLength]`, and `src[idx:idx+hashSize]` using lengths taken straight from the file (varint-decoded `prefixLength`/`suffixLength`, or fixed hash sizes) without ever checking against `len(src)` or `len(prefix)`. Any inconsistency between the encoded lengths and the actual buffer/prefix size triggers a Go runtime "slice bounds out of range" panic. [4](#0-3) 

This is the same bug class as the reported issue: a struct/record read from a binary blob is only partially validated (`FD_TEST` checks on `shred_sz`/`stride`/`shred_cnt`) while other length/offset fields inside it (the packet contents) are trusted and used to index a buffer in a downstream consumer, causing a crash.

### Impact Explanation
`Table.GetReferences()` and the surrounding parsing helpers are used by Gitaly's own reftable backend support (`internal/gitaly/storage/storagemgr/partition/reftable.go`, `transaction_manager.go`, `transaction_manager_housekeeping.go`) when a repository uses the `reftable` reference backend, i.e. as part of transaction application/verification and pack-refs housekeeping that Gitaly runs on ordinary write transactions. A `.ref` file with an inconsistent block header (mismatched `currentBS`, `RestartCount`, or varint length fields) causes an unrecovered Go panic in this code path. Because this is invoked from the transaction manager / housekeeping machinery rather than strictly inside a single gRPC handler wrapped by `panichandler`, such a panic can crash the goroutine/partition worker handling that repository's writes, denying service to that repository's storage partition (DoS), rather than being cleanly converted to a gRPC `Internal` error the way handler-level panics are. [5](#0-4) 

### Likelihood Explanation
Reaching this bug requires a `.ref` reftable file on disk whose block header/restart data is inconsistent with its declared block/table boundaries. Under normal operation, such files are only ever produced by Git itself, which is expected to write self-consistent reftables, so this is not directly reachable purely from ref names/OIDs supplied over a standard `git push`. It becomes concretely reachable when reftable files reach a Gitaly storage from a less-trusted origin — e.g. repository import/restore, replication of a reftable-backend repository from another host, or corruption/version-skew between Git and Gitaly's own reftable reader — after which routine housekeeping or transaction processing on that repository (triggered by ordinary subsequent writes) will invoke the vulnerable parser. This is a more indirect trigger than the Firedancer PoC (direct in-process memory tampering), so likelihood is assessed as lower/moderate rather than trivially exploitable by any anonymous pusher.

### Recommendation
Harden `internal/git/reftable/reftable.go` to treat all reftable-derived integers as untrusted:
- Bound-check `blockStart+4 <= len(src)` in `extractBlockLen` before slicing.
- In `getVarInt`, check `start < len(src)` (not just `blockEnd`) before every `src[start]` access, and validate `blockEnd <= len(src)`.
- In `parseRefBlock`, validate `currentBS >= 2 + 3*uint(RestartCount)` before computing `RestartStart`, and validate `RestartStart <= FullBlockSize`/`blockEnd` and is monotonic with `BlockStart`.
- In `getRefsFromBlock`, validate `prefixLength <= len(prefix)`, `idx+suffixLength <= len(src)` (and similarly for hash-size and symref-size reads) before slicing, returning a parse error instead of panicking.
- Add fuzz/unit tests feeding malformed reftable block headers (bad `RestartCount`, oversized varints, truncated buffers) to confirm the parser now returns errors instead of panicking, similar to the existing bounds-checked patterns already used in `internal/git/mvcc/manifest.go` and `internal/git/packfile/bitmap.go`.

### Proof of Concept
Conceptual PoC (not executed): construct a minimal reftable file with a valid header/footer/CRC but a ref block whose `block_len` byte and 2-byte restart-count trailer are set such that `currentBS - 2 - 3*RestartCount` underflows (e.g. `currentBS = 4`, `RestartCount = 10`), or whose varint-encoded `suffix_length` exceeds the remaining bytes in the block. Feed this file to `reftable.ParseTable` followed by `Table.GetReferences()`; the underflowed `RestartStart`/oversized `suffixLength` causes a `slice bounds out of range` panic inside `getRefsFromBlock`/`getVarInt` rather than a handled parse error, matching the same class of crash demonstrated in the original report where unchecked `fec_set_idx`/`size`/`parent_off` fields inside `fd_shred34_t.pkts[]` crashed `fd_ext_blockstore_insert_shreds`. Verifying the exact reachability path (import/replication vs. WAL replay) and exploit reliability requires running Gitaly's reftable backend directly, which is outside the scope of this read-only analysis.

// getVarInt parses a variable int and increases the index.
func (t *Table) getVarInt(src []byte, start uint, blockEnd uint) (uint, uint, error) {
	var val uint

	val = uint(src[start]) & 0x7f

	for (uint(src[start]) & 0x80) > 0 {
		start++
		if start > blockEnd {
			return 0, 0, fmt.Errorf("exceeded block length")
		}

		val = ((val + 1) << 7) | (uint(src[start]) & 0x7f)
	}

	return start + 1, val, nil
}

func (t *Table) getRefsFromBlock(src []byte, b *block) ([]git.Reference, error) {
	var references []git.Reference

	prefix := ""

	// Skip the block_type and block_len
	idx := b.BlockStart + 4

	for idx < b.RestartStart {
		var prefixLength, suffixLength, updateIndexDelta uint
		var err error

		idx, prefixLength, err = t.getVarInt(src, idx, b.RestartStart)
		if err != nil {
			return nil, fmt.Errorf("getting prefix length: %w", err)
		}

		idx, suffixLength, err = t.getVarInt(src, idx, b.RestartStart)
		if err != nil {
			return nil, fmt.Errorf("getting suffix length: %w", err)
		}

		extra := (suffixLength & 0x7)
		suffixLength >>= 3

		refname := prefix[:prefixLength] + string(src[idx:idx+suffixLength])
		idx = idx + suffixLength

		idx, updateIndexDelta, err = t.getVarInt(src, idx, b.FullBlockSize)
		if err != nil {
			return nil, fmt.Errorf("getting update index delta: %w", err)
		}
		// we don't use this for now
		_ = updateIndexDelta

		reference := git.Reference{
			Name: git.ReferenceName(refname),
		}

		switch extra {
		case 0:
			// Deletion, no value
			reference.Target = t.shaFormat().ZeroOID.String()
		case 1:
			// Regular reference
			hashSize := t.shaFormat().Hash().Size()
			reference.Target = git.ObjectID(hex.EncodeToString(src[idx : idx+uint(hashSize)])).String()

			idx += uint(hashSize)
		case 2:
			// Peeled Tag
			hashSize := t.shaFormat().Hash().Size()
			reference.Target = git.ObjectID(hex.EncodeToString(src[idx : idx+uint(hashSize)])).String()

			idx += uint(hashSize)

			// For now we don't need the peeledOID, but we still need
			// to skip the index.
			// peeledOID := ObjectID(bytesToHex(t.src[idx : idx+uint(hashSize)]))
			idx += uint(hashSize)
		case 3:
			// Symref
			var size uint
			idx, size, err = t.getVarInt(src, idx, b.FullBlockSize)
			if err != nil {
				return nil, fmt.Errorf("getting symref size: %w", err)
			}

			reference.Target = git.ReferenceName(src[idx : idx+size]).String()
			reference.IsSymbolic = true
			idx = idx + size
		}

		prefix = refname

		references = append(references, reference)
	}

// parseRefBlock parses a block and if it is a ref block, provides
// all the reference updates.
func (t *Table) parseRefBlock(src []byte, headerOffset, blockStart, blockEnd uint) ([]git.Reference, error) {
	currentBS := t.extractBlockLen(src, blockStart+headerOffset)

	fullBlockSize := t.blockSize
	if fullBlockSize == 0 {
		fullBlockSize = currentBS
	} else if currentBS < fullBlockSize && currentBS < (blockEnd-blockStart) && src[blockStart+currentBS] != 0 {
		fullBlockSize = currentBS
	}

	b := &block{
		BlockStart:    blockStart + headerOffset,
		FullBlockSize: fullBlockSize,
	}

	if err := binary.Read(bytes.NewBuffer(src[blockStart+currentBS-2:]), binary.BigEndian, &b.RestartCount); err != nil {
		return nil, fmt.Errorf("reading restart count: %w", err)
	}

	b.RestartStart = blockStart + currentBS - 2 - 3*uint(b.RestartCount)

	return t.getRefsFromBlock(src, b)
}
