### Title
Missing staleness/freshness validation of peer-supplied handshake `Time` field enables acceptance of arbitrarily old replayed handshake packets - (File: `handshake_manager.go`)

### Summary
The Nebula handshake protocol embeds a peer-controlled `Time` field in the handshake payload (`handshake/payload.go`), which is carried into `HostInfo.lastHandshakeTime` and documented as an anti-replay mechanism. However, no code path ever compares this value against the local wall-clock (`time.Now()`) to reject a handshake as stale. The only check performed, in `HandshakeManager.CheckAndComplete()`, is a *relative* comparison against whatever `lastHandshakeTime` an already-existing `HostInfo` happens to hold — the exact "missing staleness validation" bug class described in the external report, where a fetched/attacker-influenced timestamp is used without bounding it against current time.

### Finding Description
`handshake/machine.go`'s `processPayload()` extracts `payload.Time` straight into `m.result.HandshakeTime` with no bounds checking at all: `m.result.HandshakeTime = payload.Time` [4](#0-3)  — this value is fully attacker-controlled since it comes from the handshake payload before/alongside certificate verification, and its wire encoding permits any `uint64` value [5](#0-4) .

This value then flows into `HostInfo.lastHandshakeTime`, whose doc comment explicitly claims the field defends against "an attack where a handshake packet is replayed after some time" [1](#0-0) . The only consumer of this field, `CheckAndComplete()`, does a *monotonic ordering* check relative to a pre-existing hostinfo for the same VPN address — `existingHostInfo.lastHandshakeTime >= hostinfo.lastHandshakeTime` — and only when `existingHostInfo` is not the initiator side [2](#0-1) . When there is no pre-existing `HostInfo` for that peer (e.g. after a tunnel has been torn down/expired, or on first contact), this check is skipped entirely, and the handshake is accepted regardless of how old the embedded `Time` value is.

This mirrors exactly the oracle bug pattern: a value obtained from an external/untrusted source (here, an unauthenticated wire field analogous to the price feed) is used for a security decision (anti-replay) without validating `now - value` against any acceptable bound, unlike the recommendation in the report to check `block.timestamp - updatedAt`.

### Impact Explanation
Because the actual cryptographic replay protection for a completed handshake message comes from the Noise protocol's ephemeral key exchange (which independently prevents literal packet replay from completing a *new* tunnel once state is torn down and new ephemeral keys are generated on each side), the practical exploitation window is bounded by whether an old, fully-formed handshake message pair can still be replayed to re-establish a tunnel after the original tunnel has expired/rotated. Given the explicit purpose comment on `lastHandshakeTime`, its absence of an absolute-time bound is a design/implementation gap: an old captured handshake initiation (stage-1) message, replayed after the original attempt was torn down, is not rejected on the basis of staleness, contradicting the stated security property and weakening the intended defense-in-depth against handshake replay churn.

### Likelihood Explanation
Exploitation requires network-level capture/replay of a UDP handshake packet — reachable pre-authentication by any network attacker capable of observing/replaying UDP traffic to the target's listen port, without needing a CA-signed certificate of their own. No changes to relative ordering logic are hit when the target hostinfo has already been torn down (e.g., after `ConnectionManager` inactivity/expiry), which is a normal operational condition, making the missing check reachable in ordinary runtime states.

### Recommendation
Add an absolute staleness/freshness bound when consuming `HandshakeTime` (i.e., `payload.Time`): reject handshake messages whose embedded `Time` differs from the local `time.Now()` by more than a configurable acceptable skew/heartbeat window, in addition to the existing relative-ordering check in `CheckAndComplete()`. This mirrors the report's recommendation to validate `block.timestamp - updatedAt` against a heartbeat threshold rather than relying solely on relative/last-known-value comparisons.

### Proof of Concept
1. Capture a legitimate stage-1 handshake UDP packet (`HandshakeIXPSK0`, `MessageCounter == 1`) sent by peer A to peer B.
2. Wait until peer B's `HostInfo` for peer A is torn down (e.g., via `ConnectionManager` inactivity timeout, or simply never having completed a tunnel yet).
3. Replay the captured stage-1 packet to peer B any time later.
4. Observe in `HandshakeManager.HandleIncoming()` → `beginHandshake()` → `CheckAndComplete()` that, absent an existing `HostInfo` entry, no staleness check on `hostinfo.lastHandshakeTime` (derived from the replayed `payload.Time`) occurs, and the handshake proceeds to build a new tunnel using the old timestamp, contrary to the field's documented anti-replay purpose [1](#0-0) .
