## Title
Lack of 2-Step Confirmation for Account Permission (Owner/Active/Witness) Updates - (File: `actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java`)

### Summary
`AccountPermissionUpdateActuator` performs a single-step, irreversible replacement of an account's `owner`, `witness`, and `active` permissions whenever a signed `AccountPermissionUpdateContract` transaction is broadcast. Just like the reported `TimeLock.changeOwner` pattern, there is no staged "propose → accept" flow: the new permission keys are written to the `AccountCapsule` and take effect immediately in `execute()`, with no confirmation step from the new key holder.

### Finding Description
Any account holder (an unprivileged transaction broadcaster) can submit an `AccountPermissionUpdateContract` to replace their account's `owner` permission (and optionally `witness`/`active` permissions) in one atomic step: [1](#0-0) 

The new owner permission is committed directly via `AccountCapsule.updatePermissions`, overwriting the previous owner permission with no pending/staging state and no requirement that the new key holder co-sign or "accept" the change: [2](#0-1) 

`validate()` only checks structural correctness of the new permission (address format, weight/threshold arithmetic, key count, operation bitmap for Active permission) — it never verifies that the submitter can actually produce a signature satisfying the *new* owner permission, nor does it provide any rollback/acceptance mechanism: [3](#0-2) 

This mirrors the reported bug class exactly: a privileged/administrative address-change operation (here, the account's `owner` permission, which controls `onlyOwner`-equivalent authority such as `AccountPermissionUpdateContract` itself, `WitnessUpdateContract`, `TransferContract`, freeze/unfreeze, etc.) is performed as a single irreversible step instead of a 2-step propose/accept scheme.

### Impact Explanation
If a user submits an `AccountPermissionUpdateContract` that sets a wrong `owner` permission (e.g., a typo'd address, an address without a corresponding private key, or a threshold/key combination that can never be satisfied), the account's owner authority is permanently and irreversibly lost. Because the owner permission also gates the ability to submit a corrective `AccountPermissionUpdateContract`, this results in **permanent freezing of funds and permanent loss of control** over the account (TRX balance, TRC10 assets, delegated resources, voting rights, and any witness role tied to the account) — matching the "permanent freezing of funds" acceptance criterion.

### Likelihood Explanation
Likelihood is driven by user/operator error rather than an attacker; multisig usage requires `AllowMultiSign` to be enabled via committee proposal, and the account owner must self-execute the flawed contract. This is analogous to the "human error" scenario described in the source report — an unprivileged transaction broadcaster can trigger it on their own account with no on-chain safeguard, and there's no way to detect/reject an unsatisfiable permission before commit (e.g., using an address with no known key, or a threshold higher than achievable weight is validated for `>0` but not against actual key ownership).

### Recommendation
Introduce a two-step confirmation for `AccountPermissionUpdateContract` (or at minimum for `owner` permission changes): stage the proposed permission set, and require a subsequent transaction signed under the *new* permission (i.e., satisfying the proposed threshold with the proposed keys) to activate it, mirroring OpenZeppelin's `Ownable2Step` pattern referenced in the source report. As a lighter-weight mitigation, `validate()` could at least reject owner-permission updates whose new configuration cannot be satisfied by any previously known signer of the account.

### Proof of Concept
1. Committee enables `AllowMultiSign` (`DynamicPropertiesStore.getAllowMultiSign() == 1`).
2. Account `A` broadcasts an `AccountPermissionUpdateContract` signed by its current owner key, setting the new `owner` `Permission` to a `Key` for address `B`, where `B`'s private key is unknown/mistyped.
3. `AccountPermissionUpdateActuator.execute()` commits the change via `AccountCapsule.updatePermissions` immediately.
4. Account `A` can no longer produce a valid owner signature; all `onlyOwner`-style actions (further permission updates, transfers requiring owner permission, resource management) are permanently inoperable — funds and resources associated with the account become irrecoverable. [4](#0-3)

  @Override
  public boolean execute(Object object) throws ContractExeException {
    TransactionResultCapsule result = (TransactionResultCapsule) object;
    if (Objects.isNull(result)) {
      throw new RuntimeException(ActuatorConstant.TX_RESULT_NULL);
    }

    AccountStore accountStore = chainBaseManager.getAccountStore();
    long fee = calcFee();
    final AccountPermissionUpdateContract accountPermissionUpdateContract;
    try {
      accountPermissionUpdateContract = any.unpack(AccountPermissionUpdateContract.class);

      byte[] ownerAddress = accountPermissionUpdateContract.getOwnerAddress().toByteArray();
      AccountCapsule account = accountStore.get(ownerAddress);
      account.updatePermissions(accountPermissionUpdateContract.getOwner(),
          accountPermissionUpdateContract.getWitness(),
          accountPermissionUpdateContract.getActivesList());
      accountStore.put(ownerAddress, account);

      adjustBalance(accountStore, ownerAddress, -fee);
      if (chainBaseManager.getDynamicPropertiesStore().supportBlackHoleOptimization()) {
        chainBaseManager.getDynamicPropertiesStore().burnTrx(fee);
      } else {
        adjustBalance(accountStore, accountStore.getBlackhole(), fee);
      }

      result.setStatus(fee, code.SUCESS);
    } catch (BalanceInsufficientException | InvalidProtocolBufferException e) {
      logger.debug(e.getMessage(), e);
      result.setStatus(fee, code.FAILED);
      throw new ContractExeException(e.getMessage());
    }

    return true;
  }

  public void updatePermissions(Permission owner, Permission witness, List<Permission> actives) {
    Builder builder = this.account.toBuilder();

    owner = owner.toBuilder().setId(0).build();
    builder.setOwnerPermission(owner);
    if (witness != null && builder.getIsWitness()) {
      witness = witness.toBuilder().setId(1).build();
      builder.setWitnessPermission(witness);
    }

    builder.clearActivePermission();
    if (actives != null) {
      for (int i = 0; i < actives.size(); i++) {
        Permission permission = actives.get(i).toBuilder().setId(i + 2).build();
        builder.addActivePermission(permission);
      }
    }

    this.account = builder.build();
  }
