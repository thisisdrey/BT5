### Title
Wallet Contract pays the relayer fee unconditionally before the emulated ERC-20/base transfer is known to succeed - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The ETH-implicit Wallet Contract emulates ERC-20 `transfer()` calls by mapping them to a NEP-141 `ft_transfer` cross-contract call, and compensates the relaying party with a `fee` taken from the caller's attached deposit. That fee-refund promise is fired off immediately in `inner_rlp_execute`, independent of and prior to the actual outcome of the emulated transfer, which is only resolved later through a chain of promises (`nep_141_storage_balance_callback` → `rlp_execute_callback`). If the underlying NEP-141 call fails — which is exactly the class of "weird/non-standard token" failure highlighted in the referenced ERC-20 report (blacklisted accounts, paused tokens, panics inside `ft_transfer`, insufficient balance, etc.) — the relayer is still paid, while the user's intended transfer never completes.

### Finding Description
In `inner_rlp_execute`, once a transaction is parsed as `EOABaseTokenTransfer` or `ERC20Transfer`, the code eagerly schedules a fee transfer to the relayer as a standalone batched promise, decoupled from the promise chain that actually performs the requested action: [1](#0-0) 

This `refund_promise` is created with `env::promise_batch_create` / `env::promise_batch_action_transfer` and is never chained (via `.then()`) to the promise that performs the actual transfer or to `rlp_execute_callback`, which is the only place that checks `PromiseResult::Failed` for the emulated action: [2](#0-1) 

For `ERC20Transfer`, the actual NEP-141 `ft_transfer` call only happens after a `storage_balance_of` check and, potentially, a `storage_deposit` call, several async steps after the fee has already been dispatched: [3](#0-2) [4](#0-3) 

The emulated ERC-20 `transfer()` mapping itself is implemented in `try_emulation`, which builds the `ft_transfer` `FunctionCall` action with no allowance/approve semantics, but is exactly the code path whose success is not guaranteed by the time the fee is paid: [5](#0-4) 

Because NEP-141 tokens can fail `ft_transfer` for many reasons analogous to "weird ERC-20 tokens" (insufficient balance, custom pausing/blacklisting logic, panics on transfer to unregistered accounts before the storage-deposit dance completes, or gas exhaustion in a long call chain), the relayer fee is not contingent on the transfer's actual completion. This is a direct structural analog of the reported bug class: code assumes an external token call behaves as expected and moves value based on that assumption, without verifying the call's actual success/failure before finalizing payment.

### Impact Explanation
A user pays a relayer fee (deducted from their attached deposit) for a promise that the relayer will get the user's signed transaction included and executed. Because the fee payment is unconditionally scheduled and not gated on the success of the downstream `ft_transfer`/storage-deposit chain, a relayer receives compensation even when the user's underlying transfer fails and no state changes on the token contract. From the user's perspective this is a permanent, non-refundable loss of funds (the fee) for a transaction that produced no useful effect. It also means there is no economic disincentive for relayers to submit transactions destined to fail against tricky/adversarial tokens, unlike the intended design where fee-for-service should track actual execution success.

### Likelihood Explanation
Any ordinary user/relayer pair interacting with a Wallet Contract (`rlp_execute`) using an ERC20Transfer or EOABaseTokenTransfer-with-fee emulation can trigger this: no privileged role or malicious node is required. The likelihood of the underlying transfer failing is realistic given the diversity of NEP-141 token implementations (paused tokens, custom transfer hooks, insufficient balance at time of execution vs. signing, or transient failures in the multi-hop `storage_balance_of` → `storage_deposit` → `ft_transfer` chain).

### Recommendation
Move the relayer fee transfer into the same promise chain as the emulated action, chained after (or as part of) `rlp_execute_callback`, and only pay the fee when `PromiseResult::Successful` is observed for the underlying action. Alternatively, refund the fee back to the caller in the failure branch of `rlp_execute_callback` (mirroring the existing `caller_deposit` refund logic) so that a failed emulated transfer does not result in an uncompensated fee payout to the relayer.

### Proof of Concept
1. Deploy a NEP-141 token whose `ft_transfer` reverts/panics under some condition reachable by the attacker (e.g., a paused token, a token requiring an allowance/approval not modeled by the Wallet Contract's ERC-20 emulation, or simply insufficient balance at execution time even though it was sufficient at signing time).
2. User signs an Ethereum-style `transfer()` call through the Wallet Contract (`rlp_execute`) with a non-zero relayer `fee`, targeting that token.
3. `inner_rlp_execute` immediately schedules the fee transfer to the relayer (`lib.rs:381-384`), independent of the promise chain.
4. The subsequent `nep_141_storage_balance_callback` → `ft_transfer` call fails; `rlp_execute_callback` reports `success: false` for the overall action.
5. The relayer nonetheless already received the fee in step 3, while the intended ERC-20 transfer never took place, resulting in a permanent, unrecoverable loss of the fee amount to the user with no compensating benefit.

    #[private]
    pub fn nep_141_storage_balance_callback(
        &mut self,
        token_id: AccountId,
        receiver_id: AccountId,
        action: near_action::Action,
        caller_deposit: Option<CallerDeposit>,
    ) -> PromiseOrValue<ExecuteResponse> {
        self.has_in_flight_tx = false;
        let maybe_storage_balance: Option<StorageBalance> = match env::promise_result(0) {
            PromiseResult::Failed => {
                return PromiseOrValue::Value(ExecuteResponse {
                    success: false,
                    success_value: None,
                    error: Some(format!("Call to NEP-141 {token_id}::storage_balance_of failed")),
                });
            }
            PromiseResult::Successful(value) => match serde_json::from_slice(&value) {
                Ok(x) => x,
                Err(_) => {
                    return PromiseOrValue::Value(ExecuteResponse {
                        success: false,
                        success_value: None,
                        error: Some("Unexpected response from NEP-141 storage_balance_of".into()),
                    });
                }
            },
        };
        let current_account_id = env::current_account_id();
        let ext = WalletContract::ext(current_account_id).with_static_gas(RLP_EXECUTE_CALLBACK_GAS);
        let promise = match maybe_storage_balance {
            Some(_) => {
                // receiver_id is registered so we can send the transfer
                // without additional actions. Note: in the standard NEP-141
                // implementation it is impossible to have `Some` storage balance,
                // but have it be insufficient to transact.
                match action_to_promise(token_id, action)
                    .map(|p| p.then(ext.rlp_execute_callback(caller_deposit)))
                {
                    Ok(p) => p,
                    Err(e) => {
                        return PromiseOrValue::Value(e.into());
                    }
                }
            }
            None => {
                // receiver_id is not registered so we must call `storage_deposit` first.
                let storage_deposit_args =
                    format!(r#"{{"account_id": "{receiver_id}"}}"#).into_bytes();
                let transfer_function_call = match action {
                    near_action::Action::FunctionCall(x) => x,
                    _ => {
                        return PromiseOrValue::Value(ExecuteResponse {
                            success: false,
                            success_value: None,
                            error: Some(
                                "Expected function call action to perform NEP-141 transfer".into(),
                            ),
                        });
                    }
                };
                Promise::new(token_id)
                    .function_call(
                        "storage_deposit".into(),
                        storage_deposit_args,
                        NEP_141_STORAGE_DEPOSIT_AMOUNT,
                        NEP_141_STORAGE_DEPOSIT_GAS,
                    )
                    .function_call(
                        transfer_function_call.method_name,
                        transfer_function_call.args,
                        transfer_function_call.deposit,
                        transfer_function_call.gas,
                    )
                    .then(ext.rlp_execute_callback(caller_deposit))
            }
        };
        self.has_in_flight_tx = true;
        PromiseOrValue::Promise(promise)
    }
