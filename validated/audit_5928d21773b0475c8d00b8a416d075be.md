### Title
Inconsistent Tron Power Accounting Between TVM Legacy `UnfreezeBalanceProcessor` and New-Resource-Model-Aware Actuators Leads to Under-Adjusted Votes and Over-Distributed Vi-Based Rewards - (File: `actuator/src/main/java/org/tron/core/vm/nativecontract/UnfreezeBalanceProcessor.java`)

### Summary
Analogous to the SY/YT reward-basis mismatch in the external report, java-tron computes the metric that backs vote/reward entitlement ("Tron Power") using two different, non-equivalent methods across code paths that are all supposed to keep votes consistent with actually-frozen balance. The TVM-reachable legacy unfreeze path never checks the new-resource-model migration state and always uses the raw, non-authoritative `getTronPower()`, while every other vote-mutating actuator/processor consults `oldTronPowerIsInvalid()`/`oldTronPowerIsNotInitialized()` and uses `getAllTronPower()` once the new resource model is active.

### Finding Description
`AccountCapsule` exposes two different "total voting power" accessors: [1](#0-0) 

`getTronPower()` is a live recomputation from current V1 frozen fields and V2 `FrozenV2` entries (excluding `TRON_POWER` type). `getAllTronPower()` instead prefers the frozen `oldTronPower` snapshot (set once when the account transitions into the new resource model) plus the `TRON_POWER`-typed V2/V1 balances. These two values diverge once an account has migrated (`oldTronPowerIsInvalid()`/`oldTronPowerIsNotInitialized()` state machine), because further V1-style unfreezes after migration no longer reduce the frozen `oldTronPower` snapshot the same way they reduce the live-recomputed `getTronPower()`.

Every actuator that mutates votes as a side effect of unfreezing correctly branches on `supportAllowNewResourceModel()`/`oldTronPowerIsInvalid()` and picks the correct metric:
- `VoteWitnessProcessor` (TVM `voteWitness`) explicitly switches between `getAllTronPower()` and `getTronPower()`: [2](#0-1) 
- `UnfreezeBalanceV2Actuator.updateVote` also branches on `supportAllowNewResourceModel()`/`oldTronPowerIsInvalid()` and uses `getAllTronPower()`: [3](#0-2) 

However, `UnfreezeBalanceProcessor` (the TVM native contract used by the legacy `unfreezeBalance` precompile/opcode path) contains no such branching at all — it unconditionally compares vote usage against the live `getTronPower()`, never checking `oldTronPowerIsInvalid()`/`oldTronPowerIsNotInitialized()`, and never calling `initializeOldTronPower()`/`invalidateOldTronPower()` the way its sibling `UnfreezeBalanceActuator`, `UnfreezeBalanceV2Actuator`, `FreezeBalanceActuator`, `FreezeBalanceV2Actuator`, and `VoteWitnessActuator` all do: [4](#0-3) 

Because this processor is completely unaware of the `oldTronPower` migration state that other paths rely on to keep the vote/reward-backing metric internally consistent, an account that has migrated into the new resource model (`oldTronPower` snapshot fixed) but still holds legacy V1 frozen balance can unfreeze through this TVM path without the vote-clearing check ever firing in the same way the other paths intend it to, since `getTronPower()` here does not reflect the same "true" tron power basis (`getAllTronPower()`) used for validating votes at cast-time (`VoteWitnessProcessor`) and clearing votes on other unfreeze paths. The votes then remain valid/uncleared and continue to accrue `Vi`-based rewards (`VoteRewardUtil.computeReward` / `MortgageService.computeReward`) computed off `getWitnessVi` deltas, without the corresponding stake actually still backing them, i.e. rewards keep flowing to votes whose backing balance metric the rest of the system has already invalidated.

This mirrors the reported bug class exactly: two subsystems compute the "amount that entitles you to rewards" using different bases that silently diverge over time (SY vs YT there; `getTronPower()` vs `getAllTronPower()`/`oldTronPower` here), and only some code paths perform the reconciliation ("merge" there; the `oldTronPowerIsInvalid`/`getAllTronPower` branching here).

### Impact Explanation
An account can retain vote weight in excess of what its actually-backing frozen balance under the new resource model would allow, continuing to earn `Vi`-delta rewards (`DelegationStore.getWitnessVi`, `VoteRewardUtil.computeReward`) disproportionate to real stake. This diverts SR/voting rewards away from correctly-collateralized voters — a concrete misallocation of reward funds reachable by any account that can trigger the TVM legacy unfreeze path, without requiring any special/malicious-SR privilege.

### Likelihood Explanation
The path is reachable by any user/contract invoking the TVM `unfreezeBalance` native contract (gated only by `VMConfig.allowTvmVote()`/legacy freeze support flags, not by any special permission), so it can be triggered by an ordinary signed transaction. The precondition (account previously migrated to the new resource model while still holding legacy V1 frozen balance and active votes) is a normal, non-adversarial account state reachable through ordinary freeze/unfreeze/vote usage over time, making exploitation feasible without insider access.

### Recommendation
Align `UnfreezeBalanceProcessor.execute()` with the other vote-affecting actuators: check `dynamicPropertiesStore.supportAllowNewResourceModel()` and `accountCapsule.oldTronPowerIsInvalid()`/`oldTronPowerIsNotInitialized()`, call `initializeOldTronPower()`/`invalidateOldTronPower()` as appropriate, and use `getAllTronPower()` (the same basis used by `VoteWitnessProcessor` for vote validation) instead of the raw `getTronPower()` when deciding whether votes must be cleared. This ensures the same "amount backing rewards" metric is used consistently across all vote/reward-affecting code paths.

### Proof of Concept
Conceptual sequence (exact numeric PoC would require a running node/test harness which is outside available tooling):
1. Freeze TRX via V1 legacy freeze, vote for a witness via TVM `voteWitness` (uses `getAllTronPower()` for validation once new-resource-model support is active).
2. Let the account transition into the new resource model such that `oldTronPower` becomes a fixed snapshot (`oldTronPowerIsInvalid()` becomes true after later actions per `UnfreezeBalanceActuator`/`UnfreezeBalanceV2Actuator` logic).
3. Call the TVM legacy `unfreezeBalance` precompile again for a V1 frozen amount. `UnfreezeBalanceProcessor.execute()` recomputes `getTronPower()` from live V1/V2 balances (not `getAllTronPower()`), so the comparison `accountCapsule.getTronPower() < usedTronPower * TRX_PRECISION` does not reflect the same power basis that would have failed the check at vote-time or in the sibling V2 unfreeze path, letting votes and their `Vi`-based reward accrual persist beyond what the account's true (`getAllTronPower()`) stake supports.   public long getTronPower() {
    long tp = 0;
    for (int i = 0; i < account.getFrozenCount(); ++i) {
      tp += account.getFrozen(i).getFrozenBalance();
    }

    tp += account.getAccountResource().getFrozenBalanceForEnergy().getFrozenBalance();
    tp += account.getDelegatedFrozenBalanceForBandwidth();
    tp += account.getAccountResource().getDelegatedFrozenBalanceForEnergy();

    tp += getFrozenV2List().stream().filter(o -> o.getType() != TRON_POWER)
            .mapToLong(FreezeV2::getAmount).sum();
    tp += account.getDelegatedFrozenV2BalanceForBandwidth();
    tp += account.getAccountResource().getDelegatedFrozenV2BalanceForEnergy();
    return tp;
  }

  public long getAllTronPower() {
    if (account.getOldTronPower() == -1) {
      return getTronPowerFrozenBalance() + getTronPowerFrozenV2Balance();
    } else if (account.getOldTronPower() == 0) {
      return getTronPower() + getTronPowerFrozenBalance() + getTronPowerFrozenV2Balance();
    } else {
      return account.getOldTronPower() + getTronPowerFrozenBalance()
          + getTronPowerFrozenV2Balance();
    }
  }
