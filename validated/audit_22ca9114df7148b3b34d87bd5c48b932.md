Audit Report

## Title
Inbound Queue V2 `add_tip` Accepts Tips For Any Unverified Nonce, Permanently Locking Burned Bridge Funds - (File: bridges/snowbridge/pallets/inbound-queue-v2/src/lib.rs)

## Summary
`Pallet::<T>::add_tip` in `snowbridge-pallet-inbound-queue-v2` (`bridges/snowbridge/pallets/inbound-queue-v2/src/lib.rs`, lines 248-258) only checks `!Nonce::<T>::get(nonce)` — i.e., that the nonce bit is not yet set in `NonceBitmap` — before storing a tip in `Tips::<T>`. This accepts a tip for any nonce that has simply not yet been marked as processed, including nonces that will never correspond to an actual message relayed from Ethereum, unlike the sibling `outbound-queue-v2::add_tip` which validates against an existing `PendingOrders` entry (lines 483-496 of `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs`).

## Finding Description
The `AddTip` trait implementation for the inbound queue is:
```rust
impl<T: Config> AddTip for Pallet<T> {
    fn add_tip(nonce: u64, amount: u128) -> Result<(), AddTipError> {
        ensure!(amount > 0, AddTipError::AmountZero);
        ensure!(!Nonce::<T>::get(nonce.into()), AddTipError::NonceConsumed);
        Tips::<T>::mutate(nonce, |tip| {
            *tip = Some(tip.unwrap_or_default().saturating_add(amount));
        });
        return Ok(());
    }
}
``` [1](#0-0) 

`Nonce::<T>` is a `SparseBitmapImpl` over `NonceBitmap`, which is purely a "has this nonce been consumed" tracker — it has no concept of a currently pending or reachable future nonce range: [2](#0-1)  and the storage declaration confirms it is a generic bitmap keyed by nonce with no relation to expected Ethereum Gateway state: [3](#0-2) .

By contrast, `outbound-queue-v2::add_tip` requires a `PendingOrders` entry to exist, returning `AddTipError::UnknownMessage` otherwise: [4](#0-3) .

Tips are only released when `process_message` actually decodes and dispatches a matching inbound message from Ethereum: [5](#0-4) . There is no path to reclaim a tip stored against a nonce that is never delivered.

The public entry point is `snowbridge-pallet-system-v2::Pallet::add_tip`, gated only by `T::FrontendOrigin` (ordinary signed AssetHub origin via XCM), which forwards directly to `InboundQueue::add_tip` and only records into `LostTips` when the underlying call returns an `Err`: [6](#0-5) . Because the inbound implementation returns `Ok(())` for any not-yet-consumed nonce, this loss-tracking path is never triggered for an unreachable/incorrect nonce.

On AssetHub, the tip asset is swapped to Ether and burned for teleportation before the cross-chain `add_tip` call completes: [7](#0-6) . This is confirmed live and reachable by the repository's own integration test, which tips an admittedly-unprocessed nonce (`MessageId::Inbound(2)`) from an ordinary signed AssetHub account and asserts `TipProcessed{ success: true }` on BridgeHub: [8](#0-7) . The pallet's own unit tests further confirm arbitrary unconsumed nonces (`nonce: u64 = 10`) are freely tippable with no existence check, only a `NonceConsumed` check for already-processed nonces.

Existing guards (`amount > 0`, `!Nonce::get(nonce)`) are insufficient because they validate only that a nonce hasn't already been used — not that it corresponds to, or will ever correspond to, a genuine inbound message from the Ethereum Gateway.

## Impact Explanation
This matches the "permanent user-fund or bridge-state lock" impact category: real assets swapped and burned on AssetHub as Ether, once teleported and stored in `Tips::<T>` under a nonce that will never be reached by `process_message`, become permanently unrecoverable — never refunded, never recorded in `LostTips`, and never claimable by any party.

## Likelihood Explanation
High. The flow requires no privileged, relayer, validator, or governance participation — any ordinary signed AssetHub account can trigger it via the standard `add_tip` XCM path, whether by mistake (choosing a wrong/future nonce) or deliberately. The code path is exercised and confirmed working (returning success) in the repository's own emulated integration tests.

## Recommendation
Align `snowbridge-pallet-inbound-queue-v2::add_tip` with the `outbound-queue-v2` pattern: validate the nonce against a tracked notion of "expected/pending" inbound nonces before accepting a tip (e.g., only allow tipping nonces within a known valid range or already associated with an expected message), and return `AddTipError::UnknownMessage` for any nonce that cannot be validated as a genuine future delivery target, so that `system-v2::add_tip` records the failure into `LostTips` instead of silently succeeding.

## Proof of Concept
1. On AssetHub, an ordinary signed user calls `SnowbridgeSystemFrontend::add_tip` with `MessageId::Inbound(nonce)` for an arbitrary/incorrect `nonce` that will never be emitted/relayed from the Ethereum Gateway (demonstrated in-repo with `MessageId::Inbound(2)` in `add_tip_from_asset_hub_user_origin`).
2. `system-frontend::swap_and_burn` swaps the tip asset to Ether and burns it for teleportation to BridgeHub.
3. On BridgeHub, `EthereumSystemV2::add_tip` forwards to `InboundQueue::add_tip(nonce, amount)`.
4. Since `Nonce::<T>::get(nonce)` is `false` for this nonce, `add_tip` returns `Ok(())` and stores the amount in `Tips::<T>[nonce]`; `TipProcessed{ success: true }` is emitted (confirmed by the cited test).
5. Because no message with this nonce is ever relayed, `Tips::<T>::take(nonce)` in `process_message` is never invoked; the burned Ether is permanently locked with no refund and no `LostTips` record.

		pub fn process_message(relayer: T::AccountId, message: Message) -> DispatchResult {
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == message.gateway, Error::<T>::InvalidGateway);

			let (nonce, relayer_fee) = (message.nonce, message.relayer_fee);

			// Verify the message has not been processed
			ensure!(!Nonce::<T>::get(nonce), Error::<T>::InvalidNonce);

			// Mark message as received
			Nonce::<T>::set(nonce);

			let message_id = T::MessageProcessor::process_message(relayer.clone(), message)

					MessageProcessorError::ConvertMessage(e) => Error::<T>::from(e).into(),

			}

			// Emit event with the message_id
			Self::deposit_event(Event::MessageReceived { nonce, message_id });

			Ok(())
