### Title
Malicious peer can fabricate an `AttachmentPage.inventory` bit to be selected as sole download source, starving retrieval of an attachment it does not hold - ([File: stackslib/src/net/atlas/download.rs])

### Summary
`AttachmentsBatchStateContext::get_prioritized_attachments_requests` trusts the raw `inventory` bitmap returned by a peer's `/v2/attachments/inv` response without any cross-check against the peer's actual data, so a peer can claim (via a `1` bit at `position_in_page`) to hold an attachment it does not have. If that peer's `ReliabilityReport` score is highest, `AttachmentRequest::get_most_reliable_source`/`Requestable::get_url` will select only that lying peer for the actual `/v2/attachments/{hash}` fetch, while any honest peer that truly holds the data is ignored for that round.

### Finding Description
`get_prioritized_attachments_requests` (stackslib/src/net/atlas/download.rs:404-478) builds, for each missing attachment, a `sources: HashMap<UrlString, ReliabilityReport>` purely from whether a peer's previously-received `GetAttachmentsInvResponse.pages[..].inventory[position_in_page] == 1`: [1](#0-0) 
There is no verification that the bit reflects reality — the equality "inventory-claimed == attachment-actually-served" is never checked before insertion into `sources`.

The resulting `AttachmentRequest` is later dispatched to only one peer, chosen via `get_most_reliable_source`, which purely maximizes `ReliabilityReport::score()` over the (unverified) `sources` map: [2](#0-1) 
`Requestable::get_url` for `AttachmentRequest` returns only this single best-scoring peer's URL, so the actual HTTP GET for `/v2/attachments/{content_hash}` is only issued to that one peer per round, even if `sources` contains multiple candidates.

When the malicious peer is queried and fails to serve valid data (returns nothing, or content that fails `decode_atlas_get_attachment`), `extend_with_attachments` just marks the peer's report as failed and moves on — it does not fall back to another candidate within `sources` for the same round: [3](#0-2) 
The whole `AttachmentsBatch` is then requeued and retried from scratch (`bump_retry_count`), re-running the entire inventory + download pipeline, up to `max_attachment_retry_count`: [4](#0-3) 
Because the malicious peer's inventory response is fetched fresh on every retry and still lies, and because reliability score is a property of the peer (not of a specific attachment), an attacker that keeps a high aggregate score (by legitimately answering other unrelated requests, or having a higher initial score than the honest peer) will continue to be selected as the sole `get_url()` target every retry round, permanently starving the legitimate attachment from ever being requested from the honest holder until `max_attachment_retry_count` is exhausted and the batch is dropped.

### Impact Explanation
A single malicious/dishonest outbound sync peer can, through a normal, unauthenticated `/v2/attachments/inv` response with one falsified bit, cause the victim node's Atlas attachment downloader to repeatedly select it as the only download source for a specific attachment, while a legitimate peer holding the real attachment is never queried in that round. This is a targeted attachment/BNS-data unavailability (a mismatch between what inventory claims and what is served), consistent with the "attachment/BNS mismatch" High-impact category. It is repeatable per attachment and per retry cycle, and does not require flooding or bandwidth — a single crafted inventory response per retry suffices.

### Likelihood Explanation
Preconditions: the attacker must already be one of the node's outbound sync peers (reachable via normal P2P handshake, no admin/secret needed) and must have an inventory the target attachments-batch will query. The attacker's `ReliabilityReport` score must be competitive with/higher than the honest holder's score at selection time; an attacker fully controls this by behaving well on all unrelated requests. Cost is trivial: forge one bit in one HTTP response repeatedly. This is fully remote and repeatable across retries without any privileged access.

### Recommendation
Do not commit to a single "most reliable" peer per retry attempt; instead, iterate through all peers listed in `sources` (in reliability order) within the same attempt/round if the first attempt fails, before requeuing the whole batch. Additionally/optionally, track per-attachment (not just per-peer) reliability so a peer that falsely claims an attachment in its inventory but fails to serve it is penalized specifically and excluded from `sources` for that content hash on subsequent retries.

### Proof of Concept
Extend `test_downloader_context_attachment_requests` (stackslib/src/net/atlas/tests.rs:669-761) style test:
1. Create two peers, "honest" (low prior reliability) and "liar" (high prior reliability).
2. Have both report an inventory page with the bit set at the same `position_in_page` for a target attachment, but only stub the "honest" peer's HTTP handler to actually serve the attachment; have "liar" return `None`/malformed data.
3. Call `get_prioritized_attachments_requests()` and assert `request.get_url()` returns the "liar" peer's URL despite it not truly holding the data (mirrors the assertion pattern at stackslib/src/net/atlas/tests.rs:740, `assert_eq!(request.get_url(), &peer_url_3)`), confirming the false inventory bit alone determines selection.
4. Drive `extend_with_attachments` with the failing "liar" response, then re-run `get_prioritized_attachments_requests()` on a fresh inventory round; assert the "liar" is picked again (since its aggregate score remains higher), and that after `max_attachment_retry_count` iterations the batch is dropped (`context.attachments_batch.retry_count >= connection_options.max_attachment_retry_count` per stackslib/src/net/atlas/download.rs:190-198) while the attachment was never fetched from the honest peer.

    pub fn extend_with_attachments(
        mut self,
        results: &mut BatchedRequestsResult<AttachmentRequest>,
    ) -> AttachmentsBatchStateContext {
        for (request, response) in results.succeeded.drain() {
            let report = self
                .peers
                .get_mut(request.get_url())
                .expect("Atlas: unable to retrieve reliability report for peer");

            let response = if let Some(r) = response {
                r
            } else {
                report.bump_failed_requests();
                continue;
            };

            if let Ok(response) = response.decode_atlas_get_attachment() {
                self.attachments.insert(response.attachment);
                report.bump_successful_requests();
            } else {
                report.bump_failed_requests();
            }
        }
        let mut events_ids = results.faulty_peers.keys().copied().collect::<Vec<usize>>();
        self.events_to_deregister.append(&mut events_ids);

        self
    }

impl AttachmentRequest {
    pub fn get_most_reliable_source(&self) -> (&UrlString, &ReliabilityReport) {
        self.sources
            .iter()
            .max_by_key(|(_, v)| v.score())
            .expect("Atlas: trying to select an Url out of an empty set")
    }
}

impl Hash for AttachmentRequest {
    fn hash<H: Hasher>(&self, state: &mut H) {
        self.content_hash.hash(state)
    }
}

impl Ord for AttachmentRequest {
    fn cmp(&self, other: &AttachmentRequest) -> Ordering {
        other.sources.len().cmp(&self.sources.len()).then_with(|| {
            let (_, report) = self.get_most_reliable_source();
            let (_, other_report) = other.get_most_reliable_source();
            report.cmp(other_report)
        })
    }
}

impl PartialOrd for AttachmentRequest {
    fn partial_cmp(&self, other: &AttachmentRequest) -> Option<Ordering> {
        Some(self.cmp(other))
    }
}

impl Requestable for AttachmentRequest {
    fn get_url(&self) -> &UrlString {
        let (url, _) = self.get_most_reliable_source();
        url
    }

    fn make_request_type(&self, peer_host: PeerHost) -> StacksHttpRequest {
        StacksHttpRequest::new_for_peer(
            peer_host,
            "GET".to_string(),
            format!("/v2/attachments/{}", &self.content_hash),
            HttpRequestContents::new(),
        )
        .expect("FATAL: failed to create an HTTP request for infallible data")
    }
}
