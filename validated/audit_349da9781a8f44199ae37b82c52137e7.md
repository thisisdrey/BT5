### Title
Unvalidated CDH `local_header_offset` causes out-of-bounds memory access when parsing an attacker-crafted jar/zip - (File: src/tools/singlejar/input_jar.h)

### Summary
`singlejar` (used by `java_binary`/`java_import`-style rules to merge jars produced from build inputs, including jars fetched via `http_file`/`http_archive` and third-party `.jar`/`.aar` archives) memory-maps the whole input file and walks the ZIP Central Directory. For every Central Directory Header (`CDH`) it computes the corresponding Local Header (`LH`) location directly from the 32/64-bit `local_header_offset` field embedded in the (attacker-supplied) archive, and immediately dereferences it, without checking that the offset lies inside the mapped file.

### Finding Description
`InputJar::NextEntry()` in [1](#0-0)  validates that each successive `CDH` record itself lies within the mapped file via `mapped_file_.mapped(new_cdr)` before dereferencing it. However, immediately after that check it calls `LocalHeader(current_cdh)`, defined as: [2](#0-1) 

This computes `mapped_file_.address(cdh->local_header_offset() + preamble_size_)` and casts the result directly to `const LH*` — with no equivalent `mapped_file_.mapped(...)` check. `local_header_offset()` (and its 64-bit ZIP64 extension) is fully attacker-controlled data read straight from the crafted archive's `CDH` (see `CDH::local_header_offset()` in [3](#0-2) ). A malicious archive can set this to an arbitrary value (e.g. pointing past the end of the mapped region, or to an offset such that the fixed 30-byte `LH` struct plus `file_name_length()`/`extra_fields_length()` derived from further out-of-bounds bytes reads/writes beyond the mapped buffer).

Once the bogus `LH*` is returned, callers dereference multiple fields off of it — `file_name_length()`, `extra_fields()`, `zip64_extra_field()`, and ultimately `data()` used to source bytes for decompression in `TransientBytes::DecompressEntryContents` ( [4](#0-3) ). Because `file_name_length_`/`extra_fields_length_` and the derived `compressed_file_size()`/`uncompressed_file_size()` are also read from this uncontrolled memory location, the subsequent `Append`/`Inflate` calls can read from (and, via the growable output buffer bookkeeping, potentially corrupt) memory well outside the intended input/output buffers — the same fundamental bug class as CVE-2017-9992 (an unchecked, attacker-controlled offset/size drives a memory read/write past the allocated/mapped region while parsing a crafted container format).

### Impact Explanation
An attacker who controls the bytes of a jar/zip/aar file that ends up being processed by `singlejar` (e.g. a third-party jar pulled in via `http_file`/`http_jar`/`maven_jar`-style rules, especially when integrity checksums are omitted or when the archive is otherwise attacker-influenced) can trigger out-of-bounds reads relative to the mmap'd input, and, through the inflate-buffer bookkeeping in `TransientBytes`, potentially corrupt heap memory in the `singlejar` process during a build. This is a memory-safety violation in native (non-sandboxed, non-Java) code that executes as part of ordinary build actions.

### Likelihood Explanation
`singlejar` runs on every Java target compiled with a merged-jar strategy and is exercised extensively; any input jar with a forged `local_header_offset` in a `CDH` record reaches this code path deterministically, no special build configuration is required. The `is()`/signature check on `LH` happens only after the pointer is already computed and would itself read from the untrusted address, so the crash/corruption can occur before any validation.

### Recommendation
Add a `mapped_file_.mapped(...)` (or equivalent full-record bounds) check in `InputJar::LocalHeader()` immediately after computing the candidate `LH*` address and before returning/dereferencing it — validating both the fixed 30-byte header and `sizeof(LH) + file_name_length() + extra_fields_length()` against the mapped file bounds, mirroring the existing check already performed for `CDH` records in `NextEntry()`.

### Proof of Concept
A reproducible JUnit/`shell` test would: build a minimal valid ZIP with one `CDH` entry, patch the `local_header_offset` (and, for zip64, the corresponding 8-byte extra-field value) in the Central Directory to a value at/near the end of file (or larger than the file size), then run `InputJar::Open` + `NextEntry` (or the `singlejar` binary) over it and observe a heap-buffer-overflow / SEGV / ASan report when `LocalHeader()`'s unchecked pointer is dereferenced — analogous to `src/tools/singlejar/transient_bytes_test.cc`'s `DecompressEntryContents` test but with a corrupted `local_header_offset` instead of a well-formed jar.

**Caveat**: I could not fully trace every call site that consumes the `LH*` returned by `NextEntry`/`LocalHeader` (e.g. in `combiners.h`, `output_jar.h`) within this session, and I did not confirm whether `MappedFile::address()`/`mapped()` themselves perform any additional clamping that might partially mitigate this before dereference. A background Devin session with full repo access should verify `MappedFile::mapped()`'s exact semantics and trace all consumers of the unchecked `LH*` before finalizing severity.
