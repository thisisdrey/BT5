### Title
`ENERGY_FEE` (and `EXCHANGE_CREATE_FEE`) chain parameter proposal accepts any value with no range/overflow check, enabling a SR/committee proposal to charge arbitrarily large TRX per unit of energy and drain caller balances — (File: `actuator/src/main/java/org/tron/core/utils/ProposalUtil.java`)

### Summary
`ProposalUtil.validator` validates every proposal parameter value before it can be committed to `DynamicPropertiesStore`, and almost every parameter has an explicit bound (e.g. `ACCOUNT_UPGRADE_COST`, `CREATE_ACCOUNT_FEE`, `WITNESS_PAY_PER_BLOCK`, etc. are all checked against `[0, LONG_VALUE]`). However `ENERGY_FEE` and `EXCHANGE_CREATE_FEE` fall through with a bare `break` and **no validation at all**: [1](#0-0) 

This mirrors the reported bug class: a privileged actor (here, TRON's witness/committee governance instead of a single admin role) can set a fee-like parameter to an unbounded value, and that parameter is later applied directly against ordinary users' balances without any additional cap, effectively letting the "fee" consume the entire balance/reward of unrelated transaction senders.

### Finding Description
`ENERGY_FEE` is documented in the enum comment as intended to be bounded (`// 10 Sun, [0, 100000000000] TRX`): [2](#0-1) 

but unlike sibling cases in the same switch statement (`ACCOUNT_UPGRADE_COST`, `CREATE_ACCOUNT_FEE`, `WITNESS_PAY_PER_BLOCK`, etc., which explicitly enforce `value < 0 || value > LONG_VALUE`): [3](#0-2) 

`ENERGY_FEE`/`EXCHANGE_CREATE_FEE` skip validation entirely and go straight to `break`: [1](#0-0) 

Once a `ProposalCreateContract` with this parameter passes `ProposalCreateActuator.validate()` (which only calls `ProposalUtil.validator`) and is later approved and applied, `ProposalService.process` stores it unconditionally: [4](#0-3) 

The stored value is then read directly in the hot fee-charging path of every smart-contract call that exceeds the caller's free/frozen energy, `ReceiptCapsule.payEnergyBill`: [5](#0-4) 

`sunPerEnergy` is taken directly from `dynamicPropertiesStore.getEnergyFee()` with no upper bound, then multiplied by the caller's/origin's energy usage (`(usage - accountEnergyLeft) * sunPerEnergy`) to compute `energyFee`, which is subtracted straight from the account's TRX `balance`. There is no cap comparing `energyFee` to the transaction's `feeLimit` at this layer of `ReceiptCapsule`, and no re-validation that `getEnergyFee()` is sane at the time of consumption.

### Impact Explanation
If `ENERGY_FEE` is set to an extreme value via a passed proposal, every unprivileged account that triggers TVM execution beyond its free/frozen energy allowance (i.e., any ordinary smart-contract call transaction broadcast to the network) will have its entire TRX balance charged as "energy fee" for even minimal excess energy usage, since the multiplication `(usage - accountEnergyLeft) * sunPerEnergy` scales unboundedly with the parameter. This is a direct concrete instance of "the user's entire balance/reward taken as a fee," matching the reported bug class, and additionally risks integer overflow in the multiplication (`long` overflow could wrap to a small or negative fee, corrupting accounting and potentially allowing free/negative-cost energy consumption — an unbacked-balance condition on the other extreme). Either direction (extreme high fee draining balances, or overflow producing incorrect low/negative fees) constitutes concrete theft-of-funds/unbacked-balance impact reachable from ordinary transaction execution once the parameter is set.

### Likelihood Explanation
Setting the value requires a `ProposalCreateContract` from a witness account, and subsequent approval, mirroring the original report's admin-gated `setFee`. This is a governance/privileged action, not something an arbitrary unprivileged user can do directly — but it is exactly as privileged as the original finding's admin-only `setFee`, so it is an equally valid instance of "missing bound check on an admin-settable fee parameter." Given `ProposalUtil.validator` clearly enforces bounds on every sibling monetary parameter except these two, this looks like an accidental omission rather than intended design, increasing the likelihood that it is an unintended gap rather than a deliberate decision.

### Recommendation
Add the same `value < 0 || value > LONG_VALUE` (or a tighter, fee-appropriate bound) check for `ENERGY_FEE` and `EXCHANGE_CREATE_FEE` in `ProposalUtil.validator`, consistent with the other fee-related `ProposalType` cases, and consider adding a sanity/overflow guard in `ReceiptCapsule.payEnergyBill` when computing `energyFee` (e.g., using `Math.multiplyExact` and clamping to the account balance/`feeLimit`).

### Proof of Concept
1. A witness proposes a `ProposalCreateContract` with parameter code `11` (`ENERGY_FEE`) and an extreme value (e.g., `Long.MAX_VALUE / 2`).
2. `ProposalCreateActuator.validate()` calls `ProposalUtil.validator`, which hits `case ENERGY_FEE: ... break;` with no check, so the proposal passes validation. [6](#0-5) 
3. Once the proposal is approved and processed, `ProposalService.process` calls `saveEnergyFee(entry.getValue())`, storing the unbounded value. [4](#0-3) 
4. Any ordinary user broadcasting a smart-contract-invoking transaction that exceeds free/frozen energy triggers `ReceiptCapsule.payEnergyBill`, which multiplies usage by the malicious `sunPerEnergy` and deducts the result from the caller's balance, draining it entirely (or overflowing). [5](#0-4)
