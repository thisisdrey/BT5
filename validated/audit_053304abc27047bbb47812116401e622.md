### Title
Unvalidated Contract Type Value Used as Array Index in Permission Operations Check Causes IndexOutOfBoundsException - (File: `chainbase/src/main/java/org/tron/common/utils/WalletUtil.java`)

### Summary
The permission/operations bitmap check that gates whether a signer's `Active` permission is allowed to execute a given contract type indexes a fixed 32-byte (256-bit) `ByteString` using `contract.getTypeValue()` — the raw protobuf enum wire value — without validating that this value falls within `[0,255]`. Since protobuf enum wire values are not restricted to the values declared in the `.proto` file, an attacker can submit a transaction whose `Contract.type` field carries an out-of-range integer, causing an unhandled `IndexOutOfBoundsException` deep in transaction/signature validation, mirroring the root cause of CVE-2022-50315 (a fixed-size array indexed with a value that can exceed the array's declared bound).

### Finding Description
`Permission.operations` is a fixed 32-byte bitmap (256 bits, one bit per `ContractType`), and the code that determines whether a specific contract type is permitted under an `Active` permission computes: [1](#0-0) 

```
int contractType = contract.getTypeValue();
boolean b = (operations.byteAt(contractType / 8) & (1 << (contractType % 8))) != 0;
```

`contract.getTypeValue()` returns the raw `int32` value encoded on the wire for the `ContractType type = 1` field of `Transaction.Contract` [2](#0-1) 
. Protobuf does not restrict enum wire values to the ones declared in the enum — any `int32` (including negative values or values far beyond 255) deserializes successfully, with `getType()` reporting `UNRECOGNIZED` while `getTypeValue()` still returns the raw crafted integer. `operations` is asserted to be exactly 32 bytes just before this computation [3](#0-2) 
, but `contractType/8` is never bounded to `< 32`, so a `contractType` of, e.g., 1000 computes index 125, and `ByteString.byteAt(125)` throws `IndexOutOfBoundsException`. A negative `contractType` (also achievable via wire-level manipulation of a signed varint) causes similar undefined indexing behavior.

The vulnerable check is reachable from multiple unprivileged, unauthenticated entry points that any transaction broadcaster or API client can hit, all guarded only by checked exceptions (`SignatureException`, `PermissionException`, `SignatureFormatException`) that do **not** catch `RuntimeException`/`IndexOutOfBoundsException`:

- `TransactionCapsule.checkPermission` → `checkPermissionOperations`, invoked from `validateSignature`, which is invoked from `validatePubSignature` during transaction admission/verification [4](#0-3) [5](#0-4) 
- `Wallet.getTransactionApprovedList`, reachable via the gRPC/HTTP `GetTransactionApprovedList` API surface, an anonymous client-reachable query path [6](#0-5) 
- `TransactionUtil.getTransactionSignWeight`, another wallet query path with the identical unguarded call [7](#0-6) 

`validatePubSignature`'s catch block only covers checked exceptions:
```
} catch (SignatureException | PermissionException | SignatureFormatException e) {
``` [8](#0-7) 
so the unchecked `IndexOutOfBoundsException` thrown by `checkPermissionOperations` propagates out of the intended validation flow uncaught at this layer.

### Impact Explanation
An `IndexOutOfBoundsException` thrown from within transaction validation for a crafted contract carrying an out-of-range `ContractType` wire value, a permission other than the default owner permission (i.e. `permissionId != 0`, requiring an `Active` permission with a valid `operations` bitmap already configured on the target account), can escape the intended exception handling in `validatePubSignature` and in the `Wallet`/`TransactionUtil` query paths that only anticipate `SignatureException`/`PermissionException`/`SignatureFormatException`. Depending on how far up the call stack this exception propagates before being caught by a generic handler, this can manifest as a denial-of-service against the affected transaction/API-processing thread — an unauthenticated client submitting a crafted transaction to the broadcast or `GetTransactionApprovedList`/`GetTransactionSignWeight` API can trigger it repeatedly.

### Likelihood Explanation
Exploitation requires: (1) crafting a raw serialized `Transaction` with a `Contract.type` wire value outside the declared enum range (straightforward with any protobuf encoder, since wire format doesn't enforce enum ranges), and (2) the target account having a non-owner `Active` permission with `permissionId != 0` set on the contract's `permission_id` field so that `checkPermissionOperations` is reached (accounts using multisig/active permissions, a supported and reachable configuration via `AccountPermissionUpdateContract`). No special privileges are needed beyond broadcasting a transaction or issuing an unauthenticated wallet API query, making this reachable by any external client.

### Recommendation
Bound-check `contractType` before using it to index the operations bitmap: reject or treat as "not permitted" any `contractType` outside `[0, 255]` (and specifically outside the set of currently-defined `ContractType` values) in `WalletUtil.checkPermissionOperations` and `TransactionUtil.checkPermissionOperations`, mirroring the "match array bound with the actual acceptable value range" fix pattern of the referenced CVE (`EM_MAX_SLOTS` matched to `SATA_PMP_MAX_PORTS`). Additionally, ensure `IndexOutOfBoundsException` (or all `RuntimeException`s) are caught alongside the checked exceptions at every call site (`TransactionCapsule.validatePubSignature`, `Wallet.getTransactionApprovedList`, `TransactionUtil.getTransactionSignWeight`) so a malformed transaction cannot escape as an unhandled runtime exception.

### Proof of Concept
1. Construct a raw `Transaction` protobuf where `raw_data.contract[0].type` is serialized with an integer value far outside the declared `ContractType` enum (e.g., value `2000`), and `permission_id` set to a non-zero value (e.g., `2`) matching an `Active` permission already configured (with a valid 32-byte `operations` bitmap) on the `owner_address` account.
2. Submit this transaction via the standard broadcast path, or submit it unsigned to the `GetTransactionApprovedList` / `GetTransactionSignWeight` wallet API.
3. During permission verification, `WalletUtil.checkPermissionOperations`/`TransactionUtil.checkPermissionOperations` computes `contractType / 8 = 250`, and calls `operations.byteAt(250)` on a `ByteString` of only 32 bytes, throwing `IndexOutOfBoundsException`, which is not caught by the surrounding `catch (SignatureException | PermissionException | SignatureFormatException e)` blocks in the calling methods.
