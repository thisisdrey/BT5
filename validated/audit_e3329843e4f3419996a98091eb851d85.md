### Title
Internal ledger credits the caller-reported `amount` in `ft_on_transfer`/`mt_on_transfer` instead of the token contract's actual balance delta, allowing non-standard (fee-on-transfer/deflationary) NEP-141/NEP-245 tokens to mint unbacked internal credit - (File: `contracts/defuse/src/contract/tokens/nep141/deposit.rs`)

### Summary
`Contract::deposit` (called from `ft_on_transfer` and `mt_on_transfer`) credits the depositor's internal `token_balances` with exactly the `amount` value reported in the receiver-callback arguments, without ever checking that the Defuse contract's actual real-token balance increased by that same amount. This reproduces the Sherlock M-01 bug class: internal bookkeeping assumes 1:1 correspondence between the reported transfer amount and the value actually received, which breaks for any non-standard NEP-141/NEP-245 token that reduces the delivered amount (fee-on-transfer, deflationary/rebasing tokens, or a token contract that simply lies about `amount`/`used` while transferring less).

### Finding Description
`ft_on_transfer` derives the `token_id` from `env::predecessor_account_id()` and unconditionally calls `self.deposit(receiver_id, [(token_id, amount.0)], ...)`: [1](#0-0) 

`deposit()` then adds `amount` straight to `total_supplies` and to the owner's `token_balances`, with no verification against the contract's actual held balance of that token: [2](#0-1) 

The same pattern exists for `mt_on_transfer`, which also credits `amounts` verbatim into internal balances: [3](#0-2) 

A symmetric instance of the same "trust the reported value" pattern exists on withdrawal: `ft_resolve_withdraw` computes the `used` amount purely from the promise result returned by the external token contract's `ft_transfer_call` (capped at `amount`), then refunds `amount - used` back into the internal ledger: [4](#0-3) 

In all these code paths, the equality that should hold — `internal balance credited == actual value received by the contract` (on deposit) and `internal balance debited == value actually delivered to receiver_id + value refunded` (on withdraw) — is not enforced. It is entirely delegated to the external NEP-141/NEP-245 token contract self-reporting a number, with no on-chain check of Defuse's own balance before/after the transfer.

### Impact Explanation
If any token onboarded into Defuse (including a token later upgraded to add a fee, as the sponsor of the original Sherlock report warned about upgradeable tokens) delivers less value than the `amount`/`used` it reports, an attacker can:
- Deposit through `ft_on_transfer`/`mt_on_transfer` and receive full internal credit for less real value actually received by the contract, creating unbacked "phantom" balance for that `TokenId`.
- That phantom balance can immediately be used inside Defuse (transfers, `TokenDiff` swaps, withdrawals against other real depositors' funds of the same `TokenId`), meaning later legitimate withdrawers of that token cannot be fully paid — a `value debited versus value delivered` mismatch that can result in funds being permanently unrecoverable for other depositors of the same token.
- Symmetrically, on withdrawal, a token contract that reports `used == amount` in its `ft_transfer_call` return value while sending less to `receiver_id` causes Defuse to debit the sender's full internal balance without a matching refund and without the value actually reaching the receiver, i.e., a mismatched resolver refund.

### Likelihood Explanation
Requires a token with non-standard supported transfer semantics (fee-on-transfer, deflationary/rebasing, or malicious self-reporting), which the underlying report itself frames as a medium-risk, curation-dependent issue for "arbitrary ERC20 tokens." Given Defuse is designed to onboard arbitrary NEP-141/NEP-245 tokens permissionlessly (any account can call `ft_on_transfer`/`mt_on_transfer` as `predecessor_account_id()`), and given the sponsor's own caveat that "certain popular tokens are up-gradable and could potentially implement non-standard behavior," this is a realistic, not purely theoretical, condition once such a token is deposited/withdrawn.

### Recommendation
Do not rely solely on the `amount`/`used` values passed into `ft_on_transfer`, `mt_on_transfer`, `ft_resolve_withdraw`, and `mt_resolve_withdraw`. Where feasible, verify the actual balance change of the Defuse contract's own holdings of the token (e.g., query `ft_balance_of`/`mt_balance_of` before and after the transfer, or require an explicit reconciliation step) before crediting/debiting internal ledger balances, or restrict onboarding to tokens whose contracts are verified/audited to guarantee exact-amount transfer semantics.

### Proof of Concept
1. Deploy (or onboard) a NEP-141 token contract `feeToken.near` whose `ft_transfer_call` deducts an internal fee, delivering `950` real tokens to the receiver's registered balance while still invoking `ft_on_transfer(sender_id, amount=U128(1000), msg)` on Defuse with the full pre-fee `amount`.
2. Depositor calls `feeToken.ft_transfer_call(defuse.near, 1000, msg)`. Defuse's actual `feeToken` balance only increases by 950, but `Contract::deposit` (`contracts/defuse/src/contract/tokens/mod.rs:18-74`, called from `ft_on_transfer` in `contracts/defuse/src/contract/tokens/nep141/deposit.rs:38-43`) credits the depositor's `token_balances` with `1000`.
3. The depositor (or colluding party) now holds `1000` units of internal `TokenId::Nep141(feeToken.near)` credit backed only by `950` real tokens held by the contract.
4. The depositor withdraws or transfers the full `1000` internal credit; the last legitimate holder(s) of that `TokenId` cannot be paid in full when they attempt to withdraw, since Defuse's real `feeToken` balance is insufficient to cover the sum of all internally recorded balances for that token.

    fn ft_on_transfer(
        &mut self,
        sender_id: AccountId,
        amount: U128,
        msg: String,
    ) -> PromiseOrValue<U128> {
        require!(amount.0 > 0, "zero amount");

        let token_id = TokenId::Nep141(Nep141TokenId::new(env::predecessor_account_id()));

        let DepositMessage {
            receiver_id,
            action,
        } = if msg.is_empty() {
            DepositMessage::new(sender_id.clone())
        } else {
            msg.parse().unwrap_or_else(|e| panic!("{e}"))
        };

        self.deposit(
            receiver_id.clone(),
            [(token_id.clone(), amount.0)],
            Some("deposit"),
        )
        .unwrap_or_else(|err| err.panic());

        &mut self,

                    DefuseError::TokenIdTooLarge(token_id.len()).panic();

            receiver_id,

            msg.parse().unwrap_or_else(|e| panic!("{e}"))

    fn ft_resolve_withdraw(
        &mut self,
        token: AccountId,
        sender_id: AccountId,
        amount: U128,
        is_call: bool,
    ) -> U128 {
        let used = if is_call {
            // `ft_transfer_call` returns successfully transferred amount
            match promise_result_checked_json::<U128>(0) {
                Ok(Ok(used)) => used.0.min(amount.0),
                Ok(Err(_deserialize_err)) => 0,
                // do not refund on failed `ft_transfer_call` due to
                // NEP-141 vulnerability: `ft_resolve_transfer` fails to
                // read result of `ft_on_transfer` due to insufficient gas
                Err(_) => amount.0,
            }
        } else {
            // `ft_transfer` returns empty result on success
            if promise_result_checked_void(0).is_ok() {
                amount.0
            } else {
                0
            }
        };

        let refund = amount.0.saturating_sub(used);
        if refund > 0 {
            self.deposit(
                sender_id,
                [(Nep141TokenId::new(token).into(), refund)],
                Some(REFUND_MEMO),
            )
            .unwrap_or_else(|err| err.panic());
        }

        U128(used)
    }
