Audit Report

## Title
Delivery receipt `success` flag is ignored, allowing reward payout and order settlement on failed Ethereum execution - (File: `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs`)

## Summary
`Pallet::process_delivery_receipt` decodes a `DeliveryReceipt` (which carries a `success` field derived from the Ethereum `InboundMessageDispatched` event) but never reads or checks `receipt.success` before crediting `T::RewardPayment::register_reward` and removing the corresponding `PendingOrder`. This means messages whose command execution reverted on Ethereum (`success = false`) are settled and rewarded identically to genuinely successful ones.

## Finding Description
`submit_delivery_receipt` verifies the event log via `T::Verifier::verify`, decodes it into `DeliveryReceipt` via `DeliveryReceipt::try_from`, and forwards it to `process_delivery_receipt` without ever inspecting `success`: [1](#0-0) 

`process_delivery_receipt` only checks `T::GatewayAddress::get() == receipt.gateway` and that a `PendingOrder` exists for `receipt.nonce`; it then unconditionally pays `order.fee` to the reward account and removes the order, regardless of `receipt.success`: [2](#0-1) 

The `DeliveryReceipt` type explicitly decodes a `success: bool` field from the Solidity `InboundMessageDispatched` event (`event InboundMessageDispatched(uint64 indexed nonce, bytes32 topic, bool success, bytes32 reward_address)`), confirming the field exists and represents genuine Ethereum-side execution status, yet it is dropped after decode and never consumed by the pallet logic: [3](#0-2) 

The only guards present — `T::Verifier::verify` (proves the log genuinely originated from the configured gateway/chain, not that the dispatched command succeeded), the gateway-address equality check, and existence of a `PendingOrder` for the nonce — do not substitute for validating the execution-status flag carried by the event itself.

## Impact Explanation
This breaks the required invariant that bridge receipts and payout state must only advance after successful execution/settlement. Because `receipt.success` is discarded, a relayer receives the full `order.fee` reward and the `PendingOrder` for that nonce is removed via `<PendingOrders<T>>::remove(nonce)` even when the Ethereum-side command execution failed (`success == false`). This is a duplicate/unbacked-style reward payout disconnected from genuine successful delivery, corrupting the reward accounting state (`PendingOrders` map and the reward ledger via `T::RewardPayment::register_reward`) without any compensating on-chain retry/failure path being triggered.

## Likelihood Explanation
`submit_delivery_receipt` is a public, signed extrinsic reachable by any account, requiring only a valid Ethereum event proof for the real Gateway contract — including a real `success = false` event emitted after a reverted command dispatch. No malicious peer, validator, collator, governance action, or leaked key is needed; a normal relayer submitting a legitimate but failed-execution receipt triggers the bug deterministically and repeatably for every failed nonce.

## Recommendation
In `process_delivery_receipt`, branch on `receipt.success`: only call `T::RewardPayment::register_reward` and remove the `PendingOrder` when `receipt.success == true`. For `success == false`, emit a distinct failure event (e.g. `MessageDeliveryFailed`) and decide the appropriate order-lifecycle action (e.g. retry, refund fee to sender, or explicit failure settlement) instead of silently paying out and clearing the order as if it succeeded.

## Proof of Concept
1. `do_process_message` queues a message, inserting `PendingOrder { nonce, fee, .. }` into `PendingOrders`.
2. The corresponding command is delivered to Ethereum and its execution reverts; the Gateway contract still emits `InboundMessageDispatched(nonce, topic, success=false, reward_address)`.
3. A relayer obtains the log/proof and calls `submit_delivery_receipt(origin, event)`.
4. `T::Verifier::verify` succeeds (the event genuinely occurred); `DeliveryReceipt::try_from` decodes `success = false` along with `nonce`, `reward_address`, `gateway`.
5. `process_delivery_receipt` checks only `gateway` equality and `PendingOrders::get(nonce)` existence, then unconditionally calls `T::RewardPayment::register_reward(&reward_account, .., order.fee)` and calls `<PendingOrders<T>>::remove(nonce)` — the relayer is paid and the order settled despite `success == false`, which can be confirmed by adding a unit test analogous to the existing `process_delivery_receipt` tests but asserting reward payout occurs even with a `DeliveryReceipt { success: false, .. }` input.

		/// Process a delivery receipt from a relayer, to allocate the relayer reward.
		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}

sol! {
	event InboundMessageDispatched(uint64 indexed nonce, bytes32 topic, bool success, bytes32 reward_address);
}

/// Delivery receipt
#[derive(Clone, Debug)]
pub struct DeliveryReceipt {
	/// The address of the outbound queue on Ethereum that emitted this message as an event log
	pub gateway: H160,
	/// The nonce of the dispatched message
	pub nonce: u64,
	/// Message topic
	pub topic: H256,
	/// Delivery status
	pub success: bool,
	/// The reward address
	pub reward_address: [u8; 32],
}

#[derive(Copy, Clone, Encode, Decode, Eq, PartialEq, Debug, TypeInfo)]
pub enum DeliveryReceiptDecodeError {
	DecodeLogFailed,
	DecodeAccountFailed,
}

impl TryFrom<&Log> for DeliveryReceipt {
	type Error = DeliveryReceiptDecodeError;

	fn try_from(log: &Log) -> Result<Self, Self::Error> {
		let topics: Vec<B256> = log.topics.iter().map(|x| B256::from_slice(x.as_ref())).collect();

		let event = InboundMessageDispatched::decode_raw_log_validate(topics, &log.data)
			.map_err(|_| DeliveryReceiptDecodeError::DecodeLogFailed)?;

		Ok(Self {
			gateway: log.address,
			nonce: event.nonce,
			topic: H256::from_slice(event.topic.as_ref()),
			success: event.success,
			reward_address: event.reward_address.0,
		})
	}
