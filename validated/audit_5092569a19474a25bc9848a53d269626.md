Audit Report

## Title
Underpriced/zero remote-fee acceptance in Snowbridge outbound-queue `calculate_fee` due to unit-scale mismatch - (File: `bridges/snowbridge/pallets/outbound-queue/src/lib.rs`)

## Summary
`Pallet::<T>::calculate_fee` computes the Ethereum-side remote fee by taking a raw wei-denominated `U256` value from `calculate_remote_fee` and wrapping it directly with `FixedU128::from_inner(fee)` [1](#0-0) , which implicitly divides the raw wei value by `10^18` before the deliberate `convert_from_ether_decimals` scaling is applied [2](#0-1) . This compounding scale error can round `Fee.remote` down to exactly `0` for legitimate, non-zero `PricingParameters` when the wei-value (`fee_per_gas * gas_used_at_most + reward`) is small relative to the combined `10^18 * 10^(ETHER_DECIMALS - T::Decimals)` divisor, allowing messages with low-gas commands to be accepted into the outbound queue for zero remote-side cost.

## Finding Description
The exploit path is confirmed directly in the pallet code: `calculate_remote_fee` returns the raw integer `fee_per_gas * gas_used_at_most + reward` [3](#0-2) , which is then downcast to `u128` and reinterpreted with `FixedU128::from_inner` — treating the raw wei integer as if it were already a `10^18`-scaled fixed-point fraction, rather than converting it properly (e.g. via `FixedU128::from_rational(fee, 10^18)`) [4](#0-3) . The result is further divided by `10^(ETHER_DECIMALS - T::Decimals)` in `convert_from_ether_decimals` [2](#0-1) , compounding the truncation. This entry point is reachable from any unprivileged caller via `SendMessage::validate`, which calls `T::GasMeter::maximum_gas_used_at_most(&message.command)` followed directly by `calculate_fee` [5](#0-4) , so the caller-chosen `Command` (via low-gas `GasMeter` estimate) directly drives whether the rounding-to-zero condition triggers. No guard exists anywhere in this path to reject or floor a computed remote fee of `0`; the only check present (`expect("exchange rate is not zero; qed")`) guards divide-by-zero, not underflow-to-zero of the final value. The pallet's own regression test demonstrates the defect with concrete, non-degenerate `PricingParameters` (`exchange_rate = 1/1`, `fee_per_gas = 1`, `rewards = {1,1}`, `multiplier = 1`, `gas_used = 250000`), yielding `fee.remote == 0`, and the test's own comment states this is "invalid ... which should be avoided" [6](#0-5) . The `Fee<Balance>` struct's `remote` field is meant to be the sender-paid amount covering Ethereum dispatch cost [7](#0-6) , so a silent zero value contradicts the pallet's documented intent of always producing a "total fee ... to cover all costs of delivering a message to the remote destination" [8](#0-7) .

## Impact Explanation
When `fee.remote` computes to `0`, a message is still accepted, queued, committed, and eventually dispatched on Ethereum consuming real relayer/gas resources, while the sender pays nothing toward that remote cost. This matches the allowed impact category "public underpriced work that degrades block production or stalls bridge processing," since an attacker can cheaply flood the outbound queue with commands whose computed gas bound is low enough to trigger the zero-remote-fee rounding, at zero remote cost, potentially starving legitimate relayer incentives and congesting the bridge message pipeline.

## Likelihood Explanation
The vulnerability is triggered purely by the interaction between governance-configured `PricingParameters` (fee_per_gas, reward, multiplier, exchange_rate) and the caller-controlled `gas_used_at_most` derived from the specific `Command` submitted; no privileged action, compromised relayer, or leaked key is required. The scale of the bug (effectively dividing the true fee by an extra `10^18`) means it is likely to manifest whenever the wei-denominated remote-fee value is smaller than the combined divisor for the chain's currency decimals, which is a real risk for low-value commands even under plausible non-degenerate pricing parameters, as demonstrated by the pallet's own confirmatory unit test.

## Recommendation
Fix the unit conversion in `calculate_fee` to properly convert the raw wei `U256`/`u128` value into a `FixedU128` fraction via `FixedU128::from_rational(fee, 10u128.pow(18))` instead of `FixedU128::from_inner(fee)`, so the fixed-point value correctly represents `fee / 10^18` rather than reinterpreting the raw integer as pre-scaled. Additionally, add an explicit invariant check that rejects (or floors to a governance-defined minimum) any computed `fee.remote` of `0` when the underlying wei-denominated fee was non-zero, preventing free/underpriced remote-execution messages from being accepted by `SendMessage::validate`.

## Proof of Concept
The existing test `test_calculate_fees_with_valid_exchange_rate_but_remote_fee_calculated_as_zero` in `bridges/snowbridge/pallets/outbound-queue/src/test.rs` reproduces the bug directly: with `exchange_rate = 1/1`, `fee_per_gas = 1`, `rewards = {local: 1, remote: 1}`, `multiplier = 1`, and `gas_used = 250000`, `OutboundQueue::calculate_fee` returns `fee.remote == 0` despite all pricing parameters being non-zero [6](#0-5) . An external caller can reach this same code path unprivileged by submitting a message with a low-gas `Command` through the public `SendMessage::validate`/`deliver` flow, exposed via `EthereumBlobExporter`/XCM export to Ethereum, to have their message accepted into the outbound queue while paying a `0` remote fee [5](#0-4) .

		/// Calculate total fee in native currency to cover all costs of delivering a message to the
		/// remote destination. See module-level documentation for more details.
		pub(crate) fn calculate_fee(
			gas_used_at_most: u64,
			params: PricingParameters<T::Balance>,
		) -> Fee<T::Balance> {
			// Remote fee in ether
			let fee = Self::calculate_remote_fee(
				gas_used_at_most,
				params.fee_per_gas,
				params.rewards.remote,
			);

			// downcast to u128
			let fee: u128 = fee.try_into().defensive_unwrap_or(u128::MAX);

			// multiply by multiplier and convert to local currency
			let fee = FixedU128::from_inner(fee)
				.saturating_mul(params.multiplier)
				.checked_div(&params.exchange_rate)
				.expect("exchange rate is not zero; qed")
				.into_inner();

			// adjust fixed point to match local currency
			let fee = Self::convert_from_ether_decimals(fee);

			Fee::from((Self::calculate_local_fee(), fee))
		}
