### Title
Non-atomic replay-window Check/Update in `ConnectionState.Decrypt` allows a raced duplicate packet to bypass anti-replay protection - (File: `connection_state.go`)

### Summary
`ConnectionState.Decrypt` in `connection_state.go` splits its anti-replay bookkeeping into two separate critical sections — `window.Check` and `window.Update` — with the AEAD decrypt operation happening in between, unlocked. Because Nebula reads UDP packets across multiple worker queues, an attacker who can duplicate/replay a captured ciphertext packet onto the wire (a classic on-path/replay attacker who holds no certificate at all) can get two copies of the same message routed to two different reader goroutines. Both can pass `Check` before either has called `Update`, letting the same message counter be "seen" as processed twice — the identical accounting-gap failure pattern as the reported `setBeneficiaries`/`beneficiarySwitch` bug, where a stale read of shared state is acted upon before the state is durably updated.

### Finding Description
`Decrypt` performs:
1. Lock `decryptLock`, call `cs.window.Check(l, messageCounter)`, unlock. ` [1](#0-0) `
2. Perform `cs.dKey.DecryptDanger(...)` fully unlocked. ` [2](#0-1) `
3. Lock `decryptLock` again, call `cs.window.Update(l, messageCounter)`, unlock, and only *then* treat the packet as durably recorded. ` [3](#0-2) `

`Check` only inspects the current window state and returns `true` if the counter has not yet been marked; it does not itself mark the bit — that happens only in the later, separately-locked `Update` call. ` [4](#0-3) ` ` [5](#0-4) `

`readOutsidePackets` (invoked per UDP receive worker, parameterized by a queue index `q`) looks up the `HostInfo` purely from the unauthenticated header's `RemoteIndex` field and then calls `hostinfo.ConnectionState.Decrypt` directly — there is no per-packet serialization enforcing that two packets for the same `ConnectionState` are processed one at a time end-to-end. ` [6](#0-5) `

This is structurally identical to the reported smart-contract bug class: an operation (`Decrypt`/`Update`) commits based on a state check (`Check`) that was performed against a stale snapshot, and the intervening window (unlocked AEAD decrypt) allows a second, racing operation referencing the same identifier (the message counter / the beneficiary hash) to be interleaved before the first operation's effect (`Update` / `shareBps` mutation) is durably applied.

### Impact Explanation
If two copies of the same ciphertext (a genuine network-level replay, requiring no valid certificate or handshake participation — only the ability to duplicate a packet on the wire) are dispatched to different reader goroutines, both can pass `Check` and both will successfully decrypt and be delivered to the packet-processing pipeline (`handleOutsideMessagePacket`, lighthouse handling, control messages, etc.) before `Update` marks the counter seen on either path. This defeats the anti-replay guarantee that `ReplayWindow`/`Bits` is meant to provide, allowing traffic replay/duplication to reach the overlay network or control-plane handlers a second time.

### Likelihood Explanation
Exploitability requires only the ability to capture and resend one authenticated data-plane packet from an already-established tunnel and precisely race two worker goroutines — no CA-signed certificate, no valid handshake state, and no privileged position beyond the ability to view/duplicate traffic on the path (the exact class of attacker the analog rules require, matching "nonce/replay handling"). The CHANGELOG entry "Lock replay window updates so concurrent readers can't corrupt it. (#1802)" confirms the project has previously had to patch concurrency bugs in this exact window, but the current `Decrypt` implementation still leaves the Check-then-Update sequence non-atomic across the decrypt call, so the race window persists.

### Recommendation
Hold `decryptLock` across the entire `Check` → `DecryptDanger` → `Update` sequence in `ConnectionState.Decrypt` (and the analogous `VerifyRelay`), so no other goroutine can observe or act on a stale (not-yet-updated) window state for the same `ConnectionState`. Alternatively, serialize per-`ConnectionState` inbound packet processing so that only one packet for a given tunnel is in flight through the decrypt/verify path at a time.

### Proof of Concept
1. Establish a tunnel between two Nebula nodes so a `ConnectionState` with counter `N` is in use.
2. As an on-path attacker, capture a legitimate encrypted `header.Message` packet with counter `N`.
3. Resend two copies of that exact packet to the receiving node's UDP socket in rapid succession, timed so they land on different reader queues (`q` in `readOutsidePackets`).
4. Observe that both copies can pass `cs.window.Check` (since neither has yet called `Update`) and both successfully decrypt via `DecryptDanger`, resulting in duplicate delivery of the same message counter to the packet handler instead of the second copy being rejected as `ErrAlreadySeen`.

// Check returns true if i is within (or way out in front of) the window, and not a replay
func (b *Bits) Check(l *slog.Logger, i uint64) bool {
	// If i is the next number, return true.
	if i > b.current {
		return true
	}

	if b.strictlyWithinWindow(i) {
		return !b.get(i)
	}

	// Not within the window
	if l.Enabled(context.Background(), slog.LevelDebug) {
		l.Debug("rejected a packet (top)", "current", b.current, "incoming", i)
	}
	return false
}

func (b *Bits) Update(l *slog.Logger, i uint64) bool {
	// Fast path: i is the next expected counter. Split out so the function
	// stays small and avoids paying for the slow paths' slog argument-build
	// stack frame on every call. The bit read/test/write is inlined to
	// touch the backing word once.
	if i == b.current+1 {
		pos := i & b.lengthMask
		word := pos >> 6
		mask := uint64(1) << (pos & 63)
		w := b.bits[word]
		if i > b.length && w&mask == 0 {
			b.lostCounter.Inc(1)
		}
		b.bits[word] = w | mask
		b.current = i
		return true
	}
	return b.updateSlow(l, i)
}
