Based on the investigation, I found a directly analogous OOB-read pattern in `PrecompiledContracts.java`, in the helper methods used by TVM precompiled contracts that decode ABI-encoded arrays supplied by an arbitrary caller contract.

### Title
Unchecked offset/length arithmetic in `extractBytesArray`/`extractSigArray` allows out-of-bounds array read from attacker-controlled precompile input - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The radare2 CVE is a classic "attacker-controlled length/offset used to slice a buffer without validating it stays within bounds" bug. The same pattern exists in java-tron's TVM precompiled-contract helpers `extractBytesArray`, `extractSigArray`, and `extractBytes32Array`, which compute a `bytesOffset`/`len` directly from caller-supplied `DataWord` values and then index into the `words[]`/`data[]` arrays with no bound check against the actual buffer size.

### Finding Description
`extractBytesArray` and `extractSigArray` read an item count `len` from `words[offset]` and, for each element, read a `bytesOffset` value from `words[offset + i + 1]` that is fully attacker-controlled (it comes from the precompile's `data` input, i.e., the CALLDATA a contract passes to a TVM precompiled-contract call): [1](#0-0) [2](#0-1) 

These values are used to index into `words[offset + bytesOffset + 1]` and to call `extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE, bytesLen)`, which does `Arrays.copyOfRange(data, offset, offset + len)`: [3](#0-2) 

Neither `bytesOffset`, `bytesLen`, nor the derived `offset` used to index `words[]` is validated against `words.length` or `data.length` before use, so a crafted precompile call payload (with an oversized or negative-appearing offset/length after `intValueSafe()` conversion) can push these indices outside the actual array bounds.

### Impact Explanation
`words[]` indexing beyond its bounds throws an uncaught `ArrayIndexOutOfBoundsException`, and `Arrays.copyOfRange` with an out-of-range `from` similarly throws `ArrayIndexOutOfBoundsException`. This is functionally the same defect class as CVE-2018-11381 (crafted input causing an out-of-bounds read leading to a crash), but here the "crafted binary" is a transaction's TVM call data feeding a precompiled contract that any account can invoke by deploying/calling a contract that performs a `CALL`/`STATICCALL` to the relevant precompile address. Depending on how the call is wrapped by the VM's exception handling, this can surface as an uncaught exception that terminates energy-metered execution abnormally or, if not properly caught by the surrounding TVM dispatch code, could propagate and disrupt block/transaction processing on the node — a reachable, low-cost DoS vector triggerable by any unprivileged contract caller.

### Likelihood Explanation
Any account can deploy a trivial contract that calls a TVM precompiled address with a malformed ABI-encoded payload (bad "offset"/"length" words), making this trivially reachable from an anonymous transaction broadcaster/contract deployer with no special privilege — matching the "single signed transaction, contract call" reachability requirement.

### Recommendation
Add explicit bounds checks in `extractBytesArray`, `extractSigArray`, and `extractBytes32Array` verifying that computed offsets/lengths (`bytesOffset`, `bytesLen`, and any index used against `words[]`) stay within `words.length` and `data.length` before use, returning an empty/failure result (as already done for the `offset > words.length - 1` case) instead of allowing an unchecked array read.

### Proof of Concept
I could not fully confirm, within the available indexed context, which specific precompiled-contract class (e.g., `ValidateMultiSign`/`BatchValidateSign`) calls `extractBytesArray`/`extractSigArray` and whether the surrounding TVM dispatch code (e.g., in `Program.java`'s precompiled-contract invocation path) catches generic `RuntimeException`/`ArrayIndexOutOfBoundsException` before it can crash node processing. I was not able to locate the exact caller site or the `execute()`-wrapping exception handler in the indexed snippets due to index size limits. **A Devin session with full repository access would be needed to trace the exact precompile class that invokes these helper methods and to confirm whether the TVM's precompile-call wrapper swallows `ArrayIndexOutOfBoundsException`** (which would downgrade this from a crash to a benign revert) before this can be treated as confirmed proof of impact.

    if (offset > words.length - 1) {

    }
