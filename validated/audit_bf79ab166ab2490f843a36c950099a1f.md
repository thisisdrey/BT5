### Title
Unbounded full-scan of the TRC10 asset list on unauthenticated Wallet query paths - ([File: framework/src/main/java/org/tron/core/Wallet.java])

### Summary
`AssetIssueStore.getAllAssetIssues()` loads every TRC10 asset record from the database into an in-memory `List` via a full iterator scan, with no size cap. Several `Wallet` methods that back unauthenticated HTTP/gRPC/JSON-RPC endpoints call this unbounded method instead of the paginated variant, so their cost grows linearly (or worse, since some also apply a `.stream().filter()` pass) with the total number of TRC10 assets ever issued on chain — a value any account can increase by broadcasting `AssetIssueContract` transactions. [1](#0-0) 

### Finding Description
`getAllAssetIssues()` performs a full DB iteration with no limit: [2](#0-1) 

By contrast, the store also exposes a properly bounded `getAssetIssuesPaginated` that caps `limit` at `ASSET_ISSUE_COUNT_LIMIT_MAX`: [3](#0-2) 

However, `Wallet.getAssetIssueList()` (no offset/limit), `getAssetIssueByAccount()`, `getAssetIssueByName()` (same-token-name-open branch), and `getAssetIssueListByName()` all call the unbounded `getAllAssetIssues()` and then iterate/filter the entire result set on every call: [4](#0-3) [5](#0-4) [6](#0-5) 

These methods are wired directly into unauthenticated node-facing entry points: the HTTP servlet `GetAssetIssueListServlet.doGet()` calls `wallet.getAssetIssueList()` unconditionally on every request [7](#0-6) , and the gRPC `WalletSolidityApi.getAssetIssueList` / `WalletApi.getAssetIssueList` handlers do the same [8](#0-7) [9](#0-8) . Equivalent servlets exist for `GetAssetIssueByAccountServlet` and `GetAssetIssueListByNameServlet`.

The total number of TRC10 assets is directly controlled by unprivileged callers: `AssetIssueActuator.execute()` allows any account to issue a new asset for a fee, incrementing `tokenIdNum` and persisting a new `AssetIssueCapsule` with no cap on the total number of distinct assets that can exist system-wide. [10](#0-9) 

This is directly analogous to the reported bug class: an array/list-based collection of "assets" that (a) any actor can grow without an upper bound via normal, permissionless transactions, and (b) is repeatedly scanned in full by a hot code path, producing growing, unbounded work per invocation.

### Impact Explanation
As the number of issued TRC10 assets grows (trivially inflatable by an attacker willing to pay the per-asset issuance fee many times, e.g. via automated scripting), every call to `getAssetIssueList`, `getAssetIssueByAccount`, `getAssetIssueByName` (same-token-name-open path), and `getAssetIssueListByName` becomes proportionally more expensive: full deserialization of every `AssetIssueCapsule` in the DB, followed by a stream/filter pass and per-item `BandwidthProcessor.updateUsage()` calls. Because these endpoints are exposed on the node's public HTTP/gRPC surface with no pagination and no per-request cap, repeated concurrent requests to them can consume disproportionate CPU/memory on full nodes and SolidityNode/PBFT read-replicas serving these APIs, degrading or denying service to other legitimate API clients on that node. This matches the "no longer able to serve an API" criterion.

### Likelihood Explanation
Likelihood is high for the "attacker inflates the dataset" step: issuing a TRC10 asset requires only paying `AssetIssueFee` from an ordinary account, is fully permissionless, and is rate-limited only by the attacker's own TRX balance and bandwidth/energy, not by any protocol-level cap on total distinct assets. Once the dataset is large, triggering the unbounded scan requires nothing more than sending unauthenticated `GetAssetIssueList` (or `GetAssetIssueByAccount`/`GetAssetIssueListByName`) HTTP/gRPC requests, which any anonymous API client can do. The existing `RateLimiterServlet` base class only rate-limits per-caller request rate, not per-request cost, so it does not mitigate the asymptotic cost growth of a single request.

### Recommendation
- Make `Wallet.getAssetIssueList()` (no-arg) either delegate to the bounded/paginated store method with a hard-coded maximum, or require callers to always supply `offset`/`limit` bounded by `ASSET_ISSUE_COUNT_LIMIT_MAX`.
- Apply the same `ASSET_ISSUE_COUNT_LIMIT_MAX`-style bound to `getAssetIssueByAccount()` and `getAssetIssueListByName()`, or replace their full-list-then-filter pattern with a targeted, indexed lookup (e.g., keyed by owner address or name) rather than scanning `getAllAssetIssues()`.
- Consider adding a protocol-level maintained index (e.g., name→id, owner→ids) in `AssetIssueStore`/`AssetIssueV2Store` to avoid O(n) scans for name/owner-based queries entirely.

### Proof of Concept
1. From any funded account, repeatedly broadcast `AssetIssueContract` transactions (via `AssetIssueActuator`) to create a very large number of distinct TRC10 assets — each such transaction is a normal, unprivileged transaction gated only by the `AssetIssueFee`. [10](#0-9) 
2. Once the `asset-issue`/`asset-issue-v2` store contains a large number of entries, send repeated unauthenticated `GET /wallet/getassetissuelist` HTTP requests (or the equivalent gRPC `getAssetIssueList` call) to a full node. [7](#0-6) 
3. Each request forces the node to run `getAllAssetIssues()` (full DB iteration + deserialization of every asset) and then `updateUsage()` per asset, with cost scaling linearly with the attacker-controlled asset count and no pagination cap — repeated/concurrent calls can be used to degrade the node's ability to serve this and other API requests.

  private List<AssetIssueCapsule> getAssetIssuesPaginated(List<AssetIssueCapsule> assetIssueList,
      long offset, long limit) {
    if (limit < 0 || offset < 0) {
      return null;
    }

    if (assetIssueList.size() <= offset) {
      return null;
    }
    assetIssueList.sort((o1, o2) -> {
      if (o1.getName() != o2.getName()) {
        return o1.getName().toStringUtf8().compareTo(o2.getName().toStringUtf8());
      }
      return Long.compare(o1.getOrder(), o2.getOrder());
    });
    limit = limit > ASSET_ISSUE_COUNT_LIMIT_MAX ? ASSET_ISSUE_COUNT_LIMIT_MAX : limit;
    long end = offset + limit;
    end = end > assetIssueList.size() ? assetIssueList.size() : end;
    return assetIssueList.subList((int) offset, (int) end);
  }

  public List<AssetIssueCapsule> getAssetIssuesPaginated(long offset, long limit) {
    return getAssetIssuesPaginated(getAllAssetIssues(), offset, limit);
  }

  public AssetIssueList getAssetIssueByAccount(ByteString accountAddress) {

      return null;
    }

    List<AssetIssueCapsule> assetIssueCapsuleList =
        getAssetIssueStoreFinal(chainBaseManager.getDynamicPropertiesStore(),
            chainBaseManager.getAssetIssueStore(),

    BandwidthProcessor processor = new BandwidthProcessor(chainBaseManager);
    AssetIssueList.Builder builder = AssetIssueList.newBuilder();

        .filter(assetIssueCapsule -> assetIssueCapsule.getOwnerAddress().equals(accountAddress))
        .forEach(
            issueCapsule -> {
              processor.updateUsage(issueCapsule);
              builder.addAssetIssue(issueCapsule.getInstance());
            });
