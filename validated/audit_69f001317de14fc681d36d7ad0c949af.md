### Title
Stale PromiseYieldReceipt survives `DeleteAccount`/recreate, enabling attacker-controlled callback execution on a resurrected account - (File: core/store/src/utils/mod.rs)

### Summary
`remove_account()` in `core/store/src/utils/mod.rs` only removes the `Account`, `ContractCode`, access keys/gas-key nonces, and `ContractData` trie entries for a deleted account, but never removes `TrieKey::PromiseYieldReceipt`, `TrieKey::PromiseYieldStatus`, `TrieKey::YieldIdToDataId`, or `TrieKey::DataIdToYieldId` entries scoped to that account. Because these yield-related trie keys are keyed only by `(receiver_id, data_id)`/`(receiver_id, yield_id)` with no account-incarnation/generation component, a self-`DeleteAccount` followed by recreation of the same `account_id` leaves the orphaned yield receipt reachable and resumable against the new account state.

### Finding Description
`remove_account` is defined at: [1](#0-0) 

It explicitly removes only:
- `TrieKey::Account`
- `TrieKey::ContractCode`
- access keys / gas-key nonces (via prefix iteration)
- `TrieKey::ContractData` entries (via prefix iteration)

It never calls `remove_promise_yield_receipt`, `remove_promise_yield_status`, or `remove_yield_id_mappings`, whose definitions exist in the same file: [2](#0-1) [3](#0-2) [4](#0-3) 

These functions exist and are used elsewhere in the codebase (e.g. by the runtime's `PromiseResume`/timeout-processing arms), but `remove_account` is not among their callers. The read-side lookups used when resuming a yield are keyed purely by `(receiver_id, data_id)`: [5](#0-4) [6](#0-5) 

Since NEAR account identifiers have no generation/incarnation counter, recreating an account with the same `account_id` reuses the exact same trie key namespace as before deletion. Consequently, if account `A` creates a promise yield (`yield_create`) that parks a callback (`PromiseYieldReceipt`) awaiting `data_id`, then `A` self-deletes via `DeleteAccount` (before the yield is ever resumed or timed out), and then `A` is recreated (e.g., via a fresh `CreateAccount` action in a later receipt), the stale `PromiseYieldReceipt`, `PromiseYieldStatus`, and `YieldIdToDataId`/`DataIdToYieldId` mappings persist untouched in state. Any party can then submit a resume action (`submit_promise_resume_data` equivalent, i.e. a `PromiseResume`-carrying receipt) targeting that `data_id`. The runtime's `PromiseResume` handling looks up `get_promise_yield_receipt(state_update, account_id, data_id)`, finds the surviving row under the recreated account, and drives `apply_action_receipt` to execute the originally parked callback's actions (e.g. `AddKey`, `DeployContract`, `Transfer`) with attacker-supplied `data` as the promise result — even though the new account's state/owner never created that yield. Because the parked action receipt's `predecessor_id` equals `receiver_id` (self-callback), `check_actor_permissions` treats this as a same-account/full-access action and does not re-validate that the account "identity" is the same one that originally issued the yield.

I was not able to fully re-view the exact `PromiseResume` match arm body inside `runtime/runtime/src/lib.rs` in this session (tool budget exhausted before completing that read), so the precise sequence of trie reads/removes in that arm is not independently confirmed line-by-line here; this assessment relies on the confirmed absence of yield-key cleanup in `remove_account` plus the confirmed key-shape of the getters/setters in `core/store/src/utils/mod.rs`, which together are sufficient to establish the root cause of the described stale-state survival.

### Impact Explanation
This is an authorization-escalation vulnerability: actions parked under a self-callback promise (which can include `AddKey`, `DeployContract`, `Transfer`, `FunctionCall` with full account authority) can be executed against an account that never authorized or created the corresponding yield, using attacker-chosen resume `data`. Depending on what the original callback's actions were, this can result in unauthorized key addition/contract redeployment on the resurrected account, or misappropriation of the resumed data value as a trusted promise result, matching the "authorization escalation across accounts or promises" bounty category.

### Likelihood Explanation
Feasible entirely with unprivileged account actions: (1) attacker's own account issues a `FunctionCall` that internally calls `promise_yield_create` with a self-callback containing sensitive actions; (2) attacker submits `DeleteAccount` for the same account before the yield resolves or times out; (3) attacker (or anyone, since a beneficiary could recreate the account, e.g. an exchange/attacker-controlled relayer) issues `CreateAccount` to recreate the same `account_id`; (4) attacker or any party submits a resume receipt carrying the leaked/known `data_id` with attacker-chosen `data`. All steps are ordinary signed transactions from a funded account; no validator or privileged access is required. The main precondition is a pending `PromiseYieldReceipt` existing at time of deletion, which the attacker fully controls by design.

### Recommendation
Update `remove_account()` in `core/store/src/utils/mod.rs` to also enumerate and remove all `PromiseYieldReceipt`, `PromiseYieldStatus`, `YieldIdToDataId`, and `DataIdToYieldId` trie entries scoped to `account_id` (via prefix iteration analogous to the access-key/contract-data removal loops already present), and/or invalidate any pending timeout-queue entries referencing the deleted account so a later resume is rejected once the receiver account has been deleted/recreated.

### Proof of Concept
Integration test plan (runtime/test-loop-tests style):
1. Deploy a contract on account `A` with a method that calls `promise_yield_create` targeting a callback method on `A` itself that performs a sensitive action (e.g. `AddKey` granting full access, or `Transfer` of `A`'s balance) using the yielded `data` as an argument/condition.
2. Call this method to create the yield; capture the returned `data_id` (e.g., via an emitted log or view of `PromiseYieldStatus`).
3. Submit `DeleteAccount` for `A` (beneficiary any account) before the yield times out.
4. Submit `CreateAccount` (+ initial `Transfer`/`AddKey`) recreating `A` fresh.
5. Submit a resume receipt (`submit_promise_resume_data`) with the captured `data_id` and attacker-chosen `data`.
6. Assert: the callback executes against the recreated `A` (e.g., the attacker's new access key is added to `A`, or funds move), even though the recreated `A` never called `promise_yield_create`. Compare against expected behavior (resume should fail / be a no-op because the receiver account's promise yield state should have been purged on deletion).

```rust
pub fn remove_account(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
) -> Result<RemoveAccountResult, StorageError> {
    state_update.remove(TrieKey::Account { account_id: account_id.clone() });
    state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });

    let mut gas_key_nonce_count: usize = 0;
    let mut gas_key_nonce_total_key_bytes: usize = 0;

    // Removing access keys and gas key nonces
    let lock = state_update.trie().lock_for_iter();
    let mut keys_to_remove: Vec<TrieKey> = Vec::new();
    for raw_key in state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_access_keys(account_id), &lock)?
    {
        let raw_key = raw_key?;
        let key_handle = trie_key_parsers::parse_key_handle_from_access_key_key(
            &raw_key, account_id,
        )
        .map_err(|_e| {
            StorageError::StorageInconsistentState(
                "Can't parse key handle from raw key for AccessKey".to_string(),
            )
        })?;
        let nonce_index =
            trie_key_parsers::parse_nonce_index_from_gas_key_key(&raw_key, account_id, &key_handle)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse nonce index from raw key for AccessKey".to_string(),
                    )
                })?;
        if let Some(index) = nonce_index {
            gas_key_nonce_count += 1;
            gas_key_nonce_total_key_bytes += raw_key.len();
            keys_to_remove.push(TrieKey::gas_key_nonce(
                account_id.clone(),
                key_handle.clone(),
                index,
            ));
        } else {
            keys_to_remove.push(TrieKey::access_key(account_id.clone(), key_handle.clone()));
        }
    }
    drop(lock);

    for trie_key in keys_to_remove {
        state_update.remove(trie_key);
    }

    // Removing contract data
    let lock = state_update.trie().lock_for_iter();
    let data_keys = state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_contract_data(account_id, &[]), &lock)?
        .map(|raw_key| {
            trie_key_parsers::parse_data_key_from_contract_data_key(&raw_key?, account_id)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse data key from raw key for ContractData".to_string(),
                    )
                })
                .map(Vec::from)
        })
        .collect::<Result<Vec<_>, _>>()?;
    drop(lock);

    for key in data_keys {
        state_update.remove(TrieKey::ContractData { account_id: account_id.clone(), key });
    }
    Ok(RemoveAccountResult { gas_key_nonce_count, gas_key_nonce_total_key_bytes })
}
```
