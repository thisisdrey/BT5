### Title
Missing re-fractionalization guard in `fractionalize` allows the same NFT to back multiple independent fungible assets - (File: substrate/frame/nft-fractionalization/src/lib.rs)

### Summary
`fractionalize` never checks whether the target `(nft_collection_id, nft_id)` is already present in `NftToAsset`, and it never transfers the NFT out of the original owner's account — it only calls `disable_transfer` on it [1](#0-0) . Because the NFT owner is unchanged after a successful `fractionalize`, the same owner (or a colluding "attacker" acting as the original owner/beneficiary of multiple fraudulent asset issuances) can call `fractionalize` again on the very same NFT with a fresh `asset_id`, producing a second independently-minted fungible asset backed by the same underlying NFT, and silently overwriting the storage record of the first fractionalization.

### Finding Description
In `fractionalize`, the origin-ownership check only verifies that the caller is the current owner of the NFT [2](#0-1) . There is no check like `ensure!(!NftToAsset::<T>::contains_key((nft_collection_id, nft_id)), Error::<T>::AlreadyFractionalized)`. The subsequent steps — `do_lock_nft` (disables transfer flag only, does not move ownership), `do_create_asset`, `do_mint_asset`, `do_set_metadata` — all operate purely against the caller-supplied fresh `asset_id`, and finish by unconditionally overwriting the `NftToAsset` entry for that NFT key: [3](#0-2) 

Since `do_lock_nft` only calls `T::Nfts::disable_transfer` and never transfers the NFT to the pallet's sovereign account, the original owner still passes the `nft_owner == who` check on a second call. This lets the owner:
1. Call `fractionalize(nft, asset_id=A, beneficiary=victim_or_market)` → mints asset `A`, deposit `D1` held, `NftToAsset[(coll,nft)] = {asset: A, ...}`.
2. Call `fractionalize(nft, asset_id=B, beneficiary=attacker)` again on the same NFT → a second independent hold `D2` is taken, asset `B` is created/minted, and `NftToAsset[(coll,nft)]` is overwritten to `{asset: B, ...}`, discarding the record for `A`.

At this point, asset `A` is a fully transferable fungible token that markets/holders believe is redeemable for the underlying NFT, but the on-chain bookkeeping now only recognizes asset `B` as the redeemable claim. `unify` checks `details.asset == asset_id` [4](#0-3) , so only holders of `B` can ever redeem the NFT; holders of `A` are permanently locked out, and the deposit `D1` associated with the discarded entry can never be released via `unify` since that record is gone.

### Impact Explanation
This breaks the "successful call leaves a coherent state for downstream public consumers" invariant: `fractionalize` returns `Ok(())` and emits `NftFractionalized`, giving the appearance that asset `A` is validly backed, while the pallet's single-slot `NftToAsset` map can only ever honor the most recently created asset. This enables:
- Unbacked/duplicate mint: two (or more) independent fungible assets appear to represent claims on one NFT.
- Unauthorized NFT redemption/rug: the attacker/owner can redeem the NFT using asset `B` (which they fully control/minted to themselves) after having sold/distributed asset `A` to third parties, leaving `A` worthless — a wrongful-beneficiary/asset theft scenario.
- Permanent fund lock: the deposit tied to the overwritten `NftToAsset` entry can never be released through `unify` since the entry is gone.

### Likelihood Explanation
The precondition is simply that `do_lock_nft`/`disable_transfer` does not transfer NFT ownership away from the caller and is idempotent when called on an already-locked item (typical `pallet-nfts` behavior — it just flips a system attribute rather than checking existing lock state or failing). I was not able to fully verify the exact `disable_transfer` implementation semantics (e.g., whether it errors when the item is already non-transferable) before running out of tool calls in `substrate/frame/nfts/src/impl_nonfungibles.rs`; if it does error on a second call, this exact exploit path would be blocked, and the report should be treated as unconfirmed pending that check. Assuming idempotent (non-erroring) `disable_transfer`, the exploit requires only a single account performing two ordinary signed extrinsic calls — no privileged access needed.

### Recommendation
Add an explicit guard at the top of `fractionalize` rejecting re-fractionalization of an NFT that already has an `NftToAsset` entry, e.g. `ensure!(!NftToAsset::<T>::contains_key((nft_collection_id, nft_id)), Error::<T>::NftAlreadyFractionalized);`. Additionally, consider transferring the NFT into the pallet's sovereign account (rather than merely disabling transfer while leaving it with the original owner) so that a second `fractionalize` call would legitimately fail the ownership check.

### Proof of Concept
1. Owner `O` owns NFT `(C, N)`.
2. `O` calls `fractionalize(C, N, asset_id=A, beneficiary=O, fractions=100)` → succeeds; `NftToAsset[(C,N)] = {asset: A, fractions: 100, asset_creator: O, deposit: D}`; deposit `D1` held from `O`.
3. `O` sells/transfers asset `A` tokens to victims on the open market as "NFT-backed fractions."
4. `O` calls `fractionalize(C, N, asset_id=B, beneficiary=O, fractions=1)` again on the same `(C, N)` — the ownership check still passes because `T::Nfts::owner` still returns `O` (never transferred to the pallet); a new deposit `D2` is held; `NftToAsset[(C,N)]` is overwritten to `{asset: B, fractions: 1, asset_creator: O, deposit: D2}`, losing the `A` record and its deposit `D1`.
5. `O` calls `unify(C, N, asset_id=B, beneficiary=O)`, burning its own `B` tokens and reclaiming the NFT — asset `A` holders are left with unredeemable tokens, and `D1` is permanently stuck (no longer referenced by any storage entry).

Note: this PoC's feasibility depends on the exact behavior of `T::Nfts::disable_transfer`/`owner` for an item already marked non-transferable, which I could not fully confirm within the available tool calls — recommend a Devin session with full repo access to verify `substrate/frame/nfts/src/impl_nonfungibles.rs`'s `disable_transfer` semantics before treating this as confirmed exploitable.
