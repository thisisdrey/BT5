Audit Report

## Title
`process_delivery_receipt` pays relayer reward and settles pending order without checking the on-chain delivery `success` flag - ([File: bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs])

## Summary
`snowbridge-pallet-outbound-queue-v2::Pallet::process_delivery_receipt` decodes a `DeliveryReceipt` containing a `success: bool` field taken directly from the Ethereum `InboundMessageDispatched` event, but never reads or branches on that field before paying the relayer reward and removing the `PendingOrder`. As a result, a relayer can be paid the full fee — and the pending order permanently settled — even when the underlying message dispatch failed on Ethereum.

## Finding Description
`do_process_message` creates and stores a `PendingOrder { nonce, fee, block_number }` keyed by `nonce` when a message is queued for outbound delivery [1](#0-0) . The Ethereum Gateway contract emits `InboundMessageDispatched(nonce, topic, success, reward_address)`, and this is decoded into a `DeliveryReceipt` struct that explicitly carries `success: bool` [2](#0-1) , populated verbatim from the on-chain event in the `TryFrom<&Log>` implementation [3](#0-2) .

The public extrinsic `submit_delivery_receipt` verifies the event log via `T::Verifier::verify`, decodes it into `DeliveryReceipt`, and forwards it directly to `process_delivery_receipt` without any success check. `process_delivery_receipt` itself only validates the gateway address, looks up the `PendingOrder` by nonce, and unconditionally calls `T::RewardPayment::register_reward` for `order.fee` whenever `order.fee > 0`, then removes the order and emits `MessageDelivered` — `receipt.success` is never referenced [4](#0-3) . A search of the pallet source confirms there is no other guard anywhere that inspects `success` before settlement.

## Impact Explanation
This is a public underpriced-work / duplicate-settlement issue within the allowed impact gate: BridgeHub pays the relayer reward (`order.fee`) and irrevocably deletes the `PendingOrder` for messages whose Ethereum-side execution reverted or otherwise failed (`success = false`), exactly as it would for genuinely successful deliveries. This breaks the invariant that "message queues, bridge markers, receipts, and payout state must only advance after decode, dispatch, execution, and settlement succeed atomically." Because the order is removed unconditionally, there is no mechanism to retry, refund, or otherwise reconcile the failed dispatch, allowing the reward pool to be drained over repeated failed deliveries.

## Likelihood Explanation
Any signed account holding a valid proof for a real `InboundMessageDispatched` event (with `success = false`) can call the permissionless `submit_delivery_receipt` extrinsic and receive the reward — no privileged role, governance action, or compromised infrastructure is required. `success: false` outcomes (reverts, out-of-gas, execution failures) are a normal, expected occurrence on the Ethereum side, making this a deterministic and repeatable path rather than a contrived edge case.

## Recommendation
In `process_delivery_receipt`, branch on `receipt.success` before rewarding: only call `T::RewardPayment::register_reward` and remove the `PendingOrder` when `receipt.success == true`; for `false`, emit a distinct failure event (e.g., `MessageDeliveryFailed { nonce }`) and define explicit handling for the `PendingOrder` (retry, expiry-based refund, or an auditable removal without payout) so fees are never paid for unsuccessful executions.

## Proof of Concept
1. A message is enqueued via `do_process_message`, creating `PendingOrders[nonce] = PendingOrder { nonce, fee: F, block_number }` [5](#0-4) .
2. The corresponding command dispatch reverts on Ethereum, causing the Gateway to emit `InboundMessageDispatched(nonce, topic, success=false, reward_address)`.
3. Any signed relayer account gathers the standard event/receipt proof and calls `submit_delivery_receipt(origin, EventProof { event_log, proof })` [6](#0-5) .
4. Verification succeeds, `DeliveryReceipt::try_from` decodes `success: false` correctly, but `process_delivery_receipt` never reads it; it registers the reward for `order.fee` and removes the pending order regardless [7](#0-6) .
5. Result: the relayer receives fee `F` and the order is permanently settled despite the failed dispatch — repeatable for every failed delivery submitted.
