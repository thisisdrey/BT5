### Title
Excessive memory usage via unbounded `eth_newFilter` log-result queue - (File: `framework/src/main/java/org/tron/core/services/jsonrpc/filters/LogFilterAndResult.java`)

### Summary
`TronJsonRpcImpl.newFilter` (`eth_newFilter`) lets any anonymous JSON-RPC client register a persistent log filter backed by an **unbounded** `LinkedBlockingQueue`. As new blocks are produced, every matching log element is unconditionally appended to that queue with no size cap, and the queue is only drained when the client calls `eth_getFilterChanges`/`eth_getFilterLogs`. A client that creates a wide-matching filter and simply never polls it forces the node to buffer an ever-growing, unbounded amount of log data in memory for the full 5-minute filter lifetime (reset on every poll), which is the same "termination condition never reached / consumer doesn't drain fast enough" memory-exhaustion pattern described in the tokio-rustls advisory.

### Finding Description
- `eth_newFilter` creates a `LogFilterAndResult`, whose queue is instantiated with no bound: `result = new LinkedBlockingQueue<>();` [1](#0-0) 
- On every produced block, `Manager.postLogsFilter` pushes a `LogsFilterCapsule` to `filterCapsuleQueue`, which is consumed by `TronJsonRpcImpl.handleLogsFilter` for every live filter in `eventFilter2ResultFull`/`eventFilter2ResultSolidity`. [2](#0-1) 
- Matching log elements are appended to the filter's result queue unconditionally, with **no cap on the queue length**: `logFilterAndResult.getResult().addAll(localResults);` [3](#0-2) 
- The queue is only drained (`popAll()` -> `drainTo`) when the client calls `eth_getFilterChanges`/`eth_getFilterLogs`; the wait/limit condition for consuming events is entirely client-controlled, mirroring the read-vs-process disconnect in the tokio-rustls bug. [4](#0-3) 
- `maxLogFilterNum` (default 20000, from `reference.conf`) only caps the *number of filters*, not the size of each filter's internal buffer, so each of up to 20000 concurrent filters can independently accumulate an unbounded amount of `LogFilterElement` data. [5](#0-4) 
- A filter is only removed on expiry check, which happens lazily inside `processLogFilterEntry` during the next `handleLogsFilter` dispatch, and expiry (`EXPIRE_SECONDS = 5*60`) is refreshed on every poll — an attacker can poll with a large `limit`-less call just often enough to keep the filter alive while never fully draining a queue that fills faster than it is read. [6](#0-5) 
- `eth_newFilter` explicitly skips the block-range cap enforced elsewhere (`checkBlockRange=false`), permitting an open-ended `toBlock=latest` filter with no address/topic restriction, i.e. a filter that matches *every* future log on the chain. [7](#0-6) 

### Impact Explanation
This is reachable from any unauthenticated JSON-RPC client (`node.jsonrpc.httpFullNodeEnable`), one of the explicitly in-scope query paths into `TronJsonRpcImpl`. By registering a broad, unfiltered `eth_newFilter` subscription and not draining it, an attacker forces the node to retain all matching log elements produced chain-wide for the life of the filter. Repeating this across many filter IDs (up to `maxLogFilterNum`, default 20000) multiplies memory pressure. Since logs are generated continuously by ordinary contract activity (which any user can also amplify by emitting events), this can drive the node to OOM, resulting in a node crash / API service outage — matching the "node crash or halt" / "API the node can no longer serve" acceptance criteria.

### Likelihood Explanation
High likelihood: `eth_newFilter` and `eth_getFilterChanges` are unauthenticated, publicly exposed JSON-RPC methods requiring no stake, signed transaction, or special privilege — only network access to the JSON-RPC endpoint. Creating a filter with empty address/topics and `toBlock=latest` is the default/simplest usage pattern, and simply not calling `eth_getFilterChanges` (or calling it only occasionally while the queue fills faster than it drains) is trivial to automate.

### Recommendation
Bound the per-filter result queue (e.g., cap `LogFilterAndResult`'s queue size and drop/evict or reject further inserts and mark the filter as `TOO_MANY_RESULTS`, similar to the existing `JsonRpcTooManyResultException` used for `eth_getLogs`/`eth_getFilterLogs`), and/or track cumulative queued log element count against `jsonRpcMaxLogFilterNum` per filter rather than only capping filter count. Consider also shortening/expiring filters more aggressively when they accumulate unread data past a threshold, and enforcing the same block-range cap for `eth_newFilter` as for `eth_getLogs`.

### Proof of Concept
1. Enable JSON-RPC (`node.jsonrpc.httpFullNodeEnable = true`, default port 8545).
2. As an anonymous client, call:
   ```
   POST /jsonrpc
   {"jsonrpc":"2.0","id":1,"method":"eth_newFilter","params":[{"fromBlock":"latest","toBlock":"latest"}]}
   ```
   (no `address`/`topics` supplied, so it matches every log on every future block).
3. Never call `eth_getFilterChanges`/`eth_getFilterLogs` for this filter ID (or drain it slower than logs are produced by driving contract event traffic, e.g. broadcasting many trigger-emitting contract calls).
4. Repeat step 2 up to `jsonRpcMaxLogFilterNum` (default 20000) times with distinct filter requests.
5. Observe heap growth in `eventFilter2ResultFull`'s `LogFilterAndResult.result` queues as `handleLogsFilter` keeps calling `result.add()`/`addAll()` with no bound, until the node experiences memory exhaustion.

    Map<String, LogFilterAndResult> eventFilterMap;

    if (logsFilterCapsule.isSolidified()) {

    } else {
