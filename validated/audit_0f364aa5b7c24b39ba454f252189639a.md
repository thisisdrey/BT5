### Title
Self-destructed account with non-zero balance retains stale nonce/code/storage-root instead of being reset — (File: `core/state/statedb.go`)

### Summary
In `finaliseAmsterdam`, when a self-destructed account still holds a non-zero balance, the code is supposed to implement the documented EIP-8264 semantics ("nonce reset to 0, balance unchanged, code cleared, all storage cleared"). Instead it constructs the replacement object from the account's *pre-block origin data*, so nonce, code hash and storage root are not reset at all.

### Finding Description [1](#0-0) 

```go
case obj.selfDestructed:
    // EIP-8264: accounts marked for self-destruction, instead of
    // being deleted, are modified as follows:
    // - nonce is reset to 0,
    // - balance is unchanged,
    // - code is cleared,
    // - all storage is cleared
    if !obj.Balance().IsZero() {
        o := newObject(s, obj.address, obj.origin)
        o.setBalance(new(uint256.Int).Set(obj.Balance()))
        s.setStateObject(o)
        s.markUpdate(addr)
    } else {
        delete(s.stateObjects, obj.address)
        s.markDelete(addr)
        if _, ok := s.stateObjectsDestruct[obj.address]; !ok {
            s.stateObjectsDestruct[obj.address] = obj
        }
    }
```

`newObject` copies the passed account (`acct`) verbatim into `data`: [2](#0-1) 

```go

	if acct == nil {
		acct = types.NewEmptyStateAccount()
	}
	return &stateObject{
		db:                 db,
		address:            address,
		origin:             origin,
		data:               *acct,
		...
```

Since `obj.origin` holds the account's data as it existed *before this block* (pre-existing nonce, non-empty `CodeHash`, non-empty storage `Root` for any pre-existing contract), the newly-created object `o` inherits those stale values. `o.setBalance(...)` only overwrites the balance field; nonce, code hash and storage root are left exactly as they were before the self-destruct, contradicting the comment's stated rule (nonce=0, code cleared, storage cleared).

Consequences:
- `o.data.Nonce` stays at the pre-block nonce instead of 0.
- `o.data.CodeHash` stays at the pre-block code hash instead of `EmptyCodeHash`, so `Code()`/`CodeSize()` for this address will keep returning the *old* contract code after a "self-destruct".
- `o.data.Root` stays at the pre-block storage root instead of the empty root. Because this account is *not* added to `s.stateObjectsDestruct` (that only happens in the balance-zero delete branch), the storage-clearing path is skipped and `GetCommittedState`'s destructed-account short-circuit is never engaged for this address, so all of the account's pre-existing storage slots remain readable/committed.
- At commit time, `updateStateObject` persists `obj.data` (still carrying the stale nonce/codehash/root) directly into the account trie: [3](#0-2) 

This breaks the state-root equality invariant: the account's on-chain metadata after a value-carrying self-destruct differs from what the specification (as literally documented in the very same code comment) requires.

### Impact Explanation
This is a state-transition/consensus correctness bug under the `rules.IsAmsterdam` code path (`finaliseAmsterdam`). Any block containing a transaction that self-destructs a contract with non-zero balance and non-empty code/storage/nonce, evaluated under this ruleset, would commit a `stateRoot` that diverges from a correct implementation of the described semantics — a persisted account that still exposes its old code, old nonce, and old storage after being marked self-destructed. This is a High/Critical-class divergence per the stated impact categories (stateRoot/persistence no longer matches the intended executed semantics), though it is scoped to the (not-yet-mainnet-active) Amsterdam ruleset, which limits present-day exploitability until/unless that fork activates.

### Likelihood Explanation
The trigger is trivial and fully attacker-controlled: any `SELFDESTRUCT` executed by a contract that (a) still holds native balance immediately prior to finalisation and (b) has non-zero nonce, non-empty code, or non-empty storage will hit this exact branch every time `finaliseAmsterdam` runs under Amsterdam rules. No special preconditions beyond having such a contract are needed.

### Recommendation
When re-creating the surviving self-destructed-with-balance object, do not seed it from `obj.origin`. Instead create it from an empty account and only carry over the balance, e.g.:
```go
o := newObject(s, obj.address, nil)
o.setBalance(new(uint256.Int).Set(obj.Balance()))
```
and ensure the address is also registered in `s.stateObjectsDestruct` so that its storage trie is properly cleared/committed, matching the nonce=0 / code-cleared / storage-cleared semantics that the comment documents.

### Proof of Concept
1. Deploy a contract `C` that has non-zero nonce (e.g., it has previously performed a `CREATE`), non-empty code, and at least one non-zero storage slot, and that holds a non-zero ETH balance.
2. Under `rules.IsAmsterdam`, execute a transaction that triggers `SELFDESTRUCT` on `C`, leaving its balance non-zero (e.g. self-destruct sets beneficiary to itself, or another call re-funds it in the same block prior to finalisation).
3. Call `Finalise`/`IntermediateRoot`/`Commit`. Read back the account via `StateDB.GetNonce(C)`, `GetCode(C)`, and `GetState(C, slot)`.
4. Observe that `GetNonce` returns the pre-destruct nonce (not 0), `GetCode` returns the pre-destruct bytecode (not empty), and `GetState` still returns the pre-existing slot value (not cleared) — despite the code’s own comment mandating nonce=0, code cleared, and storage cleared. This diverges from the specified account-clearing behavior and would produce a different `stateRoot` than a correct implementation.
