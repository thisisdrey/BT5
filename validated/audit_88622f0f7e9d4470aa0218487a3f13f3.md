### Title
Permissionless dust transfers fill a user's `MAX_TOKENS_PER_USER` account list, DoSing deposits, collateral top-ups, and liquidations - ([File: contracts/Pool.sol])

### Summary
`Pool` tracks every deposit token and debt token a user has ever touched in `depositTokensOfAccount` / `debtTokensOfAccount` (`MappedEnumerableSet`), capped at `MAX_TOKENS_PER_USER = 30`. Every `DepositToken` mint or transfer whose recipient goes from a zero to non-zero balance calls `pool.addToDepositTokensOfAccount(recipient)`, which reverts with `UserReachedMaxTokens()` once the combined list reaches 30. Because `transfer`/`transferFrom` are public and unrestricted, an unprivileged attacker can permanently occupy slots in any victim's list by sending 1 wei of each listed `DepositToken`, blocking any subsequent first-time receipt of a new deposit token for that account — including rescue deposits and liquidation seizure payouts.

### Finding Description
The add path:

- `DepositToken._transfer` (and `_mint` via `deposit(...)`) calls `pool.addToDepositTokensOfAccount(recipient_)` when the recipient's prior balance was 0: `if (_recipientBalanceBefore == 0 && amount_ > 0) { pool.addToDepositTokensOfAccount(recipient_); }` — contracts/DepositToken.sol:518-520, 486-488.
- `Pool.addToDepositTokensOfAccount` is gated by `onlyIfAdditionWillNotReachMaxTokens(account_)`, which reverts when `debtTokensOfAccount.length(account_) + depositTokensOfAccount.length(account_) >= MAX_TOKENS_PER_USER` — contracts/Pool.sol:143-148, 216-220.
- `deposit(amount_, onBehalfOf_)` accepts any beneficiary, so griefing works via `deposit` too, not just `transfer` — contracts/DepositToken.sol:211-237.
- Nothing restricts who may add tokens to a victim's list; `addToDepositTokensOfAccount` only checks that `msg.sender` is a registered deposit token.

Attack (all unprivileged EOA calls):

1. Attacker deposits a dust amount of each of the pool's deposit tokens into their own account (or obtains msdTokens on a market).
2. For each `DepositToken d` in `pool.getDepositTokens()` the victim does not yet hold: `d.transfer(victim, 1)`. Each call adds `d` to `depositTokensOfAccount[victim]` until the combined list length hits 30.
3. From then on, any transaction that would add a *new* deposit token to the victim's list reverts inside `addToDepositTokensOfAccount`:
   - `deposit(x, victim)` for any collateral type the victim doesn't already hold — the victim can no longer open new collateral positions or top up with a different asset to restore health.
   - `Pool.liquidate(...)` → `depositToken_.seize(account_, liquidator, _toLiquidator)` → `_transfer` → `addToDepositTokensOfAccount(liquidator)` reverts if the *liquidator's* list is also dust-filled to 30 for that token. The attacker can dust-fill their own counterparty-facing addresses or spray-dust known active liquidator/MEV-bot addresses so that liquidations of underwater accounts systematically revert when the seized collateral isn't already in the liquidator's set.
   - The same griefing applies to `seize(account_, feeCollector, _fee)` when `_fee > 0` if `feeCollector`'s list is filled — making the whole `liquidate` revert for new collateral types.

The victim can only recover slots by zeroing dust balances (`transfer` of the full dust balance → `removeFromDepositTokensOfAccount`), but that cleanup is itself front-runnable: the attacker re-fills the freed slot in the same block, and if the victim has debt, `unlockedBalanceOf` may render even the dust locked.

### Impact Explanation
Temporary freezing of funds and DoS of a core liveness invariant:

- A victim's `deposit()`/`deposit(onBehalfOf)` reverts for all collateral types not already in their set — they cannot add new collateral, including to rescue a position approaching liquidation, so funds become effectively locked against the intended use and exposed to liquidation loss.
- Liquidations reverting on `seize` (because the liquidator's or fee collector's list is full) directly undermines protocol solvency guarantees: unhealthy positions cannot be closed when the seized collateral is new to the recipient. The attack cost is dust × number of deposit tokens (≤30), repeatable against any address, and matches the CVE class — an authorized user issuing crafted calls to deny service.

### Likelihood Explanation
Fully unprivileged: only public `deposit`/`transfer` on the pool's own `DepositToken` contracts, no governance/oracle/keeper assumptions. Cost is bounded by 30 dust transfers. Mitigation exists (victim can empty dust slots to free them), so the freeze is temporary rather than permanent, but front-running and locked-balance checks make cleanup unreliable under active griefing, and liquidator/fee-collector griefing is entirely outside the victim's control.

### Recommendation
- Only add to `depositTokensOfAccount` on `deposit`/`_mint` (protocol-initiated credit), not on plain `transfer`/`transferFrom`/`seize` to the recipient — or maintain the account list lazily and stop reverting at the cap (e.g., skip adding once at `MAX_TOKENS_PER_USER` and bound `depositOf`/`debtOf` iteration differently).
- Alternatively, require the recipient to opt in (pull-based registration) before a new token occupies a slot, and exempt `seize` payouts to `feeCollector` from the cap.

### Proof of Concept
Hardhat (against existing pool fixture used in `test/Pool.test.ts`):

```ts
it("griefs victim's token list via dust transfers", async () => {
  const [attacker, victim] = await ethers.getSigners();
  const depositTokens = await pool.getDepositTokens(); // assume >= 2 exist
  const debtTokens = await pool.getDebtTokens();

  // Fill victim's list to MAX_TOKENS_PER_USER with dust
  const slotsFree = 30n - BigInt(debtTokens.length);
  for (let i = 0; i < Math.min(slotsFree, depositTokens.length); i++) {
    const d = await ethers.getContractAt("DepositToken", depositTokens[i]);
    const underlying = await ethers.getContractAt("ERC20Mock", await d.underlying());
    await underlying.mint(attacker.address, 2n);
    await underlying.approve(d.target, 1n);
    await d.deposit(1n, attacker.address);              // attacker holds 1 wei msdToken
    await d.transfer(victim.address, 1n);               // adds token to victim's list
  }

  // victim is now at the cap for every new deposit token
  const dNew = await ethers.getContractAt("DepositToken", depositTokens[0]);
  // victim tries to deposit a collateral type not yet in their list -> reverts
  const underlying2 = await ethers.getContractAt("ERC20Mock", await (
    await ethers.getContractAt("DepositToken", depositTokens[slotsFree > depositTokens.length ? 0 : 0])
  ).underlying());

  // Fresh deposit token added by governor (or any victim-unheld token):
  await expect(
    dNew.deposit(1n, victim.address) // mint to victim -> addToDepositTokensOfAccount -> cap
  ).to.be.revertedWithCustomError(pool, "UserReachedMaxTokens");
});
```

Expected result: the victim's `deposit` (and any `transfer`/`seize` crediting them a new token) reverts with `UserReachedMaxTokens` until they burn/transfer dust out — which can be re-griefed in the same block. A Foundry fork test on a deployed `Pool` (addresses in `deployments/`) can reproduce identically: enumerate `getDepositTokens()`, dust `transfer` 1 wei of each to the target, then assert `depositToken.deposit(amount, victim)` reverts for any unheld collateral.
