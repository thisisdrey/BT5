### Title
Unauthenticated `/shutdown` HTTP endpoint permanently kills the signer's event receiver and runloop with a single POST - ([File: libsigner/src/events.rs])

### Summary
`SignerEventReceiver::next_event` dispatches on `request.url()` with no authentication check, and treats any POST to `/shutdown` as a legitimate stop command regardless of caller identity. Since the event thread is spawned once (not restarted) and its exit drops the channel `Sender`, a single unauthenticated request permanently terminates both the event-receiver thread and the signer's core runloop thread.

### Finding Description
In `next_event`, the dispatch table checks `request.url() == "/shutdown"` and unconditionally sets the stop flag and returns `Err(EventError::Terminated)` with no signature, secret, or peer-identity check of any kind: [1](#0-0) 

Compare this to the legitimate internal caller, `SignerStopSignaler::send`, which is only ever invoked by the signer's own runloop or the SIGINT/SIGTERM handler to gracefully shut itself down — it simply opens a TCP connection and POSTs `/shutdown` with an arbitrary body: [2](#0-1) 

Nothing distinguishes this "internal" caller from an arbitrary remote TCP client: any POST to `/shutdown` with any (or empty) body is accepted. The `EventError::Terminated` propagates up through `main_loop`, which `break`s out of its loop and returns: [3](#0-2) 

Critically, `Signer::spawn` starts the event receiver's `main_loop()` exactly once in a dedicated thread and never restarts it: [4](#0-3) 

When that thread's closure returns, the moved `event_receiver` (holding the only `Sender<SignerEvent<T>>`, added via `add_consumer` during `spawn`) is dropped. This closes the channel. The signer's own runloop thread, blocked on `event_recv.recv_timeout`, then observes `RecvTimeoutError::Disconnected` and exits its loop entirely: [5](#0-4) 

So a single crafted request from any TCP client that can reach the bound `HttpServer` collapses both signer threads permanently — there is no auto-restart path, and the process must be restarted externally (e.g., by a supervisor) to resume operation.

### Impact Explanation
The attacker achieves a full, unauthenticated remote denial of service against the signer: with one HTTP POST to `/shutdown`, both the event-receiver thread and the signer runloop thread terminate irrecoverably (absent external process supervision restarting the binary). While down, the signer stops processing `/stackerdb_chunks`, `/proposal_response`, `/new_burn_block`, and `/new_block` events entirely, meaning it cannot sign or validate blocks — a Critical unauthenticated DoS from a single message, matching the specified Critical category ("remote crash/unauthenticated DoS from few messages"). This is trivially repeatable against every signer whose event-listener port is reachable.

### Likelihood Explanation
No preconditions beyond bare TCP reachability to the signer's bound event-listener HTTP port are required — no secret, no signature, no StackerDB slot ownership, no peer/config state. The request is a single, cheap, well-formed HTTP POST (`POST /shutdown HTTP/1.1` with any body), costing the attacker essentially nothing and fully repeatable on demand.

### Recommendation
Require the `/shutdown` route (and ideally all POST routes) to only be honored from a trusted/local source, e.g., by binding the stop-signal wakeup mechanism to a loopback-only side channel distinct from the externally-reachable HTTP dispatch endpoint, or by requiring a shared secret/token known only to the local signer process and its own stop signaler, and rejecting `/shutdown` requests that don't present it. At minimum, do not accept unauthenticated shutdown commands on the same listener that receives node-pushed events if that listener is intended to be reachable beyond localhost.
