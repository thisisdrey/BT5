### Title
Precompiled contract array-length decoder allocates attacker-controlled array size before bounds validation, enabling OOM node crash - ([File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java])

### Summary
The Mattermost advisory describes a crash caused by allocating memory based on an untrusted length field taken from a msgpack frame *before* that length is validated against the actual size of the received data. `PrecompiledContracts.extractBytes32Array`, `extractBytesArray`, and `extractSigArray` in java-tron exhibit the same root-cause pattern: they read an array-length word directly from TVM calldata and immediately call `new byte[len][]`/similar allocation with that untrusted value, before checking it is consistent with the actual size of the supplied `words`/`data` buffer.

### Finding Description
`DataWord.intValueSafe()` returns up to `Integer.MAX_VALUE` for any word whose big-endian value doesn't fit cleanly in 4 bytes or is "negative" as a signed int [1](#0-0) .

This value is used unchecked to size arrays in the precompiled-contract calldata decoders:

In all three methods, the only bounds check performed is `offset > words.length - 1` (i.e., whether the length *word itself* is present), never whether `len` is a plausible/realistic array count relative to the number of remaining words or the size of `data`. The subsequent per-element accesses (`words[offset + i + 1]`) would eventually throw `ArrayIndexOutOfBoundsException` — but only *after* the `new byte[len][]` allocation has already been attempted, which is the vulnerable step. An attacker can pass a calldata word decoding to a very large `int` (e.g., `0x7FFFFFFF`), forcing the JVM to attempt allocating an object-reference array of that size (~8-17GB depending on pointer compression), which throws `OutOfMemoryError` and can destabilize or crash the whole node process — mirroring the Mattermost bug class where a length is trusted for allocation before validating it against the real payload.

### Impact Explanation
Energy/gas charged for calling a precompile is computed from the *raw calldata length* via `getEnergyForData(data)` (e.g., a flat/word-based charge), not from the internally-decoded `len` value used for allocation. This means an attacker can craft a tiny calldata payload (a handful of 32-byte words) that decodes to an enormous `len`, paying negligible energy while forcing the node to attempt a multi-gigabyte allocation. A successful `OutOfMemoryError` in the JVM can crash or hang the full node process, denying service to all users connected to that node — a CWE-789 (Memory Allocation with Excessive Size Value) condition with High impact, matching the CVSS profile of the reference advisory (unauthenticated, low complexity, availability impact).

### Likelihood Explanation
Any account able to broadcast a transaction that calls a contract exercising these decoders (used by the batch/multi signature-verification precompiles reachable at addresses `0x9`/`0xa` when `VMConfig.allowTvmSolidity059()` is enabled) can trigger this path with a single, cheap transaction. No special privileges, staking, or witness/SR role is required — it is reachable purely from calldata supplied by an ordinary contract caller, which matches the "unprivileged transaction broadcaster/contract deployer" reachability required by the scope rules.

### Recommendation
Before allocating `new byte[len][]` (or equivalent) in `extractBytes32Array`, `extractBytesArray`, and `extractSigArray`, validate `len` against the actual number of remaining `words` (e.g., `len <= words.length - offset - 1`) and reject with a normal VM exception (e.g., `Program.Exception` for bad calldata) if the declared length exceeds what the input can possibly contain, before any allocation occurs — analogous to the `verifyLength` bound checks already used elsewhere in the codebase (e.g., `RLP.calcLength`/`verifyLength`) [5](#0-4) .

### Proof of Concept
1. Enable/assume `VMConfig.allowTvmSolidity059()` (mainnet-enabled proposal) so precompile address `0x9`/`0xa` is reachable.
2. Deploy or reuse a contract that performs a low-level `staticcall`/`call` to precompile address `0000...0009` (BatchValidateSign) or `000...000a` (ValidateMultiSign), supplying calldata where the word at the offset consumed as the array-length parameter is set to `0x7FFFFFFF` (or any value whose `intValueSafe()` resolves to a very large positive int) while the remainder of calldata is only a few words long.
3. Broadcast this call as a normal transaction from any funded account.
4. During TVM execution, `extractBytes32Array`/`extractBytesArray`/`extractSigArray` executes `new byte[len][]` with `len ≈ 2^31-1`, causing the JVM to attempt to allocate an oversized array, triggering `OutOfMemoryError` and potentially crashing/hanging the executing node process — before any bound check against the actual supplied word/data length is performed.

Note: I was unable to directly view the precise `execute()` bodies of `BatchValidateSign`/`ValidateMultiSign` (the grep for those class names within the file returned no matches due to an include-filter issue, and no further tool calls were available), so the exact calldata layout expected by the calling precompile could not be fully confirmed from the index; however, the vulnerable decoder methods and the missing pre-allocation length check are directly confirmed in the cited source.
