## Analog Found

### Title
Treasury-LP minting math in vault `accrue` can divide-by-zero / underflow, permanently bricking all vault operations - (File: `mainnet/contracts/vault/v0-vault-stx.clar` and sibling vaults)

### Summary
The reported bug class is that a reward/accounting function embeds an unchecked arithmetic assumption about the relationship between two quantities (BAL reward vs. 80/20 BAL-ETH LP deposit token), and once that assumption is violated by legitimate protocol state, the function reverts unconditionally forever. The Zest vault contracts have a structurally analogous flaw in the `treasury-lp` calculation inside `accrue()`, which every core vault entry point depends on.

### Finding Description
Every Zest vault's `accrue()` computes the DAO treasury's fee share as LP-equivalent shares: [1](#0-0) 

The relevant line is:
```
(treasury-lp (if (> reserve-inc u0) (mul-div-down reserve-inc (total-supply) (- (total-assets-preview) reserve-inc)) u0))
``` [2](#0-1) 

This subtraction `(- (total-assets-preview) reserve-inc)` implicitly assumes `reserve-inc` (the protocol's cut of newly accrued interest, `debt-delta * fee-reserve / BPS`) is always strictly less than `total-assets-preview`. If a vault's cash-backing degrades relative to outstanding debt (e.g., heavy utilization plus a period without any `accrue`-triggering call, letting `debt-delta` compound), `reserve-inc` can equal or exceed `total-assets-preview`. In Clarity, an unsigned subtraction that would go negative aborts the transaction, and if the two values become exactly equal, the denominator of `mul-div-down` becomes `u0`, which also aborts on division by zero.

`accrue()` is not an optional side function — it is invoked unconditionally at the top of `deposit`, `redeem`, `system-borrow`, and repay-equivalent flows in every vault: [3](#0-2) [4](#0-3) 

Because the index/timestamp updates (`var-set index`, `var-set lindex`, `var-set last-update`) are gated behind the same `let` block that computes `treasury-lp` before any state is committed, if the abort condition is ever reached, it becomes permanent: every subsequent call re-derives the same (or worse, since debt keeps compounding) `debt-delta`/`reserve-inc` inputs and reverts identically. There is no code path that resets or bypasses this once triggered — exactly like `getReward` in the referenced report being permanently bricked once BAL is added as a supported asset.

### Impact Explanation
Once `accrue()` starts reverting, `deposit`, `redeem`, `system-borrow`, and by extension market-level `borrow`/`repay`/`collateral-add`/`collateral-remove` flows that route through this vault become permanently unusable, since they all call `accrue` first. This is a temporary-to-permanent freezing of funds for all depositors and borrowers of that vault (impact class: "temporary freezing of funds" / potentially "permanent freezing of funds" if the debt/cash ratio cannot recover through normal user action).

### Likelihood Explanation
This requires `total-assets-preview` (roughly: vault cash + outstanding debt) to shrink relative to `reserve-inc` (a bounded fraction, up to 100% via `fee-reserve` in BPS, of newly accrued interest on outstanding debt). This is most plausible in a vault that is heavily utilized (most cash lent out) combined with `fee-reserve` set near its maximum and an extended period between `accrue`-triggering calls, allowing `debt-delta` to compound. This does not require any privileged/DAO compromise beyond parameters (`fee-reserve`) that are part of normal protocol configuration, and no user action is required to trigger it once the state condition is met — the next ordinary user calling `deposit`/`redeem`/`borrow` on that vault would trip it. Likelihood is therefore conditional on protocol/state configuration, similar to the Medium-severity judgment given to the original veBAL report.

### Recommendation
Bound `reserve-inc` to be strictly less than `total-assets-preview` before performing the subtraction (e.g., `(min reserve-inc (- total-assets-preview u1))`), or restructure the treasury-lp share calculation to use `total-assets-preview` (pre-fee) as the denominator basis instead of `(total-assets-preview - reserve-inc)`, eliminating the possibility of underflow/division-by-zero regardless of how large `reserve-inc` grows relative to available assets.

### Proof of Concept
1. Vault is deployed with `fee-reserve` set to a high BPS value (allowed range up to `BPS` per config).
2. Utilization is driven high via `system-borrow` so `assets` (cash) is mostly checked out as debt, per: [5](#0-4) 
3. No `deposit`/`redeem`/`borrow` call occurs for an extended period, allowing `next-index` to compound `debt-delta` significantly.
4. The next ordinary user call to `deposit`, `redeem`, or `system-borrow` triggers `accrue()`; `reserve-inc` computed from the large compounded `debt-delta` reaches/exceeds `total-assets-preview`, causing the subtraction/division in the `treasury-lp` calculation to abort the transaction.
5. Every subsequent call to the vault hits the identical (or worse) arithmetic condition, since `last-update`/`index` were never committed, permanently freezing all vault operations for all users.
