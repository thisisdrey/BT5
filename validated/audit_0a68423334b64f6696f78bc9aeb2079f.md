### Title
Reintroduction of the 2021 RETURNDATA-corruption consensus bug: missing `CopyBytes` before overlapping `Memory.Set` in CALL opcodes - ([File: core/vm/instructions.go])

### Summary
`opCall`, `opCallCode`, `opDelegateCall`, and `opStaticCall` pass a raw (non-copied) pointer into the callee as input, and after the call completes they write the callee's return value directly back into the same memory buffer with `scope.Memory.Set(retOffset, retSize, ret)`. None of these four opcodes copy `ret` before this write. This is exactly the class of bug that caused the August 2021 mainnet minority-chain split, documented in `docs/postmortems/2021-08-22-split-postmortem.md`, whose fix was to insert `ret = common.CopyBytes(ret)` immediately before the `Memory.Set` call in each of these four opcodes. That defensive copy is absent from the current code.

### Finding Description
For every CALL-family opcode, the input arguments are obtained as a live slice into the caller's memory, not a copy: [1](#0-0) 

After execution, the call's return data is written back into the caller's memory at `retOffset`/`retSize` without ever copying `ret` first: [2](#0-1) 

The same missing-copy pattern exists in `opCallCode`, `opDelegateCall`, and `opStaticCall`: [3](#0-2) [4](#0-3) [5](#0-4) 

`Memory.Set` performs an in-place `copy()` into the backing store: [6](#0-5) 

The historical incident report shows the exact same shape of bug and the fix that must exist for these four opcodes: [7](#0-6) [8](#0-7) 

Root cause: when a callee (particularly a precompile that echoes its input, such as the identity/`dataCopy` precompile, or a nested call whose return happens to alias the caller's memory) returns a slice that is backed by the *same* array as the caller's memory region being overwritten by `Memory.Set`, and the source/destination ranges of that in-place `copy()` overlap but are shifted, Go's `copy()` semantics corrupt the data during the copy. Because `evm.returnData = ret` is assigned using the same (already-aliased, now partially-overwritten) slice, `RETURNDATASIZE`/`RETURNDATACOPY` in subsequent opcodes, and the value ultimately written to memory, become corrupted in a way that depends on Go's memory-copy implementation rather than on the EVM specification. As shown in the original 2019 postmortem, this leads to `stateRoot` divergence between clients/versions on a maliciously crafted transaction.

### Impact Explanation
This breaks the state-transition equality: two conforming implementations (or even two builds of this codebase) can compute different memory contents — and therefore different `stateRoot`s — for the same block, because the outcome depends on unspecified overlap/shift behavior of a `copy()` rather than on the EVM opcode semantics. This is a Critical-severity consensus-split bug, matching precisely the class of the real August 2021 minority-chain-split incident referenced in the repo's own postmortem docs.

### Likelihood Explanation
Likelihood is high given it is a single, self-contained transaction: attacker crafts a contract that performs a `CALL`/`STATICCALL`/`DELEGATECALL`/`CALLCODE` to a target (e.g. the identity precompile, or any callee designed to echo/alias input) with carefully chosen `inOffset/inSize`/`retOffset/retSize` such that the return slice aliases the memory region about to be overwritten with an overlapping-but-shifted range — the exact reproduction recipe documented in the historical postmortem.

### Recommendation
Reinstate the defensive copy that was added in the 2021 fix: insert `ret = common.CopyBytes(ret)` immediately before each `scope.Memory.Set(retOffset.Uint64(), retSize.Uint64(), ret)` call in `opCall`, `opCallCode`, `opDelegateCall`, and `opStaticCall` in `core/vm/instructions.go`, so the write destination and the return-data source can never share a backing array.

### Proof of Concept
1. Deploy/attacker contract sets up memory such that the input region passed to a `CALL`/`STATICCALL` to the identity precompile (address `0x04`) and the `retOffset`/`retSize` used for that same call overlap but are shifted (analogous to the 2021 PoC: `in = mem[0:4]`, `out = mem[1:5]`).
2. The precompile (or any callee returning an aliased slice) returns the same backing slice as `args`.
3. `scope.Memory.Set(retOffset, retSize, ret)` performs `copy(m.store[retOffset:retOffset+retSize], ret)` where `ret` is backed by the same array as the destination range, with overlap-but-shift — corrupting `ret`'s contents mid-copy.
4. `evm.returnData = ret` then holds the corrupted slice; a subsequent `RETURNDATACOPY`/`RETURNDATASIZE` or the value written to memory differs from the true precompile output, producing a divergent `stateRoot` versus a spec-compliant implementation that copies before overwriting (as documented in `docs/postmortems/2021-08-22-split-postmortem.md`).

// Set sets offset + size to value
func (m *Memory) Set(offset, size uint64, value []byte) {
	// It's possible the offset is greater than 0 and size equals 0. This is because
	// the calcMemSize (common.go) could potentially return 0 when size is zero (NO-OP)
	if size > 0 {
		// length of store may never be less than offset + size.
		// The store should be resized PRIOR to setting the memory
		if offset+size > uint64(len(m.store)) {
			panic("invalid memory: store empty")
		}
		copy(m.store[offset:offset+size], value)
	}
}

###  2021-08-17 RETURNDATA corruption via datacopy

On 2021-08-17, Guido Vranken submitted a report to bounty@ethereum.org. This coincided with a geth-meetup in Berlin, so the geth team could fairly quickly analyse the issue. 

He submitted a proof of concept which called the `dataCopy` precompile, where the input slice and output slice were overlapping but shifted. Doing a `copy` where the `src` and `dest` overlaps is not a problem in itself, however, the `returnData`slice was _also_ using the same memory as a backing-array.

#### Technical details

During CALL-variants, `geth` does not copy the input. This was changed at one point, to avoid a DoS attack reported by Hubert Ritzdorf, to avoid copying data a lot on repeated `CALL`s -- essentially combating a DoS via `malloc`. Further, the datacopy precompile also does not copy the data, but just returns the same slice. This is fine so far. 

After the execution of `dataCopy`, we copy the `ret` into the designated memory area, and this is what causes a problem. Because we're copying a slice of memory over a slice of memory, and this operation modifies (shifts) the data in the source -- the `ret`. So this means we wind up with corrupted returndata.


```
1. Calling datacopy

  memory: [0, 1, 2, 3, 4]
  in (mem[0:4]) : [0,1,2,3]
  out (mem[1:5]): [1,2,3,4]

2. dataCopy returns

  returndata (==in, mem[0:4]): [0,1,2,3]
 
3. Copy in -> out

  => memory: [0,0,1,2,3]
  => returndata: [0,0,1,2]
```
