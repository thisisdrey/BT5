### Title
Unauthenticated cross-peer PeerDB overwrite via attacker-chosen `HandshakeData.addrbytes/port` in outbound re-key path - ([File: stackslib/src/net/chat.rs])

### Summary
`ConversationP2P::handle_handshake` re-key branch keys the PeerDB write by `NeighborKey::from_handshake(...)`, which is built entirely from the *attacker-supplied* `HandshakeData.addrbytes`/`port` fields, not from the verified TCP socket address of the connection (`self.peer_addrbytes`/`self.peer_port`). A remote peer that a node has connected outbound to can therefore send a second Handshake with a different public key and arbitrary `addrbytes`/`port`, causing the node to load and unconditionally overwrite an unrelated frontier row's `public_key` and `expire_block_height` in its own `PeerDB`.

### Finding Description
The broken equality is: *the `NeighborKey` used to persist the re-keyed identity* should equal *the `NeighborKey` of the TCP connection this `ConversationP2P` was actually established with* (`self.to_neighbor_key()`, built from `peer_addrbytes`/`peer_port`, which come from the real socket peer address). Instead:

- `update_from_handshake_data` (stackslib/src/net/chat.rs:1131-1167) stores the raw, attacker-supplied `handshake_data.addrbytes`/`port` into `self.handshake_addrbytes`/`self.handshake_port`, and returns `updated=true` whenever the newly presented `node_public_key` differs from the previously recorded one for this connection (`cur_pubk_opt`).
- `handle_handshake` (stackslib/src/net/chat.rs:1214-1296), on `updated && self.stats.outbound`, calls `Neighbor::load_and_update(&tx, preamble.peer_version, preamble.network_id, &handshake_data)` — note it passes `handshake_data`, not `self.to_neighbor_key()`.
- `Neighbor::load_and_update` (stackslib/src/net/chat.rs:475-516) builds `addr = NeighborKey::from_handshake(...)` purely from `handshake_data.addrbytes`/`port` (stackslib/src/net/chat.rs:411-423), then does `PeerDB::get_peer(conn, network_id, &addr.addrbytes, addr.port)` — an unauthenticated lookup keyed by attacker-controlled bytes.
- If a row already exists at that key (e.g., a legitimate bootstrap node or any other known peer address:port already in the local frontier), that row is loaded, `handshake_update` overwrites `public_key`/`expire_block` with the attacker's values, and `neighbor.save_update(&tx, None)` (stackslib/src/net/neighbors/neighbor.rs:50-61) unconditionally calls `PeerDB::update_peer` (stackslib/src/net/db.rs:1286-1334), which executes `UPDATE frontier SET ... public_key = ?, expire_block_height = ? ... WHERE network_id = ? AND addrbytes = ? AND port = ?` using the attacker-chosen key — mutating the third party's row, dropping its cached StackerDB associations, and having nothing to do with the actual TCP peer.

No code path in this branch verifies `handshake_data.addrbytes == self.peer_addrbytes` (or port); the only cross-check against the real connection address exists in the *neighbor-walk* logic (`handle_handshake_accept` in stackslib/src/net/neighbors/walk.rs:705-715, and `check_handshake_pubkey_hash` in walk.rs:1663-1680), which apply to `HandshakeAccept`/pingback flows, not to this `handle_handshake` re-key branch that fires for inbound `Handshake` messages on an outbound conversation.

**Attacker's exact message:** two Handshake messages sent over one already-established outbound TCP conversation: (1) an initial Handshake with key A (sets `cur_pubk = A`, `updated=false`, no DB write via this branch), then (2) a second Handshake with a *different* key B and `HandshakeData.addrbytes/port` set to a third-party address/port already present in the node's frontier (e.g., a bootstrap peer). This second message satisfies `pubk != cur_pubk` → `updated = true`, and since the conversation is outbound, the re-key branch executes and blindly persists key B and the attacker-chosen `expire_block_height` into the third party's row.

### Impact Explanation
This is an unauthenticated write to persistent local state (the node's own `PeerDB`/frontier), matching the "Critical: unauthenticated/unauthorized write to state" category. The affected node's cached identity for an unrelated third-party peer (public key and key-expiry block) is silently corrupted by a peer it never claimed to be. Consequences include: causing subsequent outbound connection attempts / neighbor-walk logic to treat the victim address as owned by the attacker's key (weakening peer identity assumptions used elsewhere), and dropping the victim's cached StackerDB replication set (`PeerDB::drop_stacker_dbs` fires on public-key change in `update_peer`). This is repeatable per outbound conversation and can target any address/port currently present in the node's frontier table, not just the actual peer being talked to.

### Likelihood Explanation
Preconditions: the victim node must have (a) an existing outbound conversation to the attacker (a normal, permissionless occurrence — any peer can be crawled/connected to via gossip, or the attacker can simply be a peer the victim dialed), and (b) at least one other frontier row already populated for the target `addrbytes:port` (near-certain in practice, since bootstrap peers and gossiped neighbors are commonly present). Attacker cost is minimal: run one peer, complete a normal handshake, then send one more crafted Handshake message with a bogus public key and a chosen `addrbytes`/`port`. No secrets, no privileged role, and no bandwidth/volume is needed — a single crafted message suffices, and it is fully repeatable against any frontier entry.

### Recommendation
In `handle_handshake`'s re-key branch, key the PeerDB update by the conversation's actual verified peer address (`self.to_neighbor_key()`, derived from the real socket `peer_addrbytes`/`peer_port`) instead of by `handshake_data.addrbytes`/`port`. Alternatively/additionally, reject or clamp `handshake_data.addrbytes`/`port` against the real socket address before calling `Neighbor::load_and_update`/`save_update`, consistent with the check already done for `HandshakeAccept` in `handle_handshake_accept` (walk.rs:705-715).

### Proof of Concept
Rust test in `stackslib/src/net/chat.rs` test module (alongside existing handshake tests, e.g. near line 4415 `test_convo_handshake_rekey` style):
1. Set up `convo_1` (outbound) and `convo_2` as in existing handshake tests, complete an initial successful Handshake/HandshakeAccept exchange so `convo_1.connection.get_public_key()` is `Some(pubkey_A)`.
2. Pre-populate `peerdb_2`... actually the node under test is the one performing `handle_handshake` — call it "node 2" processing `convo_2` which is outbound to node "victim". Insert into node 2's `PeerDB` a row for a third-party `NeighborKey` `victim_addr:victim_port` with `public_key = pubkey_V`, `expire_block = E_V` via `PeerDB::try_insert_peer`.
3. Craft a second `HandshakeData` signed by attacker's `local_peer_1` with a fresh key `pubkey_B` (≠ `pubkey_A`), but set `handshake_data.addrbytes = victim_addr`, `handshake_data.port = victim_port` (instead of `convo_1`'s own real address).
4. Send this as a signed `Handshake` message from `convo_1` to `convo_2` on the already-authenticated outbound conversation, and call `convo_2.chat(...)` to trigger `handle_handshake`.
5. Assert: `PeerDB::get_peer(peerdb_2_conn, network_id, &victim_addr, victim_port).unwrap().public_key == pubkey_B` (and `expire_block == handshake_data.expire_block_height`), proving the victim's unrelated row was overwritten instead of (or without touching) any row keyed by `convo_1`'s actual socket address.
