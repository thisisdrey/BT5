### Title
`AttachmentsDownloader` accepts and persists attacher-supplied attachments without enforcing `AtlasConfig::attachments_max_size` - ([File: stackslib/src/net/atlas/download.rs])

### Summary
`GetAttachmentResponse::deserialize` in `stackslib/src/net/atlas/mod.rs:69-77` decodes an arbitrary-length hex string via `hex_bytes(&hex_encoded)` into `Attachment.content` with no upper bound. When the `AttachmentsDownloader` fetches an attachment from a peer that claimed to have it in its inventory, the decoded attachment is inserted into the batch context and later persisted to the `AtlasDB` via `insert_instantiated_attachment` with no size check performed anywhere in that path.

### Finding Description
The equality the config is supposed to guarantee is: *persisted attachment content length ≤ `AtlasConfig::attachments_max_size`*. That guarantee is only enforced in one place — `AtlasDB::should_keep_attachment` (`stackslib/src/net/atlas/db.rs:249-266`), which checks `attachment.content.len() as u32 > self.atlas_config.attachments_max_size`. That function is called only from the client-submitted-transaction path (`posttransaction.rs`), not from the peer-download path.

In the peer-download path:
1. `AttachmentsBatchStateContext::extend_with_attachments` (`stackslib/src/net/atlas/download.rs:530-558`) decodes a peer's HTTP response with `response.decode_atlas_get_attachment()` and does `self.attachments.insert(response.attachment)` — no size check at all.
2. `decode_atlas_get_attachment` (`stackslib/src/net/api/getattachment.rs:158-165`) calls `GetAttachmentResponse`'s `Deserialize` impl, which does `hex_bytes(&hex_encoded)` with no length cap (`stackslib/src/net/atlas/mod.rs:69-77`).
3. `AttachmentsDownloader::run`'s `Done` branch (`stackslib/src/net/atlas/download.rs:153-169`) drains `context.attachments` and calls `network.atlasdb.insert_instantiated_attachment(&attachment)` directly — again with no size check.
4. `AtlasDB::insert_instantiated_attachment` (`stackslib/src/net/atlas/db.rs:576-592`) writes `attachment.content` straight into the `attachments` SQLite table with no size validation.

Thus a malicious peer that is selected as a download source (by advertising the target hash as present in its `GetAttachmentsInvResponse` inventory) can respond to the `/v2/attachments/:hash` GET request with an oversized hex payload, and the victim node will store it verbatim, in violation of the operator-configured `attachments_max_size` (default minimum 1MB per `ATTACHMENTS_MAX_SIZE_MIN` in `stackslib/src/net/atlas/mod.rs:52`).

The only bound on the response size is whatever generic HTTP/connection-level limits exist elsewhere in `httpcore.rs`; those are not attachment-specific and are not verified in this trace to be tight enough to prevent multi-hundred-MB responses from significantly exceeding a configured `attachments_max_size`.

### Impact Explanation
A malicious peer serving attachment data can cause the requesting node to persist content in its `AtlasDB` far larger than the operator's configured `attachments_max_size`, bypassing the size guard that exists for locally-submitted attachments (`should_keep_attachment`). Repeated across multiple attachment instances/batches, this allows a peer to inflate the victim's Atlas attachment storage without volumetric flooding — a single oversized response per requested hash is sufficient. This matches the "bounded compute/storage DoS via a read/download path" impact class since it defeats an explicit configured resource cap and causes disk exhaustion.

### Likelihood Explanation
Preconditions: the attacker must be selectable as a source for the target attachment, which only requires advertising the attachment's presence in a `GetAttachmentsInvResponse` for that content hash/page — something any peer serving as an "outbound sync peer" data URL can do without any privileged role or secret. No signature or authentication guards the actual `GetAttachmentResponse` body's content length. This is fully remotely reachable via the P2P/data-URL fetch mechanism and repeatable for each attachment instance the node attempts to resolve.

### Recommendation
Enforce `AtlasConfig::attachments_max_size` in the download path: check `response.attachment.content.len() as u32 > atlas_config.attachments_max_size` inside `extend_with_attachments` (or immediately in `GetAttachmentResponse::deserialize`) and reject/mark-failed oversized responses before they enter `context.attachments`. Additionally, call `atlas_db.should_keep_attachment` (or equivalent) before `insert_instantiated_attachment` in `AttachmentsDownloader::run`'s `Done` branch as a defense-in-depth check.

### Proof of Concept
Rust test plan (in `stackslib/src/net/atlas/tests.rs` or a new test module):
1. Construct a `GetAttachmentResponse` JSON string manually: `"\"".to_string() + &"ab".repeat(200_000_000) + "\""` (≈200MB hex payload decoding to 100MB).
2. Call `serde_json::from_str::<GetAttachmentResponse>(&crafted_json)` and assert it succeeds, producing `attachment.content.len() == 100_000_000`, demonstrating no cap in `Deserialize` (`stackslib/src/net/atlas/mod.rs:69-77`).
3. Construct an `AttachmentsBatchStateContext` with an `AtlasConfig { attachments_max_size: 1_048_576, .. }`, feed the oversized `Attachment` through `extend_with_attachments` with a synthetic successful `BatchedRequestsResult`, and assert `context.attachments` contains the oversized entry despite exceeding `attachments_max_size`.
4. Drive `AttachmentsDownloader::run` to the `Done` branch and assert `atlasdb.find_attachment(&hash)` returns the full oversized content after `insert_instantiated_attachment`, proving persistence occurred without the size check that `should_keep_attachment` would have applied.     pub fn extend_with_attachments(
        mut self,
        results: &mut BatchedRequestsResult<AttachmentRequest>,
    ) -> AttachmentsBatchStateContext {
        for (request, response) in results.succeeded.drain() {
            let report = self
                .peers
                .get_mut(request.get_url())
                .expect("Atlas: unable to retrieve reliability report for peer");

            let response = if let Some(r) = response {
                r
            } else {
                report.bump_failed_requests();
                continue;
            };

            if let Ok(response) = response.decode_atlas_get_attachment() {
                self.attachments.insert(response.attachment);
                report.bump_successful_requests();
            } else {
                report.bump_failed_requests();
            }
        }
        let mut events_ids = results.faulty_peers.keys().copied().collect::<Vec<usize>>();
        self.events_to_deregister.append(&mut events_ids);

        self
    }

    pub fn should_keep_attachment(
        &self,
        contract_id: &QualifiedContractIdentifier,
        attachment: &Attachment,
    ) -> bool {
        if !self.atlas_config.contracts.contains(contract_id) {
            info!(
                "Atlas: will discard posted attachment - {} not in supported contracts",
                contract_id
            );
            return false;
        }
        if attachment.content.len() as u32 > self.atlas_config.attachments_max_size {
            info!("Atlas: will discard posted attachment - attachment too large");
            return false;
        }
        true
    }

    pub fn insert_instantiated_attachment(
        &mut self,
        attachment: &Attachment,
    ) -> Result<(), db_error> {
        let now = util::get_epoch_time_secs() as i64;
        let tx = self.tx_begin()?;
        tx.execute(
            "INSERT OR REPLACE INTO attachments (hash, content, was_instantiated, created_at) VALUES (?, ?, 1, ?)",
            params![attachment.hash(), attachment.content, now],
        )?;
        tx.execute(
            "UPDATE attachment_instances SET is_available = 1 WHERE content_hash = ?1 AND status = ?2",
            params![attachment.hash(), AttachmentInstanceStatus::Checked],
        )?;
        tx.commit()?;
        Ok(())
    }
