### Title
Cross-StackerDB chunk replay due to missing contract/message-type binding in `SlotMetadata` signature - (File: `libstackerdb/src/libstackerdb.rs`)

### Summary
`SlotMetadata::auth_digest()` computes the signed payload as only `(slot_id, slot_version, data_hash)`, never including the target StackerDB's smart-contract identifier or message type. Because signer→slot mappings are shared across multiple, distinct StackerDB contracts (the different `signers-{0|1}-{message_id}` replicas all read from the same `stackerdb-signer-slots-0/1` list), and because `try_replace_chunk` only re-validates `(slot_id, slot_version, data_hash)` against whichever signer currently owns that slot in the *target* contract, a validly-signed chunk broadcast/posted for one StackerDB replica can be replayed verbatim into a different StackerDB replica belonging to the same signer, as long as the target replica's stored version for that slot is lower.

### Finding Description
The signature commits to a minimal digest: [1](#0-0) 
which never binds the smart-contract identity of the intended StackerDB. `StackerDBChunkData::verify()`/`sign()` reuse this same digest: [2](#0-1) 

The write path (`try_replace_chunk`) looks up the *current owning signer* for `(smart_contract, slot_id)` in the target replica and checks the chunk's signature against that address plus a monotonic version bump — it never confirms the chunk was intended for this particular contract: [3](#0-2) 

The signer-to-slot assignment is deliberately shared across all message-type replicas for a signer set: `signers-{0,1}-{message_id}.clar` all delegate to the same page of `.signers`: [4](#0-3) [5](#0-4) 

Contract names are reused mod 2 across reward cycles as well: [6](#0-5) 

Critically, `reconfigure_stackerdb` only resets a slot's version if the *signer for that slot changes*; if the same signer retains the slot across reconfiguration (same reward-cycle-mod contract reused, or a re-elected signer keeping the same index), the stored version keeps incrementing independently per replica rather than resetting: [7](#0-6) 

Because different message-type replicas (`BlockResponse`, `StateMachineUpdate`, `BlockPreCommit`) are written at very different frequencies, their per-slot versions naturally diverge. An unprivileged remote attacker can observe any legitimately signed `StackerDBChunkData` (via P2P StackerDB push/gossip or via the public `POST /v2/stackerdb/:addr/:contract/chunks` endpoint) for a signer's high-traffic replica (e.g., `signers-1-1`, slot k, version 500), and simply re-POST/re-relay the identical `StackerDBChunkData` bytes to a low-traffic replica for the same signer set (e.g., `signers-1-3`, slot k, current version 5). Since the signature only covers `(slot_id, slot_version, data_hash)` — not the contract — and `slot_desc.verify(&slot_validation.signer)` succeeds (same signer address occupies slot k in both replicas), and `500 > 5` satisfies the freshness check, the write is accepted: [8](#0-7) 
The write handler for the HTTP endpoint performs exactly this check-then-store-then-relay sequence with no additional contract binding, and on success schedules the chunk for P2P relay to other nodes: [9](#0-8) [10](#0-9) 

This breaks the equality "chunk authenticated for replica X" vs. "chunk stored/served as replica X's canonical slot data" — content signed for and legitimately published to one StackerDB context is accepted as canonical, current data for an entirely different StackerDB context, and is then propagated network-wide via `StackerDBPushChunk` relay/gossip.

### Impact Explanation
This meets the "network-wide propagation of forged data" and "serving non-canonical state as canonical" impact classes: an attacker with no special privileges (not a signer, not an admin, no secret keys) can cause a signer's `BlockResponse` payload bytes to be stored and gossiped as if it were, e.g., that signer's `BlockPreCommit`/`StateMachineUpdate` payload, corrupting signer-to-signer gossip state that downstream signer/miner logic consumes from StackerDB, and forcing nodes to accept and re-propagate data the signer never intended for that context/slot.

### Likelihood Explanation
High likelihood: the attack requires no compromise of any key, no internal node access, and no unusual preconditions — only passive observation of one legitimately-broadcast, publicly-visible `StackerDBChunkData` (chunks are pushed unauthenticated-transport but signed data, and are gossiped/served publicly over StackerDB sync/HTTP) and a single unauthenticated POST/relay to a sibling replica whose per-slot version has not yet caught up. Divergent write frequencies between `BlockResponse`/`StateMachineUpdate`/`BlockPreCommit` replicas make a lower target version commonplace.

### Recommendation
Include the target StackerDB's smart-contract identifier (and/or the reward cycle / message type) in `SlotMetadata::auth_digest()` so a chunk's signature is only valid for the specific replica it was created for, e.g. `hash(contract_id || slot_id || slot_version || data_hash)`. Update `sign`/`verify` accordingly and add cross-checks in `try_replace_chunk`/`validate_received_chunk` that the chunk's implied contract binding matches the one being written to.

### Proof of Concept
1. Signer S is assigned slot `k` in both `signers-1-1` (BlockResponse, currently at version 500) and `signers-1-3` (BlockPreCommit, currently at version 5), per the shared `stackerdb-get-signer-slots-page` mapping.
2. Attacker observes/collects S's legitimately signed `StackerDBChunkData{slot_id: k, slot_version: 500, sig, data}` published to `signers-1-1` (via P2P StackerDBChunkPush or the public HTTP GET chunk endpoint).
3. Attacker issues `POST /v2/stackerdb/<signers-addr>/signers-1-3/chunks` with the exact same `StackerDBChunkData` bytes.
4. `try_replace_chunk` for `signers-1-3` looks up slot `k`'s current signer (S, unchanged), verifies the untouched signature succeeds, checks `500 > 5` (passes), and stores it — `insert_chunk` overwrites `signers-1-3` slot `k` with BlockResponse-formatted data mislabeled as BlockPreCommit content, and the node schedules `StackerDBPushChunk` relay to peers.

    pub fn reconfigure_stackerdb(
        &self,
        smart_contract: &QualifiedContractIdentifier,
        slots: &[(StacksAddress, u32)],
    ) -> Result<(), net_error> {
        let stackerdb_id = self.get_stackerdb_id(smart_contract)?;
        let mut total_slots_read = 0u32;
        for (principal, slot_count) in slots.iter() {
            total_slots_read =
                total_slots_read
                    .checked_add(*slot_count)
                    .ok_or(net_error::OverflowError(
                        "Slot count exceeeds u32::MAX".to_string(),
                    ))?;
            let slots_before_principal = total_slots_read - slot_count;
            for cur_principal_slot in 0..*slot_count {
                let slot_id = slots_before_principal + cur_principal_slot;
                if let Some(existing_validation) =
                    self.get_slot_validation(smart_contract, slot_id)?
                {
                    // this slot already exists.
                    if existing_validation.signer == *principal {
                        // no change
                        continue;
                    }
                }

                debug!("Reset slot {} of {}", slot_id, smart_contract);

                // new slot, or existing slot with a different signer
                let qry = "INSERT OR REPLACE INTO chunks (stackerdb_id,signer,slot_id,version,write_time,data,data_hash,signature) VALUES (?1,?2,?3,?4,?5,?6,?7,?8)";
                let mut stmt = self.sql_tx.prepare(qry)?;
                let args = params![
                    stackerdb_id,
                    principal.to_string(),
                    slot_id,
                    NO_VERSION,
                    0,
                    vec![],
                    Sha512Trunc256Sum([0u8; 32]),
                    MessageSignature::empty(),
                ];

                stmt.execute(args)?;
            }
        }
        debug!("Shrink {} to {} slots", smart_contract, total_slots_read);
        self.shrink_stackerdb(stackerdb_id, total_slots_read)?;
        Ok(())
    }

    /// Add or replace a chunk for a given reward cycle, if it is valid
    /// Otherwise, this errors out with Error::StaleChunk
    pub fn try_replace_chunk(
        &self,
        smart_contract: &QualifiedContractIdentifier,
        slot_desc: &SlotMetadata,
        chunk: &[u8],
    ) -> Result<(), net_error> {
        // Check per-replica chunk-size cap.
        if (chunk.len() as u64) > self.config.chunk_size {
            return Err(net_error::StackerDBChunkTooBig(chunk.len()));
        }

        let slot_validation = self
            .get_slot_validation(smart_contract, slot_desc.slot_id)?
            .ok_or(net_error::NoSuchSlot(
                smart_contract.clone(),
                slot_desc.slot_id,
            ))?;

        if !slot_desc.verify(&slot_validation.signer)? {
            return Err(net_error::BadSlotSigner(
                slot_validation.signer,
                slot_desc.slot_id,
            ));
        }
        if slot_desc.slot_version <= slot_validation.version {
            return Err(net_error::StaleChunk {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
            });
        }
        if slot_desc.slot_version > self.config.max_writes {
            return Err(net_error::TooManySlotWrites {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
                max_writes: self.config.max_writes,
            });
        }
        self.insert_chunk(smart_contract, slot_desc, chunk)
    }
