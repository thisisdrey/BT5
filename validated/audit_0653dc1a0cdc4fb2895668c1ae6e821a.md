### Title
Housekeeping activity flag is never reset on handler panic, causing permanent DoS of maintenance RPCs for a repository - ([File: internal/grpc/middleware/housekeeping/middleware.go])

### Summary
The `OpMaintenance` branch of `Middleware.UnaryServerInterceptor` and `Middleware.StreamServerInterceptor` marks a repository's housekeeping state as "active" before invoking the RPC handler, and only clears it via a plain post-call statement rather than a `defer`. If the wrapped handler panics, the "active" flag is left permanently set to `true` for that repository, and every subsequent maintenance RPC to the same repository is rejected forever, mirroring the reported bug class where a state-toggle flag is set but never guaranteed to be reset back.

### Finding Description
In the unary path, the sequence is: [1](#0-0) 

`m.markHousekeepingActive(key)` sets `activity.active = true` for the repo key, and `m.markHousekeepingInactive(key)` is expected to reset it back to `false` after the handler completes: [2](#0-1) 

However, `markHousekeepingInactive` is only called as an ordinary statement after `handler(ctx, req)` returns, with no `defer`/`recover` guarding it. If `handler` panics (e.g. an unexpected panic somewhere in the `OptimizeRepository`/maintenance code path while processing an ordinary user's request against a corrupted or unusual repository state), execution never reaches `m.markHousekeepingInactive(key)`, and the goroutine's stack unwinds past it. The in-memory `activity.active` flag for that `repoKey` stays `true` for the lifetime of the process. The same defect exists in the stream interceptor's `OpMaintenance` branch: [3](#0-2) 

By contrast, the asynchronous scheduling path (`scheduleHousekeeping`) correctly guards the reset with `defer`: [4](#0-3) 

This inconsistency confirms the reset was intended to always fire but is missing proper protection on the synchronous RPC interception paths, directly analogous to `removeLiquidity` never resetting `_opt.liquidityAdded`, permanently gating out the legitimate follow-up action (`addLiquidity` / here, any future `OpMaintenance` RPC for the repo).

### Impact Explanation
Once the flag gets stuck at `true` for a `repoKey` (storage + relative path), `isActive(key)` will return `true` forever: [5](#0-4) 

Every future call to an `OpMaintenance` RPC (e.g. `OptimizeRepository`) for that repository will be rejected with `AlreadyExists: "housekeeping already executing for repository"`, permanently preventing legitimate maintenance/optimization operations on that repository until the Gitaly process is restarted (the state lives only in the in-process `repoActivity` map). This is a persistent, unrecoverable-without-restart denial of service scoped to a specific repository's maintenance operations.

### Likelihood Explanation
Triggering requires the wrapped handler to panic while an `OpMaintenance` RPC is in flight for a given repository — a condition that can arise from unexpected runtime errors (nil dereference, index-out-of-range, etc.) surfacing while operating on unusual or adversarially-crafted repository/object states during git housekeeping. Because such maintenance RPCs process repository content that can be influenced by ordinary pushes/imports, the likelihood is not purely theoretical, but does depend on an underlying panic being triggered, so likelihood is best assessed as low-to-medium rather than trivially reproducible on demand.

### Recommendation
Wrap the state-clearing call in a `defer` (ideally combined with panic recovery/re-panicking) immediately after `markHousekeepingActive` succeeds, in both `UnaryServerInterceptor` and `StreamServerInterceptor`:
```go
m.markHousekeepingActive(key)
m.mu.Unlock()
defer m.markHousekeepingInactive(key)

resp, err := handler(ctx, req)
return resp, err
```
This ensures the `active` flag is always reset regardless of whether the handler returns normally, returns an error, or panics.

### Proof of Concept
1. Configure any RPC classified as `protoregistry.OpMaintenance` (e.g. `OptimizeRepository`) for a target repository.
2. Cause the underlying handler to panic while housekeeping is active for that repository (e.g. inject/trigger a panic in the housekeeping manager's optimize path due to unexpected repository state).
3. Observe that `markHousekeepingActive` was called but `markHousekeepingInactive` is skipped because the panic unwinds past line 172 (unary) / 247 (stream) without executing it.
4. Issue a subsequent, well-formed `OptimizeRepository` call for the same repository — it is rejected with `AlreadyExists: "housekeeping already executing for repository"` indefinitely, confirming the permanent lockout described in `isActive`/`markHousekeepingActive`/`markHousekeepingInactive`. func (m *Middleware) markHousekeepingActive(key repoKey) {
	a, ok := m.repoActivity[key]
	if !ok {
		a = newActivity()
		m.repoActivity[key] = a
	}

	a.active = true
}

func (m *Middleware) markHousekeepingInactive(key repoKey) {
	m.mu.Lock()
	defer m.mu.Unlock()

	a, ok := m.repoActivity[key]
	if !ok {
		a = newActivity()
		m.repoActivity[key] = a
	}

	a.active = false
}
