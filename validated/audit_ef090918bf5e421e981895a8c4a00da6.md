### No vulnerability found for this question.

**Analysis:** The claimed break requires an attacker to choose a `signer_id` (implicit account string) that "collides" with a public key they do not own. However, `PublicKey::to_implicit_account_id` derives the account id deterministically and one-way (hex encoding of the Ed25519 key, or Keccak256 hash for Secp256k1/P256) [1](#0-0) . `StateView::has_public_key`'s fallback for accounts with no explicit `Account` record checks exactly `account_id == public_key.to_implicit_account_id()` [2](#0-1) , and `public_key` here is not attacker-supplied metadata — it is the value returned by `MultiPayload::verify()`, which recovers/validates the key that cryptographically produced the signature over the payload [3](#0-2) [4](#0-3) .

For the fallback check to pass with a `signer_id` the attacker does not control the private key for, the attacker would need to find a public key whose deterministic hash/encoding equals a chosen implicit account string without knowing the corresponding private key — i.e., invert a preimage-resistant hash or forge a signature, which is cryptographically infeasible and out of scope (key compromise). This is the same binding NEAR itself uses to define implicit accounts, and it is enforced identically for named accounts once an explicit `Account` entry exists, where `Account::has_public_key` also gates on `me == public_key.to_implicit_account_id()` or explicit membership in `public_keys` [5](#0-4) . No path exists for an unprivileged attacker to make `execute_intents` credit/debit an implicit account's balance without actually possessing the matching private key.

impl PublicKey {
    #[inline]
    pub fn to_implicit_account_id(&self) -> AccountId {
        match self {
            Self::Ed25519(pk) => {
                // https://docs.near.org/concepts/protocol/account-id#implicit-address
                hex::encode(pk)
            }
            Self::Secp256k1(pk) => {
                // https://ethereum.org/en/developers/docs/accounts/#account-creation
                format!("0x{}", hex::encode(&Keccak256::digest(pk)[12..32]))
            }
            Self::P256(pk) => {
                // In order to keep compatibility with all existing standards
                // within Near ecosystem (e.g. NEP-245), we need our implicit
                // account_ids to be fully backwards-compatible with Near's
                // implicit AccountId.
                //
                // To avoid introducing new implicit account id types, we
                // reuse existing Eth Implicit schema with same hash func.
                // To avoid collisions between addresses for different curves,
                // we add "p256" ("\x70\x32\x35\x36") prefix to the public key
                // before hashing.
                //
                // So, the final schema looks like:
                // "0x" .. hex(keccak256("p256" .. pk)[12..32])
                format!(
                    "0x{}",
                    hex::encode(
                        &Keccak256::new_with_prefix(b"p256")
                            .chain_update(pk)
                            .finalize()[12..32]
                    )
                )
            }
        }
        .try_into()
        .unwrap_or_else(|_| unreachable!())
    }
