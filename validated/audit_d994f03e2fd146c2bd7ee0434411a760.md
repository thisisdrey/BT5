### Title
`ValidateMultiSign` precompile signs over account address/permission/data with no chain-domain separator, enabling cross-chain signature replay - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The `ValidateMultiSign` precompiled contract (TVM address `0x...0a`) is the general on-chain multisig-authorization primitive exposed to any smart contract. It recomputes the signed message as `sha256(address || permissionId || data)` and checks recovered signer weight against the account's on-chain `Permission`, with no chain identifier, genesis hash, or contract-instance value mixed into the hash. This mirrors the ChakraSettlement bug class: the signed payload omits any binding to "which chain/deployment this signature is valid for," so a signature produced for use against one chain (or one deployment) can be replayed to satisfy the identical `validatemultisign()` check on another chain that happens to have the same address/`Permission` configuration for that account.

### Finding Description
`ValidateMultiSign.execute` builds the verification hash as: [1](#0-0) 
and then recovers each signer and checks their weight against `account.getPermissionById(permissionId)` fetched from the executing chain's own state: [2](#0-1) 

Unlike a native TRON `Transaction`, whose signed hash is derived from `getTransactionId()` — itself bound to `ref_block_hash`/`ref_block_bytes` taken from a specific chain's recent block, providing implicit chain/state binding — this precompile's hash is built entirely from caller-supplied `address`, `permissionId`, and an arbitrary `data` word plus signatures, with no chain-specific salt at all: [3](#0-2) 

`Permission` objects (multisig key sets and thresholds) are ordinary account state that any account owner configures identically on multiple TRON-compatible networks (mainnet, a private/consortium chain, or any fork sharing the same genesis/account state), and TRON account addresses are derived purely from the private key with no chain-id mixed in, so the same address/permission pair can legitimately exist with the same signer set on two different chains. Any dApp/contract that uses `validatemultisign()` as its cross-chain or multi-environment authorization gate (e.g., custom bridges, vaults, or governance modules built on top of this precompile, exactly analogous to how `ChakraSettlement` builds its own signed payload without `to_chain`) inherits this gap: nothing in the precompile's hash or logic prevents the exact same `(address, permissionId, data, signatures)` tuple from being replayed against an identically-configured account/permission on a different chain.

### Impact Explanation
Any contract that relies on `validatemultisign()` for authorizing sensitive actions (fund release, minting, state transitions) across more than one chain/environment sharing account/permission state can have valid signatures from one chain replayed to authorize the same action on another chain, leading to unauthorized asset transfers or unbacked state changes — a direct funds-theft/freezing risk, consistent with the High severity of the original finding.

### Likelihood Explanation
Exploitability requires that the same address/`Permission` configuration exist on two chains that both expose the identical dApp logic calling `validatemultisign()`, which is realistic for consortium/testnet/mainnet deployments derived from the same account setup, and is directly analogous to the deterministic-deployment scenario described in the original report. No special privilege beyond normal contract deployment/invocation is needed to exploit it once such a dual-chain setup exists.

### Recommendation
Mix a chain-specific domain separator (e.g., `chain_id` from dynamic properties, or the genesis block hash) into the hash computed in `ValidateMultiSign.execute` (and consider the same for `BatchValidateSign`), so that a signature computed for one chain cannot satisfy the check on another chain even when address/permission state coincide.

### Proof of Concept
1. Deploy the same account (same private key ⇒ same address) with an identical `Permission` (same signer keys, same threshold, same `permissionId`) on two TRON-compatible chains A and B (e.g., a mainnet fork/private chain sharing genesis/account state with mainnet).
2. Deploy identical application contracts on both chains that call `validatemultisign(address, permissionId, data, signatures)` to gate a sensitive action (e.g., release of locked funds keyed by `data`).
3. Off-chain, the required signers sign `sha256(address || permissionId || data)` intending the signatures to authorize the action only on chain A.
4. Submit the same `(address, permissionId, data, signatures)` tuple to the equivalent contract call on chain B. Because `ValidateMultiSign.execute` computes the identical hash and checks against the identical `Permission` weight/threshold with no chain-binding value, the check at `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java:1080-1110` succeeds and the sensitive action executes on chain B, even though the signers never intended to authorize it there.
