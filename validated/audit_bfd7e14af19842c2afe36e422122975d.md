### Title
Unauthenticated QUIC handshake flood can exhaust `ClientConnectionTracker` slots and starve legitimate peers - ([File: streamer/src/nonblocking/quic.rs])

### Summary
The QUIC accept loop allocates a `ClientConnectionTracker` slot (bounded by `qos.max_concurrent_connections()`) *before* the handshake completes, and the per-IP `ConnectionRateLimiter` only tracks IPs that have already completed a handshake (`register_connection` is called post-handshake). An unprivileged remote client can therefore open many connections that never finish their handshake, hold tracker slots for up to `QUIC_CONNECTION_HANDSHAKE_TIMEOUT` (2s) each, and repeatedly refill them faster than they expire, causing legitimate incoming connections to be refused via `refused_connections_too_many_open_connections`.

### Finding Description
In `run_server`, incoming connections pass two pre-handshake checks before a `ClientConnectionTracker` is allocated: the global `overall_connection_rate_limiter` and the per-IP `rate_limiter.is_allowed(ip)` [1](#0-0) . Critically, `ConnectionRateLimiter::is_allowed` only consults tokens for IPs that have an existing record, and returns `true` for any IP with no record — records are only created by `register_connection`, which is explicitly called only *after* a successful handshake in `setup_connection` [2](#0-1) [3](#0-2) . This is a deliberate design choice per the comment in `run_server` (avoid IP-based punishment before "a peer has asserted control over their IP address") [4](#0-3) , but its side effect is that unfinished handshakes from a single IP are never throttled by the per-IP limiter.

`ClientConnectionTracker::new` is created immediately once the connection passes the two pre-handshake checks, incrementing `stats.open_connections` and enforcing only `qos.max_concurrent_connections()` [5](#0-4) . It is then handed into `setup_connection`, which awaits the handshake wrapped in `timeout(QUIC_CONNECTION_HANDSHAKE_TIMEOUT, connecting)` — 2 seconds [6](#0-5) [7](#0-6) . If the attacker never completes the handshake, the tracker (and its slot) is held for the full 2 seconds before being dropped in the `Err` (timeout) branch [8](#0-7) .

Because the only remaining guard against a burst of unfinished handshakes is the *global* `overall_connection_rate_limiter` (`TOTAL_CONNECTIONS_PER_SECOND = 2500`, burst `MAX_CONNECTION_BURST = 1000`) [9](#0-8) [10](#0-9) , a single unprivileged attacker can, by itself, drive enough Initial-packet-only connection attempts to consume the whole global budget, sustaining occupation of the tracker table at/above `qos.max_concurrent_connections()` for as long as it keeps generating new never-completing handshakes faster than the 2-second timeout releases old ones. Once `open_connections >= max_concurrent_connections`, subsequent legitimate `incoming.accept()` calls (from real staked/unstaked peers) are refused and counted as `refused_connections_too_many_open_connections` [11](#0-10) .

### Impact Explanation
This is a TPU-port connection-slot exhaustion denial of service: legitimate transaction traffic to the leader is refused while the flood is sustained, and the attacker never needs stake, valid handshake completion, or any privileged position — only the ability to send QUIC Initial packets to the public TPU port. Impact is bounded to connection admission (not persistent memory growth, since each slot self-expires after 2s), but it is continuously renewable as long as the attacker sustains packet generation, matching the "TPU connection slot exhaustion for the full timeout window" scoped impact and Agave's transient-resource-exhaustion / availability bounty category.

### Likelihood Explanation
Feasible for a single unprivileged remote client: it requires only crafting QUIC Initial packets that pass `incoming.accept()`'s early validation (i.e., enough to be treated as an `Incoming` and returned by `endpoints[i].accept()`) and then withholding the remaining handshake flight (or replying so slowly/incompletely that `Connecting` never resolves within 2s). No stake, cryptographic completion, or multiple source IPs are strictly required, since the per-IP limiter never engages for unverified IPs; a single IP can already exceed typical `max_concurrent_connections` settings well below the 2500/s global cap. This is continuously repeatable — the attacker simply keeps a steady stream of new half-open attempts to refill freed slots.

### Recommendation
Apply a lightweight per-IP/connection-attempt cap on *outstanding, unverified* connections (not just completed ones) — e.g., track and rate-limit `outstanding_incoming_connection_attempts` per source IP before/at `ClientConnectionTracker::new`, or reserve only a fraction of `max_concurrent_connections` for not-yet-handshaked connections so a single unverified source cannot monopolize the whole table. Alternatively, reduce `QUIC_CONNECTION_HANDSHAKE_TIMEOUT` adaptively under load or require a stateless retry/token before consuming a tracker slot at all (QUIC's built-in Retry mechanism already exists for IP-ownership proof — ensure it is enforced prior to tracker allocation rather than only informing post-hoc rate limiting).

### Proof of Concept
Rust integration test plan against `streamer::nonblocking::quic::spawn_server` / `run_server` test harness (`setup_quic_server` used elsewhere in `streamer/src/nonblocking/quic.rs` tests):
1. Configure `SwQosConfig` with a small `max_concurrent_connections` (e.g., 5) and default `QuicStreamerConfig`.
2. From a single client `Endpoint`, open `max_concurrent_connections()` QUIC connections whose `Connecting` futures are engineered to stall (e.g., by connecting to the server but never sending/receiving the final handshake flight — achievable by pausing the client task right after `endpoint.connect()` before awaiting, or using a raw UDP socket to send only an Initial packet and then go silent).
3. Assert `stats.open_connections.load(Ordering::Relaxed) == max_concurrent_connections()` while attempts are stalled.
4. From a second, legitimate client, attempt `make_client_endpoint(&server_address, None).await` and assert it is refused, and `stats.refused_connections_too_many_open_connections.load(Ordering::Relaxed) > 0`.
5. Wait > `QUIC_CONNECTION_HANDSHAKE_TIMEOUT` (2s) without sending further attacker attempts, then retry the legitimate client and assert it now succeeds, confirming slots are recycled — demonstrating the exhaustion window and its exploitability by a single unverified IP that never registers with the per-IP `ConnectionRateLimiter`.

    /// Check if the connection from the said `ip` is allowed.
    /// Here we assume that only IPs with actual confirmed connections are stored in it,
    /// since we should only modify server state once source IP is verified
    pub fn is_allowed(&self, ip: &IpAddr) -> bool {
        // Check if we have records in the rate limiter for the given IP address
        match self.limiter.current_tokens(ip) {
            Some(r) => r > 0, // we have a record, and rate is not exceeded
            None => true,     // if we have not seen IP, allow connection request
        }
    }

    pub fn register_connection(&self, ip: &IpAddr) -> bool {
        if self.limiter.consume_tokens(*ip, 1).is_ok() {
            debug!("Request from IP {ip:?} allowed");
            true // Request allowed
        } else {
            debug!("Request from IP {ip:?} blocked");
            false // Request blocked
        }
    }
