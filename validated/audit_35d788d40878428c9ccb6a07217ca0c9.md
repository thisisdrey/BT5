### Title
Duplicated delayed-receipt queue is fully inherited (not split) by both resharding children, letting one attacker's pre-split flood fully congest and reject transactions on both new shards simultaneously - ([File: chain/chain/src/resharding/manager.rs])

### Summary
When a shard splits, `ReshardingManager::get_child_congestion_info_not_finalized` copies the parent's `delayed_receipts_gas` verbatim into both the left and right child's `CongestionInfo`, while only `buffered_receipts_gas`/`receipt_bytes`-for-buffered are adjusted for the right child. Because the delayed queue itself is physically duplicated into both children's tries (per `docs/architecture/how/resharding_v2.md`), both children start the new epoch believing they own the *entire* parent's delayed-receipt gas, even though `receipt_filter_fn`-driven trimming (which discards receipts not addressed to the local shard) has not yet run. An attacker who floods the parent's delayed queue right before the split can therefore push `congestion_level()` to 1.0 on both children at once, causing `shard_accepts_transactions()` to reject new transactions on both shards for a period of time until the duplicate is drained.

### Finding Description
`CongestionControl::congestion_level` (`core/primitives/src/congestion_info.rs:44`) is the max of `incoming_congestion = delayed_receipts_gas / max_congestion_incoming_gas` (`:331`). `shard_accepts_transactions` (`:123`) rejects new transactions once this reaches `reject_tx_congestion_threshold` (default 0.8).

At the split boundary, `ReshardingManager::get_child_congestion_info` (`chain/chain/src/resharding/manager.rs:297`) calls `get_child_congestion_info_not_finalized` (`:327`):
- For the **left child** (`RetainMode::Left`), the function returns `parent_congestion_info` unchanged (`:335-337`) — comment: "The left child contains all the delayed and buffered receipts from the parent so it should have identical congestion info."
- For the **right child**, only `buffered_receipts_gas` and the corresponding `receipt_bytes` are subtracted, using `ReceiptGroupsQueue` (buffered receipts only) (`:339-358`). **`delayed_receipts_gas` is never adjusted for the right child.**

This matches `DelayedReceiptQueueWrapper::upper_bound_len` documentation (`runtime/runtime/src/congestion_control.rs:922-929`): "During resharding, we duplicate the delayed receipt queue across both child shards, which means it's possible that the child shards contain delayed receipts that don't belong to them," and `docs/architecture/how/resharding_v2.md` ("Why delayed receipts are special") confirms the delayed queue is physically copied to both children rather than partitioned.

The actual per-shard filtering happens lazily in `DelayedReceiptQueueWrapper::pop` (`congestion_control.rs:880-910`) via `receipt_filter_fn` (`:874`), which only fires as receipts are popped during `process_delayed_receipts` in subsequent chunk applications — bounded by the chunk's compute/proof-size limit each height. This correction happens *after* the child's initial `CongestionInfo` (used to gate transaction admission for the very next height, via `congestion_control_accepts_transaction` in `chain/chain/src/runtime/mod.rs:1722-1743`, which reads `prev_block.congestion_info`) has already been computed and persisted in the child's `ChunkExtra` at split time.

An unprivileged attacker can:
1. Before the resharding epoch boundary, submit many function-call transactions whose resulting receipts get pushed into the shard's delayed queue (e.g., by targeting a congested-shard account, or by attaching heavy function-call gas so receipts exceed the per-chunk compute limit and get delayed) — no special privileges, keys, or roles required, just funded transactions with attached gas (`compute_receipt_congestion_gas`, `runtime/runtime/src/congestion_control.rs:678`).
2. This inflates `delayed_receipts_gas` in the parent's `CongestionInfo` toward `max_congestion_incoming_gas`.
3. At the epoch boundary, the shard splits; both children inherit the identical, undivided `delayed_receipts_gas` (per the code above).
4. `congestion_level()` on both children can reach/exceed `reject_tx_congestion_threshold`, and both call `shard_accepts_transactions().is_no()`, rejecting transactions targeting either child — even the child whose *own* true share of the receipts is small.

No existing signature/nonce/access-key/gas-metering check stops this: congestion-based tx admission is deliberately triggerable by high gas usage; the flaw is that the resharding-time attribution of `delayed_receipts_gas` to children is not split by ownership, unlike the buffered-receipt case which the code does correctly split.

### Impact Explanation
This is a temporary denial-of-service: `shard_accepts_transactions` rejects new transactions targeting either child shard, freezing new activity there for one attacker's action, for a duration bounded by how quickly the compute-limited delayed-queue drain (interleaved with `receipt_filter_fn` skips) reduces `delayed_receipts_gas` back under threshold. This matches NEP-539 congestion-control DoS category (liveness/availability, not fund loss or consensus divergence).

### Likelihood Explanation
Feasible for an ordinary funded account: only requires submitting enough function-call transactions with attached gas to inflate `delayed_receipts_gas` close to `max_congestion_incoming_gas` before a scheduled/dynamic resharding split, timed near the shard boundary so the flood lands in the shard about to split. Dynamic resharding thresholds and cooldowns (`check_dynamic_resharding`) determine exactly when a split happens, and `proposed_split`/`get_upcoming_shard_split` are publicly derivable, making the timing knowable in advance. Cost scales with attached gas fees but is otherwise unprivileged and repeatable each time a shard splits.

### Recommendation
Split `delayed_receipts_gas` (and `receipt_bytes` attributable to delayed receipts) between children at resharding time analogous to how buffered receipts are split — e.g., by iterating the delayed queue's receipt metadata (or maintaining per-child gas/byte counters during the flat-storage split) to attribute gas only to the child that actually owns each receipt, instead of copying the parent's full `delayed_receipts_gas` to both children.

### Proof of Concept
Test-loop integration test, extending `test-loop-tests/src/tests/resharding_v3.rs`:
1. Configure a dynamic-resharding scenario with `TestReshardingParametersBuilder`, selecting a boundary account so a shard will split into a known left/right child pair.
2. Before the resharding epoch boundary, from a single funded attacker account, submit a large batch of function-call transactions to accounts on the parent shard such that receipts pile up in the delayed queue and are not fully drained before the split (attach heavy gas per call, e.g., `Gas::from_teragas(275)`, similar to existing `call_burn_gas_contract` helper).
3. Trigger the split (advance to the new epoch).
4. At the first post-split height, read `congestion_info` from both children's `ChunkExtra` (as in `insert_delayed_receipts`/`get_trie_node_value` helpers in `test-loop-tests/src/utils/resharding.rs`) and compute `CongestionControl::congestion_level()`/`shard_accepts_transactions()` for each.
5. Also submit an unrelated, low-value transaction from an innocent account targeting each child shard at that height and observe `RejectTransactionReason`.
6. Assert: both children report `congestion_level() >= reject_tx_congestion_threshold` and `shard_accepts_transactions().is_no()` immediately post-split, even though only one child truly owns the majority of the flooded receipts — demonstrating the duplicated-queue over-counting causes rejection on the shard that should not be congested.
