### Title
Legacy `ExchangeProcessor` bancor-style pow calculation causes precision-loss induced loss of funds/incorrect settlement in TRC10 Exchange trades - (File: `chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java`)

### Summary
`ExchangeProcessor#exchangeToSupply`/`exchangeFromSupply` implement the same bancor-formula compound-power calculation pattern as the DODO V3 `powFloor`/`getCompoundInterestRate` bug: a power function evaluated on a small ratio, truncated to an integer, which silently produces `0` (or otherwise incorrect) results when the ratio between trade quantity and pool balance is small enough that precision is lost.

### Finding Description
`ExchangeProcessor` computes the AMM output using `Math.pow`/`StrictMath.pow` on a `double` ratio and then truncates the result with a `(long)` cast: [1](#0-0) [2](#0-1) 

This is structurally the same bug class as the reported DODO issue: a power/compounding function whose precision loss at small magnitudes causes the computed amount to round down to `0` (or to an incorrect nonzero value), producing incorrect settlement for legitimate trades rather than the mathematically-correct proportional amount. This processor is reached directly from unprivileged, permissionless actuators — `ExchangeTransactionActuator`, `ExchangeInjectActuator`, and `ExchangeWithdrawActuator` — via `ExchangeCapsule#transaction`: [3](#0-2) 

Critically, `ExchangeProcessor` (the imprecise, double-based implementation) is still the *default* code path; the precise `BigDecimal`-based `SafeExchangeProcessor` is only used when the `hardenedCalc` flag — gated by the `allowHardenExchangeCalculation` dynamic property/committee proposal — is turned on: [4](#0-3) [5](#0-4) 

The repository's own test suite acknowledges the class of bug by asserting that the legacy (non-hardened) `ExchangeProcessor` and the hardened `SafeExchangeProcessor` diverge for the same inputs: [6](#0-5) 

I was unable to confirm from the indexed code whether `allowHardenExchangeCalculation` currently defaults to enabled on mainnet (the getter/default in `DynamicPropertiesStore.java` was not retrievable via search in the time available), so whether the vulnerable path is presently exercised in production depends on that on-chain committee-controlled flag.

### Impact Explanation
If the hardening proposal is not (or was not historically) enabled, any unprivileged account calling `ExchangeTransactionContract`/`ExchangeInjectContract`/`ExchangeWithdrawContract` with a trade size that is small relative to the pool's virtual "supply" causes `exchangeToSupply`/`exchangeFromSupply` to truncate to an incorrect (including zero) output. This can cause traders to receive zero or an incorrect (non-proportional) amount of the other asset while their input is still consumed/pool balances updated, i.e., loss of funds/value for the trader and/or state corruption of the exchange pool's tracked balances — analogous to the "loss of yield" impact described in the report, but here manifesting as loss of trade proceeds for exchange participants.

### Likelihood Explanation
Likelihood is directly tied to whether the `allowHardenExchangeCalculation` committee proposal is active on the network. If inactive (or before it was ever activated), every ordinary user of the legacy on-chain TRC10 Exchange feature is exposed whenever the trade quantity is small relative to the exchange pool's supply/balance — a condition that is easily reachable by any transaction broadcaster without special privileges.

### Recommendation
Make the `BigDecimal`-based `SafeExchangeProcessor` the unconditional implementation (remove/retire the double/`Math.pow`-based `ExchangeProcessor` entirely) rather than gating correctness behind an opt-in governance flag, so correctness does not depend on the state of `allowHardenExchangeCalculation`.

### Proof of Concept
Not independently reproduced against a live/hardened-off node in this investigation; the precision-loss mechanism is demonstrated by the divergence asserted in the existing test `ExchangeProcessorTest#testStrictMath`, which shows the same inputs producing different results between the double-based `ExchangeProcessor` and the `BigDecimal`-based `SafeExchangeProcessor`: [6](#0-5)
