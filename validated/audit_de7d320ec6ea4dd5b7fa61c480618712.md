The reported OpenClaw issue is about custom MCP headers being forwarded across a cross-origin redirect. The closest analog in this Go repository is `net/http`'s `Client` redirect-following logic in `src/net/http/client.go`, but that code already implements the exact defense the OpenClaw advisory says was missing.

- `Client.do` computes `stripSensitiveHeaders` by calling `shouldCopyHeaderOnRedirect(reqs[0].URL, req.URL)` whenever the redirect target's host differs from the original host, and passes that flag into `copyHeaders`. [1](#0-0) 
- `makeHeadersCopier`'s returned closure explicitly strips `Authorization`, `Www-Authenticate`, `Cookie`, `Cookie2`, `Proxy-Authorization`, and `Proxy-Authenticate` when `stripSensitiveHeaders` is set, i.e., on a cross-origin (non subdomain/exact-match) redirect. [2](#0-1) 
- `shouldCopyHeaderOnRedirect`/`isDomainOrSubdomain` implement the origin comparison (exact host or subdomain match only), and this logic is unit-tested with an explicit table of cross-domain cases. [3](#0-2) [4](#0-3) 
- There is also a regression test (`TestClientStripHeadersOnRepeatedRedirect`, tracking issue #70530) verifying that once a sensitive header is stripped on a cross-origin hop, it stays stripped for the rest of the redirect chain, even if control returns to the original host. [5](#0-4) 

The one gap that does exist by design — and is explicitly documented — is that `Client` only strips the fixed list of "sensitive" headers above; arbitrary custom headers (e.g., an API key header a caller sets manually) are forwarded across cross-origin redirects unless the caller uses `CheckRedirect` to intervene. This is stated directly in the `Client` doc comment as intended, long-standing, Go-1-compatible behavior, not an unpatched defect: [6](#0-5) [7](#0-6) 

Since this is documented, tested, intentional permissive behavior (dating to Go issue #4800) with an existing mitigation path (`Client.CheckRedirect`), it does not qualify as a new, unpatched vulnerability matching the OpenClaw analog — it is the same primitive class Go already defends against for the specific sensitive-header case, and the general custom-header case is explicitly called out as a documented limitation rather than a silent bug.

func shouldCopyHeaderOnRedirect(initial, dest *url.URL) bool {
	// Permit sending auth/cookie headers from "foo.com"
	// to "sub.foo.com".

	// Note that we don't send all cookies to subdomains
	// automatically. This function is only used for
	// Cookies set explicitly on the initial outgoing
	// client request. Cookies automatically added via the
	// CookieJar mechanism continue to follow each
	// cookie's scope as set by Set-Cookie. But for
	// outgoing requests with the Cookie header set
	// directly, we don't know their scope, so we assume
	// it's for *.domain.com.

	ihost, err1 := httpguts.PunycodeHostPort(initial.Hostname())
	dhost, err2 := httpguts.PunycodeHostPort(dest.Hostname())
	if err1 != nil || err2 != nil {
		return false
	}
	ihost, ok1 := ascii.ToLower(ihost)
	dhost, ok2 := ascii.ToLower(dhost)
	return ok1 && ok2 && isDomainOrSubdomain(dhost, ihost)
}

// isDomainOrSubdomain reports whether sub is a subdomain (or exact
// match) of the parent domain.
//
// Both domains must already be in canonical form.
func isDomainOrSubdomain(sub, parent string) bool {
	if sub == parent {
		return true
	}
	// If sub contains a :, it's probably an IPv6 address (and is definitely not a hostname).
	// Don't check the suffix in this case, to avoid matching the contents of a IPv6 zone.
	// For example, "::1%.www.example.com" is not a subdomain of "www.example.com".
	if strings.ContainsAny(sub, ":%") {
		return false
	}
	// If sub is "foo.example.com" and parent is "example.com",
	// that means sub must end in "."+parent.
	// Do it without allocating.
	if !strings.HasSuffix(sub, parent) {
		return false
	}
	return sub[len(sub)-len(parent)-1] == '.'
}
