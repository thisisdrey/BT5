## Analysis

The Sherlock report's core broken invariant is: **a per-item settlement loop assumes the transfer call always succeeds, and advances/deletes bookkeeping state unconditionally** — so a single failing transfer either (a) blocks the whole queue forever (CrabNetting's cursor never advances), or (b) silently loses the state-tracking record while the funds stay stuck.

Searching the FRAME code for the same pattern — "transfer, then unconditionally finalize/delete tracking state" — the closest and most exploitable local analog is `pallet-bounties`/`pallet-child-bounties`, which still use raw `Currency::transfer` calls guarded only by `debug_assert!`, which compiles to a no-op in release builds.

## Title
Bounty/child-bounty claim deletes tracking state via `debug_assert!` even when the payout `Currency::transfer` fails, permanently stranding funds - (File: `substrate/frame/bounties/src/lib.rs`, `substrate/frame/child-bounties/src/lib.rs`)

## Summary
`Bounties::claim_bounty` and `ChildBounties::claim_child_bounty` (and `impl_close_child_bounty`) perform `T::Currency::transfer(...)` to pay the curator fee and beneficiary payout, but only check the result with `debug_assert!(res.is_ok())` [1](#0-0) [2](#0-1) . `debug_assert!` is compiled out entirely in release (non-`debug-assertions`) builds, which is how production runtimes are built. Regardless of whether the transfer succeeds, the code unconditionally proceeds to delete the bounty/child-bounty tracking entry: `*maybe_bounty = None;` / `*maybe_child_bounty = None;` [3](#0-2) [4](#0-3) .

## Finding Description
The bounty/child-bounty sub-accounts (`bounty_account_id`, `child_bounty_account_id`) are pallet-derived keyless accounts; there is no separate rescue/recovery extrinsic to move funds out of them once their tracking entry is removed from storage. The claim flow is:

1. Read balance of the bounty account, compute `fee`/`payout`.
2. `T::Currency::transfer(&bounty_account, &curator, fee, AllowDeath)` — result only `debug_assert!`-checked.
3. `T::Currency::transfer(&bounty_account, &beneficiary, payout, AllowDeath)` — same.
4. Unconditionally set `*maybe_bounty = None` / `*maybe_child_bounty = None`, remove descriptions, decrement counters, and emit a `Claimed`/`BountyClaimed` event as if the payout succeeded.

This mirrors exactly the CrabNetting flaw's root cause — code that assumes an external-facing balance transfer cannot fail — except here the direction of the failure mode is reversed: instead of the *queue cursor* getting stuck (blocking future operations), the *tracking record* is deleted despite the transfer failing, so the funds become permanently unreachable (no bounty index remains to retry `claim_bounty`/`claim_child_bounty`, and no governance call exists to sweep an orphaned bounty sub-account). This directly violates the stated Polkadot SDK pivot: "payout state must only advance after ... settlement succeed atomically."

A transfer can realistically fail for a beneficiary/curator account whose receiving path is blocked — e.g. a `pallet-assets`-backed `Currency` implementation where the destination account has been frozen (analogous to a USDC-style blacklist), or where the transfer would push the destination account's balance past a type-level overflow bound, or any other case where the `Currency::transfer` trait implementation legitimately returns `Err(_)`. None of these require a privileged actor, malicious validator, or governance abuse — the failure condition lives entirely on the recipient side of an otherwise permissionless `claim_bounty`/`claim_child_bounty` call, which "anyone can trigger" per the code's own doc comment [5](#0-4) .

Existing guards do not stop this path: there is no `ensure!`/`?` on the transfer `Result`, no retry mechanism (contrast with the newer `pallet-treasury::payout`/`check_status` design and `multi-asset-bounties`, which explicitly track `PaymentState` and support `check_status`/`retry_payment` for exactly this failure mode) [6](#0-5) [7](#0-6) , and no rescue extrinsic in `pallet-bounties`/`pallet-child-bounties` to recover funds from an orphaned sub-account.

## Impact Explanation
Funds parked in a bounty/child-bounty sub-account can become permanently locked/unreachable once the tracking record is deleted despite a failed transfer, because no extrinsic exists to re-derive or reclaim that specific sub-account's balance without the bounty index. This is a "permanent user-fund lock" per the required-impact list, triggered without any privileged actor, malicious validator/collator, or governance abuse — purely via the retained `debug_assert!` instead of proper error propagation.

## Likelihood Explanation
Likelihood depends on the concrete `T::Currency` implementation used for a given runtime's bounty pallet instance. For plain `pallet-balances`, a transfer to an arbitrary receiver rarely fails outright. However, any runtime that backs bounties with an asset type supporting account freezing/blocking (directly analogous to the USDC blacklist in the original report) makes this trivially triggerable by an attacker positioning themselves (or an account they control) as beneficiary/curator with a subsequently blocked receiving path — mirroring Bob's strategy in the source report of pre-obtaining a blocked address and timing the claim.

## Recommendation
Replace `debug_assert!(res.is_ok())` with proper error propagation (`?` or `ensure!`) so that a failed transfer aborts the extrinsic without deleting the bounty/child-bounty tracking state, and/or adopt the `PaymentState`-with-`check_status`/`retry_payment` pattern already used by `pallet-treasury` and `pallet-multi-asset-bounties` so that a failed payout can be retried instead of silently discarding both the payment and the record needed to retry it.

## Proof of Concept
1. Configure (or imagine) a runtime where `pallet-bounties`'/`pallet-child-bounties`' `T::Currency` is backed by an asset type that supports per-account freeze/block (e.g., a `fungibles`-adapter over `pallet-assets` with an issuer-frozen account, analogous to a USDC blacklist).
2. Attacker becomes the beneficiary (or curator) of an active bounty/child-bounty whose payout is pending, using an address they know can be frozen.
3. Attacker (or the asset issuer, independent of this pallet) freezes that receiving address.
4. Any account calls `claim_bounty(bounty_id)` / `claim_child_bounty(parent_bounty_id, child_bounty_id)`.
5. `T::Currency::transfer(...)` to the frozen beneficiary/curator returns `Err(_)`; in a release build `debug_assert!` is compiled away, so no panic occurs.
6. Code proceeds to `*maybe_bounty = None` / `*maybe_child_bounty = None`, removing all tracking storage and emitting `Claimed`/`BountyClaimed` events.
7. The bounty sub-account (`bounty_account_id`/`child_bounty_account_id`) still holds the un-transferred balance, but there is no remaining bounty index or extrinsic to retry or reclaim it — the funds are permanently stranded.

			ensure_signed(origin)?;
			let mut spend = Spends::<T, I>::get(index).ok_or(Error::<T, I>::InvalidIndex)?;
			let now = T::BlockNumberProvider::current_block_number();
			ensure!(now >= spend.valid_from, Error::<T, I>::EarlyPayout);
			ensure!(spend.expire_at > now, Error::<T, I>::SpendExpired);
			ensure!(

				Error::<T, I>::AlreadyAttempted
			);

			let id = T::Paymaster::pay(&spend.beneficiary, spend.asset_kind.clone(), spend.amount)
