### Title
Unauthenticated peer-reported chunk-inv versions poison `expected_versions`, causing legitimate StackerDB chunk updates to be permanently rejected as stale - (File: stackslib/src/net/stackerdb/sync.rs)

### Summary
`StackerDBSync::recalculate_chunk_request_schedule` computes the node's `expected_versions` bookkeeping by taking the **maximum** `slot_version` reported across all connected replicas' `StackerDBChunkInv` messages, rather than deriving it from the locally-stored, cryptographically-verified slot versions. Because `StackerDBChunkInvData.slot_versions` is unauthenticated wire data supplied by any p2p neighbor, a malicious neighbor can report an inflated version number for any slot, which is then adopted as ground truth and used to reject subsequent legitimate (correctly signed, lower-numbered) chunk updates as stale.

### Finding Description
`StackerDBSync::recalculate_chunk_request_schedule` builds `expected_versions` purely from `self.chunk_invs`, the map of per-neighbor `StackerDBChunkInvData` replies: [1](#0-0) 

`chunk_invs` is populated in `pushchunks_try_finish` from `StackerDBChunkInvData` messages returned by any neighbor a chunk was pushed to, gated only by a length check (`slot_versions.len() == self.num_slots`) — there is no signature or authentication over the vector of version numbers itself: [2](#0-1) 

The resulting `expected_versions` is later used by `validate_downloaded_chunk` / `PeerNetwork::validate_received_chunk` to gate acceptance of legitimately signed chunks: any chunk whose `slot_version` is less than the (attacker-inflated) `expected_version` is rejected as `StaleChunk`, and any chunk whose `slot_version` exceeds `config.max_writes` is rejected outright: [3](#0-2) 

This contrasts with the "correct" path in `getchunksinv_try_finish`, which instead derives `expected_versions` from the node's own authenticated, locally-stored slot versions via `self.stackerdbs.get_slot_versions(...)`: [4](#0-3) 

The equality broken here is: "chunk version accepted as canonical" should equal "chunk version actually verified/stored by us (or the honest max thereof)," but `recalculate_chunk_request_schedule` instead trusts an arbitrary, unauthenticated per-slot integer supplied by any connected peer replying to a push. A single malicious neighbor can set an artificially high `slot_versions[i]` (up to `u32::MAX`) for a slot it does not even own, causing the victim's local `expected_versions[i]` to jump to that value. All subsequent genuine chunks for slot `i` — signed by the legitimate slot owner with normal, incrementing version numbers — will then fail the `data.slot_version < *expected_version` check in `validate_received_chunk` and be dropped as stale, indefinitely (until an honest peer coincidentally reports an even higher spurious value, or until the sync object is fully reset via `reset()`/`getchunksinv_try_finish`, which itself can be re-poisoned on the next push round).

### Impact Explanation
This is a **bounded compute/state DoS on StackerDB chunk propagation**: an unprivileged remote peer that establishes a normal p2p connection can, without any private key or admin role, cause a victim node to stop accepting/relaying legitimate signer or miner StackerDB messages for a targeted slot. Since StackerDB is used for signer coordination (`.signers-*` contracts) and miner block-commit gossip (`.miners`), this can degrade or stall the propagation of legitimate signer/miner messages on the victim node, which is used for consensus-adjacent signaling. It does not require the attacker's own node's data to be authenticated for the *fields being trusted* (the version integers), only that the attacker be a connected p2p neighbor who receives at least one `StackerDBPushChunk` from the victim and replies with a crafted `StackerDBChunkInv`.

### Likelihood Explanation
Likelihood is moderate-to-high: exploitation only requires becoming an ordinary p2p neighbor of the victim (no elevated permission) and waiting for/being selected as a push target during `pushchunks_begin`, then replying with a well-formed-length but falsified `StackerDBChunkInvData`. No cryptographic material or timing race is needed, unlike the sandwich-attack described in the source report; a single malicious reply suffices to poison the state until the next full `getchunksinv_try_finish` round overwrites it — but the poisoning recurs on the next `pushchunks_try_finish`/`recalculate_chunk_request_schedule` cycle if the attacker remains connected and keeps replying with inflated numbers.

### Recommendation
`recalculate_chunk_request_schedule` should not adopt unauthenticated peer-reported slot versions as the new `expected_versions` ground truth. Instead, it should either (a) only use `chunk_invs` values as *download prioritization hints*, keeping `expected_versions` sourced from `self.stackerdbs.get_slot_versions(...)` (as `getchunksinv_try_finish` already does), or (b) validate that a chunk purportedly at a reported high version can actually be fetched and signature-verified before raising `expected_versions` for that slot, and cap increases in `expected_versions` at `config.max_writes` derived from local, authenticated state rather than blindly trusting peer-supplied integers.

### Proof of Concept
1. Attacker connects as a normal p2p neighbor to a victim node that runs a StackerDB replica (e.g., `.signers-0-1`).
2. Victim's `StackerDBSync::pushchunks_begin` selects the attacker as a push destination for some legitimate chunk at slot `i`, version `v` [5](#0-4) .
3. Attacker replies with a `StackerDBChunkInv` whose `slot_versions[i] = u32::MAX` (only length is checked, not content) [6](#0-5) .
4. `pushchunks_try_finish` stores this into `self.chunk_invs`, and any subsequent call to `recalculate_chunk_request_schedule` sets `self.expected_versions[i] = u32::MAX` [7](#0-6) .
5. The legitimate slot owner signs and uploads a new chunk at version `v+1`; when the victim downloads/validates it via `validate_downloaded_chunk` → `validate_received_chunk`, the check `data.slot_version < *expected_version` (`v+1 < u32::MAX`) fails, and the chunk is rejected as stale [8](#0-7) , denying propagation of the legitimate update on the victim node.

    /// Recalculate the download schedule based on chunkinvs received on push
    pub fn recalculate_chunk_request_schedule(
        &mut self,
        network: &PeerNetwork,
    ) -> Result<(), net_error> {
        // figure out the new expected versions
        let mut expected_versions = vec![0u32; self.num_slots];
        for (_, chunk_inv) in self.chunk_invs.iter() {
            for (slot_version, expected_version) in chunk_inv
                .slot_versions
                .iter()
                .zip(expected_versions.iter_mut())
            {
                *expected_version = (*slot_version).max(*expected_version);
            }
        }

        let priorities =
            self.make_chunk_request_schedule(network, Some(expected_versions.clone()))?;

        self.chunk_fetch_priorities = priorities;
        self.expected_versions = expected_versions;
        Ok(())
    }
