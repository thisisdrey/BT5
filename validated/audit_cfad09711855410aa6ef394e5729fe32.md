### Title
No Vulnerability found for this question.

### Summary
The behavior described — oversized receipts (via `output_data_receivers`, promise-return, or yield mechanisms) bypassing `validate_receipt(NewReceipt)` and being clamped to `max_receipt_size` in `ReceiptSinkV2::try_forward` — is a **known, documented, and intentionally-handled** issue (nearcore issue #12606), not an undiscovered exploit. The code explicitly acknowledges the bug and implements a deliberate liveness-preserving workaround, and `ExistingReceipt` validation mode on the receiving shard is intentionally lenient to tolerate exactly this class of receipt so it does not get stuck or dropped.

### Finding Description
The comment in `runtime/runtime/src/congestion_control.rs:413-417` explicitly states: "There is a bug which allows to create receipts that are above the size limit... Let's pretend that all receipts are at most `max_receipt_size` to avoid receipts getting stuck," referencing issue #12606 directly. [1](#0-0) 

On the receiver side, `validate_receipt` deliberately skips the size check in `ExistingReceipt` mode: the `ReceiptSizeExceeded` check only runs `if mode == ValidateReceiptMode::NewReceipt`. [2](#0-1) 

The `ValidateReceiptMode::ExistingReceipt` doc comment explicitly documents this rationale: "There is a bug which allows to create receipts that are above the size limit. Runtime has to handle them gracefully until the receipt size limit bug is fixed. See https://github.com/near/nearcore/issues/12606 for details." [3](#0-2) 

Both `process_delayed_receipts` and `process_incoming_receipts` call `validate_receipt(..., ExistingReceipt)`, which — by design — accepts oversized receipts rather than rejecting them, so the receiver shard executes the receipt normally instead of panicking or dropping it. [4](#0-3) [5](#0-4) 

This exact scenario is covered by existing regression tests (`test_max_receipt_size_promise_return`, `test_max_receipt_size_value_return`, `test_max_receipt_size_yield_resume`), whose comments state the receipt "should be rejected, but currently isn't because of a bug... Runtime shouldn't die when it encounters a receipt with size above `max_receipt_size`," and which assert via `assert_oversized_receipt_occurred` that an oversized receipt is processed to completion rather than dropped or causing a panic. [6](#0-5) [7](#0-6) 

There is no evidence of "double-count or drop" of the deposit: the receipt is still forwarded intact (only the accounting `size` variable used for congestion/bandwidth bookkeeping is clamped; the actual `Receipt` object pushed to `outgoing_receipts` at line 453 is unmodified), and the receiver executes it via the normal `ExistingReceipt`-tolerant path, delivering the attached deposit as usual.

### Impact Explanation
No fund loss, freezing, double-spend, or shard halt occurs. The clamp only affects local congestion/bandwidth bookkeeping (`forward_limit.size`), not the receipt content itself, and the receiving shard's `ExistingReceipt` validation mode is intentionally designed to accept such receipts and process them to completion, guaranteeing eventual delivery consistent with the "liveness, not indefinite buffering" invariant the question worries about.

### Likelihood Explanation
N/A — this is documented, intended behavior with existing test coverage, not an exploitable flaw.

### Recommendation
No action needed for this specific path. The underlying root-cause bug (per-field limits not summing to enforce `max_receipt_size` correctly) is already tracked upstream as nearcore issue #12606; any fix should address the root-cause action/argument-size accounting (e.g., in `validate_actions_with_mode` / `action_validation.rs`) rather than the deliberate downstream congestion-control and `ExistingReceipt` tolerance, which exist specifically to keep the chain live while that root cause remains open.

### Proof of Concept
Already implemented and passing in-repo: `test-loop-tests/src/tests/max_receipt_size.rs::test_max_receipt_size_promise_return`, `test_max_receipt_size_value_return`, and `test_max_receipt_size_yield_resume`, which construct receipts exceeding `max_receipt_size` via promise-return/output-data and yield mechanisms, verify `ReceiptSizeExceeded` is raised where creation-time validation applies, and via `assert_oversized_receipt_occurred` confirm that when validation is bypassed downstream, the runtime does not die and the oversized receipt is still delivered/executed rather than dropped or stuck. [8](#0-7) [9](#0-8)

fn test_max_receipt_size_promise_return() {

    // User calls a contract method
    // Contract method creates a DAG with two promises: [A -then-> B]
    // When promise A is executed, it creates a third promise - `C` and does a `promise_return`.
    // The DAG changes to: [C ->then-> B]
    // The receipt for promise C is a maximum size receipt.
    // Adding the `output_data_receivers` to C's receipt makes it go over the size limit.
    let base_receipt_template = Receipt::V0(ReceiptV0 {
        predecessor_id: account.clone(),
        receiver_id: account.clone(),
        receipt_id: CryptoHash::default(),
        receipt: ReceiptEnum::Action(ActionReceipt {
            signer_id: account.clone(),
            signer_public_key: account_signer.public_key().into(),
            gas_price: Balance::ZERO,
            output_data_receivers: vec![],
            input_data_ids: vec![],
            actions: vec![Action::FunctionCall(Box::new(FunctionCallAction {
                method_name: "noop".into(),
                args: vec![],
                gas: Gas::ZERO,
                deposit: Balance::ZERO,
            }))],
        }),
    });
    let base_receipt_template = action_receipt_v1_to_latest(&base_receipt_template);
    let base_receipt_size = borsh::object_length(&base_receipt_template).unwrap();
    let max_receipt_size = 4_194_304;
    let args_size = max_receipt_size - base_receipt_size;

    // Call the contract

        102,
        account.clone(),
        account.clone(),
        &account_signer,
        Balance::ZERO,
        "max_receipt_size_promise_return_method1".into(),
        format!("{{\"args_size\": {}}}", args_size).into(),
        Gas::from_teragas(300),
        env.rpc_node().head().last_block_hash,
