### Title
Anti-replay window check-then-act race in `ConnectionState.Decrypt`/`VerifyRelay` allows duplicate messageCounter processing - (File: `connection_state.go`)

### Summary
`ConnectionState.Decrypt` and `ConnectionState.VerifyRelay` both violate a checks-effects pattern analogous to the reported StakingBase issue: they call `window.Check()` under `decryptLock`, release the lock, perform the expensive/blocking AEAD `DecryptDanger` operation without holding the lock, and only then reacquire the lock to call `window.Update()`. Because the lock is dropped between the check and the effect, two packets carrying the same `messageCounter` arriving concurrently (e.g. via duplicated/replayed UDP datagrams from an on-path or off-path attacker) can both pass `window.Check` before either has called `window.Update`, letting both proceed to be decrypted/verified and delivered to the application, defeating the sliding-window anti-replay guarantee.

### Finding Description
`Decrypt` at [1](#0-0)  and `VerifyRelay` at [2](#0-1)  both:
1. Lock `decryptLock`, call `window.Check(l, messageCounter)`, then **unlock**.
2. Perform `DecryptDanger` (the costly interaction) with no lock held.
3. Re-lock `decryptLock`, call `window.Update(l, messageCounter)`, then unlock.

`Bits.Check` at [3](#0-2)  is a pure read that returns true if the counter has not yet been recorded as seen; it does not mark the counter as consumed. Only `Bits.Update` at [4](#0-3)  mutates the bitmap to record the counter as seen. Because the lock is released between the read (`Check`) and the eventual write (`Update`), the sliding window state is not "reserved" atomically with the check — it mirrors the StakingBase pattern where a local/stale read is used across an external interaction window before the authoritative state is persisted, and any concurrent reentrant/parallel path can walk through the same stale check.

This is directly analogous to the reported class ("Checks-Effects-Interactions violation... allows reentrancy and balance desynchronization") mapped onto Nebula's nonce/replay-handling subsystem, which is explicitly one of the reachable categories (nonce/replay handling) for an attacker without a CA-signed certificate — any attacker who can inject or duplicate UDP datagrams toward an already-established tunnel (e.g., a network-level duplicate, or off-path attacker guessing/duplicating a captured ciphertext) can race two copies of the same encrypted frame.

### Impact Explanation
If two threads/goroutines invoke `Decrypt` concurrently for the same `messageCounter` (e.g., because the UDP read path or relay path dispatches inbound packets from multiple readers/queues, or the same physical packet is duplicated on the wire and processed twice), both can pass `window.Check` before either calls `window.Update`, so both `DecryptDanger` calls succeed and both plaintexts are delivered to the tun/application path. This breaks the anti-replay/duplicate-detection guarantee that `ReplayWindow` (`connection_state.go:15`) is meant to enforce, allowing traffic replay/duplicate delivery within an authenticated tunnel. Depending on the payload (e.g., a duplicated control message or relay frame), this can cause duplicate application-level processing/state poisoning on the receiving node.

### Likelihood Explanation
Exploitability requires the ability to get two copies of the same ciphertext (or two packets using the same counter, which for legitimate senders would only be one packet duplicated) delivered to the decrypt path concurrently, plus a codepath where `Decrypt`/`VerifyRelay` for the same `ConnectionState` can be invoked from more than one goroutine at overlapping times. Nebula's outside/UDP read loop and relay forwarding may allow such concurrent delivery for a duplicated on-the-wire packet; this is a lower-privilege, network-position-only requirement (no valid certificate needed to duplicate/replay an observed ciphertext), matching the "no CA-signed certificate" reachability constraint. The race window is bounded by one AEAD decrypt operation's duration, which is short — reducing but not eliminating practical likelihood.

### Recommendation
Hold `decryptLock` across the entire check-decrypt-update sequence (or use a single atomic check-and-reserve operation on `Bits`) so that `window.Check` and `window.Update` for a given `messageCounter` are treated as one atomic critical section, eliminating the window where two concurrent decrypt attempts for the same counter can both pass the check before either commits the update.

### Proof of Concept
1. Establish a tunnel between two Nebula nodes so `ConnectionState` with an active `window` (`Bits`) exists.
2. Capture one authenticated data-plane packet (ciphertext) destined for the peer.
3. Duplicate this exact UDP datagram and deliver both copies to the receiving node's UDP socket in rapid succession (network-level duplication requires no cryptographic material, just packet replication) so that they are processed by two concurrent goroutine invocations of `Decrypt` for the same `ConnectionState`.
4. Because `window.Check` (`connection_state.go:64`) is followed by an unlocked `DecryptDanger` call before `window.Update` (`connection_state.go:76`) is invoked, both goroutines can observe `Check` returning `true` before either performs `Update`, resulting in both copies being decrypted and delivered to the tun device instead of the second being rejected as `ErrAlreadySeen`.

func (b *Bits) Check(l *slog.Logger, i uint64) bool {

func (b *Bits) Update(l *slog.Logger, i uint64) bool {
	// Fast path: i is the next expected counter. Split out so the function
	// stays small and avoids paying for the slow paths' slog argument-build
	// stack frame on every call. The bit read/test/write is inlined to
	// touch the backing word once.
	if i == b.current+1 {
		pos := i & b.lengthMask
		word := pos >> 6
		mask := uint64(1) << (pos & 63)
		w := b.bits[word]
		if i > b.length && w&mask == 0 {
			b.lostCounter.Inc(1)
		}
		b.bits[word] = w | mask
		b.current = i
		return true
	}
	return b.updateSlow(l, i)
}
