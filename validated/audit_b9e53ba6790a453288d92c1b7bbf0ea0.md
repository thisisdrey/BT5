### Title
Check-then-act race in the anti-replay window allows double-processing of a single replayed packet - (File: connection_state.go)

### Summary
`ConnectionState.Decrypt` (and the analogous `VerifyRelay`) implements replay protection as two separate, independently-locked steps: `window.Check()` and `window.Update()`, with `decryptLock` released in between and the actual AEAD decryption happening outside the lock entirely. This is structurally the same "check, then separately act" flaw described in the external report (`claimIntent` checking status without atomically consuming it before `revertEscrow` could also succeed), just applied to Nebula's replay-window instead of an escrow-status flag.

### Finding Description
`Decrypt` in `connection_state.go` does:
1. Lock, `window.Check(l, messageCounter)` (read-only "have I seen this counter" check), unlock.
2. If `Check` says not-seen, decrypt the packet with `dKey.DecryptDanger` (no lock held).
3. Lock again, `window.Update(l, messageCounter)` (which actually marks the counter as seen and can still return `false` for a duplicate), unlock. [1](#0-0) 

Because the lock is dropped between step 1 and step 3, two concurrent invocations of `Decrypt` for the same `ConnectionState` with the same `messageCounter` value can both pass `Check` (both see "not yet marked"), both perform a full, successful AEAD decryption, and only afterward race on `Update`, where exactly one call wins and the other returns `ErrAlreadySeen`. Critically, the loser has *already decrypted and validated* the payload and, depending on call order in `outside.go`, that decrypted payload can already have been handed to the firewall / TUN device before its `Update` call ever executes and fails. [2](#0-1) 

This mirrors the escrow bug precisely: the "claimable" check (`Check`/`ACTIVE` status) and the state-mutating action (`Update`/marking `CLAIMED`) are not atomic, so a second racing caller can slip through the check window before the first caller's mutation lands, producing a double acceptance of what should be a single-use value (funds in the report; a replay-protected message counter here).

### Impact Explanation
An attacker who can capture and duplicate a single legitimate on-wire UDP frame (the standard Nebula threat model — no CA-signed certificate needed, since only observation/duplication of ciphertext is required) can send two copies of the same encrypted packet in close succession. If the two copies are processed by concurrent goroutines/paths before the window is updated, the anti-replay window — whose entire purpose is to reject exactly this — can be bypassed for that message, resulting in the same application-layer packet being delivered to the TUN device (or forwarded, in the relay case via `VerifyRelay`) more than once. This undermines the explicit security goal of `ReplayWindow`/`Bits`, and in the relay path could cause duplicate forwarding of traffic to a third party.

### Likelihood Explanation
Exploitability depends on Nebula's runtime actually invoking `Decrypt`/`VerifyRelay` for a given `ConnectionState` from more than one goroutine concurrently (e.g., multiple UDP reader routines). I was not able to fully confirm this concurrency model from the available index (see below), so likelihood is moderate/uncertain rather than proven; the code path itself, however, unambiguously has a non-atomic check-then-act structure over `decryptLock`, which is inherently unsafe if any concurrent delivery of the same connection's packets is possible (single-packet retransmission at the UDP layer is trivial for a network attacker to induce).

### Recommendation
Make the replay check-and-mark atomic: hold `decryptLock` across `Check`, decryption, and `Update`, or fold `Check`+`Update` into a single locked operation (e.g., a `Bits.CheckAndSet`) so no other goroutine can observe the "unseen" state for the same counter between the check and the mutation.

### Proof of Concept
1. Establish a Nebula tunnel between two hosts, completing the handshake so `ConnectionState` exists.
2. Capture a single legitimate data-plane message (`messageCounter = N`) leaving the sender.
3. Replay the exact same ciphertext twice to the receiver in immediate succession (e.g., two near-simultaneous UDP sends), such that both are read into `readOutsidePackets` on separate goroutines/threads before either has completed its `window.Update` call.
4. Both calls to `ConnectionState.Decrypt` execute `window.Check(l, N)` before either executes `window.Update(l, N)`; both succeed and decrypt, and one of the two decrypted payloads is delivered to `handleOutsideMessagePacket` → TUN, satisfying delivery of a replayed packet.

Note: I could not fully verify, within the available index, how many concurrent goroutines invoke `readOutsidePackets`/`Decrypt` per UDP socket/connection in this version of the codebase; confirming the exact concurrency degree would require reading `interface.go`'s listener setup in full, which the current search results did not resolve conclusively. If a background Devin session is available, it should verify `interface.go`'s reader-goroutine count and reproduce the race under `go test -race` to confirm actual double-delivery before treating this as a fully proven, exploitable bug.

}
