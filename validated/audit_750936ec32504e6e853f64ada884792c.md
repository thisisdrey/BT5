### Title
Missing cross-check of `end_block_snapshot_consensus_hash` in `try_accept_tenure_end_block` allows an unconfirmed-tenure end block to be seeded from a non-canonical fork - ([File: stackslib/src/net/download/nakamoto/tenure_downloader.rs])

### Summary
`NakamotoTenureDownloader::try_accept_tenure_end_block` gates acceptance of the tenure-end block on an exact `tenure_end_block_id` match, but this check is explicitly bypassed when `self.tenure_end_block_id == StacksBlockId([0x00; 32])` (the sentinel used for the "highest/unconfirmed" tenure). In that path, the *only* linkage validating that the served block is the correct successor of `tenure_start_block` is `tc_payload.prev_tenure_consensus_hash == tenure_start_block.header.consensus_hash`, and there is no comparison against `self.end_block_snapshot_consensus_hash`, which is the field that actually identifies the canonical successor sortition. This lets a peer feed a genuine, well-signed tenure-start block from a competing/non-canonical fork as the "tenure-end block," seeding `GetTenureBlocks` with the wrong chain's `parent_block_id`.

### Finding Description
In `try_accept_tenure_end_block` [1](#0-0) , the exact-block-ID check is skipped whenever `tenure_end_block_id` is the zero sentinel:
```
if self.tenure_end_block_id != tenure_end_block.header.block_id()
    && self.tenure_end_block_id != StacksBlockId([0x00; 32])
``` [1](#0-0) 

After signature verification and the well-formed tenure-start check, the only remaining validation of the *identity* of this block relative to the tenure it is supposed to conclude is:
```
if tc_payload.prev_tenure_consensus_hash != tenure_start_block.header.consensus_hash {
    ...
    return Err(NetError::InvalidMessage);
}
``` [2](#0-1) 

This equality only proves the served block's tenure-change transaction claims `tenure_start_block`'s tenure as its immediate predecessor — it does not prove the served block corresponds to the sortition identified by `self.end_block_snapshot_consensus_hash`, which was independently computed by the downloader from the local node's own `WantedTenure`/sortition-DB view via `TenureStartEnd::from_inventory` [3](#0-2) . `end_block_snapshot_consensus_hash` is never referenced inside `try_accept_tenure_end_block` at all — it is read elsewhere only to detect shadow tenures [4](#0-3) , not to validate the end block's own consensus hash.

Because two competing miners can each legitimately build a tenure-change block directly atop the same parent tenure (a fork), both candidate blocks would satisfy `prev_tenure_consensus_hash == tenure_start_block.header.consensus_hash` while having different `tenure_end_block.header.consensus_hash` values — only one of which corresponds to `self.end_block_snapshot_consensus_hash`, the sortition-winner the local node actually expects. When the zero-sentinel bypass is active (the unconfirmed/highest-tenure case), the downloader accepts whichever fork block the remote peer chooses to serve and advances:
```
self.state = NakamotoTenureDownloadState::GetTenureBlocks(
    tenure_end_block.header.parent_block_id.clone(),
    get_epoch_time_ms(),
);
``` [5](#0-4) 
seeding the block-fetch cursor from the wrong fork's `parent_block_id`.

In the *confirmed*-tenure case (non-zero `tenure_end_block_id`), this is not exploitable: `tenure_end_block_id` is derived by the requester itself from its own sortition DB (`wt_end.winning_block_id` in `TenureStartEnd::from_inventory`), and the equality check on `block_id()` (a content hash) pins the accepted block to the literal, unique block the requester already decided is canonical — a peer cannot substitute a different block with the same ID. The vulnerability is confined to the unconfirmed/zero-sentinel branch.

### Impact Explanation
A malicious peer serving the unconfirmed/highest tenure's "end block" can substitute a genuine but non-canonical fork block, causing the downloader's `GetTenureBlocks` cursor to be seeded from `parent_block_id` of the wrong chain. This results in the tenure-download state machine staging blocks for the wrong tenure slot (serving non-canonical state as though it were the pending tip), matching the High-severity category of "serving non-canonical state as canonical / steering a node off the tip." It does not directly corrupt persisted chainstate, since blocks fetched via `try_accept_tenure_blocks` are still checked against `self.tenure_id_consensus_hash` per-block and ultimately subject to full chainstate validation (`NakamotoChainState::check_nakamoto_tenure`, which does call `check_valid_consensus_hash` against the canonical sortition fork) before permanent acceptance — so this is a staging/steering issue in the download state machine rather than a chainstate-integrity break.

### Likelihood Explanation
Requires: (1) the local node to be actively downloading the highest/unconfirmed tenure (a routine occurrence during normal sync near the tip), (2) the attacker to be a connected peer selected to serve that block (attacker cost: run an ordinary P2P peer, no privileged role or secret needed), and (3) a genuine competing fork block to exist with a matching `prev_tenure_consensus_hash` (achievable in a burnchain-fork/miner-race scenario, which happens naturally around tenure-change boundaries). This is remotely reachable over ordinary P2P and repeatable each time the node fetches an unconfirmed tenure end block from that peer.

### Recommendation
In `try_accept_tenure_end_block`, when `self.tenure_end_block_id == StacksBlockId([0x00; 32])`, additionally verify `tenure_end_block.header.consensus_hash == self.end_block_snapshot_consensus_hash` before accepting the block, so the served end block is tied to the specific sortition the downloader was told to expect, not merely to a block that happens to declare `tenure_start_block` as its predecessor.

### Proof of Concept
Rust net test plan (extending `stackslib/src/net/tests/download/nakamoto.rs`, which already exercises `try_accept_tenure_end_block` [6](#0-5) ):
1. Construct a `NakamotoTenureDownloader` with `tenure_end_block_id = StacksBlockId([0x00; 32])` and a real `end_block_snapshot_consensus_hash` corresponding to the canonical successor tenure.
2. Build two competing, well-signed tenure-start blocks `end_block_canonical` and `end_block_fork`, both with `tc_payload.prev_tenure_consensus_hash == tenure_start_block.header.consensus_hash`, but with `end_block_fork.header.consensus_hash != self.end_block_snapshot_consensus_hash`.
3. Call `td.try_accept_tenure_end_block(&end_block_fork)` and assert it currently returns `Ok(())` and sets `self.state = GetTenureBlocks(end_block_fork.header.parent_block_id, ..)` — demonstrating the missing `end_block_snapshot_consensus_hash` cross-check.
4. After applying the fix, assert the same call returns `Err(NetError::InvalidMessage)`.

    pub fn from_inventory(
        rc: u64,
        wanted_tenures: &[WantedTenure],
        next_wanted_tenures: Option<&[WantedTenure]>,
        pox_constants: &PoxConstants,
        first_burn_height: u64,
        invs: &NakamotoTenureInv,
    ) -> Option<AvailableTenures> {
        // if bit i is set, that means that the tenure data for the ith tenure in the sortition
        // history was present.  But given that block-commits commit to the start block of the
        // parent tenure, the start-block ID for tenure i would be the StacksBlockId for the
        // next-available tenure.  Its end-block ID would be the StacksBlockId for the
        // next-available tenure after that.
        let invbits = invs.tenures_inv.get(&rc)?;
        let mut tenure_block_ids = AvailableTenures::new();
        let mut last_tenure = 0;
        let mut last_tenure_ch = None;
        debug!("Find available tenures in inventory {:?} rc {}", invs, rc);
        for (i, wt) in wanted_tenures.iter().enumerate() {
            debug!("consider wanted tenure which starts with i={} {:?}", i, &wt);

            // advance to next tenure-start sortition
            let bit = u16::try_from(i).expect("FATAL: more sortitions than u16::MAX");
            if !invbits.get(bit).unwrap_or(false) {
                debug!("i={} bit not set", i);
                continue;
            }

            // the last tenure we'll consider
            last_tenure = i;

            let Some(wt_start_idx) = ((i + 1)..wanted_tenures.len()).find(|j| {
                let bit = u16::try_from(*j).expect("FATAL: more sortitions than u16::MAX");
                invbits.get(bit).unwrap_or(false)
            }) else {
                debug!("i={} out of wanted_tenures", i);
                break;
            };

            let Some(wt_start) = wanted_tenures.get(wt_start_idx) else {
                debug!("i={} no start wanted tenure", i);
                break;
            };

            let Some(wt_end_index) = ((wt_start_idx + 1)..wanted_tenures.len()).find(|j| {
                let bit = u16::try_from(*j).expect("FATAL: more sortitions than u16::MAX");
                invbits.get(bit).unwrap_or(false)
            }) else {
                debug!("i={} out of wanted_tenures", i);
                break;
            };

            let Some(wt_end) = wanted_tenures.get(wt_end_index) else {
                debug!("i={} no end wanted tenure", i);
                break;
            };

            let tenure_start_end = TenureStartEnd::new(
                wt.tenure_id_consensus_hash.clone(),
                wt.burn_height,
                wt_start.tenure_id_consensus_hash.clone(),
                wt_start.winning_block_id.clone(),
                wt_end.tenure_id_consensus_hash.clone(),
                wt_end.winning_block_id.clone(),
                rc,
                rc,
                wt.processed,
            );
            debug!(

                i,
                wanted_tenures.len(),
                &tenure_start_end
            );
            last_tenure_ch = Some(wt.tenure_id_consensus_hash.clone());
            tenure_block_ids.insert(wt.tenure_id_consensus_hash.clone(), tenure_start_end);
