### Title
Denial of Service via unbounded `getAssetIssueList` query (`/wallet/getassetissuelist`, `GetAssetIssueList` gRPC/JSON-RPC) - (File: `framework/src/main/java/org/tron/core/Wallet.java`)

### Summary
The unauthenticated `getAssetIssueList()` API (exposed over HTTP as `/wallet/getassetissuelist`, over gRPC as `WalletApi.GetAssetIssueList`, and mirrored on Solidity/PBFT nodes) returns **every** TRC10 asset issue stored on the node with no offset/limit and no upper bound on the result size. Because any account can create new TRC10 assets (subject only to the asset-issuance fee), an attacker can grow the underlying asset-issue store to a very large size and then repeatedly call this endpoint to force the node to enumerate and serialize the entire store on every request, exhausting CPU/memory and causing the node to crash or become unresponsive — the same bug class as CVE-2022-4045 (Mattermost DoS via an API endpoint that can fetch unbounded data).

### Finding Description
`Wallet.getAssetIssueList()` (no-arg overload) fetches all asset issues via `getAllAssetIssues()`, which streams the *entire* `AssetIssueStore`/`AssetIssueV2Store` into memory with no cap: [1](#0-0) 

This differs from the *paginated* variant, `getAssetIssuesPaginated(offset, limit)`, which explicitly clamps the result with `ASSET_ISSUE_COUNT_LIMIT_MAX`: [2](#0-1) 

The unbounded, no-arg `getAssetIssueList()` is reachable from multiple unauthenticated entry points that require no signature, no permission check, and no rate-limited resource cost:
- HTTP servlet `GetAssetIssueListServlet.doGet` / `doPost`, which call `wallet.getAssetIssueList()` directly and serialize the full list to JSON: [3](#0-2) 
- gRPC `WalletApi.getAssetIssueList` / `WalletSolidityApi.getAssetIssueList`: [4](#0-3) 
- Solidity/PBFT proxy paths that forward the same unbounded call: [5](#0-4) 

TRC10 asset issuance is a normal, unprivileged, broadcastable transaction (`AssetIssueContract`) available to any funded account, so the store size behind `getAssetIssueList()` is directly attacker-controllable: an attacker can issue many assets (each issuance only costs a fixed TRX fee, not proportional to future query cost) and then repeatedly invoke the unbounded list endpoint to multiply the cost asymmetry between attacker and victim node, exactly matching the Mattermost advisory's bug class ("crash the server via multiple requests to one of the API endpoints which could fetch a large amount of data").

### Impact Explanation
Each call to the unbounded endpoint forces the node to iterate the full `AssetIssueStore`, materialize a `List<AssetIssueCapsule>`, build a full `AssetIssueList` protobuf/JSON response, and update bandwidth usage for every asset issue found (`getAssetIssueListByName`/`getAssetIssueList` both call `BandwidthProcessor.updateUsage` per element in related paths). Repeated concurrent requests amplify CPU and heap consumption linearly with the number of stored asset issues, which is itself unbounded and growable by any attacker. This can degrade or crash a fullnode/soliditynode serving public API traffic — a node crash/halt qualifying as a Medium-severity availability impact, consistent with CVE-2022-4045's CVSS (`AV:N/AC:L/PR:L/UI:N/S:U/C:N/I:N/A:H`).

### Likelihood Explanation
The endpoint requires no authentication and no special privilege — any anonymous HTTP/gRPC client can call `/wallet/getassetissuelist` or `GetAssetIssueList` repeatedly. Growing the underlying data set only requires issuing TRC10 assets, a standard unprivileged transaction type. Combined with the fact that the paginated sibling function (`getAssetIssuesPaginated`) already demonstrates that the team is aware pagination/limits are needed for this data set, the unbounded no-arg variant remaining exposed without the same cap is a straightforward, high-likelihood misconfiguration to exploit.

### Recommendation
Apply the same `ASSET_ISSUE_COUNT_LIMIT_MAX` cap (or deprecate/rate-limit) to the no-argument `getAssetIssueList()` path, or require callers to use the paginated variant exclusively; additionally, apply per-IP/global rate limiting and response-size limits to `GetAssetIssueListServlet` and the corresponding gRPC methods to bound worst-case node work per request.

### Proof of Concept
1. Fund an account and repeatedly broadcast `AssetIssueContract` transactions to create a very large number of TRC10 assets (each is a normal, low-cost, unprivileged transaction).
2. Once the `AssetIssueStore` contains a large number of entries, issue concurrent requests to `GET/POST http://<node>:8090/wallet/getassetissuelist` (or the gRPC `GetAssetIssueList` / `WalletSolidity.GetAssetIssueList` / PBFT equivalents) from an anonymous client.
3. Observe that each request forces a full store scan and full-list serialization (`Wallet.getAssetIssueList()` → `AssetIssueStore.getAllAssetIssues()`), and that sustained concurrent requests exhaust node memory/CPU, degrading or crashing the node's ability to serve further API traffic — the same effect described in GHSA-v42f-hq78-8c5m.

```java
  private List<AssetIssueCapsule> getAssetIssuesPaginated(List<AssetIssueCapsule> assetIssueList,
      long offset, long limit) {
    if (limit < 0 || offset < 0) {
      return null;
    }

    if (assetIssueList.size() <= offset) {
      return null;
    }
    assetIssueList.sort((o1, o2) -> {
      if (o1.getName() != o2.getName()) {
        return o1.getName().toStringUtf8().compareTo(o2.getName().toStringUtf8());
      }
      return Long.compare(o1.getOrder(), o2.getOrder());
    });
    limit = limit > ASSET_ISSUE_COUNT_LIMIT_MAX ? ASSET_ISSUE_COUNT_LIMIT_MAX : limit;
    long end = offset + limit;
    end = end > assetIssueList.size() ? assetIssueList.size() : end;
    return assetIssueList.subList((int) offset, (int) end);
  }
```
