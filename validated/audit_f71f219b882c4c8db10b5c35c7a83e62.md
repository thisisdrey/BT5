### Title
Unbounded growth of `DelegatedResourceAccountIndex` allows attacker-driven DoS of `getdelegatedresourceaccountindex(v2)` query APIs - (File: `chainbase/src/main/java/org/tron/core/store/DelegatedResourceAccountIndexStore.java`)

### Summary
Any account can call `DelegateResourceContract`/`FreezeBalanceContract` (with `receiver_address`) an unlimited number of times against a single victim address, each call adding a new key to the `DelegatedResourceAccountIndexStore` under that victim's `FROM_PREFIX/TO_PREFIX` (or `V2_FROM_PREFIX/V2_TO_PREFIX`) namespace. There is no cap on the number of distinct delegation relationships an account can have, and the read path (`getIndex`/`getV2Index`) does an unbounded RocksDB prefix scan and in-memory sort over all matching keys to answer a single client query.

### Finding Description
`DelegateResourceActuator.validate()`/`execute()` (`actuator/src/main/java/org/tron/core/actuator/DelegateResourceActuator.java:44-98,101-243`) and `FreezeBalanceActuator.delegateResource()` (`actuator/src/main/java/org/tron/core/actuator/FreezeBalanceActuator.java:289-370`) only require that the caller (owner) has at least `1 TRX` of available frozen balance to delegate, and that `receiverAddress` is a valid, existing, non-contract account different from the owner. There is no limit on:
- the number of *distinct* receiver addresses one owner can delegate to, or
- the number of *distinct* owner addresses that can delegate to one receiver.

Each `delegate`/`delegateV2` call writes a brand-new key `PREFIX + from + to` / `PREFIX + to + from` into `DelegatedResourceAccountIndexStore` [1](#0-0) . Because delegations only need 1 TRX and any number of distinct addresses can be used as `from`/`to`, an attacker (using disposable or newly-created accounts) can insert an effectively unbounded number of such index entries under a single target address.

The read path, used by `getIndex`/`getV2Index`, retrieves *all* matching entries in a single call via `prefixQuery`, sorts them, and builds a full list, with no bound on the returned/scanned set: [2](#0-1) 

This is invoked directly by `Wallet.getDelegatedResourceAccountIndex`/`getDelegatedResourceAccountIndexV2` [3](#0-2) , which is exposed unauthenticated via:
- HTTP: `/wallet/getdelegatedresourceaccountindex` and `/wallet/getdelegatedresourceaccountindexv2` [4](#0-3) 
- gRPC: `GetDelegatedResourceAccountIndex`/`GetDelegatedResourceAccountIndexV2` on the FullNode, Solidity, and PBFT APIs [5](#0-4) 

This mirrors the reported bug class (unbounded array/collection controllable by any external actor, later iterated fully by a reachable code path). In the visorfinance case the unbounded `nfts` array bricked `transferERC721()`; here the analogous unbounded index (attacker-populated, per-address) bricks/DoSes the `getdelegatedresourceaccountindex(v2)` read path — a node query API reachable by any unprivileged HTTP/gRPC client.

### Impact Explanation
An attacker can cheaply (1 TRX + minimal fee per relationship, using disposable accounts) grow the from/to index for an arbitrary victim address to a very large size. Subsequent calls to `getdelegatedresourceaccountindex`/`v2` for that address force the node to perform a full RocksDB prefix scan plus a `Comparator`-based sort over the entire, attacker-inflated result set on every request (no pagination, no cap), which is CPU/I-O expensive and can be repeated freely by anyone querying that address. This degrades or denies the query API for legitimate users (wallets, exchanges, explorers depending on this endpoint for the affected address), satisfying the "API the node can no longer serve" criterion. It does not directly cause fund loss but is a concrete resource-exhaustion/availability issue reachable purely through normal signed transactions plus unauthenticated read RPC calls.

### Likelihood Explanation
High likelihood: `DelegateResourceContract` and `FreezeBalanceContract` (with `receiverAddress`) are ordinary, unprivileged transaction types requiring no special permissions — any account holder can broadcast them. Creating many low-cost delegation relationships against one address is inexpensive and requires no cooperation from the victim. The read APIs are public, unauthenticated node RPC/HTTP endpoints.

### Recommendation
- Bound the number of distinct delegation relationships (both from-side and to-side) an account can have, enforced in `DelegateResourceActuator.validate()` / `FreezeBalanceActuator.validate()`, similar to the `MAX_VOTE_NUMBER` style cap used elsewhere (e.g., `VoteWitnessActuator`).
- Add pagination/limits to `DelegatedResourceAccountIndexStore.getWithPrefix()` and the corresponding `Wallet`/gRPC/HTTP methods so a single client request cannot force an unbounded scan/sort.
- Consider rate-limiting or requiring a minimum economically meaningful delegation amount that scales with the number of existing relationships to raise the cost of index-pollution attacks.

### Proof of Concept
Conceptual (no PoC code executed, based on static analysis of the actuator/store/API code):
1. Attacker creates N (e.g., 100k) throwaway accounts, each funded with the minimum required TRX and frozen balance.
2. From each throwaway account, attacker calls `DelegateResourceContract`/`FreezeBalanceContract` with `receiverAddress = victim`, delegating the minimum 1 TRX.
3. Each call adds a new `V2_TO_PREFIX/TO_PREFIX + victim + from` key to `DelegatedResourceAccountIndexStore` — no protocol-level limit rejects this.
4. Any client calls `GET /wallet/getdelegatedresourceaccountindexv2?value=<victim>` or the gRPC `GetDelegatedResourceAccountIndexV2` — the node executes `getWithPrefix()`, scanning and sorting all N entries synchronously on every call, degrading that API's responsiveness for all callers.

Note: I could not verify at runtime what the practical N threshold is to cause a "hard" DoS/crash versus mere latency degradation — that would require load-testing against an actual java-tron node, which is outside the scope of this static analysis.

  private DelegatedResourceAccountIndexCapsule getWithPrefix(byte[] fromPrefix, byte[] toPrefix, byte[] address) {
    DelegatedResourceAccountIndexCapsule tmpIndexCapsule =
        new DelegatedResourceAccountIndexCapsule(ByteString.copyFrom(address));

    byte[] key = Bytes.concat(fromPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpToList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpToList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    List<ByteString> list = tmpToList.stream()
        .map(DelegatedResourceAccountIndexCapsule::getAccount).collect(Collectors.toList());
    tmpIndexCapsule.setAllToAccounts(list);

    key = Bytes.concat(toPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpFromList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpFromList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    list = tmpFromList.stream().map(DelegatedResourceAccountIndexCapsule::getAccount).collect(
        Collectors.toList());
    tmpIndexCapsule.setAllFromAccounts(list);
    return tmpIndexCapsule;
  }

  public DelegatedResourceAccountIndex getDelegatedResourceAccountIndex(ByteString address) {
    if (address == null || address.size() != DecodeUtil.ADDRESS_SIZE / 2) {
      return DelegatedResourceAccountIndex.getDefaultInstance();
    }
    DelegatedResourceAccountIndexCapsule accountIndexCapsule =
        chainBaseManager.getDelegatedResourceAccountIndexStore().getIndex(address.toByteArray());
    if (accountIndexCapsule != null) {
      return accountIndexCapsule.getInstance();
    } else {
      return DelegatedResourceAccountIndex.getDefaultInstance();
    }
  }
