### Title
Non-constant-time authorization-token comparison in privileged RPC endpoints enables a timing side-channel attack - (File: stackslib/src/net/api/blockreplay.rs, blocksimulate.rs, postblock_v3.rs, txsimulate.rs)

### Summary
Several privileged Stacks HTTP RPC endpoints authenticate the caller by comparing the `authorization` header against the node's configured `connection_options.auth_token` using plain Rust string inequality (`auth_header != password`). This is the same bug class flagged in GHSA-jmj6-p2j9-68cp: `java.util.Arrays.equals` (and, analogously, Rust's slice/string `PartialEq`) short-circuits on the first mismatching byte, making the comparison's timing dependent on how many leading bytes of the guess are correct. An attacker with network access to the RPC port can use timing measurements to incrementally recover the secret `auth_token` byte-by-byte instead of guessing the whole secret at once.

### Finding Description
The following handlers gate access with an equality check between the caller-supplied header and the configured secret, using the default (non-constant-time) comparison operator:

- `stackslib/src/net/api/blockreplay.rs` — `try_parse_request` compares `auth_header != password` before allowing `/v3/blocks/replay/:block_id`. [1](#0-0) 

- `stackslib/src/net/api/blocksimulate.rs` — identical pattern gating `/v3/blocks/simulate/:block_id`. [2](#0-1) 

- `stackslib/src/net/api/postblock_v3.rs` — gates the authenticated/`broadcast=1` path of `POST /v3/blocks/upload`. [3](#0-2) 

- `stackslib/src/net/api/txsimulate.rs` — gates `/v3/transactions/simulate`. [4](#0-3) 

All of these handlers are registered with the same `self.auth_token` value in `StacksHttp::register_rpc_methods`, confirming they share one secret and one (non-constant-time) verification pattern across the node's RPC surface. [5](#0-4) 

In Rust, `str`/`&str` equality via `PartialEq` (used implicitly by `!=`) is implemented as a byte-wise comparison that returns as soon as a mismatch is found (after first checking length). This means the wall-clock time of the comparison leaks the length of the matching prefix between the attacker's guess and the real secret. This is precisely the CWE-208/CWE-203 issue the wildfly-elytron advisory describes for `Arrays.equals`.

### Impact Explanation
If exploited, a remote, unauthenticated attacker can incrementally recover the node operator's `auth_token` via a timing side channel, without needing the operator's key or any privileged role. Once the token is recovered, the attacker gains unauthorized access to sensitive/expensive endpoints, e.g.:
- `postblock_v3` broadcast path, allowing unauthorized submission/broadcast of blocks that would otherwise require authentication,
- `blocksimulate`/`txsimulate`, which allow costly Clarity execution against the node's chainstate (bounded compute DoS on a read endpoint),
- `blockreplay`, exposing internal chain replay functionality.

This matches the "auth bypass" / "steering... via unauthorized write" impact categories described as in-scope, since successful recovery of the token defeats the intended authentication boundary for privileged endpoints. The practical difficulty is nontrivial (network jitter makes byte-at-a-time timing attacks harder, consistent with the original CVE's `AC:H` rating), but this is a genuine, reachable difference from constant-time comparison, not merely a theoretical note — the exact same code pattern is repeated across multiple endpoints sharing one secret.

### Likelihood Explanation
Exploitation requires the attacker to have network access to the node's RPC port and to make a large number of precisely-timed requests to defeat network jitter — a realistic but non-trivial capability for a remote attacker, and it does not require the node's private key, another party's key, or an admin role. Likelihood is moderate: the vulnerability is real and remotely reachable without authentication, but extracting a token via timing analysis over a network typically requires statistical averaging over many requests.

### Recommendation
Replace all `auth_header != password` comparisons in these handlers with a constant-time comparison, e.g. using `subtle::ConstantTimeEq`, or by comparing the SHA-256 (or similar) digest of the header value against the digest of the stored secret using a constant-time compare. Apply this fix uniformly to every RPC handler that stores and compares `self.auth`/`self.auth_token`, since the same insecure pattern is duplicated per-handler.

### Proof of Concept
1. Configure a node with `connection_options.auth_token = "<long-secret>"`.
2. Send repeated requests to a gated endpoint, e.g. `POST /v3/blocks/simulate/:block_id`, with `authorization` headers that are systematically varied one byte at a time (e.g., trying all byte values for position 0, then extending the correct prefix and trying position 1, etc.), while measuring response latency for the 401 rejection path in `try_parse_request` (`stackslib/src/net/api/blocksimulate.rs:156-161`).
3. Because the comparison is non-constant-time, request latency should statistically increase for header guesses whose prefix matches more bytes of the true secret than others, allowing the attacker to reconstruct `auth_token` one byte at a time faster than brute-forcing the whole token.
