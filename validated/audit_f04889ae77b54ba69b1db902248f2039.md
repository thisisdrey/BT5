### Title
Division/underflow revert in `calc-treasury-lp-preview` when the current-period reserve fee accrual is not strictly smaller than previewed total assets - ([File: mainnet/contracts/vault/v0-vault-stx.clar])

### Summary
`calc-treasury-lp-preview` computes how many "treasury LP" shares should be minted to represent the protocol's reserve-fee cut of freshly accrued interest, by dividing `reserve-inc` by `(- ta-preview reserve-inc)`. In Clarity, `-` on `uint` aborts the transaction if the result would be negative, and `/` aborts on divide-by-zero. Both failure modes are reachable here because `ta-preview` (a rounded, fixed-point "available assets" preview) and `reserve-inc` (a rounded, fixed-point fee slice of this period's interest delta) are computed independently through several chained `mul-div-down` roundings, so there is no invariant in the code guaranteeing `ta-preview > reserve-inc`. This mirrors the DODO M-11 pattern: independent fixed-point roundings on small-decimal/high-value/low-rate inputs can degenerate a denominator (or here, a subtraction result) to zero, breaking a formula the maker/user cannot avoid triggering.

### Finding Description
`calc-treasury-lp-preview` is defined identically across all vaults (`v0-vault-stx.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`, `v0-vault-ststxbtc.clar`): [1](#0-0) 

```
(define-private (calc-treasury-lp-preview)
  (let ((scaled-principal (var-get principal-scaled))
        (idx (var-get index))
        (next (next-index))
        (old-debt (mul-div-down scaled-principal idx INDEX-PRECISION))
        (new-debt (mul-div-down scaled-principal next INDEX-PRECISION))
        (debt-delta (if (> new-debt old-debt) (- new-debt old-debt) u0))
        (reserve-inc (mul-div-down debt-delta (var-get fee-reserve) BPS))
        (ta-preview (total-assets-preview)))
    (if (> reserve-inc u0)
        (mul-div-down reserve-inc (total-supply) (- ta-preview reserve-inc))
        u0)))
```

`ta-preview` is `total-assets-preview`, itself a chain of independent fixed-point roundings: [2](#0-1) 

The subtraction `(- ta-preview reserve-inc)` is used directly as the divisor of `mul-div-down`, i.e. `(/ (* reserve-inc (total-supply)) (- ta-preview reserve-inc))`. Nothing in the code proves `ta-preview` strictly exceeds `reserve-inc`:
- `reserve-inc` is derived from `debt-delta` (this block's interest accrual on scaled principal) times `fee-reserve` (a DAO-configured small bps, analogous to DODO's small `kBid`) divided down.
- `ta-preview` is `current-assets + interest`, where `interest` is `(- debt-preview total-borrowed)` when positive, `u0` otherwise — i.e., it can legitimately be pushed to a very small residual value through the vault's normal borrow/repay/redeem lifecycle (e.g., most liquidity borrowed out, `current-assets` near zero, and `total-borrowed` tracked so tightly against `debt-preview` that the "unrealized interest" buffer is thin).

Because `old-debt`/`new-debt`/`debt-delta`/`reserve-inc` all pass through separate `mul-div-down` (floor) roundings while `ta-preview` is accumulated through a different rounding chain (`total-assets` / `debt-preview` / `total-borrowed`), for assets with small decimals and high per-unit value (e.g., sBTC, 8 decimals, high USD price) combined with a small `fee-reserve` bps, these two independently-rounded quantities can converge such that `reserve-inc >= ta-preview`. When that happens `(- ta-preview reserve-inc)` underflows a `uint` and the transaction aborts (Clarity subtraction on `uint` reverts on underflow rather than wrapping); if it lands exactly at zero the subsequent `/` divides by zero and also reverts.

`total-supply-preview` (which feeds `convert-to-shares-preview` / `convert-to-assets-preview`, used by every `deposit`/`redeem` in the vault) calls `calc-treasury-lp-preview` directly: [3](#0-2) 

So any reachable state where `reserve-inc >= ta-preview` makes `deposit`/`redeem` (and any other path relying on `total-supply-preview`) unconditionally revert for that vault, until/unless state changes (e.g., time passes, more principal is repaid) shift the values back into a "safe" region — which is not guaranteed to happen on its own since `debt-delta` keeps growing every block that interest accrues.

### Impact Explanation
If triggered, the affected vault's `deposit` and `redeem` entry points revert every time `total-supply-preview` is evaluated, which is on essentially every state-changing vault call once the ratio condition is met. This is a temporary/potentially indefinite freezing of the accrued (unclaimed) treasury yield and, more broadly, of user deposit/redeem flows on that vault, since the reverting computation sits in the common preview path shared by deposits and redemptions. This lands in the in-scope "temporary freezing of funds"/"theft or freezing of unclaimed yield" impact category (vault share math and interest accrual is explicitly an in-scope calculation category).

### Likelihood Explanation
Likelihood depends on `fee-reserve` (DAO-set, can be small, analogous to DODO's small `kBid`) and on the vault reaching a state where `current-assets` is small relative to unrealized interest (a normal state for a heavily-utilized vault, not requiring any privileged action or DAO misconfiguration beyond routine parameter setting). Because the two operands come from independently rounded fixed-point chains, the exact boundary crossing is hard to predict deterministically without on-chain state, so I cannot fully confirm from static review alone that the crossing is reachable in practice for the deployed `fee-reserve` values — this needs on-chain/state simulation to pin down concretely. I flag this uncertainty explicitly.

### Recommendation
Guard the subtraction explicitly, mirroring DODO's fix approach (clamp the degenerate corner case rather than let fixed-point rounding silently create an invalid denominator):
```
(if (> ta-preview reserve-inc)
    (mul-div-down reserve-inc (total-supply) (- ta-preview reserve-inc))
    u0) ;; or cap reserve-inc to (- ta-preview 1) if reserve-inc must be preserved for accounting
```
Apply the same fix in `calc-treasury-lp-preview` (and the analogous non-preview accrual function, if one exists) across all six vault contracts (`v0-vault-stx.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`, `v0-vault-ststxbtc.clar`).

### Proof of Concept
A concrete numeric PoC requires driving on-chain vault state (specific `principal-scaled`, `index`, `total-borrowed`, `assets`, `fee-reserve`) to the boundary where `reserve-inc >= ta-preview`. I was not able to fully construct and validate such a state trace within this review — this would require a Clarinet/Clarigen simulation exercising repeated borrow/repay/redeem cycles on a low-decimal, high-price vault (e.g., sBTC) with a small `fee-reserve`, checking `calc-treasury-lp-preview`'s intermediate values at each step until `(- ta-preview reserve-inc)` underflows. I flag this as unverified and recommend a background Devin session run the local test suite (`local-testing/`) to simulate this state transition and confirm the revert.
