### Title
Inconsistent hardening across Exchange actuators lets `ExchangeInjectActuator`/`ExchangeWithdrawActuator` bypass the `allowHardenExchangeCalculation` safety guarantee enforced only in `ExchangeTransactionActuator` - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`)

### Summary
The three exchange actuators (`ExchangeInjectActuator`, `ExchangeWithdrawActuator`, `ExchangeTransactionActuator`) all mutate the same `ExchangeCapsule` pool state, but only `ExchangeTransactionActuator` routes its core exchange-rate math through `ExchangeCapsule.transaction(...)`, which can be switched to the `SafeExchangeProcessor`/`StrictMathWrapper`-hardened path via the committee-controlled `allowHardenExchangeCalculation` flag. `ExchangeInjectActuator` and `ExchangeWithdrawActuator` never consult this flag for their own pool-balance math (only for outer fee arithmetic via `addExact`/`subtractExact` inherited from `AbstractExchangeActuator`), so their core "another token quantity" computation is always performed the same way regardless of the flag's state.

### Finding Description
`AbstractExchangeActuator` exposes `allowHarden()` which reads `dynamicStore.allowHardenExchangeCalculation()` [1](#0-0) . `ExchangeTransactionActuator` passes this flag into `ExchangeCapsule.transaction(tokenID, tokenQuant, dynamicStore.allowStrictMath(), allowHarden())` [2](#0-1) , and `ExchangeCapsule.transaction` selects between the legacy double/`Math.pow`-based `ExchangeProcessor` and the `SafeExchangeProcessor` (BigDecimal-based) plus a post-condition guard that rejects any resulting negative balance only when `hardenedCalc` is true [3](#0-2) .

In contrast, `ExchangeInjectActuator.execute()` always computes the counter-token amount with `floorDiv(multiplyExact(secondTokenBalance, tokenQuant), firstTokenBalance)` [4](#0-3) , and `ExchangeWithdrawActuator.execute()` always uses `BigInteger` exact division [5](#0-4) . Neither actuator ever calls into `ExchangeCapsule.transaction`'s hardened path, nor does either apply the non-negative post-state invariant that was added specifically to close a known AMM-precision/overflow abuse vector for `ExchangeTransactionActuator`.

This is the same class of defect described in the external Fairswap report: three interfaces that operate on shared state ("Fairswap" pools / TRON `ExchangeCapsule` pools) but are implemented inconsistently, so a caller/composing contract that assumes "hardened" protection is chain-wide can still reach the un-hardened arithmetic paths through the sibling actuators.

### Impact Explanation
Once the community enables `allowHardenExchangeCalculation` (intended to shut down precision-based AMM draining via `ExchangeTransactionContract`), an attacker can still target the same exchange pool via `ExchangeInjectContract`/`ExchangeWithdrawContract`, which never adopted the hardened invariant checks (e.g., the non-negative-balance guard, `StrictMathWrapper` overflow detection in the core ratio calc). This undermines the security guarantee the governance flag is meant to provide and preserves a path to pool balance corruption/inconsistent state across the three co-dependent actuators that all read/write the identical `ExchangeCapsule`.

### Likelihood Explanation
Any account can submit `ExchangeInjectContract` or `ExchangeWithdrawContract` transactions once market/exchange features are enabled; no privileged role is required beyond being the pool creator for inject/withdraw (`ExchangeInjectActuator`/`ExchangeWithdrawActuator` validate the caller as `exchangeCapsule.getCreatorAddress()`), and exchange creation itself is permissionless. The inconsistency is always present, not merely a corner case, since neither actuator ever checks the hardening flag for its core math.

### Recommendation
Extract a single shared pool-math interface (analogous to the recommendation in the external report) that all three exchange actuators use, and thread `allowHarden()`/`SafeExchangeProcessor`/`StrictMathWrapper` consistently through `ExchangeInjectActuator` and `ExchangeWithdrawActuator` just as `ExchangeTransactionActuator` does, including the non-negative post-condition invariant, so enabling the hardening proposal protects the pool uniformly across all mutating entry points.

### Proof of Concept
1. Committee passes the proposal enabling `allowHardenExchangeCalculation` (`ProposalService`/`DynamicPropertiesStore.allowHardenExchangeCalculation`) expecting exchange pools to be protected from precision/overflow abuse.
2. An attacker crafts `ExchangeInjectContract`/`ExchangeWithdrawContract` transactions against the same `exchange_id` targeted for hardening; these actuators still execute the pre-hardening `floorDiv(multiplyExact(...))`/`BigInteger` math paths in `ExchangeInjectActuator.execute()` / `ExchangeWithdrawActuator.execute()` with none of the non-negative-balance or `StrictMathWrapper` overflow guard added for `ExchangeTransactionActuator`'s hardened branch.
3. This lets the attacker bypass the intended safety guarantee of the governance flag through the sibling actuators that share the identical `ExchangeCapsule` pool state.

    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

          : firstTokenBalance - buyTokenQuant;

          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;
