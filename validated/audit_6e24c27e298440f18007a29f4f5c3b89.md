## Title
Missing slippage/minimum-output protection in `ExchangeWithdrawContract` allows sandwich attacks against liquidity withdrawals - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
`ExchangeWithdrawActuator` computes the counter-asset amount an exchange creator receives when withdrawing liquidity purely from the *current* on-chain pool ratio at execution time, with no user-supplied minimum-output bound. This mirrors the reported bug class ("lack of slippage check when a user requests a withdraw") because the value a withdrawer actually receives can be manipulated between the time they sign/broadcast the transaction and the time it is mined.

### Finding Description
`ExchangeWithdrawContract` only carries `owner_address`, `exchange_id`, `token_id`, and `quant` — there is no `expected` field, unlike its sibling `ExchangeTransactionContract`, which explicitly carries an `expected` minimum-received amount that is enforced in `ExchangeTransactionActuator`: [1](#0-0) [2](#0-1) 

In `ExchangeTransactionActuator.doValidate`, the validator explicitly rejects the transaction if the computed `anotherTokenQuant` is smaller than the caller-provided `tokenExpected`: [3](#0-2) 

`ExchangeWithdrawActuator`, however, has no equivalent check. It computes `anotherTokenQuant` purely from `firstTokenBalance`/`secondTokenBalance` at validation time and again at execution time, with only a precision/rounding "Not precise enough" sanity check — never a caller-specified minimum: [4](#0-3) [5](#0-4) 

Any account can freely submit `ExchangeTransactionContract` trades against the same pool (`exchange_id`) between the time a withdrawer's `ExchangeWithdrawContract` is broadcast and the time it is packed into a block, shifting `firstTokenBalance`/`secondTokenBalance` and thus the computed `anotherTokenQuant` the withdrawer will actually receive. Only the exchange creator may call withdraw (checked at `ExchangeWithdrawActuator.java:181`), but any unprivileged trader can still front-run the pending withdraw with `ExchangeTransactionContract` trades to alter the ratio before the withdraw executes, and unwind the trade afterward, extracting value from the withdrawer without any way for the withdrawer to protect themselves — exactly the "index/ratio moves between request and execution" root cause of the referenced report.

### Impact Explanation
An exchange creator (an unprivileged actor who created a TRC10 bancor-style exchange pool) withdrawing liquidity via `ExchangeWithdrawContract` can receive an arbitrarily reduced amount of the counter asset if the pool ratio is manipulated by a third party immediately before the withdraw is mined, with no way to bound their minimum acceptable output. This is a concrete loss-of-funds condition for the withdrawer, reachable by any account able to submit ordinary signed `ExchangeTransactionContract`/`ExchangeWithdrawContract` transactions — consistent with Medium severity per the analog report.

### Likelihood Explanation
Any account can submit `ExchangeTransactionContract` trades against a public bancor exchange pool without special privilege, and transaction ordering within a block is not guaranteed to match submission order, so a motivated attacker monitoring the mempool for pending `ExchangeWithdrawContract` transactions on a given `exchange_id` can reliably front-run/sandwich them. The absence of the `expected` field that `ExchangeTransactionContract` already has for the symmetric "sell" case indicates the omission was not an intentional design decision to omit slippage protection on withdrawal, making this a genuine oversight/inconsistency.

### Recommendation
Add an `expected`-style minimum-output field to `ExchangeWithdrawContract` (mirroring `ExchangeTransactionContract.expected`) and enforce, in `ExchangeWithdrawActuator.doValidate`/`execute`, that the computed `anotherTokenQuant` is not less than the caller-specified minimum, exactly as done today in `ExchangeTransactionActuator`.

### Proof of Concept
1. Account A creates a TRC10 bancor exchange pool (`exchange_id = X`) with tokens `T1`/`T2` and becomes its `creatorAddress`, then provides liquidity.
2. A signs and broadcasts `ExchangeWithdrawContract{exchange_id=X, token_id=T1, quant=Q}`, expecting to receive `anotherTokenQuant` computed from the current `firstTokenBalance`/`secondTokenBalance` ratio (`actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java:214-244`).
3. Before A's transaction is packed, an unprivileged attacker B broadcasts an `ExchangeTransactionContract` trading a large amount of `T1` for `T2` against the same `exchange_id`, drastically skewing `firstTokenBalance`/`secondTokenBalance`.
4. If B's trade is ordered before A's withdraw in the block, A's `anotherTokenQuant` is recomputed against the skewed ratio in `ExchangeWithdrawActuator.execute` (`actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java:74-89`), producing a far smaller payout than A anticipated when signing.
5. B then reverses the trade in a follow-up transaction, restoring the pool ratio and pocketing the difference — a classic sandwich attack enabled purely by the missing minimum-output parameter on `ExchangeWithdrawContract`.
