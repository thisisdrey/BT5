### Title
Per-IP QoS bypass via handshake churn exhausts shared `ClientConnectionTracker` connection pool - (File: streamer/src/nonblocking/quic.rs)

### Summary
In `run_server`/`setup_connection`, the `ConnectionRateLimiter` (per-IP QoS) only records state via `register_connection` after a QUIC handshake **successfully completes**, while a global, source-agnostic `ClientConnectionTracker` slot (bounded by `qos.max_concurrent_connections()`) is reserved for the full `QUIC_CONNECTION_HANDSHAKE_TIMEOUT` (2s) for every incoming connection attempt, including ones that never finish handshaking. An attacker from a single IP can therefore open connections that stall or abort before `register_connection` fires, never triggering per-IP throttling (`is_allowed` keeps returning `true` since no record is ever created), while repeatedly occupying `ClientConnectionTracker` slots out of the shared global pool.

### Finding Description
`run_server` (streamer/src/nonblocking/quic.rs:304-407) processes each incoming QUIC `Incoming`:
1. It performs an overall (non-per-IP) burst check by *peeking* `overall_connection_rate_limiter.current_tokens() == 0` — this does not consume a token here, so many simultaneous accepts can pass this check without being individually rate-limited.
2. It then performs a per-IP check via `rate_limiter.is_allowed(&incoming.remote_address().ip())` (streamer/src/nonblocking/connection_rate_limiter.rs:34-40). This function returns `true` whenever the IP has **no existing record** in the `KeyedRateLimiter` — and a record is only created by `register_connection`, which is called *inside* `setup_connection` **only after the handshake future resolves `Ok`** (streamer/src/nonblocking/quic.rs:476-493). If the attacker's connection never completes the handshake (stalls, or is aborted before completion), `register_connection` never runs, so `is_allowed` will keep returning `true` for that IP indefinitely — the per-IP limiter never accumulates state.
3. Regardless of per-IP state, `ClientConnectionTracker::new(stats, qos.max_concurrent_connections())` (streamer/src/nonblocking/quic.rs:236-252) is created for **every** attempt that passes the two rate checks, incrementing the global `stats.open_connections` counter and comparing it against a single shared `max_concurrent_connections` cap — with no per-IP dimension at all.
4. The tracker slot, along with `stats.outstanding_incoming_connection_attempts`, is held for up to `QUIC_CONNECTION_HANDSHAKE_TIMEOUT = Duration::from_secs(2)` (streamer/src/nonblocking/quic.rs:80, 472-475) before being released (on success, timeout, or handshake error).

Because per-IP throttling never engages for handshakes that don't complete, and the global admission cap (`ClientConnectionTracker`) is shared across all source IPs with no fairness/quota subdivision, one attacker repeatedly opening connections and immediately aborting/stalling before handshake completion can occupy up to `max_concurrent_connections` slots at a time, for `~2s` per slot, and refresh them continuously by opening new connections as old ones expire. Meanwhile `overall_connection_rate_limiter` does not block this because it is only checked as a peek (not consumed) at admission time and only actually consumed for connections that *complete* handshake in `setup_connection`. This lets a single-IP attacker keep the shared connection-admission pool saturated, causing legitimate peers' incoming connections to hit `ClientConnectionTracker::new`'s `Err` branch, incrementing `stats.refused_connections_too_many_open_connections` (streamer/src/nonblocking/quic.rs:371-379).

### Impact Explanation
This is a QoS evasion / resource-starvation issue: a single unstaked, unprivileged attacker holding one (or a small NAT pool of) source IP(s) can monopolize the shared, global connection-admission slots (`ClientConnectionTracker` / `outstanding_incoming_connection_attempts`) for sustained periods by exploiting the fact per-IP throttling (`ConnectionRateLimiter`) is keyed off handshake **completion**, not attempt. This starves legitimate senders (staked and unstaked) from establishing new QUIC connections to the leader's TPU, i.e., a scoped availability/QoS-evasion impact. It is bounded in absolute slot count by `max_concurrent_connections` (not literally unbounded memory), so it is a connection-admission DoS/QoS-evasion finding rather than an unbounded-memory or consensus-safety bug.

### Likelihood Explanation
Preconditions match the stated unprivileged threat model exactly: a remote, unstaked client sending arbitrary QUIC/UDP packets to the public TPU port, using its own real source IP (no spoofing/staking required). The attack requires only the ability to initiate a QUIC handshake and then stop responding/close before it completes (trivial to script with any QUIC client library or raw UDP). It is fully repeatable — as soon as one slot times out (2s) or is released, the attacker can immediately open another. No account for gossip/stake data, keys, or config is required.

### Recommendation
Track and bound `outstanding_incoming_connection_attempts` / pre-handshake `ClientConnectionTracker` reservations **per source IP** (not just globally), and/or make `ConnectionRateLimiter.is_allowed` gate on connection *attempts* (consumed at accept time, before handshake) rather than only on successful `register_connection`, refunding the token if the handshake later fails/times out. This restores the invariant that unstaked per-source connection/stream limits cannot be evaded purely by aborting the handshake before completion.

### Proof of Concept
Integration test plan (in `streamer/src/nonblocking/quic.rs` test module, alongside `setup_quic_server`/`SpawnTestServerResult` helpers already used by tests like `test_rate_limiting` at streamer/src/nonblocking/quic.rs / tpu-client-next/tests/connection_workers_scheduler_test.rs:601-662):
1. Spawn a test QUIC server via `setup_quic_server` with a small `max_concurrent_connections` (via `SwQosConfig`) and default `max_connections_per_ipaddr_per_min`.
2. From a single client IP (e.g., loopback bound to one address), open `N > max_concurrent_connections` concurrent `quinn::Endpoint::connect` attempts that intentionally never complete the handshake (e.g., drop the client endpoint / connecting future immediately after `connect()` returns, before `.await` resolves, or use a raw UDP socket sending only an Initial packet then going silent).
3. Concurrently, from a second, legitimate client IP/endpoint, attempt a normal connection expecting to succeed.
4. Assert that `stats.refused_connections_too_many_open_connections` increases and that the legitimate connection from step 3 is refused/times out while the attacker's stalled handshakes occupy the pool — demonstrating that `stats.open_connections` reached `max_concurrent_connections` due to a single IP's churned attempts, and that `rate_limiter.is_allowed` never blocked the attacker IP because `register_connection` was never invoked for the aborted handshakes.
5. Repeat step 2 in a loop (open → let stall/timeout → reopen) faster than `QUIC_CONNECTION_HANDSHAKE_TIMEOUT`, and assert the legitimate connection continues to be starved across multiple churn cycles, showing the per-IP limiter (`ConnectionRateLimiter`) never accumulates state (`current_tokens` stays at max for the attacker IP throughout).
