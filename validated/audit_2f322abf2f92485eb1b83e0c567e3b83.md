### Title
Unbounded attacker-controlled array-size allocation in `ValidateMultiSign` precompile can trigger uncaught `OutOfMemoryError` (DoS) - (`actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `ValidateMultiSign` TVM precompiled contract parses a signature-count field directly from calldata and uses it, without an upper-bound check on the non-hardfork code path, to allocate a Java array whose size is fully attacker-controlled. This mirrors the CVE-2021-3420 bug class: a length value taken from untrusted input is used to size a memory allocation without adequate overflow/bounds validation before allocation occurs.

### Finding Description
`ValidateMultiSign.execute()` reads a length word from the raw contract-call data and passes it into `extractBytesArray`/`extractSigArray`: [1](#0-0) 

The size check (`sigArraySize > MAX_SIZE`) that bounds the length is only performed when `VMConfig.allowTvmSelfdestructRestriction()` is enabled; when that hard-fork flag is not active, `extractBytesArray` (or `extractSigArray`) is invoked with a completely unchecked `len` derived from `words[offset].intValueSafe()`: [2](#0-1) 

`intValueSafe()` does not reject huge values — it merely clamps any value that doesn't fit safely into an `int` to `Integer.MAX_VALUE` instead of rejecting the input outright: [3](#0-2) 

That means an attacker who crafts calldata with a huge length word can force `new byte[len][]` to be executed with `len` up to `Integer.MAX_VALUE`, which is analogous to CVE-2021-3420's "unchecked length used directly in an allocation call" pattern — instead of a heap-buffer overflow (Java arrays are bounds-checked, so no memory corruption is possible), the result here is an attempted allocation of an enormous reference array, throwing `OutOfMemoryError`. Critically, this call happens **outside** the `try { ... } catch (Throwable t)` block that wraps the rest of the signature-verification logic: [4](#0-3) 

so the `OutOfMemoryError` raised while extracting the signature array is not locally caught by this actuator.

### Impact Explanation
An `OutOfMemoryError` is an unchecked `Error`, not an `Exception`. If it is not caught by a broad handler further up the TVM execution stack (opcode dispatch / `Program` / transaction-processing loop), it can propagate out of the transaction-processing thread. Depending on JVM state and how much heap the allocation attempt consumes before failing, this can degrade or crash the node process, denying service to the network — this matches the "node crash or halt" acceptance criterion. Because `ValidateMultiSign` is a reachable TVM precompile, any account can trigger this via a normal smart-contract call, i.e., no special privilege is required.

### Likelihood Explanation
Reachability is straightforward: any unprivileged account can deploy or call a contract that invokes the `ValidateMultiSign` precompiled address with crafted calldata containing an oversized "signature count" length word. Whether this currently causes real-world impact depends on:
- Whether `VMConfig.allowTvmSelfdestructRestriction()` is already enabled on production networks (if so, the `sigArraySize > MAX_SIZE` guard at lines 1066-1071 prevents the unbounded path from being reached, meaning this may already be mitigated on current mainnet forks, but would still be exploitable on any deployment/private chain running with that feature disabled).
- Whether upstream code (opcode execution / `Program`) catches generic `Throwable`/`Error` around precompile invocation, which I was unable to fully confirm within the available investigation.

These are open questions I could not fully resolve; a Devin session with full repo access could trace the exact hard-fork activation status and confirm whether `OutOfMemoryError` is caught anywhere between `PrecompiledContract.execute()` and the top-level block-application loop in `Manager`.

### Recommendation
Move the length/size validation (`sigArraySize > MAX_SIZE` or equivalent) so it unconditionally bounds the value returned by `words[...].intValueSafe()` **before** any array is allocated, regardless of the `allowTvmSelfdestructRestriction()` flag, in both `extractBytesArray` and `extractSigArray`. Additionally, `extractBytesArray`/`extractSigArray` should independently validate that `len` is within a sane bound (e.g., `MAX_SIZE`) rather than relying solely on the caller to pre-check it.

### Proof of Concept
1. Deploy a contract that performs a low-level `staticcall`/`call` to the `ValidateMultiSign` precompile address with calldata where the length word at offset `words[3]` (or the corresponding count word inside `extractBytesArray`) is set to a very large value (e.g., `0xFFFFFFFF...FF` truncated so `intValueSafe()` yields `Integer.MAX_VALUE`).
2. Ensure the network/build under test has `allowTvmSelfdestructRestriction()` disabled (or find another precompile calling `extractBytesArray`/`extractBytes32Array` without the extra guard).
3. Broadcast the transaction; observe `extractBytesArray` attempting `new byte[Integer.MAX_VALUE][]`, raising `OutOfMemoryError` outside of the local `try/catch(Throwable)` block, and trace whether this propagates to crash/degrade the node process.

   * In case of int overflow returns Integer.MAX_VALUE otherwise works as #intValue()

  public int intValueSafe() {
    int bytesOccupied = bytesOccupied();
    int intValue = intValue();
    if (bytesOccupied > 4 || intValue < 0) {
