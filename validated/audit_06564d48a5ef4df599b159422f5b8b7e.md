### Title
`remove_account` fails to purge `PostponedReceipt`/`PendingDataCount`/`PostponedReceiptId` entries, allowing a stale postponed receipt to execute privileged actions against a re-created account - ([File: core/store/src/utils/mod.rs])

### Summary
`remove_account` (invoked by `action_delete_account`) only removes `TrieKey::Account`, `TrieKey::ContractCode`, access/gas keys, and `TrieKey::ContractData` for a deleted account; it never touches `TrieKey::PostponedReceiptId`, `TrieKey::PendingDataCount`, or `TrieKey::PostponedReceipt`. An attacker who controls an account can plant a self-authorized postponed `ActionReceipt` (e.g. `AddKey`/`Transfer`/`DeployContract`) that is waiting on two `input_data_ids`, satisfy only one of them, then delete the account (which looks fully wiped) and let a new owner recreate it. When the attacker later delivers the second, pre-determined `DataReceipt`, the runtime resurrects and executes the original receipt's privileged actions against the new account's balance/keys/contract.

### Finding Description
`action_delete_account` (`runtime/runtime/src/actions.rs:314-390`) calls `remove_account(state_update, account_id)` and then unconditionally sets `*account = None`. `remove_account` (`core/store/src/utils/mod.rs:505-575`) removes only: [1](#0-0) [2](#0-1) [3](#0-2) 
It never issues `state_update.remove` for `TrieKey::PostponedReceiptId`, `TrieKey::PendingDataCount`, or `TrieKey::PostponedReceipt`, all of which are keyed by `receiver_id` (the account itself), as defined in `core/primitives/src/trie_key.rs:203-219`.

Attack construction (attacker A currently owns `x.alice.near`):
1. A's own contract, running as `x.alice.near` (so `predecessor_id == receiver_id == x.alice.near`), creates a self-targeted `ActionReceipt` with `input_data_ids = [d1, d2]` and `actions = [AddKey(A_backup_key)]` (or `Transfer`/`DeployContract`). Since this receipt cannot be executed immediately, `process_action_receipt` (`runtime/runtime/src/lib.rs:1593-1658`) stores `TrieKey::PostponedReceiptId{receiver_id: x.alice.near, data_id: d1}`, `..{data_id: d2}`, `TrieKey::PendingDataCount{receiver_id, receipt_id}=2`, and `set_postponed_receipt` (the full `Receipt`), all keyed to `x.alice.near`.
2. A satisfies `d1` (sends the first `DataReceipt`), which decrements `PendingDataCount` to 1 via `process_receipt`'s `Data` branch (`lib.rs:1367-1474`); the receipt stays postponed, still keyed to `x.alice.near`, still holding the original `predecessor_id`.
3. A calls `DeleteAccountAction`; `check_actor_permissions` passes because `actor_id == account_id == x.alice.near` (`actions.rs:761-776`), and there is no check anywhere in `action_delete_account` for outstanding postponed receipts/pending data. The account, code, keys, and data appear fully wiped.
4. A new owner (unaware of the trap) recreates `x.alice.near` (via `CreateAccountAction` from its parent), deposits funds, adds their own key, and/or deploys their own contract.
5. Attacker A delivers the second `DataReceipt` with `data_id = d2` (a value A fixed/knew at receipt-construction time, since it is deterministically derived and controlled by the account/receipt that produced it, e.g. `generate_data_id`/`create_data_id_from_receipt_id`, `core/primitives/src/utils.rs`). `process_receipt`'s `Data` branch looks up `TrieKey::PostponedReceiptId{receiver_id: x.alice.near, data_id: d2}` (still present in state), finds `PendingDataCount == 1`, decrements to 0, fetches the still-present `get_postponed_receipt` (`lib.rs:1398-1455`), and calls `apply_action_receipt` on the *original* `Receipt` object — untouched by the deletion.
6. Inside `apply_action`, `actor_id` for this receipt starts as the original `predecessor_id` (= `x.alice.near`, since it was a self-call). `check_actor_permissions` (`actions.rs:739-785`) requires `actor_id == account_id` for `AddKey`/`DeployContract`/`Transfer`-adjacent privileged actions, and this check passes trivially because the original receipt was self-authorized — it has nothing to do with who currently owns the re-created account.

The result: `AddKey`/`Transfer`/`DeployContract` execute against the new owner's account, balance, and storage, using authority derived from a receipt signed/authored by the account's *previous* owner. No existing check (nonce, access-key permission, storage-staking, delete-account-must-be-final, `DeleteAccountWithLargeState`, `GasKeyBalanceTooHigh`) inspects or clears the `PostponedReceipt*` family of trie keys.

### Impact Explanation
This breaks **authorization exactness**: a resurrected receipt authored by a former account owner can add a full-access key, transfer/drain balance, or overwrite deployed contract code on an account now controlled by a different party. This matches NEAR bounty categories for **authorization escalation across accounts** and **theft of funds** (via `Transfer` or key hijack enabling subsequent fund transfer), since the victim's post-recreation balance and contract state are directly manipulated by an action list the victim never authorized.

### Likelihood Explanation
- Fully reachable by an ordinary, unprivileged account owner using only standard host functions (`promise_batch_create` targeting self, `promise_batch_action_add_key`/`transfer`/`deploy_contract`, then `promise_batch_action_delete_account`) and later a `DataReceipt` submission (self-triggered, e.g. via a second contract call producing the matching value/promise callback).
- No special privileges, validator access, or leaked keys are required — attacker only needs control of the account before it changes hands (e.g., selling/handing off a subaccount, an account marketplace, a "burn and let someone else claim" scheme, or an account previously compromised and later "cleaned").
- The primary precondition is that a new owner is willing to reuse the exact same `AccountId` after a delete — plausible for subaccounts (`x.alice.near` can be recreated by `alice.near`) which is a common pattern (e.g., app-specific subaccounts, implicit "reset" flows).
- Cost to the attacker is minimal: a couple of low-value cross-contract calls and a delete action; fully repeatable for any account the attacker controls prior to deletion.

### Recommendation
`remove_account` should also purge all account-scoped receipt-processing state before/at deletion, specifically:
- Iterate and remove all `TrieKey::PostponedReceiptId{receiver_id: account_id, ..}`, `TrieKey::PendingDataCount{receiver_id: account_id, ..}`, and `TrieKey::PostponedReceipt{receiver_id: account_id, ..}` entries (and analogous `PromiseYieldReceipt`/`PromiseYieldStatus`/`ReceivedData` entries) for the account being deleted.
- Alternatively/additionally, disallow `DeleteAccountAction` while any postponed receipt or pending data count exists for that `receiver_id` (return a new `ActionErrorKind`, similar to `DeleteAccountWithLargeState`), forcing those to resolve or be discarded first, and require this protocol change to be introduced as a new protocol feature.

### Proof of Concept
Runtime `apply`-path integration test (in `runtime/runtime/src/tests/apply.rs` style):
1. Set up `x.alice.near` owned by attacker signer.
2. Submit an `ActionReceipt` with `predecessor_id = receiver_id = x.alice.near`, `input_data_ids = [d1, d2]`, `actions = [AddKey(attacker_backup_key)]`; assert it is postponed (`get_postponed_receipt` returns `Some`).
3. Submit a `DataReceipt{receiver_id: x.alice.near, data_id: d1, data: Some(vec![])}`; assert `PendingDataCount == 1` still exists and `PostponedReceipt` still present.
4. Submit `DeleteAccountAction{beneficiary_id: attacker}` from `x.alice.near`; commit; assert `get_account(x.alice.near) == None`.
5. Submit a `CreateAccountAction` + `AddKey(victim_key)` + `Transfer` receipt from `alice.near` recreating `x.alice.near` for a victim; commit.
6. Submit `DataReceipt{receiver_id: x.alice.near, data_id: d2, data: Some(vec![])}`.
7. Assert (expected failing/vulnerable behavior): after applying, `x.alice.near`'s access keys now include `attacker_backup_key` (or its balance/contract reflects the resurrected receipt's actions) — i.e., state diverges from being isolated to the victim's post-recreation identity, demonstrating the resurrection bug.
