### Title
Unvalidated attachment content hash in `AttachmentsBatchStateContext::extend_with_attachments` lets a peer forge attachment resolution and permanently drop a different, on-chain-committed attachment request - (File: stackslib/src/net/atlas/download.rs)

### Summary
`extend_with_attachments` decodes an `AttachmentRequest` response via `decode_atlas_get_attachment()` and inserts the returned `Attachment` into `self.attachments: HashSet<Attachment>` without ever checking that the served content's hash matches `request.content_hash` [1](#0-0) . Because resolution in the `Done` state is keyed entirely off `attachment.hash()` (the hash of the bytes as received) rather than the requested `content_hash`, a malicious peer can serve content for hash H2 in response to a request for H1, causing H1 to be permanently orphaned while H2 is resolved without ever having been legitimately requested.

### Finding Description
`get_prioritized_attachments_requests` builds `AttachmentRequest { content_hash, .. }` from on-chain-committed `AttachmentInstance` entries [2](#0-1) . When the response for such a request comes back, `extend_with_attachments` does:
```
if let Ok(response) = response.decode_atlas_get_attachment() {
    self.attachments.insert(response.attachment);
    report.bump_successful_requests();
}
``` [3](#0-2) 
`decode_atlas_get_attachment` simply JSON-decodes the HTTP body into `GetAttachmentResponse { attachment }` [4](#0-3)  — there is no assertion anywhere that `Hash160::from(&response.attachment.content) == request.content_hash`. The association between "which content_hash was requested" and "which bytes came back" is dropped at this point; only the raw `Attachment` (deduped by content via `HashSet<Attachment>`) survives into the `Done` state.

In `AttachmentsDownloader::run`, the `Done` branch then does:
```
for attachment in context.attachments.drain() {
    let attachments_instances = network.atlasdb.find_all_attachment_instances(&attachment.hash())?;
    network.atlasdb.insert_instantiated_attachment(&attachment)?;
    ...
    context.attachments_batch.resolve_attachment(&attachment.hash())
}
``` [5](#0-4) 
Everything here is indexed by the self-computed `attachment.hash()`, not by the `AttachmentRequest.content_hash` that solicited the response. So if a malicious/misbehaving peer answers a request for H1 with bytes that actually hash to H2, `insert_instantiated_attachment` stores those bytes keyed under H2, `find_all_attachment_instances(&H2)` resolves any pending instance tracked under H2 (which nobody requested from this peer), and H1's pending entry in `attachments_batch.attachments_instances` is left untouched — it is never retried against this peer for this content, and once the batch believes progress was made, it may not be re-driven correctly for H1, permanently orphaning a valid, on-chain-committed attachment request.

No guard (signature check, length check, or hash equality check) exists between the wire response and this indexing step to prevent this.

### Impact Explanation
A single malicious/misbehaving peer serving a crafted-but-otherwise-valid HTTP 200 attachment response can: (1) forge resolution of an attachment instance (H2) that it was never asked to serve, injecting attacker-chosen bytes into `atlasdb` under a hash the node did solicit for a *different* on-chain-committed instance context, and (2) permanently prevent the legitimately requested, on-chain-committed attachment (H1) from ever resolving through this code path. This is "network-wide propagation of forged data" / attachment mismatch — data is served/stored as resolved for a `content_hash` that was never actually the subject of the specific request that produced it, and a legitimately committed attachment can be dropped. This matches the High/Critical impact categories (attachment/BNS mismatch, forged-data storage).

### Likelihood Explanation
The attacker needs no privileged role — any outbound-sync peer that a node picks to fetch attachments from (an ordinary P2P peer serving the Atlas HTTP attachment endpoint) can trigger this by simply responding to any `GET /v2/attachments/<H1>` request with a 200 response whose JSON body decodes to content whose Hash160 is H2 ≠ H1. This requires no signature, no secret, and only a single crafted HTTP response — fully remotely reachable and repeatable for every attachment request the node issues to that peer.

### Recommendation
In `extend_with_attachments` (or in `decode_atlas_get_attachment`/`try_parse_response`), verify that `Hash160::from(&response.attachment.content) == request.content_hash` before inserting the attachment into `self.attachments`. Reject and treat as a failed request (bump `report.bump_failed_requests()`, and consider blacklisting/derating the peer) if the hash does not match the requested `content_hash`.

### Proof of Concept
In `stackslib::net::atlas::download` tests:
1. Construct an `AttachmentsBatchStateContext` with a pending `AttachmentsBatch` containing an instance for `content_hash = H1`.
2. Build a `BatchedRequestsResult<AttachmentRequest>` whose `succeeded` map has the `AttachmentRequest{content_hash: H1, ...}` mapped to a `StacksHttpResponse` whose JSON body is `GetAttachmentResponse { attachment: Attachment { content: B } }` where `Hash160::from(&B) = H2 != H1`.
3. Call `context.extend_with_attachments(&mut results)`, then drive the `Done` branch logic (as in `AttachmentsDownloader::run`) using a stub `AtlasDB`.
4. Assert: `atlasdb.find_attachment(&H2)` now returns `B` (unsolicited resolution), while `attachments_batch.attachments_instances` still contains the pending entry for `H1` (never resolved) — demonstrating the permanent orphaning of H1 and forged resolution of H2.

        mut self,
        results: &mut BatchedRequestsResult<AttachmentRequest>,
    ) -> AttachmentsBatchStateContext {

            let report = self
                .peers
                .get_mut(request.get_url())
                .expect("Atlas: unable to retrieve reliability report for peer");

            let response = if let Some(r) = response {
                r
            } else {
                report.bump_failed_requests();
                continue;
            };

            if let Ok(response) = response.decode_atlas_get_attachment() {
                self.attachments.insert(response.attachment);
                report.bump_successful_requests();
            } else {
                report.bump_failed_requests();
            }
        }
