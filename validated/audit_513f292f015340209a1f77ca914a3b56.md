### Title
StackerDB inventory reply advertises a chunk as stored before it is actually persisted, letting a peer's own inventory diverge from its committed state - (File: stackslib/src/net/stackerdb/mod.rs)

### Summary
`PeerNetwork::handle_unsolicited_StackerDBPushChunk` patches the outgoing `StackerDBChunkInv` reply's `slot_versions` entry to reflect the pushed chunk's new version *before* that chunk has actually been written to the local `StackerDBs` store. The write itself only happens later, asynchronously, once the message is forwarded to the relayer. This breaks the equality "advertised (served) inventory == committed state" that the rest of the StackerDB replication protocol depends on.

### Finding Description
When an unsolicited `StackerDBPushChunk` arrives, the node builds a `StackerDBChunkInv` reply via `make_StackerDBChunksInv_or_Nack`, which reflects the versions currently in the DB [1](#0-0) . It then calls `validate_received_chunk` to sanity-check the chunk's signature, size, staleness and write-count bound [2](#0-1) . If validation passes, the code directly mutates the in-memory `data.slot_versions` entry to the *new* version and comments explicitly that "we'll accept this chunk" [3](#0-2) .

Crucially, at this point the chunk bytes have not been passed to `StackerDBs::try_replace_chunk` (the only function that actually persists a chunk, verifies the slot signer, and enforces staleness/version/size bounds against the DB record) [4](#0-3) . The function only returns `(false, true)` — i.e., "forward to relayer for processing" — and separately sends the patched inventory reply back to the sender [5](#0-4) . The doc comment on the function itself notes that "write frequency is not checked for this chunk" at this stage, relying entirely on the later relay-driven store operation to actually apply the write and its own throttling/staleness checks [6](#0-5) .

This is the same class of bug as the H-01 report: a value/response is derived from an anticipated post-write state before the write that produces that state has actually happened. In `GovernanceHYBR`, shares were computed from `totalAssets()` after tokens were already deposited but the mint hadn't happened, corrupting the accounting invariant. Here, the *inventory advertisement* (what we tell a peer we have) is computed from a version bump that has not yet been committed to the StackerDB, corrupting the "what I advertise == what I actually store" invariant. If the deferred store subsequently fails or races with another concurrent write (e.g. the DB's own `write_freq`/staleness check rejects it, or another chunk for the same slot lands first via the relayer queue), the node has already told the requesting peer that it holds `slot_version = N`, while its committed state remains at an older version or unwritten.

### Impact Explanation
Peers doing StackerDB replication use `StackerDBChunkInv` responses to decide which neighbors to query for a given chunk version (rarest/newest-first scheduling, per the module docs) [7](#0-6) . A node that advertises a version it does not actually hold will cause requesting peers to select it as a source for that chunk, get a `NotFound`/stale-version reply or old data instead, and waste a sync round — effectively serving non-canonical (not-yet-committed, and possibly never-committed) state as canonical inventory. This matches the High-severity category "steering a node off the tip via false inventory" analog for StackerDB replica synchronization, since it can misdirect chunk-fetch scheduling network-wide for that replica set.

### Likelihood Explanation
This path is reachable by any peer able to send an unsolicited `StackerDBPushChunk` with a signature that passes `validate_received_chunk` (which only checks size, expected slot signer, and version bounds, not that the write actually lands) [2](#0-1) . No privileged key or blockchain event is required beyond owning (or reusing) a valid chunk signature for a StackerDB slot the attacker is authorized to write (a normal StackerDB participant such as a signer). The race window between "reply sent" and "chunk actually stored via relay" is small but real, and is explicitly acknowledged as unenforced ("write frequency is not checked for this chunk" at this stage).

### Recommendation
Do not patch/advertise the bumped `slot_version` in the `StackerDBChunkInv` reply until the chunk has actually been committed via `try_replace_chunk` (or equivalent), or defer sending the reply until after the relayer has processed and durably stored the chunk. If a synchronous ack is required for latency reasons, only advertise the new version after a successful, transactional persist, mirroring the `libstackerdb` sign/verify-before-store contract already enforced in `StackerDBs::try_replace_chunk`.

### Proof of Concept
1. A registered signer holding a private key for a valid StackerDB slot sends an unsolicited `StackerDBPushChunkData` with `slot_version = N` and a correct signature over that version/data.
2. `handle_unsolicited_StackerDBPushChunk` calls `validate_received_chunk`, which passes (size/version/signature checks only look at current on-disk `expected_versions`, not whether the coming write will succeed) [8](#0-7) .
3. The code patches `data.slot_versions[slot_id] = N` and immediately sends this `StackerDBChunkInv` back to the peer [9](#0-8) , while the actual `try_replace_chunk`/DB write is deferred to the relayer.
4. If the relayer's later store attempt fails (e.g., a concurrent higher-priority chunk for the same slot is processed first and bumps `slot_validation.version` past `N`, or `write_freq` throttling rejects the write), the node's actual stored slot version remains below `N`, yet it has already told the peer (and any other peer that queries it) that version `N` is available — a served/committed mismatch consistent with the report's bug class.

    pub fn validate_received_chunk(
        &self,
        smart_contract_id: &QualifiedContractIdentifier,
        config: &StackerDBConfig,
        data: &StackerDBChunkData,
        expected_versions: &[u32],
    ) -> Result<bool, net_error> {
        // validate -- must not exceed this replica's configured chunk size.
        if (data.data.len() as u64) > config.chunk_size {
            info!(
                "Received StackerDBChunk for {} ID {}, which is oversized: {} bytes (max {} bytes)",
                smart_contract_id,
                data.slot_id,
                data.data.len(),
                config.chunk_size
            );
            return Ok(false);
        }

        // validate -- must be a valid chunk
        let Some(expected_version) = expected_versions.get(data.slot_id as usize) else {
            info!(
                "Received StackerDBChunk for {} ID {}, which is too big ({})",
                smart_contract_id,
                data.slot_id,
                expected_versions.len()
            );
            return Ok(false);
        };

        // validate -- must be signed by the expected author
        let addr = match self
            .stackerdbs
            .get_slot_signer(smart_contract_id, data.slot_id)?
        {
            Some(addr) => addr,
            None => {
                return Ok(false);
            }
        };

        let slot_metadata = data.get_slot_metadata();
        if !slot_metadata.verify(&addr)? {
            info!(
                "StackerDBChunk for {} ID {} is not signed by {}",
                smart_contract_id, data.slot_id, &addr
            );
            return Ok(false);
        }

        // validate -- must be the current or newer version
        if data.slot_version < *expected_version {
            info!(
                "Received StackerDBChunk for {} ID {} version {}, which is stale (expected {})",
                smart_contract_id, data.slot_id, data.slot_version, *expected_version
            );
            return Ok(false);
        }

        // validate -- must not exceed max writes
        if data.slot_version > config.max_writes {
            info!(
                "Write count exceeded for StackerDBChunk for {} ID {} version {} (max is {})",
                smart_contract_id, data.slot_id, data.slot_version, config.max_writes
            );
            return Ok(false);
        }

        Ok(true)
    }

    /// Add or replace a chunk for a given reward cycle, if it is valid
    /// Otherwise, this errors out with Error::StaleChunk
    pub fn try_replace_chunk(
        &self,
        smart_contract: &QualifiedContractIdentifier,
        slot_desc: &SlotMetadata,
        chunk: &[u8],
    ) -> Result<(), net_error> {
        // Check per-replica chunk-size cap.
        if (chunk.len() as u64) > self.config.chunk_size {
            return Err(net_error::StackerDBChunkTooBig(chunk.len()));
        }

        let slot_validation = self
            .get_slot_validation(smart_contract, slot_desc.slot_id)?
            .ok_or(net_error::NoSuchSlot(
                smart_contract.clone(),
                slot_desc.slot_id,
            ))?;

        if !slot_desc.verify(&slot_validation.signer)? {
            return Err(net_error::BadSlotSigner(
                slot_validation.signer,
                slot_desc.slot_id,
            ));
        }
        if slot_desc.slot_version <= slot_validation.version {
            return Err(net_error::StaleChunk {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
            });
        }
        if slot_desc.slot_version > self.config.max_writes {
            return Err(net_error::TooManySlotWrites {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
                max_writes: self.config.max_writes,
            });
        }
        self.insert_chunk(smart_contract, slot_desc, chunk)
    }
