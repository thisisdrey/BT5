### Title
Non-constant-time `auth_token` comparison enables remote timing-based recovery of the node's privileged RPC secret - ([File: stackslib/src/net/api/postblock_proposal.rs])

### Summary
Several privileged Stacks RPC endpoints authenticate callers by comparing the `authorization` HTTP header against the node's configured `auth_token` using ordinary Rust string (in)equality (`auth_header != password`). This comparison is not constant-time, so a remote, unauthenticated attacker can use response-timing differences to recover the secret token byte-by-byte and then use it to invoke privileged write/broadcast endpoints such as `/v3/block_proposal`.

### Finding Description
The `auth_token` is a shared secret meant to gate privileged endpoints (block proposal submission, block replay/simulate, fast-call read-only, tx simulate, and authenticated block broadcast) between a `stacks-node` and its `stacks-signer`/operator: [1](#0-0) 

The same insecure comparison pattern is repeated verbatim across multiple handlers. In `postblock_proposal.rs` (guards `/v3/block_proposal`, which accepts block proposals for mining/signing consideration): [2](#0-1) 

The identical pattern appears in `blockreplay.rs`: [3](#0-2) 

in `blocksimulate.rs`: [4](#0-3) 

in `fastcallreadonly.rs`: [5](#0-4) 

and in `postblock_v3.rs`, which gates authenticated `broadcast=1` submission of blocks over `/v2/blocks`: [6](#0-5) 

In each case the check is `auth_header != password` (a `String`/`&str` comparison). Rust's default `PartialEq` for strings/byte slices is a length check followed by a `memcmp`-style comparison that is free to (and typically does, depending on codegen/CPU/compiler) short-circuit or vary timing based on the position of the first mismatching byte. This is the same class of "authenticated vs. stored" equality-check weakness noted in the external report (secrets recoverable due to insufficient protection of the equality operation), except here the *comparison mechanism itself*, not just the transport, is the fault: no `subtle`/constant-time comparison crate is used anywhere in this codebase (`grep` for `constant_time`/`subtle::` returns no hits), so every one of these six privileged endpoints is susceptible to a remote timing side-channel that leaks the auth secret.

### Impact Explanation
An attacker with only network access to the RPC port (no valid credentials) can repeatedly probe the `authorization` header value and use timing measurements to reconstruct the `auth_token` byte-by-byte (a classic byte-at-a-time timing oracle attack). Once recovered, the attacker gains the privileges gated by that single shared token across *all* of these endpoints simultaneously, including:
- submitting/broadcasting attacker-controlled block proposals via `/v3/block_proposal`,
- forcing authenticated block broadcast via `/v2/blocks?broadcast=1`,
- invoking privileged read endpoints (`fast-call-read`, block/tx simulate, block replay) that may have looser resource/DoS bounds than public endpoints.

This matches the "auth bypass" / "unauthenticated write to state" tier called out as Critical impact, since it fully defeats the node's only authentication mechanism for privileged endpoints remotely.

### Likelihood Explanation
Exploitation requires only unauthenticated network access to the RPC/API port and the ability to send many requests and measure response timing — no special privileges, node secret, or another party's key are needed. It does not rely on volumetric flooding; it is a targeted, low-bandwidth timing side channel against six independent handlers that all share the identical faulty comparison pattern, increasing the number of oracles available to average out noise. Real-world timing attacks against short shared-secret string comparisons are well documented and practically feasible, especially against endpoints reachable over low-latency/local networks (e.g., signer-to-node deployments).

### Recommendation
Replace all `auth_header != password` / `auth_header == password` checks in `postblock_proposal.rs`, `blockreplay.rs`, `blocksimulate.rs`, `fastcallreadonly.rs`, `postblock_v3.rs`, and `txsimulate.rs` with a constant-time comparison (e.g., using the `subtle` crate's `ConstantTimeEq`, or an HMAC-based comparison), applied uniformly through a single shared helper so future endpoints don't reintroduce the bug.

### Proof of Concept
1. Configure a node with `connection_options.auth_token = "<secret>"`.
2. From a remote unauthenticated client, send repeated POST requests to `/v3/block_proposal` (or any of the other five endpoints) with `authorization` headers that are correct up to position *n* and differ at position *n+1*, sweeping over candidate bytes at position *n+1*.
3. Measure response latency for the 401 rejection path (`auth_header != password` branch) for each candidate byte; statistically the candidate producing the longest average comparison time before mismatch indicates the correct next byte (because `memcmp`/slice-eq intrinsics conventionally compare byte-by-byte or word-by-word and diverge at the first mismatch).
4. Repeat byte-by-byte to fully reconstruct `auth_token`, then use it to submit forged block proposals to `/v3/block_proposal`.
