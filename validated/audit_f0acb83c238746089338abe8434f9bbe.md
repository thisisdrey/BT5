### Title
Debited wNEAR `storage_deposit` amount is never refunded when the `storage_deposit` sub-step of `ft_withdraw` fails - (File: contracts/defuse/src/contract/tokens/nep141/withdraw.rs)

### Summary
`internal_ft_withdraw` debits the withdrawn token amount **and** the wNEAR `storage_deposit` amount from the owner's internal balance up-front, then chains `near_withdraw → storage_deposit(token) → ft_transfer/ft_transfer_call → ft_resolve_withdraw`. `ft_resolve_withdraw` only receives `(token, sender_id, amount, is_call)` and only checks/refunds the outcome of the final `ft_transfer`/`ft_transfer_call` promise result; it has no parameter and no logic tied to the `storage_deposit` promise's outcome. If the token's `storage_deposit` call fails (e.g. a malicious/misbehaving token contract), the unwrapped NEAR is refunded by the runtime to the Verifier contract's own NEAR balance (not to the user's internal ledger), while the internal wNEAR debit made in `self.withdraw(...)` is never reversed.

### Finding Description
The claimed binding is:
`debited(wNEAR, storage_deposit.amount)` == `delivered(storage registered on token for receiver_id)` + `re-credited(via ft_resolve_withdraw refund)`.

Trace:
- `internal_ft_withdraw` [1](#0-0)  calls `self.withdraw(...)` which subtracts **both** the withdrawn `token` amount and, if `withdraw.storage_deposit` is `Some`, the wNEAR amount via `internal_sub_balance`/`Amounts::sub` (`Nep141TokenId::new(self.wnear_id())`), unconditionally, before any promise executes.
- The promise chain is `near_withdraw(wNEAR)` → `do_ft_withdraw` → `storage_deposit(token)` chained via `ext_ft_core::ext_on(p)` into `ft_transfer`/`ft_transfer_call` → outer `.then(ft_resolve_withdraw(token, owner_id, amount, is_call))` [2](#0-1) .
- `do_ft_withdraw` only asserts that the *near_withdraw* step succeeded (`promise_result_checked_void(0)` at index 0, referring to the predecessor of `do_ft_withdraw` itself) before issuing the `storage_deposit` call; it never checks or gates on the `storage_deposit` call's own outcome [3](#0-2) .
- `ft_resolve_withdraw` takes only `token`, `sender_id`, `amount`, `is_call` — there is no `storage_deposit` parameter at all, so it is structurally impossible for it to inspect or refund the storage_deposit sub-step's result. Its refund logic only compares `used` (derived from the `ft_transfer`/`ft_transfer_call` promise result) against `amount` (the withdrawn token amount), and refunds only `token`, never wNEAR [4](#0-3) .
- If the token's `storage_deposit` receipt fails (panics), the NEAR runtime automatically returns the attached deposit (the unwrapped NEAR) to the predecessor account, i.e. the Verifier contract's own NEAR balance — not to any user's wNEAR internal balance. Because `ft_transfer`/`ft_transfer_call` is a plain (non-callback) call that does not itself inspect the predecessor's promise result, it still executes and, if the attacker's own malicious token contract implements it to succeed, `ft_resolve_withdraw` will see a successful transfer and refund nothing.
- Net effect: the wNEAR debited for `storage_deposit` is gone from the owner's internal ledger, no storage was registered on the target contract, and no refund path exists anywhere in the codebase for this specific component of the withdrawal.

This is not merely a malicious-token edge case; it is a structural gap—`ft_resolve_withdraw`'s signature and logic never account for the storage_deposit wNEAR leg under any failure of that specific sub-step.

### Impact Explanation
The Verifier's internal ledger permanently loses the wNEAR amount attributed to `storage_deposit` for the withdrawing owner with nothing delivered (no storage registered, no re-credit). This is repeatable per `ft_withdraw` call with `storage_deposit: Some(...)` against any token contract whose `storage_deposit` fails while `ft_transfer`/`ft_transfer_call` still succeeds (trivial for an attacker's own deployed token) — each call permanently destroys the caller's own wNEAR balance amount equal to the storage deposit. While the attacker only destroys their own funds in the straightforward case (self-inflicted, no direct "theft" from another party), it breaks the debited == delivered + re-credited settlement invariant and constitutes a real accounting break where the Verifier's ledger diverges from custodied value: NEAR that should be attributable to the user (via storage registration or refund) is stranded as unattributed native NEAR sitting on the Verifier contract itself. This matches the Critical category "a refund or resolver credit that does not match what failed to settle."

### Likelihood Explanation
Preconditions are minimal and fully within an unprivileged attacker's control: deploy or use a token contract whose `storage_deposit` method panics (or simply lacks registration/fails for other legitimate reasons, e.g. paused, insufficient deposit) while its `ft_transfer`/`ft_transfer_call` succeeds; hold a wNEAR balance in the Verifier; call `ft_withdraw` (or via `execute_intents`/`FtWithdraw` intent) with `storage_deposit: Some(amount)` targeting that token. No relayer key, DAO role, or special privilege is required. It is fully attacker-controlled and reproducible on every call.

### Recommendation
Change `ft_resolve_withdraw` (and the analogous `nft_resolve_withdraw`/`mt_resolve_withdraw`) to also accept the `storage_deposit` amount, inspect the dedicated promise result index corresponding to the `storage_deposit` call, and refund the wNEAR amount to the owner via `self.deposit(...)` whenever that sub-step did not succeed, independent of the outcome of the token transfer step.

### Proof of Concept
`cargo test` plan (near-workspaces sandbox, non-mainnet):
1. Deploy a malicious FT contract whose `storage_deposit` handler always calls `env::panic_str("malicious storage_deposit failure")`, but whose `ft_transfer`/`ft_transfer_call` succeeds normally.
2. Deploy the Verifier (`defuse`) contract and wNEAR; fund a test user's internal Verifier balance with wNEAR (`storage_deposit.amount`) and with the malicious token (`withdraw.amount`).
3. Sign and submit an `ft_withdraw` intent (or call `ft_withdraw` directly with 1 yoctoNEAR attached) with `token = malicious_token`, `storage_deposit = Some(amount)`.
4. Await full promise resolution.
5. Assert:
   - `near_withdraw` succeeded (verified via receipt outcomes),
   - the malicious token's `storage_deposit` receipt failed,
   - `mt_balance_of(user, wnear_token_id)` after execution equals `initial_wnear_balance - storage_deposit.amount` (i.e., **not refunded**), demonstrating the debited wNEAR amount is permanently lost with no re-credit and no storage registered on the malicious token. [5](#0-4) [3](#0-2) [6](#0-5)

        &mut self,
        owner_id: AccountId,
        withdraw: FtWithdraw,
        force: bool,

        self.withdraw(
            &owner_id,

                Nep141TokenId::new(withdraw.token.clone()).into(),
                withdraw.amount,
            ))
            .chain(withdraw.storage_deposit.map(|amount| {
                (
                    Nep141TokenId::new(self.wnear_id().into_owned()).into(),
                    amount.as_yoctonear(),
                )
            })),
            Some("withdraw"),
            force,
        )?;

        let is_call = withdraw.is_call();
        Ok(if let Some(storage_deposit) = withdraw.storage_deposit {
            ext_wnear::ext(self.wnear_id.clone())
                .with_attached_deposit(NearToken::from_yoctonear(1))
                .with_static_gas(NEAR_WITHDRAW_GAS)
                // do not distribute remaining gas here
                .with_unused_gas_weight(0)
                .near_withdraw(U128(storage_deposit.as_yoctonear()))
                .then(
                    // schedule storage_deposit() only after near_withdraw() returns
                    Self::ext(env::current_account_id())
                        .with_static_gas(

                                .ok_or(DefuseError::GasOverflow)
                                .unwrap_or_else(|err| err.panic()),
                        )

                )

impl Contract {
    const FT_RESOLVE_WITHDRAW_GAS: Gas = Gas::from_tgas(5);
    const DO_FT_WITHDRAW_GAS: Gas = Gas::from_tgas(5)
        // do_ft_withdraw() method is called externally
        // only with storage_deposit
        .saturating_add(STORAGE_DEPOSIT_GAS);

    #[private]
    pub fn do_ft_withdraw(withdraw: FtWithdraw) -> Promise {
        let min_gas = withdraw.min_gas();
        let p = if let Some(storage_deposit) = withdraw.storage_deposit {
            require!(
                promise_result_checked_void(0).is_ok(),
                "near_withdraw failed",
            );

            ext_storage_management::ext(withdraw.token)
                .with_attached_deposit(storage_deposit)
                .with_static_gas(STORAGE_DEPOSIT_GAS)
                // do not distribute remaining gas here
                .with_unused_gas_weight(0)
                .storage_deposit(Some(withdraw.receiver_id.clone()), None)
        } else {
            Promise::new(withdraw.token)
        };

        let p = ext_ft_core::ext_on(p)
            .with_attached_deposit(NearToken::from_yoctonear(1))
            .with_static_gas(min_gas)
            // distribute remaining gas here
            .with_unused_gas_weight(1);
        if let Some(msg) = withdraw.msg {
            p.ft_transfer_call(
                withdraw.receiver_id,
                withdraw.amount.into(),
                withdraw.memo,
                msg,
            )
        } else {
            p.ft_transfer(withdraw.receiver_id, withdraw.amount.into(), withdraw.memo)
        }
    }

#[near]
impl FungibleTokenWithdrawResolver for Contract {
    #[private]
    fn ft_resolve_withdraw(
        &mut self,
        token: AccountId,
        sender_id: AccountId,
        amount: U128,
        is_call: bool,
    ) -> U128 {
        let used = if is_call {
            // `ft_transfer_call` returns successfully transferred amount
            match promise_result_checked_json::<U128>(0) {
                Ok(Ok(used)) => used.0.min(amount.0),
                Ok(Err(_deserialize_err)) => 0,
                // do not refund on failed `ft_transfer_call` due to
                // NEP-141 vulnerability: `ft_resolve_transfer` fails to
                // read result of `ft_on_transfer` due to insufficient gas
                Err(_) => amount.0,
            }
        } else {
            // `ft_transfer` returns empty result on success
            if promise_result_checked_void(0).is_ok() {
                amount.0
            } else {
                0
            }
        };

        let refund = amount.0.saturating_sub(used);
        if refund > 0 {
            self.deposit(
                sender_id,
                [(Nep141TokenId::new(token).into(), refund)],
                Some(REFUND_MEMO),
            )
            .unwrap_or_else(|err| err.panic());
        }

        U128(used)
    }
}
