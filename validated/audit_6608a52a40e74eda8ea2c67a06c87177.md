### Title
StackerDB push-chunk handler advertises accepted slot versions in `StackerDBChunkInv` before the chunk is actually committed to storage - ([File: stackslib/src/net/stackerdb/mod.rs])

### Summary
When a peer pushes a `StackerDBPushChunk`, `PeerNetwork::handle_unsolicited_StackerDBPushChunk` validates the chunk and immediately replies with a `StackerDBChunkInv` whose `slot_versions` entry is patched to the *new* version the peer just sent — before that chunk has actually been written to the local StackerDB. Actual storage happens later, asynchronously, via `Relayer::process_pushed_stacker_db_chunks` → `process_stacker_db_chunks` → `StackerDBTx::try_replace_chunk`. If that later write fails or is superseded (e.g. lost race against a concurrent write, `StaleChunk`, DB error, or reconfiguration), the node has already told its neighbor that it possesses a slot version it never actually stored.

### Finding Description
In `stackslib/src/net/stackerdb/mod.rs`, `handle_unsolicited_StackerDBPushChunk` builds a reply payload via `make_StackerDBChunksInv_or_Nack`, then runs the chunk through `validate_received_chunk` (which only checks size, signature, expected version against the *currently known* `slot_versions`, and max-writes bound): [1](#0-0) 

If validation passes and the DB is not stale/future-view, the handler mutates the outgoing `StackerDBChunkInv.slot_versions` entry to the pushed chunk's new version and — because `send_reply` is true on first receipt — signs and sends this reply to the peer immediately: [2](#0-1) 

The function then returns `(false, true)` — meaning “don’t buffer, forward to relayer” — so the *actual* write to the database happens later, out-of-band, through `Relayer::process_pushed_stacker_db_chunks`, which converts the pushed chunk into a sync result and calls `try_replace_chunk`: [3](#0-2) 

`try_replace_chunk` re-checks signature, staleness (`slot_version <= slot_validation.version`), and max-writes at commit time — a second, independent check that can fail even though the earlier `validate_received_chunk` succeeded (e.g. a concurrent write from another peer advanced the version in the interim, or the transaction otherwise errors): [4](#0-3) 

This creates an equality break between "advertised via `StackerDBChunkInv`" and "actually committed to the chunks table": the reply is generated and sent using an in-memory, pre-commit view, while the ground truth is decided later by a second, separately-arbitrated write.

### Impact Explanation
This matches the "serving non-canonical state as canonical" / "false inventory" class (High): the node tells peers it holds a specific `(slot_id, slot_version)` chunk via `StackerDBChunkInv`, which peers use to decide whether to skip requesting/re-syncing that slot from this node. If the underlying store never completes (raced by a concurrent write, or otherwise rejected in `try_replace_chunk`), the node's replica is left holding a stale or different chunk than the version it advertised, while neighbors believe the sync is complete. This can stall/steer the eventual convergence of the StackerDB replica set (used e.g. for signer message coordination), degrading availability of that DB's canonical state on the network. No privileged role or secret key is required to trigger it — any peer that can open a P2P conversation and push a validly-signed chunk can race two writes to the same slot from different connections to reproduce the mismatch.

### Likelihood Explanation
Likelihood is bounded by needing a race between two writers targeting the same `(contract_id, slot_id)`: an attacker fully controlling one writer (their own valid slot key) racing another legitimate writer for the same slot, or simply sending a chunk while a slightly-stale version is momentarily still recorded and a competing write is in flight. The two validation passes (`validate_received_chunk` at reply time vs `try_replace_chunk` at commit time) are not run under one atomic guard spanning both the read and the eventual write, so the window is real, though it requires two independent updates to the same slot arriving close together — a High-likelihood scenario is plausible in busy signer-set StackerDB traffic but is not trivially deterministic from a single message.

### Recommendation
Do not construct/patch and send the `StackerDBChunkInv` reply's `slot_versions` optimistically based on validation alone. Either:
- Defer sending the inventory reply until after the chunk has actually been committed by `try_replace_chunk` (i.e., invert the order: store first, then reply with the post-commit version), or
- Make the validate-then-reply and the eventual store operate on the same lock/transaction so the two cannot diverge, and on write failure, immediately correct/redo the previously-sent inventory (or simply not advertise until the storage attempt resolves).

### Proof of Concept
1. Two neighbors, N1 and N2, both have signing authority producible for slot `S` in StackerDB config, and both independently push `StackerDBPushChunk` messages for slot `S` with versions `V1` and `V2` (`V1, V2 > current_version`) to the target node at nearly the same time (each is a valid, remote, unauthenticated request in that no privileged role is required — just an established P2P conversation and a version-bumping chunk).
2. The target's `handle_unsolicited_StackerDBPushChunk` runs `validate_received_chunk` for the first-processed message and immediately replies with a `StackerDBChunkInv` advertising version `V1` (or `V2`) for slot `S`, per `stackslib/src/net/stackerdb/mod.rs:794-807`.
3. Both messages are subsequently routed to `Relayer::process_pushed_stacker_db_chunks` → `process_stacker_db_chunks` → `try_replace_chunk`, which processes them sequentially in a single DB transaction; only the higher version wins, and the other is rejected as `StaleChunk` (`stackslib/src/net/stackerdb/db.rs:424-429`).
4. If the version that the node already advertised via `StackerDBChunkInv` in step 2 is the one that loses the race (e.g., commit ordering differs from reply ordering, or the transaction that would have stored it errors for any reason), the neighbor now believes the target node holds slot `S` at the version it advertised, but the actual stored chunk is a different (or stale) version — an observable, reproducible false-inventory state without needing anything beyond ordinary unauthenticated StackerDB push traffic.

    pub fn validate_received_chunk(
        &self,
        smart_contract_id: &QualifiedContractIdentifier,
        config: &StackerDBConfig,
        data: &StackerDBChunkData,
        expected_versions: &[u32],
    ) -> Result<bool, net_error> {
        // validate -- must not exceed this replica's configured chunk size.
        if (data.data.len() as u64) > config.chunk_size {
            info!(
                "Received StackerDBChunk for {} ID {}, which is oversized: {} bytes (max {} bytes)",
                smart_contract_id,
                data.slot_id,
                data.data.len(),
                config.chunk_size
            );
            return Ok(false);
        }

        // validate -- must be a valid chunk
        let Some(expected_version) = expected_versions.get(data.slot_id as usize) else {
            info!(
                "Received StackerDBChunk for {} ID {}, which is too big ({})",
                smart_contract_id,
                data.slot_id,
                expected_versions.len()
            );
            return Ok(false);
        };

        // validate -- must be signed by the expected author
        let addr = match self
            .stackerdbs
            .get_slot_signer(smart_contract_id, data.slot_id)?
        {
            Some(addr) => addr,
            None => {
                return Ok(false);
            }
        };

        let slot_metadata = data.get_slot_metadata();
        if !slot_metadata.verify(&addr)? {
            info!(
                "StackerDBChunk for {} ID {} is not signed by {}",
                smart_contract_id, data.slot_id, &addr
            );
            return Ok(false);
        }

        // validate -- must be the current or newer version
        if data.slot_version < *expected_version {
            info!(
                "Received StackerDBChunk for {} ID {} version {}, which is stale (expected {})",
                smart_contract_id, data.slot_id, data.slot_version, *expected_version
            );
            return Ok(false);
        }

        // validate -- must not exceed max writes
        if data.slot_version > config.max_writes {
            info!(
                "Write count exceeded for StackerDBChunk for {} ID {} version {} (max is {})",
                smart_contract_id, data.slot_id, data.slot_version, config.max_writes
            );
            return Ok(false);
        }

        Ok(true)

    /// extract all StackerDBPushChunk messages from `unhandled_messages`

        &mut self,

        stackerdb_chunks: Vec<PushedStackerDBChunk>,

    ) -> Result<(), Error> {
        // synthesize StackerDBSyncResults from each chunk
        let sync_results = stackerdb_chunks
            .into_iter()
            .map(|pushed| {
                debug!("Received pushed StackerDB chunk {:?}", pushed.chunk);
                StackerDBSyncResult::from_pushed_chunk(pushed.chunk, pushed.peer)
            })
            .collect();

        self.process_stacker_db_chunks(
            rc_consensus_hash,
            stackerdb_configs,
            sync_results,
            event_observer,
        )
    }

    /// Add or replace a chunk for a given reward cycle, if it is valid
    /// Otherwise, this errors out with Error::StaleChunk
    pub fn try_replace_chunk(
        &self,
        smart_contract: &QualifiedContractIdentifier,
        slot_desc: &SlotMetadata,
        chunk: &[u8],
    ) -> Result<(), net_error> {
        // Check per-replica chunk-size cap.
        if (chunk.len() as u64) > self.config.chunk_size {
            return Err(net_error::StackerDBChunkTooBig(chunk.len()));
        }

        let slot_validation = self
            .get_slot_validation(smart_contract, slot_desc.slot_id)?
            .ok_or(net_error::NoSuchSlot(
                smart_contract.clone(),
                slot_desc.slot_id,
            ))?;

        if !slot_desc.verify(&slot_validation.signer)? {
            return Err(net_error::BadSlotSigner(
                slot_validation.signer,
                slot_desc.slot_id,
            ));
        }
        if slot_desc.slot_version <= slot_validation.version {
            return Err(net_error::StaleChunk {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
            });
        }
        if slot_desc.slot_version > self.config.max_writes {
            return Err(net_error::TooManySlotWrites {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
                max_writes: self.config.max_writes,
            });
        }
        self.insert_chunk(smart_contract, slot_desc, chunk)
    }
