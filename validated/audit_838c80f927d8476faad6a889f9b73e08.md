## Title
Stale `last-update` timestamp during zero-utilization periods causes retroactive interest overcharge on new borrowers - (File: `mainnet/contracts/vault/v0-vault-stx.clar` and duplicated in `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`)

### Summary
The Zest vault's `accrue` function only advances `last-update` when the borrow index (`index`) or the liquidity index (`lindex`) actually changes value. When utilization is `u0` (no outstanding debt), the computed interest rate for that utilization point can make the compounding multiplier equal exactly `INDEX-PRECISION`, so `next-index`/`next-liquidity-index` return the same value as the current index. In that case neither index changes and `last-update` is never bumped forward, exactly mirroring the reported IonPool `_calculateRewardAndDebtDistribution` bug where `lastRateUpdate` is left stale when there is no debt.

### Finding Description
`accrue` in each vault contract only writes `last-update` conditionally: [1](#0-0) 

The next index is computed from a `time-delta` since `last-update` and the current `interest-rate()`, which itself is a function of `utilization`, which is `calc-utilization(available-assets, total-debt)`: [2](#0-1) [3](#0-2) 

When `total-debt` is `u0`, `calc-utilization` returns `u0`. If the interest-rate curve's lowest util point maps to a rate of `u0` (a very common design where the "base rate" at 0% utilization is 0, and only accrues once utilization or a fixed base spread applies) `calc-multiplier-delta(rate=0, time-delta, ...)` reduces to exactly `INDEX-PRECISION`, so `calc-index-next(idx, INDEX-PRECISION) == idx`. Because both `index` and `lindex` stay unchanged in this branch, the condition `(or (not (is-eq idx next)) (not (is-eq lidx nliq)))` in `accrue` is `false`, and `last-update` is **not** advanced, no matter how much real time has elapsed while there was no debt.

The impact appears when the first borrower opens a position: `system-borrow` calls `(accrue)` before recording the new debt: [4](#0-3) 

At that call, `total-debt` is still `u0` (the new principal hasn't been added yet), so `accrue` again leaves `last-update` untouched at its old, stale value (which could be from long before, e.g. the last time the vault had any debt, or vault deployment). The borrower's new principal is recorded scaled by the (unchanged) `index`. On the *next* `accrue` call — now that utilization is non-zero and the interest rate is non-zero — `next-index` computes `time-delta = current-time - last-update`, which spans back through the entire idle, debt-free period, not just the time since the position was opened. The resulting index jump is applied to *all* current debt, including the new borrower's principal, effectively charging them interest for a period during which they had no debt outstanding.

### Impact Explanation
This inflates the debt owed by every borrower present after the stale gap is finally "caught up," because `calc-cumulative-debt` scales all `principal-scaled` positions by the same erroneously-inflated `index`. Borrowers are forced to repay more than their actual accrued interest, and undercollateralized positions could be pushed into unwarranted liquidation due to the artificially inflated debt figure. This is a direct extraction of value from borrowers' funds through the reward/debt distribution and interest accrual accounting layer, which is explicitly listed as an in-scope vault-share-math/interest-accrual analog. This lands on the Critical impact class (direct theft of user funds at rest/in motion — the excess interest charged is effectively transferred out of the borrower's position) or, at minimum, High (theft of unclaimed yield/temporary freezing) depending on the resulting liquidation exposure.

### Likelihood Explanation
The trigger condition is simply "the vault has zero outstanding debt for a period of time and the interest-rate curve's zero-utilization point yields a multiplier of exactly `INDEX-PRECISION`." This is a very plausible configuration for a lending market (e.g., a newly deployed vault, a vault that has been fully repaid, or long idle periods with no borrowers), making it likely to occur naturally without any adversarial action — any ordinary user who becomes "the first borrower" after an idle, debt-free stretch triggers the miscalculation.

### Recommendation
Always advance `last-update` to the current block time whenever `accrue` runs and the protocol is not paused, regardless of whether `index`/`lindex` numerically changed (i.e., unconditionally on the non-paused branch, not gated by `(or (not (is-eq idx next)) (not (is-eq lidx nliq)))`). This mirrors the fix applied upstream for the IonPool `_calculateRewardAndDebtDistribution` issue (Ion-Protocol PR #21) — the timestamp must reflect "time since last accrual attempt," not "time since the index last moved."

### Proof of Concept
1. Vault has zero total debt for an extended period (e.g., all previous borrowers repaid). During this time `accrue` is called repeatedly (or not at all) but because `utilization = 0` yields `rate = 0` and thus `multiplier = INDEX-PRECISION`, `index`/`lindex` never change and `last-update` stays frozen at time `T0`.
2. At time `T1` (much later), a user calls `system-borrow`. Inside, `accrue` runs first: `total-debt` is still 0 pre-borrow, so again `index` doesn't move and `last-update` remains `T0`. The new principal is recorded scaled by the unchanged `index`.
3. At time `T2` (shortly after `T1`), anyone triggers `accrue` again (e.g., another borrow/repay/deposit action). Now utilization is non-zero, so `rate > 0`, and `time-delta = T2 - last-update = T2 - T0` — spanning the entire idle period `T0→T1` plus the real elapsed time `T1→T2`.
4. The resulting `next-index` compounds interest over the full `T0→T2` interval and is applied to `principal-scaled`, which includes the borrower's position opened at `T1`. The borrower is charged interest for the `T0→T1` window during which they had no debt at all.
