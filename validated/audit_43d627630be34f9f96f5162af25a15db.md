### Title
Integer overflow in `Operator.execute` value accumulator bypasses the `msg.value` check and drains ETH held by the Operator - (File: contracts/Operator.sol)

### Summary
The external report (CVE-2022-28331) describes an integer overflow that defeats a bounds/size computation, allowing writes (sends) beyond what was provisioned. The closest Metronome analog is `Operator.execute`: it sums per-call `value` fields in an `unchecked` block and then validates `msg.value == _sumOfValues`. Because the accumulation can wrap modulo 2^256, an attacker can make the sum wrap back to equal `msg.value` while the individual calls forward strictly more ETH than was supplied, spending ETH already sitting in the Operator contract.

### Finding Description
In `Operator.execute`, each `Call` in the attacker-supplied array is dispatched with `_call.target.functionCallWithValue(_call.callData, _call.value)`. The guard that is supposed to ensure the caller paid for all forwarded ETH is a comparison against a wrapping sum:

```solidity
// contracts/Operator.sol:40-54
uint256 _sumOfValues;
for (uint256 i; i < _length; ) {
    _call = calls_[i];
    uint256 _value = _call.value;
    unchecked {
        _sumOfValues += _value;   // wraps mod 2^256
    }
    _returnData[i] = _call.target.functionCallWithValue(_call.callData, _value);
    unchecked { ++i; }
}
require(msg.value == _sumOfValues, "value-mismatch");
```

Since `_sumOfValues += _value` is unchecked, `sum(values) mod 2^256` is what is actually compared to `msg.value`. An attacker can choose values `v1, v2, …` such that `v1 + v2 + … = msg.value + 2^256`, so the check passes even though the total ETH forwarded by the calls vastly exceeds `msg.value`.

### Impact Explanation
The invariant "total ETH forwarded equals ETH supplied" is broken by the overflow. The transaction can only succeed if the Operator's balance (`B + msg.value`) covers the sum of forwarded values, so the practical exploit drains up to `B` wei of ETH that is already in the Operator contract — e.g., ETH force-fed via `selfdestruct`, ETH stuck from prior partial executions, or ETH mistakenly sent to the contract. An unprivileged EOA can extract that balance while supplying arbitrarily little `msg.value` (e.g., two calls each for `~2^255 + x` wrapping to `2x`). This is direct theft of ETH held by the contract, matching the "bounds check defeated by integer overflow" bug class.

### Likelihood Explanation
Reachability: `execute` is a public, payable, unauthenticated entry point callable by any EOA; the attacker controls the full `calls_` array including `value` fields, so the overflow inputs are fully attacker-chosen. Preconditions: the Operator must hold a nonzero ETH balance — the Operator is not designed to custody ETH, but nothing prevents ETH from being locked in it (selfdestruct force-feed, accidental transfers, leftovers). Exploitation cost is negligible once any balance exists. The `nonReentrant` guard and `setMsgSender` do not mitigate it.

### Recommendation
Remove the `unchecked` around `_sumOfValues += _value` (and ideally around the loop increment) so the accumulation reverts on overflow, or compute the sum in a checked manner and keep `require(msg.value == _sumOfValues)`. This makes the value-accounting invariant hold for all inputs.

### Proof of Concept
Foundry sketch:

```solidity
function test_executeValueOverflow() public {
    Operator operator = new Operator();
    // simulate ETH stuck/force-fed in the Operator
    vm.deal(address(operator), 4 ether);

    address attacker = address(0xA11CE);
    vm.deal(attacker, 2 ether);

    IOperator.Call[] memory calls = new IOperator.Call[](2);
    uint256 half = (type(uint256).max / 2) + 1; // 2^255, two of them wrap to 0
    // want sum == msg.value mod 2^256 -> values sum to 2^256 + msg.value
    calls[0] = IOperator.Call({target: attacker, value: half, callData: ""});
    calls[1] = IOperator.Call({target: attacker, value: half + 2 ether, callData: ""});
    // sum = 2^256 + 2 ether -> wraps to 2 ether == msg.value

    vm.prank(attacker);
    operator.execute{value: 2 ether}(calls); // reverts only if Operator balance < half; scale down to fit B

    // feasible variant: with B = 4 ether, use v1 = v2 = 2 ether + 2^255 each
    // sum mod 2^256 = 4 ether + ... ; tune so wrapped sum == msg.value and
    // sequential sends are covered by B + msg.value.
    assertGt(attacker.balance, 2 ether); // net ETH extracted from Operator
}
```

Concretely: with `B = 4 ether`, send `msg.value = 0` and two calls of `v = 2^255 + 2 ether` each — `2v mod 2^256 = 4 ether`... rather pick `v1 = 2^255`, `v2 = 2^255`, wrapped sum `0 == msg.value = 0`; each call forwards `2^255` wei which exceeds the balance, so it reverts — showing the cap is the Operator's balance, i.e., choose values summing to `2^256 + msg.value` with each `vi ≤ B + msg.value` when `B` is small but nonzero; the overflow still zeroes the required payment down to `msg.value ≤ B`. The check that fails silently is only the equality; the exploitable window is exactly the Operator's pre-existing balance.

Note: the impact is bounded by ETH present in the Operator contract at execution time; if the deployed Operator is guaranteed to always hold zero ETH, this degrades to a latent accounting bug rather than an actively drainable vulnerability. That precondition (a nonzero contract balance) is the one element that could not be fully verified against on-chain state from the repository alone.
