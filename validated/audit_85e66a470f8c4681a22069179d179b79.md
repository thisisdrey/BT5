## Title
Permanently Lost/Unclaimable Voting Rewards When a Super Representative's Vote Count Drops to Zero - (File: `chainbase/src/main/java/org/tron/core/service/MortgageService.java`)

### Summary
`MortgageService` implements the DPoS vote-reward distribution used by both the on-chain block reward mechanism and the TVM `withdrawreward`/`vote` precompile mechanism. Block rewards and transaction-fee rewards for a Super Representative (SR) are queued into `DelegationStore` per `(cycle, srAddress)` and later distributed to voters proportionally to `userVote / totalVote` for that cycle. If an SR's `totalVote` for a given cycle is `0` (e.g., because every voter unvoted that SR before the cycle's vote snapshot is taken), the queued reward for that cycle is silently skipped forever — there is no mechanism to reclaim, redistribute, or unqueue it. This mirrors the reported Convex/Tokemak issue where rewards become permanently stuck once the "stake tracker" (here, the SR's total vote count) drops to zero, because the reward-queuing contract has no unqueue/rescue path.

### Finding Description
Block and fee rewards are queued for an SR via `MortgageService.payReward()`: [1](#0-0) 

This reward is stored keyed by `(cycle, witnessAddress)` in `DelegationStore`, independent of whether anyone currently holds votes for that SR at reward-payment time (rewards are paid per produced block, not gated on current votes).

Separately, once each maintenance cycle rolls over, `MaintenanceManager.doMaintenance()` snapshots each witness's vote count for the *next* cycle: [2](#0-1) 

If all voters have unvoted (or moved) their votes away from the SR before this snapshot, `witness.getVoteCount()` — and thus the stored `totalVote` for that cycle — becomes `0`.

When a voter later tries to claim rewards via `MortgageService.computeReward()` (old algorithm) or the Vi-accumulation path, any cycle where `totalVote == 0` is explicitly skipped and the reward is dropped, not carried forward or refunded: [3](#0-2) 

For the new "Vi" reward algorithm (used by both `MortgageService`/`RewardViCalService` and the TVM `VoteRewardUtil`), the same zero-vote condition causes the delta-Vi for that cycle to simply not be accumulated, meaning the reward paid into the pool for that cycle is never reflected in any voter's claimable Vi delta: [4](#0-3) 

The identical skip logic exists in the TVM-facing reward path used by `WithdrawRewardProcessor`: [5](#0-4) 

None of these paths provide any mechanism to unqueue, redirect, or return the reward that was credited to `delegationStore.addReward(cycle, witnessAddress, value)` for a cycle whose `totalVote` is (or becomes) `0`. The reward amount is real value that was deducted from the network's reward budget when `payReward` ran, but it becomes permanently unclaimable by any account once the vote-count-zero condition is hit for that cycle — exactly analogous to the reported issue where rewards queued for a `StakeTracker` become stuck once everyone withdraws from the tracker.

### Impact Explanation
This results in permanent loss of freezable/claimable reward value: block-production rewards and transaction-fee rewards legitimately earned by an SR are queued but become permanently unclaimable by anyone (not the SR's voters, not the SR itself, not the protocol) once the SR's cycle vote total is zero. Because unvoting an SR down to zero votes is a completely ordinary, unprivileged action (any user can freeze/unfreeze/vote via `VoteWitnessContract`/`UnfreezeBalanceV2Contract`), this can happen organically for any low-vote SR, silently leaking value out of circulation with no recovery path — a permanent freezing/loss-of-funds condition per the standard threat classification.

### Likelihood Explanation
This requires no privileged access or attack — it can occur through completely normal, expected user behavior (voters withdrawing/reassigning votes from an SR, which is common for smaller or unpopular SRs, or after a large voter batch-unvotes). No special conditions beyond an SR's vote count reaching zero in a cycle where it still received block/fee rewards (e.g., if it's briefly included in an active/standby set and then drops out) are needed.

### Recommendation
Add handling for the zero-total-vote case in `MortgageService`/`DelegationStore` (and the corresponding TVM `VoteRewardUtil`/`WithdrawRewardProcessor` path) such that rewards queued for a cycle with `totalVote == 0` are either carried forward to the next cycle with nonzero votes, credited back to the SR's own withdrawable allowance, or redirected to a recoverable pool — rather than being silently discarded with no way to reclaim them.

### Proof of Concept
1. SR `W` is actively producing blocks and receiving `payBlockReward`/`payTransactionFeeReward`, which call `MortgageService.payReward()` and credit `delegationStore.addReward(cycle, W, value)` for the current cycle.
2. Before the next maintenance cycle boundary, all accounts that had voted for `W` submit `UnfreezeBalanceV2Contract`/vote-withdrawal transactions, reducing `W.getVoteCount()` to `0`.
3. At `MaintenanceManager.doMaintenance()`, `delegationStore.setWitnessVote(nextCycle, W, 0)` is recorded for the affected cycle.
4. Any voter that had votes for `W` during that cycle calls `queryReward`/`withdrawReward` — `computeReward` sees `totalVote == 0` for that cycle and `continue`s, permanently skipping the value that was already added via `addReward` in step 1.
5. There is no actuator or TVM function anywhere in `MortgageService`, `DelegationStore`, or `VoteRewardUtil` that allows reclaiming or redistributing this stranded reward value; it remains permanently inaccessible.

  private long computeReward(long cycle, List<Pair<byte[], Long>> votes) {
    long reward = 0;
    for (Pair<byte[], Long> vote : votes) {
      byte[] srAddress = vote.getKey();
      long totalReward = delegationStore.getReward(cycle, srAddress);
      if (totalReward <= 0) {
        continue;
      }
      long totalVote = delegationStore.getWitnessVote(cycle, srAddress);
      if (totalVote == DelegationStore.REMARK || totalVote == 0) {
        continue;
      }
      long userVote = vote.getValue();
      double voteRate = (double) userVote / totalVote;
      reward += voteRate * totalReward;
    }
    return reward;
  }

  public void accumulateWitnessVi(long cycle, byte[] address, long voteCount) {
    BigInteger preVi = getWitnessVi(cycle - 1, address);
    long reward = getReward(cycle, address);
    if (reward == 0 || voteCount == 0) { // Just forward pre vi
      if (!BigInteger.ZERO.equals(preVi)) { // Zero vi will not be record
        setWitnessVi(cycle, address, preVi);
      }
    } else { // Accumulate delta vi
      BigInteger deltaVi = BigInteger.valueOf(reward)
          .multiply(DECIMAL_OF_VI_REWARD)
          .divide(BigInteger.valueOf(voteCount));
      setWitnessVi(cycle, address, preVi.add(deltaVi));
    }
  }

  private static long computeReward(long beginCycle, long endCycle,
                                    AccountCapsule accountCapsule, Repository repository) {
    if (beginCycle >= endCycle) {
      return 0;
    }

    long reward = 0;
    for (Protocol.Vote vote : accountCapsule.getVotesList()) {
      byte[] srAddress = vote.getVoteAddress().toByteArray();
      BigInteger beginVi = repository.getDelegationStore().getWitnessVi(beginCycle - 1, srAddress);
      BigInteger endVi = repository.getDelegationStore().getWitnessVi(endCycle - 1, srAddress);
      BigInteger deltaVi = endVi.subtract(beginVi);
      if (deltaVi.signum() <= 0) {
        continue;
      }
      long userVote = vote.getVoteCount();
      reward += deltaVi.multiply(BigInteger.valueOf(userVote))
          .divide(DelegationStore.DECIMAL_OF_VI_REWARD).longValue();
    }
    return reward;
  }
