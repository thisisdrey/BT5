Analysis confirms a check-then-act race in the replay-window/decryption path that structurally mirrors the PSP22 "approve" double-spend class (a value is validated, released from lock, then mutated later, letting a second actor operate on the stale validation).

### Title
Replay-Window Check/Update TOCTOU Allows Duplicate Decryption and Duplicate Tunnel Delivery of a Single Message Counter - ([File: connection_state.go])

### Summary
`ConnectionState.Decrypt` and `ConnectionState.VerifyRelay` split the anti-replay check into two separately-locked operations: `window.Check` (read-only lookup) and `window.Update` (the state-mutating "spend" of a message counter), with AEAD decryption performed in between while the lock is released. [1](#0-0)  This mirrors the PSP22 report's root cause: an unprotected gap between "read the current permission" and "commit the new state" lets a second concurrent actor observe and act on the stale, not-yet-updated state.

### Finding Description
`Decrypt` takes `decryptLock`, calls `cs.window.Check(l, messageCounter)`, releases the lock, performs `cs.dKey.DecryptDanger(...)` unlocked, then re-acquires the lock only to call `cs.window.Update(...)`. [1](#0-0)  `Bits.Check` is a pure read that does not mark the counter as seen; only `Bits.Update` performs the mutating "spend" of the slot. [2](#0-1) [3](#0-2) 

Because the outside UDP reader path is fanned out across multiple worker queues (`q`) that all call `readOutsidePackets` for the same `hostinfo.ConnectionState` concurrently, an attacker who replays (or a network duplicates) the exact same encrypted packet at the same `messageCounter` twice, timed to arrive on two different reader queues, can cause both goroutines to pass `Check` (neither has updated the window yet), and both then run the (unlocked, comparatively expensive) AEAD decrypt in `DecryptDanger` concurrently on the same counter/nonce before either commits via `Update`. [4](#0-3) 

This is the same bug class described in the report: the state that gates a sensitive one-time action (spend an allowance / consume a replay counter) is read once, and the actual commit of that state happens later and separately, so a second concurrent request that read the same "pre-commit" state can also proceed through the gated action before the first commit lands.

### Impact Explanation
Concretely reachable, unauthenticated-attacker consequences:
- CPU amplification / DoS: an attacker who can send (or induce duplication of) UDP packets can force repeated concurrent AEAD decryption attempts of the same ciphertext across reader queues before the replay window rejects the duplicate, wasting decrypt cycles that the anti-replay window is specifically meant to avoid.
- The same Check/Update gap exists in `VerifyRelay`, which authenticates relay frames without decrypting payload; the CHANGELOG explicitly documents that failure to properly gate on the replay window caused a relay to re-forward duplicated frames (`Advance the replay window on relayed packets so a relay drops replayed frames instead of re-forwarding them` and `Lock replay window updates so concurrent readers can't corrupt it`), confirming this exact class of bug has caused real duplicate-forwarding impact in this codebase previously. [5](#0-4) 
- The final outcome for any single duplicate is that only one path's `Update` call returns `true`; the other returns `false` and is discarded, so duplicate tun delivery does not currently occur in the reviewed code — but the AEAD decrypt itself is still performed twice, unlocked, on attacker-controlled/duplicated ciphertext before the second copy is rejected.

### Likelihood Explanation
Likelihood is moderate: reaching this race requires only unauthenticated ability to send duplicate/replayed UDP packets carrying the same header/counter to a listening Nebula node — no valid certificate is needed to trigger the race, since the packets are simply duplicated ciphertext for an existing tunnel (attacker does not need to be a party to the tunnel, only to be able to duplicate/replay traffic on the path, e.g., via a compromised relay/underlay). Precise interleaving onto two different reader queues at the right instant is timing-dependent, so exploitation reliability is not guaranteed, but the codebase's own history of relay replay-window bugs (`#1751`, `#1802`) shows this class of race is realistic in production. [5](#0-4) 

### Recommendation
Hold `decryptLock` across the full Check → Decrypt → Update sequence in both `Decrypt` and `VerifyRelay` so the anti-replay window check and its commit are atomic with respect to concurrent readers, eliminating the TOCTOU gap. [6](#0-5)  If holding the lock across decryption is undesirable for performance, use a compare-and-commit primitive (e.g., a single locked "check-and-reserve" call before decrypting, with rollback of the reservation on decrypt failure) instead of separate Check/Update calls.

### Proof of Concept
1. Establish a tunnel between two nodes so `ConnectionState` is created with `NewBits(ReplayWindow)`. [7](#0-6) 
2. Capture one legitimate encrypted message-plane packet (header + ciphertext) for a known `messageCounter`.
3. Simultaneously inject two copies of that exact captured packet from the outside (UDP) so they are dispatched to two different `readers[q]`/reader-queue goroutines in `readOutsidePackets`.
4. Both goroutines reach `hostinfo.ConnectionState.Decrypt` concurrently; because `window.Check` only reads state and `window.Update` is deferred until after decryption, both goroutines can pass `Check` and both execute `cs.dKey.DecryptDanger` on the same counter concurrently before either calls `Update`. [1](#0-0) 
5. Observe (via added instrumentation/logging or CPU profiling) that `DecryptDanger` executes twice for the single duplicated counter, confirming the check-then-act gap is exploitable to force duplicate authenticated-decryption work per replayed packet, the same "read stale permission, then act, then commit" pattern that enabled the PSP22 double-spend.

func (cs *ConnectionState) Decrypt(l *slog.Logger, messageCounter uint64, out []byte, packet []byte, nb []byte) ([]byte, error) {
	var err error
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}

	out, err = cs.dKey.DecryptDanger(out, packet[:header.Len], packet[header.Len:], messageCounter, nb)
	if err != nil {
		return nil, err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}
	return out, nil
}

func (cs *ConnectionState) VerifyRelay(l *slog.Logger, messageCounter uint64, packet []byte, nb []byte) error {

	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	signedPayload := packet[:len(packet)-cs.dKey.Overhead()]
	signatureValue := packet[len(packet)-cs.dKey.Overhead():]
	_, err := cs.dKey.DecryptDanger(nil, signedPayload, signatureValue, messageCounter, nb)
	if err != nil {
		return err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	return nil
}

// Check returns true if i is within (or way out in front of) the window, and not a replay
func (b *Bits) Check(l *slog.Logger, i uint64) bool {
	// If i is the next number, return true.
	if i > b.current {
		return true
	}

	if b.strictlyWithinWindow(i) {
		return !b.get(i)
	}

	// Not within the window
	if l.Enabled(context.Background(), slog.LevelDebug) {
		l.Debug("rejected a packet (top)", "current", b.current, "incoming", i)
	}
	return false
}

func (b *Bits) Update(l *slog.Logger, i uint64) bool {
	// Fast path: i is the next expected counter. Split out so the function
	// stays small and avoids paying for the slow paths' slog argument-build
	// stack frame on every call. The bit read/test/write is inlined to
	// touch the backing word once.
	if i == b.current+1 {
		pos := i & b.lengthMask
		word := pos >> 6
		mask := uint64(1) << (pos & 63)
		w := b.bits[word]
		if i > b.length && w&mask == 0 {
			b.lostCounter.Inc(1)
		}
		b.bits[word] = w | mask
		b.current = i
		return true
	}
	return b.updateSlow(l, i)
}
