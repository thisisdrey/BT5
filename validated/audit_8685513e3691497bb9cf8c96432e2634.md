### Title
Stale postponed ActionReceipt survives `DeleteAccount` and re-executes with original actor privilege after account re-creation - (File: core/store/src/utils/mod.rs)

### Summary
`remove_account` (used by `action_delete_account`) deletes `Account`, `ContractCode`, `AccessKey`, and `ContractData` trie entries for a deleted account, but leaves any `TrieKey::PostponedReceiptId`, `TrieKey::PendingDataCount`, and `TrieKey::PostponedReceipt` entries keyed by that same `receiver_id` untouched. Since account ids are just strings (no per-incarnation nonce), an account can be deleted while a self-directed postponed callback is still pending, then be recreated at the exact same id (trivially via a deterministic account's reproducible id), and the stale postponed receipt will later execute against the new account, passing the `actor_id == account_id` ownership check because that check only compares account-id strings.

### Finding Description
An attacker (an ordinary account with a deployed contract) creates a self-callback: a `FunctionCall` promise from account `A` to itself with `input_data_ids` pointing at a `data_id` that only `A`'s own logic will resolve later (e.g. via `promise_then`/manual `PromiseResult`). This receipt has `predecessor_id == receiver_id == A`. Because the required `DataReceipt` has not arrived, `process_action_receipt` stores it as postponed: `TrieKey::PostponedReceiptId{receiver_id:A,...}`, `TrieKey::PendingDataCount{receiver_id:A,...}`, and `TrieKey::PostponedReceipt{receiver_id:A,...}` [8](#0-7) .

Before the pending data arrives, the same account (still `actor_id==account_id`, satisfying `check_actor_permissions`) issues `DeleteAccount` on itself. `action_delete_account` calls `remove_account`, which iterates and removes `Account`, `ContractCode`, `AccessKey`/gas keys, and `ContractData`, but never enumerates or removes `PostponedReceiptId`/`PendingDataCount`/`PostponedReceipt` rows [3](#0-2) .

Because account `A` is a deterministic account (`0s...` id derived from `keccak256(borsh(code, data))`), the attacker can resubmit an identical `DeterministicStateInitAction` to recreate `A` at the exact same account id — this is explicitly supported ("lazy initialization"/idempotent re-init) [9](#0-8) . `create_deterministic_account`/`action_deterministic_state_init` then produce a fresh `Account`/contract/data at the same id, but do not touch or clear the stale `PostponedReceipt*` rows since these were never part of the deterministic account state model [10](#0-9) .

Finally, when the originally-pending `DataReceipt` (still deliverable, receiver_id = `A`) arrives, `process_receipt` finds the matching `PostponedReceiptId`, decrements `PendingDataCount` to 0, fetches the still-present `PostponedReceipt`, and executes it via `apply_action_receipt` against the newly recreated account [7](#0-6) . Inside `apply_action_receipt`, `actor_id` is initialized purely from `receipt.predecessor_id()` — the original stale value, which equals `A` — with zero linkage to the account's creation/deletion generation [11](#0-10) . `check_actor_permissions` only compares `actor_id != account_id` as strings for privileged actions like `DeployContract`/`AddKey`/`Stake`/`DeleteKey` [2](#0-1) , so the stale receipt's privileged actions execute successfully against the brand-new account state, without any access key or authorization check tied to the new incarnation.

Existing checks that fail to catch this: signature/nonce checks are irrelevant (this is receipt-internal, not a signed transaction); access-key checks are bypassed entirely because `check_actor_permissions` for self-actions doesn't consult access keys at all — it only requires `predecessor_id == receiver_id`, a property preserved by construction since the account is calling itself; storage-staking and size-limit checks are orthogonal and do not inspect leftover postponed-receipt state.

### Impact Explanation
This is an authorization escalation across account re-creations (matching "authorization escalation across accounts or promises" in the bounty categories). A stale receipt, originally authorized under the old incarnation's contract logic/state, can mutate the brand-new account's state (e.g. `DeployContract` to backdoor the fresh contract, `AddKey` to plant a full-access key the new "owner" never approved, `Stake`, `DeleteKey`) without any signature or access key from whoever controls the new account instance. Because the affected accounts here are `0s...` deterministic accounts whose entire identity/authorization model is meant to be exactly "fully defined by its initial state," smuggling privileged mutations into the freshly (re-)initialized account undermines that invariant directly.

### Likelihood Explanation
Preconditions are all within reach of an unprivileged attacker: deploy an ordinary/global contract, create a deterministic account with that code via `DeterministicStateInitAction`, have the contract issue a self-targeted promise with an unresolved `input_data_ids` dependency, then call `DeleteAccount` on itself before resolving it, and later resubmit the same `DeterministicStateInitAction` and deliver the pending data. All steps are ordinary transactions/receipts a normal signer can submit; no validator, node-operator, or leaked-key access is required. The attack is fully repeatable and deterministic (same code+data hash → same account id every time), and costs only ordinary gas/storage-staking fees.

### Recommendation
`remove_account` (or `action_delete_account`) should also enumerate and remove any `TrieKey::PostponedReceiptId`, `TrieKey::PendingDataCount`, and `TrieKey::PostponedReceipt` entries keyed by the account being deleted before returning, mirroring the existing enumeration used for access keys and contract data. Alternatively/additionally, `DeleteAccount` could be disallowed (return an `ActionError`) while any postponed receipt still targets `account_id`, ensuring an account cannot be torn down with pending self-callbacks outstanding.

### Proof of Concept

        }
        .into());
        return Ok(());
    }

            StorageError::StorageInconsistentState("compute_usage overflow".to_string())
        })?;
    }
    *actor_id = receipt.predecessor_id().clone();
    *account = None;
    Ok(())
}

pub fn remove_account(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
) -> Result<RemoveAccountResult, StorageError> {
    state_update.remove(TrieKey::Account { account_id: account_id.clone() });
    state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });

    let mut gas_key_nonce_count: usize = 0;
    let mut gas_key_nonce_total_key_bytes: usize = 0;

    // Removing access keys and gas key nonces
    let lock = state_update.trie().lock_for_iter();
    let mut keys_to_remove: Vec<TrieKey> = Vec::new();
    for raw_key in state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_access_keys(account_id), &lock)?
    {
        let raw_key = raw_key?;
        let key_handle = trie_key_parsers::parse_key_handle_from_access_key_key(
            &raw_key, account_id,
        )
        .map_err(|_e| {
            StorageError::StorageInconsistentState(
                "Can't parse key handle from raw key for AccessKey".to_string(),
            )
        })?;
        let nonce_index =
            trie_key_parsers::parse_nonce_index_from_gas_key_key(&raw_key, account_id, &key_handle)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse nonce index from raw key for AccessKey".to_string(),
                    )
                })?;
        if let Some(index) = nonce_index {
            gas_key_nonce_count += 1;
            gas_key_nonce_total_key_bytes += raw_key.len();
            keys_to_remove.push(TrieKey::gas_key_nonce(
                account_id.clone(),
                key_handle.clone(),
                index,
            ));
        } else {
            keys_to_remove.push(TrieKey::access_key(account_id.clone(), key_handle.clone()));
        }
    }
    drop(lock);

    for trie_key in keys_to_remove {
        state_update.remove(trie_key);
    }

    // Removing contract data
    let lock = state_update.trie().lock_for_iter();
    let data_keys = state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_contract_data(account_id, &[]), &lock)?
        .map(|raw_key| {
            trie_key_parsers::parse_data_key_from_contract_data_key(&raw_key?, account_id)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse data key from raw key for ContractData".to_string(),
                    )
                })
                .map(Vec::from)
        })
        .collect::<Result<Vec<_>, _>>()?;
    drop(lock);

    for key in data_keys {
        state_update.remove(TrieKey::ContractData { account_id: account_id.clone(), key });
    }
    Ok(RemoveAccountResult { gas_key_nonce_count, gas_key_nonce_total_key_bytes })
}

pub(crate) fn action_deterministic_state_init(
    state_update: &mut TrieUpdate,
    apply_state: &ApplyState,
    maybe_account: &mut Option<Account>,
    account_id: &AccountId,
    receipt: &Receipt,
    action: &DeterministicStateInitAction,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    // See https://github.com/near/NEPs/blob/master/neps/nep-0616.md#account-state
    // for the detailed description around deterministic account state.
    let storage_usage_config = &apply_state.config.fees.storage_usage_config;
    let account = match maybe_account {
        Some(account) => account,
        None => {
            // cspell:ignore nonexist
            // `nonexist` -> `uninit` account state transition
            // Create with zero balance now and check later how much of the
            // provided deposit is needed.
            let new_account = create_deterministic_account(Balance::ZERO, storage_usage_config);
            maybe_account.insert(new_account)
        }
    };
    if account.contract().is_none() {
        // `uninit` -> `active` account state transition. "uninit" here is the
        // NEP-616 sense, a deterministic account with no contract yet, not
        // `Account::Uninitialized`: a `0u` id can never reach this, because
        // `validate_deterministic_state_init` pins the receiver to the derived
        // `0s` id.
        deploy_deterministic_account(
            state_update,
            account,
            account_id,
            &action.state_init,
            result,
            storage_usage_config,
        )?;
    }
    if result.result.is_err() {
        return Ok(());
    }

    // Use attached deposit to satisfy storage staking requirements and refund
    // the rest.
    let deposit_refund = match check_storage_stake(account, account.amount(), &apply_state.config) {
        Ok(_) => {
            // no additional storage needed, refunding all
            action.deposit
        }
        Err(StorageStakingError::LackBalanceForStorageStaking(missing_amount)) => {
            if missing_amount <= action.deposit {
                // use exactly as much as needed and refund the rest
                let new_balance = safe_add_balance(account.amount(), missing_amount)?;
                account.set_amount(new_balance);
                action
                    .deposit
                    .checked_sub(missing_amount)
                    .expect("just checked missing_amount <= action.deposit")
            } else {
                result.result = Err(ActionErrorKind::LackBalanceForState {
                    account_id: account_id.clone(),
                    amount: missing_amount,
                }
                .into());
                return Ok(());
            }
        }
        Err(StorageStakingError::StorageError(err)) => {
            return Err(RuntimeError::StorageError(StorageError::StorageInconsistentState(err)));
        }
    };

    if deposit_refund > Balance::ZERO {
        result
            .new_receipts
            .push(Receipt::new_balance_refund(receipt.balance_refund_receiver(), deposit_refund));
    }

    Ok(())
}

pub(crate) fn create_deterministic_account(
    initial_balance: Balance,
    storage_usage_config: &StorageUsageConfig,
) -> Account {
    // Unlike `CreateAccount`, this account creation does not change
    // actor_id. This is important to prevent hijacking the account.
    // Actor id remains the predecessor, so any actions following will
    // be checked against that for actor permissions, preventing
    // `AddKey`, `DeployContract`, or any other actions that only the
    // account owner is permitted to do.
    Account::new(
        initial_balance,
        Balance::ZERO,
        AccountContract::None,
        storage_usage_config.num_bytes_account,
    )
}
