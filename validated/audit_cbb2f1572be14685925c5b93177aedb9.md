### Title
Unvalidated shielded-transaction field lengths passed directly to native librustzcash JNA buffers - ([File: chainbase/src/main/java/org/tron/common/zksnark/JLibrustzcash.java])

### Summary
`validate()` in `ShieldedTransferActuator` (an actuator reachable from any broadcast `ShieldedTransferContract`) never checks the byte-lengths of `SpendDescription`/`ReceiveDescription` protobuf fields (`value_commitment`, `anchor`, `nullifier`, `rk`, `zkproof`, `spend_authority_signature`, `epk`, etc.) before forwarding them to native code, and `JLibrustzcash` itself performs no length validation for the verification path.

### Finding Description
`ShieldedTransferActuator.checkProof()` builds `CheckSpendParams`/`CheckOutputParams`/`FinalCheckParams` directly from `spendDescription.getValueCommitment().toByteArray()`, `getAnchor().toByteArray()`, `getNullifier().toByteArray()`, `getRk().toByteArray()`, `getZkproof().toByteArray()`, `getSpendAuthoritySignature().toByteArray()` with no size checks: [1](#0-0) 

Only the `ReceiveDescription` ciphertext fields are length-checked (`ZC_ENCCIPHERTEXT_SIZE`/`ZC_OUTCIPHERTEXT_SIZE`); `value_commitment`, `note_commitment`, `epk`, and `zkproof` are not: [2](#0-1) 

These arrays flow into `JLibrustzcash.librustzcashSaplingCheckSpend`, `librustzcashSaplingCheckOutput`, and `librustzcashSaplingFinalCheck`, which pass the raw `byte[]` straight to the JNA-bound native `INSTANCE` calls with **no call to `LibrustzcashParam.valid32Params`/`validParamLength`**, unlike sibling methods in the same class (e.g. `librustzcashAskToAk`, `librustzcashToScalar`, `librustzcashTreeUncommitted`, which explicitly validate fixed lengths before invoking native code): [3](#0-2) [4](#0-3) 

Because protobuf `bytes` fields default to an empty `ByteString` when unset, an attacker can craft a `ShieldedTransferContract` transaction whose `SpendDescription`/`ReceiveDescription` messages omit fields such as `value_commitment`, `anchor`, `rk`, or `zkproof`. `toByteArray()` then yields a zero-length Java array, which JNA marshals to a native pointer that the underlying Rust `librustzcash` FFI functions expect to be exactly 32/192/64 bytes. This is the direct analog of the reported openssl `MemBio::get_buf` bug: a native/FFI boundary receiving an "empty buffer" where a fixed-size, non-empty buffer is assumed, producing undefined behavior (out-of-bounds read/native crash) rather than a clean Java-level bounds exception — because the unsafe memory access happens inside the native library, not the JVM.

### Impact Explanation
If the native `librustzcash` routines dereference/read past a zero-length buffer, the result is native-code undefined behavior inside the java-tron process — most plausibly a segmentation fault / JVM crash, which is a node crash/halt reachable by any account that can broadcast a `ShieldedTransferContract` transaction. A crash triggered by a single validated-at-actuator-time transaction could be replayed against multiple witness/full nodes, threatening availability of the network (denial of service), which matches the "node crash or halt" acceptance criterion.

### Likelihood Explanation
`ShieldedTransferContract` is a standard broadcastable contract type once shielded transactions are enabled by the committee (`dynamicStore.supportShieldedTransaction()`), reachable by any unprivileged transaction broadcaster. Constructing a transaction with an omitted/empty `bytes` sub-field in `SpendDescription`/`ReceiveDescription` requires no special privileges — it is just protobuf serialization, and the existing test suite (`PrecompiledContractsVerifyProofTest`, `SendCoinShieldTest`) shows these fields are routinely manipulated by test code, illustrating the ease of constructing malformed messages. However, I could not directly inspect the native `librustzcash`/JNA implementation code (outside this repository index) to confirm empirically whether the native side actually dereferences a null/zero-length pointer versus gracefully failing; this is inferred from the missing Java-side validation and the pattern established by sibling methods that do validate.

### Recommendation
Add explicit length validation (mirroring `LibrustzcashParam.valid32Params`/`validParamLength` used elsewhere in `JLibrustzcash`) for every buffer passed into `librustzcashSaplingCheckSpend`, `librustzcashSaplingCheckOutput`, and `librustzcashSaplingFinalCheck`, and add corresponding size checks in `ShieldedTransferActuator.checkProof()` for `value_commitment` (32 bytes), `anchor` (32 bytes), `nullifier` (32 bytes), `rk` (32 bytes), `zkproof` (192 bytes), `spend_authority_signature`/`binding_signature` (64 bytes), and `epk`/`note_commitment` (32 bytes) before any native call, rejecting the transaction with `ContractValidateException`/`ZkProofValidateException` instead of forwarding unchecked buffers to native code.

### Proof of Concept
1. Craft a `ShieldedTransferContract` transaction with one `SpendDescription` where `value_commitment`, `anchor`, `rk`, or `zkproof` fields are left unset (empty `ByteString`), while `nullifier` is set to a fresh, valid-looking 32-byte value to pass the earlier duplicate/nullifier checks in `validate()`.
2. Broadcast the transaction to a full node with shielded transactions enabled.
3. `validate()` reaches `checkProof()`, which calls `JLibrustzcash.librustzcashSaplingCheckSpend` with a zero-length array for the omitted field(s).
4. Because `JLibrustzcash` performs no length validation on this path, the empty array is passed to the native JNA binding, which the underlying Rust code expects to be a fixed-size non-null buffer — potentially causing a native crash of the java-tron process.
