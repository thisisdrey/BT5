### Title
StackerDB chunk signature does not bind to the target contract, enabling cross-StackerDB signature replay - (File: `libstackerdb/src/libstackerdb.rs`)

### Summary
`SlotMetadata::auth_digest` — the message that is actually signed and verified for every StackerDB chunk write — commits only to `slot_id`, `slot_version`, and `data_hash`. It never includes the StackerDB's `QualifiedContractIdentifier` (or any other replica-scoping value, e.g. reward-cycle/network id). This is the same class of bug as the reported `LibTokenPermit::_buildDomainSeparator` issue: a signature is missing a domain-separating field, so a signature that is valid in one context (one StackerDB contract) is also valid, byte-for-byte, in any other context (a different StackerDB contract) where the same signer address happens to own the same `slot_id`.

### Finding Description
`SlotMetadata::auth_digest` builds the digest as: [1](#0-0) 

only over `slot_id`, `slot_version`, and `data_hash`. `sign`/`verify` operate purely on this digest and recover/compare a public key hash against the caller-supplied address: [2](#0-1) 

The contract identity is never part of what is signed. Enforcement of "is this signer allowed to write this slot" is delegated entirely to the caller looking up `get_slot_signer(smart_contract_id, slot_id)` and calling `verify(&addr)` against the returned address — see the P2P push-chunk validation path: [3](#0-2) 

and the HTTP write path, which stores the chunk via `try_replace_chunk` keyed only on `contract_identifier` + `slot_metadata` (itself derived only from `slot_id/slot_version/data_hash/sig`): [4](#0-3) 

Because the signed bytes never mention *which* StackerDB contract the write is for, if the same signer address is configured as the owner of the same `slot_id` in two different StackerDB replicas (this is common: signer sets are re-derived from the same signer keys across different `.signers-<cycle>-<set>` boot contracts each reward cycle, and any third-party StackerDB app can also assign that address to any slot), a chunk `(slot_id, slot_version, data, sig)` legitimately observed on the wire for contract A is a byte-for-byte valid, independently-verifiable write for contract B, as long as B's current slot version/max-writes checks are satisfied. Any remote, unauthenticated peer who has observed a broadcast/gossiped chunk can replay it into the other contract via the ordinary write paths (`POST /v2/stackerdb/:addr/:contract/chunks` or the P2P `StackerDBPushChunk` unsolicited-message handler), without possessing the signer's private key. This mirrors the missing-`block.chainid` bug exactly: the fix in the analog report is to add the omitted domain value into the signed digest; here the omitted value is the StackerDB contract identifier (and/or reward cycle/network id).

### Impact Explanation
This allows an unauthenticated remote actor to write attacker-selected, previously-observed chunk data into a *different* StackerDB replica than the one it was actually authorized for, without holding any private key — an unauthorized write to state via forged/replayed authorization, which falls under the "Critical" bucket (unauthenticated/unauthorized write to state or StackerDB, network-wide propagation of forged data) defined in scope.

### Likelihood Explanation
Likelihood is moderate-to-high in practice: signer StackerDB contracts are re-created every reward cycle from the same signer key set, so the same address frequently owns the same `slot_id` across successive `.signers-N-M` contracts, and third-party StackerDB-based apps can independently assign arbitrary addresses to arbitrary slots, increasing the chance of an address/slot_id collision that an attacker can exploit purely by observing gossiped chunk traffic (chunks are broadcast in plaintext over the P2P network and served over the public read API).

### Recommendation
Include the `QualifiedContractIdentifier` (and ideally a network/chain discriminator) as part of the digest computed in `SlotMetadata::auth_digest`, so that a chunk signature is cryptographically bound to the specific StackerDB replica it was authorized for:
```rust
fn auth_digest(&self, contract_id: &QualifiedContractIdentifier) -> Sha512Trunc256Sum {
    let mut hasher = Sha512_256::new();
    hasher.update(contract_id.serialize()); // domain separation
    hasher.update(self.slot_id.to_be_bytes());
    hasher.update(self.slot_version.to_be_bytes());
    hasher.update(self.data_hash.0);
    Sha512Trunc256Sum::from_hasher(hasher)
}
```
This requires threading the contract id through `sign`/`verify`/`recover_pk` call sites in `libstackerdb`, `stackslib/src/net/stackerdb/mod.rs`, and `stackslib/src/net/api/poststackerdbchunk.rs`.

### Proof of Concept
1. Node hosts two StackerDB contracts, A (`ST....signers-1-1`) and B (`ST....signers-2-1`), both configuring signer address `X` as the owner of `slot_id = 0` (a realistic scenario since signer sets persist keys across cycles).
2. Legit signer `X` signs and pushes chunk `(slot_id=0, slot_version=1, data=D)` to contract A via `StackerDBChunkData::sign` — this signature only commits to `(0, 1, hash(D))`, per `auth_digest`.
3. An unauthenticated observer captures this chunk (e.g., from the P2P `StackerDBPushChunk` broadcast or the public GET chunk endpoint).
4. The observer re-submits the identical `StackerDBChunkData { slot_id: 0, slot_version: 1, sig, data: D }` to contract B, either via `POST /v2/stackerdb/<B-addr>/<B-contract>/chunks` or via the P2P push-chunk handler.
5. `validate_received_chunk`/`try_replace_chunk` for contract B calls `get_slot_signer(B, 0)` → returns `X`, then `slot_metadata.verify(&X)` succeeds because the digest never encoded which contract it was for — the write is accepted as if `X` had authorized it for B, even though `X` never signed anything referencing contract B.     fn auth_digest(&self) -> Sha512Trunc256Sum {
        let mut hasher = Sha512_256::new();
        hasher.update(self.slot_id.to_be_bytes());
        hasher.update(self.slot_version.to_be_bytes());
        hasher.update(self.data_hash.0);
        Sha512Trunc256Sum::from_hasher(hasher)
    }

    /// Sign this slot metadata, committing to slot_id, slot_version, and
    /// data_hash.  Sets self.signature to the signature.
    /// Fails if the underlying crypto library fails
    pub fn sign(&mut self, privkey: &StacksPrivateKey) -> Result<(), Error> {
        let auth_digest = self.auth_digest();
        let sig = privkey
            .sign(&auth_digest.0)
            .map_err(|se| Error::SigningError(se.to_string()))?;

        self.signature = sig;
        Ok(())
    }

    /// Verify that a given principal signed this chunk metadata.
    /// Note that the address version is ignored.
    pub fn verify(&self, principal: &StacksAddress) -> Result<bool, Error> {
        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )
        .map_err(|ve| Error::VerifyingError(ve.to_string()))?;

        let pubkh = Hash160::from_node_public_key(&pubk);
        Ok(pubkh == *principal.bytes())
    }
