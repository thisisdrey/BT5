### Title
Unchecked `Math.pow` overflow-to-Infinity in `ExchangeProcessor` lets a broadcaster drain or brick a TRX/TRC10 Exchange pool - ([File: chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java])

### Summary
The Bancor-style bonding-curve math used by TRON's asset `Exchange` (analogous to Trident's `IndexPool`) computes `Math.pow` on a ratio derived directly from attacker-supplied trade quantities and casts the (possibly `Infinity`/`NaN`) result straight to a `long`, without any bound checking, exactly like the reported `weightRatio` pow-overflow issue in `IndexPool`.

### Finding Description
`ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply` compute `Maths.pow(1.0 + quant/newBalance, exponent, useStrictMath)` and immediately cast the double result to `long`: [1](#0-0) 

`Math.pow`/`StrictMath.pow` never throw on overflow — they silently return `Double.POSITIVE_INFINITY`, and Java's narrowing cast `(long) Double.POSITIVE_INFINITY` silently yields `Long.MAX_VALUE` (and `(long) NaN` yields `0`), with no exception raised anywhere in this call chain. This is the same class of bug as the reported issue: an exponentiation whose result can blow past representable range is used to compute a swap output without any sanity bound, exactly as `weightRatio` did in `IndexPool.sol`.

This code path is reached directly from unprivileged, broadcastable transactions: `ExchangeTransactionActuator.execute`/`doValidate` call `exchangeCapsule.transaction(...)` which selects the `ExchangeProcessor` (non-hardened) unless the chain-wide proposal `allowHardenExchangeCalculation` is enabled: [2](#0-1) 

Whether hardening applies is gated by `allowHarden()`, a dynamic-parameter proposal flag, not a compile-time constant — meaning the vulnerable non-hardened path is the default/legacy behavior for any exchange pair whose transactions are processed before/without that proposal being active: [3](#0-2) 

In the non-hardened branch, once `buyTokenQuant` is corrupted to `Long.MAX_VALUE` (from the `Infinity` cast) or some other absurd value, `newSecondTokenBalance = secondTokenBalance - buyTokenQuant` is computed with plain long arithmetic (silent wraparound, no `subtractExact`), so the exchange's on-chain balances become corrupted (wrap to a large positive number or go deeply negative-then-wrap) rather than raising an error: [4](#0-3) 

The comparably named `SafeExchangeProcessor` fixes overflow of the *balance bookkeeping* with `addExact`/`subtractExact`, but it does not bound the `pow` base/ratio itself — it only guards against overflow of `long+long`, not against `Math.pow` returning `Infinity` for a base ratio close to/above 1 raised to exponent `2000.0`: [5](#0-4) 

### Impact Explanation
An attacker who can submit an `ExchangeTransactionContract` (or `ExchangeInjectContract`/`ExchangeWithdrawContract`, which share the same balance-difference math) against a pool whose reserves are small enough relative to the trade quantity can drive the `quant`/`newBalance` ratio, or the `supplyQuant`/`supply` ratio in `exchangeFromSupply`, to a magnitude where `Math.pow(base, 2000.0)` returns `Infinity`. The subsequent cast to `long` and use in plain (non-`Exact`) arithmetic corrupts the pool's `firstTokenBalance`/`secondTokenBalance` fields stored in `ExchangeCapsule`/`ExchangeV2Store`. This can be used to mint an unbacked, oversized `anotherTokenQuant` credited to the attacker's account (`accountCapsule.addAssetAmountV2`/`setBalance`) — i.e., theft of unbacked funds — or to corrupt the pool into a permanently unusable/frozen state (subsequent trades reverting via balance-limit checks), matching the "High" severity of the original finding (pool no longer usable, requiring redeployment/manual repair).

### Likelihood Explanation
Reachable from a single signed transaction broadcast by any account holding the traded asset (TRX or TRC10 token) and does not require special privileges — only that `allowHardenExchangeCalculation` is not enabled for the network/pool in question, which is the historical/legacy default. Because `Exchange` pools are user/asset-issuer created with arbitrary starting balances (`ExchangeCreateActuator`), an attacker fully controls the reserve ratio to engineer the overflow condition.

### Recommendation
Bound the base/exponent inputs to `Math.pow` before use (reject or clamp when the computed ratio would make `pow` exceed a safe magnitude, e.g. check `Double.isInfinite`/`Double.isNaN` and throw `ContractValidateException`/`ArithmeticException` instead of silently casting), and ensure this validation runs unconditionally (not just under the `allowHardenExchangeCalculation` proposal) for both `exchangeToSupply` and `exchangeFromSupply` in `ExchangeProcessor`, mirroring the already-existing overflow checks in `SafeExchangeProcessor` but extended to guard the `pow` step itself, not just the surrounding integer arithmetic.

### Proof of Concept
1. Create an `Exchange` pool via `ExchangeCreateActuator` with a highly asymmetric ratio (e.g., token A balance ~1, token B balance ~10^18), while `allowHardenExchangeCalculation` proposal is inactive (default).
2. Submit `ExchangeTransactionContract` selling nearly the entire balance of one side, driving `quant/newBalance` (in `exchangeToSupply`) or `supplyQuant/supply` (in `exchangeFromSupply`) close to/above 1.
3. `Maths.pow(base, 2000.0, false)` in `ExchangeProcessor.exchangeFromSupply` (chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java:31-39) returns `Double.POSITIVE_INFINITY`; the cast `(long) exchangeBalance` yields `Long.MAX_VALUE`, which is returned as `buyTokenQuant` and used to update the pool's balances and credit the attacker's account in `ExchangeTransactionActuator.execute` (actuator/src/main/java/org/tron/core/actuator/ExchangeTransactionActuator.java:68-91), corrupting or draining the pool.

  private BigDecimal exchangeToSupply(long balance, long quant) {
    long newBalance = StrictMathWrapper.addExact(balance, quant);
    BigDecimal bdQuant = BigDecimal.valueOf(quant);
    BigDecimal bdNewBalance = BigDecimal.valueOf(newBalance);
    BigDecimal base = BigDecimal.ONE.add(
        bdQuant.divide(bdNewBalance, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 0.0005);
    return SUPPLY.negate().multiply(
        BigDecimal.ONE.subtract(BigDecimal.valueOf(powResult))).setScale(0, RoundingMode.DOWN);
  }

  private long exchangeFromSupply(long balance, BigDecimal supplyQuant) {
    BigDecimal bdBalance = BigDecimal.valueOf(balance);
    BigDecimal base = BigDecimal.ONE.add(
        supplyQuant.divide(SUPPLY, 18, RoundingMode.HALF_UP));

    BigDecimal exchangeBalance = bdBalance.multiply(
        BigDecimal.valueOf(powResult).subtract(BigDecimal.ONE));
