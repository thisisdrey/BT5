Audit Report

## Title
`unstake`/`harvest_rewards` in `pallet-asset-rewards` can be permanently DoS'd when `reward_per_token` overflows `T::Balance`, freezing staked assets and rewards with no recovery path - ([File: substrate/frame/asset-rewards/src/lib.rs])

## Summary
`reward_per_token` in `substrate/frame/asset-rewards/src/lib.rs` computes `reward_per_token_stored + reward_rate_per_block * blocks_elapsed * PRECISION_SCALING_FACTOR / total_tokens_staked` using checked (`ensure_*`) arithmetic that returns `Error::Overflow` instead of saturating or wrapping. Since every mutating extrinsic (`stake`, `unstake`, `harvest_rewards`) must call `update_pool_and_staker_rewards` → `reward_per_token` before touching any pool state, once the accumulator `reward_per_token_stored` grows large enough that a subsequent computation overflows `T::Balance`, the pool becomes permanently unusable and staked funds plus unclaimed rewards are locked with no unprivileged or privileged recovery mechanism in the pallet.

## Finding Description
`reward_per_token` is confirmed in the repository exactly as cited: [1](#0-0)  It performs `pool_info.reward_per_token_stored.ensure_add(reward_rate_per_block.ensure_mul(blocks_elapsed).ensure_mul(PRECISION_SCALING_FACTOR).ensure_div(total_tokens_staked))`, propagating `Error::Overflow` on failure rather than degrading gracefully.

This is invoked unconditionally from `update_pool_and_staker_rewards`, the pure helper that the pallet's own module docs state all mutating call handlers route through: [2](#0-1)  and its sibling `update_pool_rewards` persists whatever `reward_per_token_stored` value succeeded on the last successful call: [3](#0-2) 

`reward_per_token_stored` is monotonically non-decreasing (each successful call only adds a non-negative increment), and the divisor `total_tokens_staked` shrinks as stakers `unstake`, which increases the per-block increment over time for a fixed `reward_rate_per_block`. `PRECISION_SCALING_FACTOR` is confirmed as `4096`: [4](#0-3)  — smaller than Synthetix/Aura's typical `1e18` scaling, meaning the numerator inflation margin before overflow is smaller for equivalent-magnitude balances, exactly as the claim states.

I searched the file for any escape-hatch equivalent to an `AuraLocker::shutdown()`/`emergencyWithdraw()` function (`shutdown`, `emergency`, `withdraw`) and found no such recovery mechanism in `substrate/frame/asset-rewards/src/lib.rs`. The module doc confirms `update_pool_and_staker_rewards`/`update_pool_rewards` are deliberately pure/side-effect-free helper functions with no alternate reset path: [5](#0-4)  Since `stake`, `unstake`, and `harvest_rewards` all call `update_pool_and_staker_rewards` before any storage mutation, an `Err(Error::Overflow)` there aborts the entire extrinsic, including the parts that would otherwise unfreeze the staker's principal via `AssetsFreezer`.

The pool configuration parameters (`staked_asset_id`, `reward_rate_per_block`) that determine whether this overflow is reachable are chosen by `CreatePoolOrigin` at pool creation and can be further raised by the pool `admin`, as documented: [6](#0-5)  However, the actual trigger condition (a small `total_tokens_staked` combined with elapsed blocks) arises from ordinary staker behavior (unstaking, or simply not staking much), not from admin malice — an admin merely sets plausible-looking parameters for a low-decimal asset, and normal supply/stake fluctuation over time crosses the overflow threshold.

## Impact Explanation
This is a permanent user-fund lock: once triggered, `unstake` and `harvest_rewards` fail deterministically for every staker in the affected pool because both call sites are gated by the now-permanently-failing `reward_per_token` computation. Staked principal remains frozen (via `AssetsFreezer`) and any pending reward-asset balance becomes unclaimable, with no pallet-level (privileged or unprivileged) function to bypass the reward accounting and let stakers exit. This falls under the in-scope "permanent user-fund or bridge-state lock" impact category, since the corrupted/stuck value is `PoolInfo::reward_per_token_stored` (and by extension every staker's frozen `amount` and `rewards` in `PoolStakerInfo`) which can never again be advanced or bypassed.

## Likelihood Explanation
The root cause is a genuine arithmetic/design bug in the checked-overflow reward computation, not privileged admin abuse — the admin's role is limited to picking ordinary-looking pool parameters (a low-decimal staking asset, a nontrivial `reward_rate_per_block`), and the actual trigger (small `total_tokens_staked` after organic unstaking, plus elapsed blocks) is driven by normal, unprivileged user activity. This is a foreseeable interaction rather than an adversarial admin action, and is repeatable/deterministic once the threshold is crossed, satisfying the requirement for a reachable exploit path from ordinary operation to a permanent bad state.

## Recommendation
- Compute the `reward_per_token` numerator using a widened intermediate type (e.g., `U256`/`u128`) before dividing back down to `T::Balance`, analogous to the `BalanceToU256`/`U256ToBalance` pattern used elsewhere in the SDK (e.g. `nomination-pools`), so that overflow of `T::Balance` during the multiplication step does not brick the pool.
- Add an administrative or permissionless recovery path that allows stakers to withdraw staked principal (and settle rewards at a last-good checkpoint) even if the JIT reward computation would overflow.
- Consider bounding `reward_rate_per_block` relative to `total_tokens_staked` at pool-parameter-change time to make this overflow class unreachable by construction.

## Proof of Concept
1. `CreatePoolOrigin` creates a pool with a low-decimal `staked_asset_id`, a normal 18-decimal `reward_asset_id`, and a `reward_rate_per_block` sized such that `reward_rate_per_block * 4096` is large relative to expected `total_tokens_staked`.
2. A staker calls `stake` with a small amount, keeping `total_tokens_staked` small.
3. Blocks elapse (or additional stakers `unstake`, further shrinking `total_tokens_staked`). On the next call to `stake`/`unstake`/`harvest_rewards`, `reward_per_token` (`substrate/frame/asset-rewards/src/lib.rs:786-810`) computes an increment that, added to the already-persisted `reward_per_token_stored`, exceeds `T::Balance::MAX`, returning `Err(Error::Overflow)`.
4. From this point on, every staker's `unstake`/`harvest_rewards` call for this pool fails identically and permanently, since there is no recovery extrinsic in the pallet, permanently freezing staked assets and unclaimed rewards.

		/// Derives the current reward per token for this pool.
		pub(super) fn reward_per_token(
			pool_info: &PoolInfoFor<T>,
		) -> Result<T::Balance, DispatchError> {
			if pool_info.total_tokens_staked.is_zero() {
				return Ok(pool_info.reward_per_token_stored);
			}

			let rewardable_blocks_elapsed: u32 =
				match Self::last_block_reward_applicable(pool_info.expiry_block)
					.ensure_sub(pool_info.last_update_block)?
					.try_into()
				{
					Ok(b) => b,
					Err(_) => return Err(Error::<T>::BlockNumberConversionError.into()),
				};

			Ok(pool_info.reward_per_token_stored.ensure_add(
				pool_info
					.reward_rate_per_block
					.ensure_mul(rewardable_blocks_elapsed.into())?
					.ensure_mul(PRECISION_SCALING_FACTOR.into())?
					.ensure_div(pool_info.total_tokens_staked)?,
			)?)
		}
