### Title
Client-supplied `git_object_directory`/`git_alternate_object_directories` are joined into git object-search env vars without confinement checks in `ExecCommandFactory.newCommand` - (File: internal/git/gitcmd/command_factory.go)

### Summary
The report's root cause is structurally identical to a class the rules explicitly ask to keep: an unvalidated, attacker-influenceable "address"/path is trusted and fed into privileged logic that expands the actor's read/write scope. In Gitaly, `gitalypb.Repository.GitObjectDirectory` / `GitAlternateObjectDirectories` are ordinary client-settable proto fields [1](#0-0) , and `ExecCommandFactory.newCommand` builds `GIT_OBJECT_DIRECTORY`/`GIT_ALTERNATE_OBJECT_DIRECTORIES` for every git invocation directly via `alternates.Env(repoPath, repo.GetGitObjectDirectory(), repo.GetGitAlternateObjectDirectories())` [2](#0-1) , where `alternates.Env` simply does `filepath.Join(repoPath, objectDirectory)` with no root/quarantine confinement check at all [3](#0-2) .

### Finding Description
By contrast, other code paths that consume these same fields do apply confinement checks: `Repo.ObjectDirectoryPath` validates the resulting path is inside the storage root or matches the expected transaction-quarantine prefix [4](#0-3) , and the transaction middleware `beginTransactionForRepository` treats any request with `GitObjectDirectory`/`GitAlternateObjectDirectories` set as a "quarantine" request, rejecting it outright for mutator RPCs (`ErrQuarantineConfiguredOnMutator`) and requiring a snapshot relative-path header for accessor RPCs [5](#0-4) .

However, `ExecCommandFactory.newCommand` — the actual function that constructs the environment for every `git` subprocess Gitaly spawns — bypasses both of these safeguards. It calls `alternates.Env()` directly with the raw, client-controlled field values and only joins them against `repoPath`; it does not call `ValidateRelativePath`, does not check for the quarantine directory prefix, and is not gated behind the "is this a Rails access-check loop-back" invariant that the middleware assumes. This mirrors exactly the stNXM pattern: a value that should only ever be produced internally (the pool address / the quarantine directory) is instead accepted verbatim from an external actor and trusted deep inside privileged logic (fee/reward accounting / git object resolution) without revalidating it at the point of use.

### Impact Explanation
If any RPC path reaches `newCommand` with a `Repository` message whose `GitObjectDirectory`/`GitAlternateObjectDirectories` were set by, or derived without re-validation from, client-supplied data (e.g., an accessor RPC that isn't covered by the mutator-only middleware guard, or an internal call site that forwards a repository message before the middleware's confinement/rewrite logic runs), a crafted relative path such as `../../other-repo/objects` would let `git` search for and expose objects belonging to another repository outside the caller's own storage scope — a cross-repository object disclosure / storage confinement bypass, directly analogous to the arbitrary "pool address" being trusted to determine reward flow in the stNXM bug.

### Likelihood Explanation
Middleware-level protection (`ErrQuarantineConfiguredOnMutator`, snapshot-relative-path requirement) reduces exposure for RPCs that pass through `beginTransactionForRepository`, and accessor RPCs are explicitly allowed to carry these fields (intended for Rails access-check loop-back), which is exactly the scenario the middleware comment acknowledges is only "left unaddressed for now." Because `alternates.Env`/`newCommand` themselves perform no independent bounds check, likelihood is directly tied to whether every code path that reaches `newCommand` with a non-nil `GitObjectDirectory`/`GitAlternateObjectDirectories` has already been fully re-validated upstream — a systemic reliance on caller discipline rather than defense-in-depth at the enforcement point, matching the audit's "root cause: owner can pass any address without validation" pattern.

### Recommendation
Move the confinement check that already exists in `Repo.ObjectDirectoryPath` (root/quarantine-prefix validation) into `alternates.Env` or `ExecCommandFactory.newCommand` itself, so that every consumer of `GetGitObjectDirectory()`/`GetGitAlternateObjectDirectories()` is forced through the same validation regardless of call path, rather than relying on each RPC handler or middleware layer to have independently guarded against unrelated/escaping paths.

### Proof of Concept
Not executed against a live server; based on static code-path analysis of `internal/git/gitcmd/command_factory.go`, `internal/git/alternates/alternates.go`, and `internal/gitaly/storage/storagemgr/middleware.go`. A concrete PoC would require confirming a specific accessor RPC that (a) accepts a `Repository` message with attacker-controlled `GitObjectDirectory`, (b) reaches `newCommand` without first passing through `ObjectDirectoryPath`'s validation, and (c) is reachable by an unprivileged/ordinary caller (e.g. via Rails-loopback style access-check requests) — this last point could not be fully confirmed within available context and should be validated with a live instrumented test.

// Env returns the alternate object directory environment variables.
func Env(repoPath, objectDirectory string, alternateObjectDirectories []string) []string {
	var env []string
	if objectDirectory != "" {
		env = append(env, fmt.Sprintf("GIT_OBJECT_DIRECTORY=%s", filepath.Join(repoPath, objectDirectory)))
	}

	if len(alternateObjectDirectories) > 0 {
		var dirsList []string

		for _, dir := range alternateObjectDirectories {
			dirsList = append(dirsList, filepath.Join(repoPath, dir))
		}

		env = append(env, fmt.Sprintf("GIT_ALTERNATE_OBJECT_DIRECTORIES=%s", strings.Join(dirsList, ":")))
	}

	return env
}
