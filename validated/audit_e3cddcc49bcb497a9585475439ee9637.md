### Title
Relayer fee is paid unconditionally in `inner_rlp_execute`, independent of whether the emulated action actually succeeds - (File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs)

### Summary
The eth-implicit Wallet Contract pays a relayer "gas compensation" fee via a standalone `Promise` that is dispatched *before*, and *independently of*, the promise chain that performs the user's actual intended action (an emulated ERC-20 transfer or base-token transfer). Because the fee-payment promise is never chained (`.then`) to the outcome of the main action, the relayer is compensated even when the user's underlying action later fails, causing the wallet owner to pay for a service that was never delivered — a direct analog of paying/crediting a counterparty without checking the return/success of the corresponding transfer.

### Finding Description
In `inner_rlp_execute`, after `parse_rlp_tx_to_action` successfully decodes an Ethereum RLP transaction into a Near action and a `TransactionKind`, the code unconditionally schedules the relayer fee transfer as a brand-new, independent promise batch: [1](#0-0) 

```rust
if let TransactionKind::EthEmulation(EthEmulationKind::EOABaseTokenTransfer { fee, .. })
| TransactionKind::EthEmulation(EthEmulationKind::ERC20Transfer { fee, .. }) = &transaction_kind
{
    if !fee.is_zero() && context.predecessor_account_id != context.current_account_id {
        let refund_promise = env::promise_batch_create(&context.predecessor_account_id);
        env::promise_batch_action_transfer(refund_promise, *fee);
    }
}
```

`env::promise_batch_create` creates a *new, unrelated* receipt/promise; it is never linked with `.then()`/`.and()` to the promise chain constructed later in the same function that actually performs the user's requested action (the ERC-20 `ft_transfer` via `nep_141_storage_balance_callback` → `rlp_execute_callback`, or the plain `Transfer`/`FunctionCall` action via `action_to_promise`): [2](#0-1) 

Both the relayer-fee promise and the main-action promise chain are dispatched from the same function call, so both are executed as sibling receipts regardless of each other's outcome. If the main action fails downstream — e.g. `ft_transfer` fails because the wallet's token balance is insufficient, the token contract panics, `storage_deposit` fails, or any other cross-contract-call failure captured by `rlp_execute_callback`'s `PromiseResult::Failed` branch — the fee-payment receipt to the relayer has already succeeded independently and is not rolled back: [3](#0-2) 

Note that `rlp_execute_callback` only refunds the *deposit* (`caller_deposit`) attached by the calling relayer transaction on failure — it has no mechanism to claw back the relayer fee that was already transferred out of the wallet's own balance. Additionally, the nonce is already incremented at parse time (line 364), so this failed attempt permanently consumes the wallet's nonce and cannot be "retried" to recover the lost fee.

### Impact Explanation
This causes the wallet owner (the eth-implicit account holder) to permanently lose the fee amount in $NEAR whenever the emulated action they signed later fails for any reason unrelated to the fee itself (e.g., insufficient NEP-141 token balance at execution time, a paused/reverting token contract, or any transient failure in the multi-hop `storage_balance_of` → `storage_deposit` → `ft_transfer` chain). The relayer is paid regardless of whether it actually delivered the requested service (moving the user's tokens/near), directly mirroring the original bug class: compensating a counterparty without verifying that the corresponding transfer succeeded, resulting in permanent loss of funds for the account that trusted the accounting.

### Likelihood Explanation
Any relayer (honest or otherwise) submitting a validly-signed RLP transaction that carries a non-zero fee will trigger this path whenever the underlying emulated ERC-20/base-token action subsequently fails — a scenario that is not unusual (e.g., balance changes between signing and relaying, receiver storage registration issues, or third-party token contract behavior). No special privilege is needed by the caller beyond being a normal relayer of a user-signed transaction, and the loss occurs automatically as part of standard contract logic, not through malicious code tampering.

### Recommendation
Chain the relayer fee-payment promise to the outcome of the main action instead of dispatching it as an independent promise. For example, only issue the fee transfer from within `rlp_execute_callback` (or an equivalent callback) after observing `PromiseResult::Successful` for the main action, or attach the fee transfer as an additional action on the same promise/receipt as the main action's execution so both succeed or fail atomically.

### Proof of Concept
1. Wallet owner Alice's eth-implicit wallet contract holds enough $NEAR to cover a relayer fee but has insufficient `tokenA` (NEP-141) balance for the transfer she intends to authorize.
2. Alice signs an RLP-encoded Ethereum transaction encoding an ERC-20 `transfer(bob, 100)` call on `tokenA`, with `max_fee_per_gas * gas_limit` set to compensate the relayer (`tx_fee`), per `internal::parse_rlp_tx_to_action`. [4](#0-3) 
3. A relayer calls `rlp_execute(target=tokenA, tx_bytes_b64=...)`. Parsing succeeds, so the nonce is incremented and the fee-payment promise to the relayer is scheduled immediately.
4. The main promise chain performs `storage_balance_of`, then attempts `ft_transfer(bob, 100)` on `tokenA`; this call fails because Alice's wallet balance of `tokenA` is less than 100.
5. `rlp_execute_callback` observes `PromiseResult::Failed`, refunds only the relayer's attached NEAR deposit (`caller_deposit`), and returns `success: false`.
6. Independently, the earlier fee-payment receipt to the relayer's account has already completed successfully — the relayer keeps the fee even though Alice's tokens were never transferred, and Alice's nonce has already been consumed, permanently losing the fee for a failed transaction.

                    .trim()
                    .parse()
                    .unwrap_or_else(|_| env::panic_str("Invalid address registrar"));
                ext_registrar::ext(account_id).with_static_gas(REGISTRAR_LOOKUP_GAS)
            };
            let address = format!("0x{}", hex::encode(address));
            address_registrar.lookup(address).then(ext.address_check_callback(
                target,
                action,
                caller_deposit,

        }
        TransactionKind::EthEmulation(EthEmulationKind::ERC20Transfer { receiver_id, .. }) => {
            // In the case of the emulated ERC-20 transfer, the receiving account
            // might not be registered with the NEP-141 contract (per the NEP-145)
            // storage standard. Therefore we must create a multi-step promise where
            // first we check if the receiver is registered and then if not call
            // `storage_deposit` in addition to `ft_transfer`.
            let token_id = target;
            let callback_gas = NEP_141_STORAGE_BALANCE_CALLBACK_GAS.saturating_add(action.gas());
            let ext: WalletContractExt =
                WalletContract::ext(current_account_id).with_static_gas(callback_gas);
            let storage_balance_args =
                format!(r#"{{"account_id": "{}"}}"#, receiver_id.as_str()).into_bytes();
            Promise::new(token_id.clone())
                .function_call(
                    "storage_balance_of".into(),
                    storage_balance_args,
                    NearToken::from_yoctonear(0),
                    NEP_141_STORAGE_BALANCE_OF_GAS,
                )
                .then(ext.nep_141_storage_balance_callback(
                    token_id,
                    receiver_id,
                    action,
                    caller_deposit,
                ))
        }
        TransactionKind::EthEmulation(EthEmulationKind::SelfBaseTokenTransfer) => {
            // Base token transfers to self are no-ops on Near, so we do not need to
            // schedule an additional call. We can simply go straight to `rlp_execute_callback`.
            let ext: WalletContractExt =
                WalletContract::ext(current_account_id).with_static_gas(RLP_EXECUTE_CALLBACK_GAS);
            ext.rlp_execute_callback(caller_deposit)
        }
        _ => {
            let ext =
                WalletContract::ext(current_account_id).with_static_gas(RLP_EXECUTE_CALLBACK_GAS);
            action_to_promise(target, action)?.then(ext.rlp_execute_callback(caller_deposit))
