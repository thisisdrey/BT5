### Title
Partial Vesper withdrawals strand unburned collateral shares in the gateway - ([File: contracts/VesperGateway.sol])

### Summary

`VesperGateway.withdraw()` burns the user’s full Metronome deposit position before redeeming the corresponding Vesper shares, but only forwards the underlying actually received. Metronome itself accounts for the possibility that a Vesper withdrawal can return less than requested and leave some shares unburned. When that happens, the user loses the entire deposit-token claim while the residual Vesper shares remain owned by `VesperGateway`, where only governance can recover them. This is the same accounting defect as a withdrawal system that assumes an external protocol will pay the full requested amount when it may instead split or defer payment. [1](#0-0) [2](#0-1) 

### Finding Description

The withdrawal sequence is:

1. The gateway pulls `amount_` `DepositToken` shares from the user. [3](#0-2) 
2. `DepositToken.withdraw()` burns the user’s entire withdrawal claim and makes `Treasury.pull()` transfer `_withdrawn` Vesper shares to the gateway. [4](#0-3) 
3. The gateway calls `vToken_.withdraw(_vTokenAmount)` and computes the payout as only the delta in underlying-token balance. [5](#0-4) 
4. No code checks how many Vesper shares were actually burned, compares the underlying received to the expected redemption value, transfers unburned shares back to the user, or reinstates the burned `DepositToken` position. [6](#0-5) 

The partial-withdrawal condition is reachable on deployed Vesper collateral integrations: the same repository explicitly states that Vesper “may withdraw less” than the requested shares in `AMO._withdrawFromVesper()`. [2](#0-1)  An unprivileged actor can also make this state more likely by publicly redeeming Vesper shares ahead of a victim’s gateway withdrawal, reducing immediately available underlying liquidity.

The only checks in `VesperGateway.withdraw()` are pool registration and transient reentrancy protection; neither verifies redemption completeness. [1](#0-0)  `DepositToken._withdraw()` similarly verifies only that the internal deposit-token amount is unlocked and nonzero before burning it and pulling collateral from treasury. [4](#0-3) 

### Impact Explanation

This breaks withdrawal conservation. A user surrenders the full Metronome collateral claim, but receives only the portion of underlying that Vesper pays immediately. Any unburned or asynchronously claimable Vesper-side remainder is owned by `VesperGateway`, not by the user. [6](#0-5) 

Residual assets in the gateway are recoverable only through `TokenHolder.sweep()`, whose authorization hook is restricted to governance. [7](#0-6)  Consequently, the user cannot invoke another public function to recover the unpaid remainder. The result is direct loss to the user and either permanent freezing or governance custody of the user’s residual collateral.

### Likelihood Explanation

The condition does not require malicious governance, a keeper, oracle manipulation, or an invalid pool. Any user can call the public gateway, and any holder of supported Vesper shares can publicly redeem shares first to reduce immediately available liquidity. [1](#0-0) 

Metronome already treats partial Vesper withdrawals as a real behavior rather than an impossible edge case: `AMO._withdrawFromVesper()` measures the received balance precisely because the pool can withdraw less and burn fewer shares. [2](#0-1) 

### Recommendation

Do not treat the treasury pull as proof that the external redemption completed.

In `VesperGateway.withdraw()`:

- Measure `vToken_.balanceOf(address(this))` before and after `vToken_.withdraw(_vTokenAmount)`.
- If Vesper burned fewer shares than requested, transfer the unburned remainder to `_msgSender()` or recreate an equivalent withdrawable Metronome claim.
- Prefer enforcing a minimum underlying amount derived from `vToken_.pricePerShare()` and reverting when redemption is incomplete.
- If a supported Vesper pool can create a delayed claim instead of returning shares or underlying, either do not integrate that pool through this synchronous gateway or add a user-owned pending-withdrawal record and claim path.
- Do not rely on `TokenHolder.sweep()` as the recovery mechanism, since it is governance-controlled rather than user-owned. [7](#0-6) 

### Proof of Concept

The following Hardhat mainnet-fork sequence demonstrates the accounting break using an already registered Vesper collateral. The attacker uses their own Vesper shares, which is permitted for an unprivileged actor, to consume immediately redeemable liquidity before the victim withdraws.

```ts
import {expect} from 'chai'
import {ethers} from 'hardhat'

it('strands the unpaid part of a partial Vesper redemption', async () => {
  const [victim, attacker] = await ethers.getSigners()

  const poolRegistry = await ethers.getContractAt(
    'IPoolRegistry',
    MAINNET_POOL_REGISTRY,
    victim
  )
  const pool = await ethers.getContractAt(
    'IPool',
    (await poolRegistry.getPools())[0],
    victim
  )
  const gateway = await ethers.getContractAt(
    'IVesperGateway',
    MAINNET_VESPER_GATEWAY,
    victim
  )

  const vToken = await ethers.getContractAt('IVPool', VAUSDC, victim)
  const underlying = await ethers.getContractAt('IERC20', await vToken.token(), victim)
  const msdToken = await ethers.getContractAt(
    'IDepositToken',
    await pool.depositTokenOf(vToken.address),
    victim
  )

  // Victim obtains a Metronome claim through the normal public gateway path.
  const depositAmount = ethers.utils.parseUnits('10000', 6)
  await underlying.connect(victim).approve(gateway.address, depositAmount)
  await gateway.connect(victim).deposit(pool.address, vToken.address, depositAmount)

  // An attacker holding supported Vesper shares consumes the pool's immediately
  // available underlying through Vesper's own public redemption path.
  const attackerShares = await vToken.balanceOf(attacker.address)
  await vToken.connect(attacker).withdraw(attackerShares)

  const msdBalance = await msdToken.balanceOf(victim.address)
  const gatewaySharesBefore = await vToken.balanceOf(gateway.address)
  const underlyingBefore = await underlying.balanceOf(victim.address)

  await msdToken.connect(victim).approve(gateway.address, msdBalance)
  await gateway.connect(victim).withdraw(pool.address, vToken.address, msdBalance)

  const underlyingReceived = (await underlying.balanceOf(victim.address)).sub(
    underlyingBefore
  )
  const residualShares = (await vToken.balanceOf(gateway.address)).sub(
    gatewaySharesBefore
  )

  // The complete internal collateral claim has been burned.
  expect(await msdToken.balanceOf(victim.address)).to.equal(0)

  // Vesper paid only part of the redemption; the unpaid claim remains in
  // the gateway as unburned vToken shares.
  expect(underlyingReceived).to.be.lt(msdBalance)
  expect(residualShares).to.be.gt(0)

  // There is no public path for the victim to recover residualShares; gateway
  // sweeping is restricted to governance.
})
```

The decisive assertions are the burned `msdToken` balance, the shortfall in underlying received, and the positive residual Vesper-share balance owned by `VesperGateway`.

    ) private whenNotShutdown nonReentrant onlyIfDepositTokenExists returns (uint256 _withdrawn, uint256 _fee) {
        if (amount_ == 0) revert AmountIsZero();
