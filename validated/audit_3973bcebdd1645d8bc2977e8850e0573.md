### Title
Out-of-bounds read parsing ZIP64 extra fields in ijar central directory entries - (File: third_party/ijar/zip.cc)

### Summary
`InputZipFile::ProcessCentralDirEntry` reads each ZIP central-directory entry from an attacker-supplied `.jar`/`.zip` archive (e.g. a third-party dependency archive fetched via `http_archive`/`http_jar` and processed by the `ijar` tool that strips jars down to their public interface). Unlike other parsing paths in the same file, this function never validates that `extra_field_length` (and the individual extra-field `data_size` values nested inside it) actually stay within the bytes that were reserved for the extra field, or even within the mapped file at all.

### Finding Description
`ProcessCentralDirEntry` reads `extra_field_length` directly off the wire with no upper bound check against the file's mapped length, then walks a list of sub "extra field" records: [1](#0-0) 

The loop condition `while (extra_p != p)` assumes `data_size` values always divide the interval `[extra_p, p)` evenly. If an attacker crafts a ZIP64 extra field whose declared `data_size` is larger than the remaining bytes of the extra-field area (analogous to the GSS-NTLMSSP `av_pair` length not being checked against the remaining buffer), `extra_p` overshoots `p`. The loop's equality check `extra_p != p` never becomes false again, so the loop continues walking past the end of the extra-field region — and, because there is no `EnsureRemaining()`-style bound check as used elsewhere in this same file (e.g. `SkipFile`, `ProcessFile`, `ProcessNext` at line 316), it can walk past the end of the memory-mapped input file entirely. Each iteration calls `get_u2le`/`get_u8le` on `extra_p`, dereferencing attacker-influenced offsets. When `header_id == ZIP64_EXTRA_FIELD_TAG`, `get_u8le(extra)` reads 8 bytes from `extra`, which itself can point past the extra-field boundary because `data_size` was never validated before being trusted.

This is a direct structural analog of the GSS-NTLMSSP bug: a length field taken from untrusted, structured binary data (the `av_pair`/ZIP64 extra field size) is used to compute a read offset/size without checking it against the bounds of the buffer it is supposed to live in, leading to an out-of-bounds read when the entry is walked.

By contrast, the local-file-header path in the same file (`ProcessLocalFileEntry`) and the sibling implementation in `src/tools/singlejar/zip_headers.h`'s `ExtraField::find` both explicitly bound-check the extra field length before dereferencing: [2](#0-1) [3](#0-2) 

`ProcessCentralDirEntry` has no equivalent check, so central-directory extra-field parsing is the outlier.

### Impact Explanation
An attacker who controls the bytes of an archive that Bazel/ijar processes (e.g. a malicious or compromised jar served from a build's dependency URL, third-party maven repository mirror, or any other archive fed to the `ijar` tool) can craft a central directory entry whose ZIP64 extra field declares an oversized `data_size`. This causes `ijar` to read memory beyond the bounds of the memory-mapped input file. Depending on memory layout this can crash the build (denial of service via SIGSEGV on unmapped memory) or leak adjacent process memory contents into the interface jar's derived metadata (sizes/offsets), which is a confidentiality-relevant out-of-bounds read matching the "no size checks, OOB read via main entry point" pattern of the underlying CVE.

### Likelihood Explanation
Any build that consumes a third-party jar via `ijar`-processing (used pervasively for Java `java_import`/interface jars in Bazel Java rules) is on this code path. The archive's central directory is fully attacker-controlled content when the archive originates from an untrusted URL, and no checksum verification protects the *internal parsing* of an archive whose overall sha256 hasn't been declared or is otherwise satisfied (or where integrity checking is not configured for the specific artifact). No credentials, sandbox escape, or root-repo Starlark execution is required — simply supplying bytes that `ijar` will parse.

### Recommendation
Add the same bounds validation used elsewhere in the file: before entering the extra-field loop, verify `extra_field_length` does not exceed the space remaining before the file/central-directory boundary, and inside the loop verify that reading `header_id`/`data_size` (4 bytes) and then `data_size` more bytes does not advance `extra_p` past `p`, erroring out instead of continuing. Additionally, before dereferencing `extra` with `get_u8le`, confirm at least 8 bytes remain within the declared extra-field payload (mirroring `ExtraField::find`'s pattern of checking `byte_ptr(start) + extra_field->size() > byte_ptr(end)` in `src/tools/singlejar/zip_headers.h`).

### Proof of Concept
A `BuildIntegrationTestCase`/`src/test/shell/bazel` style reproduction:
1. Construct a minimal ZIP archive with one central directory entry.
2. Set `uncompressed_size`/`compressed_size` fields to `0xFFFFFFFF` (forcing zip64 lookup) and `extra_field_length` to a small value (e.g. 4), but embed a ZIP64 extra field header (`tag=0x0001`) with `data_size` set to a large value (e.g. `0xFFF0`) that exceeds the declared `extra_field_length` and the remaining bytes in the mapped file.
3. Run `ijar` (or the Bazel action that invokes it, e.g. building against a `java_import` with this crafted jar) against this archive.
4. Observe a crash (SIGSEGV) or an out-of-bounds read reported by ASan when `get_u8le(extra)` dereferences memory beyond the mapped file, analogous to the existing regression test `CreateZipWithMalformedExtraField` in `src/tools/singlejar/output_jar_simple_test.cc` (lines 1179–1225), which demonstrates the same malformed-extra-field pattern already guarded against in the singlejar variant but not in `third_party/ijar/zip.cc`.
