### Title
Unbounded `refs` array in `DeleteRefsRequest` allows a single RPC call to force multi-pass, unlimited CPU/memory processing and repository-lock contention - (File: internal/gitaly/service/ref/delete_refs.go)

### Summary
The Sherlock report describes a class of bug where a user-controlled array with no cardinality limit is committed and later iterated over inside on-chain loops (`_withdraw`), so a legitimate/expected operation (`withdraw`, `liquidateCollateral`) can never complete because a single transaction runs out of gas. The Gitaly analog of "one unbounded array turned into repeated per-item work inside a single call" is `RefService.DeleteRefs`: the `refs` repeated field of `DeleteRefsRequest` has no length limit, and the handler walks that array multiple times synchronously inside one RPC invocation while holding repository state, mirroring the "single call, unbounded loop, resource ceiling" shape of the reported issue.

### Finding Description
`DeleteRefs` is a unary RPC (not chunked/streamed like `UpdateReferences`, which batches updates across multiple stream messages). `validateDeleteRefRequest` only checks that `Refs` is non-empty when `ExceptWithPrefix` is empty; it never bounds `len(req.GetRefs())`: [1](#0-0) 

The handler then performs **three full passes** over the entire unbounded array within the same RPC call/goroutine, each doing per-element work:
1. Building `refnames` from `req.GetRefs()`: [2](#0-1) 
2. Validating every reference name: [3](#0-2) 
3. Queuing a `Delete()` per ref and updating an in-memory vote hash per ref, before `Prepare()`/`Commit()`/voting can even begin: [4](#0-3) 

There is no chunking, streaming, or per-request cap analogous to what `UpdateReferences` at least structurally allows via multiple `Recv()` calls: [5](#0-4) 

Because `DeleteRefs` is unary, the entire `refs` list must arrive (and be processed) in one gRPC message and one synchronous call, all before the `updateref.Updater` transaction (`Start`/`Prepare`/`Commit`) and transaction voting (`voting.Preparing`/`Prepared`/`Committed`) even complete: [6](#0-5) 

This is structurally the same defect class as the Sherlock M-13 report: an externally-supplied array with no upper bound is committed to a single, indivisible unit of work (there, an on-chain transaction bound by gas; here, a single gRPC call/transaction bound by CPU time, memory, and the reference-transaction lock held on the repository for the call's duration).

### Impact Explanation
A caller that can invoke `DeleteRefs` (any client holding the standard Gitaly auth token, the same trust level as an ordinary `git push`/`git fetch` client through gitaly-shell) can submit a `DeleteRefsRequest` with an extremely large `refs` array (bounded only by gRPC's default max message size, which can still hold well over 100k short reference names). This forces the Gitaly server to:
- Allocate and iterate the full list three times synchronously,
- Hold the repository's reference-transaction lock for the duration of building/committing a giant `git-update-ref` transaction,
- Compute a vote hash over every reference,

all inside a single RPC call, with no opportunity to fail fast or shed load. This can starve the worker/goroutine handling the request, stall other operations on the same repository (which needs the same reference lock), and in aggregate degrade or deny service on that repository/node — the same "operation fails to ever complete because of unbounded per-item work in one atomic unit" impact pattern as the original report, translated from "gas limit" to "RPC handler resource/time limit."

### Likelihood Explanation
Likelihood is limited by two factors that keep this at most a moderate-severity finding rather than a critical one:
- `DeleteRefs` is a maintenance/administrative RPC typically invoked by GitLab Rails rather than being the direct, always-exercised path of a routine `git push`/`git fetch`, so the “ordinary user” framing is weaker than the original TellerV2 report (any borrower on a permissionless lending market could trigger `submitBid`).
- The attacker still needs a valid Gitaly-authenticated client capable of issuing a `DeleteRefsRequest`, and the array is capped by gRPC's max message size, so the achievable ref count, while large, is not unbounded in an absolute sense.

Nonetheless, no application-level limit exists at all on `refs`, so any caller in a position to invoke this RPC (or any component/proxy that forwards attacker-influenced batch-delete parameters, e.g., bulk branch/tag cleanup features) can trivially maximize the array to the gRPC message ceiling with no rejection or throttling.

### Recommendation
Add an explicit, enforced upper bound on `len(req.GetRefs())` (and `ExceptWithPrefix`) in `validateDeleteRefRequest`, returning `InvalidArgument` when exceeded, and/or convert `DeleteRefs` to a streaming/batched RPC (as `UpdateReferences` already is) so that large deletions are chunked across multiple messages/transactions instead of one unbounded synchronous unit of work. Consider adding a timeout/complexity guard around the validate/delete/vote-hash loops so a single call cannot indefinitely hold the reference-transaction lock.

### Proof of Concept
1. As an authenticated Gitaly client (same trust boundary as gitaly-shell), open `RefService.DeleteRefs`.
2. Send a single `DeleteRefsRequest` with `repository` set and `refs` populated with the maximum number of short, syntactically valid reference names that fit under the gRPC max message size (e.g., hundreds of thousands of `refs/heads/x<N>` entries, no two colliding).
3. Observe the server allocate three synchronous passes over the array (`refsToRemove`, revision-validation loop, delete/vote-hash loop) before ever calling `updater.Prepare()`; the repository's reference-transaction lock is held throughout, and CPU/memory are consumed proportionally to the array size with no cap in `validateDeleteRefRequest`.
4. Concurrent operations against the same repository requiring the reference lock (pushes, other ref operations) are blocked/delayed until this single oversized call finishes, demonstrating the DoS window; repeated submissions from the same caller can sustain the denial of service.

Note: I was unable to load `internal/git/updateref` internals (e.g., `Updater.Delete`/`Prepare`/`Commit` cost characteristics) from the index to quantify exact CPU/lock-hold cost per reference; a Devin session with full repository access would be needed to benchmark the precise resource cost per additional ref and confirm the practical DoS threshold.

func validateDeleteRefRequest(ctx context.Context, locator storage.Locator, req *gitalypb.DeleteRefsRequest) error {
	if err := locator.ValidateRepository(ctx, req.GetRepository()); err != nil {
		return err
	}

	if len(req.GetExceptWithPrefix()) > 0 && len(req.GetRefs()) > 0 {
		return errors.New("ExceptWithPrefix and Refs are mutually exclusive")
	}

	if len(req.GetExceptWithPrefix()) == 0 && len(req.GetRefs()) == 0 { // You can't delete all refs
		return errors.New("empty ExceptWithPrefix and Refs")
	}

	for _, prefix := range req.GetExceptWithPrefix() {
		if len(prefix) == 0 {
			return errors.New("empty prefix for exclusion")
		}
	}

	for _, ref := range req.GetRefs() {
		if len(ref) == 0 {
			return errors.New("empty ref")
		}
	}

	return nil
}
