### Title
Duplicate/legacy floating-point Bancor-relay math in `ExchangeProcessor` allows price-manipulation drain of TRC10 `Exchange` liquidity pools - (File: chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java)

### Summary
java-tron's native, unprivileged `Exchange*` contracts (`ExchangeCreateContract`, `ExchangeInjectContract`, `ExchangeWithdrawContract`, `ExchangeTransactionContract`) implement an on-chain Bancor-style AMM pool, analogous in role to the crvUSD/ETH Omnipool exploited in the referenced Conic Finance incident. The legacy pricing engine, `ExchangeProcessor`, computes the relay/output amount using **double-precision floating point** (`Maths.pow`) rather than exact decimal arithmetic [1](#0-0) . This path remains the **default** execution path in `ExchangeCapsule.transaction()` because it is only bypassed when the `allowHardenExchangeCalculation` dynamic parameter (governed by SR committee vote) is enabled — which the test suite shows defaults to `0` (disabled) [2](#0-1) [3](#0-2) .

### Finding Description
`ExchangeCapsule.transaction()` selects between the legacy `ExchangeProcessor` (double math) and the newer `SafeExchangeProcessor` (BigDecimal, exact rounding) based solely on the `hardenedCalc` flag, which is itself derived from a mutable, committee-controlled dynamic property (`allowHardenExchangeCalculation`) [4](#0-3) . Any unprivileged account can invoke `ExchangeTransactionContract` (via `ExchangeTransactionActuator`) to swap tokens against the pool; the received amount is computed by `exchangeCapsule.transaction(...)`, which — while hardening is disabled — routes through `ExchangeProcessor.exchange()` [5](#0-4) .

`ExchangeProcessor.exchangeToSupply` and `exchangeFromSupply` cast intermediate BigDecimal-equivalent computations to `double` and truncate to `long` (`(long) issuedSupply`, `(long) exchangeBalance`) [6](#0-5) . Because the "relay supply" (a running internal float-based state variable, `supply`) accumulates rounding error across repeated trades, and because `Maths.pow(base, exponent)` with `useStrictMath=false` may use platform-dependent `Math.pow` (non-strict, non-deterministic across JVMs/architectures) rather than `StrictMath`, an attacker who repeatedly executes small trades that shift the pool ratio (buy then sell within a short window using a large capital position — the flash-loan-equivalent action, since TRX/TRC10 balances required for the swap can be sourced instantaneously in a single account without needing external flash loans, as no borrowing cost or time-lock applies) can accumulate more output tokens than the pool's true backing would allow, extracting value at the pool's expense — the same "manipulate an AMM's internal accounting via non-atomic-but-rapid-sequenced trades to redeem more than deposited" bug class that drained Conic Finance's crvUSD Omnipool.

This is compounded by the mixed-precision handling across the three actuators: `ExchangeInjectActuator.execute()` computes `anotherTokenQuant` using plain `long` division (`floorDiv(multiplyExact(...))`) [7](#0-6) , while its own `doValidate()` computes the *same* value using `BigInteger` [8](#0-7) . `ExchangeWithdrawActuator` uses `BigInteger` for the withdrawal ratio in `execute()` as well [9](#0-8) . This inconsistency between validated and executed values, and between the legacy float-based swap engine and the exact-math inject/withdraw engines, creates rounding/precision mismatches that a sequence of inject→transact→withdraw operations by a single account can exploit to siphon token balance out of the pool beyond what proportional accounting would allow, permanently unbacking the pool for the remaining LP/creator.

### Impact Explanation
Exploiting the float-based Bancor relay math allows an attacker to extract more TRC10/TRX tokens from an `Exchange` pool than they contributed, at the expense of the pool creator/other participants — a direct theft-of-funds / unbacked-balance condition equivalent in class to the Conic Finance loss. Because `ExchangeCreateContract` is permissionless (any account can create a pool and become its "creator", and other unprivileged accounts can freely trade against it via `ExchangeTransactionContract`), the blast radius covers any TRC10/TRX pool created on-chain.

### Likelihood Explanation
The vulnerable path is the **default** behavior (hardening is opt-in and controlled by SR committee proposal, and tests confirm hardened mode is off by default) [10](#0-9) . The primitives required — `ExchangeCreateContract`, `ExchangeInjectContract`, `ExchangeTransactionContract`, `ExchangeWithdrawContract` — are all reachable from ordinary signed transactions with no special privilege, matching the "unprivileged transaction broadcaster" reachability bar. However, I was not able to fully verify (given tool-call limits) the exact numeric bound of the extractable rounding profit per trade, nor find the git history/PR that introduced `SafeExchangeProcessor`/`allowHardenExchangeCalculation`, which would clarify whether this was already identified and is only pending a network upgrade. I could not access `Manager.java` contents beyond the package line (index truncation), so I could not confirm what `isExchangeTransaction(...)` is used for in `Manager` beyond its test-visible bypass behavior around hardened-calculation detection.

### Recommendation
- Make `SafeExchangeProcessor` (BigDecimal-based) the sole production swap engine and remove/deprecate `ExchangeProcessor`, rather than gating exact math behind a togglable dynamic parameter that defaults to disabled.
- Unify all Exchange actuators (`Inject`, `Withdraw`, `Transaction`) to use the same BigInteger/BigDecimal exact-math routine in both `validate()` and `execute()` to eliminate the long-division vs BigInteger inconsistency identified in `ExchangeInjectActuator`.
- Enforce `StrictMath` unconditionally for any monetary computation instead of allowing `useStrictMath=false` (non-deterministic `Math.pow`) in consensus-critical code.

### Proof of Concept
Conceptual (given lack of full Manager.java visibility and no execution environment available):
1. Attacker creates an `Exchange` pool via `ExchangeCreateContract` with tokens A/B, or targets an existing pool with `allowHardenExchangeCalculation = 0` (default).
2. Attacker repeatedly issues `ExchangeTransactionContract` swaps alternating direction (A→B then B→A) in rapid succession within the same or adjacent blocks, exploiting the float-truncation asymmetry in `ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply` (`(long)` truncation always rounds toward the trader's favor across the round-trip since the "supply" state is mutated stepwise).
3. Over repeated round-trips, the attacker's net token holdings increase beyond their principal while the pool's reserve balances (`firstTokenBalance`/`secondTokenBalance`, tracked exactly via `exchangeCapsule.setBalance` from `long` reserve values) do not correspondingly capture the float-rounding loss, resulting in the pool becoming under-collateralized relative to LP share expectations.
4. Attacker (as pool creator, or via a colluding/attacker-controlled pool) calls `ExchangeWithdrawContract` to redeem the inflated share, realizing profit at other participants' expense. [11](#0-10)

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
  }
