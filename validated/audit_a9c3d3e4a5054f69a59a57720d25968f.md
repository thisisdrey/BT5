### Title
Non-constant-time comparison of the RPC `authorization` bearer token across multiple `/v3/*` HTTP handlers - ([File: stackslib/src/net/api/fastcallreadonly.rs])

### Summary
Several `stackslib/src/net/api/*` HTTP request handlers authenticate the caller by comparing the `authorization` header directly against the configured shared secret using Rust's default `String`/`&str` `PartialEq` (`!=`/`==`), which performs an early-exit, byte-by-byte comparison rather than a constant-time comparison.

### Finding Description
Multiple RPC endpoints gate access behind a static bearer token stored in `ConnectionOptions`/handler state (`self.auth`) and compare it to the client-supplied `authorization` header using ordinary string inequality:

- `stackslib/src/net/api/blockreplay.rs:575-583` — `if auth_header != password { ... 401 ... }`
- `stackslib/src/net/api/blocksimulate.rs:153-161` — same pattern
- `stackslib/src/net/api/fastcallreadonly.rs:102-110` — same pattern
- `stackslib/src/net/api/txsimulate.rs:352-360` — same pattern
- `stackslib/src/net/api/postblock_v3.rs:104-111` — same pattern (used to gate `broadcast=1`)
- `stackslib/src/net/api/postblock_proposal.rs` — token comparison for the block-proposal validation endpoint

`String`'s `PartialEq` implementation in Rust compares lengths first and then compares bytes left-to-right, returning as soon as a mismatch is found. This means the time taken by the comparison leaks information about how many leading bytes of the guessed token are correct, i.e., a classic timing side channel — the exact bug class described in the OpenClaw advisory (GHSA-jmm5-fvh5-gf4p) for its hooks token comparison.

### Impact Explanation
An attacker with network access to any of these `/v3/*` endpoints (block replay, block simulate, tx simulate, fast-call-read-only, post-block broadcast, block-proposal validation) who can send many requests and measure response timing could, in principle, incrementally recover the shared auth token byte-by-byte. Once recovered, the token grants write/administrative-ish capability such as forcing block broadcast (`postblock_v3.rs`) or invoking block/tx simulation and validation endpoints that are otherwise disabled without auth. This does not meet "Critical" (no direct unauthenticated write/crash), and given the CVSS of the analog advisory (`AC:H`, no direct C/I/A impact besides confidentiality of the token) it aligns with an authentication-adjacent weakness rather than a High/Critical primitive on its own merit — it enables a path to auth bypass if successfully exploited.

### Likelihood Explanation
Exploitation requires the operator to have exposed these endpoints (they are opt-in and require `self.auth`/`connection_opts.auth_token` to be configured) to an untrusted network, and requires a very large number of low-jitter requests to reliably measure sub-microsecond timing differences over a real network — the same caveat noted in the original OpenClaw advisory ("real-world latency and jitter can make reliable measurement difficult"). This lowers practical likelihood significantly, matching the advisory's own `AC:H` rating.

### Recommendation
Replace the direct `!=`/`==` string comparisons in `blockreplay.rs`, `blocksimulate.rs`, `fastcallreadonly.rs`, `txsimulate.rs`, `postblock_v3.rs`, and `postblock_proposal.rs` with a constant-time comparison (e.g., convert both sides to bytes and use a constant-time-compare primitive such as `subtle::ConstantTimeEq`, or hash both values with a keyed MAC and compare the MACs) so token comparison time is independent of how many leading bytes match.

### Proof of Concept
1. Configure a node with `connection_opts.auth_token = Some("<secret>")` and expose one of the affected endpoints (e.g., `/v3/blocks/replay/:block_id`) on a network reachable by the attacker.
2. Attacker repeatedly sends requests with guessed `authorization` header values, incrementally extending a correct byte prefix (standard byte-at-a-time timing attack methodology), measuring response latency at `stackslib/src/net/api/blockreplay.rs:581` (`if auth_header != password`).
3. Statistically, guesses whose correct-byte-prefix length is longer take marginally longer to reject due to the early-exit `String` comparison, allowing incremental recovery of `password` given sufficient sampling to overcome network jitter. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4)
