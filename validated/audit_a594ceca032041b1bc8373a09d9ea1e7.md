## Title
Forced `protocol.file.allow=always` in Git submodule fetch re-enables CVE-2022-39253 local-clone file exfiltration for any `git_repository`/`new_git_repository` with submodules - (File: `tools/build_defs/repo/git_worker.bzl`)

### Summary
`git_repository`/`new_git_repository`'s submodule handling unconditionally re-enables Git's dangerous local-filesystem clone protocol for every submodule update, unwinding the exact protection Git shipped to fix CVE-2022-39253. An attacker who controls the fetched Git repository content (a hostile remote, or an untrusted branch a victim's CI clones with `init_submodules`/`recursive_init_submodules = True`) can supply a malicious `.gitmodules` entry that makes Git perform a local (`file://`/path) clone of a submodule from an attacker-chosen path on the build machine, letting Git's local-clone hardlink/dereference optimization copy files from outside the intended repository into the checked-out external repository tree.

### Finding Description
`update_submodules` in [1](#0-0)  always passes `-c protocol.file.allow=always` when running `git submodule update --init [--recursive] --checkout --force`, for both the recursive and non-recursive cases, citing bazel issue #17040 as the reason for needing it with "Git 2.38.1 and associated backport versions."

That upstream Git behavior change (default `protocol.file.allow=user` for submodules) was Git's fix for GHSA-8h2j-cgm8-r8vw / CVE-2022-39253: Git's local-clone optimization can use hardlinks or dereference symlinks when cloning from a `file://`/local path, and a hostile repository's `.gitmodules` can declare a submodule URL pointing at an arbitrary local filesystem path (not necessarily related to the parent remote at all). Combined with `--recursive`/`--force`, this lets the content of the cloned repository (fully attacker-controlled — either the origin, or an untrusted branch a victim's CI builds) drive `git` into copying arbitrary local files that are readable by the Bazel process into the submodule's checked-out contents.

Bazel's `_clone_or_update_repo` / `git_repo` flow gives the attacker exactly this reach: `remote`, `commit`/`tag`/`branch` are attacker-served-content agnostic (they come from the trusted BUILD/MODULE definition), but once the repository is cloned, its `.gitmodules` file and submodule pointers are **content of the fetched repository itself** — supplied by whoever controls that git remote/branch. `update_submodules` is invoked unconditionally whenever `ctx.attr.init_submodules` or `ctx.attr.recursive_init_submodules` is set, see [2](#0-1) , with no validation of the submodule URLs, and no check afterwards that the checked-out submodule tree stayed inside the intended checkout directory (unlike the explicit escape check performed for `strip_prefix` in [3](#0-2) ).

### Impact Explanation
Because `protocol.file.allow=always` is forced for every submodule update, Git's local-clone protection is defeated for any consumer of `git_repository`/`new_git_repository` that enables submodules — which is a commonly used, non-exotic option (exercised by Bazel's own test suite, e.g. [4](#0-3) ). A hostile repository owner (or an attacker who can push to an untrusted branch a victim's CI clones) can exfiltrate/copy arbitrary files reachable by the build user's filesystem permissions (other checkouts, cache files, potentially credentials) into the external repository contents. Those contents become part of the build graph's inputs/outputs and can be read back by the build or included in build artifacts, i.e. this is a concrete "read outside the repository/exec root" primitive driven purely by attacker-published repository content.

### Likelihood Explanation
No user opt-in beyond the already-common `init_submodules`/`recursive_init_submodules` attributes is required; the dangerous flag is set by Bazel itself, unconditionally, for both submodule code paths. Any project that vendors a `git_repository` pointing at a repository under less-trusted control (a fork, a CI-mirrored branch, or a repository the victim doesn't fully audit) is exposed the moment that repository's `.gitmodules` is crafted maliciously.

### Recommendation
Do not unconditionally force `protocol.file.allow=always`. Restrict it to the narrow case actually needed (recursive submodule updates on affected Git versions cloning from genuinely local/on-disk parent remotes), or better, resolve submodule URLs against an explicit allowlist / restrict `protocol.file.allow` to only the specific local path that Bazel itself is orchestrating (the top-level `remote`) rather than trusting `.gitmodules`-declared URLs found inside the fetched content. At minimum, add a post-checkout containment check (similar to the `strip_prefix` escape check) verifying that no submodule path/content was materialized from outside the intended checkout tree.

### Proof of Concept
1. Create `outer_repo` with a `.gitmodules` entry such as:
   ```
   [submodule "leak"]
       path = leak
       url = /etc
   ```
   (or any absolute local path the victim's build user can read, potentially a symlink further escalating scope), and commit it.
2. In a `MODULE.bazel`, declare:
   ```python
   git_repository(
       name = "outer_repo",
       remote = "<path/URL to outer_repo>",
       branch = "main",
       recursive_init_submodules = True,
   )
   ```
3. Running `bazel build` triggers `update_submodules(..., recursive=True)`, which executes `git -c protocol.file.allow=always submodule update --init --recursive --checkout --force` (see [5](#0-4) ); because `protocol.file.allow=always`, Git performs the local clone from `/etc` without the default Git 2.38+ restriction, copying `/etc`'s contents into `external/outer_repo/leak`, which can then be read by any target depending on `@outer_repo//...`.
4. This can be formalized as a `src/test/shell/bazel/starlark_git_repository_test.sh` case analogous to `test_git_repository_submodules_with_recursive_init_modules` [6](#0-5) , replacing the benign submodule with one whose `.gitmodules` URL targets a path outside `$TEST_TMPDIR/repos/outer-planets`, and asserting the forbidden file's contents appear in the Bazel-managed external repository directory.

```text
def update_submodules(ctx, git_repo, recursive = False):
    if recursive:
        # "protocol.file.allow=always" allows the submodule command clone from a local directory.
        # It's necessary for Git 2.38.1 and assoicated backport versions.
        # See https://github.com/bazelbuild/bazel/issues/17040
        _git_maybe_shallow(ctx, git_repo, "-c", "protocol.file.allow=always", "submodule", "update", "--init", "--recursive", "--checkout", "--force")
    else:
        _git_maybe_shallow(ctx, git_repo, "-c", "protocol.file.allow=always", "submodule", "update", "--init", "--checkout", "--force")
```

```shellscript
function test_git_repository_submodules_with_recursive_init_modules() {
  local outer_planets_repo_dir=$TEST_TMPDIR/repos/outer-planets

  # Create a workspace that clones the outer_planets repository.
  cat >> MODULE.bazel <<EOF
git_repository = use_repo_rule('@bazel_tools//tools/build_defs/repo:git.bzl', 'git_repository')
git_repository(
    name = "outer_planets",
    remote = "$outer_planets_repo_dir",
    tag = "1-submodule",
    recursive_init_submodules = 1,
    build_file = "//:outer_planets.BUILD",
)
EOF

  cat > BUILD <<EOF
exports_files(['outer_planets.BUILD'])
EOF
  cat > outer_planets.BUILD <<EOF
filegroup(
    name = "neptune",
    srcs = ["neptune/info"],
    visibility = ["//visibility:public"],
)

filegroup(
    name = "pluto",
    srcs = ["pluto/info"],
    visibility = ["//visibility:public"],
)
EOF

  mkdir -p planets
  cat > planets/BUILD <<EOF
genrule(
    name = "planet-info",
    srcs = [
        "@outer_planets//:neptune",
        "@outer_planets//:pluto",
    ],
    outs = ["planet-info.txt"],
    cmd = "cat \$(SRCS) > \$@",
)
EOF

  bazel build //planets:planet-info >& $TEST_log \
    || echo "Expected build/run to succeed"
  cat bazel-bin/planets/planet-info.txt > $TEST_log
  expect_log "Neptune is a planet"
  expect_log "Pluto is a planet"
}
```
