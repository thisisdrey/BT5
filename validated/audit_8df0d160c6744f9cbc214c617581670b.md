### Title
Dust-deposit griefing fills victim's token list to `MAX_TOKENS_PER_USER`, DoS-ing all subsequent deposits and borrows - (File: contracts/Pool.sol)

### Summary
`Pool.addToDepositTokensOfAccount` / `addToDebtTokensOfAccount` enforce `MAX_TOKENS_PER_USER = 30` combined entries per account and revert with `UserReachedMaxTokens()` once reached. `DepositToken.deposit(amount_, onBehalfOf_)` lets any caller mint msdTOKEN to an arbitrary `onBehalfOf_` address, and `DepositToken._transfer` likewise credits any recipient. Both paths call `pool.addToDepositTokensOfAccount` whenever the recipient's balance goes 0 → >0. An unprivileged attacker can therefore permissionlessly fill a victim's per-account token list with dust positions in every listed collateral, after which the victim cannot deposit a new collateral, receive a deposit token, be seized into a new collateral during liquidation, or mint a new synthetic (the debt-token list check shares the same limit). This is a liveness/availability analog of CVE-2023-21940 (unprivileged-triggerable, repeatable DoS of a core service).

### Finding Description
- `Pool.sol:79` sets `MAX_TOKENS_PER_USER = 30` and `Pool.sol:143-148` (`onlyIfAdditionWillNotReachMaxTokens`) reverts when `debtTokensOfAccount + depositTokensOfAccount >= 30`.
- `Pool.sol:216-220` `addToDepositTokensOfAccount` is callable by any registered `DepositToken` for any `account_`; the caller only has to be a whitelisted token, which is satisfied automatically inside `_mint`/`_transfer`.
- `DepositToken.deposit` (`DepositToken.sol:211-237`) accepts an arbitrary `onBehalfOf_` and mints to it; `_mint` (`DepositToken.sol:486-488`) adds the token to the recipient's account list on first balance.
- `DepositToken._transfer` (`DepositToken.sol:517-520`) does the same for transfers, so a plain `transfer(victim, dust)` also fills a slot.
- `DebtToken.issue`/`mint` add to `debtTokensOfAccount` via the same `onlyIfAdditionWillNotReachMaxTokens` modifier, so once the combined count hits 30 the victim cannot open any new debt position either.
- There is no opt-out: the victim cannot prevent receiving dust (deposit `onBehalfOf_` requires no consent), and any new deposit, transfer-in, seize, or issue reverts until slots are freed.

Attack trace:
1. Pool has `N` whitelisted deposit tokens (mainnet deployments list many collaterals; cap is 30 total). Attacker acquires 1 wei of each underlying (or wraps and transfers msdTOKEN dust directly).
2. For each `DepositToken` the victim doesn't hold, attacker calls `deposit(1, victim)` or `transfer(victim, 1)`.
3. Victim's `depositTokensOfAccount` length reaches 30 (attacker can also first push a few `DebtToken` entries onto themselves — irrelevant; the combined per-victim count is what matters).
4. All subsequent victim calls that would add a new token revert with `UserReachedMaxTokens()`: `deposit` of any new collateral, `DebtToken.issue`/`mint` of any new synthetic (calls `addToDebtTokensOfAccount`), `SmartFarmingManager.leverage` (mints new deposit/debt entries), and `Pool.liquidate` seizes into a deposit token the liquidator doesn't already hold also revert for the liquidator — degrading liquidation liveness for positions involving fresh collaterals.

### Impact Explanation
Temporary freezing of victim funds / protocol functionality: the victim is blocked from depositing new collateral types, borrowing new synthetics, and using leverage until they manually burn/transfer out the dust entries (each `withdraw`/`transfer` that zeroes a dust balance frees one slot via `removeFromDepositTokensOfAccount`). Recovery requires the victim to discover the attack and spend gas/fees unwinding attacker-chosen dust, and during the window a position needing a new collateral top-up to stay healthy cannot be rescued — a liquidation the victim could have prevented may proceed, compounding the loss. Liquidators can also be temporarily blocked on the `seize` leg when seizing into a token they don't already hold. Direct theft is not achieved, matching the Medium/DoS severity of the source CVE.

### Likelihood Explanation
- Fully unprivileged: any EOA calls `DepositToken.deposit`/`transfer`; no privileged role, oracle manipulation, or governance needed.
- Cost is bounded by acquiring dust of each listed collateral and per-call gas; on chains with many listed collaterals the attack scales, but even filling ~20 slots is enough in pools with few debt tokens already used by the victim.
- Repeatable: the attacker can re-grief after the victim cleans up, and can target many users or liquidation bots' executor accounts.
- Caveat: impact is bounded by the number of whitelisted deposit tokens in the pool and the victim can self-recover by withdrawing dust, so this is a temporary (though repeatable) DoS rather than permanent freezing.

### Recommendation
- Do not let unsolicited receipts consume the cap: track per-account token sets only for tokens the account actively deposited/issued (e.g., only add in `deposit`/`issue` where `_msgSender() == account_`, or maintain an `account => token => enrolled` opt-in flag set by the user).
- Alternatively, remove the hard `MAX_TOKENS_PER_USER` revert on receive paths and bound iteration differently (e.g., paginated health checks, or only counting tokens the user has collateral value in above a dust threshold).
- As a minimum mitigation, exempt `transfer`-based additions or add a per-account "trusted sender" allowance so dust cannot be force-pushed.

### Proof of Concept
```solidity
// Hardhat (ethers) — assumes `pool`, `depositTokens[]` (whitelisted), and victim already set up.
it("fills victim's token list via dust deposits on behalf", async () => {
  const tokens = await pool.getDepositTokens();
  for (const t of tokens) {
    const dt = await ethers.getContractAt("DepositToken", t);
    const underlying = await ethers.getContractAt("IERC20", await dt.underlying());
    await underlying.connect(attacker).approve(dt.address, 1);
    await dt.connect(attacker).deposit(1, victim.address); // 0 -> >0 adds slot
  }
  // victim's combined list is now at MAX_TOKENS_PER_USER
  await expect(
    newDepositToken.connect(victim).deposit(parseEther("1"), victim.address)
  ).to.be.revertedWithCustomError(pool, "UserReachedMaxTokens");
  await expect(
    debtToken.connect(victim).issue(victim.address, 1) // if victim has collateral
  ).to.be.revertedWithCustomError(pool, "UserReachedMaxTokens");
});
```
