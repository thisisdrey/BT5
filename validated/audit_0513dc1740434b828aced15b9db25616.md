## Analysis

`ExchangeTransactionContract` includes an `expected` field which `ExchangeTransactionActuator` uses to enforce a slippage floor (`if (anotherTokenQuant < tokenExpected) throw ContractValidateException`). [1](#0-0) 

However, the sibling contracts `ExchangeInjectContract` and `ExchangeWithdrawContract` have no such field — they only carry `owner_address`, `exchange_id`, `token_id`, and `quant`. [2](#0-1) 

### Title
Missing slippage control on `ExchangeInjectActuator`/`ExchangeWithdrawActuator` allows front-run manipulation of computed counter-token amount - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`, `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
`ExchangeInjectActuator.execute` and `ExchangeWithdrawActuator.execute` compute the counter-token amount (`anotherTokenQuant`) at execution time from the *current* on-chain pool ratio, but the corresponding contracts (`ExchangeInjectContract`, `ExchangeWithdrawContract`) provide no user-supplied minimum/maximum bound to protect against that ratio changing between transaction submission and block inclusion — unlike `ExchangeTransactionContract`, which has an `expected` field enforced by a validate-time check.

### Finding Description
For `ExchangeInjectActuator`, the amount of the second token required/added is derived proportionally from the live pool balances at execution time:
```
anotherTokenQuant = floorDiv(multiplyExact(secondTokenBalance, tokenQuant), firstTokenBalance);
``` [3](#0-2) 

For `ExchangeWithdrawActuator`, the amount of the second token returned to the withdrawer is likewise derived from the live pool ratio at execution time:
```
anotherTokenQuant = bigSecondTokenBalance.multiply(bigTokenQuant).divide(bigFirstTokenBalance).longValueExact();
``` [4](#0-3) 

Neither actuator's `doValidate()` checks `anotherTokenQuant` against any user-supplied bound — contrast this with `ExchangeTransactionActuator.doValidate()`, which explicitly validates `anotherTokenQuant >= tokenExpected` using the `expected` field from `ExchangeTransactionContract`. [1](#0-0)  Because `ExchangeInjectContract`/`ExchangeWithdrawContract` lack this field entirely, there is no way for a caller to bound the counter-token amount at all. [2](#0-1) 

Any account can move the pool ratio in the same block window by broadcasting an `ExchangeTransactionContract` transaction (a normal, low-privilege exchange trade) against the same `exchange_id` before the victim's `ExchangeInject`/`ExchangeWithdraw` transaction is packed, since the pool balances (`firstTokenBalance`/`secondTokenBalance`) are mutated by every trade against that exchange (`Commons.putExchangeCapsule`, called from all three actuators). This is directly analogous to the reported `LRTDepositPool.depositAsset` issue: an economic-rate-dependent transaction with no way for the sender to bound the output, letting the amount receive/require drift arbitrarily between submission and execution.

### Impact Explanation
- On `ExchangeWithdraw`, the exchange creator can receive far less of the counter token than the pool ratio implied when they signed the transaction, permanently losing value with no recourse (the transaction succeeds regardless of how unfavorable the ratio has become).
- On `ExchangeInject`, the creator can be forced to deposit (lock) far more or far less of the counter asset than intended relative to the injected token, distorting their intended liquidity contribution without any protection.

This is a direct funds-loss/unbacked-exposure risk for the exchange creator, comparable in class to the cited Medium-severity finding, though bounded to the specific exchange's creator-only operations (`ExchangeInject`/`ExchangeWithdraw` require `accountCapsule.getAddress().equals(exchangeCapsule.getCreatorAddress())`). [5](#0-4) 

### Likelihood Explanation
Any account can submit an `ExchangeTransactionContract` trade against a target exchange to shift its ratio; this requires no special privilege beyond an ordinary signed transaction and sufficient balance for a minimal trade, and Tron's mempool/block-packing ordering gives an adversary a practical window to act before a pending `ExchangeInject`/`ExchangeWithdraw` is included.

### Recommendation
Add an `expected`-style bound (e.g., `expected` for withdraw's returned counter-amount, and a `max_quant`/`expected` bound for inject's required counter-amount) to `ExchangeInjectContract` and `ExchangeWithdrawContract`, and enforce it in `ExchangeInjectActuator.doValidate()` / `ExchangeWithdrawActuator.doValidate()` the same way `ExchangeTransactionActuator` already enforces `tokenExpected` against `anotherTokenQuant`.

### Proof of Concept
1. Exchange `E` holds `firstToken`/`secondToken` balances `A`/`B`.
2. Creator submits `ExchangeWithdrawContract(exchange_id=E, token_id=firstToken, quant=Q)`, expecting `anotherTokenQuant ≈ B*Q/A` back in `secondToken`.
3. Before this transaction is packed, an attacker (any account) submits `ExchangeTransactionContract` trades against `E` that shift the ratio `A/B` unfavorably for the pending withdraw.
4. The creator's withdraw executes with the new, worse ratio in `ExchangeWithdrawActuator.execute` (lines computing `anotherTokenQuant` from live `firstTokenBalance`/`secondTokenBalance`), and there is no validation step comparing the result to any minimum the creator specified — because none exists in `ExchangeWithdrawContract`. [4](#0-3) 
5. The creator receives less `secondToken` than intended, with the transaction still reporting `code.SUCESS`.
