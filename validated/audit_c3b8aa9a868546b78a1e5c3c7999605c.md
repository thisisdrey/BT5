### Title
Unpersisted Maker Order State on Zero-Fill Edge Case Enables Double-Return of Sell Tokens via `MarketCancelOrderContract` - (File: actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java)

### Summary
In `MarketSellAssetActuator.matchSingleOrder`, when a maker order is matched down to a remaining quantity so small that the computed `makerBuyTokenQuantityReceive` rounds to zero, the code marks the maker order `INACTIVE`, refunds the unsold tokens to the maker's account balance, and returns early — **without ever calling `orderStore.put()`** to persist those changes back to the `MarketOrderStore`. This leaves an orphaned, stale order record on disk (still `ACTIVE`, with the original non-zero `sell_token_quantity_remain`) even though the order has already been removed from the owner's `MarketAccountOrderCapsule` list and from the `MarketPairPriceToOrderStore` order book. Because `MarketCancelOrderActuator` validates cancellation solely against the (stale) `MarketOrderStore` record — checking `isActive()` and owner match, but never checking whether the order is still referenced in the account's order list — the owner can subsequently submit a `MarketCancelOrderContract` for this orphaned order ID and receive a second refund of the same tokens, effectively minting an unbacked balance.

### Finding Description
`matchSingleOrder` ( [1](#0-0) ) handles the "taker > maker" branch by computing: [2](#0-1) 

When `makerBuyTokenQuantityReceive == 0` (a case the inline comment incorrectly claims "would not happen here" — it assumes `sellQuantity < buyQuantity`, which is not enforced anywhere in `validate()`), the code:
1. Already called `MarketUtils.updateOrderState(makerOrderCapsule, State.INACTIVE, marketAccountStore)` at line 465, which removes the order from the owner's `MarketAccountOrderCapsule` list ( [3](#0-2) ).
2. Calls `returnSellTokenRemain(makerOrderCapsule)`, which credits the owner's account with the remaining sell-token quantity and sets `orderCapsule.setSellTokenQuantityRemain(0L)` **in memory only** ( [4](#0-3) , [5](#0-4) ).
3. `return;`s immediately, skipping the `orderStore.put(makerOrderCapsule.getID().toByteArray(), makerOrderCapsule);` call at line 486 that would persist the updated state.

Back in the caller `matchOrder`, the post-match check `if (makerOrderCapsule.getSellTokenQuantityRemain() == 0)` (line 350) is true (same in-memory object), so the order is also removed from `pairPriceToOrderStore`'s order-book index ( [6](#0-5) ).

The net effect: the order is removed from every *index* structure (account order list, order book), but the canonical `MarketOrderStore` record is never updated — it still shows `state = ACTIVE` and the original non-zero `sell_token_quantity_remain`.

`MarketCancelOrderActuator.validate()` only checks the orphaned `MarketOrderStore` record directly, not membership in the account/order-book indices: [7](#0-6) 

Since the stale record still reports `isActive() == true` and the correct owner address, this validation passes, and `execute()` calls `MarketUtils.returnSellTokenRemain(orderCapsule, accountCapsule, ...)` again, crediting the owner's balance a second time with the same (stale) `sell_token_quantity_remain` that was already refunded once: [8](#0-7) 

### Impact Explanation
This produces tokens/TRX credited to an account without a corresponding backing debit — an unbacked-balance condition reachable by any account that places a market maker order shaped to trigger the zero-fill rounding edge case (e.g., selling a very large quantity of token A for a very small quantity of token B, so that as the order is whittled down by takers, the final partial fill rounds `makerBuyTokenQuantityReceive` to 0). The attacker fully controls order parameters (`sellTokenQuantity`, `buyTokenQuantity`) via `MarketSellAssetContract`, and inducing additional maker fills can be done with self-created taker orders from another account they control. This is directly reachable from ordinary signed transactions (`MarketSellAssetContract` and `MarketCancelOrderContract`) with no special privileges required.

### Likelihood Explanation
Triggering the zero-fill branch requires crafting a maker order with a skewed sell:buy ratio and driving its remaining quantity down via matches until the rounding-to-zero condition is hit — deterministic and fully attacker-controlled, not reliant on chain state races. It requires the `AllowMarketTransaction` feature to be enabled by committee (`dynamicStore.supportAllowMarketTransaction()`), which is a standard/expected feature flag on a functioning TRON network with the exchange/market module active, not a privileged bypass.

### Recommendation
In the `makerBuyTokenQuantityReceive == 0` branch of `matchSingleOrder`, always persist the mutated `makerOrderCapsule` via `orderStore.put(...)` before returning (mirroring line 486), so the on-disk record matches the removed-from-indices state. Additionally, harden `MarketCancelOrderActuator.validate()` to cross-check that the order ID is still present in the owner's `MarketAccountOrderCapsule` order list (not just that `orderStore` reports it active), preventing cancellation of orphaned/already-settled order records.

### Proof of Concept
1. Account A places a maker sell order: `sellTokenId = X`, `sellTokenQuantity = 1_000_000`, `buyTokenId = Y`, `buyTokenQuantity = 1` (extreme price ratio), via `MarketSellAssetContract` (goes to `MarketSellAssetActuator.execute`).
2. Account B (or A, using a second address) places successive taker orders against A's order to whittle `sellTokenQuantityRemain` down to a small value (e.g., 1) without fully consuming it, exploiting `MarketUtils.multiplyAndDivide` integer flooring in `matchSingleOrder`'s "taker < maker" / "taker == maker" branches.
3. Account B places one more taker order that lands in the "taker > maker" branch (`takerBuyTokenQuantityRemain > makerSellRemainQuantity`) computing `makerBuyTokenQuantityReceive = floor(1 * 1 / 1_000_000) = 0`, entering the buggy path in `matchSingleOrder` at [9](#0-8) . Account A's remaining 1 unit of token X is credited to A's balance, but the maker order's `MarketOrderStore` record is left stale (`ACTIVE`, `sell_token_quantity_remain = 1`).
4. Account A submits `MarketCancelOrderContract` for the stale order ID. `MarketCancelOrderActuator.validate()` passes because the stale record still shows `ACTIVE` and correct ownership ( [7](#0-6) ), and `execute()` credits A's account with the same 1 unit of token X a second time ( [10](#0-9) ), producing an unbacked balance increase.

Note: The exact numeric reachability of the zero-fill rounding condition depends on `MarketUtils.multiplyAndDivide`/`priceMatch` behavior across the full match loop, which was reviewed but not executed in a live test environment; confirming the precise sequence of taker fills needed to land exactly on the `makerBuyTokenQuantityReceive == 0` branch would benefit from a Devin session with test execution access to `MarketSellAssetActuatorTest`.

  public static void updateOrderState(MarketOrderCapsule orderCapsule,
      State state, MarketAccountStore marketAccountStore) throws ItemNotFoundException {
    orderCapsule.setState(state);

    // remove from account order list
    if (state == State.INACTIVE || state == State.CANCELED) {
      MarketAccountOrderCapsule accountOrderCapsule = marketAccountStore
          .get(orderCapsule.getOwnerAddress().toByteArray());
      accountOrderCapsule.removeOrder(orderCapsule.getID());
      marketAccountStore.put(accountOrderCapsule.createDbKey(), accountOrderCapsule);
    }
  }
