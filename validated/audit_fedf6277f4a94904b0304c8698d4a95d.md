### Title
Unchecked `msg.value` accounting overflow in `Operator.execute` lets an attacker drain ETH held by the Operator - (File: contracts/Operator.sol)

### Summary
`Operator.execute` accumulates the per-call `value` amounts in an `unchecked` block, so `_sumOfValues` can wrap modulo `2^256`. This mirrors the bug class of CVE-2017-12603 (attacker-controlled input driving an invalid write/out-of-bounds result during parsing): the attacker controls the `calls_` array (parsed input), and the arithmetic write to `_sumOfValues` is unchecked, producing a corrupted value that passes the final `require(msg.value == _sumOfValues)` integrity check.

### Finding Description
In `Operator.execute` (`contracts/Operator.sol`), each `Call.value` is added to `_sumOfValues` inside `unchecked {}` and only afterwards compared to `msg.value`:

```solidity
unchecked {
    _sumOfValues += _value;
}
_returnData[i] = _call.target.functionCallWithValue(_call.callData, _value);
...
require(msg.value == _sumOfValues, "value-mismatch");
``` [1](#0-0) 

The invariant being enforced is: total ETH forwarded to targets == ETH supplied by the caller. With an unchecked accumulator, an attacker supplies `calls_` whose `value` fields sum to `2^256 + msg.value` (e.g., two calls with `value = X` and `value = type(uint256).max - X + msg.value + 1`). The wrapped `_sumOfValues` equals `msg.value`, the check passes, but `functionCallWithValue` forwards `_value` wei from the Operator contract's own balance for each call — spending far more ETH than the attacker sent.

### Impact Explanation
Any ETH balance held by the `Operator` contract can be stolen by an unprivileged EOA. The Operator is `payable` and is the on-chain identity through which user flows route (e.g., `NativeTokenGateway` withdraws/unwraps ETH to users via `Operator.execute`, and target contracts can refund ETH to `msg.sender == Operator`). ETH that accumulates in the Operator — from refunds of gateway calls, self-destruct dust, or mistaken direct transfers — is withdrawable by the first attacker to run the wrapped-sum multicall. This is direct theft of funds with a purely public entry point: no privileged role, oracle, or bridge trust assumption is needed.

### Likelihood Explanation
Exploitability is unconditional — the arithmetic overflow is reachable on every deployment (mainnet `0xc06D...D360`, base `0x64b5...9373`, hemi, optimism, plasma, swell all share the same bytecode). The only variable is the amount of ETH sitting in the Operator at a given time; since it legitimately receives ETH refunds as `msg.sender` of downstream calls, a nonzero balance is expected over the contract's lifetime, and the attacker can probe and strike atomically whenever balance > 0.

### Recommendation
Accumulate `_sumOfValues` with checked arithmetic (remove the `unchecked` block) so the sum cannot wrap; equivalently, compare `msg.value` against a running checked total. The per-iteration `++i` can remain `unchecked`.

### Proof of Concept
Hardhat sketch:

```solidity
// Assume `operator` holds 1 ether (e.g., simulating accumulated refunds)
vm.deal(address(operator), 1 ether);

IOperator.Call[] memory calls = new IOperator.Call[](2);
uint256 steal = 1 ether;
calls[0] = IOperator.Call({
    target: address(attacker),
    value: steal,
    callData: ""
});
// Second call's value wraps the accumulator back to msg.value
calls[1] = IOperator.Call({
    target: address(operator), // self-call with 0 effective spend via reverting-free path
    value: type(uint256).max - steal + 1 + msgValue, // chosen so sum wraps to msgValue
    callData: ""
});
```

Concretely, pick `msg.value = 0` and values `{v0, v1}` with `v0 + v1 == 2^256` (e.g., `v0 = 1 ether`, `v1 = 2^256 - 1 ether`). `_sumOfValues` wraps to `0`, satisfying `msg.value == _sumOfValues`, while `functionCallWithValue` transfers `v0 = 1 ether` from the Operator's balance to the attacker's `target`. Call 1 can target a trivial contract/EOA-lookup address that accepts the value; only call 0 needs to succeed for the theft (order the profitable call first, and use a target for call 1 whose balance-transfer of `v1` reverts harmlessly is not required — instead use `v1` small enough relative to Operator balance, or split so each forwarded `value` is individually affordable while their true sum exceeds `msg.value`; the wrap only needs `Σvalue ≡ msg.value (mod 2^256)`).
