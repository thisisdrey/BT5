### Title
Freeze can be bypassed via the order-execution (and receivership) sibling authorization path in `lending_account_withdraw` - (File: `programs/marginfi/src/state/marginfi_account.rs`)

### Summary
`lending_account_withdraw` (and the drift/kamino/juplend/solend withdraw variants, plus borrow/deposit/close_balance) gate value-moving actions with two separate constraints: `account_not_frozen_for_authority` and `is_signer_authorized`. `account_not_frozen_for_authority` only blocks the action when the *signer equals the account authority*; it deliberately does not block any other signer. `is_signer_authorized`, when called with `allow_order_execution = true` or `allow_receivership = true` (as `LendingAccountWithdraw` does), returns `true` unconditionally for those states without ever re-checking `ACCOUNT_FROZEN`. As a result, once an account is placed into `ACCOUNT_IN_ORDER_EXECUTION` or `ACCOUNT_IN_RECEIVERSHIP`, a signer that is not the account authority can pass both guards and withdraw funds even though the account is frozen.

### Finding Description
`account_not_frozen_for_authority` is defined as: [1](#0-0) 
It only returns `false` (blocking) when the account is frozen **and** `signer == marginfi_account.authority`. Any non-authority signer always passes this check, frozen or not.

The complementary function `is_signer_authorized` is: [2](#0-1) 
When `allow_order_execution` is true and `ACCOUNT_IN_ORDER_EXECUTION` is set, it returns `true` unconditionally — it never inspects `ACCOUNT_FROZEN` in that branch. Similarly, when `allow_receivership` is true and `ACCOUNT_IN_RECEIVERSHIP` is set, it returns `authority != signer`, again without consulting `ACCOUNT_FROZEN`.

`LendingAccountWithdraw`'s account constraints call both functions together and pass `true, true` for receivership/order-execution: [3](#0-2) 

Combining the two checks: if `ACCOUNT_IN_ORDER_EXECUTION` (or `ACCOUNT_IN_RECEIVERSHIP`) is set on a frozen account, and the caller uses any signer key other than the frozen account's `authority` (e.g., the order keeper/executor), then:
- `account_not_frozen_for_authority` passes (signer != authority),
- `is_signer_authorized` passes (order-execution/receivership branch short-circuits before ever checking `ACCOUNT_FROZEN`).

The order-execution flag is set by `start_execute_order`, which does not check `ACCOUNT_FROZEN` at all in its handler body: [4](#0-3) 
This is asymmetric with `PlaceOrder`, which explicitly forbids creating an order on a frozen account: [5](#0-4) 
So an order placed while the account was unfrozen remains executable by any permissionless keeper/executor after the admin later freezes the account, and the resulting `lending_account_withdraw` call during that execution window bypasses the freeze because the signer is the executor, not the frozen authority.

### Impact Explanation
If freeze is intended as an absolute halt on value-moving operations for a flagged account (consistent with the fact that `PlaceOrder` refuses to even create an order on a frozen account), then an already-placed order combined with `ACCOUNT_IN_ORDER_EXECUTION` lets a keeper/executor (an unprivileged, permissionless caller) continue to withdraw/move funds out of a frozen account after admin freezes it — defeating the safety freeze with a direct financial effect (unauthorized withdrawal proceeding despite the freeze). This matches "High: unauthorized state mutation or bypass of safety freeze with financial effect."

### Likelihood Explanation
Preconditions: the account must have an active order (`PlaceOrder` executed while unfrozen) whose trigger condition has been met, and the admin must freeze the account after order placement but before the keeper executes it. Both conditions are realistic — trigger prices can be hit any time, freezes can happen asynchronously via admin action, and order execution is explicitly designed to be permissionless (any executor can call `start_execute_order`/`end_execute_order`). No admin/governance privilege is required by the attacker; a normal keeper wallet suffices. The bug is deterministic once the flag/timing conditions align, not probabilistic.

### Recommendation
Re-check `ACCOUNT_FROZEN` inside `is_signer_authorized`'s `allow_order_execution` and `allow_receivership` branches (or in `start_execute_order`/receivership-entry instructions) so that a frozen account cannot enter or continue an order-execution/receivership flow that results in a value-moving withdrawal, unless the freeze semantics are explicitly documented/intended to permit liquidation-style flows through those paths. At minimum, `start_execute_order` should reject accounts with `ACCOUNT_FROZEN` set, mirroring the check already present in `PlaceOrder`.

### Proof of Concept
1. Create a marginfi account with authority A; deposit collateral and borrow to open a two-balance position eligible for a stop-loss/take-profit order.
2. Call `place_order` (unfrozen account) to register a trigger order — succeeds per the `PlaceOrder` constraint check.
3. Admin calls the freeze instruction to set `ACCOUNT_FROZEN` on the account.
4. Move price such that the order's trigger condition is met.
5. As an unrelated keeper/executor `K` (not authority A, not admin), call `start_execute_order` → assert it currently succeeds (sets `ACCOUNT_IN_ORDER_EXECUTION`) despite `ACCOUNT_FROZEN` being set — this is the bug; expected behavior is rejection with `AccountFrozen`/similar.
6. Within the order-execution window, call `lending_account_withdraw` with `authority = K` (or any non-authority signer) against the frozen account — assert both `account_not_frozen_for_authority` and `is_signer_authorized` pass and the withdrawal executes, moving funds out of the frozen account.
7. Compare against the sibling `PlaceOrder` behavior, which correctly rejects on a frozen account (`UnexpectedOrderExecutionState`/`AccountFrozen`), demonstrating the inconsistency between sibling branches referenced in the invariant.

pub fn is_signer_authorized(
    marginfi_account: &MarginfiAccount,
    group_admin: Pubkey,
    signer: Pubkey,
    allow_receivership: bool,
    allow_order_execution: bool,
) -> bool {
    if allow_receivership && marginfi_account.get_flag(ACCOUNT_IN_RECEIVERSHIP) {
        return marginfi_account.authority != signer; // forbidden to take receivership of your own account
    }

    if allow_order_execution && marginfi_account.get_flag(ACCOUNT_IN_ORDER_EXECUTION) {
        return true;
    }

    if marginfi_account.get_flag(ACCOUNT_FROZEN) {
        return group_admin == signer;
    }

    marginfi_account.authority == signer
}
