### Title
`GetAttachmentResponse` deserialization admits attacment content of unbounded size, and `insert_instantiated_attachment` stores it without checking `AtlasConfig.attachments_max_size` - (File: `stackslib/src/net/atlas/mod.rs`, `stackslib/src/net/atlas/download.rs`, `stackslib/src/net/atlas/db.rs`)

### Summary
`GetAttachmentResponse`'s `Deserialize` impl hex-decodes the `content` field and wraps it in `Attachment::new(bytes)` with no size check against `AtlasConfig.attachments_max_size`. When this attachment is obtained via the Atlas downloader (a remote peer responding to a `GET /v2/attachments/<hash>` request), it is inserted directly via `AtlasDB::insert_instantiated_attachment`, which performs a raw SQL insert with no size validation — unlike `AtlasDB::should_keep_attachment`, which does enforce the size cap but is not on this code path.

### Finding Description
`GetAttachmentResponse::deserialize` reads an arbitrary-length hex string and constructs `Attachment::new(bytes)` unconditionally: [1](#0-0) .

When the `AttachmentsDownloader` processes a completed batch, it decodes the HTTP response via `decode_atlas_get_attachment` and stores the resulting `Attachment` into `context.attachments` with no size check: [2](#0-1) .

Then, on batch completion, every attachment drained from `context.attachments` is committed via `network.atlasdb.insert_instantiated_attachment(&attachment)`, again with no size validation: [3](#0-2) .

`AtlasDB::insert_instantiated_attachment` performs a raw `INSERT OR REPLACE` of `attachment.hash()` and `attachment.content` with no length check whatsoever: [4](#0-3) .

The same is true for the `check_attachment_instances` path, which also calls `insert_instantiated_attachment` unconditionally when resolving an inboxed attachment: [5](#0-4) .

By contrast, `AtlasDB::should_keep_attachment` explicitly checks `attachment.content.len() as u32 > self.atlas_config.attachments_max_size` and rejects oversized attachments — but this function is used for `insert_uninstantiated_attachment`/POST-transaction attachment gossip flows (e.g. `RPCPostTransactionRequestHandler::parse_posttransaction_json` at `stackslib/src/net/api/posttransaction.rs:83-90`), not for attachments fetched by the downloader from a remote peer's `GetAttachmentResponse`. This means the invariant "stored attachment size <= `AtlasConfig.attachments_max_size`" is enforced on one ingestion path (self-submitted/POST transaction attachments) but not on the peer-to-peer download path exercised by `AttachmentsDownloader`.

A malicious peer, upon receiving a `GET /v2/attachments/<hash>` request (issued because the requester learned of an `AttachmentInstance` with that content hash from a block/tx, or from the peer's own inventory advertisement), can respond with a `GetAttachmentResponse` JSON body whose hex-encoded `content` is arbitrarily large (bounded only by whatever generic HTTP/message-size ceiling exists in the transport layer, not by the Atlas-specific `attachments_max_size`, whose minimum is only 1 MiB — `ATTACHMENTS_MAX_SIZE_MIN`). This oversized content is decoded, hashed, and persisted into the requester's `AtlasDB` sqlite `attachments` table without ever being checked against the configured cap.

### Impact Explanation
The requesting node's `AtlasDB` stores attachment content that violates the operator-configured `attachments_max_size` bound, defeating the purpose of that configuration knob (bounding on-disk/in-memory attachment storage). A remote, unprivileged peer that is asked for an attachment (or that advertises an attachment in its inventory that the victim then requests) can cause the victim to persist content of essentially unbounded size (up to whatever the underlying HTTP/message transport permits) into its local Atlas database. This is repeatable per distinct `AttachmentInstance`/content hash the peer can get the victim to request, giving the attacker leverage over the victim's storage growth, i.e., attachment storage exhaustion via a single oversized gossiped attachment whose size was never checked before commit.

### Likelihood Explanation
- The attacker only needs to be a normal P2P/RPC peer serving the `/v2/attachments/<hash>` endpoint that is contacted as a natural consequence of Atlas's peer sync logic; no privileged role, secret, or StackerDB slot ownership is required.
- The attacker needs the victim to have queued an `AttachmentInstance` for a content hash that the attacker can serve arbitrary bytes for — this occurs whenever the victim processes a BNS/Atlas-tracked on-chain event referencing an attachment hash and then goes to fetch it from peers (including the attacker), which is routine, automatic behavior of the `AttachmentsDownloader`.
- Cost to the attacker is trivial: craft one oversized HTTP JSON response.
- Repeatable per attachment instance the victim requests from the attacker.

### Recommendation
Enforce `AtlasConfig.attachments_max_size` uniformly on every ingestion path for `Attachment` content, not just `insert_uninstantiated_attachment`/`should_keep_attachment`. Specifically:
- Add a size check identical to `should_keep_attachment`'s check inside `AtlasDB::insert_instantiated_attachment` (or call `should_keep_attachment`-style validation before committing) so oversized attachments are rejected/discarded rather than stored.
- Additionally, bound `GetAttachmentResponse::deserialize` itself (in `stackslib/src/net/atlas/mod.rs`) to reject hex payloads whose decoded length exceeds a hard ceiling before allocating the `Vec<u8>`, to avoid unnecessary large allocations from untrusted input.

### Proof of Concept
Rust net test plan:
1. Configure two peers with `AtlasConfig { attachments_max_size: 1_048_576 (1 MiB), .. }`.
2. On the "attacker" peer, register a `GetAttachmentResponse` handler (or directly construct an `HttpResponsePayload`) whose `attachment.content` is e.g. 8 MiB of arbitrary bytes, with hash `H = Hash160::from_data(content)`.
3. On the "victim" peer, queue an `AttachmentInstance` with `content_hash = H` pointing at a block/tx the attacker is known to have served, so the `AttachmentsDownloader` issues a `GET /v2/attachments/H` request to the attacker.
4. Drive `AttachmentsDownloader::run` to completion using `AttachmentsBatchStateMachine::try_proceed` with the crafted response injected into `BatchedRequestsResult::succeeded`.
5. Assert that after `network.atlasdb.insert_instantiated_attachment(&attachment)` is invoked (via the `Done` branch in `download.rs` around line 161), `atlasdb.find_attachment(&H)` returns `Some(Attachment { content: <8 MiB> })` despite `content.len() as u32 > atlas_config.attachments_max_size`, proving the equality "stored attachment size <= attachments_max_size" is violated.

    pub fn insert_instantiated_attachment(
        &mut self,
        attachment: &Attachment,
    ) -> Result<(), db_error> {
        let now = util::get_epoch_time_secs() as i64;
        let tx = self.tx_begin()?;
        tx.execute(
            "INSERT OR REPLACE INTO attachments (hash, content, was_instantiated, created_at) VALUES (?, ?, 1, ?)",
            params![attachment.hash(), attachment.content, now],
        )?;
        tx.execute(
            "UPDATE attachment_instances SET is_available = 1 WHERE content_hash = ?1 AND status = ?2",
            params![attachment.hash(), AttachmentInstanceStatus::Checked],
        )?;
        tx.commit()?;
        Ok(())
    }
