### Title
Stale storage-stake check in transaction verification permanently blocks a user's own `DeleteAccount`/`DeleteKey` remediation, freezing account funds - ([File: runtime/runtime/src/verifier.rs])

### Summary
The reported bug class is: a privileged party raises a threshold parameter (`proposalThreshold`), and a check against that *new* threshold is applied to a user's remedial action (`cancel()`), even though the action itself does not depend on the new threshold — permanently blocking the user's ability to undo/exit their own prior state. The nearcore analog is `check_storage_stake`, gated on the protocol parameter `storage_amount_per_byte`, which is evaluated **before** a transaction's actions execute. This pre-execution check does not account for the fact that the very action being verified (`DeleteAccount` or `DeleteKey`) would reduce or eliminate the account's storage requirement, so a user whose account falls short of the *current* storage-stake requirement can never submit the transaction that would fix or exit that situation.

### Finding Description
`verify_and_charge_tx_ephemeral` runs `check_storage_stake(account, new_amount, config)` unconditionally at transaction-verification time, using the account's *pre-execution* `storage_usage` and balance, regardless of which actions the transaction contains: [1](#0-0) 

`check_storage_stake` requires `amount + locked >= storage_amount_per_byte * storage_usage`: [2](#0-1) 

If an account's balance is (or becomes, e.g. via slashing, or via a protocol-level increase of `storage_amount_per_byte`) insufficient to cover its *current* storage usage, this check fails with `LackBalanceForState` **before any action ever executes**. This includes a `DeleteAccount` transaction — whose entire purpose is to remove the account and refund the remaining balance to a beneficiary — and a `DeleteKey` transaction that would *reduce* `storage_usage` and could restore compliance. Neither of these remediating actions is special-cased in the pre-check.

`action_delete_account` itself has no storage-stake pre-condition; it simply pays out the remaining balance and removes the account: [3](#0-2) 

But that code path is never reached if `verify_and_charge_tx_ephemeral`'s pre-check already rejects the transaction. The project's own documentation confirms this is the observed behavior for the analogous case of a slashed account: [4](#0-3) 

This is structurally identical to the reported bug: a threshold-style check (`storage_amount_per_byte * storage_usage`) is evaluated against the *current* state and blocks the one action (`cancel()` / here, `DeleteAccount`) that the user needs in order to exit the problematic state, instead of evaluating the check against the *post-action* state.

### Impact Explanation
An account whose available balance (`amount + locked`) drops below `storage_amount_per_byte * storage_usage` — which can happen from slashing, or from a network-wide increase of the `storage_amount_per_byte` runtime parameter via protocol upgrade — becomes permanently unable to originate **any** transaction from itself, including the `DeleteAccount` transaction that would reclaim its remaining balance for a beneficiary, and the `DeleteKey` transaction that would reduce its own storage footprint back into compliance. The account's remaining native-token balance is effectively frozen and can only be rescued by a transfer of additional funds from a third-party account — the user has no self-service remediation path. This matches the "permanent freezing of funds" impact category.

### Likelihood Explanation
Triggering requires either (a) an account being slashed (already a recognized event in the protocol) or (b) a protocol-level increase of `storage_amount_per_byte` (a governance-controlled runtime parameter analogous to `proposalThreshold`) that pushes previously-compliant accounts below the requirement. Both are realistic, low-frequency but non-hypothetical events; the documentation for the slashing case explicitly acknowledges the "unusable including deletion" outcome as expected behavior rather than something the code guards against, indicating the underlying check was never designed to special-case remediating actions.

### Recommendation
When verifying a transaction whose action list contains `DeleteAccount` (and, more generally, actions that only reduce `storage_usage`, such as `DeleteKey`), either skip `check_storage_stake` at the pre-execution verification stage and defer to the post-execution check in `apply_action_receipt` (which already re-validates storage stake after the action runs, see `runtime/runtime/src/lib.rs:955-977`), or simulate the action's effect on `storage_usage`/`amount` before applying the check. This ensures a user retains a self-service path out of an under-collateralized account state, consistent with how `apply_action_receipt` already re-checks `check_storage_stake` post-execution rather than blocking eligible state-reducing actions up front.

### Proof of Concept
1. Create account `A` with balance `B` and `storage_usage = S` such that `B >= storage_amount_per_byte * S` (compliant).
2. Either slash `A` (reducing `locked`) or have the protocol raise `storage_amount_per_byte` via a protocol upgrade, such that now `B < storage_amount_per_byte * S`.
3. `A` signs a `DeleteAccount` transaction (or a `DeleteKey` transaction removing enough keys to bring `storage_usage` back into compliance) using its full-access key.
4. `verify_and_charge_tx_ephemeral` (`runtime/runtime/src/verifier.rs:332-343`) calls `check_storage_stake` on the account's *current* `storage_usage`/balance, which fails, returning `InvalidTxError::LackBalanceForState`.
5. The transaction is rejected at RPC/mempool validation and never reaches `action_delete_account`/`action_delete_key`, even though executing either action would have resolved (or been irrelevant to) the shortfall. Account `A`'s remaining balance stays frozen unless a third party sends it extra funds.

```rust
pub fn check_storage_stake(
    account: &Account,
    account_balance: Balance,
    runtime_config: &RuntimeConfig,
) -> Result<(), StorageStakingError> {
    let billable_storage_bytes = account.storage_usage();
    let required_amount = runtime_config
        .storage_amount_per_byte()
        .checked_mul(u128::from(billable_storage_bytes))
        .ok_or_else(|| {
            format!(
                "Account's billable storage usage {} overflows multiplication",
                billable_storage_bytes
            )
        })
        .map_err(StorageStakingError::StorageError)?;
    let available_amount = account_balance
        .checked_add(account.locked())
        .ok_or_else(|| {
            format!(
                "Account's amount {} and locked {} overflow addition",
                account.amount(),
                account.locked(),
            )
        })
        .map_err(StorageStakingError::StorageError)?;
    if available_amount >= required_amount {
        Ok(())
    } else {
        if is_zero_balance_account(account) {
            return Ok(());
        }
        Err(StorageStakingError::LackBalanceForStorageStaking(
            required_amount.checked_sub(available_amount).unwrap(),
        ))
    }
```
