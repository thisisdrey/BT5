### Title
Any zToken holder can front-run bad-debt socialization to redeem at the pre-write-down price, shifting the entire loss onto remaining depositors - (File: `mainnet/contracts/vault/v0-vault-stx.clar` / `v0-vault-sbtc.clar` / `v0-vault-ststx.clar` / `v0-vault-usdc.clar` / `v0-vault-usdh.clar` / `v0-vault-ststxbtc.clar`, function `socialize-debt`; triggered from `mainnet/contracts/market/v0-4-market.clar`, `liquidate` / `socialize-debt-asset`)

### Summary
When a position is fully liquidated but still has residual debt, `liquidate()` in `v0-4-market.clar` calls `socialize-debt-asset`, which calls the corresponding vault's `socialize-debt`. This function performs a discrete, instantaneous write-down of the vault's liquidity index (`lindex`), reducing the redemption value of every zToken in that vault in a single state transition rather than gradually via `accrue()`. Because this write-down is reachable through an ordinary, unprivileged `liquidate()` call (any user can be the liquidator, and bad-debt existence is publicly observable), any zToken holder can redeem their shares at the pre-write-down `lindex` immediately before (or atomically in front of) the socialization event, escaping their pro-rata share of the loss and forcing it entirely onto the depositors who remain in the vault.

This is precisely analogous to `FundingManager`'s `setVirtualCollateralSupply()` in the referenced Inverter report: a privileged/system code path performs a discontinuous adjustment to the value backing already-issued receipt tokens, while ordinary redeem/deposit paths continue to price shares off the *current* stored index. The difference from the original report is direction (here the state moves the price down, not up) and trigger (here it's reachable through `liquidate()`, an unprivileged entry point, rather than a DAO-only setter) — but the exploitable mechanic is the same: the index used to price zTokens changes discretely within one transaction sequence, and whoever acts on the *old* index just before the change is at an advantage relative to those who are still holding when the *new* index applies.

Concretely:
1. `market.liquidate()` computes `no-collateral-left` and, if true, folds over `fresh-debt-list` via `socialize-debt-asset`, which calls `vault-socialize-debt` → the vault's `socialize-debt`, writing `lindex` down. [2](#0-1) 
2. `redeem()` in the vault computes the payout using the *current* `lindex`/`total-assets` at call time (via `convert-to-assets-preview`/`total-assets-preview`), with no lock, cooldown, or queued withdrawal mechanism that would force a redeemer to also absorb losses that are "in flight."
3. Since bad debt is public information (any account's collateral/debt ratio can be read on-chain) and `liquidate()` is callable by any unprivileged principal, an attacker's own contract can, in one atomic transaction, (a) redeem their zTokens at the pre-write-down price, then (b) call `liquidate()` on the known bad-debt position to trigger `socialize-debt`. This requires no race against other transactions/mempool ordering — it is deterministic self-sequencing, strictly stronger than the sandwich pattern in the referenced report.
4. Alternatively, the same effect is achieved (with mempool front-running rather than atomic self-sequencing) by watching for a third party's pending `liquidate()` call and racing a `redeem()` ahead of it.

### Impact Explanation
The loss that `socialize-debt` distributes represents real, permanently unrecoverable bad debt (the vault's `assets` are insufficient to cover the corresponding debt). Normally this loss should be borne pro-rata by all zToken holders at the moment of socialization. By redeeming immediately beforehand, an attacker extracts their shares at full (pre-loss) value, leaving the same absolute loss to be absorbed by a strictly smaller remaining pool of zToken holders — i.e., the attacker's exit is subsidized directly by the other depositors' principal. This is a permanent, non-recoverable transfer of value from passive depositors to the attacker, which lands squarely in the Critical impact bucket: theft of user funds at rest (and, in the aggregate, it degrades the vault's actual backing ratio, worsening protocol insolvency for whoever remains).

### Likelihood Explanation
- Bad-debt state (collateral fully exhausted, residual debt) is visible on-chain before liquidation executes, so identifying the opportunity requires no privileged access or oracle manipulation.
- `liquidate()` is a permissionless entry point; nothing prevents the liquidator itself from being the party who benefits from redeeming first.
- The attack can be performed as a single atomic transaction (redeem, then trigger the liquidation) with a custom caller contract, eliminating MEV/mempool-ordering risk entirely.
- The only friction is `MINIMUM-LIQUIDITY` / withdrawal availability checks (`available-assets` must cover the redemption), which does not block this pattern in the general case since the vault typically holds idle liquidity for exactly this purpose.

### Recommendation
- Introduce a mechanism so that pending bad debt is reflected in redemption pricing before it is formally socialized (e.g., mark expected bad debt against `total-assets-preview` used by `convert-to-assets`/`redeem`, so redeemers cannot escape a loss that is already knowable/pending).
- Alternatively, require that liquidations which will trigger `socialize-debt` be processed with a mechanism that pro-rates the loss against the balance *at a snapshot prior to* the attacker's same-block redemption (e.g., disallow redemptions in the same block/transaction as a socialize-debt event for the affected vault, or apply the write-down before allowing further redemptions to clear in that block).
- Consider a withdrawal queue/cooldown for large redemptions in vaults with outstanding undercollateralized positions, so realized losses cannot be front-run by immediate exits.

### Proof of Concept
1. Alice (attacker) holds `Z` zUSDC shares in `v0-vault-usdc`, and separately monitors the market for a borrower `Bob` whose collateral has been fully liquidated by price movement, leaving residual (unsecured) USDC debt, i.e. `no-collateral-left` will evaluate true on the next `liquidate()` call.
2. Alice deploys a helper contract that in a single transaction:
   a. Calls `v0-vault-usdc.redeem(Z, min-out, alice)` — this reads the *current* `lindex`/`total-assets` (pre-write-down) via `total-assets-preview`/`convert-to-assets-preview` and pays Alice the full pre-loss value of her shares.
   b. Immediately calls `v0-4-market.liquidate(bob, sbtc, usdc, debtAmount, 0, none, none)`, which detects `no-collateral-left`, folds `socialize-debt-asset` over Bob's remaining debt, and calls `v0-vault-usdc.socialize-debt(scaled-amount)`, writing `lindex` down for all *remaining* USDC zToken holders. [3](#0-2) 
3. Because Alice already exited at step (a) before the write-down, she bears none of the loss; the entire bad-debt write-down is now spread across the smaller pool of remaining zUSDC holders, each of whom sees their redemption value drop below what it would have been had Alice's shares still been part of the base at the time of socialization.

(define-private (socialize-debt-asset
                (debt-entry { aid: uint, scaled: uint })
                (acc { borrower: principal, success: bool }))
  ;; Early return if previous socialization failed
  (if (not (get success acc))
      acc
      (let ((borrower (get borrower acc))
            (failed-status { borrower: borrower, success: false })
            (asset-id (get aid debt-entry))
            (scaled-debt (get scaled debt-entry)))

            ;; Socialize in vault - pass scaled directly to avoid rounding
            (unwrap! (vault-socialize-debt asset-id scaled-debt) failed-status)
            ;; Refresh cache with new indexes post-write-down (lindex decreased)
            (map-set index-cache
                     { timestamp: stacks-block-time, aid: asset-id }
                     (unwrap! (vault-accrue asset-id) failed-status))
            ;; Remove from obligation
            (unwrap! (contract-call? .v0-market-vault
                                      debt-remove-scaled
                                      borrower
                                      scaled-debt
                                      asset-id) failed-status)
          acc)
        ))
