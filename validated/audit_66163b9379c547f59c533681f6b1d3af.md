### Title
`add_tip` failure path permanently strands relayer-tip funds in unclaimable `LostTips` storage - ([File: bridges/snowbridge/pallets/system-v2/src/lib.rs])

### Summary
`pallet_snowbridge_system_v2::add_tip` accepts a tip amount forwarded (via XCM) from `pallet-snowbridge-system-frontend` on AssetHub, where the tipper's DOT has already been withdrawn/burned before the XCM message reaches BridgeHub. If the corresponding `InboundQueue::add_tip` / `OutboundQueue::add_tip` call fails (e.g. nonce already consumed, or pending order not found), the pallet does not revert or refund — it silently records the amount into a `LostTips<T>` storage map keyed by `sender` and returns `Ok(())`. No dispatchable, hook, or governance call anywhere in the codebase reads and clears `LostTips` to pay it back to the sender. This is the direct structural analog of the "payable function with no withdraw function" pattern from the `RCOrderbook.sol` report: value is accepted/consumed on the caller's behalf, the failure state is faithfully accounted for, but there is no corresponding recovery/withdraw path.

### Finding Description
`add_tip` is a public, permissionless-relative entrypoint (any `FrontendOrigin`-authorized caller, in practice any AssetHub user via `SnowbridgeSystemFrontend::add_tip`) that: [1](#0-0) 

```
pub fn add_tip(origin, sender, message_id, amount) -> DispatchResult {
    T::FrontendOrigin::ensure_origin(origin)?;
    let result = match message_id {
        Inbound(nonce) => InboundQueue::add_tip(nonce, amount),
        Outbound(nonce) => OutboundQueue::add_tip(nonce, amount),
    };
    if let Err(ref e) = result {
        LostTips::<T>::mutate(&sender, |lost_tip| {
            *lost_tip = lost_tip.saturating_add(amount);
        });
    }
    Self::deposit_event(Event::<T>::TipProcessed { sender, message_id, amount, success: result.is_ok() });
    Ok(())
}
```

Note that the function returns `Ok(())` even on failure — the caller-side `sender`'s tokens have already left their account on the AssetHub side (the frontend pallet withdraws/burns the DOT asset before dispatching the XCM to BridgeHub), so from the user's perspective the funds are gone the moment `add_tip` fails on BridgeHub. Confirmed failure cases include tipping an already-consumed inbound nonce and tipping a non-existent outbound order: [2](#0-1) [3](#0-2) 

A codebase-wide search for any consumer of `LostTips` (`claim_lost_tips`, `withdraw_lost`, `recover_lost`, any pallet call that reads and removes entries from `LostTips`) returns nothing beyond the `mutate` that inserts into it and the tests that assert it was incremented. There is no extrinsic, migration, or governance call that ever reads `LostTips::<T>::get(...)` and pays it out or removes it.

### Impact Explanation
Any unprivileged user who tips a message whose `nonce` is already consumed (a very plausible race — many relayers can race to add a tip on a nonce that gets processed concurrently) or references a pending order that has already been removed loses their tip amount permanently. The value is withdrawn on AssetHub (real funds leave the user), the failure is faithfully recorded in `LostTips`, but there is no code path in the pallet, the runtime, or any governance call that can move `LostTips` balances back to users. This matches the report's "public underpriced work / permanent user-fund lock" impact category: value is accepted through a public entrypoint and becomes permanently unrecoverable due to a missing withdrawal mechanism, requiring only an ordinary unprivileged relayer/user action (racing a tip against nonce consumption) — no malicious peer, validator, or governance actor is needed.

### Likelihood Explanation
Likelihood is moderate-to-high: nonces get consumed continuously as messages are relayed, and `add_tip` is meant to be used exactly in situations where a message is stuck/slow, i.e. right at the boundary where a race between "message finally processed" and "tip added" is likely. The tests in this repo (`add_tip_inbound_fails_when_nonce_is_consumed`, `add_tip_outbound_fails_when_pending_order_not_found`, `tip_to_invalid_nonce_is_added_to_lost_tips`) demonstrate that this failure path is a normal, expected occurrence, not an edge case requiring adversarial conditions.

### Recommendation
Add a dispatchable (e.g. `claim_lost_tip(origin, ...)`) that allows the `sender` recorded in `LostTips` to reclaim (or have refunded via XCM back to AssetHub) their stranded balance, and clear/decrement the corresponding `LostTips` entry atomically on payout. Alternatively, make `add_tip` fail the whole XCM/transaction path so the AssetHub-side withdrawal itself reverts instead of silently recording an unrecoverable liability on BridgeHub.

### Proof of Concept
1. On AssetHub, a user calls `SnowbridgeSystemFrontend::add_tip(origin, message_id, asset)`; the frontend pallet withdraws the DOT asset from the user and forwards an XCM to BridgeHub's `EthereumSystemV2::add_tip`.
2. Concurrently (or simply because processing is fast), the inbound message for that `nonce` is fully relayed and consumed before the tip XCM arrives.
3. `EthereumSystemV2::add_tip` on BridgeHub calls `InboundQueue::add_tip(nonce, amount)`, which returns `AddTipError::NonceConsumed` (per `bridges/snowbridge/pallets/inbound-queue-v2/src/lib.rs:248-259`).
4. `add_tip` in `system-v2` catches the error, adds `amount` to `LostTips::<T>::get(sender)`, emits `TipProcessed { success: false }`, and still returns `Ok(())`.
5. The user's DOT is gone (spent on AssetHub); `LostTips` on BridgeHub now holds the amount under the user's account key, but no extrinsic exists anywhere in the pallet or runtime to read that value back out to the user — the funds are permanently locked, reproducible exactly via the existing test `add_tip_inbound_fails_when_nonce_is_consumed` (`bridges/snowbridge/pallets/system-v2/src/tests.rs:197-219`), which only asserts the loss is recorded, never that it can be recovered.
