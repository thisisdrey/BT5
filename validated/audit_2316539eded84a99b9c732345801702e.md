## Title
`process_delivery_receipt` pays relayer reward and permanently settles the pending order without checking the `DeliveryReceipt.success` flag - (File: `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs`)

## Summary
`Pallet::process_delivery_receipt` in the Snowbridge V2 outbound queue pallet pays the relayer reward and removes the corresponding `PendingOrders` entry based solely on the existence of that entry for `receipt.nonce`, without ever inspecting `receipt.success`. Since `success` is decoded directly from the Ethereum `InboundMessageDispatched` event and is meant to reflect whether the dispatched message actually executed successfully on Ethereum, a message that failed on the destination (Ethereum) side is treated identically to a successfully delivered one: the relayer is rewarded and the order is irreversibly deleted.

## Finding Description
The extrinsic `submit_delivery_receipt` verifies the event log via `T::Verifier::verify` and decodes it into a `DeliveryReceipt` (including `success`) via `DeliveryReceipt::try_from(&event.event_log)`, then calls `Self::process_delivery_receipt(relayer, receipt)`: [1](#0-0) 

`process_delivery_receipt` only checks `receipt.gateway` against `T::GatewayAddress`, resolves the reward account, looks up the order by `receipt.nonce`, and — if found — unconditionally registers the reward and removes the order: [2](#0-1) 

`DeliveryReceipt::success` is populated directly from the real Ethereum `InboundMessageDispatched(nonce, topic, success, reward_address)` event log field, so it faithfully reflects whether the Gateway's dispatch to its destination actually succeeded. A grep across the pallet crate confirms `receipt.success` (or `.success` on the receipt) is never referenced anywhere in `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs`, meaning the only gating condition for reward payout and order settlement is "does a `PendingOrders` entry exist for this nonce" — a coarse check that does not distinguish a legitimately completed dispatch from one whose execution reverted on Ethereum.

## Impact Explanation
This satisfies the "duplicate settlement or payout" / incorrect fund-release class of impact under the Polkadot SDK Impact Gate: relayer rewards, funded via `T::RewardPayment::register_reward` (backed by `pallet-bridge-relayers`), are paid out for messages whose Ethereum-side execution failed, and the `PendingOrders` entry is permanently deleted regardless of `success`. Because `MessageDelivered` is emitted unconditionally and the order is removed with no retry mechanism, a failed dispatch is irreversibly and incorrectly marked as fully settled, and reward funds are drained from the shared reward pool for work that did not achieve its intended effect.

## Likelihood Explanation
`submit_delivery_receipt` is a plain signed extrinsic open to any account that can produce a valid Ethereum proof; no privileged, governance, or malicious-collusion assumption is required. A destination-side revert (out-of-gas, insufficient allowance, reentrancy guard, etc.) on Ethereum is a normal, expected occurrence in cross-chain messaging, not a contrived edge case, so any relayer submitting a genuine, verifier-passing receipt for such a message triggers the flaw with no additional effort. The existing tests (`submit_delivery_receipt_succeeds_after_unhalt`, `invalid_nonce_for_delivery_receipt_fails`) only construct receipts with `success: true` and never assert reward-payout behavior when `success: false`, confirming the gap is untested as well as unimplemented.

## Recommendation
In `process_delivery_receipt`, branch on `receipt.success` before paying the reward and/or removing the order:
- If `receipt.success == false`, skip `T::RewardPayment::register_reward` (or apply a reduced/zero reward) and emit a distinct event (e.g., `MessageDeliveryFailed { nonce }`) instead of `MessageDelivered`.
- Consider retaining failed-delivery records (or requiring a separate retry/governance path) rather than unconditionally deleting the `PendingOrders` entry, so failed dispatches are not silently finalized as successful settlements.

## Proof of Concept
1. A message is queued via `do_process_message`, creating a `PendingOrders` entry with a non-zero `fee` for some `nonce`. [3](#0-2) 
2. On Ethereum, the Gateway's dispatch to the final destination reverts, so the Gateway emits `InboundMessageDispatched(nonce, topic, success=false, reward_address)`.
3. A relayer obtains a valid proof for this real event and calls `submit_delivery_receipt`; verification passes and the log decodes into `DeliveryReceipt { success: false, .. }`.
4. `process_delivery_receipt` finds the `PendingOrders` entry for `nonce`, calls `T::RewardPayment::register_reward(&reward_account, .., order.fee)` unconditionally, removes the order, and emits `MessageDelivered`. [4](#0-3) 
5. A unit test can be added (mirroring `submit_delivery_receipt_succeeds_after_unhalt` in `bridges/snowbridge/pallets/outbound-queue-v2/src/test.rs`) that inserts a `PendingOrder`, submits a `DeliveryReceipt` with `success: false`, and asserts that no `RewardRegistered`/reward registration occurs and that the order is not silently finalized — this assertion currently fails against the existing implementation, demonstrating the bug.

		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}
