### Title
Missing `chain_id` in `SignerCapabilityOfferProofChallengeV2` Enables Cross-Chain Replay of Signer Capability Delegation — (`File: aptos-move/framework/aptos-framework/sources/account/account.move`)

---

### Summary

`SignerCapabilityOfferProofChallengeV2`, the proof-of-knowledge struct signed by an account owner when delegating signer capability via `offer_signer_capability`, omits `chain_id` from its signed fields. The analogous struct `RotationCapabilityOfferProofChallengeV2` explicitly includes `chain_id` and its own comment states this field was added to "prevent replaying the challenge message." The omission in the signer-capability path means a valid proof-of-knowledge signature produced on one Aptos network (e.g., testnet) can be replayed on another (e.g., mainnet) by a malicious contract that obtains Alice's signer during a call, granting an attacker permanent signer capability over Alice's mainnet account.

---

### Finding Description

**Struct definitions (lines 148–159):**

`RotationCapabilityOfferProofChallengeV2` (line 148) includes `chain_id`:
```move
struct RotationCapabilityOfferProofChallengeV2 has drop {
    chain_id: u8,          // ← present; comment says this prevents replay
    sequence_number: u64,
    source_address: address,
    recipient_address: address,
}
```

`SignerCapabilityOfferProofChallengeV2` (line 155) omits `chain_id`:
```move
struct SignerCapabilityOfferProofChallengeV2 has copy, drop {
    sequence_number: u64,
    source_address: address,
    recipient_address: address,   // ← NO chain_id
}
```

**Usage in `offer_signer_capability` (lines 966–972):**
```move
let proof_challenge = SignerCapabilityOfferProofChallengeV2 {
    sequence_number: get_sequence_number(source_address),
    source_address,
    recipient_address,
};
verify_signed_message(
    source_address, account_scheme, account_public_key_bytes,
    signer_capability_sig_bytes, proof_challenge);
```

`verify_signed_message` calls `ed25519::signature_verify_strict_t`, which prepends only the Move `TypeInfo` (module address + name + struct name) — identical on every Aptos network — before verifying. No chain-specific byte is ever mixed into the signed payload.

**Cross-chain replay attack path:**

1. Alice signs a `SignerCapabilityOfferProofChallengeV2` on testnet: `{seq=N, source=Alice, recipient=Attacker}`. The signature is observable on-chain.
2. Alice's mainnet account also has `sequence_number = N` (common for accounts with symmetric histories, or for fresh accounts).
3. Attacker deploys a malicious contract on mainnet and tricks Alice into calling it (e.g., a DeFi interaction).
4. Inside the call, the malicious contract invokes `offer_signer_capability` using Alice's live `&signer` (available because Alice is the caller) and supplies the testnet `signer_capability_sig_bytes`.
5. `verify_signed_message` reconstructs `{seq=N, source=Alice, recipient=Attacker}` — identical bytes to the testnet message — and the signature verifies successfully.
6. `account_resource.signer_capability_offer.for.swap_or_fill(recipient_address)` records the attacker as the authorized signer delegate.
7. Attacker calls `create_authorized_signer(&attacker_signer, alice_address)` to obtain a live `signer` for Alice's mainnet account.
8. Attacker drains Alice's APT, modifies her resources, or performs any privileged action.

This is the exact TOCTOU scenario the extra proof-of-knowledge signature was designed to prevent — but the missing `chain_id` breaks the domain separation between networks.

---

### Impact Explanation

`create_authorized_signer` returns a full `signer` for Alice's address. Any module accepting a `&signer` — including `aptos_account::transfer`, `coin::withdraw`, staking operations, and arbitrary Move entry functions — will treat it as Alice's own signer. This constitutes **direct, unauthorized theft of APT and fungible assets** and **unauthorized state transitions** on Alice's account, matching the allowed impact gate.

---

### Likelihood Explanation

- The attacker must observe a valid testnet (or devnet) `signer_capability_sig_bytes` for Alice with the attacker as `recipient_address`.
- Alice's mainnet sequence number must equal the testnet sequence number at signing time — plausible for accounts with symmetric histories or at sequence 0.
- Alice must be induced to call a malicious contract on mainnet (social engineering / malicious DeFi contract).
- The window is permanent: the testnet signature never expires and can be replayed any time the sequence number matches.

Likelihood is **low-to-medium** given the multi-step preconditions, but the impact is **critical** (full account takeover).

---

### Recommendation

Add `chain_id` to `SignerCapabilityOfferProofChallengeV2`, mirroring the fix already applied to `RotationCapabilityOfferProofChallengeV2`:

```move
struct SignerCapabilityOfferProofChallengeV2 has copy, drop {
    chain_id: u8,          // add this field
    sequence_number: u64,
    source_address: address,
    recipient_address: address,
}
```

And populate it in `offer_signer_capability`:
```move
let proof_challenge = SignerCapabilityOfferProofChallengeV2 {
    chain_id: chain_id::get(),   // add this line
    sequence_number: get_sequence_number(source_address),
    source_address,
    recipient_address,
};
```

This is a breaking change to the signed message format; existing off-chain signers must regenerate signatures.

    public fun verify_signed_message<T: drop>(
        account: address,
        account_scheme: u8,
        account_public_key: vector<u8>,
        signed_message_bytes: vector<u8>,
        message: T,
    ) acquires Account {
        let auth_key = get_authentication_key(account);
        // Verify that the `SignerCapabilityOfferProofChallengeV2` has the right information and is signed by the account owner's key
        if (account_scheme == ED25519_SCHEME) {
            let pubkey = ed25519::new_unvalidated_public_key_from_bytes(account_public_key);
            let expected_auth_key = ed25519::unvalidated_public_key_to_authentication_key(&pubkey);
            assert!(
                auth_key == expected_auth_key,
                error::invalid_argument(EWRONG_CURRENT_PUBLIC_KEY),
            );

            let signer_capability_sig = ed25519::new_signature_from_bytes(signed_message_bytes);
            assert!(
                ed25519::signature_verify_strict_t(&signer_capability_sig, &pubkey, message),
                error::invalid_argument(EINVALID_PROOF_OF_KNOWLEDGE),
            );
        } else if (account_scheme == MULTI_ED25519_SCHEME) {
            let pubkey = multi_ed25519::new_unvalidated_public_key_from_bytes(account_public_key);
            let expected_auth_key = multi_ed25519::unvalidated_public_key_to_authentication_key(&pubkey);
            assert!(
                auth_key == expected_auth_key,
                error::invalid_argument(EWRONG_CURRENT_PUBLIC_KEY),
            );

            let signer_capability_sig = multi_ed25519::new_signature_from_bytes(signed_message_bytes);
            assert!(
                multi_ed25519::signature_verify_strict_t(&signer_capability_sig, &pubkey, message),
                error::invalid_argument(EINVALID_PROOF_OF_KNOWLEDGE),
            );
        } else {
            abort error::invalid_argument(EINVALID_SCHEME)
        };
    }
