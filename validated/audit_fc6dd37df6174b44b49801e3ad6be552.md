## Title
Digest Collision in `RelayPayload` for `StackerDBPushChunkData` Breaks Relay Deduplication Invariant — ([File: stackslib/src/net/relay.rs])

### Summary
The `RelayPayload` trait explicitly documents the invariant `m1.get_digest() == m2.get_digest() --> m1 == m2` [1](#0-0) . The implementation for `StackerDBPushChunkData` violates this invariant by hashing only the raw chunk bytes (`chunk_data.data_hash()`), omitting `slot_id`, `slot_version`, and `contract_id` [2](#0-1) . This is the direct analog of the reported bug class: distinct "actions" (here, distinct StackerDB chunk pushes for different slots/versions/contracts) can collide onto the same identifier, exactly like distinct Governor actions collapsing to the same Timelock queue-entry hash.

### Finding Description
`get_digest()` for `StackerDBPushChunkData` is defined as:
```rust
impl RelayPayload for StackerDBPushChunkData {
    fn get_digest(&self) -> Sha512Trunc256Sum {
        self.chunk_data.data_hash()
    }
    ...
}
``` [2](#0-1) 

`data_hash()` is simply `Sha512Trunc256Sum::from_data(&self.data)` [3](#0-2) , i.e., a hash of the chunk payload bytes only. It does not fold in `slot_id`, `slot_version`, or the `contract_id`/`rc_consensus_hash` that identify *which* StackerDB and slot the push targets.

This digest is used by `RelayerStats::add_relayed_message` and `RelayerStats::count_relay_dups` to track, per-neighbor, which messages have already been seen [4](#0-3) , and those counts feed directly into `get_inbound_relay_rankings`, which computes the probability distribution used to select which inbound peers receive a broadcast [5](#0-4) . This ranking is consumed by `sample_broadcast_peers` when dispatching `StackerDBPushChunk` broadcasts [6](#0-5) [7](#0-6) .

Because the digest ignores `slot_id`/`slot_version`/`contract_id`, an attacker (any unprivileged peer able to push a StackerDB chunk with attacker-controlled payload bytes, e.g. into a slot it legitimately owns) can craft push messages whose `chunk_data.data` bytes are identical to a legitimate signer's chunk payload for a *different* slot/version/DB, deliberately colliding digests. Repeatedly relaying such colliding messages inflates the "duplicate count" attributed to the *real* signer chunk's digest for arbitrary neighbors, skewing `get_inbound_relay_rankings` and biasing which inbound peers are selected to receive the real broadcast.

### Impact Explanation
This degrades propagation of legitimate StackerDB chunks (which, in Nakamoto, carry signer/miner consensus-relevant messages) by corrupting the peer-selection heuristic that is supposed to prioritize genuinely novel data to peers that haven't seen it. It does not directly cause storage corruption (chunk storage/signature checks in `try_replace_chunk`/`validate_received_chunk` are unaffected and correctly implemented) [8](#0-7) [9](#0-8) , so this is best characterized as a network propagation/relay-ranking integrity issue rather than an authentication bypass or a state-corruption bug.

### Likelihood Explanation
Exploitation requires an attacker to be able to push a chunk (or arrange for a colliding chunk to be relayed) whose bytes match a target chunk's payload for some other slot — feasible since any owner of a slot in the same or another replicated StackerDB can pick data bytes freely, and the digest computation is a straightforward oversight in a documented equality contract.

### Recommendation
Include `slot_id`, `slot_version`, and `contract_id` (and ideally `rc_consensus_hash`) in the digest computed by `StackerDBPushChunkData::get_digest()`, e.g. hash the full consensus-serialized `StackerDBPushChunkData` (as is already done for `BlocksAvailableData::get_digest()` at [10](#0-9) ) instead of only `chunk_data.data_hash()`.

### Proof of Concept
1. Peer A owns slot 0 (version 5) in StackerDB `SP...contract-1` and slot 1 (version 1) in StackerDB `SP...contract-2`.
2. Peer A signs and pushes a legitimate `StackerDBPushChunkData{contract_id: contract-1, slot_id: 0, slot_version: 5, data: X}`.
3. Attacker (owning slot 1 in `contract-2`) signs and broadcasts `StackerDBPushChunkData{contract_id: contract-2, slot_id: 1, slot_version: 1, data: X}` (same bytes `X`) repeatedly to various neighbors.
4. `RelayerStats::add_relayed_message`/`count_relay_dups` treat both messages as identical (`get_digest()` returns `Sha512Trunc256Sum::from_data(X)` for both), inflating dup counts against the digest of `X`.
5. When Peer A's node later calls `sample_broadcast_peers` for the *real* `contract-1` chunk, `get_inbound_relay_rankings` uses the poisoned dup counts for digest `hash(X)`, deprioritizing/skewing relay to legitimate inbound neighbors that never actually saw the real `contract-1`/slot 0 chunk.

                    None => {
                        break;

                    relayed.pop_front();
                } else {
                    break;
                }

            relayed.push_back((now, h));

        }

        let mut ret = HashMap::new();

                        *count += 1;
                    } else {
                        ret.insert((*nk).clone(), 1);
                    }
                }
            }
        }

    pub fn get_inbound_relay_rankings<R: RelayPayload>(
        &self,
        neighbors: &[NeighborKey],
        msg: &R,
        warmup_threshold: usize,
    ) -> HashMap<NeighborKey, usize> {
        let mut dup_counts = self.count_relay_dups(msg);
        let mut dup_total = dup_counts.values().sum::<usize>();

        if dup_total < warmup_threshold {
            // don't make inferences on small samples for total duplicates.
            // just assume uniform distribution.
            dup_total = warmup_threshold;
            dup_counts.clear();
        }

        let mut ret = HashMap::new();

        for nk in neighbors.iter() {
            let dup_count = *(dup_counts.get(nk).unwrap_or(&0));

            assert!(dup_total >= dup_count);

            // every peer should have a non-zero chance, hence the + 1
            ret.insert((*nk).clone(), dup_total - dup_count + 1);
        }

        ret
    }
