### Title
Anyone can permanently destroy `RewardsDistributor` emissions by forcing reward-index truncation via repeated `updateBeforeMintOrBurn` calls - (contracts/RewardsDistributor.sol)

### Summary
`RewardsDistributor._calculateTokenIndex` computes the per-period reward ratio with `wadDiv(_tokensAccrued, _totalSupply)` and then advances `tokenStates[token_].timestamp` to `block.timestamp` even when the division rounds down to `0`. Because `updateBeforeMintOrBurn` is permissionless ("This function also may be called by anyone"), any EOA can call it every block; each call discards the rewards accrued since the last update whenever `speed * deltaTime < totalSupply`. Repeating this continuously can cause all emissions for a token to be lost — the index never increases and the unallocated rewards remain stranded in the distributor forever.

### Finding Description
- `claimRewards`, `updateBeforeMintOrBurn`, and `updateBeforeTransfer` all funnel into `_updateTokenIndex` → `_calculateTokenIndex` (contracts/RewardsDistributor.sol:197-212, 261-282).
- `_tokensAccrued = deltaTimestamps * speed`; `_ratio = _tokensAccrued.wadDiv(_totalSupply)` uses `WadRayMath.wadDiv` which rounds down. When `_tokensAccrued < _totalSupply`, `_ratio` truncates toward a small value — and when `_tokensAccrued * 1e18 < _totalSupply`, it truncates to exactly `0`.
- Critically, `_newTimestamp = block.timestamp` is stored even when `_ratio == 0` (`_newIndex = index + 0`), so the elapsed window's accrued rewards are consumed without ever entering the index — they are permanently undistributable.
- `updateBeforeMintOrBurn(IERC20 token_, address account_)` is an unauthenticated external function guarded only by `tokenStates[token_].index > 0` (line 175-180). An attacker passes themselves as `account_` (their accrual is a no-op since their balance/accrued is unaffected) solely to advance the index timestamp.
- This mirrors the Babel bug class: emissions allocated to a debt/deposit token are not distributed to holders; a portion — here, potentially all of it, block after block — is effectively lost.

### Impact Explanation
Reward tokens emitted at `tokenSpeeds[token_]` per second are funded to the distributor to be paid to DebtToken/DepositToken holders. If an attacker keeps the per-update accrued amount below the truncation threshold (or generally forces maximum rounding loss on every update), the index stays flat while time is consumed, so `tokensAccruedOf` never credits those emissions to anyone. The yield is permanently frozen in the contract — matching the accepted impact class "theft/freezing of unclaimed yield". The same loss also occurs organically (no attacker) whenever `totalSupply == 0` during a window while speed > 0, e.g. after full repayment, since the timestamp still advances.

### Likelihood Explanation
- Cost to attack: one cheap external call per block; no capital, no privileged role, no oracle manipulation required.
- Feasibility depends on magnitude: loss per call requires `speed * deltaT < totalSupply` for full truncation; given large token supplies this holds for modest speeds and short deltas. Even when not fully truncating, every call sacrifices up to ~`totalSupply` wei of accrued reward, and calls can be made arbitrarily often.
- Deployed RewardsDistributor (mainnet/optimism deployments) exposes exactly these functions and the index/timestamp behavior is identical.

### Recommendation
Track undistributed remainder: accrue `pendingRewards += deltaTimestamps * speed` and only consume it into the index when it can be divided without (or with bounded) truncation, or accumulate the fractional remainder into the next window (e.g. keep `remainder = _tokensAccrued - _ratio * _totalSupply` and add it next update). Alternatively, only advance `timestamp` when `_ratio > 0`, and restrict `updateBeforeMintOrBurn` to the token contracts.

### Proof of Concept
Hardhat/foundry fork on deployed `RewardsDistributor`:
1. Deploy (or fork) a Pool + DebtToken + RewardsDistributor; governor sets `updateTokenSpeed(debtToken, speed)` so `tokenStates.index = INITIAL_INDEX`.
2. User opens a position so `debtToken.totalSupply() = S` and `balanceOf(user) = S`.
3. Attacker EOA calls `rewardDistributor.updateBeforeMintOrBurn(debtToken, attacker)` every block such that `speed * dt < S` (choose `speed`, e.g. `S = 1e24`, `speed = 1e18`, `dt = 1s` → `_tokensAccrued = 1e18`, `wadDiv(1e18, 1e24)` uses `(1e18 * 1e18) / 1e24 = 1e12`, small; for full zero choose `speed * dt * 1e18 < S`).
4. After N blocks: `tokenStates[debtToken].timestamp == latest`, `index` barely moved or unchanged; `claimable(user) << N * speed` — most/all emitted rewards never accrued to any account and are stuck in the distributor.
5. Baseline without attacker calls shows the user accruing ~`N * speed`; the delta equals the lost rewards.

Analogous to the `test/RewardDistributor.test.ts` harness, this can also be demonstrated with mocked `totalSupply`/`balanceOf` and `increaseTimeOfNextBlock` between spam calls.
