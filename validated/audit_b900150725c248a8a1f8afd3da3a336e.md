### Title
Silent integrity-check bypass when `remote_file_urls`/`remote_file_integrity` keys are mismatched in `http_archive` overlay downloads - (File: tools/build_defs/repo/utils.bzl)

### Summary
`http_archive`'s overlay-file feature lets a rule (or, in Bzlmod, a module-extension implementation) declare a map of relative paths to mirror URLs (`remote_file_urls`) and a corresponding map of paths to expected integrity checksums (`remote_file_integrity`). The documentation states the two maps' keys should correspond, but `download_remote_files()` never verifies this and instead silently substitutes an empty integrity value for any path missing from `remote_file_integrity`, which disables checksum verification for that specific download.

### Finding Description
`download_remote_files()` iterates `ctx.attr.remote_file_urls.items()` and, for each path, looks up the expected integrity with a permissive default: [1](#0-0) 

```
integrity = ctx.attr.remote_file_integrity.get(path, ""),
```

This is analogous to the M-10 pattern of iterating one array/collection while implicitly assuming a second, parallel collection has a matching entry, without checking that assumption. Here the "parallel array" relationship is expressed as two dictionaries that are documented to have matching keys: [2](#0-1) 

Nowhere in `_http_archive_impl` (which unconditionally calls `download_remote_files(ctx)` after the main archive download) or in `download_remote_files` itself is there a `fail()`/validation step confirming `remote_file_urls.keys()` and `remote_file_integrity.keys()` match: [3](#0-2) 

Passing `integrity = ""` to `ctx.download()` is Bazel's documented way of saying "no checksum verification requested" (this is exactly the same code path used when a repository rule author intentionally omits `sha256`/`integrity` for convenience during development). Consequently, if a path key exists in `remote_file_urls` without a matching entry in `remote_file_integrity` — whether from an authoring bug in a module extension, or because the key set is computed dynamically from attacker-influenced data (e.g., paths derived from files/listings fetched from a registry or a dependency's build logic) — the file at that path is downloaded and overlaid into the repository (as a symlink source, potentially a `BUILD`/`REPO.bazel` file) from a URL under attacker/mirror control with zero content verification, and no error or warning is raised.

This directly parallels the audited Solidity bug: multiple parallel input collections are consumed under an implicit assumption of correspondence; a mismatch does not raise an error, it silently degrades the operation (there, ignoring extra values; here, disabling the verification a security-conscious integrity pin was supposed to enforce).

### Impact Explanation
`remote_file_urls`/`remote_file_integrity` exist specifically to let `http_archive` overlay untrusted-origin files (frequently `BUILD.bazel`/`REPO.bazel` build files) onto an otherwise-verified archive, with the integrity map serving as the trust anchor for that specific mechanism. A missing key silently drops that trust anchor for the affected file instead of failing the build, so an attacker who controls (or can MITM/compromise) the mirror serving one of these URLs can inject arbitrary content into the extracted repository undetected — including a malicious `BUILD.bazel` overlay that changes build semantics for consumers of that `http_archive`. Because `http_archive` overlay attributes are commonly generated programmatically by module extensions (Bzlmod), a single key-set computation bug (or attacker-influenced key derivation) silently converts a "pinned, hermetic" download into an unpinned, non-hermetic one.

### Likelihood Explanation
This requires only that `remote_file_urls` contain a key absent from `remote_file_integrity` — no privileged access is needed, and normal `.string_dict`/`.string_list_dict` Starlark attributes do not enforce key-set equality by construction. Extension authors relying on `download_remote_files`'s implicit "keys should match" contract (as documented) have no compiler/runtime signal when they violate it; the failure mode is silent (empty-string integrity, treated by `ctx.download` as "unpinned") rather than loud, making it easy to ship and hard to notice via code review or CI (the build still succeeds).

### Recommendation
In `download_remote_files()` (tools/build_defs/repo/utils.bzl), before downloading, validate that `ctx.attr.remote_file_urls.keys()` and `ctx.attr.remote_file_integrity.keys()` are equal (or, at minimum, that every key in `remote_file_urls` has a non-empty corresponding entry in `remote_file_integrity`), and `fail()` with a clear diagnostic otherwise — mirroring the fix pattern used for the analogous Solidity M-10 report (explicit equal-length/matching-keys check instead of implicit indexing/lookup with a silent default).

### Proof of Concept
A `src/test/shell/bazel/external_remote_file_test.sh`-style shell integration test (that file already exercises `remote_file_urls`/`remote_file_integrity`, see [4](#0-3) ) can demonstrate the bypass:

1. Start a local HTTP server serving two files: a benign `BUILD.bazel` overlay and a malicious/tampered replacement at the same path.
2. Define an `http_archive` with:
   - `remote_file_urls = {"BUILD.bazel": ["http://127.0.0.1:<port>/tampered_BUILD"]}`
   - `remote_file_integrity = {}` (i.e., missing the `"BUILD.bazel"` key — simulating an extension bug or attacker-controlled key mismatch)
3. Run `bazel build @repo//...`.
4. Observe that the build **succeeds** and the tampered `BUILD.bazel` content is materialized in the repository with no integrity error, whereas supplying a wrong/incorrect `sha256`/`integrity` value for a *matching* key would correctly fail the build — demonstrating that a missing key silently disables the check rather than being treated as a configuration/integrity error.

Note: I was not able to execute this test in this environment (no filesystem/build execution access), so the reproduction is described conceptually based on the code paths cited above; running it would require a Devin session with build/test execution capability.

```text
def _http_archive_impl(ctx):
    """Implementation of the http_archive rule."""
    if ctx.attr.build_file and ctx.attr.build_file_content:
        fail("Only one of build_file and build_file_content can be provided.")

    if ctx.attr.strip_prefix and ctx.attr.strip_components:
        fail("Only one of strip_prefix and strip_components can be provided.")

    source_urls = _get_source_urls(ctx)
    download_info = ctx.download_and_extract(
        source_urls,
        ctx.attr.add_prefix,
        ctx.attr.sha256,
        ctx.attr.type,
        ctx.attr.strip_prefix,
        strip_components = ctx.attr.strip_components,
        canonical_id = ctx.attr.canonical_id or get_default_canonical_id(ctx, source_urls),
        auth = get_auth(ctx, source_urls),
        integrity = ctx.attr.integrity,
    )
    workspace_and_buildfile(ctx)

    remote_files_info = download_remote_files(ctx)
    remote_patches_info = patch(ctx)
    symlink_files(ctx)

    integrity = struct(
        archive = download_info.integrity,
        remote_files = {path: info.integrity for path, info in remote_files_info.items()},
        remote_patches = {url: info.integrity for url, info in remote_patches_info.items()},
    )

    return _update_http_archive_integrity_attrs(ctx, _http_archive_attrs, integrity)
```
