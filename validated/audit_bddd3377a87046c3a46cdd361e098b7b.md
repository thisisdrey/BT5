### Title
Unbounded HTTP response buffering in the signer's StackerDB client leads to remote memory-exhaustion DoS - (File: libsigner/src/http.rs)

### Summary
`run_http_request` in `libsigner/src/http.rs` reads an entire HTTP response from the node's StackerDB RPC endpoint into an unbounded `Vec<u8>` via `sock.read_to_end(&mut buf)` before any length checking is performed. This is the same defect class as the `centra` advisory (GHSA-v6cj-r88p-92rm): buffering a network response into memory with no size cap, when not in "stream" mode.

### Finding Description
`StackerDBSession::rpc_request` (`libsigner/src/session.rs`) calls `run_http_request(sock, ...)` for every signer→node StackerDB RPC call (`list_chunks`, `get_chunks`, `get_latest_chunks`, `put_chunk`). [1](#0-0) 

`run_http_request` writes the request, then does:
```rust
let mut buf = vec![];
sock.read_to_end(&mut buf)?;
```
before calling `decode_http_response`/`decode_http_body`, which are the only points that ever look at declared `Content-Length` or enforce `MAX_MESSAGE_LEN`. [2](#0-1) 

Unlike the equivalent server-side/StacksHttp parsing path in `stackslib`, which bounds preamble size (`HTTP_PREAMBLE_MAX_ENCODED_SIZE`) and payload size against `MAX_MESSAGE_LEN` *before* buffering the full body (e.g. `stackslib/src/net/httpcore.rs` `read_preamble`/`payload_len`, and `HttpChunkedTransferReaderState::read_chunk_bytes` which enforces `max_size` while streaming), the signer's client-side `run_http_request` performs no such bound: it accumulates the connection's entire byte stream into `buf` regardless of `Content-Length`, `Transfer-Encoding`, or any global maximum. [3](#0-2) [4](#0-3) 

The only mitigation present is a socket read/write timeout set on the `TcpStream` in `connect_or_reconnect`: [5](#0-4) 
That timeout bounds *idle* time between successful reads, not total bytes received. A peer that keeps sending data steadily (even slowly) never triggers the per-read timeout, so `buf` can grow without bound, holding a `Content-Length` header well below reality or omitting it altogether while streaming an effectively unlimited body.

### Impact Explanation
Because `StackerDBSession` connects over plain TCP (no TLS is set up in `connect_or_reconnect`), any party able to respond as, or intercept/inject into, the connection between the signer and the configured node host can return an oversized/never-ending HTTP response. The signer process will buffer that entire stream into heap memory with no upper bound, leading to unbounded memory growth and eventual OOM/crash of the signer — a remote, unauthenticated denial-of-service against the signer process, which is a privileged and security-critical component of the network.

### Likelihood Explanation
Exploitation only requires the ability to act as (or spoof/MITM) the endpoint the signer's `StackerDBSession` connects to and to keep a socket open while trickling bytes fast enough to avoid the read timeout. No authentication, valid signature, or special protocol knowledge is required — any responder to the signer's plaintext HTTP request can trigger it.

### Recommendation
Bound the response read in `run_http_request` (and `decode_http_body`'s non-chunked branch) the same way `stackslib`'s HTTP layer and `HttpChunkedTransferReaderState` already do for the node-side channel: use a `BoundReader` (already available in `stacks-common/src/util/retry.rs`) capped at `MAX_MESSAGE_LEN` (or a StackerDB-appropriate chunk-size limit) around `sock` before calling `read_to_end`, and reject/abort the connection once the cap is exceeded instead of buffering indefinitely.

### Proof of Concept
1. Stand up a TCP listener masquerading as (or MITM-ing) the node host that `StackerDBSession` is configured to talk to.
2. On accept, reply with a valid-looking `HTTP/1.1 200 OK` status line and headers, then continuously stream body bytes (e.g. writing a few KB every time the transmit buffer drains, indefinitely), never closing the connection and never sending a terminating chunk / matching a small `Content-Length`.
3. Have the signer invoke any `SignerSession` method (e.g. `list_chunks()` / `get_chunks()`), which drives `run_http_request`'s `sock.read_to_end(&mut buf)`.
4. Observe the signer process's memory usage grow without bound as long as the attacker keeps the connection open and keeps sending data within the configured `socket_timeout` between reads, eventually causing an OOM kill/crash of the signer.
