### Title
Division-by-zero DoS in vault `accrue()` treasury-LP mint calculation freezes yield accrual - (File: `mainnet/contracts/vault/v0-vault-stx.clar` and identical logic in the other `v0-vault-*.clar` contracts)

### Summary
`accrue()`, the public per-block interest-accrual entry point of each Zest lending vault, computes a treasury-LP mint amount using `mul-div-down` with a divisor of `(- (total-assets-preview) reserve-inc)`. `mul-div-down` is implemented as a raw `(/ (* x y) z)` with no zero-divisor guard, mirroring the reported EraVM `mul/div` finding where the divisor-can-be-zero case is not handled. When `total-assets-preview` equals `reserve-inc`, the division reverts the entire transaction, permanently bricking `accrue()` (and every function that calls it) for that vault.

### Finding Description
`mul-div-down` is defined identically across all vaults as:
```
(define-private (mul-div-down (x uint) (y uint) (z uint))
  (/ (* x y) z))
``` [1](#0-0) 

This is invoked from the public `accrue()` function to compute the treasury LP mint:
```
(reserve-inc (mul-div-down debt-delta (var-get fee-reserve) BPS))
(treasury-lp (if (> reserve-inc u0) (mul-div-down reserve-inc (total-supply) (- (total-assets-preview) reserve-inc)) u0))
``` [2](#0-1) 

The divisor is `(- (total-assets-preview) reserve-inc)`. If `total-assets-preview` (current vault assets plus preview interest) equals `reserve-inc` (the fee-reserve share of newly accrued debt), the subtraction yields `u0`, and `mul-div-down` performs a division by zero. In Clarity, dividing by zero aborts the entire transaction with a runtime error — there is no zero-divisor short-circuit, unlike the `total-assets`/`total-supply` conversions elsewhere in the same file which explicitly guard against `u0` divisors (`convert-to-shares-preview` / `convert-to-assets-preview`):
```
(define-private (convert-to-shares-preview (amount uint))
  (let ((ta (total-assets-preview)) (ts (total-supply-preview)))
    (if (is-eq ts u0) amount
        (if (is-eq ta u0) u0 (mul-div-down amount ts ta)))))
``` [3](#0-2) 

No equivalent guard exists for the `(- (total-assets-preview) reserve-inc)` divisor in `accrue()`'s treasury-LP branch, or in the identical `calc-treasury-lp-preview` helper:
```
(reserve-inc (mul-div-down debt-delta (var-get fee-reserve) BPS))
(ta-preview (total-assets-preview)))
(if (> reserve-inc u0)
    (mul-div-down reserve-inc (total-supply) (- ta-preview reserve-inc))
    u0))
``` [4](#0-3) 

This same pattern is duplicated verbatim across every vault: `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`. [5](#0-4) [6](#0-5) 

`accrue()` is a public, unpermissioned function callable by any principal, and is also called internally by every borrow/repay/deposit/withdraw path (e.g. `system-borrow` calls `(try! (accrue))` first): [7](#0-6) [8](#0-7) 

Since the trigger only requires `total-assets-preview == reserve-inc` at the moment `accrue` runs (i.e. the vault's total assets happen to numerically equal the freshly-computed fee-reserve increment — a state reachable simply by ordinary interest accrual arithmetic over time as debt/assets/fee-reserve parameters evolve, with no attacker privilege needed to construct it, only correctly timed unprivileged calls to accrue-triggering entry points such as deposit/borrow/repay), any principal that lands on this state — or that merely calls `accrue`/`borrow`/`repay`/`deposit`/`withdraw` while this condition holds — causes their transaction, and every subsequent transaction touching the vault, to revert.

### Impact Explanation
Once the zero-divisor condition is hit, `accrue()` reverts unconditionally, and since virtually every state-changing vault entrypoint (`deposit`, `withdraw`, `system-borrow`, `system-repay`, etc.) calls `accrue()` first, the entire vault becomes permanently unusable: no further deposits, withdrawals, borrows, repayments, or interest/index updates can occur. This constitutes permanent freezing of funds (principal and unclaimed yield) at rest in the affected vault, since assets already deposited/borrowed cannot be moved through any of the bricked entrypoints.

### Likelihood Explanation
The condition depends only on protocol-internal state (`total-assets-preview` vs. `reserve-inc`) reachable purely through normal interest accrual over time with no attacker privilege required — likelihood is a function of parameter/timing coincidence rather than of any special access, and once hit, the effect is deterministic and permanent for the vault.

### Recommendation
Guard the divisor before calling `mul-div-down` in `accrue()` and `calc-treasury-lp-preview`: if `(- (total-assets-preview) reserve-inc)` (or `(- ta-preview reserve-inc)`) is `u0`, skip the treasury-LP mint (treat as `u0`) instead of invoking `mul-div-down`, matching the explicit `is-eq ... u0` guards already used in `convert-to-shares-preview`/`convert-to-assets-preview`. More generally, `mul-div-down`/`mul-div-up` should never be called with an unchecked, dynamically-computed divisor.

### Proof of Concept
1. Vault accrues interest over time such that `debt-delta` and `fee-reserve` produce `reserve-inc = mul-div-down(debt-delta, fee-reserve, BPS) > 0`.
2. At the same block, `total-assets-preview` (current `assets` + `interest`) numerically equals `reserve-inc`.
3. Any principal calls `accrue()` directly, or calls `deposit`/`withdraw`/`system-borrow`/`system-repay`, which internally invoke `accrue()`.
4. `accrue()` evaluates `(mul-div-down reserve-inc (total-supply) (- (total-assets-preview) reserve-inc))`, the divisor equals `u0`, and Clarity's `/` runtime errors, aborting the transaction.
5. Because `index`/`lindex` were never updated (the `var-set` calls happen after the failed `let` binding, so the whole function aborts before any state changes), the vault permanently reverts on this same computation on every subsequent call, freezing all deposits, withdrawals, and lending operations in that vault.
