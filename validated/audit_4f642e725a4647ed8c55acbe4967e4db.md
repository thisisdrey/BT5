## Title
Unbounded iteration over all registered witnesses in `MaintenanceManager.doMaintenance()` causes maintenance-cycle block processing to slow linearly with witness count, which any account can permissionlessly inflate - (File: `consensus/src/main/java/org/tron/consensus/dpos/MaintenanceManager.java`)

### Summary
`MaintenanceManager.doMaintenance()` is the java-tron analog of the reported "slow ABCI method" pattern: it performs multiple full scans over the entire witness set every maintenance cycle, and the witness set can be grown without any hard cap by any account willing to pay `AccountUpgradeCost`. This mirrors the Allora bug class where a function iterated all "active" entities in a hot block-application path while the entity count was attacker-influenceable.

### Finding Description
`doMaintenance()` runs at least three unbounded, full-collection iterations over `consensusDelegate.getAllWitnesses()` (all registered witnesses, not just the active/standby subset): [1](#0-0) [2](#0-1) [3](#0-2) 

`doMaintenance()` is invoked from `applyBlock(BlockCapsule)` whenever the maintenance-time boundary is crossed - i.e. inside the consensus block-application path that every block-push goes through: [4](#0-3) 

This is called from `Manager.processBlock()`, the core block-application routine (`consensus.applyBlock(block)`), which is the java-tron equivalent of `EndBlocker`: [5](#0-4) 

Crucially, the number of witnesses that `getAllWitnesses()` returns is not fixed to the 27 active SRs or the 127 standby SRs - it is every account that has ever executed `WitnessCreateContract`, which any account can broadcast permissionlessly as long as its balance covers `AccountUpgradeCost`: [6](#0-5) [7](#0-6) 

There is no upper bound on the total number of witness registrations enforced anywhere in validate()/execute() - only a fixed TRX cost and the requirement that the address hasn't registered before. `countVote()` inside the same maintenance pass also does a full, unbounded scan of `VotesStore` (one entry per voting account since the last cycle) with per-entry nested `forEach` work: [8](#0-7) 

### Impact Explanation
Since witness registration is permissionless and only economically (not structurally) bounded, an attacker with sufficient capital can register an arbitrarily large number of witnesses. Each additional witness adds constant work to three separate full-collection passes inside `doMaintenance()`, which executes synchronously inside block application at every maintenance-time rollover. As the witness set grows, maintenance-cycle blocks take proportionally longer to process across all full nodes and SRs simultaneously (since maintenance triggers deterministically from `nextMaintenanceTime`), directly slowing block production and potentially pushing block processing time past the block interval, which can stall/halt the chain - the same "computational cost scaling with attacker-controlled state size in a mandatory block-application hot path" root cause as the referenced report.

### Likelihood Explanation
Medium-to-High: the only barrier is TRX cost per witness registration (`AccountUpgradeCost`, historically ~9999 TRX), which is within reach of a moderately funded attacker for a state-inflation campaign, and the effect (slower maintenance-cycle block application) manifests deterministically and network-wide once the witness set is large, with no existing pagination, cap, or amortization in `doMaintenance()`.

### Recommendation
Cap the number of witnesses processed by `doMaintenance()`'s reward/vote-count loops to the active + standby set (bounded by `WITNESS_STANDBY_LENGTH`) instead of `getAllWitnesses()`, or introduce a hard registration cap / pagination with amortized processing across multiple maintenance cycles, similar to the recommendation in the referenced report to bound iteration cost independent of attacker-controlled collection growth.

### Proof of Concept
1. An attacker funds N accounts, each with balance ≥ `AccountUpgradeCost`.
2. Each account broadcasts a `WitnessCreateContract` transaction; `WitnessCreateActuator.validate()`/`execute()` accepts all of them since there is no cap on total witness count, only a per-address "already exists" check.
3. At the next maintenance-time boundary, `MaintenanceManager.applyBlock()` calls `doMaintenance()`, which now performs 3 full O(N) passes (`accumulateWitnessVi`, `newWitnessAddressList` population, and brokerage/vote snapshotting) over all N attacker-created witnesses in addition to the legitimate ones.
4. As N grows (bounded only by attacker capital, not protocol logic), the maintenance-cycle block's processing time in `Manager.processBlock()` grows linearly, degrading block production for every node in the network at that height.

  private Map<ByteString, Long> countVote(VotesStore votesStore) {
    final Map<ByteString, Long> countWitness = Maps.newHashMap();
    Iterator<Entry<byte[], VotesCapsule>> dbIterator = votesStore.iterator();
    long sizeCount = 0;
    while (dbIterator.hasNext()) {
      Entry<byte[], VotesCapsule> next = dbIterator.next();
      VotesCapsule votes = next.getValue();
      votes.getOldVotes().forEach(vote -> {
        ByteString voteAddress = vote.getVoteAddress();
        long voteCount = vote.getVoteCount();
        if (countWitness.containsKey(voteAddress)) {
          countWitness.put(voteAddress, countWitness.get(voteAddress) - voteCount);
        } else {
          countWitness.put(voteAddress, -voteCount);
        }
      });
      votes.getNewVotes().forEach(vote -> {
        ByteString voteAddress = vote.getVoteAddress();
        long voteCount = vote.getVoteCount();
        if (countWitness.containsKey(voteAddress)) {
          countWitness.put(voteAddress, countWitness.get(voteAddress) + voteCount);
        } else {
          countWitness.put(voteAddress, voteCount);
        }
      });
      sizeCount++;
      votesStore.delete(next.getKey());
    }
    logger.info("There is {} new votes in this epoch", sizeCount);
    return countWitness;
  }

  private void createWitness(final WitnessCreateContract witnessCreateContract)
      throws BalanceInsufficientException {
    AccountStore accountStore = chainBaseManager.getAccountStore();
    DynamicPropertiesStore dynamicStore = chainBaseManager.getDynamicPropertiesStore();
    WitnessStore witnessStore = chainBaseManager.getWitnessStore();
    //Create Witness by witnessCreateContract
    final WitnessCapsule witnessCapsule = new WitnessCapsule(
        witnessCreateContract.getOwnerAddress(),
        0,
        witnessCreateContract.getUrl().toStringUtf8());

    logger.debug("createWitness,address[{}]", witnessCapsule.createReadableString());
    witnessStore.put(witnessCapsule.createDbKey(), witnessCapsule);
    AccountCapsule accountCapsule = accountStore
        .get(witnessCapsule.createDbKey());
    accountCapsule.setIsWitness(true);
    if (dynamicStore.getAllowMultiSign() == 1) {
      accountCapsule.setDefaultWitnessPermission(dynamicStore);
    }
    accountStore.put(accountCapsule.createDbKey(), accountCapsule);
    long cost = dynamicStore.getAccountUpgradeCost();
    adjustBalance(accountStore, witnessCreateContract.getOwnerAddress().toByteArray(), -cost);
    if (dynamicStore.supportBlackHoleOptimization()) {
      dynamicStore.burnTrx(cost);
    } else {
      adjustBalance(accountStore, accountStore.getBlackhole(), +cost);
    }
    dynamicStore.addTotalCreateWitnessCost(cost);
  }
