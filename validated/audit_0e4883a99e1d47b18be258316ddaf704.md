## Analysis

The Kairos bug is a class of **"stale signed message binds to a numeric ID whose associated content is not fixed at signing time, so a signature that was invalid when created can later become valid against unrelated, unintended content once that ID is populated."**

The closest reachable analog in java-tron is in the governance/proposal subsystem, where `ProposalId` is a monotonically increasing counter assigned by `ProposalCreateActuator`, and a witness's `ProposalApproveContract` is validated purely against the *current* value of that counter rather than against a proposal that existed (or matched specific content) when the witness signed the transaction.

### Root cause

`ProposalCreateActuator.execute` assigns proposal IDs sequentially from `DynamicPropertiesStore.getLatestProposalNum()`: [1](#0-0) 

`ProposalApproveActuator.validate` only checks that `contract.getProposalId() <= latestProposalNum` and that the proposal at that ID has not expired/cancelled — it never binds the approval to the specific content/proposer of the proposal that existed at signing time: [2](#0-1) 

A transaction is a bare signed protobuf; nothing prevents a witness (or their signing tooling) from constructing and signing a `ProposalApproveContract` for a `proposal_id` that does **not exist yet** (`proposal_id > latestProposalNum`). Such a transaction would be rejected today (`InvalidTranche`-equivalent: `"[Proposal id"+...+"] not exist"`), exactly mirroring the Kairos `offerDigest`/`checkOfferArg` mismatch where the check exists but only at execution/broadcast time, not at signature-creation time.

### Same structural flaw as the reported bug

- Kairos: `offer.tranche` is embedded in the signed digest with no bound check; validity is only checked later against `proto.nbOfTranches`/`proto.tranche[...]`, which is mutable admin state.
- java-tron: `ProposalApproveContract.proposal_id` is embedded in the signed transaction hash with no bound check against the *content* of the proposal; validity is only checked later against `DynamicPropertiesStore.getLatestProposalNum()` and the `ProposalStore`, which are mutable, protocol-driven counters advanced by any account calling `ProposalCreateContract`.

If a witness pre-signs (or a client library caches/queues) a `ProposalApproveContract` for an ID that is currently one-past-the-end, and that transaction is broadcast later (within its expiration window) after unrelated `ProposalCreateContract` calls have advanced `latestProposalNum` to cover that ID, the approval will silently attach to whatever proposal ended up occupying that slot — not the proposal the witness intended to review and approve. Because committee/witness approvals feed directly into `ProposalController.processProposal`'s `hasMostApprovals` quorum check that mutates protocol-wide dynamic parameters (energy price, bandwidth price, maintenance interval, etc.), this can result in an unintended vote counting toward passing a governance change the signer never reviewed. [3](#0-2) 

## Title
Committee/witness `ProposalApproveContract` binds only to a mutable sequential `proposal_id`, letting a stale signature attach to an unintended future proposal - (File: actuator/src/main/java/org/tron/core/actuator/ProposalApproveActuator.java)

### Summary
`ProposalApproveContract` transactions are validated solely by comparing the signed `proposal_id` against the live `DynamicPropertiesStore.getLatestProposalNum()` counter and proposal state at broadcast time, with no binding to the actual proposal content that existed when the transaction was signed.

### Finding Description
`ProposalCreateActuator.execute` assigns IDs as `latestProposalNum + 1`, a value that grows every time any account submits a valid `ProposalCreateContract`. [4](#0-3) 

`ProposalApproveActuator.validate` accepts the contract as long as `proposal_id <= latestProposalNum`, and looks up whatever proposal is currently stored at that ID key — it performs no check that this is the same proposal (proposer, parameters) the signer intended when they created the signature. [2](#0-1) 

A witness can construct and sign an approval transaction for a `proposal_id` that does not exist yet (greater than the current `latestProposalNum`); this transaction is currently rejected by `validate()`, but nothing stops it from being held (in a client queue, mempool retry logic, or delayed broadcast) until an unrelated `ProposalCreateContract` from any account advances the counter to that ID before the original transaction expires. Once that happens, the previously-invalid, already-signed approval transaction becomes valid and is applied to whatever proposal now occupies that ID slot.

### Impact Explanation
Approvals feed directly into `ProposalController.processProposal`, which checks `hasMostApprovals` against active witnesses and, if satisfied, calls `setDynamicParameters` to mutate protocol-wide dynamic properties (fees, time intervals, resource pricing, etc.). [5](#0-4) 
A witness's vote intended for one governance change can be silently re-attributed to a different proposal, contributing to an unintended quorum and enabling protocol parameter changes without genuine committee consent — a governance-integrity compromise reachable purely by broadcasting a previously-signed, self-contained transaction.

### Likelihood Explanation
Requires a witness-signed transaction (a permissioned but still ordinary broadcastable contract type) to be created for a not-yet-existing ID and later broadcast within its expiration window after the counter advances to that value; proposal creation is infrequent in practice, which narrows but does not eliminate the exploitation window, especially with automated/queued signing tooling or delayed relaying of pre-signed governance transactions.

### Recommendation
Bind the approval (and delete) signature to the actual proposal content rather than only its ordinal ID — e.g., include a hash of the proposal's `proposer_address`/`parameters`/`create_time` in the signed `ProposalApproveContract`/`ProposalDeleteContract`, and have `ProposalApproveActuator.validate`/`ProposalDeleteActuator.validate` verify that this hash matches the currently stored `ProposalCapsule` before accepting the approval/deletion.

### Proof of Concept
1. Witness W observes `latestProposalNum == N`. W signs a `ProposalApproveContract` with `proposal_id = N+1`, expecting it to approve a specific proposal they plan to review once created; broadcast is deferred (e.g., cached by tooling).
2. Before W's transaction expires, any account submits an unrelated `ProposalCreateContract`, advancing `latestProposalNum` to `N+1` via `ProposalCreateActuator.execute` (`id = latestProposalNum + 1`). [4](#0-3) 
3. W's originally-invalid transaction is now broadcast/re-broadcast. `ProposalApproveActuator.validate` sees `proposal_id (N+1) <= latestProposalNum (N+1)`, finds the (unrelated) proposal at that ID, and accepts the approval. [2](#0-1) 
4. The unrelated proposal now carries an approval vote from W that W never actually reviewed, potentially contributing to `hasMostApprovals` quorum in `ProposalController.processProposal` and triggering a parameter change W did not consent to.
