### Title
Unchecked value accumulator in `Operator.execute` can overflow, letting calls spend more ETH than `msg.value` supplied - (File: contracts/Operator.sol)

### Summary
`Operator.execute` accumulates `calls_[i].value` inside an `unchecked` block and then enforces `msg.value == _sumOfValues`. Because the addition wraps modulo 2^256, an attacker can craft a call list whose individual `value` fields sum to `2^256 + msg.value`, satisfying the final check while the contract actually dispatches far more ETH than the caller sent. This is the direct analog of the libebml integer overflow (CVE-2023-52339): a size/amount arithmetic wraps, and the downstream operation ("write" of ETH value) exceeds the bounds that the check was meant to enforce. [1](#0-0) 

### Finding Description
In `execute`, each call's `value` is added to `_sumOfValues` in `unchecked` arithmetic, then `_call.target.functionCallWithValue(_call.callData, _value)` forwards `_value` wei per call from the contract's balance. The only integrity check is `require(msg.value == _sumOfValues)`. With two calls of value `2^255` each, `_sumOfValues` wraps to `0`, so `msg.value = 0` passes while the calls attempt to send `2^256 - 1` wei total. Any ETH balance held by `Operator` at execution time is drained to attacker-chosen targets.

Note the practical constraint: `functionCallWithValue` will revert if the contract lacks the balance, so this is exploitable exactly when `Operator` holds ETH — which happens when (a) a previous `execute` batch contained a target call that refunded ETH (e.g., failed WETH unwraps, protocols refunding unused value), (b) users overpaid on an earlier batch, or (c) ETH was sent/donated to the contract. In all these cases the ETH is user funds temporarily or permanently held by the contract, and this overflow lets anyone steal it.

### Impact Explanation
Direct theft of native tokens held by `Operator`. The integrity invariant "`msg.value` equals the total value forwarded" is broken; the contract pays out more than it received, and the difference comes from pre-existing (user) funds in the contract. No privileged role is needed — `execute` is a public entry point and `nonReentrant`/`setMsgSender` do not constrain the call values.

### Likelihood Explanation
Exploitation requires `Operator` to hold a nonzero ETH balance, which is conditional — the contract does not custody funds by design. However, refund-returning calls and accidental transfers make a transient or stuck balance realistic. Severity is Medium: impact is theft of funds but only up to the contract's incidental balance, not protocol TVL.

### Recommendation
Remove `unchecked` around `_sumOfValues += _value` so the addition reverts on overflow, or accumulate per-call and check `address(this).balance >= running sum` semantics. With Solidity 0.8.24, plain checked addition is sufficient.

### Proof of Concept
Foundry sketch (fork/mainnet-config not required since `Operator` is standalone):

```solidity
// SPDX-License-Identifier: MIT
pragma solidity 0.8.24;

import "forge-std/Test.sol";
import {Operator} from "contracts/Operator.sol";
import {IOperator} from "contracts/interfaces/IOperator.sol";

contract OperatorOverflowTest is Test {
    Operator operator;
    address attacker = address(0xA11CE);
    address sink = address(0xB0B);

    receive() external payable {}

    function setUp() public {
        operator = new Operator();
        // Simulate ETH stuck in Operator (user refund/overpay/donation)
        vm.deal(address(operator), 1 ether);
    }

    function testValueOverflowDrain() public {
        // sink contract that just receives ETH
        IOperator.Call[] memory calls = new IOperator.Call[](2);
        calls[0] = IOperator.Call({
            target: sink,
            callData: "",
            value: 1 ether
        });
        // second value wraps the sum: 1 ether + (2^256 - 1 ether) == 0
        calls[1] = IOperator.Call({
            target: sink,
            callData: "",
            value: type(uint256).max - 1 ether + 1
        });

        vm.prank(attacker);
        // msg.value = 0 passes because _sumOfValues wrapped to 0
        operator.execute(calls);

        assertEq(sink.balance, 1 ether);          // drained from Operator
        assertEq(address(operator).balance, 0);   // stuck ETH stolen
    }
}
```

The second call sends 0 wei after wrap-adjustment but the sum check sees `0`; equivalently, with a larger contract balance the attacker can send `msg.value + k * 2^256` total value. Any `k > 0` combination that fits in the contract's balance succeeds while paying only `msg.value`.
