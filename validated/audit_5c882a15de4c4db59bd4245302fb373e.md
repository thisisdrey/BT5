### Title
Buffered-receipt congestion gas can be recomputed with a different `RuntimeConfig` than was used when the receipt was buffered, desyncing `CongestionInfo.buffered_receipts_gas` from the actual buffer contents - ([File: runtime/runtime/src/congestion_control.rs])

### Summary
This is the closest structural analog to the HMX bug: an aggregate/cumulative counter (`CongestionInfo::buffered_receipts_gas`, analogous to `GlobalState.reserveValueE30`) is incremented at push time using a per-item value computed from the *current* `RuntimeConfig`, but for raw (non-`StateStoredReceipt`) receipts the same per-item value is *recomputed from scratch* using whatever `RuntimeConfig` is active at pop time via `receipt_congestion_gas`/`compute_receipt_congestion_gas`. If the config values feeding that computation (e.g. `fees.fee(ActionCosts::new_action_receipt)`, action costs used by `total_prepaid_exec_fees`/`total_prepaid_send_fees`) change between the push and the pop (i.e., across a protocol upgrade while the receipt sits in the buffer), the value subtracted from the cumulative counter will not equal the value that was added, exactly mirroring the HMX flaw where `_marketConfig` changes caused the incremental delta and the fully-recomputed value to diverge. ### Finding Description
`buffer_receipt` computes `gas = compute_receipt_congestion_gas(&receipt, &apply_state.config)` at the time the receipt enters the outgoing buffer and adds it to `own_congestion_info.buffered_receipts_gas` via `add_buffered_receipt_gas` [3](#0-2) . Later, when the buffer is drained in `forward_from_buffer_to_shard`, the gas for that same receipt is obtained via `receipt_congestion_gas(&receipt, &apply_state.config)` [1](#0-0) , and subtracted with `remove_buffered_receipt_gas` [4](#0-3) . For the `StateStoredReceipt` variant this recomputation is avoided by reading `metadata().congestion_gas`, a value frozen at push time — the code comment explicitly states this design intent ("the precomputed congestion cost is read back rather than recomputed"). For the plain `ReceiptOrStateStoredReceipt::Receipt` variant, however, the gas is *recomputed from the live `RuntimeConfig`* rather than read back, via `compute_receipt_congestion_gas` → `action_receipt_congestion_gas`, which depends on `config.fees.fee(ActionCosts::new_action_receipt)` and the prepaid exec/send fee tables [5](#0-4) . The docstring on `compute_receipt_congestion_gas` even warns "The calculation is part of protocol and should only be modified with a protocol upgrade," acknowledging that this function's output is version-dependent [6](#0-5) . If a receipt sits in the outgoing buffer across a protocol upgrade that changes any fee/cost parameter feeding this calculation, the amount added to `buffered_receipts_gas` at push time and the amount subtracted at pop time will differ — exactly the HMX pattern of an aggregate updated proportionally/incrementally at one point in time and a per-item value fully recomputed with new config at another.

### Impact Explanation
I was **not able to confirm** that the raw-`Receipt` (non-`StateStoredReceipt`) code path is actually reachable on the current protocol version. `use_state_stored_receipt` is a runtime-config flag (`core/parameters/src/config.rs`, `parameters.yaml`), and if it is always `true` for all protocol versions this binary supports (`MIN_SUPPORTED_PROTOCOL_VERSION`), the legacy recompute path is dead code and the desync cannot occur in practice. I could not verify the flag's value/history within the available tool budget. If the flag can be `false` (or was `false` historically and receipts could still be draining from a pre-upgrade buffer state), the consequence would be: `remove_buffered_receipt_gas` uses `checked_sub` and returns `RuntimeError::UnexpectedIntegerOverflow` on underflow rather than panicking silently, but this error propagates as a hard runtime error during chunk application, which is a shard-halting condition rather than silent fund loss/theft.

### Likelihood Explanation
Low-to-uncertain. This would require (a) the `use_state_stored_receipt` flag to be `false` for at least one reachable protocol version with receipts genuinely buffered across a boundary, and (b) a protocol upgrade that changes the specific fee parameters used in `action_receipt_congestion_gas`. Given the code comments indicate the `StateStoredReceipt` metadata mechanism was specifically introduced to freeze this value and avoid exactly this class of bug, this looks like a deliberately-fixed hazard rather than a live, exploitable vulnerability in the current codebase, but I could not fully confirm the flag's current/historical settings to rule out any residual gap.

### Recommendation
Confirm whether `use_state_stored_receipt` is unconditionally `true` for all supported protocol versions; if any reachable configuration or historical migration path allows a raw `Receipt` to remain in the outgoing buffer across a config/fee change, ensure the congestion gas is always captured/frozen at push time (as `StateStoredReceipt` already does) rather than recomputed from the live `RuntimeConfig` at pop time.

### Proof of Concept
Not constructed — I could not verify reachability of the raw-`Receipt` congestion-gas recompute path under the currently supported protocol version range within the tool budget available. A concrete PoC would require confirming `use_state_stored_receipt`'s value across supported protocol versions and identifying a specific fee-config field change between two supported versions that alters `action_receipt_congestion_gas`'s output for an already-buffered receipt.

pub(crate) fn receipt_congestion_gas(
    receipt: &ReceiptOrStateStoredReceipt,
    config: &RuntimeConfig,

    match receipt {
        ReceiptOrStateStoredReceipt::Receipt(receipt) => {

        }
        ReceiptOrStateStoredReceipt::StateStoredReceipt(receipt) => {
            Ok(receipt.metadata().congestion_gas)

/// The calculation is part of protocol and should only be modified with a
/// protocol upgrade.
pub(crate) fn compute_receipt_congestion_gas(
    receipt: &Receipt,
    config: &RuntimeConfig,
) -> Result<Gas, IntegerOverflowError> {
    match receipt.versioned_receipt() {
        VersionedReceiptEnum::Action(action_receipt) => {
            // account for gas guaranteed to be used for executing the receipts
            action_receipt_congestion_gas(receipt, config, action_receipt.into())
        }
        VersionedReceiptEnum::Data(_data_receipt) => {
            // Data receipts themselves don't cost gas to execute, their cost is
            // burnt at creation. What we should count, is the gas of the
            // postponed action receipt. But looking that up would require
            // reading the postponed receipt from the trie.
            // Thus, the congestion control MVP does not account for data
            // receipts or postponed receipts.
            Ok(Gas::ZERO)
        }
        VersionedReceiptEnum::PromiseYield(_) => {
            // The congestion control MVP does not account for yielding a
            // promise. Yielded promises are confined to a single account, hence
            // they never cross the shard boundaries. This makes it irrelevant
            // for the congestion MVP, which only counts gas in the outgoing
            // buffers and delayed receipts queue.
            Ok(Gas::ZERO)
        }
        VersionedReceiptEnum::PromiseResume(_) => {
            // The congestion control MVP does not account for resuming a promise.
            // Unlike `PromiseYield`, it is possible that a promise-resume ends
            // up in the delayed receipts queue.
            // But similar to a data receipt, it would be difficult to find the cost
            // of it without expensive state lookups.
            Ok(Gas::ZERO)
        }
        VersionedReceiptEnum::GlobalContractDistribution(_) => Ok(Gas::ZERO),
    }
}

fn action_receipt_congestion_gas(
    receipt: &Receipt,
    config: &RuntimeConfig,
    action_receipt: VersionedActionReceipt,
) -> Result<Gas, IntegerOverflowError> {
    let prepaid_exec_gas =
        total_prepaid_exec_fees(config, &action_receipt.actions(), receipt.receiver_id())?
            .gas
            .checked_add(config.fees.fee(ActionCosts::new_action_receipt).exec_fee().gas)
            .ok_or(IntegerOverflowError)?;
    // account for gas guaranteed to be used for creating new receipts
    let prepaid_send_cost = total_prepaid_send_fees(config, &action_receipt.actions())?;
    let prepaid_gas = prepaid_exec_gas.checked_add_result(prepaid_send_cost.gas)?;

    // account for gas potentially used for dynamic execution
    let gas_attached_to_fns = total_prepaid_gas(&action_receipt.actions())?;
    let gas = gas_attached_to_fns.checked_add_result(prepaid_gas)?;

    Ok(gas)
}
