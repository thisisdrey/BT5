The strongest analog is in `third_party/ijar/zip.cc`'s `InputZipFile::ProcessCentralDirEntry`, which parses attacker-controlled ZIP central directory records used by Bazel's own JAR/interface-jar tooling (ijar) when processing `.jar` archives (e.g., from `http_jar`/`http_archive` downloads or dependency jars).

### Title
Unvalidated ZIP central-directory length fields cause out-of-bounds pointer advance in `InputZipFile::ProcessCentralDirEntry` - (File: `third_party/ijar/zip.cc`)

### Summary
`ProcessCentralDirEntry` reads `file_name_length`, `extra_field_length`, and `file_comment_length` directly from an attacker-supplied central directory record and immediately advances the cursor `p` by those amounts, with no equivalent to the `EnsureRemaining()` bounds check used elsewhere in the same file [1](#0-0) .

### Finding Description
Contrast this with `ProcessLocalFileEntry`, which explicitly calls `EnsureRemaining(file_name_length_, "file_name")` and `EnsureRemaining(extra_field_length_, "extra_field")` before advancing the pointer past attacker-controlled length fields [2](#0-1) . `ProcessCentralDirEntry`, however, reads the three 16-bit length fields (`file_name_length`, `extra_field_length`, `file_comment_length`) from the central directory header and unconditionally advances `p` past them and iterates the "extra field" chain (`while (extra_p != p)`) using attacker-controlled `data_size` values, without ever checking these lengths against the remaining size of the mapped input file [3](#0-2) . This mirrors the CVE-2016-7917 bug class: a length field taken from untrusted input is trusted to compute a subsequent read/skip offset without validating it against the actual buffer bounds, which can walk `p` past the end of the mapped file (an `mmap`'d region), causing an out-of-bounds read and, since `ProcessNext`/`CalculateOutputLength` loop by repeatedly calling `ProcessCentralDirEntry` until a signature check fails [4](#0-3) , a comment/extra field length crafted to keep landing on non-matching-but-plausible bytes could also cause pathological over-reads through file-backed memory.

### Impact Explanation
This function is reachable by ijar/singlejar tooling when processing ZIP/JAR files that originate from external, potentially attacker-controlled sources (e.g., a hostile HTTP server serving content for `http_jar`/`http_archive`, or a malicious dependency jar). An out-of-bounds read on the mmap'd file can leak adjacent process memory contents into decompressed output or crash the Bazel-invoked tool (`ijar`/`singlejar`) processing the archive.

### Likelihood Explanation
However, this is a native C++ parsing bug reachable only via crafted ZIP central-directory records; it requires the file to be processed as a JAR/ZIP by ijar or singlejar (build-action-time processing), not the checksum-verified download/extraction path itself — the sha256/integrity check on `http_archive`/`http_jar` (visible in `tools/build_defs/repo/http.bzl`) governs the raw bytes fetched but does not prevent malformed internal ZIP structure from being fed to this parser once the pinned bytes match. I was unable to fully trace whether `EndOfCentralDirectoryRecord`/central directory size bounds computed earlier in `zip.cc` (`FindZip64CentralDirectory`, around lines 659-700) constrain `central_dir_current_` such that this scenario is unreachable in practice; that would require deeper tracing of `Open()` beyond what I could verify with available context.

### Recommendation
Add bounds checks (analogous to `EnsureRemaining`) in `ProcessCentralDirEntry` before advancing `p` by `file_name_length`, `extra_field_length`, and `file_comment_length`, and before iterating the extra-field chain, rejecting the archive if `p` would go beyond the mapped buffer end (comparable to `end_of_central_dir` / mapped file length).

### Proof of Concept
Not fully constructed — a reproducible JUnit/shell test would need to build a malicious ZIP with a central directory record whose `file_name_length`/`extra_field_length`/`comment_length` exceed the remaining archive bytes, and feed it through `ijar`'s extraction path or `AddJar` in singlejar, then verify a crash/OOB read is triggered rather than a clean error. I could not confirm this reproduction end-to-end within the available tool budget.

**Note:** I was not able to fully verify whether upstream size/offset validation before this code path (e.g., zip64 EOCD checks) already prevents `p` from being advanced beyond mapped memory in all cases — this uncertainty should be resolved with a live test/build environment (e.g., a Devin session) before treating this as a confirmed exploitable finding.
