Based on my research, I found a concrete analog: `EXTCODECOPY` allocates a `lengthData`-sized byte array in `OperationActions.extCodeCopyAction` *before* the gas metering / memory-size cap in `EnergyCost.getExtCodeCopyCost` bounds the memory-extend to `MEM_LIMIT` (3 MB). ### Title
Unbounded heap allocation from attacker-controlled EXTCODECOPY length before memory-limit check - (File: `actuator/src/main/java/org/tron/core/vm/OperationActions.java`)

### Summary
`OperationActions.extCodeCopyAction` pops `lengthData` directly from the EVM stack and immediately allocates `new byte[lengthData]` for `codeCopy`, independent of the `Program`'s soft memory (`Memory.extend`) that is protected by `EnergyCost.MEM_LIMIT` (3 MB, enforced via `checkMemorySize`/`calcMemEnergy`).

### Finding Description
`extCodeCopyAction` at [1](#0-0)  does:
```
int lengthData = program.stackPop().intValueSafe();
...
byte[] codeCopy = new byte[lengthData];
```
`lengthData` comes from `DataWord.intValueSafe()`, an attacker/contract-controlled 256-bit stack value clamped to `int` range, so it can be up to `Integer.MAX_VALUE` (~2^31-1, ~2 GB). This allocation happens with `new byte[lengthData]` regardless of whether the corresponding EVM *memory* (bounded to 3 MB via `MEM_LIMIT` in `EnergyCost.java` [2](#0-1)  and `checkMemorySize` at [3](#0-2) ) would actually permit such a large write. The actual `program.memorySave(memOffset, codeCopy)` call that writes into the size-checked `Memory` object happens afterward, but the temporary `codeCopy` scratch buffer is allocated at full requested size beforehand, unconditionally.

This is structurally the same defect class as the reported kernel bug: an unvalidated/unbounded size value is used to drive a large memory allocation before the size is properly constrained by the subsystem's real limit checks, which in the kernel case caused a 4 GiB allocation and OOM/crash. Here, a single crafted/deployed contract executing `EXTCODECOPY` with a large `lengthData` on the stack can trigger allocation of a large temporary byte array per invocation before any energy/gas-based memory bound is actually applied to that temporary buffer.

### Impact Explanation
Repeated invocation (e.g., inside a loop, or via multiple internal/external calls within one transaction, or across many transactions/blocks) can drive heap pressure and potentially induce `OutOfMemoryError` / GC thrashing on the executing full node, since the temporary array size is not itself capped by `MEM_LIMIT`. This is reachable by any account that can deploy or trigger a smart contract executing `EXTCODECOPY`, i.e., any unprivileged contract deployer/caller — matching the required threat model (unprivileged TVM/contract caller triggering a node crash/resource exhaustion path).

### Likelihood Explanation
Medium. `intValueSafe()` clamps to `Integer.MAX_VALUE`, so a single call can request up to ~2 GB scratch buffer; whether the JVM heap size and energy costs (which do charge `EXT_CODE_COPY` + `calcMemEnergy` proportional to word count) make this immediately effective at scale is uncertain — gas costs for large sizes would be very high and likely be capped by the transaction's `feeLimit`/energy limit in most cases before enough iterations occur, which somewhat limits (but does not eliminate) exploitability for a single call.

### Recommendation
Bound `lengthData` (and analogous parameters in `codeCopyAction`, `callDataCopyAction`, `returnDataCopyAction`, `mCopyAction`) against `EnergyCost.MEM_LIMIT` (or a similarly-derived hard cap) before allocating the scratch buffer, mirroring the fix pattern in the referenced CVE: validate/clamp the size before it is used to size an allocation, rather than only bounding the eventual writable memory.

### Proof of Concept
A contract executing `EXTCODECOPY` with a `size` stack argument close to `Integer.MAX_VALUE` (e.g., `0x7fffffff`) targeting any address triggers `extCodeCopyAction` to execute `new byte[lengthData]`, allocating a ~2 GB array in `OperationActions.extCodeCopyAction` at [4](#0-3)  before any `MEM_LIMIT`-based rejection applies to that temporary buffer.

**Note on confidence**: I could not fully trace whether energy/fee-limit checks in the broader `Program`/VM execution path (outside the files reviewed) reject the operation before `extCodeCopyAction` executes for very large `lengthData` values, nor whether JVM-level array-size/heap constraints already mitigate this in practice. This uncertainty affects the Likelihood rating; further verification of the exact call order between `getExtCodeCopyCost` (gas charge) and `extCodeCopyAction` (execution) within the VM's opcode dispatch loop would be needed to confirm whether gas is deducted (and potentially insufficient-energy exceptions thrown) prior to the allocation for large sizes.

```java
  public static void extCodeCopyAction(Program program) {
    DataWord address = program.stackPop();
    byte[] fullCode = program.getCodeAt(address);

    int memOffset = program.stackPop().intValueSafe();
    int codeOffset = program.stackPop().intValueSafe();
    int lengthData = program.stackPop().intValueSafe();

    int sizeToBeCopied = lengthData;
    if ((long) codeOffset + lengthData > fullCode.length) {
      sizeToBeCopied = fullCode.length < codeOffset ? 0 : fullCode.length - codeOffset;
    }

    byte[] codeCopy = new byte[lengthData];

    if (codeOffset < fullCode.length) {
      System.arraycopy(fullCode, codeOffset, codeCopy, 0, sizeToBeCopied);
    }

    program.memorySave(memOffset, codeCopy);
    program.step();
```
