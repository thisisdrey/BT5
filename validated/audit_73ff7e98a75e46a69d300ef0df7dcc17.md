### Title
Unauthenticated single-packet `RecvError` message causes tunnel state poisoning / DoS - (`File: outside.go`)

### Summary
The reported ownership-transfer bug class is about a *single, unvalidated step* silently transferring a sensitive privilege (owner/admin/minter) to an attacker-influenced value, with no confirmation step to prove the new value is legitimate. The closest reachable analog in Nebula's remote-facing surface is `Interface.handleRecvError`, which tears down an established tunnel and evicts its pending-handshake state based on a single unauthenticated, unencrypted UDP packet, with only a weak source-address comparison as protection.

### Finding Description
`readOutsidePackets` dispatches `header.RecvError` packets directly to `f.handleRecvError` before any certificate or cryptographic authentication is performed [1](#0-0) . `handleRecvError` looks up the hostinfo by the attacker-supplied `RemoteIndex` field from the (unauthenticated, unencrypted) header, and if the source address of the packet matches the `HostInfo`'s currently recorded remote address, it unconditionally closes the tunnel and deletes the pending handshake state: [2](#0-1) 

The only "validation" performed is a plaintext comparison of the UDP source address (`addr`) against the value cached in `hostinfo.GetRemote()`. This is a single, one-shot check with no secondary confirmation (e.g., a signed/keyed acknowledgment, or requiring the peer to also fail decryption locally) analogous to how `PNG.sol`/`Airdrop.sol` accept a single unvalidated write to a sensitive field. `RemoteIndex` is only a 32-bit value generated by `generateIndex` and is transmitted in the clear on every packet of a tunnel, and UDP source addresses are trivially spoofable by an off-path attacker with no CA-signed certificate at all, since `RecvError` handling requires no certificate.

### Impact Explanation
An attacker with no valid Nebula certificate who can observe or infer a peer's current `RemoteIndex`/`RemoteAddr` pairing (e.g., via passive observation of unencrypted headers on shared/observable network paths, or by racing a legitimate `RecvError` sender window) can forge a single `RecvError` packet to immediately sever an active tunnel and force deletion of hostmap/handshake state, without ever completing a valid handshake. This is a remote state-poisoning / DoS action taken on the strength of a single unauthenticated packet field, mirroring the "lack of two-step" pattern: one packet, one step, and a security-relevant state transition (tunnel teardown) occurs.

### Likelihood Explanation
The `RecvError` message type is explicitly excluded from any cert/handshake requirement in `readOutsidePackets` (dispatched immediately based on `h.Type`) [1](#0-0) , so exploitation requires no CA-signed certificate. Exploitability is gated by whether `f.acceptRecvErrorConfig.ShouldRecvError(addr)` allows the sender's address and by the attacker's ability to learn/spoof the `RemoteIndex` and `RemoteAddr` pair; both are transmitted unencrypted on the wire and are not cryptographically bound to the sender, so an attacker positioned to observe traffic (or spoof UDP source addresses in an unfiltered path) can trigger this without a certificate.

### Recommendation
Require the `RecvError` teardown action to be corroborated by a second signal before evicting state — for example, only closing the tunnel after a subsequent legitimate handshake attempt fails validation, or requiring a keyed/authenticated recv-error acknowledgment tied to the session's Noise keys, rather than trusting a bare plaintext header field plus a source-address match.

### Proof of Concept
1. Establish a legitimate tunnel between `me` and `them`, noting `them`'s `RemoteIndex` and current UDP `RemoteAddr` as seen by `me` (both visible in cleartext on the wire, as demonstrated by `TestCloseTunnelAuthenticated` constructing similar bogus control packets) [3](#0-2) .
2. Craft a `header.RecvError` packet with that `RemoteIndex`, and send it from a spoofed UDP source address equal to `them`'s recorded remote address, using `f.sendRecvError`'s wire format as a reference [4](#0-3) .
3. `me`'s `handleRecvError` finds the hostinfo, sees `hr == addr`, and immediately calls `f.closeTunnel(hostinfo)` and `f.handshakeManager.DeleteHostInfo(hostinfo)` [5](#0-4) , tearing down the tunnel without the attacker ever presenting a certificate.

```go
func (f *Interface) handleRecvError(addr netip.AddrPort, h *header.H) {
	if !f.acceptRecvErrorConfig.ShouldRecvError(addr) {
		f.l.Debug("Recv error received, ignoring",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
		return
	}

	if f.l.Enabled(context.Background(), slog.LevelDebug) {
		f.l.Debug("Recv error received",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
	}

	hostinfo := f.hostMap.QueryReverseIndex(h.RemoteIndex)
	if hostinfo == nil {
		f.l.Debug("Did not find remote index in main hostmap", "remoteIndex", h.RemoteIndex)
		return
	}

	hr := hostinfo.GetRemote()
	if hr.IsValid() && hr != addr {
		f.l.Info("Someone spoofing recv_errors?",
			"addr", addr,
			"hostinfoRemote", hr,
		)
		return
	}

	f.closeTunnel(hostinfo)
	// We also delete it from pending hostmap to allow for fast reconnect.
	f.handshakeManager.DeleteHostInfo(hostinfo)
}
```
