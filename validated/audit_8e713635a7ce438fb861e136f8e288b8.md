### Title
Floating-point redemption math in the legacy Bancor-style token Exchange lets a caller extract disproportionate output when pool balances are small, mirroring the Thetanuts-style redemption-math flaw - ([File: chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java])

### Summary
Every `ExchangeTransactionContract` / `ExchangeInjectContract` / `ExchangeWithdrawContract` call that is *not* running under the "hardened" flag goes through `ExchangeCapsule.transaction()`, which by default instantiates the legacy `ExchangeProcessor` — a Bancor-formula relay computed entirely with Java `double` arithmetic and truncated with `(long) issuedSupply` / `(long) exchangeBalance` casts. [1](#0-0) [2](#0-1) 

### Finding Description
The safer, integer/BigDecimal-based path (`SafeExchangeProcessor`) only activates when `allowHardenExchangeCalculation()` returns true, a chain parameter gated behind `AbstractExchangeActuator.allowHarden()`. [3](#0-2) 

When hardening is disabled (the default/legacy state for exchanges created before the proposal is voted in, matching the report's "legacy vault" pattern), `ExchangeCapsule.transaction()` runs the `double`-based `ExchangeProcessor.exchange()`: [4](#0-3) [5](#0-4) 

`Maths.pow(1.0 + quant/newBalance, 0.0005, ...)` and `Maths.pow(1.0 + supplyQuant/supply, 2000.0, ...)` are IEEE-754 double computations; when one side of the pool balance is very small (validation only rejects a balance that is exactly `0`, not "near zero" — see `firstTokenBalance == 0 || secondTokenBalance == 0` checks in both `ExchangeTransactionActuator.doValidate` and `ExchangeWithdrawActuator.doValidate`), the ratio `quant/newBalance` or `supplyQuant/supply` can become large, and double-precision rounding/overflow in `Maths.pow` combined with truncating `(long)` casts can produce an `anotherTokenQuant`/`buyTokenQuant` that is inflated relative to the mathematically correct Bancor output. This is architecturally the same class of bug as the Thetanuts incident: legacy redemption math using imprecise arithmetic that misbehaves once one side of the balance/supply is driven near zero, letting a caller redeem far more than they are entitled to. [6](#0-5) 

The result is committed directly to on-chain balances in `execute()` with no post-hoc sanity re-check against the safe/precise formula: [7](#0-6) 

Any unprivileged holder of the exchanged token can reach this by issuing an `ExchangeTransactionContract`; no special privilege is required, only that they own a small-liquidity Exchange (any account can create one via `ExchangeCreateActuator`, and can drive down one side's balance through legitimate withdraw/inject operations before firing the exploit trade).

### Impact Explanation
If exploitable, an attacker can extract more of the counter-asset (TRX or TRC10 token) than the pool actually owes, draining the Exchange's reserves and creating an unbacked/insolvent pool — a direct "theft of funds" outcome matching the accepted-impact list (unauthorized account operation / theft of funds / unbacked balance). Because Exchange balances back real TRX and asset balances credited to the creator/traders' `AccountCapsule`, an inflated payout is a genuine on-chain balance increase, not merely an accounting artifact.

### Likelihood Explanation
Medium. The attack requires: (1) an Exchange still running under the legacy (non-hardened) code path, i.e., `allowHardenExchangeCalculation` not yet enabled on the deployed chain, and (2) driving one side of the pool balance down to a very small (but non-zero) value via ordinary withdraw/inject transactions, then submitting a trade sized to trigger the double-precision rounding error. All of these actions (`ExchangeCreateContract`, `ExchangeInjectContract`, `ExchangeWithdrawContract`, `ExchangeTransactionContract`) are reachable by any signed transaction from an unprivileged account, matching the reachable-analog constraints; the primary uncertainty is the actual default on-chain value of `allowHardenExchangeCalculation` in production main-net state, which could not be confirmed from the indexed code alone.

### Recommendation
- Make `SafeExchangeProcessor` (BigDecimal/exact-math path) the only computation path, removing the double-based `ExchangeProcessor` entirely, or force `allowHarden()` to always return `true` regardless of the proposal value.
- Tighten validation in `ExchangeTransactionActuator.doValidate` / `ExchangeInjectActuator` / `ExchangeWithdrawActuator` to reject trades when either pool balance is below a safe minimum threshold (not just `== 0`), preventing the precision-blowup region from ever being reached.
- Add an invariant check after `exchangeCapsule.transaction()` comparing the double-computed output against the BigDecimal-computed output and reject the transaction if they diverge beyond a strict tolerance.

### Proof of Concept
Not independently reproducible from the indexed code/tests alone — a concrete exploit input (specific balances/quant sizes) that provably diverges between `ExchangeProcessor` (double) and `SafeExchangeProcessor` (BigDecimal) outputs would need to be constructed and validated with a running node/unit test, which is outside the scope of static indexed-code review. The existing `ExchangeCapsuleTest.testExchange` (chainbase test) exercises both the legacy and hardened path on the same balances and shows differing but reportedly consistent results for the sampled inputs; edge-case (near-zero balance) inputs were not present in the retrieved test files, so exploitability at the exact precision-loss boundary is a hypothesis based on the code structure rather than a confirmed PoC.   private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
