### Title
Unchecked subtraction in default (non-hardened) Bancor exchange pool math can drive `ExchangeCapsule` token balances negative - ([File: chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java])

### Summary
The UMA Across `BridgePool` bug was an unchecked subtraction that could underflow a reserve/liquidity accounting variable when funds moved out of the pool faster than the code accounted for. The java-tron analog is `ExchangeCapsule.transaction()`, which computes the counter-party amount from an off-chain-style Bancor formula and then updates both pool reserves with plain `long` arithmetic (`-`) unless a chain-parameter-gated "hardened" mode is active.

### Finding Description
`ExchangeCapsule.transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath, boolean hardenedCalc)` computes `buyTokenQuant` via `ExchangeProcessor`/`SafeExchangeProcessor` and then updates the pool's two token reserves: [1](#0-0) 

When `hardenedCalc` is `false` (the legacy/default code path exercised by `ExchangeCapsule.transaction(sellTokenID, sellTokenQuant, useStrictMath)` and reachable from `ExchangeTransactionActuator`, `ExchangeInjectActuator`, and `ExchangeWithdrawActuator`), the new reserve values are computed with plain `long` subtraction (`secondTokenBalance - buyTokenQuant` / `firstTokenBalance - buyTokenQuant`) with **no post-condition check** that the result is non-negative. Only the `hardenedCalc == true` branch enforces `newFirstTokenBalance < 0 || newSecondTokenBalance < 0` and throws `ContractValidateException`: [2](#0-1) 

That hardened protection, along with `SafeExchangeProcessor`/`StrictMathWrapper`, is only activated through the `allowHardenExchangeCalculation` dynamic/chain parameter, which is toggled via a committee proposal (`ProposalUtil`, `ProposalService`) rather than being unconditionally enforced: [3](#0-2) 

If this parameter has not been activated on a given network, any account can call `ExchangeTransactionActuator` (Bancor-style trade), `ExchangeInjectActuator`, or `ExchangeWithdrawActuator` with crafted `quant`/pool state to push the legacy double/BigInteger-derived `buyTokenQuant` calculation into a value that exceeds one side's reserve, causing the plain subtraction to leave the corresponding token balance in `ExchangeCapsule` at an inconsistent/negative state — the on-chain analog of the "possible underflow" fixed upstream in the Across `BridgePool`.

### Impact Explanation
A negative or corrupted `firstTokenBalance`/`secondTokenBalance` in the persisted `ExchangeCapsule` (stored via `Commons.putExchangeCapsule`) breaks the pool's internal accounting invariant. Subsequent trades computed against this corrupted state (e.g., via `ExchangeProcessor.exchange`, which divides by pool reserves) can yield incorrect/inflated outputs, allowing extraction of TRX or TRC-10 tokens beyond what the pool legitimately holds — an unbacked-balance / fund-theft condition on the affected trading pair.

### Likelihood Explanation
Reachable by any unprivileged transaction broadcaster who is a party to a Bancor exchange (no special privilege required), by submitting `ExchangeTransactionContract`/`ExchangeInjectContract`/`ExchangeWithdrawContract` transactions. Exploitability depends on the network not having activated `allowHardenExchangeCalculation`; on networks/environments where the hardened path is off by default this is directly reachable, whereas on chains where the proposal has already passed, the guard in the `hardenedCalc == true` branch prevents it. This dependency on chain configuration state is the main source of uncertainty and could not be fully confirmed for the current mainnet parameter value from the code alone.

### Recommendation
Move the non-negative reserve check (`newFirstTokenBalance < 0 || newSecondTokenBalance < 0`) out of the `hardenedCalc`-gated branch so it is enforced unconditionally in `ExchangeCapsule.transaction()`, independent of the `allowHardenExchangeCalculation` proposal state, mirroring how the Across fix made the underflow check unconditional rather than opt-in.

### Proof of Concept
Conceptual (cannot be fully validated without live chain parameter state):
1. Create an `Exchange` pool with reserves `firstTokenBalance = X`, `secondTokenBalance = Y` on a network where `allowHardenExchangeCalculation == 0`.
2. Call `ExchangeTransactionActuator` (or repeatedly interleave `ExchangeInjectActuator`/`ExchangeWithdrawActuator`) with `quant` values chosen so the legacy `ExchangeProcessor` (double/BigInteger, non-strict) computes a `buyTokenQuant` slightly larger than the true safe bound due to rounding in the non-hardened formula.
3. Observe `ExchangeCapsule.transaction()` at [4](#0-3)  compute `newSecondTokenBalance`/`newFirstTokenBalance` via plain subtraction with no negative-value guard, then persist the corrupted `ExchangeCapsule` via `Commons.putExchangeCapsule`.
4. Use subsequent trades against the corrupted reserve to extract more value than the pool legitimately backs.
