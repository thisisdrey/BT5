### Title
Incorrect minting in PSM: `mint()` credits internal stablecoin based on the requested transfer amount instead of the external asset actually received by the reserve - ([File: substrate/frame/psm/src/lib.rs])

### Summary
`pallet-psm`'s `mint()` extrinsic moves `effective_external` of `external_asset` from the caller to the PSM reserve account via `T::Fungibles::transfer(...)`, then mints internal stablecoin (`internal_to_user` + `fee`) computed purely from the *requested* `external_amount`, and increases `PsmDebt` by the same nominal figure. The code never checks the actual balance delta on the reserve account before minting. This is the exact bug class from the external report: minting/crediting based on the amount "sent" rather than the amount actually "received."

### Finding Description
In `mint()`: [1](#0-0) 

```rust
let psm_account = Self::psm_account(&internal_asset);
T::Fungibles::transfer(
    external_asset.clone(),
    &who,
    &psm_account,
    effective_external,
    Preservation::Expendable,
)?;
T::Fungibles::mint_into(internal_asset.clone(), &who, internal_to_user)?;
if !fee.is_zero() {
    T::Fungibles::mint_into(internal_asset.clone(), &info.fee_destination, fee)?;
}
```

The return value of `T::Fungibles::transfer` is discarded (`?` only checks for `Err`, not the actual amount moved). The generic default `transfer` implementation in `fungibles::Mutate` (`substrate/frame/support/src/traits/tokens/fungibles/regular.rs:363-386`) itself only *reports* the requested `amount` as `Ok`, while the destination-side credit is applied with `BestEffort` precision: [2](#0-1) 

```rust
Self::decrease_balance(asset.clone(), source, amount, BestEffort, preservation, Polite)?;
// This should never fail as we checked `can_deposit` earlier. But we do a best-effort
// anyway.
let _ = Self::increase_balance(asset.clone(), dest, amount, BestEffort);
Self::done_transfer(asset, source, dest, amount);
Ok(amount)
```

Because `increase_balance` is called with `BestEffort`, the destination account can legitimately receive less than `amount` (e.g. existential-deposit rounding on first touch of the reserve account, issuance caps, or any asset backend for which the withdrawn amount from `who` and the credited amount to `psm_account` diverge — the same fee-on-transfer/rounding pattern as USDT's `transferFrom`), yet `transfer()` still returns `Ok(amount)` unconditionally. `mint()` has no way to detect this because it never re-reads the reserve's balance before minting.

The redemption side (`redeem()`) does add a defensive check comparing `Self::get_reserve(...)` (the PSM's actual on-chain balance) against the expected `external_out` before paying out, but the mint path has no analogous check when the funds are coming *in* — it trusts the nominal `effective_external`/`internal_equivalent` figures to update `PsmDebt` and to mint internal supply.

### Impact Explanation
`PsmDebt` and the minted internal-asset supply are meant to be backed 1:1 by the PSM reserve's external-asset balance (per the pallet's own documentation: "PSM Debt: Total internal asset minted through a PSM, backed 1:1 by external assets in that PSM's reserve"). If the reserve account ever receives less external asset than the nominal amount used to compute `internal_to_user`/`internal_equivalent` (any deposit-side shortfall under `BestEffort`), the pallet mints internal stablecoin that is not fully backed. This directly matches the "theft or unbacked mint" impact category: an attacker or even normal user under adverse conditions can end up with internal-asset credit that exceeds the collateral actually held, silently under-collateralizing the PSM and threatening the peg / redemption solvency for other users.

### Likelihood Explanation
The vulnerability requires no privileged actor, admin, governance, relayer, or peer — it is triggerable by any signed user calling the public `mint()` extrinsic, provided the configured `external_asset`'s `Fungibles` backend can, under any legitimate circumstance (ED dust destruction on first credit to a fresh reserve account, saturating/capped issuance, or any asset implementation where deposit and withdrawal amounts are not guaranteed to match exactly), deliver less to `psm_account` than requested. Because the generic `transfer()` provided method silences this discrepancy by design (`BestEffort` + unconditional `Ok(amount)`), the PSM pallet has no defense-in-depth against it, unlike `redeem()` which explicitly guards against reserve shortfall before paying out.

### Recommendation
In `mint()`, read the PSM reserve account's actual external-asset balance (or the returned amount, if the underlying `Fungibles::transfer` is fixed to return the real credited delta) before and after the transfer, and use that balance difference — not the nominal `effective_external`/`internal_equivalent` — to determine how much internal asset to mint and how much to add to `PsmDebt`. This mirrors the fix already applied on the redeem path (`get_reserve` check) and is the direct analog of the original report's recommendation to "use the balance difference to mint … tokens instead" of trusting the transferred amount.

### Proof of Concept
1. Configure a PSM instance with an `external_asset` backed by a `Fungibles` implementation where crediting `psm_account` under `BestEffort` can deliver less than the requested amount (e.g., the reserve account is not yet in existence and the asset's existential deposit / minimum balance causes the first credit to be reduced, or any asset backend whose `increase_balance` clamps rather than fails).
2. Call `Psm::mint(origin, internal_asset, external_asset, external_amount, max_fee)` with an `external_amount` that lands in exactly this edge case.
3. Observe: `T::Fungibles::transfer` returns `Ok(effective_external)` even though `psm_account`'s external-asset balance increased by less than `effective_external`.
4. `mint_into` still credits `internal_to_user` (+ fee) to the caller/fee destination based on the full nominal `internal_equivalent`, and `PsmDebt` is incremented by the full nominal amount — even though the reserve backing it is short.
5. Repeating step 2 accumulates unbacked internal-asset supply, degrading the PSM's 1:1 backing invariant that other users rely on for redemption.
