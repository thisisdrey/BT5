### Title
Removal of all StackerDB signers on-chain fails to propagate to local replica, allowing revoked signers to keep writing chunks - (File: `stackslib/src/net/stackerdb/mod.rs`)

### Summary
`StackerDBs::create_or_reconfigure_stackerdbs` decides whether to call `reconfigure_stackerdb()` (which is what actually updates the per-slot `signer` bindings used to authenticate chunk writes) based on a condition that special-cases an empty `new_config.signers` list. If the controlling smart contract legitimately revokes all signers for a StackerDB (returns an empty signer-slot list), the node skips reconfiguration entirely, leaving the previously-authorized (now revoked) signers' public-key-hash bindings intact in the local `chunks` table. Those revoked signers can then continue to push validly-signed chunks that the node will accept and re-gossip, because chunk authentication (`try_replace_chunk` / `validate_received_chunk`) checks the *stored* slot signer, not the *current* on-chain config.

### Finding Description
`create_or_reconfigure_stackerdbs` computes `new_config` from the StackerDB-controlling contract (`StackerDBConfig::from_smart_contract`) and only calls `reconfigure_stackerdb` under this guard: [1](#0-0)

If the contract's `stackerdb-get-signer-slots` now legitimately returns an empty list (all signers removed/de-authorized for this reward cycle or application-level revocation), `new_config.signers.is_empty()` is `true`, so the first disjunct is `false`. The second disjunct also is `false` unless the slot count changed. In that case `reconfigure_stackerdb` is never invoked, so the node keeps the *stale* `new_stackerdb_configs` map entry (which does reflect the new, empty `signers` for in-memory validation purposes) while the on-disk `chunks` table — which is what actually authenticates writes — still has the old `(slot_id -> old_signer)` bindings from the prior configuration, per `reconfigure_stackerdb`: [2](#0-1) 

The write-path authentication uses exactly this stored binding, not the freshly-fetched contract state: [3](#0-2) 

and the push/inventory validation path (`validate_received_chunk`) resolves the authorized signer the same way, via `get_slot_signer`, which reads from the `chunks` table: [4](#0-3) [5](#0-4) 

This breaks the intended equality "authorized-signer-per-current-on-chain-config == authorized-signer-in-local-replica": the setter (contract-driven signer-list update to empty) is silently ignored by the reconfiguration logic, so the *old* signer's signature remains valid for the node's chunk-store and gossip/relay logic even though the controlling contract has revoked that signer. This is directly analogous to the reported `setDefaultController()` / `setFeeBeneficiary()` bug class: a setter updates an authoritative value, but state that was established under the old value is never re-checked or invalidated, so the effective behavior does not match the newly-set value.

### Impact Explanation
A signer that has been de-authorized on-chain (e.g., removed from a StackerDB's contract-controlled `stackerdb-get-signer-slots`, resulting in an empty list) retains write authority on any node whose local replica happened to already contain a non-empty slot set (i.e., any node that previously synced the DB), because the reconfiguration is skipped. That revoked party can continue to author and successfully push new chunk versions (`StackerDBPushChunk`) that pass `validate_received_chunk`/`try_replace_chunk`, and the node will store and propagate them to peers as legitimate StackerDB state. This is an unauthorized write into replicated network state, and propagation of that write to peers amounts to network-wide propagation of data from an entity that should no longer be trusted — matching the "unauthenticated/unauthorized write to state or StackerDB" and "network-wide propagation of forged data" impact classes.

### Likelihood Explanation
This requires no privileged access from the attacker beyond already having previously held a valid signer slot (i.e., they are unprivileged with respect to the *current* configuration once revoked). Triggering the condition only requires the controlling application/contract to update its signer set to an empty list at some point (a normal, supported operation exposed by the StackerDB trait: `stackerdb-get-signer-slots` returning `()`), after which every node that already has a populated replica of that DB is affected — no additional attacker action beyond continuing to send previously-valid signed chunks is needed. The scenario is plausible but depends on an application/contract owner actually shrinking the signer set to zero (rather than swapping to a new non-empty set), which is a narrower trigger than a general "any reconfiguration" bug.

### Recommendation
Remove the `!new_config.signers.is_empty()` special-case from the reconfiguration guard in `create_or_reconfigure_stackerdbs`, or explicitly call `reconfigure_stackerdb`/`shrink_stackerdb` whenever `new_config != stackerdb_config` regardless of whether the new signer list is empty, so that revoking all signers is correctly propagated to the local `chunks` table and immediately invalidates prior signer bindings.

### Proof of Concept
1. Deploy/operate a StackerDB-controlling contract whose `stackerdb-get-signer-slots` initially returns `[(signer_A, 1)]`; a node syncs and stores chunk data with slot 0 bound to `signer_A` (via `reconfigure_stackerdb`/`try_replace_chunk`).
2. Contract owner updates the contract so `stackerdb-get-signer-slots` now returns `[]` (revoking `signer_A`), intending no further writes.
3. On the node's next reward-cycle refresh, `create_or_reconfigure_stackerdbs` computes `new_config.signers = []`; since `new_config != stackerdb_config` is true but `new_config.signers.is_empty()` is also true, the `reconfigure_stackerdb` call is skipped (per the guard at [1](#0-0) ).
4. `signer_A` signs and pushes a new chunk version to slot 0 with their still-valid private key. `validate_received_chunk`/`try_replace_chunk` looks up the stored (stale) slot signer via `get_slot_signer`, finds `signer_A` still bound, verifies the signature successfully, and accepts/stores/gossips the chunk — despite `signer_A` no longer being authorized by the controlling contract.

    /// Get the principal who signs a particular slot in a particular stacker DB.
    /// Returns Ok(Some(addr)) if this slot exists in the DB
    /// Returns Ok(None) if the slot does not exist
    /// Returns Err(..) if the DB doesn't exist of some other DB error happens
    pub fn get_slot_signer(
        &self,
        smart_contract: &QualifiedContractIdentifier,
        slot_id: u32,
    ) -> Result<Option<StacksAddress>, net_error> {
        let stackerdb_id = self.get_stackerdb_id(smart_contract)?;
        let sql = "SELECT signer FROM chunks WHERE stackerdb_id = ?1 AND slot_id = ?2";
        let args = params![stackerdb_id, slot_id];
        query_row(&self.conn, sql, args).map_err(|e| e.into())
    }
