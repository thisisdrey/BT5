### Title
StackerDB chunk signature omits the target contract ID, allowing cross-contract signature replay - ([File: libstackerdb/src/libstackerdb.rs])

### Summary
`SlotMetadata::auth_digest()` in `libstackerdb/src/libstackerdb.rs` computes the digest that a StackerDB writer signs over `(slot_id, slot_version, data_hash)` only. It never binds the signature to the target `smart_contract_id` (the "account"/StackerDB instance). Because the `.signers-0-{message_id}` and `.signers-1-{message_id}` contracts all derive their slot ordering from the *same* per-signer-set page (`stackerdb-get-signer-slots-page`), a given signer occupies the identical `slot_id` across every message-id contract in its signer set. A signature that a signer legitimately produced for one contract's slot is therefore also valid for the same slot in every sibling contract, letting an attacker replay an intercepted, validly-signed chunk into the wrong StackerDB contract.

### Finding Description
`SlotMetadata::auth_digest()` and `SlotMetadata::verify()`: [1](#0-0) 

only hash `slot_id`, `slot_version`, and `data_hash` — the contract identifier is absent from the signed payload. The storage-layer validation in `StackerDBTx::try_replace_chunk` and `StackerDBs::validate_received_chunk` uses the `smart_contract` argument purely to look up which slot table/owner to check against, not as part of what was signed: [2](#0-1) [3](#0-2) 

The Clarity boot contracts assign slot ordering per signer set (0 or 1, i.e. `reward_cycle % 2`), and every message-id contract within a signer set (`signers-0-1`, `signers-0-2`, `signers-0-3`, …) reuses that exact same ordering: [4](#0-3) [5](#0-4) 

Consequently, a given signer key occupies the same `slot_id` in the `BlockResponse` contract, the `StateMachineUpdate` contract, and the `BlockPreCommit` contract for its signer set. Since the signature only commits to `(slot_id, slot_version, data_hash)`, a `StackerDBChunkData` legitimately signed for one of these contracts is a byte-for-byte valid, verifiable chunk for the sibling contracts too (as long as the target slot's stored version is lower and the data hash/bytes are identical — both trivially true because the attacker has the full original wire object, since these chunks are broadcast in the clear over the p2p StackerDB push/pull protocol).

An unprivileged network observer can capture a broadcast `StackerDBPushChunkData`/HTTP POST `StackerDBChunkData` payload for contract A and resubmit the *identical* message unmodified against sibling contract B's `/v2/stackerdb/.../chunks` endpoint or over the p2p push-chunk gossip path (`handle_unsolicited_StackerDBPushChunk`); `try_replace_chunk`/`validate_received_chunk` will accept it because signer/slot/version/hash all check out — the contract binding is never verified. There is a mitigation at the higher-level signer message consumer, `signer_message_payload_matches_lane` in `libsigner/src/events.rs`, which rejects a payload whose type-prefix byte doesn't match the target contract's message lane before it is passed on to signer logic. But that check exists purely as an application-layer filter on the *signer event consumer* code path; it does nothing to prevent the actual StackerDB write and its network-wide replication into the wrong contract's replica at the protocol/storage layer (`stackslib/src/net/stackerdb/db.rs`, `stackslib/src/net/stackerdb/mod.rs`), and it offers no protection to any other consumer of raw StackerDB chunk data that doesn't happen to apply this same lane check.

### Impact Explanation
This breaks the intended equality "a chunk's signature authenticates exactly the (contract, slot, version, data) tuple it is stored/served under" — the signature only authenticates (slot, version, data). It results in an unauthenticated write of a signer's data into a StackerDB contract that signer did not intend to write to, and that write is subsequently replicated network-wide by the StackerDB gossip protocol as if it were valid, first-party content for that contract. This matches the report's underlying bug class (signed message missing the binding to the target "account"), mapped onto the StackerDB namespace ("account" ⇒ contract/lane). Any downstream software that consumes raw StackerDB chunk contents for a given contract without independently re-checking that the payload's type matches the contract's lane (i.e., anything other than the specific `TryFrom<StackerDBChunksEvent>` code path with its `signer_message_payload_matches_lane` guard) would treat cross-lane replayed data as authentic.

### Likelihood Explanation
Exploitation requires no privileged access: an attacker only needs to observe one legitimately signed chunk broadcast over the p2p network or served over the public StackerDB RPC endpoints for one `.signers-N-M` contract, and resubmit the unmodified bytes against a sibling `.signers-N-M'` contract (or via unsolicited p2p push). The only constraints are that the target slot's currently stored version must be lower than the replayed chunk's version — a condition that is easy to satisfy opportunistically, particularly right after a fresh signer set rotation when versions reset. No cryptographic material or privileged role is required.

### Recommendation
Include the target `smart_contract_id` (and ideally a StackerDB-specific `reward_cycle`/lane discriminator) inside the digest signed and verified by `SlotMetadata::auth_digest()`/`verify()` in `libstackerdb/src/libstackerdb.rs`, so that a signature is only valid for the exact contract it was produced for. This requires a coordinated protocol/version bump since it changes the wire-verifiable digest that all StackerDB participants must agree on.

### Proof of Concept
1. Wait for (or induce) a signer `S` to sign and broadcast a legitimate `StackerDBChunkData` for slot `k`, version `v`, on contract `.signers-0-1` (`BlockResponse` lane) — e.g. capture it via the p2p `StackerDBPushChunk` message or the RPC `GET /v2/stackerdb/{addr}/{contract}/chunks/{slot}` endpoint.
2. Confirm (via `stackerdb-get-signer-slots-page`) that `S` also owns slot `k` in `.signers-0-2` (`StateMachineUpdate` lane) — guaranteed by contract design since both contracts read the same page.
3. Resubmit the identical `StackerDBChunkData{ slot_id: k, slot_version: v, sig, data }` bytes to `POST /v2/stackerdb/{addr}/signers-0-2/chunks` (or replay it as an unsolicited `StackerDBPushChunkData` targeting `signers-0-2`).
4. Observe that `try_replace_chunk`/`validate_received_chunk` accepts the chunk (via `stackslib/src/net/stackerdb/db.rs:418` and `stackslib/src/net/stackerdb/mod.rs:691`) because `slot_desc.verify(&slot_validation.signer)` only checks `(slot_id, slot_version, data_hash)`, and the replayed data now propagates on the `signers-0-2` StackerDB replica set as if it were an authentic `StateMachineUpdate` write from `S`.

    /// Get the digest to sign that authenticates this chunk data and metadata
    fn auth_digest(&self) -> Sha512Trunc256Sum {
        let mut hasher = Sha512_256::new();
        hasher.update(self.slot_id.to_be_bytes());
        hasher.update(self.slot_version.to_be_bytes());
        hasher.update(self.data_hash.0);
        Sha512Trunc256Sum::from_hasher(hasher)
    }

    /// Sign this slot metadata, committing to slot_id, slot_version, and
    /// data_hash.  Sets self.signature to the signature.
    /// Fails if the underlying crypto library fails
    pub fn sign(&mut self, privkey: &StacksPrivateKey) -> Result<(), Error> {
        let auth_digest = self.auth_digest();
        let sig = privkey
            .sign(&auth_digest.0)
            .map_err(|se| Error::SigningError(se.to_string()))?;

        self.signature = sig;
        Ok(())
    }

    /// Verify that a given principal signed this chunk metadata.
    /// Note that the address version is ignored.
    pub fn verify(&self, principal: &StacksAddress) -> Result<bool, Error> {
        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )
        .map_err(|ve| Error::VerifyingError(ve.to_string()))?;

        let pubkh = Hash160::from_node_public_key(&pubk);
        Ok(pubkh == *principal.bytes())
    }
