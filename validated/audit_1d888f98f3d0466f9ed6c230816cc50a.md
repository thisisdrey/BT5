### Title
Front-runnable, permissionless initialization of the global `FeeState` PDA - ([File: programs/marginfi/src/instructions/marginfi_group/init_global_fee_state.rs])

### Summary
`init_global_fee_state` (handler `initialize_fee_state`) creates the program-wide singleton `FeeState` PDA and writes attacker-controllable arguments (`admin_key`, `fee_wallet`, and all protocol fee parameters) directly into it, with no check that the caller is the program deployer/upgrade authority or any other privileged party. This mirrors the reported `setIDOLContract` pattern: a public, unrestricted setter that permanently establishes a critical, never-again-settable-by-outsiders admin identity.

### Finding Description
The `InitFeeState` accounts struct only requires an arbitrary `payer: Signer<'info>` and uses `init` with fixed seeds `[FEE_STATE_SEED]`, so exactly one `FeeState` account can ever be created program-wide: [1](#0-0) 

The handler takes `admin_key` and `fee_wallet` as plain instruction arguments and writes them unconditionally into the new `FeeState`, with no validation that the caller (`payer`) is the intended protocol admin: [2](#0-1) 

The `global_fee_admin` set here is highly privileged: it governs `edit_global_fee_state` (which can change fees, wallet, and even reassign `global_fee_admin` itself), `config_group_fee` (enable/disable program fees per group), and `panic_pause`/`panic_unpause` (protocol-wide pause), as documented in the permissions guide: [3](#0-2) [4](#0-3) 

Because the PDA has fixed seeds and no privileged signer requirement, this is a "first caller wins" race: whoever submits `init_global_fee_state` first — attacker or deployer — permanently becomes `global_fee_admin`. This is functionally identical to the reported `setIDOLContract()` bug: a `public`, once-settable, un-authenticated setter for a value "cannot be changed after it is set" (except by whoever gets to set it).

### Impact Explanation
If an attacker front-runs the legitimate deployer's `init_global_fee_state` call (e.g., by monitoring the mempool/validator or simply calling it before the deployer does, since Solana instructions are public and race-able), the attacker becomes `global_fee_admin`. From there they can:
- Redirect `global_fee_wallet` to their own address, diverting all protocol fees.
- Arbitrarily set `program_fee_fixed`/`program_fee_rate`, `liquidation_max_fee`, etc., across every group that has program fees enabled.
- Call `config_group_fee` to toggle program fees on/off for any group.
- Control `panic_pause`/`panic_unpause`/`pause_delegate_admin`, allowing them to freeze or unfreeze protocol operation.
This constitutes unauthorized state takeover of protocol-wide fee governance and a potential denial-of-service/insolvency vector (fee-based, plus pause-based griefing) — clearly matching the "Accept only concrete theft, unauthorized transfer, insolvency/bad debt, unauthorized state change, or permanent lock/freeze" bar.

### Likelihood Explanation
This is a one-time initialization instruction expected to be called once at deployment. The realistic attack window is the gap between program deployment and the deployer's own `init_global_fee_state` transaction landing — a narrow but real window on a public blockchain, especially if deployment and initialization are not submitted atomically in the same transaction/bundle. Likelihood is moderate (init-race dependent on operational practice), but the impact if it occurs is severe and irreversible (the PDA can only be created once), which is exactly the failure mode the reported bug class targets.

### Recommendation
Restrict `init_global_fee_state` so only a known privileged key can call it — e.g., require the `payer`/caller to match the program's upgrade authority (checked via `bpf_loader_upgradeable::UpgradeableLoaderState` or a `ProgramData` account constraint) rather than accepting an arbitrary signer, similar to patterns used elsewhere in the codebase (e.g., Kamino's `initGlobalConfig` requires a `programData` account). Alternatively, deploy the program and call `init_global_fee_state` atomically within the same transaction as program deployment/upgrade to eliminate the race window, and add an explicit check/test asserting that a non-deployer signer cannot successfully call this instruction.

### Proof of Concept
1. Program is deployed but `init_global_fee_state` has not yet been called.
2. Attacker observes the deployed program (its ID and the `FEE_STATE_SEED`-derived PDA address are public/derivable).
3. Attacker submits `init_global_fee_state(admin_key = attacker_pubkey, fee_wallet = attacker_pubkey, ...)` with themselves as `payer`, before the deployer's own initialization transaction lands.
4. The `init` constraint succeeds (PDA didn't exist yet); `fee_state.global_fee_admin` and `fee_state.global_fee_wallet` are now attacker-controlled.
5. Deployer's later attempt to call `init_global_fee_state` fails because the PDA already exists (`init` constraint), permanently locking in the attacker as `global_fee_admin`.
6. Attacker then calls `edit_global_fee_state` (which only checks `has_one = global_fee_admin`) to redirect fees, alter fee rates, or set `pause_delegate_admin` to further control the protocol.

Note: I was unable to fully verify whether this exact issue is already listed as a known/out-of-scope item in `SECURITY.md` before running out of tool iterations; its contents should be checked to confirm this is not already an acknowledged/accepted risk.
