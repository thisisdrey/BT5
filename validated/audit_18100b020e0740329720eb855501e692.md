### Title
Attacker can permanently block a victim from onboarding new collateral or debt positions by dust-filling `MAX_TOKENS_PER_USER` via `deposit(..., onBehalfOf_)` - (File: contracts/DepositToken.sol)

### Summary
`Pool` enforces a hard cap of `MAX_TOKENS_PER_USER = 30` on the combined per-account lists `depositTokensOfAccount` and `debtTokensOfAccount` (`Pool.sol:79`, `Pool.sol:204-220`). Any user can call `DepositToken.deposit(amount_, onBehalfOf_)` and mint msd tokens to an arbitrary `onBehalfOf_` address (`DepositToken.sol:211-237`). When the recipient's balance goes from 0 to >0, `_mint` calls `pool.addToDepositTokensOfAccount(account_)` (`DepositToken.sol:486-488`), which reverts with `UserReachedMaxTokens` once the victim already holds 30 distinct deposit/debt tokens. An unprivileged attacker can grief any account by depositing 1-wei dust of every supported collateral type to the victim, permanently preventing that victim from depositing into a collateral not already in their list or issuing a new debt token — a protocol-level denial of service analogous to CVE-2018-2761's availability impact.

### Finding Description
1. `DepositToken.deposit` has no restriction on `onBehalfOf_` — anyone can mint deposit receipts to any address (`DepositToken.sol:211-234`).
2. `_mint` pushes the token into `depositTokensOfAccount[account_]` whenever the prior balance was 0 (`DepositToken.sol:485-488`).
3. `Pool.addToDepositTokensOfAccount` is gated by `onlyIfAdditionWillNotReachMaxTokens(account_)`, which reverts `UserReachedMaxTokens` when `depositTokensOfAccount.length + debtTokensOfAccount.length >= 30` (`Pool.sol:204-208`, `Pool.sol:79`).
4. The same grief is reachable via `transfer`/`transferFrom` — `_transfer` also calls `addToDepositTokensOfAccount(recipient_)` on a 0→>0 balance change (`DepositToken.sol:517-520`), and `DebtToken` mints likewise call `addToDebtTokensOfAccount` (which shares the cap), meaning `DebtToken.issue(amount_, to_)` can also be used to force-add entries.
5. Attack: for each `DepositToken`/`DebtToken` registered in the pool, attacker calls `deposit(1 wei underlying, victim)` (or `issue(1 wei synth, victim)`). After ~30 calls the victim's lists are full. Any subsequent `deposit` into a new collateral, `DebtToken.issue` of a new synth, `SmartFarmingManager.leverage` (which mints a new debt token), or liquidation `seize` pushing a new deposit token to a liquidator/victim all revert inside `_mint`/`_transfer` at `addToDepositTokensOfAccount` / `addToDebtTokensOfAccount`.
6. No modifier prevents this: `deposit` only requires `whenNotPaused`, `nonReentrant`, `onlyIfDepositTokenExists` and `isActive` — all satisfied on the deployed config. There is no opt-in for receiving tokens and no way to refuse a dust deposit.

### Impact Explanation
Availability/DoS on a per-user basis: the victim cannot open positions in collateral types or synths not already in their account list. Because `seize` (called by `Pool.liquidate`) also routes through `_transfer` → `addToDepositTokensOfAccount`, a griefed liquidator's liquidation call reverts if their list is full, and `SmartFarmingManager.leverage`/`flashRepay` paths that mint new debt tokens revert too. The victim can recover only by burning an entire balance to 0 (e.g., withdrawing/transferring a dust token fully) to trigger `removeFromDepositTokensOfAccount`, but the attacker can immediately re-fill the freed slot since dust deposits are permissionless — making the DoS persistently renewable at negligible cost (1 wei per token). This matches the CVE class: unauthenticated, network-reachable, availability-only impact.

### Likelihood Explanation
Cost is trivial — a few wei of each listed collateral plus gas for ~30 calls, all in one transaction or batched via a contract. Any EOA can execute it against any target address at any time; no privileged role, oracle manipulation, or flash loan is needed. The only mitigation is that it is a per-victim grief rather than global, and the victim retains full access to already-listed tokens and withdrawals, which is why severity is Medium rather than High.

### Recommendation
- Allow accounts to evict unwanted tokens regardless of balance: e.g., let `removeFromDepositTokensOfAccount`/`removeFromDebtTokensOfAccount` be callable by the account itself (or treat dust deposits under a threshold as not list-worthy).
- Alternatively, only add a token to the per-account list when the credited amount exceeds a minimum meaningful threshold, or require the recipient to opt in (claim pattern) instead of force-registering on `onBehalfOf_` deposits and transfers.

### Proof of Concept
Hardhat sketch (fork or local deploy):

```ts
// victim starts with an empty account list
expect(await pool.getDepositTokensOfAccount(victim.address)).to.have.length(0)

// attacker deposits dust of every supported collateral to the victim
const depositTokens = await pool.getDepositTokens()
for (const dt of depositTokens.slice(0, MAX)) {
  const underlying = await IDepositToken(dt).underlying()
  await IERC20(underlying).connect(attacker).approve(dt, 1)
  await IDepositToken(dt).connect(attacker).deposit(1, victim.address) // onBehalfOf = victim
}

// victim's combined token count is now at the cap
expect(await pool.getDepositTokensOfAccount(victim.address)).to.have.length(MAX)

// victim's deposit into a collateral they didn't hold reverts
await underlying.connect(victim).approve(newDepositToken.address, amount)
await expect(
  newDepositToken.connect(victim).deposit(amount, victim.address)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens')

// issuing a new synth debt also reverts (debtTokensOfAccount shares the cap)
await expect(
  newDebtToken.connect(victim).issue(1, victim.address)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens')
```

Attacker cost: ~30 dust deposits; effect persists because freed slots can be instantly re-griefed.

Caveat: I could not fully read `onlyIfAdditionWillNotReachMaxTokens`'s exact revert condition or `DebtToken.issue`'s list-add path line-by-line, but the test at `test/Pool.test.ts:1491-1521` confirms the revert behavior at the cap, and the set-add calls in `DepositToken._mint`/`_transfer` are verified above.
