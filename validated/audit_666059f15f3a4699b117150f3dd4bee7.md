### Title
`Pool.removeRewardsDistributor` removes the distributor from the registry but leaves reward accrual alive — removed `RewardsDistributor` keeps accruing and paying `rewardToken` forever - (File: contracts/Pool.sol)

### Summary
The bug class in the Olympus report is: an admin-removal function deletes an entry from a registry array/mapping but fails to clean up the dependent state that still references it, so the "removed" entity continues to influence accounting.

`Pool.removeRewardsDistributor` exhibits the same defect. It removes the distributor address from the `rewardsDistributors` set and does nothing else — it cannot zero `tokenSpeeds`, because that state lives inside `RewardsDistributor`. Afterwards, every state-changing hook on the distributor that governance controls is bricked (`_updateTokenSpeed` is gated by `onlyIfDistributorExists`, which reads `pool.getRewardsDistributors()`), while every value-extracting path (`claimRewards`, `updateBeforeMintOrBurn`, `updateBeforeTransfer`) has **no** distributor-existence check and keeps working against the stale `tokenSpeeds`/`tokenStates`.

### Finding Description

Relevant code, `contracts/Pool.sol` (lines 749–754):

```solidity
function removeRewardsDistributor(IRewardsDistributor distributor_) external onlyGovernor {
    if (address(distributor_) == address(0)) revert AddressIsNull();
    if (!rewardsDistributors.remove(address(distributor_))) revert RewardDistributorDoesNotExist();
    emit RewardsDistributorRemoved(distributor_);
}
```

In `contracts/RewardsDistributor.sol`:

- `_updateTokenSpeed` (lines 287–310) is gated by `onlyIfDistributorExists` (lines 73–85), which reverts `DistributorDoesNotExist` once the distributor is removed from the pool's set. So after removal, `updateTokenSpeed`, `updateTokenSpeeds`, and `syncTokenSpeed` all revert — speeds can never be set to 0.
- `claimRewards` (lines 150–168) is only `nonReentrant`. For any `token_` with `tokenStates[token_].index > 0` it calls `_updateTokenIndex`, which (lines 197–212) keeps adding `deltaTimestamps * tokenSpeeds[token_]` to the index as long as `tokenSpeeds[token_] > 0` — regardless of removal.
- `_updateTokensAccruedOf` / `_calculateTokenDelta` (lines 217–231, 261–266) then credit `balanceOf(account) wadMul deltaIndex` into `tokensAccruedOf`, and `_transferRewardIfEnoughTokens` (lines 248–256) pays out `rewardToken`.

So once a distributor is removed while any token speed is non-zero, the accrual index grows unboundedly and permanently: there is no code path left that can freeze it. Anyone holding the DepositToken/DebtToken can call `claimRewards(account)` (it's permissionless on `account_`) and drain the distributor's `rewardToken` balance at the stale emission rate — including for rewards that accrue long after governance intended emissions to end. This is exactly the Olympus pattern: the removal cleans the registry but not the mapping (`tokenSpeeds`/`tokenStates`), so the removed entity silently keeps driving value transfer.

### Impact Explanation
Direct theft of unclaimed yield / reward funds. After `removeRewardsDistributor`, the distributor keeps emitting `rewardToken` at the last configured speed forever with no way to stop it. Any unprivileged holder of a rewarded DepositToken or DebtToken can keep claiming rewards that were supposed to end. Early/large holders drain the contract's `rewardToken` balance ahead of honest users, and accrual continues past the intended emission horizon. Invariant broken: reward accrual should stop when the distributor is decommissioned.

### Likelihood Explanation
Removing a rewards distributor is a normal administrative lifecycle operation (migrating reward programs, decommissioning a distributor). The sequence "set speed → distribute → remove distributor" without first explicitly zeroing every token speed is a realistic operational path, and nothing in `removeRewardsDistributor` or its NatSpec warns that speeds must be zeroed first (unlike `removeDebtToken`/`removeDepositToken`, which enforce `totalSupply == 0`). The exploit path needs only a public `claimRewards` call; no privileged role, flash loan, or oracle manipulation is required for the *harm* itself.

One caveat to flag honestly: the trigger is a governor call (removal while speed > 0). The original Olympus issue had the same shape (admin `removeCategoryGroup`), so the analog stands on structure; the unprivileged profit path (continued `claimRewards` draining the contract) is attacker-reachable.

### Recommendation
Mirror the fix pattern used in `removeDepositToken`/`removeDebtToken` (which guard with `TotalSupplyIsNotZero`): in `Pool.removeRewardsDistributor`, require the distributor to be quiescent before removal — e.g., check `distributor.claimable`-style state or add a `distributor.isActive()`/all-speeds-zero assertion — or add a `RewardsDistributor.shutdown()`/speed-zeroing hook invoked atomically during removal. Alternatively, make `claimRewards`/`updateBefore*` revert when `onlyIfDistributorExists` fails so removed distributors cannot pay out accrued-at-stale-speed rewards.

### Proof of Concept
Fork a chain where a live `RewardsDistributor` is registered on a `Pool` with `tokenSpeeds[depositToken] > 0` and a nonzero `rewardToken` balance. In a Foundry test:

1. `vm.prank(governor); pool.removeRewardsDistributor(distributor);`
2. `vm.warp(block.timestamp + 30 days);`
3. Attacker (holder of the DepositToken): `distributor.claimRewards(attacker);`
4. Assert `tokensAccruedOf[attacker]` included index growth over the post-removal 30 days and `rewardToken` was transferred — i.e., `tokenStates.index` advanced despite removal, and any subsequent call to `updateTokenSpeed(token, 0)` reverts with `DistributorDoesNotExist`, proving the accrual can never be stopped.

I was not able to run or fully verify the fork test against live deployment addresses within this session (no execution environment), and the DepositToken hook path showing which distributors get invoked post-removal was only partially inspected — but the gating asymmetry (`onlyIfDistributorExists` on admin setters, none on claimers/accrual) is directly visible in `contracts/RewardsDistributor.sol` and `contracts/Pool.sol`, and sufficient to confirm the stale-accrual behavior.
