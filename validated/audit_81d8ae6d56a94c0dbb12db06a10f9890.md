### Title
ETH-implicit Wallet Contract's `has_in_flight_tx` flag can become permanently stuck, freezing the account - ([File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs])

### Summary
The `WalletContract` used by ETH-implicit accounts (NEP-518) tracks whether a transaction is currently executing via the `has_in_flight_tx` boolean, which gates all future calls to `rlp_execute`. Every callback resets this flag to `false` as its *first* statement, but the callback methods continue executing (creating further promises, transferring refunds, etc.) after that reset. If any of that subsequent logic in a callback causes the whole callback function-call receipt to fail (`ActionError`/panic), the entire state mutation of that receipt — including the earlier `has_in_flight_tx = false` reset — is rolled back per NEAR's atomic-receipt-rollback semantics. This mirrors the Kodiak bug class: a state flag intended to be cleared can remain "stuck" due to an external/paused dependency reverting the very call that was supposed to clear it.

### Finding Description
`WalletContract::rlp_execute` (`runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs:88-128`) refuses to start a new transaction whenever `self.has_in_flight_tx == true`: [1](#0-0) 

The flag is set to `true` right before returning any `Promise` (in `rlp_execute`, `address_check_callback`, and `nep_141_storage_balance_callback`), and is only ever reset back to `false` at the very start of the follow-up private callbacks (`address_check_callback`, `nep_141_storage_balance_callback`, `rlp_execute_callback`, `ban_relayer`): [2](#0-1) [3](#0-2) [4](#0-3) 

Per nearcore's runtime spec, a failed action receipt causes `state_update.rollback()`, discarding *all* state changes made during that receipt except gas/outcome accounting: [5](#0-4) 

This means that if any of these callback function calls fails *after* the `self.has_in_flight_tx = false` line executes (e.g. `address_check_callback` failing later while building the relay/registrar-follow-up promise, or `nep_141_storage_balance_callback`/`rlp_execute_callback` failing while constructing subsequent promises or refund transfers), the flag reset is rolled back along with everything else in that receipt, leaving `has_in_flight_tx` permanently `true` in the persisted state.

Because ETH-implicit accounts cannot have a full-access key added, cannot be deleted, and can only be used through `WalletContract::rlp_execute` (per the account-model doc), once `has_in_flight_tx` is stuck at `true`, `rlp_execute` will unconditionally short-circuit and reject every future transaction from the account owner: [6](#0-5) 

This effectively permanently freezes the ETH-implicit account and any $NEAR/token balance held by/routable through it, since there is no other privileged or unprivileged path to reset the flag or otherwise move funds out.

### Impact Explanation
If the invariant break is reachable (see Likelihood), the impact is a **permanent freezing of funds** in the affected ETH-implicit account — the account can never again process an `rlp_execute` call, which is its only means of transferring value or interacting with other contracts. This is a stronger outcome than the original Kodiak report (temporary lock until unpause); here there is no unpause mechanism at all, making it a permanent DoS/freeze on user funds routed through the Wallet Contract.

### Likelihood Explanation
Likelihood depends on whether any of the identified callback code paths can actually fail (panic or return an `ActionError`) strictly *after* the `has_in_flight_tx = false` reset executes within the same receipt. I was not able to conclusively find an `unwrap()`/`panic!` on that exact post-reset code path within the available index for `lib.rs`/`internal.rs` — the visible logic largely returns `Result`/`PromiseOrValue::Value` on error rather than panicking, and cross-contract promise construction (`Promise::new(...).function_call(...)`, `env::promise_batch_action_transfer`) is typically deferred (added to the outgoing receipt) rather than executed synchronously, so many "failures" would only surface asynchronously in a *later* receipt (which would not roll back this callback's state). Because I could not fully verify a concrete panicking statement located strictly between the flag reset and the function return in this index (some file sections, e.g. deeper parts of `internal.rs`, `near_action.rs`, and `types.rs`, were not fully inspected due to tool/iteration limits), I cannot confirm this is definitively reachable with the current evidence — this should be verified with a full read of `internal.rs`, `near_action.rs`, `eth_emulation.rs`, and the NEAR SDK's promise/host-function panic conditions (e.g. invalid method name encoding, oversized data, invalid public key format in `add_access_key_allowance_with_nonce`) to identify a synchronous panic path after the flag reset.

### Recommendation
- Move the `has_in_flight_tx = false` reset to occur only after all fallible callback logic that could still fail within the same receipt has completed successfully (or make the flag reset unconditionally durable regardless of any later panic, e.g. by not relying on atomic rollback for this bookkeeping).
- Add an explicit escape hatch: a way to reset `has_in_flight_tx` (e.g., a time-based expiry, or a privileged self-call that cannot itself fail) so that even if the flag gets stuck due to an unexpected panic, the account is not permanently frozen.
- Audit every private callback (`address_check_callback`, `nep_141_storage_balance_callback`, `rlp_execute_callback`, `ban_relayer`) for any panic/`unwrap()`/host-function error that can occur after the flag reset, and eliminate them or wrap them so failures cannot roll back the flag reset.

### Proof of Concept

This requires deeper inspection of `internal.rs`, `near_action.rs`, `eth_emulation.rs`, and the exact NEAR SDK behavior for promise-construction host functions, which was not completed within the available tool budget. ### Wallet Contract

The Wallet Contract (see [NEP-518](https://github.com/near/NEPs/issues/518) for more details) functions as a user account and is designed to receive, validate, and execute Ethereum-compatible transactions on the NEAR blockchain.

Without going into details, an Ethereum-compatible wallet user sends a transaction to an RPC endpoint, which wraps it and passes it to the Wallet Contract (on the target account) as an `rlp_execute(target: AccountId, tx_bytes_b64: Vec<u8>)` contract call.
Then, the contract parses `tx_bytes_b64` and verifies it is signed with the private key matching the target [ETH-implicit account ID](#eth-implicit-account-id) on which the contract is hosted.
