### Title
Unprivileged transaction flood can silently evict already-sig-verified transactions from the banking-stage ingress channel before they are scheduled - (File: `streamer/src/evicting_sender.rs`)

### Summary
The `EigenPod` finding describes an unprivileged, permissionless action (`verifyBalanceUpdate`) that can be raced ahead of a legitimate pending action (a pod owner's withdrawal), destroying the victim's state before their own action executes. The structural analog in agave is the `EvictingSender` used to bridge `sigverify` output into the banking-stage ingestion channels (`non-vote`, `tpu-vote`): when the bounded channel is full, sending a *new* batch silently evicts the *oldest* already-verified batch, regardless of whose transactions are inside it. Any unprivileged sender who can push enough valid (or even minimally valid-looking) traffic through sigverify can race ahead of another user's transaction and cause it to be dropped after all the expensive verification work has already been spent on it, before it ever reaches the scheduler/banking stage.

### Finding Description
`EvictingSender<T>::try_send` in [1](#0-0)  implements a bounded channel where, on `Full`, it pops and discards the oldest queued item to make room for the newest one. This sender is used for the banking-stage ingress channels created in `BankingTracer::channel`, i.e. the non-vote and tpu-vote channels that carry sig-verified `BankingPacketBatch`es from sigverify workers to the scheduler: [2](#0-1) .

In `SigVerifyWorkerPool::run_transaction_task`, after a batch has already passed deduplication, the priority-floor check, and full Ed25519 signature verification (i.e., real CPU work has been spent validating it as a legitimate transaction), it is pushed onto this same channel via `state.banking_stage_sender.send(...)`, and the eviction count is only recorded for metrics — the caller has no way to recover or retry the evicted batch: [3](#0-2) .

Because eviction is oldest-first and unconditional on the content of the evicted batch (it does not consider priority/fee of the transactions inside, unlike the scheduler's own priority-floor mechanism at [4](#0-3) ), a batch of a legitimate user's sig-verified transaction sitting in the channel can be evicted purely because a flood of *newer* batches (potentially cheap, unstaked, low-fee transactions) arrived afterward and filled the fixed-capacity channel. The victim's transaction is discarded with no error surfaced to the client — it is simply never scheduled, and the client observes it as a timeout, requiring them to resubmit (often too late for their intended action, mirroring how the EigenPod owner's balance-affecting withdrawal window could be raced by an attacker before they can act).

This channel sits downstream of the QUIC/UDP streamer ingestion path (`streamer/src/nonblocking/quic.rs`, `simple_qos.rs`, `swqos.rs`) which is explicitly reachable by unstaked/unprivileged clients (unstaked connections are permitted by default, just at lower throughput caps), and downstream of `core/src/sigverify.rs` / `sigverify_stage.rs`, both explicitly in the in-scope surface (QUIC/UDP streamer, packet dedup and sigverify, banking stage and scheduler).

### Impact Explanation
An unprivileged/unstaked client can cause a legitimate, otherwise-valid transaction submitted by another unprivileged user to be silently dropped after the expensive signature-verification work has already been performed on it, purely by winning a race to fill the bounded ingress channel with newer batches. This is a denial-of-service / censorship primitive against arbitrary users' transactions at the mempool-ingestion boundary, and it also represents wasted (already-spent) CPU work on transactions that are then thrown away instead of being fairly queued by fee/priority, which is the same wasted-verification-then-discard pattern flagged as a class of concern for the sigverify/banking-stage boundary.

### Likelihood Explanation
Reachability requires only submitting a sufficient volume of sig-verifiable traffic (does not require stake) to overrun a bounded per-channel capacity long enough to evict a specific victim batch; QUIC/UDP ingestion permits unstaked connections by default, and the per-connection/per-IP throttles limit throughput but not the ability of many low-cost transactions to collectively exceed channel capacity during bursts. Because eviction is oldest-first, it is not exploitable "for free" by any single unprivileged actor with certainty against a specific victim (timing-sensitive), so likelihood is moderate rather than trivially guaranteed, and its severity is best framed as amplifying network-level congestion/DoS effects rather than a deterministic fund-loss bug like the EigenPod original.

### Recommendation
Consider making the banking-stage ingress channel eviction priority-aware (mirroring the scheduler's own priority-floor logic in `scheduler_controller.rs`) rather than strict oldest-first FIFO eviction, so that a flood of low-priority/low-fee traffic cannot arbitrarily evict a higher-priority transaction that has already paid the cost of full verification. Alternatively, apply the priority-floor-style admission control before, not only after, the expensive `ed25519_verify_serial` work so verification effort is not wasted on batches likely to be evicted anyway.

### Proof of Concept
Not independently verifiable from static code review alone (requires live cluster/timing measurements to demonstrate reliable eviction of a targeted victim batch); the described mechanism, code paths, and unconditional discard behavior are confirmed directly from `streamer/src/evicting_sender.rs`, `core/src/banking_trace.rs`, and `core/src/sigverify.rs` as cited above.

impl<T> ChannelSend<T> for EvictingSender<T>
where
    T: Send + 'static,
{
    fn try_send(&self, msg: T) -> std::result::Result<(), TrySendError<T>> {
        let Err(e) = self.sender.try_send(msg) else {
            return Ok(());
        };

        match e {
            // Prefer newer messages over older messages.
            TrySendError::Full(msg) => match self.receiver.try_recv() {
                Ok(older) => {
                    // Attempt to requeue the newer message.
                    // NB: if multiple senders are used, and another sender is faster than us to send() after we've popped `older`,
                    // our try_send() will fail with Full(msg), in which case we drop the new message.
                    self.sender.try_send(msg)?;
                    // Propagate the error _with the older message_.
                    Err(TrySendError::Full(older))
                }
                // Unlikely race condition -- it was just indicated that the channel is full.
                // Attempt to requeue the message.
                Err(TryRecvError::Empty) => self.sender.try_send(msg),
                // Unreachable in practice since we maintain a reference to both the sender and receiver.
                Err(TryRecvError::Disconnected) => unreachable!(),
            },
            // Unreachable in practice since we maintain a reference to both the sender and receiver.
            TrySendError::Disconnected(_) => unreachable!(),
        }
    }

    /// Update the scheduler priority floor.
    ///
    /// Semantics: when the retained scheduler buffer is nearly full, drop
    /// arrivals that are at-or-below the current queue-min priority, i.e. no
    /// better than what the bounded scheduler candidate set would evict.
    fn update_scheduler_priority_floor(&mut self, num_dropped_on_capacity: usize) {
        let buffer_size = self.container.buffer_size();
        let saturated = self
            .saturation_state
            .update(buffer_size, num_dropped_on_capacity);
        let priority_floor = if saturated {
            self.container
                .get_min_max_priority()
                .map_or(0, |(min, _)| min)
        } else {
            0
        };

        self.saturation_state.publish_floor(priority_floor);
    }
