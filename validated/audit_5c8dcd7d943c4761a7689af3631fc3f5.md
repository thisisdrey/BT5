This confirms the analog is real and confirmed by the test suite itself: `GitObjectDirectory` is a field on the `Repository` protobuf that is attacker-influenced through GitLab's access-check callback flow — Rails echoes the quarantine object-directory path back to Gitaly in subsequent RPCs (e.g. `GetObjectDirectorySize`), and the existing test `TestGetObjectDirectorySize_quarantine/"quarantined repo with different relative path"` explicitly checks that swapping one repo's quarantine directory into another repo's request is rejected. However, that protection is bypassed for the `isTransactionQuarantineDir` branch.

### Title
Cross-repository object-directory access via quarantine bypass in `ObjectDirectoryPath` - (File: internal/git/localrepo/paths.go)

### Summary
`Repo.ObjectDirectoryPath` validates that a repository's `GitObjectDirectory` field, which can be attacker/Rails-influenced via the object-quarantine callback mechanism, actually belongs to the repository at hand. This is done with a repository-specific hash prefix check. But an overly broad `||` condition (`isTransactionQuarantineDir`) short-circuits that ownership check whenever the object directory's base name is literally `quarantine`, regardless of which repository's temp directory it lives under.

### Finding Description
`ObjectDirectoryPath` first ensures the given `GitObjectDirectory` resolves inside the storage root [1](#0-0) . It then computes `isTransactionQuarantineDir` to detect transaction-manager-created quarantine directories: [2](#0-1) 

When `isTransactionQuarantineDir` is true, the function completely skips the block that verifies the object directory belongs to the target repository via `storage.QuarantineDirectoryPrefix(repo)` (a SHA1 hash derived from the repo's relative path) [3](#0-2) . That per-repo prefix check exists specifically "to determine whether the quarantine directory does in fact belong to the repo at hand" [4](#0-3) .

The bug: the condition only checks that the **base directory name** is exactly `quarantine` (`baseDir == "quarantine"`), with no verification that this `quarantine` directory sits under the *correct* repository's or the correct transaction's temp path. Any relative object directory anywhere within the storage root whose last path component is literally `quarantine` satisfies this branch and is treated as a legitimate transaction quarantine dir without an ownership check — including a `tx-tmp/quarantine` directory belonging to a concurrent transaction/push for a *different* repository. This is directly analogous to the reported bug class: a security-relevant boolean condition (`||`) is too permissive, causing the code to skip a required check (analogous to `!paused && !whitelisted[from]` incorrectly gating instead of `!paused || whitelisted[from]`) — here the "should require AND ownership-check" path is instead entirely bypassed by an overly broad OR-branch.

This is confirmed to be a security-relevant boundary by the codebase's own tests: `TestGetObjectDirectorySize_quarantine` includes a case titled `"quarantined repo with different relative path"` that deliberately swaps quarantine directories between two different repositories and expects the request to fail with `relative path escapes root directory` [5](#0-4) . That test only exercises the manual (`quarantine.New`) quarantine path, whose directory names are `quarantine-<hash>-<random>` (not literally `quarantine`), so the ownership check applies. But it does not cover the transaction-manager quarantine path where the directory is literally named `quarantine`, which is exactly the branch that skips the ownership check.

### Impact Explanation
An attacker who can influence the `GitObjectDirectory` field of a `Repository` message sent to Gitaly (this occurs legitimately via GitLab Rails echoing quarantine info back during access checks per `doc/object_quarantine.md`) could point it at another repository's `tx-tmp/quarantine` directory that is concurrently in use by a different push/transaction. Because the ownership-prefix check is skipped, Gitaly would treat that foreign, in-flight quarantine directory as valid and use it as the object directory for RPCs like `GetObjectDirectorySize`, `ListAllBlobs`, `ListAllCommits`, etc. This enables cross-repository access to objects that are still in quarantine (not yet visible in the target repo), potentially leaking commit/blob contents from concurrent pushes belonging to other, unrelated repositories.

### Likelihood Explanation
Exploitation requires: (1) the ability to set/influence `GitObjectDirectory` on a repository message that reaches `ObjectDirectoryPath` (achievable through the GitLab access-check callback loop where Gitaly's own quarantine info is echoed back by Rails, as documented in `doc/object_quarantine.md`), and (2) knowledge or guessability of the target storage's temp directory structure and a live transaction quarantine path for another repository (e.g. `tx-tmp/quarantine` under the shared storage's temp dir) coinciding with an active push. This is a narrower race-window condition than a fully generic bypass, but it is directly reachable from ordinary access-check flows without any privileged access, matching the report's "logic gate is too permissive" bug class.

### Recommendation
Tighten `isTransactionQuarantineDir` so that matching on a bare `quarantine` base directory name is not sufficient by itself to skip the per-repository ownership check — either always run the `QuarantineDirectoryPrefix`-based verification (extended to also recognize the transaction-manager's `tx-tmp/quarantine` layout tied to the specific repository/transaction), or verify that the `quarantine` directory is nested under a path that is provably scoped to the current repository/transaction (e.g. include the transaction ID or repo hash in the temp directory name itself) rather than relying on the generic literal string `quarantine`.

### Proof of Concept
Conceptual PoC based on existing test infrastructure (`internal/git/localrepo/paths_test.go:TestRepo_ObjectDirectoryPath` and `internal/gitaly/service/repository/size_test.go:TestGetObjectDirectorySize_quarantine`):
1. Start two concurrent pushes/transactions on repo A and repo B on the same storage, both using the transaction-manager quarantine mechanism, which creates `<storage>/<tx-tmp-dir-A>/quarantine/...` and `<storage>/<tx-tmp-dir-B>/quarantine/...` respectively [6](#0-5) .
2. Craft (or, via the Rails access-check echo path, cause Gitaly to receive) an `ObjectDirectoryPath` request for repo A whose `GitObjectDirectory` is set to repo B's `tx-tmp-dir-B/quarantine` relative path.
3. Because `filepath.Base(relativeObjectDirectoryPath) == "quarantine"`, `isTransactionQuarantineDir` is `true`, and the block performing the `QuarantineDirectoryPrefix`-based ownership check at lines 53–75 is skipped entirely [7](#0-6) .
4. `ObjectDirectoryPath` returns repo B's quarantine directory as if it were valid for repo A, and any RPC using it (e.g. `GetObjectDirectorySize`) will read repo B's in-flight quarantined objects under repo A's identity.
