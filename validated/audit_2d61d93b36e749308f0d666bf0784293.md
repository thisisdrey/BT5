### Title
Stale `TrieKey::PostponedReceipt` self-directed `DeployContract` survives `remove_account` and executes against a re-created account of the same name - ([File: core/store/src/utils/mod.rs])

### Summary
`remove_account` in `core/store/src/utils/mod.rs` deletes `TrieKey::Account`, `TrieKey::ContractCode`, access/gas keys and `TrieKey::ContractData` for an account, but never removes any `TrieKey::PostponedReceipt`, `TrieKey::PendingDataCount`, or `TrieKey::PostponedReceiptId` entries keyed by that `account_id`. Because postponed-receipt bookkeeping in `process_receipt`/`process_action_receipt`/`apply_action_receipt` (`runtime/runtime/src/lib.rs`) is keyed purely by the `AccountId` string with no notion of "account generation," a self-directed `DeployContract` action receipt that was postponed before the account's deletion can later fire against an unrelated, freshly re-created account of the same name.

### Finding Description
`set_postponed_receipt`/`get_postponed_receipt`/`remove_postponed_receipt` key state solely by `(receiver_id, receipt_id)`: [1](#0-0) 

`process_action_receipt` stores a not-yet-runnable action receipt (one with unresolved `input_data_ids`) as a postponed receipt keyed by `account_id`, with no link to the account's current incarnation: [2](#0-1) 

`process_receipt` resolves a `DataReceipt` purely by `(account_id, data_id)`/`(account_id, receipt_id)`, fetches the stored postponed `Receipt`, and executes it via `apply_action_receipt` — again with no check that the account is still the same incarnation that originally postponed the receipt: [3](#0-2) 

`remove_account`, invoked from `action_delete_account`, cleans up `Account`, `ContractCode`, access/gas keys, and `ContractData`, but has no code path that scans for or removes `PostponedReceipt`/`PendingDataCount`/`PostponedReceiptId` entries for the account being deleted: [4](#0-3) [5](#0-4) 

Exploit flow:
1. Attacker creates (and owns) `victim.near`, then, from within it, issues a self-directed promise batch: a `FunctionCall` awaiting a `DataReceipt` (`input_data_ids` non-empty) followed by `Action::DeployContract(evil_code)` targeting itself. Since the account has not received all its input data yet, `process_action_receipt` stores this as a `PostponedReceipt`/`PendingDataCount` under `receiver_id = "victim.near"`.
2. Attacker submits a `DeleteAccount` action on `victim.near` (self-deletion, locked balance zero, storage under `MAX_ACCOUNT_DELETION_STORAGE_USAGE`), which succeeds through `action_delete_account` → `remove_account`. The `Account`, `ContractCode`, and keys disappear, but the postponed receipt data under the `PostponedReceipt`/`PendingDataCount`/`PostponedReceiptId` columns for `"victim.near"` remains in the trie.
3. Some unrelated party later creates a new account also named `victim.near` (account names are freely re-claimable once deleted) and deploys `legit_code`, starts receiving user calls/deposits.
4. The attacker (as predecessor of the still-outstanding data dependency) triggers delivery of the missing `DataReceipt` for the original `data_id`. `process_receipt` finds the matching `PostponedReceiptId`/`PendingDataCount` entries (still present, unrelated to the new account owner), decrements the count to zero, fetches the original postponed `Receipt`, and executes it via `apply_action_receipt` against the *current* (new) `victim.near` account.
5. Because the postponed receipt's `predecessor_id` equals `"victim.near"` (it was self-directed), `actor_id == account_id` holds textually, satisfying the self-authorization check used for `DeployContract`. The action therefore succeeds and overwrites `TrieKey::ContractCode { account_id: "victim.near" }` with `evil_code`, with no `AddKey`/`DeployContract` action ever signed by the new owner's keys.

This works because authorization for `DeployContract` is checked purely by `AccountId` string equality between `actor_id` and `account_id`, and the postponed-receipt state (and its later resolution) is likewise scoped purely by `AccountId`, with no per-incarnation (e.g., account-creation nonce/generation) binding. `action_delete_account` performs no check for outstanding postponed receipts before permitting deletion.

### Impact Explanation
This breaks the "authorization exactness" invariant: an account owner who never signed any `AddKey`/`DeployContract` transaction ends up running attacker-supplied wasm. `evil_code` can be built to add a `FullAccessKey` to itself (or transfer funds directly) the first time it runs, allowing the attacker to drain any balance subsequently deposited into `victim.near` — a direct theft-of-funds / authorization-escalation-across-accounts scenario matching NEAR's bounty categories for "theft of user funds" and "authorization escalation."

### Likelihood Explanation
Preconditions: the attacker must (a) own the eventual account name before deletion and be able to schedule a genuine, valid self-directed cross-contract callback with `DeployContract` as the resolving action, (b) delete that account (only permitted if `locked() == 0` and storage usage is below `MAX_ACCOUNT_DELETION_STORAGE_USAGE`, both attacker-controlled), and (c) wait for/arrange that a third party re-registers the exact same account name and deploys+uses it before the attacker completes the data delivery. Registering a specific, attractive account name is entirely within attacker control (e.g., use a name resembling a well-known project or a name the attacker anticipates will be squatted). The attacker fully controls the timing of step (c) (delivering the deferred `DataReceipt`), so the attack is repeatable and does not depend on any privileged, validator, or leaked-key access — only ordinary transaction submission.

### Recommendation
- On `DeleteAccount`, scan and purge any `PostponedReceipt`, `PendingDataCount`, and `PostponedReceiptId` entries scoped to `account_id` (similar to how `remove_account` already purges access keys and contract data), or reject deletion while such entries exist.
- Alternatively/additionally, bind postponed-receipt bookkeeping to an account "generation" (e.g., include the account's creation nonce/height in the trie key, or invalidate postponed receipts whose target account was deleted and recreated since they were postponed) so a stale postponed receipt can never execute against a different incarnation of the same account name.

### Proof of Concept
Integration test plan (test-loop or `runtime/runtime/src/tests/apply.rs` style, analogous to `test_function_call_after_same_chunk_delete_recreate_resolves_fresh_code`):
1. Create account `victim.near` funded by "attacker" signer.
2. Submit a receipt to `victim.near` with `input_data_ids = [data_id]` and `actions = [DeployContract(evil_code)]`, predecessor = `victim.near` (self-directed). Assert it is stored as a postponed receipt (`TrieKey::PostponedReceipt`/`PendingDataCount` present, via `get_postponed_receipt`).
3. Apply a `DeleteAccount` receipt (self, beneficiary = attacker) on `victim.near`; commit. Assert `TrieKey::Account`/`TrieKey::ContractCode` are gone but `get_postponed_receipt(state_update, &"victim.near".parse().unwrap(), receipt_id)` still returns `Some`.
4. Apply a `CreateAccount` + `DeployContract(legit_code)` receipt targeting `victim.near` from a different (new-owner) signer; commit. Assert `ContractCode` hash equals hash of `legit_code`.
5. Apply the deferred `Data` receipt for `data_id` targeting `victim.near`; commit.
6. Assert `ContractCode` hash for `victim.near` now equals hash of `evil_code`, not `legit_code`, and that no `AddKey`/`DeployContract` action signed by the new owner's access key produced this change — demonstrating unauthorized contract substitution.

pub fn set_postponed_receipt(state_update: &mut TrieUpdate, receipt: &Receipt) {
    assert!(matches!(receipt.versioned_receipt(), VersionedReceiptEnum::Action(_)));
    let key = TrieKey::PostponedReceipt {
        receiver_id: receipt.receiver_id().clone(),
        receipt_id: *receipt.receipt_id(),
    };
    set(state_update, key, receipt);
}

pub fn remove_postponed_receipt(
    state_update: &mut TrieUpdate,
    receiver_id: &AccountId,
    receipt_id: CryptoHash,
) {
    state_update.remove(TrieKey::PostponedReceipt { receiver_id: receiver_id.clone(), receipt_id });
}

/// Removes account, code and all access keys and gas keys associated to it.
pub fn remove_account(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
) -> Result<RemoveAccountResult, StorageError> {
    state_update.remove(TrieKey::Account { account_id: account_id.clone() });
    state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });

    let mut gas_key_nonce_count: usize = 0;
    let mut gas_key_nonce_total_key_bytes: usize = 0;

    // Removing access keys and gas key nonces
    let lock = state_update.trie().lock_for_iter();
    let mut keys_to_remove: Vec<TrieKey> = Vec::new();
    for raw_key in state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_access_keys(account_id), &lock)?
    {
        let raw_key = raw_key?;
        let key_handle = trie_key_parsers::parse_key_handle_from_access_key_key(
            &raw_key, account_id,
        )
        .map_err(|_e| {
            StorageError::StorageInconsistentState(
                "Can't parse key handle from raw key for AccessKey".to_string(),
            )
        })?;
        let nonce_index =
            trie_key_parsers::parse_nonce_index_from_gas_key_key(&raw_key, account_id, &key_handle)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse nonce index from raw key for AccessKey".to_string(),
                    )
                })?;
        if let Some(index) = nonce_index {
            gas_key_nonce_count += 1;
            gas_key_nonce_total_key_bytes += raw_key.len();
            keys_to_remove.push(TrieKey::gas_key_nonce(
                account_id.clone(),
                key_handle.clone(),
                index,
            ));
        } else {
            keys_to_remove.push(TrieKey::access_key(account_id.clone(), key_handle.clone()));
        }
    }
    drop(lock);

    for trie_key in keys_to_remove {
        state_update.remove(trie_key);
    }

    // Removing contract data
    let lock = state_update.trie().lock_for_iter();
    let data_keys = state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_contract_data(account_id, &[]), &lock)?
        .map(|raw_key| {
            trie_key_parsers::parse_data_key_from_contract_data_key(&raw_key?, account_id)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse data key from raw key for ContractData".to_string(),
                    )
                })
                .map(Vec::from)
        })
        .collect::<Result<Vec<_>, _>>()?;
    drop(lock);

    for key in data_keys {
        state_update.remove(TrieKey::ContractData { account_id: account_id.clone(), key });
    }
    Ok(RemoveAccountResult { gas_key_nonce_count, gas_key_nonce_total_key_bytes })
}

pub(crate) fn action_delete_account(
    state_update: &mut TrieUpdate,
    account: &mut Option<Account>,
    actor_id: &mut AccountId,
    receipt: &Receipt,
    result: &mut ActionResult,
    account_id: &AccountId,
    delete_account: &DeleteAccountAction,
    config: &RuntimeConfig,
    current_protocol_version: ProtocolVersion,
) -> Result<(), StorageError> {
    let account_ref = account.as_ref().unwrap();
    let account_storage_usage = if ProtocolFeature::FixDeleteAccountGlobalContractStorageUsage
        .enabled(current_protocol_version)
    {
        let contract_storage = get_contract_storage_usage(state_update, account_id, account_ref)?;
        account_ref.storage_usage().saturating_sub(contract_storage)
    } else {
        // Legacy behavior: only subtracts local contract code, misses the
        // global contract identifier overhead.
        let account_storage_usage = account_ref.storage_usage();
        let code_len = get_code_len_or_default(
            state_update,
            account_id.clone(),
            account_ref.local_contract_hash().unwrap_or_default(),
        )?;
        debug_assert!(
            code_len == 0 || account_storage_usage > code_len,
            "account storage usage should be larger than code size. storage usage: {}, code size: {}",
            account_storage_usage,
            code_len
        );
        account_storage_usage.saturating_sub(code_len)
    };
    if account_storage_usage > Account::MAX_ACCOUNT_DELETION_STORAGE_USAGE {
        result.result =
            Err(ActionErrorKind::DeleteAccountWithLargeState { account_id: account_id.clone() }
                .into());
        return Ok(());
    }
    let gas_key_balance_to_burn = compute_gas_key_balance_sum(state_update, account_id)?;
    if gas_key_balance_to_burn > GasKeyInfo::MAX_BALANCE_TO_BURN {
        result.result = Err(ActionErrorKind::GasKeyBalanceTooHigh {
            account_id: account_id.clone(),
            public_key: None,
            balance: gas_key_balance_to_burn,
        }
        .into());
        return Ok(());
    }
    // We use current amount as a pay out to beneficiary.
    let account_balance = account_ref.amount();
    if account_balance > Balance::ZERO {
        result
            .new_receipts
            .push(Receipt::new_balance_refund(&delete_account.beneficiary_id, account_balance));
    }
    let remove_result = remove_account(state_update, account_id)?;
    result.tokens_burnt =
        result.tokens_burnt.checked_add(gas_key_balance_to_burn).ok_or_else(|| {
            StorageError::StorageInconsistentState("tokens_burnt overflow".to_string())
        })?;
    if remove_result.gas_key_nonce_count > 0 {
        let compute = storage_removes_compute(
            &config.wasm_config.ext_costs,
            remove_result.gas_key_nonce_count,
            remove_result.gas_key_nonce_total_key_bytes,
            AccessKey::NONCE_VALUE_LEN * remove_result.gas_key_nonce_count,
        );
        result.compute_usage = safe_add_compute(result.compute_usage, compute).map_err(|_| {
            StorageError::StorageInconsistentState("compute_usage overflow".to_string())
        })?;
    }
    *actor_id = receipt.predecessor_id().clone();
    *account = None;
    Ok(())
