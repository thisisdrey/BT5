### Title
Unhandled `ArrayIndexOutOfBoundsException` in `ValidateMultiSign` precompile on short/malformed calldata causes node crash / denial of service - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The `PDF2JSON` CVE describes an invalid memory read of size 4 caused by a decoder that trusts an attacker-controlled length/offset field without validating it against the actual buffer size, leading to a crash. The same bug class exists in java-tron's `ValidateMultiSign` and related precompiled-contract calldata decoders, which use attacker-supplied word offsets to index into a `DataWord[]` array derived directly from the TVM calldata, without a length check on the initial header words.

### Finding Description
`ValidateMultiSign.execute()` parses raw calldata into a `DataWord[]` via `DataWord.parseArray(rawData)`, whose length is simply `rawData.length / WORD_SIZE` [1](#0-0) . It then immediately accesses `words[0]`, `words[1]`, `words[2]`, and later `words[3]` and `words[words[3].intValueSafe() / WORD_SIZE]` before any bounds validation [2](#0-1) . If the caller supplies calldata shorter than the expected `5` header words (e.g., fewer than 128 bytes), `words` has fewer than 4 elements and `words[3]` throws an uncaught `ArrayIndexOutOfBoundsException`. There is no top-level `try/catch` around this section of `execute()` (the existing `try { ... } catch (Throwable t)` only wraps the later signature-verification loop, not the header parsing) [3](#0-2) .

This mirrors `extractBytesArray`/`extractSigArray`/`extractBytes32Array`, which similarly compute attacker-controlled offsets (`words[offset + i + 1].intValueSafe() / WORD_SIZE`) and lengths and then call `Arrays.copyOfRange(data, offset, offset + len)` with no upper bound check against `data.length`, allowing out-of-bounds reads/`ArrayIndexOutOfBoundsException`/`NegativeArraySizeException` when the crafted offset/length exceeds the buffer [4](#0-3) .

A recent mitigation (`isValidAbiEncoding`, gated behind `VMConfig.allowTvmOsaka()`/TIP-854) validates that calldata length matches the expected ABI shape before parsing, but this guard is explicitly only active post-activation. The project's own tests document that pre-activation, malformed calldata reaching `ValidateMultiSign.execute()` is expected to throw an uncaught `RuntimeException` (`testTip854PreActivationNoOp` explicitly allows the decoder to throw) [5](#0-4) . In `BatchValidateSign`, the equivalent decoder is wrapped in an outer `try/catch(Throwable)` that swallows the exception and returns a zero result [6](#0-5) , but `ValidateMultiSign.execute()` has no such outer guard, so the exception propagates out of the precompile.

### Impact Explanation
`ValidateMultiSign` is a TVM precompiled contract reachable by any smart contract via a `CALL`/`STATICCALL` to its fixed address (activated by `VMConfig.allowTvmSolidity059()`), meaning any unprivileged contract deployer/caller can trigger it with attacker-chosen calldata. If `allowTvmOsaka` (TIP-854) is not yet activated on a given node/network, calldata shorter than the 5-word header causes an unhandled `ArrayIndexOutOfBoundsException` inside `PrecompiledContract.execute()`. Depending on how far up the call stack this propagates (i.e., whether the VM's opcode dispatcher / `Program`/`VMActuator` catches generic `RuntimeException`s versus only specific VM exceptions), this can manifest as an unexpected transaction failure/inconsistent state or, if uncaught in the actuator/block-application path, a node crash — a denial-of-service condition consistent with the CVE's "invalid read causing DoS" bug class.

### Likelihood Explanation
Triggering this requires only building calldata for the `ValidateMultiSign` precompile address with a byte length under `5 * WORD_SIZE` (160 bytes) and issuing a `CALL` from any contract — no special privileges, staking, or SR/witness status needed. This is trivially reachable by any transaction broadcaster or contract deployer.

### Recommendation
Extend the `isValidAbiEncoding` (or equivalent) length/shape validation to run unconditionally (not gated behind `VMConfig.allowTvmOsaka()`) before any `words[i]` access in `ValidateMultiSign.execute()`, `BatchValidateSign.doExecute()`, `extractBytesArray`, `extractSigArray`, and `extractBytes32Array`. Additionally, wrap the precompile `execute()` entry points in a defensive `try/catch(Throwable)` that returns a failure/zero result instead of allowing exceptions from malformed calldata to propagate up through the TVM call stack.

### Proof of Concept
1. Construct raw calldata for the `ValidateMultiSign` precompiled contract address that is fewer than 160 bytes (e.g., 64 bytes), so `DataWord.parseArray` produces only 2 `DataWord` elements.
2. From any deployed smart contract, issue a low-level `call` to the `ValidateMultiSign` precompile address with this short calldata (this requires `VMConfig.allowTvmSolidity059()` active and `VMConfig.allowTvmOsaka()` inactive, i.e., pre-TIP-854).
3. Execution reaches `words[3].intValueSafe()` in `ValidateMultiSign.execute()` at [7](#0-6)  with only 2 elements in `words`, throwing an uncaught `ArrayIndexOutOfBoundsException`, matching the behavior explicitly documented (and accepted as "existing behaviour") in `ValidateMultiSignContractTest.testTip854PreActivationNoOp` [8](#0-7) .

**Note on confidence**: I was not able to fully trace whether the exception thrown from `PrecompiledContract.execute()` is caught generically higher up in `Program`/`VMActuator`/`OperationActions.callAction` (which would downgrade this to a contained transaction revert rather than a node crash) due to tool/iteration limits — the `OperationActions.callAction`/`exeCall` code path that would show this was not fully retrieved. This should be verified before treating the "node crash" impact as confirmed; at minimum it is a confirmed unhandled-exception/inconsistent-execution bug in a reachable precompile.

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }

  private static byte[][] extractSigArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          SIG_LENGTH);
    }
    return bytesArray;
  }
