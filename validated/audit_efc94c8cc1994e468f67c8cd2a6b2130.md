### Title
Privilege Escalation via AccountPermissionUpdateContract: an Active-permission key granted only the `AccountPermissionUpdateContract` operation can rewrite Owner/Witness/Active permissions to seize full account control - ([File: actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java])

### Summary
An account owner can grant a low-privilege Active permission (e.g. a hot/automation key meant only to update permission metadata) the single operation bit for `AccountPermissionUpdateContract`. Because the actuator's `checkPermission()` validates the *new* permission structure only against the network-wide `getAvailableContractType()` bitmap — never against the operations already held by the signer's *current* permission — that Active key can use its one granted capability to overwrite the account's Owner permission (assign itself full weight/threshold), the Witness permission, and every Active permission's operations bitmap (granting itself or any address every other contract type: transfers, asset issuance, freezing, voting, etc.). This mirrors GHSA-gfv5-grx2-9jw2/CVE-2020-7009, where a caller allowed to perform one narrowly-scoped privileged action (create an API key) could leverage it to mint credentials with unbounded elevated privileges because the new privilege set was never intersected/bounded by the caller's own.

### Finding Description
- `AccountPermissionUpdateActuator.validate()` requires only that the transaction be signed with sufficient weight under *some* permission on the account (checked via `TransactionCapsule.checkPermission`/`checkWeight`, which allows `permissionId != 0`, i.e. an Active permission) as long as that permission's operations bitmap has the `AccountPermissionUpdateContract` bit set — see the signer-side check in `chainbase/src/main/java/org/tron/core/capsule/TransactionCapsule.java` (`checkPermission`, lines 635-645) and `WalletUtil.checkPermissionOperations` (`chainbase/src/main/java/org/tron/common/utils/WalletUtil.java`, lines 27-37). [1](#0-0) [2](#0-1) 
- Once that single gate passes, `AccountPermissionUpdateActuator.checkPermission()` validates each of the *new* Owner/Witness/Active permissions purely against the chain-wide `dynamicStore.getAvailableContractType()` bitmap, with no comparison to the operations/keys the calling permission already possesses: [3](#0-2) 
- `execute()` then unconditionally replaces the account's Owner permission, Witness permission, and all Active permissions with whatever was submitted, via `AccountCapsule.updatePermissions`: [4](#0-3) [5](#0-4) 
- The default Active permission template deliberately excludes the `AccountPermissionUpdateContract` bit (confirmed by `checkActiveDefaultOperationsCorrespondingToCode`), reflecting an assumption that this capability is treated as sensitive and only added deliberately by an account owner for a specific narrow purpose (e.g. letting an automation key rotate a *specific* active permission's keys). But nothing in the actuator enforces that assumption — once the bit is set on any Active permission, the holder can rewrite the entire permission tree, including Owner. [6](#0-5) 

### Impact Explanation
An account owner who grants a limited-purpose Active key the `AccountPermissionUpdateContract` capability (a plausible/expected multisig administration pattern — e.g., "this hot key may rotate active-permission signers") unintentionally grants that key the ability to become the sole Owner of the account, disabling all other signers and seizing unilateral control of funds, TRC10/TRC20 balances, voting power, and resource delegation tied to that account. This is a concrete unauthorized-account-takeover / theft-of-funds primitive reachable purely from a signed transaction crafted by the lower-privilege key holder.

### Likelihood Explanation
Exploitation requires no special network state: an attacker who already holds one Active private key with the `AccountPermissionUpdateContract` bit set — a configuration explicitly supported and plausible for legitimate multisig setups — can broadcast a single `AccountPermissionUpdateContract` transaction that redefines Owner/Witness/Active permissions to their advantage. No collusion with other signers, no committee/witness action, and no additional preconditions are needed beyond the account owner having granted that one operation bit to a non-Owner key.

### Recommendation
In `AccountPermissionUpdateActuator.validate()`/`checkPermission()`, when the transaction's own `permissionId != 0` (i.e., it is signed by an Active permission rather than Owner), restrict the operations/keys of the new Owner, Witness, and Active permissions being set to be no broader than what the signing permission itself is authorized for — e.g., disallow modifying the Owner permission at all unless signed with Owner (`permissionId == 0`), and require that any new Active permission's operations bitmap be a subset of the signing permission's own operations bitmap.

### Proof of Concept
1. Account Owner creates account `A` with default Owner permission (key `O`) and an Active permission `P2` whose operations bitmap has only the `AccountPermissionUpdateContract` bit set and key `K` with weight 1 (intending `K` to only rotate active signer lists).
2. Attacker controlling `K` crafts an `AccountPermissionUpdateContract` transaction with `permission_id = 2` (the Active permission `P2`), setting:
   - New Owner permission: single key = attacker's address `K`, threshold 1.
   - New Active permission(s): operations bitmap with all bits set (subject only to `dynamicStore.getAvailableContractType()`), key = `K`.
3. Attacker signs the transaction with `K` only (satisfies `P2`'s threshold) and broadcasts it via `Wallet.broadcastTransaction`.
4. `AccountPermissionUpdateActuator.validate()`/`execute()` accepts and applies the update because all per-permission checks in `checkPermission()` only compare against the network-wide `getAvailableContractType()`, not against `P2`'s existing operations/keys — see `actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java` lines 124-146 and 44-52.
5. Account `A`'s Owner permission now consists solely of attacker key `K`, and all Active permissions grant `K` full operation rights — attacker now has exclusive, unilateral control of account `A`.

  public static boolean checkPermissionOperations(Permission permission, Contract contract)
      throws PermissionException {
    ByteString operations = permission.getOperations();
    if (operations.size() != 32) {
      throw new PermissionException(String.format("operations size must 32, actual: %d",
          operations.size()));
    }
    int contractType = contract.getTypeValue();
    boolean b = (operations.byteAt(contractType / 8) & (1 << (contractType % 8))) != 0;
    return b;
  }

  public void updatePermissions(Permission owner, Permission witness, List<Permission> actives) {
    Builder builder = this.account.toBuilder();

    owner = owner.toBuilder().setId(0).build();
    builder.setOwnerPermission(owner);
    if (witness != null && builder.getIsWitness()) {
      witness = witness.toBuilder().setId(1).build();
      builder.setWitnessPermission(witness);
    }

    builder.clearActivePermission();
    if (actives != null) {
      for (int i = 0; i < actives.size(); i++) {
        Permission permission = actives.get(i).toBuilder().setId(i + 2).build();
        builder.addActivePermission(permission);
      }
    }

    this.account = builder.build();
  }
