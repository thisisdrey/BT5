## Title
Object directory quarantine check bypasses path traversal validation via basename-only match - ([File: internal/git/localrepo/paths.go])

### Summary
`Repo.ObjectDirectoryPath` in `internal/git/localrepo/paths.go` is supposed to resolve a repository's `GitObjectDirectory` field (which is attacker/client-controlled, since it comes from the `gitalypb.Repository` proto passed on RPC requests and is round-tripped through GitLab's `/internal/allowed` quarantine mechanism as documented in `doc/object_quarantine.md`) while ensuring the resulting path stays inside the repository or a legitimate quarantine temp directory. The classification of "is this a transaction quarantine directory" is done purely by inspecting the basename of the path, and if it matches, all subsequent traversal/containment validation is skipped entirely — mirroring the reported bug class where a permissive OR-style check (`hasCalldata`) bypasses a stricter earlier restriction (`value == 0`).

### Finding Description
The function first validates that `filepath.Join(repoPath, objectDirectoryPath)` is contained within the storage root via `storage.ValidateRelativePath`: [1](#0-0) 

Then it computes `isTransactionQuarantineDir` solely from the **basename** of the relative path — `baseDir == "quarantine"` or `parentDir == "quarantine" && strings.HasPrefix(baseDir, "tmp_objdir")`: [2](#0-1) 

When `isTransactionQuarantineDir` is `true`, the code entirely skips the block that checks whether the directory is either (a) inside the repository itself, or (b) inside the storage's temp dir under the expected, repo-specific `QuarantineDirectoryPrefix`: [3](#0-2) 

Because `isTransactionQuarantineDir` is derived from `filepath.Base(...)` — a value trivially controlled by an attacker who can put arbitrary path segments before a final `quarantine` (or `quarantine/tmp_objdir-*`) component — a `GitObjectDirectory` value such as `../../../../tmp/anything/quarantine` will pass the initial storage-relative check as a benign-looking string, hit `isTransactionQuarantineDir == true`, and skip the containment re-check against the repository or the storage's own `TempDir`/`QuarantineDirectoryPrefix`. The function then does: [4](#0-3) 

`fullPath` is simply `filepath.Join(repoPath, objectDirectoryPath)` and is returned as long as `os.Stat` succeeds — with no re-verification that it is still under `repoPath` or the storage's temp dir. This is structurally identical to the reported bug: a narrowly-scoped condition (`hasCalldata`, here `basename == "quarantine"`) is used to *skip* a stricter, previously-established check (`value == 0`, here the containment/prefix validation), enabling the bypass.

### Impact Explanation
`ObjectDirectoryPath` result is used to construct `GIT_OBJECT_DIRECTORY`/related environment for spawned Git subprocesses (catfile cache, hooks, etc., per `internal/git/catfile/cache.go`, `internal/gitaly/hook/prereceive.go`, `internal/git/gitcmd/hooks_options.go`). If an attacker (or a compromised/misbehaving upstream client such as gitlab-shell/Rails relaying object-directory metadata) can supply a crafted `GitObjectDirectory` whose basename is `quarantine`, Gitaly could be tricked into treating an arbitrary out-of-storage directory as the object database search path for subsequent Git operations, resulting in cross-repository/out-of-storage object disclosure or unexpected object visibility during hook execution — undermining the object-quarantine isolation guarantee described in `doc/object_quarantine.md`.

### Likelihood Explanation
The `GitObjectDirectory` field of `gitalypb.Repository` is populated from data that flows through the `/internal/allowed` round trip (client-supplied, converted from relative to absolute paths by Gitaly itself per `doc/object_quarantine.md`), meaning it is reachable from a push-triggered RPC path without requiring any special privilege beyond what's needed to trigger `PreReceiveHook`/`ObjectDirectoryPath` resolution. Constructing a basename of exactly `quarantine` (or `.../quarantine/tmp_objdir-*`) is trivial string manipulation, so exploitation only requires control over this field's value.

### Recommendation
Do not use `isTransactionQuarantineDir` (a basename-only heuristic) to skip containment validation. Instead, always validate that the resolved object directory path is contained either within `repoPath` or within the specific `expectedQuarantinePrefix` (`filepath.Join(tempDir, storage.QuarantineDirectoryPrefix(repo))`), regardless of whether the basename looks like `quarantine`/`tmp_objdir-*`. The basename check can be used to select *which* prefix to require, but must never be used to bypass the prefix check entirely.

### Proof of Concept
1. As a client capable of influencing the `GitObjectDirectory` field of a `Repository` message passed to an RPC that resolves `ObjectDirectoryPath` (e.g., via the quarantine round-trip during a push), set `GitObjectDirectory` to a relative path like `../../../../tmp/evil/quarantine` (or any sibling storage/temp path ending in a `quarantine` component).
2. `storage.ValidateRelativePath(storagePath, filepath.Join(repoPath, objectDirectoryPath))` succeeds as long as the final joined path is still under the storage root (e.g., another repo's directory under the same storage, or a directory Gitaly itself controls under the storage root).
3. `baseDir == "quarantine"` evaluates true, setting `isTransactionQuarantineDir = true`, skipping the block at [3](#0-2)  that would otherwise reject the path for not matching the repo's own `QuarantineDirectoryPrefix`.
4. `fullPath := filepath.Join(repoPath, objectDirectoryPath)` resolves outside the intended quarantine/temp boundary but is returned as valid if it exists on disk, and is subsequently used to configure `GIT_OBJECT_DIRECTORY` for Git subprocess execution.
