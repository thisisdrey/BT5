### Title
Out-of-bounds heap read while parsing attacker-supplied ZIP central-directory extra fields in ijar - (File: third_party/ijar/zip.cc)

### Summary
`InputZipFile::ProcessCentralDirEntry()` in `third_party/ijar/zip.cc` parses the central directory of a `.jar`/`.zip` file that Bazel's `ijar` tool mmaps directly from an on-disk (potentially externally fetched) archive. Unlike `ProcessLocalFileEntry()`, which validates remaining bytes with `EnsureRemaining()` before reading variable-length fields, `ProcessCentralDirEntry()` performs **no bounds validation at all** before reading `file_name_length`, `extra_field_length`, `file_comment_length`, and then walking the "extra field" sub-records.

### Finding Description
In `ProcessCentralDirEntry` [3](#0-2) , after reading the CDH signature, the function unconditionally does:
```
p += 16;
*compressed_size = get_u4le(p);
*uncompressed_size = get_u4le(p);
u2 file_name_length = get_u2le(p);
u2 extra_field_length = get_u2le(p);
u2 file_comment_length = get_u2le(p);
...
p += file_name_length;
const u1 *extra_p = p;
p += extra_field_length;
while (extra_p != p) {
  const u2 header_id = get_u2le(extra_p);
  const u2 data_size = get_u2le(extra_p);
  const u1 *extra = extra_p;
  extra_p += data_size;
  ...
}
p += file_comment_length;
```
None of `file_name_length`, `extra_field_length`, or the inner `data_size` values are checked against the actual end of the mmap'd input file (`input_file_->Length()`), which `EnsureRemaining()` does for the local-header path [4](#0-3) . An attacker who controls the archive bytes can set an `extra_field_length` that is inconsistent with the actual per-record `data_size` values encoded inside the extra field, causing `extra_p` to overshoot the declared extra-field region: the `while (extra_p != p)` loop condition only checks equality, not `<`, so a crafted `data_size` skips past `p` and the loop keeps consuming subsequent bytes of the mmap'd file (or, if lengths are large enough, walks past the end of the mapping entirely) as if they were more 2-byte header-id/data-size pairs, feeding attacker-uncontrolled adjacent process/heap memory into `get_u8le(extra)` calls that populate `*uncompressed_size`, `*compressed_size`, and `*offset` for the Zip64 extra-field case [5](#0-4) .

This is directly analogous to CVE-2018-8798: a length-prefixed field is trusted without bounds-checking against the actual buffer end, so parsing walks past the intended sub-structure and reads adjacent memory it should never see.

### Impact Explanation
The over-read values (`uncompressed_size`, `compressed_size`, `offset`) derived from out-of-bounds memory are subsequently used to size file-data reads and are written back into the emitted interface jar's zip headers by `OutputJar`/`ijar` machinery, and the parser can also walk unmapped memory, causing a crash (info leak of adjacent heap bytes into the produced artifact, or a segfault/DoS on the build worker). Because `ijar` runs over `.jar` files reachable via `http_jar`/`java_import`, this is attacker-reachable via a hostile download that still satisfies a declared `sha256`/`integrity` value (the attacker simply picks the byte content whose hash they publish), so pinned-checksum verification does not stop the memory-safety bug itself.

### Likelihood Explanation
An attacker only needs to control the bytes of one dependency jar (matching an advertised sha256) and does not need any privileged access to the victim's machine, credentials, or build configuration. Constructing a central-directory entry with an inconsistent `extra_field_length` vs. embedded `data_size` is a small, mechanical crafting task with a standard zip-writing library, making exploitation straightforward once a project depends on the malicious jar via `http_jar`/`java_import`.

### Recommendation
Add the same kind of remaining-bytes check used in `ProcessLocalFileEntry`'s `EnsureRemaining()` to `ProcessCentralDirEntry()`: validate `file_name_length`, `extra_field_length`, and `file_comment_length` against `input_file_->Length()` before advancing `p`, and change the extra-field walking loop to bound-check `extra_p + sizeof(header) <= p` (and `extra_p + data_size <= p`) rather than relying on `extra_p != p`, mirroring the existing bounds checks already used for local headers in `zip_headers.h`'s `ExtraField::find()` [6](#0-5) .

### Proof of Concept
A reproducible C++ unit test (in `third_party/ijar/zip_test.cc` or similar) can construct a minimal zip with:
1. A valid local file header.
2. A central directory header whose `extra_field_length` declares, e.g., 4 bytes, but whose first (and only) embedded extra-field record declares `data_size = 0xFFF0` (far larger than the 4 declared bytes) and `header_id = ZIP64_EXTRA_FIELD_TAG`.
3. A minimal EOCD record.

Running `ijar` (or directly calling `InputZipFile::ProcessCentralDirEntry`) on this crafted archive causes `extra_p` to advance far past the declared extra-field region and past `p`, so the `while (extra_p != p)` loop continues reading attacker-uncontrolled bytes beyond the intended structure (and, with a sufficiently large `data_size`, beyond the mmap'd file), demonstrating the out-of-bounds read (crash under ASan, or silent leakage of adjacent bytes into `*uncompressed_size`/`*compressed_size`/`*offset`).

bool InputZipFile::ProcessCentralDirEntry(const u1 *&p, u8 *compressed_size,
                                          u8 *uncompressed_size, char *filename,
                                          size_t filename_size, u4 *attr,
                                          u8 *offset) {
  u4 signature = get_u4le(p);

  if (signature != CENTRAL_FILE_HEADER_SIGNATURE) {
    if (signature != DIGITAL_SIGNATURE && signature != EOCD_SIGNATURE &&
        signature != ZIP64_EOCD_SIGNATURE) {
      error("invalid central file header signature: 0x%x\n", signature);
    }
    return false;
  }

  p += 16;  // skip to 'compressed size' field
  *compressed_size = get_u4le(p);
  *uncompressed_size = get_u4le(p);
  u2 file_name_length = get_u2le(p);
  u2 extra_field_length = get_u2le(p);
  u2 file_comment_length = get_u2le(p);
  p += 4;  // skip to external file attributes field
  *attr = get_u4le(p);
  *offset = get_u4le(p);
  {
    size_t len = (file_name_length < filename_size)
      ? file_name_length
      : (filename_size - 1);
    memcpy(reinterpret_cast<void*>(filename), p, len);
    filename[len] = 0;
  }
  p += file_name_length;
  const u1 *extra_p = p;
  p += extra_field_length;
  while (extra_p != p) {
    const u2 header_id = get_u2le(extra_p);
    const u2 data_size = get_u2le(extra_p);
    const u1 *extra = extra_p;
    extra_p += data_size;
    if (header_id == ZIP64_EXTRA_FIELD_TAG) {
      if (*uncompressed_size == U4_MAX) {
        *uncompressed_size = get_u8le(extra);
      }
      if (*compressed_size == U4_MAX) {
        *compressed_size = get_u8le(extra);
      }
      if (*offset == U4_MAX) {
        *offset = get_u8le(extra);
      }
    }
  }
  p += file_comment_length;
  return true;
}
