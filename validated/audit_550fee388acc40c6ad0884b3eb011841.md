### Title
Oracle downtime or zero-price reverts permanently block liquidations, withdrawals and swaps, allowing bad debt to accrue and freezing user funds - ([File: contracts/Pool.sol])

### Summary
All pricing in Metronome Synth flows through the external `IMasterOracle` (`quote`, `quoteTokenToUsd`, `quoteUsdToToken`). `contracts/Pool.sol` calls `masterOracle` unconditionally from every solvency- and exit-critical path — `debtPositionOf`, `liquidate`/`quoteLiquidate*`, `withdraw` health checks, `swap`, and `maxLiquidable` accounting. The same dependency exists in `DebtToken` (issue/burn health checks), `FeeProvider` (swap fee quoting) and `SmartFarmingManager` leverage math. Nowhere in production code is an oracle call wrapped in `try`/`catch` or backed by a fallback feed; the only `try`/`catch` occurrences in the tree are in mocks and vendored dependencies. If a constituent feed (Chainlink/Pyth/RedStone pull provider) is paused, returns zero, or goes stale — exactly the scenario of the referenced Y2K finding — every quoted call reverts, and with it every function that gates on health or price.

### Finding Description
- `Pool.liquidate` and `maxLiquidable` price both the seized collateral and the repaid debt through `masterOracle.quote`; an oracle revert makes liquidation of undercollateralized positions impossible even though that is precisely when liquidation matters most.
- `DepositToken.withdraw` → `Pool` health check → `debtPositionOf` quotes every deposit token and debt token of the account; one dead feed freezes *all* withdrawals for every account, including fully healthy ones.
- `Pool.swap` and `FeeProvider.swapFees` revert, so users cannot even swap synths to deleverage.
- There is no grace path (e.g., last-good-price cache, conservative collateral haircut mode, or governance-free emergency liquidation) analogous to what the original report recommended.

### Impact Explanation
Temporary freezing of funds (withdrawals/swaps blocked for all users for the duration of the oracle outage) plus protocol insolvency risk: undercollateralized positions cannot be liquidated while prices are unavailable, so collateral can fall further while debt keeps accruing interest, producing bad debt borne by other depositors. This is a liveness invariant break, not a pricing-accuracy issue.

### Likelihood Explanation
The trigger is an external oracle outage — the same precondition as the source finding (e.g., Chainlink pausing UST/ETH during the collapse, Pyth staleness, or a RedStone pull feed expiring as demonstrated in `test/E2E.hemi.rsETH.pullOracle.test.ts`, where `debtPositionOf` reverts with `invalid-token-price` until the feed is refreshed). On deployments using pull oracles, the outage window is realistically frequent: any gap in signed-price updates reverts all health reads. Note this cannot be forced by an unprivileged attacker; it is conditional on oracle availability, consistent with the Medium severity of the source report.

### Recommendation
Add a safeguard analogous to the report's recommendation: e.g., a bounded staleness fallback to a secondary feed or last-good-price, or a degraded mode that allows liquidation at a conservatively discounted collateral value while blocking new issuance, so that liquidations and healthy withdrawals remain possible during oracle downtime.

### Proof of Concept
Reproducible on a fork: deploy/fork a `Pool` with a deposit token priced through a Chainlink/Pyth-backed `MasterOracle`, then warp time past the feed's `stalePeriod`/expiration (the pull-oracle E2E test already demonstrates `debtPositionOf` reverting with `invalid-token-price` after expiry). Subsequent calls to `depositToken.withdraw`, `pool.liquidate`, and `pool.swap` all revert, while `debtToken` interest keeps accruing — demonstrating frozen funds and un-liquidatable bad debt.

Caveat: I verified the absence of `try`/`catch` fallbacks and the presence of 8 `masterOracle` call sites in `contracts/Pool.sol`, `IMasterOracle`'s revert-propagating interface, and the oracle-expiry revert behavior in tests, but did not read every consumer line-by-line; the conclusion that no safeguard exists rests on the grep-level evidence above.
