## Title
Wallet-contract relayer fee is paid unconditionally before the underlying emulated transfer is known to succeed - ([File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs])

### Summary
The Perennial finding is a case where an incentive/fee owed to a permissionless "keeper" role is disbursed based on the mere *triggering* of a costly action, rather than on that action actually completing/settling — allowing an attacker to collect the incentive repeatedly while draining a shared fee pool. The strongest reachable analog in this nearcore tree is the eth-implicit wallet contract's relayer-fee mechanism in `inner_rlp_execute`, where the relayer's compensation (`fee`) promise is scheduled immediately after RLP-parsing succeeds, independent of whether the wrapped Near action (the emulated base-token/ERC-20 transfer) ultimately succeeds.

### Finding Description
In `inner_rlp_execute` (`runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs:330-411`), once `internal::parse_rlp_tx_to_action` succeeds and the transaction kind is `EOABaseTokenTransfer` or `ERC20Transfer` with a non-zero `fee`, the contract immediately creates and dispatches a transfer promise paying the fee to `context.predecessor_account_id` (the relayer): [1](#0-0) 

This happens *before* the actual wrapped action (the base-token transfer or the multi-step NEP-141/ERC-20 transfer flow through `nep_141_storage_balance_callback` / `rlp_execute_callback`) is known to succeed. The success/failure of the underlying transfer is only resolved afterward in `rlp_execute_callback`, where only the *caller's attached NEAR deposit* (`CallerDeposit`) is refunded on failure — the relayer's fee promise is not rolled back or conditioned on that outcome: [2](#0-1) 

The nonce is also advanced in this same branch (except for the `address_check` sub-case), which is precisely the mechanism meant to prevent replay, not to gate the fee — i.e., the wallet's design intent (per the code comments) is that "the relayer should check the fee before sending" and "verify the fee before signing," implicitly acknowledging that the protocol itself does not guarantee the fee is tied to a successfully completed transfer: [3](#0-2) 

This mirrors the Perennial pattern: a fee meant to compensate for a completed unit of work (settlement / a completed transfer) is instead paid out purely from *triggering* the flow, decoupled from actual successful completion, letting the "keeper" (any address willing to relay, i.e., `predecessor_account_id`) extract it repeatedly.

### Impact Explanation
If the wrapped action can be made to fail deterministically after the fee promise is already dispatched (e.g., an ERC-20 transfer that reverts because the wallet's token balance is insufficient, or a base-token transfer whose value exceeds the wallet's Near balance so the subsequent `action_to_promise` transfer promise fails), the wallet's owner (the party who signs the RLP transaction and effectively controls the `fee` field) can act as their own relayer or collude with one to repeatedly drain their own wallet's NEAR balance via the fee payouts while nonce increments prevent literal replay but not repeated distinct crafted transactions. More importantly, from the "keeper" side: an honest wallet owner who signs a transaction with a fee, intending a legitimate transfer, could have the fee paid to a malicious relayer even if that relayer intentionally supplies parameters (e.g. wrong receiver/target leading to on-chain revert of the *wrapped* action but not affecting the already-independent fee promise) causing the underlying transfer to fail — the relayer is paid regardless. This is a theft-of-funds pattern analogous to the "theft of yield and protocol funds by abusing the keeper role" impact described in the Perennial report, scoped here to the wallet-contract's own balance rather than a market-wide fee pool.

### Likelihood Explanation
The relayer field (`predecessor_account_id`) is deliberately permissionless by design — any account can act as the relayer for this wallet contract, and the code comments explicitly acknowledge the trust gap ("Relayers should also verify the fee before sending to make sure the user's signed transaction will refund enough to cover the relayer's gas costs"), showing the developers were aware fee payment is not strictly coupled to successful execution. Reaching this path requires only a normal signed RLP transaction with an emulated base-token or ERC-20 transfer carrying a non-zero `fee`, executed by any external caller — no privileged or validator/network role is needed, matching the "ordinary client/contract-reachable" requirement.

### Recommendation
Defer creation of the relayer-fee transfer promise until after the wrapped action's outcome is known (i.e., move the fee-payment promise into the success branch of `rlp_execute_callback`, alongside or after the `PromiseResult::Successful` check), so the relayer is compensated only for transfers that actually completed.

### Proof of Concept
Not independently reproduced with a live test; based on static analysis of the control flow in `inner_rlp_execute` (fee promise created at lines 380-385) versus the deferred success/failure resolution in `rlp_execute_callback` (lines 296-316) which only refunds the caller's deposit, not the already-dispatched relayer fee. A concrete PoC would require constructing an `EOABaseTokenTransfer`/`ERC20Transfer` RLP transaction with a non-zero `fee` whose wrapped transfer promise is designed to fail (e.g., insufficient wallet NEAR/token balance for the transfer amount while still covering the fee), and observing that the relayer receives the `fee` payment despite the transfer failing — this exact scenario is not present in the existing test suite (`runtime/near-wallet-contract/implementation/wallet-contract/src/tests/`), which only tests the caller's deposit refund on failure and the relayer fee on *successful* transfers.

    pub fn rlp_execute_callback(
        &mut self,
        caller_deposit: Option<CallerDeposit>,
    ) -> ExecuteResponse {
        self.has_in_flight_tx = false;
        let n = env::promise_results_count();

        if n == 0 {
            // `rlp_execute_callback` is called directly in the case of an emulated self-transfer.
            return ExecuteResponse { success: true, success_value: None, error: None };
        } else if n > 1 {
            return ExecuteResponse {
                success: false,
                success_value: None,
                error: Some(format!(
                    "Invariant violation: this callback comes after a single promise. n={n}"
                )),
            };
        }

        match env::promise_result(0) {
            PromiseResult::Failed => {
                // The cross-contract call failed, refund the caller if needed
                if let Some(CallerDeposit { account_id, yocto_near }) = caller_deposit {
                    let refund_promise = env::promise_batch_create(&account_id);
                    env::promise_batch_action_transfer(
                        refund_promise,
                        NearToken::from_yoctonear(yocto_near.into()),
                    );
                }

                ExecuteResponse {
                    success: false,
                    success_value: None,
                    error: Some("Failed Near promise".into()),
                }
            }
            PromiseResult::Successful(value) => {
                ExecuteResponse { success: true, success_value: Some(value), error: None }
            }
        }
    }
