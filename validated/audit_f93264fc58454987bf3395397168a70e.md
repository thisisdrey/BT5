### Title
Unauthenticated Atlas peers can force permanent storage of unrequested attachment content - (File: stackslib/src/net/atlas/download.rs)

### Summary
`AttachmentsBatchStateContext::extend_with_attachments` accepts and stores whatever `Attachment` content a remote peer returns for an `AttachmentRequest`, without verifying that the returned content actually hashes to the `content_hash` that was requested. The mismatch is only implicitly "caught" later by re-deriving the hash of the received bytes and matching it against known instances — but the content itself is unconditionally persisted to disk via `AtlasDB::insert_instantiated_attachment` regardless of whether it corresponds to anything the node asked for or needs.

### Finding Description
When the `AttachmentsDownloader` fetches attachment data from a peer (`GET /v2/attachments/{content_hash}`), the response is processed in `extend_with_attachments`: [1](#0-0) 

Note that `response.attachment` is inserted into `self.attachments` (a `HashSet<Attachment>`) purely based on successful HTTP decoding — there is no check that `response.attachment.hash() == request.content_hash`. A malicious or compromised peer that is selected as a download source (selection itself is driven by unauthenticated inventory responses, see `extend_with_inventories`) can return arbitrary bytes instead of the content matching the hash it advertised.

Downstream, when the batch state machine finishes, every accumulated attachment is unconditionally written into the local `AtlasDB`: [2](#0-1) 

`attachment.hash()` here is the hash of the *received* bytes (not the originally requested `content_hash`), so `find_all_attachment_instances` may return zero matches, yet `network.atlasdb.insert_instantiated_attachment(&attachment)` is still called and permanently records the content: [3](#0-2) 

This row is inserted with `was_instantiated = 1`. Eviction logic (`evict_expired_uninstantiated_attachments`) only targets rows with `was_instantiated = 0`: [4](#0-3) 

so content that never corresponds to any real `AttachmentInstance` is never cleaned up — it is a permanent, unauthenticated write into node-local persistent state, sourced entirely from an untrusted remote peer's HTTP response.

This is the network-facing analog of the reported bug class: the protocol accepts and durably stores data supplied by an untrusted party without validating it against the property that makes it meaningful (a valid ERC721 in the original report; a hash-matching attachment here), leaving junk state that serves no purpose and cannot be reclaimed through normal eviction paths.

### Impact Explanation
Any StackerDB/Atlas-replicating peer that a node queries for attachment content can inject unbounded amounts of arbitrary attachment content into the victim's local `AtlasDB` `attachments` table, permanently (since `was_instantiated=1` rows are excluded from the periodic eviction routine). This is an unauthenticated write to persistent local state driven purely by a remote, untrusted actor's response payload, matching the "Critical: unauthenticated/unauthorized write to state" category in the rules. Repeated exploitation (each `AttachmentRequest`/response round) grows local storage indefinitely with attacker-chosen content.

### Likelihood Explanation
Likelihood is Low-Medium: the attacker must first get selected as a download source, which happens when the node's own outbound sync peer list includes the attacker's node and the attacker's inventory response claims to have the content (also unauthenticated and unverified, per `extend_with_inventories`). Given typical Atlas peer discovery, an attacker-controlled Stacks node in the outbound peer set can trivially satisfy this and repeatedly respond to legitimate `AttachmentRequest`s with mismatched, ever-different payloads.

### Recommendation
In `AttachmentsBatchStateContext::extend_with_attachments`, verify `response.attachment.hash() == request.content_hash` before inserting into `self.attachments`; reject and penalize (`report.bump_failed_requests()`) any response whose content does not hash to the requested value. Additionally, `insert_instantiated_attachment` in `download.rs::run` should only be called when `attachments_instances` is non-empty (i.e., the content actually resolves a tracked instance), or the `attachments` table should have an eviction path for `was_instantiated=1` rows that never got paired with any instance.

### Proof of Concept
1. Node `A` queries an `AttachmentInstance` requiring `content_hash = H` and issues `AttachmentRequest{content_hash: H}` to peer `B` (selected because `B`'s unauthenticated inventory response claimed to have `H`).
2. Malicious peer `B` responds to `GET /v2/attachments/H` with an `Attachment` payload `C` such that `hash(C) != H`.
3. `extend_with_attachments` (stackslib/src/net/atlas/download.rs:530-553) accepts `C` into `self.attachments` without checking `hash(C) == H`.
4. On batch completion (download.rs:153-169), `network.atlasdb.find_all_attachment_instances(&hash(C))` returns empty (no instance references `hash(C)`), yet `network.atlasdb.insert_instantiated_attachment(&C)` still executes, permanently writing `C` keyed by `hash(C)` into the `attachments` table with `was_instantiated = 1`.
5. Because eviction (`evict_expired_uninstantiated_attachments`) only deletes `was_instantiated = 0` rows, `C` remains in local storage indefinitely. Repeating with different `C` values for each response grows the local AtlasDB unboundedly.

    pub fn extend_with_attachments(
        mut self,
        results: &mut BatchedRequestsResult<AttachmentRequest>,
    ) -> AttachmentsBatchStateContext {
        for (request, response) in results.succeeded.drain() {
            let report = self
                .peers
                .get_mut(request.get_url())
                .expect("Atlas: unable to retrieve reliability report for peer");

            let response = if let Some(r) = response {
                r
            } else {
                report.bump_failed_requests();
                continue;
            };

            if let Ok(response) = response.decode_atlas_get_attachment() {
                self.attachments.insert(response.attachment);
                report.bump_successful_requests();
            } else {
                report.bump_failed_requests();
            }
        }

    pub fn evict_expired_uninstantiated_attachments(&mut self) -> Result<(), db_error> {
        let now = util::get_epoch_time_secs() as i64;
        let cut_off = now - self.atlas_config.uninstantiated_attachments_expire_after as i64;
        let tx = self.tx_begin()?;
        let res = tx.execute(
            "DELETE FROM attachments WHERE was_instantiated = 0 AND created_at < ?",
            params![cut_off],
        );
        res.map_err(db_error::SqliteError)?;
        tx.commit().map_err(db_error::SqliteError)?;
        Ok(())
    }

    pub fn insert_instantiated_attachment(
        &mut self,
        attachment: &Attachment,
    ) -> Result<(), db_error> {
        let now = util::get_epoch_time_secs() as i64;
        let tx = self.tx_begin()?;
        tx.execute(
            "INSERT OR REPLACE INTO attachments (hash, content, was_instantiated, created_at) VALUES (?, ?, 1, ?)",
            params![attachment.hash(), attachment.content, now],
        )?;
        tx.execute(
            "UPDATE attachment_instances SET is_available = 1 WHERE content_hash = ?1 AND status = ?2",
            params![attachment.hash(), AttachmentInstanceStatus::Checked],
        )?;
        tx.commit()?;
        Ok(())
    }
