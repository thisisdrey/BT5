Concurrency-limit Sybil via unnormalized relative-path lock keys allows per-repo resource-limit bypass - (File: internal/grpc/middleware/limithandler/middleware.go)

### Summary
`LimitConcurrencyByRepo` derives the per-repository concurrency-limiting key directly from the raw, attacker-supplied `RelativePath` field of the request message, before that path is canonicalized by `storage.ValidateRelativePath`. Because `filepath.Join`/`filepath.Clean` treats many distinct strings (e.g. `repo.git`, `repo.git/`, `./repo.git`, `sub/../repo.git`, duplicate slashes) as the same on-disk repository, a client can split what is really one repository's traffic across many distinct string variants of its `RelativePath`, each hashing to a different limiter key, while `git-receive-pack`/`git-upload-pack` and friends still all resolve to the identical physical repository once the path is cleaned deeper in the call stack.

### Finding Description
The `max_per_repo` / `max_queue_size` / `max_queue_wait` backpressure controls described in `doc/backpressure.md` exist specifically to protect a single repository's I/O from being overwhelmed by concurrent requests. The enforcement key is computed here: [1](#0-0) 

`info.Repository` is populated in `requestinfohandler.extractRequestInfo`, which pulls the `*gitalypb.Repository` straight out of the incoming protobuf message via `mi.TargetRepo(reqMsg)` with no canonicalization: [2](#0-1) 

The limit-handler interceptor runs immediately after `requestinfohandler` and before the actual RPC handler: [3](#0-2) 

Only much later, deep inside the RPC handler (e.g. `locator.GetRepoPath` / `storage.ValidateRelativePath`), is the relative path actually cleaned and validated against the storage root: [4](#0-3) 

The existing test suite confirms `ValidateRelativePath` treats numerous distinct strings as equivalent to the same canonical path (`"parent/"`, `"/parent"`, `"subfolder//"`, `"subfolder/.."` etc. all collapse): [5](#0-4) 

This is the direct structural analog of the Carapace bug: in the original report, the *check* (STokens balance) is performed against an identity (address) that can be trivially multiplied (Sybil), while the underlying resource (the deposited pool balance) is shared and finite. Here, the *check* (per-repo concurrency token) is keyed on an identity (raw relative-path string) that can be trivially multiplied by an ordinary, authenticated Gitaly client crafting harmless-looking path variants in the `Repository.RelativePath` field of any repository-scoped RPC, while the underlying resource (the single physical repository's disk I/O, working directory, git process slots) is shared and finite. Just as multiple Sybil addresses let the attacker exceed the intended single-depositor withdrawal capacity, multiple relative-path variants let the attacker exceed the intended single-repository concurrency capacity.

### Impact Explanation
An authenticated (or, where `Unauthenticated` per-RPC limits are configured, even unauthenticated) client can issue N times the configured `max_per_repo`/`max_queue_size` concurrent expensive RPCs (e.g. `PostUploadPackWithSidechannel`, `PostReceivePack`, `OptimizeRepository`) against the *same physical repository* by rotating the `RelativePath` string among N syntactically-different-but-semantically-identical variants. This defeats the backpressure mechanism that is Gitaly's stated "primary" protection against resource exhaustion (`doc/backpressure.md`), enabling denial-of-service on a single Gitaly node hosting that repository (excessive concurrent git processes/disk I/O on one repo), exactly analogous to how the original bug let an attacker exceed the intended single-depositor capacity and DOS the protocol by inflating the leverage factor.

### Likelihood Explanation
This requires only a normal client with access to invoke any repository-scoped mutator/accessor RPC and control over the `Repository.RelativePath` field of that RPC (a field routinely supplied by legitimate callers, e.g. Rails/Workhorse forwarding user pushes/fetches) — no privileged access, leaked token, or malicious peer is needed. The path variants needed (trailing slash, `./`, redundant `..` segments, doubled slashes) are all accepted unchanged by `requestinfohandler` before validation occurs. However, whether downstream RPC handlers reject some of these variants earlier (e.g. via strict client-side path formatting from Rails, or via `ValidateRepository` calls that happen to run before the limiter's key is captured in some flows) is not fully verified from static review alone — confirming the exact bypass requires exercising the full gRPC handler chain (including Praefect's repository-rewriting, which happens on a different path) end-to-end, which the current investigation could not do.

### Recommendation
Compute the concurrency-limiting key from the canonicalized relative path (i.e., run the equivalent of `storage.ValidateRelativePath`/`filepath.Clean` against the configured storage root, or use the already-resolved repository identity used later in the request pipeline) inside `LimitConcurrencyByRepo`, rather than the raw string taken directly off the incoming protobuf message, so that all path variants resolving to the same on-disk repository always map to the same limiter key.

### Proof of Concept

1. Configure `[[concurrency]] rpc = "/gitaly.SmartHTTPService/PostUploadPackWithSidechannel" max_per_repo = 1`.
2. From a single authenticated client, concurrently issue N requests against the same physical repository, each with `Repository.RelativePath` set to a different but path-equivalent string (`"repo.git"`, `"repo.git/"`, `"./repo.git"`, `"sub/../repo.git"`, `"repo.git//"`).
3. Because `LimitConcurrencyByRepo` (`internal/grpc/middleware/limithandler/middleware.go:18-25`) uses the raw string as the semaphore key, all N requests acquire distinct concurrency tokens and run concurrently against the same repository, exceeding the configured `max_per_repo=1` limit — verifiable by observing more than 1 concurrent git process against that repository's on-disk path, contrary to the guarantee described in `doc/backpressure.md:26-32`.

// ValidateRelativePath validates a relative path by joining it with rootDir and verifying the result
// is either rootDir or a path within rootDir. Returns clean relative path from rootDir to relativePath
// or an ErrRelativePathEscapesRoot if the resulting path is not contained within rootDir.
func ValidateRelativePath(rootDir, relativePath string) (string, error) {
	absPath := filepath.Join(rootDir, relativePath)
	if rootDir != absPath && !strings.HasPrefix(absPath, rootDir+string(os.PathSeparator)) {
		return "", ErrRelativePathEscapesRoot
	}

	return filepath.Rel(rootDir, absPath)
}
