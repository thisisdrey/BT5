### Title
Replay-window check/update split in `ConnectionState.Decrypt`/`VerifyRelay` allows a duplicated ciphertext to bypass anti-replay protection under concurrent readers - ([File: connection_state.go])

### Summary
`ConnectionState.Decrypt` and `ConnectionState.VerifyRelay` validate an inbound message counter against the replay window (`window.Check`), release the lock, perform the AEAD decryption *without* holding the lock, and only afterward re-acquire the lock to mark the counter as consumed (`window.Update`). This mirrors the reported bonding-curve bug class: a value is validated against a state snapshot, but the actual state-mutating action happens only after the check, based on a check that is provably stale by the time it matters, letting an attacker exploit the gap between check and commit to gain more than the check should have allowed.

### Finding Description [1](#0-0) 
`Decrypt` performs `window.Check` under `decryptLock`, releases the lock, decrypts, then re-locks to `window.Update`. `VerifyRelay` has the identical pattern for relay frames [2](#0-1) .

Nebula supports multiple concurrent UDP reader routines (`f.routines`), each independently calling `readOutsidePackets` → `ConnectionState.Decrypt`/`VerifyRelay` for packets addressed to the same tunnel/`HostInfo` [3](#0-2) [4](#0-3) [5](#0-4) . Because `window.Check(i)` only reads state and does not mark `i` as seen, two goroutines racing on the same `messageCounter` (an attacker-controlled, on-path-observable header field) can both pass `Check` before either calls `Update`. Both then independently perform AEAD decryption via `dKey.DecryptDanger` and, on success, both packets are delivered downstream (to the TUN device for data packets, or forwarded/processed for relay/control frames) before the second `Update` call ever runs and (too late) reports a duplicate.

This is the network-security analog of the reported "check on a value that can change before use" bug: the anti-replay check is evaluated against a window state that is not atomically tied to the decrypt-and-deliver action, so the actual security guarantee (each counter processed at most once) can be violated when the check and the state mutation are split across a released lock, exactly as the bonding curve's price check was decoupled from the actual execution state.

### Impact Explanation
A successful race allows a captured/duplicated ciphertext (which an attacker without a CA-signed certificate can passively capture and re-inject, since UDP is unauthenticated at the transport layer) to be decrypted and delivered twice by a legitimate receiving node. For relay-forwarding nodes this directly reintroduces the traffic-forgery/replay class explicitly called out as fixed by CHANGELOG entries "Advance the replay window on relayed packets..." and "Lock replay window updates so concurrent readers can't corrupt it" [6](#0-5) ; here the corruption is not from a torn Bits update but from the semantic check/act gap still present after fixing the storage race. For end-host delivery, duplicate processing of a data message can cause duplicate injected TUN traffic (application-level replay), and for relay `ForwardingType` frames it can cause duplicate re-forwarding, which the project's own `TestRelayReplayProtection` test explicitly treats as a security regression to guard against [7](#0-6) .

### Likelihood Explanation
Likelihood is low-to-moderate: it requires (a) `listen.batch`/multiple `routines` enabled (a supported, documented configuration, not default single-threaded), and (b) the attacker being able to duplicate a captured ciphertext onto the wire fast enough that two reader goroutines dequeue it before either finishes its Check→Decrypt→Update cycle. This is plausible for an on-path or MITM-capable attacker who can duplicate UDP datagrams (trivial at L2/L3), especially under `recvmmsg` batch reads on Linux where many packets are pulled and dispatched to worker goroutines close together [8](#0-7) .

### Recommendation
Perform the replay-window check and the mark-as-seen update as a single atomic operation under one lock acquisition (e.g., merge `Check`+`Update` into one locked "reserve" step performed before decryption, and only roll back / no-op on decrypt failure), so no other goroutine can observe the same counter as still-available between validation and delivery.

### Proof of Concept
Not executable in this environment (no filesystem/terminal access); a runtime PoC would require: start two receiver worker goroutines on the same `ConnectionState` (via `routines > 1`), capture one legitimate ciphertext+header, and inject it concurrently on two UDP reader queues to demonstrate both invoking `dKey.DecryptDanger` successfully before either `window.Update` call rejects the duplicate — this can be validated with a targeted unit test around `ConnectionState.Decrypt` using two goroutines racing on identical `messageCounter`/`packet` input, analogous to the existing `TestRelayReplayProtection` e2e test [9](#0-8) .

func (cs *ConnectionState) VerifyRelay(l *slog.Logger, messageCounter uint64, packet []byte, nb []byte) error {
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	signedPayload := packet[:len(packet)-cs.dKey.Overhead()]
	signatureValue := packet[len(packet)-cs.dKey.Overhead():]
	_, err := cs.dKey.DecryptDanger(nil, signedPayload, signatureValue, messageCounter, nb)
	if err != nil {
		return err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	return nil
}

func (f *Interface) listenOut(i int) {
	var li udp.Conn
	if i > 0 {
		li = f.writers[i]
	} else {
		li = f.outside
	}

	ctCache := firewall.NewConntrackCacheTicker(f.ctx, f.l, f.conntrackCacheTimeout)
	lhh := f.lightHouse.NewRequestHandler()
	plaintext := make([]byte, udp.MTU)
	h := &header.H{}
	fwPacket := &firewall.Packet{}
	nb := make([]byte, 12, 12)

	err := li.ListenOut(func(fromUdpAddr netip.AddrPort, payload []byte) {
		f.readOutsidePackets(ViaSender{UdpAddr: fromUdpAddr}, plaintext[:0], payload, h, fwPacket, lhh, nb, i, ctCache.Get())
	})

	// An error after teardown began is shutdown noise, the closed flag covers resources
	// Close releases itself and the cancelled ctx covers ones torn down by their owners
	// reacting to it, like the user device pipes
	if err != nil && !f.closed.Load() && f.ctx.Err() == nil {
		f.l.Error("Error while reading inbound packet, closing", "error", err)
		f.onFatal(err)
	}

	f.l.Debug("underlay reader is done", "reader", i)
}
