### Title
Permissionless `ExchangeCreateContract` lets an attacker pair a same-named fake TRC10 token with TRX/real assets, tricking traders into swapping real value for a worthless quote token - (File: actuator/src/main/java/org/tron/core/actuator/ExchangeCreateActuator.java)

### Summary
`ExchangeCreateActuator.execute()`/`validate()` allow any funded account to permissionlessly create a bancor-style TRX/TRC10 (or TRC10/TRC10) exchange pool by simply supplying `firstTokenId`/`secondTokenId` and initial reserve balances [1](#0-0) . There is no allowlist or reputational check on the tokens used to seed the pool - exactly the "pools can be deployed with malicious/incorrect quote tokens" bug class, translated to TRON's on-chain bonding-curve exchange rather than an off-chain AMM factory.

### Finding Description
When `AllowSameTokenName` is enabled (the mainnet-default long-term state, per `DynamicPropertiesStore`), token names are not unique - `AssetIssueActuator.validate()` only rejects duplicate names when `AllowSameTokenName == 0`; once enabled, only the numeric `id` is unique and the human-readable `name`/`abbr` may be freely reused [2](#0-1) . `ExchangeCreateActuator.doValidate()` never checks the reputation, name-authenticity, or issuance history of `firstTokenId`/`secondTokenId` beyond format/balance checks - it only verifies the IDs are well-formed numbers, are not identical, and that the creator holds enough balance to seed the pool [3](#0-2) . An attacker can therefore:
1. Issue a new TRC10 asset with the exact same `name`/`abbr` as a well-known token (e.g. "USDT"), obtaining a distinct token `id`.
2. Call `ExchangeCreateContract` to create a TRX/fake-"USDT" exchange, seeding it with a small amount of TRX and a large supply of the worthless fake token, which sets a favorable price curve for the attacker [4](#0-3) .
3. Publicize the exchange ID (or rely on wallets/tools that resolve exchanges by displayed token name rather than token id) so victims call `ExchangeTransactionActuator`/`ExchangeSellAsset`-style flows and swap real TRX for the fake token, believing it is the genuine asset.

This mirrors the report's core issue: the pool creator supplies trusted-but-unverified parameters (here, the "quote token" is the counterparty TRC10 asset instead of an oracle) that downstream users must implicitly trust when interacting with the pool.

### Impact Explanation
Victims permanently lose real TRX (or a legitimate TRC10 asset) in exchange for a worthless duplicate-named token, i.e., concrete unauthorized transfer/theft of value through a maliciously deployed pool. Because pool creation and asset issuance are both permissionless, any address can repeat this attack cheaply and at scale, and the created exchange is a permanent on-chain object (`ExchangeStore`/`ExchangeV2Store`) that continues to trap value from unaware users.

### Likelihood Explanation
Both `AssetIssueContract` and `ExchangeCreateContract` are ordinary, fee-gated but otherwise unrestricted transactions callable by any account with sufficient balance; no committee/witness/allowlist gating exists for either asset names or exchange token pairs. Given the well-documented history of same-name-token scams within TRC10 ecosystems, this is a straightforward, repeatable attack requiring no special privilege.

### Recommendation
Since `name` collisions cannot be avoided once `AllowSameTokenName` is enabled, `ExchangeCreateActuator` should surface (or wallets/`Wallet`/JSON-RPC query paths should return) the canonical numeric token `id` prominently instead of relying on `name`, and/or the protocol/DAO tooling should provide an authenticated registry mapping trusted `name`s to canonical `id`s so front-ends and exchanges can flag counterfeit-named tokens used in exchange pools before users trade against them.

### Proof of Concept
1. Attacker calls `AssetIssueContract` with `name = "USDT"` (or another well-known symbol) while `AllowSameTokenName == 1`; this succeeds and returns a new token `id` distinct from the genuine USDT-equivalent token, since duplicate-name rejection only applies when `AllowSameTokenName == 0` [2](#0-1) .
2. Attacker calls `ExchangeCreateContract` with `firstTokenId = "_"` (TRX) and `secondTokenId = <fake USDT id>`, seeding a small TRX reserve against a large fake-token reserve; `doValidate()` accepts this because it only checks numeric format, non-equality, and balance sufficiency [3](#0-2) .
3. Victims, seeing an exchange labeled "TRX/USDT", send TRX through the exchange-trade flow and receive the worthless fake token instead of genuine USDT, resulting in a real loss of TRX to the attacker who created and seeded the pool.
