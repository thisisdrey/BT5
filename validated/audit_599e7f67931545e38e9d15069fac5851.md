### Title
StackerDB `write_freq` write-throttle is never enforced on the accept/store path, allowing an authorized slot signer to write chunks at unlimited frequency - (File: stackslib/src/net/stackerdb/db.rs, stackslib/src/net/api/poststackerdbchunk.rs)

### Summary
`StackerDBConfig::write_freq` is documented as "minimum wall-clock time between writes to the same slot" [1](#0-0)  but the only function that actually commits a chunk write, `StackerDBTx::try_replace_chunk`, never checks it. It checks chunk size, slot signer, staleness, and max-writes only, and then unconditionally calls `insert_chunk` [2](#0-1) [3](#0-2) . The remote-facing HTTP write endpoint (`POST /v2/stackerdb/.../chunks`) calls exactly this function with no additional write-frequency gate [4](#0-3) , and the P2P/unsolicited-push acceptance path (`validate_received_chunk`) is explicitly documented as *not* checking write frequency, deferring that responsibility to "the caller" [5](#0-4) , but no caller on the accept side actually performs that check — `write_freq` is only consulted by the *sync/fetch* scheduler when deciding whether to pull an update from a peer [6](#0-5) , not when deciding whether to accept/store an inbound write.

### Finding Description
This is the same class of bug as the Truflation issue: a designed temporal gate ("lock end" / "write_freq cooldown") that is supposed to prevent an action until enough time has elapsed, but is missing from the code path that actually performs the state-changing action, letting an authorized-but-rate-limited party act outside the intended window.

`StackerDBConfig.write_freq` exists specifically to bound how often a given slot owner may write into their StackerDB slot within a reward cycle [7](#0-6) . The error variant `net_error::TooFrequentSlotWrites` even exists to report this violation [8](#0-7) , showing the design intent to enforce it. However:

- `try_replace_chunk` (the sole function that writes a chunk into the DB) validates only chunk size, slot signer/signature, staleness (`slot_version <= slot_validation.version`), and `max_writes` [2](#0-1) . There is no comparison against `slot_validation.write_time + config.write_freq` anywhere in this function, even though `SlotValidation` carries `write_time` [9](#0-8) .
- `validate_received_chunk`, used to gate p2p pushed/gossiped chunks, explicitly disclaims write-frequency checking in its own doc comment: "NOTE: does not check write frequency, since the caller has different ways of doing this" [5](#0-4) .
- The RPC write handler `RPCPostStackerDBChunkRequestHandler::try_handle_request` calls `tx.try_replace_chunk(...)` directly, with only `StaleChunk`/`NoSuchSlot`/`BadSlotSigner`/`ChunkTooBig`/`TooManySlotWrites` handled as rejection cases — there is no `TooFrequentSlotWrites` branch and no separate frequency check before the call [10](#0-9) .
- `handle_unsolicited_StackerDBPushChunk`, the entry point for a remote peer pushing a chunk over the p2p wire, also relies solely on `validate_received_chunk` before accepting/replicating the update, and its own comment confirms write frequency is intentionally skipped here too, on the (mistaken, for the HTTP path) assumption that bandwidth throttling at the conversation layer substitutes for it [11](#0-10) .

So the only place `write_freq` is actually consulted is in `StackerDBSync::find_new_chunks`, when a node decides whether it should *fetch* a peer's already-stored update, based on its own local `write_time` — a fetch-side throttle to avoid re-downloading a slot too often, not a write-side authorization check [12](#0-11) .

This exactly mirrors the equality/temporal-gate failure in M-3: the intended invariant ("you may not act again before time T") is enforced in one code path (peer-sync scheduling / lock display) but omitted from the actual state-mutating path (chunk write / lock extension), letting the authorized actor break the invariant by writing through the unguarded path.

### Impact Explanation
A stacker/signer who legitimately owns a StackerDB slot (has a valid signing key registered for that slot) can submit unlimited, arbitrarily-frequent chunk writes to their own slot via the `POST /v2/stackerdb/:principal/:contract/chunks` endpoint, and each accepted write is relayed as a `StackerDBPushChunk` to the entire network. This defeats the `write_freq` control that StackerDB-consuming applications (e.g., signer message relay contracts) rely on to bound the write budget/rate for their contract's replicas. Since `max_writes` is enforced but is generally set as a large per-reward-cycle budget while `write_freq` is the fine-grained rate control, bypassing `write_freq` lets a single authorized signer flood the replica set / bandwidth of every peer that replicates that StackerDB well beyond what the contract's configuration intends, without needing to compromise any key. This is a state/behavioral-invariant violation reachable by any remote unprivileged (but slot-owning) party — matching the "unauthorized write to state" bug class, though bounded to writes the actor is otherwise entitled to make (just not this often).

### Likelihood Explanation
High likelihood of exploitation for any party that already possesses a valid StackerDB slot signing key (a normal, unprivileged capability for anyone registered as a signer on a StackerDB-controlling contract). No special access, timing race, or additional vulnerability is required — simply repeatedly calling `try_replace_chunk`/POSTing chunks with monotonically increasing `slot_version` bypasses the missing check deterministically every time.

### Recommendation
Enforce `write_freq` inside `StackerDBTx::try_replace_chunk` (the single choke point for all chunk writes), comparing `get_epoch_time_secs()` against `slot_validation.write_time + self.config.write_freq`, returning `net_error::TooFrequentSlotWrites` when violated — mirroring how `slot_version <= slot_validation.version` and `max_writes` are already checked in the same function [13](#0-12) . Additionally wire `TooFrequentSlotWrites` into `poststackerdbchunk.rs`'s error-to-ack mapping and give it a dedicated `StackerDBErrorCodes` variant, since this error branch is currently unhandled in that match and would otherwise be silently classified as an unexpected/server error [14](#0-13) .

### Proof of Concept
1. Deploy/observe a StackerDB-controlling contract with `write-freq: uN` (N seconds) and a signer slot owned by key `K`.
2. Using `K`, sign and `POST` a `StackerDBChunkData` with `slot_version = v+1` to `/v2/stackerdb/<addr>/<contract>/chunks` — accepted, per `try_handle_request` -> `try_replace_chunk` [4](#0-3) .
3. Immediately (well under N seconds later) `POST` again with `slot_version = v+2`, signed by `K`. Since `try_replace_chunk` never compares `write_time` against `write_freq`, this second write is accepted just as fast as the version/signature/size checks allow [15](#0-14) , and it is relayed to the network via `StackerDBPushChunk` [16](#0-15) , bypassing the contract-configured write-frequency budget entirely.
