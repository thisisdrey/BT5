Audit Report

## Title
Underpriced computation in `cancel_item_attributes_approval` via attacker-controlled witness allows disproportionate storage-scan replay - (File: `substrate/frame/nfts/src/features/attributes.rs`)

## Summary
`do_cancel_item_attributes_approval` performs a full `drain_prefix` scan over all attributes stored under `Account(delegate)` for an item before validating the caller-supplied `witness.account_attributes` bound, while the dispatchable's weight is computed from that same attacker-controlled witness value. This decouples the actual O(N) storage iteration cost from the O(1) declared/charged weight when the call intentionally fails with `BadWitness`, enabling cheap repeated replay of expensive scans.

## Finding Description
In `do_cancel_item_attributes_approval`, `Attribute::<T, I>::drain_prefix((&collection, Some(item), AttributeNamespace::Account(delegate.clone())))` unconditionally drains and counts every attribute entry for `(collection, item, delegate)` before the `ensure!(attributes <= witness.account_attributes, Error::<T, I>::BadWitness)` check executes. [1](#0-0) 

Because the check happens after the drain, real computational cost is proportional to the true attribute count under that namespace — fully controlled by the item owner via unbounded `set_attribute` calls. The dispatchable `cancel_item_attributes_approval` in `substrate/frame/nfts/src/lib.rs` weighs the call using `T::WeightInfo::cancel_item_attributes_approval(witness.account_attributes)`, i.e., the attacker-supplied witness value, following the pallet's established convention for witness-bearing calls (the same pattern used for other witness-gated extrinsics such as `destroy` and `clear_all_transfer_approvals`). [2](#0-1) 

Since the call executes inside FRAME's transactional storage layer, a `BadWitness` failure rolls back the drain, restoring the attributes so the attack is repeatable. An attacker can therefore populate N attributes once (via N separately-fee'd `set_attribute` calls) and then repeatedly call `cancel_item_attributes_approval` with `witness.account_attributes = 0`, each time forcing a full O(N) `drain_prefix` iteration while being billed only for the O(1) declared weight of `witness.account_attributes = 0`.

## Impact Explanation
This matches the "public underpriced work that degrades block production" impact category: the fee/weight charged for a failing call is decoupled from the actual iteration/storage-read cost performed by `drain_prefix`, and the attacker controls both the real attribute count and the declared witness used for weighing. Repeated cheap replay forces disproportionate storage-read work per block relative to the weight budget consumed. The blast radius is confined to storage the attacker created themselves (their own item's attributes), so it is not a fund-theft or cross-user lock issue, but it is a legitimate underpriced-computation/DoS-adjacent concern.

## Likelihood Explanation
Exploitation requires only unprivileged, attacker-controlled actions: being the item owner, approving a delegate (potentially themselves or a second controlled account) via `approve_item_attributes`, populating many attributes under `Account(delegate)`, then repeatedly calling `cancel_item_attributes_approval` with a deliberately low witness. No race condition or special privilege is needed; the up-front cost is bounded by deposits/fees for initial attribute creation, after which replay is comparatively cheap and repeatable indefinitely.

## Recommendation
- Validate `witness.account_attributes` against the true count before performing the destructive/iterative work — e.g., count matching entries first (or maintain a per-`(item, delegate)` counter) and `ensure!` the bound prior to invoking `drain_prefix`, or bound iteration by `witness.account_attributes` and reject early on mismatch.
- Ensure `actual_weight` reflects real iteration cost even on the `BadWitness` failure path so failing calls cannot be charged less than the work performed.

## Proof of Concept
1. Attacker mints/owns `item` in `collection`.
2. Attacker approves themselves (or a controlled account) as delegate via `approve_item_attributes`.
3. Attacker calls `set_attribute` many times (e.g., 10,000) with `namespace = Account(delegate)`.
4. Attacker calls `cancel_item_attributes_approval(collection, item, delegate, witness = { account_attributes: 0 })`.
5. `do_cancel_item_attributes_approval` drains and counts all ~10,000 entries, then fails with `Error::BadWitness`; state rolls back via transactional storage.
6. The extrinsic is charged weight for `witness.account_attributes = 0` only, not the O(10,000) work actually performed.
7. Step 4 is repeated indefinitely without recreating attributes, each time incurring the same underpriced O(N) work.
