### Title
Wallet Contract's `has_in_flight_tx` flag is never reset on-chain if a `#[private]` callback receipt itself fails, permanently freezing the ETH-implicit account - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The Sherlock bug class is: an external call in a critical settlement path (`uniswapV3MintCallback`) can revert unexpectedly (e.g. a "revert-on-zero" ERC-20), and because the caller has no defensive handling for that failure mode, the whole operation — and every future operation depending on the same state — becomes permanently unusable (DoS/freeze). The closest concrete analog in nearcore is the `WalletContract` (NEP-518 ETH-implicit account contract), where a stateful "lock" flag (`has_in_flight_tx`) is only cleared inside the very callback receipts that are also the ones capable of failing due to unpredictable behavior of an externally-called contract (a NEP-141 token, the address registrar, or arbitrary `target` accounts).

### Finding Description
`rlp_execute` sets `self.has_in_flight_tx = true` before returning a promise chain and explicitly documents the invariant that this flag "must be `true` when a mutable method of this contract returns a promise and `false` otherwise": [1](#0-0) 

Every downstream callback (`address_check_callback`, `nep_141_storage_balance_callback`, `rlp_execute_callback`) resets this flag as its very first statement: [2](#0-1) [3](#0-2) [4](#0-3) 

For the emulated ERC-20 path, the wallet chains a `storage_balance_of` view call to an arbitrary `target` NEP-141-style contract, then a callback, then (if unregistered) a `storage_deposit` + `ft_transfer` sequence, then a final `rlp_execute_callback`: [5](#0-4) 

nearcore's own execution-model documentation states that when a receipt's execution fails, **all state changes made during that receipt are rolled back**: "failure calls `state_update.rollback()`, discarding all state changes from the receipt." [6](#0-5) 

Because `self.has_in_flight_tx = false` is a state write made *inside* the same callback receipt whose completion is contingent on the behavior of an externally-controlled contract (the `target` NEP-141 token or the address registrar), any failure of that callback receipt itself (not just a graceful `PromiseResult::Failed`, which is explicitly handled) — e.g. the callback running out of the fixed gas budget while processing an oversized/adversarial response, or any other unhandled panic while decoding an attacker-influenced cross-contract result — causes the `has_in_flight_tx = false` write to be rolled back along with everything else in that receipt. This is exactly the same root-cause pattern as the reported Ammplify issue: a critical piece of bookkeeping (clearing a lock / completing a callback) is bundled into the very call that can fail unpredictably because of another contract's behavior, with no separate, guaranteed-to-succeed path to reset it.

Once `has_in_flight_tx` is stuck at `true`, `rlp_execute` unconditionally rejects every future call: [7](#0-6) 

There is no other way to interact with an ETH-implicit account: it cannot have a full access key added, and it cannot be deleted, per the documented account model. [8](#0-7) 

### Impact Explanation
If the flag becomes permanently stuck, the ETH-implicit account is bricked: it can never again process an `rlp_execute` call, meaning any $NEAR or NEP-141 balances controlled by that wallet contract are **permanently frozen** with no possible recovery path (no full-access key, no deletion). This directly matches the "permanent freezing of funds" impact bar.

### Likelihood Explanation
The path is reachable by an ordinary signer/relayer performing a normal `rlp_execute` call for an ERC-20-emulated transfer or an EOA-to-EOA transfer needing address-registrar lookup — both are part of the documented, unprivileged user flow of the Wallet Contract (NEP-518), requiring only that the externally-called `target` contract (a NEP-141 token or the registrar) behave in a way that causes the scheduled callback receipt itself to fail (e.g. via oversized/malformed responses relative to the fixed callback gas budgets `NEP_141_STORAGE_BALANCE_CALLBACK_GAS`/`ADDRESS_CHECK_CALLBACK_GAS`). This does not require any node/network-level compromise, only a misbehaving or adversarial target contract, matching the "no amount>0 check" bug class of an unchecked externally-controlled call failure mode.

### Recommendation
Do not rely on a single privileged callback receipt to both clear the in-flight lock and process potentially attacker-influenced cross-contract data. Options:
- Reset `has_in_flight_tx` in a way that is guaranteed to be committed even if downstream promise/callback processing fails (e.g. schedule the flag-clearing as an independent/first action that cannot be rolled back by later failures in the same logical operation), or
- Add a permissionless "unstick" / timeout mechanism (e.g. based on nonce or block height) that allows clearing `has_in_flight_tx` after a bounded number of blocks if no callback has resolved, so a single failing callback receipt cannot permanently brick the account.

### Proof of Concept
Not applicable as a runnable PoC (index-only analysis); the root cause is architecturally demonstrated by:
1. `has_in_flight_tx` is set `true` in `rlp_execute` [9](#0-8) .
2. It is only ever reset to `false` as the first line inside `address_check_callback` / `nep_141_storage_balance_callback` / `rlp_execute_callback`.
3. If any of these callback receipts fails, `state_update.rollback()` discards that reset along with all other state changes from the receipt [6](#0-5) , leaving `has_in_flight_tx == true` permanently, so all future `rlp_execute` calls are rejected [10](#0-9) .
