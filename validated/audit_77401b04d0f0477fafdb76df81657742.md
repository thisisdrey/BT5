### Title
Signed-integer wraparound of manifest chunk offsets bypasses bounds checks in the MVCC manifest parser - (File: internal/git/mvcc/manifest.go)

### Summary
`ParseManifest()`'s chunk-table parser converts each chunk's file offset from an on-disk `uint64` directly to Go's platform-width signed `int` without range checking. On a 64-bit build, `int` is a signed 64-bit type, so any offset value with the most-significant bit set (`>= 2^63`) silently wraps to a negative number, exactly mirroring the `int256`→`int64` truncation bug class described in the report ("theoretical upper bound not evaluated, downcast is not overflow-checked, and a negative/incorrect result silently passes downstream checks").

### Finding Description
`parseChunks()` reads each TOC entry's offset with: [1](#0-0) 

`binary.BigEndian.Uint64(...)` yields an unsigned 64-bit value fully controlled by the bytes of the manifest file; it is then cast with `int(...)`. If the attacker sets the top bit, the resulting `int` becomes negative. The subsequent bounds check:

```go
if chunkOffsetInFile > dataEnd || nextChunkOffsetInFile > dataEnd || nextChunkOffsetInFile < chunkOffsetInFile {
``` [2](#0-1) 

compares signed integers, so a negative `chunkOffsetInFile` trivially satisfies `chunkOffsetInFile <= dataEnd` and can also satisfy `nextChunkOffsetInFile >= chunkOffsetInFile` for a wide range of crafted `nextChunkOffsetInFile` values, allowing `chunkSize := nextChunkOffsetInFile - chunkOffsetInFile` to become an attacker-chosen large or unexpected value that was never actually validated against the real file bounds. This corrupted `manifestChunk.offset`/`.size` is later used to slice `data[...]` directly (e.g. `data[objsChunk.offset : objsChunk.offset+8]`, `record := data[start : start+pw]`) in `ParseManifest()`: [3](#0-2) [4](#0-3) 

A negative offset/size feeding a Go slice expression panics at runtime (Go slices reject negative indices), producing an unrecovered panic in the parsing goroutine.

### Impact Explanation
`ParseManifest()` is invoked on manifest bytes that are read from disk after being fetched from the configured `ObjectStorage` backend via `LocalCache.prepareManifestFile()` and cached to `.../mvcc/manifests/<hash>` [5](#0-4) . The manifest hash used to select which file is fetched can be attacker-influenced: `Cache.PrepareWithManifest(ctx, hash)` is documented as being used "when the RPC already contains a manifest hash in the metadata", and is invoked from the gRPC `CacheInterceptor` middleware attached to every request against an MVCC-backed repository [6](#0-5) . The SHA-256 trailer check in `ParseManifest` only confirms self-consistency of the bytes (content-addressing), not the semantic validity of the offsets inside them, so a manifest crafted with a valid trailer but malicious TOC offsets will pass the checksum step and reach the wrap-around bug. A crash inside manifest parsing, which runs on every RPC touching an MVCC repository (`Prepare`/`PrepareWithManifest` in `cache.go`), constitutes a denial-of-service of the RPC handler for that repository.

### Likelihood Explanation
Reaching this path requires: (1) the target repository to use the MVCC reference backend, (2) the attacker (an ordinary authenticated client) to be able to place a crafted manifest at a content-addressed location and reference it by hash, either through the object storage put path or by causing the interceptor to resolve to an attacker-influenced hash. The exact mechanism for fully attacker-controlled hash injection via RPC metadata could not be traced further because the code that reads the manifest hash out of gRPC metadata was not found in the indexed subset of the repository; this is a gap in what I could verify from the available code — the plumbing for populating `hash` in `PrepareWithManifest` from request metadata was not located in the search results returned.

### Recommendation
- Bound-check the raw `uint64` offsets before converting to `int`: reject any value greater than `math.MaxInt64` (or, more conservatively, greater than `len(data)`), and perform the `chunkOffsetInFile > dataEnd` comparison using unsigned arithmetic or after confirming the value fits in a non-negative `int`.
- After conversion, explicitly assert `chunkOffsetInFile >= 0` and `nextChunkOffsetInFile >= 0` before doing any subtraction or slicing.
- Apply the same audit to every other raw multi-byte field converted to a native `int`/signed type in this parser (e.g., `pathChunk.size`, `refsChunk.size`, `numPath`, `numRefs`) to ensure consistent, checked arithmetic end-to-end, matching the report's recommendation to use one consistent, range-checked integer type throughout.

### Proof of Concept
Construct a manifest byte stream:
1. Header: magic `"MVCC"`, `version=1`, `numChunks=2`, `pathWidth=4`, `hashAlgo=1`.
2. TOC: chunk 0 = `chunkIDPath`, offset = `0x8000000000000000` (top bit set, becomes negative as `int64`); chunk 1 (terminator) offset = some small in-bounds value, e.g. `24`.
3. Append trailing SHA-256 of everything up to the trailer, as required by `assertManifestSelfNamed`.

Feeding this into `ParseManifest()` causes `chunkOffsetInFile` for the PATH chunk to become negative, `chunkSize := nextChunkOffsetInFile - chunkOffsetInFile` to become a huge/incorrect positive number, and the subsequent `data[start : start+pw]` slicing in the PATH-processing loop to panic with a negative slice index / out-of-range error, crashing the manifest-parsing goroutine for that RPC. func (m *LocalCache) prepareManifestFile(ctx context.Context, hash string) (manifest *Manifest, err error) {
	// Construct the manifest path
	manifestFilePath := filepath.Join(m.storagePath, m.repositoryID, mvccCacheDir, "manifests", hash)

	// Verify if it already exists on the local filesystem or not
	existLocally, err := fileExist(manifestFilePath)
	if err != nil {
		return nil, fmt.Errorf("check if file exists: %w", err)
	}

	if !existLocally {
		// If it does not exist, read content from ObjectStorage
		manifestReader, err := m.rs.ReadManifest(ctx, m.repositoryID, hash)
		if err != nil {
			return nil, fmt.Errorf("read manifest file: %w", err)
		}

		defer func() {
			closeErr := manifestReader.Close()
			err = errors.Join(err, closeErr)
		}()

		// Create the manifest file on the local file system atomically. This is a protection against
		// potential concurrent requests trying to create the same manifest file.
		if err = createFileAtomic(ctx, manifestFilePath, manifestReader); err != nil {
			return nil, fmt.Errorf("write manifest: %w", err)
		}
	}

	// Now that it exist on disk, let's open the file.
	manifestFile, err := os.Open(manifestFilePath)
	if err != nil {
		return nil, fmt.Errorf("opening manifest %s: %w", manifestFilePath, err)
	}

	// Read the content in memory. These files should not be that large.
	// The Manifest parsing logic needs the whole file at once to parse it.
	manifestContent := bytes.Buffer{}
	_, err = manifestContent.ReadFrom(manifestFile)
	if err != nil {
		return nil, fmt.Errorf("reading manifest: %w", err)
	}

	// Return the parsed manifest
	return ParseManifest(manifestContent.Bytes())
