### Title
Unauthenticated `RecvError` packets let an attacker with no CA-signed certificate tear down an established, authenticated tunnel by guessing/spoofing a 32-bit index and the peer's source address - (File: `outside.go`)

### Summary
Nebula's `header.RecvError` message type is processed before any certificate or AEAD authentication check. `readOutsidePackets` dispatches `RecvError` packets straight to `handleRecvError` without requiring a decrypted payload, a matching Noise handshake, or a CA-signed certificate. `handleRecvError` then trusts two attacker-controllable, unauthenticated fields — a 32-bit `RemoteIndex` and the packet's UDP source address — to unconditionally tear down the victim's active, fully-authenticated tunnel for another peer, and also deletes any pending handshake state for it.

### Finding Description
In `readOutsidePackets`, the very first attacker-observable dispatch on packet type routes `header.RecvError` to `f.handleRecvError(via.UdpAddr, h)` before any decryption or certificate check occurs: [1](#0-0) 

`handleRecvError` then:
1. Optionally gates on a config knob (`accept_recv_error`, default `always`).
2. Looks up a hostinfo purely by the attacker-supplied `h.RemoteIndex` via `QueryReverseIndex`, which is populated from wire indexes the responder itself picked and is not otherwise validated.
3. Compares the packet's `via.UdpAddr` to `hostinfo.GetRemote()` — the peer's currently-known remote UDP address — and if they match (or if no remote is set yet), unconditionally closes the tunnel and deletes the pending hostinfo: [2](#0-1) 

This mirrors the DYAD bug class: a piece of shared, security-relevant state (here, "is this tunnel alive") that belongs to a specific victim ("id") is writable by anyone who can produce a low-cost, minimally-authenticated packet ("deposit with a fake vault") that matches only a superficial, spoofable check (source-IP match / valid `id`), and the write is then trusted unconditionally by the legitimate flow (`withdraw` / ongoing tunnel) to make a security/availability decision, with no real cost or identity check on the caller.

### Impact Explanation
An attacker with no CA-signed certificate and no valid session key can force termination of any Nebula tunnel they can address, provided they can:
- Learn (or guess within a 32-bit space) the victim's local index used as key material for `RemoteIndexes`, and
- Match the victim's currently learned remote `UdpAddr` for that peer (trivial if the attacker is on-path, or if UDP source-address spoofing is possible, which is common on networks without BCP38 filtering).

This yields remote, unauthenticated denial of service: repeatedly severing tunnels, forcing constant re-handshakes, and by extension enabling further griefing (e.g., combining with `TestHandshakeWrongResponderPacketStore`/`TestWrongResponderHandshake`-style lighthouse-address confusion windows) without ever presenting a valid identity.

### Likelihood Explanation
The primary practical constraint is guessing the 32-bit `RemoteIndex` and matching the source address of an already-established tunnel; the code does not rate-limit or otherwise increase the cost of a wrong guess, and by default `accept_recv_error` is `always` and `send_recv_error` is `always`, keeping this path fully open. An attacker capable of source-address spoofing (on-path, or many end-user networks) or one who can observe traffic on the wire can trivially learn the correct index/address pair, making exploitation for on-path or address-spoofing-capable attackers straightforward, and off-path exploitation a brute-force but nonzero-probability DoS.

### Recommendation
- Require that `RecvError` (and any other zero-authentication messages) only take effect if they carry data that is cryptographically bound to the actual session (e.g., authenticate it with the current AEAD key or a value derived from it), not just an index + best-effort source-address match.
- Rate-limit and log repeated invalid `RecvError` attempts per source, and consider dropping `RecvError` entirely by default (`accept_recv_error: never`) unless explicitly opted in, since it is a purely optional performance optimization.
- Treat any state mutation triggered by pre-authentication packets (index lookups, remote-address comparisons) as a security boundary: require it to be tied to properties that cannot be forged or brute-forced cheaply (e.g., full 64+ bit random correlation tokens signed by session key material) rather than a raw 32-bit index and IP equality check.

### Proof of Concept
1. Establish a tunnel between `me` and `them` (as in `handshake_manager_test.go`/`tunnels_test.go` helpers).
2. From an attacker-controlled host, spoof the UDP source address to match `them`'s current remote `UdpAddr` as known by `me` (or be on-path to `me` so packets appear from that address).
3. Send a bare `header.RecvError` packet to `me`'s listener with `RemoteIndex` equal to `me`'s local index for the `them` tunnel (brute-forceable over the 32-bit space, or learned via traffic observation).
4. Observe `me` unconditionally calls `f.closeTunnel(hostinfo)` and `f.handshakeManager.DeleteHostInfo(hostinfo)` in `handleRecvError`, tearing down the authenticated tunnel — achieved with zero valid certificate, zero valid session key, and negligible attacker cost, directly analogous to the DYAD `idToBlockOfLastDeposit` griefing pattern. func (f *Interface) handleRecvError(addr netip.AddrPort, h *header.H) {
	if !f.acceptRecvErrorConfig.ShouldRecvError(addr) {
		f.l.Debug("Recv error received, ignoring",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
		return
	}

	if f.l.Enabled(context.Background(), slog.LevelDebug) {
		f.l.Debug("Recv error received",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
	}

	hostinfo := f.hostMap.QueryReverseIndex(h.RemoteIndex)
	if hostinfo == nil {
		f.l.Debug("Did not find remote index in main hostmap", "remoteIndex", h.RemoteIndex)
		return
	}

	hr := hostinfo.GetRemote()
	if hr.IsValid() && hr != addr {
		f.l.Info("Someone spoofing recv_errors?",
			"addr", addr,
			"hostinfoRemote", hr,
		)
		return
	}

	f.closeTunnel(hostinfo)
	// We also delete it from pending hostmap to allow for fast reconnect.
	f.handshakeManager.DeleteHostInfo(hostinfo)
}
