### Title
Attacker can saturate a victim's `depositTokensOfAccount`/`debtTokensOfAccount` set with dust transfers, making `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` invariant checks revert — DoS on deposits, transfers, and liquidation receipt - (File: contracts/DepositToken.sol)

### Summary
The TF bug class is "attacker-controlled input falsifies an internal `CHECK` assertion and crashes the process" (CWE-617, reachable DoS). The Metronome analog is a cardinality invariant the protocol asserts on every balance-list addition — `onlyIfAdditionWillNotReachMaxTokens` on `Pool.addToDepositTokensOfAccount` / `Pool.addToDebtTokensOfAccount` (`contracts/Pool.sol:204-208`) — which an unprivileged attacker can falsify for an arbitrary victim by sending dust `DepositToken.transfer`s of every registered collateral token, filling the victim's `depositTokensOfAccount` set up to `MAX_TOKENS_PER_USER`.

### Finding Description
`DepositToken._transfer` unconditionally registers the recipient in the pool's per-account token set whenever the recipient's prior balance was zero:

```solidity
// contracts/DepositToken.sol:517-520
if (_recipientBalanceBefore == 0 && amount_ > 0) {
    pool.addToDepositTokensOfAccount(recipient_);
}
```

`Pool.addToDepositTokensOfAccount` (and the symmetric `addToDebtTokensOfAccount` at `contracts/Pool.sol:204`) is guarded by `onlyIfAdditionWillNotReachMaxTokens(account_)`, which reverts once the account's set length reaches `MAX_TOKENS_PER_USER`. The set is a `MappedEnumerableSet` (`contracts/lib/MappedEnumerableSet.sol:22-32`), so each distinct token counts once — the attacker only needs to transfer 1 wei of each registered deposit token to the victim.

Attack path (all public entry points, no privileges):
1. Enumerate all registered `DepositToken`s for the pool.
2. For each token the victim doesn't yet hold, call `DepositToken.transfer(victim, 1)`. `transfer` only calls `_revertIfLocked(msg.sender, amount_)` on the *sender* (`contracts/DepositToken.sol:348-354`) — nothing restricts who the recipient is.
3. Each transfer pushes the token into `depositTokensOfAccount[victim]` until the set hits `MAX_TOKENS_PER_USER`.

Once saturated, every subsequent operation that would add a *new* token to the victim's set reverts:
- `DepositToken.transfer` / `transferFrom` of any new msdToken to the victim reverts inside `addToDepositTokensOfAccount`.
- `deposit(amount_, victim)` of a new collateral reverts in `_mint` (`contracts/DepositToken.sol:486-488`), so nobody — including the victim or `SmartFarmingManager` leverage flows — can open a position in a new collateral type for that account.
- `DepositToken.seize` during `Pool.liquidate` routes through `_transfer` (`contracts/DepositToken.sol:343-345`), so a liquidator whose own set is saturated cannot receive that collateral — the assertion falsification propagates to liquidation liveness.

This mirrors the TF advisory exactly: an attacker crafts input (dust transfers / altered SavedModel) that makes an internal consistency check (`CHECK`/`onlyIfAdditionWillNotReachMaxTokens`) fail, converting a previously valid operation into a guaranteed revert.

### Impact Explanation
Temporary freezing of funds / blocked operations for the victim: they cannot deposit new collateral types, cannot receive new msdTokens, and cannot have new debt tokens registered (`_mint` in `DebtToken.sol:598-600` has the same add-on-first-balance pattern, so `issue`/`SmartFarmingManager.leverage` into a new synth also reverts). The freeze lasts until the victim manually empties a slot by transferring dust out — which is only possible for unlocked balances and costs gas per token. Where an attacker controls which token occupies the last slot, liquidations paying out in a new token can also be stalled.

### Likelihood Explanation
Low cost, fully permissionless: the attacker needs only tiny unlocked msdToken balances of each listed collateral (obtainable by depositing dust themselves, or via `transfer` chains) and one `transfer` per token. No governor, keeper, oracle, or LZ component is required. The main limitation is that it is self-healable — a victim can reclaim slots by moving dust — which caps severity at temporary rather than permanent freezing.

### Recommendation
- Do not auto-register recipients on `transfer`/`seize`; only register on `deposit`/`_mint`, or make `addTo*TokensOfAccount` a best-effort `try` that tolerates a full set.
- Alternatively, cap the *set* but treat a saturated set as a soft condition: skip registration rather than reverting, since `debtPositionOf`/`depositOf` only need the set for enumeration of held tokens and a 1-wei entry is economically irrelevant.
- At minimum, allow anyone to call `removeFromDepositTokensOfAccount` semantics via a "sweep dust entry" path, or ignore zero/dust balances during enumeration.

### Proof of Concept
```solidity
// Foundry fork test sketch — victim = alice, pool has N registered DepositTokens
address[] memory dts = pool.getDepositTokens(); // all registered collateral tokens
for (uint i; i < dts.length; ++i) {
    DepositToken dt = DepositToken(dts[i]);
    if (dt.balanceOf(alice) == 0) {
        // attacker deposits 2 wei worth then transfers 1 wei to alice
        dt.transfer(alice, 1); // pushes dts[i] into depositTokensOfAccount[alice]
    }
}
// alice's set is now at MAX_TOKENS_PER_USER

// Any new-token operation for alice now reverts:
vm.expectRevert(); // MaxTokensPerUserReached inside addToDepositTokensOfAccount
newDepositToken.deposit(amount, alice);

vm.expectRevert();
DepositToken(dts[0]).transfer(alice, 1); // even this token if it wasn't pre-seeded
```

The revert behavior of the modifier is implied by its usage and name; the add-on-first-balance logic in `DepositToken.sol:517-520`, `DepositToken.sol:486-488`, and `DebtToken.sol:598-600` is confirmed.
