### Title
No vulnerability found for this question.

### Summary
`ValidateReference` in `internal/git/reference.go` requires that the reference name is fully qualified, i.e. must start with `refs/` [1](#0-0) . Any input beginning with `-` (e.g. `--upload-pack=...` or `-oXXX`) fails this prefix check immediately and is rejected with `"reference is not fully qualified"`, so it can never reach git as an operand, let alone be misinterpreted as a flag.

### Finding Description
The companion function `ValidateRevision` in `internal/git/revision.go`, which is used for the broader `Revision` type (not just fully-qualified reference names), explicitly guards against this exact attack: it checks `bytes.HasPrefix(revision, []byte("-"))` and returns `"revision can't start with '-'"` unless the revision exactly matches one of a small, hardcoded set of pseudo-revisions (`--all`, `--not`, `--branches`, `--tags`, `--alternate-refs`, or prefixes `--branches=`, `--tags=`, `--glob=`) that are only enabled via the explicit `AllowPseudoRevision()` option, not attacker-suppliable arbitrary strings [2](#0-1) . This means a leading-dash value is rejected as invalid input by both validators before ever being handed to a git subprocess as a bare operand.

Checking the caller `UpdateReferences` in `internal/gitaly/service/ref/update_references.go`, it calls `git.ValidateReference(reference)` on every attacker-supplied reference name before passing it to `updater.Update(...)`, so a `-`-prefixed "reference" is rejected at the RPC boundary [3](#0-2) .

The invariant described in the question ("revision passed after `--` or rejected as an option") is upheld by rejection: `ValidateReference` refuses anything not prefixed with `refs/`, and `ValidateRevision` explicitly refuses anything prefixed with `-` outside of a fixed allowlist of pseudo-revisions that are not attacker-controllable strings.

### Impact Explanation
No exploitable impact identified. Both validators reject a leading-`-` value before it can reach a spawned git process as an operand that could be misparsed as an option, `-c` config override, or transport helper (`ext::`).

### Likelihood Explanation
Not applicable — the code path rejects the malicious input at validation time regardless of attacker capability.

### Recommendation
No change required for this specific concern. General hardening recommendation (not a vulnerability): continue to route validated revisions/references through `--end-of-options`/`--` boundaries in `gitcmd` command construction for defense-in-depth in any callers that might bypass or omit `ValidateReference`/`ValidateRevision`.

### Proof of Concept
Not applicable; a Go unit test confirms rejection:
```go
if err := git.ValidateReference("-oXXX"); err == nil {
    t.Fatal("expected error for leading dash reference")
}
if err := git.ValidateRevision([]byte("--upload-pack=/bin/sh")); err == nil {
    t.Fatal("expected error for leading dash revision")
}
```
Both calls return errors (`"reference is not fully qualified"` and `"revision can't start with '-'"` respectively), confirming no injection is possible via this path.
