The claim is confirmed by direct code inspection.

`process_delivery_receipt` decodes and stores the `success` field into `DeliveryReceipt` but the function body only checks `receipt.gateway` and looks up `PendingOrders` by `receipt.nonce` — it never inspects `receipt.success` before calling `T::RewardPayment::register_reward` and removing the pending order [1](#0-0) . The `success` field is decoded from the Ethereum `InboundMessageDispatched` event log into `DeliveryReceipt.success` [2](#0-1)  and populated in the `TryFrom<&Log>` conversion [3](#0-2) , but a grep across the entire `bridges/snowbridge` tree shows the only reference to `.success` on this struct is its own definition/assignment — it is never read anywhere in the reward/order-clearing logic. The public extrinsic `submit_delivery_receipt` verifies the proof, decodes the receipt, and passes it straight to `process_delivery_receipt` with no additional gating [4](#0-3) .

Audit Report

## Title
Snowbridge v2 outbound queue pays relayer rewards for failed Ethereum executions - (File: `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs`)

## Summary
`process_delivery_receipt` registers a relayer reward and removes the `PendingOrder` for any nonce with a valid gateway-signed proof, without checking the `receipt.success` flag that reports whether the Ethereum-side execution actually succeeded. A relayer can therefore submit proof of a reverted/failed message delivery and still be paid the full order fee.

## Finding Description
The Ethereum gateway emits `InboundMessageDispatched(nonce, topic, success, reward_address)` which is decoded into `DeliveryReceipt { gateway, nonce, topic, success, reward_address }` in `TryFrom<&Log>`. `submit_delivery_receipt` verifies the Merkle/log proof via `T::Verifier::verify`, decodes the log into a `DeliveryReceipt`, and calls `Self::process_delivery_receipt(relayer, receipt)`. Inside `process_delivery_receipt`, the only checks performed are: (1) `receipt.gateway` matches `T::GatewayAddress`, and (2) a `PendingOrder` exists for `receipt.nonce`. If both pass, the fee is registered as a reward via `T::RewardPayment::register_reward` and the `PendingOrder` is removed unconditionally. `receipt.success` is decoded but never read in this control flow, so a genuine, correctly-proven `success == false` event is treated identically to a `success == true` event.

## Impact Explanation
This breaks the invariant that bridge relayer rewards must only be paid for successfully executed cross-chain messages. Every failed/reverted Ethereum-side execution still drains the reward pool for the full order fee, which is an unbacked/duplicate payout in the bridge reward flow, matching the "theft or unbacked mint/unlock" and "duplicate settlement or payout" categories of the impact gate.

## Likelihood Explanation
The path is fully public and unprivileged: any signed account can call `submit_delivery_receipt` with a legitimately verifiable proof of a real (but failed) `InboundMessageDispatched` event. No malicious relayer/validator/governance assumption is needed — the exploit only requires that the intended message dispatch fails on Ethereum (e.g., due to insufficient gas at call-time, reverted downstream call, etc.), which is a normal, expected occurrence in bridge operation, not a contrived edge case. The existing nonce/gateway checks prevent double-claiming but do nothing to gate on outcome.

## Recommendation
In `process_delivery_receipt`, branch on `receipt.success` before calling `register_reward`. On `false`, either skip the reward entirely (and still clear/mark the `PendingOrder` to avoid resubmission spam) or apply an explicitly documented reduced reward policy for failed-but-attempted deliveries. If paying regardless of `success` is truly intended, the field should be formally documented as unused for reward purposes and the security assumption stated explicitly, since as written it looks like an unintentional omission of an outcome check.

## Proof of Concept
1. Dispatch an outbound message via `do_process_message`, creating a `PendingOrder { nonce, fee, .. }`.
2. On Ethereum, the message dispatch reverts, and the gateway emits `InboundMessageDispatched(nonce, topic, success=false, reward_address)`.
3. Any signed relayer builds an `EventProof` for this real log and calls `submit_delivery_receipt(origin, event)`.
4. `T::Verifier::verify` succeeds (proof is valid), `DeliveryReceipt::try_from` succeeds with `success == false`.
5. `process_delivery_receipt` finds the matching `PendingOrder`, calls `T::RewardPayment::register_reward(&reward_account, DefaultRewardKind, order.fee)`, and removes the order — despite `success == false`.
6. The relayer calls `BridgeRelayers::claim_rewards` and receives `order.fee` for a message that never successfully executed on Ethereum. [5](#0-4)
