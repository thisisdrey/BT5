### Title
Unbounded memory growth via `sock.read_to_end` in `run_http_request` (StackerDB HTTP client) - (File: libsigner/src/http.rs)

### Summary
`run_http_request` reads an entire HTTP response into memory with `sock.read_to_end(&mut buf)` before any parsing or length validation occurs. A malicious or compromised Stacks node that a signer's `StackerDBSession` connects to can stream an unbounded response body (or simply trickle bytes slowly) and force the signer client to buffer data without limit until the process runs out of memory.

`buf` is a plain `Vec<u8>` with no capacity cap, and `read_to_end` will not return until the peer closes the socket (EOF) or an I/O error occurs — it performs no inspection of HTTP headers, `Content-Length`, or chunked terminators while accumulating data. Only *after* this unbounded read completes does the code call `decode_http_response(&buf)` to actually validate/parse the response: [2](#0-1) 

All of the size-bounding logic that exists in this file — `MAX_HTTP_HEADER_LEN`, `MAX_HTTP_HEADERS`, and the `MAX_MESSAGE_LEN` cap in `decode_http_body`'s chunked reader — is applied only to already-buffered data, i.e., strictly after the unbounded `read_to_end` call. There is no read-size limit, no `take()` wrapper, and no evidence of a bound applied to `buf`'s growth. A malicious node can respond with headers claiming `Transfer-Encoding` is absent and `Content-Length` is absent (or lie about it, since nothing enforces it before buffering), and then simply stream arbitrary bytes (or trickle a few bytes periodically to dodge any socket read timeout that might exist at the transport layer) — the vector grows without bound as long as the connection remains open.

### Impact Explanation
A single malicious StackerDB host response can force the signer client to allocate memory indefinitely, exhausting the process's memory and crashing or hanging the signer (`stacks-signer`) that depends on `libsigner`'s `StackerDBSession`/`run_http_request` for RPC calls (see `stacks-signer/src/client/stackerdb.rs`). This is an unauthenticated remote DoS reachable by any node the signer is configured to talk to that can be attacker-controlled or compromised, matching the Critical category (remote crash/unauthenticated DoS from a small number of messages/connections).

### Likelihood Explanation
The precondition is that the signer's configured Stacks node (or an entity able to man-in-the-middle/impersonate it) is malicious or compromised — this is within the described threat model since the signer's `StackerDBSession` performs `rpc_request`/`run_http_request` against the configured node's RPC endpoint. No secret, authentication, or privileged role is required from the attacker beyond being the node the client connects to; the attacker only needs to keep the TCP connection open and stream/trickle bytes, which is a low-cost, easily repeatable attack.

### Recommendation
Bound the response read in `run_http_request` (e.g., wrap `sock` with `Read::take(MAX_MESSAGE_LEN)` or an equivalent capped reader) before parsing, or read/parse headers first and enforce `Content-Length`/chunked limits incrementally instead of buffering the entire socket stream via `read_to_end` up front.

### Proof of Concept
Rust test plan:
1. Spin up a local `TcpListener` that accepts connections, reads the incoming HTTP request, then writes a valid status line + a header set omitting `Content-Length` and `Transfer-Encoding`, and continuously writes garbage bytes (or writes 1 byte every few hundred milliseconds) to the socket without ever closing it.
2. Call `run_http_request(&mut socket, ...)` against this server from a test using `TcpStream::connect`.
3. Assert that `run_http_request` either returns an error/aborts once a fixed byte threshold (e.g., `MAX_MESSAGE_LEN`) is exceeded, or that the call is time-bounded independent of attacker send rate.
4. Observe in the current implementation that `buf.len()` in `sock.read_to_end(&mut buf)` (`libsigner/src/http.rs:251`) grows unbounded and the call never returns while the server keeps streaming/trickling data, demonstrating the missing size cap.
