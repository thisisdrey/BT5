### Title
Unbounded `signer_signature` vector permits attacker-controlled loop of expensive ECDSA-recovery operations per pushed/uploaded Nakamoto block - (File: stackslib/src/chainstate/nakamoto/mod.rs)

### Summary
`NakamotoBlockHeader::signer_signature` is deserialized without any element-count cap (unlike the sibling field `problematic_txs`, which is explicitly bounded via `read_next_at_most(fd, MAX_PROBLEMATIC_TX_MARKERS as u32)`), and `verify_signer_signatures` iterates over every entry in that vector performing an expensive `secp256k1` public-key-recovery for each one, before any check compares the vector's length to the (bounded) reward-set size.

### Finding Description
`NakamotoBlockHeader::consensus_deserialize` reads `signer_signature` with a plain `read_next(fd)` call and no `read_next_at_most` bound: [1](#0-0) 

Contrast this with the immediately following field, `problematic_txs`, which the code explicitly caps: [2](#0-1) 

The only limit on the header's serialized size comes from the outer `NakamotoBlock::consensus_deserialize`, which wraps the whole block (header + txs) in a `BoundReader` capped at `MAX_MESSAGE_LEN`: [3](#0-2) 

Since each `MessageSignature` is a fixed 65-byte recoverable ECDSA signature, an attacker can pack `signer_signature` with tens of thousands of garbage-but-well-formed 65-byte signatures (limited only by `MAX_MESSAGE_LEN`), each of which is syntactically valid and will pass deserialization.

This attacker-controlled vector then flows directly into `NakamotoBlockHeader::verify_signer_signatures`, which loops over every entry and performs a full elliptic-curve public-key recovery (`Secp256k1PublicKey::recover_to_pubkey_without_validating_low_s`) *before* checking whether the recovered key belongs to the (bounded, typically small) reward set: [4](#0-3) 

There is no early bound check (e.g., `signer_signature.len() <= reward_set.signers().len()`) prior to this loop, so the cost of `verify_signer_signatures` scales with the attacker-supplied signature count, not with the actual (small) number of legitimate signers.

This function is reachable from at least two remote, unauthenticated/low-authentication paths in scope:
1. P2P-pushed Nakamoto blocks, validated in `Relayer::validate_nakamoto_blocks_push`, which calls `verify_signer_signatures` for every block in an unsolicited `NakamotoBlocksData` push before any stake/state check beyond basic sortition lookup: [5](#0-4) [6](#0-5) 

2. Unsolicited/gossip signature checks against cached reward sets via `PeerNetwork::check_nakamoto_block_signer_signature`: [7](#0-6) 

3. `NakamotoChainState::accept_block`, used for both relayed and HTTP-uploaded blocks, which also calls `verify_signer_signatures` after only lightweight burnchain/static checks: [8](#0-7) 

While `NakamotoBlocksData::consensus_deserialize` bounds the *number of blocks* per message to `NAKAMOTO_BLOCKS_PUSHED_MAX`: [9](#0-8) 

it does nothing to bound the *signature count per block*, so a small number of blocks (or even one, via the unauthenticated `/v3/blocks/upload/` HTTP endpoint) can still carry an oversized `signer_signature` vector.

### Impact Explanation
This matches the "bounded compute DoS on a read/write endpoint" category: each such crafted block forces the node to perform thousands of costly EC public-key recoveries before rejecting the block (rejection only happens once an unrecognized public key is found or the loop completes), consuming CPU disproportionate to the tiny amount of network bandwidth/data required to trigger it. This can be repeated cheaply and remotely against any node's p2p or HTTP block-ingestion path, degrading availability without requiring any privileged key or node secret.

### Likelihood Explanation
Likelihood is high for triggering the expensive loop (no authentication or stake is required to submit a syntactically-valid block header with a bloated `signer_signature` list), but the *ultimate* rejection is guaranteed (since bogus signatures won't map to reward-set members), meaning this is a repeatable CPU-exhaustion vector rather than a state-corruption bug. It requires the attacker to be able to reach either p2p push/gossip handling or the HTTP block-upload endpoint, both of which are ordinarily open to any connected peer/client.

### Recommendation
Enforce an explicit upper bound on `signer_signature.len()` during `NakamotoBlockHeader::consensus_deserialize` (e.g., using `read_next_at_most` with a bound derived from the maximum possible reward-set size, mirroring the treatment already given to `problematic_txs`), and/or add a cheap length check inside `verify_signer_signatures` (`if self.signer_signature.len() > signers.len() { return Err(...) }`) before entering the per-signature recovery loop, so that an oversized signature vector is rejected without doing any expensive cryptographic work.

### Proof of Concept
1. Craft a `NakamotoBlock` whose header contains a `signer_signature` vector filled with, e.g., 15,000 arbitrary (but well-formed, 65-byte) `MessageSignature` values — the block otherwise passes the cheap static/burnchain checks in `validate_normal_nakamoto_block_burnchain` / `validate_nakamoto_block_static`.
2. Ensure the encoded block still fits within `MAX_MESSAGE_LEN` (each signature costs 65 serialized bytes plus the transaction/tx-merkle-root consistency, which is independent of `signer_signature`).
3. Submit the block either:
   - as a p2p `NakamotoBlocks` push to a peer (reaches `Relayer::validate_nakamoto_blocks_push` → `verify_signer_signatures`), or
   - via the unauthenticated `/v3/blocks/upload/` HTTP endpoint (`postblock_v3.rs`), which eventually reaches `NakamotoChainState::accept_block` → `verify_signer_signatures`.
4. Observe that the victim node performs ~15,000 `secp256k1` public-key recoveries per submitted block before rejecting it, and repeat the submission to sustain elevated CPU load — all while the true number of registered signers may be only a few dozen.

*Note: I was not able to fully confirm the exact numeric value of `MAX_MESSAGE_LEN` (present in `stackslib/src/net/codec.rs` but its value definition was not returned by search), which determines the maximum achievable `signer_signature` length; this only affects the magnitude of the achievable amplification, not the validity of the missing-bound finding itself.*
