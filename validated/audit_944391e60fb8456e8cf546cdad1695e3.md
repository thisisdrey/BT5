### Title
Unbounded growth of `DelegatedResourceAccountIndexCapsule.toAccounts`/`fromAccounts` lists causes denial-of-service on victim accounts - (File: `actuator/src/main/java/org/tron/core/actuator/FreezeBalanceActuator.java`)

### Summary
When `ALLOW_DELEGATE_OPTIMIZATION` (default `0`, a committee-toggled chain parameter) is not yet enabled, every call to `FreezeBalanceActuator.delegateResource()` (also mirrored in `UnfreezeBalanceActuator` and the legacy delegate paths) appends the counterpart address into a single, address-keyed `DelegatedResourceAccountIndexCapsule` record via `addToAccount`/`addFromAccount`, with no upper bound on list size. This is the same bug class as the Radiant `userEarnings` DoS report: an unbounded repeated field keyed to one account that any unprivileged caller can force to grow.

### Finding Description
`FreezeBalanceActuator.delegateResource()` builds two index records, one for the delegator and one for the receiver, and appends to their repeated fields whenever a *new* counterpart address is used: [1](#0-0) 

The append operations go through `DelegatedResourceAccountIndexCapsule.addToAccount`/`addFromAccount`, which unconditionally grow the underlying protobuf repeated field with no cap: [2](#0-1) 

Because `FreezeBalanceContract` lets the caller pick an arbitrary `receiver_address` (subject only to `dynamicStore.supportDR()` / receiver-existence checks, not to any relationship whitelist, minimum-amount check, or per-account rate limit), an attacker can:
1. Freeze the minimum allowed TRX balance to themselves (`FreezeBalanceActuator` requires only `frozen_balance >= 1_000_000` SUN, i.e. 1 TRX) with a distinct receiver address on each transaction, or
2. Repeatedly delegate to a *victim's* address from many different sender accounts.

Each distinct new counterpart address adds one entry to the `toAccounts`/`fromAccounts` list of the corresponding `DelegatedResourceAccountIndexCapsule`, which is stored and retrieved as a single value under one DB key (`delegatedResourceAccountIndexStore.get(ownerAddress)` / `.get(receiverAddress)`). There is no maximum size enforced anywhere in `FreezeBalanceActuator.validate()` for this list, unlike `UnfreezeBalanceV2Actuator`, which explicitly caps entries at `UNFREEZE_MAX_TIMES = 32` for the newer `unfrozenV2` list: [3](#0-2) 

The legacy delegated-index path has no equivalent guard, so the list on a victim's `DelegatedResourceAccountIndexCapsule` can be grown indefinitely by cheap, repeated 1-TRX freeze/delegate transactions from many distinct sender addresses, exactly mirroring the Radiant `userEarnings` array-growth DoS: unbounded per-account repeated-field growth reachable from an unprivileged, low-cost transaction, with no minimum-amount threshold and no access control on who may target a given account as `receiverAddress`.

The chain already recognizes this exact bug class and mitigated it via the `ALLOW_DELEGATE_OPTIMIZATION` proposal, which switches the index storage model to per-pair keys (`delegate()`/`convert()` in `DelegatedResourceAccountIndexStore`) instead of a single growing list: [4](#0-3) 

However, this flag defaults to `0` (disabled) both in `CommonParameter`/`reference.conf` and as the initial value saved by `DynamicPropertiesStore` unless a committee proposal (`ProposalType.ALLOW_DELEGATE_OPTIMIZATION`, code 69) has been passed and takes effect on the network: [5](#0-4) [6](#0-5) 

So on any network/point in the chain's history where this committee proposal has not yet been activated, the vulnerable legacy code path in `FreezeBalanceActuator.delegateResource()` (and correspondingly `UnfreezeBalanceActuator`'s cleanup logic that reads/removes from the same lists) remains fully reachable by ordinary signed transactions.

### Impact Explanation
Once a targeted account's `DelegatedResourceAccountIndexCapsule.toAccounts`/`fromAccounts` list grows large enough, any operation that must load and iterate/serialize that record — later delegate/freeze/unfreeze calls, `getIndex()` lookups (`DelegatedResourceAccountIndexStore.getIndex`), or wallet/API queries returning that capsule — becomes increasingly expensive, and beyond a certain size will exceed available energy/CPU-time limits or cause transactions touching that account to fail deterministically (denial-of-service). This can permanently brick further freeze/unfreeze/delegate interactions for the victim account, matching the "permanent freezing of funds / node can no longer serve request" impact bar.

### Likelihood Explanation
Exploitation only requires the minimal `frozen_balance` (1 TRX, refundable after the freeze duration) sent to a chosen `receiver_address` with `is_delegate_resource = true`, repeated from many attacker-controlled addresses. No special privilege, witness role, or contract deployment is needed — a single unprivileged transaction broadcaster can execute the attack cheaply and repeatedly, limited only by transaction fees and by whether `ALLOW_DELEGATE_OPTIMIZATION` has already been activated on the target network.

### Recommendation
Enforce a maximum size on `DelegatedResourceAccountIndexCapsule.toAccounts`/`fromAccounts` (analogous to `UnfreezeBalanceV2Actuator.UNFREEZE_MAX_TIMES`) in `FreezeBalanceActuator.validate()`/`delegateResource()`, or ensure `ALLOW_DELEGATE_OPTIMIZATION` (or an equivalent per-pair key storage model) is unconditionally enabled/hard-forced on all networks rather than left as an optional committee proposal, so the legacy unbounded-list code path can never execute.

### Proof of Concept
1. Attacker controls N funded addresses `A1..AN` (each needs only ≥1 TRX to freeze).
2. On a network where `ALLOW_DELEGATE_OPTIMIZATION` has not been enabled (`supportAllowDelegateOptimization() == false`), from each `Ai` broadcast a `FreezeBalanceContract` with `frozen_balance = 1_000_000`, `is_delegate_resource = true`, `receiver_address = victim`.
3. Each transaction executes `FreezeBalanceActuator.delegateResource()`, appending `Ai` to `victim`'s `DelegatedResourceAccountIndexCapsule.fromAccounts` list via `addFromAccount` ( [7](#0-6) ) with no cap check.
4. Repeat with thousands of distinct addresses; the victim's index record grows unbounded, degrading or breaking any subsequent operation (including the victim's own unfreeze/undelegate flow) that must read or rewrite that capsule.

  public void removeFromAccount(ByteString fromAccount) {
    if (getFromAccountsList().contains(fromAccount)) {
      List<ByteString> fromList = new ArrayList<>(getFromAccountsList());
      fromList.remove(fromAccount);
      setAllFromAccounts(fromList);
    }
  }

  public List<ByteString> getToAccountsList() {
    return this.delegatedResourceAccountIndex.getToAccountsList();
  }

  public void setAllToAccounts(List<ByteString> toAccounts) {
    this.delegatedResourceAccountIndex = this.delegatedResourceAccountIndex.toBuilder()
        .clearToAccounts()
        .addAllToAccounts(toAccounts)
        .build();
  }

  public long getAllowDelegateOptimization() {
    return Optional.ofNullable(getUnchecked(ALLOW_DELEGATE_OPTIMIZATION))
        .map(BytesCapsule::getData)
        .map(ByteArray::toLong)
        .orElseThrow(
            () -> new IllegalArgumentException("not found ALLOW_DELEGATE_OPTIMIZATION"));
  }

  public boolean supportAllowDelegateOptimization() {
    return getAllowDelegateOptimization() == 1L;
  }

  public void saveAllowDelegateOptimization(long value) {
    this.put(ALLOW_DELEGATE_OPTIMIZATION, new BytesCapsule(ByteArray.fromLong(value)));
