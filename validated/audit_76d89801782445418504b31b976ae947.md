### Title
Missing verifier/contract domain separator in `ValidateMultiSign`/`BatchValidateSign` TVM precompiles allows signature replay across unrelated smart contracts - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The TVM precompiles `ValidateMultiSign` (`validatemultisign(address,uint256,bytes32,bytes[])`) and `BatchValidateSign` let any deployed smart contract verify off-chain ECDSA signatures against a TRON account's multi-sig `Permission`. The digest that is actually signed and recovered is built only from the account address, permission id, and an arbitrary caller-supplied 32-byte `data` value — it contains no domain separator tying the signature to the calling contract, the chain, or any nonce. Consequently a single off-chain signature produced for one contract can be replayed verbatim against any other contract on the same chain that calls the same precompile with the same `(address, permissionId, data)` tuple, exactly mirroring the CrosschainMerkleDistributor "lack of domain separator" bug class.

### Finding Description
`ValidateMultiSign.execute()` builds the signed hash as: [1](#0-0) 
There is no inclusion of `msg.sender`/the calling contract address, no chain id, and no distributor/application-specific salt — only the target account address, the permission id, and the raw `data` word supplied by the calling contract. `recoverAddrBySign` then recovers the signer purely from this hash: [2](#0-1)  and the recovered address is checked only against the target account's `Permission` weight table via `TransactionCapsule.getWeight` [3](#0-2) .

The Solidity-facing signature of this precompile, `validatemultisign(address,uint256,bytes32,bytes[])`, confirms that the only inputs bound into the digest are `address`, `uint256 permissionId`, and a `bytes32 data` hash chosen by the calling contract: [4](#0-3) . `BatchValidateSign` has the identical structural weakness — it recovers signers against a caller-supplied `hash` with no contract-binding component: [5](#0-4) .

Because Tron, like Tokensoft's off-chain provider, offers this precompile as a generic building block for third parties to implement signature-authorized flows (claim/whitelist/approval systems) on top of TVM smart contracts, and because the digest is not bound to the verifying contract's own address or chain id, any two independently deployed contracts that end up requesting validation with the same `(address, permissionId, data)` triple will both accept the identical signature. An off-chain signature a user produces to authorize one contract's operation (e.g. "claim my allotment for permissionId 0, dataHash X") is therefore replayable against a second, unrelated contract that happens to derive the same `data` value (e.g. the same encoded amount/nonce scheme), without any action from the signer.

### Impact Explanation
A user's single off-chain authorization signature can be reused to authorize the same weight-satisfying action on a different smart contract than the one it was created for, exactly as in the reported Tokensoft `CrosschainMerkleDistributor` finding. This can result in unauthorized execution of privileged application logic (e.g., a claim, an approval, a withdrawal gate) on a contract the signer never intended to authorize, leading to theft of funds or state manipulation controlled by that second contract, whenever application developers rely on `validatemultisign`/`batchvalidatesign` without independently embedding their own contract-address/chain-id/nonce salt into `data`.

### Likelihood Explanation
Any unprivileged contract deployer can build a contract that calls `validatemultisign`/`batchvalidatesign`, and any unprivileged caller can supply the recovered signature to trigger the actuator/precompile path — no special privilege is required. The precondition (two independently deployed contracts using the same `address`/`permissionId`/`data` encoding scheme) is plausible for common patterns such as "same total claimed amount" or "same fixed nonce," matching the exact caveat noted in the original report.

### Recommendation
Bind the digest computed inside `ValidateMultiSign`/`BatchValidateSign` to the calling contract's own address (and ideally the chain id/genesis block id) in addition to the account/permissionId/data, so a signature valid for one contract cannot be replayed against another. Document clearly for TVM contract developers that they must include their own contract address as part of the signed payload if this level of protection is not enforced at the precompile level.

### Proof of Concept
1. Deploy `ContractA`, which calls `validatemultisign(beneficiary, 0, dataHash, sigs)` to authorize releasing `amount` tokens to `beneficiary`, where `dataHash = keccak256(abi.encode(amount))`.
2. `beneficiary` signs `dataHash` off-chain to authorize the claim on `ContractA`, satisfying `TransactionCapsule.getWeight`/threshold via the precompile at [6](#0-5) .
3. Deploy `ContractB` (an unrelated distributor, e.g. from a different customer) that also computes `dataHash = keccak256(abi.encode(amount))` for the same `amount` and calls `validatemultisign(beneficiary, 0, dataHash, sigs)` with the identical signature captured from step 2.
4. Because the precompile's digest at lines 1062-1064 never includes `ContractA`'s or `ContractB`'s address, `ValidateMultiSign` returns `true` for `ContractB` as well, letting an attacker replay `beneficiary`'s single signature to also unlock funds/logic gated by `ContractB` — without `beneficiary` ever having signed anything for `ContractB`.
