Audit Report

## Title
`ERC20Transactor::withdraw_asset_with_surplus` and `deposit_asset_with_surplus` trust the ERC20 `transfer()` boolean return value instead of verifying actual balance movement - ([File: cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs])

## Summary
`ERC20Transactor` implements XCM's `TransactAsset` for ERC20-backed assets matched via `ERC20Matcher` (`cumulus/parachains/runtimes/assets/common/src/lib.rs:159-160`), which uses `IsLocalAccountKey20`/`AccountKey20ToH160` to match *any* `AccountKey20`-keyed location without any governance-curated registry check. Both `withdraw_asset_with_surplus` and `deposit_asset_with_surplus` credit/debit the XCM holding register and the shared `TransfersCheckingAccount` pool with the full nominal `amount` solely because the ABI-decoded boolean return of `IERC20::transferCall` is `true`, without ever comparing `balanceOf` before/after the call.

## Finding Description
`withdraw_asset_with_surplus` calls `transfer(checking_address, amount)` on the arbitrary contract identified by `asset_id` and, upon a `true` return, creates `AssetsInHolding::new_from_fungible_credit(what.id.clone(), Box::new(Erc20Credit(amount)))` — crediting the exact nominal `amount` regardless of what the checking account actually received: [1](#0-0) . Symmetrically, `deposit_asset_with_surplus` transfers from the checking account to the beneficiary and treats `Ok(true)` as full success with no delta verification: [2](#0-1) .

The `Erc20Credit` imbalance type is explicitly documented as bypassing runtime-level enforcement, relying entirely on the target contract's own accounting: [3](#0-2) .

Critically, the asset matcher does not restrict which contracts can be used — `ERC20Matcher` matches any `(0, [AccountKey20{..}])` location via `IsLocalAccountKey20`, converting the key directly to an `H160` with no allowlist/registry: [4](#0-3) . This confirms any deployed contract (standard or non-standard, e.g. fee-on-transfer/rebasing tokens) can be referenced by XCM as an "asset" through this transactor, consistent with the PR description that explicitly allows *any* ERC20 to be referenced by address, with no per-contract vetting: [5](#0-4) . This is wired into `asset-hub-westend`'s `AssetTransactors` tuple, so it is live in the XCM executor's transact path: [6](#0-5) .

The only existing guards are (a) checking `did_revert()` and (b) ABI-decoding the boolean return — neither of which detects a real-but-partial transfer (e.g., a standard, non-malicious fee-on-transfer ERC20 that legitimately deducts a fee yet still returns `true`). No `balanceOf` diff is performed anywhere in either function.

## Impact Explanation
Because the `TransfersCheckingAccount` is a single shared pooled account per ERC20 contract backing all users' deposits of that asset, a discrepancy between the nominal `amount` XCM credits/debits and the real ERC20 balance delta lets an attacker repeatedly withdraw-then-deposit using a fee-on-transfer/rebasing token: each withdraw credits holding with full `amount` while checking account only nets `amount - fee`; a follow-up deposit instruction then transfers the full nominal `amount` back out of checking to an attacker-controlled beneficiary. Repeating this cycle drains real value from the shared checking pool (and thus from other legitimate holders of the same ERC20-backed asset) beyond what the attacker ever deposited — a theft of pooled/shared funds, and a violation of the required invariant that contract-held value conserve exactly. This matches the Impact Gate's "theft ... or unlock" and "runtime bugs that compromise intended behavior" categories.

## Likelihood Explanation
No malicious relayer, validator, or privileged actor is required. Any ordinary user can invoke `withdraw_asset_with_surplus`/`deposit_asset_with_surplus` via standard XCM `WithdrawAsset`/`DepositAsset` instructions referencing any `AccountKey20` location, since `ERC20Matcher` is unrestricted (`cumulus/parachains/runtimes/assets/common/src/lib.rs:159-160`). The trigger condition — a non-standard-but-legitimate ERC20 with transfer fees, rebasing, or similar quirks — is common in real-world tokens, not a hypothetical. This is repeatable indefinitely against the shared checking-account pool.

## Recommendation
Replace boolean-return trust with an explicit `balanceOf` delta check on the checking account (and/or beneficiary) before and after the `transfer` call in both `withdraw_asset_with_surplus` and `deposit_asset_with_surplus`, crediting/debiting the *observed* delta rather than the requested `amount`, and erroring (not silently under/over-crediting) on mismatch.

## Proof of Concept
1. Deploy a standard-compliant but fee-on-transfer ERC20 contract (returns `true`, deducts e.g. 1% fee on every `transfer`).
2. Reference it as an XCM asset via its `AccountKey20` location on `asset-hub-westend` (no registration required, per `ERC20Matcher`).
3. Attacker A sends `WithdrawAsset` for `amount` X of this asset from A's own account: `withdraw_asset_with_surplus` calls `transfer(checking, X)`, checking account nets `X*0.99`, but holding is credited the full `X` (`erc20_transactor.rs:195-203`).
4. In the same or a follow-up XCM program, A sends `DepositAsset` for the credited `X` to A's own beneficiary address: `deposit_asset_with_surplus` calls `transfer(A, X)` from the checking account (`erc20_transactor.rs:253-266`), which succeeds as long as checking's pooled balance (from other depositors) covers `X`.
5. Net effect per cycle: checking account loses `X*0.01` more than it should, funded by the pool contributed by other users of the same asset; repeating step 3-4 drains the shared checking account.

/// `Contains<Location>` implementation that matches locations with no parents,
/// a `PalletInstance` and an `AccountKey20` junction.
pub struct IsLocalAccountKey20;
impl Contains<Location> for IsLocalAccountKey20 {
	fn contains(location: &Location) -> bool {
		matches!(location.unpack(), (0, [AccountKey20 { .. }]))
	}
}

/// Fallible converter from a location to a `H160` that matches any location ending with
/// an `AccountKey20` junction.
pub struct AccountKey20ToH160;
impl MaybeEquivalence<Location, H160> for AccountKey20ToH160 {
	fn convert(location: &Location) -> Option<H160> {
		match location.unpack() {
			(0, [AccountKey20 { key, .. }]) => Some((*key).into()),
			_ => None,
		}
	}

	fn convert_back(key: &H160) -> Option<Location> {
		Some(Location::new(0, [AccountKey20 { key: (*key).into(), network: None }]))
	}
}

/// [`xcm_executor::traits::MatchesFungibles`] implementation that matches
/// ERC20 tokens.
pub type ERC20Matcher =
	MatchedConvertedConcreteId<H160, u128, IsLocalAccountKey20, AccountKey20ToH160, TryConvertInto>;
