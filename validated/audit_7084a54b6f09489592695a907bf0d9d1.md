### Title
Attacker-inflated `DelegatedResourceAccountIndex` legacy lists cause unbounded loop in `convert()`, permanently DoS'ing a victim's freeze/delegate transactions - (File: `chainbase/src/main/java/org/tron/core/store/DelegatedResourceAccountIndexStore.java`)

### Summary
The pre-optimization `DelegatedResourceAccountIndexCapsule` stores `toAccountsList`/`fromAccountsList` as a single unbounded, append-only repeated field per account. Any account can cheaply append an entry to a victim's `fromAccountsList` by freezing a minimal amount of TRX and delegating it to the victim's address from a freshly-generated owner address. Once the chain enables the delegate-optimization feature, the very first freeze/delegate/unfreeze operation touching that account triggers `DelegatedResourceAccountIndexStore.convert()`, which iterates the *entire* legacy list in a single transaction. An attacker who has bloated the list can make this loop exceed the resources available to a single transaction, permanently preventing the victim from ever completing a freeze/delegate/unfreeze operation again — the same "unbounded array growth via cheap deposits ⇒ later legitimate operation always fails" pattern described in the reference report.

### Finding Description
`FreezeBalanceActuator.delegateResource()` appends to the legacy index lists whenever `supportAllowDelegateOptimization()` is disabled: [1](#0-0) 

This uses `DelegatedResourceAccountIndexCapsule.addFromAccount`/`addToAccount`, which unconditionally appends to the protobuf repeated field with no cap: [2](#0-1) 

Any account (attacker) can generate a fresh key, freeze the minimum allowed balance (≥1 TRX, enforced only as a floor, not a ceiling on the number of distinct delegators — see `lessThan1TrxTest`), and delegate it to the same victim receiver address repeatedly from newly generated owner addresses. Each such transaction is cheap (1 TRX, recoverable via later unfreeze, plus bandwidth/energy fee) and adds one more entry to the victim's `fromAccountsList` because the `contains()` check only dedupes per unique owner address, not the total count.

Once the network turns on `supportAllowDelegateOptimization()`, any subsequent freeze/delegate call involving that victim address (by the victim themselves, or anyone delegating to/from them) executes: [3](#0-2) 

which calls `DelegatedResourceAccountIndexStore.convert()`. This method loops over the *entire* legacy `toList`/`fromList` for the account and performs a DB `put` for every single element: [4](#0-3) 

`UnfreezeBalanceActuator` has the same conversion trigger: [5](#0-4) 

If the attacker inflates the list to a size where this single-transaction loop exceeds the energy/time budget of one transaction (the existing test only exercises 100 entries, but nothing bounds it — see `testMultiFreezeDelegatedBalanceForBandwidth`), the victim's freeze/delegate/unfreeze transaction will always fail (out of energy or, in the worst case, disproportionately slow block processing), because `convert()` is unconditionally re-run in full every time it is invoked on that address until the legacy list is fully drained (the `delete(address)` at the end only removes the raw entry once `convert` completes — if it never completes, the bloated list persists forever).

### Impact Explanation
This permanently locks the victim out of using `FreezeBalanceActuator`/`UnfreezeBalanceActuator`/`DelegateResourceActuator` for that address, effectively freezing their staked TRX/bandwidth/energy management capability — analogous to the "permanent freezing of funds" impact category, reachable purely through unprivileged, signed transactions (freeze + delegate) from attacker-controlled accounts, with no special privilege required.

### Likelihood Explanation
The precondition is that `supportAllowDelegateOptimization()` is disabled at attack time (to allow legacy list growth) and later enabled (to trigger the vulnerable `convert()` loop) — this is a real historical/upgrade sequence on java-tron style chains that add resource-delegation optimizations via committee proposals, so pre-existing bloated indices from the earlier code path remain latent landmines. The per-entry attack cost is very low (1 TRX, largely recoverable, plus minor fees), matching the "cheap dust" pattern in the source report.

### Recommendation
- Cap the number of entries `DelegatedResourceAccountIndexCapsule` can hold for `toAccountsList`/`fromAccountsList`, or reject further `addFromAccount`/`addToAccount` calls beyond a fixed limit in `FreezeBalanceActuator.delegateResource()`.
- Make `DelegatedResourceAccountIndexStore.convert()` resumable/incremental (e.g., convert and delete a bounded number of entries per invocation, tracking progress) instead of requiring the whole legacy list to be processed atomically in one transaction.
- Charge energy for `convert()` proportional to the size of the list being converted so the actuator’s `calcFee()`/validate stage can reject transactions whose implied conversion work exceeds the fee limit.

### Proof of Concept
1. Before `AllowDelegateOptimization` is enabled, attacker generates N fresh keypairs `A_1..A_N`.
2. For each `A_i`, attacker funds it with the minimum allowed amount and submits `FreezeBalanceContract` with `receiver_address = victim`, causing `FreezeBalanceActuator.delegateResource()` to append `A_i` to `victim`'s `fromAccountsList` via `addFromAccount` (`chainbase/.../DelegatedResourceAccountIndexCapsule.java:57-61`).
3. Repeat until `victim`'s `fromAccountsList` contains an arbitrarily large number of entries (no cap enforced).
4. After `AllowDelegateOptimization` activates, `victim` (or any counterparty) submits any `FreezeBalanceContract`/`DelegateResourceContract`/`UnfreezeBalanceContract` referencing `victim`'s address, triggering `delegatedResourceAccountIndexStore.convert(victim)` (`actuator/.../FreezeBalanceActuator.java:347-353`), which iterates the full inflated list and performs a DB `put` per entry (`chainbase/.../DelegatedResourceAccountIndexStore.java:42-61`), exceeding the transaction's resource budget and causing the operation to fail every time it is attempted.

  public void convert(byte[] address) {
    DelegatedResourceAccountIndexCapsule indexCapsule = this.get(address);
    if (indexCapsule == null) {
      // convert complete or have no delegate
      return;
    }
    // convert old data
    List<ByteString> toList = indexCapsule.getToAccountsList();
    for (int i = 0; i < toList.size(); i++) {
      // use index as the timestamp, just to keep index in order
      this.delegate(address, toList.get(i).toByteArray(), i + 1L);
    }

    List<ByteString> fromList = indexCapsule.getFromAccountsList();
    for (int i = 0; i < fromList.size(); i++) {
      // use index as the timestamp, just to keep index in order
      this.delegate(fromList.get(i).toByteArray(), address, i + 1L);
    }
    this.delete(address);
  }
