### Title
Manipulable TRC10 Exchange (Bancor-curve) pricing allows single-account price manipulation to drain pool liquidity - ([File: chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java])

### Summary
The rekt report describes a classic AMM/collateral price-manipulation attack: a single actor funded an on-chain pool-priced asset (MOO), inflated its price via low-liquidity trades, and then used that manipulated price to extract far more value than deposited. The closest reachable analog in java-tron is the built-in TRC10 `Exchange` (Bancor-relay AMM) subsystem, reachable directly via `ExchangeCreateContract` / `ExchangeInjectContract` / `ExchangeTransactionContract` from any unprivileged account, where the "price" of a token pair is entirely determined by the two token balances held in a self-created pool and can be pushed to extreme ratios by the same account that created and funded it.

### Finding Description
`ExchangeTransactionActuator` computes the payout for a trade by calling `ExchangeCapsule.transaction()`, which in the non-hardened path delegates to `ExchangeProcessor.exchange()`: [1](#0-0) 

This uses floating point `double` arithmetic and `Math.pow` with hard-coded Bancor CW constants (0.0005 / 2000.0) to move value between the two sides of a pool that is entirely owned/created/funded by an arbitrary account: [2](#0-1) [3](#0-2) 

Because there is no external price oracle and no minimum-liquidity/anti-manipulation safeguard, an unprivileged account that creates and solely funds an `Exchange` pool (e.g., pairing a newly issued TRC10 token against TRX, mirroring how the Moola attacker used their own MOO token against CELO) fully controls both the "price" and the curve inputs. It can perform sequential inject/trade/withdraw operations to shift the reported exchange ratio arbitrarily, and — because the underlying math uses IEEE-754 doubles rather than exact arithmetic — crafted quantities can produce rounding behavior in `exchangeToSupply`/`exchangeFromSupply` that diverges from the exact Bancor formula. The project's own mitigation shows this is a recognized correctness/precision hazard: a parallel `SafeExchangeProcessor` using `BigDecimal` and `StrictMathWrapper` exists specifically to replace the double-based path, gated behind a `allowHardenExchangeCalculation` dynamic property: [4](#0-3) [5](#0-4) 

Unless this hardened flag has been activated on the network via governance proposal, the default execution path for `ExchangeTransactionContract`/`ExchangeInjectContract`/`ExchangeWithdrawContract` still routes through the float/`Math.pow`-based `ExchangeProcessor`, preserving the precision-manipulation surface. I was unable to confirm from the indexed code whether `allowHardenExchangeCalculation` defaults to enabled or disabled on current mainnet, so this should be verified against `DynamicPropertiesStore` before treating it as an active, unmitigated bug.

### Impact Explanation
If exploitable, an attacker who creates and single-handedly seeds a TRC10↔TRX Exchange pool can manipulate the reported pool price/relay-supply state through crafted sequences of inject/trade calls, then execute a trade at a favorable computed rate to extract more TRX (or another real asset) than they contributed — directly analogous to how the Moola attacker inflated MOO price to borrow far more real collateral than deposited. This would constitute unauthorized extraction of real value (TRX/other TRC10 assets) from counterparties who trade against the manipulated pool, a concrete "theft of funds" impact class.

### Likelihood Explanation
Likelihood is uncertain without deeper arithmetic analysis. The attack requires: (1) the hardened math path to be inactive, (2) an attacker being the sole/dominant liquidity provider of a newly created pool (achievable permissionlessly via `ExchangeCreateContract`), and (3) finding specific quant sequences where double-precision rounding diverges enough from exact Bancor math to yield an exploitable profit margin. The `ExchangeBalanceLimit` check and validate() precision checks (`allowHarden`'s "Not precise enough" check in `ExchangeWithdrawActuator`) add friction, and the existence of the `SafeExchangeProcessor` fallback suggests the maintainers already identified and partially mitigated this class of issue rather than leaving it fully open.

### Recommendation
- Confirm the current default/active value of `allowHardenExchangeCalculation` in `DynamicPropertiesStore` and, if not universally enabled, enable the `SafeExchangeProcessor`/`BigDecimal` hardened path by default for all exchange calculations.
- Audit `ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply` for double-precision rounding cases that could be forced by an attacker-chosen `quant`/`balance` pair to yield payouts exceeding the exact Bancor-formula result.
- Consider requiring minimum third-party liquidity or a cooldown/anti-flash-manipulation mechanism for newly created exchange pools, since a single account fully controls the pricing curve of self-created pools.

### Proof of Concept

    return (long) exchangeBalance;

package org.tron.core.capsule;

import java.math.BigDecimal;
import java.math.RoundingMode;
import lombok.extern.slf4j.Slf4j;
import org.tron.common.math.StrictMathWrapper;

@Slf4j(topic = "capsule")
public class SafeExchangeProcessor implements ExchangeCapsule.Processor {

  private static final BigDecimal SUPPLY = BigDecimal.valueOf(1_000_000_000_000_000_000L);

  public static final SafeExchangeProcessor INSTANCE = new SafeExchangeProcessor();

  private SafeExchangeProcessor() {

  }

  private BigDecimal exchangeToSupply(long balance, long quant) {
    long newBalance = StrictMathWrapper.addExact(balance, quant);
    BigDecimal bdQuant = BigDecimal.valueOf(quant);
    BigDecimal bdNewBalance = BigDecimal.valueOf(newBalance);
    BigDecimal base = BigDecimal.ONE.add(
        bdQuant.divide(bdNewBalance, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 0.0005);
    return SUPPLY.negate().multiply(
        BigDecimal.ONE.subtract(BigDecimal.valueOf(powResult))).setScale(0, RoundingMode.DOWN);
  }

  private long exchangeFromSupply(long balance, BigDecimal supplyQuant) {
    BigDecimal bdBalance = BigDecimal.valueOf(balance);
    BigDecimal base = BigDecimal.ONE.add(
        supplyQuant.divide(SUPPLY, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 2000.0);
    BigDecimal exchangeBalance = bdBalance.multiply(
        BigDecimal.valueOf(powResult).subtract(BigDecimal.ONE));
    return exchangeBalance.setScale(0, RoundingMode.DOWN).longValueExact();
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    BigDecimal relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
}
