### Title
DepositToken DoS: fee mint/transfer to `feeCollector` reverts once its account token list reaches `MAX_TOKENS_PER_USER` - (File: contracts/DepositToken.sol)

### Summary
`DepositToken` mints deposit fees to `pool.feeCollector()` inside `deposit()` and transfers withdraw fees to it inside `_withdraw()`. Both `_mint` and `_transfer` call `pool.addToDepositTokensOfAccount(recipient)` whenever the recipient's balance of that token was previously zero, and `Pool` reverts with `UserReachedMaxTokens` once the account's combined deposit/debt token list reaches `MAX_TOKENS_PER_USER`. The `feeCollector` is a protocol-wide accumulation address that only ever receives tokens, so its list grows monotonically — organically as new deposit tokens are added, or actively via attacker dust transfers. Once it hits the cap, every `deposit()` and `withdraw()` in any token the `feeCollector` does not yet hold reverts, permanently DoSing that market.

### Finding Description
In `DepositToken.deposit`, the fee portion is minted directly to the fee collector: [1](#0-0) 

`_mint` registers the token in the recipient's per-account list when its balance was zero: [2](#0-1) 

The same registration happens on transfers, including the fee transfer inside `_withdraw`: [3](#0-2) [4](#0-3) 

`Pool.addToDepositTokensOfAccount` reverts once `MAX_TOKENS_PER_USER` is reached (deposit and debt tokens share the cap), as confirmed by the protocol's own tests: [5](#0-4) 

This is the same bug class as the LMPVault finding: a protocol-critical sink address accumulates share tokens until it hits a per-account cap, after which the code path that pushes tokens to it reverts and bricks core functions. Because `addToDepositTokensOfAccount` is invoked unconditionally inside mint/transfer, there is no exemption for `feeCollector`.

### Impact Explanation
- Once `feeCollector`'s token list is full, `deposit()` reverts for every deposit token it hasn't previously held — the fee `_mint` path cannot be skipped when `depositFee > 0`. A newly added deposit token with nonzero deposit fee is permanently unusable for deposits.
- `withdraw()`/`flashWithdraw()` revert in the same situation via the `_transfer(account_, feeCollector, fee)` step, freezing user collateral in affected markets — users cannot exit because the fee leg cannot settle.
- The state is effectively irreversible: `feeCollector` only accumulates (fees are pulled out via `Treasury`/`TokenHolder` sweeping of underlying, not msdTOKEN burns), so its list never shrinks.

### Likelihood Explanation
Two paths make the cap reachable:
1. **Organic:** every distinct deposit token ever used for a fee-bearing deposit or withdrawal adds an entry to `feeCollector`'s list. As governance lists more collateral types, the cap is approached naturally — exactly like `feeSink` organically approaching `perWalletLimit`.
2. **Attacker-accelerated:** any EOA can deposit dust into each listed deposit token and `transfer` it to `feeCollector`, forcing `addToDepositTokensOfAccount(feeCollector)` for each token and filling remaining slots cheaply. The same dust-transfer trick lets an attacker fill any victim's list, causing transfers/seizes to that victim to revert (e.g., griefing a known liquidator address so `seize` reverts during `Pool.liquidate`).

Feasibility depends on `MAX_TOKENS_PER_USER` being small relative to the number of registered deposit + debt tokens; the constant itself is defined in `Pool.sol` (its exact value was not confirmed in this pass), but the test shows it is a finite cap shared across both lists, and `depositTokensOfAccount`/`debtTokensOfAccount` entries are never pruned for the fee collector.

### Recommendation
Exempt `feeCollector` (and ideally protocol contracts generally) from the `MAX_TOKENS_PER_USER` check in `Pool.addToDepositTokensOfAccount`, or decouple the accounting: keep the bounded list for position/health-factor enumeration but allow balance-carrying tokens beyond the cap to be tracked separately. Alternatively, deliver fees to `feeCollector` in a way that does not require list registration (e.g., collect fees in underlying at the `Treasury`), mirroring the upstream fix of allowing the fee sink to exceed the per-wallet limit.

### Proof of Concept
Hardhat sketch (pool with ≥2 deposit tokens, `depositFee > 0`):

```ts
// Setup: pool with deposit tokens msdA..msdN, feeCollector set, depositFee > 0.
const feeCollector = await pool.feeCollector();
const max = (await pool.MAX_TOKENS_PER_USER()).toNumber();

// 1) Attacker fills feeCollector's token list with dust transfers.
//    (deposit 1 wei of each underlying, transfer received msdTOKEN to feeCollector)
for (const msd of depositTokens.slice(0, max)) {
  await underlying.approve(msd.address, 1);
  await msd.deposit(1, attacker.address);         // may mint dust fee too
  await msd.transfer(feeCollector, await msd.balanceOf(attacker.address));
}
expect(await pool.getDepositTokensOfAccount(feeCollector)).to.have.length(max);

// 2) A new deposit token is listed (or any token feeCollector never held).
await pool.addDepositToken(msdNew.address);

// 3) Any deposit reverts: _mint -> addToDepositTokensOfAccount -> UserReachedMaxTokens
await underlyingNew.approve(msdNew.address, parseEther('10'));
await expect(msdNew.deposit(parseEther('10'), alice.address))
  .to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');

// Same for withdraw on a token whose fee leg targets a capped feeCollector list.
```

Note: the exact value of `MAX_TOKENS_PER_USER` and the precise `addToDepositTokensOfAccount` body in `Pool.sol` were not read in this pass; the revert behavior is confirmed by `test/Pool.test.ts` and the call sites in `DepositToken.sol`.

        address account_,
        uint256 amount_
    ) private onlyIfDepositTokenIsActive updateRewardsBeforeMintOrBurn(account_) {
        if (account_ == address(0)) revert MintToTheZeroAddress();

        totalSupply += amount_;
        if (totalSupply > maxTotalSupply) revert SurpassMaxDepositSupply();

        uint256 _balanceBefore = balanceOf[account_];
        unchecked {
            balanceOf[account_] = _balanceBefore + amount_;
        }

        emit Transfer(address(0), account_, amount_);

        // Add this token to the deposit tokens list if the recipient is receiving it for the 1st time
        if (_balanceBefore == 0 && amount_ > 0) {
            pool.addToDepositTokensOfAccount(account_);
        }
    }
