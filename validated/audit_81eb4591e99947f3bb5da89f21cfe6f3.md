### Title
Unbounded/unvalidated length field in TVM precompiled-contract ABI array extraction can trigger uncontrolled array allocation - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
`PrecompiledContracts.extractBytes32Array`, `extractBytesArray`, and `extractSigArray` read a 32-byte "length" word directly out of attacker-supplied calldata and use it, unvalidated, to size a Java array (`new byte[len][]`) before any bytes are actually copied. This mirrors the go-unixfsnode HAMT bug class: a length/"fanout" field taken from untrusted input is trusted for allocation sizing without an upper bound or sign check, which the upstream advisory fixed by adding an explicit cap. In this codebase the same file already demonstrates the fix pattern elsewhere (`ModExp.UPPER_BOUND = 1024` added to cap `baseLen/expLen/modLen`), but the array-extraction helpers used by the multi-signature precompiled contracts do not have an equivalent cap.

### Finding Description
`extractBytes32Array` and `extractBytesArray`/`extractSigArray` compute `len` from `words[offset].intValueSafe()` — a value fully controlled by the calldata of any TVM contract call — and immediately allocate `new byte[len][]` with no upper bound check, before validating that `len` corresponds to any real data actually present in the input buffer: [1](#0-0) [2](#0-1) [3](#0-2) 

By contrast, `ModExp.execute` explicitly rejects any of `baseLen/expLen/modLen` above `UPPER_BOUND = 1024` before performing any allocation or big-number parsing, showing that the codebase authors are aware of and mitigate this exact bug class elsewhere in the same file: [4](#0-3) 

No analogous bound exists for the array-length words consumed in `extractBytes32Array`/`extractBytesArray`/`extractSigArray`, which are used to decode the multi-signature precompiled contracts (`ValidateMultiSign`/`BatchValidateSign`) reachable from any contract call.

### Impact Explanation
An attacker who can call the affected precompiled contract (any account can invoke a precompiled address via a `TriggerSmartContract`) can craft calldata whose embedded "array length" word is enormous. Depending on how `intValueSafe()` truncates a 256-bit word to a Java `int`, this can either force allocation of a huge array (energy-unbounded memory pressure/OOM, matching the "virtual memory leak" characterization in the advisory) or, if truncation yields a negative int, throw `NegativeArraySizeException`, an unchecked `RuntimeException` not visibly caught inside these helper methods. If such an exception is not caught by every call path that invokes precompiled contracts during block application, it can abort transaction/block processing unexpectedly, which is a reliability-impacting DoS on any node processing the malicious transaction/block.

### Likelihood Explanation
The precompiled contracts using these decoders are reachable from a single, unprivileged, signed `TriggerSmartContract` transaction — no special privilege is required. The precise exploitability depends on two unverified details I could not fully confirm within scope: (1) the exact clamping behavior of `DataWord.intValueSafe()` for values that exceed `Integer.MAX_VALUE` (whether it clamps to a safe positive maximum or can yield a negative int), and (2) whether every call site wrapping precompiled-contract execution in the TVM interpreter catches `RuntimeException`/`Throwable` broadly enough to prevent propagation into block-application logic. Given the presence of an already-fixed identical pattern (`ModExp.UPPER_BOUND`) in the same file, this is a credible, concrete gap rather than a purely theoretical one, but confirming the precise crash/no-crash outcome requires tracing `intValueSafe()` and the full precompiled-contract dispatch/catch chain, which the current index does not fully expose.

### Recommendation
Add explicit upper-bound and non-negative validation on the `len` value extracted in `extractBytes32Array`, `extractBytesArray`, and `extractSigArray` (mirroring `ModExp.UPPER_BOUND`) before performing `new byte[len][]`, and additionally validate that `len` is consistent with the actual remaining length of `words`/`data` before allocation, so a bogus length word cannot drive an unbounded or negative-sized allocation.

### Proof of Concept
Construct calldata for a call into the precompiled contract that uses `extractBytesArray`/`extractBytes32Array` (the multi-signature verification precompile) where the array-length word at the expected offset is set to a very large or maximal 256-bit value (e.g., `0xFFFFFFFF...FF`) instead of a small legitimate count. Submit this as calldata in a `TriggerSmartContract` transaction targeting the precompiled address. Trace `intValueSafe()`'s conversion of that word and observe whether `extractBytesArray`/`extractBytes32Array` proceeds to allocate `new byte[len][]` with the resulting value, and whether the resulting exception (OOM or `NegativeArraySizeException`) is caught by the surrounding precompiled-contract dispatch code in `PrecompiledContracts`/`Program`, or propagates further up during transaction execution.
