## Title
`EthereumSystem::add_tip` on BridgeHub trusts an unauthenticated `sender` field bound only to a static, replayable pallet-location origin, not the real caller - (File: `bridges/snowbridge/pallets/system-v2/src/lib.rs`)

### Summary
The `flashAction()` bug is a callback that forwards data to a receiver without binding the real initiator to the callback, so anyone can spoof the call. The Snowbridge `system-v2`/`system-frontend` pair reproduces the same broken invariant: the BridgeHub-side extrinsic `EthereumSystem::add_tip(origin, sender, message_id, amount)` accepts `sender` as an arbitrary call parameter and authenticates the call only via `T::FrontendOrigin`, which is satisfied by a fixed, chain-wide XCM origin (`AssetHub location + DescendOrigin(PalletLocation)`) that is reproducible by *any* account on the sibling chain, not tied to the specific AssetHub user who legitimately triggered `add_tip` through `system-frontend`.

### Finding Description
`system-frontend::add_tip` (AssetHub side) is the intended entrypoint: it takes the real signed caller `who = ensure_signed(origin)?`, swaps/burns the tip asset for ether via `swap_fee_asset_and_burn`, and only then builds a remote call: [1](#0-0) 

The remote XCM program that carries this call to BridgeHub is origin-agnostic with respect to the actual AssetHub account — it only descends the origin by the pallet's own static interior location: [2](#0-1) 

On BridgeHub, `system-v2::add_tip` re-authenticates the call solely via `T::FrontendOrigin::ensure_origin(origin)`, whose `Success` type is a `Location` (not an `AccountId`), and then uses the caller-supplied `sender` field verbatim — both to route lost-tip bookkeeping and to identify "the original sender of the tip" in the emitted event: [3](#0-2) 

Because the resulting BH-side origin after `DescendOrigin(T::PalletLocation::get())` is identical for every AssetHub account (it never incorporates the dispatching user's identity), any account on AssetHub capable of sending a permissionless XCM program to BridgeHub (e.g. via `pallet_xcm::send`/`execute`) can reconstruct the exact same `DescendOrigin(PalletLocation) + Transact{origin_kind: OriginKind::Xcm, ...}` envelope that `system-frontend` legitimately produces, and thereby satisfy `T::FrontendOrigin` without ever going through `system-frontend::add_tip` or performing the corresponding `swap_fee_asset_and_burn`. The forged call can supply an arbitrary `sender: AccountIdOf<T>`, `message_id`, and `amount`.

This is the exact analog of the M-24 pattern: the callback (`add_tip`) needs to authenticate "who really initiated this," but the design conflates "message came from the correct pallet-class location" with "the embedded `sender`/`amount` fields are trustworthy," exactly as `onFlashAction` conflated "call carries valid token data" with "call came from the real flash-loan initiator."

### Impact Explanation
- `sender` is used unauthenticated to attribute `LostTips::<T>` storage increments (a state used for future recovery of lost tips), so an attacker can grief arbitrary accounts by crediting fabricated lost-tip entries to them, or attribute genuine losses to accounts that never participated: [4](#0-3) 
- More seriously, `amount` reaches `InboundQueue::add_tip(nonce, amount)` / `OutboundQueue::add_tip(nonce, amount)` directly, without the corresponding on-chain burn of ether that `system-frontend::add_tip` normally performs via `swap_fee_asset_and_burn` before dispatching the remote call: [5](#0-4) . If this tip amount is later paid out to relayers from the bridge's reward pool, this is an unbacked reward inflation vector rather than a mere bookkeeping bug. This lines up with the "unbacked mint or unlock" and "theft/duplicate settlement" impact categories in scope.

### Likelihood Explanation
The attack requires no privileged role, no relayer, no validator, no admin — only a signed account on AssetHub (or any chain configured similarly) capable of issuing a permissionless XCM `send`/`execute` targeting BridgeHub. Constructing the exact `DescendOrigin(PalletLocation)` + `Transact{origin_kind: Xcm}` envelope requires only public knowledge of `T::PalletLocation` and the `EthereumSystemCall::AddTip` SCALE encoding, both of which are static and derivable from the runtime's public configuration/metadata. This makes exploitation straightforward for any unprivileged user, matching the report's likelihood profile of "most people won't bother with proper authentication and it's easy for an attacker to exploit."

### Recommendation
Bind the tipping identity to the verified origin rather than to an unauthenticated call parameter:
- Change `T::FrontendOrigin` to resolve to a `Success` type that carries (or can be converted to) the specific `AccountId`/derived-account of the dispatching user (e.g. by encoding the account into the XCM interior location before `DescendOrigin`, similar to how `RegisterTokenOrigin` in `system-frontend` is parameterized by asset location), and derive `sender` from that origin on the BH side instead of trusting the call parameter.
- Alternatively, have `system-frontend` include a bridge-specific reanchored `AccountId32` junction unique to the caller in the XCM `DescendOrigin`, and have BH's `add_tip` reject any `sender` that does not match the account recoverable from the verified origin (mirroring how flash-loan receivers now require the callback to carry the verified initiator).

### Proof of Concept
1. On AssetHub, observe (via public runtime metadata/config) `T::PalletLocation` for `snowbridge-pallet-system-frontend` and the SCALE encoding of `BridgeHubRuntime::EthereumSystem(EthereumSystemCall::AddTip { sender, message_id, amount })`.
2. As any signed account (attacker), call `pallet_xcm::execute` (or `send`) with a hand-crafted XCM:
   ```
   Xcm(vec![
       DescendOrigin(<PalletLocation>),
       UnpaidExecution { weight_limit: Unlimited, check_origin: None },
       Transact {
           origin_kind: OriginKind::Xcm,
           call: EthereumSystemCall::AddTip {
               sender: <victim_or_arbitrary_account>,
               message_id: MessageId::Outbound(<any_pending_nonce>),
               amount: <arbitrary_large_amount>,
           }.encode().into(),
           fallback_max_weight: None,
       },
   ])
   ```
   targeting `T::BridgeHubLocation`.
3. On BridgeHub, `EthereumSystem::add_tip` executes: `T::FrontendOrigin::ensure_origin` succeeds because the computed origin (`sibling AssetHub location + PalletLocation`) is identical to the one the legitimate `system-frontend` pallet produces for any user.
4. `OutboundQueue::add_tip(nonce, amount)` is credited with an attacker-chosen `amount` that was never burned on AssetHub, and/or `LostTips` is incremented against an arbitrary `sender` account — confirming the forged, unauthenticated tip/sender injection.

Note: I could not execute this end-to-end in a live runtime from static analysis alone; the exact `T::FrontendOrigin` implementation used in the production BridgeHub runtime configuration (whether it strictly checks the full location including any account-derived junction) should be verified in the actual runtime config (`bridge-hub-westend-runtime` or similar) to confirm no additional account-binding is layered on top of the pallet interface shown here.

		#[pallet::call_index(3)]
		#[pallet::weight(<T as pallet::Config>::WeightInfo::add_tip())]
		pub fn add_tip(
			origin: OriginFor<T>,
			sender: AccountIdOf<T>,
			message_id: MessageId,
			amount: u128,
		) -> DispatchResult {
			T::FrontendOrigin::ensure_origin(origin)?;

			let result = match message_id {
				Inbound(nonce) => <T as pallet::Config>::InboundQueue::add_tip(nonce, amount),
				Outbound(nonce) => <T as pallet::Config>::OutboundQueue::add_tip(nonce, amount),
			};

			if let Err(ref e) = result {
				tracing::debug!(target: LOG_TARGET, ?e, ?message_id, ?amount, "error adding tip");
				LostTips::<T>::mutate(&sender, |lost_tip| {
					*lost_tip = lost_tip.saturating_add(amount);
				});
			}

			Self::deposit_event(Event::<T>::TipProcessed {
				sender,
				message_id,
				amount,
				success: result.is_ok(),
			});

			Ok(())
		}
