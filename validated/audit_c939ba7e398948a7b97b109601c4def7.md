### Title
Unauthenticated event injection into signer's HTTP event-receiver allows forged `NewBurnBlock`/`NewBlock` data - (File: `libsigner/src/events.rs`)

### Summary
`SignerEventReceiver::next_event` routes any POST to `/new_burn_block` or `/new_block` straight into `process_event`, which only checks JSON deserializability before converting the payload into a `SignerEvent` via `TryFrom`. No signature, MAC, shared-secret, or peer-identity check exists anywhere in this file, and the sample configs bind the receiver to `0.0.0.0:<port>`, so any remote host that can reach that port can inject a fabricated burn/stacks-block event with attacker-chosen `ConsensusHash`/`BurnchainHeaderHash`/`BlockHeaderHash` values.

### Finding Description
The broken equality is: `SignerEvent::NewBurnBlock{ consensus_hash, burn_header_hash, .. }` is expected to equal a value cryptographically derived from the node's own burnchain/consensus state, but nothing in `libsigner/src/events.rs` enforces that binding.

`next_event` dispatches purely on `request.url()` and `request.method()`: [1](#0-0) 

`process_event` reads the raw HTTP body, deserializes it as JSON into `E` (`BurnBlockEvent` or `StacksBlockEvent`), and converts it via `TryInto<SignerEvent<T>>` — no signature, token, or origin check is performed anywhere in this path: [2](#0-1) 

The `TryFrom<BurnBlockEvent>` and `TryFrom<StacksBlockEvent>` conversions copy the JSON-supplied hash fields verbatim into the emitted `SignerEvent`, with no validation against any node-derived value: [3](#0-2) [4](#0-3) 

Grepping `libsigner/` confirms there is no `auth_token`/`auth_password`/`Authorization` check anywhere in this crate — the `auth_password`/`auth_token` pair documented in `docs/signing.md` and the sample configs is used only for the *outbound* signer→node RPC channel (block-proposal endpoint), not for the *inbound* node→signer event channel implemented by this file. Sample configs (`mainnet-signer.toml`, `mainnet-signer-conf.toml`, `testnet-signer.toml`) explicitly set `endpoint = "0.0.0.0:30000"`, confirming the receiver is meant to be reachable beyond loopback in some deployments, and even when bound to `127.0.0.1`, the code itself performs zero verification that the sender is the paired node — the guarantee (if any) is purely a network/firewall assumption external to this file.

Downstream, `stacks-signer/src/v0/signer.rs` consumes `SignerEvent::NewBurnBlock` and unconditionally calls `signer_db.insert_burn_block(...)` with the attacker-supplied hashes before any reconciliation against the node's real sortition view: [5](#0-4) 
This record then feeds `bitcoin_block_arrival`/`get_parent_tenure_last_block`, which per `docs/signer-flows.md` only reconciles against the real node state lazily ("settle only once the node reports this block as its canonical tip, else park it as Pending"), meaning a forged burn-block record is persisted into the signer's local database immediately, before any node-truth check occurs.

### Impact Explanation
An attacker who can reach the signer's bound event-receiver port (per sample configs, `0.0.0.0:<port>`, i.e., not restricted to loopack) can write arbitrary, non-canonical `(consensus_hash, burn_header_hash, parent_burn_block_hash, burn_height)` tuples into the signer's local `signerdb` via `insert_burn_block`, and can inject fabricated `NewBlock` events with an arbitrary `consensus_hash`/`block_id`/`signer_sighash`/transaction set that get fed into `local_state_machine.stacks_block_arrival`. This is an unauthenticated write of attacker-controlled data into the signer's persistent local state, and can be repeated per message with no rate limiting other than TCP round-trips. This matches the Critical category "unauthenticated/unauthorized write to state."

### Likelihood Explanation
No privileged role, secret, or key is required — this is purely a matter of TCP reachability to the signer's event-receiver port. The severity is contingent on network exposure: if operators strictly bind the endpoint to `127.0.0.1` and firewall it, remote exploitation requires an additional network-position assumption not covered by this code. However, the shipped reference configs in this repo (`mainnet-signer.toml`, `sample/conf/signer/mainnet-signer-conf.toml`, `testnet-signer.toml`) all set `endpoint = "0.0.0.0:30000"`, and the code path itself performs zero authentication regardless of bind address, so the vulnerability is a code-level absence of any check — reachability depends entirely on external deployment/firewall configuration, which is not enforced or documented as mandatory anywhere in `libsigner`.

### Recommendation
Add an authentication mechanism to the node→signer event channel in `libsigner/src/events.rs`, e.g., require and verify a shared secret/HMAC header (analogous to `auth_token`) on every incoming request in `next_event`/`process_event` before deserializing the body, and reject requests lacking a valid token. Alternatively/additionally, enforce that the HTTP server only accepts connections from the configured node's IP, and document/default the `endpoint` bind address to loopback-only unless a MAC is configured.

### Proof of Concept
1. Start a `SignerEventReceiver::<T>::new(false)`, call `bind()` on `127.0.0.1:0`, and spawn `main_loop`/`next_event` in a thread with a channel consumer attached via `add_consumer`.
2. From a separate `TcpStream`, send a raw HTTP POST to `/new_burn_block` with a JSON body matching `BurnBlockEvent`'s expected shape but with random 20/32-byte hex values for `consensus_hash`/`burn_block_hash`/`parent_burn_block_hash` and an arbitrary `burn_block_height`.
3. Assert that the consumer's channel receives `SignerEvent::NewBurnBlock { consensus_hash, burn_header_hash, .. }` matching exactly the attacker-supplied (non-node-derived) values, with no error/rejection — i.e., `process_event::<T, BurnBlockEvent>` at `libsigner/src/events.rs:519-542` returns `Ok` for fabricated content, and `TryFrom<BurnBlockEvent>` at lines 637-649 propagates it unchanged.

fn process_event<T, E>(mut request: HttpRequest) -> Result<SignerEvent<T>, EventError>
where
    T: SignerEventTrait,
    E: serde::de::DeserializeOwned + TryInto<SignerEvent<T>, Error = EventError>,
{
    let mut body = String::new();

    if let Err(e) = request.as_reader().read_to_string(&mut body) {
        error!("Failed to read body: {:?}", &e);
        ack_dispatcher(request);
        return Err(EventError::MalformedRequest(format!(
            "Failed to read body: {:?}",
            e
        )));
    }
    // Regardless of whether we successfully deserialize, we should ack the dispatcher so they don't keep resending it
    ack_dispatcher(request);
    let json_event: E = serde_json::from_slice(body.as_bytes())
        .map_err(|e| EventError::Deserialize(format!("Could not decode body to JSON: {:?}", e)))?;

    let signer_event: SignerEvent<T> = json_event.try_into()?;

    Ok(signer_event)
}
