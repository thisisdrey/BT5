## Title
Outbound Queue V2 settles pending orders and pays relayer rewards without checking on-chain execution success - ([File: bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs])

## Summary
`Pallet::process_delivery_receipt` in `pallet-outbound-queue-v2` decodes a `DeliveryReceipt` that carries a `success: bool` field from the Ethereum Gateway's `InboundMessageDispatched` event, but never reads that field before paying the relayer reward and removing the `PendingOrder`. A failed on-Ethereum dispatch (`success == false`) is therefore treated identically to a successful one, causing the relayer to be paid and the `MessageDelivered` event to be emitted even though the intended cross-chain effect never occurred.

## Finding Description
`DeliveryReceipt` is decoded from the verified Ethereum log with an explicit `success` field sourced from the `InboundMessageDispatched` event: [1](#0-0) . `TryFrom<&Log>` populates `success: event.success` faithfully from the decoded log [2](#0-1) .

`submit_delivery_receipt` is a public, unprivileged extrinsic that only requires `ensure_signed`, verifies the proof via `T::Verifier::verify`, decodes the receipt, and forwards it to `process_delivery_receipt`: [3](#0-2) .

`process_delivery_receipt` checks only `receipt.gateway` against the configured gateway address, resolves the reward account, fetches the `PendingOrder` by `receipt.nonce`, unconditionally pays `order.fee` via `T::RewardPayment::register_reward`, removes the order from `PendingOrders`, and emits `Event::MessageDelivered` — the `receipt.success` field is never inspected anywhere in this function: [4](#0-3) . A grep across the entire `outbound-queue-v2` pallet and primitives confirms `receipt.success`/`.success` is read only at decode time in `delivery_receipt.rs` and nowhere used in the settlement logic in `lib.rs`.

The doc comment for the pallet explicitly frames settlement as occurring "when the message has been verified and executed" [5](#0-4) , confirming the intended invariant that settlement should reflect actual successful execution — an invariant the code does not enforce.

## Impact Explanation
This breaks the invariant that "message queues, bridge markers, receipts, and payout state must only advance after decode, dispatch, execution, and settlement succeed atomically." A message whose Ethereum-side commands revert is still fully settled (order removed) and fully rewarded, exactly as if it had succeeded. This is a duplicate/unbacked payout condition (reward paid for a dispatch that did not achieve its intended effect) and misleads any on-chain or off-chain consumer of `MessageDelivered` into believing the operation succeeded when it did not, matching the "duplicate settlement or payout" and "runtime bugs that compromise intended behavior" categories in the impact gate.

## Likelihood Explanation
The path is reachable by any unprivileged, signed account: `submit_delivery_receipt` requires only `ensure_signed`, and the attacker/relayer needs only a genuine Ethereum receipt proof for a `InboundMessageDispatched` log with `success = false` (naturally producible whenever a command legitimately reverts, e.g., by supplying insufficient gas for a downstream command or triggering any revertible condition on the Gateway side) tied to a nonce that still has a `PendingOrder`. No governance, admin, or compromised-relayer assumption is required beyond normal permitted relayer action.

## Recommendation
In `process_delivery_receipt`, branch on `receipt.success`: only pay the full reward and remove the `PendingOrder` when `success == true`. When `success == false`, either withhold/reduce the reward, transition the order to a distinguishable failed state, or otherwise avoid conflating "delivery attempted" with "delivery executed successfully," while still allowing the order to be resolved (e.g., for observability or retry) without full reward payout.

## Proof of Concept
1. A message is enqueued via `do_process_message`, inserting `PendingOrders::<T>::insert(nonce, order)` with `order.fee > 0` [6](#0-5) .
2. On Ethereum, the Gateway dispatch for this nonce reverts/fails, so it emits `InboundMessageDispatched(nonce, topic, success=false, reward_address)`.
3. A relayer builds a valid finalized-header + receipt proof for this real log and calls `submit_delivery_receipt(origin, event)`.
4. `T::Verifier::verify` succeeds (the log is genuine), `DeliveryReceipt::try_from` decodes `success: false` correctly.
5. `process_delivery_receipt` pays `order.fee` to the reward account via `T::RewardPayment::register_reward`, removes the `PendingOrder`, and emits `Event::MessageDelivered { nonce }` — identical to the success path, with no branch on `receipt.success` [7](#0-6) . A unit test asserting that when `event.success == false` the reward is withheld and/or the order is not removed the same way as on success would fail against current code, demonstrating the bug.

		/// Process a delivery receipt from a relayer, to allocate the relayer reward.
		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}
