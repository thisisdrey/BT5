## Analysis

The reported bug class is a **Synthetix-style reward-accrual-without-participants bug**: a reward pool computes/records a reward amount for a period, but the reward-per-share accumulator (`rewardPerTokenStored` in Synthetix, here the witness "Vi" — value-index) is only updated based on the *current* stake weight, so if that weight is zero when the update runs, the reward that was already earned for the period is silently discarded and permanently lost to anyone entitled to it.

java-tron's DPoS reward/delegation system contains a structurally identical pattern. Rewards earned by a Super Representative (SR) for producing a block are unconditionally accumulated into a per-cycle reward bucket in `MortgageService.payReward`, independent of the SR's current vote weight: [1](#0-0) 

At the end of each maintenance cycle, `MaintenanceManager.doMaintenance` propagates that cycle's stored reward into the reward-per-vote accumulator (`Vi`) using the SR's *live* vote count at maintenance time: [2](#0-1) 

The accumulation function `DelegationStore.accumulateWitnessVi` explicitly skips the delta-Vi update — and therefore skips distributing the already-recorded reward — whenever the vote count for that cycle is zero, simply carrying forward the previous `Vi` unchanged: [3](#0-2) 

The equivalent legacy path, `RewardViCalService.accumulateWitnessVi`, has the same skip-on-zero-vote logic: [4](#0-3) 

And the old (pre-Vi) reward algorithm in `MortgageService.computeReward(cycle, votes)` similarly drops the reward whenever `totalVote == REMARK || totalVote == 0`: [5](#0-4) 

### Why this matches the reported bug class

- In Synthetix/Lybra, `notifyRewardAmount` books a reward for a time window regardless of `totalSupply`; if `totalSupply == 0` when the accumulator is later updated, the reward for that stretch of time is unclaimed and effectively burned.
- In java-tron, `payReward`/`payBlockReward` books a reward for an SR *for a specific cycle* regardless of that SR's vote weight; if the SR's vote count is zero when `accumulateWitnessVi` runs at the end of that cycle (e.g., all voters unfroze/withdrew their votes during the cycle, or an SR briefly drops out of the active/standby set after earning block rewards but before votes are re-tallied), the reward already recorded via `delegationStore.addReward(cycle, address, value)` is never folded into `Vi` and becomes permanently unclaimable by any voter — the SR's `getReward(cycle, address)` value sits in storage but is never redeemable through `MortgageService.computeReward`/`queryReward`/`withdrawReward`, or through the TVM-exposed `VoteRewardUtil.withdrawReward`/`queryReward` (reachable via the `WithdrawRewardProcessor` native contract, itself triggered by ordinary signed transactions).

This is a genuine reachable analog (any account can unfreeze/re-delegate votes via ordinary transactions, and TVM contracts can call vote/withdraw via `VoteRewardUtil`), and it results in frozen/unbacked reward accounting — funds recorded as paid into the reward pool that can never be withdrawn by anyone, a permanent-freezing-of-funds class of impact.

### Title
Witness/SR rewards can be permanently lost when vote count is zero during Vi accumulation - (File: chainbase/src/main/java/org/tron/core/store/DelegationStore.java)

### Summary
`DelegationStore.accumulateWitnessVi` (and its legacy counterpart `RewardViCalService.accumulateWitnessVi`) skips updating the reward-per-vote accumulator (`Vi`) whenever a witness's vote count is zero for the cycle, even though block/standby rewards for that witness were already unconditionally recorded via `MortgageService.payReward`. This mirrors the classic Synthetix "reward accrued while totalSupply == 0" bug, except keyed on vote weight instead of time.

### Finding Description
`MortgageService.payReward` (and callers `payBlockReward`/`payTransactionFeeReward`/`payStandbyWitness`) always calls `delegationStore.addReward(cycle, witnessAddress, value)` to book a reward for the current cycle, with no check on the witness's current vote weight. Separately, at end-of-cycle maintenance, `MaintenanceManager.doMaintenance` calls `delegationStore.accumulateWitnessVi(curCycle, witness.createDbKey(), witness.getVoteCount())` for every witness using their *current* vote count. Inside `accumulateWitnessVi`, if `voteCount == 0` (or `reward == 0`), the function does not compute a delta-Vi and simply forwards the previous `Vi` value — the reward stored for that cycle is never distributed to any voter's share of `Vi` and cannot subsequently be claimed via `MortgageService.computeReward`, `queryReward`, or `withdrawReward`, nor via the TVM-facing `VoteRewardUtil` equivalents used by the `WithdrawRewardProcessor` native contract.

### Impact Explanation
Any reward amount added for a cycle where the target witness's vote count is (or becomes) zero at maintenance time is permanently stranded — it remains recorded in `DelegationStore`'s reward key-space but is never folded into `Vi`, so no voter (past or future) can ever redeem it. This is a permanent freezing-of-funds condition on protocol-issued rewards.

### Likelihood Explanation
Vote counts for an SR can go to zero within a cycle through ordinary user actions — unvoting/unfreezing TRX (including via TVM contracts using `VoteRewardUtil`/vote-related native contracts) — while that SR may still have earned block or standby rewards earlier in the same cycle. No malicious/privileged actor is required; this can occur through routine voter behavior, especially for SRs near the vote threshold.

### Recommendation
Instead of skipping the Vi update entirely when `voteCount == 0`, carry unclaimed per-cycle rewards forward to accumulate against the next cycle in which `voteCount > 0`, analogous to the standard Synthetix fix of starting/refreshing the reward accrual window only when there is a nonzero staking base, ensuring no reward amount recorded via `addReward` is ever silently dropped.

### Proof of Concept
1. SR `W` has nonzero votes and produces blocks during cycle `N`; `MortgageService.payBlockReward` accumulates reward `R` for `(cycle=N, address=W)` via `DelegationStore.addReward`.
2. Before maintenance runs for cycle `N`, all voters call unvote/unfreeze (ordinary signed transactions, or via a TVM contract using vote-related native contracts), driving `W.getVoteCount()` to 0.
3. `MaintenanceManager.doMaintenance` runs `delegationStore.accumulateWitnessVi(N, W, 0)`.
4. Inside `DelegationStore.accumulateWitnessVi`, since `voteCount == 0`, the previous `Vi` is simply forwarded — `R` is never reflected in any `Vi` delta.
5. `getReward(N, W)` still returns `R`, but no call path (`MortgageService.queryReward`/`withdrawReward`, or TVM `VoteRewardUtil`) can ever produce a nonzero claim referencing that reward — the funds are permanently unreachable.

  private long computeReward(long cycle, List<Pair<byte[], Long>> votes) {
    long reward = 0;
    for (Pair<byte[], Long> vote : votes) {
      byte[] srAddress = vote.getKey();
      long totalReward = delegationStore.getReward(cycle, srAddress);
      if (totalReward <= 0) {
        continue;
      }
      long totalVote = delegationStore.getWitnessVote(cycle, srAddress);
      if (totalVote == DelegationStore.REMARK || totalVote == 0) {
        continue;
      }
      long userVote = vote.getValue();
      double voteRate = (double) userVote / totalVote;
      reward += voteRate * totalReward;
    }
    return reward;
  }

  public void accumulateWitnessVi(long cycle, byte[] address, long voteCount) {
    BigInteger preVi = getWitnessVi(cycle - 1, address);
    long reward = getReward(cycle, address);
    if (reward == 0 || voteCount == 0) { // Just forward pre vi
      if (!BigInteger.ZERO.equals(preVi)) { // Zero vi will not be record
        setWitnessVi(cycle, address, preVi);
      }
    } else { // Accumulate delta vi
      BigInteger deltaVi = BigInteger.valueOf(reward)
          .multiply(DECIMAL_OF_VI_REWARD)
          .divide(BigInteger.valueOf(voteCount));
      setWitnessVi(cycle, address, preVi.add(deltaVi));
    }
  }
