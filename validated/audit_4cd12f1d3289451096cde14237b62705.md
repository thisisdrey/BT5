## Analysis Result



### Title
Exchange liquidity withdrawal computes payout from manipulable spot pool ratio with no slippage/minimum-output protection, enabling sandwich attacks - (File: actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java)

### Summary
`ExchangeWithdrawContract` and its actuator compute the amount of the paired token to return during a liquidity withdrawal strictly from the exchange pool's current on-chain balance ratio, with no caller-supplied minimum-expected-output bound. This is inconsistent with `ExchangeTransactionContract`, which explicitly carries an `expected` field used as slippage protection. Because the pool's balance ratio (spot price) can be moved arbitrarily within the same block/adjacent blocks by any account trading via `ExchangeTransactionContract`, an attacker can sandwich a pending `ExchangeWithdrawContract` transaction to force the withdrawal to execute at a manipulated ratio, extracting value from the withdrawing account.

### Finding Description
`ExchangeWithdrawActuator.doValidate()`/`execute()` computes `anotherTokenQuant` directly as a function of `firstTokenBalance`/`secondTokenBalance` read at execution time: [1](#0-0) 

This same unconstrained calculation is repeated in `execute()`: [2](#0-1) 

Unlike `ExchangeTransactionContract`, which defines an explicit `expected` (minimum received) field enforced in `ExchangeTransactionActuator.doValidate()`: [3](#0-2) 

`ExchangeWithdrawContract` has no equivalent field: [4](#0-3) 

The pool's `firstTokenBalance`/`secondTokenBalance` (i.e., the spot exchange rate) is mutated by every `ExchangeTransactionContract` trade via `ExchangeCapsule.transaction()`, which anyone can broadcast against any existing pool: [5](#0-4) 

Because a pending `ExchangeWithdrawContract` transaction is visible in the mempool before inclusion, an attacker can: (1) submit a large trade via `ExchangeTransactionContract` that skews the pool ratio in a direction unfavorable to the withdrawer, (2) let the victim's withdrawal execute using that skewed ratio (siphoning a disproportionate share of one asset out of the pool relative to what the withdrawer intended), (3) submit a reverse trade to restore the ratio and pocket the difference. This is structurally identical to the reported bug class: a system computation relies on a spot/AMM-style ratio with no minimum-output bound, so the party consuming that computation (here, the pool owner performing `ExchangeWithdraw`) absorbs 100% of any price manipulation.

### Impact Explanation
A successful sandwich forces the pool owner's withdrawal to return less value than a fair, unmanipulated ratio would provide, while the attacker profits the difference by round-tripping trades through the same pool. This is a direct, deterministic loss of funds for the account executing `ExchangeWithdrawContract`, achievable by any unprivileged transaction broadcaster who can observe the mempool and submit ordinary `ExchangeTransactionContract` trades — no special privilege, witness/SR role, or off-chain access is required.

### Likelihood Explanation
Exploitation only requires: (a) an existing Bancor-style exchange pool (`ExchangeCreateContract`), (b) the pool owner submitting an `ExchangeWithdrawContract`, and (c) the attacker being able to see the pending transaction and insert trades before/after it in the same or adjacent blocks — a standard MEV/front-running setup available to any full node operator or transaction relay participant. No cross-chain bridge, oracle manipulation, or complex preconditions (as in the original Nomad scenario) are needed, making this readily reachable on java-tron whenever a liquidity pool with non-trivial balances exists.

### Recommendation
Add a caller-supplied minimum-expected-output field to `ExchangeWithdrawContract` (mirroring `ExchangeTransactionContract.expected`) and enforce it in `ExchangeWithdrawActuator.doValidate()`/`execute()`, rejecting the withdrawal if the computed `anotherTokenQuant` (or the withdrawn `tokenQuant`) falls short of the caller's specified bound. Alternatively, require withdrawals to be proportional to a tracked liquidity-share rather than an absolute token quantity so that within-block ratio manipulation cannot change the payout composition.

### Proof of Concept
1. Attacker observes an `ExchangeWithdrawContract` transaction from the pool owner in the mempool for exchange `E` (tokens A/B).
2. Attacker submits `ExchangeTransactionContract` selling a large amount of A for B, sharply moving `firstTokenBalance`/`secondTokenBalance` of `E` in `ExchangeCapsule.transaction()`.
3. The victim's withdrawal executes, computing `anotherTokenQuant` from the now-skewed ratio in `ExchangeWithdrawActuator` (lines 77-89), returning a mix of A/B far less favorable than the ratio at transaction-submission time.
4. Attacker submits a second `ExchangeTransactionContract` reversing the initial trade, restoring the pool ratio and capturing the spread as profit, net of the two market-order fees.
