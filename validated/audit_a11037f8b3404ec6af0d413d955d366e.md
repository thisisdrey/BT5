Audit Report

## Title
Missing idempotency guard lets any account re-trigger `RegisterForeignToken` dispatch to Ethereum for an already-registered token - (File: `bridges/snowbridge/pallets/system-v2/src/lib.rs`)

## Summary
`register_token` in `pallet-snowbridge-system-v2` (and the analogous `do_register_token` in `pallet-snowbridge-system`) only wraps the `ForeignToNativeId` storage write with an `if !contains_key` check, but unconditionally builds and sends `Command::RegisterForeignToken` to the outbound queue and emits `Event::RegisterToken` regardless of whether the token was already registered. This allows the same unprivileged caller (or any account whose location nests the same `asset_id`) to repeatedly enqueue duplicate `RegisterForeignToken` commands for an already-registered token.

## Finding Description
In `pallet-snowbridge-system-v2::register_token`, the caller is authorized via `T::FrontendOrigin::ensure_origin(origin)`, which is reachable from any account through `pallet-snowbridge-system-frontend::register_token` — a call explicitly documented as allowing "All origins," gated only by `T::RegisterTokenOrigin` requiring the `asset_id` be nested within the caller's own location. [1](#0-0)  After reanchoring and computing `token_id`, the function does:
```rust
if !ForeignToNativeId::<T>::contains_key(token_id) {
    ForeignToNativeId::<T>::insert(token_id, location.clone());
}
let command = Command::RegisterForeignToken { token_id, name, symbol, decimals };
let message_origin = Self::location_to_message_origin(sender_location)?;
Self::send(message_origin, command, amount)?;
Self::deposit_event(Event::<T>::RegisterToken { ... });
``` [2](#0-1)  The `contains_key` check scopes only the `insert`; the `Command::RegisterForeignToken` construction, `Self::send` dispatch to the outbound queue, and event emission execute unconditionally on every call, including repeat calls for a `token_id` that already exists in `ForeignToNativeId`. The identical pattern exists in the root-gated `pallet-snowbridge-system::do_register_token`. [3](#0-2)  No `ensure!` exists in either path to reject an already-registered `token_id` before the command is built and sent.

## Impact Explanation
Each redundant call sends a full `Command::RegisterForeignToken` message through the Snowbridge outbound queue to the Ethereum Gateway contract, consuming outbound-queue slot capacity and relayer processing resources for a token that is already mapped in `ForeignToNativeId`, matching the "public underpriced work that degrades block production or stalls bridge processing" impact category. The `Command::SetTokenTransferFees::register_token` field is explicitly documented as "The fee (Ether) for register token to discourage spamming," [4](#0-3)  confirming that a dedicated anti-spam fee mechanism exists for this action — but that fee applies equally to first-time and duplicate registrations, so it does not stop the state-inconsistent, guard-bypassing repeat dispatch. Any account controlling a location nested under its own consensus system can flood the outbound channel with redundant `RegisterForeignToken` messages for the same token indefinitely.

## Likelihood Explanation
High likelihood: `register_token` is reachable by any signed account via the permissionless `pallet-snowbridge-system-frontend::register_token` extrinsic (doc-stated "All origins are allowed"), the only origin restriction is that `asset_id` be nested in the caller's own location, and the missing guard on the command-send path is unconditionally triggered on every call — no privileged role, governance action, or race condition is required. [1](#0-0) 

## Recommendation
Turn the `contains_key` check into a hard `ensure!` that short-circuits the whole function before `Command::RegisterForeignToken` is constructed and sent:
```rust
ensure!(!ForeignToNativeId::<T>::contains_key(token_id), Error::<T>::TokenAlreadyRegistered);
ForeignToNativeId::<T>::insert(token_id, location.clone());
```
Apply this fix in both `pallet-snowbridge-system-v2::register_token` [5](#0-4)  and `pallet-snowbridge-system::do_register_token` [6](#0-5) .

## Proof of Concept
1. Account `A` calls `pallet-snowbridge-system-frontend::register_token(asset_id = A's own asset location, metadata, fee_asset)`; the XCM `Transact` reaches BridgeHub, `ForeignToNativeId` is populated, and `Command::RegisterForeignToken` is enqueued.
2. `A` (or any account whose location nests the same `asset_id`) calls `register_token` again with the identical `asset_id`.
3. `ForeignToNativeId::<T>::contains_key(token_id)` returns `true`, so the storage insert is skipped, but `Self::send(message_origin, command, amount)` and `Self::deposit_event(...)` still execute, enqueuing a second `Command::RegisterForeignToken` for the same token.
4. Repeating step 2 enqueues arbitrarily many duplicate `RegisterForeignToken` commands into the Snowbridge outbound queue for an already-registered token, with no on-chain rejection.
