### Title
Object-pool alternates satisfy pre-receive "object exists in quarantine" checks for content never actually pushed - ([File: internal/git/quarantine/quarantine.go])

### Summary
Gitaly's object quarantine mechanism is meant to let hooks/Rails verify that objects referenced by a ref update were actually part of the current push. However, the quarantine environment is built by combining the quarantine directory with the repository's *existing* alternate object directories — including a linked object pool. Because Git's alternates form a single unified search path, an "object exists" check performed against the quarantined repository succeeds equally for objects that were genuinely just pushed and for objects that merely happen to already exist in a shared object pool. This mirrors the JOJO finding's root cause: a validation intended to confirm that a specific expected action occurred (USDC actually paid / object actually pushed) instead validates an aggregate/observable state that can be satisfied through an unrelated channel (buying assets with the same USDC / objects already present via pool sharing).

### Finding Description
When a quarantine directory is created, `quarantine.Apply` sets the quarantined repository's alternates to be the original object directory *plus* any alternates the repository already had configured: [1](#0-0) 

For a repository that is a member of an object pool (e.g., a fork, see `doc/object_pools.md`), the pre-existing alternate is the object pool's `objects` directory. This means the resulting quarantine environment's alternates chain effectively is: `quarantine-dir : repo/objects : pool/objects`.

`GitLabHookManager.preReceiveHook` uses exactly this combined `GitObjectDirectory`/`GitAlternateObjectDirectories` set, derived from the `GIT_OBJECT_DIRECTORY`/`GIT_ALTERNATE_OBJECT_DIRECTORIES` environment that `git-receive-pack` supplies, and forwards it to Rails' `/internal/allowed` endpoint and to any custom hooks: [2](#0-1) 

The documented purpose of this plumbing is precisely to let hooks and RPC calls "see the objects that are being pushed" while they are still quarantined: [3](#0-2) 

The test helper `WriteCheckNewObjectExistsHook` demonstrates the exact check pattern this is designed for — a hook that only passes "if it can find the object in the quarantine directory," relying on `GIT_OBJECT_DIRECTORY`/`GIT_ALTERNATE_OBJECT_DIRECTORIES` being wired correctly: [4](#0-3) 

The flaw is that this same `git cat-file -e $oid`-style check (used by custom hooks, and semantically by any Rails access check that wants to confirm "this object is part of the current push") cannot distinguish between an object that arrived in the actual quarantine directory (i.e., genuinely part of this push) and an object that is merely reachable through the pool alternate that was already linked to the repository before the push started. Any object already present in the shared object pool — for example content contributed by another fork of the same source project, or by the pool's primary member — will make such a check succeed even though it was never transmitted in the push being evaluated.

This is structurally identical to the JOJO bug: the check `IERC20(primaryAsset).balanceOf(liquidated) - primaryLiquidatedAmount >= liquidateData.liquidatedRemainUSDC` intended to prove "the liquidator actually paid X," but any USDC arriving via an unrelated purchase satisfied it. Here, the check intended to prove "this object was actually part of the current push" is satisfied by unrelated pre-existing objects reachable via the pool alternate.

### Impact Explanation
A pusher to a pool-linked repository (an ordinary fork owner — no special privilege required) can craft a ref update whose target commit/tree/blob objects are not included in the pushed pack at all, as long as those exact objects already exist somewhere in the shared object pool. Any hook or access-check logic that uses "object reachable in quarantine/alternates" as a proxy for "object legitimately part of this push" (e.g., custom hooks scanning newly introduced content, hooks enforcing checks on pushed blobs) will incorrectly treat such objects as validated/new, even though their actual provenance and content review never happened for this push. This can be leveraged to smuggle references to pool-shared content past checks that assume all referenced objects were freshly delivered and inspected as part of the push under evaluation.

### Likelihood Explanation
Object pools are a standard, always-on feature for GitLab forks; any user who can push to a fork is automatically in this configuration. No malicious peer, MITM, or leaked credential is required — only a normal push to a repository that is (or becomes) a pool member, which is triggered simply by forking and pushing, both ordinary user actions.

### Recommendation
Hooks and access-check logic that need to determine whether an object was genuinely part of the current push should check for object presence in the quarantine directory specifically (`GIT_OBJECT_DIRECTORY`), not the combined alternates chain that also includes pre-existing pool alternates. Where the combined search path is required for functional reasons (e.g., resolving parents of newly pushed commits), any check whose semantics require proof of "was this delivered in this push" should be redesigned to not rely solely on `cat-file -e`/alternates-reachability against the quarantine + alternates set.

### Proof of Concept
1. Fork a public project `P` so the fork `F` is linked to `P`'s object pool (standard GitLab fork flow), giving `F`'s repository the pool's `objects` directory as a Git alternate.
2. Identify an object `X` (blob/tree/commit) that already exists in the shared pool (e.g., content contributed by another fork of `P`, or by `P` itself) but is not present in `F`.
3. Push a new ref to `F` whose tip commit references `X` as one of its tree entries, while omitting `X`'s raw data from the push's pack (Git will still accept it if `X` is resolvable via alternates).
4. A pre-receive hook using the pattern from `WriteCheckNewObjectExistsHook` (`git cat-file -e "$newrev"`/`git cat-file -e <blob>`) against the quarantined repository succeeds, because `GIT_ALTERNATE_OBJECT_DIRECTORIES` includes the pool's `objects` directory — even though `X` was never actually transmitted as part of this push.
5. Any downstream logic relying on this check to assert "all referenced content was uploaded and inspected in this push" is bypassed for object `X`.

// Apply applies the quarantine on the repository. This is done by setting the quarantineDirectory
// as the repository's object directory, and configuring the repository's object directory as an alternate.
func Apply(repoPath string, repo *gitalypb.Repository, quarantineDir string) (*gitalypb.Repository, error) {
	relativePath, err := filepath.Rel(repoPath, quarantineDir)
	if err != nil {
		return nil, fmt.Errorf("creating quarantine: %w", err)
	}

	// All paths are relative to the repository root.
	objectDir := repo.GetGitObjectDirectory()
	if objectDir == "" {
		// Set the default object directory as an alternate if the repository didn't
		// have the object directory overwritten yet.
		objectDir = "objects"
	}

	alternateObjectDirs := make([]string, 0, len(repo.GetGitAlternateObjectDirectories())+1)
	alternateObjectDirs = append(alternateObjectDirs, objectDir)
	alternateObjectDirs = append(alternateObjectDirs, repo.GetGitAlternateObjectDirectories()...)

	quarantinedRepo := proto.Clone(repo).(*gitalypb.Repository)
	quarantinedRepo.GitObjectDirectory = relativePath
	quarantinedRepo.GitAlternateObjectDirectories = alternateObjectDirs

	return quarantinedRepo, nil
}

func (m *GitLabHookManager) preReceiveHook(ctx context.Context, payload gitcmd.HooksPayload, repo *gitalypb.Repository, pushOptions, envs []string, changes []byte, stdout, stderr io.Writer) error {
	repoPath, err := m.locator.GetRepoPath(ctx, repo)
	if err != nil {
		return structerr.NewInternal("getting repo path: %w", err)
	}

	if gitObjDir, gitAltObjDirs := env.ExtractValue(envs, "GIT_OBJECT_DIRECTORY"), env.ExtractValue(envs, "GIT_ALTERNATE_OBJECT_DIRECTORIES"); gitObjDir != "" && gitAltObjDirs != "" {
		gitObjectDirRel, gitAltObjectDirRel, err := getRelativeObjectDirs(repoPath, gitObjDir, gitAltObjDirs)
		if err != nil {
			return structerr.NewInternal("getting relative git object directories: %w", err)
		}

		repo.GitObjectDirectory = gitObjectDirRel
		repo.GitAlternateObjectDirectories = gitAltObjectDirRel
	}

	if len(changes) == 0 {
		return structerr.NewInternal("hook got no reference updates")
	}

	if repo.GetGlRepository() == "" {
		return structerr.NewInternal("repository not set")
	}
	if payload.UserDetails == nil {
		return structerr.NewInternal("payload has no receive hooks info")
	}
	if payload.UserDetails.UserID == "" {
		return structerr.NewInternal("user ID not set")
	}
	if payload.UserDetails.Protocol == "" {
		return structerr.NewInternal("protocol not set")
	}

	params := gitlab.AllowedParams{
		RepoPath:                      repoPath,
		RelativePath:                  repo.GetRelativePath(),
		GitObjectDirectory:            repo.GetGitObjectDirectory(),
		GitAlternateObjectDirectories: repo.GetGitAlternateObjectDirectories(),
		GLRepository:                  repo.GetGlRepository(),
		GLID:                          payload.UserDetails.UserID,
		GLProtocol:                    payload.UserDetails.Protocol,
		Changes:                       string(changes),
		PushOptions:                   pushOptions,
		ClientContext:                 payload.GitalyClientContext,
	}

// WriteCheckNewObjectExistsHook writes a pre-receive hook which only succeeds
// if it can find the object in the quarantine directory. if
// GIT_OBJECT_DIRECTORY and GIT_ALTERNATE_OBJECT_DIRECTORIES were not passed
// through correctly to the hooks, it will fail
func WriteCheckNewObjectExistsHook(tb testing.TB, repoPath string) {
	WriteCustomHook(tb, repoPath, "pre-receive", []byte(
		`#!/bin/sh
		while read oldrev newrev reference
		do
			git cat-file -e "$newrev" || exit 1
		done
	`))
}
