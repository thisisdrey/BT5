The strongest analog for this "cross-context identity leak" class is the Operator meta-sender path. Let me verify what an attacker contract could do while `MSG_SENDER` is set.### Title
`Operator.execute` leaks the user's impersonated `msg.sender` to arbitrary called contracts, allowing theft of unlocked collateral - ([File: contracts/Operator.sol](contracts/Operator.sol))

### Summary
`Operator.execute` stores the EOA initiator in the transient `MSG_SENDER` slot and then performs arbitrary external calls. `SynthContext._msgSender()` resolves any call coming from `Operator` to that stored EOA. Because `MSG_SENDER` stays set for the entire batch, any contract invoked inside `execute` can call back into Metronome contracts and be treated as the initiating user — e.g., transfer or withdraw their unlocked deposit tokens. This is the same bug class as CVE-2022-1498: an implementation flaw leaks a cross-context privilege (the authenticated sender identity) to untrusted code.

### Finding Description
`Operator.execute` sets `MSG_SENDER` to `msg.sender` before iterating `calls_` and clears it only after the loop [1](#0-0) . Each call is an arbitrary `target.functionCallWithValue` chosen in the calldata [2](#0-1) . `SynthContext._msgSender()` returns `getActualMsgSender()` for *any* call whose `msg.sender` is the Operator [3](#0-2) . There is no per-call reset of the transient slot between iterations, and `nonReentrant` on `execute` only blocks re-entering `Operator`, not downstream protocol contracts.

`DepositToken.transfer` resolves `_msgSender()` and moves the caller's unlocked balance [4](#0-3) ; `withdraw` burns the caller's balance and pulls underlying from Treasury to an arbitrary `to_` [5](#0-4) . `unlockedBalanceOf` returns the full balance when the account has no debt [6](#0-5) . Neither `transfer` nor `withdraw`'s `_withdraw` path is blocked by any check that distinguishes the batched callee from the initiating user.

Attack flow:
1. Attacker deploys contract `A` (e.g., a fake "claim" or "swap helper" contract) and induces a victim holding msdTOKEN collateral to call `Operator.execute` with a batch containing `A.someFunction()` — a routine phishing/UI pattern, consistent with the UI:R nature of the source CVE.
2. During `execute`, `MSG_SENDER = victim`. `A.someFunction()` calls `depositToken.withdraw(balance, attacker)` (or `transfer(attacker, amount)`).
3. `DepositToken` sees `msg.sender == Operator`, resolves `_msgSender() = victim`, and sends the victim's unlocked collateral to the attacker.

### Impact Explanation
Direct theft of user funds: all unlocked msdTOKEN balances (the entire deposit for debt-free users) can be transferred or withdrawn to the attacker in one transaction. The identity invariant — that the resolved sender is the party that intentionally initiated the protocol call — is broken, because the authenticated identity is ambiently exposed to every contract touched by the batch.

### Likelihood Explanation
Medium-low. It requires the victim to batch a call to attacker-influenced code via `Operator.execute` (user interaction / phishing), matching CVE-2022-1498's UI:R profile. No privileged role, oracle manipulation, or third-party failure is needed; the flaw is entirely in Metronome's own forwarding design. Multicall patterns that deliberately preserve a trusted-sender context across arbitrary calls are a known hazard (cf. Uniswap's `Payments`/Permit2 discussions), and Metronome even routes legitimate flows (deposits, withdrawals, swaps) through `Operator`, making co-mingled external calls realistic.

### Recommendation
- Set the `MSG_SENDER` slot per-call or scope it so only whitelisted protocol targets may be invoked while it is set (e.g., restrict `execute` to targets registered in `PoolRegistry`, or authenticate via a signature/nonce tied to the specific calldata).
- Alternatively, in each protocol entry point, verify both `msg.sender == operator` *and* that the caller chain is expected (e.g., disallow external calls out of `execute` between protocol calls by clearing `MSG_SENDER` after each protocol call).
- At minimum, document that `calls_` targets are fully trusted as the sender, and provide a separate path for calls to untrusted contracts.
