Based on the evidence gathered, the strongest local analog to the reported bug class ("assuming a fixed/static decimals value used in a price/amount conversion, without hard-binding it to a value that cannot silently drift") is in `pallet-psm` (`substrate/frame/psm/src/lib.rs`), not in a price-feed but in its external/internal asset decimal-normalization logic that was added specifically to fix this exact bug class (PR `11819`, "pallet-psm: support external assets with different decimal precision").

The pallet's fix trades a silent mis-pricing bug for a fail-closed guard (`DecimalsMismatch`) that halts swaps whenever live asset metadata decimals diverge from the decimals snapshot taken at `add_external_asset` registration time. This guard is enforced identically in `mint` at every call via `ensure_decimals_match` [1](#0-0) , and confirmed to halt the pallet's operation for the affected asset pair rather than simply auto-adjusting, per the PR description and a dedicated regression test [2](#0-1) .

### Title
Unprivileged external-asset metadata mutation permanently locks PSM reserve funds via `DecimalsMismatch` halt - (File: `substrate/frame/psm/src/lib.rs`)

### Summary
`pallet-psm` snapshots an approved external asset's `decimals` at `add_external_asset` time and re-validates it against live `pallet-assets` metadata on every `mint`/`redeem` call. If the live decimals ever diverge from the snapshot, the pallet returns `Error::DecimalsMismatch` and refuses to process swaps for that asset pair "until governance intervenes" [3](#0-2) . Because the decimals value being checked is the *external asset's own* `pallet-assets` metadata, whoever controls that asset's `Owner`/`Admin` account (not PSM governance) can unilaterally call `pallet_assets::set_metadata` to change `decimals` at any time, immediately and permanently (until manual governance remediation) freezing redemption of that asset from the PSM reserve.

### Finding Description
`ensure_decimals_match` is invoked at the top of `mint` (and presumably `redeem`, by symmetric design) and is what gates the entire swap path [4](#0-3) . The conversion helpers `external_to_internal`/`internal_to_external` correctly use the *snapshotted* decimals for scaling [5](#0-4) , so the original TOB-style mis-pricing bug is closed. However, the anti-drift guard converts a pricing bug into an availability/fund-lock bug: any external asset approved by a PSM instance retains its normal `pallet-assets` ownership semantics, so the asset's `Owner` (a regular, non-privileged account for permissionless/local assets, or a remote sovereign account for foreign assets) can call `set_metadata` to change `decimals` without needing PSM governance approval. The moment this happens, every subsequent `mint`/`redeem` call for that `(internal_asset, external_asset)` pair reverts with `DecimalsMismatch`, exactly as demonstrated by the existing test `mint_halts_when_internal_decimals_drift` [2](#0-1) . Users who already deposited external asset into the PSM reserve and hold internal-asset balances backed 1:1 by that reserve can no longer redeem, since `redeem` shares the same decimals-drift check by design ("Runtime drift guard: mint/redeem return DecimalsMismatch if live metadata diverges from the registration snapshot") [3](#0-2) .

### Impact Explanation
This falls squarely in the "permanent user-fund or bridge-state lock" impact category: legitimate holders of the internal (pegged) asset lose the ability to redeem their claim on the PSM's external-asset reserve for as long as governance has not manually intervened, and the trigger is a normal `pallet-assets` metadata call by an unprivileged, non-governance account (the asset owner), not by PSM governance or admin. Reserve funds for that asset pair become inert — neither newly mintable nor redeemable — degrading the PSM's core peg-stability guarantee stated in the module docs.

### Likelihood Explanation
Likelihood depends on which accounts hold `Owner`/`Admin` rights over assets approved as "external" in a given PSM instance. For any externally-approved asset whose ownership was not renounced/frozen (e.g., a permissionless `pallet-assets`-created token, or one whose owner is a remote chain's sovereign account with independent metadata-update rights), the halt condition can be triggered trivially and cheaply — a single `set_metadata` extrinsic — with no need to compromise governance, a validator, a relayer, or any privileged role.

### Recommendation
Do not let external, non-PSM-governance-controlled metadata mutation unilaterally freeze redemption of already-deposited reserve funds. Options: (1) decouple redemption from the drift check — always allow `redeem` using the frozen `ExternalDecimals`/`InternalDecimals` snapshot regardless of live metadata drift (only gate `mint` on drift, since minting is where mis-pricing risk originates), or (2) require assets approved via `add_external_asset` to have their metadata ownership transferred to a governance/frozen account (or use `pallet-assets`' metadata-freezing capability) before approval, so the snapshot cannot be invalidated by a non-governance actor after the fact.

### Proof of Concept
1. Governance calls `Psm::add_external_asset(internal_asset, external_asset=X, ...)` where asset `X` is a permissionless `pallet-assets` token whose `Owner` is `attacker`; PSM snapshots `ExternalDecimals[X] = 6`.
2. Users `mint` internal asset by depositing `X` into the PSM reserve; PSM debt and reserve grow.
3. `attacker` (owner of `X`, not PSM governance) calls `pallet_assets::set_metadata(X, ..., decimals = 7)`.
4. Any subsequent `mint`/`redeem` call referencing `(internal_asset, X)` now reverts with `Error::DecimalsMismatch`, per `ensure_decimals_match` [1](#0-0)  and the regression test pattern shown at [2](#0-1) .
5. Users holding internal asset backed by `X` in the reserve can no longer redeem it; funds remain locked until governance manually updates the snapshot or migrates the asset out.

**Caveat:** I could not retrieve the full source of `ensure_decimals_match` or the `redeem` dispatchable in this session (index/context limits), so I cannot confirm from source whether the halt is scoped strictly per-`(internal, external)` pair or has any partial mitigation (e.g., an emergency redeem-only bypass). 		pub(crate) fn external_to_internal(
			amount: BalanceOf<T>,
			ext_decimals: u8,
			internal_decimals: u8,
		) -> Result<BalanceOf<T>, Error<T>> {
			use core::cmp::Ordering::*;
			match ext_decimals.cmp(&internal_decimals) {
				Equal => Ok(amount),
				Less => {
					let diff = (internal_decimals - ext_decimals) as u32;
					let factor = Self::pow10(diff)?;
					amount.checked_mul(&factor).ok_or(Error::<T>::ConversionOverflow)
				},
				Greater => {
					let diff = (ext_decimals - internal_decimals) as u32;
					let factor = Self::pow10(diff)?;
					Ok(amount.checked_div(&factor).unwrap_or_else(BalanceOf::<T>::zero))
				},
			}
		}
