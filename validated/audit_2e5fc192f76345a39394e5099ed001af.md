### Title
`Pool.removeDepositToken()` can be permanently griefed by a dust deposit inflating `totalSupply` - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
`Pool.removeDepositToken()` refuses to remove a deposit token while `depositToken_.totalSupply() > 0`. The same check exists in `removeDebtToken()`. Any unprivileged user can deposit a negligible amount of underlying through `DepositToken.deposit()`, minting dust `msdToken` to themselves, which keeps `totalSupply > 0` and blocks removal indefinitely. This mirrors the reported `removeAsset` DoS in Rio: a "must be empty to remove" invariant that an attacker can satisfy cheaply forever.

### Finding Description
The relevant code:

```solidity
// contracts/Pool.sol
function removeDepositToken(IDepositToken depositToken_) external onlyGovernor {
    if (depositToken_.totalSupply() > 0) revert TotalSupplyIsNotZero();
    ...
}

function removeDebtToken(IDebtToken debtToken_) external onlyGovernor {
    if (debtToken_.totalSupply() > 0) revert TotalSupplyIsNotZero();
    ...
}
```

`DepositToken.deposit()` is fully permissionless (`whenNotPaused nonReentrant onlyIfDepositTokenExists`) and mints to any `onBehalfOf_` address. Each `_mint` increases `totalSupply`; only `_burn` (via `withdraw`/`flashWithdraw`/`seize`) decreases it. There is no mechanism for the governor (or anyone) to force-burn another account's `msdTOKEN` balance — `seize` is only reachable through `Pool.liquidate` against an unhealthy position, and `shutdown()` would block *withdrawals* rather than clear supply.

Therefore an attacker who deposits 1 wei of underlying (e.g. via `deposit(1, attacker)`) makes `removeDepositToken` permanently revert `TotalSupplyIsNotZero` until they voluntarily withdraw. Even if the governor calls `toggleIsActive()` to stop further deposits, the already-minted dust keeps `totalSupply > 0`. The attacker can also front-run any future removal attempts by re-depositing dust as long as the token is active.

The identical issue applies to `removeDebtToken`: an attacker can `DebtToken.issue()` a dust amount of synth debt (or hold dust debt after repaying) to keep `debtToken_.totalSupply() > 0`, permanently blocking removal.

### Impact Explanation
Permanent DoS of `removeDepositToken`/`removeDebtToken` for a specific token. Governance loses the ability to delist a collateral or synth market — e.g. a deprecated/unsafe collateral cannot be removed from `depositTokens`, and `depositTokenOf[underlying]` remains occupied, also blocking `addDepositToken` for a replacement token on the same underlying (`UnderlyingAssetInUse`). The cost to the attacker is ~1 wei of underlying plus gas.

### Likelihood Explanation
Requires only public calls (`DepositToken.deposit` / `DebtToken.issue`), no privileged role, no oracle manipulation, and negligible capital. It does depend on governance attempting a removal while the attacker front-runs or pre-seeds the supply — but the attacker's dust position is cheap to maintain and can be opened at any time the token is active, so the griefing window is essentially always open. Funds are not stolen; impact is a governance/liveness DoS, consistent with a Medium/Low severity.

### Recommendation
Base removability on internal accounting the attacker cannot cheaply keep non-zero, or make removal a two-step process: `toggleIsActive()`/pause minting first, then allow `removeDepositToken` to succeed regardless of residual `totalSupply` by migrating/forfeiting residual balances (e.g. burning remaining supply and pulling the proportional collateral to treasury via an owner-sweep path). At minimum, allow the governor to force-remove while leaving stranded `msdTOKEN` holders a claim path on the treasury.

### Proof of Concept
Hardhat sketch:

```ts
it('griefs removeDepositToken with a dust deposit', async () => {
  // pool, depositToken (msdMET), underlying MET already wired; depositToken isActive
  const attacker = signers[4];

  // Attacker deposits 1 wei of underlying; totalSupply becomes 1
  await underlying.mint(attacker.address, 1);
  await underlying.connect(attacker).approve(depositToken.address, 1);
  await depositToken.connect(attacker).deposit(1, attacker.address);
  expect(await depositToken.totalSupply()).to.eq(1);

  // Governor attempts removal -> reverts
  await expect(pool.removeDepositToken(depositToken.address))
    .revertedWithCustomError(pool, 'TotalSupplyIsNotZero');

  // Even after governor disables the token, attacker's dust remains
  await depositToken.toggleIsActive(); // governor
  await expect(pool.removeDepositToken(depositToken.address))
    .revertedWithCustomError(pool, 'TotalSupplyIsNotZero');
  // Removal is permanently blocked until the attacker voluntarily withdraws.
});
```

The DebtToken variant is symmetric: `debtToken.issue(...)` a dust amount of synth against deposited collateral, then `pool.removeDebtToken(debtToken)` always reverts `TotalSupplyIsNotZero`.

        if (amount_ == 0) revert AmountIsZero();

        IERC20 _underlying = underlying;
        address _msgSender = _msgSender();

        uint256 _balanceBefore = _underlying.balanceOf(_treasury);
        _underlying.safeTransferFrom(_msgSender, _treasury, amount_);
        amount_ = _underlying.balanceOf(_treasury) - _balanceBefore;

        if (_fee > 0) {
            _mint(_pool.feeCollector(), _fee);
        }

        _mint(onBehalfOf_, _deposited);
