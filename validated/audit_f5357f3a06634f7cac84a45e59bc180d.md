### Title
Missing bounds validation in `extractBytes`/`extractBytesArray`/`extractSigArray` allows out-of-bounds array access from attacker-controlled precompile calldata - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
`PrecompiledContracts.extractBytes` computes a slice of the raw precompile input using an `offset` and `len` that are derived entirely from attacker-controlled ABI-encoded words, without validating that `offset + len` stays within `data.length`. This mirrors the reported `LibBytes.keccak` bug pattern: hashing/copying memory using an offset/length pair that is never checked against the underlying buffer's actual size.

### Finding Description
`extractBytes` is a thin wrapper around `Arrays.copyOfRange`: [1](#0-0) 

It is invoked from `extractBytesArray` and `extractSigArray`, where both `bytesOffset` and `bytesLen` (and the derived slice bounds) come directly from `DataWord[] words`, i.e., from the raw ABI-encoded calldata supplied by the caller of the `ValidateMultiSign` / `BatchValidateSign` TVM precompiled contracts: [2](#0-1) 

These helpers are reached from `ValidateMultiSign.execute` and `BatchValidateSign.doExecute`, which are precompiled contracts invocable by any smart contract via a `CALL`/`STATICCALL` opcode to their fixed address — i.e., reachable by any unprivileged transaction that deploys or calls a contract performing that call: [3](#0-2) [4](#0-3) 

Unlike the `LibBytes.keccak` recommendation (`require(offset + length <= data.length)`), there is no equivalent check here: `bytesOffset` (`words[offset + i + 1].intValueSafe() / WORD_SIZE`) and `bytesLen` (`words[offset + bytesOffset + 1].intValueSafe()`) are attacker-controlled and can be crafted to point far outside `rawData`/`data`'s actual length. `Arrays.copyOfRange(data, offset, offset + len)` will throw `ArrayIndexOutOfBoundsException` (or `NegativeArraySizeException`/`IllegalArgumentException` for pathological values) instead of the intended "hash/hash-slice out-of-bounds" memory read seen in the Solidity report, but the root cause — missing offset/length validation against the actual data length prior to the unsafe slicing operation — is the same bug class.

There is a partial mitigation added for the "Osaka" hard-fork flag (`isValidAbiEncoding`) which checks only that `data.length` is a multiple of 32 and that the tail is consistent with a fixed header/item word count — it does **not** validate that the *nested* offsets used inside `extractBytesArray`/`extractSigArray` stay within bounds: [5](#0-4) 

Before this flag is active (`allowTvmOsaka()==0`), no such structural check exists at all, and the code path is documented in tests as intentionally allowing the legacy decoder to throw: [6](#0-5) 

### Impact Explanation
A crafted `CALL` to the `ValidateMultiSign` or `BatchValidateSign` precompile with an out-of-bounds nested offset/length pair causes `extractBytes` to throw an uncaught `ArrayIndexOutOfBoundsException`/`NegativeArraySizeException`. In `ValidateMultiSign.execute`, this call is made **outside** the surrounding `try { ... } catch (Throwable t)` block that only wraps the later signature-verification loop, so the exception propagates uncaught out of `execute()`. Depending on how the TVM engine's `callToPrecompiledAddress` path handles unexpected `RuntimeException`s bubbling out of a precompiled contract's `execute()`, this can either (a) abort only the calling transaction (denial of service for that transaction/limited impact) or (b) if not properly caught somewhere up the call stack, crash the node process executing the transaction, which would be a chain-halting/availability issue for a full node processing blocks. The `OperationsTest.testTip854OuterFrameContainment` test shows the team is aware of and hardening around this exact area (TIP-854), confirming this class of uncaught exception from precompile calldata parsing is a recognized concern.

### Likelihood Explanation
High reachability: any account can submit a transaction that triggers a `CALL` to these precompiled addresses with attacker-chosen calldata bytes — no special privilege, staking, or witness/SR role required. Constructing the malformed nested-offset payload only requires basic ABI-encoding knowledge.

### Recommendation
Add explicit bounds checks in `extractBytes`, `extractBytesArray`, and `extractSigArray` verifying that `offset >= 0` and `offset + len <= data.length` before calling `Arrays.copyOfRange`, returning a failure `Pair.of(false, EMPTY_BYTE_ARRAY)` (consistent with other malformed-input handling in `PrecompiledContracts.java`) instead of letting an unchecked exception propagate. Extend `isValidAbiEncoding` (or add a dedicated check) to validate that all derived nested offsets/lengths used by `extractBytesArray`/`extractSigArray` are within `data.length`, not just that the top-level length is a multiple of `WORD_SIZE`.

### Proof of Concept
Not independently executed; based on static analysis of `extractBytes`/`extractBytesArray`/`extractSigArray` in `PrecompiledContracts.java`, a conceptual PoC would: (1) craft ABI-encoded calldata for `validatemultisign(address,uint256,bytes32,bytes[])` where the `bytes[]` header word at index `words[3]` and the per-element offset/length words are set to large or negative values exceeding `rawData.length`; (2) deploy a trivial contract that performs `CALL` to precompile address for `ValidateMultiSign`/`BatchValidateSign` with that calldata; (3) observe `Arrays.copyOfRange` in `extractBytes` throw an uncaught exception outside the `try/catch` guarding `ValidateMultiSign.execute`. Full exploitation impact (transaction-local failure vs. node crash) would need verification against `Program.callToPrecompiledAddress`'s exception handling, which could not be located/confirmed within the available tool budget.

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }

  private static byte[][] extractSigArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          SIG_LENGTH);
    }
    return bytesArray;
  }

  private static byte[] extractBytes(byte[] data, int offset, int len) {
    return Arrays.copyOfRange(data, offset, offset + len);
  }

  private static boolean isValidAbiEncoding(byte[] data, int headerWords, int itemWords) {
    if (data == null || data.length % WORD_SIZE != 0) {
      return false;
    }
    long tail = subtractExact(data.length, multiplyExact(headerWords, WORD_SIZE));
    return tail > 0 && tail % multiplyExact(itemWords, WORD_SIZE) == 0;
  }
