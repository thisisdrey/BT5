### Title
Dust `DepositToken` transfers fill a victim's per-account token list (`MAX_TOKENS_PER_USER`), blocking new collateral deposits needed to rescue an unhealthy position - ([File: contracts/DepositToken.sol](contracts/DepositToken.sol))

### Summary
`DepositToken._transfer` and `DepositToken._mint` unconditionally call `Pool.addToDepositTokensOfAccount` whenever the recipient's balance of that token transitions from 0 to positive. `Pool.addToDepositTokensOfAccount` enforces `MAX_TOKENS_PER_USER = 30` (shared between `depositTokensOfAccount` and `debtTokensOfAccount`) via `onlyIfAdditionWillNotReachMaxTokens`. An unprivileged attacker can deposit dust into every listed `DepositToken` (or receive dust through `transfer`) and push 1 wei of each msd token to a victim. Once the victim's combined list hits 30, any deposit into a *new* collateral type reverts inside `_mint`, and any mint of a *new* `DebtToken` reverts inside `DebtToken`'s equivalent hook. This lets the attacker prevent a victim from topping up collateral on an at-risk position, forcing a liquidation the victim would otherwise have avoided. This is the Metronome analog of a client-availability/crash bug class (CVE-2018-3081: difficult-to-exploit DoS plus limited integrity impact).

### Finding Description
- `DepositToken._mint` (`contracts/DepositToken.sol:469-489`) and `DepositToken._transfer` (`contracts/DepositToken.sol:498-526`) call `pool.addToDepositTokensOfAccount(recipient_)` whenever the recipient's prior balance is 0.
- `Pool.addToDepositTokensOfAccount` (`contracts/Pool.sol:216-220`) is gated by `onlyIfAdditionWillNotReachMaxTokens` (`contracts/Pool.sol:143-148`), which reverts with `UserReachedMaxTokens` when `debtTokensOfAccount.length + depositTokensOfAccount.length >= 30`.
- `DepositToken.transfer`/`transferFrom` only check `_revertIfLocked` on the *sender's* balance (`contracts/DepositToken.sol:181`); the recipient has no way to refuse the transfer, and the `addToDepositTokensOfAccount` call happens inside the same transaction, so a revert there makes the whole transfer revert only for tokens the attacker never owned a slot in — the attacker simply picks tokens not yet in the victim's list.
- Attack: attacker deposits minimum amounts into each pool `DepositToken`, then calls `transfer(victim, 1)` for each token the victim doesn't already hold, until `depositTokensOfAccount[victim] + debtTokensOfAccount[victim] == 30`. Cost is bounded by the number of listed deposit tokens (a handful per pool in practice, plus minting a few dust `DebtToken`s via `SmartFarmingManager.leverage`/`flashIssue`-style paths is not needed — the cap counts both lists, so filling with deposit tokens alone blocks new debt tokens too).
- Result: every subsequent `deposit(amount, victim)`/`transfer` that would create a *new* token entry reverts. If the victim's position later drifts toward unhealthy (interest accrual via `DebtToken.accrueInterest`, price moves), the victim cannot add a new collateral type to restore health and is forced into `Pool.liquidate`, paying liquidation bonus and `protocolLiquidationFee` (`Pool.liquidate`, `contracts/Pool.sol:571-596`).

### Impact Explanation
Temporary freezing of collateral-adding capability plus forced liquidation: the victim's ability to deposit additional (new-type) collateral or take new debt is DoS'd for as long as the attacker keeps the slots filled. The victim can recover slots only by transferring the dust away themselves (each `transfer` to zero out a balance calls `pool.removeFromDepositTokensOfAccount`, `contracts/DepositToken.sol:522-525`), costing gas per token, and the attacker can cheaply re-dust in response, including front-running cleanup transactions. The primary concrete loss is the liquidation penalty seized from the victim's position that they could not defend. This matches the accepted "temporary freezing of funds" impact class.

### Likelihood Explanation
Fully unprivileged: needs only standard deposits and ERC20 transfers of the msd tokens, no privileged role. Requirements: the victim must hold a borrow position near its collateralization limit, and the number of fillable slots (30 minus the victim's existing entries) must be reachable with the pool's listed `DepositToken`s plus debt-token entries the attacker can't force (debt tokens can't be transferred — `DebtToken.transfer` reverts — so only deposit tokens fill the victim's list; effectiveness depends on the pool listing enough deposit tokens to reach 30 combined, or the victim already holding several entries). Cleanup is self-service but races against re-griefing. Moderate likelihood where a pool lists many deposit tokens.

### Recommendation
- Do not auto-register recipients on `transfer`: only add to `depositTokensOfAccount` on `deposit`/`mint`, or make list registration opt-in for transfers (track a per-account "registered" set separate from raw balance, e.g., check locked/relevant balance in `depositOf` instead of presence in the list).
- Alternatively, allow `deposit`/`issue` to bypass the max-tokens check when the token is being added purely as a consequence of a user-initiated deposit, or raise/scope `MAX_TOKENS_PER_USER` per token-type list rather than a combined cap.
- Provide a `withdraw`/`transfer`-free path for users to purge zero-value entries (e.g., anyone can call a cleanup that removes tokens where `balanceOf(account) == 0`), which is impossible today since only balance-going-to-0 triggers removal.

### Proof of Concept
Hardhat fork outline (against a deployed Pool, e.g. Base deployment):

```ts
// victim has an open position with debt in msUSDDebt and holds some deposit tokens
const depositTokens = await pool.getDepositTokens(); // listed deposit tokens
const victim = ...; // account with unhealthy-leaning position

// Attacker: deposit dust and transfer 1 wei of each token victim doesn't hold
for (const dt of depositTokens) {
  const token = await ethers.getContractAt('DepositToken', dt);
  if ((await token.balanceOf(victim)).eq(0)) {
    const underlying = await ethers.getContractAt('IERC20', await token.underlying());
    await underlying.approve(dt, DUST);
    await token.deposit(DUST, attacker.address);           // mint dust to attacker
    await token.transfer(victim.address, 1);               // addToDepositTokensOfAccount(victim)
  }
}

const held = (await pool.getDepositTokensOfAccount(victim)).length +
             (await pool.getDebtTokensOfAccount(victim)).length;
expect(held).to.eq(await pool.MAX_TOKENS_PER_USER());

// Victim tries to deposit a collateral type not in their list -> reverts
const newDt = await ethers.getContractAt('DepositToken', newDepositToken);
await expect(newDt.connect(victim).deposit(amount, victim.address))
  .revertedWithCustomError(pool, 'UserReachedMaxTokens');

await ethers.provider.send('evm_increaseTime', [30 * 24 * 3600]);
