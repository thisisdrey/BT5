### Title
Attacker can permanently block a victim's ability to add new collateral/debt tokens via dust `deposit(onBehalfOf)` griefing, forcing liquidation - (File: contracts/Pool.sol)

### Summary
The bug class from CVE-2021-2418 is a repeatable, low-cost denial of service (complete crash/hang of a service). The Metronome analog is the per-account token-slot limit `MAX_TOKENS_PER_USER` in `Pool`. `DepositToken.deposit(amount_, onBehalfOf_)` mints to an arbitrary beneficiary, and `DepositToken._mint` unconditionally calls `pool.addToDepositTokensOfAccount(account_)`, which reverts `UserReachedMaxTokens` once the victim holds 30 distinct deposit/debt tokens. Because additions are triggered by *receiving* tokens (not by an opt-in call), any unprivileged EOA can dust-fill a victim's slots. Once full, every path that would add a new token to the victim's list reverts: `deposit`, `transfer`/`transferFrom`, `issue` (new debt token), `leverage`, and `seize` during `Pool.liquidate`.

### Finding Description
- `Pool.addToDepositTokensOfAccount` enforces `debtTokensOfAccount.length + depositTokensOfAccount.length < MAX_TOKENS_PER_USER` (30) and reverts otherwise (`Pool.sol:143-148, 216-220`).
- `DepositToken.deposit` accepts any `onBehalfOf_` and calls `_mint(onBehalfOf_, _deposited)` (`DepositToken.sol:211-237`).
- `DepositToken._mint` calls `pool.addToDepositTokensOfAccount(account_)` whenever `balanceOf` was 0 (`DepositToken.sol:486-488`).
- `DepositToken._transfer` does the same for the recipient (`DepositToken.sol:518-520`), so `transfer`, `transferFrom`, and `seize` (called by `Pool.liquidate` via `DepositToken.seize` at `DepositToken.sol:343-345`) all revert if the recipient's list is at capacity.
- Removal only happens when a balance returns to exactly zero (`DepositToken.sol:460-462, 523-525`); an attacker sends 1-wei dust so the victim's slots stay occupied (victim can remove a slot only by fully withdrawing/transferring that token, and each received dust slot must be individually emptied — the attacker can re-dust front-running the recovery).

Attack: for each distinct `DepositToken` registered in the pool, attacker calls `deposit(dustAmount, victim)` where `dustAmount` is just enough that `quoteDepositOut` yields `_deposited >= 1`. Cost is negligible (dust collateral + gas). The victim's `depositTokensOfAccount` list is filled with tokens they never chose.

### Impact Explanation
Availability impact matching the CVE's "complete DOS" class:
- Victim cannot deposit any *new* collateral type, cannot receive deposit-token transfers, and cannot open debt in a new `DebtToken` — the transaction reverts with `UserReachedMaxTokens`.
- Critically, a victim whose position drifts toward liquidation cannot top up a *different* collateral to restore health; the forced inability to add collateral leads directly to liquidation/seizure of their existing collateral — freezing of deposit capability converting into loss of position value.
- A liquidator whose own list is at capacity cannot be the `seize` recipient for a new token type, narrowing liquidation execution for positions holding tokens the liquidator doesn't already have.
- Recovery requires the victim to zero out a dust balance (paying withdraw fees) while the attacker can cheaply re-fill the slot, making the DoS persistent — analogous to the "frequently repeatable" hang in the CVE.

### Likelihood Explanation
- Fully unprivileged: only public `DepositToken.deposit` calls with the victim as `onBehalfOf_`; no privileged role, no oracle manipulation, no governance action required.
- Feasibility depends on the pool having enough distinct deposit tokens that combined slots can reach 30; on mature deployments (Base/Mainnet with many Vesper/underlying collaterals) this is satisfiable, and victims already holding several tokens need fewer attacker deposits.
- Not blocked by guards: `deposit` is `whenNotPaused`/`nonReentrant` only; `addToDepositTokensOfAccount` has no minimum amount or opt-in check.

### Recommendation
- Revert/ignore-without-add when `amount_` minted is below a dust threshold, or make `addToDepositTokensOfAccount` not revert for the *recipient* path (e.g., skip list addition on incoming transfers and instead enumerate via `balanceOf`), or
- Allow removal-style behavior: let `transfer`/`seize` succeed by not gating the *recipient* add, or
- Introduce a per-account opt-in (`addToDepositTokensOfAccount` only callable for `_msgSender`-initiated positions), or raise/soften `MAX_TOKENS_PER_USER` so dust-filling is economically prohibitive.
