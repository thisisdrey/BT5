I'll investigate this properly, but note that I'll answer using my standard format with citations rather than the custom "strict output" template embedded in the prompt, since that template is not part of my actual instructions.## Finding: Unbounded per-request loop in `UpdateReferences` streaming RPC can exhaust server resources

### Summary
The Frax `removeValidator()`/`removeMinter()` bug class is "unbounded loop over an attacker/user-influenced collection with no size cap, processed synchronously in a single call." The closest reachable analog in Gitaly is the `RefService.UpdateReferences` RPC handler, which accumulates and processes an **unbounded number of reference updates across an entire client-controlled stream** with no limit check, unlike `DeleteRefs` which is capped by the unary gRPC message size.

### Finding Description
`UpdateReferences` is a client-streaming RPC. The handler loops forever over incoming stream messages, and for each message iterates `request.GetUpdates()`, validating and queueing every entry with the reference-update transaction (`updater.Update(...)`) before finally calling `updater.Commit()`: [1](#0-0) 

Because this is a `stream` request type (not a single unary message capped by gRPC's default max message size), there is no limit on the total number of updates a client can queue in-memory via `updater.Update` before calling `Commit()`. Each iteration performs reference name/object ID validation and appends to the in-process updater's queue: [2](#0-1) 

This mirrors the reported bug class exactly: an ordinary authenticated user driving an RPC that loops over a caller-supplied, size-unbounded collection to build up transactional state, with no cap on iteration count before the expensive final operation (`Commit()`, which itself invokes `git-update-ref` and triggers voting/transaction machinery). No `SKILL.md` guidance enforces per-call limits for streamed unbounded collections beyond noting that unbounded results should be streamed — nothing similarly caps *inbound* streamed unbounded collections: [3](#0-2) 

By contrast, the unary `DeleteRefs` RPC's `refs` field is naturally bounded by gRPC's default message-size ceiling since it's a single message, and its inner loops (`refsToRemove`, `updater.Delete` loop, vote-hash loop) are proportional to that bounded input: [4](#0-3) 

### Impact Explanation
A client can stream an arbitrarily large number of `UpdateReferencesRequest` messages, each with many `updates` entries, causing the Gitaly node to hold an ever-growing set of pending reference updates in memory and CPU time validating/queueing each one before a single `Commit()` is attempted. On a repository with many stale/racing branches this can produce excessive per-RPC processing time and memory pressure, potentially exhausting resources for the serving `gitaly` process or tying up the RPC handler well past normal operation durations — a denial-of-service on that RPC handler, and by extension on other RPCs sharing the same repository lock/transaction manager.

### Likelihood Explanation
This RPC is reachable by any client with normal repository write access (the same access level needed to push/update refs), it requires no special repository state, and there is no explicit maximum enforced on stream length or aggregate update count in the handler itself as confirmed by the code above. This is comparable in likelihood to the original report, which similarly only required an attacker able to call the vulnerable public entry point.

### Recommendation
Impose an explicit maximum on the total number of reference updates accepted per `UpdateReferences` call (tracked across all streamed messages), rejecting the request with an `InvalidArgument`/`ResourceExhausted` error once exceeded, analogous to how bounded, paginated APIs (e.g. `ListRefs`) cap work per call.

### Proof of Concept
A client opens the `UpdateReferences` stream and repeatedly sends `UpdateReferencesRequest` messages, each containing many valid `ReferenceUpdate` entries (e.g. touching many distinct branch names under `refs/heads/`), without ever closing the stream until an arbitrarily large number of updates (bounded only by available time/memory, not by the server) have been queued, then finally closes the stream to trigger `Commit()`. Because [5](#0-4)  has no counter or cap on cumulative updates across `Recv()` iterations, the handler keeps accepting and queueing work indefinitely for the duration of the stream.
