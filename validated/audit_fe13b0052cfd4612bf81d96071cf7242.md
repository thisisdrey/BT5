### Title
Denial of Service via Unbounded Array Allocation in `PrecompiledContracts.extractBytesArray()` / `extractBytes32Array()` - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The `ValidateMultiSign` and `BatchValidateSign` TVM precompiled contracts read an attacker-controlled "array length" word directly from calldata and use it to allocate a Java array (`new byte[len][]`) before any signature-count bound is enforced, when the `allowTvmSelfdestructRestriction` (TIP-854) hard-fork flag is off. This mirrors the Nmap bug class: an untrusted length field drives unbounded object allocation, causing an `OutOfMemoryError` that is not contained by the surrounding logic.

### Finding Description
`PrecompiledContracts.extractBytesArray()` and `extractBytes32Array()` read the array length straight from a `DataWord` derived from raw calldata and immediately allocate a Java array of that size: [1](#0-0) 

In `ValidateMultiSign.execute()`, the `sigArraySize`/`MAX_SIZE` bound check is only performed when `VMConfig.allowTvmSelfdestructRestriction()` is true; when it is false, `extractBytesArray()` is invoked directly on the unbounded `len`: [2](#0-1) 

The same pattern repeats in `BatchValidateSign.doExecute()`, where the `sigArraySize`/`addrArraySize` bound check is likewise gated behind the same flag before `extractBytesArray`/`extractBytes32Array` are called: [3](#0-2) 

`len` comes from `words[offset].intValueSafe()` where `offset` is itself attacker-supplied (`words[3].intValueSafe() / WORD_SIZE`), so a crafted calldata word can set `len` to any value up to `Integer.MAX_VALUE`. `new byte[len][]` for such a value attempts to allocate roughly 16GB of reference slots on a 64-bit JVM before a single loop iteration executes, immediately throwing `OutOfMemoryError`.

This call happens outside of the `try { ... } catch (Throwable t) { ... }` block that wraps the rest of `ValidateMultiSign.execute()`/`doExecute()`, so the `OutOfMemoryError` propagates unguarded out of the precompile.

### Impact Explanation
`OutOfMemoryError` is an `Error`, not an `Exception`. In `VMActuator.execute()`, the outer dispatch loop only catches `Throwable` at the top level of transaction execution (`catch (Throwable e)`), which will catch it for a *single* transaction, but by the time this executes, the JVM heap may already be under severe memory pressure/fragmentation from the failed huge-array allocation attempt, and other concurrently executing threads (block validation, other transactions, RPC handling) can also throw `OutOfMemoryError` non-deterministically, since the JVM heap is shared process-wide. Depending on GC behavior and heap headroom, this can degrade or crash the FullNode/witness process — a node crash/halt is explicitly an accepted impact category for this class of finding. Because `ValidateMultiSign`/`BatchValidateSign` are reachable from any TVM contract call (an unprivileged smart-contract call to the fixed precompile address), any transaction broadcaster or contract can trigger this path.

### Likelihood Explanation
The vulnerable path is only reachable while `VMConfig.allowTvmSelfdestructRestriction()` (the TIP-854 hard-fork flag) is disabled. On networks/environments where this proposal has not yet been activated (e.g., private/test networks, or a mainnet window before the corresponding hard fork block), the guard is completely absent and any account can call the precompile with crafted calldata to trigger the huge allocation with a single, cheap transaction. On networks where the flag is already active, this specific path is not reachable because the bound check runs before the unguarded call. This makes exploitability config/height-dependent rather than universal on all java-tron deployments.

### Recommendation
Enforce the `MAX_SIZE` bound check on the decoded array length unconditionally, before calling `extractBytesArray`/`extractBytes32Array`/`extractSigArray`, regardless of the `allowTvmSelfdestructRestriction` flag state. Additionally, add defensive length validation inside `extractBytesArray()` and `extractBytes32Array()` themselves (reject `len < 0` or `len` greater than a small sane bound, e.g. `MAX_SIZE`) so the fix does not depend on call-site ordering, and wrap the array-extraction calls in the same `catch (Throwable t)` block that already guards the rest of `ValidateMultiSign`/`BatchValidateSign` execution.

### Proof of Concept
1. Deploy or use any contract, or craft a raw `TriggerSmartContract` transaction that performs a `STATICCALL`/`CALL` to the `ValidateMultiSign` precompile address (`0x...0a` fixed address family) with calldata shaped as:
   - word0: arbitrary 21-byte address
   - word1: permissionId
   - word2: 32-byte data hash
   - word3: offset pointing to a word whose value is `Integer.MAX_VALUE` (or another very large value) used as the "signatures array length"
2. Ensure the target chain/test network has `allowTvmSelfdestructRestriction` (TIP-854) not yet activated (flag off), so the `sigArraySize > MAX_SIZE` guard in [4](#0-3)  is skipped and `extractBytesArray` is called directly with the attacker-controlled `len`.
3. Broadcast the transaction; `extractBytesArray()` executes `new byte[len][]` with `len ≈ Integer.MAX_VALUE`, immediately throwing `OutOfMemoryError` during precompile execution: [5](#0-4) .
4. Observe repeated `OutOfMemoryError`s across the node process as multiple such transactions are broadcast concurrently, degrading or crashing node availability.

Note: I was unable to fully verify from the indexed code the exact current mainnet activation status of `allowTvmSelfdestructRestriction` (TIP-854) or whether all deployed java-tron networks already have it permanently enabled; this affects real-world exploitability and would need confirmation via a full checkout/chain-parameter inspection (which a Devin session with repository access could verify).

  private static byte[][] extractBytes32Array(DataWord[] words, int offset) {
    int len = words[offset].intValueSafe();
    byte[][] bytes32Array = new byte[len][];
    for (int i = 0; i < len; i++) {
      bytes32Array[i] = words[offset + i + 1].getData();
    }
    return bytes32Array;
  }

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
