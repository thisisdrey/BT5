Audit Report

## Title
Unbacked XCM asset credit and permanent fund lock from ERC20 transfers with non-standard token semantics (fee-on-transfer/rebasing) - (File: cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs)

## Summary
`ERC20Transactor::withdraw_asset_with_surplus` credits an XCM `AssetsInHolding` register with the requested transfer `amount` based solely on the boolean return value of the ERC20 `transfer()` call, never verifying the actual balance delta received by the `TransfersCheckingAccount`. [6](#0-5)  For any ERC20 contract whose real transfer semantics diverge from the requested amount (fee-on-transfer, deflationary, or rebasing tokens), this creates an unbacked mint in the XCM system and can later cause an honest holder's redemption to permanently fail.

## Finding Description
`withdraw_asset_with_surplus` calls `IERC20::transferCall` on the asset contract to move `amount` tokens into the `TransfersCheckingAccount`, then inspects only the ABI-decoded boolean return value (`is_success`) — it never reads `balanceOf(checking_address)` before/after the call. [7](#0-6)  If `is_success` is true, the code unconditionally constructs `AssetsInHolding::new_from_fungible_credit` with `Erc20Credit(amount)`, assuming exactly `amount` tokens landed in the checking account. [8](#0-7)  The `Erc20Credit` type is explicitly documented as not enforcing runtime-level balance constraints, deferring entirely to the ERC20 contract's own bookkeeping. [3](#0-2) 

The asset matcher wired for this transactor (`ERC20Matcher`) matches any local `AccountKey20`-addressed contract with no restriction to standard, non-rebasing, non-fee-on-transfer tokens. [1](#0-0)  Thus any ERC20 contract deployable via `pallet-revive` that reports `true` on `transfer()` while delivering less than `amount` (fee-on-transfer) can be registered and processed by this transactor.

On redemption, `deposit_asset_with_surplus` transfers `amount` from the checking account to the beneficiary, and if the checking account's real balance is insufficient (due to accumulated fee/rebase shortfall from prior withdrawals), the ERC20 `transfer()` returns `false` or reverts, and the code returns the asset to holding with `XcmError::FailedToTransactAsset`, with no reconciliation or recovery path. [4](#0-3)  This decoupling of internal `Erc20Credit` bookkeeping from the checking account's true balance is permanent once created.

## Impact Explanation
This breaks conservation of value for any ERC20 asset registered with this transactor whose transfer semantics diverge from the requested amount. It results in (1) an unbacked increase in XCM-tracked asset supply relative to what the checking account actually holds, matching the "unbacked mint" impact category, and (2) a subsequent honest holder's redemption attempt can permanently fail once the checking account is short, matching the "permanent user-fund lock" impact category, since there is no reconciliation mechanism anywhere in this file.

## Likelihood Explanation
Exploitability depends on whether the runtime's asset matcher/filter permits non-standard (fee-on-transfer or rebasing) ERC20 contracts to be matched. Given the actual matcher wired in this codebase (`ERC20Matcher`/`IsLocalAccountKey20`), there is no allow-list restricting to vetted standard tokens — matching is purely structural (local `AccountKey20` junction), so any unprivileged user who deploys or is otherwise permitted to use such a contract via `pallet-revive` can trigger this path through a normal XCM message, with no privileged, governance, or relayer assumption required. [5](#0-4) 

## Recommendation
Verify actual balance delta rather than trusting the boolean return value: read `balanceOf(checking_address)` (and beneficiary address for deposits) before and after the `transfer` call, and credit/debit `AssetsInHolding` with the observed delta instead of the requested `amount`. Alternatively, restrict this transactor's asset matcher to a documented allow-list of vetted, standard, non-rebasing, non-fee-on-transfer ERC20 contracts, and add a defensive check that fails the whole operation if the observed delta does not equal the requested amount.

## Proof of Concept
1. Deploy a fee-on-transfer ERC20 contract `T` (via `pallet-revive`) where `transfer(to, amount)` delivers `amount - fee` to `to` but returns `true`.
2. A user initiates an XCM operation causing `withdraw_asset_with_surplus` to call `T.transfer(checking_account, 1000)`; the checking account actually receives `950` (5% fee) but `Erc20Credit(1000)` is minted into XCM holding. [8](#0-7) 
3. The XCM message completes, crediting 1000 units of `T` elsewhere in the system, backed by only 950 real tokens at the checking account.
4. A different, previously-credited holder attempts `deposit_asset_with_surplus` to redeem an equivalent amount; because the checking account is short by the accumulated fee shortfall, `T.transfer` fails, and the holder's asset is returned to holding with `FailedToTransactAsset`, reproducing the fund-lock scenario. [9](#0-8)
