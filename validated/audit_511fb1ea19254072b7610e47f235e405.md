### Title
`relayManager.handleCreateRelayRequest()` Trusts Attacker-Supplied `RelayFromAddr` Identity Without Verifying It Matches the Authenticated Sender - (File: `relay_manager.go`)

### Summary
`handleCreateRelayRequest()` and `handleCreateRelayResponse()` treat the `RelayFromAddr` (and legacy `OldRelayFromAddr`) field of an inbound `NebulaControl` message as the true VPN identity of the party requesting the relay, but never check that this attacker-controlled field actually matches `h.vpnAddrs` — the VPN address(es) bound to the sender's own certificate on the already-authenticated tunnel `h`. This mirrors the FSDVesting root cause: a caller-supplied identity parameter (`_user` in FSD, `RelayFromAddr` here) is accepted as-is instead of being cross-checked against the verified identity of the actual caller.

### Finding Description
`HandleControlMsg` is only reachable after the outer Noise tunnel has been decrypted for hostinfo `h` [1](#0-0) , so `h` is a legitimately authenticated peer. The message it carries, however, is fully attacker-controlled protobuf content, and its `RelayFromAddr`/`RelayToAddr` fields are only checked for nil-ness before being trusted [2](#0-1) .

In `handleCreateRelayRequest`, `from` is taken directly from `m.RelayFromAddr` and used, unchecked against `h.vpnAddrs`, to:
- Discard the request only if `from` happens to fall in *my own* VPN table (self-relay guard) [3](#0-2) 
- Install relay state and respond as if `from` were the genuine identity of `h`, when `target` is me [4](#0-3) 
- Or install a `ForwardingType` relay to `target` keyed on the spoofed `from` address when I am acting as a relay node (`am_relay`) [5](#0-4) 

Nowhere is `from` verified to be one of `h.vpnAddrs` (the addresses actually certified for `h` per its verified certificate, populated during the handshake in `validatePeerCert`/`continueHandshake` [6](#0-5) ). `AddRelay` then unconditionally binds the caller-chosen `from`/`vpnIp` value as `Relay.PeerAddr` on the hostinfo, with no cross-check against the certificate-derived identity [7](#0-6) .

By contrast, the codebase does enforce this kind of caller-identity binding elsewhere — e.g. `lighthouse.go`'s `handleHostUpdateNotification` explicitly checks `slices.Contains(fromVpnAddrs, detailsVpnAddr)` before trusting a self-reported VPN address [8](#0-7) , and the firewall's remote-address check binds `fp.RemoteAddr` to the peer certificate's networks [9](#0-8) . The relay-control-message path lacks the analogous check that `from` (and, on the `handleCreateRelayResponse` side, `relayFrom`/`relayTo`) is actually owned by the authenticated sender `h`.

### Impact Explanation
An authenticated-but-malicious Nebula node can send a `CreateRelayRequest`/`CreateRelayResponse` claiming an arbitrary victim's VPN address as `RelayFromAddr`. Because this value is stored as `Relay.PeerAddr` and used as the routing key in `hm.Relays`/`relayState` (consumed later by `QueryVpnAddrsRelayFor` and `handleOutsideRelayPacket`'s `ForwardingType` path [10](#0-9) ), this lets an attacker poison relay routing state for a peer it does not own, install itself as a claimed relay endpoint for another host's address, or desynchronize relay state (`Established`/`Disestablished`/`Requested` transitions keyed on the spoofed address [11](#0-10) ). This is a remote state-poisoning vector reachable by any peer that can complete a handshake (no valid CA-signed cert required for the attack surface beyond having *some* Nebula peer identity), directly analogous to "anyone can spoof `_user`" in the original report.

I could not fully verify, within the available tooling, whether this routing-state poisoning can be escalated all the way to traffic decryption/injection for the victim's real payload, since the inner (true) end-to-end Noise session identity check on decrypted `Message` packets appears to happen independently via `QueryIndex`/`ConnectionState.Decrypt` on the recursive `readOutsidePackets` call [12](#0-11) . This limits certainty about full traffic-decryption impact and should be validated further; the confirmed impact is unauthenticated relay-state corruption/hijacking for an address the attacker does not control.

### Likelihood Explanation
Any node holding a valid certificate for the Nebula mesh (which, per the threat model here, does not require possessing a victim's identity — just *some* signed cert) can trigger this after a normal handshake, by simply crafting a `NebulaControl` message with an arbitrary `RelayFromAddr`. No additional privilege, race condition, or victim cooperation is required, making this a low-complexity, high-likelihood-of-reachability issue for any peer permitted to handshake into the mesh.

### Recommendation
In `HandleControlMsg`/`handleCreateRelayRequest`/`handleCreateRelayResponse`, validate that `RelayFromAddr` (or `OldRelayFromAddr`) is contained in the sending hostinfo's own certificate-derived `h.vpnAddrs` before using it as the relay identity, mirroring the check already done in `lighthouse.go`'s `handleHostUpdateNotification` (`slices.Contains(fromVpnAddrs, detailsVpnAddr)`). Reject and drop (with a debug log) any Create Relay Request/Response where the claimed `from` address is not one of the authenticated sender's own certificate networks.

### Proof of Concept
1. Node `A` (attacker) and node `T` (target) complete a normal, cert-valid handshake; `T` now holds hostinfo `h` for `A` with `h.vpnAddrs = [A_addr]`.
2. `A` sends a `Control`/`NebulaControl_CreateRelayRequest` message over the authenticated tunnel to `T`, setting `RelayFromAddr = Victim_addr` (a real, uninvolved peer's VPN address) and `RelayToAddr = T_addr`.
3. `T.relayManager.HandleControlMsg` → `handleCreateRelayRequest` only checks `RelayFromAddr`/`RelayToAddr` are non-nil [2](#0-1) , then, since `target == T`, calls `AddRelay(rm.l, h, f.hostMap, from, &m.InitiatorRelayIndex, TerminalType, Established)` [13](#0-12) , binding `h` (i.e., attacker `A`) to `Relay.PeerAddr = Victim_addr` without ever checking that `Victim_addr ∈ h.vpnAddrs`.
4. `T` now has relay/routing state asserting that `A` is a valid relay endpoint for `Victim`'s address, entirely under `A`'s control and without `Victim`'s participation or a certificate proving `A` owns that address.

	hm.Lock()
	defer hm.Unlock()

		index, err := generateIndex(l)
		if err != nil {
			return 0, err
		}

		_, inRelays := hm.Relays[index]
		if !inRelays {
			// Avoid standing up a relay that can't be used since only the primary hostinfo

			if !hm.unlockedMakePrimary(relayHostInfo) {

				// never be reclaimed since the delete-time cleanup has already run.
				return 0, errors.New("relay hostinfo is no longer in the hostmap")
			}

			hm.Relays[index] = relayHostInfo
			newRelay := Relay{
				Type:       relayType,
				State:      state,
				LocalIndex: index,
				PeerAddr:   vpnIp,
			}

			if remoteIdx != nil {
				newRelay.RemoteIndex = *remoteIdx
			}
			relayHostInfo.relayState.InsertRelay(vpnIp, index, &newRelay)

			return index, nil
		}
	}

	return 0, errors.New("failed to generate unique localIndexId")

// validatePeerCert checks the peer certificate for self-connection and remote allow list.
// Returns the VPN addrs, whether any of them fall within one of our own VPN
// networks, and true if valid; false if rejected.
func (hm *HandshakeManager) validatePeerCert(via ViaSender, remoteCert *cert.CachedCertificate) ([]netip.Addr, bool, bool) {
	f := hm.f
	vpnNetworks := remoteCert.Certificate.Networks()

	// The cert package rejects host certs with no networks at parse time, so
	// reaching this state would mean an invariant was bypassed elsewhere.
	// Refuse explicitly so downstream code (which indexes vpnAddrs[0]) can't
	// panic if that invariant ever changes.
	if len(vpnNetworks) == 0 {
		f.l.Info("No networks in certificate",
			"from", via, "cert", remoteCert)
		return nil, false, false
	}

	vpnAddrs := make([]netip.Addr, len(vpnNetworks))
	anyVpnAddrsInCommon := false

	for i, network := range vpnNetworks {
		if f.myVpnAddrsTable.Contains(network.Addr()) {
			f.l.Error("Refusing to handshake with myself",
				"vpnNetworks", vpnNetworks,
				"from", via,
				"certName", remoteCert.Certificate.Name(),
				"certVersion", remoteCert.Certificate.Version(),
				"fingerprint", remoteCert.Fingerprint,
				"issuer", remoteCert.Certificate.Issuer(),
			)
			return nil, false, false
		}
		vpnAddrs[i] = network.Addr()
		if f.myVpnNetworksTable.Contains(network.Addr()) {
			anyVpnAddrsInCommon = true
		}
	}

	if !via.IsRelayed {
		if !f.lightHouse.GetRemoteAllowList().AllowAll(vpnAddrs, via.UdpAddr.Addr()) {
			f.l.Debug("lighthouse.remote_allow_list denied incoming handshake",
				"vpnAddrs", vpnAddrs, "from", via)
			return nil, false, false
		}
	}

	return vpnAddrs, anyVpnAddrsInCommon, true
}
