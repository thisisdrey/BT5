### Title
Missing staleness check on `PricingParameters.exchange_rate` allows underpriced relayer fees and stalled Ethereum message delivery - (File: `bridges/snowbridge/pallets/outbound-queue/src/lib.rs`)

### Summary
The Snowbridge outbound queue computes the fee a user pays for bridging a message to Ethereum, and the relayer reward embedded in that message, from a single governance-set `PricingParameters` value (containing the ETH/DOT `exchange_rate`, `fee_per_gas`, and `rewards`). This value is not automatically refreshed on-chain and carries no timestamp or freshness check — exactly the "stale price used for settlement" pattern described in the external report, just replacing an AMM pool oracle with the bridge's pricing oracle.

### Finding Description
`PricingParameters` is a plain `StorageValue` set only via the privileged `set_pricing_parameters` extrinsic, with module docs explicitly stating governance must "manually update these parameters every few weeks" [1](#0-0) . There is no stored "last updated" timestamp and no check anywhere that rejects fee computation or message submission if the parameters are stale.

Every user-facing message submission calls `Pallet::<T>::validate`, which fetches `T::PricingParameters::get()` at send time and derives the fee purely from that potentially stale value: [2](#0-1) 

`calculate_fee` divides the remote (Ethereum) cost by `params.exchange_rate` to get the local (DOT) fee charged to the user, with no bound on how old `params` is: [3](#0-2) 

Separately, `do_process_message` (executed later by the `MessageQueue` pallet when the message is actually committed) re-reads the *current* `PricingParameters` to set the on-chain `max_fee_per_gas` and `reward` fields that will be paid out to the relayer on Ethereum: [4](#0-3) 

Because the exchange rate/fee-per-gas is a manually curated, infrequently updated global parameter (not backed by any recency guard, unlike e.g. the `pallet-honzon-oracle`'s `TimestampedValue` freshness design used elsewhere in this repo [5](#0-4) ), if the ETH/DOT rate or Ethereum gas price moves significantly between governance updates, both the fee charged to users and the reward promised to relayers are computed from an outdated ratio. There is no guard comparable to `min_amount_out`/`min_shares_out` from the original report, nor any staleness rejection, to protect either side.

### Impact Explanation
If `exchange_rate`/`fee_per_gas` become stale and ETH costs (denominated in DOT) rise, the `reward` and `max_fee_per_gas` values baked into the committed message on Ethereum become insufficient to cover the relayer's actual gas cost plus a viable profit margin. Relayers have no economic incentive to submit messages to the Ethereum Gateway, so messages queue up and outbound bridge processing stalls — this is public underpriced work degrading bridge processing, matching the in-scope impact category. Conversely, if the rate moves the other way, users are systematically overcharged relative to the real cost. Neither users nor the protocol have any way to detect or avoid using a stale rate since the pallet does not expose or check parameter freshness.

### Likelihood Explanation
This does not require a malicious actor, admin abuse, or governance misbehavior — it is a systemic design gap identical in nature to the acknowledged issue in the source report: an operationally-updated price feed used directly in fee/settlement math without a staleness check. Any period of market volatility exceeding governance's update cadence ("every few weeks" per the pallet's own documentation) triggers the condition, making it a realistic and recurring risk under normal operation rather than a contrived edge case.

### Recommendation
Store a last-updated block number/timestamp alongside `PricingParameters` when `set_pricing_parameters` is called. In `calculate_fee` (and in `do_process_message` when embedding `max_fee_per_gas`/`reward`), reject or defensively bound message submission/commit if the stored parameters exceed a configured maximum age, or incorporate an automatic decay/multiplier that widens safety margins as staleness increases, mirroring the recommendation from the original report (reject operations when prices have not been refreshed within a reasonable timeframe).

### Proof of Concept
1. Governance calls `set_pricing_parameters` once, setting `exchange_rate = 1/400` (ETH/DOT) as seen in the Rococo/Westend bridge configs [6](#0-5) .
2. Weeks pass without a governance update while the real ETH/DOT market rate moves substantially (e.g., ETH appreciates 3x against DOT), consistent with the module doc's stated multi-week update cadence [1](#0-0) .
3. Any unprivileged user submits a message to Ethereum via the normal bridging flow; `validate` computes `fee` from the stale `exchange_rate` [2](#0-1) , and later `do_process_message` embeds the same stale `reward`/`max_fee_per_gas` in the committed message [4](#0-3) .
4. Relayers observe that `Min(GasPrice, Message.MaxFeePerGas) * GasUsed() + Message.Reward` no longer covers real Ethereum gas costs and stop relaying, stalling outbound bridge processing — with no on-chain mechanism having flagged the parameters as stale before this occurred.

		pub(crate) fn calculate_fee(
			gas_used_at_most: u64,
			params: PricingParameters<T::Balance>,
		) -> Fee<T::Balance> {
			// Remote fee in ether
			let fee = Self::calculate_remote_fee(
				gas_used_at_most,
				params.fee_per_gas,
				params.rewards.remote,
			);

			// downcast to u128
			let fee: u128 = fee.try_into().defensive_unwrap_or(u128::MAX);

			// multiply by multiplier and convert to local currency
			let fee = FixedU128::from_inner(fee)
				.saturating_mul(params.multiplier)
				.checked_div(&params.exchange_rate)
				.expect("exchange rate is not zero; qed")
				.into_inner();

			// adjust fixed point to match local currency
			let fee = Self::convert_from_ether_decimals(fee);

			Fee::from((Self::calculate_local_fee(), fee))
		}
