## Analysis

The Velodrome bug's core broken invariant: **the on-chain "rate of reward accrual" is decoupled from the actual reward-token balance backing it**, so paper-accrued rewards (`reward_per_token_stored`) can exceed the real balance held for payout, causing later claimants' withdrawals to revert due to insufficient balance ("first claimer drains, late claimer reverts").

This same invariant is broken in `pallet-asset-rewards` (`substrate/frame/asset-rewards`). `reward_rate_per_block` is a value stored purely in `PoolInfo` and multiplied by elapsed blocks to compute `reward_per_token_stored` — with **no linkage whatsoever to the actual reward-asset balance held in the pool's account**. [1](#0-0) 

`create_pool` lets the caller set an arbitrary `reward_rate_per_block` and `expiry_block` with zero validation against any deposited reward-token balance: [2](#0-1) 

`deposit_reward_tokens` is merely a convenience call and is never required or tied to the rate — the pool can accrue rewards on paper indefinitely while holding zero tokens: [3](#0-2) 

`harvest_rewards` performs a real `T::Assets::transfer` of the accrued `staker_info.rewards` from the pool account to the staker, with no check that the pool's balance actually covers the sum of all stakers' accrued (but unpaid) claims: [4](#0-3) 

`set_pool_reward_rate_per_block` similarly only guards that the rate is monotonically increasing — it performs no check against the pool's current balance divided by remaining blocks-to-expiry, unlike even Velodrome's own (buggy) implementation which at least divided by `DURATION`: [5](#0-4) 

### Title
Reward accrual (`reward_per_token_stored`) is unbacked by pool balance, allowing race-to-claim insolvency in `pallet-asset-rewards` - (File: `substrate/frame/asset-rewards/src/lib.rs`)

### Summary
`pallet-asset-rewards` computes `reward_per_token_stored` purely from `reward_rate_per_block * elapsed_blocks / total_tokens_staked`, with no requirement that the pool's actual reward-asset balance can cover the total rewards implied by that rate over the pool's lifetime. This mirrors the Velodrome `Gauge.sol#notifyRewardAmount()` bug class: paper-accrued reward obligations can exceed real backing funds, so whichever staker calls `harvest_rewards` first drains the available balance, and later claimants' `harvest_rewards` calls revert on `T::Assets::transfer` due to insufficient balance, causing loss (temporary or permanent) of earned yield.

### Finding Description
`reward_per_token()` accrues rewards strictly as a function of `reward_rate_per_block`, elapsed blocks, and `total_tokens_staked` — never checking the reward pool account's real token balance: [6](#0-5) 

Nothing in `create_pool` or `set_pool_reward_rate_per_block` ties `reward_rate_per_block` to `expiry_block` and the pool's current/expected balance. `create_pool` doesn't even require a reward deposit to be made at all: [2](#0-1) 

An admin can therefore create a pool promising a reward rate that, integrated to `expiry_block`, is far larger than any funds ever deposited via `deposit_reward_tokens` (an optional, unenforced convenience call): [7](#0-6) 

Multiple unprivileged stakers accrue proportional shares of `reward_per_token_stored` as they stake/unstake, exactly as in the integration test that walks through staker1/staker2 accrual: [8](#0-7) 

When `harvest_rewards` executes, it directly transfers `staker_info.rewards` out of the pool's pot account without checking that this leaves enough balance to satisfy other stakers' already-accrued, unclaimed `rewards`: [4](#0-3) 

Because the accrual formula is decoupled from real balance, and there is no reservation/escrow mechanism nor a check like Velodrome's own recommended fix (`rewardRate <= balance / timeUntilNextPeriodFinish`), the system allows `reward_per_token_stored` to represent more value than exists in `pool_info.account`.

### Impact Explanation
This directly violates the required invariant that "Balances, assets, ... reward payouts ... must conserve value and settle exactly once to the rightful beneficiary and amount." Whichever unprivileged staker calls `harvest_rewards` first can withdraw the full available pool balance for their accrued share; subsequent stakers with a legitimate, correctly-computed accrued balance will have their `harvest_rewards` calls revert (insufficient balance in `T::Assets::transfer`), resulting in a loss (potentially permanent, if the pool is never topped up and later `cleanup_pool` sweeps remaining dust to the admin) of earned rewards for late claimants — the same "temporary or permanent loss of yield" outcome judged Medium severity in the original Velodrome report.

### Likelihood Explanation
No privileged or malicious actor is required beyond an ordinary pool admin creating a pool (a normal, permissionless-for-non-privileged-participants configuration operation under `T::CreatePoolOrigin`, which in many runtime configs is a signed/permissioned but non-governance account) with a reward rate not fully funded up front, and normal unprivileged stakers racing to call `harvest_rewards`. No proof forgery, no relayer, no validator collusion is needed — only ordinary use of the pallet's public extrinsics (`stake`, `harvest_rewards`, `unstake`) in the documented and tested pattern.

### Recommendation
Enforce that `reward_rate_per_block * (expiry_block - last_update_block)` (or the cumulative future obligation) never exceeds the reward pool's actual `T::Assets` balance at `create_pool`, `deposit_reward_tokens` is required (not merely "convenience") before/at rate-setting time, and `set_pool_reward_rate_per_block` / `set_pool_expiry_block` re-validate this invariant, mirroring Velodrome's fix: `require(rewardRate <= balance / timeUntilNextPeriodFinish)`. Alternatively, make `harvest_rewards` cap payout to the actual reducible balance and track a shortfall/debt so no committed reward is silently lost or unfairly allocated to whoever claims first.

### Proof of Concept
1. Admin calls `create_pool` with `reward_rate_per_block = R`, `expiry_block = now + N`, without ever calling `deposit_reward_tokens` (or depositing far less than `R*N`). See `create_pool`: [9](#0-8) 
2. Staker A and Staker B each `stake` equal amounts at block `now`.
3. Blocks advance to `now + N/2`. `reward_per_token()` accrues `R*(N/2)` worth of rewards split between A and B, per [10](#0-9) , regardless of whether the pool account actually holds that many reward-asset tokens.
4. Staker A calls `harvest_rewards` first and successfully drains the pool's entire available reward-asset balance via `T::Assets::transfer` ( [11](#0-10) ).
5. Staker B calls `harvest_rewards` for their equally-accrued share; the `T::Assets::transfer` call fails with insufficient balance, and B's rewards remain unclaimed/lost.

		/// Derives the current reward per token for this pool.
		pub(super) fn reward_per_token(
			pool_info: &PoolInfoFor<T>,
		) -> Result<T::Balance, DispatchError> {
			if pool_info.total_tokens_staked.is_zero() {
				return Ok(pool_info.reward_per_token_stored);
			}

			let rewardable_blocks_elapsed: u32 =
				match Self::last_block_reward_applicable(pool_info.expiry_block)
					.ensure_sub(pool_info.last_update_block)?
					.try_into()
				{
					Ok(b) => b,
					Err(_) => return Err(Error::<T>::BlockNumberConversionError.into()),
				};

			Ok(pool_info.reward_per_token_stored.ensure_add(
				pool_info
					.reward_rate_per_block
					.ensure_mul(rewardable_blocks_elapsed.into())?
					.ensure_mul(PRECISION_SCALING_FACTOR.into())?
					.ensure_div(pool_info.total_tokens_staked)?,
			)?)
		}

	fn create_pool(
		creator: &T::AccountId,
		staked_asset_id: T::AssetId,
		reward_asset_id: T::AssetId,
		reward_rate_per_block: T::Balance,
		expiry: DispatchTime<BlockNumberFor<T>>,
		admin: &T::AccountId,
	) -> Result<PoolId, DispatchError> {
		// Ensure the assets exist.
		ensure!(T::Assets::asset_exists(staked_asset_id.clone()), Error::<T>::NonExistentAsset);
		ensure!(T::Assets::asset_exists(reward_asset_id.clone()), Error::<T>::NonExistentAsset);

		// Check the expiry block.
		let now = T::BlockNumberProvider::current_block_number();
		let expiry_block = expiry.evaluate(now);
		ensure!(expiry_block > now, Error::<T>::ExpiryBlockMustBeInTheFuture);

		let pool_id = NextPoolId::<T>::try_mutate(|id| -> Result<PoolId, DispatchError> {
			let current_id = *id;
			*id = id.ensure_add(1)?;
			Ok(current_id)
		})?;

		let footprint = Self::pool_creation_footprint();
		let cost = T::Consideration::new(creator, footprint)?;
		PoolCost::<T>::insert(pool_id, (creator.clone(), cost));

		// Create the pool.
		let pool = PoolInfoFor::<T> {
			staked_asset_id: staked_asset_id.clone(),
			reward_asset_id: reward_asset_id.clone(),
			reward_rate_per_block,
			total_tokens_staked: 0u32.into(),
			reward_per_token_stored: 0u32.into(),
			last_update_block: 0u32.into(),
			expiry_block,
			admin: admin.clone(),
			account: Self::pool_account_id(&pool_id),
		};

		// Insert it into storage.
		Pools::<T>::insert(pool_id, pool);

		// Emit created event.
		Self::deposit_event(Event::PoolCreated {
			creator: creator.clone(),
			pool_id,
			staked_asset_id,
			reward_asset_id,
			reward_rate_per_block,
			expiry_block,
			admin: admin.clone(),
		});

		Ok(pool_id)
	}

	fn set_pool_reward_rate_per_block(
		admin: &T::AccountId,
		pool_id: PoolId,
		new_reward_rate_per_block: T::Balance,
	) -> DispatchResult {
		let pool_info = Pools::<T>::get(pool_id).ok_or(Error::<T>::NonExistentPool)?;
		ensure!(pool_info.admin == *admin, BadOrigin);
		ensure!(
			new_reward_rate_per_block > pool_info.reward_rate_per_block,
			Error::<T>::RewardRateCut
		);

		// Always start by updating the pool rewards.
		let rewards_per_token = Self::reward_per_token(&pool_info)?;
		let mut pool_info = Self::update_pool_rewards(&pool_info, rewards_per_token)?;

		pool_info.reward_rate_per_block = new_reward_rate_per_block;
		Pools::<T>::insert(pool_id, pool_info);

		Self::deposit_event(Event::PoolRewardRateModified { pool_id, new_reward_rate_per_block });

		Ok(())
	}
