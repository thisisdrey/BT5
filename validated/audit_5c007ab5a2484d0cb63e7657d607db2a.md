### Title
Permanent freeze of ETH-implicit wallet contract funds via stuck `has_in_flight_tx` flag - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The `WalletContract` that backs every ETH-implicit account uses a boolean guard, `has_in_flight_tx`, to serialize execution of `rlp_execute` calls. This flag is set to `true` in the receipt that dispatches a cross-contract promise chain, and is only cleared inside the corresponding `#[private]` callback (`rlp_execute_callback`, `address_check_callback`, `nep_141_storage_balance_callback`, `ban_relayer`). If the callback receipt fails to execute far enough to reach its very first statement (`self.has_in_flight_tx = false;`) — e.g. because the fixed static gas reserved for the callback is exhausted by argument deserialization before user code even runs — the flag is never reset. Because `rlp_execute` unconditionally rejects any new call while `has_in_flight_tx == true`, and an ETH-implicit account has no other entry point (no full-access key can ever be added, and it cannot be deleted), the account becomes permanently unusable, freezing any funds it holds — the same "irreversible admin/external-state lock blocks user withdrawal" root cause as the reported `daiJoin.cage` issue.

### Finding Description
`WalletContract::rlp_execute` (`runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs:89-128`) is the sole entry point for interacting with an ETH-implicit account. It guards against concurrent execution: [1](#0-0) 

When a promise chain is successfully constructed, the flag is set `true` right before the receipt returns: [2](#0-1) 

The flag is only ever cleared as the *first statement* of one of the `#[private]` callbacks, e.g.: [3](#0-2) [4](#0-3) [5](#0-4) 

Each of these callbacks is scheduled with a small, fixed static-gas budget: [6](#0-5) 
and for the address-check / ERC20 paths that budget additionally has to cover forwarding the user-controlled `action` argument through the callback: [7](#0-6) [8](#0-7) 

A NEAR contract function invocation deserializes its call arguments (here, the Borsh/JSON-encoded `near_action::Action` and `caller_deposit`) as part of gas-metered execution *before* the method body's first statement runs. If the relayer/attacker submits an RLP transaction whose derived `Action` carries a large payload (e.g. a `FunctionCall` with sizeable `args`, within protocol limits), the deserialization cost charged against the callback's fixed static gas budget can exceed that budget. In that case the callback receipt fails entirely (an "Exceeded the prepaid gas" style failure) without ever executing `self.has_in_flight_tx = false;`. Because `has_in_flight_tx = true` was already committed by the prior (successful) receipt, this failure leaves the flag permanently stuck at `true`.

Documentation confirms there is no recovery path for an ETH-implicit account outside of the wallet contract's own methods: it cannot be deleted and no full-access key can ever be added to it. [9](#0-8) 

With `has_in_flight_tx` stuck `true`, every subsequent `rlp_execute` call — the only interface for moving funds out of the account — immediately short-circuits with the "transaction already in progress" error, for the lifetime of the account: [10](#0-9) 

This is the direct structural analog of the `daiJoin.cage` bug: an external/administrative-independent state transition (here, a gas-starved callback instead of an admin's `cage()` call) permanently trips a guard that the withdrawal path unconditionally checks, with no fallback or reset mechanism reachable by the account owner.

### Impact Explanation
Once the flag is stuck, the ETH-implicit account's entire balance is permanently frozen: the wallet contract can never again dispatch a `Transfer`, `FunctionCall`, or any other action on the owner's behalf, and the account cannot be deleted or have a full-access key added to bypass the wallet contract. This is a concrete, permanent freezing-of-funds condition for any ETH-implicit account that hits this state, reachable purely through the eth-implicit wallet contract's public `rlp_execute` interface (no privileged/operator action required).

### Likelihood Explanation
Triggering this requires a relayer (which need not be honest/trusted — the whole design assumes relayers can be faulty) to submit, or a user to sign, a transaction whose parsed `Action` is large enough that its cross-contract argument-passing/deserialization cost exceeds the fixed 5–15 Tgas static budgets reserved for the private callbacks. Because the size of `FunctionCall` args (and thus deserialization cost) is attacker/relayer-influenced while the callback gas constants are fixed compile-time constants, an adversarial or merely careless relayer can realistically construct such a payload without any special privileges, making this reachable from an ordinary, unprivileged transaction flow.

### Recommendation
- Make the callback gas budgets scale with the size of the forwarded `action`/`caller_deposit` payload rather than using fixed constants, and reject `rlp_execute` requests whose derived action would not leave sufficient callback gas.
- Consider clearing `has_in_flight_tx` via a mechanism that survives receipt-level gas failure (e.g., using `env::promise_return`/`env::promise_result` checks in a small pre-callback footprint, or resetting the flag proactively rather than only inside the deep callback body), or add a timeout/self-recovery path (e.g., an owner-signed emergency reset once no promise is genuinely pending) so a single failed receipt cannot permanently disable the account.

### Proof of Concept
1. Fund/create an ETH-implicit account and deploy/attach the wallet contract (as in `runtime/near-wallet-contract/implementation/wallet-contract/src/tests/sanity.rs`).
2. As the relayer, submit an RLP transaction targeting an unregistered eth-implicit address (routing through `address_check_callback`) or an unregistered NEP-141 receiver (routing through `nep_141_storage_balance_callback`), with an `Action::FunctionCall` whose `args` are crafted to be large enough that argument-deserialization gas for the callback exceeds `ADDRESS_CHECK_CALLBACK_GAS` / `NEP_141_STORAGE_BALANCE_CALLBACK_GAS` (`lib.rs:37-41`).
3. Observe the callback receipt fails with an "Exceeded the prepaid gas" style error before `self.has_in_flight_tx = false;` executes (`lib.rs:140`, `lib.rs:202`, `lib.rs:280`).
4. Submit any subsequent `rlp_execute` call (including a plain `Transfer` intended to withdraw funds) and observe it is always rejected with "transaction already in progress, please try again later" (`lib.rs:97-105`), permanently, since no other code path resets `has_in_flight_tx`.
