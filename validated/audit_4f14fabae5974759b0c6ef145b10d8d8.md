### Title
`PeerDB::update_peer` unconditionally overwrites the stored `public_key` for an existing `(network_id, addrbytes, port)` row with no continuity check against the previous key - ([File: stackslib/src/net/db.rs])

### Summary
`PeerDB::has_peer` and `PeerDB::try_insert_peer` key an existing frontier row only on `(network_id, addrbytes, port)`, never on the peer's public key or its hash. When `try_insert_peer` finds a matching row it unconditionally calls `PeerDB::update_peer`, which issues an `UPDATE frontier SET ... public_key = ?2 ... WHERE network_id=? AND addrbytes=? AND port=?` before ever comparing the incoming key to the key already stored at that slot. Any remote peer that can get a `Neighbor` with the victim's `(addrbytes, port)` persisted through this path (e.g. via a fresh outbound handshake to a reused/attacker-controlled address, chainable with the address-forging issue in the related handshake-address question) silently replaces the previously-authenticated public key with its own.

### Finding Description
The claimed equality that must hold is: *the public key that authenticated the existing `Neighbor` row at `(network_id, addrbytes, port)` == the public key authenticating the update applied by `update_peer`*. This equality is never checked.

- `PeerDB::has_peer` (`stackslib/src/net/db.rs:949-960`) queries `SELECT 1 FROM frontier WHERE network_id=?1 AND addrbytes=?2 AND port=?3` — it does not reference `public_key`. [1](#0-0) 
- `PeerDB::try_insert_peer` (`stackslib/src/net/db.rs:1452-1488`) uses `has_peer` to decide "present," and if present calls `PeerDB::update_peer(tx, neighbor)` unconditionally — with no comparison of `neighbor.public_key` to the existing row's key before updating. [2](#0-1) 
- `PeerDB::update_peer` (`stackslib/src/net/db.rs:1286-1334`) executes the `UPDATE ... SET public_key = ?2 ...` at lines 1311-1313 unconditionally. Only *after* the write does it fetch `old_peer_opt` and compare `old_peer.public_key` vs `neighbor.public_key` (lines 1315-1331) — and that comparison is used solely to decide whether to drop the peer's StackerDB replication state, not to reject the write. [3](#0-2) 

Reachability: `Neighbor::save_update` and `Neighbor::save` both funnel into `try_insert_peer`/`update_peer` [4](#0-3) . In `ConversationP2P::handle_handshake`, an inbound `Handshake` message is verified only via `validate_handshake` (self-consistency: the message is signed by the key it carries) and `update_from_handshake_data`, which learns a "new" key whenever the *per-connection* cached key is `None` — which is always true for a freshly-opened TCP connection, regardless of what is already stored in `PeerDB` for that address. [5](#0-4)  When this happens on an outbound connection, `handle_handshake` immediately persists the change via `Neighbor::load_and_update` + `neighbor.save_update(&tx, None)`, which calls `PeerDB::update_peer` for the `(network_id, addrbytes, port)` derived from the handshake data. [6](#0-5)  There is no check anywhere in this call chain that the new key is continuous with (or a legitimate re-key signed by) the previously stored key for that address/port; `validate_handshake`'s "already know / or signed by current key" rule is enforced against the ephemeral per-`ConversationP2P` cache, not the persistent `PeerDB` frontier row.

The `test_try_insert_peer` unit test in `db.rs` even documents that "same-address, different-slot-taken" produces a rejection only because *all* fixed slots are already occupied by copies of the *same* neighbor being tested — it never exercises the case of a *present* row (matched by `has_peer`) with a *different* public key, which is exactly the vulnerable branch (`present == true` in `try_insert_peer`). [7](#0-6) 

### Impact Explanation
An attacker who obtains a fresh TCP connection to a victim node and can cause the node's outbound handshake logic to treat the attacker's address as belonging to a previously-known `(network_id, addrbytes, port)` frontier entry (e.g. via NAT/IP reassignment or the related forged-`addrbytes` handshake issue) achieves an unauthenticated write to the node's persistent `PeerDB` frontier table: the stored `public_key` of an existing neighbor entry is silently replaced with the attacker's key. This is a write to persistent state performed without ever proving possession of the original neighbor's private key, matching the Critical category "unauthenticated/unauthorized write to state." It also has secondary effects — `update_peer` additionally drops the entry's StackerDB association when the key changes, so the impact extends to StackerDB replica bookkeeping for that slot. [8](#0-7) 

### Likelihood Explanation
The attacker needs: (1) a remote outbound-reachable P2P port on the victim, (2) the victim to attempt/accept an outbound handshake to an address the attacker controls or can spoof to match an existing frontier row, and (3) no privileged secret or role — all consistent with the unprivileged remote-attacker model. The gating condition (`self.stats.outbound`) restricts the direct `chat.rs` path to connections the node itself dials, so exploitation is easiest when chained with an address-forging primitive that causes the victim to dial the attacker while believing it is reaching a known peer; absent that chaining, the attacker still benefits from natural address churn (NAT reassignment, IP reuse) that legitimately routes a new outbound handshake to the attacker's box. The DB-level flaw itself (`has_peer`/`try_insert_peer`/`update_peer` never checking key continuity) is unconditionally present and repeatable per handshake.

### Recommendation
In `PeerDB::update_peer` (and/or `try_insert_peer`), require that an update to an existing frontier row either (a) originates from a neighbor whose public key matches the currently-stored key for that `(network_id, addrbytes, port)`, or (b) is accompanied by a verifiable re-key proof (e.g., a message signed by the *previous* stored key, similar to a key-rotation certificate), before allowing `public_key` to change. Alternatively, key frontier rows by `Hash160(public_key)` in addition to address/port so that a differently-keyed peer at the same address creates a new row (subject to slot eviction policy) rather than overwriting the existing identity.

```rust
// stackslib/src/net/db.rs (test module)
#[test]
fn test_update_peer_overwrites_pubkey_without_continuity_check() {
    let addr = PeerAddress([0x00,0x01,0x02,0x03,0x04,0x05,0x06,0x07,0x08,0x09,0x0a,0x0b,0x0c,0x0d,0x0e,0x0f]);
    let port = 12345;
    let network_id = 0x9abcdef0;

    let key_a = Secp256k1PrivateKey::random();
    let pubkey_a = Secp256k1PublicKey::from_private(&key_a);
    let neighbor_a = Neighbor::empty(
        &NeighborKey { peer_version: 0, network_id, addrbytes: addr.clone(), port },
        &pubkey_a,
        0,
    );

    let key_b = Secp256k1PrivateKey::random(); // attacker's key, never related to key_a
    let pubkey_b = Secp256k1PublicKey::from_private(&key_b);
    let mut neighbor_b = neighbor_a.clone();
    neighbor_b.public_key = pubkey_b.clone();

    let mut db = PeerDB::connect_memory(network_id, 0, 0, UrlString::from_literal("http://x"), &[], &[]).unwrap();

    {
        let tx = db.tx_begin().unwrap();
        assert!(PeerDB::try_insert_peer(&tx, &neighbor_a, &[]).unwrap());
        tx.commit().unwrap();
    }
    assert!(PeerDB::has_peer(db.conn(), network_id, &addr, port).unwrap());

    // attacker's differently-keyed Neighbor at the SAME (network_id, addrbytes, port)
    {
        let tx = db.tx_begin().unwrap();
        assert!(PeerDB::try_insert_peer(&tx, &neighbor_b, &[]).unwrap()); // succeeds silently
        tx.commit().unwrap();
    }

    let stored = PeerDB::get_peer(db.conn(), network_id, &addr, port).unwrap().unwrap();
    // BUG: the row's public key was replaced with the attacker's key, with no
    // signature-continuity check against pubkey_a.
    assert_eq!(stored.public_key.to_bytes_compressed(), pubkey_b.to_bytes_compressed());
    assert_ne!(stored.public_key.to_bytes_compressed(), pubkey_a.to_bytes_compressed());
}
```
