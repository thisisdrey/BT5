### Title
Unauthenticated RecvError packet allows remote tunnel teardown / state poisoning without any spoofing-address protection race window - ([File: outside.go])

### Summary
The "malicious module/hook may not be removed" report is fundamentally about an unauthenticated/untrusted actor being able to trigger a state-changing operation (tunnel/hook removal) through a code path that doesn't adequately gate the action on proof of legitimate control, allowing an attacker to force removal of state that should require stronger authorization. The closest reachable analog in Nebula is `handleRecvError`, which tears down an established, cryptographically-authenticated tunnel based on an **unencrypted, unauthenticated** `RecvError` packet type, protected only by a source-address comparison.

### Finding Description
`readOutsidePackets` in `outside.go` dispatches `header.RecvError` packets to `handleRecvError` before any decryption or MAC verification occurs: [1](#0-0) 

`handleRecvError` looks up the hostinfo purely by the attacker-supplied `RemoteIndex` field (a 32-bit value guessable/brute-forceable, or observable on-path since handshake indexes are sent in cleartext during the handshake), and if the recorded remote UDP address of that hostinfo happens to match the packet's source address, it unconditionally tears down the tunnel and deletes the pending handshake state: [2](#0-1) 

The only "authentication" here is a comparison of the UDP source address (`hr != addr`) — which is trivially spoofable by anyone on the same network path or by an attacker who can send UDP packets with a forged source IP (common on many networks, especially where the underlay is untrusted per Nebula's own threat model). There is no cryptographic binding (no MAC/AEAD tag, no replay protection, no proof of possessing the tunnel keys) between the `RecvError` packet and the actual peer. This mirrors the "gas-griefing" report's core flaw: a state-mutating operation (module/hook removal) can be triggered by an unauthenticated/untrusted party through an interface that lacks a hard cryptographic gate, only a weak, spoofable check.

### Impact Explanation
An attacker capable of sending spoofed UDP packets (source-IP spoofing is often possible on UDP, especially for off-path but same-subnet attackers, or trivially for anyone who has observed a peer's `RemoteIndex`/address pairing from earlier traffic) can force teardown of any active Nebula tunnel between two legitimately-authenticated peers, causing denial of service / disruption of the encrypted overlay without ever presenting a valid CA-signed certificate. This is a remote, unauthenticated DoS/state-poisoning primitive directly analogous to the "malicious actor blocks/forces a state-changing operation without proper authorization" class described in the report.

### Likelihood Explanation
`RemoteIndex` values are transmitted in cleartext in every packet header (handshake and data), so an on-path or same-broadcast-domain observer can trivially harvest valid `(RemoteIndex, addr)` pairs and replay them as spoofed `RecvError` packets. The `ShouldRecvError` rate-limit config (`acceptRecvErrorConfig`) mitigates volume but not a single, well-timed spoofed packet, and IP spoofing feasibility depends on network position but is a well-known, practical attack vector for UDP-based protocols.

### Recommendation
Require `RecvError` packets to carry a cryptographic proof tied to the tunnel (e.g., a MAC computed with the session key, or require the packet to be authenticated similarly to `CloseTunnel`) rather than relying solely on source-address comparison. At minimum, treat `RecvError` as advisory (e.g., trigger a rehandshake attempt) instead of an unconditional `closeTunnel` + `DeleteHostInfo`, so a spoofed packet cannot unilaterally destroy authenticated tunnel state.

### Proof of Concept
1. Observe or infer a target's active `RemoteIndex` and current UDP remote address (visible in cleartext handshake/data headers on the wire).
2. Craft a `header.RecvError` packet with that `RemoteIndex`, spoofing the source UDP address to match the victim's recorded peer address.
3. Send it to the victim's listening port.
4. `handleRecvError` matches the spoofed address against `hostinfo.GetRemote()`, passes the check, and calls `f.closeTunnel(hostinfo)` plus `hm.DeleteHostInfo(hostinfo)`, tearing down the authenticated tunnel — repeatable to keep the tunnel from ever staying established.

```go
func (f *Interface) handleRecvError(addr netip.AddrPort, h *header.H) {
	if !f.acceptRecvErrorConfig.ShouldRecvError(addr) {
		f.l.Debug("Recv error received, ignoring",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
		return
	}

	if f.l.Enabled(context.Background(), slog.LevelDebug) {
		f.l.Debug("Recv error received",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
	}

	hostinfo := f.hostMap.QueryReverseIndex(h.RemoteIndex)
	if hostinfo == nil {
		f.l.Debug("Did not find remote index in main hostmap", "remoteIndex", h.RemoteIndex)
		return
	}

	hr := hostinfo.GetRemote()
	if hr.IsValid() && hr != addr {
		f.l.Info("Someone spoofing recv_errors?",
			"addr", addr,
			"hostinfoRemote", hr,
		)
		return
	}

	f.closeTunnel(hostinfo)
	// We also delete it from pending hostmap to allow for fast reconnect.
	f.handshakeManager.DeleteHostInfo(hostinfo)
}
```
