## Finding

The external report's bug class — a critical piece of state (rate/weight) not being updated atomically with the calculation that depends on it, allowing stale-state processing under adversarial conditions — has a direct structural analog in nebula's replay-window handling.

### Title
Non-atomic check-then-update of the replay window allows a captured packet to be processed twice (replay bypass) - (File: `connection_state.go`)

### Summary
`ConnectionState.Decrypt` and `ConnectionState.VerifyRelay` split what should be a single atomic "check-and-mark-seen" replay-window operation into two separately-locked steps with decryption happening in between, unlocked. This mirrors the audited DeFi bug where a calculation is performed against balances/rates that are updated only *after* the fact instead of atomically — here the "balance" is the anti-replay window state.

### Finding Description
`Decrypt` and `VerifyRelay` both:
1. Lock `decryptLock`, call `cs.window.Check(l, messageCounter)`, then unlock.
2. Perform `DecryptDanger` (the actual AEAD decrypt) with the lock released.
3. Re-lock `decryptLock`, call `cs.window.Update(l, messageCounter)` to actually mark the counter as seen, then unlock. [1](#0-0) [2](#0-1) 

Crucially, `Check` only *tests* whether a counter has been seen; it does not mark it. The window bitmap is only mutated by `Update`, which runs *after* decryption completes, under a second, independent lock acquisition. Between step 1 and step 3, the window state for that `messageCounter` remains unmarked.

`readOutsidePackets`, which invokes `Decrypt`/`VerifyRelay`, is run concurrently by `f.routines` independent reader goroutines (`f.listenOut(i)`), each dispatching packets — including packets belonging to the same `hostinfo`/tunnel — to this same `ConnectionState`: [3](#0-2) [4](#0-3) 

If the same ciphertext (i.e., the same `messageCounter`) is delivered more than once — trivially achievable by an on-path or off-path attacker who captures and re-injects a single valid UDP packet at (near-)the same time it is originally delivered, or via duplicate delivery across multiple listener queues/relays — two goroutines can both execute `Check` before either executes `Update`. Both see "not yet seen," both proceed to decrypt (AEAD decryption succeeds identically for both since it's the same ciphertext/counter) and both hand the plaintext up the stack for full packet processing (tun write / firewall / lighthouse / relay handling). The window is only updated afterward, too late to prevent the race.

This is exactly analogous to the reported bug: a value that should reflect "current, just-updated state" (the replay bitmap) is instead read for a decision (`Check`) using state that is stale relative to a concurrently-in-flight duplicate, because the state-mutating step (`Update`) is deferred until after the dependent work (decrypt/process) has already committed to proceeding.

Note: an existing project fix (`CHANGELOG.md`, "Lock replay window updates so concurrent readers can't corrupt it. (#1802)") addressed *internal* corruption of the `Bits` bitmap under concurrent access, but that only protects the bitmap's internal consistency — it does not make the overall check→decrypt→update sequence atomic, so the TOCTOU race at the `ConnectionState` level remains. [5](#0-4) 

### Impact Explanation
This allows a captured/duplicated valid packet to be accepted and fully processed (delivered to the tun device, passed through firewall/conntrack logic, or forwarded via relay) more than once, i.e., a genuine replay bypass of nebula's anti-replay protection under concurrent packet delivery — impacting traffic integrity guarantees the replay window is specifically designed to provide. It does not require possession of a CA-signed certificate; it only requires the ability to observe/capture and re-inject a UDP packet belonging to an already-established tunnel.

### Likelihood Explanation
Likelihood is bounded by the need for near-simultaneous delivery of a duplicate packet to different reader goroutines (a narrow timing window), but nebula explicitly runs multiple independent `listenOut` reader goroutines per interface and processes relay/duplicate paths, making duplicate concurrent delivery a realistic (if racy) network condition rather than a purely theoretical one.

### Recommendation
Make the replay-window check-and-mark operation atomic with respect to decryption: hold `decryptLock` across `Check`, decrypt, and `Update`, or restructure so the counter is provisionally reserved before decryption and only finalized/rolled back based on decrypt success — never allowing two goroutines to observe "unseen" for the same counter simultaneously.

### Proof of Concept
1. Establish a tunnel between two nebula nodes with `listen.routines` > 1 (multiple `listenOut` goroutines).
2. Capture a single legitimate encrypted data packet in flight.
3. Re-inject (replay) that exact UDP packet a second time to the receiving node's listen port(s) within the small window between the original packet's `Check` call and its `Update` call (i.e., essentially simultaneously with the original, or via delivery to a different reader queue).
4. Observe that both the original and replayed copies pass `window.Check` (both see "not yet seen"), both successfully `DecryptDanger`, and both get forwarded to `handleOutsideMessagePacket`/tun/firewall — demonstrating the same message counter processed twice, i.e., a successful replay despite the anti-replay window being present.

func (cs *ConnectionState) Decrypt(l *slog.Logger, messageCounter uint64, out []byte, packet []byte, nb []byte) ([]byte, error) {
	var err error
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}

	out, err = cs.dKey.DecryptDanger(out, packet[:header.Len], packet[header.Len:], messageCounter, nb)
	if err != nil {
		return nil, err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}
	return out, nil
}

func (cs *ConnectionState) VerifyRelay(l *slog.Logger, messageCounter uint64, packet []byte, nb []byte) error {
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	signedPayload := packet[:len(packet)-cs.dKey.Overhead()]
	signatureValue := packet[len(packet)-cs.dKey.Overhead():]
	_, err := cs.dKey.DecryptDanger(nil, signedPayload, signatureValue, messageCounter, nb)
	if err != nil {
		return err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	return nil
}
