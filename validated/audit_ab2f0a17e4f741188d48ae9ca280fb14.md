Based on my research, I found a concrete analog in the TVM precompiled contract argument parsing that mirrors the CVE-2020-25650 bug class: an unprivileged caller supplies a length field that is used to size a memory allocation without any upper bound or cross-check against the actual available data, letting a small transaction trigger a disproportionately large allocation.

### Title
Unbounded array-length-driven allocation in TVM precompile ABI decoding enables memory exhaustion DoS - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
`extractBytes32Array` and `extractBytesArray`, used by the multi-signature validation precompiled contracts (`ValidateMultiSign`/`BatchValidateSign` family) to decode ABI-encoded arrays out of contract call data, read an attacker-controlled 32-byte length word and immediately allocate a Java array of that size with no upper bound and, in the case of `extractBytes32Array`, no bounds check on the read offset at all.

### Finding Description
`extractBytes32Array` reads `len = words[offset].intValueSafe()` and unconditionally allocates `new byte[len][]` [1](#0-0) . Unlike its sibling `extractBytesArray`, it performs no `offset > words.length - 1` guard before dereferencing `words[offset]`, and neither function caps `len` against `Integer.MAX_VALUE`/available `words.length`, relying only on `intValueSafe()` to clamp a 256-bit `DataWord` into an `int` [2](#0-1) . `extractSigArray` follows the identical unbounded pattern [3](#0-2) . These helpers are invoked from the multi-signature validation precompiled contracts reachable via the TVM `STATICCALL`/`CALL` opcodes to precompile addresses when a contract deployer or any transaction sender crafts calldata with a witness/signature array whose length word is set to a large value (e.g., close to `Integer.MAX_VALUE / 32`). A crafted `len` close to `Integer.MAX_VALUE` (bounded only by `intValueSafe()`'s int clamp) causes the JVM to attempt allocating an array of that many `byte[]` references (8 bytes per reference on a 64-bit JVM, or larger for the actual `byte[]` payloads once the loop executes), which can throw `OutOfMemoryError` or consume gigabytes of heap well before the loop even attempts to fill array elements — directly analogous to the spice-vdagentd flaw where an attacker-supplied size field drove uncontrolled memory allocation from an untrusted local channel.

### Impact Explanation
Because the allocation happens before any energy is charged for touching that many elements and before the loop bounds-checks `offset + i + 1` against `words.length`, a single crafted transaction from any unprivileged account that calls a contract invoking these precompiles can force the node executing that transaction (validators and full nodes alike, since all nodes execute the same TVM code) to attempt a multi-gigabyte allocation, triggering `OutOfMemoryError` in the JVM. Depending on how the exception propagates through the TVM execution path, this can crash or destabilize the executing node process, potentially affecting all full nodes and SRs that process the transaction — a node crash/halt condition.

### Likelihood Explanation
This is reachable by any unprivileged account: it only requires deploying/calling a contract that invokes the relevant precompile address with crafted calldata containing an inflated array-length word. No special privilege, stake, or witness status is required, and the entry point is standard contract-call calldata parsing that every full node processes when applying the transaction to the chain, making this highly likely to be reachable via a single signed transaction.

### Recommendation
Add an explicit upper bound check on `len` in `extractBytes32Array`, `extractBytesArray`, and `extractSigArray` (e.g., compare against a sane maximum such as the remaining `words.length` or a fixed cap consistent with the precompile's expected signer/witness count), and add the missing `offset` bounds check to `extractBytes32Array` (mirroring the existing check in `extractBytesArray`) before performing any allocation, so that array length cannot be inflated independently of the actual calldata size.

### Proof of Concept
1. Deploy a contract that calls the multi-signature validation precompile (address associated with `ValidateMultiSign`) via `STATICCALL`, passing ABI-encoded calldata where the array length word at the target offset is set to a large value (e.g., `0x00000000000000000000000000000000000000000000000000000000FFFFFF`) while the rest of the calldata is minimal/short.
2. Send this as a normal `TriggerSmartContract` transaction from any unprivileged account.
3. When `PrecompiledContracts` dispatches to the contract's `execute(byte[] data)` and reaches `extractBytes32Array`/`extractBytesArray`/`extractSigArray`, the node attempts `new byte[len][]` with `len` from the crafted word, causing excessive/failed allocation on the executing node.

Note: I was unable to fully trace the exact `ValidateMultiSign`/`BatchValidateSign` `execute()` bodies (energy-charging order and whether any pre-check on array length exists before calling these extract helpers) due to index truncation of that section of the file; a Devin session with full file access would be needed to confirm there is no size cap applied earlier in `execute()` before these helper calls.

    int len = words[offset].intValueSafe();

    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
