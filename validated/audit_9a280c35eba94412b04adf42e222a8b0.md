### Title
Unbounded attacker-controlled array allocation from `DataWord.intValueSafe()` in TVM precompiled-contract ABI parsers can crash the node (`OutOfMemoryError`) - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
CVE-2017-9806 is a class of bug where a length/count field taken straight from untrusted document data (`WW8Fonts`) is used to size an in-memory structure without validating it against the actual size of the surrounding buffer, causing memory corruption/crash. The same bug class exists in java-tron's precompiled-contract helper methods that parse ABI-encoded call data for signature/byte-array batches: `extractSigArray` and `extractBytesArray` read a "length" word directly from the caller-supplied `data` and immediately allocate a Java array sized by that value, before any bound check against the actual payload size.

### Finding Description
`extractBytesArray` and `extractSigArray` read a length field from an attacker-controlled `DataWord` and use it to allocate an array before validating it against the data actually present: [1](#0-0) [2](#0-1) 

The `len` value comes from `words[offset].intValueSafe()`, and `intValueSafe()` only clamps to `Integer.MAX_VALUE` when the word occupies more than 4 bytes or decodes negative; a positive 4-byte value up to `0x7FFFFFFF` (~2.1 billion) passes through unmodified: [3](#0-2) 

`new byte[len][]` (a reference array) with `len` close to `Integer.MAX_VALUE` attempts to allocate on the order of many gigabytes (8-16 bytes per reference depending on compressed-oops/heap size) *before* the code ever checks `offset + i + 1` against `words.length`. This is analogous to `WW8Fonts` sizing an internal structure from an attacker-supplied count field taken from the document without verifying it against the real remaining buffer size, leading to memory corruption/crash.

Unlike a caught `RuntimeException`, `OutOfMemoryError` is a `java.lang.Error`, not a `RuntimeException`. The TVM interpreter's opcode-execution loop and precompiled-call dispatch only catch `RuntimeException` (and specific typed exceptions such as `JVMStackOverFlowException`/`OutOfTimeException`), so an `OutOfMemoryError` thrown while executing a precompiled contract is not gracefully handled there: [4](#0-3) 

An `OutOfMemoryError` raised in this path can destabilize the JVM heap for the entire node process, since JVMs frequently cannot safely recover once large object allocation exhausts available heap, especially when other subsystems (block application, consensus, RPC) share the same JVM.

### Impact Explanation
If an unprivileged party can craft a smart-contract call (or an EOA calling a contract that in turn calls a TVM precompiled contract) with data words engineered so that a length field is near `Integer.MAX_VALUE`, the node attempting to execute/validate that transaction (including full nodes validating blocks containing it) can throw `OutOfMemoryError` mid-execution. Because `Error` types bypass the `RuntimeException` handling used throughout the VM dispatch, this can crash or destabilize the node process — a denial-of-service against consensus-critical infrastructure, matching the "node crash or halt" acceptance criterion.

### Likelihood Explanation
This is reachable by any account able to broadcast a transaction that invokes the relevant precompiled contract with attacker-controlled call data (a contract-deployer/caller path, not a privileged SR/witness path). Energy metering for precompiled contracts is generally a function of `data.length`, not of the internal length field parsed out of `data`, so a small, cheap call-data payload can encode an oversized `len` value without paying proportional energy — this removes the natural economic disincentive that would otherwise limit resource-exhaustion attempts.

### Recommendation
- In `extractBytesArray` and `extractSigArray`, validate `len` against the number of remaining `words` (i.e., `len <= words.length - offset - 1`) before allocating `new byte[len][]`, rejecting the call (returning the zero/false result) if the declared count cannot possibly be satisfied by the actual data length — mirroring the bound checks already present in `RLP.verifyLength()` used elsewhere in the codebase. [5](#0-4) 
- Apply the same length-vs-available-data validation pattern used by `ContractEventParser.subBytes` (which now rejects oversized/negative lengths) to these precompiled-contract ABI extraction helpers. [6](#0-5) 

### Proof of Concept
1. Deploy or call a contract that invokes the precompiled contract using `extractSigArray`/`extractBytesArray` (e.g., the multi-signature validation precompile), passing call data where `words[offset]` encodes a value close to `Integer.MAX_VALUE` (e.g., `0x000000000000000000000000000000000000000000000000000000007FFFFFFF`) while the surrounding calldata is otherwise minimal/short.
2. Send this as a normal transaction; the node executing the TVM call reaches `extractSigArray`/`extractBytesArray`, computes `len = words[offset].intValueSafe()` ≈ `0x7FFFFFFF`, and executes `new byte[len][]`.
3. The resulting allocation attempt throws `OutOfMemoryError`, which is not caught as a `RuntimeException` by the VM's opcode loop, risking node/thread destabilization.

Note: I was unable to fully trace the exact precompiled-contract class name/address that invokes `extractSigArray`/`extractBytesArray` (only the helper methods and their call sites within `PrecompiledContracts.java` were confirmed) or the precise energy-cost formula governing that specific precompile within the scope of this analysis; a full Devin session with repo access could confirm the exact reachable entry point and energy-cost function tied to this call.

   * In case of int overflow returns Integer.MAX_VALUE otherwise works as #intValue()

  public int intValueSafe() {
    int bytesOccupied = bytesOccupied();
    int intValue = intValue();
    if (bytesOccupied > 4 || intValue < 0) {
      return Integer.MAX_VALUE;
    }
