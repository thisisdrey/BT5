### Title
Heap Out-of-Bounds Read via Unvalidated Local File Header in singlejar `InputJar::LocalHeader` - (File: `src/tools/singlejar/input_jar.h`)

### Summary
`singlejar` is Bazel's internal tool for building deploy/output jars by merging entries from input jar files. When merging jars (`OutputJar::AddJar`), each Central Directory Header (CDH) is used to locate the corresponding Local Header (LH) via `InputJar::LocalHeader()`, and the LH's size, filename length, and extra-field length are trusted without being checked against the actual mapped file bounds, unlike the Central Directory walk which does perform such a check.

### Finding Description
`InputJar::NextEntry` validates each `CDH` record's extent against the mapped file before dereferencing: it computes `new_cdr = cdh_ + cdh_->size()` and calls `mapped_file_.mapped(new_cdr)` to bail out with `diag_errx` if the computed offset falls outside the mmap'd range [1](#0-0) .

However, `InputJar::LocalHeader(cdh)` computes the LH pointer purely from the attacker-controlled `cdh->local_header_offset()` field via `mapped_file_.address(...)`, which is just pointer arithmetic (`mapped_start_ + offset`) with no bounds check at all: [2](#0-1) . The `address()` helper itself performs no validation: [3](#0-2) .

Once `LH* lh` is obtained this way, `output_jar.cc` immediately dereferences the LH's variable-length fields — `file_name_length()`, `extra_fields_length()`, `compressed_file_size()`, `uncompressed_file_size()` — and computes `lh->size()`/`lh->data()`/`lh->in_zip_size()` to decide how many bytes to copy from the mapped input, e.g. in `OutputJar::AddJar`'s copy path which calls `WriteBytes(input_jar.mapped_start() + copy_from, num_bytes)` [4](#0-3) , and in `WriteEntry`, which reads `entry->data() + entry->in_zip_size()` directly out of the mapped buffer [5](#0-4) . `LH::file_name_length()`, `extra_fields_length()`, and the size computations are read straight from packed struct fields with no bounds validation in `zip_headers.h` [6](#0-5) .

Because `local_header_offset32()` (or its zip64 extension) is fully attacker-controlled in a crafted jar/zip supplied as a dependency (e.g., a jar produced from an `http_archive`/`http_jar` fetched from an untrusted URL and then merged by `singlejar` while building a `java_binary`/`deploy_jar`), an attacker can set the offset to point near the very end of the mapped file (or make `file_name_length`/`extra_fields_length`/`compressed_file_size` large relative to the remaining mapped bytes). This causes `singlejar` to read the `LH` struct fields and subsequent `file_name`/`extra_fields`/`data()` bytes beyond the mmap'd region — a heap/mmap-boundary out-of-bounds read, directly analogous to the Redis Cluster Bus PING handler trusting an attacker-supplied length field without validating it against the actual received buffer size.

### Impact Explanation
An out-of-bounds read past the end of the mmap'd input jar can cause a crash (SIGSEGV when the read crosses an unmapped page boundary) — a build-time denial of service — and in some cases could leak adjacent process memory into the generated output jar (information disclosure), since bytes past the legitimate LH structure would be copied into `WriteBytes()`/embedded into the produced deploy jar. This matches the CVSS profile of the Redis analog (low confidentiality impact, high availability impact, no integrity impact) since `singlejar` itself does not authenticate its inputs beyond the standard sha256/checksum on the downloaded archive — the checksum protects the archive's *overall* bytes, not the internal consistency of pointer/length fields once the archive is opened and re-processed by `singlejar`.

### Likelihood Explanation
This is reachable whenever a Bazel build passes an externally-sourced jar to `singlejar` (very common: any `java_import`/`java_binary` with deps coming from an `http_jar`/`http_archive`/Maven-fetched jar merged into a deploy jar). A crafted jar with a valid sha256 (the attacker controls the served bytes, so the checksum matches whatever they publish) but an internally inconsistent/malicious local-header offset would trigger the bug on every build that processes it through `singlejar`. No further authentication step validates the internal ZIP local-header offsets after the sha256 check on the whole file passes.

### Recommendation
In `InputJar::LocalHeader()` (and anywhere `LH*` fields are subsequently read), validate that the computed LH pointer and its full extent (`sizeof(LH) + file_name_length() + extra_fields_length()`, and the in-zip data size) lie fully within `mapped_file_.start()`/`mapped_file_.end()` before returning the pointer or allowing callers to read from it — mirroring the check already present in `NextEntry` for CDH entries. On failure, fail closed with `diag_errx`, consistent with existing error handling conventions in `input_jar.cc`.

### Proof of Concept
A `BuildIntegrationTestCase`/`src/test/shell/bazel` style reproduction:
1. Programmatically construct a minimal valid ZIP (à la `output_jar_simple_test.cc`'s `CreateZipWithMalformedExtraField` helper, which already demonstrates the pattern of crafting adversarial LH/CDH/extra-field byte layouts) [7](#0-6) .
2. Set the CDH's `local_header_offset32` to point to an offset near `mapped_end_` such that the fixed 30-byte `LH` struct, or the derived `file_name_length`/`extra_fields_length`, extends past the actual mapped file size.
3. Feed this crafted jar as an `--sources` input to `singlejar` (or via `java_binary`'s deploy-jar build path) and observe an out-of-bounds read/crash, versus the expected graceful `diag_errx` failure.

Note: due to indexing limits I could not fully inspect all downstream consumers of `LH*` (e.g., `Concatenator::Merge` in `combiners.cc`) to confirm every code path's exposure; a full audit of all `LH`-dereferencing call sites would require a Devin session with complete repository access to be fully exhaustive.

std::string CreateZipWithMalformedExtraField() {
  std::string zip_data;
  const std::string filename = "evil.bin";

  // 1. Local File Header (LFH)
  size_t lh_offset = zip_data.size();
  size_t lh_size = sizeof(LH) + filename.size();
  zip_data.resize(lh_offset + lh_size, 0);
  auto* lh = reinterpret_cast<LH*>(&zip_data[lh_offset]);
  lh->signature();
  lh->version(10);
  lh->file_name(filename.data(), filename.size());

  // 2. Extra field payload containing an oversized payload_size
  uint8_t ef_buffer[8] = {0};
  auto* ef1 = reinterpret_cast<ExtraField*>(ef_buffer);
  ef1->signature(0x000d);
  ef1->payload_size(0);

  auto* ef2 = reinterpret_cast<ExtraField*>(ef_buffer + ef1->size());
  ef2->signature(0xdead);
  ef2->payload_size(0xf000);  // Malformed size exceeding extra field buffer

  // 3. Central Directory Header (CDH)
  size_t cdh_offset = zip_data.size();
  size_t cdh_size = sizeof(CDH) + filename.size() + sizeof(ef_buffer);
  zip_data.resize(cdh_offset + cdh_size, 0);
  auto* cdh = reinterpret_cast<CDH*>(&zip_data[cdh_offset]);
  cdh->signature();
  cdh->version(20);
  cdh->version_to_extract(10);
  cdh->local_header_offset32(lh_offset);
  cdh->file_name(filename.data(), filename.size());
  cdh->extra_fields(ef_buffer, sizeof(ef_buffer));

  // 4. End of Central Directory (EOCD)
  size_t ecd_offset = zip_data.size();
  zip_data.resize(ecd_offset + sizeof(ECD), 0);
  auto* ecd = reinterpret_cast<ECD*>(&zip_data[ecd_offset]);
  ecd->signature();
  ecd->this_disk_entries16(1);
  ecd->total_entries16(1);
  ecd->cen_size32(cdh_size);
  ecd->cen_offset32(cdh_offset);

  return zip_data;
}
