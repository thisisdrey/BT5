### Title
Wallet Contract `has_in_flight_tx` lock can become permanently stuck, freezing the account - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The `WalletContract` (the eth-implicit account's owner contract) serializes transaction execution with a boolean flag `has_in_flight_tx`, refusing any new `rlp_execute` call while a previous cross-contract call chain is still pending. The flag is only cleared inside the terminal `#[private]` callbacks (`rlp_execute_callback`, `address_check_callback`, `nep_141_storage_balance_callback`, `ban_relayer`). If one of these callbacks fails or panics (e.g. runs out of its fixed, small static gas budget while processing an attacker-influenced promise result), its state changes — including the `has_in_flight_tx = false` reset — are rolled back, leaving the flag permanently `true` with no other code path able to clear it. This mirrors the `Vault.blacklistProtocol` bug class: a safety/serialization mechanism that depends on an operation which can revert for reasons outside the caller's control, and once it reverts the mechanism becomes permanently unusable.

### Finding Description
`rlp_execute` guards re-entrancy purely via the persisted flag: [1](#0-0) 

The flag is set to `true` before returning any `Promise`, and is only ever reset to `false` at the very top of the terminal callbacks: [2](#0-1) 

Each of these callback methods is invoked with a fixed, small static gas allocation (`RLP_EXECUTE_CALLBACK_GAS = 5 Tgas`, optionally plus `action.gas()`), computed once when the promise chain is built: [3](#0-2) [4](#0-3) 

`target` is an arbitrary account chosen by the transaction the wallet owner signs (via `rlp_execute`'s `target` parameter, ultimately dispatched through `action_to_promise`), so the contract called can be fully attacker/relayer controlled: [5](#0-4) 

If that target contract's `FunctionCall` returns a large success value, `env::promise_result(0)` inside `rlp_execute_callback` (or the address/NEP-141 callbacks) must copy that value out of the register — a cost proportional to its size — before the callback logic even runs. Because the callback's gas budget is a fixed constant unrelated to the size of the eventual return payload, an oversized result can exhaust the callback's gas and cause the whole receipt to panic ("Exceeded the prepaid gas"). On a NEAR receipt failure, all state mutations of that receipt — including the `self.has_in_flight_tx = false` reset that the callback was supposed to perform — are discarded (`state_update.rollback()` semantics used generally in the runtime, see `runtime/runtime/src/lib.rs:967`), while the flag was already durably set to `true` in the *previous* receipt that dispatched the promise chain.

There is no other method in `WalletContract` that can reset `has_in_flight_tx` (no owner/admin/timeout escape hatch), so once this happens, every subsequent `rlp_execute` call is rejected forever: [6](#0-5) [7](#0-6) 

This is structurally the same defect as `Vault.blacklistProtocol`: a mechanism meant to enforce a safety invariant (single in-flight tx / prevent replay) depends on a sub-operation (a cross-contract call callback) that can revert for reasons the wallet contract cannot control, and once it reverts the mechanism can never be un-stuck.

### Impact Explanation
Once `has_in_flight_tx` is stuck `true`, the ETH-implicit wallet account becomes permanently unusable: `rlp_execute` — the sole entry point for the owner to move funds, call contracts, or manage keys from that account — always short-circuits with an error. All NEAR and token balances held by that wallet contract account become permanently frozen, since deletion or full-access-key addition is impossible for eth-implicit accounts and there is no reset mechanism. This matches "permanent freezing of funds."

### Likelihood Explanation
The `target` and the resulting `FunctionCall` return payload are attacker-influenced: an attacker who controls (or convinces the relayer/user to interact with) a target contract can simply have that contract return an oversized success value for the call the wallet relays, deterministically triggering an out-of-gas panic in the fixed-gas callback. No privileged access is required — only that the user's signed Ethereum-style transaction routes a call through the wallet to the attacker's contract, a normal, unprivileged interaction pattern for this feature.

### Recommendation
- Do not size the callback's static gas budget independently of the potential return-value size; either cap/limit the accepted size of promise results processed in the callback, or ensure the callback provably cannot exceed its allocated gas regardless of the callee's return payload (e.g., avoid copying/echoing arbitrarily large results, or bound `action.gas()`-derived callback gas with a safety margin proportional to worst-case return size).
- Add a recovery mechanism (e.g., an owner-signed action, or a self-call with a timeout) that can force-reset `has_in_flight_tx` if the promise chain does not resolve as expected, so a single failed callback cannot permanently brick the account.

### Proof of Concept
1. An eth-implicit account's `WalletContract` receives an RLP transaction whose decoded action is a `FunctionCall` to `target = AttackerContract`.
2. `inner_rlp_execute` builds `action_to_promise(target, action).then(ext.rlp_execute_callback(caller_deposit))` with `RLP_EXECUTE_CALLBACK_GAS` (5 Tgas) + `action.gas()` as the callback's static gas (`lib.rs:466-470`), and sets `has_in_flight_tx = true` (`lib.rs:117-119`).
3. `AttackerContract`'s function returns a large success payload (sized so that copying it via `env::promise_result(0)` inside `rlp_execute_callback` consumes more gas than the fixed callback allocation).
4. The `rlp_execute_callback` receipt fails with an out-of-gas panic; its state changes — the intended `self.has_in_flight_tx = false` (`lib.rs:280`) — are discarded, so the flag remains `true` as committed by the prior receipt.
5. Any further call to `rlp_execute` on this wallet now always returns `success: false, error: "transaction already in progress, please try again later."` (`lib.rs:97-105`), forever, since nothing else can clear the flag — the account and its funds are permanently frozen.
