## Title
Liquidation liveness DoS via unconditional `OracleMaxConfidenceExceeded` revert on price-confidence gate — (File: `programs/marginfi/src/state/price.rs`, `programs/marginfi/src/state/marginfi_account.rs`)

### Summary
Marginfi's health/liquidation engine unconditionally propagates a hard revert (`Errors::OracleMaxConfidenceExceeded`) whenever an oracle's confidence interval exceeds `bank.config.oracle_max_confidence`, with no fallback or bypass path for `Maintenance`-mode (liquidation) checks. This is the same bug class as the reported `PanopticPool.dispatchFrom()` `StaleOracle` DoS: a price-quality gate sitting in front of liquidation logic that reverts the entire transaction — including for genuinely insolvent accounts — precisely during the market conditions (high volatility) where liquidations matter most, and with no privileged bypass.

### Finding Description
For Pyth-Push and Switchboard-Pull feeds, `get_confidence_interval()` computes the oracle confidence and, if it exceeds `oracle_max_confidence`, returns a hard error instead of degrading gracefully: [1](#0-0) 

This same pattern exists for the Switchboard adapter: [2](#0-1) 

This error is not scoped to a "reduced information" path — it aborts the whole price fetch. That error is then propagated by `calc_weighted_liab_value_standalone`, which is used for the liability side of every health computation, **including `RequirementType::Maintenance`** used during liquidation checks: [3](#0-2) 

On the asset side, `calc_weighted_asset_value_standalone` only special-cases (skips) a stale/errored oracle for `RequirementType::Initial`; for `Maintenance` (the liquidation-relevant type) it still maps the oracle error straight through: [4](#0-3) 

Both of these feed into `get_health_components`, which is called unconditionally at the top of `check_pre_liquidation_condition_and_get_account_health` — the shared entrypoint used by `lending_account_liquidate`, `start_receivership` (used by both `LendingAccountLiquidate`'s liquidate-start flow and force-deleverage), and `end_receivership`: [5](#0-4) 

Since this check happens **before** the function has determined whether the account is actually insolvent, any oracle confidence spike on *any* balance in the account (asset or liability side) blocks the entire liquidation attempt with `OracleMaxConfidenceExceeded`, exactly analogous to the Panoptic `StaleOracle` gate blocking `dispatchFrom` before it distinguishes liquidation/force-exercise/settlement.

Unlike the protocol's separate pause mechanism — where a `risk_admin` forced-deleverage path is explicitly carved out to bypass the pause gate — there is no equivalent bypass for the oracle-confidence gate. `start_receivership` (used by both ordinary liquidation and forced deleverage) calls the same `check_pre_liquidation_condition_and_get_account_health`, so even the emergency risk_admin flow is blocked by this gate: [6](#0-5) 

### Impact Explanation
- **Delayed/blocked liquidations**: If any bank balance's oracle confidence interval widens beyond `oracle_max_confidence` (a well-documented Pyth/Switchboard behavior during high volatility, exactly when liquidations are most urgently needed), `check_pre_liquidation_condition_and_get_account_health` reverts for every caller, on every account sharing that bank, until confidence narrows again.
- **No privileged bypass**: Even the `risk_admin` forced-deleverage flow, which is specifically designed to operate during emergencies (bypassing the global pause), routes through the same gate and is blocked identically.
- **Bad debt risk**: Positions that are insolvent under `Maintenance` requirement cannot be closed while the condition persists, increasing the risk that losses socialize to lenders/PLPs or convert into protocol bad debt — matching the report's core impact class (insolvency/bad debt via liquidation liveness failure).
- **Griefing surface**: A liquidator submitting a valid liquidation for an account that also holds a position in a currently-wide-confidence bank will have their transaction revert, wasting gas, and will keep reverting until the oracle's reported confidence narrows — the same "Scenario B: Liveness failure during volatility" pattern described in the report; the mempool-frontrun scenario (A) is less directly applicable since attackers don't directly control Pyth/Switchboard-reported confidence the way they can push AMM spot price, but the volatility-driven liveness failure is directly reachable by any unprivileged actor (or by market conditions alone).

### Likelihood Explanation
Confidence-interval widening under volatility is a normal, frequently-observed behavior of both Pyth and Switchboard oracles — this does not require any privileged access or contrived setup, only a period of market stress, which is also exactly when insolvent positions accumulate and liquidations are most needed. The lack of a Maintenance-mode fallback (contrasted with the Initial-mode stale-oracle skip already present in `calc_weighted_asset_value_standalone`) shows the gap is specific to the liquidation path rather than a deliberate universal safety design.

### Recommendation
Apply the same mitigation strategies suggested in the referenced report:
1. For `Maintenance`/liquidation-mode price fetches, do not hard-fail on `OracleMaxConfidenceExceeded`; instead, either use the wider (unbiased/EMA) price with an explicit degraded-mode flag, or fall back to the last cached/locked price (the codebase already has a `LiquidationPriceCache`/cached-price mechanism used elsewhere) rather than reverting the whole health check.
2. Extend the existing "skip stale oracle" treatment in `calc_weighted_asset_value_standalone` (currently `Initial`-only) to also apply, in a risk-appropriate way, to `Maintenance` checks used specifically for liquidation eligibility.
3. Ensure the privileged forced-deleverage path (`risk_admin`) has an explicit bypass of the oracle-confidence gate, mirroring the bypass it already has for the global pause, so genuine insolvency can always be resolved by risk admins even when third-party oracle confidence temporarily widens.

### Proof of Concept
1. Set up a liquidatable account with collateral in bank A and debt in bank B, matching the existing test pattern in `tests/specs/basic/10_liquidate.spec.ts`.
2. Using the mock Pyth/Switchboard oracle utilities (`tests/utils/pyth-pull-mocks.ts`, `kamino-utils.ts`, etc., which already expose confidence/`CONF_INTERVAL_MULTIPLE` knobs, as seen in `confidenceInterval = 0.01 * CONF_INTERVAL_MULTIPLE` in the existing liquidate spec), set either bank's oracle confidence such that `conf_interval > price * oracle_max_confidence`.
3. Call `lending_account_liquidate` (or `start_deleverage`) against the insolvent account and observe that the instruction reverts with `MarginfiError::OracleMaxConfidenceExceeded` instead of executing the liquidation, even though the account is genuinely insolvent under Maintenance requirement.
4. Confirm the same revert occurs for the `risk_admin` forced-deleverage flow (`start_deleverage` → `start_receivership`), demonstrating there is no privileged bypass equivalent to the pause-bypass documented in `guides/ADMIN/PERMISSIONS_AND_ROLES.md`.
