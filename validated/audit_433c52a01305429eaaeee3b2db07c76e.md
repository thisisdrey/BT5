## Title
Unauthorized theft of a receivership account's funds via unrestricted `destination_token_account` in `lending_account_withdraw` - (File: `programs/marginfi/src/instructions/marginfi_account/withdraw.rs`)

### Summary
The Gearbox report flags a footgun where a caller-supplied `to` address in a liquidation-adjacent function is never checked against the intended recipient, letting funds go to an unintended (even attacker-controlled) destination. Marginfi's `LendingAccountWithdraw` instruction has the same structural flaw in a much more dangerous form: during receivership, *any* signer other than the original account authority is authorized to call withdraw, and the `destination_token_account` is completely caller-controlled with no ownership/identity constraint.

### Finding Description
`is_signer_authorized` grants authorization to withdraw from a marginfi account during receivership to any signer that is not the original account authority — it does not verify the signer is the actual `liquidation_receiver` assigned to that liquidation: [1](#0-0) 

`LendingAccountWithdraw` calls this check with `allow_receivership = true`: [2](#0-1) 

The instruction's `authority` field explicitly documents that "during receivership ... there are no signer checks whatsoever: any key can repay [withdraw] as long as the invariants checked at the end of execution are met": [3](#0-2) 

Critically, `destination_token_account` — the account that receives the withdrawn tokens — has no constraint tying it to the account authority, the designated receiver, or any protocol-owned account; it is a plain `#[account(mut)]` `InterfaceAccount<TokenAccount>` fully chosen by the caller: [4](#0-3) 

Combining these two facts: once an account enters receivership (`ACCOUNT_IN_RECEIVERSHIP`), any third-party signer (not just the legitimate `liquidation_receiver`) can call `lending_account_withdraw` and route the liquidatee's collateral to a `destination_token_account` of their choosing. This is the same bug class as the Gearbox report (uncontrolled/unvalidated destination for a withdrawal-type operation reachable by a liquidator/receiver-privileged actor), except here the impact is direct theft of the liquidatee's funds by an unrelated third party, not merely a self-inflicted mistake by the caller.

### Impact Explanation
This allows any observer of the mempool/chain (a bot racing the legitimate receiver) to drain assets from an account under receivership liquidation to their own wallet, effectively front-running/hijacking the receivership process and stealing user/liquidatee funds. This satisfies the "concrete theft, unauthorized transfer" bar for the vulnerability class.

### Likelihood Explanation
Receivership is entered via the permissionless `StartLiquidation` path whenever an account is unhealthy, which is a routine, expected occurrence for any lending protocol. Any account entering receivership is instantly exposed to withdrawal by an unrelated signer for the duration of the receivership window, until `EndLiquidation` closes it. Exploitation only requires monitoring for `ACCOUNT_IN_RECEIVERSHIP` accounts and racing a `lending_account_withdraw` transaction with an attacker-owned `destination_token_account` — no privileged access is required.

### Recommendation
Restrict `destination_token_account` during receivership so it can only route funds to an account tied to the actual `liquidation_receiver` recorded for that liquidation (e.g. validate `destination_token_account`'s owner against the `liquidation_receiver` stored on the `LiquidationRecord`, similar to how other instructions validate recipients via `has_one`), rather than relying solely on `marginfi_account.authority != signer` as the authorization check.

### Proof of Concept
1. Account `V` becomes unhealthy; anyone calls `StartLiquidation`, setting `ACCOUNT_IN_RECEIVERSHIP` on `V` and recording the legitimate `liquidation_receiver` in the `LiquidationRecord`.
2. Attacker `A` (not the recorded receiver, not `V`'s authority) submits `lending_account_withdraw` for `V`'s marginfi account, supplying their own `destination_token_account`.
3. `is_signer_authorized(&V, group_admin, A, true, true)` returns `true` because `V.authority != A` (`programs/marginfi/src/state/marginfi_account.rs:91-93`), passing the Anchor constraint at `withdraw.rs:270-275`.
4. `destination_token_account` is accepted with no ownership check (`withdraw.rs:302-303`), so the withdrawn collateral is transferred to `A`'s wallet instead of being managed by the legitimate receiver.

Note: due to indexing limits I was not able to fully trace where/if `liquidation_receiver` from `LiquidationRecord` is otherwise cross-checked against the withdraw caller anywhere else in the receivership flow (e.g., in `liquidate_start.rs`/`liquidate_end.rs`); a Devin session with full repository access should verify whether any such check exists elsewhere before this PoC is treated as fully confirmed exploitable in isolation from those files.
