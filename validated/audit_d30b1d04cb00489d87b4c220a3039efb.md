### Title
`DebtToken.quoteRepayOut` rounds the repaid debt amount in the payer's favor via `wadDiv` half-up rounding - (`contracts/DebtToken.sol`)

### Summary
The Ethos report's bug class is a rounding direction keyed on the wrong variable: `_calcCost` rounds up on sells of `DISTRUST` votes because it branches on `isPositive` instead of `isBuy`, so each inverse operation leaks dust against the protocol. The Metronome analog lives in `DebtToken.repay` / `quoteRepayOut`: the same shared gross amount is split into "debt repaid" and "fee" by a `wadDiv` that rounds **half up**, i.e. the debt-burned component is rounded in the payer's favor regardless of direction, so the protocol systematically credits slightly more debt repayment than the synth burned is worth. Repeatable rounding in the caller's favor.

### Finding Description
`repay(onBehalfOf_, amount_)` takes a gross synth amount, splits it via `quoteRepayOut`, seizes the fee portion to the fee collector, burns `_repaid` synth, and burns `_repaid` debt tokens. [1](#0-0) 

The split is:

```solidity
// contracts/DebtToken.sol
_amountToRepay = amount_.wadDiv(HUNDRED_PERCENT + _repayFee);
_fee = amount_ - _amountToRepay;
``` [2](#0-1) 

`wadDiv` is `(a * WAD + b / 2) / b` — round half up. [3](#0-2)  So `_amountToRepay` (debt written off) is rounded up whenever the exact division has a fractional part ≥ 0.5 wei, and `_fee` (what the fee collector actually receives) is computed as the remainder — the rounding error is charged to the protocol/feeCollector side, not the payer. The correct direction for the repay path is floor on `_amountToRepay` (or equivalently computing `_fee` with ceiling), because the value leaving the protocol's books (debt extinguished) should never exceed the exact pro-rata share of what the payer surrendered. The mirror-image asymmetry with `quoteRepayIn` (fee via `wadMul` half-up on `repayAll`) [4](#0-3)  means the two inverse directions are not consistent: `repayAll` charges a rounded-up fee, while `repay` credits a rounded-up repayment — the same mis-keyed rounding as `isPositive` vs `isBuy`.

### Impact Explanation
Each `repay` call lets the payer extinguish up to ~1 wei more debt (and pay ~1 wei less fee) than the exact fee math dictates. Per call this is dust, but it is unprivileged, repeatable rounding in the caller's favor, accumulating as protocol insolvency (debt supply reduced without a corresponding synth burn backing it). It also interacts with `debtFloorInUsd`: the residual-debt check uses the rounded-up `_repaid` [5](#0-4) , so edge positions can clear the floor boundary or leave a sub-wei residual that later blocks exact `BurnAmountExceedsBalance` arithmetic in `_burn` [6](#0-5) , mirroring the "last vote cannot be sold" liveness failure in the original report.

### Likelihood Explanation
Reachable by any EOA via public `DebtToken.repay` whenever `repayFee > 0` on the fee provider and the division `amount_ * 1e18 / (1e18 + repayFee)` is non-integral — which is the common case for realistic fee values. No privileged role, oracle manipulation, or special market state is required; only a nonzero `repayFee`. Impact per call is capped at wei-scale, so this is a dust-leakage / precision-loss severity, not a bulk drain.

### Recommendation
Make the rounding direction explicit and direction-aware rather than inheriting `wadDiv`'s half-up behavior: compute the repay split so the fee is never undercharged, e.g.

```solidity
uint256 _feeCeil = amount_.wadMul(_repayFee); // or Math.mulDiv(..., Math.Rounding.Ceil)
_amountToRepay = amount_ - _feeCeil;
```

or use `mulDiv(amount_, 1e18, 1e18 + _repayFee, Math.Rounding.Floor)` for `_amountToRepay`. Apply the same explicit-direction audit to `quoteRepayIn`/`repayAll` and to `Pool.quoteSwapIn`/`quoteLiquidateIn`, which use the same `wadDiv(1e18 ± fee)` pattern [7](#0-6) [8](#0-7) .

### Proof of Concept
Foundry-style test sketch (not executed — no test runner available in this environment):

```solidity
// Assume repayFee = 1e15 (0.1%) on FeeProvider; debtToken = pool debt token for msUSD.
// Attacker has debt >= 2e18 and holds msUSD.

uint256 gross = 1e18 + 1; // crafted so division is non-integral with fraction >= 0.5
(uint256 repaid,) = debtToken.quoteRepayOut(gross);
uint256 exact = gross * 1e18 / (1e18 + 1e15); // floor division
assertGt(repaid, exact); // half-up rounding credits extra debt repayment

// Loop: debtToken.repay(attacker, gross) N times via fresh debt issuance;
// sum(repaid_i) - sum(exact_i) grows by up to ~1 wei/iteration against totalSupply_,
// and the feeCollector receives correspondingly less synth than exact fee math.
```

Caveat: I verified the rounding direction statically; I did not fully trace `Pool.swap`'s balance-delta accounting or `SmartFarmingManager` leverage math for a larger-magnitude analog of this class, so a stronger instance may exist in those paths.
