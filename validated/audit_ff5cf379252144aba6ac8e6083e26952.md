### Title
Per-IP and global QUIC connection admission counters are read-only pre-handshake, letting a single unstaked IP perpetually saturate `ClientConnectionTracker` via handshake-abort churn - ([File: streamer/src/nonblocking/quic.rs])

### Summary
`run_server` admits a new QUIC connection into the bounded `ClientConnectionTracker` pool (`max_concurrent_connections`) based only on read-only checks (`overall_connection_rate_limiter.current_tokens() == 0` and `rate_limiter.is_allowed(ip)`), while the actual token consumption (`register_connection`, `overall_connection_rate_limiter.consume_tokens`) happens only in `setup_connection` after the QUIC handshake succeeds. An attacker who resets the connection before the handshake completes is never charged by either limiter, so `is_allowed()` keeps returning `true` for that IP forever, letting it re-fill the shared, capacity-bounded tracker pool continuously.

### Finding Description
In `run_server` [1](#0-0) , admission of an `Incoming` connection into the bounded resource pool is gated by two purely read-only checks: `overall_connection_rate_limiter.current_tokens() == 0` and `rate_limiter.is_allowed(&incoming.remote_address().ip())`. Neither call mutates limiter state. Once both checks pass, `ClientConnectionTracker::new(...)` reserves a slot out of the fixed-size `stats.open_connections` pool bounded by `qos.max_concurrent_connections()` [2](#0-1) , and `setup_connection` is spawned.

The actual billing only happens inside `setup_connection`, after `timeout(QUIC_CONNECTION_HANDSHAKE_TIMEOUT, connecting).await` resolves `Ok(new_connection)` (i.e., the QUIC/TLS handshake completed): only then are `rate_limiter.register_connection(&from.ip())` and `overall_connection_rate_limiter.consume_tokens(1)` called [3](#0-2) . `ConnectionRateLimiter::is_allowed` explicitly documents this design: "we assume that only IPs with actual confirmed connections are stored in it, since we should only modify server state once source IP is verified" and returns `true` for any IP it has never billed [4](#0-3) .

Consequently, an attacker that resets/aborts the connection before the handshake resolves (e.g., before completing TLS Finished) never triggers `register_connection` or `consume_tokens`. Their IP is never marked as "seen" by the per-IP limiter, so `is_allowed()` keeps returning `true` indefinitely, and the global bucket's token count is never drawn down by these attempts. The only resource actually consumed is one `ClientConnectionTracker` slot (freed on `Drop`, at most after `QUIC_CONNECTION_HANDSHAKE_TIMEOUT` = 2s, or immediately if the reset causes the `connecting` future to resolve to an `Err`) [5](#0-4) . By continuously opening and resetting connections faster than the 2-second timeout window, a single unstaked, unstaked-IP attacker can keep the shared `ClientConnectionTracker` pool (sized `max_concurrent_connections`, e.g., derived from `DEFAULT_MAX_STAKED_CONNECTIONS`/`DEFAULT_MAX_UNSTAKED_CONNECTIONS` = 2000 each) perpetually full, causing legitimate incoming connections to be refused via `refused_connections_too_many_open_connections` [6](#0-5) .

This directly defeats the invariant stated in the code's own comment block ("cap total connections per-peer/ip") [7](#0-6) : the per-IP cap is only enforced against IPs that have completed at least one handshake, not against churn of never-completed handshakes from the same IP.

### Impact Explanation
This is a QoS-evasion / availability-degradation issue: an unstaked, single-IP attacker can continuously occupy the entire bounded connection-admission pool (`ClientConnectionTracker`, sized by `qos.max_concurrent_connections()`) using only half-open, aborted QUIC handshakes, without ever being throttled by either the per-IP or global connection-rate limiters. Legitimate unstaked/staked clients attempting to connect during the attack window are refused (`stats.refused_connections_too_many_open_connections` increments) and are unable to establish streams/send transactions to the leader's TPU — a transaction-ingress denial-of-service condition, distinct from a bootstrap-only or config-fixable issue, and reachable purely from packets an unprivileged remote client can send to the public TPU QUIC port.

### Likelihood Explanation
Fully feasible with attacker-owned resources only: no stake, no gossip/peer control, single IP (the scenario explicitly allows multiple ephemeral ports on one owned IP, though not strictly required since QUIC connections are multiplexed by connection ID). The attacker only needs to open QUIC `Initial` packets and reset/abandon them before the TLS handshake resolves — client-side behavior fully controlled by the attacker, requiring no privileged network position or IP spoofing. The attack is continuously repeatable and does not require winning a race against server internals — it only needs to occur before the (attacker-controlled) handshake would otherwise complete, which the attacker trivially avoids by simply not completing it.

### Recommendation
Charge (or reserve) a fractional/pre-handshake token from the per-IP and global rate limiters at admission time (before spawning `setup_connection`), refunding it on handshake success/failure appropriately, rather than deferring all consumption to post-handshake. Alternatively, track per-IP counts of *outstanding* (not-yet-handshaken) connection attempts and enforce a hard per-IP cap on outstanding attempts independent of the "confirmed connection" per-IP limiter, so a single IP cannot monopolize the shared `ClientConnectionTracker` capacity via handshake churn.

### Proof of Concept
Integration test plan (extending existing tests like `test_rate_limiting` in `tpu-client-next/tests/connection_workers_scheduler_test.rs`):
1. Spin up `setup_quic_server` with a small `max_concurrent_connections` (via a small `SwQosConfig`/`SimpleQosConfig` staked/unstaked cap, e.g. 4).
2. From a single client IP, repeatedly open new QUIC endpoints/connections to the server and immediately `drop`/reset them before `.await`-ing the connect future resolves (i.e., before the handshake completes), looping fast enough to keep at least `max_concurrent_connections` attempts outstanding at all times for several multiples of `QUIC_CONNECTION_HANDSHAKE_TIMEOUT` (2s).
3. Concurrently, from a second, legitimate client (different port, same or different IP), attempt to establish and complete a real QUIC connection.
4. Assert that `stats.refused_connections_too_many_open_connections` increases for the legitimate client's attempts while `stats.connection_rate_limited_per_ipaddr` and `stats.connection_rate_limited_across_all` remain 0 for the attacker throughout the attack (proving `is_allowed()`/`current_tokens()` checks never converted into consumed tokens for the attacker), and that `stats.open_connections` stays pinned near `max_concurrent_connections` for the duration of the attack window.

    /// Check the max_concurrent_connections limit and if it is within the limit
    /// create ClientConnectionTracker and increment open connection count. Otherwise returns Err
    fn new(stats: Arc<StreamerStats>, max_concurrent_connections: usize) -> Result<Self, ()> {
        let open_connections = stats.open_connections.fetch_add(1, Ordering::Relaxed);
        if open_connections >= max_concurrent_connections {
            stats.open_connections.fetch_sub(1, Ordering::Relaxed);
            debug!(
                "There are too many concurrent connections opened already: open: \
                 {open_connections}, max: {max_concurrent_connections}"
            );
            return Err(());
        }

        Ok(Self { stats })
    }
