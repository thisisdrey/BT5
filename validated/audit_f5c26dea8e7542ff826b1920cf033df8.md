### Title
Dust-transfer griefing fills a victim's collateral token list to `MAX_TOKENS_PER_USER`, permanently blocking new deposits and preventing them from topping up collateral to avoid liquidation - ([File: contracts/DepositToken.sol](contracts/DepositToken.sol), [contracts/Pool.sol](contracts/Pool.sol))

### Summary
`DepositToken._transfer()` and `DepositToken._mint()` unconditionally call `pool.addToDepositTokensOfAccount(recipient_)` whenever the recipient's balance of that token transitions from zero to non-zero ( [1](#0-0) ). `Pool.addToDepositTokensOfAccount` enforces a hard cap (`UserReachedMaxTokens`, confirmed in `test/Pool.test.ts`) on the number of distinct deposit/debt tokens tracked per account. Because `transfer()` is a public ERC20 entry point and the recipient has no opt-in, an attacker can send 1 wei of each whitelisted `DepositToken` to a victim until their list hits the cap. From then on, any `deposit()` into a collateral the victim does not already hold reverts in `_mint` → `addToDepositTokensOfAccount`, so the victim cannot add new collateral types. If their position drifts toward the liquidation threshold, they cannot rescue it with a different collateral asset, guaranteeing liquidation and loss of the liquidation penalty.

### Finding Description
- Public entry point: `DepositToken.transfer(to_, amount_)` (line 348) and `transferFrom` (line 357) call `_revertIfLocked` on the *sender* only, then `_transfer`.
- `_transfer` adds the token to the *recipient's* pool-side list when `balanceOf[recipient_] == 0` ( [1](#0-0) ). The victim cannot refuse the receipt.
- `Pool.addToDepositTokensOfAccount` reverts `UserReachedMaxTokens` once the account's `MappedEnumerableSet` of deposit tokens reaches the configured max (same pattern as `addToDebtTokensOfAccount`; the cap revert is asserted at `test/Pool.test.ts:1506-1521`).
- The same revert fires inside `_mint` during `deposit(..., onBehalfOf_ = victim)` ( [2](#0-1) ), so an attacker can also fill the list without spending their own msdTOKEN balance by dust-depositing on the victim's behalf — the underlying cost is only the underlying token transferred to Treasury, which stays credited to the victim.
- Once saturated, every `deposit()` into a new collateral token reverts. Withdrawals of existing tokens still work, but each `withdraw` only *removes* entries (line 523-525 on sender side / `_burn` line 460-462), so the victim can free slots — however freeing a slot requires fully zeroing a balance, and critically, during the window where the account is under-collateralized they cannot deposit *other* collateral to restore health without first abandoning an existing position.

### Impact Explanation
Liveness / forced liquidation: the invariant "a user can always add collateral to keep a healthy position" breaks. A victim holding a near-threshold debt position can be dust-spammed so that all additional collateral deposits revert, making their liquidation by any third party inevitable and causing them to lose collateral to the liquidation fee/seizure path. This is a DoS-class analog to the reported "unexpected crash on crafted input": attacker-supplied dust input triggers a state change that causes a hard revert on the victim's subsequent legitimate calls.

### Likelihood Explanation
Fully reachable by an unprivileged EOA: cost is `N × (1 wei dust + gas)` across whitelisted deposit tokens, where N = max tokens per user minus tokens already held. No privileged role, oracle manipulation, or governance action is required. The attack is front-runnable/repeatable — even if the victim frees a slot by emptying a token, the attacker can refill it.

### Recommendation
- In `Pool.addToDepositTokensOfAccount`/`addToDebtTokensOfAccount`, only revert on the cap for operations that decrease health (e.g., skip or cap-check bypass when the caller is `_mint`/`deposit` initiated by the account owner), or
- Make list membership opt-in: track deposit tokens only for `deposit()` calls where `onBehalfOf_ == _msgSender()` or where the account has flagged the token, and/or allow `transfer` receipts without registering the token in the account list (registration lazily on first deposit/health-relevant use), and/or provide a public `removeFromDepositTokensOfAccount` for zero-relevance entries so victims can evict dust slots.

### Proof of Concept
Hardhat/fork sketch:

```ts
// setup: pool with >= MAX_TOKENS_PER_USER distinct DepositTokens, victim with open debt position
const max = await pool.maxTokensPerUser(); // configured cap
// attacker deposits dust of each deposit token on behalf of victim (or transfers 1 wei)
for (const dt of depositTokens.slice(0, max)) {
  await underlying.approve(dt.address, 1);
  await dt.deposit(1, victim.address); // or: dt.connect(attacker).transfer(victim.address, 1)
}
// victim's deposit-token list is now full
await expect(
  someNewDepositToken.connect(victim).deposit(amount, victim.address)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');
// crash victim's collateral price (or wait); liquidation proceeds because victim cannot add collateral
await expect(pool.debtPositionOf(victim.address)).to.eventually.show unhealthy;
await pool.connect(liquidator).liquidate(debtToken.address, victim.address, amt, depositToken.address);
// succeeds — victim suffered liquidation penalty they could not prevent
```

Uncertain/not fully verified (no remaining tool calls): the exact numeric value of `MAX_TOKENS_PER_USER` in `Pool.sol` and whether a public self-removal path exists for evicting dust entries; the finding stands on the confirmed revert (`test/Pool.test.ts:1520`) and the unconditional registration in `DepositToken._transfer`/`_mint`.
