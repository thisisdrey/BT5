### Title
Precompiled Contract Array Extraction Allows Unbounded Allocation Denial-of-Service via Attacker-Controlled Length Word - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The veraPDF bug class is: a parser dispatches attacker-controlled data into an allocation primitive (`array N`) that trusts an attacker-supplied integer as an allocation size with no bound relative to the actual amount of data supplied, letting a single crafted input request a multi-gigabyte allocation and crash the validator. `PrecompiledContracts.extractBytes32Array`, `extractBytesArray`, and `extractSigArray` in java-tron exhibit the same pattern: they read a 32-byte word from attacker-supplied calldata, convert it with `DataWord.intValueSafe()`, and immediately allocate a Java array sized by that untrusted value, with no check that the declared count is consistent with the actual size of the input `data`/`words` buffer. [1](#0-0) 

### Finding Description
`extractBytes32Array` and `extractBytesArray` both take `len = words[offset].intValueSafe()` directly from caller-supplied precompile input and use it to allocate `new byte[len][]` before validating that `len` corresponds to any real amount of remaining data: [1](#0-0) 

`DataWord.intValueSafe()` clamps overflowing values to `Integer.MAX_VALUE` rather than rejecting them, so any attacker who controls the relevant calldata word can force `len` up to `2147483647`: [2](#0-1) 

Allocating `new byte[Integer.MAX_VALUE][]` allocates a reference array (8 bytes/reference on a 64-bit JVM) of roughly 16 GB before a single element is populated and before the subsequent loop even has a chance to throw an `ArrayIndexOutOfBoundsException` for the mismatched `data`/`words` size. This mirrors the veraPDF flaw exactly: an allow-listed/legitimate operation (array construction) is fed a completely attacker-controlled size with no upper bound check tied to the actual payload length, so the DoS is triggered purely from parsing/decoding the call arguments — before any of the "real" per-signature/per-item validation logic runs.

This code path is reached from `PrecompiledContract.execute(byte[] data)`, which is invoked for every `CALL`/`STATICCALL`/`DELEGATECALL` to a precompiled-contract address performed by a smart contract during normal TVM execution: [3](#0-2) 

Unlike the general TVM opcode loop, which is protected by energy metering charged per-opcode and a wall-clock CPU budget (`program.spendEnergy`, `program.checkCPUTimeLimit` in `VM.play`), the energy cost for a precompiled contract call is computed from `getEnergyForData(byte[] data)`, which in the examined contracts (e.g. `Identity`, `Sha256`) is a function of `data.length` — the raw calldata size — not of any length field declared *inside* that calldata. Because `data.length` can be small (e.g., a handful of 32-byte words) while the declared `len` field can independently be set to `Integer.MAX_VALUE`, the energy charged for the call does not scale with the size of the allocation actually attempted, so the allocation happens essentially "for free" from an energy-accounting perspective before the operation can be aborted. [4](#0-3) 

### Impact Explanation
A successful trigger causes an `OutOfMemoryError` inside the node's VM execution thread while processing a single transaction that performs a call to the affected precompiled contract. This is a resource-exhaustion crash reachable by any unprivileged account that can broadcast a transaction invoking a smart contract that in turn calls the vulnerable precompile with crafted calldata (or directly, if the precompile is externally callable), consistent with "node crash or halt" impact criteria. Because there is no `catch (OutOfMemoryError ...)` around this specific allocation path distinct from the generic exception handling in `VM.play`/`VMActuator`, a large `OutOfMemoryError` can destabilize the JVM heap for the whole node process, not just the current transaction, which is more severe than a normal energy-exhaustion revert.

### Likelihood Explanation
Exploitation requires only building calldata that sets the length word at the expected `offset` to a large integer such as `0x7fffffff`, then invoking the affected precompiled contract through a normal transaction — no special privileges, keys, or node cooperation are required. This is directly analogous in complexity to the veraPDF single-payload trigger.

### Recommendation
- Validate the extracted `len` in `extractBytes32Array`/`extractBytesArray`/`extractSigArray` against the actual remaining size of `data`/`words` (e.g., `len <= (words.length - offset - 1)` and a sane absolute maximum) before allocating any array, rejecting the call otherwise.
- Ensure `getEnergyForData` (or an early pre-check) accounts for/rejects any internally declared count fields that would require more memory or elements than the physical `data.length` could represent.
- Consider capping `intValueSafe()`-derived allocation sizes used for array construction throughout `PrecompiledContracts` to a small protocol-defined maximum rather than `Integer.MAX_VALUE`.

### Proof of Concept
1. Identify (or add, if privately deployed) a contract call path that invokes one of the precompiled contracts using `extractBytes32Array`/`extractBytesArray`/`extractSigArray` (functions taking a dynamic array parameter encoded with a leading count word), reachable at a fixed precompile address.
2. Craft the transaction's calldata so that the 32-byte word at the expected `offset` (the "array length" word) is set to `0x7fffffff` while keeping the rest of the calldata minimal (a few bytes total).
3. Broadcast the transaction (or have a caller contract perform the call) so it reaches `PrecompiledContract.execute(data)` and the vulnerable extraction helper.
4. Observe the JVM thread attempt to allocate a `byte[2147483647][]` array (~16 GB reference array on 64-bit JVM), producing an `OutOfMemoryError` inside the FullNode process, before any of the per-item bounds/energy checks execute.

Note: I was unable to fully confirm from the indexed snippets exactly which specific precompiled-contract `execute` method(s) call `extractBytes32Array`/`extractBytesArray`/`extractSigArray` at what calldata `offset`, or the exact `getEnergyForData` implementation for that specific contract (only `Identity`/`Sha256` were retrieved as examples of the general pattern). A Devin session with full repository access would be needed to pinpoint the exact calling contract class and offset layout to build a concrete transaction PoC.

    int len = words[offset].intValueSafe();
    byte[][] bytes32Array = new byte[len][];
    for (int i = 0; i < len; i++) {
      bytes32Array[i] = words[offset + i + 1].getData();
    }
    return bytes32Array;
  }
