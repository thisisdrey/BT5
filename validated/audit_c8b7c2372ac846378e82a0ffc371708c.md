### Title
Access-key nonce reset via DeleteKey+AddKey(same pubkey) enables transaction replay - (File: `runtime/runtime/src/access_keys.rs`)

### Summary
`add_regular_key` unconditionally re-initializes a newly (re)added access key's nonce to `initial_nonce_value(block_height) = (block_height-1) * ACCESS_KEY_NONCE_RANGE_MULTIPLIER`, with no awareness of any nonce the same public key had already reached before being deleted. If an account owner deletes and re-adds the same public key in one transaction after having pushed that key's nonce above the new reset floor, a previously executed, previously signed transaction under the old incarnation of that key becomes valid again and can be replayed.

### Finding Description
`add_regular_key` sets the access key's nonce directly from the block height, independent of prior state: [1](#0-0) 

`initial_nonce_value` is purely a function of block height: [2](#0-1) 

`action_delete_key` fully removes the access key's trie entry (`remove_access_key`), so no memory of the key's prior nonce survives: [3](#0-2) 

Nonce validation in `verify_nonce` only compares the incoming transaction's nonce against the *currently stored* access-key nonce (`effective_nonce`) and a block-height-derived upper bound; it has no knowledge of nonces that were consumed by a since-deleted-and-recreated key: [4](#0-3) 

Exploit flow:
1. At block height H (or H-1), account A signs and submits several transactions with key `pub_k` (FullAccess), advancing the on-chain `access_key.nonce` for `pub_k` to N, where N is close to but below the bound `H * ACCESS_KEY_NONCE_RANGE_MULTIPLIER` (enforced as `NonceTooLarge` in `verify_nonce`).
2. In the same or a later block at height H, A submits one transaction (using a *different* valid nonce) containing `[DeleteKey(pub_k), AddKey(pub_k, FullAccess)]`. `action_delete_key` removes the old access-key trie entry entirely (losing N), then `action_add_key`→`add_regular_key` creates a brand-new entry for `pub_k` with `nonce = (H-1) * ACCESS_KEY_NONCE_RANGE_MULTIPLIER`, which is strictly less than N (since N was already progressed close to the ceiling for height H).
3. A resubmits the old, previously-signed, previously-executed transaction with nonce N (e.g., a Transfer) under `pub_k`. `verify_nonce` compares N against the freshly reset `effective_nonce = (H-1)*1e6` — this passes the "greater than current" check (Monotonic mode) or, if the reset value happens to align, may pass Strict mode as well — and the bound check `N < H*1e6` still holds because it was already true when the tx was first signed. The runtime has no other replay-protection mechanism (no global or per-account executed-tx-hash ledger), so the transaction is accepted a second time and its actions (e.g., Transfer) are executed again.

No existing check (signature, permission, gas, storage-staking, or size-limit) stops this, because the vulnerability is specifically that nonce state for a public key is discarded on `DeleteKey` and not carried forward on re-`AddKey` of the same key.

### Impact Explanation
This allows an account owner to double-execute one of their own previously-signed and already-processed transactions (e.g., replaying a `Transfer` action), producing incorrect double-debit/double-credit balance effects and breaking the value-conservation invariant. This falls under the double-spend/replay category in the bounty's impact list. Scoped impact is limited to the attacker's own account/receiver pair chosen by the replayed transaction (e.g., double-spending a transfer they already sent, potentially to double-pay a counterparty, double-invoke a contract call with side effects, etc.) — the attacker fully controls the replayed content since it's their own previously signed transaction.

### Likelihood Explanation
- Fully attacker-controlled: requires only an ordinary funded account and the ability to sign and submit transactions to any public RPC node.
- Requires no validator, network, or state-sync privileges.
- Preconditions are simple: (1) push the target key's nonce close to the current per-height ceiling via ordinary transactions, (2) submit one `DeleteKey`+`AddKey` transaction re-using the same public key, (3) resubmit the old signed transaction.
- Cost to the attacker is just gas/fees for a handful of transactions; fully repeatable at will and deterministic given the code path shown.

### Recommendation
When re-adding an access key with a public key that previously existed on the account (even after deletion), the new access key's nonce should never be set lower than any nonce that key may have already reached. Concretely, `add_regular_key`/`add_gas_key` should take `max(initial_nonce_value(block_height), <highest nonce previously recorded for this exact public key on this account>)`, or the protocol should retain a tombstone/high-water-mark for deleted public keys (per account) that persists across `DeleteKey`+`AddKey` cycles, so `action_add_key` can enforce nonce monotonicity per public key rather than per currently-live access-key record.

### Proof of Concept
Runtime integration test plan (e.g., extend `runtime/runtime/src/tests/apply.rs` or `integration-tests/src/tests/standard_cases/mod.rs`):
1. Create account A with FullAccess key `pub_k`, funded with balance B.
2. At block height H0, submit and apply several transactions signed by `pub_k` (e.g., no-op or small transfers) so that the stored `access_key.nonce` reaches N, with `(H0-1)*1_000_000 < N < H0*1_000_000` and N noticeably above `(H0-1)*1_000_000`.
3. Sign and execute (at height H0) transaction TX_transfer: `Transfer(amount=X)` from A to B, using nonce N under `pub_k`. Assert it succeeds; assert A's balance decreases by X and B's increases by X.
4. Construct and submit (at height H0, using a fresh valid nonce > N) a transaction with actions `[DeleteKey(pub_k), AddKey(pub_k, FullAccess)]`. Assert it succeeds and that `get_access_key` for `pub_k` now shows nonce `= (H0-1)*1_000_000`.
5. Resubmit the *same signed bytes* as TX_transfer (nonce N, still signed by `pub_k` since it's the same key material) via `verify_and_charge_tx_ephemeral`/full runtime apply. Assert it is accepted (`TxVerdict::Success` / no `InvalidNonce` or `NonceTooLarge` error).
6. Apply it and assert A's balance decreases by X a second time (double-spend), and B's balance increases by X a second time — violating value conservation.

pub(crate) fn initial_nonce_value(block_height: BlockHeight) -> Nonce {
    // Set default nonce for newly created access key to avoid transaction hash collision.
    // See <https://github.com/near/nearcore/issues/3779>.
    (block_height - 1) * near_primitives::account::AccessKey::ACCESS_KEY_NONCE_RANGE_MULTIPLIER
}

/// Verify that the transaction nonce is valid.
fn verify_nonce(
    tx_nonce: Nonce,
    current_nonce: Nonce,
    block_height: Option<BlockHeight>,
    nonce_mode: NonceMode,
) -> Result<(), InvalidTxError> {
    match nonce_mode {
        NonceMode::Monotonic => {
            if tx_nonce <= current_nonce {
                return Err(InvalidTxError::InvalidNonce { tx_nonce, ak_nonce: current_nonce });
            }
        }
        NonceMode::Strict => {
            if !current_nonce.checked_add(1).is_some_and(|expected| tx_nonce == expected) {
                return Err(InvalidTxError::InvalidNonce { tx_nonce, ak_nonce: current_nonce });
            }
        }
    }
    if let Some(height) = block_height {
        let upper_bound = height
            .saturating_mul(near_primitives::account::AccessKey::ACCESS_KEY_NONCE_RANGE_MULTIPLIER);
        if tx_nonce >= upper_bound {
            return Err(InvalidTxError::NonceTooLarge { tx_nonce, upper_bound });
        }
    }
    Ok(())
}
