## Title
Missing StackerDB-instance domain separation in chunk-authentication digest permits cross-contract signed-chunk replay - (File: `libstackerdb/src/libstackerdb.rs`)

## Summary
`SlotMetadata::auth_digest()` (and `StackerDBChunkData::sign`/`verify`/`recover_pk` which are built on it) hashes only `slot_id`, `slot_version`, and `data_hash` [1](#0-0) . It does not bind the signature to the specific StackerDB smart-contract instance (`QualifiedContractIdentifier`), network/chain ID, or any other context. Any node that receives a validly-signed chunk for one StackerDB contract can replay the exact same bytes (slot_id, slot_version, sig, data) into a different StackerDB contract in which the same signing key happens to hold the same slot_id, and the replayed chunk will pass all authentication checks.

## Finding Description
Signature verification for StackerDB chunks is performed by `SlotMetadata::verify()`, which recomputes `auth_digest()` from only `slot_id`, `slot_version`, and `data_hash`, and checks the recovered public key hash against the expected slot owner [2](#0-1) . This same digest is used both when downloading/syncing chunks (`PeerNetwork::validate_received_chunk`) [3](#0-2)  and when storing/replacing chunks in the DB layer (`try_replace_chunk`, exercised in `stackslib/src/net/stackerdb/tests/db.rs` around lines 375-443, which shows `BadSlotSigner` failing only on wrong-key-signed chunks, not on cross-contract replays) [4](#0-3) .

Crucially, none of `smart_contract_id`, `rc_consensus_hash`, `network_id`, or `chain_id` are part of the signed digest. `StackerDBConfig`'s per-contract `signers: Vec<(StacksAddress, u32)>` list assigns slot ownership independently per contract, and it is common for the *same* private key to be assigned the *same* slot_id across multiple StackerDB contract instances — e.g. the `.signers-0-N` / `.signers-1-N` boot contracts that rotate every reward cycle re-use the same signer set membership and often the same slot indexing scheme derived from reward-set ordering [5](#0-4) , and miner slot assignment is similarly index-based per election [6](#0-5) .

Because the signature commits to no contract-instance identifier, a chunk legitimately published (and publicly gossiped/broadcast over the P2P network, see `process_stacker_db_chunks` broadcasting via `StacksMessageType::StackerDBPushChunk`) [7](#0-6)  to StackerDB A is a fully valid signed chunk for StackerDB B, provided the same address owns the same slot_id in B and B's expected version for that slot has not advanced past the replayed `slot_version`. An unprivileged network observer — who needs no private key at all, only a previously observed valid signed chunk — can resubmit it via the unauthenticated HTTP `POST /v2/stackerdb/{contract}/chunks` endpoint (`poststackerdbchunk.rs`) or via the P2P `StackerDBPushChunk`/`StackerDBGetChunkData` unsolicited-push handling path (`handle_unsolicited_StackerDBPushChunk`, exercised in `stackslib/src/net/tests/relay/nakamoto.rs` lines 1224-1247, which show a validly-signed chunk gets buffered/accepted purely on signature+slot-owner match) [8](#0-7) , targeting a different contract_id than the one for which it was originally signed.

This is the same bug class as the external report: `hashAssignment()` omitted `taikoAddress`/`chainId` from its digest, permitting cross-contract/cross-chain replay of an otherwise validly-signed structure. Here, `auth_digest()` similarly omits any StackerDB-instance identifier, breaking the intended equality "signature is valid **for this specific StackerDB contract's slot**" and instead only proving "signature is valid for **some** slot_id/slot_version/data_hash tuple, in any contract where the signer holds that slot."

## Impact Explanation
This allows an unprivileged network participant to relay/forge state in a StackerDB contract that was never intended to receive it: a signer or miner message legitimately signed for one StackerDB instance (e.g., one reward cycle's `.signers-0-N` contract, or a specific tenure/election's miner-message contract) can be replayed into a different, currently-active StackerDB instance where the identical slot_id happens to be owned by the same key. Consumers such as `StackerDBListener` (which parses/acts on signer `BlockResponse`/`BlockAccepted` messages read straight out of StackerDB chunks) [9](#0-8)  would treat this replayed, out-of-context message as freshly authentic. This matches "network-wide propagation of forged data" (chunks are gossiped node-to-node) and can steer signer/miner coordination logic off of the correct state for the active reward cycle/tenure — a High-severity condition per the stated impact classes.

## Likelihood Explanation
Likelihood is moderate: it requires (a) the attacker to have observed a validly-signed chunk (trivial, since all StackerDB chunks are broadcast/gossiped in the clear over P2P and are also queryable via unauthenticated read RPCs), and (b) the same signer address to hold the identical `slot_id` in two different StackerDB contract instances (plausible given index-based slot assignment schemes reused for `.signers-0-N`/`.signers-1-N` reward-cycle rotation and per-tenure miner slots), and (c) the target contract's expected `slot_version` for that slot to not yet exceed the replayed chunk's version. No secret key or admin role is needed by the attacker.

## Recommendation
Include a domain-separation tag in `SlotMetadata::auth_digest()` — at minimum the `QualifiedContractIdentifier` of the StackerDB contract (and ideally the network/chain ID) — so that a signature is cryptographically bound to one specific StackerDB instance and cannot be replayed into another. This mirrors the report's remediation of including `taikoAddress`/`chainId` in the EIP-712-style digest.

## Proof of Concept
1. Configure two StackerDB contracts, `A` and `B`, such that address `H` (controlled by key `K`) is the assigned signer for `slot_id = 5` in both `A` and `B` (a realistic scenario for reward-cycle-rotated `.signers-0-N`/`.signers-1-N` contracts, or per-election miner slots, using index-based slot assignment).
2. The legitimate holder of `K` signs and publishes `chunk = {slot_id:5, slot_version:1, sig, data}` to contract `A` (e.g., a `BlockResponse` signer message). This chunk propagates over P2P (`StackerDBPushChunk`) and can be read by any observer.
3. An attacker (no key required) captures this `chunk` bytes-for-bytes and submits it via `POST /v2/stackerdb/B/chunks` (`poststackerdbchunk.rs`) or replays it as an unsolicited `StackerDBPushChunk` for contract `B`.
4. `validate_received_chunk`/`try_replace_chunk` for contract `B` looks up slot 5's signer for `B` (also `H`), recomputes `auth_digest()` from `slot_id=5, slot_version=1, data_hash`, and successfully verifies the identical signature — because the digest never included contract `A`'s identifier. The chunk is accepted and stored in `B`, and re-broadcast to `B`'s neighbors, despite never having been signed for `B`.

    /// Get the digest to sign that authenticates this chunk data and metadata
    fn auth_digest(&self) -> Sha512Trunc256Sum {
        let mut hasher = Sha512_256::new();
        hasher.update(self.slot_id.to_be_bytes());
        hasher.update(self.slot_version.to_be_bytes());
        hasher.update(self.data_hash.0);
        Sha512Trunc256Sum::from_hasher(hasher)
    }

    pub fn verify(&self, principal: &StacksAddress) -> Result<bool, Error> {
        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )
        .map_err(|ve| Error::VerifyingError(ve.to_string()))?;

        let pubkh = Hash160::from_node_public_key(&pubk);
        Ok(pubkh == *principal.bytes())
    }
