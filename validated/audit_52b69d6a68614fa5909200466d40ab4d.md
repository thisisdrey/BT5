### Title
`Tips` storage in the Snowbridge inbound queue records relayer rewards without any on-chain escrow of the tipped value - ([File: bridges/snowbridge/pallets/inbound-queue-v2/src/lib.rs])

### Summary
`pallet_inbound_queue_v2` lets any caller add a "tip" for a not-yet-processed nonce via the `AddTip` trait implementation, which only mutates a `Tips<T>` map entry [1](#0-0) . This tip amount is never itself escrowed, held, or reconciled against any actual balance inside this pallet — it is a bare `u128` counter. When the message is later processed, the counter is read and unconditionally folded into the relayer's payable reward via `register_reward`, which is the entry point into the real payout machinery (`pallet-bridge-relayers` / `RewardPayment`) that eventually mints/transfers real WETH out of AssetHub/BridgeHub-held funds [2](#0-1) . This is structurally the same defect as the `SmoothlyPool` report: a value that is supposed to represent "money already collected on-chain" is tracked purely as an unbacked counter, with no mapping/hold that ties the recorded amount to an actual balance debit at the point it is recorded.

### Finding Description
`Tips::<T>` is a `StorageMap<u64, u128>` keyed by message nonce, and `AddTip::add_tip` simply does:
```
ensure!(amount > 0, AddTipError::AmountZero);
ensure!(!Nonce::<T>::get(nonce.into()), AddTipError::NonceConsumed);
Tips::<T>::mutate(nonce, |tip| { *tip = Some(tip.unwrap_or_default().saturating_add(amount)); });
``` [1](#0-0) 

Nothing here withdraws, reserves, or holds `amount` from any account inside `pallet_inbound_queue_v2`. The pallet's only invariant is "nonce not yet consumed" — there is no check that the caller (or any account) actually possesses/locked `amount` in a form that can back the eventual payout. The `Tips` value is purely a promise recorded in this pallet's own storage.

That promise becomes real money later: in `process_message`, the tip is taken out of storage and added to `relayer_fee`, then handed to `T::RewardPayment::register_reward`:
```
let tip = Tips::<T>::take(nonce).unwrap_or_default();
let total_tip = relayer_fee.saturating_add(tip);
if total_tip > 0 {
    T::RewardPayment::register_reward(&relayer, T::DefaultRewardKind::get(), total_tip);
}
``` [2](#0-1) 

`register_reward` credits `pallet_bridge_relayers::RelayerRewards` [3](#0-2) , which is later paid out from the AssetHub-side account via `BridgeRewardPayer::pay_reward` → `PayAccountOnLocation`, minting/transferring real `ForeignAssets` (WETH) to the relayer's chosen beneficiary [4](#0-3) .

The gap mirrors the `SmoothlyPool` finding exactly: the pallet that records the obligation (`Tips` map / `STAKE_FEE` deposit) has no coupling to an actual escrowed balance at the point of recording, and the pallet that pays it out (`register_reward`/`claim_rewards_to`) trusts that recorded value unconditionally. Any component that is permitted to call `AddTip::add_tip` (e.g. the `system-v2`/`system-frontend` pallets, which expose `add_tip` extrinsics per the grep results) becomes the sole safeguard; if that caller's own fund-collection step (e.g. an XCM `WithdrawAsset`/`PayFees` amount, or a dry-run-estimated fee) ever under-collects, double counts, or is bypassed/mis-wired relative to the `amount` passed into `AddTip::add_tip`, the inbound-queue-v2 pallet itself provides no defense — it will happily record and later pay out a tip that was never actually backed by transferred value.

### Impact Explanation
If the tip value recorded via `add_tip` can diverge from an actual balance debit (e.g. a caller pallet allows tipping without atomically taking a matching hold, or a governance/parameter mismatch lets the recorded amount exceed what was collected), the bridge ends up paying out WETH rewards that were never funded — a direct "theft or unbacked mint" style impact on the AssetHub/BridgeHub sovereign funds backing Snowbridge rewards, consistent with the "unbacked mint or unlock" and "theft" categories in the impact gate.

### Likelihood Explanation
The likelihood hinges entirely on whether every caller of `AddTip::add_tip` (system-v2 / system-frontend pallets) enforces an atomic, exact-amount fund hold before invoking `add_tip`. Within `pallet_inbound_queue_v2` itself there is no such enforcement — the pallet trusts its caller completely, exactly as `SmoothlyPool` trusted its off-chain registration flow. This is a real gap in the pallet's own invariants regardless of whether the current call sites happen to be correctly wired, because no on-chain assertion ties `Tips` values to escrowed balance inside this pallet or in `pallet_bridge_relayers`.

### Recommendation
Add an explicit balance-backing check for `Tips`: either (a) require `AddTip::add_tip` to take a `Currency`/`fungibles` hold of exactly `amount` from the calling origin's account at the point of recording, storing the holder so it can be released/transferred atomically during `process_message`, or (b) enforce a pallet-level invariant (analogous to `do_try_state` checks used elsewhere, e.g. `substrate/frame/nomination-pools/src/lib.rs` `do_try_state`) that reconciles `Tips` totals against a tracked escrow balance before allowing `register_reward` to be called with the tip component.

### Proof of Concept
1. A caller pallet (e.g. `system-v2`) invokes `AddTip::add_tip(nonce, amount)` for a large `amount` without having actually locked/transferred `amount` in real WETH/ETH-backed funds (this can happen if the fee/tip amount used for the XCM `PayFees`/`WithdrawAsset` instruction sent to Ethereum differs from the `amount` passed to `add_tip`, or if the calling extrinsic has a rounding/estimation bug).
2. `Tips::<T>::mutate(nonce, ...)` records the inflated amount with no corresponding balance check [5](#0-4) .
3. When the relayer eventually calls `submit`/`process_message` for that nonce, `total_tip = relayer_fee + tip` is registered as a real reward for the relayer [6](#0-5) .
4. The relayer calls `claim_rewards_to`, and `PayAccountOnLocation`/`ForeignAssets::Deposited` mints/transfers real WETH to the relayer's beneficiary on AssetHub, exceeding what was actually collected [7](#0-6) .

Note: I was unable to inspect the exact fund-collection code inside `system-v2`/`system-frontend`'s `add_tip` extrinsic before running out of tool calls, so whether an actual exploitable mismatch currently exists in the wired call sites is not fully confirmed — the structural gap is in `pallet_inbound_queue_v2` itself, which provides no independent guarantee that `Tips` values are balance-backed.

	impl<T: Config> AddTip for Pallet<T> {
		fn add_tip(nonce: u64, amount: u128) -> Result<(), AddTipError> {
			ensure!(amount > 0, AddTipError::AmountZero);
			// If the nonce is already processed, return an error
			ensure!(!Nonce::<T>::get(nonce.into()), AddTipError::NonceConsumed);
			// Otherwise add the tip.
			Tips::<T>::mutate(nonce, |tip| {
				*tip = Some(tip.unwrap_or_default().saturating_add(amount));
			});
			return Ok(());
		}
	}
