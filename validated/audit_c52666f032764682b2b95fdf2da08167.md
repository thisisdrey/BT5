### Title
Attacker can fill a victim's per-account token list to `MAX_TOKENS_PER_USER` via dust `DepositToken` transfers, permanently reverting all future collateral additions for the victim - ([File: contracts/Pool.sol])

### Summary
`Pool` enforces `MAX_TOKENS_PER_USER = 30` across `debtTokensOfAccount + depositTokensOfAccount`. `DepositToken._transfer` (and `_mint`) calls `pool.addToDepositTokensOfAccount(recipient_)` whenever the recipient's balance goes from 0 to non-zero — and `transfer`/`transferFrom` only check that the **sender's** balance is unlocked. An unprivileged attacker can dust-transfer 1 wei of every distinct `DepositToken` to a victim, silently consuming their token-list slots. Once the combined list reaches 30, any subsequent `_mint`/`_transfer` to the victim for a *new* token reverts with `UserReachedMaxTokens`, and the revert propagates through `deposit`, `transfer`, `NativeTokenGateway.deposit`, `SmartFarmingManager` flows, and even `seize` during liquidations.

### Finding Description
- `DepositToken._transfer` credits the recipient and then calls `pool.addToDepositTokensOfAccount(recipient_)` on a zero-to-nonzero transition: [1](#0-0) 
- `DepositToken.transfer`/`transferFrom` only verify the sender's unlocked balance via `_revertIfLocked`; the recipient is never consulted: [2](#0-1) 
- `Pool.addToDepositTokensOfAccount` enforces `onlyIfAdditionWillNotReachMaxTokens`, which reverts once `debtTokens + depositTokens >= 30`, and the revert bubbles up and undoes the balance write: [3](#0-2) [4](#0-3) 
- `DepositToken.deposit(..., onBehalfOf_)` lets anyone mint to an arbitrary beneficiary, so an attacker can also *front-run* a victim's first deposit of any new collateral type to force the add and revert: [5](#0-4) 
- The same happens on mint (`_mint` → `addToDepositTokensOfAccount`), so every new-collateral deposit path is blocked: [6](#0-5) 

This mirrors CVE-2019-19332's bug class: a fixed-size per-account structure whose bounds enforcement turns an attacker-controlled write into a liveness/crash condition. Here the "out of bounds" write reverts instead of corrupting memory, but the effect is the same — an unprivileged request forces a state where legitimate operations cannot proceed.

### Impact Explanation
- **Temporary freezing / forced liquidation:** a victim with an open debt position who has been griefed cannot deposit *any new* collateral type to restore health. If the market moves against them, every rescue path (`deposit`, `NativeTokenGateway.deposit`, `SmartFarmingManager.leverage` minting a new deposit token) reverts, and they are force-liquidated when they could have topped up.
- **Liquidation proceeds griefing:** `Pool.liquidate` → `DepositToken.seize` → `_transfer` → `addToDepositTokensOfAccount(liquidator)`. Filling a known/active liquidator's list (or a victim's list for seize-into-account flows) causes liquidations to revert for tokens not already in their set.
- **Exit path preserved:** `withdraw` burns and removes tokens, so existing collateral is not permanently locked — the impact is temporary freezing plus forced liquidation risk, matching accepted impact classes.

### Likelihood Explanation
- Cost to the attacker is only gas plus dust balances of each distinct `DepositToken` in the pool; no privilege, no oracle manipulation, no governance.
- Feasibility depends on the deployed pool: `depositTokensOfAccount + debtTokensOfAccount` must reach 30, and debt tokens cannot be dust-transferred (DebtToken transfers are pool-restricted), so the attack requires roughly 30 registered deposit tokens in the pool — achievable on pools with many collaterals, not on small pools. Front-running a single first-time deposit of a new token, however, works regardless of pool size: an attacker can deposit 1 wei of the new `DepositToken` to the victim just before the victim's own deposit, and the victim's slot count is permanently consumed.
- Reproduction is straightforward in Hardhat/Foundry: deploy pool + ≥2 DepositTokens, open a victim position, attacker dust-transfers/deposits-on-behalf until the list is full, then `vm.expectRevert(UserReachedMaxTokens)` on the victim's next deposit.

### Recommendation
- Do not add tokens to a victim's per-account list on inbound `transfer`/`seize`/`deposit-on-behalf` without the recipient's consent; alternatively, make `addToDepositTokensOfAccount` non-reverting on overflow (return silently) so the balance write succeeds and the collateral simply isn't counted — though that has its own accounting trade-offs.
- Safer: require `recipient_ == _msgSender()` or an explicit opt-in for first-time receipt, or remove the `MAX_TOKENS_PER_USER` cap and iterate only over tokens with non-zero balances derived from the global `depositTokens` set.

### Proof of Concept
```solidity
// SPDX-License-Identifier: MIT
pragma solidity 0.8.24;

import "forge-std/Test.sol";
import {Pool} from "contracts/Pool.sol";
import {DepositToken} from "contracts/DepositToken.sol";
import {IERC20} from "contracts/dependencies/openzeppelin/token/ERC20/IERC20.sol";

contract MaxTokensGriefingTest is Test {
    Pool pool;
    DepositToken[] dts;     // deposit tokens registered in the pool
    address victim = address(0xV1C);
    address attacker = address(0xA77);

    function setUp() public {
        // ... standard fixture: deploy Pool via proxy, PoolRegistry, FeeProvider,
        // MasterOracleMock, Treasury; register N DepositTokens in the pool
        // (test/Pool.test.ts shows addDepositToken + addToDepositTokensOfAccount flow)
    }

    function test_FillVictimTokenList() public {
        // 1. Attacker deposits dust into each DepositToken on behalf of victim,
        //    or transfers 1 wei — each zero->nonzero transition calls
        //    pool.addToDepositTokensOfAccount(victim)
        for (uint256 i; i < dts.length; ++i) {
            IERC20 underlying = dts[i].underlying();
            deal(address(underlying), attacker, 1e18);
            vm.startPrank(attacker);
            underlying.approve(address(dts[i]), 1e18);
            dts[i].deposit(1, victim);          // _mint -> addToDepositTokensOfAccount(victim)
            vm.stopPrank();
        }

        // list is now at cap: debtTokensOfAccount(victim) + depositTokensOfAccount(victim) == 30
        assertEq(pool.getDepositTokensOfAccount(victim).length, 30);

        // 2. Victim tries to deposit a *new* collateral type (msdNEW) — reverts
        DepositToken dNew = dts[0]; // any token not yet in victim's list in a partial-fill variant
        IERC20 underlyingNew = dNew.underlying();
        deal(address(underlyingNew), victim, 100e18);
        vm.startPrank(victim);
        underlyingNew.approve(address(dNew), 100e18);
        vm.expectRevert(); // UserReachedMaxTokens from Pool.addToDepositTokensOfAccount
        dNew.deposit(100e18, victim);
        vm.stopPrank();
    }

    function test_LiquidationSeizeReverts() public {
        // After filling `victim`'s list: a liquidation that seizes into an
        // account whose list is full, or any seize path calling
        // DepositToken.seize -> _transfer -> addToDepositTokensOfAccount,
        // reverts, blocking the liquidation.
    }
}
```

Key assertion: `deposit` → `_mint` → `pool.addToDepositTokensOfAccount(victim)` reverts once `debtTokensOfAccount.length(victim) + depositTokensOfAccount.length(victim) >= 30`, and the whole transaction (including the treasury pull of underlying) is rolled back.

**Caveats:** I did not verify the exact number of registered `DepositToken`s on the deployed pools — on pools with fewer than ~30 deposit tokens the full-fill variant is infeasible, though the front-run-a-new-token variant still applies. I also did not fully trace `DebtToken` transfer restrictions; if debt tokens are transferable, the attack becomes easier.
