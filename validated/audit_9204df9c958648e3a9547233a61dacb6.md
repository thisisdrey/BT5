### Title
Unthrottled repair-ping verification/signing amplification in `ShredFetchStage::modify_packets` via `ServeRepair::handle_repair_response_pings` - ([File: core/src/shred_fetch_stage.rs])

### Summary
Every packet received on the repair-response UDP socket that happens to match the fixed size `REPAIR_RESPONSE_SERIALIZED_PING_BYTES` is unconditionally deserialized and passed through `Ping::verify()` (an Ed25519 verification) inside `ServeRepair::handle_repair_response_pings`, with no per-source or global rate limiter guarding this specific code path. Because an attacker can trivially construct a self-signed `RepairResponse::Ping` (they control the embedded keypair), `ping.verify()` always succeeds for their own crafted packets, which then forces the node to sign a `Pong` with its own identity keypair and `batch_send` it back — turning cheap attacker-side UDP sends into leader-side signature-verify + signature-generate + socket-write work with no throttle specific to this path.

### Finding Description
In `core/src/shred_fetch_stage.rs`, `ShredFetchStage::modify_packets` pulls every `PacketBatch` off the repair socket's receiver and, for repair contexts, immediately calls: [1](#0-0) 

`ServeRepair::handle_repair_response_pings` then iterates every packet in the batch, and for any packet whose size equals `REPAIR_RESPONSE_SERIALIZED_PING_BYTES` it deserializes it and calls `ping.verify()`: [2](#0-1) 

If `verify()` succeeds, the code builds a `Pong` (which involves the node signing with its identity `keypair`) and queues it for `batch_send` on the repair socket: [3](#0-2) 

`Ping<N>` is a self-contained challenge/response structure where the sender supplies their own keypair and signs their own payload (see `gossip/src/ping_pong.rs`); `verify()` only checks internal consistency (that the embedded pubkey signed the embedded data), not that the ping came from a real repair peer the node previously contacted. This means any unprivileged remote host can generate an unlimited number of valid, self-signed `Ping` packets offline (cheap Ed25519 signing) and blast them at the repair socket's known UDP address (advertised via `ContactInfo`/gossip). Each such packet, once received, forces the leader to perform an Ed25519 verify, an Ed25519 sign, and a socket write — with no rate limiter specific to `handle_repair_response_pings`.

By contrast, sibling repair-response handlers in this codebase do employ throttling before doing this same class of work: `ancestor_hashes_service.rs`'s `process_new_packets_from_channel` and `block_id_repair_service.rs`'s `process_responses` both use `DynamicPacketToProcessThreshold`/`SOFT_RECEIVE_CAP` to drop excess packets under load before processing pings: [4](#0-3) [5](#0-4) 

Likewise, the *request*-side listener `ServeRepair::run_listen` applies a `TokenBucket` data budget before doing similar sign/verify/serve work: [6](#0-5) 

`handle_repair_response_pings`, invoked from `ShredFetchStage::modify_packets`, has no analogous throttle — it processes every ping-shaped packet in every batch pulled from the socket, bounded only by the streamer's generic receive/coalesce loop (5ms coalescing, bounded channel size `SHRED_FETCH_CHANNEL_SIZE`), which limits queue depth but not the CPU cost incurred per unit of incoming packet rate.

### Impact Explanation
An unstaked, unprivileged remote sender can flood the leader's repair UDP socket with self-crafted, validly-signed ping packets, each of which is guaranteed to pass `ping.verify()` and trigger an identity-keypair `Pong::new` signature plus a `batch_send` socket write on the leader, with no rate limit specific to this handler. This is a CPU/signature-generation and socket-write amplification vector: the attacker's cost (crafting/signing a tiny packet) is far lower than the leader's cost (verify + sign + I/O) and there is no fee or stake gate on this path at all. This falls under "grossly underpriced pre-fee work" / sigverify-adjacent amplification for unstaked senders.

### Likelihood Explanation
Feasible and repeatable: the repair socket address is publicly discoverable via gossip `ContactInfo`, no stake or account funding is required, and generating valid self-signed `Ping` packets requires only a local keypair (client-side signing is cheap, achievable at very high rates). No existing guard in `handle_repair_response_pings` or in `ShredFetchStage::modify_packets` restricts the rate of ping-shaped packets processed per unit time, unlike comparable response-processing paths elsewhere in the repair subsystem.

### Recommendation
Add a throttle (e.g., a `DynamicPacketToProcessThreshold`/token-bucket similar to `block_id_repair_service.rs`'s `SOFT_RECEIVE_CAP`/throttle or `serve_repair.rs`'s `TokenBucket`) around ping processing in `handle_repair_response_pings` or upstream in `ShredFetchStage::modify_packets`, bounding the number of pings verified/signed/sent per unit time regardless of inbound packet volume, and/or require that pongs only be generated for pings matching an outstanding/expected challenge (as `block_id_repair_service::process_block_id_repair_ping_response` already does via `state.is_expected_ping_response`) rather than any self-consistent signature.

### Proof of Concept
Rust integration test plan (extends existing test style in `core/src/repair/serve_repair.rs` tests):
```rust
#[test]
fn test_handle_repair_response_pings_unbounded_signing_cost() {
    let keypair = Keypair::new();
    let repair_socket = test_udp_socket();
    let mut stats = ShredFetchStats::default();

    // Attacker generates N self-signed pings with distinct throwaway keypairs.
    const N: usize = 100_000;
    let mut packet_batch = PacketBatch::with_capacity(N);
    for _ in 0..N {
        let attacker_kp = Keypair::new();
        let ping = Ping::new([0u8; 32], &attacker_kp); // attacker-controlled, always verifies
        let response = RepairResponse::Ping(ping);
        let data = wincode::serialize(&response).unwrap();
        packet_batch.push(make_packet(&data)); // size == REPAIR_RESPONSE_SERIALIZED_PING_BYTES
    }

    let start = Instant::now();
    ServeRepair::handle_repair_response_pings(&repair_socket, &keypair, &mut packet_batch, &mut stats);
    let elapsed = start.elapsed();

    // Every packet triggers a verify + sign + send; no throttling drops any of them.
    assert_eq!(stats.ping_count, N as u64);
    // Assert this scales linearly with N with no cap (demonstrating unbounded cost),
    // contrasted against a bounded expectation, e.g. elapsed should NOT be
    // proportional to N once a rate limit is introduced.
    println!("processed {N} forged pings in {elapsed:?}");
}
```
Expected result today: `stats.ping_count == N` for arbitrarily large `N`, with signing/socket-write work scaling linearly and unboundedly with attacker-controlled packet rate, confirming absence of a path-specific rate limit. After remediation, the same test should show a fixed upper bound (`stats.ping_count` capped) invariant of `N`.
