Audit Report

## Title
`harvest_rewards` never persists the recomputed `PoolInfo` (`reward_per_token_stored`, `last_update_block`), causing stale pool reward-accrual state - (File: `substrate/frame/asset-rewards/src/lib.rs`)

## Summary
`Pallet::harvest_rewards` computes an updated `pool_info` via `Self::update_pool_and_staker_rewards`, which advances `reward_per_token_stored` and `last_update_block`, but only persists the recomputed `staker_info` (`PoolStakers::<T>::insert`/`remove`) — it never calls `Pools::<T>::insert(pool_id, pool_info)`. This is confirmed by direct code inspection: `stake` and `unstake` both explicitly persist the recomputed pool state with `Pools::<T>::insert(pool_id, pool_info)`, while `harvest_rewards` uses the recomputed `pool_info` only locally for `T::Assets::transfer` and discards it. [1](#0-0) [2](#0-1) [3](#0-2) 

## Finding Description
`update_pool_and_staker_rewards` is documented as side-effect free — the caller is responsible for persisting storage changes. [4](#0-3)  `stake` and `unstake` correctly persist the recomputed `pool_info` after mutating `total_tokens_staked`, keeping `Pools::<T>::get(pool_id).last_update_block` and `.reward_per_token_stored` in sync. [5](#0-4) [6](#0-5) 

`harvest_rewards`, however, computes `(pool_info, staker_info)` from `update_pool_and_staker_rewards`, uses `pool_info.reward_asset_id`/`.account` only for the transfer, and then returns after updating `PoolStakers` — `Pools::<T>` is never rewritten. [3](#0-2)  Consequently the on-chain `Pools::<T>::get(pool_id).last_update_block` and `.reward_per_token_stored` remain at their pre-harvest values. Since `reward_per_token` computes accrual as `reward_per_token_stored + reward_rate_per_block * (now - last_update_block) * PRECISION / total_tokens_staked`, using the stale `last_update_block` on the next `stake`/`unstake`/`harvest_rewards` call re-derives accrual for the whole stale interval against whatever `total_tokens_staked` applies at that later call. [7](#0-6) 

## Impact Explanation
If `total_tokens_staked` changes between an un-persisted `harvest_rewards` and the pool's next persisting operation, the reward-per-token accrued over the stale window is computed against the wrong denominator for part of that interval, misallocating reward-asset funds among stakers of the same pool (some over-credited, some under-credited) relative to their true time-weighted stake. This is a fund-accounting/value-conservation defect within a single pallet's shared reward pool, reachable purely through permissionless, unprivileged extrinsics (`stake`, `unstake`, `harvest_rewards`), consistent with "runtime bugs that compromise intended behavior" for value conservation in pools per the impact gate.

## Likelihood Explanation
High. `harvest_rewards` is callable by any signed staker (`ensure_signed`), and ordinary pool activity — any other staker calling `stake` or `unstake` on the same pool after a harvest and before the next pool-persisting call — reliably triggers the stale-state read. No adversarial timing, privileged role, or race condition beyond normal usage patterns is required, and the bug is deterministically reproducible by inspecting the code path.

## Recommendation
Persist the recomputed pool state in `harvest_rewards`, mirroring `stake`/`unstake`, by adding `Pools::<T>::insert(pool_id, pool_info);` immediately after computing `(pool_info, mut staker_info) = Self::update_pool_and_staker_rewards(...)` (or after the transfer, before returning `Ok(())`).

## Proof of Concept
1. Pool `P` has stakers A and B each with 1000 staked tokens; `reward_rate_per_block = R`; `Pools::<T>::get(P).last_update_block = N0`.
2. At block `N`, A calls `harvest_rewards`. In-memory `pool_info.last_update_block`/`.reward_per_token_stored` advance to reflect block `N`, and A's rewards are correctly transferred — but storage `Pools::<T>::get(P)` still shows `last_update_block = N0`.
3. At block `N+1`, B calls `stake` to add 1000 tokens. `stake` reads the stale `Pools::<T>::get(P)` (`last_update_block = N0`) and computes `reward_per_token` accrual for the whole interval `[N0, N+1]` using `total_tokens_staked = 1000` (the pre-increase value) for that entire span, rather than correctly splitting `[N0, N]` and `[N, N+1]`.
4. This can be encoded as a Rust unit/integration test in the pallet's mock runtime: call `harvest_rewards`, advance one block, call `stake` from a second account, then assert that `Pools::<T>::get(P).last_update_block` and `.reward_per_token_stored` do not match the values that were computed and used inside the just-completed `harvest_rewards` call, demonstrating the storage/state divergence.

		///
		/// Should be called prior to any operation involving a staker.
		///
		/// Returns the updated pool and staker info.
		///
		/// NOTE: this function has no side-effects. Side-effects such as storage modifications are
		/// the responsibility of the caller.
		pub fn update_pool_and_staker_rewards(
			pool_info: &PoolInfoFor<T>,
			staker_info: &PoolStakerInfo<T::Balance>,
		) -> Result<(PoolInfoFor<T>, PoolStakerInfo<T::Balance>), DispatchError> {
			let reward_per_token = Self::reward_per_token(&pool_info)?;
			let pool_info = Self::update_pool_rewards(pool_info, reward_per_token)?;

			let mut new_staker_info = staker_info.clone();
			new_staker_info.rewards = Self::derive_rewards(&staker_info, &reward_per_token)?;
			new_staker_info.reward_per_token_paid = pool_info.reward_per_token_stored;
			return Ok((pool_info, new_staker_info));
		}

		/// Derives the current reward per token for this pool.
		pub(super) fn reward_per_token(
			pool_info: &PoolInfoFor<T>,
		) -> Result<T::Balance, DispatchError> {
			if pool_info.total_tokens_staked.is_zero() {
				return Ok(pool_info.reward_per_token_stored);
			}

			let rewardable_blocks_elapsed: u32 =
				match Self::last_block_reward_applicable(pool_info.expiry_block)
					.ensure_sub(pool_info.last_update_block)?
					.try_into()
				{
					Ok(b) => b,
					Err(_) => return Err(Error::<T>::BlockNumberConversionError.into()),
				};

			Ok(pool_info.reward_per_token_stored.ensure_add(
				pool_info
					.reward_rate_per_block
					.ensure_mul(rewardable_blocks_elapsed.into())?
					.ensure_mul(PRECISION_SCALING_FACTOR.into())?
					.ensure_div(pool_info.total_tokens_staked)?,
			)?)
		}
