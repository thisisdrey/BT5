### Title
Unprivileged dust-transfer griefing fills a victim's per-account token list to `MAX_TOKENS_PER_USER`, reverting all deposits, issues, seizures and transfers of new token types for that account - (File: contracts/Pool.sol, contracts/DepositToken.sol)

### Summary
The FFmpeg CVE is an out-of-bounds read triggered by attacker-crafted input parameters causing a denial of service. The Metronome analog is attacker-controlled growth of the per-account `MappedEnumerableSet` lists: every deposit-token mint/transfer to a fresh holder pushes an entry into `depositTokensOfAccount`/`debtTokensOfAccount`, and `Pool.onlyIfAdditionWillNotReachMaxTokens` hard-reverts once the combined count hits `MAX_TOKENS_PER_USER`. An unprivileged attacker can deposit dust into each registered collateral and transfer 1 wei of each `DepositToken` to a victim, permanently occupying list slots and causing every subsequent first-time token interaction for that victim to revert — a state-level DoS analogous to the OOB-read crash.

### Finding Description
In `Pool.sol` the guard is:

```solidity
modifier onlyIfAdditionWillNotReachMaxTokens(address account_) {
    if (debtTokensOfAccount.length(account_) + depositTokensOfAccount.length(account_) >= MAX_TOKENS_PER_USER) {
        revert UserReachedMaxTokens();
    }
    _;
}
``` [1](#0-0) 

`addToDepositTokensOfAccount` is called from `DepositToken._transfer` whenever the recipient's prior balance was zero:

```solidity
if (_recipientBalanceBefore == 0 && amount_ > 0) {
    pool.addToDepositTokensOfAccount(recipient_);
}
``` [2](#0-1) 

and from `_mint` on first deposit. The same pattern exists for `DebtToken._mint` → `addToDebtTokensOfAccount`. Because `transfer`/`transferFrom` are permissionless ERC20-style entry points on `DepositToken` (`transfer` only checks `_revertIfLocked` on the *sender*, there is no opt-in on the recipient), anyone can force entries into a victim's list with dust amounts.

Once the victim's combined list reaches `MAX_TOKENS_PER_USER`, every path that adds a *new* token reverts:
- `DepositToken.deposit`/`_mint` into any collateral the victim doesn't already hold → `UserReachedMaxTokens`
- `DepositToken.transfer`/`transferFrom`/`seize` to the victim for a token they don't hold → reverts (this also makes the victim unseizable for collateral types a liquidator would route through, though liquidator-side seizure goes to the liquidator's own list)
- `DebtToken` issuance of a new synth for the victim → reverts, blocking new borrowing [3](#0-2) [4](#0-3) 

### Impact Explanation
Temporary freezing of funds / liveness degradation. The victim cannot open positions in new collateral types, cannot borrow new synthetic assets, and cannot receive transfers of deposit tokens they don't already hold, until they manually clean up by transferring/withdrawing each dust position to zero (each `balanceOf == 0` triggers `removeFromDepositTokensOfAccount`). Withdrawals of already-held collateral and repayments still work, so the freeze is temporary and partial — matching the CVE's medium-severity DoS profile rather than theft or permanent loss. The attacker's cost is bounded by deposit fees and the number of registered deposit tokens; on deployed pools with several collaterals this is cheap.

### Likelihood Explanation
Fully permissionless: the attacker needs only to deposit a minimal amount of each underlying collateral (e.g., via `NativeTokenGateway` or direct `deposit`) and call `transfer(victim, 1)` on each `DepositToken`. No privileged role, no oracle manipulation, no flash loan required. Repeated whenever the victim cleans up. Limitations: the victim can self-recover by zeroing dust entries, and existing positions are unaffected, which keeps severity at medium/low rather than high.

### Recommendation
- Make list additions opt-in or bounded per direction: e.g., only add on `deposit`/mint, not on `transfer`/`seize`, or skip `addToDepositTokensOfAccount` when the amount is below a dust threshold.
- Alternatively track "position-relevant" tokens only (balance above a minimum) or lazily iterate `balanceOf` instead of maintaining an enumerable per-account set.
- If the list must stay, emit/cap per-token dust and document the griefing vector so monitoring can flag list saturation.

### Proof of Concept
Hardhat sketch (fork or fixture with a deployed `Pool` + ≥2 registered `DepositToken`s):

```typescript
// attacker deposits dust in every collateral and ships 1 wei of each msdToken to victim
for (const dt of depositTokens) {
  const underlying = await ethers.getContractAt('ERC20Mock', await dt.underlying())
  await underlying.mint(attacker.address, 10)
  await underlying.connect(attacker).approve(dt.address, 10)
  await dt.connect(attacker).deposit(10, attacker.address)
  await dt.connect(attacker).transfer(victim.address, 1) // adds entry to victim's list
}

// victim's list is now at MAX_TOKENS_PER_USER
// any first-time deposit of a collateral the victim doesn't hold reverts
const newDt = depositTokensNotYetHeld // or a newly added deposit token
await expect(newDt.connect(victim).deposit(amount, victim.address))
  .to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens')

// receiving any new deposit token also reverts
await expect(otherDt.connect(attacker).transfer(victim.address, 1))
  .to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens')
```

Reproducible entirely with public entry points (`deposit`, `transfer`) — no privileged calls. (Confidence note: I verified the guard, the add/remove hooks, and that `transfer` performs no recipient opt-in; I did not execute the PoC, and exact `MAX_TOKENS_PER_USER` value and the registered-collateral count on each deployment determine the attacker's cost.)
