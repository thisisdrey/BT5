## No vulnerability found for this question.

**Analysis:**

The premise is factually incorrect: `SignedPayload::hash()` for `SignedTonConnectPayload` does **not** call `.ok()?` — it calls `.expect("ton-connect hash")` [1](#0-0) . The `.ok()?` pattern the question describes only exists in the low-level `TonConnectCellMessage::hash()` helper [2](#0-1) , which is a private detail used by `TonConnectPayload::try_prehash()` [3](#0-2) .

Critically, `TonConnect::verify()` and `TonConnectPayload`'s `Payload::hash()` both go through the **same** `try_prehash()` call, and `verify()` explicitly returns `false` (not a panic, not silent success) when `try_prehash()` returns `None`: [4](#0-3) 

In `Engine::execute_signed_intent`, `signed.verify()` is invoked and checked **before** `signed.hash()` is ever called: [5](#0-4) 

So if the Cell serialization fails (`store()` returns `Err`), `try_prehash()` returns `None`, `verify()` returns `false`, and `signed.verify().ok_or(DefuseError::InvalidSignature)?` rejects the request at line 44 — execution never reaches line 47's `signed.hash()` call, so there is no scenario where verification "silently succeeds" with a bad/`None` hash. Both functions are driven by the identical underlying computation, so they cannot diverge (verify=true, hash=None is not reachable).

Furthermore, even hypothetically assuming a divergence were possible, the "sign once, execute twice under different standards" scenario requires the **same ed25519 signature bytes** to validate against two structurally different message hashes (TonConnect's TON-specific prehash vs. NEP-413's own hash scheme) — this is not cryptographically feasible without a hash collision, since ed25519 signatures are bound to the exact hash/message they were produced over. Additionally, even if both standards somehow verified the same payload, nonce commitment (`self.state.commit_nonce(signer_id.clone(), nonce)?`) is standard-agnostic and keyed by `(signer_id, nonce)`, so a nonce reused across two submissions would be rejected on the second attempt regardless of which signature standard wrapped it: [6](#0-5) 

The attack chain described does not hold up: the failure mode is consistently and correctly propagated to `InvalidSignature` rejection, not silent acceptance, and no replay-across-standards path exists due to signature binding and nonce deduplication.

```rust
impl TonConnectPayload {
    pub fn try_prehash(&self) -> Option<[u8; 32]> {
        let timestamp: u64 = self.timestamp.as_secs().try_into().ok()?;

        let (prefix, payload) = match &self.payload {
            TonConnectPayloadSchema::Text { text } => (b"txt", text.as_bytes()),
            TonConnectPayloadSchema::Binary { bytes } => (b"bin", bytes.as_slice()),
            #[cfg(feature = "cell")]
            TonConnectPayloadSchema::Cell { schema_crc, cell } => {
                return self::cell::TonConnectCellMessage {
                    schema_crc: *schema_crc,
                    timestamp,
                    user_address: &self.address,
                    app_domain: &self.domain,
                    payload: &cell,
                }
                .hash();
            }
        };

        let domain_len: u32 = self.domain.len().try_into().ok()?;
        let payload_len: u32 = payload.len().try_into().ok()?;

        // 0xffff ++ "ton-connect/sign-data/" ++ Address ++ AppDomain ++ Timestamp ++ Payload
        let prehash = Sha256::new_with_prefix(b"\xFF\xFFton-connect/sign-data/")
            .chain_update(self.address.workchain_id.to_be_bytes())
            .chain_update(self.address.address)
            .chain_update(domain_len.to_be_bytes())
            .chain_update(self.domain.as_bytes())
            .chain_update(timestamp.to_be_bytes())
            .chain_update(prefix)
            .chain_update(payload_len.to_be_bytes())
            .chain_update(payload)
            .finalize()
            .into();

        Some(prehash)
    }
```
