### Title
Unauthenticated pending-transaction query API exposes uncommitted, revertible transactions as if final - ([File: framework/src/main/java/org/tron/core/services/http/GetTransactionFromPendingServlet.java])

### Summary
The ToBet incident relied on an off-chain gambling service polling a node's local database for a bet transaction that was still uncommitted/pending, awarding the payout, and then having the attacker roll the transaction back so it never actually settled on-chain. java-tron exposes the functional analog of this "temporarily-visible pending state" directly as a public, unauthenticated query surface: `getTransactionFromPending` / `getTransactionListFromPending` / `getPendingSize`, reachable via HTTP (`/wallet/gettransactionfrompending`), gRPC, and internally through `Manager.getTxFromPending`. Any dApp, exchange, or gaming contract that treats "transaction is visible in pending" as proof of payment/bet placement is vulnerable to exactly the same race: the transaction can vanish from chain state without ever being reverted through a state root the caller observes.

### Finding Description
`Manager.pushTransaction` adds a transaction to `pendingTransactions` after speculative execution against a temporary revoking session that is immediately merged into the shared "pending" snapshot, but this snapshot is not yet included in any block and is fully revocable. [1](#0-0) 

This pending snapshot is reset on every new block cycle by `PendingManager`, and any transaction not yet packed into a block is either requeued (`rePushTransactions`) or dropped after a timeout, without any of this being visible as an on-chain "rollback" to an observer — it simply disappears. [2](#0-1) [3](#0-2) 

`Manager.getTxFromPending` / `getTxListFromPending` scan `pendingTransactions` and `rePushTransactions` and return whatever is currently sitting in this transient, revocable state. [4](#0-3) 

This is exposed with no authentication or finality guarantee via the HTTP servlet: [5](#0-4) 

and via the equivalent gRPC/JSON-RPC-adjacent `WalletApi.getTransactionFromPending` / `getTransactionListFromPending` / `getPendingSize` RPCs registered in `RpcApiService`: [6](#0-5) [7](#0-6) 
and declared in the public API surface: [8](#0-7) 

Root cause mirrors the ToBet bug class precisely: the transaction data is visible to any external caller querying the node's local "database" (here: `pendingTransactions`/`rePushTransactions` in-memory collections plus the pending revoking snapshot) before it is committed into a block via `revokingStore` session `merge()`/`commit()` in block application, and can disappear without the caller ever seeing a corresponding, observable "revert" event. An attacker can broadcast a transaction, wait for it to appear via `getTransactionFromPending`, have an off-chain consumer act on it (credit a bet, deposit, order, etc.), and then let the transaction time out / fail re-validation / lose a resource race, so it is silently evicted by `PendingManager.txIteration`'s timeout logic without ever reaching a block. Any off-chain service (exchange, gambling dApp, bridge) built to trust the pending-transaction API for confirmation is exposed to unbacked-value / theft outcomes identical in mechanism to the ToBet loss.

### Impact Explanation
Any external consumer treating "present in pending" as final can be tricked into transferring value or granting a service (payout, order fill, deposit credit) for a transaction that ultimately never lands on-chain, producing unbacked-balance/theft outcomes for the depending business logic. Since java-tron ships and documents this exact query surface as a first-class public API, it directly enables the attack class described in the report against any downstream service built on top of it (a single signed transaction from an unprivileged broadcaster is enough to reach this path).

### Likelihood Explanation
Reachable by any unauthenticated network client with no privileges: broadcast one transaction, then poll `/wallet/gettransactionfrompending` (or the gRPC equivalent) in a loop. No special account permissions, precompiles, or SR/witness collusion are needed. The only prerequisite is a downstream service that (mis)uses this pending API as a finality signal — which is exactly the pattern the ToBet incident exploited against a similarly-designed off-chain polling flow.

### Recommendation
- Do not expose raw pending/mempool transaction contents as an authoritative-looking API without clear finality caveats; document that data returned by `getTransactionFromPending`/`getTransactionListFromPending`/`getPendingSize` is provisional and can be dropped/rolled back without notice.
- Consider adding a companion "removed from pending" / "dropped" notification/event stream so integrators can react to eviction, rather than silently disappearing via `PendingManager.txIteration`'s timeout removal.
- Rate-limit and clearly separate this diagnostic endpoint from finality-bearing endpoints (`getTransactionInfoById`, solidity-confirmed queries) so integrators are steered toward querying confirmed/solidified state instead of pending state.

### Proof of Concept
1. Attacker broadcasts a transaction `TX` via `broadcastTransaction`; it enters `pendingTransactions` per `Manager.pushTransaction`.
2. A victim off-chain service (analogous to ToBet) polls `GET /wallet/gettransactionfrompending?value=TX_ID` and, seeing `TX` present, credits a bet/deposit/order for the attacker.
3. `TX` fails to be packed into a block before its expiration/timeout (e.g., due to insufficient resources, TAPOS mismatch after a brief fork, or simple timeout) and is silently dropped by `PendingManager.close()`/`txIteration` without ever appearing in a committed block.
4. The victim service has already granted value based on the transient pending-state read, while the attacker's `TX` never settles — reproducing the ToBet "bet visible, then vanished, but payout already granted" pattern.

  public TransactionCapsule getTxFromPending(String txId) {
    AtomicReference<TransactionCapsule> transactionCapsule = new AtomicReference<>();
    Sha256Hash txHash = Sha256Hash.wrap(ByteArray.fromHexString(txId));
    pendingTransactions.forEach(tx -> {
      if (tx.getTransactionId().equals(txHash)) {
        transactionCapsule.set(tx);
        return;
      }
    });
    if (transactionCapsule.get() != null) {
      return transactionCapsule.get();
    }
    rePushTransactions.forEach(tx -> {
      if (tx.getTransactionId().equals(txHash)) {
        transactionCapsule.set(tx);
        return;
      }
    });
    return transactionCapsule.get();
  }

  public Collection<String> getTxListFromPending() {
    Set<String> result = new HashSet<>();
    pendingTransactions.forEach(tx -> {
      result.add(tx.getTransactionId().toString());
    });
    rePushTransactions.forEach(tx -> {
      result.add(tx.getTransactionId().toString());
    });
    return result;
  }

@Component
@Slf4j(topic = "API")
public class GetTransactionFromPendingServlet extends RateLimiterServlet {

  @Autowired
  private Manager manager;

  protected void doGet(HttpServletRequest request, HttpServletResponse response) {
    try {
      boolean visible = Util.getVisible(request);
      String input = request.getParameter("value");
      TransactionCapsule reply = manager.getTxFromPending(input);
      if (reply != null) {
        response.getWriter().println(Util.printTransaction(reply.getInstance(), visible));
      } else {
        response.getWriter().println("{}");
      }
    } catch (Exception e) {
      Util.processError(e, response);
    }
  }
