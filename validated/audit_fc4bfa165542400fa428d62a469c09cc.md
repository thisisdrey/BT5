### Title
Early `break` in `retry_transactions` drain loop silently drops un-yielded batched transactions without retry-queue accounting - (File: send-transaction-service/src/send_transaction_service.rs)

### Summary
In `SendTransactionService::receive_txn_thread`, once the retry pool reaches `retry_pool_max_size`, the `for (signature, mut transaction_info) in transactions.drain()` loop executes `break` at line 284 instead of `continue`. Because `HashMap::drain()`'s iterator drops all remaining un-yielded key/value pairs when the iterator itself is dropped early, breaking mid-iteration silently discards every remaining transaction still queued in the current `transactions` batch — without incrementing `transactions_to_retry`/`retry_queue_overflow`, so the drop is invisible to metrics.

### Finding Description
The receive thread accumulates incoming `TransactionInfo` entries from the RPC `sendTransaction` ingress into a local `transactions: HashMap<Signature, TransactionInfo>` [1](#0-0) . When the batch size/time threshold is hit, it forwards the batch to the TPU and then attempts to move each entry into the shared `retry_transactions` pool while holding its lock [2](#0-1) .

The insertion loop is:
```rust
for (signature, mut transaction_info) in transactions.drain() {
    ...
    transactions_to_retry += 1;
    let retry_len = retry_transactions.len();
    let entry = retry_transactions.entry(signature);
    if let Entry::Vacant(_) = entry {
        if retry_len >= retry_pool_max_size {
            break;
        } else { ... }
    }
}
``` [3](#0-2) 

Once `retry_len >= retry_pool_max_size`, the loop calls `break` rather than `continue`. `transactions.drain()` returns a `Drain` iterator over the local `transactions` map; per standard library semantics, if a `Drain` iterator is dropped before being fully consumed, all key/value pairs not yet yielded are removed from the map and discarded. Since `transactions` is a fresh local variable per batch (reused across loop iterations, cleared via `drain`), any entries not yet visited by the `for` loop at the moment of `break` are permanently lost — they are never inserted into `retry_transactions`, never counted toward `transactions_to_retry`, and thus never counted in `retry_queue_overflow` at line 292-296 [4](#0-3) .

Because Rust's default `HashMap` iteration order is a function of a randomized hasher seed and insertion pattern (not FIFO or attacker-fully-controlled, but influenced by which signatures happen to hash into buckets visited later), whichever transactions in the batch are iterated after the retry pool fills up are dropped with zero observability. An unprivileged client using the RPC `sendTransaction` path can supply large numbers of uniquely-signed transactions cheaply (submission to this service only requires syntactic/signature validity, not on-chain balance/fee sufficiency, since fee/balance checks occur at execution time, not at submission into `receive_txn_thread`). This lets an attacker keep `retry_transactions` saturated at `retry_pool_max_size` (`MAX_TRANSACTION_RETRY_POOL_SIZE` = 10,000 by default) [5](#0-4) , so that on subsequent batch flushes any victim transactions batched together with attacker spam risk being among the un-yielded remainder when the loop breaks.

### Impact Explanation
The silently dropped entries do lose their entry in the retry-scheduling pool — they will not be automatically resent on retry intervals, and the loss is not reflected in `retry_queue_overflow`/`retry_queue_size` stats, breaking the intended bounded-buffer accounting invariant. Note that the affected transactions were already sent once via `tpu_sender.send_transactions_in_batch` earlier in this flush cycle [6](#0-5) , so this is not an outright "never transmitted" censorship, but the transaction loses all follow-up retries on top of an observability blind spot for what should be an accounted overflow. Category: resource-exhaustion/DoS of the retry mechanism plus a metrics-integrity bug (silent under-reporting of `retry_queue_overflow`).

### Likelihood Explanation
Requires an attacker to sustain enough uniquely-signed transaction submissions to keep `retry_transactions` near/at its 10,000-entry cap across batch flush cycles, and depends on non-attacker-controlled HashMap iteration order to determine which of the current batch's entries fall after the break point. This is feasible for a well-resourced attacker (submitting cheap signed transactions with no balance requirement) but the exact set of victim transactions affected per flush is probabilistic, not deterministically targetable.

### Recommendation
Replace `break` with `continue` in the retry-insertion loop so `transactions.drain()` is fully consumed on every batch, ensuring every drained entry is either inserted into `retry_transactions` or explicitly counted in `retry_queue_overflow`, preserving the bounded-buffer/no-silent-drop invariant.

### Proof of Concept
Rust unit test plan:
1. Construct `retry_transactions: Arc<Mutex<HashMap<Signature, TransactionInfo>>>` pre-filled to `retry_pool_max_size - 1` with dummy `TransactionInfo` entries.
2. Build a local `transactions` HashMap with N > 2 unique-signature `TransactionInfo` entries (simulating one flush batch containing both attacker and victim signatures).
3. Run the exact insertion loop logic from `receive_txn_thread` (extracted or via a thin wrapper) with `retry_pool_max_size` such that exactly 1 more slot is available.
4. Assert: `transactions_to_retry == N` (every drained entry was accounted) — this assertion currently FAILS because the loop breaks after the first entry that finds the pool full, leaving `transactions_to_retry` less than `N`.
5. Assert: `retry_transactions.len() + retry_queue_overflow == N` — currently fails since neither count captures the un-yielded remainder.
6. Fuzz variant: randomize insertion order/signatures to confirm the dropped-count varies with HashMap iteration order, demonstrating the non-deterministic silent-drop behavior described.
