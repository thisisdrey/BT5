## Title
Unauthenticated POST /v3/blocks/upload/ triggers network-wide relay regardless of `broadcast` flag or auth — ([File: stackslib/src/net/api/postblock_v3.rs])

### Summary
`RPCPostBlockRequestHandler::try_handle_request` calls `node.set_relay_message(StacksMessageType::NakamotoBlocks(...))` solely based on whether `Relayer::process_new_nakamoto_block_ext` reports the block as accepted, completely independent of `self.broadcast` or the authentication check performed in `try_parse_request`. This means the auth-gate that is supposed to require the `authorization` header for `broadcast=1` requests has no effect on whether the node actually relays the block to the network.

### Finding Description
The claimed equality "relay triggered == authenticated broadcast intent" is broken by design in this handler. In `try_parse_request`, the auth check at [1](#0-0)  only rejects the request (401) when `broadcast=1` is present in the query string and the caller is unauthenticated; if `broadcast` is omitted (or `=0`), the request proceeds with `authenticated=false` and `broadcast=false` with no error.

Downstream, `try_handle_request` stores `self.broadcast` merely as an input to `Relayer::process_new_nakamoto_block_ext` at [2](#0-1) , but the actual network relay decision is made purely from `data_resp.accepted` at [3](#0-2) :
```rust
if data_resp.accepted {
    node.set_relay_message(StacksMessageType::NakamotoBlocks(NakamotoBlocksData {
        blocks: vec![block],
    }));
}
```
This is unconditional on `self.broadcast` and on `authenticated`. So any remote caller — with or without the configured secret, with or without `broadcast=1` — who posts a `NakamotoBlock` that `process_new_nakamoto_block_ext` accepts will cause the node to relay it via `set_relay_message`, exactly as an authenticated `broadcast=1` request would [4](#0-3) .

The intended contract implied by the `broadcast`/`auth` gate — that only authenticated callers can force this node to propagate an uploaded block to its peers — does not hold. An unprivileged remote attacker sends a plain `POST /v3/blocks/upload/` (no `broadcast` query arg, no `authorization` header) with a well-formed, otherwise-valid `NakamotoBlock` body; if that block is independently accepted by the chainstate/relay logic, the node relays it to the p2p network exactly as if the request had been an authenticated broadcast.

### Impact Explanation
The node under attack becomes an unwitting relay/amplifier for any accepted block regardless of the operator's intended access control (the whole point of gating `broadcast=1` behind `auth` is to let operators control which uploads get pushed onto the network). This is an auth-bypass on a broadcast-control mechanism, forcing network-wide propagation of block data without the caller ever proving authorization. It is repeatable per accepted block and works against any node configured with the `auth` password expecting it to gate broadcast behavior.

### Likelihood Explanation
Precondition is only that the endpoint is reachable (default RPC exposure) and that the attacker can construct/obtain a `NakamotoBlock` that will be accepted by `Relayer::process_new_nakamoto_block_ext` (i.e., a legitimately valid, properly signed block for the current tip — the attacker does not need to forge signatures, just resend/relay a valid block they observed). No secret, peer key, or privileged role is required; cost is a single POST request.

### Recommendation
Gate the `node.set_relay_message(...)` call on `self.broadcast` (and thus on the auth check that produced it), not solely on `data_resp.accepted`:
```rust
if data_resp.accepted && self.broadcast.unwrap_or(false) {
    node.set_relay_message(...);
}
```
This restores the intended coupling between the authenticated `broadcast=1` flag and actual network relay.

### Proof of Concept
Add a test in `stackslib::net::api::postblock_v3` that:
1. Constructs `RPCPostBlockRequestHandler::new(Some("secret".into()))`.
2. Builds an `HttpRequestPreamble`/query with no `authorization` header and no `broadcast` query arg, and a body containing a `NakamotoBlock` known to be accepted by a stubbed/mock `process_new_nakamoto_block_ext` (or via existing test harness patterns used elsewhere in `postblock_v3.rs` tests).
3. Calls `try_parse_request` (expect `Ok`, since no `broadcast=1` means no 401) then `try_handle_request` against a `StacksNodeState` whose relay-processing stub returns an accepted `BlockAcceptResponse`.
4. Asserts `node.set_relay_message` was invoked (e.g., by inspecting `network.pending_messages`/relay queue state), demonstrating relay occurs despite `self.broadcast == Some(false)` and `authenticated == false`.

    /// Decode a bare block from the body
    fn parse_postblock_octets(mut body: &[u8]) -> Result<NakamotoBlock, Error> {
        let block = NakamotoBlock::consensus_deserialize(&mut body).map_err(|e| {
            if let CodecError::DeserializeError(msg) = e {
                Error::DecodeError(format!("Failed to deserialize posted transaction: {}", msg))
            } else {
                e.into()
            }
        })?;
        Ok(block)
    }
}
