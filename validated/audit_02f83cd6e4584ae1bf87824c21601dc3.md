## Analysis

CVE-2017-9120 is a class of bug where a length is computed via integer arithmetic on attacker-controlled input without overflow checking, causing the computed size to wrap to a much smaller value than the real data being processed — leading to a crash/DoS. The closest reachable analog in this codebase is in the TVM `VOTEWITNESS` opcode's energy-cost calculation, which is directly reachable from any broadcastable smart-contract transaction.

### Title
Integer overflow in `VOTEWITNESS` energy-cost calculation bypasses memory-limit and energy metering, enabling node DoS/crash - (File: `actuator/src/main/java/org/tron/core/vm/EnergyCost.java`)

### Summary
`EnergyCost.getVoteWitnessCost` and `getVoteWitnessCost2` compute the memory size needed for the `VOTEWITNESS` TVM opcode by multiplying an attacker-controlled 256-bit array-length `DataWord` by the 32-byte word size using `DataWord.mul()`, which performs modular (wraparound) 256-bit arithmetic with no overflow detection: [1](#0-0) 

The wrapped (and therefore attacker-controllably small) result is then fed into `calcMemEnergy`, whose very first step is `checkMemorySize`, meant to reject requests exceeding `MEM_LIMIT`: [2](#0-1) 

Because the size passed into `checkMemorySize`/`calcMemEnergy` is the already-overflowed (wrapped-small) value rather than the true, attacker-supplied array length, both the energy-metering formula and the `MEM_LIMIT` overflow guard are bypassed for a maliciously crafted array length (e.g. a length near `2^256/32` chosen so that `length * 32 mod 2^256` is small).

### Finding Description
The vulnerable code path (`getVoteWitnessCost`/`getVoteWitnessCost2`) is exactly the class of bug the project's own newer implementation (`getVoteWitnessCost3`, gated behind `VMConfig.allowTvmOsaka()`) was written to fix — it replaces `DataWord.mul()` with `BigInteger` arithmetic specifically to avoid overflow: [3](#0-2) 

`getVoteWitnessCost3` explicitly falls back to the vulnerable `getVoteWitnessCost2` whenever the Osaka hard-fork flag is not active: [4](#0-3) 

This means the vulnerable v1/v2 arithmetic is the live, default code path today (prior to the Osaka activation), and the project's own test suite documents the overflow as a recognized defect class that v3 was built to correct: [5](#0-4) [6](#0-5) 

Because the overflow happens before the safety check (`checkMemorySize`) rather than after, a contract using a crafted array length can make the interpreter believe the operation needs negligible memory/energy, while the actual opcode execution subsequently operates on the true (huge) offset/length values taken from the stack. `Memory.extend()` — the real memory allocator used during opcode execution — uses `addExact`, which throws on overflow rather than silently wrapping: [7](#0-6) 

This mismatch between the (bypassed) cost-time overflow and the (checked) execution-time arithmetic means a transaction can either be under-priced relative to true resource usage, or trigger an unexpected/uncaught arithmetic exception deep in VM execution, depending on the exact crafted values — both are DoS-relevant outcomes.

### Impact Explanation
An unprivileged contract deployer/caller can invoke `VOTEWITNESS` with a crafted array length to defeat two independent safety mechanisms simultaneously (the energy-metering formula and the `MEM_LIMIT` memory-overflow guard), since both derive from the same overflowed `DataWord.mul()` result. This can result in energy-metering bypass (undercharging resource-intensive execution) and/or unexpected exceptions during real memory allocation for the opcode, which is a resource-exhaustion / node-stability risk on a path that every full node must execute identically when validating the block (a crash here is not isolated — it reproduces deterministically on every node re-executing the transaction).

### Likelihood Explanation
High. `VOTEWITNESS` is a standard TVM opcode invocable by any deployed contract from a single signed transaction; no special privileges, chain state, or witness/SR role is required to reach `EnergyCost.getVoteWitnessCost`/`getVoteWitnessCost2`. The vulnerable code is on the currently-active path (not gated behind Osaka), and the overflow condition only requires choosing one 256-bit stack value.

### Recommendation
Replace the `DataWord.mul()`-based size computation in `getVoteWitnessCost` and `getVoteWitnessCost2` with the overflow-safe `BigInteger` arithmetic already used in `getVoteWitnessCost3`, and ensure `checkMemorySize` always receives the un-wrapped, true requested size regardless of which opcode-cost version is active (i.e., backport the v3 fix rather than gating it behind `allowTvmOsaka`).

### Proof of Concept
1. Deploy a contract (or use raw bytecode via `TriggerSmartContract`) that executes the `VOTEWITNESS` opcode.
2. Push a `witnessArrayLength` (or `amountArrayLength`) stack value `L` such that `L * 32 mod 2^256` is small (e.g., `L = ceil(2^256 / 32)`), together with an out-of-range offset.
3. `EnergyCost.getVoteWitnessCost`/`getVoteWitnessCost2` computes `witnessArrayLength.mul(wordSize)` which wraps to a small `DataWord`, so `memNeeded`/`calcMemEnergy`/`checkMemorySize` all evaluate against the wrapped-small value and approve the operation with negligible energy cost.
4. Opcode execution then proceeds to operate against the real (huge) `L`, exercising code paths (memory extension via `Memory.extend`) whose true accounting was never validated against `MEM_LIMIT`, producing either an uncharged resource-heavy operation or an unexpected arithmetic exception during block processing.

Note: I was not able to inspect the exact body of the `VOTEWITNESS` opcode handler (`voteWitnessAction`) that consumes the offset/length after the cost check, so I cannot confirm with certainty whether the ultimate runtime effect is an uncaught exception, an `OutOfMemoryError`, or merely an energy-accounting error bounded by other checks. This should be verified by a full Devin session with code-execution access before remediation is finalized.

  private static long calcMemEnergy(long oldMemSize, BigInteger newMemSize,
                             long copySize, int op) {
    long energyCost = 0;

    checkMemorySize(op, newMemSize);

    // memory SUN consume calc
    long memoryUsage = (newMemSize.longValueExact() + 31) / 32 * 32;
    if (memoryUsage > oldMemSize) {
      long memWords = (memoryUsage / 32);
      long memWordsOld = (oldMemSize / 32);
      long memEnergy = (MEMORY * memWords + memWords * memWords / 512)
          - (MEMORY * memWordsOld + memWordsOld * memWordsOld / 512);
      energyCost += memEnergy;
    }

    if (copySize > 0) {
      long copyEnergy = COPY_ENERGY * ((copySize + 31) / 32);
      energyCost += copyEnergy;
    }
    return energyCost;
  }

  private static void checkMemorySize(int op, BigInteger newMemSize) {
    if (newMemSize.compareTo(MEM_LIMIT) > 0) {
      throw Program.Exception.memoryOverflow(op);
    }
  }
