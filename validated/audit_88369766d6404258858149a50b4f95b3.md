### Title
TOCTOU race between parallel pre-block signature validation and sequential transaction execution allows a revoked/downgraded multisig key to still move funds within the same block - (File: framework/src/main/java/org/tron/core/db/Manager.java)

### Summary
`Manager.processBlock()` performs signature/permission verification for all transactions in an incoming block in parallel, *before* any of those transactions are actually applied to state, and caches the result on each `TransactionCapsule` via an `isVerified` flag. Execution then proceeds sequentially. Because `TransactionCapsule.validateSignature()`/`validatePubSignature()` short-circuit when `isVerified` is already `true`, a transaction whose signature was checked against a "stale" (pre-block) account-permission snapshot is never re-checked against the updated permission set that an earlier transaction in the *same* block may have just written. This is a textbook check-time/use-time mismatch: the permission check is authoritative at parse time, but the balance-affecting use happens later, against a different (already-mutated) state.

### Finding Description
`processBlock` first calls `preValidateTransactionSign(txs)`: [1](#0-0) 

which submits one `ValidateSignTask` per transaction to a thread pool, all reading the *current* (pre-block) `chainBaseManager.getAccountStore()`: [2](#0-1) 

`ValidateSignTask.call()` invokes `trx.validateSignature(...)`, which — via `validatePubSignature` — reads the owner's `Permission` from `AccountStore` at that moment, verifies signatures/weights, and then sets `isVerified = true` on the capsule: [3](#0-2) [4](#0-3) 

After this parallel pre-check phase completes, `processBlock` executes the same list of transactions **sequentially**, in block order, via `processTransaction`: [5](#0-4) 

If transaction A (earlier in the block) is an `AccountPermissionUpdateContract` for owner X that revokes or reweights one of X's active keys, `AccountPermissionUpdateActuator.execute` immediately overwrites the account's permission set in `AccountStore`: [6](#0-5) 

If transaction B (later in the same block, from the same owner X) was signed by the key that A just revoked/downgraded, B's `isVerified` flag was already set to `true` during the earlier *parallel* pre-check phase (using the *old* permission, before A executed). Because `validateSignature`/`validatePubSignature` skip re-verification once `isVerified` is `true`, B is never re-checked against the *new* permission state established by A, and its actuator (e.g. `TransferActuator`) will simply execute: [7](#0-6) 

There is a partial mitigation for the mempool-replay path: `getVerifyTxs()` forces re-verification for any owner address that has a *pending* `AccountPermissionUpdateContract`, by adding that owner to `multiAddresses` and excluding it from the "already-verified-from-pending-pool" skip logic: [8](#0-7) 

However, this only affects the interaction between the **local mempool cache** and a **newly received block** — it does not protect against the ordering hazard that exists purely *within* a single incoming block's own transaction list, where `preValidateTransactionSign` validates every transaction against one shared pre-block snapshot of `AccountStore` and then `processTransaction` mutates that same store transaction-by-transaction afterward.

### Impact Explanation
This allows unauthorized use of a permission key that was intentionally revoked/downgraded by the account owner in the very same block, enabling a compromised or intentionally-removed signer to still authorize a spend (transfer, asset transfer, etc.) after the owner believed they had cut off that key's authority. This is a concrete unauthorized-account-operation / theft-of-funds vector consistent with the report's TOCTOU bug class (stale-credential authorization surviving a privilege change).

### Likelihood Explanation
Exploitation requires: (1) a multisig account with a revocable/downgradable active key, (2) the owner (or attacker with a compromised key) to broadcast a permission-downgrade transaction and a transaction signed by the old key in a way that both land in the same block with the downgrade positioned before the spend in block order, and (3) the block being received via the network path (`block.generatedByMyself == false`, since `preValidateTransactionSign` is skipped for self-generated blocks). Since block/transaction ordering within a witness-produced block, and the specific arrival timing at a syncing node, are attacker/witness-influenceable to a meaningful degree (e.g. a malicious or compromised key holder colluding with control over transaction submission timing), this is plausible though it requires precise ordering — I was not able to fully verify whether `getVerifyTxs`/pending-pool interactions always force the affected transaction to be included in the "needs revalidation" set in every processed-block code path (e.g., `pushBlock` vs. direct sync/pushBlock callers), which introduces some uncertainty about exact preconditions.

### Recommendation
Do not treat parallel pre-block signature verification as final. Either (a) re-validate signature/permission for each transaction against the *current* `AccountStore` snapshot immediately before/during `processTransaction`'s actuator execution rather than trusting the cached `isVerified` flag once any preceding transaction in the same block could have mutated the signer's `Permission`, or (b) detect, for every incoming block, any `AccountPermissionUpdateContract` transactions and force full re-verification (bypassing `isVerified`) for all other transactions from the same owner address that appear later in the same block, mirroring the existing `getVerifyTxs` multi-address logic but applied within-block rather than only against the pending pool.

### Proof of Concept
1. Owner X has an Active permission with two keys, K1 (weight 1) and K2 (weight 1), threshold 1.
2. Attacker/compromised holder of K1 creates a `TransferContract` (tx B) from X, signed with K1, sending X's balance to an attacker address.
3. Owner X creates an `AccountPermissionUpdateContract` (tx A) removing K1 from the active permission.
4. Both A and B are broadcast so that they end up in the same block, with A ordered before B (block producer chooses/accepts this order; a witness who is also the attacker, or timing manipulation for mempool inclusion, can achieve this).
5. On a syncing full node processing this block: `preValidateTransactionSign` validates both A and B in parallel against the pre-block `AccountStore`, where K1 is still valid for X → B.isVerified = true.
6. `processTransaction` executes A first, removing K1 from X's permission in `AccountStore`.
7. `processTransaction` executes B next; `TransactionCapsule.validateSignature` sees `isVerified == true` and skips re-checking against the now-updated permission; `TransferActuator.execute` moves X's funds to the attacker address despite K1 no longer being an authorized signer.

  private static class ValidateSignTask implements Callable<Boolean> {

    private TransactionCapsule trx;
    private CountDownLatch countDownLatch;
    private ChainBaseManager manager;

    ValidateSignTask(TransactionCapsule trx, CountDownLatch countDownLatch,
        ChainBaseManager manager) {
      this.trx = trx;
      this.countDownLatch = countDownLatch;
      this.manager = manager;
    }

    @Override
    public Boolean call() throws ValidateSignatureException {
      try {
        trx.validateSignature(manager.getAccountStore(), manager.getDynamicPropertiesStore());
      } catch (ValidateSignatureException e) {
        throw e;
      } finally {
        countDownLatch.countDown();
      }
      return true;
    }
  }

  /**
   * validate signature

  public boolean validatePubSignature(AccountStore accountStore,
      DynamicPropertiesStore dynamicPropertiesStore)
      throws ValidateSignatureException {
    if (!isVerified) {
      if (this.transaction.getSignatureCount() <= 0
              || this.transaction.getRawData().getContractCount() <= 0) {
        throw new ValidateSignatureException("miss sig or contract");
      }
      if (this.transaction.getSignatureCount() > dynamicPropertiesStore
              .getTotalSignNum()) {
        throw new ValidateSignatureException("too many signatures");
      }

      byte[] hash = getTransactionId().getBytes();

      long startNs = System.nanoTime();
      try {
        if (!validateSignature(this.transaction, hash, accountStore, dynamicPropertiesStore)) {
          isVerified = false;
          throw new ValidateSignatureException("sig error");
        }
      } catch (SignatureException | PermissionException | SignatureFormatException e) {
        isVerified = false;
        throw new ValidateSignatureException(e.getMessage());
      } finally {
        logSlowSigVerify(startNs);
      }
      isVerified = true;
    }
    return true;
  }

  /**
   * validate signature
   */
  public boolean validateSignature(AccountStore accountStore,
      DynamicPropertiesStore dynamicPropertiesStore) throws ValidateSignatureException {
    if (!isVerified) {
      //Do not support multi contracts in one transaction
      Transaction.Contract contract = this.getInstance().getRawData().getContract(0);
      if (contract.getType() != ContractType.ShieldedTransferContract) {
        validatePubSignature(accountStore, dynamicPropertiesStore);
      } else {  //ShieldedTransfer
        byte[] owner = getOwnerAddress();
        if (!ArrayUtils.isEmpty(owner)) { //transfer from transparent address
          validatePubSignature(accountStore, dynamicPropertiesStore);
        } else { //transfer from shielded address
          if (this.transaction.getSignatureCount() > 0) {
            throw new ValidateSignatureException("there should be no signatures signed by "
                    + "transparent address when transfer from shielded address");
          }
        }
      }
      isVerified = true;
    }
    return true;
  }
