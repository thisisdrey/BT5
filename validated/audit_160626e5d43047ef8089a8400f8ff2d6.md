### Title
StackerDB chunk signatures do not bind to the target contract, enabling cross-DB chunk replay - (File: `libstackerdb/src/libstackerdb.rs`)

### Summary
`SlotMetadata::auth_digest`, which is the message that gets signed and verified for every StackerDB chunk write, commits only to `slot_id`, `slot_version`, and `data_hash`. It never commits to the smart-contract identifier of the StackerDB instance the chunk is destined for. Any signature that authenticates a chunk write for one StackerDB contract is therefore a valid signature for the identical `(slot_id, slot_version, data_hash)` tuple on any other StackerDB contract in which the same principal address happens to control that slot. This is the same class of bug as the reported `RestoreData` issue: an authenticated message is not "rooted" to the single context (contract/tx) it was intended for, so it can be replayed elsewhere.

### Finding Description
`SlotMetadata::auth_digest` builds the digest to sign/verify as: [1](#0-0) 

```
fn auth_digest(&self) -> Sha512Trunc256Sum {
    let mut hasher = Sha512_256::new();
    hasher.update(self.slot_id.to_be_bytes());
    hasher.update(self.slot_version.to_be_bytes());
    hasher.update(self.data_hash.0);
    Sha512Trunc256Sum::from_hasher(hasher)
}
```

`verify()` recovers the public key from this digest and only checks that the recovered key hash matches the `principal` (a `StacksAddress`) passed in by the caller: [2](#0-1) 

The caller-side check that ties a signature to a *specific StackerDB contract* happens entirely outside the signed payload, in `PeerNetwork::validate_received_chunk`, which looks up the expected signer for `(smart_contract_id, slot_id)` and then calls `slot_metadata.verify(&addr)`: [3](#0-2) 

Because `smart_contract_id` is never part of the signed digest, the signature itself carries no information about which StackerDB the write is meant for. If the same `StacksAddress` is a registered slot signer in two different StackerDB replicated contracts (a common real-world pattern — e.g. multiple `.signers-*` StackerDB contracts per reward cycle, or any future contracts that reuse the same signer set/slot layout), a chunk signed for contract A at `(slot_id, slot_version, data_hash)` is also a fully valid, verifiable chunk for contract B at the same `(slot_id, slot_version, data_hash)`. An attacker who observes (or is handed, e.g. via StackerDB gossip) a legitimately signed chunk for contract A can resubmit the exact same `StackerDBChunkData` bytes to contract B's `POST /v2/stackerdb/.../chunks` endpoint (`RPCPostStackerDBChunkRequestHandler`) or push it over the P2P `StackerDBPushChunk` path, and it will pass signature verification and be written into contract B's chunk store, as long as B's slot for that ID also expects `data.slot_version` ≥ B's own latest version and the address matches.

### Impact Explanation
This is an unauthorized write to StackerDB state: data intended for/authorized against one contract's replicated slot can be forged into another contract's replicated slot without the signer's consent for that specific destination, because the equality the code relies on ("this signature authenticates data for contract X, slot Y, version Z") is not actually enforced — the signature only proves "signer S produced this `(slot_id, slot_version, data_hash)` triple," with no contract binding. Any downstream logic that trusts StackerDB chunk contents as being scoped/authorized per-contract (e.g. signer message contracts, miner-coordination contracts) can be polluted with cross-contract replayed data. This matches "unauthenticated/unauthorized write to state or StackerDB" and "network-wide propagation of forged data" (the chunk propagates via `StackerDBPushChunk` gossip once accepted) in the Critical impact bucket.

### Likelihood Explanation
Requires only two conditions that are already common: (1) a `StacksAddress` that acts as a slot signer across more than one StackerDB contract with an overlapping `(slot_id, slot_version)` scheme (achievable by any StackerDB configuration that reuses a signer's slot layout, including ones an attacker can create via a permissionless `.signers`-style contract if one is deployed with attacker/participant-controlled slot config), and (2) knowledge of one validly-signed chunk for that tuple (trivially obtainable since chunks are broadcast/gossiped publicly over StackerDB sync). No node secret or admin role is required — only a legitimately observed public chunk and a POST/relay to a different contract's StackerDB replica.

### Recommendation
Include the target StackerDB's smart contract identifier (and ideally a network/chain identifier) in `SlotMetadata::auth_digest`, so a signature for one StackerDB instance cannot be replayed against another. This mirrors the report's recommendation to "root the signature to a single" destination/context rather than leaving it free-floating.

### Proof of Concept
1. Deploy two StackerDB-replicated contracts, A and B, both configuring principal `S` as the signer for `slot_id = 0`.
2. `S` signs a `StackerDBChunkData { slot_id: 0, slot_version: 1, data }` intended only for contract A and POSTs it to A's endpoint; it is accepted.
3. Attacker captures this chunk (via gossip/`StackerDBPushChunk`, or the public POST response) and re-POSTs the identical bytes to contract B's chunk endpoint (`.../stackerdb/{B}/chunks`), or relays it over P2P `StackerDBPushChunk` for contract B.
4. `validate_received_chunk`/`try_replace_chunk` for B looks up `S` as B's slot-0 signer, calls `slot_metadata.verify(&S_addr)` using the same `auth_digest` (which never mentions A or B), the signature recovers to `S`, and the chunk is accepted and stored in B — even though `S` never signed anything authorizing a write into B.

    /// Verify that a given principal signed this chunk metadata.
    /// Note that the address version is ignored.
    pub fn verify(&self, principal: &StacksAddress) -> Result<bool, Error> {
        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )
        .map_err(|ve| Error::VerifyingError(ve.to_string()))?;

        let pubkh = Hash160::from_node_public_key(&pubk);
        Ok(pubkh == *principal.bytes())
    }
