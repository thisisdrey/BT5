### Title
Borrowers can withdraw locked collateral through `NativeTokenGateway.withdraw`, leaving uncollateralized debt - ([File: contracts/NativeTokenGateway.sol](contracts/NativeTokenGateway.sol))

### Summary
`NativeTokenGateway.withdraw` transfers a user’s deposit-token balance to the gateway and then calls `DepositToken.withdraw` from the gateway address. `DepositToken.withdraw` checks whether the **gateway’s** deposit tokens are locked, not whether the original user’s position has sufficient remaining collateral. Because the gateway has no debt, its newly received tokens are fully unlocked, allowing a borrower to withdraw collateral that should remain locked against debt. The same pattern also exists in `VesperGateway.withdraw`.

### Finding Description
`NativeTokenGateway.withdraw` executes the following sequence:

1. Transfers `amount_` deposit tokens from the user to the gateway.
2. Calls `depositToken.withdraw(amount_, address(this))`.
3. Converts the withdrawn wrapped native token to native token and sends it to the user.

The first step removes the deposit-token balance from the borrower before the withdrawal-health check can inspect that borrower’s position. [1](#0-0) 

`DepositToken.withdraw` resolves `_msgSender()` to the gateway and checks `_revertIfLocked(_msgSender, amount_)`. [2](#0-1) 

That lock check calls `unlockedBalanceOf(account_)`, which calculates the locked balance from `pool.debtPositionOf(account_)`. [3](#0-2) 

Since `account_` is the gateway rather than the borrower, and the gateway has no debt position, `debtPositionOf(gateway)` returns zero debt and the transferred deposit tokens are treated as fully unlocked. `_withdraw` then burns the gateway’s deposit tokens and pulls the underlying collateral from the Treasury. [4](#0-3) 

The critical flaw is the account substitution:

```solidity
// NativeTokenGateway.sol
_depositToken.safeTransferFrom(_msgSender, address(this), amount_);
(uint256 _withdrawn, ) = _depositToken.withdraw(amount_, address(this));
```

After `transferFrom`, the borrower no longer owns the deposit tokens, so checking the gateway’s health does not enforce the borrower’s collateralization invariant.

`VesperGateway.withdraw` contains the same account-substitution issue: it moves the user’s deposit tokens to the gateway and then calls `withdraw` as the gateway. [5](#0-4) 

### Impact Explanation
A borrower can extract all underlying collateral while retaining the full outstanding debt.

For example:

1. Deposit 100 ETH through `NativeTokenGateway.deposit`.
2. Issue the maximum permitted synthetic debt.
3. Approve `NativeTokenGateway` for the 100 `msdWETH`.
4. Call `NativeTokenGateway.withdraw(pool, 100 ether)`.
5. Receive the withdrawn ETH while retaining the synthetic assets and debt position.

The borrower’s debt remains recorded, but the corresponding collateral has already left the Treasury. This breaks the protocol solvency invariant and creates bad debt that cannot be recovered through liquidation because the collateral has already been withdrawn. The attacker directly obtains both the borrowed synthetic assets and the collateral backing them.

### Likelihood Explanation
The attack is available to any unprivileged user with a registered native-token collateral pool:

- `NativeTokenGateway.deposit` is public and only requires the supplied pool to be registered. [6](#0-5) 
- `NativeTokenGateway.withdraw` is public, non-reentrant, and similarly requires only a registered pool. [7](#0-6) 
- The required deposit-token approval is a routine ERC-20 approval and can be submitted in the same transaction through `Operator.execute`.
- No privileged role, malicious oracle, governance action, flash-loan prerequisite, or third-party failure is required.
- The final protocol state leaves the attacker with the withdrawn collateral and outstanding debt.

### Recommendation
Do not move the borrower’s deposit tokens to the gateway before checking collateral locking.

For direct withdrawals, add a privileged withdrawal path that accepts the original account and recipient but still checks the original account’s locked balance. For example:

```solidity
function withdrawFrom(address from_, uint256 amount_, address to_)
    external
    onlyIfTrustedGateway
{
    _revertIfLocked(from_, amount_);
    _withdraw(from_, amount_, to_);
}
```

The gateway should call this function with `from_ = user`, and `DepositToken` must verify that `msg.sender` is a gateway explicitly authorized by `PoolRegistry`, rather than allowing arbitrary contracts to specify `from_`.

For `VesperGateway`, apply the same fix. Avoid the transfer-to-gateway pattern because it changes the account whose debt position is evaluated. Tests should assert that a user cannot withdraw any amount greater than `unlockedBalanceOf(user)` through either gateway.

### Proof of Concept
A Foundry fork test can reproduce the issue against a deployed pool with a registered wrapped-native-token deposit token:

```solidity
function testGatewayWithdrawsLockedCollateral() public {
    address attacker = makeAddr("attacker");
    uint256 collateralAmount = 100 ether;
    uint256 borrowAmount = 80_000e18;

    IPool pool = IPool(DEPLOYED_POOL);
    NativeTokenGateway gateway = NativeTokenGateway(DEPLOYED_NATIVE_GATEWAY);
    IDebtToken debtToken = IDebtToken(DEPLOYED_DEBT_TOKEN);
    ISyntheticToken synthetic = ISyntheticToken(DEPLOYED_SYNTHETIC);
    IDepositToken depositToken = pool.depositTokenOf(gateway.nativeToken());

    vm.deal(attacker, collateralAmount);
    vm.startPrank(attacker);

    // Deposit through the gateway.
    gateway.deposit{value: collateralAmount}(pool);
    assertEq(depositToken.balanceOf(attacker), collateralAmount);

    // Borrow against the deposited collateral.
    debtToken.issue(borrowAmount, attacker);
    assertEq(synthetic.balanceOf(attacker), borrowAmount);

    // This amount should be locked, but the gateway moves it first and
    // DepositToken checks the gateway's debt position instead.
    depositToken.approve(address(gateway), collateralAmount);
    gateway.withdraw(pool, collateralAmount);

    vm.stopPrank();

    // Collateral was withdrawn even though the debt remains.
    assertEq(depositToken.balanceOf(attacker), 0);
    assertGt(debtToken.balanceOf(attacker), 0);
    assertGt(attacker.balance, 0);
    assertEq(synthetic.balanceOf(attacker), borrowAmount);
}
```

The decisive state transition is:

```solidity
depositToken.transferFrom(attacker, gateway, amount);
depositToken.withdraw(amount, gateway);
```

`withdraw` evaluates `unlockedBalanceOf(gateway)`, not `unlockedBalanceOf(attacker)`. The borrower therefore exits with both the synthetic loan proceeds and the collateral, while the pool retains the now-undercollateralized debt.
