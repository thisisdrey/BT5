## Title
Out-of-bounds array read / crash in `BatchValidateSign` precompile via unbounded offset indices in `extractBytes32Array` - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `BatchValidateSign` precompiled contract (reachable by any account through a `CALL`/`STATICCALL` from a deployed contract, i.e., a plain contract-call transaction) decodes attacker-supplied calldata into a `DataWord[]` and uses attacker-controlled offset/length values to index into that array without validating them against the array bounds in `extractBytes32Array`, unlike the sibling helpers `extractBytesArray`/`extractSigArray` which do perform a bounds check.

### Finding Description
`doExecute()` in the `BatchValidateSign` precompile parses the raw calldata into words and computes an address-array offset directly from attacker data: [1](#0-0) 

It calls `extractBytes32Array(words, words[2].intValueSafe() / WORD_SIZE)`, which reads `words[offset]` and then `words[offset + i + 1]` for `i` in `[0, len)`, where both `offset` and `len` come straight from attacker-controlled calldata, with **no bounds check** against `words.length`: [2](#0-1) 

By contrast, the analogous helpers used for the signature array explicitly guard the same offset before indexing: [3](#0-2) 

This is structurally the same bug class as the rsync `recv_files()` issue described in the report: an index/offset value supplied by an untrusted party is used to read into an allocated array without checking it lies within the array's real bounds, producing an out-of-bounds read (here, throwing `ArrayIndexOutOfBoundsException` from Java-level array access rather than a raw memory dereference, since the JVM bounds-checks primitive array access).

There is a partial guard behind `VMConfig.allowTvmSelfdestructRestriction()`: [4](#0-3) 
but this only checks `sigArraySize`/`addrArraySize` against `MAX_SIZE`; it does not validate that `words[2].intValueSafe() / WORD_SIZE` itself (the offset passed into `extractBytes32Array`) is within `words.length`. An attacker can craft calldata where `words[2]` encodes an offset far beyond the actual word-array length (e.g., pointing past the end of a short `data` payload), triggering `words[offset]` to throw `ArrayIndexOutOfBoundsException` inside `extractBytes32Array` before the size guard even has a chance to matter for that specific access pattern, or by making `offset` valid but `offset + i + 1` run past `words.length` once `len` is large.

### Impact Explanation
Whether this crashes the whole node or is contained depends on exception handling around `callToPrecompiledAddress`/`doExecute`. If the `ArrayIndexOutOfBoundsException` (a `RuntimeException`, not one of the VM's specific checked exceptions) propagates uncaught out of the precompile's constant/non-constant call path during block application, it could abort transaction processing for the whole block, which in the context of "block application in Manager" is a node-crash/halt-class issue: any node processing this transaction (broadcast by an anonymous account) would hit the same unhandled exception deterministically, potentially causing a consensus-relevant DoS if not caught symmetrically by all node code paths (e.g., differs between constant call and thread-pool call paths). Given the ask-only investigation, I could not fully confirm whether an outer `try/catch` at the `Program.callToPrecompiledAddress` level (in `actuator/src/main/java/org/tron/core/vm/program/Program.java`) blankets all `RuntimeException`s from `doExecute()`, since the relevant call site could not be retrieved in the final iteration (file read attempt returned only the package line due to tool/iteration limits). This is the main uncertainty in this finding.

### Likelihood Explanation
`BatchValidateSign` is invoked by a normal CALL opcode from any deployed smart contract, which is reachable by any unprivileged account issuing a `TriggerSmartContract` transaction with attacker-chosen calldata to a contract that forwards the call to the precompile address — no special privilege is required. Crafting `words[1]`/`words[2]` offset words to reference out-of-range indices is a simple, deterministic calldata-construction exercise, comparable in effort to the rsync PoC (crafting specific protocol fields to defeat an implicit ordering/bounds assumption).

### Recommendation
Add the same `offset > words.length - 1` (and post-increment `offset + i + 1 >= words.length`) bounds validation to `extractBytes32Array` that already exists in `extractBytesArray`/`extractSigArray`, returning a safe empty/`DATA_FALSE` result instead of throwing, and verify/ensure that any remaining `RuntimeException` paths inside all `PrecompiledContract.execute()` implementations are uniformly caught so that malformed attacker calldata can never propagate an unhandled exception into block/transaction processing in `Program`/`Runtime`.

### Proof of Concept
1. Deploy a trivial contract that forwards arbitrary calldata via `CALL` to the `BatchValidateSign` precompile address.
2. Construct calldata `data` such that:
   - `words[0]` = arbitrary 32-byte hash.
   - `words[1]` = an offset (in bytes) that, divided by `WORD_SIZE`, points to a valid short signatures array (or is crafted to pass any `MAX_SIZE` guard).
   - `words[2]` = an offset (in bytes) that, divided by `WORD_SIZE`, is **larger than** `words.length - 1` (i.e., points beyond the end of the actual `DataWord[]` produced from the calldata), or is a valid index whose declared "length" word combined with the loop `offset + i + 1` walks past `words.length`.
3. Submit a `TriggerSmartContract` transaction (unprivileged) invoking the forwarding contract with this calldata.
4. During execution, `extractBytes32Array(words, offset)` executes `words[offset]` (or `words[offset + i + 1]` inside the loop) where `offset`/`offset + i + 1 >= words.length`, throwing `ArrayIndexOutOfBoundsException`.
5. Confirm whether this exception is caught at the outer precompile-invocation boundary in `Program`/`Runtime`. If uncaught, the transaction-processing thread (and, in block application, the node applying the block) crashes or fails deterministically on every node validating that transaction/block — this last step could not be independently confirmed within the available tool iterations and should be verified directly against `Program.callToPrecompiledAddress` and `Runtime`'s top-level exception handling.

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }

  private static byte[][] extractSigArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();

      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          SIG_LENGTH);
    }
    return bytesArray;
  }
