### Title
Heap buffer over-read parsing attacker-supplied ZIP central directory entries in `ijar` - (File: `third_party/ijar/zip.cc`)

### Summary
`third_party/ijar/zip.cc`'s `InputZipFile::ProcessCentralDirEntry` parses ZIP central directory headers from an mmap'd, untrusted input file with no bounds checking, unlike the sibling local-file-header parser `InputZipFile::ProcessLocalFileEntry`, which explicitly calls `EnsureRemaining()` before every read [1](#0-0) . This mirrors the CVE-2017-9055 bug class: length/size fields taken directly from attacker-controlled input are used to advance a read cursor and copy/interpret memory without validating them against the buffer's actual extent, leading to a heap-based (mmap-based) buffer over-read.

### Finding Description
`ProcessCentralDirEntry` reads `file_name_length`, `extra_field_length`, and `file_comment_length` straight from the central directory header bytes and immediately uses them to advance the cursor `p`, `memcpy` a filename, and iterate an "extra fields" sub-loop — with zero validation against the mapped file's remaining length: [2](#0-1) 

Specifically:
- `p += file_name_length;` and the preceding `memcpy(filename, p, len)` trust `file_name_length` fully.
- `const u1 *extra_p = p; p += extra_field_length;` trusts `extra_field_length`.
- The extra-field loop `while (extra_p != p) { ... data_size = get_u2le(extra_p); extra_p += data_size; ... }` trusts each embedded `data_size` and can overshoot `p` (the intended end), in which case the loop condition `extra_p != p` never becomes false again and continues reading (and calling `get_u8le`) far past the intended entry boundary.
- Unlike `ProcessLocalFileEntry`, which guards every read with `EnsureRemaining()` [3](#0-2) , there is no equivalent guard here. The inline comment claims "the central directory is always followed by another data structure that has a signature, so parsing it this way is safe" [4](#0-3) , but that assumption only holds for well-formed archives; it does not stop a crafted `file_name_length`/`extra_field_length`/`comment_length`/`data_size` from walking the cursor past the actual mmap'd file length (`input_file_->Length()`), reading uninitialized/unmapped memory.

This code is reached whenever `ijar`/`zip_main` processes a ZIP/JAR file via `ZipExtractor::Create` → `InputZipFile::Open()` → `ProcessNext()` → `ProcessCentralDirEntry` [5](#0-4) . `ijar` (invoked by `java_common.run_ijar`) strips non-ABI parts from `.jar` files to produce interface jars used for Java compilation caching, and it is applied to arbitrary input jars, including precompiled dependency jars declared via `java_import`/`jars` attributes that can be fetched from external, attacker-controlled sources (e.g., an `http_jar`/`http_archive` whose pinned `sha256` simply matches whatever bytes the attacker published) [6](#0-5) .

### Impact Explanation
The unchecked size fields drive out-of-bounds reads relative to the mmap'd input buffer:
- Best case: the process crashes (SIGSEGV) when the cursor runs off the end of the mapping, causing a build-time denial of service for anyone building against the malicious jar.
- Worse case: if adjacent mapped pages happen to be valid memory (e.g., other parts of a larger mapping, or memory reused nearby), the over-read bytes are interpreted as ZIP64 size/offset fields (`get_u8le(extra)`), which subsequently control how many bytes of "file data" are read and copied into the produced interface jar via `processor->Process(...)`, creating a potential information-disclosure vector where adjacent process memory bytes are baked into build outputs.

This satisfies the "read outside the ... exec root" / heap-over-read class of impact required by the scan rules — it is a genuine memory-safety violation, not mere resource exhaustion, since attacker-controlled length fields directly drive out-of-bounds memory access and can leak adjacent memory content into build artifacts.

### Likelihood Explanation
Any Bazel Java build that consumes an externally-supplied `.jar` (via `java_import`, Maven-based external deps, etc.) and has `ijar` run on it (the default for compile-jar generation) will trigger this parser on attacker-supplied bytes. Since sha256/integrity checks on the outer download only guarantee the bytes are exactly what the attacker published — they do nothing to guarantee the ZIP structure inside is well-formed — an attacker who controls the published artifact (e.g., a malicious open-source package) can trivially craft a ZIP whose central directory entry declares an oversized `file_name_length`/`extra_field_length`/`data_size` to trigger the over-read deterministically. No untrusted-root-Starlark, sandbox-escape, or MITM is required.

### Recommendation
Add the same `EnsureRemaining()`-style bounds validation used in `ProcessLocalFileEntry` to `ProcessCentralDirEntry`: before reading `file_name_length` bytes, `extra_field_length` bytes, `file_comment_length` bytes, or advancing `extra_p` by `data_size`, verify the resulting cursor position does not exceed `input_file_->Length()` (or the known central-directory end offset). Bail out with an error (as `EnsureRemaining` does) rather than continuing to parse when a length would run past the mapped buffer.

### Proof of Concept
Construct a minimal ZIP file containing:
1. A valid local file header + minimal empty entry.
2. A central directory header (`CENTRAL_FILE_HEADER_SIGNATURE`) whose `extra_field_length` (or embedded extra-field `data_size`) is set to a large value (e.g., `0xFFFF`) that, combined with the actual (small) remaining bytes in the file, causes `extra_p`/`p` to advance past `input_file_->Length()`.
3. Truncate the file immediately after the central directory header bytes (no padding), so the declared lengths clearly exceed the real file size.

Run this file through `ijar`/`zip_main extract` (or via `java_common.run_ijar` on a `java_import` jar built from this crafted archive) and observe a crash (SIGSEGV) or garbage data read from beyond the mapped region, reproducible in a `src/test/shell/bazel` or standalone C++ test harness that calls `ZipExtractor::Create(malicious_zip_path, processor)` followed by `ProcessAll()`.

bool InputZipFile::ProcessCentralDirEntry(const u1 *&p, u8 *compressed_size,
                                          u8 *uncompressed_size, char *filename,
                                          size_t filename_size, u4 *attr,
                                          u8 *offset) {
  u4 signature = get_u4le(p);

  if (signature != CENTRAL_FILE_HEADER_SIGNATURE) {
    if (signature != DIGITAL_SIGNATURE && signature != EOCD_SIGNATURE &&
        signature != ZIP64_EOCD_SIGNATURE) {
      error("invalid central file header signature: 0x%x\n", signature);
    }
    return false;
  }

  p += 16;  // skip to 'compressed size' field
  *compressed_size = get_u4le(p);
  *uncompressed_size = get_u4le(p);
  u2 file_name_length = get_u2le(p);
  u2 extra_field_length = get_u2le(p);
  u2 file_comment_length = get_u2le(p);
  p += 4;  // skip to external file attributes field
  *attr = get_u4le(p);
  *offset = get_u4le(p);
  {
    size_t len = (file_name_length < filename_size)
      ? file_name_length
      : (filename_size - 1);
    memcpy(reinterpret_cast<void*>(filename), p, len);
    filename[len] = 0;
  }
  p += file_name_length;
  const u1 *extra_p = p;
  p += extra_field_length;
  while (extra_p != p) {
    const u2 header_id = get_u2le(extra_p);
    const u2 data_size = get_u2le(extra_p);
    const u1 *extra = extra_p;
    extra_p += data_size;
    if (header_id == ZIP64_EXTRA_FIELD_TAG) {
      if (*uncompressed_size == U4_MAX) {
        *uncompressed_size = get_u8le(extra);
      }
      if (*compressed_size == U4_MAX) {
        *compressed_size = get_u8le(extra);
      }
      if (*offset == U4_MAX) {
        *offset = get_u8le(extra);
      }
    }
  }
  p += file_comment_length;
  return true;
}
