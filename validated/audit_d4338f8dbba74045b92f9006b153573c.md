### Title
StackerDB chunk signatures omit the target contract identifier, permitting cross-StackerDB replay of forged writes - (File: `libstackerdb/src/libstackerdb.rs`)

### Summary
`SlotMetadata::auth_digest()` only commits to `slot_id`, `slot_version`, and `data_hash` — never to the StackerDB's `smart_contract_id` (the "contract address" analog) or any chain/network identifier. Because a single signing key (e.g. a Nakamoto signer's key) is authorized on slot indices across *multiple, distinct* StackerDB contracts (different `.signers-N-M` instances per reward cycle / message round, plus any other contract that happens to allocate the same signer the same slot index), a signature that is valid for slot `X`/version `V`/hash `H` in contract A is *also* a cryptographically valid signature for the identical slot/version/hash in contract B, even though it was never intended to authorize a write there.

### Finding Description
The signed digest is: [1](#0-0) 

```
fn auth_digest(&self) -> Sha512Trunc256Sum {
    let mut hasher = Sha512_256::new();
    hasher.update(self.slot_id.to_be_bytes());
    hasher.update(self.slot_version.to_be_bytes());
    hasher.update(self.data_hash.0);
    Sha512Trunc256Sum::from_hasher(hasher)
}
``` [2](#0-1) 
`verify()` recovers the public key from this same digest and simply checks the recovered `Hash160` against the caller-supplied `principal` (the expected signer for a given contract/slot). No contract identifier, chain ID, or network ID is folded in anywhere in the signed bytes.

The verification call sites confirm the contract is only used as a *lookup key* to find the expected signer address, never bound into the signed data itself: [3](#0-2) 

```
let addr = match self
    .stackerdbs
    .get_slot_signer(smart_contract_id, data.slot_id)?
{ ... };
let slot_metadata = data.get_slot_metadata();
if !slot_metadata.verify(&addr)? { ... }
```

This is the direct analog of the reported "Airdrop.sol" bug: the signature never binds to "which contract" (or "which chain") it is valid for. If the same signer address is assigned the same `slot_id` in two different StackerDB contracts (which happens routinely, since Nakamoto signer StackerDB contracts are instantiated per reward cycle/message-round and slot assignment is derived from the same signer key/ordering — see `NakamotoSigners::update_signers` writing `stackerdb-set-signer-slots` per reward cycle) [4](#0-3) , an unprivileged network peer that observes a legitimately-gossiped `StackerDBChunkData`/`StackerDBPushChunk` for contract A can relay that exact same bytes (signature included) into contract B. `validate_received_chunk` and `handle_unsolicited_StackerDBPushChunk` will accept it as a valid write for contract B because the digest and verification never reference `smart_contract_id`: [5](#0-4) 

### Impact Explanation
This breaks the intended equality "signed for StackerDB contract A" == "authorized write in StackerDB contract A". An unprivileged relayer/attacker can cause a node to accept and store — and then re-propagate to its own peers — a chunk into a StackerDB replica for a contract the original signer never intended to write to, using nothing but a signature that was already broadcast for a different contract. This is an unauthorized write to StackerDB state and network-wide propagation of forged/misattributed data, matching the "Critical" bucket criteria in the rules (unauthenticated/unauthorized write to StackerDB, propagation of forged data across the network).

### Likelihood Explanation
Exploitability requires: (1) the attacker observes any legitimately gossiped chunk (trivial — gossip is broadcast to all replicating peers), and (2) the target contract assigns the same signer address to the same `slot_id`, and its current `expected_version` for that slot is `<= slot_version` in the replayed chunk (per `validate_received_chunk`'s stale-version check) [6](#0-5) . Given that Nakamoto's `.signers-*` StackerDB contracts are instantiated per reward cycle and derive slot ordering from a signer's key/weight, and signers frequently remain stacked across consecutive cycles, this precondition is realistically satisfiable without any private key or privileged access — only network relay capability.

### Recommendation
Bind the StackerDB's `QualifiedContractIdentifier` (and ideally the network/chain identifier, analogous to `chain_id`/`address(this)` in the original report) into `SlotMetadata::auth_digest()`, e.g.:
```
hasher.update(smart_contract_id.serialize_to_vec());
hasher.update(chain_id.to_be_bytes());
hasher.update(self.slot_id.to_be_bytes());
hasher.update(self.slot_version.to_be_bytes());
hasher.update(self.data_hash.0);
```
This requires threading the contract ID (already available at all call sites) into `sign()`/`verify()`, and bumping the message format/versioning so chunk signatures cannot be replayed across `StackerDB` instances.

### Proof of Concept
1. Signer `S` (private key `k`) is assigned `slot_id = 0` in `.signers-0-3` (contract A) and also happens to be assigned `slot_id = 0` in `.signers-1-3` (contract B) for a subsequent reward cycle (a common occurrence for a signer who continues stacking).
2. `S` legitimately signs and pushes chunk `{slot_id: 0, slot_version: 1, data: D}` to contract A; this propagates via gossip (`StackerDBPushChunk`) to peer nodes.
3. Any peer that received this chunk (no special privilege needed) resends the same `StackerDBChunkData` bytes (`slot_id=0, slot_version=1, sig=<S's original sig>, data=D`) but wrapped with `contract_id = B` instead of `A` in a `StackerDBPushChunkData`/`StackerDBGetChunkData` reply.
4. `handle_unsolicited_StackerDBPushChunk` → `validate_received_chunk(B, ...)` looks up `get_slot_signer(B, 0)` → finds `S`'s address (since it's assigned there too), computes `slot_metadata.verify(&S_addr)` using the same contract-agnostic digest, and it passes — because the digest never included `A` or `B`.
5. The victim node stores this chunk as though it were an authentic, contract-B-scoped write from `S`, and further gossips it to its peers, propagating the cross-contract replay.

    /// Verify that a given principal signed this chunk metadata.
    /// Note that the address version is ignored.
    pub fn verify(&self, principal: &StacksAddress) -> Result<bool, Error> {
        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )
        .map_err(|ve| Error::VerifyingError(ve.to_string()))?;

        let pubkh = Hash160::from_node_public_key(&pubk);
        Ok(pubkh == *principal.bytes())
    }

    ) -> Result<bool, net_error> {
        // validate -- must not exceed this replica's configured chunk size.
        if (data.data.len() as u64) > config.chunk_size {
            info!(
                "Received StackerDBChunk for {} ID {}, which is oversized: {} bytes (max {} bytes)",
                smart_contract_id,
                data.slot_id,
                data.data.len(),
                config.chunk_size
            );
            return Ok(false);
        }

        // validate -- must be a valid chunk
        let Some(expected_version) = expected_versions.get(data.slot_id as usize) else {
            info!(
                "Received StackerDBChunk for {} ID {}, which is too big ({})",
                smart_contract_id,
                data.slot_id,
                expected_versions.len()
            );
            return Ok(false);
        };

        // validate -- must be signed by the expected author

            .stackerdbs
            .get_slot_signer(smart_contract_id, data.slot_id)?
        {

            None => {
                return Ok(false);
            }
        };

        if !slot_metadata.verify(&addr)? {
            info!(
                "StackerDBChunk for {} ID {} is not signed by {}",
                smart_contract_id, data.slot_id, &addr
            );
            return Ok(false);
        }
