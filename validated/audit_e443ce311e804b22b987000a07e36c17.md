### Title
Unvalidated `git_object_directory` / `git_alternate_object_directories` Repository fields allow object-directory path injection - ([File: internal/git/gitcmd/command_factory.go])

### Summary
Every `gitalypb.Repository` message carries caller-supplied `git_object_directory` and `git_alternate_object_directories` fields that are meant to carry Gitaly-generated quarantine paths, but nothing in the generic command-construction path or in repository validation restricts these values to a safe, storage-scoped set before they are turned into `GIT_OBJECT_DIRECTORY` / `GIT_ALTERNATE_OBJECT_DIRECTORIES` environment variables for every spawned git process. This mirrors the reported bug class: a caller-chosen field that determines a security-relevant destination/path is accepted without being checked against a set of acceptable values.

### Finding Description
The `Repository` protobuf message exposes these fields directly to RPC callers: [1](#0-0) 

`configLocator.ValidateRepository`, the central repository-validation routine invoked by most RPC handlers, only checks `StorageName` and `RelativePath` — it never inspects `GitObjectDirectory` or `GitAlternateObjectDirectories`: [2](#0-1) 

Yet the generic git-command construction path, used by essentially every git invocation issued through `ExecCommandFactory`, takes these unvalidated fields verbatim and feeds them to `alternates.Env(...)`, which is then prepended to the process environment: [3](#0-2) 

By contrast, other call sites in the codebase that resolve `GitObjectDirectory` do apply strict containment checks — e.g. `Repo.ObjectDirectoryPath` explicitly calls `storage.ValidateRelativePath` and rejects paths that escape the repository/storage, only allowing the transaction quarantine directory as an exception: [4](#0-3) [5](#0-4) 

Likewise, when Git itself resolves alternates from the on-disk `objects/info/alternates` file, Gitaly enforces that resolved paths stay within the storage root and rejects them otherwise: [6](#0-5) 

However, that containment check only applies to paths discovered by reading the alternates file from disk — it is not applied to the `git_alternate_object_directories` / `git_object_directory` values carried on the RPC `Repository` message when they are consumed by `newCommand`/`alternates.Env`. The custom-hooks environment builder shows the same unguarded pattern, joining `repoPath` with the caller-provided alternate directories without any containment check: [7](#0-6) 

I was not able to retrieve the full body of `internal/git/alternates/alternates.go`'s `Env` function in this session (tool budget exhausted), so I cannot confirm with certainty whether it performs any additional sanitation beyond a simple path join; based on every other call site inspected, no such check exists for this particular field at the point it is consumed to build the process environment.

### Impact Explanation
If a value such as `../../other-storage/other-repo/objects` (or an absolute path) is accepted in `git_object_directory`/`git_alternate_object_directories` and reaches `newCommand` unfiltered, Git operations for the target repository would read (via `GIT_ALTERNATE_OBJECT_DIRECTORIES`) or write (via `GIT_OBJECT_DIRECTORY`) objects outside of the repository's own object store — i.e., cross-repository object access or storage escape, since Gitaly's storage isolation model assumes objects for repository A never become visible/reachable through repository B without going through the pool/alternates linking APIs that do enforce these boundaries (`internal/git/objectpool`, `internal/git/dirs.go`).

### Likelihood Explanation
These `Repository` fields are part of the wire message for effectively all RPCs and are echoed back to Gitaly by GitLab Rails during quarantine-aware access checks (as documented in `doc/object_quarantine.md`), meaning any code path that forwards a `Repository` message a caller can influence (directly via gRPC, or indirectly by proxying quarantine metadata) can reach this sink. Because `ValidateRepository` does not check these fields at all, likelihood of reachability is high for any RPC that accepts a `Repository` with `target_repository` semantics.

### Recommendation
Add explicit containment validation for `GitObjectDirectory` and `GitAlternateObjectDirectories` at the point they are consumed to build the git process environment (`internal/git/gitcmd/command_factory.go`, `internal/git/alternates/alternates.go`, `internal/gitaly/hook/custom.go`), reusing the same `storage.ValidateRelativePath`/quarantine-prefix logic already implemented in `internal/git/localrepo/paths.go`'s `ObjectDirectoryPath`, so that any path resolving outside the storage root (or outside the permitted quarantine/tempdir prefix) is rejected before the environment variables are set.

### Proof of Concept
Conceptual PoC (exact reachability of an unauthenticated/ordinary RPC path needs runtime confirmation, which requires further investigation not possible with remaining tool budget):
1. Issue an RPC that accepts a `target_repository`-annotated `Repository` message (e.g. any RPC using `s.localRepoFactory.Build(repoProto)` / `ExecCommandFactory`).
2. Set `git_alternate_object_directories: ["../../../<victim-storage>/<victim-repo>/objects"]` (or an absolute path) on the `Repository` message.
3. Because `ValidateRepository` (`internal/gitaly/config/locator.go:47-63`) does not inspect this field, the request passes validation.
4. `newCommand` (`internal/git/gitcmd/command_factory.go:519`) joins this value into `GIT_ALTERNATE_OBJECT_DIRECTORIES` for the spawned git process, letting it read objects from the victim repository/storage that it should not have access to.

func (l *configLocator) ValidateRepository(ctx context.Context, repo storage.Repository, opts ...storage.ValidateRepositoryOption) error {
	var cfg storage.ValidateRepositoryConfig
	for _, opt := range opts {
		opt(&cfg)
	}

	// Only checking for `nil` isn't sufficient as Protobuf messages may be non-nil, but still
	// either invalid or empty. Thus we also explicitly verify whether both the storage name and
	// the relative path are unset.
	if repo == nil || repo.GetStorageName() == "" && repo.GetRelativePath() == "" {
		return structerr.NewInvalidArgument("%w", storage.ErrRepositoryNotSet)
	}

	relativePath := repo.GetRelativePath()
	if len(relativePath) == 0 {
		return structerr.NewInvalidArgument("%w", storage.ErrRepositoryPathNotSet)
	}

// ObjectDirectoryPath returns the full path of the object directory. The errors returned are gRPC
// errors with relevant error codes and should be passed back to gRPC without further decoration.
func (repo *Repo) ObjectDirectoryPath(ctx context.Context) (string, error) {
	repoPath, err := repo.Path(ctx)
	if err != nil {
		return "", err
	}

	objectDirectoryPath := repo.GetGitObjectDirectory()
	if objectDirectoryPath == "" {
		return "", structerr.NewInvalidArgument("object directory path is not set")
	}

	storagePath, err := repo.locator.GetStorageByName(ctx, repo.GetStorageName())
	if err != nil {
		return "", fmt.Errorf("get storage by name: %w", err)
	}

	// Ensure the path points somewhere in the storage.
	relativeObjectDirectoryPath, err := storage.ValidateRelativePath(storagePath, filepath.Join(repoPath, objectDirectoryPath))
	if err != nil {
		return "", structerr.NewInvalidArgument("validate relative path: %w", err)
	}
