### Title
Newline injection via path-scoped revisions allows `git rev-list --stdin` flag/option injection - (File: internal/gitaly/service/blob/lfs_pointers.go)

### Summary
`ListLFSPointers` validates each attacker-supplied revision with `git.ValidateRevision([]byte(revision), git.AllowPathScopedRevision(), git.AllowPseudoRevision())`, but `AllowPathScopedRevision` only validates the portion of the string before the first `:` and leaves everything after it completely unchecked (including newlines, leading `-`, and backslashes). The raw, still-attacker-controlled revision strings are subsequently joined with `\n` and piped to `git rev-list --stdin` in `internal/git/gitpipe/revision.go`, so an embedded newline in the "path" component lets an attacker smuggle an additional line that `git rev-list --stdin` parses as a standalone argument/option.

### Finding Description
`ValidateRevision` (`internal/git/revision.go:44-97`) performs its dash-prefix, whitespace, and backslash checks on the *whole* revision first, then does `revision, _, _ = bytes.Cut(revision, []byte(":"))` when `AllowPathScopedRevision` is set (`internal/git/revision.go:81`), replacing `revision` with only the part *before* the first colon for all subsequent checks. Consequently, whitespace (`\n`, `\r`, space, tab), leading `-`, and `\\` checks (`internal/git/revision.go:87-95`) are only applied to the pre-colon prefix — the doc comment even states "a path-scoped revision may contain any character except for NUL bytes... including newlines" (`internal/git/revision.go:26-27`), confirming this is a deliberate but dangerous relaxation.

`ListLFSPointers` (`internal/gitaly/service/blob/lfs_pointers.go:38-42`) calls this exact validator and then passes the raw, unmodified `in.GetRevisions()` slice into `gitpipe.Revlist` (`internal/gitaly/service/blob/lfs_pointers.go:60-64`). Inside `Revlist`, revisions are supplied to git not as separate argv elements but concatenated with `strings.Join(revisions, "\n")` and written to the child process's stdin (`internal/git/gitpipe/revision.go:453-458`), with `--stdin` passed as a flag (`internal/git/gitpipe/revision.go:333-335`). `git rev-list --stdin` parses each line of stdin exactly as if it were a separate command-line argument — including recognizing `-`-prefixed flags/options.

Because the only pre-colon segment is checked for a `-` prefix, an attacker can submit a revision such as:
```
HEAD:junk\n--output=/some/path
```
This passes `ValidateRevision` because the checked prefix is just `HEAD` (no leading dash, no whitespace, no backslash); the unchecked suffix `junk\n--output=/some/path` contains the injected newline. When joined into the stdin stream, git sees two lines: `HEAD:junk` and `--output=/some/path`, and parses the second line as a standalone option to `git-rev-list(1)`, which is not filtered by any of Gitaly's `gitcmd` command-line flag allowlisting because it never goes through `gitcmd.Flag`/argv construction — it bypasses that layer entirely via stdin.

### Impact Explanation
This corresponds to Git's documented `--output=<file>` option, which causes `git-rev-list`/`git-log` to write its listing to an arbitrary filesystem path instead of stdout. If reachable, this is an arbitrary file write primitive from an unprivileged gRPC caller (matches GitLab's "arbitrary file write / command injection via git option" bounty class). The severity depends on which paths are writable by the `git` process user (repository storage root, gitaly-owned directories) and whether write permissions on attacker-reachable directories allow further escalation (e.g., overwriting hooks or config files consumed later).

### Likelihood Explanation
Precondition is only what the question specifies: an unprivileged, authenticated caller invoking `ListLFSPointers` with a crafted `Revisions` field — no special role, repo state, or non-default configuration is required. The bug is deterministic and repeatable given the exact byte sequence (`<validname>:<anything>\n<flag>`), so it is a reliable, low-effort trigger once the crafted revision string is constructed. The only remaining uncertainty (which I could not fully verify without live git binary testing in this environment) is whether git's stdin `--stdin` revision reader for `rev-list` accepts and applies `--output` (and other option-like lines) mid-stream exactly the same way argv would — this is documented Git behavior but I did not execute a live PoC against the actual git binary in this sandbox to confirm the precise git version's parsing semantics for injected stdin lines.

### Recommendation
In `ValidateRevision` (`internal/git/revision.go`), when `AllowPathScopedRevision` cuts off the path component, still forbid NUL and newline/CR characters in the *entire* original revision (including the path suffix) before allowing it through, since git-rev-list treats embedded `\n` as a line/argument separator when read via `--stdin`. At minimum, reject any revision containing `\n` or `\r` regardless of `AllowPathScopedRevision`, and/or change `gitpipe.Revlist` to write each revision as its own NUL-terminated record via `git rev-list --stdin --end-of-options` semantics, or prefix ambiguous revisions with `--` / `./` so stdin lines can never be interpreted as options.
