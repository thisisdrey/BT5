### Title
`RemoveRepositoryHandler` unconditionally deletes Praefect's tracking record before physical deletion succeeds, permanently leaking untracked repository data on Gitaly nodes - (File: internal/praefect/remove_repository.go)

### Finding Description
`removeRepositoryHandler` follows the same "point-then-withdraw" pattern flagged in the Sherlock finding: it commits the authoritative state change (`rs.DeleteRepository`, which removes the repository's row from `repositories`/`storage_repositories`) *before* the actual data removal on the backing storages has been confirmed to succeed. [1](#0-0) 

After that irreversible bookkeeping change, the handler attempts a best-effort, time-bounded fan-out delete to every physical storage: [2](#0-1) 

The 10-second timeout and the per-goroutine `logger...ErrorContext(ctx, "failed deleting repository")` mean that any Gitaly node which cannot finish `RemoveRepository` in time — because it is under I/O/CPU load, has git processes holding the repository lock, is doing housekeeping, or is simply slow/unreachable — is left with the physical repository fully intact on disk, while Praefect's control plane has already forgotten it exists. This is architecturally identical to `updateYieldStrategy`: the pointer/authoritative record is switched unconditionally, and the "old" resource (the repository copy on that Gitaly node) is left in a state that is orphaned from the system that used to own it.

The recovery path is a background `repocleaner.Runner` that walks Gitaly storages and compares against the database, but the wired-in default action is `LogWarnAction`, which only logs a warning — it does not delete or reconcile the untracked replica: [3](#0-2) [4](#0-3) 

So unlike `objectpool.Disconnect`, which performs the exact mitigation recommended in the report (link objects first, run `git-fsck`, and only remove the alternates file — with automatic rollback — if the connectivity check passes) [5](#0-4) , `RemoveRepositoryHandler` has no analogous "verify full completion, else roll back" step, and the default operational configuration doesn't even auto-heal the resulting inconsistency.

### Impact Explanation
Any client authorized to call `RemoveRepository` through Praefect (the normal, unprivileged RPC path used for repository/fork deletion, not an admin-only tool) can, on a cluster with a transiently slow or loaded node, cause a permanent split: Praefect's database says the repository is gone, but one or more Gitaly nodes retain the full repository (objects, refs, hooks config) indefinitely unless an operator manually notices the `LogWarnAction` warning and intervenes. This is a resource/data leak (disk space never reclaimed, stale data left reachable by direct storage access or by future path reuse edge cases) with no automated remediation in the default configuration — the practical analogue of the "funds frozen with the old Strategy" scenario, except the frozen resource here is on-disk repository state.

### Likelihood Explanation
Requires nothing more than issuing an ordinary `RemoveRepository` RPC (reachable for any repository a user is permitted to delete) while one of the replicas' Gitaly node is momentarily slow to respond — e.g., mid-housekeeping/repack, high disk I/O, or brief network hiccup — well within the routine operating conditions Gitaly explicitly tries to survive (this is the same "high utilization" trigger cited in the original report, just for storage I/O instead of lending-market liquidity). The comment in the code ("It's not critical these deletions complete...") shows the authors were aware partial completion is expected/common, not a rare edge case.

### Recommendation
- Do not delete the Praefect-side tracking record until physical deletion has been confirmed on all target storages, or make the operation transactionally safe (e.g., mark the repository "pending deletion" and only remove the DB record after all storages acknowledge deletion, retrying failed ones).
- If best-effort deletion with eventual consistency is retained, make the default repocleaner action perform actual cleanup (or forced re-deletion) of untracked replicas instead of `LogWarnAction`, so orphaned data doesn't require manual operator action to reclaim.
- Increase/parameterize the deletion timeout or make it configurable so that legitimately busy nodes aren't cut off before completing, and surface partial-failure state (e.g., a queryable "pending physical deletion" list) rather than silent logs.

### Proof of Concept
1. Configure a 3-node Praefect cluster with `repositories_cleanup` using the default `LogWarnAction`.
2. Create a repository so it's replicated to `gitaly-1`, `gitaly-2`, `gitaly-3`.
3. Induce load/slowness on `gitaly-3` (e.g., run a heavy repack, or throttle I/O) so that its `RemoveRepository` RPC cannot complete within the hard-coded 10s timeout used in `removeRepositoryHandler`.
4. Call Praefect's `RemoveRepository` for that repository. `rs.DeleteRepository` succeeds immediately, deleting Praefect's DB records for all storages (including `gitaly-3`).
5. The goroutine deleting on `gitaly-3` times out; the error is only logged, not retried.
6. The repository directory remains on `gitaly-3`'s disk indefinitely; Praefect no longer tracks it, and the only signal is a warning log line from the (non-remediating) `LogWarnAction` next time the repocleaner scans that storage.
