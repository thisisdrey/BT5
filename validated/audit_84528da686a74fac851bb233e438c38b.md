Audit Report

## Title
Unchecked Zero-Point Issuance in `try_bond_funds` Can Silently Lock Bonded Funds With No Pool Credit - ([File: substrate/frame/nomination-pools/src/lib.rs])

## Summary
`BondedPool::try_bond_funds` (`substrate/frame/nomination-pools/src/lib.rs` L1315-1337) stakes a member's funds and issues pool points via `self.issue(amount)` (L1080-1085), which calls the truncating-integer-division `balance_to_point`, but never verifies `points_issued` is non-zero before staking the funds and incrementing `TotalValueLocked`. This allows a legitimate nonzero deposit to be staked into the pool while the depositor receives zero points, permanently losing their claim on the contributed value.

## Finding Description
`try_bond_funds` computes `points_issued = self.issue(amount)` and unconditionally proceeds to call `T::StakeAdapter::pledge_bond` and increment `TotalValueLocked`, returning `points_issued` with no floor check. [1](#0-0) 

`issue` derives points via `balance_to_point`, whose sibling `point_to_balance` documents the truncating `u256` division that can floor small inputs to zero; `balance_to_point` performs the analogous computation and is equally susceptible to truncation when the balance:points ratio is skewed. [2](#0-1) [3](#0-2) 

This zero-point result flows unchecked into `join`, `do_bond_extra`, and `do_create`, all of which store `points_issued` directly as/added-to the member's `points` without validating non-zero. [4](#0-3) [5](#0-4) 

However, review of the `join` extrinsic shows an existing guard not addressed in the original claim: `ensure!(amount >= MinJoinBond::<T>::get(), Error::<T>::MinimumBondNotMet);` at L2132, which rejects any deposit below a configurable minimum before `try_bond_funds` is ever invoked. [6](#0-5) 

This guard reduces — but does not eliminate — the exploit window: `MinJoinBond` bounds the raw `amount`, while `ok_to_join`'s `OverflowRisk` check only bounds the points:balance ratio up to `MaxPointsToBalance`, as shown in `ok_to_join_with_works`. Neither guard directly checks that `balance_to_point(bonded_balance, points, amount)` is non-zero, so if a pool operator sets `MinJoinBond` low relative to a large `bonded_balance/points` ratio (within the `MaxPointsToBalance` bound), the truncation-to-zero scenario remains reachable via `join`. The `bond_extra`/`bond_extra_other` paths (`do_bond_extra`) have no equivalent minimum-amount check at all, since rewards claimed via `BondExtra::Rewards` or a caller-chosen `BondExtra::FreeBalance` amount are not subject to `MinJoinBond`. [5](#0-4) 

## Impact Explanation
If `points_issued` is zero for a nonzero staked `amount`, funds are transferred/staked into the pool (increasing `TotalValueLocked` and the pool's real bonded balance) but the depositor's `PoolMember.points` remain zero, permanently severing their claim on the value they contributed — an unrecoverable fund lock for the depositor and a de facto pro-rata donation to existing members. This matches the "permanent user-fund lock" / "value not conserved to rightful beneficiary" impact class in scope.

## Likelihood Explanation
Exploitability is constrained by two existing (partial) guards: `MinJoinBond` on the `join` path, and the `OverflowRisk` ratio bound in `ok_to_join`/`ok_to_be_open`. Neither guard is a direct zero-point check, so the bug remains reachable when a pool's points:balance ratio is skewed enough (via slashing/growth, but still within `MaxPointsToBalance`) and either `MinJoinBond` is configured low enough, or the `bond_extra`/`bond_extra_other`/`create` paths are used (which have no minimum-amount floor at all). This is a real but state-dependent condition rather than trivially exploitable against any pool in its default configuration.

## Recommendation
Add an explicit non-zero check on `points_issued` inside `try_bond_funds` immediately after `self.issue(amount)`, rejecting the bond (via a new `Error::<T>::InsufficientBond` or similar) whenever `amount` is nonzero but `points_issued` is zero — mirroring the `InsufficientLiquidityMinted` guard in `pallet_asset_conversion::do_add_liquidity`.

## Proof of Concept
1. Construct or drive a pool to a state where `bonded_balance / points` is large but still within `MaxPointsToBalance` (satisfying `ok_to_join`'s `OverflowRisk` check).
2. Call `Pools::bond_extra(origin, BondExtra::FreeBalance(amount))` (unconstrained by `MinJoinBond`) with an `amount` small enough that `balance_to_point(bonded_balance, points, amount)` truncates to `0`.
3. Observe `do_bond_extra` stakes `amount` via `try_bond_funds`, `TotalValueLocked` increases, but `member.points` is unchanged (added `0`).
4. The depositor's contributed funds are staked but their `points` do not reflect the contribution — permanently locking their claim on that value.

	fn try_bond_funds(
		&mut self,
		who: &T::AccountId,
		amount: BalanceOf<T>,
		ty: BondType,
	) -> Result<BalanceOf<T>, DispatchError> {
		// We must calculate the points issued *before* we bond who's funds, else points:balance
		// ratio will be wrong.
		let points_issued = self.issue(amount);

		T::StakeAdapter::pledge_bond(
			Member::from(who.clone()),

			&self.reward_account(),
			amount,
			ty,
		)?;
		TotalValueLocked::<T>::mutate(|tvl| {
			tvl.saturating_accrue(amount);
		});

		Ok(points_issued)
	}

	fn point_to_balance(
		current_balance: BalanceOf<T>,
		current_points: BalanceOf<T>,
		points: BalanceOf<T>,
	) -> BalanceOf<T> {
		let u256 = T::BalanceToU256::convert;
		let balance = T::U256ToBalance::convert;
		if current_balance.is_zero() || current_points.is_zero() || points.is_zero() {
			// There is nothing to unbond
			return Zero::zero();
		}

		// Equivalent of (current_balance / current_points) * points
		balance(
			u256(current_balance)
				.saturating_mul(u256(points))
				// We check for zero above
				.div(u256(current_points)),
		)
	}
