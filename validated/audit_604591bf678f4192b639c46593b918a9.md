### Title
StackerDB Chunk Signatures Omit the Contract Identifier, Enabling Cross-Contract Replay of Authenticated Chunks - (File: `libstackerdb/src/libstackerdb.rs`)

### Summary
`SlotMetadata::auth_digest()` — the digest that `SlotMetadata::sign`/`SlotMetadata::verify` and therefore `StackerDBChunkData::sign`/`verify` operate on — binds only `slot_id`, `slot_version`, and `data_hash`. It never binds the target `QualifiedContractIdentifier` (the StackerDB instance) the chunk is meant for. Because many sibling StackerDB contracts share the exact same slot→signer mapping (all `signers-{set}-{message_id}` contracts read the same signer-slot page from `.signers`), a chunk validly signed for slot N in one contract is also a valid signature for slot N in every sibling contract for the same signer set. This is the direct analog of the Netty OCSP bug, where a signature/response valid for one identity was accepted for an unrelated one because the identity (CertificateID) was never checked.

### Finding Description
The signing/verification digest is computed as:
```
libstackerdb/src/libstackerdb.rs:159-166
fn auth_digest(&self) -> Sha512Trunc256Sum {
    let mut hasher = Sha512_256::new();
    hasher.update(self.slot_id.to_be_bytes());
    hasher.update(self.slot_version.to_be_bytes());
    hasher.update(self.data_hash.0);
    Sha512Trunc256Sum::from_hasher(hasher)
}
``` [1](#0-0) 

No smart-contract identifier is included. `StackerDBChunkData::sign`/`verify` simply delegate to this digest via `get_slot_metadata()`: [2](#0-1) 

Both server-side validation paths accept a chunk purely on `(slot_id, slot_version, data_hash)` signature validity plus a *per-contract* lookup of the expected signer address and version — but the signature itself carries no contract binding:

- HTTP write path: `try_replace_chunk` looks up the slot's expected signer for the given `smart_contract`, then calls `slot_desc.verify(&slot_validation.signer)?` — which only checks that the digest (slot_id/version/hash) was signed by that address, not that it was signed *for this contract*: [3](#0-2) 

- P2P sync/gossip path: `validate_received_chunk` does the same — fetch `get_slot_signer(smart_contract_id, data.slot_id)`, then `slot_metadata.verify(&addr)?`, with no contract-identity check in the signature itself: [4](#0-3) 

- The HTTP POST endpoint takes `contract_identifier` purely from the URL path and passes it only for lookup/storage — it is never mixed into what is authenticated: [5](#0-4) [6](#0-5) 

Critically, the slot→signer mapping is *identical* across every sibling message-type contract for a given signer set, because they all delegate to the same `.signers` page:
```

This is confirmed by the test that shows every `signers-{set}-{message_id}` contract, for a given set, returns the exact same `stackerdb-get-signer-slots` list: [9](#0-8) 

And the node instantiates one such sibling contract per `message_id` per signer set: [10](#0-9) 

Consequently: signer S occupies slot N in `signers-0-0` (e.g. the `Transactions` message contract) and also slot N in `signers-0-1`, `signers-0-2`, ... (e.g. `BlockResponse`, `StateMachineUpdate`, etc.) for the same signer set. A `(slot_id=N, slot_version=V, sig, data)` tuple that S legitimately signed and posted to one of these sibling contracts is a byte-for-byte valid, independently verifiable `StackerDBChunkData` for slot N in every other sibling contract, as long as the target contract's current slot version for N is `< V`. Since each sibling contract's slot versions increase and reset independently (each has its own `SlotMetadata`/`slot_validation` row per contract, per `try_replace_chunk`), this precondition is trivially satisfiable — e.g. immediately after node/contract initialization, all versions start at 0, so almost any previously-observed valid chunk with version ≥ 1 can be replayed.

### Impact Explanation
An unprivileged network observer who captures one signer's legitimately signed chunk (from p2p gossip, from public StackerDB inventory sync, or from the public HTTP `POST /v2/stackerdb/.../chunks` push-back) can replay the exact same bytes to a sibling `signers-{set}-{other_message_id}` contract owned by that same signer. The server-side signature check (`slot_desc.verify(&slot_validation.signer)`) succeeds because the digest never encodes which contract it was meant for, and the write is accepted and stored as if that signer had authored a chunk of the *wrong message type* for that slot. This chunk is then propagated network-wide through normal StackerDB p2p relay logic (`try_replace_chunk` → `handle_unsolicited_StackerDBPushChunk` → gossip to peers), i.e. forged/mis-attributed data is durably stored and disseminated across the network as if it were an authentic message of that type from that signer — an unauthorized write to StackerDB state plus network-wide propagation of forged (mis-typed) signer data. Downstream StackerDB consumers that dispatch strictly by contract/message type (e.g. `StackerDBListener`) would then attempt to deserialize attacker-replayed bytes as the wrong `SignerMessageV0` variant, at minimum causing parse failures/ignored messages, and at worst corrupting a signer's apparent state in an unrelated message channel.

### Likelihood Explanation
High. No secrets are required — only observation of one publicly-relayed, validly-signed StackerDB chunk (chunks are gossiped/replicated across all nodes and are also retrievable via ordinary read RPCs), plus a plain unauthenticated `POST /v2/stackerdb/{address}/{contract}/chunks` request to a sibling contract. The precondition (target slot version lower than the replayed version) is satisfied by default for many sibling contracts (e.g. freshly-instantiated message-type contracts, or contracts that see less traffic than the one the chunk was captured from).

### Recommendation
Include the target `QualifiedContractIdentifier` (and ideally the message/purpose it is tied to) in the signed digest — i.e. modify `SlotMetadata::auth_digest()` (or add a contract-bound wrapper used at sign/verify time) to hash the contract's issuer/name (and message-type discriminator if applicable) alongside `slot_id`, `slot_version`, and `data_hash`, mirroring RFC 6960 §3.2's requirement that the identifier in the signed artifact matches the one for which it is being used. This is a wire-format/protocol change (must be versioned carefully to remain compatible with existing chunk consumers).

### Proof of Concept
1. Observe (via p2p relay, StackerDB read RPC, or gossip capture) a legitimately signed `StackerDBChunkData { slot_id: N, slot_version: V, sig, data }` that signer S posted to contract `signers-0-M1` (slot N owned by S).
2. Confirm slot N in sibling contract `signers-0-M2` (different `message_id`, same signer set) is also owned by S (guaranteed, since both derive from the same `.signers stackerdb-get-signer-slots-page`).
3. Send:
```
POST /v2/stackerdb/{S_or_boot_addr}/signers-0-M2/chunks
{ "slot_id": N, "slot_version": V, "sig": <same sig bytes>, "data": <same data bytes> }
```
4. Server calls `try_replace_chunk` on `signers-0-M2`: it fetches the slot's expected signer (S), calls `slot_desc.verify(&S)` which succeeds (digest matches, since slot_id/version/data_hash are unchanged), and if `signers-0-M2`'s current slot N version `< V`, the write is accepted — `StackerDBErrorCodes::BadSigner`/`StaleChunk` is not returned — and the chunk is relayed via `StackerDBPushChunk` to the network, all without any privileged access, matching `stackslib/src/net/stackerdb/db.rs:411-423` and `stackslib/src/net/api/poststackerdbchunk.rs:197-201`.

    /// Sets self.signature to the signature.
    /// Fails if the underlying signing library fails.
    pub fn sign(&mut self, privk: &StacksPrivateKey) -> Result<(), Error> {
        let mut md = self.get_slot_metadata();
        md.sign(privk)?;
        self.sig = md.signature;
        Ok(())
    }

    pub fn recover_pk(&self) -> Result<StacksPublicKey, Error> {
        let digest = self.get_slot_metadata().auth_digest();
        StacksPublicKey::recover_to_pubkey_without_validating_low_s(digest.as_bytes(), &self.sig)
            .map_err(|ve| Error::VerifyingError(ve.to_string()))
    }
