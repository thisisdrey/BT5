### Title
Users can be liquidated while deposits are paused — cannot add collateral to save position - (File: contracts/Pool.sol)

### Summary
Metronome Synth's `Pool` implements a two-level emergency-stop scheme identical in shape to the Unstoppable Vault's `is_accepting_new_orders` / unpauseable `liquidate` split. `Pool.pause()` (or `PoolRegistry.pause()`) blocks `DepositToken.deposit()` via `whenNotPaused`, but `Pool.liquidate()` is gated only by `whenNotShutdown`. A user whose position becomes unhealthy while the pool is paused cannot deposit additional collateral to restore health, yet any liquidator can still seize their collateral (plus liquidation incentive and protocol fee).

### Finding Description
- `DepositToken.deposit()` is declared `whenNotPaused` (contracts/DepositToken.sol:214). `Manageable.whenNotPaused` reverts `IsPaused` if `pool.paused()` is true (contracts/access/Manageable.sol:46-49), and `Pool.paused()` additionally ORs in `_poolRegistry.paused()` (contracts/Pool.sol:608-610), so a pause at either level blocks collateral deposits.
- `Pool.liquidate()` is declared `whenNotShutdown` only (contracts/Pool.sol:537-550); it burns the liquidator's synth, burns the victim's debt token, and calls `depositToken_.seize()` to take collateral plus fee (lines 587-593).
- `docs/emergency-flags.md` states this explicitly: `DepositToken.deposit()` is disabled by `PoolRegistry.paused() || Pool.paused()`, while `Pool.liquidate()` is disabled only by `everythingStopped()`.
- The test suite enshrines the asymmetry: `test/Pool.test.ts` case "should not revert if paused" calls `pool.pause()` then successfully executes `pool.liquidate(...)` emitting `PositionLiquidated` (test/Pool.test.ts:353-365).
- Attack/impact path: user deposits collateral and issues synth debt; collateral price drops so `debtPositionOf(account)` returns `_isHealthy == false`; governor pauses the pool (e.g., routine incident response); user's `deposit()` reverts with `IsPaused`, so they cannot raise `_issuableLimitInUsd`; a liquidator calls `pool.liquidate(syntheticToken_, account_, amountToRepay_, depositToken_)` which passes the health check, `maxLiquidable` cap, and `debtFloorInUsd` check, and seizes collateral including `_liquidatorIncentive` and `_protocolFee`.
- `DebtToken.repay()`/`repayAll()` also remain available during pause (disabled only on `everythingStopped()` per docs/emergency-flags.md), but they require the victim to hold the synthetic token — a user who already sold the minted synth has no way to acquire it cheaply on-demand while the pool's `swap` may also be unavailable, and cannot deleverage via fresh collateral. This mirrors the original finding where `fund_account`/`add_margin` were paused but `liquidate` was not.

### Impact Explanation
Unfair forced liquidation with direct loss of user funds: the user loses collateral equal to the repaid debt plus the liquidator incentive and protocol fee (`quoteLiquidateOut`, contracts/Pool.sol:451-472) in a window where the only non-speculative remedy (depositing more collateral) is disabled by the protocol itself.

### Likelihood Explanation
Requires two conditions: (1) the governor pauses the pool while (2) a position is or becomes unhealthy during the pause window. Pausing is a routine emergency action, and oracle-driven price moves can make positions unhealthy at any time, including while paused. The liquidator is unprivileged and only calls the public `liquidate`. Not exploitable on demand by an attacker, but reliably triggerable whenever a pause coincides with unhealthy positions — the same reasoning accepted for the analogous Sherlock High.

### Recommendation
Either block `Pool.liquidate()` while `paused()` (i.e., add `whenNotPaused` or make pause imply shutdown for liquidations), or provide an always-available path to improve health during pause (e.g., allow `DepositToken.deposit()` for topping up existing accounts, or an explicit `addCollateral` that cannot create new exposure). Note that `shutdown()` already sets both flags (`Pauseable.sol:113-117`), so operators could alternatively be instructed to use `shutdown()` instead of `pause()` when liquidations must also halt — but relying on operator discipline leaves the flaw intact.

### Proof of Concept
Reproducible with the existing Hardhat setup (mirroring test/Pool.test.ts):

```ts
// 1. Alice deposits MET collateral and issues msETH debt.
await msdMET.connect(alice).deposit(userDepositAmount, alice.address)
await msEthDebtToken.connect(alice).issue(userMintAmount, alice.address)

// 2. Collateral price drops -> alice is unhealthy.
await masterOracle.updatePrice(met.address, toUSD('0.95'))
expect((await pool.debtPositionOf(alice.address))._isHealthy).false

// 3. Governor pauses the pool (deposit-only pause, NOT shutdown).
await pool.pause()

// 4. Alice cannot add collateral to restore health.
await expect(
  msdMET.connect(alice).deposit(extraCollateral, alice.address)
).revertedWithCustomError(msdMET, 'IsPaused')

// 5. Liquidator still seizes her collateral + incentive + fee.
await expect(
  pool.connect(liquidator).liquidate(
    msEth.address, alice.address, amountToRepay, msdMET.address)
).emit(pool, 'PositionLiquidated')
```

This is exactly the existing test at test/Pool.test.ts:353-365 ("should not revert if paused") combined with a `deposit` revert, demonstrating the asymmetry end-to-end on the deployed configuration.
