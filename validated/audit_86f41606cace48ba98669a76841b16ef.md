Based on my research, I found a viable analog in java-tron's TVM precompiled-contract call path, distinct from the actuator/exchange functions I also reviewed (which are already correctly gated by explicit owner/signer checks and don't match this bug class).

### Title
Permanent loss of TRX/TRC10 sent via `CALL` with value to TVM precompiled contract addresses - (File: actuator/src/main/java/org/tron/core/vm/program/Program.java)

### Summary
`Program.callToPrecompiledAddress()` unconditionally transfers any TRX or TRC10 `endowment` attached to a `CALL`/`CALLCODE` to the target precompiled contract's address balance before executing the precompile logic, exactly mirroring the external report's root cause: a fund-receiving code path that was never designed to hold or move value, invoked by an unsuspecting/careless caller, permanently traps the funds.

### Finding Description
When a smart contract (or any transaction constructing a message call) issues a `CALL` to one of the fixed precompiled contract addresses (e.g. the ECRecover, SHA256, batch validate-sign, etc. addresses) with a non-zero `msg.value`, `callToPrecompiledAddress()` executes: [1](#0-0) 
This code performs `MUtil.transfer(deposit, senderAddress, contextAddress, endowment)` (or the TRC10 equivalent) directly into the precompiled address's account balance, *before* checking whether the call will even succeed or is meaningful for that precompile. None of the precompiled contracts implemented in `PrecompiledContracts.PrecompiledContract` accept or forward TRX/TRC10 value, have an owner key, or expose any withdrawal mechanism — they are fixed, keyless system addresses. Unlike a normal contract account, there's no `payable`-fallback logic, no owner, and no code that can ever move that balance back out, since these addresses are permanently reserved for precompile dispatch and are never treated as spendable accounts by any actuator.

This is the same underlying bug class as `payback()` in the Sherlock report: value-accepting logic reachable from an external, unprivileged transaction with no corresponding accounting/refund path, resulting in funds becoming permanently stuck.

### Impact Explanation
Any unprivileged party who deploys a contract or crafts a `TriggerSmartContract` that performs `<address>.call.value(x)()` (or equivalent low-level call) targeting a precompiled contract address will have `x` TRX (or TRC10) irrecoverably locked into an address with no private key and no contract logic to reclaim it. This is a permanent, unbacked freezing of funds — accepted under the "permanent freezing of funds" impact category — and can be triggered purely by a single signed transaction from any account, no privileged role required.

### Likelihood Explanation
This can be triggered accidentally (e.g. by a poorly written contract, or a user misusing low-level `call.value()` against a precompile address instead of a real contract) or deliberately, requiring only a normal signed `TriggerSmartContract` transaction — the "unprivileged transaction broadcaster/contract deployer" actor explicitly in scope. No special network condition, node role, or coordination is needed.

### Recommendation
In `callToPrecompiledAddress()`, reject calls that carry a non-zero `endowment` to a precompiled address before performing any balance transfer — i.e., short-circuit with a failure/revert (push zero, refund unused energy) instead of calling `MUtil.transfer`/`addTokenBalance` when `msg.value > 0` and the destination is a precompile. This mirrors how the Sherlock recommendation restricted the payable surface to only the legitimate internal path.

### Proof of Concept
1. Deploy or use any contract, and from it execute a low-level call such as `address(0x01000...09).call.value(100)("")` (any fixed precompile address, e.g. ecrecover/batchvalidatesign precompile address) via a `TriggerSmartContract` transaction.
2. Observe in `Program.callToAddress`/`callToPrecompiledAddress` that when `programCode` is empty for that address but it resolves to a precompiled contract, `MUtil.transfer(deposit, senderAddress, contextAddress, 100)` executes unconditionally at [2](#0-1) , crediting 100 sun to the precompile address's `AccountCapsule` balance.
3. Confirm there is no actuator, precompile, or opcode in the codebase that permits withdrawing balance from a precompiled address — the value is permanently stranded.
