Confirmed: `submit_delivery_receipt` is a fully public, unprivileged extrinsic — any signed account can call it, and once the merkle/beacon proof verifies (`T::Verifier::verify`) and the log decodes into a `DeliveryReceipt`, `process_delivery_receipt` pays the reward and clears the order regardless of the `success` field's value.

### Title
`process_delivery_receipt` ignores the `DeliveryReceipt.success` flag, paying relayer rewards and settling orders even on failed Ethereum dispatch - (File: bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs)

### Summary
`DeliveryReceipt` decodes the `InboundMessageDispatched` Ethereum event, which carries an explicit `success: bool` field documented as "Delivery status" [1](#0-0) . `Pallet::process_delivery_receipt` never reads or branches on `receipt.success`; it unconditionally pays the relayer reward for `order.fee > 0` and removes the `PendingOrder` from storage [2](#0-1) . This mirrors the `retryMessage()` analog: a status flag that is supposed to gate the terminal state transition (reward/settlement vs. retry) is decoded but never consulted before the state is finalized.

### Finding Description
The extrinsic entrypoint `submit_delivery_receipt` is callable by any signed account (`ensure_signed(origin)?`), performs proof verification via `T::Verifier::verify`, decodes the log into `DeliveryReceipt`, and forwards to `process_delivery_receipt` [3](#0-2) . Inside `process_delivery_receipt`, the only checks performed are: gateway address match, and existence of a `PendingOrder` for `receipt.nonce` [4](#0-3) . There is no `ensure!(receipt.success, ...)` or branch that treats a failed dispatch (`success == false`) differently from a successful one — both paths pay the reward and remove the order, emitting `Event::MessageDelivered` regardless [5](#0-4) . The field is decoded from the real Ethereum event data (`event.success`) [6](#0-5)  and thus is attacker/reality-controlled by whatever actually happened on the Ethereum Gateway contract, but the pallet's business logic discards it.

### Impact Explanation
If the intended design (as strongly implied by the field name "Delivery status" and the parallel invariant from the external report) is that a relayer should only be rewarded and the order only "settled" when the message dispatch actually succeeded on Ethereum, this code silently breaks that invariant: a relayer submitting a receipt for a *failed* dispatch (`success = false`) still collects the fee and the order is permanently removed from `PendingOrders`, closing off any possibility of a legitimate retry/re-settlement path for that nonce. This is a fund-flow correctness bug in a public, unprivileged, signed-extrinsic entrypoint that governs bridge reward payout — exactly the class of "duplicate settlement or payout" / "permanent... bridge-state lock" impact called out in the Impact Gate, since a failed message's `PendingOrder` state is irreversibly finalized without regard to actual outcome.

### Likelihood Explanation
Any relayer that observes (or is told/forges via legitimately-verifiable event data) a Gateway `InboundMessageDispatched` event with `success = false` can submit it through `submit_delivery_receipt` — no privileged origin, governance, or malicious peer is required; only a valid proof of an on-chain Ethereum log, which is the normal/expected relayer workflow. All existing tests in the repo (`submit_delivery_receipt_succeeds_after_unhalt`, `send_weth_from_asset_hub_to_ethereum`, etc.) construct receipts with `success: true` [7](#0-6)  and none exercise or assert behavior for `success: false`, confirming the flag is unvalidated dead weight in current logic.

### Recommendation
Branch on `receipt.success` in `process_delivery_receipt`: only invoke `T::RewardPayment::register_reward` when `success == true`; for `success == false`, decide and implement the intended failure-path semantics (e.g., do not pay, and either retain the order for a bounded retry window or transition it to a distinct terminal "failed" state/event) instead of unconditionally calling `<PendingOrders<T>>::remove(nonce)` and emitting `Event::MessageDelivered`.

### Proof of Concept [2](#0-1) 
1. A message is queued via `do_process_message`, creating `PendingOrders[nonce]` with `fee > 0` [8](#0-7) .
2. The message is relayed to Ethereum and dispatch on the Gateway fails, so the emitted `InboundMessageDispatched` event has `success = false`.
3. Any signed relayer submits this real event log + proof via `submit_delivery_receipt`; `T::Verifier::verify` succeeds because the proof is genuine, and `DeliveryReceipt::try_from` decodes `success: false` faithfully [9](#0-8) .
4. `process_delivery_receipt` runs its gateway check and nonce lookup, finds `order.fee > 0`, calls `T::RewardPayment::register_reward` and removes the order — identical to the success path — despite `receipt.success == false` never being inspected [10](#0-9) .

impl TryFrom<&Log> for DeliveryReceipt {
	type Error = DeliveryReceiptDecodeError;

	fn try_from(log: &Log) -> Result<Self, Self::Error> {
		let topics: Vec<B256> = log.topics.iter().map(|x| B256::from_slice(x.as_ref())).collect();

		let event = InboundMessageDispatched::decode_raw_log_validate(topics, &log.data)
			.map_err(|_| DeliveryReceiptDecodeError::DecodeLogFailed)?;

		Ok(Self {
			gateway: log.address,
			nonce: event.nonce,
			topic: H256::from_slice(event.topic.as_ref()),
			success: event.success,
			reward_address: event.reward_address.0,
		})
	}

		/// Process a delivery receipt from a relayer, to allocate the relayer reward.
		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}

#[test]
fn submit_delivery_receipt_succeeds_after_unhalt() {
	new_tester().execute_with(|| {
		let nonce = 0;
		let fee: u128 = 1_000_000;
		let order = PendingOrder { nonce, fee, block_number: System::block_number() };
		PendingOrders::<Test>::insert(nonce, order);

		let relayer: AccountId32 = [7u8; 32].into();
		let origin = RuntimeOrigin::signed(relayer);
		let event = Box::new(mock_valid_event_proof());

		// Bridge halted — receipt rejected, order untouched.
		set_verifier_halted(true);
		assert_noop!(
			OutboundQueue::submit_delivery_receipt(origin.clone(), event.clone()),
			Error::<Test>::Verification(VerificationError::Halted)
		);
		assert!(PendingOrders::<Test>::get(nonce).is_some());

		// Bridge resumed — same receipt succeeds and the order is settled.
		set_verifier_halted(false);
		assert_ok!(OutboundQueue::submit_delivery_receipt(origin, event));
		assert!(PendingOrders::<Test>::get(nonce).is_none());

		System::assert_has_event(mock::RuntimeEvent::OutboundQueue(Event::MessageDelivered {
			nonce,
		}));
	});
