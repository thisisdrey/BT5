### Title
Potential null pointer dereference in `UnDelegateResourceActuator.execute()` from an inconsistent existence check between `validate()` and `execute()` - (`actuator/src/main/java/org/tron/core/actuator/UnDelegateResourceActuator.java`)

### Summary
`UnDelegateResourceActuator` (triggered by an unprivileged, signed `UnDelegateResourceContract` transaction) performs its "does the delegated resource exist" consistency check in `validate()` by only requiring that **either** the "unlock" bucket **or** the "lock" bucket of a `DelegatedResourceCapsule` be non-null, and by summing balances from whichever bucket(s) apply. `execute()`, however, unconditionally dereferences the "unlock" bucket capsule (`unlockResource`) without re-checking it for null, relying on an intermediate call to migrate any expired "lock" balance into the "unlock" bucket. If that migration does not populate the unlock bucket in every code path that `validate()` accepts, `execute()` will NPE while a block is being applied.

### Finding Description
In `validate()`: [1](#0-0) 
only requires `unlockResourceCapsule != null || lockResourceCapsule != null`, and the subsequent balance check for BANDWIDTH/ENERGY sums contributions from `unlockResourceCapsule` (if present) and from `lockResourceCapsule` (only if its lock has already expired): [2](#0-1) 

In `execute()`, the code calls `delegatedResourceStore.unLockExpireResource(...)` to migrate any expired lock balance into the unlock bucket, then re-fetches the unlock bucket and directly dereferences it with no null guard: [3](#0-2) 

The same pattern (fetch `unlockResource`/`delegatedResourceCapsule`, then call `.addFrozenBalanceForBandwidth(...)`/`.addFrozenBalanceForEnergy(...)` without a null check) is duplicated in the TVM native-contract precompile path used by smart contracts: [4](#0-3) 

This mirrors the structural class of the PowerDNS RPZ bug: a "consistency check" exists (`validate()`), but it does not verify the *exact* precondition that the execution code (`execute()`) actually depends on (a populated unlock-bucket capsule after migration) — it only verifies a looser OR-condition across two different storage buckets. The code even contains an explicit acknowledgment elsewhere in the same actuator that receiver-account state can legitimately become inconsistent (a comment notes "TVM contract suicide can result in no receiving account", and the corresponding null check for `receiverCapsule` was intentionally removed and instead handled with `if (receiverCapsule != null)` guards at lines 68 and 145/160). No equivalent guard exists for `unlockResource` in the same method.

### Impact Explanation
If `unLockExpireResource()` does not, in every case accepted by `validate()`, result in a non-null unlock-bucket capsule (for example, if the amount considered "expired" in `validate()`'s snapshot differs subtly from what the store mutation actually migrates, or the resource type used by `validate()`'s balance arithmetic diverges from the bucket the mutation populates), then `unlockResource.addFrozenBalanceForBandwidth(...)` / `.addFrozenBalanceForEnergy(...)` in `execute()` throws an unchecked `NullPointerException`. Because this happens inside `Manager`'s block-application / transaction-processing path (not inside the `try/catch(InvalidProtocolBufferException ...)` block that only wraps unpacking), an NPE here is not caught by the actuator's own exception handling and can propagate as an uncaught `RuntimeException` during block application — a denial-of-service condition consistent with "node crash or halt" impact criteria.

### Likelihood Explanation
`DelegateResourceContract`/`UnDelegateResourceContract` are ordinary, unprivileged broadcastable transactions available to any account holder once TRON's "resource delegation v2" feature is enabled (`supportDR()` / `supportUnfreezeDelay()`), which is the case on current mainnet/testnet configurations. Triggering the divergent state (partially-expired lock vs. unlock bucket combinations, mixed BANDWIDTH/ENERGY delegations) requires only a sequence of freeze/delegate/lock/unlock operations that are all normal, permitted API calls — no special privileges, and no cooperation from a malicious SR/witness is needed.

### Recommendation
Add an explicit null check on the `unlockResource` / `delegatedResourceCapsule` object immediately before use in `UnDelegateResourceActuator.execute()` (lines 130–176) and `UnDelegateResourceProcessor.execute()` (lines 162–209), creating a fresh empty `DelegatedResourceCapsule` if it is null (mirroring the pattern already used for `receiverCapsule`), rather than assuming `unLockExpireResource()` always leaves a non-null capsule behind. Additionally, align `validate()`'s balance-sufficiency arithmetic exactly with the bucket(s) that `execute()` will actually mutate, so that any transaction accepted by `validate()` is guaranteed to be safely executable.

### Proof of Concept
Full confirmation requires instrumenting/tracing `DelegatedResourceStore.unLockExpireResource(...)` (not retrieved during this review) to determine whether there exists a reachable sequence of `FreezeBalanceV2` → `DelegateResourceContract` (with `lock=true`) → time advance past expiry → `UnDelegateResourceContract` calls where `validate()`'s combined-bucket balance check passes while the post-migration "unlock" bucket in `execute()` remains null. This is the concrete next step needed to turn this structural inconsistency into a fully proven, reproducible NPE PoC; I was not able to complete that trace within this review, so this finding should be treated as a strong structural analog requiring confirmation via a unit test that manufactures such state (e.g., extending the existing `UnDelegateResourceActuatorTest` suite) before being treated as fully proven.
