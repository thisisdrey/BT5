This confirms the code matches the claim's citations exactly. The core technical facts are verified:

- `PRECISION_SCALING_FACTOR: u16 = 4096` [1](#0-0) 
- `reward_per_token` performs `reward_rate_per_block * blocks_elapsed * PRECISION_SCALING_FACTOR / total_tokens_staked` via integer division that truncates to zero for small deltas [2](#0-1)

Audit Report

## Title
`asset-rewards`: unbounded `stake`/`unstake`/`harvest_rewards` calls let any staker permanently zero out reward accrual via `reward_per_token` integer-division truncation - (File: substrate/frame/asset-rewards/src/lib.rs)

## Summary
`reward_per_token()` in `pallet-asset-rewards` computes `reward_rate_per_block * blocks_elapsed * PRECISION_SCALING_FACTOR / total_tokens_staked` using a fixed, small precision constant (`PRECISION_SCALING_FACTOR = 4096`), which truncates to `0` via integer division whenever the numerator is small relative to `total_tokens_staked`. `update_pool_rewards` unconditionally advances `pool_info.last_update_block` to the current block on every call regardless of whether the computed delta was non-zero, so repeated calls to the fully public `stake`, `unstake`, or `harvest_rewards` extrinsics permanently discard the truncated reward instead of allowing it to accumulate over a longer window.

## Finding Description
`reward_per_token` derives the pool's accrued-reward-per-share increment since `last_update_block`:
```rust
Ok(pool_info.reward_per_token_stored.ensure_add(
	pool_info
		.reward_rate_per_block
		.ensure_mul(rewardable_blocks_elapsed.into())?
		.ensure_mul(PRECISION_SCALING_FACTOR.into())?
		.ensure_div(pool_info.total_tokens_staked)?,
)?)
``` [8](#0-7) 

`PRECISION_SCALING_FACTOR` is a hard-coded `u16 = 4096` [1](#0-0) , far lower precision than e.g. `FixedU128` (10^18) used elsewhere in the codebase such as `pallet-nomination-pools`. For any pool where `total_tokens_staked` is large relative to `reward_rate_per_block * blocks_elapsed`, the division truncates the result to exactly `0`.

`update_pool_rewards` then unconditionally persists this (possibly zero) delta and, critically, always advances `last_update_block`:
```rust
pub fn update_pool_rewards(
	pool_info: &PoolInfoFor<T>,
	reward_per_token: T::Balance,
) -> Result<PoolInfoFor<T>, DispatchError> {
	let mut new_pool_info = pool_info.clone();
	new_pool_info.last_update_block = T::BlockNumberProvider::current_block_number();
	new_pool_info.reward_per_token_stored = reward_per_token;
	Ok(new_pool_info)
}
``` [3](#0-2) 

This function is invoked via `update_pool_and_staker_rewards` on every call to the unprivileged, `ensure_signed`-gated extrinsics `stake` [4](#0-3) , `unstake`, and `harvest_rewards` [5](#0-4) . Because the window is reset to "now" on every call — even when the computed delta was `0` — any account that repeatedly calls these extrinsics (most simply, a staker harvesting or nudging their own stake every block) keeps `blocks_elapsed` small, so the numerator never grows large enough to cross the truncation threshold, and that period's fractional reward is discarded rather than deferred.

By contrast, `pallet-nomination-pools`'s analogous accounting explicitly skips advancing `last_recorded_reward_counter` when `pending_rewards.is_zero()`, so elapsed time keeps accumulating toward eventually crossing the truncation threshold [7](#0-6) . `pallet-asset-rewards` has no equivalent guard, so the reward is permanently, not just temporarily, lost for as long as the calling pattern continues.

## Impact Explanation
This is a runtime bug that compromises the intended behavior of the reward-distribution invariant: stakers should receive rewards proportional to `reward_rate_per_block` over elapsed time, but with common decimal-scale staking assets (10-18 decimals) and modest reward rates, that reward can be truncated to zero indefinitely by ordinary or adversarial calling patterns. The undistributed reward-asset balance remains in the pool account and, once the pool is emptied of stakers, is returned entirely to the pool admin via `cleanup_pool` [9](#0-8)  — a misdirection of value away from the stakers who were promised it, without requiring any privileged or governance action to trigger.

## Likelihood Explanation
The condition `reward_rate_per_block * blocks_elapsed * 4096 < total_tokens_staked` is easily satisfied for single-block windows given realistic asset decimal precision and reward rates. Any unprivileged staker can trigger `update_pool_and_staker_rewards` every block simply by calling `harvest_rewards` on their own stake (no `BadOrigin` restriction applies to a staker acting on their own behalf) [10](#0-9) , requiring no special capital, timing, or malicious infrastructure — only routine self-interaction with a public extrinsic.

## Recommendation
- Skip advancing `pool_info.last_update_block` and `staker_info.reward_per_token_paid` when the freshly computed `reward_per_token` delta is zero, mirroring `pallet-nomination-pools`'s pattern, so elapsed blocks keep accumulating toward crossing the truncation threshold.
- Increase `PRECISION_SCALING_FACTOR` substantially (e.g., to a `FixedU128`-comparable `10^18` scale) or switch to fixed-point accounting to shrink the truncation window.
- Add a regression test analogous to `pallet-nomination-pools`'s reward-eventually-surfaces tests to assert low-reward-rate pools do not permanently lose accrual regardless of call frequency.

## Proof of Concept
1. `create_pool` with an 18-decimal `staked_asset_id`, small `reward_rate_per_block` (e.g., `1_000`), and a far-future `expiry_block`.
2. Staker A stakes `1_000_000 * 10^18` units so `total_tokens_staked` is large.
3. Each block, staker A calls `harvest_rewards` on their own stake, invoking `update_pool_and_staker_rewards` → `reward_per_token()`, computing `1_000 * 1 * 4096 / (1_000_000 * 10^18) = 0` due to integer truncation.
4. `update_pool_rewards` still sets `last_update_block` to the current block, so the next call's `blocks_elapsed` resets to `1` again — `reward_per_token_stored` never advances.
5. Repeating every block indefinitely keeps `staker_info.rewards` at zero despite the pool nominally emitting `1_000` reward tokens/block.
6. After stakers withdraw, the admin calls `cleanup_pool`, and the entire un-distributed reward-asset balance is transferred back to the admin instead of to stakers.
