## Title
Silent Truncation of Reference-Transaction Hook Updates via Oversized Ref-Update Line - (File: `internal/gitaly/hook/referencetransaction.go`)

### Summary
The `ReferenceTransactionHook` parses the raw `git reference-transaction` stdin payload with `bufio.NewScanner`, which by default truncates any single line to 64KiB (`bufio.MaxScanTokenSize`) and reports failure via `scanner.Err()`. Both `parseChanges` and `isForceDeletionsOnly` in [1](#0-0)  and [2](#0-1)  loop with `for scanner.Scan() { ... }` and never check `scanner.Err()` afterwards, so if a single `<old> <new> <ref-name>` line exceeds the scanner's buffer, the function silently stops processing and returns whatever partial `updates` it has already collected — with no error at all.

### Finding Description
`git`'s reference-transaction hook protocol writes one line per updated reference: `<old-value> SP <new-value> SP <ref-name> LF`. `ValidateReference` in [3](#0-2)  enforces only *format* rules (no leading dot, no `..`, no control characters, etc.) and imposes **no length limit** on the reference name, as confirmed by the accompanying test cases in [4](#0-3) . An ordinary user with push access can therefore create a branch/tag with an arbitrarily long, deeply nested name (e.g. `refs/heads/aaaa.../bbbb.../....`) that is accepted by Gitaly's own validation.

When such a reference is updated, `git-receive-pack` invokes the `reference-transaction` hook and streams the (very long) update line to Gitaly's `ReferenceTransactionHook` RPC handler in [5](#0-4) , which reads the raw bytes and calls `m.manager.ReferenceTransactionHook` in [6](#0-5) . That function calls `parseChanges(objectHash, bytes.NewReader(changes))` at the `prepared` and `committed` phases to build the actual `git.ReferenceUpdates` used to (a) record initial reference values in the transaction, via `tx.RecordInitialReferenceValues`, and (b) apply the update to the WAL transaction, via `tx.UpdateReferences`, as seen in [7](#0-6) .

Because `bufio.Scanner`'s default split function (`bufio.ScanLines`) fails once a single token exceeds `bufio.MaxScanTokenSize` (64 KiB) and `parseChanges`/`isForceDeletionsOnly` never inspect `scanner.Err()`, an over-long ref-update line causes the scan loop to stop silently: `parseChanges` returns `updates, nil` with the offending line (and any lines after it) dropped, rather than surfacing an error. The caller in [8](#0-7)  only handles a non-nil `err` — which never happens here — so the transaction proceeds as if the dropped reference updates never occurred.

Meanwhile, the vote hash cast via `voteOnTransaction` is computed over the *raw*, untruncated `changes` bytes (`hash := sha1.Sum(changes)` at line 130), so the vote itself still reflects the full unparsed payload. The divergence is between what is voted/hashed and what is actually recorded into `tx.RecordInitialReferenceValues` / `tx.UpdateReferences` (the parsed, truncated subset), i.e., the write-ahead log's recorded reference state silently omits the affected reference(s) even though Git has already updated them on disk.

### Impact Explanation
This produces a state divergence between the actual on-disk/loose-ref reality (Git has fully applied the update) and Gitaly's own transaction bookkeeping (WAL `RecordInitialReferenceValues`/`UpdateReferences`), because the oversized reference update is silently excluded from `git.ReferenceUpdates` without any error being raised to the RPC caller or logged. Depending on downstream consumption of the transaction's recorded reference deltas (voting/replication consistency, quarantine reconciliation, or WAL application), this can cause replicas/consumers to diverge silently for the affected reference, since no error path is triggered to abort or retry the transaction — an ordinary user's push containing a single validly-formatted but extremely long ref name is enough to trigger it, with no privileged access required.

### Likelihood Explanation
Likelihood is high for any deployment: (1) `ValidateReference` places no cap on reference-name length, only on structural validity; (2) a normal `git push` creating/updating a branch with a sufficiently long nested name is a completely standard, unprivileged operation; (3) the 64 KiB `bufio.MaxScanTokenSize` limit is a well-known default that is trivial to exceed with a crafted ref name (well under Git's/OS's own limits, especially with loose object storage or reftable backends that don't impose the same PATH_MAX constraints as traditional filesystem paths); (4) the bug requires no race condition or special timing — it triggers deterministically on the first parse of the offending line.

### Recommendation
- In `parseChanges` and `isForceDeletionsOnly`, always check `scanner.Err()` after the scan loop ends and propagate it as a hard error (aborting the transaction) rather than silently returning a partial/empty result.
- Increase (and explicitly bound) the scanner buffer via `scanner.Buffer(...)` to a size consistent with the maximum permissible reference name length that Gitaly intends to support, and enforce a corresponding maximum length in `ValidateReference` so that oversized reference names are rejected up front rather than silently mishandled downstream.
- Add regression tests exercising a reference-transaction hook payload containing a single line longer than 64 KiB to ensure it results in an explicit error rather than a silently truncated update set.

### Proof of Concept
1. As an ordinary user with push access to a repository, create/push a branch with a very long nested name, e.g. `refs/heads/` followed by thousands of path segments so the resulting reference-transaction line `<old-oid> <new-oid> refs/heads/…(>64KB total)…\n` exceeds 64 KiB. `ValidateReference` (`internal/git/reference.go`) accepts this name since it only checks format, not length.
2. Push completes; `git-receive-pack` invokes the `reference-transaction` hook for `prepared`/`committed` phases, streaming this oversized line to Gitaly's `ReferenceTransactionHook` RPC.
3. Inside `parseChanges` (`internal/gitaly/hook/referencetransaction.go`), `bufio.NewScanner(changes)` hits `bufio.ErrTooLong` on the oversized line; `scanner.Scan()` returns `false`, the loop exits, and the function returns `updates, nil` — silently omitting the update for that (and any subsequent) reference.
4. `tx.RecordInitialReferenceValues`/`tx.UpdateReferences` are called with the incomplete `updates` map, while the transaction's vote hash is computed over the full raw bytes — no error is returned to the RPC caller, and the affected reference's update is absent from Gitaly's recorded transaction state despite having been applied to the repository.

func isForceDeletionsOnly(objectHash git.ObjectHash, changes io.Reader) bool {
	// forceDeletionPrefix is the prefix of a queued reference transaction which deletes a
	// reference without checking its current value.
	forceDeletionPrefix := fmt.Sprintf("%[1]s %[1]s ", objectHash.ZeroOID)

	scanner := bufio.NewScanner(changes)

	for scanner.Scan() {
		line := scanner.Bytes()

		if bytes.HasPrefix(line, []byte(forceDeletionPrefix)) {
			continue
		}

		return false
	}

// ValidateReference checks whether a reference looks valid. It aims to be a faithful implementation of Git's own
// `check_or_sanitize_refname()` function and all divergent behaviour is considered to be a bug. Please also refer to
// https://git-scm.com/docs/git-check-ref-format#_description for further information on the actual rules.
func ValidateReference(name string) error {
	if name == "HEAD" {
		return fmt.Errorf("HEAD reference not allowed")
	}

	// TODO: this can eventually be converted to use `strings.CutPrefix()`.
	if !strings.HasPrefix(name, "refs/") {
		return fmt.Errorf("reference is not fully qualified")
	}
	name = name[len("refs/"):]

	if len(name) == 0 {
		return fmt.Errorf("refs/ is not a valid reference")
	}

	if strings.HasSuffix(name, "/") {
		return fmt.Errorf("reference must not end with slash")
	}

	if strings.HasSuffix(name, ".") {
		return fmt.Errorf("reference must not end with dot")
	}

	if strings.Contains(name, "@{") {
		return fmt.Errorf("reference must not contain @{")
	}

	if strings.Contains(name, "..") {
		return fmt.Errorf("reference must not contain double dots")
	}

	for _, c := range name {
		switch c {
		case ' ', '\t', '\n':
			return fmt.Errorf("reference must not contain space characters")
		case ':', '?', '[', '\\', '^', '~', '*', '\177':
			return fmt.Errorf("reference must not contain special characters")
		}

		// Note that we treat some of the characters below 32 specially in the switch above so
		// that we can report back more precise error messages.
		if c < 32 {
			return fmt.Errorf("reference must not contain control characters")
		}
	}

	// We need to check the components individually as components aren't allowed to have some specific constructs.
	for {
		component, tail, _ := strings.Cut(name, "/")

		if component == "" {
			if tail != "" {
				return fmt.Errorf("empty component is not allowed")
			}

			// Otherwise, if both component and tail are empty, we have fully verified the complete
			// reference and can thus return successfully.
			return nil
		}

		if strings.HasPrefix(component, ".") {
			return fmt.Errorf("component must not start with dot")
		}

		if strings.HasSuffix(component, ".lock") {
			return fmt.Errorf("component must not end with .lock")
		}

		name = tail
	}
}
