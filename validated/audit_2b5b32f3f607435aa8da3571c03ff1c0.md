## Title
Out-of-bounds read on malformed ZIP central directory entries in `InputZipFile::ProcessCentralDirEntry` - (File: `third_party/ijar/zip.cc`)

### Summary
The QEMU CVE is a case where a device handler trusts an attacker-influenced index/offset and reads/writes memory without validating it stays inside the target buffer. The closest reachable analog in bazel is bazel's own ZIP parser in `third_party/ijar/zip.cc`, which parses central-directory records of a ZIP/JAR file that can originate from attacker-controlled, checksum-pinned build inputs (an `http_archive`/`http_jar` download, a fetched Maven/registry jar, or any `.jar`/`.zip` dependency that later gets processed by the `ijar` tool or the `zipper` CLI built on the same `InputZipFile` class). Unlike `InputZipFile::ProcessLocalFileEntry`, which validates remaining buffer size with `EnsureRemaining()` before reading variable-length fields, `InputZipFile::ProcessCentralDirEntry` never calls `EnsureRemaining()` before dereferencing fixed and variable-length fields taken from the central directory record.

### Finding Description
`InputZipFile::ProcessCentralDirEntry` (`third_party/ijar/zip.cc:493-545`) reads the central directory header fields (`compressed_size`, `uncompressed_size`, `file_name_length`, `extra_field_length`, `file_comment_length`, `attr`, `offset`) directly from the input pointer `p` with `get_u4le`/`get_u2le`, and then does: [1](#0-0) 
There is no call to `EnsureRemaining()` (the bounds-check helper used elsewhere in the same class, see `third_party/ijar/zip.cc:161-170`) before reading these 46+ fixed bytes, before the `memcpy(filename, p, len)` of `file_name_length` bytes, or before advancing `p` by `extra_field_length`/`file_comment_length`. Contrast this with `ProcessLocalFileEntry`, which does bound-check before reading its variable-length `file_name`/`extra_field`: [2](#0-1) 
`FindZipCentralDirectory` (`third_party/ijar/zip.cc:704-778`) validates that `central_dir_offset + central_dir_size <= in_length`, i.e., it confirms the overall central directory blob fits in the mapped file, but it never validates that any individual entry's declared `file_name_length`/`extra_field_length`/`file_comment_length` stays within `central_dir_offset + central_dir_size` (or within the mapped file at all). A crafted ZIP whose last central directory entry declares an oversized `file_name_length` (e.g., larger than the remaining bytes in the central directory, or large enough to run past the end of the `mmap`'d file) causes `memcpy` and pointer arithmetic in `ProcessCentralDirEntry` to read past the end of the mapped buffer.

### Impact Explanation
This is an out-of-bounds *read* of process memory (heap/mmap over-read), matching the CVE's class of missing bounds validation on attacker-influenced offsets/lengths. Depending on the memory layout this can crash the build tool (`ijar`, `zipper`, or `singlejar`/blaze's own archive extraction which reuses the same `ZipExtractor` interface) via SIGSEGV, or leak adjacent heap bytes into the copied `filename` buffer or into output artifacts that get embedded in generated interface jars, which a build could then expose. Note that a declared sha256/integrity check only guarantees the bytes match what the attacker chose to publish — it does not stop the attacker from choosing bytes that are a structurally malformed ZIP with an out-of-range length field, so the checksum does not mitigate this class.

### Likelihood Explanation
Any dependency that is a `.zip`/`.jar`/`.aar` fetched via `http_archive`, `http_jar`, or a Bzlmod registry module and subsequently processed with `ijar` (used automatically for every `.jar` used in Java compilation to produce interface jars) or with the `zipper` CLI is parsed by this exact code path. An unprivileged attacker who controls the hosting of such an archive (and simply publishes a matching sha256 for their crafted bytes) can trigger this on any consuming build with default flags — no special configuration is required.

### Recommendation
Add `EnsureRemaining()`-style bounds checks in `InputZipFile::ProcessCentralDirEntry` before reading the fixed 46-byte header, before the `memcpy` on `file_name_length` bytes, and before advancing past `extra_field_length`/`file_comment_length`, mirroring the checks already present in `ProcessLocalFileEntry`. Additionally validate that each entry's read cursor does not exceed `central_dir + central_dir_size` (the previously-validated central directory bound from `FindZipCentralDirectory`).

### Proof of Concept
Construct a minimal ZIP file whose End-Of-Central-Directory record and central directory size pass `FindZipCentralDirectory`'s aggregate check, but where the sole central-directory entry declares `file_name_length` (or `extra_field_length`/`file_comment_length`) larger than the number of bytes actually available between that entry and the end of the mapped file. Feed this to the `zipper`/`ijar` binary (as already exercised by `third_party/ijar/test/zip_test.sh`, e.g. `test_no_path_traversal`) and observe a crash/OOB read under ASan, analogous to the existing `path_traversal_zip.jar` regression test referenced at: [3](#0-2) 
A new regression test following this pattern (e.g., `test_malformed_central_directory_entry_oob_read`) should assert the tool fails gracefully with a bounds-check error instead of crashing/over-reading, once `EnsureRemaining()` checks are added to `ProcessCentralDirEntry`.
