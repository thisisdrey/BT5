### Title
Improper Privilege Management in `git_repository`/`new_git_repository` submodule updates via unconditional `protocol.file.allow=always` - (File: tools/build_defs/repo/git_worker.bzl)

### Summary
`git_worker.bzl`'s `update_submodules` unconditionally passes `-c protocol.file.allow=always` to `git submodule update --init`, re-enabling the `file://` transport that upstream Git deliberately restricts (defaulting to `user`/requiring explicit opt-in) as a mitigation against exactly this class of submodule-driven local-content access. Since the `.gitmodules` content that drives this command comes from the fetched (attacker-influencable) repository, not from the Bazel rule author, a hostile commit/tag/branch can smuggle a `file://` submodule URL that git will silently honor, causing the Bazel-invoked `git` process to clone from an arbitrary local filesystem path on the machine running the fetch.

### Finding Description
`git_repo`/`_update` in `tools/build_defs/repo/git_worker.bzl` clones the attacker-influenceable remote via `add_origin`/`fetch`/`reset`, then, if `init_submodules` or `recursive_init_submodules` is set on the rule, calls `update_submodules`: [1](#0-0) 

Both branches always inject `-c protocol.file.allow=always`, unconditionally widening Git's transport allow-list for the entire submodule operation: [2](#0-1) 

The `.gitmodules` file that defines submodule URLs is part of the tree checked out from the remote (`reset`/`clean` at lines 204-208) — content that is entirely attacker-controlled once a hostile actor can influence the commit, tag, or (unpinned) branch that the `git_repository`/`new_git_repository` rule points to: [3](#0-2) 

Git's own security model treats `file://`/`ext::` submodule URLs originating from a fetched repository as untrusted "remote" input, and by default requires explicit permission (`protocol.file.allow=always`) before honoring them — precisely to prevent a malicious repository from directing a submodule checkout at an arbitrary local path (this restriction dates back to fixes for CVE-2017-1000117-class submodule abuse). Bazel's code comment even documents that this override exists only "to allow the submodule command clone from a local directory," but the override is applied globally to *every* submodule update, not scoped to a specific known-safe local path: [4](#0-3) 

Because the override is unconditional and not tied to any allow-list of expected local submodule sources, a `.gitmodules` entry such as `url = file:///home/ci/other-checkout` (or any absolute path reachable by the build machine) will be honored by `git submodule update --init [--recursive]`, causing Git to clone/copy the contents of that arbitrary local directory into the external repository under Bazel's output base.

### Impact Explanation
This breaks containment: the fetch of an external repository, which should only ever pull content from the declared `remote` URL, is turned into an arbitrary local-filesystem read primitive scoped by whatever `.gitmodules` the hostile commit supplies. On CI systems (a very common Bazel usage pattern) where multiple repositories/checkouts, credential caches, or `.netrc`/`.git-credentials` files live as sibling directories on the same runner, an attacker who can land a hostile commit reachable by a `git_repository` rule (e.g., via a compromised upstream, a hijacked branch used unpinned, or a supply-chain contribution merged upstream) can exfiltrate the contents of other local git repositories/checkouts into the build tree, where they may end up embedded in build outputs, uploaded to a remote cache, or otherwise disclosed. This satisfies the "read outside the repository / exec root / output base" impact category, driven purely by content the outsider published (the commit/`.gitmodules`), consistent with CWE-269 (Improper Privilege Management): a security restriction Git itself enforces by default is stripped away by Bazel's tooling without narrowing scope.

### Likelihood Explanation
Any `git_repository`/`new_git_repository` invocation with `init_submodules = True` or `recursive_init_submodules = True` is affected — these are commonly used, documented attributes. The attacker only needs write access to content that ends up in the fetched commit's `.gitmodules` (e.g., an accepted PR/commit to an otherwise trusted repo, or a hostile branch that an insufficiently pinned rule tracks), matching the "unprivileged outsider whose published content a victim's build consumes" threat model. No credentials, output base, or victim machine access are required by the attacker.

### Recommendation
Do not globally set `protocol.file.allow=always` for submodule updates. Instead:
- Scope the allowance to only the specific local directories Bazel itself controls/expects (e.g., via `-c protocol.file.allow=always` combined with an explicit, validated submodule URL allow-list, or by resolving/validating each submodule URL against expected patterns before permitting `file://`).
- Alternatively, default to Git's safer `protocol.file.allow=user`/`never` and only enable `always` when the rule author explicitly opts in (e.g., a new `allow_file_submodules` attribute), so a hostile `.gitmodules` cannot silently exploit the widened policy for rules that never intended to use local submodules.
- Validate that any `file://` submodule target resolves to a path under an expected/allow-listed root before invoking `git submodule update`.

### Proof of Concept
1. Create a malicious upstream repository `evil.git` whose default branch/tag/commit contains a `.gitmodules` with:
   ```
   [submodule "leak"]
       path = leak
       url = file:///home/ci-runner/other-private-checkout
   ```
2. In a victim `MODULE.bazel`/`WORKSPACE`, declare:
   ```
   git_repository(
       name = "evil",
       remote = "https://example.com/evil.git",
       commit = "<hostile-commit>",
       init_submodules = True,
   )
   ```
3. Run `bazel build @evil//...` on a machine where `/home/ci-runner/other-private-checkout` is an existing git repository (e.g., a sibling CI checkout containing credentials or proprietary source).
4. Observe that `git_worker.bzl`'s `update_submodules` executes `git -c protocol.file.allow=always submodule update --init --checkout --force`, which clones `file:///home/ci-runner/other-private-checkout` into `external/+git_repository+evil/leak`, materializing its contents inside the Bazel output base where they become buildable/inspectable — despite the rule author only intending to fetch `https://example.com/evil.git`.

This can be encoded as a `src/test/shell/bazel/starlark_git_repository_test.sh`-style test: set up a local "victim" git repo with a secret file, set up a separate "attacker" repo whose `.gitmodules` references the victim repo via `file://`, add it as a `git_repository` with `init_submodules = True`, and assert that the secret file's content becomes reachable under `bazel-out`/the external repository directory.

def update_submodules(ctx, git_repo, recursive = False):
    if recursive:
        # "protocol.file.allow=always" allows the submodule command clone from a local directory.
        # It's necessary for Git 2.38.1 and assoicated backport versions.
        # See https://github.com/bazelbuild/bazel/issues/17040
        _git_maybe_shallow(ctx, git_repo, "-c", "protocol.file.allow=always", "submodule", "update", "--init", "--recursive", "--checkout", "--force")
    else:
        _git_maybe_shallow(ctx, git_repo, "-c", "protocol.file.allow=always", "submodule", "update", "--init", "--checkout", "--force")
