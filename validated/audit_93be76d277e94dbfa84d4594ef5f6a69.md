### Title
Missing minimum-output (slippage) protection in `ExchangeWithdrawContract` enables sandwich MEV against Bancor-style TRC10 exchange liquidity withdrawals - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
java-tron's built-in Bancor-style TRC10 `Exchange` feature (created via `ExchangeCreateContract`, traded via `ExchangeTransactionContract`, and managed via `ExchangeInjectContract`/`ExchangeWithdrawContract`) exhibits the same class of vulnerability described in the external report: a multi-asset operation that only carries an amount for one of the two involved assets, with the second asset's payout computed live from the pool's reserve ratio at execution time, and no minimum-output check on that second asset. Exactly like `redeemEarlyLv` checks `raReceivedFromAmm` but not CT/DS/PA, `ExchangeWithdrawContract` lets the caller specify `quant` for one token, but the resulting `anotherTokenQuant` (computed from the live pool ratio) has no caller-supplied minimum bound, so any other unprivileged account can sandwich the withdrawal via `ExchangeTransactionContract` swaps to shift the pool ratio and extract value from the withdrawer.

### Finding Description
`ExchangeWithdrawContract` only carries `owner_address`, `exchange_id`, `token_id`, and `quant` — there is no `expected`/minimum field for the paired asset, unlike `ExchangeTransactionContract` which does carry an `expected` minimum for its (single) output asset. [1](#0-0) 

In `ExchangeWithdrawActuator.doValidate()`/`execute()`, the amount of the *other* token the withdrawer will receive (`anotherTokenQuant`) is derived purely from the current on-chain pool reserve ratio (`bigSecondTokenBalance.multiply(bigTokenQuant).divide(bigFirstTokenBalance)`), evaluated at transaction-execution time, with no user-supplied lower bound: [2](#0-1) 

The only checks performed are that the pool has enough balance and that the computed ratio isn't "imprecise," never that the amount meets a caller-specified minimum: [3](#0-2) 

Because the pool's `firstTokenBalance`/`secondTokenBalance` reserves are the same ones mutated by ordinary swaps through `ExchangeTransactionActuator.execute()` (any unprivileged account can call `ExchangeTransactionContract` to buy/sell against the pool and shift its ratio, subject only to `token expected` slippage on their own swap): [4](#0-3) 

an attacker can sandwich a pending `ExchangeWithdrawContract` transaction: submit a swap that skews the reserve ratio before the withdrawal is packed/executed, let the victim's withdrawal compute an unfavorably skewed `anotherTokenQuant` against the now-distorted ratio, then reverse the swap afterward to restore the ratio and capture the extracted value (analogous to CT/DS being drained via flash-swap manipulation of the RA/CT AMM pool in the Cork report, where only the RA leg had `amountOutMin` protection).

### Impact Explanation
An account holding an `Exchange` (created via `ExchangeCreateContract`, no elevated privilege required) that later withdraws liquidity via `ExchangeWithdrawContract` receives an amount of the counter-asset with zero minimum-output guarantee. A block producer or any observer of the mempool can insert swap transactions immediately before/after the withdrawal transaction within the same block ordering, extracting value from the withdrawer — a concrete theft-of-funds/value-extraction primitive reachable purely through ordinary signed transactions (`ExchangeTransactionContract`, `ExchangeWithdrawContract`), matching the "unauthorized... theft of funds" impact class.

### Likelihood Explanation
The `Exchange`/TRC10-Bancor feature actuators (`ExchangeCreateActuator`, `ExchangeInjectActuator`, `ExchangeWithdrawActuator`, `ExchangeTransactionActuator`) are all live, unauthenticated-by-role actuators reachable by any signed transaction and are also exposed over the wallet HTTP/gRPC APIs (`/wallet/exchangewithdraw`, `/wallet/exchangetransaction`). No special permissions (SR/witness/committee) are required — only that the victim owns an exchange and chooses to withdraw, and the attacker has funds to trade against the pool, which is a low bar. Likelihood is Medium: it requires (a) an active TRC10 exchange with meaningful liquidity, and (b) the ability to place transactions around the victim's withdrawal in the same/adjacent block, both realistic given java-tron's public mempool and deterministic actuator ordering.

### Recommendation
Add a caller-specified minimum-output field (e.g., `expected`/`min_another_token_quant`) to `ExchangeWithdrawContract`, and validate it in `ExchangeWithdrawActuator.doValidate()`/`execute()` against the computed `anotherTokenQuant`, mirroring the existing `expected` check already present in `ExchangeTransactionActuator`. Alternatively, consider disallowing/limiting swap-then-withdraw sequencing within the same block for a given exchange, similar to the "block swaps during LP exit" mitigation suggested in the original report.

### Proof of Concept
1. Victim creates an `Exchange` for tokens A/B via `ExchangeCreateContract` and injects liquidity (reserves R_A, R_B).
2. Victim broadcasts `ExchangeWithdrawContract{token_id=A, quant=Q}` expecting to receive `Q * R_B / R_A` of token B, with no `expected` field to protect this amount.
3. Before the victim's transaction is packed, an attacker broadcasts an `ExchangeTransactionContract` swap that shifts the pool ratio (e.g., sells a large amount of B into the pool, per `ExchangeTransactionActuator.execute()` at [4](#0-3) ), reducing R_B relative to R_A.
4. The victim's withdrawal executes against the skewed ratio, per [5](#0-4) , yielding materially less token B than expected, with no revert since no minimum bound exists.
5. The attacker submits a reverse swap to restore the ratio, pocketing the difference extracted from the victim's withdrawal — value transfer with no protocol-level guard.
