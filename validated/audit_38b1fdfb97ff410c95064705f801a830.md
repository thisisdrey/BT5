### Title
Fee refund promise in `inner_rlp_execute` is created unconditionally before the registrar-based relayer-fault check resolves, allowing repeatable theft of wallet NEAR - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
When `parse_rlp_tx_to_action` classifies a transaction as `EthEmulationKind::EOABaseTokenTransfer { address_check: Some(address), fee }` (i.e., target is another eth-implicit account and the honesty of `target` still needs to be confirmed via an async call to the address registrar), `inner_rlp_execute` immediately and unconditionally schedules a fee-refund transfer to `predecessor_account_id` before the registrar lookup resolves. If the registrar later reports the address is actually a registered named account (a relayer fault), `address_check_callback` aborts the action and, when the caller is not using a wallet-owned access key, neither bans anyone nor increments the nonce — leaving the signed transaction replayable while the fee has already been paid out.

### Finding Description
In `parse_rlp_tx_to_action`, when the target is `TargetKind::EthImplicit(address)` and the payload parses as an Ethereum emulation, the code produces `TransactionKind::EthEmulation(EthEmulationKind::EOABaseTokenTransfer { address_check: Some(address), fee: tx_fee })`, where `tx_fee` is computed purely from the attacker-controlled/self-relayer-controlled `tx.max_fee_per_gas * tx.gas_limit` fields of the RLP-encoded Ethereum transaction: [1](#0-0) [2](#0-1) 

In `inner_rlp_execute`, the nonce-increment logic correctly special-cases `address_check: Some(_)` to defer the nonce increment until the registrar check completes: [3](#0-2) 

However, the very next block that creates the fee-refund promise matches only on `EOABaseTokenTransfer { fee, .. }` — it does **not** distinguish `address_check: None` from `address_check: Some(_)` — so the refund transfer is created immediately, before the registrar has been consulted: [4](#0-3) 

This refund is issued via `env::promise_batch_create`/`env::promise_batch_action_transfer`, which schedules an independent outgoing receipt from the wallet's balance to `context.predecessor_account_id` — it is not chained after, or contingent on, the later `address_check_callback` outcome.

The registrar lookup and its result are only evaluated afterward in `address_check_callback`: [5](#0-4) 

If the registrar returns `Some(account_id)` (i.e., the relayer set `target` to the raw eth-implicit-style account instead of the real, registered named account — a relayer fault), the action is never executed. If the caller used its own account key rather than a wallet-owned access key (`env::signer_account_id() != current_account_id`), no ban occurs and, critically, **the nonce is not incremented** in this branch, so the exact same signed transaction and malicious `target` remain valid for the wallet's current nonce and can be resubmitted. Since `has_in_flight_tx` is reset to `false` at the top of `address_check_callback`, the relayer can call `rlp_execute` again immediately with the identical inputs.

Because the `target` parameter is not part of the user-signed Ethereum transaction (only `tx.to`, a raw 20-byte address, is signed), any caller of `rlp_execute` (no access key required — it is a public `#[payable]` method) can freely choose `target = "0x{hex(tx.to)}{suffix}"` (satisfying `parse_target`/`validate_tx_relayer_data`'s `is_valid_target` check for `TargetKind::EthImplicit`) instead of looking up the honest, registered account for `tx.to`, forcing the deferred-registrar-check path while still collecting `fee` immediately and unconditionally, then repeating the process to drain the wallet.

### Impact Explanation
This is a theft-of-user-funds vulnerability (NEAR bounty category: loss of user funds). A relayer that is handed any user's legitimately fee-bearing, signed Ethereum meta-transaction destined for the wallet contract (a normal, permitted usage per the wallet contract's meta-tx relaying design) can repeatedly extract `fee` yoctoNEAR from the target wallet's balance without ever performing the user's intended action, and without being banned or consuming the nonce, as long as it avoids using a wallet-granted access key. Each call permanently transfers NEAR out of the victim wallet to the relayer with no corresponding action executed, and the process is repeatable until the wallet's balance is exhausted.

### Likelihood Explanation
Preconditions: the attacker needs a validly user-signed RLP Ethereum transaction with `max_fee_per_gas * gas_limit > 0` addressed (via `tx.to`) to an eth address that is registered in the address registrar (the registrar's `register` method appears to be open to any account wishing to register itself, so an attacker relayer can arrange for this precondition, or simply wait for any user transaction intended for a real registered NEP-141/named account). No validator, node, or key-leak access is required — only the ability to relay a meta-transaction, which is an explicitly permitted attacker capability. The attack is fully repeatable with zero attacker cost beyond gas, since gas for a failed call is cheap relative to the extracted `fee`.

### Recommendation
Do not create the fee-refund promise in `inner_rlp_execute` for the `address_check: Some(_)` case. Defer fee refund creation until inside `address_check_callback`, only in the branch where `maybe_account_id.is_none()` (i.e., the target was legitimately confirmed to be an honest eth-implicit base-token transfer), mirroring the deferred nonce-increment logic already present for this case.

### Proof of Concept
Integration test extending `runtime/near-wallet-contract/implementation/wallet-contract/src/tests/relayer.rs` (modeled on the existing `test_relayer_invalid_address_target`, which currently uses `gas_price: 0` and therefore does not exercise this bug):
1. Deploy a wallet contract and an address registrar; register a NEP-141-style account so its derived address is present in the registrar.
2. Have the wallet owner sign an Ethereum tx with `to = <registered account's derived address>`, calldata matching an ERC-20 emulation selector, and `gas_price`/`gas_limit` set so `tx_fee > 0`.
3. Call `rlp_execute` from an attacker-controlled NEAR account (not holding a wallet access key) with `target = "0x{hex(to)}.<suffix>"` (eth-implicit format) rather than the real registered account id.
4. Assert: (a) the final `ExecuteResponse` is `success: false` with error "faulty relayer"/invalid target message; (b) `wallet_contract.nonce` is unchanged; (c) the attacker's NEAR balance increased by `tx_fee` and the wallet's balance decreased correspondingly, despite no action executing — demonstrating a balance-conservation violation.
5. Repeat step 3 a second time with the identical `tx_bytes_b64`/`target` and confirm it succeeds again (same nonce accepted) and drains `tx_fee` a second time, proving repeatability.
