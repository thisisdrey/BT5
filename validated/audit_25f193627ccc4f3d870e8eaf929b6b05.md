### Title
Non-deterministic floating-point Bancor pricing in `ExchangeTransactionActuator`/`ExchangeCapsule.transaction` can cause on-chain state divergence across nodes - (File: `chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java`)

### Summary
The bug report's core theme is a single, externally-controlled input feeding an amount calculation whose failure/inconsistency directly breaks fund-transfer correctness. The closest reachable analog in java-tron is the on-chain TRC10 `Exchange` (Bancor-style AMM) settlement path: by default it computes swap amounts with ordinary `java.lang.Math.pow` (double precision, not guaranteed bit-reproducible across JVMs/CPU architectures) rather than the deterministic `StrictMath`/`BigDecimal` implementation that exists in the same codebase but is gated behind opt-in chain parameters that default to `0`.

### Finding Description
Any unprivileged account can create/trade against an `Exchange` pool and submit an `ExchangeTransactionContract`. The actuator computes the counter-asset amount via `ExchangeCapsule.transaction()`: [1](#0-0) 

which, unless the `ALLOW_HARDEN_EXCHANGE_CALCULATION` chain parameter is enabled (default `0`), instantiates the legacy `ExchangeProcessor` with `useStrictMath = dynamicStore.allowStrictMath()`, itself gated by `ALLOW_STRICT_MATH` (also default `0`): [2](#0-1) [3](#0-2) 

With both flags at their default (disabled) value, `ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply` call `Maths.pow(a, b, false)`, which routes to the non-strict `MathWrapper.pow` (i.e., `java.lang.Math.pow`) instead of `StrictMathWrapper.pow` (`java.lang.StrictMath.pow`): [4](#0-3) [5](#0-4) 

`java.lang.Math.pow` is explicitly *not* required by the JLS/JavaDoc to be bit-for-bit reproducible across JVM vendors, versions, or hardware (it may use platform intrinsics), unlike `StrictMath.pow`, which is fixed to the fdlibm reference algorithm and is guaranteed identical on every platform. The codebase itself documents this distinction and treats `Maths` as `@Deprecated` in favor of `StrictMathWrapper` "for cross-platform consistency": [6](#0-5) 

The result of this floating-point computation (`anotherTokenQuant`) is not just returned to the caller — it is written directly into consensus state: account TRX/TRC10 balances and the `Exchange` pool reserves, inside `ExchangeTransactionActuator.execute`, which runs during block application in every full node: [7](#0-6) 

Because every validating/witness node independently re-executes the same transaction while applying the same block, any platform-dependent discrepancy in `Math.pow` output between nodes (different CPU architecture, JIT/AOT compiler, JVM vendor or version) produces a different `anotherTokenQuant`, hence different account balances and different `ExchangeCapsule` reserves, hence a different post-block state root/hash on different nodes — a chain split, entirely from a single ordinary user's signed `ExchangeTransactionContract`, requiring no malicious SR/witness/committee action.

The codebase's own test suite corroborates that the non-strict and strict paths produce *different* results for identical inputs: [8](#0-7) 

### Impact Explanation
If node JVMs/hardware are heterogeneous across the network (a realistic and common deployment scenario for a public blockchain), a legitimate `ExchangeTransactionContract` broadcast by any ordinary account can cause different nodes to persist different account balances/exchange reserves for the same block, i.e., a consensus/chain split. This satisfies the "chain split" acceptance criterion without requiring any privileged actor — the transaction sender is a normal, unprivileged trader interacting with a market-open `Exchange` pool.

### Likelihood Explanation
Exploitability requires only: (1) an existing `Exchange` pair (creatable by any account via `ExchangeCreateContract`), and (2) a normal `ExchangeTransactionContract` trade against it, both fully unprivileged operations. It does not require the default flags to be flipped by governance — it is the *default* (unpatched) behavior when `ALLOW_STRICT_MATH`/`ALLOW_HARDEN_EXCHANGE_CALCULATION` remain `0`, which reference.conf shows is the shipped default. The likelihood of an actual observable split depends on the underlying JVM/CPU heterogeneity of the network's node operators, which is not something an attacker fully controls, but the divergence is a systemic risk inherent to running non-strict floating point in consensus code, not a contrived edge case.

### Recommendation
- Make `ALLOW_STRICT_MATH` (or better, `ALLOW_HARDEN_EXCHANGE_CALCULATION`, which replaces double math with `BigDecimal`/`StrictMathWrapper` entirely) mandatory/always-on for `ExchangeTransactionActuator`/`ExchangeCapsule.transaction`, rather than an opt-in governance-gated flag defaulting to disabled.
- Remove the deprecated `Maths`/`MathWrapper` non-strict code path from any function that writes to consensus-critical state (balances, capsule reserves), restricting `Math.pow`-based computation strictly to non-consensus-affecting code (e.g., logging, off-chain estimation).
- Audit all other consensus-critical arithmetic in the codebase for similar non-strict `Math.*` usage guarded by opt-in flags with unsafe defaults.

### Proof of Concept
1. Deploy two full nodes with default configuration (`ALLOW_STRICT_MATH=0`, `ALLOW_HARDEN_EXCHANGE_CALCULATION=0`) but different JVM vendors/versions or CPU architectures (e.g., one x86-64 with JIT-vectorized `Math.pow`, one ARM64/different JVM).
2. Create a TRC10 `Exchange` pool (`ExchangeCreateContract`) with a chosen `firstTokenBalance`/`secondTokenBalance`.
3. From an ordinary unprivileged account, broadcast an `ExchangeTransactionContract` trading a `sellTokenQuant` selected such that `Math.pow` on the differing platforms produces even a single-ULP difference in the intermediate `issuedSupply`/`exchangeBalance` double values inside `ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply` (`chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java:17-45`).
4. Observe that `(long) issuedSupply` / `(long) exchangeBalance` truncation amplifies the tiny floating-point discrepancy into a differing integer `anotherTokenQuant` on the two nodes.
5. Confirm the two nodes persist different `AccountCapsule` balances and `ExchangeCapsule` reserves for the same block, i.e., diverging state roots — a chain split triggered purely by a normal user transaction under default settings.

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
