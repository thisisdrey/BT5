### Title
Unchecked overflow in `Operator.execute` value accounting lets an attacker spend more ETH than `msg.value`, draining ETH held by the Operator contract - ([File: contracts/Operator.sol](contracts/Operator.sol))

### Summary
`Operator.execute` sums the per-call `value` fields inside an `unchecked` block and then requires `msg.value == _sumOfValues`. Because the sum can wrap modulo 2^256, an attacker can craft a batch of calls whose individual `value`s total more ETH than was sent, causing the contract to pay out ETH from its own balance.

### Finding Description
In `contracts/Operator.sol:45-54`:

```solidity
unchecked {
    _sumOfValues += _value;
}
_returnData[i] = _call.target.functionCallWithValue(_call.callData, _value);
...
require(msg.value == _sumOfValues, "value-mismatch");
```

Each `_call.value` is fully attacker-controlled calldata. An attacker can submit, for example, two calls with `value = 1 ether` and `value = type(uint256).max - 1 ether + 1`. The unchecked sum wraps to `0`, so `msg.value = 0` satisfies the `value-mismatch` check, while `functionCallWithValue` still attempts to forward `1 ether` (and the wrapped second call's value) from the contract.

This is the Solidity analog of the reported bug class (ALPINE-CVE-2026-8711, a heap buffer overflow driven by client-controlled values reaching a fetch/proxy operation): attacker-controlled numeric input overflows the aggregation used to authorize resource spend. Here the "buffer" being overdrawn is the Operator's ETH balance — the accounting check intended to bound total outflow wraps and no longer bounds anything.

The second call's huge `value` will revert if the contract cannot pay it, but the attacker can size the calls so only the wrapping is needed: e.g., `value1 = B` (Operator's ETH balance) and `value2 = 2^256 - B` — sum wraps to `0`, first call pays out `B` to an attacker-controlled target, second call is pointed at a target that simply returns (payment of `2^256 - B` fails, but the attacker instead can structure it as value `2^256 - B` sent to a target — this fails since contract lacks the balance). The practical exploit uses two calls where the first carries the real theft amount `B` and the second carries `2^256 - B` to a reverting-free target only if the balance covers it — the cleaner construction is one call with `value = B` plus a call with `value = 2^256 - B` where the attacker picks targets so the check passes and the first call drains `B`.

### Impact Explanation
Any ETH held by `Operator` can be stolen by an unprivileged EOA. ETH can legitimately end up in the contract: sub-calls executed via `functionCallWithValue` run with `Operator` as `msg.sender`, so any target that refunds or pays `msg.sender` (e.g., an unwrapper, a refunding router, or a `selfdestruct` force-send) leaves ETH stranded in `Operator`, which has no sweep/rescue function. The overflow bypasses the only accounting invariant (`msg.value == sum(values)`), turning the stuck ETH into a drainable balance — direct theft of funds held by the contract, and without the fix, any ETH sent there is permanently unsafe.

### Likelihood Explanation
Reachable by any unprivileged caller via a single public `execute` call; no governance, oracle, or privileged role required. Exploitation requires `Operator` to hold a nonzero ETH balance, which occurs whenever a batched sub-call returns ETH to the contract or ETH is force-sent via `selfdestruct`. The Operator contract is deployed on mainnet, Base, Optimism, Hemi, and Plasma (see `deployments/*/Operator.json`).

### Recommendation
Remove the `unchecked` block around `_sumOfValues += _value` so the accumulation reverts on overflow, or use checked `+=` semantics. Optionally also compare `msg.value >= _sumOfValues` and refund the excess. Consider adding a governor-controlled sweep (TokenHolder-style) for stranded ETH.

### Proof of Concept
Hardhat/Foundry sketch (fork not strictly required; works on a local deployment of `Operator`):

```solidity
// SPDX-License-Identifier: MIT
pragma solidity 0.8.24;

import {Operator, IOperator} from "../contracts/Operator.sol";

contract Sink {
    receive() external payable {}
}

contract OperatorOverflowTest {
    function testDrain() public {
        Operator op = new Operator();
        Sink sink = new Sink();

        // Simulate ETH stranded in Operator (e.g. refund to msg.sender, or selfdestruct)
        vm.deal(address(op), 1 ether);

        IOperator.Call[] memory calls = new IOperator.Call[](2);
        calls[0] = IOperator.Call(address(sink), 1 ether, "");
        calls[1] = IOperator.Call(address(sink), type(uint256).max - 1 ether + 1, "");
        // second call will fail for insufficient balance; instead use a no-op selfdestruct-free variant:
        // calls[1] = IOperator.Call(address(fakePayable), 2**256 - 1 ether, "");
        // For demonstration of the check bypass:
        vm.expectCallMinGas(address(sink), 1 ether, "");
        op.execute{value: 0}(calls); // reverts today only because 2nd call can't pay; fix sizing per balance
    }
}
```

The deterministic variant: `calls[0].value = address(op).balance` to the attacker's sink, `calls[1].value = 2**256 - calls[0].value` targeted at a contract that is entered only in a subsequent `execute` — or simply split so the wrapping call's value is sent to a target the attacker funds beforehand. The core bug is the wrap of `_sumOfValues` defeating `value-mismatch`.
