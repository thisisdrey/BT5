### Title
Missing pool-membership validation in FetchIntoObjectPool allows cross-repository object exfiltration into an attacker-controlled pool - (File: internal/gitaly/service/objectpool/fetch_into_object_pool.go)

### Summary
`FetchIntoObjectPool` accepts an arbitrary `origin` repository and an arbitrary `object_pool` repository as independent, unrelated request fields and performs a `git fetch` of all refs from `origin` into `object_pool`, without ever verifying that `origin` is actually a legitimate member of that pool (i.e., that the pool's alternates actually point back to a repository that owns/created it). This mirrors the Beedle `buyLoan` bug class: an operation that should only be permitted for the rightful "owner" of a resource (the pool member relationship) is instead performed based on caller-supplied identifiers with no ownership/relationship check.

### Finding Description
The handler [1](#0-0)  builds an `ObjectPool` from `req.GetObjectPool()` and an `origin` repo from `req.GetOrigin()`, then directly calls `objectPool.FetchFromOrigin(ctx, origin, ...)`.

The only validation performed is in `validateFetchIntoObjectPoolRequest`, which merely checks that both fields are set and that they share the same storage name: [2](#0-1) . There is no check that `origin` is actually linked to (or was ever a member of) `object_pool` — unlike `Link`, which validates the relationship via `linkedToRepository`/`getRelativeObjectPath` before writing alternates [3](#0-2) , `FetchFromOrigin` performs no such reciprocal check; it only verifies that the pool itself exists (`o.Exists(ctx)`) before running `git fetch <originPath> +refs/*:refs/remotes/origin/*` [4](#0-3) [5](#0-4) .

Because Gitaly's per-node auth token is not scoped per-repository, any caller who can reach the `ObjectPoolService.FetchIntoObjectPool` RPC (e.g., via a crafted RPC on a Gitaly node, or in setups where a tenant can reach this endpoint) can supply:
- `origin` = a victim repository they do not own (any relative path on the same storage), and
- `object_pool` = a pool repository the attacker created and controls.

The RPC will then execute a full `+refs/*` fetch from the victim repository into the attacker-controlled pool, exfiltrating all reachable objects (commits, blobs, private branch/tag contents) of the victim repository into the attacker's pool — with no verification that the attacker's pool was ever authorized to associate with that origin. This is the direct analog of `buyLoan`'s missing `msg.sender == pool.lender` check: `object_pool` and `origin` are treated as trusted-pair inputs without validating the ownership/membership relationship between them.

### Impact Explanation
An attacker who can invoke this RPC with attacker-controlled parameters gains read access to the full object graph of any repository on the same Gitaly storage, without needing legitimate access to that repository. Because the pool is subsequently readable by the attacker (their own repository, or any repository they choose to link to the pool via `LinkRepositoryToObjectPool`), this results in confidentiality loss of private repository contents — a concrete cross-repository object-access escape, consistent with the "cross-repository object access" acceptance criterion.

### Likelihood Explanation
Exploitation requires the ability to invoke `ObjectPoolService.FetchIntoObjectPool` with arbitrary `origin`/`object_pool` values. In the standard GitLab architecture, this RPC is normally invoked by trusted internal callers (Sidekiq/Rails housekeeping) after authorization has already been performed at the application layer, and Gitaly's gRPC auth token is shared per node rather than scoped per repository/project. This means the practical likelihood depends heavily on deployment/multi-tenancy assumptions that are outside Gitaly's own code (i.e., whether an "ordinary" tenant/user can reach this specific internal RPC directly). Within Gitaly itself, there is no additional defense-in-depth check tying `origin` to `object_pool`, so the vulnerability is real at the RPC-handler level, but its reachability by an unprivileged, ordinary git user (push/fetch/fork) as opposed to a semi-privileged internal caller could not be fully confirmed from the available code/index.

### Recommendation
Before performing the fetch, validate that `origin` is actually associated with `object_pool` — e.g., require that `origin`'s alternates already reference `object_pool` (using the same `linkedToRepository`/`getRelativeObjectPath` logic used by `Link`), or otherwise verify pool membership/ownership before allowing `FetchFromOrigin` to pull objects from `origin` into the pool. Reject the request (e.g., with `FailedPrecondition`) if no such relationship exists, analogous to adding the `msg.sender == pool.lender` check recommended in the source report.

### Proof of Concept
1. Attacker creates repository `attacker-pool` on the same Gitaly storage and calls `CreateObjectPool` with `origin = attacker-pool` to seed a pool they fully control: [6](#0-5) .
2. Attacker (or any caller able to reach the RPC) issues:
```
FetchIntoObjectPool(FetchIntoObjectPoolRequest{
  Origin: &Repository{StorageName: "default", RelativePath: "victim/private-repo.git"},
  ObjectPool: &ObjectPool{Repository: &Repository{StorageName: "default", RelativePath: "attacker-pool.git"}},
})
```
3. The handler builds the pool from `object_pool` and fetches `+refs/*` from `victim/private-repo.git` into `attacker-pool.git` with no check that these two repositories were ever related [1](#0-0) .
4. All of the victim repository's reachable objects are now present under `refs/remotes/origin/*` in `attacker-pool.git`, which the attacker fully controls and can read (e.g., via `GetObjectPool`/direct Git access to their own pool repository) [4](#0-3) .

func validateFetchIntoObjectPoolRequest(req *gitalypb.FetchIntoObjectPoolRequest) error {
	if req.GetOrigin() == nil {
		return errors.New("origin is empty")
	}

	if req.GetObjectPool() == nil {
		return errors.New("object pool is empty")
	}

	originRepository, poolRepository := req.GetOrigin(), req.GetObjectPool().GetRepository()

	if originRepository.GetStorageName() != poolRepository.GetStorageName() {
		return errors.New("origin has different storage than object pool")
	}

	return nil
}

// FetchFromOrigin initializes the pool and fetches the objects from its origin repository
func (o *ObjectPool) FetchFromOrigin(ctx context.Context, origin *localrepo.Repo, newLocalRepo LocalRepoFactory) error {
	if !o.Exists(ctx) {
		return structerr.NewInvalidArgument("object pool does not exist")
	}

	originPath, err := origin.Path(ctx)
	if err != nil {
		return fmt.Errorf("computing origin repo's path: %w", err)
	}

	if err := o.housekeepingManager.CleanStaleData(ctx, o.Repo, housekeeping.DefaultStaleDataCleanup()); err != nil {
		return fmt.Errorf("cleaning stale data: %w", err)
	}

	if err := o.logStats(ctx, "before fetch"); err != nil {
		return fmt.Errorf("computing stats before fetch: %w", err)
	}
