### Title
Operator's transient `MSG_SENDER` is not scoped per sub-call, letting any contract reached inside an `Operator.execute` batch impersonate the user on all `SynthContext` contracts - ([File: contracts/Operator.sol](Loderfordw/metronome-synth-public--003/contracts/Operator.sol))

### Summary
`Operator.execute` stores the EOA `msg.sender` in a transient storage slot once, before iterating over the user-supplied `calls_` batch, and clears it only after the entire loop finishes. Transient storage is transaction-scoped, not call-frame-scoped, so during *every* sub-call — including nested downstream calls made by those targets — `SynthContext._msgSender()` resolves to the batch initiator whenever `msg.sender == operator`. Any attacker contract reached anywhere inside the batch can therefore call `Pool`/`DepositToken`/`DebtToken`/`SyntheticToken` functions and be treated as the victim user, enabling withdrawal of the victim's collateral and minting of debt in their name.

### Finding Description
The vulnerability combines two pieces:

1. In `Operator.execute`, `setMsgSender` writes `MSG_SENDER_STORAGE = msg.sender` once and only resets it after the whole `calls_` array executes [1](#0-0) . Each `Call` is an unrestricted `(target, value, callData)` triple invoked via `Address.functionCallWithValue` [2](#0-1) .
2. `SynthContext._msgSender()` returns `operator.getActualMsgSender()` — the stored EOA — whenever the immediate `msg.sender` is the Operator contract [3](#0-2) .

The race-condition analog is exact: the ssl bug is a read (`cert_store_stats`) observing mutated state mid-operation; here every downstream read of the sender context observes the stale `MSG_SENDER` even though the logical "operation" (the trusted sub-call that legitimately needed the user identity) has moved on to an untrusted frame. The slot is never re-validated or cleared between calls, and there is no check that the current call frame is the one the user intended to authorize.

The exploit path does not even require the victim to list the attacker's contract as a `target`: if any batched call reaches an attacker-controlled contract at any depth (e.g., a `Swapper.swapExactInput` routed through an attacker pool, a fake `vToken`/`vPool` passed to `VesperGateway`, a token with a malicious `transfer` hook, or an ERC-777-style callback), that contract can call `operator`-mediated functions directly. Because `msg.sender` to the Pool is the Operator, `_msgSender()` returns the *victim's* address.

### Impact Explanation
Direct theft of user funds. An attacker contract reached during a victim's `Operator.execute` batch can, within the same transaction:

- Call `Pool.withdraw(...)` / `DepositToken.transfer` paths authorized by `_msgSender()` to pull the victim's `unlockedBalanceOf` collateral to an attacker address.
- Call `DebtToken.issue`/`Pool.mint`-style entry points to mint synthetic debt against the victim's collateral and send the proceeds to the attacker (bounded only by the victim's remaining collateral factor).
- Call `SyntheticToken.transfer`-adjacent or `seize`-authorized flows where authorization resolves through `_msgSender()`.

The broken invariant is identity/authorization: `_msgSender()` no longer denotes the account that intentionally invoked the function. No modifier stops this because `onlyPool`, `onlyIfCanMint`, health checks, and the `nonReentrant` guard on `execute` all operate on contracts, while the impersonated caller is the *user* — `nonReentrant` on Operator does not prevent the target contract from calling Pool (a different contract), and `ReentrancyGuardTransient` is per-contract so Pool's guard is not yet entered. The final `require(msg.value == _sumOfValues)` only constrains ETH accounting, not downstream calls.

### Likelihood Explanation
Moderate-to-high. Requirements:

- The victim uses `Operator.execute` (the intended UX path for batched deposit/mint/leverage flows).
- Some call in the batch reaches attacker-influenced code at any depth. This is realistic: leverage/swap flows go through `ISwapper` with user-supplied `tokenIn_` and routing; gateway functions accept user-chosen `pool_`/`vToken_`; tokens with transfer callbacks re-enter. An attacker can also bait victims into including a "claim"/"airdrop" call to an attacker contract in a batch.

No privileged role, oracle manipulation, or governance action is needed — only a standard user batch plus one reachable malicious frame. All deployed chains (mainnet, optimism, hemi, swell, plasma) ship identical `Operator`/`SynthContext` bytecode, so the issue is live wherever the deployed `PoolRegistry.operator()` points at this contract.

### Recommendation
- Scope the trusted sender to a single call frame: inside the loop, `tstore` the sender before `functionCallWithValue` and `tstore(0)` immediately after each call, or use a per-call nonce so stale reads revert.
- Alternatively, have `getActualMsgSender()` verify the caller is mid-execution of a whitelisted target, or pass the sender explicitly as a calldata argument to protocol contracts rather than via ambient transient state.
- Disallow arbitrary `target`/`callData` in `execute`, or maintain an allowlist of protocol contracts callable through the Operator.
- Add a regression test where a batch sub-call reaches a malicious contract that attempts `Pool.withdraw`/`DebtToken.issue` as the initiator and assert it reverts.

### Proof of Concept
Foundry-style reproduction against deployed configuration:

```solidity
// SPDX-License-Identifier: MIT
pragma solidity 0.8.24;

import "forge-std/Test.sol";
import {IOperator} from "../contracts/interfaces/IOperator.sol";
import {IPool} from "../contracts/interfaces/IPool.sol";
import {IDepositToken} from "../contracts/interfaces/IDepositToken.sol";

contract Evil {
    IPool pool;
    IDepositToken dt;
    address thief;

    constructor(IPool _pool, IDepositToken _dt, address _thief) {
        pool = _pool; dt = _dt; thief = _thief;
    }

    // Reached inside the victim's Operator.execute batch (as a direct
    // target, a swap router hop, or a token callback).
    function pwn() external {
        // msg.sender == Operator => _msgSender() == victim inside SynthContext.
        uint256 unlocked = dt.unlockedBalanceOf(<victim>);
        // Withdraw victim's collateral to thief. Authorization passes because
        // Pool resolves sender via Operator.getActualMsgSender().
        pool.withdraw(address(dt), unlocked, thief);
    }
}

contract OperatorSenderLeakTest is Test {
    function test_sender_leaks_to_untrusted_frame() public {
        // fork mainnet; victim holds depositToken shares in Pool
        address victim = <victim>;
        IOperator operator = poolRegistry.operator();

        Evil evil = new Evil(pool, depositToken, attacker);

        IOperator.Call[] memory calls = new IOperator.Call[](1);
        calls[0] = IOperator.Call({
            target: address(evil),
            value: 0,
            callData: abi.encodeCall(Evil.pwn, ())
        });

        vm.prank(victim);
        operator.execute(calls);

        // Attacker now holds victim's collateral
        assertGt(underlying.balanceOf(attacker), 0);
    }
}
```

A variant where `Evil` is reached transitively (e.g., via a swap callback during a `leverage` batch) demonstrates the attack does not require the victim to knowingly include a malicious target — only that one frame in the call tree is attacker-controlled.
