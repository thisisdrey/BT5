### Title
Unbounded growth of `DelegatedResourceAccountIndexCapsule.toAccounts`/`fromAccounts` lists via repeated `FreezeBalanceContract` delegations leads to Out-of-Gas/DoS when converted or scanned - (File: `actuator/src/main/java/org/tron/core/actuator/FreezeBalanceActuator.java`)

### Summary
`FreezeBalanceActuator.delegateResource()` lets a single account append an unbounded number of distinct receiver addresses to its own `DelegatedResourceAccountIndexCapsule.toAccounts` list (and correspondingly to each receiver's `fromAccounts` list), with no cap on the number of distinct delegatees. Because this list is stored inside a single protobuf-encoded capsule value keyed by the address, an attacker can grow it to thousands of entries using cheap, repeated `FreezeBalanceContract` transactions to distinct receiver addresses. Later, this same unbounded list is fully loaded, copied and linearly scanned/mutated by `UnfreezeBalanceActuator.execute()` and — critically — by `DelegatedResourceAccountIndexStore.convert()`, which loops over every entry and performs a DB `put` for each one when migrating from the legacy index format to the sharded (per-account) format.

### Finding Description
`FreezeBalanceActuator.delegateResource` (actuator/src/main/java/org/tron/core/actuator/FreezeBalanceActuator.java:319-345) is reached whenever a legitimate account owner submits a `FreezeBalanceContract` with `receiverAddress` set (broadcastable by any account owner). When `dynamicStore.supportAllowDelegateOptimization()` is false (legacy path, still reachable pre-upgrade or on chains that haven't activated the flag), each call:

```java
List<ByteString> toAccountsList = ownerIndexCapsule.getToAccountsList();
if (!toAccountsList.contains(ByteString.copyFrom(receiverAddress))) {
  ownerIndexCapsule.addToAccount(ByteString.copyFrom(receiverAddress));
}
delegatedResourceAccountIndexStore.put(ownerAddress, ownerIndexCapsule);
``` [1](#0-0) 

There is no upper bound anywhere in `FreezeBalanceActuator.validate()` (actuator/src/main/java/org/tron/core/actuator/FreezeBalanceActuator.java:152-277) on how many distinct receiver addresses a single owner may delegate to. Each new receiver simply grows the `toAccounts`/`fromAccounts` list of `DelegatedResourceAccountIndexCapsule` by one entry via `addToAccount`/`addFromAccount` (chainbase/src/main/java/org/tron/core/capsule/DelegatedResourceAccountIndexCapsule.java:82-94), which just appends to the repeated protobuf field and re-serializes/persists the whole capsule.

This unbounded per-owner list is later consumed in two places that scale linearly (or worse) with its size, inside a single transaction each:

1. `UnfreezeBalanceActuator.execute()` copies the full list into a new `ArrayList` and does `.remove()` (an O(n) linear scan) on it for every unfreeze call: [2](#0-1) 

2. `DelegatedResourceAccountIndexStore.convert(address)` iterates over the entire legacy `toList`/`fromList` and, for every entry, performs a `delegate(...)` call that writes two new DB key-value records:
```java
List<ByteString> toList = indexCapsule.getToAccountsList();
for (int i = 0; i < toList.size(); i++) {
  this.delegate(address, toList.get(i).toByteArray(), i + 1L);
}
List<ByteString> fromList = indexCapsule.getFromAccountsList();
for (int i = 0; i < fromList.size(); i++) {
  this.delegate(fromList.get(i).toByteArray(), address, i + 1L);
}
``` [3](#0-2) 

This `convert()` is itself invoked synchronously, inside the execution of a *single* transaction, from `FreezeBalanceActuator.delegateResource()`:
```java
} else {
  // modify DelegatedResourceAccountIndexStore new
  delegatedResourceAccountIndexStore.convert(ownerAddress);
  delegatedResourceAccountIndexStore.convert(receiverAddress);
  delegatedResourceAccountIndexStore.delegate(ownerAddress, receiverAddress, ...);
}
``` [4](#0-3) 

The same `convert()` path is also invoked from `UnfreezeBalanceActuator`'s new-index-format branch for both owner and receiver addresses.

This is structurally analogous to the Sherlock report: a single, unprivileged, protocol-allowed operation (here, repeatedly calling `FreezeBalanceContract` with distinct receivers) causes an internal data structure to grow without any per-account cap, and a later single-transaction call must iterate the entire structure (here: the `convert()` migration loop, or the `UnfreezeBalanceActuator` list copy/remove), consuming energy/CPU time proportional to the attacker-controlled list size.

### Impact Explanation
An attacker who controls one account can grow its own `toAccounts` list (and simultaneously grow the `fromAccounts` list of every distinct receiver account they choose, including victim accounts they don't control) to an arbitrary size using ordinary `FreezeBalanceContract` transactions (bounded only by the attacker's TRX balance and the minimum 1 TRX freeze amount per delegation — cheap to repeat with many receiver addresses). Once the list is large:
- Any subsequent `UnfreezeBalanceContract` from that owner (or from a receiver who was delegated to) becomes proportionally more expensive/slow, because the whole list is deep-copied into an `ArrayList` and linearly scanned to remove one entry.
- Any call path that triggers `convert()` for that address (freeze/unfreeze with delegation once the network activates `AllowDelegateOptimization`) must loop over the entire legacy list and write two DB records per entry, which is unbounded CPU/DB work executed within the gas/time budget of a single transaction.

Because the `fromAccounts` list is also mutated on the *receiver* side without the receiver's consent (the receiver never chose to be delegated to), an attacker can force this unbounded growth onto arbitrary victim accounts as well, potentially causing their future freeze/unfreeze/resource-migration transactions to fail or become disproportionately expensive — a resource-exhaustion / partial denial-of-service against a specific account, achievable by a single unprivileged transaction broadcaster with no special permissions.

### Likelihood Explanation
Likelihood is moderate-to-high in principle: the actuator code path is directly reachable by any account via a standard, low-fee `FreezeBalanceContract` transaction, and there is no validation limiting the number of distinct `receiverAddress` values a single owner can delegate to. However, exploitability depends on the `AllowDelegateOptimization` dynamic parameter state on the live network (the legacy list-append path is only taken while this parameter is off; once on, growth stops in the legacy structure but `convert()` is triggered exactly once per address to migrate the already-accumulated list, which is where the unbounded loop cost is realized). This chain configuration detail could not be fully confirmed from the code alone — determining whether `AllowDelegateOptimization` is already permanently enabled on mainnet (which would make new abuse impossible but pre-existing accumulated lists still convertible) requires runtime/config inspection not available via static code search.

### Recommendation
- Enforce a maximum number of distinct delegatees (`toAccounts`) and delegators (`fromAccounts`) per `DelegatedResourceAccountIndexCapsule`, validated in `FreezeBalanceActuator.validate()`/`DelegateResourceActuator.validate()` before allowing a new delegation.
- Avoid loading, copying, and linearly scanning the entire `toAccounts`/`fromAccounts` list on every unfreeze; use a keyed/sharded store lookup (as already partly done via `V2_FROM_PREFIX`/`V2_TO_PREFIX`) instead of an in-capsule list scan.
- In `DelegatedResourceAccountIndexStore.convert()`, bound or chunk the migration work per transaction, or perform the migration lazily/incrementally rather than in one unbounded loop triggered synchronously inside a user transaction.

### Proof of Concept
1. Attacker account `A` (any funded account, no special privileges) repeatedly broadcasts `FreezeBalanceContract` transactions with `frozenBalance = 1_000_000` (1 TRX, the validated minimum) and a fresh, distinct `receiverAddress` each time (as shown feasible in the existing test `FreezeBalanceActuatorTest.testMultiFreezeDelegatedBalanceForBandwidth`, which demonstrates 100+ distinct receivers being appended without any validation rejection) [5](#0-4) .
2. Each call appends one entry to `A`'s `toAccounts` list and one entry to the corresponding receiver's `fromAccounts` list via `FreezeBalanceActuator.delegateResource()` [1](#0-0) , with no upper bound enforced in `validate()`.
3. Repeating this thousands of times (cost scales linearly with number of receivers, independent of any single receiver's balance) inflates `A`'s index capsule to a very large size.
4. A later `UnfreezeBalanceContract` from `A` (or the `convert()` call triggered on delegation-optimization migration) must copy and scan/rewrite this entire list in one transaction [2](#0-1) , [3](#0-2) , consuming CPU/energy proportional to the attacker-inflated list size — the same class of unbounded-loop-in-a-single-transaction issue described in the source report.

  public void convert(byte[] address) {
    DelegatedResourceAccountIndexCapsule indexCapsule = this.get(address);
    if (indexCapsule == null) {
      // convert complete or have no delegate
      return;
    }
    // convert old data
    List<ByteString> toList = indexCapsule.getToAccountsList();
    for (int i = 0; i < toList.size(); i++) {
      // use index as the timestamp, just to keep index in order
      this.delegate(address, toList.get(i).toByteArray(), i + 1L);
    }

    List<ByteString> fromList = indexCapsule.getFromAccountsList();
    for (int i = 0; i < fromList.size(); i++) {
      // use index as the timestamp, just to keep index in order
      this.delegate(fromList.get(i).toByteArray(), address, i + 1L);
    }
    this.delete(address);
  }
