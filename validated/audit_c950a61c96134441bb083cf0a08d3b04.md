### Title
Third-party `TransferToGasKey` action lets anyone grief gas-key/account deletion by pushing balance above the burn cap - (File: runtime/runtime/src/actions.rs, runtime/runtime/src/access_keys.rs)

### Summary
`action_transfer_to_gas_key` is reachable by any predecessor, not just the account owner, because `check_actor_permissions` explicitly skips the actor check for `Action::TransferToGasKey` [1](#0-0) . This mirrors the GOAT `createVote` bug class: a value used later in an "upper-bound" validation (`gas_key_info.balance <= MAX_BALANCE_TO_BURN`) can be inflated by an unrelated third party at negligible cost, causing a legitimate action (key/account deletion) to permanently fail.

### Finding Description
`action_transfer_to_gas_key` unconditionally adds `action.deposit` to the target gas key's `balance` field with no restriction on who the predecessor is [2](#0-1) . Since the actor-permission dispatch in `check_actor_permissions` places `TransferToGasKey` in the group that performs no `actor_id != account_id` check (unlike `WithdrawFromGasKey`, `AddKey`, `DeleteKey`, `Stake`, etc., which do enforce it) [3](#0-2) , any account can send a `Transfer`-style receipt containing this action to bump a victim's gas key balance, analogous to sending unsolicited ERC-20 tokens to a target contract in the GOAT report.

Later, `delete_gas_key` enforces an *upper-bound* check on that same attacker-controllable field: if `gas_key_info.balance > GasKeyInfo::MAX_BALANCE_TO_BURN`, the `DeleteKey` action fails with `GasKeyBalanceTooHigh` and no state changes occur [4](#0-3) . Deleting an account sums all its gas-key balances against the same `MAX_BALANCE_TO_BURN` threshold, so the same griefing vector blocks `DeleteAccount` too, as documented in the spec's invariants section [5](#0-4) .

This is structurally identical to the GOAT `createVote` bug: a check of the form "value ≤ threshold" is fed by state that an unrelated party can freely inflate via a normal, unprivileged transfer-style action, letting them deterministically break another user's transaction.

### Impact Explanation
An attacker can watch the mempool/chain for `DeleteKey` (on a gas key) or `DeleteAccount` transactions and front-run them with a cheap `TransferToGasKey` receipt carrying `MAX_BALANCE_TO_BURN + 1` yoctoNEAR (a 1-NEAR-scale deposit, essentially the account rent-exempt minimum, not the attacker's own funds since it's attached deposit taken from the attacker's balance and then burned on success). This can indefinitely deny the account owner the ability to delete that gas key or delete the account itself, a persistent denial-of-service on a normal user's ability to reclaim/close their account — this is a freezing-of-functionality bug reachable by any unprivileged signer with no special permissions, matching the "unprivileged-signer analog" class requested (access keys, action execution).

### Likelihood Explanation
Trivial to trigger: the attacker only needs to submit a single `TransferToGasKeyAction` transaction (or delegate/meta-transaction) to the victim account with any deposit above the constant threshold, and repeat it any time the victim tries to delete the key/account (since a failed `DeleteKey` due to `GasKeyBalanceTooHigh` does not consume the balance, the attacker's funds stay there ready to keep blocking future attempts, similar to the GOAT report's sandwich/no-net-cost dynamic — here the attacker's deposit is simply "parked" on the gas key rather than needing repeated funding).

### Recommendation
Restrict `Action::TransferToGasKey` to require `actor_id == account_id` in `check_actor_permissions`, matching `WithdrawFromGasKey`, `AddKey`, and `DeleteKey`, so only the account owner (or their explicitly authorized keys) can fund their own gas keys — preventing third parties from manipulating a value that is later checked against `MAX_BALANCE_TO_BURN` for deletion.

### Proof of Concept
1. Victim account `alice.near` has an existing gas key with public key `PK`.
2. Attacker (any account) submits a transaction/receipt with `Action::TransferToGasKey(TransferToGasKeyAction { public_key: PK, deposit: MAX_BALANCE_TO_BURN + 1 })` targeting `alice.near`. This succeeds because `check_actor_permissions` does not check the actor for this action [1](#0-0) , and `action_transfer_to_gas_key` adds the deposit unconditionally [6](#0-5) .
3. Alice later submits `Action::DeleteKey(DeleteKeyAction { public_key: PK })` to remove the gas key (e.g., to reclaim storage or clean up). `delete_gas_key` now sees `gas_key_info.balance > MAX_BALANCE_TO_BURN` and returns `ActionErrorKind::GasKeyBalanceTooHigh`, aborting the deletion [7](#0-6) .
4. The same balance is summed during `DeleteAccount`, so Alice also cannot delete her account while this gas key exists with the inflated balance, as noted in the invariants of the accounts/keys spec [5](#0-4) .

    result: &mut ActionResult,
    account_id: &AccountId,

    let Some(mut access_key) = get_access_key(state_update, account_id, &action.public_key)? else {
        result.result = Err(ActionErrorKind::GasKeyDoesNotExist {
            account_id: account_id.clone(),
            public_key: Box::new(action.public_key.clone()),
        }
        .into());
        return Ok(());
    };
    let Some(gas_key_info) = access_key.gas_key_info_mut() else {
        // Key exists but is not a gas key
        result.result = Err(ActionErrorKind::GasKeyDoesNotExist {
            account_id: account_id.clone(),
            public_key: Box::new(action.public_key.clone()),
        }
        .into());
        return Ok(());
    };

    gas_key_info.balance = gas_key_info.balance.checked_add(action.deposit).ok_or_else(|| {
        RuntimeError::StorageError(StorageError::StorageInconsistentState(
            "gas key balance integer overflow".to_string(),
        ))
    })?;
    set_access_key(state_update, account_id.clone(), action.public_key.clone(), &access_key);
    Ok(())
}
