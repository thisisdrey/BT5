### Title
Unchecked exit status of `git submodule update` allows silent partial/corrupted checkouts - (File: `tools/build_defs/repo/git_worker.bzl`)

### Summary
In `tools/build_defs/repo/git_worker.bzl`, every git invocation checks the `return_code` field of the `exec_result` struct returned by `ctx.execute()` and calls `_error()` on failure — except `update_submodules()`, which discards the returned status entirely. This is the direct analog of the reported Solidity bug class: a call whose success/failure is communicated via a return value is invoked but that return value is never inspected, so a genuine failure is treated as success.

### Finding Description
`git_repo()` drives the fetch/checkout sequence for `git_repository`/`new_git_repository`: [1](#0-0) 

Every helper that shells out to `git` checks the return code and fails loudly on error, e.g. `init`, `_git`, and `fetch`: [2](#0-1) [3](#0-2) 

`_git_maybe_shallow` itself returns the `exec_result` struct (carrying `return_code`, `stdout`, `stderr`) without checking it — callers are expected to check it, as `fetch()` correctly does at line 181 (`if st.return_code == 0: return`, else fall through to error handling at line 202).

However, `update_submodules()` calls `_git_maybe_shallow()` and **discards the returned struct completely**, never checking `return_code`: [4](#0-3) 

Compare this to `_git_sparse_checkout_config` and `_git_sparse_checkout`, which capture `st` and explicitly check `st.return_code != 0` before proceeding: [5](#0-4) 

### Impact Explanation
If `git submodule update --init --recursive --checkout --force` (or the non-recursive variant) fails — for example because an attacker-controlled submodule remote returns a fetch error, drops the connection, force-pushed away the pinned submodule commit, or otherwise causes git to exit non-zero for one of potentially many submodules — Bazel does not notice. The repository rule proceeds as if the checkout completed successfully, returning a `commit`/`shallow_since` struct for the top-level repo that implies a fully materialized, reproducible checkout. In reality the working tree can be left with missing, stale, or partially-initialized submodule directories, silently breaking the hermeticity/integrity guarantee that `git_repository` is supposed to provide (a repository pinned to specific commits actually containing that content on disk). This is a concrete violation of the "untrusted content stays data" / "fetch success is binding" invariant: unlike every other git operation in this file, a failed operation here is swallowed instead of surfacing as a build failure.

### Likelihood Explanation
Any `git_repository`/`new_git_repository` invocation with `init_submodules = True` or `recursive_init_submodules = True` and at least one submodule pointing at a URL not fully controlled by the trusted root repo (a common pattern — submodule URLs are frequently third-party GitHub/GitLab repos) is affected. An outsider serving content at one of those submodule URLs (or intermittently failing to serve it) can trigger `git submodule update` to fail for just that submodule while leaving the overall fetch marked successful, with no error surfaced to the user/build.

### Recommendation
Capture the `exec_result` returned by `_git_maybe_shallow()` in `update_submodules()` and check `return_code`, calling `_error()` (as done everywhere else in this file) on failure, e.g.:
```python
def update_submodules(ctx, git_repo, recursive = False):
    if recursive:
        st = _git_maybe_shallow(ctx, git_repo, "-c", "protocol.file.allow=always", "submodule", "update", "--init", "--recursive", "--checkout", "--force")
    else:
        st = _git_maybe_shallow(ctx, git_repo, "-c", "protocol.file.allow=always", "submodule", "update", "--init", "--checkout", "--force")
    if st.return_code != 0:
        _error(ctx.name, ["git", "submodule", "update"], st.stderr)
```

### Proof of Concept
A `src/test/shell/bazel` integration test can demonstrate this: set up a `git_repository` with `recursive_init_submodules = True` pointing at a local bare submodule remote; after the initial successful fetch, make the submodule remote unreachable or force-push a divergent history so `git submodule update --init --recursive --checkout --force` exits non-zero on a subsequent `bazel fetch`/`bazel build` of the same repository (simulating an attacker breaking/altering the submodule source). Observe that `bazel build` reports success and does not surface the git error, while the submodule directory on disk is missing/stale content compared to what the pinned commit should contain — confirming the swallowed failure.

    cl = ["git", "init", str(git_repo.directory)]
    st = ctx.execute(cl, environment = ctx.os.environ | _GIT_LOCAL_ENV_VARS)
    if st.return_code != 0:
        _error(ctx.name, cl, st.stderr)

def add_origin(ctx, git_repo, remote):

def fetch(ctx, git_repo):
    args = ["fetch", "origin"]

    sparse_checkout_patterns_or_file = \
        getattr(ctx.attr, "sparse_checkout_patterns", None) or \
        getattr(ctx.attr, "sparse_checkout_file", None)
    if sparse_checkout_patterns_or_file:
        if _git_sparse_checkout_config(ctx, git_repo):
            # Use filter to disable downloading file contents until we set the `sparse-checkout` patterns.
            args.append("--filter=blob:none")
        else:
            print("WARNING: Sparse checkout is not supported. Doing a full checkout.")
            sparse_checkout_patterns_or_file = None

    args.extend(["--", git_repo.fetch_ref])
    st = _git_maybe_shallow(ctx, git_repo, *args)

    if sparse_checkout_patterns_or_file:
        _git_sparse_checkout(ctx, git_repo, sparse_checkout_patterns_or_file)

    if st.return_code == 0:
        return
    if ctx.attr.commit:
        # Perhaps uploadpack.allowReachableSHA1InWant or similar is not enabled on the server;
        # fall back to fetching all branches, tags, and history.
        # The semantics of --tags flag of git-fetch have changed in Git 1.9, from 1.9 it means
        # "everything that is already specified and all tags"; before 1.9, it used to mean
        # "ignore what is specified and fetch all tags".
        # The arguments below work correctly for both before 1.9 and after 1.9,
        # as we directly specify the list of references to fetch.

        _git(
            ctx,
            git_repo,
            "fetch",
            "origin",
            "--",
            "refs/heads/*:refs/remotes/origin/*",
            "refs/tags/*:refs/tags/*",
        )
    else:

def _git_sparse_checkout(ctx, git_repo, sparse_checkout_patterns_or_file):
    """Initialize the repo with patterns for a sparse checkout.

    Args:
        ctx: Context of the calling rules.
        git_repo: The Git repository to initialize for sparse checkout.
        sparse_checkout_patterns_or_file: Either a list of patterns or a Label for a sparse-checkout file.
    """

    # Note: `init` is deprecated, but needed for older versions of Git. This command may be removed
    # in future versions.
    init_command = ["sparse-checkout", "init", "--no-cone"]
    st = _execute(ctx, git_repo, init_command)
    if st.return_code != 0:
        _error(ctx.name, init_command, st.stderr)

    if type(sparse_checkout_patterns_or_file) == "list":
        sparse_checkout_patterns = sparse_checkout_patterns_or_file
        set_command = ["sparse-checkout", "set"] + sparse_checkout_patterns
        st = _execute(ctx, git_repo, set_command)
        if st.return_code != 0:
            _error(ctx.name, set_command, st.stderr)
