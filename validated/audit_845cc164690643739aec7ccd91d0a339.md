### Title
Attached NEAR deposit is permanently lost when `rlp_execute` fails validation before a promise is created - ([File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs])

### Summary
The eth-implicit wallet contract's `rlp_execute` entry point is `#[payable]` and allows external callers/relayers to attach a NEAR deposit that is meant to be forwarded (or refunded) as part of executing an Ethereum-style transaction. The contract explicitly tracks this via `CallerDeposit` so it can be refunded if the downstream cross-contract promise fails [1](#0-0) . However, this refund logic is only wired into the final `rlp_execute_callback` after a promise has actually been dispatched [2](#0-1) . Any error that occurs in `inner_rlp_execute` *before* a promise is created — e.g. RLP/ABI parsing errors or `action_to_promise` construction errors — causes the function to return early with `Err`, discarding the already-computed `caller_deposit` without ever creating a refund transfer [3](#0-2) .

### Finding Description
When `rlp_execute` is called with an attached deposit, NEAR's protocol semantics deposit that balance into the wallet contract's account *before* contract execution starts (per the Economics API: "attached_deposit ... will be immediately deposited before the contract execution starts") [4](#0-3) . The NEAR runtime only auto-generates a deposit refund receipt when the *receipt itself fails* [5](#0-4) . If the contract method returns successfully (even with a logical failure encoded in its return value), the receipt is considered successful and no refund is produced by the protocol — any refund must be performed explicitly by the contract.

`inner_rlp_execute` computes `caller_deposit` up front from the attached deposit [6](#0-5) , but every early-exit error path — parsing failures propagated via `?` at line 347/348, explicit `return Err(err)` for `Error::User`/other errors at lines 389-409, and `action_to_promise(target, action)?` failing at line 469 (e.g. an attempted `AddFullAccessKey` action returns `Err(Error::User(UserError::UnsupportedAction(...)))` per `action_to_promise`) — simply drops `caller_deposit` and bubbles the error up. `rlp_execute` then converts this `Err` into `PromiseOrValue::Value(e.into())` without ever creating a `Promise` to refund the caller [7](#0-6) . Since the call returns a `Value` (not a `Promise`) and does not panic, the function-call receipt succeeds, and the deposit that was attached by the (external, non-owner) caller is permanently absorbed into the wallet contract's account balance with no code path to reclaim it.

This is a direct analog of the reported bug class: value is consumed/committed on one leg of a multi-step (in this case single-shard but multi-phase promise/validation) flow, and a downstream failure that occurs before the compensating logic is reached results in permanent, unrecoverable loss of the depositor's funds, because the "refund on failure" mechanism (`CallerDeposit`) was implemented for only one specific failure branch and omitted from all earlier ones.

### Impact Explanation
Any external account (a relayer or any other unprivileged account, not the wallet owner) that calls `rlp_execute` with a nonzero attached deposit and a transaction that fails validation before a promise is dispatched (invalid RLP/ABI encoding, unsupported action such as `AddFullAccessKey`/`CreateAccount`/`Delegate`/`DeleteAccount`/`DeployContract`/`Stake`, invalid access-key account id, invalid public key, etc.) permanently loses the attached NEAR. This is a genuine loss-of-funds bug for anyone who attaches a deposit to `rlp_execute` and hits one of these validation errors, since there is no owner-only privilege check bypass involved — it's reachable by any unprivileged caller/relayer interacting with the wallet contract.

### Likelihood Explanation
Likelihood is moderate-to-high in practice: relayer implementations or front-ends could easily construct an ABI-encoded action that hits one of the `UserError`/`RelayerError` branches (malformed calldata, excess yoctoNear, unsupported action types) while still attaching a NEAR deposit intended to cover fees/value for the action. Because `rlp_execute` is a generic entry point intended to be called by third-party relayers on behalf of users, and deposit + failure is a realistic combination (not requiring any adversarial control over the target contract), this can be triggered unintentionally as well as maliciously.

### Recommendation
Ensure `caller_deposit` (or the equivalent attached deposit) is refunded on every early-return error path in `inner_rlp_execute`/`rlp_execute`, not just in `rlp_execute_callback`. Concretely: before returning `Err`/`PromiseOrValue::Value` for any error variant, if `context.attached_deposit` is nonzero and `predecessor_account_id != current_account_id`, create a `Promise` transferring the deposit back to `predecessor_account_id` (mirroring the pattern already used in `rlp_execute_callback`'s `PromiseResult::Failed` branch).

### Proof of Concept
1. An external relayer account (not the wallet owner) calls `rlp_execute` on a deployed `WalletContract`, attaching a nonzero NEAR deposit, with an RLP-encoded Ethereum transaction whose ABI-decoded payload is an `AddKey` action requesting `is_full_access = true`.
2. `inner_rlp_execute` parses the transaction successfully (`parse_rlp_tx_to_action` succeeds, since `AddFullAccessKey` is only rejected in `action_to_promise`), computes `caller_deposit = Some(CallerDeposit { account_id: relayer, yocto_near: deposit })` [6](#0-5) .
3. Execution reaches the default branch and calls `action_to_promise(target, action)?`, which returns `Err(Error::User(UserError::UnsupportedAction(UnsupportedAction::AddFullAccessKey)))` [8](#0-7) [9](#0-8) .
4. The `?` propagates the error out of `inner_rlp_execute`, and `rlp_execute` converts it to `PromiseOrValue::Value(e.into())` with no promise created [7](#0-6) .
5. The function call receipt succeeds (returns an `ExecuteResponse{success:false,...}` value), so the NEAR protocol does not generate any deposit-refund receipt. The relayer's attached deposit remains in the wallet contract's account balance permanently, with no method exposed to withdraw or reclaim it on the caller's behalf.

/// A data type to keep track of the deposit given by an external caller.
/// This allows us to refund the caller's deposit if the cross-contract call fails.
#[derive(Debug, PartialEq, Eq, Clone, serde::Serialize, serde::Deserialize)]
pub struct CallerDeposit {
    pub account_id: AccountId,
    pub yocto_near: NonZeroU128,
}

impl CallerDeposit {
    pub fn new(context: &ExecutionContext) -> Option<Self> {
        // Only track for external (non-self) callers
        if context.current_account_id == context.predecessor_account_id {
            return None;
        }

        NonZeroU128::new(context.attached_deposit.as_yoctonear()).map(|yocto_near| Self {
            account_id: context.predecessor_account_id.clone(),
            yocto_near,
        })
    }
}

fn inner_rlp_execute(
    current_account_id: AccountId,
    predecessor_account_id: AccountId,
    target: AccountId,
    tx_bytes_b64: String,
    nonce: &mut u64,
) -> Result<Promise, Error> {
    if *nonce == u64::MAX {
        return Err(Error::AccountNonceExhausted);
    }
    let context = ExecutionContext::new(
        current_account_id.clone(),
        predecessor_account_id,
        env::attached_deposit(),
    )?;
    let caller_deposit = CallerDeposit::new(&context);

    let parsing_result = internal::parse_rlp_tx_to_action(&tx_bytes_b64, &target, &context, *nonce);
    let (action, transaction_kind) = match parsing_result {
        Ok((action, transaction_kind)) => {
            // Increment nonce for all cases where the registrar contract is not needed
            // to prevent replay of those transactions. For transactions that go through
            // the registrar we still do not know if the transaction has a relayer error
            // or not, therefore we must delay incrementing the nonce.
            //
            // Note: relayers with access keys cannot use this delay to needlessly spend
            // the users tokens because only one transaction is allowed to be in-flight
            // at a time.
            if let TransactionKind::EthEmulation(EthEmulationKind::EOABaseTokenTransfer {
                address_check: Some(_),
                ..
            }) = &transaction_kind
            {
            } else {
                *nonce = nonce.saturating_add(1);
            }

            // If the action is an emulated base token or ERC-20 transfer with a non-zero fee then
            // create a promise to send the refund to the relayer. This allows any relayer
            // to safely serve base token transfers from any wallet without additional
            // on-boarding because the relayer will receive some compensation for sending
            // the transaction. Users should always verify the fee before signing a base token
            // transfer. Relayers should also verify the fee before sending to make sure the
            // user's signed transaction will refund enough to cover the relayer's gas costs.
            if let TransactionKind::EthEmulation(EthEmulationKind::EOABaseTokenTransfer {
                fee,
                ..
            })
            | TransactionKind::EthEmulation(EthEmulationKind::ERC20Transfer { fee, .. }) =
                &transaction_kind
            {
                if !fee.is_zero() && context.predecessor_account_id != context.current_account_id {
                    let refund_promise = env::promise_batch_create(&context.predecessor_account_id);
                    env::promise_batch_action_transfer(refund_promise, *fee);
                }
            }

            (action, transaction_kind)
        }
        Err(err @ Error::User(_)) => {
            // Increment nonce on all user errors to prevent replay.
            *nonce = nonce.saturating_add(1);
            return Err(err);
        }
        Err(err) => {
            // Do not increment nonce on Relayer or AccountId errors.
            // The latter error is an issue in the deployment (so the nonce is meaningless).
            // The former arises from the relayer itself doing something wrong and thus the
            // user's transaction could still be valid and potentially submitted properly by
            // another relayer. To allow this we do not increment the nonce.
            //
            // Note: if a relayer is using an access key for this wallet then that key will
            // still be revoked (in the main logic of `rlp_execute`). This fact together with
            // the condition that there only be one in-flight transaction at a time implies
            // that a relayer cannot maliciously burn a large portion of the user's tokens.
            // If the relayer is not using an access key then they are spending their own
            // resources on the gas and therefore we do not care if the relayer submits
            // the same faulty transaction multiple times.
            return Err(err);
        }
    };

- `account_balance` -- the balance attached to the given account. This includes the `attached_deposit` that was attached
  to the transaction;
- `attached_deposit` -- the balance that was attached to the call that will be immediately deposited before
