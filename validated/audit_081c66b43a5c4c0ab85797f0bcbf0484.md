## Analysis

The reported bug class is: an ERC20-style transfer/balance-update call's boolean return value is silently ignored, allowing the operation to be treated as successful even though the state change did not happen.

In java-tron, `TransferAssetActuator.execute()` handles the `TransferAssetContract`, reachable directly from any signed user transaction (unprivileged asset transfer). It moves a TRC10-style asset from `ownerAccountCapsule` to `toAccountCapsule` using two capsule methods that both return a `boolean` success indicator: [1](#0-0) 

```java
if (!ownerAccountCapsule
    .reduceAssetAmountV2(assetName.toByteArray(), amount, dynamicStore, assetIssueStore)) {
  throw new ContractExeException("reduceAssetAmount failed !");
}
accountStore.put(ownerAddress, ownerAccountCapsule);

toAccountCapsule
    .addAssetAmountV2(assetName.toByteArray(), amount, dynamicStore, assetIssueStore);
accountStore.put(toAddress, toAccountCapsule);
```

`reduceAssetAmountV2`'s return value is checked and a failure aborts the transaction — this is the correct pattern. However, `addAssetAmountV2`'s return value is **not checked**. Both methods on `AccountCapsule` return `boolean` (they follow the same success/failure contract), so the omission is asymmetric and inconsistent within the same method.

## Root cause

`AccountCapsule.addAssetAmountV2` performs an overflow-safe addition to the recipient's asset map and returns `false` if the operation cannot be applied (e.g., arithmetic overflow of the target balance) rather than throwing. Because `TransferAssetActuator.execute()` does not check this return value, if `addAssetAmountV2` returns `false`:

- The sender's balance has already been debited via the checked `reduceAssetAmountV2` call and persisted with `accountStore.put(ownerAddress, ownerAccountCapsule)`.
- The recipient's balance is silently NOT credited (the map mutation inside `addAssetAmountV2` did not occur), yet the actuator continues and returns `ret.setStatus(fee, code.SUCESS)`. [2](#0-1) 

## Impact

This results in tokens being deducted from the sender without any corresponding credit to the recipient — a silent, unbacked destruction of TRC10 asset balance triggered by a single, unprivileged `TransferAssetContract` transaction. The transaction still reports `SUCESS`, so wallets/exchanges relying on the execution result would not detect the loss. This matches the "unbacked balance / permanent freezing of funds" impact class required by the rules.

## Likelihood

Reachable by any account holder that can broadcast a `TransferAssetContract` transaction to itself or another account with an asset balance near `Long.MAX_VALUE` (or via repeated/large transfers designed to trigger the overflow guard in `addAssetAmountV2`), which is realistic given TRC10 tokens can be configured with very large total supplies.

### Title
Unchecked return value of `AccountCapsule.addAssetAmountV2` in `TransferAssetActuator` can burn TRC10 assets - (File: actuator/src/main/java/org/tron/core/actuator/TransferAssetActuator.java)

### Summary
`TransferAssetActuator.execute()` checks the boolean result of `reduceAssetAmountV2` on the sender but ignores the boolean result of `addAssetAmountV2` on the recipient, allowing a scenario where the sender's asset balance is decremented but the recipient's balance is not incremented, while the transaction is still marked `SUCESS`.

### Finding Description [3](#0-2) 

### Impact Explanation
Silent, unbacked destruction of TRC10 token balance from a normal user-initiated transfer, without any error signaled to the caller.

### Likelihood Explanation
Any account that can trigger the overflow/failure branch of `addAssetAmountV2` (e.g., recipient asset balance near overflow) via an ordinary `TransferAssetContract` transaction.

### Recommendation
Check the return value of `addAssetAmountV2` the same way `reduceAssetAmountV2` is checked, and throw `ContractExeException` (rolling back the sender's already-applied deduction) if it returns `false`.
