### Title
No per-request timeout on `git upload-pack --advertise-refs` subprocess allows slow/non-reading client to hang worker and exhaust resources - (File: internal/gitaly/service/smarthttp/inforefs.go)

### Summary
`handleInfoRefs` spawns `git <service> --stateless-rpc --advertise-refs` and writes its stdout directly into the gRPC response stream, then blocks on `cmd.Wait()` using only the raw `stream.Context()` for cancellation. Because gRPC-Go blocks `stream.Send()` when the client's flow-control window is exhausted, a client that opens the stream and never reads (or reads extremely slowly) can keep the subprocess's stdout pipe full and the RPC goroutine blocked indefinitely, with no server-enforced timeout to intervene.

### Finding Description
`InfoRefsUploadPack`/`InfoRefsReceivePack` call `s.handleInfoRefs(stream.Context(), ...)` [1](#0-0)  which spawns the git subprocess with `gitcmd.WithStdout(w)`, where `w` writes into `stream.Send(...)` [2](#0-1) , and then unconditionally calls `cmd.Wait()` with no wrapping timeout or read-progress monitor [3](#0-2) .

`internal/command.New` ties process teardown strictly to the passed-in `ctx`: the process is only killed when `ctx.Done()` fires [4](#0-3) . Here `ctx` is the raw stream context, which is *not* canceled just because the client stops reading — gRPC's HTTP/2 flow control instead makes `stream.Send()` (and therefore the write into the pipe feeding `cmd`) block silently while the connection itself stays alive (the client can keep answering PING frames). The gRPC server is configured only with `KeepaliveEnforcementPolicy`/`KeepaliveParams{Time: 5m}` for connection liveness pings; there is no `MaxConnectionIdle`/`MaxConnectionAge` or any per-RPC deadline enforced in the interceptor chain for this RPC [5](#0-4) .

By contrast, the analogous SSH upload-pack path (`runUploadCommand`) deliberately guards against exactly this scenario by deriving a cancellable child context and running a `pktline.NewReadMonitor`/`timeoutTicker` to bound the negotiation phase [6](#0-5) . `handleInfoRefs` has no equivalent safeguard.

The optional concurrency-limiter middleware (`internal/grpc/middleware/limithandler`) can bound the number of concurrent/queued RPCs per repo, but it is opt-in via `[[concurrency]]` configuration and is not enabled by default; even when enabled it only limits how many slow streams can occupy a slot concurrently, it does not un-stick or reap already-blocked streams, so the slow-reader can still occupy that fixed concurrency slot indefinitely.

### Impact Explanation
An attacker can open many concurrent `InfoRefsUploadPack`/`InfoRefsReceivePack` streams (e.g. against a self-owned/forked repository seeded with a large number of refs to inflate advertisement size) and simply stop reading. Each such stream permanently pins a git subprocess, its process-group, open file descriptors/pipes, and a Gitaly server goroutine, none of which are ever reclaimed absent client-initiated cancellation or a TCP-level failure. Repeating this at scale exhausts file descriptors/goroutines/process table entries on the Gitaly node, degrading or denying `InfoRefsUploadPack`/`InfoRefsReceivePack` (and by extension git clone/fetch/push over HTTP) for all tenants sharing that node — a server-wide Denial of Service.

### Likelihood Explanation
The attacker only needs standard network access to a Gitaly/GitLab HTTP(S) endpoint and control over a repository they can fetch from (their own project, fork, or import), which satisfies the "unprivileged user" precondition. No special configuration, secrets, or race conditions are required — simply opening a stream and pausing reads (or reading at trickle rate) is sufficient and trivially repeatable/scriptable to amplify with many concurrent connections.

### Recommendation
Bound `handleInfoRefs` (and other RPC handlers that pipe subprocess stdout directly into `stream.Send`) with an explicit, request-scoped timeout/read-progress watchdog analogous to `runUploadCommand`'s `pktline.NewReadMonitor` + `timeoutTicker`, cancelling the derived context (and thus killing the subprocess via `command.New`'s teardown path) if the client fails to make read progress within a bounded window. Additionally, configure server-side `grpc.MaxConnectionIdle`/`MaxConnectionAge` and enable default concurrency limits for `InfoRefsUploadPack`/`InfoRefsReceivePack` as defense in depth.
