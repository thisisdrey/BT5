This is confirmed: `AdaptiveLimit.Update()` executes registered hooks while holding only the `AdaptiveLimit`'s own mutex, and `NewConcurrencyLimiter` registers a hook that iterates `limiter.limitsByKey` without acquiring `ConcurrencyLimiter.m`, while `getConcurrencyLimit`/`putConcurrencyLimit` mutate that same map under `c.m`. This is a genuine, reachable concurrent-map-access race triggerable purely by ordinary RPC traffic combined with the periodic adaptive-limit calibration goroutine — an unprivileged-reachable analog to the "shares accounting becomes inconsistent/corrupted under specific state transitions" bug class, here manifesting as a crash of the RPC resource-limiting subsystem (DoS) rather than fund loss.

### Title
Unsynchronized map iteration in `AdaptiveLimit.AfterUpdate` hook causes concurrent map read/write panic in `ConcurrencyLimiter` - (File: internal/limiter/concurrency_limiter.go)

### Summary
`ConcurrencyLimiter.limitsByKey` is a plain Go map protected by `ConcurrencyLimiter.m` (a `sync.RWMutex`). Every RPC that goes through the concurrency limiter calls `getConcurrencyLimit`/`putConcurrencyLimit`, which correctly lock/unlock `c.m` around all map reads and writes. [1](#0-0) [2](#0-1) 

However, `NewConcurrencyLimiter` registers an `AfterUpdate` hook on the shared `AdaptiveLimit` that iterates over `limiter.limitsByKey` directly, with no lock on `c.m` at all: [3](#0-2) 

This hook is invoked from `AdaptiveLimit.Update`, which only takes the `AdaptiveLimit`'s *own* mutex, not `ConcurrencyLimiter.m`: [4](#0-3) 

`Update` (and therefore the map iteration inside the hook) is called periodically and asynchronously by `AdaptiveCalculator.calibrateLimits`, running on its own background goroutine independent of any specific RPC: [5](#0-4) 

### Finding Description
While the calibration goroutine is executing the `AfterUpdate` hook and ranging over `limiter.limitsByKey` (an unsynchronized read), any concurrent RPC hitting a concurrency-limited endpoint calls `getConcurrencyLimit`, which takes `c.m.Lock()` and writes to the same map (`c.limitsByKey[limitingKey] = &keyedConcurrencyLimiter{...}` or increments `refcount`), or `putConcurrencyLimit`, which deletes entries from the map. Go's built-in maps are not safe for concurrent read/write, and simultaneous read (range) and write/delete on the same map from different goroutines is undefined behavior that Go's runtime actively detects and turns into a fatal, unrecoverable `fatal error: concurrent map read and map write` process crash — this cannot be caught by `recover()`.

Because concurrency-limiting is configured per-RPC via ordinary server config (`internal/gitaly/config/config.go` `Concurrency`/`ConcurrencyLimits`, and adaptive settings), and the calibration ticker in `AdaptiveCalculator.Start` fires on a fixed interval (`DefaultCalibrateFrequency = 30 * time.Second`) regardless of any privileged action, any ordinary user issuing a normal stream of RPCs against a concurrency-limited/adaptive-limited endpoint (e.g. `PackObjects`, or any RPC configured under `Concurrency` in gitaly config) is enough to race with the periodic calibration goroutine. [6](#0-5) 

### Impact Explanation
A successful race crashes the entire `gitaly` process with a fatal runtime error, taking down all in-flight RPCs on that node, not just the concurrency-limited one — this is a full denial-of-service of the RPC handler / resource-limiting subsystem, matching the "DoS of a handler" acceptance criterion. This is analogous in bug-class to the referenced report insofar as an accounting/bookkeeping structure (there: global shares; here: the per-key limiter map/refcount) is mutated from multiple code paths without a consistent invariant/lock discipline, leading to a broken state (there: locked funds; here: process crash).

### Likelihood Explanation
Likelihood is moderate-to-high in any deployment that (a) has adaptive concurrency limiting enabled for at least one RPC (a supported, documented, non-privileged configuration — see `doc/load-management-architecture.md` and `AdaptiveSetting`), and (b) receives ordinary concurrent client traffic against that RPC. No malicious input, elevated privileges, or crafted RPC fields are required — normal traffic plus the periodic 30s calibration tick is sufficient to create the race window; higher RPC concurrency and load-driven calibration events (which shrink/grow limits more frequently) increase the chance of hitting the exact interleaving.

### Recommendation
Have the `AfterUpdate` hook acquire `ConcurrencyLimiter.m` (or an equivalent lock) before iterating `limitsByKey`, and audit `keyedConcurrencyLimiter` field mutations (`queueTokens`/`concurrencyTokens.Resize`) for consistency under the same lock, so that adaptive-limit updates and per-key limiter creation/eviction cannot interleave unsynchronized. Alternatively, use a `sync.Map`, snapshot the map under `c.m.RLock()` before iterating, or route the resize operation through the existing `getConcurrencyLimit`/`putConcurrencyLimit` locking path.

### Proof of Concept
1. Configure a concurrency-limited RPC with `Adaptive: true` in Gitaly config (per `internal/gitaly/config/config.go` `ConcurrencyLimits`), so `NewAdaptiveCalculator`/`NewConcurrencyLimiter` wiring registers the unsynchronized `AfterUpdate` hook (as in `internal/limiter/concurrency_limiter.go:171-186`).
2. Drive continuous concurrent client load against that RPC from many goroutines/connections so `getConcurrencyLimit`/`putConcurrencyLimit` are constantly mutating `limitsByKey` with many distinct limiting keys (e.g., varying `repository` field to create/evict many map entries).
3. Ensure the `AdaptiveCalculator`'s calibration ticker fires (default every 30s, or shortened via `CalibrationInterval` for testing) so `calibrateLimits` → `limit.Update()` → the `AfterUpdate` hook ranges over `limitsByKey` concurrently with step 2.
4. Run with Go's race detector (`-race`) or under sustained load; observe either a `WARNING: DATA RACE` report or a `fatal error: concurrent map read and map write` process crash, terminating the gitaly server.

// getConcurrencyLimit retrieves the concurrency limit for the given key. If no such limiter exists
// it will be lazily constructed.
func (c *ConcurrencyLimiter) getConcurrencyLimit(limitingKey string) *keyedConcurrencyLimiter {
	c.m.Lock()
	defer c.m.Unlock()

	if c.limitsByKey[limitingKey] == nil {
		// Set up the queue tokens in case a maximum queue length was requested. As the
		// queue tokens are kept during the whole lifetime of the concurrency-limited
		// function we add the concurrency tokens to the number of available token.
		var queueTokens semaphorer
		if c.maxQueueLength > 0 {
			queueTokens = c.createSemaphore(uint(c.currentLimit() + c.maxQueueLength))
		}

		c.limitsByKey[limitingKey] = &keyedConcurrencyLimiter{
			monitor:               c.monitor,
			maxQueueWait:          c.maxQueueWait,
			setWaitTimeoutContext: c.SetWaitTimeoutContext,
			concurrencyTokens:     c.createSemaphore(uint(c.currentLimit())),
			queueTokens:           queueTokens,
		}
	}

	c.limitsByKey[limitingKey].refcount++

	return c.limitsByKey[limitingKey]
}

// putConcurrencyLimit drops the reference to the concurrency limit identified by the given key.
// This must only ever be called after `getConcurrencyLimit()` for the same key. If the reference
// count of the concurrency limit drops to zero then it will be destroyed.
func (c *ConcurrencyLimiter) putConcurrencyLimit(limitingKey string) {
	c.m.Lock()
	defer c.m.Unlock()

	ref := c.limitsByKey[limitingKey]
	if ref == nil {
		panic("semaphore should be in the map")
	}

	if ref.refcount <= 0 {
		panic(fmt.Sprintf("bad semaphore ref refcount %d", ref.refcount))
	}

	ref.refcount--
	if ref.refcount == 0 {
		delete(c.limitsByKey, limitingKey)
	}
}

// Update adjusts the current limit value and executes all registered update hooks.
func (l *AdaptiveLimit) Update(val int) {
	l.Lock()
	defer l.Unlock()

	if val != l.current {
		l.current = val
		for _, hook := range l.updateHooks {
			hook(val)
		}
	}
}
