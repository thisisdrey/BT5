## Analysis

The SAML "signature wrapping" bug class is: the verifier cryptographically checks one blob, but the application actually consumes/displays a *different* blob than the one it verified — allowing an attacker to smuggle unverified content into a context that appears verified.

The closest reachable analog in this Gitaly checkout is in the annotated-tag signature-splitting logic, `ExtractTagSignature`, which is unrelated to the already-hardened commit-signature parser (`internal/git/catfile/parse_commit.go`, which explicitly guards against this exact bug class for commits — see the `parseCommitStateUnexpected` handling and the "PGP signed commit with headers after the signature" test). Tags do not get the same protection. [1](#0-0) 

### Title
Tag content/signature desynchronization via naive first-marker split enables signature-wrapping-style content spoofing - (File: internal/git/catfile/tag.go)

### Summary
`ExtractTagSignature` splits an annotated tag's message into "signed content" and "signature" by locating only the *first* occurrence of the literal string `-----BEGIN` in the raw tag message, with no validation of a matching `-----END...-----` trailer and no rejection of multiple/nested `-----BEGIN` markers. An ordinary user who can create an annotated tag (via `git push` of a crafted tag object, `UserCreateTag`, or repository import/fork) fully controls the tag message and can therefore control exactly where this split occurs. [2](#0-1) 

### Finding Description
`GetTagSignatures` streams back `Content` (text believed to precede the signature) and `Signature` (text believed to be the signature block) for each requested tag, explicitly documented as "Content contains the contents which are signed by the signature." [3](#0-2) [4](#0-3) 

Because the split point is just `bytes.Index(content, []byte("-----BEGIN"))`, an attacker fully controlling the tag message (which is untrusted, attacker-suppliable data on push/import) can embed an attacker-chosen `-----BEGIN` token earlier in the message body than any real signature block. This desynchronizes what Gitaly reports as the "signed content" from the actual bytes that a downstream PGP/SSH signature verifier will parse out of the `Signature` field — the same root-cause pattern as SAML signature wrapping, where the entity that consumes the "verified" payload is not looking at the same bytes the cryptographic check actually covers. In addition, `parseTag` independently returns the entire raw, unsplit `tag.Message` (used for display purposes elsewhere) while `SignatureType` detection reads only the first line following the first detected marker, further widening the gap between "what is displayed", "what is nominally verified", and "what the split actually isolated". [5](#0-4) 

This is a direct architectural gap compared to the commit path, where the parser was explicitly hardened (with regression tests) against "malicious users draft[ing] a commit similar to a previously signed commit but with additional headers" — the exact wrapping scenario — by folding all post-signature bytes into the verified payload rather than silently truncating at the first marker. [6](#0-5) 

### Impact Explanation
A malicious, unprivileged repository contributor can craft an annotated tag whose message contains an early, attacker-chosen pseudo-signature marker. Any Gitaly consumer that trusts the `Content`/`Signature` split contract from `GetTagSignatures` (e.g., a Rails caller doing tag signature verification/badge rendering) can be misled into treating attacker-controlled trailing bytes as "part of the signature" (unverified, silently accepted) or displaying tag content that was never actually covered by the cryptographic check, while a legitimate-looking verified indicator is still produced. This mirrors the impact category of the reference report: an attacker-influenced structure defeats the intended binding between "what was verified" and "what is trusted/displayed."

### Likelihood Explanation
Likelihood is high for the *reachability* component (creating annotated tags with arbitrary messages is an ordinary, unprivileged git operation — via push, `UserCreateTag`, fork, or import) but the practical severity depends on how permissively a specific downstream consumer parses the returned `Signature` bytes. Within Gitaly's own boundary, the contract violation (returning a `Content`/`Signature` pair that does not correspond to a single, well-formed signature block) is concretely and deterministically reproducible.

### Recommendation
Harden `ExtractTagSignature` analogous to the commit-signature parser: require a properly bounded `-----BEGIN ... -----END ...-----` block, reject/flag messages containing multiple or malformed marker occurrences instead of silently splitting at the first substring match, and ensure any bytes outside the recognized well-formed signature block are treated as part of the signed content rather than being dropped from `Content` or folded unreviewed into `Signature`.

### Proof of Concept
1. As an unprivileged user, push or create (e.g. via `UserCreateTag`) an annotated tag object whose message body is:
   ```
   Legit-looking release notes
   -----BEGIN PGP SIGNATURE-----
   <attacker-chosen bytes, not a valid signature>
   -----END PGP SIGNATURE-----
   <trailing bytes appended after a genuine, previously-obtained valid signature block for different content>
   ```
2. Call `GetTagSignatures` for this tag revision.
3. Observe that `Content` returned is truncated at the first `-----BEGIN` occurrence and `Signature` contains everything after it verbatim, including the attacker-appended trailing bytes concatenated after any real signature block — with no structural validation that this represents a single, well-formed, isolated signature. [7](#0-6)

// ExtractTagSignature extracts the signature from a content and returns both the signature
// and the remaining content. If no signature is found, nil as the signature and the entire
// content are returned. note: tags contain the signature block at the end of the message
// https://github.com/git/git/blob/master/Documentation/technical/signature-format.txt#L12
func ExtractTagSignature(content []byte) ([]byte, []byte) {
	index := bytes.Index(content, []byte("-----BEGIN"))

	if index > 0 {
		return bytes.TrimSuffix(content[index:], []byte("\n")), content[:index]
	}
	return nil, content
}
