### Title
Bandwidth-request generation can silently emit **zero** requested values for a shard link whose buffered receipts exceed `max_single_grant`, permanently starving that link of the bandwidth needed to move its head receipt - (File: `core/primitives/src/bandwidth_scheduler.rs`)

### Summary
`BandwidthRequest::make_from_receipt_sizes` computes, for each buffered receipt, the cumulative size of all receipts up to and including it, and tries to find the smallest predefined bitmap value that is `>=` that cumulative size. If the cumulative size for the very first receipt whose total crosses `base_bandwidth` also exceeds the largest requestable value (`max_single_grant`), the search loop runs off the end of `values` and `break`s *without ever setting a bit*, and (because no earlier receipt had set a bit either) `bitmap.is_all_zeros()` returns `true`, so the function returns `Ok(None)` — i.e. no bandwidth request is generated at all for that link, even though the buffer genuinely needs more than `base_bandwidth` to drain.

### Finding Description
`core/primitives/src/bandwidth_scheduler.rs`:

`values[values.len()-1] == params.max_single_grant` (see `BandwidthRequestValues::new`). The only protocol guarantee is `max_single_grant >= max_receipt_size` (`BandwidthSchedulerParams::calculate`, asserted at `core/primitives/src/bandwidth_scheduler.rs:325-328`) — there is **no** guaranteed margin between `max_single_grant` and `max_receipt_size + base_bandwidth`.

An attacker-controlled shard can queue receipts to a target shard such that:
1. A small "filler" receipt (or receipts) sums to just under `base_bandwidth` — these are skipped by the `continue` branch and never influence the bitmap.
2. The next receipt (attacker-chosen size, up to `max_receipt_size`, reachable via cross-shard `promise_batch_action_function_call` payload/attached data sizing) pushes the running `total_size` past `max_single_grant`.

Because this is the *first* receipt to cross `base_bandwidth`, `cur_value_idx` starts at `0` and walks straight to `values.len()` without ever setting a bit — the loop then `break`s for the *whole* iterator, so no subsequent receipt gets a chance to set a bit either. `is_all_zeros()` returns `true`, and the caller (`SchedulerBandwidthRequest::new` / `generate_bandwidth_requests` in `runtime/runtime/src/congestion_control.rs`) receives `None`: **no `BandwidthRequest` is ever generated for that link**, on this height or any future height where the same stuck receipt remains at the head of the buffer (the computation is deterministic and repeats identically every height).

The scheduler (`runtime/runtime/src/bandwidth_scheduler/scheduler.rs`) still grants `base_bandwidth` unconditionally (`grant_base_bandwidth`, `:340`) and may hand out extra bandwidth via `distribute_remaining_bandwidth` (`:393`, in `distribute_remaining.rs`), but that fair-share stage divides *leftover* shard budget evenly across *all* allowed links regardless of actual demand — it is not guaranteed, and under any real network load is very unlikely, to reach `max_receipt_size` on this one link, since with no explicit request the scheduler has no signal that this link needs more than `base_bandwidth`. Since a receipt must be sent whole within a single height's granted bandwidth (it cannot be split), and the granted amount here can permanently remain below the head receipt's size, the head receipt at the front of the outgoing buffer for this link can never be forwarded — the link stalls indefinitely, and every subsequent receipt behind it in the same outgoing-buffer FIFO is blocked as well.

None of the existing checks (signature/nonce/access-key/gas-metering/size-limit) prevent this: the attacker only needs to control receipt sizes emitted from their own contract via ordinary cross-shard promises (`promise_batch_action_function_call_weight`), which is fully within an unprivileged account's capability, and receipt size is bounded only by `max_receipt_size`, which is exactly the value used to construct the attack.

### Impact Explanation
If this repeats deterministically every height (because the stuck head receipt and buffer state are unchanged run to run), affected outgoing-buffer entries on the targeted shard link are never delivered, permanently freezing whatever value/state transition those receipts represent (e.g., attached deposits, contract calls that would release funds). This matches **Critical – Permanent freezing of funds**, since restoring liveness on the link would require either a state-affecting migration or a protocol/hardfork-level fix (bitmap/values scheme is part of the protocol, so changing it is a protocol upgrade).

### Likelihood Explanation
- Preconditions: relies on `max_single_grant` having little or no safety margin over `max_receipt_size + base_bandwidth`. This margin is a config/economic property of `BandwidthSchedulerParams`, not something the audit could directly confirm for the exact live mainnet values from the code alone; the only enforced invariant is `max_single_grant >= max_receipt_size` (`core/primitives/src/bandwidth_scheduler.rs:325-328`), which does **not** rule out this scenario.
- Cost: trivially cheap — attacker only needs to deploy one contract and generate two or more cross-shard receipts with chosen sizes (near-zero cost beyond normal gas/storage fees).
- Repeatability: deterministic and fully reproducible in a unit test using `BandwidthRequest::make_from_receipt_sizes` directly with the parameters described above.
- Given the uncertainty about the exact production margin between `max_single_grant`, `max_receipt_size`, and `base_bandwidth`, exploitability is condition-dependent, but the code path itself is a genuine logic defect independent of any specific configuration edge.

### Recommendation
Instead of `break`-ing without recording anything once `cur_value_idx == values.len()`, cap the request to the maximum available value (`values.len() - 1`, i.e. `max_single_grant`) and set that bit before breaking. This ensures that whenever cumulative demand exceeds what can ever be granted on a single link, the request still asks for (and the scheduler still tries to grant) the maximum obtainable bandwidth, instead of silently requesting nothing.

```rust
impl SchedulerBandwidthRequest {
    pub fn new(
        sender_shard: ShardId,
        bandwidth_request: &BandwidthRequest,
        params: &BandwidthSchedulerParams,
        layout: &ShardLayout,
    ) -> Option<Self> {
        let Ok(sender_index) = layout.get_shard_index(sender_shard) else {
            // Request from a shard that is not in the current set of shards.
            return None;
        };
        let Ok(receiver_index) = layout.get_shard_index(bandwidth_request.to_shard.into()) else {
            // Request to a shard that is not in the current set of shards.
            return None;
        };
        let link = ShardLink::new(sender_index, receiver_index);

        let mut bandwidth_increases = VecDeque::new();

        // Keeps track of the total bandwidth that would be granted by the requested increases.
        // Base bandwidth is already granted on all links, so we start with that.
        let mut current_total = params.base_bandwidth;

        let request_values = BandwidthRequestValues::new(params).values;
        for bit_idx in 0..bandwidth_request.requested_values_bitmap.len() {
            if !bandwidth_request.requested_values_bitmap.get_bit(bit_idx) {
                continue;
            }

            // Request for the total value of bandwidth that should be granted on the link.
            let requested_value = request_values[bit_idx];
            if requested_value <= current_total {
                continue;
            }
            // Convert the absolute value to a bandwidth increase.
            bandwidth_increases.push_back(requested_value - current_total);
            current_total = requested_value;
        }

        if bandwidth_increases.is_empty() {
            return None;
        }

        Some(Self { link, bandwidth_increases })
    }
```
