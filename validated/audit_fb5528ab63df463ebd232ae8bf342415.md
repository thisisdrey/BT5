### Title
Missing content-hash verification in `extend_with_attachments` lets a malicious peer inflate its `ReliabilityReport` with garbage responses - (File: stackslib/src/net/atlas/download.rs)

### Summary
`AttachmentsBatchStateContext::extend_with_attachments` credits a peer with `bump_successful_requests()` as soon as its HTTP response parses as a valid `GetAttachmentResponse` JSON, without checking that the returned `Attachment`'s hash matches the `content_hash` field of the `AttachmentRequest` that was sent. A malicious peer can therefore always answer any `AttachmentRequest` with cheap, arbitrary bytes that merely decode successfully, and be rewarded exactly as if it had served the correct data.

### Finding Description
The `AttachmentRequest` sent to a peer carries a specific `content_hash: Hash160` identifying which attachment is being asked for ` [2](#0-1) `. When the response comes back, `extend_with_attachments` only checks that `response.decode_atlas_get_attachment()` succeeds (i.e., the JSON parses into a `GetAttachmentResponse`/`Attachment`) before inserting the attachment into `self.attachments` and calling `report.bump_successful_requests()`:

```rust
if let Ok(response) = response.decode_atlas_get_attachment() {
    self.attachments.insert(response.attachment);
    report.bump_successful_requests();
} else {
    report.bump_failed_requests();
}
```
` [3](#0-2) `

There is no equality check against `request.content_hash` anywhere in this function or in the surrounding `try_proceed` state machine transition that calls it ` [4](#0-3) `. Contrast this with `extend_with_inventories`, which has the analogous structure but for a different response type and likewise has no cross-check against the requested contract/pages beyond keying by `request.key()` — however for attachments, the semantic requirement is stricter: the response payload's hash must equal what was actually requested, since `self.attachments` is a `HashSet<Attachment>` keyed by content and later stored via `insert_instantiated_attachment` in `run()` ` [5](#0-4) `. Any `Attachment` whose bytes hash to something never requested is accepted into this set and later inserted into the atlas DB as an "instantiated attachment," and the peer that supplied it is rewarded via `bump_successful_requests()` regardless of whether it satisfied any pending `AttachmentInstance`.

Because `ReliabilityReport` implements `Ord`/`PartialOrd` used to order `AttachmentRequest` and `AttachmentsInventoryRequest` in the `BinaryHeap` priority queues (`get_prioritized_attachments_requests`, `get_prioritized_attachments_inventory_requests`), a peer that always returns quickly-computed garbage JSON that merely parses successfully will have its `successful_requests` counter climb identically to an honest peer serving correct attachment bytes. This lets the malicious peer's `ReliabilityReport` reach parity with, or exceed, honest peers, which skews `sources: HashMap<UrlString, ReliabilityReport>` selection in `get_prioritized_attachments_requests` toward the attacker for future attachment fetch attempts.

### Impact Explanation
The attacker permanently degrades the download subsystem's peer-selection quality on the read/download path: honest peers get statistically de-prioritized relative to an attacker who never needs to serve correct data, only syntactically-valid JSON, which is far cheaper to produce than real attachment content. This is a bounded compute/reliability-DoS on the Atlas attachment-download machinery — matching the "bounded compute DoS on a read endpoint" category. It does not cause a crash, forged canonical state, or write to StackerDB/mempool, and the malformed `Attachment` itself is not treated as satisfying any real `AttachmentInstance` (no hash match occurs when later resolving `attachments_batch.resolve_attachment`), so the practical effect is degraded availability/service prioritization rather than direct data corruption.

### Likelihood Explanation
Preconditions are minimal: the attacker only needs to run a peer that another node treats as an outbound sync peer with a discoverable data URL (`network.get_outbound_sync_peers()` / `get_data_url`), and to respond to `GET /attachments/:hash`-style Atlas requests with any body that deserializes into `GetAttachmentResponse`. This requires no privileged role, no secret, and no state manipulation — just responding to inbound requests the victim node itself initiates toward the attacker's advertised data URL. It's fully repeatable per attachment-batch cycle.

### Recommendation
In `extend_with_attachments`, after successfully decoding the response, compute the attachment's content hash (e.g., `response.attachment.hash()`) and compare it against `request.content_hash` before inserting into `self.attachments` and before calling `report.bump_successful_requests()`. On mismatch, treat it the same as a failed/faulty response (`report.bump_failed_requests()`, and optionally mark the peer as faulty/deregister the event) rather than silently discarding without penalty.

    pub fn extend_with_attachments(
        mut self,
        results: &mut BatchedRequestsResult<AttachmentRequest>,
    ) -> AttachmentsBatchStateContext {
        for (request, response) in results.succeeded.drain() {
            let report = self
                .peers
                .get_mut(request.get_url())
                .expect("Atlas: unable to retrieve reliability report for peer");

            let response = if let Some(r) = response {
                r
            } else {
                report.bump_failed_requests();
                continue;
            };

            if let Ok(response) = response.decode_atlas_get_attachment() {
                self.attachments.insert(response.attachment);
                report.bump_successful_requests();
            } else {
                report.bump_failed_requests();
            }
        }
        let mut events_ids = results.faulty_peers.keys().copied().collect::<Vec<usize>>();
        self.events_to_deregister.append(&mut events_ids);

        self
    }
