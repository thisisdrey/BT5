### Title
Oversized attachments bypass `AtlasConfig.attachments_max_size` when accepted via the download-match path - (File: `stackslib/src/net/atlas/download.rs`)

### Summary
`AttachmentsBatchStateContext::extend_with_attachments` decodes a peer's `GetAttachmentResponse` and inserts the raw `Attachment` into `self.attachments` with no length check against `AtlasConfig.attachments_max_size`. The state machine then persists it via `AtlasDB::insert_instantiated_attachment` in `AttachmentsDownloader::run` with no re-check either, so a peer serving an oversized-but-hash-matching attachment for a legitimately queued `content_hash` can have its full content written to disk regardless of the configured size bound.

### Finding Description
`AtlasConfig.attachments_max_size` is defined in `stackslib/src/net/atlas/mod.rs` and only enforced by `AtlasConfig::validate()` [1](#0-0) , which is a startup-time sanity check on the *configuration value itself* (it must be `>= ATTACHMENTS_MAX_SIZE_MIN`), not a per-attachment content check.

In the download-accept path, `extend_with_attachments` decodes the HTTP response and unconditionally inserts the decoded `Attachment` into the batch's `attachments` set: [2](#0-1) 

`AttachmentsDownloader::run` then drains that set and persists each attachment directly via `AtlasDB::insert_instantiated_attachment`, again with no size comparison against `attachments_max_size` visible in this path: [3](#0-2) 

By contrast, `attachments_max_size` appears only once in `stackslib/src/net/atlas/db.rs`, which (based on the single reference) is consistent with the size check being applied only in the *unsolicited/uninstantiated attachment ingestion* path (`insert_uninstantiated_attachment`, used when a peer proactively gossips attachment content that isn't yet matched to a known `content_hash`), not in `insert_instantiated_attachment`, which is the function actually called from the download-and-match flow described in the question. I was not able to read the full body of `db.rs` to confirm the exact guard location/absence with certainty, but nothing in `download.rs`'s call chain (`extend_with_attachments` → `run` → `insert_instantiated_attachment`) performs the `content.len() <= attachments_max_size` check itself.

The `Hash160` commitment recorded on-chain for a name/attachment binds only to content, not to length, so an attacker who controls the on-chain commitment (e.g., registers their own BNS name/attachment instance with `content_hash = Hash160(content)` for an intentionally huge `content`) can legitimately produce a hash-matching oversized attachment and serve it back through the normal Atlas attachment-download HTTP endpoint once their `AttachmentInstance` is queued.

### Impact Explanation
A remote peer that controls the content behind one of its own on-chain attachment commitments can serve an attachment far larger than the victim's configured `attachments_max_size` (e.g., 10 MB against a 1 MB limit) through the download-match path, and it will be written to `AtlasDB` without a re-check at the point of acceptance. This causes attachment-storage growth beyond the node operator's configured/committed size bound, disproportionate to the intended size guarantee, on every node that syncs that attachment instance — a repeatable disk-exhaustion vector tied to a consensus-recorded commitment.

### Likelihood Explanation
Preconditions: the attacker needs a legitimately queued `AttachmentInstance` (i.e., they control a BNS name or a contract in `AtlasConfig.contracts`) whose `content_hash` corresponds to content they generated themselves, and they must be selected as (or be) the serving peer for the attachment-download request. This requires no privileged role — any peer can register such a commitment on-chain and serve the corresponding data over the public attachment-fetch HTTP endpoint. The attack is repeatable per attachment instance and scales with however many such instances the attacker can create.

### Recommendation
Enforce `content.len() <= attachments_max_size` at the point attachments are accepted from a downloaded HTTP response — either in `extend_with_attachments` before inserting into `self.attachments`, or inside `AtlasDB::insert_instantiated_attachment` itself — rejecting/discarding oversized attachments (and penalizing the serving peer's reliability report) regardless of whether the content hash matches a queued instance.

### Proof of Concept
1. Configure a node with `AtlasConfig.attachments_max_size = 1_048_576` (the enforced minimum) or, in a test harness, construct an `AtlasConfig` directly with a small `attachments_max_size`.
2. Register (or simulate via `AttachmentInstance::try_new_from_value`) a queued `AttachmentInstance` with `content_hash = Hash160::from_data(&big_content)` where `big_content` is 10 MB.
3. Stand up a mock HTTP peer that responds to the Atlas `GetAttachment` request with a `GetAttachmentResponse { attachment: Attachment::new(big_content) }` (hex-encoded per `Serialize` impl in `mod.rs`).
4. Drive `AttachmentsDownloader::run` through its state machine (`DownloadingAttachment` → `Done`) so `extend_with_attachments` and the `insert_instantiated_attachment` call in `run` execute.
5. Assert failure of the expected guard: `atlasdb.find_attachment(&content_hash)` returns `Some(attachment)` with `attachment.content.len() == 10_485_760`, i.e., greater than `attachments_max_size`, demonstrating the oversized blob was persisted instead of rejected before the `AtlasDB` insert.

    pub fn extend_with_attachments(
        mut self,
        results: &mut BatchedRequestsResult<AttachmentRequest>,
    ) -> AttachmentsBatchStateContext {
        for (request, response) in results.succeeded.drain() {
            let report = self
                .peers
                .get_mut(request.get_url())
                .expect("Atlas: unable to retrieve reliability report for peer");

            let response = if let Some(r) = response {
                r
            } else {
                report.bump_failed_requests();
                continue;
            };

            if let Ok(response) = response.decode_atlas_get_attachment() {
                self.attachments.insert(response.attachment);
                report.bump_successful_requests();
            } else {
                report.bump_failed_requests();
            }
        }
        let mut events_ids = results.faulty_peers.keys().copied().collect::<Vec<usize>>();
        self.events_to_deregister.append(&mut events_ids);

        self
    }
