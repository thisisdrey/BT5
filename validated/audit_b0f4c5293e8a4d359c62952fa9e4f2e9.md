### Title
Cached `ConnectionPeerType` in `SwQosConnectionContext` allows a client to retain Staked-tier stream throttling limits after its stake is removed from the `StakedNodes` snapshot for the lifetime of an open QUIC connection - (File: streamer/src/nonblocking/swqos.rs)

### Summary
`SwQos::build_connection_context` computes `peer_type` and `total_stake` once, at connection establishment, from a single read of the shared `StakedNodes` snapshot via `get_connection_stake`. These values are cached inside `SwQosConnectionContext` and reused for every subsequent stream on that connection (`on_new_stream` → `max_streams_per_throttling_interval` → `StakedStreamLoadEMA::available_load_capacity_in_throttling_duration`), with no re-check against the live `StakedNodes` state, which is refreshed independently every 5 seconds by `StakedNodesUpdaterService`.

### Finding Description
`get_connection_stake` (`streamer/src/nonblocking/quic.rs:416-428`) reads the current `staked_nodes` `RwLock` snapshot and returns `(pubkey, stake, total_stake)`. This is only invoked once, in `QosController::build_connection_context` for `SwQos` (`streamer/src/nonblocking/swqos.rs:301-342`), which classifies the peer as `ConnectionPeerType::Staked(stake)` or `Unstaked` and stores `peer_type` and `total_stake` as plain fields inside `SwQosConnectionContext` (`streamer/src/nonblocking/swqos.rs:98-107`).

From then on, every stream on that connection calls `on_new_stream` (`streamer/src/nonblocking/swqos.rs:496-516`), which reads `context.peer_type()` and calls `max_streams_per_throttling_interval` (`streamer/src/nonblocking/swqos.rs:292-298`), which forwards the *cached* `conn_context.peer_type` and `conn_context.total_stake` into `StakedStreamLoadEMA::available_load_capacity_in_throttling_duration` (`streamer/src/nonblocking/stream_throttle.rs:167-188`). Nothing in this call chain re-reads `staked_nodes` for the life of the connection; `ConnectionContext::peer_type()` (`streamer/src/nonblocking/qos.rs:11-14`) is a pure accessor over the cached field, not a re-derivation.

Meanwhile, `StakedNodesUpdaterService` (`core/src/staked_nodes_updater_service.rs:22-45`) rewrites the shared `staked_nodes: Arc<RwLock<StakedNodes>>` from the root bank's current epoch stakes on a fixed 5-second cycle, independent of any individual connection's lifetime. If an attacker delegates stake just before opening the QUIC connection (so that the snapshot read by `build_connection_context` still reflects nonzero stake), and then undelegates it, the connection keeps `ConnectionPeerType::Staked(stake)` and the original `total_stake` cached in `SwQosConnectionContext` for as long as the QUIC connection stays open — there is no code path that re-evaluates `peer_type` against the refreshed `StakedNodes` for an already-established connection.

The higher per-peer connection allowance (`max_connections_per_staked_peer` vs `max_connections_per_unstaked_peer` in `SwQosConnectionContext`/`SwQos::cache_new_connection`, `streamer/src/nonblocking/swqos.rs:205-208`) is applied once at connection admission and is not the exploitable part per se (that's inherent to connection admission), but the per-stream throttling rate (`max_streams_per_throttling_interval`) is re-evaluated on *every single stream* yet still uses the stale cached `peer_type`/`total_stake`, giving the attacker a durable, ongoing Staked-tier stream quota advantage that persists well past the point where the node's live stake view says they have zero stake.

### Impact Explanation
This falls under the “unstaked/staked limits enforced per current source status” invariant described in the question. An unprivileged attacker (no real stake at time of abuse) can keep sending streams at the staked-tier rate (`max_staked_load_in_throttling_window` scaled by cached stake/total_stake, per `StakedStreamLoadEMA::available_load_capacity_in_throttling_duration`) instead of the much lower unstaked cap (`max_unstaked_load_in_throttling_window`, based on `MAX_UNSTAKED_TPS = 200`), for as long as the QUIC connection remains open. This lets the attacker unfairly consume TPU stream capacity that should be reserved for legitimately staked senders or fairly shared among unstaked senders, i.e., QoS evasion / unfair capacity capture — matching the bounty category of TPU QoS bypass.

### Likelihood Explanation
Preconditions: the attacker needs to be able to delegate stake to their own identity pubkey briefly (even a very small amount, subject to the `min_stake_ratio` check in `build_connection_context`), open a QUIC TPU connection while that stake is visible in the currently-loaded `StakedNodes` snapshot, then undelegate. Because `StakedNodesUpdaterService` only refreshes every 5 seconds from the root bank, and stake activation/deactivation is bounded by epoch boundaries (not truly "briefly" delegated/undelegated in normal Solana staking, since delegation changes take effect at epoch boundaries and require this to be their own stake), the actual attack requires the attacker to control a real stake account, which is a real-world cost/precondition but not "validator/leader/peer/gossip/staked-node control" in the disallowed sense — it's just being a token holder who stakes and unstakes, which is normal permissionless activity. Once the connection is established as Staked, the attacker only needs to keep the QUIC connection alive (via keepalives) to retain the elevated throttling rate indefinitely, which is straightforward and repeatable.

### Recommendation
Re-derive `peer_type`/`total_stake` from the live `staked_nodes` snapshot periodically (e.g., on each `on_new_stream` invocation, or via a lightweight background reconciliation task) rather than caching it once in `SwQosConnectionContext` at connection build time, and downgrade/reclassify (and re-enforce/prune) connections whose backing stake has been removed from the current snapshot, rather than trusting the connection-admission-time classification for the entire connection lifetime.

### Proof of Concept
Integration test plan (in `streamer/src/nonblocking/swqos.rs` test module style, mirroring the existing `test_build_connection_context_staked_peer` pattern):

```rust
#[tokio::test]
async fn test_stale_stake_snapshot_retains_staked_throttling() {
    let cancel = CancellationToken::new();
    let stats = Arc::new(StreamerStats::default());
    let server_keypair = Keypair::new();
    let client_keypair = Keypair::new();
    let stake_amount = 50_000_000;

    // 1. StakedNodes snapshot shows attacker as staked.
    let staked_nodes = create_staked_nodes_with_keypairs(&server_keypair, &client_keypair, stake_amount);
    let swqos = SwQos::new(SwQosConfig::default(), stats.clone(), staked_nodes.clone(), cancel.clone());

    let (connection, _c, _s) = create_connection_with_keypairs(&server_keypair, &client_keypair).await;

    // build_connection_context reads the (currently staked) snapshot once.
    let mut context = swqos.build_connection_context(&connection);
    assert!(matches!(context.peer_type(), ConnectionPeerType::Staked(_)));

    // 2. Attacker's stake is now removed from the live StakedNodes snapshot
    //    (simulating StakedNodesUpdaterService refreshing with undelegated stake).
    *staked_nodes.write().unwrap() = StakedNodes::default();

    // 3. Assert that a *new* classification would now be Unstaked...
    let fresh_context = swqos.build_connection_context(&connection);
    assert!(matches!(fresh_context.peer_type(), ConnectionPeerType::Unstaked));

    // 4. ...but the already-open connection's cached context still reports Staked,
    //    and stream throttling still grants the staked-tier allowance.
    assert!(matches!(context.peer_type(), ConnectionPeerType::Staked(_)));
    let staked_capacity = swqos.max_streams_per_throttling_interval(&context);

    context.peer_type = ConnectionPeerType::Unstaked; // what it *should* be post-refresh
    let unstaked_capacity = swqos.max_streams_per_throttling_interval(&context);

    assert!(staked_capacity > unstaked_capacity,
        "cached staked context should still yield a higher stream allowance than the corrected unstaked classification, proving the stale cache issue");
}
```

Expected result: the test demonstrates that `SwQosConnectionContext` built before the stake removal continues to yield the staked-tier `max_streams_per_throttling_interval` even though a fresh classification against the updated `StakedNodes` snapshot would correctly return `Unstaked`, confirming no per-stream re-validation occurs against current stake status.
