### Title
`ValidateMultiSign` precompile double-counts a single signer's weight via duplicate/malleable signatures, allowing multisig threshold bypass - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The `ValidateMultiSign` TVM precompile is meant to verify that the combined weight of *distinct* signers on a permission meets `permission.getThreshold()`, mirroring the intent of `TransactionCapsule.checkWeight` used for on-chain multisig transactions (which explicitly rejects a key signing twice: `"has signed twice!"`). In the precompile, the "already counted" check is keyed on the exact `(recoveredAddr, rawSign)` pair rather than on `recoveredAddr` alone, so if two different raw signature byte-strings recover to the *same* address, both are accepted and their weights are summed independently — directly analogous to the QVBaseStrategy bug, where a per-entity accounting value that should gate cumulative usage is not actually keyed/updated correctly, letting one entity's contribution be counted an unbounded number of times against the cap.

### Finding Description
In `ValidateMultiSign.execute()`: [1](#0-0) 

For each supplied signature, the code recovers the signer address, then checks:
```
if (ByteArray.matrixContains(executedSignList, recoveredAddr)) {
  if (ByteArray.matrixContains(executedSignList, sign)) {   // sign == merge(recoveredAddr, rawSign)
    continue;
  }
  MUtil.checkCPUTime();
}
long weight = TransactionCapsule.getWeight(permission, recoveredAddr);
...
totalWeight += weight;
executedSignList.add(sign);
executedSignList.add(recoveredAddr);
```
The intended de-duplication is "skip if this exact `recoveredAddr` has already contributed weight." Instead, the `continue` only fires when the *exact byte-for-byte* `sign` (address+raw signature bytes) has been seen before. If `recoveredAddr` was already counted but the caller supplies a **different raw signature** that recovers to the same address — e.g., an ECDSA signature malleated to `(r, n-s)` instead of `(r, s)`, which recovers to the identical address — the `continue` is skipped, `MUtil.checkCPUTime()` is called, and execution falls through to add that key's `weight` to `totalWeight` a second time.

This is structurally the same root cause as the reported `QVSimpleStrategy` bug: a value meant to represent "how much has this specific principal already contributed toward the cap" is not correctly tracked/keyed, so the cap check (`totalWeight >= permission.getThreshold()`) can be satisfied by repeatedly re-submitting variations attributable to a single principal instead of requiring genuinely independent principals.

By contrast, the equivalent on-chain multisig weight check `TransactionCapsule.checkWeight` explicitly de-duplicates by recovered address (via a `HashMap` keyed by the address/base64) and throws `"has signed twice!"` if the same address appears twice: [2](#0-1) 
The precompile diverges from this correct pattern, indicating the `ValidateMultiSign` de-duplication is the flawed one.

### Impact Explanation
`ValidateMultiSign` (address alias for TVM opcode `0x66` region) is invoked by any smart contract via the precompile call path in `PrecompiledContracts.getContractForAddress`; any unprivileged contract deployer/caller can invoke it as part of ordinary contract execution to check whether an off-chain-collected signature set meets an account's `Active`/`Owner` multisig permission threshold. If a single key holder (whose individual `weight` is below `threshold`) can produce two malleable signatures over the same message hash, they can single-handedly satisfy a multisig check that is supposed to require independently-controlled keys. Any contract logic gating fund transfers, withdrawals, or privileged actions on this precompile's boolean result (a common multisig-authorization pattern for smart contracts interacting with TRON accounts) can be bypassed by one key instead of the intended quorum, leading to unauthorized account operations / theft of funds contingent on this multisig gate.

### Likelihood Explanation
Reaching this path requires only a normal contract call from any account invoking the `validatemultisign` precompile with a crafted signature array — no special privilege, consensus role, or node compromise is needed. The main precondition for exploitability is that the underlying `recoverAddrBySign`/signature-recovery routine does not enforce canonical low-`s` (BIP-62-style) signatures, so that a valid ECDSA signature can be malleated into a second, distinct-byte but same-recovered-address signature. I was not able to view the implementation of `recoverAddrBySign` itself (it is declared/used in `PrecompiledContracts.java` but grep did not surface its body within the indexed context), so whether low-`s` canonicalization is enforced elsewhere in the signature-recovery/verification pipeline is unconfirmed from the available index. This is the key open uncertainty for definitively confirming exploitability of the malleability angle; however, independent of malleability, the code's de-duplication logic is provably keyed on the wrong value (full signature bytes) rather than on the signer address, which is a real logic defect matching the reported bug class regardless of whether malleable signatures are the only vector to exploit it (a caller could also simply supply the same address's signature encoded/padded differently in a way that changes the raw signature bytes without malleability, if the parsing/`extractSigArray` does not canonicalize).

### Recommendation
Change the duplicate-check in `ValidateMultiSign.execute()` to key strictly on `recoveredAddr`, matching `TransactionCapsule.checkWeight`'s approach: if `recoveredAddr` has already been counted, always `continue` (skip re-adding weight) regardless of whether the raw signature bytes differ. Concretely:
```java
if (ByteArray.matrixContains(executedSignList, recoveredAddr)) {
  continue; // an address must only contribute weight once, regardless of signature bytes used
}
long weight = TransactionCapsule.getWeight(permission, recoveredAddr);
...
totalWeight += weight;
executedSignList.add(recoveredAddr);
```
Additionally, confirm/enforce canonical (low-`s`) signature validation in the underlying `recoverAddrBySign`/signature verification utilities to eliminate the malleability vector at its source.

### Proof of Concept
Conceptual PoC (cannot be fully executed without visibility into `recoverAddrBySign`'s internals, which were not available in the indexed context):
1. Deploy/target an account with an `Active` permission containing one key `K` with `weight = 1` and `threshold = 2` (so `K` alone should never satisfy the permission).
2. Have `K` sign the message hash `hash = sha256(address || permissionId || data)` once, producing signature `sig1 = (r, s)`.
3. Derive the malleated signature `sig2 = (r, n - s)` for the same key/hash (standard secp256k1 ECDSA malleability), which recovers to the same address as `sig1` provided the recovery-id/verification does not reject high-`s` values.
4. Call the `validatemultisign` precompile with `signatures = [sig1, sig2]`.
5. Trace through `ValidateMultiSign.execute()`: for `sig1`, `recoveredAddr = K`; `executedSignList` is empty so weight `1` is added and both `merge(K, sig1)` and `K` are recorded. For `sig2`, `recoveredAddr = K` again; `matrixContains(executedSignList, K)` is true, but `matrixContains(executedSignList, merge(K, sig2))` is false (different raw bytes) — so the `continue` is skipped, and weight `1` is added again, giving `totalWeight = 2 >= threshold (2)`, returning `true` even though only one independent key participated.
