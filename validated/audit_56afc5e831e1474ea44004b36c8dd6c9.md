### Title
Excessive Memory Allocation via Unbounded Attacker-Controlled Array Length in `BatchValidateSign` Precompile - (`actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `BatchValidateSign` TVM precompiled contract (reachable from any smart contract call that any unprivileged account can trigger via a signed transaction) decodes an address-array length directly from attacker-supplied call data and uses it to allocate a two-dimensional byte array *before* any upper-bound validation is performed, mirroring the dr_flac.h bug class where a length field taken from untrusted input is used for allocation prior to sanity checking.

### Finding Description
`BatchValidateSign.doExecute()` parses the raw `data` payload of a TVM `CALL`/`STATICCALL` to the precompile address into words and immediately derives an array length from the attacker-controlled word without a preceding bound check for the address array: [1](#0-0) 

The `extractBytes32Array` helper that supplies `addresses` is called unconditionally (it is not gated by the `VMConfig.allowTvmSelfdestructRestriction()` branch, which only bounds the `sigArraySize`/`addrArraySize` read from a *different* offset and only when that feature flag is active). `extractBytes32Array` allocates `new byte[len][]` where `len = words[offset].intValueSafe()` is taken directly from the caller-supplied word, with no maximum-size check performed before the allocation: [2](#0-1) 

The `MAX_SIZE` (16) bound check that would reject an oversized request is only applied *after* the allocation has already occurred, via `cnt = signatures.length; if (cnt == 0 || cnt > MAX_SIZE ...)`: [3](#0-2) 

Because `len` comes straight from a 256-bit `DataWord` converted via `intValueSafe()`, an attacker can craft call data whose offset word encodes an extremely large integer, forcing the JVM to attempt allocating an oversized `byte[len][]` array on every node that executes/validates the transaction (or re-executes it during block validation/sync), well before the `MAX_SIZE` gate has a chance to reject it.

### Impact Explanation
A crafted transaction invoking the `BatchValidateSign` precompile (address `0x0f` in TVM) with a huge encoded address-array length can force every full node and SR that executes the transaction to attempt a huge heap allocation, potentially throwing `OutOfMemoryError` / causing significant GC pressure. Since this executes during both transaction validation (`execute`) and consensus block application, it can be triggered node-wide by a single broadcast transaction from any account with enough energy to reach the precompile, degrading or crashing node processes — a resource-exhaustion / denial-of-service impact consistent with the reported CVE class ("uncontrolled memory allocation" / VA:H in the CVSS vector).

### Likelihood Explanation
Likelihood is Medium: the precompile is reachable by any account that can deploy/call a contract invoking address `0x0f`, requiring no special privilege, and the vulnerable `extractBytes32Array` path is always exercised for the `addresses` array regardless of the `allowTvmSelfdestructRestriction` proposal state. The attacker only needs to craft the ABI-style call-data words so that the length word at the computed offset is large; energy metering (`getEnergyForData`) is based on `data.length / WORD_SIZE`, not on the derived array length, so the energy cost charged does not scale with the allocation attempted, weakening the natural cost-based mitigation.

### Recommendation
Add an explicit upper bound check (e.g., against `MAX_SIZE`) on the length word immediately after it is read in `extractBytes32Array` (and `extractBytesArray`), before allocating the `byte[len][]`/`byte[len]` arrays, mirroring the fix pattern used in dr_flac.h (validate declared length against a sane maximum/available payload size prior to allocation). Ensure the check is unconditional rather than gated behind the `allowTvmSelfdestructRestriction` feature flag, and consider charging energy proportional to the derived array length.

### Proof of Concept
Construct TVM call data for `CALL` to precompile address `0x0f`:
1. Word 0: arbitrary 32-byte `hash`.
2. Word 1: offset pointing to a small valid signatures-array section (to pass `extractSigArray`/`extractBytesArray` without early failure, or simply craft to reach `extractBytes32Array` first).
3. Word 2: offset value chosen such that `words[offset]` (the length word for the address array) is set to a very large integer, e.g. `0x7FFFFFFF`.
4. Deploy a minimal contract that performs `staticcall(gas(), 0x0f, ..., data, ...)` with this crafted payload and broadcast a signed transaction invoking it with sufficient energy.

Executing this transaction causes `extractBytes32Array` to attempt `new byte[2147483647][]` prior to the `MAX_SIZE` check, which is unbounded and reachable from an ordinary contract call.

    int len = words[offset].intValueSafe();
    byte[][] bytes32Array = new byte[len][];

      bytes32Array[i] = words[offset + i + 1].getData();
