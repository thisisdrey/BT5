### Title
StackerDB chunk signatures are not bound to the target contract, allowing cross-StackerDB signature/chunk replay - (File: `libstackerdb/src/libstackerdb.rs`)

### Summary
`SlotMetadata::auth_digest()` computes the signed digest solely from `(slot_id, slot_version, data_hash)`. It omits the StackerDB smart-contract identifier (the DB instance the chunk is destined for) entirely. Both the HTTP `POST /v2/stackerdb/:principal/:contract/chunks` handler and the p2p push/sync validation path (`try_replace_chunk`, `validate_received_chunk`) verify the signature only against the per-slot signer address that is looked up *for the contract named in the request/message* — they never check that the signature itself was produced for that contract. [1](#0-0) [3](#0-2) 

### Finding Description
If the same principal (the same private key) is registered as the owning signer of a given `slot_id` in two or more different StackerDB smart contracts (e.g. two different signer-set contracts, or a miner contract and a signer contract that happen to allocate the signer the same slot id, which is realistic since slot ids are typically assigned in signer/reward-cycle order and the same signer set participates across multiple `.signer-XX-YY` boot contracts each cycle), then a validly-signed `StackerDBChunkData` produced for contract A slot `S` version `V` with data hash `H` is a **bit-for-bit valid signature** for contract B's slot `S` version `V`/data hash `H` as well, because the signed digest never encodes which contract it was meant for.

This means:
- A chunk originally broadcast/pushed for contract A can be relayed (by any observer, not just the signer) into contract B's replica endpoint (`POST /v2/stackerdb/:addr/:contract-B/chunks`, handled by `try_handle_request` in `stackslib/src/net/api/poststackerdbchunk.rs`) and will pass `try_replace_chunk`'s signature check as long as slot/version/staleness constraints in B happen to line up.
- Equally, the p2p push-chunk and inventory-sync paths (`PeerNetwork::validate_received_chunk`, `StackerDBSync::validate_downloaded_chunk`) perform the identical `slot_metadata.verify(&addr)` check without folding in the contract id, so a forged routing of legitimately-signed data from one DB context into another passes remote validation and gets written to on-disk state via `insert_chunk`. [4](#0-3) [5](#0-4) 

This is the direct structural analog of the reported bug: a signature/authorization artifact that is only supposed to be valid for one specific intended context (the H-4 report's "one borrower's specific borrowing index") is instead scoped too loosely (here, missing the contract-id binding), so it can be replayed/misapplied into a different, unintended target that the signer/producer did not authorize for that data at that time.

### Impact Explanation
This breaks the equality that "a chunk stored under contract X, slot S was actually signed *for* contract X, slot S." A remote, unprivileged party who observes a legitimately-signed chunk in one StackerDB replication group can attempt to write (or relay for other nodes to write) that same signed payload into a different StackerDB contract's identical slot id, which the real signer never authorized for that DB. Where slot/version bookkeeping across the two DBs coincides (which is plausible since slot ids and lamport versions are independently and often similarly allocated per DB), this results in unauthorized cross-contract data being accepted and network-wide propagated as if it were legitimately authored data for that DB — an unauthorized write to StackerDB state and forged-data propagation across the network.

### Likelihood Explanation
Requires no privileged access — any network participant who can observe a signed chunk (chunks are broadcast/replicated, not secret) and knows another contract's slot allocation can attempt the replay against a different contract endpoint. The main precondition is that the same signer key owns the same `slot_id` in two contracts and the target's staleness/version checks happen to be satisfiable, which is realistic in the signer/miner StackerDB deployment pattern where the same signer set is re-registered with parallel slot layouts across consecutive `.signer-XX-YY` contracts each reward cycle.

### Recommendation
Include the StackerDB contract identifier (`QualifiedContractIdentifier`) in `SlotMetadata::auth_digest()` so signatures are cryptographically bound to the specific DB instance they are intended for, mirroring the report's mitigation of scoping the authorization artifact to the one specific intended context. This requires updating `sign`/`verify` call sites to pass the contract id, and bumping the wire format/version if backward compatibility with old signed chunks needs to be preserved.

### Proof of Concept
1. Register the same StacksPrivateKey `pk` as the signer of `slot_id = 0` in both StackerDB contract `A` and contract `B` (via `create_stackerdb`).
2. As the legitimate signer, sign `StackerDBChunkData { slot_id: 0, slot_version: 1, data: b"hello" }` with `pk` for contract `A`.
3. Take that identical `StackerDBChunkData` (same `sig`, `slot_id`, `slot_version`, `data`) and `POST` it to `/v2/stackerdb/<addr>/B-contract-name/chunks` instead of A's endpoint.
4. `try_replace_chunk` for contract B calls `slot_desc.verify(&slot_validation.signer)`, which succeeds because the digest `(slot_id=0, slot_version=1, data_hash(b"hello"))` matches and was produced by `pk`, and `pk` is also `B`'s slot-0 signer — the chunk is accepted into contract B's replica even though it was never authorized for B specifically.     fn auth_digest(&self) -> Sha512Trunc256Sum {
        let mut hasher = Sha512_256::new();
        hasher.update(self.slot_id.to_be_bytes());
        hasher.update(self.slot_version.to_be_bytes());
        hasher.update(self.data_hash.0);
        Sha512Trunc256Sum::from_hasher(hasher)
    }

        &self,
        smart_contract: &QualifiedContractIdentifier,
        slot_desc: &SlotMetadata,
        chunk: &[u8],
    ) -> Result<(), net_error> {
        // Check per-replica chunk-size cap.
        if (chunk.len() as u64) > self.config.chunk_size {
            return Err(net_error::StackerDBChunkTooBig(chunk.len()));
        }

        let slot_validation = self
            .get_slot_validation(smart_contract, slot_desc.slot_id)?
            .ok_or(net_error::NoSuchSlot(
                smart_contract.clone(),
                slot_desc.slot_id,
            ))?;

        if !slot_desc.verify(&slot_validation.signer)? {
            return Err(net_error::BadSlotSigner(
                slot_validation.signer,
                slot_desc.slot_id,
            ));
        }
