### Title
Cross-contract StackerDB chunk replay due to `SlotMetadata::auth_digest` omitting `smart_contract_id` - (File: libstackerdb/src/libstackerdb.rs)

### Summary
`SlotMetadata::auth_digest` computes the signed digest solely from `slot_id`, `slot_version`, and `data_hash`, never binding the target StackerDB's `smart_contract_id`. Consequently, a chunk signature that a slot owner produced for StackerDB contract A is equally valid for any other StackerDB contract B where that same address happens to be assigned the same `slot_id`, allowing a spectator who merely observed the gossiped/posted chunk to replay it into contract B via `POST /v2/stackerdb/.../chunks`.

### Finding Description
The broken equality is: "a signature valid for `(slot_id, slot_version, data_hash)` under contract A" is treated as equivalent to "a signature authorized by the owner of that same slot under contract B," when in fact the owner only ever intended to authorize a write into contract A's replica.

`SlotMetadata::auth_digest` in `libstackerdb/src/libstackerdb.rs` hashes only `slot_id`, `slot_version`, and `data_hash`: [1](#0-0) 

`SlotMetadata::verify` recovers the pubkey from that digest and compares its hash against the `principal` argument supplied by the caller — it never checks which contract the digest/signature was meant for: [2](#0-1) 

The verification call site, `StackerDBTx::try_replace_chunk` in `stackslib/src/net/stackerdb/db.rs`, looks up `slot_validation.signer` from contract B's own slot-owner table (populated independently per contract via `create_stackerdb`/`reconfigure_stackerdb`) and calls `slot_desc.verify(&slot_validation.signer)`: [3](#0-2) 

If the same StacksAddress is assigned to `slot_id` N in both contract A and contract B (a legitimate and unremarkable configuration overlap, e.g. the same signer set is reused across two different StackerDB replicas), the digest-only-over-(slot_id, slot_version, data_hash) signature that the owner produced and gossiped for contract A recovers to the exact same address for contract B, and `verify` returns `true` for both. The only other guards are the strictly-increasing `slot_version` check and the `max_writes` cap, both of which are per-(contract,slot) counters that are independent of contract A's version history and thus do not stop the replay as long as contract B's own version counter for that slot is behind the version used in the replayed message: [4](#0-3) 

The RPC entry point `poststackerdbchunk.rs::try_handle_request` deserializes the attacker-supplied `StackerDBChunkData` JSON body (attacker sets `contract_identifier` from the URL path to point at victim contract B, while `slot_id`, `slot_version`, `sig`, `data` are copied verbatim from the intercepted contract-A chunk) and passes it straight to `tx.try_replace_chunk`: [5](#0-4) 

No existing guard binds the signature to a specific `smart_contract_id`: the signature covers only slot-local metadata, and the contract identity used for the DB lookup is supplied entirely by the attacker via the URL path, not derived from or checked against anything inside the signed payload.

### Impact Explanation
An unprivileged attacker who has observed one legitimate signed chunk (via gossip on `StackerDBPushChunk` or `GET /v2/stackerdb/...`) can write attacker-chosen-timing (identical, but replay-timed) chunk data into a *different* StackerDB replica under the same slot, without holding any private key, as long as the two replicas share a signer at that slot index. This is an unauthenticated cross-contract write to StackerDB state: the ack for the write is set `accepted: true`, the chunk is persisted via `insert_chunk`, and it is also re-broadcast to the rest of the network via `node.set_relay_message(StacksMessageType::StackerDBPushChunk(...))`, causing network-wide propagation of a chunk stored under a `smart_contract_id` for which it was never actually authorized. This matches the "unauthenticated/unauthorized write to state or StackerDB, network-wide propagation of forged data" Critical category — though note the attacker cannot choose arbitrary *new* data (they can only replay an existing signed chunk, not forge new content), so the practical exploitation is a replay/cross-posting rather than fully free-form forgery.

### Likelihood Explanation
Exploitation requires: (1) at least two StackerDB replicas configured on the target node, (2) an overlapping slot-owner assignment between them (same address at same `slot_id` in both), and (3) contract B's stored version for that slot to be behind the `slot_version` being replayed and within `max_writes`. Whether such owner-set overlaps occur in practice (e.g. reused signer sets across StackerDB configs such as the signers' DBs across different reward cycles/contracts) depends on deployment/configuration, which was not fully verifiable from the indexed code alone — the actual `.signer-*` contract configurations and whether Stacks' production StackerDB configs guarantee distinct owner sets per contract were not available to confirm or refute in this pass. The mechanical vulnerability (digest omitting contract id) is confirmed in code; the network-wide practical severity depends on this configuration overlap, which should be verified against the concrete StackerDB configs deployed for signers/miners.

### Recommendation
Bind `smart_contract_id` (or an equivalent chain/contract-scoped domain separator) into `SlotMetadata::auth_digest`, and require callers of `sign`/`verify` to supply it. Update `StackerDBTx::try_replace_chunk` and the `sign` API surface (`StackerDBChunkData::sign`) to thread the contract identifier through, and bump the wire format / add a migration if backward compatibility with already-deployed signed chunks is a concern.

### Proof of Concept
Rust test plan (in `stackslib/src/net/stackerdb/tests/db.rs` or similar):
1. Create two StackerDB tables in `StackerDBs::connect_memory()`: contract A and contract B, each with `create_stackerdb` assigning the same `StacksAddress` (from a test private key) to `slot_id = 0`.
2. Construct a `StackerDBChunkData { slot_id: 0, slot_version: 1, data: b"hello".to_vec(), .. }`, call `.sign(&privkey)` — this signs only over `(slot_id, slot_version, data_hash)`.
3. Call `tx.try_replace_chunk(&contract_a_id, &chunk.get_slot_metadata(), &chunk.data)` — expect `Ok(())`.
4. Without any additional signing, call `tx.try_replace_chunk(&contract_b_id, &chunk.get_slot_metadata(), &chunk.data)` using the identical `SlotMetadata`/signature — assert this **also** returns `Ok(())` (demonstrating the cross-contract replay) instead of `Err(NetError::BadSlotSigner(..))`.
5. This confirms the digest/signature does not bind to the target contract, letting a chunk signed and authorized only for contract A be accepted verbatim under contract B.

    /// Get the digest to sign that authenticates this chunk data and metadata
    fn auth_digest(&self) -> Sha512Trunc256Sum {
        let mut hasher = Sha512_256::new();
        hasher.update(self.slot_id.to_be_bytes());
        hasher.update(self.slot_version.to_be_bytes());
        hasher.update(self.data_hash.0);
        Sha512Trunc256Sum::from_hasher(hasher)
    }

    pub fn verify(&self, principal: &StacksAddress) -> Result<bool, Error> {
        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )
        .map_err(|ve| Error::VerifyingError(ve.to_string()))?;

        let pubkh = Hash160::from_node_public_key(&pubk);
        Ok(pubkh == *principal.bytes())
    }
