### Title
Permanent DoS of reward distribution and token mint/burn hooks once `block.timestamp` exceeds `uint32.max` - (File: contracts/RewardsDistributor.sol)

### Summary
`RewardsDistributor._calculateTokenIndex` stores the last-update time in a `uint32 timestamp` field and updates it via `block.timestamp.toUint32()`. OpenZeppelin `SafeCast.toUint32` reverts when the input exceeds `type(uint32).max` (i.e., after 7 Feb 2106). From that point every call path that refreshes a token index — `claimRewards`, `updateBeforeMintOrBurn`, `updateBeforeTransfer`, and `syncTokenSpeed` — reverts permanently, freezing all unclaimed rewards and bricking `DepositToken`/`DebtToken` mint, burn, and transfer flows that hook the distributor. This is the same bug class as the DODO `_twapUpdate` finding: a `uint32` timestamp normalization that works today but permanently DoSes the protocol once `block.timestamp` crosses `2**32`.

### Finding Description
`TokenState.timestamp` is `uint32` (offset 28 of slot 0, per the storage layout in `deployments/mainnet/RewardsDistributor.json`). Every refresh path funnels into `_calculateTokenIndex`, which calls `block.timestamp.toUint32()` at `contracts/RewardsDistributor.sol:208` and `:210`, and `_updateTokenSpeed` does the same at `:298` and `:302`. `SafeCast.toUint32` reverts on overflow (`contracts/dependencies/openzeppelin/utils/math/SafeCast.sol`), so once `block.timestamp > 4294967295`:

- `claimRewards(...)` → `_updateTokenIndex` → revert: unclaimed reward balances in the distributor are frozen.
- `updateBeforeMintOrBurn(token, account)` (permissionless, `RewardsDistributor.sol:175`) is invoked by `DepositToken`/`DebtToken` on every mint/burn → those operations revert for any token whose `tokenStates[token].index > 0` and `tokenSpeeds[token] > 0`.
- `updateBeforeTransfer` (`:186`) → `DepositToken`/`DebtToken` transfers revert.
- `syncTokenSpeed` (`:333`) → `_updateTokenSpeed` → revert.

Unlike the DODO case, no `unchecked` wrap occurs here — `SafeCast` reverts outright, so the DoS is unconditional for any reward token with a nonzero speed.

### Impact Explanation
Permanent freezing of unclaimed yield (all accrued reward tokens remain locked in `RewardsDistributor`) and permanent DoS of deposit/debt token mint, burn, and transfer for any pool with an active reward speed. Matches the original finding's impact: liveness of core protocol functions blocked solely by the passage of time, not by any attacker action or privileged role.

### Likelihood Explanation
Certain to trigger on a fixed date (Unix timestamp `4294967296`, ~2106), identical in nature to the accepted DODO issue which was judged High despite the same time horizon. No attacker action, privileged role, or governance choice is required; the revert is deterministic given the deployed `uint32` storage layout and the `SafeCast` guard.

### Recommendation
Store timestamps as `uint64`/`uint256` in `TokenState`, or perform the cast with explicit truncation semantics (`uint32(block.timestamp % 2**32)` inside `unchecked`) and compute deltas in `unchecked` arithmetic so the wrap-around is handled correctly instead of reverting. Apply the same fix to the timestamp writes in `_updateTokenSpeed`.

### Proof of Concept
Hardhat sketch — fork mainnet, warp time past `type(uint32).max`, then any index refresh reverts:

```ts
import {time} from '@nomicfoundation/hardhat-network-helpers'
import {expect} from 'chai'

it('reverts after uint32 timestamp overflow', async () => {
  // rewardsDistributor has a reward token configured with speed > 0
  await time.increaseTo(2n ** 32n + 1n) // block.timestamp > type(uint32).max

  // Any path that touches _updateTokenIndex reverts via SafeCast.toUint32
  await expect(rewardsDistributor.claimRewards(alice.address, [depositToken.address]))
    .to.be.revertedWith("SafeCast: value doesn't fit in 32 bits")

  // DepositToken mint path is bricked because it calls updateBeforeMintOrBurn
  await expect(depositToken.mint(alice.address, parseEther('1'))).to.be.reverted
})
```

The revert originates at `RewardsDistributor.sol:208` (`_newTimestamp = block.timestamp.toUint32()`), reached through `claimRewards → _updateTokenIndex → _calculateTokenIndex`.
