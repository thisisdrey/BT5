### Title
Non-atomic two-phase reference commit in `FetchRemote` permanently applies pruned-ref deletions even when the paired reference update / object migration subsequently fails - (File: internal/gitaly/service/repository/fetch_remote.go)

### Summary
`fetchRemoteAtomic` splits the reference changes coming from a fetch into two separate `updateref.Updater` transactions — `prunedUpdater` (deletions needed to avoid F/D conflicts) and `refUpdater` (all other ref creations/updates) — and commits them sequentially rather than atomically. `prunedUpdater.Commit()` is called and durably applied to the repository *before* `refUpdater.Prepare()`, `quarantineDir.Migrate()`, and `refUpdater.Commit()` run. If any of these later steps fail, the RPC returns an error, but the pruned reference deletions that were already committed are not rolled back, leaving the repository in a partially-applied, inconsistent state that the caller has no way to detect or recover from through the same RPC.

### Finding Description
In `fetchRemoteAtomic` [1](#0-0) , ref updates parsed from `git fetch --dry-run --porcelain` output are routed into two independent reference transactions to avoid file/directory conflicts:

```go
prunedUpdater, err := updateref.New(ctx, quarantineRepo)
...
refUpdater, err := updateref.New(ctx, quarantineRepo)
```

The two transactions are then committed in sequence, not atomically: [2](#0-1) 

```go
if err := prunedUpdater.Prepare(); err != nil { ... }
if err := prunedUpdater.Commit(); err != nil { ... }   // <-- durably applied here

if err := refUpdater.Prepare(); err != nil { ... }
if err := quarantineDir.Migrate(ctx); err != nil { ... }
if err := refUpdater.Commit(); err != nil { ... }      // <-- may fail AFTER prune already committed
```

Once `prunedUpdater.Commit()` succeeds, the underlying `git update-ref` process transitions to `stateIdle` and the deletions are permanently applied to the on-disk refs backend (see `Commit()` in `internal/git/updateref/updateref.go`, lines 438-453, which finalizes state without any subsequent rollback path). If `refUpdater.Prepare()` fails (e.g. due to a lock conflict), `quarantineDir.Migrate()` fails (e.g. I/O error moving quarantined objects), or `refUpdater.Commit()` fails, the function returns an error to the client — but the already-committed pruned-ref deletions are never undone. The deferred `Close()` calls on both updaters only cancel *unfinished* transactions; a transaction that has already been `Commit()`-ted cannot be reverted by `Close()`.

This is the same root-cause pattern as the reported `Bet::cancel` bug: two logically-paired operations that must both succeed or both fail are instead executed as two independently-committed steps, so a failure partway through leaves one side's effect permanently applied while the other side's intended effect (new refs, migrated objects) is dropped.

### Impact Explanation
`FetchRemote` is a mutator RPC used for repository mirroring, where the remote URL and the fetched ref advertisement are attacker-influenced input (a user can configure a pull mirror pointing to a URL they control, or an already-configured mirror remote can be compromised/misbehave). A remote that advertises a fetch response causing pruned-ref deletions to be queued, followed by a condition that makes `refUpdater.Prepare()`/`Migrate()`/`Commit()` fail (e.g., a subsequent F/D conflict, a malformed/oversized object causing migration failure, or exhausting a lock), will cause the target repository to have its old branches/tags permanently deleted (pruned) while the corresponding new state from the fetch is never applied and the fetched objects are discarded (quarantine cleanup runs regardless via `defer quarantineCleanup()`). The net effect is silent, unrecoverable data loss/corruption of the repository's reference state, which is only reachable through a supposedly-safe RPC path and cannot be repaired by retrying `FetchRemote` (the pruned refs no longer exist to be "pruned again", and there's no guarantee the mirror source will re-advertise the exact same intermediate state).

### Likelihood Explanation
Triggering requires an ordinary user-configured pull mirror pointing at a remote that can influence the ordering/content of the fetch response, plus a failure in the second phase (a lock contention, an I/O failure during quarantine migration, or a legitimate F/D conflict in the "other" ref set). These conditions are plausible in production for large or misbehaving mirrors and can also occur incidentally due to concurrency (e.g., a concurrent write racing for the same lock during `refUpdater.Prepare()`), making this reachable without any privileged access — the RPC is a standard part of normal repository mirroring flows.

### Recommendation
Make the pruned-ref deletion and the remaining reference update atomic with respect to failure: either
1. Defer `prunedUpdater.Commit()` until after `refUpdater.Prepare()` and `quarantineDir.Migrate()` have both succeeded, committing both updaters back-to-back only once success of the remaining steps is guaranteed, or
2. If a true single git-update-ref transaction supporting mixed prune+update semantics isn't feasible, add compensating logic that re-creates the pruned references (from their known old OIDs) if the subsequent `refUpdater` phase fails, so that the repository state is restored to what it was before `fetchRemoteAtomic` began.

Either way, the function must not return an error to the caller while leaving one of the two transactions permanently applied and the other silently discarded.

### Proof of Concept
1. Configure a pull mirror for repository `R` pointing to an attacker/test-controlled remote `M`.
2. Craft `M`'s ref advertisement so that a `git fetch --prune --dry-run --porcelain` against it reports at least one pruned reference (e.g. delete `refs/heads/foo/bar` on `M` while `R` still has it) alongside a normal ref update that will trigger a failure during `refUpdater.Prepare()`/`Commit()` (e.g., a reference lock held by a concurrent operation on `R`, or an F/D conflict introduced by another concurrent ref update).
3. Invoke `FetchRemote` against `R`.
4. Observe: `prunedUpdater.Commit()` succeeds and `refs/heads/foo/bar` is deleted from `R`; then `refUpdater.Prepare()`/`Commit()` fails and `FetchRemote` returns an error.
5. Inspect `R`: the pruned reference remains deleted, but no new refs/objects from `M` were applied, leaving `R` in a state that never existed on `M` nor matches its prior local state, with no automatic recovery.

	// A repository cannot contain references with F/D (file/directory) conflicts (i.e.
	// `refs/heads/foo` and `refs/heads/foo/bar`). If fetching from the remote repository
	// results in an F/D conflict, the reference update fails. In some cases a conflicting
	// reference may exist locally that does not exist on the remote. In this scenario, if
	// outdated references are first pruned locally, the F/D conflict can be avoided. When
	// `git-fetch(1)` is performed with the `--prune` and `--dry-run` flags, the pruned
	// references are also included in the output without performing any actual reference
	// updates. Bulk atomic reference updates performed by `git-update-ref(1)` do not support
	// F/D conflicts even if the conflicted reference is being pruned. Therefore, pruned
	// references must be updated first in a separate transaction. To accommodate this, two
	// different instances of `updateref.Updater` are used to keep the transactions separate.
	prunedUpdater, err := updateref.New(ctx, quarantineRepo)
	if err != nil {
		return false, false, fmt.Errorf("spawning pruned updater: %w", err)
	}
	defer func() {
		if err := prunedUpdater.Close(); err != nil && returnedErr == nil {
			returnedErr = fmt.Errorf("cancel pruned updater: %w", err)
		}
	}()

	// All other reference updates can be queued as part of the same transaction.
	refUpdater, err := updateref.New(ctx, quarantineRepo)
	if err != nil {
		return false, false, fmt.Errorf("spawning ref updater: %w", err)
	}
	defer func() {
		if err := refUpdater.Close(); err != nil && returnedErr == nil {
			returnedErr = fmt.Errorf("cancel ref updater: %w", err)
		}
	}()
