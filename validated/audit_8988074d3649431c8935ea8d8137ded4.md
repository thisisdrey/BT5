### Title
`ValidateMultiSign`/`BatchValidateSign` TVM precompiles let an off-chain multisig approval be replayed across unrelated smart contracts because the signed hash omits the consuming contract's identity - ([File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java])

### Summary
The `ValidateMultiSign` and `BatchValidateSign` precompiled contracts, reachable by any smart contract via `CALL`, verify an off-chain ECDSA signature against a hash that binds only to the target account address, a `permissionId`, and caller-supplied `data`. Nothing in the hash construction binds the signature to the specific consuming contract ("platform") that is meant to act on it. A signature a user produces for one dApp's meta-transaction (e.g. an approval for dApp A) can therefore be replayed verbatim against a different dApp B that independently invokes the same precompile with the same `(address, permissionId, data)` triple, exactly mirroring the Futureswap `instantWithdraw` report where the signed struct lacked any Futureswap-specific (`Registry`) binding.

### Finding Description
`ValidateMultiSign.execute` computes the message hash as: [1](#0-0) 
`combine = address || permissionId || data`, then `hash = Sha256Hash(combine)`. The recovered signer addresses are checked only against the on-chain `Permission` for `address`/`permissionId`: [2](#0-1) 

Nowhere in this hash is the identity of the calling contract (the "platform" consuming the approval) incorporated — unlike a transaction signature, which is bound to a specific `raw_data` (owner, contract type, parameters, expiration, ref block), this precompile intentionally exposes a generic "verify N-of-M signatures over arbitrary caller-chosen `data`" primitive. `BatchValidateSign` is even more generic: it takes an arbitrary externally-supplied `hash` and address list with zero structural binding at all: [3](#0-2) 

This is the same bug class as the Futureswap report: the signer's off-chain approval is only as domain-specific as the `data` blob the dApp developer chooses to encode into it. Because `address` and `permissionId` are the *account* being controlled (not the *contract* being authorized to act), two unrelated dApps that both build `data` the same way (e.g. `token || amount || nonce`, mirroring the exact Futureswap userMessage shape) will produce byte-identical `combine`/`hash` values for the same user intent. A signature the user issued and intended for dApp A's specific action can be captured and replayed by anyone against dApp B's contract, causing dApp B to treat it as a valid multisig approval and execute an action the user only authorized for dApp A.

### Impact Explanation
If a wallet/relay/dApp pattern on TRON encodes off-chain multisig approvals in the generic `address+permissionId+data` shape recommended for use with `ValidateMultiSign` (this is the documented intended use of the precompile for account-abstraction-style meta-transactions), a signature can be replayed cross-contract to trigger an unauthorized account operation on a second, unrelated contract — the account holder never approved that specific contract's action, only the byte-identical data payload. This matches the "unauthorized account operation" impact bar: funds or account state can be manipulated by a party who possesses a signature meant for a different platform, without the signer's consent for that specific consuming contract.

### Likelihood Explanation
Exploitability depends on two independently-deployed contracts choosing the same `data` encoding scheme for the same account/permission — plausible given `ValidateMultiSign`'s design invites exactly this "meta-transaction/relayer" pattern across many DeFi contracts on TRON, and its documented ABI encourages minimal, generic payloads. This requires no special privilege: any transaction broadcaster can capture a signature and replay it into any contract's `CALL` to the precompile with the same account/permission/data triple.

### Recommendation
Document (and where feasible, enforce at the precompile level) that any `data` payload consumed via `ValidateMultiSign`/`BatchValidateSign` for authorization purposes must include a caller-specific domain separator — e.g., the invoking contract's address (`msg.sender`/`ORIGIN`/contract self address) or a documented `chainId`/protocol identifier — inside the hashed payload before signing, analogous to how the Futureswap fix added the `Registry` contract address to the signed struct. Consider exposing an opcode/precompile variant that automatically mixes in the calling contract address to the hash so dApp developers cannot omit this binding by mistake.

### Proof of Concept
1. dApp A and dApp B both implement an off-chain-authorized withdrawal using `ValidateMultiSign`, encoding `data = abi.encode(token, amount, nonce)` for account `Acc` with `permissionId = P`.
2. User signs `hash = Sha256(Acc || P || data)` intending to authorize dApp A's withdrawal.
3. Attacker observes the signature (e.g., from dApp A's mempool/API) and submits it as the multisig proof to dApp B's contract, which independently calls the `ValidateMultiSign` precompile with the identical `(Acc, P, data)`.
4. `PrecompiledContracts.ValidateMultiSign.execute` recomputes the identical hash, recovers the same signer, finds sufficient weight in `Acc`'s permission, and returns success — authorizing dApp B's action using a signature the user never intended for dApp B. [4](#0-3)
