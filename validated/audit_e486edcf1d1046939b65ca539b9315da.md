### Title
Attached deposit is silently dropped (never refunded) when an intermediate wallet-contract callback fails - (File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs)

### Summary
`WalletContract::rlp_execute` tracks any deposit attached by an external (non-self) predecessor in a `CallerDeposit` struct, explicitly for the purpose of "refund[ing] the caller's deposit if the cross-contract call fails." [1](#0-0) . However, that refund logic is implemented only in the final `rlp_execute_callback`, not in the two intermediate callbacks (`address_check_callback`, `nep_141_storage_balance_callback`) that also receive and forward `caller_deposit`. This is the same failure-handling asymmetry as the reported Solidity bug class: a subset of "callback" outcomes (genuine external-call failure / malformed response) is silently swallowed without executing the compensating logic that other branches of the same mechanism perform, causing user funds to be permanently stuck in the contract.

### Finding Description
`CallerDeposit::new` captures `context.attached_deposit` whenever the predecessor of `rlp_execute` differs from the wallet's own account (i.e., a relayer attaches NEAR on behalf of the eth-implicit account owner) [2](#0-1) .

For two `TransactionKind`s, execution goes through an intermediate cross-contract call before reaching `rlp_execute_callback`:
- `EOABaseTokenTransfer` with `address_check` first calls the address registrar, then routes through `address_check_callback` [3](#0-2) .
- `ERC20Transfer` first calls `storage_balance_of` on the token, then routes through `nep_141_storage_balance_callback` [4](#0-3) .

In `address_check_callback`, when the registrar call fails (`PromiseResult::Failed`) or returns malformed data (deserialize `Err`), the function returns an `ExecuteResponse::success = false` and simply drops `caller_deposit` — it is never refunded: [5](#0-4) 

The same pattern occurs in `nep_141_storage_balance_callback`'s failure/deserialize-error arms: [6](#0-5) 

By contrast, `rlp_execute_callback` — the *only* place that actually implements the refund — explicitly sends the deposit back to `caller_deposit.account_id` when its own promise fails: [7](#0-6) 

Because `has_in_flight_tx` is simply reset to `false` in the early-failure branches [8](#0-7) , [9](#0-8) , execution simply completes and the previously attached deposit remains merged into the wallet contract account's balance with no code path that later re-attributes or returns it to the relayer/caller who attached it.

### Impact Explanation
Whenever the address-registrar lookup or the NEP-141 `storage_balance_of` call fails or returns unparsable data, the relayer's (or other external caller's) attached NEAR deposit is permanently absorbed into the eth-implicit wallet contract's own account balance instead of being refunded, even though the refund mechanism (`CallerDeposit`) exists precisely for this purpose. This is a genuine, concrete freezing/loss of user funds analogous to the reported bug's "genuine external call failures are silently swallowed in the empty catch" — here, failure paths bypass the compensating refund logic that exists in the symmetric case.

### Likelihood Explanation
This is reachable by an ordinary unprivileged relayer/caller: any `EOABaseTokenTransfer` with `address_check` or `ERC20Transfer` submitted through `rlp_execute` with a nonzero attached deposit will trigger the vulnerable code path if the registrar or token contract's `storage_balance_of` call fails or returns a response the wallet contract cannot deserialize (e.g., the token contract is paused, out of gas, or returns an unexpected/incompatible JSON shape). No special privileges or malicious validator/node behavior are required — only a normal cross-contract call failure, which is a routine and expected occurrence.

### Recommendation
In `address_check_callback` and `nep_141_storage_balance_callback`, mirror the refund logic used in `rlp_execute_callback`: when the callback observes `PromiseResult::Failed` or a deserialization error, issue a transfer of `caller_deposit`'s amount back to `caller_deposit.account_id` before returning the failed `ExecuteResponse`, exactly as is already done in the terminal callback.

### Proof of Concept
1. A relayer calls `rlp_execute` for an `EOABaseTokenTransfer` with `address_check: Some(address)` and attaches a nonzero NEAR deposit (fee) for the relayer, with `predecessor_account_id != current_account_id`, so `CallerDeposit::new` returns `Some(...)`.
2. `inner_rlp_execute` schedules a call to the address registrar's `lookup`, chained `.then(ext.address_check_callback(target, action, caller_deposit))`.
3. The address registrar call fails (e.g., registrar contract is temporarily unreachable / out of gas) so `env::promise_result(0)` returns `PromiseResult::Failed` inside `address_check_callback`.
4. `address_check_callback` returns `ExecuteResponse { success: false, ... }` without ever transferring `caller_deposit.yocto_near` back to `caller_deposit.account_id`.
5. `has_in_flight_tx` is reset to `false`, allowing subsequent unrelated transactions; the deposit remains permanently merged into the wallet contract's balance with no future refund path.

/// A data type to keep track of the deposit given by an external caller.
/// This allows us to refund the caller's deposit if the cross-contract call fails.
#[derive(Debug, PartialEq, Eq, Clone, serde::Serialize, serde::Deserialize)]
pub struct CallerDeposit {
    pub account_id: AccountId,
    pub yocto_near: NonZeroU128,
}

impl CallerDeposit {
    pub fn new(context: &ExecutionContext) -> Option<Self> {
        // Only track for external (non-self) callers
        if context.current_account_id == context.predecessor_account_id {
            return None;
        }

        NonZeroU128::new(context.attached_deposit.as_yoctonear()).map(|yocto_near| Self {
            account_id: context.predecessor_account_id.clone(),
            yocto_near,
        })
    }
}
