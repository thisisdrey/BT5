### Title
Plaintext GOAUTH credentials leaked into debug log output via unsanitized `git credential fill` error message - (File: src/cmd/go/internal/auth/gitauth.go)

### Summary
`runGitAuth` embeds the raw, unsanitized output of the `git credential fill` command directly into a formatted error when the command exits non‑zero. That combined output is exactly the same payload that `parseGitAuth` later extracts `username`/`password` from on the success path, so when the helper writes credential data to stdout/stderr but the process still returns a non‑zero status (a normal external‑tool failure mode, e.g. a credential helper warning, lock error, or transient failure written before the tool exits with an error), the plaintext password ends up embedded in the returned `error`. This mirrors CVE-2017-1000157's pattern of writing plaintext secrets to a diagnostic/log channel when verbose logging is enabled.

### Finding Description
`go get`/`go mod tidy` (attacker reachable via a module path that returns a 4xx and triggers re-authentication) calls `auth.AddCredentials` → `runGoAuth` → for the `git` GOAUTH method, `runGitAuth` in [1](#0-0) . `cmd.CombinedOutput()` captures both stdout and stderr of `git credential fill`; on non-zero exit, the entire captured buffer `out` — which by protocol can legitimately contain a `password=...` line, the very data `parseGitAuth` later parses at [2](#0-1)  — is interpolated verbatim into the returned error via `%s`. This error is propagated to `cmdErrs` in `runGoAuth`, and when `cfg.BuildX` is set and no credential is ultimately found for the URL, it is written to process stderr unredacted: [3](#0-2) . Unlike the HTTP fetch path, which explicitly redacts passwords from URLs before logging (`url.Redacted()` in [4](#0-3)  and `stripPassword` in [5](#0-4) ), there is no equivalent scrubbing applied to the raw `git credential fill` output before it is embedded in the error and logged.

### Impact Explanation
If this error path is exercised while `-x`/`GOFLAGS=-x` build tracing is enabled (a supported, ordinary developer/CI workflow when diagnosing GOAUTH failures, as documented in `HelpGoAuth`, [6](#0-5) ), a plaintext credential from the user's git credential store can be written to the build's stderr trace, which is commonly captured by CI systems, shared logs, or terminal scrollback. This is a secret-disclosure primitive analogous to the CVE's plaintext-password-in-log issue, but scoped to the local credential-fill diagnostic path rather than a remote attacker directly forcing disclosure.

### Likelihood Explanation
The victim workflow is ordinary: running `go get`/`go mod tidy` against a module path requiring HTTPS auth with `GOAUTH=git <dir>` configured, optionally with `-x` for troubleshooting (also exercised by the `goauth_git.txt` script test, [7](#0-6) ). The failure/leak depends on the local `git credential` helper producing partial credential output before signaling a non-zero exit — a real but helper-dependent condition, not fully attacker-controlled, which weakens (but does not eliminate) reachability from an external, unprivileged actor.

### Recommendation
Do not interpolate raw `git credential fill` output into error messages or logs. Parse and scrub the output (reusing `parseGitAuth`) before constructing the error, or redact any `password=` fields, so that failure diagnostics never contain plaintext secrets, consistent with the redaction already applied to URLs in `cmd/go/internal/web/http.go` and `net/http/client.go`.

### Proof of Concept
```go
package auth

import (
	"errors"
	"fmt"
	"strings"
	"testing"
)

// Simulates the vulnerable formatting in runGitAuth when
// 'git credential fill' exits non-zero after already emitting
// a password line (e.g. a helper warning followed by failure).
func TestGitCredentialFillErrorLeaksPassword(t *testing.T) {
	url := "https://example.com/repo"
	out := []byte("protocol=https\nhost=example.com\nusername=alice\npassword=SuperSecret123\n")
	err := errors.New("exit status 1")

	got := fmt.Errorf("'git credential fill' failed (url=%s): %w\n%s", url, err, out)

	if strings.Contains(got.Error(), "SuperSecret123") {
		t.Fatalf("plaintext password leaked into error/log output: %v", got)
	}
}
```
Expected (buggy) result: the test fails because `got.Error()` contains `SuperSecret123`, demonstrating that the plaintext credential from `git credential fill` output is embedded verbatim in the error that can subsequently be written to stderr via `log.Printf` in `runGoAuth` under `-x` mode.
