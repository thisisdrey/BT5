Audit Report

## Title
Unbounded spot-price AMM conversion in `SwapFirstAssetTrader::buy_weight` allows underpriced XCM weight purchase - (File: `cumulus/primitives/utility/src/lib.rs`)

## Summary
`SwapFirstAssetTrader::buy_weight` converts a caller-supplied fee asset into the runtime's `Target` fee asset by invoking `SwapCredit::swap_tokens_for_exact_tokens(vec![swap_asset, Target::get()], credit_in, fee)` [1](#0-0) , executing entirely at the live spot price of the corresponding `pallet-asset-conversion` pool. Although the trait bound on `SwapCredit` requires `QuotePrice` [2](#0-1) , `buy_weight` never calls any `quote_price_*` method to sanity-check the realized swap price, so an attacker who skews the pool's reserves via their own preceding transactions can obtain the fixed `fee` amount of `Target` for a fraction of its fair-value cost in the supplied asset.

## Finding Description
The swap is bounded only by `amount_in_max = credit_in.peek()`, i.e., however much the caller supplied, not by any independent price reference: `do_swap_credit_tokens_for_exact_tokens` computes `amount_in` from current reserves via `balance_path_from_amount_out` and rejects only if `amount_in > amount_in_max` [3](#0-2) . There is no mechanism inside `buy_weight` to reject a swap whose realized price is worse than a fair/expected quote — the only check is against the caller's own supplied payment amount.

An unprivileged attacker can, using only their own ordinary extrinsics (e.g., `swap_exact_tokens_for_tokens` or `add_liquidity`/`remove_liquidity`), skew the `swap_asset`/`Target` pool's reserves within the same block so that the spot price temporarily favors converting a small amount of `swap_asset` into a disproportionately large amount of `Target`. Since the `fee` demanded by `buy_weight` for a given `weight` is a fixed absolute amount of `Target` (`WeightToFee::weight_to_fee(&weight)`) rather than scaled to the true value of `swap_asset`, skewing the pool directly reduces the real cost of acquiring that fixed `Target` amount. The attacker then submits an XCM message paying the `BuyExecution` fee in `swap_asset` sized just enough to satisfy the skewed-price swap, obtaining large `weight` allowance for a fraction of the intended cost, and can subsequently let the pool renormalize (via their own reverse trade or natural arbitrage).

## Impact Explanation
This matches the accepted "public underpriced work that degrades block production" impact category: any unprivileged party can pay a manipulated, artificially small amount of a chosen fee asset to obtain disproportionately large XCM execution weight allowance, letting them execute heavy `Transact`/`ExchangeAsset`/`DepositAsset` programs cheaply. `SwapFirstAssetTrader` is wired into live runtimes as an XCM `WeightTrader` (`asset-hub-rococo`, `asset-hub-westend`, `penpal`, `staking-async` parachain), so this can be exploited against production/testnet configurations that use this trader with any pool. Since the swap in `buy_weight` only checks the caller's own supplied amount, not an oracle/fair-price bound, there is no existing guard against this.

## Likelihood Explanation
Exploitability scales inversely with pool liquidity depth relative to attacker capital and requires the manipulation and the `buy_weight` execution to land within the same block or narrow window before arbitrage restores the price. This requires no validator, collator, relayer, or governance compromise — only self-directed, ordinary user-level transactions (pool swaps/liquidity operations plus an XCM message), all fully controllable by the attacker's own sequencing. Thinly-traded `swap_asset`/`Target` pairs (common for many foreign-asset pairs on AssetHub) make the attack both cheap and repeatable.

## Recommendation
Bound the swap in `buy_weight` using the `QuotePrice` trait already required on `SwapCredit` — e.g., obtain a reference quote via `quote_price_exact_tokens_for_tokens`/`quote_price_tokens_for_exact_tokens` before or after the swap and reject execution if the realized `amount_in` deviates beyond a configured tolerance from that reference, rather than relying solely on the caller-supplied `credit_in.peek()` as the only bound.

## Proof of Concept
1. Attacker holds `swap_asset` X and sufficient capital to briefly skew the `X`/`Target` pool (e.g., via `pallet_asset_conversion::swap_exact_tokens_for_tokens` sending `Target` into the pool for `X` out, which lowers the spot price of `Target` in terms of `X`).
2. In the same block, attacker submits an XCM message with `BuyExecution { fees: (X, small_amount), weight_limit: large_weight }`.
3. `SwapFirstAssetTrader::buy_weight` invokes `SwapCredit::swap_tokens_for_exact_tokens` with `credit_in = small_amount`; under skewed reserves this succeeds because `amount_in <= credit_in.peek()` holds for the fixed `fee` [4](#0-3) .
4. Attacker's XCM program executes `large_weight` worth of instructions for a fraction of the intended fee cost; attacker reverses the pool skew afterward to recover most of the manipulation capital.
