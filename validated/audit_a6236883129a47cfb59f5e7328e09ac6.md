### Title
StackerDB reconfiguration skips revocation when a contract legitimately reports zero signers, letting removed signers keep write access - (File: `stackslib/src/net/stackerdb/mod.rs`)

### Summary
`StackerDBs::create_or_reconfigure_stackerdbs` decides whether to apply a freshly-computed `StackerDBConfig` (signer list/slot ownership) by comparing it to the previously stored config. The comparison contains a guard that unconditionally skips reconfiguration whenever the newly computed signer list is empty, even when that empty list is the *correct, current* result of evaluating the controlling contract. This means that once a StackerDB's signer set legitimately drops to zero members (e.g. a `.signers-N` StackerDB when a reward cycle has no PoX participation), the node never revokes the previous cycle's signers from the slot-ownership table, and those signers retain the ability to write (and have relayed) chunks indefinitely.

### Finding Description
`StackerDBConfig::from_smart_contract` evaluates the `stackerdb-get-signer-slots` function of the controlling contract every reconfiguration pass: [1](#0-0) 

For the `.signers-0`/`.signers-1` StackerDBs, `signers.clar`'s backing data (`stackerdb-signer-slots-0/1`) is populated by `update_signers` in the chain state, which explicitly sets the signer list to an **empty vector** whenever the reward cycle `has_participation == false`: [2](#0-1) 

Back in the P2P layer, `create_or_reconfigure_stackerdbs` computes `new_config` from that same contract state and then applies it only under this condition: [3](#0-2) 

Specifically:
```
} else if (new_config != stackerdb_config && !new_config.signers.is_empty())
    || (new_config == stackerdb_config
        && new_config.signers.len() != self.get_slot_versions(&stackerdb_contract_id)?.len())
{
    ... self.reconfigure_stackerdb(...) ...
}
```
If the contract legitimately returns an **empty** signer list (a real, valid state change, not an error), the first disjunct is false (`!new_config.signers.is_empty()` is false) and the second disjunct is false (`new_config != stackerdb_config` in this scenario, since the signer list actually changed from N members to 0), so `reconfigure_stackerdb` is never called. The on-disk `chunks`/slot-ownership table (`slot_validation.signer`) is left untouched, still pointing at the *previous* cycle's signer addresses.

`reconfigure_stackerdb` is the only code path that updates a slot's owning signer: [4](#0-3) 

Because it is skipped, `get_slot_signer()` continues to return the stale (should-be-revoked) signer's address for every slot. This address is exactly what `validate_received_chunk` uses to authenticate incoming/relayed chunk pushes and what `poststackerdbchunk` HTTP handling uses to authenticate `PUT`-chunk requests: [5](#0-4) 

The comment attached to the guard reveals the (unrelated) reason it was written this way — to avoid a regression from issue #5142 where a StackerDB could never *shrink* — but the fix over-corrected: it now also blocks legitimate shrink-to-zero events, which is the exact "no revoke" pattern from the report (a role, once granted, cannot be turned off through the normal, sanctioned update path).

### Impact Explanation
This breaks the equality "authorized signer (per current contract state) == signer trusted to write into the slot" — the node keeps trusting a stale, no-longer-authorized signer. A previously-valid signer (who already possesses their own private key — no secret of another party or of the node is required) can continue to:
- Successfully `PUT` new chunk versions to their old slot via `poststackerdbchunk`, which the server will accept because `BadSigner` checks resolve against the never-revoked `slot_validation.signer`.
- Have those pushed/relayed chunks accepted by `validate_received_chunk` on every other node in the network that independently computed the same (buggy) empty-signer-list-skip outcome, since the bug is deterministic given the same chain state, propagating forged/stale signer data network-wide.

This matches the "High/Critical" categories called out in scope: unauthenticated/unauthorized write to state (StackerDB), and network-wide propagation of forged data written by a party that should have been revoked.

### Likelihood Explanation
The trigger condition — a `.signers-N` StackerDB transitioning to zero signers because `has_participation` is false for a reward cycle — is a legitimate, naturally occurring chain-state condition (e.g., a reward cycle where PoX stacking participation is zero, which can occur on testnets/regtest or in edge conditions on mainnet), not a contrived error path. Every full node computes this same config deterministically from chain state, so all replicas of the affected StackerDB will independently fail to revoke in lock-step, making the stale signer's write acceptance and cross-node propagation reliable rather than probabilistic.

### Recommendation
Change the reconfiguration guard so that any content change to `new_config.signers` (including a legitimate transition to the empty set) triggers `reconfigure_stackerdb`, distinguishing "config failed to load and fell back to `noop()`" from "config successfully loaded and evaluates to zero signers." For example, only suppress reconfiguration on an explicit load error (already handled via `unwrap_or_else(... StackerDBConfig::noop())`), and otherwise always reconfigure when `new_config != stackerdb_config`, regardless of whether `new_config.signers` is empty. Retain the separate length-mismatch check for the #5142 shrink-recovery case, but don't let it gate out the legitimate-empty-signers path.

### Proof of Concept
1. Configure a StackerDB backed by `.signers-N` (or any custom contract implementing `stackerdb-trait`) such that in reward cycle `C` it has one or more signers (e.g., signer `S`) and non-empty `stackerdb-get-signer-slots`.
2. Let cycle `C+1` roll over such that `has_participation` becomes `false` (or otherwise cause the contract to legitimately report an empty signer-slot list), so `stackerdb-get-signer-slots` now returns `[]`.
3. On the next call to `create_or_reconfigure_stackerdbs`, observe (via logs/DB inspection) that `new_config.signers.is_empty()` is true, `new_config != stackerdb_config`, so `reconfigure_stackerdb` is never invoked and `slot_validation.signer` for the DB's slots still shows `S`.
4. From signer `S`'s node (using their own already-known private key), send a `PUT /v2/stackerdb/<contract>/chunks/<slot>/<version>` request signed by `S`. Confirm the request is accepted (`BadSigner` is not raised) even though `S` is no longer an authorized signer per the current contract state, and the resulting chunk is relayed to peers via `handle_unsolicited_StackerDBPushChunk`.

Note: I could not execute this against a live node within the scope of this analysis; the above traces the exact code paths (`stackslib/src/net/stackerdb/mod.rs:414-428`, `stackslib/src/net/stackerdb/db.rs:302-351`, `stackslib/src/chainstate/nakamoto/signer_set.rs:577-601`) that make this reachable, and the logic was confirmed by direct reading rather than dynamic testing.

    pub fn reconfigure_stackerdb(
        &self,
        smart_contract: &QualifiedContractIdentifier,
        slots: &[(StacksAddress, u32)],
    ) -> Result<(), net_error> {
        let stackerdb_id = self.get_stackerdb_id(smart_contract)?;
        let mut total_slots_read = 0u32;
        for (principal, slot_count) in slots.iter() {
            total_slots_read =
                total_slots_read
                    .checked_add(*slot_count)
                    .ok_or(net_error::OverflowError(
                        "Slot count exceeeds u32::MAX".to_string(),
                    ))?;
            let slots_before_principal = total_slots_read - slot_count;
            for cur_principal_slot in 0..*slot_count {
                let slot_id = slots_before_principal + cur_principal_slot;
                if let Some(existing_validation) =
                    self.get_slot_validation(smart_contract, slot_id)?
                {
                    // this slot already exists.
                    if existing_validation.signer == *principal {
                        // no change
                        continue;
                    }
                }

                debug!("Reset slot {} of {}", slot_id, smart_contract);

                // new slot, or existing slot with a different signer
                let qry = "INSERT OR REPLACE INTO chunks (stackerdb_id,signer,slot_id,version,write_time,data,data_hash,signature) VALUES (?1,?2,?3,?4,?5,?6,?7,?8)";
                let mut stmt = self.sql_tx.prepare(qry)?;
                let args = params![
                    stackerdb_id,
                    principal.to_string(),
                    slot_id,
                    NO_VERSION,
                    0,
                    vec![],
                    Sha512Trunc256Sum([0u8; 32]),
                    MessageSignature::empty(),
                ];

                stmt.execute(args)?;
            }
        }
        debug!("Shrink {} to {} slots", smart_contract, total_slots_read);
        self.shrink_stackerdb(stackerdb_id, total_slots_read)?;
        Ok(())
    }
