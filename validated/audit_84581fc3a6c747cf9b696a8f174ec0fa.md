[1](#0-0) 

For every integration-backed adapter (`KaminoPythPush`, `KaminoSwitchboardPull`, `DriftPythPull`, `DriftSwitchboardPull`, `SolendPythPull`, `SolendSwitchboardPull`, `JuplendPythPull`, `JuplendSwitchboardPull`, and the `Fixed*` variants), the secondary reserve/market account is loaded via `load_kamino_reserve`, `load_drift_spot_market`, `load_solend_reserve`, or `load_juplend_lending`, each of which strictly enforces `require_keys_eq!(*reserve_info.key, bank_config.oracle_keys[1], ...)` before use. [2](#0-1) 

Because both the "cache" price and the "live" price are computed from the same validated `OracleLoadContext` produced by a single call to `load_oracle_context_with_max_age` — with `adjusted_price_feed`, `cache_raw_price`, and `cache_multiplier` all derived from the *same* checked oracle and reserve/market accounts in that one invocation — there is no code path where the cached value is bound to a different price source than the live value. [3](#0-2) 

Attempting to pass a mismatched or "wrong" reserve/spot-market/lending account is explicitly rejected, as shown by the existing test asserting `JuplendLendingValidationFailed` for a substituted lending account. [4](#0-3) 

Since `check_primary_oracle_key` (and the analogous secondary-key checks) are applied identically and atomically for both the cache-refresh path and the live-price path — they are literally the same function call, not two independently-verified paths — there is no reachable way for an unprivileged caller to bind the cache to one price source while the live path uses another. The premise of divergent cached-vs-live pricing via cross-wired reserve/oracle accounts does not hold in this codebase.

        ))
