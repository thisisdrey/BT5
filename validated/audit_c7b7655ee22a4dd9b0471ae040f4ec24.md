### Title
Out-of-bounds read on attacker-controlled JAR local file header offset - (File: src/tools/singlejar/input_jar.h)

### Summary
`singlejar` (Bazel's native JAR-merging tool used to build deploy jars / `_deploy.jar` outputs from a set of input JARs, including third-party jars pulled in as `java_import`/`http_jar` dependencies) parses ZIP/JAR structures by casting raw mapped-file bytes directly into packed C++ structs (`CDH`, `LH`) and following offsets contained in those structs, without validating every derived pointer against the mapped file bounds before dereferencing it.

### Finding Description
`InputJar::NextEntry` validates that the *next* Central Directory Header (`CDH`) pointer lies within the mapped file before dereferencing it: [1](#0-0) 

However, the Local Header pointer it hands back is computed by `InputJar::LocalHeader`, which performs pure pointer arithmetic from the *attacker-controlled* `local_header_offset` field stored in the CDH, with **no bounds check** against the memory-mapped file region: [2](#0-1) 

`MappedFile::address()` is just `mapped_start_ + offset` — it does not clamp or validate the result: [3](#0-2) 

The resulting pointer is immediately reinterpreted as an `LH*` and its packed fields (`file_name_length`, `extra_fields_length`, `compressed_file_size`, etc.) are read directly out of raw memory, e.g. in `OutputJar::AddJar`, which copies `lh->size()` and `jar_entry->compressed_file_size()` bytes starting at `jar_entry->local_header_offset()`: [4](#0-3) 

This is directly analogous to the reported `rgb` crate bug class: raw bytes from an untrusted source are reinterpreted as a typed struct (`LH`) and its fields are trusted to compute further pointers/lengths, without any invariant that the memory backing that struct is valid or in-bounds. A crafted CDH `local_header_offset` (or Zip64 64-bit `local_header_offset` extra field, computed the same unchecked way) that points before `mapped_start_` or past `mapped_end_` causes `LH::is()`, `LH::file_name_length()`, `LH::extra_fields_length()`, `LH::compressed_file_size()` to read out-of-bounds heap/mapped memory, and subsequent copy logic (`memcpy`/`WriteBytes`) can leak that out-of-bounds memory into the produced output jar or crash the process.

### Impact Explanation
`singlejar` runs as part of ordinary Java build actions (deploy jar creation, source jar merging) and consumes JAR files that can originate from external/third-party dependencies (e.g. jars fetched by `http_jar`/`http_archive`/Maven rules). A malicious jar with a doctored Central Directory (valid CDH-vs-mapped-file bounds check passes, but `local_header_offset` is bogus) reaches this unchecked code path. This is an out-of-bounds read (CWE-125/CWE-119 class) that can disclose adjacent process memory into a build output or cause a crash (denial of the build action), matching the "Critical" severity class of the analog (out-of-bounds memory access from attacker-supplied structured bytes).

### Likelihood Explanation
Likelihood is moderate: it requires that a build consumes a jar whose *bytes* are attacker-controlled (e.g., a jar served by a hostile/compromised mirror where `sha256`/`integrity` was not pinned, or a jar produced within an untrusted-branch CI dependency), and that jar must pass the CDH-in-bounds check in `NextEntry` (easy — attacker fully controls the CDH they craft) while carrying a bad `local_header_offset`. No credentials, sandbox escape, or local machine access are required beyond publishing the malicious jar content that Bazel's build graph pulls in.

### Recommendation
In `InputJar::LocalHeader` (and any other place a CDH-derived offset is converted to a pointer, e.g. Zip64 `local_header_offset()` resolution), validate the computed address with `mapped_file_.mapped(...)` (and that `address + sizeof(LH)` and `address + LH::size()` are also within bounds) before dereferencing, mirroring the existing check already performed in `NextEntry` for `CDH`. Reject/diagnose (`diag_errx`) malformed entries the same way corrupt CDH records are rejected today.

### Proof of Concept
A concrete PoC would extend the existing native test infrastructure that already exercises `InputJar`/`OutputJar` against crafted archives (e.g. `src/tools/singlejar/input_jar_scan_entries_test.h`, `src/tools/singlejar/output_jar_simple_test.cc`) by constructing a JAR whose Central Directory contains a valid, in-bounds `CDH` entry but with a forged `local_header_offset` (or Zip64 extra-field 64-bit offset) pointing outside the mapped file range (e.g., negative/huge value or pointing a few bytes before `mapped_start_`), then invoking `OutputJar::AddJar` (as `output_jar_simple_test.cc` already does via `CreateOutput`) and asserting the process performs a bounds-checked rejection (`diag_errx`) instead of dereferencing/copying out-of-bounds memory (verifiable under ASan, which would flag the heap/mmap OOB read). I could not fully verify at what exact offset value bound violations first manifest without running the actual binary/ASan, so exact malformed-offset magnitudes for a minimal reproduction were not empirically confirmed in this analysis — a background agent with build/test execution access would be needed to finalize a concrete JUnit/shell reproduction and confirm the crash/leak under sanitizers.
