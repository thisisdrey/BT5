### Title
Per-connection unstaked stream throttle scales linearly with connection count, allowing aggregate unstaked ingress far above the intended `MAX_UNSTAKED_TPS` - ([File: streamer/src/nonblocking/stream_throttle.rs])

### Summary
`StakedStreamLoadEMA::available_load_capacity_in_throttling_duration` enforces `MAX_UNSTAKED_TPS` (200 streams/sec) as a **per-connection** budget via each connection's own `ConnectionStreamCounter`, not as a cluster-wide/per-source aggregate. Since an unstaked client can open up to `max_unstaked_connections` (default `DEFAULT_MAX_UNSTAKED_CONNECTIONS = 2000`) simultaneous connections, each independently allowed `20 streams / 100ms`, the achievable aggregate unstaked stream rate scales with the number of open connections rather than being capped at 200 TPS total.

### Finding Description
`ConnectionStreamCounter` in `streamer/src/nonblocking/stream_throttle.rs` (lines 196-231) keeps `stream_count` and `last_throttling_instant` scoped to a single connection instance. `throttle_stream` (lines 233-271) only compares that connection's local `stream_count` against `max_streams_per_throttling_interval`, which for unstaked peers is computed in `StakedStreamLoadEMA::available_load_capacity_in_throttling_duration` (lines 167-188) as `self.max_unstaked_load_in_throttling_window`, a fixed constant derived from `MAX_UNSTAKED_TPS = 200` (lines 16-17, 64-68) — completely independent of how many other unstaked connections exist.

Each `ConnectionStreamCounter` is allocated per-connection inside `SwQos::cache_new_connection` / `ConnectionTable::try_add_connection` (`streamer/src/nonblocking/swqos.rs` lines 209-218), keyed by `ConnectionTableKey::new(remote_addr.ip(), pubkey)`. There is no shared/global counter aggregating stream consumption across all unstaked connections (or even across all connections from the same IP beyond the up-to-8 per-peer cap set by `DEFAULT_MAX_QUIC_CONNECTIONS_PER_UNSTAKED_PEER`). The global unstaked connection ceiling is only `max_unstaked_connections` (default 2000), enforced by `prune_unstaked_connection_table` (lines 241-256) purely as a *connection-count* limit, not a *stream-rate* limit.

Further compounding this, `StakedStreamLoadEMA::increment_load` (lines 160-165) only feeds `load_in_recent_interval` when `peer_type.is_staked()` is true — unstaked stream volume is never counted toward the EMA that governs adaptive staked throttling. So high unstaked throughput neither triggers additional cluster-wide backpressure nor is it capped anywhere beyond the fixed per-connection 20-per-100ms window.

Consequently, an attacker does not even need to precisely time stream opens at `STREAM_THROTTLING_INTERVAL` boundaries (the "race" framing in the question is not required): simply maintaining N parallel unstaked QUIC connections and sending 20 uni streams per 100ms on each yields an aggregate throughput of `N * 200` TPS, which for `N` approaching `max_unstaked_connections` (2000) can reach up to `400,000` streams/sec — nearing or exceeding the entire server-wide budget implied by `DEFAULT_MAX_STREAMS_PER_MS = 500` (500,000 pps). This directly defeats the design intent encoded in the constant name `MAX_UNSTAKED_TPS` and the comment "Max TPS allowed for unstaked connection" (which is ambiguous but the surrounding `EXPECTED_UNSTAKED_STREAMS_RATIO = 0.20` — used to reserve only 20% of total capacity for unstaked traffic in the staked budget calculation — clearly assumes unstaked aggregate consumption is bounded near 20% of total capacity, which per-connection enforcement does not guarantee).

### Impact Explanation
This is a QoS-evasion / rate-limit-bypass finding: an unstaked, unprivileged attacker can open many parallel connections (up to the `max_unstaked_connections` global cap, using distinct source IPs since per-IP connections are capped at `DEFAULT_MAX_QUIC_CONNECTIONS_PER_UNSTAKED_PEER = 8`) and drive stream/packet ingress far beyond what the per-cluster unstaked budget (`MAX_UNSTAKED_TPS`) is intended to allow. This can overwhelm downstream sigverify/banking stage capacity with unstaked traffic, starving legitimate staked traffic of its reserved throughput headroom and degrading validator ingest performance — a QoS evasion / resource-exhaustion class issue against the TPU ingress path.

### Likelihood Explanation
Feasible with only unprivileged network access: the attacker needs to establish up to a few hundred/thousand distinct QUIC connections (bounded by `max_unstaked_connections`, potentially requiring multiple source IPs due to the 8-connections-per-peer cap), which is a realistic precondition for a botnet-style or multi-homed attacker, and does not require any staked/privileged credentials, gossip participation, or config control. No precise timing synchronization is actually required — the constraint is purely "many concurrent connections," making this highly repeatable.

### Recommendation
Enforce unstaked stream throughput against a shared/global (or per-source-IP-aggregated) budget rather than a purely per-connection counter. For example, maintain a cluster-wide (or per-IP) atomic stream-budget shared across all `ConnectionStreamCounter` instances for unstaked peers inside `StakedStreamLoadEMA`, and have `available_load_capacity_in_throttling_duration` / `throttle_stream` consult and decrement that shared budget so that the aggregate unstaked TPS is capped near `MAX_UNSTAKED_TPS` regardless of how many unstaked connections are concurrently open. Additionally, incorporate unstaked load into the EMA/backpressure computation (`increment_load`) so that connection multiplication cannot be used to bypass the reserved capacity split between staked and unstaked traffic.

### Proof of Concept
Integration test plan (extends the existing `test_throttling_check_no_packet_drop` pattern in `streamer/src/nonblocking/quic.rs`):
```rust
#[tokio::test(flavor = "multi_thread")]
async fn test_aggregate_unstaked_throttle_bypass_via_many_connections() {
    // Spin up a QUIC server with SwQos + default unstaked config
    // (max_unstaked_connections = N, e.g. 50 for test scale).
    let n_connections = 50;
    let mut clients = Vec::new();
    for _ in 0..n_connections {
        clients.push(make_client_endpoint(&server_address, None).await);
    }

    let start = tokio::time::Instant::now();
    let streams_per_conn_per_interval = 20; // matches MAX_UNSTAKED_TPS window cap
    for conn in &clients {
        for i in 0..streams_per_conn_per_interval {
            let mut s = conn.open_uni().await.unwrap();
            s.write_all(format!("{i}").as_bytes()).await.unwrap();
            s.finish().unwrap();
        }
    }
    let elapsed = start.elapsed();

    // Collect accepted streams within the single throttling interval (~100ms).
    let mut received = 0;
    while received < n_connections * streams_per_conn_per_interval
        && start.elapsed() < Duration::from_millis(150)
    {
        if let Ok(batch) = receiver.try_recv() {
            received += batch.len();
        }
    }

    // Assert that aggregate accepted streams within one throttling window
    // exceed the intended cluster-wide unstaked budget
    // (MAX_UNSTAKED_TPS * STREAM_THROTTLING_INTERVAL_MS / 1000),
    // demonstrating the per-connection cap does not enforce a global ceiling.
    let intended_global_cap_per_interval = 200 * 100 / 1000; // = 20
    assert!(
        received > intended_global_cap_per_interval,
        "expected aggregate unstaked throughput ({received}) to exceed the intended \
         cluster-wide cap ({intended_global_cap_per_interval}), demonstrating throttle bypass"
    );
}
```
Expected result: `received` scales approximately linearly with `n_connections * 20`, confirming that the per-connection throttle in `throttle_stream` / `ConnectionStreamCounter` does not enforce any global/aggregate ceiling corresponding to `MAX_UNSTAKED_TPS`.
