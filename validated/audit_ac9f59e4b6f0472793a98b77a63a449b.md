### Title
Pack-objects concurrency limit keyed solely on client-supplied `remote_ip` allows any user to bypass per-source throttling by spoofing/rotating the IP field - (File: internal/gitaly/service/hook/pack_objects.go)

### Summary
The `pack-objects` concurrency limiter is meant to throttle how much `git-pack-objects` work a single source can trigger concurrently, analogous to the `userWithdrawLimitPerPeriod` check in the referenced report which was tied to an account identity that the caller could freely rotate. In Gitaly, the limiting key is derived exclusively from the `RemoteIp` field carried in `PackObjectsHookWithSidechannelRequest`, so an actor who controls what value ends up in that field (rather than a fixed, trustworthy per-connection attribute) can rotate it to obtain a fresh quota, just like Instance A rotating to Instance B in the original report.

### Finding Description
`packObjectsHook` computes the concurrency limiting key purely from `req.GetRemoteIp()`: [1](#0-0) 
The value only excludes loopback addresses from limiting; any other IP string, including one with a spoofable or attacker-influenced source (e.g., behind proxies, or via multiple parallel connections/NAT egress IPs), is accepted as the sole limiting key and passed to `runPackObjectsLimited` as `limitkey`: [2](#0-1) 
Although the code comment in `internal/limiter/concurrency_limiter.go` states the pack-objects limiter "uses request information (RemoteIP/Repository/User) as the limiting key," the actual limiting key constructed in `pack_objects.go` is just the raw IP string — it does not fold in `GlId`/`GlUsername`/repository, so the quota is entirely per-source-IP: [3](#0-2) 
This is structurally the same weakness as the reported prePO bug: a resource-consumption quota is bound to a single, cheaply-rotatable identity attribute (an IP string here, an account there) rather than to something the requester cannot change at will. A client (or, in cluster/NAT/proxy topologies, an intermediary) that can make different requests appear to originate from different `RemoteIp` values effectively gets a fresh concurrency budget per rotation, defeating the intended per-source throttling and enabling one logical actor to run many concurrent, potentially expensive `git-pack-objects` invocations against the same or different repositories.

### Impact Explanation
The pack-objects concurrency limiter exists specifically as a backpressure/DoS-prevention mechanism, as documented in `doc/backpressure.md`. Bypassing it by rotating the limiting-key input allows a single client to circumvent the intended concurrency cap on CPU/memory-intensive `git-pack-objects` invocations, undermining the resource-exhaustion protection the feature is meant to provide and enabling a DoS vector against Gitaly nodes serving fetch/clone traffic.

### Likelihood Explanation
Reachable via any ordinary fetch/clone (SSH or HTTP) that triggers the `pack-objects` hook path, since `RemoteIp` is forwarded from `gitaly-hooks` into `PackObjectsHookWithSidechannelRequest` without being cryptographically bound to a specific, unspoofable connection identity: [4](#0-3) 
Existing tests already model the limiter as being keyed by IP granularity (down to source port normalization) and by user id separately, showing the two identities are already treated somewhat interchangeably in test coverage without a combined/hardened key: [5](#0-4) 
Exploitability depends on the deployment's ability to vary the observed remote IP (e.g., multiple client machines, NAT egress rotation, or proxy layers that populate this field), so likelihood is environment-dependent but does not require any special privilege beyond normal fetch access.

### Recommendation
Compose the pack-objects concurrency limiting key from multiple corroborated, harder-to-rotate attributes together (e.g., authenticated `GlId`/user identity plus repository plus IP) rather than IP alone, and ensure the `RemoteIp`/`GlId` values used for limiting are derived from values Gitaly itself trusts (peer connection info) rather than solely from client-influenced fields, so that rotating any single attribute cannot reset the concurrency quota.

### Proof of Concept
1. An authenticated user (or an unauthenticated one, if pack-objects unauthenticated limiting is disabled/misconfigured) issues repeated fetch/clone requests that route through `packObjectsHook`.
2. For each batch of requests, the value ending up in `PackObjectsHookWithSidechannelRequest.RemoteIp` is varied (e.g., different source addresses via NAT/proxy egress rotation), as accepted by `net.ParseIP(req.GetRemoteIp())` in `packObjectsHook`.
3. Because `runPackObjectsLimited` keys the concurrency semaphore solely on this per-request IP string, each new IP value obtains an independent concurrency budget in `ConcurrencyLimiter.limitsByKey`, allowing the aggregate number of concurrent `git-pack-objects` invocations from the same logical actor to exceed the configured `pack_objects_limiting` concurrency cap. [6](#0-5)

func (s *server) runPackObjectsLimited(
	ctx context.Context,
	w io.Writer,
	limitkey string,
	req *gitalypb.PackObjectsHookWithSidechannelRequest,
	args *packObjectsArgs,
	stdin io.ReadCloser,
	key string,
) error {
	ctx = context.WithoutCancel(ctx)

	ctx, cancel := context.WithCancel(ctx)
	defer cancel()

	defer stdin.Close()

	if _, err := s.packObjectsLimiter.Limit(
		ctx,
		limitkey,
		func() (interface{}, error) {
			return nil,
				s.runPackObjectsFn(
					ctx,
					s.gitCmdFactory,
					w,
					req,
					args,
					stdin,
					key,
				)
		},
	); err != nil {
		return err
	}

// getConcurrencyLimit retrieves the concurrency limit for the given key. If no such limiter exists
// it will be lazily constructed.
func (c *ConcurrencyLimiter) getConcurrencyLimit(limitingKey string) *keyedConcurrencyLimiter {
	c.m.Lock()
	defer c.m.Unlock()

	if c.limitsByKey[limitingKey] == nil {
		// Set up the queue tokens in case a maximum queue length was requested. As the
		// queue tokens are kept during the whole lifetime of the concurrency-limited
		// function we add the concurrency tokens to the number of available token.
		var queueTokens semaphorer
		if c.maxQueueLength > 0 {
			queueTokens = c.createSemaphore(uint(c.currentLimit() + c.maxQueueLength))
		}

		c.limitsByKey[limitingKey] = &keyedConcurrencyLimiter{
			monitor:               c.monitor,
			maxQueueWait:          c.maxQueueWait,
			setWaitTimeoutContext: c.SetWaitTimeoutContext,
			concurrencyTokens:     c.createSemaphore(uint(c.currentLimit())),
			queueTokens:           queueTokens,
		}
	}

	c.limitsByKey[limitingKey].refcount++

	return c.limitsByKey[limitingKey]
}
