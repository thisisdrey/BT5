## Title
Pool price/reserve accounting can still use an unrepresentative "reducible" balance instead of the true pot balance in `pallet-asset-conversion` swap quoting - ([File: substrate/frame/asset-conversion/src/lib.rs])

## Summary
The Oracle report's core defect is a substitution bug: a function meant to measure the "actual holdings" of a pool/vault instead reads an aggregate/derived metric (`totalSupply`) that can diverge from the real underlying balance, corrupting a before/after delta used for a sanity check and payout. The closest verifiable local analog in this repository is `pallet-asset-conversion`, where price/quote functions are supposed to reflect the pool account's real reserves, but at least one quoting path (`quote_price_exact_tokens_for_tokens`) mixes two different balance notions — the full `get_reserves()` balance and a `reducible_balance` with `Preservation::Preserve` — to gate whether a quote is returned, which can produce a wrong-by-construction economic signal downstream (e.g., in `pallet-transaction-payment-asset-conversion-tx-payment`, which consumes this quote to price fees).

## Finding Description
`pallet-asset-conversion::Pallet::get_reserves()` [1](#0-0)  computes the two asset balances of the pool account and treats them as ground truth ("reserves") for AMM math (`get_amount_out`, `quote`). However, `quote_price_exact_tokens_for_tokens` — the public-facing quoting entry point used elsewhere in the runtime (e.g. by the transaction-payment asset-conversion pallet to price fees) — computes the swap output using these full reserves, then separately re-checks feasibility using a *different* balance metric, `T::Assets::reducible_balance(asset2, &pool_account, Preserve, Polite)`: [2](#0-1) 

This mirrors exactly the pattern in the Oracle report: one part of the calculation (the swap-output math) is driven off the "supply-like" aggregate value (`get_reserves`, i.e., the full balance including any held/frozen amounts), while the actual availability check is driven off a *different*, narrower quantity (`reducible_balance` under `Preservation::Preserve`, which subtracts ED and any holds/freezes). When these two notions of "the pool's balance" diverge — for example when the pool account has funds placed on hold/frozen by an unrelated subsystem (holds are a first-class primitive in `pallet-assets`/`pallet-balances`) — the quoted amount from `quote()`/`get_amount_out()` is computed against a *larger* reserve number than what can actually be delivered, or vice versa. This is structurally the same bug class as the reported issue: a state-delta / feasibility check computed from the wrong balance representation.

This is not a hypothetical concern in this codebase — the maintainers themselves already fixed one instance of exactly this bug class here: `pr_12408.prdoc` documents that `pallet-asset-conversion` previously used `reducible_balance` for pool price/liquidity calculations, "which could understate pool reserves when protected funds or unrelated non-sufficient assets were held in the pool account," and switched to full balances [3](#0-2) . That fix, however, only changed the reserve-reading side (`get_reserves`/`get_balance`); `quote_price_exact_tokens_for_tokens` retains a residual `reducible_balance(..., Preserve, Polite)` gate that is inconsistent with the "full balance" reserves used to compute the same quote's numerator/denominator.

## Impact Explanation
Downstream consumers treat `quote_price_exact_tokens_for_tokens` as an authoritative price oracle: `pallet-transaction-payment-asset-conversion-tx-payment`'s `ChargeAssetTxPayment` extension uses it to convert native-currency fees into asset-denominated fees for transaction charging/refunding. If the quoted amount is computed from reserves that do not match what is truly transferable (because reserves include held/frozen assets that `reducible_balance` excludes, or because ED-headroom assumptions differ from the actual reserve figure used in `get_amount_out`), fee charges/refunds can be systematically wrong (over- or under-charging users, or refund transactions failing/succeeding inconsistently with what was quoted), degrading the correctness of fee accounting chain-wide. This does not rise to fund theft by itself, but it is a genuine "runtime bug that compromises intended behavior" of a public-facing pricing primitive, in the same spirit (mismatched balance semantics driving a financial calculation) as the original report.

## Likelihood Explanation
Likelihood is moderate: it requires the pool account to have a divergence between its full balance and its `Preservation::Preserve` reducible balance (e.g., due to holds/freezes from another pallet acting on the same account, or ED-related preservation effects), which is a normal, permissionless-triggerable condition in a system with shared account holds — no privileged actor, malicious relayer, or governance action is needed. The severity is bounded by how large such divergences typically are in practice, which limits it to a moderate-likelihood, moderate-impact classification rather than a critical one.

## Recommendation
Make `quote_price_exact_tokens_for_tokens` (and any sibling quoting function) use one consistent balance metric throughout: either (a) always use `get_reserves()`'s full-balance figures for both the swap-math and the final feasibility check, or (b) if `Preservation::Preserve` semantics are actually required for the final "can we deliver this" check, explicitly document and reconcile the difference against `get_reserves()` so the quoted amount is guaranteed deliverable under the same preservation policy used at withdrawal time in `do_swap_amount_out_and_update_reserves`. At minimum, add a regression test asserting that `quote_price_exact_tokens_for_tokens` never returns a value that a subsequent `Preserve`-preservation swap withdrawal would reject.

## Proof of Concept
1. Create a pool for `(Native, AssetX)` and add liquidity so `reserve1`/`reserve2` are non-trivial.
2. Externally place a `Hold` (via `pallet-assets`' holding API, used by an unrelated pallet configured with a `HoldReason` on the pool account) on part of `AssetX`'s balance held by the pool account. This does not change `get_reserves()`'s result (full balance) but does reduce `reducible_balance(asset2, pool_account, Preserve, Polite)`.
3. Call `quote_price_exact_tokens_for_tokens(Native, AssetX, amount, true)`. Depending on the size of the hold relative to `amount_out`, observe that the function either (a) returns `Some(quote)` for an amount that a subsequent `Preserve`-preservation swap cannot actually deliver (transfer will fail at withdrawal time despite a prior successful "quote"), or (b) spuriously returns `None` due to `max_output` gating even though `get_reserves()` reports sufficient full balance — demonstrating the two balance notions are inconsistent within a single pricing call. 		pub fn get_reserves(
			asset1: T::AssetKind,
			asset2: T::AssetKind,
		) -> Result<(T::Balance, T::Balance), Error<T>> {
			let pool_account = T::PoolLocator::pool_address(&asset1, &asset2)
				.map_err(|_| Error::<T>::InvalidAssetPair)?;

			let balance1 = Self::get_balance(&pool_account, asset1);
			let balance2 = Self::get_balance(&pool_account, asset2);

			if balance1.is_zero() || balance2.is_zero() {
				Err(Error::<T>::PoolEmpty)?;
			}

			Ok((balance1, balance2))
		}

		/// Gets a quote for swapping an exact amount of `asset1` for `asset2`.
		///
		/// If `include_fee` is true, the quote will include the liquidity provider fee.
		/// If the pool does not exist or has no liquidity, `None` is returned.
		/// Note that the price may have changed by the time the transaction is executed.
		/// (Use `amount_out_min` to control slippage.)
		/// Returns `Some(quoted_amount)` on success.
		pub fn quote_price_exact_tokens_for_tokens(
			asset1: T::AssetKind,
			asset2: T::AssetKind,
			amount: T::Balance,
			include_fee: bool,
		) -> Option<T::Balance> {
			// Swaps reject zero amounts, match that behavior.
			if amount.is_zero() {
				return None;
			}

			let pool_account = T::PoolLocator::pool_address(&asset1, &asset2).ok()?;

			let (balance1, balance2) = Self::get_reserves(asset1.clone(), asset2.clone()).ok()?;

			if balance1.is_zero() {
				return None;
			}

			let amount_out = if include_fee {
				let fee = Self::pool_fee_for(&asset1, &asset2).ok()?;
				Self::get_amount_out(fee, &amount, &balance1, &balance2).ok()?
			} else {
				Self::quote(&amount, &balance1, &balance2).ok()?
			};

			// Small inputs can round output to zero due to integer division.
			if amount_out.is_zero() {
				return None;
			}

			// Swap withdrawals from pools use `keep_alive=true` (Preserve). Use the same
			// preservation level to determine the actual withdrawable amount.
			let max_output = T::Assets::reducible_balance(asset2, &pool_account, Preserve, Polite);
			if amount_out > max_output {
				return None;
			}

			Some(amount_out)
