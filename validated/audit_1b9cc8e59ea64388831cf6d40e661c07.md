## Title
Exchange/Market operations reference pools by a reorg-mutable sequential ID with no content binding, enabling unintended trade execution after L1 reorg — (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeCreateActuator.java`, `ExchangeTransactionActuator.java`, `ExchangeInjectActuator.java`, `ExchangeWithdrawActuator.java`)

### Summary
`ExchangeCreateActuator.execute()` assigns each newly-created exchange pool an ID derived purely from a global sequential counter (`dynamicStore.getLatestExchangeNum() + 1`), not from any content hash or transaction-specific value. `ExchangeTransactionActuator`, `ExchangeInjectActuator`, and `ExchangeWithdrawActuator` all look up the target pool solely `by ByteArray.fromLong(contract.getExchangeId())` with no binding to the pool's expected creator/content at the time the referencing transaction was signed (for `ExchangeTransactionContract`, which is callable by anyone). This mirrors the Morph `challengeState(uint64 batchIndex)` root cause: a mutable, reorg-sensitive index is trusted as if it uniquely and durably identified specific content.

### Finding Description
`ExchangeCreateActuator.execute()` computes the new exchange's ID as: [1](#0-0) 
which is strictly a function of block-execution order (`getLatestExchangeNum()`), not of the transaction's own hash or contents. That counter is then persisted and returned as the pool's permanent `exchangeId`: [2](#0-1) 

Later, unprivileged callers reference a pool purely by that numeric ID. `ExchangeTransactionActuator.doValidate()` fetches the pool by ID and only checks that the trader's token matches the pool's token pair — it performs no check that the pool is still the one the caller expected when they signed the transaction: [3](#0-2) 

`ExchangeInjectActuator` similarly resolves the pool by ID and additionally checks creator address for injection, but the ID→pool binding itself is still counter-based: [4](#0-3) 

`ExchangeWithdrawActuator` follows the same ID-lookup pattern: [5](#0-4) 

Because `getLatestExchangeNum()` is a simple per-block-application counter incremented during `applyBlock`, if two competing `ExchangeCreateContract` transactions (from different accounts, for different token pairs) are both broadcast and initially execute in one order — assigning IDs N and N+1 respectively — a chain reorg (via `Manager.switchFork`) can re-apply the two transactions in the opposite relative order, so the pool that occupies exchange ID N after the reorg is a *different* pool (different token pair, different price/balances, potentially created by an unrelated or even malicious account) than the one that occupied ID N at pre-reorg time. `switchFork` unconditionally re-executes transactions against the diverged state without any mechanism that would prevent this ID reassignment: [6](#0-5) 

An unprivileged trader who broadcasts an `ExchangeTransactionContract` referencing `exchangeId = N`, expecting to trade against a specific known pool (price/liquidity they observed before the reorg), can have that transaction confirmed post-reorg against a *different* pool at the same ID that happens to also list the same token pair (this is fully attacker-influenceable, since token IDs used in trades are commonly TRX or well-known TRC10 assets, so pair collisions across independently created pools at colliding IDs are plausible and can be deliberately engineered by racing `ExchangeCreateContract` submissions). The trader's trade then executes at an unexpected, potentially adversarial price, causing direct loss of TRX/tokens — the same "reference-by-mutable-index-without-content-check" root cause as the reported Morph `challengeState` bug.

### Impact Explanation
A trader can unknowingly execute a trade against an unintended liquidity pool (wrong price curve/balances, potentially deployed by an attacker to specifically exploit this race) after an L1 reorg, resulting in direct, unrecoverable loss of TRX or TRC10 tokens for that trader — a concrete instance of "unauthorized loss of funds" reachable via a normal, unprivileged `ExchangeTransactionContract` broadcast.

### Likelihood Explanation
Requires (a) an L1 reorg on java-tron (which does occur via the `switchFork` mechanism during witness/consensus forks — a documented, non-hypothetical event that the codebase has explicit tests for) and (b) two `ExchangeCreateContract` transactions racing for adjacent sequential IDs whose relative order flips across the reorg. This is a narrower precondition than a routine transfer, but it is a purely mechanical consequence of using an execution-order-derived integer as a permanent, unauthenticated pool identifier, and can be actively engineered by an adversary timing competing `ExchangeCreateContract` submissions around a fork boundary.

### Recommendation
Do not rely solely on the sequential `exchangeId` for state-changing operations that a third party pre-signs against expected pool content. At minimum, allow/require `ExchangeTransactionContract` (and ideally `ExchangeInjectContract`/`ExchangeWithdrawContract`) callers to assert expected pool metadata (e.g., creator address, token pair, and/or a content hash/creation-tx-hash of the `ExchangeCapsule`) and have the actuator's `validate()` reject execution if the currently stored pool at that ID does not match the asserted content — analogous to the suggested Morph fix of validating `committedBatches[batchIndex] == batchHash` before challenging.

### Proof of Concept
1. Attacker and victim both submit `ExchangeCreateContract` transactions in the same block window; assume victim's pool (token pair A/B, favorable price) is provisionally assigned `exchangeId = N` and attacker's pool (also A/B, unfavorable price) gets `N+1`.
2. Victim's counterpart submits an `ExchangeTransactionContract` referencing `exchangeId = N`, expecting to trade against the favorable pool.
3. A reorg occurs (`Manager.switchFork`) that re-applies the two `ExchangeCreateContract` transactions in reversed relative order, so the attacker's pool now receives `exchangeId = N` and the victim's pool gets `N+1`.
4. The victim's already-signed `ExchangeTransactionContract` (still referencing `exchangeId = N`) is confirmed and executes against the attacker's unfavorable pool via `ExchangeTransactionActuator`, since `doValidate()`/`execute()` only check token-pair membership by ID, not pool identity, resulting in the victim trading at the attacker's chosen unfavorable price and losing funds.
