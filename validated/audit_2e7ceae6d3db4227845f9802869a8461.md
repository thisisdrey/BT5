### Title
`ft_resolve_withdraw` never re-credits the wNEAR `storage_deposit` leg when the `storage_deposit()` call to an attacker-controlled `token` fails - ([File: contracts/defuse/src/contract/tokens/nep141/withdraw.rs])

### Summary
`Contract::internal_ft_withdraw` debits both the withdrawn `token` amount and the wNEAR `storage_deposit` amount from the caller's ledger balance in a single `withdraw()` call. When the caller supplies a `token` that does not implement NEP-145 `storage_deposit`, the batched `storage_deposit`+`ft_transfer` actions on `withdraw.token` fail, and the only recovery path, `ft_resolve_withdraw`, only re-credits the `token` amount — it never receives or re-credits the `storage_deposit` (wNEAR) amount.

### Finding Description
The broken binding is: `wnear_debited(signer) + token_debited(signer) == value_delivered_to(receiver_id) + value_re-credited_by(ft_resolve_withdraw)`.

`Contract::internal_ft_withdraw` ( [1](#0-0) ) debits both legs (`token` amount and wNEAR `storage_deposit` amount) from the caller's ledger in one `self.withdraw(...)` call, then schedules `near_withdraw` → `do_ft_withdraw` → `ft_resolve_withdraw`.

In `Contract::do_ft_withdraw` ( [2](#0-1) ), the `storage_deposit` call and the subsequent `ft_transfer`/`ft_transfer_call` call are batched as two actions on the **same** promise/receiver (`withdraw.token`), via `ext_ft_core::ext_on(p)` — the same pattern used in `upgrade.rs` (`Self::ext_on(p).state_migrate()` after `deploy_contract`) to append an action to an existing promise on the same account. If `withdraw.token` does not implement `storage_deposit` (attacker deploys their own contract lacking NEP-145), that first action fails, halting execution of the batch so the following `ft_transfer` action never runs.

`ft_resolve_withdraw` ( [3](#0-2) ) is invoked as the `.then()` callback regardless of success/failure. Its signature only carries `token`, `sender_id`, `amount` (the withdrawn `token` amount) and `is_call` — it has no `storage_deposit` parameter at all, so it can only re-credit the `token` ledger balance (via `self.deposit(sender_id, [(Nep141TokenId::new(token).into(), refund)], ...)`), never the wNEAR amount. The wNEAR that was already withdrawn from wNEAR's contract via `near_withdraw` and attached as `NearToken` deposit to the failed `storage_deposit()` call gets refunded, on failure, back to the predecessor of that action (the Defuse contract's own account balance as raw NEAR) — not credited back to the caller's internal wNEAR ledger entry, which remains permanently debited.

### Impact Explanation
Any signer who calls `ft_withdraw` with `storage_deposit: Some(amount)` and a `token` account that fails the `storage_deposit` call (e.g. an attacker-deployed contract lacking NEP-145, or any account without that method) permanently loses the wNEAR amount from their own Defuse ledger balance with no re-credit, no storage created on `token`, and no FT delivered to `receiver_id` (the `token` leg is refunded by `ft_resolve_withdraw`, but the wNEAR leg is not). This matches the "user funds permanently frozen" Critical impact category — value is destroyed from the ledger with no corresponding delivery or refund. The loss is confined to the calling account's own ledger balance per call (since `owner_id` is `ensure_auth_predecessor_id()`), but it is repeatable for any amount and any number of times by any account that holds both a `token` balance and a wNEAR balance in the ledger.

### Likelihood Explanation
Preconditions are trivial and fully attacker-controlled: the caller needs (1) a wNEAR balance in the ledger (obtained via normal deposit), and (2) a balance of some `token` in the ledger (the attacker can deploy their own FT contract, deposit some amount of it into Defuse, giving themselves ledger balance for that `token_id`), and (3) that `token` account must lack (or otherwise fail) `storage_deposit`. No privileged role, no victim key, and no relayer/DAO involvement is required — the call path is `ft_withdraw` directly, gated only by `assert_one_yocto` and `ensure_auth_predecessor_id`, which any unprivileged predecessor with `auth_by_predecessor_id` satisfies.

### Recommendation
Pass the `storage_deposit` amount (and the wNEAR `TokenId`) through to `ft_resolve_withdraw` (e.g., as an `Option<NearToken>` parameter) so that on failure of the `storage_deposit`/`ft_transfer` batch, both legs — the `token` amount and the wNEAR `storage_deposit` amount — are re-credited to `sender_id`'s ledger balance, matching the refund behavior already applied to the `token` leg.

### Proof of Concept
`cargo test` sandbox plan (`near-workspaces`):
1. Deploy the Defuse contract and wNEAR contract; deploy an attacker-controlled FT contract stub `bad_token` implementing NEP-141 core but deliberately omitting/failing `storage_management::storage_deposit`.
2. As `signer`, deposit `bad_token` balance and wNEAR balance into the Defuse ledger (record `wnear_before`, `token_before`).
3. Call `ft_withdraw { token: bad_token, receiver_id: some_account_without_storage, amount, storage_deposit: Some(deposit_amount), min_gas: None }` signed by `signer`, attaching 1 yoctoNEAR.
4. Assert the `storage_deposit` call to `bad_token` fails (MethodNotFound/panic) and that the batched `ft_transfer` action never executes (no `ft_transfer` receipt log/event on `bad_token`, `receiver_id`'s storage never registered).
5. Query Defuse ledger post-call: assert `token_after == token_before` (correctly re-credited by `ft_resolve_withdraw`), but assert `wnear_after == wnear_before - deposit_amount` (i.e., NOT restored), proving the binding `wnear_debited(signer) + token_debited(signer) == value_delivered_to(receiver_id) + value_re-credited_by(ft_resolve_withdraw)` fails by exactly `deposit_amount` on the wNEAR side.

    pub fn do_ft_withdraw(withdraw: FtWithdraw) -> Promise {
        let min_gas = withdraw.min_gas();
        let p = if let Some(storage_deposit) = withdraw.storage_deposit {
            require!(
                promise_result_checked_void(0).is_ok(),
                "near_withdraw failed",
            );

            ext_storage_management::ext(withdraw.token)
                .with_attached_deposit(storage_deposit)
                .with_static_gas(STORAGE_DEPOSIT_GAS)
                // do not distribute remaining gas here
                .with_unused_gas_weight(0)
                .storage_deposit(Some(withdraw.receiver_id.clone()), None)
        } else {
            Promise::new(withdraw.token)
        };

        let p = ext_ft_core::ext_on(p)
            .with_attached_deposit(NearToken::from_yoctonear(1))
            .with_static_gas(min_gas)
            // distribute remaining gas here
            .with_unused_gas_weight(1);
        if let Some(msg) = withdraw.msg {
            p.ft_transfer_call(
                withdraw.receiver_id,
                withdraw.amount.into(),
                withdraw.memo,
                msg,
            )
        } else {
            p.ft_transfer(withdraw.receiver_id, withdraw.amount.into(), withdraw.memo)
        }
    }

    fn ft_resolve_withdraw(
        &mut self,
        token: AccountId,
        sender_id: AccountId,
        amount: U128,
        is_call: bool,
    ) -> U128 {
        let used = if is_call {
            // `ft_transfer_call` returns successfully transferred amount
            match promise_result_checked_json::<U128>(0) {
                Ok(Ok(used)) => used.0.min(amount.0),
                Ok(Err(_deserialize_err)) => 0,
                // do not refund on failed `ft_transfer_call` due to
                // NEP-141 vulnerability: `ft_resolve_transfer` fails to
                // read result of `ft_on_transfer` due to insufficient gas
                Err(_) => amount.0,
            }
        } else {
            // `ft_transfer` returns empty result on success
            if promise_result_checked_void(0).is_ok() {
                amount.0
            } else {
                0
            }
        };

        let refund = amount.0.saturating_sub(used);
        if refund > 0 {
            self.deposit(
                sender_id,
                [(Nep141TokenId::new(token).into(), refund)],
                Some(REFUND_MEMO),
            )
            .unwrap_or_else(|err| err.panic());
        }

        U128(used)
    }
