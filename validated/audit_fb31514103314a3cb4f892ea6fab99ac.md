The code confirms all elements of the claim exactly as described: `PRECISION_SCALING_FACTOR` is `4096` (a `u16`), `reward_per_token` performs the described integer division that can floor to zero [1](#0-0) , and `update_pool_rewards` unconditionally advances `last_update_block` regardless of whether the computed increment was zero [2](#0-1) . Audit Report

## Title
Reward-per-token accrual in `pallet-asset-rewards` can permanently round to zero, freezing staker rewards - (File: `substrate/frame/asset-rewards/src/lib.rs`)

## Summary
`pallet-asset-rewards` computes the global accumulator `reward_per_token_stored` via integer division scaled by a fixed `PRECISION_SCALING_FACTOR` of only `4096` [6](#0-5) . When `total_tokens_staked` is large relative to `reward_rate_per_block * rewardable_blocks_elapsed * 4096`, the division floors to zero, and because `update_pool_rewards` unconditionally advances `last_update_block` every call [7](#0-6) , an attacker can repeatedly reset the elapsed-block window via public extrinsics to keep the increment at zero indefinitely.

## Finding Description
`reward_per_token` computes `reward_per_token_stored + reward_rate_per_block * rewardable_blocks_elapsed * PRECISION_SCALING_FACTOR / total_tokens_staked` [8](#0-7) . For realistic pool configurations (e.g., an 18-decimal staked asset with large total stake and a 6-decimal reward asset with a modest per-block rate), this numerator can be smaller than the denominator, flooring the increment to zero. `update_pool_and_staker_rewards`, invoked from `stake`, `unstake`, and `harvest_rewards` [9](#0-8) , calls `update_pool_rewards`, which writes `last_update_block = current_block_number()` regardless of whether the computed `reward_per_token` actually changed [2](#0-1) . No caller enforces a minimum elapsed-block threshold or minimum stake amount before committing this update [10](#0-9) . Consequently, any account can call `stake` (with a trivial amount) every block, resetting `rewardable_blocks_elapsed` to 1 each time and perpetuating the zero-increment condition, stalling the shared pool-wide accumulator `reward_per_token_stored` for all stakers.

## Impact Explanation
This matches the "public underpriced work" impact category in the gate: cheap, publicly callable extrinsics let an unprivileged account stall reward distribution for an entire pool's stakers, even though the pool operator has funded rewards as expected. Reward funds intended for distribution remain effectively locked/undistributed in the pool account, aligning with a permanent user-fund lock impact.

## Likelihood Explanation
The precondition — staked asset with high decimal precision/large supply paired with a reward asset with lower decimals or modest rate — is a plausible, common pool configuration and requires no privileged access, governance action, or off-chain infrastructure. Any signed account can trigger and sustain the griefing pattern using ordinary `stake`/`unstake`/`harvest_rewards` calls, and the exploit is fully reproducible via the exact arithmetic shown in `reward_per_token`.

## Recommendation
- Increase `PRECISION_SCALING_FACTOR` substantially (e.g., using a wider fixed-point scale) so realistic reward-rate/stake-size ratios do not floor to zero.
- Avoid unconditionally advancing `last_update_block` when the computed increment is zero; instead, retain the unconsumed elapsed-block window (or track dust) so it isn't discarded on every touch.
- Add tests verifying `reward_per_token` cannot stall to zero increments across repeated near-immediate updates for realistic asset-decimal combinations.

## Proof of Concept
1. Call `create_pool` with an 18-decimal staked asset (total staked ~`10^24`) and a 6-decimal reward asset with `reward_rate_per_block = 10^6` (i.e., 1 token/block).
2. Per-block increment = `10^6 * 1 * 4096 / 10^24 = 0`, per the arithmetic in `reward_per_token` [8](#0-7) .
3. Any account calls `stake` with a trivial amount every block; each call runs `update_pool_and_staker_rewards` → `update_pool_rewards`, which sets `last_update_block` to the current block despite the zero increment [2](#0-1) .
4. `reward_per_token_stored` never increases across any number of blocks; `derive_rewards` for all stakers remains stalled at zero growth [11](#0-10) , despite the configured non-zero reward rate.
