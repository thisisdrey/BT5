### Title
Downloaded attachment content is never verified against the requested `content_hash`, allowing malicious peers to inject arbitrary unauthenticated blobs into the node's AtlasDB - (File: stackslib/src/net/atlas/download.rs)

### Summary
`AttachmentsBatchStateContext::extend_with_attachments` accepts any successfully-decoded `GetAttachmentResponse` from any peer that claimed (via its inventory) to have the requested `content_hash`, and inserts the returned `Attachment` into `context.attachments: HashSet<Attachment>` with no check that `Attachment::hash() == request.content_hash`. Because `HashSet<Attachment>` dedups by the full content-derived `Eq`/`Hash`, colluding/sybil peers can each return a different, non-matching blob for the same requested `content_hash`, and every distinct blob is retained and later unconditionally persisted via `AtlasDB::insert_instantiated_attachment`.

### Finding Description
`get_prioritized_attachments_requests` (stackslib/src/net/atlas/download.rs:404-478) builds an `AttachmentRequest` whose `sources` field contains every peer that self-reported possession of the attachment via inventory bits, and the request itself carries the expected `content_hash` [1](#0-0) .

When responses come back, `extend_with_attachments` (download.rs:530-558) does:
```
if let Ok(response) = response.decode_atlas_get_attachment() {
    self.attachments.insert(response.attachment);
    report.bump_successful_requests();
}
``` [2](#0-1) 

There is no comparison between `response.attachment.hash()` and `request.content_hash` anywhere in this function - the only validation is that the HTTP body parses as JSON into a `GetAttachmentResponse` (`decode_atlas_get_attachment` in `stackslib/src/net/api/getattachment.rs:159-165`, which only does `serde_json::from_value`, no hash check) [3](#0-2) .

Because `self.attachments` is a `HashSet<Attachment>`, deduplication is keyed on the full content of the `Attachment`, not on any target `content_hash`. If N malicious peers all claim (via `AttachmentsInventoryRequest`/inventory bit) to have the same `content_hash` and then each return a distinct payload B1..BN, `BatchedRequestsResult::succeeded` will contain N distinct `(request, response)` entries (one per source url in `sources`, since `PeerNetwork::begin_request` issues one request per queued `Requestable`, and `AttachmentRequest`'s `sources` map is iterated to schedule per-peer requests), and every distinct blob passes decode and lands in the `HashSet` unfiltered.

Downstream, `AttachmentsDownloader::run` drains `context.attachments` and unconditionally calls `network.atlasdb.insert_instantiated_attachment(&attachment)` for every entry, before ever checking whether that attachment's hash matches the content hash that was actually requested:
```
for attachment in context.attachments.drain() {
    let attachments_instances = network.atlasdb.find_all_attachment_instances(&attachment.hash())?;
    network.atlasdb.insert_instantiated_attachment(&attachment)?;
    ...
    context.attachments_batch.resolve_attachment(&attachment.hash())
}
``` [4](#0-3) 

Because `find_all_attachment_instances` and `resolve_attachment` are keyed by `attachment.hash()` (the attacker's actual bytes, not the requested `content_hash`), a bogus blob whose hash doesn't match the legitimate target will not resolve the legitimate pending instance (an attacker would need a hash preimage to fully spoof legitimate content) - but the call to `insert_instantiated_attachment` happens unconditionally, before this check, so every attacker-supplied blob is persisted into the node's AtlasDB regardless of whether it matches anything the node ever asked for.

### Impact Explanation
Any peer in `outbound_sync_peers` can supply arbitrary attachment bytes that get written to the node's local AtlasDB via `insert_instantiated_attachment`, with zero validation against the `content_hash` that was the basis for issuing the request. A set of N colluding/sybil peers, each reporting (falsely or not) that it has the same attachment via its `AttachmentsInventoryRequest` response, can each return a distinct payload, and all N distinct payloads are accepted and permanently stored, once per download round, per attacker-controlled peer. This is unauthenticated write access to persistent node state (the AtlasDB attachments table), repeatable every retry/round for as long as the node's outbound sync peer set includes the attacker's peers.

### Likelihood Explanation
Preconditions: the attacker's peers must be part of the node's `outbound_sync_peers` (achievable by any unprivileged peer that establishes an outbound-eligible P2P connection and gets included in the node's peer set - no secret or privileged role required) and must respond to `AttachmentsInventoryRequest`/`AttachmentRequest` HTTP requests over the peer's data URL. No authentication, signature, or admin capability is needed to serve these responses; the only "protocol" enforced is a JSON-decodable `GetAttachmentResponse` body. This is fully remotely reachable via the P2P/HTTP data-plane and is repeatable every batch/retry cycle.

### Recommendation
In `extend_with_attachments`, after `decode_atlas_get_attachment()` succeeds, compute `response.attachment.hash()` and compare it against `request.content_hash` before inserting into `self.attachments`; drop (and mark the source `report.bump_failed_requests()`/treat as faulty) any response whose hash does not match. Consider also keying `self.attachments` by `content_hash` rather than relying on `Attachment`'s content-derived `Eq`/`Hash`, and only calling `insert_instantiated_attachment` for attachments that have been hash-verified against a request that was actually issued for that hash.

### Proof of Concept
Rust test in `stackslib/src/net/atlas/tests.rs` (or a new test module) that:
1. Constructs an `AttachmentsBatchStateContext` with a `peers` map containing several fake peer URLs.
2. Constructs a `BatchedRequestsResult<AttachmentRequest>` whose `.succeeded` map has entries `(request, Some(response))` for the SAME `AttachmentRequest` (same `content_hash`) but N different peer URLs (achieved by giving each a distinct `sources` entry in separate calls, or by directly invoking `extend_with_attachments` N times with different `AttachmentRequest`/response pairs sharing the same `content_hash`), each response's `Attachment` containing distinct random bytes B1..BN (none of which hash to `content_hash`).
3. Calls `context.extend_with_attachments(&mut results)`.
4. Asserts `context.attachments.len() == N`, and that none of the N `Attachment` values satisfy `attachment.hash() == request.content_hash`, demonstrating that unvalidated, non-matching content is accepted and would subsequently be persisted via `AtlasDB::insert_instantiated_attachment` in `AttachmentsDownloader::run`.

    pub fn decode_atlas_get_attachment(self) -> Result<GetAttachmentResponse, NetError> {
        let contents = self.get_http_payload_ok()?;
        let contents_json: serde_json::Value = contents.try_into()?;
        let resp: GetAttachmentResponse = serde_json::from_value(contents_json)
