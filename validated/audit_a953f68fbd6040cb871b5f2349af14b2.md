### Title
Contract-loading gas fee is charged on source `wasm_bytes`, not on the actual deserialized `compiled_size`, breaking metering totality for compile-bloated contracts - (File: runtime/near-vm-runner/src/wasmtime_runner/mod.rs)

### Summary
`WasmtimeVM::with_compiled_and_loaded` charges `before_loading_executable`/`after_loading_executable` gas using the original source `wasm_bytes` field cached alongside the compiled artifact, while the actual work performed — `Module::deserialize` — operates on `compiled_size`, the length of the serialized compiled module, which can be substantially larger than the source. Because the memoized/persisted cache always returns the same fixed `wasm_bytes` value regardless of how large the compiled artifact grew, every repeated `FunctionCall` against such a contract is charged proportional to the small source size while performing deserialization work proportional to the much larger compiled artifact.

### Finding Description
In `compile_and_persist` (mod.rs:657-678), the cache record stores `wasm_bytes: code.code().len() as u64` (mod.rs:670) — the original source wasm length — next to the compiled artifact bytes (`CompiledContract::Code(serialized.clone())`). Later, in `with_compiled_and_loaded`, when a cache hit occurs (memory or persistent), the closure retrieves `(wasm_bytes, module)` from that same record (mod.rs:709-719), computes `compiled_size = module.len()` (mod.rs:746) purely to use as the LRU/memory-cache "weight" for capacity accounting (mod.rs:788, comment at 784-786), and then calls `unsafe { Module::deserialize(&self.engine, &module) }` (mod.rs:747) — the actual expensive operation — on the full compiled bytes.

The tuple returned out of the cache lookup and used for gas metering is `(wasm_bytes, ...)`, i.e., the *source* size, not `compiled_size`. This value flows to `gas_counter.before_loading_executable(&config, &method, wasm_bytes)` (mod.rs:814) and `gas_counter.after_loading_executable(&config, wasm_bytes)` (mod.rs:821), which apply the `ContractLoadingBytes` per-byte fee against `wasm_bytes`. Nothing in this path re-derives the fee from `compiled_size`; `compiled_size` is discarded after being used solely for cache-weight bookkeeping.

An attacker who deploys a contract engineered to have a small source but a disproportionately large compiled artifact (e.g., heavy use of distinct function signatures/types, many exports, or constructs that near_vm's/wasmtime's code generator expands significantly) pays gas scaled to the small `wasm_bytes`, while every subsequent call — hitting the memoized cache entry — pays the same small deserialization fee even though `Module::deserialize` must process the much larger compiled bytes each time (cache holds a `PreparationResult`/instantiation pre-linked object across memory-cache hits, but persistent-cache hits still re-run `Module::deserialize` on the stored compiled bytes).

No existing check re-ties the fee to `compiled_size`; the size-limit and block-count checks referenced as "other question" bound how large the compiled module can grow relative to source, but do not correct this specific fee-basis mismatch.

### Impact Explanation
This is a metering-totality violation: gas charged for contract loading no longer bounds the true CPU work of deserialization once compiled-size inflation exceeds the assumed source-to-compiled ratio baked into the `ContractLoadingBytes` parameter. Repeated cheap `FunctionCall` transactions against such a contract let an attacker extract disproportionate deserialization CPU work from chunk producers per unit of gas paid, which is a resource-exhaustion/DoS vector against block/chunk production rather than a fund-theft or consensus-divergence bug by itself.

### Likelihood Explanation
Exploitability depends entirely on the attacker's ability to craft a wasm module with an extreme compiled/source-size ratio and on the (separately flagged) weakness of `prepare_v2`'s block-count/structural limits to prevent such inflation. Given those preconditions, the attack is fully within reach of an unprivileged account: deploy once, then submit unlimited ordinary `FunctionCall` transactions, each cheaply priced under `wasm_bytes`-based metering. Repeatability is unlimited as long as the attacker can pay the (deliberately mispriced, low) per-call gas cost.

### Recommendation
Base `ContractLoadingBytes` fee calculation on `compiled_size` (the actual bytes passed to `Module::deserialize`) rather than on the cached source `wasm_bytes`, or additionally charge a fee proportional to `compiled_size` recovered from the cache record. Ensure this corrected size is persisted so cache hits (memory and persistent) always re-derive the correct deserialization-proportional fee.

### Proof of Concept
Integration test plan:
1. Compile a "compile-bloated" contract fixture whose wasm source (`wasm_bytes`) is a few KB but which compiles into a `serialized.len()` (`compiled_size`) many times larger (e.g., via generation of hundreds of distinct function signatures/exports known to expand significantly under near_vm/wasmtime codegen).
2. Deploy via `DeployContract`; call `with_compiled_and_loaded` (or the full `run` entry point) once to populate the cache, capturing `wasm_bytes` and `compiled_size` from the cache record.
3. Assert `compiled_size` is significantly larger (e.g. >5x) than `wasm_bytes`.
4. Invoke the same contract's `FunctionCall` many times through the persistent cache path (or force cache eviction/reinsertion to force redeserialization) and measure wall-clock time of `Module::deserialize` versus the `contract_loading_bytes * wasm_bytes` gas fee that was charged in `gas_counter.before_loading_executable`/`after_loading_executable`.
5. Expected assertion: gas charged (mapped to gas-to-time ratio assumed by the parameter) is far below the actual measured deserialization time, demonstrating the fee does not bound the true cost.
