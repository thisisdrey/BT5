## Analysis

The reported bug class is a missing "not-self" check that lets a privileged party (the auction owner) interact with their own order/auction, enabling self-dealing. The closest reachable analog in java-tron is the order-book market feature reachable via `MarketSellAssetContract` (`MarketSellAssetActuator`), which is java-tron's on-chain "bid/ask" matching engine analogous to the auction contract's bid mechanism.

### Title
Missing self-trade check in MarketSellAssetActuator causes silent loss of matched funds - (`actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java`)

### Summary
`MarketSellAssetActuator` lets any account place a market order that is matched against existing resting orders in the order book. Unlike the reported Auction contract, which (after the fix) rejects `prevBidder == param.bidder`, `MarketSellAssetActuator` never checks whether the taker (the caller) is also the owner of the maker order it matches against. Because the taker's and maker's `AccountCapsule` are handled through two different in-memory objects with a stale-read/last-write-wins pattern, a self-match silently discards one side's credit, permanently destroying the matched token amount for the caller.

### Finding Description
In `execute()`, the taker's `AccountCapsule` is loaded once, mutated in-memory across the whole call, and persisted only at the very end: [1](#0-0) 

During matching, `matchSingleOrder` credits the taker's in-memory object via `addTrxOrToken(takerOrderCapsule, ..., takerAccountCapsule)`, but credits the *maker* side via a separate overload that re-reads the maker's account fresh from the store and writes it back immediately: [2](#0-1) [3](#0-2) 

There is no check anywhere in `doValidate()` or in `matchOrder`/`matchSingleOrder` comparing the taker's owner address to the maker order's owner address (`orderCapsule.getOwnerAddress()`), so a user is free to match against their own resting order — the exact self-bid/self-trade omission described in the report: [4](#0-3) 

When the maker and taker are the same account, the maker-side write in `addTrxOrToken(makerOrderCapsule, num)` (line 561, `accountStore.put(orderCapsule.getOwnerAddress().toByteArray(), accountCapsule)`) writes a stale copy of the account (read before the taker-side fee/asset deductions were persisted) back to the store. This write is then unconditionally overwritten by the final `accountStore.put(accountCapsule.createDbKey(), accountCapsule)` in `execute()` (line 148), which holds the taker's in-memory object. The taker's in-memory object never received the `makerBuyTokenQuantityReceive` credit that was applied only to the discarded maker-side copy, so that token amount is silently lost from the user's balance/asset map — a real, on-chain, permanent loss of funds for the same account, entirely reachable by a single unprivileged `MarketSellAssetContract` transaction.

### Impact Explanation
This results in permanent, non-recoverable loss of a user's own TRX/TRC10 balance (the credited leg of a self-match is dropped on every self-trade), i.e., an unbacked/incorrect account balance versus the actual token supply escrowed by the market module — a fund-safety defect matching the "permanent freezing/loss of funds" and "unbacked balance" bar. It also breaks the invariant that total balances of tokens moved into escrow by `transferBalanceOrToken` must be fully returned across a match.

### Likelihood Explanation
Trivial to trigger: any account can place a maker sell order via `MarketSellAssetContract`, then place a matching opposite order from the same account. No special privilege, timing, or race condition beyond ordinary contract calls is required — it is fully deterministic given the code path shown above.

### Recommendation
Add an explicit check in `doValidate()` (or in `matchOrder`/`matchSingleOrder`) rejecting matches where the maker order's owner address equals the taker's owner address, mirroring the Auction fix's `prevBidder == param.bidder` check. Additionally/alternatively, fix the underlying stale-read/overwrite pattern by loading and mutating a single shared `AccountCapsule` per address within a match cycle, deferring all `accountStore.put` calls to the end of `execute()`.

### Proof of Concept
1. Account A funds itself with `TOKEN_A` and `TOKEN_B`.
2. Account A calls `MarketSellAssetContract` selling `TOKEN_A` for `TOKEN_B` at some price — this becomes a resting maker order in the order book (`pairPriceToOrderStore`).
3. Account A calls `MarketSellAssetContract` again from the same address, selling `TOKEN_B` for `TOKEN_A` at a matching price.
4. `matchOrder`/`matchSingleOrder` matches the second (taker) order against A's own first (maker) order with no self-trade check.
5. `addTrxOrToken(makerOrderCapsule, makerBuyTokenQuantityReceive)` re-reads A's account, credits `TOKEN_A` (or `TOKEN_B`), and writes it to the store — but this write is subsequently overwritten by `execute()`'s final `accountStore.put` of the taker's in-memory `AccountCapsule`, which never received that credit.
6. Result: Account A's `TOKEN_A`/`TOKEN_B` balance decreases by the escrowed amount from step 2/3 without receiving the corresponding match credit — a permanent loss of tokens with no compensating benefit to any other party.

  private void matchOrder(MarketOrderCapsule takerCapsule, MarketPrice takerPrice,
      TransactionResultCapsule ret, AccountCapsule takerAccountCapsule)
      throws ItemNotFoundException, ContractValidateException {

    byte[] makerSellTokenID = buyTokenID;
    byte[] makerBuyTokenID = sellTokenID;
    byte[] makerPair = MarketUtils.createPairKey(makerSellTokenID, makerBuyTokenID);

    // makerPair not exists
    long makerPriceNumber = pairToPriceStore.getPriceNum(makerPair);
    if (makerPriceNumber == 0) {
      return;
    }
    long remainCount = makerPriceNumber;

    // get maker price list
    List<byte[]> priceKeysList = pairPriceToOrderStore
        .getPriceKeysList(MarketUtils.getPairPriceHeadKey(makerSellTokenID, makerBuyTokenID),
            (long) (MAX_MATCH_NUM + 1), makerPriceNumber, true);

    int matchOrderCount = 0;
    // match different price
    while (takerCapsule.getSellTokenQuantityRemain() != 0) {
      // get lowest ordersList
      MarketPrice makerPrice = hasMatch(priceKeysList, takerPrice);
      if (makerPrice == null) {
        return;
      }

      byte[] pairPriceKey = priceKeysList.get(0);

      // if not exists
      MarketOrderIdListCapsule orderIdListCapsule = pairPriceToOrderStore.get(pairPriceKey);

      // match different orders which have the same price
      while (takerCapsule.getSellTokenQuantityRemain() != 0
          && !orderIdListCapsule.isOrderEmpty()) {
        byte[] orderId = orderIdListCapsule.getHead();
        MarketOrderCapsule makerOrderCapsule = orderStore.get(orderId);

        matchSingleOrder(takerCapsule, makerOrderCapsule, ret, takerAccountCapsule);

        // remove order
        if (makerOrderCapsule.getSellTokenQuantityRemain() == 0) {
          // remove from market order list
          orderIdListCapsule.removeOrder(makerOrderCapsule, orderStore,
              pairPriceKey, pairPriceToOrderStore);
        }

        matchOrderCount++;
        if (matchOrderCount > MAX_MATCH_NUM) {
          throw new ContractValidateException("Too many matches. MAX_MATCH_NUM = " + MAX_MATCH_NUM);
        }
      }

      // the orders of makerPrice have been all consumed
      if (orderIdListCapsule.isOrderEmpty()) {
        pairPriceToOrderStore.delete(pairPriceKey);

        // need to delete marketPair if no more price(priceKeysList is empty after deleting)
        priceKeysList.remove(0);

        // update priceInfo's count
        remainCount = remainCount - 1;
        // if really empty, need to delete token pair from pairToPriceStore
        if (remainCount == 0) {
          pairToPriceStore.delete(makerPair);
          break;
        } else {
          pairToPriceStore.setPriceNum(makerPair, remainCount);
        }
      }
    } // end while
  }
