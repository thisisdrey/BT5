### Title
`RecurringAirdrop.claim` has no validity/deadline parameter — claimed `MET` can be delivered as time-locked `esMET` when the execution timestamp lands on the other side of the lock-expiry boundary than the simulation - (File: contracts/MetAirdrop.sol)

### Summary
`RecurringAirdrop.claim` accepts only `amount_` and `proof_` — there is no `deadline`, `validUntil`, or expected-outcome parameter. The reward delivery path in `MetAirdrop._transferReward` branches on `block.timestamp` relative to `updatedAt + lockPeriod`. A claim simulated as returning liquid `MET` can execute in a block whose timestamp falls just before the boundary, instead locking the tokens into `esMET` for a non-zero remaining lock period — a simulation-vs-execution divergence the caller cannot guard against on-chain.

### Finding Description
`claim` verifies the Merkle proof and delegates payout to `_transferReward` [1](#0-0) . The override decides the delivery mode purely from `block.timestamp`:

- If `updatedAt + lockPeriod < block.timestamp`, the user receives liquid `MET` [2](#0-1) .
- Otherwise the claimed `MET` is approved and locked via `ESMET.lockFor(to_, amount_, _remainLockPeriod)`, where `_remainLockPeriod` is clamped to at least `ESMET.MINIMUM_LOCK_PERIOD() + 1` [3](#0-2) .

Unlike `SmartFarmingManager.leverage`/`flashRepay`, which carry user-supplied slippage bounds (`depositAmountMin_`, `swapAmountOutMin_`) plus a post-execution health check [4](#0-3) , `claim` exposes no parameter letting the caller assert "revert if this would lock my tokens" or "revert after timestamp T". Because `updatedAt` is refreshed on every root update [5](#0-4) , the boundary moves, widening the window where simulation and execution disagree.

### Impact Explanation
A user simulating `claim` at a timestamp past `updatedAt + lockPeriod` expects a liquid `MET` transfer. If the transaction is mined in an earlier timestamp (or the root was just updated, resetting `updatedAt`), the full claimed amount is instead locked into `esMET` for up to `MAXIMUM_LOCK_PERIOD` — a temporary freezing of the user's claimed funds with no way to revert or specify the intended outcome. This is the same class as the referenced issue: no on-chain check ties the execution-time environment to the simulated one, and the contract silently produces a materially different result.

### Likelihood Explanation
Medium-low. It requires the claim to be submitted around the lock-expiry boundary or immediately after a `updateMerkleRoot` call. `updateMerkleRoot` is governor-called and resets `updatedAt` to `block.timestamp`, so any claim simulated under the old schedule and mined after a root update will lock tokens for the full `lockPeriod` again — not attacker-dependent, but a realistic operational race since root updates recur by design. No unprivileged attacker is required; the trigger is ordinary transaction timing.

### Recommendation
Add an explicit validity/outcome assertion to `claim`, e.g. a `deadline_` parameter (`if (block.timestamp > deadline_) revert Expired()`) and/or a `receiveLocked_`/`minLockEnd_` flag so the caller can force revert instead of accepting an unexpected `esMET` lock. Alternatively, document and expose a view (`claimOutcomePreview`) returning whether the current block would lock, and have `claim` take the expected mode as an argument.

### Proof of Concept
Hardhat sketch against `MetAirdrop`:

```ts
// setup: governor sets merkleRoot; updatedAt = t0; lockPeriod = 7 days
await airdrop.updateMerkleRoot(root, proofsFileHash);

// simulate claim at t0 + lockPeriod + 1 -> staticcall returns liquid MET path
await ethers.provider.send('evm_setNextBlockTimestamp', [t0 + lockPeriod + 1]);
const preview = await airdrop.callStatic.claim(amount, proof); // would take safeTransfer branch

// real tx mines one second earlier than simulated (boundary race)
await ethers.provider.send('evm_setNextBlockTimestamp', [t0 + lockPeriod]); // _end == ts -> else branch
await airdrop.connect(alice).claim(amount, proof);

// assert: alice holds 0 MET and an esMET position locked for >= MINIMUM_LOCK_PERIOD + 1
expect(await MET.balanceOf(alice.address)).to.eq(0);
// esMET lockFor was called with _remainLockPeriod >= MINIMUM_LOCK_PERIOD + 1
```

Same divergence occurs without timestamp manipulation: front-run a `claim` with `updateMerkleRoot` (or simply have the claim mine after it) — the new `updatedAt` resets the window and the user's reward is locked for a fresh `lockPeriod` despite the simulation showing the unlocked path.

    function claim(uint256 amount_, bytes32[] calldata proof_) external nonReentrant {
        if (merkleRoot == bytes32(0)) revert NothingToClaim();

        bytes32 _leaf = keccak256(abi.encodePacked(msg.sender, amount_));
        if (!MerkleProof.verify(proof_, merkleRoot, _leaf)) revert InvalidProof();

        uint256 _claimable = amount_ - claimed[msg.sender];
        if (_claimable == 0) revert NothingToClaim();

        claimed[msg.sender] += _claimable;

        _transferReward(msg.sender, _claimable);

        emit RewardClaimed(msg.sender, _claimable);
    }

    function updateMerkleRoot(bytes32 merkleRoot_, bytes32 proofsFileHash_) external onlyGovernor {
        if (merkleRoot_ == merkleRoot) revert NewMerkleRootSameAsCurrent();
        if (proofsFileHash_ == bytes32(0)) revert ProofsFileIsNull();

        merkleRoot = merkleRoot_;
        updatedAt = block.timestamp;
        proofsFileHash = proofsFileHash_;

        emit MerkleRootUpdated(merkleRoot_, block.timestamp);
