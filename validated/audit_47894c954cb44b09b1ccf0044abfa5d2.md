### Title
StackerDB chunk signature is not bound to the target contract, enabling cross-DB replay of an unauthenticated `POST /v2/stackerdb/.../chunks` write - (File: `libstackerdb/src/libstackerdb.rs`)

### Summary
`SlotMetadata::auth_digest()` computes the signed digest as `hash(slot_id || slot_version || data_hash)`, omitting the StackerDB smart-contract identifier that the chunk is being written into. Because the HTTP write endpoint (`/v2/stackerdb/:address/:contract/chunks`) is completely unauthenticated and accepts a bare `StackerDBChunkData` (signature only over slot metadata, no contract binding), a chunk validly signed by a signer for one StackerDB replica (e.g. one reward-cycle's `signers-0-N` contract) can be captured off the wire/gossip and replayed as-is against a *different* StackerDB contract (e.g. `signers-1-N`, or a different reward-cycle's contract) whose slot table happens to assign the same signer address to the same `slot_id`. This is the direct analog of the reported permit-replay-across-pools bug: an authentication artifact scoped to one context (token/pool vs. here, slot+version+hash) is silently accepted as valid for a different context (pool vs. here, StackerDB contract) because the identifying/contextual field is not part of the signed message.

### Finding Description
- The digest that gets signed for a chunk write is defined in `SlotMetadata::auth_digest()`: [1](#0-0) 
It hashes only `slot_id`, `slot_version`, and `data_hash`. The `QualifiedContractIdentifier` of the StackerDB instance the chunk belongs to never enters the signed payload.

- `SlotMetadata::verify()` / `StackerDBChunkData::verify()` therefore only prove "this signer authorized (slot_id, slot_version, data_hash)" — never "this signer authorized this specific contract/replica": [2](#0-1) 

- The write path, `StackerDBTx::try_replace_chunk`, takes the target `smart_contract` purely to look up the expected signer for that DB's `slot_id`, and then calls `slot_desc.verify(&slot_validation.signer)` — the contract identity is used only for lookup, not folded into what was actually signed: [3](#0-2) 

- The HTTP handler is reachable by anyone (no session/auth check beyond a well-formed body), decodes the contract identifier purely from the URL path, and forwards the client-supplied chunk straight to `try_replace_chunk`: [4](#0-3) 
There is no check that the signature was produced with knowledge of, or intent to write to, *this* `contract_identifier`.

- The same unbound digest is reused for gossip-received chunks in `validate_received_chunk`, which is used both for solicited chunk downloads and unsolicited `StackerDBPushChunk` messages: [5](#0-4) 

- Signer StackerDB contracts are deployed per message-round/reward-cycle (`signers-0-xxx.clar`, `signers-1-xxx.clar`), and slot assignment to a signer's address is derived by the signer set for that cycle — a signer that is active across cycles/rounds can plausibly retain the same `slot_id` in multiple sibling contracts (e.g., round-0 and round-1 replicas for the same or adjacent reward cycles), since slot assignment is purely a function of stake-sorted registration order, which is often stable between adjacent cycles/rounds.

### Impact Explanation
If a signer's slot in the target contract has a stored `slot_version` lower than the version in an intercepted chunk (a very common situation for a freshly-instantiated sibling contract, whose slots start at version 0), the replayed chunk passes every check in `try_replace_chunk` (chunk size, correct signer for that slot, version freshness, max-writes) and is committed as if the signer had authorized writing that exact data into that specific StackerDB instance. This is an unauthorized write to StackerDB state: data the signer only signed for context A now appears as authoritative signer output under context B. Since these StackerDBs carry consensus-relevant signer coordination messages (block responses, DKG/vote data) consumed by miners and other signers, cross-contract replay can corrupt or spoof what other participants read as "the signer's message for this round/cycle," which maps to the rules' High-impact category of serving non-canonical/mismatched data as canonical. It also triggers automatic re-broadcast: on a successful accept the node relays it network-wide via `StackerDBPushChunk`: [6](#0-5) 
propagating the misattributed/forged-context chunk to the whole network.

### Likelihood Explanation
The write endpoint requires no authentication beyond a well-formed `StackerDBChunkData` body, and chunks are also visible in p2p gossip (`StackerDBPushChunkData`) — an attacker only needs to observe one valid chunk (from HTTP traffic or gossip) and resubmit it against a sibling contract URL/path. The main precondition is that the same signer address is assigned the same `slot_id` in the sibling contract with a lower stored version, which is plausible given how signer slot assignment works across adjacent reward cycles/rounds, but is not proven deterministic from the available code — the exact slot-assignment algorithm in `signer_set.rs` was not fully confirmed within the tool budget. Likelihood is therefore assessed as plausible/likely under realistic signer-set continuity, but not certain in all deployments.

### Recommendation
Bind the signed digest to the specific StackerDB instance by including the `QualifiedContractIdentifier` (or a stable per-instance identifier, e.g. hash of contract issuer+name plus reward cycle) inside `SlotMetadata::auth_digest()`, mirroring the recommended fix for the original finding (bind the permit to the specific pool). Concretely, change:
```rust
fn auth_digest(&self) -> Sha512Trunc256Sum {
    let mut hasher = Sha512_256::new();
    hasher.update(self.slot_id.to_be_bytes());
    hasher.update(self.slot_version.to_be_bytes());
    hasher.update(self.data_hash.0);
    Sha512Trunc256Sum::from_hasher(hasher)
}
```
to also hash the contract identifier bytes, and update `sign`/`verify` call sites (`try_replace_chunk`, `validate_received_chunk`) to pass in and mix the `smart_contract` parameter, so a signature is cryptographically scoped to one StackerDB replica and cannot be replayed into another.

### Proof of Concept
1. Signer `S` (address `A`) is assigned `slot_id = 3` in StackerDB contract `signers-0-5` (reward cycle 5, round 0) and also happens to be assigned `slot_id = 3` in `signers-1-5` (round 1) — plausible since slot ordering is derived from the same stake-sorted signer set.
2. `S` legitimately signs and POSTs a chunk to `signers-0-5` at slot 3, version 1: `StackerDBChunkData{slot_id:3, slot_version:1, sig, data}`. Node A accepts it (`try_replace_chunk` succeeds) and rebroadcasts it via `StackerDBPushChunk`.
3. Attacker observes this chunk (HTTP response/log, or p2p `StackerDBPushChunk` gossip) and POSTs the *same* `(slot_id, slot_version, sig, data)` tuple to `/v2/stackerdb/<A>/signers-1-5/chunks`.
4. On the node's replica for `signers-1-5`, slot 3's current stored version is 0 (fresh contract) and its assigned signer is also `A`. `try_replace_chunk` computes `slot_desc.verify(&slot_validation.signer)`, which succeeds because the digest never included the contract name — it validates purely on `(slot_id=3, slot_version=1, data_hash)`, satisfied by the replayed signature.
5. The chunk is committed into `signers-1-5`'s state store and re-broadcast network-wide as authoritative signer data for round 1 of cycle 5, even though `S` never signed anything for that contract/context. [1](#0-0) [7](#0-6) [8](#0-7)
