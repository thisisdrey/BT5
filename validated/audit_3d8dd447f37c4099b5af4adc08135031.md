### Title
Full-repack cooldown timestamp is written before the repack succeeds, letting a failed/aborted full repack silently disable pruning of unreachable objects for 5 days - (File: internal/git/housekeeping/objects.go)

### Summary
`RepackObjects` writes the `.gitaly-full-repack-timestamp` marker via `stats.UpdateFullRepackTimestamp` *before* actually running the full repack, and the code comment openly documents that "even if the full repack fails, we would still pretend to have done it." [1](#0-0)  Since `HeuristicalOptimizationStrategy.ShouldRepackObjects` gates the next full repack behind `FullRepackCooldownPeriod` (5 days) measured from that same timestamp, any full repack that fails partway through (for example due to a crafted/oversized push that trips up `git-repack`, disk pressure, or a killed housekeeping goroutine) leaves the repository believing a full repack "happened" even though objects were never consolidated/pruned. [2](#0-1) [3](#0-2) 

### Finding Description
This is the same bug class as the reported vesting issue: an operation that only partially completes (or fully fails) nonetheless advances a "last completed" checkpoint that gates when the operation may run again, silently extending the effective lockout/DoS window well beyond a single cycle.

In gitaly, `RepackObjects` is called from `repackIfNeeded` as part of `RepositoryManager.optimizeRepository`/`optimizeRepositoryWithTransaction`, which is triggered:
- Explicitly via the `OptimizeRepository` RPC.
- Automatically after ordinary mutator RPCs (e.g. `WriteRef`, and virtually any push-triggering RPC) via `HousekeepingMiddleware.scheduleHousekeeping`, which calls `m.manager.OptimizeRepository` in the background after the handler completes. [4](#0-3) 

Inside `RepackObjects`, when a full repack is chosen, the timestamp file is updated first, and the actual `git-repack` invocation (`PerformRepack`/`PerformFullRepackingWithUnreachable`) happens afterward: [5](#0-4) 

```go
if isFullRepack {
    // Note that we write the file _before_ actually writing the new pack, which means
    // that even if the full repack fails, we would still pretend to have done it. ...
    if err := stats.UpdateFullRepackTimestamp(repoPath, time.Now()); err != nil {
        return fmt.Errorf("updating full-repack timestamp: %w", err)
    }
}
```

If the subsequent `git-repack` invocation fails or is interrupted (context cancellation from the middleware shutdown path, disk exhaustion from a large/crafted push, or a git-repack crash on pathological input), the timestamp has already been advanced. `HeuristicalOptimizationStrategy.ShouldRepackObjects` reads `Packfiles.LastFullRepack` and will refuse to schedule another full repack until `FullRepackCooldownPeriod` (5 days) has elapsed. [6](#0-5)  Because full repacks are the only path that evicts unreachable objects into (and later expires) the cruft pack, a repeatedly-failed full repack effectively parks all of that repository's unreachable/duplicate object data on disk for the full cooldown window, exactly mirroring the reported bug's pattern of a partial/failed "claim" resetting a time-gated checkpoint as if it fully succeeded.

### Impact Explanation
An attacker who can push to a repository (an ordinary, unprivileged Git user) can attempt to make full repacks fail repeatedly (e.g., by crafting pathological ref/object graphs, filling the storage volume, or otherwise causing `git-repack` to error) while relying on automatic post-push housekeeping to keep re-attempting and re-arming the 5-day cooldown. Each failed attempt still marks the repository as "recently fully repacked," suppressing further attempts to reclaim disk via cruft/pruning for up to 5 days at a time. Repeated over time, this can be used to keep a repository's on-disk footprint permanently bloated with unreachable objects, a storage-exhaustion DoS vector against the storage backend, without requiring any privileged actor.

### Likelihood Explanation
Reachability is high: the housekeeping middleware runs `OptimizeRepository` automatically after ordinary mutator RPCs from any authenticated Git user with push access, requiring no special privilege. Making the underlying `git-repack` fail deterministically (rather than merely being slow) requires some effort (e.g. disk-pressure timing or pathological object shapes), but the code path and consequence — the timestamp being intentionally written before success is known — is explicit and confirmed by the accompanying comment in the source.

### Recommendation
Only update `FullRepackTimestampFilename` after `RepackObjects` has confirmed that the full repack actually completed successfully (or track failures with a bounded/backoff cooldown that is shorter than the full success cooldown), so that a failing repack does not silently disable pruning/cruft-eviction for the full `FullRepackCooldownPeriod`. If the intent is specifically to avoid busy-spinning on huge repositories, consider a separate, shorter "failure backoff" timestamp distinct from the "last successful full repack" timestamp so failure and success cases are not conflated.

### Proof of Concept
1. Push commits to a repository until the heuristic strategy decides a full repack is due (multiple non-cruft packfiles, cooldown expired).
2. Cause the triggered `git-repack` to fail (e.g., exhaust disk space on the storage backend, or supply a repository shape that crashes/errors `git-repack` during the full repack strategy) while it runs as part of the automatic post-push housekeeping triggered by `HousekeepingMiddleware.scheduleHousekeeping`.
3. Observe that `.gitaly-full-repack-timestamp` in the repository's Git directory was updated to "now" despite `RepackObjects` returning an error.
4. Confirm via `HeuristicalOptimizationStrategy.ShouldRepackObjects` (or by re-issuing pushes) that no further full repack is scheduled for the repository until `FullRepackCooldownPeriod` (5 days) has elapsed from that timestamp, even though no full repack ever actually completed.

// RepackObjects repacks objects in the given repository and updates the commit-graph. The way
// objects are repacked is determined via the config.RepackObjectsConfig.
func RepackObjects(ctx context.Context, repo *localrepo.Repo, cfg config.RepackObjectsConfig) error {
	repoPath, err := repo.Path(ctx)
	if err != nil {
		return err
	}
	isFullRepack, err := ValidateRepacking(cfg)
	if err != nil {
		return err
	}

	if isFullRepack {
		// When we have performed a full repack we're updating the "full-repack-timestamp"
		// file. This is done so that we can tell when we have last performed a full repack
		// in a repository. This information can be used by our heuristics to effectively
		// rate-limit the frequency of full repacks.
		//
		// Note that we write the file _before_ actually writing the new pack, which means
		// that even if the full repack fails, we would still pretend to have done it. This
		// is done intentionally, as the likelihood for huge repositories to fail during a
		// full repack is comparatively high. So if we didn't update the timestamp in case
		// of a failure we'd potentially busy-spin trying to do a full repack.
		if err := stats.UpdateFullRepackTimestamp(repoPath, time.Now()); err != nil {
			return fmt.Errorf("updating full-repack timestamp: %w", err)
		}
	}

func (m *Middleware) scheduleHousekeeping(ctx context.Context, repo *gitalypb.Repository, force bool) {
	m.mu.Lock()
	defer m.mu.Unlock()

	key := m.getRepoKey(repo)

	a, ok := m.repoActivity[key]
	if !ok {
		a = newActivity()
		m.repoActivity[key] = a
	}
	a.writeCount++

	if a.active {
		return
	}

	pendingOps := m.pendingOperations(a, force)
	if len(pendingOps) == 0 {
		return
	}

	m.logger.WithFields(log.Fields{
		"forced":     force,
		"operations": pendingOps,
	}).InfoContext(ctx, "beginning scheduled housekeeping")

	// Mark that these operations are running at the current write count
	for _, op := range pendingOps {
		a.writeCountAtLastRun[op] = a.writeCount
	}

	m.markHousekeepingActive(key)

	m.wg.Add(1)
	go func() {
		// We need to call OptimizeRepository with a child context that's disowned from the parent's
		// cancellation signals we're executing it asynchronously. Providing the existing `ctx` would
		// cause it to fail, since `ctx` would be cancelled when this request completes. We still want
		// to be able to abort the worker when the middleware shuts down though, so we propagate
		// cancellation from the middleware's shutdown context.
		housekeepingCtx, housekeepingCancel := context.WithCancel(context.WithoutCancel(ctx))
		stopShutdownPropagation := context.AfterFunc(m.shutdownCtx, housekeepingCancel)

		defer func() {
			stopShutdownPropagation()
			m.markHousekeepingInactive(key)
			m.logger.InfoContext(housekeepingCtx, "ended scheduled housekeeping")
			housekeepingCancel()
			m.wg.Done()
		}()

		localRepo := m.localRepoFactory.Build(repo)
		if err := m.manager.OptimizeRepository(housekeepingCtx, localRepo,
			manager.WithOptimizationStrategyConstructor(
				func(info stats.RepositoryInfo) housekeeping.OptimizationStrategy {
					return housekeeping.NewSelectiveOptimizationStrategy(info, pendingOps)
				},
			),
			manager.WithMVCCGarbageCollection(),
		); err != nil {
			m.logger.WithError(err).ErrorContext(housekeepingCtx, "failed scheduled housekeeping")
		}
	}()
