### Title
TRC10 Exchange creator can front-run pending `ExchangeTransactionContract` swaps via unbounded `ExchangeInjectContract`/`ExchangeWithdrawContract` to steal user funds - ([File: actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java])

### Summary
Analogous to the Catalyst report, where a privileged "fee administrator" can front-run a pending `localSwap()` call and change the fee to 100% to steal the full amount of an unsuspecting user's swap (since `minOut` is often left at its default of zero/near-zero), java-tron's bancor-style TRC10 exchange has a privileged role — the exchange creator — who can front-run a pending `ExchangeTransactionContract` (a swap) with an `ExchangeInjectContract` or `ExchangeWithdrawContract` to dramatically distort the reserve ratio right before the swap executes, then revert it afterward, extracting nearly all of the swapping user's value.

### Finding Description
`ExchangeTransactionActuator` does have an `expected` (minOut) field, unlike Catalyst's `localSwap()`, but it only guards against the *taker's stated* minimum, which is commonly set to a minimal/non-protective value by unsophisticated users/wallets (exactly the "many users tend to not set minOut values" pattern called out in the report). The check is purely `anotherTokenQuant < tokenExpected` at execution time: [1](#0-0) 

The exchange's reserve balances (`firstTokenBalance`/`secondTokenBalance`), which directly determine the bonding-curve price used by `exchangeCapsule.transaction(...)`, can be adjusted at will by the exchange's creator via `ExchangeInjectContract` and `ExchangeWithdrawContract`, restricted only to `accountCapsule.getAddress().equals(exchangeCapsule.getCreatorAddress())`: [2](#0-1) [3](#0-2) 

Crucially, `ExchangeInjectContract`/`ExchangeWithdrawContract` have no analogous `expected`/slippage-protection field at all, and there is no timelock or cooldown between reserve changes and swaps: [4](#0-3) 

This mirrors the root cause in the Catalyst report exactly: a privileged actor (fee admin ↔ exchange creator) controls a parameter (fee ↔ reserve ratio) that determines swap output, can change it atomically in the same block window immediately before a victim's pending transaction executes, and revert it immediately after, while the victim's own slippage protection (`minOut`/`expected`) is commonly set too loosely to prevent the loss.

### Impact Explanation
A user submitting `ExchangeTransactionContract` with a low/default `expected` value can have the exchange creator sandwich the transaction: withdraw nearly all of the counter-token reserve via `ExchangeWithdrawContract` immediately before the victim's transaction is packed into a block, causing `exchangeCapsule.transaction()` to return a near-zero `anotherTokenQuant` (still passing the loose `expected` check), then inject the reserves back via `ExchangeInjectContract` afterward. The victim's sold tokens/TRX are absorbed into the exchange, and the creator (who fully controls the exchange's reserves) effectively steals the swapped value. This is concrete unauthorized theft of user funds reachable purely from a broadcastable transaction sequence (`ExchangeWithdrawContract` → victim's `ExchangeTransactionContract` → `ExchangeInjectContract`), requiring no consensus-level or witness privilege — only the ability to be the creator of a TRC10 exchange, which is permissionless (any account can create one via `ExchangeCreateContract`).

### Likelihood Explanation
Likelihood is Medium: it requires the attacker to be the creator of the specific exchange the victim trades against (achievable trivially since exchange creation is permissionless and the attacker can create the exchange the victim is lured to use, or already control an existing popular exchange), and requires transaction-ordering control within a block, which any broadcaster can attempt by submitting inject/withdraw transactions with equal or higher priority around the victim's transaction. Unlike the committee/witness-controlled paths excluded by scope, this is entirely achievable by a single account holder without any special node or consensus privileges.

### Recommendation
- Require `ExchangeInjectContract`/`ExchangeWithdrawContract` to be validated against the same-block state consistently and consider adding minimum/maximum output guarantees or a cooldown period between reserve changes and swap execution against the same exchange.
- Consider enforcing a stricter/non-zero minimum `expected` value in `ExchangeTransactionActuator`, or clearly warn integrators/wallets that `expected=1`/minimal values provide no real slippage protection.
- Consider disallowing exchange reserve changes (`inject`/`withdraw`) within the same block as pending transactions against that exchange, or introducing a time-weighted price mechanism resistant to atomic single-block manipulation.

### Proof of Concept
1. Attacker creates a TRC10 exchange pair (A/TRX) via `ExchangeCreateContract`, becoming its creator.
2. Victim broadcasts `ExchangeTransactionContract` to sell TRX for token A, setting `expected=1` (a minimal/default value as commonly done, per the "users tend to not set minOut" pattern).
3. Attacker broadcasts `ExchangeWithdrawContract` withdrawing nearly all of the exchange's token-A reserve just before the victim's transaction is included in the same block (validated in `ExchangeWithdrawActuator.execute`) — see reserve mutation logic at [5](#0-4) .
4. Victim's `ExchangeTransactionContract` executes against the now-depleted reserve, computing a near-zero `anotherTokenQuant`, which still satisfies `anotherTokenQuant < tokenExpected` being false (since `tokenExpected=1`) at [1](#0-0) , so the swap succeeds with the victim receiving almost nothing.
5. Attacker broadcasts `ExchangeInjectContract` to restore the reserves, and the sold TRX from the victim remains captured by the exchange, now redeemable/controlled by the creator.
