Audit Report

## Title
`process_delivery_receipt` pays relayer rewards and closes `PendingOrder` regardless of the Ethereum-side execution outcome (`success` field is decoded but never checked) - ([File: bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs])

## Summary
`snowbridge-pallet-outbound-queue-v2::process_delivery_receipt` decodes a `DeliveryReceipt` containing a `success: bool` field from the Ethereum `InboundMessageDispatched` event but never inspects it before calling `T::RewardPayment::register_reward` and removing the `PendingOrder`. A grep across the entire pallet confirms `success` is never referenced anywhere in the pallet's business logic, only in the primitive decode struct.

## Finding Description
The Solidity event and decode struct both carry `success`: [1](#0-0)  and the `TryFrom<&Log>` impl faithfully decodes it into `DeliveryReceipt.success`: [2](#0-1) .

`submit_delivery_receipt` verifies the event log proof and decodes the receipt, then forwards it unconditionally to `process_delivery_receipt`: [3](#0-2) .

`process_delivery_receipt` only checks `receipt.gateway` against `T::GatewayAddress` and that a `PendingOrder` exists for `receipt.nonce`; it never reads `receipt.success` before unconditionally calling `T::RewardPayment::register_reward` (when `order.fee > 0`) and removing the order via `<PendingOrders<T>>::remove(nonce)`: [4](#0-3) .

`T::Verifier::verify` only proves the log was genuinely emitted by the Gateway contract in a finalized Ethereum block — it makes no assertion about the semantic value of `success` inside the log. A genuine `InboundMessageDispatched(nonce, topic, success=false, reward_address)` event, which the real Gateway contract legitimately emits whenever the destination-side dispatch reverts, will pass verification and decoding identically to a `success=true` event, and will still fully reward the relayer and close the order.

## Impact Explanation
This breaks the invariant that reward payout and order settlement should only occur upon actual successful delivery. Relayers are paid, and the pallet's `PendingOrders` state is finalized as "delivered," for messages that failed execution on Ethereum. This is an incorrect-settlement/payout bug (duplicate/incorrect beneficiary-or-amount settlement) in a live-scope Snowbridge BridgeHub pallet, matching the "duplicate settlement or payout" and "message queues/receipts/payout state must only advance after decode, dispatch, execution, and settlement succeed atomically" pivot in the impact gate.

## Likelihood Explanation
No privileged actor or compromised relayer/prover assumption is needed. A `success=false` event is a normal, expected output of the real Gateway contract when destination execution reverts (e.g., insufficient gas, downstream revert). Any relayer submitting a standard, valid `submit_delivery_receipt` proof for such a legitimately emitted event triggers the erroneous unconditional payout/settlement path — this is reproducible on every occurrence of a failed dispatch on Ethereum, not a rare edge case.

## Recommendation
In `process_delivery_receipt`, branch on `receipt.success`:
- If `true`, proceed with reward payment and remove the order as done today.
- If `false`, skip (or penalize) the reward payment, and either retain the `PendingOrder` for a future correct receipt, mark it explicitly as failed, or implement refund/retry logic — do not treat a failed delivery identically to a successful one.

## Proof of Concept
1. Ethereum Gateway contract emits `InboundMessageDispatched(nonce=N, topic, success=false, reward_address=R)` because the destination-side command execution reverted.
2. A relayer builds a valid `EventProof` for this real log (receipt inclusion + beacon finality proof — all genuinely valid).
3. Relayer calls `submit_delivery_receipt(origin, event)`.
4. `T::Verifier::verify` succeeds (log is genuinely included and finalized) at [5](#0-4) .
5. `DeliveryReceipt::try_from` decodes `success: false` correctly at [6](#0-5) .
6. `process_delivery_receipt` ignores `success`, finds `PendingOrders::get(N)`, sees `order.fee > 0`, calls `T::RewardPayment::register_reward` and removes the order, emitting `MessageDelivered { nonce: N }` — even though the message delivery failed on Ethereum, at [7](#0-6) .
7. This can be reproduced by modifying the existing pallet test suite (`bridges/snowbridge/pallets/outbound-queue-v2/src/test.rs`) to construct a mock event log with `success: false` and asserting that `RewardPayment::register_reward` still fires and `PendingOrders` is still cleared.

		/// Process a delivery receipt from a relayer, to allocate the relayer reward.
		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}
