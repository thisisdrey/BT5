### Title
Inconsistent reward-pricing formula between TVM vote-reward path and native reward path causes incorrect/lost withdrawals - (File: `actuator/src/main/java/org/tron/core/vm/utils/VoteRewardUtil.java`)

### Summary
`VoteRewardUtil.computeReward`, which is reached from any TVM smart-contract call to `withdrawReward()`/`rewardBalance()`/`voteWitness()`, always prices historical vote rewards using the "new algorithm" (delta-Vi, `BigInteger`) formula, regardless of whether the cycles being paid out predate the network's `NEW_REWARD_ALGORITHM_EFFECTIVE_CYCLE`. The native reward path, `MortgageService.computeReward`, instead splits the computation: cycles before the effective cycle are priced with the legacy per-cycle `double` `voteRate * totalReward` formula (unless `allowOldRewardOpt` is enabled, in which case it defers to the same Vi-backed value). Because two different formulas can be used for the same cycle range depending on which contract path a user goes through, the resulting reward/allowance amount is inconsistent between the TVM path and the native path.

### Finding Description
`VoteRewardUtil.computeReward` unconditionally computes reward strictly from `DelegationStore`'s Vi values: [1](#0-0) 

By contrast, the native `MortgageService.computeReward(beginCycle, endCycle, accountCapsule)` explicitly forks on `getNewRewardAlgorithmEffectiveCycle()`: cycles before the threshold go through `getOldReward`, which — unless `allowOldRewardOpt()` is on — computes the *legacy* per-cycle `double` ratio formula (`voteRate = (double) userVote / totalVote; reward += voteRate * totalReward;`) instead of the Vi-based `BigInteger` delta formula used for post-threshold cycles: [2](#0-1) [3](#0-2) [4](#0-3) 

`VoteRewardUtil.withdrawReward` is directly reachable by any unprivileged transaction that calls a deployed contract executing the `WITHDRAWREWARD`/`VOTEWITNESS` opcodes, or via `UnfreezeBalanceProcessor`/`UnfreezeBalanceV2Processor` when clearing votes, or via the `RewardBalance` precompile for queries: [5](#0-4) [6](#0-5) [7](#0-6) [8](#0-7) 

Regardless of the computed reward being correct or under/over-priced, `VoteRewardUtil.withdrawReward` unconditionally advances the account's tracked reward window (`updateBeginCycle`/`updateEndCycle`/`updateAccountVote`) to the current cycle: [9](#0-8) 

so any pricing mismatch for that window is not just a one-off rounding difference — it is baked permanently into `allowance`, since the consumed cycle range can never be re-priced/reclaimed afterward.

### Impact Explanation
Because two independent implementations exist for computing the same economic value (accumulated vote reward across the same `[beginCycle, endCycle)` range) and they can diverge for cycles predating the new reward algorithm depending on which entry point (TVM vs native `WithdrawBalanceContract`) and which chain parameters (`allowOldRewardOpt`) are active, an account can either receive a permanently different (lower or higher) reward than it is legitimately owed via one path versus the other. Underpayment via the TVM path permanently freezes the unclaimed delta (window is advanced regardless of the reward value used), which is a concrete loss of funds for the account/contract. This mirrors the reported bug class: two code paths meant to evaluate the same quantity use inconsistent formulas, leading to incorrect withdrawal amounts.

### Likelihood Explanation
Reachability requires only a standard smart-contract call exercising `withdrawReward()`/`voteWitness()`/`unfreezeBalance` opcodes — no privileged role needed. The divergence is conditioned on chain-parameter state (`allowTvmVote` enabled while `allowOldRewardOpt` is not, and reward cycles spanning the pre-new-algorithm era), which is a plausible historical/production configuration window on any network that activated these features sequentially rather than simultaneously, and any account with vote history from before the new reward algorithm activation is affected the first time it withdraws via a TVM contract call.

### Recommendation
Make `VoteRewardUtil.computeReward` mirror `MortgageService.computeReward`'s split logic (using `getNewRewardAlgorithmEffectiveCycle()` and `allowOldRewardOpt()`), or, more robustly, always route both native and TVM reward computations through a single shared function so no other divergence between the two code paths is possible.

### Proof of Concept
1. Deploy the network with `NEW_REWARD_ALGORITHM_EFFECTIVE_CYCLE` set to cycle N, and `allowOldRewardOpt` disabled, `allowTvmVote` enabled.
2. An account accumulates vote rewards for cycles `< N` (before the new algorithm) with the legacy `voteRate*totalReward` semantics.
3. Withdraw via the native `WithdrawBalanceContract` (routes through `MortgageService.computeReward` → `getOldReward` → legacy formula) and compare against withdrawing the identical cycle range via a smart contract calling `withdrawReward()` (routes through `VoteRewardUtil.computeReward`, using only the Vi-based formula) for a comparable account/vote configuration.
4. Observe the two paths produce different `allowance` amounts for the same cycle range and votes, and that the TVM path irreversibly advances `beginCycle`/`endCycle`, permanently locking in the (potentially lower) computed amount as detailed in [10](#0-9) .

  private static long computeReward(long beginCycle, long endCycle,
                                    AccountCapsule accountCapsule, Repository repository) {
    if (beginCycle >= endCycle) {
      return 0;
    }

    long reward = 0;
    for (Protocol.Vote vote : accountCapsule.getVotesList()) {
      byte[] srAddress = vote.getVoteAddress().toByteArray();
      BigInteger beginVi = repository.getDelegationStore().getWitnessVi(beginCycle - 1, srAddress);
      BigInteger endVi = repository.getDelegationStore().getWitnessVi(endCycle - 1, srAddress);
      BigInteger deltaVi = endVi.subtract(beginVi);
      if (deltaVi.signum() <= 0) {
        continue;
      }
      long userVote = vote.getVoteCount();
      reward += deltaVi.multiply(BigInteger.valueOf(userVote))
          .divide(DelegationStore.DECIMAL_OF_VI_REWARD).longValue();
    }
    return reward;
  }

  private long computeReward(long cycle, List<Pair<byte[], Long>> votes) {
    long reward = 0;
    for (Pair<byte[], Long> vote : votes) {
      byte[] srAddress = vote.getKey();
      long totalReward = delegationStore.getReward(cycle, srAddress);
      if (totalReward <= 0) {
        continue;
      }
      long totalVote = delegationStore.getWitnessVote(cycle, srAddress);
      if (totalVote == DelegationStore.REMARK || totalVote == 0) {
        continue;
      }
      long userVote = vote.getValue();
      double voteRate = (double) userVote / totalVote;
      reward += voteRate * totalReward;
    }
    return reward;
  }

  private long computeReward(long beginCycle, long endCycle, AccountCapsule accountCapsule) {
    if (beginCycle >= endCycle) {
      return 0;
    }

    long reward = 0;
    long newAlgorithmCycle = dynamicPropertiesStore.getNewRewardAlgorithmEffectiveCycle();
    List<Pair<byte[], Long>> srAddresses = accountCapsule.getVotesList().stream()
        .map(vote -> new Pair<>(vote.getVoteAddress().toByteArray(), vote.getVoteCount()))
        .collect(Collectors.toList());
    if (beginCycle < newAlgorithmCycle) {
      long oldEndCycle = min(endCycle, newAlgorithmCycle,
          dynamicPropertiesStore.disableJavaLangMath());
      reward = getOldReward(beginCycle, oldEndCycle, srAddresses);
      beginCycle = oldEndCycle;
    }
    if (beginCycle < endCycle) {
      for (Pair<byte[], Long>  vote : srAddresses) {
        byte[] srAddress = vote.getKey();
        BigInteger beginVi = delegationStore.getWitnessVi(beginCycle - 1, srAddress);
        BigInteger endVi = delegationStore.getWitnessVi(endCycle - 1, srAddress);
        BigInteger deltaVi = endVi.subtract(beginVi);
        if (deltaVi.signum() <= 0) {
          continue;
        }
        long userVote = vote.getValue();
        reward += deltaVi.multiply(BigInteger.valueOf(userVote))
            .divide(DelegationStore.DECIMAL_OF_VI_REWARD).longValue();
      }
    }
    return reward;
  }
