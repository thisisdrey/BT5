## Finding

### Title
Unconditional zero-value ERC-20 `transfer` calls in `ERC20Transactor` XCM asset adapter can abort in-flight XCM programs and trap previously-withdrawn assets - (File: `cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs`)

### Summary
`ERC20Transactor::withdraw_asset_with_surplus` and `ERC20Transactor::deposit_asset_with_surplus` unconditionally invoke the target ERC-20 contract's `transfer(to, value)` selector — including when `value == 0` — exactly like the Caviar `PrivatePool.changeFeeQuote`/flash-loan bug that reverts against tokens which reject zero-value transfers.

### Finding Description
`withdraw_asset_with_surplus` matches the asset to `(asset_id, amount)` and then always builds and executes an ERC-20 `transferCall` with `value: EU256::from(amount)`, with no `amount.is_zero()` guard: [1](#0-0) 

The symmetric `deposit_asset_with_surplus` path has the identical unconditional pattern: [2](#0-1) 

If the `transferCall` reverts (per EIP-20 "weird ERC20" behavior of rejecting 0-value transfers, https://github.com/d-xo/weird-erc20#revert-on-zero-value-transfers), `return_value.did_revert()` is true and the function returns `Err(XcmError::FailedToTransactAsset(...))`, aborting that XCM instruction: [3](#0-2) [4](#0-3) 

This is registered as an `AssetTransactor` on Asset Hub Westend (`cumulus/parachains/runtimes/assets/asset-hub-westend/src/xcm_config.rs`), meaning it participates in the general XCM executor asset-transactor tuple for any ERC-20 contract that matches `Matcher::matches_fungibles`. In a multi-instruction/multi-asset XCM program (e.g. `WithdrawAsset` of several assets followed by `DepositAsset`), if the amount computed for this ERC-20 leg becomes `0` (e.g. due to fee subtraction, rounding in a swap, or a partial `TransferAsset`/`DepositAsset` filter), and the token contract reverts on zero-value transfer, the whole XCM instruction fails. Assets from *earlier, successfully executed* `WithdrawAsset`/reserve-deposit steps in the same program remain in the executor's holding register and are trapped by the standard XCM asset-trap mechanism when the program aborts, rather than being delivered to the intended beneficiary.

By contrast, the internal balance-transfer paths in this same repository explicitly special-case zero value to avoid exactly this class of bug: [5](#0-4) [6](#0-5) 

`ERC20Transactor` is the outlier that reintroduces the "revert on zero-value transfer" hazard the rest of the codebase already guards against, because it proxies to an arbitrary, non-runtime-controlled ERC-20 contract instead of the native `Currency`/`fungible` traits.

### Impact Explanation
A token issuer (or any user who deploys their own ERC-20 contract via `pallet-revive` and gets it registered/matched as a fungible asset for XCM, e.g. as a `ForeignAsset`/local ERC-20 usable in reserve transfers) can make it revert on zero-value `transfer`. Any multi-step XCM program that ends up computing a zero amount for that asset leg (fee rounding to zero, partial deposits, `AllCounted`/`Wild` filters combined with dust) will abort with `FailedToTransactAsset`, trapping any assets from prior successfully-executed legs of the same program in the XCM holding register. Recovering trapped assets requires a subsequent `ClaimAsset` XCM sent from the *exact* original origin/context, which is often impractical or impossible for cross-chain reserve-transfer flows (e.g., messages relayed from a sibling chain or bridge), effectively locking user funds.

### Likelihood Explanation
The path is reachable by any ordinary, unprivileged user: deploying a `pallet-revive` contract implementing `transfer` with a zero-value revert is normal Solidity code, not a privileged or attacker-only action, and any user submitting an XCM program via `pallet_xcm::execute`/reserve-transfer that touches a zero-computed amount for that asset will hit the bug. No validator, relayer, or governance compromise is required.

### Recommendation
Add an explicit `if !amount.is_zero() { ... }` guard around the `IERC20::transferCall` invocation in both `withdraw_asset_with_surplus` and `deposit_asset_with_surplus` in `cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs`, returning `Ok` (with an empty/zero credit or zero weight surplus as appropriate) when the amount is zero, mirroring the zero-value short-circuit already used in `substrate/frame/contracts/src/exec.rs::transfer` and `substrate/frame/revive/src/exec.rs::transfer`.

### Proof of Concept
1. Deploy (via `pallet-revive`) an ERC-20-like contract `to`/`value` `transfer` implementation that `revert()`s when `value == 0`.
2. Register/use this contract as the fungible asset matched by `Matcher` for `ERC20Transactor` (e.g., as a foreign/local asset usable in XCM on Asset Hub).
3. Construct an XCM program with multiple `WithdrawAsset`/`DepositAsset` steps such that the computed transfer amount for this ERC-20 asset in a later step rounds to `0` (e.g., via fee deduction or a filtered `DepositAsset` on remaining dust) while an earlier step already withdrew a different, non-zero asset into holding.
4. Execute the program (e.g., via `pallet_xcm::execute` or a reserve transfer). The zero-amount leg triggers `IERC20::transferCall{value:0}`, the contract reverts, `withdraw_asset_with_surplus`/`deposit_asset_with_surplus` returns `Err(XcmError::FailedToTransactAsset("ERC20 contract reverted"))`, and the XCM executor aborts the program, trapping the previously-withdrawn non-zero asset in the holding register instead of delivering it to the intended beneficiary.

	/// Transfer some funds from `from` to `to`.
	///
	/// This is a no-op for zero `value`, avoiding events to be emitted for zero balance transfers.
	///
	/// If the destination account does not exist, it is pulled into existence by transferring the
	/// ED from `origin` to the new account. The total amount transferred to `to` will be ED +
	/// `value`. This makes the ED fully transparent for contracts.
	/// The ED transfer is executed atomically with the actual transfer, avoiding the possibility of
	/// the ED transfer succeeding but the actual transfer failing. In other words, if the `to` does
	/// not exist, the transfer does fail and nothing will be sent to `to` if either `origin` can
	/// not provide the ED or transferring `value` from `from` to `to` fails.
	/// Note: This will also fail if `origin` is root.
	fn transfer<S: State>(
		origin: &Origin<T>,
		from: &T::AccountId,
		to: &T::AccountId,
		value: U256,
		preservation: Preservation,
		meter: &mut ResourceMeter<T, S>,
		exec_config: &ExecConfig<T>,
	) -> DispatchResult {
		let value = BalanceWithDust::<BalanceOf<T>>::from_value::<T>(value)
			.map_err(|_| Error::<T>::BalanceConversionFailed)?;
		if value.is_zero() {
			return Ok(());
		}
