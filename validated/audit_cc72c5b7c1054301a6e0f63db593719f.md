## Title
Attacker can forge relay identity via unauthenticated `RelayFromAddr` field, poisoning relay routing state — ([File: relay_manager.go])

### Summary
`relayManager.handleCreateRelayRequest()` trusts the `RelayFromAddr` value carried inside an authenticated `NebulaControl_CreateRelayRequest` payload as the identity of the peer the relay is being requested on behalf of, instead of binding that identity to the cryptographically verified sender of the packet (`h.vpnAddrs[0]`). This mirrors the DeFi report's root cause: authorization/identity for a sensitive operation is taken from an attacker-supplied field in the message rather than from the verified principal of the call.

### Finding Description
`HandleControlMsg` receives `h *HostInfo`, which is the already-authenticated peer that decrypted and sent this control packet — its identity (`h.vpnAddrs`) is cryptographically bound via the completed Noise handshake and certificate validation. However, `handleCreateRelayRequest` derives the relay's "from" identity purely from the message payload: [1](#0-0) 

Nothing in this function (or in the caller `HandleControlMsg`) checks that `from == h.vpnAddrs[0]`: [2](#0-1) 

Because `from` is unchecked, an authenticated peer `A` can send a `CreateRelayRequest` claiming `RelayFromAddr = V` (an arbitrary victim vpn address it does not own) and `RelayToAddr = T`. The relay server (the recipient of this message) will:
- If it is the target (`f.myVpnAddrsTable.Contains(target)`), install `AddRelay(..., from, m.InitiatorRelayIndex, TerminalType, Established)` keyed by the attacker-chosen `from` value — associating relay state for victim `V`'s address with an index the attacker controls, and reply with a `CreateRelayResponse` describing `RelayFromAddr = from` (i.e., `V`) back over the attacker's own authenticated tunnel: [3](#0-2) 

- If it is not the target and is itself acting as a relay (`am_relay`), it forwards a `CreateRelayRequest` to `target` on behalf of `from`, again with no verification that `from` corresponds to the sender's real identity: [4](#0-3) 

This is structurally the same class of bug as the DefiAppHomeCenter report: a security-relevant identity/receiver field (`from`, analogous to the DeFi `receiver`) is taken from caller-supplied data instead of the verified principal (`h.vpnAddrs[0]`, analogous to `msg.sender`/the stored receiver). The consequence is that relay routing/identity state keyed by vpn address can be created or manipulated by a peer that is not that address's legitimate owner.

### Impact Explanation
An authenticated but malicious peer can poison a relay's internal routing tables (`relayState.relayForByAddr`/`relayForByIdx`) for a victim vpn address it does not control. Depending on race conditions with the legitimate victim's own relay setup, this can be used to disrupt or hijack relay-mediated communication for that victim (denial of service on the relay path, or state confusion where the relay associates traffic for the victim's overlay address with the attacker's tunnel). This is a remote state-poisoning issue reachable by any peer holding a valid certificate that participates in the relay protocol — it does not require possessing a certificate for the victim's identity.

### Likelihood Explanation
Reaching this code path only requires being an authenticated Nebula peer (any node with a CA-signed certificate) capable of sending a `Control` message with type `CreateRelayRequest`/`CreateRelayResponse` and arbitrary `RelayFromAddr`/`RelayToAddr` fields — both attacker-controlled and unauthenticated inputs. No handshake spoofing or certificate forgery is needed; the vulnerability is entirely in the missing binding between the decrypted-channel identity (`h`) and the payload-carried `from` identity. This makes it straightforward to trigger from any node participating in relaying (`relay.am_relay`) or acting as a relay target.

### Recommendation
In `handleCreateRelayRequest` (and `handleCreateRelayResponse`/`EstablishRelay` where relevant), require that `from` (the claimed `RelayFromAddr`) equal `h.vpnAddrs[0]` (the cryptographically verified sender of the control message) before creating or updating any relay state. Reject the request (log and drop) if the payload's identity does not match the authenticated channel identity, exactly as `validatePeerCert`/`correctHostResponded` do for handshake completion elsewhere in the codebase.

### Proof of Concept
Not executed — I was unable to run tests in this environment (index/tool access only). Based on static review, a PoC would:
1. Establish a legitimate authenticated tunnel from attacker node `A` to a relay node `R` (with `relay.am_relay: true` or where `R`'s own address is the intended relay target).
2. From `A`, send a `Control`/`CreateRelayRequest` message with `RelayFromAddr` set to victim `V`'s real vpn address and `RelayToAddr` set to some target `T`.
3. Observe that `R` creates relay state (`AddRelay`) keyed by `V`'s address without ever having authenticated `V`, and sends a `CreateRelayResponse` referencing `V`'s address back to `A`.
4. Confirm that this corrupts or interferes with `V`'s legitimate later attempt to use the same relay (`existingRelay` collision path in `handleCreateRelayRequest`/`AddRelay`).

func (rm *relayManager) HandleControlMsg(h *HostInfo, d []byte, f *Interface) {
	msg := &NebulaControl{}
	err := msg.Unmarshal(d)
	if err != nil {
		h.logger(f.l).Error("Failed to unmarshal control message", "error", err)
		return
	}

	var v cert.Version
	if msg.OldRelayFromAddr > 0 || msg.OldRelayToAddr > 0 {
		v = cert.Version1

		b := [4]byte{}
		binary.BigEndian.PutUint32(b[:], msg.OldRelayFromAddr)
		msg.RelayFromAddr = netAddrToProtoAddr(netip.AddrFrom4(b))

		binary.BigEndian.PutUint32(b[:], msg.OldRelayToAddr)
		msg.RelayToAddr = netAddrToProtoAddr(netip.AddrFrom4(b))
	} else {
		v = cert.Version2
	}

	// validate:
	switch msg.Type {
	case NebulaControl_CreateRelayRequest, NebulaControl_CreateRelayResponse:
		if msg.RelayFromAddr == nil {
			if f.l.Enabled(context.Background(), slog.LevelDebug) {
				h.logger(f.l).Debug("Control message received with nil RelayFromAddr", "type", msg.Type)
			}
			return
		} else if msg.RelayToAddr == nil {
			if f.l.Enabled(context.Background(), slog.LevelDebug) {
				h.logger(f.l).Debug("Control message received with nil RelayToAddr", "type", msg.Type)
			}
			return
		}
	}

	switch msg.Type {
	case NebulaControl_CreateRelayRequest:
		rm.handleCreateRelayRequest(v, h, f, msg)
	case NebulaControl_CreateRelayResponse:
		rm.handleCreateRelayResponse(v, h, f, msg)
	}
}
