### Title
Object Pool Never Prunes Attacker-Pushed Objects, Permanently Bloating Pool Storage and Degrading FetchIntoObjectPool/Housekeeping - (File: internal/git/objectpool/fetch.go)

### Summary
The external report's bug class is: an unprivileged actor can inject arbitrary data through an unrestricted "deposit" path that permanently inflates shared, privileged state with no possibility of cleanup, degrading or blocking legitimate future operations. In Gitaly, the closest reachable analog is the object pool's `rescueDanglingObjects` mechanism: any ordinary user with push access to a fork (an object pool member) can push objects that later get fetched into the shared object pool via `FetchIntoObjectPool`, and the pool is designed to *never* delete any object it has ever seen — every dangling object is permanently pinned by a `refs/dangling/<oid>` reference.

### Finding Description
`FetchFromOrigin` (invoked by the `FetchIntoObjectPool` RPC, callable by any client that owns a pool member/fork) fetches all refs from a pool member into the pool with `+refs/*:refs/remotes/origin/*`, then calls `rescueDanglingObjects`, which runs `git fsck --connectivity-only --dangling` and creates a permanent reference `refs/dangling/$OID` for every dangling object it finds: [1](#0-0) [2](#0-1) 

The design documentation explicitly acknowledges this is a permanent, unconditional pin: "there is no point in time where it's safe to delete objects from the object pool... We thus must consider each object to still be referenced somewhere," and that this can make fetches/repacks "quite expensive": [3](#0-2) 

Just as the Treasury's `deposit()` accepted any token from any caller and permanently inflated `_totalValue` with no way to reverse it (the malicious token can never be transferred out), the object pool accepts any object reachable from any pool member's refs and permanently pins it via a dangling ref that can never be safely removed, even after the member force-pushes over or deletes the objects. Any ordinary user who can push to a repository that is (or later becomes) a pool member — e.g., via GitLab's fork-and-object-pool-linking flow — can repeatedly push-then-delete/force-push large numbers of unique blobs to grow the dangling-reference set on every `FetchIntoObjectPool` cycle, since object pools "never prune objects" (as also confirmed by the `optimize_repository_test.go` comment): [4](#0-3) 

Because the pool accumulates dangling refs, its `git-repack` housekeeping and future `FetchIntoObjectPool`/`OptimizeRepository` calls become progressively more expensive (documented as directly increasing cost of fetches and repacking): [5](#0-4) 

### Impact Explanation
Repeated abuse (push unique large blobs to a pool member repository, then delete/force-update the ref, repeated across `FetchIntoObjectPool` cycles) causes unbounded, irreversible growth of the pool repository's dangling-reference set and object storage. This degrades or times out the `FetchIntoObjectPool` RPC and the pool's housekeeping/`OptimizeRepository` pass for every other member of the shared pool — a resource-exhaustion/DoS of a Gitaly RPC handler analogous to the Treasury's inflated `_totalValue` blocking legitimate future deposits. Unlike the Treasury bug there is no outright arithmetic revert, but the growth is permanent and unrecoverable by design (no safe deletion point exists), matching the report's "no fix without redeploying" severity characterization for the analogous unbounded, un-reversible state pollution.

### Likelihood Explanation
Any ordinary user with push access to a repository that participates in an object pool (a normal, unprivileged action — e.g., pushing to one's own fork) can trigger this: no elevated privileges, leaked tokens, or MITM position are required. `FetchIntoObjectPool` is a regular mutator RPC exposed for use by the fork/pool member update cycle, so the path is reachable purely through ordinary push and object-pool housekeeping flows.

### Recommendation
- Bound the number/size of dangling references retained per pool (e.g., cap total dangling-object storage or age out dangling refs whose underlying commit is unreachable from *all* current pool members for a defined and monitored grace period), accepting the small risk of eventual pruning instead of unconditional permanent retention.
- Track and rate-limit per-member contribution to pool object count/size in `FetchFromOrigin`, so a single misbehaving member cannot unilaterally bloat the shared pool.
- Add monitoring/alerting on dangling-reference growth rate per pool (partially already logged via `logStats`) with the ability to reject or throttle `FetchIntoObjectPool` for members exceeding push-churn thresholds.

### Proof of Concept
Conceptual (not executed, no sandbox available):
1. Fork a repository, so it becomes a pool member linked to a shared object pool.
2. From the fork, repeatedly: push a unique large blob on some ref, then force-push to remove/replace that ref (deleting it from the fork).
3. Trigger `FetchIntoObjectPool` (as would normally run periodically for the pool). Each cycle: `pruneReferences` deletes the now-gone ref, but `rescueDanglingObjects` (`internal/git/objectpool/fetch.go:285-347`) has already fetched the blob object and, since it's dangling, pins it forever via `refs/dangling/$OID`.
4. Repeat across many cycles/many unique blobs to grow the pool's object store and dangling-ref count without bound, since no cleanup path exists (`doc/object_pools.md:78-103`), degrading subsequent `FetchIntoObjectPool` and pool `git-repack` housekeeping performance for all pool members.

**File:** doc/object_pools.md (L78-112)
```markdown
## Dangling Objects

When fetching from pool members into the object pool, then any force-updated
references may cause objects in the pool to not be referenced anymore. For
normal repositories, it is perfectly fine to delete those references after a
certain time. In the context of object pools, any other member of the pool may
still use any of those unreferenced objects. Deleting them would thus
potentially cause corrupt repositories.

This issue is kind of unsolvable: there is no point in time where it's safe to
delete objects from the object pool, as we do not know which repositories may be
linked to it. And even if we knew, we cannot determine all references of all
repositories at once in a race-free manner. We thus must consider each object to
still be referenced somewhere.

As a safeguard to not lose any objects by accident, we thus create dangling
references in the object pool after the fetch in `FetchIntoObjectPool`. For each
dangling object, a reference `refs/dangling/$OID` is created which points into
the object. This assures that each object is still referenced.

Having unreachable objects kept alive in this fashion does have its problems:

- For busy repositories, we generate loads of dangling references. While these
  references [cannot be seen by clients](#references), they are seen when
  performing housekeeping tasks on the object pool itself. Fetches into the
  object pool and repacking of references can thus become quite expensive.

- Keeping dangling references alive makes Git consider them as reachable. While
  this is the exact effect we want to achieve, it will also cause Git to
  generate packfiles which may use such objects as delta bases which would under
  normal circumstances be considered as unreachable. The resulting packfile is
  thus potentially suboptimal. Gitaly works around this issue by using a delta
  island for `refs/heads/` and `refs/tags/`. This can only be considered a
  best-effort strategy, as it only considers a single object pool member's
  reachability while ignoring potential reachability by any other pool member.
```
