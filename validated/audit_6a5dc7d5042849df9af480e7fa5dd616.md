### Title
Forced filling of a victim's per-account token list via dust `DepositToken` transfers blocks deposits of new collateral and new debt positions - (File: contracts/DepositToken.sol)

### Summary
Analogous to the Discourse "unlimited drafts" DoS, Metronome lets any unprivileged user force-write entries into another user's bounded accounting structure. `DepositToken` is a freely transferable ERC20, and `_transfer` calls `pool.addToDepositTokensOfAccount(recipient_)` whenever the recipient's balance goes from 0 to non-zero. `Pool.addToDepositTokensOfAccount` enforces `MAX_TOKENS_PER_USER = 30` across the combined `depositTokensOfAccount` + `debtTokensOfAccount` sets and reverts with `UserReachedMaxTokens` once the cap is hit. An attacker can deposit dust into each whitelisted collateral and transfer 1 wei of each msdTOKEN to a victim, exhausting the victim's 30 slots without any interaction or consent from the victim.

### Finding Description
- `Pool.sol` maintains per-account sets `depositTokensOfAccount` / `debtTokensOfAccount` and enforces the cap in `onlyIfAdditionWillNotReachMaxTokens` (Pool.sol:143-148, MAX = 30 at Pool.sol:79).
- `DepositToken._transfer` unconditionally calls `pool.addToDepositTokensOfAccount(recipient_)` on a recipient's first receipt (DepositToken.sol:517-520). `transfer`/`transferFrom` only check the *sender's* unlocked balance via `_revertIfLocked` (DepositToken.sol:348-376), so anyone holding unlocked msdTOKEN can push it to any address.
- Once the victim's combined list reaches 30 entries, every code path that would add a new token reverts:
  - `DepositToken.deposit` → `_mint` → `addToDepositTokensOfAccount` for any collateral the victim doesn't already hold (DepositToken.sol:469-488).
  - `DebtToken._mint` → `addToDebtTokensOfAccount` for any synth the victim doesn't already owe (DebtToken.sol:598-600), blocking `DebtToken.issue` and `SmartFarmingManager` leverage paths for new debt types.
  - `DepositToken.seize` → `_transfer` → `addToDepositTokensOfAccount` if the liquidation `to_` account's list is full (DepositToken.sol:343-345), though a liquidator can route proceeds to a fresh address, so this mainly limits victim-side flows.

Crucially, the victim cannot shed the dust entries while undercollateralized: transferring them out requires `unlockedBalanceOf(account_) >= amount`, which returns 0 once `debtPositionOf` shows no issuable headroom (DepositToken.sol:383-398). A victim with a fully-utilized leveraged position has no self-recovery until debt is repaid.

### Impact Explanation
- **Temporary freezing of funds / forced liquidation risk**: a victim with open debt cannot add a *new* collateral type to improve health during adverse price movement, since deposits of any not-yet-held collateral revert. If their existing collateral's value falls, they are pushed toward liquidation and lose the liquidation fee + seized collateral — indirect loss of funds caused by the DoS.
- **Blocked borrowing**: `issue`/`mint` of any new synthetic asset reverts, denying the victim new positions.
- **Persistence**: the attack is cheap (dust amounts of each whitelisted collateral) and, for over-leveraged victims, cannot be reversed by the victim alone because removing an entry requires a transfer that is blocked by `_revertIfLocked`.

### Likelihood Explanation
- Fully unprivileged: attacker only needs an EOA, dust amounts of whitelisted underlying tokens, and ordinary `deposit` + `transfer` calls — no privileged role, no oracle manipulation, no governance.
- Cost scales with the number of registered deposit tokens (bounded by the pool-level cap) and gas; 30 entries is reachable in a handful of transactions.
- The meaningful impact requires the victim to be a known address with an open or planned position (e.g., front-running a large deposit, or targeting a leveraged account during volatility), which lowers likelihood but is standard griefing economics.

### Recommendation
- Do not auto-add tokens to `depositTokensOfAccount` on unsolicited inbound `transfer`/`transferFrom`; only register on `deposit`, `seize`, or an explicit opt-in, or allow the list to evict/replace entries rather than revert.
- Alternatively, let `addTo*TokensOfAccount` silently skip non-registered additions on transfers, or exempt tiny "dust" balances from counting.
- Consider allowing recipients to purge entries (e.g., permissionless `removeFromDepositTokensOfAccount` when balance is below a threshold) so victims can self-recover even while collateral is locked.

### Proof of Concept
Hardhat-style sketch (assumes a deployed pool with ≥1 whitelisted `DepositToken`s and a victim with a leveraged position):

```ts
// Attacker fills victim's account token list
const victim = await ethers.getSigner(VICTIM);

for (const dtAddr of depositTokens) {           // each whitelisted DepositToken
  const dt = await ethers.getContractAt('DepositToken', dtAddr);
  const underlying = await ethers.getContractAt('IERC20', await dt.underlying());

  await underlying.approve(dt.address, DUST);
  await dt.deposit(DUST, attacker.address);      // mint dust msdTOKEN to attacker
  await dt.transfer(victim.address, 1);          // pushes entry into victim's list
}

// Repeat until pool.getDepositTokensOfAccount(victim).length + debt tokens == 30

// Now: victim deposits a NEW collateral type -> reverts UserReachedMaxTokens
const newDt = await ethers.getContractAt('DepositToken', NEW_COLLATERAL);
await expect(newDt.connect(victim).deposit(amount, victim.address))
  .to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');

// And victim cannot issue a new synth type (DebtToken._mint -> addToDebtTokensOfAccount)
await expect(debtToken2.connect(victim).issue(amount, victim.address))
  .to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');

// Recovery attempt fails while collateral is locked by debt:
// unlockedBalanceOf(victim) == 0 -> transfer of dust reverts NotEnoughFreeBalance
await expect(msdToken.connect(victim).transfer(attacker.address, 1))
  .to.be.revertedWithCustomError(msdToken, 'NotEnoughFreeBalance');
```

Caveats I could not fully verify: the exact count of registered deposit/debt tokens per deployed pool (needed to reach 30 combined slots is bounded by what's whitelisted), and whether this dust-griefing of `MAX_TOKENS_PER_USER` was already reported in prior Metronome audits, which would exclude it per the rules.
