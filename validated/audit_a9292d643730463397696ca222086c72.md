### Title
Interest-rate spike right before `accrue` retroactively inflates zToken liquidity index over a stale period, letting a borrower manufacture collateral "future capacity" and bypass the egroup capacity check - ([File: mainnet/contracts/vault/v0-vault-sbtc.clar], [File: mainnet/contracts/market/v0-4-market.clar])

### Summary
The Aerodrome report's root cause is that a position's *collateral value* can be inflated by the depositor's own activity **after** it has already passed the entry-time exposure check, and that inflated value is later reused to justify more borrowing/collateral additions without being re-validated. Zest v2 has a structurally analogous gap: the zToken collateral price is `underlying_price * lindex`, and `lindex` is advanced in `accrue()` using the *current, spot* `interest-rate()` applied over the **entire elapsed `time-delta` since `last-update`**, not a time-weighted average rate. A user who controls utilization at the moment `accrue()` fires can therefore retroactively "charge" a stale multi-block/day gap at an artificially high rate, producing a one-shot jump in `lindex` (and `index`) that is written to storage and persists after the user immediately reverses the utilization spike.

### Finding Description
In every vault (e.g. `v0-vault-sbtc.clar`, `v0-vault-stx.clar`, etc.) `accrue` computes: [1](#0-0) [2](#0-1) 

`next-index`/`next-liquidity-index` both use `time-delta = stacks-block-time - last-update` and multiply by `calc-multiplier-delta(rate, time-delta, …)`, where `rate` is derived from `interest-rate()` → `interpolate-rate(utilization(), …)`, i.e. the **instantaneous** utilization read at call time: [3](#0-2) 

`accrue()` is invoked from every state-changing public entry point (`deposit`, `redeem`, `system-borrow`, `system-repay`, `flashloan`), and it persists the new `index`/`lindex` into storage and also mints treasury LP: [4](#0-3) 

Because the rate applied for the whole stale `time-delta` is whatever `utilization()` happens to be *at the instant `accrue` executes*, a caller who spikes utilization immediately before triggering `accrue()` (e.g. via `system-borrow` to near `CAP-DEBT`, capital sourced from a flashloan is in-scope per rules as "capital for a different attack") causes the vault to apply the top-of-curve rate over the entire elapsed period in one shot, inflating `lindex` far beyond what real, time-averaged utilization would justify. The attacker then immediately repays/withdraws to restore normal utilization — the manipulation of utilization is reversed, but the inflated `lindex` value is not: `index`/`lindex` are monotonic state variables, never rolled back.

This inflated `lindex` immediately and permanently raises the USD value of every already-deposited zToken position (e.g., `zsBTC`) computed in `get-notional-evaluation`/`calculate-asset-notional-value`, since zToken price = `underlying_price * lindex`.

Critically, `market.clar`'s `collateral-add` only re-validates "future capacity must not decrease" when the **egroup mask bit changes** (i.e., adding a brand‑new collateral asset type): [5](#0-4) 

Once an asset is already flagged as active collateral for the account (mask bit already set), all subsequent additions/valuation increases of that same collateral skip the capacity check entirely ("Not new collateral - skip all checks (safe to add more)"). This mirrors the Aerodrome bug's precondition exactly: the exposure/capacity check is a one-time gate at "first deposit," and the protocol trusts the *live* valuation of already-approved collateral afterward without re-checking how that valuation grew. An attacker who first legitimately establishes a small zToken collateral position (setting the mask bit, passing the capacity check once), then inflates `lindex` via the rate-spike-then-revert technique described above, causes their existing collateral's USD value (and thus their egroup borrowing capacity) to balloon without ever passing back through the "future capacity must not decrease" gate — because that gate is bypassed for existing collateral types by design.

### Impact Explanation
The manipulation simultaneously inflates `index` (debt owed by all existing borrowers of that vault) and `lindex` (redeemable value of all existing zToken holders of that vault) for a time window that was never actually subject to the spiked rate. This:
- Retroactively overcharges every existing borrower in that vault (unclaimed-yield/interest theft from borrowers to suppliers/attacker), since interest for the stale period is now computed at a rate the attacker chose, not the real historical average.
- Lets the attacker convert this artificial `lindex` jump into artificially inflated collateral notional value on an already-approved collateral slot, bypassing the "future capacity must not decrease" exposure check that is supposed to gate growth in borrowing power — enabling additional borrowing beyond what legitimate collateral would support.

This lands in the **High** impact bucket: theft of unclaimed yield (interest that should have accrued at the real historical utilization-weighted rate is instead captured at an attacker-manufactured rate) and indirectly enables under-collateralized borrowing against an inflated valuation that skipped the intended capacity re-check.

### Likelihood Explanation
Likelihood is moderate: it requires (a) a vault where `last-update` has grown stale (little organic activity), and (b) the attacker being able to move utilization sharply within a single transaction (feasible using a flashloan as capital, permitted under the rules as "different attack" capital), then reverting it in the same transaction while triggering `accrue()` in between. Given Zest's per-vault caps (`CAP-DEBT`) and dynamic 8-point interest curves, pushing utilization from a low baseline to a curve's steep/top region is realistic with a large enough flashloan-funded `system-borrow`, especially on lower-liquidity vaults (e.g. `stSTXbtc`, `USDH`).

### Recommendation
Do not let a single call's `interest-rate()` (spot utilization) be applied over an arbitrarily large stale `time-delta`. Either (1) checkpoint/accrue at a maximum granularity (e.g., force periodic accrual so `time-delta` can never span more than a bounded window before a rate change takes effect), or (2) compute the rate to apply using utilization sampled at multiple points / a TWAP-like mechanism instead of the instantaneous value at the moment `accrue` fires. Additionally, mirror the UniswapV3-position fix cited in the referenced report: for collateral whose valuation depends on a mutable index (`lindex`) rather than a purely external oracle price, re-validate the egroup "future capacity must not decrease" style check whenever that collateral's value increases meaningfully within a position, not only when the collateral mask bit is first set.

### Proof of Concept
1. Attacker deposits a small amount into vault-sbtc, receiving `zsBTC`, and calls `market.clar`'s `collateral-add` for `zsBTC` — the mask bit for `zsBTC` is set and the one-time capacity check passes trivially (position has no debt yet, or minimal debt).
2. Attacker waits (or picks a moment) until `last-update` on `vault-sbtc` is stale (large `time-delta`), which is a natural, commonly occurring vault state absent frequent activity.
3. In a single transaction: attacker takes a flashloan, deposits it as unrelated collateral (e.g. STX), and calls `market.clar`'s `borrow` against `vault-sbtc` for a large amount, driving `utilization()` from `get-available-assets()`/`total-debt()` toward the top of the 8-point curve (`interpolate-rate`), spiking `interest-rate()`.
4. Any subsequent vault call (a second `system-borrow`/`system-repay`/`deposit`) triggers `accrue()`, which computes `next-index`/`next-liquidity-index` using this spiked `interest-rate()` applied over the full stale `time-delta`, jumping `lindex` (and `index`) far above what real elapsed-time-weighted utilization would produce; the new values are written to `var-set index`/`var-set lindex` and `last-update` is bumped.
5. Attacker immediately repays the large borrow and unwinds/repays the flashloan within the same transaction, returning `utilization()` to baseline — but `lindex` remains at its newly inflated, persisted value.
6. Attacker's previously established `zsBTC` collateral (mask bit already set in step 1) is now valued at `sBTC_price * inflated_lindex` in `calculate-asset-notional-value`; because the asset is not "new collateral," `market.clar`'s capacity re-check (`>= future-capacity current-capacity`) is never invoked for this valuation increase, so the attacker can immediately borrow against the inflated collateral value that bypassed the intended exposure/capacity gate.
