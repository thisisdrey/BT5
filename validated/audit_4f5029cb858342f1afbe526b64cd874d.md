### Title
Atlas attachment downloader accepts and stores attachments whose content does not hash to the requested `content_hash` - (File: stackslib/src/net/atlas/download.rs)

### Summary
When fetching an attachment via `GET /v2/attachments/{content_hash}`, the response is deserialized by `decode_atlas_get_attachment` and inserted into the node's attachment set by `extend_with_attachments` without ever recomputing `Attachment::hash()` and comparing it to the requested `content_hash`. Any peer serving that URL (including the requesting peer or a peer supplying the response to `BatchedRequestsResult`) can therefore have arbitrary, uncommitted bytes accepted as if they were the on-chain-committed attachment.

### Finding Description
The broken equality is `response.attachment.hash() == request.content_hash` (`Attachment::hash()` defined at `stackslib/src/net/atlas/mod.rs:158-160`, `AttachmentRequest.content_hash` set from an `AttachmentInstance` commitment). The request is built in `AttachmentRequest::make_request_type` (`stackslib/src/net/atlas/download.rs:1110-1118`) as `GET /v2/attachments/{content_hash}`. On the server side, `RPCGetAttachmentRequestHandler::try_handle_request` (`stackslib/src/net/api/getattachment.rs:93-130`) looks up the attachment by hash from the *node's own* AtlasDB and would return the correct content for a well-behaved node — but the client-side consumer, `AttachmentsBatchStateContext::extend_with_attachments` (`stackslib/src/net/atlas/download.rs:530-558`), just calls `response.decode_atlas_get_attachment()` (`stackslib/src/net/api/getattachment.rs:159-165`), which does nothing but `serde_json` deserialize the body into `GetAttachmentResponse { attachment: Attachment { content } }`, and then unconditionally does `self.attachments.insert(response.attachment)`. There is no call to `Attachment::hash()` anywhere in this function or in `decode_atlas_get_attachment`, so a malicious or misconfigured peer answering the GET request with `{"attachment":{"content": <arbitrary bytes>}}` (HTTP 200) will have those bytes accepted and merged into the downloader's `attachments` set, keyed only by content (a `HashSet<Attachment>` derived from `#[derive(Hash)]` on `content`), with no tie back to `content_hash`.

### Impact Explanation
This is an attachment/BNS mismatch: attacker-controlled bytes not committed on-chain get pulled into the node's in-memory attachment set (`self.attachments`) and subsequently flow into `AttachmentsDownloader`'s persistence path, meaning storage state is populated with data that no `AttachmentInstance` commitment produced. Legitimate BNS name resolution for that `content_hash` never completes correctly (the true content is never fetched/stored, or is overwritten/coexists inconsistently), while forged content sits in the node's attachment storage. This matches the "High – attachment/BNS mismatch" impact category.

### Likelihood Explanation
The attacker only needs to be a reachable peer (or otherwise control/be a source for one of the `sources` URLs in the `AttachmentRequest`) that the node queries for an attachment inventory/instance it is trying to resolve — no privileged key, RPC secret, or admin role is required, only the ability to answer an HTTP GET on the public RPC endpoint with attacker-chosen JSON. This is trivially repeatable per attachment request and costs nothing beyond running a normal peer/RPC responder.

### Recommendation
In `AttachmentsBatchStateContext::extend_with_attachments` (`stackslib/src/net/atlas/download.rs:547-549`), after decoding, verify `response.attachment.hash() == request.content_hash` before inserting into `self.attachments`; on mismatch, treat it as a failed request (`report.bump_failed_requests()`) and skip/continue, mirroring how other verified fields are checked elsewhere in the codebase.

    pub fn extend_with_attachments(
        mut self,
        results: &mut BatchedRequestsResult<AttachmentRequest>,
    ) -> AttachmentsBatchStateContext {
        for (request, response) in results.succeeded.drain() {
            let report = self
                .peers
                .get_mut(request.get_url())
                .expect("Atlas: unable to retrieve reliability report for peer");

            let response = if let Some(r) = response {
                r
            } else {
                report.bump_failed_requests();
                continue;
            };

            if let Ok(response) = response.decode_atlas_get_attachment() {
                self.attachments.insert(response.attachment);
                report.bump_successful_requests();
            } else {
                report.bump_failed_requests();
            }
        }
        let mut events_ids = results.faulty_peers.keys().copied().collect::<Vec<usize>>();
        self.events_to_deregister.append(&mut events_ids);

        self
    }
