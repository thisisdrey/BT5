### Title
RewardsDistributor credits `INITIAL_INDEX` worth of rewards to any holder when called before the token index has ever advanced — (`contracts/RewardsDistributor.sol`)

### Summary
`_calculateTokenDelta` treats a missing `accountIndexOf` entry (value `0`, the "null" slot) correctly only when the token index has grown past `INITIAL_INDEX`. When a reward token is first registered its `tokenStates[token_].index` is set to exactly `INITIAL_INDEX` (`1e18`), so the fallback branch is skipped, `_deltaIndex` computes to `1e18`, and the account is credited `balanceOf(account)` reward tokens — even though zero time has accrued. This is the Solidity analog of a null-dereference on an uninitialized structure: the unset mapping entry is consumed without the required default substitution.

### Finding Description
Relevant code:

- `tokenStates[token_] = TokenState({index: INITIAL_INDEX, ...})` when a token's speed first becomes non-zero [1](#0-0) 
- The fallback that is supposed to stand in for a missing account index only fires when the token index is *strictly greater* than `INITIAL_INDEX`: [2](#0-1) 

```solidity
// contracts/RewardsDistributor.sol:222-231
_tokenIndex = _tokenState.index;                 // == INITIAL_INDEX right after registration
uint256 _accountIndex = accountIndexOf[token_][account_]; // 0 = "null"

if (_accountIndex == 0 && _tokenIndex > INITIAL_INDEX) {
    _accountIndex = INITIAL_INDEX;               // not taken when _tokenIndex == INITIAL_INDEX
}

uint256 _deltaIndex = _tokenIndex - _accountIndex; // = 1e18 - 0 = 1e18
_tokensDelta = token_.balanceOf(account_).wadMul(_deltaIndex); // = full balance
```

`_calculateTokenIndex` only returns a `newIndex` when `block.timestamp - timestamp > 0 && speed > 0`; in the same block as registration (or any block where the delta/timestamp update path at lines 209–211 runs) `_updateTokenIndex` leaves `index == INITIAL_INDEX` [3](#0-2) . The publicly callable `updateBeforeMintOrBurn` ("This function also may be called by anyone") then folds the bogus delta into `tokensAccruedOf` [4](#0-3) , and `claimRewards` pays it out via `_transferRewardIfEnoughTokens` [5](#0-4) .

Note this also creates a milder liveness edge: for a token whose index has advanced (`> INITIAL_INDEX`), a brand-new account is handled correctly, but the asymmetry means correctness depends entirely on the strictly-greater comparison rather than on "has this token ever been initialized," which is the actual invariant.

### Impact Explanation
Every holder of the freshly-registered DepositToken or DebtToken can accrue `balanceOf(account)` units of `rewardToken` with zero elapsed reward time. Calling `claimRewards` immediately transfers those tokens as long as the distributor holds a sufficient reward-token balance, draining rewards that belong to future legitimate accrual — direct theft of unclaimed yield from the protocol.

### Likelihood Explanation
The trigger call is fully permissionless (`updateBeforeMintOrBurn` / `claimRewards`, no onlyGovernor/onlyPool gate beyond `tokenStates.index > 0`, which is satisfied). The only precondition is that `tokenStates[token_].index == INITIAL_INDEX`, which holds:

1. In the same block that the governor calls `updateTokenSpeed`/`updateTokenSpeeds` or the keeper calls `syncTokenSpeed` for a new token — an attacker can back-run these transactions atomically on any chain with public mempool/private bundles.
2. Indefinitely whenever `totalSupply() == 0` or `speed == 0` after registration, since `_calculateTokenIndex` then never increments the index past `INITIAL_INDEX` (case: a token registered while its supply is 0, then deposits arrive — the index stays `1e18` until a nonzero-speed block elapses; same-block depositors still trigger it).

The keeper-driven `syncTokenSpeed` path is called repeatedly and sets `INITIAL_INDEX` on first invocation, so on Vesper-integrated deployments this window recurs operationally.

### Recommendation
In `_calculateTokenDelta`, treat any unset account index as `min(INITIAL_INDEX, _tokenIndex)` — i.e., apply the fallback whenever `_accountIndex == 0`, clamping to the current token index so a never-accrued account can never have a positive delta:

```solidity
if (_accountIndex == 0) {
    _accountIndex = _tokenIndex < INITIAL_INDEX ? _tokenIndex : INITIAL_INDEX;
    // equivalently: _accountIndex = _tokenIndex;  // safest: zero delta for unseen accounts
}
```

The simplest correct fix is `_accountIndex = _tokenIndex` when the entry is unset, which preserves existing behavior for indexes `> INITIAL_INDEX` (where the historical fallback intentionally grants the `INITIAL_INDEX → current` delta) only if that grant is itself intended; otherwise document and gate it deliberately.

### Proof of Concept
Hardhat (fork or local), using the existing test harness pattern from `test/RewardDistributor.test.ts` [6](#0-5) :

```ts
// Setup: pool, msdTOKEN (DepositToken) mocks as in beforeEach; rewardDistributor initialized.

// 1. Governor registers msdTOKEN1 with nonzero speed (same tx/block context).
await rewardDistributor.updateTokenSpeed(msdTOKEN1.address, parseEther('1'))
// tokenStates[msdTOKEN1].index == INITIAL_INDEX == 1e18, accountIndexOf == 0 for alice

// 2. In the SAME block (automine off / same-timestamp), attacker updates indexes for alice.
//    Give alice a balance; totalSupply>0 is fine — _deltaTimestamps == 0 keeps index at INITIAL_INDEX.
msdTOKEN1.totalSupply.returns(parseEther('1000'))
msdTOKEN1.balanceOf.withArgs(alice.address).returns(parseEther('100'))

await network.provider.send('evm_setAutomine', [false])
// updateTokenSpeed and updateBeforeMintOrBurn mined in the same block:
await rewardDistributor.updateTokenSpeed(msdTOKEN1.address, parseEther('1'))
await rewardDistributor.updateBeforeMintOrBurn(msdTOKEN1.address, alice.address)
await mine()

// 3. tokensAccruedOf[alice] == 100e18 (full balance credited with zero reward time).
expect(await rewardDistributor.tokensAccruedOf(alice.address)).to.eq(parseEther('100'))

// 4. Fund distributor with rewardToken and claim → alice drains it.
await vsp.mint(rewardDistributor.address, parseEther('1000'))
await rewardDistributor.claimRewards(alice.address)
expect(await vsp.balanceOf(alice.address)).to.eq(parseEther('100')) // stolen yield
```

Variant without same-block timing: register the token while `msdTOKEN1.totalSupply() == 0`, then have alice deposit in the same block that the first nonzero-speed update would advance the index — before any block in which both `deltaTimestamps > 0` and `totalSupply > 0` co-occur, the index remains `1e18` and the bogus accrual still fires.
