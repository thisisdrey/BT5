### Title
Unauthenticated, peer-reported StackerDB chunk-inventory versions poison `expected_versions`, permanently blocking legitimate signed chunk writes for a slot (griefing DoS) - ([File: stackslib/src/net/stackerdb/sync.rs])

### Summary
`StackerDBSync` derives its notion of the "expected" (i.e., canonical-floor) slot version for every StackerDB slot from the unauthenticated `slot_versions` vector reported by remote peers in `StackerDBChunkInvData`. This vector carries no signature and is never validated against anything the slot's owner actually signed. Because this attacker-controlled value is later used as a hard floor/ceiling gate in `validate_received_chunk`, a single unprivileged remote peer can report an inflated slot version for a target slot and permanently prevent the victim node from ever again accepting a legitimately-signed chunk for that slot — an availability griefing directly analogous to the Ajna report's "raise a trusted derived metric via cheap, unauthenticated action to disable normal operation."

### Finding Description
`StackerDBChunkInvData` is a plain, unsigned vector of `u32` versions plus a replica count: [1](#0-0) 

Its wire codec only bounds array length; it applies no cryptographic authentication over the version values themselves: [2](#0-1) 

Any remote peer that completes a handshake and claims (also unauthenticated) to replicate a target `smart_contract_id` becomes eligible to answer `StackerDBGetChunkInv`/have its inventory merged in via `getchunksinv_try_finish` and `add_pushed_chunk`: [3](#0-2) [4](#0-3) 

`recalculate_chunk_request_schedule` then computes `expected_versions` as the **element-wise maximum over all known (unauthenticated) peer inventories**, with no weighting by trust, ownership, or signature validity: [5](#0-4) 

This `self.expected_versions` is then fed straight into `validate_downloaded_chunk` → `PeerNetwork::validate_received_chunk`, which uses it as an authoritative floor and rejects any chunk whose `slot_version` is lower (as "stale"), or whose `slot_version` exceeds `config.max_writes` (as "too many writes"): [6](#0-5) [7](#0-6) 

Because a legitimate slot owner's real, signed chunk version is intrinsically bounded by `config.max_writes`, an attacker only needs to report `slot_version = config.max_writes + 1` (or `u32::MAX`) for the targeted `slot_id`. This single unsigned claim:
1. Sets `expected_versions[slot_id]` above what any legitimately-signed chunk can ever reach, so the `data.slot_version < *expected_version` "stale" check fails forever, AND
2. Independently, any chunk that *did* try to match/exceed that inflated floor would itself now be rejected by the `data.slot_version > config.max_writes` check.

Either way, the victim node can never again validate a genuine, correctly-signed update for that slot — an equality break between "peer-claimed version" (unauthenticated) and "canonical/expected version" (should require the slot owner's signature) that the code treats as interchangeable.

### Impact Explanation
This lets any single unprivileged remote peer permanently disable legitimate write/replication acceptance for a targeted slot (and, by repeating for all slots, an entire StackerDB) on any victim node it can handshake with — without ever needing the slot owner's private key or any special role. StackerDBs back critical Nakamoto signer coordination data; bricking replication of a signer's slot on downstream replicas degrades or disables signer message propagation network-wide for that DB, matching the report's "disables the pool" impact. This aligns with the "High" impact bucket (steering a node off canonical state / bounded-compute DoS via a small number of unauthenticated messages that persistently poison read/write behavior).

### Likelihood Explanation
Low cost, fully remote, requires no privileged key or role — only a normal P2P handshake and a fabricated `StackerDBChunkInvData` reply/push, which is standard, expected protocol traffic. The victim automatically incorporates and persists the poisoned value across sync rounds via `recalculate_chunk_request_schedule`/`add_pushed_chunk`, so the attacker need only occasionally re-assert the bogus inventory to keep the slot bricked.

### Recommendation
Do not let `expected_versions` (or any acceptance gate) be derived purely from unauthenticated peer-reported inventories. Either:
- Cap/clamp any peer-reported "max" version used for scheduling/gating to `config.max_writes`, and never let it exceed the maximum a validly-signed chunk could present, or
- Decouple the download-scheduling use of peer inventories (which is fine, since downloaded chunks are separately signature-verified) from the acceptance-time "stale" floor, which should instead be derived only from the local DB's confirmed (signature-verified and stored) slot version — never from `max(peer-claimed versions)`.

### Proof of Concept
1. Stand up a malicious node, complete a P2P handshake with a victim, and advertise (unauthenticated) that it replicates the target `smart_contract_id`.
2. When queried via `StackerDBGetChunkInv`, or when pushing a chunk, reply with a `StackerDBChunkInvData` whose `slot_versions[target_slot_id] = config.max_writes + 1`.
3. Observe that `add_pushed_chunk`/`getchunksinv_try_finish` merges this into `chunk_invs`, and a subsequent `recalculate_chunk_request_schedule` sets `self.expected_versions[target_slot_id] = config.max_writes + 1`.
4. Have the real slot owner submit any validly-signed chunk at any version `<= config.max_writes`; `validate_received_chunk` rejects it as `StaleChunk` (version < expected) — the slot is now permanently unwritable/unreplicable on the victim node, reproducing the "raise a trusted metric above what's achievable to disable normal operation" griefing pattern from the source report.

        if self.slot_versions.len() > (stackerdb::STACKERDB_INV_MAX as usize) {

        }

        let slot_versions: Vec<u32> = read_next_at_most(fd, stackerdb::STACKERDB_INV_MAX)?;
        let num_outbound_replicas: u32 = read_next(fd)?;
        Ok(StackerDBChunkInvData {
            slot_versions,
            num_outbound_replicas,
        })
    }

    pub fn add_pushed_chunk(
        &mut self,
        _network: &PeerNetwork,
        naddr: NeighborAddress,
        new_inv: StackerDBChunkInvData,
        slot_id: u32,
    ) -> bool {
        // safety (should already be checked) -- don't accept if the size is wrong
        if new_inv.slot_versions.len() != self.num_slots {
            return false;
        }

        let need_resync = if let Some(old_inv) = self.chunk_invs.get(&naddr) {
            let mut resync = false;
            for (old_slot_id, (old_version, new_version)) in old_inv
                .slot_versions
                .iter()
                .zip(new_inv.slot_versions.iter())
                .enumerate()
            {
                if old_version < new_version {
                    // remote peer indicated that it has a newer version of this chunk.
                    debug!(
                        "{:?}: {}: peer {:?} has a newer version of slot {} ({} < {})",
                        _network.get_local_peer(),
                        &self.smart_contract_id,
                        &naddr,
                        old_slot_id,
                        old_version,
                        new_version,
                    );
                    resync = true;
                    break;
                }
            }
            resync
        } else {
            false
        };

        self.chunk_invs.insert(naddr, new_inv);

        self.chunk_push_priorities
            .retain(|(chunk, ..)| chunk.chunk_data.slot_id != slot_id);

        if !self.chunk_push_priorities.is_empty() {
            let next_chunk_push_priority =
                self.next_chunk_push_priority % self.chunk_push_priorities.len();
            self.next_chunk_push_priority = next_chunk_push_priority;
        }

        self.total_pushed += 1;
        need_resync
    }

    /// Recalculate the download schedule based on chunkinvs received on push
    pub fn recalculate_chunk_request_schedule(
        &mut self,
        network: &PeerNetwork,
    ) -> Result<(), net_error> {
        // figure out the new expected versions
        let mut expected_versions = vec![0u32; self.num_slots];
        for (_, chunk_inv) in self.chunk_invs.iter() {
            for (slot_version, expected_version) in chunk_inv
                .slot_versions
                .iter()
                .zip(expected_versions.iter_mut())
            {
                *expected_version = (*slot_version).max(*expected_version);
            }
        }

        let priorities =
            self.make_chunk_request_schedule(network, Some(expected_versions.clone()))?;

        self.chunk_fetch_priorities = priorities;
        self.expected_versions = expected_versions;
        Ok(())
    }
