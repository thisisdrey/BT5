### Title
Underpriced computation in `cancel_item_attributes_approval` via attacker-controlled witness allows disproportionate storage-scan replay — (File: `substrate/frame/nfts/src/features/attributes.rs`)

### Summary
`do_cancel_item_attributes_approval`, called from the public signed extrinsic `cancel_item_attributes_approval`, drains **all** attributes stored under the `Account(delegate)` namespace for an item *before* validating the attacker-supplied `witness.account_attributes` bound, and the dispatchable's weight is computed directly from that same attacker-supplied witness value.

### Finding Description
The core logic: [1](#0-0) 

`ItemAttributesApprovalsOf::<T, I>::try_mutate` removes the delegate approval, then unconditionally calls `Attribute::<T, I>::drain_prefix(...)` over every attribute keyed under `(collection, item, AttributeNamespace::Account(delegate))`, counting them as it goes. Only **after** the full drain does it check `attributes <= witness.account_attributes` and bail with `Error::BadWitness` if the caller under-reported the count.

Because the drain happens before the witness check, the actual computational/storage-read cost of this call is proportional to the *real* number of attributes stored for `(item, delegate)` under the `Account` namespace — a quantity fully controlled by the item owner (who can call `set_attribute` an unbounded number of times to populate that namespace, since there is no cap on total attributes per item/namespace other than the deposit cost).

The dispatchable's declared/charged weight, however, is computed from the caller-supplied `witness.account_attributes` field (the same field used only for the post-hoc `BadWitness` check), following the pallet's usual pattern of `T::WeightInfo::cancel_item_attributes_approval(witness.account_attributes)` for both pre-dispatch weight and post-dispatch `actual_weight`. If the call fails with `BadWitness`, the runtime bills based on the declared (attacker-chosen, e.g. `0`) weight rather than the real work performed by `drain_prefix` iterating over N storage entries.

Since the whole extrinsic executes inside FRAME's transactional storage layer, a failing call rolls back state changes (the drained attributes are restored), which means:
1. An item owner can pre-populate `N` attributes cheaply relative to per-call cost is not free — creating N attributes costs N `set_attribute` calls (each separately weighed/fee'd and deposit-bonded).
2. Once those N attributes exist, the owner can repeatedly call `cancel_item_attributes_approval` with `witness.account_attributes = 0` (or any value less than N). Each call performs a full `drain_prefix` scan/read over the N entries (real DB/trie work) but is charged only the minimal declared weight for `witness.account_attributes = 0`, then reverts on `BadWitness`.
3. This replay can be repeated indefinitely at the attacker's discretion, each time forcing the node to do O(N) work for O(1) declared/charged weight.

### Impact Explanation
This is a "public underpriced work" pattern: the fee/weight charged for a failing call is decoupled from the actual iteration cost performed by `drain_prefix`, and the attacker fully controls both the real attribute count (via prior `set_attribute` calls on their own item) and the declared witness used for weighing. Repeated cheap replay of the failing call can force disproportionate storage-read/iteration work per block relative to the weight budget consumed, degrading block execution efficiency. The blast radius is limited to storage the attacker themselves created (their own item's attributes), so it is not a cross-user fund-theft or lock issue, but it does fit the "underpriced work that degrades block production" impact category described in the review's decision standard.

### Likelihood Explanation
Exploitation requires only unprivileged actions the attacker already fully controls: being the item owner, approving themselves/a controlled delegate account (`do_approve_item_attributes`), populating many attributes under that namespace, then repeatedly invoking `cancel_item_attributes_approval` with an intentionally low `witness.account_attributes`. No special privilege or race condition is needed, only up-front capital to create the attribute set (bounded by deposit requirements and per-call fees for the initial population), after which replay of the failing cancel call is cheap.

### Recommendation
- Validate the reported `witness.account_attributes` against the true count *before* performing the destructive/iterative work — e.g., first count matching attributes (or track a per-`(item, delegate)` counter) and `ensure!` the bound prior to calling `drain_prefix`, or cap iteration to `witness.account_attributes` and reject the call before mutating state if the two disagree.
- Ensure the dispatchable's `actual_weight` reflects real iteration cost even on the `BadWitness` failure path (e.g., return a `PostDispatchInfo` with actual weight based on attributes actually scanned, not solely on the attacker-supplied witness), so failing calls cannot be charged less than the work performed.

### Proof of Concept
1. Attacker mints/owns `item` in `collection`.
2. Attacker approves themselves (or a second account they control) as delegate via `approve_item_attributes`.
3. Attacker calls `set_attribute` repeatedly (e.g., 10,000 times) with `namespace = Account(delegate)`, populating many attribute entries for `(collection, item, delegate)`.
4. Attacker calls `cancel_item_attributes_approval(collection, item, delegate, witness = { account_attributes: 0 })`.
5. `do_cancel_item_attributes_approval` performs `drain_prefix` over all ~10,000 entries (real storage read/iteration cost), then fails with `Error::BadWitness` since `10000 > 0`; state rolls back.
6. The extrinsic is charged only the weight corresponding to `witness.account_attributes = 0`, not the O(10,000) iteration actually performed.
7. Step 4 can be repeated indefinitely without needing to recreate the attributes, each time incurring the same underpriced O(N) work. [2](#0-1)

	pub(crate) fn do_cancel_item_attributes_approval(
		check_origin: T::AccountId,
		collection: T::CollectionId,
		item: T::ItemId,
		delegate: T::AccountId,
		witness: CancelAttributesApprovalWitness,
	) -> DispatchResult {
		ensure!(
			Self::is_pallet_feature_enabled(PalletFeature::Attributes),
			Error::<T, I>::MethodDisabled
		);

		let details = Item::<T, I>::get(&collection, &item).ok_or(Error::<T, I>::UnknownItem)?;
		ensure!(check_origin == details.owner, Error::<T, I>::NoPermission);

		ItemAttributesApprovalsOf::<T, I>::try_mutate(collection, item, |approvals| {
			approvals.remove(&delegate);

			let mut attributes: u32 = 0;
			let mut deposited: DepositBalanceOf<T, I> = Zero::zero();
			for (_, (_, deposit)) in Attribute::<T, I>::drain_prefix((
				&collection,
				Some(item),
				AttributeNamespace::Account(delegate.clone()),
			)) {
				attributes.saturating_inc();
				deposited = deposited.saturating_add(deposit.amount);
			}
			ensure!(attributes <= witness.account_attributes, Error::<T, I>::BadWitness);

			if !deposited.is_zero() {
				T::Currency::unreserve(&delegate, deposited);
			}

			Self::deposit_event(Event::ItemAttributesApprovalRemoved {
				collection,
				item,
				delegate,
			});
			Ok(())
		})
	}
