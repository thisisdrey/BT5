### Title
Dust deposit permanently blocks `removeDepositToken`/`removeDebtToken` griefing — ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
`Pool.removeDepositToken` and `Pool.removeDebtToken` revert unless the token's `totalSupply()` is zero. Any unprivileged user can mint a dust amount of the token (1 wei collateral deposit via `DepositToken.deposit`, or a dust debt position via `DebtToken`) and simply never withdraw/repay, permanently preventing governance from removing the token from the pool. This is the same bug class as the Sandclock finding: a `balance == 0` / `totalSupply == 0` gate on an admin migration/removal path that any user can trivially keep non-zero.

### Finding Description
In `Pool.sol`:

```solidity
function removeDebtToken(IDebtToken debtToken_) external onlyGovernor {
    if (debtToken_.totalSupply() > 0) revert TotalSupplyIsNotZero();
    ...
}

function removeDepositToken(IDepositToken depositToken_) external onlyGovernor {
    if (depositToken_.totalSupply() > 0) revert TotalSupplyIsNotZero();
    ...
}
``` [1](#0-0) 

`DepositToken.deposit` is a public, unprivileged entry point that mints `msdTOKEN` to `onBehalfOf_` for any non-zero `amount_`, with no minimum: [2](#0-1) 

Similarly, `DebtToken.issue`/`Pool` minting lets any user with collateral open a debt position (subject to `debtFloorInUsd`, which only raises the cost, not the feasibility).

Once a griefer holds even 1 wei of `msdTOKEN`, `totalSupply() > 0` forever unless they voluntarily burn. Governor deactivating the token via `toggleIsActive` (line 559) does not help: `msdTOKEN` is freely transferable (`_transfer` has no active flag check, lines 498–526), so the attacker can acquire dust even after deposits are disabled, and existing dust holders can keep balances spread across many accounts. The attacker can also frontrun each `removeDepositToken` call by transferring 1 wei to a fresh account — though even one persistent dust balance suffices.

### Impact Explanation
Governance is permanently unable to remove a deposit token or debt token from the pool's offerings. If an underlying collateral asset must be exited (depeg, oracle deprecation, migration to a new token), the stale token stays registered in `depositTokens`/`depositTokenOf` and `debtTokens`/`debtTokenOf` — new deposits cannot be fully sunset, and users' collateral/debt tied to the stale token cannot be cleanly migrated. This is a permanent liveness/cleanup denial on an administrative path for the cost of dust. Matches the accepted impact "temporary/permanent freezing" of a protocol function; no privileged attacker needed.

### Likelihood Explanation
Cost is negligible: 1 wei of underlying for `removeDepositToken` griefing, or a debt position at the `debtFloorInUsd` minimum for `removeDebtToken` griefing. The attack only needs to be performed once — unlike Sandclock where the griefer had to repeat after each redemption, here the dust balance persists indefinitely and can even be re-seeded via ERC20 transfers after the token is deactivated.

### Recommendation
Do not gate removal on `totalSupply() == 0`. Options:
- Allow removal while supply is non-zero and handle residual holders via a forced-redemption/migration path (e.g., let the pool burn dust positions and push collateral to Treasury).
- Alternatively, let removal proceed if remaining `totalSupply` is below a dust threshold, with the residual pulled into `Treasury`.
- For `DebtToken`, permit governor-forced `repay` from Treasury before removal.

### Proof of Concept
Foundry/Hardhat fork sketch:

```solidity
// Setup: pool with depositToken (e.g. msdWETH) registered, depositFee = 0

// 1. Attacker deposits 1 wei of underlying, keeps the msdTOKEN
underlying.approve(address(depositToken), 1);
depositToken.deposit(1, attacker);
assert(depositToken.totalSupply() > 0);

// 2. Governor deactivates the token (doesn't help)
vm.prank(governor);
depositToken.toggleIsActive();

// 3. Even if attacker balance were seized/burned, attacker re-seeds via transfer
//    from another dust account (transfers are unrestricted)
vm.prank(attacker2);
depositToken.transfer(attacker3, 1);

// 4. Governor attempts removal — always reverts
vm.prank(governor);
vm.expectRevert(Pool.TotalSupplyIsNotZero.selector);
pool.removeDepositToken(depositToken);
```

The same applies to `removeDebtToken` with a dust `DebtToken.issue` position (attacker deposits collateral, mints minimum debt above `debtFloorInUsd`, never repays).
