### Title
Fee-on-transfer / short-delivery NEP-141 tokens let `ft_on_transfer` over-credit Defuse's internal ledger beyond actual custody, freezing later withdrawals - ([File: contracts/defuse/src/contract/tokens/nep141/deposit.rs])

### Summary
`Contract::ft_on_transfer` in the `defuse` contract credits the depositor's internal balance with the caller-supplied `amount` parameter without verifying that Defuse's own token balance in the underlying NEP-141 contract actually increased by that amount. For any NEP-141 token whose `ft_transfer_call` implementation deducts a transfer fee (or otherwise delivers less than the nominal `amount` reported to the receiver hook), Defuse mints internal ledger balance 1:1 with the nominal amount while only custodying `amount - fee`. This is the exact accounting mismatch described in the referenced `wfCashERC4626` finding: crediting the nominal/requested value instead of the actually-received value.

### Finding Description
`ft_on_transfer` derives `token_id` from `env::predecessor_account_id()` and unconditionally calls `self.deposit(receiver_id, [(token_id, amount.0)], ...)`, using the `amount` parameter passed by the token contract: [1](#0-0) 

`Contract::deposit` then unconditionally increases `total_supplies` and the owner's `token_balances` by that exact `amount`, with no reconciliation against Defuse's real balance held by the token contract: [2](#0-1) 

Per NEP-141, the `amount` value handed to `ft_on_transfer` is chosen by the token contract's `ft_transfer_call` implementation; nothing in the standard or in this code path enforces that Defuse's own balance on that token contract rose by exactly `amount`. A token contract that implements any kind of transfer fee (deduct-and-forward, rebasing, deflationary burn-on-transfer, etc.) will report the pre-fee amount while only delivering `amount - fee` into Defuse's custodial balance on that token contract. Defuse has no allowlist gating which NEP-141 contracts may be used — any predecessor account id becomes a valid `TokenId::Nep141`, so this is fully reachable by depositing any such fee-charging token, which is the intentionally permissionless design of the deposit hook.

The same unchecked-amount-credit pattern is also present in the NEP-245 deposit path, which trusts `amounts` reported by the calling multi-token contract: [3](#0-2) 

The mismatch surfaces on withdrawal: `ft_resolve_withdraw` treats a successful `ft_transfer`/`ft_transfer_call` promise as delivering the full withdrawn `amount`, and only refunds the internal ledger when the transfer promise itself fails: [4](#0-3) 

Because each deposit of the fee-on-transfer token inflates the internal ledger (`total_supplies` for that `TokenId`) beyond what Defuse actually holds on the real token contract, the shortfall accumulates across depositors. Whichever withdrawal(s) push cumulative withdrawals past Defuse's real (fee-reduced) balance on that token contract will fail (insufficient balance on the underlying FT contract), leaving those depositors permanently unable to redeem their credited balance — an insolvent, non-1:1-backed internal ledger for that `TokenId`.

### Impact Explanation
This breaks the conservation binding between "value credited into Defuse's internal ledger" and "value actually delivered into Defuse's custody." Once enough deposits/withdrawals of a fee-charging NEP-141 token occur, some legitimate depositors' balances of that `TokenId` become unbacked and their withdrawals permanently fail, i.e., funds are frozen — matching the Critical impact criterion "funds permanently frozen," analogous to the vault insolvency in the referenced `wfCashERC4626` report.

### Likelihood Explanation
No privileged role is required. Any unprivileged user can trigger this by depositing a NEP-141 token whose `ft_transfer_call` implementation applies any fee/short-delivery before invoking the receiver hook with the pre-fee amount; Defuse imposes no allowlist restricting which NEP-141 contracts may be used as deposit assets, and the deposit hook performs no post-transfer balance verification.

### Recommendation
In `ft_on_transfer` (and the analogous `mt_on_transfer` path), verify the actual balance delta on the token contract (e.g., via a balance-before/after check or `ft_balance_of` query) before crediting the internal ledger, rather than trusting the caller-reported `amount`/`amounts` parameter, or explicitly document/enforce that only tokens with guaranteed 1:1 transfer semantics (no fee-on-transfer, no rebasing) may be deposited, and reject/flag tokens that violate this invariant.

### Proof of Concept
1. Deploy (or use) a NEP-141 token contract `feeft.near` whose `ft_transfer_call` deducts a 5% fee: on `ft_transfer_call(defuse, amount=1000, ...)`, it debits sender 1000, credits Defuse's account only 950, but still calls `defuse.ft_on_transfer(sender, amount=U128(1000), msg)`.
2. User A calls `feeft.ft_transfer_call(defuse, 1000, msg)`. Defuse's `ft_on_transfer` credits User A's internal `Nep141(feeft.near)` balance with 1000 (`contracts/defuse/src/contract/tokens/nep141/deposit.rs:38-43`), while Defuse's real balance on `feeft.near` is only 950.
3. Repeat with User B depositing another 1000 (real balance +950, ledger +1000). Defuse's internal `total_supplies` for `Nep141(feeft.near)` is now 2000, but its real custodied balance on `feeft.near` is only 1900.
4. User A withdraws 1000 via `FtWithdraw`; `ft_resolve_withdraw` sees the `ft_transfer` promise succeed and treats it as fully used (`contracts/defuse/src/contract/tokens/nep141/withdraw.rs:174-181`), further reducing Defuse's real balance to 900 (since the withdrawal transfer itself may also be fee-affected, or simply because ledger claims exceed real holdings).
5. When User B attempts to withdraw their credited 1000, Defuse's underlying `ft_transfer` call to `feeft.near` fails due to insufficient real balance; the withdrawal is refunded back into the internal ledger but the underlying tokens can never be produced — User B's balance of `Nep141(feeft.near)` is permanently unbacked and unredeemable.

    fn ft_on_transfer(
        &mut self,
        sender_id: AccountId,
        amount: U128,

        require!(amount.0 > 0, "zero amount");

        let token_id = TokenId::Nep141(Nep141TokenId::new(env::predecessor_account_id()));

        let DepositMessage {
            receiver_id,
            action,
        } = if msg.is_empty() {
            DepositMessage::new(sender_id.clone())
        } else {
            msg.parse().unwrap_or_else(|e| panic!("{e}"))
        };

        self.deposit(
            receiver_id.clone(),
            [(token_id.clone(), amount.0)],
            Some("deposit"),
        )
        .unwrap_or_else(|err| err.panic());

    pub(crate) fn deposit(
        &mut self,
        owner_id: AccountId,
        tokens: impl IntoIterator<Item = (TokenId, u128)>,
        memo: Option<&str>,
    ) -> Result<()> {
        let owner = self
            .storage
            .accounts
            .get_or_create(owner_id.clone())
            // deposits are allowed for locked accounts
            .as_inner_unchecked_mut();

        let mut mint_event = MtMintEvent {
            owner_id: owner_id.into(),
            token_ids: Vec::new().into(),
            amounts: Vec::new().into(),
            memo: memo.map(Into::into),
        };

        for (token_id, amount) in tokens {
            if amount == 0 {
                return Err(DefuseError::InvalidIntent);
            }

            mint_event.token_ids.to_mut().push(token_id.to_string());
            mint_event.amounts.to_mut().push(amount);

            let total_supply = self
                .storage
                .state
                .total_supplies
                .add(token_id.clone(), amount)
                .ok_or(DefuseError::BalanceOverflow)?;
            match token_id {
                TokenId::Nep171(ref tid) => {
                    if total_supply > 1 {
                        return Err(DefuseError::NftAlreadyDeposited(tid.clone()));
                    }
                }
                TokenId::Nep141(_) | TokenId::Nep245(_) | TokenId::Imt(_) => {}
            }

            owner
                .token_balances
                .add(token_id, amount)
                .ok_or(DefuseError::BalanceOverflow)?;
        }

impl FungibleTokenWithdrawResolver for Contract {
    #[private]
    fn ft_resolve_withdraw(
        &mut self,
        token: AccountId,
        sender_id: AccountId,
        amount: U128,
        is_call: bool,
    ) -> U128 {
        let used = if is_call {
            // `ft_transfer_call` returns successfully transferred amount
            match promise_result_checked_json::<U128>(0) {
                Ok(Ok(used)) => used.0.min(amount.0),
                Ok(Err(_deserialize_err)) => 0,
                // do not refund on failed `ft_transfer_call` due to
                // NEP-141 vulnerability: `ft_resolve_transfer` fails to
                // read result of `ft_on_transfer` due to insufficient gas
                Err(_) => amount.0,
            }
        } else {
            // `ft_transfer` returns empty result on success
            if promise_result_checked_void(0).is_ok() {
                amount.0
            } else {
                0
            }
        };

        let refund = amount.0.saturating_sub(used);
        if refund > 0 {
            self.deposit(
                sender_id,
                [(Nep141TokenId::new(token).into(), refund)],
                Some(REFUND_MEMO),
            )
            .unwrap_or_else(|err| err.panic());
        }

        U128(used)
    }
