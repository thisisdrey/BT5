# RewardsDistributor credits a full `INITIAL_INDEX` delta to accounts whose checkpoint was never initialized - (contracts/RewardsDistributor.sol)

### Summary

`RewardsDistributor._calculateTokenDelta` only backstops an uninitialized `accountIndexOf` to `INITIAL_INDEX` when the current token index is strictly greater than `INITIAL_INDEX`. When the index still equals `INITIAL_INDEX` (i.e. the same block in which a token's speed is first set), the uninitialized account index is left at `0`, producing a delta of `balance * INITIAL_INDEX` and crediting the account reward equal to its entire deposit-token balance for zero accrual time. An unprivileged attacker can front-run the governor's `updateTokenSpeed` transaction with a (flash-funded) deposit and then call the permissionless `updateBeforeMintOrBurn` / `claimRewards` to drain reward tokens held by the distributor.

### Finding Description

In `contracts/RewardsDistributor.sol`, `_calculateTokenDelta` computes:

```solidity
uint256 _accountIndex = accountIndexOf[token_][account_];

if (_accountIndex == 0 && _tokenIndex > INITIAL_INDEX) {
    _accountIndex = INITIAL_INDEX;
}

uint256 _deltaIndex = _tokenIndex - _accountIndex;
_tokensDelta = token_.balanceOf(account_).wadMul(_deltaIndex);
``` [1](#0-0) 

The `> INITIAL_INDEX` comparison mirrors the source bug class exactly: the code fails to distinguish "account existed before this accounting epoch" from "account fresh," because it only checks whether the index *moved* past the initial checkpoint rather than whether the index is merely *at* the checkpoint. The correct guard is `>= INITIAL_INDEX`.

Sequence on the deployed configuration:

1. `updateTokenSpeed` (or the first `updateTokenSpeeds` containing a new token) sets `tokenStates[token_] = TokenState({index: INITIAL_INDEX, timestamp: block.timestamp})` via `_updateTokenSpeed` — the index is initialized but cannot advance within the same block because `_calculateTokenIndex` requires `_deltaTimestamps > 0`. [2](#0-1) 
2. Any call to `updateBeforeMintOrBurn` (permissionless, callable by anyone per its own docstring) or `claimRewards` in the same block runs `_updateTokensAccruedOf` → `_calculateTokenDelta` with `_tokenIndex == INITIAL_INDEX` and `accountIndexOf == 0`. The fallback does not trigger, so `_deltaIndex = INITIAL_INDEX = 1e18`, and `tokensAccruedOf[account] += balance.wadMul(1e18) = balance`. [3](#0-2) 
3. `claimRewards(account)` then calls `_transferRewardIfEnoughTokens`, which pays out `min(tokensAccruedOf, rewardToken.balanceOf(distributor))` with no further validation. [4](#0-3) 

Because `DepositToken.mint` applies `updateRewardsBeforeMintOrBurn` *before* the mint (index is `0` at that point, so the modifier is a no-op), a deposit made in the same block as the speed update leaves `accountIndexOf == 0` while the balance is nonzero. [5](#0-4) 

### Impact Explanation

Direct theft of unclaimed yield: the attacker is credited reward tokens equal to their deposit-token balance (in wad terms) despite accruing for zero seconds, and can withdraw the distributor's entire `rewardToken` balance (capped by that accrued amount). With a flash-loaned deposit sized to the distributor's reward balance, the full reward reserve is stolen in one bundle. Invariant broken: reward accrual conservation (rewards paid must correspond to `speed * time * share`).

### Likelihood Explanation

- The trigger requires landing a transaction in the same block as the governor's `updateTokenSpeed` for a newly-added token — standard mempool front-running/bundling, within the unprivileged-attacker model.
- `updateBeforeMintOrBurn` and `claimRewards` are explicitly public entry points; `claimRewards` is `nonReentrant` but that does not block the single-shot sequence.
- Deposit → (governor tx) → update + claim → withdraw is atomic-capable: deposits without minted debt are not locked (`lockedBalanceOf` only covers collateral backing debt), so the flash loan can be unwound in the same bundle.
- The window exists exactly once per reward token — the first time speed is set while `index == INITIAL_INDEX` — so likelihood is moderate rather than high, but requires no privileged action.

### Recommendation

Change the fallback condition in `_calculateTokenDelta` to initialize accounts at the current index whenever `accountIndexOf` is zero and the token state is initialized, e.g.:

```solidity
if (_accountIndex == 0 && _tokenIndex >= INITIAL_INDEX) {
    _accountIndex = _tokenIndex; // or INITIAL_INDEX; both avoid the epoch-boundary delta
}
```

Using `_tokenIndex` (instead of `INITIAL_INDEX`) also prevents future index-rewind edge cases. Alternatively, have `_updateTokenSpeed` set `timestamp` in a way that forces the index forward, or record an `initialized` flag on `TokenState`.

### Proof of Concept

Hardhat (against `contracts/` sources; mirrors `test/RewardDistributor.test.ts` setup):

```typescript
it('steals rewards via INITIAL_INDEX boundary', async () => {
  // attacker flash-funds collateral, deposits -> msdTOKEN1 balance, no debt
  await pool.connect(attacker).deposit(msdTOKEN1.address, depositAmount); // updateBeforeMintOrBurn no-ops: index == 0

  // governor tx lands in the SAME block (front-run bundle / automine off)
  await network.provider.send('evm_setAutomine', [false]);
  await rewardDistributor.connect(governor).updateTokenSpeed(msdTOKEN1.address, parseEther('1'));

  // same block: index == INITIAL_INDEX, timestamp == now
  await rewardDistributor.connect(attacker).updateBeforeMintOrBurn(msdTOKEN1.address, attacker.address);
  const accrued = await rewardDistributor.tokensAccruedOf(attacker.address);
  expect(accrued).to.eq(await msdTOKEN1.balanceOf(attacker.address)); // deltaIndex == 1e18

  await rewardDistributor.connect(attacker).claimRewards(attacker.address);
  // attacker receives min(accrued, rewardToken.balanceOf(distributor)) for zero accrual time
  await network.provider.send('evm_mine');
});
```

Equivalent Foundry sketch: deposit, `rewardDistributor.updateTokenSpeed` and `updateBeforeMintOrBurn` in the same block via `vm.roll`/same timestamp, then `claimRewards` — assert `tokensAccruedOf == depositToken.balanceOf(attacker)` and reward token transferred.
