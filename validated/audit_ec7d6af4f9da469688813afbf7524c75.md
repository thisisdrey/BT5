### Title
Deleted account's leftover `PostponedReceipt`/`PostponedReceiptId`/`PendingDataCount` bookkeeping is silently replayed against a newly-created account of the same `account_id`, enabling privileged action execution without the new owner's authorization - (File: `runtime/runtime/src/actions.rs`, `runtime/runtime/src/lib.rs`, `core/store/src/utils/mod.rs`)

### Summary
`check_account_existence`'s `CreateAccountAction` branch only checks `account.is_some()` [1](#0-0)  and `action_create_account` unconditionally mints a fresh `Account` [2](#0-1) . Neither this code nor `action_delete_account`/`remove_account` clears receiver-scoped `PostponedReceipt`, `PostponedReceiptId`, `PendingDataCount`, or `ReceivedData` entries keyed by that `account_id` [3](#0-2) , so a stale postponed receipt planted before deletion can later be delivered and executed against a completely new incarnation of the account.

### Finding Description
`remove_account` (used by `action_delete_account`) explicitly removes `Account`, `ContractCode`, access keys, gas keys and contract data, but never scans for or removes `TrieKey::PostponedReceipt`, `TrieKey::PostponedReceiptId`, `TrieKey::PendingDataCount`, or `TrieKey::ReceivedData` entries scoped to that `account_id` [3](#0-2) . `action_delete_account` then simply sets `*account = None` [4](#0-3) .

When a later `CreateAccountAction` targets the same `account_id`, `check_account_existence` only checks `account.is_some()` and returns `AccountAlreadyExists` only if a live `Account` row exists [1](#0-0) ; it never queries the leftover `PostponedReceiptId`/`PendingDataCount`/`ReceivedData` rows. `action_create_account` then mints a brand-new zero-balance `Account` with no awareness of, or attempt to clear, that residual state [2](#0-1) .

The residual state is not inert: `process_receipt`'s handling of an incoming `Data` receipt is keyed purely by `receiver_id` (the `account_id`), with no incarnation/version binding. It writes `ReceivedData`, looks up `TrieKey::PostponedReceiptId{receiver_id, data_id}`, decrements `PendingDataCount`, and once it reaches zero, fetches and executes the old `PostponedReceipt` via `apply_action_receipt` [5](#0-4) .

Exploit flow:
1. Attacker controls a parent account `p.near` and creates sub-account `s.p.near` (allowed since `s.p.near` is a valid sub-account of `p.near`, per `action_create_account`'s sub-account check [6](#0-5) ).
2. Attacker arranges (e.g., via their own or a third-party contract) an `ActionReceipt` sent to `s.p.near` with an unmet `input_data_id`, whose predecessor/actor is `s.p.near` itself (a legitimate self-callback pattern), and whose actions include privileged operations such as `AddKey` or `DeployContract`. This gets stored as `PostponedReceipt`/`PendingDataCount`/`PostponedReceiptId` for `s.p.near`.
3. Before the matching `DataReceipt` arrives, attacker deletes `s.p.near` via `DeleteAccountAction` (refunding its own balance). `remove_account` wipes the `Account`/keys/code/data but leaves the postponed-receipt bookkeeping intact.
4. Attacker (or a buyer who subsequently acquires control of `p.near`, e.g. through a sold/transferred named parent account) creates a fresh `s.p.near` again — `check_account_existence`/`action_create_account` place no restriction on this because they never inspect the residual rows.
5. At a time of the attacker's choosing (they control the originating contract/data flow), the matching `DataReceipt` is delivered. `process_receipt` finds the still-present `PostponedReceiptId` link, decrements `PendingDataCount` to zero, and executes the stale `PostponedReceipt`'s actions against the *new* account. Because the stale receipt's `predecessor_id`/actor was `s.p.near` itself, `actor_id == account_id` checks for `AddKey`/`DeployContract`/`Stake`/`DeleteAccount` all pass [7](#0-6) , letting the attacker silently inject a full-access key or replace the contract on the new owner's account without their consent.

### Impact Explanation
This breaks the invariant that account deletion terminates all future state effects on that `account_id`; a new, unrelated owner of the same account name can have privileged actions (key injection, contract replacement) executed against their account without ever authorizing them. This matches the "authorization escalation across accounts or promises" bounty category, since a receipt authorized under one account incarnation is later applied to an unrelated new incarnation.

### Likelihood Explanation
The attacker needs only ordinary account/contract capabilities: create a sub-account, arrange a self-targeted receipt with an unresolved data dependency, delete the account, and (to affect a third party) subsequently transfer/sell control of the parent account so someone else recreates the same sub-account name — a real-world pattern for named "premium" sub-accounts. The attacker fully controls the timing of the resolving `DataReceipt`, making this deterministic and repeatable, and requires no validator/node access, only standard signed transactions.

### Recommendation
Bind postponed-receipt bookkeeping to an account incarnation identifier (e.g., include a per-account creation nonce/version in the `TrieKey`s, or invalidate/purge them), or have `action_delete_account`/`remove_account` scan and remove all `PostponedReceipt`, `PostponedReceiptId`, `PendingDataCount`, and `ReceivedData` entries for the account before deletion completes (and reject/refund any thereby-orphaned in-flight data receipts).

### Proof of Concept
Integration test using the existing test harness (`runtime/runtime/src/tests/apply.rs`) modeled on `test_promise_input_size_limit_exceeded_fails_and_cleans_up` [8](#0-7) :
1. Create account `bob.alice.near`.
2. Deliver an `ActionReceipt` to it containing an `AddKey` action, with `input_data_ids = [data_id]` unresolved, so it is stored as a postponed receipt.
3. Deliver a `DeleteAccount` action for `bob.alice.near` (predecessor = `bob.alice.near`), refunding balance to `alice.near`.
4. Assert via `get_postponed_receipt`/`TrieKey::PendingDataCount`/`TrieKey::PostponedReceiptId` that the bookkeeping still exists for `bob.alice.near` after deletion (this is the root-cause assertion).
5. Deliver `CreateAccountAction` again for `bob.alice.near` from `alice.near` — assert it succeeds (`check_account_existence` doesn't reject it).
6. Deliver the matching `DataReceipt` for `data_id` — assert the stale `AddKey` action executes and the new `bob.alice.near` account unexpectedly gains the attacker's key, without any transaction from the new account owner authorizing it.

/// Removes account, code and all access keys and gas keys associated to it.
pub fn remove_account(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
) -> Result<RemoveAccountResult, StorageError> {
    state_update.remove(TrieKey::Account { account_id: account_id.clone() });
    state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });

    let mut gas_key_nonce_count: usize = 0;
    let mut gas_key_nonce_total_key_bytes: usize = 0;

    // Removing access keys and gas key nonces
    let lock = state_update.trie().lock_for_iter();
    let mut keys_to_remove: Vec<TrieKey> = Vec::new();
    for raw_key in state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_access_keys(account_id), &lock)?
    {
        let raw_key = raw_key?;
        let key_handle = trie_key_parsers::parse_key_handle_from_access_key_key(
            &raw_key, account_id,
        )
        .map_err(|_e| {
            StorageError::StorageInconsistentState(
                "Can't parse key handle from raw key for AccessKey".to_string(),
            )
        })?;
        let nonce_index =
            trie_key_parsers::parse_nonce_index_from_gas_key_key(&raw_key, account_id, &key_handle)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse nonce index from raw key for AccessKey".to_string(),
                    )
                })?;
        if let Some(index) = nonce_index {
            gas_key_nonce_count += 1;
            gas_key_nonce_total_key_bytes += raw_key.len();
            keys_to_remove.push(TrieKey::gas_key_nonce(
                account_id.clone(),
                key_handle.clone(),
                index,
            ));
        } else {
            keys_to_remove.push(TrieKey::access_key(account_id.clone(), key_handle.clone()));
        }
    }
    drop(lock);

    for trie_key in keys_to_remove {
        state_update.remove(trie_key);
    }

    // Removing contract data
    let lock = state_update.trie().lock_for_iter();
    let data_keys = state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_contract_data(account_id, &[]), &lock)?
        .map(|raw_key| {
            trie_key_parsers::parse_data_key_from_contract_data_key(&raw_key?, account_id)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse data key from raw key for ContractData".to_string(),
                    )
                })
                .map(Vec::from)
        })
        .collect::<Result<Vec<_>, _>>()?;
    drop(lock);

    for key in data_keys {
        state_update.remove(TrieKey::ContractData { account_id: account_id.clone(), key });
    }
    Ok(RemoveAccountResult { gas_key_nonce_count, gas_key_nonce_total_key_bytes })

#[test]
fn test_promise_input_size_limit_exceeded_fails_and_cleans_up() {
    let (runtime, tries, root, mut apply_state, _, epoch_info_provider) = setup_runtime(
        vec![alice_account(), bob_account()],
        Balance::from_near(1_000_000),
        Balance::from_near(500_000),
        Gas::from_teragas(1000),
    );
    setup_promise_input_limit(&mut apply_state, promise_input_limit_version());

    let data_id_1 = hash(b"promise-input-exceeded-1");
    let data_id_2 = hash(b"promise-input-exceeded-2");
    let receipt_id = hash(b"promise-input-exceeded-receipt");
    // Two data receipts, each below `max_length_returned_data` (4 MiB) so they
    // pass receipt validation, but whose combined size exceeds the limit.
    let half = (PROMISE_INPUT_SIZE_LIMIT / 2 + 1) as usize;
    let receipts = vec![
        promise_data_receipt(alice_account(), data_id_1, half),
        promise_data_receipt(alice_account(), data_id_2, half),
        action_receipt_awaiting(alice_account(), receipt_id, vec![data_id_1, data_id_2]),
    ];

    let apply_result = runtime
        .apply(
            tries.get_trie_for_shard(ShardUId::single_shard(), root),
            &None,
            &apply_state,
            &receipts,
            SignedValidPeriodTransactions::empty(),
            &epoch_info_provider,
            Default::default(),
        )
        .unwrap();

    let outcome = apply_result
        .outcomes
        .iter()
        .find(|o| o.id == receipt_id)
        .expect("awaiting receipt should have an execution outcome");
    match &outcome.outcome.status {
        ExecutionStatus::Failure(TxExecutionError::ActionError(action_error)) => {
            assert_matches!(
                action_error.kind,
                ActionErrorKind::TotalPromiseInputSizeExceeded { .. }
            );
        }
        other => panic!("expected TotalPromiseInputSizeExceeded failure, got {other:?}"),
    }

    // The received data and postponed bookkeeping must be cleaned up.
    let mut store_update = tries.store_update();
    let new_root =
        tries.apply_all(&apply_result.trie_changes, ShardUId::single_shard(), &mut store_update);
    store_update.commit();
    let state = tries.new_trie_update(ShardUId::single_shard(), new_root);
    assert_eq!(get_received_data(&state, &alice_account(), data_id_1).unwrap(), None);
    assert_eq!(get_received_data(&state, &alice_account(), data_id_2).unwrap(), None);
    assert_eq!(get_postponed_receipt(&state, &alice_account(), receipt_id).unwrap(), None);
}
