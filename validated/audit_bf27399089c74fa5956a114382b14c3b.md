### Title
Missing null-check on unregistered `ContractType` actuator class causes unhandled `NullPointerException` in `ActuatorFactory` - (File: actuator/src/main/java/org/tron/core/actuator/ActuatorFactory.java)

### Summary
`ActuatorFactory.getActuatorByContract` looks up an `Actuator` implementation class for a transaction's `Contract.getType()` via `TransactionFactory.getActuator(type)` and immediately calls `.newInstance()` on the result without checking for `null`, unlike the sibling class `ActuatorCreator` which explicitly guards against this case.

### Finding Description
`TransactionFactory.getActuator(ContractType)` returns whatever is stored in a `ConcurrentHashMap<ContractType, Class<? extends Actuator>>`, or `null` if the type was never registered [1](#0-0) . Registration happens via reflective scanning of `AbstractActuator` subclasses at startup, so any `ContractType` enum value that does not have a corresponding actuator class (including the protobuf `UNRECOGNIZED` sentinel produced when an unknown enum number is present in the wire bytes) resolves to `null`.

`ActuatorCreator.getActuatorByContract` defends against this by explicitly checking for `null` and throwing a `ContractValidateException`: [2](#0-1) 

However, `ActuatorFactory.getActuatorByContract` — a separate, parallel implementation of the same lookup logic — does **not** perform this check before calling `clazz.newInstance()`: [3](#0-2) 

If `clazz` is `null` (unregistered/`UNRECOGNIZED` contract type), `clazz.newInstance()` throws a `NullPointerException`. This call happens inside a `forEach` lambda whose `catch` block only handles `IllegalAccessException | InstantiationException`, not `NullPointerException`: [4](#0-3) 

Because `NullPointerException` is unchecked and not caught, it propagates out of `createActuator(...)` entirely uncaught by the method's own logic, unlike `ActuatorCreator`'s path which converts the failure into a handled `ContractValidateException`. This is directly analogous to the Spring Cloud Function bug class: an operation that references a non-existent/uninitialized handler (a "function" that doesn't exist) throws instead of failing gracefully, and this is reachable by attacker-controlled composed input (here, a `Contract.getType()` value with no registered actuator).

### Impact Explanation
An uncaught `NullPointerException` thrown from a code path processing external transaction/contract data can crash or destabilize the thread/service handling the request, depending on which caller invokes `ActuatorFactory.createActuator`. If reached from a request-serving thread without further exception handling upstream, this can result in denial of service for that request path or, if unhandled at a higher level, disrupt node operation — matching the "node crash / API the node can no longer serve" impact bar.

### Recommendation
Add a `null` check for `clazz` in `ActuatorFactory.getActuatorByContract` (mirroring `ActuatorCreator`) and propagate a handled validation exception instead of allowing `NullPointerException` to escape, and ensure the `forEach` catch block in `createActuator` also handles unexpected `RuntimeException`s so no unregistered/`UNRECOGNIZED` contract type can crash the caller.

      TransactionCapsule tx) throws IllegalAccessException, InstantiationException {
    Class<? extends Actuator> clazz = TransactionFactory.getActuator(contract.getType());
    AbstractActuator abstractActuator = (AbstractActuator) clazz.newInstance();
