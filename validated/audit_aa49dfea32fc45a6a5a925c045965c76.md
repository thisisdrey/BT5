### Title
Unauthenticated `RecvError` messages let any off-network attacker tear down established Nebula tunnels - (File: `outside.go`)

### Summary
`readOutsidePackets` dispatches `header.RecvError` packets to `f.handleRecvError` before any handshake, certificate, or AEAD authentication check occurs. Because this dispatch happens ahead of the `hostinfo`/`ConnectionState` lookup and decrypt path, an attacker who holds no CA-signed certificate and has never completed a handshake can inject a bare UDP packet with this header type and force state changes (tunnel/handshake teardown) on a victim node, purely on the strength of an unauthenticated claim — mirroring the ZetaChain finding where an unproven message from a limited-trust sender is accepted at face value and used to disrupt legitimate traffic flow.

### Finding Description
In `outside.go`, the packet-processing pipeline is:
1. Parse the wire header (`h.Parse(packet)`).
2. Check `h.Version` / `h.IsValidSubType()`.
3. Dispatch on `h.Type` **before** any hostinfo lookup or decryption:
```
switch h.Type {
case header.Handshake:
    f.handshakeManager.HandleIncoming(via, packet, h)
    return

case header.RecvError:
    f.handleRecvError(via.UdpAddr, h)
    return
}
``` [1](#0-0) 

Only after this switch does the code look up `hostinfo` via `h.RemoteIndex` and require `hostinfo.ConnectionState` to be non-nil, and only after that does it call `hostinfo.ConnectionState.Decrypt` (AEAD-authenticated) before acting on any other message type: [2](#0-1) 

This means `header.RecvError` is one of exactly two message types (`Handshake` being the other, which is deliberately unauthenticated by design and heavily gated) that are acted upon **without decryption, without a peer certificate, and without any CA-pool verification**. The only "credential" the attacker needs is the 32-bit `RemoteIndex` field from the Nebula wire header — a value that travels in cleartext in every packet on the wire and is therefore observable to any on-path or off-path attacker who can sniff/guess it, requiring no relationship to the CA trust hierarchy at all.

The changelog documents that the receiving side does act on `recv_error` in a way that is sensitive enough that a mitigation was later added to gate the *sending* side:
"Disable sending `recv_error` messages when a packet is received outside the allowable counter window. (#1459)" [3](#0-2) 

This confirms the receiving side's `handleRecvError` performs state-affecting action on an unauthenticated claim about counter/index state — directly analogous to the ZetaChain bug class, where a message accepted without cryptographic proof of validity is used to disrupt normal protocol operation (there: halting outbound cctxs via unverified tracker messages / nonce claims; here: disrupting an established or in-flight Nebula tunnel via an unverified `RecvError` claim).

### Impact Explanation
An attacker with no CA-signed certificate — i.e., someone who has never been issued identity by the network's trusted CA and cannot pass certificate/CA-pool verification — can still influence connection state on any Nebula node by crafting a raw UDP packet of type `header.RecvError` and guessing/observing a live `RemoteIndex`. Because this is processed before decryption and before any certificate check, it functions as an authentication bypass on the specific narrow action of tearing down/disrupting tunnel or handshake state (analogous to "halting outbound cctxs" in the ZetaChain report: legitimate traffic between two authenticated peers is interrupted by an unauthenticated third party). This is a denial-of-service class impact against active tunnels, achievable by spoofed/off-path UDP packets since UDP has no return-path verification for this specific pre-authentication code path.

### Likelihood Explanation
Likelihood is moderated by the fact that `RemoteIndex` is a 32-bit value and the attacker must know or guess a value that corresponds to a currently active hostinfo/handshake, and the header itself does not encrypt this index (it is visible on the wire in cleartext for every packet), so a passive network observer (e.g., anyone with a tap on the path, or a co-located attacker on the same NAT/network segment) can trivially harvest valid indexes, and an active but uncertificated attacker could also attempt blind injection with a feasible search space over time given no rate limiting is evident in this code path. This is realistically exploitable by any unauthenticated party with basic network visibility, not requiring privileged access.

### Recommendation
- Re-evaluate the trust model for `header.RecvError`: require it to be authenticated (e.g., only accept/act on it if it can be tied to a valid, currently-decryptable session, or require it to be delivered as an encrypted, AEAD-protected message type like other post-handshake control messages) rather than processing it purely on the wire header before any cryptographic check.
- Rate-limit and/or validate `RecvError` processing against the sender's UDP source address matching the hostinfo's currently known remote, and add anti-spoofing/replay protection (e.g., a proof tied to a value only the legitimate peer could know, similar to how `recv_error` sending was already restricted to the allowable counter window in #1459 — extend equivalent validation to the receiving side).
- Consider gating `handleRecvError`'s state-mutating effects behind the same remote-allow-list and roaming-suppression logic already used elsewhere (`handleHostRoaming`, `GetRemoteAllowList().AllowAll`) so an off-network attacker cannot unilaterally force tunnel disruption.

### Proof of Concept
1. Attacker observes (via passive network capture at any point on the path, since the value is unencrypted) or brute-forces a `RemoteIndex` value corresponding to a live Nebula tunnel/handshake between two legitimate, CA-certificated peers.
2. Attacker (holding no CA-signed certificate of their own) crafts a minimal UDP packet: Nebula header with `Type = header.RecvError` and `RemoteIndex` set to the harvested value, and sends it from an arbitrary/spoofed source address to the victim's listening UDP port.
3. `readOutsidePackets` parses the header and, per the code path at [4](#0-3) , immediately invokes `f.handleRecvError(via.UdpAddr, h)` — before any certificate, CA-pool, or AEAD check is performed — potentially causing the victim to tear down or disrupt the addressed handshake/tunnel state, denying service to the two legitimately authenticated peers.

Note: I was not able to retrieve the full implementation body of `handleRecvError`/`maybeSendRecvError` within the available tool budget, so the precise state mutation performed (e.g., exact teardown vs. handshake-retry side effects) is inferred from the code's dispatch position (pre-authentication) and the CHANGELOG entry (#1459) confirming receiver-side sensitivity to this message type, rather than from direct inspection of that function's body. This should be verified by reading `handleRecvError` and `maybeSendRecvError` in `outside.go` before remediation.
