### Title
Path traversal via unvalidated `BackupId` in `RestoreRepository` allows reading another repository's backup - ([File: internal/gitaly/service/repository/restore_repository.go])

### Summary
`RestoreRepository` passes `in.GetBackupId()` straight to `backup.Manager`/`ManifestLocator` without any validation, while `PathPrefix` is explicitly checked with `backup.ValidatePathPrefix`. The locator and manifest loader build backup object paths with a bare `filepath.Join`/`path.Join` of `backupID`, so a `BackupId` containing `../` sequences can escape the caller's own repository backup directory and resolve to another repository's manifest/bundle/refs files on the same backup sink.

### Finding Description
`RestoreRepository` validates `Repository`, `VanityRepository`, and `PathPrefix`, but never validates `BackupId` before forwarding it into `backup.RestoreRequest.BackupID`: [1](#0-0) [2](#0-1) 

The manifest-based locator builds the manifest path with `path.Join`/`filepath.Join` of `pathPrefix`, storage name, repo relative path, and `backupID`, with no containment check: [3](#0-2) 

The same pattern is used for building bundle/ref/custom-hooks step paths in `BeginFull`/`BeginIncremental`, which directly interpolate `backupID` via `filepath.Join(cfg.pathPrefix, storageName, relativePath, backupID, "001.bundle")` etc.: [4](#0-3) [5](#0-4) 

Unlike `ValidatePathPrefix`, which explicitly rejects absolute paths and `..` components: [6](#0-5) 

there is no equivalent validation function applied to `backupID` anywhere in the restore path. The resulting joined path is passed straight into `Sink.GetReader`/`GetWriter`, which hand the relative path directly to the underlying blob bucket (`gocloud.dev/blob`) with no re-validation against the storage root, unlike `storage.ValidateRelativePath` used elsewhere in the codebase (e.g. for object-directory paths) which explicitly rejects paths escaping the root: [7](#0-6) [8](#0-7) 

Because `filepath.Join`/`path.Join` clean `..` segments, an attacker-controlled `BackupId` such as `../../../<victim-storage>/<victim-repo>.git/<victim-backup-id>` can cause the join to resolve outside the attacker's own repo's backup subtree and land on another tenant's manifest/bundle path within the same backup root. `ManifestLocator.Find` then reads that manifest and `restoreBundle` fetches the referenced bundle, both of which the RPC caller controls entirely through the crafted `BackupId`, allowing the victim's bundle/refs content to be fetched into the attacker's own repository via `FetchBundle`.

### Impact Explanation
An unprivileged attacker who can call `RestoreRepository` on their own repository (server-side backups configured) can supply a crafted `BackupId` to make the restore operation read a different repository's backup manifest, refs, and bundle files from the shared backup sink and merge that content into their own repository. This is a cross-tenant information disclosure of another project's full Git history/objects, matching GitLab's "unauthorized access to private repository data" bounty impact class.

### Likelihood Explanation
Requires server-side backups to be enabled (a supported, documented Gitaly feature, not an unusual configuration) and requires the attacker to guess/know another repository's storage name, relative path, and backup ID — backup IDs are often predictable (e.g. timestamp-based, sequential run IDs), and storage/relative paths for GitLab projects are also derivable/guessable in many self-managed setups. Given those, the exploit is a single RPC call with no additional privilege, and is fully repeatable/scriptable.

### Recommendation
Validate `BackupId` the same way `PathPrefix` is validated: reject empty components, `.`/`..` segments, absolute paths, and any input that is not a clean single path segment or a well-formed ID matching an allow-listed format (e.g. `^[A-Za-z0-9_-]+$`). Apply this validation both in `validateRestoreRepositoryRequest` (for `RestoreRepository`) and inside `ManifestLocator.Find`/`BeginFull`/`BeginIncremental` before path construction. Additionally, after building any sink-relative path from user-influenced components, run it through a `storage.ValidateRelativePath`-style containment check against the expected `<storageName>/<relativePath>` root before calling `Sink.GetReader`/`GetWriter`.

    backupPath := testhelper.TempDir(t)

    // Victim's backup, stored under its own storage/relative path.

    })

    sink, err := backup.ResolveSink(ctx, backupPath)
    require.NoError(t, err)
    l := backup.NewLocator(sink)

    // Attacker owns "attacker/repo.git" and crafts BackupId with traversal
    // to reach the victim's manifest under "victim/repo.git".
    attackerRepo := &gitalypb.Repository{
        StorageName:  "default",
        RelativePath: "attacker/repo.git",
    }
    maliciousBackupID := "../../victim/repo.git/victim-backup"

    got, err := l.Find(ctx, attackerRepo, maliciousBackupID)
    require.NoError(t, err) // if vulnerable: succeeds and returns victim's manifest
    require.Equal(t, "default/victim/repo.git/victim-backup/001.bundle", got.Steps[0].BundlePath)

Expected on a patched (fixed) implementation: `Find` returns an error (e.g. invalid backup ID / traversal rejected) instead of resolving into `victim/repo.git`. On the current code, `manifestPath` joins the traversal segments and the manifest — and subsequently the bundle referenced by it — resolves under the victim's path, which `RestoreRepository` would then fetch (`restoreBundle`) into the attacker's own repository.

// ValidatePathPrefix validates that the backup path prefix is safe for use in path construction.
// It rejects absolute paths and paths containing ".." to prevent directory traversal attacks.
// Returns ErrInvalidPathPrefix if validation fails.
func ValidatePathPrefix(prefix string) error {
	if prefix == "" {
		// Empty prefix is allowed
		return nil
	}

	if filepath.IsAbs(prefix) {
		return fmt.Errorf("%w: must be a relative path", ErrInvalidPathPrefix)
	}

	for _, part := range strings.Split(prefix, "/") {
		if part == "" || strings.Trim(part, ".") == "" {
			return fmt.Errorf("%w: must be a clean relative path without traversal", ErrInvalidPathPrefix)
		}
	}

	return nil
}

// GetWriter stores the written data into a relativePath path on the configured
// bucket. It is the callers responsibility to Close the reader after usage.
func (s Sink) GetWriter(ctx context.Context, relativePath string) (io.WriteCloser, error) {
	writer, err := s.bucket.NewWriter(ctx, relativePath, &blob.WriterOptions{
		BufferSize: s.bufferSize,
		// 'no-store' - we don't want the backup to be cached as the content could be changed,
		// so we always want a fresh and up to date data
		// https://developer.mozilla.org/en-US/docs/Web/HTTP/Headers/Cache-Control#cacheability
		// 'no-transform' - disallows intermediates to modify data
		// https://developer.mozilla.org/en-US/docs/Web/HTTP/Headers/Cache-Control#other
		CacheControl: "no-store, no-transform",
		ContentType:  "application/octet-stream",
	})
	if err != nil {
		return nil, fmt.Errorf("sink: new writer for %q: %w", relativePath, err)
	}
	return writer, nil
}

// GetReader returns a reader to consume the data from the configured bucket.
// It is the caller's responsibility to Close the reader after usage.
func (s Sink) GetReader(ctx context.Context, relativePath string) (io.ReadCloser, error) {
	reader, err := s.bucket.NewReader(ctx, relativePath, nil)
	if err != nil {
		if gcerrors.Code(err) == gcerrors.NotFound {
			err = ErrDoesntExist
		}
		return nil, fmt.Errorf("sink: new reader for %q: %w", relativePath, err)
	}
	return reader, nil
}

// ValidateRelativePath validates a relative path by joining it with rootDir and verifying the result
// is either rootDir or a path within rootDir. Returns clean relative path from rootDir to relativePath
// or an ErrRelativePathEscapesRoot if the resulting path is not contained within rootDir.
func ValidateRelativePath(rootDir, relativePath string) (string, error) {
	absPath := filepath.Join(rootDir, relativePath)
	if rootDir != absPath && !strings.HasPrefix(absPath, rootDir+string(os.PathSeparator)) {
		return "", ErrRelativePathEscapesRoot
	}

	return filepath.Rel(rootDir, absPath)
}
