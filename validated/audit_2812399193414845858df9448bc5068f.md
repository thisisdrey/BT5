Audit Report

## Title
Relayer reward paid regardless of Ethereum delivery outcome in `process_delivery_receipt` - (File: bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs)

## Summary
`DeliveryReceipt::try_from` decodes an explicit `success: bool` field from the Ethereum `InboundMessageDispatched` event log, but `Pallet::process_delivery_receipt` never reads or branches on `receipt.success` before paying the relayer reward. As a result, a relayer submitting a valid receipt for a reverted/failed inbound dispatch on Ethereum is paid the full `order.fee` exactly as if the delivery had succeeded.

## Finding Description
`DeliveryReceipt::try_from` decodes `success` straight from the Solidity event and stores it on the struct: [1](#0-0) .

In `process_delivery_receipt`, only `receipt.gateway`, `receipt.reward_address`, and `receipt.nonce` are consulted; `receipt.success` is never inspected, and a grep across the repository confirms no other code path reads this field either: [2](#0-1) .

The extrinsic wrapper `submit_delivery_receipt` verifies the log's provenance via `T::Verifier::verify` (which authenticates that the log is genuine, not its semantic `success` value), decodes the receipt, and unconditionally forwards to `process_delivery_receipt`: [3](#0-2) .

Regardless of whether the Gateway contract emitted `success = true` or `success = false`, the pallet pays `order.fee` to `reward_account` via `T::RewardPayment::register_reward`, removes the `PendingOrder` from storage, and emits `Event::MessageDelivered`. Existing guards (`GatewayAddress` check, `PendingOrders` existence check, `T::Verifier::verify`) only validate origin/provenance and nonce existence — none of them differentiate delivery outcome, so the intended reward-on-success gate is effectively absent from the code.

## Impact Explanation
This matches the "public underpriced work" impact category in the required impact gate: any permissionless relayer can collect the full relayer fee (`order.fee`) for work that did not actually complete successfully on Ethereum, since the pallet's payout logic (`T::RewardPayment::register_reward` call at lines 468-472) is not gated by `receipt.success`. This degrades the incentive alignment of the delivery-receipt mechanism, decoupling fee payout from actual successful bridge action, and is exploitable without any privileged, governance, or compromised-relayer assumption.

## Likelihood Explanation
High. The flow is invoked directly through the public, signed `submit_delivery_receipt` extrinsic. `T::Verifier::verify` only authenticates that the log is genuine and was emitted by the correct gateway/gateway address — it says nothing about the semantic `success` field. Any relayer causing a command dispatch on the Gateway contract to revert (while the contract still emits `InboundMessageDispatched` with `success=false`, as is standard Snowbridge behavior for resolving pending orders on failure) can obtain and submit a valid receipt/proof and be paid identically to a successful delivery, deterministically and repeatably for every message.

## Recommendation
Branch on `receipt.success` in `process_delivery_receipt`: only call `T::RewardPayment::register_reward` when `receipt.success == true`. For `receipt.success == false`, withhold or reduce the fee (e.g., refund to origin, apply penalty accounting, or route through a distinct failure-handling path), while still resolving/removing the `PendingOrder` (or otherwise ensuring it cannot be resubmitted indefinitely) via a code path distinct from the success path.

## Proof of Concept
1. Send a message through the outbound queue (`do_process_message`), creating a `PendingOrder{nonce, fee>0}` as shown at `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs` lines 426-440.
2. On Ethereum, arrange for the corresponding inbound message dispatch to revert (e.g., a downstream call that reverts due to gas or logic conditions); the Gateway still emits `InboundMessageDispatched(nonce, topic, success=false, reward_address)`.
3. Relay this event log and its proof via `submit_delivery_receipt`.
4. `T::Verifier::verify` succeeds (log is authentic), `DeliveryReceipt::try_from` decodes `success = false`, but `process_delivery_receipt` still executes `T::RewardPayment::register_reward(&reward_account, ..., order.fee)` and removes the order — as can be demonstrated by adapting the existing test `submit_delivery_receipt_succeeds_after_unhalt` at `bridges/snowbridge/pallets/outbound-queue-v2/src/test.rs` lines 420-449 to set `success: false` in the mocked event log and asserting the reward is still registered, confirming the missing gate.

			let reward_account = if receipt.reward_address == [0u8; 32] {

			let nonce = receipt.nonce;

			if order.fee > 0 {
				// Pay relayer reward

				);
			}

			<PendingOrders<T>>::remove(nonce);
