### Title
Active-permission delegate can fully overwrite Owner permission and lock out the account owner via `AccountPermissionUpdateContract` - (File: `actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java`)

### Summary
`AccountPermissionUpdateActuator` lets any signer whose Active permission has the `AccountPermissionUpdateContract` bit set in its `operations` bitmap completely replace the account's `Owner` permission — not merely modify permissions within its own scope. Because permission scoping in java-tron is enforced only at the coarse contract-type level (a 256-bit "which contract types may this key sign" bitmap), an owner who delegates a narrow, seemingly low-risk capability (the ability to submit `AccountPermissionUpdateContract` transactions, e.g. for routine key-rotation automation) inadvertently grants that delegate full, unilateral control to seize the account and lock out the legitimate owner — the same bug class as CVE-2017-4959 (an authorized-but-lower-privileged user taking over another account and causing lockout).

### Finding Description
Transaction-level permission enforcement in `TransactionCapsule.checkPermission` only checks two things for a non-Owner (`permissionId != 0`) signer: that the permission type is `Active`, and that the specific `ContractType` bit for the submitted contract is set in that permission's `operations` bitmap: [1](#0-0) 

This is the same coarse check used in `Wallet.getTransactionApprovedList` and `TransactionUtil.getTransactionSignWeight`: [2](#0-1) [3](#0-2) 

There is no finer-grained restriction preventing an Active-permission key (scoped only by contract type) from using `AccountPermissionUpdateContract` to rewrite the Owner permission entirely. In `AccountPermissionUpdateActuator.validate()`, the only requirement is that the target `ownerAddress` account exists and that the submitted `owner`/`witness`/`active` permission structures are internally well-formed (key counts, thresholds, weight sums, valid addresses, valid operation bits) — there is no check tying the *submitted* new owner permission back to what the *signing* permission is authorized to change: [4](#0-3) 

`execute()` then unconditionally overwrites the account's Owner (and Witness/Active) permission with attacker-supplied data: [5](#0-4) [6](#0-5) 

Because `AccountPermissionUpdateContract` is a normal `ContractType`, an owner setting up an Active permission that includes this bit (for example, to let an automated key-rotation service or a delegated administrator submit routine `AccountPermissionUpdateContract` transactions) has effectively delegated full account ownership: that Active key can submit a transaction that sets a brand-new Owner permission (arbitrary keys, arbitrary threshold) with no keys belonging to the original owner, permanently locking the real owner out of the account, changing the Witness permission (if applicable), and rewriting all Active permissions to keys it controls.

### Impact Explanation
This constitutes concrete unauthorized account takeover and permanent loss of account control matching the "Accept only" criteria: an attacker holding a narrowly-scoped Active key (one only meant to submit `AccountPermissionUpdateContract` transactions for legitimate operational reasons) can seize full custody of the account, permanently locking out the legitimate owner and all other Active/Witness keys, and can subsequently move funds or control the account/witness with self-chosen keys and threshold.

### Likelihood Explanation
Requires the account owner to have previously granted an Active permission whose `operations` bitmap includes the `AccountPermissionUpdateContract` bit (bit index corresponding to that `ContractType`). This is a legitimate, documented multi-sig delegation pattern (permission management delegated to an automated/administrative key), so it is realistic that such permissions exist in production deployments. Once such a permission exists, exploitation requires only a single signed transaction from that key — no race conditions, no additional privilege, and no interaction with other actors.

### Recommendation
Restrict what an Active-permission-authorized `AccountPermissionUpdateContract` transaction may change: e.g., disallow submitting an Owner permission whose key set does not retain the current Owner's threshold-satisfying keys, or require that only the Owner permission itself (or unanimous Owner-level signatures) may modify the Owner permission, regardless of the coarse `operations` bitmap. Alternatively, exclude `AccountPermissionUpdateContract` from the set of contract types that can be granted to non-Owner Active permissions, or add an explicit "cannot remove/replace all current owner keys" invariant check inside `AccountPermissionUpdateActuator.validate()`.

### Proof of Concept
1. Owner account `A` creates an Active permission `P` (id ≥ 2) with `operations` bitmap having the `AccountPermissionUpdateContract` bit set, and grants it to key `K` (e.g., for automated permission maintenance), per `checkPermission`'s bitmap-only enforcement: [1](#0-0) 
2. Attacker (holding `K`) crafts an `AccountPermissionUpdateContract` with `owner_address = A`, `permission_id = P.id`, and a new `Owner` permission that contains only attacker-controlled keys and a threshold `K` alone can satisfy.
3. Attacker signs and broadcasts the transaction; `AccountPermissionUpdateActuator.validate()` passes because all structural checks succeed (see `checkPermission` at lines 71-146) and `execute()` calls `account.updatePermissions(...)`, replacing the Owner permission unconditionally: [7](#0-6) 
4. Account `A`'s original owner keys are now removed from the Owner permission; the original owner can no longer sign Owner-level transactions on `A`, while the attacker (via the new Owner keys) has full control.

  public boolean validate() throws ContractValidateException {

    if (chainBaseManager == null) {
      throw new ContractValidateException(ActuatorConstant.STORE_NOT_EXIST);
    }

    if (this.any == null) {
      throw new ContractValidateException(ActuatorConstant.CONTRACT_NOT_EXIST);
    }

    AccountStore accountStore = chainBaseManager.getAccountStore();
    DynamicPropertiesStore dynamicStore = chainBaseManager.getDynamicPropertiesStore();

    if (dynamicStore.getAllowMultiSign() != 1) {
      throw new ContractValidateException("multi sign is not allowed, "
          + "need to be opened by the committee");
    }
    if (!this.any.is(AccountPermissionUpdateContract.class)) {
      throw new ContractValidateException(
          "contract type error,expected type [AccountPermissionUpdateContract],real type["
              + any.getClass() + "]");
    }
    final AccountPermissionUpdateContract accountPermissionUpdateContract;
    try {
      accountPermissionUpdateContract = any.unpack(AccountPermissionUpdateContract.class);
    } catch (InvalidProtocolBufferException e) {
      logger.debug(e.getMessage(), e);
      throw new ContractValidateException(e.getMessage());
    }
    byte[] ownerAddress = accountPermissionUpdateContract.getOwnerAddress().toByteArray();
    if (!DecodeUtil.addressValid(ownerAddress)) {
      throw new ContractValidateException("invalidate ownerAddress");
    }
    AccountCapsule accountCapsule = accountStore.get(ownerAddress);
    if (accountCapsule == null) {
      throw new ContractValidateException("ownerAddress account does not exist");
    }

    if (!accountPermissionUpdateContract.hasOwner()) {
      throw new ContractValidateException("owner permission is missed");
    }

    if (accountCapsule.getIsWitness()) {
      if (!accountPermissionUpdateContract.hasWitness()) {
        throw new ContractValidateException("witness permission is missed");
      }
    } else {
      if (accountPermissionUpdateContract.hasWitness()) {
        throw new ContractValidateException("account isn't witness can't set witness permission");
      }
    }

    if (accountPermissionUpdateContract.getActivesCount() == 0) {
      throw new ContractValidateException("active permission is missed");
    }
    if (accountPermissionUpdateContract.getActivesCount() > 8) {
      throw new ContractValidateException("active permission is too many");
    }

    Permission owner = accountPermissionUpdateContract.getOwner();
    Permission witness = accountPermissionUpdateContract.getWitness();
    List<Permission> actives = accountPermissionUpdateContract.getActivesList();

    if (owner.getType() != PermissionType.Owner) {
      throw new ContractValidateException("owner permission type is error");
    }
    checkPermission(owner);
    if (accountCapsule.getIsWitness()) {
      if (witness.getType() != PermissionType.Witness) {
        throw new ContractValidateException("witness permission type is error");
      }
      checkPermission(witness);
    }

  public void updatePermissions(Permission owner, Permission witness, List<Permission> actives) {
    Builder builder = this.account.toBuilder();

    owner = owner.toBuilder().setId(0).build();
    builder.setOwnerPermission(owner);
    if (witness != null && builder.getIsWitness()) {
      witness = witness.toBuilder().setId(1).build();
      builder.setWitnessPermission(witness);
    }

    builder.clearActivePermission();
    if (actives != null) {
      for (int i = 0; i < actives.size(); i++) {
        Permission permission = actives.get(i).toBuilder().setId(i + 2).build();
        builder.addActivePermission(permission);
      }
    }

    this.account = builder.build();
  }
