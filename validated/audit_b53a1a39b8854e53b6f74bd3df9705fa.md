### Title
Replay-Window Check/Update Race Allows Duplicate Decryption of a Single Message Counter - (File: connection_state.go)

### Summary
`ConnectionState.Decrypt` (and its relay counterpart `VerifyRelay`) split the anti-replay check into two separately-locked steps with an unlocked AEAD decrypt in between, mirroring the check/interaction/effect ordering flaw described in the reentrancy report: the "have we already processed this state" check is validated before the state-mutating effect is committed, leaving a window where the same input can pass the check twice.

### Finding Description
`Decrypt` takes `decryptLock`, calls `window.Check` to test whether `messageCounter` is a replay, releases the lock, performs the (unlocked, comparatively slow) AEAD decryption via `dKey.DecryptDanger`, and only afterwards re-acquires `decryptLock` to call `window.Update`, which is what actually marks the counter as seen: [1](#0-0) 

This is structurally the same bug class as `settleVault`: a state-consuming check (`window.Check` / vault-not-yet-`Settled`) is performed, then an expensive external/asynchronous operation happens (AEAD decrypt / `treasury.withdraw`), and only after that does the code commit the effect that should have prevented reprocessing (`window.Update` / `SettlementStatus.Settled`). Any two calls to `Decrypt` for the *same* `messageCounter` that land between the `Check` unlock and the `Update` lock will both observe "not yet seen" and both proceed to decrypt and be delivered to the tun device / message dispatch path, exactly as the DCS contract allowed two `settleVault` calls to both observe "not yet Settled" and both execute the payout.

`readOutsidePackets` is invoked from the UDP receive path once a packet is header-parsed and its `hostinfo`/`ConnectionState` is resolved by `RemoteIndex`, before any per-counter serialization is enforced beyond the `decryptLock` critical sections inside `Decrypt` itself: [2](#0-1) 

`Bits.Check` only inspects the bitmap; it does not mark anything, so it is safe to call repeatedly without mutating state — the actual "consume" step is `Bits.Update`, called separately and later: [3](#0-2) 

The relay verification path (`VerifyRelay`) has the identical Check → decrypt (unlocked) → Update ordering: [4](#0-3) 

An on-path network attacker who captures one legitimate ciphertext packet for an established tunnel can flood duplicates of that exact packet (same header, same `MessageCounter`, same ciphertext) at the target under a receive path that dispatches to multiple UDP reader routines (nebula's listener is configured to run several concurrent read routines). If two copies are processed concurrently by different goroutines, both can pass `window.Check` before either commits `window.Update`, so both duplicate ciphertexts get decrypted and delivered to the local tun interface / message dispatch logic — defeating the intended one-time-delivery guarantee of the anti-replay window, the same way the vault's `Settled` guard was defeated by re-entering before the flag was set.

### Impact Explanation
This breaks the confidentiality/integrity guarantee that the replay window is supposed to provide: a captured (not decrypted, not forged) packet can be redelivered and processed more than once under concurrency, causing duplicate application of a single message to the tun device, duplicate `TestReply`/`Control`/`LightHouse` message handling, and duplicate connection-manager/roaming side effects (`f.handleHostRoaming`, `f.connectionManager.In`) triggered by the race. It does not itself allow decrypting arbitrary attacker data (the AEAD key is still required and unknown to a non-CA attacker), so it is a replay-integrity bypass under concurrency rather than a full authentication bypass, but it directly violates the nonce/replay handling guarantee nebula relies on for tunnel integrity.

### Likelihood Explanation
Exploitation requires an attacker able to capture and duplicate a valid ciphertext packet at the network layer and land two copies close enough in time that both are picked up by different concurrent listener routines before `Update` commits — the same "requires precise conditions, narrow window" caveat the original report used to downgrade severity from critical to high. No CA-signed certificate or handshake participation is required; only network position to intercept and replay UDP datagrams for an already-established tunnel, which is exactly the threat class the replay window exists to defend against.

### Recommendation
Perform the replay check and the mark-as-seen update as a single atomic operation under one lock acquisition (Check-and-reserve pattern), so a second concurrent packet with the same `messageCounter` cannot pass the check until the first packet's effect is committed. E.g., merge `Check`+`Update` into one `CheckAndUpdate` function called under a single `decryptLock` critical section that brackets the whole `Decrypt`/`VerifyRelay` call (or reserve the counter optimistically before decrypting and roll back on decrypt failure), rather than releasing the lock between the check and the state-mutating update.

### Proof of Concept
1. Establish a tunnel between two nebula nodes (attacker observes network, does not need a certificate).
2. Capture one legitimate `header.Message`/`MessageNone` ciphertext packet, noting its `RemoteIndex` and `MessageCounter`.
3. Send N duplicate copies of the identical captured packet to the target's UDP listener in a tight burst, relying on multiple UDP reader goroutines to pick them up concurrently.
4. Because `Decrypt` releases `decryptLock` between `window.Check` and the AEAD decrypt call, multiple goroutines can each observe `Check==true` for the same counter before any of them calls `window.Update`; each such goroutine proceeds to decrypt and dispatch the packet via `readOutsidePackets`, resulting in duplicate delivery to the tun interface / message handlers instead of the single delivery the replay window is meant to guarantee. func (cs *ConnectionState) Decrypt(l *slog.Logger, messageCounter uint64, out []byte, packet []byte, nb []byte) ([]byte, error) {
	var err error
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}

	out, err = cs.dKey.DecryptDanger(out, packet[:header.Len], packet[header.Len:], messageCounter, nb)
	if err != nil {
		return nil, err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}
	return out, nil
}

func (cs *ConnectionState) VerifyRelay(l *slog.Logger, messageCounter uint64, packet []byte, nb []byte) error {
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	signedPayload := packet[:len(packet)-cs.dKey.Overhead()]
	signatureValue := packet[len(packet)-cs.dKey.Overhead():]
	_, err := cs.dKey.DecryptDanger(nil, signedPayload, signatureValue, messageCounter, nb)
	if err != nil {
		return err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	return nil
}

// Check returns true if i is within (or way out in front of) the window, and not a replay
func (b *Bits) Check(l *slog.Logger, i uint64) bool {
	// If i is the next number, return true.
	if i > b.current {
		return true
	}

	if b.strictlyWithinWindow(i) {
		return !b.get(i)
	}

	// Not within the window
	if l.Enabled(context.Background(), slog.LevelDebug) {
		l.Debug("rejected a packet (top)", "current", b.current, "incoming", i)
	}
	return false
}

// Update has three branches:
//   - i == b.current+1: fast path; advance the cursor by one and lose-count
//     the slot we just stomped (only past warmup; see the i > b.length guard
//     below).
//   - i  >  b.current+1: jump path; clear all slots between current and i
//     (or up to a full window's worth, whichever is smaller) via clearRange,
//     then mark i. Two arms here: a warmup arm that handles the very first
//     window before the cursor has slid, and a steady-state arm that treats
//     every cleared empty slot as a lost packet.
//   - i  <= b.current: in-window check for duplicates; out-of-window otherwise.
//
// NewBits seeds bits[0]=1 so counter 0 looks "received" — Update never
// clears that marker during warmup (clearRange skips position 0 when
// startPos=1), and once b.current >= b.length the marker is no longer
// consulted. The marker prevents a fictitious "lost" hit on the first real
// counter.
func (b *Bits) Update(l *slog.Logger, i uint64) bool {
	// Fast path: i is the next expected counter. Split out so the function
	// stays small and avoids paying for the slow paths' slog argument-build
	// stack frame on every call. The bit read/test/write is inlined to
	// touch the backing word once.
	if i == b.current+1 {
		pos := i & b.lengthMask
		word := pos >> 6
		mask := uint64(1) << (pos & 63)
		w := b.bits[word]
		if i > b.length && w&mask == 0 {
			b.lostCounter.Inc(1)
		}
		b.bits[word] = w | mask
		b.current = i
		return true
	}
	return b.updateSlow(l, i)
}
