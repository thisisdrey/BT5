### Title
Missing reserve non-negativity check in default (non-hardened) TRC10 Exchange swap math allows on-chain reserve to go negative / be over-drained - ([File: chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java])

### Summary
The TRC10 bancor-style AMM (`ExchangeTransactionContract` → `ExchangeTransactionActuator` → `ExchangeCapsule.transaction`) computes the counter-asset amount to pay out using a floating-point, `Math.pow`-based formula (`ExchangeProcessor`) and then updates both reserve balances with plain `long` arithmetic, **without ever validating that the resulting reserve balance is non-negative**, unless the chain-wide `allowHardenExchangeCalculation` proposal is active. This mirrors the Uranium Finance root cause: a broken/omitted reserve-integrity check around a pool's constant-formula math that let a single swap pay out far more than the pool actually holds.

### Finding Description
`ExchangeCapsule.transaction()` dispatches to `SafeExchangeProcessor` (BigDecimal, with an explicit non-negative check) only when `hardenedCalc` is `true`; otherwise it uses the legacy `ExchangeProcessor`, which performs the Bancor-like formula in raw `double` (`Math.pow`) precision: [1](#0-0) 

The critical branch:
```
newSecondTokenBalance = hardenedCalc
    ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
    : secondTokenBalance - buyTokenQuant;
...
if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
  throw new ContractValidateException("Exchange balance must be >=0 after transaction");
}
``` [2](#0-1) 

The non-negative-balance guard is gated behind `hardenedCalc`, i.e. only enforced when `allowHardenExchangeCalculation()` is on. In the default (non-hardened) path, the raw `double` math in `ExchangeProcessor.exchangeFromSupply` — `balance * (pow(1 + supplyQuant/supply, 2000.0) - 1.0)` — is trusted implicitly to always return a value smaller than `buyTokenBalance`: [3](#0-2) 

Neither `ExchangeTransactionActuator.doValidate()` nor `execute()` independently re-checks that `anotherTokenQuant` (the computed payout) is less than the counter-asset reserve before crediting the buyer and mutating on-chain reserve state: [4](#0-3) 

This is structurally the same class of bug that caused the Uranium Finance loss: the pool's balance/formula sanity check (in Uranium's case, the `x*y=k` post-fee-reserve check) was broken/omitted for certain inputs, letting an attacker extract up to ~98% of a reserve in a single swap because the code trusted the arithmetic result instead of validating it against actual reserves. Here, the equivalent safety net (`newSecondTokenBalance < 0` check) exists in the code (proving the team is aware this failure mode is possible — it's exactly what the "hardened" path was built to fix) but is not applied unless a separate governance proposal enables it, leaving the default path exposed to the same unvalidated-output failure mode.

### Impact Explanation
If the double-precision Bancor computation ever returns a `buyTokenQuant` greater than or close to the actual `secondTokenBalance` (due to floating-point rounding, extreme `sellTokenQuant`/reserve ratios, or crafted input sequences exploiting `Math.pow` precision loss), the actuator will:
1. Credit the caller with more of the counter-asset than the pool holds (`addAssetAmountV2`), and
2. Persist a negative (or effectively drained/unbacked) `secondTokenBalance`/`firstTokenBalance` into the `Exchange` capsule via `Commons.putExchangeCapsule`.

A negative or corrupted reserve balance is an on-chain unbacked-balance / permanently-broken-invariant condition for that exchange pair — any later attempt to use the pool would misbehave, and value already paid out to the attacker is real, extractable TRC10 asset, i.e. concrete theft of funds analogous to Uranium's drained reserves.

### Likelihood Explanation
This requires no privileged access — any address holding the sell-side token (or TRX) and knowing an `exchangeId` can submit an `ExchangeTransactionContract`. Because the flaw is confined to floating-point behavior of `Math.pow` and the deliberate omission of a bounds check outside the hardened path, actually triggering an output that exceeds the true reserve requires locating specific extreme/edge-case reserve ratios or accumulated rounding through repeated small trades — this is plausible but not trivially demonstrable without live experimentation against the exact `Math.pow` implementation on the JVM, so likelihood is assessed as data/precision-dependent rather than guaranteed-exploitable for arbitrary inputs.

### Recommendation
- Move the `newFirstTokenBalance < 0 || newSecondTokenBalance < 0` check out of the `hardenedCalc`-only branch and enforce it unconditionally in `ExchangeCapsule.transaction()`, regardless of `allowHardenExchangeCalculation`.
- Additionally, validate in `ExchangeTransactionActuator`/`ExchangeInjectActuator` that `anotherTokenQuant`/`buyTokenQuant` never exceeds the pre-trade counter-asset reserve, independent of which `Processor` implementation computed it.
- Consider making `SafeExchangeProcessor` (BigDecimal-based) the default processor rather than gating it behind a proposal, since the legacy `ExchangeProcessor` has known precision-related discrepancies (as already demonstrated by `ExchangeProcessorTest.testStrictMath`, which shows differing results between `Math.pow`-based and `StrictMath`/`BigDecimal`-based computations for the same inputs).

### Proof of Concept
Not independently reproducible from static analysis alone — exploitation depends on finding specific `(sellTokenBalance, buyTokenBalance, sellTokenQuant)` triples where `ExchangeProcessor.exchange()`'s double-precision `Math.pow` computation returns a `buyTokenQuant` that meets or exceeds `buyTokenBalance`. The existing test `ExchangeProcessorTest.testStrictMath` already empirically proves that the non-strict (`useStrictMath=false`) and strict/hardened computations diverge for identical inputs: [5](#0-4) 
demonstrating that the unhardened path's output is not guaranteed to match the safe, reserve-bounded computation — the specific divergence needed to exceed the counter reserve would require targeted fuzzing of the `Math.pow` implementation, which is outside the scope of static code review.

          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
