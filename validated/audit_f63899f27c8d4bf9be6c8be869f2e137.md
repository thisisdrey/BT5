### Title
Unbounded per-filter result queues in JSON-RPC `eth_newFilter`/`eth_newBlockFilter` allow an anonymous client to hog node memory - (File: `framework/src/main/java/org/tron/core/services/jsonrpc/TronJsonRpcImpl.java`)

### Summary
`eth_newFilter` / `eth_newBlockFilter` cap only the *number* of concurrently registered filters (`maxLogFilterNum` / `maxBlockFilterNum`), but each individual filter's result buffer (`LogFilterAndResult.result` / `BlockFilterAndResult.result`, both `LinkedBlockingQueue`) has no size limit. As with the Xen netback issue where a guest that stops draining its RX queue lets the hypervisor accumulate unbounded buffered packets until a (fairly long) timeout fires, here an anonymous JSON-RPC client that registers a broad filter and never calls `eth_getFilterChanges`/`eth_getFilterLogs` lets the node accumulate every matching log/block for the full 5-minute expiry window — and this is only cleaned up lazily, and can be repeated up to the filter-count cap for amplified effect.

### Finding Description
`newFilter` creates a `LogFilterAndResult` whose backing store is an unbounded `LinkedBlockingQueue`: [1](#0-0) 

Every processed block appends matching log entries to that queue via `handleLogsFilter` → `processLogFilterEntry`, with no cap on how many elements can be queued between client polls: [2](#0-1) 

The only bound on the number of *distinct* filters is `maxLogFilterNum` (default 20,000) / `maxBlockFilterNum` (default 50,000), enforced at creation time: [3](#0-2) [4](#0-3) 

A filter's expiry timer is set once at creation and only refreshed when the client actually pops results via `getFilterChanges`/`updateExpireTime`: [5](#0-4) 

Expired-filter cleanup (`eventFilterMap.remove(entry.getKey())`) is *lazy* — it only happens the next time `processLogFilterEntry` runs for that entry during block processing, meaning the queue's accumulated content isn't released proactively but only when a subsequent block event walks the map: [6](#0-5) 

The default expiry window is 5 minutes: [7](#0-6) 

This mirrors CVE-2021-28715: a consumer-controlled entity (the JSON-RPC client, analogous to the Xen guest) can simply stop consuming ("draining") data, and the producer side (the node applying blocks, analogous to the hypervisor's netback driver) keeps buffering data for it, bounded only by a multi-second/minute timeout that is long enough at realistic throughput to accumulate a large amount of memory.

### Impact Explanation
Any anonymous client reaching the JSON-RPC HTTP endpoint (`node.jsonrpc.httpFullNodeEnable`/`httpSolidityEnable`) can call `eth_newFilter` with wide match criteria (broad address lists up to `maxAddressSize`=1000, broad topics up to `maxSubTopics`=1000, matching most/all transaction logs) and then simply never call `eth_getFilterChanges`. Every subsequent block's matching logs accumulate unboundedly in that filter's queue for up to 5 minutes before lazy cleanup, and this can be repeated across up to 20,000 concurrent log filters (or 50,000 block filters), multiplying the memory amplification. On a busy chain this can drive the FullNode/Solidity node to exhaust heap memory, causing degraded service or crash (denial of service for the JSON-RPC query path), which is a valid impact per the "API the node can no longer serve" acceptance criterion.

### Likelihood Explanation
The JSON-RPC filter APIs are unauthenticated by design — any network client that can reach the configured JSON-RPC HTTP port can call `eth_newFilter`/`eth_newBlockFilter` repeatedly and simply withhold polling. No signed transaction, deployed contract, or special privilege is required, only that `jsonrpc.httpFullNodeEnable` (or the Solidity/PBFT equivalents) be enabled, which is a common production configuration for nodes serving Ethereum-compatible JSON-RPC clients.

### Recommendation
Bound each `FilterResult`'s internal queue with a maximum element/byte size (dropping oldest entries or rejecting further inserts once exceeded, with a warning log similar to the `filterCapsuleQueue.offer` pattern already used elsewhere in `Manager`), and/or proactively sweep and evict expired filters (and their queued content) on a timer rather than only lazily during the next matching block/log event.

### Proof of Concept
1. Enable `node.jsonrpc.httpFullNodeEnable = true` on a FullNode.
2. As an anonymous client, call `eth_newFilter` with a broad `FilterRequest` (e.g., no address filter, no topics) via `TronJsonRpcImpl.newFilter`.
3. Never call `eth_getFilterChanges`/`eth_getFilterLogs` for that filter ID.
4. Observe that for up to `EXPIRE_SECONDS` (300s) after creation, every block's matching logs (via `handleLogsFilter`/`processLogFilterEntry`) are appended into the filter's `LinkedBlockingQueue` with no size cap.
5. Repeat filter creation up to `maxLogFilterNum` (default 20,000) times to amplify total buffered memory before any of them are lazily reaped.

  private void processLogFilterEntry(
      Map.Entry<String, LogFilterAndResult> entry,
      Map<String, LogFilterAndResult> eventFilterMap,
      LogsFilterCapsule logsFilterCapsule) {
    LogFilterAndResult logFilterAndResult = entry.getValue();
    if (logFilterAndResult.isExpire()) {
      eventFilterMap.remove(entry.getKey());
      return;
    }

    long blockNumber = logsFilterCapsule.getBlockNumber();
    long fromBlock = logFilterAndResult.getLogFilterWrapper().getFromBlock();
    long toBlock = logFilterAndResult.getLogFilterWrapper().getToBlock();
    if (!(fromBlock <= blockNumber && blockNumber <= toBlock)) {
      return;
    }

    if (logsFilterCapsule.getBloom() != null && !logFilterAndResult.getLogFilterWrapper()
        .getLogFilter().matchBloom(logsFilterCapsule.getBloom())) {
      return;
    }

    LogFilter logFilter = logFilterAndResult.getLogFilterWrapper().getLogFilter();
    List<LogFilterElement> elements =
        LogMatch.matchBlock(logFilter, blockNumber, logsFilterCapsule.getBlockHash(),
            logsFilterCapsule.getTxInfoList(), logsFilterCapsule.isRemoved());

    List<LogFilterElement> localResults = new ArrayList<>(elements.size());
    for (LogFilterElement element : elements) {
      LogFilterElement cachedElement;
      try {
        // compare with hashcode() first, then with equals(). If not exist, put it.
        cachedElement = logElementCache.get(element, () -> element);
      } catch (ExecutionException e) {
        logger.error("Getting/loading LogFilterElement from cache fails", e); // never happen
        cachedElement = element;
      }
      localResults.add(cachedElement);
    }
    logFilterAndResult.getResult().addAll(localResults);
  }

  @Override
  public String newFilter(FilterRequest fr) throws JsonRpcInvalidParamsException,
      JsonRpcMethodNotFoundException, JsonRpcExceedLimitException {
    disableInPBFT("eth_newFilter");

    // not supports finalized as block parameter
    if (FINALIZED_STR.equalsIgnoreCase(fr.getFromBlock())
        || FINALIZED_STR.equalsIgnoreCase(fr.getToBlock())) {
      throw new JsonRpcInvalidParamsException(INVALID_BLOCK_RANGE);
    }

    Map<String, LogFilterAndResult> eventFilter2Result;
    if (getSource() == RequestSource.FULLNODE) {
      eventFilter2Result = eventFilter2ResultFull;
    } else {
      eventFilter2Result = eventFilter2ResultSolidity;
    }
    // Due to concurrent access, the threshold may occasionally be exceeded.
    if (maxLogFilterNum > 0 && eventFilter2Result.size() >= maxLogFilterNum) {
      throw new JsonRpcExceedLimitException(
          "exceed max log filters: " + maxLogFilterNum + ", try again later");
    }
    long currentMaxFullNum = wallet.getNowBlock().getBlockHeader().getRawData().getNumber();
    LogFilterAndResult logFilterAndResult = new LogFilterAndResult(fr, currentMaxFullNum, wallet);
    String filterID = generateFilterId();
    eventFilter2Result.put(filterID, logFilterAndResult);
    return ByteArray.toJsonHex(filterID);
  }
