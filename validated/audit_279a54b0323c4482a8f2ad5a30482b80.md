### Title
Per-IP handshake abuse mitigation is non-consuming pre-check, letting a single IP exhaust global QUIC connection slots via half-open handshakes - ([File: streamer/src/nonblocking/quic.rs])

### Summary
`run_server`'s accept loop gates a new `ClientConnectionTracker` slot behind a per-IP `rate_limiter.is_allowed()` check, but that check only inspects `current_tokens > 0` without consuming any tokens — actual token consumption (`register_connection`) only happens in `setup_connection` after the QUIC handshake successfully completes. An attacker who never completes the handshake (deliberately stalling just under `QUIC_CONNECTION_HANDSHAKE_TIMEOUT`) never triggers `register_connection`, so the per-IP limiter never throttles them, letting them repeatedly acquire and hold global `ClientConnectionTracker` slots (bounded by `qos.max_concurrent_connections()`) from a single source IP.

### Finding Description
In `run_server` (`streamer/src/nonblocking/quic.rs:331-379`), for every incoming QUIC `Incoming`, the server:
1. Checks `overall_connection_rate_limiter.current_tokens() == 0` — non-mutating peek.
2. Checks `rate_limiter.is_allowed(&incoming.remote_address().ip())` — also non-mutating, implemented in `ConnectionRateLimiter::is_allowed` (`streamer/src/nonblocking/connection_rate_limiter.rs:34-40`), which only returns `current_tokens(ip) > 0` and explicitly does not consume a token ("just checking should not mutate state", per its own test comment).
3. Only then constructs a `ClientConnectionTracker::new(stats.clone(), qos.max_concurrent_connections())` (`streamer/src/nonblocking/quic.rs:371-379`, definition at `streamer/src/nonblocking/quic.rs:236-251`), which increments the single global `stats.open_connections` counter and is the only hard admission gate.
4. `incoming.accept()` is called and `setup_connection` is spawned, which awaits the QUIC handshake under `timeout(QUIC_CONNECTION_HANDSHAKE_TIMEOUT, connecting)` — `QUIC_CONNECTION_HANDSHAKE_TIMEOUT = Duration::from_secs(2)` (`streamer/src/nonblocking/quic.rs:80`).

Crucially, `rate_limiter.register_connection(&from.ip())` — the only call that actually consumes a token from the per-IP `TokenBucket` — is invoked in `setup_connection` (`streamer/src/nonblocking/quic.rs:483-493`) *only after* the handshake future (`connecting`) resolves `Ok`. If the attacker stalls the handshake (e.g., sends an Initial packet and never responds to subsequent Handshake packets, or drops just before completion) until the 2-second timeout fires, `register_connection` is never called, and the per-IP bucket is never decremented. Consequently `is_allowed` will keep returning `true` for that IP indefinitely, regardless of how many stalled attempts were made.

The only real limit on the number of concurrent half-open connections one IP can hold is the *global* `qos.max_concurrent_connections()` cap checked via `ClientConnectionTracker::new`. Since that cap is shared across all staked/unstaked clients (`streamer/src/nonblocking/simple_qos.rs:422-425`, `max_staked_connections * 5 / 4` plus analogous unstaked accounting), a single attacker IP sending a steady stream of Initial-only (never-completing) QUIC handshakes at a rate exceeding `max_concurrent_connections / QUIC_CONNECTION_HANDSHAKE_TIMEOUT` can keep the global slot table saturated continuously. Legitimate clients (staked or unstaked) then hit `ClientConnectionTracker::new`'s failure branch and increment `refused_connections_too_many_open_connections` (`streamer/src/nonblocking/quic.rs:373-378`), being refused via `incoming.refuse()`.

This defeats the stated design intent in the accept loop's own comment block ("rate-limit abusive peers by (control-asserted) ip", `streamer/src/nonblocking/quic.rs:339`) because the per-IP mitigation is only asserted for peers that *complete* the handshake — the exact peers who don't complete it (the attackers in this scenario) are the ones left unthrottled.

### Impact Explanation
This is a resource-exhaustion / QoS-evasion DoS against the QUIC ingress layer of the TPU: a single unstaked, unprivileged attacker can deny legitimate unstaked (and potentially staked, depending on `max_concurrent_connections` sizing relative to staked reservation) clients the ability to open TPU QUIC connections, by keeping the global connection-tracker slot pool saturated with handshakes that are always aborted just before the 2-second timeout. This falls into the QoS-evasion / resource-exhaustion category of the bounty scope, matching the exact invariant named in the question ("connection limits enforced per source cannot be evaded by protocol-level stalling/slow-loris").

### Likelihood Explanation
Feasibility is high: the attacker only needs to be able to send raw UDP/QUIC Initial packets to the leader's public TPU port (in scope per the rules) and control when it stops responding to handshake packets — no stake, keys, or validator control required. Repeating from a single IP (optionally rotating source ports, which is irrelevant since the limiter keys only on IP) at a rate on the order of `max_concurrent_connections / 2s` sustains full occupation of the global slot table indefinitely, well within normal attacker bandwidth for reasonable `max_concurrent_connections` values (hundreds–low thousands).

### Recommendation
Consume (or reserve) a per-IP rate-limiter token at admission time — i.e., in the accept loop, before/at `ClientConnectionTracker::new` — rather than only on successful handshake completion, so that repeated stalled/never-completing handshake attempts from the same IP are throttled the same as successful ones. Alternatively, add a separate per-IP concurrent in-flight-handshake cap (distinct from the global `max_concurrent_connections`) that is decremented on `ClientConnectionTracker` drop, independent of whether the handshake ultimately succeeds.

impl ConnectionRateLimiter {
    /// Create a new rate limiter per IpAddr. The rate is specified as the count per minute to allow for
    /// less frequent connections. Higher limit also allows higher bursts.
    /// num_shards controls how many shards are used in the underlying dashmap,
    /// should be set >= number of contending threads.
    pub fn new(limit_per_minute: u64, max_burst: u64, num_shards: usize) -> Self {
        Self {
            limiter: KeyedRateLimiter::new(
                CONNECTION_RATE_LIMITER_CLEANUP_SIZE_THRESHOLD,
                TokenBucket::new(limit_per_minute, max_burst, limit_per_minute as f64 / 60.0),
                num_shards,
            ),
        }
    }

    /// Check if the connection from the said `ip` is allowed.
    /// Here we assume that only IPs with actual confirmed connections are stored in it,
    /// since we should only modify server state once source IP is verified
    pub fn is_allowed(&self, ip: &IpAddr) -> bool {
        // Check if we have records in the rate limiter for the given IP address
        match self.limiter.current_tokens(ip) {
            Some(r) => r > 0, // we have a record, and rate is not exceeded
            None => true,     // if we have not seen IP, allow connection request
        }
    }

    pub fn register_connection(&self, ip: &IpAddr) -> bool {
        if self.limiter.consume_tokens(*ip, 1).is_ok() {
            debug!("Request from IP {ip:?} allowed");
            true // Request allowed
        } else {
            debug!("Request from IP {ip:?} blocked");
            false // Request blocked
        }
    }
