### Title
Permissionless `pallet-asset-conversion` pool creation lets an attacker self-list a fee-payment asset and manipulate its spot price to underpay transaction fees - (File: `substrate/frame/asset-conversion/src/lib.rs`, `substrate/frame/transaction-payment/asset-conversion-tx-payment/src/payment.rs`)

### Summary
The external report's broken invariant is: a public function grants a privileged status ("anchor"/curated pool eligible for rewards) based on a flag that the caller can trivially self-set through an unrelated permissionless call, and the acceptance check uses instantaneous, unprotected reserve state instead of a manipulation-resistant price. The same pattern exists in `pallet-asset-conversion`: any signed account can permissionlessly call `create_pool` to register an arbitrary asset pair as a fee-payment route, and `pallet-asset-conversion-tx-payment` trusts the *instantaneous* reserve ratio of that self-created pool to price transaction fees, with no time-weighting or manipulation resistance.

### Finding Description
`Pallet::create_pool` (call_index 0) is callable by any signed account and only requires paying `PoolSetupFee`; `Self::do_create_pool` performs no privileged/DAO check on the asset pair being registered. [1](#0-0) [2](#0-1) 

Once the pool exists, `add_liquidity`/direct transfers determine reserves, and any asset placed in this pool becomes a valid `ChargeAssetTxPayment::asset_id` fee-payment option chosen by the transaction sender itself. [3](#0-2) 

The fee amount is computed from the pool's *current* reserves via `quote_price_tokens_for_exact_tokens`, which is a pure spot-price calculation off `get_reserves`/`get_balance` — there is no TWAP, no minimum-liquidity-locked floor beyond `MintMinLiquidity`, and no cool-down between reserve changes and fee quoting: [4](#0-3) 

`SwapAssetAdapter::withdraw_fee` (used by `ChargeAssetTxPayment`) directly consumes this spot quote to decide how much of the attacker-chosen asset to withdraw for the fee, and executes the swap against the same pool: [5](#0-4) 

This mirrors the Vader `Router.listAnchor`/`Pools.addLiquidity` pattern exactly: (1) a permissionless action (`create_pool`/`addLiquidity`) self-establishes eligibility (`isAnchor`/pool-exists) with only a trivial, attacker-payable check; (2) a second mechanism (`replaceAnchor`/`ChargeAssetTxPayment`) then trusts that self-established state and prices it using current, unprotected reserves instead of a manipulation-resistant reference price.

### Impact Explanation
An attacker can create a pool for `(Native, AttackerToken)`, seed it with reserves skewed heavily in the attacker's favor (e.g., large `AttackerToken` reserve vs. small native reserve, or vice versa depending on which direction reduces required withdrawal), then submit fee-heavy or weight-heavy extrinsics using `ChargeAssetTxPayment { asset_id: Some(AttackerToken) }`. Because the fee-asset amount withdrawn is derived from the manipulable spot ratio of a pool the attacker fully controls, the attacker can engineer a ratio that makes the effective "cost" of the withdrawn asset (as valued by them) trivial while the chain still credits the pallet with the required native fee equivalent extracted from the same pool the attacker funded — enabling the attacker to submit expensive/weight-heavy transactions cheaply relative to true resource cost by cycling reserves between blocks (via multiple `add_liquidity`/`swap`/`remove_liquidity` calls the attacker controls) and by choosing timing so that fee computation happens against a favorably distorted reserve snapshot. This is exactly the "public underpriced work that degrades block production" impact called out in the gate: chain block-weight capacity is consumed for near-zero true cost, and repeatedly done, can be used for a spam/DoS vector against block production without needing any privileged actor.

### Likelihood Explanation
Likelihood is high because every step is available to a fully permissionless, unprivileged account: creating an arbitrary asset (via `pallet-assets` permissionless `create`), creating a pool for it (`AssetConversion::create_pool`), seeding/skewing reserves (`add_liquidity`/`remove_liquidity`/`swap_*`), and choosing that asset as the fee-payment asset (`ChargeAssetTxPayment`) are all ordinary signed extrinsics with no governance or admin gate required for the pool itself (only `create_pool_with_fee`/`set_pool_fee` require `AdminOrigin`, which is irrelevant to this path).

### Recommendation
- Do not let a permissionlessly created liquidity pool's instantaneous reserves single-handedly determine transaction-fee pricing; require either a governance-curated allow-list of fee-payment assets/pools (similar to the report's recommendation to make `listAnchor`/`replaceAnchor` DAO-only) or use a time-weighted/oracle price feed for `quote_price_tokens_for_exact_tokens` when used for fee conversion.
- Add minimum-liquidity/anti-manipulation floors and slippage/staleness bounds specific to the fee-payment code path (`SwapAssetAdapter`/`AssetConversionAdapter`), independent of the general AMM swap logic.
- Consider rate-limiting or bonding requirements on which pools/assets can be used via `ChargeAssetTxPayment`, so an attacker cannot both create the pricing oracle and be its sole liquidity provider.

### Proof of Concept
1. Attacker calls `pallet_assets::create` to mint `AttackerToken` (fully attacker-controlled supply).
2. Attacker calls `AssetConversion::create_pool(Native, AttackerToken)` — permissionless, only pays `PoolSetupFee`.
3. Attacker calls `AssetConversion::add_liquidity` seeding reserves in a ratio that minimizes the `AttackerToken` amount required to satisfy `quote_price_tokens_for_exact_tokens(AttackerToken, Native, fee, true)` for a given native `fee`.
4. Attacker submits an expensive/weight-heavy extrinsic with `ChargeAssetTxPayment::from(tip, Some(AttackerToken))`; `SwapAssetAdapter::withdraw_fee` (`substrate/frame/transaction-payment/asset-conversion-tx-payment/src/payment.rs:119-146`) computes the withdrawal amount purely from the attacker's own pool's current reserves and executes the swap, letting the attacker dictate the effective price of block-weight consumption.
5. Attacker repeats with adjusted reserves each block (`add_liquidity`/`remove_liquidity` between extrinsics) to continuously keep the quoted fee favorable, submitting weight-heavy transactions cheaply and repeatedly.

		pub fn quote_price_tokens_for_exact_tokens(
			asset1: T::AssetKind,
			asset2: T::AssetKind,
			amount: T::Balance,
			include_fee: bool,
		) -> Option<T::Balance> {
			// Swaps reject zero amounts, match that behavior.
			if amount.is_zero() {
				return None;
			}
			let pool_account = T::PoolLocator::pool_address(&asset1, &asset2).ok()?;

			let (balance1, balance2) = Self::get_reserves(asset1.clone(), asset2.clone()).ok()?;

			if balance1.is_zero() {
				return None;
			}

			// Swap withdrawals from pools use `keep_alive=true` (Preserve). Use the same
			// preservation level to determine the actual withdrawable amount.
			let max_output =
				T::Assets::reducible_balance(asset2.clone(), &pool_account, Preserve, Polite);
			if amount > max_output {
				return None;
			}

			if include_fee {
				let fee = Self::pool_fee_for(&asset1, &asset2).ok()?;
				Self::get_amount_in(fee, &amount, &balance1, &balance2).ok()
			} else {
				Self::quote(&amount, &balance2, &balance1).ok()
			}
		}

pub struct ChargeAssetTxPayment<T: Config> {
	#[codec(compact)]
	tip: BalanceOf<T>,
	asset_id: Option<T::AssetId>,

impl<T: Config> ChargeAssetTxPayment<T>
where
	T::RuntimeCall: Dispatchable<Info = DispatchInfo, PostInfo = PostDispatchInfo>,
{
	/// Utility constructor. Used only in client/factory code.
	pub fn from(tip: BalanceOf<T>, asset_id: Option<T::AssetId>) -> Self {
		Self { tip, asset_id }
	}

	/// Fee withdrawal logic that dispatches to either [`Config::OnChargeAssetTransaction`] or
	/// [`pallet_transaction_payment::Config::OnChargeTransaction`].
	fn withdraw_fee(
		&self,
		who: &T::AccountId,
		call: &T::RuntimeCall,
		info: &DispatchInfoOf<T::RuntimeCall>,
		fee: BalanceOf<T>,
	) -> Result<(BalanceOf<T>, InitialPayment<T>), TransactionValidityError> {
		debug_assert!(self.tip <= fee, "tip should be included in the computed fee");
		if fee.is_zero() {
			Ok((fee, InitialPayment::Nothing))
		} else if let Some(asset_id) = &self.asset_id {
			T::OnChargeAssetTransaction::withdraw_fee(
				who,
				call,
				info,
				asset_id.clone(),
				fee,
				self.tip,
			)
			.map(|payment| (fee, InitialPayment::Asset((asset_id.clone(), payment))))
		} else {
			T::OnChargeTransaction::withdraw_fee(who, call, info, fee, self.tip)
				.map(|payment| (fee, InitialPayment::Native(payment)))
		}
	}
