### Title
Attacker can forcibly fill a victim's per-account token list via dust `DepositToken` transfers, blocking new collateral deposits and debt issuance until `MAX_TOKENS_PER_USER` is cleared - (File: contracts/DepositToken.sol)

### Summary
The Tomcat advisory is a liveness failure: per-connection state (active stream count) is miscounted, so resources that should be released stay open indefinitely, denying service. The Metronome analog is the per-account token-list accounting in `Pool`. `Pool` caps each account at `MAX_TOKENS_PER_USER = 30` combined debt + deposit tokens (contracts/Pool.sol:79), and enforces it in `onlyIfAdditionWillNotReachMaxTokens` (contracts/Pool.sol:143-148). `DepositToken._transfer` unconditionally pushes the token onto the *recipient's* list whenever their balance goes from 0 to positive (contracts/DepositToken.sol:517-520), with no opt-in or approval. An unprivileged attacker can therefore inflate a victim's list to the cap by sending 1 wei of each deposit token, after which `addToDepositTokensOfAccount` / `addToDebtTokensOfAccount` revert with `UserReachedMaxTokens` for that account.

### Finding Description
- `DepositToken._transfer` calls `pool.addToDepositTokensOfAccount(recipient_)` on any transfer that takes the recipient from 0 to non-zero balance (DepositToken.sol:518). `transfer`/`transferFrom` are public and require only unlocked sender balance.
- `Pool.addToDepositTokensOfAccount` reverts when `debtTokensOfAccount.length + depositTokensOfAccount.length >= 30` (Pool.sol:204-220, 143-148).
- Consequences once the victim's list is full:
  - `DepositToken` mint/`deposit` for a *new* collateral type also calls `addToDepositTokensOfAccount` (DepositToken.sol:486-488), so the victim cannot deposit new collateral — including to restore health on an unhealthy position before `Pool.liquidate`.
  - `DebtToken.issue` → `_mint` adds the debt token to the borrower's list, so the victim cannot mint any new synthetic asset either (debt position checked against `_msgSender` at DebtToken.sol:254-262).
  - Any inbound transfer of a not-yet-held deposit token reverts, so users/keepers/gateways cannot send the victim new collateral tokens.
- Modifiers don't mitigate: `whenNotShutdown`, `nonReentrant`, `SynthContext._msgSender`, and `_revertIfLocked` are orthogonal; the recipient never consented. Debt tokens can't be force-added (issue mints debt to `_msgSender`, only synths go to `to_`), so only deposit-token slots are attacker-fillable — but victim's own existing entries still count toward the 30.

### Impact Explanation
Temporary freezing of funds / griefing DoS matching the accepted impact ("temporary freezing of funds", "liveness"). A victim with an unhealthy position can be prevented from topping up with a new collateral type and liquidated; new deposits, new borrows, and inbound transfers of new tokens all revert. The freeze is temporary because the victim can remove entries by fully transferring out a dust token (`removeFromDepositTokensOfAccount` at DepositToken.sol:523-525), but this requires the victim to notice and spend gas, and the attacker can re-fill slots cheaply.

### Likelihood Explanation
Cost scales with the number of registered deposit tokens in the pool: the attacker must hold ≥1 unit of each distinct `DepositToken` (attainable via `deposit` + fee-on-transfer dust). On pools with few collaterals, the attacker only fills part of the 30 slots, reducing severity to partial griefing; on pools approaching 30 listed tokens the freeze is complete. Requires no privileged role, no oracle manipulation, and is reachable from plain ERC20 transfers — fitting the HTTP/2 "cheap unauthenticated input poisons connection accounting" class.

### Recommendation
- Only add tokens to `depositTokensOfAccount` on protocol actions (deposit/mint/seize), not on user-initiated `transfer`/`transferFrom`; or add an opt-in mechanism for inbound first-time transfers.
- Alternatively, on `UserReachedMaxTokens`, allow the transfer to succeed without list insertion and let `depositOf` iterate protocol-level tokens for health checks (structural change).
- At minimum, auto-sweep dust: allow anyone to call a cleanup that transfers a token fully out of a victim's list.

### Proof of Concept
Hardhat (pool + N registered deposit tokens, victim `v`):

```ts
// attacker deposits dust in each deposit token, then transfers to victim
for (const dt of depositTokens /* registered in pool */) {
  await dt.connect(attacker).deposit(1n, attacker.address);           // hold 1 wei msd
  await dt.connect(attacker).transfer(victim.address, 1n);            // adds to victim's list
}
// repeat until getDepositTokensOfAccount(victim).length + debtTokens == 30

// victim tries to deposit a new collateral type -> reverts
await expect(newMsdToken.connect(victim).deposit(1n, victim.address))
  .revertedWithCustomError(pool, 'UserReachedMaxTokens');

// victim tries to issue new synthetic debt -> reverts inside _mint
await expect(msXDebt.connect(victim).issue(1n, victim.address))
  .revertedWithCustomError(pool, 'UserReachedMaxTokens');
```

The existing unit test at test/Pool.test.ts:1386-1416 already demonstrates `UserReachedMaxTokens` reverting `addToDepositTokensOfAccount`; the PoC extends it by driving the cap via permissionless `DepositToken.transfer` rather than impersonated token calls. Caveat: exploit completeness depends on the deployed pool listing enough deposit tokens for the attacker to reach the 30 cap — I could not verify the exact count of registered deposit/debt tokens on the live deployments within this search.
