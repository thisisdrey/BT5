### Title
Missing G2 subgroup-membership check in `alt_bn128_pairing_check` allows forged pairing results — (`runtime/near-vm-runner/src/logic/alt_bn128.rs`)

### Summary
`decode_g2` in `runtime/near-vm-runner/src/logic/alt_bn128.rs` only validates that a submitted G2 element satisfies the twist curve equation via `bn::AffineG2::new`, but never checks that the point belongs to the prime-order `r`-subgroup, even though the function's own doc comment in `logic.rs`/`wasmtime_runner/logic.rs` explicitly promises this check ("G2 is Fr-ordered subgroup point ... If point ... is not in the subgroup ... returns AltBn128InvalidInput"). Because the BN254 twist has a large cofactor, non-`r`-order points exist whose pairing with any G1 point can collapse to the identity in the target group, letting an attacker satisfy `pairing_check` without a genuine witness.

### Finding Description
`pairing_check` in `runtime/near-vm-runner/src/logic/alt_bn128.rs` decodes each `(G1, G2)` pair via `decode_g1`/`decode_g2` and returns whether `bn::pairing_batch(&elements) == bn::Gt::one()`: [1](#0-0) 

`decode_g2` only calls `bn::AffineG2::new(x, y)`, which validates the twist curve equation but performs no scalar multiplication by the group order to confirm the point is in the intended `r`-order subgroup: [2](#0-1) 

This is a direct contradiction of the function's documented contract, which states the input is expected to be checked for subgroup membership: [3](#0-2) 

The host function is reachable from an unprivileged `FunctionCall` action through `VMLogic::alt_bn128_pairing_check` (and the equivalent `wasmtime_runner::logic::alt_bn128_pairing_check`), with no additional gating other than gas payment: [4](#0-3) 

Because the twist group `E'(Fq2)` for BN254 has order `h·r` with a large cofactor `h`, elements exist outside the `r`-order subgroup. For pairing-based Miller-loop constructions, a point whose order divides a factor of `h` that is coprime to `r` can pair trivially (to the target-group identity) with *every* G1 point, independent of any discrete-log relationship. An attacker who controls both operands of a pairing term in a contract's verification equation can therefore substitute such a point to make that term evaluate to the identity, causing the overall product-equals-one check to pass without the contract's intended cryptographic relationship holding. Any contract that treats `alt_bn128_pairing_check() == true` as proof of a valid signature/proof/multisig quorum (e.g., a Groth16-style verifier or pairing-based multisig releasing pooled deposits via `promise_batch_action_transfer`) can be tricked into authorizing a payout it never actually validated.

None of NEAR's existing checks (signature/nonce/access-key/gas/storage-staking checks) address this, since the flaw is purely in the host function's cryptographic validation of caller-supplied byte buffers — these apply at the transaction/receipt level, not to the semantic correctness of `alt_bn128` inputs.

### Impact Explanation
This breaks the authorization-exactness invariant for any third-party contract that uses `alt_bn128_pairing_check` as a gate for privileged promise actions (e.g., `Transfer`, `FunctionCall`), since the host function does not enforce the subgroup-membership precondition it documents. The scoped impact is theft of pooled funds held by such contracts (pairing-based multisig / zk verifier), matching NEAR's "theft of user funds" bounty category. Contracts that only ever pair against fixed, trusted verification-key G2 elements (never accepting adversarial G2 input) are not affected, since exploitation requires the attacker to control the crafted G2 operand.

### Likelihood Explanation
The precondition is that some deployed contract accepts an attacker-controlled G2 (or full pairing-tuple) buffer as part of its authorization logic and gates value-transferring promises on the boolean result — a realistic pattern for pairing-based signature/proof verifiers. Once such a contract exists, constructing the exploit requires only computing (offline, once) a point on the alt_bn128 twist outside the `r`-order subgroup with small residual order, which is a standard, well-documented cryptographic construction (the same class of "point not in subgroup" corner case NEAR itself patched for BLS12-381 via `bls12381_not_in_group_fix`/`BLS12381_NOT_IN_GROUP_FIX_VERSION`). The attack is then fully repeatable and costs only ordinary transaction gas.

### Recommendation
Add explicit subgroup-membership verification in `decode_g2` (and audit `decode_g1`/`decode_fr` similarly), e.g. by checking `point * GROUP_ORDER == G2::zero()` (or using a cofactor-clearing/subgroup-check routine from the `bn` crate or a maintained pairing library), matching the behavior already documented in `logic.rs`. Alternatively, bump a protocol version/feature flag analogous to `bls12381_not_in_group_fix` to gate the corrected behavior.

### Proof of Concept
Add a unit test to `runtime/near-vm-runner/src/logic/tests/alt_bn128.rs`:
1. Precompute (offline, e.g. via `arkworks`/`sage`) a point `Q` on the BN254 twist `E'(Fq2): y^2 = x^3 + 3/(9+i)` whose order divides a cofactor factor coprime to `r` (i.e., `Q` is on-curve per `bn::AffineG2::new` but not in the prime-order subgroup).
2. Call `alt_bn128::pairing_check` with a single element `(G1_generator, Q)` (or any nonzero G1 point) and assert it returns `Ok(true)`, despite no real discrete-log relation between the G1 and G2 operands.
3. Contrast with a correct implementation that would reject `Q` via `AltBn128InvalidInput` at decode time, demonstrating the documented contract in `logic.rs` (lines 1156-1158) is currently violated.

pub(crate) fn pairing_check(
    elements: &[[u8; PAIRING_CHECK_ELEMENT_SIZE]],
) -> Result<bool, InvalidInput> {
    let elements: Vec<(bn::G1, bn::G2)> = elements
        .iter()
        .map(|chunk| {
            let (g1, g2) = stdx::split_array(chunk);
            let g1 = decode_g1(g1)?;
            let g2 = decode_g2(g2)?;
            Ok((g1, g2))
        })
        .collect::<Result<Vec<_>, InvalidInput>>()?;

    let res = bn::pairing_batch(&elements) == bn::Gt::one();

    Ok(res)
}

fn decode_g2(raw: &[u8; 2 * POINT_SIZE]) -> Result<bn::G2, InvalidInput> {
    let (x, y) = stdx::split_array(raw);
    let x = decode_fq2(x)?;
    let y = decode_fq2(y)?;
    if x.is_zero() && y.is_zero() {
        Ok(bn::G2::zero())
    } else {
        bn::AffineG2::new(x, y)
            .map_err(|_err| InvalidInput::new("invalid g2", raw))
            .map(bn::G2::from)
    }
}

pub fn alt_bn128_pairing_check(
    ctx: &mut Ctx,
    memory: &mut [u8],
    value_len: u64,
    value_ptr: u64,
) -> Result<u64> {
    ctx.result_state.gas_counter.pay_base(alt_bn128_pairing_check_base)?;
    let data = get_memory_or_register(
        &mut ctx.result_state.gas_counter,
        memory,
        &ctx.registers,
        value_ptr,
        value_len,
    )?;

    let elements = alt_bn128::split_elements(&data)?;
    ctx.result_state.gas_counter.pay_per(alt_bn128_pairing_check_element, elements.len() as u64)?;

    let res = alt_bn128::pairing_check(elements)?;

    Ok(res as u64)
}
