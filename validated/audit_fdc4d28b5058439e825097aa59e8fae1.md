### Title
Unvalidated length field in `BatchValidateSign` precompile input drives unbounded/negative array allocation and out-of-bounds access - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The `BatchValidateSign` precompiled contract (reachable by any contract that performs a `CALL`/`STATICCALL` to its precompile address, i.e. from any deployed contract triggered by an unprivileged transaction) parses its ABI-encoded `data` argument with helper methods `extractSigArray`, `extractBytesArray`, and `extractBytes32Array`. Each of these reads an attacker-controlled 256-bit word as an array length via `DataWord.intValueSafe()` and immediately uses it to allocate a Java array, without first checking that the length is consistent with the remaining size of the input words/data. ### Finding Description
This mirrors the libmysofa CVE bug class: a size/length field taken directly from untrusted input is used to size a memory allocation and drive a copy loop without cross-validating it against the actual amount of available data. Concretely:

- `extractSigArray(words, offset, data)` computes `int len = words[offset].intValueSafe();` and immediately does `byte[][] bytesArray = new byte[len][];`, then loops `for (int i = 0; i < len; i++)` reading `words[offset + i + 1]` — with no check that `offset + i + 1 < words.length`.
- `extractBytesArray` and `extractBytes32Array` have the identical pattern: `int len = words[offset].intValueSafe();` followed by `new byte[len][]` and an unchecked loop over `words[offset + i + 1]`.

`intValueSafe()` clamps to `Integer.MAX_VALUE`/0 range but does not validate the value against the actual size of the `words` array derived from the precompile's `data` payload. An attacker who controls the calldata passed into the `BatchValidateSign` precompile call can set this length word to:
- A very large value (up to `Integer.MAX_VALUE`), causing `new byte[len][]` to attempt an outsized allocation (`OutOfMemoryError`) — the direct analog of the "overwriting large memory block" heap-overflow condition in the CVE, translated to the JVM's allocation-size-confusion equivalent.
- A value larger than the number of remaining `words`, causing `words[offset + i + 1]` to throw `ArrayIndexOutOfBoundsException` once the loop runs past the actual input length — the JVM analog of the out-of-bounds heap read/overwrite in the native library bug.

### Impact Explanation
If these exceptions are not fully absorbed by a `catch (Throwable)`/generic try-catch somewhere up the precompile dispatch chain, they can propagate as an uncaught runtime error during TVM execution, causing execution of the block to fail or the node process to become unstable for that transaction. At minimum this is a crash/DoS condition triggerable by any account able to broadcast a `TriggerSmartContract` transaction that calls into the `BatchValidateSign` precompile with crafted calldata — no special privileges or preconditions required beyond deploying/calling a contract that invokes the precompile address.

### Likelihood Explanation
High likelihood of reachability: `BatchValidateSign` is a standard precompiled contract dispatched by address inside `PrecompiledContracts.getContractForAddress`, callable from any TVM contract via `CALL`, and its `execute(byte[] data)` entry point is where these helpers are invoked with attacker-supplied `data`. Crafting the length word requires no cryptographic material — just placing an oversized or inconsistent 32-byte word at the expected offset in calldata.

### Recommendation
In `extractSigArray`, `extractBytesArray`, and `extractBytes32Array`, validate `len` against a sane upper bound and against the actual remaining `words.length` (i.e., `offset + len + 1 <= words.length`) before allocating or looping. Reject the call (return `Pair.of(false, ...)`) rather than allocating/iterating when the declared length is inconsistent with the provided data.

### Proof of Concept
Construct calldata for the `BatchValidateSign` precompile where the word at the array-length offset (e.g., the signature-count field consumed by `extractSigArray`) is set to a large value such as `0x7fffffff` (or any value exceeding the number of words actually supplied in `data`), while keeping the rest of the payload short. Submitting a `TriggerSmartContract` transaction whose contract invokes this precompile with that calldata will cause:
- `new byte[len][]` to throw `OutOfMemoryError` for very large `len`, or
- `words[offset + i + 1]` to throw `ArrayIndexOutOfBoundsException` once `i` exceeds the actual supplied words, since `offset > words.length - 1` is checked only for the initial `offset`, not for the subsequent indices computed from `len`.

Note: I was unable to fully trace whether the `execute()` wrapper around `BatchValidateSign` (or the outer TVM opcode dispatch) generically catches all `Throwable`/`Error` types before these helpers run, which would determine whether this manifests as a per-transaction revert (lower severity) or a broader node-level failure (higher severity). This should be verified against the exception-handling wrapper around precompile `execute()` calls in `Program`/`PrecompiledContracts` before finalizing severity.
