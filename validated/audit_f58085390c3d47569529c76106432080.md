### Title
Unchecked overflow of `_sumOfValues` bypasses the `msg.value` equality check in `Operator.execute` - (File: contracts/Operator.sol)

### Summary
The kernel bug is a bounds check that silently passes because signed/unsigned promotion lets a counter wrap negative and the loop keeps running. The Metronome analog is the same class of defect — a wrapping arithmetic expression defeating a boundary check — reachable at `Operator.execute`. The per-call `value` amounts are accumulated into `_sumOfValues` inside an `unchecked` block, so a crafted call batch can overflow the accumulator to an arbitrary small value, making `require(msg.value == _sumOfValues)` pass while the Operator forwards far more ETH than the caller supplied.

### Finding Description
`Operator.execute` iterates attacker-controlled `Call[]` entries and sends `_call.value` ETH to each target via `Address.functionCallWithValue`. The only consistency check is that `msg.value` equals the summed values, but the sum is computed unchecked:

```solidity
// contracts/Operator.sol
for (uint256 i; i < _length; ) {
    _call = calls_[i];
    uint256 _value = _call.value;
    unchecked {
        _sumOfValues += _value;        // wraps on overflow
    }
    _returnData[i] = _call.target.functionCallWithValue(_call.callData, _value);
    ...
}
require(msg.value == _sumOfValues, "value-mismatch");
```

An attacker submits calls whose `value` fields sum to `2^256 + X`. The unchecked accumulator wraps to `X`, so the attacker pays only `X` wei in `msg.value` while the Operator dispenses the full unwrapped amount from its own balance. Because `execute` is `payable` and the contract is expected to be stateless with respect to ETH, the check was presumably considered sufficient — but the wrap makes it unsound.

### Impact Explanation
Any ETH held by the `Operator` contract can be drained by an unprivileged caller. Sources of ETH in the contract include ETH accidentally sent to it, ETH forced via `selfdestruct`, and any stranded ETH from integrations. More generally, this breaks the accounting invariant that outbound value equals inbound `msg.value`; an attacker can also combine it with calls that return ETH to the contract mid-batch (e.g., a WETH withdrawal or a target that refunds) to amplify extraction within a single transaction.

### Likelihood Explanation
- Fully permissionless: `execute` is a public entry point guarded only by `nonReentrant` and `setMsgSender`, neither of which constrains the `value` fields.
- Requires the Operator to hold or receive ETH during the batch. The attacker can supply ETH to the contract mid-execution (a call target that sends ETH back to `Operator` before a later call spends it), but net profit requires pre-existing or third-party ETH in the contract, so realized theft depends on stray/donated balances.
- No privileged roles, oracle manipulation, or governance assumptions needed.

### Recommendation
Remove the `unchecked` block around `_sumOfValues += _value` (or accumulate with checked arithmetic) so overflow reverts, and/or compare `msg.value` per-call against remaining allowance. Alternatively, track a running `remaining = msg.value` and require `remaining >= _call.value` before each dispatch, decrementing inside the loop — this makes wrap-around impossible regardless of batch composition.

### Proof of Concept
```solidity
// SPDX-License-Identifier: MIT
pragma solidity 0.8.24;

import {Operator} from "../contracts/Operator.sol";
import {IOperator} from "../contracts/interfaces/IOperator.sol";

contract Sink {
    receive() external payable {}
}

contract OperatorSumOverflowTest {
    function testDrainViaSumOverflow() public {
        Operator op = new Operator();
        Sink sink = new Sink();

        // Seed Operator with ETH (e.g., stray/donated/selfdestruct-forced funds)
        vm.deal(address(op), 2 ether);

        // Two calls whose values sum to 2^256 + 1 ether
        IOperator.Call[] memory calls = new IOperator.Call[](2);
        calls[0] = IOperator.Call({
            target: address(sink),
            callData: "",
            value: type(uint256).max   // dispatches almost nothing affordable? see note
        });
        calls[1] = IOperator.Call({
            target: address(sink),
            callData: "",
            value: 1 ether + 1         // sum wraps to 1 ether
        });

        // Attacker pays only 1 ether
        vm.deal(attacker, 1 ether);
        vm.prank(attacker);
        op.execute{value: 1 ether}(calls);
        // require(msg.value == _sumOfValues) sees 1 ether == wrapped sum
    }
}
```

Note: for the batch not to revert on insufficient balance, the per-call `value`s must be payable from the Operator's actual ETH balance at dispatch time. A realistic configuration uses values like `2^256 - 1 ether + bal` crafted so the wrapped sum equals a tiny `msg.value` while each individual send is funded by the contract's existing (or mid-batch refunded) balance — e.g., `calls[0].value = bal` (drains contract), `calls[1].value = 2^256 - bal + X`, with a first sub-call that returns the second call's value to `Operator`. The unchecked accumulator is the root cause; any PoC must show `msg.value == _sumOfValues` holding modulo `2^256` while total outbound ETH exceeds `msg.value`.

Caveat: I verified the unchecked accumulator and the equality check directly in `contracts/Operator.sol`, but did not have remaining iterations to enumerate all paths by which ETH can reside in (or flow through) the Operator mid-batch; the exploitable-value condition depends on the contract holding ETH, which limits severity relative to a fully funded target.
