Audit Report

## Title
Integer-division rounding in Snowbridge outbound-queue `calculate_fee` can silently zero out the relayer fee, allowing underpriced Ethereum-bound messages - (File: bridges/snowbridge/pallets/outbound-queue/src/lib.rs)

## Summary
`Pallet::calculate_fee` in the Snowbridge outbound-queue pallet computes the remote (Ethereum-side) fee component via `convert_from_ether_decimals`, which performs a truncating integer division by `10^(18 - Decimals)`. With valid, non-zero `PricingParameters`, this truncation can collapse the remote fee to exactly `0`, as demonstrated by the pallet's own test. This value is used directly and unguarded by `SendMessage::validate` to charge senders before enqueuing Ethereum-bound work, meaning relayers can be left with no gas refund or reward for real Ethereum execution.

## Finding Description
`calculate_fee` computes the remote fee in wei via `calculate_remote_fee` (`fee_per_gas * gas_used_at_most + reward`), reinterprets it as an 18-decimal `FixedU128`, multiplies by `multiplier`, divides by `exchange_rate`, and finally calls `convert_from_ether_decimals`: [1](#0-0) 

`convert_from_ether_decimals` performs `value.checked_div(denom)` where `denom = 10^(18-Decimals)` (e.g. `10^8` for a 10-decimal chain like DOT), truncating any value smaller than the divisor to `0`: [2](#0-1) 

The pallet's own test confirms non-zero, individually-valid `PricingParameters` (`exchange_rate = 1`, `fee_per_gas = 1`, `rewards.local = rewards.remote = 1`, `multiplier = 1`) yield `fee.remote == 0`: [3](#0-2) 

`PricingParameters::validate()` only rejects parameters that are individually literally zero; it does not evaluate whether the resulting computed fee rounds to zero: [4](#0-3) 

The resulting `Fee` is consumed directly by `SendMessage::validate`, which computes `fee = Self::calculate_fee(gas_used_at_most, T::PricingParameters::get())` and returns it as the ticket price with no floor/sanity check before the message is queued for delivery to Ethereum: [5](#0-4) 

## Impact Explanation
When `fee.remote` truncates to zero, the sender pays only the `local` (on-chain weight) portion of the fee while the message is still committed via `commit()` (which embeds `reward: pricing_params.rewards.remote` into the `CommittedMessage` sent to Ethereum) and queued for relay/execution on Ethereum: [6](#0-5)  Relayers receive no gas refund or reward for delivering and executing that message on Ethereum. This is public underpriced work — any ordinary, unprivileged message sender using the standard outbound queue path can enqueue Ethereum-bound gas-consuming commands without paying the compensating remote fee, which discourages relaying and can stall or degrade Snowbridge's outbound processing pipeline.

## Likelihood Explanation
Triggering the degenerate case requires no attacker-controlled pricing manipulation — it only requires the currently governance-configured `PricingParameters` (combined with a given command's `gas_used_at_most`) to land in a numeric band where the intermediate remote-fee value is smaller than the `10^(18-Decimals)` divisor. `validate()` gives no signal that this can happen, so it is plausible in production configurations, and once it occurs, any unprivileged user sending an affected message class reproduces the zero-fee outcome deterministically, as shown by the existing unit test.

## Recommendation
Add a floor/round-up check in `convert_from_ether_decimals` or `calculate_fee`: round up (ceiling division) instead of truncating, or explicitly reject/error when the computed `Fee.remote == 0` while `gas_used_at_most > 0` and pricing parameters are non-zero, ensuring senders can never enqueue Ethereum-bound gas-consuming work for zero remote compensation.

## Proof of Concept
The existing pallet test reproduces this directly:
```rust
let gas_used: u64 = 250000;
let price_params = PricingParameters {
    exchange_rate: FixedU128::from_rational(1, 1),
    fee_per_gas: 1_u32.into(),
    rewards: Rewards { local: 1_u32.into(), remote: 1_u32.into() },
    multiplier: FixedU128::from_rational(1, 1),
};
let fee = OutboundQueue::calculate_fee(gas_used, price_params);
assert_eq!(fee.local, 698000000);
assert_eq!(fee.remote, 0); // remote compensation silently zeroed despite all non-zero params
``` [3](#0-2) 

This is the exact `fee` value `SendMessage::validate` would use to charge the sender before enqueuing the message via `T::MessageQueue::enqueue_message` in `deliver`, with no check that `remote != 0`.

		pub(crate) fn calculate_fee(
			gas_used_at_most: u64,
			params: PricingParameters<T::Balance>,
		) -> Fee<T::Balance> {
			// Remote fee in ether
			let fee = Self::calculate_remote_fee(
				gas_used_at_most,
				params.fee_per_gas,
				params.rewards.remote,
			);

			// downcast to u128
			let fee: u128 = fee.try_into().defensive_unwrap_or(u128::MAX);

			// multiply by multiplier and convert to local currency
			let fee = FixedU128::from_inner(fee)
				.saturating_mul(params.multiplier)
				.checked_div(&params.exchange_rate)
				.expect("exchange rate is not zero; qed")
				.into_inner();

			// adjust fixed point to match local currency
			let fee = Self::convert_from_ether_decimals(fee);

			Fee::from((Self::calculate_local_fee(), fee))
		}

	fn validate(
		message: &Message,
	) -> Result<(Self::Ticket, Fee<<Self as SendMessageFeeProvider>::Balance>), SendError> {
		// The inner payload should not be too large
		let payload = message.command.abi_encode();
		ensure!(
			payload.len() < T::MaxMessagePayloadSize::get() as usize,
			SendError::MessageTooLarge
		);

		// Ensure there is a registered channel we can transmit this message on
		ensure!(T::Channels::contains(&message.channel_id), SendError::InvalidChannel);

		// Generate a unique message id unless one is provided
		let message_id: H256 = message
			.id
			.unwrap_or_else(|| unique((message.channel_id, &message.command)).into());

		let gas_used_at_most = T::GasMeter::maximum_gas_used_at_most(&message.command);
		let fee = Self::calculate_fee(gas_used_at_most, T::PricingParameters::get());

		let queued_message: VersionedQueuedMessage = QueuedMessage {
			id: message_id,
			channel_id: message.channel_id,
			command: message.command.clone(),
		}
		.into();
		// The whole message should not be too large
		let encoded = queued_message.encode().try_into().map_err(|_| SendError::MessageTooLarge)?;

		let ticket = Ticket { message_id, channel_id: message.channel_id, message: encoded };

		Ok((ticket, fee))
	}
