### Title
Heap buffer over-read via unbounded central-directory field lengths in `InputZipFile::ProcessCentralDirEntry` - (File: `third_party/ijar/zip.cc`)

### Summary
`ijar`'s zip/jar parser advances its read cursor by attacker-controlled `file_name_length`, `extra_field_length`, and `file_comment_length` values taken directly from a ZIP central-directory record, without ever validating those lengths against the bounds of the memory-mapped input file. This mirrors the CVE-2017-8374 bug class: a "skip" primitive that trusts a length field embedded in untrusted media and advances a cursor past the end of the buffer, producing a heap-based over-read.

### Finding Description
`InputZipFile::ProcessCentralDirEntry` reads the central directory entry fields directly from the mmap'd file with no remaining-bytes check analogous to `EnsureRemaining()` used elsewhere in the same file: [1](#0-0) 

Specifically, `file_name_length`, `extra_field_length`, and `file_comment_length` are read as raw `u2` values from the file and used to advance `p` (`p += file_name_length; ... p += extra_field_length; ... p += file_comment_length;`) with no check that these advances stay within `input_file_->Length()`. The `memcpy` at line 520 also copies `file_name_length` bytes from `p` regardless of whether that many bytes actually remain in the mapped file: [2](#0-1) 

This contrasts with `ProcessLocalFileEntry` in the same file, which explicitly calls `EnsureRemaining()` before every read of variable-length attacker-controlled data: [3](#0-2) 

and with `singlejar`'s equivalent code path, which explicitly validates the next central-directory header stays inside the mapped region via `mapped_file_.mapped(new_cdr)`: [4](#0-3) 

The code comment justifies the lack of bounds checking by claiming "the central directory is always followed by another data structure that has a signature, so parsing it this way is safe" — but this assumption only holds for a well-formed file; a crafted length field can push `p` (and the subsequent `get_u4le` signature read in the next loop iteration of `CalculateOutputLength`/`ProcessNext`) past the end of the mmap'd region, an mmap'd/memory-mapped file that has no guard page guarantee immediately beyond its end (the tail of the mapping can be adjacent to unmapped memory or other heap data depending on OS/allocator), which is exactly the "skip past buffer end" pattern behind CVE-2017-8374's `mad_bit_skip`.

### Impact Explanation
`ijar` runs as a build action tool that processes JAR files, including ones obtained via `http_jar`/`http_archive`/`maven_install`-style dependencies where only a `sha256`/`integrity` checksum is pinned. A pinned checksum verifies byte-for-byte identity with the version the developer approved, but does not by itself guarantee the *contents* are a well-formed, safely-parsable ZIP structure — a malicious upstream artifact (or a compromised mirror serving content matching a stale/incorrectly-recorded hash) can still be a crafted ZIP that trips this parser bug. The result is a heap-based over-read: at minimum a crash/DoS of the ijar action, and potentially disclosure of adjacent heap memory into interface-jar output content depending on how far past the mapping the read lands and how the copied bytes are used downstream (e.g., embedded in the truncated `filename` buffer or subsequent parsing that treats read garbage as further header/signature data).

### Likelihood Explanation
Reaching this code path requires only that ijar be run over a JAR whose bytes are attacker-influenced (e.g. a third-party JAR dependency), which is a normal, expected build scenario in Bazel Java toolchains. No special privileges, MITM, or malicious remote-execution server is required — only that the artifact content (already checksum-pinned) itself is crafted maliciously. The bug is a straightforward integer/length trust issue requiring no complex race or timing.

### Recommendation
Add explicit bounds validation in `InputZipFile::ProcessCentralDirEntry` (and in `FindZipCentralDirectory`/`MaybeReadZip64CentralDirectory`) mirroring the `EnsureRemaining()` pattern already used in `ProcessLocalFileEntry`: before advancing `p` by `file_name_length`, `extra_field_length`, or `file_comment_length`, verify `p + length <= zipdata_in_ + input_file_->Length()`, and fail with an error (as `EnsureRemaining` does) rather than proceeding. The same bounds check should be applied to the zip64 extra-field walking loop (`extra_p`/`data_size`) at lines 526–541.

### Proof of Concept
A reproducible proof would be a `googletest`-based unit test in `third_party/ijar/zip_test.cc` (paralleling `src/tools/singlejar/zip_headers_test.cc`) that constructs a minimal in-memory ZIP central directory record whose `file_name_length` (or `extra_field_length`/`file_comment_length`) field is set to a value larger than the remaining bytes in the buffer, feeds it to `InputZipFile::Open`/`ProcessNext` (or directly to `ProcessCentralDirEntry`), and runs under AddressSanitizer to confirm a heap-buffer-overflow/over-read is reported when `p` is advanced past the allocated/mapped buffer. I was not able to locate an existing `zip_test.cc` covering this exact path in the indexed codebase — the recommendation is to add it as new test coverage; if such a file already exists with fuller contents, the full file could not be confirmed from the current index and a Devin session with full file access would be needed to check for existing coverage before adding a duplicate test.
