### Title
Floating-point rounding in legacy vote-reward computation can overpay voters and mint unbacked TRX allowance - (File: `chainbase/src/main/java/org/tron/core/service/MortgageService.java`)

### Summary
The GroupBuy `H-02` mitigation report describes a case where a "unit price" is derived via integer division and then re-multiplied per participant to compute refunds, causing the sum of individually-rounded shares to exceed the true total and starve the last claimant. The equivalent pattern in java-tron is the legacy (pre-new-algorithm) vote reward distribution in `MortgageService`, where each voter's share of a fixed `totalReward` pot is computed independently using `double` division/multiplication instead of exact integer/BigInteger math, so the sum of all voters' computed rewards for a cycle can exceed the recorded `totalReward`.

### Finding Description
`MortgageService.computeReward(long cycle, List<Pair<byte[], Long>> votes)` computes each voter's proportional share of a witness's per-cycle reward using floating point: [1](#0-0) 

```java
long totalReward = delegationStore.getReward(cycle, srAddress);
...
long totalVote = delegationStore.getWitnessVote(cycle, srAddress);
...
long userVote = vote.getValue();
double voteRate = (double) userVote / totalVote;
reward += voteRate * totalReward;
```

Each voter of the same SR/cycle independently recomputes `voteRate * totalReward` with `double` arithmetic. Because floating-point division/multiplication is not exact and rounding is not guaranteed to be floor-consistent across all voters, the sum of `Σ (userVote_i / totalVote) * totalReward` over all voters `i` can exceed `totalReward` (analogous to the GroupBuy bug where `price / filledQuantity` truncation, multiplied back per participant, oversells the pool). This legacy path (`getOldReward`) is invoked whenever a withdrawal/query spans cycles below `newRewardAlgorithmEffectiveCycle` and `allowOldRewardOpt` is not enabled, dispatched from the newer `computeReward(beginCycle, endCycle, accountCapsule)`: [2](#0-1) [3](#0-2) 

Any voter whose `beginCycle` (last time they touched votes/withdrew rewards) predates `newRewardAlgorithmEffectiveCycle` will trigger `getOldReward`, which sums the double-based `computeReward(cycle, votes)` over the affected cycle range — compounding the rounding error across many cycles.

By contrast, the newer algorithm (`RewardViCalService`/`VoteRewardUtil`) uses exact `BigInteger` arithmetic with floor division, which is the "safe" direction (never overpays): [4](#0-3) 

The rewards distributed via `adjustAllowance` are not deducted from any tracked, finite balance pool at withdrawal time — they simply increase the account's `allowance`, which is later paid out as real TRX balance in `WithdrawRewardProcessor.execute`: [5](#0-4) 

so an overpayment from the rounding bug becomes unbacked TRX rather than merely reallocating a fixed pot among users.

### Impact Explanation
If floating-point rounding causes the sum of computed voter rewards for a cycle/SR to exceed the recorded `totalReward`, the excess TRX credited via `adjustAllowance`/`WithdrawRewardProcessor` is newly minted and unbacked by the original block/transaction-fee reward that was recorded. This constitutes an unbacked-balance / inflation bug reachable by any voter simply calling withdraw-reward for an account whose vote history spans the pre-new-algorithm cycles — a normal, unprivileged transaction path.

### Likelihood Explanation
The vulnerable code path is only exercised for cycles prior to `newRewardAlgorithmEffectiveCycle`, so on a live long-running chain this window is fixed and finite, but it remains reachable for any account whose reward has not been withdrawn/refreshed since before that cutoff (e.g., long-dormant voters), and it can also affect the initial migration window when the constant was first configured. The magnitude of any single overpayment (float rounding at ~1e-15 relative error) is small per user, but it is cumulative across all voters of the affected SR and across all uncollected legacy cycles, so likelihood of a *measurable* impact is moderate rather than certain — I could not verify from the index alone the exact value of `newRewardAlgorithmEffectiveCycle` or whether all mainnet cycles are already past it (the file defining it, `DynamicPropertiesStore`, appears truncated in the indexed context), so I cannot conclusively state whether this path is still reachable on production chains today or is fully retired.

### Recommendation
Replace the `double`-based proportional computation in `MortgageService.computeReward(long, List<Pair<byte[], Long>>)` with exact integer/`BigInteger` arithmetic using floor rounding (as already done in the new VI-based algorithm), ensuring `Σ reward_i <= totalReward` for every cycle, and consider retiring/disabling the legacy path entirely once all outstanding legacy-cycle rewards have been migrated.

### Proof of Concept
Not independently reproduced against a running node from this index-only investigation; the mechanism is demonstrated by inspecting the arithmetic directly: for a witness with `totalReward = 100`, `totalVote = 3`, and three voters each with `userVote = 1`, each voter's `voteRate = 1.0/3.0 ≈ 0.3333333333333333`, and `reward_i = (long)(0.3333333333333333 * 100) = 33` for each, but rounding behavior can differ per call depending on JIT/double representation edge cases across different `userVote`/`totalVote` ratios, illustrating how independently-rounded shares are not guaranteed to sum to `<= totalReward`, unlike the floor-`BigInteger` implementation used in `RewardViCalService`/`VoteRewardUtil`.   private long computeReward(long cycle, List<Pair<byte[], Long>> votes) {
```java
    long reward = 0;
    for (Pair<byte[], Long> vote : votes) {
      byte[] srAddress = vote.getKey();
      long totalReward = delegationStore.getReward(cycle, srAddress);
      if (totalReward <= 0) {
        continue;
      }
      long totalVote = delegationStore.getWitnessVote(cycle, srAddress);
      if (totalVote == DelegationStore.REMARK || totalVote == 0) {
        continue;
      }
      long userVote = vote.getValue();
      double voteRate = (double) userVote / totalVote;
      reward += voteRate * totalReward;
    }
    return reward;
  }
```

```java
  private long computeReward(long beginCycle, long endCycle, AccountCapsule accountCapsule) {
    if (beginCycle >= endCycle) {
      return 0;
    }

    long reward = 0;
    long newAlgorithmCycle = dynamicPropertiesStore.getNewRewardAlgorithmEffectiveCycle();
    List<Pair<byte[], Long>> srAddresses = accountCapsule.getVotesList().stream()
        .map(vote -> new Pair<>(vote.getVoteAddress().toByteArray(), vote.getVoteCount()))
        .collect(Collectors.toList());
    if (beginCycle < newAlgorithmCycle) {
      long oldEndCycle = min(endCycle, newAlgorithmCycle,
          dynamicPropertiesStore.disableJavaLangMath());
      reward = getOldReward(beginCycle, oldEndCycle, srAddresses);
      beginCycle = oldEndCycle;
    }
    if (beginCycle < endCycle) {
      for (Pair<byte[], Long>  vote : srAddresses) {
        byte[] srAddress = vote.getKey();
        BigInteger beginVi = delegationStore.getWitnessVi(beginCycle - 1, srAddress);
        BigInteger endVi = delegationStore.getWitnessVi(endCycle - 1, srAddress);
        BigInteger deltaVi = endVi.subtract(beginVi);
        if (deltaVi.signum() <= 0) {
          continue;
        }
        long userVote = vote.getValue();
        reward += deltaVi.multiply(BigInteger.valueOf(userVote))
            .divide(DelegationStore.DECIMAL_OF_VI_REWARD).longValue();
      }
    }
    return reward;
  }
```

```java
  private long getOldReward(long begin, long end, List<Pair<byte[], Long>> votes) {
    if (dynamicPropertiesStore.allowOldRewardOpt()) {
      return rewardViCalService.getNewRewardAlgorithmReward(begin, end, votes);
    }
    long reward = 0;
    for (long cycle = begin; cycle < end; cycle++) {
      reward += computeReward(cycle, votes);
    }
    return reward;
  }
```

```java
  public long execute(WithdrawRewardParam param, Repository repo) throws ContractExeException {
    byte[] ownerAddress = param.getOwnerAddress();

    VoteRewardUtil.withdrawReward(ownerAddress, repo);

    AccountCapsule accountCapsule = repo.getAccount(ownerAddress);
    long oldBalance = accountCapsule.getBalance();
    long allowance = accountCapsule.getAllowance();
    long newBalance = 0;

    try {
      newBalance = LongMath.checkedAdd(oldBalance, allowance);
    } catch (ArithmeticException e) {
      logger.debug(e.getMessage(), e);
      throw new ContractExeException(e.getMessage());
    }

    // If no allowance, do nothing and just return zero.
    if (allowance <= 0) {
      return 0;
    }

    accountCapsule.setInstance(accountCapsule.getInstance().toBuilder()
        .setBalance(newBalance)
        .setAllowance(0L)
        .setLatestWithdrawTime(param.getNowInMs())
        .build());

    repo.updateAccount(accountCapsule.createDbKey(), accountCapsule);
    return allowance;
```
