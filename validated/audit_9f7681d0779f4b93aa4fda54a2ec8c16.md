## Analysis Result [1](#0-0) 

### Title
Unbounded memory allocation in precompiled-contract ABI array decoding (`extractBytes32Array`/`extractBytesArray`) - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
`extractBytes32Array` and `extractBytesArray` in `PrecompiledContracts.java` read an attacker-controlled 32-byte word from the calldata passed to a precompiled contract (e.g. the batch/multi-sign validation precompiles) and use it directly as an array-allocation size via `intValueSafe()`, with no upper bound check or correlation to the actual size of `data`, before any signature verification work happens.

### Finding Description
`extractBytes32Array` computes `len = words[offset].intValueSafe()` and immediately allocates `new byte[len][]`: [1](#0-0) 
Similarly `extractBytesArray` and `extractSigArray` derive `len` the same way and allocate `byte[len][]` before validating that `len` is consistent with the true length of the input buffer: [2](#0-1) 
`DataWord.intValueSafe()` only clamps the decoded value to a valid non-negative `int` range (up to `Integer.MAX_VALUE`), it does not restrict it to the actual number of items that would fit in the supplied `data`/`words` array. This is structurally the same class of bug as CVE-2017-12430 (ImageMagick's `ReadMPCImage`): an attacker-controlled length field taken from input data is used to size a memory allocation before the corresponding data is actually validated to exist, letting a small crafted input request an enormous allocation.

### Impact Explanation
Any account can trigger this by calling the corresponding precompiled contract (the batch/multi-signature validation precompile that uses these helpers) with crafted calldata containing a maliciously large length word, all from a single transaction executed inside the TVM. Because the allocation of `new byte[len][]` happens before any energy-metered per-item work is performed, the node can be forced to attempt allocating gigabytes of heap for a comparatively tiny transaction, resulting in `OutOfMemoryError`/JVM stalls that crash or degrade the full node — a denial-of-service against block execution.

### Likelihood Explanation
The precompile is invoked by ordinary TVM `CALL` opcodes from any deployed contract, so it is reachable by any unprivileged transaction broadcaster/contract deployer without special permissions, matching the "unprivileged reachable" criteria in scope.

### Recommendation
Bound `len` in `extractBytes32Array`, `extractBytesArray`, and `extractSigArray` to a sane maximum (e.g., derived from `words.length` or `data.length`) before allocating the destination arrays, and reject the call (return failure) rather than attempting the allocation when the declared count is inconsistent with the actual input size.

### Proof of Concept
Craft calldata to the affected precompile (batch/multi-sign validation precompile) whose ABI-encoded "count" word at the expected `offset` is set to a very large value (e.g., `0x7FFFFFFF`) while the actual `data` payload is minimal. When the precompile's `execute()` invokes `extractBytes32Array`/`extractBytesArray`, the JVM attempts `new byte[0x7FFFFFFF][]`, exhausting heap and potentially crashing the node process before any energy accounting for per-element processing occurs.

**Note on completeness:** I was unable to fully trace, within the available tool budget, the exact precompiled-contract class (e.g. `BatchValidateSign`/`ValidateMultiSign`) that calls `extractBytes32Array`/`extractBytesArray`/`extractSigArray`, nor confirm whether an outer bound check exists earlier in that caller's `execute()` method before these helpers are invoked. This should be verified directly in the file before treating this as conclusively exploitable — I recommend a full read of the `BatchValidateSign`/`ValidateMultiSign` precompile classes in `PrecompiledContracts.java` to confirm the absence of a pre-check on the count word.

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
