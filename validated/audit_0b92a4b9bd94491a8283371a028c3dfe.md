This confirms the analog: `check_actor_permissions` in [1](#0-0)  places `Action::TransferToGasKey(_)` in the group that requires no special actor permission (same bucket as `CreateAccount`, `FunctionCall`, `Transfer` — i.e., any predecessor, not just the account's own signer, can trigger it), and `action_transfer_to_gas_key` unconditionally credits the deposit onto the target gas key with no cap or owner check [2](#0-1) .

### Title
Unprivileged `TransferToGasKey` griefing can permanently block `DeleteAccount` via `GasKeyBalanceTooHigh` - (File: `runtime/runtime/src/actions.rs`, `runtime/runtime/src/access_keys.rs`)

### Summary
`action_delete_account` refuses to delete an account whenever the sum of its gas-keys' balances exceeds `GasKeyInfo::MAX_BALANCE_TO_BURN` (1 NEAR), returning `GasKeyBalanceTooHigh` and aborting the deletion (no state changes) [3](#0-2) . This "gas key balance too high" precondition is the same class of bug reported for `LRTDepositPool.removeNodeDelegatorContractFromQueue`: a balance check gating a legitimate removal operation, which can be griefed by an unrelated party topping up that balance right before the removal.

### Finding Description
`TransferToGasKey` is a permissionless action with respect to actor identity: `check_actor_permissions` treats it like `Transfer`/`FunctionCall`, requiring no ownership of the target account or its access key [4](#0-3) . Its handler, `action_transfer_to_gas_key`, only requires that the named gas key exists on the target account, then adds the attached deposit to `gas_key_info.balance` with no upper bound and no relationship to the caller [2](#0-1) .

Any account (or a receipt that any account can send) can therefore attach a deposit via `TransferToGasKey` targeting a gas key that belongs to a victim account, incrementing its balance. `action_delete_account` sums *all* gas-key balances on the account (`compute_gas_key_balance_sum`) and hard-fails the deletion if that sum exceeds the 1 NEAR burn cap, exactly mirroring the reported "attacker sends a tiny amount to manipulate a balance precondition and block removal" pattern [5](#0-4) .

### Impact Explanation
Because `DeleteAccount` aborts with `GasKeyBalanceTooHigh` rather than partially succeeding, the target account can be prevented from ever deleting itself (permanent griefing/freezing of the delete-account/beneficiary-refund path) as long as an attacker keeps re-funding gas keys above the threshold before each deletion attempt. This is a denial-of-service against an ordinary account operation reachable purely through unprivileged transactions/receipts, not through any operator, network, or mocked path.

### Likelihood Explanation
The griefer only needs to know the account id and the public key of one of its gas keys (both are public/discoverable on-chain via account/access-key state), and send a `TransferToGasKey` action with a small deposit before the victim's `DeleteAccount` transaction executes. No special privileges, races beyond ordinary transaction ordering, or unusual gas/storage costs are required, making this a low-cost, repeatable griefing vector once a target uses gas keys with meaningful balances.

### Recommendation
Do not hard-fail account deletion based on an externally-inflatable balance. Instead, either (a) cap/reject `TransferToGasKey` deposits from non-owning actors, (b) burn/refund the excess balance at deletion time instead of aborting, or (c) route the excess gas-key balance to a refund receipt (similar to how the residual `account_balance` is refunded to the beneficiary) rather than blocking deletion entirely.

### Proof of Concept
1. Victim account `V` holds a gas key `K` with balance `b <= MAX_BALANCE_TO_BURN` (1 NEAR) — deletable.
2. Attacker `A`, who has no permission over `V` or `K`, submits a receipt containing `Action::TransferToGasKey { public_key: K, deposit: d }` targeting `V`, where `b + d > MAX_BALANCE_TO_BURN`. This succeeds unconditionally per `action_transfer_to_gas_key` since no actor/ownership check applies to `TransferToGasKey`.
3. `V` (or its beneficiary flow) then submits `Action::DeleteAccount`. `action_delete_account` computes `gas_key_balance_to_burn = b + d > MAX_BALANCE_TO_BURN` and returns `ActionErrorKind::GasKeyBalanceTooHigh`, leaving the account undeleted with no state mutation.
4. Attacker repeats step 2 after each failed deletion attempt (or preemptively) to keep the account permanently undeletable.

pub(crate) fn action_transfer_to_gas_key(
    state_update: &mut TrieUpdate,
    result: &mut ActionResult,
    account_id: &AccountId,
    action: &TransferToGasKeyAction,
) -> Result<(), RuntimeError> {
    let Some(mut access_key) = get_access_key(state_update, account_id, &action.public_key)? else {
        result.result = Err(ActionErrorKind::GasKeyDoesNotExist {
            account_id: account_id.clone(),
            public_key: Box::new(action.public_key.clone()),
        }
        .into());
        return Ok(());
    };
    let Some(gas_key_info) = access_key.gas_key_info_mut() else {
        // Key exists but is not a gas key
        result.result = Err(ActionErrorKind::GasKeyDoesNotExist {
            account_id: account_id.clone(),
            public_key: Box::new(action.public_key.clone()),
        }
        .into());
        return Ok(());
    };

    gas_key_info.balance = gas_key_info.balance.checked_add(action.deposit).ok_or_else(|| {
        RuntimeError::StorageError(StorageError::StorageInconsistentState(
            "gas key balance integer overflow".to_string(),
        ))
    })?;
    set_access_key(state_update, account_id.clone(), action.public_key.clone(), &access_key);
    Ok(())
}
