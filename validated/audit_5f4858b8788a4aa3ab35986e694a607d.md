### Title
Double-precision truncation in legacy voting-reward calculation causes users to receive zero reward for entitled cycles - ([File: chainbase/src/main/java/org/tron/core/service/MortgageService.java])

### Summary
`MortgageService.computeReward(long cycle, List<Pair<byte[], Long>> votes)` computes each voter's proportional share of a Super Representative's per-cycle reward using floating-point division and multiplication, then accumulates the result into a `long`. This is directly analogous to the reported bug class: an integer/floating-point rounding operation (`totalHEU * 1e18 / totalSupply` in the external report vs. `voteRate * totalReward` here) can silently round the payout down to zero even though the caller is entitled to a nonzero share, and there is no minimum-payout safeguard.

### Finding Description
For each vote in the legacy (pre-new-algorithm) reward path, the code computes: [1](#0-0) 

```java
double voteRate = (double) userVote / totalVote;
reward += voteRate * totalReward;
```
`reward` is a `long`, so the compound assignment `reward += voteRate * totalReward` silently truncates the fractional result toward zero. When `userVote` is small relative to `totalVote` (e.g. a small delegator among many voters) and `totalReward` is a modest, non-huge cycle reward, `voteRate * totalReward` can evaluate to a value less than 1.0, which truncates to `0`, even though the voter mathematically holds a nonzero fractional share of `totalReward`.

This is reached from a real user-signed transaction path:
- `WithdrawBalanceActuator.execute()` calls `mortgageService.withdrawReward(...)`, which in turn calls `computeReward(beginCycle, endCycle, accountCapsule)`. [2](#0-1) 
- `computeReward(beginCycle, endCycle, accountCapsule)` dispatches into the vulnerable per-cycle helper via `getOldReward`, for any cycle prior to `newRewardAlgorithmEffectiveCycle`: [3](#0-2) [4](#0-3) 

Unlike the exchange-pool actuators in the same codebase (`ExchangeInjectActuator`, `ExchangeWithdrawActuator`, `ExchangeTransactionActuator`), which explicitly guard against a rounded-to-zero output with `if (anotherTokenQuant <= 0) { throw ContractValidateException(...) }`, this reward path has **no such guard**: `adjustAllowance` is simply a no-op for `amount <= 0`, so the truncated-to-zero reward silently disappears with no error, no retry mechanism, and no accounting of the lost fractional dust.

### Impact Explanation
Any account that has voted for a Super Representative and calls `WithdrawBalanceContract` (or has its reward implicitly settled via the vote/withdraw bookkeeping) can be permanently denied reward it is otherwise entitled to for a given historical cycle, whenever its vote share relative to the SR's total votes yields `voteRate * totalReward < 1`. Because `beginCycle`/`endCycle` bookkeeping is advanced past the cycle regardless of whether reward was paid, the entitlement for that cycle is not recomputed or retried later — the reward for that cycle is permanently lost to the affected account. This matches the "medium" severity classification of the source report: a rounding artifact that silently zeroes out an entitled payout, without any minimum-payout safeguard.

### Likelihood Explanation
This condition is fully deterministic and requires no special privileges — any account that stakes/votes with a small vote weight relative to a witness's total vote count, or where the accumulated `totalReward` for a cycle is modest, can trigger it purely through a normal `WithdrawBalanceContract` transaction or through automatic reward settlement during vote changes. It only affects cycles prior to `newRewardAlgorithmEffectiveCycle` (the current "Vi"-based algorithm at `computeReward(beginCycle, endCycle, accountCapsule)` lines 215–228 uses `BigInteger` arithmetic and does not have this issue), which limits it to historical cycles, but any node still replaying/settling old-cycle rewards for accounts that have not yet withdrawn is exposed.

### Recommendation
Replace the floating-point `voteRate * totalReward` computation with exact integer arithmetic (e.g., `BigInteger.valueOf(userVote).multiply(BigInteger.valueOf(totalReward)).divide(BigInteger.valueOf(totalVote))`), mirroring the pattern already used in the new Vi-based algorithm (`deltaVi.multiply(BigInteger.valueOf(userVote)).divide(DECIMAL_OF_VI_REWARD)`) and in the exchange actuators' `BigInteger`/`BigDecimal` computations. If floating point must be retained for compatibility, add an explicit floor/round strategy that avoids losing entitled dust, or track/accumulate rounding remainders so they are not permanently lost.

### Proof of Concept
1. Configure a witness with cycle `totalReward = 100` (a small transaction-fee/block reward share) and `totalVote = 10_000_000` (large aggregate vote weight from many delegators).
2. A delegator votes `userVote = 50_000` for this witness (0.5% share).
3. `voteRate = 50_000 / 10_000_000 = 0.005`; `voteRate * totalReward = 0.5`, which truncates to `0` when accumulated into the `long reward`.
4. The delegator calls `WithdrawBalanceContract` for the corresponding cycle; `computeReward` returns `0`, `adjustAllowance` no-ops, and `beginCycle`/`endCycle` for the account are advanced past that cycle — the entitled (mathematically nonzero) share of the cycle reward is permanently unclaimable, even though the delegator held a real proportional stake in the SR's reward pool for that cycle.

  private long computeReward(long cycle, List<Pair<byte[], Long>> votes) {
    long reward = 0;
    for (Pair<byte[], Long> vote : votes) {
      byte[] srAddress = vote.getKey();
      long totalReward = delegationStore.getReward(cycle, srAddress);
      if (totalReward <= 0) {
        continue;
      }
      long totalVote = delegationStore.getWitnessVote(cycle, srAddress);
      if (totalVote == DelegationStore.REMARK || totalVote == 0) {
        continue;
      }
      long userVote = vote.getValue();
      double voteRate = (double) userVote / totalVote;
      reward += voteRate * totalReward;
    }
    return reward;
  }

  private long computeReward(long beginCycle, long endCycle, AccountCapsule accountCapsule) {
    if (beginCycle >= endCycle) {
      return 0;
    }

    long reward = 0;
    long newAlgorithmCycle = dynamicPropertiesStore.getNewRewardAlgorithmEffectiveCycle();
    List<Pair<byte[], Long>> srAddresses = accountCapsule.getVotesList().stream()
        .map(vote -> new Pair<>(vote.getVoteAddress().toByteArray(), vote.getVoteCount()))
        .collect(Collectors.toList());
    if (beginCycle < newAlgorithmCycle) {
      long oldEndCycle = min(endCycle, newAlgorithmCycle,
          dynamicPropertiesStore.disableJavaLangMath());
      reward = getOldReward(beginCycle, oldEndCycle, srAddresses);
      beginCycle = oldEndCycle;
    }
    if (beginCycle < endCycle) {
      for (Pair<byte[], Long>  vote : srAddresses) {
        byte[] srAddress = vote.getKey();
        BigInteger beginVi = delegationStore.getWitnessVi(beginCycle - 1, srAddress);
        BigInteger endVi = delegationStore.getWitnessVi(endCycle - 1, srAddress);
        BigInteger deltaVi = endVi.subtract(beginVi);
        if (deltaVi.signum() <= 0) {
          continue;
        }
        long userVote = vote.getValue();
        reward += deltaVi.multiply(BigInteger.valueOf(userVote))
            .divide(DelegationStore.DECIMAL_OF_VI_REWARD).longValue();
      }
    }
    return reward;
  }
