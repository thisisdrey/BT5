### Title
Unbounded array allocation from attacker-controlled length in `PrecompiledContracts.extractBytesArray` (legacy `ValidateMultiSign` path) - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The `ValidateMultiSign` precompiled contract, reachable by any account via a normal TVM contract call, decodes an ABI array length directly from calldata and uses it to allocate a Java array without validating it against any maximum, mirroring the missing-bounds-check pattern in the CVE (`CEPH_MAX_KEY_LEN` not enforced before trusting a decoded length).

### Finding Description
`ValidateMultiSign.execute()` extracts the signature array either via `extractSigArray` (bounded path) or `extractBytesArray` (legacy path), selected by the `allowTvmSelfdestructRestriction` fork flag: [1](#0-0) 

The `sigArraySize > MAX_SIZE` bound check at line 1067-1070 is only performed inside the `if (VMConfig.allowTvmSelfdestructRestriction())` branch. When that fork flag is **not** active, `extractBytesArray` is invoked directly with no upper-bound validation on the decoded length: [2](#0-1) 

`len` is `words[offset].intValueSafe()`, a value fully attacker-controlled via calldata to the precompile. `new byte[len][]` is executed with no upper bound, no null check, and — critically — this line executes *before* the `try { ... } catch (Throwable t) { ... }` block that wraps the rest of `execute()` (the `try` begins only at account/permission lookup, after the array has already been allocated): [3](#0-2) 

Supplying a large `len` (e.g., close to `Integer.MAX_VALUE`, bounded only by `intValueSafe()`'s clamping) causes `new byte[len][]` to throw an uncaught `OutOfMemoryError`, or a negative/malformed value can throw `NegativeArraySizeException` — neither of which is caught by the later `try`/`catch (Throwable t)` block since it happens before that block executes. This is directly analogous to the CVE's root cause: a length value decoded from untrusted input is used to size a buffer/array without first being checked against a sane maximum (`CEPH_MAX_KEY_LEN`), risking overflow/resource exhaustion.

### Impact Explanation
An uncaught `OutOfMemoryError`/`NegativeArraySizeException` thrown from inside TVM execution (during contract call processing, which happens both for constant calls in query paths and for block-applying execution of broadcast transactions) can propagate up through the executing thread. Depending on the surrounding execution/thread-management machinery, this can crash or destabilize the node's transaction-processing thread, disrupt VM invocation for the current block, or exhaust node memory, resulting in denial of service — reachable by any account that can issue a TVM contract call to the address of `ValidateMultiSign` with crafted calldata, requiring no special privilege.

### Likelihood Explanation
Exploitability depends on the `allowTvmSelfdestructRestriction` fork flag being inactive on the target chain/fork height; if it is already active on the network in question, the legacy `extractBytesArray` path (and therefore this specific unbounded allocation) is unreachable, since `extractSigArray` would be used and the size would already have been bound-checked at line 1067-1070. I was not able to confirm from the available index whether this fork is enabled by default in the version under review or gated behind a not-yet-activated proposal — this should be verified directly in `DynamicPropertiesStore`/`VMConfig` before treating this as immediately exploitable on a live, fully-upgraded mainnet. On any chain/fork configuration where the flag is still off (e.g., private/consortium chains freshly deployed from this codebase, or testnets pre-activation), the path is trivially reachable by an unprivileged caller.

### Recommendation
Move the `sigArraySize`/length bound check (`> MAX_SIZE`) so it applies unconditionally before calling either `extractSigArray` or `extractBytesArray`, regardless of the `allowTvmSelfdestructRestriction` flag state. Additionally, harden `extractBytesArray` (and `extractBytes32Array`) itself to reject non-positive or overly large `len` values before allocation, and ensure the array-extraction call sits inside the existing `try { ... } catch (Throwable t) { ... }` guard in `execute()` so any allocation failure degrades gracefully to `DATA_FALSE` instead of propagating an uncaught `Error`.

### Proof of Concept
1. Deploy/call a contract that invokes the `ValidateMultiSign` precompile (fixed TVM precompile address) with a raw ABI-encoded payload where the DataWord at the array-length offset (`words[3]`) encodes a very large integer (e.g., `0x7fffffff`) instead of a small array length.
2. Ensure the target network/fork has not activated `allowTvmSelfdestructRestriction` (`VMConfig.allowTvmSelfdestructRestriction()` returns `false`), so `execute()` calls `extractBytesArray` directly without any prior bound check.
3. Broadcast the transaction; `extractBytesArray` executes `new byte[len][]` with `len` ≈ `Integer.MAX_VALUE`, throwing an uncaught `OutOfMemoryError` before the surrounding `try/catch(Throwable)` block (which starts later, at the account lookup) can intercept it, propagating the error out of the precompile execution.
