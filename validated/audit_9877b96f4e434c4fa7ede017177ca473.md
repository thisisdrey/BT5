### Title
Stale `PostponedReceipt`/`ReceivedData`/`PendingDataCount` rows survive `DeleteAccountAction` and can resolve against a re-created account of the same name - (`core/store/src/utils/mod.rs`)

### Summary
`remove_account` (invoked by `action_delete_account`) only removes the `Account`, `ContractCode`, `AccessKey`/gas-key, and `ContractData` trie entries for a deleted account; it never touches `TrieKey::ReceivedData`, `TrieKey::PostponedReceiptId`, `TrieKey::PendingDataCount`, or `TrieKey::PostponedReceipt` rows keyed by that `receiver_id`. If X had an outstanding cross-contract-call dependency at the time of deletion, these rows remain in the trie under X's name. When X is later re-created and the pending `DataReceipt` finally arrives, `Runtime::process_receipt`/`apply_action_receipt` will fetch and execute the old postponed `Receipt` against whatever account currently occupies X.

### Finding Description
The account-lifecycle asymmetry:
- `remove_account` only clears 4 trie key families: `Account`, `ContractCode`, `AccessKey`(+gas key nonces), `ContractData`. [1](#0-0) 
- The postponed-receipt bookkeeping (`TrieKey::PostponedReceiptId`, `TrieKey::PendingDataCount`, `TrieKey::PostponedReceipt`, `TrieKey::ReceivedData`) is created in `process_action_receipt`/`process_receipt` purely as a function of `receiver_id` + `data_id`/`receipt_id`, with no existence check on the target account. [2](#0-1) 
- `action_delete_account` calls `remove_account` unconditionally and does not check for, or reject deletion because of, any pending `PostponedReceiptId`/`PendingDataCount`/`PostponedReceipt` rows for the account. [3](#0-2) 
- When the missing `DataReceipt` eventually arrives, `process_receipt`'s `Data` arm looks the postponed receipt up purely by `receiver_id`/`data_id`/`receipt_id`, with no check that the account still exists (let alone that it's the "same" account), fetches the stored `Receipt`, and executes it via `apply_action_receipt`. [4](#0-3) 
- `apply_action_receipt` resolves the account only at execution time (`get_account(state_update, account_id)` after the data was already collected), so whichever account currently exists at that name — including a brand-new account created after X was deleted — is the one against which the stale actions run. [5](#0-4) 

Attack path: (1) attacker deploys a contract on X and issues a cross-contract call whose callback (self-receipt with `input_data_ids`) is still outstanding, producing `PostponedReceiptId`/`PendingDataCount`/`PostponedReceipt` rows for X; (2) attacker submits `DeleteAccountAction` on X (no check blocks deletion while postponed data exists); (3) X is re-created (by the attacker, a sub-account creator, or through a TLD registrar contract that lets a third party claim the freed name); (4) the original external contract's `DataReceipt` finally arrives and is routed by `receiver_id=X` to the still-present postponed bookkeeping, causing the old `Receipt` (with attacker-chosen `method_name`, `args`, and `predecessor_id`) to execute against the new account's deployed code and storage. No existing signature, nonce, access-key, or account-existence check intercepts this, because the postponement/resolution logic is keyed only on `AccountId`, not on any per-incarnation identifier (there is no "account generation" or account-creation-height field distinguishing old X from new X).

### Impact Explanation
This is an authorization/determinism violation: a receipt payload chosen entirely by the *old* occupant of an account name is executed later under the *new* occupant's account state, using the old receipt's `predecessor_id`. This is particularly dangerous for `#[private]`-style self-call guards common in NEAR contracts (`predecessor_id() == current_account_id()`), because a postponed self-callback receipt satisfies that check by construction regardless of which incarnation of the contract is currently deployed — allowing execution of a privileged method on the new contract without any real self-call having occurred. This maps to the "authorization escalation across accounts or promises" bounty category. It can also leave storage in the trie that is unaccounted for by the new account's `storage_usage` (unbilled state bloat), though the state root itself remains deterministic across validators (no chain split, since all nodes execute the same code path identically).

### Likelihood Explanation
Preconditions are fully attacker-controlled and cheap: deploy a contract, initiate a two-hop cross-contract call with an unresolved callback, then delete the account before the callback resolves, then have the account name re-registered. The scenario is fully repeatable at negligible gas/storage cost. The realistic complication is that the account re-creator must, in the general case, be the same actor (sub-account/registrar creation is gated by the account-naming rules), which limits the "victim is a different party" scenario to specific account types (e.g., short TLD names reclaimable via a registrar contract that allows third-party registration), and the attacker would generally need to guess or target a specific eventual method name on the replacement contract to weaponize the `#[private]` bypass. This makes the "state pollution / stale-row persistence" part of the claim fully confirmed and easily demonstrable, while the "concrete privilege-escalation against an unrelated victim" part is realistic but situational, not universally exploitable against arbitrary victims.

### Recommendation
`remove_account` should also purge, for the given `account_id`: all `TrieKey::ReceivedData`, `TrieKey::PostponedReceiptId`, `TrieKey::PendingDataCount`, and `TrieKey::PostponedReceipt` entries (mirroring the iteration pattern already used for access keys/contract data), or `action_delete_account` should reject deletion (return an `ActionError`) while any such pending rows exist for the account, forcing outstanding promises to resolve or expire before the name can be freed and reused.

### Proof of Concept
Runtime integration test plan (test-loop or `runtime/runtime/src/tests/apply.rs`-style):
1. Deploy a contract on account `x` that performs a cross-contract call to account `y` and registers a `then` callback on `x` itself (so a `TrieKey::PostponedReceiptId{receiver_id: x, data_id}` / `TrieKey::PendingDataCount{receiver_id: x, ...}` / `TrieKey::PostponedReceipt{receiver_id: x, ...}` set gets written once the callback receipt reaches `x` before `y`'s response arrives).
2. Before `y`'s `DataReceipt` is delivered, submit `DeleteAccountAction` on `x` with a valid beneficiary.
3. Assert (this is the core reproducible assertion demonstrating the bug) that after committing the delete, `state_update`/trie still contains the `PostponedReceiptId`, `PendingDataCount`, and `PostponedReceipt` rows for `x` (i.e., they were NOT removed by `remove_account`), by directly querying `near_store::get`/`get_postponed_receipt` for those `TrieKey`s.
4. Re-create account `x` (via `CreateAccountAction`) with a different deployed contract containing a `#[private]`-guarded admin method matching the pending callback's `method_name`.
5. Deliver `y`'s `DataReceipt` to `x` and assert that the postponed callback receipt executes against the new `x` account (e.g., observe a state mutation only reachable through the guarded method), confirming that a self-call-gated function executed without the new owner ever authorizing that specific invocation.

/// Removes account, code and all access keys and gas keys associated to it.
pub fn remove_account(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
) -> Result<RemoveAccountResult, StorageError> {
    state_update.remove(TrieKey::Account { account_id: account_id.clone() });
    state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });

    let mut gas_key_nonce_count: usize = 0;
    let mut gas_key_nonce_total_key_bytes: usize = 0;

    // Removing access keys and gas key nonces
    let lock = state_update.trie().lock_for_iter();
    let mut keys_to_remove: Vec<TrieKey> = Vec::new();
    for raw_key in state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_access_keys(account_id), &lock)?
    {
        let raw_key = raw_key?;
        let key_handle = trie_key_parsers::parse_key_handle_from_access_key_key(
            &raw_key, account_id,
        )
        .map_err(|_e| {
            StorageError::StorageInconsistentState(
                "Can't parse key handle from raw key for AccessKey".to_string(),
            )
        })?;
        let nonce_index =
            trie_key_parsers::parse_nonce_index_from_gas_key_key(&raw_key, account_id, &key_handle)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse nonce index from raw key for AccessKey".to_string(),
                    )
                })?;
        if let Some(index) = nonce_index {
            gas_key_nonce_count += 1;
            gas_key_nonce_total_key_bytes += raw_key.len();
            keys_to_remove.push(TrieKey::gas_key_nonce(
                account_id.clone(),
                key_handle.clone(),
                index,
            ));
        } else {
            keys_to_remove.push(TrieKey::access_key(account_id.clone(), key_handle.clone()));
        }
    }
    drop(lock);

    for trie_key in keys_to_remove {
        state_update.remove(trie_key);
    }

    // Removing contract data
    let lock = state_update.trie().lock_for_iter();
    let data_keys = state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_contract_data(account_id, &[]), &lock)?
        .map(|raw_key| {
            trie_key_parsers::parse_data_key_from_contract_data_key(&raw_key?, account_id)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse data key from raw key for ContractData".to_string(),
                    )
                })
                .map(Vec::from)
        })
        .collect::<Result<Vec<_>, _>>()?;
    drop(lock);

    for key in data_keys {
        state_update.remove(TrieKey::ContractData { account_id: account_id.clone(), key });
    }
    Ok(RemoveAccountResult { gas_key_nonce_count, gas_key_nonce_total_key_bytes })
