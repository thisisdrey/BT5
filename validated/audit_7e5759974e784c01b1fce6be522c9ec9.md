### Title
Priority-only eviction in `push_ids_into_queue` lets unschedulable high-priority spam evict schedulable low-priority victims - (File: `core/src/banking_stage/transaction_scheduler/transaction_state_container.rs`)

### Summary
`GreedyScheduler::schedule` pushes transactions that fail to schedule due to account-lock conflicts back into the container via `push_ids_into_queue`, and that function's capacity-eviction (`pop_first`) is purely priority-ordered with no notion of schedulability. Because posted priority (compute-unit price) costs nothing unless the transaction actually executes, an attacker can flood the buffer with mutually-conflicting, high-priority, permanently-unschedulable transactions that never pay a fee, causing genuinely schedulable but lower-priority legitimate transactions to be evicted instead.

### Finding Description
In `GreedyScheduler::schedule` [1](#0-0) , every popped transaction that hits `TransactionSchedulingError::UnschedulableConflicts` (from `TryLockError::MultipleConflicts` in account-lock acquisition) is pushed into `self.unschedulables` rather than dropped. Because the scan/scheduling pass can stop early due to `budget`, `max_scanned_transactions_per_scheduling_pass`, or `schedulable_threads` becoming empty, lower-priority legitimate transactions further down the `BTreeSet` may never even be popped/scanned that pass, remaining resident in the queue.

At the end of the pass, `container.push_ids_into_queue(self.unschedulables.drain(..))` [2](#0-1)  re-inserts the still-conflicting, high-priority attacker transactions into the priority queue. `push_ids_into_queue` in `TransactionStateContainer` then computes `num_dropped` purely from `id_to_transaction_state.len() - capacity` and evicts via `self.priority_queue.pop_first()` — i.e., strictly the lowest-priority items in the `BTreeSet<TransactionPriorityId>` [3](#0-2) . This eviction has no awareness of whether an entry is actually schedulable; it only compares `priority`. Since the re-inserted attacker transactions were selected precisely because they had higher priority than untouched lower-priority legitimate entries still sitting at the bottom of the same `BTreeSet`, `pop_first` will preferentially evict the legitimate low-priority-but-schedulable transactions instead of the attacker's high-priority-but-permanently-conflicting ones.

Critically, posted priority (`compute_unit_price`) is free to claim: `Consumer::check_fee_payer_unlocked` only verifies the fee payer currently has enough lamports to cover the calculated fee at buffering time — a point-in-time balance snapshot check, not a reservation/hold [4](#0-3) . The fee itself is only actually deducted at execution time in `validate_transaction_fee_payer` inside SVM [5](#0-4) . Because the attacker's cyclic-conflict transactions are designed to never actually get scheduled (`UnschedulableConflicts` every pass), they never execute and thus never actually pay the high fee they claim, while the same funded fee-payer balance can back many distinct never-executing transactions with high `compute_unit_price` values.

### Impact Explanation
This is a QoS-evasion / underpriced-work scenario: an attacker can occupy container capacity and repeatedly cause eviction of legitimate, fee-paying, schedulable transactions from `TransactionStateContainer`, purely with fee-market-highest-priority claims that are never actually paid because the spam transactions are designed to remain in permanent lock conflict and thus never execute/never get charged. The existing capacity bound of the container is respected (no unbounded memory growth), but the fairness invariant of the eviction policy — "highest fee wins, but low-fee legitimate work is dropped only when truly outcompeted by real (paid) higher-fee work" — is broken.

### Likelihood Explanation
Feasibility requires: (1) an unstaked attacker able to submit ordinary transactions over TPU/QUIC with a modestly funded fee payer sufficient to pass the balance snapshot check in `check_fee_payer_unlocked`, (2) crafting a set of mutually-conflicting transactions (a conflict graph spanning multiple threads, so `ThreadAwareAccountLocks::try_lock_accounts` returns `TryLockError::MultipleConflicts`) sized to exceed the scheduler's thread/account-lock capacity, and (3) setting compute-unit-price above the victim's. This uses only standard entrypoints already exercised by the greedy scheduler's own conflict-handling tests (e.g. `test_schedule_scan_past_highest_priority`, `test_schedule_local_fee_markets` [6](#0-5) ), which already demonstrate that conflicting transactions are routinely marked `UnschedulableConflicts` and pushed back through this exact code path. No staking, no privileged access, and no actual fee payment on the malicious transactions is required, making the attack cheap and repeatable across scheduling passes.

### Recommendation
Make `push_ids_into_queue`'s capacity eviction schedulability-aware, or at minimum bias eviction against transactions that have repeatedly failed to schedule (e.g., track a per-transaction "unschedulable streak" and prefer evicting entries with high streak counts over strictly lowest-priority entries), so that posted-but-unrealized priority cannot be used to displace transactions that are actually being serviced. Alternatively, cap how many times/how long a transaction may remain in `unschedulables` before being deprioritized or dropped, decoupling raw priority from "wins under capacity pressure."

### Proof of Concept
Rust unit test plan added to `core/src/banking_stage/transaction_scheduler/greedy_scheduler.rs` test module (uses existing `create_test_frame`/`create_container` helpers):
1. Configure a `GreedyScheduler` with `num_threads = 2` and small `target_scheduled_cus`/`max_scanned_transactions_per_scheduling_pass` to make capacity easy to exceed.
2. Build a container near capacity with:
   - One low-priority, non-conflicting "victim" transaction touching a unique pubkey (schedulable every pass).
   - N high-priority transactions forming a conflict cycle across ≥2 threads (e.g., alternating shared pubkeys across pairs) that always resolve to `TryLockError::MultipleConflicts`, all with priority > victim's priority.
3. Call `scheduler.schedule(&mut container, u64::MAX)` repeatedly (simulating several scheduling passes as in production loop), each time re-feeding `push_ids_into_queue` results.
4. Assert that after several passes, `container.get_transaction(victim_id)` returns `None` (victim evicted) while attacker transaction ids remain present in the container (`container.buffer_size()` includes them), even though `scheduling_summary.num_scheduled` for attacker ids stays 0 across all passes — demonstrating that never-executing, never-fee-paying transactions displaced a genuinely schedulable lower-priority transaction purely via posted priority.

    fn push_ids_into_queue(
        &mut self,
        priority_ids: impl Iterator<Item = TransactionPriorityId>,
    ) -> usize {
        for id in priority_ids {
            self.priority_queue.insert(id);
        }

        // The number of items in the `id_to_transaction_state` map is
        // greater than or equal to the number of elements in the queue.
        // To avoid the map going over capacity, we use the length of the
        // map here instead of the queue.
        let num_dropped = self
            .id_to_transaction_state
            .len()
            .saturating_sub(self.capacity);

        for _ in 0..num_dropped {
            let priority_id = self.priority_queue.pop_first().expect("queue is not empty");
            self.remove_state(priority_id.id);
        }

        num_dropped
    }

    // Loads transaction fee payer, collects rent if necessary, then calculates
    // transaction fees, and deducts them from the fee payer balance. If the
    // account is not found or has insufficient funds, an error is returned.
    fn validate_transaction_fee_payer<CB: TransactionProcessingCallback>(
        account_loader: &mut AccountLoader<CB>,
        message: &impl SVMMessage,
        nonce_info: Option<NonceInfo>,
        compute_budget_and_limits: SVMTransactionExecutionAndFeeBudgetLimits,
        rent: &Rent,
        relax_post_exec_min_balance_check: bool,
        error_counters: &mut TransactionErrorMetrics,
    ) -> TransactionResult<ValidatedTransactionDetails> {
        let fee_payer_address = message.fee_payer();

        // We *must* use load_transaction_account() here because *this* is when the fee-payer
        // is loaded for the transaction. Transaction loading skips the first account and
        // loads (and thus inspects) all others normally.
        let Some(mut loaded_fee_payer) =
            account_loader.load_transaction_account(fee_payer_address, true)
        else {
            error_counters.account_not_found += 1;
            return Err(TransactionError::AccountNotFound);
        };

        let fee_payer_loaded_rent_epoch = loaded_fee_payer.account.rent_epoch();
        update_rent_exempt_status_for_account(rent, &mut loaded_fee_payer.account);

        let fee_payer_index = 0;
        validate_fee_payer(
            &mut loaded_fee_payer.account,
            fee_payer_index,
            error_counters,
            rent,
            compute_budget_and_limits.fee_details.total_fee(),
            relax_post_exec_min_balance_check,
        )?;
