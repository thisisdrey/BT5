### Title
Attacker can brick `Pool.liquidate` for new collateral types by stuffing the `feeCollector`'s deposit-token list to `MAX_TOKENS_PER_USER` via dust transfers - (File: contracts/DepositToken.sol, contracts/Pool.sol)

### Summary
Analogous to the Witch finding (a revert inside the liquidation payout path makes a position un-liquidatable), Metronome's `Pool.liquidate` unconditionally seizes a fee to `_poolRegistry.feeCollector()` whenever `protocolLiquidationFee > 0`. `DepositToken._transfer` calls `pool.addToDepositTokensOfAccount(recipient_)` the first time an account receives a deposit token, and `Pool` enforces a per-account cap (`MAX_TOKENS_PER_USER`) on that `MappedEnumerableSet` list. An unprivileged attacker can dust-transfer every listed deposit token to the `feeCollector`, filling its list to the cap. Any subsequent `liquidate` that tries to pay a fee in a deposit token the `feeCollector` has never held reverts — making those liquidations impossible while the fee is enabled.

### Finding Description
`Pool.liquidate` performs two seizes (contracts/Pool.sol:589-593):

```solidity
depositToken_.seize(account_, _msgSender, _toLiquidator);

if (_fee > 0) {
    depositToken_.seize(account_, _poolRegistry.feeCollector(), _fee);
}
```

`seize` routes to `DepositToken._transfer` (contracts/DepositToken.sol:343-345, 498-525), which ends with:

```solidity
// Add this token to the deposit tokens list if the recipient is receiving it for the 1st time
if (_recipientBalanceBefore == 0 && amount_ > 0) {
    pool.addToDepositTokensOfAccount(recipient_);
}
```

`Pool.addToDepositTokensOfAccount` adds the token into `depositTokensOfAccount[account]`, a `MappedEnumerableSet` capped by `MAX_TOKENS_PER_USER`; exceeding the cap reverts (both symbols are referenced in `contracts/Pool.sol` and `contracts/interfaces/IPool.sol`). Because the recipient of the fee seize is the fixed `feeCollector` — not the liquidator — the attacker cannot control the recipient argument directly, but can control the *state* of that recipient's list:

1. Attacker deposits a dust amount (or acquires dust via `transfer`/`transferFrom`) of each whitelisted `DepositToken`.
2. Attacker calls `depositToken.transfer(feeCollector, 1 wei)` for each token. Each call succeeds (transfers to `feeCollector` are not restricted) and appends the token to `depositTokensOfAccount[feeCollector]` until the list reaches `MAX_TOKENS_PER_USER`.
3. Thereafter, any `Pool.liquidate` call on a position whose seized `depositToken_` is a token the `feeCollector` has never held reverts inside `seize` → `addToDepositTokensOfAccount`, because adding a new entry would exceed the cap. The revert happens after `syntheticToken_.burn`/`_debtToken.burn`, so the whole transaction rolls back — the liquidation simply cannot execute.

The same applies to any *new* deposit token added to the pool later: the `feeCollector`'s full list guarantees its first fee seizure reverts.

### Impact Explanation
- **Liveness break in the liquidation invariant**: positions backed by deposit tokens not yet held by `feeCollector` cannot be liquidated while `protocolLiquidationFee > 0`. Underwater positions accumulate bad debt that the protocol must absorb — the same "un-liquidatable position" outcome as the Witch `auctioneer == address(0)` bug.
- The attack is unprivileged: only public `deposit`/`transfer` calls to a fixed protocol address are needed, at dust cost.
- Duration is at least temporary and effectively indefinite for new collateral types, since the `feeCollector` cannot remove list entries without withdrawing balances (which requires the privileged role to act, and even then only frees slots for already-held tokens).

### Likelihood Explanation
- Requires `protocolLiquidationFee > 0`, which is a supported and tested configuration (`updateProtocolLiquidationFee` is exercised in `test/Pool.test.ts`).
- Cost is trivial: `MAX_TOKENS_PER_USER` dust transfers of already-whitelisted deposit tokens; no flash loan, oracle manipulation, or privileged access required.
- No existing guard stops it: `transfer` only checks `_revertIfLocked` on the sender; there is no restriction on transferring to `feeCollector`, and `liquidate` has no try/catch or fallback recipient around the fee seize.

### Recommendation
- Do not couple liquidation liveness to the `feeCollector`'s token-list cap. Options:
  - Send the liquidation fee to the liquidator or to the Treasury pull path instead of minting `DepositToken` balances to `feeCollector`.
  - Make `addToDepositTokensOfAccount` non-reverting for the `feeCollector` (or exempt `feeCollector`/`Treasury`/`Pool` from `MAX_TOKENS_PER_USER`), or have `seize` skip the list update for the fee recipient.
  - Alternatively, let the liquidator specify a fee recipient or make the fee seize tolerant (try/catch with fallback), so a full recipient list cannot revert the entire liquidation.

### Proof of Concept
Foundry/Hardhat fork outline (conceptual; to be run against deployed `Pool`/`DepositToken`/`PoolRegistry` addresses):

```solidity
// Setup: pool with protocolLiquidationFee > 0 (FeeProvider.updateProtocolLiquidationFee)
// attacker = unprivileged EOA

// 1) Fill feeCollector's deposit-token list
address feeCollector = poolRegistry.feeCollector();
IDepositToken[] memory tokens = /* all deposit tokens registered in Pool */;
uint256 cap = pool.MAX_TOKENS_PER_USER();
for (uint256 i; i < tokens.length && pool.depositTokensOfAccount(feeCollector).length < cap; ++i) {
    tokens[i].deposit(2, attacker);          // get dust balance
    tokens[i].transfer(feeCollector, 1);     // adds token to feeCollector's list
}
// Optionally repeat with other deposit tokens until list length == cap.

// 2) Pick or create an underwater position whose collateral is a depositToken
//    that feeCollector has NEVER held (e.g., a newly listed msdXYZ).
//    Manipulate price down in a normal way (market move / fresh unhealthy position).

// 3) Any liquidator call reverts inside DepositToken._transfer ->
//    Pool.addToDepositTokensOfAccount(feeCollector) due to the cap.
vm.expectRevert(); // MaxTokensPerUser / list-full error
pool.liquidate(syntheticToken, victim, amountToRepay, newDepositToken);
```

Note: the exact revert name and the `MAX_TOKENS_PER_USER` enforcement live in `Pool.sol`'s `addToDepositTokensOfAccount`/`MappedEnumerableSet` code, which the index surfaced only partially; the mechanism (first-transfer list insert at DepositToken.sol:518-520 plus the cap referenced in `IPool.sol`/`Pool.sol`) is confirmed, but the precise error and current `feeCollector` list occupancy on each deployment should be verified when writing the runnable PoC.
