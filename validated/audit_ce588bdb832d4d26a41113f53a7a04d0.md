### Title
Malicious submodule URL in an attacker-served Git repository can force local `file://` clones outside the checkout — (File: `tools/build_defs/repo/git_worker.bzl`)

### Summary
`git_repository`'s submodule handling forces Git's `protocol.file.allow` setting to `always`, which re-enables local-transport (`file://`) submodule cloning that upstream Git disabled by default (as a fix for the local-clone information-disclosure class of issue, tracked upstream as bazelbuild/bazel#17040). This lets a third-party repository that Bazel fetches — content fully controlled by an unprivileged attacker (repo owner, compromised mirror, or MITM'd `file://`/`http://` remote without integrity pinning) — declare a `.gitmodules` entry whose submodule URL is a local path on the machine running the build, causing `git submodule update --init` to copy files from that local path into the checked-out external repository tree.

### Finding Description
`update_submodules` in `tools/build_defs/repo/git_worker.bzl` always adds `-c protocol.file.allow=always` before running `submodule update --init [--recursive] --checkout --force`: [1](#0-0) 

The comment explicitly documents that this re-enables local-directory submodule cloning: [2](#0-1) 

This setting is applied unconditionally whenever `init_submodules` or `recursive_init_submodules` is set on the `git_repository`/`new_git_repository` rule: [3](#0-2) 

The submodule URLs themselves come entirely from the `.gitmodules` file inside the fetched, attacker-controlled repository — Bazel does not validate or restrict these URLs before invoking `git submodule update`. `_execute` sets the working directory to the checkout directory but does not sandbox or otherwise constrain what `git`'s local-transport clone can read: [4](#0-3) 

Git's own default (`protocol.file.allow=user`, changed from `always`) exists precisely because a malicious repository can point a submodule to a local path such as another checkout, a build cache directory, or any path readable by the invoking user, and Git's local clone optimization (hardlinking/direct object copy rather than the normal fetch protocol) will pull in that content, including files never intended to be exposed through the git protocol. By forcing `protocol.file.allow=always`, Bazel deliberately disables this protection for every `git_repository` invocation with submodules enabled, regardless of how untrusted the fetched remote is.

### Impact Explanation
An attacker who serves or owns a Git repository consumed via `git_repository(..., init_submodules = True)` (or `recursive_init_submodules = True`) can plant a `.gitmodules` file with a submodule pointing at a local filesystem path on the victim's build machine (e.g., another repository's working tree, a shared cache directory, or any path readable by the build user, potentially including the Bazel output base / execroot of other builds). When Bazel's `git submodule update --init` runs with `protocol.file.allow=always`, it will copy that local content into the checked-out repository tree under the attacker's control, breaking the containment invariant that content in the checked-out external repository originates only from the declared remote. The exfiltrated content becomes part of the workspace and can be echoed into build outputs, logs, or artifacts, disclosing files the attacker had no legitimate access to.

### Likelihood Explanation
Likelihood is moderate: it requires a victim to use `git_repository`/`new_git_repository` with `init_submodules`/`recursive_init_submodules` against a remote the attacker can control content for (a plausible supply-chain scenario — a compromised or malicious upstream dependency, or an unauthenticated mirror). No credentials, MITM, or sandbox bypass beyond normal Git submodule semantics are needed; the only enabling factor is Bazel's own explicit override of Git's safer default.

### Recommendation
Do not unconditionally force `protocol.file.allow=always` for submodule operations on repositories whose remote/content is untrusted. Scope the override narrowly (e.g., only when the top-level `remote` itself is a local path the same trust domain controls) or restrict the config so only paths under the current checkout/workspace root are honored, and document/require explicit opt-in (e.g. a rule attribute) before disabling this protection for a given `git_repository` invocation.

### Proof of Concept
1. Create `attacker.git` with a `.gitmodules` entry: `git submodule add file:///etc <victim-sensitive-copy>` (or point at another local directory containing sensitive files reachable by the build user).
2. In a `MODULE.bazel`, declare:
```
git_repository(
    name = "dep",
    remote = "https://attacker-controlled-or-compromised-host/attacker.git",
    commit = "<pinned commit chosen by attacker>",
    init_submodules = True,
)
```
3. Run `bazel fetch @dep`. Because `update_submodules` in `git_worker.bzl` passes `-c protocol.file.allow=always`, `git submodule update --init` will clone/copy the local path content into `external/+git_repository+dep/<victim-sensitive-copy>`, even though the declared `remote` never referenced that local path — demonstrating containment bypass via attacker-controlled submodule metadata. def update_submodules(ctx, git_repo, recursive = False):
    if recursive:
        # "protocol.file.allow=always" allows the submodule command clone from a local directory.
        # It's necessary for Git 2.38.1 and assoicated backport versions.
        # See https://github.com/bazelbuild/bazel/issues/17040
        _git_maybe_shallow(ctx, git_repo, "-c", "protocol.file.allow=always", "submodule", "update", "--init", "--recursive", "--checkout", "--force")
    else:
        _git_maybe_shallow(ctx, git_repo, "-c", "protocol.file.allow=always", "submodule", "update", "--init", "--checkout", "--force")
