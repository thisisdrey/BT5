## Title
Privilege escalation via improper scope enforcement in `AccountPermissionUpdateContract` execution — ([File: actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java])

### Summary
`AccountPermissionUpdateActuator` lets any signer whose active `Permission` merely has the `AccountPermissionUpdateContract` operation bit enabled completely overwrite the account's `Owner` permission (and `Witness`/other `Active` permissions), with no check that the acting key's own scope is proportionate to the change being made. This mirrors the Keycloak FGAPv2 flaw: a principal that was only granted a narrow, specific capability ("manage this client's scope" / here "call `AccountPermissionUpdateContract`") can use that single capability to grant itself unrestricted, higher-privilege control ("assign any realm role" / here "become sole Owner"), because the enforcement point only checks that the *contract type bit* is set, not that the *resulting permission state* is within the caller's authority.

### Finding Description
Transaction-level authorization for a permissioned account is enforced by checking that the signer's `Permission` (selected by `permission_id`) has its `Active` type and that the specific `ContractType` bit is set in its `operations` bitmask: [1](#0-0) 

For a `TriggerSmartContract`/`TransferContract` this is a sound, narrow scope check — the key can only perform that specific operation type. But for `AccountPermissionUpdateContract` (contract type 46), passing this same single-bit check is treated as authorization to execute the actuator, which then unconditionally overwrites the account's entire permission structure — `Owner`, `Witness`, and all `Active` permissions — with attacker-supplied `Permission` messages: [2](#0-1) 

The `validate()`/`checkPermission()` logic only sanity-checks the *shape* of the new permissions (key count, threshold, distinct addresses, valid `ContractType` bits versus `getAvailableContractType()`), never that the caller (identified by the signing `permission_id`) is authorized to set an `Owner` permission or to grant itself a threshold/weight sufficient to unilaterally satisfy future signing requirements: [3](#0-2) 

So the enforcement boundary is "does this active key's `operations` bitmask include bit 46 (`AccountPermissionUpdateContract`)?" — exactly analogous to Keycloak's improper scope-mapping enforcement, where possessing one narrow administrative capability (limited client management) was mistakenly treated as sufficient authority to project arbitrary, more-privileged roles into the token. Here, possessing the single narrow capability "may submit `AccountPermissionUpdateContract`" is treated as sufficient authority to rewrite `Owner` permission itself — the highest privilege level in the account — with keys/thresholds fully chosen by the attacker.

### Impact Explanation
If any account grants an `Active` permission the `AccountPermissionUpdateContract` operation bit (a common pattern for delegating administrative/key-rotation duties to a sub-key, expected to be scoped only to permission housekeeping), the holder of that narrowly-scoped active key can:
- Set the `Owner` permission to a new set of keys/threshold entirely of their choosing (e.g., itself alone with threshold 1), locking out the legitimate owner and all other active keys.
- Remove or alter `Witness`/other `Active` permissions.

This results in unauthorized account takeover — a concrete unauthorized-account-operation impact matching the "Accept only concrete unauthorized account operation, theft, or permanent freezing of funds" bar. Any funds, TRC10/TRC20 tokens, staked TRX, or delegated resources controlled by that account are then fully controllable by the escalated key.

### Likelihood Explanation
Requires that the account owner has previously configured a multisig `Active` permission that includes the `AccountPermissionUpdateContract` operation bit for a sub-key not intended to have full control (a realistic administrative-delegation configuration, e.g. for automated key-rotation bots or limited co-signers). Given such a configuration — analogous to the "administrator with limited client management permissions" precondition in the Keycloak advisory (PR:H in the CVSS vector) — a single signed transaction is sufficient to escalate; no additional signatures or race conditions are needed since `checkPermission`/`checkWeight` only validate against the *old* permission for the signature, not against the *new* permission content being set.

### Recommendation
When processing `AccountPermissionUpdateContract`, additionally enforce that:
1. A signer using a non-Owner `permission_id` (i.e., an `Active` permission) cannot modify the `Owner` permission at all, or can only propose changes requiring separate `Owner`-level co-signature.
2. If sub-permission modification of `Owner`/`Witness` must be allowed, require the resulting permission's keys/threshold to preserve inclusion of previously-authorized higher-tier keys, or require signatures meeting the *previous* `Owner` threshold regardless of which `permission_id` initiated the transaction.
3. Add validation in `AccountPermissionUpdateActuator.validate()` comparing the acting `permission_id`'s privilege tier against the scope of permissions being changed, similar to how Keycloak's fix restricts scope-mapping role assignment to roles within the actor's own management authority.

### Proof of Concept
1. Owner account `A` configures an `Active` permission (`permission_id = 2`) for delegate key `K`, intending `K` only to rotate/update permission structures, so the `operations` bitmask has bit 46 (`AccountPermissionUpdateContract`) set (and possibly other narrow bits) but not, e.g., `TransferContract`.
2. Attacker who controls `K` (or `K` is compromised) crafts an `AccountPermissionUpdateContract` transaction with `permission_id = 2`, setting:
   - `owner` = a new `Permission` of type `Owner` with a single key = `K`'s address, `threshold = 1`.
   - `actives` = a new `Active` permission also fully controlled by `K`.
3. Transaction passes `TransactionCapsule.checkPermission` (bit 46 set) and `AccountPermissionUpdateActuator.validate()` (shape checks pass), then `execute()` calls `account.updatePermissions(...)` unconditionally, overwriting `Owner` to `K` alone.
4. `K` now fully controls account `A`, including its balance, staked resources, and future permission changes — despite having been granted only the narrow "update permission" capability.

  @Override
  public boolean validate() throws ContractValidateException {

    if (chainBaseManager == null) {
      throw new ContractValidateException(ActuatorConstant.STORE_NOT_EXIST);
    }

    if (this.any == null) {
      throw new ContractValidateException(ActuatorConstant.CONTRACT_NOT_EXIST);
    }

    AccountStore accountStore = chainBaseManager.getAccountStore();
    DynamicPropertiesStore dynamicStore = chainBaseManager.getDynamicPropertiesStore();

    if (dynamicStore.getAllowMultiSign() != 1) {
      throw new ContractValidateException("multi sign is not allowed, "
          + "need to be opened by the committee");
    }
    if (!this.any.is(AccountPermissionUpdateContract.class)) {
      throw new ContractValidateException(
          "contract type error,expected type [AccountPermissionUpdateContract],real type["
              + any.getClass() + "]");
    }
    final AccountPermissionUpdateContract accountPermissionUpdateContract;
    try {
      accountPermissionUpdateContract = any.unpack(AccountPermissionUpdateContract.class);
    } catch (InvalidProtocolBufferException e) {
      logger.debug(e.getMessage(), e);
      throw new ContractValidateException(e.getMessage());
    }
    byte[] ownerAddress = accountPermissionUpdateContract.getOwnerAddress().toByteArray();
    if (!DecodeUtil.addressValid(ownerAddress)) {
      throw new ContractValidateException("invalidate ownerAddress");
    }
    AccountCapsule accountCapsule = accountStore.get(ownerAddress);
    if (accountCapsule == null) {
      throw new ContractValidateException("ownerAddress account does not exist");
    }

    if (!accountPermissionUpdateContract.hasOwner()) {
      throw new ContractValidateException("owner permission is missed");
    }

    if (accountCapsule.getIsWitness()) {
      if (!accountPermissionUpdateContract.hasWitness()) {
        throw new ContractValidateException("witness permission is missed");
      }
    } else {
      if (accountPermissionUpdateContract.hasWitness()) {
        throw new ContractValidateException("account isn't witness can't set witness permission");
      }
    }

    if (accountPermissionUpdateContract.getActivesCount() == 0) {
      throw new ContractValidateException("active permission is missed");
    }
    if (accountPermissionUpdateContract.getActivesCount() > 8) {
      throw new ContractValidateException("active permission is too many");
    }

    Permission owner = accountPermissionUpdateContract.getOwner();
    Permission witness = accountPermissionUpdateContract.getWitness();
    List<Permission> actives = accountPermissionUpdateContract.getActivesList();

    if (owner.getType() != PermissionType.Owner) {
      throw new ContractValidateException("owner permission type is error");
    }
    checkPermission(owner);
    if (accountCapsule.getIsWitness()) {
      if (witness.getType() != PermissionType.Witness) {
        throw new ContractValidateException("witness permission type is error");
      }
      checkPermission(witness);
    }
    for (Permission permission : actives) {
      if (permission.getType() != PermissionType.Active) {
        throw new ContractValidateException("active permission type is error");
      }
      checkPermission(permission);
    }
    return true;
