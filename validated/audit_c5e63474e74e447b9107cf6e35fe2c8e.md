### Title
Liquidator can leave dust collateral on an underwater position with no bad-debt handling, permanently stranding unbacked debt - (File: contracts/Pool.sol)

### Summary
`Pool.liquidate` has no minimum-remaining-collateral threshold and Metronome has no bad-debt write-off mechanism. A liquidator repaying an underwater position can seize nearly all of the borrower's deposit-token balance while deliberately leaving a dust remainder (even 1 wei). Because the leftover collateral is worth less than gas + incentive, no rational liquidator will ever finish the position, and the residual `DebtToken` balance is never cleared — the protocol carries permanently unbacked synthetic supply.

### Finding Description
In `Pool.liquidate` (contracts/Pool.sol:537-596) the only bounds are:

- `amountToRepay_.wadDiv(_debtTokenBalance) > maxLiquidable` reverts (partial-liquidation cap, a governance parameter not guaranteed = 100%).
- `debtFloorInUsd` check reverts only if *remaining debt* lands in `(0, debtFloorInUsd)`; it is a debt floor, not a collateral floor, and defaults to 0.
- `_totalSeized > depositToken_.balanceOf(account_)` reverts, i.e. seizing *up to* the full balance is allowed, and seizing `balance - 1 wei` is equally allowed.

There is no analog of Fraxlend's `minCollateralRequiredOnDirtyLiquidation` — no check that, after a "dirty" liquidation on a position where collateral < debt, the leftover collateral is either zero or economically meaningful. `DepositToken.seize` just transfers shares; nothing forces a full sweep. The repo's own test at test/Pool.test.ts:791-819 demonstrates exactly this: after repaying `quoteLiquidateMax`, the position is still unhealthy with a remainder of ~1600 wei of collateral left, and the borrower still holds a positive `DebtToken` balance.

Unlike Fraxlend there is not even a bad-debt write-off branch to trigger — the leftover debt simply stays backed by dust, i.e. effectively unbacked `SyntheticToken` supply circulating in the pool.

Attack path:
1. Victim position goes underwater (collateral value < debt, e.g. via price drop — no oracle manipulation needed).
2. Attacker calls `liquidate(synth, victim, amountToRepay, depositToken)` choosing `amountToRepay` such that `_totalSeized = balanceOf(victim) - ε` (ε = dust, e.g. 1 wei). All modifiers pass: `whenNotShutdown`, `nonReentrant`, token-existence checks, `maxLiquidable` bound, `debtFloorInUsd` (bypassed if set to 0, or choose repay so remaining debt ≥ floor).
3. Position remains unhealthy forever; no liquidator pays real synths to seize dust. The bad debt is silently socialized into the synth's backing.

### Impact Explanation
Protocol insolvency: synthetic tokens outstanding exceed the recoverable collateral backing them. Honest LPs/lenders absorb the loss when the dust-collateral position can never be closed — analogous to the Fraxlend finding's "last withdrawer loses funds," expressed here as degraded synth collateralization.

### Likelihood Explanation
High conditional likelihood: requires only an underwater position, which naturally occurs in volatile markets (the test suite itself produces one by halving the MET price). The attack needs no privileges, no oracle manipulation, and no governance misconfiguration beyond the default `debtFloorInUsd = 0`. Any liquidator (unprivileged EOA) executing a normal liquidation can leave dust — in fact `quoteLiquidateMax` itself can return a repay amount that leaves a remainder, so dust-leftover outcomes arise even without intent.

### Recommendation
Add a minimum-remaining-collateral (or minimum-remaining-debt) check on liquidations of underwater positions: if `_totalSeized < depositToken_.balanceOf(account_)`, require `balanceOf(account_) - _totalSeized >= minCollateralOnDirtyLiquidation` (or equivalently force the seize to the full balance when the remainder would be dust). Ensure `debtFloorInUsd` is configured > 0 as a partial mitigation, and add an explicit bad-debt handling path for positions whose collateral is fully seized while debt remains.

### Proof of Concept
Hardhat fork test, mirroring the existing suite:

```ts
// Position: alice deposits MET, mints msETH. Drop MET price so debt > collateral.
await masterOracle.updatePrice(met.address, toUSD('0.50')); // position underwater

const debt = await msEthDebtToken.balanceOf(alice.address);
const collateral = await msdMET.balanceOf(alice.address);

// Attacker picks repay so that total seized = collateral - 1 wei (dust).
// Use quoteLiquidateIn to solve for amountToRepay given totalToSeize = collateral - 1.
const { _amountToRepay } = await pool.quoteLiquidateIn(msEth.address, collateral.sub(1), msdMET.address);
// Ensure within maxLiquidable bound; if maxLiquidable < 100%, iterate dust slightly higher.

await pool.connect(liquidator).liquidate(msEth.address, alice.address, _amountToRepay, msdMET.address);

// Invariant broken: solvency. Victim still owes debt but has only 1 wei collateral.
expect(await msdMET.balanceOf(alice.address)).eq(1);
expect(await msEthDebtToken.balanceOf(alice.address)).gt(0);
const { _isHealthy } = await pool.debtPositionOf(alice.address);
expect(_isHealthy).false; // stuck forever — no incentive to seize 1 wei
```

The existing test "should liquidate by repaying max possible amount" (test/Pool.test.ts:791) already demonstrates the code path leaves a remainder balance with residual debt and `_isHealthy == false`; the PoC merely parameterizes the remainder down to 1 wei to show no floor exists.
