### Title
Unbounded Attacker-Controlled Array Allocation in TVM Precompile Signature Decoding Leads to Node Memory-Exhaustion DoS - ([File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java])

### Summary
The ImageMagick SIXEL decoder bug (CVE-2026-25970) is a signed-integer-overflow-driven buffer size computation on attacker-supplied image data that is used to allocate/resize a buffer without adequate bounds checking, corrupting memory. The closest reachable analog in java-tron is in the `PrecompiledContracts` helper routines used to decode signature/byte arrays from precompiled-contract call data (`extractSigArray`, `extractBytesArray`, `extractBytes32Array`), where an attacker-controlled 32-byte word taken directly from calldata is used as an array length with no upper-bound validation before allocation.

### Finding Description
`extractSigArray`, `extractBytesArray`, and `extractBytes32Array` in `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java` read a length value directly out of the raw ABI-encoded calldata (`words[offset].intValueSafe()`) and immediately use it to size a Java array: [1](#0-0) [2](#0-1) 

There is no upper bound check against a sane maximum (e.g. against remaining `data.length` or a fixed cap) before `new byte[len][]` is allocated — the only guard is `offset > words.length - 1`, which does not constrain `len` itself. `intValueSafe()` can return a value up to `Integer.MAX_VALUE` from a crafted 256-bit calldata word, so `len` can be attacker-chosen up to that bound. This mirrors the SIXEL bug's root cause class (CWE-190/unchecked size used for allocation from untrusted input), even though the concrete failure mode in Java is an `OutOfMemoryError`/excessive-allocation DoS rather than native memory corruption, since Java's managed heap prevents raw pointer corruption.

This code path backs the TVM precompiled contracts used for batch signature verification (`validatemultisign`/`batchvalidatesign`, as referenced by `SIG_LENGTH`, `ValidateMultiSignContractTest.java`, `BatchValidateSignContractTest.java`), which are invoked whenever any smart contract performs a `STATICCALL`/`CALL` to the corresponding precompile address — i.e., reachable from any unprivileged, unauthenticated transaction that triggers such a contract call.

### Impact Explanation
A single crafted transaction that calls the affected precompile with a maliciously large length word can force the node to attempt allocating an enormous `byte[][]` (up to `Integer.MAX_VALUE` elements/backing arrays) inside a single VM opcode execution, before any TVM energy/memory-expansion metering catches it (the precompile's own `getEnergyForData` energy accounting is independent of, and does not bound, this internal array-length parsing). This can throw `OutOfMemoryError`, which in the JVM is an unchecked `Error` (not a `RuntimeException`) and may not be caught by the VM's `catch (RuntimeException e)` handling in `VM.java`'s opcode loop, risking an uncaught error propagating up through block/transaction processing and crashing or hanging the node — a node availability/DoS impact, consistent with the "memory corruption / A:L" CWE-190 impact class in the reported advisory.

### Likelihood Explanation
Likelihood is high for triggering the excessive allocation attempt: any account can deploy a trivial contract that calls the precompile address with crafted calldata, and the vulnerable length parsing happens unconditionally as part of decoding the call data, prior to and independent of business-logic validation of signature/array contents. No special privileges, staking, or specific network conditions are required — only a normal contract call from any address.

### Recommendation
Add explicit bounds validation immediately after each `intValueSafe()` length extraction in `extractSigArray`, `extractBytesArray`, and `extractBytes32Array`, rejecting (returning failure, not throwing) if `len` exceeds a small sane cap or exceeds what the remaining `data.length` could actually encode (e.g., `len * WORD_SIZE` must not exceed the available calldata length). This mirrors the `isValidAbiEncoding` bound check already present elsewhere in the same file and should be applied consistently before any array allocation sized from untrusted calldata.

### Proof of Concept
1. Deploy a minimal contract that performs a raw `staticcall`/`call` to the batch-signature-verification precompile address used by `extractSigArray`/`extractBytesArray` (the address wired to `BatchValidateSign`/`ValidateMultiSign` in `PrecompiledContracts`).
2. Craft the calldata so that the 32-byte word at the expected "array length" offset encodes a very large integer (e.g., `0x7FFFFFFF`), while other structural fields are minimally valid enough to pass the initial `offset > words.length - 1` check.
3. Submit the transaction; `extractSigArray`/`extractBytesArray` executes `new byte[len][]` with the attacker-supplied `len`, forcing the JVM to attempt a massive allocation, producing sustained memory pressure or `OutOfMemoryError` on the executing node.

Note: I was not able to view the exact precompile `execute()` method body that calls `extractSigArray`/`extractBytesArray` (line ranges beyond what was retrieved) to confirm the precise calldata layout constraints imposed earlier in that method; this may add partial mitigating checks I could not fully verify from the available index. A Devin session with full file access would be needed to confirm the exact byte offsets required for a working end-to-end PoC transaction.

  private static byte[][] extractBytes32Array(DataWord[] words, int offset) {
    int len = words[offset].intValueSafe();
    byte[][] bytes32Array = new byte[len][];
    for (int i = 0; i < len; i++) {
      bytes32Array[i] = words[offset + i + 1].getData();
    }
    return bytes32Array;
  }

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
