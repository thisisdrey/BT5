### Title
Attacker can permanently block a victim from onboarding new collateral by filling their `depositTokensOfAccount` set to `MAX_TOKENS_PER_USER` with dust transfers - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
The Boundary bug class — an unprivileged actor withholds/abuses a shared handshake slot to block legitimate connections — maps onto Metronome's per-account token-list bookkeeping. Every `DepositToken` receipt (deposit, transfer, `seize`) registers the token in `Pool.depositTokensOfAccount[account]`, a `MappedEnumerableSet` capped at `MAX_TOKENS_PER_USER = 30` [1](#0-0) . An attacker can dust-transfer 30 distinct deposit tokens to a victim; once the set is full, `addToDepositTokensOfAccount` reverts with `UserReachedMaxTokens` [2](#0-1) , causing every subsequent receipt of a *new* deposit token for that victim to revert — deposits `onBehalfOf`, transfers, leveraged deposits via `SmartFarmingManager`, and liquidation `seize` calls where the seized token is new to the recipient.

### Finding Description
- `DepositToken._mint` and `DepositToken._transfer` call `pool.addToDepositTokensOfAccount(account_)` whenever the recipient's prior balance is zero [3](#0-2) .
- `DepositToken.transfer` only requires the sender's `unlockedBalanceOf >= amount_` [4](#0-3) . An attacker with no open debt has a fully unlocked balance, so they can dust-transfer 1 wei of each of the pool's deposit tokens to the victim.
- `Pool.addToDepositTokensOfAccount` adds to `depositTokensOfAccount` and reverts once the set reaches 30 entries [1](#0-0) .
- Thereafter, any path that would give the victim a *new* deposit token reverts: `deposit(amount, victim)` on an unused collateral, `transfer(victim, ...)` of a new token, and `DebtToken`/`SmartFarmingManager` flows that mint deposit tokens to the victim.

### Impact Explanation
Liveness break, analogous to blocking worker enrollment: legitimate "connections" (new collateral positions) for the victim are refused. Concretely, a victim whose position is drifting toward the liquidation threshold cannot deposit a *new* collateral type to restore health — `deposit` reverts in `_mint` → `addToDepositTokensOfAccount` — so the position becomes liquidatable and the attacker (or a third party) can seize it via `Pool.liquidate` [5](#0-4) . This is temporary freezing of funds rather than permanent loss, since the victim can still `withdraw` existing collateral (burning removes entries from the set), but during the freeze window they cannot top up with new collateral and may be liquidated.

### Likelihood Explanation
Cost is bounded: the attacker must hold dust of each distinct deposit token (a deposit of 1 wei of underlying per collateral) and make ≤30 transfers. No privileged role, oracle manipulation, or governance action is needed — only public `transfer`/`deposit` entry points, possibly batched via `Operator.execute`. The cap is a fixed protocol constant, not a config choice.

### Recommendation
Either remove the cap and pay the iteration gas on `debtPositionOf`, or — better — make the per-account sets opt-in only for tokens minted via `deposit`/`issue` on behalf of the actual user, and tolerate cap-overflow in `_transfer`/`seize` paths (e.g., credit balance without registering, or skip revert). At minimum, revert-free handling should apply to `seize` so liquidations are not blockable by recipient-set exhaustion.

```solidity
// Foundry fork test sketch
// Setup: fork a chain with a deployed Pool having >= 30 active DepositTokens
for (uint i; i < 30; ++i) {
    IDepositToken dt = pool.depositTokens(i);
    IERC20(dt.underlying()).approve(address(dt), 1);
    dt.deposit(1, attacker);              // mint dust to attacker
    dt.transfer(victim, 1);               // registers dt in victim's set
}
assertEq(pool.getDepositTokensOfAccount(victim).length, 30);

// Victim can no longer deposit a NEW collateral type (the 31st token):
IDepositToken newDt = pool.depositTokens(30); // newly added or unused by victim
underlying.approve(address(newDt), amount);
vm.expectRevert(Pool.UserReachedMaxTokens.selector);
newDt.deposit(amount, victim);          // reverts: cannot onboard collateral

// Nor receive it via transfer:
vm.expectRevert(Pool.UserReachedMaxTokens.selector);
newDt.transfer(victim, 1);

// Liquidation that must seize a token new to the liquidator's set can also be
// forced to revert if the liquidator's own set was pre-filled.
```
