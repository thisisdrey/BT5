### Title
Stale account-scoped state (`ReceivedData`, `PostponedReceipt`/`PostponedReceiptId`/`PendingDataCount`, `PromiseYieldReceipt`/`PromiseYieldStatus`, `YieldIdToDataId`/`DataIdToYieldId`) survives `remove_account` and is inherited by a later `CreateAccount` of the same name - (File: core/store/src/utils/mod.rs)

### Summary
`remove_account` in `core/store/src/utils/mod.rs` only deletes `TrieKey::Account`, `TrieKey::ContractCode`, `TrieKey::AccessKey`/`GasKeyNonce`, and `TrieKey::ContractData`. Eight of the twelve account-scoped columns listed in `col::COLUMNS_WITH_ACCOUNT_ID_IN_KEY` (`core/primitives/src/trie_key.rs:89-102`) - `ReceivedData`, `PostponedReceiptId`, `PendingDataCount`, `PostponedReceipt`, `PromiseYieldReceipt`, `PromiseYieldStatus`, `YieldIdToDataId`, `DataIdToYieldId` - are never removed, and all of them are writable by ordinary, unprivileged contract execution (cross-contract calls, `promise_yield_create`/`promise_yield_resume`, and receipts with unresolved input dependencies).

### Finding Description
`remove_account` (core/store/src/utils/mod.rs:505-575) performs exactly five classes of removal: [1](#0-0) [2](#0-1) [3](#0-2) 

but `col::COLUMNS_WITH_ACCOUNT_ID_IN_KEY` enumerates twelve account-scoped columns: [4](#0-3) 

The eight columns with no corresponding removal are written by the runtime's own promise/data machinery, all reachable from ordinary `FunctionCall` actions with no privileged capability required:
- `ReceivedData`/`PostponedReceipt`/`PostponedReceiptId`/`PendingDataCount`: written whenever a receipt has cross-contract callback dependencies that are not all resolved yet (`set_received_data`, `set_postponed_receipt`, `core/store/src/utils/mod.rs:76-143`), which is the normal mechanism behind any two-or-more `promise_then`/`promise_and` chain.
- `PromiseYieldReceipt`/`PromiseYieldStatus`/`YieldIdToDataId`/`DataIdToYieldId`: written by the `promise_yield_create` host function path (`set_promise_yield_receipt`, `set_promise_yield_status`, `set_yield_id_mapping`, `core/store/src/utils/mod.rs:200-297`), directly callable from contract wasm.

An attacker fully controls the sequence: deploy a contract on account `A`, issue a multi-dependency promise chain or a `promise_yield_create` call so these keys are populated for `A`, then submit `DeleteAccount` for `A` (removing only the five key classes above), then `CreateAccount` to recreate `A` (or have the freed name claimed by another account under the attacker's control, e.g. a sub-account). The stale entries remain addressable under the same trie-key namespace (`receiver_id = A`) because none of the removal loops in `remove_account` touch these prefixes.

I was not able to fully trace, within this session, the downstream receipt-resolution code path (`apply_action_receipt` handling of delayed `ReceivedData` arrival, and `promise_yield_resume`'s authorization scoping) to confirm end-to-end whether this stale state can be triggered to execute an action (e.g., transferring balance or corrupting state) against the *new* incarnation of the account without further protocol-level checks. That trace is required to convert this from a confirmed "cleanup asymmetry" into a fully proven fund-loss/authorization-escalation exploit.

### Impact Explanation
Confirmed: state-cleanup asymmetry that leaves attacker-writable, account-namespaced trie entries (`ReceivedData`, postponed-receipt bookkeeping, promise-yield bookkeeping) alive across `DeleteAccount`, inherited by whoever next owns that account name. This falls under NEAR's storage/state-integrity category. Whether it escalates to "authorization escalation across accounts or promises" (per the bounty categories referenced in the question) requires confirming that a later-arriving `ReceivedData` or a `promise_yield_resume` call against the stale keys causes the stored `PostponedReceipt`/`PromiseYieldReceipt` to execute against the new account's live state - this last link is not fully verified here.

### Likelihood Explanation
Low cost, fully attacker-controlled preconditions (self-funded account, own contract deploying multi-dependency promises or yield/resume calls, then self-initiated `DeleteAccount`/`CreateAccount`). Repeatable at will. The unresolved factor is whether the same account name can practically be reclaimed by a different, unrelated party (relevant to a true cross-victim escalation) versus only re-owned by the original attacker (which would make the impact self-inflicted and largely inert).

### Recommendation
Extend `remove_account` to also purge the remaining account-scoped columns before returning: iterate and remove `ReceivedData`, `PostponedReceiptId`, `PendingDataCount`, `PostponedReceipt`, `PromiseYieldReceipt`, `PromiseYieldStatus`, `YieldIdToDataId`, and `DataIdToYieldId` prefixed by the account, mirroring the existing access-key/gas-key and contract-data removal loops. Alternatively/additionally, add a debug-assertion or protocol-level pre-condition disallowing `DeleteAccount` while pending postponed receipts / yield promises exist for that account.

### Proof of Concept
As specified in the question: a Rust unit test in `core/store/src/utils/mod.rs` (or a new test module) that:
1. Iterates `col::COLUMNS_WITH_ACCOUNT_ID_IN_KEY`.
2. For each variant, constructs one `TrieKey` instance scoped to account `A` and writes a dummy value via `TrieUpdate::set`/`set(...)`.
3. Calls `remove_account(&mut state_update, &A)`.
4. Asserts `state_update.get(key) == None` for every variant.

Expected result: the assertion fails for `ReceivedData`, `PostponedReceiptId`, `PendingDataCount`, `PostponedReceipt`, `PromiseYieldReceipt`, `PromiseYieldStatus`, `YieldIdToDataId`, and `DataIdToYieldId`, confirming the cleanup gap. Further runtime-level integration testing (deploy contract, issue multi-dependency promise/yield, delete+recreate account, deliver delayed data) would be needed to confirm the downstream execution consequence.
