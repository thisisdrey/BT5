Audit Report

## Title
Lottery winner selection uses stale, publicly-predictable randomness without checking `known_since`, letting an unprivileged attacker guarantee a win - (File: substrate/frame/lottery/src/lib.rs)

## Summary
`pallet_lottery`'s `generate_random_number` calls `T::Randomness::random(...)` and discards the returned `known_since` block number, violating the explicit contract documented on the `Randomness` trait that callers must verify the seed became known only after the relevant commitment window closed. Because `start_lottery` enforces no minimum `delay` relative to the `RandomnessCollectiveFlip` determinism window (81 blocks), a manager-configured short `delay` makes the payout seed fully computable by any observer before ticket sales even close, letting an unprivileged attacker time a `buy_ticket` call to land on the precomputed winning index and steal the pot.

## Finding Description
The `Randomness` trait's documentation states the returned seed "should only be used to distinguish commitments made before the returned block number" and requires callers to check that the block number returned (`known_since`) is later than the last possible commitment block, re-polling later if not. [1](#0-0) 

`pallet_lottery::generate_random_number` calls `T::Randomness::random(&(T::PalletId::get(), seed).encode())` and immediately decodes only the seed, discarding the second tuple element entirely — there is no check comparable to the one required by the trait contract: [2](#0-1) 

By contrast, `polkadot/runtime/common/src/auctions/mod.rs` correctly implements the required check, only accepting the randomness if `late_end <= known_since`, i.e., only if the seed became known strictly after the relevant auction commitments closed, otherwise it defers to a later block. `pallet_lottery` has no equivalent logic in either `on_initialize` or `choose_ticket`/`generate_random_number`.

The default runtime wires `pallet_lottery::Config::Randomness = RandomnessCollectiveFlip`, confirmed in `substrate/bin/node/runtime/src/lib.rs`. That pallet's `random` implementation derives the seed from the previous 81 blocks' hashes and returns `known_since = block_number.saturating_sub(RANDOM_MATERIAL_LEN)` (81), as read directly from `substrate/frame/insecure-randomness-collective-flip/src/lib.rs` lines 138-158.

`start_lottery` accepts an arbitrary `delay: BlockNumberFor<T>` from `ManagerOrigin` with no validation against `RANDOM_MATERIAL_LEN` or any other minimum bound: [3](#0-2) 

The payout is triggered in `on_initialize` once `payout_block = start + length + delay <= n`, at which point `choose_account` → `choose_ticket` → `generate_random_number` executes and pays out immediately without ever checking whether `known_since >= start + length` (the last block at which a ticket could be bought, per `do_buy_ticket`'s check `block_number < config.start + config.length`): [4](#0-3) [5](#0-4) 

When `delay < 81`, `known_since` for the payout draw is earlier than `start + length`, meaning the entropy material was already fully public before ticket sales closed. Since the seed derivation only depends on public block hashes and the fixed `(PalletId, seed)` subject — both computable by any observer — an attacker can precompute the exact winning ticket index in advance and time their own `buy_ticket` call so `Tickets::<T>::insert(ticket_count, caller)` lands on that index, guaranteeing the win when `choose_account` resolves `Tickets::get(winning_index)`: [6](#0-5) [7](#0-6) 

The pallet's own code even flags this gap with a TODO comment referencing the freshness issue, confirming the missing check was a known, unaddressed limitation rather than an intentional design.

## Impact Explanation
This is a theft/unbacked-payout scenario matching the "treasury or reward payouts ... must settle exactly once to the rightful beneficiary" impact category: the lottery pot, funded by all ticket buyers, is stolen by a single unprivileged attacker who can deterministically steer the "random" payout to their own account by exploiting predictable, stale randomness — no privileged actor, validator, or governance action is involved, only ordinary signed `buy_ticket` extrinsics timed against publicly observable chain state.

## Likelihood Explanation
Exploitability is entirely conditional on the `delay` value chosen by `ManagerOrigin` relative to `RANDOM_MATERIAL_LEN` (81 blocks) — `start_lottery` performs no validation forcing `delay >= 81`, so this is a config-triggerable, not merely hypothetical, gap. Any lottery instance configured with a short `delay` (as several sample configurations reasonably would use) is directly exploitable via public extrinsics, requiring no special access, and is repeatable across lottery rounds.

## Recommendation
Mirror the pattern in `polkadot/runtime/common/src/auctions/mod.rs`: after calling `T::Randomness::random`, verify `known_since` is later than `config.start.saturating_add(config.length)` (the last block ticket purchases could occur). If the check fails, defer the draw (skip payout this block and re-poll on a subsequent `on_initialize` call) rather than paying out immediately. Additionally, consider enforcing a minimum `delay` in `start_lottery` tied to the configured randomness source's determinism window as a defense-in-depth measure.

## Proof of Concept
1. `ManagerOrigin` calls `start_lottery(price, length=20, delay=5, repeat=false)` at block `N` (`start = N`).
2. Ticket sales close at block `N+20`; payout triggers in `on_initialize` at block `N+25`.
3. `RandomnessCollectiveFlip::random` at block `N+25` returns `known_since = N+25-81 = N-56`, before ticket sales even opened.
4. Any observer computes `generate_random_number` off-chain during the sale window (all inputs — `PalletId`, seed, and the fixed 81-block hash window — are already public and fixed), deriving `winning_index = random_number % expected_total`.
5. Attacker waits until `TicketsCount::<T>::get() == winning_index`, then calls `buy_ticket`, causing `Tickets::<T>::insert(winning_index, attacker)`.
6. At payout, `choose_account()` resolves `Tickets::get(winning_index) = attacker`, and the full pot transfers to the attacker via `T::Currency::transfer(..., winner, lottery_balance, KeepAlive)`.
