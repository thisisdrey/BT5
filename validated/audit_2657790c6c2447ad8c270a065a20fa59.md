### Title
Griefing via `depositTokensOfAccount` cap fills victim's account list and blocks all future deposits/transfers — (File: contracts/Pool.sol, contracts/DepositToken.sol)

### Summary
`DepositToken._mint` and `DepositToken._transfer` unconditionally call `pool.addToDepositTokensOfAccount(account)` whenever the recipient's balance was previously zero. `Pool` enforces a `MAX_TOKENS_PER_USER` bound on that list and reverts with `TooManyDepositTokens` once it is reached. Because both `deposit()` (`onBehalfOf_` is attacker-chosen) and `transfer()` are public and unrestricted by lock/health checks, an unprivileged attacker can push dust amounts of each whitelisted deposit token into a victim's account list until the cap is hit. After that, every operation that would add a *new* deposit token to the victim's list reverts, denying the victim the ability to add collateral — analog to the InnoDB crash/hang class (availability loss).

### Finding Description
- `DepositToken._transfer` adds the token to the recipient's account list whenever the recipient's prior balance is zero (`contracts/DepositToken.sol:517-520`), and `deposit(amount_, onBehalfOf_)` lets any EOA mint a dust position directly into a victim (`contracts/DepositToken.sol:211-237`).
- `Pool.addToDepositTokensOfAccount` reverts once `depositTokensOfAccount(account).length()` reaches `MAX_TOKENS_PER_USER` (`contracts/Pool.sol`).
- Once the victim's list is full: any `deposit` of a collateral type the victim doesn't already hold, any inbound `transfer`/`transferFrom` of a new deposit token, and `seize` to a beneficiary at cap all revert. The attacker only needs dust (1 wei) per token; the victim cannot remove entries without first zeroing balances (burning/transferring each dust token back out — possible but costly, and re-griefable in the same block via front-running since transfers are permissionless).

### Impact Explanation
The victim is permanently unable to deposit a new collateral type or receive deposit tokens while griefed (temporary freezing of protocol functionality/funds). More critically, if the victim holds a debt position that drifts toward the liquidation threshold, they cannot add additional collateral to restore their health factor — guaranteeing liquidation and loss of collateral, a direct availability-to-loss path identical in spirit to the InnoDB DoS.

### Likelihood Explanation
- Fully unprivileged: `deposit()` and `transfer()` have no access control; `onlyIfDepositTokenExists` merely requires the token be registered.
- Feasibility depends on `MAX_TOKENS_PER_USER` versus the number of listed deposit tokens in the pool. If the cap exceeds the count of whitelisted collaterals, the attacker alone cannot fill it — this is the main uncertainty, as `Pool.sol`'s exact constant could not be fully verified in this pass. The attack also becomes easier if `debtTokensOfAccount` shares the same cap accounting (deposit tokens from multiple pools do not share lists — the list is per-pool).

### Recommendation
- Decouple the revert path: make `addToDepositTokensOfAccount` a non-reverting "best effort" (skip tracking when at cap) and let `debtPositionOf` account for untracked tokens, or
- Revert only inside `deposit` (self-consistent positions) while allowing `transfer`/`seize` to proceed, or
- Require `amount_ >= minMeaningfulAmount` to register a token in the account list.
