### Title
Attacker can permanently block a victim from receiving new deposit/debt tokens by force-filling `depositTokensOfAccount`/`debtTokensOfAccount` to `MAX_TOKENS_PER_USER` via dust deposits and `onBehalfOf` mints - (File: contracts/Pool.sol)

### Summary
`Pool.addToDepositTokensOfAccount` and `Pool.addToDebtTokensOfAccount` revert with `UserReachedMaxTokens` once a user's combined per-account token list reaches `MAX_TOKENS_PER_USER = 30`. The list is populated as a side effect of `DepositToken._mint`/`_transfer` and `DebtToken._issue`, and `DepositToken.deposit(amount_, onBehalfOf_)` lets any unprivileged caller mint dust `msdTOKEN` to an arbitrary victim. An attacker can therefore push a victim's list to the cap, after which every operation that would add a new token to the victim's list — `deposit` on their behalf, `transfer`/`transferFrom`/`seize` of a new `msdTOKEN` to them, and any new debt-token issuance on their position — reverts.

### Finding Description
- `Pool.onlyIfAdditionWillNotReachMaxTokens` enforces `debtTokensOfAccount.length(account) + depositTokensOfAccount.length(account) >= 30` → `UserReachedMaxTokens` [1](#0-0) 
- `DepositToken._mint` calls `pool.addToDepositTokensOfAccount(account_)` whenever `account_` receives its first balance [2](#0-1) 
- `DepositToken.deposit` accepts a user-chosen `onBehalfOf_` and is callable by anyone [3](#0-2) 
- `_transfer` (reachable via public `transfer`, `transferFrom`, and `seize`) adds the recipient's entry the same way [4](#0-3) 

Attack path: for each registered deposit token `d_i`, attacker calls `d_i.deposit(dust, victim)` (or `transfer(victim, dust)`). Each call appends `d_i` to `depositTokensOfAccount[victim]`. Since deposit tokens and debt tokens share the same 30-slot budget, the attacker only needs `30 − currentCount` distinct registered deposit tokens, or can combine with `Pool.mint`/leverage paths that issue new debt tokens to the victim.

### Impact Explanation
Once the cap is hit, the victim can no longer: receive any `msdTOKEN` they don't already hold (transfers, `deposit(..., victim)`, and even liquidation `seize` payouts of a new token to the victim revert), and cannot issue a new synthetic debt token type. This is a liveness/availability break of the victim's position-management surface — the same availability-impact class as the CVE (hang/crash DoS). Existing balances remain withdrawable, so funds are not permanently lost, but the victim's account is frozen out of all new collateral/debt types until they fully exit a token to free a slot (and the attacker can re-grief cheaply by dusting the freed slot again).

### Likelihood Explanation
Requires no privileges: only public `deposit`/`transfer` calls and dust amounts of each underlying. The main caveat is feasibility depends on the number of registered deposit+debt token types per pool; `addDepositToken`/`addDebtToken` are governor-gated, so on a pool with few collateral types the attacker may only partially fill the list. On pools with many registered tokens (the code anticipates up to `MAX_DEPOSIT_TOKENS`), the attack is fully reachable at gas + dust cost. Verified behavior is confirmed by the revert-on-cap tests in `test/Pool.test.ts` [5](#0-4) 

### Recommendation
Make `deposit(amount_, onBehalfOf_)` opt-in (e.g., require `onBehalfOf_ == _msgSender()` or a recipient whitelist/allowance), or move the max-tokens check so that excess receipts are permitted but only counted positions with meaningful balance are tracked. Alternatively, allow any account to permissionlessly remove tokens it holds no balance of, and skip adding tokens for sub-dust `onBehalfOf` deposits.

### Proof of Concept
Hardhat sketch:

```ts
// victim already holds k tokens; attacker dusts the rest
for (const dt of depositTokens) {
  await underlying.connect(attacker).mint(attacker.address, 1)
  await underlying.connect(attacker).approve(dt.address, 1)
  await dt.connect(attacker).deposit(1, victim.address) // adds dt to victim's list
}
// victim's combined list is now 30
await expect(
  someOtherDepositToken.connect(alice).transfer(victim.address, 1)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens')
await expect(
  someOtherDepositToken.connect(alice).deposit(100, victim.address)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens')
```
