### Title
Non-Allowlisted Delegator Can Bypass Allowlist by Calling `unlock()` - (File: `aptos-move/framework/aptos-framework/sources/delegation_pool.move`)

---

### Summary

The `delegation_pool` module supports an optional delegator allowlisting feature. When enabled by a pool owner, only allowlisted addresses should be able to interact with the pool. The `add_stake` and `reactivate_stake` entry functions both enforce this via `assert_delegator_allowlisted`, but the `unlock` entry function does not, allowing any non-allowlisted delegator to move their active stake to `pending_inactive` without restriction.

---

### Finding Description

The `DelegationPoolAllowlisting` feature is designed so that a pool owner can restrict which delegators may interact with their delegation pool. Three delegator-facing entry functions exist for managing stake:

- `add_stake` — enforces the allowlist check at line 1489
- `reactivate_stake` — enforces the allowlist check at line 1584
- `unlock` — **no allowlist check present**

`add_stake` acquires `DelegationPoolAllowlisting` and calls `assert_delegator_allowlisted` before proceeding: [1](#0-0) 

`reactivate_stake` does the same: [2](#0-1) 

But `unlock` acquires no `DelegationPoolAllowlisting` resource and performs no allowlist check before calling `unlock_internal`: [3](#0-2) 

---

### Impact Explanation

When a pool owner enables allowlisting and removes a delegator (or never adds them), the intended invariant is that the delegator cannot interact with the pool. The pool owner uses `evict_delegator` to force-unlock a non-allowlisted delegator's active stake on their own schedule. However, a non-allowlisted delegator can call `unlock()` directly at any time, bypassing the pool owner's access control. This breaks the stated invariant of the allowlisting feature: that only allowlisted addresses may interact with the pool. The delegator can self-initiate the movement of their active stake to `pending_inactive`, circumventing the pool owner's control over the timing and execution of eviction.

---

### Likelihood Explanation

Any delegator who has active stake in a pool with allowlisting enabled but is not (or is no longer) on the allowlist can trigger this. It requires no special privileges — just a standard signed transaction calling the public entry function `unlock`. The scenario is directly reachable on mainnet.

---

### Recommendation

Add `assert_delegator_allowlisted(pool_address, delegator_address)` to the `unlock` entry function, and add `DelegationPoolAllowlisting` to its `acquires` clause, consistent with `add_stake` and `reactivate_stake`:

```move
public entry fun unlock(
    delegator: &signer,
    pool_address: address,
    amount: u64
) acquires DelegationPool, GovernanceRecords, BeneficiaryForOperator, NextCommissionPercentage, DelegationPoolAllowlisting {
    if (amount == 0) { return };

    let delegator_address = signer::address_of(delegator);
    assert_delegator_allowlisted(pool_address, delegator_address);

    synchronize_delegation_pool(pool_address);
    unlock_internal(delegator_address, pool_address, amount);
}
```

---

### Proof of Concept

1. Pool owner deploys a delegation pool and enables allowlisting via `enable_delegators_allowlisting`.
2. Delegator A is allowlisted, calls `add_stake` to deposit 100 APT.
3. Pool owner removes Delegator A from the allowlist via `remove_delegator_from_allowlist`.
4. Delegator A is now non-allowlisted. Calling `add_stake` or `reactivate_stake` aborts with `EDELEGATOR_NOT_ALLOWLISTED`.
5. Delegator A calls `unlock(delegator_a, pool_address, 100_APT)` — this succeeds without error, moving their active stake to `pending_inactive`, bypassing the pool owner's intended access control and preempting the `evict_delegator` mechanism.

The existing test `test_cannot_reactivate_stake_if_not_allowlisted` at line 4841 demonstrates the allowlist is enforced on `reactivate_stake` but does not test `unlock` for the same condition, confirming the gap. [4](#0-3)

        enable_delegation_pool_allowlisting_feature(aptos_framework);

        let validator_address = signer::address_of(validator);
        let pool_address = get_owned_pool_address(validator_address);

        let delegator_1_address = signer::address_of(delegator_1);
        account::create_account_for_test(delegator_1_address);

        // allowlist is created but has no address added
        enable_delegators_allowlisting(validator);
        // allowlist delegator
        allowlist_delegator(validator, delegator_1_address);
        assert!(delegator_allowlisted(pool_address, delegator_1_address), 0);

        // delegator is allowed to add stake
        stake::mint(delegator_1, 50 * ONE_APT);
        add_stake(delegator_1, pool_address, 50 * ONE_APT);

        // restore `add_stake` fee back to delegator
        end_aptos_epoch();
        assert_delegation(delegator_1_address, pool_address, 50 * ONE_APT, 0, 0);

        // some of the stake is unlocked by the delegator
        unlock(delegator_1, pool_address, 30 * ONE_APT);
        assert_delegation(delegator_1_address, pool_address, 20 * ONE_APT, 0, 2999999999);

        // remove delegator from allowlist
        remove_delegator_from_allowlist(validator, delegator_1_address);
        assert!(!delegator_allowlisted(pool_address, delegator_1_address), 0);

        // remaining stake is unlocked by the pool owner by evicting the delegator
        evict_delegator(validator, delegator_1_address);
        assert_delegation(delegator_1_address, pool_address, 0, 0, 4999999999);

        // delegator cannot reactivate stake
        reactivate_stake(delegator_1, pool_address, 50 * ONE_APT);
        assert_delegation(delegator_1_address, pool_address, 0, 0, 4999999999);
    }
