### Title
Permissionless dust deposits/transfers fill a victim's `depositTokensOfAccount` set to `MAX_TOKENS_PER_USER`, blocking them from depositing or receiving any new collateral type - (File: contracts/DepositToken.sol)

### Summary
Metronome tracks, per account, the set of deposit/debt tokens they have ever interacted with (`depositTokensOfAccount` + `debtTokensOfAccount`), capped at `Pool.MAX_TOKENS_PER_USER`. Any unprivileged user can force entries into a victim's set: `DepositToken.deposit` accepts an arbitrary `onBehalfOf_` and `_mint` pushes the token into the recipient's set, and plain `transfer`/`transferFrom`/`seize` do the same via `_transfer`. Once the combined set reaches the cap, every subsequent `addToDepositTokensOfAccount` reverts with `UserReachedMaxTokens`, which bricks the victim's ability to deposit a collateral type they do not already hold, and can also revert liquidation `seize` flows directed at them.

### Finding Description
- `DepositToken.deposit(uint256 amount_, address onBehalfOf_)` is fully permissionless and only rejects `onBehalfOf_ == address(0)`; it mints `msdTOKEN` to `onBehalfOf_` via `_mint`. [1](#0-0) 
- `_mint` calls `pool.addToDepositTokensOfAccount(account_)` whenever the recipient's prior balance was zero and `amount_ > 0` — there is no minimum amount and no consent check. [2](#0-1) 
- `_transfer` does the same for recipients (first-time receipt) and removes the entry for senders whose balance hits zero. [3](#0-2) 
- `Pool.addToDepositTokensOfAccount` / `addToDebtTokensOfAccount` revert with `UserReachedMaxTokens` when `depositTokens + debtTokens` for the account reach `MAX_TOKENS_PER_USER` (confirmed by `test/Pool.test.ts` "should revert when reach max tokens", which fills half the cap with deposit tokens and half with debt tokens). [4](#0-3) 
- An attacker deposits 1 wei of collateral of each listed `DepositToken` with `onBehalfOf_ = victim` (or transfers 1 wei of each msdTOKEN). The victim's set fills to `MAX_TOKENS_PER_USER`. Any later `deposit` (or `seize` during liquidation) that would add a new token to the victim's set reverts inside `_mint`/`_transfer` because `addToDepositTokensOfAccount` reverts, reverting the whole transaction.
- No modifier stops this: `deposit` is `whenNotPaused nonReentrant onlyIfDepositTokenExists`, all callable by any EOA, and the set insertion has no opt-in or dust threshold.

### Impact Explanation
The victim is blocked from depositing into (and from receiving via liquidation seize) any collateral token not already in their account set. This is a temporary freeze of functionality/funds: positions cannot be topped up with a new collateral type even when the victim is approaching liquidation, which can indirectly cause avoidable liquidations. Severity is tempered because the victim can self-recover by transferring each dust balance out, which triggers `removeFromDepositTokensOfAccount` when the balance reaches zero — but on chains with many listed collateral tokens the attacker can repeat the attack cheaply and keep the victim pinned, and forced-liquidation windows may close before recovery.

### Likelihood Explanation
High reachability: requires only an EOA, dust amounts of each listed underlying, and public `deposit`/`transfer` calls — no governor, keeper, oracle manipulation, or flash loan needed. Cost scales linearly with the number of listed collateral tokens and the cap. Constraints: the attack only blocks *new* collateral types, does not affect debt tokens already held or existing deposits, and is reversible by the victim spending gas to clear the dust entries.

### Recommendation
Add a minimum-seed/dust threshold for adding a token to an account's set (or only register on user-initiated `deposit`, not on receipt), require recipient opt-in (e.g., only add on `deposit` by `onBehalfOf_ == _msgSender()` or via `permit`-style authorization), and/or let `addToDepositTokensOfAccount` fail-soft for unsolicited transfers. Alternatively allow anyone to call `removeFromDepositTokensOfAccount` for their own account regardless of token balance mechanics so cleanup is a single cheap call.

### Proof of Concept
Hardhat sketch (fork/fixed-deployment context):

```ts
// contracts under test: Pool.sol, DepositToken.sol
const depositTokens: DepositToken[] = await Promise.all(
  (await pool.getDepositTokens()).map(a => ethers.getContractAt('DepositToken', a))
);
// Ensure victim's combined token set is empty / partially filled, then:
const cap = (await pool.MAX_TOKENS_PER_USER()).toNumber();
for (const dt of depositTokens.slice(0, cap)) {
  const underlying = await ethers.getContractAt('ERC20', await dt.underlying());
  await underlying.connect(attacker).approve(dt.address, 1);
  await dt.connect(attacker).deposit(1, victim.address); // plants entry in victim's set
}
// victim's set is now full
const newDepositToken = /* any other listed deposit token not yet in victim's set */;
await expect(
  newDepositToken.connect(victim).deposit(amount, victim.address)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');
// Recovery path: victim must transfer dust out for each planted token
```

Note: exact `MAX_TOKENS_PER_USER` value and whether the cap counts deposit+debt tokens jointly were verified via `test/Pool.test.ts` rather than the full `Pool.addToDepositTokensOfAccount` body (the function body was not fully indexed); behavior is confirmed by the test's revert assertion.

    function deposit(
        uint256 amount_,
        address onBehalfOf_
    ) external override whenNotPaused nonReentrant onlyIfDepositTokenExists returns (uint256 _deposited, uint256 _fee) {
        if (amount_ == 0) revert AmountIsZero();
        if (onBehalfOf_ == address(0)) revert BeneficiaryIsNull();

        IPool _pool = pool;
        IERC20 _underlying = underlying;
        address _msgSender = _msgSender();
        address _treasury = address(_pool.treasury());

        if (_msgSender == _treasury) revert TreasuryCanNotDeposit();

        uint256 _balanceBefore = _underlying.balanceOf(_treasury);
        _underlying.safeTransferFrom(_msgSender, _treasury, amount_);
        amount_ = _underlying.balanceOf(_treasury) - _balanceBefore;

        (_deposited, _fee) = quoteDepositOut(amount_);
        if (_fee > 0) {
            _mint(_pool.feeCollector(), _fee);
        }

        _mint(onBehalfOf_, _deposited);

        emit CollateralDeposited(_msgSender, onBehalfOf_, amount_, _deposited, _fee);
    }
