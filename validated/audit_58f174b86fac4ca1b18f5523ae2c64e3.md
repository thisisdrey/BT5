### Title
Active permission holders can be granted authority to execute `AccountPermissionUpdateContract`, enabling irrevocable Owner-tier takeover of TRON accounts - (File: actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java)

### Summary
`AccountPermissionUpdateActuator.checkPermission()` validates the operations bitmap of an `Active` permission solely against `DynamicPropertiesStore.getAvailableContractType()`, which by default includes the bit for `AccountPermissionUpdateContract` itself. Nothing in the actuator, in `TransactionCapsule.checkPermission()`, or in `WalletUtil.checkPermissionOperations()` prevents an `Active`-tier permission from being authorized to call `AccountPermissionUpdateContract`. Once such a bit is set for an `Active` permission, any key holder of that lower-privileged permission tier can unilaterally rewrite the account's `Owner` permission (and `Witness`/other `Active` permissions), which is functionally equivalent to a namespace-scoped identity forging its way into cluster-root/privileged-namespace control, as in the referenced GHSA-pcqx-8qww-7f4v report.

### Finding Description
TRON's multi-sig permission model has three tiers: `Owner` (id 0, full control), `Witness` (id 1), and `Active` (id ≥2, scoped by an `operations` bitmap to specific contract types) — see the `Permission` message definition [1](#0-0) .

When an account owner (or anyone who already controls a sufficiently-weighted `Active` key) submits an `AccountPermissionUpdateContract`, `AccountPermissionUpdateActuator.validate()` calls `checkPermission()` on the `owner`, `witness`, and each `active` permission in the request. For `Active`-type permissions, the only content restriction on the `operations` bitmap is that every set bit must correspond to a contract type present in `dynamicStore.getAvailableContractType()`: [2](#0-1) 

Critically, the default `AvailableContractType` bitmap includes the bit for `AccountPermissionUpdateContract` itself (as confirmed by the test `checkAvailableContractType`, which only special-cases `UNRECOGNIZED` and `UpdateBrokerageContract`) [3](#0-2) . By contrast, the *default* `Active` permission's operations bitmap (`ActiveDefaultOperations`) deliberately excludes `AccountPermissionUpdateContract`, `ClearABIContract`, and `UpdateBrokerageContract`, as shown by the companion test `checkActiveDefaultOperationsCorrespondingToCode` [4](#0-3) . This asymmetry demonstrates the intent that `Active` permissions should not normally be capable of self-modifying the account's permission structure — but `checkPermission()` does not enforce this as an invariant; it only checks membership in the broader `AvailableContractType` set, so an explicit grant is silently accepted.

Once an `Active` permission's operations bitmap includes the `AccountPermissionUpdateContract` bit, any signer satisfying that `Active` permission's threshold can broadcast a new `AccountPermissionUpdateContract` for the account. Signature/permission enforcement at broadcast time only checks that the contract type bit is set for the referenced permission id — it performs no semantic check that the actor is restricted from altering `Owner`-level permissions: [5](#0-4) [6](#0-5) 

`AccountPermissionUpdateActuator.execute()` then unconditionally overwrites the account's `Owner`, `Witness`, and `Active` permissions with whatever is in the new contract, with no check that the caller's own permission tier (`Active`) is beneath the `Owner` tier it is modifying: [7](#0-6) 

Thus an `Active`-tier signer with this single contract-type bit set can replace the `Owner` permission's keys entirely with its own, permanently removing the true owner's control.

### Impact Explanation
This allows a lower-privileged, scoped `Active` permission holder to escalate to full `Owner`-tier control of the account — analogous to the referenced advisory where a namespace-scoped identity uses a permitted operation to obtain cluster-root-equivalent privilege. The impact is a concrete "unauthorized account operation" and "permanent freezing/loss of funds/control": once the malicious or compromised `Active` key executes `AccountPermissionUpdateContract`, it can replace `Owner` keys, permanently locking out the legitimate account owner and enabling arbitrary future transfers, staking, voting, or witness/committee actions performed as that account.

### Likelihood Explanation
Exploitation requires that the account owner has, at some point, configured an `Active` permission whose `operations` bitmap includes the bit for `AccountPermissionUpdateContract` (contract-type value 46) — either through explicit owner misconfiguration, a compromised or over-privileged delegated `Active` key, or third-party tooling that grants broad “all contract type” operations without excluding this sensitive bit. Because the actuator's validation logic imposes no special restriction preventing this grant (unlike the deliberate exclusion baked into the *default* operations bitmap), this is a silent gap rather than a deeply obscure exploit path, and any account using non-default/broadened `Active` permissions for automation or delegated signing is at risk.

### Recommendation
In `AccountPermissionUpdateActuator.checkPermission()`, explicitly forbid setting the `AccountPermissionUpdateContract` (and similarly self-referential/sensitive contract types) bit within any `Active` permission's `operations` bitmap, regardless of what `dynamicStore.getAvailableContractType()` allows — mirroring the exclusion already applied to `getActiveDefaultOperations()`. Alternatively, enforce a hard invariant in `execute()`/`validate()` that only a signer satisfying the current `Owner` permission's threshold may modify the `Owner` permission.

### Proof of Concept
1. Account `A` has default `Owner` permission (owner key `K_owner`) and configures a custom `Active` permission (id 2) with a broadened `operations` bitmap that includes bit 46 (`AccountPermissionUpdateContract`), authorized to key `K_active` with threshold 1 — this passes `checkPermission()` because bit 46 is set in `getAvailableContractType()` by default.
2. Holder of `K_active` crafts an `AccountPermissionUpdateContract` for account `A` setting `permission_id = 2` on the contract, with a new `Owner` permission containing only `K_active`'s own address, and unchanged/minimal `Active`/`Witness` permissions.
3. `K_active` signs the transaction; `TransactionCapsule.checkPermission()`/`checkWeight()` succeed since bit 46 is set and threshold is met.
4. `AccountPermissionUpdateActuator.execute()` overwrites `A`'s `Owner` permission with the attacker-controlled key, per `account.updatePermissions(...)`.
5. `K_owner` no longer satisfies any permission on account `A`; `K_active` now fully controls the account as sole Owner.

  public static boolean checkPermissionOperations(Permission permission, Contract contract)
      throws PermissionException {
    ByteString operations = permission.getOperations();
    if (operations.size() != 32) {
      throw new PermissionException(String.format("operations size must 32, actual: %d",
          operations.size()));
    }
    int contractType = contract.getTypeValue();
    boolean b = (operations.byteAt(contractType / 8) & (1 << (contractType % 8))) != 0;
    return b;
  }
