Audit Report

## Title
`add_tip` in `snowbridge-pallet-system-frontend` bypasses the `ExportOperatingMode::Halted` guard enforced by `register_token`, allowing fee-asset burns and tip dispatch while Ethereum export is halted - (File: `bridges/snowbridge/pallets/system-frontend/src/lib.rs`)

## Summary
`Pallet::register_token` explicitly checks `ensure!(!Self::export_operating_mode().is_halted(), Error::<T>::Halted)` before performing any swap/burn/XCM-Transact work [1](#0-0) . The `add_tip` extrinsic performs the equivalent value-affecting operations (asset swap-for-Ether, burn-for-teleport, and a `Transact` dispatch to Bridge Hub) but contains no such check at all [2](#0-1) .

## Finding Description
The pallet exposes `ExportOperatingMode` storage and a root-gated `set_operating_mode` extrinsic to halt Ethereum-export-related operations [3](#0-2) . `register_token` enforces this halt via an explicit `ensure!` guard using the `Error::<T>::Halted` variant [4](#0-3) [5](#0-4) . `add_tip`, however, only calls `ensure_signed(origin)?`, then unconditionally calls `swap_fee_asset_and_burn` (which swaps the asset for Ether via `T::Swap` or directly burns Ether via `burn_for_teleport`) and dispatches a `Transact` call carrying `EthereumSystemCall::AddTip` to Bridge Hub via `send_transact_call` [6](#0-5) . Nowhere in this call path is `Self::export_operating_mode().is_halted()` checked, confirmed by direct reading of the full pallet source — the only place `is_halted()` is checked in the call implementation block is inside `register_token`. There is no signed-extension, `BaseCallFilter`, or other transaction-level check present in this file that would independently re-apply the halt to `add_tip`; the `ExportPausedQuery` impl at the bottom of the file only exposes a query function used by external code (e.g. the outbound-queue-v2 exporter) and is not wired into `add_tip` itself [7](#0-6) .

## Impact Explanation
When governance sets `ExportOperatingMode::Halted` (e.g., in response to an incident on the Ethereum export/backend pipeline), `add_tip` still allows any signed account to irreversibly swap and burn assets for Ether and to enqueue an XCM `Transact` targeting Bridge Hub's `EthereumSystemCall::AddTip`, continuing to mutate reward/order state on the receiving side while the pallet's control-plane is nominally frozen. This matches the "runtime bugs that compromise intended behavior" / unbacked-burn category in the impact gate, since user funds are burned on the sending side without the halt-enforced guarantee that no further export-bound state changes will occur.

## Likelihood Explanation
High. `add_tip` is a fully permissionless, always-available extrinsic gated only by `ensure_signed`, requiring no special privilege, relayer, or governance collusion — any account holding a swappable/burnable fee asset can invoke it at any time, including immediately after a halt is set, since the code path never re-checks `export_operating_mode()`.

## Recommendation
Add the same guard used in `register_token` to the start of `add_tip`:
```rust
pub fn add_tip(origin: OriginFor<T>, message_id: MessageId, asset: Asset) -> DispatchResult {
    ensure!(!Self::export_operating_mode().is_halted(), Error::<T>::Halted);
    let who = ensure_signed(origin)?;
    ...
}
```

## Proof of Concept
1. Root calls `set_operating_mode(Root, BasicOperatingMode::Halted)`, setting `ExportOperatingMode::<T>::put(Halted)` [8](#0-7) .
2. Call `register_token(...)` — verify it fails with `Error::Halted` due to the explicit check.
3. Call `add_tip(origin, message_id, fee_asset)` as any signed user — observe it succeeds: `swap_fee_asset_and_burn` executes the swap/burn and `send_transact_call` dispatches the `Transact` XCM carrying `EthereumSystemCall::AddTip` to Bridge Hub, despite `ExportOperatingMode` being `Halted`.
4. This demonstrates that the same class of operation (`register_token`) is blocked while the parallel `add_tip` path is not, confirming the guard bypass. Note: I could not verify whether Bridge Hub's receiving-side pallet independently enforces a halt check on `EthereumSystemCall::AddTip`, since that code was not available for review in this pass; this does not affect the validity of the missing sender-side guard itself.

		fn swap_fee_asset_and_burn(
			origin: Location,
			fee_asset: Asset,
		) -> Result<u128, DispatchError> {
			let ether_location = T::EthereumLocation::get();
			let (fee_asset_location, fee_amount) = match fee_asset {
				Asset { id: AssetId(ref loc), fun: Fungible(amount) } => (loc, amount),
				_ => {
					tracing::debug!(target: LOG_TARGET, ?fee_asset, "error matching fee asset");
					return Err(Error::<T>::UnsupportedAsset.into());
				},
			};
			if fee_amount == 0 {
				return Ok(0);
			}

			let ether_gained = if *fee_asset_location != ether_location {
				Self::swap_and_burn(
					origin.clone(),
					fee_asset_location.clone(),
					ether_location,
					fee_amount,
				)
				.inspect_err(|&e| {
					tracing::debug!(target: LOG_TARGET, ?e, "error swapping asset");
				})?
			} else {
				burn_for_teleport::<T::AssetTransactor>(&origin, &fee_asset)
					.map_err(|_| Error::<T>::BurnError)?;
				fee_amount
			};
			Ok(ether_gained)
		}

		fn send_transact_call(
			origin_location: Location,
			call: BridgeHubRuntime<T>,
		) -> DispatchResult {
			let dest = T::BridgeHubLocation::get();
			let remote_xcm = Self::build_remote_xcm(&call);
			let message_id = Self::send_xcm(origin_location, dest.clone(), remote_xcm.clone())
				.map_err(|error| Error::<T>::from(error))?;

			Self::deposit_event(Event::<T>::MessageSent {
				origin: T::PalletLocation::get().into(),
				destination: dest,
				message: remote_xcm,
				message_id,
			});

			Ok(())
		}
