### Title
Signature-Weight Double-Counting in `ValidateMultiSign` Precompile Allows Multi-Sig Threshold Bypass - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `ValidateMultiSign` TVM precompiled contract accumulates signer weight in a loop very similarly to the reported `processBorrow` bug: a per-iteration `continue` is meant to filter out redundant/invalid entries before they contribute to a security-critical total (`totalWeight`), but the filter condition is too narrow. When the same recovered address supplies two different-but-valid signature byte strings over the same hash, the loop does not `continue` and instead adds that same key's weight to `totalWeight` a second time, letting a caller satisfy `permission.getThreshold()` without controlling enough independent keys.

### Finding Description
In `PrecompiledContracts.ValidateMultiSign.execute()`: [1](#0-0) 

```java
long totalWeight = 0L;
List<byte[]> executedSignList = new ArrayList<>();
for (byte[] sign : signatures) {
  byte[] recoveredAddr = recoverAddrBySign(sign, hash);
  sign = merge(recoveredAddr, sign);
  if (ByteArray.matrixContains(executedSignList, recoveredAddr)) {
    if (ByteArray.matrixContains(executedSignList, sign)) {
      continue;
    }
    MUtil.checkCPUTime();
  }
  long weight = TransactionCapsule.getWeight(permission, recoveredAddr);
  if (weight == 0) {
    return Pair.of(true, DATA_FALSE);
  }
  totalWeight += weight;
  executedSignList.add(sign);
  executedSignList.add(recoveredAddr);
}
if (totalWeight >= permission.getThreshold()) {
  return Pair.of(true, dataOne());
}
```

The intended de-duplication logic is: "if this exact `(recoveredAddr, sign)` pair was already processed, skip it so we don't double count." However the "already seen" check is keyed on the raw signature bytes (`sign = merge(recoveredAddr, sign)`), not on the recovered address alone. ECDSA signatures are malleable: for any valid `(r, s)` there exists a second valid signature `(r, n-s)` with an adjusted recovery id `v` that recovers to the *same* address over the *same* message hash. `recoverAddrBySign` performs standard ECDSA recovery without enforcing canonical/low-`s` signatures, so an attacker holding one private key can produce two syntactically different, both-valid signature blobs for the same key.

When such a pair is supplied:
1. First iteration: `recoveredAddr` not yet in `executedSignList` → weight added, `(recoveredAddr, sign)` recorded.
2. Second iteration (same address, different `sign` bytes): `matrixContains(executedSignList, recoveredAddr)` is `true`, but `matrixContains(executedSignList, sign)` is `false` (the byte-exact malleated signature was never recorded) → the `continue` is skipped, and the same key's weight is added to `totalWeight` again.

This mirrors the audited bug pattern exactly: a loop meant to gate a sum that feeds a threshold check (`totalWeight >= permission.getThreshold()`, analogous to `totalCollateralInUSD >= borrowAmountInUSD`) has a filtering condition tied to the wrong granularity (exact byte match instead of logical identity of the signer), letting a required value accumulate incorrectly and the security check pass when it should not.

### Impact Explanation
`ValidateMultiSign` is the on-chain primitive smart contracts use to authorize privileged actions (e.g., "N-of-M" custody wallets, contract-controlled treasuries) by checking whether a submitted signature set meets an account's `Permission` threshold. If a single key's weight can be doubled (or multiplied further by additional malleated variants, up to `MAX_SIZE = 5` signature slots), an attacker controlling only one authorized key — or a key with weight below the threshold — can forge authorization for actions gated by this precompile, enabling unauthorized withdrawal or execution of privileged operations from any contract that relies on `ValidateMultiSign` for access control. This is an unauthorized-account-operation / theft-of-funds class impact reachable purely by an unprivileged contract caller supplying crafted call data (`TriggerSmartContract`).

### Likelihood Explanation
The precompile is reachable by any address via `TriggerSmartContract`/contract call with no special privilege; producing a second valid signature for the same key over the same hash via ECDSA `s`-malleability is a purely local computation requiring only the corresponding private key. This is a widely-known, mechanical manipulation (not model-guessing), directly analogous to the reported bug's mechanism. However, exploitation impact depends on downstream contracts actually relying on `ValidateMultiSign`'s boolean result for authorization decisions with multi-key thresholds where an attacker controls fewer keys than required — this makes real-world severity contract-usage dependent, though the underlying precompile flaw itself is concrete and verifiable from the code shown.

### Recommendation
Change the de-duplication check to key exclusively on `recoveredAddr` (the signer identity), not on the raw signature bytes, i.e. reject/skip (or better, treat as invalid) as soon as the same `recoveredAddr` appears a second time regardless of the exact signature bytes — mirroring `TransactionCapsule.checkWeight`'s `HashMap` keyed by recovered address (`addMap.containsKey(base64)` → throw "has signed twice!"), which does not have this flaw: [2](#0-1) 

### Proof of Concept
Conceptual PoC (cannot be fully executed without access to the `recoverAddrBySign`/ECDSA malleability helper internals, but the mechanism is standard ECDSA):
1. Attacker holds one private key `K` that is a member of `permission` with `weight = W < permission.getThreshold()`, and no other authorized key.
2. Attacker signs `hash` normally to get `sig1 = (r, s, v)`.
3. Attacker derives the malleated counterpart `sig2 = (r, n - s, v')` (standard ECDSA malleability transform), which recovers to the same address `K` for the same `hash`.
4. Attacker calls the `ValidateMultiSign` precompile (`address, permissionId, data`) with `signatures = [sig1, sig2]`.
5. In the loop: iteration 1 adds `W` to `totalWeight`; iteration 2 recognizes `recoveredAddr` was seen but `sign` bytes differ, so it does **not** `continue`, and adds `W` again, yielding `totalWeight = 2W`.
6. If `2W >= permission.getThreshold()`, the precompile returns `true` (`dataOne()`), incorrectly authorizing an operation that should have required additional independent keys.

Verification of the exact malleability transform against this codebase's `recoverAddrBySign` implementation (not shown in the retrieved context) would be needed to fully confirm exploitability end-to-end; a Devin session with full repository access should locate and inspect `recoverAddrBySign` to confirm it lacks canonical-signature enforcement before treating this as fully proven.
