## Title
Handshake replay-protection bypass when the existing tunnel is initiator-side allows an old, captured handshake to roll back an established Nebula tunnel — (File: `handshake_manager.go`)

### Summary
Nebula defends against handshake replay by comparing `lastHandshakeTime`, a value taken from the signed handshake payload (`Payload.Time`, see `handshake/payload.go`), against the time recorded on the tunnel currently held in the hostmap. This is the exact analog of the C4 finding: an authenticated message (`Recovery`/handshake stage-1) that is not bound to a monotonically-enforced freshness check can be replayed later to roll back live state. In Nebula's `CheckAndComplete`, the freshness comparison is gated by `!existingHostInfo.ConnectionState.initiator`, so it is skipped entirely whenever the currently-installed tunnel has *us* as the initiator. In that case, any previously captured, cryptographically-valid stage-1 handshake packet from the same peer (whose certificate has not yet expired) is accepted, unconditionally displacing the live tunnel, exactly like the replayed `RecoveryRequestMessage` overwriting the newer `rec.pke`.

### Finding Description
`HostInfo.lastHandshakeTime` exists specifically to stop handshake replay: [1](#0-0) 

It is populated from the signed `Payload.Time` field carried in the Noise handshake payload: [2](#0-1) 

`CheckAndComplete` is the sole gate that decides whether an inbound handshake is allowed to replace an existing tunnel entry in the hostmap: [3](#0-2) 

The freshness check `existingHostInfo.lastHandshakeTime >= hostinfo.lastHandshakeTime && !existingHostInfo.ConnectionState.initiator` only rejects a stale/older handshake when the side effect of the check `!existingHostInfo.ConnectionState.initiator` is true — i.e., when we are currently the *responder* of the existing tunnel. If we are currently the *initiator* of the existing tunnel (a normal, common state for any tunnel we brought up ourselves), the freshness comparison never executes, and `hm.mainHostMap.unlockedAddHostInfo(hostinfo, f)` unconditionally installs the new (stale) `hostinfo` over the live one: [4](#0-3) 

This mirrors the `verify_update` bug exactly: `Update`-type messages in swafe strictly enforce `st.cnt == old.cnt+1` while `Recovery`-type messages have no ordering check at all, letting an old signed message overwrite fresher state. Here, `Update`-type (data-plane rekey) traffic is protected by the sliding-window replay tracker, but the handshake path's only anti-replay mechanism (`lastHandshakeTime`) is conditionally disabled depending on which side is the current initiator — an attacker doesn't need to break any cryptography, they only need to have observed one old, legitimately-signed stage-1 packet from the victim.

An attacker who has captured any past stage-1 handshake packet from a legitimate peer (from network capture, since Nebula runs over UDP with no confidentiality on the handshake) can replay it at any later time, as long as:
1. We currently hold the tunnel to that peer as the initiator side (a very common, unprivileged runtime condition, e.g. right after we punched through / rebound / re-handshook).
2. The peer's certificate embedded in that old packet has not yet expired (certificates are commonly valid for long windows).

### Impact Explanation
Successful replay causes `CheckAndComplete` to tear down and replace the live, authenticated tunnel's `HostInfo`/`ConnectionState` with one derived from stale/old key material and an old handshake result, exactly the "state poisoning" impact category (remote state poisoning of hostmap without needing the attacker's own certificate). This can be used to reliably deny service on an established tunnel (repeated overwrite prevents the current session from remaining current), forcing the local side into a fresh handshake cycle whenever the attacker chooses, and it defeats the very freshness mechanism whose doc comment states it exists "to avoid an attack where a handshake packet is replayed after some time." An attacker who continuously wins this race can indefinitely disrupt/roll back reconnection attempts between two nodes without ever needing a CA-signed certificate of their own, purely by replaying previously-observed genuine packets — directly analogous to the swafe recovery-liveness-denial scenario.

### Likelihood Explanation
The precondition (local hostinfo currently initiator-side) is a normal, frequent tunnel state rather than an edge case, and the attacker capability required (capture + replay of a UDP packet, no forgery, no valid cert) matches the "no CA-signed certificate" threat model exactly. The only additional constraint is that the replayed certificate must still be within its validity window, which is realistic for typical cert lifetimes.

### Recommendation
Remove the `!existingHostInfo.ConnectionState.initiator` carve-out (or replace it with a correct, symmetric rule) so the `lastHandshakeTime` freshness check in `CheckAndComplete` (`handshake_manager.go`) is enforced regardless of which side is currently the initiator of the existing tunnel — i.e., always reject an inbound handshake whose `lastHandshakeTime` is not strictly newer than the tunnel already installed for that peer, mirroring the strict `cnt`/version-increment enforcement style used elsewhere (e.g., the swafe mitigation's `cnt_rec` approach) rather than allowing an unconditional bypass path.

### Proof of Concept
1. Peer A and Peer B complete a handshake; A becomes the initiator-side `HostInfo` for the tunnel with B (`ConnectionState.initiator == true` on A's side).
2. An attacker M, positioned to observe UDP traffic between A and B, captures the original stage-1 packet B once sent to A when the tunnel was first (or previously) established, before B's certificate expires.
3. Time passes; A's live tunnel to B continues normally, still with A as initiator (`existingHostInfo.ConnectionState.initiator == true`).
4. M replays the captured stage-1 packet toward A's UDP listener, spoofing/relaying from B's address (or via a relay path).
5. `HandshakeManager.HandleIncoming` → `beginHandshake` → `CheckAndComplete` is invoked; because `existingHostInfo.ConnectionState.initiator` is `true`, the `lastHandshakeTime` freshness comparison in `handshake_manager.go:447` is skipped, and `unlockedAddHostInfo` (`handshake_manager.go:475`) replaces A's live `HostInfo` for B with one built from the old, replayed handshake, per [5](#0-4) .
6. Repeating step 4 whenever A re-establishes a fresh tunnel with B allows M to keep rolling back/perturbing the tunnel state, denying stable connectivity between A and B without holding any CA-signed certificate.

func (hm *HandshakeManager) CheckAndComplete(hostinfo *HostInfo, handshakePacket uint8, f *Interface) (*HostInfo, error) {
	hm.mainHostMap.Lock()
	defer hm.mainHostMap.Unlock()
	hm.Lock()
	defer hm.Unlock()

	// Check if we already have a tunnel with this vpn ip
	existingHostInfo, found := hm.mainHostMap.Hosts[hostinfo.vpnAddrs[0]]
	if found && existingHostInfo != nil {
		// Is it just a delayed handshake packet? Check every hostinfo we hold for this address.
		for _, testHostInfo := range hm.mainHostMap.unlockedGetHostList(hostinfo.vpnAddrs[0]) {
			if bytes.Equal(hostinfo.HandshakePacket[handshakePacket], testHostInfo.HandshakePacket[handshakePacket]) {
				return testHostInfo, ErrAlreadySeen
			}
		}

		// Is this a newer handshake?
		if existingHostInfo.lastHandshakeTime >= hostinfo.lastHandshakeTime && !existingHostInfo.ConnectionState.initiator {
			return existingHostInfo, ErrExistingHostInfo
		}

		existingHostInfo.logger(hm.l).Info("Taking new handshake")
	}
