### Title
FetchRemote SSRF/RCE via unvalidated `ext::` remote URL scheme - (File: internal/gitaly/service/repository/fetch_remote.go)

### Summary
`buildCommandOpts` sets `remote.inmemory.url` directly from `req.GetRemoteParams().GetUrl()` without validating the URL scheme, and `validateFetchRemoteRequest` only checks that the URL is non-empty. Because Gitaly does not set `GIT_ALLOW_PROTOCOL`/`protocol.ext.allow` before invoking `git-fetch(1)`, a remote URL using git's `ext::` transport helper can execute an arbitrary shell command on the Gitaly host.

### Finding Description
`FetchRemote` validates the request in `validateFetchRemoteRequest` (internal/gitaly/service/repository/fetch_remote.go:306-320), which only rejects a blank URL — no scheme allowlist (e.g. restricting to `http(s)://`, `git://`, `ssh://`) is applied. The URL then flows unmodified into `buildCommandOpts` (fetch_remote.go:260-304), where it becomes the value of `remote.inmemory.url` via `gitcmd.WithConfigEnv` [1](#0-0) , and is passed straight to `git-fetch(1)` in `Repo.FetchRemote` in `internal/git/localrepo/remote.go`. Git's built-in `ext::` remote helper (`ext::<command>`) executes `<command>` as a subprocess of `git-remote-ext`, substituting `%S`/`%s` placeholders; there's no evidence in the reachable code path (`buildCommandOpts`, `FetchOpts.buildFlags`, or the command execution options set in `Repo.FetchRemote`) that Gitaly sets `GIT_ALLOW_PROTOCOL` or `protocol.ext.allow=never`/`user` to disable this helper. Since the RPC is reachable from an unprivileged user's own project (e.g. configuring a pull mirror or an "import project by URL" flow that ultimately calls `FetchRemote` with a user-supplied URL), the attacker fully controls `remote_params.url`, allowing arbitrary command execution on the Gitaly node under the `git` process user.

### Impact Explanation
This maps to GitLab's "Remote Code Execution" bounty class, the most severe SSRF-adjacent outcome: instead of merely reaching internal network endpoints, the attacker gets direct code execution on the Gitaly server (arbitrary shell command execution), which can be used to read repository data of other tenants/groups, pivot within the internal network, and exfiltrate secrets from the Gitaly host.

### Likelihood Explanation
The attacker only needs the ability to set an import/mirror URL for a project they own — a capability available to any regular GitLab user (project creation via "Import project by URL" or configuring a pull mirror). No admin role, secret, or network position is required, making this trivially and repeatably exploitable if the RPC and its callers do not otherwise restrict URL schemes upstream. Note: I could not fully confirm from the indexed files whether GitLab Rails (the RPC caller) or another layer performs scheme validation before invoking `FetchRemote`; if such validation is enforced server-side in Rails, this issue would be mitigated at that layer rather than in Gitaly, but no such enforcement was found within the Gitaly codebase itself, which is the boundary in scope here.

### Recommendation
In `validateFetchRemoteRequest` (or `buildCommandOpts`), parse `req.GetRemoteParams().GetUrl()` and reject any scheme other than an explicit allowlist (`http`, `https`, `git`, `ssh`), and/or set `GIT_ALLOW_PROTOCOL=http:https:git:ssh` (and `protocol.ext.allow=never`) in the environment passed to `git-fetch(1)` in `internal/git/localrepo/remote.go`'s `FetchRemote`, mirroring the protections git upstream introduced after CVE-2017-1000117-style issues.

### Proof of Concept
```go
// internal/gitaly/service/repository/fetch_remote_test.go (illustrative)
func TestFetchRemote_extProtocolRCE(t *testing.T) {
    cfg, repoProto, _ := setupRepositoryService(t)
    client := newRepositoryClient(t, cfg, cfg.SocketPath)

    _, err := client.FetchRemote(ctx, &gitalypb.FetchRemoteRequest{
        Repository: repoProto,
        RemoteParams: &gitalypb.RemoteRepository{
            Url: `ext::sh -c "touch /tmp/pwned_via_gitaly"`,
        },
    })
    // Expect command to run on the Gitaly host; assert /tmp/pwned_via_gitaly exists,
    // or fetch fails with a git-remote-ext related error rather than a rejected-scheme error,
    // confirming the URL reached git-fetch(1) unvalidated.
}
```
Expected (vulnerable) result: the RPC invokes `git fetch` with `remote.inmemory.url=ext::sh -c "..."`, causing `git-remote-ext` to execute the shell command on the Gitaly host.
