### Title
Protocol fee is bypassed entirely on `Nep245`/`Imt` token swaps whose per-intent delta equals 1 unit - ([File: contracts/defuse/core/src/intents/token_diff.rs])

### Summary
`TokenDiff::token_fee` unconditionally zeroes the protocol fee for `Nep245` (multi-token) and `Imt` (internally-issued multi-token) assets whenever the absolute delta being moved in a single `TokenDiff` intent is `<= 1`. This exemption was designed for true NFTs (`Nep171`, always non-fungible, `amount` is always 1) but is also applied to `Nep245`/`Imt`, which are fungible-style multi-tokens that can carry arbitrary value per unit. An unprivileged signer can therefore split any trade of a `Nep245`/`Imt` asset into a sequence of same-batch `TokenDiff` intents that each move exactly `1` unit of that token, collecting the full economic value of the trade while paying zero protocol fee on every leg, even though the exact same aggregate trade routed through a single `TokenDiff` with `amount > 1` would owe a fee.

### Finding Description
The fee is computed and collected inside `TokenDiff::execute_intent`: [1](#0-0) 

The per-token fee rate used above comes from `TokenDiff::token_fee`: [2](#0-1) 

The guard `TokenIdType::Nep245 | TokenIdType::Imt if amount > 1 => {}` only lets the fee apply when the *single intent's* delta magnitude on that token exceeds 1; otherwise (`amount <= 1`) the fee rate is forced to `Pips::ZERO`, exactly like real NFTs (`Nep171`). This is sound for `Nep171` because an NFT transfer is inherently a single indivisible unit with no meaningful "amount", but `Nep245` (multi-token/semi-fungible, including cross-verifier wrapped balances) and `Imt` (internally minted multi-token, see `contracts/defuse/core/src/intents/imt.rs` / `contracts/defuse/core/src/tokens.rs`) are fungible-style assets whose single unit can represent arbitrary, attacker-chosen value (decimals are controlled by the token's minting logic, not enforced to be "NFT-like").

Because the fee check is evaluated independently for each `TokenDiff` intent inside `execute_signed_intent` (looped over in `execute_signed_intents`), and each signed intent only needs a unique nonce (no cross-intent netting of the *same token* delta for fee purposes), an attacker can decompose one large `Nep245`/`Imt` swap of `N` units into `N` separate signed `TokenDiff` intents, each with `delta = ±1` on that token, submitted together in one `execute_intents(signed: Vec<MultiPayload>)` call: [3](#0-2) 

Each of the `N` intents independently hits the `amount <= 1` branch and is charged `Pips::ZERO`, whereas a single intent moving `N` units of the same token would have been charged `fee.fee_ceil(N)`. The counterparty (solver/maker) side nets the deltas through the `TransferMatcher`/`Deltas` invariant machinery exactly the same way regardless of how many intents the transfer was split across, so the trade settles normally — only the fee owed differs from the fee collected.

### Impact Explanation
This directly falls in the "fees bypassed or over-collected" Critical impact category: `fees owed` (what `fee.fee_ceil(amount)` would compute for the true aggregate trade size) diverges from `fees collected` (zero, because each leg is artificially shrunk to `amount == 1`). Any unprivileged pair of counterparties trading a `Nep245` or `Imt` asset can permanently deprive the protocol fee collector (`fee_collector`, see `contracts/defuse/src/contract/fees.rs`) of fees on the entire notional value of the trade, with no requirement for a privileged role, relayer key, or DAO action — only ordinary signed intents from the trading accounts.

### Likelihood Explanation
Likelihood is high for any deployment where `Nep245`/`Imt` assets carry non-trivial per-unit value (e.g., a wrapped high-value token bridged in as an MT, or an `Imt` token minted with few/no fractional decimals). The only cost to the attacker is submitting `N` intents instead of `1` in a single `execute_intents` call, which is cheap and requires no special privileges — just more nonces and slightly larger payload/gas, which is explicitly out of scope to weigh against likelihood per the rules, but does not prevent exploitation.

### Recommendation
Compute the protocol fee for `Nep245`/`Imt` tokens based on the underlying value moved rather than exempting any transfer with `amount <= 1`. Concretely:
- Remove the blanket `amount <= 1` fee exemption for `Nep245`/`Imt` in `TokenDiff::token_fee` (contracts/defuse/core/src/intents/token_diff.rs:206-217), keeping the exemption only for `Nep171` (true NFTs).
- If a fee-free threshold is still desired for genuinely NFT-like `Nep245`/`Imt` tokens (i.e., tokens whose supply/decimals imply `1` unit == the whole asset), gate that exemption on token metadata (e.g., a per-token "non-fungible" flag or total-supply-of-1 check) rather than on the delta of a single intent, and/or aggregate deltas per token across the whole batch before evaluating the fee-exemption threshold so it cannot be bypassed by splitting one trade into many minimal-amount intents.

### Proof of Concept
1. Configure the Defuse contract with `fee > 0` and `fee_collector = C`.
2. Let user `U` hold `100` units of an `Imt`/`Nep245` token `T` (each unit representing meaningful value, e.g. an `Imt` minted with 0 extra decimals) and solver `S` hold the equivalent counter-asset.
3. Baseline: `U` signs one `TokenDiff` intent `{T: -100, T2: +X}`; `S` signs the matching intent. On execution, `token_fee(T, 100, fee)` returns `fee` (since `amount=100>1`), and `fee.fee_ceil(100)` is deducted and sent to `C` — as shown by `tests/src/tests/defuse/intents/token_diff.rs` swap tests using `TokenDiff::closure_delta`.
4. Attack: instead, `U` and `S` each sign `100` separate `TokenDiff` intents, each moving `delta = ∓1` of `T` (and a proportional `1/100`-sized leg of `T2`), all bundled into one `execute_intents(signed: Vec<MultiPayload>)` call.
5. For every one of the 100 intents, `TokenDiff::token_fee(T, 1, fee)` hits the `amount <= 1` branch in contracts/defuse/core/src/intents/token_diff.rs:206-217 and returns `Pips::ZERO`, so `fees_collected` stays empty and nothing is added to `C`'s balance in `execute_intent` (contracts/defuse/core/src/intents/token_diff.rs:70-78, 96-101).
6. Net result: the same aggregate `100`-unit trade of `T` completes with `fees owed = fee.fee_ceil(100) > 0` per step 3's baseline, but `fees collected = 0`, confirming the fee bypass.
