Audit Report

## Title
Permanent Fund Lock in `pallet-asset-rewards` from Uncapped `last_update_block` After Pool Expiry - (File: `substrate/frame/asset-rewards/src/lib.rs`)

## Summary
`update_pool_rewards()` sets `PoolInfo.last_update_block` to the current block number unconditionally, without capping it to `expiry_block` the way `reward_per_token()`'s `last_block_reward_applicable()` does. Once any staker calls `unstake` on their own position after `expiry_block` has passed (permitted via the `caller == staker` bypass), `last_update_block` becomes greater than `expiry_block`, and every subsequent call to `reward_per_token()` underflows in `last_block_reward_applicable(expiry_block).ensure_sub(last_update_block)`, causing a hard error that permanently reverts `stake`, `unstake`, `harvest_rewards`, `set_pool_reward_rate_per_block`, and even the admin's `set_pool_expiry_block`.

## Finding Description
`PoolInfo` stores `last_update_block` alongside `reward_per_token_stored` (`substrate/frame/asset-rewards/src/lib.rs` L160-164). `reward_per_token()` caps elapsed blocks using `last_block_reward_applicable(pool_info.expiry_block)`, which itself returns `min(now, expiry_block)` (L826-833), then does `.ensure_sub(pool_info.last_update_block)` (L794-801). However, `update_pool_rewards()` sets `new_pool_info.last_update_block = T::BlockNumberProvider::current_block_number()` unconditionally (L775-784), with no capping logic mirroring `last_block_reward_applicable`.

`unstake` allows the staker to act on their own account regardless of whether the pool has expired: `ensure!(now > pool_info.expiry_block || caller == staker, BadOrigin);` (L526), then calls `update_pool_and_staker_rewards` → `update_pool_rewards` and persists the result via `Pools::<T>::insert(pool_id, pool_info);` (L545). `stake` behaves the same way, persisting unconditionally (L489-492).

Once `last_update_block > expiry_block` is persisted, any subsequent call to `reward_per_token()` (from `stake`, `unstake`, `harvest_rewards`, `set_pool_reward_rate_per_block`, `set_pool_expiry_block`) computes `expiry_block.ensure_sub(last_update_block)`, which underflows on the unsigned `BlockNumberFor<T>` type and returns `Err`, causing the enclosing extrinsic to fail deterministically. `set_pool_expiry_block`, the admin's apparent remedy, itself calls `reward_per_token(&pool_info)` on the stale corrupted state before applying the new expiry (L953-958), so it also fails and cannot repair the pool.

## Impact Explanation
Once triggered, all extrinsics that touch the corrupted pool's reward accounting (`unstake`, `harvest_rewards`, `stake`, `set_pool_reward_rate_per_block`, `set_pool_expiry_block`) fail permanently. `cleanup_pool` requires an empty staker set, so the admin cannot force-close the pool while stakers remain. This permanently locks the staked-asset and reward-asset balances held in the pool's sub-account, matching the "permanent user-fund or bridge-state lock" impact category in the accepted impact gate.

## Likelihood Explanation
No privileged actor or malicious peer is required. Any ordinary staker can trigger this by calling `unstake` on their own stake (`caller == staker` bypasses the expiry gate) after `expiry_block` has passed while other stakers still hold non-zero balances in the pool. This is a normal, expected user action rather than an attack requiring special capability, making the likelihood high for any pool with a bounded lifetime that outlives its expiry while holding multiple stakers.

## Recommendation
In `update_pool_rewards()`, set `new_pool_info.last_update_block = Self::last_block_reward_applicable(pool_info.expiry_block)` instead of the raw current block number, mirroring the cap already applied inside `reward_per_token()`. This guarantees `last_update_block` never exceeds `expiry_block`, eliminating the underflow in `ensure_sub` and preserving the "no further accrual past expiry" invariant without corrupting checkpoint state.

## Proof of Concept
1. Create a pool with `expiry_block` set some fixed number of blocks in the future, with two stakers (`staker1`, `staker2`) both staking non-zero amounts before expiry.
2. Advance the current block number past `expiry_block` without calling `set_pool_expiry_block`.
3. `staker1` calls `unstake` on their own stake (allowed via `caller == staker` regardless of expiry); this persists `pool_info.last_update_block = now > expiry_block` through the `Pools::<T>::insert` call in `unstake`.
4. `staker2`, who still has staked tokens, calls `unstake` or `harvest_rewards`. `reward_per_token()` computes `last_block_reward_applicable(expiry_block).ensure_sub(last_update_block)`, which underflows and returns `Err`, causing the call to fail.
5. The admin's attempt to call `set_pool_expiry_block` also fails, since it first invokes `reward_per_token(&pool_info)` on the same corrupted `pool_info`.
6. `staker2`'s stake and any pending rewards remain permanently locked in the pool's sub-account with no available extrinsic path to recover them.
