### Title
Hardcoded `0.0001` relative-precision threshold in `ExchangeWithdrawActuator` does not scale with TRC10 token precision, freezing liquidity for low/zero-precision tokens - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
`ExchangeWithdrawActuator.doValidate()` rejects a withdrawal from a bancor-style token exchange with `"Not precise enough"` whenever the calculated proportional amount of the paired token diverges from the rounded integer result by more than a fixed relative tolerance of `0.0001` (0.01%). This constant is a single hardcoded value applied identically regardless of the `precision` of the TRC10 assets involved in the exchange pair, which ranges from `0` to `6` per `ActuatorConstant.PRECISION_DECIMAL` [1](#0-0) . This is directly analogous to the reported `maxDivergenceWithdraws` bug class: a fixed tolerance calibrated for one token's decimal granularity breaks down for tokens with different decimals/precision.

### Finding Description
`ExchangeCreateActuator`/`AssetIssueActuator` allow TRC10 tokens with `precision` from `0` up to `6` to be paired in an `Exchange` pool alongside TRX (6 decimals) [1](#0-0) . When the exchange creator calls `ExchangeWithdrawContract` to remove liquidity, `doValidate()` computes the proportional amount of the other token using `BigDecimal` division rounded to 4 decimal places, then checks that the relative difference between this "precise" ratio and the actual integer `anotherTokenQuant` used by `execute()` does not exceed a hardcoded `0.0001` relative-divergence tolerance: [2](#0-1) 

Because token balances/quantities are raw integer amounts (not normalized by decimals), a token with low precision (e.g., precision `0`, or a small circulating pool balance relative to the other side) produces coarse-grained integer ratios where rounding error routinely exceeds `0.01%` of the computed amount. This same hardcoded `0.0001` tolerance is duplicated for both branches of the withdraw calculation and is not configurable via `dao`/dynamic parameters the way `getExchangeBalanceLimit()` is (unlike `ExchangeTransactionActuator`, which uses a caller-supplied `expected` slippage bound instead of a fixed constant) [3](#0-2) .

### Impact Explanation
For exchange pools composed of a low-precision or low-balance TRC10 token paired with TRX or another asset, the exchange creator's `ExchangeWithdrawContract` transactions can legitimately and unavoidably fail with `"Not precise enough"` for essentially all withdrawal amounts, because the fixed `0.0001` relative tolerance does not account for the coarser integer granularity of that token. Since there is no alternate withdrawal path and no way to adjust this constant per-exchange, the creator's TRX/token liquidity locked in the `Exchange` capsule can become permanently unwithdrawable, constituting a freezing-of-funds condition reachable directly by any account that created such an exchange pool via `ExchangeCreateActuator` and later attempts `ExchangeWithdrawActuator`.

### Likelihood Explanation
Any account can create an `Exchange` between TRX and any TRC10 asset with precision as low as `0` (validated only to be `<= 6`), then inject/withdraw liquidity. Because both actuators are reachable directly from a signed `ExchangeCreateContract`/`ExchangeWithdrawContract` transaction with no special privilege required, and the rounding behavior is deterministic given integer balances, the failure condition is trivially and repeatably triggered whenever pool ratios don't divide evenly within the fixed tolerance — which is common for low-decimal or imbalanced pools.

### Recommendation
Replace the hardcoded `0.0001` relative-divergence constant in `ExchangeWithdrawActuator.doValidate()` with a tolerance derived from the actual precision of the tokens involved (e.g., scaled by `10^-precision` of the lower-precision token in the pair), or expose it as a governance-tunable dynamic property similar to `getExchangeBalanceLimit()`, so pools of tokens with precision different from TRX's 6 decimals are not systematically prevented from withdrawing liquidity.

### Proof of Concept
1. Create an `Exchange` pairing TRX with a TRC10 token `T` issued with `precision = 0` via `AssetIssueContract`/`ExchangeCreateContract`, with an imbalanced ratio (e.g., `firstTokenBalance = 3`, `secondTokenBalance = 10`).
2. As the exchange creator, submit `ExchangeWithdrawContract` withdrawing `1` unit of `T`.
3. In `ExchangeWithdrawActuator.doValidate()`, `anotherTokenQuant = 10*1/3 = 3` (integer division), while the BigDecimal 4-decimal ratio is `3.3333`; the relative remainder `0.3333/3 ≈ 11%` far exceeds the `0.0001` (0.01%) tolerance, causing `ContractValidateException("Not precise enough")` regardless of the amount chosen, permanently blocking withdrawal for this pool composition [4](#0-3) .
