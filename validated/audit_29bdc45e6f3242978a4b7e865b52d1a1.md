### Title
Missing Expiry Check in `TrustedSpender.setAllowance` Allows Timelock Bypass - ([File: tare-io__tare-contracts/contracts/TrustedSpender.sol])

### Summary
The `TrustedSpender.setAllowance` function allows a Safe owner or Guardian to set an ERC20 or NFT spending allowance for a delegate. While the function requires `validUntil > block.timestamp` at the time of setting, it does not prevent overwriting an existing, non-expired allowance with a new amount or a different expiry. This allows a delegate's spending authority to be extended or increased without waiting for the original timelock (expiry) to pass, effectively bypassing the intended temporal restriction on delegate spending power.

### Finding Description
In `TrustedSpender.sol`, the `setAllowance` and `setNFTAllowance` functions are designed to establish spending routes for delegates with a specific expiration timestamp (`validUntil`). The external report highlighted a similar issue where adding to an existing stake allowed bypassing a timelock. In Tare, the `TrustedSpender` serves as a delegated execution layer where Safes grant limited, time-bound permissions to delegates.

The `setAllowance` function [contracts/TrustedSpender.sol:69-81]() and `setNFTAllowance` function [contracts/TrustedSpender.sol:117-129]() fully overwrite the existing `Allowance` or `NFTAllowance` struct for a given `(token, from, to)` route. 

```solidity
  function setAllowance(
    address token,
    address from,
    address to,
    uint208 amount,
    uint48 validUntil
  ) external safeOrGuardian(from) {
    require(token != address(0) && from != address(0) && to != address(0), ZeroAddress());
    require(validUntil > block.timestamp, InvalidAllowanceDeadline());

    _allowances[token][from][to] = Allowance({amount: amount, validUntil: validUntil});
    emit AllowanceSet(token, from, to, amount, validUntil);
  }
```

If a Safe owner (or Guardian) has set a small allowance with a short expiry to limit a delegate's risk, they (or a compromised owner/guardian) can immediately call `setAllowance` again to increase the `amount` or extend the `validUntil` to a much later date. While the Safe owner is privileged, the protocol's design for "institutional-grade credit operations" [Tare Protocol Overview]() relies on these modules to enforce strict, predictable constraints on delegated actors. The lack of a check to ensure the previous allowance has expired before allowing an overwrite (or ensuring the new expiry is not shorter/longer than intended relative to the original) means the "timelock" provided by `validUntil` is only as strong as the immediate access control, rather than providing an independent temporal guarantee.

### Impact Explanation
An unprivileged actor (a delegate) who manages to influence a Safe owner or a Guardian (or in the event of a partial compromise of a Safe's multisig owners) can have their spending limits increased or their expiration extended without the protocol enforcing the original time-bound constraint. This leads to an unauthorized state transition where a delegate can spend more assets or spend for a longer duration than originally authorized by the Safe's governance process, leading to potential theft or diversion of USDC/vault assets.

### Likelihood Explanation
The likelihood is medium. It requires a Safe owner or Guardian to initiate the change, but the contract fails to enforce the temporal invariant that a set expiration should be respected. In institutional settings where Safes are used with specific governance delays or where Guardians act as backstops, the ability to bypass the expiration of a delegate's power is a material corruption of the intended security model.

### Recommendation
Modify `setAllowance` and `setNFTAllowance` to require that the existing allowance for the route has either expired or is being revoked (amount set to 0). Alternatively, implement a logic where if an active allowance is being updated, the `validUntil` can only be extended, or require a specific transition period.

```solidity
Allowance storage existing = _allowances[token][from][to];
require(block.timestamp > existing.validUntil || amount == 0, "Allowance not expired");
```

### Proof of Concept
1. A Safe owner sets an allowance for `Delegate A` to spend 1,000 USDC until `Timestamp T1` (1 hour from now) via `TrustedSpender.setAllowance`.
2. The `Delegate A` is now constrained by the 1,000 USDC limit and the 1-hour window.
3. Before `T1` is reached, the Safe owner (or a compromised owner) calls `setAllowance` again for the same route, setting the amount to 1,000,000 USDC and the expiry to `Timestamp T2` (1 year from now).
4. The previous constraint is immediately erased. The delegate can now drain 1,000,000 USDC, bypassing the "timelock" constraint that was supposedly active until `T1`. [1](#0-0) [2](#0-1) [3](#0-2)
