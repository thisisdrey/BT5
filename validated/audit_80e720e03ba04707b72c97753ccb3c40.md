Audit Report

## Title
Zero-valued remote delivery fee is silently accepted by `OutboundQueue::validate`, enabling underpriced Snowbridge message delivery - (File: `bridges/snowbridge/pallets/outbound-queue/src/lib.rs`)

## Summary
`Pallet::<T>::calculate_fee` derives `fee.remote` from `PricingParameters` via `saturating_mul`, `checked_div`, and `convert_from_ether_decimals`, and this derived value is never re-validated for non-zero after computation. [1](#0-0)  The pallet's own test proves that fully valid, non-zero `PricingParameters` (`exchange_rate = 1`, `fee_per_gas = 1`, `rewards = {1,1}`, `multiplier = 1`) can still yield `fee.remote == 0`, and `SendMessage::validate` in `send_message_impl.rs` returns this unchecked fee directly to the caller without any zero-check before ticket/message construction. [2](#0-1) 

## Finding Description
`PricingParameters::validate()` only checks the raw governance-set inputs (`exchange_rate`, `fee_per_gas`, `rewards.local/remote`, `multiplier`) for individually being non-zero. [3](#0-2)  The *derived* `fee.remote` computed in `calculate_fee` — after `saturating_mul(multiplier)`, `checked_div(exchange_rate)`, and `convert_from_ether_decimals` — is not checked against zero before being returned. [1](#0-0)  The existing unit test `test_calculate_fees_with_valid_exchange_rate_but_remote_fee_calculated_as_zero` demonstrates this rounding-to-zero outcome occurs with fully valid parameters. [4](#0-3)  `SendMessage::validate` calls `calculate_fee` and returns the resulting `Fee` tuple directly in the `Ok` ticket without any assertion that `fee.remote > 0`. [5](#0-4) 

However, I was unable to fully trace, within the available context, where and how the `Fee` value returned from `SendMessage::validate` is actually *collected/charged* from the caller (e.g., whether an XCM `BuyExecution`/withdrawal instruction enforces payment of `fee.local`/`fee.remote` before `deliver` is invoked, likely in the v1 exporter code in `bridges/snowbridge/primitives/outbound-queue/src/v1/`). The `deliver` function itself performs no fee-collection logic — it only checks the halted state and enqueues the message via `T::MessageQueue::enqueue_message`. [6](#0-5)  This means the actual fee charge is enforced by the XCM executor/exporter layer using the fee value from `validate`, not inside the outbound-queue pallet itself. Since `calculate_fee` is a `pub(crate)` internal helper, not a `pub` extrinsic, no unprivileged account directly calls it or chooses the pricing parameters — the parameters come from `T::PricingParameters::get()`, which is governance-controlled storage, not attacker-supplied input.

## Impact Explanation
The finding is real at the code level: a computed `fee.remote` can legitimately round to `0` under certain governance-set `PricingParameters` combinations, and neither `calculate_fee` nor `SendMessage::validate` rejects this degenerate case. This matches the "public underpriced work that degrades block production or stalls bridge processing" impact category, since messages could be enqueued for Ethereum-side dispatch without an adequate reward being collected. However, the condition depends on the specific governance-set `PricingParameters` (particularly a very low `exchange_rate`/`fee_per_gas` ratio relative to the ether-to-local decimal conversion divisor) being in effect at the time an unprivileged user submits a message — it is not something an attacker can trigger from arbitrary/default pricing parameters without those parameters already being close to degenerate. This is a genuine rounding/edge-case defect in `calculate_fee`, but its practical severity is bounded by the fact that realistic, sanely-configured `PricingParameters` (as used in other tests, e.g. yielding `fee.remote = 1000000` or `1333333`) do not trigger it.

## Likelihood Explanation
The zero-remote-fee condition is directly reproducible via the existing test `test_calculate_fees_with_valid_exchange_rate_but_remote_fee_calculated_as_zero` with minimal, individually-valid `PricingParameters`. [4](#0-3)  Whether this is reachable in production depends on the actual `PricingParameters` set by governance for BridgeHub; if configured with realistic exchange rates and gas prices (as in the non-degenerate test cases), the divisor and multiplier keep `fee.remote` well above zero. The likelihood is therefore conditional on governance parameter configuration rather than purely attacker-controlled.

## Recommendation
In `Pallet::<T>::calculate_fee`, add a check that the computed `fee.remote` (and ideally `fee.local`) is non-zero, returning a defensive fallback or rejecting via `SendError` if it is, or apply `saturating_add(1)`/rounding-up in `convert_from_ether_decimals` and `checked_div` to avoid the degenerate truncation-to-zero case shown in the test.

## Proof of Concept
Existing test in `bridges/snowbridge/pallets/outbound-queue/src/test.rs`:
```rust
#[test]
fn test_calculate_fees_with_valid_exchange_rate_but_remote_fee_calculated_as_zero() {
	new_tester().execute_with(|| {
		let gas_used: u64 = 250000;
		let price_params: PricingParameters<<Test as Config>::Balance> = PricingParameters {
			exchange_rate: FixedU128::from_rational(1, 1),
			fee_per_gas: 1_u32.into(),
			rewards: Rewards { local: 1_u32.into(), remote: 1_u32.into() },
			multiplier: FixedU128::from_rational(1, 1),
		};
		let fee = OutboundQueue::calculate_fee(gas_used, price_params.clone());
		assert_eq!(fee.local, 698000000);
		assert_eq!(fee.remote, 0);
	});
}
```
This confirms `calculate_fee` returns `fee.remote == 0` with valid, non-zero `PricingParameters`, and `SendMessage::validate` would propagate this zero fee to the caller without rejection. [5](#0-4)

		pub(crate) fn calculate_fee(
			gas_used_at_most: u64,
			params: PricingParameters<T::Balance>,
		) -> Fee<T::Balance> {
			// Remote fee in ether
			let fee = Self::calculate_remote_fee(
				gas_used_at_most,
				params.fee_per_gas,
				params.rewards.remote,
			);

			// downcast to u128
			let fee: u128 = fee.try_into().defensive_unwrap_or(u128::MAX);

			// multiply by multiplier and convert to local currency
			let fee = FixedU128::from_inner(fee)
				.saturating_mul(params.multiplier)
				.checked_div(&params.exchange_rate)
				.expect("exchange rate is not zero; qed")
				.into_inner();

			// adjust fixed point to match local currency
			let fee = Self::convert_from_ether_decimals(fee);

			Fee::from((Self::calculate_local_fee(), fee))
		}

	fn validate(
		message: &Message,
	) -> Result<(Self::Ticket, Fee<<Self as SendMessageFeeProvider>::Balance>), SendError> {
		// The inner payload should not be too large
		let payload = message.command.abi_encode();
		ensure!(
			payload.len() < T::MaxMessagePayloadSize::get() as usize,
			SendError::MessageTooLarge
		);

		// Ensure there is a registered channel we can transmit this message on
		ensure!(T::Channels::contains(&message.channel_id), SendError::InvalidChannel);

		// Generate a unique message id unless one is provided
		let message_id: H256 = message
			.id
			.unwrap_or_else(|| unique((message.channel_id, &message.command)).into());

		let gas_used_at_most = T::GasMeter::maximum_gas_used_at_most(&message.command);
		let fee = Self::calculate_fee(gas_used_at_most, T::PricingParameters::get());

		let queued_message: VersionedQueuedMessage = QueuedMessage {
			id: message_id,
			channel_id: message.channel_id,
			command: message.command.clone(),
		}
		.into();
		// The whole message should not be too large
		let encoded = queued_message.encode().try_into().map_err(|_| SendError::MessageTooLarge)?;

		let ticket = Ticket { message_id, channel_id: message.channel_id, message: encoded };

		Ok((ticket, fee))
	}

	fn deliver(ticket: Self::Ticket) -> Result<H256, SendError> {
		let origin = AggregateMessageOrigin::Snowbridge(ticket.channel_id);

		if ticket.channel_id != PRIMARY_GOVERNANCE_CHANNEL {
			ensure!(!Self::operating_mode().is_halted(), SendError::Halted);
		}

		let message = ticket.message.as_bounded_slice();

		T::MessageQueue::enqueue_message(message, origin);
		Self::deposit_event(Event::MessageQueued { id: ticket.message_id });
		Ok(ticket.message_id)
	}

	pub fn validate(&self) -> Result<(), InvalidPricingParameters> {
		if self.exchange_rate == FixedU128::zero() {
			return Err(InvalidPricingParameters);
		}
		if self.fee_per_gas == U256::zero() {
			return Err(InvalidPricingParameters);
		}
		if self.rewards.local.is_zero() {
			return Err(InvalidPricingParameters);
		}
		if self.rewards.remote.is_zero() {
			return Err(InvalidPricingParameters);
		}
		if self.multiplier == FixedU128::zero() {
			return Err(InvalidPricingParameters);
		}
		Ok(())
	}
