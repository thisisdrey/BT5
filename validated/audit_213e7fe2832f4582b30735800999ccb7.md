### Title
Integer overflow in ZIP central-directory bounds check enables out-of-bounds read - (File: `third_party/ijar/zip.cc`)

### Summary
`FindZipCentralDirectory()` in `third_party/ijar/zip.cc`, used by `ijar` (interface-jar generation for every `java_library`) and linked into Bazel's JAR-processing tools, validates that the ZIP central directory lies inside the mapped input file with an unchecked 64-bit addition. When a ZIP64 end-of-central-directory record is present, both operands are attacker-controlled 64-bit values read directly from the file, so the addition can wrap around and defeat the bounds check — the exact overflow class described in the external report (`uint(left + (right - left) / 2)` defeating an index-validity check).

### Finding Description
`FindZip64CentralDirectory()` reads `central_dir_size` and `central_dir_offset` as full 64-bit values straight from the (attacker-supplied) ZIP64 EOCD record via `get_u8le()`: [1](#0-0) 

These values are then used, without range restriction, in the containment check inside `FindZipCentralDirectory()`: [2](#0-1) 

`cd.central_dir_offset + cd.central_dir_size` is ordinary 64-bit unsigned addition. If an attacker sets `central_dir_offset` to a value close to `UINT64_MAX` and `central_dir_size` such that the sum wraps to a small number, the check `> in_length` evaluates false even though `central_dir_offset` is astronomically larger than the actual file length. `*offset` is then set to this huge value and `*central_dir` is computed as `end_of_central_dir - cd.central_dir_size` (also attacker-chosen), producing a pointer that need not lie within the mapped input buffer.

The caller, `InputZipFile::Open()`, uses this unchecked offset directly in pointer arithmetic to compute the read cursor: [3](#0-2) 

`in_offset_` is derived from `zipdata_start + central_dir_offset - central_dir`, all of which can be forced to point outside the `mmap`'d region of the input JAR by the crafted `central_dir_offset`/`central_dir_size` pair. Subsequent parsing (`ProcessCentralDirEntry`, `ProcessLocalFileEntry`) walks memory starting at this out-of-bounds cursor, reading file names, attributes, and file data from arbitrary process memory. That data is copied into the generated interface JAR (`processor->Process(...)`, `memcpy` of `filename`), i.e., adjacent-heap content can be exfiltrated into a build output artifact, or the read can simply crash the process reading unmapped memory.

The only guard within the surrounding format-level checks (`EnsureRemaining`) operates on the cursor `p` relative to `zipdata_in_`, but those checks come **after** `in_offset_`/`p` have already been derived from the overflowed offset — the invariant "central directory is contained within the file" that the addition is supposed to enforce is broken before any of the `EnsureRemaining` calls execute.

### Impact Explanation
An attacker who authors a ZIP/JAR file that a victim's build ingests (e.g., via `http_jar`, `http_archive`, a Maven artifact, or a JAR checked into a branch built by CI) can craft the ZIP64 end-of-central-directory record so the 64-bit offset/size sum overflows. This defeats the "central directory fits in file" containment check inside `ijar`'s ZIP parser, causing pointer arithmetic to escape the bounds of the memory-mapped input file. The result is an out-of-bounds read that can either crash the toolchain process or leak adjacent process memory bytes into the interface JAR / combined JAR that Bazel produces as a build output — a concrete container/pointer-containment violation reachable purely from untrusted archive bytes, matching the "Extraction and patching" surface (`ZipDecompressor`-class code) called out in scope.

### Likelihood Explanation
Exploitability requires the attacker to control the raw bytes of a ZIP/JAR file that is subsequently opened by `ijar`/`singlejar`-style tooling — which is routine for any externally-fetched `.jar` dependency or a JAR present in a source tree built by CI from an untrusted branch. Crafting a valid ZIP64 EOCD locator/record with attacker-chosen 64-bit offset/size fields requires no special privileges, only the ability to author or serve the archive; no MITM or credential access is needed.

### Recommendation
Perform the containment check using overflow-safe arithmetic, e.g., validate `central_dir_size <= in_length` and `central_dir_offset <= in_length - central_dir_size` (only after confirming `central_dir_size <= in_length`), or use 128-bit/`__builtin_add_overflow`-style overflow-checked addition, rejecting the archive if the check cannot be satisfied without wraparound. Apply the same fix to `MaybeReadZip64CentralDirectory`'s downstream consumers so that no unchecked offset ever participates in pointer arithmetic before the invariant is verified.

### Proof of Concept
A JUnit/`src/test/shell/bazel`-style reproduction would:
1. Construct a minimal ZIP file of small `in_length`.
2. Append a ZIP64 EOCD record with `central_dir_size = S` and `central_dir_offset = 2^64 - S + k` for small `k < in_length`, so `offset + size` wraps to `k`, passing `k > in_length` as false.
3. Point `ijar`/`InputZipFile::Open()` at this file and observe that `central_dir_offset` returned is far larger than `in_length`, and that subsequent parsing reads/derefs memory outside the mapped file region (observable via a sanitizer build, e.g., ASan reporting a heap-buffer-overflow read in `InputZipFile::ProcessCentralDirEntry` / `ProcessLocalFileEntry`). bool FindZip64CentralDirectory(const u1 *bytes, size_t in_length,
                               const u1 **end_of_central_dir,
                               EndOfCentralDirectoryRecord *cd) {
  // In the absence of a zip64 extensible data sector, the zip64 EOCD is at a
  // fixed offset from the regular central directory.
  if (MaybeReadZip64CentralDirectory(
          bytes, in_length,
          *end_of_central_dir - ZIP64_EOCD_LOCATOR_SIZE - ZIP64_EOCD_FIXED_SIZE,
          end_of_central_dir, cd)) {
    return true;
  }

  // If we couldn't find a zip64 EOCD at a fixed offset, either it doesn't exist
  // or there was a zip64 extensible data sector, so try going through the
  // locator. This approach doesn't work if data was prepended to the archive
  // without updating the offset in the locator.
  const u1 *zip64_locator = *end_of_central_dir - ZIP64_EOCD_LOCATOR_SIZE;
  if (zip64_locator - ZIP64_EOCD_FIXED_SIZE < bytes) {
    return true;
  }
  u4 zip64_locator_signature = get_u4le(zip64_locator);
  if (zip64_locator_signature != ZIP64_EOCD_LOCATOR_SIGNATURE) {
    return true;
  }
  u4 disk_with_zip64_central_directory = get_u4le(zip64_locator);
  u8 zip64_end_of_central_dir_offset = get_u8le(zip64_locator);
  u4 zip64_total_disks = get_u4le(zip64_locator);
  if (MaybeReadZip64CentralDirectory(bytes, in_length,
                                     bytes + zip64_end_of_central_dir_offset,
                                     end_of_central_dir, cd)) {
    // TODO(b/228519294) Add a test for a valid zip64 file with total disks = 0
    if (disk_with_zip64_central_directory != 0 || zip64_total_disks > 1) {
      fprintf(stderr, "multi-disk JAR files are not supported\n");
      return false;
    }
    return true;
  }
  return true;
}
