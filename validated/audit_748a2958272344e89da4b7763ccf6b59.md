## Analysis

I traced the external report's core invariant — *a caller/attacker-controlled address that determines where value flows is never checked against a system registry before funds move* — into the Snowbridge `outbound-queue-v2` delivery-receipt flow, which is exactly the "Snowbridge delivery flow" area named in the task scope.

`Pallet::process_delivery_receipt` decodes a `DeliveryReceipt` (which includes a `success: bool` field, decoded from the Ethereum `InboundMessageDispatched` event) but never inspects `receipt.success` before paying out the relayer's fee: [1](#0-0) [2](#0-1) 

The extrinsic entry point only checks the origin is signed and that the event proof verifies and decodes; it never uses `receipt.success` either: [3](#0-2) 

### Title
Snowbridge outbound-queue-v2 pays relayer reward on failed message execution because `DeliveryReceipt.success` is never checked - (File: bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs)

### Summary
`process_delivery_receipt` settles a `PendingOrder` and pays the associated fee purely based on the existence of a nonce entry and a matching Gateway address. It decodes `receipt.success` from the Ethereum event but discards it, so a relayer is rewarded and the order is removed regardless of whether the corresponding message actually executed successfully on Ethereum.

### Finding Description
The `InboundMessageDispatched` Solidity event carries a `success` flag indicating whether the outbound command was actually executed successfully on the Ethereum Gateway contract: [4](#0-3) 

`DeliveryReceipt::try_from` faithfully decodes this field into `DeliveryReceipt.success`: [5](#0-4) 

However, `process_delivery_receipt` only checks:
1. `receipt.gateway == T::GatewayAddress::get()` (correct contract), and
2. that `PendingOrders` contains the nonce,

then unconditionally pays `order.fee` to the reward account and removes the order — the `success` field is never read: [6](#0-5) 

This breaks the pivot requirement that "message queues, bridge markers, receipts, and payout state must only advance after decode, dispatch, execution, and settlement succeed atomically." Here settlement (fee payout, order removal) is decoupled from execution success: a message that failed to execute on Ethereum (`success = false`) still causes the pending order to be paid out and cleared exactly as if it had succeeded. Since any relayer can call `submit_delivery_receipt` with a legitimately-verified proof for a message whose execution reverted or failed on the Ethereum side (a normal, unprivileged, permissionless operation — no malicious relayer/validator assumption required, since the event and proof are real, just reporting `success=false`), the relayer is paid for work whose intended effect never materialized.

### Impact Explanation
This directly maps to "public underpriced work that degrades … stalls bridge processing" and "duplicate settlement or payout" categories in the impact gate: relayers get compensated for messages that failed on the Ethereum side, without any retry/re-delivery accounting, silently draining the reward pool for commands that never had their intended effect. Because `PendingOrders` is removed unconditionally, there is also no path left to reconcile or re-attempt the failed command — the bridge's fee-for-service guarantee is broken and reward funds are paid for no completed work.

### Likelihood Explanation
Likelihood is high: `submit_delivery_receipt` is a permissionless, signed extrinsic; `success=false` is a normal outcome path for Ethereum-side execution (e.g., an outbound command that reverts due to gas exhaustion, contract-level checks, or execution errors unrelated to relay honesty). No privileged actor, governance, or malicious relayer/validator assumption is required — a normal relayer submitting a normal (verified) proof for a normal execution failure triggers the payout.

### Recommendation
In `process_delivery_receipt`, branch on `receipt.success`: only pay `order.fee` and treat the order as settled when `receipt.success == true`. On failure, either leave the `PendingOrder` for re-delivery/retry handling or handle it through a distinct failure-settlement path (e.g., no reward, and/or explicit event indicating failed execution), instead of paying out and removing the order unconditionally.

### Proof of Concept
1. A message is queued and a `PendingOrder{nonce, fee}` is created via `do_process_message` (normal flow).
2. On Ethereum, the Gateway contract execution of the corresponding command fails/reverts for a legitimate reason (e.g. downstream call failure), emitting `InboundMessageDispatched(nonce, topic, success=false, reward_address)`.
3. A relayer builds a valid Merkle/receipt proof for this real (unmodified) event log and calls `submit_delivery_receipt(origin, event)`.
4. `T::Verifier::verify` succeeds (the proof is genuine), `DeliveryReceipt::try_from` decodes `success = false` correctly.
5. `process_delivery_receipt` checks only the gateway address and nonce existence, ignores `success`, and calls `T::RewardPayment::register_reward(&reward_account, ..., order.fee)`, then removes the `PendingOrder`.
6. Result: the relayer (or specified `reward_address`) is paid the full fee even though `success == false`, and the failed order can never be retried since it has been deleted from `PendingOrders`.

This confirms the analog to the AstariaRouter bug: a value present in attacker/relayer-controlled decoded input (`success`) that should gate a fund-moving/settlement action is decoded but never checked, allowing settlement to proceed as if the guarded condition held.

		/// Process a delivery receipt from a relayer, to allocate the relayer reward.
		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}
