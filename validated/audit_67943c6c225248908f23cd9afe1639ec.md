### Title
Anti-replay window Check/Update race allows message counter replay bypass - ([File: connection_state.go])

### Summary
`ConnectionState.Decrypt` and `ConnectionState.VerifyRelay` split the anti-replay bookkeeping into two separate critical sections: `window.Check()` is called and the lock released, decryption then happens *without holding the lock*, and only afterwards is the lock re-acquired to call `window.Update()`. This mirrors the FrankenDAO bug class: a stateful counter/window is read in one step and mutated in a later, disjoint step, so the "current" state used to decide correctness is stale by the time the mutation happens, allowing the same input to be treated as valid twice under concurrency.

### Finding Description
`Bits.Check` and `Bits.Update` together implement Nebula's sliding-window replay-protection for the Noise transport counter. `Decrypt` uses this pattern: [1](#0-0) 

The `decryptLock` is locked only around `Check`, released, then re-locked only around `Update`, with the actual AEAD decryption happening in between, outside the lock. `VerifyRelay` follows the identical pattern: [2](#0-1) 

`Bits.Check` only inspects state (it never mutates `b.bits` or `b.current`): [3](#0-2) 

`Bits.Update` is the only function that actually marks a counter as seen: [4](#0-3) 

Because `Check` and `Update` for the *same* `messageCounter` are not performed as a single atomic operation, if two goroutines invoke `Decrypt`/`VerifyRelay` for the same `ConnectionState` concurrently with the same (replayed) `messageCounter` — e.g. an attacker resending a captured on-wire packet while the original is still in flight, and Nebula's packet-handling dispatches it to a different worker/goroutine — both calls can observe `Check()==true` before either has called `Update()` to mark the counter as consumed. Both goroutines then proceed to perform a full AEAD decrypt of the (identical) ciphertext with the replayed counter. This is exactly the class of bug in the source report: a shared piece of accounting state (`tokenVotingPower`/here, the replay bitmap `b.bits`/`b.current`) is read for a decision, and the corresponding update is applied later based on assumptions about ordering that don't hold when the intervening step can interleave with another actor's read of the same state.

### Impact Explanation
This breaks the confidentiality/integrity guarantee that Nebula's Noise-based transport is supposed to provide: a captured, previously-sent ciphertext packet can be successfully decrypted and delivered to the TUN device a second time under race conditions, defeating the anti-replay protection that `ReplayWindow`/`Bits` exists to enforce. Depending on the payload (e.g., replayed ARP/DHCP-like control-plane traffic, or any idempotent-looking application data), this can result in duplicate delivery of attacker-replayed traffic to the receiving host's overlay interface, which is the concrete "replay" impact category called out in scope.

### Likelihood Explanation
This requires: (1) an attacker able to capture and resend a genuine UDP packet on the wire (no CA-signed certificate needed — this is purely at the encrypted-transport layer, after a tunnel is already up between two other parties, and only requires the attacker to duplicate/replay an observed UDP datagram), and (2) two decrypt calls for that same `ConnectionState` executing concurrently so the `Check`/`Update` window is hit. Whether Nebula's outside-packet reader dispatches packets for a single tunnel across multiple concurrent goroutines was not fully confirmed in this pass (I found references to `readOutsidePackets`/worker-related code in `interface.go` and `outside.go` but did not have remaining tool budget to verify the exact concurrency model). If reads for a given remote/tunnel are strictly single-threaded per connection, the race window narrows to genuinely concurrent decrypt paths (e.g. relay verification vs. normal decrypt, which do share the same `window`/`decryptLock`) — this still creates the same TOCTOU exposure. I cannot fully confirm the precise scheduling likelihood without further investigation of the UDP read dispatch path.

### Recommendation
Make the check-and-mark operation atomic: hold `decryptLock` across the entire `Check → Decrypt → Update` sequence in both `Decrypt` and `VerifyRelay`, or collapse `Check`+`Update` into a single locked "reserve-and-verify" method on `Bits` that atomically tests-and-sets the counter bit before decryption is attempted, only rolling back the reservation if decryption subsequently fails.

### Proof of Concept
1. Establish a tunnel between two Nebula nodes so a `ConnectionState` with an active `window *Bits` exists.
2. Have the attacker capture one legitimate encrypted UDP packet (`messageCounter = N`) in transit.
3. Immediately re-inject (replay) that exact packet, timed so it is processed by a concurrent decrypt path/goroutine before the original packet's `window.Update(N)` call has completed and released `decryptLock`.
4. Because `Check(N)` for the replayed copy can still observe `b.current < N` / bit for `N` unset (since `Update` for the original hasn't run yet), the replay passes the replay check, proceeds through AEAD decryption, and is only rejected at the very end if `Update` happens to run second — by which point the decrypted plaintext may already have been used/forwarded by the first successful path, demonstrating that the replay window is not enforced atomically.

func (cs *ConnectionState) VerifyRelay(l *slog.Logger, messageCounter uint64, packet []byte, nb []byte) error {
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	signedPayload := packet[:len(packet)-cs.dKey.Overhead()]
	signatureValue := packet[len(packet)-cs.dKey.Overhead():]
	_, err := cs.dKey.DecryptDanger(nil, signedPayload, signatureValue, messageCounter, nb)
	if err != nil {
		return err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	return nil
}

// Check returns true if i is within (or way out in front of) the window, and not a replay
func (b *Bits) Check(l *slog.Logger, i uint64) bool {
	// If i is the next number, return true.
	if i > b.current {
		return true
	}

	if b.strictlyWithinWindow(i) {
		return !b.get(i)
	}

	// Not within the window
	if l.Enabled(context.Background(), slog.LevelDebug) {
		l.Debug("rejected a packet (top)", "current", b.current, "incoming", i)
	}
	return false
}

func (b *Bits) Update(l *slog.Logger, i uint64) bool {
	// Fast path: i is the next expected counter. Split out so the function
	// stays small and avoids paying for the slow paths' slog argument-build
	// stack frame on every call. The bit read/test/write is inlined to
	// touch the backing word once.
	if i == b.current+1 {
		pos := i & b.lengthMask
		word := pos >> 6
		mask := uint64(1) << (pos & 63)
		w := b.bits[word]
		if i > b.length && w&mask == 0 {
			b.lostCounter.Inc(1)
		}
		b.bits[word] = w | mask
		b.current = i
		return true
	}
	return b.updateSlow(l, i)
}
