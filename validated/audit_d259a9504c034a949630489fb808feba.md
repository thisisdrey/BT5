### Title
Same-block DeleteKey+AddKey re-creation can reseed nonce below an already-consumed nonce, enabling replay of an old transaction - ([File: runtime/runtime/src/access_keys.rs], [File: runtime/runtime/src/verifier.rs])

### Finding Description
`AccessKey::ACCESS_KEY_NONCE_RANGE_MULTIPLIER` reseeding is designed so that when a public key is re-added after deletion, its new nonce floor is always higher than any nonce ever consumed under that pubkey, preventing replay (per near/nearcore#3779). The reseed value is computed purely from `apply_state.block_height` at `AddKey` time via `initial_nonce_value`: [1](#0-0) 

and consumed transaction nonces are bounded only by `tx_nonce < block_height * ACCESS_KEY_NONCE_RANGE_MULTIPLIER` at the height the transaction is processed: [2](#0-1) 

Both checks use the *same* `apply_state.block_height` for every transaction processed in a given chunk (`add_regular_key` at `runtime/runtime/src/access_keys.rs:230-255` uses `apply_state.block_height` passed from `action_add_key`, and `verify_nonce`'s `block_height` at execution time is also `processing_state.apply_state.block_height`, see `runtime/runtime/src/lib.rs:2054`). The invariant "reseed value > any nonce ever consumed for that pubkey" only holds when the `AddKey` transaction is applied at a block height *strictly greater* than the height at which the old, high-value nonce was consumed. If `DeleteKey(K)` + `AddKey(K)` (signed by a second full-access key `K2` on the same account) are included in the **same chunk** as a `tx1` (signed by `K`) that consumed nonce `n` close to the upper bound (`n` up to `H*1_000_000 - 1`), then `initial_nonce_value(H) = (H-1)*1_000_000` is up to `999_999` lower than `n`. Any old, previously-signed-but-not-yet-broadcast transaction from `K` with a nonce in `((H-1)*1_000_000, n)` becomes valid again against the recreated key `K` (Monotonic mode only requires `tx_nonce > current_nonce`), because `current_nonce` was reset far below `n`.

Transactions from `K` (tx1) and `K2` (DeleteKey/AddKey) belong to independent nonce sequences, so nothing in the mempool/chunk-preparation logic enforces that `tx1` and the `AddKey` land in different blocks; `process_transactions` applies whichever transactions the chunk producer selected, in the order they appear in the chunk, all under one fixed `apply_state.block_height`. No code path checks "was this pubkey ever used with a nonce higher than the new reseed value" — the reseed logic trusts block-height monotonicity alone, which is violated within a single chunk.

### Impact Explanation
This is a double-spend/replay-prevention violation: an old, already-executed transaction can be re-executed against the same account/public key after a DeleteKey+AddKey cycle, letting the signer replay a stale transaction (e.g., replaying an old transfer, function call, or any action) that should be permanently invalidated. This matches the "double-spend/replay" bounty category.

### Likelihood Explanation
Preconditions: control of the target account (attacker's own account, unprivileged), a second full-access key `K2` already present on the account, and getting `tx1` (nonce near `H*1_000_000-1`), `DeleteKey(K)`, and `AddKey(K)` included in the exact same chunk/block, with `DeleteKey` applied after `tx1`'s nonce consumption and before `AddKey`. Ordering across different signer public keys within a chunk is decided by mempool/chunk-preparation grouping, not directly controllable by the attacker, so success is not deterministic per attempt, but the attack is fully repeatable (retry across blocks) and costs only ordinary transaction fees — no validator, RPC-operator, or peer privilege is required. This makes it a probabilistic but realistic and reproducible attack given multiple attempts.

### Recommendation
Do not rely solely on block height monotonicity across the whole chain for nonce-reseed safety. When reseeding a re-created access key's nonce, also read the deleted key's previous nonce (or track a per-(account,pubkey) "highest nonce ever consumed" watermark), and set the new nonce to `max(initial_nonce_value(block_height), previous_nonce)`. Alternatively, reject `DeleteKey` followed by `AddKey` of the same public key within the same chunk, or bump `initial_nonce_value` using a chunk-local sequence counter in addition to block height so within-chunk re-creation can never undercut nonces already consumed earlier in the same chunk.

### Proof of Concept
Runtime-level unit test plan (using `runtime/runtime/src/access_keys.rs` test scaffolding, e.g. `setup_account_with_tries`):
1. At `block_height = H`, apply a transaction from key `K` with `tx_nonce = H*1_000_000 - 1` (passes `verify_nonce` upper bound `< H*1_000_000`); assert `access_key.nonce == H*1_000_000 - 1`.
2. In the *same* apply call (`block_height = H`), apply `DeleteKey(K)` signed by `K2`, then `AddKey(K)` (full access) signed by `K2`; assert the new `access_key.nonce == (H-1)*1_000_000`.
3. Construct an old signed transaction from `K` with `tx_nonce` in `((H-1)*1_000_000, H*1_000_000 - 1)` and call `verify_and_charge_tx_ephemeral`/`verify_nonce` against the recreated key; assert it returns `TxVerdict::Success` (replay succeeds) instead of `InvalidTxError::InvalidNonce`.
4. Assert the invariant violation: `initial_nonce_value(H) < n` where `n` is the nonce consumed in step 1 at the same height `H`.

pub(crate) fn initial_nonce_value(block_height: BlockHeight) -> Nonce {
    // Set default nonce for newly created access key to avoid transaction hash collision.
    // See <https://github.com/near/nearcore/issues/3779>.
    (block_height - 1) * near_primitives::account::AccessKey::ACCESS_KEY_NONCE_RANGE_MULTIPLIER
}
