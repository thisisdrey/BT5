### Title
Contract owner can front-run and change `consumeUserResourcePercent` via `UpdateSettingContract` while a victim's transaction is pending/in-flight, forcing unexpected energy cost onto the caller - (File: actuator/src/main/java/org/tron/core/actuator/UpdateSettingContractActuator.java)

### Summary
The Sherlock report describes an NFT-auction owner mutating `timeBuffer`/`minBidIncrement` (economic parameters that govern an already-active, ongoing interaction) with no restriction tied to the state of that ongoing interaction, unfairly changing the rules for participants who already committed to it. The closest reachable analog in java-tron is `UpdateSettingContractActuator`, which lets a smart-contract's origin address change `consume_user_resource_percent` for a deployed contract at any time, taking effect immediately for the very next transaction, with no cooldown, timelock, or check against transactions that are already pending/broadcast against that contract.

### Finding Description
`UpdateSettingContractActuator.execute()` directly overwrites the contract's `consume_user_resource_percent` field in `ContractStore` as soon as the `UpdateSettingContract` transaction is packed into a block, and immediately invalidates the LRU cache so the new value is used by the very next transaction that touches the contract: [1](#0-0) 

`validate()` only checks that the caller is the contract's origin address and that the new percent is within `[0, 100]` — it performs no check on whether other transactions are currently targeting the contract in the same block, or any grace period before the new setting becomes effective: [2](#0-1) 

This `consume_user_resource_percent` value is the parameter that determines how much of a TVM call's energy cost is charged to the calling account versus paid from the contract's `origin_energy_limit` budget (analogous logic is used by `VMActuator` when constructing the energy processor for a call). A caller who signs and broadcasts a transaction to the contract, expecting a certain percentage of energy fees to be paid by the contract, has no guarantee that this percentage will still hold by the time their transaction is actually executed, exactly mirroring the original bug where bidders in an active auction had no guarantee that `minBidIncrement`/`timeBuffer` would remain unchanged once they placed (or were about to place) a bid.

### Impact Explanation
Since the origin can raise `consume_user_resource_percent` to 100 immediately before a known pending transaction from another user executes, that user is forced to pay energy fees (billed in TRX, drawn from frozen energy or the account's own TRX balance for burn) far above what they anticipated when signing and broadcasting the transaction. This is an unauthorized/unexpected drain of the caller's resources/funds caused solely by a privileged party's ability to mutate a fee-determining parameter with no restriction tied to already-in-flight interactions — the same root cause class as the reported issue (uncontrolled parameter mutation affecting an ongoing/committed operation).

### Likelihood Explanation
Any account that is the `originAddress` of a deployed contract can call this actuator at will via the exposed `/wallet/updatesetting` HTTP endpoint or gRPC — this requires no special permission beyond being the contract owner, and can be timed to precede a specific victim transaction the owner observes in the mempool. Given java-tron's mempool visibility, front-running such a change against a specific pending call is straightforward.

### Recommendation
Add a mitigation similar to the `if (block.timestamp < auction.endTime) revert(...)` pattern recommended in the report: enforce a delay/cooldown (e.g. only allow the new `consume_user_resource_percent` to take effect starting from a future block, or after a minimum interval since the last update) so that transactions already broadcast/pending against the contract cannot be retroactively subjected to a worse fee-split within the same block window.

### Proof of Concept
1. Attacker deploys a contract and sets `consume_user_resource_percent` to a low value (e.g. 0) so that callers expect the contract's `origin_energy_limit` to cover most energy costs.
2. A victim observes this setting, prepares and broadcasts a `TriggerSmartContract` transaction expecting low energy cost.
3. Before the victim's transaction is packed, the attacker (contract origin) broadcasts an `UpdateSettingContract` transaction raising `consume_user_resource_percent` to 100 with a higher fee/priority so it is processed first in the same or an earlier block — reference execution path: [1](#0-0) 
4. The victim's transaction subsequently executes under the new 100% setting, causing the victim to be billed for energy that they did not expect to pay, with no on-chain mechanism preventing this timing attack.
