### Title
Unbounded array allocation from attacker-controlled length in TVM `BatchValidateSign`/`ValidateMultiSign` precompiles - ([File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java])

### Summary
`PrecompiledContracts.extractBytesArray()` and `extractBytes32Array()` allocate Java arrays (`new byte[len][]`) sized directly by an attacker-controlled 32-byte word taken from the precompile call data, with no upper bound and no validation against the actual remaining call-data size before allocation. This is analogous to the adm-zip flaw: a size/count field read from untrusted input is used to size a memory allocation before any correctness check against the real payload size.

### Finding Description
`extractBytesArray` and `extractBytes32Array` read `len` straight from `words[offset].intValueSafe()`: [1](#0-0) 

`extractBytes32Array` has no bound at all on `len`, and `extractBytesArray` only guards `offset > words.length - 1`, not `len` itself, before doing `new byte[len][]`.

These helpers are invoked from the `ValidateMultiSign` (address `0x...0a`) and `BatchValidateSign` (address `0x...09`) precompiled contracts, both of which are reachable by any account via a plain `CALL`/`STATICCALL` TVM opcode to the fixed precompile address — no special permission is required: [2](#0-1) [3](#0-2) 

Critically, the bound check (`sigArraySize > MAX_SIZE` / `addrArraySize > MAX_SIZE`) that was added to fix a related issue is gated behind `VMConfig.allowTvmSelfdestructRestriction()` — a chain parameter (`ALLOW_TVM_SELFDESTRUCT_RESTRICTION`) whose stored default is `0` (disabled) unless a committee proposal has explicitly activated it: [4](#0-3) 

When this flag is not active (e.g., a private/consortium chain, a testnet, or any deployment that hasn't yet passed the `ALLOW_TVM_SELFDESTRUCT_RESTRICTION` proposal), `extractBytesArray`/`extractBytes32Array` are invoked with a completely unchecked `len`, allowing a crafted 32-byte word (e.g., close to `Integer.MAX_VALUE`) to trigger `new byte[len][]`. Even a modest `len` in the tens/hundreds of millions is enough to exhaust heap and trigger `OutOfMemoryError`, since each element of a `byte[][]` array itself needs a reference slot (4–8 bytes) allocated eagerly regardless of the actual bytes supplied in call data — mirroring the adm-zip pattern where the declared size is trusted before any correlation with the real payload size.

### Impact Explanation
An `OutOfMemoryError` thrown inside precompile execution during transaction processing can crash or destabilize the node process depending on how/where it propagates (JVM-wide OOM conditions frequently affect other threads, including consensus and networking threads, not just the one throwing). Because any account can invoke this precompile via a single contract call (broadcastable by an unprivileged transaction sender/contract deployer), this is a network-wide denial-of-service vector against any node still running with the guarding proposal disabled.

### Likelihood Explanation
Exploitability depends entirely on the `ALLOW_TVM_SELFDESTRUCT_RESTRICTION` chain parameter being inactive. On networks where this proposal has already been passed (e.g., long-running TRON mainnet past `VERSION_4_8_1`), the guard is in effect and this path is not reachable in its vulnerable form. However, for any fresh/private/test deployment of this codebase, or any chain that has not yet passed the proposal, the flag defaults to `0`, leaving the unbounded-allocation path open to any caller with no cost/permission barrier beyond normal TVM energy accounting (and the energy formula itself does not scale with the maliciously large `len` used inside `extractBytesArray`/`extractBytes32Array`, since energy is computed from `data.length`, not from the parsed array-length header).

### Recommendation
Move the `sigArraySize`/`addrArraySize` bound checks (`> MAX_SIZE`) outside the `VMConfig.allowTvmSelfdestructRestriction()` gate so they are always enforced regardless of whether that proposal has been activated, and add an explicit upper bound check inside `extractBytesArray` and `extractBytes32Array` themselves (e.g., reject if `len` exceeds a small constant such as `MAX_SIZE`, or if `len` is inconsistent with the remaining `words.length`) before allocating the backing array.

### Proof of Concept
1. Deploy/target a contract that issues `CALL` to precompiled address `0x...0a` (`ValidateMultiSign`) or `0x...09` (`BatchValidateSign`) with ABI-encoded call data where the signatures-array length word (the word at the offset pointed to by `words[3]` for `ValidateMultiSign`, or `words[1]`/`words[2]` for `BatchValidateSign`) is set to a very large value (e.g., `0x7FFFFFFF`).
2. On a node where `ALLOW_TVM_SELFDESTRUCT_RESTRICTION` has not been activated (`allowTvmSelfdestructRestriction() == false`, the store default), the precompile calls `extractBytesArray`/`extractBytes32Array` directly, which executes `new byte[0x7FFFFFFF][]` before any signature/address content is read or validated.
3. This allocation attempt exhausts JVM heap, throwing `OutOfMemoryError` during transaction execution, potentially destabilizing the node process — reachable from a single unauthenticated/unprivileged transaction.

  private static byte[][] extractBytes32Array(DataWord[] words, int offset) {
    int len = words[offset].intValueSafe();
    byte[][] bytes32Array = new byte[len][];
    for (int i = 0; i < len; i++) {
      bytes32Array[i] = words[offset + i + 1].getData();
    }
    return bytes32Array;
  }

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }

  public void saveAllowTvmSelfdestructRestriction(long value) {

  public boolean allowTvmSelfdestructRestriction() {
