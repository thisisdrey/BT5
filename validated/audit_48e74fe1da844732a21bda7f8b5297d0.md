### Title
Unprivileged clients can grief a victim's operations on a shared repository by exhausting Gitaly's per-repository concurrency queue - (File: internal/grpc/middleware/limithandler/middleware.go)

### Summary
Gitaly's per-RPC/per-repository concurrency limiter keys its concurrency and queue tokens purely on the target repository's relative path, not on the calling user/identity. Any client that is able to invoke a rate-limited RPC against a given repository (e.g. a clone/fetch on a public project, or any member of a shared object-pool/fork network) can cheaply saturate that repository's concurrency slot and queue, causing a legitimate, time-sensitive request from a different user against the *same* repository to be rejected with `ResourceExhausted`. This mirrors the Paraspace bug class: a limited, per-target resource (there: NFT collateral balance slots; here: concurrency/queue tokens) is shared and can be filled by a third party who does not own the target, denying the intended actor's legitimate operation exactly when they need it — including as a front-running-style attack.

### Finding Description
`LimitConcurrencyByRepo` derives the lock key solely from the repository's relative path, independent of caller identity: [1](#0-0) 

This key is used by `ConcurrencyLimiter.Limit` to select a `keyedConcurrencyLimiter` shared by *every* caller hitting that RPC against that repository: [2](#0-1) 

The keyed limiter enforces a `max_per_repo` concurrency semaphore plus a bounded `max_queue_size` admission queue. Once both the concurrency slot(s) and the queue are full, all further requests for that repo/RPC are immediately rejected with `ErrMaxQueueSize`, regardless of who is making them: [3](#0-2) [4](#0-3) 

This behavior is intentional backpressure per the design doc, which explicitly limits "the number of concurrent RPCs that are in flight on each Gitaly node for each repository per RPC," with configuration such as `max_per_repo = 1`: [5](#0-4) [6](#0-5) 

Because the limiting key has no user/session component, any actor who can trigger the configured RPC against the same repository — e.g. any user with read/fetch access to a public repository, or any member of an object-pool/fork network sharing the pooled repository housekeeping RPCs — can occupy the concurrency slot(s) and fill the queue cheaply and repeatedly (issuing many concurrent requests costs the attacker little beyond opening connections/streams). A legitimate user attempting the same RPC against the same repository at that moment (e.g. `OptimizeRepository`, `PostUploadPackWithSidechannel`, or any other RPC configured under `[[concurrency]]`) will then be denied service via `ResourceExhausted`, exactly analogous to Bob's `NTOKEN_BALANCE_EXCEEDED` failure being caused by Alice's cheap third-party action filling a shared, target-keyed limited resource.

For streaming RPCs the same shared-key limiting applies on the first message of the stream, so an attacker can hold open many streams (each cheap to open, since work only begins once the limiter admits it) to keep the queue continuously saturated: [7](#0-6) 

### Impact Explanation
This is a denial-of-service of an RPC handler: it does not corrupt data or bypass authorization, but it lets a third party who shares access to a repository (fork network member, other member with fetch/read access, or another mutator on a shared repo) deny legitimate, potentially time-critical operations (e.g. `OptimizeRepository`/housekeeping, uploads/fetches) for other actors on that same repository, purely by cheaply flooding requests. Because the key is target-scoped rather than caller-scoped, the "victim" has no way to protect their own request from being crowded out by an unrelated party's cheap requests against the same repo.

### Likelihood Explanation
Requires: (1) a `[[concurrency]]` limit configured for the targeted RPC (this is an opt-in, admin-configured feature, commonly recommended for expensive RPCs like `OptimizeRepository` or `PostUploadPackWithSidechannel`), and (2) the attacker having any access sufficient to invoke that RPC against the shared repository (e.g., clone/fetch access to a public project, or membership of an object-pool network). Both preconditions are realistic in typical GitLab deployments that use Gitaly's documented concurrency-limiting backpressure feature and that host public/forkable repositories, making the likelihood moderate. The attack itself is cheap (repeated concurrent RPC invocations), similar in cost profile to the Uniswap V3 minting/removing-liquidity trick used in the referenced report.

### Recommendation
Consider making the concurrency/queue limiting key caller-aware in addition to repository-aware (e.g., composite key of repository + authenticated identity/IP) for at least a portion of the queue slots, or reserve a fraction of queue capacity per caller/session so that one actor cannot exhaust the entire shared queue for a repository. Alternatively, document and encourage separate unauthenticated vs. per-identity limiter partitions (as already exists for `Unauthenticated` limits) to be extended to authenticated callers, and expose metrics/alerts on `requestsDroppedMetric` spikes tied to a single caller so operators can detect this griefing pattern.

### Proof of Concept
1. Configure Gitaly with a tight per-repository concurrency limit, e.g.:
```toml
[[concurrency]]
rpc = "/gitaly.RepositoryService/OptimizeRepository"
max_per_repo = 1
max_queue_wait = "1m"
max_queue_size = 10
```
(matching the shape shown in `config.toml.example`, [8](#0-7) )
2. As "Alice" (any actor with permission to call `OptimizeRepository` on the target shared repository — e.g., a member of the same fork/object-pool network), open `max_per_repo + max_queue_size` (here, 11) concurrent `OptimizeRepository` calls against the repository and keep them pending (or repeatedly re-issue them just as slots free up).
3. "Bob," a legitimate user needing to run `OptimizeRepository` on the very same repository at that time, issues the same RPC and receives a `ResourceExhausted` error with `gitalypb.LimitError{ErrorMessage: "maximum queue size reached", ...}`, as produced in `ConcurrencyLimiter.Limit`: [9](#0-8) 
This is directly demonstrated in the existing test harness pattern for queue exhaustion: [10](#0-9) 
4. Because the lock key is `info.Repository.GetRelativePath()` only, Bob's request is blocked purely because of Alice's unrelated, cheap flood, without Bob having any way to differentiate his slot from Alice's.

// acquire tries to acquire the semaphore. It may fail if the admission queue is full or if the max
// queue-time ticker ticks before acquiring a concurrency token.
func (sem *keyedConcurrencyLimiter) acquire(ctx context.Context, limitingKey string) (returnedErr error) {
	if sem.queueTokens != nil {
		// Try to acquire the queueing token. The queueing token is used to control how many
		// callers may wait for the concurrency token at the same time. If there are no more
		// queueing tokens then this indicates that the queue is full and we thus return an
		// error immediately.
		if err := sem.queueTokens.TryAcquire(); err != nil {
			return err
		}

**File:** doc/backpressure.md (L33-42)
```markdown
An in-memory queue of requests can build up in Gitaly that are waiting their turn. Because
this is a potential vector for a memory leak, two other values in the `[[concurrency]]`
configuration can prevent an unbounded in-memory queue of requests:

- `max_queue_wait` is the maximum amount of time a request can wait in the
  concurrency queue. When a request waits longer than this time, it returns
  an error to the client.
- `max_queue_size` is the maximum size the concurrency queue can grow for a
  given RPC. If a concurrency queue is at its maximum, subsequent requests
  return with an error. The queue size is per repository.
```
