## Title
Wallet Contract pays the relayer fee unconditionally before validating the target address, enabling unbounded fee-draining replay by a malicious relayer - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The eth-implicit `WalletContract`'s `inner_rlp_execute` dispatches the relayer's compensation ("fee") as an independent, immediately-fired promise before the transaction's target/address validity has actually been confirmed. For the `EOABaseTokenTransfer{ address_check: Some(_) }` case, this fee payment happens *before* the async registrar lookup that determines whether the relayer's chosen `target` was actually valid, and critically, the nonce is **not** incremented if that lookup reveals the relayer was faulty. This decoupling of "amount paid" from "the validated outcome that was supposed to justify the payment" mirrors the Connext bug class: two values (fee sent vs. actual validated/successful service) are allowed to diverge, letting value be extracted repeatedly at the wallet owner's expense.

### Finding Description
In `inner_rlp_execute` [1](#0-0) , the fee refund to the relayer (`predecessor_account_id`) is sent via a standalone `promise_batch_create`/`promise_batch_action_transfer` pair, unconditionally, as soon as `parse_rlp_tx_to_action` returns an `EOABaseTokenTransfer` or `ERC20Transfer` kind with a non-zero `fee`. This promise is **not** chained (`.then`) to the actual action promise, so it executes independently of whether the real user-intended action ever succeeds.

For the specific sub-case `EOABaseTokenTransfer { address_check: Some(_), .. }`, the code explicitly *skips* incrementing the nonce at this point [2](#0-1) , deferring that decision to `address_check_callback`, which only increments the nonce once the async registrar lookup confirms the target really is not a registered account [3](#0-2) . If the lookup finds the address *is* registered (i.e., the relayer supplied a faulty/wrong `target`), the nonce is left untouched and the call returns an error response (or bans the relayer only if it were the owner's own key) — but the fee to the relayer has **already been transferred** in the earlier, independent promise.

Because the nonce is unchanged in this failure path, the exact same signed `tx_bytes_b64` (same nonce) can be resubmitted by the same relayer with the same intentionally-wrong `target` repeatedly. Each resubmission re-enters `inner_rlp_execute`, passes `validate_tx_relayer_data` (nonce still matches), and re-fires the fee-refund promise to the relayer — again before the registrar lookup can reject it. This provides no protocol-level bound on how many times a dishonest relayer can harvest the fee from a single authorized transaction.

### Impact Explanation
This allows a malicious relayer with access to call `rlp_execute` (they need not hold any private key of the wallet owner — the fee promise targets `predecessor_account_id`, the caller) to repeatedly extract the eth-transaction's `max_fee_per_gas * gas_limit`-derived fee from the wallet contract's own NEAR balance, without ever completing the user's intended action, by intentionally never supplying the registrar-correct `target`. This is concrete theft of funds from the wallet contract account, reachable purely through the eth-implicit wallet contract's public, unprivileged `rlp_execute` entry point — no elevated permissions required, only a relayer role which by design does not need to be trusted for correctness of `target` selection until after the fee has already moved.

### Likelihood Explanation
This is trivially and repeatably triggerable by any actor capable of calling `rlp_execute` as a relayer (an ordinary, permissionless action — anyone can submit a relayed transaction on behalf of a signed Ethereum-style payload). No race condition or timing dependency is required beyond normal async cross-contract call sequencing already built into the flow; the `has_in_flight_tx` guard only prevents concurrent, not sequential, replay.

### Recommendation
Chain the fee-refund transfer to the relayer only after the target/address validity is confirmed (i.e., inside/after `address_check_callback` once the registrar lookup succeeds and the nonce has been safely incremented), rather than firing it unconditionally at parse time. Alternatively, only pay the fee once the underlying action's promise result is known to be attempted with a validated target, mirroring how `rlp_execute_callback` already correctly refunds `caller_deposit` only on failure detection.

### Proof of Concept
1. Relayer crafts (or reuses) a validly-signed Ethereum-style transaction from the wallet's user, encoding a base token transfer whose `to` address happens to correspond to a Near account ID that is registered in the address registrar.
2. Relayer calls `rlp_execute(target = <raw-hex eth-implicit account>, tx_bytes_b64)`, deliberately using the raw address instead of doing the registrar lookup themselves.
3. `inner_rlp_execute` immediately schedules and sends the fee-refund transfer to the relayer (`predecessor_account_id`) per [4](#0-3) , without incrementing the nonce (since `address_check: Some(_)`).
4. The registrar lookup completes asynchronously and confirms the address is registered → `address_check_callback` returns an error response, without touching the nonce.
5. Relayer resubmits the identical `tx_bytes_b64`/`target` pair; nonce check still passes (unchanged), fee is paid out again.
6. Steps 3–5 repeat, draining the wallet contract's NEAR balance to the relayer with no on-chain action ever succeeding for the user.
