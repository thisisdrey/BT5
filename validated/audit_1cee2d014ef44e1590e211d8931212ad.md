### Title
Rewards emitted while a reward token's supply is zero are permanently locked in `RewardsDistributor` — (File: contracts/RewardsDistributor.sol)

### Summary
The external report describes emissions becoming undistributable and unrecoverable when a reward period has no eligible recipients (`totalVotesPerPeriod == 0` makes `_claimablePerPeriod` return 0, and the recovery mechanism cannot reclaim them). The same class exists in Metronome's `RewardsDistributor`: `_calculateTokenIndex` advances `timestamp` even when the tracked token's `totalSupply()` is zero, so all emissions accrued during zero-supply windows are skipped forever, and the contract has no sweep/recovery function to reclaim them.

### Finding Description
`_calculateTokenIndex` computes the reward index delta as `speed * elapsed / totalSupply`, but returns `_ratio = 0` when `totalSupply == 0` while still returning the new timestamp: [1](#0-0) 

`_updateTokenIndex` then stores the advanced `timestamp` with the unchanged index: [2](#0-1) 

Every call to `updateBeforeMintOrBurn`, `updateBeforeTransfer`, or `claimRewards` while supply is zero permanently discards `elapsed * speed` reward tokens — they can never be attributed to any index. Two concrete triggers:

1. **Speed set before first deposit**: governor/keeper calls `updateTokenSpeed`/`syncTokenSpeed` for a new DepositToken (or a gauge-like "speed on, no holders" state). Every second until the first deposit mints supply, emissions are lost — the direct analog of "gauge created, rewards notified, killed before votes exist."
2. **Permissionless withdrawal to zero**: any user can burn the entire DepositToken supply via `Pool.withdraw`. While `totalSupply == 0`, all emissions are skipped even though speed remains > 0.

Additionally, `RewardsDistributor` does not inherit `TokenHolder` and exposes no `sweep`/recovery function, so skipped emissions (like the report's `stuckEmissionsRecovery` gap) are permanently locked in the contract rather than being recoverable.

### Impact Explanation
Permanent freezing/loss of unclaimed yield: reward tokens intended for distribution sit in `RewardsDistributor` forever with no path to users or back to governance. The amount lost equals `speed × (duration supply == 0)`, which can be the entire emission budget for a period if a token's supply is empty at its start — matching the report's "rewards remain undistributed" invariant break (reward accrual conservation violated).

### Likelihood Explanation
Low-to-moderate. It requires a tracked token having `tokenSpeeds > 0` during a zero-supply window. This is plausible at token onboarding (speed set before deposits exist, mirroring the reported scenario) or whenever the sole depositor fully withdraws. No attacker profit exists, but the trigger needs no privileged misbehavior beyond normal configuration sequencing, and the keeper-driven `syncTokenSpeed` can set speed on a token whose `totalSupply` is zero.

### Recommendation
Mirror the report's fix direction: either don't advance `timestamp` (or pause accrual) when `totalSupply == 0` so emissions are deferred to the next non-zero-supply period, or add a governed `sweep`/recovery function so rewards attributable to empty-supply windows remain recoverable. The former is safer since it preserves the emission schedule.
