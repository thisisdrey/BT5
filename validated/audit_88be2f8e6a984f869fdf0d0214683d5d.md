### Title
Exchange Withdrawal Permanently Reverts (Fund Lock) Once Either Token Balance Hits Zero - ([File: actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java])

### Summary
`ExchangeWithdrawActuator`'s validation unconditionally rejects any withdrawal from a bancor-style TRC10 exchange pair once either side's token balance reaches `0`, permanently trapping the creator's remaining balance in the exchange with no recovery path — analogous to the reported oracle-returns-zero issue where a defensive zero-check blocks the very operation (fund recovery/liquidation) that is most needed in that state.

### Finding Description
`ExchangeWithdrawActuator.doValidate()` contains:
```java
if (firstTokenBalance == 0 || secondTokenBalance == 0) {
  throw new ContractValidateException("Token balance in exchange is equal with 0,"
      + "the exchange has been closed");
}
``` [1](#0-0) 

This check runs before any withdrawal amount is computed, and it applies regardless of which token the creator is trying to withdraw. Once either `firstTokenBalance` or `secondTokenBalance` in the `ExchangeCapsule` becomes `0`, `ExchangeWithdrawActuator` will reject *every* future withdrawal request for that exchange, including a withdrawal of the *other* side's balance, which is still nonzero and rightfully belongs to the exchange creator.

The zero-balance condition is reachable by any unprivileged trader, not just the creator: `ExchangeTransactionActuator` lets anyone trade against the pool via the bancor-curve `ExchangeCapsule.transaction()` method backed by `ExchangeProcessor`/`SafeExchangeProcessor`, which mutates `firstTokenBalance`/`secondTokenBalance` on every trade. [2](#0-1) [3](#0-2) 

With small pool sizes or the integer-truncating `exchangeFromSupply`/`exchangeToSupply` math in either processor implementation, a sequence of trades (or even a single large trade against a low-liquidity pool) can drive one side of the pool down to exactly `0` while the other side still holds a nonzero balance. Once that happens, `ExchangeWithdrawActuator` (the only exit path for exchange funds, guarded only by a creator-address check at line 181) becomes permanently unusable for that exchange: [4](#0-3) 

There is no other actuator or code path that lets the exchange creator retrieve the remaining balance once this state is hit — `ExchangeCapsule` exposes no alternative sweep/close function, and `ExchangeInjectActuator` only adds liquidity, it does not remove it.

### Impact Explanation
This is a permanent freezing-of-funds condition: the exchange creator's remaining TRX/TRC10 balance held in the exchange contract becomes irrecoverable forever once either side of the pool reaches zero, with no admin, governance, or fallback mechanism to unlock it. This matches the class of "critical operation permanently blocked by a zero-value guard" described in the source report, except here the consequence is direct, permanent loss of funds rather than a delayed liquidation.

### Likelihood Explanation
Reachable by any account: a trader (unprivileged transaction broadcaster) can trigger the zero-balance state simply by trading against a shallow pool via `ExchangeTransactionActuator`, and the creator (who created the exchange, itself an unprivileged action) is the only one blocked. Low-liquidity exchange pairs, or pools drained close to exhaustion by legitimate trading activity, make this state reachable without any special privilege, though the exact probability of landing exactly on `0` (versus a residual `1`) depends on curve rounding behavior in `ExchangeProcessor`/`SafeExchangeProcessor`, which was not fully proven by code execution here — this affects likelihood of *exact* zero more than the underlying design flaw of blocking withdrawal on that state.

### Recommendation
Change `ExchangeWithdrawActuator.doValidate()` to only reject withdrawal of the token whose balance is actually zero, or better, allow the creator to fully withdraw whatever remains of the exchange even when one side's balance is `0` (a special "close and drain" path), rather than blanket-rejecting withdrawals whenever either balance is zero.

### Proof of Concept
1. Create a TRC10/TRX exchange pair via `ExchangeCreateContract` with a small initial liquidity, e.g. `firstTokenBalance = 100`, `secondTokenBalance = 100`.
2. Attacker calls `ExchangeTransactionActuator` repeatedly (or once with a large enough `tokenQuant`) selling `firstToken` until `exchangeCapsule.transaction()` drives `secondTokenBalance` to `0` while `firstTokenBalance` is now large and nonzero. [5](#0-4) 
3. Exchange creator now calls `ExchangeWithdrawActuator` trying to withdraw the (large, nonzero) `firstTokenBalance`.
4. `doValidate()` hits `firstTokenBalance == 0 || secondTokenBalance == 0` → throws `ContractValidateException("Token balance in exchange is equal with 0, the exchange has been closed")`, at: [1](#0-0) 
5. The creator's remaining `firstTokenBalance` is now permanently locked, as no other actuator allows withdrawal from this exchange.

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
  }
