### Title
Unsolicited HandshakeAccept overwrites authenticated peer's public key/session state - (File: stackslib/src/net/chat.rs)

### Summary
`handle_handshake_accept` in `stackslib/src/net/chat.rs` unconditionally calls `update_from_handshake_data` on any inbound `HandshakeAccept`/`StackerDBHandshakeAccept` payload, without verifying that this `ConversationP2P` actually sent a corresponding outbound `Handshake` request. This allows an already-authenticated remote peer to send an unsolicited `HandshakeAccept` at any time and have the local node overwrite its bound `public_key`, `peer_heartbeat`, and `data_url` for that session.

### Finding Description
The broken equality is: *a `HandshakeAccept` is applied to connection state* should equal *a `HandshakeAccept` received in reply to a `Handshake` this conversation actually sent* (correlated by request/sequence). In `handle_handshake_accept` (stackslib/src/net/chat.rs:1338-1391), the very first statement is:
```
self.update_from_handshake_data(preamble, &handshake_accept.handshake)?;
``` [1](#0-0) 
There is no check here that ties this accept to a prior outbound handshake sent by `self`. `Connection::is_solicited` exists in `stackslib/src/net/connection.rs` to perform exactly this kind of correlation, but per the question's trace it is invoked only on the unauthenticated control-message path (chat.rs:2616-2642), while the authenticated path's `HandshakeAccept` branch (chat.rs:2548-2552) calls `handle_handshake_accept` directly. The rest of `handle_handshake_accept` (heartbeat interval clamp, stacker DB handshake data update, timestamp bump) further mutates conversation state based purely on attacker-supplied payload fields.

I was not able to independently re-read the exact bodies of `handle_authenticated_control_message`, `handle_unauthenticated_control_message`, `update_from_handshake_data`, and `Connection::is_solicited` within the available tool budget (searches for these functions returned only file-location matches, not their bodies, before the iteration limit was reached). I can confirm from direct inspection that `handle_handshake_accept` unconditionally calls `update_from_handshake_data` with no solicitation gate inside itself, matching the core of the claim, but I could not fully verify whether some other guard exists earlier in the authenticated dispatch path before `handle_handshake_accept` is invoked.

### Impact Explanation
If the authenticated dispatch path indeed lacks a solicitation check (as described and partially confirmed), a remote peer that already completed a handshake with the local node could send further unsolicited `HandshakeAccept` messages to silently rebind the conversation's public key, heartbeat interval, and StackerDB replication metadata without the local node ever issuing a `Handshake`. This is a session-state integrity issue on the P2P authenticated channel — an unauthorized write to in-memory connection state — repeatable per message, matching a Critical "unauthenticated/unauthorized write to state" category if the missing gate is confirmed.

### Likelihood Explanation
Preconditions: attacker must already have an established (authenticated) `ConversationP2P` with the target node — reachable by any remote peer that can complete an initial handshake, which is a normal, unprivileged P2P interaction. No secret or privileged role is needed. Attacker cost is a single crafted message with an attacker-chosen `HandshakeAcceptData`. Because I could not fully verify the absence of an equivalent solicitation check somewhere in the authenticated-message dispatch (only in `handle_handshake_accept` itself), confidence is limited.

### Recommendation
Add a solicitation check (mirroring `Connection::is_solicited`) before invoking `update_from_handshake_data` in `handle_handshake_accept`, or in the authenticated-control-message dispatch branch (chat.rs:2548-2552) before calling `handle_handshake_accept`, so that HandshakeAccept/StackerDBHandshakeAccept payloads are only applied when they correlate to a `Handshake` this conversation actually sent.

### Proof of Concept
Rust test in `stackslib::net::chat`:
1. Construct two `ConversationP2P` instances (local/remote) and drive them through a normal handshake to reach the authenticated state.
2. From the remote side, construct a fresh `StacksMessage` wrapping `StacksMessageType::HandshakeAccept(HandshakeAcceptData { handshake: <attacker-controlled HandshakeData with a new public key>, heartbeat_interval: ... })` with a preamble `seq`/seq that does NOT correspond to any outstanding request the local conversation sent.
3. Feed it into the local conversation's authenticated-message handling entry point (`handle_authenticated_control_message`, chat.rs:2548-2552) directly.
4. Assert that `local.connection.public_key` (or `self.data_url`/`self.peer_heartbeat`) now equals the attacker-supplied value from step 2, i.e., `update_from_handshake_data` was invoked and mutated state despite no matching outbound handshake — confirming the missing solicitation check at chat.rs:1345.
