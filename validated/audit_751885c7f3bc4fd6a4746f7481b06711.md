# No vulnerability found for this question.

The scenario described is not a bug — it matches exactly the intended, tested behavior of the resolver. `mt_resolve_transfer` unconditionally clamps any receiver-requested refund to `min(amount, receiver_balance)` precisely to prevent a malicious receiver from claiming a refund larger than what it actually still holds, which is what preserves conservation (it would otherwise let a receiver mint a phantom refund out of nothing). [1](#0-0) 

Once `mt_transfer_call` credits the receiver's `token_balances` (this happens unconditionally before `mt_on_transfer` is even invoked), the receiver is the legitimate owner of those tokens and is free to move them elsewhere (e.g. via a nested `execute_intents`/`mt_transfer`) exactly as any account can move its own balance. The "refund" returned from `mt_on_transfer` is a voluntary courtesy, not a guaranteed reversible escrow — the resolver only ever returns to the sender what is verifiably still present in the receiver's account at resolution time, never more. There is no double-counting: whatever the receiver moved away remains fully accounted for at the destination account, and whatever remains gets refunded to `previous_owner_id`. Total token supply and per-account balances stay conserved throughout.

This exact "drain-then-request-larger-refund" pattern is covered by the existing test `mt_transfer_call_duplicate_tokens_with_stub_execute_and_refund`, where the stub receiver executes a signed transfer moving part of its just-credited `nep245_ft1` balance to a third account (`another_receiver`) before returning a refund request, and the resolver correctly caps the refund to the balance actually remaining, refunding the sender exactly what's left while the moved tokens are held by the third account (not lost) — the assertions confirm balances net out correctly (2000 refunded to user + 2000 held by `another_receiver` = original 4000 sent). [2](#0-1) 

There is no unauthorized movement of the sender's signed transfer amount — the sender's `amount` is delivered exactly once to `receiver_id`, and any subsequent redistribution by the receiver of its own now-owned balance is a normal, authorized action by that receiver, not a breach of the sender's authorization.

            let Some(receiver) = self

                .get_mut(&receiver_id)
                // NOTE: refunds from locked accounts are allowed to prevent
                // senders from loss of funds.
                //
                // Receiver's account might have been locked between
                // `mt_transfer_call()` and `mt_resolve_transfer()`, so that
                // outgoing transfers are no longer allowed for this account.
                // But here we distinguish between regular transfers and
                // refunds, despite it would lead to `mt_transfer` event
                // emitted with `old_owner_id` being the locked account.
                //
                // Locked receivers still won't be able to transfer funds in
                // `<receiver_id>::on_mt_transfer()` implementation.
                .map(Lock::as_inner_unchecked_mut)
            else {
                // receiver doesn't have an account, so nowhere to refund from
                return amounts;
            };
            let receiver_balance = receiver.token_balances.amount_for(&token_id);
            // refund maximum what we can
            refund.0 = refund.0.min(receiver_balance);
            if refund.0 == 0 {
                // noting to refund
                continue;
            }

            // withdraw refund
            receiver
                .token_balances
                .sub(token_id.clone(), refund.0)
                .unwrap();
            // deposit refund
            self.accounts
                .get_or_create(previous_owner_id)
                // refunds are allowed for locked accounts
                .as_inner_unchecked_mut()
                .token_balances
                .add(token_id, refund.0)
                .unwrap();
