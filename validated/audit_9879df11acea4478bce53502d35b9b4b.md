### Title
`get_add_stake_fee()` Uses Stale Rewards Rate When Rate Period Has Elapsed Mid-Epoch — (`aptos-move/framework/aptos-framework/sources/delegation_pool.move`)

---

### Summary

`delegation_pool::get_add_stake_fee()` reads the stored `StakingRewardsConfig.rewards_rate` directly via `staking_config::get_reward_rate()` without first triggering `calculate_and_save_latest_epoch_rewards_rate()`. When the `periodical_reward_rate_decrease_enabled` feature is active and the rate period has elapsed mid-epoch, the stored rate is stale (higher than the actual current rate). Because `add_stake()` calls `get_add_stake_fee()` to compute the real on-chain fee deducted from delegators, this stale rate causes delegators to overpay, with the excess redistributed to existing stakers.

---

### Finding Description

`get_add_stake_fee()` is both a `#[view]` function and is called directly inside `add_stake()`: [1](#0-0) 

At line 700, it calls:

```move
let (rewards_rate, rewards_rate_denominator) = staking_config::get_reward_rate(&staking_config::get());
```

`get_reward_rate()` in `staking_config.move` reads the stored `StakingRewardsConfig.rewards_rate` directly from global storage: [2](#0-1) 

The stored `rewards_rate` is only updated by `calculate_and_save_latest_rewards_config()`, which is called at epoch boundaries via `on_new_epoch()`: [3](#0-2) 

The rate period (`rewards_rate_period_in_secs`) is typically 1 year. Epochs are far shorter. If the rate period elapses mid-epoch, the stored rate is stale until the next epoch boundary. Neither `synchronize_delegation_pool()` nor any other function called inside `add_stake()` triggers a rate update: [4](#0-3) 

The fee is computed with the stale (higher) rate and immediately applied: the delegator receives shares for `amount - add_stake_fee` while `add_stake_fee` is credited to `NULL_SHAREHOLDER` and later distributed to existing stakers.

`on_new_epoch()` obtains the staking config once at the top and passes it to `update_stake_pool()`, which also calls `get_reward_rate()` — but the epoch-boundary update of the stored rate happens separately via `calculate_and_save_latest_epoch_rewards_rate()`: [5](#0-4) 

---

### Impact Explanation

When the rewards rate period elapses mid-epoch and a delegator calls `add_stake()`, the fee is calculated with the old (higher) rate. The excess fee is transferred to `NULL_SHAREHOLDER` and distributed to existing stakers at epoch end. This is an unauthorized transfer of the delegator's staking balance to other participants.

**Concrete example:** With a 50% annual rate decrease, a 1% per-epoch rate drops to 0.5%. For a 1,000,000 APT `add_stake` call:
- Fee at old rate: `1,000,000 × 1% / (1% + 100%) ≈ 9,901 APT`
- Fee at new rate: `1,000,000 × 0.5% / (0.5% + 100%) ≈ 4,975 APT`
- Delegator overpays: **≈ 4,926 APT** per transaction

This excess is permanently redistributed to existing stakers, constituting a direct loss of staking balance for the delegator.

---

### Likelihood Explanation

- Requires `periodical_reward_rate_decrease_enabled` feature to be active (a planned mainnet feature).
- Requires the rewards rate period to have elapsed but `on_new_epoch` not yet called — a window of one epoch duration, occurring predictably once per rate period (e.g., annually).
- Any unprivileged delegator calling `add_stake()` during this window is affected. No special permissions required.

---

### Recommendation

Inside `get_add_stake_fee()`, replace the direct read with a call that computes the up-to-date rate before using it:

```move
public fun get_add_stake_fee(pool_address: address, amount: u64): u64 {
    if (stake::is_current_epoch_validator(pool_address)) {
-       let (rewards_rate, rewards_rate_denominator) = staking_config::get_reward_rate(&staking_config::get());
+       // Use the latest rate, accounting for any elapsed rate period
+       let config = staking_config::get();
+       if (features::periodical_reward_rate_decrease_enabled()) {
+           staking_config::calculate_and_save_latest_epoch_rewards_rate();
+       };
+       let (rewards_rate, rewards_rate_denominator) = staking_config::get_reward_rate(&config);
        ...
    }
}
```

Alternatively, expose a `get_reward_rate_latest()` helper in `staking_config` that calls `calculate_and_save_latest_rewards_config()` internally before returning the rate, mirroring the pattern used in `on_new_epoch`.

---

### Proof of Concept

1. Enable `periodical_reward_rate_decrease_enabled` feature.
2. Initialize `StakingRewardsConfig` with `rewards_rate = 2%`, `rewards_rate_period_in_secs = ONE_YEAR_IN_SECS`, `rewards_rate_decrease_rate = 50%`.
3. Fast-forward time by exactly `ONE_YEAR_IN_SECS` without triggering `on_new_epoch` (i.e., stay within the same epoch).
4. Call `get_add_stake_fee(pool_address, 1_000_000 * ONE_APT)` — it returns a fee based on the stale 2% rate.
5. Call `add_stake(delegator, pool_address, 1_000_000 * ONE_APT)` — the delegator is charged the inflated fee.
6. Trigger `on_new_epoch` — the rate is now updated to 1%. The fee that was charged was double what it should have been. The excess is distributed to existing stakers.

The delegator's staking balance is permanently reduced by the fee overpayment, with no recourse.

```text
    public fun get_reward_rate(config: &StakingConfig): (u64, u64) acquires StakingRewardsConfig {
        if (features::periodical_reward_rate_decrease_enabled()) {
            let epoch_rewards_rate = borrow_global<StakingRewardsConfig>(@aptos_framework).rewards_rate;
            if (epoch_rewards_rate.is_zero()) {
                (0u64, 1u64)
            } else {
                // Maximize denominator for higher precision.
                // Restriction: nominator <= MAX_REWARDS_RATE && denominator <= MAX_U64
                let denominator = fixed_point64::divide_u128((MAX_REWARDS_RATE as u128), epoch_rewards_rate);
                if (denominator > MAX_U64) {
                    denominator = MAX_U64
                };
                let nominator = (fixed_point64::multiply_u128(denominator, epoch_rewards_rate) as u64);
                (nominator, (denominator as u64))
            }
        } else {
            (config.rewards_rate, config.rewards_rate_denominator)
        }
    }
```

```text
    fun calculate_and_save_latest_rewards_config(): StakingRewardsConfig acquires StakingRewardsConfig {
        let staking_rewards_config = borrow_global_mut<StakingRewardsConfig>(@aptos_framework);
        let current_time_in_secs = timestamp::now_seconds();
        assert!(
            current_time_in_secs >= staking_rewards_config.last_rewards_rate_period_start_in_secs,
            error::invalid_argument(EINVALID_LAST_REWARDS_RATE_PERIOD_START)
        );
        if (current_time_in_secs - staking_rewards_config.last_rewards_rate_period_start_in_secs < staking_rewards_config.rewards_rate_period_in_secs) {
            return *staking_rewards_config
        };
        // Rewards rate decrease rate cannot be greater than 100%. Otherwise rewards rate will be negative.
        assert!(
            staking_rewards_config.rewards_rate_decrease_rate.ceil() <= 1,
            error::invalid_argument(EINVALID_REWARDS_RATE_DECREASE_RATE)
        );
        let new_rate = math_fixed64::mul_div(
            staking_rewards_config.rewards_rate,
            fixed_point64::create_from_u128(1).sub(staking_rewards_config.rewards_rate_decrease_rate),
            fixed_point64::create_from_u128(1),
        );
        new_rate = fixed_point64::max(new_rate, staking_rewards_config.min_rewards_rate);

        staking_rewards_config.rewards_rate = new_rate;
        staking_rewards_config.last_rewards_rate_period_start_in_secs += staking_rewards_config.rewards_rate_period_in_secs;
        return *staking_rewards_config
    }
```
