### Title
Setting `new_authority` to the zero/default pubkey in account transfer permanently locks the migrated account's funds - ([File: programs/marginfi/src/instructions/marginfi_account/transfer_account.rs])

### Summary
The `TransferToNewAccount` and `TransferToNewAccountPda` instructions let an account's own authority (an unprivileged, ordinary signer) move all balances of an existing `MarginfiAccount` into a brand-new account under an arbitrary `new_authority` pubkey, with no validation that this pubkey is non-default. This is the same bug class as the DebtRegistry report: a caller who is authorized to perform an operation involving a "beneficiary/authority"-like field can set that field to the null/zero address, silently breaking an implicit protocol invariant (that a live account always has a controllable, non-zero authority) and creating a permanently inaccessible account.

### Finding Description
`TransferToNewAccount` and `TransferToNewAccountPda` accept `new_authority` as a completely unchecked account: [1](#0-0) [2](#0-1) 

The handler copies the old account's entire `lending_account` (all deposit/borrow balances) into the new account and sets the new account's `authority` field directly to whatever key was supplied, with no check against `Pubkey::default()`: [3](#0-2) [4](#0-3) 

`is_signer_authorized`, which gates every state-changing action on a `MarginfiAccount` (deposits, withdrawals, borrows, repayments, order placement, etc.), simply checks `marginfi_account.authority == signer`: [5](#0-4) 

If `authority` is set to `Pubkey::default()`, no signer can ever satisfy `signer == Pubkey::default()` (there is no private key for the default/all-zero pubkey), so the account becomes permanently unauthorizable by its "owner" — only the group admin retains any path (and only if the account happens to be frozen, which it is not by default). The old account is simultaneously disabled and its balances zeroed out, so the funds effectively only exist in the new, now-uncontrollable account: [6](#0-5) 

Notably, the off-chain CLI client explicitly guards against this exact scenario ("Cannot transfer authority to the zero pubkey"), confirming the team is aware zero-address authorities are unsafe — but this guard is client-side only and is not enforced on-chain: [7](#0-6) 

The Anchor account struct even carries a `WARN` comment acknowledging the new authority is unchecked: [8](#0-7) 

This directly mirrors the DebtRegistry class of bug: an entity legitimately authorized to perform an operation on a record (the account owner performing a self-service migration, analogous to the authorized agent calling `insert`/`modifyBeneficiary`) can set the critical identity/ownership field to the null address, breaking the codebase's implicit assumption that this field is never zero.

### Impact Explanation
Calling `transfer_to_new_account` or `transfer_to_new_account_pda` with `new_authority = Pubkey::default()` moves 100% of the caller's own account balances (deposits and any collateral) into a new `MarginfiAccount` whose `authority` is the zero pubkey. Since no wallet can sign as the zero pubkey, and the account is neither frozen (so group-admin fallback in `is_signer_authorized` does not apply) nor in receivership/order-execution, the funds become permanently locked/frozen — unrecoverable by the original owner and inaccessible to anyone else through normal instructions. This matches the "permanent lock/freeze" impact category.

### Likelihood Explanation
The action requires no special privilege beyond being the current authority of one's own `MarginfiAccount`, which is any regular user. It could occur due to a client bug, a compromised or malicious front-end, or user/tooling error (the on-chain program does not stop it, only the CLI happens to check it for one specific call path). Since PDA-based transfers also derive seeds from `new_authority.key()` without validating non-default, the same issue applies there too.

### Recommendation
Add an explicit on-chain check in `transfer_to_new_account` and `transfer_to_new_account_pda` that rejects `new_authority == Pubkey::default()` before migrating the account, mirroring the client-side check already present in `p0-cli/src/processor/account.rs`.

### Proof of Concept
1. User A creates a `MarginfiAccount` and deposits collateral, giving them a lending position (balance shares in `lending_account`).
2. User A calls `TransferToNewAccount` (or `TransferToNewAccountPda`), supplying `new_authority = Pubkey::default()`.
3. The instruction succeeds: `initialize_migrated_account` copies `old_account.lending_account` into `new_account` and sets `new_account.authority = Pubkey::default()`; `finalize_migrated_old_account` disables the old account and zeroes its `lending_account`.
4. Any subsequent instruction that touches the new account (withdraw, borrow repay, close balance, etc.) calls `is_signer_authorized`/`account_not_frozen_for_authority`, which require `marginfi_account.authority == signer`. Because no keypair exists for `Pubkey::default()`, this check can never pass, and the account's funds are permanently stranded.

pub fn is_signer_authorized(
    marginfi_account: &MarginfiAccount,
    group_admin: Pubkey,
    signer: Pubkey,
    allow_receivership: bool,
    allow_order_execution: bool,
) -> bool {
    if allow_receivership && marginfi_account.get_flag(ACCOUNT_IN_RECEIVERSHIP) {
        return marginfi_account.authority != signer; // forbidden to take receivership of your own account
    }

    if allow_order_execution && marginfi_account.get_flag(ACCOUNT_IN_ORDER_EXECUTION) {
        return true;
    }

    if marginfi_account.get_flag(ACCOUNT_FROZEN) {
        return group_admin == signer;
    }

    marginfi_account.authority == signer
}
