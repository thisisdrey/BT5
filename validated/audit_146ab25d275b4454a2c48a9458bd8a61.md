### Title
Dust-transfer griefing fills victim's per-account token list, blocking new collateral deposits and debt issuance - ([File: contracts/DepositToken.sol](contracts/DepositToken.sol))

### Summary
`Pool.addToDepositTokensOfAccount` enforces `MAX_TOKENS_PER_USER = 30` on the *combined* count of a user's deposit-token and debt-token entries [1](#0-0) . Any `DepositToken` transfer to an address with a zero balance in that token registers it in the victim's list [2](#0-1) . Because deposit tokens are freely transferable via public `transfer`, an unprivileged attacker can push dust amounts of every registered collateral into a victim's account, exhausting the cap and causing all subsequent first-time deposits, deposits to a new collateral type, debt issuance in a new synthetic, and incoming transfers to revert with `UserReachedMaxTokens`. This is the Metronome analog of the Lighthouse resource-exhaustion DoS: an unprivileged peer inflates a bounded per-account registry until the victim's normal operations fail.

### Finding Description
- `Pool.MAX_TOKENS_PER_USER` is 30 and counts `debtTokensOfAccount + depositTokensOfAccount` [3](#0-2) [1](#0-0) .
- `DepositToken._transfer` calls `pool.addToDepositTokensOfAccount(recipient_)` whenever the recipient's prior balance is zero; the recipient has no way to opt out [4](#0-3) .
- The same registration happens on `deposit`/`_mint`, so minting to a victim address also fills the list [5](#0-4) .
- `DebtToken` issuance similarly calls `pool.addToDebtTokensOfAccount`, which is guarded by the same modifier [6](#0-5) .
- Once the victim's list reaches 30 (attacker dust across all pool-registered deposit tokens, which are themselves capped at 30 per pool [7](#0-6) ), every subsequent `addTo*` call reverts. Since the revert happens inside `transfer`/`deposit`/`issue`, the whole user transaction fails.

Attack flow:
1. Attacker deposits a small amount into each registered `DepositToken` (or acquires dust on secondary markets).
2. Attacker calls `depositToken_i.transfer(victim, 1 wei)` for each `i`. Each call adds token `i` to `victim`'s `depositTokensOfAccount`.
3. Combined with any debt tokens the victim already holds, the victim's list reaches 30.
4. Victim's `deposit(newCollateralToken, ...)` mint → `addToDepositTokensOfAccount` → `UserReachedMaxTokens`; `issue` of a new synthetic reverts identically; liquidation proceeds normally because `seize` registers the token on the *liquidator*, not the victim.

The victim cannot remove the dust entries without withdrawing each dust position entirely (withdrawal burns the balance and triggers `removeFromDepositTokensOfAccount` [8](#0-7) ), which requires N extra transactions and paying withdrawal fees on dust, and the attacker can re-grief at dust cost.

### Impact Explanation
- DoS on victim's ability to open/adjust positions in new collateral or debt types. In the critical scenario — a victim racing to top up collateral in a different token before liquidation — the attacker (who can be the liquidator) pre-fills the victim's list, the rescue deposit reverts, and the position is liquidated, inflicting a direct economic loss (liquidation fee + seized discount).
- Any protocol integration or router (e.g., `Operator.execute` batch deposits into a new collateral for a user) will have its transactions revert unpredictably.
- Impact class: temporary freezing/blocking of user operations leading to forced liquidation loss. Fits the accepted "temporary freezing of funds" / DoS category.

### Likelihood Explanation
- Fully unprivileged: requires only EOA calls to public `DepositToken.transfer`/`deposit`.
- Cost is bounded and small: dust transfers of at most 30 tokens; attacker keeps the bulk of each balance or can withdraw it afterward. On pools with few registered collaterals the attacker's spend is trivial and the victim is locked out of *all* debt tokens once the list is full.
- Not stopped by any existing guard: no min-transfer amount, no recipient consent, no cap on entries-per-token-type beyond the global one, pause/shutdown flags only make it worse.
- Caveat lowering severity: victim can clear slots by fully withdrawing each dust token, and can still deposit into collateral types already present, so a prepared victim with spare slots or existing positions is less affected. Medium likelihood, medium impact — consistent with the source report's Medium rating.

### Recommendation
- Require recipient opt-in for list registration: e.g., only register on `deposit`/`mint` (self-service or `onBehalfOf` with explicit consent), not on plain ERC20 `transfer`; for transfers, let the recipient claim/pull rather than receive-push.
- Alternatively, decouple accounting from the cap: store per-account balances in a mapping keyed by token and iterate only over governor-registered `depositTokens` (already bounded at 30 pool-wide), removing the per-account cap grief vector.
- A cheaper mitigation: exempt dust below a minimum meaningful amount (e.g., only add to the list when `amount_ >= minDeposit`), though this is weaker since dust thresholds can be set low.

### Proof of Concept
Hardhat (fork or fixture) sketch:

```ts
// contracts/Pool.sol enforces: debt + deposit tokens < 30
it('grief: dust fills victim list, blocking new deposit', async () => {
  const victim = bob;
  // attacker deposits 2 wei into every registered deposit token
  for (const dt of allDepositTokens) {              // N <= 30
    await underlying(dt).approve(dt.address, 2);
    await dt.deposit(2, attacker.address);
    await dt.connect(attacker).transfer(victim.address, 1); // adds dt to victim's list
  }
  // also issue one debt token each if needed to reach 30
  expect(await pool.getDepositTokensOfAccount(victim.address)).to.have.lengthOf(N);

  // victim tries to deposit a collateral type they don't hold -> reverts
  const newDT = someDepositTokenVictimNeverHeld;
  await underlying(newDT).connect(victim).approve(newDT.address, parseEther('10'));
  await expect(newDT.connect(victim).deposit(parseEther('10'), victim.address))
    .revertedWithCustomError(pool, 'UserReachedMaxTokens');

  // victim tries to mint a new synthetic -> reverts via addToDebtTokensOfAccount
  await expect(debtToken.connect(victim).issue(parseEther('1'), victim.address))
    .revertedWithCustomError(pool, 'UserReachedMaxTokens');
});
```

Steps assume an existing fixture where `allDepositTokens` are registered via `pool.addDepositToken`; on a mainnet fork, use the deployed Pool + DepositToken addresses and impersonate/seed underlying balances via `setBalance`/`deal`.
