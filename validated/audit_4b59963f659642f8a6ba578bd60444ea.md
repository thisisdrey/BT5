### Title
Missing enforcement of `write_freq` rate limit in StackerDB chunk-write validation causes premature slot exhaustion and broadcast amplification - (File: stackslib/src/net/stackerdb/db.rs)

### Summary
`StackerDBConfig::write_freq` is a documented, per-replica wall-clock rate limit meant to bound how often a slot owner may write a new chunk, and `SlotValidation` even carries a `write_time` column for this purpose. However, the only function that actually gates chunk acceptance, `StackerDBTx::try_replace_chunk`, never checks `write_freq`/`write_time` at all — it only checks chunk size, slot existence, signature, staleness, and `max_writes`. This is the same class of bug as the `yIntercept` report: a value that the protocol's invariants assume is being checked/deducted (here, the write-rate limit) is silently missing from the enforcement path, so the real on-chain/on-disk state diverges from the value the rest of the system assumes is being enforced.

### Finding Description
`StackerDBConfig` documents `write_freq` as a rate-limiting knob for StackerDB writes, and the schema/`SlotValidation` struct tracks `write_time` per slot specifically to support this check: [1](#0-0) 

The actual write-acceptance function, `try_replace_chunk`, performs chunk-size, slot-existence, signature, staleness (`slot_version <= slot_validation.version`), and `max_writes` checks — but at no point reads or compares against `config.write_freq` or `slot_validation.write_time`: [2](#0-1) 

The same omission exists in the peer-to-peer/gossip validation path `StackerDBSync::validate_received_chunk`, which validates size, expected version, signer, staleness, and `max_writes`, but likewise never checks `write_freq`: [3](#0-2) 

Consistent with this, the RPC POST handler's error taxonomy has no "write frequency exceeded" error code at all — only `DataAlreadyExists`, `NoSuchSlot`, `BadSigner`, `ChunkTooBig`, and `TooManySlotWrites`: [4](#0-3) 

`write_freq` is referenced only in `stackslib/src/net/stackerdb/sync.rs`, `config.rs`, and tests — i.e., only in the peer's own outbound sync-scheduling heuristics, never as an acceptance gate for incoming writes (via `POST /v2/stackerdb/.../chunks`) or incoming gossip pushes (via `process_stacker_db_chunks` in `relay.rs`). Any legitimate slot owner (who already possesses their own valid signing key for their slot — no other party's key or admin role is needed) can therefore submit chunk writes at network speed instead of the pace the smart contract config intends.

### Impact Explanation
`max_writes` and `write_freq` together are supposed to jointly bound a slot's write budget over a reward cycle: `write_freq` throttles the pace, `max_writes` caps the total count. Because `write_freq` is not enforced anywhere, an already-authorized signer can burn through their entire `max_writes` budget for a slot in a burst rather than over the intended reward-cycle timeframe. Once `max_writes` is exceeded, `try_replace_chunk` permanently rejects further writes to that slot with `TooManySlotWrites` for the remainder of the cycle (there is no reset short of reconfiguration): [5](#0-4) 

Each accepted write is also unconditionally rebroadcast to the node's neighbor set when learned via sync/relay, since successful storage is treated as evidence of novelty: [6](#0-5) [7](#0-6) 

So a burst of rapid, validly-signed writes from one already-authorized signer both (a) prematurely and permanently exhausts that slot's write budget for the rest of the cycle (denial of write-availability to legitimate future updates from that signer, e.g. signer-message StackerDBs used for signing rounds), and (b) forces amplified store-and-forward broadcast traffic to every replicating neighbor network-wide, since each of up to `max_writes` chunks is independently validated and rebroadcast. This is a state-availability and amplification impact reachable by any protocol participant who already owns a slot, without needing another party's key.

### Likelihood Explanation
Likelihood is high for any party that already holds a StackerDB slot (e.g., a signer or miner with a `.signers`/`.miners` StackerDB slot) — this requires no privilege escalation, no forged signatures, and no protocol timing constraints beyond issuing HTTP POSTs or P2P `StackerDBChunk` pushes back-to-back with monotonically increasing `slot_version`. The action is fully remote and unprivileged relative to that signer's own slot.

### Recommendation
Enforce `config.write_freq` against `slot_validation.write_time` inside `StackerDBTx::try_replace_chunk` (and correspondingly in `StackerDBSync::validate_received_chunk`), rejecting/NACKing writes that arrive sooner than `write_freq` seconds after the slot's last recorded `write_time`, matching the intent already encoded in the `SlotValidation.write_time` field and the config's documentation. Add a dedicated error code/ack (e.g. `WriteTooFrequent`) analogous to `TooManySlotWrites` so clients receive a clear, retryable rejection rather than silently being allowed to exhaust their write budget early.

### Proof of Concept
1. Configure a StackerDB contract with `write-freq: u60` (60 seconds) and `max-writes: u100`.
2. As the legitimate signer for slot `N`, submit 100 validly-signed `POST /v2/stackerdb/{addr}/{contract}/chunks` requests back-to-back (sub-second), each with `slot_version` incremented by 1.
3. Observe via `try_replace_chunk` (`stackslib/src/net/stackerdb/db.rs:400-438`) that all 100 writes succeed instantly, because no check compares `get_epoch_time_secs()` against `slot_validation.write_time + config.write_freq`.
4. The 101st write is rejected with `TooManySlotWrites` (`stackslib/src/net/stackerdb/db.rs:430-436`), well before the reward cycle's intended duration has elapsed, even though the contract configured a 60-second-per-write cadence intended to spread these 100 writes across ~100 minutes.
5. Each of the 100 accepted chunks is separately broadcast to all neighboring replicas via `PeerNetwork::process_stacker_db_chunks` (`stackslib/src/net/relay.rs:2445-2452`), producing amplified P2P traffic network-wide in a fraction of the intended time window.

    pub fn try_replace_chunk(
        &self,
        smart_contract: &QualifiedContractIdentifier,
        slot_desc: &SlotMetadata,
        chunk: &[u8],
    ) -> Result<(), net_error> {
        // Check per-replica chunk-size cap.
        if (chunk.len() as u64) > self.config.chunk_size {
            return Err(net_error::StackerDBChunkTooBig(chunk.len()));
        }

        let slot_validation = self
            .get_slot_validation(smart_contract, slot_desc.slot_id)?
            .ok_or(net_error::NoSuchSlot(
                smart_contract.clone(),
                slot_desc.slot_id,
            ))?;

        if !slot_desc.verify(&slot_validation.signer)? {
            return Err(net_error::BadSlotSigner(
                slot_validation.signer,
                slot_desc.slot_id,
            ));
        }
        if slot_desc.slot_version <= slot_validation.version {
            return Err(net_error::StaleChunk {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
            });
        }
        if slot_desc.slot_version > self.config.max_writes {
            return Err(net_error::TooManySlotWrites {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
                max_writes: self.config.max_writes,
            });
        }
        self.insert_chunk(smart_contract, slot_desc, chunk)
    }

    pub fn validate_received_chunk(
        &self,
        smart_contract_id: &QualifiedContractIdentifier,
        config: &StackerDBConfig,
        data: &StackerDBChunkData,
        expected_versions: &[u32],
    ) -> Result<bool, net_error> {
        // validate -- must not exceed this replica's configured chunk size.
        if (data.data.len() as u64) > config.chunk_size {
            info!(
                "Received StackerDBChunk for {} ID {}, which is oversized: {} bytes (max {} bytes)",
                smart_contract_id,
                data.slot_id,
                data.data.len(),
                config.chunk_size
            );
            return Ok(false);
        }

        // validate -- must be a valid chunk
        let Some(expected_version) = expected_versions.get(data.slot_id as usize) else {
            info!(
                "Received StackerDBChunk for {} ID {}, which is too big ({})",
                smart_contract_id,
                data.slot_id,
                expected_versions.len()
            );
            return Ok(false);
        };

        // validate -- must be signed by the expected author
        let addr = match self
            .stackerdbs
            .get_slot_signer(smart_contract_id, data.slot_id)?
        {
            Some(addr) => addr,
            None => {
                return Ok(false);
            }
        };

        let slot_metadata = data.get_slot_metadata();
        if !slot_metadata.verify(&addr)? {
            info!(
                "StackerDBChunk for {} ID {} is not signed by {}",
                smart_contract_id, data.slot_id, &addr
            );
            return Ok(false);
        }

        // validate -- must be the current or newer version
        if data.slot_version < *expected_version {
            info!(
                "Received StackerDBChunk for {} ID {} version {}, which is stale (expected {})",
                smart_contract_id, data.slot_id, data.slot_version, *expected_version
            );
            return Ok(false);
        }

        // validate -- must not exceed max writes
        if data.slot_version > config.max_writes {
            info!(
                "Write count exceeded for StackerDBChunk for {} ID {} version {} (max is {})",
                smart_contract_id, data.slot_id, data.slot_version, config.max_writes
            );
            return Ok(false);
        }

        Ok(true)
    }

            Self::TooManySlotWrites => 4,
