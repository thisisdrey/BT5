### Title
Unprivileged attacker can fill a victim's per-account token list with dust deposit-token transfers, blocking all new deposits and debt issuance for that account - (File: contracts/Pool.sol)

### Summary
`Pool` keeps a per-account enumerable set of deposit/debt tokens capped at `MAX_TOKENS_PER_USER = 30` ( [1](#0-0) ). Any `DepositToken._transfer` or `_mint` that takes a recipient from zero to nonzero balance unconditionally calls `pool.addToDepositTokensOfAccount(recipient_)` ( [2](#0-1) ). An unprivileged EOA can deposit dust of every listed collateral and `transfer` 1 wei of each to a victim, exhausting the cap. Thereafter every new-token deposit, `DebtToken.issue` on a new synthetic, and liquidation-seize path that adds a token reverts with `UserReachedMaxTokens` ( [3](#0-2) ). This is the same bug class as LID-15: an unprivileged actor spamming cheap state changes to DoS a core protocol operation (deposits), with no consent required from the victim.

### Finding Description
- `Pool.addToDepositTokensOfAccount` / `addToDebtTokensOfAccount` enforce `debtTokensOfAccount.length + depositTokensOfAccount.length < MAX_TOKENS_PER_USER` before adding ( [1](#0-0) ).
- `DepositToken._transfer` adds the deposit token to the recipient's account list whenever the recipient's balance was zero, with no opt-in and no minimum amount ( [4](#0-3) ).
- `DepositToken.transfer` is a public entry point gated only by `_revertIfLocked` on the *sender's* balance; there is no recipient-side check and no `minDepositTime` protection against receiving dust.
- Analogously, `DebtToken.issue` triggers `addToDebtTokensOfAccount` for the account, so once the shared 30-slot budget is exhausted the victim cannot open positions in any *new* synthetic either.
- Existing positions still work (`_mint`/`_transfer` only call the add when balance goes 0→nonzero), so this is a liveness/griefing issue on all new-position flows rather than theft of existing collateral.

### Impact Explanation
Temporary freezing of funds / protocol liveness DoS: the victim cannot deposit any collateral type they do not already hold, cannot issue any new synthetic debt, and (via `DepositToken.seize` also calling the same accounting on `transfer` for the feeCollector/liquidator receipts in some paths) liquidation flows touching new tokens for the victim revert. The victim can recover by spending gas to `transfer` the dust out, which triggers `removeFromDepositTokensOfAccount` when the balance reaches zero ( [5](#0-4) ), but until then all new-position operations are bricked and the attacker can re-grief at any time at dust cost.

### Likelihood Explanation
Fully unprivileged: the attacker only needs dust amounts of each listed underlying plus gas. No governor, keeper, or oracle cooperation is required; the modifiers (`onlyIfDepositTokenExists`, `nonReentrant`, `whenNotPaused`, SynthContext checks) do not prevent dust transfers to arbitrary recipients. On chains with several listed collaterals the attacker needs at most ~15 token types to fill half the budget (the other half can be filled by debt tokens issued for the attacker themselves before transferring, or simply by cycling dust of the same token to fresh attacker-controlled recipient counts — each distinct token counts once, so the attack cost scales with the number of listed deposit tokens, which deployments show is non-trivial but finite).

### Recommendation
- Reject `addToDepositTokensOfAccount` additions triggered by plain `transfer` to an account that has not opted in (e.g., only track tokens added via `deposit`), or apply a minimum transfer/deposit threshold before registering the token in the per-account list.
- Alternatively allow a permissionless `removeFromDepositTokensOfAccount`/`sweep` callable by the account owner so victims can self-clean without needing to move balance through transfer semantics.

### Proof of Concept
Hardhat sketch (against deployed Pool/DepositToken fixtures):

```ts
// attacker holds dust of each listed deposit token's underlying
const max = (await pool.MAX_TOKENS_PER_USER()).toNumber();
const depositTokens = await pool.getDepositTokens();
for (const dt of depositTokens.slice(0, max)) {
  const token = await ethers.getContractAt('DepositToken', dt);
  const underlying = await ethers.getContractAt('IERC20', await token.underlying());
  await underlying.connect(attacker).approve(dt, MaxUint256);
  await token.connect(attacker).deposit(2, attacker.address); // dust
  await token.connect(attacker).transfer(victim.address, 1);  // adds to victim's list
}
// victim now has depositTokensOfAccount.length == number of listed tokens
// victim's deposit of any *new* deposit token reverts:
await expect(
  newDepositToken.connect(victim).deposit(parseEther('10'), victim.address)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');
// and issue() of any new synthetic also reverts via addToDebtTokensOfAccount
await expect(
  newDebtToken.connect(victim).issue(parseEther('1'), victim.address)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');
```

Caveat: I could not fully verify `DebtToken.issue`'s `onBehalfOf` semantics within the tool budget — whether the attacker can directly push dust debt onto the victim's list (which would be stronger, since debt entries require repayment to clear) or only fill the list via deposit-token transfers. Either way, the deposit-token dust path alone reproduces the DoS.

        address sender_,

        if (recipient_ == address(0)) revert TransferToTheZeroAddress();

            balanceOf[sender_] = _senderBalanceBefore - amount_;
            balanceOf[recipient_] += amount_;

            pool.addToDepositTokensOfAccount(recipient_);
        }

        // Remove this token from the deposit tokens list if the sender's balance goes to zero
        if (amount_ > 0 && balanceOf[sender_] == 0) {
