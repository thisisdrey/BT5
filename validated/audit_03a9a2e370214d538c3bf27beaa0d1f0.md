## Title
Permanent freezing of witness block/standby rewards when `accumulateWitnessVi` skips a cycle with zero votes - (File: `chainbase/src/main/java/org/tron/core/store/DelegationStore.java`)

## Summary
The analog of the `StakingRewardsV3-1.sol` `rewardPerLiquidity` bug exists in java-tron's cycle-based super-representative (SR) voting-reward accounting. `DelegationStore.accumulateWitnessVi()` accumulates a reward-per-vote index (`Vi`, analogous to `rewardPerLiquidity`) once per maintenance cycle for every witness. If a witness earns block/transaction-fee reward during a cycle in which its snapshotted vote count is `0` (e.g., because all voters withdrew their votes for that SR right before maintenance), the method silently forwards the previous `Vi` instead of distributing the accrued reward, and that reward becomes permanently unclaimable by any account — exactly the "reward accrued while no stake/liquidity was present" freezing pattern described in the report.

## Finding Description
Every block, `Manager.payReward()` credits block reward and transaction-fee reward to the current producing witness through `MortgageService.payBlockReward`/`payTransactionFeeReward`, which both call `payReward()`: [1](#0-0) 

`payReward()` stores the accrued amount keyed by `(cycle, witnessAddress)` in `DelegationStore.addReward`: [2](#0-1) 

At the end of every maintenance cycle, `MaintenanceManager.doMaintenance()` iterates over *all* witnesses (independent of whether votes exist for that cycle) and calls `accumulateWitnessVi` to fold the per-cycle reward into a cumulative reward-per-vote index used later by voters to withdraw their share: [3](#0-2) 

The core accumulation logic is: [4](#0-3) 

If `voteCount == 0` for that witness in that cycle (this snapshot is taken independently, see `setWitnessVote` calls in `doMaintenance`), the branch `if (reward == 0 || voteCount == 0)` fires and the method **only forwards the previous `Vi`** — it never folds `reward` into the index, and there is no code path anywhere that credits this orphaned reward to any account's allowance or rolls it into a future cycle's distributable pool. The `reward` value stored via `addReward` for that `(cycle, address)` key becomes permanently unreachable: `MortgageService.computeReward` (new-algorithm path) only ever reads `Vi` deltas, never `getReward` directly, so any reward not folded into `Vi` is orphaned forever: [5](#0-4) 

This is structurally identical to the `StakingRewardsV3-1.sol` bug: reward accrues over an interval (a block/cycle) during which the "liquidity" (vote weight) backing the pool is zero, so the reward for that interval is dropped rather than carried forward or refunded, permanently locking the corresponding value in the ledger.

## Impact Explanation
A witness's earned block reward / transaction fee reward for a cycle in which it temporarily has zero snapshotted votes is permanently lost — it is neither paid to the witness's brokerage/allowance, nor to any voter, nor rolled forward to the next cycle's `Vi` computation. This is a permanent freezing/loss of protocol-issued TRX that should have been distributable, satisfying "permanent freezing of funds."

## Likelihood Explanation
Reaching a cycle where a witness has non-zero `getReward(cycle, address)` (it produced blocks / collected fees while still active) but `voteCount == 0` for that same cycle snapshot requires unusual but organically reachable conditions: any unprivileged account can call `VoteWitnessContract` to withdraw all its votes from an SR right before a maintenance boundary, or a witness can be removed from active/standby status losing all votes mid-cycle while it had already accumulated reward earlier in the same cycle via `payBlockReward`. This does not require any special privilege — normal voting and normal block production trigger the vulnerable code path.

## Recommendation
Modify `DelegationStore.accumulateWitnessVi` so that when `voteCount == 0` but `reward > 0`, the reward is not silently dropped: either (a) roll the un-distributable reward forward into the next cycle's reward pool for that witness (`addReward(cycle + 1, address, reward)`), or (b) redirect it to the witness's own allowance/brokerage, mirroring the fix recommended for `StakingRewardsV3-1.sol` of not skipping reward accounting for periods lacking active participants.

## Proof of Concept
1. Witness `W` is active and receives block rewards during cycle `N` via `Manager.payReward` → `MortgageService.payBlockReward` → `DelegationStore.addReward(N, W, reward)`.
2. Before `doMaintenance()` finalizes cycle `N`, all voters call `VoteWitnessContract` to withdraw their votes from `W`, and `MaintenanceManager.doMaintenance()` records `witnessCapsule.getVoteCount() == 0` for `W` for cycle `N` via `delegationStore.setWitnessVote(nextCycle, ...)` / the vote-count snapshot used by `accumulateWitnessVi`.
3. `MaintenanceManager.doMaintenance()` calls `delegationStore.accumulateWitnessVi(N, W, 0)`.
4. Because `voteCount == 0`, the branch at `DelegationStore.java:136-139` only forwards `preVi`; `reward` from step 1 is never folded in.
5. No subsequent code path (`MortgageService.computeReward`, `queryReward`, `withdrawReward`) ever reads `getReward(N, W)` directly for the new algorithm, so the TRX credited in step 1 is permanently unclaimable by anyone.

  public void accumulateWitnessVi(long cycle, byte[] address, long voteCount) {
    BigInteger preVi = getWitnessVi(cycle - 1, address);
    long reward = getReward(cycle, address);
    if (reward == 0 || voteCount == 0) { // Just forward pre vi
      if (!BigInteger.ZERO.equals(preVi)) { // Zero vi will not be record
        setWitnessVi(cycle, address, preVi);
      }
    } else { // Accumulate delta vi
      BigInteger deltaVi = BigInteger.valueOf(reward)
          .multiply(DECIMAL_OF_VI_REWARD)
          .divide(BigInteger.valueOf(voteCount));
      setWitnessVi(cycle, address, preVi.add(deltaVi));
    }
  }
