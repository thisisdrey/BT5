Audit Report

## Title
Reward-per-token precision loss in `pallet-asset-rewards` causes permanent, unrecoverable reward loss for stakers of high-decimal / low-reward-rate pools - (File: `substrate/frame/asset-rewards/src/lib.rs`)

## Summary
`reward_per_token()` computes each period's reward increment as `reward_rate_per_block * blocks_elapsed * PRECISION_SCALING_FACTOR (4096) / total_tokens_staked`, and this increment is checkpointed into storage every time `stake`, `unstake`, `harvest_rewards`, or `set_pool_reward_rate_per_block` is called via `update_pool_rewards`. Because `PRECISION_SCALING_FACTOR` is a fixed constant of only `4096` (~2^12) rather than a decimals-aware or much larger fixed-point base (e.g. `1e18` as used by the Synthetix model this pallet is explicitly based on), pools where `total_tokens_staked` (raw units of an arbitrary, admin-chosen asset) is large relative to `reward_rate_per_block * blocks_elapsed * 4096` will see this division truncate to `0` on every checkpoint, and that lost fraction is never recovered in subsequent periods since each checkpoint only computes the increment for its own elapsed-block window.

## Finding Description
The relevant code is: [1](#0-0) [2](#0-1) [3](#0-2) 

`reward_per_token()` is called from `update_pool_and_staker_rewards`, which every `stake`/`unstake`/`harvest_rewards` invocation routes through, and the result is persisted via `update_pool_rewards`, which simply overwrites `reward_per_token_stored` with the freshly computed cumulative value and resets `last_update_block` to the current block: [4](#0-3) 

Each call to `reward_per_token` only accounts for blocks elapsed since the *previous* checkpoint (`rewardable_blocks_elapsed`), not the pool's entire lifetime. If, in a given elapsed-block window, `reward_rate_per_block * rewardable_blocks_elapsed * 4096 < total_tokens_staked`, the `ensure_div` truncates to `0` for that window and there is no remainder tracking mechanism to carry the truncated fraction forward — the next checkpoint again starts its own independent, truncated computation over the newly elapsed window. Since `staked_asset_id`/`reward_asset_id` are arbitrary `pallet-assets` assets with independent decimals and rate, and there is no validation tying `reward_rate_per_block`/`PRECISION_SCALING_FACTOR` to plausible `total_tokens_staked` magnitudes, this can happen under ordinary (non-malicious) configuration — e.g., an 18-decimal staked asset against a modest reward rate — especially when checkpoints occur frequently (many stakers calling public `stake`/`unstake`/`harvest_rewards` extrinsics), causing systematic zeroing of reward accrual.

## Impact Explanation
This causes real reward-asset balances funded into the pool account (via `deposit_reward_tokens`) to become permanently unclaimable by legitimate stakers, since `staker_info.rewards` never advances past `0` under the triggering conditions, and `cleanup_pool` only returns leftover balance to the pool admin, not to stakers. This aligns with the permitted "permanent user-fund lock" / "runtime bug that compromises intended behavior" impact class, since ordinary stakers using public `stake`, `unstake`, and `harvest_rewards` extrinsics — not any privileged actor — trigger and perpetuate the loss once a susceptible pool configuration exists.

## Likelihood Explanation
Triggering the bug does not require a malicious actor or privileged origin at the staker level; any account calling the public `stake`/`unstake`/`harvest_rewards` extrinsics on a pool with a large-decimals staked asset and modest reward rate can reproduce the truncation deterministically, and frequent legitimate activity (many stakers interacting, or periodic harvesting) increases the number of small, truncation-prone elapsed-block windows. The pool's initial asset/rate choice is made by the (privileged) `create_pool` origin, but this is a plausible, non-malicious configuration choice (e.g., differing decimals between staked and reward assets) rather than deliberate admin abuse, and the pallet performs no validation to prevent it, so the vulnerability is a design defect in unprivileged-reachable accounting logic, not an admin-abuse scenario.

## Recommendation
Increase `PRECISION_SCALING_FACTOR` to a much larger, decimals-robust fixed-point base (e.g., `1e18`, mirroring Synthetix's `StakingRewards.sol` and matching precision levels used elsewhere in the codebase such as `pallet-nomination-pools`'s `FixedU128`-based reward counters), and/or track the truncated remainder explicitly across checkpoints so fractional reward-per-token amounts are never silently dropped when `total_tokens_staked` is large relative to `reward_rate_per_block`. Consider adding validation at `create_pool`/`set_pool_reward_rate_per_block` time bounding the plausible ratio between `reward_rate_per_block * PRECISION_SCALING_FACTOR` and expected `total_tokens_staked` magnitudes, and add targeted regression tests (as `nomination-pools`' `reward_counter_precision` module does) exercising high-decimals staked assets paired with low-rate reward assets.

## Proof of Concept
1. `create_pool` with `staked_asset_id` = an 18-decimal asset and `reward_asset_id` with `reward_rate_per_block = 1_000`.
2. Stake `1_000_000 * 10^18` units so `total_tokens_staked = 1e24`.
3. `deposit_reward_tokens` to fund the pool with a real reward-asset balance.
4. Have any account repeatedly call `stake`/`unstake` (or `harvest_rewards`) each block so `rewardable_blocks_elapsed = 1` per checkpoint in `update_pool_rewards`.
5. Each checkpoint computes `1_000 * 1 * 4096 / 1e24 = 4_096_000 / 1e24 → 0` via `ensure_div` in `reward_per_token` (`substrate/frame/asset-rewards/src/lib.rs` lines 803-809), so `reward_per_token_stored` never advances.
6. Call `harvest_rewards` for the original staker later — `derive_rewards` (lines 815-824) returns `0`, despite real elapsed blocks, a positive reward rate, and a funded pool balance.

```rust
		/// Derives the current reward per token for this pool.
		pub(super) fn reward_per_token(
			pool_info: &PoolInfoFor<T>,
		) -> Result<T::Balance, DispatchError> {
			if pool_info.total_tokens_staked.is_zero() {
				return Ok(pool_info.reward_per_token_stored);
			}

			let rewardable_blocks_elapsed: u32 =
				match Self::last_block_reward_applicable(pool_info.expiry_block)
					.ensure_sub(pool_info.last_update_block)?
					.try_into()
				{
					Ok(b) => b,
					Err(_) => return Err(Error::<T>::BlockNumberConversionError.into()),
				};

			Ok(pool_info.reward_per_token_stored.ensure_add(
				pool_info
					.reward_rate_per_block
					.ensure_mul(rewardable_blocks_elapsed.into())?
					.ensure_mul(PRECISION_SCALING_FACTOR.into())?
					.ensure_div(pool_info.total_tokens_staked)?,
			)?)
		}
```
