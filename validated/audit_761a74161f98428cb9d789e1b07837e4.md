### Title
Unvalidated `new_authority` in Account Transfer Leads to Permanent Loss of Account Access - (File: `programs/marginfi/src/instructions/marginfi_account/transfer_account.rs`)

### Summary
The `TransferToNewAccount` and `TransferToNewAccountPda` instructions let a `MarginfiAccount` authority migrate all their positions to a new account under a caller-supplied `new_authority`, but the program performs no validation that `new_authority` is non-zero or otherwise a sane, controllable key before permanently disabling the old account. [1](#0-0) [2](#0-1) 

### Finding Description
`new_authority` is declared as an `UncheckedAccount` explicitly commented "WARN: New authority is completely unchecked", and is used directly as the authority of the freshly initialized account with no `require!(new_authority != Pubkey::default())` or any other sanity check. [3](#0-2) 

Once `transfer_to_new_account` (or the PDA variant) executes, the old account is irreversibly finalized: its `lending_account` is zeroed, it is flagged `ACCOUNT_DISABLED`, and `migrated_to` is set to the new account — a one-way migration guarded by `check_eq!(old_account.migrated_to, Pubkey::default(), ...)` that prevents any retry. [4](#0-3) [5](#0-4) 

The new account is initialized with `new_authority` as its sole authority with no further check: [6](#0-5) 

This mirrors the reported `Ownable.sol` bug class — an ownership/authority transfer with no destination validation — but here it is reachable by any unprivileged marginfi user acting on their own account, and the on-chain test/comment set confirms this is by design ("WARN: User picks the new authority with no restrictions!"). [7](#0-6) 

### Impact Explanation
If a user (or client-side integration bug/typo) supplies an incorrect `new_authority` — e.g., `Pubkey::default()`, a burned key, or a key nobody controls — all of the account's lending positions (deposits/borrows, migrated verbatim via `new_account.lending_account = old_account.lending_account`) become permanently inaccessible: the old account is disabled and cannot be migrated again (`AccountAlreadyMigrated`), and the new account's sole authority is unrecoverable. [8](#0-7)  This is a permanent lock/freeze of user funds with no recovery path, since no admin override exists for account authority.

### Likelihood Explanation
Likelihood is low-to-moderate: it requires either user error, a client bug, or a malicious front-end constructing the transaction with a wrong/attacker-controlled `new_authority`, but the transfer is a single, irreversible, one-shot operation with no confirmation/staging step and no zero-address guard, unlike typical two-step ownership transfer patterns.

### Recommendation
Add an explicit check that `new_authority != Pubkey::default()` (and optionally require the new authority to co-sign or claim the account) in both `transfer_to_new_account` and `transfer_to_new_account_pda`, mirroring the zero-address guard already present in the off-chain CLI helper `marginfi_account_transfer`. [9](#0-8) 

### Proof of Concept
1. User calls `transferAccountAuthorityIx` (`TransferToNewAccount`) on their own `MarginfiAccount`, signing as `authority`, and passes `new_authority = Pubkey.default()` (or any key they do not control) along with a fresh `new_account` keypair. [10](#0-9) 
2. The instruction succeeds: `initialize_migrated_account` sets `new_account.authority = new_authority` unconditionally, and `finalize_migrated_old_account` disables the old account and records `migrated_to`. [11](#0-10) 
3. The old account can never be migrated again (`AccountAlreadyMigrated` check on retry), and the new account's funds are now controlled by an address nobody can sign for — permanently locking all migrated collateral/borrows. [12](#0-11)
