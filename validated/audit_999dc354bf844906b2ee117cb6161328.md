## Title
Unauthenticated DoS via unbounded field count in `application/x-www-form-urlencoded` HTTP API bodies bypassing the JSON parser's DoS guard - (File: `framework/src/main/java/org/tron/core/services/http/Util.java`)

### Summary
Every write-capable HTTP servlet (`BroadcastServlet`, `CreateAccountServlet`, `DeployContractServlet`, `FreezeBalanceServlet`, `CreateAssetIssueServlet`, `DelegateResourceServlet`, etc.) reads its POST body through `PostParams.getPostParams()`, which for JSON bodies feeds the body into the hardened JSON pipeline (`Constant.MAX_NESTING_DEPTH` / `Constant.MAX_TOKEN_COUNT` enforced via `StreamReadConstraints`, see `common/src/main/java/org/tron/core/Constant.java:67-69`), but for `application/x-www-form-urlencoded` bodies routes through `Util.getJsonString()`, which parses the body with Jetty's `UrlEncoded.decodeUtf8To()` into a `MultiMap` and rebuilds a `JSONObject` field-by-field with **no cap on the number of fields**. This is structurally identical to the Starlette advisory: one content-type is protected by an explicit limit, the sibling content-type for the same "parse form into structured data" operation is not.

### Finding Description
`PostParams.getPostParams()` reads the whole request body, checks only its total byte size, and for form-encoded content types converts it via `Util.getJsonString()`: [1](#0-0) 

`Util.getJsonString()` bypasses `JSON.parseObject`/the Jackson-backed parser entirely for non-JSON bodies. It hands the raw string straight to Jetty's `UrlEncoded.decodeUtf8To`, which appends every `key=value` pair into a `MultiMap` with no limit on entry count, and then iterates the entire map to build a `JSONObject`: [2](#0-1) 

Compare this with the JSON body path, which is explicitly documented and tested as a DoS mitigation: `Constant.MAX_NESTING_DEPTH = 20` and `Constant.MAX_TOKEN_COUNT = 100_000` are wired into the Jackson `StreamReadConstraints` used by `JSON.MAPPER` (`framework/src/test/java/org/tron/json/JsonTest.java:404-409`) and by `JsonFormat`'s recursion guard (`framework/src/main/java/org/tron/core/services/http/JsonFormat.java:1335-1340`). No analogous field-count or size-per-field constraint exists for the urlencoded path in `Util.getJsonString()` or in `PostParams.getPostParams()`.

`Util.checkBodySize()` only enforces total request byte size (`httpMaxMessageSize`), not field count: [3](#0-2) 

A sub-limit-size body (e.g. `a=1&a=1&...` repeated hundreds of thousands of times) can therefore contain an unbounded number of key/value pairs. `UrlEncoded.decodeUtf8To` and the subsequent `JSONObject`/`Map` construction run synchronously on the Jetty request-handling thread, exactly mirroring the Starlette bug class: one encoding of "parse form data" is guarded (JSON body via `StreamReadConstraints` token-count limit), the other (`x-www-form-urlencoded`) is not.

### Impact Explanation
Any anonymous API client can POST a small, well-under-the-byte-limit `application/x-www-form-urlencoded` body containing a very large number of fields to any write-oriented Wallet HTTP endpoint (`/wallet/broadcasttransaction`, `/wallet/createtransaction`, `/wallet/deploycontract`, etc., all of which route through `PostParams.getPostParams`). Each such request forces synchronous parsing (`MultiMap` population + `JSONObject` rebuild) proportional to the field count, consuming CPU and memory on the request thread without hitting the JSON-parser's token-count guard, since the JSON path is bypassed entirely for this content type. Concurrent requests of this shape can exhaust HTTP worker capacity, denying legitimate API access — matching the "no impact" exclusion boundary is avoided because this is a concrete "API the node can no longer serve" condition, not a purely theoretical resource concern.

### Likelihood Explanation
High: the target endpoints are unauthenticated, reachable by any external API client, accept content type negotiation, and the vulnerable helper (`Util.getJsonString`/`PostParams.getPostParams`) is shared by essentially every write-side HTTP servlet in `framework/src/main/java/org/tron/core/services/http/`. No signature, permission, or on-chain state is required to trigger it — a single crafted POST suffices.

### Recommendation
Enforce a field-count (and per-field length) limit in `Util.getJsonString()`/`PostParams.getPostParams()` for `application/x-www-form-urlencoded` bodies, symmetric to the `Constant.MAX_TOKEN_COUNT`/`MAX_NESTING_DEPTH` guard already applied to JSON bodies (e.g., reject once `UrlEncoded` produces more than N entries, or use `UrlEncoded.decodeUtf8To` overloads/`MultiMap` size checks before building the `JSONObject`), and document/configure the limit alongside `httpMaxMessageSize`.

### Proof of Concept
1. Build a POST body: `f0=v&f1=v&...&fN=v` with N ≈ 500,000–1,000,000 short fields (keeps total size well under the default `httpMaxMessageSize`).
2. Send it with `Content-Type: application/x-www-form-urlencoded` to any Wallet POST endpoint, e.g. `POST /wallet/broadcasttransaction`.
3. `PostParams.getPostParams` → `Util.getJsonString` builds a `MultiMap` and `JSONObject` with all N entries synchronously, with no field-count check, unlike the equivalent JSON-body path that is bounded by `Constant.MAX_TOKEN_COUNT`.
4. Repeat the request concurrently to observe HTTP worker-thread exhaustion / elevated CPU and memory on the node while other API calls stall or time out.

  public static String getJsonString(String str) {
    if (StringUtils.isEmpty(str)) {
      return EMPTY;
    }
    if (isValidJson(str)) {
      return str;
    }
    MultiMap<String> params = new MultiMap<>();
    UrlEncoded.decodeUtf8To(str, params);
    JSONObject json = new JSONObject();
    for (Map.Entry<String, List<String>> entry : params.entrySet()) {
      String key = entry.getKey();
      List<String> values = entry.getValue();
      if (values.size() == 1) {
        json.put(key, values.get(0));
      } else {
        json.put(key, values);
      }
    }
    return json.toString();
  }
