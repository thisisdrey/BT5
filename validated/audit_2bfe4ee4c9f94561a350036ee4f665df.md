### Title
Replay-window check/decrypt/update race in `ConnectionState.Decrypt` allows a duplicated packet to bypass replay protection - (File: connection_state.go)

### Summary
`ConnectionState.Decrypt` (and its sibling `VerifyRelay`) implement replay protection as three separate critical sections instead of one atomic operation: `window.Check` (lock/unlock), then AEAD decrypt (no lock held), then `window.Update` (lock/unlock). This is structurally the same "check external-work-then-write-state" ordering flaw described in the reference report: the authoritative state write (`window.Update`, analogous to `fundsTransfered[user] = true`) happens only *after* the expensive external-facing step (AEAD decrypt), with the lock released in between.

### Finding Description
`Decrypt` is:
```go
cs.decryptLock.Lock()
result := cs.window.Check(l, messageCounter)
cs.decryptLock.Unlock()
if !result { return nil, ErrAlreadySeen }

out, err = cs.dKey.DecryptDanger(out, packet[:header.Len], packet[header.Len:], messageCounter, nb)
...

cs.decryptLock.Lock()
result = cs.window.Update(l, messageCounter)
cs.decryptLock.Unlock()
if !result { return nil, ErrAlreadySeen }
return out, nil
``` [3](#0-2) 

Nebula supports multiple concurrent UDP reader goroutines bound to the same socket via `SO_REUSEPORT` when `routines > 1` is configured, each independently invoking `readOutsidePackets` → `hostinfo.ConnectionState.Decrypt` for whatever packet the kernel happens to hand it: [1](#0-0) [2](#0-1) 

If an attacker (who already possesses a previously captured/relayed ciphertext for an established tunnel — this does not require holding a CA-signed certificate, only network-level packet duplication/injection) transmits two copies of the same packet at once, both can land on different reader goroutines. Because `Check` and `Update` are not atomic with each other, both goroutines can pass `Check` before either calls `Update`, causing both to run `DecryptDanger` for the *same nonce/counter* with independent buffers. This decrypt-under-race pattern is the direct analog of the reentrancy bug: the guard variable (`fundsTransfered[user]` / `window` bit) is read, an expensive/externally-observable action is performed, and only then is the guard state committed — allowing the guarded action to run twice for input that was supposed to be single-use.

### Impact Explanation
Worst case, this is a duplicate-processing / replay-tolerance weakening bug: a replayed data packet can be decrypted and (if it also wins the racing `Update`) delivered to the TUN device twice, undermining Nebula's stated replay protection guarantee for that instant. Nebula's own changelog history shows the project has repeatedly hardened this exact code path (`Advance the replay window on relayed packets...`, `Lock replay window updates so concurrent readers can't corrupt it (#1802)`), demonstrating that replay-window integrity is treated as a security property. [4](#0-3) 

### Likelihood Explanation
Requires `routines > 1` (multi-reader mode) so that the two `Check` calls can race on different goroutines; single-routine deployments are not affected because packet handling is single-threaded per socket. This is a real, supported configuration (documented under `routines`/`listen.routines`), so the precondition is reachable by an attacker who can send duplicate UDP frames to a node running with multiple listener routines. [5](#0-4) 

### Recommendation
- Short term: Perform the replay-window `Check` and the final acceptance `Update` as a single atomic critical section (hold `decryptLock` across the check-decrypt-update sequence, or use a compare-and-set primitive so a second concurrent caller for the same counter is rejected before it ever calls `DecryptDanger`).
- Long term: Audit all call sites of `Bits.Check`/`Bits.Update` (`Decrypt`, `VerifyRelay`) to guarantee the mark-as-seen step cannot be separated in time from the check step, consistent with the check-effects-interactions principle: commit state before/atomically-with performing the guarded action, not after.

### Proof of Concept
1. Start a node with `routines: 2` (or more) so `SupportsMultipleReaders`/`SO_REUSEPORT` is active. [6](#0-5) 
2. Capture one legitimate encrypted data packet destined for this node from an established tunnel.
3. Fire two (or more) copies of that identical UDP datagram at the node's listen port back-to-back, so the kernel's SO_REUSEPORT load-balancer is likely to dispatch them to different reader goroutines/queues.
4. Both `listenOut` goroutines call `readOutsidePackets` → `ConnectionState.Decrypt` for the same `messageCounter`; because `window.Check` releases the lock before `DecryptDanger` runs, both can pass `Check` and both perform a full AEAD decrypt for the same nonce before either commits via `window.Update`, only one of which is truly supposed to be allowed to have proceeded past the check.
