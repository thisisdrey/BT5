### Title
Fully-terminated `pallet-revive` contracts leave an unowned, key-less account that permanently locks any value later sent to it - ([File: substrate/frame/revive/src/exec.rs])

### Summary
The bug-class in the report is: `selfdestruct()` removes contract code but leaves the address able to receive value; any transaction landing *after* the destruction succeeds trivially and its `msg.value` is permanently locked because the recipient account has no code and no private key to move the funds. `pallet-revive`'s `terminate` precompile (`ISystem.terminate`) reproduces the same primitive: it can fully remove a contract's account across distinct transactions, and the dead H160 address it leaves behind has no corresponding signing key, so any value later routed to it is unrecoverable.

### Finding Description
`do_terminate` in `substrate/frame/revive/src/exec.rs` performs the actual account removal: [1](#0-0) [2](#0-1) 

It transfers the contract's balance to `args.beneficiary` and then synchronously removes `AccountInfoOf` and `ImmutableDataOf` for the contract address in the same transaction: [3](#0-2) 

This path is reachable via the `ISystem.terminate` precompile (`terminate_caller`, `terminate_if_same_tx`) even when the contract was **not** created in the same transaction, which is explicitly documented as intentional so that termination can happen "across distinct transactions": [4](#0-3) [5](#0-4) 

The developers were aware that value can arrive *during* the same call stack that is executing termination, and added a mitigation that re-reads the current balance right before deletion so in-flight transfers in the same transaction are forwarded to the beneficiary: [6](#0-5) 

However, this only protects the same call stack/transaction. Once `do_terminate` commits (`AccountInfoOf::remove`, `ImmutableDataOf::remove`), the contract address becomes an ordinary, code-less account with **no corresponding private key** (contract addresses are deterministically derived, not EOA-derived). A confirming PR doc explicitly lists as still-outstanding, unverified work: "Test that value send to a contract after scheduling for deletion is send to the beneficiary" - i.e. only the in-flight/same-tx race was addressed, not the cross-transaction race: [7](#0-6) 

Existing tests only validate the delayed-scheduling behaviour when both the send and the pickup happen inside one call frame (same block, same call stack), and only for the precompile method: [8](#0-7) 

There is no test or code path shown that intercepts value sent to the (now nonexistent, unowned) address in a **later, independent transaction** after `do_terminate` has already committed and `AccountInfoOf` no longer exists.

### Impact Explanation
Any value transferred to the contract address after full termination has committed is credited to a plain `Balances` entry keyed by an address for which no party holds a signing key (the address was never an EOA). Just like the original Solidity finding, this is a permanent, unbacked lock of user funds with no recovery path, matching the "permanent user-fund lock" impact class for pallet-revive execution.

### Likelihood Explanation
This requires only unprivileged, public actions: any account may call `ISystem.terminate` on a contract it is not required to own/control-check beyond normal reentrancy guards, and any other user may independently send a call with value to that same contract address. Because block production naturally interleaves independent transactions from the mempool (mirroring the Alice/Bob scenario in the source report), a termination transaction and a value-carrying call to the same address landing in different transactions is a realistic, attacker-observable race, not one requiring a malicious validator, relayer, or admin.

### Recommendation
- Do not fully remove `AccountInfoOf` for a terminated contract address; instead, retain a minimal "tombstone" marker that causes any subsequent value-bearing call or transfer to that address to be rejected (revert) rather than silently succeed, or auto-forward the value to the last known beneficiary.
- Alternatively, ensure `AccountInfoOf` removal happens only after a well-defined delay/epoch during which the address is treated as unspendable-to (analogous to how EIP-4758 discourages `SELFDESTRUCT`), and reject any external value transfer targeting a queued/removed contract address at the dispatch layer.
- Extend the currently-missing test noted in the PR doc (`pr_10302.prdoc`) to explicitly cover value sent to a *fully terminated* address in a transaction strictly after termination has committed, across blocks, and assert funds are not stranded.

### Proof of Concept
1. Contract `C` is instantiated (not in the same tx as any later termination call) and is fully alive.
2. Attacker (or anyone) calls `ISystem.terminate(beneficiary)` on `C` via the precompile in transaction `T1`. `do_terminate` runs, transfers `C`'s current balance to `beneficiary`, and removes `AccountInfoOf(C)` and `ImmutableDataOf(C)` — `substrate/frame/revive/src/exec.rs:1826-1842`.
3. `T1` is included in block `N`.
4. A second, independent user's transaction `T2` (already broadcast/pending, unaware `C` was just destroyed — exactly the Alice/Bob mempool race in the original report) performs `call(C, value=X)` and lands in block `N` (after `T1`) or block `N+1`.
5. Because `AccountInfoOf(C)` no longer exists, `C`'s address behaves like an address with no contract at all: the value transfer succeeds trivially and credits `C`'s `Balances` entry.
6. `C`'s address was never an EOA (no private key exists for it), so `X` is permanently unrecoverable — reproducing the exact "H-01" fund-lock primitive from the external report inside `pallet-revive`.

	fn terminate_caller(&mut self, beneficiary: &H160) -> Result<(), DispatchError> {
		ensure!(self.top_frame().delegate.is_none(), Error::<T>::PrecompileDelegateDenied);
		let parent = self.frames_mut().nth(1).ok_or_else(|| Error::<T>::ContractNotFound)?;
		ensure!(parent.entry_point == ExportedFunction::Call, Error::<T>::TerminatedInConstructor);
		ensure!(parent.delegate.is_none(), Error::<T>::PrecompileDelegateDenied);

		let info = parent.contract_info();
		let trie_id = info.trie_id.clone();
		let code_hash = info.code_hash;
		let contract_address = T::AddressMapper::to_address(&parent.account_id);
		let beneficiary = T::AddressMapper::to_account_id(beneficiary);

		let parent_account_id = parent.account_id.clone();

		// balance transfer is immediate
		Self::transfer(
			&self.origin,
			&parent_account_id,
			&beneficiary,
			<Contracts<T>>::evm_balance(&contract_address),
			Preservation::Preserve,
			&mut top_frame_mut!(self).frame_meter,
			&self.exec_config,
		)?;

		// schedule for delayed deletion
		let args = TerminateArgs { beneficiary, trie_id, code_hash, only_if_same_tx: false };
		self.top_frame_mut().contracts_to_be_destroyed.insert(parent_account_id, args);

		Ok(())

fn sent_funds_after_terminate_shall_be_credited_to_beneficiary_precompile(
	caller_type: FixtureType,
	callee_type: FixtureType,
) {
	let (code, _) = compile_module_with_type("Terminate", callee_type).unwrap();
	let (caller_code, _) = compile_module_with_type("TerminateCaller", caller_type).unwrap();
	ExtBuilder::default().build().execute_with(|| {
		let min_balance = Contracts::min_balance();
		let _ = <Test as Config>::Currency::set_balance(&ALICE, 100_000_000_000);

		let Contract { addr, .. } = builder::bare_instantiate(Code::Upload(code))
			.constructor_data(
				Terminate::constructorCall {
					skip: true,
					method: METHOD_PRECOMPILE,
					beneficiary: DJANGO_ADDR.0.into(),
				}
				.abi_encode(),
			)
			.build_and_unwrap_contract();
		let account = <Test as Config>::AddressMapper::to_account_id(&addr);

		assert!(get_contract_checked(&addr).is_some(), "contract does not exist after create");
		assert_eq!(get_balance(&account), min_balance, "unexpected contract balance after create");

		let Contract { addr: caller_addr, .. } =
			builder::bare_instantiate(Code::Upload(caller_code))
				.native_value(125)
				.build_and_unwrap_contract();
		let caller_account = <Test as Config>::AddressMapper::to_account_id(&caller_addr);

		assert_eq!(
			get_balance(&caller_account),
			125 + min_balance,
			"unexpected caller balance before terminate"
		);

		let result = builder::bare_call(caller_addr)
			.data(
				TerminateCaller::sendFundsAfterTerminateCall {
					terminate_addr: addr.0.into(),
					value: alloy_core::primitives::U256::from(123_000_000u64),
					method: METHOD_PRECOMPILE,
					beneficiary: DJANGO_ADDR.0.into(),
				}
				.abi_encode(),
			)
			.build_and_unwrap_result();

		assert!(

			result.data.is_empty(),
			"sendFundsAfterTerminateCall returned unexpected data: {:?}",
			result.data
		);
		assert!(get_contract_checked(&addr).is_none(), "contract still exists after terminate");
		assert_eq!(
			get_balance(&DJANGO),
			123 + min_balance,
			"unexpected DJANGO balance after terminate"
		);
		assert_eq!(get_balance(&account), 0, "contract has balance after terminate");
