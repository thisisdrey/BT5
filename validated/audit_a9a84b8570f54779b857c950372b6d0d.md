### Title
RewardsDistributor credits `balance * INITIAL_INDEX` (≈1e18× balance) of rewards to pre-existing holders when claimed while the token index still equals `INITIAL_INDEX` - (File: contracts/RewardsDistributor.sol)

### Summary
`RewardsDistributor._calculateTokenDelta` treats an account index of `0` as "existed before rewards started" and backfills it with `INITIAL_INDEX`, but only when the global token index is strictly greater than `INITIAL_INDEX`. When the global index still equals `INITIAL_INDEX` (i.e., no reward accrual period has elapsed since the token was registered), the fallback is skipped, `accountIndexOf` stays `0`, and the delta index becomes `1e18`. Analogous to CVE-2021-47413 — a value populated under one condition (`_tokenIndex > INITIAL_INDEX`) is consumed under a broader one (`_tokenIndex >= INITIAL_INDEX`), so the consumer dereferences a "null" (zero) that was never meant to be read — the account's accrued reward is computed as `balance * 1e18`, letting the first claimer drain the entire `rewardToken` balance of the distributor.

### Finding Description
When a DepositToken/DebtToken is registered for rewards via `updateTokenSpeed(token_, speed_ > 0)`, its `TokenState` is initialized to `{index: INITIAL_INDEX (1e18), timestamp: block.timestamp}` and pushed into `tokens[]` (`contracts/RewardsDistributor.sol:296-299`). Any account already holding that token has `accountIndexOf[token][account] == 0`.

In `_calculateTokenDelta` (`contracts/RewardsDistributor.sol:217-231`):

```solidity
_tokenIndex = _tokenState.index;                       // = INITIAL_INDEX if no accrual yet
uint256 _accountIndex = accountIndexOf[token_][account_]; // = 0 for pre-existing holder
if (_accountIndex == 0 && _tokenIndex > INITIAL_INDEX) {  // false when _tokenIndex == INITIAL_INDEX
    _accountIndex = INITIAL_INDEX;
}
uint256 _deltaIndex = _tokenIndex - _accountIndex;     // = 1e18 - 0 = 1e18
_tokensDelta = token_.balanceOf(account_).wadMul(_deltaIndex); // = balance * 1e18
```

The intended baseline (`_accountIndex = INITIAL_INDEX`) is only applied when `_tokenIndex > INITIAL_INDEX`. In the window where `tokenSpeeds` is set but `_updateTokenIndex` has not advanced the index — most easily the same block as the `updateTokenSpeed`/`syncTokenSpeed` call — the zero account index is consumed directly, producing `_tokensDelta = balance * 1e18`, stored in `tokensAccruedOf[account]` by `_updateTokensAccruedOf` (`contracts/RewardsDistributor.sol:261-266`).

`claimRewards(address[] accounts_, IERC20[] tokens_)` is permissionless (`contracts/RewardsDistributor.sol:150-168`) and pays `tokensAccruedOf[account_]` to `account_` via `_transferRewardIfEnoughTokens` (`contracts/RewardsDistributor.sol:248-256`), which caps the payout at the distributor's whole `rewardToken` balance. The attacker therefore receives `min(balance * 1e18, distributor rewardToken balance)` — i.e., the entire reward reserve.

Note that `updateBeforeTransfer`/`updateBeforeMintOrBurn` do not protect pre-existing holders: they only fix an account's index when that account transfers/mints/burns *after* registration, and they suffer the same bug if called in the same zero-accrual window.

### Impact Explanation
Direct theft of unclaimed yield: the attacker siphons the distributor's entire `rewardToken` balance (e.g., MET or esMET funded for emissions) into `tokensAccruedOf[attacker]` and withdraws it in the same transaction via `claimRewards`. All legitimate depositors/borrowers lose their accrued and future rewards for that distributor.

### Likelihood Explanation
Reachable by any unprivileged EOA holding a registered pool's deposit/debt token. Two trigger windows:

1. **Same-block back-run:** the governor's `updateTokenSpeed(token_, speed>0)` (or keeper's `syncTokenSpeed`) transaction is observable in the mempool; the attacker holds the deposit token beforehand and sandwiches `claimRewards` in the same block before `block.timestamp` advances the index. Standard MEV/bundle ordering makes this practical on mainnet/L2.
2. **Any stale-index window:** whenever `tokenSpeeds[token] == 0` and `tokenStates[token].index == INITIAL_INDEX` — e.g., a token registered with speed then... (index > INITIAL once time passes, so the same-block window is the reliable trigger).

No modifier stops it: `claimRewards` has only `nonReentrant`, `onlyIfTokenExists` is satisfied because the token is a real DepositToken, and `tokenStates[token].index > 0` is true.

### Recommendation
Initialize the account baseline whenever the stored account index is zero, regardless of the global index value:

```solidity
if (_accountIndex == 0 && _tokenIndex >= INITIAL_INDEX) {
    _accountIndex = INITIAL_INDEX;
}
```

Equivalently, clamp `_deltaIndex` to `0` when `_tokenIndex <= _accountIndex` after the fallback, so a pre-existing holder's first update yields zero delta instead of `1e18×balance`.

### Proof of Concept
Foundry (fork or local deployment of `Pool`, `DepositToken`, `RewardsDistributor`, reward ERC20):

```solidity
// Given: pool, depositToken (attacker already holds D balance), distributor, rewardToken
// Fund distributor
deal(address(rewardToken), address(distributor), 1_000_000e18);

// Governor registers the deposit token for rewards
vm.prank(governor);
distributor.updateTokenSpeed(IERC20(address(depositToken)), 1e18); // speed > 0

// SAME BLOCK: attacker claims before index advances past INITIAL_INDEX
assertEq(distributor.tokenStates(IERC20(address(depositToken))).index, 1e18); // == INITIAL_INDEX

uint256 balBefore = rewardToken.balanceOf(attacker);
IERC20[] memory t = new IERC20[](1);
t[0] = IERC20(address(depositToken));
vm.prank(attacker);
distributor.claimRewards(attacker, t); // permissionless

// tokensAccruedOf[attacker] was set to D * 1e18; payout capped at distributor balance
assertEq(rewardToken.balanceOf(attacker) - balBefore, 1_000_000e18); // entire reserve stolen
assertEq(rewardToken.balanceOf(address(distributor)), 0);
```
