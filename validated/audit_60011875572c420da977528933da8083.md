### Title
Stale Votes from Removed-then-Re-added Owners Bypass k-of-n Approval Threshold in Multisig Account - (File: `aptos-move/framework/aptos-framework/sources/multisig_account.move`)

---

### Summary

`update_owner_schema()` removes an owner from the `owners` vector but never clears that owner's existing votes from any pending `MultisigTransaction.votes` maps. When the same address is later re-added as an owner, `num_approvals_and_rejections_internal()` immediately counts the stale votes again — without the re-added owner having to explicitly re-approve. This is the direct Aptos analog of the Sublime `pendingLinkAddresses` bug: authorization state set before revocation persists through the revocation and is silently reactivated on re-entry.

---

### Finding Description

`MultisigTransaction` stores per-owner votes in a `SimpleMap<address, bool>`:

```move
struct MultisigTransaction has copy, drop, store {
    ...
    votes: SimpleMap<address, bool>,
    ...
}
```

Vote counting in `num_approvals_and_rejections_internal` iterates the **current** `owners` list and looks up each address in the `votes` map:

```move
inline fun num_approvals_and_rejections_internal(owners: &vector<address>, transaction: &MultisigTransaction): (u64, u64) {
    ...
    owners.for_each_ref(|owner| {
        if (simple_map::contains_key(votes, owner)) {
            if (*simple_map::borrow(votes, owner)) {
                num_approvals += 1;
            } else {
                num_rejections += 1;
            };
        }
    });
    (num_approvals, num_rejections)
}
``` [1](#0-0) 

When an owner is removed, `update_owner_schema` only splices the address out of the `owners` vector. It never touches any pending transaction's `votes` map:

```move
owners_to_remove.for_each_ref(|owner_to_remove_ref| {
    let (found, index) =
        vector::index_of(owners_ref_mut, owner_to_remove_ref);
    if (found) {
        vector::push_back(
            &mut owners_removed,
            vector::swap_remove(owners_ref_mut, index)
        );
    }
});
``` [2](#0-1) 

Similarly, when an owner is re-added, `update_owner_schema` only appends to `owners` — no stale vote cleanup:

```move
if (new_owners.length() > 0) {
    multisig_account_ref_mut.owners.append(new_owners);
    ...
}
``` [3](#0-2) 

The consequence: once the removed owner's address re-enters the `owners` vector, every pending transaction that already contains that address in its `votes` map will immediately count the old vote again — without the owner having to call `approve_transaction` or `vote_transaction` again.

The codebase itself acknowledges the "removed owner vote invalidation" invariant in the test `test_validate_transaction_should_not_consider_removed_owners`:

```move
remove_owners(multisig_signer, vector[owner_1_addr]);
// Now that owner 1 is removed, their approval should be invalidated...
assert!(!can_be_executed(multisig_account, 1), 1);
``` [4](#0-3) 

But there is no corresponding test or guard for the re-addition case, and no code in `update_owner_schema` that clears stale votes when an owner is re-added.

---

### Impact Explanation

Multisig accounts are used to hold and transfer APT, fungible assets, and other on-chain resources. A pending transaction that was previously blocked (because the approving owner was removed, dropping the approval count below threshold) can become immediately executable the moment that owner is re-added — without the re-added owner casting a new vote. This constitutes unauthorized execution of a multisig transaction controlling user assets.

The `validate_multisig_transaction` function (called by the VM during prologue) enforces the approval threshold using `num_approvals_and_rejections`, which will count the stale vote:

```move
let (num_approvals, _) = num_approvals_and_rejections(multisig_account, sequence_number);
...
assert!(num_approvals >= num_signatures_required(multisig_account), ...);
``` [5](#0-4) 

---

### Likelihood Explanation

Exploitation requires the removed owner to be re-added, which itself requires k-of-n multisig approval. This limits the attack surface compared to the external bug (where no permission was needed). However, the scenario is realistic:

1. A 2-of-3 multisig (owners A, B, C). Owner A creates and auto-approves transaction T1. Owner B also approves — T1 now has 2/3 approvals and is executable.
2. Before T1 executes, C discovers T1 is malicious. C proposes removing A; B and C approve the removal. A is removed. T1 now has only 1 valid approval (B) — below the 2-of-2 threshold.
3. Later, A is re-added (e.g., after a dispute resolution, or because the owners who vote to re-add A are unaware of T1's pending state). The re-addition requires only B and C to approve.
4. The moment A is re-added, T1 has 2 approvals again (A's stale vote + B's vote) and is immediately executable — without A having to re-approve.

The owners who voted to re-add A may not have realized this would silently re-activate A's old approval on T1.

---

### Recommendation

In `update_owner_schema`, when adding a new owner (including re-adding a previously removed one), iterate over all pending transactions and remove any existing vote entry for that owner's address from each transaction's `votes` map:

```move
// When adding owners, clear any stale votes they may have from a prior tenure.
if (new_owners.length() > 0) {
    multisig_account_ref_mut.owners.append(new_owners);
    validate_owners(&multisig_account_ref_mut.owners, multisig_address);
    // Clear stale votes for newly added owners across all pending transactions.
    let seq = multisig_account_ref_mut.last_executed_sequence_number + 1;
    let next_seq = multisig_account_ref_mut.next_sequence_number;
    while (seq < next_seq) {
        let tx = multisig_account_ref_mut.transactions.borrow_mut(seq);
        new_owners.for_each_ref(|owner| {
            if (tx.votes.contains_key(owner)) {
                tx.votes.remove(owner);
            }
        });
        seq += 1;
    };
    emit(AddOwners { multisig_account: multisig_address, owners_added: new_owners });
};
```

Alternatively, clear stale votes for removed owners at removal time (so they cannot be reused if the owner is re-added).

### Proof of Concept

```move
#[test(owner_1 = @0x123, owner_2 = @0x124, owner_3 = @0x125)]
fun test_stale_vote_reactivated_on_readd(
    owner_1: &signer, owner_2: &signer, owner_3: &signer) {
    setup();
    let owner_1_addr = address_of(owner_1);
    let owner_2_addr = address_of(owner_2);
    let owner_3_addr = address_of(owner_3);
    create_account(owner_1_addr);
    let multisig_account = get_next_multisig_account_address(owner_1_addr);
    // 2-of-3 multisig
    create_with_owners(owner_1, vector[owner_2_addr, owner_3_addr], 2, vector[], vector[]);

    // Owner 1 creates and auto-approves T1. Owner 2 also approves.
    create_transaction(owner_1, multisig_account, PAYLOAD);
    approve_transaction(owner_2, multisig_account, 1);
    assert!(can_be_executed(multisig_account, 1), 0); // 2/3 approvals

    // Owner 1 is removed. T1 now has only 1 valid approval (owner 2). Not executable.
    let multisig_signer = &create_signer(multisig_account);
    remove_owners(multisig_signer, vector[owner_1_addr]);
    assert!(!can_be_executed(multisig_account, 1), 1); // 1/2 approvals

    // Owner 1 is re-added. Their stale vote is immediately counted again.
    add_owners(multisig_signer, vector[owner_1_addr]);
    // BUG: T1 is now executable again without owner_1 re-approving.
    assert!(can_be_executed(multisig_account, 1), 2); // stale vote reactivated
}
```

The `can_be_executed` call at step 2 passes because `num_approvals_and_rejections_internal` finds owner_1's address back in `owners` and reads their old `true` vote from the `votes` map — without owner_1 having called `approve_transaction` again. [6](#0-5) [7](#0-6)

    /// Add new owners, remove owners to remove, update signatures required.
    fun update_owner_schema(
        multisig_address: address,
        new_owners: vector<address>,
        owners_to_remove: vector<address>,
        optional_new_num_signatures_required: Option<u64>,
    ) {
        assert_multisig_account_exists(multisig_address);
        let multisig_account_ref_mut =
            borrow_global_mut<MultisigAccount>(multisig_address);
        // Verify no overlap between new owners and owners to remove.
        new_owners.for_each_ref(|new_owner_ref| {
            assert!(
                !vector::contains(&owners_to_remove, new_owner_ref),
                error::invalid_argument(EOWNERS_TO_REMOVE_NEW_OWNERS_OVERLAP)
            )
        });
        // If new owners provided, try to add them and emit an event.
        if (new_owners.length() > 0) {
            multisig_account_ref_mut.owners.append(new_owners);
            validate_owners(
                &multisig_account_ref_mut.owners,
                multisig_address
            );
            emit(AddOwners { multisig_account: multisig_address, owners_added: new_owners });
        };
        // If owners to remove provided, try to remove them.
        if (owners_to_remove.length() > 0) {
            let owners_ref_mut = &mut multisig_account_ref_mut.owners;
            let owners_removed = vector[];
            owners_to_remove.for_each_ref(|owner_to_remove_ref| {
                let (found, index) =
                    vector::index_of(owners_ref_mut, owner_to_remove_ref);
                if (found) {
                    vector::push_back(
                        &mut owners_removed,
                        vector::swap_remove(owners_ref_mut, index)
                    );
                }
            });
            // Only emit event if owner(s) actually removed.
            if (owners_removed.length() > 0) {
                emit(
                    RemoveOwners { multisig_account: multisig_address, owners_removed }
                );
            }
        };
