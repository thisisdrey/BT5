### Title
Unprivileged attacker can fill a victim's token list via dust `DepositToken` transfers, DoS-ing deposits, borrows, and collateral top-ups - (File: contracts/Pool.sol, contracts/DepositToken.sol)

### Summary
`Pool` enforces `MAX_TOKENS_PER_USER = 30` across `depositTokensOfAccount + debtTokensOfAccount` via the `onlyIfAdditionWillNotReachMaxTokens` modifier on `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` (Pool.sol:143-148, 204-220). Because `DepositToken._transfer` automatically registers the token on the *recipient's* list whenever their prior balance is zero (DepositToken.sol:517-520), any holder can force entries onto an arbitrary victim's list without consent. Once the combined count reaches 30, every code path that would add a new token type for the victim reverts with `UserReachedMaxTokens`.

### Finding Description
- `DepositToken.transfer`/`transferFrom` only check the *sender's* unlocked balance (`_revertIfLocked`, DepositToken.sol:348-376) and then call `_transfer`, which calls `pool.addToDepositTokensOfAccount(recipient_)` for first-time recipients.
- `Pool.addToDepositTokensOfAccount` (Pool.sol:216) validates only that the *caller* (`_msgSender()`) is a registered deposit token — the `account_` argument is fully attacker-chosen. There is no opt-in, no minimum amount, and no per-token dust threshold.
- The same cap applies to debt positions: `DebtToken` mints (issue/mint) register the debt token via `addToDebtTokensOfAccount`, which reverts at the cap.
- Attack steps (all unprivileged, directly or via `Operator.execute`):
  1. For each registered deposit token i: `depositToken_i.deposit(dustAmount, attacker)` (or buy dust on a market) to obtain `msdTOKEN_i`.
  2. `msdTOKEN_i.transfer(victim, 1)` — victim's `depositTokensOfAccount` grows by one each call.
  3. Repeat until `debtTokensOfAccount.length(victim) + depositTokensOfAccount.length(victim) == 30`.
- Afterwards, for the victim: `deposit(amount, victim)` reverts inside `_mint` → `addToDepositTokensOfAccount`; any new `DebtToken.issue` reverts in `addToDebtTokensOfAccount`; incoming `transfer`/`transferFrom`/`seize` of any not-yet-held msdToken reverts. Even third parties cannot top up collateral `onBehalfOf` the victim.

### Impact Explanation
Temporary freezing of funds / forced-liquidation griefing. A victim whose position drifts toward unhealthy cannot add a *new* collateral type to restore health, cannot open a new debt position, and cannot receive seized or transferred msdTokens of new types, until they manually transfer out one of the dusted tokens (which they may not notice, since the balance is 1 wei and no consent was required). An attacker can dust a victim while healthy and later liquidate them when the price moves — the top-up transaction reverts `UserReachedMaxTokens` while `Pool.liquidate` remains executable. Existing collateral remains withdrawable (burn paths remove list entries), so the freeze is temporary rather than permanent.

### Likelihood Explanation
Any EOA can execute this with only dust capital; no privileged role, oracle manipulation, or malicious bridge is needed. The limiting factor is the number of registered deposit tokens per pool: the attacker can only add as many entries as distinct deposit tokens exist, so the attack fully bricks the cap only in pools approaching 30 listed collaterals; in smaller pools it reduces the victim's remaining headroom proportionally. Reproducible on a Hardhat fork: deploy/attach to a live Pool, loop `deposit(1 wei…)` + `transfer(victim, 1)` over the registered `DepositToken`s, then show victim's `deposit`/`issue` of a new token type reverts while `liquidate` still succeeds.

### Recommendation
Track registrations by consent rather than by balance: e.g., only register a deposit token on `deposit()`/`seize()`-to-self flows and not on arbitrary `transfer` receipts, or add a minimum amount, or let the cap check apply to the *sender* initiating the registration. Alternatively, allow recipients to sweep unwanted dust (a `removeFromDepositTokensOfAccount` self-call when balance is below a threshold), or raise the cap / count only tokens above a meaningful USD value in `debtPositionOf`.

    function _transfer(
        address sender_,
        address recipient_,
        uint256 amount_
    ) private updateRewardsBeforeTransfer(sender_, recipient_) {
        if (sender_ == address(0)) revert TransferFromTheZeroAddress();
        if (recipient_ == address(0)) revert TransferToTheZeroAddress();

        uint256 _senderBalanceBefore = balanceOf[sender_];
        if (_senderBalanceBefore < amount_) revert TransferAmountExceedsBalance();
        uint256 _recipientBalanceBefore = balanceOf[recipient_];

        unchecked {
            balanceOf[sender_] = _senderBalanceBefore - amount_;
            balanceOf[recipient_] += amount_;
        }

        emit Transfer(sender_, recipient_, amount_);

        // Add this token to the deposit tokens list if the recipient is receiving it for the 1st time
        if (_recipientBalanceBefore == 0 && amount_ > 0) {
            pool.addToDepositTokensOfAccount(recipient_);
        }

        // Remove this token from the deposit tokens list if the sender's balance goes to zero
        if (amount_ > 0 && balanceOf[sender_] == 0) {
            pool.removeFromDepositTokensOfAccount(sender_);
        }
    }
