### Title
Missing/insufficient bounds validation when parsing reftable block data leads to out-of-bounds slice panic (DoS) - ([File: internal/git/reftable/reftable.go])

### Summary
The custom Go reftable binary parser in `internal/git/reftable/reftable.go` mirrors the reported bug class ("boundary check performed with the wrong comparison operator, so a value equal to the length/end is treated as in-bounds and the code proceeds to read one element past the valid region"). Several functions compute offsets from untrusted length/count fields read directly out of file bytes and then index into the raw byte slice without verifying those offsets stay within the slice, or within the intended sub-region (block/table boundary), before dereferencing them.

### Finding Description
`Table.getVarInt` reads `src[start]` without first checking that `start` is within `len(src)` (or even within `blockEnd`) before the initial dereference, and its loop-exit check uses `start > blockEnd` [1](#0-0) , which — exactly like the reported `txCalldataLen < offset` bug — allows `start == blockEnd` to be treated as in-bounds and still dereferences `src[start]` on that boundary value before the check can reject it, one iteration later.

`Table.extractBlockLen` slices `src[blockStart+1 : blockStart+4]` with no verification that `blockStart+4` is within `len(src)` [2](#0-1) .

`Table.parseRefBlock` computes `currentBS` (block length) directly from attacker-influenced file bytes via `extractBlockLen`, then does unsigned arithmetic `src[blockStart+currentBS-2:]` and `b.RestartStart = blockStart + currentBS - 2 - 3*uint(b.RestartCount)` [3](#0-2) . Because these are unsigned (`uint`) computations, a `currentBS` value smaller than 2, or a `RestartCount` large enough, causes integer underflow/wraparound to a huge value rather than a bounds error. The subsequent loop in `getRefsFromBlock` (`for idx < b.RestartStart`) [4](#0-3)  and every `src[idx:idx+n]` slice inside it then run with an unchecked, attacker-influenced index, ultimately causing a Go slice-bounds-out-of-range panic (rather than a silent memory overread, since Go bounds-checks slices, but the effect is an unrecovered crash of the goroutine/handler unless recovered upstream).

This is the same root-cause pattern as the CALLDATALOAD/CALLDATACOPY finding: a boundary comparison is off, or missing entirely, so a length/offset value at (or beyond) the true bound of the buffer is used to index into it before the "past-the-end" condition is properly rejected.

### Impact Explanation
Where this parser is invoked (`internal/gitaly/storage/storagemgr/partition/reftable.go`'s `stageTables`, via `reftable.ParseTable`) it operates on the `.ref` table files inside a repository's `reftable/` directory during write-transaction resequencing [5](#0-4) . If a repository's `reftable` directory can be populated with a corrupted/crafted table file — for example by transplanting/importing/replicating a repository's on-disk state that includes a hand-crafted `.ref` file — subsequent write-transaction handling that resequences tables will call into this vulnerable parsing path and can panic, denying service for that partition/repository's transaction manager.

### Likelihood Explanation
This requires a repository using the reftable reference backend, and requires that the on-disk `reftable/*.ref` file content not be produced solely by Git's own reftable writer (whose output would not exercise this malformed path). I was not able to fully verify, within the available tool budget, the exact production RPC (e.g. repository import/replication/snapshot restore) through which an ordinary user could plant a byte-for-byte crafted `.ref` file into a target repository's `reftable/` directory rather than one always freshly generated by the trusted `git` binary. This is a materially uncertain link in the exploit chain and should be validated with a full checkout (e.g., via a Devin session) before treating this as confirmed remotely triggerable.

### Recommendation
Add explicit bounds checks before every slice/indexing operation in `internal/git/reftable/reftable.go` derived from file-controlled lengths (`extractBlockLen`, `getVarInt`, `parseRefBlock`, `getRefsFromBlock`), performing them with the same `offset < length` (strict "less-than", not allowing equality to be treated as in-bounds) semantics recommended in the original report, and guard all subtractions (`currentBS-2`, `blockStart+currentBS-2-3*RestartCount`) against unsigned underflow before use.

### Proof of Concept
Not independently constructed/verified in this session (no execution environment available). Conceptually: craft a `reftable`-format `.ref` file whose ref-block header encodes a `block_len` (`currentBS`) of 0 or 1, forcing `blockStart+currentBS-2` to underflow to a very large `uint`, then have that file placed in a repository's `reftable/` directory and trigger a write transaction so that `stageTables` → `reftable.ParseTable`/`parseRefBlock` parses it, producing a slice-bounds-out-of-range panic. Confirming the exact attacker-reachable path to plant such a file requires further investigation of the repository import/replication code paths, which was not completed here.

```go
func (t *Table) getVarInt(src []byte, start uint, blockEnd uint) (uint, uint, error) {
	var val uint

	val = uint(src[start]) & 0x7f

	for (uint(src[start]) & 0x80) > 0 {
		start++
		if start > blockEnd {
			return 0, 0, fmt.Errorf("exceeded block length")
		}

		val = ((val + 1) << 7) | (uint(src[start]) & 0x7f)
	}

	return start + 1, val, nil
```

```go
func (t *Table) parseRefBlock(src []byte, headerOffset, blockStart, blockEnd uint) ([]git.Reference, error) {
	currentBS := t.extractBlockLen(src, blockStart+headerOffset)

	fullBlockSize := t.blockSize
	if fullBlockSize == 0 {
		fullBlockSize = currentBS
	} else if currentBS < fullBlockSize && currentBS < (blockEnd-blockStart) && src[blockStart+currentBS] != 0 {
		fullBlockSize = currentBS
	}

	b := &block{
		BlockStart:    blockStart + headerOffset,
		FullBlockSize: fullBlockSize,
	}

	if err := binary.Read(bytes.NewBuffer(src[blockStart+currentBS-2:]), binary.BigEndian, &b.RestartCount); err != nil {
		return nil, fmt.Errorf("reading restart count: %w", err)
	}

	b.RestartStart = blockStart + currentBS - 2 - 3*uint(b.RestartCount)

	return t.getRefsFromBlock(src, b)
```
