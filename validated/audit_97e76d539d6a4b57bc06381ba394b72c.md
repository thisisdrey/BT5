### Title
Non-constant-time auth token comparison enables timing side-channel recovery of `connection_options.auth_token` - (File: `stackslib/src/net/api/postblock_proposal.rs`, `stackslib/src/net/api/postblock_v3.rs`, `stackslib/src/net/api/blockreplay.rs`, `stackslib/src/net/api/blocksimulate.rs`, `stackslib/src/net/api/txsimulate.rs`, `stackslib/src/net/api/fastcallreadonly.rs`)

### Summary
Several privileged RPC endpoints authenticate the caller by comparing the client-supplied `authorization` header against the node's configured `auth_token` using Rust's default `!=`/`==` string comparison, which short-circuits on the first differing byte. This is a classic non-constant-time secret comparison (CWE-208/CWE-522 credential-protection weakness class, analogous to the external report's concern about weakly-protected API keys) that lets a remote, unauthenticated attacker recover the secret token byte-by-byte via repeated timing measurements, and then use it to forge authorization for state-changing endpoints such as `/v3/block_proposal` and `/v2/blocks?broadcast=1`.

### Finding Description
`RPCBlockProposalRequestHandler::try_parse_request` reads the configured secret and compares it directly to the client-supplied header value: [1](#0-0) 

The same pattern (`auth_header != password`) is repeated in `postblock_v3.rs` for the `/v2/blocks?broadcast=1` write-broadcast gate: [2](#0-1) 

and in the block-replay, block-simulate, and transaction-simulate read-endpoint handlers: [3](#0-2) [4](#0-3) 

`auth_token`/`auth_password` is documented as the shared secret that gates the node's `/v3/block_proposal` endpoint (used by `stacks-signer`) and authenticated `/v2/blocks?broadcast=1` requests: [5](#0-4) 

Because Rust's `&str`/`String` `PartialEq` implementation performs a length check followed by a byte-wise comparison that returns as soon as a mismatch is found, the wall-clock time of the comparison leaks information about how many leading bytes of the guess match the real secret. An attacker with network access to the RPC endpoint (no prior credentials needed) can exploit this by submitting many candidate `authorization` header values and using statistical timing analysis to incrementally recover the token character-by-character — a well-established technique against non-constant-time secret comparisons.

### Impact Explanation
Recovering `auth_token` breaks the "authenticated vs. stored" equality the token is meant to enforce and grants the attacker the same privileges as a legitimate `stacks-signer`/authenticated client:
- Forge accepted requests to `/v3/block_proposal`, the endpoint the miner/signer subsystem uses to validate block proposals.
- Authenticate `/v2/blocks?broadcast=1` to force this node to broadcast attacker-supplied block data as if from an authenticated source, per `postblock_v3.rs`'s broadcast gate: `if broadcast && !authenticated { return Err(...401...) }`, which the attacker can bypass with the recovered token.
This constitutes an authentication bypass on remote, unauthenticated write/control-plane endpoints, which the rules classify as Critical impact.

### Likelihood Explanation
Exploitation requires only network reachability to the RPC port (default configuration ships `auth_token` unset/disabled but any deployment that enables the signer flow, e.g. `mainnet-signer.toml`, sets a token and exposes these endpoints). No credentials, node secret key, or privileged role are needed — only repeated HTTP requests and timing measurement, which is intrinsic to the vulnerable comparison itself rather than to raw traffic volume. Practical timing side-channel attacks over local/low-latency networks against short secret tokens are well documented, making this a realistic (if statistically noisy) recovery path.

### Recommendation
Replace all direct `==`/`!=` comparisons of `auth_header` against the configured secret with a constant-time comparison (e.g., `subtle::ConstantTimeEq`) in every handler that gates on `self.auth`: `postblock_proposal.rs`, `postblock_v3.rs`, `blockreplay.rs`, `blocksimulate.rs`, `txsimulate.rs`, and `fastcallreadonly.rs`. Additionally consider hashing/comparing a fixed-length MAC of the token rather than the raw string to avoid length-based timing leakage as well.

### Proof of Concept
1. Configure a node with `[connection_options] auth_token = "<secret>"` and enable `/v3/block_proposal` (as in `sample/conf/mainnet-signer.toml`).
2. Send repeated POST requests to `/v3/block_proposal` with an `authorization` header guessing the token one byte-prefix at a time (e.g. `"a", "aa", "ab", ...`), measuring response latency for the point where `auth_header != password` fails.
3. Because the comparison exits at the first mismatching byte, correct prefixes take measurably longer than incorrect ones under many timing trials; statistically aggregate to recover the token.
4. Once recovered, submit an authenticated `/v3/block_proposal` or `/v2/blocks?broadcast=1` request bypassing the intended authentication gate shown at [6](#0-5) .
