### Title
Unguarded subtraction in `RepositoryImpl.addTotalNetWeight`/`addTotalEnergyWeight`/`addTotalTronPowerWeight` can drive total resource weight negative when triggered from the TVM freeze/unfreeze precompiles - ([File: actuator/src/main/java/org/tron/core/vm/repository/RepositoryImpl.java])

### Summary
The external report flags `protocolFeeOwed -= msg.value` in `YoloV2.sol` as unsafe because the subtraction is never checked against the current balance before being applied. The same "wrong subtraction" class exists in java-tron's `RepositoryImpl`, which backs the TVM native contracts (`freezeBalanceV2`, `unfreezeBalanceV2`, `delegateResource`, `unDelegateResource`) reachable from any smart-contract call. Unlike the "normal transaction" path that goes through `DynamicPropertiesStore`, the TVM path performs the add/subtract without any floor check.

### Finding Description
`RepositoryImpl.addTotalNetWeight`, `addTotalEnergyWeight`, and `addTotalTronPowerWeight` blindly add the signed `amount` (which is negative when unfreezing/undelegating resources) to the stored total weight and persist the result, with no lower bound check: [1](#0-0) 

Compare this to the equivalent method used by the "classic" (non-TVM) actuator path in `DynamicPropertiesStore`, which explicitly clamps the result to a minimum of `0` when `allowNewReward()` is enabled: [2](#0-1) 

The `RepositoryImpl` variants are called from the native-contract processors invoked by TVM opcodes (e.g. `UnfreezeBalanceV2Processor.updateTotalResourceWeight`, `UnDelegateResourceProcessor`, `FreezeBalanceV2Processor.execute`), meaning a smart contract can trigger `freezeBalanceV2`/`unfreezeBalanceV2`/`delegateResource`/`unDelegateResource` opcodes and reach this unguarded subtraction: [3](#0-2) [4](#0-3) 

Because the total weight is a shared, chain-wide dynamic property that is later used to compute every account's share of global bandwidth/energy limits (`calculateGlobalLimitV1`, which divides `totalLimit` by `totalWeight`), driving it negative or into an inconsistent state corrupts bandwidth/energy accounting for the entire network, not just the caller: [5](#0-4) 

### Impact Explanation
I was not able to fully prove a concrete desynchronization scenario (e.g., an account being able to unfreeze/undelegate more than it froze via the TVM path) within the available tool budget — the individual `FreezeBalanceV2Processor`/`UnfreezeBalanceV2Processor`/`DelegateResourceProcessor` validate methods appeared to check `frozenBalance <= ownerCapsule.getBalance()` and similar per-account invariants before execution, which would normally prevent an individual call from desynchronizing the aggregate weight by more than what was legitimately frozen by that account. However, the structural gap remains: the `RepositoryImpl` copy of `addTotalNetWeight`/`addTotalEnergyWeight`/`addTotalTronPowerWeight` lacks the `max(0, ...)` floor safeguard that the "classic" `DynamicPropertiesStore` copy has, which is a real inconsistency between the two code paths that maintain the same on-chain dynamic property. If any edge case (e.g. self-destruct combined with delegated resources, or a sequence of freeze/unfreeze/delegate operations invoked purely through TVM opcodes without ever going through the classic actuators) causes the aggregate to be decremented more than it was incremented on this path, the resulting negative `TOTAL_NET_WEIGHT`/`TOTAL_ENERGY_WEIGHT` would corrupt global bandwidth/energy limit calculations for all accounts network-wide (a state corruption affecting the entire node, not just the caller).

### Likelihood Explanation
Medium-to-low: reaching this code requires deploying a contract that invokes the `freezeBalanceV2`/`unfreezeBalanceV2`/`delegateResource`/`unDelegateResource` TVM opcodes, which is available to any unprivileged contract deployer. The specific structural gap (missing floor clamp compared to the non-TVM path) is confirmed by direct code comparison, but I could not fully verify within the time available whether any of the calling processors' `validate()` methods allow a sequence of calls that would actually push the aggregate below zero, so the concrete exploit path is not fully proven.

### Recommendation
Add the same lower-bound safeguard (`max(0, totalWeight, ...)`) to `RepositoryImpl.addTotalNetWeight`, `addTotalEnergyWeight`, and `addTotalTronPowerWeight` that already exists in `DynamicPropertiesStore`, so the TVM-triggered path cannot diverge from the classic actuator path's invariant. Additionally, audit all callers of these `RepositoryImpl` methods (`FreezeBalanceV2Processor`, `UnfreezeBalanceV2Processor`, `DelegateResourceProcessor`, `UnDelegateResourceProcessor`, `CancelAllUnfreezeV2Actuator`) to confirm that per-account validation is always sufficient to prevent the aggregate from underflowing, and add an explicit assertion/guard at the point of persistence as defense-in-depth.

### Proof of Concept
Not fully constructed — verifying a concrete underflow sequence would require tracing every caller of `repo.addTotalNetWeight`/`addTotalEnergyWeight`/`addTotalTronPowerWeight` under `actuator/src/main/java/org/tron/core/vm/nativecontract/` and `UnDelegateResourceProcessor`/`CancelAllUnfreezeV2Actuator` in more depth than the available tool budget allowed, to determine whether any legitimate sequence of TVM freeze/unfreeze/delegate/undelegate calls can decrement the aggregate more than it was previously incremented on this specific (`RepositoryImpl`) path.

  public void updateTotalResourceWeight(AccountCapsule accountCapsule,
                                        Common.ResourceCode freezeType,
                                        long unfreezeBalance,
                                        Repository repo) {
    switch (freezeType) {
      case BANDWIDTH:
        long oldNetWeight = accountCapsule.getFrozenV2BalanceWithDelegated(BANDWIDTH) / TRX_PRECISION;
        accountCapsule.addFrozenBalanceForBandwidthV2(-unfreezeBalance);
        long newNetWeight = accountCapsule.getFrozenV2BalanceWithDelegated(BANDWIDTH) / TRX_PRECISION;
        repo.addTotalNetWeight(newNetWeight - oldNetWeight);
        break;
      case ENERGY:
        long oldEnergyWeight = accountCapsule.getFrozenV2BalanceWithDelegated(ENERGY) / TRX_PRECISION;
        accountCapsule.addFrozenBalanceForEnergyV2(-unfreezeBalance);
        long newEnergyWeight = accountCapsule.getFrozenV2BalanceWithDelegated(ENERGY) / TRX_PRECISION;
        repo.addTotalEnergyWeight(newEnergyWeight - oldEnergyWeight);
        break;
      case TRON_POWER:
        long oldTPWeight = accountCapsule.getTronPowerFrozenV2Balance() / TRX_PRECISION;
        accountCapsule.addFrozenForTronPowerV2(-unfreezeBalance);
        long newTPWeight = accountCapsule.getTronPowerFrozenV2Balance() / TRX_PRECISION;
        repo.addTotalTronPowerWeight(newTPWeight - oldTPWeight);
        break;
      default:
        //this should never happen
        break;
    }
  }
