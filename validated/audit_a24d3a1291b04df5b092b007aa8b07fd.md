### Title
Unbounded in-memory buffering of pre-receive stdin via `io.ReadAll` allows memory-exhaustion DoS - (File: internal/gitaly/hook/prereceive.go)

### Summary
`PreReceiveHook` reads the entire `git-receive-pack` "changes" stream (one line per ref update) into memory with `io.ReadAll(stdin)` before any size validation, and the underlying gRPC stream reader (`streamio.NewReader`) imposes no cap on the number of chunks or total accumulated bytes. An unprivileged user who can push to a repository controls the number of ref updates in a single push and can therefore force Gitaly to allocate memory proportional to that count with no upper bound enforced by Gitaly itself.

### Finding Description
`internal/gitaly/service/hook/pre_receive.go`'s `PreReceiveHook` gRPC handler wraps the client-streamed `PreReceiveHookRequest.Stdin` chunks in a `streamio.NewReader` and passes that reader into `GitLabHookManager.PreReceiveHook` [1](#0-0) . That function immediately calls `changes, err := io.ReadAll(stdin)`, which drains the reader to completion and buffers the full "changes" payload (one line per updated ref: `<old-sha> <new-sha> <ref>\n`) into a single `[]byte` before any length/line-count validation is performed [2](#0-1) . The only validation applied afterward is `len(changes) == 0`, which rejects empty input but does not cap size [3](#0-2) . The buffered `changes` is subsequently copied again into `gitlab.AllowedParams.Changes` as a string and sent to the Rails `Allowed` API call, and a further copy is passed to the custom hook executor via `bytes.NewReader(changes)` [4](#0-3) [5](#0-4) , multiplying the memory footprint of a single oversized push. A repository search of the codebase found no `grpc.MaxRecvMsgSize` server-side configuration, so gRPC's own per-message default limit (4 MiB) only bounds a single stream chunk, not the total accumulated length across the many chunks `git-receive-pack` sends for a push touching a very large number of refs.

### Impact Explanation
An attacker who can push to any repository they control (no special privileges required) can craft a single push updating an extremely large number of refs, causing Gitaly to allocate memory proportional to the number of ref-update lines with several redundant copies of that buffer in flight. This matches a scoped memory-exhaustion DoS of the RPC handler that can affect the whole Gitaly node (and thus other tenants sharing that node), which corresponds to a resource-exhaustion/DoS-class impact.

### Likelihood Explanation
The precondition is minimal: any GitLab user with push access to a repository they own can trigger this by issuing a single `git push` with a very large number of ref updates or a push with a large `--push-option` set forwarded as `pushOptions`. This is fully repeatable and requires no privileged role, secret, or non-default configuration — it is a direct, attacker-controlled input path into an unbounded `io.ReadAll`.

### Recommendation
Impose a hard cap on the total size of the pre-receive stdin/changes payload (and on the number of push options) before or during the streaming read — e.g., wrap `stdin` with `io.LimitReader` set to a sane maximum, and reject the push early via `structerr.NewInvalidArgument` when the limit is exceeded rather than buffering into memory first. Apply the same treatment to `PostReceiveHook`, `ReferenceTransactionHook`, and `ProcReceiveHook`, which follow the same pattern.
