### Title
Unbounded array allocation in TVM signature precompiles when the SelfdestructRestriction proposal is inactive - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
`ValidateMultiSign` and `BatchValidateSign`, TVM precompiled contracts reachable from any smart-contract `CALL`, derive an array length directly from attacker-controlled call data and pass it unchecked into `extractBytesArray`/`extractSigArray`, which allocate `new byte[len][]`. The upper-bound check on that length (`MAX_SIZE`) is only applied when `VMConfig.allowTvmSelfdestructRestriction()` returns true; when that hard-fork gate is not active, `len` is fully attacker-controlled up to `Integer.MAX_VALUE`, mirroring the CVE-2025-14876 pattern of a missing length limit leading to uncontrolled memory allocation.

### Finding Description
`ValidateMultiSign.execute` and `BatchValidateSign.doExecute` parse the call data into `DataWord[] words` and compute the signature-array size as `words[words[3].intValueSafe() / WORD_SIZE].intValueSafe()` (`ValidateMultiSign`) or `words[words[1].intValueSafe() / WORD_SIZE].intValueSafe()` / `words[words[2].intValueSafe() / WORD_SIZE].intValueSafe()` (`BatchValidateSign`). [1](#0-0) [2](#0-1) 

The `sigArraySize > MAX_SIZE` / `addrArraySize > MAX_SIZE` bound check that prevents an oversized allocation is guarded by `if (VMConfig.allowTvmSelfdestructRestriction())`. When that condition is false, execution falls straight through to `extractBytesArray`/`extractSigArray`, which do:
```
int len = words[offset].intValueSafe();
byte[][] bytesArray = new byte[len][];
``` [3](#0-2) 

`intValueSafe()` clamps the value to the `int` range but does not impose any small upper bound, so `len` can be driven arbitrarily close to `Integer.MAX_VALUE` by any caller who can invoke the precompiled contract address (both are standard, publicly callable precompile addresses in the TVM). This is architecturally identical to the QEMU virtio-crypto AKCIPHER flaw: a length field taken from untrusted input is used directly to size a large allocation with no independent bound check, so the allocation size is fully attacker-controlled.

### Impact Explanation
A crafted `CALL` into the `ValidateMultiSign` or `BatchValidateSign` precompile with a huge encoded array-length word forces the node to attempt an array allocation of up to ~2^31 elements (each a `byte[]` reference, and further nested arrays for `extractSigArray`). This can exhaust heap memory and trigger an `OutOfMemoryError`, crashing or hanging the java-tron node process that executes the transaction (all full nodes/validators that execute it), i.e. a denial-of-service against the block-producing/validating node — matching the "node crash" acceptance criterion.

### Likelihood Explanation
The precompiles are reachable by any transaction that triggers a smart contract issuing a `CALL`/`STATICCALL` to the precompile address with attacker-supplied ABI-encoded data — no special privilege is required, and the caller only pays for `getEnergyForData`, which is computed from `data.length`, not from the parsed array length, so the energy cost does not scale with the actual (unbounded) allocation attempted inside `execute`. The severity is entirely conditioned on `VMConfig.allowTvmSelfdestructRestriction()` being disabled; this is a network hard-fork gate (`TIP`-style proposal), so exploitability depends on whether that proposal has been activated on the target chain (mainnet, a private chain, or a non-upgraded fork). This is a caveat I could not fully verify within available tooling — I was not able to confirm the current activation status of `allowTvmSelfdestructRestriction()` on the live chain that this repository targets, so the practical likelihood should be validated against the target chain's committed proposal state before treating this as immediately exploitable.

### Recommendation
Move the `sigArraySize`/`addrArraySize` upper-bound checks (and equivalent checks in `extractBytes32Array`, which has no bound check at all) outside the `allowTvmSelfdestructRestriction()` gate so that the length is always validated against `MAX_SIZE` (or another small sane cap) before any array is allocated, regardless of hard-fork proposal state. Additionally, validate `len >= 0` and `len <= someHardCap` in `extractBytesArray`, `extractSigArray`, and `extractBytes32Array` themselves, defense-in-depth, rather than relying solely on caller-side checks.

### Proof of Concept
Deploy a contract that performs a raw `CALL` to the `ValidateMultiSign`/`BatchValidateSign` precompile address, with ABI-encoded call data where the word at the signature-array-length position is set to a very large value (e.g., `0x7FFFFFFF`). When `VMConfig.allowTvmSelfdestructRestriction()` is inactive, execution reaches:
```
int len = words[offset].intValueSafe();      // ~2^31-1
byte[][] bytesArray = new byte[len][];        // huge allocation attempt
``` [4](#0-3) 
causing an `OutOfMemoryError` / large-memory-spike inside the node executing the transaction.

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
