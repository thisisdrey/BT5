### Title
Division-before-multiplication precision loss in legacy vote-reward calculation causes fund miscalculation - (File: chainbase/src/main/java/org/tron/core/service/MortgageService.java)

### Summary
`MortgageService.computeReward(long cycle, List<Pair<byte[], Long>> votes)` (the legacy pre-new-reward-algorithm path) computes a voter's share of SR reward by first dividing `userVote` by `totalVote` into a `double`, then multiplying by `totalReward`, instead of multiplying first and dividing last. This mirrors the ABDKMath64x64 "multiplication on results of division" bug class, where premature division causes precision loss/truncation in downstream multiplication.

### Finding Description
In `computeReward`, the vote share ratio is computed as a `double` before being multiplied by the reward pool: [2](#0-1) 

Because `voteRate = (double) userVote / totalVote` is computed and rounded to floating point *before* multiplying by `totalReward`, the result diverges from the mathematically exact `userVote * totalReward / totalVote`. Unlike other reward/quantity calculations in this codebase (e.g. `MarketUtils.multiplyAndDivide` at [3](#0-2)  or `EnergyProcessor.scaleByRate` at [4](#0-3) , which correctly multiply first using `BigInteger`/exact-multiply before dividing), this legacy path retains the divide-then-multiply floating point pattern. The same anti-pattern also appears in `payReward`'s brokerage computation (`brokerageRate = (double) brokerage / 100; brokerageAmount = (long) (brokerageRate * value)`) at [5](#0-4) , `payStandbyWitness` at [6](#0-5) , and `IncentiveManager.reward` at [7](#0-6) .

This legacy `computeReward(cycle, votes)` path is directly reachable by any TRX holder who has voted for an SR before `newRewardAlgorithmEffectiveCycle`: broadcasting a `WithdrawBalanceContract` invokes `WithdrawBalanceActuator.execute()` → `mortgageService.withdrawReward()` → `computeReward(beginCycle, endCycle, accountCapsule)` → for cycles before the new-algorithm cutover, `getOldReward()` → `computeReward(cycle, votes)`: [1](#0-0) [8](#0-7) 

### Impact Explanation
Unlike the newer VI-based algorithm (which correctly uses `BigInteger` multiply-then-divide, see `MortgageService.computeReward(beginCycle, endCycle, ...)` lines 215-227), the legacy per-cycle `double`-based path can systematically under- or over-pay reward allowance due to floating point truncation happening before scaling. This causes incorrect allowance credited to accounts — a form of fund miscalculation (either permanent loss for the voter or an inflated/unbacked allowance credited from the shared reward pool, at the expense of other voters or the protocol's reward accounting).

### Likelihood Explanation
This code path only executes for reward cycles predating `newRewardAlgorithmEffectiveCycle`, which the network has presumably already passed. Given the note in the codebase that this project already went through a hardening effort (`RepositoryImplHardenTest`, `allowHardenResourceCalculation`, `SafeExchangeProcessor`, `MarketUtils.multiplyAndDivide`) to replace exactly this double-arithmetic divide-then-multiply pattern elsewhere, the residual occurrence in `MortgageService.computeReward(cycle, votes)`, `payReward`, `payStandbyWitness`, and `IncentiveManager.reward` indicates these were not covered by that hardening pass, but their real-world exploitability is now bounded because they only apply to historical/legacy cycles or standby-witness/brokerage payouts rather than fresh, attacker-controlled, high-value paths.

### Recommendation
Apply the same hardening pattern already used elsewhere in the codebase (`BigInteger` multiply-then-divide, as in `MortgageService`'s new VI-reward computation, `MarketUtils.multiplyAndDivide`, and `EnergyProcessor.scaleByRate`) to `computeReward(cycle, votes)`, `payReward`'s brokerage calculation, `payStandbyWitness`, and `IncentiveManager.reward`, replacing `double`-based divide-before-multiply arithmetic with exact integer multiply-first-then-divide logic.

### Proof of Concept
Given `userVote = 1`, `totalVote = 3`, `totalReward = 10`:
- Correct (multiply-first): `1 * 10 / 3 = 3` (integer floor division of exact value `10/3`).
- Current (divide-first, `double`): `voteRate = (double) 1 / 3 = 0.3333333333333333`; `reward = (long) (0.3333333333333333 * 10) = 3` — in this trivial case results match, but for larger `totalReward`/`userVote`/`totalVote` combinations near `2^53` or with values chosen to maximize floating point rounding error, the double-precision intermediate `voteRate` loses bits that the final multiplication cannot recover, producing an off-by-one-or-more `long` result compared to the exact `BigInteger` computation — reachable by any address that voted for an SR and calls `WithdrawBalanceActuator` (`WithdrawBalanceContract`) for a reward cycle predating the new reward algorithm cutover.

  private long computeReward(long cycle, List<Pair<byte[], Long>> votes) {
    long reward = 0;
    for (Pair<byte[], Long> vote : votes) {
      byte[] srAddress = vote.getKey();
      long totalReward = delegationStore.getReward(cycle, srAddress);
      if (totalReward <= 0) {
        continue;
      }
      long totalVote = delegationStore.getWitnessVote(cycle, srAddress);
      if (totalVote == DelegationStore.REMARK || totalVote == 0) {
        continue;
      }
      long userVote = vote.getValue();
      double voteRate = (double) userVote / totalVote;
      reward += voteRate * totalReward;
    }
    return reward;
  }

  public static long multiplyAndDivide(long a, long b, long c, boolean disableMath) {
    try {
      long tmp = multiplyExact(a, b, disableMath);
      return floorDiv(tmp, c, disableMath);

    }

    BigInteger aBig = BigInteger.valueOf(a);
    BigInteger bBig = BigInteger.valueOf(b);
