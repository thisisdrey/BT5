### Title
Unauthenticated `POST /new_burn_block` on the signer's event receiver allows forged `SignerEvent::NewBurnBlock` injection into local signer state - (File: libsigner/src/events.rs)

### Summary
`SignerEventReceiver::next_event` dispatches `/new_burn_block` POSTs straight to `process_event::<T, BurnBlockEvent>` with no check of any secret, signature, or origin, unlike the node's RPC/block-proposal path which requires `auth_token`/`auth_password` to match. Any request body that deserializes as `BurnBlockEvent` is converted 1:1 via `TryFrom<BurnBlockEvent>` into `SignerEvent::NewBurnBlock{burn_height, burn_header_hash, consensus_hash, parent_burn_block_hash, ..}` and forwarded to the signer runloop, which unconditionally persists it via `insert_burn_block` in `signerdb`.

### Finding Description
`next_event` (`libsigner/src/events.rs:413-459`) reads an HTTP request from the bound listener and matches purely on URL path and method: [1](#0-0) 
There is no verification of any header, token, HMAC, or TLS client identity anywhere in this function or in `process_event` (`libsigner/src/events.rs:519-542`), which only reads the body, JSON-decodes it into `BurnBlockEvent`, and calls `TryInto<SignerEvent<T>>`: [2](#0-1) 
The `TryFrom<BurnBlockEvent>` impl copies every attacker-controlled field verbatim, including `parent_burn_block_hash` and `consensus_hash`, with zero cross-check against any burnchain view: [3](#0-2) 

This is architecturally different from the node's RPC surface, which does gate sensitive writes (e.g. block proposal validation) behind `auth_token`/`auth_password` matching, as documented in `docs/signing.md` and the sample configs: [4](#0-3) 
No equivalent secret exists for the event-receiver's HTTP endpoints in `libsigner/src/events.rs`. The reference signer config binds this listener on `0.0.0.0:30000` (all interfaces), not loopback-only: [5](#0-4) 

Once forwarded, the runloop dispatches the event to `v0::signer::handle_event_match`, which unconditionally writes the forged fields to persistent signer state via `insert_burn_block`, prunes superseded tenures, and feeds the bitcoin-block arrival state machine: [6](#0-5) 
None of this path re-derives or checks `parent_burn_block_hash`/`consensus_hash` against a locally-verified burnchain source before the write occurs — the write is unconditional at the signerdb layer, and any downstream consensus-safety logic (`bitcoin_block_arrival`, `check_parent_tenure_choice`, etc.) is explicitly out of scope per the question, but the fact remains: attacker-forged data is durably stored in signer state via `insert_burn_block` before any of that logic runs.

### Impact Explanation
An attacker who can reach the signer's bound event-receiver port (which, per the shipped reference configuration, listens on `0.0.0.0`) can POST an arbitrary, self-inconsistent `BurnBlockEvent` JSON body and have it accepted and durably written to the signer's local SQLite state (`signerdb`) as though it were an authentic node-observed burn block, with no signature, MAC, or shared-secret check at the transport layer. This is a repeatable, single-message, unauthenticated write to persistent signer state, matching the Critical category ("unauthenticated/unauthorized write to state"). Downstream effects on the signer's local state machine (tenure tracking, pruning, sortition view) are consensus-adjacent and explicitly out of scope for this finding, but the write itself is in scope and unauthenticated.

### Likelihood Explanation
- Attacker needs only TCP reachability to the signer's event-receiver port; per the reference/sample configs the port is bound to `0.0.0.0`, so it is remotely reachable unless separately firewalled — no special credential, secret, or role is required to reach or exploit the endpoint itself.
- The attack requires zero prior state: a single crafted HTTP POST to `/new_burn_block` with a valid JSON body is sufficient, and it is repeatable at will.
- No auth token, signature, or peer identity check exists on this specific HTTP surface (contrast with the node's RPC `auth_token` gate), so cost to the attacker is minimal.

### Recommendation
Add an authentication mechanism to the signer's event-receiver HTTP server analogous to the node's `auth_token`/`auth_password` scheme — e.g., require a shared secret (as a header or bearer token) configured on both the node's `events_observer` and the signer's `endpoint`, and reject requests in `next_event`/`process_event` that fail to present it. Additionally, document/enforce binding the event-receiver to loopback-only by default, and treat it as a private trust boundary (e.g., via mutual TLS or a local Unix socket) rather than a general network listener.
