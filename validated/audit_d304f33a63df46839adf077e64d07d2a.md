### Title
Non-constant-time comparison of the HTTP `authorization` header enables a remote timing side-channel to recover `auth_token` and bypass auth-gated RPC endpoints - (File: stackslib/src/net/api/postblock_v3.rs, postblock_proposal.rs, blockreplay.rs, blocksimulate.rs, txsimulate.rs, fastcallreadonly.rs)

### Summary
Multiple sensitive RPC handlers gate access by comparing the client-supplied `authorization` header against `connection_options.auth_token` using Rust's built-in `!=` operator on `&str`/`String`. This comparison is not constant-time: it returns as soon as a length mismatch or the first differing byte is found. A remote, unauthenticated attacker can exploit the resulting timing differential to recover the secret token byte-by-byte, then use it to pass the auth gate on endpoints that authorize writes (e.g. `/v3/block_proposal`, `/v3/blocks?broadcast=1`) or privileged reads (e.g. `/v3/blocks/replay/...`, `/v3/transactions/simulate`, fast-call-readonly).

The password is a plain `String` (`connection_options.auth_token`), configured and passed into each handler's constructor: [5](#0-4) [6](#0-5) 

`auth_header != password` uses Rust's default `str`/`String` equality, which is a byte-wise comparison that short-circuits on the first differing byte (or on differing length). This creates an observable timing difference proportional to the length of the correct token prefix supplied by an attacker: guesses that match more leading bytes take measurably longer to reject than guesses that mismatch early. This is the classic CWE-208 timing side-channel that breaks the intended equality check "supplied credential == stored secret," letting the attacker incrementally reconstruct the secret without ever possessing it, in violation of the rule constraint that the analog must not "require the node secret" — here the attack is the *mechanism to obtain* the secret remotely.

### Impact Explanation
Once an attacker recovers `auth_token` via timing, they gain the ability to:
- POST forged/malicious `NakamotoBlockProposal` payloads to `/v3/block_proposal` (`postblock_proposal.rs`), impersonating the coordinating signer.
- Force `/v2/blocks?broadcast=1` broadcast of an attacker-supplied Stacks block via `postblock_v3.rs`, an authenticated-only capability.
- Access authenticated debug/utility endpoints (`blockreplay.rs`, `blocksimulate.rs`, `txsimulate.rs`, `fastcallreadonly.rs`) that are otherwise gated specifically because they expose extra computation/state access.

This matches the "Critical — unauthenticated/unauthorized write to state... auth bypass" bucket, since the timing side channel is the practical route to defeating an auth gate meant to be closed to arbitrary remote clients.

### Likelihood Explanation
The comparison happens on every request to these endpoints and is fully remote/unauthenticated to probe (an attacker doesn't need any credential to start measuring). Recovering a secret via network timing requires statistical averaging over many requests per byte and is sensitive to network jitter, so it is not trivial, but it is a well-established, practical attack class (e.g., historical HMAC/keyczar timing leaks) especially against colocated or low-latency/high-bandwidth adversaries (e.g., another node on the same LAN/cloud region as the target, which is a realistic operator scenario for stacks-node/stacks-signer pairs).

### Recommendation
Replace all `auth_header != password` (and any equivalent) comparisons in `stackslib/src/net/api/blockreplay.rs`, `blocksimulate.rs`, `fastcallreadonly.rs`, `postblock_proposal.rs`, `postblock_v3.rs`, and `txsimulate.rs` with a constant-time comparison (e.g. `subtle::ConstantTimeEq`, or compare fixed-length HMACs of the header/token instead of raw strings).

### Proof of Concept
1. Configure a node with `connection_options.auth_token = "<secret>"`.
2. From a remote/unauthenticated client, repeatedly POST to `/v3/block_proposal` (or any of the other gated endpoints) with candidate `authorization` header values that share an increasing common prefix with the real token, measuring response latency for the 401 rejection path in `try_parse_request`.
3. Statistically, candidates matching more leading bytes will show a measurable (if small) latency increase due to the early-exit byte-wise `!=` comparison, allowing incremental byte-by-byte recovery of `auth_token`.
4. Once recovered, submit an authorized POST with the correct header to `/v3/block_proposal` or `/v2/blocks?broadcast=1`, bypassing the intended access control.
