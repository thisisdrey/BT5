### Title
GetInfoAttributes spawns `cat-file` using unvalidated `GitObjectDirectory`/`GitAlternateObjectDirectories` fields from the request's `Repository` message - ([File: internal/gitaly/service/repository/info_attributes.go])

### Summary
`GetInfoAttributes` only validates `in.GetRepository().RelativePath` via `s.locator.ValidateRepository`, which never inspects `GitObjectDirectory` or `GitAlternateObjectDirectories`. [1](#0-0)  The `configLocator.ValidateRepository` implementation confirms it validates only `StorageName`/`RelativePath` via `storage.ValidateRelativePath`, with no check whatsoever on the object-directory fields. [2](#0-1)  The subsequently built `localrepo.Repo` is used directly to run `cat-file -p HEAD:.gitattributes` with no additional path sanitation performed by the handler itself. [3](#0-2) 

### Finding Description
`GetInfoAttributes` builds a `localrepo.Repo` directly from the attacker-supplied `Repository` proto message and immediately calls `repo.Exec(...)` to run `cat-file`. [4](#0-3)  The only gate before that is `s.locator.ValidateRepository`, whose sole path check is `storage.ValidateRelativePath(storagePath, relativePath)` on `RelativePath` — `GitObjectDirectory` and `GitAlternateObjectDirectories` are never read or validated in this function. [5](#0-4) 

Elsewhere in the codebase, when these fields are consumed to influence a spawned Git process (e.g. custom hook environment construction), they are joined onto the repository path with plain `filepath.Join` and **no** `storage.ValidateRelativePath`/storage-root check, confirming that the codebase does not uniformly sanitize these fields for every consumer: [6](#0-5) . The one place that *does* validate an object directory, `Repo.ObjectDirectoryPath`, is a separate helper that `GetInfoAttributes` never calls before spawning `cat-file`. [7](#0-6)  There is no equivalent validation function anywhere for the `GitAlternateObjectDirectories` list (a plural field) comparable to the alternates-file-based validation performed by `git.AlternateObjectDirectories`/`altObjectDirs`, which only applies to alternates *discovered from disk* (`objects/info/alternates`), not to alternates supplied directly on the RPC `Repository` message. [8](#0-7) 

Because `GetInfoAttributes` never calls `ObjectDirectoryPath` or any comparable validator on the request's `Repository` before executing `cat-file`, an attacker who can submit a raw `GetInfoAttributesRequest` (bypassing normal Rails-mediated construction of the `Repository` message, per the stated precondition of forged/replayed auth) can freely set `GitAlternateObjectDirectories` with `../` segments. If `repo.Exec`'s underlying command construction translates these proto fields into `GIT_OBJECT_DIRECTORY`/`GIT_ALTERNATE_OBJECT_DIRECTORIES` environment variables for the spawned git process (as is the established pattern seen in the hook-environment code above), the `cat-file` process would search object stores outside the storage root.

### Impact Explanation
If reachable, the impact is limited by Git's object-lookup semantics: the alternate directory must be a valid Git object store (loose objects/pack files) containing an object matching the resolved SHA for `HEAD:.gitattributes`; this is not an arbitrary raw file read (e.g. `/etc/passwd` cannot be read this way), but it does permit disclosure of Git objects/blobs from an attacker-chosen filesystem location outside the intended storage root — a cross-repository/object-store disclosure primitive, and a violation of the storage-root confinement invariant.

### Likelihood Explanation
Exploitation requires the attacker to already have a way to submit a raw, authenticated `GetInfoAttributesRequest` directly to Gitaly with full control of the `Repository` proto's `GitAlternateObjectDirectories` field — i.e., forged/replayed Gitaly-internal auth plus bypass of the normal GitLab Rails-mediated request construction (which does not normally populate these fields for user-facing RPCs). Given that precondition, `ValidateRepository`'s confirmed omission of these fields makes the escape straightforward to construct, though the attacker also needs the target alternate location to contain a git-loose/pack object matching the SHA of `HEAD:.gitattributes`, which limits practical exploitation to known/predictable alternate object stores.

### Recommendation
Extend `ValidateRepository` (or add a dedicated check invoked by `GetInfoAttributes` and any other handler that builds a `localrepo.Repo` from a request `Repository`) to run `storage.ValidateRelativePath` against `GitObjectDirectory` and every entry of `GitAlternateObjectDirectories`, rejecting any path that escapes the storage root (mirroring the check already present in `Repo.ObjectDirectoryPath`), before any git command is executed on the repository.

func (l *configLocator) ValidateRepository(ctx context.Context, repo storage.Repository, opts ...storage.ValidateRepositoryOption) error {
	var cfg storage.ValidateRepositoryConfig
	for _, opt := range opts {
		opt(&cfg)
	}

	// Only checking for `nil` isn't sufficient as Protobuf messages may be non-nil, but still
	// either invalid or empty. Thus we also explicitly verify whether both the storage name and
	// the relative path are unset.
	if repo == nil || repo.GetStorageName() == "" && repo.GetRelativePath() == "" {
		return structerr.NewInvalidArgument("%w", storage.ErrRepositoryNotSet)
	}

	relativePath := repo.GetRelativePath()
	if len(relativePath) == 0 {
		return structerr.NewInvalidArgument("%w", storage.ErrRepositoryPathNotSet)
	}

	if cfg.SkipStorageExistenceCheck {
		return nil
	}

	storagePath, err := l.GetStorageByName(ctx, repo.GetStorageName())
	if err != nil {
		return err
	}

	if _, err := os.Stat(storagePath); err != nil {
		if os.IsNotExist(err) {
			return structerr.NewNotFound("storage does not exist").WithMetadata("storage_path", storagePath)
		}
		return structerr.New("storage path: %w", err).WithMetadata("storage_path", storagePath)
	}

	if _, err := storage.ValidateRelativePath(storagePath, relativePath); err != nil {
		return structerr.NewInvalidArgument("%w", err).WithMetadata("relative_path", relativePath)
	}

func altObjectDirs(ctx context.Context, logger log.Logger, storagePrefix, objDir string, depth int) ([]string, error) {
	const maxAlternatesDepth = 5 // Taken from https://github.com/git/git/blob/v2.23.0/sha1-file.c#L575
	if depth > maxAlternatesDepth {
		logger.WithField("objdir", objDir).WarnContext(ctx, "ignoring deeply nested alternate object directory")
		return nil, nil
	}

	fi, err := os.Stat(objDir)
	if os.IsNotExist(err) {
		logger.WithField("objdir", objDir).WarnContext(ctx, "object directory not found")
		return nil, nil
	}
	if err != nil {
		return nil, err
	}
	if !fi.IsDir() {
		return nil, nil
	}

	dirs := []string{objDir}

	alternates, err := os.ReadFile(filepath.Join(objDir, "info", "alternates"))
	if os.IsNotExist(err) {
		return dirs, nil
	}
	if err != nil {
		return nil, err
	}

	for _, newDir := range strings.Split(string(alternates), "\n") {
		if len(newDir) == 0 || newDir[0] == '#' {
			continue
		}

		if !filepath.IsAbs(newDir) {
			newDir = filepath.Join(objDir, newDir)
		}

		if !strings.HasPrefix(newDir, storagePrefix) {
			return nil, alternateOutsideStorageError(newDir)
		}

		nestedDirs, err := altObjectDirs(ctx, logger, storagePrefix, newDir, depth+1)
		if err != nil {
			return nil, err
		}

		dirs = append(dirs, nestedDirs...)
	}
