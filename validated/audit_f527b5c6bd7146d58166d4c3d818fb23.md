## Finding

### Title
Unsolicited StackerDB chunk push acknowledges/advertises a new slot version before the chunk is actually written to the store - (File: `stackslib/src/net/stackerdb/mod.rs`)

### Summary
`PeerNetwork::handle_unsolicited_StackerDBPushChunk` patches and sends back a `StackerDBChunkInv` acknowledging the *new* slot version of a pushed chunk before the chunk has actually been persisted to the local `chunks` table, and only afterwards forwards the raw chunk to the relayer for the actual write. This mirrors the reentrancy report's root cause: an accounting/inventory value is updated to reflect a future state change while the authoritative backing store (the balance / the DB row) has not yet caught up, so a third party can observe and act on a value that does not yet correspond to real, stored state.

### Finding Description
`validate_received_chunk` only checks signature, size, freshness, and max-writes — it never writes anything [1](#0-0) . The actual, durable acceptance of a chunk happens through `StackerDBTx::try_replace_chunk`, which re-verifies the signer/version and then calls `insert_chunk` [2](#0-1) .

In `handle_unsolicited_StackerDBPushChunk`, after `validate_received_chunk` returns true, the code directly mutates the outgoing inventory reply (`payload`) to claim the pushed chunk's version is now current — `*slot_version = chunk_data.chunk_data.slot_version;` — and wakes up the sync state machine, all *before* the chunk bytes are ever committed to the `chunks` table: [3](#0-2) 

The function then either signs and sends this patched `StackerDBChunkInv` reply immediately (`send_reply == true` path) or forwards the message to the relayer for later processing (`Ok((false, true))`): [4](#0-3) 

The comment at the top of the function ("Note that this can happen during a StackerDB sync's execution... The only modification possible here is to wakeup the state machine") [5](#0-4)  confirms this function itself never calls `try_replace_chunk`/`insert_chunk` — actual storage is deferred to a later step (relay/message processing). This creates a window where the node's advertised inventory (`slot_versions` in `StackerDBChunkInv`, and the state seen by `get_slot_versions`/`get_chunk`) says version N is available, but the `chunks` table still holds version N-1 (or nothing) and `StackerDBGetChunk` will therefore either return the stale chunk or a version-mismatch NACK (`StaleVersion`/`FutureVersion`), as seen in `make_stacker_db_getchunk_response`: [6](#0-5) 

This is the same class of bug as the `validateOffer()` report: an internal bookkeeping value (`_outstandingValues` / here, the advertised `slot_versions` inventory) is bumped optimistically ahead of the actual state-changing operation (asset transfer / chunk write), and anything that can observe or act on that intermediate, inconsistent state before it settles can be misled.

### Impact Explanation
Any peer that queries this node's `StackerDBChunkInv`/`StackerDBGetChunksInv` or fetches via `StackerDBGetChunk` during the gap between the optimistic ack and the actual DB write will see a version mismatch: the node claims to have version N of a slot but cannot yet serve it, or serves the previous (non-canonical relative to the announcement) version. Downstream StackerDB sync logic (`StackerDBSync::getchunks`) uses the remote's advertised `slot_versions` to decide what to fetch and can create futile fetch/backoff cycles across the network based on state this node has not actually committed yet. This falls under "steering a node off the tip via false inventory" / serving non-canonical state as canonical for StackerDB replicas (signer sets, miner/pox coordination data, etc. depend on StackerDB), which the rules classify as High.

### Likelihood Explanation
This requires no privileged access: it is triggered purely by sending a normal, validly-signed `StackerDBPushChunk` message (unsolicited, from any connected peer) and then immediately querying the node's inventory/chunk from a second connection — an interaction any remote, unauthenticated (from network perspective) peer can perform. The race window's width depends on scheduling/relay timing which I was not able to fully trace through `unsolicited.rs`/`relay.rs` in the time available, so the exact size of the exploitable window (and whether the eventual relayed write is guaranteed to occur, or can be dropped/delayed) remains unverified with the given index; this uncertainty should be validated by reading the full downstream chunk-processing path.

### Recommendation
Do not mutate/advertise the new slot version in the `StackerDBChunkInv` reply (or wake the sync state machine as if the data is present) until the chunk has actually been durably written via `try_replace_chunk`. Either perform the write synchronously inside `handle_unsolicited_StackerDBPushChunk` before constructing the ack, or only patch/send the inventory after the relayer confirms the write succeeded.

### Proof of Concept
1. Peer A opens a P2P connection and sends a valid, correctly-signed `StackerDBPushChunk` for slot 0, bumping its version from V to V+1, to node B.
2. Node B's `handle_unsolicited_StackerDBPushChunk` validates the chunk (`validate_received_chunk` passes) and patches its outbound `StackerDBChunkInv` to report slot 0 = V+1, then sends this ack back to A and forwards the raw chunk to the relayer for actual storage [3](#0-2) .
3. Before the relayer processes and calls `try_replace_chunk` to persist it, Peer C (a second connection to B) sends `StackerDBGetChunksInv`/`StackerDBGetChunk` for the same contract/slot.
4. B's `make_StackerDBChunksInv_or_Nack`/`get_slot_versions` (backed by the `chunks` table, not yet updated) still reports V, or `make_stacker_db_getchunk_response` returns a `StaleVersion`/`FutureVersion` NACK for a request at V+1 [6](#0-5) , demonstrating the advertised-vs-stored mismatch window that peer A's ack already exposed to A one step earlier.

    pub fn validate_received_chunk(
        &self,
        smart_contract_id: &QualifiedContractIdentifier,
        config: &StackerDBConfig,
        data: &StackerDBChunkData,
        expected_versions: &[u32],
    ) -> Result<bool, net_error> {
        // validate -- must not exceed this replica's configured chunk size.
        if (data.data.len() as u64) > config.chunk_size {
            info!(
                "Received StackerDBChunk for {} ID {}, which is oversized: {} bytes (max {} bytes)",
                smart_contract_id,
                data.slot_id,
                data.data.len(),
                config.chunk_size
            );
            return Ok(false);
        }

        // validate -- must be a valid chunk
        let Some(expected_version) = expected_versions.get(data.slot_id as usize) else {
            info!(
                "Received StackerDBChunk for {} ID {}, which is too big ({})",
                smart_contract_id,
                data.slot_id,
                expected_versions.len()
            );
            return Ok(false);
        };

        // validate -- must be signed by the expected author
        let addr = match self
            .stackerdbs
            .get_slot_signer(smart_contract_id, data.slot_id)?
        {
            Some(addr) => addr,
            None => {
                return Ok(false);
            }
        };

        let slot_metadata = data.get_slot_metadata();
        if !slot_metadata.verify(&addr)? {
            info!(
                "StackerDBChunk for {} ID {} is not signed by {}",
                smart_contract_id, data.slot_id, &addr
            );
            return Ok(false);
        }

        // validate -- must be the current or newer version
        if data.slot_version < *expected_version {
            info!(
                "Received StackerDBChunk for {} ID {} version {}, which is stale (expected {})",
                smart_contract_id, data.slot_id, data.slot_version, *expected_version
            );
            return Ok(false);
        }

        // validate -- must not exceed max writes
        if data.slot_version > config.max_writes {
            info!(
                "Write count exceeded for StackerDBChunk for {} ID {} version {} (max is {})",
                smart_contract_id, data.slot_id, data.slot_version, config.max_writes
            );
            return Ok(false);
        }

        Ok(true)
    }

    pub fn try_replace_chunk(
        &self,
        smart_contract: &QualifiedContractIdentifier,
        slot_desc: &SlotMetadata,
        chunk: &[u8],
    ) -> Result<(), net_error> {
        // Check per-replica chunk-size cap.
        if (chunk.len() as u64) > self.config.chunk_size {
            return Err(net_error::StackerDBChunkTooBig(chunk.len()));
        }

        let slot_validation = self
            .get_slot_validation(smart_contract, slot_desc.slot_id)?
            .ok_or(net_error::NoSuchSlot(
                smart_contract.clone(),
                slot_desc.slot_id,
            ))?;

        if !slot_desc.verify(&slot_validation.signer)? {
            return Err(net_error::BadSlotSigner(
                slot_validation.signer,
                slot_desc.slot_id,
            ));
        }
        if slot_desc.slot_version <= slot_validation.version {
            return Err(net_error::StaleChunk {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
            });
        }
        if slot_desc.slot_version > self.config.max_writes {
            return Err(net_error::TooManySlotWrites {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
                max_writes: self.config.max_writes,
            });
        }
        self.insert_chunk(smart_contract, slot_desc, chunk)
    }
