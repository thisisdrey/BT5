Audit Report

## Title
Unbounded, XCM-controlled `gas` on `Command::CallContract` breaks the fixed-gas invariant enforced for every other Snowbridge V2 outbound command - (File: `bridges/snowbridge/primitives/outbound-queue/src/v2/message.rs`)

## Summary
`ConstantGasMeter::maximum_dispatch_gas_used_at_most` returns fixed protocol constants for every `Command` variant except `Command::CallContract`, where it returns the caller-supplied `gas: u64` field unmodified. That value is decoded straight from an XCM `Transact` payload via `ContractCall::decode_all` with no upper bound, then committed into `CommandWrapper.gas` in the Merkle-hashed outbound message delivered to the Ethereum `Gateway` contract, with no linkage to the fee actually paid.

## Finding Description
`Command::CallContract` is constructed in `XcmConverter::convert` directly from a `Transact` instruction's decoded call bytes, taking `gas` verbatim: `ContractCall::V1 { target, calldata, gas, value } => commands.push(Command::CallContract { target: target.into(), calldata, gas, value })` [1](#0-0) . In `ConstantGasMeter::maximum_dispatch_gas_used_at_most`, every other branch returns a fixed constant (`40_000`, `50_000 + initializer gas`, `200_000`, `1_200_000`, `100_000`), but `Command::CallContract { gas: gas_limit, .. } => *gas_limit` passes the attacker-supplied value through unchanged [2](#0-1) . This value becomes `OutboundCommandWrapper.gas`/`CommandWrapper.gas` in `Pallet::process` in `outbound-queue-v2`, which is hashed into `MessageLeaves` and later verified on Ethereum [3](#0-2) .

I verified that `send_message_impl.rs`'s `validate` function for the v2 outbound queue only checks payload size — it does not compute or check any fee-to-gas relationship: `ensure!(payload.len() < T::MaxMessagePayloadSize::get() as usize, SendError::MessageTooLarge)` [4](#0-3) . The `fee_amount` extracted in `extract_remote_fee` only checks that `WithdrawAsset`/`PayFees` use Ether and that the reserved amount covers the paid fee — it has no connection to the `gas` requested in a later `Transact` instruction [5](#0-4) . The gating check for reaching this path is `AllowedAliasOrigin::contains(origin_location)` in `XcmConverter::convert`, which is a generic filter parameter of `EthereumBlobExporter`/`XcmConverter`, not a hardcoded privileged check [6](#0-5) , [7](#0-6) .

This confirms the core defect: the `CallContract` branch is structurally inconsistent with every other command in the same `match` — all others are bound to protocol-defined constants, while `CallContract`'s gas is fully attacker-controlled, unvalidated against the fee paid, and flows unmodified into the committed, hashed message delivered to Ethereum.

## Impact Explanation
This matches the accepted impact category of "public underpriced work that degrades block production or stalls bridge processing." An attacker able to route a `Transact` instruction through an `AllowedAliasOrigin`-permitted alias origin can request an arbitrarily large `gas` (up to `u64::MAX`) that gets committed into the message hash queued for relay/execution on Ethereum, while paying only the minimal fee validated by `extract_remote_fee` for the accompanying transfer — the gas request is entirely decoupled from cost. This can result in underpriced execution burden on relayers/Gateway or stalled processing of that message and (since nonces are sequential) potentially subsequent messages.

## Likelihood Explanation
The severity and exploitability depend entirely on how `AllowedAliasOrigin` is configured in the actual runtime deployment. I was unable to find any runtime in this repository that configures `AllowedAliasOrigin` for the V2 exporter — a search for `type AllowedAliasOrigin` returned no matches, meaning I could not confirm whether production Bridge Hub runtimes permit broad/unprivileged aliasing or restrict it to trusted origins only (e.g., sovereign accounts of specific trusted parachains). The code-level asymmetry between the constant-gas branches and the pass-through `CallContract` branch is real and directly verifiable, but the actual attacker-reachability depends on the `AllowedAliasOrigin::Contains<Location>` implementation supplied at runtime, which I could not locate/verify. If `AllowedAliasOrigin` is restrictive (e.g., limited to specific privileged/trusted locations), this significantly reduces or eliminates the "unprivileged external attacker" reachability required by this program's rules.

## Recommendation
Cap the `gas` value accepted for `Command::CallContract` at a fixed protocol maximum (consistent with the other command constants), and/or require `fee_amount` from `PayFees`/`WithdrawAsset` to scale proportionally with the requested `gas`, so that the committed gas is either protocol-bound or economically bound to what was actually paid.

## Proof of Concept
1. Construct a V2 XCM with `WithdrawAsset`/`PayFees` using a minimal fee, followed by an `AliasOrigin` accepted by the runtime's `AllowedAliasOrigin` filter, `DepositAsset`, and a `Transact` instruction encoding `ContractCall::V1 { target, calldata, gas: u64::MAX, value }`.
2. Submit through `XcmConverter::convert`, which pushes `Command::CallContract { gas: u64::MAX, .. }` without any bound check [1](#0-0) .
3. When `Pallet::process` in `outbound-queue-v2` runs, `ConstantGasMeter::maximum_dispatch_gas_used_at_most` returns `u64::MAX` as `CommandWrapper.gas`, hashed into `MessageLeaves` for relay to Ethereum, despite the minimal fee paid in step 1 [8](#0-7) .

Note: reproducing this against a live, unprivileged attacker path requires confirming a concrete runtime's `AllowedAliasOrigin` configuration permits an ordinary/unprivileged origin to alias — this could not be verified in the indexed codebase and should be checked against the actual Bridge Hub runtime configuration before treating this as fully exploitable by an unprivileged actor.

impl GasMeter for ConstantGasMeter {
	fn maximum_dispatch_gas_used_at_most(command: &Command) -> u64 {
		match command {
			Command::SetOperatingMode { .. } => 40_000,
			Command::Upgrade { initializer, .. } => {
				// total maximum gas must also include the gas used for updating the proxy before
				// the the initializer is called.
				50_000 + initializer.maximum_required_gas
			},
			Command::UnlockNativeToken { .. } => 200_000,
			Command::RegisterForeignToken { .. } => 1_200_000,
			Command::MintForeignToken { .. } => 100_000,
			Command::CallContract { gas: gas_limit, .. } => *gas_limit,
		}
	}
}
