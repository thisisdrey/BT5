### Title
Stale `updated-entry` overwrite in `collateral-add` allows a malicious FT re-entering `collateral-remove` to restore a phantom collateral mask bit after the real collateral was zeroed - ([File: mainnet/contracts/market/v0-market-vault.clar])

### Summary
`collateral-add` computes `updated-entry` (with the new asset's mask bit inserted) from a `mask` snapshot taken *before* the token transfer, then calls `receive-tokens`, and only afterwards unconditionally writes that precomputed `updated-entry` via `insert`. Because the token contract passed as `<ft-trait>` is attacker-controlled, its `transfer` implementation can re-enter the vault (through the market impl) and fully and correctly remove a different, already-fully-owned collateral asset via `collateral-remove` in between. When the outer `collateral-add` resumes, it blindly overwrites the just-corrected mask with its stale snapshot, resurrecting a mask bit for an asset whose collateral row was actually deleted.

### Finding Description
In `collateral-add`:
```

```
the `let` bindings compute `mask`, `updated-mask`, and `updated-entry` from `entry (resolve-or-create account)` *before* `(try! (receive-tokens ft amount account))` is invoked, and `add-user-collateral` for the new asset is also applied in these eager `let` bindings, ahead of the actual transfer. `receive-tokens` performs `(contract-call? asset transfer amount account current-contract none)` where `asset` is the caller-supplied `<ft-trait>` principal [1](#0-0) . Since this is a dynamic `contract-call?` to an attacker-deployed contract, arbitrary Clarity code executes at this point, including a call back through the market implementation into `collateral-remove` for a different asset that the same account fully owns.

`collateral-remove` re-reads the registry with `(resolve account)`, which at this moment still returns the *old*, un-updated entry, because the outer `collateral-add` has not yet called `insert updated-entry` [2](#0-1) . `collateral-remove` correctly zeroes the target asset's `collateral` map row (`remove-user-collateral` deletes the entry when `remaining` is `u0`) and computes and inserts a *correct* mask with that bit cleared. Control then returns to the outer `collateral-add`, which resumes after `receive-tokens` and unconditionally executes `(insert updated-entry)` with the mask it snapshotted at the start of the call - which still has the removed asset's bit set (plus the newly added asset's bit). This overwrites the correct registry state written by the re-entrant `collateral-remove`, leaving `registry[id].mask` containing a bit for an asset whose `collateral` map row no longer exists.

`check-impl-auth` (`(asserts! (is-eq contract-caller (var-get impl)) ERR-AUTH)`) does not prevent this: `contract-caller` reflects only the direct caller of the vault function, and both the outer and the re-entrant calls arrive from the market implementation contract (`impl`), which is itself invoked by the attacker's malicious FT `transfer` hook and then re-invoked by that hook. No mutex, re-entrancy guard, or "checks-effects-interactions" ordering exists in `collateral-add`/`collateral-remove` to prevent this state clobbering. [3](#0-2) 

### Impact Explanation
This produces a mask/collateral desynchronization: `registry[id].mask` claims a bit for an asset (`assetA`) that has zero backing in the `collateral` map (row deleted). Any downstream health-check or LTV computation that iterates the mask via `lookup-collateral`/`get-position` (`mainnet/contracts/market/v0-market-vault.clar:299-333`) will treat this phantom row (`get-collateral` on a deleted key `unwrap-panic`s in read-only form, but any live re-add of a small amount to the same asset makes the row exist again with a stale/incorrect stacked amount, or the borrow logic that trusts the mask/collateral pairing directly will use incorrect accounting), letting the attacker borrow against collateral that was actually withdrawn. This is a direct insolvency vector matching the Critical class: "protocol insolvency."

### Likelihood Explanation
Preconditions: attacker needs an account that (1) holds a fully-covered collateral position in one asset (`assetA`), and (2) deploys and gets `assetB` accepted as a valid `<ft-trait>` collateral asset argument to `collateral-add` (any FT contract satisfying the trait signature can be passed by the caller - the market does not require asset allow-listing at the trait-parameter level beyond `asset-id`, per the code shown; this can be confirmed further against `v0-4-market.clar`, which was not fully reviewed due to iteration limits). Capital cost is limited to the collateral already deposited plus gas; no flashloan or governance access is required. The re-entrancy trigger is a standard "malicious token with a callback in `transfer`" pattern, which is fully within an ordinary unprivileged attacker's capability. The exploit is deterministic and repeatable once the malicious FT is deployed and accepted as an asset.

### Recommendation
Apply checks-effects-interactions ordering in `collateral-add` and `collateral-remove`: perform `receive-tokens`/`send-tokens` first, then re-resolve the account/entry fresh (not from a pre-call snapshot) and compute/`insert` the updated mask and collateral amounts using the freshly re-read state after the external call returns. Alternatively, add an explicit re-entrancy guard (a boolean "busy" flag per obligation `id`, or a global lock) around the vault's collateral/debt mutation paths so that a nested call into `collateral-add`/`collateral-remove`/`debt-add-scaled`/`debt-remove-scaled` for the same `impl` aborts with an error.

### Proof of Concept
Clarinet simnet test plan:
1. Deploy `v0-market-vault.clar`, the market impl (`v0-4-market.clar`), a benign `assetA` SIP-010 token, and a malicious `assetB` token contract implementing `ft-trait` whose `transfer` function, when called with a specific trigger amount/sender, calls back into the market impl's collateral-remove entry point for `assetA` with `amount = full balance`, before returning `(ok true)`.
2. As attacker principal `M`, deposit into `assetA` via the market impl's collateral-add path until `get-collateral(M, A)` equals the full amount and `(get mask (lookup id-of-M))` has bit `A` set.
3. Call the market impl's collateral-add entry with `assetB` as the `<ft-trait>` argument for account `M`. This triggers `v0-market-vault.collateral-add`, which calls `receive-tokens` on malicious `assetB`, re-entering `collateral-remove` for `assetA`.
4. Assert: mid-reentrancy, `get-collateral(M, A)` is deleted/absent (`map-get?` returns `none`) confirming the real collateral was removed.
5. After the outer call completes, assert `(get mask (lookup id-of-M))` still has bit `A` set (phantom bit), while `get-collateral(M, A)` is absent - demonstrating the mask/collateral desync.
6. Call `lookup-collateral(id-of-M, mask, enabled-mask)` and assert it returns an entry for asset `A` (from `iter-lookup-collateral`, which will `unwrap-panic` on the missing `get-collateral` call or return a stale value depending on exact map state after any subsequent action), demonstrating that a follow-on borrow/health-check call would treat the withdrawn asset as still backing debt.

```text
(define-public (collateral-remove (account principal) (amount uint) (ft <ft-trait>) (asset-id uint) (recipient principal))
  (let ((states (var-get pause-states))
        (entry (resolve account))
        (user-id (get id entry))
        (mask (get mask entry))
        (remaining (try! (remove-user-collateral user-id asset-id amount)))
        (updated-mask (if (is-eq remaining u0)
                        (mask-update mask asset-id true false) ;; collateral, remove
                        mask))
        (updated-entry (merge entry (refresh updated-mask))))

    (try! (check-impl-auth))
    (asserts! (not (get collateral-remove states)) ERR-PAUSED)
    (asserts! (> amount u0) ERR-AMOUNT-ZERO)

    (insert updated-entry)
```
