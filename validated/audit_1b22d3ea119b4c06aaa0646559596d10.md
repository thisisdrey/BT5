### Title
Attachment reliability score bumped on successful HTTP fetch without verifying returned bytes hash to the requested `content_hash` - (File: stackslib/src/net/atlas/download.rs)

### Summary
`AttachmentsBatchStateContext::extend_with_attachments` calls `report.bump_successful_requests()` as soon as `decode_atlas_get_attachment()` succeeds, without ever comparing the returned `Attachment`'s hash to the `AttachmentRequest::content_hash` that was actually requested. Since `decode_atlas_get_attachment` (in `getattachment.rs`) performs no hash validation either, any peer can return arbitrary hex-encoded bytes for `GET /v2/attachments/<hash>` and still be scored as "successful," inflating its `ReliabilityReport` for free.

### Finding Description
The claimed fault is confirmed: reliability is bumped on "HTTP 200 + well-formed JSON," not on "bytes hash to `content_hash`."

- `Requestable::make_request_type` for `AttachmentRequest` issues `GET /v2/attachments/{content_hash}` [1](#0-0) , and `get_most_reliable_source` picks the URL purely by `ReliabilityReport::score()` [2](#0-1) .
- In `BatchedRequestsState::try_proceed`, any non-404 HTTP response is placed straight into `state.succeeded`, with no content check at all [3](#0-2) .
- `extend_with_attachments` then decodes the body via `decode_atlas_get_attachment()` and, on success, inserts `response.attachment` into `self.attachments` and immediately calls `report.bump_successful_requests()` — there is no comparison of `response.attachment.hash()` against `request.content_hash` anywhere in this path [4](#0-3) .
- `decode_atlas_get_attachment` itself only parses JSON/hex into a `GetAttachmentResponse`/`Attachment`; it does not take or check any expected hash [5](#0-4) , and `GetAttachmentResponse`'s `Deserialize` impl simply hex-decodes attacker-supplied bytes into an `Attachment` with no hash binding [6](#0-5) .
- The hash check only ever happens indirectly and later, in `AttachmentsDownloader::run()`, which uses `attachment.hash()` (the hash of whatever bytes were returned) as a lookup key into `find_all_attachment_instances`, not as a verification against the original request's `content_hash` [7](#0-6) . If the attacker's garbage bytes don't hash to any pending instance's `content_hash`, the data is simply orphaned in the DB — but the `ReliabilityReport` bump has already happened, and happens on every such garbage response.

Because `AttachmentRequest`'s `Ord` impl sorts candidates by `ReliabilityReport` score [8](#0-7) , and `get_most_reliable_source`/`get_url` route future requests for *any* `content_hash` to the highest-scoring peer [2](#0-1) [9](#0-8) , an attacker peer can cheaply farm a top reliability score by repeatedly returning small, well-formed-but-wrong hex blobs, then get preferentially selected for genuine attachment/BNS zonefile requests and keep returning garbage for those too — each such response still scores as "successful," so the retry count is never usefully consumed against a source that will ever deliver the real content, and the batch retry budget (`max_attachment_retry_count`) is exhausted on a channel that structurally cannot succeed [10](#0-9) .

### Impact Explanation
This corrupts the Atlas peer-reliability ranking used to select attachment sources, letting an unprivileged attacker peer make itself the preferred source for arbitrary attachment/BNS zonefile hashes and then reliably fail to deliver the real content while still being counted as "successful." The concrete effect is denial of legitimate attachment (including BNS zonefile) resolution for a targeted node: honest peers get deprioritized, and the node's finite `max_attachment_retry_count` budget is burned against a peer that will never supply the correct bytes, until the batch is dropped [10](#0-9) . No consensus-critical or chain-tip state is corrupted (the mismatched attachment is never linked to an `AttachmentInstance` unless its hash coincidentally matches, which is a preimage-infeasible event), so this is a resource/availability degradation on the Atlas attachment/BNS subsystem rather than a state-corruption bug.

### Likelihood Explanation
Trivial to trigger: the attacker only needs to run any outbound-syncable peer that a victim node connects to, respond to `/v2/attachments/inv` and `/v2/attachments/{hash}` requests with well-formed but arbitrary JSON payloads, and repeat. No secrets, StackerDB slots, or privileged roles are required — this matches the "unprivileged remote peer" threat model exactly. The cost per attempt is a single small HTTP response.

### Recommendation
In `AttachmentsBatchStateContext::extend_with_attachments` (`stackslib/src/net/atlas/download.rs:530-558`), after `decode_atlas_get_attachment()` succeeds, compute `response.attachment.hash()` and compare it to `request.content_hash` before calling `report.bump_successful_requests()`; only bump success on a hash match, and call `bump_failed_requests()` (or a distinct "served wrong content" penalty) otherwise, and only insert the attachment into `self.attachments` when the hash matches.

### Proof of Concept
Add a test in `stackslib/src/net/atlas/download.rs`'s test module that constructs an `AttachmentRequest` with a known `content_hash`, builds a `BatchedRequestsResult<AttachmentRequest>` whose `succeeded` map contains that request paired with a `StacksHttpResponse` encoding a `GetAttachmentResponse` for different bytes (so `attachment.hash() != content_hash`), calls `AttachmentsBatchStateContext::extend_with_attachments` on it, and asserts on the resulting `ReliabilityReport` for the peer URL: expect the fixed code to show `total_requests_success == 0`, but with current code `report.bump_successful_requests()` has already incremented the success counter despite the hash mismatch, demonstrating the reliability-bump-before-hash-check fault at `stackslib/src/net/atlas/download.rs:547-549`.

    pub fn extend_with_attachments(
        mut self,
        results: &mut BatchedRequestsResult<AttachmentRequest>,
    ) -> AttachmentsBatchStateContext {
        for (request, response) in results.succeeded.drain() {
            let report = self
                .peers
                .get_mut(request.get_url())
                .expect("Atlas: unable to retrieve reliability report for peer");

            let response = if let Some(r) = response {
                r
            } else {
                report.bump_failed_requests();
                continue;
            };

            if let Ok(response) = response.decode_atlas_get_attachment() {
                self.attachments.insert(response.attachment);
                report.bump_successful_requests();
            } else {
                report.bump_failed_requests();
            }
        }
        let mut events_ids = results.faulty_peers.keys().copied().collect::<Vec<usize>>();
        self.events_to_deregister.append(&mut events_ids);

        self
    }

impl StacksHttpResponse {
    pub fn decode_atlas_get_attachment(self) -> Result<GetAttachmentResponse, NetError> {
        let contents = self.get_http_payload_ok()?;
        let contents_json: serde_json::Value = contents.try_into()?;
        let resp: GetAttachmentResponse = serde_json::from_value(contents_json)
            .map_err(|_e| NetError::DeserializeError("Failed to load from JSON".to_string()))?;
        Ok(resp)
    }
}
