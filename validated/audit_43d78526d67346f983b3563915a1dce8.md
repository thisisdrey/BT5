### Title
Missing content-hash verification in `AttachmentsBatchStateContext::extend_with_attachments` allows unauthenticated AtlasDB poisoning - ([File: stackslib/src/net/atlas/download.rs])

### Summary
`extend_with_attachments` accepts any `GetAttachmentResponse` from a peer as long as it JSON-decodes successfully, never checking that the returned `attachment.hash()` matches the `AttachmentRequest.content_hash` that was actually requested. A malicious peer serving `GET /v2/attachments/{content_hash}` can therefore return arbitrary attachment bytes that get permanently written to the node's `AtlasDB`.

### Finding Description
The broken equality is: `response.attachment.hash() == request.content_hash` is never checked. In `extend_with_attachments`, for each `(request, response)` pair drained from `results.succeeded`, the code does: [1](#0-0) 

```rust
if let Ok(response) = response.decode_atlas_get_attachment() {
    self.attachments.insert(response.attachment);
    report.bump_successful_requests();
} else {
    report.bump_failed_requests();
}
```

`request` is bound in scope (and holds `request.content_hash`, the hash the node actually asked for) but is never used to validate `response.attachment`. `decode_atlas_get_attachment()` in `stackslib/src/net/api/getattachment.rs` only performs JSON deserialization — it does not compute or compare any hash: [2](#0-1) 

Downstream, in `AttachmentsDownloader::run`, the `Done` branch drains `context.attachments` and, for each attacker-supplied `Attachment`, computes `attachment.hash()` (the attacker-controlled hash, not the originally requested `H`) and calls `network.atlasdb.insert_instantiated_attachment(&attachment)` unconditionally: [3](#0-2) 

This means: a peer that is an outbound sync peer for Atlas downloads (reachable, unprivileged remote party running its own HTTP server) can answer the attachment fetch for hash `H` with unrelated content of hash `H'`. That data is inserted into the local AtlasDB store (`insert_instantiated_attachment`) with no on-chain `AttachmentInstance` ever pointing at `H'` (since `find_all_attachment_instances(&H')` will typically return nothing), while the batch's tracking for `H` (`attachments_batch.resolve_attachment(&attachment.hash())`) is called with the wrong hash, so the original pending request for `H` is effectively never resolved/matched either — it will just get bumped/retried or dropped, and meanwhile forged data accumulates in local storage.

No existing guard (signature check, `MAX_MESSAGE_LEN`, JSON schema check) validates content-hash equality; the only checks performed are HTTP status code (`!= 404`) and successful JSON decode.

### Impact Explanation
This is an unauthenticated write to node state: any peer the node treats as a "reliable"/outbound sync peer for Atlas attachment sync can inject arbitrary blobs (up to whatever size limit the HTTP/JSON body length allows) into the victim's `AtlasDB` via `insert_instantiated_attachment`, without those blobs corresponding to any real on-chain `AttachmentInstance`. Repeated across many distinct bogus "content hashes" this is a storage-exhaustion / data-poisoning primitive against the node's persistent Atlas attachment store. This matches "Critical - unauthenticated write to node state" per the severity rubric.

### Likelihood Explanation
Preconditions: the node must have a pending `AttachmentsBatch` entry (i.e., there is at least one un-instantiated on-chain-referenced content hash the node is trying to fetch), and the attacker must be selected as one of the `sources` peers in the corresponding `AttachmentRequest` (i.e., the attacker's peer inventory claims to have the attachment and the attacker is among `network.get_outbound_sync_peers()`). This only requires the attacker to run an ordinary peer that participates in gossip/inv responses — no admin role, no secret, no privileged access. The attack is trivially repeatable per HTTP response and costs the attacker nothing beyond running a normal peer/RPC responder.

### Recommendation
In `extend_with_attachments`, after `decode_atlas_get_attachment()` succeeds, compute `response.attachment.hash()` and compare it to `request.content_hash`; only insert into `self.attachments` (and only credit `bump_successful_requests`) if they match. Otherwise treat it as a failed/faulty response (`bump_failed_requests`, and consider adding the peer/event to `faulty_peers` for deregistration).

### Proof of Concept
Rust test in `stackslib/src/net/atlas` (or a new test module for `download.rs`):
1. Construct an `AttachmentsBatchStateContext` via `AttachmentsBatchStateContext::new` with an `AttachmentsBatch` that has `track_attachment`-ed a pending instance for hash `H`.
2. Build a `BatchedRequestsResult<AttachmentRequest>` whose `succeeded` map contains one entry: key = `AttachmentRequest { content_hash: H, .. }`, value = `Some(StacksHttpResponse)` constructed from a JSON body `{"attachment": {"content": "<bytes whose Hash160 != H>"}}` (i.e., a valid `GetAttachmentResponse` but with mismatched content).
3. Call `context.extend_with_attachments(&mut results)`.
4. Assert that `context.attachments` contains an `Attachment` whose `.hash()` (call it `H'`) is `!= H`.
5. Simulate the `Done` branch logic (or call `AttachmentsDownloader::run` end-to-end with a mocked network) and assert `atlasdb.find_attachment(&H_prime)` returns `Some(..)` after `insert_instantiated_attachment`, while `atlasdb.find_all_attachment_instances(&H_prime)` returns an empty vector (proving no on-chain `AttachmentInstance` ever referenced `H'`), demonstrating unauthenticated write of unverified data into AtlasDB.

    pub fn extend_with_attachments(
        mut self,
        results: &mut BatchedRequestsResult<AttachmentRequest>,
    ) -> AttachmentsBatchStateContext {
        for (request, response) in results.succeeded.drain() {
            let report = self
                .peers
                .get_mut(request.get_url())
                .expect("Atlas: unable to retrieve reliability report for peer");

            let response = if let Some(r) = response {
                r
            } else {
                report.bump_failed_requests();
                continue;
            };

            if let Ok(response) = response.decode_atlas_get_attachment() {
                self.attachments.insert(response.attachment);
                report.bump_successful_requests();
            } else {
                report.bump_failed_requests();
            }
        }
        let mut events_ids = results.faulty_peers.keys().copied().collect::<Vec<usize>>();
        self.events_to_deregister.append(&mut events_ids);

        self
    }

impl StacksHttpResponse {
    pub fn decode_atlas_get_attachment(self) -> Result<GetAttachmentResponse, NetError> {
        let contents = self.get_http_payload_ok()?;
        let contents_json: serde_json::Value = contents.try_into()?;
        let resp: GetAttachmentResponse = serde_json::from_value(contents_json)
            .map_err(|_e| NetError::DeserializeError("Failed to load from JSON".to_string()))?;
        Ok(resp)
    }
