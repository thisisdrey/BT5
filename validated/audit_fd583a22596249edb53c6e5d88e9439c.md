### Title
Transaction signing hash has no chain identifier, permitting signature replay across a post-fork chain split - (File: chainbase/src/main/java/org/tron/core/capsule/TransactionCapsule.java)

### Summary
Java-tron transactions are signed over `getTransactionId()`, the SHA-256 hash of `Transaction.raw` (`ref_block_bytes`, `ref_block_hash`, `expiration`, `contract`, `timestamp`, `fee_limit`, etc.). None of these fields, nor the domain used for `validateSignature`/`validatePubSignature`, contains a network/chain identifier analogous to EIP-155's `chainId` or an EIP-712 `DOMAIN_SEPARATOR`. This mirrors the reported bug class: the signed payload is not bound to a specific chain instance, so if the chain splits (hard fork producing two chains that briefly share history), a signature valid on one fork remains valid and independently broadcastable/executable on the other.

### Finding Description
The signature is created and checked purely from the raw transaction bytes: [1](#0-0) 
and verified via `validatePubSignature`/`validateSignature`, which only checks signature count, permission weights, and recovers the signer address from `getTransactionId()`—again with no chain-specific input: [2](#0-1) 

Replay protection is provided only by Tapos (`ref_block_hash`/`ref_block_bytes` matched against `RecentBlockStore`) and `expiration`, both enforced in `Manager.validateTapos`/`processTransaction`: [3](#0-2) [4](#0-3) 

The `Transaction.raw` protobuf schema itself has no chain/network identifier field: [5](#0-4) 

Because `ref_block_hash` only references a recent block within a small window (looked up by `RecentBlockStore`, keyed on the low bytes of the block number), and both branches of a fresh chain split share identical block history up to the fork point, a transaction referencing a pre-fork block hash with an unexpired timestamp is Tapos-valid and signature-valid on **both** resulting chains simultaneously. There is no chain-specific value folded into either the signed bytes or any separate domain check that would make the signature (or the transaction) rejectable on the "other" chain.

### Impact Explanation
In the event of a contentious hard fork/chain split (e.g., a disputed protocol upgrade producing two live networks sharing the same pre-fork state), any previously signed and broadcast transaction—transfers, TRC10 operations, contract triggers, freeze/vote/permission-update contracts, etc.—can be captured and rebroadcast by anyone (no privileged key needed) onto the sibling chain, where `validateTapos` and `validatePubSignature` will both accept it independently. This causes unauthorized duplicate execution of the same signed action (e.g., a transfer intended for chain A also executing on chain B), which is an unauthorized account operation / effective double-spend across the split, directly matching the accepted "chain split" impact class.

### Likelihood Explanation
Exploitation requires only a chain split/hard fork event and a network with mempool visibility (any node or public RPC observer can copy a valid signed transaction). No special privileges, keys, or malicious-SR/witness assumptions are needed—an ordinary API client that already legitimately received or observed a signed transaction can rebroadcast it to the other fork's `broadcastTransaction` endpoint. Likelihood tracks that of a hard fork occurring, which is a recognized operational risk for actively maintained chains such as java-tron.

### Recommendation
Bind the transaction signing domain to chain identity, e.g., by including a persistent chain identifier (such as the genesis block hash, already computed and available via `ChainBaseManager.getGenesisBlockId()`) as part of the hashed/signed payload, or by validating it as an additional out-of-band check during signature/Tapos validation so that transactions signed pre-fork cannot be replayed across the two post-fork networks.

### Proof of Concept
1. Prior to a chain split, user U signs and broadcasts transaction T (e.g., `TransferContract`) referencing recent block B (pre-fork) with `expiration` set in the future; T is accepted into chain A's mempool.
2. The network hard-forks at/after block B into chain A and chain B, both sharing identical history up to B.
3. An observer resubmits the identical raw bytes of T to a chain B node via `Wallet.broadcastTransaction` → `Manager.pushTransaction` → `processTransaction`.
4. `validateTapos` succeeds because chain B also has block B with the same hash in its `RecentBlockStore`; `validatePubSignature`/`validateSignature` succeed because the signing hash contains no chain-specific data.
5. T executes independently on chain B as well as chain A, resulting in the same signed action being applied twice across the two networks without a second signature from U.

  public boolean validatePubSignature(AccountStore accountStore,
      DynamicPropertiesStore dynamicPropertiesStore)
      throws ValidateSignatureException {
    if (!isVerified) {
      if (this.transaction.getSignatureCount() <= 0
              || this.transaction.getRawData().getContractCount() <= 0) {
        throw new ValidateSignatureException("miss sig or contract");
      }
      if (this.transaction.getSignatureCount() > dynamicPropertiesStore
              .getTotalSignNum()) {
        throw new ValidateSignatureException("too many signatures");
      }

      byte[] hash = getTransactionId().getBytes();

      long startNs = System.nanoTime();
      try {
        if (!validateSignature(this.transaction, hash, accountStore, dynamicPropertiesStore)) {
          isVerified = false;
          throw new ValidateSignatureException("sig error");
        }
      } catch (SignatureException | PermissionException | SignatureFormatException e) {
        isVerified = false;
        throw new ValidateSignatureException(e.getMessage());
      } finally {
        logSlowSigVerify(startNs);
      }
      isVerified = true;
    }
    return true;
  }

    byte[] refBlockHash = transactionCapsule.getInstance()
        .getRawData().getRefBlockHash().toByteArray();
    byte[] refBlockNumBytes = transactionCapsule.getInstance()
        .getRawData().getRefBlockBytes().toByteArray();
    try {
      byte[] blockHash = chainBaseManager.getRecentBlockStore().get(refBlockNumBytes).getData();
      if (!Arrays.equals(blockHash, refBlockHash)) {
        String str = String.format(
            "Tapos failed, different block hash, %s, %s , recent block %s, "
                + "solid block %s head block %s",
            ByteArray.toLong(refBlockNumBytes), Hex.toHexString(refBlockHash),
            Hex.toHexString(blockHash),
            chainBaseManager.getSolidBlockId().getString(),
            chainBaseManager.getHeadBlockId().getString());
        throw new TaposException(str);
      }

      String str = String

              chainBaseManager.getSolidBlockId().getString(),
