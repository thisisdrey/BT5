Based on my research, the closest concrete analog to the kernel `hci_dma_irq_handler` bug (an index/count that is not properly bounds-checked against the actually-allocated/validated data before being used to access an array) exists in Bazel's `singlejar` tool, which parses ZIP/JAR central-directory metadata that is fully attacker-controlled when a build consumes a third-party `.jar` file (e.g. served by an `http_jar`/`http_file`/`http_archive` dependency, a Maven artifact, or a jar produced on an untrusted CI branch).

### Title
Out-of-bounds read via unvalidated Zip64 attribute index / unchecked local-header pointer in `singlejar` CDH parsing - (File: `src/tools/singlejar/zip_headers.h`, `src/tools/singlejar/input_jar.h`)

### Summary
`singlejar` merges JAR files supplied as build inputs. When computing `CDH::local_header_offset()` for a Central Directory Header entry, the code derives an index (`attr_no`) from the 32-bit `uncompressed_file_size32`/`compressed_file_size32` "needs-extension" sentinels and uses it to index into the Zip64 extra field's `attr64()` array — without checking that index against `Zip64ExtraField::attr_count()`, which is derived independently from the extra field's own `payload_size`. This mirrors the kernel bug class: an index computed from one untrusted source is used against an array whose real bound comes from a different, unchecked source.

### Finding Description [1](#0-0) 
computes `attr_no` purely from the sentinel flags of `uncompressed_file_size32()`/`compressed_file_size32()` (both fully attacker-controlled 32-bit fields in the CDH) and then calls `z64->attr64(attr_no)`. [2](#0-1) 
shows `attr64(index)` performs no bounds check against `attr_count()` (`payload_size() / sizeof(uint64_t)`), which is set from the extra field's own (also attacker-controlled) `payload_size`. A crafted CDH can set `uncompressed_file_size32 = compressed_file_size32 = 0xFFFFFFFF` (forcing `attr_no = 2`) while supplying a Zip64 extra field whose `payload_size` only covers 0 or 1 64-bit attributes (or omitting attributes entirely), so `attr64(2)` reads 8 bytes beyond the region that was validated as belonging to that extra field.

This value then flows unchecked into `InputJar::LocalHeader()`: [3](#0-2) 
which computes `mapped_file_.address(cdh->local_header_offset() + preamble_size_)` and returns it directly as an `LH*` pointer with no validation that the address lies inside the mapped input jar, unlike the sibling `NextEntry()` path which does call `mapped_file_.mapped(new_cdr)` to validate the *next CDH* pointer: [4](#0-3) 

`NextEntry()` is invoked once per directory entry from `OutputJar::AddJar()` while merging every input jar into the output deploy jar: [5](#0-4) 

I was not able to inspect `MappedFile::address()`/`MappedFile::mapped()` in this session (not indexed/read), so I cannot fully confirm whether `address()` itself clamps or crashes on out-of-range offsets; this is a real gap in my verification.

### Impact Explanation
If the garbage/adjacent-memory value read via the unchecked `attr64()` index, or the raw `0xFFFFFFFF` sentinel returned when no Zip64 field is present at all, produces an offset outside the mapped jar, the subsequently returned `LH*` is dereferenced by callers (`lh->compressed_file_size()`, `lh->extra_fields()`, etc.) without any bounds check — an out-of-bounds read of process memory during a normal build step (`singlejar` deploy-jar construction), reachable purely from attacker-supplied JAR byte content. Depending on layout this manifests as a crash (build-time DoS, out of scope per rules) or, if the OOB read lands on mapped-but-unintended memory, an information disclosure / corrupted-length that further drives buffer-size computations later in `AppendToDirectoryBuffer` (`ReserveCdr(out_cdh_size)`), which is a memory-safety concern beyond simple DoS.

### Likelihood Explanation
`singlejar` runs on every `java_*` target that merges jars, and this parsing path executes for every Central Directory entry of every input jar with no signature/integrity check on the internal ZIP structure — a whole-file `sha256` pin on the JAR (as used by `http_jar`) only proves the file matches what the *publisher* served; it does nothing to validate the internal CDH/Zip64 structure, so a hostile origin can serve a hash-consistent-but-malicious jar directly. No sandboxing or containment mechanism inspects jar-internal structure before `singlejar` parses it.

### Recommendation
- In `CDH::local_header_offset()` (and the analogous `compressed_file_size()`), validate `attr_no < z64->attr_count()` before calling `attr64()`, and treat a mismatch as a corrupt-archive error (`diag_errx`), consistent with how `output_jar.cc`'s `AppendToDirectoryBuffer` already validates extra-field bounds (`src/tools/singlejar/output_jar.cc:936-940`).
- In `InputJar::LocalHeader()`, validate the resulting address with `mapped_file_.mapped(...)` before returning the `LH*`, mirroring the check already performed in `NextEntry()` for the next CDH pointer.

### Proof of Concept
A reproducible test would live alongside `src/tools/singlejar/input_jar_scan_entries_test.h`/`zip_headers_test.cc`: construct a minimal ZIP whose single CDH entry sets `uncompressed_file_size32 = compressed_file_size32 = 0xFFFFFFFF` and either (a) omits any Zip64 extra field, or (b) includes one with `payload_size` covering fewer than 3 `uint64` attributes, placed at the very end of the mapped file/buffer; then call `InputJar::Open()` + `NextEntry()` and observe the OOB read / invalid `LH*` dereference (e.g. under ASan) when the tool subsequently reads fields off the returned local-header pointer. I could not fully verify `MappedFile::address()`'s internal behavior in this session, so confirming whether this yields a hard crash vs. a silent OOB read would require running such a test with AddressSanitizer.
