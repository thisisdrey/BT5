### Title
Attacker can saturate a victim's per-account token set via dust `DepositToken` transfers, blocking the victim from using new collateral types and from receiving further deposit/debt tokens - (File: contracts/Pool.sol)

### Summary
This is the Metronome analog of the Knox `_redeemMax` griefing vector. Instead of an unbounded epoch loop, Metronome keeps a per-account enumerable set of held tokens (`depositTokensOfAccount`, `debtTokensOfAccount`) capped at `MAX_TOKENS_PER_USER = 30`. Because `DepositToken` shares are freely transferable and the token contract calls `Pool.addToDepositTokensOfAccount` whenever a recipient's balance goes from `0` to non-zero, an attacker can push dust shares of every listed deposit token to a victim, filling the victim's set to the cap. From then on, every operation that would add a *new* token to the victim's set reverts with `UserReachedMaxTokens`.

### Finding Description
`Pool` maintains two `MappedEnumerableSet.AddressSet` structures per account — `depositTokensOfAccount` and `debtTokensOfAccount` (`contracts/storage/PoolStorage.sol`). Both `addToDebtTokensOfAccount` and `addToDepositTokensOfAccount` are gated by `onlyIfAdditionWillNotReachMaxTokens`, which reverts when `debtTokensOfAccount.length(account_) + depositTokensOfAccount.length(account_) >= MAX_TOKENS_PER_USER` (`contracts/Pool.sol` L143-148). These functions are invoked by `DebtToken`/`DepositToken` whenever an account's balance transitions from zero to positive (i.e., on deposits, mints, issues, seizures, and plain ERC-20 `transfer`s to a fresh holder) — see the NatSpec at L199-220.

Attack path:

1. Attacker deposits a dust amount of underlying into each of the pool's deposit tokens (the pool itself is capped at 30 deposit tokens via `addDepositToken`'s `ReachedMaxDepositTokens` check, so there are at most 30 distinct tokens to seed).
2. Attacker calls `depositToken.transfer(victim, 1 wei)` for each deposit token. Each transfer triggers `Pool.addToDepositTokensOfAccount(victim)`, which succeeds while the victim's combined list length is `< 30`.
3. Once the victim's combined `depositTokensOfAccount + debtTokensOfAccount` length reaches 30:
   - The victim cannot deposit into any collateral type they don't already hold — the resulting mint calls `addToDepositTokensOfAccount` and reverts.
   - The victim cannot mint/issue a synthetic whose debt token they don't already hold — `addToDebtTokensOfAccount` reverts.
   - Any inbound `DepositToken` transfer of a token the victim doesn't already hold reverts.
4. Recovery requires the victim to fully zero out dust positions (transfer them out so `removeFromDepositTokensOfAccount` fires), paying gas per token — and the attacker can top the set back up cheaply with another dust transfer, since removing is O(1) but re-adding is also a single cheap call for the attacker.

The same set feeds `debtOf`/`depositOf`/`debtPositionOf`, but those loops are hard-bounded at 30 iterations, so this is not an unbounded-loop/gas DoS — the vulnerability is the *set-capacity exhaustion* and forced revert on all new-token entry points, matching the Knox bug class ("block other users by transferring tokens to victim") mapped to "Account list / freeze griefing" on this codebase.

### Impact Explanation
- **Liveness / temporary freezing of position functionality:** the victim is locked out of opening positions with any new collateral or new synthetic debt token until they manually eject the dust tokens, which costs them gas per token. During that window the victim cannot increase collateralization with a different asset even if their position is drifting toward liquidation — they can only add to collateral types already in their set.
- **Blocked inbound value:** anyone (including `DepositToken.seize` paying out a liquidator, or a treasury/OTC transfer) sending the victim a deposit token they don't already hold will revert, since the balance transition `0 → >0` calls `addToDepositTokensOfAccount`.
- The attack is cheap and repeatable: one dust deposit per collateral type plus one `transfer` per victim. It does not require the victim's cooperation and works entirely through public entry points.
- Modifiers don't stop it: `addToDepositTokensOfAccount` has no pause check on the add path for transfers (transfers are a token-level operation, not a `whenNotShutdown` pool function), `MAX_TOKENS_PER_USER` is a hard cap the attacker exploits rather than a mitigation, and nothing restricts `DepositToken.transfer` to willing recipients — matching the original report's recommendation that unsolicited transfers are the vector.

### Likelihood Explanation
- Requires only an EOA with enough underlying to make dust deposits in each supported collateral — no privileged role, oracle manipulation, or governance interaction.
- Cost scales with the number of listed deposit tokens (≤30) times one `deposit` + one `transfer`.
- The victim's own transactions (deposit into a new collateral, issue a new synthetic, receiving a transfer) deterministically revert once the set is full; the attack is not probabilistic.
- Mitigating factors that keep it below Critical/High: the victim's *existing* funds are not frozen — withdrawals of already-held collateral and repayment of already-held debt still succeed (they only remove set entries), so this is a temporary functional freeze/griefing attack rather than theft or permanent lockup, consistent with the source report's Medium severity.

### Recommendation
- Allow accounts to remove themselves from a token set permissionlessly: e.g., a `Pool` function `exitToken(IDepositToken)` callable by the account that burns/transfers their residual dust and calls `removeFromDepositTokensOfAccount`, so victims aren't forced to find a recipient willing to accept dust.
- Alternatively, only add an account to the set when balance crosses a non-trivial threshold (e.g., > some wei or a USD-denominated floor), making dust seeding ineffective.
- Or make `addToXTokensOfAccount` failure non-fatal for inbound transfers (skip the add and let the set be slightly stale, reconciling lazily inside `depositOf`/`debtOf` by checking `balanceOf > 0`), though this complicates the accounting invariant.
- At minimum, cap combined deposit+debt tokens per account with headroom (e.g., split the limit or raise it) and document the griefing vector.

### Proof of Concept
Reproducible in the repo's Hardhat setup (`test/Pool.test.ts` already wires `Pool`, `DepositToken`, `DebtToken`, `MasterOracle` mocks). Sketch:

```typescript
// contracts/Pool.sol :: onlyIfAdditionWillNotReachMaxTokens reverts at >= 30
const pool: Pool = ...           // deployed Pool with N deposit tokens added by governor
const depositTokens: DepositToken[] = [...] // all pool deposit tokens
const [alice, bob] = await ethers.getSigners() // alice = attacker, bob = victim

// 1) Alice seeds a dust balance in every deposit token
for (const dt of depositTokens) {
  await dt.connect(alice).deposit(1)           // mints 1 wei share to alice
}

// 2) Alice transfers dust of every token to Bob
for (const dt of depositTokens) {
  await dt.connect(alice).transfer(bob.address, 1) // adds bob to depositTokensOfAccount
}

// Bob's combined set is now at MAX_TOKENS_PER_USER (assuming >= 30 tokens
// or topping up with whatever remains after bob's own holdings)
expect(await pool.getDepositTokensOfAccount(bob.address)).to.have.lengthOf(30)

// 3) Bob tries to deposit into a collateral type he doesn't hold -> reverts
const newDepositToken = depositTokens[0] // or any token not in bob's set pre-attack
await expect(
  newDepositToken.connect(bob).deposit(parseEther('100'))
).to.be.revertedWith('UserReachedMaxTokens')

// 4) Any inbound transfer of a token bob doesn't hold also reverts
await expect(
  depositTokens[0].connect(alice).transfer(bob.address, 1)
).to.be.revertedWith('UserReachedMaxTokens') // if it would push past the cap

// 5) Bob must spend gas ejecting each dust token to recover
for (const dt of depositTokens) {
  await dt.connect(bob).transfer(alice.address, 1) // balance -> 0, removeFromDepositTokensOfAccount fires
}
```

Note: I did not read `DepositToken.sol`/`DebtToken.sol` internals in this pass, so the exact hook (`_transfer`/`_mint` calling `pool.addToDepositTokensOfAccount`) is inferred from the NatSpec at `contracts/Pool.sol` L199-220 and the `SenderIsNotDepositToken`/`SenderIsNotDebtToken` guards — this should be confirmed against `contracts/DepositToken.sol` when writing the final PoC, but the revert path through `onlyIfAdditionWillNotReachMaxTokens` is directly visible in `Pool.sol`.
