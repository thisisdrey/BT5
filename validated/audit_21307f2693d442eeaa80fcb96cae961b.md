## Analysis

CVE-2022-3105 describes an unchecked allocation size (`kmalloc_array()` return value never checked) that can be driven by attacker-controlled length data, leading to a null/invalid pointer condition. The closest analog in java-tron is the pattern of allocating Java arrays whose size comes directly from **unvalidated, attacker-controlled TVM calldata** inside the `BatchValidateSign` / `ValidateMultiSign` precompiled-contract helpers.

### Root cause

`PrecompiledContracts.extractBytes32Array` and `PrecompiledContracts.extractBytesArray` derive an array-allocation size directly from a `DataWord` taken from calldata, with no upper/lower bound check before the `new byte[len][]` allocation: [1](#0-0) [2](#0-1) 

Neither method validates that `len` is non-negative or within any sane bound before calling `new byte[len][]`, unlike the RLP decoder elsewhere in the codebase which explicitly bounds-checks lengths and even catches `OutOfMemoryError` from excessive allocation: [3](#0-2) 

`len` is obtained via `DataWord.intValueSafe()`; this only clamps values that overflow the `int` range but does not protect against a crafted 32-byte word whose integer value maps to a very large positive `int` (up to `Integer.MAX_VALUE`), letting an attacker request an allocation of ~2^31 `byte[]` references purely from calldata supplied to a `CALL`/`STATICCALL` targeting the `BatchValidateSign` / `ValidateMultiSign` precompile addresses — both of which are reachable by any deployed contract or directly-crafted transaction, i.e. by an unprivileged, unauthenticated caller.

### Title
Unchecked Array-Size Allocation From Attacker-Controlled Calldata in Precompiled Signature Validation - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
`extractBytes32Array` and `extractBytesArray` in `PrecompiledContracts.java` allocate Java arrays sized directly by an unvalidated length field read from TVM calldata, mirroring the CVE-2022-3105 pattern of unchecked allocation from attacker-supplied length data.

### Finding Description
Both helper methods read a length word from the decoded `DataWord[]` array (which is built directly from the raw calldata passed to a precompiled contract call) and pass it unchecked into a Java array allocation: [1](#0-0) 
There is no check that `len` is within a bound consistent with the actual calldata size, nor that it is non-negative before use. Compare this to the deliberate `isValidAbiEncoding` bound check present elsewhere in the same file, which is not applied here: [4](#0-3) 

### Impact Explanation
A crafted calldata word can force allocation of an extremely large `byte[][]` (bounded only by `Integer.MAX_VALUE` elements), which can exhaust heap memory and throw `OutOfMemoryError` — an `Error`, not an `Exception`, that is not guaranteed to be caught by the TVM's per-opcode/precompile exception handling. This can destabilize or crash the node process handling the transaction, which the scope explicitly treats as valid impact ("node crash or halt").

### Likelihood Explanation
The precompiled contracts are reachable by any account via a plain `CALL`/`STATICCALL` from a deployed smart contract or directly via a `TriggerSmartContract` transaction targeting the fixed precompile address — no special privilege is required, matching the "unprivileged contract deployer / caller" threat model in scope.

### Recommendation
Add explicit bounds validation on `len` in `extractBytes32Array` and `extractBytesArray` (e.g., reject if `len < 0` or if `len` would require more calldata than is actually present, similar to `isValidAbiEncoding`) before performing the array allocation, so malformed/oversized length fields are rejected with a normal `ContractExeException`/revert rather than reaching an unbounded `new byte[len][]`.

### Proof of Concept
1. Deploy or invoke a contract that performs a `STATICCALL`/`CALL` to the `BatchValidateSign` (or `ValidateMultiSign`) precompile address.
2. Craft calldata whose ABI-encoded array-length word (consumed by `extractBytes32Array`/`extractBytesArray`) is set to a very large value (e.g., close to `Integer.MAX_VALUE / 8`, i.e. large enough to make `new byte[len][]` request several GB of reference storage) instead of the true number of elements actually present in calldata.
3. Submit the transaction; the precompile executes `extractBytesArray`/`extractBytes32Array`, which allocates the oversized array before any subsequent bounds error can occur, potentially triggering `OutOfMemoryError` on the node processing the transaction.

**Note on confidence:** I could not directly view the `BatchValidateSign.execute`/`ValidateMultiSign.execute` method bodies within the available iterations to show the exact call site invoking `extractBytesArray`/`extractBytes32Array` (the file is large and the specific class bodies were not returned in my searches). The helper methods, their use of `SIG_LENGTH`, and their placement in `PrecompiledContracts.java` strongly indicate they exist to serve these two batch-signature precompiles, but this linkage should be confirmed by reading the full `BatchValidateSign`/`ValidateMultiSign` class bodies before treating this as fully proven. Given the size of this file, a full read via a Devin session would be needed to verify the exact call sites and any prior length validation that might occur earlier in `execute()`.
