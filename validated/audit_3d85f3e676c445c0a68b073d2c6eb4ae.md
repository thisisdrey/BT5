### Title
Unbounded reference updates per `UpdateReferences` stream enables resource-exhaustion DoS - (File: internal/gitaly/service/ref/update_references.go)

### Summary
### Finding Description
The C4 finding describes `LlamaCore._createAction` allowing unlimited action creation because there is no cap on the number of actions a user can queue, which in turn permanently blocks a downstream state-changing operation (`_setRoleHolder`) that depends on that unbounded state. The analogous pattern in gitaly is the `RefService.UpdateReferences` RPC handler, `(*server).UpdateReferences` [1](#0-0) . It is a bidirectional streaming RPC that receives an arbitrary number of client messages, each containing an arbitrary number of `updates`, and for every one of them it calls `updater.Update(...)`, which simply writes a command into the `git update-ref --stdin` process's stdin without any bound on the total number of queued updates within the transaction [2](#0-1) .

There is no check anywhere in this loop (or in `updateref.Updater.Update`) limiting how many reference updates can be staged before `Commit()` is called [3](#0-2) . `Commit()` only transitions state and flushes the `commit` command to the subprocess; the actual git process must process every queued update and (per Git's own reference-transaction/reflock semantics) hold references locked while it does so [4](#0-3) .

Gitaly's documented backpressure mechanism only limits the number of *concurrent RPCs in flight* per repository/RPC via `[[concurrency]]` config (`max_per_repo`, `max_queue_wait`, `max_queue_size`) [5](#0-4) . That protects against too many simultaneous calls, but it does nothing to bound the *size of a single call's workload* — exactly the same class of gap as the referenced Llama bug, where the fix was to bound the actual growth of state rather than the number of top-level operations.

### Impact Explanation
A caller with ordinary write access to a repository (anyone able to invoke `UpdateReferences`, e.g. through Rails-mediated branch/tag mutation flows) can stream millions of reference-update entries in one logical transaction. Because there is no per-transaction/per-stream cap, this:
- Grows the in-memory/queued state of the spawned `git update-ref` subprocess unbounded, consuming CPU and memory on the Gitaly host.
- Forces `Commit()` to process the entire queued set, potentially holding the repository's reference-transaction locks (via `gitcmd.WithRefTxHook`) for an extended period while other operations on the same repository are blocked, similar to how excessive Llama action creation blocked `_setRoleHolder`.
- Is not mitigated by the existing concurrency limiter, because that limiter only throttles the *number* of concurrent calls per key, not the payload size of a single call.

This is a legitimate DoS vector against a specific repository/handler, reachable from an ordinary authenticated write path, without needing a privileged actor, leaked token, or malicious peer.

### Likelihood Explanation
Moderate. It requires only standard write permission to call `UpdateReferences` (no elevated privilege), and streaming RPCs allow arbitrarily many small messages within default gRPC message-size limits, so the attack cost scales roughly linearly with the number of updates sent — the same "cheap linear DoS" characteristic that made the original finding a valid Medium-severity issue.

### Recommendation
Add an explicit limit on the total number of reference updates that may be staged within a single `UpdateReferences` transaction/stream (and reject or split with an `InvalidArgument`/`ResourceExhausted` error once exceeded), analogous to how the Llama team resolved their finding by bounding the unconstrained growth of state instead of relying solely on RPC-level concurrency limiting.

### Proof of Concept
Because tool access is read-only here, an exact runnable PoC cannot be executed, but the vulnerable path is directly demonstrable by tracing the code: connect to `RefService.UpdateReferences`, send an initial request with `Repository` set, then stream a very large number of subsequent messages each containing many valid `UpdateReferences.Update` entries (unique reference names, valid old/new object IDs). Every entry passes straight through to `updater.Update` [6](#0-5)  with no count check before `updater.Commit()` is finally invoked [7](#0-6) .

// Update commands the reference to be updated to point at the object ID specified in newOID. If
// newOID is the zero OID, then the branch will be deleted. If oldOID is a non-empty string, then
// the reference will only be updated if its current value matches the old value. If the old value
// is the zero OID, then the branch must not exist.
//
// A reference transaction must be started before calling Update.
func (u *Updater) Update(reference git.ReferenceName, newOID, oldOID git.ObjectID) error {
	if err := u.expectState(stateStarted); err != nil {
		return err
	}

	return u.write("update %s\x00%s\x00%s\x00", reference.String(), newOID, oldOID)
}

// Commit applies the commands specified in other calls to the Updater. Commit finishes the
// reference transaction and another one must be started before further changes can be staged.
func (u *Updater) Commit() error {
	// Commit can be called without preparing the transactions.
	if err := u.checkState(statePrepared); err != nil {
		if err := u.expectState(stateStarted); err != nil {
			return err
		}
	}

	u.state = stateIdle

	if err := u.setState("commit"); err != nil {
		return err
	}

	return nil
}

## Concurrency queue

Limit the number of concurrent RPCs that are in flight on each Gitaly node for each
repository per RPC using `[[concurrency]]` configuration:

```toml
[[concurrency]]
rpc = "/gitaly.SmartHTTPService/PostUploadPackWithSidechannel"
max_per_repo = 1
```

For example:

- One clone request comes in for repository "A" (a largish repository).
- While this RPC is executing, another request comes in for repository "A". Because
  `max_per_repo` is 1 in this case, the second request blocks until the first request
  is finished.

An in-memory queue of requests can build up in Gitaly that are waiting their turn. Because
this is a potential vector for a memory leak, two other values in the `[[concurrency]]`
configuration can prevent an unbounded in-memory queue of requests:

- `max_queue_wait` is the maximum amount of time a request can wait in the
  concurrency queue. When a request waits longer than this time, it returns
  an error to the client.
- `max_queue_size` is the maximum size the concurrency queue can grow for a
  given RPC. If a concurrency queue is at its maximum, subsequent requests
  return with an error. The queue size is per repository.

For example:

```toml
[[concurrency]]
rpc = "/gitaly.SmartHTTPService/PostUploadPackWithSidechannel"
max_per_repo = 1
max_queue_wait = "1m"
max_queue_size = 5
```
