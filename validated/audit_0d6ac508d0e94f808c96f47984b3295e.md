### Title
Unbounded value minting via `subsidized_amount` skip-deduct path in `promise_batch_action_function_call_weight` - ([File: runtime/near-vm-runner/src/logic/logic.rs])

### Finding Description
`promise_batch_action_function_call_weight` contains a `skip_deduct` branch that bypasses the normal balance deduction whenever `amount == 1 yoctoNEAR`, the `one_yocto_on_promise` config flag is enabled, and `current_account_balance` is zero: [1](#0-0) 

In the normal (non-skip) path, `deduct_balance(amount)` removes real balance from the calling contract's account before the `amount` is attached as a deposit to the outgoing `FunctionCall` action via `append_action_function_call_weight`. In the `skip_deduct` branch, no balance is removed from the caller, yet the same `amount` (1 yoctoNEAR) is still passed unchanged into `append_action_function_call_weight` and therefore still becomes part of the deposit carried by the outgoing receipt: [2](#0-1) 

The only bookkeeping performed for the skipped deduction is an unconditional accumulation into `result_state.subsidized_amount` via `checked_add`, with no per-call or per-receipt cap on how many times this can be repeated within a single function call (limited only by gas/action-count metering, not by a monetary bound): [3](#0-2) 

Because an attacker fully controls their own contract's wasm, and can trivially arrange for `current_account_balance` to be exactly zero (i.e., don't fund it beyond storage stake) while issuing `promise_batch_create` + `promise_batch_action_function_call_weight(amount_ptr -> 1)` in a loop, they can generate an arbitrary number of receipts—each carrying a real 1 yoctoNEAR deposit—without ever having that value deducted from their own account. Each such receipt, once applied at the receiving shard, will credit the receiver with that deposit exactly as if it were funded, which is the value-conservation violation described in the question.

I could not fully verify, within the scope of this investigation, whether `runtime/runtime/src/lib.rs` (which references `subsidized_amount` 10 times) reconciles this accumulated value against some other ledger entry (e.g., burning an equivalent amount elsewhere, capping the subsidy centrally, or excluding these 1-yocto deposits from total-supply accounting). That reconciliation logic in `runtime/runtime/src/lib.rs` and `runtime/runtime/src/function_call.rs` is the remaining piece needed to determine whether the emitted receipts truly represent new, unbacked value or whether the protocol treats this subsidy as an explicitly allowed, non-inflationary gas-refund-like mechanism.

### Impact Explanation
If the accumulated `subsidized_amount` is not fully reconciled/burned/capped by the runtime layer, each skipped-deduction call mints 1 yoctoNEAR of receipt deposit that is not backed by any real balance decrease, which is a token-inflation / value-conservation bug (NEAR bounty category: token minting / total-supply integrity). Given `ft_transfer_call`-style patterns often check only "is deposit == 1 yoctoNEAR" as an authorization signal rather than treating it as a real value transfer, downstream contracts crediting user balances based on this deposit could compound the impact, though the per-call unit value (1 yoctoNEAR) is minuscule.

### Likelihood Explanation
The attacker only needs an unprivileged account with zero extra balance (trivial to arrange, e.g., an account created with exactly the minimum storage stake) and a self-deployed contract that loops `promise_batch_create` + `promise_batch_action_function_call_weight(amount=1)`. The main throttle is gas/action-count limits per function call and per receipt, not any monetary cap, so the attack is repeatable across many transactions/blocks at negligible cost (only gas fees, which are burnt regardless).

### Recommendation
- Cap `subsidized_amount` per call/per receipt or eliminate the unconditional `skip_deduct` bypass; require that the runtime, when applying receipts, deduct/burn an amount equal to the accumulated `subsidized_amount` from a protocol-controlled source (or refuse to attach the deposit at all) so that no value is created out of nothing.
- Audit `runtime/runtime/src/lib.rs` and `runtime/runtime/src/function_call.rs` to confirm exactly how `subsidized_amount` is consumed after being returned from `logic.rs`, and add an explicit invariant/assertion that total supply is unchanged when this path is exercised.
- Add a protocol-level total-supply conservation check in the runtime apply loop that fails (or is enforced by tests) whenever `sum(receipt deposits) - subsidized_amount != actual balance deducted from sender`.

### Proof of Concept
1. Deploy a contract whose account balance is reduced to exactly its minimum storage-stake requirement (zero spendable balance).
2. In one function call, loop N times: `promise_batch_create(receiver)` then `promise_batch_action_function_call_weight(promise_idx, method, args, amount_ptr -> 1, gas, weight)`.
3. Execute the transaction; capture: (a) sender account balance before/after, (b) `result_state.subsidized_amount`, (c) the deposit amounts recorded in the N generated `FunctionCall` actions/receipts, and (d) chain total supply before/after receipt processing (via `runtime/runtime/src/tests/apply.rs` style integration test).
4. Assert: `sender_balance_before - sender_balance_after == sum(receipt deposits)`. If this assertion fails (i.e., sender balance is unchanged while `sum(receipt deposits) == N` yoctoNEAR), and total supply increased by `N` yoctoNEAR without any correlated burn, the minting bug is confirmed.
5. Cross-check `subsidized_amount`'s consumption in `runtime/runtime/src/lib.rs`/`function_call.rs` to see if it is ever subtracted from total supply or capped; if not, the PoC demonstrates unbacked value creation matching the described invariant violation.
