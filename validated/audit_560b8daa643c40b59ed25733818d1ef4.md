### Title
Reward distribution computation silently truncates via unchecked `BigInteger.longValue()` instead of using overflow-checked arithmetic - ([File: chainbase/src/main/java/org/tron/core/service/MortgageService.java])

### Summary
The witness/voter reward-distribution logic computes each voter's share using the accumulated "virtual index" (`Vi`) mechanism stored as `BigInteger`, then converts the final result to a `long` with the unchecked `BigInteger.longValue()` call, which silently truncates to the low 64 bits instead of throwing on overflow (as `longValueExact()` would, or as `LongMath.checkedAdd/checkedMultiply` do elsewhere in the same codebase). This mirrors the reported Synthetix bug class: a reward-distribution multiplication result is stored/converted into a narrower integer type than the arithmetic actually requires, causing silent value corruption when the true result exceeds the narrower type's range.

### Finding Description
The core computation appears identically in three places that all feed the same `DelegationStore`/`RewardViStore` accumulated `Vi` values into the same truncating conversion: [1](#0-0) [2](#0-1) [3](#0-2) 

All three do:
```java
reward += deltaVi.multiply(BigInteger.valueOf(userVote))
    .divide(DelegationStore.DECIMAL_OF_VI_REWARD).longValue();
```
`deltaVi` is an unbounded, ever-accumulating `BigInteger` per witness, stored via `DelegationStore.setWitnessVi`/`RewardViStore` [4](#0-3) . It grows every cycle a witness earns block/standby rewards without any voter withdrawing, since `deltaVi` is `endVi - beginVi` and `Vi` values are cumulative across all past cycles. `BigInteger.longValue()` does not check range — if `deltaVi * userVote / DECIMAL_OF_VI_REWARD` exceeds `Long.MAX_VALUE`/`Long.MIN_VALUE`, the value silently wraps (two's-complement truncation) into an arbitrary, potentially negative, `long`.

This truncation is asymmetric with the rest of the reward-payment code path, which explicitly guards against overflow using `LongMath.checkedAdd` (e.g. `WithdrawRewardProcessor.execute` and `VoteWitnessProcessor.execute`) [5](#0-4)  — showing the developers were aware overflow-safety was needed for these values but missed it at the actual reward-conversion step.

### Impact Explanation
If the truncated `reward` becomes negative or a small/garbage positive value, `adjustAllowance` silently drops any non-positive amount [6](#0-5) , meaning legitimately earned rewards for that cycle range are permanently lost to the voter with no error surfaced — a silent freezing/loss of funds for any account that voted for the affected witness. Because `Vi` accumulates monotonically forever for a witness once it starts earning rewards, this is a systemic time-bomb affecting every voter delegated to a long-lived, high-reward witness, not just the caller — reachable purely by normal `VoteWitnessContract`/`WithdrawBalanceContract`/TVM `vote`/`withdrawreward` calls that any account can broadcast.

### Likelihood Explanation
Triggering this requires `deltaVi * userVote` to exceed `Long.MAX_VALUE * DECIMAL_OF_VI_REWARD` (i.e., `Vi` scaled by `10^18`), which in practice requires very long-lived, high-vote/high-reward witnesses and a very large accumulated `Vi` before a voter withdraws. This makes exploitation a matter of chain longevity/witness reward accumulation rather than a single attacker-controlled transaction, so likelihood is lower than a directly attacker-triggerable bug, but the code path is unconditionally reachable by any voter and the resulting corruption/loss is silent and undetected by any check in the current code.

### Recommendation
Replace `BigInteger.longValue()` with `BigInteger.longValueExact()` (or an explicit range check) in `MortgageService.computeReward`, `VoteRewardUtil.computeReward`, and `RewardViCalService.getNewRewardAlgorithmReward`, and surface the resulting `ArithmeticException` as a `ContractExeException`/error so any potential overflow is detected and rejected rather than silently truncated, consistent with the `LongMath.checkedAdd` pattern already used in nearby withdraw code.

### Proof of Concept
Conceptual: A witness accumulates `Vi` (BigInteger) every cycle proportional to `reward * 10^18 / totalVoteCount` without bound as long as no voter withdraws. Once accumulated `deltaVi` for a long-lived, high-reward witness grows large enough that `deltaVi.multiply(userVote).divide(10^18)` exceeds `Long.MAX_VALUE`, any voter calling `WithdrawBalanceContract`, `VoteWitnessContract`, or the TVM `withdrawreward`/`vote` opcodes triggers `computeReward`, whose `.longValue()` call silently wraps the true (unbounded) reward amount into a corrupted/negative `long`, which is then either credited incorrectly or dropped entirely by the `amount <= 0` guard in `adjustAllowance`.

  public void accumulateWitnessVi(long cycle, byte[] address, long voteCount) {
    BigInteger preVi = getWitnessVi(cycle - 1, address);
    long reward = getReward(cycle, address);
    if (reward == 0 || voteCount == 0) { // Just forward pre vi
      if (!BigInteger.ZERO.equals(preVi)) { // Zero vi will not be record
        setWitnessVi(cycle, address, preVi);
      }
    } else { // Accumulate delta vi
      BigInteger deltaVi = BigInteger.valueOf(reward)
          .multiply(DECIMAL_OF_VI_REWARD)
          .divide(BigInteger.valueOf(voteCount));
      setWitnessVi(cycle, address, preVi.add(deltaVi));
    }
  }
