### Title
Active-permission holders can be granted authority to overwrite Owner/Witness permissions, enabling full account takeover - (File: `actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java`)

### Summary
`AccountPermissionUpdateContract` is authorized like any other contract type: whichever permission ID signs the transaction is checked only against that permission's own threshold and its 32-byte `operations` bitmap of allowed contract types, exactly like TRC-20 transfers, TVM calls, etc. Nothing in the validation logic special-cases `AccountPermissionUpdateContract` to require the `Owner` permission. If an `Active` permission is ever configured (by the account owner, a wallet UI default, or a delegation tool) to include `AccountPermissionUpdateContract` in its allowed-operations bitmap, any key that satisfies that `Active` permission's (possibly much lower) threshold can call `AccountPermissionUpdateContract` and unconditionally rewrite the account's `Owner`, `Witness`, and all `Active` permissions in `execute()`, completely displacing the original owner's keys.

### Finding Description
Authorization for any contract, including `AccountPermissionUpdateContract`, is performed generically:
- `TransactionCapsule.validateSignature` looks up the permission by `permissionId` from the contract and calls `checkPermission`, which — for non-zero (i.e., non-default-owner) permission IDs — only verifies `permission.getType() == Active` and that the contract type bit is set in that permission's `operations` bitmap via `checkPermissionOperations`. [1](#0-0) [2](#0-1) 

- The threshold check (`checkWeight`) is only evaluated against that same `Active` permission, not against the `Owner` permission being modified. [3](#0-2) 

- When `AccountPermissionUpdateActuator.validate()` constructs a new `Active` permission's `operations` bitmap, it only checks that each set bit corresponds to *some* valid `ContractType` known to `DynamicPropertiesStore.getAvailableContractType()` — it does not exclude `AccountPermissionUpdateContract` from being assignable to an `Active` permission. [4](#0-3) 

- `execute()` then unconditionally overwrites the account's `Owner`, `Witness`, and `Active` permissions with whatever is in the new contract, with no check that the signer used the `Owner` permission or that the previous owner's key remains present: [5](#0-4) 

This mirrors the CVE-2024-37293 pattern: a component (here, the `Active` permission holder) is granted a broad, unrestricted capability (`sts:AssumeRole`-equivalent = "can send `AccountPermissionUpdateContract`") without any structural limitation preventing it from being used to seize the account's top-level (`Owner`) authority — the elevated resource it should never be able to reach on its own.

### Impact Explanation
If any `Active` permission on an account is configured to allow `AccountPermissionUpdateContract` (whether intentionally by a multisig/custody scheme delegating "admin" duties to a lower-weight key, by a buggy wallet/tooling default, or by a compromised low-privilege co-signer), that key alone (meeting only the `Active` permission's threshold, which can be as low as 1) can submit a transaction that replaces the `Owner` permission entirely, removing the legitimate owner's keys. This is a permanent, unauthorized takeover of the account and all its TRX/TRC10/TRC20 assets and delegated resources — satisfying "unauthorized account operation" / "theft or permanent freezing of funds."

### Likelihood Explanation
Exploitation requires only a signed `AccountPermissionUpdateContract` transaction meeting the threshold of an `Active` permission that already includes this operation bit — no special validator/witness/network position is needed, and the actuator/authorization path is reachable by any single broadcaster. The main precondition is that some `Active` permission actually carries this operation bit, which is a configuration decision left entirely to account owners/tooling with no protocol-level guardrail preventing it, making this a design gap rather than a one-off implementation bug, comparable to ADF's design flaw of not scoping the `sts:AssumeRole` permission.

### Recommendation
Disallow `AccountPermissionUpdateContract` (and any other permission-management contract types) from ever being set in the `operations` bitmap of a non-`Owner` permission during `checkPermission`, and/or require that any `AccountPermissionUpdateContract` transaction be authorized specifically via `permissionId == 0` (the `Owner` permission) regardless of bitmap contents, similar to how ADF v4.0.0 restricted the bootstrap role's `sts:AssumeRole` scope.

### Proof of Concept
1. Owner creates an `Active` permission (id 2, threshold 1) for a delegated "operator" key, and includes bit corresponding to `AccountPermissionUpdateContract` in its 32-byte `operations` field (allowed today because `checkPermission` only validates the bit against `getAvailableContractType()`, not against a denylist). [6](#0-5) 
2. Operator key builds a new `AccountPermissionUpdateContract` with `permissionId = 2`, setting `Owner` permission to a single key of its own choosing, and signs it once with the operator key (satisfying threshold 1 of permission id 2).
3. `TransactionCapsule.validateSignature`/`checkPermission` authorize the transaction because the operator's `Active` permission allows this contract type and its threshold is met. [7](#0-6) 
4. `AccountPermissionUpdateActuator.execute()` overwrites the account's `Owner` permission with the attacker-controlled key, unconditionally. [8](#0-7) 
5. The original owner is permanently locked out; the attacker now fully controls the account.

  public static boolean validateSignature(Transaction transaction,
      byte[] hash, AccountStore accountStore, DynamicPropertiesStore dynamicPropertiesStore)
      throws PermissionException, SignatureException, SignatureFormatException {
    Transaction.Contract contract = transaction.getRawData().getContractList().get(0);
    int permissionId = contract.getPermissionId();
    byte[] owner = getOwner(contract);
    AccountCapsule account = accountStore.get(owner);
    Permission permission = null;
    if (account == null) {
      if (permissionId == 0) {
        permission = AccountCapsule.getDefaultPermission(ByteString.copyFrom(owner));
      }
      if (permissionId == 2) {
        permission = AccountCapsule
            .createDefaultActivePermission(ByteString.copyFrom(owner), dynamicPropertiesStore);
      }
    } else {
      permission = account.getPermissionById(permissionId);
    }
    if (permission == null) {
      throw new PermissionException("permission isn't exit");
    }
    checkPermission(permissionId, permission, contract);
    long weight = checkWeight(permission, transaction.getSignatureList(), hash, null);
    if (weight >= permission.getThreshold()) {
      return true;
    }
    return false;
  }
