### Title
Dust transfers of deposit tokens fill a victim's `MAX_TOKENS_PER_USER` slots, blocking new collateral deposits and debt positions — (File: contracts/Pool.sol)

### Summary
`Pool` tracks each account's held deposit tokens and debt tokens in two `MappedEnumerableSet.AddressSet` lists (`depositTokensOfAccount`, `debtTokensOfAccount`) and enforces a shared cap of `MAX_TOKENS_PER_USER = 30` via the `onlyIfAdditionWillNotReachMaxTokens` modifier, which reverts with `UserReachedMaxTokens` when `debtTokensOfAccount.length + depositTokensOfAccount.length >= 30` (`contracts/Pool.sol:79`, `contracts/Pool.sol:143-148`). The lists are append-only on the receiving side: any time an account's `DepositToken` balance goes from zero to non-zero — via `deposit` (with an attacker-chosen `onBehalfOf_`), `transfer`, `transferFrom`, or liquidation `seize` — `DepositToken` calls `pool.addToDepositTokensOfAccount(recipient)` (`contracts/DepositToken.sol:486-488`, `contracts/DepositToken.sol:517-520`). An unprivileged attacker can therefore force entries into a victim's per-account set without the victim's consent, exactly like the OpenQ "limit blocks all further additions" bug class: once the cap is hit, every action that would add a *new* token to the victim's set reverts, even though the victim never opted into the filler entries.

### Finding Description
Attack path:

1. The attacker deposits dust amounts of each registered collateral through `DepositToken.deposit(dust, victim)` — `deposit` takes an arbitrary `onBehalfOf_` beneficiary and mints to it (`contracts/DepositToken.sol:211-237`), or simply `transfer(victim, dust)` after depositing to itself (`contracts/DepositToken.sol:348-354`).
2. Each first-time receipt pushes the deposit token into `depositTokensOfAccount[victim]`. The attacker repeats until the victim's combined deposit + debt token count reaches 30.
3. From then on:
   - Any `deposit(..., onBehalfOf_=victim)` of a collateral the victim does not yet hold reverts in `_mint → pool.addToDepositTokensOfAccount` with `UserReachedMaxTokens`.
   - Any `transfer`/`transferFrom`/`seize` of a new deposit token to the victim reverts — this also **breaks liquidations** where `Pool.liquidate` seizes a collateral type the victim doesn't already hold into the liquidator/victim accounting path, and blocks `SmartFarmingManager.leverage` flows that mint a fresh deposit token to the account.
   - If the victim's debt entries plus attacker-forced deposit entries sum to 30, the victim cannot issue debt in a *new* synthetic (`DebtToken.issue/mint → pool.addToDebtTokensOfAccount` uses the same capped path), and — critically — cannot deposit a *new* collateral type to restore health.

The victim can only evict an entry by zeroing its balance (`_transfer`/`_burn` call `removeFromDepositTokensOfAccount`, `contracts/DepositToken.sol:460-462`, `523-525`). But `transfer`/`withdraw` are gated by `_revertIfLocked`, which uses `unlockedBalanceOf` (`contracts/DepositToken.sol:180-182`, `383-398`): a victim with an unhealthy or zero-issuable position has `unlockedBalanceOf == 0` for the dust tokens, so the attacker-forced entries are **stuck** and cannot be removed. The only escape is repaying debt first — which may itself require the very deposit/mint operations that are now blocked.

The exact sub-variant from the original report ("revert even when the token is already in the set") does not occur because `addToDepositTokensOfAccount` is only invoked when `balanceOf == 0` beforehand, i.e. only for genuinely new tokens — the exploitable analog is the forced-insertion side of the same bug class.

### Impact Explanation
- Griefing / temporary freezing of position management: the victim is unable to open positions in new collateral or synthetic tokens.
- Forced liquidation: a victim whose position is near the liquidation threshold cannot add a new collateral type to recover health if the attacker has filled all 30 slots and the dust entries are locked (`unlockedBalanceOf == 0`), leading to liquidation losses that healthy top-ups would have prevented.
- DoS on liquidation/incentive flows: `seize` into an account at the cap reverts, so liquidations involving a collateral new to the recipient set can revert.

### Likelihood Explanation
- Fully unprivileged: `deposit`, `transfer`, and `transferFrom` are public; `onBehalfOf_` is attacker-chosen.
- Cost is bounded by 30 dust deposits; however, the attacker needs enough registered deposit tokens to fill the victim's free slots (pool deposit tokens are themselves capped at 30 via `ReachedMaxDepositTokens`, `contracts/Pool.sol:703`), so the attack is strongest against victims that already carry several debt tokens. If fewer than 30 deposit tokens exist, the attacker can only fill the gap partially, limiting the block to victims already near the cap.
- No modifier stops it: `deposit` has `whenNotPaused nonReentrant onlyIfDepositTokenExists`, none of which restrict the beneficiary.

### Recommendation
Apply the OpenQ fix pattern — only enforce the cap when the set actually grows, and prevent non-consensual insertion:

- In `onlyIfAdditionWillNotReachMaxTokens`, return early if the token being added is already present, i.e. check `depositTokensOfAccount.contains(msg.sender)` / `debtTokensOfAccount.contains(msg.sender)` inside `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` before reverting on length.
- More fundamentally, restrict who can grow a victim's set: e.g. allow `deposit` to `onBehalfOf_` but require `recipient_ == _msgSender()` (or an opt-in) for the set-growing first receipt in `transfer`/`transferFrom`, or let accounts evict dust entries via a `removeFromDepositTokensOfAccount` escape path that ignores the lock check when the balance is below a dust threshold.

### Proof of Concept
Hardhat sketch (extend `test/Pool.test.ts` fixtures; assumes a pool with ≥2 deposit tokens `msdA`, `msdB` and a debt token `msdDebt`):

```ts
it('griefs victim by filling MAX_TOKENS_PER_USER with dust deposit tokens', async function () {
  const victim = alice.address;
  const attacker = bob;

  // Victim opens a debt position so dust deposits become locked
  await depositTokenA.connect(victimSigner).deposit(collateralAmount, victim);
  await debtToken.connect(victimSigner).issue(smallDebt); // debtTokensOfAccount[victim] = 1

  // Attacker deposits dust of every other registered deposit token to victim
  const max = (await pool.MAX_TOKENS_PER_USER()).toNumber();
  const depositTokens = await pool.getDepositTokens();
  for (let i = 0; i < depositTokens.length && i < max - 1; ++i) {
    const dt = await ethers.getContractAt('DepositToken', depositTokens[i]);
    const underlying = await ethers.getContractAt('ERC20', await dt.underlying());
    await underlying.connect(attacker).approve(dt.address, 1);
    await dt.connect(attacker).deposit(1, victim); // forces addToDepositTokensOfAccount(victim)
  }

  // Victim's combined count is now >= 30
  const held = (await pool.getDepositTokensOfAccount(victim)).length +
               (await pool.getDebtTokensOfAccount(victim)).length;
  expect(held).to.be.gte(max);

  // 1) Victim cannot deposit a collateral type not yet held
  await underlyingNew.connect(victimSigner).approve(newDepositToken.address, parseEther('10'));
  await expect(
    newDepositToken.connect(victimSigner).deposit(parseEther('10'), victim)
  ).to.revertedWithCustomError(pool, 'UserReachedMaxTokens');

  // 2) Attacker cannot even transfer a new deposit token to victim
  await expect(
    newDepositToken.connect(attacker).transfer(victim, 1)
  ).to.revertedWithCustomError(pool, 'UserReachedMaxTokens');

  // 3) Victim cannot evict locked dust while underwater/zero issuable
  const dust = await ethers.getContractAt('DepositToken', depositTokens[0]);
  await expect(
    dust.connect(victimSigner).transfer(attacker.address, 1)
  ).to.revertedWithCustomError(dust, 'NotEnoughFreeBalance'); // unlockedBalanceOf == 0
});
```

The test mirrors the existing cap test at `test/Pool.test.ts:1386-1416`, but drives `addToDepositTokensOfAccount` through the real public `deposit`/`transfer` path rather than impersonated deposit-token signers, and shows the victim-side revert plus the locked-dust eviction failure.
