### Title
Content-Length header parsing accepts "+" prefix, enabling HTTP request smuggling behind proxies - (File: stackslib/src/net/http/request.rs, stackslib/src/net/http/response.rs)

### Summary
The Stacks node's HTTP preamble parsers for both requests and responses parse the `Content-Length` header value with `value.parse::<u32>()`, which is the same bug class as GHSA-hmr7-m48g-48f6 (Jetty): Rust's built-in integer `FromStr` implementation accepts an optional leading `+` sign, so a value like `+16` is accepted and parsed as `16`, even though RFC 9110 §8.6 requires `Content-Length` to be a string of digits `0-9` only, with no sign.

### Finding Description
`HttpReservedHeader::try_from_str` and the request preamble deserializer both parse the Content-Length value directly with `value.parse::<u32>()`: [1](#0-0) [2](#0-1) 

The response preamble deserializer does the same: [3](#0-2) 

Rust's numeric `FromStr` implementation (`u32::from_str`) tolerates a leading `+` character before the digit sequence (this is documented standard-library behavior, not specific to this repo), so `"+16".parse::<u32>()` succeeds and yields `16`, whereas RFC 9110 mandates the header value be a pure digit string. The existing test suite in this repo only validates rejection of a leading `-` and non-numeric strings, but never tests a leading `+`: [4](#0-3) 

This is functionally identical to the Jetty issue: an intermediary (reverse proxy, load balancer, or any HTTP-aware middlebox commonly deployed in front of a Stacks node's RPC endpoint) that correctly rejects `Content-Length: +16` per RFC would return a 400, while the Stacks node would happily parse and honor the same value as a valid 16-byte length. If the front-end and the Stacks node disagree on the boundary of the request/response body because of this differing interpretation, and the front-end reuses the same persistent/keep-alive connection to the backend, an attacker can smuggle a spoofed extra request/response through the split, breaking the "bytes declared == bytes actually consumed as a message boundary" invariant that both parties are expected to enforce identically.

### Impact Explanation
This falls under the explicitly listed Critical category: "request smuggling or auth bypass." A successful smuggling attack against a Stacks node placed behind a compliant reverse proxy could let a remote, unauthenticated attacker inject requests that are misattributed to another client's connection, poison the connection's request/response pairing, or bypass proxy-enforced access controls (e.g., IP allow-lists, admin-only paths) that sit in front of the RPC API's `/v2/*` endpoints.

### Likelihood Explanation
Exploitability requires the Stacks node's HTTP interface to sit behind a strictly RFC-compliant intermediary that also reuses backend connections — a very common production topology (nginx, HAProxy, cloud load balancers in front of `/v2/...` RPC endpoints). No authentication, secret key, or special privilege is needed; the attacker only needs to send a single crafted request with a `+`-prefixed Content-Length. The parsing divergence is deterministic and remotely triggerable in one request.

### Recommendation
Reject `Content-Length` header values containing any character outside `0-9` (in particular, reject a leading `+` or `-`) before calling `.parse::<u32>()`, in all three parse sites: `HttpReservedHeader::try_from_str` (`stackslib/src/net/http/common.rs`), the request preamble deserializer (`stackslib/src/net/http/request.rs`), and the response preamble deserializer (`stackslib/src/net/http/response.rs`). A simple fix is to validate `value.bytes().all(|b| b.is_ascii_digit())` prior to parsing, matching RFC 9110 §8.6's strict digit-only grammar.

### Proof of Concept
Send an HTTP request to the node's RPC listener with:
```
POST /v2/transactions HTTP/1.1
Host: <node>:20443
Content-Length: +16
Connection: close

0123456789abcdef
```
The node's `HttpRequestPreamble::consensus_deserialize` will parse `Content-Length` as `16` and accept/process the 16-byte body, while any RFC-compliant reverse proxy (nginx, Apache httpd) placed in front would reject the same request with `400 Bad Request`. This divergence is the same primitive as CVE-2023-40167 and can be used for request smuggling in a proxied deployment. [2](#0-1)
