### Title
Liquidation dead zone: attacker can push a victim's debt into the `[debtFloor, debtFloor/(1-maxLiquidable))` band where `Pool.liquidate` always reverts - ([File: contracts/Pool.sol])

### Summary
`Pool.liquidate` enforces two constraints that interact destructively: `amountToRepay_` must be `<= maxLiquidable * debt` (Pool.sol:567) and the *remaining* debt must be either `0` or `>= debtFloorInUsd` (Pool.sol:571-579). Because `DebtToken.repay(onBehalfOf_, amount_)` is permissionless and lets anyone pay down another account's debt (DebtToken.sol:418-457), an unprivileged attacker can repay a victim's position down to a debt value `D` satisfying `debtFloor <= D < debtFloor/(1 - maxLiquidable)`. In that band every `liquidate` call reverts: any partial repayment leaves `0 < remaining < debtFloor` (`RemainingDebtIsLowerThanTheFloor`), and the only floor-compliant amount (full repayment `D`) violates `D/D > maxLiquidable` (`AmountGreaterThanMaxLiquidable`) whenever `maxLiquidable < 1e18`.

### Finding Description
1. `Pool.liquidate` computes `_debtTokenBalance = _debtToken.balanceOf(account_)` and rejects `amountToRepay_` above `maxLiquidable * _debtTokenBalance` (Pool.sol:565-569).
2. It then quotes the post-repayment debt in USD and reverts if `0 < _newDebtInUsd < debtFloorInUsd` (Pool.sol:571-579).
3. Solving both constraints: liquidation is possible only if `maxLiquidable * debt >= debt - floorEquiv`, i.e. `debt >= floorEquiv / (1 - maxLiquidable)`. With `maxLiquidable = 0.5e18` (as configured in tests, Pool.test.ts:441), the dead zone is `floor <= debt < 2*floor`.
4. `DebtToken.repay` accepts an arbitrary `onBehalfOf_` and burns the caller's synthetic tokens to reduce the victim's debt (DebtToken.sol:453-454). Its own floor check only prevents landing *below* the floor — landing exactly at or slightly above the floor inside the dead zone is allowed.
5. Attack path: victim is liquidatable with debt `D0 > 2*floor`. Attacker calls `debtToken.repay(victim, x)` so remaining debt lands at e.g. `1.1*floor`. From then on every `liquidate(victim)` reverts until interest accrual grows the debt past `2*floor` or the victim repays voluntarily.

### Impact Explanation
Liveness/liquidation-bound invariant break: a deeply underwater position cannot be liquidated at all for a window of time, while interest keeps accruing against it. This is the MySQL-CVE analog (attacker-induced hang/unavailability of a critical operation): the liquidation path — the protocol's solvency backstop — is reproducibly DoS'd, allowing bad debt to accumulate and potentially become unrecoverable if collateral value keeps falling. Cost to the attacker is bounded (repaying `D0 - ~floor` of synth debt), which can be sourced from the attacker's own deposit/issue or market purchase.

### Likelihood Explanation
- Requires `debtFloorInUsd > 0` and `maxLiquidable < 1e18`. Both are per-pool governance parameters; the test suite exercises `maxLiquidable = 50%` and non-zero floors together (Pool.test.ts:408-451), confirming this configuration is supported. If deployed pools run `maxLiquidable = 1e18`, the dead zone collapses to zero and the finding does not hold on that deployment — this must be checked per chain (`deployments/*/Pool.json`).
- No privileged role, oracle manipulation, or helper needed; a plain EOA calling `DebtToken.repay` suffices. `whenNotShutdown`/`nonReentrant` do not block it.
- The DoS is temporary (interest accrual or victim self-repay eventually lifts the debt out of the band), matching a medium-severity availability impact rather than permanent freezing.

### Recommendation
- In `Pool.liquidate` (and symmetrically in `DebtToken.repay`), treat the floor check as: allow any `amountToRepay_` that leaves `remaining == 0`, and when `maxLiquidable * debt < debt - floorEquiv`, clamp the maximum repayable to the full debt so a full liquidation is always executable. E.g. compute `maxRepay = max(maxLiquidable * debt, debt - floorEquiv)` capped at `debt`.
- Alternatively, waive `maxLiquidable` when the only floor-compliant liquidation is a full close, or allow liquidations that reduce remaining debt below the floor as long as the position becomes healthy or fully closed.

### Proof of Concept
```solidity
// Hardhat/Foundry fork of a pool with debtFloorInUsd = F > 0, maxLiquidable = 0.5e18
// 1. Victim is unhealthy: collateral value fell, debt D0 with F < D0 and D0 > 2F (in USD terms).
// 2. Attacker buys/mints synth and calls:
//    debtToken.repay(victim, D0 - 1.1*F)   // leaves debt ~= 1.1*F  (>= F, allowed)
// 3. Any liquidator call now fails:
//    pool.liquidate(synth, victim, a, depositToken)
//      - a <= 0.5*debt  => remaining = debt - a in (0.6F, 1.1F) < F  => RemainingDebtIsLowerThanTheFloor
//      - a == debt      => a/debt = 1 > 0.5                          => AmountGreaterThanMaxLiquidable
//    vm.expectRevert(...) on all a in (0, debt].
// 4. Assert: pool.debtPositionOf(victim)._isHealthy == false and no liquidate call succeeds
//    until enough interest accrues to push debt >= 2F.
```

Note: verification that the deployed pools actually run `debtFloorInUsd > 0` together with `maxLiquidable < 1e18` was not completed within the available search budget — if production uses `maxLiquidable = 1e18`, this dead zone cannot be reached and the finding should be downgraded accordingly.
