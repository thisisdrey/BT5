## Finding

<br>

### Title
pallet-revive grants full reentrancy (`AllowReentry`) instead of a stipend-restricted deny-reentry guard for real non-zero-value `.transfer()`/`.send()` calls, breaking the Solidity gas-stipend reentrancy invariant that ported contracts rely on - (File: `substrate/frame/revive/src/vm/evm/instructions/contract.rs`)

### Summary
`pallet-revive`'s EVM-compatibility layer decides whether a `CALL` opcode is allowed to reenter the calling contract based on a heuristic match on `(value.is_zero(), gas_limit == CALL_STIPEND)` in `run_call` [1](#0-0) . The match is ordered so that **any non-zero-value call** — which is exactly the pattern Solidity's `.transfer(amount)`/`.send(amount)` compile to — is assigned `ReentrancyProtection::AllowReentry`, while only the rare zero-value edge case (`transfer(0)`/`send(0)`) receives the `AllowNext` deny-reentry protection. This is confirmed by the project's own documentation in `prdoc/stable2603/pr_11227.prdoc`, which states that for `target.transfer(amount)` with `amount > 0`, solc passes `gas_limit = 0` (the 2300 stipend is added implicitly by the EVM, not detected by the `gas_limit == CALL_STIPEND` heuristic) [2](#0-1) . As a result, the overwhelmingly common security-critical usage — sending value with the classic reentrancy-safe stipend — gets no explicit reentrancy denial in pallet-revive, only whatever incidental protection the weight-equivalent-to-2300-gas budget (`determine_call_stipend`) provides.

### Finding Description
In real Ethereum, `.transfer()`/`.send()` are considered reentrancy-safe because the EVM caps the callee to 2300 gas, which is provably insufficient to execute another `CALL` opcode (whose base cost alone exceeds 2300 gas with cold-access surcharges), so no meaningful reentrant call — let alone a state-changing one — can be performed. Solidity/EVM ports commonly rely on this invariant instead of an explicit reentrancy guard.

`pallet-revive` re-implements this via a two-part defense:
1. A weight budget (`determine_call_stipend`) computed by converting `EVMGas(CALL_STIPEND)` into a `Weight`, via `<EVMGas as Token<T>>::weight(...)` plus an event-deposit weight allowance [3](#0-2) .
2. An explicit `ReentrancyProtection` enum (`Strict` / `AllowNext` / `AllowReentry`) that denies subsequent reentry into the current frame when set to `Strict` or `AllowNext` [4](#0-3) .

The bug is in how `run_call` picks between these protections:

```
let (add_stipend, reentracy) =
    match (value.is_zero(), gas_limit.try_into().is_ok_and(|limit: u64| limit == CALL_STIPEND))
    {
        (false, _) => (true, ReentrancyProtection::AllowReentry),
        (_, true) => (true, ReentrancyProtection::AllowNext),
        (_, _) => (false, ReentrancyProtection::AllowReentry),
    };
``` [1](#0-0) 

Because tuple matching evaluates the first field first, **every non-zero-value call falls into the first arm and gets `AllowReentry`**, regardless of the actual `gas_limit` passed. The `AllowNext` deny-reentry protection is reserved exclusively for the zero-value case, which per the project's own PRDoc table is only reached by `transfer(0)`/`send(0)` — not by the standard `transfer(amount>0)`/`send(amount>0)` pattern, which solc compiles with `gas_limit = 0` [5](#0-4) .

This means the security-critical, widely-used pattern (sending non-zero value expecting stipend-based reentrancy safety) is protected **only** by the numeric precision of `determine_call_stipend`'s weight conversion, and gets **no** explicit `Strict`/`AllowNext` backstop — unlike the rare zero-value edge case, which gets both the stipend weight cap **and** the explicit deny-reentry flag. `determine_call_stipend` derives its weight from a benchmarked, aggregate cost model (`EVMGas` → `Weight` conversion plus a fixed event-deposit weight), not a faithful per-opcode replication of EVM gas costs; there is no guarantee that this weight budget is too small to cover the fixed weight cost of one more nested `call()`/`call_evm()` host-function invocation in PolkaVM, the way 2300 real EVM gas is provably too small to cover a `CALL` opcode on Ethereum.

### Impact Explanation
Any contract migrated or deployed to pallet-revive that uses `.transfer()`/`.send()` as its sole reentrancy defense for value-bearing withdrawals (a legacy but still-common Solidity pattern, e.g. in vaults, escrow, or payment-splitting contracts) is exposed to reentrancy if the stipend's weight-equivalent budget is sufficient to execute a nested call in PolkaVM's cost model. This falls squarely under "contracts or revive execution" and "public wrappers... must not undercharge nested execution" from the impact scope: the reentered frame is effectively undercharged relative to the security assumption baked into its bytecode, enabling unauthorized reentrant execution and consequent state manipulation/fund drain in the reentered contract — the same broken-invariant class as the source Curve V2 report (a narrowly-scoped guard condition that omits the actually-exploitable case).

### Likelihood Explanation
This is triggerable by any unprivileged EOA/contract that calls into a target contract relying on `.transfer()`/`.send()` for value transfer inside its own logic (e.g. calling `withdraw()`), with no need for a malicious validator, collator, relayer, or privileged actor — it is a pure public-entrypoint contract-execution bug, matching the "Contracts or revive execution" bucket. It requires only that the stipend's weight budget be sufficient to cover one nested `call` host-function invocation in PolkaVM, which depends on the specific `EVMGas`→`Weight` conversion and runtime cost table, making exploitability implementation-parameter-dependent but not requiring any privileged capability.

### Recommendation
Fix the match ordering/logic in `run_call` so that `add_stipend`/protection selection is based on whether the *effective* granted gas equals the stipend (i.e., detect the stipend case independent of `value.is_zero()`), and apply `ReentrancyProtection::Strict`/`AllowNext` to **all** stipend-only calls, including the common non-zero-value `.transfer(amount)`/`.send(amount)` case (where solc passes `gas_limit = 0` and the EVM implicitly grants exactly 2300 gas). At minimum, do not grant unrestricted `AllowReentry` whenever a stipend-sized budget is being provided; if reliance is purely on weight sizing, audit that `determine_call_stipend`'s weight is provably insufficient to cover the fixed cost of a nested `call`/`call_evm` host call in the interpreter, matching the real-EVM guarantee that 2300 gas cannot execute another `CALL`.

### Proof of Concept
1. Deploy `VictimVault` (EVM bytecode via pallet-revive) with a `withdraw()` function that does `msg.sender.transfer(amount)` after decrementing the caller's balance — the standard "checks-effects-interactions with stipend-safe transfer" pattern.
2. Deploy `Attacker` whose `receive()`/fallback attempts to call back into `VictimVault.withdraw()` (or any state-mutating function) using the stipend budget granted by the incoming value-transfer call.
3. Attacker calls `VictimVault.withdraw()`. Internally, `VictimVault` executes `to.transfer(amount)`, which compiles to a `CALL` with `value = amount`, `gas_limit = 0`.
4. In `run_call`, `value.is_zero() == false` matches the first arm unconditionally, returning `ReentrancyProtection::AllowReentry` (not `AllowNext`), per `substrate/frame/revive/src/vm/evm/instructions/contract.rs:193-203`.
5. `Attacker.receive()` executes with the stipend-equivalent weight budget and, if that budget is sufficient to cover one nested `call`/`call_evm` host invocation, reenters `VictimVault.withdraw()` before state is finalized, allowing the attacker to withdraw more than their entitled balance — reproducing the vault-drain pattern from the source report, adapted to pallet-revive's execution model instead of Curve's Vyper pools.

const STIPEND_LOG_DATA_LEN: u32 = 64;

fn determine_call_stipend<T: Config>() -> Weight {
	let gas_weight = <EVMGas as Token<T>>::weight(&EVMGas(CALL_STIPEND));
	let event_weight = <RuntimeCosts as Token<T>>::weight(&RuntimeCosts::DepositEvent {
		num_topic: STIPEND_LOG_TOPICS,
		len: STIPEND_LOG_DATA_LEN,
	});
	gas_weight.saturating_add(event_weight)
}
