### Title
Native token withdrawals revert for contract-based depositors without `receive()` — no recipient parameter in `NativeTokenGateway.withdraw` - (File: contracts/NativeTokenGateway.sol)

### Summary
`NativeTokenGateway.withdraw()` force-pushes unwrapped native tokens (ETH/AVAX/BNB) to `_msgSender()` via `Address.sendValue`, with no way for the caller to specify a different recipient. If the depositor is a contract account (smart wallet, multisig, contract calling via `Operator.execute` meta-sender) that lacks a payable `receive()`/`fallback`, the final ETH transfer reverts and the entire withdrawal fails. This mirrors the FootiumEscrow bug class: native tokens pushed to `msg.sender` with no `to` parameter.

### Finding Description
In `contracts/NativeTokenGateway.sol:61-70`:

```solidity
function withdraw(IPool pool_, uint256 amount_) external override nonReentrant {
    if (!_poolRegistry.isPoolRegistered(address(pool_))) revert UnregisteredPool();
    address _msgSender = _msgSender();
    IDepositToken _depositToken = pool_.depositTokenOf(nativeToken);
    _depositToken.safeTransferFrom(_msgSender, address(this), amount_);
    (uint256 _withdrawn, ) = _depositToken.withdraw(amount_, address(this));
    nativeToken.withdraw(_withdrawn);
    Address.sendValue(payable(_msgSender), _withdrawn);
}
```

The ETH recipient is hard-coded to `_msgSender()`. A contract account that deposited through `deposit()` (which works fine — it only requires sending `msg.value`) cannot complete `withdraw()` because `Address.sendValue` reverts when the target has no payable receive logic. Notably, the gateway itself is designed for meta-transactions via `SynthContext._msgSender()`, so even a contract calling through `Operator.execute` hits the same wall, since the actual sender — not the operator — receives the ETH.

### Impact Explanation
The revert is atomic, so the user's deposit tokens are not burned — but the withdrawal path is permanently bricked for that account: every `withdraw` call reverts. The user retains a partial workaround (calling `DepositToken.withdraw(amount, to)` directly to receive WETH, then having an EOA unwrap it), so this is not absolute permanent freezing, but the protocol's native-token exit is unusable for contract depositors, and funds earmarked for an atomic withdraw-and-repay flow cannot leave as native tokens. Matches the accepted Medium severity of the source finding.

### Likelihood Explanation
Requires the depositor to be a contract without a payable fallback — plausible for smart wallets, multisigs, or integrations that interact with the gateway. Unprivileged users trigger it purely through the public `deposit`/`withdraw` entry points; no privileged actor is needed.

### Recommendation
Add a `to_` recipient parameter (or a variant `withdrawTo`) so callers can direct unwrapped native tokens to an address that can receive them, e.g.:

```solidity
function withdraw(IPool pool_, uint256 amount_, address to_) external nonReentrant {
    ...
    Address.sendValue(payable(to_), _withdrawn);
}
```

Alternatively, keep the deposit token's WETH withdrawal and let the gateway return WETH to callers that cannot receive ETH.

### Proof of Concept
Hardhat/Foundry fork sketch:

```solidity
contract NoReceive {
    function deposit(NativeTokenGateway g, IPool pool) external payable {
        g.deposit{value: msg.value}(pool);
    }
    function withdraw(NativeTokenGateway g, IPool pool, uint256 amt) external {
        g.withdraw(pool, amt); // reverts: sendValue to this contract fails
    }
    function approve(address token, address spender, uint256 amt) external {
        IERC20(token).approve(spender, amt);
    }
    // note: no receive()/fallback payable
}

function test_NoReceiveCannotWithdrawNative() public {
    NoReceive c = new NoReceive();
    c.deposit{value: 1 ether}(gateway, pool);          // succeeds
    IDepositToken dt = pool.depositTokenOf(gateway.nativeToken());
    c.approve(address(dt), address(gateway), type(uint256).max);
    vm.expectRevert();                                  // Address.sendValue fails
    c.withdraw(gateway, pool, dt.balanceOf(address(c)));
}
```

Caveat: the atomic revert leaves the user's deposit tokens intact and a WETH withdrawal path exists via `DepositToken.withdraw`, so residual impact is a bricked native-token path rather than literal permanent loss; validators may weigh that as Low rather than Medium.
