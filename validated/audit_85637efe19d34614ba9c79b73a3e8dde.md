### Title
NEP-245/IMT `TokenDiff` fee bypass via unit-amount leg splitting - ([File: contracts/defuse/core/src/intents/token_diff.rs])

### Summary
`TokenDiff::execute_intent` computes the protocol fee independently per `TokenDiff` intent leg, and `TokenDiff::token_fee` waives the fee entirely for NEP-245/IMT tokens whenever the leg's `|delta| <= 1`. Because the fee is never aggregated across the multiple `TokenDiff` intents that make up a `MultiPayload` batch (or across separate `execute_intents` calls), an attacker can split any negative delta on a NEP-245/IMT token into a sequence of `-1` legs and pay zero fee regardless of the true magnitude of the trade.

### Finding Description
The intended binding is: for token `T`, `fees_collected(T)` over a logical trade of size `N` should equal `Pips::fee_ceil(fee, N)`.

The actual code in `TokenDiff::execute_intent` computes, per intent, per token leg: [1](#0-0) 
```
for (token_id, delta) in &self.diff {
    ...
    if *delta < 0 {
        let amount = delta.unsigned_abs();
        let fee = Self::token_fee(token_id, amount, protocol_fee).fee_ceil(amount);
        fees_collected.add(token_id.clone(), fee)...
    }
}
```
and `token_fee` explicitly zeroes the fee for NEP-245/IMT legs of size `<= 1`: [2](#0-1) 

Since `Amounts`/`BTreeMap<TokenId,i128>` requires a unique key per token per `TokenDiff`, a single intent cannot hold both a `-2` and a compensating positive delta split on the same token; but nothing prevents the signer from decomposing `-2` into two separate `TokenDiff` intents, each carrying a `-1` leg on the same `token_id`, signed with distinct nonces (or submitted in two separate `execute_intents` calls). Each `-1` leg independently hits the `amount <= 1` zero-fee branch of `token_fee`, so `fees_collected(T)` for the whole logical trade becomes `0` instead of `Pips::fee_ceil(fee, 2)`.

Conservation itself is untouched: engine-level accounting is enforced per `execute_intents` call by `TransferMatcher::finalize`, which nets `internal_add_balance`/`internal_sub_balance` calls (including the fee credit itself, since fee is deposited via `internal_add_balance` and thus tracked as a deposit in the same `TransferMatcher`): [3](#0-2) [4](#0-3) 
As long as the attacker (or an accomplice/second account they control) supplies a matching positive counter-leg (positive deltas never generate fees regardless of size, per the `if *delta < 0` guard), the batch's per-token deltas sum to zero and `finalize()` succeeds - there is no `InvariantViolated` error, only a missing fee credit to `fee_collector`.

None of the existing guards prevent this: `MultiPayload::verify`, nonce/salt checks, and `Lock` checks are orthogonal to fee computation; `TransferMatcher::finalize` only checks that deposits equal withdrawals, and the fee credit (or its absence) is simply one more term in that sum, so removing it does not violate the invariant, it just changes who receives value. The root cause is that `token_fee`'s `amount > 1` threshold was designed assuming a `TokenDiff`'s delta on a token is atomic, but an unprivileged signer fully controls how many intents/legs a logical transfer is split into.

### Impact Explanation
The `fee_collector`'s configured revenue on NEP-245/IMT token flows can be reduced to zero for any trade size by decomposing the negative delta into unit (`amount == 1`) legs, each in its own `TokenDiff` intent (matched by compensating positive legs, which never incur fees). This is a direct, repeatable "protocol fees bypassed" condition (explicitly Critical per the audit scope), applicable to every NEP-245 and IMT token configured with `Pips` fee > 0, for arbitrarily large trade volumes (not just the `delta = -2` example), and repeatable indefinitely across accounts/tokens/batches with no cost beyond extra intents/gas.

### Likelihood Explanation
The attacker needs only: (1) an existing Verifier balance of an NEP-245/IMT `TokenId`, (2) the ability to sign multiple `TokenDiff` intents with distinct nonces (trivial, unprivileged), and (3) a way to supply the compensating positive leg(s) - either a second self-controlled account, or a cooperating/naive counterparty. No special role, relayer key, or DAO permission is required, and the technique degrades gracefully to standard `execute_intents`/`simulate_intents` calls with a `MultiPayload` batch. This is straightforward to execute and does not require timing races or privileged state.

### Recommendation
Compute and enforce the NEP-245/IMT fee-exemption threshold on the *aggregate* negative delta per `(signer, token_id)` across the whole batch (and ideally track cumulative amount per token/signer within a bounded window), rather than per individual `TokenDiff` intent leg, so that splitting a transfer into unit-sized legs cannot avoid crossing the `amount > 1` fee threshold.

    // Finalizes all transfers, or returns unmatched deltas.
    // If unmatched deltas overflow, then Err(None) is returned.
    pub fn finalize(self) -> Result<Transfers, InvariantViolated> {
        let mut transfers = Transfers::default();
        let mut deltas = TokenDeltas::default();
        for (token_id, transfer_matcher) in self.0 {
            if let Err(unmatched) = transfer_matcher.finalize_into(&token_id, &mut transfers)
                && (unmatched == 0 || deltas.apply_delta(token_id, unmatched).is_none())
            {
                return Err(InvariantViolated::Overflow);
            }
        }
        if !deltas.is_empty() {
            return Err(InvariantViolated::UnmatchedDeltas {
                unmatched_deltas: deltas,
            });
        }
        Ok(transfers)
    }
