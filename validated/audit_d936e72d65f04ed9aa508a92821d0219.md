### Title
Stale `tokenSpeed` keeps accruing rewards after the Vesper reward rate ends or drops, letting depositors claim unearned reward tokens until the keeper syncs - (File: contracts/RewardsDistributor.sol)

### Summary
`RewardsDistributor` accrues `rewardToken` to deposit/debt token holders via an index driven by `tokenSpeeds[token]` (`_calculateTokenIndex`, L197-212). That speed is supposed to mirror the underlying Vesper pool's `rewardRate * treasuryVPoolBalance / vPoolTotalSupply`, but it is only refreshed inside `syncTokenSpeed` (L333-348), which is gated to `tokenSpeedKeeper` (`if (_msgSender() != tokenSpeedKeeper) revert NotTokenSpeedKeeper()`, L334), or via `updateTokenSpeed` which is `onlyGovernor` (L315). This is the same bug class as the Omnipool report: a reward-determining state variable is updated only on a privileged path, while the real-world condition it represents changes due to permissionless activity. Here, the true speed changes every time the Vesper `periodFinish` passes, the `rewardRate` changes, or any user deposits/withdraws into the underlying `vPool` (altering `balanceOf(treasury) / totalSupply`). Between the state change and the keeper's next `syncTokenSpeed` call, index accrual uses a stale, incorrect speed.

### Finding Description
In `_calculateTokenIndex` (contracts/RewardsDistributor.sol L197-212), accrued rewards are `_deltaTimestamps * tokenSpeeds[token_]` — the stored speed, not the live Vesper rate. `syncTokenSpeed` (L333-348) computes the correct speed as:

```solidity
if (block.timestamp < _rewards.periodFinish(address(rewardToken))) {
    _speed = (_rewards.rewardRates(address(rewardToken)) * _vPool.balanceOf(address(pool.treasury()))) / _vPool.totalSupply();
}
// else _speed stays 0
```

Key consequences:

1. **Reward period ended → speed should be 0.** Once `block.timestamp >= periodFinish`, the true speed is 0, but `tokenSpeeds[token]` keeps its old nonzero value until the keeper calls `syncTokenSpeed`. Every second in that window, index accrual continues (`_tokensAccrued = _deltaTimestamps * _speed`, L205), minting unearned entitlements.

2. **User actions change the true speed.** Any depositor entering or leaving the underlying Vesper `vPool`, or the treasury's balance shifting via Metronome deposits/withdrawals, changes `balanceOf(treasury)/totalSupply` and hence the correct speed — none of these paths call `syncTokenSpeed`, exactly like Omnipool withdrawals changing pool balance without resetting `rebalancingRewardActive`.

3. **Claiming is permissionless and settles immediately.** `claimRewards(address[] accounts_, IERC20[] tokens_)` (L150-168) updates the index with the stale speed, accrues into `tokensAccruedOf`, and `_transferRewardIfEnoughTokens` (L248-256) pays out on a first-come, first-served basis while balance remains.

Anyone can also call `updateBeforeMintOrBurn`/`updateBeforeTransfer` (L175-192) arbitrarily, so an attacker can snapshot accrual at the stale rate on demand.

### Impact Explanation
Over-accrual at a stale nonzero speed is theft of unclaimed yield: the attacker (any holder of the affected `DepositToken`/`DebtToken`, including balances acquired via flash-minted deposits) calls `claimRewards` and drains `rewardToken` they are not entitled to, before the keeper syncs the speed to 0 or a lower value. Because `_transferRewardIfEnoughTokens` silently pays nothing when the distributor's balance is insufficient (L251), users who legitimately accrued rewards earlier but claim after the drain receive nothing — permanent loss of their unclaimed yield. Symmetrically, when the true speed rises (e.g., rewardRate increases, or a large withdrawal reduces `vPool.totalSupply`), depositors under-accrue and lose entitled rewards during the stale window, mirroring the original report's "users lose entitled rewards because the flag/state wasn't updated outside the privileged path."

### Likelihood Explanation
The desync window is structural: `syncTokenSpeed` is an off-chain-keeper-driven "temporary fix" (comment L331-332), so every Vesper reward epoch boundary (`periodFinish` passing) deterministically opens a window where stored speed > 0 while true speed = 0. No attacker privilege is needed — the attacker only needs to hold (even transiently, via mint/burn or transfer within the same period) a deposit/debt token balance and call the public `claimRewards`. Attacker also can worsen desync by trading into/out of the underlying `vPool` to move `balanceOf(treasury)/totalSupply`, then claiming under the stale speed. The only mitigation is keeper latency, which is operational, not enforced by code.

### Recommendation
Remove the keeper dependency for correctness-critical accrual: compute the effective speed lazily inside `_calculateTokenIndex`/`_updateTokenIndex` by reading `rewardRates`, `periodFinish`, and the treasury's vPool share directly (or cache it with a permissionless `poke()` that anyone can call to refresh `tokenSpeeds`), so the index always accrues at the current true rate. At minimum, make `syncTokenSpeed` permissionless so any user can force a refresh before claiming, and settle each user's accrued delta at the per-second true rate rather than the last-synced one.

### Proof of Concept
Hardhat fork test against mainnet deployment (deployments/mainnet/RewardsDistributor.json):

```ts
// Setup: mainnet fork, real Pool, DepositToken (e.g., msVaUSDC), RewardsDistributor, rewardToken (VSP)
// Impersonate a depositToken holder or deposit underlying via Pool.deposit to get balance.

// 1. Wait until / warp past Vesper poolRewards.periodFinish(VSP) so true speed == 0.
await time.increaseTo(periodFinish + 1);

// 2. Do NOT call syncTokenSpeed (keeper hasn't). tokenSpeeds[depositToken] is still > 0.
const speed = await distributor.tokenSpeeds(depositToken.address);
expect(speed).to.be.gt(0);

// 3. Advance N seconds; index keeps accruing at stale speed.
await time.increase(N);

// 4. Attacker claims at the stale inflated index.
const before = await vsp.balanceOf(attacker.address);
await distributor['claimRewards(address)'](attacker.address);
const after = await vsp.balanceOf(attacker.address);

// attacker received N * speed * share worth of VSP that should not exist post-periodFinish.
expect(after.sub(before)).to.be.gt(0);

// 5. Honest user who accrued rewards during the valid period now claims;
// _transferRewardIfEnoughTokens sees insufficient balance -> pays 0.
const userBefore = await vsp.balanceOf(honestUser.address);
await distributor['claimRewards(address)'](honestUser.address);
expect(await vsp.balanceOf(honestUser.address)).to.eq(userBefore); // yield stolen/frozen
```

Note: this PoC asserts the keeper does not sync within the window; the validity window can be demonstrated deterministically by manipulating fork time past `periodFinish`. Uncertainty: if the production keeper syncs in the same block as the period boundary, the exploitable window shrinks — but the code itself contains no invariant tying index accrual to the live rate, and the NatSpec explicitly calls the keeper mechanism a temporary fix.
