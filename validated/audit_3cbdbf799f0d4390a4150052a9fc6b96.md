### Title
Non-constant-time `Authorization` token comparison enables remote timing attack to forge auth on privileged write endpoints - (File: `stackslib/src/net/api/postblock_proposal.rs`)

### Summary
Every privileged RPC endpoint that gates access with `connection_options.auth_token` compares the client-supplied `Authorization` header to the configured secret using Rust's built-in `String` `!=` operator, which short-circuits on the first mismatching byte. This is a textbook variable-time secret comparison and is remotely distinguishable by response latency, allowing an attacker to recover the auth token byte-by-byte and subsequently forge authentication to a write endpoint such as `/v3/block_proposal`.

### Finding Description
The same pattern appears identically across all `auth_token`-gated handlers: [1](#0-0) 

```rust
let Some(password) = &self.auth else {
    return Err(Error::Http(400, "Bad Request.".into()));
};
let Some(auth_header) = preamble.headers.get("authorization") else {
    return Err(Error::Http(401, "Unauthorized".into()));
};
if auth_header != password {
    return Err(Error::Http(401, "Unauthorized".into()));
}
```

The identical `auth_header != password` check (a plain, non-constant-time `String` comparison) is duplicated in: [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4) [6](#0-5) 

Rust's `PartialEq` for `String`/`&str` delegates to the standard byte-slice comparison, which returns as soon as it finds a differing byte — it is not implemented in constant time (no `subtle::ConstantTimeEq` or similar is used anywhere in the repo; a search for `constant_time`, `ct_eq`, `subtle::` returned zero matches). This breaks the intended equality invariant "authenticated == stored secret" into an observable, incremental oracle: the timing of the 401/400 response leaks how many leading bytes of the guessed token matched the real secret.

The `/v3/block_proposal` endpoint is documented as requiring only this bearer-token check (`security: - rpcAuth: []` in the OpenAPI spec) and is explicitly the trust boundary between the signer network and block validation: [7](#0-6) [8](#0-7) 

### Impact Explanation
An attacker who can measure response latency to a stacks-node's RPC port (no other credentials, no prior authorization) can perform a classic byte-at-a-time timing attack against `auth_token` to recover it, then submit forged, authenticated requests to `/v3/block_proposal` (and the other gated endpoints: `/v3/blocks/upload` broadcast-authenticated path, `/v3/blocks/replay`, `/v3/blocks/simulate`, `/v3/transactions/simulate`, fast read-only calls). Since `/v3/block_proposal` is the interface by which signers submit blocks for validation, an attacker forging this token could flood the node's proposal validation pipeline or interfere with the miner/signer validation flow — an unauthorized write/interaction with node state that this token is specifically meant to prevent. This matches the "unauthenticated/unauthorized write to state" class called out as Critical impact in scope.

### Likelihood Explanation
Extracting a secret via network timing side-channels is a known, exploitable technique (well documented against string-compare-based API-key checks, e.g. GitHub's/Keyczar's historical timing bugs), though it typically requires many repeated requests and statistical averaging to overcome network jitter, especially over the open internet versus a LAN/co-located attacker. Feasibility is higher when the attacker is on the same LAN/segment as the node (common in signer/miner deployments where this token is shared), which is a realistic scenario given that `auth_token` explicitly exists to authenticate `stacks-signer` traffic to a `stacks-node`. This lowers the practical likelihood compared to a direct logic bypass, but the vulnerability is real and remotely reachable without any prior privilege.

### Recommendation
Replace all `auth_header != password` (and equivalent `!=`) checks across `postblock_proposal.rs`, `blockreplay.rs`, `blocksimulate.rs`, `txsimulate.rs`, `fastcallreadonly.rs`, and `postblock_v3.rs` with a constant-time comparison (e.g., using the `subtle` crate's `ConstantTimeEq`, or by comparing over a fixed-length HMAC/hash of both values) so that the number of bytes compared, and therefore latency, does not depend on how much of the secret matches.

### Proof of Concept
1. Configure a node with `connection_options.auth_token = "<secret>"`.
2. Send repeated `POST /v3/block_proposal` requests with an `authorization` header consisting of a candidate prefix followed by all possible next bytes, timing the average round-trip latency to the point where the `if auth_header != password` branch returns (measured before deserialization/validation work, isolating the token-compare cost).
3. The candidate byte causing a statistically larger latency (due to matching one additional byte before the byte-wise comparison diverges) is retained as the next correct byte of `auth_token`.
4. Repeat until the full token is recovered, then use it to submit a normally-rejected/unauthenticated block proposal successfully.
