### Title
Dust-transfer griefing via `MAX_TOKENS_PER_USER` permanently blocks a victim from receiving new deposit-token positions — (File: contracts/DepositToken.sol)

### Summary
The Multer bug is a Denial of Service where a single malformed, attacker-crafted request triggers an unhandled exception that crashes the process. The Metronome analog is the deposit-token account-list mechanism: every `DepositToken._transfer` / `_mint` / `seize` unconditionally calls `pool.addToDepositTokensOfAccount(recipient_)` whenever the recipient's balance goes from zero to non-zero (`DepositToken.sol:518-520`). `Pool` enforces `MAX_TOKENS_PER_USER` on that list, reverting once the cap is reached. An unprivileged attacker can therefore dust-transfer 1 wei of each listed `DepositToken` to a victim, permanently filling the victim's account list. After that, every transfer, `deposit(onBehalfOf = victim)`, or `seize` of a deposit token the victim doesn't already hold reverts — an "unhandled" state failure for any new collateral, exactly the DoS primitive of the original report.

### Finding Description
- `DepositToken._transfer` (called by `transfer`, `transferFrom`, `seize`) and `_mint` (called by `deposit`, `flashDeposit` paths) add the token to the recipient's per-account set in `Pool` when `_recipientBalanceBefore == 0` (`DepositToken.sol:486-488`, `518-520`). Removal only happens when a balance returns to exactly zero (`523-525`).
- `Pool.addToDepositTokensOfAccount` stores tokens in `MappedEnumerableSet` (`MappedEnumerableSet.sol:22-32`) and enforces `MAX_TOKENS_PER_USER`; once reached, the add reverts and the entire parent transaction (transfer / deposit / seize) reverts.
- The attacker only needs an *unlocked* dust balance of each deposit token: deposit 1 wei of underlying via `DepositToken.deposit`, then `transfer(victim, dust)`. Repeating across all listed deposit tokens fills the victim's list to the cap.
- Once full: any third-party `deposit(amount, victim)` for a token the victim doesn't hold reverts; any `transfer` of a new deposit token to the victim reverts; critically, `Pool.liquidate`/`seize` flows that would route a *new* collateral type to the victim revert.

### Impact Explanation
Denial of service / temporary freezing of funds. The victim cannot acquire any additional collateral type — via deposit, transfer, or liquidation seizure — until they fully withdraw one of the dust positions. If the victim's position is approaching liquidation, they cannot deposit a *new* collateral to restore health; their margin-maintenance path is blocked, and liquidations of already-held collateral types proceed on a worsened position. The attacker spends only dust amounts of whitelisted collateral and a few transfers — no privileged role, no oracle manipulation, no governance action.

### Likelihood Explanation
- Fully reachable by any EOA through public `DepositToken.deposit` + `transfer` (or `Operator.execute` batching).
- Cost is bounded by the number of listed deposit tokens (small) × dust; no capital lockup required since the attacker can withdraw their own dust afterwards by transferring it back out — actually the tokens stay in the victim's list only while victim holds them; attacker dust stays with victim permanently (burned value is negligible).
- No modifier stops it: `transfer` only checks `_revertIfLocked` on the *sender* (`DepositToken.sol:350`), never the recipient; `updateRewardsBeforeTransfer` doesn't gate on recipient either.

### Recommendation
Cap should be enforced on the *sender's* ability to add entries rather than reverting the recipient's credit, or better: on add-overflow, don't revert — skip tracking (with a `values()`-based fallback in health checks), or require a minimum first-transfer amount (`MIN_FIRST_TRANSFER`) so dust cannot register a new entry cheaply. Alternatively let users opt out via a receive-list flag, or charge the sender for the SSTORE.

### Proof of Concept
Hardhat/fork sketch (deployed Pool + listed DepositTokens):

```ts
// attacker
for (const dt of await pool.getDepositTokens()) {
  const token = await ethers.getContractAt('DepositToken', dt)
  const underlying = await ethers.getContractAt('IERC20', await token.underlying())
  await underlying.approve(token.address, 1)
  await token.deposit(1, attacker.address)       // acquire dust msdTOKEN
  await token.transfer(victim.address, 1)        // adds dt to victim's list
}
// victim's depositTokensOf(victim) length == MAX_TOKENS_PER_USER now

// any of these revert:
await expect(token2.deposit(amount, victim.address)).to.be.reverted  // new collateral for victim
await expect(token2.connect(other).transfer(victim.address, 1)).to.be.reverted
// victim cannot deposit a new collateral type to save an unhealthy position
```

Uncertainty: I could not re-verify the exact revert name inside `Pool.addToDepositTokensOfAccount` and the `MAX_TOKENS_PER_USER` value (grep only confirmed the constant exists in `Pool.sol`); the mechanism (revert-on-cap inside a mandatory hook on every credit) is confirmed by `DepositToken.sol:486-488` and `518-520`.
