### Title
Snowbridge relayer reward is paid out even when the delivery receipt reports `success == false` - (File: `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs`)

### Summary
The core broken invariant in the external report is: a caller-influenced value that identifies "was the job actually done correctly" is never checked before the protocol releases funds to a caller-controlled destination. The local analog is in `OutboundQueue::process_delivery_receipt`, which decodes a `DeliveryReceipt` (including a `success` flag and an attacker/relayer-influenced `reward_address`) and pays the relayer reward whenever the pre-registered fee is non-zero, without ever checking `receipt.success`.

### Finding Description
`DeliveryReceipt` is decoded from the Ethereum `InboundMessageDispatched` event, and explicitly carries a `success: bool` field indicating whether the inbound message was actually dispatched successfully on Ethereum, plus a `reward_address` chosen by whoever triggered the event: [1](#0-0) 

`process_delivery_receipt` decodes this receipt, resolves the reward destination from `receipt.reward_address` (or the calling relayer if zeroed), fetches the pending fee order by nonce, and pays the reward purely based on `order.fee > 0` — the `success` field is destructured but never consulted: [2](#0-1) 

Compare this to `process_message`, which correctly records `fee` in a `PendingOrder` keyed by `nonce` when the message is first committed for delivery: [3](#0-2) 

The invariant that should hold — "payout state must only advance after decode, dispatch, execution, and settlement succeed atomically" — is broken here: the pallet advances settlement (registers the reward and removes the `PendingOrder`) after decode alone, regardless of whether `execution` (the `success` flag) actually succeeded.

### Impact Explanation
Because reward registration is gated only on `order.fee > 0` and not on `receipt.success`, a relayer who delivers a message that fails on the Ethereum side (e.g., crafts the transaction so the inner dispatch reverts/returns `success: false`, while the outer transaction that emits the log still lands) can still collect the full protocol-held fee via `T::RewardPayment::register_reward`. This drains the reward/fee pot for work that was never actually completed, which matches the impact-gate categories of "theft or unbacked...unlock" of bridge fee funds and "public underpriced work that... stalls bridge processing," since the fee incentive no longer reflects successfully delivered messages.

### Likelihood Explanation
Likelihood is low-to-moderate: it requires no privileged role, malicious peer, or governance abuse — any account submitting a valid (but failed) delivery receipt through the normal inbound flow can trigger the reward payout, matching the "public dispatch wrapper... unauthorized execution" and "duplicate/incorrect settlement" categories that are in scope, while not requiring a malicious relayer/validator/prover assumption beyond what is inherent to permissionless relaying already supported by the design.

### Recommendation
Gate the call to `T::RewardPayment::register_reward` on `receipt.success == true`. If `success` is `false`, either withhold the reward entirely, refund the fee to the original sender, or apply a reduced "delivery attempt" reward that is explicitly distinguished from the full execution reward, and emit a distinct event (e.g. `MessageDeliveryFailed`) instead of `MessageDelivered` so downstream consumers can tell the difference.

### Proof of Concept
1. A user submits an outbound message via `process_message`, which stores a `PendingOrder { nonce, fee, .. }` with `fee > 0`. [4](#0-3) 
2. A relayer delivers this message to the Ethereum Gateway contract but engineers execution so the inner message dispatch fails (Gateway still emits `InboundMessageDispatched(nonce, topic, success=false, reward_address=<relayer_or_arbitrary>)`), which is a supported/anticipated outcome per the receipt schema itself. [1](#0-0) 
3. The relayer (or anyone relaying the proof) submits this receipt back to BridgeHub; `process_delivery_receipt` decodes it, resolves `reward_account` from `receipt.reward_address`, and pays out `order.fee` unconditionally because only `order.fee > 0` is checked — `receipt.success` (already `false`) is ignored. [5](#0-4) 
4. Result: the relayer collects the full fee for a message that was never successfully delivered, while `PendingOrders` is cleared as if delivery had succeeded.

Note: I was not able to fully trace, within the available index, the exact extrinsic in `pallet-inbound-queue-v2` (or wherever `process_delivery_receipt` is invoked) that supplies the `relayer` parameter and enforces the Ethereum header/log proof binding for the receipt; the proof-binding itself (gateway/nonce check) does appear present via `ensure!(T::GatewayAddress::get() == receipt.gateway, ...)`, but I could not confirm from the indexed code whether any additional check elsewhere conditions reward payment on `success`. This should be verified directly in the full repository before treating this as conclusively exploitable.

		/// Process a delivery receipt from a relayer, to allocate the relayer reward.
		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}
