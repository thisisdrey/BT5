Based on my analysis of the nonce-seeding mechanism in `action_implicit_account_creation_transfer` (`runtime/runtime/src/actions.rs:213-244`), `initial_nonce_value` (`runtime/runtime/src/access_keys.rs:46-50`), and `action_delete_account` (`runtime/runtime/src/actions.rs:314-390`), combined with the verifier's nonce checks (`runtime/runtime/src/verifier.rs:211-237`):

The math does allow a theoretical overlap: if the account's last pre-deletion nonce `n_last`, the self-`DeleteAccount`, and the refunding `Transfer`'s receipt execution all land at the *exact same block height* `H`, then `n_last` can exceed the new seed `(H-1)*M` while still being `< H*M` (the `NonceTooLarge` bound at that height), so the naive replay would pass `verify_nonce`. However, tracing through the actual receipt-processing model in this codebase rules this out as a practically reachable, attacker-controllable exploit:

- A self-`DeleteAccount` (signer_id == receiver_id) becomes a **local receipt**, executed in the same block its transaction is included <cite repo="Lauraivanka/nearcore--002" path="docs/architecture/how/tx_receipts.
