### Title
Partial-path traversal in ijar's `UnzipProcessor::Process` allows zip-entry escape into sibling directories - (File: `third_party/ijar/zip_main.cc`)

### Summary
The `zipper`/`unzip_bin` extraction tool in `third_party/ijar/zip_main.cc` guards against zip-slip path traversal by string-prefix-comparing the normalized target path against the normalized output root, but it never verifies that the byte following the shared prefix is a path separator. This is the same bug class as CVE-2024-24569 (`ZipSecurity#isBelowCurrentDirectory`): a string-prefix check without a boundary/separator check lets an attacker-crafted zip entry escape into a *sibling* directory of the extraction root while still passing the "containment" check.

### Finding Description
`UnzipProcessor::Process` builds the destination path for each zip entry and validates it like this: [1](#0-0) 

```
if (extract_) {
    char path[PATH_MAX];
    if (!concat_path(path, sizeof(path), output_root_, output_file_name)) { abort(); }
    std::string normalized_root = normalize_path(output_root_);
    std::string normalized = normalize_path(path);
    if (normalized.compare(0, normalized_root.size(), normalized_root) != 0) {
      ... abort();
    }
    ...
}
```

`normalize_path` (`third_party/ijar/platform_utils.cc:125-128`) resolves `..`/`.` segments via `blaze_util::Path::AsPrintablePath()` but produces a plain normalized path string, not a canonical filesystem path bound to a trailing separator. The check `normalized.compare(0, normalized_root.size(), normalized_root)` only tests that `normalized` *starts with the same characters* as `normalized_root` — it does not check that the next character is `/` (or that the strings are otherwise equal). This is structurally identical to the vulnerable `ZipSecurity.isBelowCurrentDirectory` pattern cited in the CVE, which likewise used a bare `startsWith` prefix test.

Concretely: if `output_root_` is `/tmp/out` and a malicious zip entry name is `../out-evil/PWNED`, then:
- `concat_path` produces `/tmp/out/../out-evil/PWNED`
- `normalize_path` collapses it to `/tmp/out-evil/PWNED`
- `normalized_root` = `/tmp/out`
- `normalized.compare(0, 8, "/tmp/out")` compares the first 8 characters of `/tmp/out-evil/PWNED`, which are exactly `/tmp/out` — the check passes even though the resulting path is a sibling directory, not a path inside `/tmp/out`.

The existing regression test only exercises full-directory escape (`../ZIPPER_POC_OWNED`), not the sibling-prefix bypass, so it does not catch this: [2](#0-1) 

### Impact Explanation
`zipper`'s extraction path (`extract()` / `UnzipProcessor`) is the containment boundary meant to stop a malicious/untrusted zip archive from writing files outside the requested extraction directory. Because the check is a bare string-prefix comparison instead of a proper "is-ancestor-directory" test, an attacker who controls the contents of a zip file that gets extracted with `zipper x <archive> -d <dir>` (or the embedded `unzip_single_jar`/tools install paths that reuse this code) can place entries whose normalized target path shares a string prefix with, but is not actually inside, the extraction root — e.g. writing into a sibling directory such as `<dir>-something-else/...`. This is a containment/write-outside-target-directory bug, matching the accepted impact class ("write outside the exec root/output base"), though the blast radius is scoped to sibling paths of the chosen output directory rather than arbitrary filesystem locations.

### Likelihood Explanation
Reachable whenever `zipper`/ijar's unzip path is invoked against zip content that is not fully trusted (e.g., extracting a downloaded jar/zip artifact). No special privileges are required beyond controlling entry names inside a zip file that the victim's tooling extracts; the bypass only requires crafting entry names with `..` segments that resolve to a path sharing the output directory's name as a string prefix, which is trivial to construct once the output directory name is known or predictable (e.g., a `mktemp -d` pattern with a fixed prefix, as used in the project's own test harness).

### Recommendation
Change the containment check in `zip_main.cc` to require that `normalized` either equals `normalized_root` exactly or that `normalized_root` is followed immediately by a path separator, e.g.:

```cpp
if (normalized.compare(0, normalized_root.size(), normalized_root) != 0 ||
    (normalized.size() > normalized_root.size() &&
     normalized[normalized_root.size()] != '/')) {
  // reject: path escapes output_root_
}
```
(with an OS-appropriate separator check on Windows as well), or better, use a real "is ancestor directory" helper (comparable to `paths.bzl`'s `_starts_with`, which already implements the correct separator-boundary check) rather than a raw `std::string::compare` prefix test.

### Proof of Concept
1. Build a malicious zip archive with a single entry named `../out-evil/PWNED` (path separators as appropriate for target OS).
2. Extract it via `zipper x malicious.zip -d /tmp/out` where `/tmp/out` does not yet exist but `/tmp` is writable.
3. Observe that `zipper` creates `/tmp/out-evil/PWNED` instead of failing, because the prefix check `normalized.compare(0, len("/tmp/out"), "/tmp/out")` succeeds against `/tmp/out-evil/PWNED`.
4. A regression test analogous to `test_no_path_traversal` in `third_party/ijar/test/zip_test.sh` [2](#0-1)  should be added asserting that extraction into a `mktemp -d`-created directory `X` cannot create files under a sibling path `X-evil` when the archive contains an entry like `../$(basename X)-evil/PWNED`.
