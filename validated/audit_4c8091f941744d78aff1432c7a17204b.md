Confirmed: `textproto.MIMEHeader.Add`/`Set` perform no CR/LF validation on header names or values, and `multipart.Writer.CreatePart` writes them verbatim into the multipart stream via `fmt.Fprintf`.

### Title
Multipart part header injection via unvalidated custom header values in `multipart.Writer.CreatePart` - (File: src/mime/multipart/writer.go)

### Summary
`multipart.Writer.CreatePart` builds each MIME part's headers by iterating a caller-supplied `textproto.MIMEHeader` and writing `"%s: %s\r\n"` for every key/value pair without checking either for embedded CR or LF characters. Any application that forwards untrusted data (e.g., a user-supplied filename, content type, or custom header value) into a `textproto.MIMEHeader` before calling `CreatePart` allows that data to inject additional header lines or terminate the header block early, mirroring the httpx2 `FileField.render_headers()` flaw.

### Finding Description
Attacker-controlled string (e.g., an upload's declared content type or a custom header value taken from user input) is placed into a `textproto.MIMEHeader` via `MIMEHeader.Set`/`Add` in `src/net/textproto/header.go:13-23`, which perform no character validation at all — no CR/LF stripping or rejection. That header map is passed to `Writer.CreatePart` in `src/mime/multipart/writer.go:98-126`, specifically the loop at lines 111-115:
```go
for _, k := range slices.Sorted(maps.Keys(header)) {
    for _, v := range header[k] {
        fmt.Fprintf(&b, "%s: %s\r\n", k, v)
    }
}
```
Neither `k` nor `v` is checked for `\r` or `\n` before being interpolated into the header block, and the block is written straight to `w.w` (line 117). A value containing `\r\n` terminates the current header line and lets the attacker inject a fabricated header (or, with `\r\n\r\n`, terminate the header section prematurely and begin injecting into what the downstream multipart parser treats as body content). Only the convenience helpers `CreateFormField`/`CreateFormFile`/`FileContentDisposition` sanitize their inputs via `escapeQuotes` (writer.go:128-169), which percent-encodes CR/LF in the field/file *name* — but this sanitization does not apply to a `Content-Type` value or any custom header set directly via `header.Set(...)` before calling `CreatePart` directly, which is the documented, supported low-level API.

### Impact Explanation
This allows part-header/boundary confusion in the generated `multipart/form-data` body: an attacker who controls a value flowing into a header set on a `textproto.MIMEHeader` passed to `CreatePart` can inject arbitrary additional headers into that part, or manipulate how a downstream multipart parser interprets part boundaries — potentially bypassing header-based validation performed by that receiver (e.g., smuggling a different `Content-Type` or `Content-Disposition` for the same part). This is an integrity/parsing-confusion issue (comparable to CRLF/header injection classes), not remote code execution. It would fall under Go's PUBLIC track as a low/medium-severity hardening issue rather than an urgent exploit, since it requires a specific, unusual application pattern of piping untrusted data directly into part headers.

### Likelihood Explanation
Exploitability depends on an unprivileged victim workflow that constructs a `multipart.Writer` and inserts attacker-influenced strings into `textproto.MIMEHeader` values (for example, a proxy or gateway service that copies an untrusted upstream `Content-Type` header into an outgoing multipart part) and then calls `CreatePart` directly rather than the higher-level `CreateFormField`/`CreateFormFile` helpers. This is a plausible but non-default usage pattern; the safe, commonly-used helpers already escape CR/LF in the values they construct.

### Recommendation
Validate/reject or escape CR and LF characters in both header keys and values inside `Writer.CreatePart` (mirroring the CRLF rejection already performed for HTTP response/request headers in `net/http`), returning an error instead of silently emitting malformed multipart headers.

### Proof of Concept
```go
package multipart_test

import (
	"bytes"
	"mime/multipart"
	"net/textproto"
	"strings"
	"testing"
)

func TestCreatePartHeaderInjection(t *testing.T) {
	var buf bytes.Buffer
	w := multipart.NewWriter(&buf)
	w.SetBoundary("BOUNDARY")

	h := make(textproto.MIMEHeader)
	h.Set("Content-Disposition", `form-data; name="file"; filename="a.txt"`)
	// Attacker-controlled content type containing CRLF injection
	h.Set("Content-Type", "text/plain\r\nX-Injected: evil")

	pw, err := w.CreatePart(h)
	if err != nil {
		t.Fatalf("CreatePart error: %v", err)
	}
	pw.Write([]byte("body"))
	w.Close()

	out := buf.String()
	if strings.Contains(out, "X-Injected: evil") {
		t.Fatalf("header injection succeeded, unsanitized output:\n%s", out)
	}
}
```

// CreateFormFile is a convenience wrapper around [Writer.CreatePart]. It creates
// a new form-data header with the provided field name and file name.
func (w *Writer) CreateFormFile(fieldname, filename string) (io.Writer, error) {
	h := make(textproto.MIMEHeader)
	h.Set("Content-Disposition", FileContentDisposition(fieldname, filename))
	h.Set("Content-Type", "application/octet-stream")
	return w.CreatePart(h)
}

// CreateFormField calls [Writer.CreatePart] with a header using the
// given field name.
func (w *Writer) CreateFormField(fieldname string) (io.Writer, error) {
	h := make(textproto.MIMEHeader)
	h.Set("Content-Disposition",
		fmt.Sprintf(`form-data; name="%s"`, escapeQuotes(fieldname)))
	return w.CreatePart(h)
}

// FileContentDisposition returns the value of a Content-Disposition header
// with the provided field name and file name.
func FileContentDisposition(fieldname, filename string) string {
	return fmt.Sprintf(`form-data; name="%s"; filename="%s"`,
		escapeQuotes(fieldname), escapeQuotes(filename))
}

// Add adds the key, value pair to the header.

func (h MIMEHeader) Add(key, value string) {
