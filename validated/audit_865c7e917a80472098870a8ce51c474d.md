## Title
Unbounded HashSet growth from `pages_indexes` before `MAX_ATTACHMENT_INV_PAGES_PER_REQUEST` cap - (File: stackslib/src/net/api/getattachmentsinv.rs)

## Summary
`RPCGetAttachmentsInvRequestHandler::try_parse_request` parses every comma-separated `pages_indexes` value into a `HashSet<u32>`, sorts it into a `Vec`, and stores it, without ever checking `MAX_ATTACHMENT_INV_PAGES_PER_REQUEST`. That cap is only enforced later, in `try_handle_request`, meaning the parse step performs allocation/hashing/sorting work proportional to the number of distinct u32 values supplied by the caller before the request can be rejected.

## Finding Description
In `try_parse_request` [1](#0-0) , each `pages_indexes` entry is split on `,`, parsed as `u32`, and inserted into a `HashSet<u32>` with no limit on count. The set is then converted to a `Vec` and sorted [2](#0-1) . Only afterward, in `try_handle_request`, is `page_indexes.len() > MAX_ATTACHMENT_INV_PAGES_PER_REQUEST` checked and the request rejected [3](#0-2) . So the equality claimed in the question — dedup-then-cap happens before the request-level bound is applied — is accurate at the code level.

However, this work is bounded by the HTTP request's overall size limits (URL/query-string length caps enforced by the HTTP preamble parser), which constrain how many comma-separated u32 tokens can fit into a single request in the first place. I was unable to fully confirm the exact numeric limit on query-string/URL length in the preamble parser (`stackslib/src/net/httpcore.rs` / `stackslib/src/net/mod.rs`) within this investigation, so I cannot definitively bound the maximum number of distinct values (e.g., whether it truly permits "thousands" as the question assumes) versus a much smaller practical ceiling. This is a real gap in my verification, not a resolved fact.

## Impact Explanation
Assuming the URL/query length limit does permit thousands of short comma-separated u32 tokens (each token can be as short as 1-10 bytes, e.g. `0,1,2,...`), a single request could force the handler to perform up to O(N) hash-insertions and an O(N log N) sort with N in the thousands before the size check rejects it. This is a bounded, single-request compute/allocation cost on a read-only RPC endpoint (`/v2/attachments/inv`), not a crash, forged-data, or state-corruption issue. It fits the "bounded compute DoS on a read endpoint" category only if the bound (N) is meaningfully larger than what the eventual page-processing loop would ever handle (`MAX_ATTACHMENT_INV_PAGES_PER_REQUEST` = 8), i.e., wasted work scales with attacker input rather than the intended cap.

## Likelihood Explanation
No authentication is required to hit `/v2/attachments/inv`; this is a plain unauthenticated RPC GET. Attacker cost is a single crafted URL. Repeatability is only limited by the node's normal HTTP connection/request handling (not in scope per the rules, which explicitly exclude "volumetric DDoS, bandwidth flooding" — a single request's parsing cost, bounded by max URL size, is a much smaller concern than those excluded classes).

## Recommendation
Move the `page_indexes.len() > MAX_ATTACHMENT_INV_PAGES_PER_REQUEST` check into `try_parse_request`, either by capping the number of parsed tokens as they are inserted into the `HashSet` (reject/break once the set size would exceed the max) or by checking the split-token count before insertion, so no more than `MAX_ATTACHMENT_INV_PAGES_PER_REQUEST` distinct values are ever allocated or sorted during parsing.

## Proof of Concept
A stackslib net test would construct an `HttpRequestPreamble` for `GET /v2/attachments/inv?index_block_hash=<valid hex>&pages_indexes=0,1,2,...,N` with N in the thousands (bounded by whatever the actual URL/query length limit turns out to be — this must be empirically determined against the preamble parser's size limit), call `RPCGetAttachmentsInvRequestHandler::try_parse_request` directly, and assert that `self.page_indexes.as_ref().unwrap().len()` reflects all N distinct values collected before any `MAX_ATTACHMENT_INV_PAGES_PER_REQUEST` check has run — demonstrating the parse-time allocation is unbounded by the per-request page cap. Note: given the uncertainty over the concrete query-length ceiling, this PoC should first measure the maximum achievable N under real HTTP preamble limits to determine whether the resulting allocation is actually significant enough to matter, since the rules require excluding bandwidth/traffic-volume-only DoS.
