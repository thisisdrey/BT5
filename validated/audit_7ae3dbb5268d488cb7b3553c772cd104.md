### Title
Remote panic (`assert!`) in `ConversationP2P::validate_blocks_push` / `validate_microblocks_push` from attacker-controlled `preamble.payload_len` - (File: `stackslib/src/net/chat.rs`)

### Summary
`stackslib/src/net/chat.rs` contains `assert!(preamble.payload_len > 5)` in `validate_blocks_push` and `validate_microblocks_push`, and `assert!(preamble.payload_len > 1)` in `validate_transaction_push`/`validate_stackerdb_push`/`validate_nakamoto_block_push`. These asserts fire on `Preamble::payload_len`, a field fully controlled by the remote peer and only loosely bounded (`>= 5` and `< MAX_MESSAGE_LEN`) at deserialization time in `Preamble::consensus_deserialize`. [1](#0-0) [2](#0-1) 

### Finding Description
`Preamble::consensus_deserialize` only enforces `payload_len >= 5` (comment: "minimum is 5 bytes -- a zero-length vector (4 bytes of 0) plus a type identifier (1 byte)") and `payload_len < MAX_MESSAGE_LEN`. [3](#0-2) 

`validate_blocks_push` and `validate_microblocks_push`, however, assert the stronger invariant `payload_len > 5` — i.e., they assume it is *impossible* for a legitimately-decoded message to have `payload_len == 5` exactly. But `payload_len == 5` is exactly the minimum value that passes the preamble decode check (1-byte payload type identifier + 4-byte zero-length vector for the relayers list, with an empty payload body such as an empty `BlocksAvailableData`/blocks vector). This mirrors the TensorFlow `UnbatchGrad` bug class: an op/function assumes a structural invariant about attacker-supplied data ("id is scalar", "batch_index has 3x elements") that is never actually validated before a `CHECK`/`assert!`, so a boundary-value input reaches the assert and aborts the process. [4](#0-3) [5](#0-4) 

The equality/inequality that is broken: the decoder's accepted range for `payload_len` (`[5, MAX_MESSAGE_LEN)`) is broader than the range the handler actually assumes (`(5, MAX_MESSAGE_LEN)`), and nothing between message decode (`StacksMessage::consensus_deserialize` / `read_payload`) and the call into `validate_blocks_push`/`validate_microblocks_push` re-checks or rejects `payload_len == 5` before the `assert!` executes. [6](#0-5) 

### Impact Explanation
`ConversationP2P` message handling runs on the p2p path for any connected/authenticated peer that sends a `Blocks`/`Microblocks`-push (or analogous) message. Reaching `payload_len == 5` requires only that the peer craft a message whose relayers vector is empty (4 zero bytes) and whose payload type + body serializes to exactly 1 byte (a valid, minimal `BlocksData`/`MicroblocksData` with zero entries encodes this way), with `preamble.payload_len` set to the true serialized length (5), which is required to pass signature verification (`preamble.verify`) as well — an attacker with a legitimate/authenticated p2p handshake (any remote peer can complete a handshake) can produce this. Hitting the `assert!` calls Rust's panic machinery, which — unless caught — aborts the connection-handling thread/process, i.e., an unauthenticated-oncethe-handshake-completes remote-triggerable crash of the node from a single well-formed message. This matches the "Critical – remote crash/unauthenticated DoS from few messages" impact bucket in the rules.

### Likelihood Explanation
Likelihood is high for any code path that can be reached with a completed p2p handshake: no privileged key or admin role is required beyond a normal, unauthenticated peer connecting and completing the standard handshake (which every neighbor can do). Constructing the byte-exact `payload_len == 5` message requires only knowledge of the (public) wire format in `stackslib/src/net/codec.rs`, no cryptographic secrets. The main uncertainty is whether Rust's panic in this specific worker context is caught by a top-level `catch_unwind`/`panic::catch_unwind` guard elsewhere in the p2p event loop (which was not directly located in the parts of `stackslib/src/net` examined) — if such a guard exists, the "crash" may be downgraded to a per-connection failure rather than a full node crash; this could not be conclusively verified within scope.

### Recommendation
Replace `assert!(preamble.payload_len > 5)` / `assert!(preamble.payload_len > 1)` in `validate_blocks_push`, `validate_microblocks_push`, `validate_transaction_push`, `validate_stackerdb_push`, and `validate_nakamoto_block_push` with a graceful early return of `Err(net_error::InvalidMessage)` (mirroring the "process_relayers" error path used a few lines below in the same functions), or tighten `Preamble::consensus_deserialize`'s minimum bound to be consistent with what the handlers actually require. This follows the project's own CONTRIBUTING.md guidance that "functions that act on externally-submitted data must never panic" and "untrusted data ingestion must not panic." [7](#0-6) [8](#0-7) 

### Proof of Concept
1. Craft a `StacksMessage` whose `payload` is a `StacksMessageType::Blocks(BlocksData { blocks: vec![] })` (or the corresponding microblocks variant) and whose `relayers` vector is empty.
2. Serialize per `StacksMessage::consensus_serialize` (`stackslib/src/net/codec.rs:1339`): this yields `relayers` bytes = 4 zero bytes (empty vec length) and `payload` bytes = 1 byte (message type tag) for the empty body, i.e., a 5-byte body.
3. Set `preamble.payload_len = 5` and sign the preamble over these bytes with `Preamble::sign` (any valid keypair for a peer that has completed the handshake).
4. Send this message to a victim node over an established p2p connection. `Preamble::consensus_deserialize` accepts `payload_len = 5` (only rejects `< 5`), the message decodes successfully, and when `ConversationP2P` dispatches it to `validate_blocks_push` (or `validate_microblocks_push`), the `assert!(preamble.payload_len > 5)` fails, panicking the handling thread/process. [9](#0-8)
