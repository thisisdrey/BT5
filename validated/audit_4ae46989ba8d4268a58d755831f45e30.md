### Title
Git merge driver for `MODULE.bazel.lock` silently accepts attacker-controlled `registryFileHashes` overrides on conflict, bypassing checksum pinning - (File: `scripts/bazel-lockfile-merge.jq`)

### Summary
Bazel ships a custom `jq`-based git merge driver for `MODULE.bazel.lock` files, intended to reconcile lockfile changes when merging branches. The driver's `shallow_merge` helper resolves any key present in multiple input lockfiles with unconditional last-wins semantics, including for `registryFileHashes` entries that pin the checksum of registry files (`MODULE.bazel`, `source.json`) used to skip re-downloading and re-verifying those files. Because the merge never detects or rejects a genuine value conflict (two branches recording *different* hashes for the *same* registry URL), a hostile branch merged into a trusted one can silently overwrite an author-recorded, trusted registry-file hash with an attacker-chosen one.

### Finding Description
The lockfile documents that `registryFileHashes` pins the hash of every remote registry file consulted during module resolution, and that "Bazel uses the hashes from the lockfile to look up registry files in the repository cache before downloading them" [1](#0-0) . These hashes are meant to be author/CI-verified and are strict enough that Bazel rejects a corrupted one outright (`Invalid checksum: not a checksum.`) [2](#0-1) , and refuses to proceed with a missing one under `--lockfile_mode=error` [3](#0-2) .

The merge tool that reconciles this file across git branches, however, does not apply the same rigor. `shallow_merge(f)` concatenates the arrays produced from each of the (base, left, right) lockfiles, uniquifies them, and folds them together with jq's `add`, which overwrites duplicate keys in encounter order — i.e., last input wins with no conflict detection: [4](#0-3) . This helper is applied directly to `registryFileHashes`: [5](#0-4) . The driver is invoked by git as `jq -s '<script>' -- base left right`, so `right` (the incoming/attacker branch in a typical merge) is the last input and therefore wins any key collision, as demonstrated by the test harness itself: [6](#0-5) .

Unlike a normal textual 3-way merge (which would flag a real conflict when both sides change the same line differently), this structured JSON merge treats differing values for the same `registryFileHashes` URL key as a non-conflict and silently picks one side. An attacker who can get an unprivileged branch merged (e.g., a PR merged by CI, or a build that consumes an untrusted branch as documented in the threat model) can include a modified `MODULE.bazel.lock` that changes the hash recorded for an existing registry URL (for example the `source.json` or `MODULE.bazel` entry for a dependency already pinned by the maintainers). After the merge, the resulting lockfile silently carries the attacker's substituted hash bound to that URL, with no warning, diff conflict marker, or build failure to alert a reviewer.

### Impact Explanation
`registryFileHashes` is the pinning mechanism bzlmod relies on to trust registry content without re-fetching it every time, and it directly affects `source.json` / `MODULE.bazel` file selection that drives which archive `integrity`/`sha256` values, patches, and overlays get applied to a dependency. Corrupting this hash via a silently-resolved merge conflict undermines the integrity guarantee the lockfile is designed to provide (the same class of bug as the Linkr manifest-tampering CVE: unauthenticated, tampered manifest data ends up trusted by the client). Because this happens transparently during a routine `git merge`/CI merge of a possibly untrusted branch, a downstream `bazel build`/`bazel mod deps` invocation using the merged lockfile inherits the attacker-influenced checksum without any indication to the developer that the file changed maliciously.

### Likelihood Explanation
This requires the project to have wired up the documented jq merge driver for `.lockfile` merges and to merge branches from less-trusted contributors/CI jobs, which is exactly the stated in-scope scenario ("files on an untrusted branch CI builds"). No credentials, local machine access, or malicious peer/MITM is needed — only a hostile branch whose diff happens to touch the same `registryFileHashes` key as the base.

### Recommendation
Modify `shallow_merge` (or add a dedicated pass for `registryFileHashes`/`selectedYankedVersions`) to detect when the same key maps to differing values across the three inputs and treat that as a hard merge conflict (non-zero exit / conflict markers) rather than silently picking the last value. At minimum, `registryFileHashes` entries should only ever be "add new key" merges; any attempt to change the value of a key already present in `base` should abort the merge and require manual resolution.

### Proof of Concept
Extend `scripts/bazel_lockfile_merge_test.sh` with a case mirroring `test_synthetic_merge` but where `base`, `left`, and `right` all define the *same* `registryFileHashes` key with *different* values, e.g.:
```
base:  "https://example.org/modules/foo/1.0/MODULE.bazel": "AAAA"
left:  "https://example.org/modules/foo/1.0/MODULE.bazel": "AAAA"   # unchanged
right: "https://example.org/modules/foo/1.0/MODULE.bazel": "EVIL"   # attacker-modified
```
Running `do_merge base left right` produces a merged lockfile with `"EVIL"` for that key and no failure/conflict, confirming the trusted hash was silently replaced by the attacker-supplied one [5](#0-4) .

**File:** scripts/bazel-lockfile-merge.jq (L13-30)
```text
# Like unique, but preserves the order of the first occurrence of each element.
def stable_unique:
  reduce .[] as $item ([]; if index($item) == null then . + [$item] else . end);

# Given an array of objects, shallowly merges the result of applying f to each
# object into a single object, with a few special properties:
# 1. Values are uniquified before merging and then merged with last-wins
#    semantics. Assuming that the first value is the base, this ensures that
#    later occurrences of the base value do not override other values. For
#    example, when this is called with B A1 A2 and A1 contains changes to a
#    field but A2 does not (compared to B), the changes in A1 will be preserved.
# 2. Object keys on the top level are sorted lexicographically after merging,
#    but are additionally split on ":". This ensures that module extension IDs,
#    which start with labels, sort as strings in the same way as they due as
#    structured objects in Bazel (that is, //python/extensions:python.bzl
#    sorts before //python/extensions/private:internal_deps.bzl).
def shallow_merge(f):
  map(f) | stable_unique | add | to_entries | sort_by(.key | split(":")) | from_entries;
```

function do_merge() {
  local base="$1"
  local left="$2"
  local right="$3"

  assert_not_contains "'" "$JQ_SCRIPT_FILE"
  # Simulate the setup of a git merge driver, which can only be configured as a
  # single command passed to sh and overwrites the "left" version. The check
  # above verifies that wrapping the jq script in single quotes is sufficient to
  # escape it here.
  jq_script="$(cat "$JQ_SCRIPT_FILE")"
  merge_cmd="\"$JQ\" -s '${jq_script}' -- $base $left $right > ${left}.jq_tmp && mv ${left}.jq_tmp ${left}"
  sh -c "${merge_cmd}" || fail "merge failed"
}
