### Title
Stake proposal survives receipt rollback after `RecordedStorageExceeded`, causing an unbacked `ValidatorStake` proposal that can trigger a fatal shard-halting invariant violation - (File: `runtime/runtime/src/lib.rs`)

### Summary
When a receipt contains `[Stake, FunctionCall(storage-heavy)]` and the `FunctionCall` trips `RecordedStorageExceeded`, the account's `amount`/`locked` mutation from `action_stake` is correctly discarded by `state_update.rollback()`, but the `ValidatorStake` proposal generated by `action_stake` is copied into the chunk-level `validator_proposals` list *unconditionally*, before the commit/rollback decision is made. This decouples the proposal (forwarded to the epoch manager) from the account's actual locked balance (rolled back), and can later trip the fatal `StorageInconsistentState` invariant check in `update_validator_accounts`.

### Finding Description
`action_stake` (`runtime/runtime/src/actions.rs:59-110`) mutates the in-memory `account` (moving `amount`→`locked`) and unconditionally pushes a `ValidatorStake` proposal into `result.validator_proposals` (`actions.rs:90-94`) whenever the stake amount check passes — this happens independent of whether later actions in the same receipt succeed.

In `apply_action_receipt` (`runtime/runtime/src/lib.rs:776`+), actions are executed in a loop (`lib.rs:892-951`), and each per-action `ActionResult` is merged into the receipt-level `result: ActionReceiptResult`, which accumulates `validator_proposals` across all actions applied so far, even if a later action fails and breaks the loop (`lib.rs:947-950`).

After the loop:
- The account is only persisted to `state_update` via `set_account` if `result.result.is_ok()` (`lib.rs:955-960`), so a failing receipt (e.g., due to `RecordedStorageExceeded` from the `FunctionCall`) never writes the mutated `amount`/`locked` to the trie.
- `state_update.rollback()` is called on `Err` (`lib.rs:1031-1033`), discarding any other prospective writes for the receipt.
- **Critically**, `validator_proposals.append(&mut result.validator_proposals);` (`lib.rs:1022`) executes unconditionally, *before* the `Ok`/`Err` match that decides commit vs. rollback. There is no gating on `result.result.is_ok()`.

So the `ValidatorStake` proposal generated by the successful `Stake` action is forwarded into the chunk's `validator_proposals` vector regardless of whether the overall receipt later fails via `RecordedStorageExceeded` (or any other action-index error). This proposal eventually reaches `update_validator_accounts` (`lib.rs:1663`), which processes proposals at epoch boundaries and asserts the staking invariant:
```
if account.locked() < *max_of_stakes {
    return Err(StorageError::StorageInconsistentState(...));
}
```
(`lib.rs:1682-1688`). Since the account's actual `locked` field was rolled back to its pre-receipt value (lower than the leaked proposal), this invariant can be violated, causing `update_validator_accounts` to return a fatal `StorageInconsistentState` error — a shard-halting panic path.

### Impact Explanation
This is a consensus/liveness bug: an unprivileged account can submit a receipt combining a `Stake` action with a storage-heavy `FunctionCall` engineered to trip `RecordedStorageExceeded`. The account balance itself is correctly protected (no permanent balance loss from this specific path — `set_account` gating plus `state_update.rollback()` prevent the amount/locked shift from persisting). However, the leaked `ValidatorStake` proposal is forwarded to the epoch manager without the corresponding balance ever being locked, creating a state where `EpochInfo`'s recorded max-of-stakes for the account can exceed the account's actual `locked` balance. At the next epoch boundary this can trip the `update_validator_accounts` fatal invariant check, returning `StorageError::StorageInconsistentState`, which crashes chunk application — a shard-halting condition, matching the "shard-halting panic" bounty category.

### Likelihood Explanation
The attacker only needs an ordinary funded account and a self-deployed contract: submit one transaction/receipt with actions `[Stake(stake > current locked, above minimum stake), FunctionCall(reads enough state to exceed `per_receipt_storage_proof_size_limit`)]`. No validator/node privileges are required. It is repeatable and deterministic (the storage-proof limit is a fixed protocol parameter), so the attacker can reliably produce receipts that succeed on the `Stake` action and then fail via `RecordedStorageExceeded` on the following `FunctionCall`, on any account they control.

### Recommendation
Gate the `validator_proposals.append(&mut result.validator_proposals);` call in `runtime/runtime/src/lib.rs` on `result.result.is_ok()`, matching the same condition already used to gate `set_account`. Proposals accumulated from actions in a receipt that ultimately fails should be discarded together with the rest of the receipt's prospective state changes, consistent with the "failed receipt atomicity" invariant documented for this function.

### Proof of Concept
Integration/runtime-test-loop plan (in `runtime/runtime/src/tests/apply.rs`, alongside existing `RecordedStorageExceeded` tests such as `test_add_keys_after_large_read_exceed_receipt_storage_proof_limit`):
1. Deploy a contract on `alice_account()` with a method that reads enough distinct storage keys/values to exceed `per_receipt_storage_proof_size_limit`.
2. Build a single receipt with actions `[Stake(stake_amount above minimum, above current locked), FunctionCall(that method)]`.
3. Apply the receipt with `recording_reads_new_recorder()` so the storage proof is tracked.
4. Assert the receipt fails with `ActionErrorKind::FunctionCallError(FunctionCallError::ExecutionError(...))` containing `"storage proof"` (i.e., `RecordedStorageExceeded`).
5. Assert `account.amount`/`account.locked` are byte-identical to pre-receipt values (VALUE_CONSERVATION — expected to pass).
6. Additionally assert on `apply_result.validator_proposals` (or the equivalent chunk-level output) — check whether it contains a `ValidatorStake` proposal for `alice_account()` with the failed stake amount. This exposes the leak: the proposal list is non-empty despite the receipt failure, demonstrating the account/proposal desync.
7. (Extended) Drive `update_validator_accounts` with a `ValidatorAccountsUpdate` derived from this leaked proposal and the account's actual (rolled-back) `locked` value to show the `StorageInconsistentState` fatal panic is reachable.
