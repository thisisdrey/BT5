### Title
Stale postponed action receipts survive `remove_account` and execute privileged self-actions against a recreated account - (File: core/store/src/utils/mod.rs / runtime/runtime/src/actions.rs)

### Summary
`remove_account` deletes the `Account`, `ContractCode`, access keys, and `ContractData` rows for a deleted account, but never touches `TrieKey::PostponedReceipt`, `TrieKey::PendingDataCount`, or `TrieKey::PostponedReceiptId` entries. A self-targeted postponed action receipt (e.g. containing `DeployContract`/`Stake`) therefore survives account deletion and will still be applied later — with full permission — once its outstanding data dependency is satisfied, even though the account has since been deleted and recreated by a different funder/owner.

### Finding Description
`remove_account` only clears account-scoped state: [1](#0-0) 
It iterates and removes access keys/gas keys and contract data, but there is no removal of `PostponedReceipt`, `PendingDataCount`, or `PostponedReceiptId` keys anywhere in this function: [2](#0-1) 

`action_delete_account` calls this function directly when processing a `DeleteAccount` action: [3](#0-2) 

A postponed action receipt is stored keyed purely by `(receiver_id, receipt_id)` — not by any account "incarnation"/creation nonce — via `set_postponed_receipt`/`get_postponed_receipt`/`remove_postponed_receipt`: [4](#0-3) 

`process_action_receipt` postpones any incoming action receipt with unmet `input_data_ids` by writing `PostponedReceiptId`, `PendingDataCount`, and the serialized receipt itself: [5](#0-4) 

When the missing `DataReceipt` later arrives (`process_receipt`), the runtime looks the postponed receipt up solely by `receiver_id`/`receipt_id`, has no notion that the account was deleted/recreated in the interim, and executes it: [6](#0-5) 

At execution time (`apply_action_receipt`), the account is freshly loaded from state — i.e. the newly recreated incarnation — and `actor_id` is initialized from `receipt.predecessor_id()`: [7](#0-6) 

The only authorization gate for privileged self-actions (`DeployContract`, `Stake`, `AddKey`, `DeleteKey`, etc.) is `check_actor_permissions`, which merely checks string equality `actor_id == account_id`: [8](#0-7) 

Because the stale receipt's `predecessor_id` equals `receiver_id` (it was created as a self-receipt by the original account owner), this check passes trivially against the *new* account incarnation — there is no check binding the postponed receipt to the specific account generation that originally created it. `account_did_not_exist` is tracked in `apply_action_receipt` but is not used to invalidate or discard stale postponed actions; it appears reserved for gas-reward accounting only, not authorization.

**Exploit flow:**
1. Attacker's own contract on `attacker.near` issues a promise batch (`promise_batch_action_deploy_contract`, etc. — legitimate host functions available to any contract) creating a self-targeted action receipt with an unmet `input_data_id` D (e.g., a callback awaiting a cross-contract call result), causing it to be stored as a `PostponedReceipt{receiver_id: attacker.near, receipt_id}`.
2. Attacker submits a self `DeleteAccount` (`predecessor_id == receiver_id == attacker.near`), which passes `check_actor_permissions` and calls `remove_account`, wiping the `Account`/keys/code/data but leaving the `PostponedReceipt`/`PendingDataCount`/`PostponedReceiptId` entries intact.
3. Account name `attacker.near` (if a sub-account or otherwise re-creatable) is later recreated and funded by an unrelated party (victim), unaware of the dormant postponed entry.
4. When data D eventually arrives (the original async chain completing naturally, since receipt delivery is independent of account lifecycle), `process_receipt` finds the still-present `PostponedReceiptId`/`PendingDataCount`, retrieves the stale `PostponedReceipt`, and executes its actions (`DeployContract`, `Stake`, etc.) against the victim-funded account, passing `check_actor_permissions` because `actor_id == account_id` still holds as plain strings.

No existing check (nonce, signature, storage-staking, or size limit) detects that the account was deleted and recreated between postponement and execution.

### Impact Explanation
This is an authorization escalation: privileged self-actions (`DeployContract`/`Stake`) execute against an account incarnation that never authorized them, potentially deploying attacker-controlled code onto a victim-funded account or staking/spending its balance without consent. This matches the NEAR bounty category "authorization escalation across accounts or promises."

### Likelihood Explanation
The attacker needs only: an ordinary contract account, the ability to construct a self-targeted promise with an outstanding data dependency, and a subsequent self `DeleteAccount`. All of these are reachable via standard, unprivileged transactions/contract calls (`promise_batch_action_*` host functions, `DeleteAccountAction`). The main precondition requiring further scenario-specific validation is that the account name become recreatable by a third party who funds it (e.g., sub-account reuse, or squatting on top-level/implicit account names) — this is a realistic but scenario-dependent precondition, not a protocol guarantee. The bug itself (stale postponed-receipt survival across `remove_account`) is fully demonstrated by the code and is deterministically reproducible.

### Recommendation
When `remove_account` deletes an account, also enumerate and remove any `PostponedReceipt`, `PendingDataCount`, and `PostponedReceiptId` entries keyed by that `receiver_id` (mirroring the access-key/contract-data cleanup pattern), or alternatively re-validate `check_actor_permissions`/account existence invariants against the account state as it existed at postponement time (e.g., by refusing to fire postponed self-actions if the account was deleted and recreated since being postponed).

### Proof of Concept
Integration test plan (runtime/runtime/src/tests/apply.rs style, matching existing test patterns like `test_function_call_after_same_chunk_delete_recreate_resolves_fresh_code`):
1. Create `attacker.near`; send it a self action receipt (`predecessor_id == receiver_id == attacker.near`) with `input_data_ids: [D]` and `actions: [DeployContract(malicious_code)]`. Apply and assert `get_postponed_receipt(state, attacker.near, receipt_id)` returns `Some(..)`.
2. Apply a self `DeleteAccount` receipt for `attacker.near`. Assert `get_account(state, attacker.near)` is `None`, but `get_postponed_receipt(state, attacker.near, receipt_id)` still returns `Some(..)` (this alone proves the stale-state bug).
3. Apply a `CreateAccount` receipt for `attacker.near` from a different predecessor (simulating a victim funding recreation), followed by a `Transfer` funding it.
4. Deliver the `DataReceipt` with `data_id == D`. Assert the postponed receipt fires: `get_account(state, attacker.near).contract()` now equals `malicious_code`'s hash, proving the stale, pre-deletion-authorized action executed against the newly funded account.

pub(crate) fn check_actor_permissions(
    action: &Action,
    account: &Option<Account>,
    actor_id: &AccountId,
    account_id: &AccountId,
) -> Result<(), ActionError> {
    match action {
        Action::DeployContract(_)
        | Action::Stake(_)
        | Action::AddKey(_)
        | Action::DeleteKey(_)
        | Action::DeployGlobalContract(_)
        | Action::UseGlobalContract(_)
        | Action::WithdrawFromGasKey(_) => {
            if actor_id != account_id {
                return Err(ActionErrorKind::ActorNoPermission {
                    account_id: account_id.clone(),
                    actor_id: actor_id.clone(),
                }
                .into());
            }
        }
        Action::DeleteAccount(_) => {
            if actor_id != account_id {
                return Err(ActionErrorKind::ActorNoPermission {
                    account_id: account_id.clone(),
                    actor_id: actor_id.clone(),
                }
                .into());
            }
            let account = account.as_ref().unwrap();
            if !account.locked().is_zero() {
                return Err(ActionErrorKind::DeleteAccountStaking {
                    account_id: account_id.clone(),
                }
                .into());
            }
        }
        Action::CreateAccount(_)
        | Action::FunctionCall(_)
        | Action::Transfer(_)
        | Action::TransferToGasKey(_) => (),
        Action::Delegate(_) | Action::DelegateV2(_) => (),
        Action::DeterministicStateInit(_) => (),
    };
    Ok(())
}
