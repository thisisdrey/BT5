### Title
`ExchangeCapsule.transaction` legacy path allows an unprivileged trader to drive AMM pool balances negative, permanently corrupting the Bancor-exchange pool - (File: `chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java`)

### Summary
The `ExchangeTransactionActuator` lets any account call `exchangeCapsule.transaction(...)` to swap tokens against a Bancor-style on-chain liquidity pool. When the "hardened" accounting path is not active, the balance update after a trade is a plain, unchecked subtraction that can drive one side of the pool negative, corrupting pool state for all future traders in a way that mirrors the reported YieldBox `_currentBalance` underflow bug class (an unguarded subtraction reachable by a single unprivileged actor that bricks core accounting).

### Finding Description
`ExchangeCapsule.transaction` computes the counter-party amount via `Processor.exchange(...)` and then updates the two pool balances: [1](#0-0) 

In the non-hardened branch, the new balances are computed with raw `long` arithmetic (`firstTokenBalance - buyTokenQuant` / `secondTokenBalance - buyTokenQuant`) with **no negativity check**, unlike the hardened branch which explicitly validates `newFirstTokenBalance < 0 || newSecondTokenBalance < 0` and throws `ContractValidateException`: [2](#0-1) 

This method is called directly from `validate()` and `execute()` of `ExchangeTransactionActuator`, an actuator reachable by any signed transaction from any account: [3](#0-2) [4](#0-3) 

Whether the hardened (safe) path or the legacy (unsafe) path is used is controlled by a runtime flag (`allowHarden()` in `AbstractExchangeActuator`, backed by `dynamicStore`/fork configuration). When the legacy path is exercised, the Bancor `Processor.exchange` math (double/BigDecimal-based per `ExchangeProcessor`) can, under boundary quantities (e.g. selling a quantity close to or exceeding pool reserves, or extreme reserve ratios), compute a `buyTokenQuant` that exceeds the current reserve of the token being bought. Because there is no bounds check in the legacy branch, this silently persists a negative `firstTokenBalance`/`secondTokenBalance` into the `ExchangeCapsule` (V1) or `ExchangeV2Capsule` and store, which is exactly analogous to the reported bug: an unguarded arithmetic operation on pooled/accounted funds, triggerable by a single unprivileged trade, that corrupts the shared accounting state used by every subsequent interaction with that resource (here, the exchange pool; in the report, the YieldBox strategy's `_currentBalance`).

Once a pool balance goes negative, every subsequent `ExchangeTransactionActuator`, `ExchangeInjectActuator`, or `ExchangeWithdrawActuator` call against that `exchangeId` operates on a corrupted invariant (negative reserve), producing incorrect exchange rates, division/multiplication anomalies (e.g., `BigInteger.divide` by a negative reserve in `ExchangeWithdrawActuator`), and in the worst case permanent inability to safely quote/exchange or withdraw from that pool — effectively bricking that exchange, analogous to the `sDaiStrategy` being bricked by underflow.

### Impact Explanation
Impact is Medium: a corrupted, permanently negative reserve for a specific `Exchange`/`ExchangeV2` entry breaks the AMM invariant for that pool, causing incorrect pricing for `ExchangeInjectActuator`, `ExchangeWithdrawActuator`, and `ExchangeTransactionActuator` operations against it (potential permanent freezing/misallocation of the assets locked in that pool, and possible unbacked/incorrect exchange amounts for subsequent traders). It does not directly compromise consensus or the whole node, but it is a concrete state-corruption/fund-freezing bug scoped to the affected exchange, matching the "permanent freezing of funds" acceptance criterion.

### Likelihood Explanation
Likelihood is Medium-to-Low: it requires (a) the hardened-accounting path to be disabled/not yet active for the relevant chain configuration, and (b) an attacker crafting a legitimate `ExchangeTransactionContract` with quantities/reserve ratios that push the computed `buyTokenQuant` at or beyond the counter-reserve. This is achievable by any single account without special privileges, similar to the original report where a single attacker triggers the flaw with minimal capital, but it does depend on the specific reserve state/ratio and on the hardened path not being enforced.

### Recommendation
Make the negative-balance guard (`newFirstTokenBalance < 0 || newSecondTokenBalance < 0` check, currently only in the `hardenedCalc` branch) unconditional in `ExchangeCapsule.transaction`, regardless of the `hardenedCalc`/`allowHarden()` flag, so that any computed post-trade balance below zero causes the transaction to fail validation rather than silently persisting a corrupted state. Additionally, ensure `ExchangeWithdrawActuator`/`ExchangeInjectActuator` validate that pool reserves remain non-negative before performing further arithmetic (e.g., `BigInteger` division) against them.

### Proof of Concept
1. Ensure the chain configuration has the hardened exchange math path (`allowHarden()`) disabled (legacy behavior), which is the pre-hardening default for `ExchangeCapsule.transaction`.
2. Create an `Exchange` pool via `ExchangeCreateActuator` with a small reserve on one side (e.g., `firstTokenBalance = X`, `secondTokenBalance = Y`) — reachable by any funded account.
3. Submit an `ExchangeTransactionContract` selling a quantity of the counter token computed (via the Bancor formula in `ExchangeProcessor`) to return `buyTokenQuant > firstTokenBalance` (or `> secondTokenBalance`), exploiting floating point/BigDecimal rounding at extreme ratios.
4. Because the legacy branch in `ExchangeCapsule.transaction` performs unchecked `firstTokenBalance - buyTokenQuant` (`chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java:151-153`), the resulting `newFirstTokenBalance` persists as negative in the `ExchangeV2Store`/`ExchangeStore`.
5. Subsequent calls to `ExchangeTransactionActuator`, `ExchangeInjectActuator`, or `ExchangeWithdrawActuator` against this `exchangeId` now operate on a corrupted, negative reserve, producing incorrect exchange math and/or permanently locking assets tied to that pool.

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
