### Title
Unverified attachment content accepted from peer response bypasses hash binding, permanently persisting attacker-chosen content in the `attachments` table - ([File: stackslib/src/net/atlas/download.rs])

### Summary
When the Atlas downloader requests an attachment by `content_hash` from a peer, the response is decoded via `StacksHttpResponse::decode_atlas_get_attachment` and inserted into the batch's attachment set without ever checking that the returned content's `Hash160` matches the requested hash. `AtlasDB::insert_instantiated_attachment` then persists that attachment keyed by its own (attacker-controlled) hash, and only *conditionally* updates `attachment_instances.is_available` for rows whose `content_hash` equals that hash, meaning unrelated content is stored permanently even when it satisfies zero legitimate on-chain-confirmed instances.

### Finding Description
The claimed fault is real: `attachments.hash` is never checked for equality against any confirmed `attachment_instances.content_hash` before the `INSERT OR REPLACE` in `insert_instantiated_attachment` runs.

Trace:
- `extend_with_attachments` in `stackslib/src/net/atlas/download.rs` (around lines 530-559) decodes each peer's HTTP response via `response.decode_atlas_get_attachment()` and does `self.attachments.insert(response.attachment)` [1](#0-0)  — there is no comparison of `response.attachment.hash()` to the `content_hash`/URL hash that was actually requested for that peer/request.
- `decode_atlas_get_attachment` in `stackslib/src/net/api/getattachment.rs` simply parses the JSON body into `GetAttachmentResponse` with no hash validation [2](#0-1) .
- In `AttachmentsDownloader::run`, once the batch state machine reaches `Done`, every attachment collected this way is looked up by its *own* hash (`find_all_attachment_instances(&attachment.hash())`) and then unconditionally passed to `insert_instantiated_attachment(&attachment)`, regardless of whether any instance actually matched [3](#0-2) .
- `insert_instantiated_attachment` performs `INSERT OR REPLACE INTO attachments (hash, content, was_instantiated, created_at) VALUES (?, ?, 1, ?)` keyed by `attachment.hash()`, then a *separate* `UPDATE attachment_instances SET is_available = 1 WHERE content_hash = ?1 AND status = ?2` [4](#0-3) . The insert into `attachments` happens unconditionally even if the `UPDATE` affects zero rows.
- There is no eviction routine for `was_instantiated = 1` rows: `evict_expired_uninstantiated_attachments` and `evict_k_oldest_uninstantiated_attachments` both filter on `was_instantiated = 0` only [5](#0-4) .

Exploit flow: an attacker who is selected as one of the node's outbound sync peers (`network.get_outbound_sync_peers()`) responds to a legitimate `GET /v2/attachments/<hash>` request (issued because the victim has a pending, on-chain-confirmed `AttachmentInstance` for `content_hash = X`) with arbitrary content `Y` such that `Hash160(Y) != X`. The victim never checks the returned content's hash against `X` before accepting it into `self.attachments`, so `Y` gets permanently written to the `attachments` table keyed by `Hash160(Y)`, with `was_instantiated = 1`, and no confirmed instance ever references `Hash160(Y)`.

### Impact Explanation
Each malicious response permanently adds one row to the victim's `attachments` SQLite table containing arbitrary attacker-chosen bytes (bounded only by whatever size limits exist on the HTTP JSON body / attachment content field), with no corresponding on-chain commitment and no eviction path. Repeating this across many distinct hashes (attacker controls the content, hence the hash) causes unbounded disk growth in the Atlas DB — an attachment/BNS mismatch: content is served/stored as though instantiated, without ever matching a confirmed `attachment_instances.content_hash`. This matches the "attachment/BNS mismatch" High-severity category in scope.

### Likelihood Explanation
Preconditions: the attacker must be one of the outbound sync peers the victim selects to fetch attachments from (achievable for any remote peer that gossips into the victim's peer set and offers a `data_url`), and the victim must have at least one pending/queued `AttachmentInstance` to trigger a `GET /v2/attachments/<hash>` request. No RPC secret, private key, or privileged role is required — only the ability to answer HTTP responses to outbound requests the victim itself initiates. The attack is fully repeatable per request/response cycle and costs the attacker only the effort of returning arbitrary JSON content.

### Recommendation
In `extend_with_attachments` (or immediately in `decode_atlas_get_attachment`/`try_parse_response`), verify that `response.attachment.hash()` equals the `content_hash` that was actually requested for that `AttachmentRequest` before inserting it into `self.attachments`; discard/penalize the peer (bump failed requests) on mismatch. Additionally, `insert_instantiated_attachment` should not blindly `INSERT OR REPLACE` into `attachments` unless the `UPDATE attachment_instances ... WHERE content_hash = ?1` actually affected at least one row (or the hash is independently confirmed to belong to a pending instance), and an eviction policy should exist for `was_instantiated = 1` rows that never got legitimately paired.

### Proof of Concept
Rust test plan (in `stackslib::net::atlas::download` or `db` test module):
1. Construct an `AtlasDB` with one pending `AttachmentInstance` with `content_hash = X`, `status = Checked`, `is_available = 0`.
2. Craft an `Attachment` `Y` whose `content` differs from anything committed, i.e., `Y.hash() != X`.
3. Simulate the peer response path by directly calling `network.atlasdb.insert_instantiated_attachment(&Y)` (mirroring what `AttachmentsDownloader::run` does unconditionally at `download.rs:161`), bypassing any hash-to-request correlation, since none exists in `extend_with_attachments`.
4. Assert via raw SQL `SELECT COUNT(*) FROM attachments WHERE hash = ? AND was_instantiated = 1` that the row for `Y.hash()` exists.
5. Assert `attachment_instances` for `content_hash = X` still has `is_available = 0` (the `UPDATE` affected 0 rows), proving `Y` was persisted despite never being confirmed on-chain.
6. Call `evict_expired_uninstantiated_attachments` and `evict_k_oldest_uninstantiated_attachments`; assert the row for `Y.hash()` still exists (no eviction path covers `was_instantiated = 1`), demonstrating permanent storage growth.

    pub fn evict_k_oldest_uninstantiated_attachments(&mut self, k: u32) -> Result<(), db_error> {

        let res = tx.execute(
            "DELETE FROM attachments WHERE hash IN (SELECT hash FROM attachments WHERE was_instantiated = 0 ORDER BY created_at ASC LIMIT ?)",

        tx.commit().map_err(db_error::SqliteError)?;

    pub fn insert_instantiated_attachment(
        &mut self,
        attachment: &Attachment,
    ) -> Result<(), db_error> {
        let now = util::get_epoch_time_secs() as i64;
        let tx = self.tx_begin()?;
        tx.execute(
            "INSERT OR REPLACE INTO attachments (hash, content, was_instantiated, created_at) VALUES (?, ?, 1, ?)",
            params![attachment.hash(), attachment.content, now],
        )?;
        tx.execute(
            "UPDATE attachment_instances SET is_available = 1 WHERE content_hash = ?1 AND status = ?2",
            params![attachment.hash(), AttachmentInstanceStatus::Checked],
        )?;
        tx.commit()?;
        Ok(())
    }
