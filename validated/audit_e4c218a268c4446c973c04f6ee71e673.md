### Title
Unauthenticated `header.RecvError` UDP packet with spoofed source address and guessed `RemoteIndex` triggers `closeTunnel` DoS - ([File: outside.go])

### Summary
`Interface.handleRecvError` authorizes a `RecvError` packet solely by comparing the spoofable UDP source address (`addr`) against `hostinfo.GetRemote()`, and identifies the target tunnel purely from the unauthenticated 32-bit `h.RemoteIndex` field. Neither value is cryptographically verified, so an attacker who can spoof UDP packets and knows (or guesses) a victim's `localIndexId` and the victim's real remote UDP endpoint can force `f.closeTunnel(hostinfo)` and `f.handshakeManager.DeleteHostInfo(hostinfo)`, tearing down a legitimate, established tunnel.

### Finding Description
`readOutsidePackets` dispatches `header.RecvError` packets before any decryption or crypto verification: [1](#0-0) 

`handleRecvError` then does:
1. A rate-limit style check `f.acceptRecvErrorConfig.ShouldRecvError(addr)` — this is a policy/rate gate, not a cryptographic authentication of `addr`.
2. Looks up the hostinfo purely via the attacker-controlled `h.RemoteIndex`: `f.hostMap.QueryReverseIndex(h.RemoteIndex)`.
3. Compares the packet's UDP source address `addr` to `hostinfo.GetRemote()` — a plain value comparison on data that came from the UDP packet's source address, which is trivially spoofable since Nebula runs over UDP with no source-address validation prior to this point.
4. If the comparison passes (or `hr` is not yet valid), it calls `f.closeTunnel(hostinfo)` and `f.handshakeManager.DeleteHostInfo(hostinfo)`: [2](#0-1) 

No certificate, no crypto handshake state, no AEAD/MAC check ties this `RecvError` packet to the real peer — the check at line 564 (`hr.IsValid() && hr != addr`) is exactly the "Someone spoofing recv_errors?" heuristic named in the log message itself, and it only detects the mismatch case; it does not cryptographically prevent it, because `addr` is the network-layer source address which is fully attacker-controlled over raw/spoofed UDP.

The two attacker-known/guessable inputs are:
- `h.RemoteIndex`: a 32-bit value identifying the victim's local hostinfo (`localIndexId`), sent unencrypted in this header type and observable by an on-path or passive attacker, or brute-forceable given enough attempts (32-bit space, no replay/rate limiting tied to guesses other than `ShouldRecvError`).
- `addr`: the victim's real remote UDP endpoint, which for many Nebula deployments (lighthouses, static peers with known public IP/port) is not secret at all.

Given both, an off-path attacker with no certificate can send a single spoofed UDP packet of type `header.RecvError` with `RemoteIndex` = the victim's local index and a spoofed source `AddrPort` equal to the real remote peer's endpoint, causing the victim to tear down that tunnel.

### Impact Explanation
This is an unauthenticated, remote denial-of-service against an established Nebula tunnel: the victim's `HostInfo` is deleted from the hostmap and its pending handshake state is deleted, forcing tunnel teardown and requiring a fresh handshake. Repeated spoofed packets can be used to continuously disrupt a session, preventing stable connectivity between two legitimate, certificate-authenticated peers — matching the "remote crash/wedge"/availability disruption category, without requiring any certificate, key material, or on-path position beyond source-address spoofing and knowledge/guessing of the 32-bit index.

### Likelihood Explanation
Feasibility depends on:
- Ability to spoof UDP source `IP:port` — feasible on many networks lacking egress/ingress filtering (no BCP38), and trivially feasible for an attacker who is on the same network segment or otherwise able to send raw/spoofed UDP.
- Knowledge of the victim's real remote endpoint — often not secret (lighthouse addresses are commonly public; static peer configs are often known).
- Knowledge/guessing of `h.RemoteIndex` (32-bit) — observable to passive/on-path attackers from earlier legitimate traffic (index values are sent in cleartext headers), reducing this from a brute-force problem to simple observation in many realistic scenarios (e.g., a previously on-path/observing attacker who has since lost that position but can still spoof packets).
This is a known, already-partially-mitigated design tradeoff (the `ShouldRecvError` rate-limit and the address-match heuristic exist specifically because of this risk), but the mitigations are heuristic, not cryptographic, so the underlying bypass remains exploitable under the stated preconditions.

### Recommendation
Do not act on `RecvError` based solely on UDP source address and cleartext index. Options:
- Require `RecvError` handling only from `IsRelayed`/verified paths, or bind acceptance to a value that is authenticated (e.g., require a valid short MAC/nonce derived from an already-established symmetric key associated with that hostinfo, rather than comparing raw UDP addresses).
- Alternatively, treat `RecvError` purely as a hint to trigger a lightweight liveness probe/re-handshake rather than immediately deleting hostinfo state, so a spoofed packet cannot unilaterally destroy an established session.

### Proof of Concept
Unit test in `outside_test.go` (or new test file) exercising `Interface.handleRecvError` directly:
1. Set up an `Interface` with a real `HostInfo` inserted into `f.hostMap` for a "victim" with a known `localIndexId` and `hostinfo.remote` set to `victimAddr`.
2. Construct a `header.H` with `Type = header.RecvError` and `RemoteIndex = victim.localIndexId`.
3. Call `f.handleRecvError(victimAddr, h)` directly with `addr == victimAddr` (simulating a spoofed source address, since the real UDP layer never authenticates `addr` against any certificate).
4. Assert that `f.hostMap.QueryReverseIndex(victim.localIndexId)` returns `nil` afterward (i.e., `closeTunnel` was invoked) and that `f.handshakeManager` no longer has the pending hostinfo — confirming that tunnel teardown occurred based purely on unauthenticated header content and a spoofable address equality check, with no certificate or AEAD verification anywhere in the call path (`readOutsidePackets` → `handleRecvError` → `closeTunnel`).

```go
func (f *Interface) handleRecvError(addr netip.AddrPort, h *header.H) {
	if !f.acceptRecvErrorConfig.ShouldRecvError(addr) {
		f.l.Debug("Recv error received, ignoring",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
		return
	}

	if f.l.Enabled(context.Background(), slog.LevelDebug) {
		f.l.Debug("Recv error received",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
	}

	hostinfo := f.hostMap.QueryReverseIndex(h.RemoteIndex)
	if hostinfo == nil {
		f.l.Debug("Did not find remote index in main hostmap", "remoteIndex", h.RemoteIndex)
		return
	}

	hr := hostinfo.GetRemote()
	if hr.IsValid() && hr != addr {
		f.l.Info("Someone spoofing recv_errors?",
			"addr", addr,
			"hostinfoRemote", hr,
		)
		return
	}

	f.closeTunnel(hostinfo)
	// We also delete it from pending hostmap to allow for fast reconnect.
	f.handshakeManager.DeleteHostInfo(hostinfo)
}
```
