### Title
Attacker can fill a victim's `depositTokensOfAccount` list via dust `DepositToken` transfers, permanently reverting all new-collateral deposits for that account (DoS / forced-liquidation vector) - (File: contracts/Pool.sol)

### Summary
`Pool.addToDepositTokensOfAccount` enforces a hard per-account cap (`MAX_TOKENS_PER_USER` across deposit + debt tokens) and reverts with `UserReachedMaxTokens` once the cap is reached. Because `DepositToken._transfer` unconditionally calls `pool.addToDepositTokensOfAccount(recipient_)` whenever the recipient's balance of that token goes from `0` to nonzero, any holder can push entries into an arbitrary victim's per-account list simply by transferring dust amounts of each listed deposit token. Once the victim's combined list hits the cap, every operation that would add a *new* token to their list reverts — including `deposit(..., onBehalfOf_ = victim)` for a collateral type they don't yet hold, `DebtToken.issue`/`mint` for a new synthetic (which calls `addToDebtTokensOfAccount`), and any `transfer` of a new deposit token to them.

### Finding Description
The cleanup/NULL-deref DoS class in CVE-2023-27783 maps to an attacker-reachable revert that bricks a code path for a victim. In Metronome:

1. `DepositToken._transfer` (contracts/DepositToken.sol:498-526) adds `recipient_` to `depositTokensOfAccount` on first receipt of each deposit token — no consent, no opt-in.
2. `Pool.addToDepositTokensOfAccount` (contracts/Pool.sol:216-220) runs `onlyIfAdditionWillNotReachMaxTokens(account_)`, which reverts once `debtTokensOfAccount.length + depositTokensOfAccount.length >= MAX_TOKENS_PER_USER` (contracts/Pool.sol:143-148).
3. `DepositToken._mint` (contracts/DepositToken.sol:486-488) adds the beneficiary's entry on deposit, so `deposit()`/`deposit on behalf` revert for any *new* collateral once the cap is saturated.
4. `DebtToken._mint` (contracts/DebtToken.sol:597-600) symmetrically calls `addToDebtTokensOfAccount`, so opening a debt position in a *new* synthetic also reverts.

Attack path: attacker deposits a dust amount of underlying into each of the pool's `N` deposit tokens (cheap, balance-delta `deposit()` in `DepositToken.sol:211-237` mints dust msdTOKEN), then `transfer(victim, 1 wei)` on each. Each transfer inserts the token into the victim's list. With `MAX_TOKENS_PER_USER` entries saturated, the victim cannot:

- deposit any additional collateral type (mint path reverts),
- receive msdTOKEN of a type they don't already hold,
- issue debt in any new synthetic token.

Notably the victim *cannot self-clean*: entries are only removed when the balance reaches zero (`removeFromDepositTokensOfAccount` requires the caller be the token contract), but dust pushed by the attacker sits in the victim's balance, and the victim can burn it via `withdraw` — however each `withdraw` is itself gated by `_revertIfLocked`/`unlockedBalanceOf` for the transfer path and requires health checks; more importantly, removing one entry just lets the attacker re-add it in the same or next transaction (attacker keeps dust reserves), so the DoS is sustainable at negligible cost.

### Impact Explanation
Temporary-to-indefinite denial of service of the victim's position management and a forced-liquidation vector:

- A victim who is approaching liquidation cannot add a *new* collateral type to restore health (any `deposit(onBehalfOf = victim)` for a non-held token reverts), and cannot open debt in a new synthetic. If they lack the synthetic tokens to repay and don't hold enough of their existing collateral type, the position is liquidated and they take the liquidation penalty/bad-debt loss.
- Funds are not permanently frozen (existing-token withdrawals and `repay`/`repayAll` still work since they remove, not add, entries), so the realized impact is a persistent DoS plus liquidation-loss enablement, which fits "temporary freezing of funds" / griefing thresholds rather than direct theft.
- Cost to the attacker is bounded by `MAX_TOKENS_PER_USER` dust deposits + transfers — trivially cheap relative to the victim's harm.

### Likelihood Explanation
Fully reachable by an unprivileged EOA through public entry points (`deposit`, `transfer` on any listed `DepositToken`). No privileged role, oracle manipulation, or malicious infrastructure is needed. The only constraints: it requires multiple listed deposit tokens to approach the cap (cap is shared with debt tokens, so partial saturation still blocks victims already holding some positions), and the victim retains escape paths (repay + withdraw) that limit the outcome to DoS/forced liquidation rather than outright theft. Success depends on the deployed count of deposit tokens being reasonably close to `MAX_TOKENS_PER_USER` to saturate economically.

### Recommendation
- Do not add a token to `depositTokensOfAccount` on inbound `transfer`; only register on `deposit()`/`_mint`, or make list insertion consent-based (e.g., recipient must already be tracked or call an `accept`/`enterMarkets`-style function).
- Alternatively, allow the account itself to purge entries (a user-callable `removeFromDepositTokensOfAccount` gated on zero balance is already effectively possible via withdraw, but giving users a direct "exit token" path makes the griefing trivially cleanable).
- Consider excluding dust below a minimum-mint threshold from triggering list insertion (`amount_ > MIN`).

### Proof of Concept
Foundry fork sketch (Hardhat equivalent works against the pool fixtures in `test/Pool.test.ts`):

```solidity
// SPDX-License-Identifier: MIT
pragma solidity 0.8.24;

import "forge-std/Test.sol";
import {IPool} from "../contracts/interfaces/IPool.sol";
import {IDepositToken} from "../contracts/interfaces/IDepositToken.sol";
import {IERC20} from "../contracts/dependencies/openzeppelin/token/ERC20/IERC20.sol";

contract TokenListGriefingTest is Test {
    IPool pool = IPool(POOL_PROXY);            // deployed pool
    address victim = address(0xBEEF);
    address attacker = address(0xA77AC);

    function test_fillVictimTokenList() public {
        uint256 cap = pool.MAX_TOKENS_PER_USER();
        address[] memory dTokens = pool.getDepositTokens();

        vm.startPrank(attacker);
        for (uint256 i; i < dTokens.length && i < cap; ++i) {
            IDepositToken dt = IDepositToken(dTokens[i]);
            IERC20 underlying = dt.underlying();
            deal(address(underlying), attacker, 10);
            underlying.approve(address(dt), 10);
            dt.deposit(10, attacker);            // mints dust msdTOKEN
            dt.transfer(victim, 1);              // inserts into victim's list
        }
        vm.stopPrank();

        // Victim's list is now saturated.
        assertGe(
            pool.getDepositTokensOfAccount(victim).length +
            pool.getDebtTokensOfAccount(victim).length,
            cap
        );

        // Any deposit of a NEW collateral type on behalf of victim reverts.
        IDepositToken newDt = IDepositToken(dTokens[0]); // token victim "burned" or a newly added one
        IERC20 u2 = newDt.underlying();
        deal(address(u2), attacker, 100);
        vm.startPrank(attacker);
        u2.approve(address(newDt), 100);
        // If victim removed an entry, attacker re-adds it first; otherwise:
        vm.expectRevert(IPool.UserReachedMaxTokens.selector);
        newDt.deposit(100, victim);
        vm.stopPrank();
    }
}
```

Caveats: the PoC assumes enough distinct deposit tokens (plus any debt tokens the victim accrues) exist to reach `MAX_TOKENS_PER_USER`; on deployments with few collaterals the cap may be unreachable, which would downgrade this to a partial-DoS (only blocks the "next" token once the victim legitimately approaches the cap). I was unable to confirm the exact `MAX_TOKENS_PER_USER` constant value or the live count of registered deposit tokens within the available iterations.
