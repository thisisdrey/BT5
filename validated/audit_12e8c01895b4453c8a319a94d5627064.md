### Title
Unbounded Growth of `DelegatedResourceAccountIndex.toAccounts`/`fromAccounts` Lists via Repeated `DelegateResourceContract` Calls - (File: `actuator/src/main/java/org/tron/core/actuator/DelegateResourceActuator.java`)

### Summary
`DelegateResourceActuator` lets any account holder delegate as little as 1 TRX of frozen bandwidth/energy to an arbitrary receiver address. Each successful delegation unconditionally appends the receiver to the owner's `DelegatedResourceAccountIndexCapsule.toAccounts` list (and the owner to the receiver's `fromAccounts` list), with no cap on the number of distinct entries and no deduplication beyond what the caller chooses to do. This mirrors the CVE-2016-10724 bug class: an attacker-controlled operation causes an in-protocol data structure (here a protobuf-backed list persisted per account, analogous to Bitcoin's infinitely-growing alert map) to grow without bound, and the entire structure is loaded into memory as a single object whenever it is read.

### Finding Description
`DelegateResourceActuator.validate()` only checks that the delegated balance is `>= 1 TRX` and that receiver/owner addresses are valid; it performs no check on how many distinct receivers an owner has already delegated to: [1](#0-0) 

On execution, `delegateResource()` calls `delegatedResourceAccountIndexStore.delegateV2(...)`, which (per `DelegatedResourceAccountIndexCapsule.addToAccount`) unconditionally appends to the protobuf list with no size limit: [2](#0-1) 

The same unbounded-append pattern exists in the VM-native path `DelegateResourceProcessor.delegateResource()`, reachable from smart-contract calls to the freeze/delegate precompiled native contract: [3](#0-2) 

Because the minimum delegation amount is only 1 TRX, an attacker who freezes a modest amount of TRX for bandwidth/energy can issue a very large number of cheap `DelegateResourceContract` transactions, each targeting a freshly generated receiver address, causing the owner's (and correspondingly many receivers') `DelegatedResourceAccountIndex` list to grow without bound. Unlike the JSON-RPC filter maps in `TronJsonRpcImpl` (`eventFilter2Result`, `blockFilter2Result`), which are explicitly capped via `maxLogFilterNum`/`maxBlockFilterNum` and tested for exceed-limit behavior: [4](#0-3) 
there is no analogous size guard anywhere in `DelegateResourceActuator` or `DelegatedResourceAccountIndexCapsule`.

### Impact Explanation
Every query of the index (e.g., via `GetDelegatedResourceAccountIndex`/`GetDelegatedResourceAccountIndexV2` API paths into `Wallet`) deserializes and returns the entire list as one object. As the list grows unbounded, per-account state size and serialization cost grow without limit, degrading node memory/CPU on every read and increasing on-chain storage size proportional to attacker-issued transactions. This is a resource-exhaustion/DoS vector reachable by any funded but otherwise unprivileged account, consistent with the "memory exhaustion via unbounded map/list growth" bug class of CVE-2016-10724, though the practical severity is bounded by the cost of issuing many transactions (bandwidth/energy fees), which is a mitigating factor not present in the original Bitcoin alert-key bug.

### Likelihood Explanation
Any account that has frozen at least 1 TRX worth of bandwidth or energy for V2 can trigger this by sending repeated `DelegateResourceContract` transactions to distinct newly generated receiver addresses. No special privilege, witness/SR role, or contract deployment is required — this is reachable purely through standard signed transactions.

### Recommendation
Add an explicit cap (mirroring `jsonrpc.maxLogFilterNum`-style bounds) on the number of distinct entries permitted in `DelegatedResourceAccountIndex.toAccounts`/`fromAccounts` per account, enforced in `DelegateResourceActuator.validate()` (and the corresponding VM native `DelegateResourceProcessor` path) before appending a new entry, rejecting the transaction once the limit is reached.

### Proof of Concept
1. Freeze a small amount of TRX for bandwidth/energy (V2) on an owner account to obtain delegable balance.
2. In a loop, generate N fresh receiver addresses and submit `DelegateResourceContract` transactions from the owner to each, each delegating the 1 TRX minimum.
3. Observe that `DelegatedResourceAccountIndexStore.getV2Index(owner)` (`getIndex` for V1) returns a `toAccounts` list whose size grows linearly and unbounded with N, with no validation error or rejection at any point, as confirmed by the existing test pattern that exercises multi-delegation growth: [5](#0-4) 

**Note:** I was unable to fully verify within the available iterations whether any global/config-level cap (e.g., in `DynamicPropertiesStore` or `common/reference.conf`) restricts the total number of delegation entries per account, since the search results only showed size caps for JSON-RPC filters and no equivalent for `DelegatedResourceAccountIndex`. A Devin session with full repository access would be needed to conclusively confirm the absence of such a limit before treating this as fully validated.

    long duration = 3;

    String[] RECEIVE_ADDRESSES = new String[RECEIVE_COUNT + 1];

            ByteString.copyFrom(ByteArray.fromHexString(OWNER_ADDRESS)));

      ECKey ecKey = new ECKey(Utils.getRandom());
      RECEIVE_ADDRESSES[i] = ByteArray.toHexString(ecKey.getAddress());
      if (i != RECEIVE_COUNT) {
        ownerIndexCapsule.addToAccount(ByteString.copyFrom(ecKey.getAddress()));
      }
    }
    dbManager.getDelegatedResourceAccountIndexStore().put(
        ByteArray.fromHexString(OWNER_ADDRESS), ownerIndexCapsule);
    AccountCapsule receiverCapsule =
        new AccountCapsule(
            ByteString.copyFromUtf8("receiver"),
            ByteString.copyFrom(ByteArray.fromHexString(RECEIVE_ADDRESSES[RECEIVE_COUNT])),
            AccountType.Normal,
            initBalance);
    dbManager.getAccountStore().put(receiverCapsule.getAddress().toByteArray(), receiverCapsule);

    TransactionResultCapsule ret = new TransactionResultCapsule();
    FreezeBalanceActuator actuator = new FreezeBalanceActuator();
    actuator.setChainBaseManager(dbManager.getChainBaseManager())
        .setAny(getDelegatedContractForBandwidth(
            OWNER_ADDRESS, RECEIVE_ADDRESSES[RECEIVE_COUNT], frozenBalance, duration));
    try {
      ownerIndexCapsule = dbManager
          .getDelegatedResourceAccountIndexStore().getIndex(ByteArray.fromHexString(OWNER_ADDRESS));
      List<ByteString> beforeList = ownerIndexCapsule.getToAccountsList();
      actuator.validate();
      actuator.execute(ret);

      //check DelegatedResourceAccountIndex convert
      ownerIndexCapsule = dbManager
          .getDelegatedResourceAccountIndexStore().get(ByteArray.fromHexString(OWNER_ADDRESS));
      Assert.assertNull(ownerIndexCapsule);

      ownerIndexCapsule = dbManager
          .getDelegatedResourceAccountIndexStore().getIndex(ByteArray.fromHexString(OWNER_ADDRESS));
      Assert.assertEquals(0, ownerIndexCapsule.getFromAccountsList().size());
      List<ByteString> tmpList = ownerIndexCapsule.getToAccountsList();
      Assert.assertEquals(RECEIVE_COUNT + 1, ownerIndexCapsule.getToAccountsList().size());

        Assert.assertEquals(beforeList.get(i), tmpList.get(i));
      }
