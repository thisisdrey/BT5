### Title
Predictable `@cluster` Replica/Pool Paths Allow Repository-Creation Front-running / DoS - ([File: internal/gitaly/storage/repository_path.go])

### Summary
Praefect derives the on-disk storage path for every repository and object pool solely from the sequential, numeric repository ID via `DeriveReplicaPath`/`DerivePoolPath`, embedding the plaintext ID in the path. Because repository IDs are monotonically incrementing and easily observable/guessable by any user who can create repositories, an attacker can pre-create a directory at the future replica/pool path of a not-yet-created repository, causing the legitimate repository/fork/pool creation for that ID to fail — the same "front-run to block state-changing creation" bug class described in the TaikoL1 `verifyProof()` report, where a stateful operation identified by a guessable/predictable key can be won by an unprivileged party ahead of the intended caller.

### Finding Description
`DeriveReplicaPath`/`DerivePoolPath` compute the storage path as `@cluster/repositories/<h0>/<h1>/<repositoryID>` (or `@cluster/pools/...`), where `<h0>,<h1>` are just the first two hex bytes of `sha256(strconv.Itoa(repositoryID))` used only for directory fan-out, and the trailing path component is the **literal decimal repository ID**, not a secret hash: [1](#0-0) 

`RouteRepositoryCreation` reserves the next `RepositoryID` from Praefect's datastore sequence and immediately derives the deterministic replica path from it before Gitaly creates anything on disk: [2](#0-1) 

Repository IDs are assigned from a simple auto-incrementing sequence (`repository_id`), which any authenticated Gitaly/Praefect client that creates repositories (fork, import, project creation, `CreateObjectPool`) observes and can extrapolate to predict the ID that will be assigned to the *next* repository created by someone else.

The repository/pool-creation RPC path (`CreateRepository`, `CreateFork`, `CreateRepositoryFromBundle`, `CreateRepositoryFromURL`, `CreateObjectPool`, `ReplicateRepository`) explicitly tolerates a pre-existing directory at the target path only in narrow cases and otherwise fails outright once the target path is occupied: [3](#0-2) [4](#0-3) 

This mirrors the report's bug class exactly: a stateful, ID-keyed operation (`verifyProof()`/instance replacement) can be triggered ahead of time by an unprivileged actor using a guessable key, causing the *intended* caller's operation on that same key to revert/fail — here, the "key" is the sequential `repositoryID` rather than an SGX instance address, but the mechanics (predict future state key → occupy it early → legitimate creation fails) are the same.

### Impact Explanation
If an attacker can pre-create (or place a stale lock/directory) at the predicted `@cluster/repositories/.../<id>` (or `@cluster/pools/.../<id>`) path shortly before Praefect assigns that same ID to a legitimate fork/import/project, the subsequent `repoutil.Create` invocation will fail with `AlreadyExists`/`FailedPrecondition` ("repository exists already" / "target path exists already"), denying creation of that specific project, fork, or object pool. This is a targeted, repeatable denial-of-service against repository/fork/object-pool creation for victims whose upcoming repository ID can be predicted, without requiring any credentials scoped to the victim's project.

### Likelihood Explanation
Exploitability hinges on (a) the ability of an ordinary/low-privilege client to invoke repository-creating RPCs with an arbitrary `RelativePath` under `@cluster/...`, and (b) accurately predicting a target repository ID before it is reserved. Repository IDs are sequential and can typically be inferred with reasonable precision by an actor who is themselves actively creating repositories/forks on the instance (observing consecutive IDs), making short-window races plausible, particularly against automated/predictable creation flows (e.g., forking, imports, or object pool creation for freshly forked projects, which happen in a tight sequence). The `@cluster` prefix and its structure are also publicly documented in this codebase, which lowers the bar for constructing the exact target path.

### Recommendation
- Do not derive publicly-computable storage paths solely from a sequential numeric ID; incorporate a per-repository random/secret component (as Rails' `@hashed`/`@pools` scheme already does using a full SHA256 of an unpredictable value) so the future path cannot be guessed in advance.
- Reserve/atomically claim the target path and repository record together (closing the known "assignments created before repository creation" gap referenced in the code) so that a pre-existing directory cannot silently occupy a not-yet-reserved slot: [5](#0-4) 
- Restrict which callers may specify `@cluster/...` relative paths directly on Gitaly RPCs to trusted internal callers (Praefect only), rather than trusting the relative path supplied in the request.

### Proof of Concept
1. As a low-privilege, authenticated client capable of creating repositories, repeatedly create small repositories/forks and observe the returned/replicated `repository_id` sequence to establish the current counter value `N`.
2. Compute the deterministic future path for the next reservation: `replicaPath = DeriveReplicaPath(N+1)` (or `DerivePoolPath(N+1)` for pools), following the exact algorithm in `deriveDiskPath`: [6](#0-5) 
3. Issue a `CreateRepository`/`CreateRepositoryFromBundle` (or, on a Gitaly node directly, any RPC accepting an arbitrary `Repository.RelativePath`) request targeting `replicaPath` to create an empty/garbage directory at that exact location before the victim's fork/import/pool creation is processed.
4. When the legitimate operation reserves ID `N+1` and Praefect/Gitaly attempt to create the repository at `DeriveReplicaPath(N+1)`, the creation fails because the path is already occupied, reproducing the "preexisting directory" failure path: [7](#0-6) 

Note: full confirmation that an external, non-Praefect-privileged actor can supply arbitrary `@cluster/...` relative paths directly to a Gitaly node (versus this path only being reachable internally from Praefect) could not be fully verified within the indexed code; this should be validated in a live/session-based review of the RPC authorization boundary before treating this as conclusively exploitable end-to-end.

```go
// DeriveReplicaPath derives a repository's disk storage path from its repository ID. The repository ID
// is hashed with SHA256 and the first four hex digits of the hash are used as the two subdirectories to
// ensure even distribution into subdirectories. The format is @cluster/repositories/ab/cd/<repository-id>.
func DeriveReplicaPath(repositoryID int64) string {
	return deriveDiskPath(praefectRepositoryPathPrefix, repositoryID)
}

// DerivePoolPath derives an object pools's disk storage path from its repository ID. The repository ID
// is hashed with SHA256 and the first four hex digits of the hash are used as the two subdirectories to
// ensure even distribution into subdirectories. The format is @cluster/pools/ab/cd/<repository-id>. The pools
// have a different directory prefix from other repositories so Gitaly can identify them in OptimizeRepository
// and avoid pruning them.
func DerivePoolPath(repositoryID int64) string {
	return deriveDiskPath(praefectPoolPathPrefix, repositoryID)
}

func deriveDiskPath(prefixDir string, repositoryID int64) string {
	hasher := sha256.New()
	// String representation of the ID is used to make it easier to derive the replica paths with
	// external tools. The error is ignored as the hash.Hash interface is documented to never return
	// an error.
	hasher.Write([]byte(strconv.FormatInt(repositoryID, 10)))
	hash := hasher.Sum(nil)
	return filepath.Join(prefixDir, fmt.Sprintf("%x/%x/%d", hash[0:1], hash[1:2], repositoryID))
```
