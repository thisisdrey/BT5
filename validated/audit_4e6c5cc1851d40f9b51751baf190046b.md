### Title
Zero-value settlement lets a taker drain a maker's asset for free in exact-match order fills - (File: actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java)

### Summary
`MarketSellAssetActuator.matchSingleOrder` settles TRC10/TRX market orders by computing the counter-amount each side receives via integer division (`MarketUtils.multiplyAndDivide`, which uses `floorDiv`). In the branch that handles an *exact match* between taker and maker remaining quantities, the amount owed back to the maker (`makerBuyTokenQuantityReceive`) is never checked for being zero, unlike the sibling "taker > maker" branch which explicitly guards against and special-cases a zero result.

### Finding Description
In `matchSingleOrder` [1](#0-0) , when `takerBuyTokenQuantityRemain == makerOrderCapsule.getSellTokenQuantityRemain()` (the "taker == maker" exact-match branch): [2](#0-1) 

`makerBuyTokenQuantityReceive` is computed via `MarketUtils.multiplyAndDivide(makerSellRemainQuantity, makerBuyQuantity, makerSellQuantity, ...)`, which performs floor division and can legitimately return `0` when `makerSellRemainQuantity * makerBuyQuantity < makerSellQuantity` [3](#0-2) . Unlike the analogous "taker > maker" branch, which explicitly checks `if (makerBuyTokenQuantityReceive == 0)` and returns the maker's remaining sell tokens instead of completing the trade [4](#0-3) , the "taker == maker" branch has **no such guard**. It unconditionally sets `makerOrderCapsule.setSellTokenQuantityRemain(0)` and marks the maker order `INACTIVE`, then calls `addTrxOrToken(makerOrderCapsule, makerBuyTokenQuantityReceive)` with `makerBuyTokenQuantityReceive == 0`, while the taker still receives the *full* remaining sell-token quantity of the maker's order via `addTrxOrToken(takerOrderCapsule, takerBuyTokenQuantityReceive, takerAccountCapsule)` where `takerBuyTokenQuantityReceive = makerOrderCapsule.getSellTokenQuantityRemain()` (the entire remaining balance, not zero).

`MarketSellAssetActuator.validate()` does not constrain the sell/buy quantity ratio beyond a generic upper bound (`getMarketQuantityLimit()`) [5](#0-4) , so a resting maker order can have an arbitrarily skewed price (e.g., very large `sellTokenQuantity` for a very small `buyTokenQuantity`). As the order is naturally partially filled (or engineered to be partially filled) down to a small remaining sell quantity, the residual amount owed back to the maker rounds down to zero while the maker's entire remaining asset balance is still transferred out to the final matching taker.

### Impact Explanation
An attacker acting as taker can submit a `MarketSellAssetContract` transaction sized to exactly match a victim maker order's tiny remaining sell quantity, extracting the maker's remaining token/TRX balance for free while the maker receives `0` in return. This is unauthorized theft of on-chain funds/assets triggered purely by an ordinary signed transaction from an unprivileged order placer, matching the in-scope "exchange and market order handling" category. Severity is Medium/High depending on achievable ratios and typical remaining-balance sizes, but it is a concrete asset-theft vector, not merely a resource or availability issue.

### Likelihood Explanation
Reaching the vulnerable branch requires: (1) a resting maker order with a skewed sell/buy ratio (attacker can create this ratio unilaterally since no ratio bound is enforced, then let it get partially filled by any takers, or be the sole initial partial-filler), and (2) a final taker transaction whose computed `takerBuyTokenQuantityRemain` exactly equals the maker's tiny remaining quantity. Both conditions are achievable by a single unprivileged actor controlling transaction inputs, and the precise-equality requirement is a deterministic integer computation the attacker can pre-calculate, making exploitation practical rather than merely theoretical.

### Recommendation
Add the same zero-amount guard used in the "taker > maker" branch to the "taker == maker" exact-match branch: if `makerBuyTokenQuantityReceive == 0`, return the maker's remaining sell-token quantity to the maker instead of completing the transfer, or otherwise reject/abort the match rather than transferring the maker's full remaining balance for a zero counter-payment.

### Proof of Concept
1. Maker places `MarketSellAssetContract` selling large `sellTokenQuantity` (token A) for very small `buyTokenQuantity` (e.g., ratio such that `buyTokenQuantity / sellTokenQuantity` is fractional), e.g. `sellTokenQuantity = 1_000_000`, `buyTokenQuantity = 1`.
2. Through one or more prior fills (attacker-controlled or organic), the maker order's `sellTokenQuantityRemain` is reduced to a small value `R` such that `R * buyTokenQuantity < sellTokenQuantity` (e.g., `R = 100` gives `100*1/1_000_000 = 0` after floor division).
3. Attacker submits a taker `MarketSellAssetContract` whose computed `takerBuyTokenQuantityRemain` (via `MarketUtils.multiplyAndDivide`) exactly equals `R`, hitting the `taker == maker` branch in `matchSingleOrder`.
4. `makerBuyTokenQuantityReceive` evaluates to `0`; the code unconditionally sets the maker's remaining quantity to `0` and calls `addTrxOrToken(makerOrderCapsule, 0)`, while the taker receives `R` units of token A via `addTrxOrToken(takerOrderCapsule, R, takerAccountCapsule)` — the attacker obtains the maker's remaining tokens for free.

  public static long multiplyAndDivide(long a, long b, long c, boolean disableMath) {
    try {
      long tmp = multiplyExact(a, b, disableMath);
      return floorDiv(tmp, c, disableMath);
    } catch (ArithmeticException ex) {
      // do nothing here, because we will use BigInteger to compute again
    }

    BigInteger aBig = BigInteger.valueOf(a);
    BigInteger bBig = BigInteger.valueOf(b);
    BigInteger cBig = BigInteger.valueOf(c);

    return aBig.multiply(bBig).divide(cBig).longValue();
  }
