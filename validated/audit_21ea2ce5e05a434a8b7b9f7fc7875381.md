### Title
Unbounded, unauthenticated queue growth before signature verification enables memory-exhaustion DoS in `Manager.pushTransaction` - (File: `framework/src/main/java/org/tron/core/db/Manager.java`)

### Summary
The reported OpenSSH bug (CVE-2025-26466) is a classic "allocate-before-verify" pattern: a per-request object is queued and only released after an expensive handshake step completes, allowing unauthenticated clients to grow the queue unboundedly. java-tron's transaction broadcast path in `Manager.pushTransaction` has the same structural flaw: every transaction submitted via `Wallet.broadcastTransaction` is unconditionally added to an **unbounded** `LinkedBlockingQueue` before signature verification is performed, and the pending-size guard that is supposed to bound this queue is checked in a separate, non-atomic step in the caller.

### Finding Description
`Manager` declares `pushTransactionQueue` with no capacity bound: [1](#0-0) 

In `pushTransaction`, the incoming `TransactionCapsule` is added to this unbounded queue **before** `trx.validateSignature(...)` is invoked; the entry is only removed from the queue in the `finally` block after validation/execution completes (success or failure): [2](#0-1) [3](#0-2) 

The only protection against unbounded growth, `Manager.isTooManyPending()`, is invoked by `Wallet.broadcastTransaction` **before** calling `dbManager.pushTransaction(trx)`, as a separate check-then-act step with no shared lock between the check and the subsequent enqueue: [4](#0-3) [5](#0-4) 

Because this check-and-enqueue is not atomic across threads (the HTTP/gRPC/JSON-RPC servlet layer processes many concurrent broadcast requests, each on its own thread), multiple concurrent `broadcastTransaction` calls can all observe `isTooManyPending() == false` at the same instant and then all proceed to add their (potentially near-max-size, ~500KB, expensive-to-verify) transactions to `pushTransactionQueue` simultaneously — exactly mirroring the SSH "pong queued before kex completes" root cause. Signature verification (`validateSignature`) is CPU-bound (ECDSA/other crypto), so a burst of concurrent large transactions can sit in the unbounded queue for a non-trivial time before being validated and evicted, letting the queue size balloon far past the configured `maxTransactionPendingSize` (default 2000) before the cap has any effect.

### Impact Explanation
An unauthenticated/unprivileged transaction broadcaster who opens many concurrent connections and submits maximum-size transactions can force `pushTransactionQueue` to grow well beyond its intended bound during the verification window, consuming heap proportional to (concurrent connections × max transaction size). Sustained abuse can drive the node to OutOfMemoryError, crashing or hanging the full node / API-serving node — a concrete node-crash/halt DoS, matching the accepted impact categories (node crash or an API the node can no longer serve).

### Likelihood Explanation
The `broadcastTransaction` RPC is a standard, unauthenticated entry point exposed via gRPC/HTTP for any client. Triggering the race only requires ordinary concurrent connections and standard-sized signed transactions (no privileged access, no malicious peer/SR/witness role needed), making this readily reachable by any external client capable of connecting to the node's public API.

### Recommendation
Make the pending-size check and the enqueue atomic (e.g., perform the size check and `pushTransactionQueue.add`/`pendingTransactions.add` under the same lock used elsewhere in `pushTransaction`, or use a bounded queue with `offer`/rejection instead of `add`), and consider bounding `pushTransactionQueue` itself with a fixed capacity so it cannot grow past the configured cap regardless of concurrent callers.

### Proof of Concept
1. From an unauthenticated client, open N concurrent gRPC/HTTP connections to the node's `broadcastTransaction` endpoint (N well below any per-connection limit).
2. Simultaneously submit N distinct, validly-formed but large (near `TRANSACTION_MAX_BYTE_SIZE`) signed transactions.
3. Because `Wallet.broadcastTransaction`'s `dbManager.isTooManyPending()` check [4](#0-3)  races against `Manager.pushTransaction`'s unconditional `pushTransactionQueue.add(trx)` [6](#0-5) , all N requests can pass the check before any of them finish signature validation and get removed, causing `pushTransactionQueue` to temporarily hold N × max-tx-size bytes.
4. Repeating this burst continuously (many attackers/connections) drives sustained memory growth beyond `maxTransactionPendingSize`'s intended cap, culminating in OOM/node instability.

Note: I could not verify the exact numeric formula inside `isTooManyPending()`/`getCachedTransactionSize()` (the method body itself was not returned by search, only its call sites and tests), so the precise threshold arithmetic is inferred from `ManagerTest.testIsTooManyPendingIncludesPushQueue` behavior rather than direct inspection of the method body.
