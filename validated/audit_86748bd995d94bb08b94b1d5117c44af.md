### Title
Intra-batch write-write lock check in `AccountLocks::try_lock_transaction_batch` operates against stale state, allowing two writable-conflicting transactions in one batch to both return `Ok(())` - ([File: accounts-db/src/account_locks.rs])

### Summary
`try_lock_transaction_batch` validates every transaction's account keys in a first pass using `can_lock_accounts`, but that pass reads `self`'s lock state without ever mutating it, so it only detects conflicts with locks that existed *before* the batch was submitted. It never detects conflicts *between* transactions inside the same batch. The second pass then unconditionally calls `lock_accounts` for every transaction still marked `Ok`, incrementing the lock counters without re-validating, so two transactions in the same batch that both write the same account both come back `Ok(())`.

### Finding Description
`try_lock_transaction_batch` is implemented as two independent passes: [1](#0-0) 

Pass 1 (`validated_batch_keys.iter_mut().for_each(...)`) calls `self.can_lock_accounts(keys.clone())` for each transaction, but `can_lock_accounts` only *reads* `self.write_locks`/`self.readonly_locks`: [2](#0-1) 

`self` is never mutated during pass 1, so when transaction A and transaction B in the same batch both write the same key `X`, both checks run against the identical pre-batch lock state and both succeed.

Pass 2 (`.into_iter().map(|available_keys| available_keys.map(|keys| self.lock_accounts(keys)))`) then unconditionally locks every transaction still marked `Ok`, without re-checking for conflicts: [3](#0-2) 

For A, `lock_write(X)` sets `write_locks[X] = 1` and returns `Ok(())`. For B, immediately afterward, `lock_write(X)` increments `write_locks[X] = 2` and *also* returns `Ok(())`, because `lock_accounts`/`lock_write` never check `can_write_lock` before locking. Both transactions in the batch are reported as successfully locked despite an intra-batch write-write conflict.

This is reachable from `Accounts::lock_accounts`, which is what `Bank::try_lock_accounts_with_results` / `prepare_sanitized_batch_with_results` call when constructing a `TransactionBatch` for leader packet processing in `consumer.rs`: [4](#0-3) [5](#0-4) 

The existing test suite masks this bug: `test_accounts_locks_intrabatch_conflicts` has a block explicitly labeled `// ww conflict in-batch succeeds` but it actually constructs `[w_tx, r_tx]` (a write/read pair, not two writers), never exercising a true write-write same-key-in-batch case: [6](#0-5) 

No sigverify, dedup, or QoS stage deduplicates writable-account collisions within a batch; those stages only check signatures and cost limits, not account-lock conflicts, and `validate_account_locks`/`has_duplicates` only reject duplicate keys *within a single transaction's own account list*, not across transactions in a batch: [7](#0-6) 

### Impact Explanation
Two attacker-crafted transactions sharing a writable account key can both be reported as lock-acquired by `AccountLocks`, breaking the fundamental invariant that conflicting writable-account transactions cannot be concurrently held-locked. Downstream (`Bank::load_and_execute_transactions`/execution and commit code) relies on this lock as the sole mechanism preventing concurrent modification of the same account; a violated invariant here corresponds to the "invalid block due to inconsistent-with-sequential-execution entries" bounty category, since the batch's committed results can diverge from what strictly-sequential per-account execution would produce.

### Likelihood Explanation
This requires only two sanitized, signature-valid transactions that share a writable account key (e.g., identical fee payer or same target writable account) sent together in one packet batch by an unstaked remote client to the leader's TPU. No special privileges, staking, or timing races beyond normal batch submission are needed, and the flaw is deterministic (not probabilistic) given the code's two-phase check pattern above.

### Recommendation
Merge the check-and-lock into a single pass so that each transaction's lock validation is performed against the state as mutated by the previous transactions of the same batch — i.e., call `can_lock_accounts` immediately followed by `lock_accounts` (or a combined check-and-lock helper) for each transaction sequentially in one loop, rather than doing a global pre-check pass followed by an unconditional lock pass.

### Proof of Concept
```rust
// accounts-db/src/account_locks.rs (add to `mod tests`)
#[test]
fn test_intrabatch_write_write_conflict_both_ok_is_a_bug() {
    let mut locks = AccountLocks::default();
    let x = Pubkey::new_unique();

    // Two transactions in the SAME batch, both writing to `x`.
    let tx_a_keys = vec![(&x, true)].into_iter();
    let tx_b_keys = vec![(&x, true)].into_iter();

    let batch = vec![Ok(tx_a_keys), Ok(tx_b_keys)];
    let results = locks.try_lock_transaction_batch(batch);

    // Correct sequential semantics require exactly one Ok and one
    // Err(AccountInUse) for overlapping writable keys in the same batch.
    let ok_count = results.iter().filter(|r| r.is_ok()).count();
    assert_eq!(
        ok_count, 1,
        "expected exactly one Ok result for conflicting writable keys, got: {results:?}"
    );
}
```
Running this against current `try_lock_transaction_batch` fails: both entries come back `Ok(())` and `write_locks[x]` ends at `2`, demonstrating both transactions were treated as concurrently write-locked on the same account within a single batch.

    pub fn try_lock_transaction_batch<'a>(
        &mut self,
        mut validated_batch_keys: Vec<
            TransactionResult<impl Iterator<Item = (&'a Pubkey, bool)> + Clone>,
        >,
    ) -> Vec<TransactionResult<()>> {
        validated_batch_keys.iter_mut().for_each(|validated_keys| {
            if let Ok(keys) = validated_keys.as_ref()
                && let Err(e) = self.can_lock_accounts(keys.clone())
            {
                *validated_keys = Err(e);
            }
        });

        validated_batch_keys
            .into_iter()
            .map(|available_keys| available_keys.map(|keys| self.lock_accounts(keys)))
            .collect()
    }

    fn can_lock_accounts<'a>(
        &self,
        keys: impl Iterator<Item = (&'a Pubkey, bool)>,
    ) -> TransactionResult<()> {
        for (key, writable) in keys {
            if writable {
                if !self.can_write_lock(key) {
                    return Err(TransactionError::AccountInUse);
                }
            } else if !self.can_read_lock(key) {
                return Err(TransactionError::AccountInUse);
            }
        }

        Ok(())
    }

    pub fn lock_accounts<'a>(
        &self,
        txs: impl Iterator<Item = &'a (impl SVMMessage + 'a)>,
        results: impl Iterator<Item = Result<()>>,
        tx_account_lock_limit: usize,
    ) -> Vec<Result<()>> {
        // Validate the account locks, then get keys and is_writable if successful validation.
        // We collect to fully evaluate before taking the account_locks mutex.
        let validated_batch_keys = txs
            .zip(results)
            .map(|(tx, result)| {
                result
                    .and_then(|_| validate_account_locks(tx.account_keys(), tx_account_lock_limit))
                    .map(|_| TransactionAccountLocksIterator::new(tx).accounts_with_is_writable())
            })
            .collect::<Vec<_>>();

        let account_locks = &mut self.account_locks.lock().unwrap();
        account_locks.try_lock_transaction_batch(validated_batch_keys)
    }
