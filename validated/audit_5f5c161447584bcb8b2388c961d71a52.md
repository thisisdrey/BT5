### Title
Attacker can fill a victim's per-account token set with dust deposits/transfers, blocking them from depositing new collateral or opening new debt positions - (File: contracts/Pool.sol)

### Summary
The `Pool` enforces a hardcoded `MAX_TOKENS_PER_USER = 30` cap on the combined length of `debtTokensOfAccount` and `depositTokensOfAccount` via the `onlyIfAdditionWillNotReachMaxTokens` modifier. [1](#0-0)  Entries are added to a *recipient's* set whenever their `DepositToken` balance goes from 0 to positive — whether via `deposit(amount_, account_)`, `transfer`, or liquidation `seize` credit. [2](#0-1)  An attacker can therefore push entries into a victim's set by dust-depositing (on-behalf) or dust-transferring every whitelisted `DepositToken` to the victim until the combined count hits 30, after which `Pool.addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` revert with `UserReachedMaxTokens`. [3](#0-2) 

### Finding Description
The invariant "the token-count cap reflects tokens the user actually wants" breaks because the set is populated by the balance-change hook, not by user intent. Unlike the OpenQ bug (where the array never shrank), `MappedEnumerableSet.remove` does shrink the count — but only when the victim's balance returns to zero, which requires the victim to actively transfer each dust token out, and the attacker can re-fill freed slots with new dust in the same or next block. The same griefing vector also hits the *liquidator*: `Pool.liquidate` → `DepositToken.seize` mints seized `msdTOKEN` to the liquidator, which calls `addToDepositTokensOfAccount(liquidator)`; a targeted liquidator whose set is full cannot execute liquidations involving deposit tokens they don't already hold.

### Impact Explanation
A victim with a full set (30 combined entries) cannot deposit any *new* collateral type (`deposit` reverts when the hook runs) and cannot mint any *new* synthetic asset type (debt-token addition reverts). For a user near the liquidation boundary, this directly blocks the standard remedy — depositing a different collateral — so their existing collateral is exposed to liquidation, constituting temporary freezing/denial of the deposit liveness guarantee. Recovery requires the victim to manually clear entries one at a time while the attacker can cheaply re-fill them.

### Likelihood Explanation
Reachable entirely by an unprivileged EOA through public entry points (`DepositToken.deposit`, `DepositToken.transfer`); no privileged role needed. Constraints: the attack needs enough distinct whitelisted `DepositToken`s to fill the victim's remaining slots (global `depositTokens` is itself capped at `MAX_TOKENS_PER_USER = 30`, so feasibility depends on the deployed configuration and the victim's existing entries). [4](#0-3)  The victim can partially mitigate by sending dust away, so the DoS is contestable rather than strictly permanent — consistent with a medium-severity liveness/griefing issue.

### Recommendation
Track eligibility separately from incidental balance: either (a) maintain an explicit opt-in set for collateral counting, or (b) enforce a minimum meaningful balance (e.g., a USD-denominated dust floor) before calling `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount`, or (c) raise/soften the cap so that forced dust entries cannot exhaust it. Also consider making `seize` credit liquidation proceeds without adding to the liquidator's set cap, or exempting already-listed tokens.

### Proof of Concept
Hardhat-style sketch (contracts use existing test fixtures):

```ts
// Victim: alice. Assume pool whitelists >= N deposit tokens such that
// alice's existing (debt + deposit) entries + N == MAX_TOKENS_PER_USER (30).

// 1) Attacker deposits 1 wei of underlying on behalf of alice for each
//    deposit token alice doesn't already hold:
for (const dt of depositTokensAliceDoesntHave) {
  await underlying.approve(dt.address, 1);
  await dt.deposit(1, alice.address); // balance 0 -> >0 => addToDepositTokensOfAccount(alice)
}
// Alternatively: await dt.transfer(alice.address, 1) from attacker-held msdTOKEN.

// 2) alice now has 30 entries; any new collateral type reverts:
await expect(newDepositToken.connect(alice).deposit(1e18, alice.address))
  .to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');

// 3) Any new debt position reverts the same way via addToDebtTokensOfAccount,
//    and a liquidator with a full set reverts in DepositToken.seize.
```

Fork reproduction would require counting the deployed `getDepositTokens()` list on the target chain to confirm the cap is reachable for a victim's residual slot count.

Uncertainty note: I could not fully enumerate the number of whitelisted deposit/debt tokens on each deployed chain or verify `DepositToken.deposit`'s exact signature ordering beyond the test usage `deposit(toDeposit, bob.address)` at `test/DepositToken.test.ts:477`; if deployed deposit tokens plus a victim's debt tokens cannot reach 30, the attack is not feasible on that chain.
