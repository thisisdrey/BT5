### Title
Single-step account permission (owner) update in `AccountPermissionUpdateActuator` can permanently lock an account with no two-step confirmation - ([File: actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java])

### Summary
`AccountPermissionUpdateContract`, processed by `AccountPermissionUpdateActuator`, lets an account holder overwrite the account's `Owner`, `Witness`, and `Active` permissions — including the entire key/threshold set that controls the account — in a single atomic transaction. There is no two-step "propose then claim" pattern analogous to `Ownable2Step`: the new owner keys take effect immediately in `execute()`, with no confirmation step from the new key holders before the old permission is discarded.

### Finding Description
`AccountPermissionUpdateActuator.execute()` unpacks the contract and immediately calls `account.updatePermissions(...)`, replacing the account's owner permission in the same transaction that is validated: [1](#0-0) 

`validate()` and the helper `checkPermission()` only check structural correctness of the new permission (key count, distinctness, address format validity via `DecodeUtil.addressValid`, threshold vs. weight sum, name length, parent id, and operations bitmap for Active permissions): [2](#0-1) 

None of these checks verify that the submitted key addresses are actually controlled by a private key the sender has proven possession of beyond format validity, and there is no mechanism requiring the proposed new owner key(s) to countersign or "claim" the permission change before it takes effect, unlike the two-step ownership transfer recommended in the reference report. Once `execute()` runs, `accountStore.put(ownerAddress, account)` commits the new permission set irrevocably in that same transaction: [3](#0-2) 

### Impact Explanation
Because the owner permission is the root of authority for the account (it is required to sign further `AccountPermissionUpdateContract` transactions and other owner-only operations), a single mistaken or malformed transaction — e.g., a typo'd key address, an inaccessible key, or a threshold/weight configuration for which the sender does not actually hold sufficient keys — permanently locks the account: no future transaction can meet the new owner threshold, and the account's funds and permissions become irrecoverable. This matches "permanent freezing of funds" for the affected account, reachable directly by any account holder issuing a single signed `AccountPermissionUpdateContract` transaction (broadcastable by any unprivileged transaction broadcaster, subject to `AllowMultiSign` being enabled) with no admin/SR/witness privilege required.

### Likelihood Explanation
Any account with multi-sign enabled (`getAllowMultiSign() != 1` check) can trigger this by broadcasting a single `AccountPermissionUpdateContract` transaction: [4](#0-3)  No second confirmation transaction from the newly designated keys is required, so operator/user error (a common real-world occurrence, as cited in the analogous report) is sufficient to trigger irreversible loss of control — no attacker collusion needed, only a single mistaken broadcast.

### Recommendation
Introduce a two-step permission update flow for the `Owner` permission: first require submission of the proposed new owner permission (pending state), then require a confirmation transaction signed under the proposed new permission before it is committed to `AccountStore`, mirroring the `Ownable2Step` pattern referenced in the external report.

### Proof of Concept
1. Account A has multi-sign enabled and a normal owner permission with a single key `K1`.
2. A broadcasts an `AccountPermissionUpdateContract` transaction (signed with `K1`) setting the new `Owner` permission to a single key `K2`, where `K2` is a typo'd/incorrect address or a key whose private key A does not actually possess.
3. `AccountPermissionUpdateActuator.validate()` passes because `K2` is a structurally valid address (`DecodeUtil.addressValid`) and all other numeric checks pass.
4. `execute()` commits the new permission immediately via `account.updatePermissions(...)` and `accountStore.put(...)`.
5. No further transaction can reach the new owner threshold since A does not control `K2`; the account is now permanently unable to execute any owner-permission-gated action (including reverting this very permission change), freezing account funds/authority.
