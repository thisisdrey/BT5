### Title
Quadratic DB-row-visit blowup in mempool `/v2/mempool/query` streaming bypasses `mempool_max_tx_query` bound - (File: `stackslib/src/net/api/postmempoolquery.rs`, `stackslib/src/core/mempool.rs`)

### Summary
`StacksMemPoolStream::generate_next_chunk` caps the SQL `LIMIT` for each `static_find_next_missing_transactions` call using the *remaining tx-emission budget* (`max_txs - num_txs`), not a global row-visited budget. Because `num_txs` only increments when a transaction is actually emitted (not per row scanned), a crafted `MemPoolSyncData::TxTags` filter that matches long runs of real txids interleaved with rare misses can force each of up to `max_txs` successive chunk-generation calls to scan close to `max_txs` rows each, causing total DB rows visited in one HTTP request to approach `max_txs²` instead of the intended `max_txs`.

### Finding Description
`try_handle_request` (`postmempoolquery.rs:266-317`) reads `max_txs = network.connection_opts.mempool_max_tx_query` and constructs `StacksMemPoolStream::new(mempool_db, mempool_query, max_txs, coinbase_height, page_id)` [1](#0-0) . `generate_next_chunk` (lines 126-215) computes `remaining = self.max_txs.saturating_sub(self.num_txs)` and calls `static_find_next_missing_transactions(..., 1, remaining)` — passing a hardcoded per-call tx cap of `1` and `remaining` as the SQL row-visit cap (`max_run`) [2](#0-1) .

Inside `static_find_next_missing_transactions` (`mempool.rs:2891-2966`), the SQL statement uses `LIMIT ?3` bound to `max_run`, and the in-loop guard `if num_rows_visited >= max_run { break; }` enforces that each *single call* visits at most `max_run` rows [3](#0-2) . The row is only skipped (not counted toward `ret`) if `contains` is true (i.e., attacker's `TxTags`/bloom filter already claims to have it); the tx is only pushed to `ret`, and the emitted-tx cap `ret.len() >= max_txs` (here fixed at `1`) checked, once a genuinely non-matching row is found [4](#0-3) .

Because `self.num_txs` in `generate_next_chunk` increases only by the count of *emitted* transactions (`next_txs.len()`, effectively 0 or 1 per call), and `remaining` is recomputed from `self.num_txs` each call, `remaining` does **not** shrink to account for rows already scanned-and-skipped in prior calls. An attacker who crafts a `TxTags` filter such that most real txids in the randomized-hash order are reported as "already have" (`contains == true`) but a few are not, forces each `generate_next_chunk` call to scan up to `remaining` (~`max_txs`) rows before hitting the rare miss that lets it emit one tx and advance `last_randomized_txid`. Since the stream keeps calling `generate_next_chunk` until `num_txs >= max_txs`, this can repeat up to `max_txs` times, each time re-scanning up to ~`max_txs` rows, yielding total rows visited on the order of `max_txs²` for the whole HTTP request — the row-visit bound is only enforced *per call*, not cumulatively across the stream, so the effective compute cost scales quadratically with the configured cap rather than linearly.

### Impact Explanation
This is a bounded compute DoS on a read endpoint (`/v2/mempool/query`, no auth required, confirmed by `security: []` in the OpenAPI spec) [5](#0-4) . A single crafted request can force the node to visit roughly `mempool_max_tx_query²` mempool DB rows instead of the intended `mempool_max_tx_query`, tying up a DB read handle for substantially longer than the operator's configured cap anticipates. This does not achieve a full unbounded table scan (the SQL `LIMIT` still caps each individual call), but it breaks the intended linear relationship between the configured cap and per-request DB work, which is the "BOUNDS-style" fault described. Repeatable per request; cost scales with mempool size up to the quadratic bound.

### Likelihood Explanation
No authentication or special peer state required — only a large enough mempool (which any node naturally accumulates) and knowledge of a set of real txids to build the "false positive" `TxTags` list (an attacker can learn plausible in-mempool txids by observing normal mempool sync traffic or the network's own inventory gossip). `mempool_max_tx_query` is operator-configurable but even moderate defaults amplify request cost quadratically. Attack cost is a single POST request; result is repeatable at will.

### Recommendation
Track a single, request-scoped "rows visited so far" counter in `StacksMemPoolStream` and pass `max_txs.saturating_sub(total_rows_visited)` (not `max_txs.saturating_sub(num_txs)`) as `max_run` to `static_find_next_missing_transactions`, so cumulative DB rows visited across the whole stream — not just emitted transactions — is capped at `mempool_max_tx_query`.

### Proof of Concept
Rust test in `stackslib::net::api::tests::postmempoolquery`:
1. Populate a `MemPoolDB` with `N` (e.g., 100,000) transactions.
2. Build a `MemPoolSyncData::TxTags` set that matches every txid except roughly one per `max_txs`-sized window (crafted via `TxTag::from(seed, &txid)` for all but sparse misses), and set `max_txs` small (e.g., 50).
3. Drive `StacksMemPoolStream::generate_next_chunk` in a loop (as in `test_stream_mempool_txs`), instrumenting/wrapping `MemPoolDB::static_find_next_missing_transactions` (or counting via a modified test hook) to sum `num_rows_visited` returned across all calls.
4. Assert `total_rows_visited <= max_txs` — this assertion fails, demonstrating total visited rows approaches `max_txs * max_txs` rather than being bounded by `max_txs`.
