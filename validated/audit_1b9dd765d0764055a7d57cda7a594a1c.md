Audit Report

## Title
Unconditional curator-deposit charge in `accept_curator` double-locks funds when parent curator accepts the same role for a child-bounty - ([File: substrate/frame/multi-asset-bounties/src/lib.rs])

## Summary
The `CuratorDeposit` storage item in `pallet-multi-asset-bounties` is documented at [1](#0-0)  as being "charged only once" when the parent curator is also assigned to a child-bounty, but the `accept_curator` extrinsic unconditionally creates a new `Consideration` deposit on every call, regardless of whether the caller already holds a deposit for the parent bounty. This causes the curator's funds to be reserved twice for the same underlying role when they accept curatorship of both the parent bounty and a child bounty under it.

## Finding Description
The doc-comment on `CuratorDeposit` explicitly states the single-charge invariant [2](#0-1) , but the storage map itself is indexed independently by `(parent_bounty_id, child_bounty_id)` [3](#0-2) , and there is no code path found that checks whether `parent_curator == child_curator` before inserting a new deposit for the child bounty — unlike `pallet-child-bounties`'s `calculate_curator_deposit`, which explicitly returns zero in that scenario. The pallet's own test suite (`accept_curator_works`) asserts that a curator who accepts both parent and child curator roles ends up with `reserved_balance` equal to double the child deposit, confirming the double-charge occurs in practice rather than being merely theoretical.

## Impact Explanation
This is a documentation/implementation mismatch causing excess fund locking beyond what the pallet's own specification promises, rather than theft, unbacked mint, unauthorized origin escalation, or duplicate settlement to a wrong beneficiary — the funds remain correctly reserved from and refundable to the same curator account when the bounty completes or is unassigned. The impact gate calls for issues like "permanent user-fund lock" or "runtime bugs that compromise intended behavior" tied to a concrete corrupted value (balance, beneficiary, nonce, receipt, etc.). Here, the reserved balance is higher than the doc implies, but it is not permanently lost, misdirected, or unrecoverable — it is simply an extra reservation of the curator's own funds, refundable through the normal deposit-release paths (`CuratorDeposit::take` on award/unassign). This weakens the severity significantly relative to what the impact gate targets, since no value is stolen, minted incorrectly, or permanently locked beyond recovery.

## Likelihood Explanation
The scenario (a curator accepting both parent and child curator roles) is reachable through normal, unprivileged extrinsic calls (`propose_curator` + `accept_curator`), and is demonstrated by the pallet's own tests, so it is easily reproducible. However, reachability alone does not establish that this rises to a scoped "impact" under the gate, since it results only in extra self-reservation of the curator's own balance rather than fund theft, misdirected payout, or permanent lock.

## Recommendation
Align `accept_curator` with the documented invariant: check whether the parent-bounty curator equals the child-bounty curator before inserting a new `Consideration` for the child bounty, mirroring `pallet-child-bounties::calculate_curator_deposit`'s zero-deposit special case, or update the doc-comment to accurately reflect that the deposit is charged per bounty (parent and child) rather than once per curator.

## Proof of Concept
1. Fund a parent bounty and have `curator` accept the curator role, reserving `consideration(value)`.
2. Add a child bounty and assign the same `curator` as child-bounty curator via `propose_curator`.
3. Call `accept_curator(parent_bounty_id, Some(child_bounty_id))` as the same curator.
4. Observe `CuratorDeposit(parent_bounty_id, Some(child_bounty_id))` is inserted with a second, independent `Consideration`, and `Balances::reserved_balance(&curator)` increases again — as shown in the existing `accept_curator_works` test in `substrate/frame/multi-asset-bounties/src/tests.rs`.
