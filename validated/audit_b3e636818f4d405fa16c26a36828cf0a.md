### Title
Missing slippage protection in `ExchangeInjectActuator`/`ExchangeWithdrawActuator` allows front-running to force unfavorable liquidity ratios - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`)

### Summary
`ExchangeInjectContract` and `ExchangeWithdrawContract` let an exchange creator add or remove liquidity from a TRON on-chain bancor-style exchange pool. Unlike `ExchangeTransactionContract` (the trade/swap operation), which carries an explicit `expected` field enforced at validation time (`tokenExpected`), the inject/withdraw contracts carry no minimum/maximum bound on the computed `anotherTokenQuant`. Any unprivileged account can submit an `ExchangeTransactionContract` (a swap) that shifts the pool's `firstTokenBalance`/`secondTokenBalance` ratio immediately before the creator's inject/withdraw transaction is packed into a block, forcing the creator's operation to execute at a manipulated ratio with no on-chain check to reject unfavorable execution.

### Finding Description
`ExchangeTransactionActuator.doValidate()` reads the caller-supplied `tokenExpected` and reverts if the actual `anotherTokenQuant` computed from the live pool ratio is less than expected: [1](#0-0) 

This is the correct analog of Uniswap's `amountOutMinimum`/`amountInMaximum` slippage guard that the external report says is missing in `heal`/`costToHeal`.

However, `ExchangeInjectActuator` computes `anotherTokenQuant` purely from the pool's *current* balances at execute time, with no caller-supplied bound to protect against ratio movement between submission and execution: [2](#0-1) 

The validate path likewise only checks `anotherTokenQuant <= 0` and balance-limit ceilings — never a caller-specified expected/min/max value: [3](#0-2) 

The `ExchangeWithdrawContract` execution path exhibits the identical pattern — `anotherTokenQuant` is derived from live pool state with no user-supplied bound to reject unfavorable results: [4](#0-3) 

Any address can freely submit `ExchangeTransactionContract` swaps against the pool (no special permission required) because `ExchangeTransactionActuator` only checks that the caller has sufficient balance/asset, not that they are the pool creator: [5](#0-4) 

Since `ExchangeInjectActuator`/`ExchangeWithdrawActuator` restrict the *caller* to the exchange creator but do not protect against pool-state manipulation by *other* unprivileged accounts occurring between transaction broadcast and block inclusion, an attacker can broadcast a swap transaction designed to land in the same block just before the creator's inject/withdraw transaction, shifting `firstTokenBalance`/`secondTokenBalance` so the creator either deposits far more of one asset than intended for the same proportional injection, or withdraws a smaller share of the paired asset than expected — all without any on-chain mechanism for the creator's transaction to detect and reject the adverse price movement, exactly mirroring the `sqrtPriceLimitX96`/missing `amountOutMinimum` root cause in the reported issue.

### Impact Explanation
A successful front-run forces the exchange creator's inject/withdraw transaction to execute against a manipulated pool ratio, causing them to lock in more of one token than intended (inject) or receive materially less of the paired token than intended (withdraw) — a direct, unrecoverable loss of value for the transaction submitter with no revert path, since neither actuator enforces a caller-specified acceptable bound.

### Likelihood Explanation
Any account can trivially submit `ExchangeTransactionContract` swaps against a given exchange pool with only a valid balance, and TRON's public mempool/ordering makes transaction front-running feasible for MEV-motivated actors observing pending `ExchangeInjectContract`/`ExchangeWithdrawContract` transactions targeting pools with material balances, similar to well-documented AMM sandwich patterns.

### Recommendation
Add caller-supplied minimum/maximum bound fields (analogous to `ExchangeTransactionContract.expected`) to `ExchangeInjectContract` and `ExchangeWithdrawContract`, and enforce them in `ExchangeInjectActuator.doValidate()`/`execute()` and `ExchangeWithdrawActuator.doValidate()`/`execute()` by rejecting the transaction if the pool-ratio-derived `anotherTokenQuant` falls outside the caller's specified tolerance at execution time.

### Proof of Concept
1. Attacker observes a pending `ExchangeInjectContract` from the pool creator for exchange `E` injecting `tokenQuant` of `firstTokenId`.
2. Attacker submits (and gets included first, e.g. via fee/ordering) an `ExchangeTransactionContract` swap against `E` that heavily skews `firstTokenBalance`/`secondTokenBalance`.
3. The creator's `ExchangeInjectActuator.execute()` then computes `anotherTokenQuant` from the now-skewed ratio: [6](#0-5) 
4. The creator's account is debited a disproportionate `anotherTokenQuant` of the second token relative to what they intended when they signed the transaction, with no validation check available to abort — reproducing the "no price-impact protection" bug class from the external report inside java-tron's on-chain exchange feature.
