### Title
HookService RPCs meant only for internal `gitaly-hooks` invocation are reachable on the same authenticated surface as ordinary client RPCs, letting any authorized caller directly invoke hook logic and manipulate unrelated in-flight transactions - (File: internal/gitaly/service/hook/pre_receive.go, internal/gitaly/hook/postreceive.go, proto/hook.proto)

### Summary
`HookService` (`PreReceiveHook`, `PostReceiveHook`, `UpdateHook`, `ReferenceTransactionHook`, `ProcReceiveHook`) is documented and architected to be invoked only by the `gitaly-hooks` binary acting on behalf of a live `git-receive-pack` process, analogous to `receiveCollateral()` being intended for `ActivePool` only. [1](#0-0)  Unlike `SignalPostReceiveReady`, which Gitaly explicitly hardens with a `backchannel.GetPeerID` caller-identity check, none of the other `HookService` RPCs verify that the caller is the trusted `gitaly-hooks` process for a genuine push; they only require the same shared gRPC auth token used for all ordinary client RPCs.

### Finding Description
The `hook.proto` service comment states hooks are "typically invoked via the `gitaly-hooks` binary... to ensure that the actual hook logic is executed in the context of the server." [1](#0-0)  Gitaly's own test suite acknowledges this gap directly: a comment in `pre_receive_test.go` states the `HookService` is being called through Gitaly's *external* API in tests only as a workaround, and that "we should stop serving `HookService` on the external socket given it is a service intended only to be used internally by Gitaly for hook callbacks," linking to gitlab-org/gitaly#3746 as an open issue. [2](#0-1) 

By contrast, Gitaly demonstrates it knows how to correctly restrict an internal-only hook RPC: `SignalPostReceiveReady` explicitly checks `backchannel.GetPeerID(ctx)` and rejects the call with `PermissionDenied` if it did not arrive via Praefect's backchannel. [3](#0-2)  No equivalent caller-identity check exists for `PreReceiveHook`, `PostReceiveHook`, `UpdateHook`, or `ReferenceTransactionHook` — their handlers only validate the repository field, not who is calling. [4](#0-3) [5](#0-4) 

This matters because `PostReceiveHook`'s implementation trusts the `environment_variables` field of the request (fully attacker-suppliable in a direct RPC call) to decode a `HooksPayload`, including a numeric `TransactionID` that is then used to fetch and commit an existing, potentially unrelated, in-flight transaction from the shared `txRegistry`: [6](#0-5) 

If a caller can invoke `PostReceiveHook` directly (as acknowledged as reachable via the external socket) and set an `environment_variables` payload referencing another push's `TransactionID`, it can commit or interfere with a transaction it does not own, similar to how the original `receiveCollateral()` finding let an unprivileged caller mutate state (`_tokens`/`_amounts`) belonging to `StabilityPool` on behalf of `ActivePool`.

### Impact Explanation
An authenticated-but-unprivileged caller (e.g., any GitLab component holding the shared Gitaly auth token, which is the same credential used for ordinary push/pull RPCs) could invoke `PreReceiveHook`/`PostReceiveHook`/`UpdateHook` directly instead of going through the real `git-receive-pack` → `gitaly-hooks` path. This can: (1) trigger Rails `/internal/allowed` and `PostReceive` access-check calls and custom hook execution with attacker-crafted `stdin`/`push_options` unconnected to a real push, and (2) reach into the `PostReceiveRegistry`/transaction-commit logic with a forged `TransactionID`, potentially disrupting or prematurely committing another user's concurrently running push transaction. This is a state-corruption/DoS class issue affecting shared server-side coordination structures, not merely an information leak.

### Likelihood Explanation
Likelihood is moderate-to-high in any deployment where components other than `gitaly-hooks` share the Gitaly auth token (the normal GitLab.com/self-managed architecture, where Workhorse, GitLab Shell, Sidekiq, and Rails all authenticate with the same shared secret). The vulnerability is explicitly flagged as a known architectural gap in the codebase's own test comments (gitlab-org/gitaly#3746), indicating the maintainers are aware `HookService` is exposed where it shouldn't be, but no caller-identity enforcement equivalent to `SignalPostReceiveReady`'s backchannel check has been added to the mutating hook RPCs.

### Recommendation
Restrict `PreReceiveHook`, `PostReceiveHook`, `UpdateHook`, `ReferenceTransactionHook`, and `ProcReceiveHook` to Gitaly's internal-only socket (as already done for other internal RPCs), or add an explicit caller-identity check analogous to `SignalPostReceiveReady`'s `backchannel.GetPeerID` gate before executing hook logic or touching the transaction registry. Additionally, do not trust `TransactionID` or other transaction-scoping metadata sourced from the attacker-controlled `environment_variables` request field without binding it cryptographically or contextually to the specific gRPC connection/transaction that legitimately created it.

### Proof of Concept
Concrete exploit code could not be constructed with certainty from static review alone — this requires verifying at runtime whether `gitcmd.HooksPayloadFromEnv`/`NewHooksPayload` cryptographically signs the payload (which was not found in the reviewed files) and whether the external gRPC listener indeed serves `HookService` in the current build (confirmed reachable in `pre_receive_test.go` via the external `client.New` connection). A background Devin session with terminal access to run and instrument a live Gitaly server would be needed to confirm exploitability end-to-end (e.g., issuing a raw `PostReceiveHook` RPC with a forged `environment_variables` payload referencing another transaction's ID and observing registry state mutation), which is outside the scope of this read-only investigation.

func (m *GitLabHookManager) PostReceiveHook(ctx context.Context, repo *gitalypb.Repository, pushOptions, env []string, stdin io.Reader, stdout, stderr io.Writer) error {
	payload, err := gitcmd.HooksPayloadFromEnv(env)
	if err != nil {
		return structerr.NewInternal("extracting hooks payload: %w", err)
	}

	// When transactions are enabled, new writes to the repository are only available for readers (other than the
	// transaction itself) after the transaction is committed. Commit usually happens in middleware after the gRPC
	// request handler returns. Because the post-receive hook is invoked within the request handler, the transaction
	// will still be in flight, and the new writes will not be available to other transactions yet. Rails sends
	// further requests from its post-receive handler. Each of these requests are handled in their own transactions.
	//
	// To address this, explicitly commit the transaction here. We then begin a new transaction to provide the hook
	// with read-only access to the repository and its newly written changes. A new transaction is needed because
	// the previous transaction's snapshot would've been discarded by the commit. As the changes have been committed,
	// the subsequent requests sent from Rails' post-receive handler will have access to the new changes.
	//
	// We perform this dance here instead of the transaction middleware as the post-receive hook may need to write
	// messages directly to the client.
	if payload.TransactionID > 0 {
		tx, err := m.txRegistry.Get(payload.TransactionID)
		if err != nil {
			return fmt.Errorf("get transaction: %w", err)
		}

		originalRepo := tx.OriginalRepository(repo)

		// The transaction may already be committed if the RPC invokes git-receive-pack(1) with the
		// proc-receive hook enabled. Ignore the error indicating that here.
		if commitLSN, err := tx.Commit(ctx); err != nil {
			if !errors.Is(err, storage.ErrTransactionAlreadyCommitted) {
				return fmt.Errorf("commit transaction: %w", err)
			}

			// If the transaction was already committed, we don't log the line below.
		} else {
			storage.LogTransactionCommit(ctx, m.logger.WithFields(payload.LogFields), commitLSN, "post-receive")
		}
