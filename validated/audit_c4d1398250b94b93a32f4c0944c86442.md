### Title
Race between `Bits.Check` and `Bits.Update` in `ConnectionState.Decrypt` allows duplicate/replayed packet processing - (File: `connection_state.go`)

### Summary
`ConnectionState.Decrypt` implements anti-replay validation as two separate locked operations — a `Check` and, after decryption completes outside the lock, an `Update` — rather than a single atomic check-and-mark. This mirrors the reported bug class: a security-relevant state check is split across two calls with a window in between where the same input can independently satisfy the check twice, allowing an invariant ("each message counter is processed at most once") to be bypassed. [1](#0-0) 

### Finding Description
`Decrypt` takes the `decryptLock`, calls `cs.window.Check(l, messageCounter)`, and immediately releases the lock before doing the actual AEAD decryption. Only after decryption succeeds does it re-acquire the lock and call `cs.window.Update(l, messageCounter)` to mark the counter as seen: [1](#0-0) 

Between the `Check` and the subsequent `Update`, the lock is not held, and `DecryptDanger` (the actual AEAD unseal) runs unlocked. If two packets carrying the same `messageCounter` (e.g., a replayed/duplicated UDP datagram racing with the original, or two copies delivered via different network paths/relay hops) are processed concurrently by separate goroutines against the same `ConnectionState`, both can call `Check` before either calls `Update`. Both will see the counter as "not yet seen" (`Check` returns true for both), both proceed to decrypt and hand the plaintext to the application (TUN write / firewall path), and only afterward does one lose the `Update` race and get discarded. The damage — duplicate delivery of the same message to the inside network — has already happened by that point.

This is structurally the same class of defect as the `PriceFeed.fetchPrice()` finding: a stateful check (`bothOraclesUntrusted`/`usingChainlinkFallbackUntrusted` there, replay-window membership here) is read, acted upon, and only committed in a second, separate step, so two overlapping invocations can each observe the pre-commit state and both take the "trusted" path. `Bits.Check`/`Bits.Update` are individually correct (as shown extensively in `bits_test.go`), but the composition in `Decrypt` reintroduces a TOCTOU (check-then-act) gap that the `Bits` API's split design invites callers to get wrong. [2](#0-1) [3](#0-2) 

The same pattern is duplicated in `VerifyRelay`, used on the relay-forwarding path: [4](#0-3) 

Note the project's own regression test explicitly calls out that the relay path previously failed to advance the replay window at all (a related but distinct bug, since fixed) — underscoring that this replay-window bookkeeping is a known fragile area: [5](#0-4) 

### Impact Explanation
An attacker who can deliver duplicate copies of a captured/observed ciphertext packet to a victim node in close temporal proximity (no valid cert needed — this is on the packet-decryption path reached from any inbound UDP packet or relayed frame) could get a single valid message counter processed twice by the data plane before the replay window commits. Depending on payload content this could cause duplicate delivery of application data to the TUN interface, double execution of any state-changing effect tied to a single message (e.g., replayed control-plane packets like `closetunnel`/`Test` messages if they ever race), or, on the relay path, double-forwarding, defeating the purpose of `advance the replay window` fix noted in the CHANGELOG. This is a genuine remote-reachable replay/duplicate-processing weakness in the anti-replay enforcement, not merely theoretical, since it requires no valid certificate and operates purely on the wire-format nonce/counter check that any peer address can trigger.

### Likelihood Explanation
Exploitation requires the attacker to race two copies of the exact same ciphertext (same message counter) into the receive path fast enough to lose the lock window between `Check` and `Update`. This is plausible on networks where UDP packets can be duplicated (common with certain routing/relay setups, or an attacker directly injecting two copies), but the race window is narrow (bounded by one AEAD decrypt operation), so reliable exploitation needs either a slow decrypt path or deliberate concurrent injection from the attacker. This keeps likelihood at a similar tier to the referenced Medium-severity report: a real defense-bypass condition, not a high-probability, easily-automated one.

### Recommendation
Make replay-window admission atomic: hold `decryptLock` across `Check` (or fold the check into `Update`) so that only one caller can ever observe "not yet seen" for a given counter, and reject duplicate concurrent packets before decryption is attempted — i.e., call `window.Update` (which already performs the duplicate check) under a single critical section that also gates whether decryption proceeds, rather than calling `Check` and `Update` as two independently-lockable steps with decryption sandwiched in between. Apply the same fix to `VerifyRelay`.

### Proof of Concept
Conceptual PoC (concurrency-dependent, not deterministic without instrumentation):
1. Capture one legitimate ciphertext packet destined for hostA (as in `TestRelayReplayProtection`'s capture step). [6](#0-5) 
2. Fire two goroutines that call `hostA.ConnectionState.Decrypt` (or, for the relay path, `VerifyRelay`) with the identical packet and `messageCounter` concurrently, e.g. by injecting the same UDP packet twice back-to-back so both are picked up by separate reader routines before either completes its `Update` call.
3. Instrument/observe: both calls to `cs.window.Check` return `true` because neither has called `Update` yet; both proceed through `DecryptDanger`; the second `Update` call fails but only after the plaintext from the duplicate has already been produced and (in the real pipeline) delivered to the TUN device or forwarded by the relay.
4. Because the actual race window is sub-millisecond, reliably demonstrating this requires artificially widening the window (e.g., a test hook that sleeps between `Check` and `Update` in `Decrypt`) to prove the logical possibility — the existing `bits_test.go` suite does not exercise concurrent `Check`/`Update` interleavings, only sequential ones, so this concurrency gap is not covered by current tests. [7](#0-6)

func (cs *ConnectionState) Decrypt(l *slog.Logger, messageCounter uint64, out []byte, packet []byte, nb []byte) ([]byte, error) {
	var err error
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}

	out, err = cs.dKey.DecryptDanger(out, packet[:header.Len], packet[header.Len:], messageCounter, nb)
	if err != nil {
		return nil, err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}
	return out, nil
}

func (cs *ConnectionState) VerifyRelay(l *slog.Logger, messageCounter uint64, packet []byte, nb []byte) error {
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	signedPayload := packet[:len(packet)-cs.dKey.Overhead()]
	signatureValue := packet[len(packet)-cs.dKey.Overhead():]
	_, err := cs.dKey.DecryptDanger(nil, signedPayload, signatureValue, messageCounter, nb)
	if err != nil {
		return err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	return nil
}

// Check returns true if i is within (or way out in front of) the window, and not a replay
func (b *Bits) Check(l *slog.Logger, i uint64) bool {
	// If i is the next number, return true.
	if i > b.current {
		return true
	}

	if b.strictlyWithinWindow(i) {
		return !b.get(i)
	}

	// Not within the window
	if l.Enabled(context.Background(), slog.LevelDebug) {
		l.Debug("rejected a packet (top)", "current", b.current, "incoming", i)
	}
	return false
}

func (b *Bits) Update(l *slog.Logger, i uint64) bool {
	// Fast path: i is the next expected counter. Split out so the function
	// stays small and avoids paying for the slow paths' slog argument-build
	// stack frame on every call. The bit read/test/write is inlined to
	// touch the backing word once.
	if i == b.current+1 {
		pos := i & b.lengthMask
		word := pos >> 6
		mask := uint64(1) << (pos & 63)
		w := b.bits[word]
		if i > b.length && w&mask == 0 {
			b.lostCounter.Inc(1)
		}
		b.bits[word] = w | mask
		b.current = i
		return true
	}
	return b.updateSlow(l, i)
}

func TestBits(t *testing.T) {
	l := test.NewLogger()
	b := NewBits(16)
	assert.EqualValues(t, 16, b.length)

	// This is initialized to zero - receive one. This should work.
	assert.True(t, b.Check(l, 1))
	assert.True(t, b.Update(l, 1))
	assert.EqualValues(t, 1, b.current)
	g := []bool{true, true, false, false, false, false, false, false, false, false, false, false, false, false, false, false}
	assert.Equal(t, g, b.snapshot())

	// Receive two
	assert.True(t, b.Check(l, 2))
	assert.True(t, b.Update(l, 2))
	assert.EqualValues(t, 2, b.current)
	g = []bool{true, true, true, false, false, false, false, false, false, false, false, false, false, false, false, false}
	assert.Equal(t, g, b.snapshot())

	// Receive two again - it will fail
	assert.False(t, b.Check(l, 2))
	assert.False(t, b.Update(l, 2))
	assert.EqualValues(t, 2, b.current)

	// Jump ahead to 25, which clears the window and sets slot 25%16 = 9.
	assert.True(t, b.Check(l, 25))
	assert.True(t, b.Update(l, 25))
	assert.EqualValues(t, 25, b.current)
	g = []bool{false, false, false, false, false, false, false, false, false, true, false, false, false, false, false, false}
	assert.Equal(t, g, b.snapshot())

	// Mark 24, which is in window (current 25, length 16, window covers [10,25]).
	assert.True(t, b.Check(l, 24))
	assert.True(t, b.Update(l, 24))
	assert.EqualValues(t, 25, b.current)
	g = []bool{false, false, false, false, false, false, false, false, true, true, false, false, false, false, false, false}
	assert.Equal(t, g, b.snapshot())

	// Mark 5, not allowed because 5 <= current-length (25-16=9).
	assert.False(t, b.Check(l, 5))
	assert.False(t, b.Update(l, 5))
	assert.EqualValues(t, 25, b.current)
	g = []bool{false, false, false, false, false, false, false, false, true, true, false, false, false, false, false, false}
	assert.Equal(t, g, b.snapshot())

	// Make sure we handle wrapping around once to the same slot. With
	// length=16, packets 1 and 17 share slot 1.
	b = NewBits(16)
	assert.True(t, b.Update(l, 1))
	assert.True(t, b.Update(l, 17))
	assert.Equal(t, []bool{false, true, false, false, false, false, false, false, false, false, false, false, false, false, false, false}, b.snapshot())

	// Walk through a few windows in order
	b = NewBits(16)
	for i := uint64(1); i <= 100; i++ {
		assert.True(t, b.Check(l, i), "Error while checking %v", i)
		assert.True(t, b.Update(l, i), "Error while updating %v", i)
	}

	assert.False(t, b.Check(l, 1), "Out of window check")
}
