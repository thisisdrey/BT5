### Title
`PeerDB::try_insert_peer` allows unauthenticated overwrite of a peer's `public_key` at a self-declared `(network_id, addrbytes, port)` frontier slot - ([File: stackslib/src/net/db.rs])

### Summary
`PeerDB::try_insert_peer` (db.rs:1452-1488) keys the frontier table purely on the self-declared `(network_id, addrbytes, port)` tuple carried inside `HandshakeData`, not on any value bound to the actual TCP socket of the connection. Because the handshake signature only proves that the sender controls the private key for the public key it is presenting — not that it controls the specific `addrbytes`/`port` it is claiming — a peer we have an outbound session with can declare a victim's already-registered address and have `handle_handshake` (chat.rs:1214-1296) silently rewrite that victim's frontier row via `PeerDB::update_peer`.

### Finding Description
The frontier `slot` is a deterministic hash of `addrbytes`/`port` (per the design comment at db.rs:289-296), and `try_insert_peer` first checks `PeerDB::has_peer` for that exact tuple; if present, it unconditionally calls `PeerDB::update_peer`, overwriting the stored `public_key` [1](#0-0) .

The value written comes from `HandshakeData`, which is entirely attacker-controlled (self-reported `addrbytes`/`port`/`node_public_key`), not from the actual remote socket address of the connection. In `handle_handshake`, after `validate_handshake` succeeds (which only checks the message's cryptographic signature and preamble fields, proving control of the presented private key — not control of the claimed address), the code path that persists to `PeerDB` is gated only on `self.stats.outbound`: [2](#0-1) 
`Neighbor::load_and_update` builds the `Neighbor` (and hence the `addr` used for the DB write) from `handshake_data`'s self-declared fields, not from the verified peer socket address, then `neighbor.save_update` persists it (which internally reaches `try_insert_peer`/`update_peer`).

The equality that should hold — "public_key persisted at (network_id, addrbytes, port) == the key that most recently proved ownership of the private key for that exact addrbytes/port" — is broken because the signature check only proves ownership of a private key matching the *presented* public key, and never proves the signer is reachable at, or previously proven to own, the specific `addrbytes`/`port` it declares. Since a remote node can freely pick any outbound connection target and simply lie about its own `addrbytes`/`port` in the handshake, it can claim an already-registered victim's address/port and overwrite the victim's `public_key` row.

### Impact Explanation
An attacker can cause the node to silently replace a legitimate, previously-authenticated peer's identity (`public_key`) in the local `PeerDB` frontier with the attacker's own key, without ever proving control of the victim's private key. This is an unauthenticated write to persistent peer-identity state and can be used to evict/impersonate a legitimate neighbor for future dialing/whitelisting decisions built on `PeerDB`, satisfying the "unauthenticated/unauthorized write to state" Critical category. It is repeatable against any address/port the node has previously learned, each time the attacker (re)completes an outbound handshake declaring that address.

### Likelihood Explanation
Precondition: the target node must have (or establish) an outbound session to the attacker's real socket, which is routine — nodes regularly dial peers discovered via gossip (`NeighborAddress` lists), and an attacker can advertise itself to be walked-to. No secrets, privileged roles, or victim key material are required; the attacker only needs to run a reachable peer and send a self-signed `Handshake` declaring the victim's `addrbytes`/`port`. This is low-cost and remotely triggerable purely through the P2P handshake protocol.

### Recommendation
Bind the frontier slot / stored `NeighborKey` for a persisted handshake to the verified transport-level peer identity: for inbound connections, validate the self-declared `addrbytes`/`port` against the actual socket peer address before persisting; for outbound connections, persist under the address we dialed (not the self-declared one), and require proof-of-possession of the previously-registered public key (e.g., re-handshake signed by the currently stored key) before allowing a `public_key` change at an already-occupied slot.

### Proof of Concept
Rust test in `stackslib::net::db`:
1. Insert a `Neighbor` `victim` with `public_key = pk1` at `(network_id, addrbytes=X, port=P)` via `try_insert_peer` (tx1, commit).
2. Construct a second `Neighbor` `attacker` with identical `addr = (network_id, X, P)` but `public_key = pk2` (a different `Secp256k1PublicKey`), with no handshake/signature-ownership proof of `pk1`.
3. Call `PeerDB::try_insert_peer(&tx2, &attacker, &[])`, commit.
4. `PeerDB::get_peer(conn, network_id, &X, P)` and assert `public_key == pk2`, showing the original `pk1` entry was silently overwritten — reproducing the broken equality without any handshake proving ownership of `pk1`'s private key.
