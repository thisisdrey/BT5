## Analysis

The Morpho report's core broken invariant is: **a matching/settlement queue bounded by a per-transaction iteration limit leaves a leftover ("delta") that is silently mis-recorded as settled, and this leftover degrades the outcome for other participants — and an attacker can force this leftover cheaply.**

The closest real local analog is the new `on_idle` auto-rebag mechanism in `pallet-bags-list`, added in [PR #8684](https://github.com/paritytech/polkadot-sdk/pull/8684) (`prdoc/stable2509/pr_8684.prdoc`). It processes a bounded number of list-correction items per block using a persistent cursor (`NextNodeAutoRebagged`), exactly like Morpho's bounded-iteration queue producing a "delta". Here the cursor can be forced to reset every block by an attacker who inflates the `PendingRebag` queue, permanently starving correction of legitimate accounts deeper in the `SortedListProvider` list that feeds staking/election weighting. ### Title
Attacker-inflatable `PendingRebag` queue permanently resets the `bags-list` auto-rebag cursor, starving correction of legitimate voter positions - (File: `substrate/frame/bags-list/src/lib.rs`)

### Summary
`Pallet::on_idle` in `pallet-bags-list` incrementally corrects misplaced list nodes each block, bounded by `T::MaxAutoRebagPerBlock`, using a persisted cursor `NextNodeAutoRebagged` to resume traversal of the regular `ListNodes` on the next block. `PendingRebag` entries (created whenever `on_insert`/score-change calls occur while the list is `Locked`, e.g. during the staking election snapshot window) are always prioritized ahead of regular nodes in the same bounded batch. If `PendingRebag` accumulates more entries than `MaxAutoRebagPerBlock`, the entire per-block budget is consumed by pending entries every block, the regular-list iterator is never advanced, and the cursor-selection logic falls through to the `None => kill()` branch, wiping `NextNodeAutoRebagged` back to the head of the list instead of preserving forward progress.

### Finding Description
The batch construction is: [3](#0-2) 

`PendingRebag::<T, I>::iter_keys()` is chained *before* the regular cursor-resumed iterator, and only `rebag_budget + 1` items are taken in total. When `PendingRebag` count exceeds `rebag_budget`, `to_process` and `next_cursor` are populated entirely from `PendingRebag`, so the regular-list iterator (`regular_iter`, built from the persisted cursor) is never even pulled from.

The cursor-update logic then does: [2](#0-1) 

`next_regular_account` searches `next_cursor` for an entry that is *not* in `PendingRebag`. Since `next_cursor` in this scenario is itself drawn from `PendingRegab`, no such entry is found, hitting the `None => { NextNodeAutoRebagged::<T,I>::kill(); ... }` branch. This discards the previously saved forward-progress cursor and forces the next block's regular traversal to restart from `Self::iter()` (head of the list) rather than resuming where it left off.

`PendingRebag` entries are produced whenever `on_insert` (or score-changing operations) occur while the pallet is locked: [4](#0-3) 

The lock window corresponds to the staking election snapshot phase, during which normal (unprivileged) bonding/nominating activity is redirected into `PendingRebag` rather than being inserted immediately. An attacker does not need any privileged role — they only need to submit enough ordinary `bond`/`nominate`-triggering list-mutation transactions (from many stash accounts, or by repeatedly changing their own stake) during a lock window so that `PendingRebag`'s size persistently exceeds `MaxAutoRebagPerBlock`.

### Impact Explanation
As long as `PendingRebag` remains oversized (which an attacker can sustain indefinitely by feeding a small trickle of pending-inducing transactions across successive election-lock windows), the regular auto-rebag cursor is killed every block that the batch is entirely pending-derived. This means legitimate accounts beyond the very head of the `ListNodes` iteration order whose score has drifted out of their bag's threshold are **never** automatically corrected by `on_idle`, indefinitely. Since `pallet-bags-list` implements `SortedListProvider` consumed by staking (`pallet-staking`/`pallet-staking-async`) for nominator/validator ordering and voter snapshotting, stale bag positions bias who gets included/weighted in election snapshots and reward/slashing computations — a chain-level runtime correctness defect ("runtime bugs that compromise intended behavior") reachable without any privileged actor, governance action, or malicious validator/collator involvement.

### Likelihood Explanation
Likelihood is moderate-to-high: the attacker primitive (ordinary bond/nominate calls timed against the public, predictable election-snapshot lock window) is available to any unprivileged account, requires no leaked keys or validator/collator collusion, and only needs to keep the `PendingRebag` count above the configured per-block budget, which is a fixed, publicly known runtime constant (`MaxAutoRebagPerBlock`).

### Recommendation
Decouple the pending-priority processing from the regular-list cursor logic so pending items never consume the entire budget in a way that erases forward-progress state. Specifically:
- Cap how much of the per-block budget `PendingRebag` items may consume (e.g. reserve a minimum slice of the budget for regular-list traversal every block), and/or
- Only kill `NextNodeAutoRebagged` when the regular-list iterator itself is confirmed exhausted (i.e., track regular-list exhaustion independently of whether `next_cursor` happens to contain a `PendingRebag` entry), rather than inferring exhaustion from `next_regular_account == None`.

### Proof of Concept
1. Set `MaxAutoRebagPerBlock = N` (small, as in most runtime configs).
2. During a staking election snapshot window, `BagsList::lock()` is engaged (as validated in `substrate/frame/bags-list/src/tests.rs` lock tests).
3. From many unprivileged stash accounts, submit ordinary stake/nominate operations that trigger `on_insert`/score changes while locked; each such call is diverted into `PendingRebag` per the flow demonstrated in `pending_rebag` test at `substrate/frame/bags-list/src/tests.rs:1023-1053`.
4. Ensure `PendingRebag::<T,I>::count() > N` before unlocking.
5. After unlock, on each subsequent block's `on_idle`, the collected `accounts` batch of size `N+1` is drawn entirely from `PendingRebag` (since it is chained first and its count exceeds `N`); `next_cursor`'s single leftover element is also a `PendingRebag` key, so `next_regular_account` resolves to `None` and `NextNodeAutoRebagged::<T,I>::kill()` fires every block.
6. Repeat this pending-inflation across subsequent election cycles to keep `PendingRebag` perpetually above `N`; observe (via storage inspection or `try_state`) that regular `ListNodes` entries whose bag no longer matches their score are never corrected by `on_idle`, unlike the intended incremental-progress behavior demonstrated in `rebags_resumes_from_node_after_rebagging` (`substrate/frame/bags-list/src/tests.rs:882-905`).
