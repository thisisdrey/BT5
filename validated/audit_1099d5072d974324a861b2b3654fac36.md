### Title
Stored failed LayerZero messages can be retried to mint synthetic tokens after bridging is disabled — `retryMessage`/`_creditTo` re-arms a delivery path that teardown was meant to stop - ([File: contracts/ProxyOFT.sol](contracts/ProxyOFT.sol), [File: contracts/dependencies/@layerzerolabs/solidity-examples/contracts-upgradeable/lzApp/NonblockingLzAppUpgradeable.sol](contracts/dependencies/@layerzerolabs/solidity-examples/contracts-upgradeable/lzApp/NonblockingLzAppUpgradeable.sol))

### Summary
`ProxyOFT._debitFrom` enforces `isBridgingActive()` and `isDestinationChainSupported()` before burning tokens for an outbound bridge, but the inbound mint path `_sendAck -> _creditTo` performs no equivalent check. Failed inbound deliveries are persisted in `NonblockingLzAppUpgradeable.failedMessages` and can be re-executed at any later time by anyone via `retryMessage`, which mints through `_creditTo` unconditionally — a stored "callback" that re-fires after the bridging path has been torn down.

### Finding Description
The outbound leg checks the emergency switch:

- `ProxyOFT._debitFrom` reverts with `BridgingIsPaused` if `syntheticToken.poolRegistry().isBridgingActive()` is false. [1](#0-0) 

The inbound leg does not:

- `ProxyOFT._creditTo` calls `syntheticToken.mint(toAddress_, amount_)` with no `isBridgingActive` or trusted-remote revalidation. [2](#0-1) 
- `OFTCoreUpgradeable._sendAck` decodes the payload and calls `_creditTo`. [3](#0-2) 

When an inbound message reverts during delivery (e.g., mint temporarily failing against a supply cap, gas exhaustion inside `nonblockingLzReceive`), `_blockingLzReceive` catches the failure and stores `keccak256(_payload)` in `failedMessages[_srcChainId][_srcAddress][_nonce]`. [4](#0-3) 

`retryMessage` is public, clears the stored hash, and re-executes `_nonblockingLzReceive`, which reaches `_sendAck -> _creditTo -> syntheticToken.mint` — regardless of the current bridging state. [5](#0-4) 

This is structurally identical to the referenced kernel bug: teardown (deactivating bridging) neither waits for nor prevents a pending callback (the stored message) from re-firing against the resource that was conceptually retired (the mint path).

### Impact Explanation
If governance disables bridging via `isBridgingActive` as an emergency stop (e.g., in response to a source-chain issue or a mint-side bug), every previously stored failed message remains executable and will mint `SyntheticToken` supply on this chain while the bridge is supposed to be off. The mint check bypass is permanent for the lifetime of the stored entries — `failedMessages` entries are never cleared when bridging is disabled and `retryMessage` has no pause flag. Depending on the mint-side condition that caused the original failure, this can inflate synthetic supply at a moment the protocol deliberately froze minting, breaking the invariant that the bridging pause halts all bridge-driven supply changes. Inbound minted supply that escapes the emergency stop can translate to protocol insolvency if the pause was enacted to contain an over-mint or chain-side incident.

### Likelihood Explanation
Triggering requires: (1) an attacker-initiated legitimate `sendFrom` on the remote chain (unprivileged — `sendFrom` only requires owning the tokens burned) whose destination delivery fails and gets stored — an attacker can arrange this by choosing a gas-limited delivery or timing it against a `bridgedIn`/supply-cap revert; and (2) bridging subsequently being deactivated, after which the attacker (or anyone) calls `retryMessage` with the recorded payload. `retryMessage` is permissionless and present in the deployed ABIs (e.g., `deployments/base/MsETHProxyOFT.json`). [6](#0-5)  The minted amount is bounded by what was burned on the source chain, so the primary harm is defeating the emergency stop rather than arbitrary minting, but the delivery-stored-then-teardown ordering is fully attacker-influenceable.

### Recommendation
Mirror the fix class of the kernel patch (`timer_shutdown_sync` on teardown): when bridging is deactivated, the stored callback must not be able to re-fire. Concretely:

- Add an `isBridgingActive()` check in `ProxyOFT._creditTo` (or override `retryMessage`/`_nonblockingLzReceive` in `ProxyOFT` to revert when bridging is inactive), so retries inherit the same guard as the original delivery path.
- Alternatively, provide a governor function to clear specific `failedMessages` entries, or gate `retryMessage` on `poolRegistry().isBridgingActive()`.

### Proof of Concept
A Hardhat fork test reproducing the ordering:

```solidity
// SPDX-License-Identifier: MIT
pragma solidity 0.8.24;

import "forge-std/Test.sol";
import {ProxyOFT} from "contracts/ProxyOFT.sol";

// Fork a chain where MsETHProxyOFT is deployed (e.g. Base) with a real
// SyntheticToken + PoolRegistry so mint/poolRegistry() resolve.

contract RetryAfterTeardown is Test {
    ProxyOFT proxyOft;
    address poolRegistry;
    address governor;
    address attacker;

    function setUp() public {
        // vm.createSelectFork("base");
        proxyOft = ProxyOFT(payable(<PROXY_OFT>));
        poolRegistry = address(proxyOft.syntheticToken().poolRegistry());
        governor = proxyOft.owner();
        attacker = makeAddr("attacker");
    }

    function test_RetryMintsAfterBridgingDisabled() public {
        uint16 srcChain = 110;                 // e.g. LZ id of a configured peer
        bytes memory srcAddr = abi.encodePacked(proxyOft.getProxyOFTOf(srcChain));
        uint64 nonce = 1;
        uint256 amount = 10 ether;

        // 1. Simulate a failed inbound PT_SEND delivery: the endpoint calls
        //    lzReceive -> _blockingLzReceive, the inner mint reverts
        //    (e.g. temporarily capped), and the payload hash is stored.
        //    On a fork this can be produced via a real sendAndCall/sendFrom
        //    with insufficient destination gas, or by etching/mock endpoint.
        //    Resulting state: failedMessages[srcChain][srcAddr][nonce] != 0.
        bytes memory payload = abi.encode(uint16(0), abi.encodePacked(attacker), amount);
        // (arrange delivery failure so _storeFailedMessage runs)

        // 2. Teardown: governor deactivates bridging.
        vm.prank(governor);
        // IPoolRegistry(poolRegistry).toggleBridgingIsActive() / equivalent setter
        // assert(!IPoolRegistry(poolRegistry).isBridgingActive());

        // 3. Attacker re-fires the stored callback — mint still succeeds
        //    because _creditTo never consults isBridgingActive().
        uint256 balBefore = proxyOft.syntheticToken().balanceOf(attacker);
        proxyOft.retryMessage(srcChain, srcAddr, nonce, payload);
        assertEq(proxyOft.syntheticToken().balanceOf(attacker), balBefore + amount);
    }
}
```

Caveat on reproduction details: I located the retry/credit path and confirmed `retryMessage` is permissionless and `isBridgingActive` is only checked in `_debitFrom`, but I did not enumerate the exact `PoolRegistry` setter name that deactivates bridging or the precise revert condition that first causes `_storeFailedMessage` — those would need to be pinned down when writing the executable test (a mint temporarily reverting on a cap, or a mocked `lzEndpoint` delivering the payload, both work). The core invariant violation — a stored delivery executing a mint after bridging teardown — follows directly from the code cited above.

    function retryMessage(uint16 _srcChainId, bytes calldata _srcAddress, uint64 _nonce, bytes calldata _payload) public payable virtual {
        // assert there is message to retry
        bytes32 payloadHash = failedMessages[_srcChainId][_srcAddress][_nonce];
        require(payloadHash != bytes32(0), "NonblockingLzApp: no stored message");
        require(keccak256(_payload) == payloadHash, "NonblockingLzApp: invalid payload");
        // clear the stored message
        failedMessages[_srcChainId][_srcAddress][_nonce] = bytes32(0);
        // execute the message. revert if it fails again
        _nonblockingLzReceive(_srcChainId, _srcAddress, _nonce, _payload);
        emit RetryMessageSuccess(_srcChainId, _srcAddress, _nonce, payloadHash);
