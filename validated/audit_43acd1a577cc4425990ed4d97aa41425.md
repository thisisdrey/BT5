**Analysis:** The `chunks` table has `PRIMARY KEY(stackerdb_id, slot_id)` [1](#0-0) , meaning only a single row (the current version) exists per slot at any time — there is no on-disk history of prior versions. `insert_chunk` performs an `UPDATE ... SET version = ?1, data = ?4 ... WHERE stackerdb_id = ?6 AND slot_id = ?7`, overwriting the row in place rather than appending a new version row [2](#0-1) .

`get_chunk` queries `WHERE stackerdb_id = ?1 AND slot_id = ?2 AND version = ?3` [3](#0-2) . Since only the current version's row exists, a request for any non-current `slot_version` matches zero rows and returns `Ok(None)`, which `RPCGetStackerDBChunkRequestHandler::try_handle_request` maps to an `HttpNotFound` response [4](#0-3) . There is no code path that returns stale bytes for a mismatched version — the equality the question hypothesizes (stale chunk served for old version) cannot occur because old data is destroyed by the `UPDATE`, not retained. Requesting exactly the current version returns exactly the owner-signed bytes for that version; requesting any other version returns 404, not stale data.

        &self,
        smart_contract: &QualifiedContractIdentifier,
        slot_desc: &SlotMetadata,
        chunk: &[u8],
    ) -> Result<(), net_error> {
        let stackerdb_id = self.get_stackerdb_id(smart_contract)?;
        let sql = "UPDATE chunks SET version = ?1, data_hash = ?2, signature = ?3, data = ?4, write_time = ?5 WHERE stackerdb_id = ?6 AND slot_id = ?7";
        let mut stmt = self.sql_tx.prepare(sql)?;

        let args = params![
            slot_desc.slot_version,

            slot_desc.signature,
            chunk,
            u64_to_sql(get_epoch_time_secs())?,
            stackerdb_id,
            slot_desc.slot_id,
        ];

        stmt.execute(args)?;
        Ok(())
    }
