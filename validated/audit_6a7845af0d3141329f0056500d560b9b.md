### Title
Attacker can fill a victim's per-account token list via dust deposits/transfers, blocking the victim from depositing new collateral or issuing debt - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
`Pool` maintains two per-account enumerable sets, `depositTokensOfAccount` and `debtTokensOfAccount`, whose combined size is capped at `MAX_TOKENS_PER_USER = 30`. Entries are added to `depositTokensOfAccount` whenever an account's `DepositToken` balance goes from 0 to non-zero — on `deposit()` to `onBehalfOf_`, and on any plain `transfer`/`transferFrom`/`seize`. Any unprivileged user can push entries into a *victim's* list by depositing dust on the victim's behalf or by transferring dust `msdTOKEN` to the victim. Once the cap is hit, every subsequent first-time deposit, incoming transfer, or `DebtToken.issue`/`mint` to that account reverts with `UserReachedMaxTokens`.

### Finding Description
`Pool.onlyIfAdditionWillNotReachMaxTokens` reverts when `debtTokensOfAccount.length(account_) + depositTokensOfAccount.length(account_) >= MAX_TOKENS_PER_USER` (30). [1](#0-0) 

`addToDepositTokensOfAccount` is callable only by a registered `DepositToken`, but the trigger is entirely under the caller's control: [2](#0-1) 

In `DepositToken._transfer`, any recipient whose balance was zero gets the token pushed into their per-account list — no opt-in: [3](#0-2) 

`DepositToken._mint` does the same, and `deposit(amount_, onBehalfOf_)` lets anyone mint to an arbitrary beneficiary: [4](#0-3) [5](#0-4) 

Symmetrically, `DebtToken._mint` adds to `debtTokensOfAccount` on first issuance, so a saturated victim cannot open a new debt position either (`issue` → `_mint` → `addToDebtTokensOfAccount` reverts). [6](#0-5) 

Attack path (no privileged role needed):

1. Attacker acquires dust amounts of `msdTOKEN` for each deposit token listed in the pool (by calling `deposit(dust, attacker)` — cheap if underlying has low unit value, or by depositing once and splitting).
2. For each `DepositToken`, attacker calls `transfer(victim, 1)` (or `deposit(1, victim)` — `_revertIfLocked` only restricts the *sender's* balance). Each call pushes a new entry into `depositTokensOfAccount[victim]`.
3. Once `depositTokensOfAccount[victim] + debtTokensOfAccount[victim]` reaches 30, any subsequent `deposit` of a collateral the victim doesn't yet hold, any incoming msdTOKEN transfer of a new token, and any `DebtToken.issue` of a synth the victim doesn't yet owe reverts in `addTo{Deposit,Debt}TokensOfAccount`.

This is the same bug class as the OpenQ finding: a permissionless entry point lets an attacker consume a bounded per-object list (`fundBountyToken`'s token-address cap there; `MAX_TOKENS_PER_USER` here) to block a legitimate user's action. Feasibility depends on the pool listing enough deposit tokens (the combined cap includes debt tokens, and `addDepositToken` itself is capped at `MAX_TOKENS_PER_USER`, so up to 30 entries can be forced if governance lists that many collaterals). [7](#0-6) 

### Impact Explanation
Temporary freezing / denial of service of core protocol functions for the targeted account: the victim cannot deposit new collateral types, cannot receive new msdTOKEN transfers, and cannot issue new synthetic debt while the list is full. This can be timed to grief a specific transaction (e.g., front-run a victim's first `issue` or a leveraged position via `SmartFarmingManager`, which internally mints debt to the account). The victim can recover by transferring the dust balances to a fresh account (each zeroed balance triggers `removeFromDepositTokensOfAccount`), so the freeze is temporary and incurs gas costs — consistent with a medium-severity DoS.

### Likelihood Explanation
Requires the pool to list a meaningful number of deposit tokens (each forced entry needs a distinct registered `DepositToken`) and the attacker to spend gas and a small amount of real collateral per entry. The attack is permissionless, front-runnable against a known upcoming victim transaction, and costs the attacker only dust plus gas. Counter-mitigation: the victim can self-clean the list, which bounds the impact.

### Recommendation
Do not let unsolicited inbound balance changes consume the cap unconditionally. Options:
- Only add to `depositTokensOfAccount` on `deposit()` where the beneficiary is `_msgSender()` or an explicitly authorized account, or gate additions behind a per-account opt-in.
- Alternatively, let removal be forced by the account even when at the cap (already possible via transfers) and document it, or raise `MAX_TOKENS_PER_USER` / switch to a mapping-based accounting that does not enumerate per account.

### Proof of Concept
Hardhat (repo's existing test setup uses smock/hardhat-deploy fixtures; sketch against deployed-style contracts):

```typescript
// Setup: pool with N listed DepositTokens (d1..dN), victim with some existing tokens
const max = (await pool.MAX_TOKENS_PER_USER()).toNumber(); // 30
const victim = bob.address;

// Attacker holds dust of each listed deposit token
for (const dt of depositTokens) {
  const under = await ethers.getContractAt('ERC20', await dt.underlying());
  await under.connect(attacker).approve(dt.address, 1);
  // push into victim's list without victim's consent
  await dt.connect(attacker).deposit(1, victim); // or: deposit(1, attacker) then transfer(victim, 1)
}

const used = (await pool.getDepositTokensOfAccount(victim)).length
           + (await pool.getDebtTokensOfAccount(victim)).length;
expect(used).to.eq(max);

// Victim's new deposit into a collateral he doesn't hold reverts
await expect(newDepositToken.connect(bob).deposit(parseEther('1'), bob.address))
  .to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');

// Victim's issuance of a new synth debt reverts
await expect(newDebtToken.connect(bob).issue(amount, bob.address))
  .to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');
```

Note: the PoC requires the pool to list enough deposit tokens to reach the 30-slot cap (counting the victim's existing debt tokens). If deployed pools list far fewer than 30 collaterals, attacker-only filling cannot saturate the list, in which case this reduces to a low-severity grief rather than a reliable block.

Given that dependency on deployment configuration and the victim's ability to self-recover by moving dust, this is a real but bounded analog of the reported bug class.
