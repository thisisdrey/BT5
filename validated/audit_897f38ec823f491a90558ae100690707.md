### Title
`StorageWeightReclaim` measures PoV proof size before its own post-dispatch bookkeeping writes, letting the extension's self-inflicted proof-size cost go unpaid and unaccounted - (File: cumulus/pallets/weight-reclaim/src/lib.rs)

### Summary
`StorageWeightReclaim::post_dispatch_details` snapshots the node-side proof size right after the wrapped call/extensions finish executing, and uses that number as the ground truth for how much PoV was "actually" consumed by the extrinsic. It then performs several storage mutations of its own (`frame_system::BlockWeight::mutate`, `frame_system::ExtrinsicWeightReclaimed::put`) to record the reclaim. Those mutations happen strictly *after* the proof-size snapshot was taken, so their own proof-size cost is never included in `measured_proof_size`, and is only nominally covered by the static, benchmarked `T::WeightInfo::storage_weight_reclaim()` charge taken in `weight()`. This is the same broken invariant as the Mantra `xfeemarket` bug: a resource-consumption snapshot is taken before the fee/refund bookkeeping runs, so the bookkeeping's own resource usage silently escapes accounting.

### Finding Description
The `StorageWeightReclaim` transaction extension is meant to wrap the whole extension pipeline and reclaim over-benchmarked PoV/ref-time weight after dispatch: [1](#0-0) 

In `post_dispatch_details`, the "after" proof size is fetched from the host via `get_proof_size()`: [2](#0-1) 

That `proof_size_after_dispatch` value is treated as the final, authoritative measurement of everything the extrinsic + extension pipeline consumed. But the code then goes on to *itself* perform additional storage mutations — `frame_system::BlockWeight::<T>::mutate(...)` (which reads and writes the current-block weight tracker, and conditionally accrues extra weight for `pov_size_missing_from_node`) and `frame_system::ExtrinsicWeightReclaimed::<T>::put(...)` — after the snapshot was already taken: [3](#0-2) [4](#0-3) 

These storage read/writes generate real trie proof nodes (increasing the actual PoV size the node must gossip/include), exactly like the Mantra bug where the gas-burn and tip-refund bank transfers executed *after* the gas snapshot consumed real, unaccounted gas. Here the only charge collected for this bookkeeping work is the static benchmarked constant `T::WeightInfo::storage_weight_reclaim()` added in `weight()` — a single fixed number that cannot reflect the variable cost of these mutations (e.g. whether `BlockWeight`/`ExtrinsicWeightReclaimed` trie nodes are freshly created vs. already warm, or whether the `pov_size_missing_from_node` branch triggers an extra `accrue` write). If the benchmark underestimates this self-incurred cost (which by construction it cannot measure, since the measurement point in the extension precedes the mutations it is benchmarking against), the true PoV consumed by the block exceeds what was charged to the submitter.

### Impact Explanation
PoV proof size is a hard, protocol-enforced resource limit for parachains (it directly bounds how much data a collator can include in a PoV block that must fit within the relay chain's validation constraints). If the weight-reclaim extension's own bookkeeping cost is systematically undercharged, a submitter can repeatedly trigger the refund path (any transaction whose actual weight is less than declared, which is trivially achievable) to get real, physical PoV consumption for free beyond the static benchmark. Because this happens on every single reclaiming extrinsic in blocks that mostly consist of normal transactions, the aggregate effect is "public, underpriced work" that degrades block production by exhausting the PoV budget faster than fee accounting reflects, potentially causing collators to build blocks that are more expensive to include/validate than their measured weight suggests, or forcing conservative safety margins that reduce parachain throughput.

### Likelihood Explanation
No privileged actor is required — any signed extrinsic that goes through a runtime using `StorageWeightReclaim` (the documented drop-in replacement for `frame_system::WeightReclaim` on parachains) exercises this code path on every block, since the refund arithmetic and the `BlockWeight`/`ExtrinsicWeightReclaimed` storage writes execute unconditionally in `post_dispatch_details`, not just in adversarial edge cases. This makes the miscalibration systematic rather than a rare edge case, though the magnitude of leaked PoV per extrinsic is presumably small (bounded by the cost of a couple of storage mutations), similar in order of magnitude to the ~19% gas leakage documented in the original report for a comparable "bookkeeping after snapshot" flaw.

### Recommendation
Take the "after" proof-size measurement (`get_proof_size()`) *after* all of `StorageWeightReclaim`'s own storage mutations have completed, or alternatively benchmark and add a dedicated constant covering the exact storage operations performed after the snapshot (analogous to the `BankSendGasConsumption` constant recommended in the original report) so the extrinsic is charged for the reclaim bookkeeping's own PoV footprint rather than having it fall outside both the measured and the benchmarked totals.

### Proof of Concept
1. Deploy a parachain runtime with `StorageWeightReclaim<T, S>` wrapping the extension pipeline (as documented/tested in `cumulus/pallets/weight-reclaim/src/tests.rs`).
2. Submit any extrinsic whose `post_info.actual_weight` is lower than the pre-dispatch weight (trivial — nearly all extrinsics report some unspent weight), driving the code through `post_dispatch_details`.
3. Instrument or trace the node-side proof size before and after the full `post_dispatch_details` call (including the `BlockWeight::mutate` and `ExtrinsicWeightReclaimed::put` calls) versus the `proof_size_after_dispatch` value captured at line 202-206.
4. Observe that the storage mutations executed at lines 235-262 and 271 occur after this snapshot and are not reflected in `measured_proof_size`, so their contribution to the block's real PoV is only covered by the fixed `T::WeightInfo::storage_weight_reclaim()` constant, not by live measurement, mirroring the exact "snapshot-then-unaccounted-post-processing" pattern in the referenced Mantra `xfeemarket` finding.
