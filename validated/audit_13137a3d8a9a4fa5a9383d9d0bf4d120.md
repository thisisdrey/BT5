### Title
Arbitrary Command Execution via git `core.fsmonitor` Hook in `go build -buildvcs` VCS Status Stamping - (File: `src/cmd/go/internal/vcs/vcs.go`)

### Summary
The `go` command's VCS-stamping feature (`-buildvcs`, on by default for the main module when it's a git repository) calls `gitStatus`, which shells out to `git status --porcelain` in the working tree without disabling git hooks. If an attacker-controlled repository sets `core.fsmonitor` to a malicious command in `.git/config`, that command executes with the victim's privileges the moment they run `go build`/`go install`/`go version -m` inside the repo — the same primitive described in CVE-2026-67623 for Mistral Vibe.

### Finding Description
When the main module is inside a git working tree, `cmd/go`'s VCS status logic invokes `vcsGit.Status`, implemented as `gitStatus`: [1](#0-0) 

`gitStatus` calls `vcsGit.runOutputVerboseOnly(rootDir, "status --porcelain")`, which flows through `run1` into an `exec.Command("git", "status", "--porcelain", ...)` executed with `dir=rootDir` (the repository root): [2](#0-1) [3](#0-2) 

Unlike `vcsHg`, which sets `Env: []string{"HGPLAIN=+strictflags"}` to suppress user-configured extension behavior, `vcsGit` sets no `Env` field at all: [4](#0-3) [2](#0-1) 

There is no `-c core.fsmonitor=`, no `GIT_CONFIG_NOSYSTEM`, no `--no-optional-locks`, or any other hook-suppression flag passed when invoking `git status`. Native `git status` (and `git status --porcelain`) executes the configured `core.fsmonitor` hook, if present in the repository's `.git/config`, to accelerate status computation — exactly the mechanism the CVE describes for Mistral Vibe. An attacker who can get a victim to clone/checkout a crafted git repository (e.g., a dependency's source tree checked out directly, a forked project, or any repo shared out-of-band) with a malicious `core.fsmonitor` entry in `.git/config` will have that command executed the first time the victim runs `go build` (or any command triggering VCS stamping) inside that repository, because `gitStatus` is called unconditionally as part of build metadata collection.

### Impact Explanation
This is a remote/arbitrary command execution primitive triggered by a normal developer workflow (`go build` on a checked-out repository), not a deliberate `git status` invocation by the user. The victim never has to run git manually — `-buildvcs` stamping is on by default for `go build`/`go install` of the main module when it detects a VCS root. This matches Go's PUBLIC/critical-track class of "unexpected code execution triggered by a routine workflow on attacker-supplied input" if `-buildvcs` auto-detection combined with an untrusted `.git/config` is confirmed reachable without an explicit opt-in by the user. However, note the caveat below on likelihood.

### Likelihood Explanation
This requires the victim to (a) obtain/clone an attacker-crafted repository containing a poisoned `.git/config` (not just poisoned tracked source files) and (b) run `go build`/`go install`/`go version -m` inside it, at which point `-buildvcs` auto-stamping calls `gitStatus`. This is a real developer workflow (e.g., building a forked/cloned repository, or a repo received via zip/tarball that includes a `.git` directory), analogous to how Mistral Vibe's `git status --porcelain` call was exploited. It is a plausible but non-trivial attack because `.git/config` is not typically synced by normal `git clone` of tracked content — it must be delivered via a repository archive, a shared `.git` directory, or a hook installed through some other local means, which somewhat narrows the practical attacker capability compared to a pure "clone and build" scenario. I could not fully verify within the available context whether upstream Go/git already applies mitigations (e.g., some git versions and configurations restrict `core.fsmonitor` to trusted paths, or `safe.directory` protections limit hook execution for non-owned repos) at the git-binary layer itself, since that enforcement lives outside `cmd/go`.

### Recommendation
When invoking `git status` for VCS stamping in `gitStatus`, disable hook execution explicitly, e.g. run `git -c core.fsmonitor= -c core.hooksPath=/dev/null status --porcelain` (or equivalent flags Git provides to disable the fsmonitor hook), similar to how `vcsHg` sets `HGPLAIN` to suppress user-configurable behavior. This prevents repository-local git config from executing arbitrary commands during otherwise passive VCS status queries performed by the toolchain.

### Proof of Concept
Since this requires an actual `git` binary and filesystem access to a working tree with a crafted `.git/config`, a full end-to-end Go test cannot be included in a pure code review, but the following test using `os/exec` and a temp git repo would validate the primitive at the `vcs` package boundary:

```go
func TestGitStatusHookExecution(t *testing.T) {
    dir := t.TempDir()
    run := func(args ...string) {
        cmd := exec.Command("git", args...)
        cmd.Dir = dir
        if out, err := cmd.CombinedOutput(); err != nil {
            t.Fatalf("git %v: %v\n%s", args, err, out)
        }
    }
    run("init")
    run("commit", "--allow-empty", "-m", "init")

    marker := filepath.Join(dir, "pwned")
    hookScript := filepath.Join(dir, "hook.sh")
    os.WriteFile(hookScript, []byte("#!/bin/sh\ntouch "+marker+"\nexit 0\n"), 0755)
    run("config", "core.fsmonitor", hookScript)

    // Simulate what vcsGit.Status/gitStatus does internally.
    cmd := exec.Command("git", "status", "--porcelain")
    cmd.Dir = dir
    cmd.Run()

    if _, err := os.Stat(marker); err != nil {
        t.Fatalf("expected fsmonitor hook to execute and create marker file, got: %v", err)
    }
}
```

Expected assertion: the marker file exists after `git status --porcelain` runs, confirming that `gitStatus`'s underlying invocation (identical arguments, no hook-suppressing flags) would trigger an attacker-controlled `core.fsmonitor` hook whenever `go build -buildvcs` stamps VCS metadata inside such a repository.
