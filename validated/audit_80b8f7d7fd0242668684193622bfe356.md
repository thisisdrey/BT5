### Title
CreateSmartContract Deployment Can Be Griefed via Front-Run Account Creation at the Deterministic Contract Address - (File: `actuator/src/main/java/org/tron/core/actuator/VMActuator.java`)

### Summary
`VMActuator.create()` computes the new contract's address deterministically from the pending transaction's raw data hash and owner address, then rejects deployment if an account already exists at that address. Because the raw transaction (and thus the future contract address) is visible in the mempool before it is packed into a block, any third party can pre-create a normal account at that exact address (e.g., via a cheap `TransferContract`) and permanently block that specific deployment transaction from succeeding — a front-running griefing attack analogous to the "initializer can be front-run" bug class, where the lack of any protection against a third party interfering before the intended state-initializing action completes leads to denial of the legitimate operation.

### Finding Description
The contract address for a `CreateSmartContract` transaction is derived purely from public, pre-broadcast data: [1](#0-0) 

The same deterministic scheme is used at execution time in `VMActuator.create()`, which computes `contractAddress` from the transaction and then **rejects** the deployment if any account already occupies that address: [2](#0-1) 

Meanwhile, `TransferActuator.execute()` (and similarly `TransferAssetActuator`) will silently auto-create a `Normal` `AccountCapsule` at *any* destination address that does not yet exist, with zero permission checks tying the destination address to anything the sender controls: [3](#0-2) 

Because a `CreateSmartContract` transaction is visible in the mempool/P2P network before it is included in a block, any node or client observing it can:
1. Compute `contractAddress = generateContractAddress(trx)` from the raw transaction bytes and owner address (both public).
2. Broadcast a minimal `TransferContract` (1 sun) to that computed address, which the network will confirm as long as it lands in an earlier block/position, auto-creating a `Normal` account there via `TransferActuator.execute()`.
3. When the original `CreateSmartContract` transaction executes, `VMActuator.create()` finds `rootRepository.getAccount(contractAddress) != null` and throws `ContractValidateException("Trying to create a contract with existing contract address: ...")`, permanently failing that specific deployment transaction.

This is structurally the same class of issue as the reported `initialize()` front-run: an operation intended to establish/claim state exclusively for its legitimate initiator (contract creation at a specific address) has no guard preventing an unrelated party from squatting/poisoning that address first, causing denial of the intended operation.

### Impact Explanation
A malicious actor monitoring the mempool can selectively and repeatedly deny specific contract deployments by any target deployer, at negligible cost (one `TransferContract` costs a fixed `TRANSFER_FEE` plus an account-creation fee, both far cheaper than a contract deployment's `feeLimit`/energy cost). This is a griefing/DoS vector against dApp deployers — deployment transactions fail, consuming bandwidth/energy resources and requiring redeployment with a new transaction (and hence a new address), which can be repeatedly front-run again. It does not directly steal funds or corrupt consensus, but it is a reliable, cheap, and repeatable denial-of-service against a core, commonly used broadcastable operation (TVM contract creation).

### Likelihood Explanation
Likelihood is high: the attack requires only observing pending transactions (standard mempool visibility) and issuing an ordinary signed `TransferContract` transaction to a computed address — no special privileges, and the address computation function (`WalletUtil.generateContractAddress` / `Util.generateContractAddress`) is public and simple (`sha3omit12(txRawDataHash || ownerAddress)`), fully derivable by any observer before block inclusion.

### Recommendation
Do not unconditionally fail contract deployment purely because a `Normal` account exists at the pre-image address. Instead, allow contract creation to proceed and take over/merge the existing non-contract account state (similar to how `createAccountIfNotExist`/`addBalance` handle pre-funded contract addresses elsewhere in the VM), or bind account creation at the address to some non-front-runnable value (e.g., using the sender's account sequence/nonce rather than the raw transaction hash, or requiring the account, if pre-existing, to have zero balance/no prior activity and be of `Normal` type before permitting deployment, rather than rejecting outright). At minimum, document and rate-limit this griefing surface, and consider merging balances into the newly created contract account instead of hard-failing.

### Proof of Concept
1. Deployer signs and broadcasts a `CreateSmartContract` transaction `T` with owner address `O`.
2. Attacker observes `T` in the mempool, computes `addr = sha3omit12(sha256(T.raw_data) || O)` exactly as done in `Util.generateContractAddress` (`framework/src/main/java/org/tron/core/services/http/Util.java:236-248`).
3. Attacker broadcasts a `TransferContract` sending 1 sun to `addr`. If this transaction is confirmed in a block prior to (or in the same block, ordered before) `T`, `TransferActuator.execute()` creates a `Normal` `AccountCapsule` at `addr` (`actuator/src/main/java/org/tron/core/actuator/TransferActuator.java:48-58`).
4. When `T` executes, `VMActuator.create()` finds `rootRepository.getAccount(contractAddress) != null` and throws `ContractValidateException("Trying to create a contract with existing contract address: ...")` (`actuator/src/main/java/org/tron/core/actuator/VMActuator.java:360-364`), permanently failing `T`'s intended contract deployment.

  public static byte[] generateContractAddress(Transaction trx, byte[] ownerAddress) {
    // get tx hash
    byte[] txRawDataHash = Sha256Hash
        .of(CommonParameter.getInstance().isECKeyCryptoEngine(), trx.getRawData().toByteArray())
        .getBytes();

    // combine
    byte[] combined = new byte[txRawDataHash.length + ownerAddress.length];
    System.arraycopy(txRawDataHash, 0, combined, 0, txRawDataHash.length);
    System.arraycopy(ownerAddress, 0, combined, txRawDataHash.length, ownerAddress.length);

    return Hash.sha3omit12(combined);
  }
