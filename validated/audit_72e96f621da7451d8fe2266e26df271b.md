Audit Report

## Title
Global per-block message cap in Snowbridge `OutboundQueue` lets a single channel monopolize commitment capacity and delay other users' cross-chain settlement - (File: `bridges/snowbridge/pallets/outbound-queue/src/lib.rs`)

## Summary
`pallet_snowbridge_outbound_queue::do_process_message` gates every channel's message commitment with a single, pallet-wide counter `MessageLeaves`, compared against the shared `T::MaxMessagesPerBlock` (`ConstU32<32>` on Bridge Hub Westend), reset only once per block in `on_initialize`. Because the cap is global rather than per-channel, whichever channel's queue is serviced first by `pallet-message-queue`'s round-robin within a block can exhaust the entire per-block commitment budget, forcing every other channel — including the governance channel — to `Yield` until a subsequent block.

## Finding Description
`MessageLeaves` is declared as a single `StorageValue<_, Vec<H256>, ValueQuery>` shared by every registered channel and cleared once per block via `MessageLeaves::<T>::kill()` in `on_initialize`. [1](#0-0) 
`do_process_message`, invoked by `pallet-message-queue`'s `MessageProcessor` hook regardless of which channel's queue is currently being serviced, checks this same counter and yields once the limit is reached: [2](#0-1) 
The cap is configured identically for all channels via `MaxMessagesPerBlock`: [3](#0-2) 

Although `pallet-message-queue` implements fair, round-robin scheduling across per-origin queues (`ReadyRing`/`ServiceHead`) so that weight is distributed fairly among queues, [4](#0-3) 
that fairness operates purely at the weight-consumption level and has no knowledge of the `MessageProcessor`'s internal state. Once one channel's queue is serviced early in a round and consumes the whole shared `MessageLeaves` budget, `do_process_message` returns `Yield` for every subsequent channel visited later in the *same* round — including the governance channel — even though the module doc explicitly states "processing of governance commands can never be halted." [5](#0-4) 

The pallet's own test confirms this reachable path: 40 low-priority messages from a sibling channel are enqueued, then a governance message is enqueued; with `ServiceWeight` set to `Weight::MAX` (removing weight as a limiting factor), only the mock's `MaxMessagesPerBlock` worth of sibling messages get processed and the governance message is left unprocessed for that entire block-processing round, demonstrating that the shared cap — not weight — is what blocked governance's commitment. [6](#0-5) 

No existing guard reserves capacity per channel or prioritizes the governance channel ahead of ordinary channels when the shared cap is contested; `Nonce` is tracked per-channel but `MessageLeaves` capacity is not. [7](#0-6) 

## Impact Explanation
Any channel with routine access to the Snowbridge exporter (e.g., ordinary AssetHub token-transfer traffic) can, by generating enough outbound messages in a service round, consume the entire shared 32-message (runtime value) commitment budget for that round, delaying delivery of every other channel's messages to Ethereum — including the governance channel, contradicting the pallet's documented liveness guarantee. This is a liveness/fairness degradation of bridge message commitment reachable by unprivileged, fee-paying users, matching the impact gate's "public underpriced work that ... stalls bridge processing."

## Likelihood Explanation
No governance, admin, relayer, validator, or malicious peer/node action is required. An ordinary fee-paying user or a busy parachain generating normal Snowbridge-bound XCM traffic can trigger the condition. It is not a theoretical scenario — the exact mechanism is exercised in the pallet's existing unit test.

## Recommendation
Track commitment capacity per-channel (e.g., a per-channel counter checked against a per-channel share of `MaxMessagesPerBlock`), or reserve a guaranteed minimum slot for the governance channel each block, so that no single channel's message volume can exhaust the entire shared per-block commitment budget and delay other channels, particularly the governance channel.

## Proof of Concept
The existing test `governance_message_does_not_get_the_chance_to_processed_in_same_block_when_congest_of_low_priority_sibling_messages` reproduces the issue: enqueue a large volume of low-priority messages from one sibling channel, then enqueue a governance message, run the block with unrestricted `ServiceWeight`, and observe that the governance message remains unprocessed for that round because the shared `MessageLeaves` cap was already exhausted by the sibling channel. [8](#0-7)

//! The pallet runs each block in `on_initialize` or when being manually called through
//! [`frame_support::traits::ServiceQueues::service_queues`].

//! First it tries to "rotate" the `ReadyRing` by one through advancing the `ServiceHead` to the

//! remaining weight became insufficient to service this queue. If there is enough weight it tries
//! to advance to the next *ready* queue and service it. This continues until there are no more

#[test]
fn governance_message_does_not_get_the_chance_to_processed_in_same_block_when_congest_of_low_priority_sibling_messages(
) {
	use snowbridge_core::PRIMARY_GOVERNANCE_CHANNEL;
	use AggregateMessageOrigin::*;

	let sibling_id: u32 = 1000;
	let sibling_channel_id: ChannelId = ParaId::from(sibling_id).into();

	new_tester().execute_with(|| {
		// submit a lot of low priority messages from asset_hub which will need multiple blocks to
		// execute(20 messages for each block so 40 required at least 2 blocks)
		let max_messages = 40;
		for _ in 0..max_messages {
			// submit low priority message
			let message = mock_message(sibling_id);
			let (ticket, _) = OutboundQueue::validate(&message).unwrap();
			OutboundQueue::deliver(ticket).unwrap();
		}

		let footprint = MessageQueue::footprint(Snowbridge(sibling_channel_id));
		assert_eq!(footprint.storage.count, (max_messages) as u64);

		let message = mock_governance_message::<Test>();
		let (ticket, _) = OutboundQueue::validate(&message).unwrap();
		OutboundQueue::deliver(ticket).unwrap();

		// move to next block
		ServiceWeight::set(Some(Weight::MAX));
		run_to_end_of_next_block();

		// first process 20 messages from sibling channel
		let footprint = MessageQueue::footprint(Snowbridge(sibling_channel_id));
		assert_eq!(footprint.storage.count, 40 - 20);

		// and governance message does not have the chance to execute in same block
		let footprint = MessageQueue::footprint(Snowbridge(PRIMARY_GOVERNANCE_CHANNEL));
		assert_eq!(footprint.storage.count, 1);

		// move to next block
		ServiceWeight::set(Some(Weight::MAX));
		run_to_end_of_next_block();

		// now governance message get executed in this block
		let footprint = MessageQueue::footprint(Snowbridge(PRIMARY_GOVERNANCE_CHANNEL));
		assert_eq!(footprint.storage.count, 0);

		// and this time process 19 messages from sibling channel so we have 1 message left
		let footprint = MessageQueue::footprint(Snowbridge(sibling_channel_id));
		assert_eq!(footprint.storage.count, 1);

		// move to the next block, the last 1 message from sibling channel get executed
		ServiceWeight::set(Some(Weight::MAX));
		run_to_end_of_next_block();
		let footprint = MessageQueue::footprint(Snowbridge(sibling_channel_id));
		assert_eq!(footprint.storage.count, 0);
	});
}
