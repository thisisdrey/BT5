### Title
Unauthenticated account-list stuffing via dust transfers permanently blocks victim from onboarding new collateral/debt tokens (position-management DoS) - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
`Pool` enforces a per-account cap `MAX_TOKENS_PER_USER = 30` across `debtTokensOfAccount + depositTokensOfAccount`, reverting with `UserReachedMaxTokens` once reached. Any `DepositToken` mint (`_mint`) or plain `transfer`/`transferFrom` to a first-time holder calls `pool.addToDepositTokensOfAccount`, which enforces the cap. An unprivileged attacker can dust-transfer 1 wei of every listed deposit token to a victim, permanently filling their account list. After that, any `deposit`, `mint`, `issue`, or inbound `transfer` involving a token not already in the victim's list reverts — the victim cannot add a new collateral type, open a new debt position, or even receive deposit tokens from third parties. ### Finding Description
- `DepositToken._transfer` and `DepositToken._mint` call `pool.addToDepositTokensOfAccount(recipient_)` whenever the recipient's prior balance is `0` and `amount_ > 0` — there is no minimum amount and no opt-in. [5](#0-4) [6](#0-5) 
- `Pool.addToDepositTokensOfAccount` / `addToDebtTokensOfAccount` apply `onlyIfAdditionWillNotReachMaxTokens`, which reverts once `debtTokensOfAccount + depositTokensOfAccount >= 30`. [7](#0-6) 
- The attacker only needs to deposit dust amounts of each whitelisted collateral via `DepositToken.deposit` (public, `whenNotPaused`), then `transfer` 1 wei of each to the victim. If the pool lists N deposit tokens and the victim's combined list is already size `30 - N` or less, one transaction batch fills it.
- Consequences after stuffing:
  - `deposit`/`mint` of any *new* collateral type reverts (`addToDepositTokensOfAccount` → `UserReachedMaxTokens`), so the victim cannot top up with a different collateral when their position approaches liquidation. Front-running the victim's rescue deposit keeps the block in place. [8](#0-7) 
  - `DebtToken.issue`/`mint` of any new synthetic reverts the same way via `addToDebtTokensOfAccount`, so the victim cannot open additional debt positions. [9](#0-8) 
  - Any inbound `transfer`/`transferFrom`/`seize` of a deposit token the victim doesn't hold reverts, freezing the victim's ability to receive collateral tokens.
- No modifier stops this: `transfer` has no cap or whitelist check, pause flags are governance-controlled and off in normal operation, and `SynthContext`/`ReentrancyGuardTransient` are irrelevant to the attack path.

### Impact Explanation
Temporary freezing of funds and denial of position management: the victim is blocked from depositing new collateral types, issuing new synths, and receiving deposit tokens. If the victim's position drifts toward the liquidation threshold while their existing collateral type cannot save them (e.g., exhausted `issuableLimit`), the stuffed list prevents adding a fresh collateral type, forcing liquidation and realizing bad debt/seizure that a healthy deposit would have avoided. The victim can clear slots by sending out the dust tokens (only they own them), but the attacker can re-stuff each freed slot in the same or subsequent transactions (front-running), so remediation is unreliable — analogous to the CVE's unauthenticated-input-driven DoS: a permissionless `transfer` poisons per-account state used by an authorization-style cap check.

### Likelihood Explanation
- Attacker requirements: only EOAs/public entry points — `DepositToken.deposit` for each whitelisted underlying (dust), then `DepositToken.transfer` to the victim. Cost is bounded by the number of listed collateral tokens in the pool (well under 30 in practice) × dust amount + gas.
- Impact is real but bounded: positions the victim can still service with existing collateral are unaffected, and the victim can self-clean the list (subject to re-stuffing races). Consistent with a DoS-class (A:H) issue rather than direct theft.

### Recommendation
- Do not revert on cap exhaustion in `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` when triggered by unsolicited transfers; alternatively, only enforce `MAX_TOKENS_PER_USER` for tokens the account is actually using (e.g., tokens with locked collateral or debt participation), or drop unsolicited dust entries: e.g., require a minimum amount (`amount_` or resulting balance above a threshold) before inserting into `depositTokensOfAccount`, and/or let recipients remove entries themselves via a `removeFromDepositTokensOfAccount(account_, token_)`-style escape hatch authorized to `account_` when balance is zero.
- Alternatively, only add tokens on `deposit`/`issue` initiated by the account, not on inbound `transfer`.

### Proof of Concept
Hardhat fork test against a deployed `Pool` (e.g., Base/mainnet per `deployments/*/Pool.json`):

```ts
// test/griefing.maxTokens.spec.ts — run with: npx hardhat test --network hardhat (fork config in hardhat.config.ts)
import {ethers} from "hardhat";
import {expect} from "chai";

const POOL = "0x<deployedPool>";          // e.g. deployments/base/Pool.json address
const VICTIM = "0x<victim>";             // account with open position, combined token list size S

it("stuffs victim's account list with dust, blocking new collateral deposits", async () => {
  const [attacker] = await ethers.getSigners();
  const pool = await ethers.getContractAt("Pool", POOL);
  const depositTokens: string[] = await pool.getDepositTokens(); // all whitelisted collaterals

  // Victim's current list size
  const existing = (await pool.getDepositTokensOfAccount(VICTIM))
    .concat(await pool.getDebtTokensOfAccount(VICTIM));

  // 1. For each deposit token the victim doesn't hold, attacker deposits dust
  //    then transfers 1 wei of msdTOKEN to the victim -> addToDepositTokensOfAccount
  for (const dt of depositTokens) {
    if (existing.includes(dt)) continue;
    const msd = await ethers.getContractAt("DepositToken", dt);
    const underlying = await ethers.getContractAt("IERC20", await msd.underlying());
    await underlying.approve(dt, 1);               // attacker holds/obtains dust underlying
    await msd.deposit(1, attacker.address);
    await msd.transfer(VICTIM, 1);                 // inserts dt into victim's list
    if ((await pool.getDepositTokensOfAccount(VICTIM)).length
        + (await pool.getDebtTokensOfAccount(VICTIM)).length
        >= await pool.MAX_TOKENS_PER_USER()) break;
  }

  // 2. Victim attempts to deposit a collateral type they don't yet hold -> reverts
  const newCollateral = await ethers.getContractAt(
    "DepositToken",
    depositTokens.find(dt => !(await pool.getDepositTokensOfAccount(VICTIM)).includes(dt))!
  );
  await expect(newCollateral.deposit(1e6, VICTIM)).to.be.revertedWithCustomError(pool, "UserReachedMaxTokens");

  // 3. Any inbound transfer of a not-held deposit token also reverts
  await expect(msdAny.transfer(VICTIM, 1)).to.be.revertedWithCustomError(pool, "UserReachedMaxTokens");
});
```

On a local non-fork setup the same flow is reproduced using the real `Pool`, `DepositToken`, `DebtToken` deployments as in `test/Pool.test.ts` ("should revert when reach max tokens"), except driven by `DepositToken.transfer(VICTIM, 1)` from the attacker instead of impersonated token calls — demonstrating that the cap check `onlyIfAdditionWillNotReachMaxTokens` is reachable by any unprivileged sender pushing dust into the victim's `depositTokensOfAccount`.
