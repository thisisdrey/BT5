### Title
Precision-manipulable Bancor pricing in TRC10 Exchange enables value extraction via floating-point rounding - ([File: chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java])

### Summary
The default (non-hardened) TRC10 `Exchange` pricing engine computes swap output using `double`-precision `Math.pow` calls and truncates intermediate and final results with `(long)` casts [1](#0-0) [2](#0-1) . This is the exact price-computation path reached by any unprivileged account that broadcasts an `ExchangeTransactionContract`, `ExchangeInjectContract`, or `ExchangeWithdrawContract` [3](#0-2) . The codebase itself acknowledges this arithmetic is imprecise and unsafe: a parallel `SafeExchangeProcessor` using `BigDecimal` and exact-overflow arithmetic was added, gated behind the `allowHardenExchangeCalculation` dynamic property which is only enabled through a committee/SR governance proposal (`ProposalUtil`, `ProposalService`) rather than being the default path [4](#0-3) . A dedicated regression test explicitly demonstrates that the legacy `ExchangeProcessor` and the hardened `SafeExchangeProcessor` produce *different* results for identical inputs (`Assert.assertNotEquals(anotherTokenQuant, result)`), confirming the legacy path's output diverges from the mathematically-correct value [5](#0-4) .

### Finding Description
`ExchangeCapsule.transaction()` selects between two `Processor` implementations based on the `hardenedCalc` flag, which is derived from `chainBaseManager.getDynamicPropertiesStore().allowHardenExchangeCalculation()` [6](#0-5) . Unless this dynamic property has been switched on via governance, every `ExchangeTransactionActuator.execute()` call routes through `ExchangeProcessor`, whose Bancor-style relay-token math relies on `double` arithmetic and `(long)` truncation at two chained stages (`exchangeToSupply` then `exchangeFromSupply`) [7](#0-6) .

Because floating-point `Math.pow` results are then hard-truncated toward zero via `(long) issuedSupply` / `(long) exchangeBalance`, the effective exchange rate for a given trade can deviate from the theoretically correct Bancor-curve value, and this deviation is a deterministic function of trade size and pool ratio. An attacker who can freely choose `tokenQuant` (fully attacker-controlled input in `ExchangeTransactionContract`) can probe/split trades to consistently land on rounding-favorable outputs, repeatedly extracting more of the counter-asset than the pool's true price implies, or forcing pool reserves in `ExchangeCapsule` (persisted via `Commons.putExchangeCapsule`) into a manipulated state that skews subsequent trades for other users. This mirrors the Loopscale root cause conceptually — a self-referential pricing mechanism whose numeric integrity can be gamed by a caller who fully controls the trade parameters that feed into it — except in java-tron's case the "oracle" is the Exchange contract's own internal bonding-curve calculation rather than an external price feed.

The `validate()` paths for `ExchangeTransactionActuator`/`ExchangeInjectActuator`/`ExchangeWithdrawActuator` only bound-check the *result* of this same imprecise function (e.g. `anotherTokenQuant < tokenExpected`) [8](#0-7) , so validation cannot catch systemic drift introduced by the pricing function itself — it only confirms the actuator is internally self-consistent with its own (buggy) math.

### Impact Explanation
If `allowHardenExchangeCalculation` is not enabled on a running network (which appears to be the historical/default state, since it is proposal-gated rather than unconditionally enabled), any account can submit `ExchangeTransactionContract`/`ExchangeInjectContract`/`ExchangeWithdrawContract` transactions that exploit the floating-point truncation in `ExchangeProcessor` to systematically skew swap outputs in their favor at the expense of the exchange pool and other liquidity participants. Repeated exploitation can drain TRX/TRC10 balances held in `ExchangeCapsule` pools, i.e., unauthorized value extraction / theft of funds reachable purely through unprivileged transaction broadcast.

### Likelihood Explanation
High reachability: any account holding TRX/TRC10 balance can construct and broadcast the relevant contract with attacker-chosen `quant`/`expected` values with no special privileges, matching the "unprivileged transaction broadcaster" threat model. The likelihood of the flaw's existence is corroborated by the project's own test suite proving the legacy processor's output differs from the corrected `BigDecimal`-based one for identical inputs.

### Recommendation
Make `SafeExchangeProcessor` (or an equivalent exact-arithmetic implementation) unconditionally the exchange pricing path for `ExchangeTransactionActuator`, `ExchangeInjectActuator`, and `ExchangeWithdrawActuator`, rather than gating exact math behind an optional governance proposal (`allowHardenExchangeCalculation`). At minimum, add monotonicity/invariant checks (e.g. constant-product/Bancor invariant bounds) in `ExchangeCapsule.transaction()` that reject any pricing result inconsistent with the exact BigDecimal-computed value, independent of which processor executed.

### Proof of Concept
1. Deploy/observe a TRC10 `Exchange` pool that has not had `allowHardenExchangeCalculation` enabled (default committee parameter value), so `ExchangeCapsule.transaction()` uses `ExchangeProcessor` (legacy double math) per [6](#0-5) .
2. As an unprivileged account, broadcast a sequence of `ExchangeTransactionContract` calls (choosing `quant` values calibrated near pool-ratio thresholds where the `(long)` truncation in `exchangeToSupply`/`exchangeFromSupply` [9](#0-8)  rounds in the caller's favor).
3. Compare received `anotherTokenQuant` against the exact value computed by `SafeExchangeProcessor` for the same inputs — the project's own `ExchangeProcessorTest.testStrictMath` demonstrates these values differ for a broad range of realistic pool/quant combinations [10](#0-9) .
4. Repeating step 2 across many transactions compounds the discrepancy, extracting value from the pool beyond what the true bonding curve would allow.

**Uncertainty note:** I was unable to directly confirm the compiled default value of `allowHardenExchangeCalculation` (the `DynamicPropertiesStore.java` file content could not be fully retrieved due to indexing limits), so I cannot state with certainty whether this property currently defaults to `0` (vulnerable) on mainnet or has already been enabled via a passed proposal. The `ProposalUtil`/`ProposalService` gating pattern strongly suggests it is off-by-default until an SR vote enables it, consistent with typical java-tron hard-fork rollout mechanics, but this should be verified directly against current mainnet chain parameters before treating this as an active, exploitable condition.

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
