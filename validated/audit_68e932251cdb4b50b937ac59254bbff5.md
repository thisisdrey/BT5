### Title
nearcore mishandles receipt size checking, allowing oversized `ActionReceipt` past `max_receipt_size` validation - (File: `runtime/runtime/src/receipt_manager.rs`)

### Summary
The btcd advisory concerns witness/receipt size checking being validated at the wrong point relative to when the object is finalized, allowing an oversized object to slip past the size gate. nearcore has a directly analogous, in-scope defect in receipt-size enforcement: `ReceiptManager::create_action_receipt` mutates an *already validated* receipt's `output_data_receivers` by pushing new `DataReceiver` entries after the parent receipt has already passed size validation, so a receipt that was at (or near) `max_receipt_size` can grow beyond the limit without being re-checked. This is a known, still-present bug (tracked as nearcore issue #12606) reachable purely from an ordinary account's function-call transactions.

### Finding Description
`validate_receipt` in `runtime/runtime/src/verifier.rs` computes `borsh::object_length(receipt)` and rejects it with `ReceiptSizeExceeded` if it exceeds `limit_config.max_receipt_size`, but only for `ValidateReceiptMode::NewReceipt`, immediately after the receipt is produced: [1](#0-0) 

However, `ReceiptManager::create_action_receipt` — used when a contract creates a promise dependent on other promises (`promise_and`/`promise_then`/`promise_batch_then`) — pushes a new `DataReceiver` into the *already-created, already-sized* parent receipt's `output_data_receivers` vector: [2](#0-1) 

Because `output_data_receivers` can be mutated *after* the parent receipt has been sized/validated (e.g., when a later `promise_then` call references it as a dependency, or via `promise_return`), the final borsh-serialized receipt that gets committed to state/witness can exceed `max_receipt_size` even though it passed the `ReceiptSizeExceeded` check at creation time. The runtime code explicitly documents this as a known, unresolved bug and works around its symptoms rather than fixing the root cause: [3](#0-2) [4](#0-3) 

The project's own test-loop tests reproduce this exact class of bug and mark it explicitly as unfixed: [5](#0-4) [6](#0-5) 

This is the same bug class as the btcd advisory: a size gate is checked before the object is fully assembled, so subsequent mutation invalidates the previously-performed size check, permitting an oversized on-wire object into the system.

### Impact Explanation
An oversized receipt bypasses the protocol's `max_receipt_size` invariant (4 MiB), which is documented as load-bearing for keeping `ChunkStateWitness` bounded (target ~21 MiB total): [7](#0-6) 
Oversized receipts inflate outgoing-receipt/witness sizes beyond the values the protocol assumes when bounding chunk witness size, and `try_forward` in cross-shard forwarding has to special-case and clamp the observed size as a "bug workaround" to avoid receipts getting permanently stuck in the outgoing buffer: [3](#0-2) 
This can manifest as chunks/witnesses growing beyond their intended size ceiling (network/availability degradation reachable from an ordinary contract call) and, in the resume/yield or value-return paths, receipts stuck or requiring special handling to avoid a validator crash ("runtime shouldn't die when it encounters a large receipt").

### Likelihood Explanation
The bug is triggered by ordinary, unprivileged contract calls — no validator or network-level privilege is required. The project's own tests construct it via standard `FunctionCall` actions (`promise_return`, `yield`/`resume`, and value-return code paths) from a regular signed transaction, confirming it is reachable purely from a deployed contract driven by a normal user transaction: [8](#0-7) 

### Recommendation
Re-validate (or re-check) receipt size after any post-creation mutation to `output_data_receivers` (and any other field mutated after the initial `validate_receipt` call), or defer the `ReceiptSizeExceeded` check until the receipt is fully finalized (i.e., until no further `output_data_receivers`/output mutations can occur) rather than checking it once at initial creation. Remove the compensating "clamp to max_receipt_size" workaround in `try_forward` only once the root-cause fix guarantees receipts can no longer exceed the limit.

### Proof of Concept
The project's own regression tests are a working PoC of the same defect class:
- `test_max_receipt_size_promise_return`: builds a receipt at exactly `max_receipt_size`, then has the contract logic add `output_data_receivers`, pushing it over the limit; the receipt is not rejected as intended. [9](#0-8) 
- `test_max_receipt_size_value_return`: a returned value wrapped into a `Data` receipt exceeds `max_receipt_size` and is likewise not rejected as expected. [10](#0-9) 

Both tests are annotated in-source as reproducing "a bug" (linking nearcore issue #12606), confirming that the root-cause defect (size validated before receipt is fully mutated) exists and is currently only mitigated, not fixed.

pub(crate) fn validate_receipt(
    limit_config: &LimitConfig,
    receipt: &Receipt,
    current_protocol_version: ProtocolVersion,
    mode: ValidateReceiptMode,
) -> Result<(), ReceiptValidationError> {
    if mode == ValidateReceiptMode::NewReceipt {
        let receipt_size: u64 =
            borsh::object_length(receipt).unwrap().try_into().expect("Can't convert usize to u64");
        if receipt_size > limit_config.max_receipt_size {
            return Err(ReceiptValidationError::ReceiptSizeExceeded {
                size: receipt_size,
                limit: limit_config.max_receipt_size,
            });
        }

    pub(super) fn create_action_receipt(
        &mut self,
        input_data_ids: Vec<CryptoHash>,
        receipt_indices: Vec<ReceiptIndex>,
        receiver_id: AccountId,
    ) -> Result<ReceiptIndex, VMLogicError> {
        assert_eq!(input_data_ids.len(), receipt_indices.len());
        for (data_id, receipt_index) in input_data_ids.iter().zip(receipt_indices.into_iter()) {
            self.action_receipts
                .get_mut(receipt_index as usize)
                .ok_or(HostError::InvalidReceiptIndex { receipt_index })?
                .output_data_receivers
                .push(DataReceiver { data_id: *data_id, receiver_id: receiver_id.clone() });
        }

        let new_receipt = ActionReceiptMetadata {
            receiver_id,
            refund_to: None,
            output_data_receivers: vec![],
            input_data_ids,
            actions: vec![],
            is_promise_yield: false,
        };
        let new_receipt_index = self.action_receipts.len() as ReceiptIndex;
        self.action_receipts.push(new_receipt);
        Ok(new_receipt_index)
    }

#[test]
fn test_max_receipt_size_promise_return() {
    init_test_logger();

    let account = create_account_id("account0");
    let account_signer = create_user_test_signer(&account);
    let mut env = TestLoopBuilder::new()
        .enable_rpc()
        .add_user_account(&account, Balance::from_near(10_000))
        .build();

    // Deploy the test contract
    let deploy_contract_tx = SignedTransaction::deploy_contract(
        101,
        &account,
        near_test_contracts::rs_contract().into(),
        &account_signer,
        env.rpc_node().head().last_block_hash,
    );
    env.rpc_runner().run_tx(deploy_contract_tx, Duration::seconds(5));

    // User calls a contract method
    // Contract method creates a DAG with two promises: [A -then-> B]
    // When promise A is executed, it creates a third promise - `C` and does a `promise_return`.
    // The DAG changes to: [C ->then-> B]
    // The receipt for promise C is a maximum size receipt.
    // Adding the `output_data_receivers` to C's receipt makes it go over the size limit.
    let base_receipt_template = Receipt::V0(ReceiptV0 {
        predecessor_id: account.clone(),
        receiver_id: account.clone(),
        receipt_id: CryptoHash::default(),
        receipt: ReceiptEnum::Action(ActionReceipt {
            signer_id: account.clone(),
            signer_public_key: account_signer.public_key().into(),
            gas_price: Balance::ZERO,
            output_data_receivers: vec![],
            input_data_ids: vec![],
            actions: vec![Action::FunctionCall(Box::new(FunctionCallAction {
                method_name: "noop".into(),
                args: vec![],
                gas: Gas::ZERO,
                deposit: Balance::ZERO,
            }))],
        }),
    });
    let base_receipt_template = action_receipt_v1_to_latest(&base_receipt_template);
    let base_receipt_size = borsh::object_length(&base_receipt_template).unwrap();
    let max_receipt_size = 4_194_304;
    let args_size = max_receipt_size - base_receipt_size;

    // Call the contract
    let large_receipt_tx = SignedTransaction::call(
        102,
        account.clone(),
        account.clone(),
        &account_signer,
        Balance::ZERO,
        "max_receipt_size_promise_return_method1".into(),
        format!("{{\"args_size\": {}}}", args_size).into(),
        Gas::from_teragas(300),
        env.rpc_node().head().last_block_hash,
    );
    env.rpc_runner().run_tx(large_receipt_tx, Duration::seconds(5));

    // Make sure that the last promise in the DAG was called
    let assert_test_completed = SignedTransaction::call(
        103,
        account.clone(),
        account,
        &account_signer,
        Balance::ZERO,
        "assert_test_completed".into(),
        "".into(),
        Gas::from_teragas(300),
        env.rpc_node().head().last_block_hash,
    );
    env.rpc_runner().run_tx(assert_test_completed, Duration::seconds(5));

    assert_oversized_receipt_occurred(&env.validator());
}
