### Title
Missing domain separation (StackerDB contract ID) in `SlotMetadata` signature allows chunk replay across StackerDB contracts - ([File: libstackerdb/src/libstackerdb.rs])

### Summary
`SlotMetadata::auth_digest` — the digest that `StackerDBChunkData` signatures are computed and verified over — commits only to `slot_id`, `slot_version`, and `data_hash`. It never binds the signature to the StackerDB smart-contract identifier (or any network/chain identifier) that the chunk is destined for. This is exactly the "missing domain separator" bug class described in the report (there, chain ID was missing from an EIP-712-style domain separator, enabling cross-chain replay). Here, the StackerDB contract ID is the analogous "domain," and its absence enables cross-contract (cross-"chain") chunk replay for any signer who owns the same `slot_id` in two different StackerDB contracts.

### Finding Description
`SlotMetadata::auth_digest()` computes:
```rust
hasher.update(self.slot_id.to_be_bytes());
hasher.update(self.slot_version.to_be_bytes());
hasher.update(self.data_hash.0);
``` [1](#0-0) 

`sign`/`verify` operate purely on this digest, with the caller-supplied `StacksAddress` used only to check *who* signed, not *what contract* the signature was scoped to: [2](#0-1) 

The actual write-path validation, `StackerDBs::validate_received_chunk` (used both for downloaded chunks and for unsolicited `StackerDBPushChunk`), looks up the expected signer address *for that specific contract* (`get_slot_signer(smart_contract_id, slot_id)`) and then calls `slot_metadata.verify(&addr)` — but the cryptographic signature itself carries no record of `smart_contract_id`: [3](#0-2) 

Crucially, the signer→slot mapping is *shared identically* across the different message-lane StackerDB contracts for a given signer set. The `signers-1-xxx.clar` boot contract simply proxies to the single shared page in `.signers`:
```
(define-read-only (stackerdb-get-signer-slots)
    (contract-call? .signers stackerdb-get-signer-slots-page u1))
``` [4](#0-3) 

and `stackerdb-get-signer-slots-page` returns the exact same ordered list (`stackerdb-signer-slots-1`) to *every* lane contract for signer set 1 (BlockResponse, Transactions, DkgResults, etc.): [5](#0-4) 

Consequently, a given signer `X` is assigned the *same* `slot_id` in every one of these sibling lane contracts (`signers-1-0`, `signers-1-1`, `signers-1-2`, …). Because `auth_digest` does not include the contract ID, a chunk `(slot_id, slot_version, data_hash, sig)` that was legitimately signed and broadcast by signer `X` for lane contract `signers-1-0` is a *bit-for-bit valid* signed chunk for the identical slot in sibling contract `signers-1-1` (or any future lane sharing the mapping) — no private key is required by the attacker; they only need to have observed the chunk on the wire (StackerDB chunks/pushes are unencrypted P2P/HTTP payloads) and resubmit it to a different contract/replica, or via `StackerDBPushChunk` gossip.

The only mitigation is an application-layer, best-effort heuristic in the signer's own `SignerEvent` decoder — `signer_message_payload_matches_lane` — which inspects the first payload byte to guess whether a `SignerMessageTypePrefix` matches the expected lane, and the code explicitly documents that this mapping is fixed to v0 semantics and will silently fail to protect future message versions: [6](#0-5) 

This is filtering only in the higher-level signer-event consumer path, not in the StackerDB storage/replication layer itself (`net/stackerdb/mod.rs`, `net/api/poststackerdbchunk.rs`), which will happily accept, store, and further gossip the replayed chunk as a validly-signed slot update for the wrong contract, since `validate_received_chunk`/`try_replace_chunk` never check contract identity as part of the signature.

### Impact Explanation
This breaks the "authenticated for this specific contract" equality that StackerDB storage relies on: a signature that authenticates data for contract A is accepted as authenticating (differently-interpreted) data for contract B, purely because the digest omits the contract ID. This allows:
- Unauthenticated write of forged/misattributed data into a StackerDB slot of another contract (the "chunk" itself is legitimately signed, but for the wrong context), causing that slot to serve stale or wrong-lane bytes as if freshly authored for that contract.
- Network-wide propagation of this forged-for-context chunk via the P2P StackerDB push/replication protocol (`handle_unsolicited_StackerDBPushChunk`), since the signature check alone passes.
This satisfies the Critical/High bar of "unauthenticated/unauthorized write to state or StackerDB" and "network-wide propagation of forged data."

### Likelihood Explanation
Likelihood is real but conditional: it requires (a) the same signer address being assigned the same `slot_id` across two StackerDB contracts (which is the *guaranteed* case for sibling message-lane contracts under a signer set, as shown above), and (b) the target slot's current version being lower than the replayed chunk's version (an attacker-observable, often satisfiable condition, especially for freshly-provisioned lanes/reward cycles starting at version 0). No private key or privileged role is needed — only passive observation of gossiped/pushed chunks and the ability to relay a copy of the wire message, which any P2P peer can do.

### Recommendation
Include the StackerDB smart-contract identifier (and ideally the node's `network_id`/chain ID) as part of the signed digest in `SlotMetadata::auth_digest`, e.g., hash `contract_id.to_string()` (or a fixed-width serialization of the qualified contract identifier) together with `slot_id`, `slot_version`, and `data_hash`. This requires plumbing the contract ID into `sign`/`verify`/`recover_pk` call sites (`StackerDBChunkData::sign/verify/recover_pk`, `SlotMetadata::sign/verify`), and updating all StackerDB write/validation paths (`net/stackerdb/mod.rs::validate_received_chunk`, `net/stackerdb/db.rs::try_replace_chunk`, `net/api/poststackerdbchunk.rs`) and libsigner's own chunk signing/verification (`StackerDBChunkData::sign` calls in `stacks-signer`) accordingly, since this is a wire-format/signature-scheme change requiring careful compatibility handling.

### Proof of Concept
1. Attacker observes signer `X`'s validly-signed `StackerDBChunkData { slot_id: 3, slot_version: 5, sig, data: <BlockResponse bytes> }` being pushed/gossiped for contract `ST....signers-1-0`.
2. Attacker resubmits the identical `StackerDBChunkData` bytes (same `slot_id`, `slot_version`, `sig`, `data`) to a peer node, but targeting contract `ST....signers-1-1` (a different message-id lane for the same signer set 1), either via the `PostStackerDBChunk` RPC or via `StackerDBPushChunk` gossip.
3. Because `signers-1-1` shares the identical `(signer → slot_id)` mapping via `stackerdb-get-signer-slots-page`, `get_slot_signer(signers-1-1, 3)` resolves to the same address `X`.
4. `SlotMetadata::verify` succeeds because the signed digest never included the contract ID — the signature that was valid for `signers-1-0` is equally valid for `signers-1-1`.
5. If the target slot's stored version in `signers-1-1` is `< 5`, `validate_received_chunk`/`try_replace_chunk` accept and store the chunk, and it is further relayed to other peers as legitimate content for `signers-1-1`, slot 3 — even though it was never signed with that contract in mind.

    fn auth_digest(&self) -> Sha512Trunc256Sum {

    /// Sign this slot metadata, committing to slot_id, slot_version, and
    /// data_hash.  Sets self.signature to the signature.
    /// Fails if the underlying crypto library fails
    pub fn sign(&mut self, privkey: &StacksPrivateKey) -> Result<(), Error> {
        let auth_digest = self.auth_digest();
        let sig = privkey
            .sign(&auth_digest.0)
            .map_err(|se| Error::SigningError(se.to_string()))?;

        self.signature = sig;
        Ok(())
    }

    /// Verify that a given principal signed this chunk metadata.
    /// Note that the address version is ignored.
    pub fn verify(&self, principal: &StacksAddress) -> Result<bool, Error> {
        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )
        .map_err(|ve| Error::VerifyingError(ve.to_string()))?;

        let pubkh = Hash160::from_node_public_key(&pubk);
        Ok(pubkh == *principal.bytes())
    }
