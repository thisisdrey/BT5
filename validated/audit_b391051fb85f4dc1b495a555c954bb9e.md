Audit Report

## Title
Unauthenticated deposits to the DAP staging account are trusted as legitimate burns, letting anyone deflate `InactiveIssuance`/active issuance at will - (File: `substrate/frame/dap/src/lib.rs`)

## Summary
`pallet-dap`'s `on_idle` hook reads whatever `reducible_balance` is present in the deterministically-derived `staging_account()` and unconditionally treats the full amount as a legitimate slash/burn credit, calling `Unbalanced::deactivate()` on it. Since `staging_account()` is a plain `AccountId` derived via `into_sub_account_truncating(DAP_PALLET_ID, DAP_STAGING_ACCOUNT_ID)`, any signed account can fund it via ordinary `pallet_balances::transfer_allow_death`/`transfer_keep_alive`, causing the runtime to silently deactivate issuance with no real slash/burn having occurred.

## Finding Description
`Pallet::staging_account()` derives a sub-account from public constants `DAP_PALLET_ID = PalletId(*b"dap/buff")` and `DAP_STAGING_ACCOUNT_ID = b"staging"`, and is even exposed via the `staging()` view function, so no guessing is required: [3](#0-2) [4](#0-3) [5](#0-4) .

Legitimate slash/burn flows deposit into this account via the `OnUnbalanced` impl (`on_nonzero_unbalanced`) and its legacy adapter: [6](#0-5) .

`on_idle` then reads the account's raw `reducible_balance` — with no provenance tracking distinguishing a wired `OnUnbalanced` credit from an ordinary transfer — moves it to the buffer account, and deactivates the exact same amount via `deactivate_buffer_funds`: [7](#0-6) .

Because `staging_account()` is a normal `AccountId`, any signed account can call `pallet_balances::transfer_allow_death` or `transfer_keep_alive` — both of which are unrestricted, unprivileged, signed extrinsics that accept any destination `AccountId` — to send funds there: [1](#0-0) [2](#0-1) . No check anywhere in `on_idle` or `staging_account()`/the `OnUnbalanced` impl binds a balance increase to an actual slash/burn event; the pallet trusts "balance present in staging" as proof that a real burn credit occurred.

`deactivate()` lowers `active_issuance` (`total_issuance - InactiveIssuance`) while leaving `total_issuance` untouched, as confirmed by the conformance test: [8](#0-7) , and reproduced in the pallet's own integration test for the legitimate path: [9](#0-8) .

The pallet's own doc comment confirms the governance significance: deactivation is meant to "exclude [funds] from governance voting": [10](#0-9) , and `Balances::InactiveIssuance` is read by `pallet-referenda`'s servicing logic per its weight/storage annotations, making active issuance a governance-threshold-critical value.

## Impact Explanation
Any unprivileged, funded account can deterministically compute or query `staging_account()`, transfer an arbitrary self-chosen amount to it via a completely ordinary `Balances::transfer_keep_alive` call, and have `on_idle` process it as if it were a genuine slash/burn, deflating `active_issuance` without any real burn occurring. Since `active_issuance` feeds OpenGov referenda support/approval threshold arithmetic, this compromises intended runtime accounting/governance-threshold behavior — a runtime bug that corrupts a specific state value (`Balances::InactiveIssuance`, and consequently `active_issuance`) without requiring any privileged role, matching the "runtime bugs that compromise intended behavior" impact criterion.

## Likelihood Explanation
Highly feasible and fully repeatable: the target account is deterministic and even exposed via a public view function, requiring no guessing; the only prerequisite is a funded, ordinary signed account and a single standard `transfer_keep_alive`/`transfer_allow_death` call — no governance, validator, collator, or relayer privilege is needed. `on_idle` automatically drains and deactivates on the next idle block, so the attack is mechanical, low-effort, and repeatable at will (bounded only by the attacker's own funds, which move into the buffer account rather than being returned).

## Recommendation
Do not use the raw balance of `staging_account()` as ground truth for the deactivation amount. Instead, track the amount to deactivate explicitly at the point of `OnUnbalanced::on_nonzero_unbalanced` (e.g., accumulate a dedicated `PendingDeactivation` storage value incremented only within the trusted burn/slash callback), and have `on_idle` drain and deactivate exactly that tracked amount instead of `reducible_balance(staging_account)`. Alternatively, ensure the staging account cannot receive ordinary transfers (e.g., via a transfer-blocking account type or filter) so only the pallet's own `OnUnbalanced` credit path can fund it.

## Proof of Concept
1. Query `pallet_dap::Pallet::<Runtime>::staging()` (or derive `sp_dap::DAP_PALLET_ID.into_sub_account_truncating(sp_dap::DAP_STAGING_ACCOUNT_ID)`).
2. From any funded, unprivileged account, submit `Balances::transfer_keep_alive(staging_account, X)` for an arbitrary `X`.
3. Allow `pallet_dap::on_idle` to run on the next idle block (automatic).
4. Observe: buffer account balance increases by `X`, and `Balances::InactiveIssuance` increases by `X` — identical to the legitimate slash-path assertions in `substrate/frame/dap/src/tests/on_unbalanced.rs` (lines 132-144) — despite no slash, burn, or wired `OnUnbalanced` event having occurred; the deposit was an ordinary user-initiated transfer.

		fn on_idle(_block: BlockNumberFor<T>, remaining_weight: Weight) -> Weight {
			let mut meter = WeightMeter::with_limit(remaining_weight);

			// Need at least one read (staging account balance).
			if meter.try_consume(T::DbWeight::get().reads(1)).is_err() {
				return meter.consumed();
			}

			let staging_account = Self::staging_account();
			let available = T::Currency::reducible_balance(
				&staging_account,
				Preservation::Preserve,
				Fortitude::Polite,
			);

			if available.is_zero() {
				return meter.consumed();
			}

			// Need 1 read and 2 writes for the transfer, plus 1 read and 1 write for
			// deactivate (InactiveIssuance) and 1 read for TotalIssuance.
			if meter.try_consume(T::DbWeight::get().reads_writes(3, 3)).is_err() {
				return meter.consumed();
			}

			let buffer = Self::buffer_account();
			if T::Currency::transfer(&staging_account, &buffer, available, Preservation::Preserve)
				.is_err()
			{
				defensive!("DAP: staging account transfer to buffer failed");
				return meter.consumed();
			}

			Self::deactivate_buffer_funds(available);
			Self::deposit_event(Event::StagingDrained { amount: available });

			log::debug!(
				target: LOG_TARGET,
				"DAP: drained {available:?} from staging account to DAP buffer"
			);

			meter.consumed()
		}
