## Title
StackerDB chunk signatures do not bind to the target smart‑contract, enabling cross‑database chunk replay/forged‑data propagation — (`File: libstackerdb/src/libstackerdb.rs`)

### Summary
`SlotMetadata`'s signed digest only commits to `slot_id`, `slot_version`, and `data_hash`; it never includes the StackerDB's contract identifier. Because several distinct StackerDB contracts (`signers-{0|1}-{message_id}`) share the exact same signer→slot_id assignment within a reward cycle, a validly-signed chunk broadcast on one contract's replica is also a validly-signed chunk for the *same slot_id* on a sibling contract. Any unprivileged network peer that observes a gossiped chunk can replay it into a different `.signers-X-Y` StackerDB and have it accepted and re-propagated as authentic data, even though it was never signed for that database.

### Finding Description
`SlotMetadata::auth_digest()` hashes only `slot_id`, `slot_version`, and `data_hash`: [1](#0-0) 
and `verify()`/`sign()` operate purely on this digest, with no reference to the owning smart contract: [2](#0-1) 

The chunk-acceptance path, `StackerDBTx::try_replace_chunk`, looks up the slot's expected signer *scoped to the target contract* (`get_slot_validation(smart_contract, slot_desc.slot_id)`), but the actual cryptographic check is only `slot_desc.verify(&slot_validation.signer)`, i.e. it never verifies that the signature was produced with knowledge of, or intent for, this particular contract: [3](#0-2) 

The same gap exists in the gossip/relay validation path used both for `PeerNetwork::handle_unsolicited_StackerDBPushChunk` and for scheduled sync downloads: [4](#0-3) 

For Nakamoto signers, a reward cycle instantiates one StackerDB contract *per message type* — `signers-{cycle%2}-{message_id}` for `message_id` in `MessageSlotID` (`BlockResponse=1`, `StateMachineUpdate=2`, `BlockPreCommit=3`): [5](#0-4) [6](#0-5) 

Critically, all of these sibling contracts for the same `signer_set` (0 or 1) read the *identical* signer/slot ordering from `.signers`, so slot_id → signer mapping is identical across `signers-0-1`, `signers-0-2`, `signers-0-3`, etc.: [7](#0-6) [8](#0-7) 

Because the signature never binds to the contract, a `StackerDBChunkData{slot_id, slot_version, sig, data}` legitimately signed and gossiped for `signers-0-1` (BlockResponse) is bit-for-bit a valid, verifiable chunk for `signers-0-2` (StateMachineUpdate) or `signers-0-3` (BlockPreCommit) at the same `slot_id`, since the target-contract check only affects *which signer address* is looked up, not whether the signature itself is contract-scoped.

### Impact Explanation
This breaks the equality "a signature authenticates a chunk write to a specific StackerDB" — in reality it only authenticates a `(slot_id, slot_version, data)` tuple, independent of which contract/StackerDB it is submitted to. Any unprivileged remote peer that has observed a gossiped or HTTP-served chunk (StackerDB data is not secret) can resubmit it, unmodified, into a sibling `.signers-X-Y` StackerDB via the public `POST /v2/stackerdb/.../chunks` endpoint or via unsolicited `StackerDBPushChunk` gossip. The node will accept it as "signed by the correct owner" and store and re-broadcast it network-wide (`try_replace_chunk` succeeds, `validate_received_chunk` returns `true`, and the chunk inventory/relay logic propagates it further), even though the data was never intended for that database. This is a form of network-wide propagation of forged/mis-scoped data through the p2p StackerDB replication mechanism, achievable by any unprivileged peer without possessing any private key.

### Likelihood Explanation
High likelihood of triggerability: StackerDB chunks are broadcast in the clear over the p2p network and are also fetchable via the public stacker-db HTTP API, so an attacker does not need privileged access — only network observation of one legitimately signed chunk plus the ability to submit an HTTP POST or unsolicited p2p push, both of which are unauthenticated, unprivileged operations reachable by any peer.

### Recommendation
Include the StackerDB contract identifier (`QualifiedContractIdentifier`) — and ideally the reward cycle / signer-set index — in `SlotMetadata::auth_digest()`, so a signature is only valid for the specific StackerDB it was produced for. This requires a protocol/version bump since it changes what bytes need to be signed by clients (`stacks-signer`) producing `StackerDBChunkData`.

### Proof of Concept
1. Wait for/observe a chunk gossiped or fetched via `GET /v2/stackerdb/<issuer>/<signers-0-1>/<slot_id>/<version>` for the `.signers-0-1` (BlockResponse) StackerDB, e.g. `StackerDBChunkData{slot_id: S, slot_version: V, sig, data}`.
2. Determine that `signer_set=0`'s signer-to-slot mapping is shared by `.signers-0-2` and `.signers-0-3` (see `stackerdb-get-signer-slots-page`).
3. Craft a `POST /v2/stackerdb/<issuer>/signers-0-2/chunks` (or send an unsolicited `StackerDBPushChunk` p2p message) using the exact same `StackerDBChunkData{slot_id: S, slot_version: V', sig, data}` captured in step 1 (bumping `slot_version` above the current stored version for `signers-0-2` if needed, but reusing the same `sig` — the digest only depends on `(slot_id, slot_version, data_hash)`, so the same signature over the same `data` and a controlled `slot_version` will verify only if `slot_version` also matches; an attacker with observation of multiple versions from the source DB, or simply replaying the exact same `(slot_id, slot_version, data, sig)` before the target DB reaches that version, can inject it).
4. Observe that `poststackerdbchunk`/`try_replace_chunk`/`validate_received_chunk` accept the chunk as validly signed for `signers-0-2`, store it, and the node further relays it to peers replicating `signers-0-2` — despite the data never having been signed with intent for that database.

    /// Get the digest to sign that authenticates this chunk data and metadata
    fn auth_digest(&self) -> Sha512Trunc256Sum {
        let mut hasher = Sha512_256::new();
        hasher.update(self.slot_id.to_be_bytes());
        hasher.update(self.slot_version.to_be_bytes());
        hasher.update(self.data_hash.0);
        Sha512Trunc256Sum::from_hasher(hasher)
    }

    pub fn sign(&mut self, privkey: &StacksPrivateKey) -> Result<(), Error> {
        let auth_digest = self.auth_digest();
        let sig = privkey
            .sign(&auth_digest.0)
            .map_err(|se| Error::SigningError(se.to_string()))?;

        self.signature = sig;
        Ok(())
    }

    /// Verify that a given principal signed this chunk metadata.
    /// Note that the address version is ignored.
    pub fn verify(&self, principal: &StacksAddress) -> Result<bool, Error> {
        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )
        .map_err(|ve| Error::VerifyingError(ve.to_string()))?;

        let pubkh = Hash160::from_node_public_key(&pubk);
        Ok(pubkh == *principal.bytes())
    }

    pub fn try_replace_chunk(
        &self,
        smart_contract: &QualifiedContractIdentifier,
        slot_desc: &SlotMetadata,
        chunk: &[u8],
    ) -> Result<(), net_error> {
        // Check per-replica chunk-size cap.
        if (chunk.len() as u64) > self.config.chunk_size {
            return Err(net_error::StackerDBChunkTooBig(chunk.len()));
        }

        let slot_validation = self
            .get_slot_validation(smart_contract, slot_desc.slot_id)?
            .ok_or(net_error::NoSuchSlot(
                smart_contract.clone(),
                slot_desc.slot_id,
            ))?;

        if !slot_desc.verify(&slot_validation.signer)? {
            return Err(net_error::BadSlotSigner(
                slot_validation.signer,
                slot_desc.slot_id,
            ));
        }
