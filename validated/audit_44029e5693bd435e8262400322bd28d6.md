### Title
Smart-contract-initiated TRX/TRC10 transfers bypass the new-account creation fee charged by native `TransferContract`/`TransferAssetContract` — ([File: actuator/src/main/java/org/tron/core/vm/program/Program.java])

### Summary
Ordinary account-creating transfers on java-tron charge `getCreateNewAccountFeeInSystemContract()` in addition to bandwidth costs, but the equivalent account-creation path reachable from TVM contract execution (`createAccountIfNotExist` → `createNormalAccount`) creates the account for free, with no equivalent system fee charged. This is the same bug class as the BlueBerry Bank report: one code path enforces a fee for an operation (crediting funds into a new/target account), while an alternate reachable path performs the equivalent state change (funds delivered, account instantiated) without applying the fee, causing the protocol/black-hole to lose the fee revenue it is designed to always collect for this operation.

### Finding Description
`TransferActuator.execute()` and `TransferAssetActuator.execute()` explicitly add `dynamicStore.getCreateNewAccountFeeInSystemContract()` to the transaction fee whenever the destination account does not exist yet, and that fee is burned/sent to the black hole: [1](#0-0) [2](#0-1) 

These are validated in `validate()` as well, requiring the sender to have sufficient balance to cover this extra fee: [3](#0-2) 

However, when a smart contract sends TRX or a TRC10 token to a non-existent address during TVM execution (e.g. via `CALL`/native token transfer or `SUICIDE`), the account is silently created through `Program.createAccountIfNotExist()`, which only calls `deposit.createNormalAccount(contextAddress)` — no equivalent `getCreateNewAccountFeeInSystemContract()` charge is applied anywhere in this path: [4](#0-3) 

Any unprivileged user can deploy a contract and issue a `TriggerSmartContractContract` transaction whose bytecode transfers value to an arbitrary, never-before-seen address (or self-destructs to one), thereby creating a brand-new account while only paying VM energy costs — not the protocol-mandated account creation fee that is otherwise always charged by the native transfer paths.

### Impact Explanation
This is a direct financial-loss/fee-bypass analog to the reported issue: the chain is designed to always collect `getCreateNewAccountFeeInSystemContract()` (burned to the black hole, i.e., value permanently removed from circulating supply / protocol revenue) whenever a new account is instantiated as a side effect of a value transfer. By routing the same effect (funds delivered to a freshly created account) through a smart contract call instead of a native `TransferContract`/`TransferAssetContract`, users can systematically avoid this fee, resulting in an unbacked/uncollected fee for every "many small transfers to fresh addresses" operation performed via contracts (e.g., airdrops), undermining the fee model and causing measurable, repeatable revenue loss to the protocol — directly analogous to Bob withdrawing lending via `liquidate()` to dodge `withdrawLend()`'s fee.

### Likelihood Explanation
High likelihood: any address can deploy a trivial contract that forwards TRX/TRC10 to a large batch of fresh, never-used addresses (or self-destructs into one), which is a common, cheap, and repeatable operation. No special privileges, timing, or race conditions are required — only ordinary `CreateSmartContract`/`TriggerSmartContract` transactions.

### Recommendation
Charge the equivalent of `getCreateNewAccountFeeInSystemContract()` (in energy terms, or as an explicit TRX fee subtracted from the calling contract's/originating account's balance) whenever `Program.createAccountIfNotExist()` actually creates a new account during VM execution, mirroring the fee logic already present in `TransferActuator`/`TransferAssetActuator`. Alternatively, ensure the energy cost model for account-creating `CALL`/`SUICIDE` operations is calibrated to fully recoup the same amount collected on the native transfer path, and audit other TVM-reachable account-creation entry points (e.g. `ContractState.java`, `RepositoryImpl.java`) for the same gap.

### Proof of Concept
1. Attacker deploys a contract with a function `forward(address payable to)` that does `to.transfer(msg.value)`.
2. Attacker calls `TriggerSmartContractContract` with a fresh, never-used `to` address and some TRX value.
3. During execution, `Program.createAccountIfNotExist()` creates the new account via `deposit.createNormalAccount(contextAddress)` — no `getCreateNewAccountFeeInSystemContract()` is deducted, unlike the equivalent native `TransferContract`/`TransferAssetContract` flow shown in `TransferActuator.execute()`/`TransferAssetActuator.execute()`.
4. Repeating this for many fresh addresses lets the attacker create arbitrarily many new accounts while paying only VM energy, avoiding the protocol's mandated account-creation fee that native transfers always enforce.

  private void createAccountIfNotExist(Repository deposit, byte[] contextAddress) {
    if (VMConfig.allowTvmSolidity059()) {
      //after solidity059 proposal , allow contract transfer trc10 or TRX to non-exist address(would create one)
      AccountCapsule sender = deposit.getAccount(contextAddress);
      if (sender == null) {

      }
    }
