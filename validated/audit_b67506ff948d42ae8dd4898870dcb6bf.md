### Title
Rewards permanently lost when `RewardsDistributor._updateTokenIndex` advances `timestamp` while `wadDiv` rounds the index delta to zero - (File: contracts/RewardsDistributor.sol)

### Summary
`RewardsDistributor._updateTokenIndex()` always commits the new `timestamp` once `block.timestamp` moves, but only credits accrued emissions to `index` via `_tokensAccrued.wadDiv(_totalSupply)`. When `deltaTime * speed * 1e18 < totalSupply / 2`, the index delta rounds to 0 while the elapsed time is consumed. The corresponding emissions are permanently lost — identical bug class to the LoopFi `lastBalance`-advances-without-index flaw. The update path is permissionless (`updateBeforeMintOrBurn` / `updateBeforeTransfer` / `claimRewards`) and is also triggered on every deposit, borrow, repay, withdraw, and token transfer, so accrual time can be consumed in arbitrarily small slices by any EOA.

### Finding Description
In `contracts/RewardsDistributor.sol:197-212`, `_calculateTokenIndex` computes:

```solidity
uint256 _tokensAccrued = _deltaTimestamps * _speed;
uint256 _ratio = _totalSupply > 0 ? _tokensAccrued.wadDiv(_totalSupply) : 0;
_newIndex = (_supplyState.index + _ratio).toUint224();
_newTimestamp = block.timestamp.toUint32();
```

`wadDiv` (`contracts/lib/WadRayMath.sol:39-41`) computes `(a * 1e18 + b/2) / b`, so `_ratio = 0` whenever `_tokensAccrued * 1e18 < _totalSupply / 2`. In `_updateTokenIndex` (`contracts/RewardsDistributor.sol:271-282`), `_newTimestamp > 0` is sufficient to store the new timestamp in both branches — so the elapsed seconds are consumed even though `index` gained nothing. Unlike the audited LoopFi code where `accrued` is a balance delta that could in principle be recovered later, here the accrued emission is `speed * deltaTime` computed lazily; once `timestamp` advances, that emission is gone forever. No user can ever claim it.

Reachability:
- `updateBeforeMintOrBurn(token_, account_)` is explicitly callable by anyone (comment at line 173: "This function also may be called by anyone to update stored indexes"), gated only by `tokenStates[token_].index > 0` (`contracts/RewardsDistributor.sol:175-180`).
- `claimRewards` is unpermissioned and calls `_updateTokenIndex` for every tracked token (`contracts/RewardsDistributor.sol:150-168`).
- `DepositToken`/`DebtToken` mint/burn/transfer hooks call `updateBeforeMintOrBurn`/`updateBeforeTransfer` on every user operation, so normal protocol activity also slices accrual windows.

The rounding loss compounds: each call burns up to ~0.5 wei of index while consuming the elapsed time, and an attacker can force the zero-delta case once per block whenever `12 * speed * 1e18 < totalSupply / 2`. This is reachable for large-supply `DepositToken`s (e.g., msUSD/msETH with hundreds of millions in supply, i.e., `totalSupply ~ 1e26-1e30`) combined with modest emission speeds set via `updateTokenSpeed` or the Vesper `syncTokenSpeed` path (`contracts/RewardsDistributor.sol:333-348`), where `speed` is derived from `rewardRates * treasuryBalance / vPoolTotalSupply` and can be arbitrarily small.

### Impact Explanation
Permanent loss of unclaimed yield: reward tokens emitted per second (`speed`) are never reflected in `index`, so `tokensAccruedOf` never credits them and they remain locked in the distributor or undistributed. Because `timestamp` is consumed, the loss is not recoverable by later calls. There is also a systematic ~0.5-wei-per-update rounding loss on every index update and a second dust loss in `_tokensDelta = balance.wadMul(deltaIndex)` (`contracts/RewardsDistributor.sol:230`), which accumulates over the lifetime of the contract.

### Likelihood Explanation
Any unprivileged user can trigger the truncation path every block via `updateBeforeMintOrBurn` or `claimRewards` at gas cost only, with no position required. Whether the index delta rounds to zero in a single call depends on the deployed `speed` and the token's `totalSupply`; it is guaranteed whenever `deltaTime * speed * 1e18 < totalSupply / 2`. For large deposit-token supplies and low emission rates (common when `syncTokenSpeed` distributes a Vesper reward rate across a big treasury share), frequent updates make each `_tokensAccrued` small enough to truncate, and each truncation permanently destroys that interval's emissions. Note `wadMul`/`wadDiv` round half-up, which slightly mitigates but does not eliminate the truncation once `accrued * 1e18 < totalSupply/2`.

### Recommendation
Track the unindexed residual instead of discarding it. Compute `_deltaIndex = _tokensAccrued.wadDiv(_totalSupply)` and only advance `timestamp` by the portion actually credited, or carry a remainder: store `pendingRewards += deltaTime * speed` and only consume `timestamp` when `pendingRewards` is large enough to move the index, so `index` and `timestamp` advance at the same pace. Alternatively, accumulate emissions in higher precision (ray) for the index to make truncation dust negligible.

### Proof of Concept
Hardhat-style sketch:

```ts
// Arrange: deposit token with huge supply, small speed
await rewardDistributor.updateTokenSpeed(msdToken.address, speed); // e.g. speed = 1e8
msdToken.totalSupply.returns(parseEther('1000000000')); // 1e27
msdToken.balanceOf.returns(parseEther('1000'));

// Record index/timestamp
const before = await rewardDistributor.tokenStates(msdToken.address);

// Attacker (or any user op) updates index every block; deltaTime = 1s..12s
for (let i = 0; i < N; i++) {
  await increaseTimeOfNextBlock(1);
  await rewardDistributor.updateBeforeMintOrBurn(msdToken.address, alice.address);
}

const after = await rewardDistributor.tokenStates(msdToken.address);
// accrued over N seconds = N * speed; ratio = (1*speed).wadDiv(1e27) = 0 each call
expect(after.index).to.eq(before.index);        // index never moved
expect(after.timestamp).to.be.gt(before.timestamp); // but time was consumed
// N * speed reward tokens are permanently undistributed:
// claimable(alice) == 0 despite N seconds of emissions
```

To make it fully reproducible, pick `speed` and `totalSupply` such that `12 * speed * 1e18 < totalSupply / 2` (e.g., `totalSupply = 1e30`, `speed = 1e9`), deposit so `index` is initialized, then loop single-second updates and assert `index` is unchanged while `claimable` stays 0.
