### Title
Vec<u8>/StacksString length-prefix allocation is bounded only by the constant `MAX_MESSAGE_LEN`, not by the actual remaining bytes of the enclosing payload, allowing a ~16MB allocation from a tiny P2P message - ([File: stacks-codec/src/strings.rs], [File: stacks-common/src/codec/mod.rs])

### Summary
`StacksString::consensus_deserialize` reads its inner `Vec<u8>` through `BoundReader::from_reader(fd, MAX_MESSAGE_LEN as u64)`, and the generic `Vec<u8>` decoder (`read_next_vec` in `stacks-common/src/codec/mod.rs`) validates the declared length only against the constant `MAX_MESSAGE_LEN` (~16MB) before calling `Vec::with_capacity(len)`. It never checks the length against the bytes actually remaining in the enclosing `StacksMessage` payload (bounded by `Preamble.payload_len`), so a message whose `payload_len` is only a few hundred bytes can still trigger a near-16MB allocation for a single `StacksString` (or other `Vec<T>`) field before the read fails.

### Finding Description
`StacksString::consensus_deserialize` wraps the reader in a `BoundReader` capped at `MAX_MESSAGE_LEN` and calls the generic `Vec<u8>` decode: [1](#0-0) 

The generic `Vec<T>` impl delegates to `read_next_at_most(fd, u32::MAX)` → `read_next_vec`: [2](#0-1) 

`read_next_vec` reads the 4-byte length prefix, checks it against `max_items` (here `u32::MAX`, i.e. no real cap), then checks `size_of::<T>() * len > MAX_MESSAGE_LEN` (for `T = u8` this is just `len > MAX_MESSAGE_LEN`), and only *then* calls `Vec::with_capacity(len)` before attempting to read any bytes: [3](#0-2) 

Crucially, this size check is against the hard-coded `MAX_MESSAGE_LEN` constant — not against how many bytes are actually left in the current message. The P2P framing layer (`connection.rs`) only buffers/passes exactly `preamble.payload_len` bytes to `read_payload`/`StacksMessage::deserialize_body`, which parses the payload from an in-memory `Cursor` over that slice: [4](#0-3) [5](#0-4) 

The `Preamble` only enforces `5 <= payload_len < MAX_MESSAGE_LEN`, with no relationship enforced between `payload_len` and the length fields declared by nested structures inside the payload: [6](#0-5) 

So an attacker can craft a P2P message with `Preamble.payload_len` set to, e.g., a few hundred bytes, whose payload body contains a `StacksMessageType` variant carrying a `StacksString` (or any other field parsed via the generic `Vec<T>`/`BoundReader::from_reader(fd, MAX_MESSAGE_LEN)` pattern — this same pattern recurs for `Vec<TransactionAuthField>`, `StacksMicroblock.txs`, `MicroblocksData.microblocks`, etc.) whose embedded 4-byte length prefix declares a value close to `MAX_MESSAGE_LEN` (~16MB). `Vec::with_capacity(len)` will attempt to allocate up to ~16MB from a payload that is genuinely only a few hundred bytes on the wire, and the read will only fail afterward with an `UnexpectedEof`/`ReadError` from the underlying `Cursor` once the actual bytes run out. `BoundReader` itself does not pre-validate available length; it simply short-circuits `read()` calls once `max_len` is reached and returns 0 bytes on subsequent reads, but that check happens on individual `read()` calls, after the allocation has already occurred: [7](#0-6) 

Existing guards do not close this gap: `Preamble.payload_len < MAX_MESSAGE_LEN` bounds the outer message size but not any inner field; the `BoundReader` wrapping only bounds the *total bytes read* against `MAX_MESSAGE_LEN`, not against the bytes actually available in the current message; and `read_next_vec`'s only pre-allocation check is against the same constant `MAX_MESSAGE_LEN`, unrelated to how much data remains in the buffer being decoded.

### Impact Explanation
Each malicious P2P message (as small as a few hundred bytes) can force the receiving node to allocate up to ~16MB in a single `Vec::with_capacity` call before the parse fails. Repeated sends (a single attacker connection can pipeline many such tiny messages) generate large numbers of large, transient allocations, which stresses the allocator, increases memory churn/page faults, and amplifies attacker-supplied bytes by roughly 4-5 orders of magnitude in allocation size. This is a bounded-compute/memory amplification DoS reachable from any P2P peer sending arbitrary messages containing a `StacksString` or similarly-decoded `Vec<T>` field — no authentication or privileged role is required to reach `consume_messages`/`read_payload` on a listening P2P port.

### Likelihood Explanation
No preconditions beyond TCP connectivity to a node's P2P port are required. The attacker does not need any secret, peer key, or StackerDB slot — they simply need to open a connection and send a crafted `Preamble` + payload with a forged inner length field, which is fully attacker-controlled at the byte level. The attack is trivially repeatable per message and cheap for the attacker (small message, large forced allocation on the target).

### Recommendation
Bound the length checks in `read_next_vec` (and the analogous `BoundReader::from_reader(fd, MAX_MESSAGE_LEN as u64)` call sites in `stacks-codec/src/strings.rs`, `stacks-codec/src/transaction.rs`, `stackslib/src/chainstate/stacks/block.rs`, `stackslib/src/net/codec.rs`, etc.) to the actual number of bytes remaining in the current bounded reader/`payload_len`, not the global `MAX_MESSAGE_LEN` constant. For example, expose the `BoundReader`'s `max_len`/remaining budget to `read_next_vec` so the pre-allocation check uses `min(remaining_budget, MAX_MESSAGE_LEN)`, or read length-prefixed byte blobs (`Vec<u8>`) via `read_exact` sized against a conservatively small `Vec::with_capacity` (e.g., grow incrementally, or cap initial capacity to something like 8KB and rely on `Read::take`/chunked reads) rather than trusting the untrusted length for the initial allocation.

### Proof of Concept
Rust test plan (to be run in `stackslib`/`stacks-codec` test context):
1. Build a `Preamble` with `payload_len` set to a small value (e.g. 300 bytes).
2. Build a payload buffer for a `StacksMessageType` variant that embeds a `StacksString` field (or reuse `StacksMessage::deserialize_body`), but hand-craft the 4-byte length prefix for the string's inner `Vec<u8>` to be `0x00FFFFFF` (~16MB), followed by only a few actual bytes.
3. Call `StacksP2P::read_payload(&preamble, &buf[..payload_len])` (or directly `StacksString::consensus_deserialize` on a `Cursor` over the truncated buffer).
4. Instrument/assert that `Vec::with_capacity` is invoked with a value close to `MAX_MESSAGE_LEN` (e.g., via a custom allocator counter or `#[global_allocator]` wrapper tracking large single allocations) even though the source buffer is only ~300 bytes, and that the call ultimately returns `Err(codec_error::ReadError(_))` only after the large allocation has already happened — demonstrating the assertion "deserialization fails with a bound tied to `payload_len`" does not hold; instead it fails only after committing the oversized allocation.

fn read_next_vec<T: StacksMessageCodec + Sized, R: Read>(
    fd: &mut R,
    num_items: u32,
    max_items: u32,
) -> Result<Vec<T>, Error> {
    let len = u32::consensus_deserialize(fd)?;

    if max_items > 0 {
        if len > max_items {
            // too many items
            return Err(Error::DeserializeError(format!(
                "Array has too many items ({len} > {max_items})"
            )));
        }
    } else if len != num_items {
        // inexact item count
        return Err(Error::DeserializeError(format!(
            "Array has incorrect number of items ({len} != {num_items})"
        )));
    }

    if (mem::size_of::<T>() as u128) * (len as u128) > MAX_MESSAGE_LEN as u128 {
        return Err(Error::DeserializeError(format!(
            "Message occupies too many bytes (tried to allocate {}*{}={})",
            mem::size_of::<T>() as u128,
            len,
            (mem::size_of::<T>() as u128) * (len as u128)
        )));
    }

    let mut ret = Vec::with_capacity(len as usize);
    for _i in 0..len {
        let next_item = T::consensus_deserialize(fd)?;
        ret.push(next_item);
    }

    Ok(ret)
}

impl<R: Read> Read for BoundReader<'_, R> {
    fn read(&mut self, buf: &mut [u8]) -> io::Result<usize> {
        let intended_read = self
            .read_so_far
            .checked_add(buf.len() as u64)
            .ok_or_else(|| io::Error::other("Read would overflow u64".to_string()))?;
        let max_read = if intended_read > self.max_len {
            self.max_len - self.read_so_far
        } else {
            buf.len() as u64
        };

        let nr = self.fd.read(&mut buf[0..(max_read as usize)])?;
        self.read_so_far += nr as u64;
        Ok(nr)
    }
