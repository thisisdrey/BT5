### Title
Uncontrolled Resource Consumption via Unbounded BigInteger Parsing in Shielded TRC-20 Parameter Construction - (File: framework/src/main/java/org/tron/core/Wallet.java)

### Summary
The `/wallet/createshieldedcontractparameters` and `/wallet/createshieldedcontractparameterswithoutask` HTTP endpoints (and their gRPC equivalents) accept attacker-controlled `from_amount` / `to_amount` string fields that are converted directly into `BigInteger` objects with no length or magnitude bound before validation occurs. This mirrors the `parse_duration` CWE-400 pattern: unbounded numeric-string parsing performed prior to any sanity check, allowing quadratic-cost `BigInteger` construction (and subsequent `BigInteger` arithmetic) to be triggered by a single, unauthenticated, pre-signature API call.

### Finding Description
`Wallet.getBigIntegerFromString` performs no length validation on its input: [1](#0-0) 

This method is invoked with request-supplied strings before any bounds checking happens: [2](#0-1) [3](#0-2) 

The size check (`checkBigIntegerRange`, `bitLength() > 256`) only happens *after* the `BigInteger` object has already been constructed from the raw string: [4](#0-3) 

These calls are reachable directly from unauthenticated HTTP POST requests, requiring no signature or prior wallet interaction — only network access to the node's HTTP API: [5](#0-4) 

`PrivateShieldedTRC20Parameters.getFromAmount()`/`getToAmount()` are plain `string` fields in the protobuf definition (confirmed present in `protocol/src/main/protos/api/api.proto`), with no length constraint enforced by the proto schema or by `JsonFormat.merge` before reaching `Wallet`.

This is directly analogous to the `parse_duration` advisory: there, an attacker-supplied duration string with a large exponent caused the library to construct arbitrarily large numeric values before any validation, consuming excessive CPU/memory. Here, an attacker can submit a `from_amount`/`to_amount` string consisting of, e.g., millions of decimal digits; `new BigInteger(trimmedIn, 10)` must parse and internally represent this value (Java's radix-10 `BigInteger` string constructor is quadratic in the number of digits for large inputs), and the value is validated only afterward.

Notably, this codebase elsewhere demonstrates awareness of exactly this class of bug and defends against it — `JsonRpcApiUtil.parseBlockNumber` explicitly caps input length *before* calling `BigInteger`, with a comment citing the "BigInteger parsing cost grows quadratically with length" concern: [6](#0-5) 

`Wallet.getBigIntegerFromString`, used on the shielded TRC-20 parameter-building path, lacks this same guard.

### Impact Explanation
An unauthenticated remote client can send a single HTTP POST to `/wallet/createshieldedcontractparameters` (or the `WithoutAsk` variant, or the gRPC equivalent) with an extremely long digit string in `from_amount`/`to_amount`. Each such request forces the node to perform expensive `BigInteger` string parsing and subsequent `mod`/`divide` operations on that oversized value inside `checkPublicAmount`, before any size check rejects it. Because the endpoint requires no prior transaction signing or account interaction, an attacker can repeat this cheaply and concurrently, driving up CPU and memory consumption on the full node's API-serving threads and potentially degrading or denying the JSON/HTTP API service to legitimate clients (matches "an API the node can no longer serve" in the accepted-impact criteria).

### Likelihood Explanation
Likelihood is high: the endpoint is part of the standard public HTTP/gRPC wallet API surface, requires no authentication or funds, and the vulnerable code path (`getBigIntegerFromString` → `checkPublicAmount` → `checkBigIntegerRange`) is trivially reached with a single crafted request. The presence of an identical guard already implemented elsewhere in the codebase for a similar `BigInteger` parsing DoS (`parseBlockNumber`) indicates the underlying risk is well understood by the maintainers but was not consistently applied to this endpoint.

### Recommendation
Add an explicit length/character-count bound on `from_amount` and `to_amount` (and any other user-supplied numeric strings converted to `BigInteger`) before calling `new BigInteger(...)`, analogous to `JsonRpcApiUtil.parseBlockNumber`'s `MAX_BLOCK_NUM_HEX_LEN` guard. Since the amounts are ultimately range-checked to at most 256 bits (`checkBigIntegerRange`), a reasonable cap (e.g., ~80 decimal digits, generously covering 256-bit values) should be enforced in `getBigIntegerFromString` prior to construction, rejecting oversized strings immediately with a validation error.

### Proof of Concept
1. Send an HTTP POST to `/wallet/createshieldedcontractparameters` with a JSON body such as:
```json
{
  "shielded_TRC20_contract_address": "<21-byte hex address>",
  "from_amount": "9999999999999999999999999999999999999999999999999999999999999999999999999999999999999999999999999999999999999999999999999999999999999999999999999999999999999999999999999999999999999999999999...(repeated to many thousands/millions of digits)",
  "to_amount": "0"
}
```
2. No signature or prior authentication is needed — the request only needs to reach `wallet.createShieldedContractParameters`, which calls `getBigIntegerFromString(request.getFromAmount())` before any length validation.
3. Repeating this request concurrently from multiple connections forces the node to repeatedly perform expensive `BigInteger` decimal parsing, consuming CPU/memory on the API-serving path and degrading node responsiveness for other API clients.

Note: I was unable to directly inspect the full `api.proto` message definitions or `JsonFormat.merge`'s size-guarding behavior (e.g., `Util.checkBodySize`) in this pass due to indexing limits — a background Devin session with full repository access would be needed to confirm the exact maximum request-body size enforced upstream and thereby precisely bound the achievable digit-string length for a definitive severity assessment.

  private long[] checkPublicAmount(byte[] address, BigInteger fromAmount, BigInteger toAmount)
      throws ContractExeException, ContractValidateException {
    checkBigIntegerRange(fromAmount);
    checkBigIntegerRange(toAmount);

    BigInteger scalingFactor;
    try {
      byte[] scalingFactorBytes = getShieldedContractScalingFactor(address);
      scalingFactor = ByteUtil.bytesToBigInteger(scalingFactorBytes);
    } catch (ContractExeException e) {
      throw new ContractExeException("Get shielded contract scalingFactor failed");
    }
    if (scalingFactor.compareTo(BigInteger.ZERO) <= 0) {
      throw new ContractValidateException("scalingFactor must be positive");
    }

    // fromAmount and toAmount must be a multiple of scalingFactor
    if (!(fromAmount.mod(scalingFactor).equals(BigInteger.ZERO)
        && toAmount.mod(scalingFactor).equals(BigInteger.ZERO))) {
      throw new ContractValidateException("fromAmount or toAmount invalid");
    }

    long[] ret = new long[2];
    try {
      ret[0] = fromAmount.divide(scalingFactor).longValueExact();
      ret[1] = toAmount.divide(scalingFactor).longValueExact();
    } catch (ArithmeticException e) {
      throw new ContractValidateException("fromAmount or toAmount invalid");
    }

    return ret;
  }

  private void checkBigIntegerRange(BigInteger in) throws ContractValidateException {
    if (in.compareTo(BigInteger.ZERO) < 0) {
      throw new ContractValidateException("public amount must be non-negative");
    }
    if (in.bitLength() > 256) {
      throw new ContractValidateException("public amount must be no more than 256 bits");
    }
  }

  /**
   * Max allowed length for a JSON-RPC block number hex/decimal input.
   * API-level DoS guard: rejects pathological inputs before BigInteger parsing,
   * whose cost grows quadratically with length. A block number fits a signed long,
   * so the longest valid input is 19 chars (decimal Long.MAX_VALUE) or 18 (0x + 16
   * hex); 20 leaves a small margin.
   */
  private static final int MAX_BLOCK_NUM_HEX_LEN = 20;

  /**
   * Parse a JSON-RPC block number (hex "0x..." or decimal) into a long,
   * enforcing the {@link #MAX_BLOCK_NUM_HEX_LEN} length limit, rejecting
   * negative values, and rejecting values that overflow a signed 64-bit
   * block number.
   */
  public static long parseBlockNumber(String blockNum)
      throws JsonRpcInvalidParamsException {
    if (blockNum == null || blockNum.length() > MAX_BLOCK_NUM_HEX_LEN) {
      throw new JsonRpcInvalidParamsException(BLOCK_NUM_ERROR);
    }
    BigInteger value;
    try {
      value = ByteArray.hexToBigInteger(blockNum);
    } catch (Exception e) {
      throw new JsonRpcInvalidParamsException(BLOCK_NUM_ERROR);
    }
    if (value.signum() < 0) {
      throw new JsonRpcInvalidParamsException(BLOCK_NUM_ERROR);
    }
    try {
      return value.longValueExact();
    } catch (ArithmeticException e) {
      throw new JsonRpcInvalidParamsException(BLOCK_NUM_ERROR);
    }
  }
