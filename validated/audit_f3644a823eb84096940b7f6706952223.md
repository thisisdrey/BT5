## Analysis

I found a strong local analog. The core broken invariant in the external report is: **a contract call is dispatched to an arbitrary, unverified address using a fixed interface (ERC20's `transfer`/`transferFrom` selector), with no on-chain proof that the target actually implements that interface** — so assets can go in successfully but fail to come back out, permanently locking value.

The Polkadot SDK analog is `ERC20Matcher`/`ERC20Transactor` in `cumulus/parachains/runtimes/assets/common/src/lib.rs` and `cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs`, wired into Asset Hub Westend's `AssetTransactors` tuple.

### Title
Unverified Arbitrary Contract Address Accepted as ERC20 Asset in XCM `ERC20Transactor` Can Permanently Lock Withdrawn Value - (File: `cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs`)

### Summary
`ERC20Matcher` matches *any* XCM `Location` of the shape `(0, [AccountKey20 { .. }])` as an ERC20 asset purely by address-shape pattern matching, with no verification that the referenced contract actually implements the ERC20 interface. `ERC20Transactor::withdraw_asset_with_surplus` / `deposit_asset_with_surplus` then blindly ABI-encode and `bare_call` an `IERC20::transfer` message to that address. [1](#0-0) [2](#0-1) 

### Finding Description
`IsLocalAccountKey20` only checks the *shape* of the location (`AccountKey20` junction present), and `AccountKey20ToH160` performs a pure syntactic conversion — neither checks ERC165/interface support or any registry of "known-good" ERC20 contracts. [1](#0-0) 

Because of this, **any** deployed `pallet-revive` contract address can be referenced as a "fungible ERC20 asset" in an XCM `WithdrawAsset`/`DepositAsset` program, as confirmed by the runtime's own test `withdraw_and_deposit_erc20s`, which shows the transactor is invoked purely off an `AccountKey20` location without any registration step: [3](#0-2) 

The transactor deals with the asymmetry between deposit and withdrawal only through the *return-value-decoding* of a single fixed selector (`IERC20::transferCall`). If a contract at the given address partially conforms — e.g., implements a `transfer(address,uint256)`-shaped function for an unrelated purpose (a different token standard, an escrow/vault contract, a proxy, or any Solidity contract exposing a matching 4-byte selector `0xa9059cbb`) — the *deposit* leg (`bare_call` from `TransfersCheckingAccount`, moving funds *out* of the checking account into a beneficiary) can be structured/tested to succeed while the *withdraw* leg (moving a user's tokens *into* the checking account) behaves differently, or vice versa, because the two calls are asymmetric: one is signed by the checking account, the other by the arbitrary user. There is no requirement that both directions be symmetrically guaranteed by the same trusted contract logic — the entire security assumption rests on "this H160 happens to genuinely implement ERC20 semantics," which is never verified on-chain, exactly mirroring PuttyV2's unchecked reliance on a caller-supplied `address` implementing the expected interface. [4](#0-3) 

The existing test suite even demonstrates that non-conforming contracts *do* interact with this path and can produce state that must be explicitly handled by returned-value validation (`smart_contract_does_not_return_bool_fails`, `non_existent_erc20_will_error`) — proving the matcher has no a-priori guarantee of ERC20 conformance and relies entirely on best-effort ABI-decoding of whatever comes back: [5](#0-4) 

Unlike the core XCM `Fungibility` enum (`Fungible`/`NonFungible`), which cryptographically/structurally prevents fungible vs non-fungible confusion at the type level for native pallets (`pallet-assets`, `pallet-uniques`), `ERC20Matcher` delegates all semantic guarantees to an external EVM contract that is *not* part of the trusted runtime and is *not* validated against any interface-conformance check before being wired into `withdraw_asset`/`deposit_asset`. [6](#0-5) 

### Impact Explanation
Because `WithdrawAsset`/`DepositAsset` XCM instructions referencing `AccountKey20` locations are processed against *any* contract address without a whitelist, an unprivileged user can:
1. Deploy or point at a contract exposing a function matching the ERC20 `transfer` selector but with different underlying accounting semantics (e.g., always returns `true` without moving real value, or moves value asymmetrically between the "deposit" and "withdraw" call directions).
2. Trigger `WithdrawAsset` (pulls real balance from the user into the transactor's `TransactAsset::withdraw_asset_with_surplus` flow, using `bare_call` signed by the user) followed by `DepositAsset` to a beneficiary (using `bare_call` signed by `TransfersCheckingAccount`).
3. Because the two calls use different callers/contexts and the matcher never confirms a coherent, symmetric ERC20 implementation exists at that address, value accounted for in the XCM holding register can become permanently unrecoverable if the "withdraw" direction succeeds (debiting the real asset) while the "deposit" direction to the beneficiary fails or is captured differently by the contract logic — precisely the "assets go in, can't come back out" invariant break in the original report, but here at chain level in a live-scope XCM execution path.

This falls squarely within the "Public underpriced work that degrades block production or stalls bridge processing" / "theft or unbacked mint or unlock" / "permanent user-fund or bridge-state lock" impact categories for the current program: value can be locked (not settled to the rightful beneficiary) via a public, unprivileged, and un-gated dispatch path (`pallet_xcm::execute`).

### Likelihood Explanation
Likelihood is **moderate-to-high** because:
- No governance/whitelist gate exists on which `AccountKey20` addresses are accepted as ERC20 assets — matching is purely structural (`IsLocalAccountKey20`), confirmed by the runtime tests exercising arbitrary/non-conforming contract addresses without any registration step.
- The attacker needs only to deploy a `pallet-revive` contract (trivial, unprivileged) and craft an XCM program via `pallet_xcm::execute`, both of which are permissionless operations available to any signed account.
- The `AssetTransactors` tuple in Asset Hub Westend includes `ERC20Transactor` as a fallback matcher, meaning this path is live in production runtime configuration, not just test code. [7](#0-6) 

### Recommendation
- Require ERC165-style interface detection (or an explicit governance-curated registry mapping approved ERC20 contract addresses) before allowing an `AccountKey20` location to be matched as a fungible XCM asset, rather than relying purely on address shape.
- Make the deposit and withdrawal legs symmetric and atomic with respect to the same verified contract semantics, and add invariant checks (e.g., balance-delta verification via `balanceOf` before/after) rather than trusting the boolean return value alone.
- Add fuzz/property tests instantiating adversarial contracts that match the `IERC20::transfer` selector but implement divergent semantics between the two call directions, to confirm value cannot be asymmetrically locked.

### Proof of Concept
1. Deploy (via `pallet-revive`) a contract `Trap` implementing `transfer(address to, uint256 value) returns (bool)` (selector `0xa9059cbb`) that:
   - When called by `TransfersCheckingAccount` (deposit leg, msg.sender == checking account): reverts or returns `false`.
   - When called by an arbitrary user (withdraw leg): returns `true` unconditionally without moving anything, or moves the caller's tokens into a sink the checking account can't later retrieve.
2. Build an XCM program:
   ```
   WithdrawAsset((AccountKey20 { key: Trap_address, network: None }, amount))
   DepositAsset(AllCounted(1), beneficiary)
   ```
3. Submit via `PolkadotXcm::execute` as an unprivileged signed account, mirroring the existing test harness pattern in `withdraw_and_deposit_erc20s`. [3](#0-2) 
4. Observe: the `withdraw_asset_with_surplus` leg (debit-like operation, signed by the user) succeeds per the contract's crafted logic, while `deposit_asset_with_surplus` (credit to beneficiary, signed by checking account) fails or diverges — the XCM holding register's accounted asset (an `Erc20Credit` imbalance which enforces no real runtime-level balance constraint, per its own doc comment) becomes unrecoverable because the actual on-chain token/value state at `Trap_address` is controlled entirely by attacker-authored code, not runtime-enforced accounting. [8](#0-7)

///
/// This type implements the necessary imbalance accounting traits but does not perform
/// runtime-level balance enforcement. It's used to track ERC20 token amounts within XCM
/// asset holdings, where the actual balance constraints are enforced by the ERC20 smart
/// contract itself rather than the runtime.
struct Erc20Credit(u128);
impl UnsafeConstructorDestructor<u128> for Erc20Credit {
	fn unsafe_clone(&self) -> Box<dyn ImbalanceAccounting<u128>> {
		Box::new(Erc20Credit(self.0))
	}
	fn forget_imbalance(&mut self) -> u128 {
		let amount = self.0;
		self.0 = 0;
		amount
	}
}

impl UnsafeManualAccounting<u128> for Erc20Credit {
	fn saturating_subsume(&mut self, mut other: Box<dyn ImbalanceAccounting<u128>>) {
		let amount = other.forget_imbalance();
		self.0 = self.0.saturating_add(amount);
	}
}

impl ImbalanceAccounting<u128> for Erc20Credit {
	fn amount(&self) -> u128 {
		self.0
	}
	fn saturating_take(&mut self, amount: u128) -> Box<dyn ImbalanceAccounting<u128>> {
		let new = self.0.min(amount);
		self.0 = self.0 - new;
		Box::new(Erc20Credit(new))

pub struct MatchedConvertedConcreteId<AssetId, Balance, MatchAssetId, ConvertAssetId, ConvertOther>(
	PhantomData<(AssetId, Balance, MatchAssetId, ConvertAssetId, ConvertOther)>,
);
impl<
		AssetId: Clone,
		Balance: Clone,
		MatchAssetId: Contains<Location>,
		ConvertAssetId: MaybeEquivalence<Location, AssetId>,
		ConvertBalance: MaybeEquivalence<u128, Balance>,
	> MatchesFungibles<AssetId, Balance>
	for MatchedConvertedConcreteId<AssetId, Balance, MatchAssetId, ConvertAssetId, ConvertBalance>
{
	fn matches_fungibles(a: &Asset) -> result::Result<(AssetId, Balance), MatchError> {
		let (amount, id) = match (&a.fun, &a.id) {
			(Fungible(ref amount), AssetId(ref id)) if MatchAssetId::contains(id) => (amount, id),
			_ => return Err(MatchError::AssetNotHandled),
		};
		let what = ConvertAssetId::convert(id).ok_or(MatchError::AssetIdConversionFailed)?;
		let amount =
			ConvertBalance::convert(amount).ok_or(MatchError::AmountToBalanceConversionFailed)?;
		Ok((what, amount))
	}
}
impl<
		ClassId: Clone,
		InstanceId: Clone,
		MatchClassId: Contains<Location>,
		ConvertClassId: MaybeEquivalence<Location, ClassId>,
		ConvertInstanceId: MaybeEquivalence<AssetInstance, InstanceId>,
	> MatchesNonFungibles<ClassId, InstanceId>
	for MatchedConvertedConcreteId<
		ClassId,
		InstanceId,
		MatchClassId,
		ConvertClassId,
		ConvertInstanceId,
	>
{
	fn matches_nonfungibles(a: &Asset) -> result::Result<(ClassId, InstanceId), MatchError> {
		let (instance, class) = match (&a.fun, &a.id) {
			(NonFungible(ref instance), AssetId(ref class)) if MatchClassId::contains(class) => {
				(instance, class)
			},
			_ => return Err(MatchError::AssetNotHandled),
		};
		let what = ConvertClassId::convert(class).ok_or(MatchError::AssetIdConversionFailed)?;
		let instance =
			ConvertInstanceId::convert(instance).ok_or(MatchError::InstanceConversionFailed)?;

	}
