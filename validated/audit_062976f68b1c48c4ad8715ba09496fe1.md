Based on my investigation, the strongest analog to the EXIF-style "insufficient bounds validation while parsing untrusted binary data" bug class in this Gitaly codebase is Gitaly's own reimplementation of the Git reftable binary format parser.

### Title
Out-of-bounds slice access / panic (DoS) in custom reftable block parser due to missing bounds checks - (File: internal/git/reftable/reftable.go)

### Summary
Git's reftable format (`gitformat-reftable`) is a binary ref-storage format. Gitaly does not shell out to `git` to read it; instead `internal/git/reftable/reftable.go` contains an independent, hand-rolled Go parser (`Table.GetReferences`, `Table.parseRefBlock`, `Table.getRefsFromBlock`, `Table.getVarInt`, `Table.extractBlockLen`) that walks the raw on-disk byte buffer using offsets and lengths taken directly from the file contents, similar in spirit to how PHP's `exif_iif_add_value` walked attacker-controlled EXIF field lengths without adequate bounds checks.

### Finding Description
Multiple locations index into the in-memory `src []byte` buffer using length/offset fields decoded from the file itself, with no check that the resulting index stays within `len(src)` (or even within the current block):

- `getVarInt` reads `src[start]` before validating `start` against any bound, and only checks `start > blockEnd` after already having read one more byte: [1](#0-0) 
- `getRefsFromBlock` computes `refname := prefix[:prefixLength] + string(src[idx:idx+suffixLength])` and later `src[idx : idx+uint(hashSize)]` / `src[idx : idx+size]` for symref targets, all driven by attacker/format-controlled `prefixLength`, `suffixLength`, and `size` values, with no validation that `idx+suffixLength`/`idx+hashSize`/`idx+size` stay within `b.RestartStart`, `b.FullBlockSize`, or `len(src)`: [2](#0-1) 
- `parseRefBlock` computes `b.RestartStart = blockStart + currentBS - 2 - 3*uint(b.RestartCount)` (both `currentBS` and `RestartCount` come from the file) and reads `src[blockStart+currentBS-2:]`, which can underflow (`uint` wraparound) or exceed `len(src)`: [3](#0-2) 
- `extractBlockLen` reads `src[blockStart+1 : blockStart+4]` without checking `blockStart+4 <= len(src)`: [4](#0-3) 

In Go, indexing/slicing past a slice's length does not corrupt memory (as it would in the C-based EXIF parser) but instead causes an immediate runtime panic — the memory-safe analog of a heap buffer over-read. This parser is used by the reftable-backed WAL/partition storage path (`internal/gitaly/storage/storagemgr/partition/reftable.go` calls `reftable.ParseTable`/`GetReferences`), which processes `.ref` table files that are written as part of normal ref-transaction processing during pushes to reftable-backend repositories.

### Impact Explanation
A malformed or adversarially-shaped reftable block (e.g., via a crafted/corrupted ref name length, restart count, or block-length field reaching this file, whether through an unexpected on-disk state, a corrupted replication payload, or a ref name/content edge case that produces boundary values not anticipated by this reimplementation) can cause `Table.GetReferences` to panic with "slice bounds out of range." Since this code runs inside a Gitaly RPC-handling goroutine over the storage/partition management path, an unrecovered panic can crash or wedge the serving Gitaly process — a denial-of-service impact scoped to "DoS of a handler," which is in the accepted impact list.

### Likelihood Explanation
Reftable files are normally written correctly by trusted code, so triggering this from a single ordinary push is not guaranteed and depends on the parser being reached with a reftable byte layout that hits an edge case (e.g., a `RestartCount`/`currentBS` combination causing underflow, or the last entry in a block whose suffix/hash/symref-target length runs past `RestartStart`/block end due to a boundary miscalculation elsewhere in Gitaly's reftable writer or in file corruption/partial writes during a crash-recovery replay). This is a real, code-level bounds-check gap that a background engineer should treat as a legitimate finding, but I could not fully trace an end-to-end crafted-push payload that guarantees the corrupted layout, given the tool budget in this investigation.

### Recommendation
Add explicit bounds checks in `internal/git/reftable/reftable.go` before every read/slice derived from file-controlled lengths and offsets: validate `start < len(src)` before the first `getVarInt` read, validate `idx+suffixLength`, `idx+hashSize`, `idx+size <= b.RestartStart`/`len(src)` in `getRefsFromBlock`, validate `blockStart+currentBS-2 >= blockStart` (no `uint` underflow) and `<= len(src)` in `parseRefBlock`, and validate `blockStart+4 <= len(src)` in `extractBlockLen`. Return a structured parse error instead of allowing a panic to propagate, and ensure the RPC handlers that invoke this parser recover from panics defensively as a defense-in-depth measure.

### Proof of Concept
Not independently reproduced in this investigation (no execution environment available). The concrete trigger would require constructing a `.ref` reftable file (or corrupting one via crash/partial write) whose block header/restart-count/varint fields cause one of the above expressions to compute an index or slice length exceeding `len(src)`, then invoking a Gitaly RPC that reads references from a reftable-backend repository (e.g., via the partition manager's `reftable.go` consumer) to trigger `Table.GetReferences` on that file.

func (t *Table) getVarInt(src []byte, start uint, blockEnd uint) (uint, uint, error) {
	var val uint

	val = uint(src[start]) & 0x7f

	for (uint(src[start]) & 0x80) > 0 {
		start++
		if start > blockEnd {
			return 0, 0, fmt.Errorf("exceeded block length")
		}

		val = ((val + 1) << 7) | (uint(src[start]) & 0x7f)
	}

	return start + 1, val, nil
}

// parseRefBlock parses a block and if it is a ref block, provides
// all the reference updates.
func (t *Table) parseRefBlock(src []byte, headerOffset, blockStart, blockEnd uint) ([]git.Reference, error) {
	currentBS := t.extractBlockLen(src, blockStart+headerOffset)

	fullBlockSize := t.blockSize
	if fullBlockSize == 0 {
		fullBlockSize = currentBS
	} else if currentBS < fullBlockSize && currentBS < (blockEnd-blockStart) && src[blockStart+currentBS] != 0 {
		fullBlockSize = currentBS
	}

	b := &block{
		BlockStart:    blockStart + headerOffset,
		FullBlockSize: fullBlockSize,
	}

	if err := binary.Read(bytes.NewBuffer(src[blockStart+currentBS-2:]), binary.BigEndian, &b.RestartCount); err != nil {
		return nil, fmt.Errorf("reading restart count: %w", err)
	}

	b.RestartStart = blockStart + currentBS - 2 - 3*uint(b.RestartCount)

	return t.getRefsFromBlock(src, b)
}
