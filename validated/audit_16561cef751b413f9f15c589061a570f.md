### Title
Malicious NFT contract can make `nft_resolve_withdraw` refund a token it already transferred away, creating an unbacked ledger credit - (File: contracts/defuse/src/contract/tokens/nep171/withdraw.rs)

### Summary
`nft_resolve_withdraw` decides whether to refund a withdrawn NFT purely by trusting the boolean JSON value the token contract returns from `nft_transfer_call`, with no verification that the contract actually retained/returned the token. A token contract fully controlled by the withdrawing account can perform the real transfer to `receiver_id` while returning `false`, causing the resolver to re-credit `token_balances` for an NFT the Verifier no longer custodies.

### Finding Description
The binding that should hold is:
`amount debited from sender_id in withdraw() (1)` == `amount that actually left Verifier custody to receiver_id (1)` + `amount re-credited by nft_resolve_withdraw on failure (0 if success)`.

In `internal_nft_withdraw`, the balance is unconditionally debited via `self.withdraw(...)` before any promise is scheduled: [1](#0-0) 
This also zeroes `total_supplies` for that `Nep171TokenId` (see `contracts/defuse/src/contract/tokens/mod.rs` `withdraw()` which calls `total_supplies.sub`).

The actual transfer is delegated to `ext_nft_core::nft_transfer_call` on `withdraw.token`, an attacker-supplied/attacker-deployed account: [2](#0-1) 

`nft_resolve_withdraw` then decides `used` purely from the callback's deserialized boolean, with no on-chain verification of actual ownership/custody: [3](#0-2) 

If `promise_result_checked_json::<bool>(0)` returns `Ok(Ok(false))`, `used=false` and the code calls `self.deposit(sender_id, [(Nep171TokenId::new(token, token_id).into(), 1)], ...)`. `deposit()` in `contracts/defuse/src/contract/tokens/mod.rs` re-adds 1 to `total_supplies` and to `sender_id`'s `token_balances`, only rejecting when the resulting total supply exceeds 1: [4](#0-3) 
Because `withdraw()` had already zeroed `total_supplies` for this token, the refund's `total_supply.add` returns exactly `1`, so the `NftAlreadyDeposited` guard (`total_supply > 1`) never triggers - the uniqueness invariant does not catch this case.

Root cause: a token contract that the withdrawing account fully controls can transfer the NFT to `receiver_id` internally while lying about the outcome in `nft_transfer_call`'s return value, since the resolver trusts that value unconditionally (aside from the unrelated `Err(_) => true` branch that only guards against gas-starved callbacks, not against `Ok(Ok(false))`). None of `assert_one_yocto`, `#[private]`, `#[pause]`, or the `NftAlreadyDeposited` check inspect actual custody, so nothing prevents the divergence.

### Impact Explanation
After the exploit, the Verifier's ledger shows `sender_id` owning 1 unit of `Nep171TokenId{contract_id: token, nft_token_id: token_id}` (`total_supply == 1`), while the real NFT was already moved out to `receiver_id` and is not custodied by the Verifier. This is a resolver credit that does not match what actually failed to settle, and it lets the account create a self-controlled asset that the Verifier's own ledger treats as fully backed and unique (`total_supply <= 1`), which can subsequently be used in swap/`token_diff` intents against other Verifier participants who rely on that invariant, or repeated to accumulate further phantom credits. The affected token type is confined to `Nep171TokenId` pairs where the token contract is attacker-controlled, so it does not directly reach balances of unrelated, legitimate tokens.

### Likelihood Explanation
The only precondition is that the attacker deploys and controls the NFT contract used for `token`, and owns/withdraws a unit they previously deposited from that same contract - both explicitly within the stated attacker capabilities (deploy/control own NFT contracts). No role, relayer key, or victim key is required; the attacker triggers the exploit entirely through their own `nft_withdraw` call and their own contract's `nft_transfer_call` implementation. The action is repeatable per withdraw call.

### Recommendation
Do not rely solely on the token contract's self-reported boolean for NFT resolve. Verify actual custody state via a follow-up `nft_token(token_id)` query on `withdraw.token` before crediting a refund, or, at minimum, treat `Ok(Ok(false))` from a token contract the same way unrecoverable custody mismatches are treated elsewhere (e.g., require an authoritative ownership check before re-minting `total_supplies`/`token_balances`).

### Proof of Concept
`cargo test` sandbox plan (near-workspaces):
1. Deploy a malicious NFT contract whose `nft_transfer_call` actually calls its internal transfer logic (moving `token_id` ownership to the argument `receiver_id`) but returns serialized JSON `false`.
2. From `sender_id`, deposit `token_id` from the malicious contract into the Defuse Verifier via `nft_transfer_call` to the Verifier (credits `token_balances[Nep171TokenId] == 1`, `total_supply == 1`).
3. Call `nft_withdraw(token=malicious_contract, receiver_id=some_account, token_id, ...)` from `sender_id`.
4. Assert before/after: before, `total_supplies` for the `Nep171TokenId` is `1` and the malicious contract's `nft_token(token_id).owner_id` is the Verifier/sender; after resolve, assert the malicious contract's `nft_token(token_id).owner_id == receiver_id` (real transfer happened) AND `sender_id`'s `token_balances` for that `Nep171TokenId` is `1` again (phantom refund), demonstrating `debited(1) != custody_lost(1) + refunded(1)`.
