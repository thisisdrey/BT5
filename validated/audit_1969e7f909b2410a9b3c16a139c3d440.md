### Title
Order-book accounting flaw: stale maker order state on zero-receive match branch enables duplicate token refund via cancel - ([File: actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java])

### Summary
`MarketSellAssetActuator.matchSingleOrder` contains an edge case (`makerBuyTokenQuantityReceive == 0` in the "taker > maker" branch) that mutates and refunds a maker order's tokens in memory, marks it inactive, and removes it from the order-book indices, but returns **before** persisting the updated `MarketOrderCapsule` to `orderStore`. The maker's on-chain order record is left stale — still `State.ACTIVE` with its pre-match nonzero `sellTokenQuantityRemain` — even though the underlying tokens have already been credited back to the owner's balance. `MarketCancelOrderActuator` trusts this stale on-disk record (`isActive()` + `getOwnerAddress()`) without cross-checking the order-book/`marketAccountStore` indices, allowing the order owner to "cancel" the already-refunded ghost order and receive a second, unbacked credit of the same token quantity.

### Finding Description
In `matchSingleOrder` (actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java), the "taker > maker" branch computes: [1](#0-0) 

When `makerBuyTokenQuantityReceive` truncates to `0` (integer division), the code calls `makerOrderCapsule.setSellTokenQuantityReturn()` then the actuator's private `returnSellTokenRemain(makerOrderCapsule)` helper, which fetches the owner's `AccountCapsule`, credits it with `orderCapsule.getSellTokenQuantityRemain()` via `MarketUtils.returnSellTokenRemain`, zeroes the in-memory remain, and persists the **account** update: [2](#0-1) [3](#0-2) 

The method then `return`s, **skipping** the `orderStore.put(makerOrderCapsule...)` call that normally persists the maker order's final state: [4](#0-3) 

Because the in-memory object was already mutated (remain=0), the caller `matchOrder` still correctly removes the order from `pairPriceToOrderStore` and, via `updateOrderState`, removes it from the owner's `marketAccountStore` order list: [5](#0-4) 

However, the raw record in `orderStore` (a separate key-value store keyed by order ID) is **never rewritten** in this branch — it still contains whatever was last persisted (typically `State.ACTIVE` and the pre-match nonzero `sellTokenQuantityRemain`), even though the tokens were already returned to the owner's balance.

The code comment explicitly claims this branch "would not happen," but the invariant only holds for orders where `sellQuantity < buyQuantity`; it does not hold when `makerSellQuantity > makerBuyQuantity` (a valid, common order shape), so `multiplyAndDivide(remain, buyQuantity, sellQuantity)` can legitimately truncate to `0` for a partially filled maker order: [6](#0-5) 

`MarketCancelOrderActuator` does not verify order-book/account-list consistency; it trusts the (now stale) `orderStore` record directly: [7](#0-6) 

and on execute simply re-runs `MarketUtils.returnSellTokenRemain`, crediting the owner a second time with the stale `sellTokenQuantityRemain`, before touching the (already-removed) order-book indices: [8](#0-7) 

This is the same bug class described in the Secured Finance report: an order-book accounting flaw that treats a partially/fully processed ("unfilled" from the stale on-disk view) order as still valid, generating an invalid/unbacked balance.

### Impact Explanation
An order owner can trigger this sequence with self-controlled orders (no special privilege needed): create a maker order with `sellQuantity > buyQuantity`, get it partially filled down to a small remainder by any counter order, then trigger a taker match that fully consumes the remaining (tiny) balance and hits the zero-receive branch. The owner's account is credited once via the match's early-return refund and then a second time via `MarketCancelOrderContract` on the now-ghost order ID — an unbacked balance is minted with no corresponding token debit, directly analogous to the reported $180k Secured Finance loss caused by treating stale/unfilled order state as valid for withdrawal.

### Likelihood Explanation
Reachable by any unprivileged account via three ordinary, unprivileged transactions: `MarketSellAssetContract` (create/partial-fill maker order), `MarketSellAssetContract` (taker order that fully consumes the remainder and lands in the truncation branch), and `MarketCancelOrderContract` (double refund). All quantities can be chosen precisely by the attacker to force the integer-division truncation, so the exploit is deterministic, not probabilistic.

### Recommendation
In `matchSingleOrder`, persist the `makerOrderCapsule` to `orderStore` (and ensure `updateOrderState`/index removal is consistent) in **every** code path that mutates it, including the `makerBuyTokenQuantityReceive == 0` early-return branch, before returning. Additionally, harden `MarketCancelOrderActuator.validate()` to cross-check that the order is actually present in `marketAccountStore`'s owner order list and in the corresponding `pairPriceToOrderStore` list before allowing a refund, rather than trusting `orderStore`'s `isActive()` flag alone.

### Proof of Concept
1. Attacker creates maker order O: sell 200 units of TokenB for 1 unit of TokenA (`sellTokenQuantity=200`, `buyTokenQuantity=1`), remain=200, ACTIVE, via `MarketSellAssetActuator`.
2. A counter-order partially fills O down to `sellTokenQuantityRemain=150` (a normal partial "taker < maker" match), persisted correctly.
3. Attacker (or anyone) submits a taker order requesting more of TokenB than O's remaining 150 units at this price level, triggering the "taker > maker" branch in `matchSingleOrder`. `makerBuyTokenQuantityReceive = multiplyAndDivide(150, 1, 200) = 0`, hitting the buggy branch: attacker's account is credited 150 TokenB, O's in-memory remain set to 0, O removed from `marketAccountStore`/`pairPriceToOrderStore`, but `orderStore` for O is left with stale `State.ACTIVE`, `sellTokenQuantityRemain=150`.
4. Attacker submits `MarketCancelOrderContract{orderId=O}`. `validate()` passes (`orderStore.get(O).isActive()==true`, owner matches). `execute()` calls `MarketUtils.returnSellTokenRemain` again, crediting attacker's account with another 150 TokenB — an unbacked duplicate credit with no corresponding asset debit.
