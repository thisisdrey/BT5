### Title
Deleted-account postponed `ActionReceipt`s (with self-authorized `AddKey`) survive `DeleteAccount` and re-execute with full permission against a reused account name - ([File: runtime/runtime/src/actions.rs], [File: core/store/src/utils/mod.rs], [File: runtime/runtime/src/lib.rs])

### Summary
`remove_account` (called from `action_delete_account`) purges the `Account`, access keys, gas keys and contract data but never touches `TrieKey::PostponedReceipt`, `TrieKey::PendingDataCount`, or `TrieKey::PostponedReceiptId` entries that may still be parked under that same `AccountId`. Because `check_actor_permissions` only compares raw `AccountId` strings (`actor_id != account_id`) with no notion of account "incarnation," a postponed multi-dependency `ActionReceipt` created and self-authorized under the old owner (predecessor_id == receiver_id == the deleted account) can be resurrected and executed once the account name is recreated by a different, unrelated owner, granting the original attacker's `AddKeyAction(FullAccess)` on the new account.

### Finding Description
`remove_account` in `core/store/src/utils/mod.rs:505-575` removes `TrieKey::Account`, `TrieKey::ContractCode`, access/gas keys, and `TrieKey::ContractData`, but has no logic to remove `TrieKey::PostponedReceipt`, `TrieKey::PendingDataCount`, or `TrieKey::PostponedReceiptId` for the account: [1](#0-0) [2](#0-1) 

`action_delete_account` (`runtime/runtime/src/actions.rs:314-390`) calls `remove_account` and clears the `Account`, with no check for outstanding postponed receipts: [3](#0-2) 

These trie keys are indexed purely by `(receiver_id: AccountId, receipt_id/data_id)` (`core/primitives/src/trie_key.rs:203-219`), with no binding to any "account incarnation" concept — the raw account-name string is the only identity anchor: [4](#0-3) 

`process_action_receipt` (`runtime/runtime/src/lib.rs:1593-1658`) postpones an incoming `ActionReceipt` whenever any `input_data_ids` are missing, storing `PendingDataCount`/`PostponedReceiptId`/`PostponedReceipt` under the receiver's account name: [5](#0-4) 

`process_receipt`'s `Data` branch (`runtime/runtime/src/lib.rs:1386-1474`) resurrects and executes the postponed receipt purely based on decrementing `PendingDataCount` to zero for the matching `(receiver_id, receipt_id)` — with no re-validation that the account is in the same state/ownership as when the receipt was postponed: [6](#0-5) 

When the resurrected receipt is finally applied, `apply_action_receipt` re-derives `actor_id` solely from the (stale, already-signed) `receipt.predecessor_id()`: [7](#0-6) 

`check_actor_permissions` for `Action::AddKey` only requires `actor_id == account_id` as plain string equality, with no check that the account hasn't been deleted and recreated by an unrelated party in the interim: [8](#0-7) 

**Exploit flow**: Attacker (controlling `attacker.near`) creates subaccount `victim.attacker` (a name only the attacker's parent account can create — no cooperation needed from any third party for this step). A contract on `victim.attacker` makes a self-promise (`predecessor_id == receiver_id == victim.attacker`) with `promise_and` (2 `input_data_ids`) and an `AddKeyAction(FullAccess, attacker_pubkey)` — legitimate at creation time since attacker owns the account. Only one of the two `DataReceipt`s is supplied, leaving the receipt permanently postponed (`PendingDataCount == 1`). Attacker then sends `DeleteAccountAction` on `victim.attacker`; this succeeds (`actor_id == account_id`, no locked stake) and clears the `Account` record but leaves `PostponedReceipt`/`PendingDataCount`/`PostponedReceiptId` under the string key `victim.attacker` intact. Later, when the same account name is freed and reused (e.g., a short top-level name recycled via the registrar, or the attacker itself later re-issues the subaccount under a "sale/rent" scheme to an unrelated party — the top-level-name-recycling path requires no cooperation from the new owner and is the strongest instance of this bug), the new owner deploys and funds their own contract at `victim.attacker`. The attacker then finally supplies the withheld `DataReceipt`, which drives `PendingDataCount` to 0 and triggers `apply_action_receipt` on the dormant receipt. `check_actor_permissions` compares `actor_id` ("victim.attacker", from the stale receipt) to `account_id` ("victim.attacker", the new owner's live account) and they are textually equal, so the `AddKeyAction(FullAccess, attacker_pubkey)` executes and installs the attacker's full-access key on the new owner's account.

### Impact Explanation
This is an authorization-escalation bug: a promise created and authorized entirely under one account incarnation is executed with full privilege against a different, unrelated incarnation of the same account name, because the runtime treats `AccountId` strings as a permanent identity with no invalidation on deletion. Concrete impact is theft of funds/contract control: the attacker obtains a full-access key on an account they no longer legitimately own, which they can use to drain balance or hijack the contract deployed there by the new (innocent) owner.

### Likelihood Explanation
The attacker fully controls every step needed to set the trap (subaccount creation, promise/`promise_and` construction, withholding one `DataReceipt`, deletion) using only ordinary signed transactions and their own deployed contract — no special privileges are required. The only external dependency is that the account name eventually gets reused by an unrelated party; for reusable top-level names via the registrar this occurs without any attacker involvement in the re-registration and is a known/expected occurrence in NEAR's account-name lifecycle (deleted top-level names becoming available again). The trap can remain dormant indefinitely (postponed receipts are permanent trie state until resolved), and the trigger (supplying the final `DataReceipt`) is entirely attacker-controlled and repeatable for multiple victims/pre-planted account names.

### Recommendation
When deleting an account, purge or invalidate any outstanding `TrieKey::PostponedReceipt`, `TrieKey::PendingDataCount`, and `TrieKey::PostponedReceiptId` entries scoped to that account (iterate and remove them in `remove_account`, mirroring how access keys/contract data are already enumerated and removed). Alternatively/additionally, bind postponed-receipt resolution to an account "incarnation" (e.g., a creation nonce/height stored on the `Account` and checked against a copy embedded in the postponed receipt) so a stale receipt cannot be resurrected against a different incarnation of the same account name.

### Proof of Concept
Runtime/integration test plan:
1. Unit test (`runtime/runtime/src/actions.rs` / `actions_test_utils.rs` style): set up `TrieUpdate` with an account `victim.attacker`; call `process_action_receipt`-equivalent logic to store a postponed `ActionReceipt` (predecessor_id == receiver_id == `victim.attacker`, actions = `[AddKeyAction(FullAccess, attacker_pubkey)]`, `input_data_ids` = 2 hashes) via `set_postponed_receipt`/`set` for `PendingDataCount`/`PostponedReceiptId`. Assert these trie keys exist.
2. Call `action_delete_account` on `victim.attacker`. Assert the `Account` key is gone but `TrieKey::PostponedReceipt { receiver_id: victim.attacker, receipt_id }`, `TrieKey::PendingDataCount`, and `TrieKey::PostponedReceiptId` still exist (`get_postponed_receipt`/`get` return `Some`).
3. Simulate account recreation: `set_account` a fresh `Account` for `victim.attacker` (different owner/no attacker key).
4. Feed the second `DataReceipt` (matching the still-pending `data_id`) through the runtime's `process_receipt` path; assert it decrements `PendingDataCount` to 0, retrieves and removes the postponed receipt, and calls `apply_action_receipt`.
5. Assert the `AddKeyAction` executes successfully (`check_actor_permissions` passes because `actor_id (== old predecessor_id) == account_id`) and that `get_access_key(state_update, "victim.attacker", attacker_pubkey)` now returns `Some(AccessKey::full_access())` — demonstrating the attacker gained a full-access key on the recreated account without ever having authority over the new incarnation.

pub(crate) fn check_actor_permissions(
    action: &Action,
    account: &Option<Account>,
    actor_id: &AccountId,
    account_id: &AccountId,
) -> Result<(), ActionError> {
    match action {
        Action::DeployContract(_)
        | Action::Stake(_)
        | Action::AddKey(_)
        | Action::DeleteKey(_)
        | Action::DeployGlobalContract(_)
        | Action::UseGlobalContract(_)
        | Action::WithdrawFromGasKey(_) => {
            if actor_id != account_id {
                return Err(ActionErrorKind::ActorNoPermission {
                    account_id: account_id.clone(),
                    actor_id: actor_id.clone(),
                }
                .into());
            }
        }
