### Title
Read-check/decrypt/write-effect race in `ConnectionState.Decrypt` allows a duplicate packet to bypass replay protection - ([File: connection_state.go])

### Summary
`ConnectionState.Decrypt` splits replay-window enforcement into three separate critical sections (`Check` → `DecryptDanger` → `Update`), releasing `decryptLock` between the read of window state and the AEAD decrypt, and again before the write that marks the counter as consumed. This mirrors the reported Solidity bug class: a state *check* is performed, an expensive *interaction* (external/heavy operation) happens without the lock held, and the *effect* (marking the nonce/counter as seen) is applied only afterward. Nebula's `nebula` process reads and dispatches inbound UDP packets across `numWorkers` concurrent goroutines (`f.readers[q]`, driven from `interface.go`'s listen loop), so two goroutines can race on the same `ConnectionState` for a duplicated ciphertext with the same `messageCounter`.

### Finding Description
`connection_state.go` implements the replay/anti-replay logic as: [1](#0-0) 

The function:
1. Takes `decryptLock`, calls `cs.window.Check(l, messageCounter)` (a pure read of the `Bits` replay window), and releases the lock.
2. Performs `cs.dKey.DecryptDanger(...)` — the AEAD decrypt, a comparatively expensive operation — entirely **without holding `decryptLock`**.
3. Re-acquires `decryptLock`, calls `cs.window.Update(l, messageCounter)` to mark the counter as consumed, and releases the lock.

Because the lock is dropped between step 1 and step 3, if two packets carrying the *same* `messageCounter` (e.g., an attacker-captured and replayed UDP frame, or a duplicated frame from a relay/network path) arrive and are processed concurrently by two different reader goroutines, both can pass `Check` (both see the counter as "not yet seen") before either has called `Update`. Both goroutines then proceed to decrypt the packet successfully and deliver the plaintext up the stack (`outside.go`'s `readOutsidePackets`, which calls `Decrypt` at line 126 and then proceeds into `handleOutsideMessagePacket`/firewall/TUN write on success). [2](#0-1) 

This is structurally identical to the reported bug: the "effect" (state mutation marking a resource as spent — here, the replay-window bit) is deferred until after an "interaction" (an expensive/external call — here, AEAD decryption), creating a window in which the same nonce/counter can be accepted twice, defeating the anti-replay guarantee that `Bits`/`ReplayWindow` is meant to enforce.

The `Bits.Check`/`Update` split is explicitly documented as a two-step check-then-mark protocol: [3](#0-2) 

and the second-stage `Update` is what actually commits the "seen" state and rejects duplicates: [4](#0-3) 

Note the CHANGELOG even records this exact class of bug being partially fixed for relayed traffic ("Advance the replay window on relayed packets so a relay drops replayed frames instead of re-forwarding them", "Lock replay window updates so concurrent readers can't corrupt it"), confirming replay-window concurrency has been a known problem area, but the Check→Decrypt→Update gap in `Decrypt`/`VerifyRelay` itself remains. [5](#0-4) 

The same pattern is duplicated in `VerifyRelay`, used for relay-forwarded frames: [6](#0-5) 

### Impact Explanation
A network-position attacker who can duplicate/replay a captured ciphertext UDP frame (no valid certificate needed — this operates on already-encrypted wire bytes, which are visible/replayable by any observer on the path, including through a relay) can, under concurrent packet processing, cause the same encrypted message to be decrypted and accepted **twice** by the receiver before the replay window is updated to reflect it as seen. Depending on payload semantics this can lead to duplicate delivery to the TUN device (double processing of the same application-layer packet) or, for relayed traffic, duplicate forwarding, undermining the guarantee that Nebula's replay window (`ReplayWindow = 1024`) is supposed to provide. This is a concrete instance of "traffic decryption/forgery/replay" bypass in the sense that the anti-replay control can be defeated by a race rather than by breaking cryptography.

### Likelihood Explanation
Exploitability depends on Nebula's inbound UDP processing model dispatching packets to multiple concurrent workers (`f.readers[q]` / multiple reader goroutines referenced in `interface.go`), which is the normal multi-queue configuration in production deployments. An attacker only needs to capture one legitimate ciphertext frame and re-inject it (or induce network-level duplication) at approximately the same time as the original arrives at a different worker, which is plausible on any network path where duplication or attacker-controlled re-injection is possible (including through a relay hop, which the CHANGELOG shows was already a real-world hardening target). This makes the likelihood moderate: it requires precise timing to win the race but does not require any cryptographic material or valid certificate.

### Recommendation
Hold `decryptLock` (or otherwise atomically combine the check-mark-decrypt sequence) across the entire "check window, decrypt, mark window" sequence so no other goroutine can observe/mutate the window state between `Check` and `Update` for the same `ConnectionState`. Concretely, refactor `Decrypt` and `VerifyRelay` to: (1) acquire the lock, (2) call `Check`, (3) perform (or complete) the `Update` immediately upon successful decrypt while still holding the lock, ensuring the effect (marking the counter consumed) is committed atomically with respect to the check, i.e., true checks-effects-interactions ordering rather than check → unlocked interaction → effect.

### Proof of Concept
1. Establish a tunnel between two Nebula nodes so a `ConnectionState` with an active replay `Bits` window exists.
2. Have the legitimate sender transmit a data packet, capturing the exact ciphertext UDP frame (header + AEAD ciphertext) with a specific `messageCounter`.
3. Configure/observe a receiver with multiple concurrent UDP reader workers (`f.readers[q]`, `numWorkers` in the config).
4. Re-inject (replay) the captured frame twice in rapid succession, timed so that both copies are picked up by different reader goroutines before either finishes `ConnectionState.Decrypt`.
5. Observe that `cs.window.Check` in `connection_state.go:64` returns `true` for both copies (since `Update` has not yet run for either), both `DecryptDanger` calls succeed, and both plaintexts are delivered (e.g., both reach `handleOutsideMessagePacket`/TUN write), demonstrating a successful replay bypass rather than the expected single acceptance and rejection of the duplicate via `ErrAlreadySeen`.

Note: I could not fully verify the exact number/scheduling of concurrent UDP reader goroutines from the indexed portions of `interface.go` (the relevant loop body was only partially visible in search results), so the precision of "how easily" the race window can be won under default configuration is not fully confirmed from the available index — a live test against a running multi-worker Nebula instance would be needed to measure actual win rates.

func (cs *ConnectionState) Decrypt(l *slog.Logger, messageCounter uint64, out []byte, packet []byte, nb []byte) ([]byte, error) {
	var err error
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}

	out, err = cs.dKey.DecryptDanger(out, packet[:header.Len], packet[header.Len:], messageCounter, nb)
	if err != nil {
		return nil, err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}
	return out, nil
}

// Check returns true if i is within (or way out in front of) the window, and not a replay
func (b *Bits) Check(l *slog.Logger, i uint64) bool {
	// If i is the next number, return true.
	if i > b.current {
		return true
	}

	if b.strictlyWithinWindow(i) {
		return !b.get(i)
	}

	// Not within the window
	if l.Enabled(context.Background(), slog.LevelDebug) {
		l.Debug("rejected a packet (top)", "current", b.current, "incoming", i)
	}
	return false
}
