### Title
Compute-budget semantic validation deferred until after account-lock and ALT-resolution work, allowing cheap-to-detect invalid packets to consume expensive per-packet processing - (File: `core/src/banking_stage/transaction_scheduler/receive_and_buffer.rs`)

### Summary
`TransactionViewReceiveAndBuffer::try_handle_packet` performs cheap structural compute-budget parsing early (inside `translate_to_runtime_view`), but defers the semantic/value-range validation of compute-budget instructions (`sanitize_and_convert_to_compute_budget_limits`, called via `view.transaction_configuration(...)`) until *after* the full account-lock-limit check, address-lookup-table (ALT) resolution, and duplicate-lock validation have already run. An attacker who crafts a v0 transaction referencing a real ALT and an instruction-data-level-valid-but-semantically-invalid `ComputeBudgetInstruction` (e.g. `SetLoadedAccountsDataSizeLimit(0)` or an out-of-range heap size) forces the node to pay for ALT resolution and lock validation before the packet is finally rejected on the cheaper `ComputeBudget` check.

### Finding Description
In `translate_to_runtime_view` [1](#0-0) , the order of operations is:
1. `SanitizedTransactionView::try_new_sanitized` (cheap parse)
2. `RuntimeTransaction::<SanitizedTransactionView<_>>::try_new` - this internally calls `from_sanitized_transaction_view`, which invokes `ComputeBudgetInstructionDetails::try_from(...)` [2](#0-1)  — this only catches *structural* issues (duplicate compute-budget instructions, wrong instruction discriminant), not value-range/semantic errors.
3. `total_num_accounts` vs. lock-limit check (cheap)
4. `load_addresses_for_view` — full ALT resolution requiring bank account lookups/deserialization (expensive)
5. Second `RuntimeTransaction::<ResolvedTransactionView<_>>::try_new`
6. `validate_account_locks` duplicate-lock check

Only after all of this, back in `try_handle_packet`, is `view.transaction_configuration(&working_bank.feature_set)` called [3](#0-2) , which internally calls `sanitize_and_convert_to_compute_budget_limits` [4](#0-3) . This function performs checks that require *no* ALT/lock information at all — e.g. heap-size bounds/alignment, and `loaded_accounts_bytes == 0` returning `TransactionError::InvalidLoadedAccountsDataSizeLimit` [5](#0-4) . These checks operate purely on data already extracted during step 2 (structural parse), so they could be evaluated immediately after parsing, before any ALT resolution or lock validation is attempted.

Because the check is deferred, a packet with, e.g., `ComputeBudgetInstruction::set_loaded_accounts_data_size_limit(0)` combined with a v0 message referencing a real, resolvable ALT will: pass steps 1–3, incur a full ALT resolution (bank account fetch + deserialization) in step 4, pass steps 5–6, and only then fail with `PacketHandlingError::ComputeBudget`. The `ReceivingStats` counters (`num_dropped_on_compute_budget`) confirm this classification is reached only via the post-ALT-resolution path [6](#0-5) .

### Impact Explanation
This is a per-packet CPU-cost amplification issue, not a memory-safety, consensus, or verification bypass bug. It falls under the "grossly underpriced pre-fee work" bounty category referenced in the question: an unstaked, unprivileged attacker can force the node to spend ALT-resolution and lock-validation work on every rejected packet, even though the ultimate rejection reason (a semantically invalid compute-budget value) was fully determinable from data available immediately after cheap parsing. The amplification is bounded to one extra ALT lookup/deserialization and one lock-duplicate scan per attacker packet — a real but modest inefficiency rather than an unbounded-cost or crash primitive.

### Likelihood Explanation
Preconditions are all attacker-controllable and require no special privilege: the attacker only needs (a) a self-signed keypair (free, sigverify only checks the signature matches the included pubkey — no stake or funding required to reach this stage), and (b) a public/well-known or attacker-created ALT address to include as an address-table lookup so that `load_addresses_for_view` performs real resolution work. This is fully repeatable per packet and does not depend on validator/operator misconfiguration, mocked paths, or any privileged access — it is directly reachable from `handle_packet_batch_message` on every leader/hold cycle.

### Recommendation
Move the semantic compute-budget validation (`sanitize_and_convert_to_compute_budget_limits`) to run immediately after the initial structural parse (right after `ComputeBudgetInstructionDetails::try_from` inside `from_sanitized_transaction_view`/`try_new` for `SanitizedTransactionView`), before `total_num_accounts`/ALT resolution/lock validation are attempted, so that fully self-contained, cheap-to-detect invalidity is rejected before any bank-dependent expensive work (ALT resolution, lock validation) is performed.

### Proof of Concept
Add a unit test to `core/src/banking_stage/transaction_scheduler/receive_and_buffer.rs` similar to the existing `test_receive_and_buffer_failed_alt_resolve` test, but construct a v0 transaction that:
1. References a *real, resolvable* ALT (so ALT resolution succeeds), and
2. Includes `ComputeBudgetInstruction::set_loaded_accounts_data_size_limit(0)` (structurally valid, semantically invalid).

Expected (current, buggy) behavior: `num_dropped_on_parsing_and_sanitization == 0`, `num_dropped_on_compute_budget == 1`, and the ALT resolution path (`load_addresses_for_view`) is exercised (verifiable via instrumentation/mock bank call-count) before rejection — demonstrating the invalid packet was rejected only after paying for ALT resolution and lock validation. A corrected implementation should show the same final rejection classification while asserting (via call-count instrumentation on the mock bank/ALT lookup) that `load_addresses_for_view` is never invoked for this packet.

pub(crate) fn translate_to_runtime_view<D: TransactionData>(
    data: D,
    bank: &Bank,
    transaction_account_lock_limit: usize,
    sanitize_config: &SanitizeConfig,
) -> Result<(RuntimeTransaction<ResolvedTransactionView<D>>, u64), PacketHandlingError> {
    // Parsing and basic sanitization checks
    let Ok(view) = SanitizedTransactionView::try_new_sanitized(data, sanitize_config) else {
        return Err(PacketHandlingError::Sanitization);
    };

    let Ok(view) = RuntimeTransaction::<SanitizedTransactionView<_>>::try_new(
        view,
        MessageHash::Compute,
        None,
    ) else {
        return Err(PacketHandlingError::Sanitization);
    };

    // Discard non-vote packets if in vote-only mode.
    if bank.vote_only_bank() && !view.is_simple_vote_transaction() {
        return Err(PacketHandlingError::Sanitization);
    }

    if usize::from(view.total_num_accounts()) > transaction_account_lock_limit {
        return Err(PacketHandlingError::LockValidation);
    }

    let (loaded_addresses, deactivation_slot) = load_addresses_for_view(&view, bank)?;

    let Ok(view) = RuntimeTransaction::<ResolvedTransactionView<_>>::try_new(
        view,
        loaded_addresses,
        bank.get_reserved_account_keys(),
    ) else {
        return Err(PacketHandlingError::Sanitization);
    };

    // Validate no duplicate accounts (must be after resolution to catch ALT duplicates)
    if validate_account_locks(view.account_keys(), transaction_account_lock_limit).is_err() {
        return Err(PacketHandlingError::LockValidation);
    }

    Ok((view, deactivation_slot))
}

    pub fn sanitize_and_convert_to_compute_budget_limits(
        &self,
        feature_set: &FeatureSet,
    ) -> Result<ComputeBudgetLimits> {
        // Sanitize requested heap size
        let updated_heap_bytes =
            if let Some((index, requested_heap_size)) = self.requested_heap_size {
                if Self::sanitize_requested_heap_size(requested_heap_size) {
                    requested_heap_size
                } else {
                    return Err(TransactionError::InstructionError(
                        index,
                        InstructionError::InvalidInstructionData,
                    ));
                }
            } else {
                MIN_HEAP_FRAME_BYTES
            }
            .min(MAX_HEAP_FRAME_BYTES);

        // Calculate compute unit limit
        let compute_unit_limit = self
            .requested_compute_unit_limit
            .map_or_else(
                || self.calculate_default_compute_unit_limit(feature_set),
                |(_index, requested_compute_unit_limit)| requested_compute_unit_limit,
            )
            .min(MAX_COMPUTE_UNIT_LIMIT);

        let compute_unit_price = self
            .requested_compute_unit_price
            .map_or(0, |(_index, requested_compute_unit_price)| {
                requested_compute_unit_price
            });

        let loaded_accounts_bytes =
            if let Some((_index, requested_loaded_accounts_data_size_limit)) =
                self.requested_loaded_accounts_data_size_limit
            {
                NonZeroU32::new(requested_loaded_accounts_data_size_limit)
                    .ok_or(TransactionError::InvalidLoadedAccountsDataSizeLimit)?
            } else {
                MAX_LOADED_ACCOUNTS_DATA_SIZE_BYTES
            }
            .min(MAX_LOADED_ACCOUNTS_DATA_SIZE_BYTES);

        Ok(ComputeBudgetLimits {
            updated_heap_bytes,
            compute_unit_limit,
            compute_unit_price,
            loaded_accounts_bytes,
        })
    }
