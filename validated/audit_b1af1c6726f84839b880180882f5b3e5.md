### Title
Single griefing contributor can permanently block `Crowdloan::refund` for all other contributors and prevent fund dissolution - ([File: polkadot/runtime/common/src/crowdloan/mod.rs])

### Summary
The KIM report's core broken invariant is: a push-style refund inside a shared/looped code path can be made to fail by one uncooperative recipient, and because the surrounding logic propagates that single failure (`?`) instead of isolating it, it blocks state progression (cancel/refund) for *everyone else* sharing that path. The same push-refund-in-a-loop pattern with unguarded error propagation exists in `Pallet::refund` of the `pallet-crowdloan` module.

### Finding Description
`Crowdloan::refund` iterates over all contributors of an ended fund and, for each one, calls: [1](#0-0) 

```rust
for (who, (balance, _)) in contributions {
    if refund_count >= T::RemoveKeysLimit::get() {
        all_refunded = false;
        break;
    }
    CurrencyOf::<T>::transfer(&fund_account, &who, balance, AllowDeath)?;
    ...
}
```

The `?` on `CurrencyOf::<T>::transfer` propagates any transfer failure straight out of the dispatchable. Because FRAME wraps every dispatchable call in an implicit storage transaction, any `Err` returned from the call rolls back *all* storage mutations performed during that call — including the `contribution_kill` and `fund.raised` updates for contributors that were already successfully refunded earlier in the same loop iteration. This mirrors exactly the KIM pattern: "if there is an existing bid… the bid will be returned… For some tokens/accounts, refunds are not always successful," and the failure of a single refund blocks the whole batched cancellation/refund flow for every other participant.

`Currency::transfer` with `ExistenceRequirement::AllowDeath` can deterministically fail for a contributor's own account when the transferred amount does not meet requirements to (re)create the destination account — e.g. if the contributor's account has since been reaped (zero providers, no existential deposit) and the refunded `balance` is below `ExistentialDeposit`. `MinContribution` is only a soft configuration recommendation ("should almost certainly be at least ExistentialDeposit" — not enforced as an invariant), so a contributor can:
1. Contribute the minimum allowed amount to `Crowdloan::contribute`.
2. Drain/transfer away the rest of their own balance so their account is reaped (falls below ED and loses all providers) before the crowdloan ends.
3. When `refund` is eventually called by anyone, the transfer back to this now-nonexistent account with a sub-ED balance fails, the whole extrinsic errors out and reverts — including refunds already applied earlier in the same call to *other, honest* contributors.

Because `refund` always begins iterating the child-trie from the same starting point (`contribution_iterator`) and there is no skip-and-continue or "quarantine failed transfer" logic, the attacker's poisoned entry keeps failing the whole batch on every subsequent call as well, permanently blocking progress. `dissolve` requires `fund.raised.is_zero()`, which can never be reached, so the fund (and the SubmissionDeposit escrowed by the depositor) is permanently stuck, and every other contributor's funds remain locked inside `fund_account`.

### Impact Explanation
This breaks the "message queues/payout state must only advance after settlement succeeds atomically for the intended beneficiary and amount" invariant — one attacker with a minimal contribution can cause permanent lock of an entire crowdloan pot (all other contributors' funds) and its associated deposit, since neither `refund` nor `dissolve` can ever complete. This is a fund-lock DoS reachable from a fully unprivileged, non-governance, non-validator actor — squarely in the accepted "permanent user-fund lock" impact category.

### Likelihood Explanation
Likelihood is low-to-moderate: contribution amounts and reaping an account (spending down to zero, causing `dec_providers`) are entirely within an ordinary user's control and require no validator/relayer/governance privilege. The scenario needs the contributor's balance to genuinely drop under `ExistentialDeposit` for that account by the time `refund` executes, which is plausible for a small, deliberate contribution timed at `MinContribution` if that value is not itself hardened to be `>= ExistentialDeposit` (only documented as a recommendation, not enforced in code). The exact conditions (config-dependent `MinContribution`, whether `AllowDeath`+sub-ED destination reliably errors instead of silently succeeding) would need to be confirmed empirically in a running node/test, which is the main uncertainty here.

### Recommendation
Do not let a single failed transfer abort the whole `refund` loop. Catch the error per-contributor (e.g. `let _ = CurrencyOf::<T>::transfer(...)` combined with `.defensive()` logging, or explicit handling that skips/retains the entry for manual/queued reclaim) and continue refunding the remaining contributors, similar to the recommendation in the source report of recording failed transfers and exposing a separate claim path instead of relying on all pushes succeeding atomically.

### Proof of Concept
1. `Crowdloan::create` a fund with `MinContribution` set at or near `ExistentialDeposit`.
2. Attacker account contributes exactly `MinContribution` via `Crowdloan::contribute`.
3. Attacker transfers away the rest of their balance (`transfer_allow_death`) so their account is reaped and its providers/balance drop to zero.
4. Let the crowdloan end (block ≥ `fund.end`).
5. Anyone calls `Crowdloan::refund(origin, para_id)`. The loop reaches the attacker's entry, `CurrencyOf::<T>::transfer(&fund_account, &attacker, balance, AllowDeath)` fails (destination doesn't exist and balance < ED), the `?` propagates the error, and the whole extrinsic reverts — including refunds already credited to earlier contributors in the same call.
6. Every subsequent call to `refund` fails identically at the same entry; `dissolve` can never succeed since `fund.raised` never reaches zero, permanently locking the remaining pot and the depositor's `SubmissionDeposit`.
