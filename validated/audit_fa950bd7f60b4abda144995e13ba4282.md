### Title
Reentrant `collateral-add` in vault allows nested obligation creation to overwrite `reverse[account]`, permanently orphaning previously-deposited collateral - ([File: mainnet/contracts/market/v0-market-vault.clar])

### Summary
`collateral-add` in `v0-market-vault.clar` reads the account's obligation id via `resolve-or-create` and only persists it to the `reverse`/`registry` maps at the very end via `insert`, *after* the external token transfer (`receive-tokens`) has executed. Because the transferred asset is an attacker-supplied `<ft-trait>` contract, its `transfer` implementation can call back into the same `collateral-add` flow before the outer `insert` runs, creating a second obligation id for the same account. When the outer call resumes, its stale `insert` overwrites `reverse[account]` back to the first id, permanently orphaning the collateral recorded under the second id.

### Finding Description
In `collateral-add` [1](#0-0) :

1. `(entry (resolve-or-create account))` reads `reverse[account]`; if absent, `create` allocates a new id via `(increment)` but this is only a returned struct - `reverse`/`registry` are **not** written yet [2](#0-1) .
2. `add-user-collateral` immediately writes `collateral{user-id, asset-id} = amount` as part of the `let` binding evaluation, before any of the `try!` checks in the body run [3](#0-2) .
3. `(try! (receive-tokens ft amount account))` performs `(contract-call? asset transfer amount account current-contract none)` — a synchronous call into the attacker-controlled `ft` contract [4](#0-3) .
4. Only *after* that external call returns does the function execute `(insert updated-entry)`, which is the sole place that commits `map-set reverse (get account params) id` and `map-set registry id params` [5](#0-4) , [6](#0-5) .

Because `reverse[account]` is not written until step 4, a malicious `ft` contract's `transfer` function can, before returning control to the outer call, re-enter the market hub's `collateral-add` for the *same* `account` (routed back through the hub contract set as `impl`, so `check-impl-auth`'s `contract-caller == (var-get impl)` check still passes on the nested call [7](#0-6) ). The nested call's own `resolve-or-create` still sees no `reverse[account]` entry (outer hasn't written it), so it allocates a second id `N+1`, writes `collateral{N+1, asset-id2} = amount2`, and commits `reverse[account] = N+1` via its own `insert` before returning. Control then returns to the outer call, which finishes with its own stale `updated-entry` (id `N`) and calls `insert`, clobbering `reverse[account]` back to `N`. The collateral row at `{id: N+1, asset: asset-id2}` remains in the `collateral` map but is now unreachable: `resolve`, `resolve-safe`, and `get-position` all key off `reverse[account]`, which now points only to `N` [8](#0-7) . No public function can ever re-derive id `N+1` for that account again, since `resolve-or-create` will always resolve to `N`.

No pause flag, `check-impl-auth`, or amount-zero check prevents this, because they check only outer-call preconditions and do not guard against reentrant mutation of `reverse`/`registry` mid-flow, and Clarity's `contract-call?` semantics permit synchronous reentrant calls through the hub contract.

### Impact Explanation
Real tokens corresponding to `amount2` are transferred into the vault contract (assuming `ft2` is a genuine SIP-010 asset) and recorded in the `collateral` map, but the position becomes permanently unreachable via any public entry point once `reverse[account]` is overwritten to `N`. This is a **Critical - permanent freezing of funds**: value is locked in the vault with no code path to withdraw or liquidate it.

### Likelihood Explanation
The attacker needs only to deploy a contract implementing `ft-trait` (no privileged role required) and pass it as the `ft` argument to `collateral-add`, having its `transfer` function issue a nested call to the market hub's `collateral-add` for the same `account`/asset before returning. This is fully within the attacker's control (their own contract, their own call ordering) and is repeatable for any never-before-tracked account, including the attacker's own. Capital cost is limited to the amount deposited in the nested call, which becomes the frozen amount.

### Recommendation
Follow checks-effects-interactions ordering: commit the obligation id via `insert` (writing `reverse`/`registry`) **before** performing the external token transfer, or add an explicit reentrancy guard on `collateral-add`/`debt-add-scaled` (e.g., a boolean lock checked and set before `receive-tokens` and cleared/asserted after). Alternatively, compute and persist `resolve-or-create`'s allocation atomically prior to any external call, so a reentrant call sees the already-registered id instead of creating a duplicate.

### Proof of Concept
Clarinet/vitest simnet plan:
1. Deploy `malicious-ft.clar` implementing `ft-trait`, whose `transfer` function (when invoked with a designated flag/amount) calls `contract-call? .v0-4-market collateral-add account amount2 .ft2 asset-id2` before returning `(ok true)`.
2. Deploy a second benign asset `ft2` (or reuse `malicious-ft` for the nested leg with a non-reentrant flag).
3. From attacker account, call market hub's `collateral-add(account, amount1, malicious-ft, asset-id)` where `account` has no `reverse` entry yet.
4. Inside `malicious-ft.transfer`, before returning, trigger the nested `collateral-add(account, amount2, ft2, asset-id2)` call.
5. After the outer transaction settles, assert:
   - `(contract-call? .v0-market-vault resolve account)` returns id `N` (the outer id).
   - `(contract-call? .v0-market-vault get-collateral N+1 asset-id2)` equals `amount2 > 0`.
   - `(contract-call? .v0-market-vault get-position account MAX-U128)` does not include the `asset-id2`/`amount2` entry, confirming it is unreachable from the account's resolved position.

(define-public (collateral-add (account principal) (amount uint) (ft <ft-trait>) (asset-id uint))
  (let ((states (var-get pause-states))
        (entry (resolve-or-create account))
        (user-id (get id entry))
        (mask (get mask entry))
        (updated-mask (mask-update mask asset-id true true)) ;; collateral, insert
        (updated-entry (merge entry (refresh updated-mask)))
        (result (add-user-collateral user-id asset-id amount)))

    (try! (check-impl-auth))
    (asserts! (not (get collateral-add states)) ERR-PAUSED)
    (asserts! (> amount u0) ERR-AMOUNT-ZERO)

    (try! (receive-tokens ft amount account))
    
    (insert updated-entry)

    (print {
      action: "collateral-add",
      caller: contract-caller,
      data: {
        account: account,
        asset-id: asset-id,
        amount: amount,
        updated-collateral-amount: result,
        mask-before: mask,
        mask-after: updated-mask
      }
    })
      
    (ok result)))
