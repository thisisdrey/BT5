Audit Report

## Title
Unconditional zero-amount `IERC20::transfer` calls in `ERC20Transactor` allow public XCM messages to revert legitimate asset settlement - (File: `cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs`)

## Summary
`ERC20Transactor::withdraw_asset_with_surplus` and `ERC20Transactor::deposit_asset_with_surplus` extract `amount` from the XCM `Asset` via `Matcher::matches_fungibles(what)` and pass it directly into `IERC20::transferCall { value: EU256::from(amount) }` without any zero-value check, executed via `pallet_revive::Pallet::<T>::bare_call` [1](#0-0) [2](#0-1) . If the target ERC20 contract reverts on a zero-value `transfer` (a documented, standards-permitted behavior), the transactor surfaces `XcmError::FailedToTransactAsset`, aborting the whole XCM program.

## Finding Description
Both entrypoints compute `amount` from the matched fungible asset and unconditionally build and dispatch a `transferCall` with that value, then treat `return_value.did_revert() == true` as a hard `FailedToTransactAsset` error, aborting execution of the entire XCM instruction [3](#0-2) [4](#0-3) . There is no `amount.is_zero()` short-circuit anywhere in either function. `ERC20Transactor` is wired into Asset Hub Westend's `AssetTransactors` tuple alongside `FungibleTransactor`, `FungiblesTransactor`, `ForeignFungiblesTransactor`, and `UniquesTransactor` [5](#0-4) , making it reachable from any XCM program that resolves a `WithdrawAsset`/`DepositAsset` instruction to an ERC20-backed asset — including public entrypoints such as `pallet_xcm::execute` and incoming reserve/bridge transfers.

The Snowbridge outbound-queue converter explicitly tests for and rejects `Fungible(0)` assets with `XcmConverterError::ZeroAssetTransfer` before they are ever placed into an XCM program [6](#0-5) , confirming that zero-amount legs are a recognized, real occurrence class in this codebase's XCM flows that other components explicitly guard against — but `ERC20Transactor` does not.

However, examining sibling transactors reveals this is not a defect unique to `ERC20Transactor`: `FungibleTransactor` (`fungible_adapter.rs`) and `FungiblesTransactor` (`fungibles_adapter.rs`) also call `Fungible::withdraw`/`Assets::withdraw` and `Fungible::issue`/`Assets::issue` without any zero-amount short-circuit [7](#0-6) [8](#0-7) . The reason these do not revert on zero amounts is not an explicit zero check but rather that `pallet-balances`/`pallet-assets`' underlying `withdraw`/`issue` operations are no-ops (or succeed trivially) for a zero balance change — i.e., the safety comes from the settlement backend's tolerant behavior, not from a guard in the adapter. `ERC20Transactor`'s backend is an arbitrary, attacker/asset-issuer-controlled ERC20 contract via `pallet-revive`, which is not guaranteed to be tolerant of zero-value transfers, so the same adapter-level omission that is harmless for native/`pallet-assets`-backed transactors becomes a genuine external-dependency risk for ERC20-backed assets specifically.

## Impact Explanation
Since `ERC20Transactor` is part of Asset Hub's `AssetTransactors`, an XCM program that includes a `WithdrawAsset`/`DepositAsset` leg for a zero-value (or rounded-to-zero) ERC20-backed asset causes `FailedToTransactAsset`, aborting the entire XCM instruction. If other legs of the same multi-asset program had already withdrawn/moved funds before this abort, those funds can become stuck pending manual recovery, and the intended beneficiary never receives settlement for the ERC20 leg. This aligns with the "permanent user-fund or bridge-state lock" / "public underpriced work that... stalls bridge processing" impact class, though whether funds become truly *unrecoverable* versus recoverable via existing XCM error-handling/refund mechanisms (e.g. `SetAssetClaimer`) depends on the specific XCM program structure and was not independently verified against a concrete unrecoverable-fund scenario in this review.

## Likelihood Explanation
Triggering the code path requires no privileged access — any account able to submit `pallet_xcm::execute` or an incoming reserve/bridge transfer resolving to an ERC20-backed asset with amount zero can reach it. The actual severity, however, is conditioned on an external, out-of-repo factor: whether the specific ERC20 contract registered for a given asset actually reverts on `transfer(value=0)`. Most common ERC20 implementations (OpenZeppelin, etc.) do **not** revert on zero-value transfers; only a minority of nonstandard tokens do. This makes the vulnerability's practical likelihood contingent on which token contracts get registered against `ERC20Transactor`, which is governance-controlled asset-registration behavior, not something the attacker fully controls.

## Recommendation
Add an explicit zero-amount short-circuit in `ERC20Transactor::withdraw_asset_with_surplus` and `deposit_asset_with_surplus`, returning success with a zero fungible credit/no-op instead of invoking `IERC20::transferCall` when `amount == 0`, consistent with the zero-check pattern used elsewhere in the codebase (e.g. `pallet-staking`'s `make_payout`, `pallet-nomination-pools`' `do_reward_payout`). The same fix should be applied to `pallet_revive::impl_fungibles::{burn_from, mint_into}` for consistency, since they share the identical zero-value transfer call pattern.

## Proof of Concept
1. Deploy an ERC20 contract behind `pallet-revive` whose `transfer` function reverts when `value == 0`.
2. Register this contract as a recognized asset for `ERC20Transactor` on Asset Hub via governance/asset registration.
3. Submit an XCM program via `pallet_xcm::execute` (or an incoming reserve transfer) containing a `WithdrawAsset`/`DepositAsset` instruction for this asset with `Fungible(0)`.
4. Observe `ERC20Transactor::withdraw_asset_with_surplus` build `IERC20::transferCall{value:0}`, dispatch via `bare_call`, get `did_revert() == true`, and return `Err(XcmError::FailedToTransactAsset("ERC20 contract reverted"))`, aborting the XCM program [9](#0-8) .
