### Title
Stale PromiseYield state after account deletion enables cross-owner callback execution against a recreated account - (File: core/store/src/utils/mod.rs, runtime/runtime/src/lib.rs)

### Summary
`remove_account` (core/store/src/utils/mod.rs:505-575) does not clear `TrieKey::PromiseYieldReceipt`/`PromiseYieldStatus`/`YieldIdToDataId`/`DataIdToYieldId` rows created by `create_promise_yield_receipt`/`create_promise_yield_receipt_with_id` (runtime/runtime/src/ext.rs:353-400). If the yield-creating account is deleted via `Action::DeleteAccount` and later recreated at the same `AccountId`, a subsequent `PromiseResume` (attacker-controlled, since anyone can call `promise_yield_resume`/timeout mechanism resolves it) will still find the stale `PromiseYieldReceipt` in `apply_action_or_receipt`/`process_receipt` (runtime/runtime/src/lib.rs:1514-1562) and execute the old callback's actions against whatever account currently exists at that id.

### Finding Description
`create_promise_yield_receipt`/`create_promise_yield_receipt_with_id` in `runtime/runtime/src/ext.rs:353-400` store the pending callback receipt (in `receipt_manager`, later persisted via `set_promise_yield_receipt`, `runtime/runtime/src/lib.rs:1495-1498`) keyed only by `(receiver_id: AccountId, data_id)`, with no binding to any account-lifetime nonce/epoch such as the account's storage nonce, creation counter, or code hash. When a `PromiseResume` (or a timeout-generated resume, `resolve_promise_yield_timeouts`, `runtime/runtime/src/lib.rs:3009-3105`) arrives, `lib.rs:1514-1562` looks up the pending receipt purely by `(account_id, data_id)`, and if found, executes the parked action receipt (the callback, e.g. `Action::Transfer` to the attacker) against the account currently present at that id — with no check that this is the "same" account instance that created the yield.

`action_delete_account` (`runtime/runtime/src/actions.rs:314-390`) calls `remove_account` (`core/store/src/utils/mod.rs:505-575`), which removes `TrieKey::Account`, `TrieKey::ContractCode`, access keys/gas keys, and `TrieKey::ContractData`, but has no code path touching `TrieKey::PromiseYieldReceipt`, `TrieKey::PromiseYieldStatus`, `TrieKey::YieldIdToDataId`, or `TrieKey::DataIdToYieldId`. So a pending yield's receipt and status rows survive account deletion untouched.

Exploit flow: attacker deploys a contract at `sub.attacker.near`, calls `promise_yield_create` (or `..._with_id`) with a callback that transfers the account's full balance out; before resume, the contract self-submits `Action::DeleteAccount(beneficiary_id: attacker)`; the account is then recreated (`CreateAccount`) and refunded/funded by new deposits from a third party or the same attacker acting as a new "owner." When the yield resolves (attacker-controlled, either by calling `submit_promise_resume_data`/`promise_yield_resume` themselves before deletion completes, or by waiting for the yield's timeout in `resolve_promise_yield_timeouts`), the parked receipt executes against the **new** account instance, transferring its balance to the attacker via the pre-existing `Action::Transfer` in the callback, without the new account owner ever authorizing that action.

Existing checks don't stop this: `remove_account` is unaware of yield state; `action_delete_account` doesn't query or purge `PromiseYieldReceipt`/`PromiseYieldStatus`/yield-id mappings for the account being deleted; and the resume/timeout lookup path (`get_promise_yield_receipt`, `lib.rs:1514`) has no concept of "account generation" to reject stale receipts.

### Impact Explanation
This matches theft-of-funds / value-conservation-violation impact: an old, dangling PromiseYield callback (created and controlled entirely by the *previous* owner of an account id) can execute against a newly-recreated, independently-funded account and drain its balance via `Action::Transfer`, without any signature or transaction from the new account's controller. This is a cross-account-lifetime authorization bypass — the "receiver_id" account-id namespace is reused but the underlying trust/ownership context is not, and the runtime has no mechanism to invalidate promise-yield state tied to a destroyed account.

### Likelihood Explanation
Preconditions are all attacker-controlled and cheap: deploy any wasm contract on a subaccount (`sub.attacker.near`), create a yield with a callback doing `Action::Transfer` to an attacker address, then delete the same account with `Action::DeleteAccount`, then let (or cause) recreation and funding of the same account id, then trigger the callback via resume or (if unable to resume directly) simply wait for the yield timeout (`resolve_promise_yield_timeouts`) to auto-fire the resume. All steps are ordinary signed transactions from the account owner — no validator/node access needed. The scenario is fully repeatable and can be scripted as a runtime/apply-path integration test.

### Recommendation
When deleting an account (`action_delete_account` / `remove_account`), also purge any pending `TrieKey::PromiseYieldReceipt`, `TrieKey::PromiseYieldStatus`, `TrieKey::YieldIdToDataId`, and `TrieKey::DataIdToYieldId` rows for that account (e.g., iterate/prefix-scan those columns for the account id, similar to how access keys and contract data are already purged in `remove_account`, and either refund/burn or fail the deletion if pending yields exist), so no dangling promise-yield callback receipt can survive to execute against a future account instance at the same id.

### Proof of Concept
Runtime integration test (in `integration-tests/src/tests/runtime/` alongside `test_yield_resume.rs`):
1. Deploy a test contract at `victim.alice.near` whose method `yield_create_drain` calls `promise_yield_create` with callback `drain_to_attacker` (an `Action::Transfer` of the account's full balance to `attacker.near`).
2. Submit a transaction calling `yield_create_drain`, capture the returned `data_id`.
3. In a subsequent transaction from `victim.alice.near`, submit `Action::DeleteAccount(beneficiary_id: attacker.near)`.
4. Submit `Action::CreateAccount` + `Action::Transfer` (funding) to recreate `victim.alice.near` with a fresh balance, funded by an unrelated party.
5. Submit `promise_yield_resume(data_id, payload)` (or advance blocks until the yield timeout fires via `resolve_promise_yield_timeouts`).
6. Assert: the recreated account's balance decreases by the transferred amount and `attacker.near`'s balance increases correspondingly, with no transaction signed by the new account's key authorizing the transfer — demonstrating unauthorized value transfer via stale `PromiseYieldReceipt`/`PromiseYieldStatus` state that `remove_account` failed to clear.
