## Finding: Heap buffer over-read parsing a truncated Central Directory Header in `InputJar::NextEntry`

### Title
Heap-based buffer over-read when parsing a truncated ZIP Central Directory Header - (File: `src/tools/singlejar/input_jar.h`)

### Summary
`singlejar`, which Bazel's Java rules invoke to merge dependency jars (including jars fetched from external, attacker-controlled origins via `http_jar`/`maven_jar`/`http_archive`), parses each `CDH` (Central Directory Header) entry with a bounds check that only validates that a *single byte* at the start of the next header lies inside the mapped buffer, not that the entire fixed-size header struct fits.

### Finding Description
`InputJar::NextEntry` advances to the next Central Directory Header and validates it with: [1](#0-0) 

The check `mapped_file_.mapped(new_cdr)` only verifies that the *pointer itself* is within `[mapped_start_, mapped_end_)`: [2](#0-1) 

It does not verify that the full, fixed 46-byte `CDH` structure — whose `file_name_length_`, `extra_fields_length_`, and `comment_length_` fields sit at fixed offsets near the end of that struct — actually lies inside the mapped region: [3](#0-2) [4](#0-3) 

Because `cdh_->size()` (called at line 71 of `input_jar.h`, before the very check that is supposed to validate it) and later `cdh_->is()`, `file_name_length()`, `extra_fields_length()`, `comment_length()` all read fixed offsets relative to `cdh_`, a crafted jar whose final Central Directory Header is truncated so that `new_cdr` sits only 1–3 bytes before `mapped_end_` will cause these accessors to read past the end of the mapped file buffer. This is structurally the same bug class as CVE-2020-19751: a size/length field belonging to a container record is consumed to advance a cursor and interpret subsequent structure fields without first confirming that the full record fits within the allocated/mapped buffer, leading to a heap-based buffer over-read.

The buffer here is a `mmap`'d file (`MappedFile`), so depending on file-size/page alignment this either (a) reads adjacent zero-filled bytes within the last page — corrupting parsed `file_name_length`/`extra_fields_length`/`comment_length` with attacker-uncontrolled but out-of-record data that is subsequently used to compute `file_name()`/`extra_fields()` pointers and lengths, which flow into `memcpy`s when re-emitting the entry into the merged output jar — or (b) if the truncated header lands exactly at the final mapped page boundary, reads past the mapping into unmapped memory, causing a SIGSEGV crash of the Bazel build action.

### Impact Explanation
An attacker who publishes/serves a jar dependency (e.g. via a compromised or malicious `http_jar`/`maven` artifact URL) that a victim's build consumes through `singlejar`'s jar-merging step (used pervasively by `java_binary`/`java_library` rule implementations) can trigger this over-read. Depending on memory layout this produces either a worker-process crash (build breakage) or corrupted length fields that get propagated into `memcpy` calls building the output jar's directory records, potentially copying adjacent heap contents into the merged output artifact.

### Likelihood Explanation
Any build that merges a jar from an external, attacker-published source into a deploy/merged jar via `singlejar` will exercise this code path when reading the jar's Central Directory. The only requirement is a slightly truncated final Central Directory Header, which is straightforward to construct in a crafted zip and is not something a `sha256` pin on the archive would prevent since the sha256 pins exactly this malicious file's bytes.

### Recommendation
In `InputJar::NextEntry`, before dereferencing any `CDH` field, validate that at least `sizeof(CDH)` bytes (and subsequently the full `cdh_->size()`, including variable-length name/extra/comment fields) remain within the mapped region — i.e. check `mapped_file_.mapped(new_cdr) && mapped_file_.mapped(new_cdr + sizeof(CDH) - 1)` prior to calling `cdh_->size()`, `is()`, or any length accessor, and re-validate the full computed `size()` before advancing again.

### Proof of Concept
A `gtest`-based reproduction (in the spirit of the existing `CreateZipWithMalformedExtraField` helper in `output_jar_simple_test.cc`) would: [5](#0-4) 

1. Build an in-memory zip whose EOCD (`ECD`) declares a Central Directory containing 2 entries, but truncate the buffer so the second `CDH` starts only 2 bytes before the buffer's end.
2. Call `InputJar::Open(path, data, length)` (the in-memory overload) followed by repeated `NextEntry()` calls.
3. Run under AddressSanitizer/heap-buffer-overflow detection (or feed a `mmap`'d file whose size is exactly a multiple of the page size for the true unmapped-page crash variant) to observe the out-of-bounds read when `cdh_->size()`/`file_name_length()` are evaluated on the truncated second header, before the `mapped()` check on the *next* cursor advance would have any chance to reject it.

std::string CreateZipWithMalformedExtraField() {
  std::string zip_data;
  const std::string filename = "evil.bin";

  // 1. Local File Header (LFH)
  size_t lh_offset = zip_data.size();
  size_t lh_size = sizeof(LH) + filename.size();
  zip_data.resize(lh_offset + lh_size, 0);
  auto* lh = reinterpret_cast<LH*>(&zip_data[lh_offset]);
  lh->signature();
  lh->version(10);
  lh->file_name(filename.data(), filename.size());

  // 2. Extra field payload containing an oversized payload_size
  uint8_t ef_buffer[8] = {0};
  auto* ef1 = reinterpret_cast<ExtraField*>(ef_buffer);
  ef1->signature(0x000d);
  ef1->payload_size(0);

  auto* ef2 = reinterpret_cast<ExtraField*>(ef_buffer + ef1->size());
  ef2->signature(0xdead);
  ef2->payload_size(0xf000);  // Malformed size exceeding extra field buffer

  // 3. Central Directory Header (CDH)
  size_t cdh_offset = zip_data.size();
  size_t cdh_size = sizeof(CDH) + filename.size() + sizeof(ef_buffer);
  zip_data.resize(cdh_offset + cdh_size, 0);
  auto* cdh = reinterpret_cast<CDH*>(&zip_data[cdh_offset]);
  cdh->signature();
  cdh->version(20);
  cdh->version_to_extract(10);
  cdh->local_header_offset32(lh_offset);
  cdh->file_name(filename.data(), filename.size());
  cdh->extra_fields(ef_buffer, sizeof(ef_buffer));

  // 4. End of Central Directory (EOCD)
  size_t ecd_offset = zip_data.size();
  zip_data.resize(ecd_offset + sizeof(ECD), 0);
  auto* ecd = reinterpret_cast<ECD*>(&zip_data[ecd_offset]);
  ecd->signature();
  ecd->this_disk_entries16(1);
  ecd->total_entries16(1);
  ecd->cen_size32(cdh_size);
  ecd->cen_offset32(cdh_offset);

  return zip_data;
}
