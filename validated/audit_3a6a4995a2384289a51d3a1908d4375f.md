## Title
Missing domain separator in `ValidateMultiSign` precompile hash construction enables cross-contract/cross-chain signature replay - (`File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `ValidateMultiSign` TVM precompile (contract address `0x...0a`) lets any deployed smart contract verify an off-chain signature against a TRON account's multi-sig `Permission`. The message hash it checks against is built purely from the signer account's address, a permission id, and an arbitrary caller-supplied payload — it never binds the signature to the calling contract's address or to the chain id. This is the exact bug class described in the external report: a signature-verification routine that omits an EIP-712-style domain separator, allowing a signature produced for one context to be replayed in a different context.

### Finding Description
`ValidateMultiSign.execute()` computes the hash that signers must sign as: [1](#0-0) 

```
byte[] address = words[0].toTronAddress();
int permissionId = words[1].intValueSafe();
byte[] data = words[2].getData();
byte[] combine = ByteUtil.merge(address, ByteArray.fromInt(permissionId), data);
byte[] hash = Sha256Hash.hash(..., combine);
```

The resulting `hash` is what off-chain signers sign (as shown by the test helper building `toSign` the same way) [2](#0-1) , and it is only ever composed of `(account address, permissionId, arbitrary data)`. There is no inclusion of:
- the address of the **calling smart contract** (the "verifier"/relying party), and
- the **chain id** / network identifier.

Any smart contract deployed on the network can call this precompile at address `0x...a` (gated only by `VMConfig.allowTvmSolidity059()`) [3](#0-2) , supplying whatever `data` value it wants checked. If a user signs a hash `sha256(address || permissionId || data)` to authorize action `data` in contract A, that exact same signature is valid input to `validatemultisign` for any other contract B (or on any other TRON-derived chain/testnet sharing the same account-address space) that happens to check the same `(address, permissionId, data)` triple — because nothing in the hash commits the signature to contract B or to a specific chain.

This mirrors the reported `hashForKYC()` flaw: the fix there was to add `chain.id` and the verifying contract's address into the signed hash so a signature can't be replayed across chains/contracts. `ValidateMultiSign` has the analogous gap.

### Impact Explanation
Multiple independently-deployed TVM contracts (and independent TRON-compatible chains/testnets that reuse the same account key/address derivation) can legitimately use `validatemultisign` as a generic "does this account approve this payload" oracle for arbitrary application logic (order approval, withdrawal authorization, off-chain KYC-style attestations, etc.). Because the signed hash has no domain separator tying it to the calling contract or chain, an attacker who obtains a signature intended for use in one dApp/contract can replay it to satisfy the same `(address, permissionId, data)` check in a different, unrelated dApp/contract (or the same contract redeployed on another chain), potentially causing unauthorized account operations or approvals within that second contract — a concrete authorization bypass leading to theft or unauthorized action, not merely a low-impact issue.

### Likelihood Explanation
Exploitability depends on application-level reuse of identical `(address, permissionId, data)` triples across multiple contracts/chains, which is a realistic and encouraged usage pattern for a generic "verify account approval" precompile — the precompile's own design provides no protection, so any dApp author who assumes the signature is scoped to their contract is silently exposed. This requires only a normal signed message from a user and a malicious/careless second contract deployment — reachable by an ordinary contract deployer, no special privilege needed.

### Recommendation
Include a domain separator in the hash computed by `ValidateMultiSign` (and `BatchValidateSign` if it shares this pattern), analogous to the `hashForKYC` fix: incorporate `chain.id` and/or the address of the calling contract (`msg.sender`/the precompile caller context) into the `combine` buffer before hashing, so a valid signature for one contract/chain cannot be replayed against another.

### Proof of Concept
1. User signs `toSign = sha256(accountAddress || permissionId || dataX)` intending to authorize `dataX` in Contract A, which calls `validatemultisign(accountAddress, permissionId, dataX, [sig])`.
2. Attacker deploys Contract B that also calls `validatemultisign(accountAddress, permissionId, dataX, [sig])` for its own unrelated authorization check (e.g., approving a withdrawal keyed by the same `dataX` hash, perhaps because `dataX` is a commonly-derived value such as a hash of a well-known constant or a value the attacker can force to collide).
3. Because the hash construction at `PrecompiledContracts.java:1062-1064` never differentiates between Contract A and Contract B (or between chains), the same `sig` recovers successfully in Contract B's call to `ValidateMultiSign`, letting the attacker's contract treat the user's account as having approved an action it never intended for Contract B.
