### Title
Null Pointer Dereference in TVM Dynamic Energy Accounting - (File: actuator/src/main/java/org/tron/core/vm/program/Program.java)

### Summary
`Program.addContextContractUsage(long value)` fetches a `ContractStateCapsule` from the contract-state store and immediately calls a member method on it without checking for `null`, unlike its sibling method `updateContextContractFactor()` a few lines above, which explicitly null-checks the same lookup and lazily creates the capsule when absent.

### Finding Description
`Program.java` contains two closely related methods that both retrieve a `ContractStateCapsule` for the currently executing contract address via `contractState.getContractState(getContextAddress())`:

- `updateContextContractFactor()` (lines 2371-2394) explicitly handles the `null` case: [1](#0-0) 
```
public long updateContextContractFactor() {
    ContractStateCapsule contractStateCapsule =
        contractState.getContractState(getContextAddress());

    if (contractStateCapsule == null) {
      contractStateCapsule = new ContractStateCapsule(
          contractState.getDynamicPropertiesStore().getCurrentCycleNumber());
      contractState.updateContractState(getContextAddress(), contractStateCapsule);
    } else {
```

- `addContextContractUsage(long value)` (lines 2396-2402) performs the identical lookup but dereferences the result directly, with **no null check**: [2](#0-1) 
```
public void addContextContractUsage(long value) {
    ContractStateCapsule contractStateCapsule =
        contractState.getContractState(getContextAddress());

    contractStateCapsule.addEnergyUsage(value);
    contractState.updateContractState(getContextAddress(), contractStateCapsule);
}
```

`contractState.getContractState(address)` returns whatever is stored in the `ContractStateStore` for that address; if no entry exists (a fresh contract-address context, or one whose state has not yet been initialized by `updateContextContractFactor` for the current call path), the result is `null`, and `contractStateCapsule.addEnergyUsage(value)` throws a `NullPointerException`. This is the same bug class as the reported TensorFlow CVE: a pointer/reference obtained from state is dereferenced without validating it is non-null, where a sibling code path performing the identical lookup correctly guards against the null case.

This dynamic energy usage tracking is part of the TVM's dynamic energy adjustment feature (`VMConfig.allowTvmFreezeV2`/dynamic energy threshold logic used across `Program.java`), which is invoked during ordinary smart-contract execution triggered by `TriggerSmartContract`/`CreateSmartContract` transactions and reached from `VM.java` during normal opcode execution.

### Impact Explanation
An uncaught `NullPointerException` thrown during TVM execution inside `VM.play()` propagates as a `BytecodeExecutionException`/unchecked runtime exception through the actuator/`VMActuator` execution path. Depending on where in the call stack it is caught, this can cause a transaction to fail unexpectedly for legitimate contract interactions, or, if not properly caught by the node's transaction-processing guard, cause the node to enter an inconsistent state during block application, potentially crashing the processing thread. Any node executing the same block deterministically hits the same code path, meaning it can also lead to a full network-wide processing failure/halt rather than an isolated node crash if the condition is reachable in a real block-application flow.

### Likelihood Explanation
This is contingent on the exact invocation order between `updateContextContractFactor()` and `addContextContractUsage()` on any given contract address' execution context within `VM.java`; the tool budget did not allow full verification of call-graph guarantees at the `VM.java` call site (only one call site was located, but its precise ordering relative to `updateContextContractFactor()` for the same address could not be fully confirmed with the available reasoning budget). The asymmetry between the two nearly-identical methods — one carefully guards against `null`, the other does not — is a strong code-smell indicator consistent with an unintentionally missing safety check, matching the reported vulnerability's root cause pattern precisely.

### Recommendation
Add the same null-check/lazy-initialization pattern used in `updateContextContractFactor()` to `addContextContractUsage()`:
```java
public void addContextContractUsage(long value) {
    ContractStateCapsule contractStateCapsule =
        contractState.getContractState(getContextAddress());
    if (contractStateCapsule == null) {
      contractStateCapsule = new ContractStateCapsule(
          contractState.getDynamicPropertiesStore().getCurrentCycleNumber());
    }
    contractStateCapsule.addEnergyUsage(value);
    contractState.updateContractState(getContextAddress(), contractStateCapsule);
}
```
