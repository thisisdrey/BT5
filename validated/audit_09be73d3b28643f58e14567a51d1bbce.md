### Title
Permissionless reward-index updates can permanently strand rounded emissions - ([File: contracts/RewardsDistributor.sol](contracts/RewardsDistributor.sol))

### Summary
`RewardsDistributor.updateBeforeMintOrBurn()` is permissionless and updates each reward token’s timestamp even when fixed-point rounding causes the newly emitted rewards to produce no index increase or lose their fractional component. [1](#0-0)   
Because the fractional reward is not carried into the next accounting interval, an unprivileged caller can force an update every timestamp and repeatedly discard rounding remainders. [2](#0-1)   
The contract can therefore retain reward tokens that no user can ever accrue, while neither the public interface nor the implementation exposes a way to recover that undistributed balance. [3](#0-2) [4](#0-3) 

### Finding Description
`_calculateTokenIndex()` computes emissions as `deltaTimestamp * speed`, converts that amount into a WAD-scaled index increment with `wadDiv()`, stores the rounded index, and advances `timestamp` to `block.timestamp`. [2](#0-1)   
`WadRayMath.wadDiv()` rounds half-up rather than preserving a numerator remainder, so any fraction below the nearest index unit disappears from future accounting once the timestamp is stored. [5](#0-4)   
For example, with four users each holding `2e18` deposit-token units, total supply `8e18`, and a speed of `10` wei per second, each one-second update emits `10` wei but produces a rounded index increment of `1`; the four users can collectively accrue only `8` wei and the remaining `2` wei is skipped. [6](#0-5)   
Calling `updateBeforeMintOrBurn()` once per timestamp prevents the fractional component from accumulating across multiple seconds, maximizing the discarded amount without requiring any privileged role. [1](#0-0)   
`claimRewards()` only transfers amounts previously recorded in `tokensAccruedOf`, so the skipped portion remains in the distributor and cannot be claimed by any user. [7](#0-6) [4](#0-3) 

### Impact Explanation
The invariant that emitted reward tokens remain attributable to users is broken because the accounting timestamp advances without retaining unallocated fractional emissions. [8](#0-7)   
This results in permanent freezing of unclaimed yield: funded reward tokens remain in the contract, but no account’s index delta can ever credit them. [4](#0-3)   
The loss can repeat once per timestamp for every incentivized deposit or debt token, allowing the stranded balance to accumulate over the lifetime of an active reward configuration. [9](#0-8)   
The attacker does not directly receive the stranded tokens, but can reliably reduce or eliminate rewards credited to all users in configurations where the per-update index calculation rounds down. [2](#0-1) 

### Likelihood Explanation
The entry point is explicitly callable by anyone and is also invoked during normal deposit-token and debt-token balance changes, so frequent index updates occur without governance or keeper involvement. [10](#0-9)   
Rounding loss occurs whenever `elapsed * speed / totalSupply` has a nonzero fractional WAD component, and the loss becomes total when that value is below `0.5` WAD. [5](#0-4)   
Because the discarded fraction is not persisted, an attacker can call the function at every new timestamp rather than allowing multiple seconds of emissions to aggregate into a larger index increment. [1](#0-0) [8](#0-7)   
The issue requires an active token speed and a distributor balance, but does not require malicious governance, oracle manipulation, flash liquidity, reentrancy, or a privileged caller. [11](#0-10) 

### Recommendation
Retain the unallocated reward remainder across index updates, either by accumulating raw emitted rewards separately or by storing the reward index at higher precision such as RAY. [2](#0-1)   
The index update should consume the carried remainder before advancing the accounting timestamp so sub-unit emissions are not erased by frequent updates. [8](#0-7)   
The distributor should also provide a bounded recovery mechanism for reward tokens that can no longer be attributed after rewards are stopped, while protecting balances corresponding to existing `tokensAccruedOf` liabilities. [4](#0-3) [12](#0-11)

```typescript
it('strands rewards discarded by repeated index rounding', async function () {
  // Two users represent the whole 4-token supply.
  msdTOKEN1.totalSupply.returns(parseEther('4'))
  msdTOKEN1.balanceOf.whenCalledWith(alice.address).returns(parseEther('2'))
  msdTOKEN1.balanceOf.whenCalledWith(bob.address).returns(parseEther('2'))

  // Fund exactly five seconds of emissions at 5 wei/second.
  await vsp.transfer(rewardDistributor.address, 25)
  await rewardDistributor.updateTokenSpeed(msdTOKEN1.address, 5)

  // Anyone can advance the index timestamp once per second.
  // Each second emits 5 wei, but 5 / 4e18 = 1.25 WAD rounds to 1.
  for (let i = 0; i < 5; ++i) {
    await increaseTimeOfNextBlock(1)
    await rewardDistributor.updateBeforeMintOrBurn(msdTOKEN1.address, alice.address)
  }

  const state = await rewardDistributor.tokenStates(msdTOKEN1.address)
  expect(state.index).eq(DEFAULT_INDEX.add(5))

  const aliceBefore = await vsp.balanceOf(alice.address)
  const bobBefore = await vsp.balanceOf(bob.address)

  await rewardDistributor['claimRewards(address[],address[])'](
    [alice.address, bob.address],
    [msdTOKEN1.address]
  )

  const aliceClaimed = (await vsp.balanceOf(alice.address)).sub(aliceBefore)
  const bobClaimed = (await vsp.balanceOf(bob.address)).sub(bobBefore)

  // Each user receives 2e18 * 5 / 1e18 = 10 wei.
  expect(aliceClaimed).eq(10)
  expect(bobClaimed).eq(10)

  // 25 wei were emitted and funded, but only 20 wei became claimable.
  // The remaining 5 wei is permanently stranded in the distributor.
  expect(await vsp.balanceOf(rewardDistributor.address)).eq(5)
})
```
