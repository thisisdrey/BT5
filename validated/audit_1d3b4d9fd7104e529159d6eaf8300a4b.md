### Title
Mid-loop revert in `VoteWitnessProcessor.execute` wastes caller-paid energy on partial vote batches - (File: `actuator/src/main/java/org/tron/core/vm/nativecontract/VoteWitnessProcessor.java`)

### Summary
The `VOTEWITNESS` native contract (invoked from smart-contract execution via `Program.java`, reachable by any unprivileged contract-call transaction) iterates over a caller-supplied list of votes and can revert with `ContractExeException` partway through the loop after already performing state-mutating operations (reward withdrawal, vote clearing), matching the reported bug class of "distribution/iteration reverts mid-loop, wasting substantial gas."

### Finding Description
`VoteWitnessProcessor.execute` first calls `VoteRewardUtil.withdrawReward(ownerAddress, repo)` and clears the account's existing votes, then iterates the new vote list: [1](#0-0) 

Inside the loop, for each vote entry it checks whether the target witness exists and throws `ContractExeException` if not, or if the vote count is negative, without any `continue`-based recovery — one bad entry anywhere in the list aborts the whole call: [2](#0-1) 

Because the reward withdrawal and `clearVotes()`/`clearNewVotes()` calls already ran (and consumed TVM energy for all preceding loop iterations) before the exception surfaces, a caller who submits a large vote list with even one invalid witness address near the end pays for all the prior iterations' energy and the exception unwinds the whole native-contract call, exactly like the reported `_distribute` issue where partial iteration work is wasted on a late-stage revert. This is reachable from any account that calls a smart contract exposing the `VOTEWITNESS` opcode, i.e., any unprivileged transaction broadcaster invoking a contract.

By contrast, the "actuator" path `VoteWitnessActuator` fully validates every vote (including witness existence) in `validate()` before `execute()` runs, so it does not have this defect — the vulnerability is specific to `VoteWitnessProcessor`, which merges validation and mutation in a single loop.

### Impact Explanation
An unprivileged caller triggering the `VOTEWITNESS` native operation with a large vote array can pay substantial energy (all iterations processed before the failing entry, plus prior state-read work and the reward-withdrawal computation) and still have the transaction revert, losing the paid energy/fee for no effect. This is a gas-griefing/wasted-fee issue for the transaction sender; it does not directly move funds but forces unnecessary, unrecoverable energy expenditure that scales with vote-list size and position of the invalid entry.

### Likelihood Explanation
Likelihood is moderate-to-high: any contract account can construct a vote list mixing valid and invalid witness addresses (e.g., a witness that was removed via governance/maintenance between vote list construction and execution, or a typo/never-existing address), and the check is per-entry inside the loop rather than pre-validated, so the failure mode is easily triggered without any special privileges.

### Recommendation
Perform witness-existence and vote-count validation for the entire vote list *before* executing any state mutation (reward withdrawal, vote clearing), similar to how `VoteWitnessActuator.validate()` separates validation from `execute()`. Alternatively, skip invalid individual vote entries (using `continue`) rather than aborting the whole call, so that valid votes in the same batch are not wasted alongside the invalid one.

### Proof of Concept
1. Deploy/call a contract that invokes the `VOTEWITNESS` TVM operation with a vote list `[validWitness1, validWitness2, ..., nonExistentWitnessN]`.
2. `VoteWitnessProcessor.execute` withdraws pending reward, clears existing votes, then iterates the list; on reaching the entry for `nonExistentWitnessN`, `repo.getWitness(witnessAddress) == null` triggers `throw new ContractExeException(...)` at [3](#0-2) .
3. The whole native-contract call reverts, but energy for all prior loop iterations, the reward withdrawal, and vote-clearing has already been metered and charged to the caller.
