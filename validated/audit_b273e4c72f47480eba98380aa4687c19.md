Audit Report

## Title
`ERC20Transactor` trusts the ERC-20 `transfer()` boolean return value instead of verifying actual balance movement, allowing minting of unbacked XCM asset holdings - (File: cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs)

## Summary
`ERC20Transactor::withdraw_asset_with_surplus` and `deposit_asset_with_surplus` bridge XCM `Asset` semantics to `pallet-revive`-hosted ERC-20 contracts by calling `transfer()` via `bare_call` and treating a decoded `true` return as full proof that `amount` moved, without ever checking real balances before/after the call. Combined with `ERC20Matcher` (`assets_common::ERC20Matcher = MatchedConvertedConcreteId<H160, u128, IsLocalAccountKey20, ...>`), which accepts *any* locally deployed contract at an `AccountKey20` location as a valid XCM fungible asset with no allowlist/registration step, an attacker can deploy a contract whose `transfer()` always returns `true` regardless of real balance movement and cause the XCM executor to record `AssetsInHolding` credit unbacked by the checking account's actual token balance.

## Finding Description
`withdraw_asset_with_surplus` calls `IERC20::transferCall` to move `amount` from `who` to the checking account via `pallet_revive::Pallet::<T>::bare_call` [1](#0-0) , then unconditionally constructs an `Erc20Credit(amount)` fungible credit the moment the ABI-decoded return value is `true`, without any `balanceOf` check [2](#0-1) . The comment on `Erc20Credit` explicitly documents that "the actual balance constraints are enforced by the ERC20 smart contract itself rather than the runtime" [3](#0-2) . `deposit_asset_with_surplus` mirrors this pattern for the checking-account-to-beneficiary leg, treating `Ok(true)` as final settlement [4](#0-3) .

Critically, `ERC20Matcher` is defined as `MatchedConvertedConcreteId<H160, u128, IsLocalAccountKey20, AccountKey20ToH160, TryConvertInto>` [5](#0-4) , and `IsLocalAccountKey20` matches *any* location of the shape `(0, [AccountKey20 { .. }])` [6](#0-5) . Since any account can deploy a contract under `pallet-revive` and obtain an `AccountKey20` address, there is no governance/registration gate before a contract becomes usable as an XCM-recognized fungible asset — the amount is also arbitrarily chosen by the XCM program author, not derived from any independently verified balance. `ERC20Transactor` is wired into `asset-hub-westend`'s live `AssetTransactors` tuple [7](#0-6) , so this path is reachable in production configuration.

The only existing guard is `return_value.did_revert()` plus ABI-decode validation of the boolean return — neither of which verifies actual token movement, matching exactly the flagged pattern of trusting a self-reported success flag instead of bracketing the external call with authoritative balance reads.

## Impact Explanation
An unprivileged attacker who deploys (or targets) a `pallet-revive` contract with non-standard/malicious `transfer()` semantics (always returns `true`, fee-on-transfer, rebasing, or an upgradeable proxy that changes behavior post-onboarding) can cause the XCM executor's `AssetsInHolding` to be credited with `amount` that the checking account's real ERC-20 balance never received. This unbacked credit is a first-class XCM asset that can be deposited to any beneficiary or, where AssetConversion/swap paths exist in the runtime configuration, exchanged for genuinely backed assets — constituting an unbacked-mint / theft-of-value impact against the "conserve value and settle exactly once" pivot for asset custody and payout.

## Likelihood Explanation
No privileged role, compromised relayer, or validator misbehavior is required. Any account can deploy a contract via `pallet-revive` and submit an XCM program (e.g., via `pallet_xcm::execute` or an incoming XCM from a location they control) performing `WithdrawAsset`/`DepositAsset` against that contract's address, since `ERC20Matcher` accepts it automatically as a valid asset. The exploit is fully attacker-controlled and repeatable.

## Recommendation
Read the checking account's (and, for deposits, the beneficiary's) real ERC-20 balance via `balanceOf` immediately before and after the `transfer()` `bare_call`, and only mint/settle the `AssetsInHolding` credit when the measured delta equals the requested `amount`. Additionally, consider gating which contracts are eligible to back XCM assets via an explicit registry rather than matching any `AccountKey20` location.

## Proof of Concept
1. Deploy an ERC-20-shaped contract under `pallet-revive` whose `transfer(address,uint256)` always returns `true` without moving the declared `value` (e.g., a no-op implementation).
2. Since `ERC20Matcher` matches any `AccountKey20` location with no allowlist [8](#0-7) , this contract's address is automatically usable as an XCM `AssetId`.
3. Submit an XCM program performing `WithdrawAsset` for this asset from an attacker-controlled `who` for an arbitrary `amount`; `withdraw_asset_with_surplus` calls `transfer(checking_address, amount)`, receives `true`, and mints `AssetsInHolding` credit of the full `amount` regardless of the checking account's real balance [9](#0-8) .
4. Chain a `DepositAsset`/further instruction to move this unbacked credit to a beneficiary or into a value-exchange path, realizing value not actually backed by the token contract's real ledger.

/// `Contains<Location>` implementation that matches locations with no parents,
/// a `PalletInstance` and an `AccountKey20` junction.
pub struct IsLocalAccountKey20;
impl Contains<Location> for IsLocalAccountKey20 {
	fn contains(location: &Location) -> bool {
		matches!(location.unpack(), (0, [AccountKey20 { .. }]))
	}
}

/// Fallible converter from a location to a `H160` that matches any location ending with
/// an `AccountKey20` junction.
pub struct AccountKey20ToH160;
impl MaybeEquivalence<Location, H160> for AccountKey20ToH160 {
	fn convert(location: &Location) -> Option<H160> {
		match location.unpack() {
			(0, [AccountKey20 { key, .. }]) => Some((*key).into()),
			_ => None,
		}
	}

	fn convert_back(key: &H160) -> Option<Location> {
		Some(Location::new(0, [AccountKey20 { key: (*key).into(), network: None }]))
	}
}

/// [`xcm_executor::traits::MatchesFungibles`] implementation that matches
/// ERC20 tokens.
pub type ERC20Matcher =
	MatchedConvertedConcreteId<H160, u128, IsLocalAccountKey20, AccountKey20ToH160, TryConvertInto>;
