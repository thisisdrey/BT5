### Title
Unchecked null `DelegatedResourceCapsule` in `UnDelegateResourceActuator.execute()` causes NullPointerException / block-processing crash - (File: `actuator/src/main/java/org/tron/core/actuator/UnDelegateResourceActuator.java`)

### Summary
`UnDelegateResourceActuator.validate()` only requires that *at least one* of the "unlock" or "lock" `DelegatedResourceCapsule` records exists for the (owner, receiver) pair, but `execute()` unconditionally fetches and dereferences the "unlock" capsule without re-checking for null, mirroring the HDF5 CVE pattern: a "defined but not fully specified" state is not normalized before the value is used, and a code path downstream dereferences a null object it assumed was always present.

### Finding Description
In `validate()`: [1](#0-0) 
the check is `unlockResourceCapsule == null && lockResourceCapsule == null` → throws only when **both** are null. This means validate() passes successfully in the legitimate state where only the "locked" delegation record exists and the "unlocked" record is absent (`unlockResourceCapsule == null`, `lockResourceCapsule != null`), as long as the balance/resource-type checks based on the combined `delegateBalance` (which sums both unlock and expired-lock balances) are satisfied.

In `execute()`, however, the code fetches the unlock resource again from the store: [2](#0-1) 
and then unconditionally calls methods on it inside the `BANDWIDTH`/`ENERGY` switch without any null guard: [3](#0-2) 
`unlockResource.addFrozenBalanceForBandwidth(...)` / `unlockResource.addFrozenBalanceForEnergy(...)` will throw `NullPointerException` if `unlockResource` is null — exactly the class of bug in the CVE, where a "defined" flag combined with a not-fully-normalized size/state reaches a code path (`H5Pget_fill_value` → `H5T_path_find`) that dereferences a NULL pointer.

The companion native-contract processor `UnDelegateResourceProcessor.execute()` used by the TVM precompile path has the same shape — it re-fetches `delegatedResourceCapsule` via `repo.getDelegatedResource(key)` and dereferences it unconditionally in the switch statement: [4](#0-3) 
while its own `validate()` only checks a single non-null delegatedResourceCapsule for the *unlock* key: [5](#0-4) 
so this processor is not directly affected by the same "lock/unlock either exists" ambiguity as the actuator, but the actuator itself is reachable by unprivileged, ordinary `UnDelegateResourceContract` transactions.

### Impact Explanation
Because `execute()` runs during block/transaction application in `Manager`, an unhandled `NullPointerException` here is not caught by the actuator's own catch blocks (only `InvalidProtocolBufferException` is caught in `execute()`); it will propagate up through transaction processing. This can crash or halt block application on every node that processes the malicious transaction deterministically (since all nodes evaluate the same state), which is a full-node denial-of-service / potential chain-halt condition triggered by a single crafted, otherwise-valid signed transaction from any account holding a delegatable frozen balance.

### Likelihood Explanation
Reaching the vulnerable state requires an attacker to:
1. Freeze balance for resource delegation (`FreezeBalanceV2`).
2. Delegate resources with a lock (`DelegateResourceContract` with lock=true) to a receiver, while ensuring no separate non-locked delegation record exists for that (owner, receiver) pair (or delete/consume it, e.g. by first delegating locked-only).
3. Wait for the lock to be at least partially eligible for unlock/expiry handling, or otherwise arrange that `unlockResourceCapsule` is `null` at validate time while `lockResourceCapsule` satisfies the balance check.
4. Submit an `UnDelegateResourceContract` transaction with `unDelegateBalance` covering only the locked portion.

This is achievable purely through standard, publicly available transaction types (`FreezeBalanceV2Contract`, `DelegateResourceContract`, `UnDelegateResourceContract`) without special privileges, making it reachable by any unprivileged account. The exact edge condition (unlock resource capsule literally absent from the store, not just zero-balanced) needs confirmation in a live/test environment, since `delegatedResourceStore.unLockExpireResource(...)` is called earlier in `execute()` and could mutate state in ways that create the unlock record as a side effect before the null-fetch — this interaction was not fully traced/confirmed. I could not fully verify from static reading alone whether `unLockExpireResource` always creates a persisted unlock record before line 130 reads it back, which is the crux of whether `unlockResource` can truly be null at that point. This uncertainty should be resolved with dynamic testing/tracing before treating this as fully confirmed.

### Recommendation
Add an explicit null check for `unlockResource` in `UnDelegateResourceActuator.execute()` immediately after fetching it (mirroring the validate-time OR-based null tolerance), treating a null unlock capsule as a capsule with zero frozen balances (e.g., construct a fresh `DelegatedResourceCapsule` or skip the `addFrozenBalanceFor*` calls) before entering the `BANDWIDTH`/`ENERGY` switch. Add a corresponding regression test that creates only a locked delegation (no unlocked one) and calls `execute()` for an amount that should be drawn purely from the locked balance, verifying no `NullPointerException` is thrown.

### Proof of Concept
Not independently reproduced end-to-end (requires live/test chain state manipulation to force `unlockResourceCapsule == null` at execute-time while passing validate — see caveat above). The suggested reproduction path, based on static analysis of `UnDelegateResourceActuator.java`:
1. Freeze balance for BANDWIDTH via `FreezeBalanceV2Contract`.
2. Delegate it with `lock = true` via `DelegateResourceContract` to a receiver, ensuring no prior non-locked delegation exists between the pair.
3. Submit `UnDelegateResourceContract` for the owner/receiver pair with `balance` equal to the locked, expired amount.
4. Observe whether `delegatedResourceStore.get(unlockKey)` in `execute()` (line 130-131) returns `null`, and whether the subsequent `unlockResource.addFrozenBalanceForBandwidth(...)` call at line 137 throws `NullPointerException`, crashing transaction/block processing.
