### Title
Fee-on-transfer / deflationary NEP-141 tokens allow internal ledger to diverge from actual custody, permanently over-crediting balances - ([File: contracts/defuse/src/contract/tokens/nep141/deposit.rs])

### Summary
The `ft_on_transfer` deposit handler credits the depositor's internal balance based purely on the `amount` argument reported in the callback, without verifying that the contract's actual NEP-141 token balance increased by that same amount.

### Finding Description
`ft_on_transfer` in `contracts/defuse/src/contract/tokens/nep141/deposit.rs` unconditionally calls `self.deposit(receiver_id.clone(), [(token_id.clone(), amount.0)], Some("deposit"))` [1](#0-0) , minting internal multi-token balance equal to the `amount` value NEAR passed into the callback. There is no check comparing the token contract's balance held by the vault before and after the transfer. If the underlying NEP-141 token contract implements any deflationary/fee-charging behavior when moving tokens between its internal accounts (e.g., taking a cut before crediting the receiver, similar in spirit to Solidity fee-on-transfer ERC20s), the amount actually available to the `Contract` in the token contract can be less than `amount.0`, while the intents contract still mints `amount.0` of internal `TokenId::Nep141` balance to the depositor. This breaks the conservation invariant that the sum of internally tracked NEP-141 balances for a given underlying token must equal the token contract's real balance held by the vault (`internal ledger == actual custody`). The same unchecked minting pattern appears in the NEP-245 (`mt_on_transfer`) analog at `contracts/defuse/src/contract/tokens/nep245/deposit.rs` (lines 66-73), which mints based on `amounts` reported to the callback rather than an independently verified balance delta.

### Impact Explanation
If any accepted underlying token (now or via a future governance-approved listing) implements such fee/deflationary transfer semantics, the vault's ledger becomes over-collateralized on paper: total internal balances/`total_supplies` for that `TokenId` exceed what the contract actually holds. Subsequent withdrawals (`ft_withdraw`) for other, legitimate depositors of the same token will eventually fail or race to drain the shortfall, effectively freezing/losing funds for whoever withdraws last. This matches the "funds permanently frozen" / broken conservation criteria (Critical) because the equality `sum(internal balances for token X) == token X vault custody` is violated by design, not by an attacker exploiting authorization — it is a systemic conservation-boundary gap analogous to the referenced Sandclock fee-on-transfer issue, but manifesting as silent over-minting rather than a revert.

### Likelihood Explanation
Likelihood depends on whether any token accepted for deposit implements non-standard, fee-charging NEP-141 transfer semantics. NEP-141 as a standard does not mandate 1:1 delivery guarantees the way this contract's `ft_on_transfer` assumes; any token contract could legally implement such behavior while remaining a compliant `FungibleTokenReceiver` caller. Since token acceptance appears governed by listing/whitelisting practice rather than an enforced protocol-level balance check, this is a latent risk rather than an always-exploitable bug — likelihood is Medium, contingent on future token listings.

### Recommendation
In `ft_on_transfer` (and `mt_on_transfer`), verify the actual token balance delta held by the contract (e.g., via a synchronous `ft_balance_of` check before/after, or restrict deposits to tokens verified not to apply transfer fees) before crediting `amount.0` to the depositor's internal balance, rather than trusting the caller-supplied `amount` value unconditionally.

### Proof of Concept
1. A NEP-141 token `X` is listed that, on `ft_transfer_call`, deducts an internal fee such that the receiver's (vault's) real balance only increases by `amount * (1 - fee)`.
2. User calls `X.ft_transfer_call(defuse_contract, amount, msg)`.
3. `ft_on_transfer` executes `self.deposit(receiver_id, [(TokenId::Nep141(X), amount.0)], ...)` [1](#0-0) , crediting the user the full `amount`, while the vault's actual `X` balance only grew by `amount * (1 - fee)`.
4. Repeating deposits/withdrawals across users of token `X` causes the sum of internally tracked balances to exceed the vault's real token holdings, so some withdrawer's `ft_withdraw` call will fail due to insufficient real tokens, freezing part of the pooled balance for that token.
