I found a genuine, unmitigated data race, concretely in `OperationRegistry`/`JumpTable`: the "transaction" table (`tableMap.get(LATEST_VERSION)`) is a **single shared, mutable** `JumpTable` instance that every non-constant-call transaction execution thread mutates via `prepareAndGetTable(false)` → `adjustTable(table)` (`adjustMemOperations`, `adjustVoteWitness`, `adjustSelfdestruct`), each of which does `table.set(...)` based on `VMConfig` flags, immediately before `VM.play(program, table)` reads from that same table concurrently on other threads.

### Title
Unsynchronized mutation of the shared consensus JumpTable causes a cross-thread data race in TVM opcode dispatch - ([File: actuator/src/main/java/org/tron/core/vm/OperationRegistry.java])

### Summary
`OperationRegistry.getTable(false)` returns one process-wide `JumpTable` object (`tableMap.get(LATEST_VERSION)`) shared by every concurrently executing non-constant-call transaction (`OperationRegistry.java:125-127`). `VMActuator.execute()` calls `OperationRegistry.prepareAndGetTable(isConstantCall)` right before `VM.play(program, table)` for every transaction (`actuator/src/main/java/org/tron/core/vm/program/../actuator/VMActuator.java:195`), and `prepareAndGetTable` unconditionally calls `adjustTable(table)` → `table.set(...)` on that shared instance (`OperationRegistry.java:118-134`, `714-739`). ### Finding Description
This is analogous to `multiqueue`'s bug class (CWE-362): a data structure that is unconditionally treated as safely shared across threads without the synchronization its mutation actually requires. `JumpTable.set()` mutates an internal array/map keyed by opcode with no synchronization visible in `OperationRegistry`, and the same instance is handed out to every concurrent, non-constant-call transaction thread (`getTable(false)` always returns the identical `tableMap.get(LATEST_VERSION)` object). If TRON's node-side transaction/energy-metering execution is invoked concurrently for multiple pending transactions (e.g. via multi-threaded signature/energy pre-validation or a multi-threaded execution path any caller of `VMActuator.execute` runs on), each call to `adjustMemOperations`, `adjustVoteWitness`, and `adjustSelfdestruct` overwrites `Op.MLOAD/MSTORE/MSTORE8`, `Op.VOTEWITNESS`, and `Op.SUICIDE` entries in-place on the shared table while another thread's `VM.play` may be dispatching through the same entries. Because `VMConfig`'s dynamic flags (`allowHigherLimitForMaxCpuTimeOfOneTx`, `allowTvmOsaka`, `allowEnergyAdjustment`, `allowTvmSelfdestructRestriction`) are read-then-written non-atomically per call, one thread can transiently observe a torn/half-updated `Operation` object (e.g., an `Operation` with an energy-cost function from one adjustment and an action from another, if `JumpTable.set` performs a non-atomic array write during racing writers) or a completely different opcode implementation/cost function than the one intended for its transaction.

### Impact Explanation
An opcode's energy cost function and behavior are consensus-critical: SSTORE/MLOAD/SUICIDE energy accounting and VOTEWITNESS/SUICIDE semantics directly determine account balances, resource consumption, and whether a transaction succeeds or reverts. A race that causes one full node to observe the "adjusted" (higher-limit) operation variant while another observes the "default" variant for the same opcode in the same logical execution — or a genuinely corrupted `Operation` object mid-write — can make two otherwise-identical nodes execute the same transaction with different energy costs or different SUICIDE/VOTEWITNESS logic, producing divergent state roots (chain split / consensus failure), or an attacker-influenced/racy under-charge of energy leading to free/underpaid contract execution (unbacked resource consumption).

### Likelihood Explanation
Any externally submitted contract-triggering transaction (`TriggerSmartContract`/`CreateSmartContract`) reaches `VMActuator.execute`, which calls `prepareAndGetTable` and thus mutates the shared table on every single execution — this is not a rare edge case but the routine hot path for every smart-contract transaction. The race window is small but is hit on every transaction, and any environment that executes `VMActuator` instances concurrently (multiple worker threads processing pending/re-pushed transactions, or overlap between normal block-application and constant-call/JSON-RPC `eth_call` paths that still hit `getTable(false)`) will trigger it repeatedly under load, matching the CVSS AC:H (race is timing dependent but reachable without special privileges from any unprivileged contract caller).

### Recommendation
Do not mutate the shared consensus `JumpTable` per-call. Precompute all `VMConfig`-dependent variants once (already partially done via `ADJUSTED_MLOAD`/`OSAKA_VOTEWITNESS`/etc.) and make `getTable`/`prepareAndGetTable` select an immutable, already-correct table/`Operation` per invocation rather than calling `table.set(...)` on a globally shared instance; alternatively, make the table effectively immutable after initialization and store the config-dependent selection in `Program`/`VMActuator` local state (mirroring the `VMConfig.setLocalSnapshot`/`setGlobalSnapshot` isolation pattern already used to fix the analogous `VMConfig` global-pollution issue documented in `VMConfigIsolationTest`).

### Proof of Concept
Not independently reproduced against a live multi-threaded execution harness within the scope of this analysis — the reachability chain (`VMActuator.execute` → `OperationRegistry.prepareAndGetTable(false)` → `table.set(...)` on the shared `tableMap.get(LATEST_VERSION)` instance, immediately followed by `VM.play` reading the same table) is directly shown in the cited code, but confirming actual concurrent invocation of `VMActuator.execute` instances against the *same* shared table object (rather than serialized execution guarded by `Manager`'s `transactionLock`/`synchronized(this)` in `pushTransaction`/`generateBlock`) would require tracing every caller of `VMActuator`/`Runtime` across the framework module, which was not fully completed in this pass. **This is the main uncertainty**: java-tron's transaction application appears largely serialized through `Manager.pushTransaction` (`synchronized (transactionLock)` / `synchronized (this)`) and single-threaded block generation, which would substantially reduce or eliminate real-world concurrent access to this table during consensus-critical block application. Whether any other concurrent caller (e.g., parallel constant-call/`eth_call` handling, or a multi-threaded pending-transaction pre-processing path) actually invokes `getTable(false)`/`prepareAndGetTable(false)` concurrently from more than one thread was not conclusively established with the available tools, so this finding should be validated with a full call-graph trace of `VMActuator` instantiation sites before treating it as confirmed-exploitable rather than a latent unsafe-sharing pattern.

  public static void adjustMemOperations(JumpTable table) {
    boolean adjusted = VMConfig.allowHigherLimitForMaxCpuTimeOfOneTx();
    table.set(adjusted ? ADJUSTED_MLOAD : DEFAULT_MLOAD);
    table.set(adjusted ? ADJUSTED_MSTORE : DEFAULT_MSTORE);
    table.set(adjusted ? ADJUSTED_MSTORE8 : DEFAULT_MSTORE8);
  }

  public static void adjustVoteWitness(JumpTable table) {
    if (VMConfig.allowTvmOsaka()) {
      table.set(OSAKA_VOTEWITNESS);
    } else if (VMConfig.allowEnergyAdjustment()) {
      table.set(ADJUSTED_VOTEWITNESS);
    } else {
      table.set(DEFAULT_VOTEWITNESS);
    }
  }

  public static void adjustSelfdestruct(JumpTable table) {
    if (VMConfig.allowTvmSelfdestructRestriction()) {
      table.set(RESTRICTED_SUICIDE);
    } else if (VMConfig.allowEnergyAdjustment()) {
      table.set(ADJUSTED_SUICIDE);
    } else {
      table.set(DEFAULT_SUICIDE);
    }
  }
