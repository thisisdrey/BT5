## Title
Unbounded per-call scan of `Transaction.referenceUpdates` in `UpdateReferences` causes quadratic-time DoS of the `RefService/UpdateReferences` RPC handler - (File: `internal/gitaly/storage/storagemgr/partition/transaction_manager.go`)

### Summary
The `RefService.UpdateReferences` RPC is a client-streamed, unbounded-size RPC: a caller can send an arbitrary number of `UpdateReferencesRequest` messages, each carrying an arbitrary number of reference updates, before closing the stream [1](#0-0) . Every incoming batch is forwarded into `Transaction.UpdateReferences`, whose body loops over the batch's references and, for every single reference, re-scans the *entire* accumulated `txn.referenceUpdates` slice built up from all previous calls in the same transaction [2](#0-1) . This is directly analogous to the Carapace `ProtectionPool.lockCapital()`/`_accruePremiumAndExpireProtections()` bug class: an attacker-controlled, unbounded collection is iterated in full on every unit of work, and the collection itself grows with attacker input.

### Finding Description
`Transaction.UpdateReferences` is called once per streamed `UpdateReferencesRequest` batch (and also once per reference-transaction hook invocation during ordinary pushes) [3](#0-2) . Inside, for every reference in the *current* batch, the code does:

```go
for _, updates := range txn.referenceUpdates {
    if txUpdate, ok := updates[reference]; ok {
        ...
    }
}
``` [4](#0-3) 

`txn.referenceUpdates` is a slice that gets one new entry appended at the end of every call [5](#0-4) , so its length grows linearly with the number of streamed batches the client has sent so far. Because the inner loop re-scans this whole slice for *every reference* in the new batch, the total work across a transaction with `N` streamed batches of `M` references each is `O(N² · M)`. Neither the RPC handler in `internal/gitaly/service/ref/update_references.go` nor `Transaction.UpdateReferences` enforces any cap on the number of streamed messages, the number of references per message, or the cumulative size of `txn.referenceUpdates` — the loop bound is entirely attacker-controlled, exactly like the unbounded `activeProtectionIndexes` array in the Sherlock report.

### Impact Explanation
An authenticated user with write access to a repository can send a single `UpdateReferences` stream consisting of many small batches (e.g., thousands of single-reference update messages) that reference names other clients don't otherwise conflict with, driving the quadratic blow-up purely through request shape. Because `TransactionManager` serializes transaction processing per partition, a handler stuck doing quadratic work also blocks progress of other transactions sharing that partition, turning a single client's oversized RPC into a broader denial-of-service for the partition, mirroring how the too-many-protections scenario rendered `ProtectionPool` unusable for all protection buyers.

### Likelihood Explanation
The RPC is reachable without any special privilege beyond normal repository write access, and no request-size or reference-count limit is visible in the traversed code path (`update_references.go`, `transaction_manager.go`). Any client capable of calling `UpdateReferences` (used directly, and indirectly during ordinary pushes via `receivePackReferenceUpdates`/reference-transaction-hook handling) can trigger the quadratic path deterministically, so likelihood is high for a motivated but otherwise unprivileged actor.

### Recommendation
Bound the total number of references (and/or streamed messages) processed by a single transaction/RPC call, and replace the linear re-scan of `txn.referenceUpdates` with an amortized-O(1) lookup structure (e.g., maintain a single running `map[git.ReferenceName]git.ReferenceUpdate` of "last known new OID per reference" instead of a growing slice of per-call maps that must be scanned in full each time).

### Proof of Concept
1. Open an `UpdateReferences` stream to a repository the attacker can write to.
2. Send `N` (e.g., 50,000) small `UpdateReferencesRequest` messages, each containing one (or a few) legitimate but distinct/no-op-safe reference updates, before closing the stream.
3. Observe that server-side CPU time in `Transaction.UpdateReferences` grows quadratically with `N` because each new message triggers a full scan of `txn.referenceUpdates`, which by then contains up to `N-1` prior entries — eventually stalling the RPC and, transitively, other transactions on the same partition.

func (txn *Transaction) UpdateReferences(ctx context.Context, updates git.ReferenceUpdates) error {
	u := git.ReferenceUpdates{}

	for reference, update := range updates {
		// Transactions should only stage references with valid names as otherwise Git would already
		// fail when they try to stage them against their snapshot. `update-ref` happily accepts references
		// outside of `refs` directory so such references could theoretically arrive here. We thus sanity
		// check that all references modified are within the refs directory.
		//
		// HEAD is a special case and refers to a default branch update.
		if !strings.HasPrefix(reference.String(), "refs/") && reference != "HEAD" {
			return InvalidReferenceFormatError{ReferenceName: reference}
		}

		oldOID := update.OldOID
		oldTarget := update.OldTarget

		if initialValue, ok := txn.initialReferenceValues[reference]; ok {
			if !initialValue.IsSymbolic {
				oldOID = git.ObjectID(initialValue.Target)
			} else {
				oldTarget = git.ReferenceName(initialValue.Target)
			}
		}

		if oldOID == update.NewOID && oldTarget == update.NewTarget {
			// This was a no-op.
			continue
		}

		for _, updates := range txn.referenceUpdates {
			if txUpdate, ok := updates[reference]; ok {
				if txUpdate.NewOID != "" {
					oldOID = txUpdate.NewOID
				}

				if txUpdate.NewTarget != "" {
					oldTarget = txUpdate.NewTarget
				}
			}
		}

		u[reference] = git.ReferenceUpdate{
			OldOID:    oldOID,
			NewOID:    update.NewOID,
			OldTarget: oldTarget,
			NewTarget: update.NewTarget,
		}
	}
