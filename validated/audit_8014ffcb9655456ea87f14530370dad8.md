### Title
Unbounded length field causes out-of-bounds slice panic in ARM ELF attribute parsing - (File: src/cmd/link/internal/loadelf/ldelf.go)

### Summary
`parseArmAttributes` in `cmd/link/internal/loadelf` parses the `.ARM.attributes` section of an ELF relocatable object file supplied to the Go linker, using attacker-controlled length fields to slice byte buffers without validating that those lengths fit within the remaining data. A malicious/malformed `.o`/`.syso` object file (e.g. bundled in a module or produced by a build step and later consumed by `go build`/`go link`) can supply a `sectionlength`, `subsectionsize`, or other length value that is smaller than the already-consumed header size, causing a Go runtime slice-bounds panic and crashing the linker. This is the closest Go analog to the GDAL netCDF attribute-parsing overflow: an unvalidated size field taken directly from untrusted attribute/metadata is used to index into a buffer.

### Finding Description
Attacker-controlled input: an ELF relocatable object file (`.o`) targeted for `arm` with an `SHT_ARM_ATTRIBUTES` section, consumed by `cmd/link/internal/loadelf.Load` (called from `cmd/link` when linking object files, including cgo-generated `.o` files or `.syso` archives bundled in module source). Entry point: `Load()` reads the ELF section table and, for ARM attribute sections, invokes `parseArmAttributes(e, sect.base)` [1](#0-0) .

Inside `parseArmAttributes`, the 32-bit `sectionlength` is read directly from attacker data and used unchecked to slice the buffer: [2](#0-1) 
If `sectionlength < 4` or `sectionlength` exceeds `len(data)`, `data[4:sectionlength]` and `data[sectionlength:]` panic with "slice bounds out of range". The same unchecked pattern repeats for the nested subsection parsing: [3](#0-2) 
where `subsectionsize` (also attacker-controlled) is used to slice `sectiondata` without a bounds check, and the `elfAttributeList.uleb128`/`string` helpers advance through the buffer similarly without checking `size`/`nul` against `len(a.data)` bounds in all cases [4](#0-3) . No check validates that `sectionlength`/`subsectionsize` are ≥ the header bytes already consumed or ≤ remaining buffer length before slicing — the failed check is the absence of `sectionlength >= 4 && sectionlength <= len(data)` (and analogous checks for `subsectionsize`).

### Impact Explanation
The sink is a Go runtime-enforced panic (index/slice-bounds-out-of-range) rather than actual memory corruption, since Go bounds-checks slices; there is no equivalent stack buffer overflow / memory corruption possible in this managed-language analog. The concrete effect is a crash (denial of service) of the `go build`/`go link` process when linking an untrusted ARM object file. This does not achieve code execution or data disclosure, so per Go's security-bug classification it would be a PUBLIC-track robustness/DoS bug (parser panic on malformed input) rather than an URGENT-track memory-safety vulnerability, since Go's own runtime prevents the out-of-bounds write/read that made the original GDAL bug memory-unsafe.

### Likelihood Explanation
The victim workflow is a normal `go build`/`go link` invocation targeting `GOARCH=arm` that links an object file containing a `.ARM.attributes` section — this occurs routinely with cgo output or when a module/vendor tree ships a precompiled `.syso`/`.o` file. An attacker who can supply such an object file (e.g., via a malicious dependency, cgo archive, or vendored binary blob) needs no special privileges beyond having their file consumed by a normal build; no host, credential, or TLS/server control is required, matching the required "ordinary/published input consumed by a normal workflow" threat model.

### Recommendation
Add explicit bounds checks before every length-based slice in `parseArmAttributes` and the `elfAttributeList` helpers: verify `len(data) >= 4` and `4 <= sectionlength <= len(data)` before computing `sectiondata := data[4:sectionlength]`; verify `sz+4 <= len(sectiondata)` and `sz+4 <= subsectionsize <= len(sectiondata)` before slicing `subsectiondata`; and have `uleb128()`/`string()` return an error (`io.ErrUnexpectedEOF`) instead of proceeding when `binary.Uvarint` fails (`size <= 0`) or `nul < 0`, propagating failure up through `elfAttributeList.err` consistently.

func parseArmAttributes(e binary.ByteOrder, data []byte) (found bool, ehdrFlags uint32, err error) {
	found = false
	if data[0] != 'A' {
		return false, 0, fmt.Errorf(".ARM.attributes has unexpected format %c\n", data[0])
	}
	data = data[1:]
	for len(data) != 0 {
		sectionlength := e.Uint32(data)
		sectiondata := data[4:sectionlength]
		data = data[sectionlength:]

		nulIndex := bytes.IndexByte(sectiondata, 0)
		if nulIndex < 0 {
			return false, 0, fmt.Errorf("corrupt .ARM.attributes (section name not NUL-terminated)\n")
		}
		name := string(sectiondata[:nulIndex])
		sectiondata = sectiondata[nulIndex+1:]

		if name != "aeabi" {
			continue
		}
		for len(sectiondata) != 0 {
			subsectiontag, sz := binary.Uvarint(sectiondata)
			subsectionsize := e.Uint32(sectiondata[sz:])
			subsectiondata := sectiondata[sz+4 : subsectionsize]
			sectiondata = sectiondata[subsectionsize:]

			if subsectiontag != TagFile {
				continue
			}
			attrList := elfAttributeList{data: subsectiondata}
			for !attrList.done() {
				attr := attrList.armAttr()
				if attr.tag == TagABIVFPArgs && attr.ival == 1 {
					found = true
					ehdrFlags = 0x5000402 // has entry point, Version5 EABI, hard-float ABI
				}
			}
			if attrList.err != nil {
				return false, 0, fmt.Errorf("could not parse .ARM.attributes\n")
			}
		}
	}
	return found, ehdrFlags, nil
}
