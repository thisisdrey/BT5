### Title
`Pool.liquidate` permanently bricks unhealthy positions whose debt is below `debtFloorInUsd / (1 - maxLiquidable)` — unliquidatable bad debt - ([File: contracts/Pool.sol])

### Summary
`Pool.liquidate` enforces two independent constraints on `amountToRepay_`: it cannot exceed `maxLiquidable * debtBalance` (line 567), and any nonzero remaining debt must be ≥ `debtFloorInUsd` (lines 571–579). When `maxLiquidable < 100%` and `debtFloorInUsd > 0`, these constraints are mutually unsatisfiable for any position with `debtBalance < debtFloorInUsd / (1 - maxLiquidable)`. Every liquidation attempt on such a position reverts — either with `AmountGreaterThanMaxLiquidable` or `RemainingDebtIsLowerThanTheFloor` — making the bad debt permanently unliquidatable. This mirrors the advisory's bug class: an unauthenticated, network-reachable path that produces a repeatable availability failure (hang/DoS of a core protocol function).

### Finding Description
The relevant logic in `liquidate`:

- Line 567: `if (amountToRepay_.wadDiv(_debtTokenBalance) > maxLiquidable) revert AmountGreaterThanMaxLiquidable();`
- Lines 571–579: if `debtFloorInUsd > 0`, then `0 < remainingDebt < debtFloorInUsd` reverts with `RemainingDebtIsLowerThanTheFloor`.

For a position with debt `D` and `maxLiquidable = m < 1e18`, the maximum repayable amount is `m·D`, leaving minimum remaining debt `D·(1 - m)`. If `D·(1 - m) < debtFloorInUsd` (i.e., `D < floor/(1-m)`), then:

- Any `amountToRepay_ ≤ m·D` leaves `remaining ∈ (0, floor)` → reverts.
- Any `amountToRepay_ > m·D` (including full repayment) → reverts at the cap check.

There is no escape valve: `liquidate` is the only function that seizes collateral against third-party debt, and `DepositToken.seize` is callable only by the Pool (`onlyIfCanSeize`, DepositToken.sol:99-102). The victim's collateral cannot be seized and the debt cannot be cleared by anyone.

An attacker constructs this state permissionlessly: deposit collateral, call `DebtToken.issue` to borrow an amount in `(debtFloorInUsd, floor/(1-m))`, then wait for interest accrual (`DebtToken.accrueInterest`) or ordinary collateral-price movement to push the position below healthy. Once unhealthy, no liquidator can ever act on it. The test suite itself confirms the floor mechanics (`test/Pool.test.ts:408-436`) but only exercises it with `maxLiquidable` at a setting where full repay is reachable.

### Impact Explanation
Protocol insolvency / liveness failure of the liquidation path. Positions in the gap range accumulate interest-bearing bad debt whose collateral is permanently unseizable: the account's collateral is effectively locked against the debt (locked via `unlockedBalanceOf` → `NotEnoughFreeBalance` on withdraw/transfer), yet liquidators are mathematically blocked from recovering it. The protocol must absorb the shortfall. This matches the accepted impact classes: permanent freezing of funds (the position's collateral) and protocol insolvency (unclearable bad debt), plus a repeatable DoS of `liquidate` — the availability impact of the CVE.

### Likelihood Explanation
Requires `debtFloorInUsd > 0` and `maxLiquidable < 1e18` in the deployed configuration. Both are governor-tuned parameters intended to be nonzero/sub-100% in normal operation (`updateDebtFloor`, `updateMaxLiquidable` exist precisely for this; the floor exists to keep liquidations profitable). The gap window is `floor/(1-m)` wide — e.g., floor = $1,000 and `maxLiquidable` = 50% bricks every position under $2,000 of debt, which is a large portion of small retail positions. Triggering requires no privileged role, no oracle manipulation, and no flash loan — only an ordinary borrow in the affected range that later becomes unhealthy through market movement or interest accrual.

**Caveat:** the deployed values of `maxLiquidable` and `debtFloorInUsd` are on-chain state not readable from the deployment JSON artifacts (they contain ABI/devdoc only). If `maxLiquidable` is set to exactly `1e18` on all deployed pools, the gap collapses and the finding does not apply. This must be verified against live state (or `Pool1.json`/`Pool2.json` init params) before reporting.

### Recommendation
Reorder/merge the two checks so the floor never conflicts with the cap: when `debtFloorInUsd > 0` and `amountToRepay_` would leave a sub-floor remainder, either (a) allow full repayment regardless of `maxLiquidable` (e.g., `if (_debtTokenBalance - amountToRepay_ < floor-equivalent) require amountToRepay_ == _debtTokenBalance`), or (b) enforce a minimum debt at issuance time in `DebtToken.issue` ≥ `floor/(1 - maxLiquidable)` so positions can never enter the dead zone. Option (a) is minimal and preserves the floor's intent.

### Proof of Concept
Hardhat fork/test sketch (extend `test/Pool.test.ts` debt-floor suite):

```ts
// given: pool with maxLiquidable = 50%, debtFloorInUsd = $3,000
await pool.updateMaxLiquidable(parseEther('0.5'));
await pool.updateDebtFloor(parseEther('3000'));

// attacker deposits MET and borrows msETH worth ~$4,000 (< 2*floor)
await msdMET.connect(alice).deposit(collateral, alice.address);
await msEthDebtToken.connect(alice).issue(msEthAmount /* ~$4,000 */, alice.address);

// when: collateral price drops -> position unhealthy, debt still < 2*floor
await masterOracle.updatePrice(met.address, newMetPrice);
expect((await pool.debtPositionOf(alice.address))._isHealthy).false;

// then: every liquidation reverts
const debt = await msEthDebtToken.balanceOf(alice.address);
// (a) full/partial repay above cap
await expect(pool.connect(liq).liquidate(msEth.address, alice.address, debt, msdMET.address))
  .revertedWithCustomError(pool, 'AmountGreaterThanMaxLiquidable');
// (b) any repay within cap leaves sub-floor remainder
await expect(pool.connect(liq).liquidate(msEth.address, alice.address, debt.div(2), msdMET.address))
  .revertedWithCustomError(pool, 'RemainingDebtIsLowerThanTheFloor');
// position is permanently unliquidatable; collateral unseizable
```
