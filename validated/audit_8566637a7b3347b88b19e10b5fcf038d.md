### Title
`RewardsDistributor` grants a full `INITIAL_INDEX` worth of rewards to any account whose `accountIndexOf` is still `0` when the global index equals `INITIAL_INDEX` - (File: contracts/RewardsDistributor.sol)

### Summary
The tank report's bug class is "a stored checkpoint (`start_s`/`start_g`) is set lower than the value actually used in the payout computation, so part of the same accrual can be claimed twice." `RewardsDistributor._calculateTokenDelta` contains the same class of error in reverse: when `accountIndexOf[token][account] == 0`, the account's starting index is only snapped to `INITIAL_INDEX` if the global index is *strictly greater* than `INITIAL_INDEX`. While the global index still equals `INITIAL_INDEX` (i.e., the same timestamp in which the reward token was registered via `_updateTokenSpeed`), the account index stays `0`, so `_deltaIndex = INITIAL_INDEX - 0 = 1e18` and the account accrues `balance * 1e18` reward units — equal to its entire token balance — despite having earned nothing. `updateBeforeMintOrBurn` is permissionless, so anyone can trigger this for themselves or for any existing holder.

### Finding Description [1](#0-0) 

```solidity
uint256 _accountIndex = accountIndexOf[token_][account_];

if (_accountIndex == 0 && _tokenIndex > INITIAL_INDEX) {
    _accountIndex = INITIAL_INDEX;
}

uint256 _deltaIndex = _tokenIndex - _accountIndex;
_tokensDelta = token_.balanceOf(account_).wadMul(_deltaIndex);
```

When a token is first added, `tokenStates[token_] = TokenState({index: INITIAL_INDEX, timestamp: block.timestamp})` [2](#0-1) . `_calculateTokenIndex` only moves the index forward when `_deltaTimestamps > 0`, so inside the same block the stored index remains `INITIAL_INDEX` [3](#0-2) . In that window the guard `_tokenIndex > INITIAL_INDEX` is false, `_accountIndex` remains `0`, and `_updateTokensAccruedOf` credits the account with `balance.wadMul(1e18) = balance` reward tokens [4](#0-3) . The attacker then calls `claimRewards(account, tokens)` and `_transferRewardIfEnoughTokens` pays out up to the full distributor balance [5](#0-4) .

Attack trace (all public, unprivileged):

1. Before (or in the same block as) `updateTokenSpeed`/`syncTokenSpeed` registers a DepositToken/DebtToken, the attacker holds `B` units of that token via `DepositToken.deposit` or `DebtToken.issue`.
2. In the same timestamp as registration, call `RewardsDistributor.updateBeforeMintOrBurn(token, attacker)` — permissionless [6](#0-5) . `tokensAccruedOf[attacker] += B`.
3. Call `claimRewards(attacker, [token])` (or batch with other accounts) and receive `min(B, distributorBalance)` of `rewardToken`.

### Impact Explanation
Theft of unclaimed yield: the attacker is credited reward tokens equal to their entire DepositToken/DebtToken balance without any time-weighted accrual, and can withdraw up to the entire `rewardToken` balance of the distributor, draining rewards meant for all users.

### Likelihood Explanation
Requires an account holding a nonzero balance while `tokenStates[token].index == INITIAL_INDEX`, which only holds within the registration timestamp (or whenever accrual has never advanced the index, e.g., zero-supply periods followed by a deposit before the index moves). It is exploitable by front-running/back-running the speed-setting transaction, and `syncTokenSpeed` is keeper-callable rather than governor-only, widening the observable window [7](#0-6) . No modifier, reentrancy guard outcome, or health check prevents it; the only mitigation is that the window is one timestamp wide.

### Recommendation
Treat `accountIndexOf == 0` as `INITIAL_INDEX` unconditionally (`if (_accountIndex == 0) _accountIndex = INITIAL_INDEX;`), or use a sentinel/initialized flag so a never-initialized account can never have a delta computed against index `0`. As defense in depth, initialize `accountIndexOf` to `INITIAL_INDEX` when an account first interacts after token registration.

### Proof of Concept
Hardhat-style reproduction against a fork where `RewardsDistributor` is deployed and a reward `token` has not yet been assigned a speed:

```ts
// attacker already holds `amount` of depositToken (e.g. msdVaUSDC)
await depositToken.deposit(amount, attacker.address); // prior block

// same block as governor/keeper sets the speed (index == INITIAL_INDEX, timestamp = now)
await rewardDistributor.updateTokenSpeed(depositToken.address, speed); // or syncTokenSpeed by keeper

// permissionless: credit attacker `amount` reward units
await rewardDistributor.updateBeforeMintOrBurn(depositToken.address, attacker.address);
expect(await rewardDistributor.tokensAccruedOf(attacker.address)).to.eq(amount); // bug: free accrual

// drain reward token balance up to `amount`
await rewardDistributor['claimRewards(address,address[])'](attacker.address, [depositToken.address]);
expect(await rewardToken.balanceOf(attacker.address)).to.eq(min(amount, distributorBalance));
```

The invariant broken is reward-accrual conservation: `Σ tokensDelta` exceeds `Σ deltaTimestamps * speed` because an account with index `0` is paid for the `[0, INITIAL_INDEX)` span it never participated in.
