### Title
Gas-key nonce reseed on same-height DeleteKey+AddKey enables replay of a previously executed GasKeyNonce transaction, double-spending the newly deposited balance - ([File: runtime/runtime/src/access_keys.rs])

### Finding Description
`add_gas_key` (invoked from `action_add_key` when the added key is a gas key) unconditionally re-seeds every gas-key nonce slot to `initial_nonce_value(block_height) = (block_height - 1) * ACCESS_KEY_NONCE_RANGE_MULTIPLIER` (1e6), regardless of what nonce value that slot previously held: [1](#0-0) 
`delete_gas_key` (called from `action_delete_key` for a gas key) fully removes the nonce rows and burns any residual balance up to `GasKeyInfo::MAX_BALANCE_TO_BURN` (≤1 NEAR): [2](#0-1) 

`verify_nonce` accepts a `TransactionNonce::GasKeyNonce` as valid whenever `tx_nonce > current_nonce` (Monotonic mode) and `tx_nonce < current_block_height * 1e6` (upper bound): [3](#0-2) 

Exploit flow, all as an ordinary account owner (no privileged access needed):
1. At height H0 ≤ H, `AddKey(K, GasKeyFullAccess)` creates gas key K; nonce slot 0 seeded to `(H0-1)*1e6`.
2. `TransferToGasKey(K, D1)` funds K via `action_transfer_to_gas_key`, which simply does `balance += deposit`: [4](#0-3) 
3. At block height H, the attacker submits a `TransactionV1` signed by K with `nonce_index=0` and `nonce = M`, chosen deliberately close to the upper bound for height H (any `M` satisfying `(H-1)*1e6 < M < H*1e6` works). This spends part of K's balance and stores `M` as the new nonce for slot 0.
4. In the same block height H (a second transaction, since `DeleteAccount`/delete-final rules only constrain `DeleteAccount`, not `DeleteKey`—`Action::DeleteKey` has no "must be final" restriction, so `DeleteKey`+`AddKey`+`TransferToGasKey` can be combined or split across transactions freely at the account owner's discretion): [5](#0-4) 
   the owner deletes K (burns the ≤1 NEAR residual) and re-adds K with a fresh `TransferToGasKey(K, D2)` deposit. `add_gas_key` resets slot 0's nonce back to `(H-1)*1e6`, which is **less than M** by construction.
5. The already-broadcast, already-included transaction from step 3 (with signature over nonce `M`) is public chain data. Anyone (not just the original owner) can resubmit those exact signed bytes. Since the stored nonce for slot 0 is now `(H-1)*1e6 < M`, and the upper-bound check at replay time (`tx_nonce < replay_height*1e6`) trivially holds for any later height, `verify_nonce` re-accepts the stale transaction, re-executing its action (e.g., a `Transfer`) a second time — now debiting the newly-funded balance `D2` — without any new signature or authorization.

The root cause is that the nonce reseed formula `(block_height-1)*1e6` (intended to avoid tx-hash collisions on key reuse, referencing near/nearcore#3779) is not guaranteed to exceed nonces already consumed in the same block, because gas-key nonces are chosen independently by the signer within a `[prev_nonce, height*1e6)` window rather than being tied to the account's monotonic counter across recreation. No check compares the pre-delete nonce value to the reseed value, and no mechanism invalidates historically-broadcast gas-key transactions on key deletion beyond removing/re-seeding the nonce row.

### Impact Explanation
This is a value-conservation / double-spend bug: a transaction that already consumed part of a gas key's balance can be legitimately re-executed against a freshly deposited balance on the same account, purely by broadcasting previously-seen, publicly visible signed bytes. This maps to the "double-spend/replay" bounty category and directly causes loss of the account owner's gas-key funds (the replayed action executes again, e.g. re-sending a `Transfer`, re-calling a contract method, etc., using funds the owner believed were freshly and singularly authorized).

### Likelihood Explanation
The attacker only needs to be the account owner (or anyone who observed/archived a previously included gas-key transaction) and standard RPC access to submit two ordinary transactions at the same block height plus rebroadcast previously seen tx bytes — no validator/node privilege, no key compromise. The precondition (choosing `M` within `((H-1)*1e6, H*1e6)`) is trivially satisfiable since it is exactly the standard valid-nonce range for any transaction executed at height H; an attacker signing the "spend" transaction to be included at height H would naturally pick such a nonce. The only timing constraint is that the spend tx and the delete/re-add tx land in the same block height H, which is achievable by controlling submission order/timing on a single shard. This is repeatable for every gas key the attacker controls.

### Recommendation
When recreating an access key (in particular a gas key, or any key) via `add_gas_key`/`add_regular_key`, the new nonce seed must never be lower than the highest nonce previously used for that (account, public_key, nonce_index) tuple — persist a monotonically increasing per-(account, public_key) "epoch" or track the last-used nonce independent of key deletion (e.g., seed with `max(initial_nonce_value(block_height), last_known_nonce + 1)`), or alternatively make the public key itself non-reusable within the same "epoch" until enough blocks have passed that all previously valid nonces for it are guaranteed expired via the upper-bound check.

### Proof of Concept
Unit test outline (extending `runtime/runtime/src/access_keys.rs` gas-key tests, similar to `test_delete_gas_key_burns_balance`/`test_apply_gas_key_transaction`):
1. At height H0, add gas key K with `num_nonces=1`, fund with `D1` via `action_transfer_to_gas_key`.
2. Build and sign (but don't yet mark consumed) a `TransactionV1` `spend_tx` from K with `nonce_index=0`, `nonce=M` where `(H-1)*1e6 < M < H*1e6` for the target height H, action `Transfer{deposit: X}` with `X < D1`.
3. Apply `spend_tx` at height H — assert gas key balance becomes `D1 - gas_cost - X_related_cost` and nonce slot 0 == `M`.
4. At the same height H, apply `DeleteKey(K)` then `AddKey(K, GasKeyFullAccess)` + `TransferToGasKey(K, D2)` — assert nonce slot 0 resets to `(H-1)*1e6` and balance becomes `D2`.
5. Re-apply the exact same `spend_tx` bytes (same signature) at height H (or a later height H' with no intervening nonce_index=0 tx) via `verify_and_charge_gas_key_tx_ephemeral`/`validate_verify_and_charge_transaction` — assert it returns `TxVerdict::Success` (not `InvalidNonce`), and that the resulting `GasKeyInfo.balance` equals `D2 - gas_cost - X` a second time (i.e., `balance_after_double_spend`), rather than remaining at `D2` (`balance_after_single_spend` expectation the invariant requires). The test should fail this assertion, demonstrating the double-spend.

pub(crate) fn action_transfer_to_gas_key(
    state_update: &mut TrieUpdate,
    result: &mut ActionResult,
    account_id: &AccountId,
    action: &TransferToGasKeyAction,
) -> Result<(), RuntimeError> {
    let Some(mut access_key) = get_access_key(state_update, account_id, &action.public_key)? else {
        result.result = Err(ActionErrorKind::GasKeyDoesNotExist {
            account_id: account_id.clone(),
            public_key: Box::new(action.public_key.clone()),
        }
        .into());
        return Ok(());
    };
    let Some(gas_key_info) = access_key.gas_key_info_mut() else {
        // Key exists but is not a gas key
        result.result = Err(ActionErrorKind::GasKeyDoesNotExist {
            account_id: account_id.clone(),
            public_key: Box::new(action.public_key.clone()),
        }
        .into());
        return Ok(());
    };

    gas_key_info.balance = gas_key_info.balance.checked_add(action.deposit).ok_or_else(|| {
        RuntimeError::StorageError(StorageError::StorageInconsistentState(
            "gas key balance integer overflow".to_string(),
        ))
    })?;
    set_access_key(state_update, account_id.clone(), action.public_key.clone(), &access_key);
    Ok(())
}

fn verify_nonce(

    current_nonce: Nonce,
    block_height: Option<BlockHeight>,
    nonce_mode: NonceMode,
) -> Result<(), InvalidTxError> {
    match nonce_mode {
        NonceMode::Monotonic => {
            if tx_nonce <= current_nonce {
                return Err(InvalidTxError::InvalidNonce { tx_nonce, ak_nonce: current_nonce });
            }
        }
        NonceMode::Strict => {
            if !current_nonce.checked_add(1).is_some_and(|expected| tx_nonce == expected) {
