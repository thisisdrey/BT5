Audit Report

## Title
`process_delivery_receipt` pays relayer rewards without checking the Ethereum-side `success` flag, allowing reward payout for failed message execution - (File: `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs`)

## Summary
`DeliveryReceipt::success`, decoded from the Ethereum `InboundMessageDispatched(uint64 nonce, bytes32 topic, bool success, bytes32 reward_address)` event in `bridges/snowbridge/primitives/outbound-queue/src/v2/delivery_receipt.rs`, is never consulted in `process_delivery_receipt`. The function pays the full relayer reward whenever `order.fee > 0`, regardless of whether the Ethereum-side execution actually succeeded.

## Finding Description
`submit_delivery_receipt` verifies the Ethereum event proof via `T::Verifier::verify`, decodes it into a `DeliveryReceipt` (which includes `success: bool`), and forwards it to `process_delivery_receipt`, as shown in `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs` lines 298-317. `process_delivery_receipt` (lines 445-480) only validates the gateway address (`T::GatewayAddress::get() == receipt.gateway`) and looks up the `PendingOrder` by `receipt.nonce`; it then pays `T::RewardPayment::register_reward` unconditionally whenever `order.fee > 0`. The `receipt.success` field, populated directly from the decoded Solidity event in `DeliveryReceipt::try_from` (`bridges/snowbridge/primitives/outbound-queue/src/v2/delivery_receipt.rs` lines 35-51), is read into the struct but never checked anywhere in the pallet — confirmed by grep returning zero matches for "success" in `bridges/snowbridge/pallets/outbound-queue-v2/`. The reward-payout gate is thus keyed purely on `order.fee > 0`, a value fixed at message submission time, rather than on the actual outcome of dispatch on Ethereum, so the check degenerates to "always pay if fee was attached," irrespective of delivery outcome.

## Impact Explanation
Any relayer who submits a real, cryptographically valid delivery-receipt proof for a message whose Ethereum-side execution reverted (`success = false`) still receives the full `order.fee` reward via `register_reward`, because payout is unconditional on `receipt.success`. This drains relayer reward funds for messages that never completed successfully on Ethereum, constituting an unbacked/duplicate-style payout where the protocol disburses value for work not genuinely performed, aligning with the impact-gate categories "theft or unbacked mint or unlock" and "duplicate settlement or payout."

## Likelihood Explanation
No privileged actor or malicious behavior is required. `submit_delivery_receipt` is a plain signed extrinsic open to any relayer; the only requirement is a legitimate Ethereum receipt proof for an `InboundMessageDispatched` event with `success = false`, which naturally occurs on gas misestimation or command reverts on the destination chain. A normal relayer submitting a receipt for a legitimately failed delivery triggers the erroneous payout under standard usage, with no special conditions.

## Recommendation
Gate `T::RewardPayment::register_reward` on `receipt.success == true`. For `receipt.success == false`, withhold or apply a distinct compensation path, while still resolving `PendingOrders::<T>::remove(nonce)` (or implementing retry/requeue logic) to avoid stale state, and emit a distinguishing event (e.g., `MessageDeliveryFailed`) so failed deliveries are observable and reconciled on-chain.

## Proof of Concept
1. `do_process_message` commits a message and creates `PendingOrder { nonce, fee: 1_000_000, .. }` (`bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs` lines 426-436).
2. On Ethereum, message execution reverts; the Gateway still emits `InboundMessageDispatched(nonce, topic, success=false, reward_address)`.
3. A relayer builds a valid `EventProof` for this log (following the existing proof-construction pattern in `bridges/snowbridge/pallets/outbound-queue-v2/src/test.rs`) with `success` encoded as `false`, and calls `submit_delivery_receipt`.
4. `T::Verifier::verify` succeeds and `DeliveryReceipt::try_from` decodes `success = false` correctly, but `process_delivery_receipt` still calls `T::RewardPayment::register_reward(&reward_account, .., order.fee)` since it only checks `order.fee > 0`.
5. `submit_delivery_receipt` returns `Ok(())`, `Event::MessageDelivered` fires, and the relayer collects `order.fee` despite the failed Ethereum-side execution — demonstrating the missing `receipt.success` check. [1](#0-0) [2](#0-1) [3](#0-2)

		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}

sol! {
	event InboundMessageDispatched(uint64 indexed nonce, bytes32 topic, bool success, bytes32 reward_address);
}

/// Delivery receipt
#[derive(Clone, Debug)]
pub struct DeliveryReceipt {
	/// The address of the outbound queue on Ethereum that emitted this message as an event log
	pub gateway: H160,
	/// The nonce of the dispatched message
	pub nonce: u64,
	/// Message topic
	pub topic: H256,
	/// Delivery status
	pub success: bool,
	/// The reward address
	pub reward_address: [u8; 32],
}

#[derive(Copy, Clone, Encode, Decode, Eq, PartialEq, Debug, TypeInfo)]
pub enum DeliveryReceiptDecodeError {
	DecodeLogFailed,
	DecodeAccountFailed,
}

impl TryFrom<&Log> for DeliveryReceipt {
	type Error = DeliveryReceiptDecodeError;

	fn try_from(log: &Log) -> Result<Self, Self::Error> {
		let topics: Vec<B256> = log.topics.iter().map(|x| B256::from_slice(x.as_ref())).collect();

		let event = InboundMessageDispatched::decode_raw_log_validate(topics, &log.data)
			.map_err(|_| DeliveryReceiptDecodeError::DecodeLogFailed)?;

		Ok(Self {
			gateway: log.address,
			nonce: event.nonce,
			topic: H256::from_slice(event.topic.as_ref()),
			success: event.success,
			reward_address: event.reward_address.0,
		})
	}
