### Title
Silent `long` overflow in resource-usage/weight accounting produces corrupted bandwidth/energy accounting - (File: `chainbase/src/main/java/org/tron/core/db/ResourceProcessor.java`, `actuator/src/main/java/org/tron/core/vm/repository/RepositoryImpl.java`)

### Summary
The reported Sablier bug is a classic "attacker-controlled multiplicand overflows a fixed-width integer used in balance/debt accounting" pattern. java-tron's own resource-accounting math (`increase()`, `getUsage()`, `calculateGlobalEnergyLimit()`/`calculateGlobalLimitV2()`) performs the same class of multiplication (`usage * precision`, `frozeBalance * totalLimit`, etc.) using primitive `long` values, and the engineers have already added a `BigInteger`-based "hardened" alternative path guarded by the `allowHardenResourceCalculation` proposal flag. Because this flag defaults to off (like every other `allow*` proposal flag, activated only by committee vote per `actuator/src/main/java/org/tron/core/utils/ProposalUtil.java`), the *default*, currently-active production code still executes the vulnerable unmitigated `long` multiplication path.

### Finding Description
`ResourceProcessor.increase()` [1](#0-0)  and `getUsage()` [2](#0-1)  compute average bandwidth/energy usage by multiplying a `usage`/`lastUsage` value by `precision` (1,000,000) or `windowSize`, using plain `long` arithmetic when `hardenCalculation()` is false. `RepositoryImpl.calculateGlobalEnergyLimit()` similarly divides by weight after a `long` multiplication in the non-hardened branch [3](#0-2) , and `ResourceProcessor.getNewWindowSize()` sums `lastUsage*lastWindowSize + usage*windowSize` in plain `long` [4](#0-3) . All of these mirror `SablierFlow._ongoingDebtOf()`'s `elapsedTime * ratePerSecond` pattern: a multiplication of two attacker-influenceable quantities stored in a fixed-width integer.

The codebase's own hardened tests demonstrate the exploitability of the un-hardened path explicitly: `testIncreaseOverflowSilentWithoutHardening()` shows that with `allowHardenResourceCalculation` off, an overflow is silently produced with no exception [5](#0-4) , and `testGetUsageCorrectAcrossOverflowBoundary()` proves the non-hardened result is wrong (`assertNotEquals`) [6](#0-5) . Unlike the Solidity bug, which *reverts* the transaction (a DoS), the java-tron default path *silently wraps*, producing an incorrect (potentially negative or drastically wrong) usage/weight value that is then persisted to the `AccountCapsule` and used for resource-limit checks (`AccountResourceInsufficientException`) and billing — i.e., a corrupted-accounting analog rather than a pure freeze, but reachable the same way: through ordinary account resource operations (freeze/delegate/undelegate/vote) available to any unprivileged transaction sender.

The proposal flag itself is gated exactly like every other hard-fork flag in `VMConfig.Snapshot`/`ProposalUtil`, defaulting to inactive until committee-approved [7](#0-6) .

### Impact Explanation
If triggered on the default (non-hardened) path, this can corrupt an account's stored bandwidth/energy usage or the network-wide `totalNetWeight`/`totalEnergyWeight`, leading to either (a) permanently wrong resource-limit accounting for an account (denial of expected free bandwidth/energy, or conversely unlimited free resource — a form of unbacked resource grant), or (b) corruption of global weight totals affecting every account's global energy/bandwidth limit computation. This is a Medium-severity accounting-integrity issue, not an outright fund-freeze like the Sablier report, since the values involved (`usage`, `windowSize`, `precision`) are much more bounded in TRON's design (`usage` is capped by resource limits, `precision` is a constant 1,000,000) than Sablier's fully attacker-controlled `ratePerSecond` (up to `type(uint128).max`). Reaching an actual overflow (`usage * 1_000_000 > Long.MAX_VALUE`, i.e., `usage > ~9.2e12`) requires usage values far beyond realistic network bandwidth/energy limits, and `calculateGlobalEnergyLimit`'s `frozeBalance * totalLimit` would need economically infeasible frozen TRX amounts. This significantly reduces likelihood of "cheap, small-transaction" exploitation compared to the Sablier PoC, which trivially sets `ratePerSecond = type(uint128).max` in a single call.

### Likelihood Explanation
Low-to-Medium. The overflow-prone code path exists and is reachable by any account through freeze/unfreeze/delegate/vote-reward flows, but exploiting it to actually overflow a `long` (threshold ~9.2 × 10^12 after scaling by `precision`) requires either resource-usage or frozen-balance magnitudes that are not attacker-cheap to produce (they are bounded by real TRX economics, chain-wide resource limits, and existing validation), unlike Sablier's single-parameter, single-transaction, small-deposit trigger. Additionally, the fix already exists in-repo (hardened `BigInteger` path) but is inactive by default pending a committee-approved hard fork.

### Recommendation
Activate `allowHardenResourceCalculation` (or make the `BigInteger`-safe arithmetic unconditional rather than proposal-gated) so the default production path always uses overflow-checked arithmetic in `ResourceProcessor.increase()/getUsage()/getNewWindowSize()` and `RepositoryImpl.calculateGlobalEnergyLimit()/calculateGlobalLimitV2()`, matching the recommendation in the report to always use a wider/safe integer type through the full calculation chain before any final truncation, and add explicit bounds validation on `usage`/`windowSize`/`frozeBalance` inputs at the actuator level rather than relying solely on downstream arithmetic hardening.

### Proof of Concept
Not independently reproduced against a live node; based on static analysis, `framework/src/test/java/org/tron/core/vm/repository/RepositoryImplHardenTest.java` (`testIncreaseOverflowSilentWithoutHardening`, `testGetUsageCorrectAcrossOverflowBoundary`) and `framework/src/test/java/org/tron/core/db/CalculateGlobalLimitHardenTest.java` (`testGlobalEnergyLimitOverflowDetectedWithHardening`) already contain in-repo tests demonstrating both the silent-overflow behavior on the default (non-hardened) path and the `ArithmeticException` behavior on the hardened path, confirming the vulnerable arithmetic exists and is only mitigated behind an inactive feature flag.
