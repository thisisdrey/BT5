### Title
Unbounded, Unannounced Validator (Witness) Commission Rate Changes via `UpdateBrokerageContract` - (File: `actuator/src/main/java/org/tron/core/actuator/UpdateBrokerageActuator.java`)

### Summary
Any Super Representative (witness) can broadcast a signed `UpdateBrokerageContract` transaction to change their own reward-sharing "brokerage" (commission) rate at any time, by any amount within the allowed `[0,100]` range, with no rate-of-change cap, no advance-notice window meaningful to voters, and no on-chain event for voters/delegators to react to before the new rate is applied to their rewards.

### Finding Description
`UpdateBrokerageActuator.execute()` unconditionally stores whatever brokerage value the owner requests via `delegationStore.setBrokerage(ownerAddress, brokerage)` [1](#0-0) . The only bound checked in `validate()` is that the raw value is between `0` and `ActuatorConstant.ONE_HUNDRED` [2](#0-1) , meaning a witness can jump straight from, e.g., `0%` to `100%` commission in a single transaction with no throttling on frequency or step size.

The pending value is written to a sentinel "-1" cycle key via `setBrokerage(byte[] address, int brokerage)` → `setBrokerage(-1, address, brokerage)` [3](#0-2) . It is only materialized for a concrete reward cycle during the next `MaintenanceManager.doMaintenance()` run, which copies the pending value forward to `nextCycle` for every witness: `delegationStore.setBrokerage(nextCycle, witness.createDbKey(), delegationStore.getBrokerage(witness.createDbKey()))` [4](#0-3) . The maintenance interval defaults to only 6 hours (`maintenanceTimeInterval = 21600000`) [5](#0-4) , so the new rate becomes binding for reward computation almost immediately, well before delegators can realistically observe the change (there is no `ValidatorCommissionRateChanged`-equivalent event) and adjust their votes.

Once effective, `MortgageService.payReward()` applies the stored brokerage percentage directly against the full reward before crediting the remainder to voters: `brokerageAmount = (long) (brokerageRate * value); value -= brokerageAmount;` [6](#0-5) . There is no mechanism analogous to the report's recommended timelock, maximum-change-per-update limit, or delegator notification event.

### Impact Explanation
A witness can unilaterally and abruptly redirect a much larger share (up to 100%) of block/transaction-fee rewards to itself at the very next maintenance cycle, reducing voters' expected yield without warning. Because reward accrual and vote lifecycle are cycle-based (`beginCycle`/`endCycle` bookkeeping in `MortgageService`/`DelegationStore`), voters who voted expecting a given rate can have that expectation violated for reward periods they cannot retroactively opt out of, causing them measurable, unexpected financial loss. This matches the Medium classification of the source report (unexpected financial consequence to delegators from unrestrained commission changes), not a Critical/High fund-theft or chain-halt bug.

### Likelihood Explanation
Any account that has registered as a witness (a normal, permissionless on-chain action) can trigger this at will via a single signed `UpdateBrokerageContract` transaction, requiring no special privilege beyond being a witness and no coordination, cost, or governance approval — the same low-barrier profile as the original report's `setValidatorCommissionRate` issue.

### Recommendation
- Cap the maximum brokerage rate change allowed per update (e.g., a few percentage points per cycle) instead of allowing full-range jumps in `UpdateBrokerageActuator.validate()`.
- Introduce a delay/timelock (multiple maintenance cycles) between when a new brokerage value is submitted and when it becomes effective, giving voters time to withdraw/redirect votes.
- Emit an on-chain event when brokerage is updated so off-chain services and delegators can be notified promptly, analogous to the recommended `ValidatorCommissionRateChanged` event in the source report.

### Proof of Concept
1. Register/operate a witness account `W` with an active brokerage of `0%` (default is `DEFAULT_BROKERAGE = 20` if unset [7](#0-6) ; assume it has been previously set to `0` for illustration).
2. Voters vote for `W` expecting to receive ~100% of `W`'s share of rewards net of a low commission.
3. `W` broadcasts a signed `UpdateBrokerageContract{owner_address: W, brokerage: 100}` transaction via `/wallet/updateBrokerage` (`UpdateBrokerageServlet` → `UpdateBrokerageActuator`) [8](#0-7) . `validate()` only checks `0 ≤ brokerage ≤ 100`, so it succeeds instantly.
4. At the next maintenance event (≤6 hours later), `MaintenanceManager.doMaintenance()` forwards this new `100%` rate into the concrete `nextCycle` brokerage slot.
5. From that cycle onward, `MortgageService.payReward()` sends 100% of `W`'s reward share to the witness and 0% to voters, with no prior on-chain notice or opportunity for voters to withdraw votes to another witness before the change took effect for that cycle.

  private void payReward(byte[] witnessAddress, long value) {
    long cycle = dynamicPropertiesStore.getCurrentCycleNumber();
    int brokerage = delegationStore.getBrokerage(cycle, witnessAddress);
    double brokerageRate = (double) brokerage / 100;
    long brokerageAmount = (long) (brokerageRate * value);
    value -= brokerageAmount;
    delegationStore.addReward(cycle, witnessAddress, value);
    adjustAllowance(witnessAddress, brokerageAmount);
  }
