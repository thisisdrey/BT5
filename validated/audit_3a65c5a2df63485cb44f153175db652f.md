### Title
Missing Zero-Address Validation in `set_beneficiary_for_operator` Permanently Blocks Staker Fund Distribution - (File: `aptos-move/framework/aptos-framework/sources/staking_contract.move`)

---

### Summary

`staking_contract::set_beneficiary_for_operator` (and its mirror in `delegation_pool`) accepts an arbitrary `new_beneficiary: address` with no zero-address or reserved-address guard. Setting it to `@0x0` (`@vm_reserved`) causes every subsequent call to `distribute_internal` to abort when it tries to deposit the operator's commission to `@0x0`, permanently blocking the staker's APT distribution until the operator voluntarily corrects the value.

---

### Finding Description

`staking_contract::set_beneficiary_for_operator` stores `new_beneficiary` directly with no validation: [1](#0-0) 

Compare this with `vesting::set_beneficiary`, which explicitly calls `assert_account_is_registered_for_apt(new_beneficiary)` before storing the address: [2](#0-1) 

`delegation_pool::set_beneficiary_for_operator` has the identical omission: [3](#0-2) 

When `distribute_internal` runs, it resolves the operator's recipient via `beneficiary_for_operator(operator)` and immediately calls `aptos_account::deposit_coins` on the result: [4](#0-3) 

`aptos_account::deposit_coins` calls `create_account(to)` when the address has no account: [5](#0-4) 

`create_account` aborts for `@vm_reserved` (`@0x0`), `@aptos_framework`, and `@aptos_token`: [6](#0-5) 

The abort propagates up through `distribute_internal` → `distribute`, blocking the entire distribution loop — including the staker's own share — not just the operator's commission.

---

### Impact Explanation

An operator who sets `new_beneficiary = @0x0` causes every call to `distribute(staker, operator)` to abort. The staker's unlocked APT (principal + rewards) cannot be withdrawn. If the operator is malicious or loses their key, the staker's funds are durably frozen. If `@0x0` happens to have an account (e.g., after a future framework change), the commission is silently sent to an uncontrolled address, constituting permanent loss. This matches the "permanent freezing of staking balances" impact in the allowed scope.

---

### Likelihood Explanation

The operator is a separate party from the staker. A malicious operator can call `set_beneficiary_for_operator` with `@0x0` in a single unprivileged transaction at any time after the staking contract is created. No governance approval is required. The staker has no on-chain mechanism to override the operator's beneficiary setting.

---

### Recommendation

Add a reserved-address and zero-address guard in both `staking_contract::set_beneficiary_for_operator` and `delegation_pool::set_beneficiary_for_operator`, mirroring the pattern already used in `vesting::set_beneficiary`:

```move
assert!(
    !system_addresses::is_reserved_address(new_beneficiary),
    error::invalid_argument(EINVALID_BENEFICIARY_ADDRESS)
);
assert_account_is_registered_for_apt(new_beneficiary);
```

---

### Proof of Concept

1. Staker creates a staking contract with operator `OP`.
2. `OP` calls `staking_contract::set_beneficiary_for_operator(op_signer, @0x0)`.
   - No assertion fires; `BeneficiaryForOperator { beneficiary_for_operator: @0x0 }` is stored under `OP`.
3. Rewards accumulate; anyone calls `distribute(staker, OP)`.
4. `distribute_internal` enters the distribution loop; when `recipient == OP`, it resolves to `beneficiary_for_operator(OP) == @0x0`.
5. `aptos_account::deposit_coins(@0x0, coins)` is called.
6. `account::exists_at(@0x0)` returns `false`; `create_account(@0x0)` is called.
7. `create_account` aborts because `@0x0 == @vm_reserved`.
8. The entire `distribute` transaction reverts; the staker's unlocked APT remains trapped in the pool indefinitely. [1](#0-0) [7](#0-6) [5](#0-4)

    public entry fun set_beneficiary_for_operator(
        operator: &signer, new_beneficiary: address
    ) acquires BeneficiaryForOperator {
        assert!(
            features::operator_beneficiary_change_enabled(),
            std::error::invalid_state(EOPERATOR_BENEFICIARY_CHANGE_NOT_SUPPORTED)
        );
        // The beneficiay address of an operator is stored under the operator's address.
        // So, the operator does not need to be validated with respect to a staking pool.
        let operator_addr = signer::address_of(operator);
        let old_beneficiary = beneficiary_for_operator(operator_addr);
        if (exists<BeneficiaryForOperator>(operator_addr)) {
            borrow_global_mut<BeneficiaryForOperator>(operator_addr).beneficiary_for_operator =
                new_beneficiary;
        } else {
            move_to(
                operator,
                BeneficiaryForOperator { beneficiary_for_operator: new_beneficiary }
            );
        };

        emit(
            SetBeneficiaryForOperator {
                operator: operator_addr,
                old_beneficiary,
                new_beneficiary
            }
        );
    }
