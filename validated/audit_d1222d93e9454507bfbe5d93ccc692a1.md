### Title
Claimable rewards permanently frozen for users blacklisted on the reward token - (File: contracts/RewardsDistributor.sol)

### Summary
`RewardsDistributor.claimRewards` always transfers accrued `rewardToken` to the fixed `account_` that earned the rewards, with no mechanism to redirect the payout to an alternative address. If the reward token implements a blacklist (e.g., USDC/USDT-style tokens, or any future reward token with a blocklist), a user who gets blacklisted after accruing rewards can never claim them — every `claimRewards` call reverts at the `safeTransfer`, permanently freezing their unclaimed yield in the distributor contract. This is the same bug class as the Dinari `BuyOrderIssuer._cancelOrderAccounting` finding: a push-style payout to a fixed recipient that reverts when the recipient is token-blacklisted.

### Finding Description
The claim flow is:

```solidity
// contracts/RewardsDistributor.sol
function claimRewards(address[] memory accounts_, IERC20[] memory tokens_) public override nonReentrant {
    ...
    for (uint256 j; j < _accountsLength; j++) {
        address _account = accounts_[j];
        _transferRewardIfEnoughTokens(_account, tokensAccruedOf[_account]);
    }
}

function _transferRewardIfEnoughTokens(address account_, uint256 amount_) private {
    IERC20 _rewardToken = rewardToken;
    uint256 _balance = _rewardToken.balanceOf(address(this));
    if (amount_ > 0 && amount_ <= _balance) {
        tokensAccruedOf[account_] = 0;
        _rewardToken.safeTransfer(account_, amount_);
        emit RewardClaimed(account_, amount_);
    }
}
```

Key properties that create the issue:

- The recipient is hard-bound to `account_` — the function signature offers no `to_` parameter, unlike `DepositToken.withdraw(amount_, to_)` where the user freely chooses the destination. There is no escape hatch.
- `rewardToken` is an arbitrary `IERC20` set once in `initialize` (`contracts/RewardsDistributor.sol:103-109`). Nothing restricts it to non-blacklistable tokens; a distributor can be deployed pointing at USDC, USDT, or any centrally-administered ERC20.
- Because `tokensAccruedOf[account_] = 0` and the `safeTransfer` are in the same transaction, a revert preserves the accounting — the user never loses accrued rewards — but also can never move them. The funds remain in the distributor's balance indefinitely, only recoverable by governance `sweep`/migration, which requires privileged action and is not guaranteed.
- `claimRewards` is callable by anyone for any `account_`, so third parties (keeper bots, "claim for" helpers) also cannot route around the blacklist — the destination is always `account_`.

Contrast with the analogous withdrawal path in `Treasury.pull` (`contracts/Treasury.sol:66-72`) / `DepositToken._withdraw` (`contracts/DepositToken.sol:536-554`): there `to_` is caller-supplied, so a blacklisted user simply withdraws to a fresh address. No such alternative exists for reward claims.

### Impact Explanation
Permanent freezing of unclaimed yield. A user who accrued rewards and is later added to the reward token's blacklist has `tokensAccruedOf[account_]` locked forever; every claim attempt reverts inside `safeTransfer`. The rewards are protocol-owed funds that can never reach the user through any unprivileged path — matching the original finding's impact ("users blacklisted after requesting an order can't get tokens in the refund process"). The impact is bounded to affected (blacklisted) accounts and to the reward-claim surface, consistent with Medium severity.

### Likelihood Explanation
Likelihood depends on two conditions: (1) a `RewardsDistributor` instance whose `rewardToken` implements a blacklist — plausible, since nothing in the code constrains the token choice and deployments use fiat-backed stablecoins elsewhere in the system as collateral; (2) a reward earner getting blacklisted by the token issuer, which happens in practice for sanctioned addresses, compliance flags, and mistaken listings. Both conditions are external to the attacker, so likelihood is moderate. No privileged actor is needed for the failure to manifest — it is purely a consequence of the fixed-recipient push design.

### Recommendation
Change the claim to a pull-over model with a caller-selected destination, or add a separate function allowing the account owner to redirect claims:

```solidity
function claimRewardsTo(address account_, address to_) external nonReentrant {
    if (_msgSender() != account_) revert SenderIsNotAccount();
    _updateAccrued(account_);
    uint256 _amount = tokensAccruedOf[account_];
    if (_amount > 0 && _amount <= rewardToken.balanceOf(address(this))) {
        tokensAccruedOf[account_] = 0;
        rewardToken.safeTransfer(to_, _amount);
    }
}
```

Alternatively, keep accrued rewards in a withdrawal-mapping and let the user pull them to an arbitrary `to_` address, as the original report recommended ("transfer tokens to the address that wanted").

### Proof of Concept
Hardhat fork test (reward token assumed to be a blacklistable ERC20 such as a USDC-mock or real USDC on a fork where the distributor is funded):

```typescript
it("blacklisted user can never claim accrued rewards", async () => {
  const {distributor, rewardToken, alice} = await setup(); // rewardToken = USDC-like token with blacklist
  // alice earns rewards as a supplier/borrower
  await mine(1_000_000); // accrue via tokenSpeed
  const accrued = await distributor.claimable(alice.address);
  expect(accrued).to.be.gt(0);

  // token issuer blacklists alice AFTER accrual
  await rewardToken.connect(issuer).blacklist(alice.address);

  // every claim path reverts — recipient is fixed to alice
  await expect(distributor.claimRewards(alice.address)).to.be.reverted;
  await expect(distributor.connect(bob).claimRewards(alice.address)).to.be.reverted; // third-party claim also fails

  // accrued balance intact but permanently unclaimable
  expect(await distributor.claimable(alice.address)).to.eq(accrued);
  expect(await rewardToken.balanceOf(distributor.address)).to.be.gte(accrued);
  // no function on RewardsDistributor allows redirecting to another address → frozen
});
```

Note on residual uncertainty: the index did not expose the concrete `rewardToken` address configured in the deployment JSONs for existing `RewardsDistributor` instances, so whether a live deployment currently uses a blacklistable reward token could not be confirmed from in-scope code alone. The vulnerability is structural — the fixed-recipient `safeTransfer` with no alternative-destination path exists regardless — and materializes the moment any distributor's reward token has a blacklist, matching the validated Dinari analog.
