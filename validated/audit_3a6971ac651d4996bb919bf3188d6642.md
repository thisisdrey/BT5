### Title
Unbounded/unvalidated firewall conntrack timeout settings can crash or corrupt the TimerWheel - (File: `firewall.go`)

### Summary
Nebula's `NewFirewall` builds a `TimerWheel` directly from user-supplied `firewall.conntrack.tcp_timeout`, `udp_timeout`, and `default_timeout` config durations with no minimum, maximum, or zero-value validation, mirroring the nouns-builder analog where unbounded `duration`/`timeBuffer`/`delay` settings could brick governance/auctions. The wheel-length computation `wLen := int((max / min) + 2)` in `timeout.go` can overflow or misbehave for extreme or zero timeout ratios, and the code explicitly flags this as unresolved with a `//TODO: error on 0 duration` comment.

### Finding Description
`NewFirewallFromConfig` reads the three conntrack timeouts straight from config via `c.GetDuration(...)` with only type defaults, and passes them unchecked into `NewFirewall`: [1](#0-0) 

`NewFirewall` computes `tmin`/`tmax` from these three values and immediately builds a `TimerWheel` from them, with an explicit acknowledgment that zero-duration inputs are not handled: [2](#0-1) 

The wheel length is derived as `int((max / min) + 2)` in `NewTimerWheel`: [3](#0-2) 

If `min` is 0 (a zero-value duration from a bad/malicious config, since neither `GetDuration` nor `NewFirewall` reject `<= 0`), this division is either a divide-by-zero panic or, since these are `time.Duration` (int64) values, produces an extreme/overflowing `wLen`, which is then used to allocate a slice (`make([]*TimeoutList[T], wLen)`). Extremely large ratios between `min` and `max` (e.g., a very small `udp_timeout` combined with a very large `default_timeout`) can likewise generate an unreasonably large or overflowing `wLen`, causing excessive memory allocation or an integer overflow leading to a crash — directly analogous to the report's "large `duration`"/"large `delay`" bricking pattern, but here reachable purely through firewall config parsing rather than governance parameters. The CHANGELOG confirms this exact class of defect was previously exploitable ("Fix crash if you set unlucky values for the firewall timeout configuration options."), and the code still carries the unresolved `//TODO: error on 0 duration` marker, indicating the validation gap has not been fully closed at the type level. [4](#0-3) 

### Impact Explanation
A misconfigured or attacker-influenced (e.g., via a compromised/careless deployment or a maliciously distributed config) set of conntrack timeout values can crash the Nebula process at startup or on config reload (denial of service of the entire node's firewall/tunnel processing), or leave the firewall's connection-tracking state permanently degraded (e.g., a wheel sized incorrectly relative to actual traffic timing), which can cause packets to be dropped or incorrectly permitted after the timer wheel misbehaves. Because the firewall's conntrack timer wheel underlies all traffic admission decisions (`inConns`/`addConn` use `f.Conntrack.TimerWheel`), a corrupted or panicking wheel is a remote-crash / state-poisoning-adjacent failure mode reachable purely from configuration input validation gaps, matching the "no rational minimums/maximums" root cause identified in the external report. [5](#0-4) 

### Likelihood Explanation
Likelihood is low-to-moderate: it requires an operator (or an untrusted config-management pipeline) to set an unreasonable or zero-valued `firewall.conntrack.*_timeout`, similar to the original report's assumption that "founders" (here, operators) will normally set sane values. However, unlike the nouns-builder case, this path is hit on every node process start and every config hot-reload (`reloadFirewall`), so any deployment automation bug, template default (0s), or malicious config distributed to a node (e.g., via a compromised config management system or supply-chain vector) reliably triggers the defect without requiring cryptographic bypass. [6](#0-5) 

### Recommendation
Add explicit range validation in `NewFirewall`/`NewFirewallFromConfig` (and in `NewTimerWheel`) rejecting `tcpTimeout`, `UDPTimeout`, and `defaultTimeout` values that are `<= 0`, and enforcing a sane upper bound (e.g., reject values larger than some maximum such as days/weeks) so `max/min` cannot overflow or produce an unreasonably large wheel. Resolve the existing `//TODO: error on 0 duration` by returning an error from `NewFirewallFromConfig` (propagated to config load/reload) instead of silently constructing a wheel with unchecked min/max.

### Proof of Concept
1. Set `firewall.conntrack.udp_timeout: 0s` (or an extremely disparate value vs. `tcp_timeout`/`default_timeout`) in a node's `config.yml`.
2. Start (or SIGHUP-reload) Nebula; `NewFirewallFromConfig` reads this via `c.GetDuration("firewall.conntrack.udp_timeout", ...)` with no lower-bound check and passes it to `NewFirewall`. [7](#0-6) 
3. `NewFirewall` sets `tmin = 0`, then calls `NewTimerWheel(tmin, tmax)`, which computes `wLen := int((max / min) + 2)` — a divide-by-zero panic in Go for `time.Duration` division by zero, crashing the node's firewall initialization (or, for extreme non-zero min/max ratios, an oversized/overflowed slice allocation). [8](#0-7) 
4. Because this occurs both at initial firewall construction and at every `firewall`-config-change reload path, the node either fails to start or crashes/reload-fails on a subsequent SIGHUP, stalling all traffic processing for that node. [9](#0-8)

func (f *Firewall) addConn(fp firewall.Packet, incoming bool) {
	var timeout time.Duration
	c := &conn{}

	switch fp.Protocol {
	case firewall.ProtoTCP:
		timeout = f.TCPTimeout
	case firewall.ProtoUDP:
		timeout = f.UDPTimeout
	default:
		timeout = f.DefaultTimeout
	}

	conntrack := f.Conntrack
	conntrack.Lock()
	if _, ok := conntrack.Conns[fp]; !ok {
		conntrack.TimerWheel.Advance(time.Now())
		conntrack.TimerWheel.Add(fp, timeout)
	}

	// Record which rulesVersion allowed this connection, so we can retest after
	// firewall reload
	c.incoming = incoming
	c.rulesVersion = f.rulesVersion
	c.Expires = time.Now().Add(timeout)
	conntrack.Conns[fp] = c
	conntrack.Unlock()

func (f *Interface) reloadFirewall(c *config.C) {
	cs := f.pki.getCertState()
	curCert := cs.getCertificate(cert.Version2)
	if curCert == nil {
		curCert = cs.getCertificate(cert.Version1)
	}

	// The firewall builds its routableNetworks set from the certificate's UnsafeNetworks at construction.
	// Check to see if that set has changed, and if so, rebuild the firewall.
	certUnsafeChanged := curCert != nil && !slices.Equal(curCert.UnsafeNetworks(), f.firewall.unsafeNetworks)

	if !c.HasChanged("firewall") && !certUnsafeChanged {
		f.l.Debug("No firewall config change detected")
		return
	}

	fw, err := NewFirewallFromConfig(f.l, cs, c)
	if err != nil {
		f.l.Error("Error while creating firewall during reload", "error", err)
		return
	}
