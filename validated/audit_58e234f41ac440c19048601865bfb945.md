### Title
Bancor-curve exchange reserves can be driven to exactly zero, permanently freezing remaining pooled funds - (File: chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java)

### Summary
`ExchangeCapsule.transaction()` computes AMM swaps using a double-precision Bancor-style relay formula (`ExchangeProcessor`). Because this default (non-hardened) path performs no bounds check on the resulting balances, a legitimate sell order that drives one side of the pool reserve to exactly `0` permanently locks the entire pool: every subsequent trade, inject, and withdraw actuator explicitly rejects any exchange whose `firstTokenBalance == 0 || secondTokenBalance == 0`. This mirrors the reported Hyperdrive `applyCheckpoint` issue, where reserves reaching a "close-to-0" state make a core state-mutating path permanently revert, locking up pool/trader funds.

### Finding Description
`ExchangeCapsule.transaction()` [1](#0-0)  computes swap output via `Processor.exchange()`. In the default, non-hardened path it uses `ExchangeProcessor`, which relies on floating-point `Math.pow` for the constant-product-like Bancor relay curve [2](#0-1) . The resulting `newFirstTokenBalance`/`newSecondTokenBalance` are only checked for negativity when `hardenedCalc` is true; in the default path there is no bound at all on the resulting balances [3](#0-2) .

Because the relay curve is asymptotic (`1 - (1+x)^-2000` as `x -> ∞`), a sufficiently large `sellTokenQuant` pushes the double-precision `pow` result to exactly `1.0`, causing `exchangeFromSupply` to return a `buyTokenQuant` equal to the *entire remaining* `buyTokenBalance` — driving that reserve to exactly `0`, not merely close to `0`. Any single unprivileged account can trigger this by broadcasting an `ExchangeTransactionContract` (via `ExchangeTransactionActuator`) with a large enough `tokenQuant` for one side of a low-balance pool [4](#0-3) .

Once either token balance in the exchange equals `0`, all subsequent actuators unconditionally refuse to operate on the pool:
- `ExchangeTransactionActuator.doValidate` — `"Token balance in exchange is equal with 0,the exchange has been closed"` [5](#0-4) 
- `ExchangeInjectActuator.doValidate` — same check [6](#0-5) 
- `ExchangeWithdrawActuator.doValidate` — same check [7](#0-6) 

There is no other actuator path to recover the remaining non-zero-side balance, so any funds still held in the opposite token (`firstTokenBalance` or `secondTokenBalance` > 0) become permanently locked inside the exchange capsule. This is directly analogous to the reported Hyperdrive issue: an ordinary, unprivileged trade drives reserves to a boundary state (0 vs. "close to 0"), after which a core state-mutating code path (checkpoint application vs. exchange trade/withdraw) unconditionally rejects, permanently freezing pooled funds.

### Impact Explanation
Any account (creator or trader) that had TRX/TRC10 balance locked in the exchange pool loses permanent access to it once the opposite-side reserve hits `0` — the creator cannot even withdraw remaining funds via `ExchangeWithdrawActuator` because it performs the identical zero-balance rejection. This is a permanent freezing-of-funds condition triggerable by a single unprivileged transaction against an ordinary, unprivileged, already-created exchange pool.

### Likelihood Explanation
Reachability is straightforward: no permissions are required to call `ExchangeTransactionContract` against an existing exchange; the actor only needs to choose a `tokenQuant` large enough to push the floating-point-computed `buyTokenQuant` to exactly the remaining opposite balance. Low-liquidity pools (which are common, since anyone can create an exchange with an arbitrarily small `firstTokenBalance`/`secondTokenBalance` via `ExchangeCreateActuator`) are most exposed, since less precision "headroom" is needed for the double computation to saturate to the full remaining balance. Note: I could not fully confirm within the available time whether `allowHarden()`/`AllowHardenExchangeCalculation` (referenced in `AbstractExchangeActuator`, `DynamicPropertiesStore`, and `ProposalUtil`) is enabled by default on this chain configuration — if it is enabled by default (hardened math path, `SafeExchangeProcessor`, `BigDecimal`-based), the precision-saturation avenue is reduced, but the *lock-on-zero-balance* design flaw in the three actuators (`ExchangeTransactionActuator`, `ExchangeInjectActuator`, `ExchangeWithdrawActuator`) remains independent of which processor is used, since exact-zero balances are still reachable at the boundary of any trade that fully drains one side (e.g., the last unit of a token via `ExchangeWithdrawActuator` itself, or a sell that exactly matches remaining supply under `SafeExchangeProcessor`'s `BigDecimal` rounding).

### Recommendation
Do not treat a `0` balance in either exchange side as an unconditional "closed" state that blocks all operations. At minimum, allow the creator to withdraw any remaining balance from the still-nonzero side via `ExchangeWithdrawActuator` even when the other side is `0`, so no funds become irrecoverably stuck. Separately, review whether the non-hardened floating-point Bancor curve should be deprecated in favor of the `SafeExchangeProcessor`/`BigDecimal` path by default, and add belt-and-suspenders bounds checks (analogous to Hyperdrive's recommendation to avoid the "close-to-0 reserves" trap) so no single legitimate trade can single-handedly zero out a reserve side and lock the remainder.

### Proof of Concept
Conceptual PoC (mirrors the Hyperdrive PoC's "trade to boundary, then get locked out" structure):
1. Create a low-liquidity exchange pool via `ExchangeCreateActuator` (e.g., `firstTokenBalance = 100`, `secondTokenBalance = 1_000_000_000_000L`), so the Bancor relay curve computation is highly sensitive to floating-point saturation for a large sell quantity of the low-balance side's counterpart.
2. Broadcast an `ExchangeTransactionContract` (`ExchangeTransactionActuator`) selling a very large quantity of `secondTokenId`, sized so that `ExchangeProcessor.exchangeFromSupply`'s `Math.pow` result saturates to `1.0`, making `buyTokenQuant == firstTokenBalance` exactly, so `newFirstTokenBalance == 0`.
3. Attempt to withdraw the remaining `secondTokenBalance` via `ExchangeWithdrawActuator`, or continue trading via `ExchangeTransactionActuator`/`ExchangeInjectActuator`.
4. Observe `ContractValidateException("Token balance in exchange is equal with 0,the exchange has been closed")` on every subsequent call, permanently locking the remaining pooled `secondTokenBalance`.

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
  }

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
