# #Analog Found

### Title
Unauthenticated `RecvError` message allows source-spoofed remote tunnel teardown (state poisoning) - ([File: outside.go])

### Summary
The reported Connext bug is a signature/authorization-replay issue: a control message intended to authorize a single, bounded action lacks any mechanism to bind it to a single legitimate use, letting an untrusted party (the Gelato relayer) repeatedly trigger a privileged effect. The closest reachable Nebula analog, exploitable by an attacker who holds **no valid CA-signed certificate**, is the `header.RecvError` control message: it is processed entirely before any handshake/certificate/AEAD authentication and is validated only by comparing the packet's *source UDP address* to a cached remote address, not by any cryptographic binding to the peer's identity or to a specific, single-use handshake/session state.

### Finding Description
`readOutsidePackets` dispatches `header.RecvError` in the "Unencrypted packets" branch, before any `ConnectionState`, certificate, or AEAD check is performed: [1](#0-0) 

`handleRecvError` then authorizes the teardown purely by comparing the sender's UDP source address against the cached remote endpoint for the `HostInfo` referenced by the attacker-supplied `RemoteIndex`: [2](#0-1) 

There is no signature, no HMAC, no session-bound nonce, and no replay-window/one-time-use tracking on this message — the same missing-uniqueness class of flaw as the reported bug (a message with a coarse binding — “count of routers” / “source IP” — is treated as sufficient proof of legitimacy and can be repeatedly leveraged to trigger a privileged action, here `f.closeTunnel(hostinfo)` and `f.handshakeManager.DeleteHostInfo(hostinfo)`). An attacker capable of spoofing UDP source addresses (a standard capability for a network-path or off-path attacker against connectionless UDP, and explicitly acknowledged in-code via the log line `"Someone spoofing recv_errors?"`) can repeatedly send crafted `RecvError` packets with a guessed/observed `RemoteIndex` to tear down arbitrary victim tunnels without ever presenting a valid Nebula certificate.

### Impact Explanation
This allows unauthenticated, repeatable remote state poisoning/denial of service: an attacker with no certificate can force teardown of established tunnels between legitimate peers, causing service disruption and repeated re-handshake churn, analogous to the "griefing" impact acknowledged in the Connext report (no funds/keys compromised, but fairness/availability is undermined). It does not achieve authentication bypass or traffic decryption, only forced, repeatable disruption.

### Likelihood Explanation
Likelihood depends on the attacker's ability to (a) observe or guess a 32-bit `RemoteIndex` and the victim's real UDP endpoint, and (b) spoof a UDP source address matching the victim's cached remote — feasible for an on-path/network-adjacent attacker without any Nebula credentials. This is weaker than the original finding's guaranteed replay (no index/address guessing needed there), so likelihood here is lower and should be treated as **Low/Medium** pending further verification of index predictability and network exposure — I was not able to fully trace how unpredictable `RemoteIndex` values are (generated via `generateIndex`), which materially affects real-world exploitability and I could not verify this within the available searches.

### Recommendation
Bind `RecvError` acceptance to authenticated session state (e.g., require the message to be authenticated similarly to `CloseTunnel`'s AEAD-protected path, or require a matching, freshly-issued nonce/challenge) rather than relying solely on source-address comparison, closing the same "no single-use binding" gap identified in the original report.

### Proof of Concept
Conceptual (not verified end-to-end due to tool limitations): an attacker crafts a `header.RecvError` packet with `RemoteIndex` set to a victim tunnel's known/guessed local index and sends it from a spoofed UDP source matching the victim's `HostInfo.GetRemote()`; `handleRecvError` passes the address check and calls `closeTunnel`, tearing down the tunnel — repeatable indefinitely against any tunnel whose remote index/address the attacker can observe.

**Note on confidence:** Given the strict "no CA-signed certificate" constraint, most other replay-shaped candidates in this codebase (relay frame replay via `VerifyRelay`/`ConnectionState.window`, handshake retransmission via `CheckAndComplete`/`ErrAlreadySeen`) were already hardened and require analysis showing they are the *closest* remaining analog, not a certain vulnerability at the same severity as the original Connext finding. I was unable to fully verify real-world predictability of `RemoteIndex` values, which is necessary to firmly establish practical exploitability.

func (f *Interface) handleRecvError(addr netip.AddrPort, h *header.H) {
	if !f.acceptRecvErrorConfig.ShouldRecvError(addr) {
		f.l.Debug("Recv error received, ignoring",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
		return
	}

	if f.l.Enabled(context.Background(), slog.LevelDebug) {
		f.l.Debug("Recv error received",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
	}

	hostinfo := f.hostMap.QueryReverseIndex(h.RemoteIndex)
	if hostinfo == nil {
		f.l.Debug("Did not find remote index in main hostmap", "remoteIndex", h.RemoteIndex)
		return
	}

	hr := hostinfo.GetRemote()
	if hr.IsValid() && hr != addr {
		f.l.Info("Someone spoofing recv_errors?",
			"addr", addr,
			"hostinfoRemote", hr,
		)
		return
	}

	f.closeTunnel(hostinfo)
	// We also delete it from pending hostmap to allow for fast reconnect.
	f.handshakeManager.DeleteHostInfo(hostinfo)
}
