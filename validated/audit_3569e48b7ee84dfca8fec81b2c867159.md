### Title
Missing slippage control and deadline on Vesper pool deposit/withdraw in `VesperGateway` — ([File: contracts/VesperGateway.sol](https://github.com/Loderfordw/metronome-synth-public--011/blob/main/contracts/VesperGateway.sol))

### Summary
`VesperGateway.deposit` and `VesperGateway.withdraw` convert user funds to/from Vesper `vTokens` (yield-bearing vault shares whose mint/redeem rate is a live `pricePerShare`) with no `minAmountOut` parameter and no deadline check. This is the same bug class as the Blueberry ICHI vault issue: the user commits a fixed underlying amount (`amount_`) or a fixed share amount (`amount_`), but the quantity of the other side is entirely determined by the vault's exchange rate at execution time, which an unprivileged attacker can move via direct Vesper pool interactions (deposit/withdraw/donation of underlying to the pool) in surrounding transactions or while the user's transaction sits pending.

### Finding Description
In `deposit()` (contracts/VesperGateway.sol:44-65) the user transfers `amount_` of underlying, the gateway calls `vToken_.deposit(amount_)`, and forwards whatever shares come back into `DepositToken.deposit`, minting `msdToken` 1:1 by share count. There is no `minShares`/`minDeposited` argument. A Vesper `VPool`'s share count is `amount * PRECISION / pricePerShare`, and `pricePerShare` is derived from the pool's total underlying balance divided by share supply — so an attacker holding existing vToken shares can donate underlying to the pool (raising `pricePerShare`) right before the victim's transaction lands, causing the victim to mint materially fewer vTokens and hence fewer `msdToken`. The donated value is then recoverable by the attacker redeeming their (now more valuable) shares.

In `withdraw()` (contracts/VesperGateway.sol:73-93) the user specifies `amount_` of `msdToken` to burn; the gateway calls `vToken_.withdraw(_vTokenAmount)` and forwards whatever underlying comes out, with no `minUnderlying` check. An attacker can lower `pricePerShare` (e.g., by triggering pool losses/fees or sandwiching around pool report/strategy state changes that move `totalValue`) so the user redeems less underlying than expected.

There is also no deadline parameter, so a transaction delayed in the mempool executes against a stale, moved exchange rate with no way for the user to bound their execution price — exactly the "pending transaction + price drift" scenario in the reference report.

This is distinct from `SmartFarmingManager.leverage`/`flashRepay`, which do expose `depositAmountMin_`/`swapAmountOutMin_` slippage parameters (contracts/SmartFarmingManager.sol:98-144, 155-211); the gateway surface was simply never given equivalent bounds.

### Impact Explanation
Direct loss of user funds: the victim's collateral minted (`msdToken`) or underlying received is reduced below fair value, with the difference accruing to the attacker's vToken position. The attack requires only public calls to the Vesper pool and normal front-running/mempool ordering — no privileged role, oracle manipulation, or protocol internals.

### Likelihood Explanation
`deposit()` is `nonReentrant`-unprotected and callable by any user for any registered pool/vToken pair; `pricePerShare` of Vesper pools is manipulable by a same-block donation of the underlying directly to the pool contract before the user's tx and a redemption after it. Attack cost is bounded by share supply (attacker must hold or mint shares first, but can mint them in the same bundle). Pending-transaction drift additionally harms users with no attacker needed.

### Recommendation
Add a `minVTokenOut_`/`minUnderlyingOut_` parameter to `deposit()`/`withdraw()` and revert if the measured balance delta is below it; optionally add a `deadline_` check (`block.timestamp <= deadline_`). This mirrors the existing `LeverageSlippageTooHigh`/`FlashRepaySlippageTooHigh` pattern in `SmartFarmingManager`.

### Proof of Concept
Hardhat fork test (mainnet):
1. Deploy/fork at a block with a live `VesperGateway` and a registered `VPool` (e.g., vaUSDC) with a live `DepositToken`.
2. Victim approves underlying to gateway and submits `gateway.deposit(pool, vToken, 100e6)`.
3. In a bundle before the victim tx: attacker deposits into the same `VPool` to acquire shares, then `underlying.transfer(pool, X)` donating enough to raise `pricePerShare` significantly.
4. Victim tx executes: `vToken.deposit` mints shares at the inflated `pricePerShare` → victim receives materially fewer `msdToken`.
5. Attacker calls `vToken.withdraw(theirShares)` to reclaim underlying including the redistributed victim value; assert `attackerUnderlyingGain > donationCost - victimLoss` and victim `msdToken` minted < honest-path quote. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3)

    function withdraw(IPool pool_, IVPool vToken_, uint256 amount_) external override nonReentrant {
        if (!_poolRegistry.isPoolRegistered(address(pool_))) revert UnregisteredPool();

        address _msgSender = _msgSender();

        // 1. Get `msdTokens`
        IDepositToken _depositToken = pool_.depositTokenOf(vToken_);
        _depositToken.safeTransferFrom(_msgSender, address(this), amount_);

        // 2. Withdraw `vTokens` from `Synth`
        (uint256 _vTokenAmount, ) = _depositToken.withdraw(amount_, address(this));

        // 3. Withdraw `underlying` from `VPool`
        IERC20 _underlying = IERC20(vToken_.token());
        uint256 _balanceBefore = _underlying.balanceOf(address(this));
        vToken_.withdraw(_vTokenAmount);
        uint256 _underlyingAmount = _underlying.balanceOf(address(this)) - _balanceBefore;

        // 4. Transfer `underlying` to the `_msgSender()`
        _underlying.safeTransfer(_msgSender, _underlyingAmount);
    }
