## Title
Protocol fee bypass on `TokenDiff` swaps involving NEP-245/IMT-wrapped assets - ([File: contracts/defuse/core/src/intents/token_diff.rs])

### Summary
The reported bug is that `UniswapV3Swapper` binds its pool address to a fixed `poolFee` for every token pair, so the fee actually enforced by the underlying pool contract does not correspond to the fee/value that the code assumes, causing a mismatch between the intended and actual pool. The analogous defect in this repository is in `TokenDiff::token_fee()`, which decides whether a protocol fee is owed based on the *asset type and raw integer amount* rather than the *value being moved*. For `Nep245` (multi-token) and `Imt` (intent-mintable token) assets, any transfer with `unsigned_abs(delta) <= 1` is unconditionally exempted from the protocol fee, regardless of how much real economic value that single indivisible unit represents.

### Finding Description
`TokenDiff::execute_intent()` computes and collects the protocol fee for every negative delta (token being given up) using: [1](#0-0) 

The fee rate itself is determined by `TokenDiff::token_fee()`: [2](#0-1) 

This function returns `Pips::ZERO` (no fee) for `Nep171` (NFTs) unconditionally, and for `Nep245`/`Imt` whenever the traded `amount <= 1`. The intent behind this exemption is presumably to avoid charging fees on genuinely non-fungible or "1-of-1" style assets. However, `Nep245TokenId` and `ImtTokenId` are fully attacker-controlled identifiers — any account can act as an NEP-245 contract (see `Nep245TokenId::new(contract_id, mt_token_id)`), and the `mt_token_id` string, decimal convention, and "1 unit" granularity are entirely defined by that external/attacker contract: [3](#0-2) 

Because the protocol only inspects the raw integer `delta`/`amount`, and never any value/price oracle, an attacker can define (or already control) an NEP-245 (or IMT) token whose "1 unit" represents an arbitrarily large amount of underlying value (e.g., a token with 0 decimals mapped 1:1 to a valuable underlying NEP-141, or an IMT token minted by the attacker itself via `ImtMint`). By constructing every `TokenDiff` swap leg with `|delta| == 1` for that token, the attacker guarantees `token_fee()` always returns `Pips::ZERO`, fully bypassing the protocol fee that would otherwise be owed on the equivalent value in a normal (fungible, `Nep141`) swap.

This breaks the "fees owed versus fees collected" binding: the fee that *should* be owed (protocol_fee × economic value moved) is decoupled from the fee that is *actually* collected (always zero, because collection is gated on raw unit count rather than value), exactly analogous to how the Uniswap V3 report's fee/pool binding is decoupled from the actual token pair being swapped.

### Impact Explanation
Any user or solver can route value through the `TokenDiff` intent using an NEP-245/IMT-denominated leg with `|delta| == 1` to completely avoid the protocol fee (`engine.state.fee()`) that would normally be charged and deposited to `fee_collector()`: [4](#0-3) 

This is a fee-bypass finding — a value that should have accrued to the fee collector never does, at no cost to the attacker (aside from possibly needing to mint/control the token id, which is permissionless via `ImtMint` or by deploying/using any NEP-245-compliant contract). Repeated across trades, this results in ongoing loss of protocol revenue proportional to trade volume routed this way.

### Likelihood Explanation
Medium-to-High: any user can trivially mint an `Imt` token (permissionless `ImtMint` intent) or wrap value via nested NEP-245 (e.g., cross-Defuse `mt_transfer_call` composition observed throughout the NEP-245 tests) and structure a `TokenDiff` swap leg with `|delta| == 1` for that asset. No privileged role, relayer, or governance action is required — only knowledge of the fee-exemption threshold, which is public in the source code.

### Recommendation
Do not exempt fee calculation based solely on raw unit count for `Nep245`/`Imt` token types. Either:
1. Remove the `amount <= 1` fee exemption for `Nep245`/`Imt` entirely and treat them the same as `Nep141` for fee purposes, or
2. If the exemption is meant to protect genuinely non-fungible semantics, gate it on an explicit, verifiable "non-fungible" flag/metadata rather than an amount threshold that is trivially satisfiable regardless of underlying value.

### Proof of Concept
1. Attacker mints an `Imt` token via `ImtMint` (permissionless), or otherwise obtains/controls an `Nep245` token id, structured so that "1 unit" corresponds to significant value (e.g., pegged 1:1 against a valuable `Nep141` asset via nested deposits, as shown in the NEP-245 cross-Defuse wrapping tests).
2. Attacker (or a colluding counterparty) submits a `TokenDiff` intent swapping `-1` unit of the `Imt`/`Nep245` asset for a large amount of another (e.g. `Nep141`) token.
3. In `TokenDiff::execute_intent()`, since `delta.unsigned_abs() == 1` for the `Imt`/`Nep245` leg, `token_fee()` returns `Pips::ZERO`, and no protocol fee is collected for that leg despite the significant value transferred: [5](#0-4) 
4. Compare against an equivalent-value swap denominated purely in `Nep141` tokens, where the fee is enforced per `fee_ceil(amount)` proportional to the full traded amount — demonstrating the fee owed vs. fee collected mismatch introduced solely by the token type/amount heuristic.
