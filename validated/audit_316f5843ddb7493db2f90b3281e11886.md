### Title
Non-deterministic AMM pricing in TRC10 Exchange (`Math.pow` vs `StrictMath.pow`) — ([File: chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java])

### Summary
The Wise Lending V2 report describes a flash-loan attack that exploited internal price/accounting logic to drain a pool within a single atomic sequence. The closest in-scope, unprivileged-transaction analog in java-tron is the TRC10 "Bancor" AMM implemented by `ExchangeTransactionActuator` / `ExchangeWithdrawActuator`, whose pricing math (`ExchangeProcessor`) is gated by the `useStrictMath` flag and can, when that flag is off, compute a `double`-precision `Math.pow` result that differs from the `StrictMath.pow`/`SafeExchangeProcessor` (BigDecimal) result for the same trade inputs.

### Finding Description
`ExchangeCapsule.transaction()` selects a pricing `Processor` based on two independently-toggleable dynamic parameters, `useStrictMath` and `hardenedCalc`: [1](#0-0) 

When `hardenedCalc` is false (the legacy/default code path used by `ExchangeTransactionActuator.execute` and `ExchangeWithdrawActuator.execute`), the trade amount is computed by `ExchangeProcessor`, which uses `Maths.pow(base, exponent, useStrictMath)` to evaluate the bonding-curve formula: [2](#0-1) 

The project's own test `testStrictMath` in `ExchangeProcessorTest` directly demonstrates that, for a large set of realistic pool-balance/quantity inputs, the non-strict (`Math.pow`) result differs from the strict (`StrictMath.pow`) / hardened `BigDecimal`-based result: [3](#0-2) 

`Math.pow` is only required to be accurate to within 1 ULP and different JVM builds/JIT paths/CPU targets (e.g., HotSpot intrinsics vs. software fallback, different architectures) are permitted to return different bit-exact results for the same inputs, whereas `StrictMath.pow` (fdlibm) is bit-reproducible everywhere. Because `ExchangeTransactionActuator`/`ExchangeWithdrawActuator` write the resulting token quantities directly into `AccountCapsule` balances and the `ExchangeCapsule` pool state, and this state becomes part of the block's Merkle root, any node whose JVM/hardware evaluates `Math.pow` differently for the same transaction will compute a different `anotherTokenQuant`, producing a different post-state for an otherwise identical transaction.

The project clearly recognized this class of risk: it introduced `useStrictMath` and, further, a fully deterministic `SafeExchangeProcessor` (BigDecimal-based) gated behind `AllowHardenExchangeCalculation`. Both of these are optional, committee-activated dynamic parameters — meaning the vulnerable, non-deterministic `Math.pow` path remains the code that actually executes whenever those parameters are not (yet) turned on for a given deployment/network. Any unprivileged account can trigger this code merely by submitting a normal `ExchangeTransactionContract` or `ExchangeWithdrawContract` transaction — no special privilege is required.

### Impact Explanation
If different full nodes in the network are running JVMs/hardware that evaluate `Math.pow` with different (ULP-level) results for the same operands, they will independently compute different `anotherTokenQuant` values for the same `ExchangeTransactionContract`/`ExchangeWithdrawContract` transaction. Because that value directly mutates account balances (`AccountCapsule.setBalance`/`addAssetAmountV2`) and pool reserves (`ExchangeCapsule.setBalance`) that are part of consensus state, this divergence leads to differing state roots across nodes for the same block — i.e., a chain split / consensus failure. This matches the "chain split" impact category explicitly accepted by the validation rules, and is more severe than the pool-drain from the external Wise Lending report because it threatens network-wide consensus, not just one protocol's balance sheet.

### Likelihood Explanation
Exploitation (or accidental triggering) requires: (1) heterogeneous JVM/hardware in the network's node set, and (2) a trade whose input reserves happen to fall in an operand region where `Math.pow` and `StrictMath.pow` diverge by at least 1 ULP after truncation to a `long`. The project's own test data shows this divergence is not rare — nearly all of the 47 sampled real-world-like trades in `testStrictMath` diverge between strict and non-strict computation. However, actually causing a *cross-node* divergence additionally depends on real heterogeneity of deployed JVMs across the validator/full-node set, which cannot be confirmed from the repository alone — likelihood is therefore assessed as Medium: the numerical divergence itself is trivially reproducible and already proven by the codebase's tests, but network-wide impact is contingent on deployment diversity outside the code's control.

### Recommendation
- Make `useStrictMath` (and ideally the BigDecimal-based `SafeExchangeProcessor`/`AllowHardenExchangeCalculation`) mandatory rather than opt-in dynamic parameters, or hard-fork them to "always on" for all networks that still run the legacy Bancor exchange.
- Remove/deprecate the `Math.pow`-based `ExchangeProcessor` code path entirely once `SafeExchangeProcessor` is proven equivalent, so no network can be left running the non-deterministic calculation.
- Add consensus-level regression tests across multiple JVM vendors/architectures to catch any remaining non-strict floating-point usage in state-mutating actuators.

### Proof of Concept
1. Deploy two nodes on different JVM builds/CPU architectures (e.g., one on an x86_64 build using AVX-optimized `Math.pow` intrinsics vs. one on a different JIT/architecture without that intrinsic), with `useStrictMath` and `AllowHardenExchangeCalculation` left at their default/disabled values.
2. Submit an ordinary `ExchangeTransactionContract` (or `ExchangeWithdrawContract`) trade against a TRC10 exchange pool with reserve values matching (or near) any of the data rows demonstrated to diverge in `ExchangeProcessorTest.testStrictMath` (e.g., `{4732214L, 2202692725330L, 29218L}`), see: [4](#0-3) 
3. Observe that `ExchangeProcessor.exchange()` on the two nodes can return different `buyTokenQuant` values for the identical transaction inputs, causing divergent `AccountCapsule`/`ExchangeCapsule` state and, ultimately, divergent block state roots between the two nodes.
