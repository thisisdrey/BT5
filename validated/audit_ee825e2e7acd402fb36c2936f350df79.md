## Title
Unanchored Pool-Repository Classification Regex Allows Bypass of Object Pool Directory Containment Check - (File: `internal/gitaly/storage/repository_path.go`)

### Summary
The reported bug class is a security decision ("is this address a contract or an EOA?") made via a spoofable runtime check, causing the wrong validation branch to run and a real signature check to be silently skipped. The Gitaly analog is the pool-repository classification performed by `storage.IsPoolRepository()` (and its helpers `IsRailsPoolRepository`/`IsPraefectPoolRepository`), which decides whether an object-pool `RelativePath` supplied in an RPC request is treated as a "genuine" pool repository. Because the underlying regexes are not anchored to the start of the string, an attacker-influenced `RelativePath` can be misclassified as a legitimate pool path, which causes `objectpool.FromProto` to skip the only containment check that otherwise restricts non-pool-shaped paths to the storage's temporary directory.

Both `railsPoolDirRegexp` and `praefectPoolDirRegexp` are anchored only at the end (`$`), not at the start (`^`). `regexp.MatchString` looks for the pattern anywhere in the string, so any `RelativePath` that merely *ends* with the expected pool suffix (e.g. `.../@pools/ab/cd/<64-hex>.git` or `.../@cluster/pools/ab/cd/<id>`) is classified as a pool repository, regardless of what precedes it.

This classification is used as the sole gate in `objectpool.FromProto` to decide whether to enforce that the resolved pool path lives under the storage's temp directory: [2](#0-1) 

If `IsPoolRepository` returns `true` (which an attacker can force via a crafted suffix), the `strings.HasPrefix(poolPath, tempDir)` containment check is skipped entirely, and the code proceeds directly to `pool.IsValid(ctx)`, which only confirms the target is *some* valid git repository — not that it is a properly-provisioned pool created via `CreateObjectPool`.

Note that `locator.GetRepoPath`/`ValidateRepository` do confine the resolved path within the storage root via `storage.ValidateRelativePath` [5](#0-4) , so this is not a full path-escape outside the storage. The impact is scoped to *within* a given storage: an attacker who can influence the `RelativePath` of an `ObjectPool`/`Repository` message (e.g., via `CreateObjectPool`, `LinkRepositoryToObjectPool`, or Praefect's `DeleteObjectPool`) can construct a path that satisfies the pool-classification regex by suffix alone, bypassing the "must live in temp dir" restriction that is otherwise the only structural safeguard preventing arbitrary repository paths within the storage from being treated as trusted object pools.

### Impact Explanation
Object pools are treated specially by housekeeping (excluded from certain pruning/GC operations) and are used as shared alternate object stores linked into member repositories via `GIT_ALTERNATE_OBJECT_DIRECTORIES`. Misclassifying an attacker-chosen path as a "genuine" pool bypasses the directory-containment invariant Gitaly relies on to distinguish provisional/temporary pool creation from arbitrary repository paths, which is a violation of the intended trust boundary for object-pool provisioning and could let a repository outside the expected `@pools`/`@cluster/pools` layout be linked in as an alternate object store, affecting object visibility/deduplication and housekeeping behavior for other repositories in the same storage.

### Likelihood Explanation
The `RelativePath` field is part of the `Repository`/`ObjectPool` protobuf messages passed by RPC callers (including GitLab Rails, `gitaly-praefect`, and any authenticated gRPC client). Constructing a suffix that matches the required hex/id format is mechanical, requiring only that the caller can already issue `CreateObjectPool`/`LinkRepositoryToObjectPool`/`DeleteObjectPool` requests — i.e., no additional privilege beyond normal RPC access to these object-pool RPCs is needed to trigger the misclassification branch.

### Recommendation
Anchor both `railsPoolDirRegexp` and `praefectPoolDirRegexp` at the start of the relative path (`^@pools/...` and `^` + `praefectPoolPathPrefix` respectively), or otherwise validate that the matched pattern spans the entire relative path (not just the suffix), so an attacker cannot force pool classification by appending a matching suffix to an arbitrary prefix.

### Proof of Concept
1. As a client authorized to call `CreateObjectPool`, submit `ObjectPool.Repository.RelativePath = "arbitrary/prefix/@cluster/pools/ab/cd/12345"` (or the Rails equivalent ending in `@pools/ab/cd/<64-hex>.git`).
2. `storage.ValidateRelativePath` in `ValidateRepository` accepts it because it does not escape the storage root.
3. `storage.IsPraefectPoolRepository` (or `IsRailsPoolRepository`) returns `true` because the regex only checks the suffix, matching `internal/gitaly/storage/repository_path.go:36-43`.
4. `objectpool.FromProto`'s temp-dir containment check at `internal/git/objectpool/pool.go:63-75` is skipped as a result, allowing the arbitrary-prefixed path to be treated as a valid object pool as long as `pool.IsValid` (i.e., it is *some* git repository) succeeds.

// IsRailsPoolRepository returns whether the repository is a pool repository generated by Rails.
func IsRailsPoolRepository(repo Repository) bool {
	matches := railsPoolDirRegexp.FindStringSubmatch(repo.GetRelativePath())
	if matches == nil || !strings.HasPrefix(matches[3], matches[1]+matches[2]) {
		return false
	}

	return true
}

// IsPraefectPoolRepository returns whether the repository is a Praefect generated object pool repository.
func IsPraefectPoolRepository(repo Repository) bool {
	return praefectPoolDirRegexp.MatchString(repo.GetRelativePath())
}

// IsPoolRepository returns whether the repository is an object pool.
func IsPoolRepository(repo Repository) bool {
	return IsRailsPoolRepository(repo) || IsPraefectPoolRepository(repo)
}
