### Title
Multi-signature weight double-counting via ECDSA signature malleability in `ValidateMultiSign` TVM precompile bypasses multisig threshold - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The Druid advisory describes a case where a validation/authorization barrier meant to gate access can be bypassed by a caller who is still nominally "checked" but the check's dedup/filter logic is insufficient, letting the caller obtain more than intended. The analogous flaw in java-tron is in the `ValidateMultiSign` precompiled contract, which recomputes multisig weight itself instead of reusing the hardened `TransactionCapsule.checkWeight` path, and its signature-dedup logic can be defeated with ECDSA signature malleability, allowing a single private key to be counted twice toward a multisig threshold.

### Finding Description
`ValidateMultiSign.execute` in `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java` (lines 1080-1118) implements its own ad-hoc signature/weight accounting loop: [1](#0-0) 

For each supplied signature it recovers `recoveredAddr`, then builds `sign = merge(recoveredAddr, sign)` and dedups by checking whether this exact merged byte array (`address || raw signature bytes`) was already seen — not by whether the *address* was already seen and credited weight. If the same address appears again but with a *different* raw signature encoding, the code does **not** `continue`; it only calls `MUtil.checkCPUTime()` (a CPU-time guard) and then falls through to add `weight` to `totalWeight` again via `TransactionCapsule.getWeight(permission, recoveredAddr)`.

Because ECDSA signatures are malleable (for any valid `(r, s)` there is a second valid `(r, n-s)` with a flipped recovery id that recovers to the *same* address for the *same* message hash), an attacker holding a single private key can submit two syntactically distinct 65-byte signatures that both recover to the same address. Both are accepted and their weight is summed twice, so a single key with weight `W` can satisfy any threshold `≤ 2W` — defeating the purpose of the multi-key permission structure.

This is the same bug class the transaction-level signature verifier (`TransactionCapsule.checkWeight`) once had and was fixed for: `checkWeight` dedups by `encode58Check(address)` after `ForkController.instance().pass(Parameter.ForkBlockVersionEnum.VERSION_4_7_1)`, i.e. by *address*, not by raw signature bytes: [2](#0-1) 

That fix was never applied to the TVM `ValidateMultiSign` precompile, which still dedups by the merged `(address, signature-bytes)` pair rather than by address alone, leaving the malleability bypass open in the TVM code path that smart contracts (e.g., on-chain multisig wallets, escrow, DAO-style contracts) rely on for authorization decisions.

### Impact Explanation
Any smart contract on TRON that uses the `ValidateMultiSign` precompile (address `0x0000...0009` reachable via `STATICCALL`/`CALL` from TVM bytecode) to gate privileged operations (e.g., "N signers must approve this withdrawal") can have its threshold check bypassed by a single colluding/compromised key. This directly enables unauthorized account/contract operations and theft of funds held by contracts that rely on this precompile for multisig authorization — a concrete violation of an authorization barrier reachable purely via a signed transaction that invokes a contract calling this precompile, with no special privilege required by the caller.

### Likelihood Explanation
Exploitation only requires: (1) a smart contract that uses the `ValidateMultiSign` precompile for authorization (a documented, intended usage pattern), and (2) an attacker who controls one signing key with nonzero weight and knows the message hash to sign — both trivial for a broadcaster/order-placer/contract-caller. Generating the malleable twin signature `(r, n-s)` from `(r, s)` is a well-known, cheap operation, requiring no private key recovery. The only friction is `MUtil.checkCPUTime()`, a performance guard, not a security control.

### Recommendation
Change the dedup key in `ValidateMultiSign.execute` (and the analogous `BatchValidateSign`/other precompiles doing manual signer accounting) from the merged `(address, signature bytes)` array to the recovered `address` alone, mirroring the fix already applied in `TransactionCapsule.checkWeight`: once an address has been credited weight, any further signature recovering to that same address must be skipped entirely rather than only skipped when byte-for-byte identical. Also normalize/reject signatures with non-canonical `s` values (`s > n/2`) at the entry point to eliminate malleable duplicates outright.

### Proof of Concept
1. Deploy or use an existing contract that gates a fund transfer on `ValidateMultiSign(ownerAddress, permissionId, dataHash, signatures[])` returning true when `totalWeight >= threshold`, e.g. a 2-of-2 (or N-of-N) permission where two distinct keys are each weight 1 and threshold 2.
2. As the holder of only one of the required keys, sign `dataHash` normally to get `sig1 = (r, s, v)`.
3. Compute the malleable counterpart `sig2 = (r, n-s, v')` (standard secp256k1 malleability transform), which recovers to the *same* address as `sig1` for the same hash.
4. Call the target contract, passing `signatures = [sig1, sig2]` into `ValidateMultiSign`.
5. In `PrecompiledContracts.ValidateMultiSign.execute`, both signatures recover to the same `recoveredAddr`; since `merge(recoveredAddr, sig1) != merge(recoveredAddr, sig2)`, the identical-byte check at line 1093 fails to `continue`, and the weight for that single address is added twice (`totalWeight` reaches `2` instead of `1`).
6. `totalWeight >= permission.getThreshold()` (2 >= 2) evaluates true, and the precompile returns `dataOne()` even though only one distinct authorized key actually signed — bypassing the intended 2-signer requirement and authorizing the guarded operation. [3](#0-2)
