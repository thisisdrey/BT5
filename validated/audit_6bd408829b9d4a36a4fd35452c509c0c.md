### Title
Unbounded attacker-controlled `estimated_len` causes integer overflow in `minimum_fee` computation - (File: `stackslib/src/net/api/postfeerate.rs`)

### Summary
`RPCPostFeeRateRequestHandler::try_parse_request` computes `estimated_len` as `max(body.estimated_len.unwrap_or(0), payload_data.len())`, where `body.estimated_len` is a fully attacker-controlled `u64` JSON field with no upper bound check (`MAX_PAYLOAD_LEN` only bounds the raw HTTP content length, not this field). This value flows unchecked into `estimate_tx_fee_from_cost_and_length`, where `let minimum_fee = estimated_len * MINIMUM_TX_FEE_RATE_PER_BYTE;` performs plain (non-checked) multiplication.

### Finding Description
In `try_parse_request` (`stackslib/src/net/api/postfeerate.rs:180-181`), `estimated_len` is taken directly from client JSON with no range validation:
```
let estimated_len = std::cmp::max(body.estimated_len.unwrap_or(0), payload_data.len() as u64);
```
`content_len` (the raw byte length of the whole POST body) is checked against `MAX_PAYLOAD_LEN` (`stackslib/src/net/api/postfeerate.rs:152-158`), but this bounds only the HTTP message size, not the numeric value of the JSON field `estimated_len`, which is a separate `u64` deserialized from `FeeRateEstimateRequestBody` (`stackslib/src/net/api/postfeerate.rs:37-42`). An attacker can send a small JSON body such as `{"estimated_len": 18446744073709551615, "transaction_payload": "0x..."}` with a tiny valid payload, easily fitting under `MAX_PAYLOAD_LEN`.

This unbounded value is stored in `self.estimated_len` and passed to `estimate_tx_fee_from_cost_and_length` (`stackslib/src/net/api/postfeerate.rs:112`):
```
let minimum_fee = estimated_len * MINIMUM_TX_FEE_RATE_PER_BYTE;
```
This is a plain `*` operation on `u64`, not `checked_mul`/`saturating_mul`. In a debug build (`overflow-checks` on), this multiplication panics on overflow. In a release build, it silently wraps, producing an arbitrary/garbage `minimum_fee` that could end up far lower or higher than intended, corrupting the fee estimate returned to any caller of this public, unauthenticated endpoint.

No existing guard intercepts this: `content_len < MAX_PAYLOAD_LEN` only bounds the wire size of the JSON body, not the numeric magnitude of a field inside it; there is no explicit cap on `body.estimated_len` anywhere in `try_parse_request`.

### Impact Explanation
- In debug/testing builds with overflow checks enabled, a single crafted POST to `/v2/fees/transaction` panics the thread handling the request, causing an unauthenticated remote crash/DoS-per-request against the RPC handler thread — repeatable indefinitely with one message each time.
- In release builds (default `cargo build --release`, no `overflow-checks`), the multiplication wraps silently, producing an incorrect `minimum_fee` that is then applied to floor all `RPCFeeEstimate.fee` values in the response (`stackslib/src/net/api/postfeerate.rs:114-118`). This serves callers (wallets, tooling) a corrupted/misleading fee estimate they may rely on for constructing a valid transaction, which matches the "High" impact category of steering behavior via a read endpoint with attacker-controlled bounded compute/data corruption — though it does not compromise consensus state.
- No authentication is required; `/v2/fees/transaction` has no auth gate.

### Likelihood Explanation
- No preconditions: the endpoint requires no auth secret, no peer relationship, no StackerDB ownership — any remote client with network access to the RPC port can send this request.
- Attacker cost is a single small HTTP POST with a valid-but-minimal `transaction_payload` and `estimated_len: u64::MAX` (or any value causing overflow when multiplied by `MINIMUM_TX_FEE_RATE_PER_BYTE`).
- Fully repeatable per request, with the outcome depending on the build profile (panic vs. silent wrap), but the underlying missing-bounds-check condition is deterministic in both cases.

### Recommendation
Use `checked_mul` or `saturating_mul` in `estimate_tx_fee_from_cost_and_length` when computing `minimum_fee`, returning `HttpBadRequest` on overflow rather than performing raw multiplication. Additionally, clamp/validate `body.estimated_len` in `try_parse_request` against a sane upper bound (e.g., `MAX_PAYLOAD_LEN` or a small multiple thereof) and reject values that exceed it with `Error::DecodeError`.

### Proof of Concept
Add a test in `stackslib/src/net/api/tests/postfeerate.rs`:
1. Construct a `FeeRateEstimateRequestBody` with `estimated_len: Some(u64::MAX)` and a small valid hex `transaction_payload` (e.g. a minimal `TokenTransfer` payload).
2. Serialize to JSON and drive it through `RPCPostFeeRateRequestHandler::try_parse_request` (or the full HTTP request/response cycle via `StacksHttpRequest::new_post_fee_rate`).
3. Call `RPCPostFeeRateRequestHandler::estimate_tx_fee_from_cost_and_length` with the resulting `estimated_len` and assert that it either:
   - returns an `Err`/`HttpBadRequest` cleanly, or
   - does not panic (in a debug build with `overflow-checks=true`) at `let minimum_fee = estimated_len * MINIMUM_TX_FEE_RATE_PER_BYTE;` (`stackslib/src/net/api/postfeerate.rs:112`).

Currently, running this in a debug build with overflow checks reaches the panic site directly; in release mode the assertion should check that `minimum_fee` is not a wrapped/garbage value inconsistent with `estimated_len`. [1](#0-0) [2](#0-1) [3](#0-2)

    pub fn estimate_tx_fee_from_cost_and_length(
        preamble: &HttpRequestPreamble,
        fee_estimator: &dyn FeeEstimator,
        metric: &dyn CostMetric,
        estimated_cost: ExecutionCost,
        estimated_len: u64,
        stacks_epoch: StacksEpoch,
    ) -> Result<RPCFeeEstimateResponse, StacksHttpResponse> {
        let scalar_cost =
            metric.from_cost_and_len(&estimated_cost, &stacks_epoch.block_limit, estimated_len);
        let fee_rates = fee_estimator.get_rate_estimates().map_err(|e| {
            StacksHttpResponse::new_error(preamble, &HttpBadRequest::new_json(e.into_json()))
        })?;

        let mut estimations = RPCFeeEstimate::estimate_fees(scalar_cost, fee_rates).to_vec();

        let minimum_fee = estimated_len * MINIMUM_TX_FEE_RATE_PER_BYTE;

        for estimate in estimations.iter_mut() {
            if estimate.fee < minimum_fee {
                estimate.fee = minimum_fee;
            }
        }

        Ok(RPCFeeEstimateResponse {
            estimated_cost,
            estimations,
            estimated_cost_scalar: scalar_cost,
            cost_scalar_change_by_byte: metric.change_per_byte(),
        })
    }

    fn try_parse_request(
        &mut self,
        preamble: &HttpRequestPreamble,
        _captures: &Captures,
        query: Option<&str>,
        body: &[u8],
    ) -> Result<HttpRequestContents, Error> {
        let content_len = preamble.get_content_length();
        if !(content_len > 0 && content_len < MAX_PAYLOAD_LEN) {
            return Err(Error::DecodeError(format!(
                "Invalid Http request: invalid body length for FeeRateEstimate ({})",
                content_len
            )));
        }

        if preamble.content_type != Some(HttpContentType::JSON) {
            return Err(Error::DecodeError(
                "Invalid content-type: expected application/json".to_string(),
            ));
        }

        let body: FeeRateEstimateRequestBody = serde_json::from_slice(body)
            .map_err(|e| Error::DecodeError(format!("Failed to parse JSON body: {}", e)))?;

        let payload_hex = if body.transaction_payload.starts_with("0x") {
            &body.transaction_payload[2..]
        } else {
            &body.transaction_payload
        };

        let payload_data = hex_bytes(payload_hex).map_err(|_e| {
            Error::DecodeError("Bad hex string supplied for transaction payload".into())
        })?;

        let tx = TransactionPayload::consensus_deserialize(&mut payload_data.as_slice())?;
        let estimated_len =
            std::cmp::max(body.estimated_len.unwrap_or(0), payload_data.len() as u64);

        self.transaction_payload = Some(tx);
        self.estimated_len = Some(estimated_len);
        Ok(HttpRequestContents::new().query_string(query))
    }
