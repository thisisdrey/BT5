### Title
Integer overflow in VOTEWITNESS opcode energy cost estimation via `DataWord.mul()` wraparound allows energy under-charging - (File: actuator/src/main/java/org/tron/core/vm/EnergyCost.java)

### Summary
`EnergyCost.getVoteWitnessCost2` (the legacy/default cost path used whenever `VMConfig.allowTvmOsaka()` is disabled) computes the memory-expansion cost for the `VOTEWITNESS` TVM opcode using 256-bit `DataWord` arithmetic. The array-length operand supplied directly by the calling contract's stack input is multiplied by the EVM word size using `DataWord.mul()`, which internally performs `value().multiply(word.value()).and(MAX_VALUE)` — i.e. it silently truncates/wraps modulo 2^256 with no overflow detection [1](#0-0) . This is structurally identical to the TensorFlow advisory's root cause: an unchecked integer multiplication feeding a resource/cost-estimation routine, where attacker-controlled operands can wrap and desynchronize the estimated cost from the real resource consumption.

### Finding Description
The vulnerable code path is: [2](#0-1) 

`amountArrayLength` and `witnessArrayLength` are raw 256-bit stack values fully controlled by the executing contract (pushed immediately before the `VOTEWITNESS` opcode). `getVoteWitnessCost` and `getVoteWitnessCost2` call `DataWord.mul(wordSize)` to compute `length * 32`. Because `DataWord.mul` never checks for overflow and instead masks the BigInteger result with `MAX_VALUE` (2^256-1), an attacker can choose a length such that `length * 32 mod 2^256` produces a small or zero value, even though the "true" mathematical memory requirement is astronomically large. The resulting (wrapped) `amountArrayMemoryNeeded`/`witnessArrayMemoryNeeded` is fed into `calcMemEnergy`, which then computes energy based on the wrapped, artificially small memory size [3](#0-2) .

The project's own test suite explicitly documents and reproduces this exact overflow class as a known hazard in the legacy path, and shows that a hardened `getVoteWitnessCost3` (BigInteger-based, no truncation) was introduced specifically to fix it — but `cost3` only activates when `VMConfig.allowTvmOsaka()` is enabled; otherwise it "self-dispatches" back to the vulnerable `cost2`/`DataWord.mul()` path: [4](#0-3) [5](#0-4) 

This means the fixed/hardened calculation is gated behind a feature flag (`allowTvmOsaka`), and on any network/version where that flag is not yet activated, the legacy overflow-prone `getVoteWitnessCost2` remains live and reachable by any contract executing `VOTEWITNESS`.

### Impact Explanation
An attacker-controlled smart contract can invoke the `VOTEWITNESS` opcode with crafted (very large, near 2^256) array-length operands that wrap the memory-size computation to a small value. This causes the energy metering for that opcode's memory expansion to be computed on a bogus, undercharged memory size while the actual downstream processing (array construction/witness list handling) may still act on attacker-supplied large lengths, decoupling energy accounting from real resource consumption. This falls squarely in the "TVM opcodes, precompiles and energy metering" and "bandwidth/energy accounting" attack surface explicitly in scope, and an incorrect energy charge for VM opcodes is a resource-accounting integrity flaw that can be leveraged to consume node resources cheaper than intended or destabilize energy accounting invariants relied on by the network.

### Likelihood Explanation
Reachable directly from an unprivileged, unmodified TVM contract call — no special privileges, SR/witness/committee status, or network-level position required. The only precondition is that `allowTvmOsaka` (a chain parameter) is not yet enabled, in which case `getVoteWitnessCost3` transparently falls back to the unguarded `getVoteWitnessCost2`/`DataWord.mul()` path documented above.

### Recommendation
Make the BigInteger-based, overflow-safe `getVoteWitnessCost3` calculation unconditional (or otherwise decouple it from the `allowTvmOsaka` hard fork flag) so the fixed accounting logic is always active regardless of chain-parameter activation state, and audit all other TVM opcode cost helpers still using `DataWord.mul()`/`DataWord.add()` for length arithmetic to ensure they route through the checked BigInteger `memNeeded`/`checkMemorySize` path rather than wrap-around DataWord arithmetic.

### Proof of Concept
1. Deploy a contract that pushes a witness-array length and amount-array length onto the stack such that `length * 32 mod 2^256` produces a small/zero result (e.g., `length = (2^256)/32` or similar value making the product wrap to near-zero), followed by offsets, then executes `VOTEWITNESS`.
2. With `VMConfig.allowTvmOsaka()` disabled (default/legacy chain parameter state), `OperationRegistry` dispatches to `getVoteWitnessCost2` [2](#0-1) , which calls `DataWord.mul()` and silently wraps the huge length into a small value.
3. `calcMemEnergy` then computes energy for a small memory region instead of the true value implied by the original operand, as reproduced by the project's own regression test `testLargeArrayLengthOverflow`/`testCost3FallsBackToCost2WhenOsakaOff` in `VoteWitnessCost3Test.java`, which explicitly demonstrates that cost2 "wraps away" the overflow that cost3 correctly detects [6](#0-5) .

  public static long getVoteWitnessCost2(Program program) {
    if (!VMConfig.allowEnergyAdjustment()) {
      return getVoteWitnessCost(program);
    }

    Stack stack = program.getStack();
    long oldMemSize = program.getMemSize();
    DataWord amountArrayLength = stack.get(stack.size() - 1).clone();
    DataWord amountArrayOffset = stack.get(stack.size() - 2);
    DataWord witnessArrayLength = stack.get(stack.size() - 3).clone();
    DataWord witnessArrayOffset = stack.get(stack.size() - 4);

    DataWord wordSize = new DataWord(DataWord.WORD_SIZE);

    amountArrayLength.mul(wordSize);
    amountArrayLength.add(wordSize); // dynamic array length is at least 32 bytes
    BigInteger amountArrayMemoryNeeded = memNeeded(amountArrayOffset, amountArrayLength);

    witnessArrayLength.mul(wordSize);
    witnessArrayLength.add(wordSize); // dynamic array length is at least 32 bytes
    BigInteger witnessArrayMemoryNeeded = memNeeded(witnessArrayOffset, witnessArrayLength);

    return VOTE_WITNESS + calcMemEnergy(oldMemSize,
        (amountArrayMemoryNeeded.compareTo(witnessArrayMemoryNeeded) > 0
            ? amountArrayMemoryNeeded : witnessArrayMemoryNeeded), 0, Op.VOTEWITNESS);
  }

  private static long calcMemEnergy(long oldMemSize, BigInteger newMemSize,
                             long copySize, int op) {
    long energyCost = 0;

    checkMemorySize(op, newMemSize);

    // memory SUN consume calc
    long memoryUsage = (newMemSize.longValueExact() + 31) / 32 * 32;
    if (memoryUsage > oldMemSize) {
      long memWords = (memoryUsage / 32);
      long memWordsOld = (oldMemSize / 32);
      long memEnergy = (MEMORY * memWords + memWords * memWords / 512)
          - (MEMORY * memWordsOld + memWordsOld * memWordsOld / 512);
      energyCost += memEnergy;
    }

    if (copySize > 0) {
      long copyEnergy = COPY_ENERGY * ((copySize + 31) / 32);
      energyCost += copyEnergy;
    }
    return energyCost;
  }

      overflowCaught = true;
    } finally {

  public void testCost3FallsBackToCost2WhenOsakaOff() {
    // cost3 self-dispatches: with osaka off it delegates to cost2, so a cost3 left in the shared
    // jump table (e.g. read by a constant call whose view has osaka off) still charges v2 energy.
    String maxHex = "ffffffffffffffffffffffffffffffffffffffffffffffffffffffffffffffff";
    DataWord huge = new DataWord(maxHex);
    DataWord zero = new DataWord(0);

    VMConfig.initAllowTvmOsaka(0);
    long viaCost3 =
        EnergyCost.getVoteWitnessCost3(mockProgram(zero, new DataWord(1), zero, huge, 0));
    long viaCost2 =
        EnergyCost.getVoteWitnessCost2(mockProgram(zero, new DataWord(1), zero, huge, 0));
    assertEquals("cost3 must equal cost2 when osaka is off", viaCost2, viaCost3);

    // sanity: with osaka on, cost3 instead runs v3 and detects the overflow that cost2 wraps away.
    VMConfig.initAllowTvmOsaka(1);
    try {
      EnergyCost.getVoteWitnessCost3(mockProgram(zero, new DataWord(1), zero, huge, 0));
      fail("cost3 with osaka on must overflow-throw on the huge length");
    } catch (Program.OutOfMemoryException expected) {
      // expected
    } finally {
      VMConfig.initAllowTvmOsaka(0);
    }
