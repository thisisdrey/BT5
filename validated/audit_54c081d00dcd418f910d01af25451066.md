## Analysis

The reported bug's core defect is: a "refund/beneficiary" address is computed differently depending on which call path is taken, and in several paths it resolves to an address that the intended recipient does not control — resulting in silent loss of value with no way to recover it.

A structurally identical pattern exists in the Snowbridge relayer reward payout flow.

### Title
Relayer rewards are irrecoverably lost when the cross-chain `DepositAsset` to the claimed beneficiary fails, because the fallback asset-trap claimer is bound to a synthetic bridge origin the relayer cannot control - (File: `bridges/snowbridge/primitives/core/src/reward.rs`)

### Summary
`PayAccountOnLocation::pay_reward` (used as `BridgeRewardPayer` for `BridgeReward::Snowbridge` in `cumulus/parachains/runtimes/bridge-hubs/bridge-hub-westend/src/bridge_common_config.rs`) builds and fire-and-forgets an `UnpaidExecution` XCM to AssetHub that deposits the reward to a relayer-chosen `beneficiary` `Location`. `pay_reward` returns `Ok(())` as soon as the message is *sent*, not once the deposit actually succeeds on AssetHub. Meanwhile, `pallet-bridge-relayers::do_claim_rewards` already debits the relayer's reward from on-chain storage before/atomically-with calling `pay_reward`. If the remote `DepositAsset` step fails (bad beneficiary conversion, ED not met, foreign-asset trust issue, etc.), the assets fall back to `AssetTrap`, whose claimer is derived from the XCM `context.origin` — which by this point has been overwritten by `UniversalOrigin(GlobalConsensus(EthereumNetwork))`, a location the relayer neither owns nor can use to reclaim the trapped assets. The relayer's reward is deducted from `RelayerRewards` and effectively burned/permanently locked.

### Finding Description
`pay_reward` builds:
```rust
let xcm: Xcm<()> = alloc::vec![
    UnpaidExecution { weight_limit: Unlimited, check_origin: None },
    DescendOrigin(InboundQueueLocation::get().into()),
    UniversalOrigin(GlobalConsensus(EthereumNetwork::get())),
    ReserveAssetDeposited(assets.into()),
    DepositAsset { assets: AllCounted(1).into(), beneficiary },
]
.into();
``` [1](#0-0) 

No `SetAssetClaimer` instruction is included. On the executor side, if any instruction after holding is populated fails (e.g. `DepositAsset` to an unconvertible/underfunded `beneficiary`), the executor traps the remaining holding using:
```rust
let claimer = self.asset_claimer.as_ref().or(self.context.origin.as_ref()).unwrap_or(&self.original_origin);
let trap_weight = Config::AssetTrap::drop_assets(claimer, self.holding, &self.context);
``` [2](#0-1) 

Since no `asset_claimer` was set and `UniversalOrigin` had already overwritten `context.origin` to `Location::new(2, [GlobalConsensus(Ethereum)])`, the trap is registered under that global-consensus origin — not under the relayer's beneficiary key. The relayer has no signing key or account that maps to `GlobalConsensus(Ethereum)` on AssetHub, so the trapped reward can never be reclaimed by them.

Compounding this, `pay_reward` reports success (`Ok(())`) purely on successful **enqueue/delivery** of the XCM ticket:
```rust
let (ticket, fee) = validate_send::<XcmSender>(AssetHubLocation::get(), xcm).map_err(|_| XcmSendFailure)?;
XcmExecutor::charge_fees(relayer.clone(), fee).map_err(|_| ChargeFeesFailure)?;
XcmSender::deliver(ticket).map_err(|_| XcmSendFailure)?;
Ok(())
``` [3](#0-2) 

The caller, `do_claim_rewards`, removes the reward from storage inside the same atomic `try_mutate_exists` closure that calls `pay_reward`:
```rust
let reward_balance = maybe_reward.take().ok_or(Error::<T, I>::NoRewardForRelayer)?;
T::PaymentProcedure::pay_reward(&relayer, reward_kind, reward_balance, beneficiary.clone())
    .map_err(|e| { ... Error::<T, I>::FailedToPayReward })?;
``` [4](#0-3) 

Because `pay_reward` only checks *send success*, not *remote execution success*, the debit is committed and `RewardPaid` is emitted even though the actual credit on AssetHub can later fail and become permanently unclaimable.

### Impact Explanation
This is a genuine value-conservation break: relayer rewards (bridge-earned, real economic value) are debited on BridgeHub, "sent" cross-chain, and can be lost forever if remote execution fails, since the fallback claimer is bound to an uncontrollable synthetic bridge origin rather than the relayer's chosen beneficiary. This matches the "permanent user-fund/bridge-state lock" and "theft or unbacked... loss" categories in the impact gate — value that should settle exactly once to the rightful beneficiary is instead unrecoverable.

### Likelihood Explanation
Any unprivileged relayer calling `claim_rewards_to` with `BridgeRewardBeneficiaries::AssetHubLocation` can trigger this by supplying (or ending up with) a `beneficiary` `Location` that AssetHub cannot successfully deposit to at execution time (e.g. targeting a location/account that isn't a valid, funded AccountId32/AccountKey20 on AssetHub, or one that doesn't reach existential deposit for the received asset). This requires no privileged actor, malicious validator, or governance action — only a normal relayer using the public `claim_rewards_to` extrinsic with an unlucky/misconfigured beneficiary, or transient conditions on AssetHub (e.g., asset momentarily untrusted/paused) at the exact time of XCM execution.

### Recommendation
- Do not remove/finalize the on-chain reward record until the remote deposit is confirmed (e.g., use a response-tracked query or a two-phase pending-claim model instead of `Ok(())` on `deliver()` alone), or
- Include a `SetAssetClaimer` instruction in the reward XCM that points to a Location the relayer actually controls (e.g., the relayer's own account/location or the `beneficiary`), so any traps land somewhere reclaimable, and
- Validate/convert `beneficiary` into an executable AssetHub deposit target before consuming the reward record on BridgeHub.

### Proof of Concept
1. Relayer accrues a `BridgeReward::Snowbridge` reward on BridgeHub via normal message processing (`register_reward`), as shown in [5](#0-4) .
2. Relayer calls `pallet_bridge_relayers::claim_rewards_to` with `BridgeRewardBeneficiaries::AssetHubLocation(VersionedLocation)` set to a `Location` that will fail `DepositAsset` conversion/execution on AssetHub (e.g. a location that does not resolve to a valid/funded local account for the Ethereum-native reserve asset), as exercised structurally in [6](#0-5) .
3. `do_claim_rewards` takes/removes the reward from `RelayerRewards` and calls `PayAccountOnLocation::pay_reward`, which only checks that `XcmSender::deliver` succeeded, then returns `Ok(())` — see [7](#0-6) .
4. On AssetHub, the `DepositAsset { beneficiary, .. }` instruction fails to execute; holding is trapped under `context.origin`, which was overwritten to `Location::new(2, [GlobalConsensus(EthereumNetwork)])` by the preceding `UniversalOrigin` instruction, not the relayer's beneficiary.
5. The relayer's reward has been debited on BridgeHub and is now trapped on AssetHub under an origin the relayer cannot sign for or claim — permanent loss.
