### Title
Vote count rounding truncation in partial unfreeze permanently loses voting power and reward yield - (File: `actuator/src/main/java/org/tron/core/actuator/UnfreezeBalanceV2Actuator.java`, `actuator/src/main/java/org/tron/core/vm/nativecontract/UnfreezeBalanceV2Processor.java`)

### Summary
When an account partially unfreezes staked TRX via `UnfreezeBalanceContract`/`UnfreezeBalanceV2Contract` (or the TVM native `unfreezeBalanceV2` opcode) while still having outstanding SR votes, the protocol proportionally re-scales the voter's existing votes to fit the reduced Tron Power. This re-scaling is done per-witness using floating-point division and a truncating `(long)` cast, which floors every individual vote independently. Because the floor operation is applied separately to each vote entry rather than once to the total, the sum of the recomputed votes is systematically smaller than the actual remaining Tron Power the account is entitled to use, and the discarded fraction (up to `totalVote - 1` votes) is silently and permanently dropped instead of being redistributed.

### Finding Description
The vote-truncation logic lives in `updateVote` of `UnfreezeBalanceV2Actuator.java`: [1](#0-0) 

and identically in the native-contract path used by the TVM's `unfreezeBalanceV2` precompiled/native opcode, `UnfreezeBalanceV2Processor.java`: [2](#0-1) 

For every SR the account previously voted for, the new vote count is computed as:
```
long newVoteCount = (long) ((double) vote.getVoteCount() / totalVote * ownedTronPower / TRX_PRECISION);
```
Each term is floored independently. If an account has voted for `N` different witnesses, the aggregate loss can be up to `N` votes (each up to just-under-1 vote unit) instead of at most 1 unit total, since no remainder/dust is redistributed back to any witness. Additionally, a vote with `newVoteCount == 0` after truncation is dropped entirely from `addVotes`/`votesToAdd` — see the `if (newVoteCount > 0)` guard — meaning small-weight votes to minor witnesses can be wiped out completely rather than merely reduced, even though the account still legitimately owns enough residual Tron Power to justify a nonzero allocation across all previously-voted witnesses when it is computed jointly rather than independently.

This exactly parallels the reported bug class: a mechanical truncation/rounding rule applied at the wrong granularity systematically reduces a user's yield-bearing quantity (there: locked duration vs. `MAX_LOCK`; here: post-unfreeze vote count vs. `ownedTronPower`), and the loss is not a fluke but is guaranteed by the math whenever `totalVote` does not evenly divide `ownedTronPower / TRX_PRECISION` across every vote entry.

The same `updateVote`/native-processor code path is triggered by:
- `UnfreezeBalanceV2Actuator.execute` — a directly broadcastable transaction type (`UnfreezeBalanceV2Contract`), reachable by any account holder.
- `UnfreezeBalanceV2Processor.execute` — reachable from a smart contract executing the `unfreezeBalanceV2` TVM native/precompiled opcode, i.e., reachable by any contract deployer/caller.

### Impact Explanation
Any voter who splits their vote across multiple SR candidates and later performs a partial unfreeze that reduces their Tron Power below their total committed vote count will have their vote allocation recomputed with independent floor-rounding per witness. This causes:
- Permanent loss of "voting weight" (and thus SR reward yield accrued via `VoteRewardUtil.computeReward`/`MortgageService.computeReward`, which are driven by `Vote.getVoteCount()`), disproportionate to the number of witnesses voted for.
- Complete and silent removal of votes toward witnesses whose truncated share rounds to zero, even though in aggregate the account still holds sufficient Tron Power to justify continuing to vote for them.
- The lost voting weight is not returned to the user nor to any other witness; it is simply discarded, functioning as an unrecoverable reduction in future reward accrual for the affected account, mirroring the "significant loss of yield" impact in the reference report.

### Likelihood Explanation
This is trivially reachable with ordinary, unprivileged operations: any account can vote for multiple witnesses via `VoteWitnessContract`, then submit a normal `UnfreezeBalanceV2Contract` transaction (or call `unfreezeBalanceV2` through a contract) for a small amount that reduces Tron Power below total votes. No special permissions, malicious SR/witness collusion, or unusual chain state is required — it happens deterministically as a byproduct of routine partial unfreezing while voting for more than one SR, which is an encouraged usage pattern (vote diversification).

### Recommendation
Recompute the proportional vote redistribution using integer arithmetic that tracks and redistributes the rounding remainder (e.g., largest-remainder method) instead of flooring each vote entry independently, ensuring `sum(newVoteCount)` is as close as possible to `ownedTronPower / TRX_PRECISION` rather than systematically less than it. Alternatively, accumulate the total floor error and apply it to the largest vote entry, or recompute votes based on `Math.round` with proper carry handling instead of independent truncation per witness.

### Proof of Concept
1. Freeze balance to obtain Tron Power `P` (e.g., `P = 1000` units after `/TRX_PRECISION`).
2. Vote for 3 witnesses: `VoteWitnessContract` with `{A: 400, B: 300, C: 300}` (`totalVote = 1000`).
3. Partially unfreeze via `UnfreezeBalanceV2Contract` such that `ownedTronPower` drops to, say, `999` (just below `totalVote * TRX_PRECISION`).
4. `updateVote` runs the truncating loop in `UnfreezeBalanceV2Actuator.java` lines 371-381: each of the three votes is computed as `(long)((double)voteCount/1000*999/TRX_PRECISION)` independently, causing up to 3 units of Tron Power to be lost across the three witnesses instead of just 1, and any witness whose truncated share becomes `0` is dropped entirely from `accountCapsule.getVotesList()`.
5. Compare `sum(newVoteCount)` against the account's actual `ownedTronPower / TRX_PRECISION` — the sum will be strictly less, and the deficit grows with the number of witnesses voted for, directly reducing the account's future reward computed by `VoteRewardUtil.computeReward`/`MortgageService.computeReward`.
