### Title
Unprivileged attacker can fill a victim's token list via dust `DepositToken` transfers, permanently DoS-ing new collateral deposits and transfers - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
`Pool` enforces `MAX_TOKENS_PER_USER = 30` across `depositTokensOfAccount + debtTokensOfAccount`, reverting with `UserReachedMaxTokens` whenever a new token is added (`Pool.sol:79`, `Pool.sol:143-148`, `Pool.sol:216-220`). `DepositToken._transfer` unconditionally calls `pool.addToDepositTokensOfAccount(recipient_)` whenever the recipient's prior balance is zero (`DepositToken.sol:517-520`). Any EOA can push dust `msdToken` amounts to a victim, filling the victim's list until every subsequent deposit of a *new* collateral type — and every incoming transfer of a token the victim doesn't already hold — reverts. This is the on-chain analog of the Manta DDoS incident: an unprivileged, cost-bounded request flood that denies service to a target.

### Finding Description
- `DepositToken.transfer`/`transferFrom` only check the *sender's* unlocked balance via `_revertIfLocked` (`DepositToken.sol:348-376`); there is no opt-in or hook on the recipient side, so dust transfers cannot be refused.
- Each transfer to a fresh token triggers `addToDepositTokensOfAccount`, which reverts once the combined list reaches 30 (`Pool.sol:143-148`).
- `_mint` during `deposit()` also calls `addToDepositTokensOfAccount` on a zero prior balance (`DepositToken.sol:486-488`), so a saturated victim cannot `deposit` any collateral type they don't already hold.
- The check also fires inside `seize` during `Pool.liquidate` when the liquidator's balance of that deposit token is zero (`DepositToken.sol:343-345`), so a liquidator who has been pushed to the cap cannot take payouts in a new collateral type.

The victim can only free a slot by driving some balance to zero (`withdraw`, `transfer`, or burn via liquidation). If their collateral is locked by debt (`_revertIfLocked` / `unlockedBalanceOf` returns ~0, `DepositToken.sol:383-398`), they cannot withdraw or transfer out — so they cannot free a slot, cannot add a new collateral type to restore health, and their position is forced into liquidation. Slots are per-token-identity, so the attacker can re-fill any freed slot for the cost of one wei of that token.

### Impact Explanation
Permanent-to-persistent freezing of a victim's ability to onboard new collateral and receive `msdToken` transfers, plus forced-liquidation risk for leveraged positions that can only be saved by depositing a collateral type they don't yet hold. Attacker cost is bounded: one dust deposit per distinct listed deposit token (no fees beyond gas, dust remains withdrawable by the attacker afterward since attacker has no debt). No privileged role, oracle manipulation, or governance action is required — only public `transfer` calls.

### Likelihood Explanation
Requires the pool to list enough deposit tokens (combined with the victim's existing entries) to reach 30. On main Metronome pools listing many collaterals (msdMET/msdETH/msdBTC plus Vesper `va*` deposit tokens), an attacker can cheaply acquire dust of each by depositing minimum amounts. Persistence is high: re-griefing a freed slot costs one dust transfer. Severity is bounded because it does not drain funds directly and victims with unlocked balances can evict entries.

### Recommendation
- Make `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` non-reverting at the cap for *transfers* (skip adding and accept the accounting consequence), or
- Drop the `MAX_TOKENS_PER_USER` cap and bound iteration elsewhere (the lists are only iterated in view paths like `debtOf`/`depositOf`/`debtPositionOf` used on-chain — cap iterations instead), or
- Require recipient opt-in: only auto-add tokens on `deposit`/`mint`, not on inbound `transfer`/`seize`, and let users add/remove list entries themselves.

### Proof of Concept
```solidity
// Foundry fork test sketch
// Setup: fork a chain where Pool P lists N deposit tokens {dt_i}.
// Attacker: for each dt_i, deposit dust -> receives msd_i dust (unlocked, attacker has no debt).
function test_fillVictimTokenList() public {
    address victim = makeAddr("victim");
    // victim has open position with debt -> unlockedBalanceOf(victim) == 0 for all tokens

    for (uint i; i < depositTokens.length; ++i) {
        IDepositToken dt = depositTokens[i];
        dt.transfer(victim, 1); // attacker pushes dust; each adds dt to victim's list
    }
    // force victim to 30 entries (combine with victim's existing debt/deposit tokens)

    // Now any new-collateral deposit reverts:
    vm.expectRevert(Pool.UserReachedMaxTokens.selector);
    newDepositToken.deposit(amount, victim); // via _mint -> addToDepositTokensOfAccount

    // And inbound transfers of a token victim doesn't hold revert:
    vm.expectRevert(Pool.UserReachedMaxTokens.selector);
    otherToken.transfer(victim, 1);

    // Victim cannot withdraw locked collateral to free a slot:
    vm.expectRevert(DepositToken.NotEnoughFreeBalance.selector);
    vm.prank(victim);
    someToken.withdraw(1, victim);
}
```
Key assertions: `pool.getDepositTokensOfAccount(victim).length` hits the cap, subsequent `deposit`/`transfer` into the victim revert with `UserReachedMaxTokens`, and `unlockedBalanceOf(victim) == 0` prevents self-recovery while debt is outstanding.
