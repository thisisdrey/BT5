### Title
Potential double-payment of vote rewards across the old/new reward-algorithm boundary cycle in `MortgageService.computeReward` - (File: chainbase/src/main/java/org/tron/core/service/MortgageService.java)

### Summary
The M-18 report describes a class of bugs where two independent claim mechanisms are allowed to draw from the same underlying reward pool without a strict, atomic accounting split, so the sum of what can legitimately be claimed exceeds what was actually deposited, letting an earlier claimant take funds that belong to a later one. In java-tron, witness voting rewards are similarly accounted from a single per-cycle-per-witness reward bucket (`DelegationStore` reward key) that is read and drained by two different reward-computation code paths depending on whether the cycle is before or after `NEW_REWARD_ALGORITHM_EFFECTIVE_CYCLE`.

### Finding Description
Block/transaction-fee rewards for a witness in a cycle are deposited into a single bucket via `MortgageService.payReward` [1](#0-0) , which calls `delegationStore.addReward(cycle, witnessAddress, value)`.

That same per-cycle reward value is consumed by **two independent computation paths**:
1. The legacy, proportional-share algorithm `computeReward(cycle, votes)` which divides `getReward(cycle, srAddress)` by `getWitnessVote(cycle, srAddress)` and multiplies by the individual voter's vote count [2](#0-1) .
2. The new Vi-based algorithm, which turns the *same* `getReward(cycle, address)` value into a per-cycle delta-Vi accumulator (`accumulateWitnessVi`) that is later used to compute rewards via `deltaVi * userVote / DECIMAL_OF_VI_REWARD` [3](#0-2) [4](#0-3) .

The switch-over between these two algorithms is governed by `newRewardAlgorithmCycle`/`getOldReward`, which splits a claim's `[beginCycle, endCycle)` range at the effective cycle boundary [4](#0-3) . There is also an entirely separate, redundant Vi-accumulation implementation in `RewardViCalService.accumulateWitnessVi` used for pre-effective-cycle backfilling [5](#0-4)  and one used live in `MaintenanceManager.doMaintenance()` for every new cycle post-switch [6](#0-5) .

Both computation paths (`computeReward` legacy share formula and the Vi-delta formula) read from the exact same underlying `getReward(cycle, address)` bucket rather than each having its own dedicated bucket, and the boundary cycle is handled by a `min(...)` cutover rather than a hard, non-overlapping partition validated against total deposited reward. If the boundary logic (`oldEndCycle = min(endCycle, newAlgorithmCycle, ...)`) or the backfill service (`RewardViCalService`) ever computes Vi for a cycle that also gets consumed by the legacy per-cycle share formula for a voter whose reward accounting wasn't strictly cut over atomically with all witnesses' state, the same underlying reward bucket can be claimed twice through the two different formulas — mirroring the M-18 pattern where two claim types (game players vs vault stakers) draw against one pool whose combined claims can exceed the actual deposited amount.

Note: I was not able to fully trace every invariant that guarantees mutual exclusivity between the legacy and Vi-based ranges for all vote-history edge cases (e.g. a voter with `beginCycle < newAlgorithmCycle < endCycle` whose account-vote snapshots straddle the switch, combined with `RewardViCalService`'s asynchronous backfill of Vi for cycles `< newRewardCalStartCycle`), because these interactions span multiple asynchronous services (`RewardViCalService`, `MaintenanceManager`, `MortgageService`) whose exact ordering guarantees are enforced through `CommonParameter`/checkpoint flushing rather than a single atomic invariant, and the reasoning here is based on static code review, not a concrete reproduced trace.

### Impact Explanation
If double accounting can occur across the reward-algorithm boundary, a voter/witness could receive more `allowance` (withdrawable via `WithdrawBalanceActuator`/`WithdrawRewardProcessor`) than was actually paid into the reward pool for that cycle, which is an unbacked-balance / theft-of-funds class issue (rewards ultimately convert into TRX balance and can be withdrawn). Since this affects consensus reward accounting used chain-wide, an accounting drift would also produce state-root/merkle-root divergence (`RewardViCalService.calcMerkleRoot`), which can contribute to a chain split if nodes disagree on the effective cutover timing.

### Likelihood Explanation
This requires a specific, narrow precondition: the `ALLOW_NEW_REWARD_ALGORITHM`/`NEW_REWARD_ALGORITHM_EFFECTIVE_CYCLE` transition, combined with a voter/witness whose claim window straddles the cutover cycle, and the asynchronous `RewardViCalService` backfill completing (or not) at a particular relative time to `MaintenanceManager.doMaintenance()`. This is a governance-triggered, one-time migration event rather than an attacker-controlled trigger, and it was not reproduced concretely — it is a code-review-level concern based on two independent reward-formula code paths sharing one underlying reward bucket, matching the reported bug class, but confidence in actual exploitability is low without a concrete PoC trace through the transition.

### Recommendation
Add an explicit, tested invariant that the sum of rewards distributable via the legacy per-cycle-share formula and the Vi-delta formula for any given cycle can never exceed the amount actually deposited by `payReward`/`addReward` for that witness/cycle, and add regression tests that specifically exercise voters/witnesses with claim windows straddling `NEW_REWARD_ALGORITHM_EFFECTIVE_CYCLE`, including cases where `RewardViCalService`'s asynchronous backfill has not yet completed when a withdrawal is requested.

### Proof of Concept
Not reproduced; this is a code-review-derived analog rather than a validated exploit. A concrete PoC would require constructing a chain state around a `NEW_REWARD_ALGORITHM_EFFECTIVE_CYCLE` transition with a voter whose `beginCycle`/`endCycle` window spans the switch, then verifying via `MortgageService.queryReward`/`withdrawReward` and `RewardViCalService.getNewRewardAlgorithmReward` whether the combined payout for that voter (plus other voters/witness brokerage) for the boundary cycle exceeds `delegationStore.getReward(cycle, srAddress)` deposited that cycle.

  private long computeReward(long cycle, List<Pair<byte[], Long>> votes) {
    long reward = 0;
    for (Pair<byte[], Long> vote : votes) {
      byte[] srAddress = vote.getKey();
      long totalReward = delegationStore.getReward(cycle, srAddress);
      if (totalReward <= 0) {
        continue;
      }
      long totalVote = delegationStore.getWitnessVote(cycle, srAddress);
      if (totalVote == DelegationStore.REMARK || totalVote == 0) {
        continue;
      }
      long userVote = vote.getValue();
      double voteRate = (double) userVote / totalVote;
      reward += voteRate * totalReward;
    }
    return reward;
  }

  private long computeReward(long beginCycle, long endCycle, AccountCapsule accountCapsule) {
    if (beginCycle >= endCycle) {
      return 0;
    }

    long reward = 0;
    long newAlgorithmCycle = dynamicPropertiesStore.getNewRewardAlgorithmEffectiveCycle();
    List<Pair<byte[], Long>> srAddresses = accountCapsule.getVotesList().stream()
        .map(vote -> new Pair<>(vote.getVoteAddress().toByteArray(), vote.getVoteCount()))
        .collect(Collectors.toList());
    if (beginCycle < newAlgorithmCycle) {
      long oldEndCycle = min(endCycle, newAlgorithmCycle,
          dynamicPropertiesStore.disableJavaLangMath());
      reward = getOldReward(beginCycle, oldEndCycle, srAddresses);
      beginCycle = oldEndCycle;
    }
    if (beginCycle < endCycle) {
      for (Pair<byte[], Long>  vote : srAddresses) {
        byte[] srAddress = vote.getKey();
        BigInteger beginVi = delegationStore.getWitnessVi(beginCycle - 1, srAddress);
        BigInteger endVi = delegationStore.getWitnessVi(endCycle - 1, srAddress);
        BigInteger deltaVi = endVi.subtract(beginVi);
        if (deltaVi.signum() <= 0) {
          continue;
        }
        long userVote = vote.getValue();
        reward += deltaVi.multiply(BigInteger.valueOf(userVote))
            .divide(DelegationStore.DECIMAL_OF_VI_REWARD).longValue();
      }
    }
    return reward;
  }

  public void accumulateWitnessVi(long cycle, byte[] address, long voteCount) {
    BigInteger preVi = getWitnessVi(cycle - 1, address);
    long reward = getReward(cycle, address);
    if (reward == 0 || voteCount == 0) { // Just forward pre vi
      if (!BigInteger.ZERO.equals(preVi)) { // Zero vi will not be record
        setWitnessVi(cycle, address, preVi);
      }
    } else { // Accumulate delta vi
      BigInteger deltaVi = BigInteger.valueOf(reward)
          .multiply(DECIMAL_OF_VI_REWARD)
          .divide(BigInteger.valueOf(voteCount));
      setWitnessVi(cycle, address, preVi.add(deltaVi));
    }
  }
