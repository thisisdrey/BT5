### Title
`UNFREEZE_DELAY_DAYS` governance parameter changes instantly and retroactively extends the lock-up applied to already-frozen balances - ([File: framework/src/main/java/org/tron/core/consensus/ProposalService.java])

### Summary
The `UNFREEZE_DELAY_DAYS` dynamic parameter, which determines how long a user's TRX stays locked after calling `UnfreezeBalanceV2`/`WithdrawExpireUnfreeze`, is applied immediately and globally as soon as a committee proposal is approved, with no grandfathering for balances that were already frozen under the previous (shorter) delay assumption. This mirrors the `overdueBlocks` finding: a protocol-controlled threshold that governs the terms of an already-existing user commitment can be changed instantly and retroactively degrades the terms the user agreed to when locking funds, with no timelock or migration path.

### Finding Description
When a user freezes TRX via `FreezeBalanceV2Contract`, they do so under the currently configured `UNFREEZE_DELAY_DAYS` value, expecting that once they later call `UnfreezeBalanceV2Contract` their funds will become withdrawable after that many days.

`UNFREEZE_DELAY_DAYS` is a standard committee-governed chain parameter, validated only for a static range (1-365 days) with no additional constraints or delay-before-effect logic beyond normal proposal processing: [1](#0-0) 

Once a proposal is approved, `ProposalService.process` immediately writes the new value via `saveUnfreezeDelayDays`, and also grants system-contract permission to `FreezeBalanceV2Contract`, `UnfreezeBalanceV2Contract`, `WithdrawExpireUnfreezeContract`, `DelegateResourceContract`, and `UnDelegateResourceContract` in the same step: [2](#0-1) 

The new value takes effect for any future unfreeze operation regardless of when the corresponding freeze happened. Specifically, `UnfreezeBalanceV2Actuator.calcUnfreezeExpireTime` (and the equivalent TVM-native `UnfreezeBalanceV2Processor.calcUnfreezeExpireTime`) reads the *current* `getUnfreezeDelayDays()` value at the moment the unfreeze transaction executes — not the value that was in effect when the balance was originally frozen: [3](#0-2) [4](#0-3) 

There is no timelock or notice period between proposal approval and the parameter taking effect beyond the ordinary maintenance-cycle processing performed by `ProposalController.processProposal`/`processProposals`, and there is no mechanism that "locks in" the delay a user saw at freeze time: [5](#0-4) 

This is structurally identical to the `overdueBlocks` issue: a threshold value that governs an existing, already-established position (frozen balance / a "loan" of resources) can be instantly changed by a privileged actor (the committee, analogous to the protocol owner) and applied retroactively to positions that were opened under different terms, with no grandfathering and no advance-warning mechanism for the affected party.

### Impact Explanation
A user who freezes TRX expecting a short unfreeze delay (e.g., `UNFREEZE_DELAY_DAYS = 1`) can have that value raised (up to 365) via committee proposal before they call unfreeze. When they then submit `UnfreezeBalanceV2Contract`, `calcUnfreezeExpireTime` computes the expiry using the new, much larger delay, locking their principal for far longer than they agreed to when they froze it. Because the increase is retroactive to already-frozen balances (there is no snapshot of the delay at freeze-time), this results in unexpectedly extended freezing of user funds — a direct funds-availability impact for TRX holders across the network, not merely a UX inconvenience.

### Likelihood Explanation
Triggering the harmful state requires only ordinary use of standard, unprivileged, broadcastable transactions (`FreezeBalanceV2Contract` then later `UnfreezeBalanceV2Contract`) combined with a normal governance proposal changing `UNFREEZE_DELAY_DAYS`, which is a supported and expected chain-parameter change path (used, e.g., to raise or lower the delay for legitimate operational reasons). No malicious committee behavior is required — the design simply lacks any decoupling between the delay value at freeze time and at unfreeze time, so any legitimate parameter adjustment can unintentionally and retroactively harm honest stakers who already froze balance.

### Recommendation
- Snapshot `UNFREEZE_DELAY_DAYS` at the time a balance is frozen (store it alongside the `FreezeV2` entry) and use that snapshot instead of the current global value when computing `calcUnfreezeExpireTime` for that balance, so changes only affect newly-frozen balances.
- Alternatively, introduce an effective-delay window for `UNFREEZE_DELAY_DAYS` proposals (e.g., apply the new value only to freezes created after the proposal's effective time), giving existing stakers a way to unfreeze under the previously agreed terms before the new delay applies.

### Proof of Concept
1. Committee approves a proposal setting `UNFREEZE_DELAY_DAYS = 1`. `ProposalService.process` calls `saveUnfreezeDelayDays(1)` [6](#0-5) .
2. A user broadcasts `FreezeBalanceV2Contract` to freeze TRX for bandwidth/energy, expecting a 1-day unfreeze delay once they decide to withdraw.
3. Before the user unfreezes, the committee approves another proposal raising `UNFREEZE_DELAY_DAYS` to 365; `ProposalController.processProposal` applies it at the next maintenance cycle with no separate notice period for existing frozen positions [7](#0-6) .
4. The user then broadcasts `UnfreezeBalanceV2Contract`. `UnfreezeBalanceV2Actuator.calcUnfreezeExpireTime` reads the now-current `getUnfreezeDelayDays()` (365) and computes `expireTime = now + 365 * FROZEN_PERIOD` [3](#0-2) , locking the user's principal for a full year instead of the 1 day they expected when they froze it.

  public void processProposals() {
    long latestProposalNum = manager.getDynamicPropertiesStore().getLatestProposalNum();
    if (latestProposalNum == 0) {
      logger.info("latestProposalNum is 0, return");
      return;
    }

    long proposalNum = latestProposalNum;

    ProposalCapsule proposalCapsule = null;

    while (proposalNum > 0) {
      try {
        proposalCapsule = manager.getProposalStore()
            .get(ProposalCapsule.calculateDbKey(proposalNum));
      } catch (Exception ex) {
        logger.error("", ex);
        proposalNum--;
        continue;
      }

      if (proposalCapsule.hasProcessed()) {
        logger
            .info("Proposal has processed, id:[{}], skip it and before it",
                proposalCapsule.getID());
        //proposals with number less than this one, have been processed before
        break;
      }

      if (proposalCapsule.hasCanceled()) {
        logger.info("Proposal has canceled, id:[{}], skip it", proposalCapsule.getID());
        proposalNum--;
        continue;
      }

      long currentTime = manager.getDynamicPropertiesStore().getNextMaintenanceTime();
      if (proposalCapsule.hasExpired(currentTime)) {
        processProposal(proposalCapsule);
        proposalNum--;
        continue;
      }

      proposalNum--;
      logger.info("Proposal has not expired, id:[{}], skip it", proposalCapsule.getID());
    }
    logger.info("Processing proposals done, oldest proposal[{}]", proposalNum);
  }
