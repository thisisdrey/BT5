Audit Report

## Title
Non-zero-value EVM calls with an explicit low `gas_limit` (e.g. the classic `call{value: x, gas: 2300}("")` anti-reentrancy pattern) are unconditionally granted `AllowReentry` and an unearned stipend in `pallet-revive`'s EVM interpreter - (File: `substrate/frame/revive/src/vm/evm/instructions/contract.rs`)

## Summary
`run_call` in `substrate/frame/revive/src/vm/evm/instructions/contract.rs` decides reentrancy protection via a match on `(value.is_zero(), gas_limit == CALL_STIPEND)`, and the `(false, _)` arm unconditionally returns `ReentrancyProtection::AllowReentry` regardless of the `gas_limit == CALL_STIPEND` check, which is only reachable when `value.is_zero()` is true. This means any non-zero-value call explicitly capped at the classic `gas: 2300` stipend by the calling contract — a widely used Solidity anti-reentrancy idiom — is misclassified as an unrestricted, fully-reentrant call, defeating the developer's intended protection. [1](#0-0) 

## Finding Description
The reentrancy classification logic is:
```rust
let (add_stipend, reentracy) =
    match (value.is_zero(), gas_limit.try_into().is_ok_and(|limit: u64| limit == CALL_STIPEND))
    {
        (false, _) => (true, ReentrancyProtection::AllowReentry),
        (_, true) => (true, ReentrancyProtection::AllowNext),
        (_, _) => (false, ReentrancyProtection::AllowReentry),
    };
``` [2](#0-1) 

Because Rust match arms are evaluated top-to-bottom and the first arm matches on `value.is_zero() == false` alone (using `_` for the gas condition), any non-zero-value call takes the `(false, _)` branch unconditionally — the `gas_limit == CALL_STIPEND` check is never evaluated for non-zero-value calls. This is confirmed directly in the code as retrieved from the repository. The PR documentation for the associated feature (`pr_10166.prdoc`) confirms `AllowNext` exists precisely to emulate Ethereum's 2300-gas stipend guarantee against reentrancy, and the companion PR (`pr_11227.prdoc`) confirms testing/hardening was performed only for the zero-value `transfer(0)`/`send(0)` compiler-injected pattern, not for manual non-zero-value `call{value: x, gas: 2300}("")` usage. [3](#0-2) [4](#0-3) 

The `call<E: Ext>` entrypoint pops `gas_limit`, `to`, and `value` from the stack and passes them straight into `run_call`, so a contract author's explicit choice of `gas: 2300` alongside `value != 0` is indistinguishable, in this code path, from a call that forwards unlimited remaining gas. [5](#0-4) 

## Impact Explanation
This is a genuine runtime logic bug in `pallet-revive`'s EVM-compatibility layer (in-scope: implementation bugs that compromise intended behavior). It defeats a well-known, still-used Solidity anti-reentrancy pattern for any deployed EVM-bytecode contract using `call{value: x, gas: 2300}("")`, enabling reentrant calls that the original contract logic assumed were blocked by the low gas cap. This can lead to draining of contract-held value beyond what the contract's internal accounting permits — matching the "theft or unbacked mint/unlock" impact bucket, reachable via ordinary, unprivileged contract-to-contract calls during normal transaction execution.

## Likelihood Explanation
High for any EVM contract deployed to `pallet-revive` using this idiom. No special privileges, validator/collator/relayer compromise, or governance action is required — the bug is deterministic and reproducible on every non-zero-value call regardless of caller-supplied `gas_limit`, triggered purely by ordinary EVM bytecode execution.

## Recommendation
Restructure the match in `run_call` so that the `gas_limit == CALL_STIPEND` check is evaluated independently of `value.is_zero()`. Any call — zero or non-zero value — whose `gas_limit` equals `CALL_STIPEND` should receive `ReentrancyProtection::AllowNext`; only calls forwarding materially more gas than the stipend should receive `AllowReentry`, restoring parity with the Ethereum-emulation intent documented in `pr_10166.prdoc`.

## Proof of Concept
1. Deploy a `Victim` EVM contract with `withdraw(uint amount)` that debits an internal balance then executes `(bool ok,) = msg.sender.call{value: amount, gas: 2300}("");`.
2. Deploy an `Attacker` contract whose `receive()` re-enters `Victim.withdraw(...)` before the outer call returns.
3. Call `Victim.withdraw()` from `Attacker`. Because `value != 0`, `run_call`'s match takes `(false, _)` → `ReentrancyProtection::AllowReentry`, ignoring the `gas: 2300` cap encoded in the bytecode. [6](#0-5) 
4. `Attacker`'s `receive()` successfully reenters `Victim.withdraw()` (unlike genuine Ethereum, where the 2300 stipend would make the nested call fail), permitting repeated withdrawals against a balance debited only once, draining more funds than `Attacker`'s recorded balance — analogous to, but not covered by, the existing `testTransferReentrancy`/`testSendReentrancy` fixtures which only exercise the zero-value path. [7](#0-6)

		interpreter.memory.slice(input).to_vec(),
		scheme,

		return_memory_range,
