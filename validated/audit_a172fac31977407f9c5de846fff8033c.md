### Title
Permanent per-repository housekeeping lock on handler panic causes irrecoverable DoS of maintenance RPCs - (File: `internal/grpc/middleware/housekeeping/middleware.go`)

### Summary
The report describes a state that is set (bad debt/seized share) and only cleared through a follow-up code path that is unreachable once a specific invariant becomes false, leaving the state stuck forever and permanently blocking legitimate future operations. The closest concrete, reachable-by-ordinary-user analog in Gitaly is the `Middleware.markHousekeepingActive` / `markHousekeepingInactive` lock in `internal/grpc/middleware/housekeeping/middleware.go`, which marks a repository "busy" before running an `OpMaintenance` RPC and only unmarks it via a *non-deferred* statement after the handler returns normally — never on panic.

### Finding Description
For `OpMaintenance` RPCs, both the unary and stream interceptors do: [1](#0-0) 

`m.markHousekeepingActive(key)` sets `activity.active = true` for the `repoKey{storage, relativePath}` before invoking `handler(ctx, req)`, and `m.markHousekeepingInactive(key)` clears it — but the clearing call is a plain statement, not wrapped in `defer`/`recover`. The same pattern exists in the stream interceptor: [2](#0-1) 

Gitaly installs a global panic-recovery interceptor that recovers any panic raised inside RPC handlers and converts it into an `Internal` gRPC error: [3](#0-2) 

Because the panic handler interceptor wraps (is outer to) the housekeeping middleware in the interceptor chain, a panic occurring inside the maintenance handler (e.g. `OptimizeRepositoryRepository`, `PackRefs`, or similar RPCs classified as `OpMaintenance`) unwinds the Go call stack straight through the housekeeping interceptor's stack frame, skipping the `m.markHousekeepingInactive(key)` call at line 172/247, and is only caught by the outer `panichandler` interceptor. The `active` flag for that specific `repoKey` is left `true` permanently, in-memory, for the remaining lifetime of the `gitaly` process. This is directly analogous to the report's core defect: an operation that transitions a resource into a state, but whose invariant/guard (`isActive`) can never be reset back to a safe value through the normal code path once a certain codepath is taken, permanently blocking legitimate subsequent operations gated by that same check (`removeCollateralTo` reverting on `share == 0` in the original report ≈ `isActive(key)` returning `true` forever here).

### Impact Explanation
Every subsequent `OpMaintenance` RPC for the affected repository will be rejected with `AlreadyExists("housekeeping already executing for repository")` [4](#0-3)  — a permanent, repo-scoped denial of service for maintenance operations (repack/gc-class RPCs) that can only be cleared by restarting the Gitaly process (which reinitializes `repoActivity` in `NewHousekeepingMiddleware`) [5](#0-4) . Repositories that never get housekeeping performed accumulate loose objects/unpacked refs indefinitely, degrading performance and disk usage over time, mirroring how the original bug's unresolved bad debt permanently corrupted protocol-level accounting and blocked further legitimate actions.

### Likelihood Explanation
Triggering requires only that an ordinary, otherwise-authorized RPC classified as `OpMaintenance` panics while processing a request for a given repository — this is plausible via a malformed/edge-case request field that hits an unhandled nil-dereference or index-out-of-range in the underlying housekeeping manager code, without requiring any privileged actor, leaked token, or malicious peer. Because the resulting `Internal` panic error is caught and converted to a normal gRPC error by `panichandler`, the crash itself is silent to the operator and easy to overlook, while the per-repo lock persists indefinitely, and each subsequent client attempt to run maintenance on that repository will fail deterministically.

### Recommendation
Wrap `m.markHousekeepingInactive(key)` in a `defer` immediately after `m.markHousekeepingActive(key)` succeeds (both in `UnaryServerInterceptor` and `StreamServerInterceptor`), so the active flag is cleared unconditionally regardless of whether the handler returns normally, returns an error, or panics.

### Proof of Concept
1. Send a crafted `OpMaintenance`-classified RPC (e.g. an `OptimizeRepository`/maintenance-class request) for a target repository, engineered to reach a code path in `manager.Manager` that panics (e.g. via a malformed but syntactically valid message field causing a nil dereference deep in the housekeeping manager).
2. Observe: the client receives `codes.Internal` (from `panichandler`), but `repoActivity[key].active` remains `true` because `markHousekeepingInactive` at line 172/247 was never reached.
3. Immediately retry a normal, well-formed `OpMaintenance` RPC against the same repository: it is rejected with `AlreadyExists("housekeeping already executing for repository")`.
4. Repeat step 3 indefinitely — the repository is permanently locked out of maintenance until the Gitaly process is restarted.

// UnaryPanicHandler creates a new unary server interceptor that handles panics.
func UnaryPanicHandler(logger log.Logger) grpc.UnaryServerInterceptor {
	return func(ctx context.Context, req interface{}, info *grpc.UnaryServerInfo, handler grpc.UnaryHandler) (resp interface{}, err error) {
		defer handleCrash(logger, info.FullMethod, func(grpcMethodName string, r interface{}) {
			err = toPanicError(grpcMethodName, r)
		})

		return handler(ctx, req)
	}
}
