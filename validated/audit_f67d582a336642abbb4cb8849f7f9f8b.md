### Title
`extend_with_attachments` rewards `ReliabilityReport.bump_successful_requests()` for any well-formed but content-hash-mismatched attachment response - ([File: stackslib/src/net/atlas/download.rs])

### Summary
`AttachmentsBatchStateContext::extend_with_attachments` (download.rs:530-558) only checks that a peer's HTTP response deserializes via `decode_atlas_get_attachment()`; it never compares `response.attachment.hash()` against the requested `AttachmentRequest::content_hash` before calling `report.bump_successful_requests()` and inserting the attachment into `self.attachments`. This lets a remote, unprivileged peer inflate its `ReliabilityReport` score by returning syntactically valid, but wrong-content, attachments.

### Finding Description
In `extend_with_attachments`:
```rust
if let Ok(response) = response.decode_atlas_get_attachment() {
    self.attachments.insert(response.attachment);
    report.bump_successful_requests();
} else {
    report.bump_failed_requests();
}
``` [1](#0-0) 

The success/failure classification is based solely on whether `decode_atlas_get_attachment()` (which just parses JSON into a `GetAttachmentResponse`, see `stackslib/src/net/api/getattachment.rs:159-165`) succeeds — it does not verify `response.attachment.hash() == request.content_hash`. Any peer that returns a well-formed JSON body containing arbitrary (non-matching) attachment content will still cause `report.bump_successful_requests()` to fire.

`ReliabilityReport.score()` is used both by `AttachmentRequest::get_most_reliable_source` (download.rs:1074-1079) and by `Ord for AttachmentRequest`/`AttachmentsInventoryRequest` (download.rs:1088-1096, 1016-1020) to prioritize which peer's URL is queried next for a given `content_hash`. Because the score is derived from a success counter that is decoupled from actual hash correctness, a peer that always serves wrong-but-parseable attachments accrues the same score growth as a peer serving correct data, and will be preferentially selected by `get_most_reliable_source` for future requests targeting the same or other content hashes.

I was unable to fully trace what happens to `self.attachments` after being inserted into the `HashSet`/collection at line 548 (e.g., whether a downstream validation step in the state machine, such as the `Done` state transition or the code that persists into the Atlas DB, subsequently re-checks `attachment.hash() == content_hash` before storing to `AtlasDB`). This is a meaningful gap in the trace: if such downstream validation exists and rejects mismatched attachments before they are relayed or persisted as canonical, the primary damage is limited to reliability-score poisoning (steering future requests to a bad peer, wasting round-trips) rather than actual corruption of stored attachment data. The question, as scoped, is specifically about the `ReliabilityReport`/`Ord` selection logic at download.rs:547-552 and 1074-1079, which is confirmed unguarded by a hash-equality check.

### Impact Explanation
A remote unprivileged peer that answers every `/v2/attachments/<hash>` GET request with a syntactically valid `GetAttachmentResponse` body — regardless of whether the contained attachment's hash matches — will have its `ReliabilityReport` score climb identically to a peer serving correct data. Since `Ord` for `AttachmentRequest` and `AttachmentsInventoryRequest` directly depend on this score to rank sources (download.rs:1088-1096, 1016-1020), and `get_most_reliable_source` (download.rs:1074-1079) selects based on `max_by_key(|(_, v)| v.score())`, the node's download scheduler will increasingly prefer this malicious peer for attachment resolution. This degrades attachment/BNS resolution correctness for future requests, matching the "attachment/BNS mismatch" High-impact category described in scope, contingent on whatever downstream check (unverified here) does or does not exist before an attachment is treated as canonical/stored.

### Likelihood Explanation
The attacker only needs to run an ordinary Atlas-capable peer reachable over the node's HTTP/P2P attachment-fetch endpoint and answer `GET /v2/attachments/<hash>` with any well-formed JSON `{"attachment": {...}}` payload — no secret, signature, or privileged role is required, and the interaction is fully repeatable per request/response cycle within the batched attachment-download state machine (`BatchedRequestsState`/`AttachmentsBatchStateMachine`, download.rs:562-618).

### Recommendation
In `extend_with_attachments` (download.rs:547-552), after `decode_atlas_get_attachment()` succeeds, compare `response.attachment.hash() == request.content_hash` before calling `bump_successful_requests()`; call `bump_failed_requests()` (and optionally treat the peer as faulty) on mismatch instead of crediting the peer's reliability score.

### Proof of Concept
Add a test in `stackslib/src/net/atlas/tests.rs` that:
1. Constructs an `AttachmentRequest` with a known `content_hash`.
2. Builds a `BatchedRequestsResult` whose `succeeded` map contains a `StacksHttpResponse` decodable via `decode_atlas_get_attachment()` but whose `GetAttachmentResponse.attachment.content` hashes to a different value than `content_hash`.
3. Calls `AttachmentsBatchStateContext::extend_with_attachments` on this result.
4. Asserts `report.score()` (via `peers.get(url)`) is identical to the score obtained from a control response containing the correctly-hashed attachment — demonstrating `bump_successful_requests()` fires in both cases despite the hash mismatch, i.e., `report.score()` after N mismatched-but-well-formed responses == `report.score()` after N correctly-matching responses.
