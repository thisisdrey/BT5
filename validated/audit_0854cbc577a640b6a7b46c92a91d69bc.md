### Title
`DynamicPacketToProcessThreshold` can be driven to an unrecoverable `max_packets == 0` absorbing state, permanently forcing `should_drop()` to true - (File: `core/src/repair/packet_threshold.rs`)

### Summary
`PacketThresholdUpdate::calculate` uses integer arithmetic (`saturating_mul(90)/100` for decrease, `saturating_mul(100)/90` for increase) with no floor, so repeated `Decrease` calls can round `max_packets` down to `0`, and once at `0` the `Increase` branch (`0*100/90=0`) can never recover it. From that point `should_drop(total)` returns `true` for every `total >= 0`, i.e. for all future traffic, since `update()` and `should_drop()` treat `0` as a normal threshold with no minimum-bound guard.

### Finding Description
`PacketThresholdUpdate::calculate` at `core/src/repair/packet_threshold.rs:11-20` computes `current * 90 / 100` (Decrease) or `current * 100 / 90` (Increase) with plain integer division and no lower bound. `DynamicPacketToProcessThreshold::update` at `core/src/repair/packet_threshold.rs:40-49` only decreases when `total_packets >= self.max_packets` **and** `compute_time > TIME_THRESHOLD` (1s), and increases otherwise, but it never enforces `max_packets >= 1`. `should_drop` at `core/src/repair/packet_threshold.rs:51-53` is `total >= self.max_packets`, so once `max_packets == 0`, `should_drop` returns `true` unconditionally, since any `total_packets` (including `0`) satisfies `total >= 0`.

Because `total_packets >= self.max_packets` is trivially true when `max_packets == 0`, `update()` will keep re-evaluating the compute-time comparison forever; but `Increase.calculate(0) = 0*100/90 = 0` (integer division), so the threshold can never leave `0` even under fast, benign processing conditions. This is an absorbing state with no recovery path in the code as written.

This struct is instantiated per-service in `core/src/repair/block_id_repair_service.rs:341` (`throttle = DynamicPacketToProcessThreshold::default()`) and used to gate processing of packets arriving on the block-id repair response socket (`process_responses`, `core/src/repair/block_id_repair_service.rs:479-528`), and similarly in `core/src/repair/ancestor_hashes_service.rs`. `throttle.update(total_packets, compute_timer.elapsed())` is called with real wall-clock compute time of processing a batch of attacker-influenced response packets [1](#0-0) , and `throttle.should_drop(total_packets)` gates whether additional batches are processed or silently dropped [2](#0-1) . ### Impact Explanation
If `max_packets` ever reaches `0`, the throttle enters a permanently broken state: `should_drop` returns `true` for any input, so all subsequent block-id / ancestor-hash repair response processing is silently dropped for the lifetime of the process, requiring a validator restart to recover (the in-memory `DynamicPacketToProcessThreshold` is not persisted or reset elsewhere). This matches a liveness/availability bug in the repair pipeline (permanent silent denial of repair-response processing), not a memory-safety or consensus-safety bug.

### Likelihood Explanation
Reaching `max_packets == 0` from the default `1024` requires roughly 65 consecutive `update()` calls where `total_packets >= max_packets` **and** `compute_time > 1s` for the batch being processed. In the actual call site, per-packet processing on the block-id-repair path is cheap (wincode deserialization plus a nonce hashmap lookup in `process_block_id_repair_response`); an attacker sending unsolicited/garbage UDP packets without a valid nonce hits the cheap "invalid nonce" rejection path, not the expensive merkle-proof verification path, making it hard to sustain >1s of compute time per batch purely from spam packets. The question's precondition ("sustaining compute_time > TIME_THRESHOLD across many update() calls") is therefore a strong, not-obviously-attacker-achievable assumption via this exact reachable path; the logic bug itself (absorbing state at 0, unbounded by design) is real and file/function-confirmed independent of that reachability question.

### Recommendation
Add a minimum floor (e.g. `max_packets = current.max(MIN_PACKETS)` after each update, with `MIN_PACKETS >= 1`) so the threshold can never reach `0`, and/or special-case `Increase.calculate` to ensure `0` maps to some positive minimum rather than staying at `0`.

### Proof of Concept
```rust
// core/src/repair/packet_threshold.rs (added to #[cfg(test)] mod test)
#[test]
fn test_threshold_can_get_stuck_at_zero() {
    let mut threshold = DynamicPacketToProcessThreshold::default();
    let slow = Duration::from_secs(2); // > TIME_THRESHOLD

    // Repeatedly decrease: total_packets kept >= current max_packets, compute_time slow.
    for _ in 0..200 {
        let total = threshold.max_packets; // satisfies total_packets >= max_packets
        threshold.update(total, slow);
        if threshold.max_packets == 0 {
            break;
        }
    }
    assert_eq!(threshold.max_packets, 0, "threshold reached absorbing zero state");

    // Now even fast/benign processing cannot recover it.
    let fast = Duration::from_millis(1);
    threshold.update(0, fast); // Increase branch: 0*100/90 = 0
    assert_eq!(threshold.max_packets, 0, "threshold permanently stuck at zero");

    // should_drop now rejects everything, including empty/legit batches.
    assert!(threshold.should_drop(0));
    assert!(threshold.should_drop(1));
}
```
This test directly exercises `DynamicPacketToProcessThreshold::update`/`should_drop` and demonstrates the absorbing-zero liveness bug; it does not by itself prove the full remote-exploitability chain through `block_id_repair_service.rs`, which depends on sustaining >1s compute time per batch from the socket-receive path.

    pub fn update(&mut self, total_packets: usize, compute_time: Duration) {
        if total_packets >= self.max_packets {
            let threshold_update = if compute_time > Self::TIME_THRESHOLD {
                PacketThresholdUpdate::Decrease
            } else {
                PacketThresholdUpdate::Increase
            };
            self.max_packets = threshold_update.calculate(self.max_packets);
        }
    }

    pub fn should_drop(&self, total: usize) -> bool {
