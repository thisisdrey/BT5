### Title
Verbose internal error disclosure via `TriggerSmartContract`/`EstimateEnergy` responses (gRPC and HTTP) — (File: framework/src/main/java/org/tron/core/services/RpcApiService.java)

### Summary
Any unauthenticated caller invoking `triggerconstantcontract`, `estimateenergy`, or the gRPC `triggerContract`/`triggerConstantContract`/`estimateEnergy` RPCs can trigger an unexpected `RuntimeException`/`Exception` from the TVM execution path. The catch blocks embed the raw Java exception's fully-qualified class name and `getMessage()` text directly into the `Return.message` field of the response returned to the caller, disclosing internal implementation details (exception types, internal state, and sometimes library/stack-derived text) analogous to CVE-2020-10097's verbose-error disclosure class.

### Finding Description
In `RpcApiService.callContract` and `RpcApiService.WalletApi.estimateEnergy`, the generic exception handlers build the response message as `e.getClass() + " : " + e.getMessage()`: [1](#0-0) [2](#0-1) 

The same pattern is present in the HTTP counterparts `TriggerConstantContractServlet` and `EstimateEnergyServlet`, which also concatenate `e.getClass() + " : " + errString` into the JSON response body served to any HTTP client: [3](#0-2) [4](#0-3) 

`Wallet` helper methods used for shielded-contract queries follow the identical pattern (`e.getClass() + " : " + e.getMessage()`), further widening the surface: [5](#0-4) [6](#0-5) 

By contrast, several other API paths in the codebase have already been deliberately hardened to avoid leaking internals — e.g., `Util.processError`/`Util.printErrorMsg` log the exception server-side but return sanitized messages, `JsonRpcServlet.handleSingle` maps unexpected `RuntimeException`s to a generic "Internal error", and `HttpService.OversizedRequestErrorHandler` explicitly notes it avoids "the default error page that leaks the exception stack and internal request sizes": [7](#0-6) [8](#0-7) [9](#0-8) 

This shows the project's own security posture treats raw exception-class/message leakage as something to avoid — the `triggerContract`/`estimateEnergy`/`TriggerConstantContractServlet`/`EstimateEnergyServlet`/shielded-query paths are inconsistent stragglers that still leak `Throwable.getClass()` (fully-qualified internal class name, e.g. package-qualified custom exception types or JDK exception types such as `NullPointerException`, `ArrayIndexOutOfBoundsException`) plus the raw message, both attacker-observable and reachable with a single unsigned, unauthenticated smart-contract-call-style request (no broadcast/signature required).

### Impact Explanation
This is an information-disclosure issue, not a fund-theft or consensus issue: it reveals internal class names/package structure and raw exception text of the TVM/actuator internals to any caller, which can help an attacker fingerprint the node's internal code paths (e.g., distinguishing VM internal errors, database/store exceptions, or NPEs) to craft more targeted follow-on exploits — directly matching the CVE-2020-10097 bug class ("verbose error messages that disclose internal application or infrastructure information ... could aid attackers in successfully exploiting other vulnerabilities").

### Likelihood Explanation
High likelihood of triggering: `triggerconstantcontract`/`estimateenergy` and their gRPC equivalents are unauthenticated, free (constant-call), and reachable by any client; malformed contract addresses, malformed call data, or edge-case VM state easily trigger `RuntimeException`s (NPEs, `ArrayIndexOutOfBoundsException`, `IllegalStateException`, etc.) inside `VMActuator`/`Program`, which then propagate the class+message straight back to the caller.

### Recommendation
Sanitize these catch blocks the same way `Util.processError`/`JsonRpcServlet` already do elsewhere: log the full exception with `e.getClass()`/`getMessage()`/stack trace server-side only, and return a generic, non-identifying error string (e.g., "internal error") to the caller for the `RuntimeException`/`Exception` branches in `RpcApiService.callContract`, `RpcApiService.WalletApi.estimateEnergy`, `TriggerConstantContractServlet`, `EstimateEnergyServlet`, and the shielded-contract helper methods in `Wallet.java`.

### Proof of Concept
1. Call the HTTP API `POST /wallet/triggerconstantcontract` (or gRPC `triggerConstantContract`) with a `contract_address` that is a valid smart contract but with `data`/`function_selector` crafted to cause the TVM to throw an unexpected `RuntimeException` (e.g., malformed ABI decode causing an internal NPE/ArrayIndexOutOfBoundsException deep in `VMActuator`/opcode handling) rather than a normal revert.
2. Observe the JSON/gRPC response's `result.message` field contains `<FullyQualifiedExceptionClassName> : <raw message>`, e.g. `java.lang.NullPointerException : null` or an internal `org.tron.core.vm...` class name, confirming disclosure of internal implementation details to an unauthenticated caller.
