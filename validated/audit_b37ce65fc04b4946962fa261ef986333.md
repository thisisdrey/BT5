### Title
`PeerAddress::is_in_private_range` fails to classify the IPv6 unspecified address `::` as private, letting a peer-advertised URL steer outbound requests to the local host - (File: `stacks-common/src/types/net.rs`)

### Summary
`PeerAddress::is_in_private_range` is the sole gate that decides whether a resolved peer/data-URL address is "routable" enough for the node to contact when private-neighbor connections are disabled. Its IPv6 branch only flags `fc00::/7` and the loopback address `::1` as private, but never checks for the unspecified address `::` (all-zero bytes). This is the exact bug class described in GHSA-v9mp-j8g7-2q6m/CVE-2023-24623 (paranoidhttp): `[::]` is treated by most OS network stacks equivalently to a loopback/any-address target, but the filter doesn't recognize it as private.

### Finding Description
`is_in_private_range` checks are:
```
stacks-common/src/types/net.rs:201-213
pub fn is_in_private_range(&self) -> bool {
    if self.is_ipv4() {
        self.0[12] == 10 || (...) || self.0[12] == 127
    } else {
        // private address (fc00::/7) or localhost (::1)
        self.0[0] >= 0xfc || (self.0[0..15] == [0u8; 15] && self.0[15] == 1)
    }
}
```
`::` is `[0u8; 16]`, so `self.0[0] >= 0xfc` is false and `self.0[15] == 1` is also false (last byte is 0). This means `is_in_private_range()` returns `false` for `::`, exactly mirroring the paranoidhttp flaw where `[::]` slipped past the private-address filter. Note that a *different*, unrelated helper, `is_anynet`, does detect `[0x00;16]`, but that helper is not used at any of the call sites that gate outbound network requests.

This filter is consulted before the node performs an outbound HTTP request to a peer-supplied data URL during mempool sync:
```
stackslib/src/net/mempool/mod.rs:485-498
MempoolSyncState::SendQuery(ref url, ref addr, ref page_id) => {
    if !network.get_connection_opts().private_neighbors
        && PeerAddress::from_socketaddr(addr).is_in_private_range()
    {
        ... skip, private IP ...
    }
    ...
    self.mempool_sync_send_query(network, url, addr, mempool, page_id.clone())
```
and again as the sole "unroutable" filter for accepting/dialing a neighbor connection:
```
stackslib/src/net/p2p.rs:1917-1924
// unroutable?
if !self.connection_opts.private_neighbors && neighbor_key.addrbytes.is_in_private_range() {
    ...
    return Err(net_error::Denied);
}
```
The `addr`/`neighbor_key.addrbytes` values are derived from data supplied by the remote party (a peer's advertised `data_url`, resolved via `dns.rs`'s `resolve()` which just calls `to_socket_addrs()`, or directly parsed as a literal IPv6 host in `chat.rs`'s `try_decode_data_url_ipaddr`). A remote peer that advertises `http://[::]:<port>/...` as its `data_url` supplies an address that resolves to the unspecified IPv6 address, bypasses the private-range check, and causes the local node to originate an outbound TCP connection/HTTP request to `[::]:<port>`. On most OS network stacks, connecting to the unspecified address `::` is treated equivalently to connecting to `::1` (loopback), so the node's own outbound query gets redirected to a service listening on its own loopback interface (e.g., another local port the operator did not intend to expose to the P2P network, or the node's own RPC server) — the classic SSRF pattern from the referenced advisory.

### Impact Explanation
This lets a single malicious/compromised peer, with no further privilege, cause a Stacks node to send outbound requests (mempool-sync HTTP `GET`/`POST`, or a p2p handshake attempt) to `localhost`/loopback services on the victim node's own host, i.e., a Server-Side Request Forgery against the node operator's private/loopback surface. This falls in the "High" impact bucket the rubric allows for read-endpoint / mismatch-style issues that reach through a validated address filter, though the exact blast radius depends on what else is listening on loopback (could range from information disclosure of local-only RPC responses to disrupting the node's mempool-sync/peer bookkeeping state).

### Likelihood Explanation
Likelihood is moderate-to-high in principle: it requires only that a peer's `data_url` or IPv6 host literal be `[::]` (or resolve to it) and that `connection_opts.private_neighbors` is `false` (the intended "reject private/unroutable peers" mode). Any peer participating in gossip/mempool-sync can supply this. However, I could not fully verify from the excerpted code (index limits) whether upstream URL-parsing / socket-connect code elsewhere additionally rejects the unspecified address before `is_in_private_range` is consulted, or whether the runtime's `connect()` behavior with `::` reliably yields a loopback connection across the target platforms Stacks nodes run on (this OS-level behavior is what the CVE assumes but is not something visible in this repo).

### Recommendation
Extend `PeerAddress::is_in_private_range` (or add a dedicated check called at every gating site) to also treat the unspecified/any address (`0.0.0.0` / `::`, i.e., what `is_anynet()` already detects) as non-routable/private, and ensure that check is invoked alongside `is_in_private_range()` wherever peer- or DNS-resolved addresses gate outbound connections (`stackslib/src/net/mempool/mod.rs:488-490`, `stackslib/src/net/p2p.rs:1918`, and any other call site using this address as a dial target).

### Proof of Concept
1. Run a malicious Stacks peer that advertises a `data_url` (or neighbor handshake `PeerAddress`) resolving to `[::]:<port>`, e.g. via a literal IPv6 host `http://[::]:20443/v2/...`.
2. Connect this malicious peer to a target node configured with `private_neighbors = false`.
3. Have the target node initiate mempool sync against this peer: `mempool_sync_pick_outbound_peer` → `mempool_sync_send_query` reaches the `SendQuery` state in `stackslib/src/net/mempool/mod.rs:485-498`; `PeerAddress::from_socketaddr(&addr).is_in_private_range()` evaluates `false` for `[::]`, so the private-IP skip does not trigger.
4. The node calls `mempool_sync_send_query`, which opens an outbound TCP/HTTP connection to `[::]:<port>` — on most OSes this routes to the node's own loopback interface, letting the attacker-controlled peer redirect the victim's own outbound request to a local service.
