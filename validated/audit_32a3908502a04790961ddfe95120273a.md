### Title
Truncating division-then-multiplication in standby witness reward distribution causes permanent, per-block loss of staking yield - (File: `chainbase/src/main/java/org/tron/core/service/MortgageService.java`)

### Summary
`MortgageService.payStandbyWitness()` computes a per-vote reward rate by dividing the fixed reward pool by the total vote count, and then multiplies that rate back out per witness, truncating to `long` on every multiplication. This is the exact "divide-then-multiply" precision-loss pattern from the reported LockingMultiRewards bug, except it is invoked on every single applied block rather than once per epoch, making the systemic loss of stake-holder yield permanent and continuously compounding rather than a one-off rounding error.

### Finding Description
`payStandbyWitness()` first computes a floating-point per-vote rate and then truncates the per-witness payout: [1](#0-0) 

```
long totalPay = dynamicPropertiesStore.getWitness127PayPerBlock();
double eachVotePay = (double) totalPay / voteSum;
for (WitnessCapsule w : witnessStandbys) {
  long pay = (long) (w.getVoteCount() * eachVotePay);
  payReward(w.getAddress().toByteArray(), pay);
}
```

Because `totalPay` is divided by `voteSum` *before* being multiplied back by each witness's `voteCount`, and the result is truncated (`(long)` cast) for each of up to 127 standby witnesses, the sum of all distributed `pay` values is systematically less than `totalPay`. The undistributed remainder is never credited to any account — it is simply discarded every time this function runs.

The same divide-then-truncate pattern also exists in the brokerage split immediately below, in `payReward()`: [2](#0-1) 

and in the legacy/disabled path `IncentiveManager.reward()`: [3](#0-2) 

Crucially, unlike the original report where the precision loss happens once per reward-notification epoch (e.g., weekly), `payStandbyWitness()` is invoked unconditionally on **every produced block** via `Manager.payReward()`, which is called from `processBlock()`/`applyBlock()`: [4](#0-3) 

```
if (getDynamicPropertiesStore().allowChangeDelegation()) {
  mortgageService.payBlockReward(...);
  mortgageService.payStandbyWitness();
  ...
```

Since `processBlock` runs for every block during normal chain-application (including forward sync and fork switching), the reward pool `getWitness127PayPerBlock()` (default 16,000,000 sun) is divided by `voteSum` (often in the range of billions of votes) and re-multiplied per witness with `(long)` truncation on every single block — an unattended, unrecoverable leak that runs at block-production frequency (~once every 3 seconds) rather than the weekly cadence assumed acceptable by the original report.

### Impact Explanation
Every applied block permanently drops a fraction of the `WITNESS_127_PAY_PER_BLOCK` allocation that should have been distributed pro-rata to standby witnesses (and, transitively, to the TRX holders who voted for and receive brokerage from them). Because this runs at block cadence instead of epoch cadence, the aggregate lost yield accrues far more frequently than in the referenced report, and the loss is unrecoverable — the truncated remainder is never accounted for or credited anywhere, constituting a permanent loss of staking yield for standby-witness voters network-wide.

### Likelihood Explanation
This code path executes unconditionally on every block once `allowChangeDelegation` is active (the standard reward-distribution mode on production TRON networks), requiring no attacker action, special transaction, or privileged role — it is a guaranteed, deterministic side effect of ordinary block application reachable purely through normal chain operation.

### Recommendation
Avoid dividing the reward pool before multiplying it back out. Instead, compute each witness's share directly as `totalPay * voteCount / voteSum` using integer/BigInteger arithmetic (multiply first, divide last, as already done correctly for the `Vi`-based reward accumulation in `RewardViCalService.accumulateWitnessVi` and `MortgageService.computeReward`), and explicitly track/carry forward any remainder instead of discarding it silently.

### Proof of Concept
1. Enable `allowChangeDelegation` (standard reward mode).
2. Observe `payStandbyWitness()` executing at every block via `Manager.payReward()`.
3. With `totalPay = 16000000` and `voteSum` in the order of tens of billions (realistic mainnet vote totals across 127 standby witnesses), `eachVotePay = totalPay / voteSum` loses fractional precision; multiplying back per witness and truncating with `(long)` causes `sum(pay) < totalPay` on essentially every block, as also demonstrated by the existing test `DelegationServiceTest.testPay`, which independently recomputes the same truncated double-based formula to match expected values, confirming the truncation is inherent to the production code path rather than a test artifact: [5](#0-4)
