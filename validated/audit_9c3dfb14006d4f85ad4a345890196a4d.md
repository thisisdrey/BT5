### Title
Unauthenticated stage-1 handshake can trigger a local-index allocation that collides with an existing pending/main hostinfo, silently discarding the legitimate handshake attempt - (File: `handshake_manager.go`)

### Summary
`beginHandshake()` allocates the responder's local handshake index directly via `generateIndex(f.l)`, bypassing the collision-checked `hm.allocateIndex()` path used by the initiator side (`buildStage0Packet`). The uniqueness of that index against the pending-handshake map (`hm.indexes`) and the main hostmap (`hm.mainHostMap.Indexes`) is only checked afterward, inside `CheckAndComplete()`. If a collision is detected there, `handleCheckAndCompleteError` for `ErrLocalIndexCollision` only logs an error and returns — the in-flight responder-side hostinfo is dropped with no response ever sent to the real initiator, and no retry/backoff correction is attempted for that hostinfo.

### Finding Description
`generateIndex()` produces a random 32-bit non-zero value with no visibility into currently-in-use indexes: [1](#0-0) 

The initiator-side allocation path (`buildStage0Packet`) instead goes through `hm.allocateIndex(hh)`, which explicitly loops and checks both `hm.indexes` (pending) and `hm.mainHostMap.Indexes` (main) for a free slot before committing: [2](#0-1) [3](#0-2) 

But the responder-side path, reached by any unauthenticated peer sending an unsolicited stage-1 handshake packet (`HandleIncoming` → `beginHandshake`, reachable pre-certificate-verification since the packet's certificate is only validated as part of the same `machine.ProcessPacket` call that also triggers the `IndexAllocator` callback), allocates its local index with the raw, uncoordinated `generateIndex(f.l)`: [4](#0-3) 

Only later, when the resulting `HostInfo` is committed via `CheckAndComplete`, is the index actually checked for collisions against the pending and main hostmaps: [5](#0-4) 

If a collision is found, the entire handshake attempt is abandoned with only a log message — no handshake response is sent back to the initiator, and the hostinfo built for the incoming packet is discarded outright: [6](#0-5) [7](#0-6) 

This mirrors the external report's bug class: an operation that should only succeed with a fresh, uniquely-checked identifier is instead executed against an identifier resource whose uniqueness is validated too late, and a conflict causes the entire attempt to be discarded (analogous to the reverting `try/catch` around `createProxyWithNonce` failing when a nonce/address was already claimed). Here, the "counterpart" that gets silently blocked is the legitimate peer's handshake completion.

### Impact Explanation
Impact is limited primarily by the astronomically low a-priori collision probability of a uniformly random 32-bit value (~1/2^32 per attempt) against the (typically small) set of concurrently pending/established local indexes on a given node. A remote, uncertified attacker cannot directly choose or predict the value `generateIndex` will produce for a victim's responder-side handshake, so this cannot be turned into a reliable, on-demand DoS primitive comparable to the deterministic CREATE2-address prediction in the original report. The most this yields is: (a) a latent correctness/robustness gap where the responder path does not use the same collision-checked allocator as the initiator path, and (b) in the rare event of a genuine collision (e.g., under high churn/index pressure, or via other bugs that shrink the effective index space), a legitimate handshake attempt is silently dropped rather than retried, and the peer must wait for its own retransmit/timeout logic to try again.

### Likelihood Explanation
Low. Exploiting this deterministically would require the attacker to force `generateIndex()` (backed by `crypto/rand`) to produce a value already in use, which is not currently controllable from the network. It would only be observed as an intermittent/racy defect, not a targeted, repeatable attack an unauthenticated peer can trigger at will.

### Recommendation
Route the responder-side index allocation in `beginHandshake` through the same collision-checked allocator used by `buildStage0Packet` (i.e., `hm.allocateIndex`), so uniqueness against `hm.indexes` and `hm.mainHostMap.Indexes` is enforced at allocation time rather than discovered afterward in `CheckAndComplete`. Additionally, when `ErrLocalIndexCollision` is encountered for an inbound handshake, retry with a freshly generated index instead of unconditionally discarding the attempt, so a legitimate peer's handshake is not silently dropped.

### Proof of Concept
Not concretely reproducible against an unauthenticated peer with today's `crypto/rand`-backed `generateIndex`: no method was found in the reachable code paths that lets a certificate-less attacker choose or predict the 32-bit index value assigned by `beginHandshake`, so a deterministic PoC analogous to the original report's CREATE2 address prediction could not be constructed from the available code. This is a structural code-path gap (missing collision check at allocation time) rather than a demonstrated exploitable collision.

// allocateIndex generates a unique localIndexId for this HostInfo
// and adds it to the pendingHostMap. Will error if we are unable to generate
// a unique localIndexId
func (hm *HandshakeManager) allocateIndex(hh *HandshakeHostInfo) (uint32, error) {
	hm.mainHostMap.RLock()
	defer hm.mainHostMap.RUnlock()
	hm.Lock()
	defer hm.Unlock()

	for range 32 {
		index, err := generateIndex(hm.l)
		if err != nil {
			return 0, err
		}

		_, inPending := hm.indexes[index]
		_, inMain := hm.mainHostMap.Indexes[index]

		if !inMain && !inPending {
			hh.hostinfo.localIndexId = index
			hm.indexes[index] = hh
			return index, nil
		}
	}

	return 0, errors.New("failed to generate unique localIndexId")
}

func generateIndex(l *slog.Logger) (uint32, error) {
	b := make([]byte, 4)

	// Let zero mean we don't know the ID, so don't generate zero
	var index uint32
	for index == 0 {
		_, err := rand.Read(b)
		if err != nil {
			l.Error("Failed to generate index", "error", err)
			return 0, err
		}

		index = binary.BigEndian.Uint32(b)
	}

	if l.Enabled(context.Background(), slog.LevelDebug) {
		l.Debug("Generated index", "index", index)
	}
	return index, nil
}

// beginHandshake handles an incoming handshake packet that doesn't match any
// existing pending handshake. It creates a new responder Machine and processes
// the first message.
func (hm *HandshakeManager) beginHandshake(via ViaSender, packet []byte, h *header.H) {
	f := hm.f
	cs := f.pki.getCertState()

	v := cs.DefaultVersion()
	if cs.GetCredential(v) == nil {
		f.l.Error("Unable to handshake with host because no certificate is available",
			"from", via, "certVersion", v)
		return
	}

	machine, err := handshake.NewMachine(
		v, cs.GetCredential,
		hm.certVerifier(), func() (uint32, error) { return generateIndex(f.l) },
		false, header.HandshakeIXPSK0,
	)
	if err != nil {
		f.l.Error("Failed to create handshake machine", "from", via, "error", err)
		return
	}

	response, result, err := machine.ProcessPacket(nil, packet)
	if err != nil {
		f.l.Error("Failed to process handshake packet", "from", via, "error", err)
		return
	}
