Audit Report

## Title
`process_delivery_receipt` pays the full relayer reward without checking the Ethereum-side `success` flag - ([File: bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs])

## Summary
`process_delivery_receipt` decodes a `DeliveryReceipt` from a verified Ethereum event log that carries an explicit `success: bool` field indicating whether the inbound message dispatch on the gateway contract succeeded, but the function never checks this flag before crediting the relayer reward and clearing the pending order. Any relayer who obtains a valid proof of an `InboundMessageDispatched` log — regardless of whether `success` is `true` or `false` — receives the full `order.fee` payout and the order is permanently removed.

## Finding Description
`DeliveryReceipt` is decoded directly from the Ethereum `InboundMessageDispatched(nonce, topic, success, reward_address)` event log, preserving the `success` boolean from the on-chain dispatch outcome ( [2](#0-1) , [3](#0-2) ).

`submit_delivery_receipt` is reachable by any signed account; it only verifies the merkle/header proof for the event log via `T::Verifier::verify` and decodes the receipt before calling `Self::process_delivery_receipt` ( [4](#0-3) ).

`process_delivery_receipt` validates `receipt.gateway == T::GatewayAddress::get()` and looks up the `PendingOrder` by `receipt.nonce`, but the only condition gating the reward payout is `order.fee > 0` — `receipt.success` is read during decoding but never referenced in the payout logic ( [1](#0-0) ). The function unconditionally calls `T::RewardPayment::register_reward(&reward_account, T::DefaultRewardKind::get(), order.fee)` and then `<PendingOrders<T>>::remove(nonce)`, treating a failed dispatch (`success == false`) identically to a successful one.

## Impact Explanation
Because `receipt.success` is ignored, a relayer who submits proof of a failed inbound dispatch (`success == false`, e.g., reverted command, out-of-gas, invalid payload on Ethereum) still receives the full `order.fee` reward via `T::RewardPayment::register_reward`, and the `PendingOrders` entry for that `nonce` is permanently removed via `<PendingOrders<T>>::remove(nonce)`. This decouples relayer payout from actual successful bridge delivery — a duplicate/incorrect settlement condition where the reward pot pays out for deliveries that did not complete, and forecloses any retry logic since the pending order state is destroyed regardless of outcome.

## Likelihood Explanation
The path is reachable by any unprivileged, signed account via `submit_delivery_receipt`, requiring only a valid proof of an existing `InboundMessageDispatched` log — the relayer does not need to influence the `success` value, only choose which legitimate log to submit. No governance, admin, or privileged role is required, and this is the pallet's normal relayer-facing reward flow.

## Recommendation
Add an explicit `ensure!(receipt.success, Error::<T>::MessageDeliveryFailed)` check in `process_delivery_receipt` before crediting the reward and removing the order, and define distinct handling for `success == false` (e.g., preserve the order for retry or route to a non-reward cleanup path) instead of treating failed and successful deliveries identically.

## Proof of Concept
1. `do_process_message` enqueues a message, producing a `PendingOrder { nonce, fee, .. }` with `fee > 0` ( [5](#0-4) ).
2. On Ethereum, the corresponding inbound dispatch fails, and the gateway contract emits `InboundMessageDispatched(nonce, topic, success=false, reward_address)`.
3. A relayer obtains a valid proof for this log and calls `submit_delivery_receipt`; `T::Verifier::verify` succeeds and `DeliveryReceipt::try_from` decodes `success: false` without error.
4. `process_delivery_receipt` checks `receipt.gateway` and `order.fee > 0` only, then unconditionally calls `T::RewardPayment::register_reward` with `order.fee` and removes the order — the relayer is fully rewarded for a delivery Ethereum itself reported as failed.
