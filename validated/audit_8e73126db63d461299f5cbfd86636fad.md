### Title
Self-beneficiary `DeleteAccount` permanently burns the account's balance instead of refunding it - ([File: runtime/runtime/src/actions.rs])

### Summary
`DeleteAccountAction { beneficiary_id }` is validated only for account-ID format, never for whether `beneficiary_id` differs from the account being deleted. If a caller (owner or any actor with `check_actor_permissions` authority, e.g. a full-access key holder or a contract issuing a batch promise) sets `beneficiary_id == account_id`, the balance-refund receipt generated to pay out the remaining funds targets an account that has already been removed from state within the same action, causing the funds to be irrecoverably burnt.

### Finding Description
`validate_delete_action` only checks that `beneficiary_id` is a syntactically valid account id — it never rejects `beneficiary_id == account_id`: [1](#0-0) 

In `action_delete_account`, the remaining balance is queued as an outgoing `Receipt::new_balance_refund(&delete_account.beneficiary_id, account_balance)` **before** the account row is removed from the trie via `remove_account`, and `*account` is then set to `None`: [2](#0-1) 

`Receipt::new_balance_refund` builds a system-predecessor `Transfer` receipt: [3](#0-2) 

When `beneficiary_id == account_id`, this refund receipt is later executed against an account that no longer exists (it was just deleted in the very action that created the refund). `check_account_existence` classifies refund receipts as ineligible for implicit account creation (`is_refund` disables `implicit_account_creation_eligible`), so `check_transfer_to_nonexisting_account`/`check_account_existence` returns `ActionErrorKind::AccountDoesNotExist`: [4](#0-3) [5](#0-4) 

Because the refund's predecessor is `"system"`, a failed refund is treated specially: the runtime does not re-generate a refund (refunds are free/final), and instead the entire deposit is permanently added to `other_burnt_amount`: [6](#0-5) 

This burn-on-failed-refund behavior is also documented as intentional protocol design for genuinely failed refunds ("If the execution of a refund fails, the refund amount is burnt"): [7](#0-6) 

but it was never intended to be *triggerable at will* by a user simply naming themselves as their own beneficiary — the account is guaranteed to not exist by the time the refund lands, since `action_delete_account` unconditionally deletes it in the same action that spawns the refund receipt.

### Impact Explanation
Any account owner (or any actor with delete-account permission over the account, e.g., a full-access key holder, or a contract deploying a self-referential `promise_batch_action_delete_account`) can trigger unconditional, permanent loss of that account's entire remaining NEAR balance by setting `beneficiary_id` to its own account id. This is a direct token-loss bug: funds that should be refunded to the beneficiary are instead burnt via `other_burnt_amount`, silently reducing total supply with no economic benefit and no recovery path. Because `DeleteAccountAction` is reachable directly from any ordinary signed transaction or from any contract via `promise_batch_action_delete_account`, this requires no privileged or malicious-node access — it is purely a self-inflicted-but-preventable fund-loss bug, analogous to the Unlock `transferFrom(_from == _recipient)` finding where missing input validation on the destination-equals-source case destroys value that a `require` check should have prevented.

### Likelihood Explanation
Likelihood of accidental triggering is the same as in the original report (user/tooling error, e.g., a wallet or SDK defaulting `beneficiary_id` to the signer's own account, or a contract author reusing the deleting account's id as a placeholder beneficiary). No adversarial capability beyond normal transaction signing or FunctionCall-based promise batching is required, and the outcome (guaranteed burn) is deterministic once triggered — there is no race condition or timing dependency.

### Recommendation
Add an explicit validation check in `validate_delete_action` (`runtime/runtime/src/action_validation.rs`) rejecting `beneficiary_id == account_id` (the receiver of the delete-account receipt), returning a new `ActionsValidationError` (e.g., `DeleteAccountBeneficiaryIsSelf`) before the account balance is refunded. Since account-id equality checks at validation time require the receiver id (already passed into `validate_action_with_mode` as `receiver`), the check can be added directly in `validate_delete_action`/`validate_action_with_mode` by comparing `action.beneficiary_id` against `receiver`. This mirrors the recommended `require(_from != _recipient)` fix from the referenced report.

### Proof of Concept
1. Create/own account `alice.near` with a nonzero balance.
2. Submit a transaction from `alice.near` (or have a contract owned by `alice.near` issue a promise batch) with a single `DeleteAccount { beneficiary_id: "alice.near" }` action, targeting `alice.near` itself.
3. `action_delete_account` (`runtime/runtime/src/actions.rs:314-389`) computes `account_balance = account_ref.amount()`, pushes `Receipt::new_balance_refund(&"alice.near", account_balance)`, then calls `remove_account` and sets `account = None` — `alice.near` no longer exists in state.
4. The queued balance-refund receipt (predecessor `"system"`, receiver `"alice.near"`) is later executed. `check_account_existence` returns `AccountDoesNotExist` because the account is gone and refund receipts are not implicit-account-creation eligible (`runtime/runtime/src/actions.rs:819-827`, `857-870`).
5. Since the failing receipt's predecessor is `"system"`, `apply_action_receipt` in `runtime/runtime/src/lib.rs:993-1000` adds the entire `account_balance` to `stats.balance.other_burnt_amount` instead of refunding it to anyone — the funds are permanently destroyed.

Refund receipts are identified by having `predecessor_id == "system"`. They are also special because they don't cost any gas to generate or execute. As a result, they also do not contribute to the block gas limit.

If the execution of a refund fails, the refund amount is burnt.
The refund receipt is an `ActionReceipt` that consists of a single action `Transfer` with the `deposit` amount of the refund.
