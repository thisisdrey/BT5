### Title
Protocol fees systematically bypassed on Nep245/Imt token transfers by chunking a large transfer into unit-sized (`amount == 1`) `TokenDiff` intents - (File: contracts/defuse/core/src/intents/token_diff.rs)

### Summary
`TokenDiff::token_fee` waives fees on `Nep245`/`Imt` tokens whenever the *individual intent's* `|delta| <= 1`, but this exemption is evaluated per-intent rather than on the aggregate volume moved by a signer across a batch. An attacker pair can split any large `Nep245`/`Imt` transfer into N intents of `delta = ±1` each, causing `fee_ceil(1)` to always be `0` while the true economic transfer volume (`N` units) is large, letting them settle in one `execute_intents` call with zero protocol fee collected.

### Finding Description
The broken binding: `fee_collected_for_token(nep245_id) == protocol_fee.fee(total_volume_moved_for_nep245_id)` is violated - LHS is always `0`, RHS is nonzero for any `fee > 0` and `total_volume > 1`.

In `TokenDiff::execute_intent`, for each negative delta in a single intent's diff map, fee is computed as: [1](#0-0) 

and `token_fee` explicitly zeroes the fee for `Nep245`/`Imt` when `amount <= 1`: [2](#0-1) 

The `amount` parameter here is only `delta.unsigned_abs()` from that single `TokenDiff` intent instance - it has no visibility into how many other `TokenDiff` intents (from the same or a colluding counter-signer) move the same token in the same `execute_intents` batch. Since `TokenDiff.diff` is a `BTreeMap<TokenId, i128>` (via `Amounts`), a single intent cannot repeat the same `token_id` twice, but nothing stops a `DefusePayload::message` (`DefuseIntents`) or a batch of separately-signed `MultiPayload`s from containing many `TokenDiff` intents that each touch the same `Nep245`/`Imt` `token_id` with `delta = ±1`.

Batch-wide settlement is enforced only by `TransferMatcher`/`Deltas::finalize`, which requires that the sum of all deposits/withdrawals per token across the whole batch nets to zero (`InvariantViolated::UnmatchedDeltas` otherwise): [3](#0-2) 

This invariant only checks that balance changes net to zero; it does not check or aggregate fee amounts. The fee itself is fed into the same `Deltas`/`TransferMatcher` accounting via `internal_add_balance` to the fee collector: [4](#0-3) 
so the invariant is happily satisfied with `fee = 0` per unit-intent - there is no cross-intent or cross-batch aggregation check tying `token_fee`'s `amount` to the total volume transferred for that `token_id` by a signer in the batch.

Attacker exploit flow: signer1 and signer2 (attacker-controlled, or even the same signer trading with a counterparty) construct `N` `TokenDiff` intents, each with `diff = {nep245_token_id: -1}` (signer1) matched against `N` intents from signer2 with `diff = {nep245_token_id: +1, other_token: ...}`, batched into one `execute_intents`/`MultiPayload` call. Each of the `N` calls to `Self::token_fee(nep245_token_id, 1, fee)` returns `Pips::ZERO` per the `amount > 1` guard, so `fees_collected` for that token is `0` for every intent, while the aggregate transfer volume is `N` (arbitrarily large). Compare this to a single `TokenDiff` intent moving `N` units of the same token, where `token_fee` would return `fee` (nonzero) and `fee_ceil(N)` would be collected.

None of the existing guards (`MultiPayload::verify`, nonce/salt checks, `TransferMatcher::finalize`) prevent this, because they validate signature/nonce validity and balance-conservation, not fee correctness relative to aggregate volume.

### Impact Explanation
The fee collector under-collects protocol fees on any `Nep245`/`Imt` token transfer that can be structured this way - value that should flow to the `fee_collector` account instead stays with the trading counterparties. This matches the "protocol fees bypassed" Critical category. The blast radius covers every `Nep245`/`Imt` `token_id` in the Verifier when `Pips > 0`, and is repeatable indefinitely per batch, by any pair of unprivileged signers, at no cost beyond the extra gas of issuing more, smaller intents (each intent still requires a valid signature/nonce from the real owner of the funds, but since the attacker controls both counterparties this is not a privilege boundary).

### Likelihood Explanation
Preconditions are realistic and match what's stated in the question: two accounts holding balance in a valuable `Nep245`/`Imt` token, and a protocol fee `Pips > 0` configured for that token. No privileged role, relayer key, or bypass of signature verification is required - both signers legitimately sign their own intents, they only choose to split delta into unit-sized chunks. The primary limiting factor is gas/transaction size for very large `N`, but for any moderate volume (tens to low hundreds of units per transaction, well within a single NEAR transaction's gas budget), the fee bypass is fully effective and can be repeated across multiple transactions to move arbitrarily large aggregate volume at zero fee.

### Recommendation
Do not compute the `Nep245`/`Imt` "amount <= 1" fee exemption on the per-intent delta alone. Options: (a) apply the fee exemption based on whether the token is inherently non-fungible/unit-only (e.g., check token metadata/supply semantics) rather than the instantaneous transfer amount; or (b) track and aggregate per-signer, per-token_id transferred volume across the whole batch (in `Deltas`/`TransferMatcher`) before applying the `amount <= 1` threshold, so that chunking many unit-diffs cannot evade the check that would apply to the equivalent single larger diff.

    // Finalizes all transfers, or returns unmatched deltas.
    // If unmatched deltas overflow, then Err(None) is returned.
    pub fn finalize(self) -> Result<Transfers, InvariantViolated> {
        let mut transfers = Transfers::default();
        let mut deltas = TokenDeltas::default();
        for (token_id, transfer_matcher) in self.0 {
            if let Err(unmatched) = transfer_matcher.finalize_into(&token_id, &mut transfers)
                && (unmatched == 0 || deltas.apply_delta(token_id, unmatched).is_none())
            {
                return Err(InvariantViolated::Overflow);
            }
        }
        if !deltas.is_empty() {
            return Err(InvariantViolated::UnmatchedDeltas {
                unmatched_deltas: deltas,
            });
        }
        Ok(transfers)
    }
