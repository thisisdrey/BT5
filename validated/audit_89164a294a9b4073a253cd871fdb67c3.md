### Title
Stale `PromiseYieldReceipt`/`PromiseYieldTimeout` state survives `DeleteAccount`, enabling privileged action replay (AddKey/DeployContract) against a re-created account - (File: `core/store/src/utils/mod.rs`, `runtime/runtime/src/actions.rs`, `runtime/runtime/src/lib.rs`)

### Summary
`remove_account` (called by `action_delete_account`) removes `Account`, `ContractCode`, access/gas keys, and `ContractData`, but never removes any yield/resume state (`PromiseYieldReceipt`, `PromiseYieldStatus`, `PromiseYieldTimeout` queue entries, `YieldIdToDataId`/`DataIdToYieldId`). Because a parked `PromiseYield` receipt always has `predecessor_id == receiver_id == <account_id string>`, and the actor-permission check for privileged actions (`AddKey`, `DeployContract`, `Stake`, `DeleteAccount`) only compares that string equality, a stale yield receipt planted before deletion is later executed with full self-authorization against whatever new account occupies that same `account_id` after re-creation.

### Finding Description
- `remove_account` (`core/store/src/utils/mod.rs:504-575`) removes `TrieKey::Account`, `TrieKey::ContractCode`, all access/gas keys, and `TrieKey::ContractData` for `account_id`, but has no logic touching `TrieKey::PromiseYieldReceipt`, `TrieKey::PromiseYieldStatus`, `TrieKey::YieldIdToDataId`/`DataIdToYieldId`, or the global `PromiseYieldTimeout` queue. [1](#0-0) 
- `action_delete_account` (`runtime/runtime/src/actions.rs:314-390`) refunds the account balance and calls `remove_account`, then sets `*account = None` — it performs no additional cleanup of yield state. [2](#0-1) 
- A `PromiseYield` receipt created via `promise_yield_create`/`promise_yield_create_with_id` always targets the creating contract itself: `receiver_id == predecessor_id == account_id`. Its action list (`actions: vec![]`, later populated via `promise_batch_action_*` host calls on the returned promise index) can include *any* batch action, including `AddKey`, `DeployContract`, `Stake`, `DeleteAccount` — the host functions do not restrict which actions may be attached, they only use "signer is receiver" (`sir`) for fee accounting. [3](#0-2) [4](#0-3) 
- Per protocol rules, `AddKey`/`DeployContract`/`Stake`/`DeleteAccount` are only permitted when `predecessor_id == receiver_id` (self-call). [5](#0-4) 
- When the parked receipt is eventually delivered — either via an explicit `promise_yield_resume` (`runtime/runtime/src/ext.rs:402-426`, which checks `has_promise_yield_receipt`/`has_promise_yield_status` keyed only by `(receiver_id, data_id)`) or automatically via the never-cleaned `PromiseYieldTimeout` queue entry (`resolve_promise_yield_timeouts`, `runtime/runtime/src/lib.rs:3009-3105`, which checks `state_update.contains_key(&promise_yield_key,...)`), the runtime fetches the *original* stored `Receipt` via `get_promise_yield_receipt` and executes it with `apply_action_receipt` against whatever account currently exists at that `account_id`. [6](#0-5) [7](#0-6) 
- Since none of this state is scrubbed on deletion, an attacker who (1) owns account `A`, (2) calls `promise_yield_create` and appends `promise_batch_action_add_key_with_full_access(attacker_key)` to the resulting promise, and (3) immediately `DeleteAccount(A)`s, leaves a "time bomb" `PromiseYieldReceipt`/`PromiseYieldTimeout` row keyed to `A` in state. If account `A` is later re-created (e.g. a factory/session pattern that deletes and re-creates the same sub-account name for different users, or a released name is re-registered) and funded, the surviving timeout entry autonomously fires a `PromiseResume` once its `expires_at` block height passes — no cooperation from the new owner or its contract is required. The runtime finds the old `PromiseYieldReceipt`, and since its `predecessor_id == receiver_id == A` (a pure string match, oblivious to the fact the account was deleted and recreated), the self-authorization check for `AddKey` trivially passes, granting the attacker a full-access key on the new account and full control of its funds.

### Impact Explanation
This is an authorization-escalation vulnerability enabling outright account takeover / theft of funds: an attacker can arm a stale privileged action (`AddKey` full-access, or `DeployContract`, `DeleteAccount`) against an account name they no longer control, and have it fire automatically once someone else re-establishes that account and deposits value. This matches the NEAR bounty categories "authorization escalation across accounts or promises" and "theft ... of user funds."

### Likelihood Explanation
Preconditions are attacker-controlled and cheap: the attacker only needs their own contract account, ability to call `promise_yield_create`, `promise_batch_action_add_key_with_full_access`, and `DeleteAccount` — all ordinary unprivileged transactions. The trigger is deterministic (timeout expiry) requiring no interaction from the future re-creator/owner of the account. The scenario is most directly exploitable in factory/marketplace-style dApps that delete and re-issue identically-named sub-accounts to different tenants (a common pattern), making it repeatable per session/tenant.

### Recommendation
`remove_account` in `core/store/src/utils/mod.rs` should also purge all account-scoped receipt/yield bookkeeping for the deleted `account_id`: `PromiseYieldReceipt`, `PromiseYieldStatus`, `YieldIdToDataId`/`DataIdToYieldId`, `PostponedReceipt`/`PostponedReceiptId`/`PendingDataCount`, and `ReceivedData`. The global `PromiseYieldTimeout` queue should either be scanned/pruned for entries referencing the deleted account or the timeout-resolution and resume-delivery paths must additionally check that the parked receipt's account "generation" matches (e.g., compare against an account creation nonce/height) before treating a stale receipt as self-authorized.

### Proof of Concept
Integration/runtime test-loop plan:
1. Create account `A` with attacker-controlled full-access key; deploy a contract that calls `promise_yield_create` then `promise_batch_action_add_key_with_full_access(promise_idx, attacker_key_2)`.
2. Capture the returned `data_id`; confirm `PromiseYieldReceipt{receiver_id: A, data_id}` and a `PromiseYieldTimeout` queue entry exist in state.
3. Submit `DeleteAccount(A)`; assert account is deleted (no `Account` row) but `has_promise_yield_receipt(trie, A, data_id)` still returns `true` (this is the root-cause assertion).
4. Recreate `A` via `CreateAccount` + `Transfer` + `AddKey(new_owner_key)`, funding it with balance.
5. Advance blocks past `expires_at` (or explicitly call `promise_yield_resume` from a receipt targeting `A`) and assert that after the timeout/resume fires, `attacker_key_2` has been added as a full-access key on the *new* `A` account, and/or that the new account's balance/state has been mutated by the stale receipt — demonstrating cross-generation privilege leak.
6. As a fix-validation assertion: after the fix, `has_promise_yield_receipt` must return `false` for any `data_id` immediately after `remove_account`, regardless of subsequent `CreateAccount`.

/// Removes account, code and all access keys and gas keys associated to it.
pub fn remove_account(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
) -> Result<RemoveAccountResult, StorageError> {
    state_update.remove(TrieKey::Account { account_id: account_id.clone() });
    state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });

    let mut gas_key_nonce_count: usize = 0;
    let mut gas_key_nonce_total_key_bytes: usize = 0;

    // Removing access keys and gas key nonces
    let lock = state_update.trie().lock_for_iter();
    let mut keys_to_remove: Vec<TrieKey> = Vec::new();
    for raw_key in state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_access_keys(account_id), &lock)?
    {
        let raw_key = raw_key?;
        let key_handle = trie_key_parsers::parse_key_handle_from_access_key_key(
            &raw_key, account_id,
        )
        .map_err(|_e| {
            StorageError::StorageInconsistentState(
                "Can't parse key handle from raw key for AccessKey".to_string(),
            )
        })?;
        let nonce_index =
            trie_key_parsers::parse_nonce_index_from_gas_key_key(&raw_key, account_id, &key_handle)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse nonce index from raw key for AccessKey".to_string(),
                    )
                })?;
        if let Some(index) = nonce_index {
            gas_key_nonce_count += 1;
            gas_key_nonce_total_key_bytes += raw_key.len();
            keys_to_remove.push(TrieKey::gas_key_nonce(
                account_id.clone(),
                key_handle.clone(),
                index,
            ));
        } else {
            keys_to_remove.push(TrieKey::access_key(account_id.clone(), key_handle.clone()));
        }
    }
    drop(lock);

    for trie_key in keys_to_remove {
        state_update.remove(trie_key);
    }

    // Removing contract data
    let lock = state_update.trie().lock_for_iter();
    let data_keys = state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_contract_data(account_id, &[]), &lock)?
        .map(|raw_key| {
            trie_key_parsers::parse_data_key_from_contract_data_key(&raw_key?, account_id)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse data key from raw key for ContractData".to_string(),
                    )
                })
                .map(Vec::from)
        })
        .collect::<Result<Vec<_>, _>>()?;
    drop(lock);

    for key in data_keys {
        state_update.remove(TrieKey::ContractData { account_id: account_id.clone(), key });
    }
    Ok(RemoveAccountResult { gas_key_nonce_count, gas_key_nonce_total_key_bytes })
}

    /// Helper function to return the receipt index corresponding to the given promise index.
    /// It also pulls account ID for the given receipt and compares it with the current account ID
    /// to return whether the receipt's account ID is the same.
    fn promise_idx_to_receipt_idx_with_sir(
        &self,
        promise_idx: u64,
    ) -> Result<(ReceiptIndex, bool)> {
        let promise = self
            .promises
            .get(promise_idx as usize)
            .ok_or(HostError::InvalidPromiseIndex { promise_idx })?;
        let receipt_idx = match &promise {
            Promise::Receipt(receipt_idx) => Ok(*receipt_idx),
            Promise::NotReceipt(_) => Err(HostError::CannotAppendActionToJointPromise),
        }?;

        let account_id = self.ext.get_receipt_receiver(receipt_idx);
        let sir = account_id == &self.context.current_account_id;
        Ok((receipt_idx, sir))
    }

Each transaction consists a list of actions to be performed on the `receiver_id` side. Since transactions are first

For the following actions, `predecessor_id` and `receiver_id` are required to be equal:

- `DeleteKey`
- `DeleteAccount`
