### Title
Non-constant-time authentication token comparison enables remote timing attack to recover `auth_token` and bypass write-protected RPC endpoints - (File: stackslib/src/net/api/postblock_v3.rs, stackslib/src/net/api/txsimulate.rs, stackslib/src/net/api/blockreplay.rs, stackslib/src/net/api/blocksimulate.rs, stackslib/src/net/api/fastcallreadonly.rs, stackslib/src/net/api/postblock_proposal.rs)

### Summary
Several RPC HTTP request handlers in `stackslib/src/net/api/*` authenticate privileged/state-mutating requests by comparing the client-supplied `authorization` header against the node's configured `auth_token` with a plain `!=` string comparison, e.g. in `postblock_v3.rs`:

```
if auth_header != password {
    return Err(Error::Http(401, "Unauthorized".into()));
}
``` [1](#0-0) 

The same pattern (`auth_header != password`) recurs in `blockreplay.rs`, `txsimulate.rs`, `blocksimulate.rs`, and `fastcallreadonly.rs`. [2](#0-1) [3](#0-2) 

### Finding Description
Rust's `String`/`&str` `PartialEq` (used by `!=`/`==`) performs a byte-wise comparison that returns as soon as a length mismatch or the first differing byte is found — it is **not constant-time**. This is directly analogous to the bug class in the referenced advisory (CVE-2023-26556): a secret-dependent branch/early-exit inside an equality/verification routine leaks information about the secret through observable timing differences. In the tss-lib case the secret was an ECDSA private key leaked via non-constant-time scalar multiplication; here the secret is the node's `auth_token` (configured via `connection_options.auth_token`), leaked via a non-constant-time string comparison against attacker-controlled, arbitrarily-chosen prefixes sent in the HTTP `Authorization` header.

This `auth_token` is the sole authentication mechanism gating:
- `/v3/blocks?broadcast=1` (`postblock_v3.rs`) — unauthenticated broadcast of a Stacks block is otherwise blocked; `authenticated` is only set true after the byte-wise header check succeeds [4](#0-3) 
- `/v3/transactions/simulate` (`txsimulate.rs`)
- `/v3/blocks/replay/:block_id` (`blockreplay.rs`)
- block/tx simulation and fast read-only call endpoints (`blocksimulate.rs`, `fastcallreadonly.rs`)

The config documentation confirms this token is meant to secure exactly these sensitive endpoints and the signer communication channel: "This token is used in the `Authorization` header for certain requests... It is also used to authenticate requests to `/v2/blocks?broadcast=1`." [5](#0-4) 

An attacker who can measure response latency for repeated requests (byte-at-a-time guessing, exploiting the early-exit comparison) can, in principle, reconstruct the `auth_token` without any credentials, then use it to authenticate to `/v3/blocks?broadcast=1` and force the node to accept/broadcast an attacker-supplied block, i.e., an unauthenticated write bypassing the auth gate — matching the "auth-gate that fails open" / "unauthenticated/unauthorized write to state" criteria in scope.

### Impact Explanation
If exploitable with sufficient statistical averaging, this allows full recovery of the shared secret `auth_token` from a remote, unauthenticated position, and its use to bypass authentication on `postblock_v3`'s broadcast path — a Critical-class outcome per policy ("unauthenticated/unauthorized write to state ... auth bypass"). The blast radius also includes the txsimulate/blockreplay/fastcallreadonly/blocksimulate endpoints, which would otherwise be gated behind the same secret.

### Likelihood Explanation
Likelihood is **low-to-uncertain** in practice, and this materially differs from the source CVE:
- The original bug involved leakage of a private key through *cryptographic* scalar multiplication timing (microsecond-level, amplifiable via many operations per guess) — a much cleaner signal than an 8–64 byte string comparison over a network round trip, where OS/network jitter typically swamps the sub-microsecond timing difference of one extra byte compared.
- No batching/pipelining primitive is evident that would let an attacker average out network noise to the level needed to resolve single-byte comparison timing over a WAN.
- The comparison is short (bounded by `auth_token` length), reducing the number of guessable positions, but per-byte guess space is large (full byte alphabet), and there is no rate limiting/lockout observed at this layer.
This is a legitimate, in-scope code-quality/timing-side-channel weakness (real fault site, real remote reachability, real impact if exploited), but the exploitability bar is materially higher than the original tss-lib EC scalar-mult side channel — I cannot confirm actual exploitability without further empirical timing measurement, which is outside the scope of static analysis.

### Recommendation
Replace all `auth_header != password` / `auth_header == password` comparisons in `stackslib/src/net/api/{postblock_v3,txsimulate,blockreplay,blocksimulate,fastcallreadonly,postblock_proposal}.rs` with a constant-time comparison (e.g., `subtle::ConstantTimeEq`, or a fixed-time byte-wise XOR-accumulate compare that always compares the full max length regardless of early mismatches), and additionally hash-compare (e.g., compare HMAC/SHA-256 digests of both strings) to avoid leaking length as well as content. Add basic rate limiting/backoff on repeated authentication failures per source IP for these endpoints as defense in depth.

### Proof of Concept
1. Configure a node with `connection_options.auth_token = "<secret>"`, exposing `/v3/blocks?broadcast=1`.
2. From a remote host, repeatedly send POST requests to `/v3/blocks?broadcast=1` with an `Authorization` header value that varies one byte at a time (e.g., trying `"\x00...", "\x01...", ... "\xff..."` for position 0, keeping the best-guessed prefix and moving to the next byte), measuring server response latency for each guess with statistical averaging (many repeated trials per candidate byte to filter network noise).
3. If the comparison exits early on mismatch, correctly-guessed prefixes should exhibit a measurable additional processing delay (one more byte compared) versus incorrect guesses at that position, allowing incremental reconstruction of `auth_token`.
4. Once the full token is recovered, issue `POST /v3/blocks?broadcast=1` with `Authorization: <recovered_token>` and an attacker-crafted block payload; per `postblock_v3.rs`, `authenticated` becomes `true` and `broadcast` is honored, i.e., the endpoint's auth gate is bypassed [4](#0-3) .

Note: I was unable to further verify actual timing exploitability (e.g., magnitude of measurable delta over realistic network conditions) using static code review alone; this would require dynamic/network-level timing experiments to confirm practical feasibility.

                if auth_header != password {

        // see if broadcast=1 is set

            }
        }
