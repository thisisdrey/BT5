### Title
Unbounded memory growth via unbounded `Content` chunks in `UserCommitFiles` stream loop - (File: internal/gitaly/service/operations/commit_files.go)

### Summary
The `userCommitFiles` receive loop accumulates all `UserCommitFilesAction_Content` chunks into an in-memory `pbActions` slice via `*content = append(*content, payload.Content...)` before performing any size validation or streaming the content to disk/blob storage. [1](#0-0)  An attacker with ordinary push access can send an unbounded sequence of `Content` messages for a single file action, causing Gitaly to buffer arbitrarily large amounts of data in memory before ever reaching a size check.

### Finding Description
In `userCommitFiles`, the stream-receive loop reads every `UserCommitFilesRequest` and, for `UserCommitFilesAction_Content` payloads, appends the raw bytes onto the last action's `content []byte` field with no per-message or aggregate size cap: [2](#0-1) 
This loop only terminates on `io.EOF` or a stream error, so a malicious client can hold the stream open and continuously send `Content` frames. [3](#0-2)  Only after the full loop completes (i.e., only when the client eventually sends EOF) does the code proceed to process `pbActions` into blobs via `quarantineRepo.WriteBlob`. [4](#0-3)  There is no `structerr.NewResourceExhausted` check, no aggregate content-size limit, and no per-message size validation anywhere in this function.

I could not find any gRPC server-level `MaxRecvMsgSize` override in the codebase (`grep_search` for `MaxRecvMsgSize`/`MaxCallRecvMsgSize` returned no results), meaning individual message sizes are bounded only by gRPC's built-in default (4 MiB per message), but there is **no limit on the number of messages/chunks**, so the aggregate buffered content for a single file (or across many `Header`+`Content` action pairs within one RPC) is unbounded by application logic.

I located a `burdenmonitor`/`LoadShedder` subsystem that can cancel in-flight RPCs under PSI CPU/memory/IO pressure or OOM-kill conditions [5](#0-4) , which is a system-wide mitigating control, but it is a reactive, threshold-based mechanism gated behind feature flags (`featureflag.BurdenMonitorTrackCommands`) and triggers only after the node is already under measurable pressure — it does not prevent a single RPC from ballooning memory before that pressure is detected, nor does it impose any static bound on this specific handler's buffering behavior.

### Impact Explanation
An attacker who can push to any repository they own (default RPC access, no special role required) can stream gigabytes of `Content` chunks in a single `UserCommitFiles` call. Because this data is fully buffered in Go heap memory (`pbActions[i].content`) before any size check, a single connection can consume large amounts of RSS, potentially triggering Gitaly OOM and impacting other tenants/repositories co-located on the same Gitaly node — a resource-exhaustion/DoS impact matching GitLab's "Denial of Service" bounty class.

### Likelihood Explanation
Preconditions are minimal: the attacker only needs ordinary push access to a repository they own, which is the default capability of any authenticated GitLab user with a repo. The attack is straightforward to script (open the `UserCommitFiles` stream, send a `Header`, then loop sending `Content` frames) and is fully repeatable and automatable. The only friction is gRPC's default per-message size cap (~4 MiB), which does not stop aggregation across many messages.

### Recommendation
Enforce a maximum aggregate content size per action (and/or per RPC) while receiving the stream, returning `structerr.NewResourceExhausted` once exceeded, before appending further bytes to `pbActions[i].content`. Alternatively, refactor to stream content directly into `quarantineRepo.WriteBlob` via a pipe/reader as chunks arrive (bounding memory to a small buffer) rather than buffering the entire file into memory first. Also consider setting an explicit gRPC `MaxRecvMsgSize` and a maximum total actions/content byte budget for the whole `UserCommitFiles` call.

### Proof of Concept
```go
// Pseudocode gRPC client PoC against UserCommitFiles
stream, _ := client.UserCommitFiles(ctx)
stream.Send(&gitalypb.UserCommitFilesRequest{
    Action: &gitalypb.UserCommitFilesRequestAction{
        Payload: &gitalypb.UserCommitFilesRequestAction_Header_{
            Header: &gitalypb.UserCommitFilesActionHeader{
                Action:   gitalypb.UserCommitFilesActionHeader_CREATE,
                FilePath: []byte("evil.bin"),
            },
        },
    },
})
chunk := make([]byte, 4*1024*1024) // near gRPC per-message cap
for {
    stream.Send(&gitalypb.UserCommitFilesRequest{
        Action: &gitalypb.UserCommitFilesRequestAction{
            Payload: &gitalypb.UserCommitFilesRequestAction_Content_{
                Content: &gitalypb.UserCommitFilesActionContent{Content: chunk},
            },
        },
    }) // repeat indefinitely, never close send / never EOF-terminate cleanly
}
```
Expected (vulnerable) behavior: Gitaly RSS for the worker handling this stream grows unbounded as chunks are received, with no `ResourceExhausted` error returned, confirmable by observing process memory (`/proc/<pid>/status VmRSS`) climbing linearly with bytes sent in `internal/gitaly/service/operations/commit_files.go`'s receive loop at line 630-631.
