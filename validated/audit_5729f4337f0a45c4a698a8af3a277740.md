### Title

Initial reward-index boundary is misclassified as uninitialized, allowing theft of unearned rewards - ([File: contracts/RewardsDistributor.sol])

### Summary

`RewardsDistributor` initializes a newly enabled reward token at `INITIAL_INDEX == 1e18`. [1](#0-0)  However, `_calculateTokenDelta()` substitutes `INITIAL_INDEX` for a zero account index only when the token index is strictly greater than `INITIAL_INDEX`; when the index is exactly `1e18`, the account delta becomes `1e18` instead of zero. [2](#0-1)  An account holding tracked `DepositToken` or `DebtToken` balance before reward tracking is enabled can therefore receive `balance * 1e18 / 1e18 == balance` reward tokens without waiting for any reward period.

### Finding Description

When a token first receives a nonzero speed, its global index is initialized to `INITIAL_INDEX` and its timestamp to the current block timestamp. [3](#0-2)  Calling `claimRewards()` during that same block invokes `_updateTokensAccruedOf()` for each supplied account. [4](#0-3) 

Because no timestamp elapsed, `_updateTokenIndex()` leaves the token index at `INITIAL_INDEX`. `_calculateTokenDelta()` then reads `accountIndexOf[token][account] == 0`, but the `>` comparison fails to recognize the initial boundary as initialized state. [2](#0-1) 

The resulting delta is:

```solidity
_tokenIndex - _accountIndex = 1e18 - 0 = 1e18
token_.balanceOf(account).wadMul(1e18) = token_.balanceOf(account)
```

The public `updateBeforeMintOrBurn()` and `updateBeforeTransfer()` functions also reach the same accounting path. [5](#0-4)  `claimRewards()` then transfers the inflated `tokensAccruedOf` amount if the distributor has sufficient reward-token balance. [6](#0-5) 

### Impact Explanation

An attacker can steal up to their tracked-token balance from the reward distributor without earning those rewards. This directly converts each unit of preexisting `DepositToken` or `DebtToken` balance into one unit of `rewardToken` and is bounded only by the distributor's reward balance. [6](#0-5) 

The reward-accounting invariant is broken because the attacker receives rewards for the full initial index range rather than for the period during which the account's index was initialized.

### Likelihood Explanation

The vulnerable state occurs when a token's reward speed transitions from zero to nonzero while accounts already hold balances and have `accountIndexOf == 0`. An unprivileged attacker can establish such a balance before a routine reward activation and call `claimRewards()` in the same block, or exploit an existing deployment state that already satisfies those conditions.

No malicious oracle, reentrancy, privileged attacker role, or invalid token registration is required: `claimRewards()` is externally callable and transfers the calculated amount to the specified account. [7](#0-6) 

### Recommendation

Treat every zero account index on an initialized token index as beginning at `INITIAL_INDEX`, including the equality boundary:

```solidity
if (_accountIndex == 0 && _tokenIndex >= INITIAL_INDEX) {
    _accountIndex = INITIAL_INDEX;
}
```

Alternatively, initialize `_accountIndex` to `INITIAL_INDEX` whenever `_accountIndex == 0` and `_tokenIndex > 0`. Add a regression test in which an account has a nonzero tracked-token balance, reward speed is enabled, and a claim in the same block accrues zero rewards.

### Proof of Concept

The following Foundry-style test uses an attacker with a deposit-token balance before the token's first nonzero speed is configured. The activation and claim occur at the same timestamp:

```solidity
function test_initialIndexBoundaryStealsRewards() external {
    address attacker = makeAddr("attacker");
    uint256 attackerDeposit = 100e18;

    // Attacker obtains a tracked balance while tokenStates[token].index == 0.
    underlying.mint(attacker, attackerDeposit);
    vm.startPrank(attacker);
    underlying.approve(address(depositToken), attackerDeposit);
    depositToken.deposit(attackerDeposit, attacker);
    vm.stopPrank();

    // Fund the distributor so the inflated accrual is payable.
    rewardToken.mint(address(rewardsDistributor), 1_000e18);

    // Enable rewards and claim at the same block timestamp.
    vm.warp(1_000_000);

    vm.prank(governor);
    rewardsDistributor.updateTokenSpeed(
        IERC20(address(depositToken)),
        1e18
    );

    IERC20[] memory tokens = new IERC20[](1);
    tokens[0] = IERC20(address(depositToken));

    vm.prank(attacker);
    rewardsDistributor.claimRewards(attacker, tokens);

    // Vulnerable result: attacker receives attackerDeposit despite zero elapsed time.
    assertEq(rewardToken.balanceOf(attacker), attackerDeposit);
}
```

The decisive state transition is that `updateTokenSpeed()` writes `TokenState({index: 1e18, timestamp: block.timestamp})`; the same-block claim leaves that index unchanged, and the strict `>` fallback leaves the attacker's account index at zero. [3](#0-2) [2](#0-1)
