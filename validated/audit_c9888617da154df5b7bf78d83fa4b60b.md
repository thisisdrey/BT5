### Title
Cross-repository object disclosure via unauthenticated `origin`/`additional_repository` field in `FetchIntoObjectPool` — ([File: internal/gitaly/service/objectpool/fetch_into_object_pool.go])

### Summary
`FetchIntoObjectPool` accepts two repository references, `object_pool` (`target_repository`, subject to normal permission checks against the caller) and `origin` (`additional_repository`, only validated for existence and matching storage). Gitaly itself performs no check that the `origin` repository is actually a pool member, or that the caller who is authorized to write to `object_pool` is also authorized to read `origin`. This mirrors the Magnetar `_exitPositionAndRemoveCollateral()` pattern: a multi-purpose function combines a "privileged" target the caller controls with an arbitrary secondary address, and the missing cross-check lets the caller redirect the operation onto a victim's asset.

### Finding Description
The RPC handler `(s *server) FetchIntoObjectPool` builds a `localrepo.Repo` directly from `req.GetOrigin()` and passes it to `objectPool.FetchFromOrigin`, which performs `git fetch <originPath> +refs/*:refs/remotes/origin/*` into the pool repository: [1](#0-0) 

The only validation performed is `validateFetchIntoObjectPoolRequest`, which checks that `origin` and `object_pool` are non-nil and share the same storage name — it does **not** verify that `origin` is an existing pool member of `object_pool`, nor that the caller has read access to `origin`: [2](#0-1) 

The actual fetch performs an unrestricted `+refs/*:refs/remotes/origin/*` refspec against the origin path, pulling all reachable objects and references into the pool: [3](#0-2) 

Because `object_pool` is the `target_repository` field, a caller only needs authorization over the pool repository (e.g., a pool they created for their own fork via `CreateObjectPool`/`LinkRepositoryToObjectPool`) — the same "primary owner" role the report's attacker plays with Magnetar's approved oTAP position. The `origin` field is the "arbitrary address" analog: nothing in Gitaly enforces that `origin` was ever the repository the pool was created from or that it is linked to this pool at all. [4](#0-3) 

Once objects and refs from an arbitrary `origin` repository land in the attacker-controlled pool (as `refs/remotes/origin/*` plus their reachable trees/blobs/commits), the attacker can read them directly out of the pool repository they own via any read RPC (e.g., `GetBlob`, `TreeEntry`, `CommitService`), since the pool is a repository the attacker fully controls. This is precisely analogous to the two-step Magnetar attack: step one moves/exposes protected content into an attacker-influenced location using an under-validated "target"/"origin" combination, step two lets the attacker read/claim it from a location they own.

### Impact Explanation
If the underlying repository/storage layer routing allows an `origin` relative path belonging to a repository the caller does not otherwise have read access to (Rails' access-check model for `FetchIntoObjectPool` largely relies on this RPC only being called by trusted internal jobs against a pool's own established member, not on Gitaly enforcing pool membership), this results in disclosure of another repository's full object graph (commit content, blobs, refs) — a private-repository confidentiality breach. This is High severity because it is theft/disclosure of repository content across a trust boundary, similar in class to the reported theft of a victim's locked assets in Magnetar.

### Likelihood Explanation
Likelihood depends on whether GitLab Rails' authorization layer independently enforces that the caller of `FetchIntoObjectPool` is the actual pool's registered "primary member" for the specific `origin` supplied, since Gitaly's own validation is limited to storage-name equality. I was unable to fully confirm from the available Gitaly index whether such enforcement exists purely at the Rails layer (which is out of scope here) versus being expected in Gitaly. Within Gitaly's own code, there is no defense against an `origin`/`object_pool` mismatch beyond storage equality, so if any caller path allows supplying an uncontrolled `origin`, the vulnerability is directly reachable.

### Recommendation
- In `FetchIntoObjectPool` (and `CreateObjectPool`, which similarly clones an arbitrary `origin`/`additional_repository` into a `target_repository` the caller controls), verify that `origin` is actually linked as an alternate/member of the target `object_pool` (or was the pool's original seed) before performing the fetch/clone, rather than trusting the caller-supplied pairing.
- Do not rely solely on `target_repository`/`additional_repository` protobuf annotations for authorization; add an explicit ownership/membership check inside the RPC handler itself.
- Consider requiring that the `origin` repository be resolvable only from a Gitaly-maintained pool-membership record rather than an arbitrary caller-supplied `Repository` message.

### Proof of Concept
Conceptual (not executed against the codebase, consistent with the "arbitrary address across a multi-purpose function" bug class from the source report):
1. Attacker creates repository `A` and calls `CreateObjectPool` with `object_pool = poolA`, `origin = A`, then links `A` to `poolA` — the attacker now fully owns and can read `poolA`.
2. Attacker calls `FetchIntoObjectPool` with `object_pool = poolA` (their own, satisfies `target_repository` authorization) but `origin = victim's private repository V` (only required to share storage with `poolA`, per `validateFetchIntoObjectPoolRequest`).
3. Gitaly executes `git fetch <path to V> +refs/*:refs/remotes/origin/*` into `poolA`'s object store, per `FetchFromOrigin`.
4. Attacker reads `poolA` via any accessor RPC (`GetBlob`, `TreeEntry`, `FindCommit`, etc.) using the newly created `refs/remotes/origin/*` references, obtaining the contents of `V` that they never had access to. [1](#0-0) [5](#0-4)

func validateFetchIntoObjectPoolRequest(req *gitalypb.FetchIntoObjectPoolRequest) error {
	if req.GetOrigin() == nil {
		return errors.New("origin is empty")
	}

	if req.GetObjectPool() == nil {
		return errors.New("object pool is empty")
	}

	originRepository, poolRepository := req.GetOrigin(), req.GetObjectPool().GetRepository()

	if originRepository.GetStorageName() != poolRepository.GetStorageName() {
		return errors.New("origin has different storage than object pool")
	}

	return nil
}

func (o *ObjectPool) FetchFromOrigin(ctx context.Context, origin *localrepo.Repo, newLocalRepo LocalRepoFactory) error {
	if !o.Exists(ctx) {
		return structerr.NewInvalidArgument("object pool does not exist")
	}

	originPath, err := origin.Path(ctx)
	if err != nil {
		return fmt.Errorf("computing origin repo's path: %w", err)
	}

	if err := o.housekeepingManager.CleanStaleData(ctx, o.Repo, housekeeping.DefaultStaleDataCleanup()); err != nil {
		return fmt.Errorf("cleaning stale data: %w", err)
	}

	if err := o.logStats(ctx, "before fetch"); err != nil {
		return fmt.Errorf("computing stats before fetch: %w", err)
	}
