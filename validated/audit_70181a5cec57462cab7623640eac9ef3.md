### Title
`VaultShareToken.setVault` rotates the vault pointer but never grants `MINTER_ROLE`/`BURNER_ROLE` to the new vault, bricking deposits and redemptions - (File: `contracts/VaultShareToken.sol`)

### Summary
This is the same root cause as the reported `Reserve.sol`/`DAO.sol` issue: a governance rotation updates a pointer to a new authorized address in one contract, but a *separate* contract's permission state (a role/allowlist gating a `msg.sender` check) is not updated in the same step. The next privileged call from the "new" authority reverts because the permission-checking contract still doesn't recognize it.

### Finding Description
`VaultShareToken.setVault` is the designated migration path for rotating which `PortfolioVault` instance is allowed to mint/burn shares: [1](#0-0) 

```solidity
function setVault(address newVault) external onlyRole(GUARDIAN_ROLE) {
    require(newVault != address(0), ZeroAddress());

    // Revoke mint/burn authority from the outgoing vault so an exploited old
    // vault cannot mint or burn shares.
    address oldVault = _vault;
    _revokeRole(MINTER_ROLE, oldVault);
    _revokeRole(BURNER_ROLE, oldVault);

    _vault = newVault;
    emit VaultUpdate(_asset, newVault);
}
```

It correctly revokes `MINTER_ROLE`/`BURNER_ROLE` from the outgoing vault, and updates the `_vault` pointer (used by the ERC-7575 `vault(asset)` lookup), but it never calls `_grantRole(MINTER_ROLE, newVault)` / `_grantRole(BURNER_ROLE, newVault)` for the incoming vault. Only the constructor grants these roles, and only to the vault passed in at deployment: [2](#0-1) 

```solidity
_setRoleAdmin(MINTER_ROLE, GUARDIAN_ROLE);
_setRoleAdmin(BURNER_ROLE, GUARDIAN_ROLE);
_grantRole(MINTER_ROLE, vault_);
_grantRole(BURNER_ROLE, vault_);
_grantRole(SHAREHOLDER_ROLE, vault_);
```

`mint`/`burn` are gated by these roles: [3](#0-2) 

After `setVault(newVault)` runs, `PortfolioVault.approveDeposit` (which calls `shareToken.mint(...)`) and `PortfolioVault.approveRedemption` (which calls `shareToken.burn(...)`) on the new vault both revert with `AccessControlUnauthorizedAccount`, because `newVault` never received `MINTER_ROLE`/`BURNER_ROLE`. This is exactly analogous to the M-10 pattern: the DAO/vault pointer is repointed in one place (`_vault`, analogous to `BASE`'s DAO pointer), while the permission-checking side of the relationship (`onlyGrantor`/`onlyRole(MINTER_ROLE)`) is not updated for the new authorized caller, causing the privileged function to revert on its very next invocation.

This is documented as an already-identified issue in the repo's own audit artifacts (`pashov-ai-audit-report-20260429.md`), though the write-up there is stale relative to current code (it also claims the old vault's roles aren't revoked, which the current code does correctly handle) — the missing-grant-to-new-vault half of the bug is still present in the current `VaultShareToken.sol`.

### Impact Explanation
This breaks the vault migration flow described in `specs/vault-migration-runbook.md` and blocks core user-facing flows (`approveDeposit`/`approveRedemption`, and by extension `deposit`/`mint`/`redeem`/`withdraw` claims that depend on shares having been minted/burned) for every shareholder using the new vault until a guardian notices and issues a follow-up `grantRole` call. This is a material production DoS on NAV-sensitive approvals across all users of the migrated vault, matching the allowed impact "Material production DoS ... that blocks funding, disbursement, withdrawals, claims, NAV-sensitive approvals, or loan settlement across users."

It does not directly cause fund theft (funds aren't lost — `SHAREHOLDER_ROLE` is separately granted to the vault, and USDC/loan-side migration is otherwise handled by the runbook), but it strands the migration in a half-broken state.

### Likelihood Explanation
Any time a guardian performs a vault rotation (per the documented migration runbook) and relies on `setVault` to finish the job — the runbook does not call out a separate `grantRole(MINTER_ROLE/BURNER_ROLE, newVault)` step — the very next `approveDeposit`/`approveRedemption` on the new vault will revert. This is a deterministic, guaranteed-to-trigger operational failure on the standard migration path, not a rare edge case; it doesn't require any attacker, only the intended governance action.

### Recommendation
Update `setVault` to grant `MINTER_ROLE` and `BURNER_ROLE` (and `SHAREHOLDER_ROLE`, mirroring the constructor) to `newVault` in the same transaction that revokes them from `oldVault`, e.g.:

```solidity
function setVault(address newVault) external onlyRole(GUARDIAN_ROLE) {
    require(newVault != address(0), ZeroAddress());
    address oldVault = _vault;
    _revokeRole(MINTER_ROLE, oldVault);
    _revokeRole(BURNER_ROLE, oldVault);
    _grantRole(MINTER_ROLE, newVault);
    _grantRole(BURNER_ROLE, newVault);
    _grantRole(SHAREHOLDER_ROLE, newVault);
    _vault = newVault;
    emit VaultUpdate(_asset, newVault);
}
```

### Proof of Concept
1. Deploy `VaultShareToken` with `vault_ = vaultA`; `vaultA` holds `MINTER_ROLE`, `BURNER_ROLE`, `SHAREHOLDER_ROLE`.
2. Guardian calls `setVault(vaultB)` as part of a vault migration.
3. `vaultA` loses `MINTER_ROLE`/`BURNER_ROLE` (correct); `vaultB` receives neither role (bug); `_vault` now points at `vaultB`.
4. A shareholder calls `vaultB.requestDeposit(...)` then the manager calls `vaultB.approveDeposit(...)`, which internally calls `shareToken.mint(receiver, shares)`.
5. `mint` reverts with `AccessControlUnauthorizedAccount(vaultB, MINTER_ROLE)`, blocking every deposit approval (and analogously every redemption approval via `burn`) on the newly migrated vault until a guardian issues a follow-up `grantRole` transaction. [4](#0-3)
