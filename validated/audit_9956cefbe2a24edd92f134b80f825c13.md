### Title
Bridged-in supply cap checked only at mint time can permanently freeze user funds in failed LayerZero messages - (File: contracts/SyntheticToken.sol)

### Summary
`SyntheticToken._mint` enforces `maxBridgedInSupply` when called by `ProxyOFT._creditTo`, i.e. on the *receiving* side of a bridge transfer. The sending path (`ProxyOFT._debitFrom` → `SyntheticToken._burn`) only enforces `maxBridgedOutSupply` on the source chain and does nothing to guarantee the destination chain can actually mint. If a cross-chain transfer arrives at a chain whose `bridgedInSupply()` is at/above `maxBridgedInSupply` (or whose `maxTotalSupply` would be exceeded), the mint reverts, the LayerZero message is stored as failed, and every `retryMessage` call reverts the same way. The user's tokens are already burned on the source chain and there is no refund/recall path, so funds are stuck until the governor raises the cap — the exact asymmetric-quota bug class in the reference report.

### Finding Description
Bridging out calls `ProxyOFT.sendFrom` → `OFTCoreUpgradeable._send` → `ProxyOFT._debitFrom`, which checks only `isBridgingActive()`, destination-chain support, and then calls `syntheticToken.burn(from_, amount_)` [1](#0-0) . Inside `_burn`, the ProxyOFT caller path increments `totalBridgedOut` and enforces only the *source-side* cap `maxBridgedOutSupply` [2](#0-1) .

On the destination chain, `lzReceive` → `_nonblockingLzReceive` → `_sendAck` → `ProxyOFT._creditTo` → `syntheticToken.mint(to, amount)` [3](#0-2) [4](#0-3) . `_mint` increments `totalBridgedIn` and reverts with `SurpassMaxBridgingSupply` if `bridgedInSupply() > maxBridgedInSupply`, and also reverts with `SurpassMaxSynthSupply` if `totalSupply > maxTotalSupply` [5](#0-4) .

There is no symmetric check at send time that the *destination* chain has remaining bridged-in headroom — `sendFrom` cannot know it. When the destination mint reverts, the nonblocking LZ app stores the payload hash in `failedMessages`; `retryMessage` re-executes the same `_creditTo` → `mint` and reverts identically until the governor calls `updateMaxBridgedInSupply`/`updateMaxTotalSupply`. Unlike the Taiko case there isn't even a source-chain recall, so the burned tokens have no recovery path at all while the cap holds.

### Impact Explanation
Temporary freezing of user funds (and permanent if the cap is never raised): a user bridges X tokens from chain A to chain B; the burn succeeds on A, the mint on B reverts on the supply cap, and the tokens exist on neither chain until governance intervenes. Every affected in-flight transfer is trapped in `failedMessages` with no user-reachable alternative recovery (`retryOFTReceived` only covers `PT_SEND_AND_CALL`, and `sendAndCall` is disabled in `ProxyOFT` anyway [6](#0-5) ). The project's own docs acknowledge this dependency: "some scenarios where the protocol governor must act in order to unstuck transactions (e.g., increase caps)" [7](#0-6) .

### Likelihood Explanation
Caps are finite on all deployments: mainnet msUSD `maxBridgedInSupply` is 10M vs 40M `maxBridgedOutSupply`, and msETH uses 4500 for both [8](#0-7) . The gap is especially acute for msUSD, where the out-cap on one chain is 4× the in-cap — a chain can legitimately send far more than a peer can receive once the peer's net bridged-in supply saturates. Saturation can be reached by ordinary user bridging volume or by an attacker deliberately filling the remaining bridged-in headroom right before (or after) a victim's send, front-running the victim's receive. No privileged action is required to trigger; the checks at `_debitFrom` (`BridgingIsPaused`, `DestinationChainNotAllowed`, `SenderIsNotTheOwner`) do not prevent it.

### Recommendation
- When a destination-side mint fails on cap, allow the message to be retried *or* provide a governor/user callable escape that credits the amount back on the source chain (e.g., a documented recovery path that re-mints via `_creditTo` on the origin chain once headroom exists).
- Monitor `bridgedInSupply()` against `maxBridgedInSupply` per chain and raise caps before in-flight transfers saturate them; consider alerting on failed `lzReceive` payloads reverting with `SurpassMaxBridgingSupply`.
- Optionally, reorder accounting so `totalBridgedIn`/`totalBridgedOut` on paired chains make receive-headroom predictable, or keep `maxBridgedInSupply ≥ sum of peers' maxBridgedOutSupply` for each synth.

### Proof of Concept
Foundry fork on the destination chain (e.g., Optimism fork for the msUSD ProxyOFT):

```solidity
// 1. Observe state
uint256 bridgedIn = msUSD.bridgedInSupply();
uint256 cap = msUSD.maxBridgedInSupply();

// 2. Simulate saturating the in-cap: craft and deliver a PT_SEND payload
//    sized so bridgedIn + amount > cap (or have an attacker fill headroom first
//    by bridging in normally until bridgedInSupply() == cap).
bytes memory payload = abi.encode(PT_SEND, abi.encodePacked(victim), amount);

// 3. Deliver via LZ endpoint (or invoke stored failedMessages path):
//    _sendAck -> _creditTo -> msUSD.mint -> revert SurpassMaxBridgingSupply
vm.expectRevert(SurpassMaxBridgingSupply.selector);
proxyOFT.lzReceive(srcChainId, srcAddress, nonce, payload); // via endpoint

// 4. The payload is cached in failedMessages; retryMessage reverts identically
vm.expectRevert(SurpassMaxBridgingSupply.selector);
proxyOFT.retryMessage(srcChainId, srcAddress, nonce, payload);

// 5. Assert victim received nothing on this chain while the burn already
//    occurred on the source chain -> funds stuck until governor raises cap
//    via updateMaxBridgedInSupply.
```

The reverts stem from `SyntheticToken._mint` lines 338–348; the unrecoverable loop is `retryMessage` → `_nonblockingLzReceive` → `_sendAck` → `_creditTo` → `mint`.
