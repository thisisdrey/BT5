Audit Report

## Title
Truncating integer division in `convert_from_ether_decimals` underprices Snowbridge outbound-queue fees, allowing free/cheap spam of Ethereum-bound messages - (File: bridges/snowbridge/pallets/outbound-queue/src/lib.rs)

## Summary
`Pallet::<T>::calculate_fee` computes the remote (Ethereum-side) portion of a message's delivery fee in 18-decimal WAD precision, then downscales it via `convert_from_ether_decimals`, which performs a plain floor `checked_div` with no rounding-up and no minimum-fee floor. Any WAD-scaled value below the divisor (`1e8` for 10-decimal chains, `1e6` for 12-decimal chains) collapses to exactly `0`, and this is confirmed by the repository's own test.

## Finding Description
`calculate_fee` computes the remote fee entirely in wei/WAD terms and converts to local currency via `FixedU128` multiplier/exchange-rate division, then calls `convert_from_ether_decimals` to rescale to the local chain's decimals: [1](#0-0) 

`convert_from_ether_decimals` performs unconditional floor division: [2](#0-1) 

`T::Decimals` is constrained to `10` or `12` via `integrity_test`, fixing `denom` at `1e8` or `1e6`: [3](#0-2) 

This fee is charged to the sender via the public XCM export path (`EthereumBlobExporter::validate` → `OutboundQueue::validate`), which any account routing an XCM message to Ethereum (e.g., an AssetHub reserve transfer) can trigger without special privilege: [4](#0-3) [5](#0-4) 

Critically, the repository's own unit test confirms that even with fully valid, non-zero `PricingParameters` (which pass `PricingParameters::validate()`), the computed remote fee truncates to zero: [6](#0-5) 

`PricingParameters::validate()` only checks that fields are non-zero, not that they are large enough to survive the decimal rescaling without truncating to zero: [7](#0-6) 

This is exactly the reported pattern: correct 18-dp arithmetic degenerates to an incorrect (zero) result once naively rescaled to lower-dp local currency via plain truncating division, with no minimum-fee safeguard anywhere in the path.

## Impact Explanation
When the governance-configured `PricingParameters` place the WAD-scaled local fee below the fixed truncation threshold (`1e8`/`1e6`), any unprivileged user submitting an Ethereum-bound XCM message is charged `fee.remote = 0` while the message is still queued and must still be relayed and executed on Ethereum at real gas cost. This matches the "public underpriced work that degrades block production or stalls bridge processing" impact: an unprivileged actor can spam Ethereum-bound commands for free/underpriced, degrading relayer incentives and potentially congesting the outbound queue, with no privileged action required to *exploit* the bug (only to have set the triggering parameters, which the code's own validation fails to prevent).

## Likelihood Explanation
The repository's own test (`test_calculate_fees_with_valid_exchange_rate_but_remote_fee_calculated_as_zero`) demonstrates that fully valid, realistic parameter combinations (`exchange_rate=1`, `fee_per_gas=1`, `reward=1`, all non-zero and passing `validate()`) produce a zero remote fee — the code comment explicitly states this "should be avoided." Since `PricingParameters` are periodically updated market values and `validate()` does not guard against this truncation, the zero-fee condition is a realistic, reachable state, not a purely theoretical edge case, and is directly exploitable by any unprivileged sender once the condition holds.

## Recommendation
- Replace the floor `checked_div` in `convert_from_ether_decimals` with a ceiling/round-up division so any non-zero remote cost never truncates to a zero local fee.
- Enforce a protocol-level minimum non-zero fee, or reject messages whose computed fee rounds to zero.
- Strengthen `PricingParameters::validate` (or `set_pricing_parameters`) to reject configurations that would cause the computed local fee to round to zero for the configured `T::Decimals`.

## Proof of Concept
The existing test already reproduces the bug: [6](#0-5) 
With `exchange_rate = 1`, `fee_per_gas = 1`, `rewards = {local:1, remote:1}`, `multiplier = 1` — all valid per `PricingParameters::validate()` — `OutboundQueue::calculate_fee` returns `fee.remote == 0` despite non-zero configured pricing. An attacker can then submit an Ethereum-bound XCM message (via `SendMessage::validate`/`EthereumBlobExporter::validate`) while these or similarly-triggering parameters are live, paying zero remote-cost compensation for a message that still requires real Ethereum gas from relayers.

		pub(crate) fn calculate_fee(
			gas_used_at_most: u64,
			params: PricingParameters<T::Balance>,
		) -> Fee<T::Balance> {
			// Remote fee in ether
			let fee = Self::calculate_remote_fee(
				gas_used_at_most,
				params.fee_per_gas,
				params.rewards.remote,
			);

			// downcast to u128
			let fee: u128 = fee.try_into().defensive_unwrap_or(u128::MAX);

			// multiply by multiplier and convert to local currency
			let fee = FixedU128::from_inner(fee)
				.saturating_mul(params.multiplier)
				.checked_div(&params.exchange_rate)
				.expect("exchange rate is not zero; qed")
				.into_inner();

			// adjust fixed point to match local currency
			let fee = Self::convert_from_ether_decimals(fee);

			Fee::from((Self::calculate_local_fee(), fee))
		}

	fn validate(
		message: &Message,
	) -> Result<(Self::Ticket, Fee<<Self as SendMessageFeeProvider>::Balance>), SendError> {
		// The inner payload should not be too large
		let payload = message.command.abi_encode();
		ensure!(
			payload.len() < T::MaxMessagePayloadSize::get() as usize,
			SendError::MessageTooLarge
		);

		// Ensure there is a registered channel we can transmit this message on
		ensure!(T::Channels::contains(&message.channel_id), SendError::InvalidChannel);

		// Generate a unique message id unless one is provided
		let message_id: H256 = message
			.id
			.unwrap_or_else(|| unique((message.channel_id, &message.command)).into());

		let gas_used_at_most = T::GasMeter::maximum_gas_used_at_most(&message.command);
		let fee = Self::calculate_fee(gas_used_at_most, T::PricingParameters::get());

		let queued_message: VersionedQueuedMessage = QueuedMessage {
			id: message_id,
			channel_id: message.channel_id,
			command: message.command.clone(),
		}
		.into();
		// The whole message should not be too large
		let encoded = queued_message.encode().try_into().map_err(|_| SendError::MessageTooLarge)?;

		let ticket = Ticket { message_id, channel_id: message.channel_id, message: encoded };

		Ok((ticket, fee))
	}

#[test]
fn test_calculate_fees_with_valid_exchange_rate_but_remote_fee_calculated_as_zero() {
	new_tester().execute_with(|| {
		let gas_used: u64 = 250000;
		let price_params: PricingParameters<<Test as Config>::Balance> = PricingParameters {
			exchange_rate: FixedU128::from_rational(1, 1),
			fee_per_gas: 1_u32.into(),
			rewards: Rewards { local: 1_u32.into(), remote: 1_u32.into() },
			multiplier: FixedU128::from_rational(1, 1),
		};
		let fee = OutboundQueue::calculate_fee(gas_used, price_params.clone());
		assert_eq!(fee.local, 698000000);
		// Though none zero pricing params the remote fee calculated here is invalid
		// which should be avoided
		assert_eq!(fee.remote, 0);
	});
}
