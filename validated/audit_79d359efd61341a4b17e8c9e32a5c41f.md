### Title
`write_freq` slot-write-frequency limit is never enforced at the chunk-write choke point - ([File: stackslib/src/net/stackerdb/db.rs])

### Summary
`StackerDBConfig::write_freq` is documented as "the minimum wall-clock time between writes to the same slot" [1](#0-0)  and the schema even tracks a `write_time` column and exposes `get_slot_write_timestamps()` for this purpose [2](#0-1) . However, the actual chunk-acceptance function `StackerDBTx::try_replace_chunk`, which is the single write choke-point used by both the unsolicited HTTP `POST /v2/stackerdb/.../chunks` endpoint and the P2P chunk-download/store path, never checks `write_freq` or `write_time` at all — it only checks chunk size, signer, staleness, and `max_writes` [3](#0-2) .

### Finding Description
The only place `write_freq` is consulted is in the *sync scheduler* (`StackerDBSync::getchunks_getpages`), which uses it purely as an optimization to decide whether the **local peer should bother requesting** a chunk from a remote replica ("skip fetching if written too recently") [4](#0-3) . This is confirmed by an explicit comment on `validate_received_chunk`/`validate_downloaded_chunk`: *"NOTE: does not check write frequency, since the caller has different ways of doing this"* and *"no need to validate the timestamp, because we already skipped requesting it if it was written too recently"* [5](#0-4) [6](#0-5) .

That assumption is false for the unsolicited-write path: `RPCPostStackerDBChunkRequestHandler::try_handle_request` accepts a chunk directly from an HTTP client and calls `tx.try_replace_chunk(...)` with no prior `write_freq`/timestamp check anywhere in the handler [7](#0-6) . `try_replace_chunk` itself performs: chunk-size check, signer verification, stale-version check, and `max_writes` check — and then calls `insert_chunk`, which unconditionally stamps the current time and stores the new version [3](#0-2) [8](#0-7) . The `write_time` column is only ever consulted by the download-scheduling code, never by the write-acceptance code, so it functions like a dead/ignored equivalent of the reported `lastWeightUpdate` mapping: a value the protocol design relies on to gate a rate limit, but which the enforcement point never reads.

This lets any principal holding a valid StackerDB slot signing key push new chunk versions to a node as fast as it can produce valid signatures — limited only by `max_writes` (a per-reward-cycle version ceiling, not a temporal throttle) — via the unauthenticated-connection HTTP endpoint. Each accepted, higher-versioned chunk is then a legitimate candidate for `PeerNetwork` to relay/gossip and other nodes' `validate_received_chunk` to also accept and further relay (since `validate_received_chunk` explicitly skips frequency checks) [9](#0-8) .

### Impact Explanation
This breaks the intended equality "one accepted write per `write_freq` interval per slot" that the config is explicitly designed to enforce. The `write_freq` field is a modeled, deliberate anti-spam/anti-flood throttle (analogous to a "minimum interval" mapping never actually consulted), and its total bypass allows a legitimate slot-signer (which need not be a privileged/admin party — any principal listed in the StackerDB's control contract) to write and trigger downstream chunk-inventory advertisement/gossip at essentially unthrottled speed, up to `max_writes` versions. This is a bounded-but-real amplification of gossip/storage churn across a StackerDB replica set, consistent with a "bounded compute/bandwidth DoS via a legitimate but unthrottled write path" rather than requiring arbitrary traffic volume from an unauthorized party — the volume itself is the direct, intended consequence of the missing check, not incidental flooding.

### Likelihood Explanation
High, mechanically: the code path is simple and always reachable by anyone with a valid slot-signing key (a normal, unprivileged StackerDB writer, e.g., a signer client), and does not require any race condition, network position, or privileged role — merely sending consecutive valid `POST /v2/stackerdb/.../chunks` requests with incrementing `slot_version`.

### Recommendation
Enforce `write_freq` inside `StackerDBTx::try_replace_chunk` (or immediately before it in the shared handler path) by comparing the incoming write's time to `slot_validation.write_time` (which is already fetched) and rejecting with a `TooFrequentSlotWrites` error (which already exists in the error enum [10](#0-9)  but appears unused in the write path) when `now < write_time + write_freq`. Ensure this check applies uniformly to both the HTTP push path and the sync/download path, rather than relying on the downloader's own scheduling heuristic as the sole enforcement mechanism.

### Proof of Concept
1. Register/obtain a valid StackerDB slot signing key for a contract that configures a non-zero `write_freq` (e.g., `write_freq: 120`).
2. Sign a `StackerDBChunkData` with `slot_version = 1` and `POST` it to `/v2/stackerdb/<address>/<contract>/chunks`; observe acceptance via `try_replace_chunk` [3](#0-2) .
3. Immediately (well within the 120s `write_freq` window) sign and `POST` `slot_version = 2`, then `3`, etc. Each request is accepted with no delay enforced, because neither `poststackerdbchunk.rs` [11](#0-10)  nor `try_replace_chunk` [3](#0-2)  consults `write_time`/`write_freq`.
4. Each accepted write updates the DB's slot inventory and is eligible to be relayed to the peer's DB neighbors, demonstrating the throttle intended by `write_freq` is fully bypassed.

    pub fn try_replace_chunk(
        &self,
        smart_contract: &QualifiedContractIdentifier,
        slot_desc: &SlotMetadata,
        chunk: &[u8],
    ) -> Result<(), net_error> {
        // Check per-replica chunk-size cap.
        if (chunk.len() as u64) > self.config.chunk_size {
            return Err(net_error::StackerDBChunkTooBig(chunk.len()));
        }

        let slot_validation = self
            .get_slot_validation(smart_contract, slot_desc.slot_id)?
            .ok_or(net_error::NoSuchSlot(
                smart_contract.clone(),
                slot_desc.slot_id,
            ))?;

        if !slot_desc.verify(&slot_validation.signer)? {
            return Err(net_error::BadSlotSigner(
                slot_validation.signer,
                slot_desc.slot_id,
            ));
        }
        if slot_desc.slot_version <= slot_validation.version {
            return Err(net_error::StaleChunk {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
            });
        }
        if slot_desc.slot_version > self.config.max_writes {
            return Err(net_error::TooManySlotWrites {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
                max_writes: self.config.max_writes,
            });
        }
        self.insert_chunk(smart_contract, slot_desc, chunk)
    }
