### Title
Unsafe truncating `DataWord.intValue()` cast used for TVM memory addressing bypasses energy-safe bounds checks - ([File: actuator/src/main/java/org/tron/core/vm/program/Program.java])

### Summary
The reported Tokensoft bug is a classic "unsafe narrowing cast" pattern: a value is validated/limited using one representation (`uint256`) but a *different, truncating* cast of the same value is used for the state-mutating effect (`uint120`), so a value that overflows the smaller type silently wraps instead of being rejected. The same pattern exists in java-tron's TVM memory-access layer: `DataWord.intValue()` truncates a full 256-bit stack value down to a 32-bit `int` by repeated `(intVal << 8) + byte` shifting, which in Java silently wraps (keeping only the low 4 bytes) instead of throwing, even though its own Javadoc claims it "checks for lost information" and "throws ArithmeticException". `Program.memorySave(DataWord,DataWord)`, `Program.memoryLoad(DataWord)`, and `Program.memoryExpand(DataWord,DataWord)` use this unsafe `intValue()` directly on attacker-controlled stack operands (MSTORE/MLOAD offsets, CALL `outDataOffs`/`outDataSize`), while the corresponding energy-cost/overflow-check code paths (`EnergyCost.getSha3Cost`, `codeCopyAction`, `callDataCopyAction`, `revertAction` in `OperationActions.java`) consistently use the safe `intValueSafe()`/`longValueSafe()` conversions that clamp to `Integer.MAX_VALUE`/`Long.MAX_VALUE` instead of wrapping.

### Finding Description
`DataWord.intValue()` at [1](#0-0)  iterates over all 32 bytes of the word and shifts an `int` accumulator by 8 bits per byte. Because `int` is only 32 bits wide, this operation discards all but the lowest 4 bytes of the 256-bit value with no exception, contradicting the method's own documented contract ("throws ArithmeticException — if this will not fit in an int") [2](#0-1) . The safe counterpart `intValueSafe()` correctly detects overflow via `bytesOccupied()` and clamps to `Integer.MAX_VALUE` [3](#0-2) .

`Program.java` mixes both conversions for memory addressing that is entirely attacker-controlled via TVM opcode stack operands:
- `memorySave(DataWord addrB, DataWord value)` uses raw `addrB.intValue()` [4](#0-3) 
- `memoryExpand(DataWord outDataOffs, DataWord outDataSize)` uses raw `.intValue()` on both offset and size [5](#0-4) 
- `memoryLoad(DataWord addr)` uses raw `addr.intValue()` [6](#0-5) 

By contrast, sibling opcode handlers in `OperationActions.java` explicitly use the safe conversion for the same class of operand (memory offsets/lengths): `callDataCopyAction` uses `memOffsetData.intValueSafe()` [7](#0-6) , and `codeCopyAction`/`revertAction` likewise use `.intValueSafe()` for offsets and sizes [8](#0-7) [9](#0-8) . `exeCall` (used for CALL/STATICCALL/DELEGATECALL/CALLCODE) pops `outDataOffs`/`outDataSize` as raw `DataWord`s and passes them straight into `program.memoryExpand(outDataOffs, outDataSize)` — the unsafe path [10](#0-9) .

Energy accounting for memory growth (`EnergyCost.calcMemEnergy`/`memNeeded`, e.g. as used in `getSha3Cost`) computes cost based on `longValueSafe()`/safe conversions that correctly detect out-of-range operands and throw `OutOfMemoryException` [11](#0-10) . Because the *actual* memory access performed later goes through the unsafe `.intValue()` path, a contract can construct a stack operand whose full 256-bit value is huge (so it would normally be rejected/charged an enormous, unaffordable energy cost by the safe-path checks) but whose low 4 bytes decode to a small, cheap offset. This creates a divergence between what is charged/validated and what memory address is actually touched.

### Impact Explanation
This mismatch between the "charged/validated" representation and the "actually used" representation of the same operand is functionally identical to the reported Distributor bug class (validate against one width, act on a differently-truncated value). In the TVM memory subsystem this can be leveraged by any account that can submit a `TriggerSmartContract` transaction (an unprivileged contract-call path) to:
- Desynchronize energy metering from actual memory footprint, potentially bypassing the intended `MEM_LIMIT`/OutOfMemory protections that are supposed to bound VM memory growth, and
- Cause inconsistent/undefined memory addressing (writes/reads at unintended offsets), risking incorrect execution results, `ArrayIndexOutOfBoundsException`/crash in the executing node, or divergent execution results between nodes if the underlying `Memory` implementation handles negative/wrapped ints differently in different JVMs.

Both outcomes are in-scope: an energy-metering/DoS bypass and node crash potential for TVM opcode handling reachable from a single signed transaction.

### Likelihood Explanation
Any external contract call (`TriggerSmartContract`) that executes bytecode reaching MSTORE/MLOAD/CALL-family opcodes with attacker-chosen 256-bit stack operands can exercise this path with no special privileges. Constructing a DataWord whose full value is large but whose low 4 bytes are small is trivial (e.g., `PUSH32 0x00000001_00000000...00000000_00000064` type patterns) — an unprivileged deployer/caller fully controls this.

### Recommendation
Replace all uses of `DataWord.intValue()`/raw `.intValue()` for memory-offset and memory-size operands in `Program.memorySave(DataWord,DataWord)`, `Program.memoryExpand(DataWord,DataWord)`, and `Program.memoryLoad(DataWord)` with the overflow-safe `intValueSafe()`, matching the pattern already used in `OperationActions.callDataCopyAction`/`codeCopyAction`/`revertAction`. Additionally, either fix `DataWord.intValue()`'s implementation to actually throw `ArithmeticException` on overflow (as documented) or rename/deprecate it to make clear it silently truncates, to prevent future unsafe use.

### Proof of Concept
Not independently executed (index-only investigation); the code-path analysis above is derived directly from `Program.java`, `DataWord.java`, `OperationActions.java`, and `EnergyCost.java`. A concrete PoC would deploy a minimal contract that issues `MSTORE`/`CALL` with a `PUSH32` operand such as `0x0000000100000000000000000000000000000000000000000000000000000064` (value > `Integer.MAX_VALUE` but low 4 bytes = `0x64`=100) as the memory offset, and observe that `Program.memorySave`/`memoryExpand` operate at offset `100` rather than raising the `OutOfMemoryException` that the safe-conversion energy-cost paths (e.g. `EnergyCost.calcMemEnergy`) would otherwise trigger for such a large offset — this divergence would need to be confirmed by running the TVM test harness (e.g. extending `framework/src/test/java/org/tron/common/runtime/vm/` tests) in a live Devin session, which this ask-only analysis could not do.

   * In case of int overflow returns Integer.MAX_VALUE otherwise works as #intValue()

  public int intValueSafe() {
    int bytesOccupied = bytesOccupied();
    int intValue = intValue();
    if (bytesOccupied > 4 || intValue < 0) {

    }

  public static void codeCopyAction(Program program) {
    byte[] fullCode = program.getCode();

    int memOffset = program.stackPop().intValueSafe();
    int codeOffset = program.stackPop().intValueSafe();
    int lengthData = program.stackPop().intValueSafe();

    int sizeToBeCopied = lengthData;
    if ((long) codeOffset + lengthData > fullCode.length) {
      sizeToBeCopied = fullCode.length < codeOffset ? 0 : fullCode.length - codeOffset;
    }

    byte[] codeCopy = new byte[lengthData];

    if (codeOffset < fullCode.length) {
      System.arraycopy(fullCode, codeOffset, codeCopy, 0, sizeToBeCopied);
    }

    program.memorySave(memOffset, codeCopy);
    program.step();
  }
