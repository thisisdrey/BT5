### Title
Per-IP QoS bypass via cheap IPv6 address churn in `ConnectionRateLimiter` (no /64 subnet aggregation) - (File: streamer/src/nonblocking/connection_rate_limiter.rs)

### Summary
`ConnectionRateLimiter::register_connection` keys the `KeyedRateLimiter<IpAddr>` token bucket strictly by the exact source `IpAddr`, with no normalization or aggregation to a subnet prefix for IPv6. An unprivileged attacker who owns (or is delegated, as is common and effectively free from many ISPs/cloud providers) a `/64` IPv6 block can rotate through distinct addresses within that block, and each new address is allocated a fresh, fully-topped-off `TokenBucket`, defeating the intended per-source throttle. The port-churn variant on a single IPv4/IPv6 address, however, does **not** bypass the limiter, since the key is the IP address only and does not include the source port.

### Finding Description
`ConnectionRateLimiter::register_connection` calls `self.limiter.consume_tokens(*ip, 1)` [1](#0-0) , and `KeyedRateLimiter::consume_tokens` looks up/creates an entry solely by the `K` (here `IpAddr`) value in a `DashMap<K, TokenBucket>`; if no entry exists for that exact key, a brand-new bucket is cloned from `prototype_bucket` (starting with full/initial tokens) and inserted [2](#0-1) .

Because the key is the full `IpAddr` (all 128 bits for IPv6) rather than a normalized subnet (e.g., `/64` or `/56`), an attacker holding a `/64` allocation can send connection attempts from a virtually unlimited number of distinct last-64-bit suffixes. Each distinct address:
- Is treated by `is_allowed`/`register_connection` as "never seen before," so it is always allowed (`None => true`) [3](#0-2) .
- Gets its own fresh `TokenBucket` cloned from the prototype with full initial tokens, so `consume_tokens` always succeeds for the first `initial_tokens` uses of that address [4](#0-3) .

The `CONNECTION_RATE_LIMITER_CLEANUP_SIZE_THRESHOLD` / LazyLRU `maybe_shrink` mechanism bounds only *memory* usage of the map (evicting least-recently-used entries once the map grows too large) [5](#0-4) ; it does nothing to prevent an attacker from continuously minting brand-new, fully-refilled buckets for freshly chosen IPv6 suffixes. Thus the "per-IP" throttle is only effective against attackers confined to a single source address — it provides no aggregate limiting for an attacker who can cheaply vary the low-order bits of an IPv6 address within an owned prefix.

The port-churn variant described in the question (opening/aborting connections from many ephemeral source ports on the *same* IP) does not bypass anything: the rate-limiter key is `IpAddr` only (no port component), so repeated connections from the same IP correctly continue to draw down the same bucket, matching the existing unit test behavior (`test_connection_rate_limiter`) [6](#0-5) .

### Impact Explanation
This matches the QoS-evasion / per-IP limit bypass category referenced in the question's scope: an attacker with control over a `/64` IPv6 block (a trivially obtainable resource, as most ISPs/hosting providers hand out at least a `/64` per customer) can generate effectively unlimited independent per-IP token buckets, each granting the attacker the full connection burst allowance. Because `register_connection` is the gate used to admit/deny QUIC connections into the streamer, this allows the attacker to sustain far more admitted connections than the per-IP policy is meant to allow, consuming TPU-facing connection/stream capacity that would otherwise be shared fairly among legitimate unstaked senders limited to their single real IP.

### Likelihood Explanation
The precondition is only "attacker has more than one usable IPv6 address," which is realistic without any staked/privileged access — many residential and cloud IPv6 allocations default to a `/64` or larger per customer. No leader/staked cooperation is required; the attacker only needs to originate QUIC connections from many suffixes of their own delegated prefix, a purely client-side action. This is straightforward to repeat indefinitely and scales with how many addresses the attacker chooses to rotate through.

### Recommendation
Normalize the key used by `ConnectionRateLimiter` for IPv6 addresses to a fixed prefix (e.g., the standard `/64` subnet, matching how many other Solana/Agave IP-based accounting mechanisms treat IPv6) before inserting/looking up in the `KeyedRateLimiter`, so that all addresses within an attacker-controlled prefix share a single token bucket rather than each minting an independent one. IPv4 addresses can remain keyed by exact address (or normalized to a smaller aggregation such as /32 unchanged, since IPv4 address space is not free to acquire in bulk).

### Proof of Concept
```rust
// streamer/src/nonblocking/connection_rate_limiter.rs (new test)
#[tokio::test]
async fn test_ipv6_subnet_bypasses_per_ip_limit() {
    use std::net::Ipv6Addr;

    // Small burst so bypass is easy to observe.
    let limiter = ConnectionRateLimiter::new(3, 3, 4);

    // Fixed /64 prefix, attacker rotates the low 64 bits.
    let prefix: u128 = 0x2001_0db8_0000_0001_0000_0000_0000_0000;

    let mut allowed_count = 0;
    for suffix in 0u128..1000 {
        let ip = IpAddr::V6(Ipv6Addr::from(prefix | suffix));
        if limiter.register_connection(&ip) {
            allowed_count += 1;
        }
    }

    // Expectation under a correctly-scoped /64 aggregate limiter: allowed_count
    // should be bounded by the configured burst (3) for the whole /64 prefix.
    // Actual behavior: each unique suffix gets its own fresh bucket, so
    // allowed_count == 1000 (every single connection attempt is admitted),
    // demonstrating the per-IP QoS limit provides no effective throttling
    // against IPv6 /64 address churn.
    assert!(
        allowed_count <= 3,
        "expected per-/64 burst limit to cap admissions at 3, got {allowed_count}"
    );
}
```
Running this test against current code will show `allowed_count == 1000`, failing the assertion and demonstrating the bypass. A fuzz/invariant version can randomize the suffix ordering and assert `sum(over all suffixes) of granted tokens <= burst`, which will fail identically.

    fn maybe_shrink(&self) {
        let mut actual_len = 0;
        let target_shard_size = self.target_capacity / self.data.shards().len();
        if target_shard_size == 0 {
            return;
        }
        let mut entries = Vec::with_capacity(target_shard_size * 2);
        for shardlock in self.data.shards() {
            let mut shard = shardlock.write();

            if shard.len() <= target_shard_size * 3 / 2 {
                actual_len += shard.len();
                continue;
            }
            entries.clear();
            entries.extend(
                shard.drain().map(|(key, value)| {
                    (key, value.get().last_update.load(Ordering::SeqCst), value)
                }),
            );

            entries.select_nth_unstable_by_key(target_shard_size, |(_, last_update, _)| {
                Reverse(*last_update)
            });

            shard.extend(
                entries
                    .drain(..)
                    .take(target_shard_size)
                    .map(|(key, _last_update, value)| (key, value)),
            );
            debug_assert!(shard.len() <= target_shard_size);
            actual_len += shard.len();
        }
