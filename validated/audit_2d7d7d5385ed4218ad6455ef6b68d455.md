### Title
Intra-batch write-write account lock conflicts are not detected, allowing two conflicting transactions to hold write locks simultaneously - ([File: accounts-db/src/account_locks.rs])

### Summary
`AccountLocks::try_lock_transaction_batch` performs a validation pass that calls the read-only `can_lock_accounts` check for every entry in the batch *before* any entry's locks are actually applied via `lock_accounts` in a second pass. Because `can_lock_accounts` only inspects the current (unmutated) `write_locks`/`readonly_locks` maps and the mutation only happens afterward, two transactions in the same batch that write the same pubkey both see the account as unlocked during validation, so both get `Ok(())`, and both subsequently have their write lock counts incremented for the same key.

### Finding Description
`try_lock_transaction_batch` [1](#0-0)  first loops over `validated_batch_keys` calling `self.can_lock_accounts(keys.clone())`, which is a `&self` read-only check [2](#0-1) . Crucially, this loop never calls the mutating `lock_accounts`/`lock_write` for any entry while validating subsequent entries — locking only happens in the second, separate `.into_iter().map(...)` pass. `can_write_lock` checks `!is_locked_readonly(key) && !is_locked_write(key)` against the current map state [3](#0-2) , which has not yet been updated for any transaction earlier in the same batch during the validation pass. Consequently, if tx0 and tx1 in the same call both write the same pubkey, both pass `can_lock_accounts` as `Ok`, and both are then locked in the second pass via `lock_write`, which merely increments a counter [4](#0-3)  rather than re-checking exclusivity.

This is directly reachable from the untrusted transaction ingestion path: `Accounts::lock_accounts` collects `validated_batch_keys` for a batch of transactions and calls `try_lock_transaction_batch` under a single mutex acquisition [5](#0-4) , which is invoked by `Bank::try_lock_accounts_with_results` / `prepare_sanitized_batch_with_results` [6](#0-5) , used by banking stage when preparing a locked batch of leader-received transactions for execution [7](#0-6) . An unstaked attacker submitting a batch of transactions to a leader's TPU can control the relative ordering/content of transactions within a single packet batch, and there is no other guard (sigverify, QoS, dedup) that detects same-pubkey write-write conflicts within one batch — dedup only catches identical message hashes via `AlreadyProcessed` [8](#0-7) , which does not apply to two distinct transactions writing the same account.

The repository's own existing test, `test_accounts_locks_intrabatch_conflicts`, documents this exact behavior by asserting that an in-batch conflicting pair returns `Ok(()), Ok(())` [9](#0-8) , confirming that both transactions in a conflicting pair currently succeed rather than exactly one failing with `AccountInUse`.

### Impact Explanation
This allows two write-conflicting transactions to both receive successful lock results and be scheduled/committed into the same TransactionBatch, meaning the bank's execution/commit pipeline would process both transactions believing account isolation is guaranteed by the lock subsystem for the account, when it is not. This falls under the "invalid recorded block" / consensus-safety category since the account-locking primitive is supposed to be the fundamental guarantee that prevents concurrent mutation of the same account state within a leader's processed batch; violating it undermines core execution serialization invariants documented directly in the function's own doc comment ("prevent multiple threads from modifying the same account state at the same time") [10](#0-9) .

### Likelihood Explanation
The precondition is simply constructing a batch (or set of QoS-passed transactions) where two transactions write the same pubkey — trivially achievable by an unstaked remote attacker submitting ordinary transfer transactions to two different destination or fee-payer/writable accounts colliding on a shared writable account, with distinct message hashes so `AlreadyProcessed` dedup does not intervene. It is deterministically reproducible on every call with such input, as shown by the existing (mislabeled) test.

### Recommendation
Merge the validation and locking passes in `try_lock_transaction_batch` into a single pass so that each transaction's lock is applied (mutating `write_locks`/`readonly_locks`) immediately after it passes its own check, before checking the next transaction in the batch — matching the intended "first come, first locked" semantics within a batch.

### Proof of Concept
```rust
// accounts-db/src/account_locks.rs (unit test)
#[test]
fn test_try_lock_transaction_batch_intra_batch_write_conflict() {
    let pubkey = Pubkey::new_unique();
    let mut locks = AccountLocks::default();

    let tx0_keys = vec![(&pubkey, true)]; // write
    let tx1_keys = vec![(&pubkey, true)]; // write, same key

    let batch = vec![
        Ok(tx0_keys.into_iter()),
        Ok(tx1_keys.into_iter()),
    ];

    let results = locks.try_lock_transaction_batch(batch);

    let ok_count = results.iter().filter(|r| r.is_ok()).count();
    assert_eq!(
        ok_count, 1,
        "exactly one write-conflicting transaction should succeed, got: {results:?}"
    );
}
```
Expected current (buggy) behavior: both entries return `Ok(())` (`ok_count == 2`), failing the assertion, matching the pattern already present in `test_accounts_locks_intrabatch_conflicts` [9](#0-8) .

    pub fn try_lock_transaction_batch<'a>(
        &mut self,
        mut validated_batch_keys: Vec<
            TransactionResult<impl Iterator<Item = (&'a Pubkey, bool)> + Clone>,
        >,
    ) -> Vec<TransactionResult<()>> {
        validated_batch_keys.iter_mut().for_each(|validated_keys| {
            if let Ok(keys) = validated_keys.as_ref()
                && let Err(e) = self.can_lock_accounts(keys.clone())
            {
                *validated_keys = Err(e);
            }
        });

        validated_batch_keys
            .into_iter()
            .map(|available_keys| available_keys.map(|keys| self.lock_accounts(keys)))
            .collect()
    }

    fn can_lock_accounts<'a>(
        &self,
        keys: impl Iterator<Item = (&'a Pubkey, bool)>,
    ) -> TransactionResult<()> {
        for (key, writable) in keys {
            if writable {
                if !self.can_write_lock(key) {
                    return Err(TransactionError::AccountInUse);
                }
            } else if !self.can_read_lock(key) {
                return Err(TransactionError::AccountInUse);
            }
        }

        Ok(())
    }

    pub fn lock_accounts<'a>(
        &self,
        txs: impl Iterator<Item = &'a (impl SVMMessage + 'a)>,
        results: impl Iterator<Item = Result<()>>,
        tx_account_lock_limit: usize,
    ) -> Vec<Result<()>> {
        // Validate the account locks, then get keys and is_writable if successful validation.
        // We collect to fully evaluate before taking the account_locks mutex.
        let validated_batch_keys = txs
            .zip(results)
            .map(|(tx, result)| {
                result
                    .and_then(|_| validate_account_locks(tx.account_keys(), tx_account_lock_limit))
                    .map(|_| TransactionAccountLocksIterator::new(tx).accounts_with_is_writable())
            })
            .collect::<Vec<_>>();

        let account_locks = &mut self.account_locks.lock().unwrap();
        account_locks.try_lock_transaction_batch(validated_batch_keys)
    }

    /// Attempt to take locks on the accounts in a transaction batch, and their cost
    /// limited packing status and duplicate transaction conflict status
    pub fn try_lock_accounts_with_results(
        &self,
        txs: &[impl TransactionWithMeta],
        tx_results: impl Iterator<Item = Result<()>>,
    ) -> Vec<Result<()>> {
        let tx_account_lock_limit = self.get_transaction_account_lock_limit();

        // we must fail transactions that duplicate a prior message hash
        let mut batch_message_hashes = AHashSet::with_capacity(txs.len());
        let tx_results = tx_results
            .enumerate()
            .map(|(i, tx_result)| match tx_result {
                Ok(()) => {
                    // `HashSet::insert()` returns `true` when the value does *not* already exist
                    if batch_message_hashes.insert(txs[i].message_hash()) {
                        Ok(())
                    } else {
                        Err(TransactionError::AlreadyProcessed)
                    }
                }
                Err(e) => Err(e),
            });

        self.rc
            .accounts
            .lock_accounts(txs.iter(), tx_results, tx_account_lock_limit)
    }
