Audit Report

## Title
Permanently blocked bounty beneficiary can lock a parent bounty forever via `ChildBountiesPerParent` - (File: `substrate/frame/multi-asset-bounties/src/lib.rs`)

## Summary
`pallet-multi-asset-bounties` requires `ChildBountiesPerParent::<T, I>::get(parent_bounty_id) == 0` before a parent bounty can be closed or awarded, and this counter is decremented only in `remove_bounty`, which is only reached from the `PaymentState::Succeeded` branches inside `check_status`. If the payout (or refund) to a child bounty's beneficiary can never succeed — e.g., the beneficiary account is frozen/blocked for the relevant asset — the child bounty is permanently stuck in `PayoutAttempted`/`RefundAttempted`, `retry_payment` keeps re-attempting and failing indefinitely, `ChildBountiesPerParent` never reaches zero, and both `close_bounty(parent_id, None)` and `award_bounty(parent_id, None, ...)` are permanently blocked.

## Finding Description
`award_bounty` (parent-level, `child_bounty_id: None`) and `close_bounty` (parent-level) both gate on `ChildBountiesPerParent::<T, I>::get(parent_bounty_id) == 0`, returning `Error::<T, I>::HasActiveChildBounty` otherwise. [1](#0-0) [2](#0-1) 

`ChildBountiesPerParent` is only decremented inside `remove_bounty`, which is called only from the `PaymentState::Succeeded` arms of `check_status` for `RefundAttempted` and `PayoutAttempted` statuses. [3](#0-2) [4](#0-3) 

A child bounty enters `PayoutAttempted` when the curator calls `award_bounty`, which calls `do_process_payout_payment` targeting the caller-supplied `beneficiary`. [5](#0-4) 

If that payment can never succeed, `check_status`'s `PayoutAttempted` arm keeps returning `PaymentState::Pending | PaymentState::Failed | PaymentState::Attempted { .. }`, which simply re-writes the same `PayoutAttempted` status rather than resolving it — there is no branch that clears the status, decrements the counter, or otherwise unblocks the parent on failure. [6](#0-5) 

`retry_payment` exhibits the identical structure: on `PayoutAttempted`, it simply re-invokes `do_process_payout_payment` and rewrites the same status, again with no failure-recovery or timeout path, no matter how many times it is called. [7](#0-6) 

I was unable to inspect the bodies of `do_process_payout_payment` / `do_check_payout_payment_status` (only their call sites/signatures were located within the tool budget) or the concrete `Paymaster` trait/implementation to confirm the exact semantics of a payment to a frozen/blocked asset account (e.g., whether `pallet-assets`-style `Frozen`/`Blocked` account status actually causes `Paymaster::pay` to report `Failed` rather than some other outcome). However, the structural gap in `check_status`/`retry_payment`/`award_bounty`/`close_bounty` — no path exists anywhere in the pallet's public entrypoints to release the `ChildBountiesPerParent` slot for a child bounty whose payout/refund can never complete — is directly confirmed by reading the code. There is no force-cancel, timeout-based write-off, or beneficiary-redirect entrypoint for a stuck `PayoutAttempted`/`RefundAttempted` child bounty anywhere in the pallet.

## Impact Explanation
This matches the "permanent user-fund or bridge-state lock" impact category: if a payout to a beneficiary can permanently fail (a condition plausible whenever `T::Paymaster` is backed by an asset system supporting account freezing/blocking, and beneficiaries are supplied via `T::BeneficiaryLookup` from curator/attacker-influenced input), the parent bounty's funds and any state gated on `close_bounty`/`award_bounty` (including sibling child bounties' funding source) become permanently locked with no recovery path in the pallet's public API.

## Likelihood Explanation
Reaching this state requires only ordinary, unprivileged signed calls (`award_bounty`, `check_status`, `retry_payment`) plus one condition external to this pallet: the beneficiary account being permanently unable to receive the asset via the configured `Paymaster`. Whether this condition is actually reachable in a concrete deployment depends on the specific `Paymaster`/asset-kind implementation wired into the runtime, which was not fully verified here — this is a plausible but not fully confirmed precondition given the incomplete trace of `do_process_payout_payment`/`do_check_payout_payment_status` and the `Paymaster` trait implementation. The structural absence of any escape hatch in the pallet itself, however, is verified directly from the code.

## Recommendation
Add an administrative or timeout-gated recovery path (e.g., a `force_close`/`write_off_stuck_payment` call restricted to `RejectOrigin` or the parent curator) that can remove a child bounty stuck in `PayoutAttempted`/`RefundAttempted` and decrement `ChildBountiesPerParent` without requiring the underlying payment to succeed, or allow redirecting a permanently failing payout to an alternate beneficiary so `remove_bounty` can eventually execute normally.

## Proof of Concept
1. Create a parent bounty and a child bounty using an asset kind serviced by a `Paymaster` whose backing asset system supports permanently blocking/freezing an account (e.g., `pallet-assets` `AccountStatus::Frozen`/`Blocked`, per existing test patterns such as `transferring_to_blocked_account_should_not_work` in `substrate/frame/assets/src/tests.rs`).
2. As curator, call `award_bounty(parent_id, Some(child_id), beneficiary)` where `beneficiary` is/becomes frozen/blocked for that asset.
3. `do_process_payout_payment` initiates the payment; the underlying transfer to the blocked beneficiary fails, moving the child bounty to `PayoutAttempted { payment_status: Failed/Pending }`.
4. Repeatedly call `check_status(parent_id, Some(child_id))` and `retry_payment(parent_id, Some(child_id))` — per the code at lines 1256-1292 and 1372-1390, the status never leaves `PayoutAttempted`.
5. `ChildBountiesPerParent::<T, I>::get(parent_id)` remains `1` forever (per `remove_bounty`, lines 1663-1682, never being invoked).
6. `close_bounty(parent_id, None)` and `award_bounty(parent_id, None, ...)` now always fail with `Error::<T, I>::HasActiveChildBounty` (lines 1013-1019, 1099-1105), permanently locking the parent bounty.

Note: full confirmation that step 3 (payment failure against a frozen/blocked account) actually occurs as described requires reading `do_process_payout_payment`, `do_check_payout_payment_status`, and the concrete `Paymaster` implementation used by a target runtime, which could not be completed within the available tool budget.
