### Title
Unvalidated attacker-controlled offsets in `VerifyTransferProof` precompile cause out-of-bounds array access - ([File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java])

### Summary
This is analogous to CVE-2017-17095: a fixed-size buffer is allocated/validated against one size check, but the code then uses attacker-supplied length/offset fields taken from the same input to index into that buffer without bounds-checking the offsets against the buffer's actual size, producing an out-of-bounds access.

### Finding Description
`VerifyTransferProof.execute(byte[] data)` (the TVM precompile at address `0x1000002`) is reachable directly from any contract call via `CALL`/`STATICCALL` when `VMConfig.allowShieldedTRC20Transaction()` is enabled [2](#0-1) . The method only checks that `data.length` is one of four fixed values (2080/2368/2464/2752) [3](#0-2) .

It then reads three offsets directly from attacker-controlled `data` — `spendOffset`, `spendAuthSigOffset`, `receiveOffset` — via `parseInt(data, 0/32/64)` [4](#0-3) , and uses those raw offsets to read `spendCount`, `spendAuthSigCount`, `receiveCount` from arbitrary positions inside `data` [5](#0-4) . Only the *counts* are range-checked (1-2) [6](#0-5) , but `spendOffset`, `spendAuthSigOffset`, and `receiveOffset` themselves are never validated to be within `[0, data.length)`, nor is `spendOffset + 320*spendCount + 128 + 192` (etc.) checked against `data.length` before the subsequent `System.arraycopy` loops copy `nullifier`, `anchor`, `spendCv`, `rk`, `spendProof`, `spendAuthSig`, `receiveCm`, `receiveCv`, `receiveEpk`, `receiveProof` out of `data` at `spendOffset + 320*i + ...` and `receiveOffset + 288*i + ...` [7](#0-6) . `parseInt`/`parseLong` on this class read 32-byte big-endian words and can yield arbitrary `int` values, including negative ones, since there's no sign or magnitude check shown before use as an array index/offset.

This mirrors the CVE-2017-17095 bug class exactly: fixed/validated top-level container size, but internal length/offset fields taken from the same untrusted buffer are trusted for subsequent memory copy operations without cross-checking against the actual buffer bounds.

### Impact Explanation
Because Java arrays throw `ArrayIndexOutOfBoundsException` on out-of-bounds `System.arraycopy` rather than silently corrupting heap memory, the practical impact in the JVM is a runtime exception rather than a classic C heap overflow. That exception is only caught by the generic `catch (Throwable any)` block, so it does not crash the whole node, but it demonstrates uncontrolled/unauthenticated internal-offset trust from a permissionless entry point (any contract call can invoke this precompile through `CALL`), and any future refactor to native/unsafe/off-heap buffers (as already happens through JNI calls into `JLibrustzcash`) would reintroduce a genuine heap-overflow-class vulnerability. As currently written, the primary confirmed effect is an uncontrolled exception path (potential resource waste/DoS at worst) rather than fund theft or RCE, since it is guarded by try/catch and TRC20 shielded transfers require the feature switch `allowShieldedTRC20Transaction()`.

### Likelihood Explanation
High reachability: the precompile is invoked by any signed transaction that triggers a smart-contract call to precompile address `0x1000002` when the shielded TRC20 feature is enabled — no special privilege is required, matching the "unprivileged transaction broadcaster/contract deployer" reachability requirement. Constructing malicious offset values is trivial since `spendOffset`/`spendAuthSigOffset`/`receiveOffset` are fully attacker-controlled 32-byte fields.

### Recommendation
Validate that `spendOffset`, `spendAuthSigOffset`, and `receiveOffset` are non-negative and, together with the derived per-record sizes (`320*spendCount`, `64*spendAuthSigCount`, `288*receiveCount`), do not exceed `data.length` before performing any `System.arraycopy`. Apply the same bounds validation pattern already used for `leafCount` (`if (leafCount >= TREE_WIDTH ...) return`) to all offset/length fields parsed from `data` in `VerifyMintProof`, `VerifyTransferProof`, and `VerifyBurnProof`.

### Proof of Concept
Craft a `data` payload of exactly one of the whitelisted lengths (e.g., 2080 bytes) where the 32-byte big-endian value at offset 0 (`spendOffset`) encodes a large positive integer close to `Integer.MAX_VALUE`, and set the value at `data[spendOffset]` region (or rely on it reading past `data.length`) such that `spendCount` parses to 1 or 2 to pass the count check, while `spendOffset + 320*spendCount + 128 + 192` exceeds `data.length`. Submitting this as calldata to a contract that performs `staticcall` to precompile `0x1000002` (or via `TriggerSmartContract`) throws `ArrayIndexOutOfBoundsException` inside `execute()`, confirming the offset is trusted without bounds validation against the actual buffer size.
