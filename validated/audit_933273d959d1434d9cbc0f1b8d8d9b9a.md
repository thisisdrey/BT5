Audit Report

## Title
Snowbridge relayer reward is paid out even when the delivery receipt reports `success == false` - (File: `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs`)

## Summary
`DeliveryReceipt::success`, decoded from the Ethereum `InboundMessageDispatched` event, is never consulted by `OutboundQueue::process_delivery_receipt` before releasing the relayer reward. The function pays `order.fee` to `reward_account` based solely on `order.fee > 0`, ignoring whether the message actually dispatched successfully on Ethereum, so a relayer can be rewarded for a failed delivery.

## Finding Description
`DeliveryReceipt` explicitly carries a `success: bool` field populated from the on-chain event log during decoding: <cite repo="ThankGodontt/polkadot-sdk--028" path="bridges/snowbridge/primitives/outbound-queue/src/v2/delivery_receipt.rs" start="14="27" /> [1](#0-0) 

`process_delivery_receipt` destructures `receipt` into `gateway`, `reward_address`, and `nonce`, resolves the reward destination, fetches the `PendingOrder`, and pays the reward whenever `order.fee > 0` — `receipt.success` is never referenced anywhere in this function: [2](#0-1) 

The only invocation site, `submit_delivery_receipt`, is a public, permissionless extrinsic — any `ensure_signed` origin can call it once it has a valid proof for the (potentially failed) event log, and it forwards the decoded receipt straight into `process_delivery_receipt` without any success check: [3](#0-2) 

The `PendingOrder` (with its `fee`) is created unconditionally at message-send time in `do_process_message`, independent of eventual delivery outcome: [4](#0-3) 

The only guard present is `ensure!(T::GatewayAddress::get() == receipt.gateway, ...)`, which binds the receipt to the correct contract address but says nothing about delivery outcome. There is no check anywhere in this pallet gating `T::RewardPayment::register_reward` on `receipt.success`.

## Impact Explanation
Reward registration should conserve value and settle exactly once to the rightful beneficiary based on successful execution, but here the reward is paid regardless of whether the inbound dispatch on Ethereum actually succeeded. This lets the fee/reward pot be drained for delivery attempts that never completed successfully, matching the "theft or unbacked...payout" and "duplicate/incorrect settlement" impact categories, since `PendingOrders` is cleared and the reward is registered as if delivery had genuinely succeeded.

## Likelihood Explanation
Any unprivileged, signed account can call the public `submit_delivery_receipt` extrinsic with a validly-proven event log whose `success` field is `false` (this is a legitimate, anticipated outcome of the event schema itself, not a forged proof). No malicious relayer/validator assumption beyond ordinary permissionless relaying is required — the bug is purely a missing invariant check in `process_delivery_receipt`, reachable through completely normal use of the public extrinsic.

## Recommendation
Gate the call to `T::RewardPayment::register_reward` on `receipt.success == true`. When `success` is `false`, do not register the full reward — options include withholding it, refunding the original sender, or emitting a distinct event (e.g., `MessageDeliveryFailed`) instead of `MessageDelivered`, so downstream consumers and fee accounting can distinguish successful from failed deliveries.

## Proof of Concept
1. A message is sent via `do_process_message`, creating `PendingOrder { nonce, fee, .. }` with `fee > 0` in `PendingOrders`. [5](#0-4) 
2. The message is delivered to the Ethereum Gateway, but execution fails; the Gateway still emits `InboundMessageDispatched(nonce, topic, success=false, reward_address=<attacker>)`.
3. Anyone calls `submit_delivery_receipt` with a valid proof of this log; `T::Verifier::verify` succeeds (the log itself is genuine), `DeliveryReceipt::try_from` decodes `success: false` correctly. [6](#0-5) 
4. `process_delivery_receipt` checks only `order.fee > 0`, calls `T::RewardPayment::register_reward(&reward_account, ..., order.fee)`, and removes the `PendingOrder` — paying the full reward despite `receipt.success == false`. [7](#0-6) 

A unit test asserting that `process_delivery_receipt` with `receipt.success = false` results in no call to `register_reward` (or a reduced/zero payout) would currently fail against this code, confirming the vulnerability.

		/// Process a delivery receipt from a relayer, to allocate the relayer reward.
		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}
