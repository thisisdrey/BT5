This confirms the claim exactly as stated. `DeliveryReceipt` decodes `success: bool` from the Ethereum `InboundMessageDispatched` event [1](#0-0) , but `process_delivery_receipt` never reads or checks `receipt.success` — it only validates `receipt.gateway` and looks up `PendingOrders` by `receipt.nonce`, then unconditionally pays the reward and removes the order [2](#0-1) . The public `submit_delivery_receipt` extrinsic is reachable by any signed account and only requires a valid verifier proof of the event log, not any particular `success` value [3](#0-2) .

Audit Report

## Title
Relayer reward paid and pending order settled regardless of on-chain execution outcome (`DeliveryReceipt.success` never checked) - ([File: bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs])

## Summary
`Pallet::process_delivery_receipt` pays the relayer reward and clears the `PendingOrders` entry based only on `receipt.gateway` matching `T::GatewayAddress` and a successful `PendingOrders` lookup by `receipt.nonce`. The `success` field of the decoded `DeliveryReceipt`, which reflects whether the Ethereum-side message dispatch actually succeeded, is decoded in `DeliveryReceipt::try_from` but never read anywhere in `process_delivery_receipt` or `submit_delivery_receipt`.

## Finding Description
`DeliveryReceipt` is decoded from the `InboundMessageDispatched(uint64 nonce, bytes32 topic, bool success, bytes32 reward_address)` Solidity event and includes the `success: bool` field [4](#0-3) . `submit_delivery_receipt` verifies the event log proof via `T::Verifier::verify`, decodes the receipt, and forwards it directly to `process_delivery_receipt` [3](#0-2) .

`process_delivery_receipt` performs exactly two checks: gateway address equality, and a `PendingOrders::get(nonce)` lookup. It never inspects `receipt.success` before calling `T::RewardPayment::register_reward(&reward_account, T::DefaultRewardKind::get(), order.fee)` and unconditionally removes the order via `<PendingOrders<T>>::remove(nonce)` [5](#0-4) . Neither the gateway check nor the nonce-based order lookup says anything about whether the Ethereum-side dispatch actually succeeded — they only confirm that a matching pending order exists and that the event genuinely originated from the correct Gateway contract. Both a `success = true` and `success = false` event produce byte-identical downstream behavior: full reward payout and permanent removal of the `PendingOrder`.

## Impact Explanation
This is public underpriced/incorrect settlement of bridge state: a failed Ethereum-side delivery (success = false) is treated identically to a successful one, causing the relayer reward (`order.fee`) to be paid via `T::RewardPayment::register_reward` for work that did not actually complete, and causing the `PendingOrder` to be permanently deleted from `PendingOrders` so it can never be retried or correctly reconciled. This matches the required "payout state must only advance after decode, dispatch, execution, and settlement succeed atomically" invariant, which is violated here since settlement occurs irrespective of the encoded execution outcome.

## Likelihood Explanation
`submit_delivery_receipt` is a public, signed-origin extrinsic with no privileged requirement [6](#0-5) . Any account holding (or able to construct/obtain) a valid proof for a genuine `InboundMessageDispatched` event — including ones with `success = false`, which naturally occur whenever the target contract call reverts on Ethereum — can trigger full reward payout and order settlement. No governance, admin, or relayer-collusion assumption is required; a naturally occurring failed dispatch on Ethereum is sufficient to trigger the bug via ordinary relayer operation.

## Recommendation
In `process_delivery_receipt`, branch on `receipt.success`:
- If `true`, keep current behavior (pay reward, remove order).
- If `false`, do not call `T::RewardPayment::register_reward` (or pay per an explicit failure policy), and decide whether to remove the `PendingOrder` (closing the order) or retain it for retry/reconciliation. Emit a distinct event (e.g., `MessageDeliveryFailed`) so this outcome is observable on-chain rather than being silently conflated with success.

## Proof of Concept
1. `do_process_message` creates `PendingOrders::<T>::insert(nonce, PendingOrder { nonce, fee, block_number })` with `fee > 0` [7](#0-6) .
2. On Ethereum, the target contract call for that message reverts, so the Gateway emits `InboundMessageDispatched(nonce, topic, success=false, reward_address)`.
3. Any signed account submits `submit_delivery_receipt(origin, event)` with a proof of this genuine event. `T::Verifier::verify` succeeds and `DeliveryReceipt::try_from` decodes `success = false`.
4. `process_delivery_receipt` passes the gateway check, finds the `PendingOrder` by nonce, and — because `success` is never checked — calls `register_reward` with the full `order.fee` and removes the order, emitting `Event::MessageDelivered { nonce }` as if the delivery had succeeded.
5. This can be verified by adapting the existing test `submit_delivery_receipt_succeeds_after_unhalt` to use a mocked event/receipt with `success: false` and asserting the reward is still registered and the order still removed [8](#0-7) .

		/// Process a delivery receipt from a relayer, to allocate the relayer reward.
		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}
