### Title
`AccountLocks::try_lock_transaction_batch` fails to detect write-write conflicts between distinct transactions within the same batch, allowing two conflicting transactions to be locked and executed together - (File: accounts-db/src/account_locks.rs)

### Summary
`Accounts::lock_accounts` (accounts-db/src/accounts.rs:455-474) validates each transaction independently via `validate_account_locks` and then calls `AccountLocks::try_lock_transaction_batch` (accounts-db/src/account_locks.rs:22-40) to acquire locks for the whole batch. The check pass and the lock-acquisition pass in `try_lock_transaction_batch` are split into two separate loops, and the check pass only compares each transaction against the pre-batch lock state, never against other transactions being admitted in the same call. This lets two distinct transactions that write the same account both be marked `Ok(())` and both have their locks incremented, defeating the fundamental "no two transactions with conflicting writes may be scheduled together" invariant.

### Finding Description
`try_lock_transaction_batch` works in two phases:

1. First loop (accounts-db/src/account_locks.rs:28-34): for every transaction in the batch, `can_lock_accounts` is called against `self` (the shared `AccountLocks` state). Crucially, `can_lock_accounts` is a read-only check — it never mutates `self.write_locks` / `self.readonly_locks`. So every transaction in the loop is checked against the *same, unchanged* pre-batch lock state, not against locks that would be taken by earlier transactions processed within this same call.
2. Second loop (accounts-db/src/account_locks.rs:36-39): for every transaction still marked `Ok`, `self.lock_accounts(keys)` is called unconditionally, incrementing `write_locks`/`readonly_locks` counters without re-checking `can_write_lock`/`can_read_lock` against locks that other transactions in the same batch just took.

Consequence: if transaction A and transaction B (each individually valid and passing `validate_account_locks`, i.e. no duplicate keys within either transaction, and neither exceeding `tx_account_lock_limit`) both declare the same account as writable, and neither conflicts with any *pre-existing* lock, both are marked `Ok` in phase 1 (because self was untouched at check time) and both get their write-lock counters incremented unconditionally in phase 2 without ever comparing against each other. `Accounts::lock_accounts` (accounts-db/src/accounts.rs:455-474) returns `Ok(())` for both, so both are handed to the SVM for execution in the same batch/PoH entry — violating the exclusivity guarantee the rest of the pipeline (parallel account loading, entry construction, replay) assumes for writable accounts within one batch.

Root cause: the check-then-lock logic is split across two loops using stale `self` state for validation instead of accumulating "would-be locks already taken in this call" during the check pass (or re-checking during the lock pass).

### Impact Explanation
This breaks the account-locking invariant that guarantees no two transactions execute concurrently against the same writable account within a batch/entry. Two write-conflicting transactions being admitted to the SVM together can produce non-deterministic/non-serializable state depending on execution order, corrupt the resulting bank state, and can produce different results on different validators replaying the same entry — a consensus/invalid-recorded-block class issue. This matches the "invalid recorded block" / "verification bypass of account-lock guard" bounty category referenced in the question's scope.

### Likelihood Explanation
The only precondition is that an unprivileged remote client submit two ordinary, individually-valid transactions that share a writable account and land in the same call to `Accounts::lock_accounts` (i.e., the same processing batch, e.g. via banking stage `consumer.rs`/`TransactionBatch`). No special access, staking, or scheduler control is required from the attacker's perspective — this is standard transaction submission via TPU. Whether this is fully exploitable end-to-end depends on whether an upstream scheduler (e.g. `scheduling-utils/src/thread_aware_account_locks.rs`, `greedy_scheduler.rs`) already filters out intra-batch write conflicts before calling `lock_accounts`; I was not able to fully confirm from the available index whether every code path that calls `Accounts::lock_accounts` guarantees conflict-free batches upstream. Regardless, `account_locks.rs` itself provides no defense-in-depth against this — the function's contract ("prevent multiple threads from modifying the same account state at the same time") is not actually enforced for the described interleaving.

### Recommendation
Fix `try_lock_transaction_batch` to check-and-lock atomically per transaction in a single pass (interleave `can_lock_accounts` + `lock_accounts` for each transaction in order, so subsequently-checked transactions in the batch see locks already taken by earlier ones in the same call), rather than splitting into a stale-state check pass followed by an unconditional lock pass.

### Proof of Concept
```rust
// accounts-db/src/account_locks.rs (test module)
#[test]
fn test_try_lock_transaction_batch_detects_intra_batch_write_conflict() {
    let mut account_locks = AccountLocks::default();
    let shared_account = Pubkey::new_unique();

    // Two distinct, individually-valid transactions writing the same account.
    let tx1_keys = vec![(&shared_account, true)];
    let tx2_keys = vec![(&shared_account, true)];

    let validated_batch_keys: Vec<TransactionResult<_>> = vec![
        Ok(tx1_keys.into_iter()),
        Ok(tx2_keys.into_iter()),
    ];

    let results = account_locks.try_lock_transaction_batch(validated_batch_keys);

    // Expect: exactly one of the two conflicting transactions should be
    // rejected with AccountInUse.
    let ok_count = results.iter().filter(|r| r.is_ok()).count();
    assert_eq!(
        ok_count, 1,
        "both write-conflicting transactions were admitted in the same batch: {:?}",
        results
    );
}
```
Fuzz extension: generate pairs of `SVMMessage`-like key sets sweeping `tx_account_lock_limit` boundary values and random overlapping writable/readonly key sets, call `Accounts::lock_accounts`, and assert that for any pair sharing a writable key, at most one result is `Ok(())`.
