### Title
Bridge-in supply counters are monotonic and never released when bridged-in synths are burned locally, permanently bricking inbound bridging and freezing in-flight bridged funds - ([File: contracts/SyntheticToken.sol](contracts/SyntheticToken.sol))

### Summary
`SyntheticToken` tracks `totalBridgedIn` / `totalBridgedOut` as cumulative counters. `totalBridgedIn` is incremented only inside `_mint` when the caller is `proxyOFT` [1](#0-0) , and `totalBridgedOut` is incremented only inside `_burn` when the caller is `proxyOFT` [2](#0-1) . No code path ever decrements either counter, so burning bridged-in synths through a non-OFT path (repay, liquidate, swap) permanently consumes `bridgedInSupply` — the analog of "releasing a reference that was never re-acquired": the decrement side of the accounting pair simply does not exist [3](#0-2) .

### Finding Description
`ProxyOFT._creditTo` mints on message receipt, incrementing `totalBridgedIn` [4](#0-3) . The symmetric "release" — decrementing `totalBridgedIn` when those same tokens are destroyed — is missing. `DebtToken.repay`/`repayAll` burn synths via `_syntheticToken.burn(_msgSender, _repaid)` where `_msgSender` resolves through `SynthContext` to the pool-side `DebtToken`/payer, never `proxyOFT` [5](#0-4) . Same for `Pool.liquidate` (`syntheticToken_.burn(_msgSender, ...)`) [6](#0-5)  and `Pool.swap` (`syntheticTokenIn_.burn`) [7](#0-6) . Since `bridgedInSupply() = totalBridgedIn - totalBridgedOut` and `_mint` reverts with `SurpassMaxBridgingSupply` once it exceeds `maxBridgedInSupply`, an attacker can inflate `totalBridgedIn` without bound by cycling:

1. Acquire msUSD/msETH on a supported remote chain (buy on a remote AMM or issue debt there).
2. `ProxyOFT.sendFrom` on the remote chain → `_creditTo` mints here, `totalBridgedIn += amount`.
3. Locally `DebtToken.repay` (own position) or `Pool.swap`/`liquidate` to burn the minted synths; counters untouched.
4. Repeat until `bridgedInSupply() > maxBridgedInSupply`.

After that, every inbound `_creditTo` → `SyntheticToken.mint` reverts, so every legitimate LayerZero receive fails permanently for that synth on that chain.

### Impact Explanation
Permanent freezing of funds / liveness failure: any user who bridges out after the cap is saturated (or whose in-flight message is retried via `retryMessage`/`retryOFTReceived`) has their source-chain tokens burned but can never be minted on the destination — the mint always reverts. Additionally, all cross-chain synth inflows are bricked until governance manually raises `maxBridgedInSupply`, which only postpones the attack since the attacker can keep inflating the counter at the cost of a repay fee per cycle. The deployed configs enforce finite `maxBridgedInSupply` values (verified in fork tests asserting `expectedMaxBridgedInSupply`) [8](#0-7) .

### Likelihood Explanation
Requires only an unprivileged EOA. Bridging is enabled on the deployed config (`isBridgingActive`, supported destination chains) and `sendFrom` is a public payable entry point [9](#0-8) . `repay`, `liquidate`, and `swap` are public `whenNotShutdown` entry points with no access control on the payer [10](#0-9) . Cost per cycle is roughly the repay fee plus LZ fees; the attacker recovers principal by repaying their own debt and withdrawing collateral. No modifier, reentrancy guard, pause flag, or supply check prevents the mismatch — the counter inflation is silent.

### Recommendation
Make the bridging counters symmetric: in `_burn`, decrement `totalBridgedIn` (saturating at 0) when the burned supply corresponds to bridged-in tokens, or track net circulation differently — e.g., compute `bridgedInSupply` from a counter that is decremented on every burn regardless of caller, or replace cumulative counters with `circulatingSupply`-based checks in `ProxyOFT` [11](#0-10) . At minimum, decrement `totalBridgedIn` in the AMO/pool burn paths proportionally, or add a governor-recoverable but attacker-inaccessible correction function plus off-chain monitoring.

### Proof of Concept
Hardhat mainnet-fork sketch (adapted from `test/E2E.mainnet.next.test.ts` bridge cases):

```ts
// fork mainnet; pool, synth(msUSD), oft, debt(msd) wired as in existing tests
const cap = await synth.maxBridgedInSupply();
const amount = parseEther('1000');

// open a local position to repay against
await issueSynth(debt, amount);

// cycle: bridge in from remote (simulate via oft._creditTo path on dst chain,
// or on this chain impersonate remote flow by sending out then back in)
for (let i = 0; bridgedInSupply().lte(cap); i++) {
  // on remote chain: oftRemote.sendFrom(attacker, thisChainId, attacker, amount)
  // -> locally _creditTo -> synth.mint: totalBridgedIn += amount
  // then burn locally without touching counters:
  await debt.repay(attacker.address, amount); // burns synth, totalBridgedIn unchanged
}

// victim tries to bridge in -> permanently reverts
await expect(victimBridgeIn(amount)).revertedWithCustomError(synth, 'SurpassMaxBridgingSupply');
```

In practice the fork PoC needs two chains; an equivalent single-fork variant calls `synth.mint` via a pranked `proxyOFT` caller only to demonstrate the missing-decrement invariant — the production trigger is a normal remote `sendFrom`, which requires no privileged role.
