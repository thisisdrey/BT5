Audit Report

## Title
Minting fee deduction can leave a user's PSM internal-asset balance permanently below `min_swap_amount`, making it unredeemable - (File: substrate/frame/psm/src/lib.rs)

## Summary
`Pallet::mint` gates its `min_swap_amount` check on `internal_equivalent`, the pre-fee gross amount, while the amount actually minted to the caller is `internal_to_user = internal_equivalent - fee`. `Pallet::redeem` gates its own `min_swap_amount` check on the caller-supplied `internal_amount` with no exception for redeeming a full remaining balance, so a balance produced by `mint` that lands below `min_swap_amount` because of the fee deduction can never pass the `redeem` check.

## Finding Description
In `mint`, the threshold check occurs before the fee is subtracted: [1](#0-0) 
The fee is then computed with ceiling rounding and subtracted before minting to the user, with no re-check against `min_swap_amount`: [2](#0-1) [3](#0-2) 

In `redeem`, the gate is applied directly to the caller-supplied `internal_amount`, with no bypass for redeeming an entire remaining balance: [4](#0-3) 

Since `internal_to_user = internal_equivalent - fee` and the mint-side check only requires `internal_equivalent >= min_swap_amount`, any mint whose gross `internal_equivalent` is at or slightly above `min_swap_amount`, combined with a non-zero minting fee rate, deterministically produces `internal_to_user < min_swap_amount`. Because `redeem`'s check requires `internal_amount >= min_swap_amount` for whatever value the caller submits (up to their full balance), no value the caller can supply for a balance below `min_swap_amount` will ever satisfy the check. This traps the minted tokens with no pallet-provided exit route other than minting additional funds to clear the threshold — which is precisely the "top up to unlock" workaround pattern that represents a genuine, permanent partial fund lock for ordinary unprivileged use of the public `mint`/`redeem` extrinsics.

## Impact Explanation
This matches the "permanent user-fund or bridge-state lock" impact category: funds credited via the public, unprivileged `mint` extrinsic become stuck in the internal asset with no path back through `redeem`, even though the PSM reserve fully backs them. The user retains a valid, non-zero balance that is functionally unredeemable unless they deposit additional external asset to push the balance above `min_swap_amount`, at which point they still cannot cleanly redeem their original dust separately — the underlying gate remains asymmetric between entry (gross, pre-fee) and exit (net, whatever is submitted), with no full-balance bypass.

## Likelihood Explanation
High. Any PSM instance with a non-zero minting fee rate (`MintingFee`) combined with a mint whose gross `internal_equivalent` falls between `min_swap_amount` and `min_swap_amount / (1 - fee_rate)` will trigger this deterministically. No privileged action, price movement, or adversarial timing is required — a single ordinary, unprivileged `mint` call by a normal user reaching that quantized value suffices, and it is trivially repeatable.

## Recommendation
Re-check the post-fee amount (`internal_to_user`) against `info.min_swap_amount` in `mint` and reject mints that would leave the user under the floor, and/or allow `redeem` to bypass the `min_swap_amount` floor when `internal_amount` equals the caller's entire remaining internal-asset balance for that PSM instance, mirroring the "full unbond always allowed" pattern (`is_full_unbond`) used in `pallet-nomination-pools`: [5](#0-4) 

## Proof of Concept
1. `create_psm` registers `INTERNAL_ASSET_ID` with `min_swap_amount = M` and a non-zero minting fee rate (e.g. `DefaultFee` of 0.5%), with external asset `X` at matching decimals.
2. A user calls `Psm::mint(origin, INTERNAL_ASSET_ID, X, external_amount, max_fee)` where `external_amount` converts to `internal_equivalent == M`, which passes: [6](#0-5) 
3. `fee = fee_rate.mul_ceil(M) > 0`, so `internal_to_user = M - fee < M`, and this amount is minted to the user via `T::Fungibles::mint_into`: [7](#0-6) 
4. The user calls `Psm::redeem(origin, INTERNAL_ASSET_ID, X, internal_to_user, max_fee)` (their full balance).
5. The check `ensure!(internal_amount >= info.min_swap_amount, Error::<T>::BelowMinimumSwap)` fails for every value the user can pass (since their entire balance is below `M`), so the call reverts unconditionally: [4](#0-3)
