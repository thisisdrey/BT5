### Title
Cross-StackerDB chunk-signature replay: `SlotMetadata` signature does not bind the target contract, allowing valid chunks to be replayed into a different signers StackerDB - (File: `libstackerdb/src/libstackerdb.rs`)

### Summary
`SlotMetadata::auth_digest()` computes the message a signer signs over `(slot_id, slot_version, data_hash)` only. It never includes the smart-contract identifier of the StackerDB the chunk is meant for. Multiple StackerDB contracts (`signers-{0,1}-1` for `BlockResponse`, `signers-{0,1}-2` for `StateMachineUpdate`, `signers-{0,1}-3` for `BlockPreCommit`) share the exact same signer-to-slot assignment for a given reward cycle, since they all read the same `stackerdb-signer-slots-N` list from the `.signers` boot contract. Because the signature never commits to which of these contracts it is destined for, a chunk legitimately signed by a signer for one message-type DB is also a "validly signed" chunk for the same slot in every sibling message-type DB, letting an unprivileged network relay replay it cross-contract.

Neither includes `smart_contract_id`/`contract_id`. All consumers of this signature check the recovered address only against the *target* replica's configured slot signer, never against the contract the signature was originally produced for:

- HTTP write path: `StackerDBTx::try_replace_chunk` looks up `slot_validation.signer` purely from `(smart_contract, slot_id)` and calls `slot_desc.verify(&slot_validation.signer)`, with no contract binding in the digest itself: [3](#0-2) 

- P2P write/relay path: `PeerNetwork::validate_received_chunk` resolves the signer address for `smart_contract_id` and then calls `slot_metadata.verify(&addr)`, again with no dependency of the signed digest on which contract is being validated: [4](#0-3) 

This function is used both for chunks pushed unsolicited over P2P (`handle_unsolicited_StackerDBPushChunk`, including the buffered `FutureView` path) and for chunks fetched during sync, and a successfully-validated chunk is stored and then rebroadcast/gossiped to other peers.

Multiple distinct StackerDB contracts share an identical signer→slot mapping for the same reward cycle because they are all populated from the same `stackerdb-get-signer-slots-page` data in the `.signers` contract: [5](#0-4) 

and the corresponding message-type-to-contract mapping is enumerated via `MessageSlotID`: [6](#0-5) 

Because the digest signed by a signer key does not encode which of the `BlockResponse` / `StateMachineUpdate` / `BlockPreCommit` contracts (or any future additional per-message StackerDB) it authorizes, a signature produced for slot `S`, version `V` in contract A is equally "valid" for slot `S`, version `V` in contract B, as long as the same signer occupies slot `S` in both — which is guaranteed by the shared slot-assignment source. An attacker who merely observes network traffic (no private key needed) can take a legitimately signed `StackerDBChunkData`/`StackerDBPushChunkData` intended for one message-type DB and resubmit it (via the HTTP `POST /v2/stackerdb/.../chunks` endpoint, or by injecting a `StackerDBPushChunk` P2P message) against a different message-type DB for the same reward cycle, provided the target replica's stored slot version for that slot is currently lower than the replayed chunk's version.

### Impact Explanation
If accepted, the replayed chunk is written into a StackerDB whose consumers (signers, miners) interpret its bytes according to that DB's own message schema (e.g., data serialized as a `BlockPreCommit` payload being written into the `BlockResponse` slot, or vice versa). Depending on how deserialization handles malformed/mistyped payloads downstream, this can at minimum pollute a signer's state-machine/coordination channel with attacker-replayable (though not attacker-forged-content) data from a different context, and the accepting node will further relay/gossip the chunk to its peers as legitimate content for that DB (network-wide propagation of misapplied data). This matches "unauthenticated/unauthorized write to state or StackerDB" / "network-wide propagation of forged data" since the write into the target DB slot occurs without the signer ever intending or authorizing that specific (contract, slot, version) triple.

### Likelihood Explanation
Likelihood is Low-to-Medium: the attacker needs no key, only to observe/capture a validly signed chunk broadcast on the network (which is by design public/gossiped) and needs the slot_version at the target contract to be lower than the version being replayed (a state that naturally exists early in write history for each contract, and can also be produced/waited for by an attacker monitoring versions across the sibling contracts). No signature forgery is required — this is a pure replay of legitimately-produced data across an insufficiently-scoped signature.

### Recommendation
Bind the StackerDB's smart-contract identifier into the signed digest, e.g. include `smart_contract_id` (and/or `MessageSlotID`) as part of `SlotMetadata::auth_digest()` in `libstackerdb/src/libstackerdb.rs`, and thread the target contract id through `sign()`/`verify()` and all call sites (`StackerDBChunkData::sign`/`verify`, `try_replace_chunk`, `validate_received_chunk`). This mirrors the report's recommendation of making the equivalent of "app data" (the destination context) immutable/committed-to in the signature, so a signature valid for one StackerDB contract cannot be replayed into another.

### Proof of Concept
1. During a reward cycle, a signer key `K` occupies slot `S` in both `signers-0-1` (BlockResponse) and `signers-0-3` (BlockPreCommit), per the shared slot list in `.signers`.
2. Signer `K` signs and pushes a legitimate `StackerDBChunkData{slot_id: S, slot_version: V, data: D}` to `signers-0-3` (`BlockPreCommit`) — this is broadcast on P2P and visible to any peer.
3. An attacker with no private key captures this chunk and constructs a `StackerDBPushChunkData{contract_id: signers-0-1, chunk_data: <same slot_id, slot_version, sig, data>}` (or a `POST /v2/stackerdb/{signers-0-1 issuer}/{signers-0-1 name}/chunks` HTTP request) targeting `signers-0-1` (`BlockResponse`), provided that DB's currently stored version for slot `S` is `< V`.
4. `PeerNetwork::validate_received_chunk` (or `poststackerdbchunk`'s handler → `try_replace_chunk`) resolves the slot signer for `signers-0-1`/slot `S` as `K`, calls `slot_metadata.verify(&K)`, which succeeds because `auth_digest()` never referenced `signers-0-3` vs `signers-0-1`.
5. The chunk is accepted, stored in `signers-0-1`'s slot `S`, and further gossiped to peers as a legitimate `BlockResponse`-DB chunk, even though it was never signed for that contract.

    /// Get the digest to sign that authenticates this chunk data and metadata
    fn auth_digest(&self) -> Sha512Trunc256Sum {
        let mut hasher = Sha512_256::new();
        hasher.update(self.slot_id.to_be_bytes());
        hasher.update(self.slot_version.to_be_bytes());
        hasher.update(self.data_hash.0);
        Sha512Trunc256Sum::from_hasher(hasher)
    }

    /// Note that the address version is ignored.
    pub fn verify(&self, principal: &StacksAddress) -> Result<bool, Error> {
        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )
        .map_err(|ve| Error::VerifyingError(ve.to_string()))?;

        let pubkh = Hash160::from_node_public_key(&pubk);
        Ok(pubkh == *principal.bytes())
    }
