### Title
Whole-receipt rollback discards a successful DelegateAction's access-key nonce bump, enabling replay/double-spend of the delegate's inner deposit - ([File: runtime/runtime/src/lib.rs, runtime/runtime/src/actions.rs])

### Summary
`apply_action_receipt` executes all actions of a receipt inside a single `TrieUpdate` transaction and calls `state_update.rollback()` for the whole receipt if *any* action fails, discarding every trie write made by earlier, successful actions in that receipt. `validate_delegate_action_key` persists the meta-transaction nonce bump via a direct `set_access_key(state_update, ...)` call rather than through the `ActionResult`/`ActionReceiptResult` bookkeeping that other side effects flow through, so it is silently erased by this rollback when a later sibling action in the same receipt fails.

### Finding Description
`apply_action_receipt` runs receipt actions sequentially in a loop, breaking at the first failing action and recording its index [1](#0-0) . At the end of the function, the receipt's fate is decided as a single unit: success commits, any error rolls back the entire `state_update` accumulated since the receipt started [2](#0-1) .

For a `Delegate`/`DelegateV2` action, `apply_delegate_action` calls `validate_delegate_action_key`, which — on successful validation — bumps the sender's access-key (or gas-key) nonce by writing directly to `state_update` via `set_access_key`/`set_gas_key_nonce` [3](#0-2) . This write is a raw trie mutation, not part of `ActionResult.new_receipts`/`validator_proposals`/`tokens_burnt` (the only fields `set_error` clears) [4](#0-3) . In other words, the nonce bump "escapes" the normal per-action result object and lives only in the shared `state_update` for the rest of the receipt's execution.

If the `Delegate` action is action index 0 in a multi-action receipt/transaction and succeeds, its nonce write lands in `state_update`. If a later action (index 1+) in the same receipt then fails deterministically, `apply_action_receipt`'s loop breaks, `result.result` becomes `Err`, and the whole-receipt `state_update.rollback()` at the end discards *all* uncommitted trie changes since the receipt began — including the delegate's nonce bump from action 0, even though that action itself completed without error. `check_actor_permissions` places no restriction preventing `Delegate`/`DelegateV2` from being combined with other action kinds in the same action list [5](#0-4) , and nothing in `apply_action_receipt`'s loop treats successful actions specially before the receipt-level commit/rollback decision.

After rollback, the sender's access key nonce is back to its pre-delegate value. The identical, previously-"consumed" `SignedDelegateAction` (same nonce, same signature) can then be resubmitted — alone, or paired with an action that now succeeds — and will pass nonce validation and execute again, re-spending its inner deposit.

### Impact Explanation
This breaks the nonce-monotonicity invariant relied upon to make `SignedDelegateAction`s single-use, allowing replay of a meta-transaction and double-spend of any deposit/value moved by its inner actions. This matches the "double-spend/replay" bounty category (loss of funds via replaying the same signed authorization).

### Likelihood Explanation
The attacker needs to be an ordinary account holder acting as its own relayer: craft/submit a transaction (or an outgoing receipt via a contract) whose action list is `[Delegate(valid, deposit-bearing inner action), OtherAction(deterministically fails)]` — e.g., a second action that violates a permission check or targets state guaranteed to fail (no special privilege required, just a self-authored failing action appended after the Delegate action). Cost is a single transaction fee; the exploit is fully repeatable because after each successful "capture and rollback," the sender's nonce is unchanged, so the same SignedDelegateAction can be replayed indefinitely (subject to `max_block_height` on the DelegateAction, and to the relayer paying the resubmission gas each time). No signature, nonce, or access-key check in `validate_delegate_action_key` or elsewhere anticipates this partial-success/whole-rollback interaction, since it checks nonce *before* the sibling-action failure occurs, and the nonce write is not restored to a checkpoint independent of the rest of the receipt's outcome.

### Recommendation
Persist the delegate-action nonce bump so it survives sibling-action failures within the same receipt — e.g., commit the nonce update in its own `state_update` checkpoint immediately after `validate_delegate_action_key` succeeds (before continuing to subsequent actions), or otherwise decouple it from the receipt's all-or-nothing rollback so a validated/consumed nonce is never rolled back even if a later, unrelated action in the same receipt fails.

### Proof of Concept
Add a unit test in `runtime/runtime/src/actions.rs` (alongside `test_delegate_action`) that:
1. Builds an `ActionReceipt` with two actions: `[Action::Delegate(signed_delegate_action)`, an action guaranteed to fail deterministically (e.g., an `AddKey`/`DeleteKey` action executed by an actor lacking permission, or a `DeployContract` exceeding a limit)].
2. Calls the full `apply_action_receipt` path (or `Runtime::apply` via the test-loop/integration harness in `runtime/runtime/src/tests/apply.rs`, reusing `generate_delegate_actions`-style receipt construction) with this receipt.
3. Asserts the receipt's outcome is `Failure`, then reads back the sender's `AccessKey.nonce` from state and asserts it equals the **pre-execution** nonce (proving the bump from the successful `Delegate` action was rolled back).
4. Resubmits the identical `SignedDelegateAction` (alone, in a receipt with no failing sibling) and asserts it is accepted and executed a second time (nonce check passes, inner deposit action runs again) — demonstrating replay/double-spend.
