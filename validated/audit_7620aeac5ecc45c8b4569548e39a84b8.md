### Title
`TokenDiff` protocol fee is bypassed by splitting a single large Nep245/Imt delta into many single-unit `TokenDiff` intents in one signed payload - ([File: contracts/defuse/core/src/intents/token_diff.rs])

### Summary
`TokenDiff::execute_intent` computes the fee for each `TokenDiff` intent independently, and `TokenDiff::token_fee` exempts Nep245/Imt token deltas from fees when `amount <= 1`. Because a `DefusePayload` (one signature, one nonce) can carry an arbitrary list of intents, a signer can split one `TokenDiff{delta: -1000}` into 1000 `TokenDiff{delta: -1}` intents inside a single signed batch, and pay zero fee instead of `fee_ceil(1000)`.

### Finding Description
The intended binding is: `fee_collected_from_signer_for_token_X_over_a_batch == Pips::fee_ceil(fee, total_negative_delta_on_token_X_in_that_batch)` — i.e. the fee should depend on the *total* amount of `token_X` the signer moves inward, not on how that movement is chopped into intents.

In practice, the fee is computed strictly per intent, per token, using only that single intent's `delta`: [1](#0-0) 

And the per-token fee-rate function explicitly zeroes the fee for Nep245/Imt tokens when the absolute delta is `<= 1`: [2](#0-1) 

A `DefusePayload<T>` bundles a signer, nonce, deadline and an arbitrary message (a list of intents) under one signature: [3](#0-2) 

and the test helper `sign_defuse_payload_default(&env.defuse, [TokenDiff{...}])` shows intents are passed as a list to be signed together, so a single signature can contain any number of `TokenDiff` intents: [4](#0-3) 

Exploit: instead of signing one `TokenDiff{diff: {NEP245_TOKEN: -1000, OUT_TOKEN: +X}}` (which pays `fee_ceil(fee, 1000)` on the Nep245 leg because `amount=1000 > 1`), the attacker signs one payload containing 1000 separate `TokenDiff` intents, each `{diff: {NEP245_TOKEN: -1, OUT_TOKEN: +x_i}}`. For each of these, `token_fee` sees `amount = 1` for a `Nep245`/`Imt` token type and returns `Pips::ZERO`, so `fees_collected` for that intent is `0`. Summed over the whole batch, the signer moves the same net `-1000` of the token, but the protocol collects `0` fee at `fee_collector` instead of `fee_ceil(fee, 1000)`.

Existing guards do not prevent this: `MultiPayload::verify`, `has_public_key`, `verify_intent_nonce`, `Lock::get_mut` and `TransferMatcher::finalize` check signature validity, nonce uniqueness, and balance-matching across the whole batch — none of them re-aggregate per-token deltas across multiple `TokenDiff` intents for fee purposes. The fee logic is scoped strictly inside `execute_intent` for one `TokenDiff` at a time, so no batch-level or payload-level aggregation exists to close this gap.

### Impact Explanation
The signer's net balance change is identical to the "honest" single-intent version, but the fee normally owed to `fee_collector` is entirely avoided (a full fee-ceiling bypass, not merely reduced) whenever the token is `Nep245`/`Imt` and the delta can be decomposed into unit-sized legs. This is repeatable per batch, per account, and per Nep245/Imt token, and scales linearly with attacker effort (more intents = more amount moved fee-free). This matches the Critical category "protocol fees bypassed or over-collected" since it is a deterministic, signer-controlled, zero-cost way to divert value that should go to `fee_collector` back to the signer.

Caveat/uncertainty: the `amount <= 1` exemption is explicitly commented as being intended for genuine NFT-like semantics ("do not take fees on NFTs and MTs with `|delta| <= 1`"), which suggests the code's authors were aware unit deltas are fee-exempt by design for true non-fungible items. Whether this constitutes an unintended "bypass via decomposition" versus an accepted limitation of a coarse per-intent fee model is a judgment call that the maintainers would need to confirm; I could not find any explicit batch-level aggregation of `token_fee` inputs across intents in this codebase to rule out that the fee model is deliberately per-intent-only.

### Likelihood Explanation
No special privileges are required: any unprivileged account holding (or having deposited) a `Nep245`/`Imt`-type balance can construct and sign one `MultiPayload`/`DefusePayload` with many `TokenDiff` intents and call `execute_intents` or `simulate_intents`. The cost is purely computational (constructing N intents in one signed message and the extra gas of executing N intents in one transaction, which is excluded from scope as "unbounded gas/storage" only if it caused resource exhaustion — the fee bypass itself does not depend on hitting gas limits for smaller N). Feasibility is high and fully repeatable across accounts, tokens, and batches for any Nep245/Imt token where amounts can be legitimately decomposed into unit legs.

### Recommendation
Aggregate `TokenDiff` fee computation across all intents in a single payload/batch per `(signer_id, token_id)` before applying the `amount <= 1` exemption, rather than evaluating it per individual intent. Alternatively, restrict the exemption to token IDs whose semantics guarantee `amount` can never legitimately exceed 1 across a session (i.e., verified true NFTs), rather than using a runtime `amount > 1` check that can be defeated by splitting deltas.

### Proof of Concept
`cargo test` plan (in `contracts/defuse` or `tests/` crate, using the sandbox harness already used by `tests/src/tests/defuse/intents/token_diff.rs`):
1. Deploy `defuse` with fee `Pips::ONE_PERCENT` (non-zero) and `fee_collector`.
2. Create a `Nep245`-typed token wrapper with a fungible-style balance for user `signer` (initial balance ≥ 1000 of that Nep245 token id).
3. **Baseline**: sign and execute a single `TokenDiff{diff: {nep245_token: -1000, out_token: TokenDiff::closure_delta(nep245_token, -1000, fee)... }}` (or matched against a counterparty solver intent as in `solver_user_closure`), and assert `fee_collector`'s balance of `nep245_token` increased by exactly `Pips::ONE_PERCENT.fee_ceil(1000)`.
4. **Exploit**: reset state; sign ONE `MultiPayload`/`DefusePayload` containing 1000 `TokenDiff` intents, each `{diff: {nep245_token: -1, out_token: +x_i}}` (matched by a counterparty solver taking the other side, netting the batch to zero per `TransferMatcher::finalize`), and execute via `execute_intents`.
5. Assert: `fee_collector`'s balance of `nep245_token` after step 4 is `0`, while the signer's net `nep245_token` balance change is `-1000` (identical to step 3).
6. Assert the equality-violation: `fee_collected(step3) == Pips::ONE_PERCENT.fee_ceil(1000) > 0 == fee_collected(step4)` despite equal net signer balance deltas — proving the fee-bypass magnitude equals the entire fee that should have been collected.
