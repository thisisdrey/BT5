### Title
Unprivileged attacker permanently occupies a victim's per-account token slots with dust transfers, DoS-ing new deposits and mints - (File: contracts/Pool.sol)

### Summary
`Pool` enforces `MAX_TOKENS_PER_USER = 30` across `debtTokensOfAccount` + `depositTokensOfAccount` via `onlyIfAdditionWillNotReachMaxTokens` (Pool.sol:143-148). Any holder of a `DepositToken` can `transfer()` an arbitrary dust amount to any victim, and `DepositToken._transfer` unconditionally calls `pool.addToDepositTokensOfAccount(recipient_)` whenever the recipient's balance goes from 0 to >0 (DepositToken.sol:517-520). By transferring 1 wei of every listed deposit token, an attacker fills the victim's set to the cap. All subsequent first-time deposits (`_mint` → `addToDepositTokensOfAccount`) and first-time synth mints (`DebtToken` mint → `addToDebtTokensOfAccount`) for that account revert with `UserReachedMaxTokens`, a repeatable crash of core user flows analogous to the CVE's easy, repeatable DoS.

### Finding Description
- `DepositToken._transfer` adds the recipient to `depositTokensOfAccount` on any non-zero transfer to a zero-balance recipient (DepositToken.sol:517-520); `Pool.addToDepositTokensOfAccount` reverts once `debtTokensOfAccount.length + depositTokensOfAccount.length >= 30` (Pool.sol:144-145, 216-219).
- `DepositToken._mint` (invoked by `deposit`, `depositFor`, gateway deposits, leverage) performs the same add at DepositToken.sol:485-488.
- `DebtToken` adds to `debtTokensOfAccount` on mint/issue; `addToDebtTokensOfAccount` enforces the same shared cap (Pool.sol:204-208). So filling 30 deposit-token slots also blocks the victim from issuing any new synthetic token.
- Liquidation `seize` uses `_transfer` (DepositToken.sol:343-345), so a liquidator whose list was griefed to 30 cannot be paid out in a collateral type they don't already hold, disrupting liquidations.
- Recovery requires the victim to transfer out the dust tokens one by one (each `transfer` that zeroes a balance calls `removeFromDepositTokensOfAccount`, DepositToken.sol:522-525), costing gas per slot; dust is below `unlockedBalanceOf` so `_revertIfLocked` does not block removal, but the victim is DoS'd until cleanup completes.

### Impact Explanation
Temporary freezing of protocol functionality and funds for a targeted account: the victim cannot add new collateral types, cannot mint new synthetic assets, and (for a liquidator) cannot receive seized collateral in new token types. The attack is permissionless (any EOA holding dust of each msdTOKEN), cheap (bounded by number of listed deposit tokens × ~1 transfer each plus trivial initial deposits), and repeatable — the attacker can re-fill slots after the victim cleans them.

### Likelihood Explanation
Requires no privileged role, no oracle manipulation, no reentrancy — only ordinary `transfer`/`deposit` calls on live DepositToken contracts. Cost is limited by the number of deposit tokens listed in the pool (governor-capped but typically enough to reach 30 combined with debt tokens over time). Victim self-recovery is possible but costs gas and can be re-griefed, matching a Medium availability-impact profile.

### Recommendation
- Add an opt-out / allowlist mechanism: only add to `depositTokensOfAccount` on deposits/mints initiated by or for the account, not on inbound `transfer` (e.g., track via a `receivesDustTransfers` flag or require recipient acknowledgment).
- Alternatively, exempt dust amounts below a minimum threshold (e.g., require `amount_` ≥ some floor in underlying USD terms before adding to the set), or let users remove entries themselves via a privileged `removeFromDepositTokensOfAccount`-style self-call path.
- At minimum, allow `Pool.liquidate`'s `seize` path to bypass the cap or route seized collateral to Treasury for later claim.

### Proof of Concept
Hardhat fork-style outline:

```ts
// Setup: fork mainnet; pool, depositTokens = await pool.getDepositTokens()
const attacker = await ethers.getSigner(attackerAddr);
const victim = victimAddr;

// Attacker deposits dust into every listed DepositToken and transfers 1 wei to victim
for (const dtAddr of depositTokens) {
  const dt = await ethers.getContractAt('DepositToken', dtAddr, attacker);
  const underlying = await dt.underlying();
  const erc20 = await ethers.getContractAt('IERC20', underlying, attacker);
  await erc20.approve(dtAddr, dustAmount);
  await dt.deposit(dustAmount);              // mints msdTOKEN to attacker
  await dt.transfer(victim, 1);              // adds dt to victim's depositTokensOfAccount
}

const victimSlots = (await pool.getDepositTokensOfAccount(victim)).length
  + (await pool.getDebtTokensOfAccount(victim)).length;
expect(victimSlots).to.equal(30);            // MAX_TOKENS_PER_USER

// Victim can no longer deposit a collateral type they don't already hold,
// nor mint a synth they don't already owe:
await expect(
  someDepositToken.connect(victimSigner).deposit(amount) // first-time token for victim
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');

await expect(
  debtToken.connect(victimSigner).issue(amount) // first-time debt token
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');
```
