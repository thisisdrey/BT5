### Title
Duplicate `input_data_ids` in an ActionReceipt cause `pending_data_count` to overcount, permanently stalling the postponed receipt and freezing its attached deposit - (File: `runtime/runtime/src/lib.rs`)

### Summary
`process_action_receipt` increments `pending_data_count` once for every entry in `action_receipt.input_data_ids()` without deduplicating the list, while the trie key used to register the wake-up hook (`TrieKey::PostponedReceiptId{receiver_id, data_id}`) is unique per `data_id`. If the same `data_id` appears twice in `input_data_ids`, the counter is initialized to 2 but only one hook exists, so only one decrement can ever occur when the corresponding `DataReceipt` is delivered, leaving the postponed receipt permanently stuck.

### Finding Description
In `process_action_receipt` [1](#0-0) , the code loops over `action_receipt.input_data_ids()` and, for every id not yet received, both increments a local `pending_data_count` and calls `set(..., TrieKey::PostponedReceiptId{receiver_id, data_id}, receipt.receipt_id())`. This trie key is keyed only by `(receiver_id, data_id)`, so writing it twice for the same `data_id` is an idempotent overwrite — it does not create two separate wake-up records. However, `pending_data_count` is a plain counter incremented per loop iteration with no deduplication, so it ends up storing `2` for a receipt whose actual distinct dependency set has only one member [2](#0-1) .

Because a given `data_id` can only ever be satisfied by exactly one `DataReceipt` (it corresponds to a single promise output), and the wake-up structure (`PostponedReceiptId`) for that `data_id` exists only once regardless of how many times it appears in `input_data_ids`, the counter can only ever be decremented once when that data arrives. The stored `PendingDataCount` therefore never reaches zero, and the postponed action receipt (together with any attached deposit) is never re-executed or refunded — it stays permanently parked in state.

An unprivileged attacker can reach this via the promise API from their own deployed contract: `promise_and` accepts a list of promise indices and joins their `data_id`s into the input data of a new receipt. Passing the same underlying promise index (or logically the same `data_id`-producing promise) more than once yields a resulting `ActionReceipt` whose `input_data_ids` contains a duplicate. This path does not require any signature bypass, gas limit bypass, or size-limit bypass — the receipt is a normal, protocol-valid receipt produced by the contract-controlled promise graph, not a directly forged network message. Existing checks (signature/nonce/access-key/gas metering/storage staking/size limits) do not validate uniqueness of `input_data_ids`, since dependency lists are computed by the runtime itself when interpreting the host-function call graph and are not being size- or content-validated for duplicates in `process_action_receipt`.

### Impact Explanation
This matches the "permanent freezing of user funds" category: any deposit/value attached to the receipt (and, transitively, deposits carried in the promise chain gated behind this dependency) becomes permanently unreclaimable since the postponed receipt can never execute and no refund path triggers, because the code never treats it as a stuck/expired postponed receipt. It is a liveness violation localized to the contract account that constructed the duplicated dependency (self-inflicted or via inducing a callee to do so), but any funds attached to that action are permanently lost.

### Likelihood Explanation
This requires only deploying an ordinary wasm contract and using existing public host functions (`promise_batch_create`, `promise_then`/`promise_and`) with a duplicated promise/data dependency, which is trivially reachable by any account able to pay for deployment and a function call — no special privilege, validator access, or protocol bypass needed. It is deterministically repeatable.

### Recommendation
Deduplicate `input_data_ids` before computing `pending_data_count` in `process_action_receipt` (e.g., use a `HashSet<CryptoHash>` over `action_receipt.input_data_ids()` and set `pending_data_count` to the deduplicated length), or make `PostponedReceiptId` decrementing idempotent per (receipt_id, data_id) pair to guarantee the counter cannot diverge from the number of distinct wake-up hooks actually registered. Additionally, consider rejecting/normalizing duplicate promise joins at the `promise_and` host-function level.

### Proof of Concept
Unit test in `runtime/runtime/src/lib.rs` or an integration test under `runtime/runtime/tests/test_async_calls.rs`:
1. Construct an `ActionReceipt` with `input_data_ids = [data_id, data_id]` (same hash twice) targeting a receiver account, and call `process_action_receipt` directly (or drive it via `apply_action_receipt`/`process_receipt` runtime harness).
2. Assert state after processing: `get::<u32>(state_update, TrieKey::PendingDataCount{receiver_id, receipt_id})` equals `2`, and the postponed receipt is stored via `get_postponed_receipt`.
3. Deliver a single `DataReceipt` with `data_id` and the expected payload/deposit, processed through the normal data-receipt path.
4. Assert that after this delivery, `PendingDataCount` is `1` (not removed/zero), the postponed receipt is still present in state, and no execution outcome/refund was produced for it — demonstrating the deposit is permanently stuck despite the single logical dependency being "received."
