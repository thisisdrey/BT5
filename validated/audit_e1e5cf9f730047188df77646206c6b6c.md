### Title
Sidechannel-served bytes are invisible to the gRPC cost-trailer's byte accounting, letting the reported `x-gitaly-cost` stay fixed regardless of actual clone/fetch size - (File: internal/grpc/middleware/costhandler/costhandler.go)

### Summary
Gitaly's `x-gitaly-cost` trailer combines a static per-method weight with a "dynamic" component computed from gRPC in/out payload bytes recorded by the `grpcstats.PayloadBytes` stats handler. For sidechannel RPCs such as `PostUploadPackWithSidechannel` / `SSHUploadPackWithSidechannel`, the actual pack data never flows through the gRPC message stream that `stats.Handler` observes — it flows over a separate Yamux sidechannel connection. As a result, the dynamic byte count is always `0` for these RPCs and the cost is pinned to the hardcoded static override, no matter whether the transfer is 1 MB or 100 GB. This is the same bug class as the Chainlink oracle issue: a value that is supposed to scale proportionally with a real, attacker-controllable quantity (USD-feed decimals scaling the price; here, payload bytes scaling the cost) is instead computed from an assumption (all bytes flow through the instrumented path) that does not hold for certain inputs, producing an output that is wrong by orders of magnitude.

### Finding Description
`computeCost` combines `staticCostForMethod` and `dynamicCostFromContext`: [1](#0-0) 

The dynamic component solely comes from `grpcstats.PayloadBytesStatsFromContext`, which is populated by the `PayloadBytes` stats.Handler's `HandleRPC` reacting to gRPC `stats.InPayload`/`stats.OutPayload` events: [2](#0-1) 

However, `PostUploadPackWithSidechannel` (and the SSH sidechannel equivalents) transfer the actual pack/negotiation data over a dedicated Yamux stream that is opened out-of-band from the gRPC call, explicitly to avoid gRPC/Protobuf framing overhead: [3](#0-2) [4](#0-3) 

Because the sidechannel bytes never pass through the gRPC `stats.Handler` machinery, `dynamicCostFromContext` always returns `0` for these RPCs, and the reported cost is entirely determined by the hardcoded `staticCostOverrides` entry (`10`), independent of how much data is actually served: [5](#0-4) 

The project's own architecture doc acknowledges this limitation explicitly, framing it as a known trade-off rather than treating it as a security-relevant gap: [6](#0-5) 

### Impact Explanation
The `x-gitaly-cost` trailer is the sole per-RPC signal Gitaly exports for **upstream, complexity-based rate limiting**: Workhorse/Rails translate it into the `X-Score` HTTP header, which feeds Cloudflare's rate limiter on GitLab.com: [7](#0-6) [8](#0-7) 

Because the sidechannel path is also explicitly exempted from Gitaly's own concurrency limiter ("Cost-Aware Admission... bypasses the concurrency limiter entirely"): [9](#0-8) 

an ordinary, authenticated user performing repeated large clones/fetches of a large repository via `PostUploadPackWithSidechannel`/`SSHUploadPackWithSidechannel` produces requests that are simultaneously (a) exempt from Gitaly's internal concurrency limiter, and (b) reported to the outer rate limiter as a flat, small cost (`10`) regardless of whether tens of megabytes or many gigabytes were served. This lets a client's real resource consumption evade the upstream complexity-based rate limiter, undermining the DoS-mitigation defense-in-depth chain that this trailer is designed to drive.

### Likelihood Explanation
Any authenticated user who can issue a `clone`/`fetch` (which routes through `PostUploadPackWithSidechannel` over HTTP or `SSHUploadPackWithSidechannel`/`SSHUploadPack` over SSH) against a large repository triggers this path — no special privilege, malicious peer, or leaked token is required. The condition is deterministic (not a race or timing issue): every sidechannel-served RPC always reports the flat static cost. This is a normal, everyday Git operation (large clone/fetch), making the analog highly reachable.

### Recommendation
Track bytes transferred over sidechannel connections (e.g., via the `helper.CountingWriter` already used in `internal/gitaly/service/ssh/upload_pack.go`) and feed that count into `dynamicCostFromContext`/`computeCost` for sidechannel RPCs instead of relying solely on the gRPC-stats-handler-derived byte count. Alternatively, replace the flat `staticCostOverrides` entries for sidechannel RPCs with a cost model that incorporates the post-hoc `PackfileNegotiationStatistics`/served-bytes metrics that are already computed for these RPCs (see `recordServedBytes`) before setting the trailer.

### Proof of Concept
1. As an ordinary authenticated user, perform a full clone of a very large repository (e.g., 50 GB) via `PostUploadPackWithSidechannel`.
2. Observe the `x-gitaly-cost` trailer returned: it equals the static override (`10`), identical to what a trivial no-op `ls-refs` sidechannel call would return, because `dynamicCostFromContext` sees `InPayloadBytes/OutPayloadBytes == 0` for this call (confirmed by `internal/grpc/middleware/costhandler/costhandler_test.go` cases showing the "no stats"/"static only when no bytes" cases return the same value as the static override).
3. Repeat the clone in a loop; each request bypasses the internal concurrency limiter (per `doc/load-management-architecture.md`) and reports the same low cost to the upstream rate limiter via `X-Score`, regardless of the true bandwidth/CPU/disk load generated, allowing sustained high-cost traffic to slip past complexity-based throttling that assumes cost scales with actual transferred bytes.

// computeCost returns the cost score for a completed RPC. It combines a static
// base cost for the RPC type with a dynamic component from actual bytes
// transferred, read from the RPCEntry in context.
func computeCost(ctx context.Context, fullMethod string) int {
	static := staticCostForMethod(fullMethod)
	dynamic := dynamicCostFromContext(ctx)
	return static + dynamic
}

// HandleRPC implements per-RPC tracing and stats instrumentation.
func (s *PayloadBytes) HandleRPC(ctx context.Context, rs stats.RPCStats) {
	switch st := rs.(type) {
	case *stats.InPayload:
		bytesStats := ctx.Value(payloadBytesStatsKey{}).(*PayloadBytesStats)
		bytesStats.InPayloadBytes += int64(st.Length)
	case *stats.OutPayload:
		bytesStats := ctx.Value(payloadBytesStatsKey{}).(*PayloadBytesStats)
		bytesStats.OutPayloadBytes += int64(st.Length)
	}
}

func (s *server) PostUploadPackWithSidechannel(ctx context.Context, req *gitalypb.PostUploadPackWithSidechannelRequest) (*gitalypb.PostUploadPackWithSidechannelResponse, error) {
	repoPath, gitConfig, err := s.validateUploadPackRequest(ctx, req)
	if err != nil {
		return nil, structerr.NewInvalidArgument("%w", err)
	}

	var sidechannelRetryableError sidechannel.RetryableError
	conn, err := sidechannel.OpenSidechannel(ctx)
	if err != nil {
		if errors.As(err, &sidechannelRetryableError) {
			// Clients of PostUploadPackWithSidechannel are configured to retry the RPC upon receiving
			// Unavailable, so it should be OK to return it in this case.
			//nolint:gitaly-linters
			return nil, structerr.NewUnavailable("open sidechannel: %w", err)
		}
		return nil, structerr.NewInternal("open sidechannel: %w", err)
	}
	defer conn.Close()

	stats, err := s.runUploadPack(ctx, req, repoPath, gitConfig, conn, conn)
	if err != nil {
		return nil, structerr.NewInternal("running upload-pack: %w", err)
	}

	if err := conn.Close(); err != nil {
		return nil, structerr.NewInternal("close sidechannel connection: %w", err)
	}

	return &gitalypb.PostUploadPackWithSidechannelResponse{
		PackfileNegotiationStatistics: stats.ToProto(),
	}, nil
}

### Cost-Aware Admission

A separate admission layer that sits before the concurrency limiter in the
gRPC interceptor chain. If a request can be served from
[`streamcache`](../internal/streamcache/cache.go), it bypasses the concurrency
limiter entirely and proceeds directly to the handler. Currently this applies
to:

- [`PostUploadPackWithSidechannel`](../internal/gitaly/service/smarthttp/upload_pack.go) (clone/fetch)

```plaintext
Request -> Cost-Aware Admission -> Concurrency Limiter -> Handler
                 |
           (cache hit?)
                 |
           bypass limiter -> Handler directly
```

The concurrency limiter today treats every request as equally expensive. In
practice, requests served from cache consume minimal resources (disk streaming)
while cache misses run full Git subprocess pipelines. Rather than feeding the
limiter a cost hint (which still consumes a limiter slot), cache-hit requests
skip the limiter entirely — keeping the concurrency limiter pure and ensuring
limits designed for expensive operations do not penalize cheap ones.
```

### RPC Cost Score (`x-gitaly-cost`)

Gitaly returns a cost score for each RPC as a gRPC response trailer.
Gitaly has the most context about the actual cost of each RPC, making it the right
place to own this value. Rails and Workhorse translate the `x-gitaly-cost`
trailer into an `X-Score` HTTP response header, making the cost signal
available to any upstream rate limiter.

> On GitLab.com, the `X-Score` header feeds Cloudflare's
> [complexity-based rate limiting](https://developers.cloudflare.com/waf/rate-limiting-rules/request-rate/#complexity-based-rate-limiting).
> Self-managed deployments can use the same header with any upstream
> rate limiter or ignore it.
```

Static scores are derived from historical data per RPC type. A static score hides
variance (e.g. `PostUploadPackWithSidechannel` is the same cost whether it serves
1 MB or 10 GB), but dynamic cost (bytes transferred, object count) is only known
after the RPC completes. The two approaches can be combined: use the static score
