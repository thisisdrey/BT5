### Title
Anti-replay window `Check`-then-decrypt-then-`Update` race allows replayed packets to bypass replay protection - (File: `connection_state.go`)

### Summary
`ConnectionState.Decrypt` (and its sibling `VerifyRelay`) validates the anti-replay window with `window.Check()`, releases the lock, performs the (comparatively expensive) AEAD decryption, and only *afterwards* re-acquires the lock to actually record the counter as seen via `window.Update()`. Because the "read the state" step (`Check`) and the "commit the state" step (`Update`) are two separate critical sections separated by an unlocked, non-trivial amount of work, two goroutines processing the *same* replayed ciphertext concurrently can both pass `Check` before either has called `Update`, causing the same packet to be decrypted and delivered twice. This mirrors the reported DeFi bug class: a ratio/permission is computed from state that is mutated only *after* the decision was already made, so the mutation happens too late to prevent the extra benefit granted by the stale read.

### Finding Description
`ConnectionState.Decrypt` is: [1](#0-0) 

The check and the mutation are split across two independently-locked sections:
1. `cs.window.Check(l, messageCounter)` under `decryptLock`, then unlock.
2. `cs.dKey.DecryptDanger(...)` performed **without holding `decryptLock`**.
3. `cs.window.Update(l, messageCounter)` under `decryptLock` again.

`Bits.Check` only inspects state; it does not mark the counter as seen. Only `Bits.Update` mutates the bitmap: [2](#0-1) [3](#0-2) 

Nebula supports multiple concurrent UDP reader goroutines for the same socket via `SO_REUSEPORT` (`listen.routines`/`tun.routines` > 1) and `recvmmsg` batching: [4](#0-3) [5](#0-4) 

Each reader routine independently calls `readOutsidePackets`, which for a data packet calls `hostinfo.ConnectionState.Decrypt`: [6](#0-5) 

If an on-path or off-path attacker captures one legitimate ciphertext packet from the wire and re-transmits two (or more) copies of it so that they land on two different reader sockets/goroutines at roughly the same time, both goroutines can execute `Check(messageCounter)` before either has executed `Update(messageCounter)`, since the lock is released between the two calls and `DecryptDanger` runs unlocked in between. Both goroutines will then successfully decrypt the identical ciphertext (decryption success does not depend on the window state) and both will proceed to deliver the plaintext to `handleOutsideMessagePacket`/tun injection, etc. Only one of the two subsequent `Update` calls will "win" and mark the bit; but by that point both payloads have already been decrypted and acted upon — the anti-replay protection has already been defeated for that duplicate delivery.

This is analogous to the reported GMX bug: `shareAmt`/ratio (here: "is this counter allowed") is computed from state (`Check`) before the fee-minting/side-effect mutation (`Update`) that should have foreclosed the second actor's benefit; the expensive intervening operation (decryption here, external calls there) creates the window in which the stale read is exploited.

### Impact Explanation
This breaks a core Noise/WireGuard-style security guarantee: that each authenticated ciphertext counter is processed exactly once. An attacker with the ability to capture/replay UDP packets on the path (no CA-issued certificate required — they only need visibility of a single legitimate ciphertext already exchanged between two valid peers) can cause a captured application-layer or control-layer packet (e.g., a tun payload, `CloseTunnel`, `Control` relay message) to be delivered twice into the interface's processing pipeline, subverting the replay window that is nebula's sole defense against message replay. Depending on the payload this can duplicate injected traffic or duplicate protocol side effects (e.g., duplicate relay control processing), a concrete traffic-replay/forgery impact.

### Likelihood Explanation
Exploitability requires `listen.batch`/`tun.routines` > 1 (a supported, documented configuration, not a default-off dev flag) so that separate goroutines/OS threads read from the shared, `SO_REUSEPORT`-bound socket concurrently, and requires the attacker to win a narrow race by delivering duplicate copies of a previously-observed ciphertext within the small window between `Check` and `Update` (bounded by one AEAD decrypt). This is a genuine, remotely triggerable race but with a timing dependency, which is why it is a medium- rather than high-likelihood finding.

### Recommendation
Hold `decryptLock` for the entire check-decrypt-update sequence (or otherwise make the window check-and-reserve atomic, e.g., speculatively marking the counter as "in flight" under the lock before decrypting and rolling back on failure) so that a second concurrent attempt with the same counter cannot pass `Check` until the first attempt has either committed or failed. Alternatively, restructure `Bits` to expose a single atomic `CheckAndReserve` operation used by both `Decrypt` and `VerifyRelay`.

### Proof of Concept
1. Configure two nebula peers with `listen.batch` or `tun.routines`/`listen.routines` set so multiple reader goroutines read from the same `SO_REUSEPORT` UDP socket (see `NewInterface`/`activate` and `udp.NewListener(..., multi=true, ...)`).
2. Establish a tunnel and let peer A send one authenticated data packet to peer B; capture the raw ciphertext UDP datagram (e.g., via a MITM/packet capture on the path — no certificate needed).
3. Simultaneously re-inject two (or more) identical copies of the captured datagram toward peer B such that they are picked up by two different reader goroutines at effectively the same time (this is directly reproducible in-process by calling `readOutsidePackets`/`ConnectionState.Decrypt` from two goroutines concurrently with the same `messageCounter` and ciphertext, as in `connection_state_test.go`'s harness).
4. Observe that both goroutines pass `window.Check` (since neither has called `Update` yet), both successfully `DecryptDanger` the payload, and both proceed to deliver/process the plaintext — i.e., the same message counter is accepted and acted on twice, even though `Bits.Update` ultimately only records it once.

func (b *Bits) Check(l *slog.Logger, i uint64) bool {
	// If i is the next number, return true.
	if i > b.current {
		return true
	}

	if b.strictlyWithinWindow(i) {
		return !b.get(i)
	}

	// Not within the window
	if l.Enabled(context.Background(), slog.LevelDebug) {
		l.Debug("rejected a packet (top)", "current", b.current, "incoming", i)
	}
	return false
}

func (b *Bits) Update(l *slog.Logger, i uint64) bool {
	// Fast path: i is the next expected counter. Split out so the function
	// stays small and avoids paying for the slow paths' slog argument-build
	// stack frame on every call. The bit read/test/write is inlined to
	// touch the backing word once.
	if i == b.current+1 {
		pos := i & b.lengthMask
		word := pos >> 6
		mask := uint64(1) << (pos & 63)
		w := b.bits[word]
		if i > b.length && w&mask == 0 {
			b.lostCounter.Inc(1)
		}
		b.bits[word] = w | mask
		b.current = i
		return true
	}
	return b.updateSlow(l, i)
}
