## Title
Balancer-style join/exit MEV analog: `ExchangeInjectContract` and `ExchangeWithdrawContract` (TRX/TRC10 Bancor-style AMM) accept no minimum/maximum bound on the counter-asset amount, enabling sandwich theft - ([File: actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java], [File: actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java])

### Summary
java-tron's built-in `Exchange` feature is a Bancor-style constant-product AMM for TRX/TRC10 pairs, exposed through three actuators: `ExchangeInjectActuator` (add liquidity / "join"), `ExchangeWithdrawActuator` (remove liquidity / "exit"), and `ExchangeTransactionActuator` (swap). The swap path already implements slippage protection via an `expected` minimum-output field that is checked in validation, but the inject and withdraw paths have no equivalent bound, mirroring exactly the Balancer `join`/`exit`/`swap` MEV report where some actions lacked `minValueOut`/`maxValueIn` checks.

### Finding Description
`ExchangeTransactionContract` (the swap action) carries an `expected` field and is validated against it: [1](#0-0) [2](#0-1) 

In contrast, `ExchangeInjectContract` and `ExchangeWithdrawContract` only carry `token_id` and `quant` — no minimum/maximum bound on the paired ("another") token amount at all: [3](#0-2) 

In `ExchangeInjectActuator`, the amount of the counter-asset the user must simultaneously deposit (`anotherTokenQuant`) is derived purely from the *current* pool ratio at execution time, and the only checks are that it is `> 0`: [4](#0-3) 
and it is then unconditionally deducted from the user's balance during `execute()`: [5](#0-4) 

Similarly, `ExchangeWithdrawActuator` computes the counter-asset amount the user *receives* (`anotherTokenQuant`) from the current pool ratio, with checks only for a rounding "precision" bound (0.01%), not for any user-specified minimum: [6](#0-5) 
and this amount is credited to the account in `execute()` with no further protection: [7](#0-6) 

Because the pool ratio (`firstTokenBalance`/`secondTokenBalance`) can be shifted arbitrarily within the same block by any other account issuing `ExchangeInjectContract`, `ExchangeWithdrawContract`, or `ExchangeTransactionContract` transactions against the same `exchange_id` immediately before the victim's transaction is packed, an attacker (including a block-producing witness, or any actor able to order transactions ahead of the victim's in the mempool) can sandwich a victim's inject/withdraw exactly as described in the Balancer report:
- Front-run: shift the pool ratio unfavorably for the victim.
- Victim tx executes: pays far more of "anotherToken" on inject, or receives far less "anotherToken" on withdraw, than the ratio at submission time implied.
- Back-run: attacker reverses their own trade, capturing the difference.

### Impact Explanation
This is a direct value-extraction / theft-of-funds vector reachable by any account that has TRX/TRC10 balances and issues a normal `ExchangeInjectContract` or `ExchangeWithdrawContract` transaction — no special privilege required. Victims lose real, backed TRX/TRC10 balance to the attacker on every inject/withdraw against an actively-traded exchange pair, exactly matching the accepted impact bar of "theft of funds" via unauthorized value extraction from a normal user operation.

### Likelihood Explanation
Any unprivileged account can create the `Exchange` pool (`ExchangeCreateContract`) and any unprivileged account can trade against it via `ExchangeTransactionContract` in the same block, giving an attacker full control to manipulate `firstTokenBalance`/`secondTokenBalance` immediately before a victim's `ExchangeInject`/`ExchangeWithdraw` transaction executes. This requires only transaction ordering within a block (achievable by a witness producing the block, or generally by broadcasting transactions with favorable timing/fee), which is the same capability MEV searchers use against Balancer today. No exotic preconditions are needed.

### Recommendation
Add a `min_expected` (for withdraw, e.g., minimum `anotherTokenQuant` the user is willing to receive) and a `max_expected` (for inject, e.g., maximum `anotherTokenQuant` the user is willing to pay) field to `ExchangeInjectContract` and `ExchangeWithdrawContract`, and validate the actual computed `anotherTokenQuant` against these bounds in `ExchangeInjectActuator.doValidate()` and `ExchangeWithdrawActuator.doValidate()`, the same way `ExchangeTransactionActuator` already validates `expected` against the computed swap output.

### Proof of Concept
1. Attacker creates or identifies an `Exchange` pool with pair `(A, B)` and current balances `(balA, balB)`.
2. Victim broadcasts `ExchangeInjectContract{exchange_id, token_id=A, quant=Q}`, expecting to also deposit `~balB*Q/balA` of `B` based on the pool state they observed.
3. Attacker, seeing the victim's pending transaction, front-runs with their own `ExchangeInjectContract` or `ExchangeTransactionContract` on the same `exchange_id` that shifts `balA`/`balB` sharply (e.g., swaps a large amount of `A` for `B`), inflating the implied price of `B` relative to `A`.
4. Victim's inject executes against the manipulated ratio in `ExchangeInjectActuator.execute()` ( [5](#0-4) ), forcing the victim to pay a much larger amount of `B` than intended, with only an `anotherTokenQuant <= 0` guard and no upper bound.
5. Attacker back-runs, reversing their manipulation trade and withdrawing the excess value extracted from the victim's inject (or, symmetrically, from a withdraw sandwiched to minimize the victim's `anotherTokenQuant` received).
