### Title
Attacker can fill `feeCollector`'s per-account token list to `MAX_TOKENS_PER_USER`, DoSing withdrawals, deposits, and liquidations - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
`Pool` tracks per-account token holdings in `depositTokensOfAccount`/`debtTokensOfAccount` and caps them at `MAX_TOKENS_PER_USER = 30`. Any transfer of a `DepositToken` to an address with a zero balance pushes that token onto the recipient's list via `Pool.addToDepositTokensOfAccount`, which reverts with `UserReachedMaxTokens` once the combined list hits 30 [1](#0-0) [2](#0-1) . The protocol fee collector is a regular address that receives fee transfers inside `_withdraw` and `Pool.liquidate` [3](#0-2) [4](#0-3) . An unprivileged attacker can dust-transfer 1 wei of up to 30 distinct deposit tokens to `feeCollector`, filling its list and causing every subsequent fee-bearing withdrawal, deposit, and liquidation to revert.

### Finding Description
1. `DepositToken._transfer` calls `pool.addToDepositTokensOfAccount(recipient_)` whenever the recipient's balance was zero [2](#0-1) .
2. `Pool.addToDepositTokensOfAccount` enforces `onlyIfAdditionWillNotReachMaxTokens`, reverting when `debtTokensOfAccount.length + depositTokensOfAccount.length >= 30` [1](#0-0) [5](#0-4) .
3. `DepositToken._withdraw` sends the fee to `pool.feeCollector()` via `_transfer` before burning [6](#0-5) , and `Pool.liquidate` seizes `_fee` to `feeCollector` [4](#0-3) . Deposit fees follow the same pattern.
4. `feeCollector` is an arbitrary address (EOA/multisig) set in `PoolRegistry`; nothing prevents third parties from transferring deposit tokens to it, and the cap is per-recipient, not per-sender.
5. Once the attacker stuffs 30 dust positions into `feeCollector`'s list, any fee transfer of a token the collector doesn't already hold reverts. Since the cap equals the max number of deposit tokens a pool can register (`ReachedMaxDepositTokens` at `MAX_TOKENS_PER_USER`) [7](#0-6) , the attacker can fill all 30 slots, blocking every fee-bearing operation pool-wide.

### Impact Explanation
- All `withdraw`/`deposit` calls that charge a nonzero fee revert → temporary freezing of user collateral (liveness break).
- `Pool.liquidate` reverts at the fee seize step → positions cannot be liquidated while fees are enabled, risking protocol insolvency from bad debt.
- Recovery requires the fee collector to notice and fully empty dust balances (balance→0 removes entries via `removeFromDepositTokensOfAccount`), which is manual and can be re-griefed.

### Likelihood Explanation
Fully unprivileged: attacker deposits dust into each listed collateral, then calls `DepositToken.transfer(feeCollector, 1)` for each. No privileged role, no oracle manipulation, minimal capital. Requires `depositFee`/`withdrawFee`/liquidation protocol fee > 0 (check `FeeProvider`/`PoolStorage` config on the deployed pool).

### Recommendation
Exempt `feeCollector` (or all protocol-internal recipients) from the `MAX_TOKENS_PER_USER` check, or make `addToDepositTokensOfAccount` skip the cap for the fee collector address. Alternatively, accumulate fees in the `DepositToken`/`Treasury` itself rather than transferring to an external list-tracked account.

### Proof of Concept
Hardhat sketch (fork or local deployment):
```ts
// pool has >= 2 deposit tokens and nonzero deposit/withdraw fee
for (const dt of await pool.getDepositTokens()) {
  const depositToken = await ethers.getContractAt('DepositToken', dt);
  const underlying = await ethers.getContractAt('ERC20', await depositToken.underlying());
  await underlying.mint(attacker.address, 1n);
  await underlying.connect(attacker).approve(depositToken.address, 1n);
  await depositToken.connect(attacker).deposit(1n);           // attacker gets dust msdToken
  await depositToken.connect(attacker).transfer(feeCollector, 1n); // fills feeCollector list
}
expect(await pool.getDepositTokensOfAccount(feeCollector)).to.have.length(30);

// victim tries to withdraw -> _transfer fee to feeCollector reverts
await expect(depositToken.connect(victim).withdraw(victimBal, victim.address))
  .to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');

// liquidation also reverts on fee seize
await expect(pool.connect(liquidator).liquidate(unhealthy, synth, repayAmt, depositToken.address))
  .to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');
```
