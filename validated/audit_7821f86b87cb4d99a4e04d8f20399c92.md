### Title
Missing contract-domain separation in StackerDB chunk signatures allows cross-lane forged-chunk replay and network-wide propagation - ([File: stackslib/src/net/stackerdb/mod.rs])

### Summary
`SlotMetadata::auth_digest()` (in `libstackerdb`, used by the in-scope `stackslib/src/net/stackerdb` code) signs only `(slot_id, slot_version, data_hash)` — it never binds the signature to the target `QualifiedContractIdentifier`. Because the Nakamoto signer-set boot contracts `signers-{0,1}-{message_id}` deterministically assign the *same* signer→slot_id mapping across all `message_id` lanes for a given signer-set parity (`signers-0-1`, `signers-0-2`, `signers-0-3` share identical slot ownership), a validly-signed chunk originally produced for one lane (e.g. `BlockResponse`, message_id=1) is a *fully valid* signed chunk for a sibling lane (e.g. `StateMachineUpdate`, message_id=2) at the same slot. Any remote, unprivileged peer who has observed one such (public) signed chunk can replay it into a sibling StackerDB contract via the P2P `StackerDBPushChunk` message or the `POST /v2/stackerdb/.../chunks` RPC, and the in-scope validation/storage code will accept and persist it, and the network will replicate it, without ever checking it was intended for that contract/lane.

### Finding Description
The signature-domain for StackerDB chunks is defined in `auth_digest()`: [1](#0-0) 

Note this digest never includes the `QualifiedContractIdentifier` (StackerDB contract) the chunk is destined for — only `slot_id`, `slot_version`, and `data_hash`.

The two authoritative acceptance paths inside the in-scope `stackslib/src/net/stackerdb` module rely solely on this digest, keyed by *this replica's own contract-scoped* signer table, but never re-derive or check a contract-specific binding in the signature itself:

- `StackerDBs::try_replace_chunk` (used by the RPC write path, `POST /v2/stackerdb/:addr/:contract/chunks`): [2](#0-1) 

- `PeerNetwork::validate_received_chunk` (used both for `StackerDBSync::validate_downloaded_chunk` pull-sync and for `handle_unsolicited_StackerDBPushChunk` gossip-push): [3](#0-2) 

Both paths look up "the signer that owns slot X *in this contract*" and then call `SlotMetadata::verify(&addr)`, which only recovers the public key from `(slot_id, slot_version, data_hash)` and checks the hash matches `addr`: [4](#0-3) 

Because the Nakamoto signer StackerDB contract-naming scheme assigns slot ownership purely by signer-set parity, independent of `message_id`: [5](#0-4) 

...and the boot contracts for every `message_id` within one signer-set parity call the identical slot-assignment function: [6](#0-5) 

...the slot→signer mapping is identical simultaneously across `signers-P-1` (BlockResponse), `signers-P-2` (StateMachineUpdate), and `signers-P-3` (BlockPreCommit) for the active parity `P`. This is confirmed by the boot-contract test, which shows the *same* signer list applies for a given `signer_set` regardless of `message_id`: [7](#0-6) 

Consequently, a chunk `(slot_id=X, slot_version=V, sig=S, data=D)` that a real signer validly produced and pushed to `signers-P-1` also passes `slot_desc.verify(&slot_validation.signer)` for the identically-slotted signer address in `signers-P-2` / `signers-P-3`, since the digest and signature are indistinguishable between contracts. Any observer of the (public, unauthenticated) P2P `StackerDBChunk`/`StackerDBPushChunk` traffic — i.e., any peer on the network, not the signer, and not requiring any privileged role — can lift that chunk and resubmit it under the sibling contract's namespace. `validate_received_chunk`/`try_replace_chunk` will accept it as "signed by the expected author" purely because the digest coincidentally recovers to the correct address for the wrong contract, and the chunk will be stored and then relayed/gossiped further to peers via the normal `StackerDBChunkInv`/`StackerDBPushChunk` propagation path: [8](#0-7) 

This breaks the equality the protocol relies on: "a signature that verifies for slot X in contract C authenticates content intended for contract C," when in fact it only authenticates `(slot_id, slot_version, hash(data))` with no contract binding at all.

### Impact Explanation
This allows an unprivileged remote party to inject forged/misplaced but validly-signed data into a StackerDB lane that was never signed for that lane, and to have the network-wide StackerDB replication/gossip machinery (`handle_unsolicited_StackerDBPushChunk`, `StackerDBChunkInv` patch/propagate logic) treat and relay it as authentic slot content for that contract. This matches the "network-wide propagation of forged data" / Critical impact class: nodes that rely on the signer-lane StackerDB contents (block-response aggregation, state-machine-update tracking, pre-commit tracking used by miners/signers to make consensus-adjacent decisions) can be fed data that was authenticated for a different purpose/lane, at attacker-chosen timing, purely by relaying previously-observed public gossip — no signer key, no admin role, and no privileged position are required.

Note: an application-level type-prefix filter (`signer_message_payload_matches_lane`) exists in `libsigner/src/events.rs`, but that file is explicitly out of scope per the rules, and more importantly it is a downstream consumer-side filter, not a control in the `stackslib/src/net/stackerdb` storage/validation/relay layer — the vulnerable acceptance-and-propagation logic in scope (`try_replace_chunk`, `validate_received_chunk`, `handle_unsolicited_StackerDBPushChunk`) has no contract-domain check at all.

### Likelihood Explanation
High likelihood: StackerDB chunk contents and signatures are transmitted in the clear over the P2P network and via public RPC (`POST /v2/stackerdb/...`), so any peer can observe a legitimately-signed chunk for one lane. Replaying it into a sibling contract requires only re-issuing the same bytes with a different `contract_id` field — no cryptographic work, no privileged credentials, and it is reachable purely by a remote, unauthenticated peer within the P2P/RPC surface of `stackslib/src/net`.

### Recommendation
Bind the StackerDB chunk signature to the target contract by including the `QualifiedContractIdentifier` (or a domain-separation tag derived from it) in `SlotMetadata::auth_digest()`, and reject/require re-verification wherever `try_replace_chunk` / `validate_received_chunk` currently assume that contract-scoped signer-address verification alone proves the chunk was intended for that specific contract. Update `libstackerdb::SlotMetadata::sign`/`verify` and all StackerDB signing call sites (`stacks-signer`, `stacks-node`) accordingly, versioning the wire format if backward compatibility is required.

### Proof of Concept
1. Node has an active reward cycle with signer-set parity `P`. The `.signers` contract assigns signer `Alice` (privkey `pkA`) to `slot_id = 3` for parity `P`. This slot assignment is identical for contracts `signers-P-1` (BlockResponse), `signers-P-2` (StateMachineUpdate), and `signers-P-3` (BlockPreCommit), per `NakamotoSigners::make_signers_db_name` and the `stackerdb-get-signer-slots` boot-contract call (`stackslib/src/chainstate/nakamoto/signer_set.rs:1060-1073`, `stackslib/src/chainstate/stacks/boot/signers-0-xxx.clar`).
2. Alice legitimately signs and pushes a `StackerDBChunkData { slot_id: 3, slot_version: 7, sig: S, data: D_blockresponse }` to `signers-P-1` (BlockResponse lane). This is publicly observable on the P2P network (`StackerDBPushChunk`) or via RPC ack.
3. An unprivileged attacker who observed this chunk crafts a new `StackerDBPushChunkData { contract_id: signers-P-2, chunk_data: StackerDBChunkData { slot_id: 3, slot_version: 7, sig: S, data: D_blockresponse } }` (identical slot fields/signature/data, only `contract_id` swapped) and sends it to any node, or POSTs it to `/v2/stackerdb/<addr>/signers-P-2/chunks`.
4. `PeerNetwork::validate_received_chunk` (or `StackerDBs::try_replace_chunk` for the RPC path) looks up `get_slot_signer(signers-P-2, 3)`, which resolves to Alice's address (same as in `signers-P-1`), then calls `slot_metadata.verify(&addr)` — which succeeds because the digest `(3, 7, hash(D_blockresponse))` and signature `S` are unchanged and valid for Alice's key, regardless of which contract they are checked against.
5. The forged chunk is accepted into `signers-P-2`'s slot 3, and `handle_unsolicited_StackerDBPushChunk` proceeds to update the local inventory and wake the sync state machine, causing the chunk to be relayed/gossiped to other peers as authentic `StateMachineUpdate` data for slot 3 — despite never having been signed by Alice for that lane.

    fn auth_digest(&self) -> Sha512Trunc256Sum {
        let mut hasher = Sha512_256::new();
        hasher.update(self.slot_id.to_be_bytes());
        hasher.update(self.slot_version.to_be_bytes());
        hasher.update(self.data_hash.0);
        Sha512Trunc256Sum::from_hasher(hasher)
    }

    pub fn verify(&self, principal: &StacksAddress) -> Result<bool, Error> {
        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )
        .map_err(|ve| Error::VerifyingError(ve.to_string()))?;

        let pubkh = Hash160::from_node_public_key(&pubk);
        Ok(pubkh == *principal.bytes())
    }
