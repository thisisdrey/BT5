### Title
Parser confusion in `net/http/cgi.RequestFromMap` produces wrong `URL.Path` for request URIs starting with `//` - ([File: src/net/http/cgi/child.go])

### Summary
`cgi.RequestFromMap` reconstructs the incoming request's `URL` from CGI environment variables (`REQUEST_URI`, or `SCRIPT_NAME`+`PATH_INFO`+`QUERY_STRING`). When the `HTTP_HOST` variable is absent/empty, it falls back to `url.Parse(uriStr)` [1](#0-0)  instead of `url.ParseRequestURI(uriStr)`. `url.Parse` treats a leading `//` as a network-path reference and consumes the first path segment as the authority/host, exactly the same root cause as CVE-2025-29914 in Coraza WAF.

### Finding Description
A client sends an HTTP/1.0-style request without a `Host` header (or the front-end CGI/FastCGI server otherwise leaves `HTTP_HOST` empty) with a request line such as `GET //bar/uploads/foo.php?a=b`. The server passes this through in `REQUEST_URI` unmodified, as is standard behavior for CGI implementations per RFC 3875. Inside `RequestFromMap`, since `r.Host == ""`, execution reaches the fallback branch that calls `url.Parse(uriStr)` (viaRequest=false) rather than `url.ParseRequestURI` (viaRequest=true) [2](#0-1) . Internally, `net/url.parse` treats any `rest` starting with `//` as introducing an authority component whenever `viaRequest` is false [3](#0-2) , so `bar` is consumed into `url.Host` and `url.Path` becomes `/uploads/foo.php`, silently dropping the leading `/bar` segment — a wrong, attacker-influenced `URL.Path`/`URL.Host` is handed to the Go program built on top of `cgi.Request()`/`RequestFromMap`. Any CGI-based Go program that performs path-based security decisions (route matching, path-prefix authorization, static file mapping) using `req.URL.Path` after calling this API can be bypassed the same way Coraza's `REQUEST_FILENAME`-based rules were bypassed. This is the same confusion the Go authors deliberately fixed in the request-line parser at `readRequestLimit` by using `url.ParseRequestURI` (viaRequest=true), which intentionally skips the authority-parsing branch for empty-scheme "//..." paths [4](#0-3) ; `cgi.RequestFromMap`'s fallback branch does not receive that same protection.

### Impact Explanation
Concrete impact: silent corruption of `req.URL.Path`/`req.URL.Host` for a subset of legitimately-constructed HTTP requests reaching a CGI/FastCGI Go program, which can lead to authorization/routing bypass in application code that trusts `URL.Path` from `cgi.Request()`. This is a parser-confusion class bug matching CWE-706 (URI parsing ambiguity), analogous to the Coraza advisory. Given the narrowness of the trigger (only reachable when `HTTP_HOST`/`Host` is empty, which is uncommon for modern HTTP/1.1 clients but is standard for HTTP/1.0 or certain proxy/CGI configurations) and that it only affects the little-used `net/http/cgi` package, this would likely be evaluated on Go's PUBLIC track as a low-severity issue rather than urgent, since exploitation depends heavily on how downstream CGI application code uses `URL.Path`.

### Likelihood Explanation
An unauthenticated attacker sending an ordinary HTTP request with a path starting with `//` and no `Host` header (achievable via raw HTTP/1.0 request or through certain proxy/CGI gateway configurations that forward `REQUEST_URI` verbatim) can trigger the mis-parse without any special privileges, matching the "ordinary user data through normal victim workflow" pattern used in the report.

### Recommendation
In `src/net/http/cgi/child.go`, change the fallback branch of `RequestFromMap` to use `url.ParseRequestURI(uriStr)` instead of `url.Parse(uriStr)`, consistent with how `net/http.readRequestLimit` already parses the request line, so that a leading `//` is preserved as `Path` rather than misinterpreted as an authority.

### Proof of Concept
```go
package cgi

import "testing"

func TestRequestWithoutHost_DoubleSlash(t *testing.T) {
	env := map[string]string{
		"SERVER_PROTOCOL": "HTTP/1.1",
		"HTTP_HOST":       "",
		"REQUEST_METHOD":  "GET",
		"REQUEST_URI":     "//bar/uploads/foo.php?a=b",
	}
	req, err := RequestFromMap(env)
	if err != nil {
		t.Fatalf("RequestFromMap: %v", err)
	}
	// Vulnerable behavior: url.Parse("//bar/uploads/foo.php?a=b") treats
	// "bar" as Host and drops it from Path, corrupting req.URL.Path.
	if req.URL.Host == "bar" || req.URL.Path != "//bar/uploads/foo.php" {
		t.Fatalf("parser confusion: got Host=%q Path=%q; want Host=%q Path=%q",
			req.URL.Host, req.URL.Path, "", "//bar/uploads/foo.php")
	}
}
```
This test fails against the current implementation (asserting the corrupted `Host="bar"`, `Path="/uploads/foo.php"`), demonstrating the same class of parser confusion described in GHSA-q9f5-625g-xm39. [5](#0-4)
