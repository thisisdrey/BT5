### Title
Out-of-bounds array read in TVM precompiled-contract ABI array parsing - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
`PrecompiledContracts.extractBytesArray` and `extractBytesArray32` parse ABI-encoded dynamic array arguments (`bytes[]`/`bytes32[]`) supplied as raw precompiled-contract call data without validating that the derived indices stay within the bounds of the `words` array built from that data, mirroring the class of bug in Assimp's `MDLImporter::InternReadFile_Quake1` where attacker-controlled length/offset fields are used to index a buffer without a bounds check.

### Finding Description
`extractBytes32Array` reads `words[offset]` to get an array length and then indexes `words[offset + i + 1]` for `i` in `[0, len)` with no check that `offset + len` is within `words.length`: [1](#0-0) 

`extractBytesArray` guards only the initial `offset` value (`offset > words.length - 1`), then derives `bytesOffset` and `bytesLen` from attacker-supplied words and uses them to index further into `words` (`words[offset + bytesOffset + 1]`) with no bound on `bytesOffset`/`len` relative to `words.length`: [2](#0-1) 

Both `offset`, `len`, and `bytesOffset` originate from `intValueSafe()` on `DataWord`s taken directly from the precompiled contract call's `data` argument — i.e., attacker-controlled ABI input supplied by any contract that performs a `CALL`/`STATICCALL` to a precompile that uses these helpers (e.g. the batch/multisig validation precompiles that parse signature/address arrays). Because `words` is a finite array sized to the actual input length, a crafted `len`/`bytesOffset` value that is inconsistent with the real `words.length` causes an `ArrayIndexOutOfBoundsException` when the code reads past the end of the array — directly analogous to the Assimp bug where a length field taken from untrusted input is used to index a buffer without validating it against the buffer's real size.

### Impact Explanation
An `ArrayIndexOutOfBoundsException` thrown deep inside precompiled-contract execution during TVM opcode processing is an unchecked `RuntimeException` originating from ordinary contract-call inputs, not a `Program`/VM-specific exception that the interpreter's `try/catch` blocks are designed to convert into a controlled revert. If this exception propagates out of `Program`'s expected exception hierarchy during transaction execution/block application, it can abort the enclosing transaction-processing logic in `Manager` in an unexpected way, functioning as a denial-of-service against block application for any block/transaction containing the crafted call, rather than a clean revert. At minimum it is an unhandled-exception "escape" from a code path any anonymous contract caller can trigger, undermining the intended fail-safe (i.e., "revert on bad input") behavior of the precompiled contract API.

### Likelihood Explanation
The trigger requires only a normal signed transaction that calls a contract which in turn `CALL`s a precompiled address whose implementation uses `extractBytesArray`/`extractBytes32Array` with attacker-controlled ABI-encoded array headers (length and offset words) — no special privileges, validator status, or network position are needed, making this reachable directly from the same untrusted transaction surface the report addresses (single contract call / broadcastable transaction).

### Recommendation
Add explicit bounds checks in `extractBytes32Array` and `extractBytesArray` (in `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`) verifying that `offset + len` (and `offset + bytesOffset + 1`, `offset + bytesOffset + len` for the byte-array variant) do not exceed `words.length` before indexing, returning an empty/failure result (as `extractBytesArray` already does for the initial `offset` check) instead of allowing the array index to exceed bounds. Ensure any resulting exception is caught within the precompiled contract dispatch layer and translated into a normal execution failure/revert.

### Proof of Concept
Craft a transaction that calls a contract performing a low-level `call` to a precompiled address whose contract implementation invokes `extractBytesArray`/`extractBytes32Array`, with ABI-encoded call data where the "array length" word (`words[offset]`) or the per-element "bytesOffset"/"bytesLen" words are set to large values inconsistent with the actual number of 32-byte words present in the supplied `data` (e.g., `len = 0xFFFFFFFF` while only a few words are actually supplied). This causes `words[offset + i + 1]` in `extractBytes32Array` or `words[offset + bytesOffset + 1]` in `extractBytesArray` to index past the end of the `words` array, throwing `ArrayIndexOutOfBoundsException` during precompiled-contract execution triggered by the transaction.

---
Note: I was unable to fully trace, within the available tool budget, the exact concrete precompiled-contract callers (e.g., `BatchValidateSign`/`ValidateMultiSign`) that invoke `extractBytesArray`/`extractBytes32Array`, nor confirm precisely how far up the call stack (`Program` → opcode dispatch → `Manager`) the resulting `ArrayIndexOutOfBoundsException` propagates before being caught. This limits certainty on whether the ultimate effect is a clean per-transaction revert (lower severity) or an uncaught failure affecting block application (higher severity as claimed above). This should be verified against the live call sites and exception-handling wrappers before treating the Impact/Likelihood sections as fully confirmed.
