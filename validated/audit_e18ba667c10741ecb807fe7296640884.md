### Title
Protocol fee bypass via structuring NEP-245/IMT `TokenDiff` intents into repeated unit-amount (`|delta|==1`) trades - (File: `contracts/defuse/core/src/intents/token_diff.rs`)

### Summary
`TokenDiff::token_fee` unconditionally returns `Pips::ZERO` for `TokenIdType::Nep171 | TokenIdType::Nep245 | TokenIdType::Imt` whenever the per-intent `amount <= 1`, with the fee applying only when a *single* `TokenDiff` moves `amount > 1` of a NEP-245/IMT token. Because this check is evaluated independently per `TokenDiff::execute_intent` call, an unprivileged signer can split a large NEP-245/IMT transfer into N separate unit-amount (`delta.unsigned_abs()==1`) `TokenDiff` intents and pay zero aggregate protocol fee, whereas a single `TokenDiff` moving the same total volume in one call would pay `fee_ceil(N)`.

### Finding Description
The broken binding: `total_fee(N deltas of magnitude 1 on token T) == total_fee(1 delta of magnitude N on token T)` is expected by the protocol's fee-collection intent (a proportional fee on token-in volume), but the code makes these unequal.

Code path: `TokenDiff::execute_intent` computes, for each negative delta in the intent, `Self::token_fee(token_id, amount, protocol_fee).fee_ceil(amount)` and adds it to `fees_collected`, which is then credited to `fee_collector` via `internal_add_balance`. [1](#0-0) 

`token_fee` itself: [2](#0-1) 

For `TokenIdType::Nep245 | TokenIdType::Imt`, if `amount > 1` the fee equals `protocol_fee`; if `amount <= 1` it returns `Pips::ZERO`, mirroring the NFT (`Nep171`) exemption. Since `Pips::fee_ceil` rounds any nonzero percentage up to at least 1 unit for `amount == 1` [3](#0-2) 
the exemption is a deliberate design choice to avoid charging a disproportionate whole-unit fee on indivisible NFT-like transfers — but it is evaluated purely on the `amount` field of a single intent call, with no state tracking cumulative volume for a `(signer, token_id)` pair across intents or across `execute_intents` calls.

Exploit: attacker (or attacker plus a matched counterparty within each batch, since `TransferMatcher::finalize` enforces net-zero deltas within each `execute_intents` call) signs N `MultiPayload`s, each containing a `TokenDiff` with `diff = {token_T: -1, ...}` matched by an offsetting `+1` from a counterparty account. Each call independently hits the `amount <= 1` branch and contributes `Pips::ZERO` to `fees_collected`, so `internal_add_balance` to the fee collector is never invoked for that token. Repeating this N times moves the same aggregate volume of `token_T` that a single `TokenDiff{token_T: -N}` intent would have moved, but the latter would have paid `fee_ceil(N)` via the `amount > 1` branch.

None of the existing guards (`MultiPayload::verify`, nonce/salt checks, `TransferMatcher::finalize` zero-sum invariant, `assert_one_yocto`) prevent this, because they only ensure signature validity and batch-level balance conservation — they do not track or rate-limit per-token cumulative fee-exempt volume across separate calls.

### Impact Explanation
Value transferred through the Verifier via NEP-245/IMT `TokenDiff` intents can bypass the protocol fee entirely by structuring the trade into unit-amount deltas, at the direct expense of the `fee_collector` (protocol revenue), matching the "protocol fees bypassed" Critical category. This is repeatable indefinitely across any NEP-245/IMT token (including attacker-deployed multi-token contracts) and any account pair, limited only by the number of `execute_intents` calls the attacker/counterparty are willing to submit.

### Likelihood Explanation
Preconditions: attacker needs a NEP-245/IMT token (which they can deploy and mint themselves, or use any existing multi-token whose unit represents meaningful value) and a counterparty (can be attacker's own second account) willing to net each unit trade to zero within a batch. No privileged role, relayer key, or DAO permission is required — any signer can submit `execute_intents`/`simulate_intents` calls. Cost is simply gas for N transactions instead of one; this scales linearly and is fully within reach of an unprivileged actor.

### Recommendation
Track and charge fees based on cumulative traded volume per `(signer_id, token_id)` within a time/nonce window, or remove the `amount <= 1` fee exemption for `TokenIdType::Nep245 | TokenIdType::Imt` (keep it only for genuinely non-fungible `Nep171`), or apply a minimum absolute fee floor independent of per-call `amount` so that structuring into unit trades cannot zero out the aggregate fee.

### Proof of Concept
`cargo test` in `contracts/defuse/core` (or `tests/src/tests/defuse/intents/token_diff.rs` using the sandbox harness already present):
1. Deploy/mint a NEP-245 token `mt1` with a fungible-like key (`amount` divisible), set `protocol_fee = Pips::ONE_PERCENT`.
2. Path A: user1 and user2 sign+execute a single `TokenDiff` pair with `{mt1: -100}` / `{mt1: +100, other: -X}` in one `execute_intents` batch. Assert `fee_collector` balance for `mt1` equals `Pips::ONE_PERCENT.fee_ceil(100)` (nonzero, from the `amount > 1` branch).
3. Path B: reset balances; user1 and user2 sign+execute 100 separate `MultiPayload`/`execute_intents` calls, each with `TokenDiff{mt1: -1}` / `{mt1: +1, other: -X/100}`. Assert `fee_collector` balance for `mt1` after all 100 calls equals `0` (each call hits the `amount <= 1` branch returning `Pips::ZERO`).
4. Assert the two `fee_collector` totals differ despite identical net `mt1` volume transferred (100 units), demonstrating attacker/counterparty capture of the avoided fee versus Path A.

    pub fn token_fee(token_id: impl Into<TokenIdType>, amount: u128, fee: Pips) -> Pips {
        let token_id = token_id.into();
        match token_id {
            TokenIdType::Nep141 => {}
            TokenIdType::Nep245 | TokenIdType::Imt if amount > 1 => {}

        }
