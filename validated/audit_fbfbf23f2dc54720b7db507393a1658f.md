### Title
Panic in `TransactionStateContainer::push_ids_into_queue` when held/pending transactions exceed capacity margin - (File: `core/src/banking_stage/transaction_scheduler/transaction_state_container.rs`)

### Summary
`push_ids_into_queue` derives the number of items to evict from the *whole* transaction map (`id_to_transaction_state`, which also contains `Pending` and `Held` transactions that are **not** in the `priority_queue`), but then pops that many items exclusively from `priority_queue` using `.expect("queue is not empty")`. This mirrors the VotiumStrategy pattern of computing an "available amount" from one accounting source and then blindly consuming from a narrower structure without checking that the narrower structure actually has enough entries — leading to a hard failure (there: `revert`; here: a Rust panic) when the assumption breaks down.

### Finding Description
The container's invariant (documented at the top of the struct) is: [1](#0-0) 

i.e. `id_to_transaction_state` (a `Slab`) holds every transaction that is `Queued`, `Pending` (popped by the scheduler, being processed by a `ConsumeWorker`, but still in the map), or `Held` (moved out of the queue into `held_transactions` until the next flush), while `priority_queue` only holds `Queued` entries.

`push_ids_into_queue` computes the eviction count from the map length, not from the queue length, and then pops strictly from the queue: [2](#0-1) 

If, at the time new transactions are inserted, the sum of `Pending` + `Held` entries is large enough that `id_to_transaction_state.len() - capacity > priority_queue.len()`, the `for _ in 0..num_dropped { ... pop_first().expect("queue is not empty") ... }` loop will call `pop_first()` on an already-empty (or prematurely exhausted) `priority_queue`, and the `.expect()` will panic.

This is structurally the same root-cause class as the VotiumStrategy report: the code computes a threshold/quantity from a superset of state (`unlockable + balance` there; `id_to_transaction_state.len()` here) and then assumes a subset structure (`lockedBalances` array there; `priority_queue` here) can always satisfy operations derived from that superset quantity, without an explicit guard for the case where the subset is smaller than expected.

### Impact Explanation
A panic inside `push_ids_into_queue` — which is invoked from the unprivileged transaction-ingestion path (`insert_new_transaction`, and via `retry_transaction` / `flush_held_transactions`) — will unwind on the banking-stage/scheduler thread. In Agave, an unhandled panic on a critical validator thread crashes the validator process, which is a concrete node-panic DoS impact.

### Likelihood Explanation
This requires the container to be filled with enough transactions marked `Pending` (currently checked out by `ConsumeWorker`s) or `Held` (blocked pending retry, e.g., due to nonce or account-lock conflicts) that their combined count, together with newly queued transactions, exceeds `capacity` by more than the number of entries that are actually sitting in `priority_queue` at that moment. This is plausible under sustained load with many conflicting/nonce transactions competing for the same accounts, since account contention and nonce handling are entirely attacker/user controllable via ordinary transaction submission — no privileged or operator role is needed. I was not able to fully trace every call site (`receive_and_buffer.rs`, `greedy_scheduler.rs`, `scheduler_controller.rs`) within the tool budget to confirm the exact numeric bound under which this becomes reachable in production configurations, so likelihood should be treated as plausible-but-unverified pending closer review of those call sites.

### Recommendation
Bound `num_dropped` by `priority_queue.len()` (i.e., `id_to_transaction_state.len().saturating_sub(capacity).min(priority_queue.len())`), or replace the `.expect("queue is not empty")` with a defensive `if let Some(priority_id) = self.priority_queue.pop_first() { ... } else { break; }` so an accounting mismatch degrades gracefully instead of panicking. More fundamentally, the eviction accounting should be derived from `priority_queue.len()` directly (the structure actually being drained) rather than from `id_to_transaction_state.len()`, which includes `Pending`/`Held` entries that are not eligible for eviction from the queue.

### Proof of Concept
Conceptual reproduction (exact reachability from `receive_and_buffer.rs`/`greedy_scheduler.rs` call sites not fully verified within this investigation):
1. Fill the container near `capacity` with transactions.
2. Cause a large fraction of them to become `Pending` (dispatch to workers) or `Held` (e.g., submit many transactions that reuse the same durable nonce or contend for the same writable account so they get retried via `hold_transaction` instead of being immediately re-queued) — see `retry_transaction`: [3](#0-2) .
3. Submit additional new transactions via `insert_new_transaction`, which calls `push_ids_into_queue` with only the newly inserted id(s).
4. If `id_to_transaction_state.len()` (including the `Pending`/`Held` transactions from step 2) exceeds `capacity` by more than the number of items presently in `priority_queue`, the eviction loop's `pop_first().expect("queue is not empty")` panics.

    fn push_ids_into_queue(
        &mut self,
        priority_ids: impl Iterator<Item = TransactionPriorityId>,
    ) -> usize {
        for id in priority_ids {
            self.priority_queue.insert(id);
        }

        // The number of items in the `id_to_transaction_state` map is
        // greater than or equal to the number of elements in the queue.
        // To avoid the map going over capacity, we use the length of the
        // map here instead of the queue.
        let num_dropped = self
            .id_to_transaction_state
            .len()
            .saturating_sub(self.capacity);

        for _ in 0..num_dropped {
            let priority_id = self.priority_queue.pop_first().expect("queue is not empty");
            self.remove_state(priority_id.id);
        }

        num_dropped
    }
