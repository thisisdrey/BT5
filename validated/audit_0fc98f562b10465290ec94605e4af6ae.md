### Title
Active permission holders can be granted rights to execute `AccountPermissionUpdateContract`, allowing them to unilaterally overwrite the Owner permission and lock out the true account owner - (File: `actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java`)

### Summary
TRON's multi-sig permission model mirrors the Vault's operator model: an `Owner` permission and one or more `Active` permissions, each with its own key set and threshold. `AccountPermissionUpdateActuator.checkPermission` validates the structure of a submitted `Permission` (threshold, key weights, operations bitmap) but never restricts which `ContractType` bits an `Active` permission's `operations` bitmap may contain, and specifically never excludes `AccountPermissionUpdateContract` itself from being delegated to an `Active` permission.

### Finding Description
When a transaction carries `AccountPermissionUpdateContract`, the signature check is dispatched purely based on the `permission_id` field on the contract, not necessarily the `Owner` permission (id 0). `TransactionCapsule.checkPermission` at [1](#0-0)  only requires that, if `permissionId != 0`, the resolved permission is of type `Active` and its `operations` bitmap authorizes the contract type being executed - there is no special-case that forbids `Active` permissions from authorizing `AccountPermissionUpdateContract`.

`AccountPermissionUpdateActuator.checkPermission` at [2](#0-1)  validates the `operations` bitmap only against `dynamicStore.getAvailableContractType()`, i.e. it only checks that the bit corresponds to a currently-enabled contract type - it never excludes `AccountPermissionUpdateContract` from the set of operations an `Active` permission may be granted.

Consequently, if an account's `Active` permission is ever configured (by design or mistake) with the `AccountPermissionUpdateContract` bit set, any key holder in that lower-tier `Active` permission (which was meant to have limited authority, e.g. only `TransferContract`) can sign and broadcast a new `AccountPermissionUpdateContract` that completely replaces the `Owner` permission and all `Active` permissions - install itself as sole key with `Owner` rights, and drop every other operator/key, including the original account owner. `AccountCapsule.updatePermissions` unconditionally overwrites `owner_permission` and clears/rebuilds `active_permission` with whatever list is supplied in the contract, with no verification that the previous `Owner` keys retain any control: [3](#0-2) .

This is the direct analog of the reported Vault issue: a privileged-but-lower-tier role (`Active` permission holder) is able to remove/replace every privileged actor (`Owner` and other `Active` permissions) in one action, with no safeguard preventing the account from being left solely under the control of the delegate, or the legitimate owner being permanently locked out of the account (unable to sign owner-privileged transactions or later fix the permission set with their old owner key).

### Impact Explanation
This results in unauthorized account takeover and permanent loss of control (permanent freezing of funds and account-management ability) for the original owner and any other privileged co-signers, whenever a lesser-privileged `Active` key is (mistakenly or maliciously by a coordinated subset) empowered with the `AccountPermissionUpdateContract` operation bit. This meets the Medium/High bar of "unauthorized account operation" and "permanent freezing of funds," matching the class of the original Vault finding (loss of core account functionality due to unchecked privilege removal).

### Likelihood Explanation
Requires the account owner to have granted the `AccountPermissionUpdateContract` bit within an `Active` permission's operations bitmap (via a normal, signed `AccountPermissionUpdateContract` transaction) - there is no protocol-level restriction preventing this configuration, and no warning/validation step blocks it, so it can occur through operator misconfiguration or through an Active-permission holder(s) deliberately colluding, exactly mirroring the trust assumption caveat in the original report.

### Recommendation
In `AccountPermissionUpdateActuator.checkPermission`, explicitly forbid the `AccountPermissionUpdateContract` bit from being set for permissions of type `Active` (only `Owner` should ever be allowed to authorize account permission changes), i.e. reject any `Active` permission whose `operations` bitmap has the bit corresponding to `AccountPermissionUpdateContract` set.

### Proof of Concept
1. Owner submits an `AccountPermissionUpdateContract` transaction (signed with `Owner` permission) that creates/updates an `Active` permission whose `operations` bitmap includes the bit for `AccountPermissionUpdateContract`, and grants a key `K` sufficient weight to meet that `Active` permission's threshold.
2. Key `K` alone (using `permission_id` pointing at that `Active` permission) now signs and broadcasts a new `AccountPermissionUpdateContract` that sets `Owner` permission to itself only, and removes all other `Active` permissions.
3. `TransactionCapsule.validateSignature`/`checkPermission` at [4](#0-3)  accepts the transaction because `K`'s `Active` permission authorizes `AccountPermissionUpdateContract`.
4. `AccountPermissionUpdateActuator.execute` applies `updatePermissions`, permanently replacing `Owner` and `Active` permissions - the original owner and other operators lose all control of the account.

      }

        permission = AccountCapsule

      }
    } else {
      permission = account.getPermissionById(permissionId);
    }
    if (permission == null) {
      throw new PermissionException("permission isn't exit");
    }
    checkPermission(permissionId, permission, contract);
    long weight = checkWeight(permission, transaction.getSignatureList(), hash, null);
    if (weight >= permission.getThreshold()) {
      return true;
    }
    return false;

  public void updatePermissions(Permission owner, Permission witness, List<Permission> actives) {
    Builder builder = this.account.toBuilder();

    owner = owner.toBuilder().setId(0).build();
    builder.setOwnerPermission(owner);
    if (witness != null && builder.getIsWitness()) {
      witness = witness.toBuilder().setId(1).build();
      builder.setWitnessPermission(witness);
    }

    builder.clearActivePermission();
    if (actives != null) {
      for (int i = 0; i < actives.size(); i++) {
        Permission permission = actives.get(i).toBuilder().setId(i + 2).build();
        builder.addActivePermission(permission);
      }
    }

    this.account = builder.build();
  }
