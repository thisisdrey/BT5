### Title
Leftover-file migration deletes `.keep` protection files, exposing packfiles to concurrent housekeeping deletion - (File: internal/gitaly/storage/storagemgr/partition/migration/leftover_file_migration.go)

### Summary
The Beanstalk report describes value that is received into Beanstalk (Beans transferred during order creation) but never recorded in the accounting structure (`internal balance`) that a later migration process relies on to preserve state — causing silent, permanent loss of user funds. The analogous class of bug in Gitaly is: a filesystem migration process that walks a repository and moves any file not matching its "tracked state" model into a lost+found/trash location, while the file it moves (a Git `.keep` file) is actually load-bearing protection state for other tracked data (a packfile) that the migration's own model does not understand. Because the protection is untracked by the regex-based "keep" model, it is stripped, and a concurrent/subsequent Git housekeeping operation can then delete the very packfile the `.keep` file was protecting — resulting in object loss for the repository.

### Finding Description
`NewRegexSnapshotFilter` in `internal/gitaly/storage/storagemgr/partition/snapshot/snapshot_filter.go` defines the set of paths that Gitaly's WAL/transaction system considers part of the "tracked" repository state. Its include patterns for `objects/pack` only match `.pack`, `.idx`, `.rev`, and `.bitmap` files: [1](#0-0) 

`.keep` and `.mtime` files are deliberately excluded from this pattern set, as confirmed by the test fixtures which list `.keep`/`.mtime` files under "Directories and files that should be included by default filter and excluded by the regex based filter": [2](#0-1) 

`NewLeftoverFileMigration` (`internal/gitaly/storage/storagemgr/partition/migration/leftover_file_migration.go`) uses exactly this filter to decide what counts as "leftover garbage" in a repository being migrated onto the transactional/WAL storage backend. Any file that does not match `snapshotFilter.Matches` is linked into a lost+found trash directory and then **permanently removed from the repository** via `os.Remove` and `tx.FS().RecordRemoval`: [3](#0-2) 

Since `.keep` files under `objects/pack/*.keep` do not match the include regex, they are treated as leftover garbage and deleted from the live repository the same way arbitrary junk files are. The code does contain a special case (`needBackupObjectsDir`) that detects the presence of `.keep` files or a `logs` directory and, if found, performs a *second* walk that additionally copies the whole `objects` directory into the lost+found trash as a backup: [4](#0-3) [5](#0-4) 

However, this backup only *copies* objects into the trash directory for disaster-recovery purposes — it does not prevent removal of the `.keep` file from its original location in the live `objects/pack` directory, nor does it restore or recreate the `.keep` protection there. In stock Git, a `<pack>.keep` file is a sentinel that tells `git repack`/`git gc`/`git prune-packed` that the corresponding packfile must not be repacked away or deleted, even if it appears to contain no currently reachable objects (this is used, for example, to protect packs that are mid-transfer, or objects that are referenced only by data not yet visible to ordinary ref-walking, such as during concurrent replication/fetch operations). By stripping the `.keep` sentinel without any coordinated lock against concurrent Git housekeeping, the migration creates a window where a background `git gc`/repack invoked on the same repository (via Gitaly's own `OptimizeRepository`/housekeeping manager, or by an external `git gc`) can legitimately decide the now-unprotected pack is disposable and remove or repack it, permanently losing the objects it was safeguarding.

This migration is invoked transparently on any repository access once WAL/transactions are enabled and the migration hasn't yet run for that repository — it is triggered from `migrationManager.Begin`, which every partition transaction (including ordinary read/write RPCs from an unprivileged user, as shown by the test calling `RepositorySize`) passes through: [6](#0-5) [7](#0-6) 

Just as Beanstalk's migration process only preserved value present in "internal balance" and dropped anything held outside that structure, Gitaly's leftover-file migration only preserves the *live* repository state that its regex filter is aware of, and it destroys the `.keep` sentinel — an out-of-band protection mechanism not modeled by that filter — resulting in objects that are no longer safe from garbage collection.

### Impact Explanation
If a repository migrated to the WAL/transactional backend has an active `.keep` file protecting a packfile at the moment the leftover migration runs, the `.keep` file is deleted from its live location. Any subsequent Git housekeeping (repack/gc/prune) that runs against that repository — whether triggered by Gitaly's own optimization scheduler or an external process — may then legitimately treat the previously-protected pack as unreferenced garbage and delete or repack it away, causing permanent object loss (dangling refs, missing blobs/commits, corrupted history) for the repository. This is a data-integrity/DoS-class impact on ordinary repository operations, triggered purely by normal RPC traffic that lazily invokes the migration — no attacker privilege is required.

### Likelihood Explanation
The trigger condition requires: (1) the `leftover_migration` feature flag enabled and the repository not yet migrated, and (2) a `.keep` file present in `objects/pack` at migration time (a legitimate, if narrow, window — `.keep` files are typically short-lived, created by tools like `git receive-pack`/`git-http-backend`/replication to guard in-flight packs) and (3) a housekeeping/gc pass racing against the migration on the same repository. Because migrations run automatically and transparently on the first transaction against a repository (see `manager.go`'s `Begin`/`migrate`), the exposure window is determined by ordinary traffic timing rather than any special access, making this reachable without elevated privilege, though it depends on a timing race with the `.keep` file's short lifetime.

### Recommendation
When the leftover-file migration encounters a `.keep` file (or a `logs` directory) that indicates active or recent Git housekeeping/lock state, it should not merely back up the objects directory to lost+found for forensics — it should either (a) preserve the `.keep` file in its original location (add it to the snapshot filter's include set, or special-case it to be linked rather than removed), or (b) coordinate with the housekeeping/lock subsystem (e.g., take the same lock `git gc`/repack would take, or abort/retry the migration) so that the pack's protection is never dropped while it may still be needed. At minimum, the migration should recreate the `.keep` file in-place after copying, rather than only stashing a copy in a separate trash directory that ordinary Git tooling never consults.

### Proof of Concept
1. Enable the `leftover_migration` feature flag and create (or have) a repository not yet migrated to the WAL-managed migration state.
2. Simulate an in-flight pack transfer by placing a `.keep` file next to a packfile in `objects/pack/` (as done in `leftover_file_migration_test.go`'s `hasDotKeepFiles` scenario) to mark that packfile as currently required and not to be garbage collected.
3. Issue any ordinary RPC against the repository (e.g., `RepositorySize`) to trigger `migrationManager.Begin` → `performMigrations` → `NewLeftoverFileMigration`, as exercised in `TestNewLeftoverFileMigration`: [7](#0-6) 
4. Observe that the `.keep` file is removed from `objects/pack` in the live repository (only a copy exists under the `LostFoundPrefix` trash directory), while the referenced pack remains in place but is no longer protected.
5. Concurrently or subsequently trigger Git housekeeping (`git repack`/`git gc`/`OptimizeRepository`) on the same repository; because the `.keep` sentinel is gone, the housekeeping process may repack/prune the previously-protected pack, permanently discarding objects it once guarded.
