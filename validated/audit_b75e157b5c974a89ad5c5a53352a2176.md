### Title
Post-Receive Notification Race Allows Stale-Replica Reads Before Praefect Commit Settles - ([File: internal/gitaly/hook/postreceive.go])

### Summary
Gitaly's `post-receive` hook notifies GitLab Rails (`/internal/allowed`, `/post_receive`) about a push as soon as the primary Gitaly node's local transaction commits, without necessarily waiting for Praefect to confirm that all secondary replicas have applied the write and that the routing/database state has been updated. This creates a window — gated by a feature flag that defaults to **disabled** — in which Rails (and, transitively, any client action Rails triggers such as a subsequent API call, fetch, or read routed by Praefect) can observe or act on the "new" state signal before the multi-node write has actually settled everywhere. This is the direct Gitaly analog of the reported oracle sandwich-attack bug class: an attacker or ordinary user can race the notification/settlement gap to obtain inconsistent (stale) read state right after their own write.

### Finding Description
Git's `post-receive` hook is executed on the Gitaly primary node once the local Git transaction has committed [1](#0-0) . Immediately after committing (and, when running as primary, before any cross-replica settlement guarantee), the hook proceeds to call Rails' `/internal/allowed` and `/post_receive` endpoints and to synchronize with secondaries via a vote [2](#0-1) .

In a Praefect (HA) deployment, the actual multi-node consistency guarantee (DB generation update + replication job enqueueing) is a separate, asynchronous step performed by Praefect after the transaction's committed phase concludes. Gitaly added a `SignalPostReceiveReady` RPC and a `PostReceiveRegistry` specifically to close this gap: the primary's post-receive hook is supposed to block (`waitForPraefectSignal` / `RegisterWaiter`) until Praefect calls back to confirm the DB write and replication jobs are queued [3](#0-2) . This callback path is implemented behind the `PraefectPostReceiveSignal` feature flag, which is explicitly documented as preventing "a race where Rails is notified before all replicas have applied the write" [4](#0-3) .

Critically, this feature flag **defaults to `false`** [5](#0-4) . This means that, in the default/unpatched code path, the race the flag is meant to fix is still live: the post-receive hook calls Rails and completes as soon as the local Git write and the primary's own commit finish, without waiting for the Praefect-side signal confirming that the routing table / DB generation has advanced and all replicas hold the write. The `SignalPostReceiveReady` RPC itself documents the exact race it addresses: "a race condition where Rails is notified before all Gitaly replicas have applied the write and before Praefect has updated its database for routing decisions" [6](#0-5) .

This is structurally identical to the reported bug class: a state transition (oracle exchange-rate update / here, the multi-replica commit and routing-table update) is not atomic with the "unlocking" event that other actors rely on (Alice's withdrawal / here, Rails-driven client operations such as follow-up API calls, MR creation, or reads that get routed by Praefect based on generation numbers). An ordinary authenticated user who performs a normal `git push` triggers this window on every push; a second, concurrent RPC (their own follow-up fetch, another user's read, or a CI job reading the just-pushed ref) can be served by a Praefect-routed replica that has not yet received the write, observing pre-push state despite Rails/GitLab already having been told the push succeeded and reference values had been recorded.

### Impact Explanation
Any ordinary user with normal push access can trigger this race on every push in a Praefect/HA Gitaly cluster. It can cause:
- Read-after-write inconsistency: a client immediately fetching/cloning after a push, or Rails performing follow-up operations that assume the write is durable across the cluster, may see a Gitaly node that has not received the new objects/refs yet.
- Downstream side effects driven by GitLab's `/post_receive` webhook logic (e.g., CI job triggering, MR update) firing based on a write that has not fully propagated, opening a window for stale reads/replays similar in spirit to the sandwich attack's "act between old and new state."
This does not directly corrupt data, but it breaks the consistency guarantee the `SignalPostReceiveReady` mechanism was explicitly built to provide, and it is reachable purely through an unprivileged, ordinary push RPC.

### Likelihood Explanation
The vulnerable condition is the *default* configuration (feature flag off) [5](#0-4) , so no special configuration or privileged actor is required — it triggers on every push through Praefect. The race window is narrow (single commit round-trip) but deterministic in existence, and is explicitly acknowledged in the codebase's own comments as a real, previously-unaddressed timing issue.

### Recommendation
- Enable `PraefectPostReceiveSignal` by default (or remove the flag once validated) so that `PostReceiveHook` always waits on `PostReceiveRegistry.RegisterWaiter` for the Praefect `SignalPostReceiveReady` callback before calling Rails' `/internal/allowed` and `/post_receive` endpoints.
- Ensure `waitForPraefectSignal` enforces a bounded timeout with a safe failure mode (fail-closed) rather than silently proceeding without confirmation if the signal is delayed.
- Add regression tests that assert Rails is never notified before the corresponding Praefect DB generation/routing update has been observed to have occurred, across primary/secondary node combinations.

### Proof of Concept
Not independently reproducible from static analysis alone; the race is timing-dependent and requires a live Praefect/Gitaly HA cluster. The following sequence is described in the codebase's own documentation and comments and represents the reachable attack surface:
1. An ordinary authenticated user performs `git push` to a Praefect-fronted repository.
2. The primary Gitaly node commits its local transaction and, because `PraefectPostReceiveSignal` is disabled by default, immediately invokes the `post-receive` hook logic, which calls Rails `/internal/allowed`/`/post_receive` without waiting for `SignalPostReceiveReady` [2](#0-1) .
3. Concurrently (or via a Rails-triggered follow-up call), a read RPC is routed by Praefect to a secondary node before that secondary's replication job (still being enqueued asynchronously) has applied the write, observing stale state despite the push having been acknowledged.

**Note:** I was not able to inspect `internal/gitaly/service/hook/signal_post_receive.go` in full (only located via `grep_search`), so the exact wait/timeout implementation on the primary's blocking path (`waitForPraefectSignal`) could not be fully verified. A Devin session with full file access would be needed to confirm the precise blocking/timeout semantics and fail-open/fail-closed behavior.

// PostReceiveRegistry coordinates PostReceiveHook execution with Praefect signaling.
// When Praefect transactions are active, the PostReceiveHook needs to wait for Praefect
// to signal that all replicas have completed and the database has been updated before
// calling Rails. This registry provides the synchronization mechanism.
//
// Signal and RegisterWaiter race, and Signal can arrive first. Both are driven off the
// same event — the transaction's committed phase concluding — but then run on
// independent paths:
//
//   - Praefect (async monitor): CommittedConcluded -> DB generation write -> backchannel
//     SignalPostReceiveReady RPC -> Signal.
//   - Primary Gitaly (the push): committed-phase vote returns -> git finishes the ref
//     update -> post-receive hook runs -> waitForPraefectSignal -> RegisterWaiter.
//
// The committed phase concludes at essentially the same instant on both sides, so if the
// signal path (which includes a DB round-trip and a network RPC) happens to complete
// before the primary reaches its post-receive hook — e.g. fast/local Postgres or
// single-node quorum — Signal is called before RegisterWaiter. To handle this, Signal
// buffers the result in `signaled` and RegisterWaiter returns a pre-populated channel if
// a signal is already waiting. This buffering is required for correctness: without it the
// hook would block until timeout whenever the signal wins the race.

  // This RPC is called by Praefect after the request finalizer has completed (DB update

  // transaction that was used to coordinate the write across replicas.

    option (op_type) = {
      op: ACCESSOR
