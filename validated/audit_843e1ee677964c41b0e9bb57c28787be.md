### Title
Unauthenticated `RecvError` packets allow replayable, spoofable tunnel teardown - (File: outside.go)

### Summary
Nebula's `RecvError` message type is processed entirely outside the AEAD/Noise authentication path. Unlike every other message type (`Message`, `LightHouse`, `Test`, `CloseTunnel`, `Control`), which are only dispatched after `hostinfo.ConnectionState.Decrypt` succeeds (which validates the message counter against the anti-replay window in `Bits`), `RecvError` is handled immediately in `readOutsidePackets` before any decryption, signature, or nonce check occurs.

### Finding Description
In `readOutsidePackets`, the header is parsed and, for `header.RecvError`, the handler is invoked directly with no AEAD decryption and no replay-window check: [1](#0-0) 

`handleRecvError` looks up the hostinfo purely by the plaintext `RemoteIndex` carried in the (unencrypted, unsigned) header and only checks that the packet's source address matches the currently known remote address for that hostinfo: [2](#0-1) 

The `RemoteIndex` value is not secret — it is transmitted in cleartext in the header of every single packet for a session (`header.Encode(..., hostinfo.remoteIndexId, c)` in the send path), so any observer of a single packet on the wire learns the value needed to forge a `RecvError` for that session: [3](#0-2) 

Because there is no nonce, timestamp, or message-counter binding on `RecvError` (it is not encrypted/authenticated at all, unlike `CloseTunnel`, which travels through the same encrypted/replay-protected path as data messages), a captured or inferred `(RemoteIndex, source-address)` pair can be replayed indefinitely to repeatedly force `f.closeTunnel(hostinfo)` and `f.handshakeManager.DeleteHostInfo(hostinfo)`, tearing the tunnel down on demand. This is the same bug class as the reported `pauseDeposits` issue: an authorization/action-triggering message that lacks a nonce/freshness mechanism, so the same "signature" (here, a guessable index plus a spoofable source address rather than a cryptographic signature) can be reused to repeatedly disrupt a security-relevant state (the tunnel), rather than being a strictly one-time action.

### Impact Explanation
An attacker that can observe (or spoof from) the source UDP address of one side of an established tunnel — for example an on-path attacker, someone sharing the same NAT/carrier-grade NAT egress IP, or anyone who intercepts a single legitimate packet header — can force repeated teardown of that tunnel by replaying `RecvError` packets. This is a denial-of-service / repeated-disruption impact directly analogous to the "repeatedly pause the system" impact in the report: a security control (the guardian pause signature vs. here the internal error-recovery signal) can be re-triggered without needing the ongoing consent of, or fresh authorization from, the affected party.

### Likelihood Explanation
Exploitation requires: (1) obtaining a valid `RemoteIndex` for a target session — trivial, since it is cleartext in every packet header of that session and observable to any on-path/network observer or one that captures a single packet; and (2) sending from (or spoofing) the address the target believes is its current remote. UDP source-address spoofing is often feasible depending on network path (no return-routability check beyond source IP match), and on-path/NAT-sharing attackers do not need to spoof at all. Both `sendRecvErrorConfig`/`acceptRecvErrorConfig` (`ShouldRecvError`) provide some rate limiting, but do not add cryptographic freshness or a nonce, so replay across the rate-limit window remains possible.

### Recommendation
Do not act on `RecvError` signals from the cleartext, unauthenticated fast path. Either (a) remove the unauthenticated `RecvError` shortcut and require in-tunnel authenticated signaling for error recovery, or (b) bind `RecvError` to a fresh, single-use nonce/session-specific token (e.g., a value derived from the current message counter or handshake time) verified against a value that cannot be replayed, similar to how ordinary data-plane messages are bound to the anti-replay `Bits` window. At minimum, rate-limit and require that a `RecvError` correspond to an outbound packet actually sent very recently, and treat repeated events from a single peer/index as suspicious.

### Proof of Concept
Conceptual PoC (source/network-level, no valid certificate required):
1. Observe one packet exchanged between `A` and `B` on an established Nebula tunnel; extract `RemoteIndex` from its cleartext header (this is the local index `B` uses to identify the session with `A`), and note `A`'s UDP source address.
2. Craft a UDP packet to `A`'s address with `header.Type = header.RecvError`, `RemoteIndex` set to the value observed, and `MessageCounter = 0` (unauthenticated, unencrypted — see `sendRecvError` construction at [4](#0-3) ), sourced from (or spoofed as) `B`'s known address.
3. Send this crafted packet from a position that can reach `A` with a matching source address (on-path or spoofable network position). `A`'s `handleRecvError` will find the matching hostinfo by `RemoteIndex`, confirm the source address matches the currently known remote, and call `f.closeTunnel(hostinfo)`, tearing the tunnel down.
4. Repeat at will (subject only to internal rate limiting, not any cryptographic freshness check) to keep the tunnel from ever staying up.

**Note on confidence:** I was unable to fully inspect `sendRecvErrorConfig`/`acceptRecvErrorConfig` (`ShouldRecvError`) implementation details (found only in `interface.go`, whose relevant lines were not returned by search), so the exact rate-limiting behavior that might partially mitigate replay frequency is not fully verified here. Suggest a Devin session inspect `interface.go`'s `ShouldRecvError`/`recvErrorConfig` definitions directly to confirm whether any additional freshness constraints exist beyond simple rate limiting.

```go
func (f *Interface) handleRecvError(addr netip.AddrPort, h *header.H) {
	if !f.acceptRecvErrorConfig.ShouldRecvError(addr) {
		f.l.Debug("Recv error received, ignoring",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
		return
	}

	if f.l.Enabled(context.Background(), slog.LevelDebug) {
		f.l.Debug("Recv error received",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
	}

	hostinfo := f.hostMap.QueryReverseIndex(h.RemoteIndex)
	if hostinfo == nil {
		f.l.Debug("Did not find remote index in main hostmap", "remoteIndex", h.RemoteIndex)
		return
	}

	hr := hostinfo.GetRemote()
	if hr.IsValid() && hr != addr {
		f.l.Info("Someone spoofing recv_errors?",
			"addr", addr,
			"hostinfoRemote", hr,
		)
		return
	}

	f.closeTunnel(hostinfo)
	// We also delete it from pending hostmap to allow for fast reconnect.
	f.handshakeManager.DeleteHostInfo(hostinfo)
}
```
