## Title
Floating-Point Precision Manipulation in the On-Chain Bancor-Style Exchange Enables Value Extraction — (File: `chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java`)

### Summary
The MBUToken exploit (reported class: price manipulation) drained ~2.16M BUSD by exploiting a flawed balance/rate-accounting path that let an attacker force a swap contract to compute a token-exchange rate more favorable than the real one, letting it swap a manipulated balance for real, liquid funds in a single transaction. The strongest reachable analog in java-tron is the built-in TRC10/TRX Bancor-style "on-chain Exchange" (`ExchangeCreateContract` / `ExchangeInjectContract` / `ExchangeWithdrawContract` / `ExchangeTransactionContract`), whose default (non-hardened) rate calculation is performed with IEEE-754 `double` arithmetic and `Math.pow`, not exact integer/BigDecimal math, in `ExchangeProcessor`.

### Finding Description
`ExchangeTransactionActuator.execute()` is reachable by any signed transaction from any account — no special permission is required — and computes the counter-token amount via `ExchangeCapsule.transaction()`: [1](#0-0) 

`ExchangeCapsule.transaction()` selects the pricing engine based on `allowHarden()` (governed by the `AllowHardenExchangeCalculation` dynamic parameter, which is `0`/disabled unless a committee proposal enables it): [2](#0-1) 

When hardening is off (the historical/default behavior), pricing is computed by `ExchangeProcessor`, which uses `double` math and `Math.pow` for both legs of the Bancor formula: [3](#0-2) 

This is fundamentally the same bug class as the external report: a value-conversion/rate computation that trusts an imprecise (here, floating-point) calculation instead of an exact one. Just as the MBUToken vault miscomputed the amount of MBU/BUSD credited on deposit/swap and let the attacker walk away with mismatched value, `ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply` can, for adversarially chosen `sellTokenQuant`/pool-balance combinations, round in the trader's favor due to `double` truncation (`(long) issuedSupply`, `(long) exchangeBalance`), letting a caller extract more of the counter-asset than the true continuous Bancor curve would yield. Because `ExchangeTransactionActuator` allows arbitrary, repeated single-transaction calls with attacker-chosen `tokenQuant`, an attacker can probe/repeat trades that hit favorable rounding boundaries to drain the pool's TRX/TRC10 reserves, mirroring the single-transaction AMM drain pattern in the report. The project's own introduction of a `SafeExchangeProcessor` using `BigDecimal`/`RoundingMode.HALF_UP` and `hardenedCalc` overflow/negative-balance guards (only used when `AllowHardenExchangeCalculation` is enabled) is itself evidence that the legacy double-based path was recognized as numerically unsafe: [4](#0-3) 

### Impact Explanation
If exploitable, an attacker could repeatedly call `ExchangeTransactionContract` against a TRX/TRC10 exchange pool, extracting more counter-token/TRX value per trade than the pool should mathematically yield, permanently draining real, backed TRX/TRC10 balances from the pool's creator and other liquidity participants — a direct unbacked-balance/theft-of-funds condition reachable by any unprivileged broadcaster of a signed transaction.

### Likelihood Explanation
The `ExchangeTransactionContract` path requires no special privilege — any funded account can create the pool interaction and immediately submit trades with attacker-chosen `tokenQuant`. The double-precision Bancor computation is the historical default (hardening off), so any exchange pool created before hardening is enabled, or on any network/private chain that has not turned on `AllowHardenExchangeCalculation`, is exposed. Actual exploitability of a specific profitable rounding sequence would require careful selection of pool balances/trade sizes (similar to how the MBUToken attacker had to identify the specific flawed function/parameters), but the fundamental numerical-precision defect is present in shipped code and reachable via one signed transaction type.

### Recommendation
Make hardened (BigDecimal, `RoundingMode.HALF_UP`/exact) exchange math the mandatory calculation path for `ExchangeTransactionActuator`/`ExchangeInjectActuator`/`ExchangeWithdrawActuator` rather than an opt-in dynamic parameter, or add strict invariant checks (e.g., verify `buyTokenQuant` computed via double math never exceeds the exact BigDecimal-computed upper bound) before mutating account/exchange balances in `ExchangeCapsule.transaction()`.

### Proof of Concept
Not independently reproduced; conceptual PoC based on the shared bug class:
1. Create/observe an on-chain `Exchange` pool with `AllowHardenExchangeCalculation` disabled (default).
2. Repeatedly submit `ExchangeTransactionContract` trades (`ExchangeTransactionActuator.execute`) with `tokenQuant` values chosen to exploit `double`/`Math.pow` rounding in `ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply`.
3. Each favorable-rounding trade extracts a small excess of the counter-token/TRX; repeating across many transactions drains the pool analogous to the single-swap drain in the MBUToken report.

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  private BigDecimal exchangeToSupply(long balance, long quant) {
    long newBalance = StrictMathWrapper.addExact(balance, quant);
    BigDecimal bdQuant = BigDecimal.valueOf(quant);
    BigDecimal bdNewBalance = BigDecimal.valueOf(newBalance);
    BigDecimal base = BigDecimal.ONE.add(
        bdQuant.divide(bdNewBalance, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 0.0005);
    return SUPPLY.negate().multiply(
        BigDecimal.ONE.subtract(BigDecimal.valueOf(powResult))).setScale(0, RoundingMode.DOWN);
  }

  private long exchangeFromSupply(long balance, BigDecimal supplyQuant) {
    BigDecimal bdBalance = BigDecimal.valueOf(balance);
    BigDecimal base = BigDecimal.ONE.add(
        supplyQuant.divide(SUPPLY, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 2000.0);
    BigDecimal exchangeBalance = bdBalance.multiply(
        BigDecimal.valueOf(powResult).subtract(BigDecimal.ONE));
    return exchangeBalance.setScale(0, RoundingMode.DOWN).longValueExact();
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    BigDecimal relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
