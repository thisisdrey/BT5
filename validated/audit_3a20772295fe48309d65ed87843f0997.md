## Title
Shell-injection via unescaped single-quote wrapping of `patch_args` in `patch()` - (File: tools/build_defs/repo/utils.bzl)

### Summary
`tools/build_defs/repo/utils.bzl`'s `patch()` helper — used by `http_archive`, `git_repository`, and any module-extension-generated repository rule that falls back to the external `patch` tool — builds a shell command line by wrapping each `patch_args` element in single quotes with a bare `"'%s'" % arg` format, exactly the class of insufficient shell-metacharacter handling described in CVE-2026-41526's `KShell::quoteArgs`. If any `patch_args` string itself contains a single quote, the quoting is broken and the remainder of the string is interpreted as shell syntax by the `bash -c` invocation that follows.

### Finding Description
In `patch()`: [1](#0-0) 
each local patch is applied by building:
```
command = "{patchtool} {patch_args} < {patchfile}".format(
    patchtool = patch_tool,
    patchfile = ctx.path(patchfile),
    patch_args = " ".join(["'%s'" % arg for arg in patch_args]),
)
st = ctx.execute([bash_exe, "-c", command], working_directory = patch_directory or "")
```
The quoting function only wraps each argument in single quotes; it performs no escaping of embedded single quotes (unlike a correct implementation that would replace `'` with `'\''`). This is the identical bug class as the KDE advisory: a quoting routine intended to make attacker-influenced strings shell-safe fails to handle the quote metacharacter itself, allowing an escape from the intended argument boundary into shell command context.

This code path is reached whenever `native_patch` is false (i.e., `patch_tool` is explicitly set, or `patch_args` contains any argument other than a bare `-p<N>`), which is the exact condition documented in the `patch_args` attribute docs: "If arguments other than `-p` are specified, Bazel will fall back to use patch command line tool instead of the Bazel-native patch implementation" [2](#0-1) , confirming that a non-`-p` valued `patch_args` entry deterministically routes execution into the vulnerable `bash -c` string-building path rather than the native, shell-free `ctx.patch()` call at [3](#0-2) .

`patch_args` is read from `ctx.attr.patch_args` [4](#0-3)  — an attribute of the repository rule invocation. Under Bzlmod, module extensions evaluated across the full dependency graph incorporate tag values contributed by every module that uses the extension (not just the root module); a module extension shared with the root module can forward tag-supplied strings from a non-root, attacker-published module version directly into a generated repository rule's `patch_args` (or `patch_tool`) list. Because the extension's own implementation is not attacker-controlled Starlark under the rules of this scan (it is fixed, in-scope code), but the *tag values themselves* originate from an attacker-published module's `MODULE.bazel`, a crafted `patch_args` string containing a single quote followed by shell metacharacters breaks out of the intended argument and executes arbitrary commands during repository fetch/patch, before any build target of the malicious module is ever built.

### Impact Explanation
Successful exploitation results in arbitrary command execution in the context of the Bazel client process during repository setup (fetch/patch phase) — i.e., a write/execute outside the sandboxed repository content, executed with the privileges of the user running `bazel build`/`bazel fetch`. This is a full build-time RCE, matching the "escape from intended containment" impact class analogous to the KDE advisory's terminal-injection escape.

### Likelihood Explanation
Requires that (a) some in-scope module extension forwards externally-supplied tag data into a `patch_args`/`patch_tool` value used by `http_archive`/`git_repository`-style rules that call `patch()`, and (b) that `patch_args` contains at least one non-`-p` value so the vulnerable shell-based branch (rather than native `ctx.patch()`) executes. This is a plausible but not universal configuration, since the default/native patch path avoids the shell entirely; likelihood is moderate and depends on downstream extension design, consistent with the Medium severity and `AC:H`/`UI:R`-like conditions of the source advisory.

### Recommendation
Replace the naive `"'%s'" % arg` quoting in `tools/build_defs/repo/utils.bzl`'s `patch()` with proper POSIX shell quoting that escapes embedded single quotes (e.g., `"'" + arg.replace("'", "'\\''") + "'"`), or avoid string-interpolated shell commands altogether by invoking the patch tool via an argv list (`ctx.execute([patch_tool] + patch_args + ...)` with input redirection handled without a shell) so that `patch_args` values can never be interpreted as shell syntax regardless of content.

### Proof of Concept
1. Define (or have an attacker-controlled module extension forward) a repository rule invocation with:
   - `patch_tool = "patch"` (or any explicit tool) and
   - `patch_args = ["-p1'; touch /tmp/pwned; '"]`
2. Provide at least one entry in `patches` so the local-patch loop executes.
3. Because `patch_args` contains a value other than a bare `-p<N>`, `_use_native_patch` returns false, routing execution to:
   ```
   command = "patch '-p1'; touch /tmp/pwned; '' < <patchfile>"
   ctx.execute([bash_exe, "-c", command], ...)
   ```
   which executes `touch /tmp/pwned` as an independent shell statement.
4. A JUnit/`src/test/shell/bazel` test can assert that after invoking a repository rule with the crafted `patch_args`, the side-effect file (`/tmp/pwned` or an equivalent marker inside the test's `$TEST_TMPDIR`) exists, proving command injection outside the intended patch invocation.
