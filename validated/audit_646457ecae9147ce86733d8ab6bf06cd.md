### Title
`ReliabilityReport::score()` is monotonically increasing in request count regardless of success rate, letting an always-answering-but-non-delivering peer permanently out-rank honest peers - ([File: stackslib/src/net/atlas/download.rs])

### Summary
`ReliabilityReport::score()` computes `success*1000/(n*1000) + n`, which reduces to `floor(success/n) + n`. Since `floor(success/n)` is capped at `1` (only when `success == n`) and `0` otherwise, the score is dominated entirely by `n = total_requests_sent`. Consequently, a peer that answers `AttachmentsInventoryRequest`s (bumping `total_requests_sent`/`total_requests_success` via `bump_successful_requests`) but always fails to deliver the actual `AttachmentRequest` (bumping only `total_requests_sent` via `bump_failed_requests`) still sees its score increase with every single interaction, honest or dishonest, because `n` grows unconditionally.

### Finding Description
`get_prioritized_attachments_inventory_requests` and `AttachmentRequest::get_most_reliable_source`/`Ord` both rank peers purely by `ReliabilityReport::cmp`, which is `score().cmp(...)` [1](#0-0) [2](#0-1) .

The score formula is:
```
score() = total_requests_success * 1000 / (total_requests_sent * 1000) + total_requests_sent
``` [3](#0-2) 

Because this is integer arithmetic, `success*1000/(n*1000)` is exactly `floor(success/n)`, which is `1` only when `success == n` and `0` in every other case (since `success <= n` always, enforced by `bump_successful_requests`/`bump_failed_requests` at [4](#0-3) ). So in practice:
- `score() == n + 1` while the peer is 100% successful.
- `score() == n` the moment even a single request fails, and it keeps climbing with every subsequent request, success or failure.

This means an adversarial peer's score is monotonically non-decreasing with the number of times it is contacted, independent of whether it ever actually serves an attachment. The attacker only needs to:
1. Register as an outbound sync peer with a data URL (`network.get_data_url`), which any peer can legitimately do.
2. Always answer `AttachmentsInventoryRequest` with a well-formed, decodable bit-vector claiming full availability (`[1;8]`), so `extend_with_inventories` takes the success branch and calls `report.bump_successful_requests()` [5](#0-4) .
3. Never actually deliver on `AttachmentRequest` (return `None`/404/garbage), which routes through `extend_with_attachments`'s failure branch and calls `report.bump_failed_requests()` [6](#0-5) .

Each round-trip - success or failure - increments `n`, and the score formula never actually penalizes the attacker relative to `n`'s growth. An honest peer that is contacted less frequently (e.g., because there are multiple candidate peers and requests are batched/limited by `max_inflight_attachments`) will have a lower `n` and thus a lower score even at 100% success, so `get_most_reliable_source` and the `BinaryHeap` orderings in `get_prioritized_attachments_inventory_requests`/`get_prioritized_attachments_requests` will systematically prefer the attacker peer as `n` accumulates over successive retries and batches (the reports persist across batches in `AttachmentsDownloader::reliability_reports` [7](#0-6) [8](#0-7) ).

No existing guard corrects this: there is no cap, decay, or success-ratio-weighted term that would down-rank a peer whose failure count is growing; the design intent (rank by reliability) is broken by the integer-division truncation collapsing the success-rate term to at most `1`.

### Impact Explanation
This does not allow content forgery: the downloaded `Attachment`'s hash is recomputed from actual content and matched against `content_hash` via `find_all_attachment_instances`/`resolve_attachment` [9](#0-8) , so an attacker cannot cause wrong data to be accepted as canonical without a hash preimage. The impact is instead resolution starvation/degradation: because peer selection is driven by a scoring function that rewards mere request volume over success, a lying/non-delivering peer's score climbs indefinitely and out-competes genuinely reliable peers in both the inventory phase and the `AttachmentRequest::get_most_reliable_source` selection used to pick which peer's URL actually gets the download HTTP request. This causes legitimately committed, on-chain-referenced attachments to be repeatedly (and, per the retry/backoff bound `max_attachment_retry_count`, eventually permanently) unresolved because retries are wasted on the attacker peer instead of being directed at an honest peer that could actually serve the content - matching the "bounded compute DoS on a read endpoint" / degraded BNS resolution category.

### Likelihood Explanation
Preconditions are minimal and match the unprivileged remote-attacker model: the attacker only needs to be an ordinary outbound sync peer with a registered data URL - a normal, unprivileged P2P handshake capability, no secret or admin role required. The attack is fully repeatable across every attachment batch cycle and costs the attacker only cheap, well-formed HTTP responses to `/v2/attachments/inv` (never needing to actually possess the paginated data).

### Recommendation
Fix `ReliabilityReport::score()` so that failure count actually penalizes the score instead of unconditionally increasing it, e.g., weight the score by success ratio scaled to a fixed range (such as `(success * SCALE) / n` alone, without adding raw `n`), or require a minimum number of successful `AttachmentRequest` (not just inventory) completions before a peer's score can exceed peers with fewer but fully successful downloads. Consider tracking inventory-claim accuracy separately from attachment-delivery success, since currently both feed the same counter and an inventory "success" (well-formed but false-content bitvector) inflates the same score used to select download sources.

### Proof of Concept
Add a unit test in `stackslib/src/net/atlas/tests.rs` (or a standalone `#[test]`) directly on `ReliabilityReport`:
```rust
#[test]
fn test_reliability_score_favors_liar_over_honest_peer() {
    // Honest peer: 2 requests, both successful
    let mut honest = ReliabilityReport::empty();
    honest.bump_successful_requests();
    honest.bump_successful_requests();

    // Lying peer: 1 successful inventory response, then 5 failed attachment downloads
    let mut liar = ReliabilityReport::empty();
    liar.bump_successful_requests(); // inventory "success" (claims data it doesn't have)
    for _ in 0..5 {
        liar.bump_failed_requests(); // never actually delivers
    }

    // BUG: the liar, despite a 1/6 success ratio, outranks the honest peer with a 2/2 ratio
    assert!(liar.score() > honest.score(), "expected liar.score()={} > honest.score()={}", liar.score(), honest.score());
}
```
This demonstrates that `AttachmentRequest::get_most_reliable_source` (which does `sources.iter().max_by_key(|(_, v)| v.score())` [10](#0-9) ) and the `BinaryHeap<AttachmentsInventoryRequest>`/`BinaryHeap<AttachmentRequest>` orderings will select the non-delivering peer over the fully reliable one, causing batch convergence to stall on attachments only the honest peer can actually serve.
