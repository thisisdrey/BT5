### Title
StackerDB chunk signatures omit the contract/DB identity from the signed digest, enabling cross-StackerDB signature replay - (File: libstackerdb/src/libstackerdb.rs)

### Summary
`SlotMetadata::auth_digest()` (and therefore `StackerDBChunkData::sign`/`verify`) commits only to `slot_id`, `slot_version`, and `data_hash`. It never includes the smart-contract identifier (`QualifiedContractIdentifier`) of the specific StackerDB the chunk belongs to — the direct analog of the Solana report's missing `bump`/incomplete seed phrase, which let a signature/PDA validate in a context other than the one it was meant for.

### Finding Description
`SlotMetadata::auth_digest` hashes `slot_id || slot_version || data_hash` only: [1](#0-0) 

`verify()` then only checks that the recovered pubkey hash equals the expected principal for *that* slot in *that* DB — it has no way to distinguish which contract the signature was produced for, because the contract was never hashed into the digest: [4](#0-3) 

Slot ownership is validated per-contract via `get_slot_signer`/`get_slot_validation`, but the *actual authorization check* (`slot_desc.verify(&slot_validation.signer)`) only proves "some address that matches the local slot-signer record produced this exact `(slot_id, slot_version, data_hash)` tuple" — not "this signature was produced specifically for StackerDB X": [5](#0-4) 

Crucially, the signer-node client reuses the *same* numeric `SignerSlotID` across every `.signers-N-M` StackerDB contract for a given signer in a reward cycle, and only switches the underlying `StackerDBSession`/contract per message type: [3](#0-2) 

Because slot assignment is per-signer-index (not per-contract) and identical numeric slot IDs are used across contracts belonging to the same reward cycle/signer set, a chunk signed by signer S for slot K in contract `signer-0-1` (e.g. a `BlockResponse`) is bit-for-bit indistinguishable, at the signature-verification layer, from a legitimately-signed chunk for slot K, same version, same data, in a *different* contract `signer-0-2` (e.g. a different message lane) where S also owns slot K. Any node that stores/relays chunks (`try_replace_chunk`, `validate_received_chunk`, `handle_unsolicited_StackerDBPushChunk`) will accept and forward such a chunk into the wrong contract/lane as long as slot ownership, version freshness, and max-writes checks pass for that target contract — none of which depend on contract identity being part of the signed material. [6](#0-5) [7](#0-6) 

This is the direct structural analog of the Solana finding: the signed/committed material (seeds in Solana, the auth digest here) is missing a component that should uniquely bind the authorization to its intended context (the bump in Solana, the contract identifier here), allowing a validly-signed artifact to be accepted where it was never authorized.

### Impact Explanation
An attacker who observes a validly-signed StackerDB chunk from a signer (chunks are broadcast/relayed in the clear over the p2p network and are also fetched via public `/v2/stackerdb/...` HTTP endpoints) can replay it into any other StackerDB contract where that same signer happens to own the same numeric slot and where the target contract's current slot version and data-hash requirements are met. Depending on how the consuming code (`StackerEvent`/`SignerMessage` deserialization in `libsigner/src/events.rs`) interprets payload bytes for a given lane/message-id, this can result in a forged/misattributed signer message being propagated network-wide as authentic for a lane the signer never intended it for — a form of forged-data propagation / message-type confusion caused by an authentication gap, matching the "network-wide propagation of forged data" impact bucket.

### Likelihood Explanation
Exploitation requires: (1) the attacker to observe one legitimately-signed chunk (trivial — StackerDB chunks are broadcast and independently queryable over unauthenticated HTTP GET), and (2) the same signer to own the same slot index in two different StackerDB contracts within scope, and (3) the target contract's freshness/version/max-writes gate to currently accept that exact `(slot_id, slot_version, data_hash)` triple. Condition (2) depends on how slot assignment across `.signers-N-M` contracts is computed in the reward-set/boot-contract logic, which I could not fully verify from the accessible code (the assignment algorithm itself lives outside what I was able to inspect in the time available); I can confirm the client reuses one `SignerSlotID` per signer across sessions/contracts, but I could not conclusively confirm from the available files whether the *server-side* per-contract slot-to-signer mapping is guaranteed to differ across message lanes for a given signer. This uncertainty affects likelihood, not the root-cause finding (the missing contract binding in `auth_digest` is confirmed and unambiguous).

### Recommendation
Bind the StackerDB's contract identifier (and ideally the reward-cycle/signer-set context) into the signed digest in `SlotMetadata::auth_digest`, e.g. hash `smart_contract_id.serialize() || slot_id || slot_version || data_hash`, and thread the contract identifier through `sign()`/`verify()` call sites (`StackerDBChunkData::sign/verify/get_slot_metadata`, `try_replace_chunk`, `validate_received_chunk`) so a signature can only ever validate for the specific StackerDB it was produced for.

### Proof of Concept
Not independently reproduced end-to-end (would require standing up two `.signers-N-M` StackerDB contracts sharing a signer/slot assignment and confirming cross-acceptance); the root-cause code path (missing contract binding in `auth_digest`) is directly demonstrated via the cited `libstackerdb/src/libstackerdb.rs` lines and the existing unit test `test_stackerdb_slot_metadata_sign_verify`, which shows `verify()` only fails on `slot_id`, `slot_version`, or `data_hash` mismatches — never on contract mismatch, since the contract is not part of the signed material: [8](#0-7)

    fn auth_digest(&self) -> Sha512Trunc256Sum {
        let mut hasher = Sha512_256::new();
        hasher.update(self.slot_id.to_be_bytes());

        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )
