## Title
Weight double-counting in `ValidateMultiSign` precompile via duplicate/malleable signatures allows multisig threshold bypass - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `ValidateMultiSign` TVM precompile, reachable by any smart contract via a `TriggerSmartContract` call from an unprivileged sender, is supposed to prove that signatures from distinct authorized keys collectively meet a permission's weight threshold. Its duplicate-detection logic only rejects a signature if the *exact same signature bytes* were already counted for an address that already contributed weight; it does not prevent the *same recovered address* from contributing weight more than once when a different (but still validly-recovering) signature blob is supplied for that address. This mirrors the reported CSRF flaw's root cause: a security check comparing two attacker-controlled values for exact byte equality instead of verifying the underlying authorization is actually distinct/fresh, letting an attacker satisfy the check by crafting inputs that differ trivially but represent the same authority.

### Finding Description
In `execute()`: [1](#0-0) 

For each signature in the caller-supplied array:
1. `recoveredAddr` is derived from the raw signature bytes and the fixed message hash.
2. `sign` becomes `merge(recoveredAddr, sign)`.
3. If `executedSignList` already contains `recoveredAddr`:
   - if it also contains this exact `sign` blob, the iteration is skipped (`continue`), correctly rejecting a literal re-submission of the identical signature.
   - **otherwise** (same address, but a byte-different valid signature), the code only calls `MUtil.checkCPUTime()` — a CPU/DoS accounting guard — and then falls straight through to add `weight` for that address **again** into `totalWeight`.

Because ECDSA signing is non-deterministic (or, even with deterministic nonces, is trivially malleable via the `s → n-s` transform), a holder of a single private key can produce two (or more, up to `MAX_SIZE`) byte-distinct valid signatures over the same hash that both recover to the same address. Each such signature is treated by the loop as if it came from a different authorized key, and its `weight` is added to `totalWeight` every time, up to `MAX_SIZE` times.

This directly undermines the multisig weight-threshold guarantee that `Permission`/`checkWeight` semantics are supposed to enforce elsewhere in the codebase — contrast with `TransactionCapsule.checkWeight`, which explicitly de-duplicates by **recovered address** (via `addMap` keyed by the encoded address, post fork `VERSION_4_7_1`) and throws `PermissionException("... has signed twice!")`: [2](#0-1) 

The precompile does not apply the same "one weight contribution per address" invariant; it applies it only per unique signature-byte blob.

### Impact Explanation
`ValidateMultiSign` (and its sibling `BatchValidateSign`) is a general-purpose TVM precompile at a fixed address, invocable by any deployed contract in response to any account's transaction. Wallet contracts, exchanges, DAOs, or custody contracts built on TRON that rely on this precompile to gate privileged operations (fund transfers, ownership changes, order execution) behind an on-chain multisig weight check can be tricked into believing the threshold has been met when in fact only a single (or fewer than required) actual keys signed. An attacker controlling a single low-weight key in a permission can forge two or more distinct-but-equivalent signatures for that one key and drive `totalWeight` above `permission.getThreshold()`, causing the precompile to return `dataOne()` (success) even though the real signer set does not meet policy. This is a concrete authorization bypass that can lead to unauthorized account/contract operations and theft of funds in any downstream contract trusting this check — squarely within the "unauthorized account operation / theft of funds" impact class.

### Likelihood Explanation
The bug is reachable by a single unprivileged party: any contract deployer can write a contract that calls this precompile, and any transaction sender can trigger it, with no special privileges, node access, or consensus role required. Producing two distinct valid signatures from one private key over the same hash is trivial (either by re-signing with fresh randomness, or applying the well-known ECDSA `s`/`n-s` malleability transform). The vulnerable code path is exercised on every call with `signatures.length > 1`, which is unauthenticated user-controlled input entirely.

### Recommendation
Change the duplicate/anti-replay check in `ValidateMultiSign` (and audit `BatchValidateSign` similarly) to de-duplicate strictly by **recovered address**, not by the raw signature bytes, so a second signature for the same address is never allowed to add weight again — mirroring `TransactionCapsule.checkWeight`'s `addMap`-keyed-by-address approach: [3](#0-2) 

### Proof of Concept
1. Create an account with an `Active` permission containing key `K` with `weight = W < threshold`, and no other keys.
2. Sign the message hash (`sha256(address ‖ permissionId ‖ data)`) twice with `K`'s private key, producing two byte-distinct valid signatures `sig1` and `sig2` that both recover to `K`'s address (via normal re-signing or the `s → n-s` malleability transform on one signature).
3. Deploy/invoke a contract that calls the `ValidateMultiSign` precompile with `signatures = [sig1, sig2]`.
4. In the precompile loop, `recoveredAddr` for both entries equals `K`'s address; for the second entry, `executedSignList` contains `recoveredAddr` but not the differing `sign` blob, so it falls through and adds `weight` a second time, producing `totalWeight = 2W`.
5. If `2W >= threshold` while `W < threshold`, the precompile returns `dataOne()` (success), even though only one authorized key actually signed — demonstrating the multisig threshold bypass. [4](#0-3)
