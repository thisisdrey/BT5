## Title
`ProxyType::NonTransfer` fails to filter `pallet_asset_conversion` calls, allowing a proxy delegate to redirect a proxied account's assets to itself via `add_liquidity` (and `remove_liquidity`/swaps) - (File: `cumulus/parachains/runtimes/assets/asset-hub-westend/src/lib.rs`, `cumulus/parachains/runtimes/assets/asset-hub-rococo/src/lib.rs`, `substrate/frame/asset-conversion/src/lib.rs`)

## Summary
`Pallet::add_liquidity` transfers `amount1`/`amount2` out of the signed origin's account into the pool and mints LP tokens to a fully caller-controlled `mint_to` account, with no check that `mint_to == who`, as confirmed at `substrate/frame/asset-conversion/src/lib.rs` lines 855-879 and 468-490. The `ProxyType::NonTransfer` filter in both `asset-hub-westend` and `asset-hub-rococo` excludes `Balances`, `Assets`, `NftFractionalization`, `Nfts`, and `Uniques` calls, but does not exclude `RuntimeCall::AssetConversion`, confirmed by inspecting the `matches!` blocks at `cumulus/parachains/runtimes/assets/asset-hub-westend/src/lib.rs` lines 834-849 and `cumulus/parachains/runtimes/assets/asset-hub-rococo/src/lib.rs` lines 616-623, and by a repo-wide grep showing no `RuntimeCall::AssetConversion` reference in either runtime's proxy filter logic.

## Finding Description
`add_liquidity` calls `ensure_signed(origin)` to get `sender`, then calls `do_add_liquidity(&sender, ..., &mint_to)`, which transfers `amount1`/`amount2` from `who` (`sender`) to the pool account and mints LP tokens directly to the caller-supplied `mint_to` (`substrate/frame/asset-conversion/src/lib.rs` lines 468-490, 855-879). Similarly, `do_remove_liquidity` burns LP tokens from `who` and transfers pooled assets to a caller-supplied `withdraw_to` (lines 895-965). Neither function checks that the beneficiary equals the paying signer, which is safe for ordinary signed extrinsics where the signer chooses their own counterparties, but breaks under `pallet_proxy` composition: the delegator remains the dispatch origin (and thus the party whose funds are moved), while the delegate fully controls the call arguments including `mint_to`/`withdraw_to`. Because `ProxyType::NonTransfer`'s exclusion list in both runtimes only names `Balances`, `Assets`, `NftFractionalization`, `Nfts`, and `Uniques` (and, in asset-hub-westend, also `Scheduler`, `Treasury`, `Vesting::vested_transfer`, `ConvictionVoting`, `Referenda`, `Whitelist`), `RuntimeCall::AssetConversion` calls pass the `NonTransfer` filter unblocked, allowing a delegate to move a delegator's funds through the pool despite holding a proxy type explicitly documented as "Can execute any call that does not transfer funds or assets."

## Impact Explanation
A delegate holding only a `NonTransfer` proxy over a victim account can call `AssetConversion::add_liquidity` with `mint_to` set to their own account, pulling the victim's assets into a pool and minting the resulting LP-token claim to themselves with no proxy required for the follow-up step; the delegate can then call `AssetConversion::remove_liquidity` (or use swap functions with `send_to` set to themselves) under their own signed origin to redeem the pooled value, completing a full unauthorized transfer of the victim's assets to the delegate. This matches the "theft of user funds"/"wrongful beneficiary" impact category under the Polkadot SDK impact gate, since asset custody is not conserved and value settles to an account the delegator never authorized.

## Likelihood Explanation
Exploitation requires only an unprivileged, existing (or attacker-obtained) `NonTransfer` proxy relationship — a common, low-trust delegation pattern intended specifically to disallow value movement — and an existing (or attacker-creatable, since `create_pool` is likewise unfiltered) liquidity pool for assets the victim holds. No governance, validator, or infrastructure compromise is needed; the attack is fully reachable via public extrinsics (`Proxy::proxy` wrapping `AssetConversion::add_liquidity`, followed by `AssetConversion::remove_liquidity`) that any delegate holding this specific proxy grant can call.

## Recommendation
Add `RuntimeCall::AssetConversion { .. }` to the exclusion list matched against in `ProxyType::NonTransfer`'s filter in both `cumulus/parachains/runtimes/assets/asset-hub-westend/src/lib.rs` and `cumulus/parachains/runtimes/assets/asset-hub-rococo/src/lib.rs` (and any other runtime including `pallet_asset_conversion` with an analogous `NonTransfer` filter), or alternatively enforce at the pallet level in `substrate/frame/asset-conversion/src/lib.rs` that `mint_to`/`withdraw_to`/`send_to` equal the signed origin unless explicitly authorized otherwise.

## Proof of Concept
1. Victim `V` grants delegate `D` a `Proxy::add_proxy` of `ProxyType::NonTransfer`.
2. A liquidity pool for `(Native, AssetX)` exists and `V` holds balances of both (or `D` calls the unfiltered `AssetConversion::create_pool` first via the same proxy).
3. `D` submits `Proxy::proxy(real: V, force_proxy_type: Some(NonTransfer), call: AssetConversion::add_liquidity(Native, AssetX, amount1, amount2, 0, 0, mint_to: D))`. The `NonTransfer` filter's `matches!` check does not match `RuntimeCall::AssetConversion`, so `filter()` returns `true` and the call proceeds; inside, `ensure_signed(origin) == V`, so `V`'s tokens move to the pool account while LP tokens mint to `D`.
4. `D`, using their own signed origin (no proxy needed), calls `AssetConversion::remove_liquidity(Native, AssetX, lp_token_burn, 0, 0, withdraw_to: D)`, redeeming the pooled assets to themselves.
5. Result: `V`'s assets have moved to `D` despite `V` only ever granting a `NonTransfer` proxy, verifiable via a unit test asserting `ProxyType::NonTransfer.filter(&RuntimeCall::AssetConversion(pallet_asset_conversion::Call::add_liquidity { .. }))` returns `true` in the affected runtimes.
