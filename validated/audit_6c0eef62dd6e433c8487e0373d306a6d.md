Confirmed. The vulnerability is in `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`, the `inner_rlp_execute` function combined with `address_check_callback`.

### Title
Repeatable relayer-fee extraction via unconditional fee payment on a nonce-preserving faulty-relayer path - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
In the eth-implicit `WalletContract::rlp_execute` flow, `inner_rlp_execute()` fires the relayer's `fee` refund promise unconditionally as soon as parsing succeeds, *before* it is known whether the transaction will ultimately succeed. For the `EOABaseTokenTransfer { address_check: Some(_), .. }` branch, the code deliberately does *not* increment the wallet's nonce (deferring that decision to `address_check_callback`), specifically so that an "honest relayer" can retry after a registrar-lookup failure. But the `fee` payment to the relayer/predecessor is not deferred along with the nonce — it is sent out regardless of which path is later taken.

### Finding Description
`inner_rlp_execute` (`runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs:347-385`) processes the parsed transaction in two independent steps that should be tied together but aren't:

1. Nonce increment is conditionally skipped only for `EOABaseTokenTransfer { address_check: Some(_), .. }`: [1](#0-0) 

2. The `fee` refund promise to `context.predecessor_account_id` (the relayer) is created unconditionally whenever `fee` is non-zero, for *both* `EOABaseTokenTransfer` and `ERC20Transfer`, with no check for whether the address-check path was taken: [2](#0-1) 

When `address_check: Some(address)` is set, execution proceeds to an address-registrar lookup and `address_check_callback` (`runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs:134-192`). If the registrar reports the address *does* correspond to an existing named account, the callback explicitly does **not** increment the nonce (comment at lines 162-164) and either bans the relayer (only if the relayer used the wallet's own access key) or simply returns a failure `ExecuteResponse`: [3](#0-2) 

Since the nonce was never incremented, the exact same signed RLP transaction (same nonce) remains valid and can be resubmitted indefinitely — the whole point of the design, per the comment, is to let "an honest relayer... still be able to successfully send the user's intended transaction". However, the `fee` transfer promise created back in `inner_rlp_execute` already fired and paid the relayer *before* this outcome was known, and it fires again on every resubmission. Unlike `caller_deposit`, which is refunded on failure inside `rlp_execute_callback` (`:296-317`), there is no corresponding refund/clawback of `fee` when the address-check path fails. A relayer without the wallet's access key (so it is never banned, per `rlp_execute` logic at `:121-125` requiring `env::signer_account_id() == current_account_id`) can therefore repeatedly resubmit the identical signed transaction targeting an address that is registered to a named account, collecting `fee` every single time while the underlying action never completes and the nonce never advances to block the replay.

### Impact Explanation
This allows unlimited draining of the wallet contract's $NEAR balance via `fee` payments extracted from repeated resubmission of a single user-signed transaction that can never succeed (concrete theft of funds from the eth-implicit account). The nonce replay-protection mechanism, which is the sole guard against reusing a signed transaction, is intentionally bypassed for this exact branch, and the state-changing `fee` transfer is not gated behind that same protection.

### Likelihood Explanation
Any third-party relayer (no special privileges, no access key required — `predecessor_account_id` just needs to differ from `current_account_id`, per the `!fee.is_zero() && context.predecessor_account_id != context.current_account_id` check) can trigger this by relaying a transaction whose ABI-encoded action targets another wallet contract's address which is also registered as a named account in the address registrar, and simply resubmitting the same call in a loop. No cooperation from the user's signing key is needed beyond the original signature; the same signed bytes are reusable because the nonce is never advanced on this path.

### Recommendation
Do not send the `fee` refund promise until it is certain the transaction will not enter the nonce-preserving faulty-relayer branch: either move the fee-payment promise into the tail of the successful completion path (e.g., chain it after `address_check_callback` confirms `maybe_account_id.is_none()`), or make the fee payment itself refundable/reversible in the same way `caller_deposit` is refunded in `rlp_execute_callback` when the underlying action ultimately fails or is rejected.

### Proof of Concept
1. Deploy a `WalletContract` for user Alice's eth-implicit account with balance B.
2. Alice signs an Ethereum-style RLP transaction with `to` = an address that the relayer knows resolves (via the address registrar) to an existing named Near account, with a non-zero `max_fee_per_gas * gas_limit` (i.e., non-zero `fee`), and `target` set to another (non-existent as a name) eth-implicit account matching that address so `TargetKind::EthImplicit` triggers the `address_check: Some(address)` branch (`runtime/near-wallet-contract/implementation/wallet-contract/src/internal.rs:107-122`).
3. A malicious relayer (any account, without the wallet's access key) calls `rlp_execute(target, tx_bytes_b64)`.
4. `inner_rlp_execute` does not increment the nonce (line 358-365) but immediately schedules the `fee` transfer to the relayer (line 367-385).
5. `address_check_callback` looks up the registrar, finds `maybe_account_id.is_some()`, and since the relayer is not the wallet's own signer, simply returns a failure response without banning anyone and without incrementing the nonce (lines 161-173).
6. The relayer resubmits the identical `tx_bytes_b64`/`target` pair in step 3 repeatedly; each call re-triggers the unconditional `fee` payment in step 4, draining the wallet's balance in increments of `fee` with no bound, while the underlying transfer/action never executes.
