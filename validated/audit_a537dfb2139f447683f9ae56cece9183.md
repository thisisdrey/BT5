### Title
Silent constructor self-assignment bug drops the `ReceiveDescription` parameter in `ReceiveDescriptionCapsule` - ([File: framework/src/main/java/org/tron/core/capsule/ReceiveDescriptionCapsule.java])

### Summary
The audited Solidity bug is a class of defect where a decoded input parameter is never actually persisted into the object that represents on-chain state, silently discarding user-supplied data. The analogous defect in java-tron is in the `ReceiveDescriptionCapsule(final ReceiveDescription outputDescription)` constructor, which never assigns its `outputDescription` parameter to the object's backing field.

### Finding Description
The constructor is: [1](#0-0) 

```java
public ReceiveDescriptionCapsule(final ReceiveDescription outputDescription) {
    this.receiveDescription = receiveDescription;
}
```

The parameter is named `outputDescription`, but the assignment references the bare identifier `receiveDescription`, which resolves to the (still-uninitialized, default-`null`) instance field `this.receiveDescription` rather than the constructor argument. This is the identical bug class described in the external report: a value that is decoded/passed into a constructor/actuator is never stored into the persisted object — here, the entire `ReceiveDescription` (containing the shielded-output note commitment, value commitment, ephemeral key, ciphertexts, and zk-proof) is silently discarded and replaced with `null`, instead of raising a compile error or being caught by review, because the code compiles cleanly (self-assignment of a field to itself).

Any caller of this one-argument constructor overload ends up with a `ReceiveDescriptionCapsule` object whose internal `receiveDescription` is `null`; any subsequent call to `getInstance()`, `getData()`, or any of the specific getters (`getValueCommitment()`, `getEphemeralKey()`, `getEncCiphertext()`, etc.) will throw a `NullPointerException` because they all dereference `this.receiveDescription` directly: [2](#0-1) [3](#0-2) 

This capsule is used in the shielded-transfer transaction construction path (`ZenTransactionBuilder.java`, `ShieldedTRC20ParametersBuilder.java`), which are invoked from `Wallet`'s shielded transaction creation APIs (`createShieldedTransaction` / `createShieldedContractParameters` reachable via gRPC/HTTP), i.e. code paths triggered directly by an anonymous API client constructing a shielded (zk-SNARK) transfer.

### Impact Explanation
If the one-argument `ReceiveDescriptionCapsule(ReceiveDescription)` constructor is invoked anywhere along the shielded-transaction construction path, the resulting object holds a `null` `ReceiveDescription` instead of the caller-supplied one. Downstream consumption of this capsule (`getInstance()`, `getData()`, any getter) throws `NullPointerException`, which — depending on where it is caught — either aborts the specific shielded-transfer construction request (denial-of-service against that specific wallet/API request) or, if uncaught in a service thread, disrupts an API endpoint the node exposes for shielded transaction building. Because shielded outputs carry the note commitment and encrypted note data that determine spendability of shielded funds, silently losing this data (rather than an exception) would also risk producing malformed/incomplete shielded outputs, which is directly analogous in severity class to the original "metadata not stored" finding (loss of intended state).

### Likelihood Explanation
Likelihood depends on whether this specific single-argument overload is actually invoked from the production shielded-transaction-building code (`ZenTransactionBuilder`, `ShieldedTRC20ParametersBuilder`) as opposed to the other multi-argument overload also present in the class. I was not able to conclusively confirm, within the available tool budget, which overload is called at each of the two production call sites found via `grep_search` (each file contains exactly one `new ReceiveDescriptionCapsule(...)` call). If either of these call sites uses the broken single-argument constructor, the bug is trivially and deterministically reachable by any user who calls the shielded-transaction-creation API with valid note/output parameters — no privileged access is required.

### Recommendation
Fix the constructor to assign the parameter, not the field, to itself:
```java
public ReceiveDescriptionCapsule(final ReceiveDescription outputDescription) {
    this.receiveDescription = outputDescription;
}
```
Additionally, audit `ZenTransactionBuilder.java` and `ShieldedTRC20ParametersBuilder.java` to confirm whether this constructor overload is invoked in the shielded-transaction build path, and add a unit test asserting that `new ReceiveDescriptionCapsule(receiveDescription).getInstance()` equals the input, to prevent regression of this exact self-assignment defect.

### Proof of Concept
```java
ReceiveDescription rd = ReceiveDescription.newBuilder()
    .setNoteCommitment(ByteString.copyFromUtf8("cm"))
    .build();
ReceiveDescriptionCapsule capsule = new ReceiveDescriptionCapsule(rd);
capsule.getInstance(); // returns null instead of rd
capsule.getValueCommitment(); // throws NullPointerException, because this.receiveDescription is null
```
This demonstrates that the supplied `ReceiveDescription` is discarded, exactly mirroring the "metadata not being stored" root cause from the external report, applied to java-tron's shielded-transaction capsule construction code.
