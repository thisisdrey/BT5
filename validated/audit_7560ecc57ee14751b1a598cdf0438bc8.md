### Title
Griefing via dust `deposit(onBehalfOf)` fills a victim's token list to `MAX_TOKENS_PER_USER`, DoS-ing their deposits and debt issuance — (`contracts/Pool.sol:143-148`, `contracts/DepositToken.sol:211-237`)

### Summary
The reported bug class is "attacker front-runs a legitimate management action with a permissionless call that flips a lock/freeze flag, causing a permanent-ish DoS of the victim's ability to manage their position." The direct Metronome analog lives in `Pool.addToDepositTokensOfAccount` / `addToDebtTokensOfAccount`: both revert with `UserReachedMaxTokens` once an account's combined deposit + debt token count reaches `MAX_TOKENS_PER_USER`. Because `DepositToken.deposit` accepts an arbitrary `onBehalfOf_`, any EOA can dust-deposit every listed collateral type into a victim's account, filling the per-account list and permanently blocking the victim from depositing any new collateral type or issuing any new synth debt type. Front-running a victim's first deposit of a new token makes the victim's own transaction revert.

### Finding Description
`DepositToken.deposit(amount_, onBehalfOf_)` pulls `underlying` from the caller but mints `msdTOKEN` to `onBehalfOf_`, with no opt-in from the beneficiary (`DepositToken.sol:211-237`). Inside `_mint`, a first-time balance triggers `pool.addToDepositTokensOfAccount(account_)` (`DepositToken.sol:485-488`). That function is gated by `onlyIfAdditionWillNotReachMaxTokens`, which reverts when `debtTokensOfAccount.length(account_) + depositTokensOfAccount.length(account_) >= MAX_TOKENS_PER_USER` (`Pool.sol:143-148`, `Pool.sol:216-220`). Symmetrically, `DebtToken._mint` calls `addToDebtTokensOfAccount` on first borrow (`DebtToken.sol:597-600`), so debt positions count toward the same shared cap.

The attacker seeds the victim's `depositTokensOfAccount` list with 1-wei deposits of each listed `DepositToken`. Once the combined length hits `MAX_TOKENS_PER_USER`:

- Any `deposit()` minting a token the victim does not already hold reverts in `addToDepositTokensOfAccount`.
- Any `DebtToken.issue()` for a synth the victim has no debt in reverts in `addToDebtTokensOfAccount`.
- Plain `msdTOKEN` `transfer()`/`transferFrom()` to the victim also reverts, since `_transfer` calls `addToDepositTokensOfAccount` for first-time recipients (`DepositToken.sol:517-520`).

This mirrors the report: a permissionless call (`registerDerivative` there; `deposit(_, victim)` here) front-runs the victim and poisons a shared accounting list, causing the victim's subsequent management transaction to revert.

### Impact Explanation
Liveness violation / temporary freezing of funds. The victim cannot add new collateral types or open new debt positions while the list is saturated; inbound `msdTOKEN` transfers to them revert as well. Recovery requires burning a dust token balance down to exactly zero (via `withdraw` of the full balance of that token) to trigger `removeFromDepositTokensOfAccount`, but the attacker can re-grief cheaply by repeating the dust deposit, and each `withdraw` pays `withdrawFee`. In a busy mempool the attacker can persistently front-run the victim's freeing deposit, making the DoS effectively continuous. No solvency or fund-theft impact; impact is capped at freezing.

### Likelihood Explanation
Feasibility depends on the deployed token count: the attacker needs `MAX_TOKENS_PER_USER` distinct deposit/debt token entries, and `addDepositToken` itself caps listings at `MAX_TOKENS_PER_USER` (`Pool.sol:703`), so the attack is only fully saturating when the pool lists close to the cap — otherwise the victim's usable slots shrink proportionally to the listed token count but can still be exhausted. Cost is ~1 wei of each underlying plus gas per token; no privileged role, oracle, or flash loan is required. The `nonReentrant`, `whenNotPaused`, `onlyIfDepositTokenExists`, and `SynthContext._msgSender()` checks do not stop it because `deposit` is intentionally public and `onBehalfOf_` is unrestricted. Note: `deposit` pulls funds from the caller, so the attacker does spend (dust amounts of) real collateral.

### Recommendation
Do not count attacker-forced dust positions against the victim's cap, or make the cap per-token-list rather than combined. Options: add an opt-in/whitelist for `onBehalfOf_` deposits (or skip `addToDepositTokensOfAccount` when the deposit was not initiated by the beneficiary); enforce a minimum first-deposit amount (`minAmountToDeposit` / `debtFloorInUsd`-style floor for deposits) so filling the list costs meaningful capital; or allow any account to purge zero/dust entries from its own lists.

### Proof of Concept
Hardhat sketch against deployed Pool/DepositToken set:

```ts
// victim has 0 positions; attacker front-runs victim's first deposit
const depositTokens: DepositToken[] = await getListedDepositTokens(pool);

// Attacker: dust-deposit each listed collateral to victim
for (const dt of depositTokens) {
  const underlying = await ethers.getContractAt('IERC20', await dt.underlying());
  await underlying.connect(attacker).approve(dt.address, 1);
  await dt.connect(attacker).deposit(1, victim.address); // fills depositTokensOfAccount[victim]
}
// If list now >= MAX_TOKENS_PER_USER:
await expect(
  depositTokens[0].connect(victim).deposit(parseEther('10'), victim.address)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');

// First borrow of a new synth also reverts via addToDebtTokensOfAccount
await expect(
  msUsdDebtToken.connect(victim).issue(parseEther('1'), victim.address)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');

// Re-grief: after victim withdraws a dust token to free a slot, attacker re-deposits dust
```

Caveat: the revert only triggers once the combined per-account list reaches `MAX_TOKENS_PER_USER`; on deployments with few listed tokens the attack reduces the victim's usable slots but may not fully saturate the cap unless the attacker also holds debt entries — which cannot be pushed onto the victim (debt mints only to `_msgSender`). The deposit-side saturation alone is sufficient to block all *new* deposit token types and all transfers-in once reached.
