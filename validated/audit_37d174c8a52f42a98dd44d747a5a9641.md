## Title
Protocol fee bypass on NEP-245/IMT `TokenDiff` swaps via unit-sized delta chunking — (`contracts/defuse/core/src/intents/token_diff.rs`)

### Summary
`TokenDiff::token_fee` skips the protocol fee entirely for `Nep245` and `Imt` token deltas whenever the absolute delta is `≤ 1`. Because `TokenDiff::execute_intent` enforces no minimum trade size (only rejecting a `delta == 0`), any swap involving a NEP-245-wrapped or IMT token can be split into many unit-sized (`|delta| == 1`) `TokenDiff` intents and packed into a single `execute_intents`/`MultiPayload` batch, letting the fee be evaded on the full traded amount while the ledger still nets to zero. This breaks the "fees owed vs. fees collected" invariant independent of any deployer misconfiguration, since it holds for any nonzero configured fee.

### Finding Description
`TokenDiff::execute_intent` computes the protocol fee per-token-per-intent using `Self::token_fee`: [1](#0-0) 

```
let protocol_fee = engine.state.fee();
...
if *delta < 0 {
    let amount = delta.unsigned_abs();
    let fee = Self::token_fee(token_id, amount, protocol_fee).fee_ceil(amount);
    ...
}
```

`token_fee` special-cases NEP-245 multi-tokens and IMT tokens: [2](#0-1) 

```
pub fn token_fee(token_id: impl Into<TokenIdType>, amount: u128, fee: Pips) -> Pips {
    let token_id = token_id.into();
    match token_id {
        TokenIdType::Nep141 => {}
        TokenIdType::Nep245 | TokenIdType::Imt if amount > 1 => {}
        // do not take fees on NFTs and MTs with |delta| <= 1
        TokenIdType::Nep171 | TokenIdType::Nep245 | TokenIdType::Imt => return Pips::ZERO,
    }
    fee
}
```

The comment implies this exemption targets NFT-like single-unit transfers, but `Nep245TokenId`/`ImtTokenId` are used generically to represent arbitrary fungible balances bridged/wrapped across Defuse deployments (e.g. an NEP-141 balance wrapped into an NEP-245 token when transferred cross-contract): [3](#0-2) 

There is no minimum-amount enforcement anywhere in the intent execution path other than rejecting an exact-zero delta: [4](#0-3) 

Consequently, an attacker who wants to move a large NEP-245/IMT balance can decompose the trade into `N` separate `TokenDiff` intents, each with `delta == ±1` on the wrapped token, matched by a counter-intent (potentially the attacker's own second account) so that each pair still sums to zero for the batch invariant. Every one of these unit-delta legs hits the `amount <= 1` branch of `token_fee`, returning `Pips::ZERO`, so `fees_collected` for that token is always `0`, regardless of the total notional amount moved. All of these intents can be bundled into one signed `MultiPayload`/`execute_intents` call, so the only cost to the attacker is compute/gas, not `N` separate fee payments.

### Impact Explanation
This directly breaks the "fees owed versus fees collected" binding: the protocol's configured `Pips` fee (`engine.state.fee()`) is meant to be charged on every `token_in` leg of a `TokenDiff`, and `fee_collector` is meant to receive it via `internal_add_balance`: [5](#0-4) 

By chunking any NEP-245 or IMT trade into unit-sized deltas, an attacker can collect the full swapped amount while paying zero protocol fee, for any configured non-zero fee rate. This is a systemic fee-bypass affecting an entire class of tokens (all bridged/wrapped multi-tokens and all IMT tokens), not a one-off edge case, and qualifies as "fees bypassed" under the Critical impact criteria.

### Likelihood Explanation
Exploitation requires only that the attacker (optionally self-matching with a second account they control, or paired with any willing counterparty) submit a batch of unit-delta `TokenDiff` intents in a single signed `MultiPayload`. No privileged role, no admin misconfiguration, and no reliance on a zero-configured fee is needed — the exemption is unconditional in code for `Nep245`/`Imt` token types whenever `|delta| <= 1`. The batch nature of `execute_intents` allows many such legs to be processed in one transaction, keeping gas overhead manageable relative to the fee saved on large notional amounts.

### Recommendation
Remove the `amount <= 1` fee exemption for `Nep245` and `Imt` token types in `TokenDiff::token_fee` (keep the exemption only for genuinely non-fungible `Nep171` tokens), or alternatively track and fee cross-intent cumulative deltas per signer/token within a batch so that decomposition into unit-sized legs cannot zero out the effective fee.

### Proof of Concept
1. Deployer configures a non-zero protocol fee via `set_fee` (e.g., `Pips::ONE_PERCENT`), per `contracts/defuse/src/contract/fees.rs`.
2. Attacker holds a large NEP-245-wrapped balance (e.g., 1,000,000 units of `mt.near:token_id`), obtained normally, e.g. via `mt_transfer_call` into the Defuse contract as shown in `tests/src/tests/defuse/intents/simulate.rs:314-411`.
3. Instead of a single `TokenDiff { diff: {token: -1_000_000, other_token: +X} }` (which would incur the full protocol fee via `fee_ceil`), attacker signs and batches 1,000,000 individual `TokenDiff` intents, each `{ token: -1, other_token: +x }`, matched against counter-intents (their own second account or a willing counterparty) summing to zero per the batch invariant, and submits them all via one `execute_intents(MultiPayloadArgs)` call.
4. For every one of these legs, `TokenDiff::token_fee` returns `Pips::ZERO` because `amount == 1`, so `fees_collected` for the token stays empty and no balance is ever credited to `fee_collector()`.
5. Net result: the full 1,000,000-unit swap completes with `fees_collected == 0`, versus the fee that would have been charged had the trade been executed as a single intent.
