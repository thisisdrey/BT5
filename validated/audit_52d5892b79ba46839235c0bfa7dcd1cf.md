### Title
Floating-point precision loss in TRC10 Exchange (Bancor-style AMM) swap math allows value extraction via repeated small trades - (File: `chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java`)

### Summary
`ExchangeTransactionActuator`, `ExchangeInjectActuator`, and `ExchangeWithdrawActuator` let any account swap/inject/withdraw against a TRC10↔TRX (or TRC10↔TRC10) liquidity pool. By default (`allowHardenExchangeCalculation() == false`), the swap output is computed by `ExchangeProcessor`, which performs the bancor relay-token formula using Java `double` arithmetic and `Math.pow`, then truncates to `long`. This is the exact bug class behind the OTSea report — imprecise/roundable value computation in a value-transfer path reachable by any unprivileged caller — and it is reachable purely via a signed `ExchangeTransactionContract`/`ExchangeInjectContract`/`ExchangeWithdrawContract` transaction.

### Finding Description
`ExchangeCapsule.transaction()` selects between two processors based on the `ALLOW_HARDEN_EXCHANGE_CALCULATION` chain parameter: [1](#0-0) 

When the hardened flag is off (the default value returned by `getAllowHardenExchangeCalculation()` is `0`, i.e. disabled unless a committee proposal enables it): [2](#0-1) 

...the legacy `ExchangeProcessor` is used, which computes both legs of the swap with `double`/`Math.pow`: [3](#0-2) 

Because IEEE-754 double precision and `(long) issuedSupply` / `(long) exchangeBalance` truncation are not exact, the "supply" relay-token accounting drifts from its true rational value with each call. `ExchangeTransactionActuator.execute()` invokes this untrusted-precision computation directly and immediately mutates real account balances/asset amounts based on its output, with no post-hoc sanity/precision check on the taker side (unlike `ExchangeWithdrawActuator`, which does apply a "Not precise enough" BigDecimal check, but only for withdraw, not for the core swap or inject legs): [4](#0-3) 

An attacker fully controls `tokenQuant` per call and can issue many small transactions against the same pool. Repeated interaction with a `double`-based bancor curve is a known class of exploit where a caller can bias cumulative rounding error in their favor over many iterations, extracting value from the pool that is not backed by any real deposited asset. This mirrors the OTSea incident pattern: an EOA-reachable value-computation function with insufficient precision guarantees, ultimately resulting in theft of pooled funds.

### Impact Explanation
Any account (unprivileged EOA) can create and repeatedly trade against a TRC10/TRX exchange pool it does not control. If the accumulated floating-point rounding bias favors the taker, an attacker can systematically siphon TRX or TRC10 tokens out of the pool balance across many transactions, producing an unbacked balance for the attacker and a shortfall for the pool/other participants — a concrete theft-of-funds / unbacked-balance condition, matching Medium-severity impact.

### Likelihood Explanation
The vulnerable path is the default on-chain behavior: `ALLOW_HARDEN_EXCHANGE_CALCULATION` defaults to `0` and only flips via a committee proposal, so all exchange pools are exposed to the legacy double-precision math unless/until the hardened calculation is explicitly activated network-wide. Exploitation only requires broadcasting ordinary `ExchangeTransactionContract`/`ExchangeInjectContract` transactions against an existing pool — no special privilege, no witness/committee role, and no contract deployment beyond a normal token/exchange setup.

### Recommendation
- Enable `ALLOW_HARDEN_EXCHANGE_CALCULATION` by default (or via committee activation on all networks) so `SafeExchangeProcessor`'s `BigDecimal`-based computation is always used instead of `ExchangeProcessor`'s double/`Math.pow` path.
- Alternatively, deprecate/remove the legacy `ExchangeProcessor` double-math code path entirely and route all exchange actuators (`ExchangeTransactionActuator`, `ExchangeInjectActuator`, `ExchangeWithdrawActuator`) through the hardened, exact-arithmetic implementation unconditionally.
- Add invariant checks after every swap/inject that verify pool balances only move by amounts consistent with exact rational math (no rounding advantage to the caller across repeated calls).

### Proof of Concept
1. Create a TRC10↔TRX exchange pool via `ExchangeCreateActuator` with initial balances (e.g., firstTokenBalance=1_000_000_000_000, secondTokenBalance=10_000_000).
2. With `ALLOW_HARDEN_EXCHANGE_CALCULATION` left at its default (0), repeatedly submit small `ExchangeTransactionContract` transactions (e.g., quant=100) via `ExchangeTransactionActuator`, alternating sell direction if needed, as demonstrated by the existing test harness pattern: [5](#0-4) 
3. Track cumulative `firstTokenBalance + secondTokenBalance` valuation of the pool versus the attacker account's balance before/after N iterations. Because `ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply` use `double` and truncate with `(long)` casts (`chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java:17-45`), repeated small trades accumulate rounding in the taker's favor, measurably draining pool balance relative to the exact bancor formula computed by `SafeExchangeProcessor` (BigDecimal) for the same sequence of trades — confirming value extraction not backed by deposited assets.

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
