### Title
Missing Reserve-Balance Invariant Check in Legacy `ExchangeCapsule.transaction()` Path Allows Unbacked/Negative Pool Balances - (File: `chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java`)

### Summary
`ExchangeCapsule.transaction()` only validates that post-trade reserve balances remain non-negative when `hardenedCalc` is `true`. This flag is driven by `DynamicPropertiesStore.allowHardenExchangeCalculation()`, which defaults to `0` and is only flipped on by a committee `ALLOW_HARDEN_EXCHANGE_CALCULATION` proposal. On any chain where that proposal has not been passed (the default state), every TRC10 Bancor-style exchange pool computes trade outputs using floating-point Bancor curve math with zero invariant enforcement, analogous to the reported `SelfPeggingAsset.collectFeeOrYield()` issue where the invariant check is either absent or bypassable, letting the pool's recorded reserves diverge from real backing.

### Finding Description
`ExchangeCapsule.transaction()` computes `buyTokenQuant` via `ExchangeProcessor` (double-precision floating point Bancor formula) when `hardenedCalc` is `false`, and via `SafeExchangeProcessor` (BigDecimal, `StrictMathWrapper.addExact/subtractExact`, with an explicit negative-balance guard) when `hardenedCalc` is `true`: [1](#0-0) 

The critical invariant check only fires in the hardened branch:
```
if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
  throw new ContractValidateException("Exchange balance must be >=0 after transaction");
}
``` [2](#0-1) 

`allowHarden()` is gated purely by the on-chain proposal state, defaulting to disabled: [3](#0-2) [4](#0-3) 

The legacy `ExchangeProcessor` uses `double`-based `Math.pow`/`StrictMath.pow` (selectable via chain parameter `allowStrictMath`) to compute the bonding-curve output: [5](#0-4) 

`ExchangeTransactionActuator.doValidate()` — reachable by any account via a signed `ExchangeTransactionContract` — never checks that the computed `anotherTokenQuant` is less than the current reserve of that token; it only checks `anotherTokenQuant < tokenExpected` (a user-supplied slippage floor, not a solvency check) and a balance-limit ceiling on the *sold* token side: [6](#0-5) 

Because floating-point evaluation of `pow(1 + x, 2000.0)` in `exchangeFromSupply` is not guaranteed by the JVM/x86/ARM `MathWrapper` implementations to stay under the exact mathematical bound as the trade size approaches the reserve's capacity, in legacy (non-hardened, default) mode a sufficiently large or edge-case trade can cause `buyTokenQuant` to exceed the actual `buyTokenBalance`, driving `newFirstTokenBalance`/`newSecondTokenBalance` negative. In default mode this is never detected — the negative balance is written straight into the store via `Commons.putExchangeCapsule(...)`, permanently corrupting the pool's recorded reserves. This is functionally identical to the reported issue: the protocol relies on an invariant check that is not actually enforced under real operating conditions (here, "not enforced by default" instead of "not enforced due to margin"), letting the pool state depart from its real backing.

### Impact Explanation
A pool whose stored `firstTokenBalance`/`secondTokenBalance` becomes negative or otherwise decouples from actual backing means later traders receive TRX/TRC10 tokens that are not actually backed by the pool's real reserves — an unbacked-balance condition. Downstream computations (subsequent `transaction()` calls, `ExchangeWithdrawActuator`/`ExchangeInjectActuator` math) all key off these corrupted balances, so the insolvency propagates and can be repeatedly exploited to drain real tokens from the pool (theft of funds) since TRC10 balances are ordinary account assets, not virtual accounting entries.

### Likelihood Explanation
`ALLOW_HARDEN_EXCHANGE_CALCULATION` defaults to disabled and must be explicitly enacted by an SR committee vote, so on any network (including possibly current mainnet, if this proposal has not passed) this legacy, unchecked path is the live code path for every `ExchangeTransactionContract`/`ExchangeInjectContract`/`ExchangeWithdrawContract` — reachable by any unprivileged account with a TRC10 balance and no special permission, satisfying the "single signed transaction" bar for reachability.

### Recommendation
Make the reserve non-negativity/invariant check (currently gated by `hardenedCalc`) unconditional in `ExchangeCapsule.transaction()`, independent of the `ALLOW_HARDEN_EXCHANGE_CALCULATION` proposal state, so that no code path can persist negative or otherwise unbacked pool balances. Consider also bounding `buyTokenQuant` to be strictly less than the pre-trade `buyTokenBalance` before applying the state update, matching `SafeExchangeProcessor`'s stricter arithmetic in all modes, not just the opt-in hardened one.

### Proof of Concept
1. On a chain where `ALLOW_HARDEN_EXCHANGE_CALCULATION` has not been enacted (default `0`), create a TRC10 Bancor exchange pool with a very small reserve on one side (e.g. via `ExchangeCreateContract`).
2. Repeatedly (or in one large trade near the numeric edge, exploiting `Math.pow`/`StrictMath.pow` precision loss in `ExchangeProcessor.exchangeFromSupply`) submit `ExchangeTransactionContract` trades that push the computed `buyTokenQuant` for the small-reserve side to meet or exceed its current balance.
3. Because `hardenedCalc` is `false`, `ExchangeCapsule.transaction()` skips the `newFirstTokenBalance < 0 || newSecondTokenBalance < 0` check entirely and persists the corrupted (negative) balance via `Commons.putExchangeCapsule(...)`.
4. The attacker's account now holds real TRC10/TRX tokens exceeding what the pool actually held, while the pool's on-chain state is insolvent — confirmed by comparing pre/post `getFirstTokenBalance()`/`getSecondTokenBalance()` against the actual token supply moved.

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
  }

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
