### Title
Expired airdrop lock boundary incorrectly forces claims into a new esMET lock - (File: `contracts/MetAirdrop.sol`)

### Summary
`MetAirdrop._transferReward` treats the configured lock period as expired only when `block.timestamp` is strictly greater than `updatedAt + lockPeriod`. A claim executed exactly at the expiration timestamp incorrectly takes the esMET locking path and creates a new lock lasting at least `ESMET.MINIMUM_LOCK_PERIOD() + 1`, instead of transferring unlocked `MET` to the claimant. [1](#0-0) 

### Finding Description
`RecurringAirdrop.claim` marks the claimant’s full distribution amount as claimed and delegates reward delivery to `_transferReward`. [2](#0-1) 

In `MetAirdrop._transferReward`, `_end = updatedAt + lockPeriod` represents the point at which the lock period has elapsed. The code only sends unlocked `MET` when `_end < block.timestamp`. [3](#0-2) 

At exactly `_end == block.timestamp`, execution falls through to the lock path. The remaining duration calculation clamps zero remaining time up to `ESMET.MINIMUM_LOCK_PERIOD() + 1`, then calls `ESMET.lockFor` with that positive duration. [4](#0-3)  The external interface documents `lockFor` as creating a position whose `unlockTime` is `now + lockPeriod`. [5](#0-4) 

Thus, although the airdrop lock period has already elapsed, the user’s claim is consumed and converted into a newly locked esMET position.

### Impact Explanation
A claimant calling `claim` at the exact expiration timestamp loses immediate access to the distributed `MET` for a new externally enforced lock duration. This temporarily freezes a valid unlocked reward claim and marks the airdrop allocation as fully claimed, preventing the user from retrying after the intended expiration. [6](#0-5) 

### Likelihood Explanation
The vulnerable window is one timestamp value per distribution round. It requires an eligible claimant to submit the transaction in a block whose timestamp exactly equals `updatedAt + lockPeriod`. This is uncommon but does not require privileged access, malicious governance, oracle manipulation, or contract deployment. The deployed mainnet `MetAirdrop` contains the same code path. [1](#0-0) 

### Recommendation
Treat the boundary as expired:

```solidity
if (_end <= block.timestamp) {
    MET.safeTransfer(to_, amount_);
    return;
}
```

This preserves the locking behavior while `block.timestamp < _end` and prevents an expired lock from being replaced with a fresh minimum-duration esMET lock.

### Proof of Concept
The following Hardhat fork test extends the existing `MetAirdrop` fixture, which deploys `MetAirdrop`, initializes a Merkle root, and funds it with `MET`. [7](#0-6) 

```ts
it('locks an expired claim when block.timestamp equals unlock time', async function () {
  const amount = rewards0[alice.address]
  const leaf = generateLeaf(alice.address, amount)
  const proof = merkleTree0.getHexProof(leaf)

  const unlockTime = (await airdrop.updatedAt()).add(await airdrop.lockPeriod())

  // Execute the claim exactly at the intended expiration boundary.
  await time.setNextBlockTimestamp(unlockTime)

  const nextTokenId = await esMET721.nextTokenId()
  const tx = await airdrop.connect(alice).claim(amount, proof)
  await tx.wait()

  // The claim is consumed.
  expect(await airdrop.claimed(alice.address)).eq(amount)

  // Expected behavior: Alice receives unlocked MET.
  // Actual behavior: Alice receives no MET.
  expect(await met.balanceOf(alice.address)).eq(0)

  // A fresh esMET position was created with a future unlockTime.
  const position = await esMET.positions(nextTokenId)
  expect(position.lockedAmount).eq(amount)
  expect(position.unlockTime).gt(unlockTime)
})
```

With the current condition, the assertion `position.unlockTime > unlockTime` holds because zero remaining time is clamped to `ESMET.MINIMUM_LOCK_PERIOD() + 1`. [4](#0-3)

    function _transferReward(address to_, uint256 amount_) internal override {
        uint256 _end = updatedAt + lockPeriod;

        if (_end < block.timestamp) {
            MET.safeTransfer(to_, amount_);
            return;
        }

        uint256 _min = ESMET.MINIMUM_LOCK_PERIOD() + 1;
        uint256 _max = ESMET.MAXIMUM_LOCK_PERIOD();

        // Ensures valid lock period
        uint256 _remainLockPeriod = Math.min(Math.max(_end - block.timestamp, _min), _max);

        token.safeApprove(address(ESMET), 0);
        token.safeApprove(address(ESMET), amount_);
        ESMET.lockFor(to_, amount_, _remainLockPeriod);
