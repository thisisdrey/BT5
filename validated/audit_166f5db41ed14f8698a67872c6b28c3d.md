### Title
`convert-to-shares-preview` mints zero shares for depositors when `total-assets` is zero but `total-supply` (zft) is non-zero, permanently freezing deposited funds — analogous to the `updateGlobalExchangeRate` zero-total-shares bug (File: `mainnet/contracts/vault/v0-vault-stx.clar`, and identically in `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`)

### Summary
The referenced Covalent finding shows that `updateGlobalExchangeRate` breaks when `totalGlobalShares` is `0` while there is still reward/asset value in the system: the exchange-rate/share math is only defensively coded for the "no shares yet" case, not for the "assets went to zero while shares still exist" case, and this mismatch causes funds to become permanently unclaimable. Zest's vault `convert-to-shares-preview` function has the exact mirror-image gap: it defensively handles `total-supply == 0` (first deposit, mint 1:1) but when `total-supply != 0` and `total-assets == 0`, it silently returns `u0` shares instead of reverting or preventing the deposit, letting a depositor's underlying tokens be pulled into the vault while they receive zero zTokens in return.

### Finding Description
Each vault's private conversion helper is defined identically:

```clarity
(define-private (convert-to-shares-preview (amount uint))
  (let ((ta (total-assets-preview))
        (ts (total-supply-preview)))
    (if (is-eq ts u0)
        amount
        (if (is-eq ta u0)
            u0
            (mul-div-down amount ts ta)))))
``` [1](#0-0) 

`total-assets-preview` is derived from the mutable `assets` variable plus accrued interest above `total-borrowed`: [2](#0-1) 

The `assets` var can be driven to `u0` by `socialize-debt`, which is explicitly designed to write down `assets`, `total-borrowed`, and `principal-scaled` (and the liquidity index `lindex`) when bad debt must be absorbed by the pool, while doing nothing to burn or otherwise account for the outstanding zft share supply:

```clarity
(define-public (socialize-debt (scaled-amount uint))
  (let ((scaled-principal (var-get principal-scaled))
        ...
        (new-lindex (if (and (> old-total-assets u0) (> old-total-assets debt-reduction))
                       (mul-div-down current-lindex (- old-total-assets debt-reduction) old-total-assets)
                       u0)))
    (try! (check-caller-auth))
    (asserts! (> scaled-amount u0) ERR-AMOUNT-ZERO)
    (var-set lindex new-lindex)
    (var-set principal-scaled (if (> scaled-principal scaled-amount) (- scaled-principal scaled-amount) u0))
    (var-set total-borrowed (if (> borrowed principal-reduction) (- borrowed principal-reduction) u0))
    (var-set assets (if (> current-assets principal-reduction) (- current-assets principal-reduction) u0))
    ...
``` [3](#0-2) 

If bad debt large enough relative to the pool is socialized (e.g., after an under-collateralized liquidation shortfall triggered through the market contract), `assets` (and thus `total-assets-preview`) can be driven to `u0` while `total-supply` (existing zft holders' shares) remains non-zero. From that point on, `deposit` becomes broken for any ordinary caller:

```clarity
(define-public (deposit (amount uint) (min-out uint) (recipient principal))
    (let (
      ...
      (inkind (convert-to-shares-preview amount)))
    (asserts! (not (get deposit states)) ERR-PAUSED)
    (asserts! (var-get initialized) ERR-INIT)
    (asserts! (not (var-get in-flashloan)) ERR-REENTRANCY)

    (asserts! (>= inkind min-out) ERR-SLIPPAGE)

    (try! (receive-underlying amount account))
    (try! (ft-mint? zft inkind recipient))
    (var-set assets (+ current-assets amount))
    ...
``` [4](#0-3) 

Because `inkind` (`convert-to-shares-preview amount`) evaluates to `u0` when `ta == 0` and `ts != 0`, the only guard against this is `(asserts! (>= inkind min-out) ERR-SLIPPAGE)`. Any depositor supplying `min-out = 0` — which is the normal, unprivileged default a user or an integrating contract would pass when it doesn't yet know the exchange rate — passes this check trivially (`0 >= 0`), `receive-underlying` pulls in the full `amount` of underlying tokens, `ft-mint?` mints `0` zft to `recipient`, and `assets` is bumped back up by `amount`. The depositor has just donated their entire deposit to the existing zft holders with zero shares of their own to redeem it — a direct, un-refundable loss of the deposited principal for that specific unprivileged caller.

This is the structural analog of the C4 report: the code has a defensive branch for "shares are zero" (mint 1:1) but not for the symmetric hazard "assets are zero while shares are non-zero" (should either revert the deposit or use some minimum-liquidity floor), exactly matching the judge's characterization of a shares/assets accounting split that isn't protected against a degenerate zero state reached through a privileged-but-triggerable path (`socialize-debt`, analogous to `disableValidator`).

### Impact Explanation
Funds transferred by an ordinary depositor are irrecoverably lost from that depositor's perspective — they permanently lose their principal with no shares minted to redeem it, and it is effectively donated to existing zft holders. This is a **theft/permanent freezing of user funds at rest** for the specific depositor who is not the one causing the zero-asset condition (which is driven by the privileged `socialize-debt` caller responding to bad debt) — it lands squarely in the "permanent freezing of funds" / theft-of-principal impact class.

### Likelihood Explanation
Likelihood is conditioned on `socialize-debt` having previously reduced `assets` to `u0` for that specific vault while its zft `total-supply` remains non-zero — a state that requires meaningful bad debt relative to pool assets, which is a real, reachable operational scenario (e.g., severe undercollateralized liquidation shortfall) rather than a purely theoretical one, and once in that state, *any* subsequent unprivileged deposit call with the common `min-out = 0` default will trigger the loss without any special attacker skill.

### Recommendation
In `convert-to-shares-preview` (and the identical helper across all six vault contracts), do not return `u0` shares silently when `ts != 0` and `ta == 0`; instead the deposit path should revert (e.g., a dedicated `ERR-VAULT-INSOLVENT`) so `min-out = 0` cannot mask the degenerate state, or the vault should burn/retire the outstanding zft supply as part of `socialize-debt` so `ts` returns to `0` in lockstep with `ta`, restoring the "first depositor" 1:1 minting branch instead of leaving a shares/assets mismatch.

### Proof of Concept
1. Vault (e.g., `v0-vault-stx`) has non-zero `assets` and non-zero zft `total-supply` from prior deposits.
2. Through the market's liquidation/bad-debt flow, the privileged caller invokes `socialize-debt` with a `scaled-amount` large enough that `principal-reduction >= current-assets`, driving `(var-set assets u0)` per [5](#0-4) , while zft `total-supply` remains unchanged (shares are never burned in `socialize-debt`).
3. An ordinary user calls `deposit(amount, min-out=0, recipient=self)`. `convert-to-shares-preview` computes `ts != 0`, `ta == 0` → returns `u0` per [1](#0-0) .
4. `(asserts! (>= inkind min-out) ERR-SLIPPAGE)` passes (`0 >= 0`); `receive-underlying` pulls `amount` from the user; `ft-mint?` mints `0` zft to the user; `assets` becomes `amount` again per [6](#0-5) .
5. The user now holds `0` zft shares and has no way to redeem the underlying they just deposited — their funds are permanently lost/frozen, transferred in effect to the pre-existing zft holders.
