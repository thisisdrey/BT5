### Title
Missing length limit on `Query` in `SearchFilesByContent` allows resource-exhaustion via oversized PCRE pattern passed to `git grep` - ([File: internal/gitaly/service/repository/search_files.go])

### Summary
`validateSearchFilesRequest` only checks that `Query` is non-empty, unlike the sibling `SearchFilesByName` path which caps `Filter` at `searchFilesFilterMaxLength` (1000 bytes) before compiling it as a Go regexp. In `SearchFilesByContent`, the unbounded `Query` is passed directly as the `-e` argument to `git grep --perl-regexp`, so an attacker-controlled repo owner can submit large PCRE patterns (up to the gRPC message limit) that are expensive to compile/execute, and can repeat this concurrently against their own repo to consume CPU/memory on the shared Gitaly node.

### Finding Description
`SearchFilesByContent` (internal/gitaly/service/repository/search_files.go:32) calls `validateSearchFilesRequest` (line 174) which only validates the repository, checks `len(req.GetQuery()) == 0`, and validates the ref — there is no upper bound on `Query` length. The raw `req.GetQuery()` value is then passed unmodified as the value of the `-e` flag to a spawned `git grep --perl-regexp` child process (lines 41-56). By contrast, `SearchFilesByName` explicitly guards against this class of issue by enforcing `searchFilesFilterMaxLength = 1000` on `req.GetFilter()` before calling `regexp.Compile` (lines 118-128), showing this is a known and previously mitigated risk that was not carried over to the content-search path.

Because there is no gRPC-level `MaxRecvMsgSize` override configured in `internal/gitaly/server/server.go` (verified: no such option is set in `serverOptions`), the effective bound on `Query` is grpc-go's default `4 MiB` per-message limit — well within "several MB" as posited in the question. A 4 MiB PCRE pattern passed to `--perl-regexp` can be expensive for PCRE2/git-grep to compile and can exhibit expensive backtracking behavior depending on pattern construction, and this cost is incurred per invocation of `git grep`, once per file/blob scanned in the target ref's tree.

### Impact Explanation
An attacker who owns/controls a repository can issue `SearchFilesByContentRequest` calls with a `Query` up to the gRPC message-size ceiling (~4 MiB) and repeat this concurrently. Each call spawns a `git grep --perl-regexp` process that must compile and evaluate this large pattern against every blob in the given ref, consuming CPU and process memory on the Gitaly node. Since Gitaly nodes are multi-tenant (hosting many repositories/projects), sustained concurrent abuse can degrade or deny service for other repositories co-located on the same node — this matches a node-level Denial of Service impact class.

### Likelihood Explanation
This requires no privileged role: any authenticated GitLab user who owns or can push to a repository can invoke `SearchFilesByContent` against it. The request is trivial to construct (a single gRPC call with a large `Query` string) and can be trivially parallelized to multiply resource pressure. The only limiting factor is the default gRPC 4 MiB message-size ceiling (not an explicit Gitaly-side control), so the attacker is not blocked by any application-level cap the way they would be for `SearchFilesByName`'s `Filter`.

### Recommendation
Add an explicit maximum-length check on `Query` in `validateSearchFilesRequest` for the `SearchFilesByContent` path (or a dedicated constant mirroring `searchFilesFilterMaxLength`), rejecting oversized patterns with `InvalidArgument` before spawning `git grep`. Consider also applying a timeout/resource limit on the spawned `grep` command independent of message size, since even short patterns can trigger catastrophic PCRE backtracking.

```go
func validateSearchFilesRequest(ctx context.Context, locator storage.Locator, req searchFilesRequest) error {
	if err := locator.ValidateRepository(ctx, req.GetRepository()); err != nil {
		return err
	}

	if len(req.GetQuery()) == 0 {
		return errors.New("no query given")
	}

	if len(req.GetRef()) == 0 {
		return errors.New("no ref given")
	}

	if bytes.HasPrefix(req.GetRef(), []byte("-")) {
		return errors.New("invalid ref argument")
	}

	return nil
}
```
