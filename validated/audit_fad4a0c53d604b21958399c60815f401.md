### Title
Floating-point precision loss in the default TRC10 `Exchange` (Bancor-style AMM) swap math enables value-extraction from swap pools - (File: `chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java`)

### Summary
The on-chain TRC10 AMM (`Exchange...Contract` family) that any account can trade against via `ExchangeTransactionContract` computes swap output using IEEE-754 `double` arithmetic and `Math.pow`-based bonding-curve formulas in `ExchangeProcessor`, instead of the fixed-point `BigDecimal` implementation available in `SafeExchangeProcessor`. The safe path is gated behind the `allowHardenExchangeCalculation` dynamic property, which is disabled by default (tests explicitly toggle it on and reset it to `0`), so unauthenticated swap transactions execute against the floating-point implementation by default.

### Finding Description
`ExchangeCapsule.transaction()` picks the processor implementation based on the `hardenedCalc` flag: [1](#0-0) 

When hardening is not enabled, swaps route to `ExchangeProcessor`, which performs the Bancor relay-token math with `double` and `Math.pow`: [2](#0-1) 

The safer, deterministic `BigDecimal`-based implementation (`SafeExchangeProcessor`) exists but is only used when `allowHardenExchangeCalculation` is set: [3](#0-2) 

This gate defaults to disabled, as shown by every test that exercises the hardened path explicitly enabling and then disabling it (`saveAllowHardenExchangeCalculation(1)` ... `saveAllowHardenExchangeCalculation(0)` in `finally`): [4](#0-3) 

`ExchangeTransactionActuator.execute()` (the swap entrypoint reachable by any signed transaction from any account, with no creator/permission restriction) calls `exchangeCapsule.transaction(...)` and directly applies the processor's output to real token/TRX balances: [5](#0-4) 

Because `double`/`Math.pow` computations are approximate and rounding-direction is not guaranteed to be conservative (unlike the `BigDecimal`+`RoundingMode.DOWN` truncation used in `SafeExchangeProcessor`), an attacker can search for `sellTokenQuant` values where floating-point rounding yields an output greater than the mathematically exact bonding-curve amount, repeatedly executing such swaps to extract value from the pool beyond what the invariant should allow. `ExchangeTransactionActuator` only validates `tokenExpected`/balance sufficiency; it does not independently verify that the processor's output is bounded by the exact bonding-curve invariant, so any floating-point rounding-in-favor-of-attacker case is accepted and settled.

### Impact Explanation
Any account can create/fund an `Exchange` (via `ExchangeCreateContract`, permissionless) and any other account can trade against it via `ExchangeTransactionContract` without restriction (unlike `ExchangeInjectContract`/`ExchangeWithdrawContract`, which require the pool creator). If floating-point rounding in `ExchangeProcessor` can be steered to favor the trader, repeated swaps allow an attacker to drain TRX/TRC10 balances held in the pool beyond the amount that the bonding-curve math should award — a concrete unauthorized extraction of on-chain value, matching the "theft/unbacked balance" class of impact this scan targets.

### Likelihood Explanation
Medium. Exploitation requires: (1) locating or creating a pool with favorable liquidity ratios, and (2) finding `sellTokenQuant` inputs where the `double`/`Math.pow` rounding diverges unfavorably against the pool (a search problem, not a cryptographic one, since the formula and rounding behavior are fully known/public in the open-source client). No special privileges, signatures, or third-party dependencies are needed — only ordinary signed `ExchangeTransactionContract` transactions from an unprivileged account. The hardened, safe alternative already exists in the codebase (`SafeExchangeProcessor`) but is off by default, indicating the maintainers are aware of precision concerns yet the exploitable legacy path remains the default.

### Recommendation
- Make `allowHardenExchangeCalculation` (or an equivalent deterministic `BigDecimal`/fixed-point exchange formula) the default and only supported path for `ExchangeTransactionActuator`, `ExchangeInjectActuator`, and `ExchangeWithdrawActuator`, removing the floating-point `ExchangeProcessor` from production use entirely (or activating it via a hard-fork proposal that is enabled network-wide).
- Add an invariant check in `ExchangeTransactionActuator.execute()`/`ExchangeCapsule.transaction()` that rejects any swap whose output would increase the constant-product/bonding-curve value of the pool in the trader's favor beyond a strict, provably-safe bound, independent of the underlying floating-point/BigDecimal implementation.
- Add fuzz/property-based tests comparing `ExchangeProcessor` and `SafeExchangeProcessor` outputs across a wide range of balances/quantities to detect and quantify all rounding-favorable cases before considering the legacy processor safe to keep as a fallback.

### Proof of Concept
Conceptual (requires live-network numeric search, not reproducible purely from static code):
1. Create (or locate) a TRC10 `Exchange` pool via `ExchangeCreateContract` with attacker-favorable initial balances.
2. Iterate candidate `quant` values for `ExchangeTransactionContract`, computing the exact bonding-curve output with arbitrary precision (e.g., in Python/`mpmath`) and compare to what `ExchangeProcessor.exchange()` (`double`/`Math.pow`, in `chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java` lines 17-45) would return.
3. Select `quant` values where the `double`-computed output exceeds the exact value (rounding-in-favor-of-attacker).
4. Broadcast repeated `ExchangeTransactionContract` swaps with these `quant` values from an unprivileged account; `ExchangeTransactionActuator.execute()` (lines 61-91) will credit the excess amount each time, cumulatively draining the pool's TRX/TRC10 reserves.

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
