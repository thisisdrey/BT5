### Title
Missing Timeout on Attacker-Controlled HTTP Fetch in `CreateRepositoryFromSnapshot` Allows RPC Handler DoS - ([File: internal/gitaly/service/repository/create_repository_from_snapshot.go])

### Summary
`CreateRepositoryFromSnapshot` lets a caller supply an arbitrary `http_url` that Gitaly fetches and streams directly into `tar` for extraction. The shared `httpClient`/`newResolvedHTTPClient` used by `untar()` never set `http.Client.Timeout`, only the transport-level `ResponseHeaderTimeout` (bounds time-to-first-byte, not total transfer time) [1](#0-0) . Once headers are received, `client.Do(req)` and the subsequent `rsp.Body` read (piped as `tar` stdin) can hang indefinitely if the remote server trickles bytes slowly or stalls, with no per-request deadline distinct from the caller-supplied gRPC context [2](#0-1) .

### Finding Description
`untar()` builds a request from `in.GetHttpUrl()` and executes it with `client.Do(req)`, then hands `rsp.Body` straight to a spawned `tar` process as stdin [3](#0-2) . The client only relies on `httpTransport`'s `ResponseHeaderTimeout: 30 * time.Second`, which only bounds the time until response headers arrive — it does not bound how long the body can take to stream [4](#0-3) . There is no `http.Client.Timeout` set, unlike other Gitaly HTTP clients (e.g. `NewHTTPClientWithOpts`, which explicitly sets `Timeout: readTimeout(readTimeoutSeconds)`) [5](#0-4) .

Unlike `FetchRemote`, which explicitly derives a bounded `ctx` from `req.GetTimeout()` before performing any remote operation [6](#0-5) , `CreateRepositoryFromSnapshot` performs no such bounding — it relies solely on whatever deadline (if any) the calling gRPC client happens to set on the context [7](#0-6) . Gitaly's gRPC server does not impose a default per-RPC deadline itself (confirmed via `internal/gitaly/server/server.go`, which configures interceptors/keepalive but no deadline enforcement).

### Impact Explanation
A caller of `CreateRepositoryFromSnapshot` can point `http_url` at a server (including one under their control) that responds with valid headers but then stalls or drips the archive body extremely slowly. Because there is no client-side read/body timeout, the RPC handler, its underlying HTTP connection, and the spawned `tar` subprocess can be held open indefinitely (bounded only by an optional caller-set gRPC deadline). Repeated such requests can exhaust Gitaly's goroutines, file descriptors, and subprocess slots, degrading or denying service — matching the "RPC-handler resource limits" DoS category. The code comment itself acknowledges the archive/URL is "trusted *a lot*" and flags it as needing hardening before being pointed at untrusted endpoints [8](#0-7) .

### Likelihood Explanation
Exploitation only requires invoking `CreateRepositoryFromSnapshot` with an `http_url` pointing to a slow/stalling HTTP endpoint — no special privileges beyond normal RPC access, and no reliance on a leaked token or MITM position. This is a straightforward, repeatable trigger via a crafted RPC field.

### Recommendation
Set an explicit overall timeout on the HTTP client(s) used in `untar()` (e.g. `http.Client{Timeout: ...}` or via `context.WithTimeout` wrapping the fetch), and/or enforce a minimum read-rate / total-duration timeout on the response body before it's piped to `tar`. Additionally, ensure `CreateRepositoryFromSnapshot` derives a bounded context server-side (similar to `FetchRemote`'s `req.GetTimeout()` pattern) rather than depending entirely on caller-supplied gRPC deadlines.

### Proof of Concept
1. Stand up an HTTP server that responds with `200 OK` and valid headers immediately, then writes the response body at a negligible rate (e.g., 1 byte every few seconds) or simply blocks after headers, never closing the connection.
2. Call `CreateRepositoryFromSnapshot` with `http_url` pointing at this server and no client-side gRPC deadline (or a very long one).
3. Observe that the Gitaly RPC handler, the underlying HTTP connection, and the `tar` subprocess remain blocked indefinitely, since `ResponseHeaderTimeout` was already satisfied and no overall client timeout exists — repeating this ties up increasing server resources.

// httpTransport defines a http.Transport with values that are more restrictive
// than for http.DefaultTransport.
//
// They define shorter TLS Handshake, and more aggressive connection closing
// to prevent the connection hanging and reduce FD usage.
var httpTransport = &http.Transport{
	Proxy: http.ProxyFromEnvironment,
	DialContext: (&net.Dialer{
		Timeout:   30 * time.Second,
		KeepAlive: 10 * time.Second,
	}).DialContext,
	MaxIdleConns:          2,
	IdleConnTimeout:       30 * time.Second,
	TLSHandshakeTimeout:   10 * time.Second,
	ExpectContinueTimeout: 10 * time.Second,
	ResponseHeaderTimeout: 30 * time.Second,
}

// httpClient defines a http.Client that uses the specialized httpTransport
// (above). It also disables following redirects, as we don't expect this to be
// required for this RPC.
var httpClient = &http.Client{
	Transport: correlation.NewInstrumentedRoundTripper(otelhttp.NewTransport(httpTransport)),
	CheckRedirect: func(*http.Request, []*http.Request) error {
		return http.ErrUseLastResponse
	},
}

func (s *server) untar(ctx context.Context, path string, in *gitalypb.CreateRepositoryFromSnapshotRequest) error {
	req, err := http.NewRequestWithContext(ctx, "GET", in.GetHttpUrl(), nil)
	if err != nil {
		return structerr.NewInvalidArgument("Bad HTTP URL: %w", err)
	}

	client := httpClient
	if resolvedAddress := in.GetResolvedAddress(); resolvedAddress != "" {
		client, err = newResolvedHTTPClient(in.GetHttpUrl(), resolvedAddress)
		if err != nil {
			return structerr.NewInvalidArgument("creating resolved HTTP client: %w", err)
		}
	}

	if in.GetHttpAuth() != "" {
		req.Header.Set("Authorization", in.GetHttpAuth())
	}

	rsp, err := client.Do(req)
	if err != nil {
		return structerr.NewInternal("HTTP request failed: %w", err)
	}
	defer rsp.Body.Close()

	if rsp.StatusCode < http.StatusOK || rsp.StatusCode >= http.StatusMultipleChoices {
		return structerr.NewInternal("HTTP server: %s", rsp.Status)
	}

	cmd, err := command.New(ctx, s.logger, []string{"tar", "-C", path, "-xvf", "-"}, command.WithStdin(rsp.Body))
	if err != nil {
		return err
	}

	return cmd.Wait()
}

func (s *server) CreateRepositoryFromSnapshot(ctx context.Context, in *gitalypb.CreateRepositoryFromSnapshotRequest) (*gitalypb.CreateRepositoryFromSnapshotResponse, error) {
	repository := in.GetRepository()
	if err := s.locator.ValidateRepository(ctx, repository, storage.WithSkipRepositoryExistenceCheck()); err != nil {
		return nil, structerr.NewInvalidArgument("%w", err)
	}

	if err := repoutil.Create(ctx, s.logger, s.locator, s.gitCmdFactory, s.catfileCache, s.txManager, s.repositoryCounter, repository, func(repo *gitalypb.Repository) error {
		path, err := s.locator.GetRepoPath(ctx, repo, storage.WithRepositoryVerificationSkipped())
		if err != nil {
			return structerr.NewInternal("getting repo path: %w", err)
		}

		// The archive contains a partial git repository, missing a config file and
		// other important items. Initializing a new bare one and extracting the
		// archive on top of it ensures the created git repository has everything
		// it needs (especially, the config file and hooks directory).
		//
		// NOTE: The received archive is trusted *a lot*. Before pointing this RPC
		// at endpoints not under our control, it should undergo a lot of hardening.
		if err := s.untar(ctx, path, in); err != nil {
			return structerr.NewInternal("extracting snapshot: %w", err)
		}

		return nil
	}); err != nil {
		return nil, structerr.NewInternal("creating repository: %w", err)
	}
