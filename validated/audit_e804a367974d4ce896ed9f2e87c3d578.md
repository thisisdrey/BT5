## Analog Found

### Title
Attacker can pre-occupy a deterministic CREATE2 contract address to permanently DoS a specific deployment - (File: `actuator/src/main/java/org/tron/core/vm/program/Program.java`)

### Summary
The Solana report shows that because an associated token account's address is fully deterministic (derived from the lockbox PDA + NFT mint), an attacker can pre-create it and cause Anchor's `init` constraint to fail forever, permanently blocking `deposit()` for that specific NFT. The same "deterministic-address pre-emption" bug class exists in java-tron's TVM `CREATE2` handling: the resulting contract address is a public, offline-computable function of `sender`, `salt`, and `code hash`, and if an account/contract already occupies that address when the real deployment executes, the create is rejected with a hard, unrecoverable error for that exact salt/sender/code combination.

### Finding Description
`Program.createContractImpl()` computes `newAddress` for `CREATE2` via `TransactionUtil.generateContractAddress2` / `WalletUtil.generateContractAddress2`, which is `sha3(sender || salt || sha3(code))` [1](#0-0)  — this is the standard CREATE2 formula and is fully predictable off-chain by anyone who knows the deploying factory's address and the salt/init-code that will be used (the TRON test contract even documents this exact formula for prediction) [2](#0-1) .

When the real deployment transaction executes, `createContractImpl` looks up `existingAccount` at `newAddress` and, if Constantinople rules are active, only clears the "already exists" flag when `isContractExist` reports there is no live contract there; otherwise `contractAlreadyExists` stays `true` [3](#0-2) . If `contractAlreadyExists` is `true`, the create attempt is rejected with a permanent exception rather than being retried or silently succeeding:

```java
if (contractAlreadyExists) {
  createResult.setException(new BytecodeExecutionException(
      "Trying to create a contract with existing contract address: 0x" + Hex
          .toHexString(newAddress)));
}
``` [4](#0-3) 

This mirrors the Solana bug precisely: the target address is deterministically derivable from public inputs before the legitimate actor's transaction is confirmed, and the "creation" primitive has an unconditional existing-account failure path with no `init_if_needed`/upgrade fallback for the "contract already deployed" case. An attacker who observes a pending CREATE2 deployment in the mempool (or who can predict the salt a protocol will use, e.g., deterministic factory patterns) can front-run it with a cheap transaction that deploys any contract to the same `newAddress`, permanently poisoning that specific `(sender, salt, code)` triple: the legitimate deployer's later, retried, or resubmitted CREATE2 calls with the same salt will always hit the `contractAlreadyExists` branch and fail.

### Impact Explanation
This is a Medium-severity denial of service, not a fund-theft bug — exactly matching the reported class. Any protocol on TRON relying on deterministic CREATE2 addresses for a given salt (counterfactual wallets, deterministic factory deployments, state-channel/vault patterns) can have a specific salt permanently blocked from ever being deployed to, breaking application logic that depends on deploying at a pre-committed address (e.g., counterfactual instantiation patterns common in smart-contract wallets/multisigs). No funds are stolen or frozen by this path itself, but application flows depending on that exact address become permanently unusable, matching the original report's "permanent DoS, no assets stolen or locked" impact profile.

### Likelihood Explanation
High. Any unprivileged account can submit an ordinary `TriggerSmartContract` transaction calling a `CREATE2`-executing factory to occupy a target address — the only requirement is knowing (or observing) `sender`, `salt`, and `code hash`, all of which are either publicly fixed contract parameters or visible in the pending transaction's calldata before it lands on-chain.

### Recommendation
- For protocols exposing CREATE2-based deployment through a public factory pattern, avoid using attacker-guessable/enumerable salts, or bind the salt to caller-specific data (e.g., include `msg.sender` in salt derivation) so an attacker cannot pre-compute and squat a specific caller's intended address.
- At the protocol level, consider whether the "contract already exists" rejection in `Program.createContractImpl()` (`actuator/src/main/java/org/tron/core/vm/program/Program.java:916-919`) could instead surface as a normal revert (already the case) so factory contracts can catch it and retry with an alternate salt — application-level mitigation is required since the TVM opcode semantics themselves follow standard CREATE2 rules and changing them would break EVM equivalence.

### Proof of Concept
1. Legitimate deployer plans to CREATE2-deploy `TestContract` from `Factory` at `salt = 100` (as in `Create2Test.testCreate2`) [5](#0-4) .
2. Attacker observes the pending transaction (or predicts the salt), independently computes the same `expectedContract` address using `generateContractAddress2(factoryAddress, salt, code)` [1](#0-0) .
3. Attacker submits a transaction that gets included first, deploying any contract to that address via the same `deploy(bytes,uint256)` factory call and salt.
4. When the legitimate deployer's transaction (or any retry using the same salt) executes, `createContractImpl` finds `existingAccount != null` and a live contract there, sets `contractAlreadyExists = true`, and the create call permanently fails with `BytecodeExecutionException("Trying to create a contract with existing contract address...")` [4](#0-3) , exactly as demonstrated (commented out but present) in `Create2Test.create2AddressTest`, where a second deploy attempt with the same salt fails with an exception [6](#0-5) .

    // selector: 0xbb63e785
    // Predict CREATE2 address without deploying
    //
    // TRON CREATE2 formula (differs from standard EVM):
    //   address = keccak256(prefix ++ sender[20] ++ salt[32] ++ keccak256(code)[32])[12:]
    //
    // - Standard EVM uses 0xff as prefix (magic byte)
    // - TRON replaces it with the address prefix byte (0x41 for mainnet, 0xa0 for testnet)
    // - This value is hardcoded at compile time by tron-solc
    //
    function getCreate2Addr(uint256 salt) public view returns (address) {
        bytes memory bytecode = type(FreezeContract).creationCode;
        bytes32 hash = keccak256(
            abi.encodePacked(
                bytes1(0x41),       // TRON mainnet address prefix
                address(this),      // 20-byte factory address
                salt,               // 32-byte salt
                keccak256(bytecode) // 32-byte code hash
            )
        );
        return address(uint160(uint256(hash)));
    }
```
