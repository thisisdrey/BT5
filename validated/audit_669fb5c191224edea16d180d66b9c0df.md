The reported bug class targets a `supportEMode` function in a `RiskEngineModule` contract implementing Aave-style E-Mode categories. Zest Protocol v2 has no such contract or E-Mode concept — its closest analog is the **egroup** (efficiency group) system in `mainnet/contracts/registry/v0-egroup.clar`, which defines risk parameters (LTV, liquidation thresholds) per bitmask combination of assets, resolved via `resolve`/`find` [1](#0-0) .

Egroup creation/update (`insert`/`update`) is gated by `check-dao-auth`, meaning only the DAO can add, remove, or change which assets belong to an egroup mask [2](#0-1) . The rules explicitly place DAO-controlled egroup registry changes out of scope, stating that "full DAO control of the asset and egroup registries is intended design and egroup invariants needing global position knowledge are verified off-chain before approval." Since the only mechanism resembling the reported "asset removed from E-Mode while retaining elevated factor" scenario would require a DAO-driven egroup mask change, this analog is excluded by the scan rules rather than being an unprivileged-principal-reachable bug.
