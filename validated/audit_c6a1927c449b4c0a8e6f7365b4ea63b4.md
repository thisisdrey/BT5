### Title
Precision loss in the legacy vote-reward distribution (divide-before-multiply on floating point) allows reward-pool value extraction - ([File: chainbase/src/main/java/org/tron/core/service/MortgageService.java])

### Summary
`MortgageService` computes SR voting rewards using the same anti-pattern flagged in the external report: it divides first and then multiplies by a large, attacker-influenced quantity, instead of multiplying first and dividing last. This happens in two places reachable indirectly from ordinary account operations (voting/freezing and withdrawing rewards): `payStandbyWitness()` and the legacy `computeReward(long cycle, List<Pair<byte[], Long>> votes)` used for cycles prior to `newRewardAlgorithmEffectiveCycle`. ### Finding Description
`payStandbyWitness()` calculates `eachVotePay = (double) totalPay / voteSum` (a rounded per-unit "price"), then multiplies this already-imprecise unit value by each witness's `voteCount`:
```java
double eachVotePay = (double) totalPay / voteSum;
...
long pay = (long) (w.getVoteCount() * eachVotePay);
``` [3](#0-2) 

This is structurally identical to the reported bug class: a division happens first to obtain a per-unit rate, and the resulting (rounded) value is then scaled up by a large `voteCount`, instead of computing `totalPay * voteCount / voteSum` in one multiply-then-divide step. The legacy `computeReward` used for pre-`newRewardAlgorithmEffectiveCycle` cycles has the same pattern:
```java
double voteRate = (double) userVote / totalVote;
reward += voteRate * totalReward;
``` [4](#0-3) 

By contrast, the newer Vi-based reward algorithm (`RewardViCalService`/`DelegationStore.accumulateWitnessVi`) explicitly avoids this by using `BigInteger` and a large fixed-point `DECIMAL_OF_VI_REWARD` scale, multiplying before dividing:
```java
BigInteger deltaVi = BigInteger.valueOf(reward)
    .multiply(DECIMAL_OF_VI_REWARD)
    .divide(BigInteger.valueOf(voteCount));
``` [5](#0-4) 

The existence of this "hardened" replacement strongly suggests the legacy double-based computation in `MortgageService` was a known source of precision drift, but the vulnerable code path (`computeReward` for cycles before the new-algorithm cutover, and `payStandbyWitness`, which is unconditional) remains reachable.

### Impact Explanation
Both paths are triggered by ordinary, unprivileged actions: freezing/voting for a witness (`VoteWitnessContract`/TVM `vote`), and withdrawing rewards (`WithdrawBalanceContract` or TVM `withdrawReward`). Because the division happens on a shared pool (`totalPay`/`totalReward`) before multiplying by each voter's individual share, per-voter rounding is not guaranteed to sum back to the original pool — errors can round in either direction across many small-value votes. An attacker who splits stake across many small-vote accounts, or repeatedly triggers withdrawal against many cycles/witnesses, can accumulate rounding-favorable outcomes over many transactions, extracting value beyond what the reward pool actually holds (an unbacked/incorrect balance credit) — directly analogous to the "many tokens for cheap" theft pattern in the report, except realized as reward over-payment rather than a single large flash-loan-sized transaction.

### Likelihood Explanation
The double-precision rounding error per individual operation is small (mantissa precision ~1e-15 relative), so a single voter/withdrawal cannot extract a large amount in one shot the way the Solidity report describes for a single flash-loaned trade. Exploitation requires repeated, patient interaction over many voting cycles/witnesses/accounts to accumulate a meaningful skew, and is gated by whether the network's `newRewardAlgorithmEffectiveCycle` has already passed the point where the legacy code stops being used for freshly-elapsed cycles (the legacy path is only used for cycles strictly before that boundary). `payStandbyWitness()`, however, is unconditional and runs every maintenance cycle regardless of the reward-algorithm version, so it remains permanently exposed.

### Recommendation
Convert both computations to integer/BigInteger multiply-then-divide, matching the fix already implemented for `DelegationStore`/`RewardViCalService`:
- In `payStandbyWitness()`, compute `pay = totalPay * voteCount / voteSum` using `Math.multiplyExact`/`BigInteger` instead of `double eachVotePay`.
- In the legacy `computeReward(long cycle, List<Pair<byte[], Long>> votes)`, replace `voteRate * totalReward` with `totalReward * userVote / totalVote` using integer or `BigInteger` arithmetic, and verify that per-cycle payouts never exceed the recorded `totalReward` for that cycle (add an invariant/assert to cap distributed rewards at the pool amount).

  private long computeReward(long cycle, List<Pair<byte[], Long>> votes) {
    long reward = 0;
    for (Pair<byte[], Long> vote : votes) {
      byte[] srAddress = vote.getKey();
      long totalReward = delegationStore.getReward(cycle, srAddress);
      if (totalReward <= 0) {
        continue;
      }
      long totalVote = delegationStore.getWitnessVote(cycle, srAddress);
      if (totalVote == DelegationStore.REMARK || totalVote == 0) {
        continue;
      }
      long userVote = vote.getValue();
      double voteRate = (double) userVote / totalVote;
      reward += voteRate * totalReward;
    }
    return reward;
  }
