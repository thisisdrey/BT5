### Title
Delegated `WithdrawFromGasKey` bypasses `gas_key_costs` accounting in pending transaction queue - ([File: chain/client/src/pending_transaction_queue.rs])

### Summary
`add_chunk_transactions` scans `tx.actions()` for `Action::WithdrawFromGasKey` at lines 280-288 without unwrapping `Action::Delegate`/`Action::DelegateV2`, while `is_deploy_like_action` (lines 174-196) explicitly recurses into delegate actions for the deploy-exclusivity check. A `WithdrawFromGasKey` nested inside a `SignedDelegateAction`'s `actions` list (a valid `NonDelegateAction`, confirmed by `core/primitives/src/action/delegate.rs` allowing any non-delegate action type to be wrapped, and validated end-to-end in `runtime/runtime/src/action_validation.rs::validate_delegate_action`) is therefore never counted into `chunk_data.gas_key_costs`, silently under-reporting the pending commitment against the target gas key.

### Finding Description
`add_chunk_transactions` in `chain/client/src/pending_transaction_queue.rs` iterates the outer transaction's `tx.actions()` flatly (lines 280-288) looking for `Action::WithdrawFromGasKey` to add its `amount` into `chunk_data.gas_key_costs[(signer_id, withdraw.public_key)]`. This mirrors the `has_deploy_action`/`is_deploy_like_action` pattern used a few lines earlier (line 266), but that helper explicitly recurses into `Action::Delegate`/`Action::DelegateV2` inner actions (lines 180-185), whereas the withdraw scan does not. Consequently, if the outer transaction's top-level action list contains an `Action::Delegate(SignedDelegateAction)` whose inner `actions` (a `Vec<NonDelegateAction>`) contain a `WithdrawFromGasKey`, the loop at line 280 never observes it (it only ever sees the single top-level `Action::Delegate` variant, which doesn't match the `if let Action::WithdrawFromGasKey(..)` pattern), and no amount is added to `chunk_data.gas_key_costs`. ` [1](#0-0) ` ` [2](#0-1) `

However, I could not confirm within available context whether `PendingTxSession::check_pending`'s admission logic actually uses `gas_key_costs` keyed the same way the relayed transaction's inner `WithdrawFromGasKey` would need for a real admission bypass. Specifically:
- The `gas_key_costs` map key is `(tx.signer_id(), withdraw.public_key)` — i.e., the **outer transaction's signer** (the relayer, for a `Delegate` action) paired with the gas key's public key from the inner action. For the inner `WithdrawFromGasKey` to actually execute against the delegator's (`sender_id`) gas key at apply time, the runtime must resolve the account being debited via the `DelegateAction.sender_id`, not the relayer's account id. I was unable to verify in the available code (`runtime/runtime/src/actions.rs`, `runtime/runtime/src/access_keys.rs`) exactly which account is charged when `WithdrawFromGasKey` executes as an inner delegate action, due to tool/iteration limits. If the account charged is the delegate's `sender_id` (the normal semantics of meta-transactions — inner actions execute "on behalf of" `sender_id`), then even a *correctly recursing* fix to the pending-queue scan would need to key by `sender_id`, not `tx.signer_id()`, meaning today's code is doubly wrong: it neither recurses into `Delegate` nor uses the correct account key for gas-key accounting purposes of the inner action.
- Similarly, `session_gas_key_withdrawals` in `PendingTxSession::check_pending` (lines 532-541) has the exact same flat, non-recursing scan over `tx.transaction.actions()`, so the same gap exists in the ephemeral, same-chunk-production-session tracking, not just in the persisted chunk queue.

### Impact Explanation
If validated, this would fall under "under-reported pending commitment" / admission-invariant violation described in the question: `paid_from_gas_key` returned by `get_pending_constraints`/`check_pending` would not reflect a delegated withdrawal, potentially allowing further transactions against the same gas key to be admitted into the pending queue beyond the key's real remaining balance across multiple uncertified chunks. As the question itself notes, apply-time balance checks in the runtime (verifier/access key balance checks) remain authoritative and would still reject execution of transactions that overdraw the actual on-chain gas key balance, so this does not by itself cause fund loss, double-spend, or state-root divergence — it can at most cause spurious admission of doomed transactions (wasted queue slots / relayer inclusion), which is a liveness/pending-admission bookkeeping issue rather than a fund-safety or consensus-safety issue.

### Likelihood Explanation
The precondition (attacker relays a `SignedDelegateAction` wrapping `WithdrawFromGasKey`) is achievable by any unprivileged account that funds a gas key and crafts a delegate action, since `WithdrawFromGasKey` is a valid `NonDelegateAction` and delegate-action validation in `action_validation.rs` does not disallow it. However, because apply-time metering (verifier + gas key balance checks) is authoritative for actual balance correctness, the practical damage is bounded to pending-admission bookkeeping drift, not a concrete loss/freezing of funds or consensus divergence as required by the bounty scope.

### Recommendation
Make the `WithdrawFromGasKey` scan in `add_chunk_transactions` (and the analogous scan in `PendingTxSession::check_pending`) recurse into `Action::Delegate`/`Action::DelegateV2` inner actions the same way `is_deploy_like_action` does, and ensure the correct account (the delegate's `sender_id`, not the relayer's `tx.signer_id()`) is used as the key when the withdrawal action originates from an inner delegate action.

### Proof of Concept
Add a unit test in `chain/client/src/pending_transaction_queue.rs` constructing a `SignedTransaction` whose action list is `[Action::Delegate(SignedDelegateAction { delegate_action: DelegateAction { actions: [NonDelegateAction::try_from(Action::WithdrawFromGasKey(...)).unwrap()], sender_id, public_key, .. }, .. })]`, call `add_chunk_transactions`, and assert that `pending_gas_key_costs` contains the withdrawal amount for the target gas key — this assertion currently fails since the flat scan at lines 280-288 never observes the nested action, confirming the accounting gap (though not a concrete fund-safety violation given apply-time authoritative checks).

fn is_deploy_like_action(action: &Action) -> bool {
    match action {
        Action::DeployContract(_)
        | Action::DeployGlobalContract(_)
        | Action::UseGlobalContract(_)
        | Action::DeterministicStateInit(_) => true,
        Action::Delegate(signed_delegate) => {
            signed_delegate.delegate_action.get_actions().iter().any(is_deploy_like_action)
        }
        Action::DelegateV2(signed_delegate) => {
            signed_delegate.delegate_action.get_actions().iter().any(is_deploy_like_action)
        }
        Action::CreateAccount(_)
        | Action::FunctionCall(_)
        | Action::Transfer(_)
        | Action::Stake(_)
        | Action::AddKey(_)
        | Action::DeleteKey(_)
        | Action::DeleteAccount(_)
        | Action::TransferToGasKey(_)
        | Action::WithdrawFromGasKey(_) => false,
    }
}
