Confirmed: `ExchangeInjectActuator` has no creator restriction, unlike `ExchangeWithdrawActuator`, meaning any account can inject liquidity into any exchange pool without slippage protection.

### Title
No slippage protection in `ExchangeInjectActuator` allows economic loss from unfavorable pool ratio changes - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`)

### Summary
`ExchangeInjectActuator` lets any account inject liquidity into a TRX/TRC10 bancor-style exchange pool. The counter-token amount (`anotherTokenQuant`) the injector must pay is derived from the pool's live `firstTokenBalance`/`secondTokenBalance` ratio at execution time, but the `ExchangeInjectContract` protobuf message carries no `expected`/minimum-output-style bound, unlike its sibling `ExchangeTransactionContract`.

### Finding Description
`ExchangeInjectContract` only carries `owner_address`, `exchange_id`, `token_id`, and `quant` [1](#0-0) . In contrast, `ExchangeTransactionContract` was explicitly given an `expected` field to guard against unfavorable price movement between signing and execution [2](#0-1)  and this field is checked during validation, throwing `"token required must greater than expected"` if the computed output falls below it [3](#0-2) .

`ExchangeInjectActuator`, however, computes `anotherTokenQuant` purely from the pool's current on-chain balances via a live ratio calculation, both in `doValidate()` and again in `execute()`: [4](#0-3) 

This mirrors the reported Burve pattern exactly: the amount of the second asset the caller must contribute (analogous to shares minted) depends on a fluctuating state variable — the exchange pool ratio — that can move between the time the transaction is signed/broadcast and the time it is packed into a block, since other users can send concurrent `ExchangeTransactionContract` (buy/sell), `ExchangeInjectContract`, or the creator's `ExchangeWithdrawContract` transactions against the same `exchange_id` in the interim, all of which mutate `firstTokenBalance`/`secondTokenBalance` via `ExchangeCapsule.transaction()` and the inject/withdraw balance updates. Unlike `ExchangeWithdrawActuator`, which restricts execution to the exchange creator only, `ExchangeInjectActuator` has no such creator check, so this is reachable by any unprivileged account submitting an `ExchangeInjectContract` transaction. There is no `minAnotherTokenQuant`/`expected` cap enforced against the computed `anotherTokenQuant`, so the injecting account has no on-chain guarantee about the maximum amount of the counter-token it will be forced to pay for a given `tokenQuant`.

### Impact Explanation
A user broadcasting an `ExchangeInjectContract` intending to inject liquidity at a known ratio can, due to ratio drift caused by intervening transactions on the same pool, end up paying substantially more of the counter-token than expected for the same `tokenQuant`, resulting in economic loss to that user and a corresponding value transfer to the pool/other participants. This is a fund-loss issue directly analogous to the reported Medium-severity Burve finding, reachable purely through normal transaction broadcasting with no privileged role required.

### Likelihood Explanation
Exchange pools are typically low-liquidity relative to TRX supply on TRC10 exchanges, so ratio shifts from a handful of concurrent transactions are plausible; any account can trigger the adverse condition simply by submitting buy/sell/inject transactions against the same `exchange_id` shortly before the victim's inject transaction is packed, making this a realistically triggerable (Medium likelihood) condition rather than a purely theoretical one.

### Recommendation
Add an `expected`/`maxAnotherTokenQuant` (or `minAnotherTokenQuant` when withdrawing) field to `ExchangeInjectContract`, analogous to the existing `expected` field on `ExchangeTransactionContract`, and enforce it in `ExchangeInjectActuator.doValidate()`/`execute()` so the transaction fails if the computed counter-token amount exceeds the caller-specified bound.

### Proof of Concept
1. Pool P has `firstTokenBalance = 1_000_000_000`, `secondTokenBalance = 10_000_000` (ratio 100:1).
2. Alice signs and broadcasts `ExchangeInjectContract{tokenID=first, quant=100_000_000}` expecting to pay `~1_000_000` of the second token (per the formula in `ExchangeInjectActuator.execute()` lines 73-76 and `doValidate()` lines 215-220).
3. Before Alice's transaction is packed into a block, Bob broadcasts an `ExchangeTransactionContract` (or another `ExchangeInjectContract`) against the same `exchange_id` that shifts `firstTokenBalance`/`secondTokenBalance` toward a ratio unfavorable to Alice (e.g., 50:1).
4. When Alice's transaction executes, `anotherTokenQuant` is recomputed against the new ratio, forcing her to pay roughly double the second token she anticipated, with no on-chain check rejecting the transaction, since `ExchangeInjectContract` has no `expected`/max-bound field. [5](#0-4)
