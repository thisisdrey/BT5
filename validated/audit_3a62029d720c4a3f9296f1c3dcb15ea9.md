Based on my research, the strongest analog in java-tron is the unbounded, self-growable `toAccounts`/`fromAccounts` list stored inside a single `DelegatedResourceAccountIndex` protobuf record, which is read, `.contains()`-scanned, mutated and fully rewritten on every legacy `FreezeBalanceContract`/`UnfreezeBalanceContract` transaction to a new counterparty.

### Title
Unbounded per-account `DelegatedResourceAccountIndex.toAccounts`/`fromAccounts` list causes linear-scan and full-record-rewrite cost on every delegated freeze/unfreeze - ([File: actuator/src/main/java/org/tron/core/actuator/FreezeBalanceActuator.java])

### Summary
When the legacy (`supportAllowDelegateOptimization() == false`) code path is active, `FreezeBalanceActuator.delegateResource` and `UnfreezeBalanceActuator.execute` maintain a single `DelegatedResourceAccountIndexCapsule` per account containing an in-protobuf `List<ByteString>` of every counterparty address the account has ever delegated resources to/from. Every new delegation to a distinct receiver address performs an `O(n)` `.contains()` check over this list and then appends to it and rewrites the whole capsule; an attacker (or any unprivileged user) can grow this list without any upper bound simply by issuing many cheap `FreezeBalanceContract` transactions to distinct receiver addresses.

### Finding Description
`FreezeBalanceActuator.delegateResource` reads the owner's and receiver's `DelegatedResourceAccountIndexCapsule`, does a linear `.contains()` check on `toAccountsList`/`fromAccountsList`, appends the new address, and calls `delegatedResourceAccountIndexStore.put(...)` to persist the entire updated list back as one DB value: [1](#0-0) 

The same unbounded list is read, mutated, and rewritten again on `UnfreezeBalanceActuator.execute` (via `new ArrayList<>(...)`, `.remove(...)`, `setAllToAccounts`/`setAllFromAccounts`): [2](#0-1) 

The underlying capsule stores the whole list inline in a single protobuf message with no cap on size: [3](#0-2) 

A project test explicitly demonstrates the list growing linearly with the number of distinct receivers (100+ entries in one account's index), and each subsequent freeze operation reads/rewrites the growing list: [4](#0-3) 

This is the same bug class as the reported `plugins[]` issue: an application-controlled, growable array with no explicit maximum size that is looped/scanned on every "claim"-equivalent transaction (here, every delegated freeze/unfreeze), causing cost per-transaction to grow with the number of distinct counterparties, and the whole record to be re-serialized/rewritten on each operation.

Note: java-tron later introduced `supportAllowDelegateOptimization()` (`DynamicPropertiesStore`), which switches to a per-pair keyed storage scheme (`delegatedResourceAccountIndexStore.delegate/delegateV2`, keyed rows instead of an embedded list) specifically to avoid this scalability problem — this is essentially the fix the original report recommended (bounding/avoiding the unbounded array). However, the legacy code path (`FreezeBalanceActuator`/`UnfreezeBalanceActuator` unoptimized branch and the `convert()` migration logic in `DelegatedResourceAccountIndexStore`) remains present in the codebase and is only inert if the `ALLOW_DELEGATE_OPTIMIZATION` proposal is active on a given chain/config. On any network/testnet/private chain where that proposal has not been activated, this legacy unbounded-list path is fully reachable by ordinary unprivileged `FreezeBalanceContract`/`UnfreezeBalanceContract` transactions.

### Impact Explanation
Where the legacy path is active, per-transaction cost of `FreezeBalanceContract`/`UnfreezeBalanceContract` grows linearly with the number of distinct delegation counterparties an account has accumulated, since each freeze/unfreeze does an `O(n)` `.contains()`/`.remove()` scan and rewrites the full list to storage. An attacker can cheaply mint a large number of tiny freeze delegations to many distinct receiver addresses, inflating their own and receivers' index size, degrading transaction processing performance for those accounts and increasing capsule storage/serialization size without bound (resource-exhaustion / node performance degradation vector), consistent in class with the reported "unbounded array looped frequently" issue.

### Likelihood Explanation
Likelihood is conditional: it requires the network to not have activated the `ALLOW_DELEGATE_OPTIMIZATION` proposal (default/legacy behavior). On networks where it is inactive, the attack is straightforward and requires only the minimum freeze amount and gas/bandwidth for many transactions, making it fully reachable by any unprivileged account.

### Recommendation
- Verify whether `ALLOW_DELEGATE_OPTIMIZATION` is enabled by default on all deployed chains using this codebase; if not, backport the same keyed-storage optimization (or an explicit upper bound with pruning) to the legacy path unconditionally, removing the toggle-dependent unbounded-list branch.
- Add an explicit maximum-size check (analogous to `MAX_VOTE_NUMBER` in `VoteWitnessProcessor`) before appending to `toAccountsList`/`fromAccountsList` in `FreezeBalanceActuator.delegateResource`.

### Proof of Concept
1. On a chain where `supportAllowDelegateOptimization()` returns `false`, issue N `FreezeBalanceContract` transactions from account A, each delegating a minimal frozen balance to a distinct newly-generated receiver address.
2. Each transaction triggers `FreezeBalanceActuator.delegateResource`, which does `ownerIndexCapsule.getToAccountsList().contains(...)` (O(current size)) then `addToAccount(...)` and persists the whole growing list.
3. Repeat for large N (as shown feasible for N=100 in `FreezeBalanceActuatorTest.testMultiFreezeDelegatedBalanceForBandwidth`) to observe linearly increasing processing cost and storage size for account A's `DelegatedResourceAccountIndex` record, with no enforced cap.
