## Title
Missing cross-check of `RelayFromAddr` against the sending peer's certified `vpnAddrs` in `relayManager.handleCreateRelayRequest` allows relay-state poisoning with a spoofed identity - (File: `relay_manager.go`)

## Summary
`handleCreateRelayRequest` reads `from := protoAddrToNetAddr(m.RelayFromAddr)` (or the legacy `OldRelayFromAddr`) directly from the attacker-controlled `NebulaControl_CreateRelayRequest` body and uses it as the key for `AddRelay`/relay-state operations without ever checking that `from` is one of `h.vpnAddrs` for the authenticated sending `HostInfo h`. This lets a peer with one legitimate, CA-signed tunnel to a relay-capable node claim an arbitrary victim address as the relay "from" identity in both the terminal branch (`AddRelay(rm.l, h, f.hostMap, from, ...)` at line 482) and the forwarding branch (`AddRelay(rm.l, peer, f.hostMap, from, nil, ForwardingType, Requested)` at line 548).

## Finding Description
`relayManager.HandleControlMsg` (relay_manager.go:298-342) unmarshals the control message and only rejects it if `RelayFromAddr`/`RelayToAddr` are nil; it never compares `msg.RelayFromAddr` to `h.vpnAddrs`, where `h` is the `HostInfo` of the already-authenticated peer that physically sent the packet.

`handleCreateRelayRequest` (relay_manager.go:426-605) then computes:
```go
from := protoAddrToNetAddr(m.RelayFromAddr)
target := protoAddrToNetAddr(m.RelayToAddr)
```
It only checks that `from` is not one of *my* own addresses (`f.myVpnAddrsTable.Contains(from)`, line 441) — it never checks `from` against `h.vpnAddrs` (the addresses actually certified for the authenticated sender). Two branches then key relay state directly off this unverified `from`:

- Terminal branch (target == me): `AddRelay(rm.l, h, f.hostMap, from, &m.InitiatorRelayIndex, TerminalType, Established)` (relay_manager.go:482) inserts a `Relay{PeerAddr: from}` into `h.relayState`, the relayState object of the directly-connected attacker `HostInfo`. `from` can be any address (a victim's certified address) chosen by the attacker.
- Forwarding branch (target != me, `am_relay` enabled): `AddRelay(rm.l, peer, f.hostMap, from, nil, ForwardingType, Requested)` (relay_manager.go:548) inserts `Relay{PeerAddr: from}` into `peer.relayState` (the relay-target's HostInfo relay state on the local relay node), again keyed on the attacker-chosen `from`, before any address ownership is confirmed.

Notably, when *forwarding* the request onward, the code re-derives the outgoing `RelayFromAddr` from `h.vpnAddrs[0]` (line 577: `req.RelayFromAddr = netAddrToProtoAddr(h.vpnAddrs[0])`), showing the authors were aware `h.vpnAddrs[0]` is the trustworthy value — but this re-derivation is only applied to the message sent onward to the next hop, not to the locally-inserted relay-state keyed by `from` at line 548, nor to the terminal-case `AddRelay` call at line 482. This is an inconsistency: the local relay bookkeeping trusts the unauthenticated field while the outbound protocol message uses the authenticated one.

Because `Relay.PeerAddr` is used by `QueryRelayForByIp`/`UpdateRelayForByIpState` (called from `StartRelays`, relay_manager.go:104, 167, 213/553, and the terminal path at line 448) to decide whether an existing relay path already exists for a given victim vpn address and to update its state, an attacker can plant/perturb relay bookkeeping entries associated with a victim address it does not own, on a node it has one legitimate, unprivileged tunnel to.

## Impact Explanation
This is remote hostmap/relay state poisoning: an authenticated-but-unprivileged peer (one CA-signed cert, one established tunnel to a relay-capable node) can insert `Relay` records keyed to a victim's vpn address into another `HostInfo`'s `relayState` without any check that the attacker's certificate actually covers that address. Because completion of these relay records is index-based (`CompleteRelayByIdx`/`CompleteRelayByIP`), the practical exploitability of full traffic redirection depends on whether the index-based completion also re-validates the `PeerAddr`/address association at completion time — this could not be fully confirmed from the available files (`hostmap.go`'s `CompleteRelayByIdx`/`CompleteRelayByIP` implementation and their address-matching logic were not retrieved before the tool budget ran out). At minimum, this is a confirmed logic flaw: relay state is created and modified using an attacker-supplied address field that is never checked against the sender's certified `vpnAddrs`, which is inconsistent with the invariant that relay trust must derive only from the authenticated identity of the requesting `HostInfo`.

## Likelihood Explanation
Preconditions match the attacker model exactly: one CA-signed cert, one established tunnel to a relay-capable node (`am_relay` enabled, or being the terminal target of a relay). No spoofed source address or privileged access is required — this is a single, ordinary UDP `header.Control` packet with a crafted `NebulaControl_CreateRelayRequest` body. The bug is trivially and repeatably reachable: any peer that can complete a normal handshake can send this control message.

## Recommendation
In `relayManager.handleCreateRelayRequest` (and `HandleControlMsg`), before using `m.RelayFromAddr`/`m.OldRelayFromAddr`:
- In the terminal branch (target == me, relay_manager.go:441-487), require that `from` is contained in `h.vpnAddrs` (the certified addresses of the authenticated sender) before calling `AddRelay(rm.l, h, f.hostMap, from, ...)`; reject/log-and-return otherwise. This branch legitimately represents "the sender IS the relayed-from party," so `from` must equal one of `h`'s own certified addresses.
- In the forwarding branch (relay_manager.go:525-604), since `h` here is the *previous hop*, not the ultimate origin, do not trust the raw `from` value from the message for authorization purposes; if origin-address enforcement is desired transitively, it should be re-derived/re-validated the same way the outgoing `RelayFromAddr` already is (`h.vpnAddrs[0]`), rather than keying local `peer.relayState` on the unauthenticated `from`.
- Add unit tests asserting that a `CreateRelayRequest` whose `RelayFromAddr` does not match any address in `h.vpnAddrs` is rejected (terminal case) or does not create relay state keyed to an address foreign to the authenticated chain (forwarding case).

## Proof of Concept
Unit test plan for `relay_manager_test.go`:
1. Construct two `HostInfo` objects: `h` with `vpnAddrs = [A]` (attacker's real certified address) and a victim address `B` not in `h.vpnAddrs`.
2. Build a `NebulaControl{Type: NebulaControl_CreateRelayRequest, RelayFromAddr: netAddrToProtoAddr(B), RelayToAddr: netAddrToProtoAddr(<node under test's own address>)}` (terminal case) and call `rm.handleCreateRelayRequest(cert.Version2, h, f, msg)`.
3. Assert that no `Relay` entry is created in `h.relayState` for address `B`, or that the request is rejected with an error/log, because `B ∉ h.vpnAddrs`.
4. Repeat for the forwarding branch: set `am_relay=true`, `RelayToAddr` = some third node `C` reachable from the relay node, and assert that `peer.relayState` (C's HostInfo relay state) is not populated with `PeerAddr = B` when `B ∉ h.vpnAddrs`.
5. Currently, both assertions fail — the relay state is created keyed on `B` with no address-ownership check, confirming the finding.
