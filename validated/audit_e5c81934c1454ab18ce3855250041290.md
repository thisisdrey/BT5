### Title
Unbounded O(total_vote_accounts) work in `VoteAccounts::clone_and_filter_for_vat` allows cheap junk-vote-account spam to inflate epoch-boundary bank-freeze cost - ([File: vote/src/vote_account.rs])

### Summary
`VoteAccounts::clone_and_filter_for_vat` always iterates the *entire* `vote_accounts` map to build `entries_to_sort` and perform the BLS/stake/balance checks before any truncation to `max_vote_accounts` happens. Because any unprivileged client can get an arbitrary vote-program account inserted into the global `stakes_cache.vote_accounts` map simply by funding a rent-exempt, correctly-sized, initialized vote account (no stake or minimum balance required for insertion), an attacker can inflate the size of this map arbitrarily, and every epoch-boundary recomputation (`Bank::get_top_epoch_stakes` / `compute_new_epoch_caches_and_rewards`) pays cost linear in the injected junk count even though none of the junk accounts survive filtering.

### Finding Description
`clone_and_filter_for_vat` loops over `self.vote_accounts.iter()` unconditionally to compute `has_bls`, `has_stake`, `has_balance` for every entry before the `max_vote_accounts` cap is ever applied: [1](#0-0) . Only after this full pass does it attempt to truncate to `max_vote_accounts` via `select_nth_unstable_by` [2](#0-1) . There is no early bound tying the initial scan cost to `max_vote_accounts`; the cost is strictly `O(len(self.vote_accounts))`.

The `vote_accounts` map that feeds this function is populated in `StakesCache::check_and_store`, which inserts *any* vote-program-owned account with nonzero lamports and a correctly sized/initialized `VoteStateVersions` payload, regardless of stake or balance: [3](#0-2) , via `upsert_vote_account`/`VoteAccounts::insert` [4](#0-3) [5](#0-4) . Nothing here requires the account to be staked, delegated, or above the VAT minimum balance for *insertion* — those checks only apply later inside `clone_and_filter_for_vat`.

This unfiltered map is what feeds the per-epoch-boundary VAT computation: `Bank::get_top_epoch_stakes` calls `clone_and_filter_for_vat` directly on `self.stakes_cache.stakes()` [6](#0-5) , and `compute_new_epoch_caches_and_rewards` (invoked at epoch boundaries) also calls `unfiltered_distribution_vote_accounts.clone_and_filter_for_vat(...)` on the full stakes-derived vote-account set [7](#0-6) . Any account an attacker creates and funds (via a normal `CreateAccount` + vote-program `InitializeAccount`-style transaction, no stake delegation needed) is written to accounts-db and then absorbed into `stakes_cache` on the next `update_stakes_cache` pass over executed transactions [8](#0-7) . None of the has_stake/has_balance filters in `clone_and_filter_for_vat` gate *insertion* into the map — they only gate *survival* of the filter, after the full-map scan has already been paid for.

Consequently, an attacker who submits many low-cost transactions creating zero-stake (or below-VAT-minimum-balance) vote accounts can grow `vote_accounts.len()` far beyond the real, staked validator population, without any of these accounts ever surviving the VAT filter. Every epoch boundary, `clone_and_filter_for_vat` must still visit all of them.

### Impact Explanation
This is a work-proportionate-to-fee / bounded-resources violation: creating a vote account costs one transaction fee plus a recoverable rent-exempt deposit, while the recurring cost imposed on every validator is a full linear scan (BLS check + balance check + HashMap insert) at every epoch boundary for the lifetime of the account (until closed). Because the rent-exempt deposit is refundable capital (not burned), the attacker's ongoing marginal cost per junk account approaches only the one-time transaction fee, while the imposed per-epoch CPU cost on the entire validator set recurs indefinitely and scales with the number of junk accounts. This falls under the Bounded Resources / grossly-underpriced-work category — it can stall or measurably delay `Bank::freeze`/epoch-boundary slot processing proportionally to injected junk vote-account count, per the scoped impact statement.

### Likelihood Explanation
Feasible for any unstaked, unprivileged actor: creating a vote account requires no delegated stake, no leader/gossip/validator role — only a funded keypair issuing the vote-program's account-creation instruction with a rent-exempt balance. The attack is repeatable indefinitely (accounts can also be closed and their rent reclaimed, then recreated), and the cost scales roughly linearly with the number of junk accounts, while the resulting per-epoch validator-side CPU burden also scales linearly. The main friction is the aggregate rent-exempt capital that must be locked at any given time and the number of transactions/fees needed to create the accounts, both of which are attacker-controlled and can be amortized across many low-cost transactions over time.

### Recommendation
Bound the pre-filter scan cost, e.g. by maintaining an incrementally-updated sorted/partitioned structure (or a bounded top-K heap keyed on stake) inside `VoteAccounts` so that `clone_and_filter_for_vat` does not need to touch every zero-stake/below-minimum-balance entry on every call; alternatively, track and evict zero-stake/insufficient-balance vote accounts from `stakes_cache.vote_accounts` as soon as they fail the has_stake/has_balance predicate (rather than only at VAT-filter time) so the cached map size stays bounded by the realistically staked/qualified set, and consider charging rent or a minimum balance for insertion into `vote_accounts` at the `check_and_store` stage.

### Proof of Concept
Integration test plan (Rust, `runtime/tests/vote_account.rs` style, or a `runtime/src/bank/tests.rs` bench-style test):
```rust
#[test]
fn test_clone_and_filter_for_vat_scan_cost_scales_with_junk_accounts() {
    use std::time::Instant;

    // Baseline: a small number of legitimate, VAT-qualifying accounts.
    let real_accounts = new_staked_vote_accounts(
        &mut rand::rng(), 100, 100, None,
        MIN_STAKE_FOR_STAKED_ACCOUNT, MAX_STAKE_FOR_STAKED_ACCOUNT, |_| 10_000_000_000,
    );
    let t0 = Instant::now();
    let _ = real_accounts.clone_and_filter_for_vat(MAX_ALPENGLOW_VOTE_ACCOUNTS, MIN_STAKE_FOR_STAKED_ACCOUNT);
    let baseline_us = t0.elapsed().as_micros();

    // Attacker-simulated: same 100 legit accounts + N=200_000 zero-stake / below-minimum-balance
    // "junk" vote accounts (as would result from unstaked CreateAccount+InitializeAccount spam).
    let mut junked = real_accounts.clone();
    for _ in 0..200_000 {
        let account = new_rand_vote_account(&mut rand::rng(), None, true); // has BLS pubkey, but...
        // zero delegated stake and/or balance below minimum_vote_account_balance_for_vat
        junked.insert(Pubkey::new_unique(), VoteAccount::try_from(account).unwrap(), || 0);
    }
    let t1 = Instant::now();
    let filtered = junked.clone_and_filter_for_vat(MAX_ALPENGLOW_VOTE_ACCOUNTS, MIN_STAKE_FOR_STAKED_ACCOUNT);
    let attacked_us = t1.elapsed().as_micros();

    // None of the junk survives filtering...
    assert_eq!(filtered.len(), real_accounts.clone_and_filter_for_vat(MAX_ALPENGLOW_VOTE_ACCOUNTS, MIN_STAKE_FOR_STAKED_ACCOUNT).len());
    // ...yet wall time scales near-linearly with injected junk, not staying ~constant.
    assert!(attacked_us > baseline_us * 100, "expected near-linear blowup, got baseline={baseline_us}us attacked={attacked_us}us");
}
```
Expected result: `attacked_us` grows proportionally with the injected junk-account count while `filtered.len()` stays unchanged, demonstrating that the per-epoch-boundary cost is driven by `vote_accounts.len()` rather than by the number of accounts that actually pass VAT filtering.

    pub fn insert(
        &mut self,
        pubkey: Pubkey,
        new_vote_account: VoteAccount,
        calculate_stake: impl FnOnce() -> u64,
    ) -> Option<VoteAccount> {
        let vote_accounts = Arc::make_mut(&mut self.vote_accounts);
        match vote_accounts.entry(pubkey) {
            Entry::Occupied(mut entry) => {
                // This is an upsert, we need to update the vote state and move the stake if needed.
                let (stake, old_vote_account) = entry.get_mut();

                if let Some(staked_nodes) = self.staked_nodes.get_mut() {
                    let old_node_pubkey = old_vote_account.node_pubkey();
                    let new_node_pubkey = new_vote_account.node_pubkey();
                    if new_node_pubkey != old_node_pubkey {
                        // The node keys have changed, we move the stake from the old node to the
                        // new one
                        Self::do_sub_node_stake(staked_nodes, *stake, old_node_pubkey);
                        Self::do_add_node_stake(staked_nodes, *stake, *new_node_pubkey);
                    }
                }

                // Update the vote state
                Some(mem::replace(old_vote_account, new_vote_account))
            }
            Entry::Vacant(entry) => {
                // This is a new vote account. Use the caller-provided stake for the initial
                // cache entry.
                let (stake, vote_account) = entry.insert((calculate_stake(), new_vote_account));
                if let Some(staked_nodes) = self.staked_nodes.get_mut() {
                    Self::do_add_node_stake(staked_nodes, *stake, *vote_account.node_pubkey());
                }
                None
            }
        }
