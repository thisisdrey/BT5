### Title
`WalletContract` re-entrancy guard can become permanently stuck, freezing all funds/tokens of an ETH-implicit account - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
This report's underlying bug class is an admin/state flag (`live` in `CollateralJoin`) that, once flipped, is checked by a withdrawal path with no way to ever flip it back, permanently trapping user funds that were otherwise fully repaid/entitled to release. The closest reachable analog in this nearcore tree is the `has_in_flight_tx` re-entrancy guard in the ETH-implicit `WalletContract` (`runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`), which gates the *sole* entry point (`rlp_execute`) that lets an ETH-implicit account holder move any of its own funds or tokens.

### Finding Description
`rlp_execute` is the only method by which an ETH-implicit account (an ordinary unprivileged user's wallet, created automatically on first transfer, cf. `action_implicit_account_creation_transfer`) can transfer NEAR, call other contracts, or manage its own access keys: [1](#0-0) 

Before doing anything, it rejects the call outright if `has_in_flight_tx` is `true`: [2](#0-1) 

The flag is set to `true` right before returning a promise, and is only ever reset to `false` at the top of the corresponding `#[private]` callback (`rlp_execute_callback`, `address_check_callback`, `nep_141_storage_balance_callback`, `ban_relayer`): [3](#0-2) [4](#0-3) 

The static gas budgeted for each of these callbacks is hard-coded and small (5–15 Tgas total), independent of the actual work the callback performs (deserializing responses, building further promises, issuing refund transfers): [5](#0-4) 

Because NEAR receipt execution is all-or-nothing — a failing receipt causes `state_update.rollback()`, discarding *every* state write made during that receipt, including ones made earlier in the same function body — any panic/abort inside one of these callbacks (e.g. running out of the fixed static gas, or an unexpected panic while building the next promise) after the in-memory `self.has_in_flight_tx = false` assignment causes that reset to be rolled back: [6](#0-5) 

Since `has_in_flight_tx` was already persisted as `true` by the preceding `rlp_execute` receipt (a separate, already-committed state transition), and the callback is `#[private]` (only callable by the contract itself via a promise chain it initiates), there is no external mechanism to reset it once stuck. Every subsequent call to `rlp_execute` from the account owner will be rejected at the guard check, permanently disabling all further NEAR transfers, contract calls, or key management from that account — even though the account may hold a NEAR balance and NEP-141 token balances that the user is fully entitled to move.

This mirrors the `CollateralJoin` bug exactly: a boolean "must-be-clear" guard is flipped by a legitimate operation, the guard can end up stuck in the "blocked" state through a code path other than deliberate admin action, and the single gate that checks it (`live == 1` there, `!has_in_flight_tx` here) has no recovery path once tripped, permanently locking funds that are otherwise validly owned by the user.

### Impact Explanation
An ETH-implicit account cannot have a full-access key added and cannot be deleted (per `docs/DataStructures/Account.md`), so `rlp_execute` is the *only* way to move funds out of it. If `has_in_flight_tx` gets stuck at `true`, all NEAR and any NEP-141/other token balances held by that specific ETH-implicit account become permanently frozen — a genuine, irrecoverable freezing-of-funds condition for that account, matching the "user funds may get locked" bug class in the report.

### Likelihood Explanation
Triggering this requires a callback receipt (`rlp_execute_callback`/`address_check_callback`/`nep_141_storage_balance_callback`) to fail *after* the `has_in_flight_tx = false` line executes in memory but before the receipt commits successfully — for example by exhausting the small fixed static gas budget during a heavier callback path (e.g., building a chained `storage_deposit` + transfer promise, or issuing a refund transfer) or via any other panic in that segment of code. I was not able to fully confirm from static reading alone that the current constant gas budgets (5/10/15 Tgas) are provably insufficient in a concrete scenario, nor enumerate every internal panic site in `action_to_promise`/`near_action` construction, due to remaining tool-call budget. This is the main uncertainty in this finding, and it should be validated with gas-accounting analysis or fuzzing of the callback paths (particularly cases that chain multiple cross-contract calls, e.g. NEP-141 transfers requiring `storage_deposit`).

### Recommendation
Make the "clear the in-flight guard" step failure-tolerant / order-independent from the rest of the callback logic:
- Reset `has_in_flight_tx = false` using a mechanism that cannot be undone by a later panic in the same receipt (e.g., perform the flag write as the very last state-changing operation, or use `env::promise_batch_then`/a guaranteed low-gas "finally" callback dedicated solely to clearing the flag).
- Alternatively/additionally, size callback gas budgets defensively (with margin) rather than fixed minimal constants, and add regression tests that force an out-of-gas failure partway through each callback to assert `has_in_flight_tx` returns to `false` on the next block/receipt.
- Consider adding a self-healing recovery path (e.g., a timeout-based mechanism allowing the owner to clear a stuck flag after N blocks with no pending promise) as defense in depth, analogous to how the `CollateralJoin` report recommended making `cage` reversible.

### Proof of Concept
Conceptual (not executed, due to tool constraints):
1. Create an ETH-implicit account and fund it with NEAR/NEP-141 tokens via the `WalletContract`.
2. Submit an `rlp_execute` transaction whose emulated action requires the heavier callback path — e.g., an NEP-20/ERC-20-style transfer to an unregistered receiver, which chains `storage_deposit` + the transfer inside `nep_141_storage_balance_callback` before calling `rlp_execute_callback`: [7](#0-6) 
3. Attach exactly enough prepaid gas so that after the first cross-contract hop, the remaining allocation for `nep_141_storage_balance_callback` (bounded by `NEP_141_STORAGE_BALANCE_CALLBACK_GAS`) is insufficient to complete the branch that builds the chained promise and calls `.then(...)`, causing an out-of-gas failure inside that callback after `self.has_in_flight_tx = false;` has already executed in memory.
4. Because the whole receipt fails, its state changes roll back, and `has_in_flight_tx` reverts to (remains) `true` on-chain.
5. The account owner now calls `rlp_execute` again with a legitimate, simple transfer; the call is rejected immediately by the `has_in_flight_tx` guard, and remains rejected forever, since only the contract's own `#[private]` callbacks can clear the flag and none will ever run again.
