Audit Report

## Title
Global per-block `MaxMessagesPerBlock` cap in Snowbridge's outbound queue lets a low-cost sender monopolize the entire bridge's outbound slot and stall all other channels' Ethereum-bound messages - (File: bridges/snowbridge/pallets/outbound-queue/src/lib.rs)

## Summary
The Snowbridge outbound-queue pallet gates commitment of Ethereum-bound messages behind a single, pallet-wide `MessageLeaves` counter shared by every channel; `do_process_message` yields for any channel's message once `MessageLeaves::<T>::decode_len()` reaches `T::MaxMessagesPerBlock::get()` regardless of which channel is being serviced. This is confirmed directly in the pallet code: the acceptance check is performed before any channel-specific state (`Nonce`, keyed by `ChannelId`) is touched, and the check itself has no channel scoping.

## Finding Description
`do_process_message` enforces the cap purely against the global `MessageLeaves` storage value before decoding or inspecting `queued_message.channel_id`: [1](#0-0) 

`MessageLeaves` is an unbounded, un-keyed `StorageValue` reset only once per block in `on_initialize`, shared by every channel using the bridge: [2](#0-1) 

The only per-channel state is `Nonce`, which is unrelated to the acceptance gate and is only mutated after the global check already passed: [3](#0-2) [4](#0-3) 

On the `pallet-message-queue` side, a channel corresponds to a distinct queue/origin (`AggregateMessageOrigin::Snowbridge(ChannelId)`). `service_queue` drains a given origin's ready pages in a `while` loop until weight is exhausted or a page returns `Bailed`/`NoProgress`, only then moving to the next origin in the ready ring: [5](#0-4) 

A `ProcessMessageError::Yield` from `do_process_message` maps to `MessageExecutionStatus::Unprocessable { permanent: false }`, which is treated as `NoProgress` and causes `service_page`/`service_queue` to stop advancing that origin's queue for the remainder of the servicing call: [6](#0-5) 

Because `service_queue` fully drains one origin's ready pages before yielding control to the next origin in the ready ring, and the `MessageLeaves` cap is checked globally rather than per-origin, an origin with many queued (cheap) messages queued ahead of others in the ready ring can consume the entire `MaxMessagesPerBlock` budget for the block before any other channel's queue is serviced at all. The actual configured cap in production runtimes is small: `MaxMessagesPerBlock = ConstU32<32>` in both `bridge-hub-rococo` and `bridge-hub-westend`: [7](#0-6) [8](#0-7) 

This confirms the core structural claim: the acceptance gate is genuinely global/un-keyed by channel, the existing per-channel `Nonce` state does not provide any isolation for the scarce per-block budget, and the tests explicitly document this yield-on-exhaustion behavior without any per-channel fairness mechanism: [9](#0-8) 

Existing mitigations that reduce (but do not eliminate) the practical severity of this design:
- Every outbound message requires payment of an upfront delivery fee computed from `WeightToFee` and `PricingParameters` (gas price, reward, exchange rate), documented and implemented in `calculate_fee`/`calculate_local_fee`: [10](#0-9) 
This fee is a flat, per-message cost based on weight and Ethereum gas/reward parameters — it is *not* a congestion-based fee that scales with how full the shared `MaxMessagesPerBlock` budget is, so it does not inherently deter an attacker willing to pay the flat per-message fee repeatedly to occupy all 32 slots each block.
- `validate` in `send_message_impl.rs` requires the sender's channel to be registered (`T::Channels::contains`), but does not restrict how many messages a given channel can inject relative to `MaxMessagesPerBlock`: [11](#0-10) 

I was unable to fully trace the exact fee amount an attacker would pay per message in the live `bridge-hub-westend`/`bridge-hub-rococo` `PricingParameters` configuration to quantify precisely how cheap sustained spam is, since those parameters are set by governance and can change at runtime; this is consistent with the original claim's own acknowledgment of this limitation.

## Impact Explanation
This matches the "public underpriced work that degrades block production or stalls bridge processing" impact category. Any unprivileged, registered channel (i.e., any sibling parachain able to route XCM exports through BridgeHub, or any account able to trigger the system pallet's governance channel messages within the same shared quota) can pay the flat per-message fee repeatedly to occupy the entire `MaxMessagesPerBlock = 32` budget, since the acceptance check `MessageLeaves::<T>::decode_len().unwrap_or(0) < T::MaxMessagesPerBlock::get()` at [12](#0-11)  has no per-channel keying, and `pallet-message-queue`'s `service_queue` fully drains one origin before moving to the next, so the attacker's channel does not need to interleave with the victim's to dominate the shared budget. This can repeatedly delay commitment (and thus relayer delivery to Ethereum) of legitimate cross-chain messages from other channels for as long as the spam continues.

## Likelihood Explanation
Feasibility depends on the flat delivery fee versus the value of occupying a scarce global slot; because the fee formula (`calculate_fee`) is not congestion-priced and is governance-set rather than dynamically scaled to slot scarcity, an attacker paying the going per-message fee (which is proportional to weight/gas cost, not to how contested the shared per-block quota is) can realistically flood 32 slots per block indefinitely as long as they're willing to pay that flat per-message cost repeatedly. The exact economic cost in current live `PricingParameters` values could not be confirmed from this index, but the structural absence of per-channel isolation and the confirmed drain-one-origin-before-next behavior of `pallet-message-queue` support the claim's mechanism.

## Recommendation
- Scope the per-block acceptance budget per channel (e.g., track `MessageLeaves` count keyed by `ChannelId`, with either a per-channel sub-quota of `MaxMessagesPerBlock` or a fair-queuing/weighted round-robin scheme across channels) so no single channel can exhaust the shared budget for all others.
- Alternatively, apply congestion-based fee scaling so that consuming a larger share of the scarce global per-block slot costs proportionally more, discouraging monopolization by a single low-value sender.

## Proof of Concept
1. At block start, `MessageLeaves` is empty (`on_initialize` kills it).
2. An attacker-controlled sibling parachain channel enqueues ≥32 cheap outbound messages ahead of the victim's channel in the `pallet-message-queue` ready ring (e.g. by having its queue populated earlier that block).
3. `service_queue` for the attacker's origin drains its ready pages in the `while` loop at `substrate/frame/message-queue/src/lib.rs:1241-1252`, each message calling `do_process_message`, which increments the shared `MessageLeaves` counter until it reaches `T::MaxMessagesPerBlock::get()` (32 in `bridge-hub-westend`/`bridge-hub-rococo`).
4. When the victim's channel is serviced afterward in the same block, `do_process_message` immediately returns `Yield` due to the exhausted global counter check at `bridges/snowbridge/pallets/outbound-queue/src/lib.rs:309-313`, causing `NoProgress`/`Unprocessable{permanent:false}` and deferring the victim's message.
5. Repeating steps 1–4 every subsequent block (attacker refills the quota immediately after `on_initialize`) perpetually stalls the victim's legitimate transfer, matching the existing unit test `process_message_yields_on_max_messages_per_block` at `bridges/snowbridge/pallets/outbound-queue/src/test.rs:74-101`, which confirms the yield-on-exhaustion behavior with no per-channel isolation.

		/// remote destination. See module-level documentation for more details.
		pub(crate) fn calculate_fee(
			gas_used_at_most: u64,
			params: PricingParameters<T::Balance>,
		) -> Fee<T::Balance> {
			// Remote fee in ether
			let fee = Self::calculate_remote_fee(
				gas_used_at_most,
				params.fee_per_gas,
				params.rewards.remote,
			);

			// downcast to u128
			let fee: u128 = fee.try_into().defensive_unwrap_or(u128::MAX);

			// multiply by multiplier and convert to local currency
			let fee = FixedU128::from_inner(fee)
				.saturating_mul(params.multiplier)
				.checked_div(&params.exchange_rate)
				.expect("exchange rate is not zero; qed")
				.into_inner();

			// adjust fixed point to match local currency
			let fee = Self::convert_from_ether_decimals(fee);

			Fee::from((Self::calculate_local_fee(), fee))
		}

		/// Calculate fee in remote currency for dispatching a message on Ethereum
		pub(crate) fn calculate_remote_fee(
			gas_used_at_most: u64,
			fee_per_gas: U256,
			reward: U256,
		) -> U256 {
			fee_per_gas.saturating_mul(gas_used_at_most.into()).saturating_add(reward)
		}

		/// The local component of the message processing fees in native currency
		pub(crate) fn calculate_local_fee() -> T::Balance {
			T::WeightToFee::weight_to_fee(
				&T::WeightInfo::do_process_message().saturating_add(T::WeightInfo::commit_single()),
			)
		}

	fn validate(
		message: &Message,
	) -> Result<(Self::Ticket, Fee<<Self as SendMessageFeeProvider>::Balance>), SendError> {
		// The inner payload should not be too large
		let payload = message.command.abi_encode();
		ensure!(
			payload.len() < T::MaxMessagePayloadSize::get() as usize,
			SendError::MessageTooLarge
		);

		// Ensure there is a registered channel we can transmit this message on
		ensure!(T::Channels::contains(&message.channel_id), SendError::InvalidChannel);

		// Generate a unique message id unless one is provided
		let message_id: H256 = message
			.id
			.unwrap_or_else(|| unique((message.channel_id, &message.command)).into());

		let gas_used_at_most = T::GasMeter::maximum_gas_used_at_most(&message.command);
		let fee = Self::calculate_fee(gas_used_at_most, T::PricingParameters::get());

		let queued_message: VersionedQueuedMessage = QueuedMessage {
			id: message_id,
			channel_id: message.channel_id,
			command: message.command.clone(),
		}
		.into();
		// The whole message should not be too large
		let encoded = queued_message.encode().try_into().map_err(|_| SendError::MessageTooLarge)?;

		let ticket = Ticket { message_id, channel_id: message.channel_id, message: encoded };

		Ok((ticket, fee))
	}
