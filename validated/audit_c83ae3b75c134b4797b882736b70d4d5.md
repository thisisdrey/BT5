### Title
Fee bypass via TokenDiff delta-splitting on NEP-245/IMT tokens - ([File: contracts/defuse/core/src/intents/token_diff.rs])

### Summary
`TokenDiff::token_fee` waives the protocol fee whenever the *per-intent* absolute delta on a NEP-245 (or IMT) token is `<= 1`, and `TokenDiff::execute_intent` computes/collects the fee independently for each `TokenDiff` intent it processes, with no aggregation across intents in the same batch. An unprivileged party can therefore split one intended `-1000` NEP-245 delta into 1000 separately signed `TokenDiff` intents, each carrying `delta == -1` on the same `Nep245TokenId`, causing every leg to be classified as fee-exempt and the entire 1000-unit volume to settle with zero fee credited to `fee_collector`.

### Finding Description
The broken binding: for a genuine 1000-unit NEP-245 outflow, the protocol expects
`fee_collected == Pips::fee_ceil(protocol_fee, 1000)` (a nonzero amount when `fee = Pips::ONE_PERCENT`),
but the actual code computes
`fee_collected == sum_{i=1..1000}(Pips::fee_ceil(TokenDiff::token_fee(token_id, 1, fee), 1)) == 0`.

Root cause is in `TokenDiff::token_fee`: [1](#0-0) 
which returns `Pips::ZERO` whenever a NEP-245/IMT leg's absolute amount is `<= 1`, intended to avoid meaningless fractional fees on atomic MT items. This exemption is applied inside `TokenDiff::execute_intent`, per intent, per token entry: [2](#0-1) 
There is no cross-intent aggregation of the same signer's deltas on the same token before the fee is derived — each signed `TokenDiff` intent independently applies its delta via `internal_apply_deltas` and independently computes its own fee.

The batch-level invariant enforced by `TransferMatcher::finalize` only checks that all deltas across the batch net to zero (balance conservation), it performs no fee validation: [3](#0-2) 

Exploit flow: the attacker (or two colluding attacker-controlled accounts, e.g. mirroring a normal swap) signs 1000 distinct `TokenDiff` payloads, each with a unique nonce and a diff map `{ nep245_token_id: -1 }` (matched on the counterparty side by 1000 legs of `+1`, or any other token legs needed to keep the aggregate zero-sum). All 1000 payloads are submitted in one `execute_intents` (or split across several calls — repeatable). Each leg passes `token_fee` returning `Pips::ZERO` because `amount == 1` is not `> 1` for `TokenIdType::Nep245`. No existing guard (`MultiPayload::verify`, nonce checks, `TransferMatcher::finalize`) inspects the *aggregate* magnitude of same-token deltas belonging to the same signer, so the fee-exemption designed for atomic 1-unit MT transfers is trivially reusable to launder arbitrarily large fungible-style MT volumes fee-free.

### Impact Explanation
This under-collects protocol fees owed to `fee_collector` on MT-denominated (NEP-245/IMT) swap volume — exactly the "protocol fees bypassed or over-collected" Critical category. Any unprivileged solver/user pair can repeat this for any NEP-245 token and any volume, splitting into as many 1-unit legs as gas/nonce budget allows per transaction, and repeating across transactions to launder unbounded volume. No victim signature is forged and no balances are stolen from other users' accounts, but expected protocol revenue is systematically diverted away from `fee_collector`.

### Likelihood Explanation
Preconditions are minimal: any account with an NEP-245 (or IMT) balance in the Verifier, and a nonzero `fee` configured, i.e. exactly the default expected operating mode. No role, no relayer key, no DAO action, and no counterparty cooperation beyond ordinary swap counterparties who would sign matching legs anyway. Attacker cost is just extra nonce/message signing and gas for more intents per call (or spreading across multiple calls) — fully within an ordinary unprivileged user's capability. This is highly likely and easily automatable by any solver wanting to save on fees for MT-token flow.

### Recommendation
Aggregate per-signer, per-token deltas across the whole batch (or at least detect repeated identical-token legs from the same signer within one `execute_intents` call) before applying the `amount <= 1` NEP-245/IMT fee exemption, so the exemption only applies to genuinely atomic single-unit transfers rather than to fee computed on a per-leg basis that can be fragmented arbitrarily. Alternatively, compute/accumulate the total negative delta per `(signer, token_id)` across the whole `Deltas`/`TransferMatcher` state before invoking `token_fee`, so `fee_ceil` is applied over the true aggregate amount.

### Proof of Concept
`cargo test` (near-workspaces sandbox) plan:
1. Configure `env` with `fee = Pips::ONE_PERCENT`, create solver + counterparty accounts, deposit an NEP-245 (MT) balance of `>= 1000` units to solver.
2. Case A ("split"): sign 1000 `TokenDiff` intents, each `diff = { mt_token: -1 }` from solver, matched by counterparty legs of `+1` (or equivalent zero-net batch); submit all in one `execute_intents`.
3. Case B ("single"): sign one `TokenDiff` intent `diff = { mt_token: -1000 }` from solver matched by counterparty `+1000`; submit via `execute_intents`.
4. Assert: `fee_collector` MT balance after Case A `== 0`, while `fee_collector` MT balance after Case B `== Pips::ONE_PERCENT.fee_ceil(1000) > 0` — demonstrating the fee-bypass equality divergence (`sum(fee_ceil(1))*1000 == 0 != fee_ceil(1000)`).

    // If unmatched deltas overflow, then Err(None) is returned.
    pub fn finalize(self) -> Result<Transfers, InvariantViolated> {
        let mut transfers = Transfers::default();
        let mut deltas = TokenDeltas::default();
        for (token_id, transfer_matcher) in self.0 {
            if let Err(unmatched) = transfer_matcher.finalize_into(&token_id, &mut transfers)
                && (unmatched == 0 || deltas.apply_delta(token_id, unmatched).is_none())
            {
                return Err(InvariantViolated::Overflow);
            }
        }
        if !deltas.is_empty() {
            return Err(InvariantViolated::UnmatchedDeltas {
                unmatched_deltas: deltas,
            });
        }
        Ok(transfers)
    }
