### Title
Fee-on-transfer / non-compliant NEP-141 tokens cause internal ledger to be credited beyond actual custody in `ft_on_transfer` - (File: contracts/defuse/src/contract/tokens/nep141/deposit.rs)

### Summary
`Contract::ft_on_transfer` credits the internal multi-token ledger with the `amount` parameter reported by the calling token contract, without ever verifying that the same amount of tokens is actually held by the Defuse contract. For any NEP-141 token whose transfer semantics deduct a fee (or otherwise deliver less value than the nominal `amount` argument passed into the receiver hook), this creates a permanent gap between the sum of internally recorded balances (`owner.token_balances`, `total_supplies`) and the token's real balance held by the contract.

### Finding Description
`ft_on_transfer` unconditionally trusts the `amount: U128` argument supplied by the predecessor token contract and immediately calls `self.deposit(receiver_id, [(token_id, amount.0)], ...)`, which increments both the depositor's `token_balances` entry and the global `total_supplies` entry for that `TokenId`: [1](#0-0) 

`Contract::deposit` itself performs no external balance check; it purely mutates internal accounting based on the `amount` it is given: [2](#0-1) 

For a compliant, fee-free NEP-141 token, the standard guarantees that `amount` equals what the token contract itself moved from sender to receiver's ledger entry, so this trust is normally safe. However, Defuse is explicitly designed to accept *any* NEP-141 contract id as a `Nep141TokenId` — there is no allow-list or verification that the token conforms strictly to a 1:1, fee-free transfer model. If a token contract's `ft_transfer_call` implementation deducts a fee (or otherwise credits the receiver with less than the nominal `amount` it reports to `ft_on_transfer`), Defuse will still credit the depositor's account, and the global `total_supplies[token_id]`, with the full nominal `amount`, while its actual on-chain token balance for that `token_id` only increases by `amount - fee`.

This breaks the binding: `sum(internal ledger balances for token_id) == actual token balance held by Defuse for token_id`. The same unguarded pattern exists in the NFT and multi-token deposit hooks as well (`nft_on_transfer`, `mt_on_transfer`), which likewise credit the reported amount/count without any custody check: [3](#0-2) [4](#0-3) 

### Impact Explanation
Once the ledger is inflated relative to real custody, any account holding a credited-but-unbacked balance can withdraw via `ft_withdraw`, pulling real tokens out of the contract that were never actually deposited by them. Because `total_supplies` and per-account balances are all inflated identically, the first withdrawer(s) for that token can extract more real tokens than the contract holds, at the expense of other depositors/holders of the same `token_id`, whose later withdrawals will fail or be short — i.e., funds become permanently frozen/unavailable for the remaining, honest holders of that token. This is a "value debited versus value delivered" conservation break with concrete value loss to other users of the same token pool, satisfying the Critical impact bar (funds credited without valid backing / funds permanently frozen for other holders).

### Likelihood Explanation
Likelihood depends entirely on an attacker choosing to deposit a token whose NEP-141 implementation is not a pure 1:1 fee-free transfer (e.g., a fee-on-transfer or rebasing NEP-141 token). Since Defuse imposes no restriction on which NEP-141 contracts can call `ft_on_transfer`, any unprivileged user can deploy or use such a token and immediately create the described ledger/custody mismatch — no privileged role, relayer, or victim key is required.

### Recommendation
Before crediting the internal ledger in `ft_on_transfer` (and analogously in `mt_on_transfer`/`nft_on_transfer` where applicable), measure the actual balance delta held by the contract for that token (e.g., compare `ft_balance_of(current_account_id)` before and after the transfer, or otherwise use the smaller of the reported `amount` and the balance actually gained) rather than trusting the caller-supplied `amount` outright, and credit only the amount actually received.

### Proof of Concept
1. Deploy a custom NEP-141 token contract whose `ft_transfer_call` deducts a fee: it decreases the sender's balance by `amount`, but increases the receiver's (Defuse's) recorded balance by only `amount - fee`, then calls `ft_on_transfer(sender_id, U128(amount), msg)` with the full nominal `amount`.
2. Attacker calls `ft_transfer_call` on this token targeting Defuse with `amount = 1000`, `fee = 100`. Defuse's actual token holdings increase by 900, but `ft_on_transfer` credits the attacker's internal balance (and `total_supplies`) with 1000 via `self.deposit(...)` in `contracts/defuse/src/contract/tokens/nep141/deposit.rs:38-43`.
3. Attacker signs and executes an `FtWithdraw` intent for 1000 of that `token_id`. Defuse attempts to withdraw 1000 real tokens even though it only ever received 900, draining 100 units of value that belongs to other depositors' recorded balances of the same `token_id` (or leaving later withdrawers of that token permanently unable to fully withdraw).

    fn ft_on_transfer(
        &mut self,
        sender_id: AccountId,
        amount: U128,
        msg: String,
    ) -> PromiseOrValue<U128> {
        require!(amount.0 > 0, "zero amount");

        let token_id = TokenId::Nep141(Nep141TokenId::new(env::predecessor_account_id()));

        let DepositMessage {
            receiver_id,
            action,
        } = if msg.is_empty() {
            DepositMessage::new(sender_id.clone())
        } else {
            msg.parse().unwrap_or_else(|e| panic!("{e}"))
        };

        self.deposit(
            receiver_id.clone(),
            [(token_id.clone(), amount.0)],
            Some("deposit"),
        )
        .unwrap_or_else(|err| err.panic());

impl Contract {
    pub(crate) fn deposit(
        &mut self,
        owner_id: AccountId,
        tokens: impl IntoIterator<Item = (TokenId, u128)>,
        memo: Option<&str>,
    ) -> Result<()> {
        let owner = self
            .storage
            .accounts
            .get_or_create(owner_id.clone())
            // deposits are allowed for locked accounts
            .as_inner_unchecked_mut();

        let mut mint_event = MtMintEvent {
            owner_id: owner_id.into(),
            token_ids: Vec::new().into(),
            amounts: Vec::new().into(),
            memo: memo.map(Into::into),
        };

        for (token_id, amount) in tokens {
            if amount == 0 {
                return Err(DefuseError::InvalidIntent);
            }

            mint_event.token_ids.to_mut().push(token_id.to_string());
            mint_event.amounts.to_mut().push(amount);

            let total_supply = self
                .storage
                .state
                .total_supplies
                .add(token_id.clone(), amount)
                .ok_or(DefuseError::BalanceOverflow)?;
            match token_id {
                TokenId::Nep171(ref tid) => {
                    if total_supply > 1 {
                        return Err(DefuseError::NftAlreadyDeposited(tid.clone()));
                    }
                }
                TokenId::Nep141(_) | TokenId::Nep245(_) | TokenId::Imt(_) => {}
            }

            owner
                .token_balances
                .add(token_id, amount)
                .ok_or(DefuseError::BalanceOverflow)?;
        }
