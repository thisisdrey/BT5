### Title
Users cannot repay/deposit to escape liquidation when their collateral token is frozen/paused, while liquidation proceeds unaffected - (File: programs/marginfi/src/instructions/marginfi_account/liquidate.rs)

### Summary
Classic liquidation (`lending_account_liquidate`) never moves tokens into or out of the liquidatee's own token account — it only mutates internal share balances and performs one PDA-to-PDA SPL transfer (bank liquidity vault → bank insurance vault). By contrast, the user-controlled ways to prevent liquidation — `deposit` (add collateral) and `repay` (pay down debt) — require a real SPL transfer *from the user's own token account*. If that token account (or the entire mint) is frozen/paused at the SPL-token level (e.g., a Circle-style freeze on a USDC associated token account, or a Token-2022 mint with a pausable/permanent-delegate extension), the user's `deposit`/`repay` calls will revert, but the liquidator can still liquidate the position without interruption.

### Finding Description
In `lending_account_liquidate`, the only bank-state checks performed are `validate_bank_state(..., InstructionKind::FailsInPausedState)` against `asset_bank`/`liab_bank`, which check the *marginfi-controlled* `BankOperationalState` (admin-set Paused/ReduceOnly/etc.), not the underlying SPL mint's freeze state: [1](#0-0) 

The actual liquidation accounting only manipulates internal shares via `BankAccountWrapper` (`withdraw_ignore_borrow_cap`, `deposit_ignore_deposit_cap`, `repay`) for both the liquidator and liquidatee legs — no SPL transfer touches either party's personal wallet: [2](#0-1) [3](#0-2) 

The single real SPL transfer in the whole instruction moves the insurance fee between two protocol-owned vault PDAs (`bank_liquidity_vault` → `bank_insurance_vault`), never touching a user-owned account: [4](#0-3) 

Meanwhile, `deposit` and `repay` (the user's only defenses against liquidation) require a genuine SPL transfer from the user's own token account into the bank's liquidity vault — this is corroborated by the codebase's own admission that liquidators/users "cannot deposit fresh funds ... or repay their debts" during disruptions, while liquidations continue unaffected: [5](#0-4) 

This is the exact bug class from the GMX report: liquidation is a pure internal-accounting operation that can never be blocked by a frozen/paused collateral token, while the user-facing remediation paths (`deposit`, `repay`) are real token transfers that a frozen account or paused mint can block.

### Impact Explanation
A user holding a mint with freeze authority (e.g., USDC, PYUSD, or any Token-2022 mint using the `PermanentDelegate`/pausable-style extensions supported by this codebase, cf. `T22WithFee` bank fixtures) who becomes subject to an account freeze (compliance action, mint-level pause, etc.) loses all ability to top up collateral or repay debt to stay above the liquidation threshold. The liquidator, however, is completely unaffected because the liquidation instruction never attempts to move tokens into/out of the liquidatee's wallet — it operates purely on internal shares plus a vault-to-vault SPL transfer. The liquidatee is therefore liquidated (losing discounted collateral to the liquidator and paying liquidation + insurance fees) with no avenue to prevent it, even though they would otherwise have been able to save the position by depositing/repaying.

### Likelihood Explanation
This requires an external condition (freeze of the specific collateral token account, or a token-level pause) that is outside marginfi's control, similar to the original GMX report's premise. It is a rare-but-real risk given marginfi explicitly supports USDC, PyUSD, and Token-2022 mints with freeze/permanent-delegate/transfer-fee extensions as first-class collateral/liability assets. No privileged action or misconfiguration by marginfi is required — only a normal, permissionless liquidation call against an already-unhealthy account whose owner cannot use `deposit`/`repay` due to a frozen token account.

### Recommendation
Consider one or more of:
1. Allow a "tokenless" self-service repayment/top-up path (similar to the existing `TOKENLESS_REPAYMENTS_ALLOWED` risk-admin mechanism) that a user (not just the risk admin) could trigger in narrowly-scoped emergency conditions, or
2. Document this as an accepted risk (consistent with the GMX sponsor's own stance that forcing a transfer on liquidation is not worth the added complexity), explicitly noting that frozen/paused collateral tokens can prevent a user from defending their position even though liquidation itself is unaffected, and
3. For admin-known freeze events, provide fast-response guidance to place the affected bank into `Paused` state (which does block liquidation per `validate_bank_state`) as a mitigation once a freeze is discovered.

### Proof of Concept
1. User A deposits USDC as collateral and borrows SOL, becoming a normal marginfi position.
2. USDC issuer freezes User A's specific associated token account (a legitimate, real-world SPL Token capability, independent of marginfi).
3. SOL price rises / USDC price context changes such that User A's position becomes eligible for liquidation.
4. User A attempts `lending_account_deposit` or `lending_account_repay` using their frozen USDC token account — the SPL `transfer` call inside these instructions reverts because the source account is frozen.
5. A liquidator calls `lending_account_liquidate` targeting User A's account. This instruction performs no SPL transfer touching User A's wallet (only internal share updates plus a vault-to-vault insurance-fee transfer), so it succeeds normally, seizing User A's collateral shares and repaying the debt at the liquidation discount — despite User A having had no way to prevent it.
