Audit Report

## Title
Unbacked relayer reward: `relayer_fee` is a self-declared field trusted without any cross-check against transferred value - (File: bridges/snowbridge/pallets/inbound-queue-v2/src/lib.rs)

## Summary
`Message::try_from` decodes `relayer_fee` directly from the untrusted `OutboundMessageAccepted` Ethereum event payload, and `Pallet::process_message` unconditionally credits this value to the submitting relayer via `T::RewardPayment::register_reward`, with no check that `relayer_fee` bears any relationship to `message.value` or any other economically-bound quantity moved through the bridge in the same message.

## Finding Description
`Message::try_from` decodes `relayer_fee` straight out of `event_payload.relayerFee`, an attacker-controlled field emitted by whoever calls the Ethereum Gateway contract, with no validation against `value` or `execution_fee`: [1](#0-0) 

`Pallet::process_message` verifies the gateway address and nonce (replay protection), dispatches the message via `T::MessageProcessor`, and then pays out the reward using `relayer_fee` taken verbatim from the decoded message, summed with any pre-registered tip — with no check whatsoever relating `relayer_fee` to `message.value` or to any amount actually reserved for the message: [2](#0-1) 

The `RewardLedger::register_reward` call does not mint or transfer funds directly; it registers a claim in the `RelayerRewards` storage map of `pallet-bridge-relayers`, which is later paid out via `PaymentProcedure::pay_reward` by transferring from a "rewards account" (a sovereign account derived from `RewardsAccountParams`) to the relayer: [3](#0-2) [4](#0-3) 

Because `relayer_fee` is never bounded relative to `message.value`/`execution_fee`, and because the reward is settled against a shared rewards-account balance rather than a per-message escrowed amount, an attacker who controls the Ethereum-side call to the Gateway (an unprivileged, ordinary bridge user) can set an arbitrarily large `relayerFee` in the event payload while transferring only a minimal `value`. Once any honest relayer submits a valid receipt/beacon proof of that event (the normal, expected relaying flow), the pallet registers the full inflated fee as a claimable reward. The beacon/receipt verification (`T::Verifier::verify`) only proves the authenticity of the log — it does not, and cannot, constrain what the emitting contract chose to put in the `relayerFee` field. I was not able to fully determine within the available index whether the on-chain Solidity Gateway contract (off-repo/out of scope for this Substrate-side review) enforces `msg.value >= relayerFee + executionFee + Σassets`; if it does not, this defect allows draining the shared rewards-account pot (funded to cover legitimate rewards for other messages) using an artificially inflated, self-declared fee field, unrelated to the actual value bridged in that message.

## Impact Explanation
This matches the "theft or unbacked mint or unlock" / "runtime bugs that compromise intended behavior" impact category: the reward-registration logic in `Pallet::process_message` credits a relayer with an amount (`relayer_fee`) that is completely decoupled from any actual value moved through the bridge for that message, allowing drainage of the shared bridge rewards account beyond what is economically justified by the message being relayed.

## Likelihood Explanation
The attack requires no privileged role, validator collusion, or relayer misbehavior — it needs only an ordinary Ethereum account able to call the public Gateway contract methods, plus a normal, honest relayer performing the expected, intended relaying action. The Substrate-side pallet code provides no defense-in-depth check tying `relayer_fee` to `message.value`, `execution_fee`, or any reserved amount, so exploitability is fully determined by the Solidity Gateway's (off-repo) enforcement of the invariant, which cannot be verified from this repository's Rust code alone.

## Recommendation
In `Pallet::process_message` (or in the message-to-XCM converter, which already has access to `message.value` and `message.execution_fee`), enforce that `relayer_fee` cannot exceed the value actually reserved/deposited for the message (e.g., cap `relayer_fee` at `message.value`, or require an explicitly reserved fee bucket that is asset-backed). Do not treat `relayer_fee` as trusted purely because the containing log passed beacon/receipt verification, since that verification proves authenticity of the log, not economic soundness of its self-declared fields.

## Proof of Concept
1. On Ethereum, call the Gateway's `v2_sendMessage` with a minimal `value` but an arbitrarily large `relayerFee`.
2. Any relayer submits `Pallet::submit` with a valid receipt/beacon proof for the resulting event; `T::Verifier::verify` succeeds because the log is authentic.
3. `Message::try_from` decodes `relayer_fee` from the payload verbatim: [1](#0-0) 
4. `process_message` registers the full inflated `relayer_fee` as a reward with no check against `message.value`: [5](#0-4) 
5. Existing unit tests confirm `relayer_fee` is paid out exactly as supplied regardless of `value`: [6](#0-5)

		pub fn process_message(relayer: T::AccountId, message: Message) -> DispatchResult {
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == message.gateway, Error::<T>::InvalidGateway);

			let (nonce, relayer_fee) = (message.nonce, message.relayer_fee);

			// Verify the message has not been processed
			ensure!(!Nonce::<T>::get(nonce), Error::<T>::InvalidNonce);

			// Mark message as received
			Nonce::<T>::set(nonce);

			let message_id = T::MessageProcessor::process_message(relayer.clone(), message)
				.map_err(|e| match e {
					MessageProcessorError::ProcessMessage(e) => e,
					MessageProcessorError::ConvertMessage(e) => Error::<T>::from(e).into(),
					MessageProcessorError::SendMessage(e) => Error::<T>::from(e).into(),
				})?;

			// Pay relayer reward
			let tip = Tips::<T>::take(nonce).unwrap_or_default();
			let total_tip = relayer_fee.saturating_add(tip);
			if total_tip > 0 {
				T::RewardPayment::register_reward(&relayer, T::DefaultRewardKind::get(), total_tip);
			}

/// Reward payment procedure that executes a `balances::transfer` call from the account
/// derived from the given `RewardsAccountParams` to the relayer or an alternative beneficiary.
pub struct PayRewardFromAccount<T, Relayer, LaneId, RewardBalance>(
	PhantomData<(T, Relayer, LaneId, RewardBalance)>,
);

impl<T, Relayer, LaneId, RewardBalance> PayRewardFromAccount<T, Relayer, LaneId, RewardBalance>
where
	Relayer: Decode + Encode,
	LaneId: Decode + Encode,
{
	/// Return account that pays rewards based on the provided parameters.
	pub fn rewards_account(params: RewardsAccountParams<LaneId>) -> Relayer {
		params.into_sub_account_truncating(b"rewards-account")
	}
}

impl<T, Relayer, LaneId, RewardBalance>
	PaymentProcedure<Relayer, RewardsAccountParams<LaneId>, RewardBalance>
	for PayRewardFromAccount<T, Relayer, LaneId, RewardBalance>
where
	T: frame_support::traits::fungible::Mutate<Relayer>,
	T::Balance: From<RewardBalance>,
	Relayer: Clone + Debug + Decode + Encode + Eq + TypeInfo,
	LaneId: Decode + Encode,
{
	type Error = sp_runtime::DispatchError;
	type Beneficiary = Relayer;

	fn pay_reward(
		_: &Relayer,
		reward_kind: RewardsAccountParams<LaneId>,
		reward: RewardBalance,
		beneficiary: Self::Beneficiary,
	) -> Result<(), Self::Error> {
		T::transfer(
			&Self::rewards_account(reward_kind),
			&beneficiary.into(),
			reward.into(),
			Preservation::Expendable,
		)
		.map(drop)
	}
}
