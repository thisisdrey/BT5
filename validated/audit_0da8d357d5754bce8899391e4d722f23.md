Based on the investigation, the strongest analog to CVE-2024-56072 (an attacker-controlled "count" field driving unbounded allocation/iteration and crashing the process) is the `extractBytesArray` / `extractBytes32Array` helper methods used by the `ValidateMultiSign` and `BatchValidateSign` TVM precompiled contracts.

### Title
Unbounded array allocation from attacker-controlled length word in `ValidateMultiSign`/`BatchValidateSign` precompiles causes uncaught crash - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
`ValidateMultiSign.execute()` and `BatchValidateSign.execute()` decode call-data supplied by any account that calls the precompiled contracts at addresses `0x9` and `0xa`. The "signature array length" and "address array length" values are read directly from the caller-supplied `DataWord` at an attacker-chosen offset via `words[offset].intValueSafe()`, and immediately used to allocate a two-dimensional array with `new byte[len][]` in `extractBytesArray`/`extractBytes32Array`, before any bound check against `MAX_SIZE` is enforced.

### Finding Description
`extractBytesArray` reads the count with no upper-bound validation and allocates accordingly: [1](#0-0) 

The `MAX_SIZE` check that is supposed to reject oversized arrays is only applied when `VMConfig.allowTvmSelfdestructRestriction()` is active, and even then it is evaluated on a *different* field read (`words[words[3]...]`) before calling the bounded `extractSigArray` variant. When that config flag is not active, `ValidateMultiSign.execute()` calls the unbounded `extractBytesArray` directly, and the `signatures.length > MAX_SIZE` check happens only **after** the array has already been allocated inside `extractBytesArray`: [2](#0-1) 

Critically, this call to `extractBytesArray` sits **outside** any try/catch block in `ValidateMultiSign.execute()` — the surrounding `try { ... } catch (Throwable t) { ... }` only wraps the later account/permission-weight logic, not the array extraction: [3](#0-2) 

The only gate against a malformed shape is `isValidAbiEncoding`, which merely checks that total calldata length is a multiple of header+item words — it does not validate that embedded length/offset words are consistent with the calldata size: [4](#0-3) 

This means an attacker can craft a small ABI-encoded call whose "length" word at the dynamic-array position is an arbitrarily large 32-byte integer (e.g. close to `Integer.MAX_VALUE`), causing `new byte[len][]` to either throw `NegativeArraySizeException`/`OutOfMemoryError` or consume excessive heap — mirroring the FastNetMon bug class where a crafted "many samples" count field is used without bound checking before allocation, crashing the process.

### Impact Explanation
If this code path is reachable (i.e., `VMConfig.allowTvmSelfdestructRestriction()` is not active for the target network/height), any unprivileged account can send a transaction (`TriggerSmartContract`) that calls the precompiled address `0xa` (`ValidateMultiSign`) with crafted calldata, forcing an uncaught `OutOfMemoryError`/`NegativeArraySizeException` to propagate out of the precompile's `execute()` method during transaction execution/validation by every full node and SR, potentially causing node crash or halted block processing — a network-wide denial of service. `BatchValidateSign` has a similar unbounded read but wraps `doExecute` in a `catch (Throwable t)`, which is more resilient (though repeated OOM attempts can still degrade node health).

### Likelihood Explanation
This is only exploitable on chains/heights where `allowTvmSelfdestructRestriction` (a TIP hard-fork parameter) is not yet active — I was unable to confirm within the available iterations whether this flag defaults to active on the current mainnet configuration in this repository snapshot (`chainbase/src/main/java/org/tron/core/store/DynamicPropertiesStore.java` and `actuator/src/main/java/org/tron/core/utils/ProposalUtil.java` reference it, but activation state depends on runtime chain parameters not fully traced here). If it is already permanently enabled on mainnet, this path is dead code for production TRON but remains live on any private/test/sidechain network still running with the flag off, or during any window before its activation.

### Recommendation
Move the `MAX_SIZE` bound check to validate the raw length word **before** calling `extractBytesArray`/`extractBytes32Array` regardless of `allowTvmSelfdestructRestriction`, and wrap the entire decode-and-extract sequence (not just the later permission logic) in `ValidateMultiSign.execute()` in a `try/catch(Throwable)` that returns `DATA_FALSE` on any decoding failure, consistent with how `BatchValidateSign.execute()` already guards `doExecute`.

### Proof of Concept
1. Build ABI-encoded calldata for `validatemultisign(address,uint256,bytes32,bytes[])` matching the byte-length invariant checked by `isValidAbiEncoding` (header 5 words + N*5 words).
2. At the calldata offset that `words[3].intValueSafe() / WORD_SIZE` resolves to (the `bytes[]` length slot), place a 32-byte word encoding a very large integer (e.g. `0x00000000000000000000000000000000000000000000000000000005F5E100`, ~100,000,000) instead of the true element count.
3. Send this as calldata in a `TriggerSmartContract` transaction targeting precompile address `0x000...a`.
4. `extractBytesArray` executes `new byte[100000000][]`, consuming/exhausting heap before the `MAX_SIZE` check is ever reached, throwing outside the guarding try/catch and propagating up through the node's transaction execution path.

    if (offset > words.length - 1) {
