## Title
`pallet-contracts` (legacy `frame/contracts`) still double-counts storage-deposit accounting on same-contract reentrancy because it never received the `bank_pending_changes` fix applied to `pallet-revive` — (File: `substrate/frame/contracts/src/exec.rs`, `substrate/frame/contracts/src/storage/meter.rs`)

### Summary
The external report's core broken invariant is: a callback triggered mid-operation (`onERC721Received`) is allowed to reenter and mutate shared accounting state *before* the outer operation finishes writing its own pending update, causing the same delta to be counted twice (or once too many/few times) against a global counter. The exact same broken invariant — a nested/reentrant call seeing and mutating a parent's *not-yet-finalized* pending storage diff, followed by the parent re-applying its own already-materialized diff on top — was found and fixed in `pallet-revive` (`prdoc/pr_12267.prdoc`, `substrate/frame/revive/src/metering/storage.rs::bank_pending_changes`, `substrate/frame/revive/src/exec.rs::bank_pending_changes_and_invalidate`). The legacy `pallet-contracts` crate (`substrate/frame/contracts/src/exec.rs`) implements the identical `push_frame` / cache-invalidation / `finalize()` pattern that caused the bug in `pallet-revive` before the fix, but has no equivalent `bank_pending_changes` mechanism.

### Finding Description
In `substrate/frame/contracts/src/exec.rs::push_frame` (lines 909-948), before entering a nested frame the code persists the *current* (parent) `ContractInfo` cache to storage:

```
let frame = self.top_frame();
if let (CachedContract::Cached(contract), ExportedFunction::Call) =
    (&frame.contract_info, frame.entry_point)
{
    <ContractInfoOf<T>>::insert(frame.account_id.clone(), contract.clone());
}
``` [1](#0-0) 

This is the same "preview persist before child executes" primitive that `pallet-revive`'s `push_frame` had before commit `1b9ea1c3656` (PR #10920) introduced pending-diff preview-apply for refund pro-rating, and which caused the parent's still-pending `own_contribution` to be re-applied a second time on top of the reloaded (already-updated) `ContractInfo` in `finalize()` — exactly documented in `prdoc/pr_12267.prdoc`:

> "For `X` writes `K1` → calls itself → writes `K2`: ... The parent's `finalize()` re-applies its still-pending `own_contribution` (which still contains `K1`) on top of the reloaded info → `K1` counted twice." [2](#0-1) 

The fix for `pallet-revive` added `RawMeter::bank_pending_changes` and `Frame::bank_pending_changes_and_invalidate` in `substrate/frame/revive/src/metering/storage.rs` and `substrate/frame/revive/src/exec.rs` (`pop_frame`, line ~1667-1670) specifically to consume the parent's pending diff at the cache-invalidation point so `finalize()` cannot double-apply it: [3](#0-2) [4](#0-3) 

The equivalent `pallet-contracts` code path (`push_frame` inserting the cached `ContractInfo` before descending, `in_memory_changes_not_discarded` test showing the same reload-on-reentry behavior at `substrate/frame/contracts/src/exec.rs:2904-2965`) has no such banking step in its `RawMeter`/`finalize_own_contributions` logic. `finalize_own_contributions` simply calls `self.own_contribution.update_contract(info)` unconditionally with no mechanism to detect that an intervening same-contract reentrant frame already persisted (and consumed) part of that diff. This is precisely the unpatched shape of the bug that was fixed in the sibling `pallet-revive` crate.

### Impact Explanation
Same-contract (or transitive, `X→Y→X`) reentrancy in `pallet-contracts` inflates the persisted `storage_items`, `storage_bytes`, `storage_item_deposit`, and `storage_byte_deposit` fields of `ContractInfo`, and inflates the net storage deposit charged to (or refunded from) the origin — matching the `same_contract_reentry_does_not_double_count_storage` / `transitive_reentry_does_not_double_count_storage` regression scenarios that `pallet-revive` added tests for. This directly corrupts on-chain accounting of a contract's storage deposit obligations: an attacker-controlled contract can engineer write→reenter→write sequences to inflate its own recorded deposit, causing incorrect (typically under-refunded, but structurally miscounted) storage-deposit settlement — a runtime accounting bug that "compromises intended behavior" for value conservation of storage deposits, which is exactly one of the listed live-scope impacts (implementation bugs that compromise intended behavior / storage-deposit accounting failing to settle exactly once).

### Likelihood Explanation
`pallet-contracts` still permits WASM contracts to call themselves (or via an intermediary) — reentrancy is opt-in per call (`allows_reentry` flag) but is a normal, permissionless, unprivileged capability available to any contract deployer; no admin/governance/relayer/validator involvement is required. The trigger requires only ordinary contract-to-contract calls with `allows_reentry = true`, which is fully within reach of any user deploying and calling a WASM contract. This is the same reachability profile that made the `pallet-revive` bug real enough to require a dedicated fix and 4-test regression suite.

### Recommendation
Port the `pallet-revive` fix to `pallet-contracts`: add a `bank_pending_changes`-equivalent to `substrate/frame/contracts/src/storage/meter.rs`'s `RawMeter`, and invoke it at the cache-invalidation site in `push_frame`/`pop_frame` in `substrate/frame/contracts/src/exec.rs` whenever an ancestor frame with the same `account_id` is found, so that `finalize_own_contributions` never re-applies a diff that was already banked into a reloaded `ContractInfo`. Add regression tests mirroring `same_contract_reentry_does_not_double_count_storage` and `transitive_reentry_does_not_double_count_storage` from `substrate/frame/revive/src/metering/tests.rs`.

### Proof of Concept
Not independently executed against `pallet-contracts` in this session (the fix for `pallet-revive` includes concrete failing-without-fix test cases that can be directly adapted). The concrete reproduction pattern, as validated for `pallet-revive` and structurally identical for `pallet-contracts`:
1. Deploy contract `X` with a WASM entry point that: writes storage key `K1`, calls itself (`ctx.ext.call(..., X, ..., allows_reentry: true, ...)`), then writes storage key `K2`.
2. Compare the resulting persisted `ContractInfo` (`storage_items`, `storage_bytes`, `storage_item_deposit`, `storage_byte_deposit`) and net deposit charged to the origin against a non-reentrant baseline that performs the same two writes without the self-call.
3. In `pallet-revive` prior to the fix, this produced `storage_items == 3` instead of the correct `2` (test `same_contract_reentry_does_not_double_count_storage`, `substrate/frame/revive/src/metering/tests.rs:172-224`) — i.e., `K1`'s write was counted twice. [5](#0-4) 
4. Because `pallet-contracts`'s `push_frame` (`substrate/frame/contracts/src/exec.rs:909-948`) performs the same unconditional `ContractInfoOf::insert` before descending into the child frame, and its `finalize_own_contributions` (`substrate/frame/contracts/src/storage/meter.rs`) has no banking/consumption step for an ancestor's pending diff, the identical write-reenter-write sequence executed against `pallet-contracts` is expected to reproduce the same inflated accounting, since no fix analogous to `bank_pending_changes` exists in that crate.

**Uncertainty**: I did not execute a live test against `substrate/frame/contracts` in this session to empirically confirm the double-count reproduces exactly (the grep for `bank_pending_changes`/`own_contribution` in that crate did not return matches, confirming the fix is absent, but I did not run `metering::tests::nested_call_storage_refund`-style test against it). A Devin session with tool access to build and run the `pallet-contracts` test suite (write an analogous `ReentryStorage`-style fixture and test, mirroring `substrate/frame/revive/src/metering/tests.rs`) would give a definitive confirmation.

    For `X` writes `K1` → calls itself → writes `K2`:

    1. `push_frame` (`exec.rs:1212-1223`) and the same-contract `cached_info` shortcut (`exec.rs:2150-2160`) clone the parent's `ContractInfo`, preview-apply the parent's pending diff to the clone, and use it as the child's view. The child persists that clone via `insert_contract` on success.

The existing #10920 regression test (`metering::tests::nested_call_storage_refund` with the `setAndCallClear` fixture) does not catch the case because the parent performs no write after the nested call returns — its cache stays `Invalidated`, the outer pop's `as_contract()` returns `None`, and the diff is never re-applied.

**File:** substrate/frame/revive/src/metering/storage.rs (L512-528)
```rust
	/// Apply the pending diff to `info` and push its deposit as a final charge, then reset
	/// `own_contribution` so finalize does not apply it a second time.
	pub fn bank_pending_changes(&mut self, contract: T::AccountId, info: &mut ContractInfo<T>) {
		if let Contribution::Alive(_) = &self.own_contribution {
			let deposit = self.own_contribution.update_contract(Some(info));
			self.own_contribution = Contribution::Alive(Default::default());
			if !deposit.is_zero() {
				self.charge_deposit(contract, deposit);
			}
		} else {
			debug_assert!(
				false,
				"on-stack ancestor frames have not finalized yet, so own_contribution \
				 should be Alive when banked; qed",
			);
		}
	}

/// Direct same-contract reentry (X -> X): a write, a self-reenter, then another write
/// must not double-count the pre-reentry write in the persisted `ContractInfo`. The
/// reentrant run must match a non-reentrant baseline exactly (both persisted accounting
/// and the net deposit charged to the origin). Regression repro for contract-issues#213.
#[test_case(FixtureType::Solc   ; "solc")]
#[test_case(FixtureType::Resolc ; "resolc")]
fn same_contract_reentry_does_not_double_count_storage(fixture_type: FixtureType) {
	let (code, _) = compile_module_with_type("ReentryStorage", fixture_type).unwrap();

	ExtBuilder::default().build().execute_with(|| {
		let _ = <Test as Config>::Currency::set_balance(&ALICE, 100_000_000_000);

		// Baseline: two writes, no reentry.
		let Contract { addr: baseline_addr, .. } =
			builder::bare_instantiate(Code::Upload(code.clone()))
				.salt(Some([1; 32]))
				.build_and_unwrap_contract();
		let baseline = builder::bare_call(baseline_addr)
			.data(ReentryStorage::writeTwiceCall {}.abi_encode())
			.build();
		let baseline_info = AccountInfo::<Test>::load_contract(&baseline_addr).unwrap();

		// Reentrant: write, reenter self (an empty frame), write. Same end state.
		let Contract { addr: reentrant_addr, .. } = builder::bare_instantiate(Code::Upload(code))
			.salt(Some([2; 32]))
			.build_and_unwrap_contract();
		let reentrant = builder::bare_call(reentrant_addr)
			.data(ReentryStorage::writeReenterWriteCall {}.abi_encode())
			.build();
		let reentrant_info = AccountInfo::<Test>::load_contract(&reentrant_addr).unwrap();

		assert!(baseline.result.is_ok(), "baseline call failed: {:?}", baseline.result);
		assert!(reentrant.result.is_ok(), "reentrant call failed: {:?}", reentrant.result);

		// Without the bank-pending-changes fix the pre-reentry write is applied to the
		// persisted ContractInfo twice, inflating every storage field and over-charging
		// the origin. Assert the full set so a partial regression still fails.
		assert_eq!(
			reentrant_info.storage_items, baseline_info.storage_items,
			"storage_items inflated by double-applied pending diff under same-contract reentry",
		);
		assert_eq!(
			reentrant_info.storage_bytes, baseline_info.storage_bytes,
			"storage_bytes inflated under same-contract reentry",
		);
		assert_eq!(
			reentrant_info.storage_item_deposit, baseline_info.storage_item_deposit,
			"storage_item_deposit inflated under same-contract reentry",
		);
		assert_eq!(
			reentrant_info.storage_byte_deposit, baseline_info.storage_byte_deposit,
			"storage_byte_deposit inflated under same-contract reentry",
		);
		assert_eq!(
			reentrant.storage_deposit, baseline.storage_deposit,
			"net storage deposit charged to origin inflated under same-contract reentry",
		);
	});
}
