### Title
Unauthenticated `RecvError` packet allows remote tunnel teardown / state poisoning without certificate verification - (File: outside.go)

### Summary
This is a genuine analog to the Astaria `ClearingHouse.safeTransferFrom` bug class: an unauthenticated caller can trigger a security-relevant state transition (tunnel teardown) because the check gating that transition relies on attacker-controllable/spoofable data rather than cryptographic proof of identity, similar to how `payment >= currentOfferPrice` in `ClearingHouse` could be satisfied by an unauthenticated dust transfer instead of a real, verified purchase.

### Finding Description
`header.RecvError` packets are handled in the "Unencrypted packets" branch of `readOutsidePackets`, before any Noise/cert-based authentication is performed: [1](#0-0) 

`handleRecvError` then looks up the hostinfo purely by the wire-supplied `RemoteIndex` and validates the sender only by comparing the packet's *UDP source address* against the value cached in `hostinfo.GetRemote()`: [2](#0-1) 

If the (spoofable) UDP source address happens to match, `f.closeTunnel(hostinfo)` is called immediately, tearing down an already-established, authenticated tunnel — with no Noise handshake, no certificate check, and no cryptographic binding of the `RecvError` message to the peer's key. The only "authentication" is an IP/port comparison, which is not a security boundary over UDP (source addresses are trivially spoofable by an off-path or on-path attacker without any CA-signed certificate).

This mirrors the reported bug class precisely: in `ClearingHouse`, `safeTransferFrom` finalizes protocol state (`settleAuction`) based on an attacker-satisfiable condition (ERC20 balance) instead of verifying the actual authorized caller (Seaport/conduit). Here, `handleRecvError` finalizes protocol state (tunnel teardown, entry removed from both hostmaps) based on an attacker-satisfiable condition (matching source `AddrPort`) instead of verifying a cryptographically authenticated sender.

### Impact Explanation
An attacker who can spoof UDP packets from a legitimate peer's address (or who is on-path/off-path with knowledge of the `RemoteIndex`, which is exchanged in cleartext during handshake and visible on the wire) can force `closeTunnel` on a victim node, and the entry is also removed from the pending hostmap via `hm.DeleteHostInfo`. This is a remote, unauthenticated denial-of-service / state-poisoning primitive: it destroys an established, authenticated tunnel without needing a CA-signed certificate, degrading availability and forcing renegotiation (which itself has a nontrivial handshake cost and creates a window for wrong-responder / racing attacks already tested elsewhere in the codebase, e.g. `TestWrongResponderHandshake`).

### Likelihood Explanation
- `RemoteIndex` is observable from any captured/relayed handshake or data packet header, so an on-path attacker (no cert required) or an attacker who can observe/guess the 32-bit index has what's needed.
- UDP source-address spoofing is a well-known, low-cost technique; the code's own comment ("Someone spoofing recv_errors?") acknowledges this exact threat but only logs it — it still processes and tears down the tunnel whenever the spoofed address happens to match the cached remote.
- The project's own `CHANGELOG.md` shows this exact message type has already been treated as a security-sensitive lever multiple times (`send_recv_error`/`accept_recv_error` config knobs, disabling `RecvError` outside the valid counter window), confirming the class of risk is recognized, but the default behavior (`recvErrorAlways`) as implemented in `ShouldRecvError` still accepts these packets from any address unless operators explicitly restrict to private/never.

### Recommendation
- Do not act on `RecvError` (or any other type in the "unencrypted packets" switch) based solely on address matching. Require cryptographic evidence that the sender possesses a valid session context for that index — e.g., bind `RecvError` acceptance to a corresponding encrypted acknowledgment, or require it to be authenticated similarly to `CloseTunnel`/`Message` packets which are decrypted with the peer's session keys before being acted upon.
- At minimum, harden the default `acceptRecvErrorConfig` to not silently trust cleartext control packets network-wide (`recvErrorAlways`), and strongly rate-limit/validate before calling `closeTunnel`.
- Consider requiring `RecvError` to be delivered as an authenticated packet (i.e., processed only after the encrypted-packet path, similar to `header.CloseTunnel`), so an unauthenticated third party cannot trigger tunnel teardown just by spoofing a source address and reusing an observed index.

### Proof of Concept
1. Attacker observes (or is on-path for) a handshake between Node A and Node B, learning B's `RemoteIndex` value used by A (visible in handshake/message headers, unencrypted at the transport level).
2. Attacker crafts a UDP packet with header type `header.RecvError`, `RemoteIndex` set to the observed index, and spoofs the source `AddrPort` to match B's known UDP endpoint, then sends it to A.
3. `readOutsidePackets` routes the packet to `f.handleRecvError(via.UdpAddr, h)` before any decryption/authentication step: [3](#0-2) .
4. `handleRecvError` finds the hostinfo via `QueryReverseIndex`, compares `hr != addr` (the spoofed address matches), and calls `f.closeTunnel(hostinfo)`, tearing down A's established tunnel to B without any certificate or Noise-level authentication: [4](#0-3) .

Note: I was unable to fully verify (index limits) whether `generateIndex`'s randomness makes brute-forcing infeasible for a purely off-path attacker without any observation of traffic; on-path/observing attacker feasibility is clearly established from the code alone.

func (f *Interface) handleRecvError(addr netip.AddrPort, h *header.H) {
	if !f.acceptRecvErrorConfig.ShouldRecvError(addr) {
		f.l.Debug("Recv error received, ignoring",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
		return
	}

	if f.l.Enabled(context.Background(), slog.LevelDebug) {
		f.l.Debug("Recv error received",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
	}

	hostinfo := f.hostMap.QueryReverseIndex(h.RemoteIndex)
	if hostinfo == nil {
		f.l.Debug("Did not find remote index in main hostmap", "remoteIndex", h.RemoteIndex)
		return
	}

	hr := hostinfo.GetRemote()
	if hr.IsValid() && hr != addr {
		f.l.Info("Someone spoofing recv_errors?",
			"addr", addr,
			"hostinfoRemote", hr,
		)
		return
	}

	f.closeTunnel(hostinfo)
	// We also delete it from pending hostmap to allow for fast reconnect.
	f.handshakeManager.DeleteHostInfo(hostinfo)
}
