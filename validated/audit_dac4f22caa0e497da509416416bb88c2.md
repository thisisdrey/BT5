### Title
Wrong Identity Used in `RotationProofChallenge` Allows Cross-Delegate Signature Replay in `rotate_authentication_key_with_rotation_capability` - (File: aptos-move/framework/aptos-framework/sources/account/account.move)

---

### Summary

`rotate_authentication_key_with_rotation_capability` constructs a `RotationProofChallenge` using the **delegate's** sequence number instead of the **offerer's** sequence number. Because the challenge is supposed to be uniquely bound to the offerer's account state, this mismatch allows a `cap_update_table` signature (produced by the new key) to be replayed by a different delegate who happens to share the same sequence number, enabling unauthorized rotation of the offerer's authentication key.

---

### Finding Description

In `rotate_authentication_key_with_rotation_capability`, the `RotationProofChallenge` is constructed as:

```move
let challenge = RotationProofChallenge {
    sequence_number: get_sequence_number(delegate_address),   // ← WRONG
    originator: rotation_cap_offerer_address,
    current_auth_key: curr_auth_key,
    new_public_key: new_public_key_bytes,
};
``` [1](#0-0) 

The `RotationProofChallenge` struct's own comment states the `sequence_number` field is **"the sequence number of the account whose key is being rotated"** — i.e., the offerer's account: [2](#0-1) 

The sibling function `rotate_authentication_key` correctly uses the account-being-rotated's sequence number:

```move
let challenge = RotationProofChallenge {
    sequence_number: account_resource.sequence_number,   // ← CORRECT
    originator: addr,
    ...
};
``` [3](#0-2) 

The `cap_update_table` signature is the new key's proof-of-knowledge that it consents to being the new authentication key for the offerer's account. By binding the challenge to the **delegate's** sequence number rather than the **offerer's**, the uniqueness guarantee is broken: two different delegates with the same sequence number produce identical challenges for the same offerer/current-auth-key/new-key tuple, making the signature reusable across delegates.

---

### Impact Explanation

An attacker who is granted rotation capability can replay a `cap_update_table` signature that was originally produced for a different delegate's rotation of the same offerer account, forcing the offerer's authentication key to be set to a key the attacker controls (or has colluded with). This constitutes **unauthorized reassignment of an account's authentication key**, giving the attacker full control of the victim's account and all assets held there.

---

### Likelihood Explanation

Required conditions:
1. Alice (offerer) grants rotation capability to Bob (delegate, seq# = N); Bob rotates Alice's key to `K_new`; Alice rotates her key back to `K_A`.
2. Alice grants rotation capability to Charlie (delegate, seq# = N — e.g., a fresh account if N = 0).
3. Charlie (attacker) replays the on-chain `cap_update_table` signature from step 1.

The `cap_update_table` signature is publicly visible on-chain. If N = 0 (Bob's first-ever transaction was the rotation), any fresh account Charlie satisfies condition 2. This is a realistic scenario for newly-deployed delegation flows.

---

### Recommendation

Replace `get_sequence_number(delegate_address)` with `get_sequence_number(rotation_cap_offerer_address)` in the challenge construction inside `rotate_authentication_key_with_rotation_capability`:

```move
let challenge = RotationProofChallenge {
    sequence_number: get_sequence_number(rotation_cap_offerer_address),  // FIX
    originator: rotation_cap_offerer_address,
    current_auth_key: curr_auth_key,
    new_public_key: new_public_key_bytes,
};
```

This matches the documented intent of the `RotationProofChallenge` struct and is consistent with how `rotate_authentication_key` constructs the same challenge. [4](#0-3) 

---

### Proof of Concept

```
Setup:
  Alice  (offerer):  address = 0xA, auth_key = K_A, seq# = 0
  Bob    (delegate): address = 0xB, seq# = 0
  Charlie(attacker): address = 0xC, seq# = 0
  K_new: a key pair controlled by Charlie (or colluding party)

Step 1 – Alice grants rotation capability to Bob.
  Alice calls offer_rotation_capability(..., bob_addr).

Step 2 – Bob rotates Alice's key to K_new.
  challenge = { seq: 0 /*Bob's seq*/, originator: 0xA, current_auth_key: K_A, new_pk: K_new }
  sig = Sign(K_new_sk, challenge)
  Bob calls rotate_authentication_key_with_rotation_capability(0xA, ED25519, K_new, sig)
  → Alice's auth_key = K_new. Bob's seq# → 1.

Step 3 – Alice rotates her key back to K_A.
  Alice calls rotate_authentication_key(...) directly.
  → Alice's auth_key = K_A again.

Step 4 – Alice revokes Bob's capability; grants rotation capability to Charlie.
  Alice calls offer_rotation_capability(..., charlie_addr).
  Charlie's seq# = 0 (fresh account).

Step 5 – Charlie replays Bob's sig.
  challenge = { seq: 0 /*Charlie's seq*/, originator: 0xA, current_auth_key: K_A, new_pk: K_new }
  This is IDENTICAL to the challenge from Step 2.
  Charlie calls rotate_authentication_key_with_rotation_capability(0xA, ED25519, K_new, sig)
  → Signature verification passes (same challenge, same sig).
  → Alice's auth_key = K_new. Charlie (who controls K_new) now owns Alice's account.
```

The `cap_update_table` signature `sig` from Step 2 is publicly visible on-chain and is accepted again in Step 5 because the challenge is bound to the delegate's sequence number (0 in both cases) rather than the offerer's. [5](#0-4)
