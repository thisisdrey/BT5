#No Vulnerability found for this question.

The premise doesn't hold up against the code. `burnt_amount` is computed exactly once, via `tx_cost`/`calculate_tx_cost`, *before* `verify_and_charge_gas_key_tx_ephemeral` is even invoked, and the resulting `TransactionCost::burnt_amount` value is destructured and reused identically for both the `TxVerdict::Success` and `TxVerdict::DepositFailed` branches — there is no separate/alternate rounding step on the `DepositFailed` path. [1](#0-0) [2](#0-1) [3](#0-2) 

The `gas_key_info.balance.checked_sub(burnt_amount)` charge in the `DepositFailed` case (`new_key_balance_on_deposit_failure`) and the `result.burnt_amount` field in the `Success` case both come from the same `burnt_amount` local pulled out of the single `*transaction_cost` passed in by the caller, so there is no arithmetic divergence between the two branches for identical inputs. [4](#0-3) 

`calculate_tx_cost` itself is a pure function of the `RuntimeConfig` (versioned by protocol version, e.g. `fix_ml_dsa_cost_charging`), the transaction's actions/keys, and `current_gas_price` — all of which are consensus-determined inputs (same runtime config store per protocol version, same block gas price for all validators applying the same chunk). There is no data-dependent (e.g., account-balance-dependent) branch inside `calculate_tx_cost` that would compute `burnt_amount` differently depending on whether the deposit later succeeds or fails. [5](#0-4) 

This is corroborated by the existing test suite, which explicitly asserts `result.burnt_amount == cost.burnt_amount` in the `DepositFailed` case, matching the value computed independently via `tx_cost`. [6](#0-5) [7](#0-6) 

Since protocol version and gas price are both consensus-agreed per block (not validator-local choices), and `burnt_amount` is computed once from these deterministic inputs prior to branching on `TxVerdict`, there is no mechanism by which different honest validators applying the same chunk at the same protocol version could compute different `burnt_amount` values for this transaction on the `DepositFailed` path versus each other, nor versus the `Success`/`Failed` paths for the same cost struct. No state-root divergence or token-supply divergence is reachable through this code path.

```rust
pub fn calculate_tx_cost(
    receiver_id: &AccountId,
    signer_id: &AccountId,
    signer_public_key: &PublicKey,
    actions: &[Action],
    config: &RuntimeConfig,
    current_gas_price: Balance,
) -> Result<TransactionCost, IntegerOverflowError> {
    let sender_is_receiver = receiver_id == signer_id;
    let fees = &config.fees;
    let mut burnt: ParameterCost =
        fees.fee(ActionCosts::new_action_receipt).send_fee(sender_is_receiver);
    burnt = burnt.checked_add_result(total_send_fees(
        config,
        sender_is_receiver,
        actions,
        receiver_id,
    )?)?;
    // Burn the signature-verification cost as part of converting the
    // transaction. This raises the gas the signer must buy (burnt_amount /
    // total_cost below) but never `gas_remaining` (the gas attached to / left
    // for the resulting receipts), so on-chain function-call gas budgets are
    // unaffected.
    burnt = burnt.checked_add_result(signature_verification_cost(
        fees,
        signer_public_key,
        actions,
        config.wasm_config.fix_ml_dsa_cost_charging,
    )?)?;
```
