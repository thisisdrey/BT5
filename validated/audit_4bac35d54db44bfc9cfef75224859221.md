### Title
Unauthenticated frontier identity takeover via unchecked `HandshakeData.addrbytes/port` on first handshake of any connection - (File: `stackslib/src/net/db.rs`, `stackslib/src/net/chat.rs`)

### Summary
`PeerDB::try_insert_peer` finds an existing frontier row by `(network_id, addrbytes, port)` and, if present, calls `PeerDB::update_peer` unconditionally, which only compares old vs. new public key *after* writing (to decide whether to `drop_stacker_dbs`), never before writing (to reject the change). This same `update_peer` primitive is also reached directly from `ConversationP2P::handle_handshake`'s "re-key" path via `Neighbor::save_update`, and that path's only continuity check (`self.peer_addrbytes`/`self.peer_port` must equal `HandshakeData.addrbytes/port`) is skipped whenever the local `ConversationP2P` has no public key recorded yet for that connection — which is always true on the very first `Handshake` received on a freshly-established socket, even one the victim node itself dialed outbound.

### Finding Description
`PeerDB::try_insert_peer` (`stackslib/src/net/db.rs:1452-1488`) does:
```
let present = PeerDB::has_peer(tx, network_id, addrbytes, port)?;
if present {
    PeerDB::update_peer(tx, neighbor)?;   // unconditional UPDATE ... WHERE network_id/addrbytes/port
    ...
}
```
`update_peer`'s `UPDATE frontier SET ... public_key = ?2 ... WHERE network_id=?, addrbytes=?, port=?` (as quoted in the audit prompt) writes the new public key before comparing it to the previously stored one; the old-vs-new comparison only gates the subsequent `drop_stacker_dbs` call, not the write itself. There is no proof-of-continuity check (e.g., that the writer holds the *old* private key, or that the claimed address matches the actual TCP peer) inside `update_peer`/`try_insert_peer`.

The exploitable entry point is `ConversationP2P::handle_handshake` (`stackslib/src/net/chat.rs:1214-1296`), which is invoked for *every* inbound `Handshake` message, on any connection direction. `validate_handshake` (`chat.rs:1047-1092`) only checks that `HandshakeData.addrbytes/port` match the connection's real socket address (`self.peer_addrbytes`/`self.peer_port`) inside the `Some(_)` branch — i.e., only when `self.connection.get_public_key()` is already `Some(..)` for this specific conversation object. On the `None` branch (no public key yet recorded for this connection), the code only verifies the message is self-signed by the *claimed* `node_public_key` — it never checks that the claimed `addrbytes`/`port` match the socket:
```rust
match self.connection.get_public_key() {
    None => {
        message.verify_secp256k1(&handshake_data.node_public_key) ... // self-signature only
    }
    Some(_) => {
        if self.stats.outbound && (... self.peer_addrbytes != handshake_data.addrbytes ...) { reject }
    }
}
```
`get_public_key()` is `None` for every brand-new `ConversationP2P`, including ones the victim node itself dialed outbound to a peer that the attacker legitimately controls (e.g., the attacker simply runs a reachable P2P node that gets gossiped/added to the frontier as any ordinary peer). Once such an outbound socket exists, the remote (attacker) side can send a `Handshake` (not just a `HandshakeAccept`) over that same duplex connection at any time, self-signed with its own key `B`, but with `HandshakeData.addrbytes/port` set to a *third-party victim's* already-known address/port (any entry already present in the node's PeerDB frontier).

Because `get_public_key()` is `None` on this fresh conversation, the address-match guard never fires. `handle_handshake` then proceeds: `updated` becomes true (key `None -> B`), and since `self.stats.outbound` is true for this connection, the "re-key" block executes (`chat.rs:1275-1286`):
```rust
let (mut neighbor, _) = Neighbor::load_and_update(&tx, peer_version, network_id, &handshake_data)?;
neighbor.save_update(&tx, None)?;
```
`Neighbor::load_and_update` keys the lookup via `NeighborKey::from_handshake` (`chat.rs:411-423`), which uses `handshake_data.addrbytes/port` — the attacker-forged, victim-claimed address — not the real socket address. It loads the victim's existing PeerDB row (with pubkey `A`), `handshake_update` overwrites `public_key` to `B`, and `Neighbor::save_update` (`stackslib/src/net/neighbors/neighbor.rs:50-61`) calls `PeerDB::update_peer(tx, self)` directly — the same unconditional-write/compare-after-write primitive described in the question. The result: the victim's frontier row at `(network_id, victim_addrbytes, victim_port)` is silently rewritten with the attacker's public key, with no proof that the attacker ever controlled `victim_addrbytes:victim_port` at the TCP layer.

### Impact Explanation
This is an unauthenticated write to persistent P2P state: an attacker who merely runs their own reachable peer (no privileged role, no secret, no access to any victim's key) can overwrite the stored identity (public key) of an arbitrary, already-known peer entry in a node's frontier database, as long as they get that node to open (or already have) any outbound connection to them and can send a raw `Handshake` message on it. Because `public_key` changed, `drop_stacker_dbs` will also fire for the victim's slot, invalidating that peer's tracked StackerDB replica list — cascading loss of state for a legitimate peer. This matches "unauthenticated/unauthorized write to state" — Critical.

### Likelihood Explanation
- Attacker only needs to be a reachable, otherwise-ordinary P2P peer that the target node dials outbound to (trivial: gossip yourself, or wait for the node's neighbor walk to discover and connect to you).
- No secrets, no victim private key, no privileged role, no local/physical access, and no need to spoof/intercept the actual victim IP:port — the forged address is only ever compared against the real socket address in the `Some(_)` branch, which never applies to a fresh conversation.
- The victim node must already have a frontier entry for the target address/port being clobbered (any bootstrap peer or previously-seen peer works) and must open/maintain an outbound connection to the attacker (both are ordinary, expected node behavior).
- Repeatable: the attacker can also legitimately re-run this on any subsequent fresh connection object (e.g. after reconnects) to keep clobbering the entry.

### Recommendation
Fix `PeerDB::update_peer` / `try_insert_peer` to reject (rather than silently overwrite) a public-key change for an existing `(network_id, addrbytes, port)` row unless continuity is proven — e.g., require the new message to be signed by the *previously stored* public key, or require the update to only apply to the exact `ConversationP2P`/socket that was already authenticated for that address. Separately, close the underlying root cause in `ConversationP2P::validate_handshake`: always validate `HandshakeData.addrbytes/port` against the real, observed socket address (`self.peer_addrbytes`/`self.peer_port`) regardless of whether `self.connection.get_public_key()` is `None` or `Some`, not only in the `Some(_)`+outbound branch.

### Proof of Concept
Rust test plan (in `stackslib::net::chat` test module, extending the existing `convo_handshake_badpeeraddress`-style tests):
1. Seed `peerdb_1` (victim's local frontier) with a `Neighbor` at `(network_id, victim_addr, victim_port)` with public key `A` (via `PeerDB::try_insert_peer`).
2. Create `convo_1` as an **outbound** `ConversationP2P` (`stats.outbound = true`) to `attacker_addr:attacker_port`, with `connection.get_public_key() == None` (fresh conversation, matching a real fresh socket to a reachable attacker peer).
3. Craft and self-sign (with attacker's private key `B`) a `StacksMessageType::Handshake` whose `HandshakeData { addrbytes: victim_addr, port: victim_port, node_public_key: B, .. }` — i.e., claiming the victim's address, not the attacker's own dialed address.
4. Feed this message into `convo_1.chat(...)` / `handle_authenticated_control_message` -> `handle_handshake`, and assert it returns `Ok` (not `net_error::InvalidHandshake`), proving `validate_handshake` did not reject the address mismatch.
5. Assert `PeerDB::get_peer(peerdb_1.conn(), network_id, &victim_addr, victim_port)` now returns public key `B` (not `A`), and that `drop_stacker_dbs` was invoked for that peer's slot — proving the takeover succeeded via `Neighbor::save_update -> PeerDB::update_peer` without any proof the attacker ever controlled `victim_addr:victim_port`.
