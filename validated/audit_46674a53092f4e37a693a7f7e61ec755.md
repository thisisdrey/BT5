This confirms the actual mechanism precisely as described. In `do_purchase`, `price` is not directly chosen by the caller — it is `Self::sale_price(&sale, now)`, a deterministic function of block time along the leadin decay curve; `price_limit` is merely a cap the buyer accepts [1](#0-0) . An attacker cannot pick an arbitrary price, but can time which block/transaction lands as the one that pushes `cores_sold` across `ideal_cores_sold`, thereby controlling which point on the known, public, monotonically-decaying leadin price curve becomes `sellout_price` — this is the "timing" attack the claim describes.

Audit Report

## Title
Coretime sale `sellout_price` (and therefore next-sale `target_price`/`end_price`/renewal pricing) is derived from a single purchase transaction instead of a volume/time-weighted observation - (File: `substrate/frame/broker/src/utility_impls.rs`)

## Summary
`purchase_core` overwrites `sale.sellout_price` with the price of every purchase made while `cores_sold <= ideal_cores_sold`, so the value ultimately used is just the price of the single purchase that happens to be the last one at or below that threshold. This single point-sample is fed unmodified into `AdaptPrice::adapt_price` at `rotate_sale` to set the entire next sale's `end_price`/`target_price`, and `target_price` is also stamped into every `PotentialRenewalRecord` for leases expiring into the new region, meaning one purchase's timing on the public leadin-decay curve can shift pricing for an entire subsequent sale period and all its lease renewals.

## Finding Description
`purchase_core` sets `sale.sellout_price = Some(price)` on every purchase while `sale.cores_sold <= sale.ideal_cores_sold` (or if none has been set yet), so the final stored value is simply whichever purchase happened to be made at or crossing that threshold [2](#0-1) . At `rotate_sale`, this single value is passed via `SalePerformance::from_sale` directly into `T::PriceAdapter::adapt_price` to compute the new sale's prices [3](#0-2) , and `CenterTargetPrice::adapt_price` (wrapped by `MinimumPrice`, which is what production runtimes actually configure) derives `target_price = sellout_price` and `end_price = sellout_price / 10` directly from that one observation, with no averaging across multiple purchases [4](#0-3) . `coretime-westend`'s runtime confirms `MinimumPrice<Balance, MinimumEndPrice>` is the configured `PriceAdapter`, which only clamps the floor of `end_price`/`target_price` — it does not change the single-observation nature of the input [5](#0-4) . The resulting `target_price` is then written into `PotentialRenewalRecord.price` for every lease expiring at the region boundary [6](#0-5) , and that recorded price directly bounds/derives the renewal price cap used in `do_renew` (`price_cap = max(record.price + bump*record.price, end_price)`) [7](#0-6) .

Purchases go through `do_purchase`, where the actual charged `price` is computed deterministically from the public leadin-decay curve as a function of elapsed time (`Self::sale_price(&sale, now)`), and `price_limit` only serves as the buyer's accepted ceiling — the buyer does not choose the price itself [8](#0-7) , [9](#0-8) . Since the leadin curve and current `cores_sold` count are both public on-chain state, any unprivileged account can predict exactly which price will be charged at any future block and can time a purchase to land as the transition purchase around `ideal_cores_sold`, thereby selecting (within the bounds of the deterministic decay curve, by choosing *when* to buy) the value that becomes `sellout_price`. This is a real timing-based manipulation of a single data point that is supposed to represent aggregate sale performance, and the existing `MinimumPrice` floor mitigation does not address the single-observation weakness — it only prevents `end_price` going below a configured minimum.

## Impact Explanation
A single, well-timed purchase transaction can materially distort `target_price`/`end_price` for an entire subsequent coretime sale period and for every lease renewal computed off that period's `target_price`, degrading the pallet's intended price-discovery mechanism. This matches the impact-gate category of "runtime bugs that compromise intended behavior," since the deterministic tie between one purchase's timing and the pricing signal for an entire following sale/region is a genuine, code-verified design weakness, not a hypothetical or off-repo consideration.

## Likelihood Explanation
No privileged role, governance action, or malicious-node assumption is required; any signed account with funds for one core purchase can call the public `purchase` extrinsic (`do_purchase`) and, by observing `SaleInfo::cores_sold` and the deterministic leadin-decay `sale_price` formula, choose the block at which to submit the transaction that crosses `ideal_cores_sold`. This is a low-cost, repeatable manipulation available every sale rotation, though the actual price value achievable is still bounded by the public leadin curve rather than freely chosen by the attacker (a nuance the original claim slightly overstates, since `price_limit` does not let the attacker set price to any value, only accept the curve's current value).

## Recommendation
Compute the pricing signal fed to `AdaptPrice` as an aggregate (e.g., volume-weighted average price across all purchases in the sale, or specifically across purchases near the `ideal_cores_sold` threshold) rather than overwriting `sellout_price` with each qualifying purchase's raw price in `purchase_core` (`substrate/frame/broker/src/utility_impls.rs`). Alternatively, add a per-rotation dampening/clamp on how much `target_price`/`end_price` can move relative to the prior period, independent of the `MinimumPrice` floor already in place.

## Proof of Concept
1. Track `SaleInfo::cores_sold` and `SaleInfo::ideal_cores_sold` for the active sale, and compute the deterministic `sale_price(sale, now)` leadin curve value at any target block.
2. Submit `Broker::purchase(price_limit)` at a self-chosen block such that this purchase is the one that sets `cores_sold` to (or just under) `ideal_cores_sold`, with `price_limit` ≥ the curve price at that block — per the `cores_sold <= ideal_cores_sold` branch in `purchase_core`, this purchase's price overwrites `sale.sellout_price`.
3. Observe at the next `rotate_sale` call that `new_prices.end_price`/`new_prices.target_price` (via `CenterTargetPrice`/`MinimumPrice::adapt_price`) are derived solely from that single purchase's price, and that `PotentialRenewalRecord.price` for all leases expiring into the new region is set to `target_price` — confirming the single-purchase-to-region-wide-price propagation described above.

	fn adapt_price(performance: SalePerformance<Balance>) -> AdaptedPrices<Balance> {
		let Some(sellout_price) = performance.sellout_price else {
			return AdaptedPrices {
				end_price: performance.end_price,

			sellout_price
		} else {
			price
		};

		AdaptedPrices { end_price: price, target_price: sellout_price }
	}
