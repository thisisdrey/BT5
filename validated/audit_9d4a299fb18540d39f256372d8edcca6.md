### Title
Unauthenticated RecvError packets with a spoofed source address can tear down a victim's active tunnel - (`outside.go`)

### Summary
`handleRecvError` accepts a cleartext, unauthenticated `header.RecvError` packet and, if the packet's `h.RemoteIndex` matches an existing hostinfo and the sender's `UdpAddr` matches the hostinfo's currently recorded remote, immediately calls `f.closeTunnel(hostinfo)` and `f.handshakeManager.DeleteHostInfo(hostinfo)`. Since `RemoteIndex` is a cleartext 32-bit value transmitted on the wire in every packet, and UDP allows source-address spoofing when the attacker is on-path or the network path lacks egress/ingress filtering, an attacker can forge this packet to force a legitimate session teardown without ever presenting a certificate or completing a handshake.

### Finding Description
In `readOutsidePackets` (`outside.go:81-84`), packets of `header.RecvError` type are dispatched to `f.handleRecvError(via.UdpAddr, h)` before any hostinfo/certificate/crypto validation occurs — this happens in the "Unencrypted packets" switch, prior to the `hostMap.QueryIndex` / decrypt path used for authenticated traffic. [1](#0-0) 

`handleRecvError` then does:
1. Checks `f.acceptRecvErrorConfig.ShouldRecvError(addr)` — this is a config-driven policy (default `always`), not an authentication check. [2](#0-1) 
2. Looks up the hostinfo purely by the cleartext `RemoteIndex` via `f.hostMap.QueryReverseIndex(h.RemoteIndex)` — no cryptographic binding is checked. [3](#0-2) 
3. The only anti-spoofing check present is `hr := hostinfo.GetRemote(); if hr.IsValid() && hr != addr { ... return }` — this rejects the packet only if the observed source address does not match the hostinfo's currently known remote `UdpAddr`. [4](#0-3) 
4. If that check passes, the code unconditionally tears down the session: `f.closeTunnel(hostinfo)` followed by `f.handshakeManager.DeleteHostInfo(hostinfo)`. [5](#0-4) 

The `hr != addr` check only guards against an attacker whose spoofed source address differs from the victim's real remote address — it does nothing against an attacker who (a) is on-path and can sniff both the `RemoteIndex` and the peer's `UdpAddr` from cleartext headers, or (b) already knows the victim's public `UdpAddr` (e.g., a well-known lighthouse or gateway with a static/known endpoint) and can spoof UDP source IP/port on networks without strict egress filtering. `RemoteIndex` itself is sent unencrypted in every packet header (`header.Encode` in `sendRecvError`, `outside.go:531`), so it is trivially observable by anyone who can see any packet in either direction of the tunnel, and does not require any counter, nonce, MAC, or certificate to be presented. This violates the stated invariant that unauthenticated input must never mutate hostmap/session state — `closeTunnel`/`DeleteHostInfo` mutate `HostMap` state from a fully unauthenticated code path.

### Impact Explanation
An attacker satisfying the described preconditions (observed/guessed `RemoteIndex` + matching source address to the victim's known remote) can force `f.closeTunnel` on a legitimate hostinfo, tearing down an active session and forcing a costly re-handshake — this is an unauthenticated denial-of-service against Nebula tunnels. Because this only requires a single spoofable UDP datagram and no certificate/session key material, it is a remote state-poisoning / DoS primitive that could be repeated to indefinitely disrupt a target's connectivity or to force repeated re-handshakes that increase exposure to the wrong-responder race referenced in `TestWrongResponderHandshake`/`TestHandshakeWrongResponderPacketStore`.

### Likelihood Explanation
- On-path attacker: trivial and fully repeatable — they observe `RemoteIndex` and true `UdpAddr` from any packet and can immediately forge a matching `RecvError`.
- Off-path attacker: requires (1) knowing the victim's real public `UdpAddr` (often knowable, e.g., static lighthouse/gateway endpoints) and (2) either brute-forcing the 32-bit `RemoteIndex` (expensive but not infeasible for a sustained/low-cost UDP flood, especially given there's no rate-limiting on `handleRecvError`) or having previously observed it, and (3) successfully spoofing the UDP source address, which depends on the network path's anti-spoofing (BCP38) enforcement — not universally deployed. `acceptRecvErrorConfig` defaults to `recvErrorAlways`, meaning the feature is enabled for all endpoints by default, maximizing exposure.

### Recommendation
Do not allow an unauthenticated `RecvError` packet to unilaterally close a tunnel based solely on `RemoteIndex` + source-address match. Options: require the `RecvError` message to include a MAC/counter tied to session key material (as with other authenticated control packets), rate-limit accepted `RecvError` per hostinfo, and/or treat `RecvError` only as a hint to trigger a re-handshake probe rather than an immediate `closeTunnel`+`DeleteHostInfo`, deferring the actual teardown to the counter-based crypto/handshake state machine that can validate authenticity.

### Proof of Concept
Unit test in `outside_test.go` (or a new test file) constructing a `HostMap` with a legitimate hostinfo whose `GetRemote()` returns a known `UdpAddr` (e.g., `1.2.3.4:4242`) and whose reverse index is registered via `QueryReverseIndex`. Then:
1. Build a forged `header.H` with `Type = header.RecvError` and `RemoteIndex` equal to the victim's real index.
2. Call `f.handleRecvError(spoofedAddr, h)` using `spoofedAddr` set to exactly `1.2.3.4:4242` (simulating a spoofed source, no certificate, no handshake).
3. Assert that before the call, `hostMap.QueryReverseIndex` returns the valid hostinfo, and after the call `hostMap.QueryReverseIndex`/`QueryVpnAddr` returns nil (tunnel destroyed) and `handshakeManager.QueryIndex` no longer contains the pending hostinfo — demonstrating unauthenticated state mutation succeeded purely from a forged UDP packet with a guessed/observed index and spoofed source, with no certificate or handshake completion.
