Confirmed: `lending_pool_close_bank` checks `lending_position_count`, `borrowing_position_count`, `total_asset_shares`/`total_liability_shares`, and `emissions_remaining`, but never checks `collected_insurance_fees_outstanding`, `collected_group_fees_outstanding`, or `collected_program_fees_outstanding` before allowing the bank account to close.

### Title
Bank can be closed while `collected_insurance_fees_outstanding`/`collected_group_fees_outstanding`/`collected_program_fees_outstanding` are still non-zero, permanently stranding uncollected fees - (File: `programs/marginfi/src/instructions/marginfi_group/close_bank.rs`)

### Summary
`lending_pool_close_bank` validates that a bank has zero open positions, zero total shares, and zero remaining emissions before closing the `Bank` account, but it never checks whether the bank still has outstanding, uncollected fees recorded in `collected_insurance_fees_outstanding`, `collected_group_fees_outstanding`, or `collected_program_fees_outstanding`. This mirrors the Backd `[M-18]` bug class, where removing a pool/bank reference before sweeping its accrued fees causes those fees to become permanently unreachable.

### Finding Description
Interest/origination fees accrue into three fields on `Bank`: `collected_insurance_fees_outstanding`, `collected_group_fees_outstanding`, and `collected_program_fees_outstanding` [1](#0-0) [2](#0-1) [3](#0-2) . These amounts are only moved out of the `liquidity_vault` into `insurance_vault`/`fee_vault`/`fee_ata` by the permissionless `lending_pool_collect_bank_fees` instruction [4](#0-3) , and that instruction requires an active `Bank` account loader (`bank: AccountLoader<'info, Bank>`) [5](#0-4) .

`lending_pool_close_bank` closes the `Bank` account (`close = admin`) after checking only:
- `CLOSE_ENABLED_FLAG` is set
- `lending_position_count == 0 && borrowing_position_count == 0`
- `total_asset_shares` and `total_liability_shares` are zero-with-tolerance
- `emissions_remaining` is zero-with-tolerance [6](#0-5) 

There is no check on `collected_insurance_fees_outstanding`, `collected_group_fees_outstanding`, or `collected_program_fees_outstanding`. Since these fields accrue from interest even without any open positions requiring nonzero shares at the moment of the check (fees can be outstanding independently, e.g. right after `accrue_interest` runs but before `LendingPoolCollectBankFees` executes, or if a permissionless caller simply never invokes fee collection before the admin closes the bank), an admin (or anyone able to trigger the close after positions are wound down) can close the bank while these fee fields are still non-zero.

Once the `Bank` account is closed:
- The `Bank` account no longer exists, so `lending_pool_collect_bank_fees`'s `AccountLoader<'info, Bank>` cannot load it, and the instruction cannot be invoked for that bank ever again.
- The vault authority PDAs (`liquidity_vault_authority`, `fee_vault_authority`, `insurance_vault_authority`) are derived using bump seeds read from the (now-closed) `Bank` account data (`bump = bank.load()?.liquidity_vault_authority_bump`, etc.) [7](#0-6) , making it impossible to reconstruct a valid signer for the liquidity vault to move out the outstanding fee amounts recorded on-chain.
- Any tokens still sitting in `liquidity_vault` that correspond to `collected_*_fees_outstanding` become permanently stuck/unrecoverable, since the accounting record of "how much is owed as fees" (the `Bank` struct) has been deleted along with the bank.

This is directly analogous to the reported Backd bug: removing the pool/bank reference before sweeping its fees causes those fees to become permanently stranded.

### Impact Explanation
This is a permanent-lock/loss-of-funds issue: uncollected insurance/group/program fees left in the bank's `liquidity_vault` at bank-close time become permanently unrecoverable because the on-chain record of the amount owed (the `Bank` account) is deleted, and no future instruction can reference the vault-authority bump seeds needed to move funds out. This affects protocol-fee revenue (group fee vault) and program fee revenue, not user deposits directly, but it is still a loss/freeze of protocol funds.

### Likelihood Explanation
Likelihood is moderate: `lending_pool_collect_bank_fees` is permissionless and it's expected to be run before closing a bank per the documented workflow (guides mention running collect fees "just before a withdraw") [8](#0-7) , but `lending_pool_close_bank` does not enforce this ordering on-chain. Any admin closing a bank without first (or atomically) calling `lending_pool_collect_bank_fees`—including via automated tooling/CLI scripts that don't explicitly sequence these two calls—can trigger the stuck-fee condition, especially since interest can still accrue fees between the last user withdrawal and the close-bank call.

### Recommendation
Add a check in `lending_pool_close_bank` requiring `collected_insurance_fees_outstanding`, `collected_group_fees_outstanding`, and `collected_program_fees_outstanding` to all be zero (with the same `ZERO_AMOUNT_THRESHOLD` tolerance used for shares/emissions) before allowing the bank to close, mirroring the existing checks for `total_asset_shares`/`total_liability_shares`/`emissions_remaining` [9](#0-8) . Alternatively, require `lending_pool_collect_bank_fees` to be called atomically as part of (or immediately preceding, within the same transaction and enforced via a CPI/composite instruction) the close-bank flow so outstanding fees are always swept before the bank account is destroyed.

### Proof of Concept
1. Group admin adds a bank and users deposit/borrow so interest accrues, incrementing `collected_group_fees_outstanding`/`collected_insurance_fees_outstanding`/`collected_program_fees_outstanding` on the `Bank` account.
2. All users fully repay and withdraw (`lending_position_count == 0`, `borrowing_position_count == 0`, `total_asset_shares`/`total_liability_shares` zero), but the admin does **not** call `lending_pool_collect_bank_fees` first.
3. Admin calls `lending_pool_close_bank` on the bank. All existing checks pass (positions/shares/emissions are zero) because none of them examine the `collected_*_fees_outstanding` fields [10](#0-9) ; the `Bank` account is closed and its lamports go to `admin`.
4. Any tokens still in the (now-orphaned) `liquidity_vault` corresponding to the previously outstanding fee amounts can no longer be swept: `lending_pool_collect_bank_fees` cannot load the closed `Bank` account, and the vault-authority PDA bump needed to sign a transfer out of `liquidity_vault` was only stored in the now-deleted `Bank` data.

pub fn lending_pool_close_bank(ctx: Context<LendingPoolCloseBank>) -> MarginfiResult {
    let mut group = ctx.accounts.group.load_mut()?;
    // Note: Groups created prior to 0.1.2 have a non-authoritative count here, so subtraction
    // without saturation could reduce the count below zero.
    group.banks = group.banks.saturating_sub(1);

    let bank = ctx.accounts.bank.load()?;

    // banks created prior to 0.1.4 can never be closed because we cannot guarantee an accurate
    // position count for those banks.
    check!(
        bank.get_flag(CLOSE_ENABLED_FLAG),
        MarginfiError::BankCannotClose,
        "Only banks created in 0.1.4 and later can close"
    );
    check!(
        bank.lending_position_count == 0 && bank.borrowing_position_count == 0,
        MarginfiError::BankCannotClose,
        "Only banks with no open positions can close"
    );
    check!(
        I80F48::from(bank.total_asset_shares).is_zero_with_tolerance(ZERO_AMOUNT_THRESHOLD)
            && I80F48::from(bank.total_liability_shares)
                .is_zero_with_tolerance(ZERO_AMOUNT_THRESHOLD),
        MarginfiError::BankCannotClose
    );
    check!(
        I80F48::from(bank.emissions_remaining).is_zero_with_tolerance(ZERO_AMOUNT_THRESHOLD),
        MarginfiError::BankCannotClose
    );

    drop(bank);

    // Bank will now be closed by anchor

    Ok(())
}

## How Fees Are Collected

(1) Interset accrues and increases the number in `fees_outstanding` fields. Optionally, origination
fees are charged and do the same.

(2) Anyone (the ix is permissionless) runs `LendingPoolCollectBankFees`. This moves:
* The amount specified in `collected_insurance_fees_outstanding` from the `liquidity_vault` to the
  `insurance_vault`
* The amount specified in `collected_group_fees_outstanding` from the `liquidity_vault` to the `fee_vault`
* The amount specified in `collected_program_fees_outstanding` from the `liquidity_vault` to the
    `fee_ata`, which is the cannonical ATA of the global fee wallet.

Then the `fees_outstanding` are all reset to zero. The vast majority of the time, we run this ix just before a withdraw.
