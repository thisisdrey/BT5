Based on my investigation, the vulnerability claim holds.

### Title
Downloaded `Attachment.content` bypasses `should_keep_attachment` size check in `AttachmentsDownloader::run`, allowing unbounded attachment storage growth - (`stackslib/src/net/atlas/download.rs`)

### Summary
`AttachmentsDownloader::run` inserts attachments obtained from a remote peer's `/v2/attachments/{hash}` response directly into `AtlasDB` via `insert_instantiated_attachment` without ever calling `AtlasDB::should_keep_attachment`, which is the only function that enforces `attachment.content.len() as u32 <= self.atlas_config.attachments_max_size`. A malicious peer that is queried for an attachment can therefore return an oversized `content` blob, which the requesting node will persist regardless of `AtlasConfig::attachments_max_size`.

### Finding Description
The size bound `stored_content_len <= attachments_max_size` is only checked inside `AtlasDB::should_keep_attachment` [1](#0-0)  against `self.atlas_config.attachments_max_size` (default `ATTACHMENTS_MAX_SIZE_MIN`) [2](#0-1) .

In the attachment-download path, `AttachmentsBatchStateContext::extend_with_attachments` decodes the `GetAttachmentResponse` from a peer's `/v2/attachments/{hash}` reply (`decode_atlas_get_attachment`, which does JSON deserialization with no length cap on `attachment.content`) and inserts the resulting `Attachment` unconditionally into `self.attachments` (a `HashSet<Attachment>`) [3](#0-2) , and `GetAttachmentResponse::deserialize`/`Attachment::new` place no size limit on the hex-decoded bytes [4](#0-3) .

When the state machine reaches `Done`, `AttachmentsDownloader::run` drains `context.attachments` and calls `network.atlasdb.insert_instantiated_attachment(&attachment)` directly, with no call to `should_keep_attachment` anywhere in this code path [5](#0-4) . `insert_instantiated_attachment` itself performs an unconditional SQL `INSERT OR REPLACE` of `attachment.content` with no size validation [6](#0-5) .

By contrast, `should_keep_attachment` is only referenced from the gossip/HTTP-ingest path (`posttransaction.rs`) and in tests, not from the download-resolution path [1](#0-0) . The `check_attachment_instances` helper used for queued/initial attachments also inserts previously-inboxed attachments (`insert_instantiated_attachment`) without a size re-check [7](#0-6) , but those attachments would already have passed `should_keep_attachment` at ingestion time via `insert_uninstantiated_attachment`'s caller. The download path from a remote peer response has no equivalent gate at all.

No response-size cap specific to attachment content was found in the download/mod.rs atlas code; HTTP-level body caps (if any) are generic and not scoped to `attachments_max_size`, so they do not restore the intended per-attachment bound.

### Impact Explanation
A malicious or compromised peer that is queried by a victim node for a missing attachment can respond with an arbitrarily large `content` field (multi-megabyte or larger, limited only by generic HTTP/message size limits, not by `attachments_max_size`). The victim node will store this oversized blob permanently in its `AtlasDB` `attachments` table via `insert_instantiated_attachment`, bypassing the configured `attachments_max_size` bound entirely. This is repeatable per attachment instance that the node needs to resolve, allowing unbounded disk growth via the P2P/RPC attachment-download flow — an unauthenticated write of unbounded-size data to persistent node state, matching the "Critical: unauthenticated/unauthorized write to state" category.

### Likelihood Explanation
Preconditions are minimal: the attacker just needs to be selected as a data source for an `AttachmentRequest` (i.e., advertise the attachment in its `GetAttachmentsInvResponse` inventory) and then serve an oversized `GetAttachmentResponse` when the victim's `AttachmentsDownloader` requests it via `/v2/attachments/{hash}`. No secret, privileged role, or special node configuration is required — any peer that a node syncs attachments from can trigger this. This is a normal, expected step in the Atlas gossip protocol (attachment inventory advertisement followed by attachment content fetch), so the attack surface is easily and repeatably reachable.

### Recommendation
In `AttachmentsDownloader::run` (and in `check_attachment_instances`'s "inboxed" branch), before calling `network.atlasdb.insert_instantiated_attachment(&attachment)`, call `atlasdb.should_keep_attachment(&contract_id, &attachment)` (deriving `contract_id` from the associated `AttachmentInstance`) and discard/skip attachments that fail the check, bumping the peer's failure count instead of storing the oversized content.

### Proof of Concept
```rust
// stackslib/src/net/atlas/download.rs (test module)
#[test]
fn test_oversized_attachment_bypasses_size_check_on_download() {
    let atlas_config = AtlasConfig {
        contracts: {
            let mut c = HashSet::new();
            c.insert(boot_code_id("bns", false));
            c
        },
        attachments_max_size: 1024, // small cap for test
        max_uninstantiated_attachments: 10,
        uninstantiated_attachments_expire_after: 10,
        unresolved_attachment_instances_expire_after: 10,
        genesis_attachments: None,
    };
    let mut atlas_db = AtlasDB::connect_memory(atlas_config.clone()).unwrap();

    // Craft an oversized attachment (bigger than attachments_max_size)
    let big_content = vec![0xAB; 2 * 1024 * 1024]; // 2MB > 1024 bytes cap
    let big_attachment = Attachment::new(big_content);

    // Sanity: should_keep_attachment rejects it
    let bns_contract_id = boot_code_id("bns", false);
    assert!(!atlas_db.should_keep_attachment(&bns_contract_id, &big_attachment));

    // Simulate extend_with_attachments inserting it into the batch context
    let mut ctx = AttachmentsBatchStateContext::new(
        AttachmentsBatch::new(),
        HashMap::new(),
        &ConnectionOptions::default(),
    );
    ctx.attachments.insert(big_attachment.clone());

    // Simulate what AttachmentsDownloader::run does in the Done branch:
    // no should_keep_attachment call before insert_instantiated_attachment
    atlas_db.insert_instantiated_attachment(&big_attachment).unwrap();

    // Confirm it was stored despite exceeding attachments_max_size
    let stored = atlas_db.find_attachment(&big_attachment.hash()).unwrap();
    assert!(stored.is_some(), "oversized attachment was stored, bypassing attachments_max_size");
    assert!(stored.unwrap().content.len() as u32 > atlas_db.atlas_config.attachments_max_size);
}
```
This test demonstrates that `insert_instantiated_attachment`, as called directly in `AttachmentsDownloader::run`'s `Done` branch, stores content exceeding `attachments_max_size` because `should_keep_attachment` is never invoked in that path.

    pub fn should_keep_attachment(
        &self,
        contract_id: &QualifiedContractIdentifier,
        attachment: &Attachment,
    ) -> bool {
        if !self.atlas_config.contracts.contains(contract_id) {
            info!(
                "Atlas: will discard posted attachment - {} not in supported contracts",
                contract_id
            );
            return false;
        }
        if attachment.content.len() as u32 > self.atlas_config.attachments_max_size {
            info!("Atlas: will discard posted attachment - attachment too large");
            return false;
        }
        true
    }

    pub fn extend_with_attachments(
        mut self,
        results: &mut BatchedRequestsResult<AttachmentRequest>,
    ) -> AttachmentsBatchStateContext {
        for (request, response) in results.succeeded.drain() {
            let report = self
                .peers
                .get_mut(request.get_url())
                .expect("Atlas: unable to retrieve reliability report for peer");

            let response = if let Some(r) = response {
                r
            } else {
                report.bump_failed_requests();
                continue;
            };

            if let Ok(response) = response.decode_atlas_get_attachment() {
                self.attachments.insert(response.attachment);
                report.bump_successful_requests();
            } else {
                report.bump_failed_requests();
            }
        }
        let mut events_ids = results.faulty_peers.keys().copied().collect::<Vec<usize>>();
        self.events_to_deregister.append(&mut events_ids);

        self
    }
