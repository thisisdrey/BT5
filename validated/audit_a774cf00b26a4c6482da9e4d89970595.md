### Title
Handshake `HandshakeTime` payload field is trusted for freshness without any absolute staleness check, allowing replayed stale handshakes to be accepted as current - ([File: hostmap.go])

### Summary
The `HostInfo.lastHandshakeTime` field is populated directly from the peer-supplied `Time` field inside the Noise handshake payload (`handshake/payload.go`), which the sender sets and the responder later trusts (`handshake/machine.go`, `m.result.HandshakeTime = payload.Time`). This value is explicitly documented as an anti-replay mechanism ("used to avoid an attack where a handshake packet is replayed after some time," `hostmap.go:270-273`), yet the only check ever performed against it is a *relative* comparison against whatever value is already cached for an existing hostinfo entry (`handshake_manager.go` `CheckAndComplete`). There is no absolute freshness bound (e.g., "reject if `abs(now - Time) > N minutes`"), exactly mirroring the oracle report's root cause: a timestamp/freshness field is present but never checked against the current time, only ever cross-checked against other user-supplied data.

### Finding Description
`hostinfo.lastHandshakeTime` is set from `result.HandshakeTime`, which comes straight from the wire payload's `Time` field: [1](#0-0) [2](#0-1) 

`hostmap.go` documents the intent of this field as an anti-replay guard, but the check performed is only relative to a possibly-nonexistent prior value: [3](#0-2) 

The actual enforcement point is `CheckAndComplete`, which only rejects a handshake if `existingHostInfo.lastHandshakeTime >= hostinfo.lastHandshakeTime`. If no `existingHostInfo` is present for the vpn address (e.g., the tunnel was previously torn down, the process restarted, or this is the first handshake seen for that peer since eviction), there is nothing to compare against, and the handshake — including an arbitrarily old `Time` value — is accepted unconditionally: [4](#0-3) 

Unlike the certificate expiry checks, which validate `NotBefore`/`NotAfter` against `time.Now()` (`cert/ca_pool.go` `verify`, `cert/cert_v1.go`/`cert_v2.go` `Expired`), no analogous absolute-time check exists anywhere for the handshake `Time` payload field: [5](#0-4) 

This is the same bug class as the external report: a freshness/timestamp field supplied by an untrusted party is only used opportunistically (comparison against other supplied/cached data) instead of being validated against local wall-clock time with a bounded tolerance window.

### Impact Explanation
An on-path attacker who has captured a legitimate handshake stage-0 packet (`msg1`) from an earlier session can replay it after the original hostinfo entry has been evicted (tunnel torn down due to inactivity, restart, cert rotation, etc.). Because there is no absolute staleness bound on `Time`, the responder will process the packet, validate the (still-CA-trusted, non-expired) attached certificate, and create a new `HostInfo` keyed to the real peer's vpn address with the stale `lastHandshakeTime`, occupying that hostmap slot with a session the responder believes is legitimate. This is a replay of previously-captured handshake data being accepted as fresh — the packet/handshake-authentication analog of the oracle price-feed staleness bug, and it is reachable purely from replaying captured ciphertext, without the attacker possessing any CA-signed certificate of their own.

### Likelihood Explanation
Requires an attacker capable of capturing a prior handshake `msg1` on the wire (on-path or having observed earlier traffic) and later replaying it after the corresponding hostinfo entry has aged out of the hostmap — a state that naturally occurs on tunnel teardown, restart, or connection-manager eviction. No cryptographic break or CA-signed certificate is needed by the attacker; only unmodified replay of previously observed bytes is required, since the acceptance check is relative-only and there is no entry left to compare against in the eviction window.

### Recommendation
Add an absolute freshness check on `payload.Time` at the point it is validated in `handshake/machine.go` (`processPayload`) or `handshake_manager.go`: reject handshakes where `Time` deviates from the responder's/initiator's local `time.Now()` by more than a small configurable tolerance (accounting for clock skew), in addition to the existing relative comparison against cached `lastHandshakeTime`. This closes the gap for the case where no prior hostinfo entry exists to compare against.

### Proof of Concept
Not independently reproduced beyond code-path tracing (no test-harness execution was performed for this analysis). The trace is:
1. Attacker captures a legitimate `msg1` (`header.HandshakeIXPSK0`) with an arbitrary `Time` value from a real handshake between two valid peers.
2. The corresponding `HostInfo` entry for the initiator's vpn address is later evicted from the responder's hostmap (teardown/restart/inactivity, see `connection_manager.go` inactivity handling).
3. Attacker replays the captured `msg1` to the responder. `beginHandshake` → `CheckAndComplete` finds no `existingHostInfo` for that vpn address, so the relative `lastHandshakeTime` comparison is skipped entirely, and the stale handshake is accepted as if fresh: [4](#0-3) 

Because the initiator ephemeral/static private keys are unknown to the attacker, this does not permit decrypting the resulting tunnel, but it does demonstrate that a captured-and-stale handshake message is accepted with no absolute freshness validation, occupying/poisoning the responder's hostmap slot for that peer.
