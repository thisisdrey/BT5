## Title
Unvalidated `ContractType` value used as an array index in permission-operations bitmask check causes uncaught `IndexOutOfBoundsException` (node crash / transaction-processing halt) - (File: `chainbase/src/main/java/org/tron/core/capsule/TransactionCapsule.java`, `actuator/src/main/java/org/tron/core/utils/TransactionUtil.java`, `chainbase/src/main/java/org/tron/common/utils/WalletUtil.java`)

### Summary
The CVE-2024-2698 bug class is: a delegation/authorization check (`check_allowed_to_delegate`/`ipadb_match_acl`) that uses an untrusted "target" argument without proper validation, breaking the intended ACL enforcement. java-tron has a structurally similar pattern in its multi-sig "Active permission operations" ACL: the bitmask lookup that gates which `ContractType` a delegated (non-owner) permission key may invoke uses the raw, attacker-controlled `getTypeValue()` of the transaction's `Contract.type` field as a direct index into a fixed 32-byte bitmap, with no bounds check.

### Finding Description
`Permission.operations` is a fixed 32-byte (256-bit) bitmap; bit `i` says whether `ContractType` value `i` is authorized for that Active permission [1](#0-0) . The enforcement logic is duplicated in three places and all use the same unchecked pattern:

- `TransactionCapsule.checkPermission` (used by `validateSignature`/`addSign`) calls `checkPermissionOperations(permission, contract)` when `permissionId != 0` [2](#0-1) .
- `WalletUtil.checkPermissionOperations` / `TransactionUtil.checkPermissionOperations` compute `int contractType = contract.getTypeValue();` and then do `operations.byteAt(contractType / 8) & (1 << (contractType % 8))` with no range check that `contractType` is within `[0, 255]` [3](#0-2) [4](#0-3) .

Because the protobuf schema is `proto3` [5](#0-4) , the `type` field on `Transaction.Contract` accepts any wire-format int32 value; `getTypeValue()` returns that raw value even when it doesn't correspond to a defined `ContractType` enum constant. An attacker who has already enabled a multi-sig `Active` permission on their own account (a normal, permissionless self-service operation via `AccountPermissionUpdateContract`, gated only by `dynamicStore.getAllowMultiSign()` which is enabled on mainnet [6](#0-5) ) can hand-craft a transaction with `permissionId` referencing that Active permission and set the raw `Contract.type` field to an out-of-range value (e.g., a large integer). When the node reaches `checkPermission`/`checkPermissionOperations`, `contractType / 8` will exceed the operations `ByteString`'s length (32), causing `ByteString.byteAt()` to throw an unchecked `IndexOutOfBoundsException`.

Critically, this check runs *before* signature-weight verification in `validateSignature` (`checkPermission(...)` is called on line 490, before `checkWeight(...)` on line 491) [7](#0-6) , and the surrounding `try/catch` in `validatePubSignature` only catches `SignatureException | PermissionException | SignatureFormatException` — not generic `RuntimeException` — so the `IndexOutOfBoundsException` is not swallowed there [8](#0-7) . The same unguarded pattern is reachable from the `Wallet.getTransactionApprovedList` gRPC/HTTP API path [9](#0-8)  and from `TransactionUtil.getTransactionSignWeight` [10](#0-9)  — those two paths do wrap the whole block in `catch (Exception ex)`, so they are less severe, but the transaction-broadcast/signature-validation path in `TransactionCapsule` does not have that generic safety net at the point the exception is thrown.

This mirrors the CVE-2024-2698 bug class conceptually: an ACL/delegation-scoping mechanism (the operations bitmap, analogous to the SFU2Proxy target-service ACL) is invoked with an attacker-influenced "target" value (`ContractType`) that is not properly validated/bounded before being used to look up the delegation rule, breaking the intended access-control mechanism.

### Impact Explanation
An account owner that has configured any multi-sig `Active` permission (a routine, unprivileged, self-service action) can trigger an uncaught `IndexOutOfBoundsException` during transaction signature/permission validation by submitting a transaction with a malformed `Contract.type` value and a `permissionId` pointing at that Active permission. If this exception is not caught by an outer generic handler in the transaction-processing/block-application call chain (`Manager`/`TronNetDelegate`), it can crash or halt processing of that transaction path on any node that receives/validates it (broadcast propagation, block application), which qualifies as a node crash / denial-of-service impact under the stated acceptance criteria.

### Likelihood Explanation
Reaching this code path requires only: (1) `AllowMultiSign` enabled (already active on mainnet), (2) the attacker's own account has an `Active` permission configured (self-service, requires no special privilege), and (3) crafting a raw transaction with an arbitrary `Contract.type` wire value and referencing that `permissionId` — all of which are actions available to any unprivileged transaction broadcaster.

### Recommendation
Bound-check `contractType` before indexing into `operations` in `checkPermissionOperations` (both `WalletUtil` and `TransactionUtil` copies) and in the equivalent logic path in `TransactionCapsule`: verify `0 <= contractType < operations.size() * 8` (i.e., `< 256`), and reject/deny the operation (throw a `PermissionException`/return `false`) instead of allowing an out-of-range value to flow into `ByteString.byteAt()`. Also verify `contract.getType() != ContractType.UNRECOGNIZED` is rejected consistently across all permission-check call sites, and audit whether `Manager`/`TronNetDelegate` catch broad `RuntimeException` around signature validation as defense in depth.

### Proof of Concept
1. Attacker account `A` has `AllowMultiSign` active on-chain; `A` submits `AccountPermissionUpdateContract` to add an `Active` permission (id=2) with a valid key/threshold — a normal, permissionless operation [11](#0-10) .
2. Attacker crafts a raw `Transaction` whose single `Contract` has `permission_id = 2` and manually sets the enum field `type` at the wire level to an out-of-range value (e.g., raw varint `100000`), with any `parameter` payload.
3. Attacker broadcasts (or otherwise submits) the transaction; node calls `TransactionCapsule.validateSignature` → `checkPermission` → `checkPermissionOperations`, computing `contractType/8 = 12500`, `operations.byteAt(12500)` on a 32-byte `ByteString` throws `IndexOutOfBoundsException`, uncaught by `validatePubSignature`'s catch clause [12](#0-11) .

Note: I was not able to fully trace whether `Manager.java`'s transaction/block application call sites wrap `validateSignature`/`validatePubSignature` in a catch-all `Exception` handler (the search only located call sites, not their surrounding exception handling) — confirming whether this actually crashes the node process versus being caught and only rejecting the single transaction would require reading `Manager.java` and `TronNetDelegate.java` in full, which the index did not surface in enough detail within the remaining budget.

    }
    return false;

  public static boolean checkPermissionOperations(Permission permission, Contract contract)
      throws PermissionException {
    ByteString operations = permission.getOperations();
    if (operations.size() != 32) {
      throw new PermissionException(String.format("operations size must 32, actual: %d",
          operations.size()));
    }
    int contractType = contract.getTypeValue();
    boolean b = (operations.byteAt(contractType / 8) & (1 << (contractType % 8))) != 0;
    return b;
  }

  @Override
  public boolean validate() throws ContractValidateException {

    if (chainBaseManager == null) {
      throw new ContractValidateException(ActuatorConstant.STORE_NOT_EXIST);
    }

    if (this.any == null) {
      throw new ContractValidateException(ActuatorConstant.CONTRACT_NOT_EXIST);
    }

    AccountStore accountStore = chainBaseManager.getAccountStore();
    DynamicPropertiesStore dynamicStore = chainBaseManager.getDynamicPropertiesStore();

    if (dynamicStore.getAllowMultiSign() != 1) {
      throw new ContractValidateException("multi sign is not allowed, "
          + "need to be opened by the committee");
    }
    if (!this.any.is(AccountPermissionUpdateContract.class)) {
      throw new ContractValidateException(
          "contract type error,expected type [AccountPermissionUpdateContract],real type["
              + any.getClass() + "]");
    }
    final AccountPermissionUpdateContract accountPermissionUpdateContract;
    try {
      accountPermissionUpdateContract = any.unpack(AccountPermissionUpdateContract.class);
    } catch (InvalidProtocolBufferException e) {
      logger.debug(e.getMessage(), e);
      throw new ContractValidateException(e.getMessage());
    }
    byte[] ownerAddress = accountPermissionUpdateContract.getOwnerAddress().toByteArray();
    if (!DecodeUtil.addressValid(ownerAddress)) {
      throw new ContractValidateException("invalidate ownerAddress");
    }
    AccountCapsule accountCapsule = accountStore.get(ownerAddress);
    if (accountCapsule == null) {
      throw new ContractValidateException("ownerAddress account does not exist");
    }

    if (!accountPermissionUpdateContract.hasOwner()) {
      throw new ContractValidateException("owner permission is missed");
    }

    if (accountCapsule.getIsWitness()) {
      if (!accountPermissionUpdateContract.hasWitness()) {
        throw new ContractValidateException("witness permission is missed");
      }
    } else {
      if (accountPermissionUpdateContract.hasWitness()) {
        throw new ContractValidateException("account isn't witness can't set witness permission");
      }
    }

    if (accountPermissionUpdateContract.getActivesCount() == 0) {
      throw new ContractValidateException("active permission is missed");
    }
    if (accountPermissionUpdateContract.getActivesCount() > 8) {
      throw new ContractValidateException("active permission is too many");
    }

    Permission owner = accountPermissionUpdateContract.getOwner();
    Permission witness = accountPermissionUpdateContract.getWitness();
    List<Permission> actives = accountPermissionUpdateContract.getActivesList();

    if (owner.getType() != PermissionType.Owner) {
      throw new ContractValidateException("owner permission type is error");
    }
    checkPermission(owner);
    if (accountCapsule.getIsWitness()) {
      if (witness.getType() != PermissionType.Witness) {
        throw new ContractValidateException("witness permission type is error");
      }
      checkPermission(witness);
    }
    for (Permission permission : actives) {
      if (permission.getType() != PermissionType.Active) {
        throw new ContractValidateException("active permission type is error");
      }
      checkPermission(permission);
    }
    return true;
  }
