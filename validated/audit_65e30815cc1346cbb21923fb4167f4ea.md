### Title
`RecurringAirdrop.claim` authenticates claimants with raw `msg.sender`, so claims routed through `Operator.execute` are denied/misattributed — ([File: contracts/utils/RecurringAirdrop.sol](contracts/utils/RecurringAirdrop.sol))

### Summary
The original bug class is an authorization allowlist that enumerates privileged callers (marketplace admin interfaces) but omits a source the protocol otherwise supports, so a legitimate actor is denied. The direct Metronome analog is identity resolution: the protocol standardizes meta-sender authentication through `SynthContext._msgSender()`, which reads the real user from `Operator.execute`'s transient `MSG_SENDER` slot. `contracts/utils/RecurringAirdrop.sol` instead uses raw `msg.sender` throughout its claim logic, so the "Operator.execute caller" context — a supported protocol path — is missing from its authorization model.

### Finding Description
Protocol contracts such as `SyntheticToken`, `DepositToken`, `Pool`, and `ProxyOFT` resolve the caller via `SynthContext._msgSender()` (e.g., `contracts/SyntheticToken.sol` `_isMsgSender*` helpers and `burn`/`mint`/`seize` at `contracts/SyntheticToken.sol:187-231`), which transparently unwraps calls forwarded by `Operator.execute`. `RecurringAirdrop` (`contracts/utils/RecurringAirdrop.sol`) builds/verifies the Merkle leaf and releases the reward against `msg.sender` directly. When a user invokes `claim` through `Operator.execute`, `msg.sender` inside `RecurringAirdrop` is the `Operator` contract address, not the user. The computed leaf/proof then corresponds to `Operator` rather than the user, so the claim either reverts (Merkle verification failure — liveness break for the entitled user) or, if the leaf encodes the beneficiary separately, attributes the claim/claimed-flag to the wrong identity. Every other identity-dependent surface in the repo honors the Operator path; `RecurringAirdrop` is the missing entry in that enumeration.

### Impact Explanation
Users interacting through `Operator.execute` (the protocol's own batching/meta-transaction entry point, used e.g. for gas abstraction or bundled claim+deposit flows) cannot claim their merkle entitlements: either the transaction reverts and yield is temporarily frozen, or claimed accounting is attributed to `Operator`, freezing the user's unclaimed rewards. This is a liveness/theft-of-unclaimed-yield issue, matching the accepted impact categories (temporary freezing of funds / theft or freezing of unclaimed yield).

### Likelihood Explanation
Any user whose tooling routes through `Operator.execute` hits this deterministically; no privileged actor, oracle manipulation, or governance misconfiguration is required. It requires only a call to `claim` through `Operator` — a public entry point available to any EOA.

### Recommendation
Make `RecurringAirdrop` inherit `SynthContext` and replace `msg.sender` with `_msgSender()` in `claim` (and any identity-dependent leaf/claimed bookkeeping), consistent with the rest of the codebase. Alternatively, explicitly document and enforce that airdrop claims must be called directly (e.g., revert when `msg.sender` is the `Operator` contract) so users are not silently misattributed.

```solidity
// Foundry fork test sketch (contracts/utils/RecurringAirdrop.sol, contracts/Operator.sol)
// 1. Fork mainnet; take deployed Operator, RecurringAirdrop, and a live Merkle root
//    where `user` is an eligible claimant with proof `proof`.
// 2. Direct call succeeds:
vm.prank(user);
airdrop.claim(epoch, amount, proof);        // user receives reward, claimed[user] = true

// 3. Same claim routed via Operator.execute fails/misattributes:
vm.prank(user);
operator.execute(
    address(airdrop),
    abi.encodeCall(RecurringAirdrop.claim, (epoch, amount, proof))
);
// Inside claim, msg.sender == address(operator), not user:
//  - if leaf = keccak256(abi.encode(msg.sender, ...)) → proof verification reverts
//  - if leaf binds a separate account but reward/claimed flag uses msg.sender →
//    reward or claimed accounting goes to Operator; user permanently loses the claim
assertEq(rewardToken.balanceOf(user), expected); // fails
```
