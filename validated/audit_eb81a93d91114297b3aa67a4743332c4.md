### Title
`TokenDiff::token_fee` fee bypass via splitting a Nep245/Imt trade into unit-amount legs - (File: contracts/defuse/core/src/intents/token_diff.rs)

### Summary
`TokenDiff::token_fee` waives the protocol fee whenever a single `TokenDiff` leg's `|delta| <= 1` for `Nep245`/`Imt` token types, but this check is evaluated independently per `TokenDiff` intent instance rather than on the aggregate volume a signer actually moves. A signer can split what would logically be one `N`-unit trade into `N` separate `TokenDiff` intents (same batch, same or distinct `Nep245TokenId` legs, each with `diff = -1`) and pay zero fee on every leg, whereas expressing the identical net trade as a single `TokenDiff` with `delta = -N` would incur `fee.fee_ceil(N) > 0`.

### Finding Description
Binding claimed broken: `Pips::ONE_PERCENT.fee_ceil(N)` (fee owed for one signer consuming `N` units of a Nep245/Imt token in a single logical trade) should equal `Σ_{i=1..N} TokenDiff::token_fee(token_id_i, 1, Pips::ONE_PERCENT).fee_ceil(1)` for the semantically-equivalent split trade. Before exploit (single `TokenDiff{ diff: {token_id: -N} }`): `token_fee` hits `TokenIdType::Nep245 | TokenIdType::Imt if amount > 1 => {}` (true branch, since `N>1`), falls through to `fee`, giving `fee.fee_ceil(N) = ceil(N/100)` for `ONE_PERCENT`, which is `>0` for `N>=1`. After exploit (`N` separate `TokenDiff` intents, each `diff = {token_id_i: -1}`): each call is `token_fee(token_id_i, 1, fee)`, which hits the `amount > 1` guard as false, falls to `TokenIdType::Nep171 | TokenIdType::Nep245 | TokenIdType::Imt => return Pips::ZERO` at [1](#0-0)  — so every leg's fee is `0`, and the sum across all `N` legs is `0 != ceil(N/100)`.

The reachable path is: `Engine::execute_signed_intents` iterates every signed `MultiPayload` and calls `execute_signed_intent` for each [2](#0-1) , which in turn calls `DefuseIntents::execute_intent`, iterating every `TokenDiff` (or other intent) inside that one signed payload independently [3](#0-2) . Each `TokenDiff::execute_intent` computes and collects its own fee per-instance and credits `fee_collector` immediately via `internal_add_balance` [4](#0-3) . There is no aggregation of `amount` across multiple `TokenDiff` intents (whether inside one signed payload or across many signed payloads in one `execute_intents` batch) before `token_fee` is evaluated — the "amount > 1" carve-out for NFT-style single-unit MT items is trivially defeated by re-partitioning the same net trade into unit legs.

None of the existing guards prevent this: `MultiPayload::verify`, `has_public_key`, nonce/salt checks, and `TransferMatcher::finalize`'s invariant check [5](#0-4)  only validate that deltas net to zero across the whole batch and that signatures/nonces are valid — they never touch or reconstruct the fee that should have been charged. Nothing stops a signer from choosing how many `TokenDiff` intents to emit for what is economically one trade.

The attacker's exact payload: within one `MultiPayload`/`DefuseIntents` signed message (or across several signed messages in the same `execute_intents`/`simulate_intents` call), include `N` `TokenDiff` intents, each with `diff = {token_id: -1, counterpart_token_id: +k}` (using the same `token_id` repeated across intents, or `N` distinct `Nep245TokenId`s representing the same asset family the attacker already holds `N` units of) instead of one `TokenDiff{ diff: {token_id: -N, ...} }`.

### Impact Explanation
`fee_collector` under-collects the protocol fee owed on Nep245/Imt-denominated volume: for any real Nep245 multi-token balance a signer holds in the Verifier, splitting the "token_in" leg into unit-sized `TokenDiff` intents zeroes the fee entirely regardless of `N`, while the semantically identical single-intent trade would pay `fee.fee_ceil(N)`. This is repeatable on every trade, by every account, for every Nep245/Imt token, with no cap — this is a systemic fee bypass matching the "protocol fees bypassed" Critical category, since it diverts revenue that should accrue to `fee_collector` with no equivalent value returned to the Verifier.

### Likelihood Explanation
No privileged role is required — any signer constructing their own `MultiPayload` of `TokenDiff` intents can do this at will, at the cost only of slightly larger message/gas size for the extra legs. It requires only that the signer already hold (or has deposited) an Nep245/Imt balance and that a counterparty (or their own matched leg) is willing to complete the trade, both of which are standard, unprivileged Verifier usage. This is fully attacker-controlled and trivially repeatable across accounts and tokens.

### Recommendation
Aggregate the true intended amount before applying the `amount > 1` NFT/MT exemption — e.g., compute/require fee based on total negative delta on a given `TokenId` accumulated across all `TokenDiff` intents from the same signer within an execution batch (or disallow multiple `TokenDiff` intents referencing the same `token_id` split into sub-unit legs), rather than evaluating `token_fee` per isolated `TokenDiff` instance.

### Proof of Concept
`cargo test` (near-workspaces sandbox, in `tests/src/tests/defuse/intents/token_diff.rs` style):
1. Deploy an MT contract, deposit balance `N` (e.g. `N=1000`) of a single `Nep245TokenId` to `solver` inside the Verifier; set `fee = Pips::ONE_PERCENT`.
2. Sign one `MultiPayload` containing a single `TokenDiff{ diff: {token_id: -N, token_out: +k} }` matched against a counterparty; execute; assert `fee_collector` balance of `token_id` equals `Pips::ONE_PERCENT.fee_ceil(N)` (>0).
3. Reset state; sign a second `MultiPayload` containing `N` separate `TokenDiff` intents each `{token_id: -1, token_out: +k/N}` (matched leg by leg against counterparty intents summing to the same net trade); execute.
4. Assert `fee_collector` balance of `token_id` after step 3 is `0`, while `Pips::ONE_PERCENT.fee_ceil(N) > 0` — demonstrating the binding is broken.
