### Title
Unbounded array allocation from attacker-controlled ABI length field in TVM precompiles `ValidateMultiSign`/`BatchValidateSign` (rpcbomb-style OOM) - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The `ValidateMultiSign` and `BatchValidateSign` precompiled contracts decode an ABI-encoded `bytes[]`/`address[]` array by reading a length word directly from attacker-supplied call data and immediately allocating a Java array of that size — `new byte[len][]` — before any bound is enforced. The bounding check (`MAX_SIZE`) only runs when the `ALLOW_TVM_SELFDESTRUCT_RESTRICTION` chain parameter has been activated by governance, which defaults to `0` (disabled) unless a super-representative proposal explicitly turns it on. This mirrors the root cause of CVE-2017-8779 (rpcbomb): a length field taken from untrusted input is used to size a memory allocation without first validating it against the actual size of the available data.

### Finding Description
`extractBytesArray` and `extractBytes32Array` read an unchecked length and allocate accordingly: [1](#0-0) 

Both `ValidateMultiSign.execute` and `BatchValidateSign.doExecute` only bound-check the declared array size when `VMConfig.allowTvmSelfdestructRestriction()` is true; otherwise they call the unbounded extractor directly: [2](#0-1) [3](#0-2) 

`allowTvmSelfdestructRestriction()` defaults to `false` (`0`) unless a proposal is passed to enable it, so on any chain (or any point in time before that governance proposal passes) the vulnerable, unbounded path is the one exercised: [4](#0-3) 

The declared length `words[offset].intValueSafe()` is fully attacker-controlled and independent of the actual `rawData`/`data` byte-array length. `getEnergyForData` computes cost from the *real* `data.length` only, not from the value embedded at the attacker-chosen offset: [5](#0-4) [6](#0-5) 

Because the energy charge is decoupled from the declared array length, an attacker can craft a small, cheap call whose payload contains one word pointing at a "length" of up to `Integer.MAX_VALUE`, causing `new byte[len][]` (or `bytesArray = new byte[len][]` inside the loop) to attempt to allocate an enormous reference array before the loop ever touches the (small) real data — exactly the "do not consider the maximum data size during memory allocation" pattern from the rpcbomb advisory.

### Impact Explanation
Any account can trigger this by issuing a `TriggerSmartContract` (or via an internal `CALL`/`STATICCALL` from any contract) to the `ValidateMultiSign` or `BatchValidateSign` precompiled contract addresses with crafted calldata. A successful huge allocation attempt throws `OutOfMemoryError`, which is not a checked `Exception` and is not guaranteed to be caught cleanly by every caller path (the `BatchValidateSign.execute` wrapper only catches `Throwable` for its own body but the OOM can still destabilize the JVM heap for the whole node process, including other concurrently executing threads/witness/API threads). This is a genuine node crash / denial-of-service vector reachable from an unprivileged, unauthenticated transaction broadcaster or JSON-RPC/HTTP caller triggering constant calls, matching the "node crash or halt" acceptance criterion.

### Likelihood Explanation
High: the vulnerable path is the *default* behavior on any deployment where the `ALLOW_TVM_SELFDESTRUCT_RESTRICTION` proposal has not been passed (default `0`), and precompiles are reachable from ordinary smart-contract calls with attacker-chosen calldata at negligible energy cost (the cost formula only reflects real calldata length, not the crafted length field). No special permission or SR/witness role is required — a single crafted contract call from any funded account (or even an unfunded static/constant call in some RPC paths) is sufficient to reach `extractBytesArray`/`extractBytes32Array`.

### Recommendation
Move the `MAX_SIZE` (and any other sanity bound, e.g., against `rawData.length`/`data.length`) check unconditionally before calling `extractBytesArray`, `extractSigArray`, and `extractBytes32Array`, independent of the `allowTvmSelfdestructRestriction` feature flag, so the fix applies to already-deployed/legacy behavior as well. Additionally, `extractBytesArray`/`extractBytes32Array` should validate the declared `len` against the remaining bytes actually available in `data` (similar to the `verifyLength`/`calcLength` bound-checking pattern already used in `RLP.java`) before allocating any array.

### Proof of Concept
1. Ensure `ALLOW_TVM_SELFDESTRUCT_RESTRICTION` proposal has not been activated (default state, `getAllowTvmSelfdestructRestriction()` returns `0`).
2. Construct calldata for `validatemultisign(address,uint256,bytes32,bytes[])` (selector for `ValidateMultiSign`) where the static head correctly encodes `address`, `permissionId`, `hash`, and the offset for `bytes[]`, but the word at that offset (the array's declared length) is set to a very large value (e.g., `0x7FFFFFFF`), while the actual calldata trailing the offset is only a few bytes long — keeping `data.length` small so `getEnergyForData` charges minimal energy.
3. Issue this as a `TriggerConstantContract`/`TriggerSmartContract` call (or a `CALL` opcode from another contract) targeting the `ValidateMultiSign` precompile address.
4. `extractBytesArray(words, offset, rawData)` executes `int len = words[offset].intValueSafe();` then `new byte[len][]`, attempting an allocation on the order of gigabytes, which triggers `OutOfMemoryError` in the VM execution thread — verified structurally by the code at [7](#0-6)  and the flag-gated bound check at [2](#0-1) .

Note: I was unable to inspect the exact implementation of `DataWord.intValueSafe()` in this session (only its declaration location was located), so the precise clamping behavior for out-of-int-range words (e.g., whether it throws, clamps to `Integer.MAX_VALUE`, or wraps) could not be confirmed from source in this pass — this affects the exact magnitude of the allocation attempt but does not change the underlying finding that the length used for allocation is unbounded relative to the real payload size before the `MAX_SIZE` check.

  private static byte[][] extractBytes32Array(DataWord[] words, int offset) {
    int len = words[offset].intValueSafe();
    byte[][] bytes32Array = new byte[len][];
    for (int i = 0; i < len; i++) {
      bytes32Array[i] = words[offset + i + 1].getData();
    }
    return bytes32Array;
  }

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }

  public long getAllowTvmSelfdestructRestriction() {
    return Optional.ofNullable(getUnchecked(ALLOW_TVM_SELFDESTRUCT_RESTRICTION))
        .map(BytesCapsule::getData)
        .map(ByteArray::toLong)
        .orElse(0L);
  }

  public void saveAllowTvmSelfdestructRestriction(long value) {
    this.put(ALLOW_TVM_SELFDESTRUCT_RESTRICTION, new BytesCapsule(ByteArray.fromLong(value)));
  }

  public boolean allowTvmSelfdestructRestriction() {
    return getAllowTvmSelfdestructRestriction() == 1L;
  }
