### Title
Integer truncation in `CostModel::get_instructions_data_cost` under-accounts data-byte CU cost, unlike other cost model rounding, enabling systematic QoS-limit underpricing - ([File: cost-model/src/cost_model.rs])

### Summary
The Bond `_currentMarketPrice` bug was a rounding-direction inconsistency: one price-computation path rounded up (protecting makers), a parallel path used plain (floor) division, silently underpricing the same quantity. The Agave cost model exhibits the same class of inconsistency: most per-transaction cost components round **up** (ceiling division) to conservatively account for partial units, but `get_instructions_data_cost` performs plain integer (floor) division, silently under-accounting the "data bytes" compute-unit cost component that feeds directly into block/account QoS limits and transaction scheduling priority.

### Finding Description
`CostModel::get_instructions_data_cost` computes the CU cost for instruction data bytes using truncating integer division: [1](#0-0) 

```rust
fn get_instructions_data_cost(transaction: &impl TransactionMeta) -> u16 {
    transaction.instruction_data_len() / (INSTRUCTION_DATA_BYTES_COST as u16)
}
```

`INSTRUCTION_DATA_BYTES_COST` is itself `140 / COMPUTE_UNIT_TO_US_RATIO` = `140/30` = 4 (also floor-divided), so any `instruction_data_len` that is not an exact multiple of 4 loses the remainder entirely instead of being rounded up to the next whole compute unit: [2](#0-1) 

By contrast, the sibling helper `calculate_pages_for_bytes`, used for the loaded-accounts-data-size cost component in the very same file, explicitly rounds up via ceiling division with a documented rationale ("Compute the number of pages needed to contain provided number of bytes"): [3](#0-2) 

This is exactly the Bond pattern: two computations of conceptually the same class of quantity (a "cost that should be rounded conservatively upward") diverge in rounding direction within the same module, and the one that matters for downstream limits/pricing (`get_instructions_data_cost`) is the one that under-rounds.

`data_bytes_cost` computed this way is summed into every transaction's total accounted cost via `TransactionCost::sum()`: [4](#0-3) 

That sum is what `CostTracker::would_fit` uses to admit/reject transactions against the block, per-account, and other QoS limits: [5](#0-4) 

It is also used to compute per-transaction "priority" (`P = R / (1 + C)`) in both the banking-stage scheduler path and the forwarding-stage priority-floor path, where `C` is this same cost sum: [6](#0-5) [7](#0-6) 

### Impact Explanation
Because instruction data cost is truncated rather than rounded up, every transaction whose total instruction data length is not an exact multiple of 4 bytes has its accounted CU cost underestimated by up to 3 CU (`INSTRUCTION_DATA_BYTES_COST - 1`, since the constant itself is 4). This is a small per-transaction slippage, but it is:
- Systematic and attacker-controllable: any unprivileged user can craft instruction data lengths (e.g., `4k+3` bytes) to always land in the worst-case truncation bucket, maximizing under-accounting per transaction.
- Multiplied across an entire block: with tens of thousands of transactions per block, the aggregate CU under-accounting against `MAX_BLOCK_UNITS`/`MAX_WRITABLE_ACCOUNT_UNITS` becomes a nontrivial, deliberately exploitable discount versus the true resource consumption, i.e., "grossly underpriced pre-fee work" relative to the cost model's own accounting intent — a QoS/cost-limit evasion vector, analogous to makers being shortchanged by the Bond rounding-direction mismatch.
- It also skews the scheduler's `P = R / (1 + C)` priority formula, since the recorded cost `C` is understated, systematically inflating computed priority for transactions with data lengths crafted to hit the truncation worst case, relative to transactions whose lengths round cleanly.

The magnitude per transaction is small, but the vulnerability class matches the pattern explicitly called out as acceptable ("grossly underpriced pre-fee work" / QoS evasion) because it is a reproducible, adversarially-optimizable, protocol-level inconsistency, not a one-off rounding artifact.

### Likelihood Explanation
High likelihood of triggering: any transaction submitted by any unprivileged network participant with an instruction-data length not divisible by 4 hits this path; an attacker who wants to maximize the discount simply pads/crafts instruction data length to `4k+3`. No special permissions, staking, or leader status are required — this fires on the standard banking-stage/cost-model code path used for every transaction that reaches `CostModel::calculate_cost`/`calculate_cost_for_executed_transaction`/`estimate_cost`.

### Recommendation
Change `get_instructions_data_cost` to use ceiling (round-up) division, consistent with `calculate_pages_for_bytes` and the rest of the cost model's conservative-rounding convention:

```rust
fn get_instructions_data_cost(transaction: &impl TransactionMeta) -> u16 {
    transaction
        .instruction_data_len()
        .div_ceil(INSTRUCTION_DATA_BYTES_COST as u16)
}
```

This mirrors the Bond Protocol fix of switching `_currentMarketPrice` from `mulDiv` (floor) to `mulDivUp` (ceiling) to match the already-correct rounding direction used elsewhere in the same contract.

### Proof of Concept
1. Construct a transaction whose total instruction data length across all instructions is `4k + 3` bytes for some `k` (e.g., 7 bytes of instruction data).
2. Compute `CostModel::get_instructions_data_cost` for this transaction: `7 / 4 = 1` (truncated), whereas the "true" ceiling-rounded cost should be `⌈7/4⌉ = 2`.
3. This transaction cost is 1 CU lower than it should be, and is summed into `TransactionCost::sum()`, `CostTracker::would_fit`'s block/account cost checks, and the `calculate_priority_and_cost` denominator used by both the greedy scheduler and forwarding-stage priority floor.
4. Repeat with many transactions each crafted to have data length `≡ 3 (mod 4)`; the aggregate under-accounting scales linearly with transaction count in the block, systematically discounting the true resource cost recorded against `MAX_BLOCK_UNITS` / `MAX_WRITABLE_ACCOUNT_UNITS`, exactly mirroring how Bond's floor-divided `_currentMarketPrice` silently underpriced tokens relative to the whitepaper's specified ceiling-rounded price.

```rust
pub(crate) fn calculate_priority_and_cost<Tx: TransactionMeta + SVMStaticMessage>(
    bank: &Bank,
    transaction: &Tx,
    transaction_configuration: &TransactionConfiguration,
) -> (u64, u64) {
    let cost = CostModel::calculate_cost_for_executed_transaction(
        transaction,
        u64::from(transaction_configuration.compute_unit_limit),
        transaction_configuration.loaded_accounts_data_size_limit,
        &bank.feature_set,
    )
    .sum();
    let fee_details = solana_fee::calculate_fee_details(
        transaction,
        bank.fee_structure().lamports_per_signature,
        transaction_configuration.priority_fee_lamports,
        bank.fee_features(),
    );
    let reward = bank
        .calculate_reward_and_burn_fee_details(&CollectorFeeDetails::from(fee_details))
        .get_deposit();

    // We need a multiplier here to avoid rounding down too aggressively.
    // For many transactions, the cost will be greater than the fees in terms of raw lamports.
    // For the purposes of calculating prioritization, we multiply the fees by a large number so that
    // the cost is a small fraction.
    // An offset of 1 is used in the denominator to explicitly avoid division by zero.
    const MULTIPLIER: u64 = 1_000_000;
    (
        reward
            .saturating_mul(MULTIPLIER)
            .saturating_div(cost.saturating_add(1)),
        cost,
    )
}
```

```rust
fn calculate_priority(
    transaction: &RuntimeTransaction<SanitizedTransactionView<&[u8]>>,
    bank: &Bank,
) -> Option<u64> {
    let transaction_configuration = transaction
        .transaction_configuration(&bank.feature_set)
        .ok()?;

    // Manually estimate fee here since currently interface doesn't allow a on SVM type.
    // Doesn't need to be 100% accurate so long as close and consistent.
    let prioritization_fee = transaction_configuration.priority_fee_lamports;
    let signature_details = transaction.signature_details();
    let signature_fee = signature_details
        .total_signatures()
        .saturating_mul(bank.fee_structure().lamports_per_signature);
    let fee_details = FeeDetails::new(signature_fee, prioritization_fee);

    let reward = bank
        .calculate_reward_and_burn_fee_details(&CollectorFeeDetails::from(fee_details))
        .get_deposit();

    let cost = CostModel::estimate_cost(
        transaction,
        transaction.program_instructions_iter(),
        transaction.num_requested_write_locks(),
        &bank.feature_set,
    );

    // We need a multiplier here to avoid rounding down too aggressively.
    // For many transactions, the cost will be greater than the fees in terms of raw lamports.
    // For the purposes of calculating prioritization, we multiply the fees by a large number so that
    // the cost is a small fraction.
    // An offset of 1 is used in the denominator to explicitly avoid division by zero.
    const MULTIPLIER: u64 = 1_000_000;
    Some(
        MULTIPLIER
            .saturating_mul(reward)
            .wrapping_div(cost.sum().saturating_add(1)),
    )
}
```
