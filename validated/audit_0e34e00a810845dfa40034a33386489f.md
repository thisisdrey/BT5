### Title
`transfer_to_new_account`/`transfer_to_new_account_pda` allow migrating a marginfi account to the zero-address authority, permanently locking funds - ([File: programs/marginfi/src/instructions/marginfi_account/transfer_account.rs])

### Summary
The `TransferToNewAccount` and `TransferToNewAccountPda` instructions accept a `new_authority` account that is explicitly documented as "completely unchecked," with no on-chain guard against `Pubkey::default()`. This mirrors the reported bug class: a critical address parameter is missing a zero-address guard, so the state machine can be driven into an unrecoverable state — here, permanently freezing the migrated marginfi account's assets under an unownable authority.

### Finding Description
`transfer_to_new_account` and `transfer_to_new_account_pda` move a user's entire `lending_account` (all deposits/borrows) from `old_marginfi_account` to a freshly initialized `new_marginfi_account`, whose `authority` field is set to whatever `new_authority` account is passed in: [1](#0-0) 

The `new_authority` account is declared with a comment acknowledging it is unchecked: [2](#0-1) [3](#0-2) 

No `check!`/`require!` anywhere in `transfer_to_new_account` or `transfer_to_new_account_pda` verifies `new_authority.key() != Pubkey::default()`. Once the instruction succeeds, the old account is irreversibly finalized: its `lending_account` is zeroed out, it is flagged `ACCOUNT_DISABLED`, and `migrated_to` is set to the new account, which also blocks any retry (`AccountAlreadyMigrated`): [4](#0-3) [5](#0-4) 

If `new_authority` is `Pubkey::default()`, the new account (holding all the migrated balances) becomes permanently uncontrollable: every downstream instruction (`withdraw`, `borrow`, `repay`, `place_order`, etc.) requires `authority: Signer<'info>` to match the account's stored authority via `is_signer_authorized`, and nobody can produce a valid signature for the zero pubkey. This is the same bug class as the external report: a missing zero-address check on a critical actor/beneficiary field bypasses the intended safety invariant and drives the system into an irrecoverable state.

Only the CLI (`p0-cli`) client adds a client-side guard against this: [6](#0-5) 
This is not an on-chain enforcement — any other caller (a different frontend, a malicious dApp, a buggy integration, or a raw transaction) can submit `new_authority = Pubkey::default()` directly to the program without going through this CLI check.

### Impact Explanation
This is a permanent-lock/freeze of user funds: once `transfer_to_new_account`/`transfer_to_new_account_pda` completes with `new_authority == Pubkey::default()`, the old account is disabled and drained, and the new account — now holding all the deposits/collateral — can never be signed for again. All assets in that account become permanently inaccessible, a full loss of funds for the account owner.

### Likelihood Explanation
This is reachable directly by an unprivileged, non-admin marginfi account authority: `TransferToNewAccount`/`TransferToNewAccountPda` require only the account's own `authority` signature (`is_signer_authorized`), not an admin. Likelihood of accidental self-triggering is low but plausible (fat-fingered/spoofed `new_authority` value in a UI or scripted flow, or malicious dApp front-running the intended value), and since the operation is irreversible and its safety currently depends entirely on client-side (off-chain) validation in one CLI, the on-chain program itself has no defense-in-depth against this specific input.

### Recommendation
Add an on-chain check in both `transfer_to_new_account` and `transfer_to_new_account_pda` requiring `ctx.accounts.new_authority.key() != Pubkey::default()` before initializing the new account, returning an explicit error (e.g. `MarginfiError::InvalidAuthority`) otherwise — analogous to the fix applied to `registerProposal`/`refund` in the referenced report.

### Proof of Concept
1. Create a marginfi account and deposit collateral as `authority = A`.
2. Call `marginfi_account_transfer_to_new_account` (or the PDA variant) with `new_authority = Pubkey::default()` and a fresh `new_marginfi_account` keypair/PDA.
3. The instruction succeeds: `old_marginfi_account` is zeroed/disabled and `migrated_to` points at the new account; `new_marginfi_account.authority == Pubkey::default()` while it now holds all the migrated balances. [7](#0-6) 
4. Any subsequent attempt to operate on `new_marginfi_account` (withdraw, borrow, repay, close, place order) fails permanently because no signer can match `Pubkey::default()` in `is_signer_authorized`, leaving the funds permanently locked with no recovery path.
