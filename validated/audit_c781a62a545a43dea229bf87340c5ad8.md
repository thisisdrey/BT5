### Title
Replay-window bypass via TOCTOU race between `Check` and `Update` in `ConnectionState.Decrypt`/`VerifyRelay` - (File: `connection_state.go`)

### Summary
`ConnectionState.Decrypt` and `ConnectionState.VerifyRelay` split the anti-replay check into two separately-locked operations — `window.Check()` and `window.Update()` — with the actual AEAD decryption happening in between while the lock is released. This mirrors the `fillOrder` bug class: a value used for an authorization decision (`limitPrice_e36` / here, "has this counter been seen") is read once, mutated/relied-on state is used to perform expensive work, and the authoritative commit of that state happens only afterward, allowing a second concurrent operation to slip through the same window before the first commits.

### Finding Description
`Decrypt` and `VerifyRelay` in `connection_state.go` perform:
1. `cs.decryptLock.Lock(); result := cs.window.Check(l, messageCounter); cs.decryptLock.Unlock()`
2. Perform the (unlocked) AEAD decrypt/verify operation.
3. `cs.decryptLock.Lock(); result = cs.window.Update(l, messageCounter); cs.decryptLock.Unlock()` [1](#0-0) [2](#0-1) 

The replay-window primitive itself (`bits.go`) is correct for a single sequential caller: `Check` only tests whether a counter is `set`, and `Update` is the routine that actually marks it seen, advances the cursor, and rejects duplicates. [3](#0-2) [4](#0-3) 

However, because the lock is dropped between `Check` and `Update`, two goroutines that receive the same message counter `i` (a duplicated/replayed on-wire packet) can both execute `Check` before either calls `Update`. Since `Check` only inspects state, not writes it, both calls can see `i` as "not yet seen" and return `true`. Both goroutines then proceed to decrypt/verify the (identical, replayed) ciphertext, and only afterward call `Update` — at which point one of the two `Update` calls will correctly detect the duplicate and return false, but by then the decrypted/verified payload from the first `Update`-losing goroutine has already been accepted and handed off up the stack (e.g. delivered to the TUN device or, for `VerifyRelay`, forwarded by a relay) before its `Update` call runs.

This is architecturally analogous to the `fillOrder` finding: the "check" (`limitPrice_e36` read / `window.Check`) is decoupled from the state-mutating "use" (`amtOut` calculation and transfer / `window.Update`), and an adversarial or merely concurrent second message can be interleaved in between, letting a message the accounting eventually intends to reject still produce user-visible/consequential effects.

Nebula's interface is explicitly multi-routine: `listenIn`/`listenOut` are spawned per queue (`interface.go`), so packets belonging to the same tunnel/`HostInfo` can, depending on socket/queue affinity, be processed concurrently by different goroutines that call into the same shared `ConnectionState`. [5](#0-4) 

An attacker needs no CA-signed certificate to exploit this: they only need to capture one legitimate ciphertext packet on the wire (nonce/replay handling is exactly the class explicitly in scope) and retransmit it twice, timed to land on two different UDP receive queues/goroutines, to win the race window between `Check` and `Update`.

### Impact Explanation
A successful race allows a captured, previously-transmitted ciphertext packet to be decrypted and accepted a second time despite the replay window being designed to reject it — i.e., a concrete traffic-replay bypass of the anti-replay protection. For relayed traffic (`VerifyRelay`), this could cause a relay node to re-forward an already-seen relay frame, defeating the fix that was specifically added to guarantee relays "drop replayed frames instead of re-forwarding them" per the changelog entry for #1751/#1802. [6](#0-5) 

### Likelihood Explanation
Exploitation requires winning a narrow race window (the time between the unlocked `Check` and the later `Update`, which includes a full AEAD decrypt), and depends on the specific socket/queue architecture actually delivering duplicate packets to different goroutines concurrently for the same `ConnectionState`. I was not able to fully confirm, within the available tool budget, whether Nebula's socket-queue affinity (e.g., a captured packet re-sent twice) can reliably land on two different `listenIn`/`listenOut` goroutines for the same peer at the same time, or whether routing/queue selection is deterministic per-source in a way that would serialize such packets onto the same goroutine (which would eliminate the race in practice). This is the key uncertainty limiting confidence in real-world exploitability.

### Recommendation
Hold `decryptLock` for the entire duration of `Check` → decrypt → `Update` in both `Decrypt` and `VerifyRelay`, so no other goroutine can observe a not-yet-committed state for the same message counter. Alternatively, make the check-and-mark atomic (a single locked `CheckAndUpdate` that returns false immediately if the counter is a duplicate, before any decrypt work begins) so a losing concurrent duplicate is rejected before doing any AEAD work or exposing decrypted output.

### Proof of Concept
Conceptual PoC (not executed, due to uncertainty about queue/goroutine affinity noted above):
1. Establish or observe an active Nebula tunnel and capture one legitimate encrypted data-plane (or relay) packet with message counter `N`.
2. Simultaneously replay this exact captured packet twice in quick succession, e.g. via two sockets/paths likely to be serviced by different `listenIn`/`listenOut` routines (`listen.routines` > 1 config increases queue parallelism, widening the race window).
3. If both copies reach `ConnectionState.Decrypt` (or `VerifyRelay`) before either commits via `window.Update`, both will pass `window.Check`, and the duplicate packet's payload will be decrypted/verified and delivered a second time (or, for relay frames, forwarded a second time) even though the replay window should have rejected the duplicate.

// VerifyRelay verifies AEAD protected (but not encrypted) relay frames. packet must be length-checked by the caller.
func (cs *ConnectionState) VerifyRelay(l *slog.Logger, messageCounter uint64, packet []byte, nb []byte) error {
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	signedPayload := packet[:len(packet)-cs.dKey.Overhead()]
	signatureValue := packet[len(packet)-cs.dKey.Overhead():]
	_, err := cs.dKey.DecryptDanger(nil, signedPayload, signatureValue, messageCounter, nb)
	if err != nil {
		return err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	return nil
}

// Check returns true if i is within (or way out in front of) the window, and not a replay
func (b *Bits) Check(l *slog.Logger, i uint64) bool {
	// If i is the next number, return true.
	if i > b.current {
		return true
	}

	if b.strictlyWithinWindow(i) {
		return !b.get(i)
	}

	// Not within the window
	if l.Enabled(context.Background(), slog.LevelDebug) {
		l.Debug("rejected a packet (top)", "current", b.current, "incoming", i)
	}
	return false
}

func (b *Bits) Update(l *slog.Logger, i uint64) bool {
	// Fast path: i is the next expected counter. Split out so the function
	// stays small and avoids paying for the slow paths' slog argument-build
	// stack frame on every call. The bit read/test/write is inlined to
	// touch the backing word once.
	if i == b.current+1 {
		pos := i & b.lengthMask
		word := pos >> 6
		mask := uint64(1) << (pos & 63)
		w := b.bits[word]
		if i > b.length && w&mask == 0 {
			b.lostCounter.Inc(1)
		}
		b.bits[word] = w | mask
		b.current = i
		return true
	}
	return b.updateSlow(l, i)
}

func (f *Interface) listenIn(reader io.ReadWriteCloser, i int) {
	packet := make([]byte, mtu)
	out := make([]byte, mtu)
	fwPacket := &firewall.Packet{}
	nb := make([]byte, 12, 12)

	conntrackCache := firewall.NewConntrackCacheTicker(f.ctx, f.l, f.conntrackCacheTimeout)

	for {
		n, err := reader.Read(packet)
		if err != nil {
			// Same shutdown noise handling as listenOut
			if !f.closed.Load() && f.ctx.Err() == nil {
				f.l.Error("Error while reading outbound packet, closing", "error", err, "reader", i)
				f.onFatal(err)
			}
			break
		}

		f.consumeInsidePacket(packet[:n], fwPacket, nb, out, i, conntrackCache.Get())
	}

	f.l.Debug("overlay reader is done", "reader", i)
}
