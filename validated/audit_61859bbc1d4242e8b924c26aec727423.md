## Analysis

The Olympus bug's core broken invariant is: **a value-transfer is priced against a stale AMM state at entry, while the matching value-transfer at exit is priced against a *different*, attacker-manipulated AMM state**, and the attacker controls the manipulation step end-to-end within a single, self-contained operation (no malicious relayer/validator needed).

The closest local analog is `pallet-asset-conversion-tx-payment`'s `SwapAssetAdapter`, which pays transaction fees in a non-native asset by swapping through `pallet-asset-conversion` pools twice per extrinsic: once at `withdraw_fee` (pre-dispatch) and once at `correct_and_deposit_fee` (post-dispatch, for refunding unused fee). [1](#0-0) [2](#0-1) 

Between these two calls, the extrinsic's own `RuntimeCall` is dispatched. If the user's `asset_id` (chosen fee-payment asset) is pool with the native asset via `pallet-asset-conversion`, the user can craft the dispatched `RuntimeCall` itself to perform a swap against that exact pool, shifting reserves between the pre-dispatch withdrawal (state S0) and the post-dispatch refund conversion (state S1). `pallet-asset-conversion`'s own `QuotePrice` documentation explicitly warns this gap is unsafe: "the quoted price is only guaranteed if no other swaps are made after the price is quoted and before the target swap... the swap is made immediately within the same transaction" — a guarantee that `withdraw_fee` and `correct_and_deposit_fee` each individually respect (quote immediately followed by swap), but which is violated across the *pair*, because a third-party swap (the dispatched call itself) can execute strictly between them. [3](#0-2) 

This lets an unprivileged signed-extrinsic sender: (1) pay fees in asset X, withdrawing a small `asset_fee` at pool state S0 via `quote_price_tokens_for_exact_tokens`/`swap_tokens_for_exact_tokens`; (2) have the dispatched call itself execute a large `swap_exact_tokens_for_tokens`/`swap_tokens_for_exact_tokens` against the same X/native pool, shifting the reserve ratio to S1; (3) collect a refund of unused fee computed via `quote_price_exact_tokens_for_tokens(A, X, refund_amount, true)` and swapped back at the now-favorable S1 ratio, extracting more asset X than is fair relative to what was withdrawn at S0 — the exact "deposit at price1 → manipulate → withdraw at price2" pattern from the Olympus report, self-contained in one atomic extrinsic and paid for out of the AMM's own liquidity (LPs bear the loss). [4](#0-3) [5](#0-4) 

### Title
Fee-refund price computed after the wrapped call executes lets an attacker self-sandwich the fee-payment AMM pool via `SwapAssetAdapter` - (File: substrate/frame/transaction-payment/asset-conversion-tx-payment/src/payment.rs)

### Summary
`SwapAssetAdapter::withdraw_fee` converts asset `X` into native fee currency `A` at the pool's pre-dispatch reserve ratio, while `SwapAssetAdapter::correct_and_deposit_fee` converts the unspent portion of `A` back into `X` at the pool's *post*-dispatch reserve ratio. Because the dispatched `RuntimeCall` executes strictly between these two points and can itself invoke `pallet-asset-conversion`'s swap extrinsics on the very same pool, a user paying fees in asset `X` can move the pool price between the withdrawal and the refund legs of their own transaction, extracting value from the pool's liquidity providers instead of just paying a fair fee.

### Finding Description
`ChargeAssetTxPayment::prepare` calls `OnChargeAssetTransaction::withdraw_fee`, which quotes and immediately swaps `X → A` for the estimated `fee`, at pool state S0. [6](#0-5) 

The runtime then dispatches the extrinsic's `RuntimeCall` (standard FRAME extension lifecycle: `validate` → `prepare` → dispatch → `post_dispatch_details`). [7](#0-6) 

`post_dispatch_details` then calls `OnChargeAssetTransaction::correct_and_deposit_fee`, which quotes and swaps `A → X` for the unspent `refund_amount`, at whatever pool state (S1) exists after the call ran. [2](#0-1) 

`pallet-asset-conversion`'s own `QuotePrice` trait documents that a quote is only valid if "no other swaps are made after the price is quoted and before the target swap... immediately within the same transaction" — but here the "transaction" spans the entire extrinsic, and the wrapped call is exactly an "other swap" opportunity fully controlled by the fee payer. [3](#0-2) 

If the dispatched call is (or contains, e.g. via `pallet_utility::batch`) a swap against the same `X`/`A` pool that pushes the reserve ratio so that `X` becomes relatively cheaper in terms of `A` (i.e., increases `reserve_X`/`reserve_A`), the subsequent refund conversion `A → X` yields more `X` per unit of `A` refunded than the price paid when `X` was withdrawn upfront. No existing guard (slippage check, `TransactionalProcessor`, or reentrancy lock) prevents the wrapped call from mutating the same pool used for the extension's own fee conversion — the two swap legs are individually "quote-then-swap-immediately" safe, but the pair straddling the call dispatch is not.

### Impact Explanation
This allows systematic, repeatable extraction of value from AMM liquidity providers by any signed-extrinsic sender, with no privileged access, malicious validator/collator, or off-chain infrastructure required — matching the "public underpriced work that degrades... " and unbacked-value-extraction impact categories: fees intended to price block space/weight can be effectively reduced or converted at a manipulated rate, and the resulting loss is borne by the liquidity pool rather than reflecting the actual cost of the dispatched work. Runtimes such as Asset Hub that configure `ChargeAssetTxPayment`/`SwapAssetAdapter` with `pallet-asset-conversion` pools are exposed wherever the fee-payment asset is pool-paired with the native asset and ordinary users can also swap in that pool.

### Likelihood Explanation
The attack requires only a single, self-authored signed extrinsic: no cross-block timing, no relayer/validator collusion, and no privileged origin. The attacker fully controls both the fee-payment asset choice and the wrapped call's content (which can itself be an AMM swap on the same pool, or a `batch` including one). The profitability is bounded by the pool's depth, LP fee, and how much of the withdrawn fee is refunded (larger when the declared dispatch weight/fee exceeds the actual consumed weight), giving the attacker a straightforward profitability calculation before executing, exactly as in the source report.

### Recommendation
Do not let the refund leg's price reflect state mutated by the extrinsic's own dispatched call. Options: (1) cache the pool price (or a bound derived from the withdrawal-time price) at `withdraw_fee` time and enforce it as a max/min bound on the refund quote in `correct_and_deposit_fee`; (2) require refunds to use the SAME reserve snapshot as the initial withdrawal rather than re-quoting post-dispatch; (3) disallow paying fees in an asset whose pool the wrapped call is permitted to mutate, or force the refund swap through a `TransactionalProcessor`-protected sub-block that reverts any call-induced state change to that specific pool before refund pricing.

### Proof of Concept
1. Configure a runtime with `ChargeAssetTxPayment<SwapAssetAdapter<Native, Fungibles, AssetConversion, OU>>` and a `X`/`Native` pool via `pallet-asset-conversion`.
2. Attacker submits an extrinsic with `asset_id = X`, a large declared `dispatch_info.weight` (so `fee` computed in `validate`/`prepare` is large), and a `RuntimeCall` that: (a) via `pallet_utility::batch`, swaps a large amount of `X` for `Native` in the same pool (pushing `reserve_X` up / `reserve_Native` down), and (b) returns quickly / reports a small actual weight in `PostDispatchInfo` (e.g. a call whose actual weight is far below its declared worst-case weight).
3. `withdraw_fee` (pre-dispatch) withdraws `asset_fee` of `X` at the original ratio S0, swapping for exactly `fee` of `Native`.
4. The batched call executes, shifting the pool to S1 as in step 2(a).
5. `correct_and_deposit_fee` (post-dispatch) computes `refund_amount = fee - corrected_fee` (large, since actual weight was small) and swaps it `Native → X` at the manipulated ratio S1, crediting the attacker more `X` than the fair amount implied by S0.
6. Attacker reverses the batched swap in a later (or same) transaction; net gain equals the spread between S0 and S1 pricing on `refund_amount`, minus round-trip AMM fees/slippage on the manipulation leg — profitable whenever the refunded fee portion is large relative to the manipulation cost, mirroring the original report's profitability condition.

	fn withdraw_fee(
		who: &T::AccountId,
		_call: &T::RuntimeCall,
		_dispatch_info: &DispatchInfoOf<<T>::RuntimeCall>,
		asset_id: Self::AssetId,
		fee: Self::Balance,
		_tip: Self::Balance,
	) -> Result<Self::LiquidityInfo, TransactionValidityError> {
		if asset_id == A::get() {
			// The `asset_id` is the target asset, we do not need to swap.
			let fee_credit = F::withdraw(
				asset_id.clone(),
				who,
				fee,
				Precision::Exact,
				Preservation::Preserve,
				Fortitude::Polite,
			)
			.map_err(|_| InvalidTransaction::Payment)?;

			return Ok((fee_credit, fee));
		}

		// Quote the amount of the `asset_id` needed to pay the fee in the asset `A`.
		let asset_fee =
			S::quote_price_tokens_for_exact_tokens(asset_id.clone(), A::get(), fee, true)
				.filter(|asset_fee| !asset_fee.is_zero())
				.ok_or(InvalidTransaction::Payment)?;

		// Withdraw the `asset_id` credit for the swap.
		let asset_fee_credit = F::withdraw(
			asset_id.clone(),
			who,
			asset_fee,
			Precision::Exact,
			Preservation::Preserve,
			Fortitude::Polite,
		)
		.map_err(|_| InvalidTransaction::Payment)?;

		let (fee_credit, change) = match S::swap_tokens_for_exact_tokens(
			vec![asset_id, A::get()],
			asset_fee_credit,
			fee,
		) {
			Ok((fee_credit, change)) => (fee_credit, change),
			Err((credit_in, _)) => {
				defensive!("Fee swap should pass for the quoted amount");
				let _ = F::resolve(who, credit_in).defensive_proof("Should resolve the credit");
				return Err(InvalidTransaction::Payment.into());
			},
		};

		// Since the exact price for `fee` has been quoted, the change should be zero.
		ensure!(change.peek().is_zero(), InvalidTransaction::Payment);

		Ok((fee_credit, asset_fee))
	}
