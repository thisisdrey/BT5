This confirms the analog. TRON's Bancor-style Exchange feature (`ExchangeCreateContract`/`ExchangeInjectContract`/`ExchangeWithdrawContract`/`ExchangeTransactionContract`) is still fully live and reachable via broadcastable transactions from any account. Crucially, `ExchangeTransactionContract` explicitly has a `tokenExpected`/`expected` slippage-protection field that's checked (`token required must greater than expected`), but `ExchangeWithdrawContract` has **no equivalent minimum-received field at all** — the exact same class of bug as the reported "amountAMin/amountBMin = 1" issue: the withdrawer has zero on-chain slippage protection and must accept whatever the current AMM-style ratio yields at execution time.

### Title
Missing Slippage/Minimum-Amount Protection in `ExchangeWithdrawActuator` Enables Front-Running Value Extraction - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
`ExchangeWithdrawContract`, unlike its sibling `ExchangeTransactionContract`, carries no `expected`/minimum-received parameter. The pool ratio used to compute the counter-token amount is read fresh at execution time from the current `ExchangeCapsule` balances, so an attacker who sees a pending withdraw transaction in the mempool can sandwich it with `ExchangeTransactionContract` trades to skew the ratio and force the withdrawer to receive far less than expected — the same "no slippage bound" bug class described in the external report.

### Finding Description
`ExchangeWithdrawActuator.execute` computes `anotherTokenQuant` purely from the exchange's live `firstTokenBalance`/`secondTokenBalance` at the moment of execution: [1](#0-0) 
There is no field in `ExchangeWithdrawContract` (per the protocol definition) analogous to `expected` that would let the caller bound the minimum acceptable `anotherTokenQuant`: [2](#0-1) 
Contrast this with `ExchangeTransactionActuator`, which explicitly validates that the computed `anotherTokenQuant` meets a caller-supplied `tokenExpected`: [3](#0-2) 
The withdraw-side validation in `ExchangeWithdrawActuator.doValidate` only checks a "precision" bound (0.01% rounding tolerance) relative to the balances *at validation time*, not a caller-chosen slippage tolerance, and this check is bypassed entirely if the ratio shifts between broadcast and execution: [4](#0-3) 
Since transactions sit in the mempool before block inclusion, and `ExchangeTransactionContract` trades from any account can move `firstTokenBalance`/`secondTokenBalance` arbitrarily (up to the balance limit), an attacker can front-run a pending withdraw with a large trade that skews the ratio, let the victim's withdraw execute at the skewed ratio, then reverse the trade in a following transaction — a classic sandwich attack extracting value from the exchange creator's withdrawal.

### Impact Explanation
The exchange creator (the only account authorized to call `ExchangeWithdrawContract`, per the `is not creator` check) can be forced to receive an amount of the counter-token substantially below fair value, resulting in a direct loss of funds for that account and a corresponding profit for the attacker who manipulated the pool ratio around the withdraw transaction. This is a concrete, unauthorized value-transfer/loss-of-funds impact reachable purely by two ordinary signed transactions (an `ExchangeTransactionContract` trade around a targeted `ExchangeWithdrawContract`), no privileged role required.

### Likelihood Explanation
Any account can create an exchange, inject liquidity, and any account can freely trade against it via `ExchangeTransactionContract` (no minimum liquidity or anti-sandwich protection at the exchange level itself). Mempool visibility of pending `ExchangeWithdrawContract` transactions is inherent to any public broadcaster/miner-visible mempool. The attack requires only relative-timing/ordering control over transactions in the same block window, which is a standard front-running capability, making exploitation realistic wherever this legacy exchange feature is actively used.

### Recommendation
Add a `expected`/`amountXMin`-style field to `ExchangeWithdrawContract`, and enforce it in `ExchangeWithdrawActuator.execute`/`doValidate` analogous to the `tokenExpected` check already present in `ExchangeTransactionActuator`, so withdrawers can bound the minimum counter-token amount they are willing to accept.

### Proof of Concept
1. Attacker monitors the mempool for a pending `ExchangeWithdrawContract` from a known exchange creator address for exchange `X`.
2. Attacker submits an `ExchangeTransactionContract` selling a large amount of `firstToken` into the pool (front-run), shifting `firstTokenBalance`/`secondTokenBalance` sharply.
3. The victim's `ExchangeWithdrawContract` executes, computing `anotherTokenQuant` from the now-skewed ratio in `ExchangeWithdrawActuator.execute` (lines 74-89), yielding far less `secondToken` than the pre-attack ratio implied — with no caller-supplied minimum to reject the trade.
4. Attacker submits a reverse `ExchangeTransactionContract` trade to restore the ratio and realize profit extracted from the victim's withdrawal.
