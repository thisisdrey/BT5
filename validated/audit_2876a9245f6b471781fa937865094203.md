## Title
Outbound Queue V2 fee calculation trusts an attacker-supplied `gas` value for `Command::CallContract`, decoupling the charged fee from actual Ethereum execution cost - (File: `bridges/snowbridge/primitives/outbound-queue/src/v2/message.rs`)

### Summary
The Holograph bug (`H-03`) was caused by computing the fee/gas budget for a cross-chain message using values disconnected from the actual cost of executing the message on the destination chain, which could underprice delivery and permanently strand assets. Snowbridge's Outbound Queue V2 `ConstantGasMeter` has the same structural flaw: for `Command::CallContract`, the gas figure used to compute the delivery fee is taken verbatim from a message field that is fully controlled by whoever constructs the `Command`, with no relationship to the calldata size or actual execution cost of the call being forwarded to Ethereum.

### Finding Description
`GasMeter::maximum_dispatch_gas_used_at_most` is the function used to derive `gas_used_at_most`, which directly feeds `calculate_remote_fee` (`fee_per_gas * gas_used_at_most + reward`) used to price message delivery [1](#0-0) .

For all other v2 commands (`SetOperatingMode`, `Upgrade`, `UnlockNativeToken`, `RegisterForeignToken`, `MintForeignToken`), the gas figure is a fixed constant calibrated from actual forge gas-report measurements of the Gateway contract. But for `Command::CallContract`, the implementation does:

```rust
Command::CallContract { gas: gas_limit, .. } => *gas_limit,
``` [2](#0-1) 

This `gas` field is part of the `Command::CallContract` variant itself, alongside an unbounded `calldata: Vec<u8>` field [3](#0-2) . The `gas` is whatever value the message constructor (e.g. an XCM `ExportMessage`/`Transact`-derived command originating from any sibling parachain through the `XcmForSnowbridgeV2`/`EthereumBlobExporter` path) chooses to declare — it is not derived from, or checked against, the size of `calldata` or any measured execution cost. Unlike Ethereum transactions, where calldata itself has an intrinsic gas cost (≈16 gas/non-zero byte) charged on top of execution gas, nothing in this fee-calculation path accounts for calldata size at all; the entire "cost" used for pricing is just whatever number the sender put in the `gas` field.

This mirrors exactly the broken invariant in the Holograph report: a parameter meant to represent "cost of executing on the destination chain" is populated from a value that has no guaranteed correspondence to the actual destination-chain execution cost, so a message can be validated and enqueued with a `fee` that is insufficient to cover what the Gateway contract will actually need to spend on Ethereum.

### Impact Explanation
If the declared `gas` is small (e.g. attacker declares `gas: 21000` while attaching a large `calldata` payload targeting an expensive contract call), `maximum_dispatch_gas_used_at_most` returns an artificially low number. `calculate_fee`/`calculate_remote_fee` then computes a `remote` fee far below what covers real dispatch cost on Ethereum [4](#0-3) . The message is nonetheless accepted, queued, and committed — following the documented pipeline (validate → enqueue → commit → merkle-proof relay) [5](#0-4)  — with no gate rejecting an underpriced-for-calldata message. On the Ethereum side this systematically underprices relayer compensation for genuinely expensive calls, discouraging relayers from executing them (public underpriced work degrading bridge message processing), and for calls that actually need more gas than declared, execution reverts on delivery. Since `process_delivery_receipt` only pays out the `order.fee` that was already fixed at enqueue time and then removes the `PendingOrders` entry unconditionally on receipt [6](#0-5) , an underpriced message that never gets a valid delivery receipt has no other path to be fixed, refunded, or retried — this is the same "stuck in limbo forever" outcome as the Holograph bug, applied to Snowbridge's V2 message queue.

### Likelihood Explanation
This requires no privileged actor, malicious relayer, or admin — any account able to originate a V2 `CallContract` command (via XCM from a sibling chain routed through `XcmForSnowbridgeV2`) can set an arbitrary `gas` value independent of the size of the accompanying `calldata`, and the pallet performs no validation tying the two together before computing and locking in the fee.

### Recommendation
Compute `maximum_dispatch_gas_used_at_most` for `Command::CallContract` as a function of both the declared `gas` and the calldata length (e.g. `gas_limit + calldata.len() * PER_BYTE_GAS_COST + fixed_dispatch_overhead`), or independently bound/validate `gas` against `calldata.len()` at `validate()` time so the fee always reflects the true worst-case Ethereum execution+calldata cost, consistent with how `ConstantGasMeter` already accounts for payload-size effects in other commands (e.g. `Upgrade`'s `initializer.maximum_required_gas`).

### Proof of Concept
1. Construct a V2 `Message` with a single `Command::CallContract { target, calldata: <large arbitrary bytes>, gas: 21_000, value: 0 }` and route it through the V2 exporter so `send_message_impl`/`validate` computes `gas_used_at_most = maximum_dispatch_gas_used_at_most(&command) = 21_000` per `Command::CallContract { gas: gas_limit, .. } => *gas_limit` [7](#0-6) .
2. `calculate_fee`/`calculate_remote_fee` locks in a `remote` fee sized only for 21,000 gas, ignoring the actual size of `calldata` [1](#0-0) .
3. The message is enqueued, committed into `PendingOrders` with this fee, and later relayed; on Ethereum the call requires far more gas than 21,000 due to calldata processing and target contract logic, so the transaction reverts or the relayer is drastically under-rewarded relative to true cost, and no on-chain mechanism corrects the `order.fee` or retries with a higher fee before `process_delivery_receipt` removes/settles the pending order [8](#0-7) .

		pub(crate) fn calculate_fee(
			gas_used_at_most: u64,
			params: PricingParameters<T::Balance>,
		) -> Fee<T::Balance> {
			// Remote fee in ether
			let fee = Self::calculate_remote_fee(
				gas_used_at_most,
				params.fee_per_gas,
				params.rewards.remote,
			);

			// downcast to u128
			let fee: u128 = fee.try_into().defensive_unwrap_or(u128::MAX);

			// multiply by multiplier and convert to local currency
			let fee = FixedU128::from_inner(fee)
				.saturating_mul(params.multiplier)
				.checked_div(&params.exchange_rate)
				.expect("exchange rate is not zero; qed")
				.into_inner();

			// adjust fixed point to match local currency
			let fee = Self::convert_from_ether_decimals(fee);

			Fee::from((Self::calculate_local_fee(), fee))
		}

impl GasMeter for ConstantGasMeter {
	fn maximum_dispatch_gas_used_at_most(command: &Command) -> u64 {
		match command {
			Command::SetOperatingMode { .. } => 40_000,
			Command::Upgrade { initializer, .. } => {
				// total maximum gas must also include the gas used for updating the proxy before
				// the the initializer is called.
				50_000 + initializer.maximum_required_gas
			},
			Command::UnlockNativeToken { .. } => 200_000,
			Command::RegisterForeignToken { .. } => 1_200_000,
			Command::MintForeignToken { .. } => 100_000,
			Command::CallContract { gas: gas_limit, .. } => *gas_limit,
		}
	}
}

		/// Process a delivery receipt from a relayer, to allocate the relayer reward.
		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}
