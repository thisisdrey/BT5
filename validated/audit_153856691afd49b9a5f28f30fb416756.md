### Title
Unchecked `u64` multiplication of attacker-controlled `estimated_len` in fee estimation causes silent wraparound - (File: stackslib/src/net/api/postfeerate.rs)

### Summary
`RPCPostFeeRateRequestHandler::estimate_tx_fee_from_cost_and_length` computes `minimum_fee = estimated_len * MINIMUM_TX_FEE_RATE_PER_BYTE` using plain `u64` multiplication with no bounds check on `estimated_len`. Since `estimated_len` is derived from the unauthenticated, attacker-supplied JSON field `estimated_len: Option<u64>` (bounded only by the field's own numeric range, not by request body size), a remote caller can trigger integer overflow/wraparound in release builds, yielding a corrupted `fee`/`fee_rate` returned with HTTP 200.

### Finding Description
In `try_parse_request` (stackslib/src/net/api/postfeerate.rs:180-181), `estimated_len` is computed as `max(body.estimated_len.unwrap_or(0), payload_data.len() as u64)`. `body.estimated_len` comes directly from client JSON and is not clamped to any sane maximum — the only size restriction enforced is on the overall HTTP body via `content_len < MAX_PAYLOAD_LEN` (line 153), which limits the number of bytes in the request, not the numeric value of a JSON integer field. A small JSON body can easily encode a `u64::MAX`-scale number (e.g., `"estimated_len": 18446744073709551615`), which is well within `MAX_PAYLOAD_LEN`.

This attacker-controlled `estimated_len` then flows unmodified into `estimate_tx_fee_from_cost_and_length` (line 96-126), where line 112 performs:
```rust
let minimum_fee = estimated_len * MINIMUM_TX_FEE_RATE_PER_BYTE;
```
This is ordinary `u64 * u64` multiplication with no `checked_mul`/`saturating_mul`. In a standard release build (Rust default `overflow-checks = false` for release profile), this silently wraps instead of panicking, producing an arbitrary, incorrect `minimum_fee` value that then clamps `estimate.fee` (lines 114-118) to that wrapped result. The response is still served as `200 OK` (line 256) with `RPCFeeEstimateResponse` containing the corrupted fee.

No existing guard prevents this: `MAX_PAYLOAD_LEN` bounds request size, not field magnitude; there is no explicit maximum check on `estimated_len` anywhere in `try_parse_request` or `estimate_tx_fee_from_cost_and_length`.

### Impact Explanation
An unauthenticated remote caller (this endpoint requires no auth token) can cause the node's `/v2/fees/transaction` RPC endpoint to return an arbitrary, attacker-influenced fee value (due to wraparound) while returning HTTP 200. Any wallet or client trusting this endpoint for fee estimation could be misled into constructing transactions with wildly incorrect fees (too low to be mined, or arbitrarily inflated). This matches the "High" impact bucket explicitly called out in the question — silent wraparound misleading fee decisions on a publicly reachable read endpoint. It does not crash the node (debug builds would panic on overflow, but release builds — the default deployment — wrap silently), and it does not corrupt any consensus or persisted state; the damage is confined to a single, repeatable, per-request wrong answer.

### Likelihood Explanation
Trivial to trigger: attacker needs only network access to the node's RPC port (no P2P key, no StackerDB slot, no admin role) and can send a single crafted POST to `/v2/fees/transaction` with a valid hex `transaction_payload` and an `estimated_len` field near `u64::MAX`. Cost is negligible and fully repeatable on demand against any node exposing this RPC.

### Recommendation
Clamp or validate `estimated_len` to a sane maximum (e.g., `MAX_PAYLOAD_LEN` or a small multiple thereof) in `try_parse_request` before storing it, and/or use `checked_mul`/`saturating_mul` in `estimate_tx_fee_from_cost_and_length` when computing `minimum_fee`, returning a `HttpBadRequest` if the value would overflow or is implausibly large.

### Proof of Concept
Add a test in `stackslib/src/net/api/tests/postfeerate.rs` that builds a `FeeRateEstimateRequestBody` with `estimated_len: Some(u64::MAX / 2)` (or `u64::MAX`) and a valid small `transaction_payload`, sends it through `RPCPostFeeRateRequestHandler::try_parse_request` + `estimate_tx_fee_from_cost_and_length`, and asserts that:
- In a debug build, the call panics on overflow (`'attempt to multiply with overflow'`), OR
- The returned `minimum_fee` is not silently smaller than `MINIMUM_TX_FEE_RATE_PER_BYTE` itself (i.e., detect the wrapped value), demonstrating that no bounds check rejects the oversized `estimated_len` before the multiplication at line 112. [1](#0-0) [2](#0-1)

    pub fn estimate_tx_fee_from_cost_and_length(
        preamble: &HttpRequestPreamble,
        fee_estimator: &dyn FeeEstimator,
        metric: &dyn CostMetric,
        estimated_cost: ExecutionCost,
        estimated_len: u64,
        stacks_epoch: StacksEpoch,
    ) -> Result<RPCFeeEstimateResponse, StacksHttpResponse> {
        let scalar_cost =
            metric.from_cost_and_len(&estimated_cost, &stacks_epoch.block_limit, estimated_len);
        let fee_rates = fee_estimator.get_rate_estimates().map_err(|e| {
            StacksHttpResponse::new_error(preamble, &HttpBadRequest::new_json(e.into_json()))
        })?;

        let mut estimations = RPCFeeEstimate::estimate_fees(scalar_cost, fee_rates).to_vec();

        let minimum_fee = estimated_len * MINIMUM_TX_FEE_RATE_PER_BYTE;

        for estimate in estimations.iter_mut() {
            if estimate.fee < minimum_fee {
                estimate.fee = minimum_fee;
            }
        }

    fn try_parse_request(
        &mut self,
        preamble: &HttpRequestPreamble,
        _captures: &Captures,
        query: Option<&str>,
        body: &[u8],
    ) -> Result<HttpRequestContents, Error> {
        let content_len = preamble.get_content_length();
        if !(content_len > 0 && content_len < MAX_PAYLOAD_LEN) {
            return Err(Error::DecodeError(format!(
                "Invalid Http request: invalid body length for FeeRateEstimate ({})",
                content_len
            )));
        }

        if preamble.content_type != Some(HttpContentType::JSON) {
            return Err(Error::DecodeError(
                "Invalid content-type: expected application/json".to_string(),
            ));
        }

        let body: FeeRateEstimateRequestBody = serde_json::from_slice(body)
            .map_err(|e| Error::DecodeError(format!("Failed to parse JSON body: {}", e)))?;

        let payload_hex = if body.transaction_payload.starts_with("0x") {
            &body.transaction_payload[2..]
        } else {
            &body.transaction_payload
        };

        let payload_data = hex_bytes(payload_hex).map_err(|_e| {
            Error::DecodeError("Bad hex string supplied for transaction payload".into())
        })?;

        let tx = TransactionPayload::consensus_deserialize(&mut payload_data.as_slice())?;
        let estimated_len =
            std::cmp::max(body.estimated_len.unwrap_or(0), payload_data.len() as u64);

        self.transaction_payload = Some(tx);
        self.estimated_len = Some(estimated_len);
        Ok(HttpRequestContents::new().query_string(query))
    }
