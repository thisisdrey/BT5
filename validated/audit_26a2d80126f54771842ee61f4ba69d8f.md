## Analog Found: Front-run griefing DoS in `MarketSellAssetActuator.matchOrder()` via `MAX_MATCH_NUM` revert

### Title
Front-run grieving attack can permanently block TRON market (Bancor-exchange) sell orders via `MAX_MATCH_NUM` revert - (File: `actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java`)

### Summary
The `MarketSellAssetActuator` (`ContractType.MarketSellAssetContract`), reachable by any signed transaction from an unprivileged account, matches a taker's sell order against existing maker orders in a loop. If the number of matched maker orders in a single taker transaction exceeds `MAX_MATCH_NUM` (20), the entire transaction is aborted with `ContractValidateException("Too many matches...")` instead of partially filling the order and leaving the remainder on the book. This mirrors the reported `liquidate()` bug pattern: instead of gracefully capping/partial-executing, the code performs an all-or-nothing check that a third party can manipulate to force reverts of another user's transaction.

### Finding Description
In `matchOrder()`, the taker's order is matched greedily against the best-price maker orders, and `matchOrderCount` is incremented per matched maker order: [1](#0-0) 

If more than `MAX_MATCH_NUM` (20) maker orders are consumed while filling a single taker order, the whole operation throws instead of stopping the match loop and leaving the rest of the taker order on the book: [2](#0-1) [3](#0-2) 

This exception propagates up and is caught in `execute()`, which marks the whole transaction failed: [4](#0-3) 

Any unauthenticated account can freely place many small maker orders on a token pair (the only per-account limit is `MAX_ACTIVE_ORDER_NUM = 100`, easily bypassed with multiple accounts, and there is no minimum order size check beyond `> 0`): [5](#0-4) 

By placing more than `MAX_MATCH_NUM` tiny maker orders at the best price on a given trading pair, an attacker can guarantee that any legitimate taker order large enough to need more than 20 fills at that price level will always revert with `Too many matches. MAX_MATCH_NUM = 20`, exactly analogous to how an inflated `amountCall` in `liquidate()` forces `paid > oldDebt` to revert the victim's transaction — a caller-controllable, shared piece of state (the order book, or the position's debt) is manipulated by a third party so that an all-or-nothing check on the victim's transaction fails.

### Impact Explanation
An attacker can grief the on-chain decentralized exchange feature: legitimate large sell orders on any token pair can be made to permanently and repeatedly fail (wasting the victim's TRX fee/bandwidth each attempt) simply by pre-seeding the order book with more than 20 tiny counter-orders at the best price. Because the check is a hard revert rather than a partial-fill cap, victims cannot get partial execution and have no way to work around the griefing other than splitting into many small orders themselves (defeating the purpose of the market feature) — effectively denying use of this on-chain trading API to targeted market participants.

### Likelihood Explanation
Any account can freely issue `MarketSellAssetContract` transactions (validated only by `dynamicStore.supportAllowMarketTransaction()`, balance, and basic parameter checks) and cheaply create many small maker orders, since order size only needs to be `> 0`. Multiple accounts can trivially be used to exceed the 100-active-order-per-account cap. No special privilege is required, making the attack cheap and repeatable by any anonymous transaction broadcaster.

### Recommendation
Instead of throwing when `matchOrderCount > MAX_MATCH_NUM`, the actuator should stop matching at the limit and persist the taker's remaining (unfilled) quantity back onto the order book (as is already done via `saveRemainOrder()` when `getSellTokenQuantityRemain() != 0`), so the transaction succeeds with a partial fill rather than reverting entirely.

### Proof of Concept
1. Attacker controls (or Sybils) 25+ accounts and creates 25 sell orders of `TOKEN_A` for `TOKEN_B` each with minimal quantity (e.g., `sellTokenQuantity = 1`) at the best available price for the `TOKEN_B -> TOKEN_A` pair, using `MarketSellAssetActuator` (as exercised in `framework/src/test/java/org/tron/core/actuator/MarketSellAssetActuatorTest.java`). [6](#0-5) 
2. Victim submits a `MarketSellAssetContract` selling a large amount of `TOKEN_B` for `TOKEN_A` at that price, which would need to match against more than 20 of the attacker's resting orders to fill.
3. `matchOrder()` walks through the resting orders one by one; once `matchOrderCount` exceeds `MAX_MATCH_NUM` (20), it throws `ContractValidateException("Too many matches. MAX_MATCH_NUM = 20")`. [7](#0-6) 
4. The victim's entire transaction fails (`ContractExeException`), the fee/bandwidth is consumed, and the trade never executes — repeatable indefinitely as long as the attacker maintains ≥21 resting orders at the best price.
