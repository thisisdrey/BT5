## Title
Front-Runnable Permissionless Bank PDA Seed Enables DoS on `lending_pool_add_bank_permissionless` - (File: `programs/marginfi/src/instructions/marginfi_group/add_pool_permissionless.rs`)

### Summary
`lending_pool_add_bank_permissionless` derives the new `Bank` account's PDA from `[marginfi_group, bank_mint, bank_seed]`, where `bank_seed` is a caller-supplied `u64` and the instruction is callable by anyone (no admin/owner check). This is structurally identical to the reported `SplitFactory.createSplit()` issue, where a `merkleRoot` used as CREATE2 `salt` let an attacker front-run and permanently consume that salt. Here, an attacker can observe a pending `lending_pool_add_bank_permissionless` transaction in the mempool and submit their own transaction with the same `(marginfi_group, bank_mint, bank_seed)` triple (using a different, arbitrary validator/stake-pool), which lands first via `init`, causing the legitimate transaction to revert with "already in use."

### Finding Description
The `bank` account is created with Anchor's `init` constraint and PDA seeds built entirely from public/predictable inputs supplied in the instruction call itself: [1](#0-0) 

The surrounding `Accounts` struct has no admin/authority gating — only `fee_payer: Signer<'info>` is required, making the instruction permissionless by design (intended for validators to self-register their stake pool as collateral): [2](#0-1) [3](#0-2) 

Because `marginfi_group` and `bank_mint` are public accounts and `bank_seed` is chosen by the caller (often starting from small/sequential values, as seen in tests deriving seeds via brute-force loops), an attacker monitoring the mempool can extract the exact `(marginfi_group, bank_mint, bank_seed)` tuple from a pending transaction and resubmit a competing transaction with a higher priority fee using the same tuple but a different `validator_vote_account`/`stake_pool`/`sol_pool`. Since `init` requires the PDA to not already exist, whichever transaction lands first claims the PDA; the other reverts. This mirrors the `salt: keccak256(abi.encode(merkleRoot))` collision in the original finding exactly — the seed space is not bound to the submitter (`msg.sender`/`fee_payer`), so any external party can claim it first.

This is corroborated by the seed-brute-force pattern used elsewhere in the test suite for the analogous admin-gated `lending_pool_add_bank_with_seed`/`lending_pool_clone_bank` instructions, which share the same seed-derivation and `init` pattern: [4](#0-3) 

### Impact Explanation
A malicious actor can grief a specific pending `lending_pool_add_bank_permissionless` call by front-running with the same `(group, mint, bank_seed)`, causing the legitimate transaction to revert. Beyond simply wasting the fee payer's transaction fee, the attacker's own transaction succeeds in `group.add_bank()`, consuming one of the group's limited bank slots with an attacker-chosen validator/stake-pool instead of the one the original submitter intended, resulting in an unauthorized state change to the group's bank list at the address the legitimate caller expected to control. The legitimate caller must pick a new, unpredictable `bank_seed` and retry, and the attack is trivially repeatable against any subsequent attempt observed in the mempool.

### Likelihood Explanation
The instruction is fully permissionless (no `has_one = admin` or owner check), so any network participant can call it. Front-running via higher priority fees is a standard capability on Solana. The only requirement for the attacker is to observe the pending transaction (public mempool/RPC) and know the `bank_mint`/`marginfi_group`/`bank_seed`, all of which are plaintext instruction arguments/accounts.

### Recommendation
Bind the bank PDA seed to the caller so it cannot be squatted by a third party, e.g., incorporate `fee_payer.key()` (or the intended `validator_vote_account`) into the seeds:
```rust
seeds = [
    marginfi_group.key().as_ref(),
    bank_mint.key().as_ref(),
    fee_payer.key().as_ref(),
    &bank_seed.to_le_bytes(),
],
```
Alternatively, derive the seed deterministically from the `validator_vote_account` (which is already validated in the handler) instead of an arbitrary caller-chosen `u64`, removing the free-form salt entirely.

### Proof of Concept
1. Victim (a validator or their agent) submits `lending_pool_add_bank_permissionless(bank_seed = X)` for `marginfi_group = G`, `bank_mint = M`, targeting `validator_vote_account = V1`.
2. Attacker observes the pending transaction in the mempool and extracts `(G, M, X)`.
3. Attacker submits their own `lending_pool_add_bank_permissionless(bank_seed = X)` with the same `G`, `M`, but a different, arbitrary valid `validator_vote_account = V2`/`stake_pool`/`sol_pool`, with a higher priority fee.
4. Attacker's transaction lands first; the PDA at `seeds = [G, M, X]` is initialized for `V2`.
5. Victim's original transaction fails on `init` for `bank` (`already in use`), reverting the entire transaction; the victim's intended bank was never created at that seed, and the group's finite bank-slot count has already been consumed by the attacker's bank.
