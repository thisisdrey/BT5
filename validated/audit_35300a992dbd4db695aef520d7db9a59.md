### Title
Servicer can forge the borrower identity on a loan and pull USDC from an arbitrary approver - (File: `contracts/Loans.sol`)

### Summary
The C4 report shows that `NextGenCore.setCollectionData` lets a trusted-but-unprivileged caller rebind the "signing" identity (artist) of a collection through a self-controlled book before the binding becomes immutable, letting them forge a signature and later swap in the real identity while keeping the forged proof. Tare has the same root cause in `Loans.updateBorrower`: the address that will be charged for a loan is validated only against a registry that the caller (the servicer) fully controls, so the servicer can bind an arbitrary victim address to the loan's borrower role and then pull funds from it.

### Finding Description
`updateBorrower` re-assigns the `borrowers[loanId]` role using only the *servicer's own* address book as the source of truth: [1](#0-0) 

```solidity
function updateBorrower(
    uint64 loanId,
    address borrower
) external whenNotPaused onlyServicerOrAdmin(loanId) notTerminal(loanId) {
    require(borrower != address(0), ZeroAddress());
    require(isRegisteredForRole(servicers[loanId], Roles.Borrower, borrower), UnregisteredAddress(borrower));

    borrowers[loanId] = borrower;
    ...
}
```

`isRegisteredForRole(servicers[loanId], Roles.Borrower, borrower)` checks `addressBook[servicers[loanId]][borrower]`, and `LoansAuth.registerAddress` is **permissionless per-caller**: [2](#0-1) 

```solidity
function registerAddress(Roles role, address addr) external {
    addressBook[msg.sender][addr] |= (1 << uint8(role));
    emit AddressRegistered(msg.sender, role, addr);
}
```

Any address can call `registerAddress(Roles.Borrower, V)` under its own book. A servicer who is the registered servicer of some loan (`onlyServicerOrAdmin(loanId)`) can therefore:
1. Call `LoansAuth.registerAddress(Roles.Borrower, V)` from its own account, adding `V` to its own book as a valid borrower.
2. Call `updateBorrower(loanId, V)` — this passes because `isRegisteredForRole(servicers[loanId] == self, Roles.Borrower, V)` is true, regardless of whether `V` ever agreed to be the borrower on this loan.
3. Once `borrowers[loanId] = V`, any function that pulls currency from the loan's `borrowers[loanId]` via `safeTransferFrom` (borrower payment / disbursement-repayment paths) will attempt to debit `V` directly, using whatever standing USDC allowance `V` has already given to `Loans` (e.g. because `V` is a legitimate borrower on a *different* loan and has `USDC.approve(Loans, MAX)` per the deployment runbook).
4. The servicer (or an accomplice) then routes the pulled funds back out via the normal servicer/waterfall withdrawal path.

This mirrors the NextGen bug precisely: the protocol's core invariant "a role can only be bound to the address that actually holds/consented to it" is broken because the validation check is anchored on a book that the attacking role fully controls (`servicers[loanId]`, analogous to the collection admin controlling `setCollectionData`), not on any consent or on-chain action by the victim itself. `LoansAuth.registerAddress` never verifies that `addr == msg.sender`; it lets `msg.sender` (the servicer) declare `V` a "borrower" in its own book unilaterally, exactly like the fake-artist substitution in `setCollectionData`.

### Impact Explanation
This directly matches the allowed impact "Theft, diversion, or unauthorized reassignment of USDC ... from honest users or shared protocol state" and "Unauthorized state transition ... that lets an unprivileged actor act for another ... borrower". A servicer role is a designated operational role, not necessarily the same trust tier as the Tare-team admin/guardian multisig described in the deployment runbook, and per `loan_permissions.md` a servicer alone is authorized to `updateBorrower`. Once `V`'s address has a standing `USDC.approve(Loans, MAX)` (which is standard operating procedure for every borrower Safe per the deployment runbook), the servicer can redirect a debit against `V` into a loan `V` never took, draining `V`'s USDC allowance to cover another borrower's obligation.

### Likelihood Explanation
The trigger requires only actions available to a role already trusted with `onlyServicerOrAdmin(loanId)` on an existing loan, and the `registerAddress` call is fully permissionless — no signature, no consent, no admin/guardian involvement is needed to mount the address-book poisoning step. Any address that has ever given the standard max USDC approval to `Loans` (which is the deployment default for every borrower Smart Account) is a potential victim on any loan a malicious/compromised servicer services. This matches the C4 medium likelihood pattern: not requiring privileged escalation beyond the servicer's own already-granted role.

### Recommendation
Require borrower-role registration to be self-attested (i.e., only the address itself can add itself to any book for `Roles.Borrower`), or require `updateBorrower` to check consent from `borrower` directly (e.g., a stored acceptance flag set by `borrower` calling a dedicated function), rather than trusting an entry in a book owned by the very party (`servicers[loanId]`) making the reassignment. At minimum, gate `registerAddress` so `addr` must equal `msg.sender`, eliminating third-party registration of arbitrary victim addresses.

### Proof of Concept
```solidity
// Servicer registers victim V as a "Borrower" in its own book — no consent from V required
vm.prank(servicer);
loansAuth.registerAddress(Roles.Borrower, V);

// Servicer rewrites the loan's borrower to V
vm.prank(servicer);
loans.updateBorrower(loanId, V);

assertEq(loans.borrowers(loanId), V);
// Any subsequent borrower-payment pull against `loanId` will attempt safeTransferFrom(V, ...)
// using V's pre-existing USDC allowance to `Loans`, even though V never agreed to this loan.
