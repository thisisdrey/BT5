### Title
Dust deposits/transfers permanently occupy `depositTokensOfAccount` slots, freezing a victim's ability to add collateral - ([File: contracts/DepositToken.sol](contracts/DepositToken.sol))

### Summary
Analogous to the kernel bug where an allocated object is never freed, `Pool.depositTokensOfAccount` entries are allocated to an account's `MappedEnumerableSet.AddressSet` on every 0→nonzero balance transition and are never released until the balance returns to zero. An unprivileged attacker can allocate all `MAX_TOKENS_PER_USER = 30` slots on a victim's account by depositing or transferring dust amounts of every deposit token to them, after which any further first-time receipt of a deposit token reverts with `UserReachedMaxTokens`, blocking the victim from depositing new collateral types.

### Finding Description
`DepositToken._mint()` adds the token to the recipient's account set whenever the prior balance was zero (`_balanceBefore == 0 && amount_ > 0` → `pool.addToDepositTokensOfAccount(account_)`), and `deposit(uint256 amount_, address onBehalfOf_)` lets anyone mint directly onto an arbitrary victim [1](#0-0) [2](#0-1) . `_transfer()` does the same on plain ERC20 transfers and `seize`, so an attacker can also mint dust to themselves and `transfer`/`transferFrom` it to the victim [3](#0-2) . On the `Pool` side, `onlyIfAdditionWillNotReachMaxTokens` reverts once `debtTokensOfAccount + depositTokensOfAccount` length reaches `MAX_TOKENS_PER_USER = 30` [4](#0-3) [5](#0-4) . Slots are only freed when a balance returns exactly to zero via `_burn` or `_transfer` [6](#0-5) .

### Impact Explanation
Temporary freezing of funds. While the victim's account is at the cap: (1) `deposit(amount_, victim)` for any deposit token the victim doesn't already hold reverts (the `_mint` → `addToDepositTokensOfAccount` call reverts the whole transaction); (2) incoming `transfer`/`transferFrom`/`seize` of new deposit tokens revert. A victim whose existing collateral is a single asset and whose position approaches liquidation cannot add a different collateral type to restore health, converting the freeze into real loss via liquidation. An attacker can also keep their own account saturated to make `seize` of a specific collateral token revert, degrading liquidation liveness for that token.

### Likelihood Explanation
Cost is limited to acquiring dust of up to 30 whitelisted underlyings (plus deposit fees, which must leave `_deposited > 0` since `quoteDepositOut` can zero out very small amounts). No privileged role, oracle manipulation, or malicious token is needed — `deposit`'s `onBehalfOf_` is permissionless. Mitigating factor: the victim can recover at any time by transferring or withdrawing the dust (dust is excess collateral and therefore unlocked under `unlockedBalanceOf`/`_revertIfLocked`, provided the position is not already unhealthy), possibly batched atomically before a legitimate deposit [7](#0-6) [8](#0-7) . The attack is therefore a griefing/DoS with real consequence only when the victim is time-constrained (imminent liquidation) or unaware.

### Recommendation
- Do not auto-register tokens on `transfer`/`transferFrom`/`seize`; restrict `addToDepositTokensOfAccount` to the `deposit` path and require an opt-in flag per account/token, or
- Enforce a minimum meaningful balance (`minDeposit`) before a token occupies a set slot, and/or
- Raise/decouple `MAX_TOKENS_PER_USER` from an attacker-influenceable count, e.g., only count tokens the account itself deposited.

### Proof of Concept
```solidity
// SPDX-License-Identifier: MIT
pragma solidity 0.8.24;

import "forge-std/Test.sol";
import {Pool} from "../contracts/Pool.sol";
import {DepositToken} from "../contracts/DepositToken.sol";
import {IERC20} from "../contracts/dependencies/openzeppelin/token/ERC20/IERC20.sol";

contract DustSlotGriefingTest is Test {
    // Fork mainnet/Base; `pool` is a live Pool, `depositTokens` are its enabled DepositTokens
    Pool pool;
    DepositToken[] depositTokens; // >= 30 configured on the pool
    address attacker = makeAddr("attacker");
    address victim = makeAddr("victim");

    function test_dustFillsAccountSlots() public {
        // Attacker deposits dust of each underlying on behalf of the victim
        uint256 max = pool.MAX_TOKENS_PER_USER(); // 30
        for (uint256 i; i < max; ++i) {
            IERC20 underlying = depositTokens[i].underlying();
            deal(address(underlying), attacker, 1e6);
            vm.startPrank(attacker);
            underlying.approve(address(depositTokens[i]), 1e6);
            depositTokens[i].deposit(1e6, victim); // mints dust to victim, occupies a slot
            vm.stopPrank();
        }

        assertEq(pool.getDepositTokensOfAccount(victim).length, max);

        // Victim tries to deposit a new collateral type (index `max`) -> reverts
        DepositToken newToken = depositTokens[max]; // a 31st deposit token added by governor
        IERC20 u = newToken.underlying();
        deal(address(u), victim, 1e18);
        vm.startPrank(victim);
        u.approve(address(newToken), 1e18);
        vm.expectRevert(Pool.UserReachedMaxTokens.selector);
        newToken.deposit(1e18, victim);
        vm.stopPrank();
    }
}
```
