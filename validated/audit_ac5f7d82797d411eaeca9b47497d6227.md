## Title
Symlink-as-`custom_hooks` extraction via `ExtractHooks`/`SetCustomHooks` allows repository hooks directory to become an attacker-controlled symlink - (File: internal/gitaly/repoutil/custom_hooks.go)

## Summary
`ExtractHooks` shells out to the system `tar` binary to extract a caller-supplied tar stream, and if the top-level `custom_hooks` entry is a `TypeSymlink`, GNU `tar` will happily create that symlink in the temp directory rather than a real directory. `SetCustomHooks` then does `os.Rename(tempHooksPath, repoHooksPath)`, and since `rename(2)` operates on the directory entry itself (not the symlink target), the symlink — not a directory — ends up installed as `repoPath/custom_hooks`.

## Finding Description
`ExtractHooks` (`internal/gitaly/repoutil/custom_hooks.go:55-95`) invokes the external `tar -xf - -C <path> --strip-components 0 custom_hooks` command with no post-extraction validation of entry types [1](#0-0) . Unlike the manual Go-based tar extractor used elsewhere in the codebase (`extractTarToDirectory` in `internal/gitaly/service/repository/replicate.go`, which explicitly rejects absolute symlinks and validates that relative symlink targets stay inside the extraction directory) [2](#0-1) , `ExtractHooks` has no equivalent check because it defers entirely to the system `tar` binary, which does not validate symlink targets when simply creating the link object.

In `SetCustomHooks`, the flow is:
1. `ExtractHooks(ctx, logger, reader, tmpDir.Path(), false)` extracts the tarball into a fresh temp dir [3](#0-2) . If the tar's top-level entry named `custom_hooks` is `TypeSymlink -> /tmp/evil` (or any absolute/relative path), `tar` creates `tmpDir/custom_hooks` as a symlink rather than a directory.
2. `os.Mkdir(tempHooksPath, mode.Directory)` fails with `fs.ErrExist` (because the symlink entry already exists at that path name) and this error is explicitly ignored [4](#0-3) .
3. `newDirectoryVote(tempHooksPath)` calls `filepath.WalkDir` on a path whose root is a symlink, not a directory; `WalkDir`'s underlying `Lstat` sees a non-directory entry, so it does not descend, and it treats the symlink itself as a leaf. Since `entry.IsDir()` is false, the code proceeds to `os.Open(path)` and hash its contents [5](#0-4)  — `os.Open` follows the symlink, so if the target is a directory this errors out and aborts `SetCustomHooks` before the rename; if the target is a readable regular file, this succeeds and the flow continues.
4. `os.Rename(tempHooksPath, repoHooksPath)` at line 221 renames the directory entry — since `rename(2)` never dereferences symlinks for either the source or destination, this moves the **symlink itself** into the repository, so `repoPath/custom_hooks` becomes a symlink pointing at the attacker-chosen path [6](#0-5) .

None of the storage/path-validation utilities (`storage.ValidateRelativePath`, locator joining) apply here since this operation is purely filesystem-level tar extraction plus a rename, and there is no symlink check anywhere in this code path (unlike the hardened `extractTarToDirectory`).

## Impact Explanation
If `repoPath/custom_hooks` becomes a symlink to an arbitrary path, subsequent hook execution (`pre-receive`/`update`/`post-receive`/`reference-transaction`) that looks up scripts under `custom_hooks/` would follow that symlink, and `GetCustomHooks` (which tars the `custom_hooks` directory back out with `archive.WriteTarball`) could potentially package and return the contents of an arbitrary host path/directory that the symlink points at, resulting in host filesystem content disclosure or hook substitution outside the repository boundary. This corresponds to the "hook or quarantine bypass" / "archive extraction escape" impact classes in the bounty scope. Note that step 3 (`newDirectoryVote` calling `os.Open` on a symlinked directory) will actually cause `SetCustomHooks` to fail before the rename occurs unless the attacker points the symlink at a readable **regular file** rather than a directory, which constrains — but does not eliminate — the exploitability of turning `custom_hooks` into a directory-like symlink usable for later traversal.

## Likelihood Explanation
The critical precondition that could not be confirmed from the available code is whether an **unprivileged** GitLab user can actually invoke the `SetCustomHooks`/`RestoreCustomHooks` gRPC RPCs. These RPCs are implemented in `internal/gitaly/service/repository/set_custom_hooks.go` and are primarily invoked internally by GitLab Rails or the backup/restore subsystem (`internal/backup/repository.go`, `internal/backup/backup.go`) [7](#0-6) , not through ordinary git push/fetch/fork/import operations that an unprivileged user performs. Reaching this code path as described in the question ("attacker can call SetCustomHooks") requires either an admin-level "custom hooks" feature in GitLab Rails or direct authenticated gRPC access to Gitaly — both of which fall outside the stated unprivileged-attacker threat model (no admin role, no direct backend RPC access). I was not able to fully verify GitLab Rails-side authorization for this RPC (out of scope for this repo), so I cannot conclusively confirm or reject reachability by a genuinely unprivileged actor.

## Recommendation
Harden `ExtractHooks` to reject or validate any `custom_hooks` tar entry that is a symlink (or contains symlinks) before/after extraction — either using `tar --no-same-owner` plus post-extraction `os.Lstat` checks to confirm `custom_hooks` is a real directory, or replacing the system-`tar` based extraction with the same manual Go-based `extractTarToDirectory`-style walker used in `replicate.go` that explicitly rejects absolute symlinks and validates relative symlink targets stay within the extraction directory. Additionally, in `SetCustomHooks`, verify via `os.Lstat(tempHooksPath)` that the extracted `custom_hooks` entry is a directory (not a symlink) before proceeding with `os.Rename`.

```go
func TestSetCustomHooks_SymlinkEscape(t *testing.T) {
    ctx := testhelper.Context(t)
    cfg := testcfg.Build(t)
    repoProto, repoPath := gittest.CreateRepository(t, ctx, cfg)
    locator := config.NewLocator(cfg)

    var tarBuf bytes.Buffer
    tw := tar.NewWriter(&tarBuf)
    require.NoError(t, tw.WriteHeader(&tar.Header{
        Name:     "custom_hooks",
        Typeflag: tar.TypeSymlink,
        Linkname: "/tmp/evil-hooks",
    }))
    require.NoError(t, tw.Close())

    err := repoutil.SetCustomHooks(ctx, testhelper.NewLogger(t), locator, transaction.NewManager(cfg, testhelper.NewLogger(t)), &tarBuf, repoProto)
    // Expect this to fail safely; instead, if a regular file target is used
    // for Linkname instead of a directory, SetCustomHooks succeeds and:
    fi, lerr := os.Lstat(filepath.Join(repoPath, "custom_hooks"))
    require.NoError(t, lerr)
    require.Zero(t, fi.Mode()&os.ModeSymlink, "custom_hooks should never be a symlink")
}
```
Expected (vulnerable) result: `repoPath/custom_hooks` is a symlink to `/tmp/evil-hooks` (when the attacker points it at a readable file rather than a directory, so `newDirectoryVote`'s `os.Open`/`io.Copy` step does not error out first).

```go
func (s *server) SetCustomHooks(stream gitalypb.RepositoryService_SetCustomHooksServer) error {
	ctx := stream.Context()

	firstRequest, err := stream.Recv()
	if err != nil {
		return structerr.NewInternal("getting first request: %w", err)
	}

	repo := firstRequest.GetRepository()
	if err := s.locator.ValidateRepository(ctx, repo); err != nil {
		return structerr.NewInvalidArgument("%w", err)
	}

	reader := streamio.NewReader(func() ([]byte, error) {
		if firstRequest != nil {
			data := firstRequest.GetData()
			firstRequest = nil
			return data, nil
		}

		request, err := stream.Recv()
		return request.GetData(), err
	})

	if err := repoutil.SetCustomHooks(ctx, s.logger, s.locator, s.txManager, reader, repo); err != nil {
		return structerr.NewInternal("setting custom hooks: %w", err)
	}

	return stream.SendAndClose(&gitalypb.SetCustomHooksResponse{})
}
```
