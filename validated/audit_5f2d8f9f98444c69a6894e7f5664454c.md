### Title
Unauthenticated attachment poisoning via unverified content-hash on download response — `/v2/attachments/:hash` serves data no confirmed `AttachmentInstance` committed to - ([File: stackslib/src/net/atlas/download.rs], [File: stackslib/src/net/api/getattachment.rs])

### Summary
`AttachmentsBatchStateContext::extend_with_attachments` accepts any `GetAttachmentResponse` from a peer and inserts `response.attachment` into the pending set without ever checking it against the `content_hash` that was actually requested. `AttachmentsDownloader::run` then unconditionally calls `AtlasDB::insert_instantiated_attachment(&attachment)`, which stores the content under `Hash160::from_data(&content)` (the *actual* hash of whatever bytes the peer sent) with `was_instantiated = 1`, with no check that any `AttachmentInstance.content_hash` in the DB equals that hash. `RPCGetAttachmentRequestHandler::try_handle_request` (`stackslib/src/net/api/getattachment.rs:104-118`) then serves this content to any unauthenticated HTTP client via `find_attachment`, which only checks `was_instantiated = 1`, not the existence of a matching, confirmed `AttachmentInstance`.

### Finding Description
The broken equality: "bytes served under hash H by `/v2/attachments/H`" should equal "bytes whose hash H a confirmed on-chain name operation (`AttachmentInstance.content_hash == H`) committed to." This equality is broken because nothing in the write path enforces it.

- Trace: `AttachmentsDownloader::run` (`stackslib/src/net/atlas/download.rs:93-213`) drives `AttachmentsBatchStateMachine::try_proceed`, which in its `DownloadingAttachment` state calls `AttachmentsBatchStateContext::extend_with_attachments` (`download.rs:530-558`).
- In `extend_with_attachments`, for each successfully completed HTTP request, the code does:
```
if let Ok(response) = response.decode_atlas_get_attachment() {
    self.attachments.insert(response.attachment);
    report.bump_successful_requests();
}
```
There is **no check** that `response.attachment.hash() == request.content_hash`. The `AttachmentRequest` (`download.rs:1066-1071`) that was sent carries the expected `content_hash`, but this value is discarded after the request is dispatched — it's never compared with the received content.
- Back in `run()` (`download.rs:153-169`), for each accepted `attachment`:
```
let attachments_instances = network.atlasdb.find_all_attachment_instances(&attachment.hash())?;
network.atlasdb.insert_instantiated_attachment(&attachment)?;   // <-- unconditional
```
`insert_instantiated_attachment` (`stackslib/src/net/atlas/db.rs:576-592`) inserts the attachment into the `attachments` table with `was_instantiated = 1` keyed on `attachment.hash()` (the hash of the content itself, recomputed locally) — it does **not** require `attachments_instances` (i.e., a matching `AttachmentInstance`) to be non-empty. Whether or not any block-committed `AttachmentInstance` exists for that hash, the content is stored as "validated" data.
- `RPCGetAttachmentRequestHandler::try_handle_request` (`stackslib/src/net/api/getattachment.rs:104-118`) calls `find_attachment(&attachment_hash)` (`db.rs:641-648`), which is simply `SELECT content FROM attachments WHERE hash = ? AND was_instantiated = 1` — again with no join/check against `attachment_instances`.

Exploit flow: An attacker-controlled peer that is chosen as an outbound sync peer (any regular peer can be, no privileged role or secret required) advertises (via `/v2/attachments/inv`) that it has some attachment content available for a requested `content_hash` X. When the node requests `GET /v2/attachments/X` from that peer, the attacker returns a `GetAttachmentResponse` containing **arbitrary bytes Y** (whose real hash is `Z = Hash160(Y) ≠ X`). This response is accepted unconditionally, and the node inserts Y under hash Z as "instantiated"/validated, with no `AttachmentInstance` for Z ever existing. Any subsequent unauthenticated remote client hitting `GET /v2/attachments/Z` on this node receives Y as if it were validated BNS attachment data.

Existing guards that fail to prevent this: there is no signature check on `GetAttachmentResponse` bodies (attachments are raw off-chain blobs with no signing scheme), no `content.hash() == requested_content_hash` comparison anywhere in `extend_with_attachments`, and `insert_instantiated_attachment` performs no join against `attachment_instances` before marking data "instantiated." The only mitigation elsewhere (`check_attachment_instances` used for queued/initial instances) does not apply to this download-response path.

### Impact Explanation
Any remote peer that becomes a download source for attachment content can cause an arbitrary, non-committed blob to be served by the victim's `/v2/attachments/:hash` endpoint as if it corresponds to a confirmed BNS zonefile/attachment operation. This is a High-severity "attachment/BNS mismatch" — data served under a hash for which no confirmed on-chain name operation ever registered, breaking the trust assumption that any content returned by this endpoint is validated against chain-committed `content_hash` values. It is repeatable per accepted attachment response and does not require the attacker to control the specific hash that any legitimate `AttachmentInstance` references — the attacker fully controls both the stored bytes and the effective hash under which they are served (since the local hash used for storage is recomputed from the attacker's own bytes).

### Likelihood Explanation
Preconditions: the attacker must run a normal peer that participates in the Atlas attachments protocol and gets selected as an inventory/data source (a routine, low-cost condition — no signer role, no RPC secret, no admin access). The node must have at least one queued/unresolved `AttachmentInstance` to trigger a download cycle, which is normal in ongoing operation. Attacker cost is a single crafted HTTP response to a `GetAttachment` request; the attack is trivially repeatable across multiple content hashes.

### Recommendation
In `AttachmentsBatchStateContext::extend_with_attachments` (`stackslib/src/net/atlas/download.rs:530-558`), verify `response.attachment.hash() == request.content_hash` before inserting into `self.attachments`; drop/blacklist the peer and bump `report.bump_failed_requests()` on mismatch. Additionally, harden `AtlasDB::insert_instantiated_attachment` to only mark content as instantiated (`was_instantiated = 1`) when there exists at least one `attachment_instances` row with matching `content_hash` and `status = Checked`, mirroring the check already performed in `check_attachment_instances`.

### Proof of Concept
Rust test plan in `stackslib/src/net/atlas/tests.rs` or `stackslib/src/net/api/tests/getattachment.rs`:
1. Construct an `AtlasDB` (in-memory) with no `AttachmentInstance` rows referencing a target hash `Z`.
2. Simulate the poisoning path directly (as the question specifies) by calling `atlas_db.insert_instantiated_attachment(&Attachment{content: b"evil".to_vec()})` — this is exactly the call `download.rs:159-162` makes for any unverified peer response, without requiring `find_all_attachment_instances(&Z)` to be non-empty first.
3. Confirm precondition: `atlas_db.find_all_attachment_instances(&Z).unwrap().is_empty()` is `true` (no confirmed `AttachmentInstance`).
4. Instantiate `RPCGetAttachmentRequestHandler`, build a `StacksHttpRequest::new_getattachment(host, Z)`, drive it through `try_parse_request` and `try_handle_request` against a `StacksNodeState` wired to this `AtlasDB`.
5. Assert the response status is 200 and `GetAttachmentResponse.attachment.content == b"evil"` — i.e., the handler serves attacker content for hash `Z` despite `find_all_attachment_instances(&Z)` being empty, proving `find_attachment` (`db.rs:641-648`) does not require a corresponding confirmed `AttachmentInstance`.         )?;

    pub fn extend_with_attachments(
        mut self,
        results: &mut BatchedRequestsResult<AttachmentRequest>,
    ) -> AttachmentsBatchStateContext {
        for (request, response) in results.succeeded.drain() {
            let report = self
                .peers
                .get_mut(request.get_url())
                .expect("Atlas: unable to retrieve reliability report for peer");

            let response = if let Some(r) = response {
                r
            } else {
                report.bump_failed_requests();
                continue;
            };

            if let Ok(response) = response.decode_atlas_get_attachment() {
                self.attachments.insert(response.attachment);
                report.bump_successful_requests();
            } else {
                report.bump_failed_requests();
            }
        }
        let mut events_ids = results.faulty_peers.keys().copied().collect::<Vec<usize>>();
        self.events_to_deregister.append(&mut events_ids);

        self
    }
