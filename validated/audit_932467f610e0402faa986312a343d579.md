### Title
`account::verify_signed_message` Rejects SingleKey/MultiKey Schemes, Permanently Blocking Multisig Migration for Modern-Key Accounts - (File: `aptos-move/framework/aptos-framework/sources/account/account.move`)

### Summary

`account::verify_signed_message` is a public framework function that only handles `ED25519_SCHEME` (0) and `MULTI_ED25519_SCHEME` (1), aborting with `EINVALID_SCHEME` for any other scheme. The Aptos framework defines and fully supports `SINGLE_KEY_SCHEME` (2) and `MULTI_KEY_SCHEME` (3) as valid on-chain account types (covering Secp256k1, WebAuthn, and Keyless accounts). Any caller that passes `account_scheme = 2` or `3` will unconditionally abort. The two mainnet-reachable callers are `multisig_account::create_with_existing_account` and `multisig_account::create_with_existing_account_and_revoke_auth_key`, both public entry functions. Users whose accounts are secured by SingleKey or MultiKey authentication keys are permanently unable to use these migration paths.

### Finding Description

`account.move` defines four scheme constants: [1](#0-0) 

`verify_signed_message` only branches on the first two: [2](#0-1) 

The `else` branch at line 1317–1319 unconditionally aborts with `EINVALID_SCHEME` for any scheme value other than 0 or 1. The formal spec confirms this is the intended (but incomplete) behavior: [3](#0-2) 

Both public entry functions in `multisig_account` delegate signature verification to this function: [4](#0-3) [5](#0-4) 

The stablecoin example `transfer_from` (the direct Aptos analog of the ERC-20 permit pattern) also calls `verify_signed_message` and is broken for the same reason: [6](#0-5) 

### Impact Explanation

Any account whose on-chain authentication key was derived from a `SingleKey` (Secp256k1, WebAuthn, Keyless) or `MultiKey` public key — both of which are fully supported and actively used on Aptos mainnet — will receive an unconditional abort when calling `create_with_existing_account` or `create_with_existing_account_and_revoke_auth_key`. These are the only framework-provided migration paths for converting an existing account into a multisig account without already holding the signer. The result is a permanent, irremediable denial of this capability for all modern-key account holders. For `create_with_existing_account_and_revoke_auth_key`, the function is supposed to atomically migrate and revoke the old auth key; the abort prevents the migration but does not lock the account, so funds are not directly frozen — however the user is permanently excluded from the migration path.

### Likelihood Explanation

Secp256k1 and WebAuthn (`SingleKey`) accounts are actively created on Aptos mainnet today. Any such account holder who attempts to use `create_with_existing_account` will hit the abort deterministically. The trigger is a normal, unprivileged user transaction with no special preconditions.

### Recommendation

Extend `verify_signed_message` to handle `SINGLE_KEY_SCHEME` and `MULTI_KEY_SCHEME` analogously to how `rotate_authentication_key_from_public_key` already does: [7](#0-6) 

Add corresponding branches in `verify_signed_message` that deserialize the public key via `single_key::new_public_key_from_bytes` / `multi_key::new_public_key_from_bytes`, derive the expected authentication key, compare it to the on-chain key, and then verify the signature using the appropriate scheme's verification logic.

### Proof of Concept

1. Create an account on Aptos mainnet using a Secp256k1 key (SingleKey scheme, scheme id = 2). The account's on-chain authentication key is `SHA3-256(secp256k1_pubkey_bytes || 0x02)`.
2. Construct a valid `MultisigAccountCreationMessage`, sign it with the Secp256k1 private key.
3. Submit a transaction calling `multisig_account::create_with_existing_account(multisig_address, owners, num_sigs, 2 /*SINGLE_KEY_SCHEME*/, secp256k1_pubkey_bytes, signed_message, [], [])`.
4. The VM executes `account::verify_signed_message` with `account_scheme = 2`. The function falls through to the `else` branch at line 1317 and aborts with `error::invalid_argument(EINVALID_SCHEME)` (error code `0x1000c`).
5. The transaction fails. The user with a Secp256k1 account has no alternative framework entry point to perform this migration. [8](#0-7) [9](#0-8)

    public fun verify_signed_message<T: drop>(
        account: address,
        account_scheme: u8,
        account_public_key: vector<u8>,
        signed_message_bytes: vector<u8>,
        message: T,
    ) acquires Account {
        let auth_key = get_authentication_key(account);
        // Verify that the `SignerCapabilityOfferProofChallengeV2` has the right information and is signed by the account owner's key
        if (account_scheme == ED25519_SCHEME) {
            let pubkey = ed25519::new_unvalidated_public_key_from_bytes(account_public_key);
            let expected_auth_key = ed25519::unvalidated_public_key_to_authentication_key(&pubkey);
            assert!(
                auth_key == expected_auth_key,
                error::invalid_argument(EWRONG_CURRENT_PUBLIC_KEY),
            );

            let signer_capability_sig = ed25519::new_signature_from_bytes(signed_message_bytes);
            assert!(
                ed25519::signature_verify_strict_t(&signer_capability_sig, &pubkey, message),
                error::invalid_argument(EINVALID_PROOF_OF_KNOWLEDGE),
            );
        } else if (account_scheme == MULTI_ED25519_SCHEME) {
            let pubkey = multi_ed25519::new_unvalidated_public_key_from_bytes(account_public_key);
            let expected_auth_key = multi_ed25519::unvalidated_public_key_to_authentication_key(&pubkey);
            assert!(
                auth_key == expected_auth_key,
                error::invalid_argument(EWRONG_CURRENT_PUBLIC_KEY),
            );

            let signer_capability_sig = multi_ed25519::new_signature_from_bytes(signed_message_bytes);
            assert!(
                multi_ed25519::signature_verify_strict_t(&signer_capability_sig, &pubkey, message),
                error::invalid_argument(EINVALID_PROOF_OF_KNOWLEDGE),
            );
        } else {
            abort error::invalid_argument(EINVALID_SCHEME)
        };
    }

    public entry fun create_with_existing_account_and_revoke_auth_key(
        multisig_address: address,
        owners: vector<address>,
        num_signatures_required: u64,
        account_scheme: u8,
        account_public_key: vector<u8>,
        create_multisig_account_signed_message: vector<u8>,
        metadata_keys: vector<String>,
        metadata_values: vector<vector<u8>>,
    ) {
        // Verify that the `MultisigAccountCreationMessage` has the right information and is signed by the account
        // owner's key.
        let proof_challenge = MultisigAccountCreationWithAuthKeyRevocationMessage {
            chain_id: chain_id::get(),
            account_address: multisig_address,
            sequence_number: account::get_sequence_number(multisig_address),
            owners,
            num_signatures_required,
        };
        account::verify_signed_message(
            multisig_address,
            account_scheme,
            account_public_key,
            create_multisig_account_signed_message,
            proof_challenge,
        );

        // We create the signer for the multisig account here since this is required to add the MultisigAccount resource
        // This should be safe and authorized because we have verified the signed message from the existing account
        // that authorizes creating a multisig account with the specified owners and signature threshold.
        let multisig_account = &create_signer(multisig_address);
        create_with_owners_internal(
            multisig_account,
            owners,
            num_signatures_required,
            option::none<SignerCapability>(),
            metadata_keys,
            metadata_values,
        );

        // Rotate the account's auth key to 0x0, which effectively revokes control via auth key.
        let multisig_address = address_of(multisig_account);
        account::rotate_authentication_key_internal(multisig_account, ZERO_AUTH_KEY);
        // This also needs to revoke any signer capability or rotation capability that exists for the account to
        // completely remove all access to the account.
        if (account::is_signer_capability_offered(multisig_address)) {
            account::revoke_any_signer_capability(multisig_account);
        };
        if (account::is_rotation_capability_offered(multisig_address)) {
            account::revoke_any_rotation_capability(multisig_account);
        };
    }
