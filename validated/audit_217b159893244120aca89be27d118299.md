### Title
Exchange actuators ignore the `boolean` return of `reduceAssetAmountV2`/`addAssetAmountV2`, allowing balance updates to proceed even when the deduction silently fails - (File: actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java, ExchangeTransactionActuator.java, ExchangeWithdrawActuator.java)

### Summary
`AccountCapsule.reduceAssetAmountV2` / `addAssetAmountV2` return a `boolean` success flag rather than throwing on failure, exactly like the ERC20 `transfer`/`approve` functions in the External Report that return `false` on failure without reverting. `TransferAssetActuator.execute()` correctly checks this return value and aborts the transaction if it is `false` [1](#0-0) . However, `ExchangeInjectActuator`, `ExchangeTransactionActuator`, and `ExchangeWithdrawActuator` call the same asset-balance-adjusting methods and discard the return value entirely, treating the call as always successful.

### Finding Description
`ExchangeInjectActuator.execute()` calls `accountCapsule.reduceAssetAmountV2(tokenID, tokenQuant, ...)` and `accountCapsule.reduceAssetAmountV2(anotherTokenID, anotherTokenQuant, ...)` without checking their `boolean` return values [2](#0-1) . The exchange pool balance (`exchangeCapsule.setBalance(...)`) and the account's own balance bookkeeping are updated unconditionally before/independently of this call, and the result is committed to the store regardless of whether the underlying asset deduction actually occurred [3](#0-2) .

The same pattern repeats in `ExchangeTransactionActuator.execute()` at the `reduceAssetAmountV2`/`addAssetAmountV2` call sites [4](#0-3) , and in `ExchangeWithdrawActuator.execute()` [5](#0-4) .

This mirrors the report's bug class precisely: the code assumes a state-changing call succeeded because it did not throw/revert, without inspecting the boolean success indicator that the API contract explicitly provides (as proven by the correct handling in `TransferAssetActuator`).

### Impact Explanation
If `reduceAssetAmountV2` can return `false` for a condition that `validate()` does not already fully re-check at execute time (e.g. a race/consistency edge case in the SameTokenName V1/V2 asset map, or an internal map inconsistency), the exchange actuators would still update the `ExchangeCapsule` pool balances and the account's balance/asset map as if the deduction succeeded. This produces an inconsistency between recorded exchange pool reserves and actual backing asset balances — i.e., unbacked/phantom balance in the exchange pool, which any order placer could subsequently attempt to withdraw or trade, effectively minting value not backed by real deposited assets.

### Likelihood Explanation
This path is reachable by any unprivileged asset holder submitting `ExchangeInjectContract`, `ExchangeTransactionContract`, or `ExchangeWithdrawContract` transactions (all broadcastable, no special permission required) via the standard actuator validate/execute flow. The likelihood of actually triggering a `false` return from `reduceAssetAmountV2`/`addAssetAmountV2` at `execute()` time (bypassing the `validate()` sufficiency checks) is not fully confirmed — I was unable to read the full body of `AccountCapsule.reduceAssetAmountV2`/`addAssetAmountV2` to identify concrete state combinations where it returns `false` instead of throwing, due to index/context limits. This should be verified by inspecting `chainbase/src/main/java/org/tron/core/capsule/AccountCapsule.java` directly.

### Recommendation
Update `ExchangeInjectActuator`, `ExchangeTransactionActuator`, and `ExchangeWithdrawActuator` to check the boolean return values of `reduceAssetAmountV2` and `addAssetAmountV2` and throw `ContractExeException` on `false`, mirroring the existing pattern in `TransferAssetActuator.execute()`, so that exchange pool and account balances are never committed inconsistently with the underlying asset ledger.

### Proof of Concept
Not independently reproduced — this analysis is based on static comparison of call sites. A concrete PoC requires confirming, via `AccountCapsule.reduceAssetAmountV2`/`addAssetAmountV2` source, a state under which the method returns `false` (rather than being caught by `validate()`'s pre-checks), then submitting an `ExchangeInjectContract`/`ExchangeTransactionContract`/`ExchangeWithdrawContract` transaction that hits that state to show the exchange pool balance is updated without the corresponding asset actually being deducted from the account.
