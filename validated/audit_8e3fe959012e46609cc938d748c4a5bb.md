### Title
Unbounded per-reference-update loop in non-atomic proc-receive hook causes RPC/transaction DoS via unbatched subprocess spawns - ([File: internal/gitaly/hook/receivepack/receive_pack.go])

### Summary
The proc-receive hook path in Gitaly parses an attacker/pusher-controlled, unbounded list of reference updates from the client's push and, in non-atomic mode, processes them one at a time in a loop, spawning a full `git-update-ref` subprocess and running the `update` hook for every single reference. There is no limit on the number of reference updates a single push may contain, nor any batching of the per-update work, mirroring the "no minimum/no batching" root cause from the external report that allowed an attacker to slow the system down by queuing many small unbounded operations.

### Finding Description
`NewProcReceiveHandler` reads reference updates from the `proc-receive` hook's pkt-line stream in an unbounded loop with no cap on count: [1](#0-0) 

These attacker-supplied updates are later consumed by `procReceiveHook`. When the push is non-atomic, updates are processed **one at a time** in a `for` loop: [2](#0-1) 

For every single update, `receivePackReferenceUpdates` is invoked, which:
1. builds a fresh hooks-payload environment,
2. spawns a brand-new `updateref.New(...)` process (`git update-ref --stdin`),
3. synchronously runs the `update` hook via `hookManager.UpdateHook`,
4. calls `updater.Commit()` to finalize just that one reference. [3](#0-2) 

Each of these steps is an independent, non-batched, relatively expensive operation (process fork/exec, hook execution, disk I/O for the ref-update transaction). Because there is no cap on `handler.ReferenceUpdates()` and no batching of the per-reference work — analogous to the reported chain issue where an unbounded number of queued stake-removal items were each processed individually per block without limits — a client that can trigger the proc-receive hook (i.e., pushes references matching the server's configured `receive.procReceiveRefs` prefixes) can submit an arbitrarily large number of tiny reference updates in one push and force Gitaly to sequentially spawn thousands of subprocesses and hook executions within a single RPC invocation, while holding the associated `storage.Transaction` (`tx`) open the entire time until `tx.Commit(ctx)` is finally called after the loop completes: [4](#0-3) 

### Impact Explanation
This causes a resource-exhaustion style denial of service against the Gitaly node handling the push: repeated subprocess spawning and hook execution for an attacker-controlled number of reference updates consumes CPU, memory, and file descriptors, and keeps the underlying `ReceivePack`/proc-receive RPC and its transaction (which participates in cluster-wide reference-transaction voting per `doc/hooks.md`) open for an extended period. In a Praefect-coordinated cluster this can stall the quorum/voting machinery that other nodes are waiting on, degrading availability similarly in spirit to the original chain-halting report, though scoped to the RPC handler and transaction rather than a global consensus loop.

### Likelihood Explanation
Likelihood is moderate: it requires the target repository to have `receive.procReceiveRefs` configured to intercept the ref prefixes the attacker pushes to (this is used by GitLab for certain ref namespaces), and it requires the attacker to have push access to those refs. No malicious peer/node or privileged access is required beyond normal push permission, and the number of reference updates per push is entirely attacker-controlled with no server-side cap.

### Recommendation
Impose an explicit maximum on the number of reference updates accepted per proc-receive invocation (reject or truncate excessively large update sets), and/or batch the non-atomic per-update work (hook invocation and `git update-ref` transactions) into chunks processed via a single or few `updateref` sessions rather than spawning a fresh subprocess and hook run per individual reference, similar to how `UpdateReferences` batches updates into one `updateref.Updater` transaction.

### Proof of Concept
1. Configure a repository so that `receive.procReceiveRefs` matches a ref prefix the attacker can push to (as used by Gitaly's proc-receive hook flow).
2. Perform a non-atomic push (`git push` without atomic push option) containing a very large number of reference updates under that prefix (e.g., tens of thousands of distinct ref names), which is accepted without limit by `NewProcReceiveHandler`'s parsing loop (`internal/gitaly/hook/procreceive_handler.go:80-99`).
3. Observe that `procReceiveHook`'s non-atomic branch (`internal/gitaly/hook/receivepack/receive_pack.go:112-138`) sequentially spawns one `git update-ref` subprocess and one `update` hook execution per reference, causing high CPU/process load and prolonging the RPC and its transaction well beyond normal push durations, while concurrent operations on the same transaction/quorum are blocked.

func receivePackReferenceUpdates(
	ctx context.Context,
	cfg config.Cfg,
	req gitcmd.ReceivePackRequest,
	repo *localrepo.Repo,
	hookManager hook.Manager,
	updates []hook.ReferenceUpdate,
	stdout, stderr io.Writer,
) (returnedErr error) {
	hooksPayload, err := setupHooksPayloadEnv(ctx, cfg, req, repo, gitcmd.UpdateHook)
	if err != nil {
		return fmt.Errorf("creating hooks payload: %w", err)
	}

	updater, err := updateref.New(ctx, repo, updateref.WithNoDeref())
	if err != nil {
		return fmt.Errorf("spawning ref updater: %w", err)
	}
	defer func() {
		if err := updater.Close(); err != nil && returnedErr == nil {
			returnedErr = fmt.Errorf("cancel ref updater: %w", err)
		}
	}()

	if err := updater.Start(); err != nil {
		return fmt.Errorf("start reference transaction: %w", err)
	}

	for _, update := range updates {
		if err := hookManager.UpdateHook(
			ctx,
			req.GetRepository(),
			update.Ref.String(),
			update.OldOID.String(),
			update.NewOID.String(),
			[]string{hooksPayload},
			stdout, stderr,
		); err != nil {
			return fmt.Errorf("running update hook: %w", err)
		}

		if err := updater.Update(update.Ref, update.NewOID, update.OldOID); err != nil {
			return fmt.Errorf("queueing ref to be updated: %w", err)
		}
	}

	if err := updater.Commit(); err != nil {
		return updateError{error: err}
	}

	return nil
}
