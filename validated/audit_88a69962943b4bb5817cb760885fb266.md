### Title
Fee-on-transfer NEP-141 tokens allow crediting more internal Defuse balance than tokens actually custodied, insolvency/frozen-funds for other holders of that asset - (File: contracts/defuse/src/contract/tokens/nep141/deposit.rs)

### Summary
`ft_on_transfer` credits the internal Defuse ledger with the `amount` value declared by the token contract's `ft_transfer_call` payload, without verifying that the `defuse` contract's actual on-chain balance of that token increased by the same amount. For a fee-on-transfer NEP-141 token this breaks the invariant that the sum of internal balances (`total_supplies`) for a `TokenId` must equal the real tokens the contract holds.

### Finding Description
`ft_on_transfer` receives `amount: U128` as reported by the caller (the token contract), builds `TokenId::Nep141(...)`, and calls `self.deposit(receiver_id, [(token_id, amount.0)], ...)` unconditionally: [1](#0-0) 

`Contract::deposit` mints exactly `amount` into `total_supplies` (the global ledger for that `TokenId`) and into the receiver's `token_balances`, with no check against the actual token balance held by the contract: [2](#0-1) 

There is no balance-before/balance-after comparison anywhere in this deposit path, unlike the pattern recommended for fee-on-transfer compatibility (checking `balanceOf` delta). If the underlying NEP-141 token deducts a transfer fee (i.e., is a fee-on-transfer token), `defuse` actually receives strictly less than `amount`, yet credits the depositor with the full `amount` in the internal ledger. This means:

`sum(internal balances for TokenId) > actual token balance held by defuse contract`

This equality (total internal credited balance == actual custodied balance) is the custody binding that gets broken.

On withdrawal, `ft_withdraw`/`internal_ft_withdraw` debits the internal ledger by the requested `amount` and then attempts an actual `ft_transfer`/`ft_transfer_call` of that same `amount` out of the contract's real token balance: [3](#0-2) [4](#0-3) 

Since the internal ledger for that `TokenId` is inflated relative to what the contract actually holds, once enough withdrawals occur, the last withdrawer(s) of that token will find that `ft_transfer` fails (insufficient real balance on the underlying token contract) even though their internal balance appears valid — permanently freezing their credited balance for that token — or, depending on fee mechanics/order of operations, earlier withdrawers effectively drain the shared pool at the expense of others holding balances of the same fee-on-transfer `TokenId`.

### Impact Explanation
This is a shared-custody insolvency: `defuse` is a multi-user vault where all users' balances of a given `TokenId` are backed by one pooled real-token balance held by the contract. Any user (attacker or not) depositing a fee-on-transfer NEP-141 token creates a permanent shortfall between the internal ledger and the actual pooled balance for that `TokenId`. This can result in some legitimate depositors of that same token being unable to withdraw their credited balance (funds permanently frozen) once the pool is depleted by earlier withdrawers, which matches the "funds permanently frozen" / broken-conservation impact category.

### Likelihood Explanation
Deposits into `defuse` via `ft_on_transfer` are permissionless — any account can call `ft_transfer_call` on any NEP-141 contract (including one they control) with `defuse` as receiver, and `defuse` will accept and credit any NEP-141 `TokenId` without an allowlist visible in this deposit path. Fee-on-transfer tokens are a known real-world token pattern, so an attacker (or an unaware integrator) depositing such a token, or even a legitimate protocol-listed token that later switches to charging a transfer fee, would trigger this shortfall without any privileged action.

### Recommendation
In `ft_on_transfer` (`contracts/defuse/src/contract/tokens/nep141/deposit.rs`), measure the actual token balance received by the contract before crediting the internal ledger — e.g., record `ft_balance_of(current_account_id)` before/after via a cross-contract call, or restrict deposits to an allowlist of tokens known not to charge transfer fees, and reject/require the credited amount to equal the amount actually received rather than trusting the caller-supplied `amount`.

### Proof of Concept
1. An attacker deploys (or uses) a fee-on-transfer NEP-141 token `FOT` that deducts e.g. 5% on every transfer.
2. Attacker calls `FOT.ft_transfer_call(defuse, amount=1000, msg=DepositMessage{receiver_id: attacker})`.
3. `defuse` actually receives 950 `FOT` tokens (due to the fee), but `ft_on_transfer` credits the attacker's internal balance with the full `amount.0 = 1000`, and `total_supplies[TokenId::Nep141(FOT)] += 1000`. [5](#0-4) 
4. A second, honest user also deposits 1000 `FOT` the same way, similarly only 950 actually land in the contract, but 1000 is credited; total internal ledger for `FOT` is now 2000 while actual contract balance is 1900.
5. Attacker calls `ft_withdraw(token=FOT, amount=1000)` — internal ledger is debited 1000, and `do_ft_withdraw` issues `ft_transfer(receiver, 1000)` from the contract's real `FOT` balance (1900), succeeding and leaving 900 real tokens for the honest user, whose internal balance still shows 1000. [6](#0-5) 
6. Honest user calls `ft_withdraw(token=FOT, amount=1000)` — internal ledger debit succeeds, but the underlying `ft_transfer` for 1000 fails because the contract only holds 900 real `FOT`, permanently freezing/losing the honest user's credited balance (or, depending on the fee-on-transfer token's exact semantics on the outbound leg, further compounding the shortfall).

    fn ft_on_transfer(
        &mut self,
        sender_id: AccountId,
        amount: U128,
        msg: String,
    ) -> PromiseOrValue<U128> {
        require!(amount.0 > 0, "zero amount");

        let token_id = TokenId::Nep141(Nep141TokenId::new(env::predecessor_account_id()));

        let DepositMessage {
            receiver_id,
            action,
        } = if msg.is_empty() {
            DepositMessage::new(sender_id.clone())
        } else {
            msg.parse().unwrap_or_else(|e| panic!("{e}"))
        };

        self.deposit(
            receiver_id.clone(),
            [(token_id.clone(), amount.0)],
            Some("deposit"),
        )
        .unwrap_or_else(|err| err.panic());

impl Contract {
    pub(crate) fn deposit(
        &mut self,
        owner_id: AccountId,
        tokens: impl IntoIterator<Item = (TokenId, u128)>,
        memo: Option<&str>,
    ) -> Result<()> {
        let owner = self
            .storage
            .accounts
            .get_or_create(owner_id.clone())
            // deposits are allowed for locked accounts
            .as_inner_unchecked_mut();

        let mut mint_event = MtMintEvent {
            owner_id: owner_id.into(),
            token_ids: Vec::new().into(),
            amounts: Vec::new().into(),
            memo: memo.map(Into::into),
        };

        for (token_id, amount) in tokens {
            if amount == 0 {
                return Err(DefuseError::InvalidIntent);
            }

            mint_event.token_ids.to_mut().push(token_id.to_string());
            mint_event.amounts.to_mut().push(amount);

            let total_supply = self
                .storage
                .state
                .total_supplies
                .add(token_id.clone(), amount)
                .ok_or(DefuseError::BalanceOverflow)?;
            match token_id {
                TokenId::Nep171(ref tid) => {
                    if total_supply > 1 {
                        return Err(DefuseError::NftAlreadyDeposited(tid.clone()));
                    }
                }
                TokenId::Nep141(_) | TokenId::Nep245(_) | TokenId::Imt(_) => {}
            }

            owner
                .token_balances
                .add(token_id, amount)
                .ok_or(DefuseError::BalanceOverflow)?;
        }

    #[private]
    pub fn do_ft_withdraw(withdraw: FtWithdraw) -> Promise {
        let min_gas = withdraw.min_gas();
        let p = if let Some(storage_deposit) = withdraw.storage_deposit {
            require!(
                promise_result_checked_void(0).is_ok(),
                "near_withdraw failed",
            );

            ext_storage_management::ext(withdraw.token)
                .with_attached_deposit(storage_deposit)
                .with_static_gas(STORAGE_DEPOSIT_GAS)
                // do not distribute remaining gas here
                .with_unused_gas_weight(0)
                .storage_deposit(Some(withdraw.receiver_id.clone()), None)
        } else {
            Promise::new(withdraw.token)
        };

        let p = ext_ft_core::ext_on(p)
            .with_attached_deposit(NearToken::from_yoctonear(1))
            .with_static_gas(min_gas)
            // distribute remaining gas here
            .with_unused_gas_weight(1);
        if let Some(msg) = withdraw.msg {
            p.ft_transfer_call(
                withdraw.receiver_id,
                withdraw.amount.into(),
                withdraw.memo,
                msg,
            )
        } else {
            p.ft_transfer(withdraw.receiver_id, withdraw.amount.into(), withdraw.memo)
        }
    }
