### Title
Bounty sub-account funds permanently stranded when holding assets outside the statically-configured `RelevantAssets` list - (File: `substrate/frame/bounties/src/lib.rs`)

### Summary
`pallet-bounties` returns a bounty's funds to the treasury via the `TransferAllAssets` trait, most commonly implemented by `TransferAllFungibles<AccountId, Fungibles, RelevantAssets>`. This implementation only sweeps the fixed, statically-configured `RelevantAssets` list [1](#0-0) . Both `close_bounty` and the newer permissionless `reclaim_bounty_funds` extrinsic rely solely on this mechanism to recover a bounty sub-account's balance [2](#0-1) [3](#0-2) . Any asset a bounty account holds that is not in `RelevantAssets` is permanently unreachable by the treasury and by the permissionless reclaim path, exactly mirroring the ERC1155 "not in the enumerated withdrawal set" value-leak pattern from the external report.

### Finding Description
`Bounty` accounts are pallet-owned sub-accounts (`Self::bounty_account_id(bounty_id)`) that can receive arbitrary fungible assets sent to them by anyone (there is no restriction preventing an outside party — or a mistaken/malicious curator interaction — from transferring an asset into a bounty's sub-account) [2](#0-1) . When a bounty is closed or reclaimed, only assets present in the runtime-configured `RelevantAssets: Get<Vec<AssetId>>` list are ever transferred back to the treasury account:

```
let assets_twice = RelevantAssets::get().into_iter().chain(RelevantAssets::get().into_iter());
for id in assets_twice {
    let balance = Fungibles::reducible_balance(id.clone(), from, ...);
    ...
}
``` [4](#0-3) 

This is confirmed by the pallet's own test suite: assets `3` and `4` are deliberately outside `RelevantAssets = [WithId(1), Native, WithId(2)]` [5](#0-4) , and `close_bounty_with_additional_assets_works` explicitly asserts that after closing the bounty, the "irrelevant" asset balances (10 units of asset `4`, and asset `3` when sufficient/insufficient) remain stuck in the bounty pot account rather than being swept to the treasury [6](#0-5) . `reclaim_bounty_funds`, added specifically to sweep "stranded funds," has the identical limitation since it calls the same `T::TransferAllAssets::force_transfer_all_assets` [7](#0-6) , so it cannot recover assets outside `RelevantAssets` either.

Just as the Party protocol's `rageQuit()` could only enumerate ETH and ERC20 balances (never ERC1155), leaving a rage-quitter's fair share of ERC1155 tokens permanently in the treasury, `pallet-bounties`' asset-recovery path can only enumerate the finite, governance/runtime-configured `RelevantAssets` set, leaving any other asset type sent to (or accrued in) the bounty account permanently locked with no dispatchable path to move it — not even via the permissionless `reclaim_bounty_funds` extrinsic that was purpose-built to fix "stranded funds."

### Impact Explanation
This is a permanent value/fund lock: any asset kind not enumerated in `RelevantAssets` that ends up in a bounty's sub-account becomes irretrievable via any pallet-bounties dispatchable, including the extrinsic (`reclaim_bounty_funds`) explicitly designed to solve stranded-funds cases. On chains with a growing/evolving set of asset kinds (new `pallet-assets` IDs, new sufficient assets, XCM-derived foreign assets, etc.), this gap widens over time since `RelevantAssets` is a static, compile-time/config-time list that cannot be updated without a runtime upgrade.

### Likelihood Explanation
No privileged actor is required: any account can permissionlessly transfer an out-of-list asset into a live bounty's sub-account (which is a normal, publicly-derived `AccountId`) before or during a bounty's lifecycle, and the funds become stuck once the bounty is closed. This can happen accidentally (a user sending the wrong asset) or be triggered deliberately by anyone wanting to lock value in a treasury-controlled account, and neither `close_bounty` nor `reclaim_bounty_funds` provide any recovery route for that specific asset.

### Recommendation
Extend `TransferAllAssets`/`TransferAllFungibles` (or add a fallback dispatchable) to enumerate all balances actually held by the bounty account rather than only the statically configured `RelevantAssets` list — e.g., by iterating `frame_system::Account` references/asset ownership indices for the account, or by exposing a governance-gated "sweep arbitrary asset" call scoped to closed bounty accounts, so that any asset type accidentally or maliciously deposited can still be recovered by the treasury.

### Proof of Concept
1. Configure a runtime with `pallet-bounties::TransferAllAssets = TransferAllFungibles<AccountId, Fungibles, RelevantAssets>` where `RelevantAssets` lists only assets `{Native, 1, 2}` (as in the existing test setup) [5](#0-4) .
2. Propose, approve, and fund a bounty; have any account transfer asset `4` (not in `RelevantAssets`) into the bounty's sub-account (`Bounties::bounty_account_id(bounty_id)`).
3. Call `close_bounty` (or later `reclaim_bounty_funds`); observe — as shown by `close_bounty_with_additional_assets_works` — that native balance and assets `1`/`2` move to the treasury, but asset `4`'s balance remains on the (still-existing) bounty sub-account permanently [8](#0-7) .
4. No further pallet-bounties call can move that asset `4` balance out of the sub-account; the value is permanently stranded.

/// Transfer all `RelevantAssets` of the `Fungibles` from one account to another.
///
/// The native asset should be the first in the list of `RelevantAssets`, otherwise the transfers
/// of the other maybe fails.
pub struct TransferAllFungibles<AccountId, Fungibles, RelevantAssets>(
	core::marker::PhantomData<(AccountId, Fungibles, RelevantAssets)>,
);
impl<AccountId, Fungibles, RelevantAssets> TransferAllAssets<AccountId>
	for TransferAllFungibles<AccountId, Fungibles, RelevantAssets>
where
	Fungibles: FungiblesMutate<AccountId> + FungiblesCreate<AccountId>,
	RelevantAssets: Get<Vec<<Fungibles as FungiblesInspect<AccountId>>::AssetId>>,
	AccountId: Eq + Clone,
{
	fn force_transfer_all_assets(from: &AccountId, to: &AccountId) -> Result<bool, DispatchError> {
		// We iterate through all assets twice in case that the Native asset was not last in the
		// list and ED remained because of an insufficient asset at the end of the list.
		let assets_twice =
			RelevantAssets::get().into_iter().chain(RelevantAssets::get().into_iter());

		let mut transferred_any = false;
		for id in assets_twice {
			let balance = Fungibles::reducible_balance(
				id.clone(),
				from,
				Preservation::Expendable,
				Fortitude::Polite,
			);
			if balance.is_zero() {
				continue;
			}

			// Ignore errors since this can only fail if the receiver does not exist.
			if Fungibles::transfer(id, from, to, balance, Preservation::Expendable).is_ok() {
				transferred_any = true;
			}
		}
		Ok(transferred_any)
	}
