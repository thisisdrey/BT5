### Title
Uncontrolled Resource Consumption via Full Asset-Issue Store Scan+Sort on Every Paginated Query - (File: chainbase/src/main/java/org/tron/core/store/AssetIssueStore.java)

### Summary
`AssetIssueStore.getAllAssetIssues()` iterates the *entire* `asset-issue` key-value store on every call, and `getAssetIssuesPaginated(offset, limit)` builds on top of it by loading the full list into memory and re-sorting it in full before slicing out the requested page. This is reachable from multiple unauthenticated HTTP/gRPC endpoints (`/wallet/getassetissuelist`, `/wallet/getpaginatedassetissuelist`, `/wallet/getassetissuebyaccount`, and their `WalletSolidity`/`WalletOnPBFT` equivalents), so any anonymous API client can force the node to repeatedly perform a full-store read plus an `O(n log n)` sort regardless of the tiny `limit` requested — directly analogous to the HAPI FHIR issue where a paginated "history" request still triggered a full index scan (`SELECT COUNT`) on every call.

### Finding Description
`getAllAssetIssues()` performs `Streams.stream(iterator()).map(Entry::getValue).collect(Collectors.toList())` over the whole underlying store: [1](#0-0) 

`getAssetIssuesPaginated` then sorts this entire in-memory list before returning a small slice, so the "pagination" only limits the *response* size, not the *work* performed: [2](#0-1) 

This is invoked from `Wallet.getAssetIssueList()`, `Wallet.getAssetIssueList(offset, limit)`, and `Wallet.getAssetIssueByAccount()`, all of which call `getAllAssetIssues()` under the hood on every single request: [3](#0-2) 

These are exposed via public, unauthenticated servlets: `GetAssetIssueListServlet`, `GetPaginatedAssetIssueListServlet` [4](#0-3) , mirrored on the FullNode, WalletSolidity, and PBFT HTTP/gRPC interfaces: [5](#0-4) [6](#0-5) 

No offset/limit sanity bound is applied before scanning — `limit` is only capped *after* the full list is built and sorted (`limit > ASSET_ISSUE_COUNT_LIMIT_MAX ? ...`), so the expensive full-scan-and-sort work is unavoidable no matter what parameters the caller sends: [7](#0-6) 

### Impact Explanation
Every call to these public, unauthenticated endpoints does a full linear scan of the asset-issue store plus a full sort, even when the caller only wants a single row (`offset=0&limit=1`). An attacker capable of sending a modest number of concurrent requests can force the node to repeatedly perform this expensive scan+sort, consuming CPU and I/O and degrading or denying the API to legitimate users — the same class of impact accepted for the original HAPI FHIR advisory ("an API the node can no longer serve"). Because `GetAssetIssueList`/`GetPaginatedAssetIssueList` are enabled by default (not in `node.disabledApi`) and rate-limited only by the generic default (`QpsRateLimiterAdapter qps=1000`) unless an operator has explicitly configured a stricter per-servlet limit, the default configuration does not meaningfully throttle this cost amplification.

### Likelihood Explanation
The endpoints require no authentication, no signed transaction, and no special permissions — any external HTTP/gRPC client can invoke them directly. The cost of a single request scales with the total number of assets ever issued on the network (which only grows over time and is a shared, cumulative resource across the whole network, not something a single caller needs to have created). Given the default rate limits (1000 QPS unless a stricter servlet-specific policy is configured), an attacker can trivially issue a sustained volume of these requests to keep the store fully re-scanned and re-sorted on almost every call.

### Recommendation
- In `AssetIssueStore`, avoid loading and sorting the entire store on every paginated call. Maintain an ordered index (e.g., a sorted secondary index keyed by name/order) that can be scanned incrementally starting at `offset`, or cache the sorted list and invalidate/refresh it only when the store changes.
- Cap `offset` and `limit` to sane bounds before any store iteration begins, rejecting or clamping excessively large offsets early.
- Apply a stricter, servlet-specific rate limit (e.g., `IPQPSRateLimiterAdapter` or `GlobalPreemptibleAdapter`) by default for `GetAssetIssueListServlet`, `GetPaginatedAssetIssueListServlet`, and their Solidity/PBFT equivalents (and the analogous gRPC methods), rather than relying on the generic 1000 QPS default.
- Consider adding a maximum result cap enforced independent of the sort step (fail fast if the store is large and the request pattern indicates abuse).

### Proof of Concept
1. Deploy or connect to a java-tron FullNode with HTTP API enabled and a moderately large `asset-issue` store (grows naturally over time as accounts issue TRC10 tokens; can also be grown by an attacker willing to pay the standard asset-issuance fee repeatedly).
2. From an unauthenticated client, issue concurrent requests:
   ```
   POST /wallet/getpaginatedassetissuelist
   {"offset": 0, "limit": 1}
   ```
   repeated at high concurrency/QPS (within the default 1000 QPS ceiling).
3. Each request triggers `AssetIssueStore.getAllAssetIssues()` (full store iteration) followed by an `O(n log n)` sort of the full result set inside `getAssetIssuesPaginated`, even though only 1 result is requested — observe elevated CPU/latency on the node under sustained concurrent load, degrading service for other API callers.

  private List<AssetIssueCapsule> getAssetIssuesPaginated(List<AssetIssueCapsule> assetIssueList,
      long offset, long limit) {
    if (limit < 0 || offset < 0) {
      return null;
    }

    if (assetIssueList.size() <= offset) {
      return null;
    }
    assetIssueList.sort((o1, o2) -> {
      if (o1.getName() != o2.getName()) {
        return o1.getName().toStringUtf8().compareTo(o2.getName().toStringUtf8());
      }
      return Long.compare(o1.getOrder(), o2.getOrder());
    });
    limit = limit > ASSET_ISSUE_COUNT_LIMIT_MAX ? ASSET_ISSUE_COUNT_LIMIT_MAX : limit;
    long end = offset + limit;
    end = end > assetIssueList.size() ? assetIssueList.size() : end;
    return assetIssueList.subList((int) offset, (int) end);
  }

  public AssetIssueList getAssetIssueList() {
    BandwidthProcessor processor = new BandwidthProcessor(chainBaseManager);

  public AssetIssueList getAssetIssueList(long offset, long limit) {
    AssetIssueList.Builder builder = AssetIssueList.newBuilder();

    List<AssetIssueCapsule> assetIssueList =
        getAssetIssueStoreFinal(chainBaseManager.getDynamicPropertiesStore(),
            chainBaseManager.getAssetIssueStore(),
            chainBaseManager.getAssetIssueV2Store()).getAssetIssuesPaginated(offset, limit);

    if (CollectionUtils.isEmpty(assetIssueList)) {
      return null;
    }

    BandwidthProcessor processor = new BandwidthProcessor(chainBaseManager);
    assetIssueList.forEach(
        issueCapsule -> {
          processor.updateUsage(issueCapsule);
          builder.addAssetIssue(issueCapsule.getInstance());
        }
    );
    return builder.build();
  }

  public AssetIssueList getAssetIssueByAccount(ByteString accountAddress) {
    if (accountAddress == null || accountAddress.isEmpty()) {
      return null;
    }

    List<AssetIssueCapsule> assetIssueCapsuleList =
        getAssetIssueStoreFinal(chainBaseManager.getDynamicPropertiesStore(),
            chainBaseManager.getAssetIssueStore(),
            chainBaseManager.getAssetIssueV2Store()).getAllAssetIssues();

    BandwidthProcessor processor = new BandwidthProcessor(chainBaseManager);
    AssetIssueList.Builder builder = AssetIssueList.newBuilder();
    assetIssueCapsuleList.stream()
        .filter(assetIssueCapsule -> assetIssueCapsule.getOwnerAddress().equals(accountAddress))
        .forEach(
            issueCapsule -> {
              processor.updateUsage(issueCapsule);
              builder.addAssetIssue(issueCapsule.getInstance());
            });

    return builder.build();
  }
