The `TryFromToken for u128` implementation explicitly checks range before truncation, refuting the premise of the question.

### Title
No vulnerability: `u128` decode in wallet-contract already rejects values above `2^128 - 1` - ([File: ethabi_utils.rs])

### Summary
The premise that `ethabi_utils::abi_decode` silently narrows a `uint256` value to `u128` via truncation is factually incorrect. The `TryFromToken for u128` implementation performs an explicit bounds check (`x <= U128_MAX`) before calling `low_u128()`, and returns `Err(INVALID_ABI_DATA)` for any value exceeding `2^128 - 1`, so a `value` of exactly `2^128` is rejected deterministically, not truncated to `0`.

### Finding Description
In `runtime/near-wallet-contract/implementation/wallet-contract/src/eth_emulation.rs`, the ERC-20 `transfer` selector handling decodes the ABI-encoded `(Address, uint256)` payload into `(Address, u128)` via `ethabi_utils::abi_decode(&ERC20_TRANSFER_SIGNATURE, &tx.data[4..])`. [1](#0-0) 

The actual decode logic lives in `TryFromToken for u128` in `ethabi_utils.rs`, which converts the token to a `U256` via `into_uint()` and compares it against `U128_MAX = U256([u64::MAX, u64::MAX, 0, 0])` (i.e., `2^128 - 1`) before returning the value; if the input exceeds this bound, it returns `Err(INVALID_ABI_DATA)` instead of truncating. [2](#0-1) 

This is the same pattern used consistently for `u8`, `u32`, and `u64` narrowing conversions in the same file, all of which perform explicit range checks rather than relying on truncating accessors like `low_u128()`/`low_u32()`/`low_u64()` unconditionally. [3](#0-2) 

Because the range check happens in this repo's own code (not merely relying on `ethabi`'s crate-level `U256` decode semantics, which just parses the raw 256-bit word), there is no "narrowing" behavior dependent on `ethabi` version upgrades that could produce divergent outcomes across differing library versions. A value of `2^128` is deterministically an `Err` on every build, not a truncation to `k`.

### Impact Explanation
No impact: the described exploit path does not exist. There is no truncation of `uint256` to `u128` that could produce a smaller minted/transferred amount than encoded; over-range values are uniformly rejected with `UserError::InvalidAbiEncodedData`, so `ft_transfer` is never invoked with a wrong amount and no value-conservation or determinism violation occurs.

### Likelihood Explanation
Not applicable — the bounds check is present in all builds of this code, so there is no dependency on external crate version differences and no scenario in which two honest nodes running this codebase would compute different outcomes for the same encoded `value`.

### Recommendation
No fix required for this specific claim. (General note: it would still be reasonable to add an explicit unit test asserting `TryFromToken::try_from_token` for `u128` returns `Err` on `U256::from(2u128).pow(128.into())` and `Ok` on `U128_MAX`, to guard against regressions from future refactors of this file — but this is a hardening suggestion, not a vulnerability fix.)

### Proof of Concept
Not applicable, since no vulnerability exists. A regression-guarding test could assert:

impl TryFromToken for u8 {
    fn try_from_token(t: Token) -> Result<Self, Error> {
        const U8_MAX: U256 = U256([u8::MAX as u64, 0, 0, 0]);
        let x = t.into_uint().ok_or(INVALID_ABI_DATA)?;
        if x <= U8_MAX {
            Ok(x.low_u32() as u8)
        } else {
            Err(INVALID_ABI_DATA)
        }
    }
}
