Audit Report

## Title
Restricted/blacklisted accounts can still receive staking reward payouts via `payee`, bypassing the staking participation `Filter` - (File: `substrate/frame/staking/src/pallet/mod.rs`, `substrate/frame/staking/src/pallet/impls.rs`)

## Summary
`pallet-staking`'s `T::Filter::contains` restriction, intended to blacklist accounts already participating in staking another way (e.g. via nomination pools), is only enforced against the `stash` origin in `bond`/`bond_extra`/`rebond`, never against the `payee`/reward-destination account. Any unrestricted account can bond and name a restricted account as `RewardDestination::Account`, letting that restricted account continuously receive staking reward payouts without ever passing through the `Filter` check itself.

## Finding Description
`Pallet::<T>::bond` checks the filter only on the signer/stash: [1](#0-0) . The `Config::Filter` doc explicitly states its purpose is to blacklist accounts "participating in staking in another way (such as pools)" [2](#0-1) .

`set_payee` (the extrinsic) and the `StakingInterface::set_payee` implementation never call `T::Filter::contains` on the destination account — they only check virtual-staker self-payment restrictions: [3](#0-2) [4](#0-3) .

Confirmed also in the async pallet variant, with the same pattern in `set_payee`: [5](#0-4) .

The actual payout mechanism (`make_payout` in `pallet-staking`, `make_payout_from_provider`/`make_payout_legacy` in `pallet-staking-async`) resolves `RewardDestination::Account(dest_account)` and mints/transfers funds directly into that account with no filter check at all: [6](#0-5) [7](#0-6) . This is confirmed to actually work by the existing `reward_destination_account` test, which shows funds landing in an arbitrary destination account `7` that never itself bonded: [8](#0-7) .

Meanwhile the existing test `restricted_accounts_can_only_withdraw` confirms that the same restricted account *cannot* call `bond` directly, showing the check is asymmetric — enforced on the caller but not on the beneficiary: [9](#0-8) . The only "reward destination restriction" that exists in the codebase guards against virtual stakers naming themselves as payee (`RewardDestinationRestricted`), which is an unrelated invariant (compounding-lock issue), not the `Filter`/blacklist invariant: [10](#0-9) .

## Impact Explanation
This is a genuine gap in the intended runtime invariant that restricted accounts (e.g., accounts already staking through `pallet-nomination-pools`) cannot obtain staking-economics value. An unrestricted account `A` can perpetually route staking rewards to a restricted account `B` by setting `payee = RewardDestination::Account(B)`, and `B` accumulates reward payouts every era despite never itself passing the `Filter` gate. This falls under "runtime bugs that compromise intended behavior," matching the accepted impact gate. It does not create unbacked minting, double-settlement, or origin escalation of the staker's own funds — the payout amount and validator reward math are unaffected; only the destination beneficiary's restriction is bypassed, which is a policy/invariant violation rather than a value-conservation or fund-theft bug.

## Likelihood Explanation
Exploitation requires only public, unprivileged use of the `bond`/`set_payee` extrinsics by any signed account naming any other account (restricted or not) as `RewardDestination::Account`. No compromised keys, governance, or malicious infrastructure roles are needed, and it is fully repeatable every era for as long as the payee stays configured.

## Recommendation
Extend `T::Filter::contains` checks to cover the `payee`/`reward_acc` account when it resolves to `RewardDestination::Account` in: `Pallet::<T>::bond`'s payee argument, `Pallet::<T>::set_payee` extrinsic, and the `StakingInterface::set_payee`/`bond` implementations in both `pallet-staking` and `pallet-staking-async`, rejecting with `Error::<T>::Restricted` (or a similarly-named error) if the destination is restricted — mirroring the existing check on the stash side.

## Proof of Concept
1. Configure a runtime with `Filter = MockedRestrictList` and add account `B` (e.g. `302`) to the restrict list, per the mock helper `restrict(&bob)`: [11](#0-10) .
2. Confirm `B` alone cannot bond: `Staking::bond(RuntimeOrigin::signed(B), 100, RewardDestination::Staked)` fails with `Error::<T>::Restricted`, as in `restricted_accounts_can_only_withdraw`: [9](#0-8) .
3. Have unrestricted account `A` bond and call `Staking::set_payee(RuntimeOrigin::signed(A), RewardDestination::Account(B))` — succeeds because only `A` is checked against `Filter`, not `B`: [3](#0-2) .
4. Advance to a rewarded era and trigger payout (`payout_stakers`/`make_all_reward_payment`); assert `B`'s free balance increases, analogous to the existing `reward_destination_account` test pattern that verifies funds landing in a named `Account` destination: [8](#0-7) .

	fn set_payee(stash: &Self::AccountId, reward_acc: &Self::AccountId) -> DispatchResult {
		// Since virtual stakers are not allowed to compound their rewards as this pallet does not
		// manage their locks, we do not allow reward account to be set same as stash. For
		// external pallets that manage the virtual bond, they can claim rewards and re-bond them.
		ensure!(
			!Self::is_virtual_staker(stash) || stash != reward_acc,
			Error::<T>::RewardDestinationRestricted
		);

		let ledger = Self::ledger(Stash(stash.clone()))?;
		ledger
			.set_payee(RewardDestination::Account(reward_acc.clone()))
			.defensive_proof("ledger was retrieved from storage, thus its bonded; qed.")?;

		Ok(())
	}

	/// Determine the payout account from a reward destination.
	fn payout_account_for_dest(
		stash: &T::AccountId,
		dest: &RewardDestination<T::AccountId>,
	) -> Option<T::AccountId> {
		match dest {
			RewardDestination::Stash | RewardDestination::Staked => Some(stash.clone()),
			RewardDestination::Account(ref dest_account) => Some(dest_account.clone()),
			RewardDestination::None => None,
			#[allow(deprecated)]
			RewardDestination::Controller => Self::bonded(stash),
		}
	}

	/// Make a payment to a staker from an era reward pot (transfer, not mint).
	fn make_payout_from_provider(
		era: EraIndex,
		stash: &T::AccountId,
		amount: BalanceOf<T>,
	) -> Option<(BalanceOf<T>, RewardDestination<T::AccountId>)> {
		if amount.is_zero() {
			return None;
		}

		let dest = match Self::payee(Stash(stash.clone())) {
			Some(d) => d,
			None => {
				Self::deposit_event(Event::<T>::Unexpected(UnexpectedKind::MissingPayee {
					era,
					stash: stash.clone(),
				}));
				return None;
			},
		};

		let payout_account = Self::payout_account_for_dest(stash, &dest)?;

		let staker_rewards_pot =
			T::RewardPots::pot_account(RewardPot::Era(era, RewardKind::StakerRewards));
		if let Err(e) = T::Currency::transfer(
			&staker_rewards_pot,
			&payout_account,
			amount,
			Preservation::Expendable,
		) {
			log!(
				error,
				"Failed to transfer reward from pot for era {:?}, stash {:?}: {:?}",
				era,
				stash,
				e
			);
			return None;
		}

		// For Staked destination, update ledger.
		if matches!(dest, RewardDestination::Staked) {
			if let Ok(mut ledger) = Self::ledger(Stash(stash.clone())) {
				ledger.active += amount;
				ledger.total += amount;
				let _ = ledger
					.update()
					.defensive_proof("ledger fetched from storage, so it exists; qed.");
			}
		}

		Some((amount, dest))
	}

#[test]
fn reward_destination_account() {
	ExtBuilder::default().nominate(false).build_and_execute(|| {
		// initial conditions
		assert!(Session::validators().contains(&11));
		assert_ok!(Staking::set_payee(RuntimeOrigin::signed(11), RewardDestination::Account(7)));

		assert_eq!(asset::total_balance::<T>(&11), 1001);
		assert_eq!(
			Staking::ledger(11.into()).unwrap(),
			StakingLedgerInspect {
				stash: 11,
				total: 1000,
				active: 1000,
				unlocking: Default::default(),
			}
		);

		// reward era 1 and payout at era 2
		Eras::<T>::reward_active_era(vec![(11, 1)]);
		Session::roll_until_active_era(2);
		let _ = staking_events_since_last_call();

		mock::make_all_reward_payment(1);
		assert_eq!(ClaimedRewards::<T>::get(1, &11), vec![0]);

		assert_eq!(
			staking_events_since_last_call(),
			vec![
				Event::PayoutStarted { era_index: 1, validator_stash: 11, page: 0, next: None },
				Event::Rewarded { stash: 11, dest: RewardDestination::Account(7), amount: 7500 }
			]
		);

		// balance and ledger the same, 7 is unded
		assert_eq!(asset::total_balance::<T>(&11), 1001);
		assert_eq!(
			Staking::ledger(11.into()).unwrap(),
			StakingLedgerInspect {
				stash: 11,
				total: 1000,
				active: 1000,
				unlocking: Default::default(),
			}
		);
		assert_eq!(asset::total_balance::<T>(&7), 7500);
	});
}

#[test]
fn restricted_accounts_can_only_withdraw() {
	ExtBuilder::default().build_and_execute(|| {
		start_active_era(1);
		// alice is a non blacklisted account.
		let alice = 301;
		let _ = Balances::make_free_balance_be(&alice, 500);
		// alice can bond
		assert_ok!(Staking::bond(RuntimeOrigin::signed(alice), 100, RewardDestination::Staked));
		// and bob is a blacklisted account
		let bob = 302;
		let _ = Balances::make_free_balance_be(&bob, 500);
		restrict(&bob);

		// Bob cannot bond
		assert_noop!(
			Staking::bond(RuntimeOrigin::signed(bob), 100, RewardDestination::Staked,),
			Error::<Test>::Restricted
		);

		// alice is blacklisted now and cannot bond anymore
		restrict(&alice);
		assert_noop!(
			Staking::bond_extra(RuntimeOrigin::signed(alice), 100),
			Error::<Test>::Restricted
		);
