### Title
Unbounded ZIP64 extra-field parsing loop in `InputZipFile::ProcessCentralDirEntry` allows out-of-bounds read past the central directory buffer - (File: third_party/ijar/zip.cc)

### Summary
`ijar` is Bazel's interface-jar generator. It memory-maps an input `.jar`/`.zip` and walks its central directory via `InputZipFile::ProcessCentralDirEntry` to compute per-entry sizes and Zip64 fields. The jar being parsed can be a file that a build fetches from an untrusted source (e.g. a `.jar` obtained through `http_jar`/`http_archive`/a module registry archive) and then processes with `ijar` as part of normal Java toolchain interface-jar creation, so its bytes are attacker-controlled content that the victim's build consumes.

### Finding Description
`FindZipCentralDirectory` (third_party/ijar/zip.cc:704-778) validates only that `cd.central_dir_offset + cd.central_dir_size <= in_length` before handing off `central_dir` as the start pointer for per-entry parsing [1](#0-0) . Individual central directory entries are then parsed by `ProcessCentralDirEntry`, which reads a 16-bit `extra_field_length` from attacker-controlled bytes and walks the extra-field records with:
```
const u1 *extra_p = p;
p += extra_field_length;
while (extra_p != p) {
    const u2 header_id = get_u2le(extra_p);
    const u2 data_size = get_u2le(extra_p);
    const u1 *extra = extra_p;
    extra_p += data_size;
    ...
}
``` [2](#0-1) 

There is no check that `data_size` values sum exactly to `extra_field_length`, nor any check that `extra_p` stays within the mapped central-directory/file bounds. Unlike `InputZipFile::ProcessLocalFileEntry`, which guards every read with `EnsureRemaining()` against `input_file_->Length()` [3](#0-2) , `ProcessCentralDirEntry` performs no equivalent bounds check on any of its fields (compressed/uncompressed size, filename, extra field, comment length) before advancing `p`/`extra_p` and dereferencing them via `get_u2le`/`get_u4le`/`get_u8le`. A crafted central directory record with a `data_size` field that does not align with `extra_field_length` causes the `while (extra_p != p)` loop to either terminate late (reading and dereferencing memory beyond the intended extra-field slice) or never satisfy `extra_p == p` if it overshoots, walking `extra_p` arbitrarily far past the end of the mapped file while repeatedly calling `get_u2le`/`get_u8le` on unmapped memory.

This mirrors the class of bug in the referenced Chromium/PDFium CVE-2019-5855: attacker-supplied, length-prefixed structured data (there: a PDF; here: a ZIP central directory's Zip64 extra field) drives pointer/size arithmetic without full bounds validation, in a code path that is trusted to be internally consistent, leading to reads (and, since `*uncompressed_size`/`*compressed_size`/`*offset` values populated from these fields propagate into later size computations used for buffer sizing and memory copies in `ProcessFile`/`CalculateOutputLength`) potential corruption of the derived size accounting.

### Impact Explanation
A malicious `.jar` fetched as a build dependency (e.g. a Maven jar behind `http_jar`, or a vendored archive) that is subsequently run through `ijar` to generate an interface jar can trigger out-of-bounds reads of process memory adjacent to the mmap'd input file. Because the resulting (possibly corrupted) `compressed_size`/`uncompressed_size` values feed size accounting elsewhere in the ijar pipeline, this can also produce inconsistent buffer-length assumptions in the downstream extraction logic, which is the same "size fields silently drive unchecked memory operations" shape as the PDFium integer-overflow bug class.

### Likelihood Explanation
This requires no special privilege: any party who can get a crafted `.jar`/`.zip` file into the build (a dependency archive, a mirrored jar, or a file on an untrusted CI branch) can trigger the code path, since `ijar` runs as an unconditional step of Java compilation/interface-jar generation with no external checksum gating the *content structure* of the archive (only the whole-file hash, if declared, is checked before `ijar` ever parses it — an attacker who controls the origin server for an undeclared/omitted checksum, or exploits the window before checksum pinning, can still reach this parser).

### Recommendation
Add explicit bounds checks in `ProcessCentralDirEntry`'s extra-field loop (and generally for every field read in that function) to ensure `extra_p + 4 <= p` before reading `header_id`/`data_size`, that `extra_p + data_size <= p`, and that all central-directory field reads stay within `[central_dir_, central_dir_ + central_dir_size]` and within the overall mapped file bounds — mirroring the `EnsureRemaining()` guard already used in `ProcessLocalFileEntry`.

### Proof of Concept
A `src/test/shell/bazel` or standalone `ijar` unit test can construct a minimal ZIP whose central directory entry declares `extra_field_length = 4` but embeds a Zip64 extra-field record with `header_id = 0x0001` and `data_size = 0xFFFF` (i.e., far larger than the declared `extra_field_length`), so that `extra_p` never equals `p` and the loop walks past the mapped central directory buffer, which under ASan/valgrind should manifest as a heap-buffer-overflow read when running `ijar` against the crafted archive.
