Audit Report

## Title
ERC20 XCM Asset Transactor credits the nominal transfer amount instead of the actual ERC20 balance delta, permanently locking funds for fee-on-transfer/deflationary tokens - (File: `cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs`)

## Summary
`ERC20Transactor::withdraw_asset_with_surplus` and `deposit_asset_with_surplus` call the ERC20 contract's `transfer()` and, on a `true` return without revert, unconditionally credit/debit the nominal `amount` taken from the XCM `Asset` into `AssetsInHolding`/`Erc20Credit`, never verifying the real balance delta via `balanceOf`. Any unprivileged user can deploy an arbitrary fee-on-transfer/deflationary ERC20 contract through `pallet_revive` and reference it via an `AccountKey20` junction, since `ERC20Matcher`/`IsLocalAccountKey20` accept any such location without a registry or allow-list.

## Finding Description
`withdraw_asset_with_surplus` transfers `amount` to the checking address and, if `transferCall` returns `true` without reverting, records `AssetsInHolding::new_from_fungible_credit(what.id.clone(), Box::new(Erc20Credit(amount)))` using the nominal `amount`, not an observed balance change. [1](#0-0) 

`Erc20Credit` is a bare accounting wrapper holding a `u128` with no link to actual contract state. [2](#0-1) 

Symmetrically, `deposit_asset_with_surplus` transfers `amount` from the checking account to the beneficiary and treats a `true` return as full success. [3](#0-2) 

The `ERC20Matcher` used by this transactor on Asset Hub Westend matches any local `AccountKey20` location without any registry check — `IsLocalAccountKey20::contains` only checks the junction shape, not the contract's legitimacy. [4](#0-3)  The transactor is wired into `AssetTransactors` on Asset Hub Westend. [5](#0-4) 

The existing runtime test confirms the permissionless deploy-then-use flow: an ordinary account (`ALICE`) calls `bare_instantiate` to deploy `MyToken` and immediately uses its address as an `AccountKey20` asset id in a self-submitted `PolkadotXcm::execute` withdraw/deposit program — no allow-listing step exists. [6](#0-5) 

For a fee-on-transfer token, `transferCall` would move less than `amount` while still returning `true`. `withdraw_asset_with_surplus`'s only checks are `did_revert()` and the decoded boolean return value — neither detects a real-vs-nominal amount mismatch — so `Erc20Credit(amount)` is recorded even though the checking account's actual token balance increased by less than `amount`. A subsequent `deposit_asset_with_surplus` for the full recorded `amount` will then either fail (checking account short of `amount`) or, if residual balance from unrelated deposits exists, pay out of other users' funds.

## Impact Explanation
This matches the "permanent user-fund or bridge-state lock" / "public underpriced work" impact category: an unprivileged user can create an accounting divergence between the runtime's internal `AssetsInHolding`/`Erc20Credit` ledger and the real ERC20 balance custodied by `TransfersCheckingAccount`, leading to value being stranded in the checking account when the excess credited amount cannot be actually transferred out, or to a mismatch that lets downstream XCM legs assume unbacked value.

## Likelihood Explanation
High feasibility: deploying a contract via `pallet_revive` and submitting a self-authored XCM program via `pallet_xcm::execute` requires no special privilege, governance action, or validator/relayer collusion — exactly the flow already exercised (with a normal, non-fee token) in the existing `withdraw_and_deposit_erc20s` test. [7](#0-6) 

## Recommendation
In both `withdraw_asset_with_surplus` and `deposit_asset_with_surplus`, query `balanceOf` for the relevant account before and after the `transferCall`, and use the measured delta — not the nominal `amount` — when constructing/consuming `Erc20Credit`. If the observed delta is less than the requested `amount`, fail the operation with `XcmError::FailedToTransactAsset` rather than crediting a fictitious amount, so the internal ledger can never diverge from real contract balances.

## Proof of Concept
1. Deploy a fee-on-transfer/deflationary ERC20 contract via `pallet_revive::Pallet::bare_instantiate`, following the same pattern as `withdraw_and_deposit_erc20s`. [8](#0-7) 
2. Submit `PolkadotXcm::execute` with a `WithdrawAsset`/`DepositAsset` program referencing the contract via `AccountKey20`, mirroring lines 1901-1916 of the same test. [9](#0-8) 
3. Observe `withdraw_asset_with_surplus` records `Erc20Credit(amount)` for the full nominal amount despite the checking account's real ERC20 balance increasing by less. [10](#0-9) 
4. Trigger the subsequent `deposit_asset_with_surplus` for the full `amount` and observe it either fails outright or pays out of unrelated funds in the checking account. [11](#0-10)

		// Fund all accounts involved.
