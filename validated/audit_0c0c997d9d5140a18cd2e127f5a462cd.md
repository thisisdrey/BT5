### Title
Bancor-style exchange pool withdrawals (`ExchangeWithdrawActuator`) compute counter-token payout from live pool reserves with no caller-supplied minimum-output/slippage protection, enabling sandwich attacks - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
`ExchangeWithdrawContract` (used to remove liquidity from a TRX/TRC10 Bancor-style exchange pool) carries no minimum-expected-output field. The `ExchangeWithdrawActuator` computes the counter-token amount the withdrawer receives purely from the exchange's current on-chain reserves at execution time, with no way for the caller to bound the output, exactly analogous to the reported `AuraSpell.closePositionFarm` issue where `minAmountsOut` are hardcoded to zero and users are forced to accept whatever price the pool has at execution time.

### Finding Description
`ExchangeWithdrawContract` only carries `owner_address`, `exchange_id`, `token_id`, and `quant` [1](#0-0) . In contrast, the sibling `ExchangeTransactionContract` (used for trading against the pool) explicitly carries an `expected` field for slippage protection, and its actuator validates `anotherTokenQuant < tokenExpected` before executing [2](#0-1) [3](#0-2) .

`ExchangeWithdrawActuator.execute` computes `anotherTokenQuant` (the amount of the second/counter token returned to the withdrawer) as a live pro-rata function of the current pool reserves (`firstTokenBalance`/`secondTokenBalance`) and the withdrawn `tokenQuant`, using `BigInteger` multiplication/division against whatever the pool balances are at execution time [4](#0-3) . The validation path (`doValidate`) only checks that the derived amount is non-zero, that exchange balances are sufficient, and a "precision" bound (a rounding-consistency check, not an economic slippage bound) — there is no comparison against any caller-supplied minimum-expected value because the protocol contract has no such field to supply one [5](#0-4) .

Because pool reserves (`first/second_token_balance`) can be moved between the time a withdrawal transaction is broadcast and the time it is packed into a block by any account issuing `ExchangeTransactionContract` trades against the same `exchange_id` (an operation any unprivileged account can broadcast), a withdrawer has no on-chain mechanism to guarantee a minimum counter-token amount, unlike traders using `ExchangeTransactionContract`.

### Impact Explanation
A block producer or any actor who can order transactions within a block (or simply race ahead of a pending withdrawal in the mempool) can execute `ExchangeTransactionContract` trades immediately before a victim's `ExchangeWithdrawContract` transaction to move the pool's price ratio unfavorably, then trade back after, extracting value from the withdrawer — a classic sandwich attack. The withdrawer receives a materially reduced amount of the counter token with no recourse, resulting in a realized value loss for the account performing the withdrawal.

### Likelihood Explanation
Any account holding a first- or second-token balance in a live exchange pool can be targeted whenever they submit a withdrawal; the attack only requires the ability to submit ordinary `ExchangeTransactionContract` transactions before and after the victim's transaction, which is available to any unprivileged transaction broadcaster. This is a straightforward and repeatable MEV-style attack against a public, permissionless exchange pool primitive.

### Recommendation
Add an `expected`/minimum-output field to `ExchangeWithdrawContract` (mirroring `ExchangeTransactionContract.expected`) and enforce it in `ExchangeWithdrawActuator.doValidate`, rejecting the withdrawal if the computed `anotherTokenQuant` (and/or the withdrawn `tokenQuant` itself, if partial) falls below the caller-supplied minimum.

### Proof of Concept
1. Attacker observes a pending `ExchangeWithdrawContract` transaction from victim for `exchange_id=E`, `token_id=first`, `quant=Q` in the mempool.
2. Attacker submits an `ExchangeTransactionContract` trade against exchange `E` that shifts `firstTokenBalance`/`secondTokenBalance` unfavorably for the withdrawer, and gets it ordered/mined before the victim's transaction.
3. Victim's `ExchangeWithdrawActuator.execute` runs against the now-skewed reserves, computing a reduced `anotherTokenQuant` via the pro-rata formula at lines 74-89 of `ExchangeWithdrawActuator.java`; since no minimum-output check exists, the withdrawal succeeds at the worse rate.
4. Attacker submits a reverse `ExchangeTransactionContract` trade to restore the pool and capture the spread, profiting at the victim's expense.
