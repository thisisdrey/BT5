### Title
Unbounded array allocation from attacker-controlled length in `ValidateMultiSign.execute()` can crash the node with an uncaught `OutOfMemoryError` - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The KissFFT CVE is an integer-overflow-driven undersized allocation leading to heap corruption. The closest reachable analog in java-tron is not a heap-overflow write, but an unchecked, attacker-controlled allocation size in the `ValidateMultiSign` precompiled contract, reachable from any contract call. `extractBytesArray()`/`extractSigArray()` derive an array length directly from calldata (`words[...].intValueSafe()`) and allocate `new byte[len][]` before any upper bound is enforced when `VMConfig.allowTvmSelfdestructRestriction()` is not active, and the allocation call site is outside any try/catch in `ValidateMultiSign.execute()`.

### Finding Description
`ValidateMultiSign.execute()` reads the signature-array length straight from calldata and, only when the `allowTvmSelfdestructRestriction` hard fork flag is active, checks it against `MAX_SIZE` (5) before extraction: [1](#0-0) 

When that flag is not active, `extractBytesArray` is invoked directly on the unchecked, attacker-supplied length taken from calldata: [2](#0-1) 

`len` comes from `words[offset].intValueSafe()`, which clamps out-of-range values to `Integer.MAX_VALUE` rather than throwing: [3](#0-2) 

`new byte[len][]` with `len` near `Integer.MAX_VALUE` triggers an immediate `OutOfMemoryError` ("Requested array size exceeds VM limit") from the JVM. Critically, this allocation happens in `ValidateMultiSign.execute()` *before* the surrounding `try`/`catch(Throwable t)` block that only wraps the later signature-verification loop: [4](#0-3) 

so the error is not caught by that precompile at all. By contrast, `BatchValidateSign.execute()` wraps its entire `doExecute()` call in `try { ... } catch (Throwable t) { ... }`, which would catch the same class of error: [5](#0-4) 

`ValidateMultiSign` has no equivalent top-level guard.

### Impact Explanation
If the `OutOfMemoryError` thrown by the array allocation is not caught anywhere further up the call chain (in `Program.callToPrecompiledAddress` / the TVM interpreter loop / transaction execution), it can propagate out of transaction processing on a single signed transaction, potentially terminating the executing thread or destabilizing node state during block application — a node crash/DoS condition, which the rules accept as in-scope impact. This is reachable by any account able to deploy a contract calling the `validatemultisign` precompile (address `0x...a`) with crafted calldata, i.e., an unprivileged contract deployer/caller.

### Likelihood Explanation
Exploitability depends on (a) `VMConfig.allowTvmSelfdestructRestriction()` being inactive for the relevant hard fork state, and (b) whether an outer catch in `Program`/`Runtime` around precompile execution actually intercepts `Throwable`/`Error` for this call path — this could not be fully verified within the available tool budget (the `Program.callToPrecompiledAddress` call site and its exception handling were located but not fully inspected due to running out of iterations). Given TIP-854 test coverage (`ValidateMultiSignContractTest`, `BatchValidateSignContractTest`) shows the project has already been actively hardening exactly this class of malformed-calldata issue (ABI-shape validation, `MAX_SIZE` bounds, outer-frame containment tests), it is plausible this specific gap is already mitigated for currently active networks/config flags, but the asymmetry between `ValidateMultiSign` (no top-level catch) and `BatchValidateSign` (has a top-level `catch (Throwable t)`) is a real, verifiable code difference in this snapshot.

### Recommendation
- Enforce the `MAX_SIZE` bound check (and use `min(len, calldata-implied-max)` sizing) unconditionally in `extractBytesArray`/`extractSigArray`/`extractBytes32Array`, not gated behind `allowTvmSelfdestructRestriction()`.
- Wrap the entirety of `ValidateMultiSign.execute()` — including the array-extraction calls — in a `try { ... } catch (Throwable t) { ... }` matching the pattern already used in `BatchValidateSign.execute()`, so a hostile length value degrades to `Pair.of(true, DATA_FALSE)` rather than an uncaught `Error`.
- Validate `len` against a sane upper bound derived from `rawData.length` before allocating any array proportional to it.

### Proof of Concept
Craft calldata for `validatemultisign(address,uint256,bytes32,bytes[])` where the offset word for the `bytes[]` array is valid but the length word at that offset is set to a very large value (e.g., `0xffffffff` truncated/clamped by `intValueSafe()` to `Integer.MAX_VALUE`, or any value large enough that `new byte[len][]` exceeds the JVM's max array allocation) while `VMConfig.allowTvmSelfdestructRestriction()` is disabled. Invoking this precompile via a `CALL` from a deployed contract routes into `ValidateMultiSign.execute()`, hits `extractBytesArray`, and throws `OutOfMemoryError` outside any local `catch`.

**Uncertainty note:** I could not confirm within the available search budget whether an outer catch in `Program.callToPrecompiledAddress` (in `actuator/src/main/java/org/tron/core/vm/program/Program.java`) intercepts `Throwable`/`Error` for precompile calls generally, which would determine whether this actually escapes to crash the node or is safely contained. This should be verified directly in that file before treating the impact as confirmed rather than potential.
