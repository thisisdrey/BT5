### Title
Non-unique TRC10 asset naming under `AllowSameTokenName` lets any account mask/impersonate an existing token by name - ([File: actuator/src/main/java/org/tron/core/actuator/AssetIssueActuator.java])

### Summary
When the `ALLOW_SAME_TOKEN_NAME` dynamic parameter is enabled (`getAllowSameTokenName() != 0`), `AssetIssueActuator.validate()` skips the uniqueness check on the human-readable asset `name` field entirely. The `"Token exists"` check is only performed when `dynamicStore.getAllowSameTokenName() == 0`: [1](#0-0) 
Any unprivileged account can therefore issue a brand-new TRC10 token whose `name` field is byte-for-byte identical to an already-existing, legitimate token (e.g. one issued earlier by a well-known entity), because the only per-name storage that enforces uniqueness (`assetIssueStore`, the V1 store keyed by name) is bypassed and only the V2 store, keyed by numeric token ID, is written: [2](#0-1) 

### Finding Description
This is the direct java-tron analog of the Nextcloud report: an unprivileged user can create a resource (external storage folder there, a TRC10 token here) using the exact same name as one already owned/shared by another party, and that name collision is used by downstream lookup-by-name code paths, masking/shadowing the legitimate resource for anyone who queries by name.

- `AssetIssueActuator.validate()` only rejects duplicate names in "SameTokenName closed" mode (`getAllowSameTokenName() == 0`). Once the network parameter is open (which is the intended, forward-compatible mode of TRON since assets are keyed by numeric ID in V2), name uniqueness is not enforced at all at the protocol layer.
- `Wallet.getAssetIssueByName()` still performs a name-based lookup across the V2 store and explicitly anticipates multiple matches, throwing `NonUniqueObjectException` only when it detects more than one asset sharing the name: [3](#0-2) 
This proves that the runtime data model allows and even handles (rather than rejects at creation time) multiple TRC10 tokens with an identical `name`.
- `ParticipateAssetIssueActuator` and other actuators resolve which store to search by name/ID via `Commons.getAssetIssueStoreFinal()`, which simply switches between the ID-keyed V2 store or name-keyed V1 store depending on the flag: [4](#0-3) [5](#0-4) 
Any client, wallet, exchange, or contract-calling API path that still resolves TRC10 assets by human-readable name (as opposed to numeric ID) after `ALLOW_SAME_TOKEN_NAME` is enabled is thus exposed to a name-collision/spoofing condition it cannot distinguish from the legitimate token, exactly mirroring the Nextcloud "localstrg" collision — an attacker names their own asset identically to the target's asset to intercept operations aimed "at that name."

### Impact Explanation
The root cause is purely a broadcastable-transaction condition: it only requires a single `AssetIssueContract` transaction from any funded account (asset-issue fee only) to create a colliding name. Consumers of `GetAssetIssueByName` (HTTP/gRPC/JSON endpoints such as `GetAssetIssueByNameServlet`, `RpcApiService`) and any actuator/off-chain integration that resolves an asset by `name` rather than by the unique numeric `id` can be misdirected toward the attacker-issued token. This can result in a user or automated integrator sending value/interacting with (or believing they are interacting with) the wrong token contract, which is a concrete account/asset-confusion vector with monetary consequences, matching the "unauthorized account operation" bar in the validation rules.

### Likelihood Explanation
Likelihood is high for exploitation feasibility (any account can issue an asset for the standard asset-issue fee, no special privilege needed, and there is no check preventing name reuse when `ALLOW_SAME_TOKEN_NAME=1`), though the assets that actually key on `name` (rather than the immutable numeric `id`) are limited to legacy/compat callers of `getAssetIssueByName` and any external system that still resolves tokens by name string instead of ID.

### Recommendation
Enforce global uniqueness of the `name` field for `AssetIssueContract` regardless of the `ALLOW_SAME_TOKEN_NAME` setting (e.g., maintain a name→id reverse index in the V2 path and reject creation if a live, non-expired asset already holds that name), or clearly deprecate/reject all by-name asset resolution APIs (`GetAssetIssueByName` and equivalents) once `ALLOW_SAME_TOKEN_NAME` is active, forcing all callers onto the unique numeric `id`.

### Proof of Concept
1. Ensure `ALLOW_SAME_TOKEN_NAME` is enabled on the target network (`dynamicStore.getAllowSameTokenName() == 1`, the modern default state).
2. Victim/legitimate issuer broadcasts `AssetIssueContract` with `name = "PopularToken"`, receiving token id `N`.
3. Attacker (any funded account) broadcasts a second `AssetIssueContract` with the identical `name = "PopularToken"`; `AssetIssueActuator.validate()` at [1](#0-0)  does not reject it because the `getAllowSameTokenName() == 0` guard is false, and the transaction succeeds, creating token id `M`.
4. Any caller that queries `GetAssetIssueByName("PopularToken")` via `Wallet.getAssetIssueByName` now observes two colliding assets sharing the same name (confirmed by the multi-match handling logic at [3](#0-2) ), and any legacy/off-chain component that keys off `name` instead of `id` can resolve to the attacker's token `M` instead of the legitimate token `N`.
