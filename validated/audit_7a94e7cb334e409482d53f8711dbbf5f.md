### Title
`MarketSellAssetActuator::matchSingleOrder` "taker == maker" branch omits zero-result check on `makerBuyTokenQuantityReceive`, allowing a taker to drain a maker's sell-side balance for free - (File: actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java)

### Summary
`MarketSellAssetActuator::matchSingleOrder` computes exchanged token quantities using integer division via `MarketUtils.multiplyAndDivide`, which can floor to `0` when the numerator is smaller than the denominator. Two of the three branches explicitly guard against this rounding-to-zero condition, but the "taker == maker" branch does not, letting a taker consume the maker's entire remaining sell-side asset while the maker receives `0` tokens in return — a direct on-chain analog of the reported `TokenSaleProposalBuy` decimal-rounding free-token bug.

### Finding Description
In `matchSingleOrder`, when a taker's remaining buy-side demand exactly equals the maker's remaining sell-side supply, the code takes the "taker == maker" branch: [1](#0-0) 

Here `makerBuyTokenQuantityReceive` is computed via `MarketUtils.multiplyAndDivide(makerSellRemainQuantity, makerBuyQuantity, makerSellQuantity, ...)`, which performs `floorDiv(multiplyExact(a,b), c)` and can legitimately return `0` when `makerSellRemainQuantity * makerBuyQuantity < makerSellQuantity`: [2](#0-1) 

Unlike this branch, the other two branches in the same method explicitly guard against a `0` result of the identical `multiplyAndDivide` computation:
- The very first computed quantity, `takerBuyTokenQuantityRemain`, is checked for `== 0` and safely returned/refunded if so: [3](#0-2) 
- The "taker > maker" branch explicitly checks `makerBuyTokenQuantityReceive == 0` before proceeding, refunding the maker's remaining sell tokens instead of consuming them: [4](#0-3) 

The "taker == maker" branch has no equivalent guard. When it hits, `takerBuyTokenQuantityReceive` is set to the maker's full remaining sell quantity (`makerOrderCapsule.getSellTokenQuantityRemain()`, guaranteed non-zero since it equals the also-nonzero `takerBuyTokenQuantityRemain`), while `makerOrderCapsule.setSellTokenQuantityRemain(0)` fully closes out the maker's order and marks it `INACTIVE`. Both `addTrxOrToken` calls then execute unconditionally: [5](#0-4) 

The taker's account is credited with the maker's full remaining sell-side asset amount, while the maker's account is credited with `0` of the corresponding buy-side asset — the maker's sell-side asset is consumed to zero balance with no compensation.

### Impact Explanation
This is a direct, permanent loss-of-funds bug reachable by any account that can place a `MarketSellAssetContract` transaction (an ordinary signed transaction, no special privilege required). A taker can craft or wait for a matching scenario where the maker's remaining sell quantity is small relative to the maker's original price ratio (i.e., `makerSellRemainQuantity * makerBuyQuantity < makerSellQuantity`), causing the "taker == maker" equality branch to fire with `makerBuyTokenQuantityReceive == 0`. The taker receives the maker's entire remaining sell-token balance for free, while the maker's order is closed with zero payment received — an unbacked balance transfer / theft of funds from the maker.

### Likelihood Explanation
The bug-class root cause (unchecked integer division that floors to zero) is proven to exist in this exact function via two sibling branches that were patched with explicit `== 0` checks, showing the authors were aware of and mitigated the issue elsewhere but missed the third, symmetric branch. Triggering the condition only requires ordinary, unprivileged `MarketSellAssetContract` transactions to build up an order book state where a maker's remaining quantity becomes small enough that the division rounds to zero exactly when the taker's remaining demand matches it — fully achievable by a single actor controlling both the maker order (partially filled over several trades) and the final matching taker order, or simply by monitoring the order book for such states.

### Recommendation
Add the same zero-result guard used in the sibling branches to the "taker == maker" branch: after computing `makerBuyTokenQuantityReceive` via `MarketUtils.multiplyAndDivide`, check `if (makerBuyTokenQuantityReceive == 0)` and handle it identically to the "taker > maker" branch — return the maker's remaining sell-token quantity to the maker instead of zeroing it out and crediting the taker unconditionally. More broadly, audit all uses of `MarketUtils.multiplyAndDivide` and any other floor-division/decimal-normalization logic (e.g., `ExchangeProcessor`, `ParticipateAssetIssueActuator`, `ExchangeInjectActuator`/`ExchangeWithdrawActuator` validate/execute pairs) to ensure execute()-side computations cannot silently produce a zero transfer that still fully debits the counterparty.

### Proof of Concept
1. Maker places a sell order: sell token A quantity = `makerSellQuantity` (e.g. 1,000,000), buy token B quantity = `makerBuyQuantity` (e.g. 1), i.e., an extreme price ratio.
2. The maker order is partially filled over one or more prior matches until `makerOrderCapsule.getSellTokenQuantityRemain()` becomes very small, e.g. `1` (while `makerSellQuantity`/`makerBuyQuantity` on the order remain at the original 1,000,000/1 ratio used for the price calc in `multiplyAndDivide`).
3. A taker places a `MarketSellAssetContract` selling token B for token A such that, after routing through `matchOrder`, `takerBuyTokenQuantityRemain` computed in `matchSingleOrder` equals `makerOrderCapsule.getSellTokenQuantityRemain()` (i.e., `1`), triggering the "taker == maker" branch at [6](#0-5) .
4. `makerBuyTokenQuantityReceive = multiplyAndDivide(1, 1, 1_000_000) = floorDiv(1, 1_000_000) = 0`.
5. `takerBuyTokenQuantityReceive` is set to `1` (the maker's full remaining sell quantity), the maker's order is fully closed (`setSellTokenQuantityRemain(0)`, state `INACTIVE`), and `addTrxOrToken` credits the taker with `1` unit of token A while crediting the maker with `0` units of token B — the maker's final unit of token A is lost with no compensation.

  public static long multiplyAndDivide(long a, long b, long c, boolean disableMath) {
    try {
      long tmp = multiplyExact(a, b, disableMath);
      return floorDiv(tmp, c, disableMath);
    } catch (ArithmeticException ex) {
      // do nothing here, because we will use BigInteger to compute again
    }

    BigInteger aBig = BigInteger.valueOf(a);
    BigInteger bBig = BigInteger.valueOf(b);
    BigInteger cBig = BigInteger.valueOf(c);

    return aBig.multiply(bBig).divide(cBig).longValue();
  }
