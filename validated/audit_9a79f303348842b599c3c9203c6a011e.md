### Title
Inconsistent SSRF-like authorization: `TransferAssetActuator` skips the version-1 (EVM-compatible) smart-contract transfer guard enforced by `TransferActuator`, permanently locking TRC-10 tokens - ([File: actuator/src/main/java/org/tron/core/actuator/TransferAssetActuator.java])

### Summary
`TransferActuator` (the actuator behind the `TransferContract`, i.e. plain TRX transfers) enforces two sequential authorization checks before crediting a smart-contract account: (1) the `ForbidTransferToContract` policy, and (2) — once `AllowTvmCompatibleEvm` is enabled — a check that blocks direct balance transfers to any contract whose `ContractCapsule.getContractVersion() == 1` (an EVM-compatible contract), explicitly forcing callers to use `TriggerSmartContract` instead so the contract's code actually executes on receipt of value.

`TransferAssetActuator` (the sibling actuator behind `TransferAssetContract`, i.e. TRC-10 asset transfers) enforces only the first check (`ForbidTransferToContract`) and never re-implements the second, version-1 guard. An unprivileged account can therefore broadcast a `TransferAssetContract` transaction that deposits TRC-10 token balance directly into an EVM-compatible contract's asset map, completely bypassing the code path (`TriggerSmartContract`/VM execution) that the contract relies on to become aware of and account for the incoming value.

### Finding Description
Both actuators mutate account state that a smart contract owns, and both are guarded by the same central policy intent — "an actuator-only transfer that does not invoke contract code must not be allowed to credit an EVM-compatible (`version == 1`) contract account; the caller must instead go through `TriggerSmartContract` so the contract's fallback/receive logic executes."

`TransferActuator.validate()` implements this policy fully: [1](#0-0) 

`TransferAssetActuator.validate()` implements only the `ForbidTransferToContract` half of the same policy and has no equivalent check against `contractCapsule.getContractVersion() == 1`: [2](#0-1) 

This exactly mirrors the reported bug class: a central authorization/guard policy ("do not let this class of value-transfer bypass contract code execution for version-1 contracts") is enforced on one code path (`TransferActuator`/TRX) but a structurally similar sibling code path (`TransferAssetActuator`/TRC-10) resolves the target account and mutates its balance directly without consulting the same guard — just as `network_icmp_probe`/`network_traceroute` resolved and probed targets without consulting the SSRF authorization policy that `network_rtt_measure` enforced.

`TransferAssetActuator.execute()` then unconditionally moves the asset balance into the contract's `AssetV2` map: [3](#0-2) 

Because this happens through the plain actuator path (`RuntimeImpl` routes `TransferAssetContract` through the generic `Actuator`/`Actuator2` dispatch, not through `VMActuator`), no VM code of the target contract ever runs: [4](#0-3) 

The `AllowTvmCompatibleEvm` version-1 guard was clearly added as a defense specifically so that value cannot silently land on a contract's balance/asset map outside of the VM call path (the error message explicitly says: "Instead please use TriggerSmartContract"). That defense is bypassed entirely for TRC-10 assets.

### Impact Explanation
TRC-10 tokens sent via `TransferAssetContract` to a `version == 1` (EVM-compatible) contract address are credited into `AccountCapsule`'s asset map without the contract's code ever being invoked. An EVM-compatible contract that tracks token deposits/accounting only through logic triggered during a `TriggerSmartContract` call (e.g., ERC20-style deposit bookkeeping, escrow, DEX pool balances) will never observe this deposit. Since there is no code path within the contract that got a chance to record or react to the transfer, the deposited TRC-10 balance is stranded on the contract's account with no application-level mechanism to withdraw or account for it — a permanent freezing/loss-of-funds condition for the sender, and a state inconsistency between the contract's internal ledger and its actual TRC-10 balance. Any unprivileged asset holder broadcasting a single `TransferAssetContract` transaction can trigger this.

### Likelihood Explanation
Any account holding a TRC-10 asset can construct and broadcast a `TransferAssetContract` transaction to an arbitrary EVM-compatible contract address with no special privilege, signature exception, or committee proposal beyond the already-active `AllowTvmCompatibleEvm` hard fork (which is required for `contractVersion == 1` contracts to exist at all). No race condition or special preconditions are required — the missing check is a straightforward code-path omission that is deterministically reachable on every such transaction.

### Recommendation
Apply the identical `AllowTvmCompatibleEvm` / `ContractCapsule.getContractVersion() == 1` guard used in `TransferActuator.validate()` to `TransferAssetActuator.validate()` (and audit any other actuators that can credit a contract account's balance/asset maps outside the VM call path for the same gap). Reject `TransferAssetContract` transactions whose `toAddress` resolves to a version-1 contract once `AllowTvmCompatibleEvm` is active, directing callers to route token transfers through `TriggerSmartContract` instead, consistent with the TRX transfer policy.

### Proof of Concept
1. Enable `AllowTvmCompatibleEvm` (already active on networks supporting EVM-compatible contracts) and deploy an EVM-compatible contract (`ContractCapsule.getContractVersion() == 1`) that expects TRC-10 deposits to be recorded via a `TriggerSmartContract` call (e.g., a deposit-tracking contract).
2. As an unprivileged account holding the TRC-10 asset, broadcast a `TransferAssetContract` transaction with `toAddress` set to the contract's address and a nonzero `amount`.
3. Observe that `TransferAssetActuator.validate()` only checks `ForbidTransferToContract` — see [5](#0-4) 
— and does not perform the version-1 check present in `TransferActuator.validate()` [6](#0-5) 
so the transaction succeeds and `execute()` credits the contract's `AssetV2` map directly, without any VM execution ever observing the deposit — leaving the tokens permanently unaccounted for and unrecoverable through the contract's normal logic.
