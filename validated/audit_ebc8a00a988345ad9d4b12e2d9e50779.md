### Title
Unbounded Full-List Query Endpoints (`getAssetIssueList`, `getExchangeList`, `getWitnessList`) Enable Node-Level Denial of Service - (File: framework/src/main/java/org/tron/core/Wallet.java)

### Summary
The Palmera finding describes an "unbonded" (unbounded) collection of `orgHash` values that grows as an attacker repeatedly creates organizations, eventually causing functions that iterate the full collection to become a denial-of-service vector. java-tron has a structurally identical pattern: several on-chain registries (`AssetIssueStore`, `ExchangeStore`, `WitnessStore`) are exposed through non-paginated Wallet/RPC methods that materialize the *entire* store into a single in-memory response on every call, with no upper bound on how large that collection can grow.

### Finding Description
`Wallet.getAssetIssueList()` calls `getAllAssetIssues()` and iterates every entry in the store to build a single `AssetIssueList` response: [1](#0-0) 

The backing store performs an unbounded full-table scan with no size limit: [2](#0-1) 

The same unbounded-collection pattern exists for exchanges: [3](#0-2) [4](#0-3) 

...and for witnesses: [5](#0-4) [6](#0-5) 

Each of these `getAllX()` calls has no limit, no offset, and no cap — every asset ever issued, every exchange ever created, and every witness ever registered is loaded into memory and serialized into a single protobuf response, every time the corresponding endpoint is hit. There is no mechanism analogous to `removeOrg` to prune the collection either — assets, exchanges, and witnesses are never removed from these stores once created.

These non-paginated methods are directly reachable by any anonymous HTTP/gRPC client, with no authentication or rate-based cost beyond a normal transaction fee to create the underlying entries:
- `GetAssetIssueListServlet` → `wallet.getAssetIssueList()` [7](#0-6) 
- gRPC `getAssetIssueList` in `RpcApiService`, mirrored on Solidity/PBFT nodes.
- `ListExchangesServlet` → `wallet.getExchangeList()` [8](#0-7) 
- gRPC `listExchanges` [9](#0-8) 
- gRPC `listWitnesses` (`wallet.getWitnessList()`) [10](#0-9) 

Notably, java-tron already recognizes this exact class of bug elsewhere — it added *paginated* variants (`getAssetIssueList(offset, limit)`, `getPaginatedExchangeList`, `getPaginatedNowWitnessList`) specifically to bound query cost, but left the original unbounded methods live and reachable alongside them: [11](#0-10) [12](#0-11) 

### Impact Explanation
An attacker who creates a large number of assets (`AssetIssueContract`), exchanges (`ExchangeCreateContract`), or witnesses causes the size of the underlying store to grow without bound. Because there is no removal path and no cap enforced by these specific query methods, every subsequent call to the unbounded endpoints scans and serializes the whole collection. As the collection grows, CPU time, heap allocation, and network payload size for each request increase linearly (or worse, given `getAssetIssueByName`/`getAssetIssueByAccount` also call `getAllAssetIssues()` and then filter/stream over the full list). This can degrade or stall the servicing thread pool of a full node's HTTP/gRPC interface for all clients — a resource-exhaustion/availability issue on a query path the node must continue to serve, consistent with the "API the node can no longer serve" acceptance criterion.

### Likelihood Explanation
Creating assets, exchanges, and witnesses requires paying the respective on-chain fee (`AssetIssueFee`, `ExchangeCreateFee`, witness creation fee), so this is not a zero-cost attack, but it is a standard, permissionless, unprivileged operation available to any account holder — exactly the "attacker creates lots of orgs" scenario in the original report, just gated by a fixed TRX cost rather than being entirely free. Over time (or with modest capital), an attacker can grow any of these three collections to a size that makes the corresponding non-paginated query meaningfully expensive, while the paginated siblings prove the developers already consider unboundedness here a known risk category.

### Recommendation
Remove or hard-cap the non-paginated `getAssetIssueList()`, `getExchangeList()`, and `getWitnessList()` code paths (and their HTTP/gRPC exposures), forcing all such endpoints to be paginated with an enforced maximum `limit` (as already done for `getAssetIssueList(offset, limit)`, `getPaginatedExchangeList`, and `getPaginatedNowWitnessList`). Where full listings must remain supported for backward compatibility, apply a server-side maximum result size and streaming rather than building the entire response in memory.

### Proof of Concept
1. From an unprivileged account, repeatedly broadcast `AssetIssueContract` (or `ExchangeCreateContract` / `WitnessCreateContract`) transactions, each paying the required fee, to grow `AssetIssueStore` (or `ExchangeStore` / `WitnessStore`) to a large number of entries.
2. Call the unbounded query endpoint, e.g. HTTP `GET /wallet/getassetissuelist` (backed by `GetAssetIssueListServlet` → `Wallet.getAssetIssueList()`), or gRPC `Wallet/GetAssetIssueList`, `Wallet/ListExchanges`, `Wallet/ListWitnesses`.
3. Observe that each call performs a full store scan (`AssetIssueStore.getAllAssetIssues()` / `ExchangeStore.getAllExchanges()` / `WitnessStore.getAllWitnesses()`) and serializes every entry into one response, with latency and memory usage scaling with the attacker-grown collection size, while no pagination or cap is enforced on these specific methods.

  public ExchangeList getPaginatedExchangeList(long offset, long limit) {
    if (limit < 0 || offset < 0) {
      return null;
    }

    long latestExchangeNum = chainBaseManager.getDynamicPropertiesStore()
        .getLatestExchangeNum();
    if (latestExchangeNum <= offset) {
      return null;
    }
    limit =
        limit > EXCHANGE_COUNT_LIMIT_MAX ? EXCHANGE_COUNT_LIMIT_MAX : limit;
    long end = offset + limit;
    end = end > latestExchangeNum ? latestExchangeNum : end;

    ExchangeList.Builder builder = ExchangeList.newBuilder();
    ImmutableList<Long> rangeList = ContiguousSet
        .create(Range.openClosed(offset, end), DiscreteDomain.longs())
        .asList();
    rangeList.stream().map(ExchangeCapsule::calculateDbKey).map(key -> {
      try {
        return getExchangeStoreFinal(chainBaseManager.getDynamicPropertiesStore(),
            chainBaseManager.getExchangeStore(),
            chainBaseManager.getExchangeV2Store()).get(key);
      } catch (Exception ex) {
        return null;
      }
    }).filter(Objects::nonNull)
        .forEach(exchangeCapsule -> builder
            .addExchanges(exchangeCapsule.getInstance()));
    return builder.build();

  }
