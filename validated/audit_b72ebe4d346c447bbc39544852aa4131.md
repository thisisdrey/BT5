## Finding: Unbounded array-length field in precompiled-contract ABI parsing leads to `OutOfMemoryError` (node/thread crash) — `PrecompiledContracts.java`

### Summary
`PrecompiledContracts.extractBytesArray`, `extractBytes32Array`, and `extractSigArray` derive an array length directly from attacker-supplied calldata words via `DataWord.intValueSafe()` and immediately allocate a Java array of that size, with no check that the length is consistent with the actual size of the input data.

### Finding Description
The helper methods used to decode ABI-encoded dynamic arrays passed into precompiled contracts read the length word and allocate an array before validating it against the real payload size: [1](#0-0) [2](#0-1) [3](#0-2) 

`len` comes from `words[offset].intValueSafe()`. `intValueSafe()` does not throw or clamp to a value bounded by the actual input size — it only avoids Java's checked-overflow exceptions, returning up to `Integer.MAX_VALUE` for any value that doesn't fit safely in an int: [4](#0-3) 

Because a caller can freely craft calldata to a precompiled contract (e.g., by invoking a precompile that parses multi-signature/array parameters), `len` can be set to a huge value such as `0x7FFFFFFF`. This directly reaches `new byte[len][]` / `new byte[len][32]` allocations — analogous to the CVE's "crafted size value" being used, without a `mode`/bounds sanity check, to drive a memory-corrupting/invalid operation on the size input. In this Java setting, the analogous consequence is an immediate massive allocation attempt causing `OutOfMemoryError`, which propagates out of the executing thread.

This differs from other similarly-shaped code in the same file, e.g. `VerifyTransferProof.execute`, which explicitly bounds `spendCount`/`receiveCount` to `[1,2]` before allocating (`spendCount < 1 || spendCount > 2 ...`) — a defense that is absent from `extractBytesArray`/`extractSigArray`/`extractBytes32Array`.

### Impact Explanation
An `OutOfMemoryError` thrown while executing a transaction's TVM call into a precompiled contract can crash or destabilize the FullNode/SR-node process (or at minimum abort the executing thread in a way not cleanly handled by the VM's exception model), since `OutOfMemoryError` is an `Error`, not a checked `Exception`, and is not guaranteed to be caught by the same `try/catch(Throwable)`-style guards used elsewhere for validation errors. Any unprivileged account that can construct a transaction invoking the affected precompiled contract can trigger this — this maps to "node crash or halt" under the validation criteria.

### Likelihood Explanation
Reaching this code only requires broadcasting a transaction that calls the specific precompiled contract with a crafted `len` word set to a very large value (e.g., `0xFFFF...FF` or `0x7FFFFFFF`), which any external account or contract can construct. No special privilege, timing, or state is required, making this straightforward for an unprivileged party to attempt.

### Recommendation
Add explicit upper-bound validation on `len` in `extractBytesArray`, `extractBytes32Array`, and `extractSigArray` against the real remaining size of `data`/`words` (similar to the `spendCount`/`receiveCount` bound check in `VerifyTransferProof`) before allocating any array, and reject with a normal validation failure (returning a zero/false result) rather than allowing an unabounded allocation to be attempted.

### Proof of Concept
Conceptually (exact precompile address/selector not confirmed due to indexing limits — see note below):
1. Craft calldata to the precompiled contract that uses `extractBytesArray`/`extractSigArray`, placing at the `offset` word a length value of `0xFFFFFFFF` (or any value causing `intValueSafe()` to return `Integer.MAX_VALUE`).
2. Submit as a `TriggerSmartContract` transaction calling this precompile.
3. Execution reaches `int len = words[offset].intValueSafe(); byte[][] bytesArray = new byte[len][];`, attempting to allocate a huge array, throwing `OutOfMemoryError`.

**Note on verification limits:** I was unable to fully enumerate, within the available search budget, exactly which precompiled contract(s) at which fixed addresses invoke `extractBytesArray`/`extractSigArray`/`extractBytes32Array` (the grep only confirmed 8 usages within `PrecompiledContracts.java` without line-level detail for the call sites). A Devin session with full file access would be needed to pin down the exact reachable precompile address/selector for a concrete end-to-end PoC transaction.
