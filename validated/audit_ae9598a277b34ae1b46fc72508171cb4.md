### Title
Permanent freeze of an ETH-implicit wallet account via out-of-gas panic in a fixed-gas callback while `has_in_flight_tx` is set - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The `WalletContract` (the eth-implicit wallet contract used to let ETH-style accounts issue NEAR actions) guards against concurrent execution with a single boolean flag, `has_in_flight_tx`, that is set to `true` before a cross-contract promise is dispatched and only cleared to `false` inside the corresponding `#[private]` callback. If that callback ever fails to run to completion (e.g. panics from running out of its fixed, hard-coded gas budget) rather than returning normally, the state mutation clearing the flag is rolled back, and `has_in_flight_tx` remains `true` forever with no externally callable reset/rescue path — permanently freezing the wallet.

### Finding Description
`rlp_execute` refuses to start a new transaction whenever `self.has_in_flight_tx` is `true`, returning immediately without touching contract state: [1](#0-0) 

The flag is only cleared inside the private callbacks (`address_check_callback`, `nep_141_storage_balance_callback`, `rlp_execute_callback`), each of which sets `self.has_in_flight_tx = false` as their very first statement: [2](#0-1) [3](#0-2) [4](#0-3) 

These callbacks are executed with small, fixed gas budgets (`RLP_EXECUTE_CALLBACK_GAS`, `ADDRESS_CHECK_CALLBACK_GAS`, `NEP_141_STORAGE_BALANCE_CALLBACK_GAS`, each 5–15 TGas) that also have to cover deserializing an attacker-influenced cross-contract response: [5](#0-4) 

In `nep_141_storage_balance_callback`, the callback deserializes the `storage_balance_of` JSON response coming back from `token_id` — an account chosen by the ETH transaction's `to` field, i.e. effectively an arbitrary/attacker-controlled "ERC-20" NEP-141 contract emulated through this wallet: [6](#0-5) 

If that token contract returns a response engineered to be expensive to parse (e.g. a deeply-nested JSON structure, up to the max cross-contract return-value size), `serde_json::from_slice` can consume gas disproportionate to the payload size. Because the callback's gas is capped (`NEP_141_STORAGE_BALANCE_CALLBACK_GAS.saturating_add(action.gas())`), this can push the callback past its prepaid gas, causing the runtime to abort the receipt with "Exceeded the prepaid gas" (a VM panic), which rolls back all of that receipt's state changes — including the pending `self.has_in_flight_tx = false` write. `has_in_flight_tx` therefore remains `true` on the persisted contract state.

There is no other externally reachable method that can reset `has_in_flight_tx`; every subsequent call to `rlp_execute` (the sole entry point for using the wallet) short-circuits at the top-of-function check and never reaches the code that could clear the flag: [7](#0-6) 

This is directly analogous to the reported `P2pSuperformProxy` bug class: an "emergency"/interrupted intermediate state (`has_in_flight_tx = true`) can be entered and then never exited because a downstream step can fail in a way that prevents the flag-clearing state transition, and — unlike the reported bug's recommendation — there is no rescue/reset mechanism exposed to the account owner or anyone else.

### Impact Explanation
Once `has_in_flight_tx` is stuck `true`, the eth-implicit account can never again submit any NEAR action (transfers, function calls, ERC-20 emulation, etc.) through the wallet contract, since `rlp_execute` is the only entry point and it always short-circuits on this flag. All $NEAR and NEP-141 token balances held by that account become permanently unreachable/unusable through the wallet's intended interface — a permanent freezing of funds for that account, matching the "concrete... permanent freezing of funds" acceptance bar.

### Likelihood Explanation
Triggering the underlying out-of-gas panic requires a user/relayer to route an eth-emulated ERC-20 transfer (`inner_rlp_execute` → `EthEmulationKind::ERC20Transfer`) through a NEP-141 contract that returns an expensive-to-deserialize `storage_balance_of` response. Since the "token" contract targeted by an ETH transaction is derived from the address the wallet owner's Ethereum-style transaction points to, a malicious or compromised token contract (or one deployed by an attacker and pointed at by a phished/tricked signature) can supply such a payload. The fixed, relatively small callback gas budgets make this a narrow but real gas-griefing/DoS surface with no owner-level recovery path once triggered.

### Recommendation
1. Ensure `has_in_flight_tx` cannot get permanently stuck: e.g., budget callback gas generously and independent of untrusted response size, bound/limit the size or complexity of data deserialized from `promise_result` before parsing (reject or truncate abnormally large/deeply nested payloads cheaply), or perform expensive parsing with gas checks that fail gracefully (returning `ExecuteResponse{success:false,...}`) instead of allowing an uncontrolled panic.
2. Add an explicit rescue/reset mechanism (e.g., a privileged or time-locked "force clear `has_in_flight_tx`" method, analogous to the recommended rescue function in the reported bug) so that if the flag ever does get stuck, the account owner or a subsequent transaction can safely recover the wallet's usability without requiring a contract redeploy.

### Proof of Concept
1. Deploy (or have an attacker deploy) a NEP-141-like contract at some account `T` whose `storage_balance_of` method returns a very deeply nested (but size-bounded, e.g. well under 4MB) JSON value crafted to be extremely expensive for `serde_json::from_slice` to parse (a classic "JSON depth bomb").
2. Have the ETH-implicit wallet owner (or an attacker tricking them) sign an RLP ERC-20 transfer transaction whose `to` address resolves to `T`, and submit it via `rlp_execute` with `target = T`.
3. `inner_rlp_execute` sets `has_in_flight_tx = true` and dispatches `storage_balance_of` on `T`, chained to `nep_141_storage_balance_callback` with gas capped at `NEP_141_STORAGE_BALANCE_CALLBACK_GAS.saturating_add(action.gas())` (`runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs:433-457`).
4. When `T`'s crafted response comes back, `nep_141_storage_balance_callback`'s `serde_json::from_slice::<Option<StorageBalance>>` (`lib.rs:211-220`) consumes more gas than the callback's prepaid budget, and the receipt aborts with an out-of-gas panic before `self.has_in_flight_tx = false` is committed.
5. Any further call to `rlp_execute` on this wallet now immediately returns `"Error: transaction already in progress, please try again later."` (`lib.rs:97-105`) forever, with no method available to clear the flag — the wallet and all its held funds are permanently frozen.
