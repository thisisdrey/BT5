### Title
`replace_neighbors` evicts always-allowed neighbors without checking the replaced peer's `allowed` status - ([File: stackslib/src/net/neighbors/db.rs])

### Summary
`PeerDBNeighborWalk::replace_neighbors` only checks whether the *incoming* replacement address is denied via `PeerDB::is_address_denied`, but never checks whether the peer currently occupying the target slot is marked always-allowed (`allowed < 0`, i.e. operator-configured/bootstrap peer). This lets an unprivileged remote peer, after grinding source IPs to land in the same slot bucket as a protected neighbor, overwrite that trusted neighbor's frontier entry via a normal handshake sequence.

### Finding Description
The equality that should hold — "if the peer at the target slot is always-allowed, it must not be evicted" — is never checked. In `replace_neighbors`: [1](#0-0) 

the only guard is:
```rust
let replaced_opt = PeerDB::get_peer_at(&tx, network_id, *slot)?;
if let Some(replaced) = replaced_opt {
    if PeerDB::is_address_denied(&tx, &replacement.addr.addrbytes)? {
        continue;
    }
    ...
    PeerDB::insert_or_replace_peer(&tx, replacement, *slot)?;
```
This checks only whether the *attacker's* address is denied — it never inspects `replaced.allowed` (`Neighbor::is_always_allowed()` exists at `stackslib/src/net/mod.rs:1491-1493` but is unused here). `PeerDB::insert_or_replace_peer` performs an unconditional `INSERT OR REPLACE` into the `frontier` table at the given slot, with no allowed-status re-check inside the DB layer either: [2](#0-1) 

The candidate slot to target is determined by `find_replaced_neighbor_slot`, which computes bucket slots from the *attacker's own* `NeighborKey` via `PeerDB::peer_slots`: [3](#0-2) 

Because slot assignment is a deterministic function of the connecting peer's address/ASN, an attacker can grind source IPs/ports until one hashes into the same slot bucket as a known always-allowed neighbor (bootstrap node or operator-configured peer set via `PeerDB::set_allow_peer` with `allowed = -1`, as done for bootstrap peers in `stacks-node/src/neon_node.rs:4730-4746` and in test harnesses `stackslib/src/net/mod.rs:2961-2973`).

Exploit flow: attacker completes ordinary, unauthenticated handshakes (`Handshake`/`HandshakeAccept`) from disposable source addresses until the frontier is full and `add_or_schedule_replace_neighbor` (`stackslib/src/net/neighbors/db.rs:368-426`) schedules a replacement for the slot occupied by the always-allowed peer. The walk then proceeds through `ping_existing_neighbors_begin`/`Finish` and finally calls `replace_neighbors` (`stackslib/src/net/neighbors/walk.rs:1885-1890`), which overwrites the slot because the attacker's own address is not denied — regardless of the evicted peer's `allowed` flag.

### Impact Explanation
This is an unauthenticated/unauthorized write to node state: a remote, unprivileged peer can cause the victim node to overwrite its PeerDB frontier slot holding a trusted, operator/bootstrap-configured neighbor with the attacker's own neighbor record, dropping that connection (`DropReason::ReplacedConnection`) and removing associated StackerDB contract bindings (`PeerDB::drop_stacker_dbs`, called inside `insert_or_replace_peer` when the peer identity changes). This can degrade the node's connectivity to trusted bootstrap/relay peers and is repeatable across walk cycles, matching the "Critical — unauthenticated/unauthorized write to node state" category.

### Likelihood Explanation
Preconditions are attacker-achievable without privilege or reward-cycle timing: the frontier must be full (bounded and reachable with a modest number of distinct source IPs/ports performing normal handshakes), and the attacker's connecting address must hash (via `PeerDB::peer_slots`) into the same slot bucket as the target always-allowed peer, which requires grinding addresses but no cryptographic secret or admin role. The P2P port is remotely reachable by design, and the whole sequence uses only standard, protocol-legal Handshake/HandshakeAccept messages.

### Recommendation
In `replace_neighbors`, before calling `PeerDB::insert_or_replace_peer`, check `replaced.is_always_allowed()` (or more generally `replaced.is_allowed()`) and skip the replacement if true, just as is already done for `is_address_denied`. Consider also excluding always-allowed peers' slots from `find_replaced_neighbor_slot`'s candidate set so they are never scheduled for replacement in the first place.

### Proof of Concept
Rust test in `stackslib/src/net/neighbors/db.rs` test module:
1. Create an in-memory `PeerDB`, insert an always-allowed neighbor `victim` at a known slot `N` via `PeerDB::insert_or_replace_peer` then `PeerDB::set_allow_peer(..., -1)`.
2. Construct a `NeighborReplacements` and call `replacements.add_neighbor(attacker_naddr, attacker_neighbor, N)` to simulate `add_or_schedule_replace_neighbor` having targeted slot `N`.
3. Call `PeerDBNeighborWalk::default().replace_neighbors(&mut network, &replacements, &mut result)`.
4. Assert: `PeerDB::get_peer_at(tx, network_id, N)` no longer equals `victim` but instead equals `attacker_neighbor`, and `victim.is_always_allowed()` was `true` beforehand — demonstrating the eviction of a protected neighbor with only the "is denied" check having been (falsely) satisfied.

        &self,
        network: &mut PeerNetwork,
        replacements: &NeighborReplacements,
        result: &mut NeighborWalkResult,
    ) -> Result<(), net_error> {
        let network_id = network.bound_neighbor_key().network_id;
        let local_peer_str = format!("{:?}", network.get_local_peer());

        let tx = network.peerdb_tx_begin()?;
        for (replaceable_naddr, slot) in replacements.iter_slots() {
            let replacement = match replacements.get_neighbor(replaceable_naddr) {
                Some(n) => n,
                None => {
                    continue;
                }
            };

            if let Some(replaced) = replaced_opt {

                    key: replaced.addr.clone(),

                });
