### Title
Reward ledger is settled before beneficiary deposit succeeds, allowing relayer rewards to be silently lost to an unroutable/invalid beneficiary Location - ([File: bridges/snowbridge/primitives/core/src/reward.rs])

### Summary
`PayAccountOnLocation::pay_reward` accepts an attacker-controlled `Location` beneficiary and treats successful *delivery* of an `UnpaidExecution` XCM to AssetHub as proof of successful *payment*, even though the actual `DepositAsset` into that beneficiary happens asynchronously and may fail. The calling pallet, `pallet-bridge-relayers`, removes the reward from storage and emits `RewardPaid` as soon as `pay_reward` returns `Ok(())`. This mirrors the reported `LibERC20.mint` bug: value is "minted"/accounted for a beneficiary that is never validated, and if that beneficiary cannot actually receive the funds, the tokens are permanently lost while the internal ledger has already recorded the payout as complete.

### Finding Description
`claim_rewards_to` in `bridges/modules/relayers/src/lib.rs` calls `do_claim_rewards`, which: [1](#0-0) 
removes the relayer's `RelayerRewards` entry via `maybe_reward.take()`, invokes `T::PaymentProcedure::pay_reward(...)`, and — only if `pay_reward` returns `Err` — maps it to `Error::FailedToPayReward` (which rolls back the `try_mutate_exists`). If `pay_reward` returns `Ok(())`, the reward entry stays removed and `Event::RewardPaid` is emitted unconditionally, with no way to know whether the beneficiary actually received the funds.

For the Snowbridge reward kind, `pay_reward` is implemented by `PayAccountOnLocation::pay_reward`: [2](#0-1) 
This builds an XCM containing `ReserveAssetDeposited` (minting the reward asset from the Ethereum reserve) followed by `DepositAsset { assets: AllCounted(1).into(), beneficiary }`, where `beneficiary` is the caller-supplied `Location` from `claim_rewards_to` (routed through `BridgeRewardPayer::pay_reward` in `bridge_common_config.rs`, which only checks that the `VersionedLocation` converts, not that it is a valid, receivable account): [3](#0-2) 
`pay_reward` returns `Ok(())` as soon as `XcmSender::deliver(ticket)` succeeds — i.e., once the message is queued for delivery, not once the funds are actually deposited into `beneficiary` on AssetHub. If `beneficiary` cannot resolve to an account capable of holding the reserve asset on AssetHub (e.g., an unsupported/incomplete junction sequence, a Location for a system/pallet rather than an account, or one lacking the required `AccountId32`/`AccountKey20` junction), `DepositAsset` fails during execution on AssetHub. The freshly reserve-minted asset is then trapped rather than delivered to any account the relayer can control, exactly like minting `LibERC20` tokens to `address(0)`: the supply-affecting step (`ReserveAssetDeposited`) happens, but the destination cannot receive it.

Because `do_claim_rewards` already deleted the `RelayerRewards` entry and emitted `RewardPaid` based only on successful XCM *delivery*, there is no local retry path: the relayer's accounted reward is gone, and recovering trapped assets on AssetHub requires reconstructing the exact origin (`UniversalOrigin(Ethereum) + DescendOrigin(InboundQueueLocation)`) and asset hash via XCM's `ClaimAsset`, which an ordinary relayer cannot practically do.

### Impact Explanation
This falls under "permanent user-fund... lock" and "message queues... must only advance after decode, dispatch, execution, and settlement succeed atomically" from the impact gate: settlement (`RelayerRewards` removal + `RewardPaid`) advances on BridgeHub before the corresponding deposit succeeds on AssetHub. A relayer's legitimately earned reward can be permanently and unrecoverably lost due to a beneficiary value that was never validated for correctness, with the chain's own accounting falsely reporting the reward as paid.

### Likelihood Explanation
`claim_rewards_to` is a public, unprivileged, signed extrinsic — any registered relayer with an accrued reward can supply an arbitrary `BridgeRewardBeneficiaries::AssetHubLocation` value. No governance, admin, or malicious-peer assumption is required; the caller directly controls the `beneficiary` argument that is never validated for account-resolvability before the ledger is settled.

### Recommendation
Before removing the `RelayerRewards` entry and emitting `RewardPaid`, validate that the `beneficiary` `Location` decodes to a well-formed, asset-receivable account (e.g., require a terminal `AccountId32`/`AccountKey20`-style junction, matching what `LocationToAccountId`-style converters expect on AssetHub), analogous to `require(_to != address(0))`. Alternatively, make settlement conditional on execution/delivery confirmation rather than mere XCM send success, so failed deposits can restore the reward to the relayer's claimable balance instead of silently trapping it.

### Proof of Concept
1. A relayer accrues a `BridgeReward::Snowbridge` reward via `register_reward`.
2. The relayer calls `claim_rewards_to(origin, BridgeReward::Snowbridge, BridgeRewardBeneficiaries::AssetHubLocation(VersionedLocation::V5(malformed_location)))` where `malformed_location` is a `Location` that does not resolve to a valid AssetHub account (e.g., missing the `AccountId32` junction, or targeting a non-account interior location).
3. `BridgeRewardPayer::pay_reward` → `PayAccountOnLocation::pay_reward` builds and sends the `UnpaidExecution`/`ReserveAssetDeposited`/`DepositAsset` XCM; `validate_send` and `XcmSender::deliver` succeed because delivery only requires a routable destination (AssetHub), not a resolvable beneficiary within it.
4. `do_claim_rewards` observes `Ok(())`, permanently removes the relayer's `RelayerRewards` entry, and emits `Event::RewardPaid`.
5. On AssetHub, `DepositAsset` fails to credit `malformed_location`; the reserve-minted asset is trapped and effectively lost, while BridgeHub state records the reward as fully paid with no remaining claim for the relayer.

	fn pay_reward(
		relayer: &Relayer,
		_: (),
		reward: RewardBalance,
		beneficiary: Self::Beneficiary,
	) -> Result<(), Self::Error> {
		let ethereum_location = Location::new(2, [GlobalConsensus(EthereumNetwork::get())]);
		let assets: Asset = (ethereum_location.clone(), reward.into()).into();

		let xcm: Xcm<()> = alloc::vec![
			UnpaidExecution { weight_limit: Unlimited, check_origin: None },
			DescendOrigin(InboundQueueLocation::get().into()),
			UniversalOrigin(GlobalConsensus(EthereumNetwork::get())),
			ReserveAssetDeposited(assets.into()),
			DepositAsset { assets: AllCounted(1).into(), beneficiary },
		]
		.into();

		let (ticket, fee) =
			validate_send::<XcmSender>(AssetHubLocation::get(), xcm).map_err(|_| XcmSendFailure)?;
		XcmExecutor::charge_fees(relayer.clone(), fee).map_err(|_| ChargeFeesFailure)?;
		XcmSender::deliver(ticket).map_err(|_| XcmSendFailure)?;

		Ok(())
	}
