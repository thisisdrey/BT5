### Title
Missing account-index baseline in `RewardsDistributor._calculateTokenDelta` lets pre-existing holders steal reward tokens equal to their full balance - (File: contracts/RewardsDistributor.sol)

### Summary
The Munchables H-05 bug class is a **missing state reset in the reward-accounting checkpoint**: a function transitions a position without updating the accrual-related state, breaking reward accounting. In Metronome, the analog lives in `RewardsDistributor._calculateTokenDelta` (`contracts/RewardsDistributor.sol:217-231`). When an account's stored `accountIndexOf` is `0` but the token index equals `INITIAL_INDEX` (i.e. the reward token was just whitelisted and no index growth has occurred yet), the fallback that should normalize the account index to `INITIAL_INDEX` is skipped because the guard uses `>` instead of `>=`. The account then accrues `balanceOf(account) * INITIAL_INDEX`, stealing reward tokens.

### Finding Description
`_calculateTokenDelta` contains this normalization:

```solidity
uint256 _accountIndex = accountIndexOf[token_][account_];

if (_accountIndex == 0 && _tokenIndex > INITIAL_INDEX) {
    _accountIndex = INITIAL_INDEX;
}

uint256 _deltaIndex = _tokenIndex - _accountIndex;
uint256 _tokensDelta = token_.balanceOf(account_).wadMul(_deltaIndex);
``` [1](#0-0) 

The intent is: an account with no stored index (0) should be treated as if it entered at `INITIAL_INDEX`, so `_deltaIndex == 0` for a fresh index. But the guard only fires when `_tokenIndex > INITIAL_INDEX`. When the token was just added via `_updateTokenSpeed`, its index is set exactly to `INITIAL_INDEX` (`contracts/RewardsDistributor.sol:296-299`). Any account that already holds the underlying (DepositToken/DebtToken) at that moment keeps `_accountIndex = 0`, producing `_deltaIndex = INITIAL_INDEX` and `_tokensDelta = balanceOf(account).wadMul(1e18) = balanceOf(account)` reward tokens credited in `_updateTokensAccruedOf` (`contracts/RewardsDistributor.sol:261-265`).

Reachability for an unprivileged attacker:
1. Attacker deposits collateral via `DepositToken.deposit(amount, attacker)` and holds `msdTOKEN` (`contracts/DepositToken.sol:211-237`). This requires no privileged role.
2. Governor later whitelists `msdTOKEN` as a reward token via `updateTokenSpeed(msdTOKEN, speed)` — a routine configuration action, not an attack prerequisite the attacker controls maliciously; attackers who already hold deposits qualify automatically.
3. Attacker calls the permissionless `updateBeforeMintOrBurn(msdTOKEN, attacker)` (`contracts/RewardsDistributor.sol:175-180`) — explicitly "may be called by anyone" per the NatSpec — or simply performs a dust `transfer`/`deposit` which invokes `updateRewardsBeforeMintOrBurn`/`updateRewardsBeforeTransfer` (`contracts/DepositToken.sol:124-144`). `tokensAccruedOf[attacker]` is credited `attacker's msdTOKEN balance`.
4. Attacker calls `claimRewards(attacker)`; `_transferRewardIfEnoughTokens` transfers `min(accrued, distributor reward-token balance)` (`contracts/RewardsDistributor.sol:248-255`), draining the reward pool up to the attacker's deposit size. The same exploit applies to every pre-existing holder of the whitelisted token and to subsequently whitelisted tokens — the window is from speed activation until the index first grows above `INITIAL_INDEX` (the first accrual second), and anyone can trigger their own inflated accrual during it.

The broken invariant is reward accrual conservation: `tokensAccruedOf` is inflated without any corresponding elapsed reward distribution.

### Impact Explanation
Every account holding the token at the moment it is added to a `RewardsDistributor` (or added with a new token) can instantly claim reward tokens equal to their full token balance. This is direct theft of the distributor's reward-token reserves (unclaimed yield of all legitimate users). With a large deposit — obtainable via flash-loan-free ordinary deposits, or even via flashIssue-style leverage patterns — an attacker can drain the entire reward balance in one call sequence.

### Likelihood Explanation
The trigger requires a reward token to be whitelisted while users already hold the tracked token — a normal operational sequence (rewards are typically enabled after a pool has deposits). Calling `updateBeforeMintOrBurn` is permissionless, so no privileged cooperation is needed once the token is added; any pre-existing holder (or frontrunner of the `updateTokenSpeed` transaction who deposits in the same block before index growth) is exploitable. No pause flag, reentrancy guard, or SynthContext check prevents it: `claimRewards` is `nonReentrant` but the theft happens in a single accounting write.

### Recommendation
Normalize the zero account index unconditionally (or to the current index) rather than only when the token index exceeds `INITIAL_INDEX`:

```solidity
if (_accountIndex == 0) {
    _accountIndex = _tokenIndex > INITIAL_INDEX ? INITIAL_INDEX : _tokenIndex;
}
```

Alternatively, in `_updateTokensAccruedOf`, snapshot `accountIndexOf[token_][account_] = _tokenIndex` for accounts whose stored index is `0` before computing the delta, so first-contact accounts never accrue retroactively.

### Proof of Concept
Hardhat-style sketch (mirroring `test/RewardDistributor.test.ts` which already mocks `msdTOKEN`):

```ts
// Setup: alice deposits 1000 msdTOKEN before rewards are enabled for it.
msdTOKEN1.balanceOf.whenCalledWith(alice.address).returns(parseEther('1000'))
msdTOKEN1.totalSupply.returns(parseEther('2000'))

// Governor enables rewards AFTER alice already holds tokens.
await rewardDistributor.connect(governor).updateTokenSpeed(msdTOKEN1.address, parseEther('1'))
// tokenStates[msdTOKEN1].index == INITIAL_INDEX (1e18)

// Alice (unprivileged) checkpoints herself the same block.
await rewardDistributor.updateBeforeMintOrBurn(msdTOKEN1.address, alice.address)

// Bug: deltaIndex = INITIAL_INDEX - 0 => accrued = balance * 1 = 1000 reward tokens
const accrued = await rewardDistributor.tokensAccruedOf(alice.address)
expect(accrued).to.eq(parseEther('1000')) // should be 0

// Alice drains the distributor.
const vspBefore = await vsp.balanceOf(alice.address)
await rewardDistributor['claimRewards(address)'](alice.address)
expect((await vsp.balanceOf(alice.address)).sub(vspBefore)).to.eq(parseEther('1000'))
```

Expected result: `tokensAccruedOf[alice]` equals her full `msdTOKEN1` balance despite zero elapsed distribution time, and `claimRewards` transfers that amount from the distributor, confirming theft of unclaimed yield from the reward pool.
