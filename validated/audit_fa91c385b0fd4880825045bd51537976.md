### Title
Two-pass account lock validation in `try_lock_transaction_batch` allows conflicting write/read locks to both succeed within the same batch - ([File: accounts-db/src/account_locks.rs])

### Summary
`AccountLocks::try_lock_transaction_batch` validates every transaction's account access against the current lock state in a first pass (`can_lock_accounts`, which is read-only and does not mutate `self`), and only actually applies the locks in a second pass (`lock_accounts`). Because the validation pass never mutates the lock maps in between transactions of the same batch, two transactions in the same batch that conflict on the same key (e.g. one write, one read) can both pass validation against the identical pre-batch snapshot, and both then acquire their (mutually exclusive) locks in the second pass.

### Finding Description
`try_lock_transaction_batch` first iterates the whole batch calling `self.can_lock_accounts(keys.clone())` for each transaction: [1](#0-0) 

`can_lock_accounts` takes `&self` and only reads `write_locks`/`readonly_locks`; it never records that a key is "about to be locked" by an earlier transaction in the same batch: [2](#0-1) 

Only after this entire validation pass completes does the second loop call the mutating `lock_accounts` for each still-`Ok` transaction: [3](#0-2) 

`can_write_lock`/`can_read_lock` are checked purely against the global `write_locks`/`readonly_locks` maps as they existed before the batch started processing: [4](#0-3) 

Consider a batch containing transaction A (writes key `K`) and transaction B (reads key `K`), where `K` is otherwise unlocked. During the validation pass: checking A finds `K` unlocked → `Ok`; checking B *also* finds `K` unlocked (because A's check didn't mutate state) → `Ok`. Both entries remain `Ok` after the validation pass. In the second pass, `lock_accounts` for A increments `write_locks[K]`, and `lock_accounts` for B increments `readonly_locks[K]` — both succeed, leaving `K` simultaneously write-locked and read-locked. This defeats the core invariant that account locks are supposed to guarantee: mutually exclusive access per account across concurrently scheduled transactions.

There is no other guard preventing this: `validate_account_locks` only checks for duplicate keys *within a single transaction's* account list, not conflicts *between different transactions in the same batch*: [5](#0-4) 

An unprivileged attacker fully controls the account keys and writable/readonly flags of transactions in a packet batch it submits to the leader's TPU. No staking, gossip, or leader-side control is required — simply crafting two transactions in a single batch that reference the same pubkey with conflicting write/read access is sufficient to trigger the flaw, assuming the key isn't already locked by unrelated in-flight activity.

### Impact Explanation
This breaks the fundamental account-locking invariant that prevents concurrent execution of transactions touching the same account. Both conflicting transactions would be reported as successfully locked and handed off for concurrent execution/scheduling, creating a data race on account state, non-deterministic results, and potential production of an invalid recorded block whose execution outcome differs from what the rest of the network (running a correct implementation) would produce — a consensus-relevant correctness bug matching the "invalid recorded block" / bank-halt bounty category.

### Likelihood Explanation
The precondition is minimal: two transactions in the same banking packet batch that reference a shared account key with conflicting write/read access, and that key not already locked by other concurrent traffic. This is trivially and repeatably constructible by any unstaked client submitting transactions to a leader's TPU, without needing any special privileges, staking, or timing races against other validators.

### Recommendation
Merge validation and locking into a single pass per transaction (check-then-lock atomically for each transaction before moving to the next), so that a transaction's lock takes effect immediately and is visible to subsequent transactions in the same batch — restoring the original single-pass "validate and lock" semantics instead of a global validate-all-then-lock-all split.

### Proof of Concept
```rust
#[test]
fn test_batch_write_read_conflict_both_granted() {
    use solana_pubkey::Pubkey;

    let key = Pubkey::new_unique();
    let mut locks = AccountLocks::default();

    // Transaction A: write-locks `key`
    let tx_a_keys: Vec<(&Pubkey, bool)> = vec![(&key, true)];
    // Transaction B: read-locks `key`
    let tx_b_keys: Vec<(&Pubkey, bool)> = vec![(&key, false)];

    let batch = vec![
        Ok(tx_a_keys.into_iter()),
        Ok(tx_b_keys.into_iter()),
    ];

    let results = locks.try_lock_transaction_batch(batch);

    // BUG: both succeed, even though write+read on the same key
    // must be mutually exclusive.
    assert!(results[0].is_ok());
    assert!(results[1].is_ok()); // should be Err(AccountInUse), but currently is Ok

    // Confirms the invariant violation directly on internal state.
    assert!(locks.is_locked_write(&key));
    assert!(locks.is_locked_readonly(&key)); // both true simultaneously
}
```
Expected (fixed) behavior: the second transaction's lock attempt should return `Err(TransactionError::AccountInUse)`, and `is_locked_write`/`is_locked_readonly` should never both report true for the same key at the same time.

    fn can_lock_accounts<'a>(
        &self,
        keys: impl Iterator<Item = (&'a Pubkey, bool)>,
    ) -> TransactionResult<()> {
        for (key, writable) in keys {
            if writable {
                if !self.can_write_lock(key) {
                    return Err(TransactionError::AccountInUse);
                }
            } else if !self.can_read_lock(key) {
                return Err(TransactionError::AccountInUse);
            }
        }

        Ok(())
    }

    fn can_read_lock(&self, key: &Pubkey) -> bool {
        // If the key is not write-locked, it can be read-locked
        !self.is_locked_write(key)
    }

    fn can_write_lock(&self, key: &Pubkey) -> bool {
        // If the key is not read-locked or write-locked, it can be write-locked
        !self.is_locked_readonly(key) && !self.is_locked_write(key)
    }

pub fn validate_account_locks(
    account_keys: AccountKeys,
    tx_account_lock_limit: usize,
) -> TransactionResult<()> {
    if account_keys.len() > tx_account_lock_limit {
        Err(TransactionError::TooManyAccountLocks)
    } else if has_duplicates(account_keys) {
        Err(TransactionError::AccountLoadedTwice)
    } else {
        Ok(())
    }
}
