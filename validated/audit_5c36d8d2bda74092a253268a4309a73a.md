## Title
Division by zero via `assert`-only guard in `RepositoryImpl.calculateGlobalEnergyLimit` when `totalEnergyWeight == 0` under hardened resource calculation - (File: `actuator/src/main/java/org/tron/core/vm/repository/RepositoryImpl.java`)

### Summary
`RepositoryImpl.calculateGlobalEnergyLimit` guards against a zero `totalEnergyWeight` denominator only with a Java `assert` statement, which is a no-op in production (Java assertions are disabled by default unless the JVM is started with `-ea`). If `totalEnergyWeight` is `0` and `hardenResourceCalculation()` (`VMConfig.allowHardenResourceCalculation`) is enabled, execution falls through to a `BigInteger.divide(BigInteger.ZERO)`, which throws an uncaught `ArithmeticException`.

### Finding Description [1](#0-0) 

```java
public long calculateGlobalEnergyLimit(AccountCapsule accountCapsule) {
    long frozeBalance = accountCapsule.getAllFrozenBalanceForEnergy();
    if (frozeBalance < TRX_PRECISION) {
      return 0;
    }
    long energyWeight = frozeBalance / TRX_PRECISION;
    long totalEnergyLimit = getDynamicPropertiesStore().getTotalEnergyCurrentLimit();
    long totalEnergyWeight = getDynamicPropertiesStore().getTotalEnergyWeight();

    assert totalEnergyWeight > 0;

    if (hardenResourceCalculation()) {
      return BigInteger.valueOf(energyWeight)
          .multiply(BigInteger.valueOf(totalEnergyLimit))
          .divide(BigInteger.valueOf(totalEnergyWeight))
          .longValueExact();
    }
    return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
}
```

Unlike the sibling non-VM implementations in `EnergyProcessor.calculateGlobalEnergyLimit` and `BandwidthProcessor.calculateGlobalNetLimit`, which both explicitly check `if (totalEnergyWeight <= 0) return 0;` before dividing, [2](#0-1)  the VM-facing `RepositoryImpl` variant relies only on an `assert`, which does not execute in a production JVM (no `-ea` flag). This is the exact bug-class analog to the reported CVE-2022-21735: a numeric operation whose zero-denominator precondition is checked in a way that is not enforced at runtime, letting a divide-by-zero reach the actual arithmetic operation.

This method is reachable from TVM execution paths that call into `Repository` for freeze/energy resource accounting (`calculateGlobalEnergyLimit` is part of the `Repository` interface used by native contract processors invoked from the TVM/actuator layer during transaction execution), and is exercised by hardened-vs-legacy parity tests in `RepositoryImplHardenTest` and `CalculateGlobalLimitHardenTest`. When `hardenResourceCalculation()` is enabled (governed by `VMConfig.allowHardenResourceCalculation`, a chain parameter) and `totalEnergyWeight` reaches `0`, the `BigInteger.divide(BigInteger.ZERO)` call throws `java.lang.ArithmeticException: BigInteger divide by zero`.

### Impact Explanation
An uncaught `ArithmeticException` thrown during actuator/TVM execution while processing a transaction is not a standard, expected `ContractExeException`/`ContractValidateException`; if it propagates up through block application in `Manager`, it can crash the node process or halt block processing for all nodes that reach the same state deterministically, which is consistent with the "node crash or halt" acceptance criterion. Because `totalEnergyWeight` is a global chain aggregate (sum of network-wide energy weight from frozen balances), reaching `0` would generally require pathological/edge network states (e.g., very early chain bootstrap or a state where no account holds frozen-for-energy balance), which limits real-world likelihood on an established mainnet but remains a legitimate latent defect matching the reported bug class.

### Likelihood Explanation
Likelihood is Medium: the guard exists only as an `assert`, meaning any production JVM run without `-ea` (the default, and the normal way `java-tron` nodes are started) has zero protection at runtime. The precondition (`totalEnergyWeight == 0`) is unlikely on a mature network, but is a state achievable in test networks, private/consortium chains, or unusual initial-genesis states before any energy freezing has occurred network-wide, and it is a state the code path is specifically supposed to handle safely (as proven by the presence of explicit zero-checks in the sibling `EnergyProcessor`/`BandwidthProcessor` implementations, which the VM `RepositoryImpl` copy is missing).

### Recommendation
Replace the `assert totalEnergyWeight > 0;` statement in `RepositoryImpl.calculateGlobalEnergyLimit` (and audit the analogous `calculateGlobalNetLimit`/`getAccountEnergyUsageBalanceAndRestoreSeconds`/`getAccountNetUsageBalanceAndRestoreSeconds`-style helpers in `RepositoryImpl` for the same pattern) with an explicit runtime check, e.g.:
```java
if (totalEnergyWeight <= 0) {
    return 0;
}
```
mirroring the guard already present in `EnergyProcessor.calculateGlobalEnergyLimit` and `BandwidthProcessor.calculateGlobalNetLimit`.

### Proof of Concept
1. Bring `DynamicPropertiesStore.getTotalEnergyWeight()` to `0` (e.g., via a chain/test configuration where no account has frozen balance for energy, or through the existing test harness `RepositoryImplHardenTest`/`CalculateGlobalLimitHardenTest` which directly manipulate `saveTotalEnergyWeight`).
2. Enable hardened resource calculation: `VMConfig.initAllowHardenResourceCalculation(1)` (equivalently, activate the `ALLOW_HARDEN_RESOURCE_CALCULATION` chain parameter).
3. Have an account with `getAllFrozenBalanceForEnergy() >= TRX_PRECISION` (any account that has frozen balance for energy) trigger a TVM path that calls `Repository.calculateGlobalEnergyLimit(accountCapsule)` (e.g., via delegate/undelegate resource native contracts or energy accounting during a contract call).
4. `BigInteger.valueOf(totalEnergyWeight)` is `BigInteger.ZERO`; `.divide(BigInteger.ZERO)` throws `ArithmeticException`, which is not caught by `ContractExeException`/`ContractValidateException` handlers in the surrounding actuator code, propagating the exception up through transaction/block processing.
