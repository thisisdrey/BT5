### Title
Per-Repository Concurrency Limit Bypass via Source/Additional Repository Manipulation - (File: internal/grpc/middleware/limithandler/middleware.go)

### Summary
Gitaly's `[[concurrency]]` per-repository backpressure mechanism keys its limiter solely off the RPC's `target_repository` field. For RPCs that operate against two repositories — a "target" (checked) and a "source"/"origin"/"pool" repository (the one actually read from or fetched over the network, e.g. `CreateFork.SourceRepository`, `FetchSourceBranch.SourceRepository`, `FetchIntoObjectPool.Origin`, `ReplicateRepository.Source`) — the concurrency limit is enforced against the target only. A caller can repeatedly issue such requests using freshly created, never-before-seen target repositories while always pointing the source/origin field at the same expensive repository, completely bypassing the `max_per_repo`/`max_queue_size`/`max_queue_wait` protections meant to shield that (potentially large/hot) repository from resource exhaustion.

### Finding Description
The concurrency-limiting middleware derives its lock key exclusively from `info.Repository`, which is populated by `requestinfohandler.extractRequestInfo` using `mi.TargetRepo(reqMsg)` — the field annotated `[(target_repository)=true]` in the `.proto` definition. [1](#0-0) [4](#0-3) 

Several mutator RPCs are explicitly documented as reading from a "second repository that is not the target repository" — this is recorded as `sourceRepository`/`objectPool` purely for tag/log correlation, never fed into the limiter's lock key: [5](#0-4) 

Concrete examples where the expensive I/O happens against the *unlimited* source repository rather than the *limited* target:
- `CreateFork`: fetches from `SourceRepository` via `gitcmd.InternalGitalyURL`/sidechannel while the target is a brand-new (attacker-controlled, disposable) repository. [3](#0-2) 
- `ReplicateRepository`: pulls a full snapshot/fetch from `Source`, keyed by `Repository` (target) only in the concurrency config; a dedicated hard-coded singleton limiter exists for this RPC precisely because of its cost, but it is still keyed globally, not per-source-repo, so the bypass concern applies to any per-repo-configured RPC of this shape. [6](#0-5) 
- `FetchIntoObjectPool` / `LinkRepositoryToObjectPool`: operate against `Origin`/pool member while the "repository" administratively scoped for limiting purposes may be a disposable one.

Because Gitaly's concurrency limiting exists specifically to prevent "a surge of requests... to retrieve or change a piece of Git data" from overwhelming the node for a given repository, an attacker who repeatedly varies the target repository while holding the source repository fixed defeats this protection entirely. [7](#0-6) 

### Impact Explanation
The entire purpose of per-repository concurrency limiting (protecting a specific, likely large or hot repository from being overwhelmed by concurrent expensive operations such as clone/fetch/replicate) is nullified whenever the expensive I/O target can be supplied via a non-limited "source" field. This is directly analogous to the reported PearVault issue where tier limits were enforced on the wrong (attacker-chosen) address instead of the actual resource-consuming party. In Gitaly's case, an unprivileged but authenticated caller (e.g., through GitLab creating forks or replicating from a public source repo) can repeatedly trigger unbounded concurrent expensive operations against one target repository by disguising each request under a distinct throwaway "target" repository, causing denial-of-service style resource exhaustion (CPU/IO/memory) on that repository's storage node, circumventing operator-configured `max_per_repo`/`max_queue_size`/`max_queue_wait` protections.

### Likelihood Explanation
Any authenticated client capable of invoking `CreateFork`, `ReplicateRepository`, `FetchSourceBranch`, or `FetchIntoObjectPool` (all reachable via ordinary GitLab fork/replication workflows) can trigger this: each call only requires creating disposable target repositories (which is a normal, permitted, low-privilege operation) while pointing the source at the repository to be hammered. No special privilege beyond normal repository-creation/fork rights is required, making this readily reachable in practice wherever these RPCs are exposed with per-repo concurrency configuration intended to bound load from a specific repository.

### Recommendation
For cross-repository mutator RPCs, incorporate the source/origin/additional repository (as recorded in `RequestInfo.sourceRepository`/`objectPool`) into the concurrency-limiting lock key — or enforce a separate limiter keyed on the source repository — rather than relying solely on the target repository's relative path. At minimum, RPCs that perform their dominant I/O cost against a non-target repository should be limited by that repository's identity.

### Proof of Concept
1. Configure Gitaly with a per-repo concurrency limit for `CreateFork` (or `FetchSourceBranch`/`FetchIntoObjectPool`), e.g. `max_per_repo = 1`, targeting protection of a large `SourceRepository` S.
2. As an authenticated client, repeatedly issue `CreateForkRequest{ SourceRepository: S, Repository: <new disposable repo N_i> }` for `i = 1..K`, always using a freshly generated `Repository` (target) value.
3. Because `LimitConcurrencyByRepo` keys off `info.Repository.GetRelativePath()` (the target `N_i`, unique each time), every one of the K concurrent fetches from `S` is admitted simultaneously — the `max_per_repo` limit intended to protect `S` never triggers, exhausting Gitaly's git-clone/fetch capacity against S.

func (i *RequestInfo) extractRequestInfo(request any) {
	type poolScopedRequest interface {
		GetObjectPool() *gitalypb.ObjectPool
	}

	if poolScoped, ok := request.(poolScopedRequest); ok {
		i.objectPool = poolScoped.GetObjectPool()
	}

	// Requests like CreateFork and FetchSourceBranch read from a second repository that is not the
	// target repository. Record it so that such cross-repository operations can be correlated back
	// to their source project.
	type sourceScopedRequest interface {
		GetSourceRepository() *gitalypb.Repository
	}

	if sourceScoped, ok := request.(sourceScopedRequest); ok {
		i.sourceRepository = sourceScoped.GetSourceRepository()
	}

	if reqMsg, ok := request.(proto.Message); ok {
		// This handles extracting nested and non-nested *gitalypb.Repository fields from the request. In cases of
		// multiple such fields, it will choose the one with the `target_repository` extension.
		if mi, err := protoregistry.GitalyProtoPreregistered.LookupMethod(i.FullMethod); err == nil {
			switch mi.Scope {
			case protoregistry.ScopeRepository:
				if targetRepo, err := mi.TargetRepo(reqMsg); err == nil {
					i.Repository = targetRepo
				}
			case protoregistry.ScopeStorage:
			case protoregistry.ScopePartition:
				if storage, err := mi.Storage(reqMsg); err == nil {
					i.storageName = storage
				}
				if ptn, err := mi.Partition(reqMsg); err == nil {
					i.partition = ptn
				}
			}
		}
	}

# Request limiting in Gitaly

In the GitLab ecosystem, Gitaly is the service that is at the bottom of the
stack for Git data access. This means that when there is a surge of
requests to retrieve or change a piece of Git data, the I/O happens in Gitaly.
This can lead to Gitaly being overwhelmed due to system resource exhaustion
because all Git access goes through Gitaly.

If there is a surge of traffic beyond what Gitaly can handle, Gitaly should
be able to push back on the client calling. Gitaly shouldn't subserviently agree
to process more than it can handle.

We employ concurrency limiting as our primary backpressure mechanism in Gitaly.

## Concurrency queue

Limit the number of concurrent RPCs that are in flight on each Gitaly node for each
repository per RPC using `[[concurrency]]` configuration:

```toml
[[concurrency]]
rpc = "/gitaly.SmartHTTPService/PostUploadPackWithSidechannel"
max_per_repo = 1
```
