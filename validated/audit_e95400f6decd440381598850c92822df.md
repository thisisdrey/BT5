## Title
Permissionless front-runnable initializer for the global `FeeState` singleton allows an attacker to seize `global_fee_admin` - (File: `programs/marginfi/src/instructions/marginfi_group/init_global_fee_state.rs`)

### Summary
The Cnote `_setAccountantContract()` bug class — a permissionless "run-once" setter with no access control that lets an attacker front-run the legitimate caller and seize a privileged role — has a direct analog in marginfi-v2's `init_global_fee_state` instruction. This instruction initializes the program-wide `FeeState` singleton PDA and accepts an arbitrary `admin_key`/`fee_wallet` argument from *any* signer, with no check that the caller is the intended protocol deployer/owner.

### Finding Description
`init_global_fee_state` is documented as "(Runs once per program)" [1](#0-0) . Its handler `initialize_fee_state` writes the caller-supplied `admin_key` directly into `fee_state.global_fee_admin` and `fee_wallet` into `fee_state.global_fee_wallet`, with no validation of who is allowed to call it [2](#0-1) .

The associated `Accounts` struct only requires:
- `payer: Signer<'info>` (any wallet, just pays rent)
- `fee_state`: a PDA derived from the fixed seed `FEE_STATE_SEED` with the Anchor `init` constraint (only succeeds if the account does not already exist)
- `system_program`

There is no admin allowlist, no hardcoded pubkey check, and no check against the program's upgrade authority [3](#0-2) .

Because the `FeeState` PDA is a **global singleton** (`"Unique per-program"` [4](#0-3) ) derived from a fixed, publicly known seed, its address is deterministic and known before deployment. Any actor monitoring the network for the legitimate `init_global_fee_state` transaction (or simply racing to call it first after the program is deployed) can submit their own `init_global_fee_state` instruction first and permanently become `global_fee_admin`.

Once set, `global_fee_admin` is exactly the highest-privilege fee/pause role in the system, per the docs:
- Edit global fee parameters (program fee rates, origination fee shares, init fees)
- Change the global fee wallet
- Set or clear the `pause_delegate_admin`
- Panic-pause the entire protocol [5](#0-4) 

All subsequent privileged operations on `FeeState` (`edit_global_fee_state`, `panic_pause`/`panic_unpause`, `config_group_fee`) are gated only by `has_one = global_fee_admin` checks against this attacker-controlled field [6](#0-5) [7](#0-6) .

### Impact Explanation
Unlike the original Cnote report — where the judge downgraded severity because the "worst case is a re-deploy" of a regular contract — the Solana PDA in this case is derived from a **fixed seed** (`FEE_STATE_SEED`) with an Anchor `init` constraint, meaning the account can only be created once. If an attacker wins the race, the legitimate deployer cannot simply re-run the initializer at the same address; recovering control would require either a program upgrade (changing the seed) or some other migration path not present in the current instruction set. The attacker-controlled `global_fee_admin` can then:
- Set an attacker-controlled `global_fee_wallet` to redirect all protocol/program fees network-wide.
- Manipulate `program_fee_fixed`/`program_fee_rate`, `liquidation_max_fee`, `order_execution_max_fee`, and flat SOL fees across every group.
- Trigger `panic_pause` to freeze the entire protocol (subject to rate limits), or clear the `pause_delegate_admin`.

This is a permanent, protocol-wide unauthorized state change / denial-of-service and fee-theft vector, not merely a redeploy inconvenience.

### Likelihood Explanation
Likelihood depends entirely on deployment operational security: the `FeeState` PDA address is deterministic and publicly derivable before the legitimate `init_global_fee_state` transaction lands, so any party watching the chain (or simply racing after the program's first deployment) can call it first. This is analogous to the classic "front-runnable initializer" pattern, and is realistic in practice for any public devnet/mainnet deployment where the init transaction is not bundled atomically with program deployment (e.g., via a single guarded deploy script or same-transaction bundling).

### Recommendation
- Gate `init_global_fee_state` so it can only be called by a fixed, program-known authority (e.g., verify the caller against the program's upgrade authority via the `bpf_loader_upgradeable` program's `ProgramData` account, similar to patterns used elsewhere for privileged one-time setup), rather than accepting an arbitrary `admin_key` argument from any signer.
- Alternatively, bundle `init_global_fee_state` in the same atomic transaction as program deployment/upgrade so no window exists for front-running.

### Proof of Concept
1. Program is deployed; the `FeeState` PDA (seed `FEE_STATE_SEED`) does not yet exist.
2. Attacker (any wallet, no special privileges) submits `init_global_fee_state(admin = attacker_pubkey, fee_wallet = attacker_wallet, ...)` before the legitimate deployer's equivalent transaction is confirmed — see the account/ix wiring in [3](#0-2) .
3. The `init` constraint succeeds because the PDA did not exist; `fee_state.global_fee_admin` and `fee_state.global_fee_wallet` are now attacker-controlled, as executed in `initialize_fee_state` [8](#0-7) .
4. The legitimate deployer's subsequent `init_global_fee_state` transaction fails (Anchor `init` on an already-initialized account errors out), permanently locking out the intended admin from the singleton account.
5. Attacker now calls `edit_global_fee_state` / `panic_pause` using the `has_one = global_fee_admin` check that now matches their own key [6](#0-5) , gaining full control over protocol-wide fees and pause functionality.

pub fn initialize_fee_state(
    ctx: Context<InitFeeState>,
    admin_key: Pubkey,
    fee_wallet: Pubkey,
    bank_init_flat_sol_fee: u32,
    liquidation_flat_sol_fee: u32,
    order_init_flat_sol_fee: u32,
    program_fee_fixed: WrappedI80F48,
    program_fee_rate: WrappedI80F48,
    liquidation_max_fee: WrappedI80F48,
    order_execution_max_fee: WrappedI80F48,
) -> Result<()> {
    let mut fee_state = ctx.accounts.fee_state.load_init()?;
    fee_state.global_fee_admin = admin_key;
    fee_state.global_fee_wallet = fee_wallet;
    fee_state.key = ctx.accounts.fee_state.key();
    fee_state.bank_init_flat_sol_fee = bank_init_flat_sol_fee;
    fee_state.bump_seed = ctx.bumps.fee_state;
    fee_state.program_fee_fixed = program_fee_fixed;
    fee_state.program_fee_rate = program_fee_rate;
    fee_state.liquidation_max_fee = liquidation_max_fee;
    fee_state.liquidation_flat_sol_fee = liquidation_flat_sol_fee;
    fee_state.order_execution_max_fee = order_execution_max_fee;
    fee_state.order_init_flat_sol_fee = order_init_flat_sol_fee;

    Ok(())
}

## Global Fee Admin

The `global_fee_admin` is separate from the group-level admin roles. It is stored on the `FeeState`
account (a global singleton).

**Can do:**
- Edit global fee parameters (program fee rates, origination fee shares, init fees)

- Set or clear the dedicated pause delegate admin
