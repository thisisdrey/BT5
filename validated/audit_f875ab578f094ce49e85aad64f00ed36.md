### Title
Hard revert of the entire `liquidate` call on partial bad-debt-socialization failure permanently blocks liquidation of that position — ([File: mainnet/contracts/market/v0-4-market.clar])

### Summary
`liquidate` closes out a borrower's remaining debt via `socialize-debt-asset`, which is folded over every remaining debt entry. If any single step inside that fold fails, the fold's accumulator is marked `success: false`, and the outer `asserts!` immediately reverts the entire liquidation transaction with `ERR-BAD-DEBT-SOCIALIZATION-FAILED`. Because none of the on-chain state that caused the failure changes as a side effect of the failed attempt, every subsequent liquidation attempt on that same borrower/asset combination will hit the exact same revert — a deterministic, permanent denial-of-service on liquidating that under-collateralized position, mirroring the reported `BulkCreateUnstakes` bug class where a hard stop on a single mismatch causes indefinite reprocessing failure.

### Finding Description
When a liquidation empties a position's collateral (`no-collateral-left`), the market attempts to write off any remaining debt across all the borrower's debt assets: [1](#0-0) 

This calls `fold socialize-debt-asset fresh-debt-list …` and then hard-fails the whole transaction if any element of the fold did not succeed: [2](#0-1) 

`socialize-debt-asset` uses `unwrap!` three times per debt entry — on `vault-socialize-debt`, on `vault-accrue`, and on `.v0-market-vault debt-remove-scaled` — and any single one of these failing anywhere in the list causes `success: false` to propagate through the rest of the fold (the early-return branch at line 905) and ultimately trips the `asserts!` at line 1548, reverting the *entire* `liquidate` call, including the collateral removal (`collateral-remove`) that already happened earlier in the same transaction.

Crucially, none of the state examined by `debt-remove-scaled`'s own guard is mutated by a failed attempt: [3](#0-2) [4](#0-3) 

Since `liquidate` is atomic, a failure inside the socialization fold leaves the borrower's position, the vault totals, and the debt/collateral maps exactly as they were before the call. As in the audited report ("transactions will always keep coming back... this will effectively result in the denial-of-service of the notary session processing as a whole"), any liquidator retry against that same borrower will retrace the identical computation and hit the identical mismatch/failure, so the position becomes permanently unliquidatable via this code path — the bad debt can never be socialized and written off.

### Impact Explanation
This lands on **permanent freezing of funds / protocol insolvency**: a borrower position that has lost all its collateral but still carries debt across multiple assets can become permanently stuck if any single sub-step of `socialize-debt-asset` fails for that borrower. The debt is never removed from `market-vault`, the vault's liquidity index is never corrected via `vault-accrue`/`vault-socialize-debt`, and lenders backing that vault continue to hold an un-writable-off bad debt indefinitely — an unrecoverable, permanently growing insolvency for the affected vault, with no way for anyone (including the DAO, since `liquidate`/`socialize-debt-asset` have no override/skip path) to force closure of that specific bad debt through this mechanism.

### Likelihood Explanation
This requires a genuine (not necessarily attacker-crafted) mismatch between the position's per-asset stored scaled debt and what `debt-remove-scaled`/`vault-socialize-debt` will accept — the kind of low-probability accounting drift (e.g., accrual rounding divergence between `vault-accrue` and the position's cached scaled amounts, accumulated across many blocks/positions) explicitly called out as the trigger class in the reference report ("low probability... e.g., DB corruption"). Because the fold has no graceful-skip/continue behavior (unlike the recommended fix in the reference report) and instead hard-aborts the whole liquidation on any single-asset failure, once such a mismatch occurs for a borrower it is deterministic and permanent, not transient.

### Recommendation
Mirror the reference fix: instead of unconditionally `asserts!`-reverting the whole `liquidate` transaction when `socialize-debt-asset`'s fold reports `success: false`, log/emit the specific failing debt entry and either (a) skip that entry and continue socializing the remaining debt assets, or (b) allow the position to be marked with an explicit "bad-debt-stuck" flag that a privileged/DAO-gated recovery path can resolve, rather than silently reverting the entire liquidation (including the already-computed collateral seizure) with no alternative remediation path.

### Proof of Concept
Conceptual trigger (exact numeric reproduction would require simulating long-run interest accrual/rounding drift across a vault, which is out of scope to fully enumerate here):
1. A borrower holds debt in two assets and collateral that, upon liquidation of the primary debt asset, is fully exhausted (`no-collateral-left` = true), with debt still outstanding in the secondary asset.
2. `liquidate` builds `fresh-debt-list` containing the secondary asset's stored `scaled` amount and folds `socialize-debt-asset` over it (`mainnet/contracts/market/v0-4-market.clar:1544-1548`).
3. If `vault-socialize-debt`/`vault-accrue`/`debt-remove-scaled` for that secondary asset fails for any reason tied to a divergence between the position's cached scaled debt and the vault's live accounting (e.g., rounding drift accumulated via repeated `mul-div-down`/`mul-div-up` operations across many prior accrual cycles), `unwrap!` short-circuits to `failed-status`, propagating `success: false` through the fold.
4. `(asserts! (get success socialization-result) ERR-BAD-DEBT-SOCIALIZATION-FAILED)` reverts the entire `liquidate` call.
5. Because no state changed, any subsequent liquidator call against this borrower repeats steps 1–4 identically — the position can never be fully liquidated, permanently locking the un-socialized bad debt in the vault.

(define-private (socialize-debt-asset
                (debt-entry { aid: uint, scaled: uint })
                (acc { borrower: principal, success: bool }))
  ;; Early return if previous socialization failed
  (if (not (get success acc))
      acc
      (let ((borrower (get borrower acc))
            (failed-status { borrower: borrower, success: false })
            (asset-id (get aid debt-entry))
            (scaled-debt (get scaled debt-entry)))

            ;; Socialize in vault - pass scaled directly to avoid rounding
            (unwrap! (vault-socialize-debt asset-id scaled-debt) failed-status)
            ;; Refresh cache with new indexes post-write-down (lindex decreased)
            (map-set index-cache
                     { timestamp: stacks-block-time, aid: asset-id }

                                      debt-remove-scaled

        ))

(define-private (remove-user-scaled-debt (user-id uint) (asset-id uint) (amount uint))
  (let ((key { id: user-id, asset: asset-id })
        (current-scaled-debt (default-to u0 (get scaled (map-get? debt key)))) ;; graceful default to u0
        (legal? (asserts! (<= amount current-scaled-debt) ERR-INSUFFICIENT-DEBT))
        (updated-scaled-debt (- current-scaled-debt amount)))
    (if (is-eq updated-scaled-debt u0)
        (map-delete debt key)
        (map-set debt key { scaled: updated-scaled-debt }))
    (ok updated-scaled-debt)))
