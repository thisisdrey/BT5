## Analog Found

### Title
Relayer fee is paid unconditionally in the Wallet Contract even if the underlying relayed action fails - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The GMX bug is a case where a fee/slippage check is applied on the success path of an operation but skipped (or wrongly parameterized) on the failure path, letting an unprivileged actor (a keeper) benefit at the user's expense when the operation fails. The NEAR analog is in the ETH-implicit Wallet Contract (`WalletContract::rlp_execute` → `inner_rlp_execute`), where the relayer's compensation fee is sent out as an independent promise *before* — and unconditionally of — whether the actual user-intended action (transfer / ERC-20 transfer emulation) succeeds.

### Finding Description
`inner_rlp_execute` parses the relayed Ethereum-style transaction and, for `EOABaseTokenTransfer` and `ERC20Transfer` emulation kinds, immediately fires a transfer promise paying the parsed `fee` to the relayer (`context.predecessor_account_id`): [1](#0-0) 

This fee-payment promise is created via `env::promise_batch_create` as a standalone batch — it is not chained (`.then(...)`) to, or made conditional on, the promise that actually performs the user's intended action, which is only constructed afterward: [2](#0-1) 

The only failure-handling / refund logic that exists is for the caller's attached deposit (`CallerDeposit`), which is refunded in `rlp_execute_callback` if the main action's promise fails: [3](#0-2) 

There is no equivalent mechanism to reclaim or avoid paying the `fee` if the subsequent action fails. This is structurally identical to the GMX pattern: a value transfer that is supposed to compensate for a successful operation (swap in GMX, relayed action here) is validated/paid using the "success" assumption, while the actual code path allows the paid-for operation to fail independently, and the payer (user) bears the loss while the payee (keeper/relayer) keeps the benefit.

The user-facing documentation itself confirms the fee is meant as pure relayer compensation contingent on the transfer occurring, not an unconditional payment: "the relayer will receive some compensation for sending the transaction" — but no code ties that compensation to actual delivery.

### Impact Explanation
A relayer (an unprivileged transaction submitter, analogous to a GMX keeper) that is dishonest, misconfigured, or simply had the underlying action fail for reasons outside the user's control (e.g., destination account issues, gas exhaustion in a chained `FunctionCall`/`ft_transfer`, or a registrar-triggered relayer ban after the fee is already dispatched) still collects the fee from the eth-implicit account's balance even though the user's transfer/transaction was never completed. This is a concrete theft of funds from the wallet-contract's owner to the relayer, with no recovery path, since the fee-refund promise executes and finalizes independently of the outcome of the main action's promise.

### Likelihood Explanation
Any relayer processing `rlp_execute` calls controls when/whether to submit the transaction and, in the `address_check: Some(...)` branch, the fee is sent out even before the registrar lookup that can lead to the relayer being banned — meaning a faulty/malicious relayer's fee payment is unaffected by that later-detected fault. Even without malice, ordinary conditions causing the relayed action to fail (contract-side reverts, insufficient attached gas relative to what the receiving contract needs, account-existence issues) are common and outside the wallet owner's control once the transaction is signed, making this a persistently reachable path, not a contrived edge case.

### Recommendation
Chain the relayer fee-payment promise to the outcome of the main action promise (e.g., pay the fee only in `rlp_execute_callback` conditioned on `PromiseResult::Successful`), mirroring how `CallerDeposit` refunds are already gated on the action's promise result, so the relayer is compensated only when the user's intended action actually executes successfully.

### Proof of Concept
1. A relayer holding a `FunctionCall`-permission access key for a Wallet Contract account submits an RLP-encoded `EOABaseTokenTransfer`/ERC-20 transfer with a non-zero `fee`.
2. `inner_rlp_execute` immediately creates and sends the fee-transfer promise to the relayer at `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs:381-384`.
3. The subsequent action promise (the actual transfer/`ft_transfer`) is constructed and dispatched separately at `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs:412-472` and fails (e.g., destination issue, insufficient chained gas, or the relayer is later banned via `address_check_callback`'s registrar check).
4. `rlp_execute_callback` observes `PromiseResult::Failed`, refunds only the `CallerDeposit` (if any) and reports failure — the fee already paid to the relayer in step 2 is never recovered.
5. Net effect: the wallet-contract owner's balance is permanently reduced by `fee` with no corresponding service rendered.
