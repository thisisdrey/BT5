Audit Report

## Title
Snowbridge outbound-queue-v2 `PendingOrders` have no expiry or reap path, permanently locking relayer-reward fees if no `submit_delivery_receipt` is ever submitted - (File: bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs)

## Summary
`do_process_message` inserts a `PendingOrder { nonce, fee, block_number }` into `PendingOrders<T>` for every outbound message accepted, but the only code path that ever removes an entry is `process_delivery_receipt`, reachable exclusively via the public extrinsic `submit_delivery_receipt`, which requires an off-chain relayer to eventually produce a valid Ethereum execution-receipt proof. There is no time-based expiry, no permissionless reap mechanism, and no storage bound on `PendingOrders`, so if a relayer never submits a receipt for a given nonce (e.g. an economically unattractive fee, Ethereum-side congestion, or a stuck transaction), the associated `fee` reward is permanently unclaimable and the map entry persists in state forever.

## Finding Description
`do_process_message` builds and inserts the `PendingOrder` unconditionally for every accepted message: [1](#0-0) 

The pallet's entire call surface exposes only `submit_delivery_receipt`, which is the sole path into `process_delivery_receipt`: [2](#0-1) 

`process_delivery_receipt` is the only function that calls `<PendingOrders<T>>::remove(nonce)`, and it requires a verified `EventProof` from Ethereum containing the delivery event for that specific nonce: [3](#0-2) 

The pallet's `on_initialize`/`on_finalize` hooks only manage `Messages` and `MessageLeaves` (killed each block for commitment purposes) and never touch `PendingOrders`: [4](#0-3) 

The storage definition confirms `PendingOrders` is an unbounded `StorageMap` with no age-based cap: [5](#0-4) 

The only other code that touches `PendingOrders` is `AddTip::add_tip`, which increases `order.fee` on an existing entry but does not provide any removal or expiry logic: [6](#0-5) 

This confirms the claim as written: there is genuinely no fallback, timeout, or reap path for stuck `PendingOrders` entries in this pallet.

## Impact Explanation
The `fee` recorded in a `PendingOrder` is only ever paid out via `T::RewardPayment::register_reward` inside `process_delivery_receipt`. If a relayer never submits a valid receipt for a nonce, the associated `order.fee` value can never be forwarded to a relayer nor reclaimed by the sender, and the map entry accumulates indefinitely in `PendingOrders` (unbounded storage growth). This is a legitimate but narrow instance of the "permanent... bridge-state lock" impact category: the locked value is the relayer-reward accounting for that nonce, not necessarily an end-user balance directly held in this pallet (the actual point where a sender's balance is debited for `fee` is in the `system-frontend`/exporter code that constructs the `Message`, which is outside this file and was not fully traceable in the available index). The severity is bounded by the fact that this requires ordinary externalities (relayer non-participation, congestion, or an unprofitable fee) rather than a directly exploitable attack that forges state or double-pays; it is a systemic liveness/design gap rather than a corruption of proof or origin logic.

## Likelihood Explanation
This condition is highly likely to occur over time given normal system operation: any message with a `fee` too low to economically justify relaying, or any scenario where Ethereum-side execution never completes, will foreseeably never receive a `submit_delivery_receipt` call. No malicious actor or privileged behavior is required — this is an inherent property of relaying being voluntary and economically motivated, and the pallet has no housekeeping mechanism to detect or resolve stale orders.

## Recommendation
- Add a time/age-based reap mechanism for `PendingOrders` (e.g., a permissionless `reap_stale_order(nonce)` extrinsic gated on `block_number` exceeding a configured max age), with a defined policy for refunding or otherwise disposing of the associated fee.
- Bound `PendingOrders` storage growth and document the lifecycle/liveness assumptions for pending orders, similar to how `pallet_message_queue` documents and handles its "permanently overweight" scenario via `execute_overweight`.
- Clarify and verify (in `system-frontend`/exporter code) whether `fee` is pre-charged from the sender or drawn from a shared reward pot at payout time, to precisely scope the fund-lock semantics for downstream fixes.

## Proof of Concept
1. A message is sent via `snowbridge_pallet_system_v2::Pallet::send`/`EthereumBlobExporter`, reaching `do_process_message`, which inserts `PendingOrders::<T>::insert(nonce, order)` with `order.fee = F`.
2. No relayer ever calls `submit_delivery_receipt(nonce, ...)` for this nonce.
3. `PendingOrders::<T>::get(nonce)` remains `Some(order)` indefinitely, since `process_delivery_receipt` (the only removal path) requires a valid Ethereum event proof for that nonce that is never produced.
4. Fee `F` is never released to a relayer nor refunded, and the map entry persists in chain state permanently — confirmed by inspecting the full pallet call surface, hooks, and storage definitions, none of which provide any expiry/reap path.

		/// Process a delivery receipt from a relayer, to allocate the relayer reward.
		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}
