### Title
Nil-pointer dereference from unvalidated XCOFF relocation symbol index in `cmd/link/internal/loadxcoff` - ([File: src/internal/xcoff/file.go], [File: src/cmd/link/internal/loadxcoff/ldxcoff.go])

### Summary
Go's XCOFF reader builds relocation records by looking up `rel.Rsymndx` (an attacker-controlled index read straight from the object file) in a symbol map that is only sparsely populated, and any index that misses (out-of-range, or pointing at a skipped/non-exported symbol entry) yields a `nil` `*Symbol`. The linker's XCOFF loader then dereferences that `nil` symbol directly, causing a crash. This mirrors the CVE's root cause — a relocation-referenced value taken from untrusted input and used before being validated — even though the concrete failure mode here is a nil dereference rather than a raw OOB slice read.

### Finding Description
`internal/xcoff.NewFile` parses relocation entries for `.text`/`.data` sections and resolves each relocation's symbol via `idxToSym[int(rel.Rsymndx)]`, where `rel.Rsymndx` is a raw `uint32` taken directly from the file with no range/existence check against the map: [1](#0-0) 

`idxToSym` is populated only for symbol table entries that pass several filters (storage class, `numaux` bounds, section-number bounds, string-table offset validity); any symbol index that fails these checks (`goto skip`) or that lies outside `[0, nsyms)` is never inserted into the map: [2](#0-1) 

Consequently `reloc.Symbol` can legitimately be `nil` for a crafted `Rsymndx`, with no validation performed by the reader before returning the `File`. The consumer, `cmd/link/internal/loadxcoff.Load` (used when the Go linker processes AIX XCOFF host object files, e.g. cgo-compiled `.o`/`.syso` files pulled into a build), iterates `sect.Relocs` and unconditionally dereferences `rx.Symbol`: [3](#0-2) 

A relocation with `Rsymndx` pointing at an unresolved/absent symbol index causes `rx.Symbol.Name` to panic with a nil-pointer dereference.

### Impact Explanation
This is a denial-of-service crash of the Go toolchain (`cmd/link`) triggered purely by feeding it a malformed/malicious XCOFF object file — analogous to the binutils bug where an unvalidated relocation field leads to invalid memory access. It does not grant code execution or data disclosure; the effect is a build-time panic, not exploitation of the built binary. Under Go's vulnerability policy this would sit at most on the PUBLIC track as a low-severity parser-robustness bug (crash on malformed input during `go build`/`go tool link`), not urgent, since it only affects `GOOS=aix` builds and requires supplying a crafted object file to the linker.

### Likelihood Explanation
The victim workflow is a normal `go build`/`go install` on `GOOS=aix` that links in a cgo object file or `.syso` file — such object files are commonly pulled from third-party packages/modules without being individually vetted for well-formed relocation tables. An attacker who can supply such an object (e.g., via a module dependency containing a crafted `.syso`/cgo archive) can trigger the crash when the victim builds with the standard toolchain, with no special privileges beyond publishing a package the victim chooses to build.

### Recommendation
In `internal/xcoff.NewFile`, validate `rel.Rsymndx` against `nsyms` and check that `idxToSym[...]` actually returned a symbol before assigning it to `reloc.Symbol`; return a parse error (`errorf`-style) instead of allowing a `nil` `Symbol`. In `cmd/link/internal/loadxcoff.Load`, add a defensive nil check on `rx.Symbol` before dereferencing `rx.Symbol.Name`, erroring out with a descriptive message (consistent with the existing `unknown relocation of type` error path) rather than panicking.

```go
package xcoff_test

import (
	"internal/xcoff"
	"os"
	"testing"
)

// TestMalformedRelocSymndx crafts a minimal XCOFF64 object whose single
// relocation entry references a symbol index that was never populated
// in idxToSym (e.g., index >= number of symbols, or an index for a
// symbol filtered out by the C_EXT/storage-class checks).
func TestMalformedRelocSymndx(t *testing.T) {
	data := buildCraftedXCOFF64WithBadRsymndx(t) // constructs header+section+bogus reloc
	f, err := os.CreateTemp(t.TempDir(), "bad.o")
	if err != nil {
		t.Fatal(err)
	}
	f.Write(data)
	f.Close()

	r, err := os.Open(f.Name())
	if err != nil {
		t.Fatal(err)
	}
	xf, err := xcoff.NewFile(r)
	if err != nil {
		t.Fatalf("unexpected parse error: %v", err)
	}
	for _, sect := range xf.Sections {
		for _, rel := range sect.Relocs {
			// Expectation (post-fix): Symbol must never be nil here.
			if rel.Symbol == nil {
				t.Fatalf("relocation has nil Symbol for Rsymndx pointing outside populated symbol map")
			}
		}
	}
}
```
Expected (current, vulnerable) behavior: `xcoff.NewFile` succeeds and returns a `Reloc` with `Symbol == nil`; passing this file to `cmd/link/internal/loadxcoff.Load` then panics with a nil-pointer dereference on `rx.Symbol.Name`. Expected (fixed) behavior: `NewFile` (or `Load`) returns an explicit error instead of a nil `Symbol`/panic.
