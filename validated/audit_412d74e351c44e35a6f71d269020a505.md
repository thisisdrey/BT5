### Title
Unsynchronized `triggerConstantContract` reads a live, concurrently-mutating repository, causing null-pointer crash on the RPC/HTTP query path - ([File: framework/src/main/java/org/tron/core/Wallet.java])

### Summary
`CVE-2021-46982` is a TOCTOU bug where the f2fs compression code obtains a page reference, releases the lock, and later dereferences the (possibly now-freed) page without re-checking, causing a kernel panic when a concurrent `truncate()` deletes the page. The same "check pointer, unlock, then blindly dereference" pattern exists in java-tron's constant-call (query) execution path: `Wallet.triggerConstantContract`/`callConstantContract` builds a **new, unsynchronized** `RepositoryImpl` on top of the live head snapshot and executes a full VM run with no coordination against the block-application thread that is concurrently mutating the very same underlying `SnapshotRoot`/`AccountStore`/`ContractStore`.

### Finding Description
`Wallet.triggerConstantContract()` first checks contract existence: [1](#0-0) 
then calls `callConstantContract`, which builds a fresh `TransactionContext`/`RepositoryImpl` directly from `StoreFactory.getInstance()` (i.e., the current live chain state, not a stable, isolated snapshot) and runs a `VMActuator`: [2](#0-1) 

This RPC-triggered execution is **not** synchronized with `Manager.pushBlock()`/`processBlock()`, which mutates `AccountStore`, `ContractStore`, and `CodeStore` in place while applying each transaction of a new block (including contract self-destructs via `RepositoryImpl.deleteContract`, which deletes code, account and contract entries): [3](#0-2) 

Inside `VMActuator.call()`, several places fetch an `AccountCapsule`/`ContractCapsule` and *immediately* dereference it without a null check, exactly mirroring the kernel bug's "get pointer → unlock → dereference without re-check":

- `AccountCapsule caller = rootRepository.getAccount(callerAddress);` is passed straight into `getTotalEnergyLimit`, and if `creator` is non-null, `getTotalEnergyLimitWithFixRatio`/`WithFloatRatio` immediately call `creator.getAddress()`/`creator.getBalance()` with no null guard: [4](#0-3) 
- The contract lookup at the top of `create()`/`call()` (`rootRepository.getContract`/`getAccount`) happens once, but the *inner* helper `getTotalEnergyLimitWithFixRatio` re-fetches the contract a second time via `rootRepository.getContract(contract.getContractAddress().toByteArray())` and immediately calls `contractCapsule.getConsumeUserResourcePercent(...)` without checking for null: [5](#0-4) 

Because `Wallet.triggerConstantContract` and `Manager.pushBlock`/`processBlock` run on independent thread pools (gRPC/JSON-RPC worker threads vs. the net/block-processing thread) with no shared lock, a witness broadcasting a block that self-destructs/deletes a contract (or an account) can race with an unprivileged client's `triggerConstantContract`/`triggerContract` (JSON-RPC `eth_call`) request for the same address. The initial existence check in `Wallet.triggerContract`/`triggerConstantContract` passes, but by the time the second, unguarded `getContract`/`getAccount` call executes inside `VMActuator`, the block-processing thread has already removed the row from `ContractStore`/`AccountStore`, so the second fetch returns `null` and the immediate field access throws an unhandled `NullPointerException`.

### Impact Explanation
An unhandled `NullPointerException` thrown mid-VM-execution on the RPC serving thread is not one of the caught exception types listed in `callContract`'s catch blocks in `RpcApiService`/`TronJsonRpcImpl` for a clean, generic `RuntimeException`-style response — however, more importantly, this same code path is reachable via any public read query (`triggerConstantContract`, `triggerContract`, JSON-RPC `eth_call`, and the PBFT servlet variant), and any unprivileged client can trigger it repeatedly and cheaply (constant calls have no on-chain fee/energy cost to the caller, no transaction broadcast needed) by simply calling a contract that a witness is expected to self-destruct/replace in an upcoming block, or by racing ordinary account deletions from concurrent block application. Because this executes on shared executor thread pools servicing all gRPC/HTTP/JSON-RPC clients, sustained triggering can degrade or crash worker threads handling the node's public query API, denying service to other API consumers (matches "an API the node can no longer serve").

### Likelihood Explanation
Exploitation requires only two ordinary, unprivileged actions happening close in time: (1) any contract's SELFDESTRUCT/CREATE2 redeploy or normal account deletion being processed in a new block, and (2) a `triggerConstantContract`/`eth_call` request for the same address arriving on an RPC thread while that block is being applied. Both are attacker-controllable — an attacker can deploy a self-destructing contract and simultaneously flood the constant-call API for its address — making the race easy to hit repeatedly, similar in spirit to how `pos_fsstress` in the original report reliably triggered the kernel race through concurrent syscalls.

### Recommendation
- Make `callConstantContract`/`VMActuator` execute against an immutable, isolated snapshot (e.g. build/borrow a dedicated `ISession`/`Snapshot` for the duration of the constant call) rather than the live root store shared with block application.
- Add null checks after every second/subsequent `getAccount`/`getContract` fetch inside `VMActuator` (`getTotalEnergyLimitWithFixRatio`, `getTotalEnergyLimitWithFloatRatio`, `call()`, `create()`), failing with a `ContractExeException`/`ContractValidateException` instead of allowing an NPE to propagate.
- Ensure `Wallet.triggerConstantContract`/`triggerContract` catch and translate `NullPointerException` (and other `RuntimeException`s arising mid-VM-execution) into a proper `CONTRACT_EXE_ERROR` response instead of letting it escape uncaught on shared RPC worker threads.

### Proof of Concept
1. Deploy contract `C` with a `kill()` function that calls `selfdestruct`.
2. Concurrently:
   - Thread A: broadcast a transaction calling `C.kill()` so that a subsequent block deletes `C`'s entries from `AccountStore`/`ContractStore`/`CodeStore` via `RepositoryImpl.deleteContract` during `Manager.processBlock`.
   - Thread B: repeatedly call gRPC `triggerConstantContract`/JSON-RPC `eth_call` against address `C` in a tight loop.
3. When Thread B's call lands between the block-processing thread's `deleteContract` calls (which touch multiple stores non-atomically w.r.t. an external unsynchronized reader) and the follow-up internal `getContract`/`getAccount` fetch inside `VMActuator.getTotalEnergyLimitWithFixRatio`/`WithFloatRatio`, the second lookup returns `null` and the subsequent `creator.getAddress()`/`getBalance()` call throws an uncaught `NullPointerException` on the RPC worker thread, mirroring the f2fs `find_lock_page()` returning `NULL` after the concurrently truncated page was already unlocked and referenced.
