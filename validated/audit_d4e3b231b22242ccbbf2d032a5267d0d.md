Based on the code paths and fee schedule, this claim does not hold up.

**Analysis:**

The premise requires a receipt sized "just below `size_upper_bound` (100kB)" to be created with "cheap FunctionCall" wasm gas, such that the extra `pop_back`+`push_back` TrieQueue churn in `ReceiptGroupsQueue::update_on_receipt_pushed` (`core/store/src/trie/outgoing_metadata.rs:275-314`) dominates the charged gas. This is false because receipt size for a `FunctionCall` action is driven almost entirely by `method_name` + `args` bytes, and those bytes are already charged at `action_function_call_per_byte` rates via `pay_action_per_byte` at promise-creation time [1](#0-0) , invoked directly from `promise_batch_action_function_call_weight` [2](#0-1) .

With `function_call_cost_per_byte` at roughly 2,235,934 gas/byte for both `send_sir` and `execution` [3](#0-2) , a receipt with ~100,000 bytes of args/method-name costs roughly 2 × 2.24M × 100,000 ≈ 447 billion gas in prepaid+burnt fees just from the per-byte action fee — before the base `function_call_cost` and `new_action_receipt` fees are even added. This is charged to the calling contract's attached gas at creation time, satisfying "metering totality": the cost is incurred and burnt/prepaid before the receipt is buffered.

By contrast, the extra work in `update_on_receipt_pushed` when `should_start_new_group` triggers a new group is a small, bounded number of additional trie reads/writes (one extra `pop_back`/`push_back` pair on the `ReceiptGroupsQueue`, storing a small fixed-size `ReceiptGroup` record) [4](#0-3) . This is O(1) additional trie IO per receipt — dwarfed by the ~447 billion gas already charged for producing a receipt large enough to trigger the churn in the first place.

Since a chunk's total gas limit caps overall receipt production (~1000 Tgas), and each 100kB-sized `FunctionCall` receipt already consumes on the order of hundreds of billions of gas due to existing per-byte action fees [5](#0-4) , an attacker cannot cheaply mass-produce many such maximally-churning receipts — the cost scales with receipt size exactly as intended by the fee schedule, not "near-free." The `outgoing_metadatas.update_on_receipt_pushed` call site in `buffer_receipt` [6](#0-5)  only runs once per buffered receipt regardless of group churn pattern, and `ReceiptGroupsConfig::should_start_new_group` bounds group size to ~100kB by design, which is a data-structure optimization for bandwidth-request generation, not a bypass of gas accounting [7](#0-6) .

/// A helper function to pay per byte gas fee for batching an action.
pub fn pay_action_per_byte(
    gas_counter: &mut GasCounter,
    fees_config: &RuntimeFeesConfig,
    action: ActionCosts,
    num_bytes: u64,
    sir: bool,
) -> Result<()> {
    let per_byte_fee = fees_config.fee(action);
    let burn_cost =
        per_byte_fee.send_fee(sir).checked_mul(num_bytes).ok_or(HostError::IntegerOverflow)?;
    let use_gas = burn_cost
        .gas
        .checked_add(
            per_byte_fee.exec_fee().gas.checked_mul(num_bytes).ok_or(HostError::IntegerOverflow)?,
        )
        .ok_or(HostError::IntegerOverflow)?;
    gas_counter.pay_action_accumulated(burn_cost, use_gas, action)
}

    pub fn should_start_new_group(
        &self,
        last_group: &ReceiptGroup,
        new_receipt_size: ByteSize,

        let mut group_size = last_group.size();
        add_size_checked(&mut group_size, new_receipt_size);

            // The new group would be too large, start a new group.
            return true;

        add_gas_checked(&mut group_gas, new_receipt_gas);
        if group_gas > self.gas_upper_bound.as_gas().into() {
            // The new group would have too much gas, start a new group.
            return true;
        }

        false
    }
