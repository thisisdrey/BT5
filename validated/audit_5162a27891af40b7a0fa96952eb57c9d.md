### Title
Stale in-memory cache not invalidated on `RepositoryImpl.deleteContract()` can resurrect a deleted contract/account/code on commit - ([File: actuator/src/main/java/org/tron/core/vm/repository/RepositoryImpl.java])

### Summary
`RepositoryImpl.deleteContract()` deletes an address's records directly from the underlying `AccountStore`, `CodeStore`, and `ContractStore`, but never removes or invalidates the corresponding entries in the repository's own in-memory `accountCache`, `codeCache`, and `contractCache` maps that back all reads/writes performed during transaction execution. This is the same class of bug as CVE-2023-21255 (use of a stale/freed object reference after its "container" object was released): the deletion path frees the persistent record while a live, cached in-memory object referencing the same key remains reachable and gets written back on `commit()`. [1](#0-0) 

### Finding Description
`deleteContract(address)` is implemented as:
```
getCodeStore().delete(address);
getAccountStore().delete(address);
getContractStore().delete(address);
``` [1](#0-0) 

This bypasses the `accountCache`, `codeCache`, and `contractCache` `HashMap`s that `RepositoryImpl` maintains for the duration of a transaction/contract-creation context [2](#0-1) . All normal reads (`getAccount`, `getContract`) populate these caches and return cached copies on subsequent reads within the same execution [3](#0-2) [4](#0-3) . On `commit()`, `commitAccountCache`/`commitCodeCache`/`commitContractCache` iterate the caches and write back any entry whose `Value.Type` is `CREATE` or `DIRTY`, regardless of whether the record was subsequently deleted at the store layer: [5](#0-4) 

If, within the same execution context, the address was read/created/marked dirty before `deleteContract()` is invoked (e.g., during contract-creation processing that populates `accountCache`/`contractCache`/`codeCache` for the newly created address), the direct store-level delete has no effect on those cache entries. On `commit()` the stale cached object is flushed back to the underlying store, effectively resurrecting the account/contract/code that `deleteContract` was supposed to permanently remove.

`deleteContract` is exposed through the `Repository` interface and reachable from `ContractState` (used by every TVM execution context) [6](#0-5) , and is invoked from `TransactionTrace` to roll back a contract when its constructor/init fails during `TRX_CONTRACT_CREATION_TYPE` handling [7](#0-6)  — a path directly reachable by any unprivileged smart-contract deployer who can craft a contract whose constructor is designed to fail after account/code state has already been cached.

### Impact Explanation
If exploitable end-to-end, an attacker-controlled contract-creation transaction could cause the node to persist an account, contract bytecode, or contract record that the rollback logic intended to erase. Depending on which cached fields survive the write-back, this could result in:
- An "unbacked" balance/account state being retained after a supposedly failed/rolled-back deployment.
- Contract code/`ContractCapsule` metadata persisting for an address that should not exist, which downstream code (energy metering, `isContractExist` checks, TVM dispatch) may treat as a valid deployed contract.
This falls under "unbacked balance" / "unauthorized account operation" impact categories.

### Likelihood Explanation
Medium confidence. I confirmed the root-cause mechanism precisely (deletion bypasses the cache, and `commit()` unconditionally flushes dirty/create cache entries) with exact file/line evidence. However, I could not fully trace the exact ordering of cache population vs. `deleteContract()` invocation inside `TransactionTrace`'s contract-creation-failure path within the available tool budget, so I cannot certify that a cache entry is always populated before the delete call in every current call site. This uncertainty should be resolved by direct code review of `TransactionTrace`'s use of `deleteContract` (the read cut off before the call site's surrounding logic could be inspected).

### Recommendation
Make `deleteContract()` also evict (or mark as a tombstone/DELETE type) the corresponding entries in `accountCache`, `codeCache`, and `contractCache`, and ensure `commitAccountCache`/`commitCodeCache`/`commitContractCache` treat a deleted key as an explicit delete against the target store/parent deposit rather than skipping it. Add a regression test that: (1) triggers a path where an address is read/cached, (2) calls `deleteContract` on that address, (3) commits, and (4) asserts the address is absent from the account/code/contract stores.

### Proof of Concept
Conceptual (not fully verified against exact `TransactionTrace` call ordering):
1. Deploy a contract via `TriggerSmartContract`/`CreateSmartContract` whose constructor performs an operation that causes the newly created account/contract to be read into `RepositoryImpl`'s `accountCache`/`contractCache` (e.g., a `CALL`/self-reference or delegate-resource-style access) before reverting/failing.
2. Constructor execution fails, triggering `TransactionTrace`'s cleanup path that calls `Repository.deleteContract(newContractAddress)`.
3. Because `deleteContract` only deletes from the underlying stores and not the caches, the previously cached `CREATE`/`DIRTY` entries for that address remain in `accountCache`/`contractCache`/`codeCache`.
4. On `commit()`, `commitAccountCache`/`commitContractCache`/`commitCodeCache` write the stale cached entries back to the store, resurrecting the account/contract despite the deployment having "failed."

Due to index size limits, the full body of `TransactionTrace.java` around the `deleteContract` call site could not be retrieved in this session; a Devin session with full repository access is recommended to confirm the exact call-site ordering and validate the PoC against a running node.

  private void commitAccountCache(Repository deposit) {
    accountCache.forEach((key, value) -> {
      if (value.getType().isCreate() || value.getType().isDirty()) {
        if (deposit != null) {
          deposit.putAccount(key, value);
        } else {
          getAccountStore().put(key.getData(), new AccountCapsule(value.getValue()));
        }
      }
    });
  }

  private void commitCodeCache(Repository deposit) {
    codeCache.forEach(((key, value) -> {
      if (value.getType().isDirty() || value.getType().isCreate()) {
        if (deposit != null) {
          deposit.putCode(key, value);
        } else {
          getCodeStore().put(key.getData(), new CodeCapsule(value.getValue()));
        }
      }
    }));
  }

  private void commitContractCache(Repository deposit) {
    contractCache.forEach(((key, value) -> {
      if (value.getType().isDirty() || value.getType().isCreate()) {
        if (deposit != null) {
          deposit.putContract(key, value);
        } else {
          ContractCapsule contractCapsule = new ContractCapsule(value.getValue());
          if (!abiStore.has(key.getData())) {
            abiStore.put(key.getData(), new AbiCapsule(contractCapsule));
          }
          getContractStore().put(key.getData(), contractCapsule);
        }
      }
    }));
  }
