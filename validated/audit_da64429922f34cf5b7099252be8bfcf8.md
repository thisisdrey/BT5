### Title
Attacker can permanently fill a victim's per-account token list via dust `deposit(..., onBehalfOf_)`, freezing them out of all new collateral and debt positions - (File: contracts/Pool.sol)

### Summary
`DepositToken.deposit` accepts an arbitrary `onBehalfOf_` recipient and mints msdTOKEN to them, which registers the token in the victim's `depositTokensOfAccount` list via `Pool.addToDepositTokensOfAccount`. That list is hard-capped at `MAX_TOKENS_PER_USER = 30` combined debt + deposit entries. An unprivileged attacker can dust-deposit 1 wei of every listed collateral `onBehalfOf` any victim, filling all 30 slots and causing every subsequent `addToDepositTokensOfAccount` / `addToDebtTokensOfAccount` for that account to revert with `UserReachedMaxTokens`.

### Finding Description
- `DepositToken.deposit(amount_, onBehalfOf_)` pulls underlying from the caller but mints to `onBehalfOf_` (contracts/DepositToken.sol:211-237).
- `_mint` calls `pool.addToDepositTokensOfAccount(account_)` whenever the recipient's balance goes 0 → >0 (contracts/DepositToken.sol:486-488).
- `Pool.addToDepositTokensOfAccount` enforces `onlyIfAdditionWillNotReachMaxTokens`, reverting once `debtTokensOfAccount.length + depositTokensOfAccount.length >= 30` (contracts/Pool.sol:143-148, 216-220). The same cap applies to `addToDebtTokensOfAccount` (contracts/Pool.sol:204-208).
- Because `onBehalfOf_` is attacker-chosen and unrestricted, the attacker spends ~30 dust deposits of underlying (e.g., 1 wei each of USDC, WETH, MET, vaTokens, etc., scaled up if `depositFee > 0` so at least 1 wei of msdTOKEN is minted) to permanently occupy all slots of any EOA or contract victim.

### Impact Explanation
Once the victim's list is saturated:
- Any `transfer`/`transferFrom`/`seize`/`deposit onBehalf` of a deposit token the victim doesn't already hold reverts in `addToDepositTokensOfAccount` — no new collateral types can ever reach the account.
- Any `DebtToken.issue`/`flashIssue` of a synthetic the victim doesn't hold reverts in `addToDebtTokensOfAccount` — the victim can no longer open any new borrowing position.
- Same-transaction griefing: an attacker can front-run a victim's first borrow or a liquidator's `liquidate` and brick the transaction (`seize` calls `_transfer`, which reverts when the liquidator's list is full), temporarily freezing liquidation liveness for targeted liquidators.

This is a direct availability break — the analog of the JavaFX availability DoS — that requires only a public entry point and negligible attacker capital.

### Likelihood Explanation
- Fully permissionless: `deposit` has no allowlist on `onBehalfOf_`; no governor, oracle, or privileged role needed.
- Cost is bounded by ~30 dust transfers of underlying collateral already listed in the pool.
- It is recoverable per-slot (the victim can `transfer` the dust away or `withdraw` it, calling `removeFromDepositTokensOfAccount` at contracts/DepositToken.sol:523-525), so the freeze persists only until the victim manually clears slots — a temporary freezing of position management, not of existing withdrawable funds. Impact is therefore a griefing/DoS, not theft.

### Recommendation
- In `DepositToken.deposit`, require `onBehalfOf_ == _msgSender()` for new tokens, or let `addToDepositTokensOfAccount` fail-open for dust additions (e.g., skip list registration below a minimum deposit threshold and exclude unregistered tokens from `depositOf`).
- Alternatively, enforce a non-zero `minDeposit` so that registering a token slot costs meaningful capital, making the 30-slot fill attack economically irrational.

### Proof of Concept
Hardhat/Foundry fork sketch:

```solidity
// Fork mainnet Pool with N listed deposit tokens; victim = fresh EOA
for (uint i; i < pool.getDepositTokens().length && i < 30; ++i) {
    IDepositToken dt = IDepositToken(pool.getDepositTokens()[i]);
    IERC20 underlying = dt.underlying();
    deal(address(underlying), attacker, 1e6); // or amount covering depositFee
    underlying.approve(address(dt), 1e6);
    dt.deposit(1e6, victim); // mints dust msdTOKEN to victim, fills a slot
}
assertEq(pool.getDepositTokensOfAccount(victim).length, 30); // plus any debt tokens

// Victim now cannot borrow a synth they don't already hold:
vm.prank(victim);
vm.expectRevert(Pool.UserReachedMaxTokens.selector);
debtTokenMsETH.issue(1e18, victim); // addToDebtTokensOfAccount reverts

// And cannot receive a new collateral type (none left, but transfers of any
// token victim doesn't hold also revert via _transfer -> addToDepositTokensOfAccount)
```

Validation caveat: with `depositFee > 0` the attacker must deposit enough so `_deposited > 0` mints (contracts/DepositToken.sol:229-234); check deployed `FeeProvider.depositFee()` on the forked chain.
