### Title
Auth-gated `broadcast` flag is not enforced at relay time — unauthenticated `/v3/blocks` POST still triggers peer relay - (File: stackslib/src/net/api/postblock_v3.rs)

### Summary
The 401 check in `try_parse_request` only fires when the client explicitly sets `broadcast=1`; a request with no query string defaults `broadcast` to `false` and completely skips the `if broadcast && !authenticated` gate. Critically, `try_handle_request` never re-checks `self.broadcast` before deciding to relay: it queues the block for peer gossip solely based on `data_resp.accepted`, so an unauthenticated, non-broadcast submission that is accepted into chainstate is relayed to peers exactly as if it had been an authenticated `broadcast=1` request.

### Finding Description
`try_parse_request` computes `broadcast` from `form_urlencoded::parse(query.as_ref().unwrap_or(&"").as_bytes())`, defaulting to `false` when no query string is present, and the authorization check is short-circuited by `if broadcast && !authenticated` [1](#0-0) . This is consistent with the stated design intent of "store locally without auth, only gate broadcast," since `self.broadcast` is passed as a parameter into `Relayer::process_new_nakamoto_block_ext` [2](#0-1) .

However, in `try_handle_request`, the decision to actually queue the block for network relay does not consult `self.broadcast` at all — it is driven purely by `data_resp.accepted`:
```rust
if data_resp.accepted {
    node.set_relay_message(StacksMessageType::NakamotoBlocks(NakamotoBlocksData {
        blocks: vec![block],
    }));
}
``` [3](#0-2) 

This means the outcome the auth gate was supposed to prevent — an unauthenticated caller causing this node to gossip a block to its peers — happens anyway whenever the posted block is accepted, regardless of whether `broadcast` was `1` or absent/`0`. The `broadcast` value only affects what `process_new_nakamoto_block_ext` itself does internally with the block (its acceptance semantics), not whether the resulting accepted block is queued for relay in this handler.

Note: whether the underlying block passes chainstate/consensus validation (e.g., signer-signature checks in `accept_block`/`process_new_nakamoto_block_ext`) is out of scope per the audit rules (consensus block-validation internals), so this finding does not claim forged/invalid blocks can be relayed — only that a *valid* block posted without authentication is relayed exactly as an authenticated broadcast request would be, defeating the purpose of the `authorization` gate that operators configure specifically to control who can make their node push new blocks onto the network.

### Impact Explanation
Any unprivileged remote party who can reach the RPC port can POST a validly-signed Nakamoto block (e.g., one they observed elsewhere but the target node has not yet received) to `/v3/blocks/upload/` with no query string and no `authorization` header. If the block is accepted into chainstate, the node will still call `node.set_relay_message(...)`, causing it to gossip the block onward to its own peers — the exact action the `authorization`/`broadcast=1` gate exists to restrict to authenticated callers. This is a logic flaw that breaks the intended access-control boundary between "store for my own state" and "use my node to push data to the network," even though it does not enable forging invalid data.

### Likelihood Explanation
No privileged role or secret is needed — only remote RPC reachability and possession of (or access to) an already-valid, correctly-signed Nakamoto block, which is realistically obtainable by any node operator monitoring the network. The attack is repeatable per accepted block and costs only one HTTP POST.

### Recommendation
In `try_handle_request`, gate the `node.set_relay_message(...)` call on `self.broadcast == Some(true)` in addition to `data_resp.accepted`, so that relay behavior actually matches the authenticated `broadcast` intent established in `try_parse_request`.

### Proof of Concept
Rust net test: construct an `HttpRequestPreamble` for `POST /v3/blocks/upload/` with no query string and no `authorization` header, and a well-formed, validly-signed `NakamotoBlock` as the octet-stream body. Call `try_parse_request` to confirm `handler.broadcast == Some(false)` and no 401 is returned. Then drive `try_handle_request` against a `StacksNodeState` where the block is accepted, and assert that `node.get_relayer_stats()`/relay-message queue is non-empty (i.e., `set_relay_message` was invoked) even though `self.broadcast` was `false` and no authentication was supplied — demonstrating the disconnect between the auth-gated `broadcast` flag and the actual relay trigger at [4](#0-3) .
