This confirms the claim. The `DeliveryReceipt` struct decoded from the Ethereum `InboundMessageDispatched` event explicitly includes a `success: bool` field [1](#0-0) , populated directly from the decoded Solidity event log [2](#0-1) . Audit Report

## Title
Outbound queue v2 pays relayer reward and settles pending orders while ignoring the delivery receipt's `success` field - (File: `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs`)

## Summary
`Pallet::process_delivery_receipt` decodes a `DeliveryReceipt` that includes an explicit `success: bool` field sourced from the Ethereum Gateway's `InboundMessageDispatched(nonce, topic, success, reward_address)` event, but never inspects this field before paying the relayer reward and permanently removing the `PendingOrders` entry. As a result, a relayer reward is paid and the pending order is deleted even when the underlying command execution on Ethereum failed (`success == false`).

## Finding Description
`submit_delivery_receipt` verifies the event log/proof pair via `T::Verifier::verify`, decodes it into a `DeliveryReceipt` via `DeliveryReceipt::try_from`, and calls `process_delivery_receipt` [4](#0-3) . The `DeliveryReceipt` type and its `TryFrom<&Log>` decode logic explicitly capture the Solidity event's `success` boolean into `DeliveryReceipt.success` [5](#0-4) .

`process_delivery_receipt` only checks `receipt.gateway == T::GatewayAddress::get()`, resolves the reward account, fetches the `PendingOrders` entry by `receipt.nonce`, and — if `order.fee > 0` — calls `T::RewardPayment::register_reward` before unconditionally calling `<PendingOrders<T>>::remove(nonce)` and emitting `Event::MessageDelivered` [3](#0-2) . The decoded `receipt.success` value is never read anywhere in this function or in `submit_delivery_receipt`. Since the Gateway emits `InboundMessageDispatched` with `success` reflecting the actual outcome of the dispatched command (not solely on success), any relayer can obtain a valid proof for a failed dispatch and still trigger reward payment and permanent removal of the pending order's bookkeeping.

## Impact Explanation
Because `PendingOrders` is the sole on-chain bookkeeping used to reconcile outbound message delivery and fee settlement, ignoring `receipt.success` means a failed cross-chain command execution is treated identically to a successful one: the relayer is paid `order.fee` via `T::RewardPayment::register_reward`, and the order record is deleted with no remaining trace that the corresponding command never actually executed. This is a duplicate/incorrect settlement of bridge reward funds and an unrecoverable loss of the chain's own record of an outstanding delivery obligation — matching the "duplicate settlement or payout" and "permanent user-fund or bridge-state lock" impact categories for Snowbridge/BridgeHub scope.

## Likelihood Explanation
`submit_delivery_receipt` requires only `ensure_signed(origin)` [6](#0-5) , meaning any unprivileged, unpermissioned account can submit a receipt as long as they can produce a valid log/proof pair — the same tooling any legitimate relayer already uses. Since the Gateway contract itself is documented to emit `success` as a first-class parameter of `InboundMessageDispatched`, any dispatch that fails on Ethereum but still logs this event (which is the entire purpose of the field) is directly exploitable without any privileged access, compromised relayer assumption, or off-chain infrastructure control.

## Recommendation
In `process_delivery_receipt`, branch on `receipt.success`: only call `T::RewardPayment::register_reward` and `<PendingOrders<T>>::remove(nonce)` when `receipt.success == true`. On `receipt.success == false`, either retain the `PendingOrder` for retry, or move it to a distinct failure-settlement path (e.g., refund logic) that does not pay a relayer reward, and emit a distinct event (e.g., `Event::MessageDeliveryFailed`) rather than `Event::MessageDelivered`.

## Proof of Concept
1. A message is enqueued via `do_process_message`, creating a `PendingOrders[nonce]` entry with `fee > 0` [7](#0-6) .
2. On Ethereum, the corresponding command dispatch reverts/fails, and the Gateway emits `InboundMessageDispatched(nonce, topic, success=false, reward_address)`.
3. Any account obtains a valid proof for this log and calls `submit_delivery_receipt(origin, event)`; `T::Verifier::verify` succeeds because the log itself is authentic, and `DeliveryReceipt::try_from` decodes `success: false` into the struct.
4. `process_delivery_receipt` never checks `receipt.success`, so it pays `order.fee` to the reward account via `register_reward` and calls `<PendingOrders<T>>::remove(nonce)`, settling and rewarding a failed delivery as if it had succeeded — a unit test asserting `PendingOrders::get(nonce)` is `None` and the reward was registered after submitting a receipt with `success: false` would confirm this.

				// Pay relayer reward

					&reward_account,

					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });
