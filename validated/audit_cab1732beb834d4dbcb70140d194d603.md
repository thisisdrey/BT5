### Title
Neighbor-of-neighbor `HandshakeAccept` public key is trusted without verifying it matches the advertised `NeighborAddress.public_key_hash` - (File: stackslib/src/net/neighbors/walk.rs)

### Summary
In the neighbor-walk protocol, when the local node asks a peer for its neighbors (`GetNeighbors`) and then attempts to handshake with each reported `NeighborAddress`, the resulting `HandshakeAccept` should be validated so that the public key returned by the socket actually corresponds to the public-key-hash advertised in the gossiped `NeighborAddress`. This check exists in one code path (`pingback_handshakes_try_finish`) but is missing in the sibling path (`neighbor_handshakes_try_finish` / `handle_neighbor_handshake_accept`), mirroring the `decodeData.payer` vs `msg.sender` equality that was never enforced in the D3Proxy report.

### Finding Description
`NeighborWalk::pingback_handshakes_try_finish` explicitly checks the identity of a peer that replies to a handshake before trusting/storing it: [1](#0-0) [2](#0-1) 

This function computes `Hash160::from_node_public_key_buffer(&data.handshake.node_public_key)` and rejects the reply if it doesn't equal `naddr.public_key_hash` — i.e., it enforces that the public key returned in the `HandshakeAccept` is the one that was actually being contacted, not an arbitrary key an attacker could supply.

However, the analogous path for handshaking with **neighbors-of-neighbors** (`neighbor_handshakes_begin`/`neighbor_handshakes_try_finish`) does not perform this same check before calling `handle_neighbor_handshake_accept`: [3](#0-2) [4](#0-3) 

Here, `naddr` (the `NeighborAddress` gossiped to us by `cur_neighbor` in a prior `Neighbors` reply) is passed straight to `handle_neighbor_handshake_accept`, which immediately calls `self.neighbor_db.add_or_schedule_replace_neighbor(network, preamble, &data.handshake, db_data, ...)` using `data.handshake.node_public_key` — the self-reported key from the `HandshakeAccept` payload — without ever comparing `Hash160::from_node_public_key(&data.handshake.node_public_key)` against `naddr.public_key_hash`. My tool budget was exhausted before I could open `stackslib/src/net/neighbors/db.rs::add_or_schedule_replace_neighbor` to confirm exactly which fields get persisted to the `PeerDB`, so I cannot fully rule out that some downstream check re-derives and compares the address; based on the grep results, `check_handshake_pubkey_hash` appears exactly twice in `walk.rs` (its definition and its one call site in `pingback_handshakes_try_finish`), meaning it is not invoked anywhere in the `neighbor_handshakes_*` code path.

### Impact Explanation
If confirmed (pending the `add_or_schedule_replace_neighbor` review noted above), this breaks the equality "authenticated public key == the identity claimed for this connection," analogous to the D3Proxy `decodeData.payer` vs `msg.sender` check. A remote peer (`cur_neighbor`) that we already trust enough to walk can report attacker-chosen `NeighborAddress` entries (IP:port + arbitrary `public_key_hash`); when the local node subsequently connects to that IP:port and gets a `HandshakeAccept` back, the code stores whatever public key came back in the accept without confirming it matches the pubkey hash it originally set out to reach. This could let a malicious relay/neighbor steer entries in the local node's `PeerDB`/frontier toward keys/identities that were never verified against the gossiped hash, i.e. non-canonical peer data served/stored as canonical — matching the High-impact category "steering a node off the tip via false inventory" / storing unauthenticated data as authenticated.

### Likelihood Explanation
Reaching this code path only requires being (or controlling) a neighbor that the victim node is willing to walk, and returning a `Neighbors` message containing crafted `NeighborAddress` entries plus responding to the resulting handshake — no privileged key or admin role is required, matching remote/unprivileged reachability.

### Recommendation
Add the same `check_handshake_pubkey_hash`-style validation in `handle_neighbor_handshake_accept` (or immediately before it is invoked in `neighbor_handshakes_try_finish`), rejecting any `HandshakeAccept` whose `Hash160::from_node_public_key(&data.handshake.node_public_key)` does not equal `naddr.public_key_hash`, exactly as is already done for the pingback path.

### Proof of Concept
Conceptual (not executed, due to no filesystem/test access in this mode):
1. Run a malicious/compromised neighbor `cur_neighbor`.
2. When queried via `GetNeighbors`, return a `NeighborAddress` pointing at an IP:port the attacker controls, with an arbitrary `public_key_hash`.
3. The victim node's `NeighborWalk` proceeds to `neighbor_session_begin`/handshake against that address; the attacker's listener replies with a `HandshakeAccept` signed by a completely different keypair than the advertised `public_key_hash`.
4. `handle_neighbor_handshake_accept` accepts this without comparing keys and calls `add_or_schedule_replace_neighbor`, storing/scheduling the attacker's actual key/identity into the victim's neighbor frontier/PeerDB — unlike the pingback path, which would have rejected the mismatch via `check_handshake_pubkey_hash`.

Confirmation of the exact downstream persistence effects in `add_or_schedule_replace_neighbor` (`stackslib/src/net/neighbors/db.rs`) could not be completed within the available tool budget; further review of that function is recommended before treating this as fully proven.

    /// Does a given handshakedata represent an expected public key hash?
    fn check_handshake_pubkey_hash(
        nk: &NeighborKey,
        data: &HandshakeAcceptData,
        naddr: &NeighborAddress,
    ) -> bool {
        let neighbor_pubkey_hash =
            Hash160::from_node_public_key_buffer(&data.handshake.node_public_key);
        if neighbor_pubkey_hash != naddr.public_key_hash {
            debug!(
                "Neighbor {:?} had an unexpected pubkey hash: expected {:?} != {:?}",
                nk, &naddr.public_key_hash, &neighbor_pubkey_hash
            );
            return false;
        }

        true
    }
