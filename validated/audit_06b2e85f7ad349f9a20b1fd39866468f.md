### Title
Forced dust deposits permanently occupy per-account token slots and can freeze a victim's ability to add new collateral or debt — (`contracts/Pool.sol`)

### Summary
The external report (CVE-2018-13420) is a "leak" class issue: registration entries (`MallocExtension::Register`/`InitModule`) are allocated and never released. The Metronome analog is the per-account registration sets `depositTokensOfAccount` / `debtTokensOfAccount` in `Pool`, backed by `MappedEnumerableSet`. Entries are only ever released when the account's token balance returns to exactly `0` — i.e., they are retained for as long as a nonzero balance exists. Because `DepositToken.deposit(amount, onBehalfOf)` accepts an arbitrary beneficiary and `DepositToken.transfer/transferFrom` are public ERC-20 paths, any unprivileged attacker can force-add dust entries to a victim's list until it reaches `MAX_TOKENS_PER_USER`, after which `onlyIfAdditionWillNotReachMaxTokens` makes every new token-type addition for that account revert.

### Finding Description
`Pool.addToDepositTokensOfAccount` is gated by `onlyIfAdditionWillNotReachMaxTokens(account_)`, which reverts `UserReachedMaxTokens` when `debt + deposit` list length hits the cap (Pool.sol:143-148, 216-220). The only place entries are removed is `removeFromDepositTokensOfAccount`, invoked from `DepositToken._burn` / `DepositToken._transfer` exclusively when the balance becomes `0` (DepositToken.sol:460-462, 523-525). Symmetrically for debt tokens (DebtToken.sol:540-542, 598-600).

Two attacker-reachable add paths exist:
- `DepositToken.deposit(amount_, onBehalfOf_ = victim)` — public, `whenNotPaused`, no beneficiary consent check; `_mint` calls `pool.addToDepositTokensOfAccount(victim)` on first receipt (DepositToken.sol:211-237, 486-488).
- `DepositToken.transfer(victim, dust)` / `seize` during liquidation — `_transfer` adds the token to the recipient's list when the recipient's prior balance is `0` (DepositToken.sol:518-520).

The attacker cycles through every whitelisted deposit token (and, for maximum pressure, holds tiny residual balances so the entry never self-cleans), filling the victim's set. Once at cap, the victim cannot deposit a collateral type they don't already hold, cannot `issue`/`mint` a new synthetic debt token (`addToDebtTokensOfAccount` reverts), and any liquidation `seize` that would add a new token to the liquidator's account is unaffected — but the victim's account is stuck.

The victim can free a slot only by driving the dust balance to `0` via `transfer` or `withdraw`, both of which require `unlockedBalanceOf >= amount` (`_revertIfLocked`, DepositToken.sol:180-182, 383-398). If the victim's position is healthy, cleanup is possible but the attacker can re-fill slots in a griefing loop (each refill costs the attacker underlying dust, which is routed to the Treasury at DepositToken.sol:226). If the victim's position is unhealthy (`_issuableInUsd == 0` → unlocked balance `0`), the dust entries cannot be removed at all — matching the CVE's "retained forever" pattern — though in that state the account is already liquidatable.

### Impact Explanation
Temporary freezing of protocol funds/functionality: while at the cap, every code path that would add a new token to the victim's account reverts — new-collateral deposits, new synthetic issuance, and leverage flows through `SmartFarmingManager`/`DebtToken.mint`. Existing collateral remains withdrawable as long as it is unlocked, so this is not permanent theft; severity tracks the CVE's disputed-medium profile rather than a full loss-of-funds bug.

### Likelihood Explanation
Attack cost is one dust deposit (or dust transfer of already-held msdTOKEN) per slot — bounded by `MAX_TOKENS_PER_USER` and the number of whitelisted deposit/debt tokens. No privileged role, oracle manipulation, or special market conditions are needed; `deposit` is callable by any EOA. Mitigations: the victim can self-clean slots while healthy, each attacker refill burns real underlying, and `AmountIsZero` prevents free registration (DepositToken.sol:215).

### Recommendation
- Cap or permission beneficiary-based registration: have `deposit`/`_transfer` only register tokens for `msg.sender`, or let accounts opt in to new token types.
- Alternatively, allow `removeFromDepositTokensOfAccount`/`removeFromDebtTokensOfAccount` to be invoked by the account owner themselves (not only the token contract) so a victim can always evict unwanted dust entries regardless of lock state.
- Consider a minimum meaningful balance (`dust threshold`) below which entries are not registered.

Caveats from this pass: `MAX_TOKENS_PER_USER`'s concrete value and `MappedEnumerableSet` internals were not fully verified in this iteration, and `RecurringAirdrop.sol` does not exist in this repo, so the airdrop `claimed[]` analog could not be evaluated.
