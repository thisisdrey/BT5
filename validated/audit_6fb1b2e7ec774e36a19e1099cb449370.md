### Title
Rounding-direction inconsistency in the TRC10 Bancor-style Exchange lets an unprivileged trader skim value from exchange liquidity - (File: `chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java`)

### Summary
The GVault report describes a class of bug where `convertToShares`/`convertToAssets` always round in the *same* direction regardless of which side (protocol vs. user) should bear the rounding loss, letting a user repeatedly mint/withdraw to skim value from the vault. The closest reachable analog in java-tron is the legacy Bancor-relay exchange math used by the TRC10 `Exchange` (`ExchangeTransactionContract` / `ExchangeInjectContract` / `ExchangeWithdrawContract`), which is directly triggerable by any signed transaction from an unprivileged account.

### Finding Description
`ExchangeCapsule.transaction()` selects between two `Processor` implementations depending on the `allowHardenExchangeCalculation` dynamic property and the `hardenedCalc` flag passed by the caller: [1](#0-0) [2](#0-1) 

When the hardened path is not used, `ExchangeProcessor` computes both legs of the trade with `Math.pow`/`StrictMath.pow` in floating point and truncates the result with a `(long)` cast, which is a `RoundingMode.DOWN`/toward-zero truncation applied independently at *each* of the two conversion steps (`sellToken -> relay supply` and `relay supply -> buyToken`): [3](#0-2) 

This is exactly the rounding-direction problem the report calls out: the two conversions (analogous to `convertToShares`/`convertToAssets`) are not both being rounded in favor of the same party. The "hardened" replacement, `SafeExchangeProcessor`, fixes this by using `BigDecimal` with `RoundingMode.HALF_UP` for the intermediate relay computation and only truncating (`RoundingMode.DOWN`) the final output, explicitly rounding in favor of the pool: [4](#0-3) 

The existence of `SafeExchangeProcessor` and the `allowHardenExchangeCalculation`/`hardenedCalc` flags is direct evidence that the original `ExchangeProcessor` computation was known to be imprecise/inconsistent. The unprivileged entry point that exercises the un-hardened path is `ExchangeTransactionActuator.execute()`, which calls `exchangeCapsule.transaction(...)` and has **no** BigDecimal "not precise enough" sanity check (unlike `ExchangeWithdrawActuator`, which does perform such a check): [5](#0-4) [6](#0-5) 

Similarly `ExchangeInjectActuator.execute()` computes the proportional other-token amount with `floorDiv`, always rounding down, in the "fast" (execute) path, while the validate path uses BigDecimal division; the direction of rounding is not guaranteed to be symmetric with the direction used when a user later withdraws liquidity via `ExchangeWithdrawActuator`, which itself computes the proportional amount with `divideToIntegralValue` (down) plus a separate epsilon "precision" check: [7](#0-6) [8](#0-7) 

### Impact Explanation
An unprivileged account that repeatedly calls `ExchangeTransactionContract` (buy/sell round trips on the same TRC10 `Exchange` pool created by another user's `ExchangeCreateContract`/`ExchangeInjectContract` liquidity) can exploit the floating-point truncation asymmetry between `exchangeToSupply` and `exchangeFromSupply` to extract slightly more value than a fair AMM curve would allow on many trades, at the expense of the liquidity provider's pool balances (`firstTokenBalance`/`secondTokenBalance` fields persisted in `ExchangeCapsule`). Because these balances are TRX/TRC10 balances directly redeemable via `ExchangeWithdrawContract`, this is a direct drain of on-chain economic value ("unbacked balance"/theft of funds), not merely a bookkeeping curiosity. The magnitude per trade is small (sub-unit rounding), but — exactly as in the GVault report's exploit scenario — it is designed to be repeated to accumulate meaningful losses over time.

### Likelihood Explanation
Medium. The exploit requires only a normal signed transaction (`ExchangeTransactionContract`), reachable by any account with TRX/TRC10 balance and no special privileges — it does not require a malicious SR/witness/committee member. However: (1) it requires committee's `allowHardenExchangeCalculation` proposal to remain disabled (or the caller to avoid the `hardenedCalc=true` code path, which appears to only be exercised by specific callers/tests, not the default actuator flow) for the un-hardened `ExchangeProcessor` to be used; (2) per-trade skim is bounded by 1 unit-of-smallest-denomination-level rounding, so many transactions (and fees) are needed to accumulate a material profit, making it a "high difficulty, low-and-slow" attack similar to the one described in the original report.

### Recommendation
Audit `ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply` and `ExchangeInjectActuator`/`ExchangeWithdrawActuator` to guarantee that all rounding in the Bancor-relay math consistently favors the exchange pool (protocol/liquidity providers) rather than the individual trader, matching the direction already implemented in `SafeExchangeProcessor`. Consider making the hardened path (`SafeExchangeProcessor`/BigDecimal-based math) the unconditional default rather than gated behind `allowHardenExchangeCalculation`, and add symmetric precision checks to `ExchangeTransactionActuator` and `ExchangeInjectActuator` similar to the "Not precise enough" check already present in `ExchangeWithdrawActuator`. Expand differential fuzz testing (already partially present in `ExchangeProcessorTest`) that compares `ExchangeProcessor` vs `SafeExchangeProcessor` outputs across a wide range of pool sizes/trade sizes and asserts pool balances never decrease from a sequence of round-trip trades.

### Proof of Concept
1. Account A creates a TRC10 `Exchange` and injects significant first/second token liquidity via `ExchangeCreateContract`/`ExchangeInjectContract`.
2. Attacker (unprivileged) account B repeatedly submits `ExchangeTransactionContract` transactions alternating direction (sell token1 for token2, then sell token2 back for token1) on the same `exchangeId`, using `useStrictMath=false`/default (non-hardened) execution, per `ExchangeCapsule.transaction(tokenID, tokenQuant, dynamicStore.allowStrictMath(), allowHarden())` in `ExchangeTransactionActuator.execute()`.
3. Because `exchangeToSupply`/`exchangeFromSupply` in `ExchangeProcessor` independently truncate toward zero at each leg using floating-point `Math.pow`, each round trip returns B a fractional unit more (or the pool a fractional unit less) than a symmetric-rounding implementation (`SafeExchangeProcessor`) would, verified by the existing differential test `ExchangeProcessorTest.testStrictMath()` which shows `ExchangeProcessor` and `SafeExchangeProcessor` diverge (`Assert.assertNotEquals(anotherTokenQuant, result)`), confirming the non-hardened path is measurably different/exploitable.
4. Repeating step 2 thousands of times drains the pool's `firstTokenBalance`/`secondTokenBalance` stored in `ExchangeCapsule`, which B (or a colluding account) can then redeem via `ExchangeWithdrawContract`, realizing the skimmed value as real TRX/TRC10 balance.

Note: I was unable to fully confirm within the available time whether `allowHardenExchangeCalculation` is enabled by default on current mainnet/testnet configurations (this is a chain-parameter/committee-controlled proposal value, and its concrete default could not be verified from the indexed files). If it is already enabled network-wide, the exposure of the un-hardened `ExchangeProcessor` path is reduced to historical/legacy state rather than a currently live issue — this should be verified directly against `DynamicPropertiesStore.allowHardenExchangeCalculation()`'s default and current on-chain value before treating this as an active, exploitable issue.

  private BigDecimal exchangeToSupply(long balance, long quant) {
    long newBalance = StrictMathWrapper.addExact(balance, quant);
    BigDecimal bdQuant = BigDecimal.valueOf(quant);
    BigDecimal bdNewBalance = BigDecimal.valueOf(newBalance);
    BigDecimal base = BigDecimal.ONE.add(
        bdQuant.divide(bdNewBalance, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 0.0005);
    return SUPPLY.negate().multiply(
        BigDecimal.ONE.subtract(BigDecimal.valueOf(powResult))).setScale(0, RoundingMode.DOWN);
  }

  private long exchangeFromSupply(long balance, BigDecimal supplyQuant) {
    BigDecimal bdBalance = BigDecimal.valueOf(balance);
    BigDecimal base = BigDecimal.ONE.add(
        supplyQuant.divide(SUPPLY, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 2000.0);
    BigDecimal exchangeBalance = bdBalance.multiply(
        BigDecimal.valueOf(powResult).subtract(BigDecimal.ONE));
    return exchangeBalance.setScale(0, RoundingMode.DOWN).longValueExact();
  }
