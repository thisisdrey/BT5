### Title
Attacker can permanently block a victim from using new collateral or minting new synthetics by stuffing `depositTokensOfAccount` to `MAX_TOKENS_PER_USER` with dust transfers — (`File: contracts/Pool.sol`)

### Summary
`Pool` caps the combined length of an account's `debtTokensOfAccount` and `depositTokensOfAccount` sets at `MAX_TOKENS_PER_USER = 30` in `onlyIfAdditionWillNotReachMaxTokens`. Both `DepositToken.deposit(..., onBehalfOf_)` and `DepositToken.transfer` let any unprivileged account add a new entry to an arbitrary victim's list for an arbitrarily small amount (dust). Filling the victim's list makes every subsequent `_mint` or `DebtToken` issuance revert, bricking deposits of new collateral types and minting of new synths for that account.

### Finding Description
`addToDepositTokensOfAccount` is called from `DepositToken._mint` (deposit path) and `_transfer` (transfer path) whenever the recipient's balance moves from 0, and it is guarded by `onlyIfAdditionWillNotReachMaxTokens`, which reverts with `UserReachedMaxTokens` once the combined count hits 30. [1](#0-0) [2](#0-1) [3](#0-2) 

The attacker has two permissionless vectors to grow a victim's list:

1. `deposit(amount_, onBehalfOf_)` credits `onBehalfOf_` — the attacker deposits 1 wei of each distinct underlying with `onBehalfOf_ = victim`, calling `_mint` → `addToDepositTokensOfAccount(victim)`. [4](#0-3) [5](#0-4) 

2. `transfer(victim, dust)` calls `_transfer`, which adds the token to the victim's list with no consent check and no lock check on the recipient side. [6](#0-5) [7](#0-6) 

Once `debtTokensOfAccount.length(victim) + depositTokensOfAccount.length(victim) == 30`:

- `deposit()` into any deposit token the victim does not already hold reverts inside `_mint` (after the underlying has already been pulled to Treasury in the same tx, so the whole tx reverts).
- `DebtToken.issue`/`mint` for any synthetic the victim does not already owe reverts via `addToDebtTokensOfAccount`, which shares the same 30-slot budget.
- Critically, `transfer`/`transferFrom`/`seize` to the victim also revert if the token is new to them — a liquidator seizing a collateral type the victim doesn't already hold cannot receive it (the liquidator's own list fills too, but more importantly the victim cannot receive rescue deposits).

Note the victim cannot be un-bricked cheaply by the attacker-side entries being dust: removal from the list only happens when the victim's balance goes exactly to 0, and the victim must spend gas to withdraw/transfer each dust position, and dust withdrawals of locked-position accounts are further constrained by `_revertIfLocked`/`unlockedBalanceOf`. [8](#0-7) [9](#0-8) 

### Impact Explanation
This is a liveness/temporary-freeze analog of the NanoMQ crafted-message DoS: a single crafted, unprivileged input path renders core protocol functions permanently unavailable to the victim. Concretely: the victim loses the ability to add *new* collateral types (all `deposit` calls to fresh tokens revert) and to mint *new* synthetic assets (`issue` reverts). If the victim's position is deteriorating and they need to deposit a different collateral to avoid liquidation, they are blocked until they manually clear slots — each dust entry must be individually withdrawn or transferred out, and with a borrow open, `unlockedBalanceOf` may lock dust collateral, making self-recovery impossible without first repaying debt they may have intended to refinance. During this window liquidations continue normally, so the DoS can convert directly into a loss of funds. This meets "temporary freezing of funds" and denial of protocol functionality.

### Likelihood Explanation
- Fully unprivileged: only requires holding dust amounts of underlying assets (or dust msdTokens obtained by depositing to self first).
- Cost is bounded by `30` tiny deposits/transfers; each `deposit` requires only `amount_ > 0` and no minimum, and `transfer` has no minimum either.
- No governor, keeper, oracle, or privileged role is involved; `onlyIfDepositTokenExists`, `whenNotPaused`, and `nonReentrant` do not stop it — transfers are not paused-gated at all.
- The constraint is that the attacker needs up to `30 - current length` distinct deposit tokens registered in the victim's pool; mainnet deployments have fewer than 30 deposit tokens per pool, but any victim with a moderate number of existing entries (debt tokens + deposit tokens) can be pushed over the cap, and pools continue adding collateral types over time.

### Recommendation
- Decouple the per-account accounting: track deposit/debt exposure in a bounded hash set or iterate lazily so a hard cap is unnecessary; or
- Make list membership opt-in: only add a token to `depositTokensOfAccount` when the recipient initiated the action (deposit `onBehalfOf` self, or an explicit `acceptToken`/opt-in), not on incoming `transfer`/`seize`; or
- Raise/eliminate the cap by bounding `debtPositionOf` gas another way (e.g., iterate only over tokens the account actually owes meaningful balances in), and add a `sweepDust`/self-removal escape hatch that lets an account remove a token from its list even with a tiny nonzero balance by auto-burning it.

### Proof of Concept
Hardhat-style sketch (fork or in-repo fixtures):

```ts
// attacker stuffs victim's token list to MAX_TOKENS_PER_USER
const victim = alice.address;
const poolTokens: DepositToken[] = [msdMET, msdETH, msdWBTC /* ...all registered deposit tokens */];

for (const dt of poolTokens) {
  const under = await ethers.getContractAt('ERC20', await dt.underlying());
  // 1 wei deposit credited to victim adds the token to victim's list
  await under.connect(attacker).approve(dt.address, 1);
  await dt.connect(attacker).deposit(1, victim);        // vector 1
  // or: await dt.connect(attacker).transfer(victim, 1); // vector 2
}

// combined list is now at the cap (30 including victim's existing debt tokens)
const count =
  (await pool.getDepositTokensOfAccount(victim)).length +
  (await pool.getDebtTokensOfAccount(victim)).length;
expect(count).to.eq(await pool.MAX_TOKENS_PER_USER());

// victim can no longer deposit into a new collateral type
await expect(
  newDepositToken.connect(victim).deposit(amount, victim)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');

// victim can no longer mint a new synthetic (adds a new DebtToken to the list)
await expect(
  newDebtToken.connect(victim).issue(parseEther('1'), victim)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');
```

The revert propagates from `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` inside `_mint`/`_transfer`, so no amount of retries or alternate callers rescues the victim's ability to onboard new tokens until slots are manually cleared — matching the "crafted input → persistent denial of service" profile of CVE-2024-42650.
