### Title
Unauthenticated `recv_error` packets allow any remote attacker to force-close established tunnels with no cert required - ([File: outside.go])

### Summary
`GasThrottle`'s flaw was that an externally-influenced, unauthenticated signal (`_FAST_GAS_ORACLE`) fed a check with no way to disable or bound it, so poisoning that signal permanently broke a core operation (swaps) for everyone. The closest reachable analog in Nebula is `Interface.handleRecvError` in `outside.go`, which processes the unauthenticated `header.RecvError` packet type and can tear down an active, authenticated tunnel based on attacker-supplied, unauthenticated input, before any certificate or firewall check is applied.

### Finding Description
`readOutsidePackets` dispatches `header.RecvError` packets to `f.handleRecvError` immediately after header parsing, before any certificate, handshake, or firewall validation: [1](#0-0) 

`handleRecvError` looks up the hostinfo purely by the attacker-supplied `h.RemoteIndex` (a 32-bit value carried in plaintext in the header) and, if a spoofing guard doesn't fire, unconditionally tears the tunnel down: [2](#0-1) 

The only defense is comparing the packet's source address to the `HostInfo`'s last known remote (`hr`) — and that check is skipped entirely whenever `hr.IsValid()` is false (e.g., a tunnel that hasn't finished roaming/punching, is mid-handshake recovery, or otherwise has no confirmed remote yet):
```go
hr := hostinfo.GetRemote()
if hr.IsValid() && hr != addr {
    ...
    return
}
f.closeTunnel(hostinfo)
f.handshakeManager.DeleteHostInfo(hostinfo)
```
This is the "oracle" analog: an externally-controlled value (the guessed/observed `RemoteIndex`) drives a binary decision (tear down the tunnel) with no cryptographic authentication of the sender, mirroring the unauthenticated, always-consulted `_FAST_GAS_ORACLE` value in the original report.

### Impact Explanation
An attacker with no valid Nebula certificate — but who can send arbitrary UDP packets to a node's listen port and knows or can observe a valid `RemoteIndex` (these are exchanged in plaintext during/after handshakes and are visible on the wire, or crossable by brute force since it's only a 32-bit space) — can force any established tunnel into `closeTunnel` + `DeleteHostInfo`, disrupting connectivity. Because the check is bypassed whenever the host's remote address hasn't been "confirmed" yet (`!hr.IsValid()`), repeated spoofed `RecvError` packets can prevent a tunnel from ever stabilizing, denying service to that peer indefinitely as long as the attacker keeps sending forged packets — directly analogous to the GasThrottle DOS in that a single unauthenticated signal permanently defeats normal operation with no cryptographic backstop.

### Likelihood Explanation
Nebula does provide a configuration knob (`listen.accept_recv_error`, default `"always"`) that operators can set to `"never"` or `"private"` to reduce exposure, so this is not literally "no way to turn off," but the default is permissive and most deployments will not proactively disable it. The `RemoteIndex` is not secret-derived from the certificate — it's a locally generated random 32-bit index exchanged during the handshake — so cross-referencing or brute-forcing it is the main obstacle to exploitation, which lowers likelihood somewhat compared to the original C4 report where the oracle value required no such guess.

### Recommendation
- Require some proof of session knowledge (e.g., checking against a currently pending/recent index and rate-limiting per source) before honoring `RecvError`, rather than relying solely on the optional `hr.IsValid()` address check.
- Treat `!hr.IsValid()` as the *most* sensitive case (no confirmed remote), not as a bypass of the spoofing check — a tunnel that hasn't confirmed its remote is precisely the one most vulnerable to being permanently starved by forged `RecvError` traffic.
- Consider defaulting `listen.accept_recv_error` to `"private"` rather than `"always"`, and document the tradeoff explicitly as the GasThrottle report recommends (allow disabling entirely, which Nebula already supports, but make the safer default).

### Proof of Concept
1. Attacker observes (or brute-forces across the 32-bit space) a `RemoteIndex` used by a real Nebula host pair, learned from any handshake/message traffic it can capture on the path (no valid certificate needed to observe or replay these values).
2. Attacker crafts a `header.RecvError` packet (`header.Encode(..., header.RecvError, 0, index, 0)`) addressed to the victim's listen port from an arbitrary source address.
3. If the victim's `HostInfo.GetRemote()` for that index is not yet "confirmed" (`!hr.IsValid()`, e.g. during roaming/handshake or before the first punch), `handleRecvError` skips the address check and calls `f.closeTunnel(hostinfo)` plus `f.handshakeManager.DeleteHostInfo(hostinfo)`, destroying tunnel state.
4. Repeating this defeats reconnection/stabilization for as long as the attacker can keep sending forged packets, unless the operator has set `listen.accept_recv_error` to `"never"`.

```go
func (f *Interface) handleRecvError(addr netip.AddrPort, h *header.H) {
	if !f.acceptRecvErrorConfig.ShouldRecvError(addr) {
		f.l.Debug("Recv error received, ignoring",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
		return
	}

	if f.l.Enabled(context.Background(), slog.LevelDebug) {
		f.l.Debug("Recv error received",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
	}

	hostinfo := f.hostMap.QueryReverseIndex(h.RemoteIndex)
	if hostinfo == nil {
		f.l.Debug("Did not find remote index in main hostmap", "remoteIndex", h.RemoteIndex)
		return
	}

	hr := hostinfo.GetRemote()
	if hr.IsValid() && hr != addr {
		f.l.Info("Someone spoofing recv_errors?",
			"addr", addr,
			"hostinfoRemote", hr,
		)
		return
	}

	f.closeTunnel(hostinfo)
	// We also delete it from pending hostmap to allow for fast reconnect.
	f.handshakeManager.DeleteHostInfo(hostinfo)
}
```
