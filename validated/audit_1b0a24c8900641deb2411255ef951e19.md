Found a real analog. In `AttachmentsDownloader::run` (`stackslib/src/net/atlas/download.rs`), when a batch of attachment fetch requests completes, downloaded attachments are inserted into the DB **keyed by the hash of the content actually received**, not the hash that was requested — and there is no comparison against the `content_hash` that the on-chain `AttachmentInstance` committed to before that content is treated as "resolved" and handed to the event observer / callers as matching that instance.

### Title
Downloaded Atlas attachment content is stored and paired to `AttachmentInstance`s without verifying it matches the requested `content_hash` - (File: stackslib/src/net/atlas/download.rs)

### Summary
This mirrors the report's bug class: a value meant to act as an integrity/commitment guarantee (`sqrtRatioLimit` for slippage in the original report; here, `content_hash` for content-addressing) is accepted into state without the code actually checking that the received data matches what was promised, silently substituting attacker-controlled data for the committed value instead of rejecting the mismatch.

### Finding Description
`AttachmentInstance::content_hash` is the on-chain commitment to the attachment's content — established by a smart contract event and is supposed to make Atlas data content-addressed [1](#0-0) . When attachments are fetched from a peer via `extend_with_attachments`, the response is decoded and the returned `Attachment` (whose bytes are entirely peer-controlled) is inserted directly into `self.attachments` with no check that `Hash160::from_data(&content)` equals any expected `content_hash`: [2](#0-1) 

Then in `AttachmentsDownloader::run`, once the batch state machine reaches `Done`, every attachment collected in `context.attachments` is looked up **by its own hash** (`attachment.hash()`) to find "matching" `AttachmentInstance`s, and is stored via `insert_instantiated_attachment`, and paired with those instances as resolved data that gets forwarded to callers/observers: [3](#0-2) 

Because the lookup key (`attachment.hash()`) is derived from the attacker-supplied bytes themselves, the equality that's supposed to be enforced — "the content whose hash the chain committed to == the content received" — is never actually checked against the specific `content_hash` that triggered the batch/request. `find_all_attachment_instances` only matches instances whose `content_hash` column equals the (attacker-controlled) `attachment.hash()`; there's no round-trip verification that the URL/peer queried for a *specific* `content_hash` actually returned bytes hashing to that exact value versus, e.g., a peer returning some other valid-looking attachment content for a different, unrelated instance it also happens to have queued in the same batch, or bytes that don't hash-match at all but still get inserted as "instantiated" and immediately looked up by their own (self-consistent) hash.

The `try_replace_chunk`/`validate_received_chunk` code path in `stackslib/src/net/stackerdb/mod.rs` shows the correct pattern this code is missing: chunk data is hashed and that hash is compared against a **pre-declared** ("expected") value from a source outside the peer's control (a signed `SlotMetadata`) before acceptance [4](#0-3) . The Atlas download path has no equivalent binding step tying a specific outbound request's expected `content_hash` to the specific attachment payload received for it.

### Impact Explanation
This falls under the report's "served/committed" and "non-canonical state served as canonical" category from the rules. A malicious or compromised peer can serve attachment bytes that don't correspond to the actual on-chain `AttachmentInstance.content_hash` being resolved, and the AttachmentsDownloader will still classify it as validated ("Checked"/"is_available") data associated with that instance's contract event (e.g., BNS name/zonefile data), because the only verification loop is self-referential (hash of data == hash of data). This is an attachment/BNS mismatch class finding: downstream consumers (BNS name resolution, event observers such as `POST /attachments/new`) can receive and treat forged or mismatched attachment content as canonical, resolved data tied to a legitimate on-chain commitment.

### Likelihood Explanation
Reachable by any peer that a node syncs Atlas attachments from (`get_outbound_sync_peers`), requiring only that the attacker's node be selected to serve an `AttachmentRequest` for some in-flight batch — no special privileges, keys, or consensus-level access needed.

### Recommendation
Before calling `insert_instantiated_attachment`/marking an attachment "Checked"/resolved, explicitly recompute `Hash160::from_data(&attachment.content)` and compare it against the exact `content_hash` that was requested for that specific `AttachmentRequest`/`AttachmentInstance` (not merely use the attacker-supplied bytes' own hash as the lookup key). Reject and penalize (via `report.bump_failed_requests()`) any response whose content hash does not match the requested `content_hash`.

### Proof of Concept
Not independently executable from static review alone; the control-flow trace above (`extend_with_attachments` → `run`/`Done` branch) demonstrates the missing equality check. This would need to be exercised in an integration test that queues an `AttachmentInstance` with `content_hash = H1`, has a malicious peer respond to the corresponding `AttachmentRequest` with content whose real hash is `H2 != H1` but is otherwise decodable, and observes whether `insert_instantiated_attachment`/`resolved_attachments` accept it — this dynamic confirmation is unverified by me and should be validated with a live/test harness (noted as uncertain since only static code paths were reviewed here, not test execution).
