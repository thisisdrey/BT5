## Title
Out-of-bounds read in ijar central-directory extra-field parsing via unbounded length loop - (File: third_party/ijar/zip.cc)

### Summary
`InputZipFile::ProcessCentralDirEntry` in ijar's zip reader parses the "extra fields" of a Central Directory Header using a `while (extra_p != p)` loop that trusts the attacker-controlled `data_size` field of each extra-field record without ever validating it against the actual bounds of the extra-field region or the underlying memory-mapped file [1](#0-0) . This mirrors the CVE-2024-37371 bug class: a length field taken directly from untrusted input drives pointer arithmetic with no bounds check, leading to an invalid memory read.

### Finding Description
`ProcessCentralDirEntry` reads `file_name_length`, `extra_field_length`, and `file_comment_length` directly off the wire, then sets `extra_p = p` and advances `p += extra_field_length` to mark the end of the extra-field data [2](#0-1) . It then loops:

```cpp
while (extra_p != p) {
  const u2 header_id = get_u2le(extra_p);
  const u2 data_size = get_u2le(extra_p);
  const u1 *extra = extra_p;
  extra_p += data_size;
  if (header_id == ZIP64_EXTRA_FIELD_TAG) {
    if (*uncompressed_size == U4_MAX) *uncompressed_size = get_u8le(extra);
    ...
  }
}
``` [3](#0-2) 

Every iteration blindly reads 4 header bytes and then jumps `extra_p` forward by the attacker-supplied `data_size`, with the loop's *only* termination condition being pointer equality to `p`. Unlike the local-file-header path, which explicitly validates lengths with `EnsureRemaining()` before touching memory [4](#0-3) , there is no equivalent check here:
- If `data_size` is chosen so `extra_p` overshoots `p` (rather than landing exactly on it), the loop condition never becomes false, and it keeps reading 4-byte header/size pairs and jumping further, walking past the extra-field region, past the entry, and potentially past the end of the mmap'd file.
- The `get_u8le(extra)` call for a `ZIP64_EXTRA_FIELD_TAG` reads 8 bytes from `extra` without verifying `data_size >= 8` or that those 8 bytes lie within the mapped region.

Because the input file is opened via `mmap` (`MappedInputFile`), reading past the mapped extent is an out-of-bounds/invalid memory access, not merely logic corruption — directly analogous to the "invalid memory reads ... from message tokens with invalid length fields" described in CVE-2024-37371.

### Impact Explanation
An attacker who controls the bytes of a `.jar`/`.zip` file that ends up processed by ijar (e.g., a jar fetched by `http_jar`/`http_archive`/Maven-style rules and later used to build an interface jar with `ijar`, or singlejar-adjacent zip processing) can craft a Central Directory extra-field with an invalid `data_size` to trigger reads outside the mapped file region. This is an invalid-memory-read (crash/DoS at minimum; on some platforms adjacent-page over-read could leak process memory into subsequent error messages or comparisons) triggered purely by content the attacker publishes.

### Likelihood Explanation
The comment on the function claims safety by asserting "the central directory is always followed by another data structure that has a signature, so parsing it this way is safe" — but that guarantee applies only to entry-to-entry advancement, not to the inner extra-field loop, which has no bound at all tied to `extra_field_length` beyond exact-equality of a pointer that an attacker fully controls via `data_size`. Since sha256/integrity checks (as used in Bazel's `http_archive`/`http_jar`) validate the *whole downloaded file's bytes*, they do nothing to prevent an internally malformed-but-checksum-matching zip from containing this malicious extra field — the checksum only proves the attacker's bytes were delivered unmodified, not that their internal structure is sane. This makes the bug directly reachable from attacker-controlled, checksum-verified archive content.

### Recommendation
In `InputZipFile::ProcessCentralDirEntry`, bound the extra-field parsing loop by remaining length rather than exact pointer equality: track `remaining = p - extra_p` before each header/size read, verify `remaining >= 4` before reading `header_id`/`data_size`, and verify `data_size <= remaining - 4` before advancing `extra_p` and before calling `get_u8le`. Reject the entry (return `false`/error) if any of these invariants are violated, matching the pattern already used by `EnsureRemaining()` in the local-file-header path.

### Proof of Concept
A reproducible test would use ijar's zip reading directly (or via `singlejar`), analogous to the existing `zip_headers_test.cc`/`ProcessCentralDirEntry` coverage: construct a minimal zip with one Central Directory Header where `extra_field_length` is small (e.g., 4) but the embedded `data_size` value is set to a large value (e.g., `0xFFFF`) causing `extra_p` to jump past `p` and past the mapped file boundary, then call `ProcessCentralDirEntry` (or run the full `InputZipFile::ProcessNext()` path used by `ZipExtractor::Create`) and observe a segmentation fault / ASAN heap-buffer-overflow on read, rather than the graceful `error(...)` returns exercised in `zip_headers_test.cc` for other malformed inputs [5](#0-4) .

Note: I was unable to locate the higher-level Java `ZipDecompressor`/`DecompressorValue` sources for `http_archive` extraction in the indexed content (search for `class ZipDecompressor` returned no matches), likely due to index size limits — if you need to confirm the exact call path from `http_archive`/Bzlmod registry archive fetch into this native ijar code (versus its more direct callers in `singlejar`/`archive_utils.cc`), a full Devin session with complete repository access would be needed to trace that precisely.
