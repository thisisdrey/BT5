### Title
Optimistic inventory patching in `handle_unsolicited_StackerDBPushChunk` can advertise a chunk version that is never actually stored (advertised vs. stored state mismatch) - (File: `stackslib/src/net/stackerdb/mod.rs`)

### Summary
`PeerNetwork::handle_unsolicited_StackerDBPushChunk` patches the `StackerDBChunkInv` reply that is sent back to the pushing peer *before* the chunk is durably written to the local StackerDB. The actual persistence of the pushed chunk (via `StackerDBTx::try_replace_chunk`) happens later, out-of-band, gated on the write-frequency check that this function explicitly skips. If that later write fails for any reason, the node has already told the network it holds a newer `slot_version` that it does not actually have — the same class of bug as the reported `rescheduleGame`: one half of a two-part invariant (advertised version vs. persisted version / start time vs. end time) is updated while the other half is left stale, letting the two diverge.

### Finding Description
In `make_StackerDBChunksInv_or_Nack` / `handle_unsolicited_StackerDBPushChunk`: [1](#0-0) 

`validate_received_chunk` checks size, signer, staleness (`slot_version < expected_version`) and `max_writes`, but explicitly does **not** check write frequency: [2](#0-1) 

The doc comment on the handler states this omission is intentional and that write-frequency enforcement, and the actual storage, are deferred to later processing (the relayer path), triggered only via the returned "forward to relayer" boolean: [3](#0-2) 

Despite storage not having happened yet, the function immediately mutates the `slot_versions` vector inside the `StackerDBChunkInv` payload to reflect the *pushed* version, and this patched inventory is what gets signed and sent back to the peer as the ACK/response: [4](#0-3) [5](#0-4) 

The actual on-disk commit only happens via `StackerDBTx::try_replace_chunk`, which independently re-validates staleness, signer, and `max_writes`, and can fail (`StaleChunk`, `BadSlotSigner`, `TooManySlotWrites`) at that later point: [6](#0-5) 

Because the inventory patch and the actual write are not atomic and are gated by different checks (write-frequency being the notable one deferred entirely), there is a window in which the node's advertised inventory (`slot_versions`) claims to hold a chunk version it has not actually persisted — analogous to the reported bug updating `game.startTime` while leaving `game.endTime` stale, producing an inconsistent, exploitable state.

### Impact Explanation
A remote, unprivileged peer can push a validly-signed chunk that passes `validate_received_chunk` but is subsequently rejected or not durably applied by the deferred storage step (e.g., write-frequency throttling, races with a concurrent StackerDB sync also modifying slot state, as explicitly flagged by the "be very careful" comment). The victim node will nonetheless have already broadcast a `StackerDBChunkInv` claiming the newer version is present. Peers that trust this inventory and steer their sync decisions off it (e.g., decide not to re-fetch that slot, or mark it as caught up) can be led to believe the network view is more current than it actually is — this matches the "steering a node off the tip via false inventory" High-impact category, since inventory-driven StackerDB sync state machines make forward-progress decisions based on this advertised data.

### Likelihood Explanation
Requires only an unprivileged peer sending an unsolicited `StackerDBPushChunk` with a validly signed chunk (using a legitimate slot signer's key for a StackerDB the attacker already has write access to, e.g. as a registered signer) while conditions cause the deferred write to fail or race (e.g. concurrent `StackerDBSync` activity, hitting write-frequency limits, or overlapping pushes to the same slot). No forged signatures or privileged roles are needed beyond normal StackerDB writer status; the mismatch window is a function of node concurrency/timing rather than attacker sophistication, making it moderately likely under sustained traffic from a legitimate writer.

### Recommendation
Only patch/emit the `StackerDBChunkInv` reply's `slot_versions` entry after the chunk has actually been durably committed via `try_replace_chunk` (or after confirming write-frequency and other deferred checks pass), rather than optimistically before the write. Alternatively, make the ACK conditional on synchronous storage success, or explicitly document/re-verify at inventory-read-time that `slot_versions` matches what is in the DB before it's used to drive sync decisions elsewhere.

### Proof of Concept
1. Attacker controls (or has been assigned) a legitimate signer slot in a StackerDB with a small `write_freq` throttle or restrictive `max_writes` state on the target.
2. Attacker sends `StackerDBPushChunk` with a validly signed chunk and a `slot_version` that passes `validate_received_chunk` (signature, size, staleness, `max_writes` all satisfied) at `stackslib/src/net/stackerdb/mod.rs:649-718`.
3. `handle_unsolicited_StackerDBPushChunk` patches `data.slot_versions` at line 807 and immediately signs/sends the `StackerDBChunkInv` reply (lines 861-870) advertising the new version — before the chunk is forwarded/committed.
4. Deferred storage (via `try_replace_chunk`) later fails or is delayed (e.g., due to write-frequency gating not checked here, or a race with a concurrent `StackerDBSync` reconfiguring/pruning the slot), leaving the actual persisted `slot_version` behind what was already advertised.
5. Peers that received the inventory in step 3 believe the node has the newer chunk and adjust their own sync/inventory state accordingly, even though the node's DB still holds the old version.

Note: I was unable to fully trace the exact downstream relayer code path that performs the deferred `try_replace_chunk` call and its write-frequency enforcement (ran out of tool iterations before confirming this precisely in `stackslib/src/net/relay.rs`), so the exact failure trigger for the deferred write should be verified in a follow-up review.

    /// Add or replace a chunk for a given reward cycle, if it is valid
    /// Otherwise, this errors out with Error::StaleChunk
    pub fn try_replace_chunk(
        &self,
        smart_contract: &QualifiedContractIdentifier,
        slot_desc: &SlotMetadata,
        chunk: &[u8],
    ) -> Result<(), net_error> {
        // Check per-replica chunk-size cap.
        if (chunk.len() as u64) > self.config.chunk_size {
            return Err(net_error::StackerDBChunkTooBig(chunk.len()));
        }

        let slot_validation = self
            .get_slot_validation(smart_contract, slot_desc.slot_id)?
            .ok_or(net_error::NoSuchSlot(
                smart_contract.clone(),
                slot_desc.slot_id,
            ))?;

        if !slot_desc.verify(&slot_validation.signer)? {
            return Err(net_error::BadSlotSigner(
                slot_validation.signer,
                slot_desc.slot_id,
            ));
        }
        if slot_desc.slot_version <= slot_validation.version {
            return Err(net_error::StaleChunk {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
            });
        }
        if slot_desc.slot_version > self.config.max_writes {
            return Err(net_error::TooManySlotWrites {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
                max_writes: self.config.max_writes,
            });
        }
        self.insert_chunk(smart_contract, slot_desc, chunk)
    }
