### Title
Yield-timeout resolution starvation via shared, unprioritized chunk-wide storage-proof budget - ([File: runtime/runtime/src/lib.rs])

### Finding Description
`process_receipts` (runtime/runtime/src/lib.rs:2681-2737) processes local receipts, then delayed receipts, then incoming receipts, and only *last* calls `resolve_promise_yield_timeouts` (runtime/runtime/src/lib.rs:2717-2719) to resolve expired `PromiseYieldTimeout` queue entries. [1](#0-0) 

All four stages share a single `TrieRecorder`/`upper_bound_size` counter that is only reset once per chunk `apply` call (it is never reset between stages), and each stage's loop guards on the identical chunk-wide `state_update.trie.check_proof_size_limit_exceed()` predicate: [2](#0-1) [3](#0-2) [4](#0-3) 

`resolve_promise_yield_timeouts` uses the exact same shared counter as its break condition and processes the `PromiseYieldTimeout` queue strictly FIFO by `first_index`/`expires_at`: [5](#0-4) 

`check_proof_size_limit_exceed` simply compares the monotonically-growing `upper_bound_size` against `proof_size_limit` (`main_storage_proof_size_soft_limit`, 4MB per `docs/misc/state_witness_size_limits.md`), and this counter is incremented by every trie read/removal recorded anywhere earlier in the same chunk: [6](#0-5) 

Because yield-timeout resolution runs strictly after local/delayed/incoming receipt processing in every chunk, an attacker who reliably pushes `upper_bound_size` past the soft limit via cheap local receipts (e.g., a contract method that reads several megabytes of storage, as demonstrated in `integration-tests/src/tests/features/storage_proof_size_limit.rs`) will cause the yield-timeout loop to `break` at line 3026 before advancing `promise_yield_indices.first_index`, deferring resolution to the next chunk without error.

### Impact Explanation
This is a liveness/griefing issue rather than a permanent loss: since `first_index` is unchanged whenever the loop breaks early, the queue entries (and hence any refund/callback logic gated on `PromiseYieldTimeout` firing) are delayed to the next chunk, exactly like delayed receipts that miss the same soft limit. Because `resolve_promise_yield_timeouts` is scheduled last and shares a common, non-reserved budget, it is the easiest of the four consumers to starve. As long as an attacker keeps re-saturating `upper_bound_size` above the soft limit every chunk, other accounts' yield timeouts (and any funds/logic gated behind them) remain unresolved — a temporary, attacker-sustained freezing that self-heals the moment the attacker stops.

### Likelihood Explanation
Generating several MB of storage-proof per chunk via `storage_read`-heavy contract calls is a documented, cheap technique (see the "hard per-receipt limit" test in `integration-tests/src/tests/features/storage_proof_size_limit.rs`), well within normal gas limits, and requires no special privilege — any funded account can deploy and call such a contract repeatedly. However, sustaining this indefinitely requires the attacker to pay real gas fees every single chunk forever, and it equally congests/throttles the attacker's own shard traffic (existing congestion-control mechanisms documented in `protocol-model/spec/cross-shard-congestion.md` apply uniformly here), making "permanent" freezing economically bounded by continuous attacker spend rather than a one-shot exploit.

### Recommendation
Reserve a portion of the per-chunk storage-proof budget specifically for `resolve_promise_yield_timeouts` (e.g., check the limit against a separately tracked sub-budget, or run yield-timeout resolution before/interleaved with incoming-receipt processing) so that local/delayed/incoming receipt volume cannot fully deprioritize timeout resolution.

### Proof of Concept
Integration test plan: deploy a "read_n_megabytes"-style contract; create one victim `promise_yield_create` receipt with a short `timeout_length`; in the same and subsequent chunks, submit attacker local transactions that read enough storage to keep `upper_bound_size` above `main_storage_proof_size_soft_limit`; run `runtime.apply` across N chunks and assert whether `PromiseYieldIndices.first_index` for the victim's queue entry advances/whether the victim's `PromiseResume` receipt is ever produced, versus a control run without the attacker load where it resolves on the expected chunk.
