### Title
Signature-malleability weight duplication in `ValidateMultiSign` precompile lets one key bypass a multi-sig permission threshold - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The `ValidateMultiSign` TVM precompile is meant to let a smart contract verify that a set of signatures over a hash together meet a Tron account `Permission`'s weight `threshold` (Tron's on-chain analog of a multi-sig wallet). Its de-duplication logic only rejects an exact repeated `(address, signature-bytes)` pair, not a second, distinct-but-valid signature from the same key. Because ECDSA signatures are malleable (and a key holder can always produce a second syntactically different valid signature over the same hash), a caller controlling just one key in the permission's key list can supply two differently-encoded signatures from that single key and have the precompile sum that key's weight twice, potentially crossing the threshold alone.

### Finding Description
`PrecompiledContracts.ValidateMultiSign.execute` iterates over the supplied `signatures` array, recovers the signer address for each, and only skips weight accumulation when both the recovered address *and* the exact merged `(recoveredAddr+sign)` byte string were already seen: [1](#0-0) 

```
long totalWeight = 0L;
List<byte[]> executedSignList = new ArrayList<>();
for (byte[] sign : signatures) {
  byte[] recoveredAddr = recoverAddrBySign(sign, hash);
  sign = merge(recoveredAddr, sign);
  if (ByteArray.matrixContains(executedSignList, recoveredAddr)) {
    if (ByteArray.matrixContains(executedSignList, sign)) {
      continue;
    }
    MUtil.checkCPUTime();
  }
  long weight = TransactionCapsule.getWeight(permission, recoveredAddr);
  if (weight == 0) {
    return Pair.of(true, DATA_FALSE);
  }
  totalWeight += weight;
  executedSignList.add(sign);
  executedSignList.add(recoveredAddr);
}
if (totalWeight >= permission.getThreshold()) {
  return Pair.of(true, dataOne());
}
``` [2](#0-1) 

When the same address appears a second time, the code checks whether the exact `sign` byte-blob was already recorded. If a *different* raw signature bytes for that same address is presented (e.g., produced by ECDSA malleability: `s' = n - s` on an existing valid `(r,s)`, which always verifies to the same public key without needing the private key at all, or simply re-signing with a fresh nonce, which any legitimate key holder can trivially do), the "already fully seen" check fails, `continue` is skipped, and `totalWeight += weight` executes again for the same address. The weight for one key is thus counted multiple times (bounded only by `MAX_SIZE = 5`).

This directly undermines the semantic guarantee of Tron's multi-sig `Permission` model (`threshold`/`Key.weight`), which `TransactionCapsule.checkWeight` correctly enforces for on-chain transaction signature verification by keying its duplicate-map on the recovered *address* rather than the raw signature bytes: [3](#0-2) 

The precompile reimplements this same weight/threshold check but with a weaker, signature-bytes-based dedup instead of address-based dedup, reintroducing the exact class of bug ("single key treated as multiple independent authorizers") that the underlying wallet-custody incident (single-signature funds being drained because the intended multi-party control was not actually enforced) illustrates.

### Impact Explanation
Any TVM contract that relies on the `ValidateMultiSign` precompile (opcode/precompiled address reachable via `TriggerSmartContract`) to gate a privileged action — e.g., a custom multisig wallet contract, an exchange/custodial contract, or a governance/withdrawal contract that checks "M-of-N approvals" before moving funds or changing state — can be tricked into accepting authorization from a single compromised or malicious key holder whose individual weight is below the configured threshold. This is a concrete "unauthorized account operation" / theft-enabling primitive: it defeats the multi-party control the permission system was designed to enforce, exactly analogous to the Coincheck loss where funds nominally protected by a stronger custody scheme were moved by insufficient signer diversity. Because the precompile is reachable by any unprivileged contract caller/deployer via a normal signed transaction, and the impact is unauthorized authorization of on-chain actions gated by this primitive, severity is High.

### Likelihood Explanation
Exploitation only requires:
1. Deploying (or already having) a contract that uses `ValidateMultiSign` for authorization (a documented, commonly-used Tron precompile for building multisig-style contracts).
2. Possessing one private key that is a member of the target permission's key list with weight below `threshold`.
3. Producing a second valid signature over the same hash from that key (trivial: sign again, or malleate `s -> n-s`).

No privileged access, no race condition, and no reliance on other signers is needed — the attacker fully controls the signature set submitted to the precompile. This makes exploitation straightforward for anyone who legitimately holds a single key in a supposedly N-of-M scheme.

### Recommendation
Change the de-duplication key in `ValidateMultiSign.execute` (and audit `BatchValidateSign` for similar patterns) to reject on `recoveredAddr` alone once its weight has already been counted, rather than requiring an exact match of the merged signature bytes. I.e., once `matrixContains(executedSignList_addresses, recoveredAddr)` is true, always `continue` (skip adding weight again) regardless of whether the raw signature bytes differ, mirroring the address-keyed logic already used in `TransactionCapsule.checkWeight`/`getWeight`.

### Proof of Concept
1. Create an account with an `Active` permission containing two keys, `key1` (weight 1) and `key2` (weight 1), `threshold = 2` (i.e., a true 2-of-2 style requirement), as constructed in the existing test scaffolding: [4](#0-3) 
2. Compute `hash` and the `toSign` message exactly as the precompile does (`merge(address, permissionId, data)` then SHA-256).
3. Using only `key1`, produce two different valid signatures over `toSign`:
   - `sigA = key1.sign(toSign)`
   - `sigB` = malleated variant of `sigA` (flip `s -> secp256k1_n - s`), or simply call `key1.sign(toSign)` again if the signer uses randomized nonces — both recover to `key1`'s address and both pass ECDSA verification.
4. Call the `ValidateMultiSign` precompile with `signatures = [sigA, sigB]` (never involving `key2` at all).
5. Because `sigA` and `sigB` are byte-distinct, the second iteration's `matrixContains(executedSignList, sign)` check fails to detect the repeat, so `totalWeight` becomes `1 + 1 = 2`, which is `>= threshold (2)`, and the precompile returns `true`/`dataOne()` even though only one of the two required keys ever participated. Compare against the legitimate "weight not enough" case in the existing test suite that only supplies one *identical* signature and correctly returns `DATA_FALSE`: [5](#0-4)

  public static class ValidateMultiSign extends PrecompiledContract {

    private static final int ENGERYPERSIGN = 1500;
    private static final int MAX_SIZE = 5;
    private static final int ABI_HEADER_WORDS = 5;
    private static final int ABI_ITEM_WORDS = 5;


    @Override
    public long getEnergyForData(byte[] data) {
      long cnt = (data.length / WORD_SIZE - 5) / 5;
      // one sign 1500, half of ecrecover
      return cnt * ENGERYPERSIGN;
    }

    @Override
    public Pair<Boolean, byte[]> execute(byte[] rawData) {
      if (VMConfig.allowTvmOsaka()
          && !isValidAbiEncoding(rawData, ABI_HEADER_WORDS, ABI_ITEM_WORDS)) {
        return Pair.of(false, EMPTY_BYTE_ARRAY);
      }
      DataWord[] words = DataWord.parseArray(rawData);
      byte[] address = words[0].toTronAddress();
      int permissionId = words[1].intValueSafe();
      byte[] data = words[2].getData();

      byte[] combine = ByteUtil.merge(address, ByteArray.fromInt(permissionId), data);
      byte[] hash = Sha256Hash.hash(CommonParameter
          .getInstance().isECKeyCryptoEngine(), combine);

      if (VMConfig.allowTvmSelfdestructRestriction()) {
        int sigArraySize = words[words[3].intValueSafe() / WORD_SIZE].intValueSafe();
        if (sigArraySize > MAX_SIZE) {
          return Pair.of(true, DATA_FALSE);
        }
      }
      byte[][] signatures = VMConfig.allowTvmSelfdestructRestriction() ?
          extractSigArray(words, words[3].intValueSafe() / WORD_SIZE, rawData) :
          extractBytesArray(words, words[3].intValueSafe() / WORD_SIZE, rawData);

      if (signatures.length == 0 || signatures.length > MAX_SIZE) {
        return Pair.of(true, DATA_FALSE);
      }

      AccountCapsule account = this.getDeposit().getAccount(address);
      if (account != null) {
        try {
          Permission permission = account.getPermissionById(permissionId);
          if (permission != null) {
            //calculate weight
            long totalWeight = 0L;
            List<byte[]> executedSignList = new ArrayList<>();
            for (byte[] sign : signatures) {
              byte[] recoveredAddr = recoverAddrBySign(sign, hash);

              sign = merge(recoveredAddr, sign);
              if (ByteArray.matrixContains(executedSignList, recoveredAddr)) {
                if (ByteArray.matrixContains(executedSignList, sign)) {
                  continue;
                }
                MUtil.checkCPUTime();
              }
              long weight = TransactionCapsule.getWeight(permission, recoveredAddr);
              if (weight == 0) {
                //incorrect sign
                return Pair.of(true, DATA_FALSE);
              }
              totalWeight += weight;
              executedSignList.add(sign);
              executedSignList.add(recoveredAddr);
            }

            if (totalWeight >= permission.getThreshold()) {
              return Pair.of(true, dataOne());
            }
          }
        } catch (Throwable t) {
          if (t instanceof OutOfTimeException) {
            throw t;
          }
          logger.info("ValidateMultiSign error:{}", t.getMessage());
        }
      }
      return Pair.of(true, DATA_FALSE);
    }
