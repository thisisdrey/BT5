### Title
Legacy floating-point Bancor-style exchange math allows precision-loss extraction on TRC10 `Exchange` pools - ([File: chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java])

### Summary
The external report describes SVT tokens losing ~$400,000 because an attacker exploited an economic-model/precision loophole in the token's AMM-style pricing contract through repeated buy/sell operations funded by a flash loan. java-tron's on-chain TRC10 `Exchange` feature (bonded via a Bancor-formula relay/"supply") is reachable by any signed account through `ExchangeTransactionActuator`, `ExchangeInjectActuator`, and `ExchangeWithdrawActuator`, and its default (non-hardened) math path performs the core price computation using `double`/`Math.pow` arithmetic instead of exact decimal arithmetic.

### Finding Description
`ExchangeCapsule.transaction()` selects between two pricing engines: the legacy `ExchangeProcessor` (uses `double` arithmetic via `Maths.pow`) and `SafeExchangeProcessor`/`StrictMathWrapper` (uses `BigDecimal`), gated by `hardenedCalc` = `allowHarden()` in `AbstractExchangeActuator`, which itself reads `chainBaseManager.getDynamicPropertiesStore().allowHardenExchangeCalculation()`. [1](#0-0) [2](#0-1) 

The legacy `ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply` compute the bonding-curve relay and output quantity using `double` precision and `Math.pow`, then truncate to `long` via a plain cast: [3](#0-2) 

This is exactly the class of bug the report describes for SVT: a token/pool pricing/accounting formula whose rounding/precision behavior is asymmetric for buy vs. sell (or for different transaction sizes), letting an attacker construct a sequence of small trades (which a flash loan can fund with large temporary capital) that repeatedly extracts value the invariant is supposed to preserve. The `Exchange` capsule's `hardenedCalc` branch adds an explicit non-negative-balance check (`newFirstTokenBalance < 0 || newSecondTokenBalance < 0`) only when hardened math is active, implying the legacy double-based path lacks the same protection against balance drift: [4](#0-3) 

The existence of `SafeExchangeProcessor` (BigDecimal-based, `RoundingMode.HALF_UP`) as a "hardened" alternative, and dedicated tests explicitly showing `testStrictMath` producing **different** results between legacy double math and BigDecimal/strict math for the same inputs, confirms the legacy path is numerically inexact and diverges from the exact economic model: [5](#0-4) 

Because `allowHardenExchangeCalculation` (and `allowStrictMath`) are governed by a committee/proposal parameter rather than being unconditionally enabled, any TRC10 `Exchange` created while the hardened flag is off falls back to the double-precision code path for the lifetime of `ExchangeTransactionActuator`/`ExchangeWithdrawActuator`/`ExchangeInjectActuator` calls against it. An unprivileged account can call these actuators directly and repeatedly (buy then sell against the same pool, potentially amplified by borrowing tokens/TRX before the sequence and repaying after, i.e., the flash-loan pattern) to accumulate residual value from the double-precision truncation errors across many round-trips, draining the pool's balances relative to what the exact Bancor formula would allow.

### Impact Explanation
If exploitable, an attacker can drain TRC10↔TRC10/TRX liquidity held in an on-chain `Exchange` pool — this is direct theft of pooled user/asset-issuer funds without any privileged role, matching the "unauthorized account operation / theft of funds" bar. The blast radius is bounded by the specific exchange's pooled balances, but is fully reachable via ordinary signed `ExchangeTransactionContract`/`ExchangeInjectContract`/`ExchangeWithdrawContract` transactions.

### Likelihood Explanation
Medium: exploitability depends on (a) whether `allowHardenExchangeCalculation`/`allowStrictMath` are enabled network-wide by proposal at the time of attack (if hardened math and `StrictMathWrapper` overflow checks are already active by default on mainnet, the legacy path may be unreachable in practice), and (b) whether the actual per-transaction floating-point error is large enough, and consistently biased in the attacker's favor, to be profitable after fees across many repeated transactions. This could not be fully confirmed from the available index — the concrete default value/activation status of `allowHardenExchangeCalculation` and `allowStrictMath` in `DynamicPropertiesStore` could not be retrieved in the remaining exploration budget.

### Recommendation
- Confirm whether `allowHardenExchangeCalculation` / `allowStrictMath` are enabled by default (or already activated via proposal on mainnet); if not, treat the legacy `ExchangeProcessor` double-math path as unsafe and deprecate/disable it.
- Add the same non-negative and invariant-preserving checks (`newFirstTokenBalance < 0 || newSecondTokenBalance < 0`, overflow-checked arithmetic) to the legacy (non-hardened) `transaction()` branch in `ExchangeCapsule`, not just the hardened branch.
- Add fuzz/property tests that repeatedly round-trip buy/sell on the legacy `ExchangeProcessor` and assert the pool's total value (in a common unit) never increases beyond the fee-adjusted invariant, to detect precision-based value extraction.

### Proof of Concept
Not independently verifiable from static code review alone within the current tooling — reproducing the exploit requires running `ExchangeCapsule.transaction()` with the legacy (non-hardened) processor across many repeated buy/sell cycles on a pool and measuring whether the attacker's net token balance increases beyond the pool's fee/spread, which would require dynamic execution (e.g., a Devin session with test/runtime access) to confirm numerically.

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }
