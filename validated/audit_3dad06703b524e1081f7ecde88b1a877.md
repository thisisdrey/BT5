## Title
Replay-window check-then-decrypt-then-update race allows a captured ciphertext to bypass anti-replay protection - (File: `connection_state.go`)

### Summary
`ConnectionState.Decrypt` and `ConnectionState.VerifyRelay` in `connection_state.go` implement anti-replay protection as three separate critical sections instead of one atomic operation: lock → `window.Check` → unlock, then an unlocked, expensive AEAD decrypt, then lock → `window.Update` → unlock. Because nebula runs multiple concurrent reader goroutines per interface (`f.routines`, see `interface.go`'s `listenOut`/`run`), and relay frames re-enter `readOutsidePackets` recursively (`outside.go`'s `handleOutsideRelayPacket`), two copies of the same captured ciphertext processed concurrently can both pass `Check` before either calls `Update`, letting a replayed packet slip through the anti-replay window and be delivered a second time.

### Finding Description
`Decrypt` performs:
1. `cs.decryptLock.Lock(); result := cs.window.Check(...); cs.decryptLock.Unlock()`
2. `cs.dKey.DecryptDanger(...)` — the expensive, externally-triggerable AEAD operation — done **without holding the lock**
3. `cs.decryptLock.Lock(); result = cs.window.Update(...); cs.decryptLock.Unlock()` [1](#0-0) 

`VerifyRelay` has the identical shape, used on the relay data-plane path: [2](#0-1) 

This is structurally the same class of bug as the external report: a state check is performed, an external/expensive interaction happens while that state is stale, and only afterward is the state mutated to reflect the interaction. In the Reserve Protocol case, the gap was between computing `basketsNeeded`/balances and the token transfer callback; here the gap is between `Bits.Check` (read of the replay window) and `Bits.Update` (write of the replay window), with the costly `DecryptDanger` call sitting unprotected in between.

Nebula is architected for concurrent packet handling: `Interface.run()` launches `f.routines` independent goroutines each calling `listenOut(i)`, which call `readOutsidePackets` on whatever socket/queue receives a given datagram [3](#0-2) [4](#0-3) . `readOutsidePackets` looks up the `HostInfo`/`ConnectionState` purely by wire index and immediately calls `Decrypt` [5](#0-4) . There is no per-hostinfo serialization forcing all packets for one tunnel through a single queue/goroutine, and relay forwarding causes `readOutsidePackets` to be re-entered recursively for the same underlying `hostinfo.ConnectionState` [6](#0-5) , giving an attacker (or just an unlucky scheduling of retransmits/relay hops) additional avenues to have two goroutines processing the same `messageCounter` value concurrently.

Under this race:
- Goroutine A captures/replays ciphertext with counter `N`. It calls `Check(N)` → true (not yet marked).
- Before A calls `Update(N)`, goroutine B (processing a duplicate/racing copy of the same captured packet, or a relay recursion) also calls `Check(N)` → still true, because A hasn't updated the window yet.
- Both A and B proceed to `DecryptDanger` successfully (same valid ciphertext, same key/nonce) and both produce the same plaintext.
- Both then call `Update(N)`; only one of them will find the slot still clear and mark it, but by then **both** decrypts already completed and both callers already treat the packet as authenticated — the losing `Update` only prevents a *third* attempt from succeeding, it does not undo the already-completed decrypt+delivery of the second copy.

The changelog documents the project already fixing bit-level corruption from concurrent `Bits` mutation (“Lock replay window updates so concurrent readers can't corrupt it”) [7](#0-6)  and a related relay double-forward issue (“Advance the replay window on relayed packets…”) [8](#0-7) , but those fixes only protect the internal bitmap data structure from corruption — they do not close the semantic TOCTOU gap between `Check` and `Update` that spans the unlocked `DecryptDanger` call.

### Impact Explanation
This is a replay-handling bypass: an on-path or MITM attacker who has captured one legitimate ciphertext frame (no CA-signed certificate needed — this is a receive-side race, not a signing/authentication bypass) can, by re-delivering the same UDP datagram concurrently (e.g., to multiple `SO_REUSEPORT` queues or via relay-forwarding recursion), cause the packet to be decrypted and delivered to the TUN device (or re-forwarded, on a relay node) more than once despite the anti-replay window's intent to reject duplicates. This directly undermines the guarantee the replay window (`ReplayWindow`, `bits.go`) is supposed to provide, and on relay nodes specifically re-enables the double-forwarding class of issue the project had previously worked to close.

### Likelihood Explanation
Exploitability requires only network position to capture and re-inject a single legitimate ciphertext frame at high concurrency — no cryptographic material or valid certificate is needed, and nebula's own multi-reader-routine and relay-recursion architecture provides the concurrency needed to win the race. The window for the race is bounded by the AEAD decrypt latency, which is short but non-zero and can be widened by contention (e.g., flooding many packets to trigger scheduler preemption between the two lock sections).

### Recommendation
Hold `cs.decryptLock` for the entire check-decrypt-update sequence (or otherwise make `Check`+`Update` atomic with respect to the decrypt) so that no second caller can observe the "not yet seen" state for a counter that is already in-flight being processed by another goroutine. Alternatively, reserve the counter (mark it provisionally "in use") under the lock before releasing it for the decrypt step, and only clear/finalize it after decrypt failure, guaranteeing a given counter can be fully processed by at most one caller at a time.

### Proof of Concept
1. Establish a tunnel and capture one legitimate encrypted `Message` (or relay) frame with counter `N`, e.g. as in `TestRelayReplayProtection` [9](#0-8) .
2. Instead of replaying serially, fire multiple copies of the identical captured UDP datagram at the target near-simultaneously from many goroutines/sockets so they land on different reader queues (`f.routines > 1`) or via a relay recursion path.
3. Because `Check` and `Update` in `connection_state.go` are separate critical sections bracketing the unlocked `DecryptDanger` call, more than one copy can pass `Check` before any `Update` lands, causing more than one successful decrypt+delivery (or more than one relay forward) for the same replayed counter — violating the anti-replay guarantee that `bits.go`'s `Bits.Check`/`Bits.Update` are meant to enforce.

func (cs *ConnectionState) Decrypt(l *slog.Logger, messageCounter uint64, out []byte, packet []byte, nb []byte) ([]byte, error) {
	var err error
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}

	out, err = cs.dKey.DecryptDanger(out, packet[:header.Len], packet[header.Len:], messageCounter, nb)
	if err != nil {
		return nil, err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}
	return out, nil
}

// VerifyRelay verifies AEAD protected (but not encrypted) relay frames. packet must be length-checked by the caller.
func (cs *ConnectionState) VerifyRelay(l *slog.Logger, messageCounter uint64, packet []byte, nb []byte) error {
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	signedPayload := packet[:len(packet)-cs.dKey.Overhead()]
	signatureValue := packet[len(packet)-cs.dKey.Overhead():]
	_, err := cs.dKey.DecryptDanger(nil, signedPayload, signatureValue, messageCounter, nb)
	if err != nil {
		return err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	return nil
}

func (f *Interface) listenOut(i int) {
	var li udp.Conn
	if i > 0 {
		li = f.writers[i]
	} else {
		li = f.outside
	}

	ctCache := firewall.NewConntrackCacheTicker(f.ctx, f.l, f.conntrackCacheTimeout)
	lhh := f.lightHouse.NewRequestHandler()
	plaintext := make([]byte, udp.MTU)
	h := &header.H{}
	fwPacket := &firewall.Packet{}
	nb := make([]byte, 12, 12)

	err := li.ListenOut(func(fromUdpAddr netip.AddrPort, payload []byte) {
		f.readOutsidePackets(ViaSender{UdpAddr: fromUdpAddr}, plaintext[:0], payload, h, fwPacket, lhh, nb, i, ctCache.Get())
	})

	// An error after teardown began is shutdown noise, the closed flag covers resources
	// Close releases itself and the cancelled ctx covers ones torn down by their owners
	// reacting to it, like the user device pipes
	if err != nil && !f.closed.Load() && f.ctx.Err() == nil {
		f.l.Error("Error while reading inbound packet, closing", "error", err)
		f.onFatal(err)
	}

	f.l.Debug("underlay reader is done", "reader", i)
}
