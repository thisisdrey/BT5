### Title
Unbounded Resource Consumption via Never-Completing `PostReceivePack`/`SSHReceivePack` Streams - ([File: internal/gitaly/service/smarthttp/receive_pack.go])

### Summary
Gitaly's push-receiving RPCs (`PostReceivePack` over HTTP, `SSHReceivePack` over SSH) spawn a `git-receive-pack` subprocess as soon as the first stream message (containing only `Repository`/`GlId`) arrives, then block indefinitely reading subsequent stream chunks as the subprocess's stdin. There is no server-enforced timeout on how long a client may take to send (or continue sending) the pack data, and no concurrency limiter is applied to these RPCs by default. An ordinary authenticated user (or, for the SmartHTTP path, an unauthenticated caller if the endpoint is exposed without gitlab-shell/workhorse auth) can open many such streams and trickle data arbitrarily slowly, or never send a `CloseSend`, tying up a git subprocess, goroutines, and pipe file descriptors per stream — directly analogous to CWE-400 "unfinished HTTP/1.1 requests" resource exhaustion.

### Finding Description
`postReceivePack` in `internal/gitaly/service/smarthttp/receive_pack.go` wraps the gRPC stream in a `streamio.NewReader` and passes it directly as stdin to `git-receive-pack --stateless-rpc`, then calls `cmd.Wait()`: [1](#0-0) [2](#0-1) 

The subprocess is spawned before the full stream is consumed and `cmd.Wait()` blocks until the process exits — which itself blocks until stdin is fully drained (EOF) or the process errors. If the client sends data very slowly or never closes the stream, `cmd.Wait()` (and thus the RPC goroutine, the spawned OS process, and any pipes) stay alive for as long as the client wants, with no server-side deadline being enforced on the negotiation/data-transfer phase for this specific RPC.

The same pattern exists for `SSHReceivePack`: [3](#0-2) 

Gitaly does have a purpose-built mitigation for exactly this bug class — `pktline.ReadMonitor`, whose doc comment explicitly describes the "use-after-check" DoS/security risk of a client controlling stdin timing indefinitely after an access check has completed: [4](#0-3) 

However, this mechanism is wired up only for the SSH upload-pack (fetch) negotiation phase: [5](#0-4) 

A repo-wide search confirms `pktline.NewReadMonitor` has exactly one call site outside its own package/tests — `internal/gitaly/service/ssh/upload_command.go`. It is not used by `PostReceivePack`, `SSHReceivePack`, or `PostUploadPackWithSidechannel` (SmartHTTP fetch).

Separately, Gitaly's concurrency-limiting middleware (`internal/grpc/middleware/limithandler`) only creates limiters for RPCs explicitly listed in the operator's `[[concurrency]]` TOML configuration, plus one hardcoded default for `ReplicateRepository`: [6](#0-5) 

`PostReceivePack` and `SSHReceivePack` are not on that default list, so out of the box there is no cap on how many concurrent stalled push streams (and thus subprocesses) a single client/repo can create.

### Impact Explanation
Each stalled `PostReceivePack`/`SSHReceivePack` call holds:
- A live `git-receive-pack` OS process,
- An RPC-serving goroutine blocked in `cmd.Wait()`,
- Associated pipes/file descriptors and (for SSH) an explicit `os.Pipe()` plus copy goroutine.

Because there is no default concurrency limit and no read/negotiation timeout for these specific RPCs, a client can multiply this cost by opening many concurrent pushes and stalling each one, exhausting process table entries, file descriptors, or goroutines/memory on the Gitaly node — a genuine denial-of-service condition reachable from an ordinary authenticated push, matching the report's bug class (resource exhaustion via requests that are opened but never completed).

### Likelihood Explanation
Any authenticated user capable of initiating a `git push` (HTTP or SSH) can trigger this: send the first stream message, then pause or trickle subsequent chunks arbitrarily. No special privilege, token leak, or MITM position is required — this is the same generic capability GitLab's ordinary push flow requires. Default Gitaly configuration ships without an explicit `[[concurrency]]` entry for these RPCs, so the exposure is present unless an operator has proactively added one.

### Recommendation
- Extend the negotiation/read-timeout pattern already implemented by `pktline.ReadMonitor` (currently only used in `internal/gitaly/service/ssh/upload_command.go`) to `PostReceivePack` and `SSHReceivePack`, bounding how long the server will wait for stdin progress before aborting the subprocess and returning a deadline-exceeded error.
- Add default `[[concurrency]]` entries (with sane `max_per_repo`, `max_queue_size`, `max_queue_wait`) for `PostReceivePack` and `SSHReceivePack` similar to the existing default for `ReplicateRepository`, so operators get baseline protection without manual configuration.
- Consider an idle-read timeout on the underlying gRPC stream reads themselves (independent of the git subprocess), so a stalled client cannot indefinitely pin a goroutine/process regardless of RPC.

### Proof of Concept
1. As an authenticated user with push access, open a `PostReceivePack` gRPC stream and send only the first message (`Repository`, `GlId`) as required by `validateReceivePackRequest`.
2. Do not send further `Data` frames (or send them at a very slow trickle, e.g., one byte every few minutes) and never call `CloseSend`.
3. Observe that Gitaly spawns and keeps alive a `git receive-pack --stateless-rpc` process indefinitely, with the RPC goroutine blocked in `cmd.Wait()`.
4. Repeat steps 1–3 concurrently across many streams/repositories; since no default concurrency limiter is configured for this RPC, subprocess/goroutine/FD counts grow unbounded until the node is resource-exhausted.

func (s *server) sshReceivePack(stream gitalypb.SSHService_SSHReceivePackServer, req *gitalypb.SSHReceivePackRequest) (returnedErr error) {
	ctx := stream.Context()

	stdin := streamio.NewReader(func() ([]byte, error) {
		request, err := stream.Recv()
		return request.GetStdin(), err
	})

	var m sync.Mutex
	stdout := streamio.NewSyncWriter(&m, func(p []byte) error {
		return stream.Send(&gitalypb.SSHReceivePackResponse{Stdout: p})
	})

	// We both need to listen in on the stderr stream in order to be able to judge what exactly
	// is happening, but also relay the output to the client. We thus create a MultiWriter to
	// enable both at the same time.
	var stderrBuilder strings.Builder
	stderr := streamio.NewSyncWriter(&m, func(p []byte) error {
		return stream.Send(&gitalypb.SSHReceivePackResponse{Stderr: p})
	})
	stderr = io.MultiWriter(&stderrBuilder, stderr)

	repoPath, err := s.locator.GetRepoPath(ctx, req.GetRepository())
	if err != nil {
		return err
	}

// ReadMonitor monitors an io.Reader, waiting for a specified packet. If the
// packet doesn't come within a timeout, a cancel function is called. This can
// be used to place a timeout on the *negotiation* phase of some git commands,
// aborting them if it is exceeded.
//
// This timeout prevents a class of "use-after-check" security issue when the
// access check for a git command is run before the command itself. The user
// has control of stdin for the git command, and if they can delay input for
// an arbitrarily long time, they can gain access days or weeks after the
// access check has completed.
//
// This approach is better than placing a timeout on the overall git operation
// because there is a conflict between mitigating the use-after-check with a
// short timeout, and allowing long-lived git operations to complete. The
// negotiation phase is a small proportion of the time taken for a large git
// fetch, for instance, so tighter limits can be placed on it, leading to a
// better mitigation.
