### Title
Relayer reward is paid on Snowbridge outbound delivery receipts regardless of message execution success - (File: bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs)

### Summary
`Pallet::process_delivery_receipt` in `pallet-outbound-queue-v2` unconditionally pays the full relayer fee for any nonce present in `PendingOrders`, without checking the `success` field of the decoded `DeliveryReceipt`. This mirrors the external report's broken invariant: a settlement/payout path that skips a critical validity check (there, undercollateralization slippage; here, delivery success), letting an unprivileged actor cause an incorrect state transition to be accepted as final.

### Finding Description
`DeliveryReceipt` is decoded from the Ethereum `InboundMessageDispatched(uint64 nonce, bytes32 topic, bool success, bytes32 reward_address)` event log [1](#0-0) . The `success` field explicitly exists to indicate whether the outbound message's execution/dispatch on Ethereum succeeded.

In `Pallet::submit_delivery_receipt`, once the merkle/verifier proof for the event log is valid, the receipt is passed straight to `process_delivery_receipt` [2](#0-1) .

`process_delivery_receipt` only validates the `gateway` address and looks up the `PendingOrders` entry by `nonce`; it never reads or branches on `receipt.success` before paying the reward: [3](#0-2) 

Because the message was verifiably emitted by the real Gateway contract (proof is legitimate), any relayer who gets the message dispatched on Ethereum — even one that intentionally fails/reverts inside the message's Transact/command execution so that `success = false` is emitted — will still receive the full `order.fee` reward on BridgeHub. No unprivileged/permissionless retry, penalty, or reduced-fee path exists for failed deliveries; the outcome (paid vs not) is identical in both cases.

### Impact Explanation
This breaks the "settle exactly once, only after successful execution" invariant for bridge payout state described in the Pivots: `Message queues, bridge markers, receipts, and payout state must only advance after decode, dispatch, execution, and settlement succeed atomically.` Here, `PendingOrders` is removed and the reward is registered even when execution failed, decoupling payout from actual successful delivery. This is a public, unprivileged-relayer-triggerable state/fund-flow bug (any address can call `submit_delivery_receipt` once it has a valid proof of an emitted event, and the emitted event's `success` value depends only on what happened during dispatch, not on relayer honesty) that results in relayer rewards being paid for messages that did not actually get correctly delivered/executed — a form of unbacked/incorrect payout under the "duplicate settlement or payout" / "public underpriced work" category.

### Likelihood Explanation
Likelihood is high: the check simply doesn't exist, so no race condition or edge case needs to be hit — every failed-but-emitted delivery (e.g. a message whose commands revert on the Ethereum Gateway due to insufficient gas allocation, a malformed Transact payload, or intentional self-sabotage by the relayer submitting the underlying transaction) results in full reward payment. No admin, governance, or malicious-validator assumption is needed; only a permissionless relayer acting through the normal `submit_delivery_receipt` flow.

### Recommendation
In `process_delivery_receipt`, branch on `receipt.success` before paying the reward: pay full/agreed fee only when `success == true`; when `false`, either withhold/reduce the reward, keep the order pending for retry, or route it to a distinct failure-handling path (e.g. re-enqueue or refund the original sender) so that `PendingOrders` removal and reward issuance are conditioned on the delivery actually having succeeded.

### Proof of Concept
1. A message with `fee = F` is queued through `do_process_message`, creating `PendingOrders[nonce] = { nonce, fee: F, ... }` [4](#0-3) .
2. Any relayer relays the message to the Ethereum Gateway but arranges for the command dispatch to fail on-chain (e.g., under-supplying gas for the inner Transact, or targeting a call that reverts) such that the Gateway emits `InboundMessageDispatched(nonce, topic, success=false, reward_address)`.
3. The relayer fetches this real event log and its proof and submits `submit_delivery_receipt(event)` on BridgeHub.
4. `T::Verifier::verify` succeeds because the log genuinely exists on Ethereum; `DeliveryReceipt::try_from` decodes `success: false` correctly.
5. `process_delivery_receipt` ignores `receipt.success`, finds the `PendingOrders` entry, and calls `T::RewardPayment::register_reward(&reward_account, ..., order.fee)` for the full fee [5](#0-4) , then removes the order and emits `MessageDelivered`, even though the message was not successfully delivered/executed.

Note: I was not able to fully verify from the index whether any downstream consumer (e.g., a runtime-level hook) re-checks `success` before or after this pallet call, since `T::RewardPayment` is a generic trait implemented per-runtime; a Devin session with full repo access should confirm no such check exists at the `BridgeRewardPayer`/`pallet-bridge-relayers` integration layer before treating this as final.

		/// Process a delivery receipt from a relayer, to allocate the relayer reward.
		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}
