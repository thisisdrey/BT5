### Title
Single-step, irreversible `AccountPermissionUpdate` allows instant, unconfirmed replacement of an account's owner permission - (File: `actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java`)

### Summary
`AccountPermissionUpdateContract`/`AccountPermissionUpdateActuator` is the java-tron analog of Solidity's `Ownable.transferOwnership()`: it lets the current owner permission replace the account's `owner`, `witness`, and `active` permissions in a single atomic transaction, with no two-step "propose then accept" confirmation from the incoming key holder, exactly the pattern criticized in the referenced report.

### Finding Description
`AccountPermissionUpdateActuator.execute()` unconditionally overwrites the account's owner permission with whatever `Permission` is supplied in the contract, via `AccountCapsule.updatePermissions()`: [1](#0-0) [2](#0-1) 

`updatePermissions` fully replaces `ownerPermission` (`builder.setOwnerPermission(owner)`), discarding the old set of keys entirely, so as soon as the transaction is applied the previous owner key(s) lose all authority over the account, including the authority to submit any future `AccountPermissionUpdate` correcting the mistake.

`validate()`/`checkPermission()` only check syntactic well-formedness of the new keys (valid address format, non-zero weight, distinct addresses, threshold reachable by weight sum, key/permission counts within limits): [3](#0-2) 

There is no requirement that the new key addresses be proven-controlled (e.g., a matching signature from the new key, or a pending/accept step) before the swap takes effect — unlike OpenZeppelin's `Ownable2Step`, which requires the pending owner to call `acceptOwnership()` before the transfer is finalized.

### Impact Explanation
If a user submits an `AccountPermissionUpdateContract` with a typo'd, unreachable, or otherwise uncontrolled address for the new `owner` permission, the account's owner authority is destroyed irrecoverably in that single transaction — there is no fallback keyholder and no on-chain path to reverse it, since the old owner key(s) are simultaneously revoked. Any TRX/TRC10/frozen-resource balance controlled solely by that owner permission becomes permanently inaccessible (permanent freezing of funds), because every future `onlyOwner`-equivalent action (further `AccountPermissionUpdate`, withdrawal via required-signature multisig, resource management, etc.) now requires signatures the sender no longer holds.

### Likelihood Explanation
This is triggerable by any unprivileged account holder in a single signed transaction once multi-sign is enabled (`AllowMultiSign == 1`), which is standard, expected TRON functionality (not a privileged/insider-only path) reachable through the normal actuator validate/execute flow and exposed via the public Wallet/HTTP `updateaccountpermission` API. No malicious third party, SR, or node operator involvement is required — a routine self-service key-management action fails unsafely with no recovery path, mirroring the exact risk pattern flagged in the referenced Ownable single-step transfer report.

### Recommendation
Introduce a two-step confirmation flow analogous to `Ownable2Step` for owner-permission changes: require the transaction to stage the new owner permission and only finalize/activate it once a transaction signed by the new owner key(s) explicitly accepts it (or at minimum require the new owner permission's own signature to co-sign the `AccountPermissionUpdateContract` proving control of the new key set before the old owner permission is overwritten).

### Proof of Concept
1. Attacker/careless user submits `AccountPermissionUpdateContract` for `ownerAddress` A, setting `owner` Permission keys to address B, where B's private key is unknown/mistyped/lost.
2. `AccountPermissionUpdateActuator.validate()` passes because B is a syntactically valid TRON address, distinct, non-zero weight, threshold satisfied. [4](#0-3) 
3. `execute()` calls `account.updatePermissions(owner, ...)`, replacing A's owner permission with the one referencing only B. [5](#0-4) 
4. From this block forward, no transaction signed by A's original key(s) satisfies `account.getPermissionById(0)` (owner) any longer, since `updatePermissions` discarded them; if B's key is unusable, the account's owner-permission-gated funds/operations are permanently locked with no recovery mechanism in the protocol.

  public void updatePermissions(Permission owner, Permission witness, List<Permission> actives) {
    Builder builder = this.account.toBuilder();

    owner = owner.toBuilder().setId(0).build();
    builder.setOwnerPermission(owner);
    if (witness != null && builder.getIsWitness()) {
      witness = witness.toBuilder().setId(1).build();
      builder.setWitnessPermission(witness);
    }

    builder.clearActivePermission();
    if (actives != null) {
      for (int i = 0; i < actives.size(); i++) {
        Permission permission = actives.get(i).toBuilder().setId(i + 2).build();
        builder.addActivePermission(permission);
      }
    }

    this.account = builder.build();
  }
