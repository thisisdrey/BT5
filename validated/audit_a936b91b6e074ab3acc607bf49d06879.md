## Title
Permanent channel lockout via strict sequential-nonce enforcement combined with atomic dispatchable rollback in Snowbridge Inbound Queue (V1) - (File: `bridges/snowbridge/pallets/inbound-queue/src/lib.rs`)

## Summary
`Pallet::submit` performs a strict, sequential nonce check (`envelope.nonce != nonce.saturating_add(1)`) and mutates `Nonce<T>` *before* payload decode, XCM conversion, fee burning, and `send_xcm` are attempted, yet the entire call is auto-wrapped in `with_storage_layer` by the pallet macro, so any later, deterministic failure unwinds the nonce mutation along with everything else. Since a message must exactly match `last_nonce + 1`, any message whose conversion or dispatch step fails deterministically becomes permanently unprocessable and blocks every subsequent message on that channel, with no on-chain recovery path.

## Finding Description
The confirmed code path is: [1](#0-0) 
performs the nonce check/advance strictly before: [2](#0-1) 
decodes the payload, converts to XCM via `do_convert`/`T::MessageConverter::convert`, burns fees, and calls `send_xcm`. `Error<T>` maps `SendXcm` failures (`ExceedsMaxMessageSize`, `DestinationUnsupported`, `NotRoutable`, etc.) into pallet errors that abort the call: [3](#0-2) . Every `#[pallet::call]` dispatchable, including `submit`, is wrapped in `with_storage_layer` by the procedural macro [4](#0-3) , whose semantics are "any `Err` rolls back all storage writes made in the call" [5](#0-4) . Because the nonce advance happens inside this same transactional scope, a downstream deterministic failure (in `do_convert` or `send_xcm`) reverts `Nonce<T>` for that channel every time the identical proof is resubmitted, and the equality check `envelope.nonce != nonce.saturating_add(1)` in `<Nonce<T>>::try_mutate` [6](#0-5)  means no message with a higher nonce can ever be accepted for that channel afterward.

I verified that `T::MessageConverter::convert` (the production `MessageToXcm` implementation) *can* deterministically fail for a well-formed, successfully-decoded message: `convert_send_native_token` unconditionally returns `Err(ConvertMessageError::InvalidDestination)` for any `Destination` other than `AccountId32` [7](#0-6) , and `CannotReanchor`/`InvalidToken`/`UnsupportedFeeAsset` are similarly possible pure-function outcomes based purely on message fields and static config (`GlobalAssetHubLocation`, `EthereumUniversalLocation`, `ConvertAssetId`) [8](#0-7) , none of which are re-evaluated across retries — meaning any message triggering one of these branches will fail identically forever. I also confirmed the pallet exposes no nonce-skip, force-advance, or dead-letter mechanism; `set_operating_mode` only halts/resumes the entire pallet [9](#0-8) , and a search of the bridge crates found no `execute_overweight`/`skip_nonce`/`force_set_nonce` equivalent.

One mitigating factor I could not fully rule in or out: for `SendToken`/`RegisterToken`, all XCM instructions are built from fixed-size primitive fields (`H160`, `u128`, `[u8;32]`/`[u8;20]`, enum variants) with no unbounded attacker-controlled strings/vectors, so the "oversized payload exceeds `SendXcm` max message size" scenario in the original PoC is not obviously reachable through the current `MessageToXcm` implementation — message size is essentially fixed regardless of attacker input. The top-level `send_xcm` destination (`channel.para_id`) also comes from `T::ChannelLookup::lookup`, a pre-registered/trusted mapping, not directly attacker-controlled, making "unroutable destination" for the *outer* `send_xcm` call unlikely in a correctly configured runtime. However, the `CannotReanchor`/`InvalidDestination` failure modes in `convert_send_native_token` demonstrate the same class of deterministic, non-recoverable failure is reachable through `do_convert` alone, independent of `send_xcm` sizing concerns, and no such gate exists to reject these messages before the nonce mutation commits.

## Impact Explanation
This matches the "permanent... bridge-state lock" / "message queues... must only advance after decode, dispatch, execution, and settlement succeed atomically" impact category. A single message that decodes successfully but deterministically fails at `ConvertMessage::convert` (e.g., `SendNativeToken` with a non-`AccountId32` destination, or a mis-mapped `TokenId` causing `CannotReanchor`) permanently halts `Nonce<T>` advancement for that `channel_id`, blocking all subsequent legitimate messages on that channel indefinitely, with no on-chain remediation short of a runtime upgrade.

## Likelihood Explanation
Whether this is practically triggerable depends on constraints enforced by the off-repo Solidity Gateway contract, which is out of scope here — the code comment in `convert_send_native_token` notes that the `InvalidDestination` case is "validated on the Ethereum side," which may prevent that specific trigger in practice. However, other deterministic failure modes (`CannotReanchor`, `InvalidToken`, `UnsupportedFeeAsset`) depend on on-chain `ConvertAssetId`/location config and registered `TokenId` mappings rather than Ethereum-side Solidity validation, and are not defended against by the pallet at all. The root architectural flaw — atomic rollback of the nonce advance whenever any downstream step fails, combined with strict sequential nonce enforcement and no skip mechanism — is fully confirmed in-repo and requires no privileged actor to exploit once a qualifying message reaches `submit`.

## Recommendation
- Decouple replay-protection bookkeeping (nonce advance) from downstream processing outcomes: record the nonce as consumed even if XCM conversion/dispatch fails, routing failures to a recoverable/parked state instead of aborting the whole call and rolling back the nonce.
- Add a governance-gated mechanism to explicitly skip/park a nonce whose conversion or dispatch deterministically fails, analogous to `pallet-message-queue`'s permanent-unprocessable handling.
- Add test coverage submitting a `SendNativeToken` message with a non-`AccountId32` destination (or an unreanchorable `TokenId`) and asserting that (a) it fails as expected and (b) subsequent, valid higher-nonce messages remain deliverable after remediation — currently they would not be.

## Proof of Concept
1. Register a `TokenId` via `RegisterToken`/governance whose associated `Location` (via `ConvertAssetId::maybe_convert`) cannot be reanchored against `GlobalAssetHubLocation`/`EthereumUniversalLocation` (or otherwise construct a `SendNativeToken` message with a non-`AccountId32` `Destination`).
2. Have this message emitted from the Ethereum Gateway as nonce `N` for a channel, decode-valid and verifier-valid.
3. Relayer calls `submit(origin, event)`: verification, decode, gateway/channel checks pass; `Nonce<T>` is mutated to `N` inside `<Nonce<T>>::try_mutate`; `do_convert` then returns `Err(ConvertMessageError::CannotReanchor)` (or `InvalidDestination`), causing `submit` to return `Err`.
4. Because `submit` runs inside `with_storage_layer`, the entire call — including the `Nonce<T>` mutation — is rolled back; on-chain `Nonce<T>` remains at `N-1`.
5. Retrying `submit` with the same proof fails identically every time (deterministic, proof data unchangeable).
6. Any subsequent message with nonce `> N-1` for that channel is rejected by `Error::<T>::InvalidNonce`, permanently halting the channel.

```rust
/// Execute the supplied function, adding a new storage layer.
///
/// This is the same as `with_transaction`, but assuming that any function returning an `Err` should
/// rollback, and any function returning `Ok` should commit. This provides a cleaner API to the
/// developer who wants this behavior.
pub fn with_storage_layer<T, E, F>(f: F) -> Result<T, E>
where
	E: From<DispatchError>,
	F: FnOnce() -> Result<T, E>,
{
	with_transaction(|| {
		let r = f();
		if r.is_ok() {
			TransactionOutcome::Commit(r)
		} else {
			TransactionOutcome::Rollback(r)
		}
	})
}
```
