### Title
Unescaped colon in `GIT_ALTERNATE_OBJECT_DIRECTORIES` allows alternate object search-path injection - (File: `internal/git/alternates/alternates.go`)

### Summary
`alternates.Env` builds the `GIT_ALTERNATE_OBJECT_DIRECTORIES` environment variable by naively joining a list of directory paths with `:` (the POSIX `PATH_LIST_SEPARATOR`), without ever checking whether an individual path already contains a `:` character. Since Gitaly's own relative-path validation does not forbid `:` (it only rejects traversal outside the repository/storage root), a caller-supplied `GitObjectDirectory`/`GitAlternateObjectDirectories` value containing a colon will be silently mis-parsed by Git as two separate search-path entries. This is the same bug class as the external report: a separator character that is meaningful to a downstream consumer is not rejected/escaped when building a composite identifier, corrupting the resulting value.

### Finding Description
`internal/git/localrepo/paths.go` `ObjectDirectoryPath()` validates `repo.GetGitObjectDirectory()` only for path-traversal safety via `storage.ValidateRelativePath`: [1](#0-0) 

There is no check anywhere that rejects a `:` character in `GitObjectDirectory` or in any entry of `GitAlternateObjectDirectories`. Both fields are ordinary public fields on the `Repository` gRPC message that any caller can set on any request carrying a `Repository`: [2](#0-1) 

When Gitaly spawns a Git subprocess, it calls `alternates.Env`, which joins every entry of `alternateObjectDirectories` with `filepath.Join(repoPath, dir)` and then concatenates the resulting list with a literal `":"`: [3](#0-2) 

This is invoked on every Git command for a repository: [4](#0-3) 

If an alternate-directory string supplied by the request contains a `:` (which passes `ValidateRelativePath` because `:` is a legal path-component character on POSIX and is not a traversal sequence), the resulting joined absolute path — e.g. `/storage/repo/some:extra` — gets embedded as a single string in the env value. Git itself (and any downstream parser, e.g. Gitaly's own quarantine/hook re-parsing logic in `internal/gitaly/hook/prereceive.go` which reads `GIT_ALTERNATE_OBJECT_DIRECTORIES` back via `env.ExtractValue`) will treat the `:` as a field separator and split the single intended path into two independent path fragments — `/storage/repo/some` and `extra`. The second fragment is not anchored to the storage root at all; it is interpreted directly by Git relative to its current working directory, entirely bypassing the traversal-safety checks that were performed on the original (unsplit) string. [5](#0-4) 

This exactly mirrors the external report's bug class: a reserved delimiter character (`:`) is not rejected before being embedded into a colon-delimited composite value, so validation performed on the pre-split string does not apply to the post-split fragments.

### Impact Explanation
Because the alternate/object-directory fields flow into the Git object search path used by every git invocation for the repository (including within the pre-receive hook's authorization callback flow, where Gitaly re-derives `repo.GitObjectDirectory`/`GitAlternateObjectDirectories` from the environment and forwards them to GitLab's `Allowed` API and to subsequent RPCs), a crafted value can:
- corrupt Git's alternates search path, causing legitimate quarantined objects to become invisible to Git commands (denial of service for that push/RPC — commands that should find the pushed objects fail with "object not found"), or
- cause Git to search an unintended location outside of the intended repository/storage sandbox (the split-off fragment is not subject to `ValidateRelativePath`'s traversal checks), which is a storage isolation/argument-injection bypass consistent with "cross-repository object access" or "storage escape" impact categories.

The severity is bounded by the fact that the attacker only controls the content, not the ability to make Git execute arbitrary code — but it functionally defeats the intended path-validation boundary and can produce a reliable DoS against pushes/RPCs that rely on the alternates mechanism (analogous to the "permanent DoS" nature of the original report, since any repository/RPC path containing this pattern will consistently misbehave, not just under an attacker's active exploitation).

### Likelihood Explanation
Exploitability requires only that an ordinary/unprivileged gRPC client set a `GitObjectDirectory`/`GitAlternateObjectDirectories` entry containing a `:`. These are plain string fields on the widely-used `Repository` message present in virtually every Gitaly RPC, and are not restricted to Gitaly-internal callers at the protocol level — they are only validated for traversal, not for `:`. This makes the trigger straightforward for anyone able to issue Gitaly RPCs (a "crafted RPC field" scenario matching the validated scan criteria), without requiring privileged access, a leaked token, or a malicious peer.

### Recommendation
Reject (or escape) any path component containing the OS path-list separator (`:` on POSIX) in `GitObjectDirectory` and `GitAlternateObjectDirectories` during repository-field validation (e.g., in `storage.ValidateRelativePath` or in `ObjectDirectoryPath`/`alternates.Env`), so that a single logical alternate directory can never be split into multiple entries by Git or by Gitaly's own environment re-parsing logic.

### Proof of Concept
1. Issue any Gitaly RPC that carries a `Repository` message and reaches `alternates.Env` (e.g., via a repository-scoped RPC), setting:
   - `git_object_directory = "objects"`
   - `git_alternate_object_directories = ["objects/incoming-1:../../../other-storage-path"]`
2. `ValidateRelativePath` accepts this string because it contains no `..` traversal at the top level and stays formally "within" the repository directory structure as a single string.
3. `alternates.Env` produces:
   `GIT_ALTERNATE_OBJECT_DIRECTORIES=/storage/repo/objects/incoming-1:../../../other-storage-path`
4. Git (and Gitaly's `env.ExtractValue`/`getRelativeObjectDirs` re-parsing in the pre-receive hook flow) splits this on `:` into two directories: `/storage/repo/objects/incoming-1` and `../../../other-storage-path`, the latter resolved relative to the Git process's working directory rather than the validated repository root — demonstrating that the colon delimiter defeats the intended traversal validation, exactly as the external report's unescaped `:` defeated the NFT token-ID validator.

```go
// Env returns the alternate object directory environment variables.
func Env(repoPath, objectDirectory string, alternateObjectDirectories []string) []string {
	var env []string
	if objectDirectory != "" {
		env = append(env, fmt.Sprintf("GIT_OBJECT_DIRECTORY=%s", filepath.Join(repoPath, objectDirectory)))
	}

	if len(alternateObjectDirectories) > 0 {
		var dirsList []string

		for _, dir := range alternateObjectDirectories {
			dirsList = append(dirsList, filepath.Join(repoPath, dir))
		}

		env = append(env, fmt.Sprintf("GIT_ALTERNATE_OBJECT_DIRECTORIES=%s", strings.Join(dirsList, ":")))
	}

	return env
}
```
