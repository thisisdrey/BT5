### Title
Deleted-account promise-yield state (`PromiseYieldReceipt`/`PromiseYieldStatus`) is never cleaned up, letting a stale timeout deliver and execute against a later-created same-named account - (`File: runtime/runtime/src/actions.rs`, `runtime/runtime/src/lib.rs`)

### Summary
`action_delete_account` calls `remove_account` to clean up an account's state, but never removes the account's outstanding `TrieKey::PromiseYieldReceipt` / `TrieKey::PromiseYieldStatus` entries. `resolve_promise_yield_timeouts` later resolves a queued `PromiseYieldTimeout{index}` purely by `account_id`/`data_id` string identity, with no check that the account is still the same incarnation that created the yield. If the account name is deleted and re-created before the timeout fires, the stale parked `ActionReceipt` is delivered to and executed against the new occupant of that account name.

### Finding Description
- `promise_yield_create` (`runtime/near-vm-runner/src/wasmtime_runner/logic.rs:3959`) creates a `PromiseYield` receipt and enqueues a `PromiseYieldTimeout{account_id, data_id, expires_at}` entry keyed only by a global FIFO index (`core/store/src/utils/mod.rs:182-198`, `TrieKey::PromiseYieldTimeout{index}` in `core/primitives/src/trie_key.rs:239-241`).
- When the `PromiseYield` receipt is processed it is stored as `TrieKey::PromiseYieldReceipt{receiver_id, data_id}` (`core/store/src/utils/mod.rs:200-212`, `runtime/runtime/src/lib.rs:1495-1499`), a key that is keyed by `AccountId` string, not tied to any per-account incarnation/generation identifier.
- `action_delete_account` (`runtime/runtime/src/actions.rs:314-390`) computes storage usage, burns gas-key balances, refunds the account balance, and calls `remove_account(state_update, account_id)` (line 371) - but nowhere in this function, nor in `remove_account`'s call site, is `remove_promise_yield_receipt`/`remove_promise_yield_status` invoked. The `remove_account` return value only reports `gas_key_nonce_count`/`gas_key_nonce_total_key_bytes`, indicating it targets specific known account-scoped columns (access keys, gas keys, contract data) rather than sweeping every column that could be keyed by the account name, including the promise-yield columns.
- `resolve_promise_yield_timeouts` (`runtime/runtime/src/lib.rs:3009-3116`) processes the timeout queue strictly by global index and `expires_at` order (line 3025-3044). For an expired entry it only checks `state_update.contains_key(&promise_yield_key)` where `promise_yield_key = TrieKey::PromiseYieldReceipt{receiver_id: queue_entry.account_id, data_id: queue_entry.data_id}` (lines 3047-3051) - there is no check that the account currently named `queue_entry.account_id` is the same account that originally created the yield.
- If that key is still present because it was never cleaned up at deletion time, a `PromiseResume{data: None}` receipt is synthesized with `predecessor_id = receiver_id = queue_entry.account_id` (lines 3060-3068) and forwarded/buffered to be delivered locally.
- On delivery, `process_receipt` for `PromiseResume` (`runtime/runtime/src/lib.rs:1500-1518`) again looks up `get_promise_yield_receipt(state_update, account_id, data_id)` by the same string-keyed identity, finds the stale parked `ActionReceipt` from the deleted incarnation, and executes it via the normal action-receipt path against whatever account/contract now occupies `alice.near`.

None of the existing checks (signature/nonce validation, access-key permissions, storage staking) address this because the exploit does not forge any signature or access key - it relies purely on the ordinary DeleteAccount → CreateAccount sequence and the runtime's failure to invalidate promise-yield state tied to the old account instance.

### Impact Explanation
This is a cross-account authorization/determinism violation: an action receipt created under the semantics and intent of the original `alice.near` (arbitrary method name/args baked into the parked receipt at `promise_yield_create` time) is delivered into and executed against a completely different, unrelated account that merely happens to reuse the name. Depending on what the new account deploys, this can corrupt the new occupant's contract state, unexpectedly invoke privileged callback methods (e.g., `ft_resolve_transfer`-style callbacks) against the wrong balances/storage, or fail/spam with `MethodNotFound` errors - in all cases violating account isolation determinism. This matches the "authorization escalation across accounts or promises" bounty category.

### Likelihood Explanation
Preconditions are entirely reachable by unprivileged actors: (1) any account can call `promise_yield_create` with a large `yield_timeout_length_in_blocks`-bounded `expires_at`, (2) any account owner can self-delete via `DeleteAccount`, and (3) any other party can subsequently submit `CreateAccount` for the now-vacant name (subject to normal TLA registrar rules, not attacker-controlled but not a blocker either). The attacker/victim overlap is unusual - it requires the *original* account owner to voluntarily delete their own account while a yield is outstanding, and requires someone else to claim the name before timeout - which is a narrower, more contrived scenario than a pure single-attacker exploit, but it is a genuine determinism/state-corruption bug reachable through ordinary transactions with no privileged access, and it is deterministically repeatable.

### Recommendation
On `DeleteAccount`, enumerate and remove any outstanding `PromiseYieldReceipt`/`PromiseYieldStatus`/pending timeout-queue entries associated with the account before finalizing deletion (or maintain a per-account generation counter included in the `PromiseYieldTimeout`/`PromiseYieldReceipt` keys so a later re-created account with the same name cannot match stale entries). Alternatively, when a `DeleteAccount` occurs, immediately execute or drop all of that account's still-queued yields, and reject `CreateAccount` for a name until all such deferred obligations against it have drained.

### Proof of Concept
Test-loop integration test:
1. Deploy a contract on `alice.near` that calls `promise_yield_create` with `expires_at` far in the future, storing/no-op'ing on timeout callback; capture the `data_id`.
2. Submit `DeleteAccount(alice.near, beneficiary)` from `alice.near`.
3. Submit `CreateAccount(alice.near)` funded/controlled by an unrelated account, optionally deploying a different contract with observable state (e.g., a counter).
4. Advance blocks to `expires_at`; run `process_receipts` so `resolve_promise_yield_timeouts` fires.
5. Assert: a `PromiseResume` receipt is produced with `receiver_id == alice.near` and executes against the *new* `alice.near` account (verify via `get_promise_yield_receipt`/execution outcome logs or observable state mutation on the new contract), demonstrating the timeout callback bound to the old owner's yield is delivered into the new occupant's account rather than being dropped - violating account-isolation determinism.
