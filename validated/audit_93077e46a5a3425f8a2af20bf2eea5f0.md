### Title
Atlas attachment downloader never enforces `AtlasConfig::attachments_max_size` on attachments fetched from peers - ([File: stackslib/src/net/atlas/download.rs], [File: stackslib/src/net/api/getattachment.rs])

### Summary
`StacksHttpResponse::decode_atlas_get_attachment` decodes a `GetAttachmentResponse` body with no size check, and `AttachmentsBatchStateContext::extend_with_attachments` unconditionally inserts the decoded `Attachment` into its result set, which is later persisted via `AtlasDB::insert_instantiated_attachment` without ever calling `AtlasDB::should_keep_attachment` (the only function in the codebase that enforces `attachments_max_size`). A malicious peer that the node has selected as an attachment source can therefore return an oversized attachment payload that is stored to the local Atlas DB, breaking the intended invariant that stored attachment size never exceeds `attachments_max_size`.

### Finding Description
The invariant the config is supposed to guarantee is: for every attachment stored in `AtlasDB`, `content.len() as u32 <= atlas_config.attachments_max_size`. That check exists in exactly one place, `AtlasDB::should_keep_attachment`: [1](#0-0) 
which is used by the transaction-with-attachment POST path (`posttransaction.rs`), not by the peer-to-peer Atlas downloader.

The downloader path is:
1. `StacksHttpResponse::decode_atlas_get_attachment` just JSON-decodes the body into a `GetAttachmentResponse` with no size validation: [2](#0-1) 
2. `AttachmentsBatchStateContext::extend_with_attachments` takes any successfully-decoded response and inserts `response.attachment` into `self.attachments` (a `HashSet<Attachment>`) with no length check: [3](#0-2) 
3. When the state machine reaches `Done`, every attachment in `context.attachments` is persisted directly via `AtlasDB::insert_instantiated_attachment`, again with no size check and without calling `should_keep_attachment`: [4](#0-3) [5](#0-4) 

`GetAttachmentResponse`'s deserializer only hex-decodes an arbitrary-length string into `Attachment::content`, imposing no bound: [6](#0-5) 

Root cause: the size-limiting logic (`should_keep_attachment`) was implemented only for the "attachment submitted with a transaction" ingestion path, but the Atlas gossip/download ingestion path (which fetches attachments from arbitrary remote peers via `/v2/attachments/{hash}`) bypasses it entirely.

Attack flow: the attacker runs a normal Stacks peer that is selected as a data-serving peer for Atlas sync (e.g., by advertising availability in its `/v2/attachments/inv` response for content the node needs). When the node's `AttachmentsDownloader` requests `/v2/attachments/{hash}` from the attacker's node, the attacker's HTTP server returns a `GetAttachmentResponse` JSON body whose hex-encoded `content` is arbitrarily large (only bounded by whatever generic HTTP framing limits exist in `stackslib/src/net/http.rs`, which are unrelated to and not derived from `attachments_max_size`). This response is decoded and stored without any size check.

### Impact Explanation
A remote, unprivileged peer that becomes an attachment source for a victim node can cause that node's `AtlasDB` (a persistent sqlite database) to store attachment content of unbounded size (limited only by generic HTTP transport limits, not by the node operator's configured `attachments_max_size`), defeating the configured resource cap intended to bound Atlas storage growth. This is repeatable per attachment instance the node needs to resolve, and can be repeated across many attachment instances over time, leading to storage growth on the victim node beyond its configured/expected bound.

### Likelihood Explanation
Preconditions: the victim node must need to resolve an on-chain-committed attachment instance (e.g., BNS name registration) and must select the attacker as a download source, which requires only that the attacker (a) be an outbound-sync peer of the victim, and (b) advertise (truthfully or not, since there is no hash-match verification in this code path either) that it has the attachment in its `/v2/attachments/inv` response. Both are within the capability of an unprivileged remote party running their own peer that is naturally used in Atlas sync. No secrets, admin roles, or privileged access are required. This is directly reachable and repeatable.

### Recommendation
In `AttachmentsBatchStateContext::extend_with_attachments` (or in `AtlasDownloader::process`/before `insert_instantiated_attachment`), reject/drop any decoded attachment whose `content.len() as u32 > atlas_config.attachments_max_size`, mirroring the check already implemented in `AtlasDB::should_keep_attachment`. Ideally route all attachment ingestion (both POST-supplied and peer-downloaded) through a single size- and hash-checked insertion function.

### Proof of Concept
Rust test in `stackslib/src/net/atlas/download.rs` (or `tests.rs`):
1. Build an `AttachmentsBatchStateContext` as in `test_downloader_context_attachment_requests`.
2. Construct a `BatchedRequestsResult<AttachmentRequest>` whose `succeeded` map contains one `AttachmentRequest` mapped to `Some(StacksHttpResponse)` built from a `GetAttachmentResponse { attachment: Attachment { content: vec![0u8; ATTACHMENTS_MAX_SIZE_MIN as usize * 4] } }` (via the same construction used in `getattachment.rs` tests, e.g. `StacksHttpResponse::new(...)` with a JSON body produced by serializing `GetAttachmentResponse`).
3. Call `context.extend_with_attachments(&mut results)` and assert `context.attachments` contains the oversized attachment: `assert!(context.attachments.iter().any(|a| a.content.len() as u32 > ATTACHMENTS_MAX_SIZE_MIN))`.
4. Additionally, call `atlas_db.insert_instantiated_attachment(&oversized_attachment)` directly (as `download.rs` does) with an `AtlasConfig { attachments_max_size: ATTACHMENTS_MAX_SIZE_MIN, .. }` and confirm it succeeds (`Ok(())`) despite exceeding `attachments_max_size`, contrasting with `AtlasDB::should_keep_attachment` returning `false` for the same input.

    pub fn should_keep_attachment(
        &self,
        contract_id: &QualifiedContractIdentifier,
        attachment: &Attachment,
    ) -> bool {
        if !self.atlas_config.contracts.contains(contract_id) {
            info!(
                "Atlas: will discard posted attachment - {} not in supported contracts",
                contract_id
            );
            return false;
        }
        if attachment.content.len() as u32 > self.atlas_config.attachments_max_size {
            info!("Atlas: will discard posted attachment - attachment too large");
            return false;
        }
        true
    }

    pub fn extend_with_attachments(
        mut self,
        results: &mut BatchedRequestsResult<AttachmentRequest>,
    ) -> AttachmentsBatchStateContext {
        for (request, response) in results.succeeded.drain() {
            let report = self
                .peers
                .get_mut(request.get_url())
                .expect("Atlas: unable to retrieve reliability report for peer");

            let response = if let Some(r) = response {
                r
            } else {
                report.bump_failed_requests();
                continue;
            };

            if let Ok(response) = response.decode_atlas_get_attachment() {
                self.attachments.insert(response.attachment);
                report.bump_successful_requests();
            } else {
                report.bump_failed_requests();
            }
        }
        let mut events_ids = results.faulty_peers.keys().copied().collect::<Vec<usize>>();
        self.events_to_deregister.append(&mut events_ids);

        self
    }

impl<'de> Deserialize<'de> for GetAttachmentResponse {
    fn deserialize<D: serde::Deserializer<'de>>(d: D) -> Result<GetAttachmentResponse, D::Error> {
        let payload = String::deserialize(d)?;
        let hex_encoded = payload.parse::<String>().map_err(de_Error::custom)?;
        let bytes = hex_bytes(&hex_encoded).map_err(de_Error::custom)?;
        let attachment = Attachment::new(bytes);
        Ok(GetAttachmentResponse { attachment })
    }
}
