Based on my review of `contracts/LoansNFT.sol`, the specific "owner/unlocker epoch mismatch" mechanism hypothesized in the question does **not** hold up — but the same functions do contain a distinct, real durable-lock vulnerability that fits the stated invariant and impact gate.

**Why the "epoch mismatch" framing fails:** `_update` reads `unlocker` and `from` from storage, validates authorization, bumps `ownershipNonce`, performs the actual `super._update`, and then deletes `_unlockers[tokenId]` — all synchronously, with no external call interleaved between the unlocker check and the unlocker deletion. [1](#0-0) 
Any receiver callback (`ERC721Utils.checkOnERC721Received`) fires only after `_update` has already fully committed the new owner and cleared the lock, so there is no reentrancy window in which `ownerAndUnlocker()` can return a stale/inconsistent pair. [2](#0-1) 

**The real bug in the same functions:** `lock()` authorizes any address that is `_isAuthorized` for the token — owner, operator, **or a plain per-token approved address** — to call `lock(unlocker, id)` and freely choose *any* `unlocker` address, not necessarily itself. [3](#0-2) 
Once locked, the only way to release the token is `unlock(id)` called by `msg.sender == _unlockers[id]`. [4](#0-3) 
Critically, the guardian's rescue path `forceTransfer` explicitly refuses to touch a locked token (`require(_unlockers[tokenId] == address(0), TokenLocked())`), so once locked with a non-cooperating or dead `unlocker`, there is no privileged or unprivileged recovery path. [5](#0-4) 
This means an address that only received a narrow per-token `approve()` (e.g., for a legitimate marketplace listing) can call `lock()` directly on `LoansNFT` (bypassing `LoansExchange`'s intended `lock(address(this), id)` pattern) and name an unrelated, unresponsive address as `unlocker`, permanently freezing the victim owner's NFT and any downstream cashflow/withdrawal routing tied to it, with no admin/guardian override available.

### Title
Unprivileged per-token approved address can permanently freeze a Loan NFT via arbitrary `unlocker` in `lock()` - (File: contracts/LoansNFT.sol)

### Summary
`LoansNFT.lock()` allows any address holding a mere per-token ERC-721 approval (not just an operator or the token owner) to lock the token and designate an arbitrary, attacker-chosen `unlocker`. Because `unlock()` can only be called by that exact `unlocker`, and `forceTransfer` (the guardian rescue path) explicitly refuses to act on locked tokens, a malicious/negligent approved party can durably strand the token and any cashflow rights routed through it.

### Finding Description
`lock()`'s authorization check uses `_isAuthorized(tokenOwner, msg.sender, id)`, which is satisfied by the token owner, an approved-for-all operator, or a single-token approved address [3](#0-2) . The `unlocker` parameter passed to `lock` is fully attacker-controlled and unrelated to `msg.sender`'s identity — nothing constrains it to be the caller or any protocol-trusted contract. Once set, the token becomes non-transferable and non-approvable except by the unlocker (`approve()` reverts while locked at line 124, and `_update` reverts any transfer where `auth != unlocker` at lines 160-163). The single privileged rescue mechanism, `forceTransfer`, is gated on the token being unlocked (`_unlockers[tokenId] == address(0)`), so it cannot help once the token is locked with a bogus unlocker.

### Impact Explanation
This is a permanent, unrecoverable lock of a Loan NFT and its associated cashflow/ownership rights caused entirely through an ordinary, unprivileged NFT approval + `lock()` call — matching the "Permanent or practically unrecoverable lock of ... loan NFTs" impact category. It harms the token owner (a different user than the attacker holding the approval), not just the attacker's own position.

### Likelihood Explanation
Requires the victim to grant a per-token `approve()` to an untrusted/compromised address (a realistic scenario for marketplace listings or delegated actions) and that address to call `lock()` directly on `LoansNFT` with a bogus unlocker instead of going through the intended `LoansExchange` flow.

### Recommendation
Restrict `lock()`'s permitted `unlocker` values (e.g., require `unlocker == msg.sender`, or restrict callable-by-per-token-approval callers to only set themselves as unlocker), and/or allow the guardian's `forceTransfer` (or a dedicated admin recovery function) to clear a stuck `_unlockers` entry under appropriate safeguards.

### Proof of Concept
1. Owner `O` calls `LoansNFT.approve(A, tokenId)` for a legitimate purpose (e.g., intending `A` to list the loan on `LoansExchange`).
2. Instead, `A` calls `LoansNFT.lock(B, tokenId)` directly, where `B` is an address `A` controls but never intends to use to `unlock`.
3. `lock()` succeeds because `_isAuthorized(O, A, tokenId)` is true (per-token approval) [3](#0-2) .
4. `O` can no longer transfer, approve, or otherwise move the token; `B` never calls `unlock`.
5. Guardian's `forceTransfer(O, rescueAddr, tokenId)` reverts with `TokenLocked()` [5](#0-4) , leaving the NFT permanently stranded.

  function _update(address to, uint256 tokenId, address auth) internal override returns (address previousOwner) {
    address unlocker = _unlockers[tokenId];
    address from = _ownerOf(tokenId);

    bool isLocked = from != address(0) && unlocker != address(0);
    if (isLocked && auth != unlocker) {
      revert TokenLocked();
    }

    // Bump per-address ownership nonce so external integrators can detect any
    // change to the NFT ownership set of a given address. The zero address is
    // skipped (mint's `from`, burn's `to`) because no consumer reads that slot.
    unchecked {
      if (from != address(0)) ++ownershipNonce[from];
      if (to != address(0)) ++ownershipNonce[to];
    }

    // When the unlocker is transferring a locked token, bypass the standard
    // ERC-721 approval check (pass address(0) as auth) because the unlocker
    // is not set via the normal approve() storage slot.
    previousOwner = super._update(to, tokenId, isLocked ? address(0) : auth);

    if (previousOwner != address(0) && unlocker != address(0)) {
      delete _unlockers[tokenId];
      emit Unlock(tokenId);
    }
  }
