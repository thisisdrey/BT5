### Title
`do_native_withdraw` has no resolver to refund the debited wNEAR balance when the final NEAR `transfer` action fails - (File: `contracts/defuse/src/contract/tokens/nep141/native.rs`)

### Summary
`Contract::do_native_withdraw` only checks the result of the preceding `near_withdraw` call via `promise_result_checked_void(0)`, then schedules `Promise::new(withdraw.receiver_id).transfer(withdraw.amount)` with no `.then()` callback to verify that transfer succeeded. Unlike every sibling withdraw path (`ft_resolve_withdraw`, and the analogous resolvers for NFT/MT withdrawals), there is no re-credit logic if the final transfer receipt fails, so a failed native transfer permanently destroys the debited wNEAR balance.

### Finding Description
The broken binding is: `value debited from owner_id's wNEAR balance == value delivered to receiver_id (native NEAR) + value re-credited to owner_id on failure`.

The flow in `State::native_withdraw` at [1](#0-0)  first calls `self.withdraw(...)`, which performs `internal_sub_balance` and irreversibly debits `owner_id`'s wNEAR balance in the same receipt as the intent execution. It then schedules `ext_wnear::near_withdraw` followed by `.then(Self::ext(...).do_native_withdraw(withdraw))`.

`Contract::do_native_withdraw` at [2](#0-1)  only asserts `promise_result_checked_void(0).is_ok()` (the `near_withdraw` result) and then issues `Promise::new(withdraw.receiver_id).transfer(withdraw.amount)` as the function's return value, with no further `.then()` callback attached to inspect whether that transfer receipt succeeds.

Compare this to `internal_ft_withdraw` / `ft_resolve_withdraw` at [3](#0-2)  and [4](#0-3) , which always chains a `_resolve_withdraw` callback that checks the outer transfer's promise result and calls `self.deposit(...)` to refund the amount on failure. `do_native_withdraw` has no equivalent resolver.

If `withdraw.receiver_id` refers to an account that does not exist on-chain (a syntactically valid but never-created named account, or one deleted between intent signing and execution), the `Transfer` action's receipt fails (`AccountDoesNotExist`). The already-unwrapped NEAR from `near_withdraw` is lost with the failed receipt, and the wNEAR balance debited from `owner_id` in the prior receipt is never reverted because no resolver exists to re-credit it. This breaks the settlement invariant that debited value must equal delivered value plus re-credited value.

### Impact Explanation
Any account (owner_id) that submits a `NativeWithdraw` intent with a non-existent/deleted `receiver_id` will have its wNEAR balance debited from the Verifier permanently with no compensating native NEAR delivery and no refund — the funds are effectively burned/lost. This is repeatable per withdrawal attempt and independent of amount, affecting any account using native withdraw, not limited to the calling attacker. This matches the "user funds permanently frozen/lost due to a refund/resolver credit that does not match what failed to settle" impact category, since the intended `value debited == value delivered + value re-credited` invariant is broken.

### Likelihood Explanation
The precondition is simply supplying a `receiver_id` that does not exist as an account (or gets deleted after signing but before settlement — e.g., a user closes/deletes their sub-account between intent creation and relaying). No special role, balance, or privileged access is needed; any signer of a `NativeWithdraw` intent can trigger this by naming an invalid/soon-to-not-exist `receiver_id`, and it costs only the transaction/gas fee.

### Recommendation
Add a `native_resolve_withdraw` callback chained after the `Promise::new(receiver_id).transfer(amount)` in `do_native_withdraw` (mirroring `ft_resolve_withdraw`), which inspects the transfer's promise result and, on failure, re-credits the debited wNEAR amount back to `owner_id` via `self.deposit(...)`.

### Proof of Concept
`cargo test` plan (near-workspaces sandbox, in `tests/src/tests/defuse/intents/native_withdraw.rs`):
1. Set up a Defuse contract instance and an account `owner` with a wNEAR balance of `N` yoctoNEAR.
2. Sign and execute a `NativeWithdraw` intent from `owner` with `receiver_id` set to a syntactically valid but non-existent named account (e.g., `"never-created-1234.test.near"`).
3. Assert the outer `execute_intents` transaction succeeds (the failure occurs only in the async `transfer` receipt).
4. Query `owner`'s wNEAR balance via the Verifier's `mt_balance_of`/view method: assert it is `0` (fully debited).
5. Inspect the receipts/logs: assert no `NativeWithdraw`-refund event or resolver receipt exists, and that the sandbox environment's balance for `receiver_id` never increased.
6. Assert the total value (`owner`'s remaining Verifier balance + any native balance delivered to `receiver_id` + any refund) is strictly less than `N`, demonstrating the debited-vs-delivered-plus-recredited equality is violated and the funds are unrecoverable.

impl FungibleTokenWithdrawResolver for Contract {
    #[private]
    fn ft_resolve_withdraw(
        &mut self,
        token: AccountId,
        sender_id: AccountId,
        amount: U128,
        is_call: bool,
    ) -> U128 {
        let used = if is_call {
            // `ft_transfer_call` returns successfully transferred amount
            match promise_result_checked_json::<U128>(0) {
                Ok(Ok(used)) => used.0.min(amount.0),
                Ok(Err(_deserialize_err)) => 0,
                // do not refund on failed `ft_transfer_call` due to
                // NEP-141 vulnerability: `ft_resolve_transfer` fails to
                // read result of `ft_on_transfer` due to insufficient gas
                Err(_) => amount.0,
            }
        } else {
            // `ft_transfer` returns empty result on success
            if promise_result_checked_void(0).is_ok() {
                amount.0
            } else {
                0
            }
        };

        let refund = amount.0.saturating_sub(used);
        if refund > 0 {
            self.deposit(
                sender_id,
                [(Nep141TokenId::new(token).into(), refund)],
                Some(REFUND_MEMO),
            )
            .unwrap_or_else(|err| err.panic());
        }

        U128(used)
    }
}
