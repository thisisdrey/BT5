### Title
Unauthenticated block upload triggers P2P-wide relay based solely on chainstate acceptance, not the authenticated `broadcast` flag - ([File: stackslib/src/net/api/postblock_v3.rs])

### Summary
`RPCPostBlockRequestHandler::try_parse_request` only requires authentication when the caller explicitly requests `broadcast=1`; an unauthenticated POST with no `broadcast` parameter is accepted with `self.broadcast = Some(false)`. However, `try_handle_request` decides whether to call `node.set_relay_message(...)` (which propagates the block to the node's P2P peers) purely based on `data_resp.accepted`, never consulting `self.broadcast`/`authenticated`. This breaks the intended invariant that network relay only occurs for authenticated, broadcast-requested uploads.

### Finding Description
In `try_parse_request` [1](#0-0) , authentication is only enforced when `broadcast` is requested (`if broadcast && !authenticated { return Err(...) }`). An unauthenticated caller with no `broadcast=1` query arg passes this check freely, and `self.broadcast` is set to `Some(false)`.

In `try_handle_request`, the `broadcast` value is passed into `Relayer::process_new_nakamoto_block_ext(..., self.broadcast.unwrap_or(false))` [2](#0-1) , but the actual decision to relay the block over the P2P network is made afterward and depends only on chainstate acceptance:

```rust
if data_resp.accepted {
    node.set_relay_message(StacksMessageType::NakamotoBlocks(NakamotoBlocksData {
        blocks: vec![block],
    }));
}
``` [3](#0-2) 

Nothing in this branch checks `self.broadcast`/`authenticated`. So the `broadcast` bool that was gated behind auth is consumed only by `process_new_nakamoto_block_ext` (an internal chainstate-processing parameter unrelated to network gossip), while the actual `set_relay_message` call - which is what causes the node's relay/event loop to gossip `NakamotoBlocksData` to connected peers - fires whenever chainstate deems the block acceptable, regardless of whether the request was authenticated or asked for broadcast.

This means: any unprivileged remote party who can reach the `/v3/blocks/upload/` RPC endpoint (no `authorization` header, no `broadcast=1`) can submit any block that chainstate would accept (e.g., a legitimately signed block they intercepted, or one they otherwise obtained but that the node operator did not intend to have re-broadcast through this particular node), and the node will still gossip it to its peers via `set_relay_message`. The `broadcast`-gated authentication check in `try_parse_request` is therefore security theater with respect to the actual relay behavior - it does not prevent unauthenticated relay, it only prevents unauthenticated callers from explicitly requesting the internal "broadcast" processing hint passed to `process_new_nakamoto_block_ext`.

### Impact Explanation
Any unauthenticated caller can cause a node to propagate an uploaded Nakamoto block to its peers via `set_relay_message`/`NakamotoBlocksData`, bypassing the auth gate that was specifically designed to restrict this ability to authenticated, `broadcast=1` requests. This is repeatable per accepted block and does not require the node's RPC secret. It matches the "network-wide propagation of forged/unauthorized data" category, since the operator's intent (restrict broadcast-triggering uploads to authenticated parties) is defeated for any block that chainstate accepts - relay is effectively unconditional on acceptance, not on caller authorization.

### Likelihood Explanation
Preconditions: the node has `self.auth` configured (so unauthenticated + `broadcast=1` requests are normally rejected), and the attacker has network access to the node's RPC port. No signer keys, secrets, or privileged role are required — the attacker only needs a block that chainstate will accept (which could be a legitimately produced/signed block obtained through any external channel, e.g., overheard, replayed, or independently constructed if valid). This is trivially reachable and cheap: one crafted POST per block, repeatable indefinitely.

### Recommendation
Gate the `set_relay_message` call on `self.broadcast == Some(true)` (i.e., only relay when the caller was authenticated and explicitly requested broadcast), not solely on `data_resp.accepted`:
```rust
if data_resp.accepted && self.broadcast.unwrap_or(false) {
    node.set_relay_message(...);
}
```
This restores the intended equality that relay-to-peers only occurs for authenticated broadcast requests.

### Proof of Concept
Rust test in `stackslib/src/net/api/postblock_v3.rs` tests (or a new integration test):
1. Construct `RPCPostBlockRequestHandler::new(Some("secret".into()))`.
2. Build an HTTP POST to `/v3/blocks/upload/` with no `authorization` header and no `broadcast` query arg, body containing a valid, chainstate-acceptable `NakamotoBlock` (using existing test chainstate fixtures that make `process_new_nakamoto_block_ext` return "accepted").
3. Call `try_parse_request` — assert it succeeds (no 401), with `self.broadcast == Some(false)`.
4. Call `try_handle_request` against a `StacksNodeState` built over the test chainstate.
5. Assert `node.relay_message` (or equivalent internal field captured after `set_relay_message`) is `Some(StacksMessageType::NakamotoBlocks(...))`, demonstrating relay occurred despite lack of authentication/broadcast intent — proving the bug (fix should make this assertion `None`/absent instead).
