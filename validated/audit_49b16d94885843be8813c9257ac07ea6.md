### Title
Attacker can permanently fill `feeCollector`'s per-account token set, DoSing all fee-bearing deposits, issues, and liquidations - (contracts/Pool.sol)

### Summary
`Pool.addToDepositTokensOfAccount` / `addToDebtTokensOfAccount` enforce a global cap of `MAX_TOKENS_PER_USER` tokens per account and revert with `UserReachedMaxTokens` once reached. Because `DepositToken._mint` and `DepositToken._transfer` unconditionally register the recipient's first balance of a token into that set, an unprivileged attacker can stuff the protocol `feeCollector`'s set to the cap with dust deposits/transfers. After that, every code path that mints or seizes a *new* token type to `feeCollector` reverts — including `DepositToken.deposit` (deposit fee mint), `DebtToken.issue` (issue fee mint), and `Pool.liquidate` (protocol-fee `seize`). The lock/cap is never released unless `feeCollector` itself can dispose of dust balances, mirroring the CVE class of "a lock that remains unavailable indefinitely after an error/exhaustion condition."

### Finding Description
In `Pool.sol`, the modifier `onlyIfAdditionWillNotReachMaxTokens` reverts when `debtTokensOfAccount.length(account_) + depositTokensOfAccount.length(account_) >= MAX_TOKENS_PER_USER` (contracts/Pool.sol:143-148). It guards `addToDepositTokensOfAccount` (contracts/Pool.sol:216) and `addToDebtTokensOfAccount` (contracts/Pool.sol:204).

`DepositToken._mint` calls `pool.addToDepositTokensOfAccount(account_)` whenever the recipient's prior balance is zero (contracts/DepositToken.sol:485-488), and `_transfer` does the same for the recipient (contracts/DepositToken.sol:517-520). `deposit` mints the fee to `_pool.feeCollector()` (contracts/DepositToken.sol:230-232), and `Pool.liquidate` seizes the protocol fee to `_poolRegistry.feeCollector()` (contracts/Pool.sol:591-593). `DebtToken.issue` likewise mints an issue fee to the fee collector.

Attack steps (unprivileged EOA):
1. For each deposit token supported by the pool, call `DepositToken.deposit(1 wei, feeCollector)` — `onBehalfOf_` is arbitrary, so dust is minted to `feeCollector` and it is registered in `depositTokensOfAccount[feeCollector]`. Where `deposit` is awkward, the attacker can instead `transfer` 1 wei of their own unlocked msdTOKEN balance to `feeCollector` (transfers only check the *sender's* unlocked balance, contracts/DepositToken.sol:348-354).
2. Repeat across deposit tokens until `depositTokensOfAccount[feeCollector]` reaches `MAX_TOKENS_PER_USER` (feeCollector has no debt tokens, so all slots go to deposit tokens).
3. Thereafter, any deposit whose `quoteDepositOut` yields `_fee > 0` reverts in `_mint(feeCollector)`, and any liquidation whose `protocolFee > 0` reverts in `seize(account_, feeCollector, _fee)` — the whole `liquidate` transaction reverts atomically.

The pool-deployed `FeeCollector`/fee-collector address is a passive recipient; there is no code path that lets it proactively drain arbitrary msdTOKEN balances (uncertain whether governance could route around this via `sweep`-style functions — `TokenHolder._requireCanSweep` is `onlyGovernor`-gated in DepositToken (contracts/DepositToken.sol:493), so recovery needs privileged intervention even if possible).

### Impact Explanation
Temporary-to-permanent liveness failure of core protocol functions, matching the accepted "temporary freezing of funds" / DoS class:
- All `deposit` calls revert while `depositFee > 0` (governance-set, currently nonzero on deployed configs) — users cannot add collateral to rescue positions.
- All `liquidate` calls revert while `protocolFee > 0` — underwater positions cannot be liquidated, allowing bad debt to accrue, which threatens solvency/liveness.
- `issue`/fee-bearing mints revert similarly.
The set only shrinks if `feeCollector` transfers each dust balance down to zero (each `transfer` removes the token when the sender's balance hits 0), which the fee collector contract may not expose; otherwise the condition is permanent for that deployment.

### Likelihood Explanation
Fully unprivileged: the attacker needs only dust amounts of each underlying and pays gas proportional to `MAX_TOKENS_PER_USER`. No governor, keeper, oracle manipulation, or malicious LZ endpoint is required. The precondition is that deposit/liquidation/issue fees are nonzero (otherwise the fee path is skipped); this is a normal deployed configuration. Cost is bounded and one-shot per pool; griefing a high-TVL pool's liquidation path is plausibly profitable when combined with a manipulated position, but even without profit it is cheap griefing. Mitigation note: if `feeCollector` can transfer tokens out, it can self-heal — hence the honest severity is Medium, mirroring the source CVE.

### Recommendation
- Do not apply `onlyIfAdditionWillNotReachMaxTokens` to the protocol `feeCollector` (whitelisting it), or track per-account lists only for addresses that can hold debt/collateral positions.
- Alternatively, route protocol fees to a dedicated accounting mechanism (e.g., accumulate in the DepositToken and let `feeCollector` pull via `withdraw`/`transfer`, which removes entries rather than adding them), or make fee seizure burn-and-transfer underlying directly from `Treasury` instead of minting msdTOKEN to `feeCollector`.
- Add a regression test: fill `feeCollector`'s deposit-token set to `MAX_TOKENS_PER_USER`, then assert `deposit`/`liquidate` still succeed.

### Proof of Concept
Hardhat sketch (setup mirrors `test/Pool.test.ts` and `test/DepositToken.test.ts`):

```ts
// given: pool with depositFee > 0 and protocol liquidationFee > 0
const feeCollector = await poolRegistry.feeCollector()
const max = (await pool.MAX_TOKENS_PER_USER()).toNumber()

// attacker deposits 1 wei of every supported collateral on behalf of feeCollector
for (const dt of depositTokens) { // length >= max
  const underlying = await dt.underlying()
  await IERC20.at(underlying).connect(attacker).approve(dt.address, 1)
  await dt.connect(attacker).deposit(1, feeCollector)
}
expect(await pool.getDepositTokensOfAccount(feeCollector)).to.have.length(max)

// now: victim deposits revert
await expect(
  depositTokens[0].connect(victim).deposit(amount, victim.address)
).to.revertedWithCustomError(pool, 'UserReachedMaxTokens') // via _mint(feeCollector, fee)

// and: liquidations revert
await expect(
  pool.connect(liquidator).liquidate(victim.address, synth.address, repayAmt, depositTokens[0].address)
).to.revertedWithCustomError(pool, 'UserReachedMaxTokens') // via seize(..., feeCollector, fee)
```

If the deposit path is undesirable (fee minted to collector requires balance==0 handling), the same fill is achievable with plain `dt.connect(attacker).transfer(feeCollector, 1)` on unlocked dust balances, since `transfer` only enforces the sender's unlocked balance (contracts/DepositToken.sol:348-354).

Uncertain aspects: I did not locate a `FeeCollector` contract source to confirm it lacks a generic token-transfer escape hatch; if it can move msdTOKENs, the DoS becomes recoverable (still valid as temporary fund freezing). Fee parameters (`depositFee`, `liquidationFees.protocolFee`) being nonzero on deployed configs is assumed from `FeeProvider` defaults but not verified per-chain.
