### Title
`VanityRepository.RelativePath` traversal check is skipped entirely, allowing cross-repository backup lookup in `RestoreRepository` - (File: `internal/gitaly/service/repository/restore_repository.go`)

### Summary
`validateRestoreRepositoryRequest` validates `VanityRepository` with `storage.WithSkipStorageExistenceCheck()`, but `configLocator.ValidateRepository` returns success immediately once it sees this option, **before** it ever calls `storage.ValidateRelativePath`. This means `VanityRepository.RelativePath` — the field used to look up which backup to restore — receives no traversal/containment validation at all, unlike `Repository` (validated with `WithSkipRepositoryExistenceCheck()`, which does reach `storage.ValidateRelativePath`).

### Finding Description
In `internal/gitaly/service/repository/restore_repository.go:61-65`: [1](#0-0) 
the `VanityRepository` is validated with `storage.WithSkipStorageExistenceCheck()`. Looking at `configLocator.ValidateRepository`: [2](#0-1) 
when `cfg.SkipStorageExistenceCheck` is true, the function returns `nil` right after checking that `relativePath` is non-empty — the subsequent `storage.ValidateRelativePath(storagePath, relativePath)` call, which is the only check that rejects `..` traversal, is never reached for `VanityRepository`. By contrast, `Repository` is validated with `WithSkipRepositoryExistenceCheck()` only, which does not skip storage existence checking and therefore does exercise `storage.ValidateRelativePath`.

The unsanitized `VanityRepository.RelativePath` is then passed straight into `backup.Manager.Restore`: [3](#0-2) 
which uses it via `mgr.locator.Find`/`FindLatest` against `VanityRepository`, not `Repository`. These functions build the manifest lookup key with plain `path.Join`, without any root-containment check: [4](#0-3) 
`path.Join` cleans `..` segments, so a crafted `RelativePath` such as `../other-project.git` cancels out the `storageName` component of the constructed key (`manifests/<storageName>/<relativePath>`), letting the lookup resolve to a manifest directory outside the one that corresponds to the caller's actual repository. `backup.ValidatePathPrefix` is correctly implemented and does reject `..` in `PathPrefix` (confirmed against `internal/backup/backup_test.go` cases), so that specific field is not exploitable — the gap is specific to `VanityRepository.RelativePath`.

The actual write target of `Restore` (git objects, refs, hooks) is always `req.Repository`, which is properly validated with `storage.ValidateRelativePath`. So the traversal cannot redirect where data is *written* on disk. It can, however, redirect which backup is *read/looked up* — i.e., which repository's manifest/bundle content gets pulled into the attacker's own, properly-owned repository, since `VanityRepository` is otherwise unconstrained and unbound to any ownership check tying it to the caller's actual project.

### Impact Explanation
An unprivileged user who owns a repository and can invoke `RestoreRepository` (server-side backups enabled) can craft `VanityRepository.RelativePath` with `../` segments to make the backup locator resolve a manifest belonging to a different repository within the same backup storage tree. Because the git content is restored into the attacker's own `Repository` target, this results in disclosure of another project's git objects/refs/history to the attacker — a cross-repository object access / information disclosure impact.

Note: escaping the backup sink's root directory entirely is likely additionally constrained by the underlying `gocloud.dev/blob` driver (e.g. `fileblob` enforces containment within its configured directory, and S3/GCS/Azure treat keys as flat strings with no directory semantics), so full filesystem traversal outside the backup bucket is not confirmed. The confirmed, concrete issue is the missing validation itself and the resulting cross-repository manifest/backup confusion within the backup storage namespace.

### Likelihood Explanation
Requires only that server-side backup restore (`s.backupSink`/`s.backupLocator`) is configured — a supported, non-default-but-documented deployment mode — and that the attacker can call `RestoreRepository` for a repository they own while freely setting `VanityRepository`. No admin privilege, secret, or peer compromise is needed; the attacker fully controls the `RestoreRepositoryRequest` fields for their own repo. This is a straightforward RPC-level exploit.

### Recommendation
Do not let `WithSkipStorageExistenceCheck()` bypass path-traversal validation in `configLocator.ValidateRepository`. Move the `storage.ValidateRelativePath` check (or an equivalent containment/`..`-rejection check) before the `SkipStorageExistenceCheck` early return, so it always runs regardless of which validation options are supplied. Additionally, consider binding `VanityRepository` to the actual `Repository` (e.g., verifying it belongs to the same project/storage the caller is authorized for) rather than trusting it unconditionally as a backup lookup key.

### Proof of Concept
```go
func TestRestoreRepository_VanityRepositoryTraversal(t *testing.T) {
    // Setup: attacker owns repoA (storage "default", relative path "attacker/repoA.git").
    // A backup exists for a different project at manifests/default/victim/repoV.git/<backupID>.toml
    // (simulating another tenant's repository backup on the same shared backup sink).

    req := &gitalypb.RestoreRepositoryRequest{
        Repository: &gitalypb.Repository{ // attacker-owned, properly validated
            StorageName:  "default",
            RelativePath: "attacker/repoA.git",
        },
        VanityRepository: &gitalypb.Repository{ // used only for backup lookup key
            StorageName:  "default",
            RelativePath: "../victim/repoV.git", // ".." never validated due to SkipStorageExistenceCheck early-return
        },
        BackupId:  "existing-backup-id",
        UseLatest: true,
    }

    _, err := client.RestoreRepository(ctx, req)
    require.NoError(t, err)

    // Assert: attacker's repoA now contains victim's repoV git objects/refs,
    // e.g. by fetching a commit/ref known to exist only in repoV's backup.
}
```
Expected (buggy) result: request passes `validateRestoreRepositoryRequest` without error despite the `..` in `VanityRepository.RelativePath`, and the manifest lookup key `manifests/default/../victim/repoV.git/<id>.toml` resolves to the victim project's backup manifest, causing its content to be restored into the attacker-owned repository.
