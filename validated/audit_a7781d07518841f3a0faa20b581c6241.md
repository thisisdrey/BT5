### Title
TRX (and TRC10) value sent via CALL/CALLCODE/DELEGATECALL to a precompiled-contract address is permanently and irrecoverably locked - (File: actuator/src/main/java/org/tron/core/vm/program/Program.java)

### Summary
`Program.callToPrecompiledAddress` unconditionally transfers the `endowment` (TRX or TRC10 value attached to a `CALL`) from the caller to the precompiled contract's address before invoking the precompile logic. Precompiled contract addresses are reserved, code-less accounts that only exist to be dispatched to native Java logic (`PrecompiledContracts.PrecompiledContract.execute`); they have no private key, no contract bytecode, and no built-in sweep/withdraw logic to move the received value back out. Any TRX or TRC10 value sent this way therefore accumulates on that address forever, exactly analogous to the LamboVEthRouter case where ETH silently piles up in a contract with no way to retrieve it.

### Finding Description
In `callToPrecompiledAddress`, before the precompiled logic is even executed, the code performs the balance transfer: [1](#0-0) 

This happens regardless of whether the precompiled contract actually needs or uses the value; the precompile's `execute(data)` method only returns a success/failure pair and output bytes — it has no mechanism to return, forward, or otherwise account for TRX/TRC10 that was staged into its address balance. Since this is a native/precompiled address rather than a deployed smart contract or a real user account, there is no bytecode path (no `transfer`, no `suicide`, no EOA private key) that can ever move funds back out of it. Once TRX (or a TRC10 token) is deposited into a precompiled address's balance via this call path, it is permanently unspendable — the address can never initiate an outgoing transfer, because no transaction can be signed by a matching private key and no contract code exists at that address to be triggered.

This mirrors the reported bug class precisely: a "receive"-like pathway accepts value with no corresponding sweep/return functionality, so value silently and permanently accumulates over time.

### Impact Explanation
Any signed transaction that triggers a smart contract, which in turn issues a `CALL`/`CALLCODE`/`DELEGATECALL` (with nonzero value) to a precompiled-contract address — whether intentionally, by attacker-crafted contract logic, or by an ordinary contract making an addressing mistake — permanently burns/locks that TRX or TRC10 balance. This is unrecoverable freezing of user funds with no admin or protocol mechanism to reclaim them, satisfying the "permanent freezing of funds" impact bar. Because it is reachable from an arbitrary contract call (not requiring any privileged role), and because energy/fee-based DoS or malicious-actor exclusions do not apply (any regular user can trigger this merely by calling a contract that performs such a call), it should be assessed as Medium/High depending on how easily/likely contracts route value calls toward these fixed addresses (e.g., off-by-address bugs, fuzzed/attacker-supplied target addresses in generic low-level `call{value:...}()`).

### Likelihood Explanation
Likelihood is moderate: precompiled address values are fixed and well-known (they occupy a specific, low or reserved address range), so it is plausible for buggy or malicious contracts (or fat-fingered developers) to route a payable low-level call there, and once done there is no recovery path. It does not require any privileged actor — a normal externally-owned account deploying/calling a contract that performs an arbitrary-address value call is sufficient to reach this path.

### Recommendation
- In `callToPrecompiledAddress`, reject calls that carry non-zero `endowment`/TRC10 value to a precompiled address unless the specific precompile documents and implements value handling (fail the call / refund value to the sender instead of transferring it first).
- Alternatively, add an explicit sweep mechanism at the chain level (e.g., during block application in `Manager`, or via a dedicated maintenance routine) that returns/burns-to-blackhole any balance accidentally accumulated on precompiled addresses, so funds are not indefinitely orphaned outside of accounted supply.

### Proof of Concept
1. Deploy a contract `Router` with a function that does:
   `address(precompiledAddr).call{value: 1000}("")` where `precompiledAddr` is one of the fixed precompiled-contract addresses recognized by `PrecompiledContracts`.
2. Call `Router`'s function from a normal TRX-holding account with `callValue = 1000`.
3. Observe in `Program.callToPrecompiledAddress` that `MUtil.transfer(deposit, senderAddress, contextAddress, endowment)` moves the 1000 sun to `contextAddress` (the precompiled address) at: [2](#0-1) 
4. Verify via `AccountStore`/repository lookup that the precompiled address's `balance` now holds 1000 sun.
5. Confirm there is no transaction type, actuator, or opcode path that lets that address (no private key, no deployed code) issue an outgoing transfer of that balance — the value is permanently stranded.
