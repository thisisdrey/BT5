### Title
Governance-controlled `PricingParameters` (ETH/DOT `exchange_rate`, `fee_per_gas`, `rewards`) are re-read independently at message-submission time and at message-processing time, letting the fee charged to a sender diverge from the reward/fee promised to relayers on Ethereum - (File: `bridges/snowbridge/pallets/outbound-queue/src/lib.rs`)

### Summary
This is the closest local analog to the `.latestRoundData()` bug: a price/parameter value that can move between two points in a pipeline is read twice, independently, instead of being snapshotted once and carried through. In `ExchangeRate.sol`, the stale read let a user deposit/withdraw around a price update. In `pallet_outbound_queue` (Snowbridge), the ETH/DOT `exchange_rate`, `fee_per_gas` and `rewards` (`PricingParameters`) are fetched once to compute the **fee charged to the sender** in `SendMessage::validate` (submission time), and fetched **again, independently**, to compute the **`max_fee_per_gas`/`reward` actually committed into the message that Ethereum relayers get paid against** in `Pallet::do_process_message` (queue-processing time). Because message processing is decoupled from submission (it happens through `T::MessageQueue`, and can even `Yield` and be deferred to a later block when `MaxMessagesPerBlock` is hit), governance can change `PricingParameters` in between, so the amount collected from the user and the amount promised to relayers on the remote side are computed against two different price snapshots for the same message.

### Finding Description
`calculate_fee` derives the fee from `PricingParameters` (`exchange_rate`, `fee_per_gas`, `rewards`, `multiplier`): [1](#0-0) 

`SendMessage::validate` (executed synchronously when the user submits/sends the message, e.g. via XCM export or `snowbridge_pallet_system::Pallet::send`) reads `T::PricingParameters::get()` **once**, at submission time, to compute the `Fee` that is charged to the sender: [2](#0-1) 

The message is then only *enqueued* (`deliver`), not committed yet: [3](#0-2) 

Later, `Pallet::do_process_message` is invoked by `T::MessageQueue` — potentially in a different block, since the function explicitly `Yield`s (defers processing) once `MaxMessagesPerBlock` is reached for the block: [4](#0-3) 

When it does run, it reads `T::PricingParameters::get()` **again, independently**, and bakes `max_fee_per_gas` and `reward` directly into the `CommittedMessage` that is Merkle-committed and eventually relayed to the Ethereum Gateway contract, which is what actually determines the relayer payout on the remote side: [5](#0-4) 

Governance can change `exchange_rate`, `fee_per_gas`, or `rewards` at any time via the permissioned but ordinary `set_pricing_parameters` extrinsic, which simply overwrites the single shared `PricingParameters` storage item and also sends a `SetPricingParameters` command to Ethereum: [6](#0-5) 

There is no mechanism binding the specific message to the `PricingParameters` snapshot that was used to charge its sender: the fee is computed and charged against `params_T0` in `validate`, while the values embedded in the on-chain committed message (and thus the amount Ethereum will actually pay the relayer for that specific message) are computed against `params_T1` in `do_process_message`. Existing guards (`params.validate()` non-zero checks in `set_pricing_parameters`, the `Yield` back-pressure, `MaxMessagesPerBlock`) only ensure parameters are non-degenerate and bound per-block throughput — none of them ensure the two reads use the same snapshot for the same message.

### Impact Explanation
If `PricingParameters` (particularly `fee_per_gas` or `rewards.remote`, which directly become `max_fee_per_gas`/`reward` on the committed message) increase between a message's submission and its (possibly delayed) processing, the committed message promises Ethereum-side relayers a larger payout than what was actually collected from the sender on the Substrate side at submission time. Since relayer rewards are ultimately funded from the bridge's Ethereum-side reward pool/gateway balance and are meant to be backed by fees collected per message, this creates a systematic under-collection relative to the promised payout for every message that straddles a parameter change plus a processing delay (`Yield`). Symmetrically, if parameters decrease, senders are overcharged relative to what relayers will actually receive. This falls under "public underpriced work that degrades ... bridge processing" and risks a value mismatch/fund drain from the bridge's remote-side reward accounting, without requiring a malicious relayer, validator, or governance-abuse assumption — the mismatch is a structural consequence of two independent unsynchronized reads of mutable governance state across an asynchronous queue boundary.

### Likelihood Explanation
`set_pricing_parameters` is documented as something governance is expected to call periodically ("every few weeks") — a routine, non-malicious operation, not privileged-abuse. The `Yield` path is a normal, permissionless-triggerable condition (any user can submit enough messages in a block to make later messages in the same block, or a burst period, get deferred to the next block) which widens the window during which a parameter change can land between `validate` and `do_process_message` for a given message. No attacker privilege beyond normal message submission is required to be caught in — or to engineer — this window.

### Recommendation
Snapshot `PricingParameters` once at `validate`/submission time, store the snapshot inside the `QueuedMessage`/ticket, and have `do_process_message` use that stored snapshot (rather than re-reading `T::PricingParameters::get()`) when constructing `max_fee_per_gas`/`reward` for the `CommittedMessage`. This binds the fee charged to the sender and the reward promised on-chain for that specific message to a single price snapshot, eliminating the read/read divergence.

### Proof of Concept
1. Block N: User submits message `M1`. `validate` reads `PricingParameters = P0` (e.g. `fee_per_gas = X`, `reward = R`) and charges the sender `fee(P0)`. `M1` is enqueued via `T::MessageQueue`.
2. Same block N: enough other messages are queued/processed such that `MessageLeaves` hits `T::MaxMessagesPerBlock`, so `do_process_message` for `M1` returns `Err(Yield)` (see `lib.rs:309-313`) and is retried in block N+1.
3. Between block N and N+1, governance calls `set_pricing_parameters` raising `fee_per_gas`/`rewards.remote` to `P1 > P0` (a routine, documented governance action, not an attack).
4. Block N+1: `do_process_message` for `M1` runs, reads `PricingParameters = P1`, and embeds `max_fee_per_gas`/`reward` derived from `P1` into the `CommittedMessage` for `M1`.
5. Result: the sender of `M1` paid `fee(P0)` at submission, but the message committed to Ethereum promises relayers a payout computed from the higher `P1`, i.e. the bridge commits to paying out more than it collected for that message — an unbacked promise analogous to withdrawing at a "freshly updated" price after depositing at a stale one.

		pub(crate) fn calculate_fee(
			gas_used_at_most: u64,
			params: PricingParameters<T::Balance>,
		) -> Fee<T::Balance> {
			// Remote fee in ether
			let fee = Self::calculate_remote_fee(
				gas_used_at_most,
				params.fee_per_gas,
				params.rewards.remote,
			);

			// downcast to u128
			let fee: u128 = fee.try_into().defensive_unwrap_or(u128::MAX);

			// multiply by multiplier and convert to local currency
			let fee = FixedU128::from_inner(fee)
				.saturating_mul(params.multiplier)
				.checked_div(&params.exchange_rate)
				.expect("exchange rate is not zero; qed")
				.into_inner();

			// adjust fixed point to match local currency
			let fee = Self::convert_from_ether_decimals(fee);

			Fee::from((Self::calculate_local_fee(), fee))
		}

	fn validate(
		message: &Message,
	) -> Result<(Self::Ticket, Fee<<Self as SendMessageFeeProvider>::Balance>), SendError> {
		// The inner payload should not be too large
		let payload = message.command.abi_encode();
		ensure!(
			payload.len() < T::MaxMessagePayloadSize::get() as usize,
			SendError::MessageTooLarge
		);

		// Ensure there is a registered channel we can transmit this message on
		ensure!(T::Channels::contains(&message.channel_id), SendError::InvalidChannel);

		// Generate a unique message id unless one is provided
		let message_id: H256 = message
			.id
			.unwrap_or_else(|| unique((message.channel_id, &message.command)).into());

		let gas_used_at_most = T::GasMeter::maximum_gas_used_at_most(&message.command);
		let fee = Self::calculate_fee(gas_used_at_most, T::PricingParameters::get());

		let queued_message: VersionedQueuedMessage = QueuedMessage {
			id: message_id,
			channel_id: message.channel_id,
			command: message.command.clone(),
		}
		.into();
		// The whole message should not be too large
		let encoded = queued_message.encode().try_into().map_err(|_| SendError::MessageTooLarge)?;

		let ticket = Ticket { message_id, channel_id: message.channel_id, message: encoded };

		Ok((ticket, fee))
	}

	fn deliver(ticket: Self::Ticket) -> Result<H256, SendError> {
		let origin = AggregateMessageOrigin::Snowbridge(ticket.channel_id);

		if ticket.channel_id != PRIMARY_GOVERNANCE_CHANNEL {
			ensure!(!Self::operating_mode().is_halted(), SendError::Halted);
		}

		let message = ticket.message.as_bounded_slice();

		T::MessageQueue::enqueue_message(message, origin);
		Self::deposit_event(Event::MessageQueued { id: ticket.message_id });
		Ok(ticket.message_id)
	}

			origin: OriginFor<T>,
			params: PricingParametersOf<T>,
		) -> DispatchResult {
			ensure_root(origin)?;
			params.validate().map_err(|_| Error::<T>::InvalidPricingParameters)?;
