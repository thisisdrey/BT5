### Title
Pushed microblocks are stored/relayed without a `pox_valid` check, unlike pushed anchored blocks - (File: stackslib/src/net/relay.rs)

### Summary
`Relayer::preprocess_pushed_microblocks` (relay.rs:1516) accepts a microblock for any `index_anchor_block` as long as `chainstate.get_block_header_hashes` resolves it, but it never inspects the associated `BlockSnapshot::pox_valid` flag the way `Relayer::validate_blocks_push` does for anchored blocks. This breaks the invariant that only microblocks tied to a PoX-valid tip should be stored/relayed.

### Finding Description
`Relayer::validate_blocks_push` explicitly loads the `BlockSnapshot` for the block's `consensus_hash` and rejects the push if `sn.pox_valid` is `false`, preventing forged/relayed anchored blocks from attaching to an already-invalidated PoX fork. `Relayer::preprocess_pushed_microblocks`, which handles the `MicroblocksData` push path, only resolves the microblock's parent anchored block via `chainstate.get_block_header_hashes(index_anchor_block)` to confirm the anchor block is locally known, then calls `chainstate.preprocess_streamed_microblock` directly. There is no corresponding lookup of the burn `BlockSnapshot` for that anchor block's consensus hash, and therefore no `pox_valid` gate.

Because PoX validity for a given consensus hash can be retroactively flipped to `false` (i.e., a reward-cycle anchor block that was accepted as valid is later determined invalid, marking descendant sortitions/chain state as PoX-invalid) while the underlying Stacks anchored block and its header hashes remain present in `chainstate`, an attacker who pushes a microblock referencing that now-invalidated anchor block will have it accepted and relayed by `preprocess_pushed_microblocks`, since the function's only gate is local presence of the anchor block, not its current PoX validity.

### Impact Explanation
A remote, unprivileged peer that simply gossips a `MicroblocksData` message can get a node to store and re-relay (via the `new_microblocks` map returned to the relay/broadcast logic) a microblock chained to a consensus-invalid PoX fork. This is network-wide propagation of forged/invalid data — other peers receiving the relayed microblock have no independent reason to distrust it, since it came from a node that "accepted" it. This matches the Critical category: "network-wide propagation of forged data."

### Likelihood Explanation
The attacker needs no privileged role: any P2P peer can send a `MicroblocksData` push. The only precondition is that the target anchor block exists locally (already stored via normal chain sync) and that its PoX validity has since been invalidated in `sortdb` — a state reachable through normal PoX-fork dynamics without attacker-side special access. This is a low-cost, repeatable message-send attack (one crafted `MicroblocksData` per attempt), remotely reachable over the P2P port.

### Recommendation
In `Relayer::preprocess_pushed_microblocks`, after resolving the anchor block's index hash, look up the corresponding `BlockSnapshot` (as `validate_blocks_push` does) and reject the microblock (do not call `chainstate.preprocess_streamed_microblock`, and exclude it from `new_microblocks`) if `sn.pox_valid` is `false`.

### Proof of Concept
Add a `stackslib::net::relay` test that:
1. Sets up a `SortitionDB`/`StacksChainState` pair with an anchored block whose `consensus_hash` maps to a `BlockSnapshot`.
2. Flips/persists that snapshot's `pox_valid` to `false` (simulating post-hoc PoX invalidation) while leaving the anchored block's header hashes resolvable via `get_block_header_hashes`.
3. Constructs a `MicroblocksData` message referencing that anchor block's `index_anchor_block` and calls `Relayer::preprocess_pushed_microblocks`.
4. Asserts that the microblock is (incorrectly) present in the returned `new_microblocks` map, demonstrating the missing `pox_valid` guard; the fix should make this assertion fail (microblock excluded). [1](#0-0)
