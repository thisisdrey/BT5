Audit Report

## Title
Optimistic Fee Burn Before Cross-Chain Confirmation Causes Permanent Loss of User Funds in `add_tip` - (File: `bridges/snowbridge/pallets/system-frontend/src/lib.rs`)

## Summary
`pallet-snowbridge-system-frontend::add_tip` on Asset Hub irrevocably burns the caller's tip asset via `swap_fee_asset_and_burn` before it is known whether the corresponding `EthereumSystemCall::AddTip` transact on Bridge Hub will succeed. If the Bridge Hub-side `add_tip` fails (nonce already consumed / order already resolved), the burned value is only recorded into `LostTips`, a non-refundable bookkeeping map, with no path back to the user. [1](#0-0) [2](#0-1) 

## Finding Description
On Asset Hub, `Pallet::add_tip` calls `swap_fee_asset_and_burn`, which permanently destroys the user's asset via `burn_for_teleport` (or swaps then burns), before firing an `UnpaidExecution`/`Transact` XCM to Bridge Hub with no confirmation awaited. [3](#0-2) [4](#0-3) 

On Bridge Hub, `snowbridge_pallet_system_v2::Pallet::add_tip` dispatches to `InboundQueue::add_tip` or `OutboundQueue::add_tip`; on error it only mutates `LostTips` and emits `TipProcessed{success:false}` — no mint, refund, or credit occurs. [5](#0-4)  The pallet's own storage doc comment for `LostTips` confirms there is currently no recovery path: "Capturing the lost tips here supports implementing a recovery method in the future." [6](#0-5) 

The underlying `AddTip` implementations fail deterministically once state has advanced:
- Outbound queue: `PendingOrders::get(nonce)` returns `None` after `process_delivery_receipt` removes the entry, yielding `AddTipError::UnknownMessage`. [7](#0-6) [8](#0-7) 
- Inbound queue: `Nonce::get(nonce)` being already set yields `AddTipError::NonceConsumed`. [9](#0-8) 

Because message delivery/receipt submission by relayers and the tip's cross-chain `Transact` execution are asynchronous and race with each other, any unprivileged, honest user can trigger this loss simply by tipping a message that gets delivered/consumed shortly before their tip's XCM executes on Bridge Hub. This violates the invariant that settlement/payout state should only advance after execution success is confirmed atomically with the source-chain value transfer — here the burn is unconditional and irreversible while the destination-side effect is uncertain.

## Impact Explanation
This is a direct value-conservation violation: real Ether-denominated value is destroyed on Asset Hub with no reward delivered and no refund mechanism, whenever Bridge Hub state (nonce/order) has already advanced by the time the tip transact executes. This matches the "permanent user-fund... lock" / value-destruction class of impact under the Polkadot SDK impact gate, since burned tip funds become permanently unrecoverable, parked only as a non-actionable ledger entry in `LostTips`.

## Likelihood Explanation
No privileged actor, malicious relayer, or governance action is required — this is triggered by normal, honest relayer activity racing against an ordinary user's `add_tip` call. Given that messages are continuously and legitimately delivered/relayed, this race is a realistic, recurring occurrence rather than a contrived edge case, and it is fully reachable through the public `add_tip` extrinsic exposed to any signed user.

## Recommendation
Do not burn/destroy the tip asset on Asset Hub before Bridge Hub confirms the `add_tip` action succeeded. Escrow the tip asset (or defer the burn) until a success confirmation/receipt is received from Bridge Hub, or have the Bridge Hub-side failure path trigger a refund XCM back to the original tipper instead of only recording into `LostTips`. At minimum, add a claim/recovery extrinsic that lets users reclaim value tracked in `LostTips`, matching the pallet's own stated intent ("supports implementing a recovery method in the future") — currently no such extrinsic exists.

## Proof of Concept
1. User calls `pallet_snowbridge_system_frontend::add_tip(message_id = Outbound(N), asset)` on Asset Hub; `swap_fee_asset_and_burn` burns the user's asset. [10](#0-9) 
2. Before the resulting `Transact` XCM executes on Bridge Hub, a relayer submits a delivery receipt for nonce `N`, causing `process_delivery_receipt` to remove the `PendingOrders` entry. [7](#0-6) 
3. The delayed `AddTip{nonce: N}` call executes on Bridge Hub; `OutboundQueue::add_tip` returns `AddTipError::UnknownMessage` because `PendingOrders::get(nonce)` is now `None`. [8](#0-7) 
4. `snowbridge_pallet_system_v2::add_tip` catches the error, mutates `LostTips` only, and emits `TipProcessed{success:false}`. [11](#0-10) 
5. Result: the user's burned value is permanently gone with no refund and no claim mechanism, confirmed by the existing test `tip_to_invalid_nonce_is_added_to_lost_tips` in the integration test suite, which asserts `TipProcessed{success:false}` and a nonzero `LostTips` entry with no subsequent recovery step.

			origin: Location,
			fee_asset: Asset,
		) -> Result<u128, DispatchError> {
			let ether_location = T::EthereumLocation::get();
			let (fee_asset_location, fee_amount) = match fee_asset {
				Asset { id: AssetId(ref loc), fun: Fungible(amount) } => (loc, amount),
				_ => {
					tracing::debug!(target: LOG_TARGET, ?fee_asset, "error matching fee asset");
					return Err(Error::<T>::UnsupportedAsset.into());
				},
			};
			if fee_amount == 0 {
				return Ok(0);
			}

			let ether_gained = if *fee_asset_location != ether_location {
				Self::swap_and_burn(
					origin.clone(),
					fee_asset_location.clone(),

					fee_amount,

					tracing::debug!(target: LOG_TARGET, ?e, "error swapping asset");
				})?

				burn_for_teleport::<T::AssetTransactor>(&origin, &fee_asset)
					.map_err(|_| Error::<T>::BurnError)?;
				fee_amount
			};
			Ok(ether_gained)
		}
