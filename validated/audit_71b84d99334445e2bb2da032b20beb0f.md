### Title
Unchecked `msg.value` accounting overflow in `Operator.execute` allows draining ETH held by the Operator contract — (File: contracts/Operator.sol)

### Summary
`Operator.execute` iterates an attacker-supplied `Call[]` array and accumulates the per-call `value` into `_sumOfValues` inside an `unchecked` block. If the sum of call values overflows `uint256`, the final `require(msg.value == _sumOfValues)` check can be satisfied with a much smaller `msg.value` than the ETH actually forwarded to the call targets. The excess ETH is paid out of the `Operator` contract's own balance.

### Finding Description
The kernel bug (CVE-2017-18257) is an integer overflow in `__get_data_block` reachable by an unprivileged local user through crafted syscall inputs. The Metronome analog is an integer overflow reachable by an unprivileged EOA through crafted `Operator.execute` inputs.

In `contracts/Operator.sol:42-54`, each `_call.value` is added to `_sumOfValues` under `unchecked` at line 46, and the per-call value is actually dispatched via `Address.functionCallWithValue` at line 48 — the value is sent from `address(this)` balance. Only after the loop, at line 54, is `msg.value == _sumOfValues` enforced.

An attacker crafts two calls, e.g. `value = 2^255` each (plus a third small call if needed), such that `_sumOfValues` wraps around modulo `2^256` to exactly the `msg.value` they send (which can be `0` or a dust amount). Each `functionCallWithValue` legitimately executes, spending the contract's ETH. The overflow — not any balance check — is what makes the attack possible.

There is no `onlyGovernor`/allowlist on `execute`; it is a public, `payable`, unprivileged entry point. `nonReentrant` and `setMsgSender` do not prevent the overflow.

### Impact Explanation
Any ETH balance held by the `Operator` contract at execution time can be drained by the attacker. `Operator` is `payable` and can accumulate residual ETH (over-refunded LayerZero/native-gateway fees, ETH sent by mistake, ETH left from prior multi-calls where targets refunded). Additionally, a same-transaction attack is possible: a victim's pending `execute` that leaves ETH in the contract mid-sequence can be sandwiched, but more simply, any standing ETH balance is stealable. This is direct theft of funds held by a production contract, satisfying the impact bar.

### Likelihood Explanation
Likelihood is bounded by whether the deployed `Operator` holds a non-trivial ETH balance. The contract is intended to be stateless with respect to user funds (ETH in == ETH out within one call), so the balance is typically dust. However, smart contracts on mainnet inevitably accumulate ETH (self-destruct force-feeds, refunds, mistaken sends, protocol fee leftovers), and the overflow check gives the attacker the entire balance for free. The vulnerability is deterministic and requires no privileged role, no oracle manipulation, and no timing — only a non-zero contract balance.

### Recommendation
Remove `unchecked` around `_sumOfValues += _value` so that overflow reverts, or accumulate with checked arithmetic. Alternatively, track spent ETH via `address(this).balance` delta before/after the loop and require it not to exceed `msg.value`. Keep `unchecked { ++i }` — that is safe.

### Proof of Concept
Hardhat (fork not strictly required; local is sufficient):

```ts
const operator = await Operator.deploy(); // or attach deployed instance
// Fund operator to simulate accumulated ETH
await attacker.sendTransaction({to: operator.address, value: ethers.utils.parseEther("1")});

const HALF = ethers.BigNumber.from(2).pow(255);
await operator.connect(attacker).execute([
  {target: attacker.address, value: HALF, callData: "0x"},
  {target: attacker.address, value: HALF, callData: "0x"},
], {value: 0}); // sum = 2^256 ≡ 0 (mod 2^256), check passes
// assert attacker received 1 ETH from operator's balance
```

Note: I was unable to confirm the deployed `Operator`'s actual ETH holdings from the indexed code; the exploit's profitability depends on that balance, but the overflow path itself is verified in source.
