### Title
Zero-fee dust trades against the Bancor-style TRX Exchange pool allow attacker-favorable rounding drift with no economic cost - ([File: chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java])

### Summary
`ExchangeTransactionActuator` (the actuator behind the user-facing `ExchangeTransactionContract` / `exchangeTransaction` API, reachable by any signed transaction) charges a protocol fee of exactly `0` for every trade against a TRC10↔TRX or TRC10↔TRC10 Bancor-style liquidity pool, and there is no minimum trade size enforced. This mirrors the Sherlock M-4 pattern: a market participant can create arbitrarily many "positions" (here, trades) that are individually too small to matter but cost nothing and can be repeated without bound, while the pricing math itself is done in double-precision floating point (unless the `allowHardenExchangeCalculation` governance flag is enabled), which is known to be imprecise for tiny inputs.

### Finding Description
`ExchangeTransactionActuator.calcFee()` unconditionally returns `0`: [1](#0-0) 

The actual swap amount is computed by `ExchangeCapsule.transaction()`, which by default (when the `allowHardenExchangeCalculation` committee-controlled parameter is `0`, i.e. before the community-gated hardening upgrade is enabled) uses the legacy `ExchangeProcessor`, a bonding-curve implementation built on `double`/`Math.pow`: [2](#0-1) [3](#0-2) 

There is no validation in `ExchangeTransactionActuator.doValidate()` enforcing any minimum `tokenQuant`/notional size for a trade — the only checks are that the token exists in the pool and that the resulting `anotherTokenQuant` is at least the caller-supplied `expected` value: [4](#0-3) 

Because the double-precision Bancor formula (`exchangeToSupply`/`exchangeFromSupply`, using `(long) issuedSupply` truncation and `Math.pow`) is not guaranteed to be monotonic or exactly reproducible for very small `sellTokenQuant` values, and because each of these micro-trades costs the caller nothing in protocol fee (only bandwidth/energy, which any funded account can supply cheaply or via free bandwidth points), an attacker can economically probe and repeatedly execute a large volume of dust-sized trades against a pool. This is structurally the same defect class as the reported M-4 issue: the protocol assumes each unit of activity is either large enough to be economically "self-policing" (fee ⇒ discourages abuse) or negligible in aggregate, but with zero fee and no minimum size, a well-funded actor can perform unbounded numbers of tiny operations that each individually pass validation, exploiting floating-point rounding behavior cumulatively without ever paying for the privilege — unlike `ExchangeInjectActuator`/`ExchangeWithdrawActuator`, which at least charge `calcFee()` (a `WITNESS_CREATE`-style flat TRX fee) for state-changing pool operations, `ExchangeTransactionActuator` charges nothing at all.

### Impact Explanation
If the cumulative rounding bias of the legacy floating-point processor is not neutral (which is exactly why the project introduced `SafeExchangeProcessor`/`allowHardenExchangeCalculation` as a hardening fix, `chainbase/src/main/java/org/tron/core/capsule/SafeExchangeProcessor.java`), repeated zero-cost dust trades let an attacker slowly walk the pool's `firstTokenBalance`/`secondTokenBalance` state away from what a single, fee-paying, honest trade of equivalent aggregate size would produce. Because these balances back real TRX/TRC10 deposited by other injectors, systematic drift creates an unbacked balance in the `Exchange`/`ExchangeV2` store: some accounts can withdraw or trade out more value than the pool actually holds in reserve relative to honest accounting, which is a form of protocol insolvency analogous to the "bad debt that the exchange will have to cover" impact described in the source report.

### Likelihood Explanation
Likelihood is bounded by two facts: (1) the vulnerable legacy `ExchangeProcessor` path is only active while the `allowHardenExchangeCalculation` committee proposal parameter is `0` (the pre-hardening default), and (2) executing enough transactions to accumulate a meaningful drift requires many transactions, each consuming bandwidth/energy, so a well-resourced or bandwidth-subsidized account is needed — the same "well-funded attacker" caveat that the original Sherlock report itself received pushback on (Medium, not High/Critical, due to cost/impracticality debate). No fee at all (vs. a positive-but-too-small fee in the original report) makes the java-tron analog marginally easier to execute once the vulnerable path is reachable.

### Recommendation
- Charge a non-zero fee for `ExchangeTransactionContract` (mirroring `ExchangeInjectActuator`/`ExchangeWithdrawActuator`), or enforce a minimum trade notional so dust trades cannot be repeated for free.
- Make `allowHardenExchangeCalculation` (BigDecimal-based `SafeExchangeProcessor`) the mandatory, non-optional code path rather than a governance-toggleable legacy fallback, since the underlying floating-point math is the root cause of any exploitable rounding drift.
- Add invariant checks after every trade (as already partially done for the hardened path, `chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java` lines 160-162) requiring pool balances to never fall below values reconstructable from cumulative deposits, even for the legacy path.

### Proof of Concept
Conceptual (cannot be executed without running a live node/test harness):
1. Ensure `allowHardenExchangeCalculation == 0` (default/pre-upgrade state).
2. Create or use an existing `Exchange` pool via `ExchangeCreateActuator`.
3. Submit many `ExchangeTransactionContract` transactions with minimal `sellTokenQuantity` (e.g., 1 unit) from a funded account, each calling `ExchangeTransactionActuator.execute()`, which pays `calcFee() == 0`.
4. Compare the pool's `firstTokenBalance`/`secondTokenBalance` after N micro-trades against the balances predicted by performing one equivalent-sized trade with `SafeExchangeProcessor` (`chainbase/src/main/java/org/tron/core/capsule/SafeExchangeProcessor.java`); the project's own test suite (`framework/src/test/java/org/tron/core/capsule/utils/ExchangeProcessorTest.java`, `testStrictMath`) already demonstrates `anotherTokenQuant` values differ between the legacy `ExchangeProcessor` and `SafeExchangeProcessor` for identical inputs, confirming the rounding divergence exists and is measurable, at zero fee cost per trade.

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
