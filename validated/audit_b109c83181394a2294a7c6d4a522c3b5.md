Audit Report

## Title
`claim_rewards` permanently reverts for Snowbridge relayer rewards because `BeneficiaryOf` derived from the caller is always `LocalAccount`, which `BridgeRewardPayer` rejects for `BridgeReward::Snowbridge` - ([File: cumulus/parachains/runtimes/bridge-hubs/bridge-hub-westend/src/bridge_common_config.rs])

## Summary
The generic `claim_rewards` entry point in `pallet-bridge-relayers` derives its `Beneficiary` from the caller's raw `AccountId32` via `From<AccountId32> for BridgeRewardBeneficiaries`, which unconditionally produces `LocalAccount` [1](#0-0) . `BridgeRewardPayer::pay_reward` explicitly rejects `LocalAccount` for `BridgeReward::Snowbridge`, returning an error and only accepting `AssetHubLocation` for that reward kind [2](#0-1) . As a result, any relayer holding a `Snowbridge`-kind reward who calls the natural, parameter-minimal `claim_rewards` extrinsic will deterministically fail.

## Finding Description
`do_claim_rewards` calls `T::PaymentProcedure::pay_reward` with whatever `beneficiary` was supplied, and maps any `Err` from the payment procedure into `Error::<T, I>::FailedToPayReward` [3](#0-2) . `claim_rewards_to` takes an explicit `beneficiary: BeneficiaryOf<T, I>` parameter and forwards it directly to `do_claim_rewards` [4](#0-3) .

On BridgeHub Westend, `BridgeRewardBeneficiaries` has exactly two variants (`LocalAccount(AccountId)` and `AssetHubLocation(VersionedLocation)`), and the only `From<AccountId32>` conversion available maps a bare account ID to `LocalAccount` unconditionally [5](#0-4) . Since `claim_rewards` (the caller-derived variant) must build its beneficiary through this conversion, it can never produce anything other than `LocalAccount`.

`BridgeRewardPayer::pay_reward` matches on `reward_kind`. For `BridgeReward::Snowbridge`, it explicitly errors out on `LocalAccount` and only proceeds via `PayAccountOnLocation` when the beneficiary is `AssetHubLocation` [2](#0-1) . This is confirmed directly by the integration test, which asserts that `claim_rewards` for `BridgeReward::Snowbridge` fails with `FailedToPayReward`, while `claim_rewards_to` with an explicit `AssetHubLocation` beneficiary is required [6](#0-5) .

No existing guard prevents this: `RelayerRewards` storage is only cleared via `try_mutate_exists` upon a successful `pay_reward` call, so the reward entry is preserved (no fund loss), but the "default"/simplest claim path is structurally guaranteed to fail for this one reward kind.

## Impact Explanation
This does not directly cause fund loss or theft — `RelayerRewards` entries survive failed attempts because of the `try_mutate_exists` semantics. The impact is that a legitimate, public extrinsic (`claim_rewards`) that is the natural call for "claim my own accumulated reward" is a deterministic dead end for an entire reward class (`Snowbridge`), degrading relayer participation and reward-claim reliability for the bridge. This matches the "runtime bugs that compromise intended behavior" category of the impact gate — the payout mechanism does not behave as intended for Snowbridge relayers using the default claim path, forcing reliance on `claim_rewards_to` with manually constructed XCM locations.

## Likelihood Explanation
High and deterministic — no race conditions, special preconditions, or privileged access are required. Any relayer who accrues a `Snowbridge` reward (via normal message/receipt processing) and calls `claim_rewards(origin, BridgeReward::Snowbridge)` will hit this failure on every attempt, as directly reproduced by the existing test in the repository.

## Recommendation
Either make `claim_rewards` reward-kind aware so that for `BridgeReward::Snowbridge` it constructs an `AssetHubLocation` beneficiary derived from the relayer's account rather than `LocalAccount`, or explicitly reject `claim_rewards` for `Snowbridge`-kind rewards with a clear, documented error (e.g., `UnsupportedClaimMethod`) rather than surfacing an opaque `FailedToPayReward`, and document that `claim_rewards_to` must be used for this reward kind.

## Proof of Concept
1. A relayer accrues a `BridgeReward::Snowbridge` credit via `register_reward` (through normal inbound queue processing).
2. The relayer calls `BridgeRelayers::claim_rewards(origin, BridgeReward::Snowbridge)`.
3. The beneficiary is built via `BridgeRewardBeneficiaries::from(relayer_account_id)`, always yielding `LocalAccount(relayer)`.
4. `BridgeRewardPayer::pay_reward` matches `(Snowbridge, LocalAccount(_))` and returns an `Err`.
5. `do_claim_rewards` converts this into `Error::FailedToPayReward`; the call reverts every time, as reproduced by the existing test at `cumulus/parachains/runtimes/bridge-hubs/bridge-hub-westend/tests/tests.rs` lines 768-796 [7](#0-6) .

		fn do_claim_rewards(
			relayer: T::AccountId,
			reward_kind: T::Reward,
			beneficiary: BeneficiaryOf<T, I>,
		) -> DispatchResult {
			RelayerRewards::<T, I>::try_mutate_exists(
				&relayer,
				reward_kind,
				|maybe_reward| -> DispatchResult {
					let reward_balance =
						maybe_reward.take().ok_or(Error::<T, I>::NoRewardForRelayer)?;
					T::PaymentProcedure::pay_reward(
						&relayer,
						reward_kind,
						reward_balance,
						beneficiary.clone(),
					)
					.map_err(|e| {
						tracing::error!(
							target: LOG_TARGET,
							error=?e,
							?relayer,
							?reward_kind,
							?reward_balance,
							?beneficiary,
							"Failed to pay rewards"
						);
						Error::<T, I>::FailedToPayReward
					})?;
