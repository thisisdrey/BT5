### Title
Unrecoverable trapped funds in Snowbridge inbound-queue v1 `SendToken`/`SendNativeToken` XCM programs — ([File: bridges/snowbridge/primitives/inbound-queue/src/v1.rs])

### Summary
Snowbridge inbound-queue v1's `MessageToXcm::convert_send_token` and `convert_send_native_token` build XCM programs that withdraw/reserve-deposit Ethereum-bridged assets and end with a bare `DepositAsset { ..., beneficiary }` to the user-supplied destination, with **no `AssetClaimer` hint and no error-handling appendix protecting the final deposit**. This mirrors the XVS report's root cause exactly: value is moved out of a "safe" custodial/withdrawal step with the assumption that a subsequent step (crediting/depositing to the final recipient) will always succeed, but when it does not, the funds become effectively unrecoverable by an ordinary user.

### Finding Description
`convert_send_token` [1](#0-0)  builds a program that does `ReserveAssetDeposited` into holding, then either:
- for `None` (direct AssetHub destination): a single trailing `DepositAsset { assets: Wild(AllCounted(2)), beneficiary }` with no error handler at all [2](#0-1) .
- for `Some(dest_para_id)` (forward to sibling parachain): a `SetAppendix` that only protects the **local** leg (AssetHub) by returning unspent local assets to the bridge sovereign, followed by `DepositReserveAsset` whose **remote** program (executed on the destination parachain) ends in `DepositAsset { assets: Wild(AllCounted(2)), beneficiary }` with **no appendix or error handler of its own** [3](#0-2) .

`convert_send_native_token` has the identical pattern: `WithdrawAsset` into holding followed by a bare `DepositAsset` to `beneficiary` with no appendix/claimer [4](#0-3) .

If the final `DepositAsset` fails for any reason a relayer/user cannot fully control ahead of time — e.g. the beneficiary account does not exist and the deposited asset is not "sufficient" to satisfy the existential deposit, a foreign asset is not registered as sufficient on the target chain, `AllCounted(2)` miscounts due to fee exhaustion leaving a different number of holding entries, or the destination-parachain leg runs out of weight — the XCM executor's generic holding-drain logic traps the remaining assets via `Config::AssetTrap::drop_assets` under the *current XCM origin at the point of failure* [5](#0-4) .

Unlike inbound-queue v2 — which explicitly threads an `AssetClaimer`/`SetHints` claimer location through every converted message (`PreparedMessage::claimer`, defaulted to a `LocalNetwork`-anchored bridge-owner account precisely so a real signed account can later call `pallet_xcm::claim_assets`) [6](#0-5)  — v1's `SendToken`/`SendNativeToken` XCM programs set no claimer at all. The origin present when the trap fires is derived from `UniversalOrigin(GlobalConsensus(network))` after `DescendOrigin(PalletInstance(inbound_queue_pallet_index))` [7](#0-6) , i.e. an Ethereum-universal-consensus-anchored location on the local leg, or an AssetHub-reserve-transfer-sovereign origin on the remote leg. Neither of these is an origin that `pallet_xcm::claim_assets`'s `ExecuteXcmOrigin::ensure_origin` (a signed-account origin check) can ever reproduce from a normal signed extrinsic [8](#0-7) . The only way to reconstruct that exact origin is to replay another privileged `UniversalOrigin`+`DescendOrigin` sequence, which is not available to ordinary users/relayers — this is the direct structural analog of "the recipient must be a contract, and if it isn't, funds are locked in the bridge with no exposed recovery function," except here the missing piece is a missing/absent `AssetClaimer` binding rather than a missing `sweepToken`-style function.

Note the fix already applied in v2 (PR #11919, `network: Some(LocalNetwork::get())` on the fallback claimer) demonstrates the Snowbridge team is aware of and actively patching exactly this bug class, but the same protective pattern (default `AssetClaimer` hint bound to a recoverable, network-correct location) was never back-ported into the still-shipping v1 `SendToken`/`SendNativeToken` code paths.

### Impact Explanation
A failed final `DepositAsset` in either `convert_send_token`'s `None` branch, the remote leg of its `Some(dest_para_id)` branch, or in `convert_send_native_token` results in permanent, protocol-level loss of user funds bridged from Ethereum: the assets are burned/withdrawn from the Ethereum side (an irreversible on-chain action already recorded by the Gateway contract and inbound-queue `submit`), yet on the Polkadot side they end up trapped under an origin that no ordinary account can present to `pallet_xcm::claim_assets`. This is unbacked-mint/permanent-fund-lock territory affecting arbitrary bridge users, not merely relayers, admins, or governance — it fits the "permanent user-fund or bridge-state lock" impact category directly.

### Likelihood Explanation
This does not require a malicious actor: it triggers on ordinary conditions such as sending assets to a not-yet-existing beneficiary account paired with a non-"sufficient" asset (a common configuration for less-liquid bridged ERC-20s), fee mis-estimation causing partial holding drains before `DepositAsset`, or the remote destination-parachain leg running short of weight/fees during `DepositReserveAsset`. Because the v1 message content (destination account, fee amounts) is attacker/user controlled on the Ethereum side via `v1_sendToken`-equivalent calls, a user (even unintentionally, or an attacker targeting another victim's transfer by manipulating amount/fee fields) can reliably reproduce a failing final deposit.

### Recommendation
Back-port the v2 pattern into v1: attach an explicit `SetHints([AssetClaimer { location }])` (or equivalent `SetAppendix` refund-to-known-recoverable-account) to every `convert_send_token`/`convert_send_native_token` XCM program, anchored on a location that a real signed account (the sender's own beneficiary account, or a bridge-owner sovereign pinned with `network: Some(LocalNetwork::get())`) can later present to `pallet_xcm::claim_assets`. Apply the same fix to the destination-parachain leg's remote XCM inside `DepositReserveAsset`, not just the local AssetHub appendix.

### Proof of Concept
1. Construct an inbound Ethereum `SendToken` message with `Destination::AccountId32 { id }` where `id` is an account that does not exist on AssetHub and the transferred asset is a `ForeignAssets` instance not marked "sufficient" (common for newly registered ERC-20s prior to liquidity bootstrapping), or set `fee` low enough that after `BuyExecution` the leftover asset amount is insufficient to satisfy ED.
2. Submit via `snowbridge_pallet_inbound_queue::Pallet::submit` with a valid Ethereum proof; `convert_send_token` produces the XCM shown above.
3. On AssetHub, `ReserveAssetDeposited` succeeds (assets placed in holding) but the trailing `DepositAsset { assets: Wild(AllCounted(2)), beneficiary }` fails with `FailedToTransactAsset`/`TooExpensive`, per the semantics of pallet-assets `Transfer`-with-ED behavior demonstrated generically in `smart_contract_does_not_return_bool_fails`-style deposit failures.
4. The XCM executor's `post_process` trap fires because holding is non-empty [5](#0-4) ; `AssetsTrapped` is emitted with `origin` equal to the `UniversalOrigin(GlobalConsensus(Ethereum))`/`DescendOrigin` context, not a recoverable signed-account location.
5. No signed account on AssetHub can call `claim_assets` successfully for that trap hash, because `ExecuteXcmOrigin::ensure_origin` cannot produce that universal-consensus-derived `Location` from any real signed extrinsic origin, exactly as guarded against for the v2 fallback case in the `fallback_claimer_traps_to_bridge_owner_and_claim_assets_succeeds` regression test [9](#0-8)  — a protection that was never added to the v1 code path exercised here.

				fee,
			),
		};
