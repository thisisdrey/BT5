Audit Report

## Title
`process_delivery_receipt` ignores the `DeliveryReceipt.success` flag and unconditionally pays the relayer reward for failed Ethereum-side message execution - ([File: bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs])

## Summary
`Pallet::process_delivery_receipt` decodes a `DeliveryReceipt` whose `success: bool` field reports whether the message's dispatched command actually executed successfully on the Ethereum Gateway, but the function never reads or checks that field before paying the relayer reward and permanently removing the `PendingOrder`. This decouples relayer payouts from actual successful message execution on Ethereum.

## Finding Description
`submit_delivery_receipt` is a public, unprivileged, signed extrinsic. It verifies the Ethereum event log/proof via `T::Verifier::verify`, then decodes a `DeliveryReceipt` from the log using `DeliveryReceipt::try_from`, and calls `Self::process_delivery_receipt(relayer, receipt)`. [1](#0-0) 

`DeliveryReceipt` is decoded directly from the Ethereum `InboundMessageDispatched(nonce, topic, success, reward_address)` event, and explicitly retains the `success` field indicating whether the corresponding Gateway command execution succeeded or reverted. [2](#0-1) 

`process_delivery_receipt` only validates `receipt.gateway == T::GatewayAddress::get()` and that a `PendingOrder` exists for `receipt.nonce`. It never reads `receipt.success`; if `order.fee > 0` it unconditionally calls `T::RewardPayment::register_reward` and then removes the order from `PendingOrders`, closing it permanently. [3](#0-2) 

The `PendingOrder` struct persisted in storage only holds `nonce`, `block_number`, and `fee` — there is no field to reconcile execution outcome, so no downstream mechanism exists to distinguish a genuinely successful delivery from a reverted one. [4](#0-3) 

The order itself is created with a non-zero `fee` at message commit time in `do_process_message`, independent of any later execution outcome. [5](#0-4) 

This violates the required invariant that message queues, bridge markers, receipts, and payout state must only advance after decode, dispatch, execution, and settlement succeed atomically — here, settlement (reward payment + order removal) proceeds regardless of whether execution succeeded.

## Impact Explanation
This permits unbacked relayer reward payout on BridgeHub for messages whose command execution failed on Ethereum (`success = false`), directly matching the "duplicate settlement or payout" / "theft or unbacked mint or unlock" categories in the impact gate. Every legitimately-failing dispatch (insufficient dispatch gas relative to `GasMeter::maximum_dispatch_gas_used_at_most`, or any ordinary on-chain revert in command execution) still results in a real, provable event log that any relayer can submit to be paid the full `order.fee`, while the order is irrevocably removed (`PendingOrders::remove(nonce)`), preventing any retry or reconciliation.

## Likelihood Explanation
Likelihood is Medium-to-High: the exploit path requires no malicious peer, prover, validator, or privileged actor — only a normal signed extrinsic call (`submit_delivery_receipt`) by any relayer submitting a genuine, correctly-proven Ethereum event for a message whose Gateway-side execution reverted. Execution failures for reasons such as gas-estimate mismatches or downstream reverts are a realistic, recurring operational condition in cross-chain message dispatch, not a contrived edge case.

## Recommendation
1. Add a check such as `ensure!(receipt.success, Error::<T>::DeliveryFailed)` (or an explicit failure branch) in `process_delivery_receipt` before invoking `T::RewardPayment::register_reward`.
2. Separate order resolution from reward payment: only pay the relayer when `receipt.success == true`; on failure, emit a distinct event (e.g., `MessageDeliveryFailed`) and implement explicit fee refund/retry handling instead of paying out silently.
3. Consider retaining enough context in `PendingOrder` (e.g., `topic`) to cross-check `receipt.topic` against the originally committed message for the given nonce.

## Proof of Concept
1. A message is committed via `do_process_message`, inserting `PendingOrders[nonce] = { nonce, fee>0, block_number }`. [5](#0-4) 
2. The message is relayed to Ethereum; the dispatched command reverts/fails execution on the Gateway (e.g., insufficient gas). The Gateway still emits `InboundMessageDispatched(nonce, topic, success=false, reward_address)`.
3. Any relayer obtains a valid proof of this genuine event and calls `submit_delivery_receipt(event)`; verification succeeds and `DeliveryReceipt::try_from` decodes `success = false` correctly. [6](#0-5) 
4. `process_delivery_receipt` checks only `receipt.gateway` and pending-order existence, ignoring `receipt.success`, so `order.fee > 0` triggers `T::RewardPayment::register_reward` and `PendingOrders::remove(nonce)` permanently closes the order. [7](#0-6) 
5. The relayer is paid the full fee for a message that never executed successfully on Ethereum, and the order cannot be resubmitted or reconciled — an unbacked, non-reversible payout.

		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}

sol! {
	event InboundMessageDispatched(uint64 indexed nonce, bytes32 topic, bool success, bytes32 reward_address);
}

/// Delivery receipt
#[derive(Clone, Debug)]
pub struct DeliveryReceipt {
	/// The address of the outbound queue on Ethereum that emitted this message as an event log
	pub gateway: H160,
	/// The nonce of the dispatched message
	pub nonce: u64,
	/// Message topic
	pub topic: H256,
	/// Delivery status
	pub success: bool,
	/// The reward address
	pub reward_address: [u8; 32],
}

#[derive(Copy, Clone, Encode, Decode, Eq, PartialEq, Debug, TypeInfo)]
pub enum DeliveryReceiptDecodeError {
	DecodeLogFailed,
	DecodeAccountFailed,
}

impl TryFrom<&Log> for DeliveryReceipt {
	type Error = DeliveryReceiptDecodeError;

	fn try_from(log: &Log) -> Result<Self, Self::Error> {
		let topics: Vec<B256> = log.topics.iter().map(|x| B256::from_slice(x.as_ref())).collect();

		let event = InboundMessageDispatched::decode_raw_log_validate(topics, &log.data)
			.map_err(|_| DeliveryReceiptDecodeError::DecodeLogFailed)?;

		Ok(Self {
			gateway: log.address,
			nonce: event.nonce,
			topic: H256::from_slice(event.topic.as_ref()),
			success: event.success,
			reward_address: event.reward_address.0,
		})
	}
