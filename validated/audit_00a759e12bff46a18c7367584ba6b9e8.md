### Title
Unauthenticated `RecvError` packet can force-close a tunnel when the cached remote address is unset - (File: outside.go)

### Summary
`Interface.handleRecvError` is reachable pre-authentication (it is dispatched directly from the unencrypted packet-type switch in `readOutsidePackets`, before any certificate/Noise verification occurs) and tears down a tunnel based only on a `RemoteIndex` lookup and a same-source-address check. That check is skipped entirely whenever the hostinfo's cached remote address is not yet valid, which mirrors the `lastRPS`-style bug class: a cached "last known good" value that, when left in its zero/uninitialized state, silently disables the safeguard that depends on it.

### Finding Description
`readOutsidePackets` routes `header.RecvError` packets to `f.handleRecvError` without requiring any certificate, CA-pool verification, or Noise handshake completion: [1](#0-0) 

`handleRecvError` resolves the target purely from the numeric `RemoteIndex` in the packet header via `QueryReverseIndex`, then tries to prevent spoofing by comparing the packet's source address to the hostinfo's cached remote: [2](#0-1) 

The anti-spoofing check is:
```go
hr := hostinfo.GetRemote()
if hr.IsValid() && hr != addr {
    f.l.Info("Someone spoofing recv_errors?", ...)
    return
}
f.closeTunnel(hostinfo)
```
This is structurally the same pattern as the LoopFi finding: a cached value (`hr`, the "last known remote address") is consulted to gate a security-relevant decision, but the code only enforces the gate `if hr.IsValid()`. When `hr` is the zero value (i.e. not "cached" yet, analogous to `lastRPS == 0`), the guard is bypassed entirely and `closeTunnel` executes unconditionally for any attacker who can guess or observe a live `RemoteIndex`. `RemoteIndex` values are attacker-observable on the wire (they appear in every handshake/message header) and are not secret, so an attacker with no CA-signed certificate can forge a bare `RecvError` packet (header-only, no encryption) carrying a captured/guessed index.

### Impact Explanation
If `hr.IsValid()` is false — e.g., before the tunnel's remote endpoint has been recorded, or transiently in states where `HostInfo`'s remote-address cache hasn't been populated — an unauthenticated, off-path attacker can force `f.closeTunnel(hostinfo)` and additionally purge the pending handshake state (`hm.DeleteHostInfo(hostinfo)`), causing a remote denial-of-service against an established or forming Nebula tunnel. This matches the "Recommendation" rule category of remote state poisoning / firewall-adjacent teardown reachable without a valid certificate, and is a direct analog of the LoopFi issue where an unguarded zero-value cache disables the mechanism meant to gate a state transition.

### Likelihood Explanation
Reaching this path requires only sending a 1-byte-header UDP packet of type `header.RecvError` with a `RemoteIndex` value that matches an entry in `RemoteIndexes`; no cryptographic material or certificate is needed, and the code path executes before any peer authentication. The gating condition (`hr.IsValid()`) depends on internal timing/state of `HostInfo.GetRemote()`/`SetRemote()`, which was not observable in the indexed portion of `hostmap.go` in this session — I could not confirm from the retrieved snippets exactly which states leave `GetRemote()` returning an invalid `AddrPort` (e.g., freshly created pending hostinfos, relayed-only hostinfos, or a race window during roaming). This is the primary uncertainty in this analysis and should be verified directly against `hostmap.go`'s `GetRemote`/`SetRemote` implementation, which the indexed context did not fully surface.

### Recommendation
Treat an invalid/zero cached remote (`!hr.IsValid()`) as "no reliable last-known-good value" and refuse to act on unauthenticated `RecvError` packets in that state (or require some other proof of tunnel possession) rather than silently allowing the teardown, mirroring the LoopFi fix of never letting an unguarded zero/invalid cached value bypass the safeguard it exists to enforce.

### Proof of Concept
Conceptual PoC (matches the existing `recv_error` config already in the codebase, e.g. `TestCloseTunnelAuthenticated`-style harness):
1. Establish or observe a Nebula node whose `HostInfo.remote` has not yet been populated (e.g., inspect `GetRemote()` immediately after `beginHandshake`/`continueHandshake` before `SetRemote` is called, or during relay-only paths where `SetRemote` is skipped: `outside.go:114-124` never calls `SetRemote` for `isMessageRelay` packets).
2. From an arbitrary unauthenticated network position, send a bare `header.RecvError` packet with `RemoteIndex` set to a value observed on the wire for that tunnel (index values are transmitted in cleartext headers).
3. Because `hostinfo.GetRemote()` returns an invalid `AddrPort` in that state, `handleRecvError`'s spoof check at [3](#0-2)  is skipped, and `f.closeTunnel(hostinfo)` plus `hm.DeleteHostInfo(hostinfo)` execute, tearing down the tunnel/pending handshake without any authentication.

Note: I was unable to fully confirm, from the indexed portions of `hostmap.go` available in this session, every code path where `HostInfo.GetRemote()` legitimately returns an invalid `netip.AddrPort`; this should be validated directly against `hostmap.go`'s `remote` field and `GetRemote`/`SetRemote` methods (not fully retrievable here) before treating this as a confirmed exploitable condition rather than a structural analog.
