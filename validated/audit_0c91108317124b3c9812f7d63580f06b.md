## Finding: Unauthenticated `RecvError` Packets Allow Remote Tunnel Teardown (DoS / State Poisoning)

### Title
Unauthenticated `RecvError` message allows any network attacker to tear down an established tunnel - (`outside.go`)

### Summary
The external report's bug class — a privileged state-mutating action (`revokeRole`) reachable without any access-control/authentication check — has a concrete analog in nebula's handling of the cleartext `RecvError` message type. `handleRecvError` accepts an unauthenticated, unencrypted UDP packet and uses it to unilaterally tear down ("revoke") an established, cryptographically-authenticated tunnel, gated only by a weak, spoofable source-address comparison.

### Finding Description
In `readOutsidePackets` (`outside.go`), `header.RecvError` is dispatched *before* any decryption or handshake authentication is required — it is processed straight off the wire: [1](#0-0) 

The handler itself performs only a policy check and a source-address equality check, never verifying possession of any cryptographic material (no AEAD tag, no signature, no replayed-counter validation of the kind applied to `Message`/`Test`/`CloseTunnel` traffic which all require `ConnectionState.Decrypt`/`VerifyRelay` first): [2](#0-1) 

Compare this to `CloseTunnel`, which is only actioned *after* `hostinfo.ConnectionState.Decrypt` succeeds (i.e., it requires possession of the session key derived from a CA-verified handshake): [3](#0-2) 

`RecvError` skips that gate entirely. The only defense is:
1. A config policy (`ShouldRecvError`) that may allow errors from any endpoint (`recvErrorAlways`) or from private endpoints (`recvErrorPrivate`).
2. A check that the reported endpoint (`addr`) matches the tunnel's currently known remote (`hr`). [4](#0-3) 

Neither of these is a cryptographic authentication mechanism — the "source matches known remote" check is a plain UDP source-address comparison, which is spoofable by an attacker without possessing any CA-signed certificate or session key. UDP has no return-routability handshake, so any attacker capable of source-spoofing UDP packets (very common absent egress/ingress filtering), or an on-path/off-path attacker who can observe the wire, can craft this packet, since `RemoteIndex` travels in cleartext in every packet's header: [5](#0-4) 

Once the spoofed check passes, `handleRecvError` directly calls `f.closeTunnel(hostinfo)` and deletes pending handshake state — mirroring the reported bug's shape exactly: a state-mutating/"revocation" operation (tearing down an authenticated security context) is reachable and actioned without proof of authorization equivalent to holding the tunnel's session key or a CA-signed identity.

### Impact Explanation
An attacker with no CA-signed certificate and no valid session key can force teardown of active, legitimately-established Nebula tunnels between any two hosts whose current UDP remote address and `RemoteIndex` they can observe or guess, causing denial of service (repeated forced re-handshakes, connectivity flapping) — the same "remove critical relationship state without authorization" impact class described in the external report, translated from RBAC roles to VPN tunnel state.

### Likelihood Explanation
Reaching this code path requires:
- Knowing/guessing the victim's `RemoteIndex` (32-bit, transmitted in cleartext on every packet — observable to any on-path/passive observer, or by traffic analysis if the attacker is on the same broadcast segment).
- Spoofing (or being positioned to send from) the exact UDP source address currently recorded as the tunnel's remote.
- The receiving node's `listen.recv_error`/accept policy not being set to `recvErrorNever` (nebula's `1.9.7` changelog shows this control surface exists and was recently tightened, indicating maintainers consider `recv_error` handling security-sensitive) — see: [6](#0-5) 

Likelihood is moderate: it does not require breaking cryptography, only UDP source spoofing/on-path visibility and knowledge of a value transmitted in the clear, whereas the CloseTunnel path (a legitimate teardown mechanism) mandates full AEAD authentication.

### Recommendation
Require cryptographic authentication before acting on `RecvError`, mirroring what `CloseTunnel` already does — e.g., include the message inside the encrypted/AEAD-protected channel (or require a MAC keyed by the tunnel's session key) rather than acting on a bare, cleartext, source-address-checked signal. At minimum, default `listen.recv_error` handling to `never` unless explicitly opted in, and treat address-match-only validation as insufficient given UDP's spoofability.

### Proof of Concept
1. Attacker passively observes (or is on-path for) traffic between hosts `A` and `B`, learning `A`'s currently-assigned `RemoteIndex` for the `B→A` direction and `A`'s current advertised UDP endpoint (both visible in cleartext packet headers).
2. Attacker crafts a UDP packet with header `Type = header.RecvError`, `RemoteIndex` set to the observed value, and source IP/port spoofed to match `B`'s known remote address as seen by `A`.
3. Sends it to `A`'s listening UDP port.
4. `A.handleRecvError` finds the matching `hostinfo` via `QueryReverseIndex`, sees `hr == addr` (spoofed match), and calls `f.closeTunnel(hostinfo)`, tearing down the legitimate tunnel — with zero cryptographic proof of identity or session possession, analogous to the unauthenticated `revokeRole()` call in the original report.

Note: I was unable to fully confirm the compiled-in *default* value of the `listen.recv_error`/accept policy constant (`recvErrorAlways` vs `recvErrorPrivate` vs `recvErrorNever`) from the index before running out of tool iterations; this affects exploitability in default deployments and should be verified directly in a full checkout (`interface.go`, config loading for `recvErrorConfig`) before treating this as exploitable out-of-the-box.

```go
func (f *Interface) handleRecvError(addr netip.AddrPort, h *header.H) {
	if !f.acceptRecvErrorConfig.ShouldRecvError(addr) {
		f.l.Debug("Recv error received, ignoring",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
		return
	}

	if f.l.Enabled(context.Background(), slog.LevelDebug) {
		f.l.Debug("Recv error received",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
	}

	hostinfo := f.hostMap.QueryReverseIndex(h.RemoteIndex)
	if hostinfo == nil {
		f.l.Debug("Did not find remote index in main hostmap", "remoteIndex", h.RemoteIndex)
		return
	}

	hr := hostinfo.GetRemote()
	if hr.IsValid() && hr != addr {
		f.l.Info("Someone spoofing recv_errors?",
			"addr", addr,
			"hostinfoRemote", hr,
		)
		return
	}

	f.closeTunnel(hostinfo)
	// We also delete it from pending hostmap to allow for fast reconnect.
	f.handshakeManager.DeleteHostInfo(hostinfo)
}
```

**File:** interface.go (L124-143)

```go
type recvErrorConfig uint8

const (
	recvErrorAlways recvErrorConfig = iota
	recvErrorNever
	recvErrorPrivate
)

func (s recvErrorConfig) ShouldRecvError(endpoint netip.AddrPort) bool {
	switch s {
	case recvErrorPrivate:
		return endpoint.Addr().IsPrivate()
	case recvErrorAlways:
		return true
	case recvErrorNever:
		return false
	default:
		panic(fmt.Errorf("invalid recvErrorConfig value: %d", s))
	}
}
```

```go
// Parse is a helper function to parses given bytes into new Header struct
func (h *H) Parse(b []byte) error {
	if len(b) < Len {
		return ErrHeaderTooShort
	}
	// get upper 4 bytes
	h.Version = uint8((b[0] >> 4) & 0x0f)
	// get lower 4 bytes
	h.Type = MessageType(b[0] & 0x0f)
	h.Subtype = MessageSubType(b[1])
	h.Reserved = binary.BigEndian.Uint16(b[2:4])
	h.RemoteIndex = binary.BigEndian.Uint32(b[4:8])
	h.MessageCounter = binary.BigEndian.Uint64(b[8:16])
	return nil
}
```
