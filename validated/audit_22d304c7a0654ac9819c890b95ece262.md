### Title
Unvalidated attacker-controlled length fields in `PrecompiledContracts` array extraction helpers can throw uncontained `NegativeArraySizeException`/`OutOfMemoryError`/`ArrayIndexOutOfBoundsException` - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The FFmpeg CVE root cause is that `cdxl_decode_frame` fails to validate/exclude a format field (`CHUNKY`) before processing image data, causing a heap overflow on crafted input. The analogous pattern in java-tron is in the ABI-array-extraction helpers used by the `ValidateMultiSign` and `BatchValidateSign` TVM precompiled contracts: `extractBytes32Array`, `extractBytesArray`, and `extractSigArray` read an attacker-controlled "array length" word directly from calldata and use it to allocate arrays and index into the `words` array, without first validating that the declared length is consistent with the actual remaining data. [1](#0-0) 

### Finding Description
`extractBytes32Array(DataWord[] words, int offset)` reads `len = words[offset].intValueSafe()` and immediately does `new byte[len][]`, then loops `words[offset + i + 1]` with no check that `offset+len` is within `words.length`. [2](#0-1) 

`extractBytesArray` and `extractSigArray` only guard against `offset > words.length - 1`, but once past that single check, the `len` value taken from calldata is used unchecked both to allocate `new byte[len][]` and to index `words[offset + i + 1]` — a huge or negative `len` produces `NegativeArraySizeException`/`OutOfMemoryError`, and a `len` inconsistent with the real array length produces `ArrayIndexOutOfBoundsException`. [3](#0-2) 

These helpers are invoked from `ValidateMultiSign.execute()` and `BatchValidateSign.doExecute()`, both of which are TVM precompiled contracts reachable from any smart-contract `CALL` opcode issued by any signed transaction. In `ValidateMultiSign.execute()`, the size-cap guard (`sigArraySize > MAX_SIZE`) that was added is only applied when `VMConfig.allowTvmSelfdestructRestriction()` is enabled; when that flag is not active, the code falls back to the unguarded `extractBytesArray` call, and this call happens *before* the method's own `try { ... } catch (Throwable t)` block, so an exception thrown during extraction is not locally contained. [4](#0-3) 

Existing test comments confirm this class of bug was previously a real, unguarded failure mode ("TIP-854 ... a too-short input raises inside the decoder; that is the documented pre-activation failure mode") and that new tests were added specifically to assert the *post-activation* code no longer lets such exceptions escape to the outer VM frame — implying the pre-fix/flag-disabled behavior does let exceptions propagate uncontained. [5](#0-4) [6](#0-5) [7](#0-6) 

### Impact Explanation
If the exception (particularly `OutOfMemoryError` from `new byte[len][]` with an attacker-chosen huge `len`) is not fully contained by the VM/transaction execution framework, a single crafted transaction calling `ValidateMultiSign` (when the `allowTvmSelfdestructRestriction` feature is inactive) could destabilize or crash the node process handling that transaction — a denial-of-service impact analogous to the FFmpeg crash-on-crafted-input CVE. Even if contained per-transaction, it represents a reachable, attacker-triggerable crash path in consensus-critical VM code with no privilege required beyond broadcasting an ordinary transaction that performs a `CALL` to the precompile address.

### Likelihood Explanation
The precompiled contract is reachable by any account via a standard smart-contract `CALL` — no special privilege, stake, or witness/SR role is required. The unguarded path is taken whenever `VMConfig.allowTvmSelfdestructRestriction()` is false, which is the pre-upgrade/pre-activation configuration on any node or network that hasn't enabled that feature bit, making this trivially reachable in that state.

### Recommendation
Add strict length validation in `extractBytes32Array`, `extractBytesArray`, and `extractSigArray` (mirroring the `isValidAbiEncoding` header/tail checks already used elsewhere in the file) before allocating arrays or indexing `words`, unconditionally — not only when `allowTvmSelfdestructRestriction` is active. Ensure the extraction calls in `ValidateMultiSign.execute()` are also wrapped in the same defensive `try/catch(Throwable)` used later in the method, so malformed calldata always fails safely with `Pair.of(true, DATA_FALSE)` rather than propagating an exception out of the precompile.

### Proof of Concept
Craft a transaction that performs a `CALL` to the `ValidateMultiSign` precompiled address with ABI-encoded input where the "signature array length" word (at the offset pointed to by word index 3) is set to a very large value (e.g., `0x7FFFFFFF`), while `VMConfig.allowTvmSelfdestructRestriction()` is not yet activated on the target node/network. This drives execution into `extractBytesArray`, which attempts `new byte[Integer.MAX_VALUE][]`, throwing an uncontained `OutOfMemoryError`/`NegativeArraySizeException` in the precompile execution path described above. [8](#0-7)

    int len = words[offset].intValueSafe();
    byte[][] bytes32Array = new byte[len][];
    for (int i = 0; i < len; i++) {

    return bytes32Array;

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
