## Analysis

The Belt Finance incident is a flash-loan-driven manipulation of an AMM's internal price/share math to extract funds. The closest reachable analog in this repo is the TRC10 **Exchange** (Bancor-style AMM) actuators, which are directly reachable by any unprivileged transaction broadcaster via `ExchangeTransactionContract`.

### Title
Floating-point Bancor-formula rounding in the default TRC10 Exchange pricing path enables value extraction from pool reserves - (File: `chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java`)

### Summary
The default (non-"hardened") TRC10 exchange trade calculation, `ExchangeProcessor.exchange()`, computes swap output using `double`/`Math.pow` arithmetic and truncates intermediate "relay supply" and output amounts with raw `(long)` casts. This is the same class of bug that underlies AMM/flash-loan price-manipulation incidents like Belt Finance: an unprivileged account can drive the pool through a sequence of `ExchangeTransactionContract` trades (zero fee) chosen to exploit the accumulated rounding/precision loss of the double-based formula, extracting more value than deposited from the shared reserve funded by other users' `ExchangeInjectActuator` deposits.

### Finding Description
`ExchangeCapsule.transaction()` selects between two pricing engines based on the `hardenedCalc` flag: [1](#0-0) 

By default `hardenedCalc` is `allowHarden()` from `AbstractExchangeActuator`, which is gated by the dynamic property `allowHardenExchangeCalculation`: [2](#0-1) 

This property is an opt-in committee proposal value (see `ProposalUtil.java` / `DynamicPropertiesStore.java`), meaning the *default* live pricing path is `ExchangeProcessor`, not the `BigDecimal`-based `SafeExchangeProcessor`. The default processor computes both directions of the Bancor formula with `double` math and truncates with `(long)` casts: [3](#0-2) 

Compare this to the "hardened" replacement, which exists specifically to fix precision loss via `BigDecimal` with explicit scale/rounding: [4](#0-3) 

The existence of `SafeExchangeProcessor` as an opt-in hardening path is itself evidence that the team recognized the double-precision Bancor math in `ExchangeProcessor` is imprecise/exploitable, yet it remains the default unless a committee proposal activates `allowHardenExchangeCalculation`.

`ExchangeTransactionActuator.execute()` invokes this pricing engine directly from a single signed transaction, with no protocol-level fee (`calcFee()` returns `0`), so an attacker can execute many round-trip trades cheaply: [5](#0-4) [6](#0-5) 

The only user-side protection is a minimum-`expected` check that the attacker fully controls: [7](#0-6) 

There is no anti-manipulation mechanism (e.g., TWAP, per-block trade cap, or a single canonical fixed-point implementation) protecting the shared pool reserves (`firstTokenBalance`/`secondTokenBalance`) that other users fund through `ExchangeCreate`/`ExchangeInject`.

### Impact Explanation
Because the default trade math is floating-point based and independently truncates the "relay supply" step and the "output" step, sequences of trades sized to straddle rounding boundaries can cause the pool's tracked reserves to drift from the true conserved-value invariant. An attacker who repeatedly buys/sells (funding the round-trip from their own balance, playing the role a flash loan would play on Belt Finance/BSC) can extract more tokens than they contributed, permanently depleting reserves funded by other injectors — i.e., theft of pooled funds / unbacked balance in the exchange's ledger, matching the "unbacked balance"/"theft of funds" impact bar.

### Likelihood Explanation
Medium. Exploitation requires an attacker to work out and iterate the exact rounding boundary conditions of the `double`/`(long)`-cast formula (non-trivial but automatable/offline-computable), and the win-per-trade would likely be small, requiring many transactions to accumulate a meaningful drain — but each transaction is cheap (fee is `0`) and fully attacker-controlled (`tokenQuant`, `expected`), and the vulnerable path (`ExchangeProcessor`) is the default unless a chain-wide proposal has switched to hardened math.

### Recommendation
- Make `SafeExchangeProcessor` (the `BigDecimal`-based, rounding-mode-explicit implementation) the default and unconditional pricing engine for `ExchangeCapsule.transaction()`, removing the `hardenedCalc`/`allowHardenExchangeCalculation` toggle so all networks always use the precise path.
- Alternatively, if a phased proposal-based rollout is required for existing chains, ensure new deployments activate `allowHardenExchangeCalculation` at genesis rather than defaulting to the legacy double-precision processor.
- Add pool-invariant checks (e.g., verifying the product/relay-supply monotonicity or minimum reserve deltas) in `ExchangeTransactionActuator.execute()` independent of the `expected` parameter, so no sequence of trades can reduce total pool value below what conservation of the Bancor formula requires.

### Proof of Concept
Conceptual sequence, reachable purely with signed `ExchangeTransactionContract` transactions against a live (non-hardened) exchange pair:
1. Attacker (or colluding accounts) create/fund an `Exchange` pair via `ExchangeCreateActuator`/`ExchangeInjectActuator` (or reuse an existing one), establishing `firstTokenBalance`/`secondTokenBalance`.
2. Attacker submits a crafted sequence of `ExchangeTransactionContract` trades (sell A→B, then B→A, ...), choosing `quant` values near the truncation boundaries of `exchangeToSupply`/`exchangeFromSupply` in `ExchangeProcessor.java`.
3. Because `calcFee()` is `0` and only the attacker's own `expected` minimum gates each trade, the attacker repeats the round trip trades within the block(s) needed to accumulate a net positive token balance that exceeds what a fee/invariant-conserving AMM should allow, draining reserves contributed by other injectors.
4. This mirrors the Belt Finance bug class: manipulate an under-protected pricing/share calculation via a rapid sequence of self-funded trades to extract more value than deposited.

*Note:* I could not fully re-derive the exact numeric rounding direction/magnitude of the exploit within the available search tooling (this would require running the formula against many candidate `quant` values), so the precise minimal PoC transaction sequence and drained amount are not verified end-to-end — only the structural vulnerability (unconditioned double-precision AMM math as the default, zero-fee, attacker-controlled trade path) is confirmed from the code.

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }

  private BigDecimal exchangeToSupply(long balance, long quant) {
    long newBalance = StrictMathWrapper.addExact(balance, quant);
    BigDecimal bdQuant = BigDecimal.valueOf(quant);
    BigDecimal bdNewBalance = BigDecimal.valueOf(newBalance);
    BigDecimal base = BigDecimal.ONE.add(
        bdQuant.divide(bdNewBalance, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 0.0005);
    return SUPPLY.negate().multiply(
        BigDecimal.ONE.subtract(BigDecimal.valueOf(powResult))).setScale(0, RoundingMode.DOWN);
  }

  private long exchangeFromSupply(long balance, BigDecimal supplyQuant) {
    BigDecimal bdBalance = BigDecimal.valueOf(balance);
    BigDecimal base = BigDecimal.ONE.add(
        supplyQuant.divide(SUPPLY, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 2000.0);
    BigDecimal exchangeBalance = bdBalance.multiply(
        BigDecimal.valueOf(powResult).subtract(BigDecimal.ONE));
    return exchangeBalance.setScale(0, RoundingMode.DOWN).longValueExact();
  }
