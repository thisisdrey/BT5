### Title
`vesting.distribute_many` / `vest_many` / `unlock_rewards_many` Abort on Any Single Failing Contract, Blocking All Others in the Batch - (File: aptos-move/framework/aptos-framework/sources/vesting.move)

---

### Summary

`vesting.distribute_many`, `vest_many`, and `unlock_rewards_many` iterate over a caller-supplied list of vesting contract addresses and call their single-contract counterparts inside a closure loop. Because Move has no try-catch mechanism, any abort inside the loop — triggered by a single terminated, slashed, or otherwise invalid contract — propagates immediately and reverts the entire transaction, preventing every other contract in the batch from being processed.

---

### Finding Description

`unlock_rewards_many`, `vest_many`, and `distribute_many` are public entry functions that accept a `vector<address>` and call `unlock_rewards`, `vest`, or `distribute` respectively for each element via `for_each_ref`:

```move
// vesting.move line 643-652
public entry fun unlock_rewards_many(contract_addresses: vector<address>) acquires VestingContract {
    let len = contract_addresses.length();
    assert!(len != 0, error::invalid_argument(EVEC_EMPTY_FOR_MANY_FUNCTION));
    contract_addresses.for_each_ref(|contract_address| {
        let contract_address: address = *contract_address;
        unlock_rewards(contract_address);   // <-- can abort
    });
}

Concrete abort conditions inside the loop include:

1. **Terminated contract** — `assert_active_vesting_contract` aborts with `EVESTING_POOL_NOT_ACTIVE` if the contract state is `VESTING_POOL_TERMINATED`.
2. **Arithmetic underflow** — `total_active_stake - vesting_contract.remaining_grant - commission_amount` underflows if the underlying stake pool has been slashed below the recorded principal.
3. **Deposit failure** — inside `distribute`, `aptos_account::deposit_coins` is called for each shareholder's beneficiary address; if any beneficiary account is invalid, the entire `distribute` call (and thus the entire `distribute_many` batch) aborts. [6](#0-5) 

---

### Impact Explanation

Any unprivileged caller can submit a `distribute_many` / `vest_many` / `unlock_rewards_many` transaction that includes one terminated or otherwise problematic contract address alongside many valid ones. The entire transaction aborts, and none of the valid contracts receive their distributions. Vesting beneficiaries are denied their entitled APT payouts for that batch invocation. While individual `distribute` / `vest` / `unlock_rewards` calls still work, the batch entry points — which are the primary mechanism for operators managing many contracts — are rendered unreliable and can be griefed by any party who can observe on-chain contract state.

---

### Likelihood Explanation

Vesting contracts are terminated via `terminate_vesting_contract` by admins, which is a normal lifecycle event. Any operator who batches a terminated contract address alongside active ones (by mistake or due to a race condition between termination and batch submission) will trigger the abort. Additionally, stake slashing — though rare — can cause the arithmetic underflow path. Both conditions are reachable without any privileged access to the batch functions themselves.

---

### Recommendation

Add a guard before each inner call to skip contracts that would abort, mirroring the BondAggregator fix pattern. Since Move has no try-catch, the check must be done explicitly before calling the aborting function:

```move
public entry fun distribute_many(contract_addresses: vector<address>) acquires VestingContract {
    assert!(contract_addresses.length() != 0, error::invalid_argument(EVEC_EMPTY_FOR_MANY_FUNCTION));
    contract_addresses.for_each_ref(|contract_address| {
        let contract_address = *contract_address;
        // Skip non-active contracts instead of aborting the whole batch
        if (exists<VestingContract>(contract_address) &&
            borrow_global<VestingContract>(contract_address).state == VESTING_POOL_ACTIVE) {
            distribute(contract_address);
        };
    });
}
```

Apply the same pattern to `unlock_rewards_many` and `vest_many`.

---

### Proof of Concept

1. Deploy two vesting contracts: `contract_A` (active) and `contract_B` (active).
2. Call `terminate_vesting_contract(admin, contract_B)` — `contract_B` is now in `VESTING_POOL_TERMINATED` state.
3. Call `distribute_many(vector[contract_A, contract_B])` from any account.
4. The transaction aborts because `distribute(contract_B)` hits `assert_active_vesting_contract` and aborts with `EVESTING_POOL_NOT_ACTIVE`.
5. `contract_A`'s shareholders receive nothing despite `contract_A` being fully valid and having withdrawable stake.

The same scenario applies to `vest_many` and `unlock_rewards_many`. The abort path through arithmetic underflow can be triggered by including a contract whose stake pool has been slashed below its recorded principal.
