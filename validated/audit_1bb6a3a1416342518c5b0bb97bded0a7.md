### Title
Whale/flash-loan attacker can permanently DoS `DepositToken.deposit` by filling `maxTotalSupply` - (File: contracts/DepositToken.sol)

### Summary
`DepositToken._mint` enforces a governor-set `maxTotalSupply` cap and reverts with `SurpassMaxDepositSupply` once `totalSupply` reaches it. An unprivileged attacker can front-run a victim's `deposit` and push `totalSupply` to the cap, causing the victim's deposit to revert. Because the attacker has no debt, their entire `msdTOKEN` balance is unlocked, so they can immediately `withdraw` and recycle the same capital — meaning the attack costs only gas and can be executed with a flash loan of the underlying collateral. This is the direct analog of the Reality Cards `maxContractBalance` griefing: a deposit cap that any user can saturate to deny deposits to others.

### Finding Description
`deposit` pulls `underlying` to the Treasury, then calls `_mint(onBehalfOf_, _deposited)` [1](#0-0) . Inside `_mint`:

```solidity
totalSupply += amount_;
if (totalSupply > maxTotalSupply) revert SurpassMaxDepositSupply();
``` [2](#0-1) 

`withdraw` burns msdTokens and pulls collateral back via `_pool.treasury().pull(to_, _withdrawn)`, gated only by `_revertIfLocked` (unlocked when the attacker has no debt) and `whenNotShutdown` — there is no withdrawal cooldown or exit penalty beyond the withdraw fee [3](#0-2) [4](#0-3) .

Attack trace (all public entry points):
1. Attacker flash-borrows `underlying` (e.g., WETH/USDC/WBTC) equal to `maxTotalSupply - totalSupply + ε`.
2. `approve` + `deposit(amount, attacker)` → `totalSupply` hits the cap.
3. In the same block/bundle, victim's `deposit` reverts on `SurpassMaxDepositSupply`.
4. Attacker `withdraw(amount, attacker)` → recovers collateral, repays flash loan.
5. Repeat whenever deposits become useful again; the attacker can keep the cap saturated for the cost of a withdraw fee (and even avoid the fee's impact by redepositing).

Because `deposit` is the only path to acquire collateral positions needed for `mint`/`leverage` in `Pool`/`SmartFarmingManager`, denying deposits denies all protocol entry — equivalent to the Reality Cards "can't deposit → can't rent/bid" impact. A competitor can also block a specific user's collateral top-up while their position approaches liquidation, indirectly enabling forced liquidation profit.

Note `Pool.debtPositionOf`/`unlockedBalanceOf` and `onlyIfDepositTokenIsActive` do not help: a debt-free attacker's balance is fully unlocked, and `isActive` only blocks mints (which is the point of the attack anyway). `whenNotPaused`/`whenNotShutdown` are not set in normal operation. No invariant like solvency breaks — the broken property is **liveness of deposits**.

### Impact Explanation
Temporary, repeatable denial of deposits: any user can be prevented from depositing collateral, minting synthetics, or topping up collateral to avoid liquidation. If deposits are also used to rescue unhealthy positions, targeted DoS can contribute to bad-liquidation profit. Meets the "temporary freezing of funds / liveness" acceptance category.

### Likelihood Explanation
Requires capital equal to the remaining cap headroom, obtainable via flash loan in the same transaction, so cost is gas + withdraw fee only. Feasibility depends on the deployed `maxTotalSupply` values; if caps are set near circulating supply (as they typically are to bound collateral risk), the headroom is cheap to fill. Can also be done with the attacker's own funds held at the cap indefinitely.

### Recommendation
Either remove `maxTotalSupply` enforcement from `_mint`, set it to `type(uint256).max` (using it as a boolean deposit toggle like the Reality Cards team's mitigation), or make the cap non-griefable — e.g., per-account deposit limits, or pricing the cap usage so saturation is expensive. At minimum, document that saturating the cap is a known DoS vector and monitor `totalSupply` proximity to `maxTotalSupply`.

### Proof of Concept
Hardhat/Foundry fork sketch:

```solidity
// fork state with a live DepositToken (e.g., msdWETH) where
// maxTotalSupply - totalSupply = headroom
uint256 headroom = depositToken.maxTotalSupply() - depositToken.totalSupply();

// attacker: fill the cap (flashloan or own funds)
underlying.approve(address(depositToken), headroom + 1);
depositToken.deposit(headroom, attacker);

// victim: any deposit now reverts
vm.prank(victim);
vm.expectRevert(DepositToken.SurpassMaxDepositSupply.selector);
depositToken.deposit(1 ether, victim);

// attacker exits fully (no debt => fully unlocked)
depositToken.withdraw(depositToken.balanceOf(attacker), attacker);

// deposits are possible again — attacker can re-saturate at will
```

Confirmed by existing test coverage: `DepositToken.test.ts` shows `deposit` reverts with `SurpassMaxDepositSupply` once supply would exceed the cap [5](#0-4) .

    function _mint(
        address account_,
        uint256 amount_
    ) private onlyIfDepositTokenIsActive updateRewardsBeforeMintOrBurn(account_) {
        if (account_ == address(0)) revert MintToTheZeroAddress();

        totalSupply += amount_;
        if (totalSupply > maxTotalSupply) revert SurpassMaxDepositSupply();

        uint256 _balanceBefore = balanceOf[account_];
        unchecked {
            balanceOf[account_] = _balanceBefore + amount_;
        }

        emit Transfer(address(0), account_, amount_);

        // Add this token to the deposit tokens list if the recipient is receiving it for the 1st time
        if (_balanceBefore == 0 && amount_ > 0) {
            pool.addToDepositTokensOfAccount(account_);
        }
    }
