### Title
Attacker fills a victim's per-account token lists via dust `DepositToken` transfers, blocking collateral top-ups and forcing liquidation - ([File: contracts/Pool.sol])

### Summary
`Pool` tracks each account's deposit and debt tokens in `MappedEnumerableSet.AddressSet` lists, and enforces a global cap `MAX_TOKENS_PER_USER` on the combined length via the `onlyIfAdditionWillNotReachMaxTokens` modifier on `addToDepositTokensOfAccount` / `addToDebtTokensOfAccount` [1](#0-0) . Because `DepositToken` is a freely transferable ERC20, any holder can dust-transfer each registered `DepositToken` to a victim, permanently occupying slots in `depositTokensOfAccount[victim]` until the victim's combined count hits the cap [2](#0-1) . Once filled, every subsequent first-time receipt of a deposit token, `deposit(amount, onBehalfOf=victim)` for a token the victim doesn't hold, and any `DebtToken.issue`/`flashIssue` on behalf of the victim reverts with `UserReachedMaxTokens` — locking the victim out of adding new collateral while their position decays into liquidation.

### Finding Description
`DepositToken._transfer` calls `pool.addToDepositTokensOfAccount(recipient_)` whenever the recipient's balance was previously zero [2](#0-1) . `Pool.addToDepositTokensOfAccount` reverts if `debtTokensOfAccount.length + depositTokensOfAccount.length >= MAX_TOKENS_PER_USER` [3](#0-2) . There is no opt-in/consent: the victim cannot refuse receipt, and the slot is only freed when the victim's balance for that specific token returns to zero (`removeFromDepositTokensOfAccount` is called on burn/full transfer-out) [4](#0-3) .

Attack trace (all public, unprivileged):
1. Attacker deposits a dust amount of the underlying into every registered `DepositToken` (`deposit(amount, attacker)`), then calls `depositToken.transfer(victim, 1 wei)` for each.
2. Each transfer inserts the token into `depositTokensOfAccount[victim]`. Combined with the victim's existing deposit/debt tokens, the list reaches `MAX_TOKENS_PER_USER`.
3. Now `deposit(amount_, victim)` reverts for any deposit token the victim doesn't already hold (mint → `addToDepositTokensOfAccount` → `UserReachedMaxTokens`), and the victim cannot receive any new deposit token via transfer.
4. If the victim's position approaches the collateral-factor boundary, they cannot diversify/top up with a new collateral type to restore health; a price move then lets any liquidator call `Pool.liquidate` and seize the position — the victim's only escape is repaying debt, which requires already holding the synthetic.

The analog to CVE-2016-8289: an unprivileged ("local") user corrupts per-account state (integrity) to deny service (availability) — here, denial of collateral deposits/new positions enabling forced liquidation.

### Impact Explanation
Denial of a victim's ability to add collateral or open new debt positions, leading to preventable liquidations and loss of the victim's collateral to liquidators (seized via `DepositToken.seize` during `Pool.liquidate`). This is temporary freezing/griefing of account functionality plus indirect theft via liquidation, satisfying the accepted impact classes. Severity is bounded: the victim retains full use of tokens already in their list (withdraw/repay of existing positions still works), so damage requires the victim to need a *new* token to rescue the position.

### Likelihood Explanation
Cost is proportional to the number of registered deposit tokens the victim doesn't hold: one dust deposit + one transfer each. On deployments with many listed collaterals the cost is real but modest; on deployments with few tokens it's trivial. Requires a victim whose rescue path needs a not-yet-held collateral, which is common when the cheapest available collateral differs from what they hold.

### Recommendation
- Make slot occupation consent-based: only add to `depositTokensOfAccount` on mint/`deposit`, not on ERC20 `transfer`/`transferFrom` — or whitelist transfers so recipients can reject. Alternatively exempt `transfer`-initiated adds from the cap and lazily skip zero/dust entries in `depositOf`/`debtOf` iteration.
- Alternatively raise/remove the cap and bound iteration gas differently, or let an account "eject" unwanted dust tokens (a `removeMyDust` that transfers sub-wei balances to a sink).

### Proof of Concept
Hardhat (fork or local) sketch:

```ts
// victim has a healthy position with 1 deposit token type (msdMET)
const depositTokens = await pool.getDepositTokens(); // all registered
for (const dt of depositTokens) {
  if (dt === msdMET.address) continue;
  const token = await ethers.getContractAt('DepositToken', dt);
  const underlying = await ethers.getContractAt('ERC20', await token.underlying());
  await underlying.connect(attacker).approve(token.address, 1);
  await token.connect(attacker).deposit(1, attacker.address);   // mint dust
  await token.connect(attacker).transfer(victim.address, 1);    // occupies a slot
}
// also issue dust debt on behalf of victim for each DebtToken to fill remaining slots
// now:
await expect(
  msdWETH.connect(victim).deposit(parseEther('1'), victim.address) // any NEW deposit token
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');
await expect(
  msdMET.connect(charity).deposit(1, victim.address) // even deposits on behalf with held token OK;
  // but any token not already in victim's list reverts
);
// crash price, victim cannot add collateral → liquidate succeeds
await masterOracle.updatePrice(met.address, lowPrice);
await pool.connect(liquidator).liquidate(msEth.address, victim.address, amount, msdMET.address);
```

Uncertainties I could not fully verify within iteration limits: the exact deployed `MAX_TOKENS_PER_USER` value (it is a constant in `Pool.sol`; the ABI exposes it) and whether `DebtToken.issue(amount, onBehalfOf=victim)` is callable by arbitrary third parties (needed to fill debt-side slots — deposit-token dust alone suffices if the victim's existing list is short only on the deposit side). Neither blocks the core finding.
