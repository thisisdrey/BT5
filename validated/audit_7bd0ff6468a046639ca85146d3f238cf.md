### Title
`ERC20Transactor` credits/debits the XCM holding register with the nominal transfer amount instead of the actual ERC20 balance delta, allowing fee-on-transfer/rebasing ERC20 assets to drain or lock the shared checking account - (File: cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs)

### Summary
`ERC20Transactor::withdraw_asset_with_surplus` and `deposit_asset_with_surplus` implement XCM's `TransactAsset` for ERC20 tokens held in `pallet-revive` contracts, wired into `asset-hub-westend`'s `xcm_config.rs` via a shared `TransfersCheckingAccount`. Both functions issue an ERC20 `transfer()` call and, on success, unconditionally treat the requested nominal `amount` as the value moved — never checking `balanceOf` before/after. This is the same root cause as the confirmed High-severity THORChain finding: code that assumes an ERC20 transfer moves exactly the requested amount, when the token may be fee-on-transfer or rebasing.

### Finding Description
`withdraw_asset_with_surplus` (`erc20_transactor.rs:150-216`) transfers `amount` from a user's account to the single shared `TransfersCheckingAccount`, and on a successful (non-reverted, `true`-returning) ERC20 call, credits the XCM holding register with `Erc20Credit(amount)`: [1](#0-0) 

`deposit_asset_with_surplus` (`erc20_transactor.rs:218-306`) then transfers that same nominal `amount` out of the checking account to the beneficiary, again trusting the boolean return value of `transfer()` rather than verifying the actual balance moved: [2](#0-1) 

Neither function reads `IERC20.balanceOf(checking_account)` before and after the call to compute the real delta, unlike the balance-diff pattern the external report itself cites as the correct fix (`_startBal`/`balanceOf` diff around `transferFrom`). For any ERC20 whose `transfer()` does not move exactly `value` tokens 1:1 (fee-on-transfer, deflationary/rebasing supply mechanics, or any token whose internal accounting divides/multiplies balances by a mutable factor), the nominal `amount` recorded in the ephemeral XCM holding register diverges from the real balance held by the single, shared `TransfersCheckingAccount`. Because that account is shared across every user and every XCM message that moves that asset class (confirmed by its use in `asset-hub-westend/src/xcm_config.rs`), a persistent mismatch accumulates in the *real* on-chain ERC20 balance versus what the code assumes:
- If the token takes a fee/negative rebase on transfer, the checking account ends up under-funded relative to the sum of nominal amounts still "in flight"; the next unrelated user's `deposit_asset_with_surplus` for the same asset can fail (locking funds) or drain balance genuinely belonging to a different pending transfer.
- If the token can positive-rebase (balance increases without a corresponding transfer), the checking account accumulates untracked surplus that is not represented by any withdraw-credited amount, and is not reachable by any legitimate accounting path but *is* reachable by any account that manages to trigger a `deposit_asset_with_surplus` for that asset — draining funds that other users are still relying on to back their outstanding nominal credits.

The check `is_success`/`did_revert()` only verifies the call didn't revert and returned `true`; it provides no guarantee about the magnitude actually transferred, exactly mirroring the router pattern flagged as High in the external report.

### Impact Explanation
This directly matches the "theft or unbacked mint/unlock" and "permanent user-fund or bridge-state lock" impact classes for a public, unprivileged entrypoint (any account can construct an XCM program using `WithdrawAsset`/`DepositAsset` against an ERC20 asset registered with this transactor, no admin/governance/relayer involvement required). A malicious actor can cause other users' funds routed through the shared `TransfersCheckingAccount` to be stolen or locked once a non-standard-transfer ERC20 (fee-on-transfer or rebasing) is registered as a matched fungible asset for this transactor.

### Likelihood Explanation
Likelihood depends on whether any asset registered with `Matcher: MatchesFungibles` for this transactor is a non-standard ERC20 (fee-on-transfer or rebasing). Since `pallet-revive` allows arbitrary Solidity contracts to be deployed and subsequently whitelisted/matched as XCM-fungible assets, and the transactor performs no defensive balance check, any future/whitelisted asset with non-1:1 transfer semantics turns this into an exploitable path without any privileged action — the vulnerable code path itself requires no malicious admin or relayer, only a token with mutable transfer semantics interacting with an already-shipped transactor.

### Recommendation
In both `withdraw_asset_with_surplus` and `deposit_asset_with_surplus`, read `IERC20.balanceOf` on the checking account (and/or the source/destination account) immediately before and after the `transfer()` call, and use the actual delta — not the nominal `amount` — both for the value credited into `AssetsInHolding` and for any downstream accounting. Reject or clamp when the delta does not match the requested amount, consistent with the safe-transfer pattern already recommended in the cited report.

### Proof of Concept
1. Deploy (or otherwise register via `MatchesFungibles`) an ERC20 contract `X` whose `transfer()` deducts a fee (or is rebasing) such that `balanceOf(recipient)` increases by less than the `value` argument.
2. Register `X` as a matched fungible asset for `ERC20Transactor` (e.g. via whatever governance/registration path adds assets to the `Matcher` config on asset-hub).
3. Alice holds `X` and executes an XCM program (e.g. via `pallet_xcm::execute`) containing `WithdrawAsset` for `X` amount `A`, followed by `DepositAsset` to Bob for the same nominal amount `A`.
4. `withdraw_asset_with_surplus` transfers `A` to `TransfersCheckingAccount`; actual balance received is `A - fee`. Holding register is nonetheless credited with `Erc20Credit(A)`.
5. `deposit_asset_with_surplus` attempts to transfer `A` from the checking account to Bob. If the checking account has residual balance from an unrelated prior/pending transfer (e.g. left over from another user's shortfall or a positive-rebase surplus), the transfer succeeds, draining balance that belongs to that other user/transfer; otherwise the ERC20 call fails and the transfer reverts, permanently stalling that user's `DepositAsset` (locked funds) despite the withdraw having already succeeded and consumed weight/deposit.
6. Repeated over many transactions, the checking account's real ERC20 balance diverges from the sum of nominal in-flight amounts, enabling systematic fund loss/lock for users sharing that asset's checking account — the same underlying flaw the external report rated High severity.
