### Title
Missing cap on `GetAttachmentsInvResponse.pages` length/uniqueness allows response-size-proportional compute cost during Atlas attachment inventory processing - ([File: stackslib/src/net/atlas/download.rs], [File: stackslib/src/net/api/getattachmentsinv.rs])

### Summary
`decode_atlas_attachments_inv_response` deserializes the response body straight into `GetAttachmentsInvResponse { block_id, pages: Vec<AttachmentPage> }` with no check that `pages.len()` matches the number of page indexes the requesting node asked for, and no de-duplication of `index` values. `extend_with_inventories` and `get_prioritized_attachments_requests` then store and iterate this attacker-controlled `Vec` as-is.

### Finding Description
The request side caps `page_indexes.len()` to `MAX_ATTACHMENT_INV_PAGES_PER_REQUEST` (8) both when building the request (`AttachmentsInventoryRequest::make_request_type`, `stackslib/src/net/atlas/download.rs:1028-1056`) and when the server validates an incoming request (`stackslib/src/net/api/getattachmentsinv.rs:159-168`). However this cap constrains only what a *well-behaved* server returns; it is never re-checked on the client/consumer side. [1](#0-0) 

`decode_atlas_attachments_inv_response` simply parses arbitrary JSON into the response struct with no length/uniqueness validation: [2](#0-1) 

`GetAttachmentsInvResponse`/`AttachmentPage` place no `#[serde]` bound on vector length: [3](#0-2) 

`extend_with_inventories` stores whatever `pages` Vec came back, per peer, without checking it against the originating request's page count: [4](#0-3) 

That stored response is later linearly scanned once per missing attachment index, per peer, via `response.pages.iter().find(...)`: [5](#0-4) 

So the invariant "`len(response.pages) == len(requested page_indexes)`" is indeed never enforced, and a malicious peer that is queried for an attachment inventory can return an inflated `pages` array (with far more than 8 entries, or duplicate `index` values) in a single HTTP response.

However, this response is still bounded by the generic HTTP body size limits enforced by the shared HTTP parsing layer (`stackslib/src/net/http/response.rs`, using `MAX_MESSAGE_LEN`/chunked-encoding caps) that apply to *every* Stacks HTTP RPC response, not just this endpoint. So the attacker cannot make `pages.len()` literally unbounded — it is capped by however many small JSON `AttachmentPage` objects fit inside the existing global HTTP response size ceiling. Within that ceiling, though, nothing stops the attacker from filling the response with thousands of small/duplicate page entries instead of the ≤8 legitimate ones, causing extra (but linear, not exponential) iteration cost in `get_prioritized_attachments_requests` for every missing attachment that shares that page-group key.

### Impact Explanation
A malicious Atlas peer that a victim node queries for `/v2/attachments/inv` can inflate the returned `pages` array well beyond the 8-page cap the victim itself enforces on outbound requests and on its own server-side handling of inbound requests. This causes the victim to do additional, but linearly-bounded (bounded by the pre-existing global HTTP message-size cap), compute work per attachment-batch cycle while resolving missing attachments. This is a real validation gap (bypassing the intended per-request page cap on the read/consume path) but the resulting compute cost is bounded by an already-existing generic protection (max HTTP response/message size), not unbounded, and it affects the Atlas attachment-batching subsystem rather than crashing the node, corrupting consensus state, or exposing memory. It best matches "bounded compute DoS on a read endpoint," but only weakly given the existing generic size cap already limits the blast radius considerably.

### Likelihood Explanation
Any peer whose advertised URL a node adds to its Atlas peer set (attainable by simply being a discoverable neighbor, with no privileged credentials) can serve this response whenever queried, with no signature or authentication requirement, at the cost of one crafted HTTP response body. Repeatable on every attachment-inventory query.

### Recommendation
In `decode_atlas_attachments_inv_response` (or immediately after, in `extend_with_inventories`), validate that `response.pages.len() <= MAX_ATTACHMENT_INV_PAGES_PER_REQUEST` and that all `AttachmentPage.index` values are unique (and ideally match the originally-requested indices for that request), rejecting/discarding the response (and penalizing the peer's reliability score) otherwise.

### Proof of Concept
1. In `stackslib/src/net/api/tests/getattachmentsinv.rs`, construct a raw JSON body for `GetAttachmentsInvResponse` with `block_id` set to any value and `pages` containing, e.g., 500 `AttachmentPage { index: 1, inventory: vec![] }` entries (duplicated index, far above `MAX_ATTACHMENT_INV_PAGES_PER_REQUEST`).
2. Wrap it into a `StacksHttpResponse` (as done in `stackslib/src/net/atlas/tests.rs::new_attachments_inventory_response`, but bypassing the normal server encoding that enforces the 8-page cap) and call `.decode_atlas_attachments_inv_response()`.
3. Assert `resp.pages.len() == 500` (i.e., no error and no truncation), proving the deserializer/consumer does not enforce the request-side cap. This test does not need to bypass the global HTTP message size limit as long as 500 small JSON entries fit under it.

    pub fn extend_with_inventories(
        mut self,
        results: &mut BatchedRequestsResult<AttachmentsInventoryRequest>,
    ) -> AttachmentsBatchStateContext {
        for (request, response) in results.succeeded.drain() {
            let report = self
                .peers
                .get_mut(request.get_url())
                .expect("Atlas: unable to retrieve reliability report for peer");

            let response = if let Some(r) = response {
                r
            } else {
                report.bump_failed_requests();
                continue;
            };

            if let Ok(response) = response.decode_atlas_attachments_inv_response() {
                let peer_url = request.get_url().clone();
                match self.inventories.entry(request.key()) {
                    Entry::Occupied(responses) => {
                        responses.into_mut().insert(peer_url, response);
                    }
                    Entry::Vacant(v) => {
                        let mut responses = HashMap::new();
                        responses.insert(peer_url, response);
                        v.insert(responses);
                    }
                };
                report.bump_successful_requests();
            } else {
                report.bump_failed_requests();
            }
        }
        let mut events_ids = results.faulty_peers.keys().copied().collect::<Vec<usize>>();
        self.events_to_deregister.append(&mut events_ids);

        self
    }
