## Title
Missing check for the "zero" TRON address (prefix + 20 zero bytes) in `TransferActuator`/`TransferAssetActuator` allows permanent loss of user funds - (File: `actuator/src/main/java/org/tron/core/actuator/TransferActuator.java`, `actuator/src/main/java/org/tron/core/actuator/TransferAssetActuator.java`)

### Summary
`DecodeUtil.addressValid()`, the single validation routine every actuator uses to sanity-check a destination/receiver address, only verifies the address length and the network prefix byte — it never rejects the degenerate address consisting of the prefix byte followed by 20 zero bytes (TRON's analog of Solidity's `address(0)`). Because `TransferActuator` and `TransferAssetActuator` auto-create the destination account when it does not yet exist and then unconditionally move TRX/TRC10 balance to it, a user (or a wallet/dApp bug) that submits a `TransferContract`/`TransferAssetContract` with `to_address` set to this all-zero address will have their funds moved to an address nobody can practically control, exactly mirroring the reported `TimeLockPool` bug class ("missing `address(0)` check → user loses funds").

### Finding Description
`DecodeUtil.addressValid()`: [1](#0-0) 

only checks `address.length == 21` and `address[0] == addressPreFixByte`; it does not check whether the remaining 20 bytes are all-zero.

`TransferActuator.validate()` uses exactly this check on `toAddress`, only additionally guarding against `toAddress == ownerAddress`, with no zero-address guard: [2](#0-1) 

`TransferActuator.execute()` then auto-creates the account for `toAddress` if none exists and irreversibly moves the transferred amount there: [3](#0-2) 

The same pattern (address-format-only validation plus auto account creation) exists in `TransferAssetActuator.validate()`/`execute()` for TRC10 asset transfers: [4](#0-3) [5](#0-4) 

Since finding a private key whose derived address hashes to all zero bytes is computationally infeasible (same assumption underlying Ethereum's `address(0)` burn semantics), any TRX or TRC10 tokens sent to `prefix||0x00*20` are permanently and irrecoverably lost — unlike the actual TRON "black hole" address, which is a distinct, deliberately-chosen, well-known address (`accountStore.getBlackhole()`), the all-zero address here is not a sanctioned burn target and receives no special handling.

### Impact Explanation
Any unprivileged account holder can, by mistake (e.g., a bug in wallet software, a misconfigured API client, or copy/paste error zeroing out the destination bytes) permanently lose TRX or TRC10 asset balance with no possibility of recovery, since the actuator happily creates the destination account and credits it. This is a permanent loss-of-funds condition, matching the impact class accepted by the rules (permanent freezing/loss of user funds), reachable purely through a single signed `TransferContract`/`TransferAssetContract` transaction broadcast by any account — no privileged role required.

### Likelihood Explanation
Likelihood is driven by client-side/wallet bugs or malformed input rather than deliberate on-chain manipulation (an attacker cannot steal funds this way, only cause the sender to self-harm). It is nonetheless a realistic occurrence class (identical to what auditors flagged in TimeLockPool) since nothing in the node-side validation stops it — the check is entirely absent, so the only defense today is external tooling correctly avoiding the zero pattern.

### Recommendation
Add an explicit rejection of the all-zero-payload address (prefix byte followed by 20 zero bytes) in `DecodeUtil.addressValid()` or, at minimum, add a dedicated check in `TransferActuator.validate()` and `TransferAssetActuator.validate()` (and any other actuator that auto-creates a destination account) that rejects `toAddress`/`receiverAddress` equal to this degenerate value, similar to the existing `Arrays.equals(toAddress, ownerAddress)` self-transfer guard.

### Proof of Concept
1. Construct a `TransferContract` with `owner_address = <funded account>` and `to_address = <prefix_byte> + 20×0x00` (21 bytes total, valid TRON address format).
2. Sign and broadcast the transaction.
3. `TransferActuator.validate()` passes `DecodeUtil.addressValid(toAddress)` (correct length/prefix) and passes the self-transfer check (`toAddress != ownerAddress`).
4. `TransferActuator.execute()` finds no existing account at the zero address, creates one, and credits it with the transferred amount — funds are now held by an address with no discoverable private key, i.e., permanently lost.

  public static boolean addressValid(byte[] address) {
    if (ArrayUtils.isEmpty(address)) {
      logger.warn("Warning: Address is empty !!");
      return false;
    }
    if (address.length != ADDRESS_SIZE / 2) {
      logger.warn(
          "Warning: Address length need " + ADDRESS_SIZE + " but " + address.length
              + " !!");
      return false;
    }

    if (address[0] != addressPreFixByte) {
      logger.warn("Warning: Address need prefix with " + addressPreFixByte + " but "
          + address[0] + " !!");
      return false;
    }
    return true;
  }
