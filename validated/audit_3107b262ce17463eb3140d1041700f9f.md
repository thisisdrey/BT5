### Title
Zip extraction containment check bypass via prefix comparison without path-separator boundary check - (File: `third_party/ijar/zip_main.cc`)

### Summary
`UnzipProcessor::Process` in ijar's zip/unzip tool validates that an extracted entry stays inside the requested output directory by doing a raw string-prefix comparison of the normalized output path against the normalized output root, but never verifies that a path separator (or end-of-string) follows the matched prefix. This is the same bug class as the ENS `BytesUtils.compare` finding: a length-bounded comparison that is supposed to gate a security decision but omits the boundary check needed to make "is-a-prefix-of" mean "is-contained-in", allowing a sibling path that merely shares a textual prefix with the root to be treated as contained.

### Finding Description
The containment check is: [1](#0-0) 

```cpp
std::string normalized_root = normalize_path(output_root_);
std::string normalized = normalize_path(path);
if (normalized.compare(0, normalized_root.size(), normalized_root) != 0) {
  ...
  abort();
}
```

`std::string::compare(0, n, other)` only checks whether the first `n` characters of `normalized` equal `normalized_root`. It does not check that the character immediately following the matched prefix is `/` (i.e., that `normalized_root` is an actual ancestor path segment, not merely a leading substring). Consequently, an output path such as `/tmp/extract_evil/file`, whose first `len("/tmp/extract")` characters equal `/tmp/extract`, satisfies the comparison even though `/tmp/extract_evil` is a sibling directory of `/tmp/extract`, not a subdirectory.

The archive entry name (`filename`) that is concatenated into `path` via `concat_path()` and then normalized comes directly from the zip central directory, i.e., from bytes an attacker fully controls when they author or serve a malicious archive that a victim's build extracts with this tool. By choosing an entry name such as `../extract_evil/payload` (or any name that, after `output_root_ + "/" + filename` is path-normalized, collapses to a sibling of `output_root_` sharing its literal prefix), the resulting `normalized` string still passes the buggy prefix check, while `make_dirs`/`write_file` subsequently create/write the file **outside** the intended output directory.

This mirrors exactly the reported bug class: a truncated/length-based comparison (`BytesUtils.compare` masking only the last chunk, vs. `std::string::compare(0, n, ...)` only checking the first `n` bytes) that is relied upon for a security-relevant decision (string/path equality or containment) but is missing the extra condition needed for correctness (masking irrelevant trailing bytes in all loop iterations vs. checking the boundary separator after the matched prefix).

### Impact Explanation
A hostile zip archive processed by this extractor (Bazel's ijar `unzip` tool, used by build/packaging rules and available as a general-purpose zip extraction utility invoked on archive content that can originate from external, attacker-influenced sources) can escape the declared output directory and write files to an attacker-chosen sibling path on the filesystem, corrupting or overwriting files outside the intended repository/output tree. This is a concrete "write outside the repository/output-directory" containment bypass, not merely denial of service.

### Likelihood Explanation
Exploitability only requires the attacker to control the name of one entry in a zip file that is fed to this extractor — a low bar for anyone able to publish or serve an archive that a victim's build consumes. No credentials, sandbox escape, or trusted-root BUILD file access is needed; the only "trust" that is broken is the assumption that the prefix check enforces containment, which it does not.

### Recommendation
Change the containment check to also validate that the character following the matched prefix is a path separator or the end of the string, mirroring the correct pattern already used elsewhere in the codebase (e.g., `paths.bzl`'s `_starts_with`, which explicitly checks `norm_a[len(norm_b)] == "/"`): [2](#0-1) 

```cpp
if (normalized.compare(0, normalized_root.size(), normalized_root) != 0 ||
    (normalized.size() > normalized_root.size() &&
     normalized[normalized_root.size()] != '/')) {
  ...
  abort();
}
```

### Proof of Concept
1. Craft a malicious zip archive whose central directory contains an entry name that, when concatenated with the extraction `output_root_` and passed through `normalize_path`, resolves to a sibling directory sharing the root's literal prefix (e.g., entry name `../extract_evil/payload` when `output_root_` is `/tmp/extract`, so `normalized` becomes `/tmp/extract_evil/payload`).
2. Invoke the ijar `unzip` tool (`UnzipProcessor::Process`, `third_party/ijar/zip_main.cc:105-149`) with `output_root_ = "/tmp/extract"` on this archive.
3. Observe that `normalized.compare(0, normalized_root.size(), normalized_root)` returns `0` (match) because the first 12 characters of `/tmp/extract_evil/payload` equal `/tmp/extract`, so the containment check at line 136 does not `abort()`.
4. `make_dirs`/`write_file` then create `/tmp/extract_evil/payload`, a location outside the declared `/tmp/extract` output root, confirming the containment bypass.

A JUnit/C++ unit test replicating this scenario (asserting that `UnzipProcessor::Process` rejects or does not escape when given such a crafted entry name) would fail against the current implementation and pass once the boundary-character fix above is applied.

    """Returns True if and only if path_b is an ancestor of path_a.

    if not path_b:
        # all paths start with the empty string

    norm_a = _normalize(path_a)

    if len(norm_b) > len(norm_a):
        return False
