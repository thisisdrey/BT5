## Title
Infinite-loop Denial of Service in JSON request parsing due to missing EOF check in `JsonFormat.merge`/`Tokenizer` - (File: `framework/src/main/java/org/tron/core/services/http/JsonFormat.java`)

## Summary
The CVE describes an `ImageMagick` text-image reader loop that never checks the end-of-file condition, causing an infinite loop on crafted input. The same bug class — a parsing loop that fails to check for end-of-input before continuing — exists in java-tron's HTTP JSON body parser, `JsonFormat`, which every unauthenticated HTTP API POST endpoint (contract deployment, transaction creation, asset issuance, exchange operations, etc.) uses to turn a client-supplied JSON string into a protobuf message.

## Finding Description
The top-level `JsonFormat.merge(CharSequence, ...)` entry point parses a JSON object with: [1](#0-0) 

Unlike the nested-object parser `handleObject`, which explicitly guards against running past the end of input with `if (tokenizer.atEnd()) { throw ... }` before each iteration: [2](#0-1) 

the top-level loop at line 292 (`while (!tokenizer.tryConsume("}")) { mergeField(...); tokenizer.tryConsume(","); }`) has **no such `atEnd()` check**.

The loop's only guard against non-termination is that `mergeField` -> `tokenizer.consumeIdentifier()` should throw a `ParseException` on bad input. But `consumeIdentifier()` is implemented as: [3](#0-2) 

The validation `for (int i = 0; i < currentToken.length(); i++)` is skipped entirely when `currentToken` has length 0 — which is exactly the state `Tokenizer` reaches at end-of-input, per `atEnd()`: [4](#0-3) 

and per `nextToken()`'s EOF branch, which repeatedly sets `currentToken = ""` without ever throwing or advancing state once the matcher region is exhausted: [5](#0-4) 

So for a truncated top-level JSON object (e.g. `{"key":"value"` with no closing `}`), once the tokenizer reaches EOF:
1. `tryConsume("}")` fails (current token is `""`, not `"}"`), so the `while` loop body runs.
2. `mergeField` -> `consumeIdentifier()` returns `""` without throwing and without ever changing tokenizer state.
3. Field lookup for the empty name fails, `unknown` stays false or field stays null, control returns to the `while` loop.
4. `tryConsume(",")` also fails silently.
5. The loop repeats step 1 forever — the tokenizer state never advances and never satisfies the exit condition, producing an unbounded, CPU-pinned infinite loop on the HTTP request-handling thread.

This mirrors the `ImageMagick` `ReadTXTImage` bug class exactly: a parsing loop that omits an end-of-input check that a sibling routine in the same file (`handleObject`) already recognizes as necessary.

## Impact Explanation
`JsonFormat.merge` is the shared JSON-body-to-protobuf bridge used by nearly all Wallet HTTP servlets that accept POST JSON bodies (e.g. `DeployContractServlet`, `CreateAssetIssueServlet`, `FreezeBalanceServlet`, `FreezeBalanceV2Servlet`, `ExchangeCreateServlet`, `ExchangeInjectServlet`, `ExchangeTransactionServlet`, `ExchangeWithdrawServlet`, `AccountPermissionUpdateServlet`, `DelegateResourceServlet`, `CreateCommonTransactionServlet`, and dozens more under `framework/src/main/java/org/tron/core/services/http/`), all reachable by any anonymous API client without any signature or authentication requirement:


An attacker sending a request with a truncated/malformed top-level JSON object to any of these endpoints pins the handling thread in an infinite loop. Repeating this against the finite HTTP thread pool exhausts it, making the node's HTTP Wallet API unavailable — "an API the node can no longer serve," matching the accepted impact criteria.

## Likelihood Explanation
This requires no authentication, no signed transaction, and no special privilege — only an HTTP POST with a deliberately truncated JSON body (missing a closing `}`) to any servlet that calls `JsonFormat.merge`. The bug is trivially and repeatedly triggerable by any remote, anonymous client.

## Recommendation
Add the same `atEnd()` guard to the top-level `merge` loop that already exists in `handleObject` (throw a `ParseException` when the tokenizer reaches end-of-input before the closing `}` is found), and make `consumeIdentifier()` throw when `currentToken` is empty rather than silently accepting a zero-length identifier.

## Proof of Concept
Send a POST request to any Wallet HTTP endpoint that parses its JSON body via `JsonFormat.merge` (e.g. `/wallet/deploycontract`, `/wallet/createassetissue`) with a body such as:
```
{"owner_address":"41...
```
(a JSON object opened with `{` but never closed with `}`, and cut off mid-token, e.g. ending in the middle of a quoted string). The truncated token drives the `Tokenizer` to end-of-input while `mergeField`'s `consumeIdentifier()` returns an empty identifier without throwing, and the top-level `while (!tokenizer.tryConsume("}"))` loop in `JsonFormat.merge` never terminates, pinning the handling thread at 100% CPU indefinitely.

    Tokenizer tokenizer = new Tokenizer(input);

    while (!tokenizer.tryConsume("}")) { // Continue till the object is done

      tokenizer.tryConsume(",");

    if (!tokenizer.atEnd()) {

          "Expecting the end of the stream, but there seems to be more data!  "

    }
