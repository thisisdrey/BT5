### Title
Unchecked git-fetch failure heuristic allows silent continuation on genuine command errors - (File: internal/gitaly/service/repository/fetch_remote.go)

### Summary
`fetchRemoteAtomic` distinguishes "benign" `git-fetch(1)` failures (where some references failed to update but others should still be applied) from genuine failures using two weak signals: whether `stderr` is empty, and whether the Go `exec` error's string representation equals exactly `"exit status 1"`. Any failure mode that produces empty stderr and coincidentally exits with status 1 is treated as a partial-success case, and the RPC proceeds to migrate quarantined objects and commit reference updates, rather than aborting.

### Finding Description
In `fetchRemoteAtomic` [1](#0-0) , when `quarantineRepo.FetchRemote` returns an error, the code does not check the actual git exit status via `command.ExitStatus`, nor validate that the failure specifically corresponds to a reference-update rejection (e.g. non-fast-forward). Instead, it relies purely on:
1. `stderr.String() == ""`
2. `err.Error() == "exit status 1"`

If both hold, the function assumes the failure was "a failed reference update" and continues normal processing: parsing whatever porcelain output was collected, queuing reference updates, migrating quarantined objects out of quarantine, and committing the reference transaction. This is analogous to the reported ERC20 issue, where a call's failure signal (a `false` return instead of a revert) was not properly validated and the failed operation was treated as valid, allowing downstream logic to proceed incorrectly. Here, the analogous failure signal is the process error string/stderr content, which is not a reliable indicator of "only some refs failed" — many other error paths in `git-fetch` (killed by resource limits, some transport errors, `--dry-run` misbehavior, unexpected git version differences) can also produce exit code 1 with empty stderr under `--porcelain --dry-run`, especially since verbose/porcelain output goes to stdout, not stderr.

### Impact Explanation
If the heuristic misfires, Gitaly proceeds to apply a partial/incomplete set of reference updates derived from potentially incomplete or corrupted porcelain stdout output, migrates whatever objects made it into the quarantine directory, and commits those changes as if the fetch had cleanly completed except for some ref conflicts. This can leave the repository in an inconsistent state, silently drop expected updates, or (in the pull-mirror path) mask real fetch failures such as truncated/interrupted transfers as normal operation, since the caller only observes `TagsChanged`/`RepoChanged` and no error.

### Likelihood Explanation
`FetchRemote` is reachable by any caller permitted to invoke repository mirroring/pull-mirror RPCs supplying attacker-influenced `RemoteParams` (URL, refspecs). Triggering an exit-status-1 failure with empty stderr from `git-fetch` against a crafted/misbehaving remote is plausible (e.g., a remote that aborts the connection at a specific point, or intentionally malformed pack data causing failure after some refs are already parsed in stdout), making this reachable without special privileges beyond permission to configure a remote/mirror.

### Recommendation
Replace the string-based heuristic with a structural check: parse the porcelain output to confirm which references failed (`RefUpdateTypeUpdateFailed`) independent of the process exit status, and use `command.ExitStatus`/well-defined git exit codes to confirm the failure is exactly the "some refs rejected" case (git-fetch documents exit code 1 for this), rather than matching on the literal string `"exit status 1"` and empty stderr, which does not reliably distinguish this case from other failure modes.

### Proof of Concept
Not directly demonstrable without a controllable git-fetch failure injection; the logic itself is visible at [1](#0-0) , showing the flow proceeds past the error unless `stderr` is non-empty or the error string differs from `"exit status 1"`.
