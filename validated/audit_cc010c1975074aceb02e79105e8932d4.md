### Title
Attacker fills victim's per-account token list with dust deposits/transfers, DoS-ing their deposits and borrows via `UserReachedMaxTokens` - ([File: contracts/Pool.sol])

### Summary
CVE-2018-18398 is a "pre-seeded shared state" bug: an unprivileged local user plants files in `/tmp` before the victim runs an operation, causing the victim's code path to crash. The on-chain analog is the per-account token lists `depositTokensOfAccount` / `debtTokensOfAccount` in `Pool.sol`. Because `DepositToken.deposit(amount_, onBehalfOf_)` and `DepositToken.transfer` add the token to the *recipient's* list (not the caller's), an attacker can pre-fill a victim's list up to `MAX_TOKENS_PER_USER = 30` with dust, causing every subsequent deposit, mint/issue, or leverage action for the victim that introduces a new token to revert with `UserReachedMaxTokens`.

### Finding Description
`Pool.sol` enforces a hard cap:

```solidity
modifier onlyIfAdditionWillNotReachMaxTokens(address account_) {
    if (debtTokensOfAccount.length(account_) + depositTokensOfAccount.length(account_) >= MAX_TOKENS_PER_USER) {
        revert UserReachedMaxTokens();
    }
    _;
}
``` [1](#0-0) [2](#0-1) 

Both `addToDebtTokensOfAccount` and `addToDepositTokensOfAccount` are gated by this modifier and are invoked from the token contracts whenever an account's balance transitions from zero — i.e., on behalf of the *beneficiary*, not the caller. [3](#0-2) 

`DepositToken.deposit` takes an arbitrary `onBehalfOf_` and mints the deposit token to that account, and `transfer` moves the token (and hence a list entry) to any `to_`: [4](#0-3) [5](#0-4) 

Attack steps (all unprivileged, standard calls):

1. Attacker calls `depositToken_i.deposit(1 wei, victim)` (or transfers 1 wei) for each of the pool's deposit tokens, until `depositTokensOfAccount[victim].length + debtTokensOfAccount[victim].length == 30`. Cost is a handful of dust units of each underlying plus gas; since `depositTokens` is itself capped at 30 ( [6](#0-5) ), at most 30 calls are needed.
2. When the victim later calls `deposit` on a collateral they haven't used, `_mint` → `addToDepositTokensOfAccount(victim)` reverts with `UserReachedMaxTokens`. Same for `DebtToken.issue`/`mint` (which call `addToDebtTokensOfAccount` via `_mint`, [7](#0-6) ) and for `SmartFarmingManager.leverage` flows that mint a new debt token to the victim.
3. The attacker can front-run the victim's cleanup (the victim must transfer/withdraw each dust token to zero to remove an entry) and re-add entries, keeping the griefing persistent.

No modifier stops this: `deposit` is `whenNotPaused nonReentrant` only and `onBehalfOf_` is attacker-chosen; the list-add path has no opt-in or minimum-amount check.

### Impact Explanation
Temporary freezing of funds / liveness break on a per-victim basis: the victim cannot open positions with any new collateral or debt token while the list is full. More critically, if the attack is applied to an account mid-flow (e.g., against a SmartFarmingManager user or a leveraged position needing an additional debt token), `issue`/`mint` reverts, which can prevent refinancing/repaying-with-new-debt paths during price volatility. Liquidation `seize` → `_transfer` also adds the seized deposit token to the liquidator's list; an attacker-liquidator interaction is self-inflicted, but a griefer can fill a known liquidation bot's account to delay liquidations of unhealthy positions, contributing to bad-debt risk. The victim can recover by zeroing dust balances (transfer out or withdraw), so impact is temporary freeze plus gas griefing rather than permanent loss — consistent with a Medium-severity analog.

### Likelihood Explanation
Fully permissionless: only requires dust amounts of listed underlyings and standard `deposit`/`transfer` calls — no privileged role, no oracle manipulation, no fake contracts. The limiting factors are that the attacker must spend gas on up to ~30 transactions per victim and the victim can self-recover, so it's a targeted griefing vector rather than a mass attack — matching the CVE's local, per-victim pre-seeding profile.

### Recommendation
- Add a minimum meaningful amount (e.g., USD-denominated dust floor via the oracle) before registering a token in `depositTokensOfAccount`/`debtTokensOfAccount`, or
- Make list membership opt-in (only add on `deposit`/`issue` initiated by the beneficiary via `SynthContext._msgSender`, not on inbound `transfer`/`seize`), or
- Remove the hard cap and bound `debtOf`/`depositOf` iteration differently, or
- Add a `sweep`/forced-removal path so a user can evict entries cheaply in a single tx.

### Proof of Concept
Hardhat test sketch (adapt `test/Pool.test.ts` max-tokens cases at lines 1386–1416 and 1491–1521):

```typescript
it('griefer fills victim token list via dust deposits', async () => {
  // given: pool with N deposit tokens deployed
  const victim = bob.address;
  for (const dt of depositTokens) {
    await underlying.connect(alice).mint(alice.address, 10);
    await underlying.connect(alice).approve(dt.address, 10);
    // attacker deposits dust directly to victim's list
    await dt.connect(alice).deposit(1, victim);
  }
  // fill remainder with debt tokens via issue by an attacker helper account if needed
  expect(await pool.getDepositTokensOfAccount(victim)).to.have.length(30);

  // when: victim tries to deposit a new collateral / issue new debt
  await expect(
    newDepositToken.connect(bob).deposit(parseEther('1'), victim)
  ).to.revertedWithCustomError(pool, 'UserReachedMaxTokens');
});
```

Caveat: I verified the revert path (`addToDepositTokensOfAccount` under `onlyIfAdditionWillNotReachMaxTokens`) and the attacker-reachable entry points (`deposit(onBehalfOf_)`, `transfer`), but I could not fully confirm whether this is a previously-disclosed/known issue in Metronome audits; if it is already documented, the validator rules would exclude it.
