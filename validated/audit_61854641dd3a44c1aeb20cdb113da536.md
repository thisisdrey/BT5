### Title
Un-liquidatable dust debt: `debtFloorInUsd` and `maxLiquidable` checks combine to permanently block liquidation of small positions - (File: contracts/Pool.sol)

### Summary
`Pool.liquidate` enforces two bounds on `amountToRepay_`: (1) it cannot exceed `maxLiquidable` (default 50%) of the account's total debt balance, and (2) the post-liquidation remaining debt must be either zero or `>= debtFloorInUsd`. For any account whose debt is below `2 * debtFloorInUsd / (1 - maxLiquidable-ish)` these bounds are mutually exclusive: repaying 100% violates `maxLiquidable`, and every allowed partial repayment leaves a remainder `> 0` and `< debtFloorInUsd`. Such positions can never be liquidated, freezing the backing collateral and embedding permanent bad debt.

### Finding Description
In `Pool.liquidate`:

```solidity
// contracts/Pool.sol:567-579
if (amountToRepay_.wadDiv(_debtTokenBalance) > maxLiquidable) {
    revert AmountGreaterThanMaxLiquidable();
}

if (debtFloorInUsd > 0) {
    uint256 _newDebtInUsd = masterOracle().quoteTokenToUsd(
        address(syntheticToken_),
        _debtTokenBalance - amountToRepay_
    );
    if (_newDebtInUsd > 0 && _newDebtInUsd < debtFloorInUsd) {
        revert RemainingDebtIsLowerThanTheFloor();
    }
}
```

With `maxLiquidable = 0.5e18` (set in `initialize`, Pool.sol:181) and a nonzero `debtFloorInUsd`, take an account with synthetic debt of USD value `D` where `D <= 2 * debtFloorInUsd` (approx, for same-price synth):

- Full repayment `amountToRepay_ = D` gives `wadDiv = 1e18 > 0.5e18` → reverts `AmountGreaterThanMaxLiquidable`.
- Any partial repayment `x` leaves `D - x`. Since `x <= D/2`, remainder `>= D/2`; and any `x > D - debtFloorInUsd` leaves `0 < remainder < debtFloorInUsd` → reverts `RemainingDebtIsLowerThanTheFloor`. Once `D <= 2 * floor`, the interval `(D - floor, D/2]` covers all repayments that could approach zero while remaining valid, and when `D <= floor` every nonzero repayment that stays within `maxLiquidable` either reverts or leaves sub-floor dust.

Concretely: floor = $100, `maxLiquidable = 50%`, account debt = $150. Repaying ≤$50 leaves remainder ≥$100 (allowed), repaying $50–$75 leaves $75–$100 < floor or equal boundary, and repaying all $150 exceeds `maxLiquidable`. After one valid $50 liquidation the debt sits at $100: every repayment `x ∈ (0, 50]` leaves `0 < 100 - x < 100` → always reverts; `x = 100` reverts on `maxLiquidable`. The position is permanently un-liquidatable.

### Impact Explanation
An account in this state cannot be liquidated at all. If its collateral value drops below its debt, the pool accrues permanent bad debt that no liquidator can clear — `liquidate` always reverts. Additionally, the position's collateral remains locked (`unlockedBalanceOf` returns ~0 while debt exists), so the collateral backing the stuck debt is frozen in the pool indefinitely unless the borrower voluntarily repays in full via `DebtToken.repay` (which is not subject to `maxLiquidable`/floor checks). A borrower who abandons the position leaves the protocol holding the loss.

### Likelihood Explanation
The trigger requires `debtFloorInUsd > 0`, which is a deployed-configuration choice — the floor mechanism exists precisely for this (`updateDebtFloor`, tested in `test/Pool.test.ts:408-436`). Positions enter the dead zone naturally: interest accrual, normal `repay` calls, and prior liquidations each push debt downward; the last liquidation step that lands debt in `(floor, 2*floor]` makes the next one impossible. An attacker can also deliberately manufacture the state cheaply at the margin — e.g., partially repaying a victim's debt (if `repay` accepts an arbitrary `account_` parameter, burning the attacker's synth) to push it just into the band, or keeping many small positions alive so they decay into the gap. Cost to the attacker is bounded by the size of the dust band rather than the full debt.

Modifiers do not stop this: `liquidate` is `whenNotShutdown`/`nonReentrant` only; the reverts are unconditional math on `amountToRepay_`, `_debtTokenBalance`, `maxLiquidable`, and `debtFloorInUsd`.

### Recommendation
When the remaining debt after a `maxLiquidable`-bounded repayment would land in `(0, debtFloorInUsd)`, either:
- allow full liquidation in that case (waive `maxLiquidable` when `quoteTokenToUsd(_debtTokenBalance) < debtFloorInUsd` or when `maxLiquidable * debt` would leave sub-floor dust), or
- clamp `amountToRepay_` to clear the remainder, treating "repay-to-zero" as always permitted for underwater/dust positions.

### Proof of Concept
Hardhat sketch (mirroring `test/Pool.test.ts` debt-floor block):

```ts
// given: pool.updateDebtFloor(parseEther('100')) // $100 floor
//        alice has ~$150 msETH debt, collateral dropped -> unhealthy
await pool.updateDebtFloor(parseEther('100'))
const debt = await msEthDebtToken.balanceOf(alice.address) // ~$150

// step 1: valid partial liquidation ($50 repaid, remainder $100 == floor)
await pool.connect(liquidator).liquidate(msEth.address, alice.address, repay50usd, msdMET.address)

// step 2: debt is now $100 — every repayment reverts
const dust = await msEthDebtToken.balanceOf(alice.address)
await expect(
  pool.connect(liquidator).liquidate(msEth.address, alice.address, dust, msdMET.address)
).to.be.revertedWithCustomError(pool, 'AmountGreaterThanMaxLiquidable')
await expect(
  pool.connect(liquidator).liquidate(msEth.address, alice.address, dust.div(2), msdMET.address)
).to.be.revertedWithCustomError(pool, 'RemainingDebtIsLowerThanTheFloor')
// Position is permanently un-liquidatable; collateral stays locked.
```

Caveats not fully verified within the index: whether `DebtToken.repay` permits paying down an arbitrary `account_` (affects only the attacker-manufacture vector, not the organic one), and whether production `debtFloorInUsd` is nonzero on the deployed pools — the finding is conditional on that configuration flag being enabled.
