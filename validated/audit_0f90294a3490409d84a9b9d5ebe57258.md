## Title
Unconditional relayer-fee payment before target validation completes in the ETH-implicit Wallet Contract allows fee draining via nonce-frozen replay - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The NEP-518 Wallet Contract (the contract deployed on ETH-implicit accounts to emulate Ethereum transactions, see `docs/DataStructures/Account.md:124-136`) pays the "relayer fee" attached to an emulated base-token transfer *before* it has confirmed that the transfer's target validation will actually succeed. When that validation later fails, the wallet's nonce is deliberately left unchanged so an honest relayer can retry — but this also means any party can resubmit the exact same signed payload and collect the fee again, repeatedly, without the underlying action ever completing. This mirrors the D3Vault bug class: a token/fund transfer (`promise_batch_action_transfer` for the fee) is executed unconditionally, decoupled from whether the paired operation (the actual transfer/`ft_transfer`) succeeds, so it can result in "the debt being repaid... but the collateral not transferred"-style fund loss.

### Finding Description
In `inner_rlp_execute` (`runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs:330-410`), after a transaction is parsed successfully: [1](#0-0) 

- Nonce advancement is **skipped** specifically for `TransactionKind::EthEmulation(EthEmulationKind::EOABaseTokenTransfer { address_check: Some(_), .. })` — this is the case where the "to" address of the Ethereum-style transaction is interpreted as another ETH-implicit account (`TargetKind::EthImplicit`) and must be verified against the address registrar before it is known whether the intended action is valid (`runtime/near-wallet-contract/implementation/wallet-contract/src/internal.rs:107-122`).
- Regardless of that deferred nonce state, the relayer fee is transferred immediately and unconditionally to `context.predecessor_account_id` (i.e., whoever is the current caller of `rlp_execute`) via `env::promise_batch_action_transfer`, *before* the address-registrar lookup / `address_check_callback` has resolved: [2](#0-1) 

The actual disposition is only decided later in `address_check_callback` (`runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs:134-192`). If the registrar shows the target *is* a real named account (meaning the relayer mis-targeted the raw hex address instead of the resolved account), the transaction is rejected as a "faulty relayer" error and, critically, **the nonce is only incremented / the relayer only banned when `env::signer_account_id() == current_account_id`** (i.e., only when the caller used the wallet's own access key): [3](#0-2) 

When `rlp_execute` is instead invoked directly by an ordinary external NEAR account (no access key of the wallet), `env::signer_account_id() != current_account_id`, so no banning occurs and the nonce is never consumed for this failure path. Because the ETH-side `tx_bytes_b64` payload plus `target` are just plain call arguments to a public payable method, and since a submitted transaction (and its calldata) is publicly observable on-chain, **any account** can resubmit the identical `tx_bytes_b64`/`target` pair to `rlp_execute` as many times as desired. Each resubmission repeats the same sequence: fee paid immediately to the caller, registrar lookup performed, target confirmed to be a registered/mismatched account, request rejected — with the wallet's nonce never advancing and no penalty imposed on the (non-access-key) caller.

### Impact Explanation
An attacker who observes any signed ETH-implicit-account transaction with a nonzero fee that lands in this `address_check: Some` / relayer-fault path can repeatedly call `rlp_execute` with the same arguments, each time collecting `fee` yoctoNEAR from the wallet's own account balance while performing no useful work, until the wallet's NEAR balance is exhausted (subject only to the attacker's own gas cost per call, which is far less than a reasonably-set relayer fee). This is a direct, repeatable theft of user (wallet owner) funds — concrete loss of funds from an ordinary user's account, reachable without any privileged role, matching the required "eth-implicit wallet contract" and "meta-transactions" scope.

### Likelihood Explanation
Exploitation requires only: (1) a wallet owner ever signs one such transaction with `fee > 0` whose target is misresolved to the raw hex ETH-implicit form of an already-registered account (a state a relayer, or the wallet owner using an unaware/buggy relayer client, can trigger unintentionally, or an attacker can induce by choosing to relay-but-mistarget on the user's behalf), and (2) the attacker submits the call without using the wallet's access key. No cryptographic forgery is needed — the attacker only replays already-signed, publicly-visible bytes. This makes the attack straightforward to execute once a qualifying transaction exists, and it can be repeated indefinitely against the same wallet balance.

### Recommendation
Do not pay the relayer/caller fee until the target/action validation has definitively succeeded. Move the `promise_batch_action_transfer` fee payment into the success branch (e.g., only after `address_check_callback` confirms the target is unregistered and the transfer is scheduled, or fold it into `rlp_execute_callback` conditioned on `PromiseResult::Successful`), and/or ensure the nonce is always consumed (or the caller otherwise penalized/rate-limited) whenever a fee has already been paid out, regardless of whether the caller used an access key.

### Proof of Concept
1. Wallet owner signs (or a naive relayer produces) an Ethereum-style transaction whose `data` matches an ERC-20 selector and whose `to` field, decoded as a hex address, corresponds to `target` = some ETH-implicit-style account ID that is *also* a real registered named account in the address registrar; `max_fee_per_gas * gas_limit` is set to a nonzero relayer fee.
2. This transaction is submitted once (e.g., by a relayer) to `rlp_execute(target, tx_bytes_b64)` on the wallet contract, `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs:89-128`; parsing succeeds, `TransactionKind::EthEmulation(EOABaseTokenTransfer{address_check: Some(_), fee})` is chosen, nonce increment is skipped, and the fee is immediately transferred to the caller.
3. `address_check_callback` runs, finds the registrar returns `Some(account_id)` for the target, and since the caller was not using the wallet's own access key, simply returns a failure `ExecuteResponse` — no ban, no nonce change.
4. Attacker observes the (now on-chain, publicly visible) `tx_bytes_b64`/`target` pair and calls `rlp_execute` again with identical arguments from their own account. Steps 2–3 repeat identically, and the attacker collects `fee` again.
5. Repeat step 4 until the wallet's balance is drained of the accumulated fee payments.
