Confirmed: `intValueSafe()` clamps int overflow to `Integer.MAX_VALUE` [1](#0-0) , so `extractBytesArray`/`extractSigArray`/`extractBytes32Array` can receive `len = Integer.MAX_VALUE` directly from attacker-controlled calldata words.

### Title
Unvalidated array-length field from TVM precompile calldata causes huge allocation / DoS - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
`ValidateMultiSign` and `BatchValidateSign` precompiled contracts (addresses `0x9` and `0xa`) parse a length word directly from attacker-supplied calldata and use it, unbounded, to allocate a `byte[len][]` array before any sanity check against the actual size of the data buffer — the same bug class as pypdf trusting an oversized `/Size` or `/N` field before validating it against the real object stream size.

### Finding Description
`extractBytesArray` and `extractSigArray` read a length word from calldata via `words[offset].intValueSafe()` and immediately allocate `new byte[len][]` and loop `for (int i = 0; i < len; i++)` before validating that `len` actually corresponds to available data [2](#0-1) . `extractBytes32Array` has the identical pattern, allocating `new byte[len][]` from an unchecked `intValueSafe()` value [3](#0-2) .

`intValueSafe()` returns `Integer.MAX_VALUE` whenever the underlying 256-bit word doesn't fit cleanly into a 4-byte non-negative int [1](#0-0) , so a crafted calldata word (e.g. `0xffffffff...`) is coerced to `2^31-1` rather than being rejected — this mirrors the pypdf flaw of accepting an implausibly large `/Size`/`/N` value without bounds-checking it against the real container size before use.

These functions are invoked from `ValidateMultiSign.execute` and `BatchValidateSign.execute`, both reachable via a plain `CALL`/`STATICCALL` from any smart contract in a normal transaction [4](#0-3) [5](#0-4) .

Mitigating factor: post-TIP-854, `allowTvmOsaka()` gates both `execute()` entry points with `isValidAbiEncoding(data, ABI_HEADER_WORDS, ABI_ITEM_WORDS)`, which checks `data.length` is a multiple of the item/word size before any `intValueSafe()`-derived length is used for allocation [6](#0-5) [7](#0-6) [8](#0-7) . When `allowTvmSelfdestructRestriction()` is also active, an additional `sigArraySize > MAX_SIZE` pre-check bounds `len` to 5 or 16 before the array-length is used for allocation [9](#0-8) [10](#0-9) . I could not determine from the index whether `allowTvmOsaka` and `allowTvmSelfdestructRestriction` are both already activated on current mainnet — this depends on `ForkController`/`VMConfig` proposal activation state, which is outside the scope of what I could verify.

### Impact Explanation
If reached with either hard-fork flag not yet activated (or on private/sidechain networks that haven't activated these TIPs), `new byte[Integer.MAX_VALUE][]` on the `len` branch throws `OutOfMemoryError` inside precompile execution. `BatchValidateSign.execute` wraps its body in `try { return doExecute(data); } catch (Throwable t) {...}` [11](#0-10) , so `OutOfMemoryError` (a `Throwable`, not `Exception`) is caught, but the JVM heap pressure caused by the massive attempted allocation before the exception is thrown can still degrade or crash the node process depending on heap configuration — this is a resource-exhaustion / node-availability concern rather than a fund-theft or corruption one, so severity should be scoped as Medium at most, contingent on activation state.

### Likelihood Explanation
Low-to-Medium: the vulnerable path is reachable by any account via a simple contract call to precompile address `0x9` or `0xa`, but it is only exploitable when the newer TIP-854 (`allowTvmOsaka`) length-validation guard is inactive, since that guard bounds `len` implicitly by requiring `data.length` to match a computed word count. On networks/forks where this guard is already active (which appears to be the intended, hardened state given the extensive `Tip854` test coverage found [12](#0-11) ), this analog is not exploitable.

### Recommendation
Bound `len` in `extractBytes32Array`, `extractBytesArray`, and `extractSigArray` against the actual remaining `words.length`/`data.length` before allocating, independent of the `allowTvmOsaka`/`allowTvmSelfdestructRestriction` fork flags, so the fix is unconditional rather than fork-gated.

### Proof of Concept
Not constructed — exploitability depends on runtime fork-activation state (`allowTvmOsaka`, `allowTvmSelfdestructRestriction`) that could not be confirmed from the indexed code alone; a background Devin session with access to `ForkController`/current chain parameters would be needed to confirm whether the guarded path is actually reachable on a live deployment.

   * In case of int overflow returns Integer.MAX_VALUE otherwise works as #intValue()
   */
  public int intValueSafe() {
    int bytesOccupied = bytesOccupied();
    int intValue = intValue();
    if (bytesOccupied > 4 || intValue < 0) {
      return Integer.MAX_VALUE;
    }
    return intValue;
  }

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }

  // TIP-854: after activation, batchValidateSign (H=5, I=6) must reject calldata
  // whose byte length is incompatible with the (words - 5) / 6 shape the per-call
  // energy formula already assumes, returning (false, empty). The guard lives in
  // doExecute(); the outer try/catch does not mask it because the guard does not
  // throw (pure arithmetic + a static getter).
  @Test
  public void testTip854RejectsMalformedCalldata() {
    contract.setVmShouldEndInUs(System.nanoTime() / 1000 + 2_000_000);
    VMConfig.initAllowTvmOsaka(1);
    try {
      // Bucket 1: 32-aligned head + sub-word trailing bytes (r=1, r=31).
      for (int r : new int[]{1, 31}) {
        byte[] data = new byte[(5 + 6) * 32 + r];
        Pair<Boolean, byte[]> ret = contract.execute(data);
        Assert.assertFalse("non-32-aligned len=" + data.length, ret.getLeft());
        Assert.assertSame(ByteUtil.EMPTY_BYTE_ARRAY, ret.getRight());
      }
      // Bucket 2: fewer than the static head's 5 words.
      for (int bytes : new int[]{0, 32, 64, 96, 128}) {
        Pair<Boolean, byte[]> ret = contract.execute(new byte[bytes]);
        Assert.assertFalse("len=" + bytes + " < 5 words", ret.getLeft());
        Assert.assertSame(ByteUtil.EMPTY_BYTE_ARRAY, ret.getRight());
      }
      // Bucket 3: 32-aligned but tail not a multiple of I=6 words (k = 1..5).
      for (int k = 1; k <= 5; k++) {
        byte[] data = new byte[(5 + k) * 32];
        Pair<Boolean, byte[]> ret = contract.execute(data);
        Assert.assertFalse("aligned bad-tail k=" + k, ret.getLeft());
        Assert.assertSame(ByteUtil.EMPTY_BYTE_ARRAY, ret.getRight());
      }
      // Null calldata: explicit spec clause.
      Pair<Boolean, byte[]> ret = contract.execute(null);
      Assert.assertFalse("null calldata", ret.getLeft());
      Assert.assertSame(ByteUtil.EMPTY_BYTE_ARRAY, ret.getRight());
    } finally {
      VMConfig.initAllowTvmOsaka(0);
    }
    System.gc();
  }
