### Title
Full-batch refund on oversized `mt_batch_transfer_call` result causes double credit - ([File: contracts/defuse/src/contract/tokens/nep245/withdraw.rs])

### Summary
`mt_resolve_withdraw` treats any `Err(_)` from `promise_result_checked_json_with_len::<Vec<U128>>(0, amounts.len())` as a "gas-starved, assume nothing happened" case and refunds the *entire* batch to `sender_id` via `self.deposit`. A malicious `token` contract that legitimately delivers `token_ids`/`amounts` to `receiver_id` via `mt_batch_transfer_call`, but returns a syntactically valid `Vec<U128>` JSON payload padded past `Vec::<U128>::max_json_length_root(amounts.len())`, forces `env::promise_result_checked` (called inside `promise_result_checked_json_with_len`) to fail the length check and return `Err`, hitting the `Err(_) => amounts.clone()` branch even though the transfer actually succeeded.

### Finding Description
The broken binding: `amount_debited_from_sender == amount_delivered_to_receiver_id + amount_recredited_by_mt_resolve_withdraw`.

Path: [1](#0-0) 

- `mt_withdraw`/`internal_mt_withdraw` debits `sender_id`'s internal balance for `(token, token_ids)` by `amounts`, then schedules `do_mt_withdraw` → `mt_batch_transfer_call(receiver_id, token_ids, amounts, ...)` on the attacker-supplied `token` contract, followed by `mt_resolve_withdraw` as callback. [2](#0-1) 
- `mt_resolve_withdraw` reads the promise result with a length cap sized only from `amounts.len()`: `promise_result_checked_json_with_len::<Vec<U128>>(0, amounts.len())`. If reading fails (`Err(_)`), it assumes the transfer didn't happen and sets `used = amounts.clone()` (i.e., refund everything), mirroring the documented NEP-141 gas-starvation workaround in `ft_resolve_withdraw`. [3](#0-2) 
- The length cap `Vec::<U128>::max_json_length_root((length, ()))` is computed assuming a tightly/pretty-printed, honestly-sized response; it does not bound what an adversarial contract can actually return. [4](#0-3) 
- Since the attacker fully controls the `token` contract's `mt_batch_transfer_call` implementation, they can (a) genuinely transfer the tokens to `receiver_id`, and (b) return an oversized-but-valid JSON body (e.g., extra whitespace/padding fields) that exceeds the computed `max_len`, causing `env::promise_result_checked` to return `Err` for reasons unrelated to gas starvation. This drives execution into `Err(_) => amounts.clone()`, and `self.deposit(sender_id, ...)` re-credits the *full* batch back to `sender_id`. [5](#0-4) 

Existing guards do not prevent this: `#[private]` only restricts the callback to be self-invoked (which it is, as part of the promise chain), and there is no check reconciling "was the result truly unreadable due to gas" vs. "was the result truly too large due to attacker padding." Both collapse into the same `Err(_)` branch.

### Impact Explanation
For the specific `(token, token_id)` the attacker controls (their own deployed MT contract), this creates a Defuse-internal ledger balance in excess of what was actually removed from custody: `receiver_id` holds the externally delivered multi-tokens on the attacker's contract, while `sender_id`'s Defuse-internal balance for the same units is simultaneously restored in full. This violates the invariant that debited amount == delivered + recredited, i.e. "a batch whose balance changes do not net to zero so the Verifier owes more than it custodies" for that token. The double-minted internal balance can subsequently be used in intents (swaps) to extract real assets from counterparties who treat the Defuse-tracked balance as legitimate, extending the blast radius beyond the attacker's own sandboxed token. Repeatable per batch, per attacker-controlled token contract, at will.

### Likelihood Explanation
The attacker needs only to deploy their own MT contract as the `token` for `mt_withdraw`/an equivalent intent, and hold a Defuse-internal balance for that (token, token_id) pair (which they themselves fully control the deposit side of). No privileged role, relayer key, or DAO action is required — this is reachable purely from `mt_withdraw`/`mt_force_withdraw`-adjacent flows via `execute_intents` with a self-authorized withdraw for a self-deployed token, and crafting the oversized JSON response is a straightforward contract implementation detail, not requiring any exotic runtime condition.

### Recommendation
Do not conflate "unreadable due to length cap" with "assume the call never executed." Either: (1) size `max_json_length_root` to be an actual hard protocol-level bound and treat any oversized response as a genuine, verifiable no-op/failure by rejecting the whole cross-contract call pattern (e.g., require callee registration/allowlisting or bound `amounts.len()` such that padding cannot plausibly exceed the cap while remaining within reasonable per-item JSON size), or (2) separate the "insufficient gas to read result" case (which can be distinguished via `FunctionCallError`/gas usage telemetry, not solely by comparing payload length) from a "response too large" case, and treat the latter as `used = vec![U128(0); amounts.len()]` (no refund, since the call executed and its result is simply untrusted/unparseable) rather than a full refund.

#[near]
impl MultiTokenWithdrawResolver for Contract {
    #[private]
    fn mt_resolve_withdraw(
        &mut self,
        token: AccountId,
        sender_id: AccountId,
        token_ids: Vec<defuse_nep245::TokenId>,
        amounts: Vec<U128>,
        is_call: bool,
    ) -> Vec<U128> {
        require!(
            token_ids.len() == amounts.len() && !amounts.is_empty(),
            "invalid args"
        );

        let mut used = if is_call {
            // `mt_batch_transfer_call` returns successfully transferred amounts
            match promise_result_checked_json_with_len::<Vec<U128>>(0, amounts.len()) {
                Ok(Ok(used)) if used.len() == amounts.len() => used,
                Ok(_) => vec![U128(0); amounts.len()],
                // do not refund on failed `mt_batch_transfer_call` due to
                // NEP-141 vulnerability: `mt_resolve_transfer` fails to
                // read result of `mt_on_transfer` due to insufficient gas
                Err(_) => amounts.clone(),
            }
        } else {
            // `mt_batch_transfer` returns empty result on success
            if promise_result_checked_void(0).is_ok() {
                amounts.clone()
            } else {
                vec![U128(0); amounts.len()]
            }
        };

        self.deposit(
            sender_id,
            token_ids
                .into_iter()
                .zip(amounts)
                .zip(&mut used)
                .filter_map(|((token_id, amount), used)| {
                    // update min during iteration
                    used.0 = used.0.min(amount.0);
                    let refund = amount.0.saturating_sub(used.0);
                    if refund > 0 {
                        Some((Nep245TokenId::new(token.clone(), token_id).into(), refund))
                    } else {
                        None
                    }
                }),
            Some(REFUND_MEMO),
        )
        .unwrap_or_else(|err| err.panic());

        used
    }

impl<T> MaxJsonLength for Vec<T>
where
    T: MaxJsonLength,
{
    type Args = (usize, T::Args);

    fn max_json_length_at(depth: usize, (length, item_args): (usize, T::Args)) -> usize {
        const INDENT_STEP: usize = "        ".len();

        if depth >= MAX_JSON_LENGTH_RECURSION_LIMIT {
            return usize::MAX;
        }

        let ident = INDENT_STEP.saturating_mul(depth);
        let item_indent = ident.saturating_add(INDENT_STEP);

        item_indent
            .saturating_add(T::max_json_length_at(depth + 1, item_args))
            .saturating_add(",\n".len())
            .saturating_mul(length)
            .saturating_add(" [\n] ".len() + ident)
    }
}
