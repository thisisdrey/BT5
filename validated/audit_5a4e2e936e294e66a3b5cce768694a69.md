Audit Report

## Title
Relayer reward paid regardless of delivery outcome in Snowbridge outbound-queue-v2 `process_delivery_receipt` - (File: `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs`)

## Summary
`process_delivery_receipt` pays the full relayer reward for a `PendingOrder` whenever `order.fee > 0`, without ever inspecting the `success` field of the decoded `DeliveryReceipt`, even though that field is explicitly present in the receipt and carries the on-Ethereum dispatch outcome. This means a relayer submitting proof of a failed remote dispatch is rewarded identically to one submitting proof of a successful dispatch.

## Finding Description
`submit_delivery_receipt` verifies the event log/proof via `T::Verifier::verify`, decodes it into a `DeliveryReceipt` via `TryFrom<&Log>`, and forwards it to `process_delivery_receipt` without any success check: [1](#0-0) 

The `DeliveryReceipt` struct is decoded directly from the Ethereum `InboundMessageDispatched(nonce, topic, success, reward_address)` event log and explicitly carries a `success: bool` field that is populated from the event: [2](#0-1) 

`process_delivery_receipt` only checks `receipt.gateway` against `T::GatewayAddress`, looks up the `PendingOrder` by `receipt.nonce`, and pays `order.fee` to the reward account whenever `order.fee > 0`, then unconditionally removes the order and emits `MessageDelivered` — `receipt.success` is never read: [3](#0-2) 

The existing halted/unhalted test only exercises `set_verifier_halted` gating and asserts the order is settled and paid regardless of the `success` field encoded in the mock event data — it never varies `success` to `false` and never asserts `RewardRegistered`/no-payout behavior for a failed dispatch, confirming no guard exists for this path: [4](#0-3) 

## Impact Explanation
Any unprivileged relayer who submits a genuine proof for a message whose remote execution reverted on Ethereum (`success=false`) still receives the full `order.fee` reward via `T::RewardPayment::register_reward`, exactly as in the success case. This is an underpriced/unconditional payout for work that did not achieve its intended effect, matching the "public underpriced work that degrades... stalls bridge processing" and "duplicate settlement or payout" impact classes, since settlement (removal of `PendingOrders` + reward registration) advances purely from proof-of-log-existence and never branches on the encoded outcome carried in that same log.

## Likelihood Explanation
The path is reachable by any `ensure_signed` caller calling the public extrinsic `submit_delivery_receipt`, requiring only a legitimate Merkle/event proof of an `InboundMessageDispatched` event with `success=false` — a normal, expected occurrence when a bridged command (e.g., a nested `Transact` or token operation) fails to execute on Ethereum. No malicious peer, validator, governance action, or leaked key is needed.

## Recommendation
In `process_delivery_receipt`, branch on `receipt.success` before calling `T::RewardPayment::register_reward`: only pay the full fee when `success == true`; define and implement the intended failure-handling policy (e.g., no reward, reduced reward, or refund path) for `success == false`. Add a unit test asserting a `DeliveryReceipt`/mock event log encoding `success: false` results in the `PendingOrder` being resolved without a reward payout.

## Proof of Concept
1. `do_process_message` inserts a `PendingOrder { nonce, fee, .. }` with `fee > 0` as shown at [5](#0-4) .
2. The message dispatch fails on Ethereum, and the Gateway emits `InboundMessageDispatched(nonce, topic, success=false, reward_address)`.
3. A relayer calls `submit_delivery_receipt(origin, event)` with a genuine proof of this log; `T::Verifier::verify` succeeds and `DeliveryReceipt::try_from` decodes `success: false` correctly per [6](#0-5) .
4. `process_delivery_receipt` runs, never inspects `receipt.success`, and pays `order.fee` to the reward account regardless, per [7](#0-6) .
5. This can be verified by extending `submit_delivery_receipt_succeeds_after_unhalt` in `bridges/snowbridge/pallets/outbound-queue-v2/src/test.rs` with a mock event log encoding `success: false` and asserting no `RewardRegistered`/reward-ledger call occurs — the current test suite lacks such a case.

sol! {
	event InboundMessageDispatched(uint64 indexed nonce, bytes32 topic, bool success, bytes32 reward_address);
}

/// Delivery receipt
#[derive(Clone, Debug)]
pub struct DeliveryReceipt {
	/// The address of the outbound queue on Ethereum that emitted this message as an event log
	pub gateway: H160,
	/// The nonce of the dispatched message
	pub nonce: u64,
	/// Message topic
	pub topic: H256,
	/// Delivery status
	pub success: bool,
	/// The reward address
	pub reward_address: [u8; 32],
}

#[derive(Copy, Clone, Encode, Decode, Eq, PartialEq, Debug, TypeInfo)]
pub enum DeliveryReceiptDecodeError {
	DecodeLogFailed,
	DecodeAccountFailed,
}

impl TryFrom<&Log> for DeliveryReceipt {
	type Error = DeliveryReceiptDecodeError;

	fn try_from(log: &Log) -> Result<Self, Self::Error> {
		let topics: Vec<B256> = log.topics.iter().map(|x| B256::from_slice(x.as_ref())).collect();

		let event = InboundMessageDispatched::decode_raw_log_validate(topics, &log.data)
			.map_err(|_| DeliveryReceiptDecodeError::DecodeLogFailed)?;

		Ok(Self {
			gateway: log.address,
			nonce: event.nonce,
			topic: H256::from_slice(event.topic.as_ref()),
			success: event.success,
			reward_address: event.reward_address.0,
		})
	}
