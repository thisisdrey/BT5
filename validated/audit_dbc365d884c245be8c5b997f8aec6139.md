Audit Report

## Title
Bridge relayer rewards are marked as paid on XCM send/delivery success, not on actual asset deposit — permanent reward loss without recourse - (File: `bridges/snowbridge/primitives/core/src/reward.rs`)

## Summary
`PayAccountOnLocation::pay_reward` [1](#0-0)  only validates that the XCM program is accepted and delivered to Asset Hub's outbound queue via `validate_send`, `charge_fees`, and `XcmSender::deliver`, but never checks whether the embedded `DepositAsset` instruction actually succeeded on Asset Hub. `pallet_bridge_relayers::do_claim_rewards` treats `pay_reward() == Ok(())` as final settlement and irreversibly removes `RelayerRewards` before the remote deposit outcome is known [2](#0-1) .

## Finding Description
The XCM built inside `pay_reward` descends origin, sets `UniversalOrigin(GlobalConsensus(Ethereum))`, does `ReserveAssetDeposited`, then `DepositAsset { assets: AllCounted(1).into(), beneficiary }`, and is sent unpaid to Asset Hub [3](#0-2) . Success is defined purely as "message accepted for delivery" — there is no receipt or callback that reports the result of the remote `DepositAsset` back to BridgeHub.

`do_claim_rewards` takes the reward balance out of `RelayerRewards` via `try_mutate_exists`, calls `pay_reward`, and only rolls back the storage mutation if `pay_reward` itself returns a synchronous `Err` (i.e., XCM validate/charge/deliver failure). On any other outcome it emits `RewardPaid` and finalizes the payout [4](#0-3) . This wiring is confirmed in BridgeHub Westend's runtime config, where `BridgeReward::Snowbridge` routes directly to `PayAccountOnLocation::pay_reward` [5](#0-4) .

The xcm-executor's own unit tests confirm that a failed `DepositAsset` (e.g., due to `BelowMinimum`/ED failure) aborts the instruction and traps the leftover holding via `post_process`/`AssetTrap`, rather than returning the assets to the original owner or notifying the sending chain [6](#0-5) . Because the crafted XCM uses `UniversalOrigin(GlobalConsensus(Ethereum))`, any trapped assets are keyed to the Ethereum universal origin rather than to the relayer, leaving no relayer-controlled recovery path.

## Impact Explanation
This matches the "permanent user-fund lock" and "payout state advances before settlement" impact patterns: a relayer's earned reward can be irrecoverably lost when the remote `DepositAsset` fails for mundane reasons (beneficiary below ED, frozen/nonexistent account, unsupported junction) while BridgeHub has already deleted the `RelayerRewards` entry and emitted `RewardPaid`.

## Likelihood Explanation
No privileged access, malicious relayer, or compromised keys are required — an ordinary relayer supplying an underfunded or otherwise invalid Asset Hub beneficiary location (a realistic, common condition for a fresh claim destination) triggers the loss deterministically through the sole reward-payment code path (`pay_reward` → `do_claim_rewards`).

## Recommendation
Do not treat local XCM delivery as final settlement for cross-chain reward payouts. Options include: requiring an explicit delivery/settlement receipt from Asset Hub before clearing `RelayerRewards`; keeping the claim "pending" with re-crediting on observed/reported deposit failure; or making the relayer (not `GlobalConsensus(Ethereum)`) the recorded trap owner so trapped funds are recoverable by the relayer.

## Proof of Concept
1. Accrue a reward for a relayer via `register_reward(relayer, BridgeReward::Snowbridge, amount)`.
2. Call `claim_rewards_to(origin, BridgeReward::Snowbridge, BridgeRewardBeneficiaries::AssetHubLocation(loc))` with `loc` resolving to a zero-balance Asset Hub account and `amount` below the relevant asset's minimum balance.
3. `do_claim_rewards` deletes the `RelayerRewards` entry and emits `RewardPaid` because `pay_reward` returns `Ok(())` (XCM validated and delivered) [7](#0-6) .
4. On Asset Hub, `DepositAsset` fails with `BelowMinimum`; per the xcm-executor test suite, assets are trapped under the `GlobalConsensus(Ethereum)` key rather than returned to the relayer [8](#0-7) .
5. The relayer's reward entry is gone (`NoRewardForRelayer` on re-claim attempt) and the trapped assets are unreachable by the relayer — permanent loss.

	fn pay_reward(
		relayer: &Relayer,
		_: (),
		reward: RewardBalance,
		beneficiary: Self::Beneficiary,
	) -> Result<(), Self::Error> {
		let ethereum_location = Location::new(2, [GlobalConsensus(EthereumNetwork::get())]);
		let assets: Asset = (ethereum_location.clone(), reward.into()).into();

		let xcm: Xcm<()> = alloc::vec![
			UnpaidExecution { weight_limit: Unlimited, check_origin: None },
			DescendOrigin(InboundQueueLocation::get().into()),
			UniversalOrigin(GlobalConsensus(EthereumNetwork::get())),
			ReserveAssetDeposited(assets.into()),
			DepositAsset { assets: AllCounted(1).into(), beneficiary },
		]
		.into();

		let (ticket, fee) =
			validate_send::<XcmSender>(AssetHubLocation::get(), xcm).map_err(|_| XcmSendFailure)?;
		XcmExecutor::charge_fees(relayer.clone(), fee).map_err(|_| ChargeFeesFailure)?;
		XcmSender::deliver(ticket).map_err(|_| XcmSendFailure)?;

		Ok(())
	}

			relayer: T::AccountId,
			reward_kind: T::Reward,
			beneficiary: BeneficiaryOf<T, I>,

			RelayerRewards::<T, I>::try_mutate_exists(

				reward_kind,

					let reward_balance =
						maybe_reward.take().ok_or(Error::<T, I>::NoRewardForRelayer)?;

							?beneficiary,

						relayer: relayer.clone(),
						reward_kind,
						reward_balance,
						beneficiary,
					});
