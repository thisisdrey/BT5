### Title
Reference-counter leak from asymmetric pre-receive/post-receive invocation in `UpdateReference` - (File: internal/gitaly/hook/updateref/update_with_hooks.go)

### Summary
`UpdaterWithHooks.UpdateReference` calls the GitLab-integration `PreReceiveHook`, which increments GitLab Rails' per-repository "active push" reference counter via `gitlabClient.PreReceive`, and is only supposed to be balanced by a later call to `PostReceiveHook`, which decrements the same counter via `gitlabClient.PostReceive`. Every failure path between a successful pre-receive and the final `PostReceiveHook` call returns immediately without invoking `PostReceiveHook`, permanently leaking the increment.

### Finding Description
`PreReceiveHook` executes `m.gitlabClient.PreReceive(ctx, repo.GetGlRepository())`, which the docs describe as incrementing "a reference counter that tracks how many pushes are active at the same time," used by GitLab to know when a repository "can be moved." [1](#0-0) [2](#0-1) 

The counter is only decremented in `postReceiveHook` via `m.gitlabClient.PostReceive`. [3](#0-2) 

In `UpdateReference` (used by most `OperationService` RPCs such as `UserCommitFiles`, `UserCreateTag`, `UserCherryPick`, `UserRevert`, `UserUpdateSubmodule`), `PostReceiveHook` is invoked only at the very end of the function, after `UpdateHook`, both `ReferenceTransactionHook` votes, `updater.Prepare()`, `updater.Commit()`, and the committed-state `ReferenceTransactionHook` all succeed: [4](#0-3) 

Every one of these intermediate steps returns early on error without ever calling `PostReceiveHook`:
- `UpdateHook` failure → returns without post-receive
- `ReferenceTransactionHook(Preparing)` failure → returns without post-receive
- `updater.Prepare()` failure (e.g. reference already locked by a concurrent RPC, as demonstrated in `TestUpdater_concurrentLocking`) → returns without post-receive
- `ReferenceTransactionHook(Prepared)` failure (e.g. Praefect vote/quorum failure) → returns without post-receive
- `updater.Commit()` failure → returns without post-receive
- `ReferenceTransactionHook(Committed)` failure → returns without post-receive

This asymmetry is directly exercised by the existing test suite, e.g. `TestUpdaterWithHooks_UpdateReference`'s "reference-transaction error" case shows `preReceive` succeeding while `postReceive` is never configured/called when `referenceTransaction` fails. [5](#0-4) 

Because the corresponding "decrement" callback (`PostReceiveHook`/`/internal/post_receive`) is never invoked on these failure paths, GitLab Rails' internal reference counter for the affected repository is permanently incremented and never brought back down.

### Impact Explanation
This is a structural analog of the reported "check happens, but the compensating step is skippable" callback bug: `PreReceiveHook`'s external call (`/internal/allowed`, `/internal/pre_receive`) mutates shared state in the *callback target* (GitLab Rails), and the balancing callback (`PostReceiveHook`/`/internal/post_receive`) is conditioned on every subsequent internal step succeeding rather than being guaranteed via `defer`/error-safe cleanup. Any ordinary authenticated user who triggers an `OperationService` write RPC (`UserCommitFiles`, `UserCreateTag`, `UserMergeBranch`, `UserCherryPick`, `UserRevert`, `UserUpdateSubmodule`, etc.) that is naturally rejected or aborted after passing the pre-receive access check — for example by racing a concurrent write to the same reference so that `updater.Prepare()` hits `AlreadyLockedError`, by triggering a `reference-transaction` vote failure, or by a custom `update` hook rejecting the change — leaves the "active push" counter permanently incremented for that repository. Repeated triggering by an unprivileged user causes the counter to grow without bound, which per the documented purpose ("If the reference counter is not at 0, there are active pushes happening") can indefinitely block GitLab-side operations that depend on the repository having zero in-flight pushes (e.g., repository/storage moves), i.e. a resource-exhaustion / DoS of a Rails-side administrative operation reachable purely through Gitaly RPC handling.

### Likelihood Explanation
The race is easy to trigger with ordinary means: two concurrent legitimate write RPCs (e.g. two simultaneous `UserCommitFiles` calls) to the same branch will reliably cause one of them to fail at `updater.Prepare()` with `AlreadyLockedError` after its `PreReceiveHook` has already succeeded and incremented the counter, as shown by `TestUpdater_concurrentLocking`. [6](#0-5) 
No elevated privileges, malicious peers, or leaked tokens are required — any two overlapping legitimate write requests from a normal user (or an intentional flood of concurrent writes) to the same reference reproduce the leak deterministically.

### Recommendation
Ensure the `PostReceive` decrement callback is invoked whenever the `PreReceive` increment succeeded, regardless of what happens afterward — for example by tracking whether `PreReceiveHook` succeeded and using a `defer` in `UpdateReference` to always call `PostReceiveHook` (or a lighter-weight decrement-only call) on any exit path once the increment has happened, rather than only on the final success path. Alternatively, move the counter increment/decrement bookkeeping so it is symmetric and exception-safe regardless of intermediate git-level failures (lock contention, hook rejection, vote failure).

### Proof of Concept
1. As an ordinary authenticated user with write access, issue two concurrent `UserCommitFiles` (or any other `OperationService` write RPC) requests targeting the same branch of the same repository.
2. Both requests pass `PreReceiveHook`, and via `gitlabClient.PreReceive`, GitLab Rails increments the repository's active-push reference counter twice.
3. One request proceeds to `updater.Prepare()` first and succeeds; the second hits `AlreadyLockedError` (as reproduced in `TestUpdater_concurrentLocking`) and `UpdateReference` returns immediately with `Error{... Cause: AlreadyLockedError}` without calling `PostReceiveHook`.
4. The losing request's counter increment is never balanced by a decrement; the counter is now permanently off by one for that repository.
5. Repeating this concurrently (e.g. a user scripting many colliding writes) drives the leaked counter arbitrarily high, which — per the documented semantics of the counter — will keep GitLab from treating the repository as having zero active pushes indefinitely.

func TestUpdater_concurrentLocking(t *testing.T) {
	t.Parallel()

	ctx := testhelper.Context(t)

	cfg := testcfg.Build(t)

	_, repoPath := gittest.CreateRepository(t, ctx, cfg, gittest.CreateRepositoryConfig{
		SkipCreationViaService: true,
	})
	repo := gittest.NewRepositoryPathExecutor(t, cfg, repoPath)
	commitID := gittest.WriteCommit(t, cfg, repoPath)

	for _, tc := range []struct {
		desc string
		lock func(*Updater) error
	}{
		{
			desc: "prepare",
			lock: func(u *Updater) error {
				return u.Prepare()
			},
		},
		{
			desc: "commit",
			lock: func(u *Updater) error {
				return u.Commit()
			},
		},
	} {
		t.Run(tc.desc, func(t *testing.T) {
			ref := git.ReferenceName("refs/heads/" + tc.desc)

			// Create the first updater that prepares the reference transaction so that the reference
			// we're about to update is locked.
			firstUpdater, err := New(ctx, repo)
			require.NoError(t, err)
			require.NoError(t, firstUpdater.Start())
			require.NoError(t, firstUpdater.Update(ref, commitID, ""))
			require.NoError(t, firstUpdater.Prepare())

			// Now we create a second updater that tries to update the same reference.
			secondUpdater, err := New(ctx, repo)
			require.NoError(t, err)
			require.NoError(t, secondUpdater.Start())
			require.NoError(t, secondUpdater.Update(ref, commitID, ""))

			if gittest.DefaultReferenceBackend == git.ReferenceBackendReftables {
				// Reftable locks are on an entire table instead of per reference, so
				// git doesn't output the name of the individual ref.
				require.Equal(t, AlreadyLockedError{}, tc.lock(secondUpdater))
			} else {
				// Try locking the reference via the second updater. This should fail now because the reference
				// is locked already.
				require.Equal(t, AlreadyLockedError{
					ReferenceName: string(ref),
				}, tc.lock(secondUpdater))
			}

			// Whereas committing the first transaction should succeed.
			require.NoError(t, firstUpdater.Commit())
		})
	}
