### Title
Unbounded recursion in `encoding/gob` struct decoding causes stack-overflow DoS - ([File: src/encoding/gob/decode.go])

### Summary
`jv_contains` in the reported jq CVE recurses into nested JSON structures with no depth limit, exhausting the C stack. The Go analog is `encoding/gob`'s decode path for concrete (non-ignored) struct/pointer fields: `decOpFor` generates a closure that calls `Decoder.decodeStruct`, which for self-referential types recurses once per level of nesting present in the *wire data*, with no depth counter, unlike the sibling "ignore" path (`decIgnoreOpFor`) which explicitly tracks `dec.ignoreDepth` against `maxIgnoreNestingDepth` (10000). `gob` is the wire format used by `net/rpc`, so a remote/unauthenticated peer sending a deeply nested gob-encoded value for a recursive destination type (e.g. a linked-list/tree struct) can drive unbounded recursion in the receiving process.

### Finding Description
Attacker input: a gob stream encoding a deeply nested value of a recursive struct type (e.g. `type RT struct{ A string; Next *RT }`), sent to a `net/rpc` server/client that calls `gob.NewDecoder(conn).Decode(...)` (`src/net/rpc/server.go`, `src/net/rpc/client.go`).

Entry point: `Decoder.Decode` → `Decoder.decodeStruct` (`src/encoding/gob/decode.go:469`). For each struct field decode instruction, `decOpFor` (`src/encoding/gob/decode.go:836`) generates, for `reflect.Struct` fields, an op that calls back into `dec.decodeStruct(*enginePtr, value)` (`src/encoding/gob/decode.go:904-907`) — i.e., decoding one nested/pointed-to struct invokes `decodeStruct` again. This chain repeats once per level present in the attacker-supplied wire data (e.g., following a `Next *RT` chain, or nested composite fields).

Failed check: there is no depth counter on this path. Contrast with `decIgnoreOpFor` (`src/encoding/gob/decode.go:923-929`), which explicitly increments `dec.ignoreDepth` and errors out via `errors.New("invalid nesting depth")` once `dec.ignoreDepth > maxIgnoreNestingDepth` (`maxIgnoreNestingDepth = 10000`, line 920) — proven by the existing regression test `TestIgnoreDepthLimit` (`src/encoding/gob/gobencdec_test.go:801-836`). No equivalent depth counter exists for the "decode into destination" path exercised by `decodeStruct`/`decOpFor`.

Sink: unbounded Go-stack growth via mutual recursion between `decodeStruct` and the field op closures, terminating in a runtime fatal ("goroutine stack exceeds ... limit") — an unrecoverable process crash, not a `panic` that can be caught by `recover()`.

### Impact Explanation
A crash of the decoding process (goroutine stack overflow is a fatal, non-recoverable runtime error in Go) constitutes a denial of service against any process using `encoding/gob` to decode untrusted input into a recursive/self-referential destination type — most notably `net/rpc`, which uses gob as its default wire codec for client/server RPC. This would fall under Go's PUBLIC track as a DoS if a concrete, currently-supported reachable path can be demonstrated end-to-end through `net/rpc`.

### Likelihood Explanation
Requires: (1) a victim program registering/using a recursive Go type as an RPC argument/result (or otherwise decoding gob into such a type from a network peer), and (2) an attacker able to send arbitrary bytes to that RPC endpoint/connection — plausible for services exposing `net/rpc` over TCP/HTTP without additional input validation. This matches "unauthenticated request / ordinary user data" per the rules.

### Recommendation
Add a depth counter (mirroring `ignoreDepth`/`maxIgnoreNestingDepth`) to the concrete-value decode path (`decodeStruct`, and the struct/array/slice/map recursive `decOpFor`-generated closures) in `src/encoding/gob/decode.go`, erroring out once a bounded nesting depth is exceeded, consistent with the existing bound already applied to unknown/ignored fields.

The following sketch illustrates the intended reproduction; it should be validated with `go test -run TestGobRecursiveDepth ./src/encoding/gob` in a Devin session, increasing `depth` until either a graceful `gob:` error is returned (safe) or the process crashes with a stack-overflow fatal error (vulnerable):

```go
package gob

import (
	"bytes"
	"testing"
)

type RT struct {
	A    string
	Next *RT
}

func TestGobRecursiveDepth(t *testing.T) {
	const depth = 2_000_000 // tune upward to attempt to exceed the goroutine stack limit
	root := &RT{A: "x"}
	cur := root
	for i := 0; i < depth; i++ {
		cur.Next = &RT{A: "x"}
		cur = cur.Next
	}

	var buf bytes.Buffer
	if err := NewEncoder(&buf).Encode(root); err != nil {
		t.Fatalf("encode error: %v", err)
	}

	var out RT
	// Expect: either a bounded "gob: ... nesting depth" error (fixed),
	// or (vulnerable, unfixed) an unrecoverable stack-overflow fatal error
	// terminating the test binary instead of returning a normal error.
	err := NewDecoder(&buf).Decode(&out)
	if err == nil {
		t.Log("decode succeeded; no depth limit enforced on concrete decode path")
	} else {
		t.Logf("decode returned error: %v", err)
	}
}
```

Given the uncertainty about whether this reproduces a stack overflow at practically reachable depths (versus being bounded first by memory/buffer limits), and because I could not execute this test to confirm the crash, treat this as an unverified analog requiring hands-on confirmation before filing, rather than a proven vulnerability.
