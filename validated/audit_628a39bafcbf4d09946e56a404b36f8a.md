### Title
Closing a bank does not require outstanding fee buckets to be zero, permanently locking uncollected fees - ([File: programs/marginfi/src/instructions/marginfi_group/close_bank.rs])

### Summary
`lending_pool_close_bank` validates that a bank has no open lending/borrowing positions and no pending emissions before closing, but never checks that `collected_insurance_fees_outstanding`, `collected_group_fees_outstanding`, or `collected_program_fees_outstanding` are zero, nor does it verify the `liquidity_vault`/`insurance_vault`/`fee_vault` token balances are drained. Once the `Bank` account is closed, the only on-chain record of those outstanding-fee amounts is destroyed, and every fee-collection instruction requires a live, deserializable `Bank` account, so any tokens still sitting in the vaults tied to unflushed fee buckets become permanently unreachable.

### Finding Description
This mirrors the reported bug class ("outflow of locked tokens accounted for only in certain calculations, so total-asset accounting excludes them, and closing/withdrawing everything does not unlock them"). In marginfi:

- Fee accrual is folded into `Bank.collected_insurance_fees_outstanding`, `Bank.collected_group_fees_outstanding`, and `Bank.collected_program_fees_outstanding` [1](#0-0) . These fee amounts live inside `liquidity_vault` until `lending_pool_collect_bank_fees` sweeps them out to `insurance_vault`/`fee_vault`/`fee_ata` [2](#0-1) .
- These fee buckets are excluded from `total_asset_shares`/`total_liability_shares` accounting — exactly like the report's "calculation of total assets excludes the locked funds" — so a bank can have `total_asset_shares == 0` and `total_liability_shares == 0` while still holding un-swept fee tokens in its liquidity vault, as confirmed by the fuzz-invariant that reconciles `vault_balance - outstanding_fees` against `total_deposits - total_liabilities` [3](#0-2) .
- `lending_pool_close_bank` checks only `lending_position_count`, `borrowing_position_count`, `total_asset_shares`, `total_liability_shares`, and `emissions_remaining` before closing the `Bank` account: [4](#0-3) . It does not check the three `collected_*_fees_outstanding` fields, and its `Accounts` struct doesn't even include the vault accounts, so it cannot verify or drain them [5](#0-4) .
- Because the `Bank` account is closed (`close = admin`), its data (including bump seeds and the fee-outstanding counters) is zeroed and the discriminator invalidated. `LendingPoolCollectBankFees` and `LendingPoolWithdrawFees` both require `AccountLoader<'info, Bank>` to deserialize successfully with `has_one = group` and derive vault seeds from live bank data [6](#0-5) . Once the bank account is closed, this path can never run again, so any tokens still in the liquidity vault tied to unflushed insurance/group/program fees become permanently stranded — no instruction exists that can recover them.

### Impact Explanation
This is a permanent-lock/freeze of protocol funds: legitimately-earned insurance fund contributions, group fees, and program fees (owed to the global fee wallet) can be made permanently inaccessible. Since anyone can create a marginfi group and become its admin (group admin is not a protocol-wide privileged role — it is scoped only to that user's own group/bank), a group admin can trigger this either by mistake or to grief the protocol's program-fee recipient and insurance fund by closing a bank while `collected_program_fees_outstanding` / `collected_insurance_fees_outstanding` are still positive, permanently denying the program fee wallet and insurance vault their due funds.

### Likelihood Explanation
Moderate. It requires the bank's `total_asset_shares`/`total_liability_shares`/`emissions_remaining` to be zero (i.e., no active depositors/borrowers) while the fee buckets are still non-zero — a realistic state, since fee accrual runs on every user-triggered interaction (including borrow-side activity that ends right before close) and `LendingPoolCollectBankFees` is a separate, permissionless-but-optional instruction that may not have run recently. A group admin only needs to call `close_bank` without first running `collect_bank_fees`.

### Recommendation
Add a check in `lending_pool_close_bank` requiring `collected_insurance_fees_outstanding`, `collected_group_fees_outstanding`, and `collected_program_fees_outstanding` to be zero (or below tolerance) before allowing the bank to close — analogous to the existing `emissions_remaining` check. Optionally, also verify/drain the `liquidity_vault`, `insurance_vault`, and `fee_vault` balances (or require `LendingPoolCollectBankFees` and `LendingPoolWithdrawFees` to be run immediately prior) so no token balance can outlive the `Bank` account it depends on.

### Proof of Concept
1. Group admin creates a bank and it accrues interest/fees over time via normal borrow/repay activity, incrementing `collected_group_fees_outstanding` / `collected_insurance_fees_outstanding` / `collected_program_fees_outstanding` (see accrual logic at [1](#0-0) ).
2. All depositors/borrowers exit so `total_asset_shares` and `total_liability_shares` fall to zero (dust is intentionally re-routed into `collected_insurance_fees_outstanding` on `withdraw_all`/`close_balance`, see [7](#0-6)  and [8](#0-7) ), and `emissions_remaining` is reduced to zero.
3. Admin skips (or intentionally avoids) calling `LendingPoolCollectBankFees`.
4. Admin calls `lending_pool_close_bank`; the checks in [4](#0-3)  all pass because none of them examine the fee-outstanding fields, and the `Bank` account is closed.
5. Any subsequent attempt to call `LendingPoolCollectBankFees` or `LendingPoolWithdrawFees` fails because the `Bank` account no longer exists/deserializes, permanently stranding the fee tokens still held in the bank's liquidity vault.

Note: I was unable to find any test (e.g. `tests/specs/basic/13_closebank.spec.ts`) that explicitly exercises non-zero fee buckets at close time, so I cannot confirm whether the test suite already covers or silently prevents this scenario in practice; a Devin session with full repository/test access would be needed to run and confirm this end-to-end.
