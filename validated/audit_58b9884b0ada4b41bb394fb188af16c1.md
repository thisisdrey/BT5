### Title
Replay-window bypass via unlocked gap between `window.Check` and `window.Update` allows duplicate decrypt/injection - ([File: connection_state.go])

### Summary
`ConnectionState.Decrypt` releases `decryptLock` after `cs.window.Check` and re-acquires it only after `dKey.DecryptDanger` completes, before calling `cs.window.Update`. Two goroutines processing packets with the same `messageCounter` concurrently (e.g. via multiple UDP reader routines) can both pass `Check` before either calls `Update`, so both packets get decrypted and forwarded to `tun.Write`.

### Finding Description
`ConnectionState.Decrypt` in `connection_state.go`: [1](#0-0) 

The lock is dropped between the `Check` call (line 64) and the `Update` call (line 76), leaving `DecryptDanger` (line 70) executed outside the critical section. If two packets carrying the identical `header.MessageCounter` arrive and are dispatched to the interface concurrently, both can call `cs.window.Check(l, messageCounter)` before either calls `cs.window.Update(l, messageCounter)`, since `Check` only inspects the bitmap without marking it. Both goroutines then independently call `cs.dKey.DecryptDanger` with the same counter/nonce and both succeed (AEAD decryption with a given nonce is deterministic and stateless, not itself replay-protected), producing two decrypted copies of the payload that are handed back up through `outside.go`'s packet-processing path to `tun.Write`.

Packets reach `readOutsidePackets` from independent UDP reader goroutines (`f.routines` listener queues in `main.go`/`interface.go`) that look up the target `hostinfo` from `f.hostMap.QueryIndex(h.RemoteIndex)` per-packet rather than being sharded by session, so two packets belonging to the same `ConnectionState` can legitimately be processed by different queues concurrently: [2](#0-1) 

The existing replay defense (`Bits.Check`/`Bits.Update`) assumes serialized check-then-mark semantics, but the actual implementation splits these into two separately-locked operations with unprotected decryption work in between, defeating the intended at-most-once guarantee.

### Impact Explanation
This allows an attacker who can duplicate/race a captured or replayed ciphertext (same 96-bit-nonce-bound counter) to have the same encrypted UDP payload decrypted and delivered twice to the local tun device, causing duplicate frame injection into the tun interface. This matches the "traffic decryption/forgery/replay" impact category — a replay-window bypass leading to duplicate plaintext delivery, which can be leveraged for traffic duplication/injection at the application layer above nebula, even though the AEAD tag/authentication itself is not broken (both decryptions are of the exact same legitimately-encrypted packet, not forged plaintext).

### Likelihood Explanation
Preconditions: an established session (`ConnectionState` already exists, no cert forgery needed) and the ability to get the interface to process two copies of the same ciphertext concurrently on different reader queues — achievable by an unprivileged network attacker replaying (racing) a duplicate UDP datagram, since Nebula's own UDP fan-out uses multiple reader goroutines that do not serialize packets by peer/session before hitting `Decrypt`. This is a genuine, deterministic race window (not a hypothetical), reproducible with a targeted unit test using two goroutines and a synchronization point between `Check` and `DecryptDanger`.

### Recommendation
Hold `decryptLock` for the entire duration of `Check` → `DecryptDanger` → `Update` (or use a single atomic "claim slot" operation before performing decryption) so that no two goroutines can both pass the replay check for the same counter before one of them marks it seen. Equivalent for `VerifyRelay`, which has the same pattern.

### Proof of Concept
Unit test in `connection_state_test.go`:
1. Build a `ConnectionState` with a real `dKey`/`window` via `newConnectionStateFromResult` or equivalent test helper.
2. Craft one valid encrypted packet for `messageCounter = N`.
3. Launch two goroutines that both call `cs.Decrypt(l, N, out1, packet, nb)` and `cs.Decrypt(l, N, out2, packet, nb)` concurrently, using a `sync.WaitGroup`/barrier (e.g. inject a small sleep or use `-race` with repeated iterations) so both goroutines pass `window.Check` before either reaches `window.Update`.
4. Assert that only one of the two calls returns a non-nil plaintext/nil error, and the other returns `ErrAlreadySeen`. Currently, both can return successfully, demonstrating the bypass.
5. Optionally use `go test -race -run TestDecryptRace -count=100` to make the race window reliably observed given `GOMAXPROCS>1`.

	var err error

	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}

	if err != nil {
		return nil, err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}
	return out, nil
}
