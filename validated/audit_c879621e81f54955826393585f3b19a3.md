Let me look more closely at the exact flow in `staking_contract.move` to confirm the finding.

### Title
Commission Percentage Applied Retroactively to Pending-Inactive Rewards — (`aptos-move/framework/aptos-framework/sources/staking_contract.move`)

---

### Summary

In `staking_contract.move`, the `distribute_internal` function charges commission on rewards earned by `pending_inactive` stake using the **current** `commission_percentage` at the time of distribution, not the rate that was in effect when the stake was unlocked. Because `update_commision` (callable by the staker at any time) does not lock in the commission rate for already-queued pending-inactive distributions, a staker can reduce the commission to 0% immediately after calling `unlock_stake`, then collect the full rewards — including the portion that should have gone to the operator — when the lockup expires.

---

### Finding Description

**Root cause — `distribute_internal` reads live `commission_percentage`:** [1](#0-0) 

`update_distribution_pool` is called with `staking_contract.commission_percentage` — the value stored in the struct at the moment `distribute` is invoked, not the value that existed when the distribution entry was originally created.

**`update_distribution_pool` charges commission on growth since last snapshot:** [2](#0-1) 

The commission deducted from each non-operator shareholder equals `(current_worth − previous_worth) × commission_percentage / 100`. If `commission_percentage` has been changed to 0 between the time the distribution was created and the time `distribute` is called, the operator receives nothing on those rewards.

**`update_commision` does not protect pending-inactive rewards:** [3](#0-2) 

`update_commision` calls `distribute_internal` first, but if the lockup has not yet expired there is no inactive stake to withdraw, so `distribute_internal` returns early at line 875–878 without updating the distribution pool. It then calls `request_commission_internal`, which explicitly excludes `pending_inactive` from its calculation: [4](#0-3) 

The comment says "commission has already been extracted" for pending_inactive, but this is only true for the **principal** amount. The rewards that will accrue on the pending_inactive stake **during the remaining lockup period** are not locked in at the old rate. After `update_commision` sets `commission_percentage = new_commission_percentage` (line 592), those future rewards will be charged at the new (potentially 0%) rate.

**Contrast with `delegation_pool.move`**, which correctly defers commission changes to the next lockup cycle: [5](#0-4) 

`staking_contract.move` has no equivalent deferral mechanism.

---

### Impact Explanation

A staker can steal the operator's commission on all rewards earned by pending-inactive stake during the lockup period:

1. Staker calls `unlock_stake(amount)` — `amount` APT enters `pending_inactive`; a distribution entry is created for the staker at the current commission rate (e.g. 10%).
2. Staker immediately calls `update_commision(operator, 0)` — `distribute_internal` returns early (no inactive coins yet); `request_commission_internal` locks in 10% only on **active** rewards; `commission_percentage` is set to 0.
3. Lockup expires — `pending_inactive` becomes `inactive`, now worth `amount + rewards`.
4. Anyone calls `distribute` — `update_distribution_pool` is invoked with `commission_percentage = 0`; the operator receives **zero** commission on `rewards`, which should have been `rewards × 10%`.

For a 1,000,000 APT unlock at 1% per-lockup reward rate and 10% commission, the operator loses **1,000 APT** per lockup cycle. The attack is repeatable.

---

### Likelihood Explanation

The staker is an unprivileged on-chain account. `update_commision` has no cooldown, no minimum commission floor, and no restriction on being called while a pending-inactive distribution is in flight. Any staker with an active staking contract can execute this in two sequential transactions.

---

### Recommendation

Cache the commission percentage inside the distribution pool entry at the time `add_distribution` is called (analogous to how `delegation_pool.move` uses `NextCommissionPercentage` deferred to the next lockup cycle). When `update_distribution_pool` is called at distribution time, use the cached rate rather than the live `staking_contract.commission_percentage`. Alternatively, mirror the `delegation_pool` pattern: make commission changes effective only at the start of the next lockup cycle, so no in-flight pending-inactive distribution can be retroactively repriced.

---

### Proof of Concept

```
// Pseudocode — all calls are unprivileged entry functions

// 1. Staker creates contract with 10% commission
create_staking_contract(staker, operator, 1_000_000_APT, 10);

// 2. Validator earns rewards for one epoch
end_epoch();  // pending_inactive = 0, active grows

// 3. Staker unlocks 1,000,000 APT — enters pending_inactive
//    add_distribution records staker's shares at 10% commission
unlock_stake(staker, operator, 1_000_000_APT);

// 4. Staker immediately drops commission to 0%
//    distribute_internal: no inactive coins → returns early (no pool update)
//    request_commission_internal: only touches active stake, not pending_inactive
//    commission_percentage := 0
update_commision(staker, operator, 0);

// 5. Lockup expires; pending_inactive (≈1,010,000 APT) becomes inactive
fast_forward_to_unlock(pool_address);

// 6. Anyone distributes — update_distribution_pool called with commission_percentage=0
//    Operator receives 0 APT on the ~10,000 APT of rewards
//    Staker receives full 1,010,000 APT instead of 1,009,000 APT
distribute(staker, operator);

// Operator has been robbed of ~1,000 APT (10% of ~10,000 APT rewards)
```

The exact stolen amount is `(rewards on pending_inactive during lockup) × original_commission_percentage / 100`, reachable in a single lockup cycle with no privileged access.
