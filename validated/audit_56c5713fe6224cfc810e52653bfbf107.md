### Title
Collateral/debt accounting keyed by an unchecked `asset-id` allows crediting real-asset collateral while transferring a worthless attacker-controlled token - (File: `mainnet/contracts/market/v0-market-vault.clar`)

### Summary
`v0-market-vault.clar` records collateral and debt in maps keyed by a caller-supplied `asset-id` (a bare `uint`), while the actual token movement is driven by a separately supplied `<ft-trait>` reference. Nothing in this contract ties the `ft` trait's contract identity to the `asset-id` being credited, mirroring the C4 root cause of "the safety check does not verify that the value actually moved matches what is being recorded" (there, an address equality check; here, no check at all).

### Finding Description
`collateral-add` accepts `(account principal) (amount uint) (ft <ft-trait>) (asset-id uint)` and:
1. Computes accounting updates keyed purely by `asset-id`: `add-user-collateral user-id asset-id amount` [1](#0-0) .
2. Moves tokens via whatever contract `ft` happens to reference: `receive-tokens ft amount account`, which is just `(contract-call? asset transfer amount account current-contract none)` [2](#0-1) .
3. Inserts the updated mask/collateral entry regardless of whether `ft`'s contract address is the token the protocol actually designates for `asset-id` [3](#0-2) .

There is no `asset-id -> token contract` registry anywhere in this contract (grep for `register-asset`/`add-asset` inside this file only turns up the unrelated `send-tokens`/`asset-contract` local binding used solely to special-case the STX wrapper) [4](#0-3) . The only defense is `check-impl-auth`, which merely requires `contract-caller` to equal the registered `impl` (the market's front-end logic contract) [5](#0-4) ; it does not constrain which `(ft, asset-id)` pairs are valid together. The same pattern repeats symmetrically in `collateral-remove`, `debt-add-scaled`, and `debt-remove-scaled` [6](#0-5) .

Just as the VTVL bug let the admin bypass the "is this the vesting token" check via a second valid address for the same logical token, here the vault has no positive check at all binding `asset-id` accounting to the `ft` trait's real identity — an ordinary user, through the market's normal deposit path (which ultimately calls `collateral-add` as `impl`), can supply their own SIP-010-compliant contract implementing `ft-trait` (returning success on `transfer` while moving negligible/worthless value) alongside an `asset-id` that corresponds to a real, valuable listed asset (e.g., sBTC/USDC). The vault credits full `amount` of collateral for the valuable `asset-id` while the real underlying balance backing that asset-id never increases.

### Impact Explanation
Because collateral is credited per `asset-id` independent of what token actually moved, an attacker can fabricate phantom collateral for a high-value asset-id and then borrow real, valuable assets against it through the market's borrow flow (which reads `get-collateral`/health-check state from this same registry) [7](#0-6) . This is a direct path to theft of real user/protocol funds and protocol insolvency — the vault's real token balance becomes insufficient to cover legitimate depositors' claims, exactly as in the original finding where the vesting balance became insufficient for legitimate claimants.

### Likelihood Explanation
Exploitability depends entirely on whether the calling `impl` market contract enforces a canonical `asset-id -> token contract` mapping before forwarding to `collateral-add`/`collateral-remove`. That validation, if it exists, lives in a different contract not covered in this file, so likelihood cannot be fully confirmed from `v0-market-vault.clar` alone; however, this contract itself provides zero enforcement, making it a single point of failure should the caller-side validation be missing or bypassable (e.g., through any code path that lets a user choose the `ft` trait argument independently of `asset-id`).

### Recommendation
Maintain an explicit on-chain `asset-id -> token principal` registry inside `v0-market-vault.clar` (populated only via DAO-gated configuration) and assert `(is-eq (contract-of ft) (unwrap-panic (map-get? asset-registry asset-id)))` at the top of `collateral-add`, `collateral-remove`, `debt-add-scaled`, and `debt-remove-scaled`, rather than trusting the caller to supply a consistent pair.

### Proof of Concept
1. Attacker deploys `evil-token.clar` implementing `ft-trait`, whose `transfer` always returns `(ok true)` without moving real value (or moves a negligible amount).
2. Attacker calls the market's deposit entry point (which is `impl` and thus authorized to call `market-vault`), passing `ft = evil-token` and `asset-id = <id of a real listed asset, e.g. sBTC>` with `amount = 100_000_000_00`.
3. `collateral-add` in `v0-market-vault.clar` runs `receive-tokens evil-token amount account` — succeeds trivially — then calls `add-user-collateral user-id asset-id amount`, crediting the attacker with fake sBTC collateral [3](#0-2) .
4. Attacker now borrows real sBTC (or another asset) against this phantom collateral through the market's borrow flow, which reads the fabricated `get-collateral` entry.
5. The vault's real token reserves are drained relative to what its internal accounting believes is backed, leaving legitimate depositors unable to withdraw — mirroring the original PoC where Alice's legitimate claim could not be honored due to accounting/balance divergence.

(define-private (add-user-collateral (user-id uint) (asset-id uint) (amount uint))
  (let ((key { id: user-id, asset: asset-id })
        (collateral-amount (default-to u0 (map-get? collateral key))) ;; graceful default
        (updated-collateral-amount (+ collateral-amount amount)))
      (map-set collateral key updated-collateral-amount)
      updated-collateral-amount))

(define-public (collateral-add (account principal) (amount uint) (ft <ft-trait>) (asset-id uint))
  (let ((states (var-get pause-states))
        (entry (resolve-or-create account))
        (user-id (get id entry))
        (mask (get mask entry))
        (updated-mask (mask-update mask asset-id true true)) ;; collateral, insert
        (updated-entry (merge entry (refresh updated-mask)))
        (result (add-user-collateral user-id asset-id amount)))

    (try! (check-impl-auth))
    (asserts! (not (get collateral-add states)) ERR-PAUSED)
    (asserts! (> amount u0) ERR-AMOUNT-ZERO)

    (try! (receive-tokens ft amount account))
    
    (insert updated-entry)

    (print {
      action: "collateral-add",
      caller: contract-caller,
      data: {
        account: account,
        asset-id: asset-id,
        amount: amount,
        updated-collateral-amount: result,
        mask-before: mask,
        mask-after: updated-mask
      }
    })
      
    (ok result)))

(define-public (collateral-remove (account principal) (amount uint) (ft <ft-trait>) (asset-id uint) (recipient principal))
  (let ((states (var-get pause-states))
        (entry (resolve account))
        (user-id (get id entry))
        (mask (get mask entry))
        (remaining (try! (remove-user-collateral user-id asset-id amount)))
        (updated-mask (if (is-eq remaining u0)
                        (mask-update mask asset-id true false) ;; collateral, remove
                        mask))
        (updated-entry (merge entry (refresh updated-mask))))

    (try! (check-impl-auth))
    (asserts! (not (get collateral-remove states)) ERR-PAUSED)
    (asserts! (> amount u0) ERR-AMOUNT-ZERO)

    (insert updated-entry)
    (try! (send-tokens ft amount recipient))
    
    (print {
      action: "collateral-remove",
      caller: contract-caller,
      data: {
        account: account,
        recipient: recipient,
        asset-id: asset-id,
        amount: amount,
        updated-collateral-amount: remaining,
        mask-before: mask,
        mask-after: updated-mask
      }
    })
    
    (ok remaining)))
