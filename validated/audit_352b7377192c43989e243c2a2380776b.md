### Title
Global adaptive energy limit can be manipulated by a single account to throttle bandwidth/energy for all users - ([File: chainbase/src/main/java/org/tron/core/db/EnergyProcessor.java])

### Summary
The chain-wide `TotalEnergyCurrentLimit`, which determines how much energy every frozen-TRX holder can draw from the shared energy pool, is derived from a decaying moving average of *aggregate* block energy usage (`TotalEnergyAverageUsage`). Because this average is fed purely by the sum of energy consumed in recent blocks with no per-account attribution or cap, any account (or coordinated set of accounts) that repeatedly issues high-energy TVM calls can push the global average above the target and force the shared limit to contract, degrading energy availability for every other account until the moving average decays back down or the committee intervenes via a governance proposal.

### Finding Description
`EnergyProcessor.updateTotalEnergyAverageUsage()` accumulates `BLOCK_ENERGY_USAGE` (the energy consumed by all transactions in each block) into a decaying-window average `TotalEnergyAverageUsage`, using the same time-decayed "usage/window" accounting pattern used elsewhere for individual account bandwidth/energy: [1](#0-0) 

`EnergyProcessor.updateAdaptiveTotalEnergyLimit()` then compares this aggregate average against `TotalEnergyTargetLimit` and either contracts (`CONTRACT_RATE`) or expands (`EXPAND_RATE`) `TotalEnergyCurrentLimit`, which is the *global* denominator used by `calculateGlobalEnergyLimit`/`calculateGlobalNetLimit`-style functions to translate every account's frozen balance into usable energy/bandwidth: [2](#0-1) 

This is the same class of bug described in the external report: a *global* counter is derived purely from aggregated, attacker-influenceable activity (block energy usage) with no protection against a single party dominating that aggregate, and the resulting throttled/expanded limit is applied uniformly to all unrelated users. In the referenced `TimeLockStrategy` report, an attacker inflates a shared daily accounting bucket to lock out legitimate transfers; here, an attacker inflates the shared `TotalEnergyAverageUsage` bucket (by repeatedly calling energy-intensive contracts) to contract `TotalEnergyCurrentLimit`, reducing every other frozen-energy holder's available energy for their own contract calls.

The window/target parameters (`ADAPTIVE_RESOURCE_LIMIT_TARGET_RATIO`, `ADAPTIVE_RESOURCE_LIMIT_MULTIPLIER`) and contraction/expansion rates are fixed governance-controlled constants, so once the limit is squeezed down by sustained attacker-driven usage, ordinary users have no way to raise it themselves — only decay over time or an SR committee proposal (`ProposalService`) can restore it: [3](#0-2) 

### Impact Explanation
Because `TotalEnergyCurrentLimit` is the shared denominator for every account's `calculateGlobalEnergyLimit`, artificially contracting it (via sustained attacker-driven energy consumption feeding the aggregate moving average) reduces the amount of energy every other frozen-TRX holder can draw from their stake for TVM execution. This effectively degrades the usable value of legitimate users' frozen/staked TRX for running smart-contract calls — a shared, unrelated resource — until the average decays (which can itself be perpetually re-inflated by the attacker) or governance manually raises `TOTAL_CURRENT_ENERGY_LIMIT`/adjusts the adaptive-limit parameters via a witness proposal. This matches the reported issue's core impact: legitimate users are inconvenienced/blocked from normal operation of a shared resource until the chain operators intervene.

### Likelihood Explanation
Any account can trigger this by broadcasting ordinary smart-contract-call transactions (`TriggerSmartContract`) that consume energy — no special privileges are required, only enough TRX/energy budget to repeatedly push `BLOCK_ENERGY_USAGE` above `TotalEnergyTargetLimit` across the `averageWindowSize` window. This is continuously reachable by any unprivileged contract caller and requires no witness/SR/peer compromise.

### Recommendation
Rework the adaptive energy/bandwidth limit calculation so that the *aggregate* usage feeding `TotalEnergyAverageUsage`/`TotalEnergyCurrentLimit` cannot be dominated by a single account or a small set of colluding accounts (e.g., attribute/cap per-account contribution to the moving average, or require usage to originate from a sufficiently diverse set of accounts/blocks before contracting the global limit), and add bounds/rate limits so contraction driven by a narrow set of callers cannot persistently suppress the shared resource for unrelated users.

### Proof of Concept
1. Freeze TRX for energy on account A (attacker) and account B (victim).
2. From account A, continuously trigger high-energy-consuming smart contract calls across many blocks so that per-block `BLOCK_ENERGY_USAGE` stays above `TotalEnergyTargetLimit` for a sustained period (`EnergyProcessor.updateTotalEnergyAverageUsage`/`updateAdaptiveTotalEnergyLimit` run each block/maintenance cycle: [4](#0-3) ).
3. Observe `TotalEnergyCurrentLimit` progressively shrink (contraction path, `CONTRACT_RATE_NUMERATOR/DENOMINATOR`).
4. Query account B's resources via `Wallet.getAccountResource` / `calculateGlobalEnergyLimit`: [5](#0-4)  and observe B's available energy from the same frozen balance has decreased, purely as a side effect of A's activity, with no way for B to restore it without A stopping or governance intervening.

  public void updateAdaptiveTotalEnergyLimit() {
    long totalEnergyAverageUsage = dynamicPropertiesStore
        .getTotalEnergyAverageUsage();
    long targetTotalEnergyLimit = dynamicPropertiesStore.getTotalEnergyTargetLimit();
    long totalEnergyCurrentLimit = dynamicPropertiesStore
        .getTotalEnergyCurrentLimit();
    long totalEnergyLimit = dynamicPropertiesStore.getTotalEnergyLimit();

    long result;
    if (totalEnergyAverageUsage > targetTotalEnergyLimit) {
      result = scaleByRate(totalEnergyCurrentLimit,
          AdaptiveResourceLimitConstants.CONTRACT_RATE_NUMERATOR,
          AdaptiveResourceLimitConstants.CONTRACT_RATE_DENOMINATOR);
    } else {
      result = scaleByRate(totalEnergyCurrentLimit,
          AdaptiveResourceLimitConstants.EXPAND_RATE_NUMERATOR,
          AdaptiveResourceLimitConstants.EXPAND_RATE_DENOMINATOR);
    }
    long upperBound = hardenCalculation()
        ? BigInteger.valueOf(totalEnergyLimit).multiply(BigInteger.valueOf(
            dynamicPropertiesStore.getAdaptiveResourceLimitMultiplier())).longValueExact()
        : totalEnergyLimit * dynamicPropertiesStore.getAdaptiveResourceLimitMultiplier();
    result = min(max(result, totalEnergyLimit, this.disableJavaLangMath()),
        upperBound, this.disableJavaLangMath());

    dynamicPropertiesStore.saveTotalEnergyCurrentLimit(result);
    logger.debug("Adjust totalEnergyCurrentLimit, old: {}, new: {}.",
        totalEnergyCurrentLimit, result);
  }
