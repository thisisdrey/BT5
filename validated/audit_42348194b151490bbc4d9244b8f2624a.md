## Analysis

The reported bug class — a protocol computing a payout/exchange amount from the **live ratio of two pooled balances**, with no slippage/deviation bound, allowing an attacker to sandwich the call with a swap to skew the ratio — has a direct analog in java-tron's on-chain token Exchange (bancor-style AMM) actuators.

### Title
Sandwichable ratio-based liquidity inject/withdraw amounts in `ExchangeInjectActuator`/`ExchangeWithdrawActuator` — ([File: actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java])

### Summary
`ExchangeInjectActuator` and `ExchangeWithdrawActuator` compute the amount of the "other" token to be paid/received during a liquidity inject or withdraw purely from the **current spot ratio** of `firstTokenBalance`/`secondTokenBalance` held in the `ExchangeCapsule`, with no caller-supplied minimum/maximum bound (`expected`) and no TWAP or deviation check. Any unprivileged account can call the public `ExchangeTransactionContract` (a normal swap) to shift that ratio in the same or adjacent block, then let the pending inject/withdraw execute against the skewed ratio, and finally reverse the swap — extracting value at the expense of the exchange creator, exactly mirroring the Salty.IO liquidation-reward manipulation described in the report (an estimate based on an assumed/manipulable token ratio).

### Finding Description
`ExchangeInjectActuator.doValidate()`/`execute()` reads the pool's current balances and derives `anotherTokenQuant` as a straight cross-multiplication of the live ratio: [1](#0-0) 

The `execute()` path performs the same unguarded computation and immediately debits/credits the account and pool state: [2](#0-1) 

The equivalent applies for withdrawals — `anotherTokenQuant` is derived purely from the instantaneous ratio of `firstTokenBalance`/`secondTokenBalance`: [3](#0-2) 

Neither `ExchangeInjectContract` nor `ExchangeWithdrawContract` carries an "expected"/slippage-bound field, unlike `ExchangeTransactionContract`, which explicitly supports `expected` to guard against unfavorable execution: [4](#0-3) 

`ExchangeTransactionContract` execution is unrestricted (any account may call it) and directly mutates the same pool balances via `ExchangeCapsule.transaction()`/`ExchangeProcessor`: [5](#0-4) [6](#0-5) 

Because inject/withdraw is restricted to the exchange creator: [7](#0-6) 

an attacker cannot directly force the ratio calculation into their own inject/withdraw, but any unprivileged observer of the creator's pending inject/withdraw transaction can front-run it with an `ExchangeTransactionContract` swap that pushes `firstTokenBalance`/`secondTokenBalance` to an extreme, causing the creator's inject to be forced to contribute a wildly disproportionate `anotherTokenQuant` (or the withdraw to yield a wildly disproportionate payout), then back-run with an opposite swap to restore the pool and pocket the difference — a classic sandwich against an unguarded AMM-ratio-derived amount, the same root cause as the reported Salty.IO bug (fee/amount derived from a manipulable pool ratio with no bound check).

### Impact Explanation
A successful sandwich forces the exchange creator's inject to lock in far more of `anotherTokenID` than intended, or forces a withdraw to release far less of `anotherTokenID` than the creator should receive — a direct, quantifiable theft of pooled token value extracted by the attacker's swap-and-reverse, which is an unauthorized transfer of value between chain participants purely through public transaction ordering (no privileged role required).

### Likelihood Explanation
The `ExchangeTransactionContract` used for the manipulating swap has no permission gate and no fee beyond `calcFee()`, making it trivially callable by anyone: [8](#0-7) 
Coupled with the missing slippage bound on inject/withdraw, exploitation only requires observing a pending inject/withdraw and racing it with ordinary transactions — no special privileges, keys, or SR/witness control needed.

### Recommendation
Add an `expected`/minimum-or-maximum bound field to `ExchangeInjectContract` and `ExchangeWithdrawContract` (mirroring `ExchangeTransactionContract.expected`), and validate the computed `anotherTokenQuant` against it in `doValidate()`/`execute()` for both `ExchangeInjectActuator` and `ExchangeWithdrawActuator`, rejecting the transaction if the pool ratio has moved beyond the caller's tolerance.

### Proof of Concept
1. Attacker monitors the mempool for the exchange creator's `ExchangeInjectContract` (or `ExchangeWithdrawContract`) transaction targeting exchange `id`.
2. Attacker submits an `ExchangeTransactionContract` swap on the same `id` that heavily skews `firstTokenBalance`/`secondTokenBalance` (e.g., dumping token A to make token B scarce), executed via `ExchangeCapsule.transaction()`.
3. The creator's inject transaction executes against the skewed ratio in `ExchangeInjectActuator.execute()`, computing an inflated `anotherTokenQuant` and debiting the creator far more of token B than intended (analogous for withdraw yielding far less token B than expected).
4. Attacker submits a reverse `ExchangeTransactionContract` swap restoring the ratio, realizing the value difference extracted from the creator's inject/withdraw.
