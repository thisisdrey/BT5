### Title
Attacker can block a victim's account from depositing into new collateral types by filling `depositTokensOfAccount` up to `MAX_TOKENS_PER_USER` via dust deposits/transfers - (contracts/DepositToken.sol, contracts/Pool.sol)

### Summary
Analogous to the GeniXCMS bug — where an unprivileged user registers a crafted username to block another user's account — an unprivileged EOA can block a victim's Metronome account by force-populating the victim's per-account token list. `DepositToken._mint` and `DepositToken._transfer` unconditionally call `Pool.addToDepositTokensOfAccount(recipient_)` whenever the recipient's balance of that token goes from 0 to positive, with no opt-in from the recipient. `Pool` enforces a combined cap of `MAX_TOKENS_PER_USER` across deposit and debt tokens and reverts with `UserReachedMaxTokens` once the cap is hit (see `test/Pool.test.ts:1386-1416`). An attacker who deposits dust into each registered `DepositToken` and transfers 1 wei to the victim (or simply calls `deposit(1, victim)` directly, since `onBehalfOf_` is attacker-chosen) fills the victim's list, after which every subsequent `deposit`/`transfer`/`seize` that would add a *new* token type to the victim's account reverts inside `_mint`/`_transfer`.

### Finding Description
- `DepositToken.deposit(amount_, onBehalfOf_)` accepts an arbitrary beneficiary and calls `_mint(onBehalfOf_, ...)` (`DepositToken.sol:211-237`).
- `_mint` adds the token to the recipient's pool tracking list on first receipt, with no consent check (`DepositToken.sol:485-488`).
- `_transfer` does the same on the recipient side (`DepositToken.sol:517-520`), gated only by `_revertIfLocked` on the *sender* (`DepositToken.sol:348-354`), so dust transfers are unrestricted.
- `Pool.addToDepositTokensOfAccount` reverts with `UserReachedMaxTokens` once `depositTokensOfAccount + debtTokensOfAccount == MAX_TOKENS_PER_USER` (verified behavior in `test/Pool.test.ts:1386-1416` and `:1491-1521`).

Because the revert happens inside the token's `_mint`, the entire `deposit` transaction reverts — the victim cannot open a position in any deposit token they don't already hold.

### Impact Explanation
Temporary denial of service / account blockage of the victim's account: all `deposit(..., victim)`, `transfer(..., victim, ...)` of new token types, and liquidation `seize` payouts to a fresh-token liquidator path for the victim revert. Concretely, a victim with an open debt position who needs to add a *different* collateral type (e.g., the only collateral they can still acquire, or the only one whose oracle price would rescue them) cannot do so while the attacker's dust occupies the list — exposing the position to liquidation it could otherwise have survived. The blockage is temporary and not full fund freezing: the victim can transfer each dust token out (balance → 0 triggers `removeFromDepositTokensOfAccount`, `DepositToken.sol:522-525`), and deposits of already-held tokens still work, but the attacker can cheaply re-fill freed slots, making the griefing persistent for as long as they choose to spend gas.

### Likelihood Explanation
Fully reachable by an unprivileged attacker: only public `deposit`/`transfer` entry points are needed, the dust cost is negligible (1 wei per token × number of registered deposit tokens), and no privileged role, oracle manipulation, or timing is required. The only mitigation is the victim self-cleaning their list at gas cost, which the attacker can race. Impact is bounded to blockage of new-token-type actions rather than loss of already-deposited funds, matching the Medium severity of the reference advisory.

### Recommendation
Do not track per-account token membership by pushing onto a bounded list on recipient-side balance changes, or decouple the revert: (a) let `addToDepositTokensOfAccount` skip rather than revert when the cap is hit (iterate lazily / drop the oldest entry), or (b) require recipient consent for list insertion (e.g., only add on `deposit` initiated by the account itself, or an explicit opt-in), or (c) remove `MAX_TOKENS_PER_USER` and make `debtPositionOf`/liquidation paths handle unbounded lists safely via off-chain-supplied token subsets.

// Foundry-style PoC against deployed pool `pool` with deposit tokens dt[0..N)

contract DustGrief {
    function attack(IPool pool, address victim) external {
        uint256 max = pool.MAX_TOKENS_PER_USER(); // combined deposit+debt cap
        IDepositToken[] memory dts = /* all pool.getDepositTokens() */;
        for (uint256 i; i < dts.length && i < max; ++i) {
            IERC20 underlying = dts[i].underlying();
            underlying.approve(address(dts[i]), 1);
            dts[i].deposit(1, victim); // _mint -> addToDepositTokensOfAccount(victim)
        }
        // Now: victim's deposit into any NEW deposit token reverts:
        // dts[k].deposit(x, victim) -> _mint -> addToDepositTokensOfAccount -> UserReachedMaxTokens
        // Also victim.transfer of a new token type to victim reverts the same way.
    }
}
