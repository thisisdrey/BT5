### Title
Missing slippage ("expected") protection in `ExchangeWithdrawActuator` allows front-running to reduce a creator's withdrawal proceeds - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
`ExchangeWithdrawActuator`, which lets a bancor-exchange creator withdraw one token and receive a proportional amount of the paired token, computes the paired-token amount from the exchange pool's *current* on-chain balances at validate/execute time, with no user-supplied minimum-expected-output check. This is the same missing-slippage-protection bug class as the reported OpenQ `refundDeposit` issue: an amount computed from mutable pool state at execution time, with no bound supplied by the caller, so the value can be silently reduced by a state change that happens first.

### Finding Description
In `ExchangeWithdrawActuator.doValidate()` / `execute()`, the amount of the "other" token a withdrawer receives (`anotherTokenQuant`) is derived purely from the exchange's live `firstTokenBalance`/`secondTokenBalance` ratio at the moment the transaction is processed: [1](#0-0) [2](#0-1) 

The `ExchangeWithdrawContract` message and its actuator never take/validate a caller-provided minimum acceptable `anotherTokenQuant`, unlike its sibling contract type `ExchangeTransactionContract`, whose actuator explicitly implements this protection via the `expected` field: [3](#0-2) 

Because any account can submit `ExchangeTransactionContract` (a swap) against the same exchange pool, an attacker can front-run a pending `ExchangeWithdrawContract` transaction (visible in the mempool) with a swap that shifts the `firstTokenBalance`/`secondTokenBalance` ratio in their favor. When the withdraw transaction is then included, `exchangeCapsule.transaction(...)`/the ratio math in `execute()` yields a smaller `anotherTokenQuant` than the creator expected when they signed and broadcast the transaction, with no way to bound or revert on this outcome: [4](#0-3) 

This mirrors the reported pattern exactly: an amount ("volume"/"anotherTokenQuant") is recomputed from currently-available state ("availableFunds"/pool balances) instead of being bounded by a value the caller committed to, so a transaction ordered ahead of the victim's silently reduces (never reverts) the amount the victim receives.

### Impact Explanation
The exchange creator withdrawing funds can receive materially less of the paired token than they intended when they signed the transaction, because the withdraw proportion is computed from a pool ratio that any other account can manipulate first via an ordinary swap. This is a direct value-extraction / MEV vector causing the withdrawer to lose expected funds, matching the "unbacked/incorrect balance realized by user" impact class.

### Likelihood Explanation
Any account with TRX/tokens can submit `ExchangeTransactionContract` swaps against the same exchange pool ID that a pending `ExchangeWithdrawContract` targets, and can observe pending transactions to time this front-run — the actuator performs no additional access restriction on who can trade against the pool, only the withdraw itself is creator-restricted. No special privilege beyond broadcasting an ordinary transaction is required.

### Recommendation
Add a caller-supplied minimum acceptable output (an `expected` field, analogous to `ExchangeTransactionContract.getExpected()`) to `ExchangeWithdrawContract`, and have `ExchangeWithdrawActuator.doValidate()`/`execute()` revert if the computed `anotherTokenQuant` falls below that bound, exactly as `ExchangeTransactionActuator` already does at [5](#0-4) .

### Proof of Concept
1. Exchange pool has `firstTokenBalance = X`, `secondTokenBalance = Y`.
2. Creator broadcasts `ExchangeWithdrawContract` withdrawing `tokenQuant` of the first token, expecting `anotherTokenQuant ≈ Y * tokenQuant / X` per the ratio math in [6](#0-5) .
3. Attacker observes this pending transaction and broadcasts an `ExchangeTransactionContract` swap that shifts the ratio (e.g., dumps the first token into the pool), which gets included first in the same block.
4. When the creator's withdraw executes, `firstTokenBalance`/`secondTokenBalance` have changed, so `anotherTokenQuant` computed in `execute()` is now materially smaller than what the creator expected, and the transaction still succeeds (no revert, no minimum check) — see execute() logic at [7](#0-6) .
