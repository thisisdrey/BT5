### Title
Unbounded `git-fetch(1)` execution via `FetchRemoteRequest.Timeout=0` enables slow-loris resource-exhaustion DoS - (File: internal/gitaly/service/repository/fetch_remote.go)

### Summary
`FetchRemote` only wraps the RPC context with a deadline when the caller-supplied `Timeout` field is greater than zero; when `Timeout` is unset (default `0`), the fetch runs with no server-side ceiling. An attacker who controls the fetched remote (e.g., a repo mirror/import pointing at an attacker-owned server) can trickle the smart-HTTP/SSH response indefinitely, keeping the `git-fetch(1)` process, quarantine directory, and reference-transaction updater goroutines alive indefinitely.

### Finding Description
In `FetchRemote`, the timeout is applied conditionally: [1](#0-0) 
If `req.GetTimeout()` is `0` (the protobuf default when the field is omitted), no `context.WithTimeout` is ever set, so `ctx` retains whatever deadline the gRPC client set (which for an attacker-controlled call may be none). This `ctx` is passed straight into `fetchRemoteAtomic`, which spawns the `git-fetch(1)` subprocess against `req.GetRemoteParams().GetUrl()` and `req.GetSshKey()`/`req.GetKnownHosts()`: [2](#0-1) 
Because `DryRun`/`Porcelain` fetch plus a quarantine directory and two `updateref.Updater` instances are held open for the whole duration of the fetch, a remote that never completes ref advertisement or trickles bytes keeps: the `git` subprocess, the quarantine tempdir, and the started-but-uncommitted `prunedUpdater`/`refUpdater` (each itself a live `git update-ref` process) all alive for as long as the attacker's server keeps the connection open.
There is no default/maximum timeout enforced by Gitaly itself; `validateFetchRemoteRequest` only checks that `Repository` and `RemoteParams.Url` are set/valid, and never rejects `Timeout <= 0`: [3](#0-2) 
The only mitigation available is the opt-in `[[concurrency]]` limiter, which is disabled by default and, even when configured, only bounds the number of concurrent in-flight calls per RPC/repo — it does not cap the duration of a single call: [4](#0-3) 

### Impact Explanation
An attacker who owns a repository can configure a pull mirror or import source pointing at their own slow-loris server and omit (or set to `0`) the `Timeout` field of `FetchRemoteRequest`. Each such call ties up a `git`/`ssh` process slot, a quarantine directory, and the reference-transaction lock for that repository indefinitely. Repeated with several repositories/mirrors, this can exhaust the process/thread budget of the Gitaly storage shard, degrading or denying service for other tenants on that shard — matching a GitLab bounty "Denial of Service" impact class scoped to a single RPC handler.

### Likelihood Explanation
The only precondition is that the attacker controls the remote endpoint being fetched from (achievable via project pull-mirror/import configuration on a repository they own) and can omit or zero out `Timeout`. No privileged role, secret, or non-default Gitaly configuration is required, and the behavior is fully reproducible via a direct `FetchRemoteRequest` gRPC call or via GitLab Rails-triggered mirroring against an attacker-controlled server.

### Recommendation
Enforce a server-side maximum timeout ceiling for `FetchRemote` regardless of the client-supplied `Timeout` (e.g., always apply `context.WithTimeout` using `min(req.GetTimeout(), maxAllowedFetchTimeout)` with a sane non-zero default when `Timeout` is unset), and/or reject requests with `Timeout <= 0` in `validateFetchRemoteRequest`.

func TestFetchRemote_NoTimeoutSlowLoris(t *testing.T) {
    ctx := testhelper.Context(t)
    cfg, client := setupRepositoryService(t)

    _, remoteRepoPath := gittest.CreateRepository(t, ctx, cfg)
    repoProto, _ := gittest.CreateRepository(t, ctx, cfg)

    // never respond, simulating a slow-loris smart-HTTP remote
    block := make(chan struct{})
    gitCmdFactory := gittest.NewCommandFactory(t, cfg)
    port := gittest.HTTPServer(t, ctx, gitCmdFactory, remoteRepoPath,
        func(w http.ResponseWriter, r *http.Request, next http.Handler) {
            <-block // never closed: connection hangs forever
        })
    defer close(block)

    req := &gitalypb.FetchRemoteRequest{
        Repository: repoProto,
        RemoteParams: &gitalypb.Remote{
            Url: fmt.Sprintf("http://127.0.0.1:%d/%s", port, filepath.Base(remoteRepoPath)),
        },
        // Timeout intentionally omitted -> defaults to 0, no ctx deadline is applied
    }

    callCtx, cancel := context.WithTimeout(ctx, 5*time.Second)
    defer cancel()
    _, err := client.FetchRemote(callCtx, req)
    // Expectation if vulnerable: request is still blocked when the 5s test-level
    // timeout is hit (DeadlineExceeded on the *test* context, not a Gitaly-enforced
    // limit), proving Gitaly applied no ceiling of its own.
    require.ErrorIs(t, err, context.DeadlineExceeded)
}

func (s *server) validateFetchRemoteRequest(ctx context.Context, req *gitalypb.FetchRemoteRequest) error {
	if err := s.locator.ValidateRepository(ctx, req.GetRepository()); err != nil {
		return structerr.NewInvalidArgument("%w", err)
	}

	if req.GetRemoteParams() == nil {
		return structerr.NewInvalidArgument("missing remote params")
	}

	if req.GetRemoteParams().GetUrl() == "" {
		return structerr.NewInvalidArgument("blank or empty remote URL")
	}

	return nil
}
