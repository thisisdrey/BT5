### Title
Signer `BlockAccepted.response_data` (tenure-extend timestamps) is not covered by the signer's signature but is trusted to steer miner tenure-extension timing - ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
`StackerDBListener`'s block-response handling verifies a signer's signature only over `block_sighash`, then unconditionally extracts and uses `response_data` (which is not part of the signed digest) to update per-signer timing state that the miner relies on to decide when to extend its tenure. This is the same bug class as the Taiko `GuardianProver` finding: a signature commits to only part of a message, while a semantically consequential field is delivered alongside the signature but is not authenticated by it, letting the message's author (a single signer, not any special "admin") unilaterally choose an unsigned value that downstream logic treats as trustworthy.

### Finding Description
In the signer-message processing loop, when a `SignerMessageV0::BlockResponse(BlockResponse::Accepted(accepted))` is received, the code destructures: [1](#0-0) 

and validates the signature only against `block_sighash`: [2](#0-1) 

Note that `signer_pubkey.verify(block_sighash.bits(), &signature)` checks the signature over `block_sighash` alone — `response_data` (containing `tenure_extend_timestamp` and `read_count_extend_timestamp`) is never included in the signed digest. Despite this, once the signature check passes, the (unauthenticated) `tenure_extend_timestamp` / `read_count_extend_timestamp` values are fed into the node's idle/read-count timestamp tracking: [3](#0-2) 

This mirrors the report's core defect exactly: the equality that should hold — "the value used to drive a consequential decision is the same value that was cryptographically committed to by the signer" — is broken. Here, a legitimate signer (who correctly signs `block_sighash` for a real, valid block) can attach an arbitrary `tenure_extend_timestamp`/`read_count_extend_timestamp` without invalidating their signature, because that data was never part of what they signed.

### Impact Explanation
`tenure_extend_timestamp` and `read_count_extend_timestamp` feed per-signer idle-time and read-count bookkeeping (`update_idle_timestamp` / `update_read_count_timestamp`) that the miner uses to decide when to extend or end its tenure. Because this timing data isn't bound to the signature, any single signer in the current reward-cycle signer set can inject falsified timestamps riding on an otherwise-valid, correctly-signed block-acceptance message. Depending on how these values are subsequently aggregated (this repo slice does not show the full aggregation/threshold logic beyond this file), a single non-majority signer could cause the miner to make a premature or delayed tenure-extension decision — i.e., steer node behavior away from the canonical/intended timing using data that was never actually agreed upon/signed by that signer. This falls under "steering a node off the tip via false inventory"-class impact (here, false tenure-timing data), which is a High-impact analog per the rules, since it lets an unauthenticated (with respect to this specific field) message component drive protocol-relevant node behavior.

### Likelihood Explanation
Likelihood is moderate-to-high for any single member of the active signer set: they need no special privilege beyond normal signer participation (which the protocol already grants to potentially many entities), and no coordination with other signers is required to forge this specific field, since it is never checked against the signature at all. The attack requires only sending a syntactically valid, properly-signed `BlockResponse::Accepted` message (which the signer can produce trivially for real blocks) with a manipulated `response_data`.

### Recommendation
Include `response_data` (i.e., `tenure_extend_timestamp` and `read_count_extend_timestamp`) in the data that is signed/verified, e.g. by having signers sign over `hash(block_sighash || response_data)` instead of `block_sighash` alone, and updating the verification at `stacks-node/src/nakamoto_node/stackerdb_listener.rs:411` to check the combined digest. This closes the gap between what is cryptographically authenticated and what is subsequently trusted and acted upon.

### Proof of Concept
1. As a member of the current signer set, construct a legitimate `BlockAccepted` for a real, valid block `B`, with correct `signer_signature_hash = block_sighash`.
2. Sign only `block_sighash` as required by the protocol (`signer_pubkey.verify(block_sighash.bits(), &signature)` at line 411 only checks this).
3. Set `response_data.tenure_extend_timestamp` / `response_data.tenure_extend_read_count_timestamp` to arbitrary attacker-chosen values (e.g., far in the future or far in the past).
4. Publish this message to the signer's StackerDB slot.
5. `StackerDBListener` accepts the signature as valid (it only covers `block_sighash`), then calls `update_idle_timestamp`/`update_read_count_timestamp` with the forged, unauthenticated timing values at lines 472–483, propagating the falsified data into the miner's tenure-extension decision logic.
