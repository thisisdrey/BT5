### Title
Malformed StackerDB chunk write leaks internal DB/error details in HTTP 500 response - (File: `stackslib/src/net/api/poststackerdbchunk.rs`)

### Summary
`RPCPostStackerDBChunkRequestHandler::try_handle_request` catches the catch-all branch of `try_replace_chunk` failures and echoes the raw `Debug` representation of the internal `net_error`/`db_error` directly into the HTTP response body sent back to the (unauthenticated) client.

### Finding Description
The endpoint `POST /v2/stackerdb/:address/:contract/chunks` has no `auth_token` check (contrast with `blockreplay`/`blocksimulate`/`fastcallreadonly`, which are constructed with `self.auth_token.clone()`), so it is reachable by any remote, unprivileged peer. [1](#0-0) 

When a submitted chunk fails `try_replace_chunk`, the handler classifies known, client-attributable failures (`StaleChunk`, `NoSuchSlot`, `BadSlotSigner`/`VerifyingError`, `StackerDBChunkTooBig`, `TooManySlotWrites`) into a structured JSON ack. Any other error falls into the catch-all `_` arm, which formats the error's `Debug` output directly into the HTTP body:
```
return Err(StacksHttpResponse::new_error(
    &preamble,
    &HttpServerError::new(format!(
        "Failed to store StackerDB chunk for {}: {:?}",
        &contract_identifier, &e
    )),
));
``` [2](#0-1) 

The same pattern repeats for the subsequent `get_slot_metadata` and `tx.commit()` failure paths, which also embed `{:?}` of the underlying error into the client-visible `HttpServerError` body. [3](#0-2) [4](#0-3) 

`try_replace_chunk` and its helper `get_slot_validation`/`insert_chunk` propagate arbitrary DB-layer errors (via `?`) that are not among the explicitly matched `net_error` variants — e.g. SQLite failures, malformed schema-state errors, or other `db_error`-derived conditions — through this same generic path. [5](#0-4)  The `HttpServerError` payload is then serialized verbatim as the HTTP response text. [6](#0-5) 

This is directly analogous to the reported parse-server issue: a request that triggers a database-layer failure results in the internal error's structured detail being surfaced unsanitized to the requesting client, rather than a generic message with details logged server-side only.

### Impact Explanation
An unauthenticated remote client that can trigger any unclassified/unexpected DB error on `try_replace_chunk` (e.g. transient SQLite contention, disk/IO errors, or any future/rare `net_error`/`db_error` variant not enumerated in the match) will receive that error's full `Debug` string in the HTTP body. This can disclose internal implementation details such as SQL error text, internal state, and file/error context that should remain server-side only, per the project's own comment that unexpected errors are meant to be classified as opaque HTTP 500s but the implementation leaks the detail into the response rather than logging-only. This does not itself corrupt state or bypass any signature check — the classified/security-relevant errors (`BadSlotSigner`, `VerifyingError`, size/version caps) are handled correctly and return sanitized codes — the exposure is limited to the generic catch-all branch and the metadata-reload/commit failure paths.

### Likelihood Explanation
Likelihood of triggering the *unclassified* error branch specifically depends on being able to induce a genuine DB-layer failure (e.g., disk pressure, concurrent-write contention, or another latent `net_error` path) rather than any client-controlled input alone, since normal malformed-chunk cases (bad signer, stale version, oversized chunk, too many writes) are already funneled into sanitized, coded acks. [7](#0-6)  This makes the exposure narrower than the parse-server case (which was reachable via a simple malformed regex string on every request); confirming an easily-reproducible remote trigger for the catch-all branch alone would require deeper investigation of the SQLite/`db_error` code paths, which I was not able to fully enumerate here.

### Recommendation
In the catch-all branch and the metadata-reload/commit-failure branches of `try_handle_request` in `stackslib/src/net/api/poststackerdbchunk.rs`, log the detailed error server-side only (as already done via `error!(...)`) and return a generic, non-detailed message (e.g. `"Failed to store StackerDB chunk"`) in the `HttpServerError` body instead of interpolating `{:?}` of the internal error into the client-facing text.

### Proof of Concept
Not able to construct a concrete, reliably-reproducible remote trigger for the unclassified-error branch without deeper access to conditions that cause `try_replace_chunk`/`get_slot_metadata`/`tx.commit()` to return a `net_error` variant outside the explicitly matched set (e.g., forcing a SQLite-level failure). This is a genuine information-disclosure code pattern (unsanitized `{:?}` of an internal error surfaced to an unauthenticated caller), but I could not verify within the available tool budget that a purely network-request-driven input (without needing local DB corruption/resource exhaustion) can deterministically reach the catch-all arm the way a malformed `$regex` deterministically reaches the leaking code in the parse-server report. This uncertainty should be resolved by a background engineer with the ability to run the node and attempt to force a `db_error` (e.g., via disk-full simulation, concurrent write races, or corrupted stackerdb DB file) to confirm end-to-end exploitability.

    pub fn try_replace_chunk(
        &self,
        smart_contract: &QualifiedContractIdentifier,
        slot_desc: &SlotMetadata,
        chunk: &[u8],
    ) -> Result<(), net_error> {
        // Check per-replica chunk-size cap.
        if (chunk.len() as u64) > self.config.chunk_size {
            return Err(net_error::StackerDBChunkTooBig(chunk.len()));
        }

        let slot_validation = self
            .get_slot_validation(smart_contract, slot_desc.slot_id)?
            .ok_or(net_error::NoSuchSlot(
                smart_contract.clone(),
                slot_desc.slot_id,
            ))?;

        if !slot_desc.verify(&slot_validation.signer)? {
            return Err(net_error::BadSlotSigner(
                slot_validation.signer,
                slot_desc.slot_id,
            ));
        }
        if slot_desc.slot_version <= slot_validation.version {
            return Err(net_error::StaleChunk {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
            });
        }
        if slot_desc.slot_version > self.config.max_writes {
            return Err(net_error::TooManySlotWrites {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
                max_writes: self.config.max_writes,
            });
        }
        self.insert_chunk(smart_contract, slot_desc, chunk)
    }
