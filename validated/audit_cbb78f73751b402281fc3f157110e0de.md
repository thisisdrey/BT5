## Analysis

`pallet-bounties::claim_bounty` in `substrate/frame/bounties/src/lib.rs` shows the exact same broken invariant as the Ajna `RewardsManager._claimRewards` report: the payout owed to the beneficiary/curator is silently capped to the bounty account's *current* balance instead of the recorded `bounty.value`/`bounty.fee`, and the bounty record is deleted unconditionally, so any shortfall is permanently and irrecoverably lost. [1](#0-0) 

### Title
Bounty payout silently capped to bounty account balance, permanently losing curator/beneficiary funds - (File: `substrate/frame/bounties/src/lib.rs`)

### Summary
`claim_bounty` computes `fee = bounty.fee.min(balance)` and `payout = balance.saturating_sub(fee)` using the bounty sub-account's *current* free balance rather than the bounty's recorded `value`/`fee`. If the bounty account is underfunded relative to the amount that was approved/awarded (e.g., due to a prior partial slash, an accounting inconsistency, or any external reduction of the sub-account's balance), the curator and beneficiary receive less than entitled, the bounty entry is deleted (`*maybe_bounty = None`), and there is no mechanism to reclaim the shortfall later — mirroring the Ajna `rewardsEarned > ajnaBalance => rewardsEarned = ajnaBalance` bug exactly.

### Finding Description
In `claim_bounty` [2](#0-1) :
```rust
let balance = T::Currency::free_balance(&bounty_account);
let fee = bounty.fee.min(balance); // just to be safe
let payout = balance.saturating_sub(fee);
...
let res = T::Currency::transfer(&bounty_account, &curator, final_fee, AllowDeath); // should not fail
debug_assert!(res.is_ok());
let res = T::Currency::transfer(&bounty_account, &beneficiary, payout, AllowDeath); // should not fail
debug_assert!(res.is_ok());
*maybe_bounty = None;
```
The code comment ("just to be safe") shows this is a deliberate defensive cap against the sub-account being underfunded — the same defensive pattern flagged as unsafe in the Ajna report. Instead of asserting that `balance >= bounty.value` (the amount that was funded from the treasury when the bounty was approved) and reverting/erroring if not, the pallet just pays out whatever happens to be present and deletes the bounty state (`Bounties::<T,I>::try_mutate_exists` sets `*maybe_bounty = None`, plus `BountyDescriptions::remove` and `T::ChildBountyManager::bounty_removed`). Once the record is gone, the outstanding, unpaid difference between the intended payout and the actual balance can never be claimed — there is no ledger tracking the deficit. The existing test `claim_handles_high_fee` in `substrate/frame/bounties/src/tests.rs` (lines 889-925) explicitly demonstrates this: after slashing 10 units from the bounty account, `BountyClaimed { payout: 0, ... }` is emitted and the beneficiary receives `0` instead of the value they were awarded — the funds are simply gone, not deferred. [3](#0-2) 

The existing "safety" guard (`.min(balance)`, `saturating_sub`) is precisely the anti-pattern the audit report criticizes: it avoids a panic/revert but converts an accounting bug into a silent, permanent loss of value for a legitimate claimant, and does so unconditionally for *any* caller (`claim_bounty` can be triggered by any signed account, not just curator/beneficiary — "anyone can trigger claim").

### Impact Explanation
This breaks the "conserve value and settle exactly once to the rightful beneficiary and amount" invariant required by the SDK impact gate. A curator or beneficiary can lose part or all of an approved/awarded bounty payout with no path to recovery, and the bounty record disappears so the shortfall cannot even be tracked, proposed again, or made whole via governance without manual off-chain reconciliation. While bounty-account underfunding is not supposed to happen under normal flow (the treasury moves the exact `value` into the bounty sub-account at approval time), any code path that reduces the sub-account balance below the recorded `value`/`fee` (slashing, an account-lock interaction, an ED-related dust removal, or a future refactor that shares the sub-account) turns into permanent fund loss instead of a recoverable error.

### Likelihood Explanation
Likelihood is moderate: under the pallet's own normal happy path the balance should always equal `value`, so this is not exploitable by an unprivileged attacker through the intended flow alone. However, the pattern is a genuine implementation defect — identical in structure to the confirmed Ajna finding — and any external interference with the bounty sub-account's balance (which is a normal `AccountId` subject to system-wide slashing/interactions) silently and irreversibly shortchanges the beneficiary rather than erroring out, which is exactly the risk class the recommendation in the source report calls out ("revert if insufficient... available").

### Recommendation
Replace the `.min(balance)`/`saturating_sub` capping logic with an explicit check that `balance >= bounty.fee.saturating_add(payout_owed)` (i.e., verify the bounty account actually holds the full recorded `value`) and return an error (e.g., `Error::<T, I>::InsufficientBountyBalance`) instead of silently reducing the payout and deleting the bounty record when underfunded. If a partial-funding scenario must be supported, track the outstanding deficit in a persistent storage item so it can be claimed once the account is topped up, rather than discarding the bounty via `*maybe_bounty = None`.

### Proof of Concept
The existing unit test already reproduces the bug end-to-end:

#[test]
fn claim_handles_high_fee() {
	ExtBuilder::default().build_and_execute(|| {
		Balances::make_free_balance_be(&Treasury::account_id(), 101);
		Balances::make_free_balance_be(&4, 30);
		assert_ok!(Bounties::propose_bounty(RuntimeOrigin::signed(0), 50, b"12345".to_vec()));

		assert_ok!(Bounties::approve_bounty(RuntimeOrigin::root(), 0));

		go_to_block(2);

		assert_ok!(Bounties::propose_curator(RuntimeOrigin::root(), 0, 4, 49));
		assert_ok!(Bounties::accept_curator(RuntimeOrigin::signed(4), 0));

		assert_ok!(Bounties::award_bounty(RuntimeOrigin::signed(4), 0, 3));

		go_to_block(5);

		// make fee > balance
		let res = Balances::slash(&Bounties::bounty_account_id(0), 10);
		assert_eq!(res.0.peek(), 10);

		assert_ok!(Bounties::claim_bounty(RuntimeOrigin::signed(1), 0));

		assert_eq!(
			last_event(),
			BountiesEvent::BountyClaimed { index: 0, payout: 0, beneficiary: 3 }
		);

		assert_eq!(Balances::free_balance(4), 70); // 30 + 50 - 10
		assert_eq!(Balances::free_balance(3), 0);
		assert_eq!(Balances::free_balance(Bounties::bounty_account_id(0)), 0);

		assert_eq!(pallet_bounties::Bounties::<Test>::get(0), None);
		assert_eq!(pallet_bounties::BountyDescriptions::<Test>::get(0), None);
	});
}
