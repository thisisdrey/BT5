## Analysis

The reported bug class — a signed message that omits a domain separator (chainID) and is therefore replayable across a different execution context (a forked chain) — maps directly onto how StackerDB chunk signatures are constructed in this repo.

`SlotMetadata::auth_digest()` computes the signed digest as only `slot_id || slot_version || data_hash`: [1](#0-0) 

Verification (`SlotMetadata::verify`) recovers the public key from this same digest and compares only against the `principal` address passed in by the caller — the smart-contract/StackerDB identity is never part of what's signed: [2](#0-1) 

Both the node-side write path (`StackerDBs::try_replace_chunk`) and the gossip-validation path (`StackerDBSync::validate_received_chunk` / `PeerNetwork::handle_unsolicited_StackerDBPushChunk`) look up the expected signer *for a given contract_id + slot_id* and then call this same contract-agnostic `verify()`: [3](#0-2) [4](#0-3) 

The node runs many StackerDB contracts concurrently that reuse the *same slot ordering* for the *same signer set*. In particular, every `.signers-{set}-{message_id}` contract simply re-exports the shared `.signers` slot ordering: [5](#0-4) [6](#0-5) 

Because a given signer occupies the identical `slot_id` in every `.signers-{set}-*` contract (one per signer-message lane), and the signature covers only `(slot_id, slot_version, data_hash)` — never the contract/DB identity — a chunk that a signer validly authored and pushed for one message lane (e.g. `.signers-1-0`, BlockResponse) can be captured (it is broadcast in the clear over p2p, and also fetchable from the public `/v2/stackerdb/.../chunks` read endpoint) and replayed byte-for-byte into a *different* `.signers-1-N` contract at the same `slot_id`, as long as the replayed `slot_version` exceeds whatever version that other contract's slot currently has (trivial for an unused/low-version slot). Nothing in `try_replace_chunk`, `validate_received_chunk`, or `SlotMetadata::verify` ties the signature to the specific contract it was intended for — the cross-contract "authenticated for A" vs. "stored/propagated as valid for B" equality is broken.

This is a legitimate remote, unauthenticated write: the attacker needs no secret key and no admin role, only the ability to observe an already-published, validly-signed chunk and re-POST/re-gossip it against a sibling StackerDB contract. The resulting write is genuinely accepted (passes signature, version, and size checks) and gets stored and replicated network-wide, injecting wrong-lane payload bytes into a signer's slot in an unrelated message-type DB — which downstream signer/consumer logic (e.g. `SignerMessageV0` deserialization, state-machine update evaluators) was never designed to receive from that lane, since payload-type/lane matching (`signer_message_payload_matches_lane`) is enforced only client-side, not at the StackerDB storage layer: [7](#0-6) 

### Title
StackerDB chunk signatures omit the target contract/DB identity, enabling cross-contract signature replay - (File: libstackerdb/src/libstackerdb.rs)

### Summary
`SlotMetadata::auth_digest()` signs only `(slot_id, slot_version, data_hash)`, with no binding to the StackerDB smart-contract identifier the chunk is destined for. Because multiple boot StackerDB contracts (one per signer message "lane": `.signers-{set}-{message_id}`) share the exact same signer→slot_id ordering, a validly-signed chunk observed in one contract's replica can be replayed unmodified into a sibling contract at the same slot_id, and will pass all node-side validation (`SlotMetadata::verify`, `try_replace_chunk`, `validate_received_chunk`).

### Finding Description
`auth_digest` builds the signed hash from only three fields — slot id, slot version, and the chunk's data hash — omitting any contract/DB-scoped domain separator: [1](#0-0) 

`verify()` recovers the pubkey from that digest and checks it against whatever `principal` the caller supplies — it has no notion of "which StackerDB this signature was meant for": [2](#0-1) 

The write path resolves the expected signer purely from `(smart_contract, slot_id)`, then calls the contract-agnostic `verify`: [3](#0-2) 

The gossip/push validation path does the same: [4](#0-3) 

Every signer-message-lane contract for a given signer set (`.signers-1-0`, `.signers-1-1`, ... `.signers-1-N`) derives its slot assignment from the same underlying `.signers` state, so a given signer's address occupies the identical `slot_id` across all of them: [5](#0-4) [6](#0-5) 

Consequently, an attacker who captures a legitimately signed `StackerDBChunkData` (broadcast over the p2p network, or retrievable from the public HTTP StackerDB read endpoint) from contract A can re-submit the identical bytes (slot_id, slot_version, sig, data) against contract B, where the same signer occupies the same slot_id. Since B's stored slot version is independent of A's, the replayed `slot_version` will typically exceed B's current version, satisfying the `StaleChunk`/`TooManySlotWrites` checks, and the signature check succeeds because it never encoded which contract it belonged to.

### Impact Explanation
This is an unauthenticated write of forged-context data into a StackerDB replica that then propagates network-wide via the normal StackerDB chunk-gossip mechanism (`try_replace_chunk` → broadcast to peers replicating that DB). The write is not "signed by the wrong key" (which the code already rejects via `BadSlotSigner`) — it is a validly-signed message accepted outside its intended contract/lane, corrupting a signer's message-lane state with content the signer never intended for that lane (e.g. an old BlockResponse chunk injected into a state-machine-update lane). Any consumer that trusts "signed by signer X in slot Y" as sufficient authorization for lane Y (rather than separately re-validating message-type/lane match, which today is enforced only client-side) is at risk of processing spoofed or stale cross-lane data. This matches the "network-wide propagation of forged data" / unauthorized write category.

### Likelihood Explanation
Low difficulty, matching the original report's "Difficulty: Low" rating. The attacker needs no privileged key or admin role — only to observe one previously broadcast, validly signed chunk (StackerDB traffic and the `/v2/stackerdb/.../chunks` endpoint are both attacker-observable) and re-submit it against a different, but sibling, contract where the version counter is behind.

### Recommendation
Short term: include the StackerDB's contract identifier (or a chain/network-scoped domain tag analogous to `chainID`) in `SlotMetadata::auth_digest()`, e.g. `hasher.update(contract_id.serialize())`, so a signature is only valid for the exact StackerDB it was created for. Update `sign()`/`verify()` call sites (`try_replace_chunk`, `validate_received_chunk`, etc.) to pass and check the contract identifier as part of the digest rather than only as a lookup key for the expected signer.

Long term: audit all signature schemas in the repo for missing domain separation (network id, contract id, epoch/chain-tip binding) to ensure a signature can't be replayed outside the exact context it was produced for.

### Proof of Concept
1. Configure two `.signers-{set}-X` and `.signers-{set}-Y` boot contracts for the same reward cycle/signer set (both exist by default per [6](#0-5) ), where signer S occupies `slot_id = k` in both.
2. Have signer S sign and push a legitimate `StackerDBChunkData{slot_id: k, slot_version: v, data: D}` into contract X (observable via p2p gossip or the public `/v2/stackerdb/<X>/chunks` endpoint).
3. As an unauthenticated attacker, take the exact same `StackerDBChunkData` bytes and POST/gossip them against contract Y at slot k, choosing a `slot_version` greater than Y's currently stored version for slot k (trivially satisfied for an idle/low-traffic lane).
4. Observe that `SlotMetadata::verify()` in `libstackerdb/src/libstackerdb.rs` succeeds (digest only covers slot_id/slot_version/data_hash) and `try_replace_chunk` in `stackslib/src/net/stackerdb/db.rs` accepts and stores/broadcasts the chunk under contract Y, even though S never authorized writing this payload to Y.

    fn auth_digest(&self) -> Sha512Trunc256Sum {
