### Title
Unauthenticated event-listener HTTP endpoints allow forged signer/StackerDB/burn-block events to be injected into the `stacks-signer` — (File: libsigner/src/events.rs)

### Summary
The `SignerEventReceiver` in `libsigner/src/events.rs` opens an HTTP server (bound, per documented configuration, to `0.0.0.0:<port>`) that accepts unauthenticated `POST` requests on `/stackerdb_chunks`, `/proposal_response`, `/new_burn_block`, and `/new_block`, and directly deserializes and forwards their bodies into the signer's runloop as trusted events, with no `Authorization` check anywhere in the receive path.

### Finding Description
`SignerEventReceiver::next_event` dispatches based solely on the request URL and method, with no authentication check: [1](#0-0) 

`process_event` reads the raw body, JSON-deserializes it into the target event type, and converts it into a `SignerEvent` without any origin verification: [2](#0-1) 

By contrast, the node-side endpoints that receive privileged writes from a signer (`/v3/block_proposal`, `/v3/blocks/upload/?broadcast=1`, fast-call-read-only) explicitly gate on a configured `auth` token compared against the `authorization` header: [3](#0-2) 

No equivalent check exists on the signer's event listener. The documentation frames `auth_token`/`auth_password` as securing "the communication channel between this node and a connected `stacks-signer` instance" and explicitly ties it to `/v3/block_proposal`, but it is never applied to the signer's own inbound HTTP listener: [4](#0-3) 

Sample configs confirm the signer's listener is meant to be reachable, with `endpoint = "0.0.0.0:30000"` bound on all interfaces: [5](#0-4) 

Within `StackerDBChunksEvent` processing, chunk authenticity is derived only from `chunk.recover_pk()`, i.e., whichever public key recovers from the (attacker-supplied) signature — there is no check in this ingestion path that the recovered key belongs to a registered signer for that StackerDB slot (that check exists only on the node's own StackerDB replication path in `stackslib/src/net/stackerdb/mod.rs::validate_received_chunk`, which is not invoked here): [6](#0-5) 

This is the same bug class as the reported advisory: a network-reachable, unauthenticated endpoint accepts attacker-controlled data and treats it as authoritative internal state (forged `StackerDBChunksEvent`/signer messages, forged `BlockValidateResponse`, forged `BurnBlockEvent`/`NewBlock`), exactly mirroring the "connect and gain a valid session with no credentials, then invoke privileged operations" pattern from the LinkDave advisory.

### Impact Explanation
An attacker with network access to the signer's event port can:
- Inject forged `SignerEvent::SignerMessages` (via `/stackerdb_chunks`) purporting to originate from any signer identity recoverable from an attacker-chosen signature, feeding false peer-signer state into the local signer's decision logic.
- Inject forged `BlockValidateResponse` (via `/proposal_response`) and forged burn-block/new-block events, which can desynchronize or corrupt the signer's view of chain/tenure state.
This is an unauthenticated write into a security-critical component's internal event stream — matching the Critical-tier criteria in scope ("unauthenticated/unauthorized write to state ... network-wide propagation of forged data").

### Likelihood Explanation
The signer listener is documented and commonly deployed bound to `0.0.0.0`, and reaching it requires no credentials, session, or prior interaction — only network access to the configured port. Exploitation requires crafting a JSON POST body, which is low effort.

### Recommendation
Add an authentication check (reusing the same `auth_token`/`auth_password` mechanism already used for the node's `/v3/block_proposal` endpoint) to `SignerEventReceiver::next_event` before processing any event body, rejecting requests lacking a valid `Authorization` header. Additionally, for `StackerDBChunksEvent`, validate that the recovered signer key corresponds to a registered/expected signer for the given contract/slot before treating the message as authoritative, mirroring `validate_received_chunk` in `stackslib/src/net/stackerdb/mod.rs`.

### Proof of Concept
1. Configure/start a `stacks-signer` per `sample/conf/signer/mainnet-signer-conf.toml` with `endpoint = "0.0.0.0:30000"`.
2. From a remote host with network access to port 30000, send:
```
POST /stackerdb_chunks HTTP/1.1
Host: <signer-ip>:30000
Content-Type: application/json
Content-Length: <len>

{"contract_id": ..., "modified_slots": [{"slot_id":0,"slot_version":1,"sig": <attacker-signed>, "data": <forged SignerMessage>}]}
```
No `Authorization` header is required or checked (confirmed by `next_event`/`process_event` in `libsigner/src/events.rs`); the request is accepted, deserialized, and forwarded to the signer runloop as a legitimate `SignerEvent::SignerMessages`, as demonstrated by the equivalent unauthenticated flow in `libsigner/src/tests/mod.rs::test_simple_signer`.

fn process_event<T, E>(mut request: HttpRequest) -> Result<SignerEvent<T>, EventError>
where
    T: SignerEventTrait,
    E: serde::de::DeserializeOwned + TryInto<SignerEvent<T>, Error = EventError>,
{
    let mut body = String::new();

    if let Err(e) = request.as_reader().read_to_string(&mut body) {
        error!("Failed to read body: {:?}", &e);
        ack_dispatcher(request);
        return Err(EventError::MalformedRequest(format!(
            "Failed to read body: {:?}",
            e
        )));
    }
    // Regardless of whether we successfully deserialize, we should ack the dispatcher so they don't keep resending it
    ack_dispatcher(request);
    let json_event: E = serde_json::from_slice(body.as_bytes())
        .map_err(|e| EventError::Deserialize(format!("Could not decode body to JSON: {:?}", e)))?;

    let signer_event: SignerEvent<T> = json_event.try_into()?;

    Ok(signer_event)
}
