### Title
Protocol swap fee can be bypassed by using paired `Transfer` intents instead of `TokenDiff` - ([File: contracts/defuse/core/src/intents/tokens.rs])

### Summary
The intents contract charges a protocol fee only inside `TokenDiff::execute_intent`, on the negative ("token_in") side of a matched trade. The `Transfer` intent, which moves tokens between two accounts inside the same contract, never computes or collects any fee. Because a `Transfer` can move any token to any other account with no counter-asset requirement, two parties can achieve the exact same economic outcome as a `TokenDiff`-matched swap — token A moves from party 1 to party 2, token B moves from party 2 to party 1 — using two `Transfer` intents bundled into one `execute_intents` call, while paying zero protocol fee. This is the same bug class as the mStable `redeemMasset()` report: a fee is enforced on one path used to change asset composition (`TokenDiff`), but not on a functionally equivalent path (`Transfer`) that achieves the same swap result.

### Finding Description
`TokenDiff::execute_intent` computes and collects the protocol fee only on negative deltas: [1](#0-0) 

By contrast, `Transfer::execute_intent` only debits the sender and credits the receiver — it never touches `engine.state.fee()` or `fees_collected`: [2](#0-1) 

Both intent types are dispatched from the same `Intent` enum and executed synchronously within a single `execute_intents`/`execute_signed_intents` call: [3](#0-2) 

Since a `Transfer` places no constraint requiring the receiver to send anything back, two counterparties (e.g., a "user" and a "solver", or two colluding accounts) can independently sign one `Transfer` intent each — user sends token A to solver, solver sends token B to user — and submit both signed payloads together via `execute_intents(signed: Vec<MultiPayload>)`: [4](#0-3) 

This produces an atomic bilateral swap of token A for token B with the same net effect as a `TokenDiff`-based swap, but without going through the fee-charging code path at all. The equality that should hold — `fees_owed_on_swap(A↔B) == fees_collected(A↔B)` — is broken: fees owed under the protocol's fee model for exchanging one asset for another are zero when the exchange is executed as two `Transfer` intents instead of a `TokenDiff`.

### Impact Explanation
This falls under "fees bypassed or over-collected" in the Critical impact bucket. The protocol's fee (and the DAO/fee-collector's revenue) is designed to be charged on token swaps. Any two parties who can agree off-chain on a price (functionally identical to solver/RFQ matching that normally goes through `TokenDiff`) can settle their trade with paired `Transfer` intents and pay zero fee, permanently depriving the fee collector of revenue on that trade with no restriction on repetition or trade size.

### Likelihood Explanation
No privileged role, relayer key, or victim key is required — any two ordinary accounts holding balances in the intents contract can construct and co-sign this pattern themselves (e.g. a market maker offering "fee-free swaps" off the order-matching path). The only requirement is that both parties are willing counterparties, which is trivially satisfiable by a single actor controlling two accounts, or by a market-maker service advertising this route to any user.

### Recommendation
Charge the protocol fee inside `Transfer::execute_intent` as well when moving certain token types, or restrict `Transfer` to strictly non-swap semantics (e.g., only permitting transfers within a single signer's own set of accounts, or disallowing bundling of independently-signed `Transfer` intents from different signers whose deltas net to a token-for-token exchange). Alternatively, compute fees at the batch level across the whole `MultiPayload` set based on net per-account, per-token deltas, so any negative delta on a token (regardless of whether it came from `TokenDiff` or `Transfer`) is subject to the same fee.

### Proof of Concept
1. User and Solver both hold balances in the intents contract for token A and token B respectively (via prior deposit).
2. User signs a `Transfer` intent: `receiver_id = solver`, `tokens = {A: 100}`.
3. Solver signs a `Transfer` intent: `receiver_id = user`, `tokens = {B: 200}`.
4. Both signed payloads are submitted together in one `execute_intents` call.
5. Result: User ends up with -100 A, +200 B; Solver ends up with +100 A, -200 B — identical to a `TokenDiff`-matched swap of A for B — but `fees_collected` in `TokenDiff::execute_intent` is never invoked, so the fee collector receives nothing, whereas the same swap executed via `TokenDiff` would have charged `Self::token_fee(...).fee_ceil(amount)` on the negative deltas as shown at [5](#0-4) .

impl ExecutableIntent for Transfer {
    fn execute_intent<S, I>(
        self,
        sender_id: &AccountIdRef,
        engine: &mut Engine<S, I>,
        intent_hash: [u8; 32],
    ) -> Result<()>
    where
        S: State,
        I: Inspector,
    {
        if sender_id == self.receiver_id || self.tokens.is_empty() {
            return Err(DefuseError::InvalidIntent);
        }

        engine
            .inspector
            .on_event(DefuseEvent::Transfer(Cow::Borrowed(
                [MaybeIntentEvent::new_intent(
                    AccountEvent::new(sender_id, TransferEvent::from(&self)),
                    intent_hash,
                )]
                .as_slice(),
            )));

        engine
            .state
            .internal_sub_balance(sender_id, self.tokens.clone())?;
        engine
            .state
            .internal_add_balance(self.receiver_id.clone(), self.tokens.clone())?;

        if let Some(mut notification) = self.notification {
            notification.min_gas = Some(
                notification
                    .min_gas
                    .unwrap_or(MT_ON_TRANSFER_GAS_DEFAULT)
                    .max(MT_ON_TRANSFER_GAS_MIN),
            );

            engine
                .state
                .notify_on_transfer(sender_id, self.receiver_id, self.tokens, notification);
        }

        Ok(())
    }

impl ExecutableIntent for Intent {
    fn execute_intent<S, I>(
        self,
        signer_id: &AccountIdRef,
        engine: &mut Engine<S, I>,
        intent_hash: [u8; 32],
    ) -> Result<()>
    where
        S: State,
        I: Inspector,
    {
        match self {
            Self::AddPublicKey(intent) => intent.execute_intent(signer_id, engine, intent_hash),
            Self::RemovePublicKey(intent) => intent.execute_intent(signer_id, engine, intent_hash),
            Self::Transfer(intent) => intent.execute_intent(signer_id, engine, intent_hash),
            Self::FtWithdraw(intent) => intent.execute_intent(signer_id, engine, intent_hash),
            Self::NftWithdraw(intent) => intent.execute_intent(signer_id, engine, intent_hash),
            Self::MtWithdraw(intent) => intent.execute_intent(signer_id, engine, intent_hash),
            Self::NativeWithdraw(intent) => intent.execute_intent(signer_id, engine, intent_hash),
            Self::StorageDeposit(intent) => intent.execute_intent(signer_id, engine, intent_hash),
            Self::TokenDiff(intent) => intent.execute_intent(signer_id, engine, intent_hash),
            Self::SetAuthByPredecessorId(intent) => {
                intent.execute_intent(signer_id, engine, intent_hash)
            }
            Self::AuthCall(intent) => intent.execute_intent(signer_id, engine, intent_hash),
            #[cfg(feature = "imt")]
            Self::ImtMint(intent) => intent.execute_intent(signer_id, engine, intent_hash),
            #[cfg(feature = "imt")]
            Self::ImtBurn(intent) => intent.execute_intent(signer_id, engine, intent_hash),
        }
    }
}
