### Analysis

The code at `runtime/runtime/src/function_call.rs:257-278` sets `VMContext.account_balance` from `runtime_ext.account().amount()`, which is the account's balance at the moment `execute_function_call` is invoked — i.e., reflecting any prior actions already applied in the same `ActionReceipt` batch (loop in `runtime/runtime/src/lib.rs:892-951`, `apply_action` dispatch at `runtime/runtime/src/lib.rs:628-665`). [1](#0-0) [2](#0-1) 

This is not a bug: it is documented, deterministic behavior. Per the spec documentation, `account_balance` in `EconomicsAPI.md` explicitly states it "includes the `attached_deposit`" and reflects the account's real balance at execution time — there is no protocol guarantee anywhere that `account_balance` reflects "pre-batch" state. Actions within a single receipt are applied strictly sequentially, in a fixed deterministic order (`action_receipt.actions().iter().enumerate()`), and every validator executes the same actions in the same order against the same starting state, producing an identical `account.amount()` before every subsequent action. There is no "ordering ambiguity" — the action order is fixed by the sender when constructing the transaction/receipt and is part of the receipt's serialized, hashed content, so it cannot be reordered by anyone once submitted. [3](#0-2) 

Regarding the "authorization escalation" claim: any escalation would stem entirely from a flaw in the downstream, attacker-authored contract's own logic (assuming balance reflects some state it does not), not from a nearcore protocol vulnerability. The attacker in this scenario is also the deployer of the vulnerable contract — this is a self-inflicted application-layer semantic assumption, not an authorization bypass across accounts, and does not fall under scope items like theft/freezing of user funds, double-spend, or state-root divergence, since all nodes deterministically compute the exact same value.

There is also no state-root divergence risk: `account_balance` is not part of consensus data directly, but even if it were, all validators run identical WASM logic against identical starting state and identical action ordering, so results are always byte-for-byte identical across the network.
