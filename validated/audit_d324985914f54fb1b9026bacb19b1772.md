## Title
`AccountPermissionUpdateActuator` allows account permissions (owner/active) to be set to the burn/zero address, permanently freezing account funds - (File: `actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java`)

### Summary
The Sherlock report flags a `GovernorBravoDelegator` constructor that fails to reject a zero-address `timelock_`, letting `admin` become permanently unset/uncontrollable. The equivalent weakness exists in `AccountPermissionUpdateActuator`, where a signed `AccountPermissionUpdateContract` transaction can (re)configure an account's `owner`, `witness`, and `active` permissions with key addresses that pass only a format check, not a "not the burn/zero address" check.

### Finding Description
`AccountPermissionUpdateActuator.checkPermission()` validates each `Key` in a permission only for format validity and positive weight: [1](#0-0) 
The address check delegates to `DecodeUtil.addressValid`, which only verifies length (21 bytes) and the `0x41` prefix byte — it never rejects the all-zero address `0x410000000000000000000000000000000000000` (or any other address for which no private key is known): [2](#0-1) 

Because `validate()` in the actuator reuses this same `checkPermission` for the mandatory `owner` permission and every mandatory `active` permission (an update always requires `owner` + at least one `active` permission), an owner can submit a self-signed `AccountPermissionUpdateContract` that sets the sole key (or all keys meeting the threshold) of their `owner`/`active` permission to the zero address: [3](#0-2) 
Execution then persists these permissions directly onto the account with no additional sanity check: [4](#0-3) 

Since nobody controls the private key for the zero/burn address, any subsequent transaction requiring that permission's threshold (transfers via `active` permission, or further permission changes via `owner` permission) can never collect enough valid signatures to meet the threshold.

### Impact Explanation
If the `active` permission (the one gating asset-moving contracts, e.g. `TransferContract`) is set this way, the account's TRX/TRC10/TRC20 balances become permanently unspendable — a direct case of permanent freezing of funds. If the `owner` permission is bricked instead, the account can never again update its own permission structure, permanently locking out any future recovery. This mirrors exactly the impact class in the reference report: an unvalidated "admin"/authority field ends up pointing at an address nobody can ever control.

### Likelihood Explanation
This is reachable by any single signed transaction from the account owner (no special privilege, an unprivileged transaction broadcaster with a normal account can trigger it), and the actuator's validation logic provides no denylist or minimum-safety guard against zero/burn addresses, keys equal to well-known unspendable addresses, or all-key thresholds that could realistically never be satisfiable. This can occur from user misconfiguration (analogous to a deployer misconfiguring a constructor) or be leveraged in a phishing/social-engineering flow to trick a user into "updating" their permissions to an address the attacker claims is theirs.

### Recommendation
In `AccountPermissionUpdateActuator.checkPermission()`, explicitly reject keys equal to the zero address (and other well-known unspendable/blackhole addresses) for `owner` and `active` permission types, in addition to the existing format/weight/threshold checks.

### Proof of Concept
1. An account owner (with multi-sign enabled, `AllowMultiSign == 1`) crafts an `AccountPermissionUpdateContract`:
   - `owner` permission: single `Key{address: 0x4100000000000000000000000000000000000000, weight: 1}`, `threshold: 1`.
   - `actives`: single `Key{address: 0x4100000000000000000000000000000000000000, weight: 1}`, `threshold: 1`.
2. Sign and broadcast with the account's current valid key (passes existing signature checks against the *current* permissions).
3. `AccountPermissionUpdateActuator.validate()` passes because `DecodeUtil.addressValid` only checks format/prefix, threshold/weight math is internally consistent.
4. `execute()` persists the new permissions via `account.updatePermissions(...)`.
5. Any subsequent `TransferContract` (needs `active` permission) or another `AccountPermissionUpdateContract` (needs `owner` permission) can never be signed, since no one holds the private key for the zero address — funds and account control are permanently frozen.
