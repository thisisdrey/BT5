### Title
Missing wallet-contract single point of failure freezes all ETH-implicit account funds - (File: runtime/runtime/src/actions.rs)

### Summary
The report's bug class is a single external dependency that many mint/redeem operations rely on, whose unavailability (pause, cap, retirement) permanently DoSes user funds with no fallback. The nearcore analog is the `EthImplicitGlobalContract` design: every ETH-implicit account is created pointing at one shared global contract identified by a hardcoded hash (`eth_wallet_global_contract_hash`), and that account can *only* ever be used through that global contract's code, with no recovery path if the code is absent from state.

### Finding Description
When any unprivileged user sends a `Transfer` action to an ETH-implicit account id (`0x` + 40 hex chars), `action_implicit_account_creation_transfer` creates the account with `AccountContract::Global(global_contract_hash)`, where `global_contract_hash` is a hardcoded per-chain constant returned by `eth_wallet_global_contract_hash` [1](#0-0) [2](#0-1) . This creation path requires no proof that the referenced global contract code hash is actually deployed in state — it is unconditionally hard-coded per `chain_id`.

Documented account semantics state the account "can only be used by calling the methods of the Wallet Contract... It cannot be deleted, nor can a full access key be added" [3](#0-2) . `RuntimeContractIdentifier::resolve` always treats such an account's contract as `Global { code_hash }`, i.e. code is looked up in the shared `TrieKey::GlobalContractCode` store, never a per-account fallback [4](#0-3) .

If the code for that global hash is not present in the trie (e.g., on a fresh/non-production chain_id before someone deploys it with `DeployGlobalContractAction`, or, more importantly, if the well-known code is ever pruned/garbage-collected/never distributed to a particular shard), any attempt to call the wallet contract's `rlp_execute` on the account resolves to `VMRunnerError::ContractCodeNotPresent`, which is converted into a graceful `FunctionCallError::CompilationError(CodeDoesNotExist)` NOP outcome rather than a fatal/consensus error [5](#0-4) . Since ETH-implicit accounts cannot receive a full access key and cannot be deleted, the wallet-contract call is the *only* channel through which the account's balance can ever be moved. With no code at that hash, this channel is permanently non-functional for that account: the deposited/transferred NEAR is trapped forever with no admin override, no manual rebalancing path, and no alternate execution route — mirroring the reported single-point-of-failure pattern where `_update()`'s sole reliance on Aave/Compound blocks all mint/redeem.

Unlike the DSU report where any user could still theoretically wait for the dependency to recover, here the shared global contract hash is a compile-time constant baked into the binary (`eth_wallet_global_contract_hash`); on non-production chains (`localnet`/test/custom chain ids) it resolves from whatever WASM happens to be compiled into the binary at genesis time and must be independently deployed as a global contract by *someone* before it is usable, since the runtime does not deploy or guarantee it exists automatically.

### Impact Explanation
Any NEAR value sent to (or already residing in) an ETH-implicit account whose corresponding global wallet-contract code hash is missing from state becomes permanently frozen: it cannot be withdrawn, transferred, or otherwise recovered by the private-key holder, the relayer, or governance, because ETH-implicit accounts structurally forbid `AddKey`/`DeleteAccount`/local code deployment and their only usable path is through the (potentially missing) global contract's `rlp_execute`. This is a permanent freezing-of-funds condition reachable by an ordinary user simply by transferring to a valid ETH-implicit account id.

### Likelihood Explanation
On mainnet/testnet, the wallet-contract global hash is hard-coded to values that node operators are expected to have deployed prior to `EthImplicitGlobalContract` activation, so the window is narrow (and this activation-ordering dependency is itself a systemic single point of failure that this codebase does not enforce with an on-chain invariant). The likelihood is materially higher for any non-production/custom `chain_id` (the `_ => LOCALNET...` branch), where the hash is derived from whatever binary-embedded code exists and there is no protocol-level guarantee that this code has been deployed as a global contract before users start funding ETH-implicit accounts on that chain — any user can trigger account creation via `send_money` before the operator deploys the global contract.

### Recommendation
Add a consensus-visible guard so that ETH-implicit account creation (or, better, the protocol-feature activation) fails/no-ops instead of silently creating an unusable account when `eth_wallet_global_contract_hash` code is not present in state, and/or bundle the wallet-contract global-contract deployment atomically with (or prior to and enforced by) the `EthImplicitGlobalContract` feature activation so it is never possible to create a `Global`-contract-referencing ETH-implicit account whose code does not exist. Additionally, consider an escape hatch (e.g., allowing beneficiary recovery via `refund_to`-style mechanism or a protocol-governed fallback) so an account bricked by a missing/garbage-collected global contract is not permanently unrecoverable.

### Proof of Concept
Not executed (no live sandbox); the path is demonstrated by code reading:
1. `action_implicit_account_creation_transfer` unconditionally assigns `AccountContract::Global(eth_wallet_global_contract_hash(chain_id))` to any ETH-implicit account created by a plain `Transfer`, with no check that this hash exists in the trie [1](#0-0) .
2. `RuntimeContractIdentifier::resolve` always routes such accounts through the `Global` code path [4](#0-3) .
3. If that code hash's trie entry is absent, `execute_function_call` returns a graceful `CodeDoesNotExist` NOP rather than erroring the transaction pre-execution, meaning every subsequent `rlp_execute` call on the account fails identically forever [5](#0-4) .
4. Documentation confirms ETH-implicit accounts have no alternate recovery mechanism (no full-access key, no deletion) [3](#0-2) .
