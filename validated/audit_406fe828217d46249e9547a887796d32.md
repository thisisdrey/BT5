### Title
Missing committee feature-gate check (`supportUnfreezeDelay`) in TVM native-contract Delegate/Unfreeze processors bypasses a Java-level actuator restriction - (File: `actuator/src/main/java/org/tron/core/vm/nativecontract/UnfreezeBalanceV2Processor.java`, `actuator/src/main/java/org/tron/core/vm/nativecontract/DelegateResourceProcessor.java`)

### Summary
`UnfreezeBalanceV2Actuator` and `DelegateResourceActuator` (the transaction-level entry points, reachable by any signed `UnfreezeBalanceV2Contract`/`DelegateResourceContract`) both require `dynamicStore.supportUnfreezeDelay()` to be enabled before allowing the operation [1](#0-0) [2](#0-1) . However, the corresponding TVM native-contract (precompile) processors that implement the same operation when invoked from inside a smart contract — `UnfreezeBalanceV2Processor.validate()` and `DelegateResourceProcessor.validate()` — never perform this check [4](#0-3) [3](#0-2) . This mirrors the report's bug class exactly: one code path enforces a committee-controlled feature toggle, a second, functionally-equivalent code path used to perform the same state-changing action omits it.

### Finding Description
`ProposalUtil` treats `UNFREEZE_DELAY_DAYS` (which backs `supportUnfreezeDelay()`) as a distinct, committee-gated chain parameter [5](#0-4) , and `DelegateResourceActuator`/`UnfreezeBalanceV2Actuator`/`UnDelegateResourceActuator`/`WithdrawExpireUnfreezeActuator`/`FreezeBalanceV2Actuator` all reference `supportUnfreezeDelay()` in their `validate()` methods as a prerequisite gate for the FreezeV2/DelegateResource feature set. This confirms the feature is intended to be off by default until the committee explicitly turns it on, exactly analogous to the `self_service` toggle in the Move contract.

The TVM native-contract processors (`org.tron.core.vm.nativecontract.DelegateResourceProcessor` and `UnfreezeBalanceV2Processor`), which are invoked when a deployed smart contract calls the corresponding native/precompiled resource-management function, reimplement most of the actuator's validation logic (`supportDR()`, balance checks, unfreeze-count limits, `supportAllowNewResourceModel()`) but never call `supportUnfreezeDelay()`. Because these processors are a separate code path from the actuators and do not delegate to the actuator's `validate()` method, the omission is not caught anywhere else in the validation chain that I was able to locate.

### Impact Explanation
If `UNFREEZE_DELAY_DAYS`/`supportUnfreezeDelay` has not yet been approved by the committee (i.e., the FreezeV2 delay/delegate-resource feature is disabled), a smart contract could still invoke the native `delegateResource`/`unfreezeBalanceV2` operations through TVM, bypassing the intended feature gate that the corresponding actuators enforce for ordinary transactions. This is an unauthorized account operation: it allows delegating or unfreezing FreezeV2 balances (and mutating `FrozenV2`/`UnfrozenV2` lists, total net/energy weight, and vote counts) while the network has not yet activated support for this resource model, potentially producing state inconsistent with pre-FreezeV2-delay invariants relied upon elsewhere in the codebase (e.g., `BandwidthProcessor`/`EnergyProcessor`, which also gate behavior on `supportUnfreezeDelay`).

### Likelihood Explanation
Likelihood depends on whether `UNFREEZE_DELAY_DAYS` is disabled on a given network/chain at the time an attacker deploys and calls a contract that invokes the native delegate/unfreeze functions. On mainnet the flag is very likely already enabled (making this currently low-impact there), but on any private, test, or newly bootstrapped chain, or during the window before the committee approves the proposal, this path is exploitable by any account able to deploy/trigger a smart contract — i.e., an ordinary unprivileged user, matching the report's low-difficulty rating.

### Recommendation
Add `if (!repo.getDynamicPropertiesStore().supportUnfreezeDelay()) { throw new ContractValidateException(...); }` (mirroring the message used in the actuators) to `DelegateResourceProcessor.validate()` and `UnfreezeBalanceV2Processor.validate()`, and audit the other FreezeV2-related native-contract processors (`UnDelegateResourceProcessor`, and any `WithdrawExpireUnfreeze`/`FreezeBalanceV2` native processors) for the same gap so that TVM-invoked native contracts enforce identical committee feature gates as their transaction-actuator counterparts.

On a test chain where `UNFREEZE_DELAY_DAYS` has not been set (i.e., `supportUnfreezeDelay()` returns false), attempt `UnfreezeBalanceV2Actuator`/`DelegateResourceActuator` via a normal transaction and confirm it is rejected with "Not support Delegate resource transaction, need to be opened by the committee" — [6](#0-5) .
