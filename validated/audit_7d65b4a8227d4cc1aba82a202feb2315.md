### Title
Emissions accrued while a rewarded token has zero totalSupply are permanently burned and unrecoverable - (File: contracts/RewardsDistributor.sol)

### Summary
`RewardsDistributor._calculateTokenIndex` advances the token state's `timestamp` even when `token_.totalSupply() == 0`, contributing `_ratio = 0` to the index for the elapsed period. Emissions (`_deltaTimestamps * _speed`) for that interval are silently skipped. Because there is no sweep/recovery function for `rewardToken` in the contract, the reward tokens corresponding to skipped periods remain in the distributor but can never be accrued to or claimed by any account — a direct analog of "stuck emissions for nullified epochs."

### Finding Description
The vulnerable logic is in `contracts/RewardsDistributor.sol:197-212` (`_calculateTokenIndex`):

```solidity
if (_deltaTimestamps > 0 && _speed > 0) {
    uint256 _totalSupply = token_.totalSupply();
    uint256 _tokensAccrued = _deltaTimestamps * _speed;
    uint256 _ratio = _totalSupply > 0 ? _tokensAccrued.wadDiv(_totalSupply) : 0;
    _newIndex = (_supplyState.index + _ratio).toUint224();
    _newTimestamp = block.timestamp.toUint32();
}
```

When `_totalSupply == 0`, `_ratio` is 0 but `_newTimestamp` is still set to `block.timestamp`. `_updateTokenIndex` (lines 271-282) then persists this timestamp, so the emissions that should have been emitted over `_deltaTimestamps` are never reflected in the index — the window is permanently skipped.

This is reachable from public entry points without any privileged role:
- `updateBeforeMintOrBurn(IERC20,address)` (line 175) is callable by anyone ("may be called by anyone to update stored indexes" per its natspec) and calls `_updateTokenIndex`.
- `updateBeforeTransfer` (line 186) and `claimRewards` (line 150) do the same.
- Additionally, every mint/burn/transfer hook on `DepositToken`/`DebtToken` invokes these update functions, so the burn happens automatically on the next user action after supply hits zero.

Reproduction path (unprivileged):
1. Governor configures `tokenSpeeds[msdToken] > 0` (deployed config on mainnet/optimism per `deployments/*/RewardsDistributor.json`).
2. All holders withdraw so `msdToken.totalSupply() == 0` (or the token simply has no deposits yet after being added as a reward token — `_updateTokenSpeed` initializes `index = INITIAL_INDEX` and `timestamp = block.timestamp` even while supply is 0, lines 296-299).
3. Time passes; emissions `speed * elapsed` are notionally allocated.
4. Any EOA calls `RewardsDistributor.updateBeforeMintOrBurn(msdToken, attacker)` — or any deposit/transfer occurs — advancing `timestamp` with zero index delta. The elapsed emissions are burned: they remain as `rewardToken` balance in the contract but no account's index delta will ever capture them.
5. There is no function to recover `rewardToken` from the distributor (no sweep/rescue; `claimRewards` only pays `tokensAccruedOf`), so the tokens are permanently frozen.

### Impact Explanation
Permanent freezing/loss of unclaimed yield. Reward tokens emitted during zero-supply windows are unclaimable by all users and unrecoverable by governance — matching the accepted impact category "theft/freezing of unclaimed yield" / permanent freezing of funds. The amount lost scales with `speed × duration of zero-supply window`.

### Likelihood Explanation
Moderate. Reaching `totalSupply() == 0` on a rewarded `DepositToken`/`DebtToken` requires a full exit (or the window between reward-token registration via `updateTokenSpeed` and first deposit, which is guaranteed to exist since speed is set before/independently of deposits). No attacker privilege is needed — the loss happens on the next index update, which any EOA can trigger via the permissionless `updateBeforeMintOrBurn`. The only mitigation is operational (governor setting speed to 0 before supply empties), which is not enforced on-chain.

### Recommendation
When `totalSupply() == 0` and `speed > 0`, do not advance the stored `timestamp` (i.e., treat the zero-supply period like the `_speed == 0` branch so emissions resume accumulating from the last update once supply returns), or accumulate unassigned emissions into a treasury-recoverable bucket and add a governor sweep function for undistributed `rewardToken` balance. Cite: `contracts/RewardsDistributor.sol` lines 203-211 and the absence of any recovery path alongside `_transferRewardIfEnoughTokens` at lines 248-256.

### Proof of Concept
Hardhat (fork or unit, consistent with `test/RewardDistributor.test.ts` setup):

```typescript
// contracts/RewardsDistributor.sol — zero-supply emissions burn
it('burns emissions during zero totalSupply window', async function () {
  // governor configures speed for a deposit token
  await rewardDistributor.updateTokenSpeed(msdTOKEN1.address, parseEther('1'));

  // token has no supply; fund distributor
  msdTOKEN1.totalSupply.returns(0);
  await vsp.mint(rewardDistributor.address, parseEther('1000'));

  // 100s pass with zero supply -> 100 VSP notionally emitted
  await increaseTimeOfNextBlock(100);

  // anyone (unprivileged) updates index; timestamp advances, index unchanged
  await rewardDistributor.updateBeforeMintOrBurn(msdTOKEN1.address, bob.address);

  // alice deposits -> supply appears
  msdTOKEN1.totalSupply.returns(parseEther('100'));
  msdTOKEN1.balanceOf.whenCalledWith(alice.address).returns(parseEther('100'));
  await rewardDistributor.updateBeforeMintOrBurn(msdTOKEN1.address, alice.address);

  // only emissions AFTER this point accrue; the 100 VSP window is gone
  await increaseTimeOfNextBlock(10);
  await rewardDistributor['claimRewards(address)'](alice.address);

  // alice receives ~10 VSP, not ~110; the ~100 VSP stays locked forever
  expect(await vsp.balanceOf(alice.address)).to.be.lt(parseEther('100'));
  expect(await vsp.balanceOf(rewardDistributor.address)).to.be.gt(parseEther('900'));
  // and there is no function to recover it
});
```
