### Title
Sidechannel-transferred bytes are excluded from `x-gitaly-cost`, letting ordinary clone/fetch requests evade upstream rate limiting - (File: internal/grpc/middleware/costhandler/costhandler.go)

### Summary
The `x-gitaly-cost` trailer is meant to let Rails/Workhorse translate Gitaly's per-RPC resource cost into an `X-Score` header for upstream (Cloudflare) complexity-based rate limiting [6](#0-5) . For the RPCs that actually transfer the most data — `PostUploadPackWithSidechannel`, `SSHUploadPackWithSidechannel`, `SSHUploadPack`, `SSHReceivePack`, `PostReceivePack` — the cost is a fixed static override (`10`) plus a "dynamic" component computed purely from `grpcstats.PayloadBytesStatsFromContext`, which is populated by a gRPC `stats.Handler` that only observes `InPayload`/`OutPayload` events of the gRPC framing itself [7](#0-6) .

### Finding Description
For sidechannel RPCs, the packfile bytes never traverse gRPC message payloads; they are streamed over a raw sidechannel connection obtained via `sidechannel.OpenSidechannel` and written to directly (`conn`), with the gRPC request/response messages being tiny metadata-only wrappers [8](#0-7) . `dynamicCostFromContext` therefore always sees near-zero `InPayloadBytes`/`OutPayloadBytes` for these RPCs, no matter whether the client fetches a 1 KB repo or a 10 GB monorepo, so `computeCost` returns the same fixed value (`10 + 0/1`) in both cases [9](#0-8) . Gitaly does separately track true served bytes via `recordServedBytes`/`CountingWriter` for Prometheus metrics [10](#0-9) , but that data is never fed into the cost trailer computation.

### Impact Explanation
Any ordinary, unprivileged user who can `git clone`/`git fetch` a repository over SSH or smart HTTP triggers RPCs whose reported `x-gitaly-cost` is disproportionately (and constantly) low relative to the true server-side resource consumption (CPU for pack generation, disk I/O, egress bandwidth) once the transfer happens over the sidechannel. Since Workhorse forwards `x-gitaly-cost` directly to the `X-Score` header that feeds Cloudflare's complexity-based rate limiting for exactly these clone/fetch/push RPCs (the doc states "Workhorse reads the `x-gitaly-cost` trailer... Rails is only in the auth path" for Git operations) [11](#0-10) , an attacker can issue a high volume of large, expensive clones/fetches against big repositories while the upstream rate limiter perceives each request as cheap and constant-cost. This directly undermines the DoS-mitigation purpose of the mechanism and enables resource-exhaustion at the innermost Gitaly node with an under-scored signal exported outward, i.e., a DoS-relevant accounting bypass of a resource-limiting handler.

### Likelihood Explanation
High: this requires no privilege beyond issuing ordinary `git clone`/`git fetch` requests, which is the design's expected code path for large-repository transfers (documented explicitly as diverging: "the same cost whether it serves 1 MB or 10 GB") [5](#0-4) . No malicious peer, leaked token, or privileged actor is needed — a normal read-only clone client reliably reproduces the under-counted cost every time.

### Recommendation
Feed the sidechannel byte counters (already computed via `CountingWriter`/`recordServedBytes` in `internal/gitaly/service/ssh/upload_pack.go` and `internal/gitaly/service/smarthttp/upload_pack.go`) into `dynamicCostFromContext`/`computeCost`, e.g., by storing served/received sidechannel byte counts in the request context (similar to `grpcstats.PayloadBytesStats`) and summing them alongside in-band gRPC payload bytes before computing the trailer, rather than relying solely on the gRPC `stats.Handler`, which is blind to out-of-band sidechannel traffic.

### Proof of Concept
1. As an unprivileged user with read access to a large repository (e.g., several GB), perform `git clone` over SSH (`SSHUploadPackWithSidechannel`) or HTTP (`PostUploadPackWithSidechannel`).
2. Observe the `x-gitaly-cost` gRPC trailer returned by Gitaly — it stays at the static override value (`10`, plus at most the negligible in-band grpc control-message bytes divided by `1<<20`), regardless of the multi-GB pack transferred over the sidechannel [12](#0-11) .
3. Repeat the clone/fetch many times in a loop (or in parallel) against the same or different large repositories.
4. Compare Prometheus `uploadPackServedBytesMetrics` (or `BurdenMonitor` CPU/duration data, per `doc/load-management-architecture.md`) against the `X-Score` values Workhorse derives from `x-gitaly-cost` for these calls — the externally visible score stays flat and low while actual node resource consumption (CPU, I/O, bandwidth) scales with repository size and request volume, demonstrating that the upstream rate limiter is being fed a signal that does not reflect true cost, allowing repeated expensive clones to bypass Cloudflare's complexity-based throttling.

```go
// computeCost returns the cost score for a completed RPC. It combines a static
// base cost for the RPC type with a dynamic component from actual bytes
// transferred, read from the RPCEntry in context.
func computeCost(ctx context.Context, fullMethod string) int {
	static := staticCostForMethod(fullMethod)
	dynamic := dynamicCostFromContext(ctx)
	return static + dynamic
}

// staticCostForMethod returns the static cost weight for the given full method
// name. It first checks per-RPC overrides, then falls back to a default based
// on the method's operation type from the proto registry.
func staticCostForMethod(fullMethod string) int {
	if cost, ok := staticCostOverrides[fullMethod]; ok {
		return cost
	}

	methodInfo, err := protoregistry.GitalyProtoPreregistered.LookupMethod(fullMethod)
	if err != nil {
		return defaultUnknownCost
	}

	switch methodInfo.Operation {
	case protoregistry.OpAccessor:
		return defaultAccessorCost
	case protoregistry.OpMutator:
		return defaultMutatorCost
	case protoregistry.OpMaintenance:
		return defaultMaintenanceCost
	default:
		return defaultUnknownCost
	}
}

// dynamicCostFromContext computes the dynamic cost contribution from payload
// bytes tracked by the grpcstats.PayloadBytes stats handler.
func dynamicCostFromContext(ctx context.Context) int {
	stats := grpcstats.PayloadBytesStatsFromContext(ctx)
	if stats == nil {
		return 0
	}
	totalBytes := stats.InPayloadBytes + stats.OutPayloadBytes

	return int(math.Ceil(float64(totalBytes) / float64(byteCostDivisor)))
```

```go
func (s *server) PostUploadPackWithSidechannel(ctx context.Context, req *gitalypb.PostUploadPackWithSidechannelRequest) (*gitalypb.PostUploadPackWithSidechannelResponse, error) {
	repoPath, gitConfig, err := s.validateUploadPackRequest(ctx, req)
	if err != nil {
		return nil, structerr.NewInvalidArgument("%w", err)
	}

	var sidechannelRetryableError sidechannel.RetryableError
	conn, err := sidechannel.OpenSidechannel(ctx)
	if err != nil {
		if errors.As(err, &sidechannelRetryableError) {
			// Clients of PostUploadPackWithSidechannel are configured to retry the RPC upon receiving
			// Unavailable, so it should be OK to return it in this case.
			//nolint:gitaly-linters
			return nil, structerr.NewUnavailable("open sidechannel: %w", err)
		}
		return nil, structerr.NewInternal("open sidechannel: %w", err)
	}
	defer conn.Close()

	stats, err := s.runUploadPack(ctx, req, repoPath, gitConfig, conn, conn)
	if err != nil {
		return nil, structerr.NewInternal("running upload-pack: %w", err)
	}

	if err := conn.Close(); err != nil {
		return nil, structerr.NewInternal("close sidechannel connection: %w", err)
	}

	return &gitalypb.PostUploadPackWithSidechannelResponse{
		PackfileNegotiationStatistics: stats.ToProto(),
	}, nil
}
```

```markdown
### RPC Cost Score (`x-gitaly-cost`)

Gitaly returns a cost score for each RPC as a gRPC response trailer.
Gitaly has the most context about the actual cost of each RPC, making it the right

> Self-managed deployments can use the same header with any upstream
> rate limiter or ignore it.
```
