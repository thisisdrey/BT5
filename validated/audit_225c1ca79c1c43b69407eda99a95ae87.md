Based on my investigation, the ETH-implicit Wallet Contract's `rlp_execute_callback` function sets `self.has_in_flight_tx = false` as the *first* line — before doing any work that could exceed gas. This means that even if a hardcoded gas constant like `RLP_EXECUTE_CALLBACK_GAS` (5 Tgas) becomes insufficient in the future, the runtime's out-of-gas panic occurs *inside* the function-call execution, and per NEAR's execution model a failing `FunctionCall` receipt rolls back **all** state changes for that receipt [1](#0-0) , including the `self.has_in_flight_tx = false` write that already happened in-memory during that call. Since `has_in_flight_tx` was set to `true` by the *previous* step (e.g., `rlp_execute` or `nep_141_storage_balance_callback`) and already committed to state before the callback promise was even created [2](#0-1) , a callback that panics due to insufficient hardcoded gas would leave `has_in_flight_tx = true` permanently, since `rlp_execute` refuses new transactions whenever this flag is `true` [3](#0-2) .

The hardcoded gas constants in question are:

```
const NEP_141_STORAGE_DEPOSIT_GAS: Gas = Gas::from_tgas(5);
const NEP_141_STORAGE_BALANCE_OF_GAS: Gas = Gas::from_tgas(5);
const REGISTRAR_LOOKUP_GAS: Gas = Gas::from_tgas(5);
const RLP_EXECUTE_CALLBACK_GAS: Gas = Gas::from_tgas(5);
const ADDRESS_CHECK_CALLBACK_GAS: Gas = Gas::from_tgas(5).saturating_add(RLP_EXECUTE_CALLBACK_GAS);
const NEP_141_STORAGE_BALANCE_CALLBACK_GAS: Gas = Gas::from_tgas(5)
    .saturating_add(NEP_141_STORAGE_DEPOSIT_GAS)
    .saturating_add(RLP_EXECUTE_CALLBACK_GAS);
``` [4](#0-3) 

This is architecturally analogous to Solidity's hardcoded `2300`-gas `.transfer()`: a fixed, statically-chosen gas budget attached to a follow-up call/callback that assumes current host-function/action costs, and which could become insufficient if NEAR's gas-cost parameters for cross-contract calls, JSON (de)serialization, or WASM execution rise in the future (via a protocol upgrade to `RuntimeConfig` costs, similar in spirit to `AccountCostIncrease`/NEP-536-style repricing events already seen in this codebase) [5](#0-4) .

However, I was not able to fully verify one crucial link needed to promote this into a hard "permanent freezing of funds" finding: whether an out-of-gas failure specifically occurs *within* `rlp_execute_callback`/`nep_141_storage_balance_callback` execution (as opposed to failing earlier, e.g., at receipt-creation/gas-purchase time, which would instead just fail the whole transaction cleanly without leaving `has_in_flight_tx` stuck). I could not locate host-function gas-metering code confirming that a WASM function that runs out of its attached gas mid-execution triggers a full-receipt rollback that reverts an *already-executed* `self.has_in_flight_tx = false` assignment inside that same function body (as opposed to it never being an issue because the flag write happens as the very first executed instruction, before any further gas is consumed calling into `env::promise_result`/JSON parsing, which is precisely where the gas shortfall would occur). Given `has_in_flight_tx = false` is the first statement in `rlp_execute_callback`, an OOG deep in the same function's later logic (e.g., JSON parsing of a large promise result, or building the next promise) would still roll back that assignment along with the rest of the receipt per the "failure calls `state_update.rollback()`, discarding all state changes from the receipt" rule [1](#0-0) .

Given the residual uncertainty over exact triggering conditions (this requires a future protocol gas-cost increase that specifically outpaces this fixed 5 Tgas budget — an external/speculative precondition, much like the original ENS report's own "if gas costs change in the future" framing that the judges ultimately weighed against), and because I cannot demonstrate today's parameter values already make this exploitable rather than merely theoretically fragile, I'll note this is the closest analog found but present it with the caveat below rather than asserting it as a confirmed, presently-exploitable vulnerability.

### Title
Hardcoded static gas budgets for Wallet Contract cross-contract callbacks could permanently lock the account if future gas-cost repricing exceeds them - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The ETH-implicit account Wallet Contract attaches fixed, hardcoded `Gas` constants (`RLP_EXECUTE_CALLBACK_GAS`, `NEP_141_STORAGE_BALANCE_CALLBACK_GAS`, `ADDRESS_CHECK_CALLBACK_GAS`, each derived from `5 Tgas`) to its own callback promises rather than deriving them from current, governance-adjustable cost parameters [4](#0-3) .

### Finding Description
`rlp_execute` and its intermediate callbacks (`address_check_callback`, `nep_141_storage_balance_callback`) always set `self.has_in_flight_tx = true` before scheduling the next promise, and the final `rlp_execute_callback` is expected to set it back to `false` as its first statement [6](#0-5) . The gas attached to `rlp_execute_callback` is a compile-time constant (`5 Tgas`) baked into the deployed global wallet contract code, not derived from the runtime's current `RuntimeConfig` fee schedule. If host-function or cross-contract-call costs increase in a future protocol version, this fixed budget may become insufficient for the callback to complete, causing the callback receipt to fail with an out-of-gas error and roll back all its state changes — including the reset of `has_in_flight_tx` — per the standard failed-receipt rollback semantics [1](#0-0) .

### Impact Explanation
If `has_in_flight_tx` remains stuck at `true`, `rlp_execute` will permanently reject all further transactions for that account [7](#0-6) , since the contract cannot be redeployed (ETH-implicit accounts cannot have their contract code changed) and there is no owner-callable "unstick" method. This would permanently freeze the user's ability to transact from that ETH-implicit account (though funds could still be received via plain `Transfer`, since `Transfer` doesn't invoke contract code).

### Likelihood Explanation
Low today, since current mainnet gas-cost parameters give ample headroom under `5 Tgas` for the trivial logic in these callbacks. It would only become likely following a future protocol-level gas-repricing change (analogous to `AccountCostIncrease`/NEP-536) that specifically increases the per-call/host-function costs enough to exceed 5 Tgas, and only for wallets that happen to be mid-transaction at the moment that repricing activates or hit the more complex NEP-141/ERC-20 emulation paths with larger promise-result payloads.

### Recommendation
Avoid hardcoding fixed `Gas` constants for the contract's own callbacks; instead, either compute the attached gas dynamically from `env::prepaid_gas()` remaining balance (as is already done for the user-facing minimum-gas check in `validate_tx_relayer_data`, see `env::prepaid_gas()` usage) [8](#0-7) , or add generous headroom/margin and a governance-controlled path to redeploy/upgrade the global wallet contract's gas constants if protocol costs change.

### Proof of Concept
Not independently reproducible from the indexed code alone — this requires simulating a future `RuntimeConfig` gas-cost increase (not present in the current 2.13.0 parameter set) that pushes real execution cost of `rlp_execute_callback`/`nep_141_storage_balance_callback` above their hardcoded `5 Tgas` budgets, then observing that a mid-flight `rlp_execute` transaction leaves `has_in_flight_tx = true` after the callback's `FunctionCall` receipt fails with `FunctionCallError::HostError(GasExceeded)`. I could not fully confirm this sequence-of-rollback behavior against actual VM gas-metering code within the available context, so this should be validated with a live/sandboxed repro (e.g. via a modified `RuntimeConfig` with inflated wasm/host costs) before treating it as confirmed.
