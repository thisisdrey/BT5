### Title
Witnesses can approve/disapprove a proposal after it has already been resolved (APPROVED/DISAPPROVED) - (File: `actuator/src/main/java/org/tron/core/actuator/ProposalApproveActuator.java`)

### Summary
`ProposalApproveActuator.validate()` only rejects a `ProposalApproveContract` when the proposal is expired (by wall-clock `latestBlockHeaderTimestamp` vs `expirationTime`) or `CANCELED`. It never checks whether the proposal's `State` has already been finalized to `APPROVED` or `DISAPPROVED` by `ProposalController`. This mirrors the reported Aragon `Voting.sol` bug class: the actuator lets an account vote/approve after the outcome has already been decided.

### Finding Description
`ProposalApproveActuator.validate()` performs the following checks before mutating approvals: [1](#0-0) 

It checks `now >= expirationTime` (expired) and `State.CANCELED`, but there is no check against `State.APPROVED` / `State.DISAPPROVED` — i.e. it never calls the existing helper `hasProcessed()`: [2](#0-1) 

Proposal finalization, however, is driven by a *different* clock than the one used in the actuator's validate(). `ProposalController.processProposals()` finalizes (sets `APPROVED`/`DISAPPROVED`) a proposal once it is expired relative to `nextMaintenanceTime`, not relative to `latestBlockHeaderTimestamp`: [3](#0-2) [4](#0-3) 

Meanwhile, the actuator's expiry gate uses `dynamicStore.getLatestBlockHeaderTimestamp()`: [5](#0-4) 

Because `expirationTime` is computed at proposal-creation time as a maintenance-interval-aligned boundary derived from `nextMaintenanceTime` (not from the running `latestBlockHeaderTimestamp`): [6](#0-5) 

these two time references can diverge (e.g. when `nextMaintenanceTime` advances due to maintenance cycles that are independent of the exact `latestBlockHeaderTimestamp` progression, or with maintenance interval reconfiguration/parameter changes mid-cycle). In such a window, `ProposalController` can already flip the proposal state to `APPROVED`/`DISAPPROVED`, while the actuator's `now >= expirationTime` check still evaluates false, leaving `validate()` to only see a non-`CANCELED` state and allow the approval/removal transaction to succeed — silently mutating `approvals` on a proposal whose outcome has already been executed (e.g. `setDynamicParameters` already applied for `APPROVED`).

### Impact Explanation
A witness can broadcast `ProposalApproveContract` transactions (add or remove approval) after `ProposalController.processProposal()` has already resolved the proposal (setting chain parameters for `APPROVED`, or discarding for `DISAPPROVED`). This corrupts on-chain proposal state (approvals list no longer reflects the actually-applied decision) and can be leveraged to manipulate audit trails of already-executed governance decisions. It does not directly cause unbacked balances but represents an incorrect state-machine transition allowed on a finalized governance object, comparable to the "vote during objection despite already-rejected" analog in the report.

### Likelihood Explanation
Any witness (unprivileged in the sense that no additional permission beyond being a witness is required — the same actor set that can already call this actuator) can trigger this by submitting a `ProposalApproveContract` transaction; the actuator itself provides no defense against submitting it after finalization aside from the wall-clock expiry check, which is decoupled from the actual finalization clock (`nextMaintenanceTime`). The exact window's width depends on chain configuration (`maintenanceTimeInterval`, `proposalExpireTime`) and is not systematically prevented by any other actuator or validation path.

### Recommendation
Add an explicit check in `ProposalApproveActuator.validate()` (and consider `ProposalDeleteActuator`) rejecting any approval mutation once `proposalCapsule.hasProcessed()` (i.e., `State.APPROVED` or `State.DISAPPROVED`) is true, in addition to the existing `CANCELED` and timestamp-expiry checks — mirroring the fix recommended in the original report.

### Proof of Concept
1. Create a proposal via `ProposalCreateActuator`; `expirationTime` is computed from `nextMaintenanceTime` and `maintenanceTimeInterval`.
2. Allow enough maintenance cycles to pass so that `ProposalController.processProposals()` finalizes the proposal (`State.APPROVED`/`DISAPPROVED`) based on `nextMaintenanceTime`, while `latestBlockHeaderTimestamp` (used by the actuator) has not yet reached `expirationTime`.
3. Submit a `ProposalApproveContract` (`isAddApproval=true/false`) for that proposal id.
4. `ProposalApproveActuator.validate()` passes because state is neither `CANCELED` nor is `now >= expirationTime`; `execute()` mutates `approvals` on an already-finalized proposal capsule. [7](#0-6)

  public void processProposals() {
    long latestProposalNum = manager.getDynamicPropertiesStore().getLatestProposalNum();
    if (latestProposalNum == 0) {
      logger.info("latestProposalNum is 0, return");
      return;
    }

    long proposalNum = latestProposalNum;

    ProposalCapsule proposalCapsule = null;

    while (proposalNum > 0) {
      try {
        proposalCapsule = manager.getProposalStore()
            .get(ProposalCapsule.calculateDbKey(proposalNum));
      } catch (Exception ex) {
        logger.error("", ex);
        proposalNum--;
        continue;
      }

      if (proposalCapsule.hasProcessed()) {
        logger
            .info("Proposal has processed, id:[{}], skip it and before it",
                proposalCapsule.getID());
        //proposals with number less than this one, have been processed before
        break;
      }

      if (proposalCapsule.hasCanceled()) {
        logger.info("Proposal has canceled, id:[{}], skip it", proposalCapsule.getID());
        proposalNum--;
        continue;
      }

      long currentTime = manager.getDynamicPropertiesStore().getNextMaintenanceTime();
      if (proposalCapsule.hasExpired(currentTime)) {
        processProposal(proposalCapsule);
        proposalNum--;
        continue;
      }
