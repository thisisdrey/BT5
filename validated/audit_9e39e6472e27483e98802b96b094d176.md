### Title
Unbounded array allocation from attacker-controlled length in TVM precompiled contract input parsing - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The XWiki advisory describes a Denial-of-Service where an attacker-supplied "huge number" field is used directly to drive a memory allocation, exhausting the JVM heap whenever the object is processed. The analogous pattern exists in java-tron's TVM precompiled-contract call-data parsers `extractBytes32Array` and `extractBytesArray`, which read a length word straight out of untrusted contract call data and immediately allocate a Java array of that size with no upper bound check.

### Finding Description
`extractBytes32Array` and `extractBytesArray` take the `len` value directly from the decoded call data (`words[offset].intValueSafe()`) and use it to allocate `new byte[len][]` before any validation against the actual remaining data length or any sane maximum: [1](#0-0) 

`intValueSafe()` only guards against `DataWord` overflow by clamping to `Integer.MAX_VALUE`-range values — it does not impose any application-level bound related to expected input size. Because `data` (raw call-data bytes) is fully controlled by whoever calls the precompiled contract (any TVM `CALL`/`STATICCALL` to the precompile address from a smart contract invoked by an unprivileged, signed transaction), an attacker can craft `words[offset]` to be a large value (e.g. close to `Integer.MAX_VALUE`), causing `new byte[len][]` to attempt to allocate an enormous object-reference array (up to ~8 bytes × len on 32-bit refs, or more once each per-element array is subsequently allocated in the loop), well before any subsequent bounds check on the loop body has a chance to fail.

This mirrors the XWiki bug class (CWE-400/CWE-787): a single untrusted numeric field from user-controlled input is used unchecked as an allocation size, letting one caller force a large memory allocation.

### Impact Explanation
A successful huge-length call can force the executing node to attempt allocating gigabytes of heap for a single array, triggering `OutOfMemoryError` in the TVM execution thread. Depending on how broadly the JVM heap is shared, this can degrade or crash the full node process, denying service to the whole node/validator for all subsequent transactions — a resource-consumption DoS reachable by any account that can send a triggering transaction invoking the affected precompiled contract path.

### Likelihood Explanation
The precompiled contract is invoked via ordinary TVM opcodes (`CALL`/`STATICCALL`) from any deployed smart contract, meaning any unprivileged transaction broadcaster or contract deployer can reach this code path with attacker-chosen call data. No special privilege, SR/witness status, or non-transaction path is required — only a normal signed transaction that triggers a contract making the corresponding precompiled call.

### Recommendation
Add an explicit sanity/maximum bound check on `len` before allocating (e.g., cap by the remaining size of `words`/`data`, and reject if `len` exceeds a small protocol-defined maximum for the number of signatures/byte arrays expected), mirroring the bounds validation used elsewhere in `PrecompiledContracts` (e.g., in `isValidAbiEncoding`) so an out-of-range length fails fast with a normal execution revert rather than an allocation attempt.

  private static byte[][] extractBytes32Array(DataWord[] words, int offset) {
    int len = words[offset].intValueSafe();
    byte[][] bytes32Array = new byte[len][];
    for (int i = 0; i < len; i++) {
      bytes32Array[i] = words[offset + i + 1].getData();
    }
    return bytes32Array;
  }

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
