### Title
Any repository write can seize the Praefect-wide reference write lock before doing real work, letting a low-cost/no-op write hold the lock and DoS all other writers to that repository - (File: `internal/praefect/datastore/lock_manager.go`)

### Summary
The Tessera report describes an attacker seizing a shared, priority-gated resource (a proposal slot) for negligible cost and refusing to let it resolve, blocking legitimate use ("holding the vault hostage"). The closest reachable analog in Gitaly is the Praefect `RepoReferenceWriteLockManager`, which grants an *exclusive, repository-wide* write lock to whichever transaction casts the `PREPARING_PHASE` vote first — before any actual Git work has happened — and only releases it on `COMMITTED_PHASE`, explicit cancellation, or a 20-second TTL expiry.

### Finding Description
Per `doc/serialized_writes.md`, every Gitaly write path (`update_with_hooks.go`, `repoutil/create.go`, `repoutil/remove.go`, `objectpool/*.go`, `service/operations/squash.go`, `service/ref/delete_refs.go`) casts a `Preparing` vote **before any ref or file lock is acquired**: [1](#0-0) 

Praefect's transaction manager owns the lock lifecycle: `PREPARING_PHASE` calls `WriteLockManager.Lock`, which blocks until exclusive per-repository access is granted; `PREPARED_PHASE` renews it; `COMMITTED_PHASE` releases it: [2](#0-1) 

The production implementation, `RepoReferenceWriteLockManager`, stores one lock row per `(virtualStorage, relativePath)` in PostgreSQL with a hard-coded 20-second TTL (`renewInterval`), acquired via an UPSERT that only succeeds for a brand-new caller, the same `txnID` (idempotent), or an **expired** row: [3](#0-2) 

The lock is only released when the holder's `unlock` runs (on `COMMITTED_PHASE`, `StopTransaction`, `cancelTransaction`, or context cancellation) or when it naturally expires: [4](#0-3) [5](#0-4) 

Because acquisition happens at `PREPARING_PHASE` — i.e., before the requester has done any of the expensive or verifiable work (no ref lock taken yet, no quorum reached, no actual write committed) — an ordinary client with normal push/write access can register a transaction, cast the `PREPARING_PHASE` vote to grab the exclusive repository lock, and then simply stall (never reaching quorum, never voting `Committed`, or deliberately delaying the on-disk Git write, e.g. via a slow hook or by holding the gRPC context open). Every other legitimate write to that same repository is blocked in `WriteLockManager.Lock` for the duration the lock is held (up to the 20s TTL per acquisition, and renewable at `PREPARED_PHASE`), and the attacker can immediately repeat the sequence — starting a fresh cheap transaction as soon as the old one expires or is cancelled — to sustain the block indefinitely, mirroring the Tessera pattern of "grab the slot at negligible cost, then let it lapse only to grab it again."

### Impact Explanation
This lets a single unprivileged (but write-authorized) user hold the entire repository's write path hostage: no other user's push, branch deletion, squash, or repository creation/removal RPC can proceed while the lock is contended, because they all queue on the same `PREPARING_PHASE` gate. The doc explicitly designed this as cluster-wide serialization ("blocking until exclusive access"), so the blast radius is every Praefect node routing writes for that repository, not just one Gitaly backend.

### Likelihood Explanation
Likelihood is moderate-to-high in any deployment that has enabled this serialized-writes/WAL feature with a real `WriteLockManager` (vs. `NoopWriteLockManager`). It requires only ordinary write access to a repository (a capability every contributor with push rights already has) and no privileged token, node compromise, or MITM — it is a pure logic/ordering issue: the lock is granted on intent-to-write rather than on completion or resource-committed guarantee, exactly like Tessera granting the "held proposal" state to a bid regardless of its economic value.

### Recommendation
- Do not grant the exclusive per-repository lock purely on `PREPARING_PHASE`; require forward progress (e.g., bound the time between `PREPARING_PHASE` and `PREPARED_PHASE`/`COMMITTED_PHASE` far below the 20s TTL, or shrink the TTL and disallow indefinite re-acquisition loops from the same client/IP).
- Rate-limit or cap the number of concurrent/rapid `RegisterTransaction`+`VoteTransaction(PREPARING_PHASE)` sequences a single actor can initiate per repository within a rolling window.
- Consider requiring proof of "readiness to write" (e.g., an already-acquired local Git ref lock) before granting the cluster-wide serialization lock, rather than acquiring it speculatively.

### Proof of Concept
Not independently reproduced (no runtime environment available); the mechanism is reconstructed from the design documentation and the lock-manager/transaction-manager source:
1. Client A (any authorized pusher) starts a reference transaction and casts `PREPARING_PHASE` — this alone acquires the exclusive repo lock via `tryLock`'s UPSERT (`internal/praefect/datastore/lock_manager.go:304-356`), without having done any real Git write yet.
2. Client A stalls (e.g., slow-loris the gRPC call, or delays reaching quorum/committing), keeping the context open so the lock is not released by cancellation, and optionally renews at `PREPARED_PHASE`.
3. Client B, an unrelated legitimate user, attempts any write RPC (push, branch delete, squash) to the same repository; it blocks in `WriteLockManager.Lock` until Client A's lock expires or is released — confirmed by the existing test `TestPraefectWriteSerialization_HangAfterPrepared`, which demonstrates a transaction hanging after `PREPARED_PHASE` and blocking the lock until expiry: [6](#0-5) 
4. Client A repeats this immediately after expiry/cancellation to re-seize the lock, sustaining the denial of service to Client B's repository indefinitely at negligible cost (a single cheap RPC call per cycle), analogous to the Tessera attacker repeatedly creating and rejecting low-collateral proposals to hold the vault hostage.

```markdown
`internal/praefect/transactions/manager.go` owns the lock lifecycle. A
repository-scoped write lock backed by PostgreSQL is acquired, renewed, and
released according to the phase of each `VoteTransaction` call:

| Phase            | Action                                                  |
|------------------|---------------------------------------------------------|
| `PREPARING_PHASE`| `WriteLockManager.Lock` — block until exclusive access  |
| `PREPARED_PHASE` | `lock.Renew` — keep the lock alive across phases        |
| `COMMITTED_PHASE`| `lock.Unlock` — release once the write is durable       |

If any phase fails before commit, the deferred
`unlockRepoForTransaction` releases the lock so the next transaction can
proceed. Transactions that are explicitly stopped or canceled
(`StopTransaction`, `cancelTransaction`) also release the lock to avoid
stranding it in PostgreSQL.
```

```go
func (r *RepoReferenceWriteLockManager) tryLock(ctx context.Context, virtualStorage, relativePath string, txnID uint64,
) tryLockResult {
	lockID := repoLockID(virtualStorage, relativePath)
	// Register for a lock release notification before attempting the INSERT, so
	// that no release event can be missed between a failed attempt and the caller
	// beginning to wait, thus eliminating the race window between contention detection
	// and notification.
	notificationCh, deregister := r.handler.RegisterForLockRelease(lockID)

	query := `
INSERT INTO repository_reference_write_locks as locks (lock_id, holder_txn_id, expired_at)
VALUES ($1, $2, NOW() + $3::interval)
ON CONFLICT (lock_id) DO UPDATE
  SET holder_txn_id = EXCLUDED.holder_txn_id,
      expired_at    = EXCLUDED.expired_at
WHERE locks.expired_at < NOW() OR locks.holder_txn_id = $2
RETURNING lock_id, holder_txn_id, expired_at;`

	start := time.Now()
	rows, err := r.qc.QueryContext(ctx, query, lockID, txnID, r.renewInterval)
	r.operationDuration.WithLabelValues(virtualStorage, "trylock").Observe(time.Since(start).Seconds())
	if err != nil {
		r.lockAcquiredTotal.WithLabelValues(virtualStorage, "error").Inc()
		deregister()
		return tryLockResult{
			Acquired: false,
			Err:      fmt.Errorf("acquire repo reference write lock: %s, %w", lockID, err),
		}
	}
	defer func() {
		if err := rows.Close(); err != nil {
			r.logger.WithError(err).Error("close rows")
		}
	}()
	if rows.Next() {
		_, alreadyHeld := r.lockAcquiredAt.LoadOrStore(lockID, time.Now())
		if !alreadyHeld {
			r.locksHeld.WithLabelValues(virtualStorage).Inc()
			r.lockAcquiredTotal.WithLabelValues(virtualStorage, "new_acquisition").Inc()
		}
		deregister()
		unlockFn := func() error {
			return r.unlock(virtualStorage, relativePath, txnID)
		}
		renewFn := func(renewCtx context.Context) error {
			return r.renew(renewCtx, virtualStorage, relativePath, txnID)
		}
		return tryLockResult{
			Acquired: true,
			Unlock:   unlockFn,
			Renew:    renewFn,
		}
	}
```

```go
// unlock releases the write lock held by txnID. It is a no-op if the lock is not currently held by txnID
// (e.g. it expired and was taken over by another transaction).
func (r *RepoReferenceWriteLockManager) unlock(virtualStorage string, relativePath string, txnID uint64) error {
	// unlock has its own context, because the lock must be released regardless of
	// the request's lifecycle. Don't use the caller's ctx because if the caller's request
	// context is cancelled (e.g. client disconnected, deadline exceeded), the request is
	// done but the lock row still exists in the database.
	ctx, cancel := context.WithTimeout(context.Background(), 3*time.Second)
	defer cancel()

	query := `
DELETE FROM repository_reference_write_locks
WHERE lock_id = $1 AND holder_txn_id = $2;`
	lockID := repoLockID(virtualStorage, relativePath)
	start := time.Now()
	_, err := r.qc.ExecContext(ctx, query, lockID, txnID)
	r.operationDuration.WithLabelValues(virtualStorage, "unlock").Observe(time.Since(start).Seconds())

	if err != nil {
		return fmt.Errorf("release repo reference write lock: %s, %w", lockID, err)
	}

	if acquiredAt, ok := r.lockAcquiredAt.LoadAndDelete(lockID); ok {
		r.locksHeld.WithLabelValues(virtualStorage).Dec()
		r.lockHoldDuration.WithLabelValues(virtualStorage).Observe(time.Since(acquiredAt.(time.Time)).Seconds())
	}
	return nil
}
```

```go
func (mgr *Manager) releaseRepoLockOnPhase(transactionID uint64, phase string) {
	v, ok := mgr.repoLocks.LoadAndDelete(transactionID)
	if !ok {
		return
	}
	logFields := log.Fields{
		"transaction.id": transactionID,
	}
	if phase != "" {
		logFields["phase"] = phase
	}
	lock := v.(datastore.RepoLock)
	if err := lock.Unlock(); err != nil {
		mgr.logger.WithError(err).WithFields(logFields).Error("release repo lock")
	}
}

func (mgr *Manager) releaseRepoLock(transactionID uint64) {
	mgr.releaseRepoLockOnPhase(transactionID, "")
}
```

```go
func TestPraefectWriteSerialization_HangAfterPrepared(t *testing.T) {
	t.Parallel()
	db := testdb.New(t)
	ctx := testhelper.Context(t)
	logger := testhelper.SharedLogger(t)
	repoWriteLockMgr := datastore.NewRepoReferenceWriteLockManager(ctx, db, testdb.GetConfig(t, db.Name), logger)

	storageName := "mock"
	relativePath := "hang/after/prepared.git"
	voters := []transactions.Voter{{Name: "primary", Votes: 1}}
	threshold := uint(1)

	cc, txMgr, cleanup := runPraefectServerAndTxMgrAndLockMgr(t, ctx, repoWriteLockMgr)
	defer cleanup()
	client := gitalypb.NewRefTransactionClient(cc)

	// Txn1: PREPARING + PREPARED, then "hang" (no COMMITTED)
	txn1, _, err := txMgr.RegisterTransaction(ctx, voters, threshold)
	require.NoError(t, err)
	hash1 := sha1.Sum([]byte("txn1"))

	for _, phase := range []gitalypb.VoteTransactionRequest_Phase{
		gitalypb.VoteTransactionRequest_PREPARING_PHASE,
		gitalypb.VoteTransactionRequest_PREPARED_PHASE,
	} {
		_, err := client.VoteTransaction(ctx, &gitalypb.VoteTransactionRequest{
			TransactionId:        txn1.ID(),
			Repository:           &gitalypb.Repository{StorageName: storageName, RelativePath: relativePath},
			Node:                 voters[0].Name,
			ReferenceUpdatesHash: hash1[:],
			Phase:                phase,
		})
		require.NoError(t, err)
	}
	// Intentionally skip COMMITTED phase to simulate a stuck client.

	// Simulate lock expiry by back-dating the row
	_, err = db.ExecContext(ctx, `
          UPDATE repository_reference_write_locks
          SET expired_at = NOW() - INTERVAL '1 second'
          WHERE lock_id = $1`, storageName+"|"+relativePath)
	require.NoError(t, err)

	// Txn2: PREPARING should succeed (steals the expired lock)
	txn2, cancel2, err := txMgr.RegisterTransaction(ctx, voters, threshold)
	require.NoError(t, err)
	defer func() { require.NoError(t, cancel2()) }()
	hash2 := sha1.Sum([]byte("txn2"))

	_, err = client.VoteTransaction(ctx, &gitalypb.VoteTransactionRequest{
		TransactionId:        txn2.ID(),
		Repository:           &gitalypb.Repository{StorageName: storageName, RelativePath: relativePath},
		Node:                 voters[0].Name,
		ReferenceUpdatesHash: hash2[:],
		Phase:                gitalypb.VoteTransactionRequest_PREPARING_PHASE,
	})
	require.NoError(t, err)
}
```
