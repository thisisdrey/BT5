Based on the code excerpts confirmed in the report and cross-checked against the pallet logic:

- `bid()` is indeed a `Signed`-origin, unprivileged extrinsic that reserves a `candidate_deposit` and pushes an entry into the `Bids` storage vector with no cap on total queue length in the visible insertion path. [1](#0-0) 
- `on_initialize` unconditionally triggers `rotate_intake` → `select_new_candidates` at every intake boundary, with no permission check, and this is charged a **fixed** weight of `weights.max_block / 20` regardless of `Bids.len()`. [2](#0-1) 
- `select_new_candidates` retrieves the full `Bids` vector and calls `bids.retain(...)` over it; `max_selections` only caps how many bids get accepted as candidates, not how many are iterated — the `retain` closure runs once per element regardless of acceptance. [3](#0-2) 
- `rotate_intake` is called automatically from `on_initialize`, with no admin or governance trigger required. [4](#0-3) 

I was unable to find any `Config`-level bound (e.g., `MaxBids`) that caps the total length of the `Bids` vector, nor did the benchmarking or migration files reveal such a constraint within the scope I could inspect. The `Bids` storage item appears to be an unbounded `Vec`-backed value rather than a `BoundedVec`, and insertion via `insert_bid` in `bid()` has no visible length check. This matches the structure of the claim precisely: unbounded, permissionless growth of an array that is fully iterated by an automatic, flat-weight-charged operation.

This satisfies the required elements: an unprivileged, publicly reachable entry point (`bid()`), a concrete broken invariant (weight charged for `on_initialize`/`rotate_intake` does not scale with `Bids.len()`), a reachable exploit path (repeatedly calling `bid()` from many funded accounts to inflate `Bids`, then triggering the automatic intake rotation), and a named corrupted/miscosted value (the weight accounted for `on_initialize`, `weights.max_block / 20`, undercharges the true cost of the `retain` scan as `Bids.len()` grows). This aligns with the "public underpriced work that degrades block production" impact category under the Polkadot SDK impact gate, since the trigger is automatic (`on_initialize`) and requires no governance or admin action — only a signed account and the refundable `candidate_deposit`.

Audit Report

## Title
Unbounded, flat-weight iteration of the permissionless `Bids` queue in `pallet-society::select_new_candidates` allows cheap DoS of block-level intake processing - (File: `substrate/frame/society/src/lib.rs`)

## Summary
The public, unprivileged `bid()` extrinsic appends to the unbounded `Bids` storage vector, and the automatic `on_initialize` → `rotate_intake` → `select_new_candidates` path performs a full linear `retain` scan over that vector every intake period. The weight charged for this work is a fixed constant (`weights.max_block / 20`), independent of `Bids.len()`, so an attacker who cheaply inflates the bid queue can push the real execution cost of automatic intake processing past its charged weight, degrading block production.

## Finding Description
`bid()` reserves `candidate_deposit` and pushes into `Bids` with no length cap enforced in the insertion path. [1](#0-0)  `on_initialize` unconditionally invokes `rotate_intake` at every intake boundary and accrues a flat `weights.max_block / 20` for it, with no dependency on the size of `Bids`. [2](#0-1)  `rotate_intake` calls `select_new_candidates`, which does `Bids::<T, I>::get()` followed by `bids.retain(...)`, visiting every element in the vector; `max_selections` bounds only how many bids are *accepted*, not how many are *iterated*. [3](#0-2)  No `Config`-level bound (e.g., a `BoundedVec` with a `MaxBids` type) was found constraining `Bids` length, so the queue can grow proportionally to the number of signed accounts an attacker controls.

## Impact Explanation
Because the weight accounted in `on_initialize` for the intake rotation is a fixed fraction of the block weight limit rather than a function of the true cost of scanning `Bids`, an attacker who inflates the bid queue causes the automatic, unavoidable `on_initialize` logic to underdeclare its actual computational cost. This is public, underpriced work that degrades block production for any runtime including `pallet-society`, matching the allowed "public underpriced work that degrades block production" impact category.

## Likelihood Explanation
The only precondition is a signed account with enough balance to cover the refundable `candidate_deposit`; no root, governance, or admin interaction is required. The trigger (`on_initialize`) runs automatically at every intake boundary and cannot be paused by users once the queue is inflated, making the attack fully repeatable and cheap (deposit is reserved, not burned, and can later be unbid/refunded).

## Recommendation
- Bound `Bids` with a `BoundedVec<_, T::MaxBids>` and reject `bid()` once the cap is reached, and/or
- Charge `on_initialize`/`rotate_intake` weight proportionally to `Bids::decode_len()`, similar to how `elections-phragmen::do_phragmen` bounds/early-exits on `MaxVoters`.
- Process `select_new_candidates` in bounded batches across multiple blocks instead of a single unbounded `retain` pass.

## Proof of Concept
1. Attacker funds N accounts and calls `Society::bid(origin, value)` from each, growing `Bids` to N entries with no cap blocking this. [1](#0-0) 
2. At the next intake boundary, `on_initialize` calls `rotate_intake` → `select_new_candidates`, which performs `Bids::<T,I>::get()` then `bids.retain(...)` over all N entries. [3](#0-2) 
3. The weight charged for this step remains fixed at `max_block / 20` regardless of N. [2](#0-1)  For sufficiently large N, actual computation time exceeds the weight accounted, degrading block production.
