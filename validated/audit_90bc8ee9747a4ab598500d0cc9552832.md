### Title
Exchange Trade Can Drive Bancor Pool Reserve To Zero, Permanently Freezing The Pair And Locking Remaining Liquidity - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeTransactionActuator.java`)

### Summary
Notional's `enterMaturity` treats `vaultState.totalAssetCash == 0` as the only "healthy/open" state and permanently rejects new deposits once that invariant is broken by an emergency action, with no code path to restore it. java-tron's bancor-style token Exchange has the same "closed if reserve == 0" invariant, guarded identically in three separate actuators, but the reserve can be driven to exactly zero by an ordinary, permissionless `ExchangeTransactionContract` trade due to integer-truncating division in the bancor formula. Once either reserve hits zero, `ExchangeTransactionActuator`, `ExchangeInjectActuator`, and `ExchangeWithdrawActuator` all permanently revert for that exchange, with no actuator able to reset the balances.

### Finding Description
`ExchangeTransactionActuator.doValidate()` and `.execute()` allow any account to submit a trade against an exchange pair without any check that the computed `anotherTokenQuant` stays below the current opposite-side reserve: [1](#0-0) 

Contrast this with `ExchangeWithdrawActuator`, which explicitly checks `firstTokenBalance < tokenQuant || secondTokenBalance < anotherTokenQuant` before allowing an operation: [2](#0-1) 

No equivalent sufficiency check exists in `ExchangeTransactionActuator`. The trade amount is computed via `exchangeCapsule.transaction(...)`, a bancor/constant-product style calculation using integer (`longValueExact`/floor) arithmetic. Because the formula truncates, a sufficiently large `tokenQuant` input can cause the computed `anotherTokenQuant` to round to exactly the full remaining balance of the opposite token — driving that reserve to precisely `0` — which is mathematically impossible with continuous arithmetic (an asymptote) but achievable with integer truncation.

Once either reserve becomes `0`, all three actuators treat the exchange as permanently closed and revert with `"Token balance in exchange is equal with 0, the exchange has been closed"`: [3](#0-2) [4](#0-3) [5](#0-4) 

This is the direct analog of the Notional bug: an ordinary, permissionless operation (a trade, analogous to the emergency settlement) leaves a state variable (`firstTokenBalance`/`secondTokenBalance`, analogous to `totalAssetCash`) in a value that the entry-guard code treats as terminal/closed, and there is no actuator path in java-tron to reopen the exchange or reset its reserves (there is no "re-inject when balance is 0" bypass, since `ExchangeInjectActuator` enforces the same zero-balance guard). Unlike the Notional case (where users can still exit with a proportional share), here the creator's remaining reserve on the *other* token is also permanently unwithdrawable, because `ExchangeWithdrawActuator` requires *both* `firstTokenBalance != 0` and `secondTokenBalance != 0` before allowing any withdrawal.

### Impact Explanation
Any residual liquidity left in the exchange (the creator's remaining reserve of the token that did not reach zero) becomes permanently frozen: the creator can no longer withdraw it via `ExchangeWithdrawActuator`, no one can inject more liquidity via `ExchangeInjectActuator` to reopen trading, and no further trades are possible via `ExchangeTransactionActuator`. This is a permanent freezing-of-funds condition triggerable by any anonymous market order placer via a single signed `ExchangeTransactionContract` transaction — no privileged role is required.

### Likelihood Explanation
Triggering this requires only a single, ordinary `ExchangeTransactionContract` transaction with a `quant` large enough (relative to the reserves) that the bancor formula's integer truncation rounds the opposite-side output to the full remaining balance. This is entirely reachable by an unprivileged transaction broadcaster and does not require malicious validators, network conditions, or elevated permissions — only careful selection of the trade size relative to a thin/small-reserve exchange pool (most exploitable on newly created or low-liquidity exchange pairs).

### Recommendation
In `ExchangeTransactionActuator.doValidate()`, add an explicit sufficiency check (mirroring `ExchangeWithdrawActuator`) that rejects trades where the computed `anotherTokenQuant` would consume the entire opposite-side reserve (e.g., require `anotherTokenQuant < tokenBalance` strictly, not merely `> 0`). Additionally, consider adding a recovery path (e.g., allow the creator to re-inject liquidity even when one reserve is zero) so an exchange cannot become unrecoverably locked, analogous to Notional's recommendation to allow re-entry or document the permanent-lock behavior explicitly.

### Proof of Concept
Conceptual reproduction (exact numeric trigger not verified against `ExchangeCapsule.transaction()` internals due to tool/iteration limits, but the guard logic and missing check are confirmed in source):
1. Creator calls `ExchangeCreateActuator` to create a pool with small reserves, e.g. `firstTokenBalance = 100`, `secondTokenBalance = 100`.
2. Attacker submits `ExchangeTransactionContract` selling `firstToken` with a very large `tokenQuant` (e.g., `1_000_000`).
3. `exchangeCapsule.transaction()` computes `anotherTokenQuant` via bancor formula with integer truncation; with a sufficiently large input relative to reserves, the truncated result equals `secondTokenBalance` (100), setting `secondTokenBalance` to `0` after `execute()`.
4. All subsequent calls to `ExchangeInjectActuator`, `ExchangeWithdrawActuator`, and `ExchangeTransactionActuator` on this exchange ID now revert at the `firstTokenBalance == 0 || secondTokenBalance == 0` check, permanently locking the exchange and any remaining `firstToken` reserve held by the contract/creator.
