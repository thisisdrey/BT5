### Title
Empty `GetTenureBlocks` response permanently wedges a tenure downloader without marking the peer dead - ([File: stackslib/src/net/download/nakamoto/tenure_downloader.rs])

### Summary
`NakamotoTenureDownloader::try_accept_tenure_blocks` returns `Ok(None)` immediately when the decoded tenure block list is empty, performing no validation and no state advancement. Because this is treated as a normal (non-error) outcome, `NakamotoTenureDownloaderSet::run` never records a failure or drops the peer, allowing a malicious peer to repeatedly answer `GetTenureBlocks` with an empty-but-well-formed response and keep the download slot for that tenure stuck forever.

### Finding Description
The claimed equality is: *idle-cycles-without-progress == bounded retry/backoff before disconnection*. Tracing the code shows this equality does **not** hold for the empty-tenure-blocks case.

In `try_accept_tenure_blocks` [1](#0-0) , an empty `tenure_blocks` vector short-circuits to `Ok(None)` before any of the cursor/signature/consensus-hash checks that would otherwise reject a bad response.

`handle_next_download_response` calls `decode_nakamoto_tenure()` then `try_accept_tenure_blocks(blocks)`; since the empty-vec path returns `Ok(None)` (not `Err`), execution falls through to `self.idle = true;` [2](#0-1)  — the response is treated as a *successful* round-trip. Critically, `self.state` (the `GetTenureBlocks(block_cursor, ..)` value) is left completely unchanged, so the next call to `make_next_download_request` reissues the exact same `new_get_nakamoto_tenure(peerhost, end_block_id.clone(), None)` request [3](#0-2) .

In `NakamotoTenureDownloaderSet::run`, the response-handling loop only calls `mark_failed_and_deprioritize_peer` / `neighbor_rpc.add_dead` when `handle_next_download_response` returns `Err(..)` [4](#0-3) . Since the empty-blocks case returns `Ok(None)`, that branch (`Ok(None) => continue;`) is taken, which does not touch `attempt_failed_tenures`, `deprioritized_peers`, or `neighbor_rpc`'s dead-peer bookkeeping at all. The downloader is not marked done (`is_done()` checks `state == Done`, which never changes), so it stays in the `downloaders` list and keeps being scheduled via `send_next_download_request` on the next `run()` invocation, sending the identical `GetTenureBlocks(block_cursor)` request again.

No existing guard catches this: there is no minimum-blocks-per-response check, no retry counter tied to “stalled state” (only tied to hard decode/validation errors), and no timeout mechanism visible in this state machine that forces a disconnect purely from repeated empty/no-progress responses.

### Impact Explanation
A single malicious/unprivileged peer that has been assigned to download a specific historic tenure (`ch`) can keep answering every `GetTenureBlocks` HTTP request with a syntactically valid but empty tenure body indefinitely. This does not crash the node or forge data, but it wedges the downloader slot bound to that peer/tenure combination: the state machine never advances past `GetTenureBlocks`, is never marked `Done`, and the peer is never added to `neighbor_rpc`'s dead list nor deprioritized. This matches the "bounded compute DoS on a read endpoint"/availability degradation category — it stalls progress toward completing that tenure's download, though it does not itself corrupt canonical state, since no invalid blocks are ever accepted (the empty vec is simply discarded). The remainder of the download-scheduling system (`make_tenure_downloaders`, `has_downloader_for_tenure`) will continue to treat that tenure as "already has a downloader," preventing another peer from being tried for it.

### Likelihood Explanation
Preconditions are minimal and attacker cost is low: the attacker only needs to be selected as a candidate peer for the tenure download schedule (i.e., simply advertise inventory for the tenure and respond to the P2P/RPC handshake, which any unprivileged remote peer can do) and then answer the specific tenure's `GetTenureBlocks` HTTP GET with a 200 response whose decoded body is an empty block list. This requires no secret, no signature forgery, and can be repeated on every request cycle with a single crafted response replayed indefinitely, making it a cheap, remotely reachable, repeatable interaction.

### Recommendation
Treat an empty `tenure_blocks` response in `try_accept_tenure_blocks` as a failure (or at least count it as a no-progress attempt) rather than a benign `Ok(None)`. Specifically:
- Return `Err(NetError::InvalidMessage)` (or a dedicated "empty response" error) when `tenure_blocks.is_empty()` and the state machine has not yet reached `tenure_start_block`, so `NakamotoTenureDownloaderSet::run` will route it through the existing `mark_failed_and_deprioritize_peer` / `add_dead` path.
- Alternatively, add an explicit stall/attempt counter to `NakamotoTenureDownloader` that increments whenever `state` fails to change across a request/response cycle for `GetTenureBlocks`, and disconnect/deprioritize the peer once a bounded threshold is exceeded.

### Proof of Concept
Add a test under `stackslib/src/net/tests/download/nakamoto.rs` (or a focused unit test in `tenure_downloader.rs`):
1. Construct a `NakamotoTenureDownloader` in state `GetTenureBlocks(cursor, t0)` with a known `tenure_start_block_id`/`tenure_end_block_id` and valid signer sets (as done in existing tenure-downloader tests).
2. Call `try_accept_tenure_blocks(vec![])` directly and assert it returns `Ok(None)` while `self.state` is unchanged (`assert_eq!(downloader.state, GetTenureBlocks(cursor, t0))`), demonstrating no progress and no error.
3. In a `NakamotoTenureDownloaderSet` harness with a mock peer/`NeighborRPC` that always returns a `StacksHttpResponse` decoding to an empty tenure via `decode_nakamoto_tenure()`, call `set.run(...)` in a loop (e.g., 50 iterations) and assert:
   - `set.attempt_failed_tenures.get(&ch)` remains `None`/`0`.
   - the peer is never present in any dead/deprioritized peer set (`deprioritized_peers` stays empty for that peer).
   - `downloader.is_done()` is `false` after all iterations, confirming the slot is permanently wedged.
