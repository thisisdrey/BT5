## Finding

### Title
Overly verbose internal exception details (class name + message) leaked to unauthenticated API callers on smart-contract call failures - (File: `framework/src/main/java/org/tron/core/Wallet.java`, `framework/src/main/java/org/tron/core/services/RpcApiService.java`, `framework/src/main/java/org/tron/core/services/http/TriggerConstantContractServlet.java`, `framework/src/main/java/org/tron/core/services/http/TriggerSmartContractServlet.java`, `framework/src/main/java/org/tron/core/services/http/EstimateEnergyServlet.java`)

### Summary
The HTTP (`/wallet/triggerconstantcontract`, `/wallet/triggersmartcontract`, `/wallet/estimateenergy`) and gRPC (`triggerContract`, `triggerConstantContract`, `estimateEnergy`) entry points that let any anonymous caller execute or estimate a smart contract call catch generic `RuntimeException`/`Exception` and echo `e.getClass() + " : " + e.getMessage()` straight back in the API response, instead of returning a sanitized, generic error.

### Finding Description
The CVE describes MapServer's OGR driver returning verbose, low-level backend error text (from a failed data connection) directly to a remote caller, leaking internal information about the backend. The java-tron analog is the family of TVM/contract-call servlets and RPC handlers that, on any exception other than the expected `ContractValidateException`/`VMIllegalException`, build the response message from the raw Java exception: [1](#0-0) [2](#0-1) [3](#0-2) 

The same pattern exists in the gRPC service for `triggerContract`/`triggerConstantContract`/`estimateEnergy`: [4](#0-3) 

And in `Wallet.isShieldedTRC20NoteSpent` (used by shielded TRC20 note-spent checks reachable indirectly through wallet RPCs): [5](#0-4) 

Because contract execution (`VMActuator`/`Program`) can surface a broad range of `RuntimeException` types (VM internal errors, `IllegalStateException`, `NullPointerException`, or `RuntimeException`s wrapping `RocksDBException`/`IOException` thrown by the storage layer, e.g. `RuntimeException(dataBaseName, e)` in `RocksDbDataSourceImpl.getData`/`putData`), any unexpected backend failure while processing a user-supplied `TriggerSmartContract` (attacker fully controls `contract_address`, `data`, `function_selector`, `parameter`) is converted into `e.getClass() + " : " + e.getMessage()` and returned verbatim to the caller — an unprivileged, unauthenticated API client: [6](#0-5) 

Similar verbatim `e.getMessage()` propagation to callers exists in `TronJsonRpcImpl.estimateGas` (JSON-RPC path): [7](#0-6) 

### Impact Explanation
The exposed exception class names/messages can reveal internal implementation details: fully-qualified internal class names, DB store names, VM internal state, or details about which internal component failed (e.g. distinguishing a RocksDB corruption/IO condition from a VM logic error). This is information disclosure that helps an attacker fingerprint the node's internal architecture, discover which internal exception types are reachable from external input (useful for crafting further, more damaging inputs), and diagnose backend failures (e.g., DB corruption, resource exhaustion) that operators would prefer kept private. It does not by itself allow theft of funds, but it is a genuine verbose-error information-leak reachable by any anonymous contract-triggering request, matching the CVE's bug class exactly (verbose backend error surfaced through a client-facing API on failure).

### Likelihood Explanation
High reachability: any anonymous client can call `/wallet/triggerconstantcontract`, `/wallet/triggersmartcontract`, `/wallet/estimateenergy`, or the equivalent gRPC/JSON-RPC methods with attacker-chosen contract address/data, and trigger arbitrary VM execution paths, including ones that throw unexpected `RuntimeException`s. No special privileges, signatures, or preconditions are required beyond forming a valid request. The severity of what specific message leaks depends on which exception is thrown, so realistic likelihood of a *sensitive* leak is Medium, though the code pattern itself is present across many endpoints.

### Recommendation
Do not return `e.getClass()`/`e.getMessage()` for generic `RuntimeException`/`Exception` branches in these contract-call and RPC entry points. Log the full exception server-side (as is already done via `logger.warn(...)`) and return a fixed, generic message (e.g., "Internal error running contract") to the caller, similar to how `RpcApiService.getRunTimeException` and the JSON-RPC internal-error handling elsewhere already sanitize responses. Apply this consistently to `Wallet.triggerConstantContract`/`triggerContract`/`estimateEnergy`/`isShieldedTRC20NoteSpent`, `RpcApiService.callContract`/`estimateEnergy`, and the corresponding HTTP servlets.

### Proof of Concept
1. Send a POST to `/wallet/triggerconstantcontract` with a `contract_address` pointing at a contract, and `data`/`function_selector` crafted to drive VM/actuator execution into an unexpected internal failure path (e.g., conditions causing a `RuntimeException` other than `ContractValidateException`/`VMIllegalException`, such as a wrapped DB error surfaced as `RuntimeException(dataBaseName, e)`).
2. Observe the JSON response's `message` field containing `e.getClass() + " : " + e.getMessage()` — i.e., the raw internal exception class and message — as coded in `TriggerConstantContractServlet.doPost` catch block.
3. Repeat via the gRPC `Wallet.triggerConstantContract`/`estimateEnergy` methods and confirm identical verbose exception details in `Return.message`.
