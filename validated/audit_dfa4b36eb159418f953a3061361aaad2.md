### Title
Unprotected reserve-ratio pricing in ExchangeInjectActuator/ExchangeWithdrawActuator allows sandwich manipulation of the exchange creator's liquidity operations - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`, `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
TRON's built-in bancor-style Exchange (`ExchangeCapsule`) prices `ExchangeInjectContract` and `ExchangeWithdrawContract` operations purely off the current on-chain `firstTokenBalance`/`secondTokenBalance` reserves at execution time, with no caller-supplied minimum/maximum ("expected") bound like the one present in the sibling `ExchangeTransactionContract`. This mirrors the reported bug class: pricing derived from spot reserves that "can be easily manipulated by attackers" via front-running, with no slippage protection to fall back on.

### Finding Description
`ExchangeCapsule.transaction()` and the swap actuator (`ExchangeTransactionActuator`) implement the recommended fix from the external report already: the caller supplies `contract.getExpected()`, and `doValidate()` enforces `anotherTokenQuant < tokenExpected` → revert [1](#0-0) .

However, `ExchangeInjectActuator` (adding liquidity) and `ExchangeWithdrawActuator` (removing liquidity) compute the counter-party token amount solely as a ratio of the *current* pool reserves, with no equivalent min/max protection field in their contracts:
- Inject: `anotherTokenQuant = bigSecondTokenBalance.multiply(bigTokenQuant).divide(bigFirstTokenBalance)` [2](#0-1) 
- Withdraw: `anotherTokenQuant = bigSecondTokenBalance.multiply(bigTokenQuant).divide(bigFirstTokenBalance)` [3](#0-2) 

Because these balances live in `ExchangeCapsule`/`ExchangeV2Store` and are freely, atomically moved by any account submitting an `ExchangeTransactionContract` swap against the same exchange id, an unprivileged transaction broadcaster can shift the reserve ratio immediately before the exchange creator's inject/withdraw transaction is packed into the same block (transaction ordering within a block is attacker-influenceable via fee/ordering, and TRON blocks batch many transactions per block), then reverse the swap afterward to restore price and pocket the difference — a classic sandwich, exactly the scenario the external report describes for "buying" against manipulated reserves, except here it targets the pool's own inject/withdraw math instead of an external DEX oracle.

The withdraw actuator does add a "Not precise enough" 0.01% rounding check [4](#0-3) , but that only bounds rounding error against the *caller-supplied ratio itself*, not against a price the caller actually intended — it does not protect against the reserves having been skewed by a prior manipulative swap in the same block.

### Impact Explanation
The exchange creator (an asset issuer who created the TRON on-chain exchange pair) can be forced to inject tokens at a manipulated ratio (overpaying the counter-token) or withdraw at a manipulated ratio (receiving less of the counter-token than the fair reserve ratio implies), directly transferring value to the attacker who sandwiches the operation with two `ExchangeTransactionContract` swaps. This is a concrete theft-of-funds vector against the pool operator, reachable by any account able to broadcast ordinary signed transactions.

### Likelihood Explanation
Medium: the attack requires knowledge of a pending inject/withdraw transaction from the specific exchange creator and the ability to have both a front-running and back-running swap land in the same or adjacent blocks — feasible for anyone monitoring the mempool, similar to the sandwich-attack economics cited in the original report.

### Recommendation
Add a caller-specified expected/min-max bound (analogous to `ExchangeTransactionContract.expected`) to `ExchangeInjectContract` and `ExchangeWithdrawContract`, and enforce it in `ExchangeInjectActuator`/`ExchangeWithdrawActuator` validation the same way `ExchangeTransactionActuator` already does, so liquidity operations revert if the reserve-derived ratio deviates beyond the caller's tolerance.

### Proof of Concept
1. Exchange creator broadcasts `ExchangeInjectContract` (or `ExchangeWithdrawContract`) for exchange id `E`, computed off-chain assuming the current visible `firstTokenBalance`/`secondTokenBalance`.
2. Attacker observes the pending transaction and broadcasts an `ExchangeTransactionContract` swap against the same `E` with higher fee/priority to land first in the block, shifting `firstTokenBalance`/`secondTokenBalance` sharply via `ExchangeCapsule.transaction()` [5](#0-4) .
3. The creator's inject/withdraw executes against the now-skewed reserves in `ExchangeInjectActuator.execute()`/`ExchangeWithdrawActuator.execute()`, producing an `anotherTokenQuant` unfavorable to the creator.
4. Attacker submits a reverse swap to restore the original ratio, extracting the value taken from the creator.

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
