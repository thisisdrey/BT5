Confirmed: `AdaptiveLimit.Update()` (internal/gitaly/limiter/adaptive_limit.go:67-77) invokes each registered hook while holding only `AdaptiveLimit`'s own mutex, and the hook registered in `NewConcurrencyLimiter` (internal/limiter/concurrency_limiter.go:173-184) iterates `limiter.limitsByKey` **without acquiring `c.m`**, the `sync.RWMutex` that otherwise guards all reads/writes of that map in `getConcurrencyLimit()`/`putConcurrencyLimit()` (lines 245-292). ### Title
Unsynchronized map access between `ConcurrencyLimiter.limitsByKey` and its adaptive-limit resize hook can crash the Gitaly process (DoS) - ([File: internal/limiter/concurrency_limiter.go])

### Summary
`ConcurrencyLimiter` maintains a map of per-key semaphores (`limitsByKey`) protected by `c.m sync.RWMutex`. When the adaptive concurrency limit changes, the resize hook registered in `NewConcurrencyLimiter` iterates that same map to resize each semaphore, but does so without taking `c.m`. Ordinary RPC traffic mutates the map under the correct lock at the same time, producing an unguarded concurrent map access.

### Finding Description
- `getConcurrencyLimit()` and `putConcurrencyLimit()` correctly lock `c.m` before reading/writing `c.limitsByKey`. [1](#0-0) 
- The resize callback registered via `limit.AfterUpdate(...)` in `NewConcurrencyLimiter` ranges over `limiter.limitsByKey` with no locking whatsoever. [2](#0-1) 
- `AdaptiveLimit.Update()` invokes all registered hooks synchronously while holding only the `AdaptiveLimit`'s own mutex, unrelated to `ConcurrencyLimiter.m`. [3](#0-2) 
- `ConcurrencyLimiter.Limit()` is the entry point invoked per RPC call (e.g. via `TypePerRPC` and `TypePackObjects` limiters used for push/fetch/pack-objects handling), and internally calls `getConcurrencyLimit`/`putConcurrencyLimit` on every request. [4](#0-3) 

Because the adaptive-limit calculator runs on its own goroutine independent of RPC handling, an ordinary user simply issuing concurrent Git operations (pushes/fetches/clones) that flow through the limiter is enough to race against a concurrent limit recalculation. Go's runtime map implementation is not safe for concurrent read/write, and this specific pattern (`range` on the map by one goroutine while another goroutine writes to it via `delete`/insert) is exactly the kind of access the Go runtime actively detects and turns into a fatal error terminating the whole process, rather than a recoverable panic.

### Impact Explanation
This is the closest reachable analog to the reported bug class: a state mutation path (`Update`/resize hook) is not gated by the same synchronization used by the "normal" mutation path (`getConcurrencyLimit`/`putConcurrencyLimit`), similar to how `finalize()`/`_addCommitment()` in the original report used inconsistent guards on shared state. Here the consequence is not an off-by-one token accounting bug but an outright crash of the Gitaly process — a full denial of service affecting every repository served by that node, triggerable by ordinary, unprivileged concurrent RPC traffic combined with the adaptive limiter changing its target concurrency (which happens automatically based on system load/backoff, not requiring attacker control).

### Likelihood Explanation
Likelihood depends on the concurrency limiter and adaptive limit being enabled with more than one distinct limiting key in use (so the map has more than a trivial number of entries) at the moment an adaptive resize occurs. This is a timing-dependent data race, so it will not reproduce on every request, but any Gitaly deployment using adaptive per-RPC or pack-objects concurrency limits under real traffic will periodically hit resize events, and normal traffic continuously inserts/deletes map entries via `getConcurrencyLimit`/`putConcurrencyLimit`. I could not fully verify from the available index how frequently `Update()` fires in production (that logic lives in `internal/limiter/adaptive_calculator.go`, which I was not able to fully inspect within the remaining budget), so the exact trigger frequency is uncertain.

### Recommendation
Have the `AfterUpdate` hook in `NewConcurrencyLimiter` acquire `c.m` (a read lock is insufficient since it needs to safely iterate while other goroutines may concurrently insert/delete; consider taking the same lock used by `getConcurrencyLimit`/`putConcurrencyLimit`, or restructure to snapshot the map under lock before iterating) so that all readers/writers of `limitsByKey` share the same synchronization domain.

### Proof of Concept
Not independently reproduced in this session; the finding is based on static analysis of the locking discipline:
1. `internal/limiter/concurrency_limiter.go:173-184` — resize hook iterates `limiter.limitsByKey` unlocked.
2. `internal/limiter/concurrency_limiter.go:245-270` and `272-292` — `getConcurrencyLimit`/`putConcurrencyLimit` mutate the same map under `c.m`.
3. `internal/limiter/adaptive_limit.go:66-77` — `Update()` calls hooks synchronously, independent of `c.m`.

A reproduction would require running the concurrency limiter with at least two limiting keys under sustained concurrent RPC load while simultaneously invoking `AdaptiveLimit.Update()` from a separate goroutine (as the real adaptive calculator does), and observing `go test -race` or a production crash log for `fatal error: concurrent map ...`. I was not able to execute this within the current session; a background Devin session with access to `go test -race ./internal/limiter/...` and the ability to add a targeted racing test would be needed to confirm the crash empirically.

func (c *ConcurrencyLimiter) getConcurrencyLimit(limitingKey string) *keyedConcurrencyLimiter {
	c.m.Lock()
	defer c.m.Unlock()

	if c.limitsByKey[limitingKey] == nil {
		// Set up the queue tokens in case a maximum queue length was requested. As the
		// queue tokens are kept during the whole lifetime of the concurrency-limited
		// function we add the concurrency tokens to the number of available token.
		var queueTokens semaphorer
		if c.maxQueueLength > 0 {
			queueTokens = c.createSemaphore(uint(c.currentLimit() + c.maxQueueLength))
		}

		c.limitsByKey[limitingKey] = &keyedConcurrencyLimiter{
			monitor:               c.monitor,
			maxQueueWait:          c.maxQueueWait,
			setWaitTimeoutContext: c.SetWaitTimeoutContext,
			concurrencyTokens:     c.createSemaphore(uint(c.currentLimit())),
			queueTokens:           queueTokens,
		}
	}

	c.limitsByKey[limitingKey].refcount++

	return c.limitsByKey[limitingKey]
}
