## Finding [1](#0-0) [2](#0-1) 

Both `transfer_to_new_account` and `transfer_to_new_account_pda` accept a `new_authority: UncheckedAccount<'info>` with the explicit warning "New authority is completely unchecked", and neither the account constraints nor the instruction bodies validate that `new_authority.key() != Pubkey::default()`.

### Title
Missing zero-address check on `new_authority` permanently locks migrated funds - (File: `programs/marginfi/src/instructions/marginfi_account/transfer_account.rs`)

### Summary
`transfer_to_new_account` and `transfer_to_new_account_pda` let a marginfi account authority migrate all lending positions to a brand-new `MarginfiAccount` under a caller-supplied `new_authority`. Neither instruction checks that `new_authority` is non-zero before using it to initialize the new account and disable the old one.

### Finding Description
`initialize_migrated_account` writes `ctx.accounts.new_authority.key()` directly into the new `MarginfiAccount.authority` field [3](#0-2) , and `finalize_migrated_old_account` then wipes the old account's `lending_account` (setting it to `LendingAccount::zeroed()`) and flags it `ACCOUNT_DISABLED`, making the migration irreversible [4](#0-3) . The `new_authority` account is typed as `UncheckedAccount` with only a doc comment warning that it is unchecked, and there is no `constraint` in either `TransferToNewAccount` or `TransferToNewAccountPda` account structs enforcing `new_authority.key() != Pubkey::default()` [5](#0-4) [6](#0-5) . This mirrors the reported bug class in TimeLoans.sol, where internal `_mint`/`_burn` operations lack zero-address validation before mutating balance state that could otherwise be checked by the caller-supplied address, but here the analog is stronger because `new_authority` is a fully user-controlled instruction argument, not `msg.sender`.

By contrast, the CLI wrapper for this same instruction does perform this check off-chain (`bail!("Cannot transfer authority to the zero pubkey")`) [7](#0-6) , confirming the team recognizes zero-address `new_authority` as invalid, yet the on-chain program itself performs no such enforcement, so any direct caller of the on-chain instruction (not using the CLI) can bypass it.

### Impact Explanation
If `new_authority` is passed as `Pubkey::default()` (System Program address, which has no corresponding private key), the new `MarginfiAccount` is created with an authority that can never produce a valid `Signer` for future instructions (deposits, withdraws, borrows, repays, order placement, or another `transfer_to_new_account`). Since the old account's `lending_account` is simultaneously zeroed and the old account is permanently `ACCOUNT_DISABLED` [8](#0-7) , all lending positions (deposits and open borrow shares) migrated in this call become permanently locked/frozen with no recovery path — a permanent, protocol-level fund freeze.

### Likelihood Explanation
The instruction is callable directly by any marginfi account authority (unprivileged, ordinary end-user), without any protocol-level gate beyond normal authorization checks (`account_not_frozen_for_authority`, `is_signer_authorized`) [9](#0-8) . The known-good CLI path guards against this misuse, but any third-party integrator, custom client, or malformed transaction constructed directly against the on-chain program can supply `Pubkey::default()` (accidentally via a bug, or maliciously via a compromised/spoofed front-end tricking a user into migrating to an attacker-influenced "burn" address) and trigger the fund lock in a single transaction.

### Recommendation
Add an explicit on-chain check in both `transfer_to_new_account` and `transfer_to_new_account_pda` (and ideally as an Anchor `constraint`) that `new_authority.key() != Pubkey::default()`, returning a dedicated error (e.g., `MarginfiError::InvalidAuthority`) before any account mutation occurs, mirroring the check already present in the `p0-cli` client code.

### Proof of Concept
1. Attacker/user calls `transfer_to_new_account` (or `transfer_to_new_account_pda`) with a legitimately-owned `old_marginfi_account` that holds deposits/borrow positions, signing as `authority`.
2. Pass `new_authority = Pubkey::default()` (System Program ID) as the `new_authority` account.
3. Transaction succeeds: `initialize_migrated_account` sets the new account's `authority` field to `Pubkey::default()` and copies over all of `old_account.lending_account` [10](#0-9) ; `finalize_migrated_old_account` disables the old account and zeroes its lending state [8](#0-7) .
4. No keypair exists for `Pubkey::default()`, so no future instruction (`lending_account_withdraw`, `lending_account_repay`, another `transfer_to_new_account`, etc.) can ever be signed for the new account — the migrated funds are permanently unrecoverable.

    new_account_key: Pubkey,
    current_timestamp: u64,

    old_account.migrated_to = new_account_key;
    old_account.last_update = current_timestamp;
