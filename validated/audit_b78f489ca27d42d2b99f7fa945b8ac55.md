### Title
HookService RPCs intended for internal-only invocation are exposed on Gitaly's external gRPC socket - (File: `internal/gitaly/server/server.go`)

### Summary
The external report describes `deposit` in the Hypervisor contract being reachable by anyone even though it is designed to be invoked only through the trusted `UniProxy` intermediary, allowing bypass of intended controls. The same "should-only-be-called-internally" pattern exists in gitaly for `HookService` RPCs (`PreReceiveHook`, `PostReceiveHook`, `UpdateHook`, `ReferenceTransactionHook`), which are designed to be triggered only by the `gitaly-hooks` binary through the internal socket as part of the `git-receive-pack`/`OperationService` execution flow, but are also registered and reachable on Gitaly's external gRPC listener.

### Finding Description
`doc/hooks.md` and the `HookService` proto documentation state that `HookService` "is typically invoked via the `gitaly-hooks` binary to ensure that the actual hook logic is executed in the context of the server" [1](#0-0) , and the intended flow is: Git spawns `gitaly-hooks`, which dials the *internal* unix socket using a token derived from the hooks payload, then calls the RPC [2](#0-1) .

However, `setup.RegisterAll` registers `HookService` (along with all other services) on every listener configured in `serve.go`, including the external TCP/TLS/unix socket, not only the internal socket [3](#0-2) . The server factory itself acknowledges this ordering assumption is fragile: "Only the HookService calls should arrive through the internal socket. Requests coming from there would already be running in a transaction..." [4](#0-3) , and a test explicitly documents the gap: "we should stop serving HookService on the external socket given it is a service intended only to be used internally by Gitaly for hook callbacks," referencing gitaly issue #3746 [5](#0-4) .

Handlers such as `PreReceiveHook` perform no check that the caller arrived via the internal socket/backchannel — they only validate the repository argument via `locator.ValidateRepository` [6](#0-5) , then forward attacker-controlled `EnvironmentVariables`, `GitPushOptions`, and stdin straight into `s.manager.PreReceiveHook` [7](#0-6) . This is architecturally analogous to the `deposit`/`UniProxy` bug: a function meant to be reachable only from one trusted, gated caller is instead reachable directly by any client that can talk to the external API, allowing that caller to skip the legitimate `git-receive-pack` orchestration (quarantine setup, actual object push, `OperationService` transaction context) that is supposed to precede the hook's execution.

By contrast, the newer `SignalPostReceiveReady` RPC in the same service was hardened against exactly this pattern by explicitly checking `backchannel.GetPeerID(ctx)` and rejecting calls that don't originate from Praefect's backchannel [8](#0-7) , confirming that the older `PreReceiveHook`/`PostReceiveHook`/`UpdateHook`/`ReferenceTransactionHook` RPCs lack equivalent internal-only enforcement.

### Impact Explanation
Any client with access to Gitaly's external gRPC endpoint (the same access level used for ordinary `git push`/`fetch`/RPC operations) can directly invoke `PreReceiveHook`/`PostReceiveHook`/`UpdateHook`/`ReferenceTransactionHook` against an arbitrary repository it has access to, without going through an actual `git-receive-pack` invocation. This can be used to:
- Trigger Rails `/internal/allowed` access-check calls and reference-counter increment/decrement out of band, independent of any real push, potentially confusing concurrency/locking assumptions tied to the reference counter.
- Supply attacker-controlled `EnvironmentVariables` that are passed down toward custom-hook execution (`internal/gitaly/hook/custom.go`), which — depending on how those variables are merged into the subprocess environment — could influence custom hook behavior with attacker-chosen values.
- Bypass the implicit contract that these RPCs are only exercised after Gitaly's own quarantine/transaction setup, since a direct external call supplies its own `Repository`/quarantine fields without an accompanying legitimate object quarantine having been created by `git-receive-pack`.

I was not able to fully verify, within the available exploration budget, exactly how far attacker-supplied `EnvironmentVariables` propagate into custom-hook subprocess environments in `internal/gitaly/hook/custom.go` (the grep found matches but the file contents were not read), so the concrete degree of environment/argument injection achievable through custom hooks remains unconfirmed and should be validated directly against that file.

### Likelihood Explanation
Likelihood is moderate: exploitation requires only an authenticated client capable of reaching Gitaly's external gRPC socket for a given repository (the same access level as a normal push/fetch client), with no additional privilege escalation needed — this mirrors the "anyone can call `deposit` directly" pattern from the reference report. The issue is also independently acknowledged in-repo (test comment referencing gitaly issue #3746), indicating it is a known, real architectural gap rather than a speculative one.

### Recommendation
Register `HookService` only on the internal gRPC listener (as `SignalPostReceiveReady`-style backchannel checks do for the newer RPC), or add an explicit internal-socket/backchannel-token check at the top of `PreReceiveHook`, `PostReceiveHook`, `UpdateHook`, and `ReferenceTransactionHook` handlers, consistent with the pattern already implemented in `SignalPostReceiveReady` [9](#0-8) , so these RPCs reject any request that did not originate from `gitaly-hooks` via the internal socket.

### Proof of Concept
1. Obtain a gRPC connection to Gitaly's external listener with valid credentials for a target repository (the same level of access a normal git client has).
2. Call `HookService.PreReceiveHook` (or `PostReceiveHook`/`UpdateHook`/`ReferenceTransactionHook`) directly with a crafted `PreReceiveHookRequest{Repository: <target repo>, EnvironmentVariables: [...], GitPushOptions: [...]}` and arbitrary stdin, exactly as shown being exercised through the external socket in the existing test `TestPreReceiveHook_GitlabAPIAccess` [10](#0-9) .
3. Observe that the RPC executes fully (triggering the Rails `/internal/allowed` call and reference counter changes) without any real `git-receive-pack` invocation or quarantine having occurred, and without any check that the call came from the internal socket/`gitaly-hooks`.

func dialGitaly(ctx context.Context, payload gitcmd.HooksPayload) (*grpc.ClientConn, error) {
	var dialOpts []grpc.DialOption
	if payload.InternalSocketToken != "" {
		dialOpts = append(dialOpts, grpc.WithPerRPCCredentials(gitalyauth.RPCCredentialsV2(payload.InternalSocketToken)))
	}

	// Propagate correlation ID
	unaryInterceptors := []grpc.UnaryClientInterceptor{
		labkitcorrelation.UnaryClientCorrelationInterceptor(
			labkitcorrelation.WithClientName("gitaly-hooks"),
		),
	}
	streamInterceptors := []grpc.StreamClientInterceptor{
		labkitcorrelation.StreamClientCorrelationInterceptor(
			labkitcorrelation.WithClientName("gitaly-hooks"),
		),
	}

	if spanContext, err := tracing.PropagateFromEnv(os.Environ()); err == nil {
		unaryInterceptors = append(unaryInterceptors, tracing.UnaryPassthroughInterceptor(spanContext))
		streamInterceptors = append(streamInterceptors, tracing.StreamPassthroughInterceptor(spanContext))
	}

	dialOpts = append(dialOpts,
		grpc.WithChainUnaryInterceptor(unaryInterceptors...),
		grpc.WithChainStreamInterceptor(streamInterceptors...),
	)
	conn, err := client.New(ctx, "unix://"+payload.InternalSocket, client.WithGrpcOptions(dialOpts))
	if err != nil {
		return nil, fmt.Errorf("error when dialing: %w", err)
	}

	return conn, nil
