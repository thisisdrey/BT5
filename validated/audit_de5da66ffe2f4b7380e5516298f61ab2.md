### Title
Priority-floor parse-failure path forces full ed25519 verification for a class of packets that never pay a fee - (File: `core/src/sigverify.rs`)

### Summary
`apply_priority_floor_to_batch` treats any packet for which `calculate_priority_from_bytes` fails as `any_kept = true`, i.e. it is left un-discarded and proceeds to `ed25519_verify_serial` / `verify_packet` even when the scheduler priority floor is saturated. `calculate_priority_from_bytes` fails at a later, stricter parsing stage (`RuntimeTransaction::<SanitizedTransactionView>::try_new` and `transaction_configuration()`, which validate compute-budget instructions/heap-size) than `verify_packet`, which only re-runs the earlier, looser `SanitizedTransactionView::try_new_sanitized` check before doing the real signature-verification crypto.

### Finding Description
`apply_priority_floor_to_batch` (`core/src/sigverify.rs:413-440`) calls `calculate_priority_from_bytes(bank, data)` (`core/src/transaction_priority.rs:73-88`) per packet. That function chains three fallible steps:
1. `SanitizedTransactionView::try_new_sanitized` — basic wire-format parse.
2. `RuntimeTransaction::<SanitizedTransactionView<_>>::try_new(...)` — builds `CachedTransactionMeta`, which includes `ComputeBudgetInstructionDetails::try_from(...)` / `InstructionMeta::try_new(...)` (`runtime-transaction/src/runtime_transaction/transaction_view.rs:68-121`).
3. `runtime_tx.transaction_configuration(&bank.feature_set)` — converts details to concrete limits, which can fail (e.g. tx-v1 heap-size range/alignment check in `runtime-transaction/src/transaction_meta.rs:156-164`).

If *any* of these three steps fails, `calculate_priority_from_bytes` returns `None`, and in `apply_priority_floor_to_batch` this maps to the `_ => any_kept = true` branch (`core/src/sigverify.rs:436`) — the packet is **not** marked `discard`, regardless of the floor value, and the comment explicitly says "Unparseable packets are kept and left for downstream rejection" (`core/src/sigverify.rs:430`).

The actual downstream sigverify check, `verify_packet` (`perf/src/sigverify.rs:20-63`), only repeats step (1) — `SanitizedTransactionView::try_new_sanitized` — and then goes straight to real ed25519 `signature.verify(...)` calls (`perf/src/sigverify.rs:43-52`). It never calls `RuntimeTransaction::try_new` or `transaction_configuration()`, so it has no knowledge of compute-budget/heap-size sanitization failures.

Consequently, an attacker can build a minimal, wire-format-valid transaction (passes step 1) that deliberately fails step 2 or 3 — e.g. a duplicate/invalid compute-budget instruction that makes `ComputeBudgetInstructionDetails::try_from` return an error, or (for tx-v1) an out-of-range/misaligned heap size that fails the check at `runtime-transaction/src/transaction_meta.rs:156-164`. For such a packet:
- `calculate_priority_from_bytes` returns `None` → floor check cannot drop it, no matter how saturated the floor is.
- `verify_packet` still parses it successfully at step 1 and performs full ed25519 signature verification.

This transaction will always be rejected downstream in `receive_and_buffer.rs`'s `translate_to_runtime_view` (same checks, `core/src/banking_stage/transaction_scheduler/receive_and_buffer.rs:394-398`) and thus never pays any fee or reaches execution — meaning the attacker forces genuinely expensive, unbounded, unpaid cryptographic work exactly during the state (saturated priority floor) meant to bound that cost.

### Impact Explanation
This is a CPU-exhaustion / QoS-evasion issue in the sigverify hot path: it defeats the intended purpose of `SchedulerPriorityFloor` (`banking-stage-ingress-types/src/lib.rs:71-95`, wired into `SigVerifyStage`/`tpu.rs:277-292`) — cheap pre-verification rejection of below-floor traffic — for a specific, attacker-craftable subclass of packets. The impact is scoped to sigverify-stage CPU usage (elliptic-curve verify operations) being spent on packets that are guaranteed to never pay a fee, matching the "grossly underpriced pre-fee work" / DoS bounty category for an unstaked TPU-facing attacker.

### Likelihood Explanation
Requires only: (1) the scheduler to have published a nonzero floor (an ordinary condition under load, per `SaturationState`/`scheduler_controller.rs`), and (2) the attacker to send a flood of packets that are valid wire-format transactions but fail compute-budget/heap sanitization. Both are fully within reach of an unstaked remote client sending arbitrary packets to a leader's public TPU port — no keys, stake, or config needed. The attack is trivially repeatable at arbitrary volume, limited only by attacker bandwidth/QUIC connection quotas, which is orthogonal to this bug.

### Recommendation
Make the priority-floor drop decision reuse exactly the same "cheap-parse success" criterion that `verify_packet` uses (i.e., only require that `SanitizedTransactionView::try_new_sanitized` succeeds) rather than the stricter, later-failing `calculate_priority_from_bytes` chain. Concretely, in `apply_priority_floor_to_batch`, treat compute-budget/`transaction_configuration` failures the same as a below-floor priority (discard) instead of `any_kept = true`, since such packets are guaranteed to be rejected by `verify_packet`/downstream sanitization anyway and can be dropped immediately without loss of legitimate traffic. Alternatively, tighten `verify_packet` to also perform the compute-budget/config sanitization check before running signature verification, so both paths share one authoritative "cheap reject" surface.

### Proof of Concept
```rust
// core/src/sigverify.rs (new test)
#[test]
fn priority_floor_does_not_drop_compute_budget_sanitize_failure() {
    // Build a versioned transaction that parses fine as `SanitizedTransactionView`
    // (valid header/signature count) but fails compute-budget instruction
    // sanitization, e.g. by including a duplicate SetComputeUnitLimit
    // compute-budget instruction, or (for tx-v1) an out-of-range heap size.
    let (bank, mint) = test_bank_with_lamports_per_signature(5_000);
    let bytes = make_tx_bytes_with_duplicate_compute_budget_ix(&mint, bank.last_blockhash());

    // 1. Priority-floor check cannot compute a priority for this packet.
    assert!(calculate_priority_from_bytes(&bank, &bytes).is_none());

    // 2. Yet `verify_packet`'s own cheap check (SanitizedTransactionView parse)
    //    succeeds, so it proceeds to real ed25519 signature verification.
    let view = SanitizedTransactionView::try_new_sanitized(&bytes[..], &sanitize_config());
    assert!(view.is_ok());

    // 3. Confirm apply_priority_floor_to_batch keeps the packet regardless of floor.
    let mut batch = PacketBatch::from(vec![Packet::from_data(None, &bytes).unwrap()]);
    let (dropped, all_below) = apply_priority_floor_to_batch(&mut batch, u64::MAX, &bank);
    assert_eq!(dropped, 0);
    assert!(!all_below);
    assert!(!batch[0].meta().discard());
}
```
Expected result: the packet is never discarded by the floor check no matter how high the floor is set, while a benchmark comparing verify-stage CPU time for a flood of such packets vs. a flood of trivially-garbage (unparseable at step 1) packets would show the former consuming full `ed25519_verify_serial` CPU cost per packet, confirming the bypass.
