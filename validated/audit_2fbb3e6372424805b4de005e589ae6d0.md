### Title
Missing slippage/output-bound protection in `ExchangeInjectContract` and `ExchangeWithdrawContract` allows front-run loss of funds - ([File: actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java])

### Summary
The reported bug class is a hard-coded/missing slippage parameter that lets a swap execute at an arbitrarily bad price, causing user fund loss. java-tron's bancor-style TRX/TRC10 `Exchange` (v1/v2) pools have this exact protection gap in the inject and withdraw paths, while the sibling "sell" path was explicitly hardened with a user-supplied bound.

### Finding Description
`ExchangeTransactionContract` (a true swap) includes an `expected` field that the caller sets and that `ExchangeTransactionActuator` enforces against the computed output before execution: [1](#0-0) 
Likewise `MarketSellAssetContract` treats `buy_token_quantity` as a caller-chosen "min to receive" bound: [2](#0-1) 

However, `ExchangeInjectContract` and `ExchangeWithdrawContract` — which also convert one side's `quant` into a counter-token amount computed from the *live* pool ratio at execution time — carry no equivalent bound field at all: [3](#0-2) 
In `ExchangeInjectActuator.execute`, `anotherTokenQuant` (the amount of the paired token the account will be debited/credited) is derived purely from `firstTokenBalance`/`secondTokenBalance` at execution time, with no user-supplied floor/ceiling to compare against: [4](#0-3) 
The corresponding validation in `doValidate()` only checks that the calculated amount is `> 0` and within the global balance limit — never against caller intent: [5](#0-4) 
`ExchangeWithdrawActuator` has the identical pattern: `anotherTokenQuant` is computed from the current pool ratio with only a "not precise enough" rounding check, no min-out bound requested by the withdrawer: [6](#0-5) 

### Impact Explanation
Because `ExchangeInjectContract`/`ExchangeWithdrawContract` transactions are public and pending on the network before being packed into a block, an attacker can observe a queued inject/withdraw transaction and submit an `ExchangeTransactionContract` swap ahead of it to shift `firstTokenBalance`/`secondTokenBalance`. When the victim's inject/withdraw then executes, `anotherTokenQuant` is recomputed against the manipulated ratio:
- On inject, the victim can be forced to deposit far more of the counter-token than they intended (direct fund loss with no cap).
- On withdraw, the victim can receive far less of the counter-token than expected for the liquidity given up.

Since these funds are TRX/TRC10 balances moved via `accountCapsule.setBalance`/`reduceAssetAmountV2`/`addAssetAmountV2`, this is a concrete, unauthorized-value-transfer style loss of user funds reachable by any account that can submit signed transactions — matching the High severity of the original slippage report.

### Likelihood Explanation
Both `ExchangeInjectContract` and `ExchangeWithdrawContract` are reachable via ordinary signed transactions (or the `/wallet/exchangeinject` and `/wallet/exchangewithdraw` HTTP endpoints), require no special privilege, and the front-running technique (submitting a competing `ExchangeTransactionContract` with higher energy/priority before the target tx is packed) is a well-known and practically executable MEV/sandwich pattern on any chain with public mempools/broadcast. The bug is a pure missing-validation issue, not a hypothetical: the actuators already contain the numeric hooks (`anotherTokenQuant`) where a user-supplied bound would be compared but no such comparison exists for inject/withdraw.

### Recommendation
Add an explicit caller-supplied bound field to `ExchangeInjectContract` and `ExchangeWithdrawContract` (e.g., `expected`/`min_another_token_quant` for withdraw, `max_another_token_quant` for inject), and enforce it in `ExchangeInjectActuator.doValidate()` / `ExchangeWithdrawActuator.doValidate()` the same way `tokenExpected` is enforced in `ExchangeTransactionActuator.doValidate()`, so a transaction reverts rather than executing at an unfavorable ratio.

### Proof of Concept
1. Attacker monitors the mempool/broadcast queue for a victim's `ExchangeInjectContract` (or `ExchangeWithdrawContract`) transaction on exchange `exchange_id`.
2. Attacker broadcasts an `ExchangeTransactionContract` swap against the same `exchange_id` with sufficient `quant` to materially shift `firstTokenBalance`/`secondTokenBalance`, ensuring it is confirmed first (e.g., via bandwidth/energy prioritization).
3. Once the pool ratio has moved, the victim's `ExchangeInjectActuator.execute` (or `ExchangeWithdrawActuator.execute`) runs, computing `anotherTokenQuant` from the now-manipulated `firstTokenBalance`/`secondTokenBalance` at lines [7](#0-6) .
4. The victim's account is debited/credited using this manipulated `anotherTokenQuant` via `reduceAssetAmountV2`/`addAssetAmountV2`, with no validation step available to reject an unfavorable outcome — resulting in direct loss relative to the ratio the victim observed when signing.
