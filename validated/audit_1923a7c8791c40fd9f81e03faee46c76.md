### Title
Missing zero-index fallback in `RewardsDistributor._calculateTokenDelta` lets any depositor claim `balance * 1e18` reward tokens the moment a reward speed is set - ([File: contracts/RewardsDistributor.sol](contracts/RewardsDistributor.sol))

### Summary
When a reward token's index is freshly initialized to `INITIAL_INDEX` (1e18) but has not yet grown past it, `_calculateTokenDelta` fails to substitute the `INITIAL_INDEX` fallback for accounts whose stored `accountIndexOf` is 0 (the uninitialized default). The resulting `_deltaIndex` equals the full `INITIAL_INDEX`, so a permissionless call to `updateBeforeMintOrBurn` accrues `balance.wadMul(1e18)` reward tokens to the caller, and `claimRewards` pays out the distributor's entire reward token balance.

### Finding Description
`tokenStates[token_]` is only initialized inside `_updateTokenSpeed`, where it is set to `TokenState({index: INITIAL_INDEX, timestamp: block.timestamp})` [1](#0-0) .

The uninitialized-account fallback in `_calculateTokenDelta` only applies when the index has *strictly* grown beyond `INITIAL_INDEX`:

```solidity
if (_accountIndex == 0 && _tokenIndex > INITIAL_INDEX) {
    _accountIndex = INITIAL_INDEX;
}
uint256 _deltaIndex = _tokenIndex - _accountIndex;
_tokensDelta = token_.balanceOf(account_).wadMul(_deltaIndex);
``` [2](#0-1) 

In the window where `_tokenIndex == INITIAL_INDEX` (i.e., the same block/timestamp in which the governor sets the speed, before `_calculateTokenIndex` can advance it), an account with `accountIndexOf == 0` keeps `_accountIndex = 0`, so `_deltaIndex = INITIAL_INDEX` and `_tokensDelta = balance * 1e18`.

The attack path is fully permissionless:
1. Attacker deposits underlying into a `DepositToken` (or holds `DebtToken` balance) so `token_.balanceOf(attacker) > 0`.
2. Governor (or keeper via `syncTokenSpeed`) calls `updateTokenSpeed`, initializing `tokenStates[token_].index = INITIAL_INDEX`.
3. In the same block, attacker calls `updateBeforeMintOrBurn(token_, attacker)` — a public function gated only by `tokenStates[token_].index > 0` [3](#0-2) . `_updateTokenIndex` is a no-op because `_deltaTimestamps == 0` [4](#0-3) , then `_updateTokensAccruedOf` writes `accountIndexOf = INITIAL_INDEX` and adds the inflated delta to `tokensAccruedOf[attacker]` [5](#0-4) .
4. Attacker calls `claimRewards(attacker, tokens)`; `_transferRewardIfEnoughTokens` transfers `min(tokensAccruedOf, distributorBalance)` of `rewardToken` — effectively the whole balance [6](#0-5) .

The same-block window is reliable to hit: `updateTokenSpeed`/`syncTokenSpeed` transactions are public mempool events, and the attacker can also atomically bundle via `Operator.execute`. No modifier (`nonReentrant` only wraps `claimRewards`, not `updateBeforeMintOrBurn`), pause flag, or health check intervenes. Step 2–4 can also repeat for every newly added reward token, since `tokens.push` happens for each fresh token.

### Impact Explanation
Direct theft of unclaimed yield: the attacker drains the entire `rewardToken` balance held by the `RewardsDistributor` that was accrued for all legitimate suppliers/borrowers. With any nonzero token balance (dust suffices — `wadMul` of 1 wei × 1e18 already exceeds any realistic reward balance), `tokensAccruedOf` exceeds the contract's balance, so the payout is capped only by `balanceOf(address(this))`. All other users' accrued rewards become unclaimable.

### Likelihood Explanation
Requires only: (a) the attacker holds or mints a `DepositToken`/`DebtToken` balance in the same transaction beforehand, and (b) lands `updateBeforeMintOrBurn` in the same block as the speed-setting transaction — a routine mempool back-run. `syncTokenSpeed` is callable by a keeper and `updateBeforeMintOrBurn` by anyone, so no privileged role is needed on the attack path. Every reward-token initialization event is a fresh opportunity.

### Recommendation
Change the fallback condition in `_calculateTokenDelta` to `>= INITIAL_INDEX` (or equivalently `_accountIndex == 0 → _accountIndex = _tokenIndex < INITIAL_INDEX ? _tokenIndex : INITIAL_INDEX`), so a zero stored index can never produce a nonzero `_deltaIndex`. Alternatively, initialize `accountIndexOf` to `INITIAL_INDEX` on first touch, or require `_tokenIndex > INITIAL_INDEX` before computing deltas.

### Proof of Concept
```typescript
// Hardhat fork test sketch (test/RewardDistributor.test.ts fixture style)
// 1. Attacker deposits MET -> msdMET balance > 0
await depositToken.connect(attacker).deposit(attacker.address, parseEther('1'));

// 2. Governor enables rewards for msdMET (sets index = INITIAL_INDEX, ts = now)
await rewardsDistributor.connect(governor).updateTokenSpeed(msdMET.address, parseEther('1'));

// 3. Same block: attacker calls permissionless index update
await network.provider.send('evm_setAutomine', [false]);
await rewardsDistributor.connect(attacker).updateBeforeMintOrBurn(msdMET.address, attacker.address);
await network.provider.send('evm_mine');

// tokensAccruedOf[attacker] == 1e18 * 1e18 >> distributor balance
expect(await rewardsDistributor.tokensAccruedOf(attacker.address))
  .to.eq(parseEther('1').wadMul(parseEther('1')));

// 4. Fund distributor with rewardToken, attacker claims everything
await rewardToken.mint(rewardsDistributor.address, parseEther('1000'));
await rewardsDistributor.connect(attacker).claimRewards(attacker.address, [msdMET.address]);
expect(await rewardToken.balanceOf(attacker.address)).to.eq(parseEther('1000'));
```

Key assertion: `tokenStates.index == INITIAL_INDEX` and `accountIndexOf == 0` yield `_deltaIndex == 1e18` before any time elapses, inflating accrual by ~1e18×.
