Based on the evidence I was able to gather, I found a strong structural analog to the LES bug in the custom `substrate/client/hop` module. I could not fully read `lib.rs`/`pool.rs` in the final round due to tool errors, so parts of the internal wiring (exact runtime-detection code path) are inferred from the module's own README documentation rather than directly-read source; I flag that explicitly below.

### Title
HOP maintenance task silently drops "promoted" submissions when runtime lacks `HopRuntimeApi`, while RPC reports success - (File: `substrate/client/hop/src/promotion.rs`, `substrate/client/hop/README.md`)

### Summary
The `sc-hop` client component exposes an `hop_submit` RPC that accepts a blob, stores it in a local pool, and returns a `SubmitResult` that looks like success. The actual on-chain effect only happens later, when a background maintenance task "promotes" pooled entries into a real extrinsic via `HopPromoter::promote` and submits it to the transaction pool [1](#0-0) . Per the module's own documentation, `build_maintenance_task` "detects `HopRuntimeApi` support at startup and falls back to cleanup-only if the runtime doesn't implement it" [2](#0-1) . This is structurally identical to the LES bug: one code path (the RPC submit) accepts the request and reports it as accepted, while a required downstream forwarding step (promotion to the actual chain state) is silently skipped under a specific condition, with no error surfaced to the caller.

### Finding Description
The `hop_submit(data, recipients, signature, signer, submit_timestamp) -> SubmitResult` RPC stores a blob for later delivery, with the runtime-declared cap being "the authoritative" size limit, and no separate node-side ceiling [3](#0-2) . This immediately returns a `SubmitResult` to the caller, giving the impression that submission succeeded.

The real work of turning that pooled blob into an actual on-chain extrinsic happens asynchronously via `RuntimeApiPromoter::promote`, which builds a promotion extrinsic from the runtime API and pushes it into the local transaction pool with `tx_pool.submit_local(...)` [1](#0-0) . This promotion path is driven by `build_maintenance_task`, wired up conditionally based on whether the connected runtime exposes `HopRuntimeApi` [4](#0-3) .

When the runtime does not implement `HopRuntimeApi` (e.g. node paired with an older/foreign runtime, during a staged runtime upgrade, or misconfigured chain spec), the task documented behavior is to fall back to "cleanup-only": it will continue accepting and storing submissions via the RPC (since `hop_submit` performs no runtime-capability check before accepting) but will never call `promote()`, so entries just sit until they expire via `--hop-retention-secs` and are dropped by the cleanup routine [5](#0-4) . This mirrors op-geth's LES `SendTx`, which added to the tx pool but never called out to the sequencer RPC — the "front door" accepts the write, but the required forwarding step to make it effective is silently absent.

### Impact Explanation
A caller submitting data through `hop_submit` receives a success-looking `SubmitResult` even though, on a node whose runtime lacks `HopRuntimeApi`, the data will never be promoted into an actual extrinsic and will eventually be purged after `hop-retention-secs`. This is a permanent loss of the submitted work/state with a misleading success response — the same "false acceptance, no actual delivery" invariant break identified in the source report, applied to this repo's local RPC/promotion pipeline instead of LES/sequencer forwarding.

### Likelihood Explanation
This does not require a malicious peer, validator, or admin — it is triggered purely by ordinary operating conditions (a node connected to a runtime build that does not (yet) implement `HopRuntimeApi`, e.g. during staged rollout or misconfiguration), and the RPC itself performs no capability check before accepting submissions, so unprivileged users hit this silently under normal use.

### Recommendation
`hop_submit` should verify `HopRuntimeApi` support against the currently connected runtime before accepting and storing a submission, and return an explicit error/rejection (not a `SubmitResult` implying success) when the runtime does not support promotion — matching the recommendation in the source report to make both paths consistent rather than letting one silently drop.

### Proof of Concept
Conceptual reproduction (based on documented behavior, not a full runtime trace since `lib.rs`/`pool.rs` contents were not fully retrievable in this session):
1. Run a node with `--enable-hop` connected to a runtime build lacking the `HopRuntimeApi` implementation.
2. Call `hop_submit(data, recipients, signature, signer, submit_timestamp)` — the call succeeds and returns a `SubmitResult`.
3. Because the runtime lacks `HopRuntimeApi`, `build_maintenance_task` runs in "cleanup-only" mode and never calls `HopPromoter::promote`.
4. After `--hop-retention-secs` elapses, the entry is purged with no on-chain effect ever having occurred, and the original caller has no indication that promotion never happened.

**Caveat:** I was unable to read `substrate/client/hop/src/lib.rs` and `pool.rs` directly in this session (tool errors on the final iteration), so the exact call sequence between `hop_submit` and the maintenance task is based on the module's README description rather than confirmed by reading the RPC handler source. A Devin session with full file access should verify `lib.rs` and `rpc.rs` to confirm there is no capability check gating `hop_submit` before finalizing this as a concrete, exploitable finding.

	fn promote(

		signer: MultiSigner,
		signature: MultiSignature,
		submit_timestamp: u64,
