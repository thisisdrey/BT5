### Title
Division-by-zero on unvalidated `totalEnergyWeight` in `EnergyProcessor.calculateGlobalEnergyLimit` crashes energy accounting for any TVM call — ([File: chainbase/src/main/java/org/tron/core/db/EnergyProcessor.java])

### Summary
`EnergyProcessor.calculateGlobalEnergyLimit()` guards the division by `totalEnergyWeight` only when `dynamicPropertiesStore.allowNewReward()` is true; otherwise it falls back to a Java `assert totalEnergyWeight > 0;`, which is a no-op in production JVMs (assertions are disabled by default, no `-ea` flag). If `totalEnergyWeight` is ever `0` while the hardened-calculation path is active, execution proceeds into `calculateGlobalLimitV1`, which performs `BigInteger.valueOf(totalLimit).divide(BigInteger.valueOf(totalWeight))` — an unguarded division by a value that can legitimately be zero, throwing `ArithmeticException` from a hot path invoked on every energy-consuming transaction/contract call.

### Finding Description
`calculateGlobalEnergyLimit` reads `totalEnergyWeight` directly from `DynamicPropertiesStore` and only special-cases zero under the `allowNewReward()` feature flag: [1](#0-0) 

When `allowNewReward()` is false (a valid runtime configuration on chains/forks where that feature has not been activated), the code relies on `assert totalEnergyWeight > 0;` to enforce the invariant. Java assertions are disabled by default in production (`-ea` is not part of standard `java` invocation), so this check silently does nothing. Execution then falls through to the hardened path: [2](#0-1) 

`calculateGlobalLimitV1` performs `BigInteger.divide(BigInteger.valueOf(totalWeight))` with no zero check, identical in structure to the FreeRDP bug class where an attacker/protocol-supplied field (`nBlockAlign`) reaches a `%`/`/` operator without a zero guard. Here the "unvalidated denominator" is the global `totalEnergyWeight` counter, which is mutated on every freeze/unfreeze operation (`repo.addTotalEnergyWeight(...)`) reachable from ordinary `FreezeBalanceV2`/`UnfreezeBalanceV2`/TVM `freezeBalanceV2`/`unfreezeBalanceV2` native contracts: [3](#0-2) 

`calculateGlobalEnergyLimit` itself is invoked from `useEnergy()`, which every energy-consuming transaction and TVM call path executes: [4](#0-3) 

The counterpart in `BandwidthProcessor.calculateGlobalNetLimit` explicitly adds an unconditional `if (totalNetWeight == 0) return 0;` guard regardless of `allowNewReward()`: [5](#0-4) 

but the energy path is missing this unconditional guard — it is inconsistently protected only under one feature flag, leaving the legacy/non-`allowNewReward()` configuration exposed.

### Impact Explanation
An uncaught `ArithmeticException` thrown from `BigInteger.divide` inside `calculateGlobalEnergyLimit`/`calculateGlobalLimitV1`, invoked from `useEnergy()` during ordinary contract-triggering transactions, is not specifically caught for this exception type in the surrounding actuator/VM call stack, so it can propagate up through transaction processing and crash the node process or halt block application — a Medium/High-severity denial-of-service matching "node crash or halt" in the acceptance criteria.

### Likelihood Explanation
Reaching `totalEnergyWeight == 0` under the non-`allowNewReward()` branch requires the network-wide aggregate to actually be zero (e.g., a freshly-initialized chain/private network before the reward feature is enabled and before/immediately after all energy-freezers have unfrozen), which is a state achievable during chain bootstrap/test-network operation rather than by a single malicious transaction against an established mainnet with existing frozen balances. This lowers the likelihood versus a fully attacker-controlled trigger, but the missing symmetry with `BandwidthProcessor`'s unconditional guard indicates the omission is a genuine defect rather than an intentionally accepted invariant, and any transaction that consumes energy while this state holds (including an ordinary `TriggerSmartContract` from any account) exercises the vulnerable code path.

### Recommendation
Add an unconditional zero-check for `totalEnergyWeight` in `EnergyProcessor.calculateGlobalEnergyLimit` (mirroring `BandwidthProcessor.calculateGlobalNetLimit`'s `if (totalNetWeight == 0) return 0;`) instead of relying on `assert`, and audit `calculateGlobalLimitV1`/`calculateGlobalLimitV2` in `ResourceProcessor` to guard against zero denominators directly rather than trusting callers.

### Proof of Concept
Not independently reproducible from static analysis alone — no test in the indexed codebase exercises `allowNewReward()==false` together with `totalEnergyWeight==0` through the hardened (`allowHardenResourceCalculation()`) path; existing tests (`CalculateGlobalLimitHardenTest`) only exercise nonzero-weight parity/overflow cases. Confirming real-world exploitability would require verifying whether `totalEnergyWeight` can reach exactly 0 on a live/mainnet-equivalent chain state while `allowNewReward()` is false and the hardened calculation flag is enabled — this could not be fully confirmed from the available indexed code and should be validated with a running node/test harness.

  public long calculateGlobalEnergyLimit(AccountCapsule accountCapsule) {
    long frozeBalance = accountCapsule.getAllFrozenBalanceForEnergy();
    if (dynamicPropertiesStore.supportUnfreezeDelay()) {
      return calculateGlobalEnergyLimitV2(frozeBalance);
    }
    if (frozeBalance < TRX_PRECISION) {
      return 0;
    }

    long totalEnergyLimit = dynamicPropertiesStore.getTotalEnergyCurrentLimit();
    long totalEnergyWeight = dynamicPropertiesStore.getTotalEnergyWeight();
    if (dynamicPropertiesStore.allowNewReward() && totalEnergyWeight <= 0) {
      return 0;
    } else {
      assert totalEnergyWeight > 0;
    }
    if (hardenCalculation()) {
      return calculateGlobalLimitV1(frozeBalance, totalEnergyLimit, totalEnergyWeight);
    }
    long energyWeight = frozeBalance / TRX_PRECISION;
    return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
  }
