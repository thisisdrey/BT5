### Title
Unbounded `GitAlternateObjectDirectories` in Repository proto causes unbounded per-command env growth and repeated object-directory scans - ([File: internal/git/gitcmd/command_factory.go])

### Summary
The `Repository` protobuf message exposes a client-controlled, unbounded repeated string field `GitAlternateObjectDirectories`, which is used on every Git command invocation to construct the `GIT_ALTERNATE_OBJECT_DIRECTORIES` environment variable. There is no upper bound on the number of entries a caller can supply, and this list is consumed on every single git subprocess spawn for that repository, directly mirroring the `poolColl.tokens[]` unbounded-array pattern from the referenced report: an attacker/caller-controlled list that grows without limit and is fully scanned/processed on every subsequent operation.

### Finding Description
`Repository.GitAlternateObjectDirectories` is a `repeated string` field on the RPC-level `Repository` message with no documented or enforced maximum length: [1](#0-0) 

Every time Gitaly spawns a Git subprocess for a given repository, `ExecCommandFactory.newCommand` takes this field directly off the request-derived repository and feeds it into `alternates.Env(...)`, which becomes part of the git subprocess environment via `GIT_ALTERNATE_OBJECT_DIRECTORIES`: [2](#0-1) 

This means the field is fully re-processed (turned into an env var, parsed by Git as a colon-separated alternate object search path) on **every** git invocation for the repository, for the lifetime of any RPC that carries this field (e.g., any RPC re-entered from Rails during `pre-receive` access checks, which explicitly re-populates `GitObjectDirectory`/`GitAlternateObjectDirectories` on the `Repository` message as documented in the quarantine flow): [3](#0-2) 

Unlike the local alternates-file walk in `internal/git/dirs.go`, which enforces a `maxAlternatesDepth` of 5 to bound recursive alternates-file resolution: [4](#0-3) 

there is no equivalent bound on the number of entries supplied via the RPC-level `GitAlternateObjectDirectories` field itself. Every Git process spawned with a large number of alternate directories must open/stat each one to build its object search path, and Git will scan through this full alternates search path on every object lookup within that process (for `cat-file`, `rev-parse`, `diff`, `log`, etc. — i.e. the hot path of nearly all read/write RPCs). This is architecturally identical to the reported bug class: an attacker-influenced list (`poolColl.tokens[]` in the original report vs. `GitAlternateObjectDirectories` here) that has no size cap and is iterated on every subsequent call (`getVC()` there vs. every spawned `git` subprocess here), causing gradually increasing per-call cost.

### Impact Explanation
A caller able to control the `Repository.GitAlternateObjectDirectories` field on a request (this is legitimately populated end-to-end from Rails' access-check callback path during pushes, as documented) can supply an arbitrarily large list of directory strings. Since this field is threaded into every subsequent git subprocess's environment for the request/transaction scope, each invocation incurs cost proportional to the list size (environment construction, and Git internally opening/stat'ing/parsing an `objects/info/alternates`-equivalent search path for each entry). In the worst case, with a sufficiently large list, this can degrade performance of every git command run against the repository in that RPC scope, or exhaust process resources (argument/environment size limits, file descriptor/stat overhead), producing a DoS of the RPC handler — analogous to the "Out of Gas"/"Block Gas Limit" DoS in the original report, but manifesting as CPU/latency exhaustion or process failure in Gitaly.

### Likelihood Explanation
Moderate. This isn't reachable from an entirely untrusted, unauthenticated user directly crafting arbitrary RPCs unless the calling layer (Rails or another internal client of the gRPC API) fails to bound the number of alternate directories it forwards. It requires a privileged/internal caller (Rails or a component reusing the object-directory quarantine round-trip) to pass through a very large list, or a bug in path handling that leads to duplication/accumulation of entries across repeated quarantine `Apply` calls. Gitaly-side, there is no defensive validation limiting the size of this repeated field before it's consumed by `newCommand`, so any component that can set this field with many entries can trigger the degradation.

### Recommendation
- Enforce a maximum count (and total byte size) on `Repository.GitAlternateObjectDirectories` in request validation (e.g., in `locator.ValidateRepository` or a dedicated validation step) before it reaches `ExecCommandFactory.newCommand`, similar to the `maxAlternatesDepth` bound already used for the on-disk alternates-file walk in `internal/git/dirs.go`.
- Reject RPCs whose `GitAlternateObjectDirectories` exceeds the bound with an `InvalidArgument` error rather than silently accepting and processing an unbounded list on every git invocation.

### Proof of Concept
Not independently exploitable purely from the indexed code — validating actual reachability from an external, unprivileged RPC caller (versus only internal Rails-to-Gitaly round trips) would require inspecting the full request-validation pipeline and confirming no size cap exists anywhere before `newCommand` consumes the field. This is a concrete architectural gap (unbounded field, consumed per-command with no cap), but I could not confirm within the indexed code that an external/unprivileged caller can set arbitrarily large values for `GitAlternateObjectDirectories` end-to-end (this field is normally set internally via the quarantine/Rails access-check loop-back, not directly by ordinary push/fetch clients). Given the "Reject privileged-actor... no-impact analogs" rule, and the lack of confirmed direct external reachability with unbounded attacker control, this should be treated as a **hardening gap** rather than a confirmed independently-reachable vulnerability from an ordinary user's push/fetch. I recommend a Devin session with full filesystem/build access to trace all producers of `Repository.GitAlternateObjectDirectories` (especially in `internal/gitlabshell`, `internal/gitlab/http_client.go`, and Praefect's request rewriting) to conclusively determine whether an ordinary, unprivileged push/fetch can inflate this field without going through the trusted Rails round trip.
