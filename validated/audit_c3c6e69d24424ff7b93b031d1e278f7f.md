### Title
Adaptive concurrency limit can decay to zero, silently disabling `PackObjectsHook`/RPC concurrency backpressure - (File: `internal/limiter/concurrency_limiter.go`, `internal/limiter/adaptive_calculator.go`)

### Summary
Gitaly's `ConcurrencyLimiter` treats a current limit value of `0` (or less) as "unlimited" and bypasses all queuing/semaphore logic. Under the adaptive limiting feature, the current limit is driven purely by multiplicative decrease of a `Min`/`Max`-bounded integer, and if an operator configures (or leaves default) `Min: 0` for an adaptive limit, sustained backoff events will floor the limit at `0`, which is then interpreted by the consumer as "no limit at all" rather than "min limit" — the same "zero means infinity" flaw as the reported `VariableSupplyERC20Token` bug.

### Finding Description
`ConcurrencyLimiter.Limit` short-circuits all limiting whenever the current limit is non-positive: [1](#0-0) 

The adaptive limit value is computed by `AdaptiveCalculator.calibrateLimits`, which performs a multiplicative decrease clamped only at `setting.Min`: [2](#0-1) 

`AdaptiveLimit.Update` simply stores whatever value it is given and fires the resize hooks, without ever distinguishing "the configured floor is 0" from "there is no limit": [3](#0-2) 

Because `AdaptiveSetting.Min` is an ordinary `int` with no explicit validation forcing it to be `> 0` when adaptive limiting is enabled (confirmed by reading `AdaptiveSetting`/`NewAdaptiveLimit` in `adaptive_limit.go`), an operator who sets (or defaults to) `min_limit = 0` for `[pack_objects_limiting]` (wired up in `internal/cli/gitaly/serve.go`) will see the concurrency limit decay to `0` under sustained CPU/memory/PSI backoff pressure. At that point `ConcurrencyLimiter.Limit`'s `c.currentLimit() <= 0` check causes the limiter to stop limiting entirely — precisely at the moment the system is under the most resource pressure — for both the `PackObjectsHook` limiter and any other RPC wired through `[[concurrency]]`/adaptive limiting.

This mirrors the reported bug class exactly: a value that legitimately decreases toward zero through ordinary system dynamics (mint activity in the ERC20 case; backoff events here) gets reinterpreted as "unlimited" instead of "minimum," defeating the very protection the field was meant to enforce.

### Impact Explanation
`PackObjectsHook` and other concurrency-limited RPCs (e.g. `PostUploadPackWithSidechannel`) are Gitaly's primary backpressure mechanism against resource exhaustion from git-upload-pack/pack-objects operations triggered by ordinary clone/fetch traffic, as described in `doc/backpressure.md`: [4](#0-3) 
If the adaptive limit collapses to zero exactly when the host is under CPU/memory/PSI pressure (the trigger condition for backoff), all queuing and per-repo concurrency caps for the affected RPC disappear, allowing unbounded concurrent `git-pack-objects`/`upload-pack` processes to spawn from ordinary fetch/clone requests — amplifying the very resource exhaustion the adaptive limiter is meant to mitigate. This is a DoS-class impact on an RPC handler resource limit.

### Likelihood Explanation
Likelihood is Medium: it requires the adaptive limiting feature to be enabled (`cfg.PackObjectsLimiting.Adaptive` or any adaptive `[[concurrency]]` entry) with a `Min` (a.k.a. `min_limit`) of `0`, either explicit misconfiguration or an unvalidated zero default, combined with sustained backoff events (real resource pressure) that is itself easy to induce via ordinary heavy but unprivileged git traffic. No privileged access or malicious peer is required — only normal push/fetch/clone load plus a config value of `0`.

### Recommendation
Treat "no limit configured" and "limit floored at zero" as distinct states: either (a) reject/validate `Min == 0` for adaptive limits at config-load time, forcing a minimum of `1`, or (b) change `ConcurrencyLimiter.Limit`'s bypass condition so that `0` is only treated as "unlimited" when the limiter was constructed as a static, non-adaptive `0` (e.g., via an explicit sentinel such as `-1` for "unlimited", never `0` reachable through decay), and always keep at least one concurrency token available once a limit was ever configured as > 0.

### Proof of Concept
1. Configure adaptive pack-objects limiting with `initial_limit = 20`, `max_limit = 100`, `min_limit = 0`, `backoff_factor = 0.5` (wired in `internal/cli/gitaly/serve.go` lines 373–386).
2. Induce sustained CPU/memory/PSI pressure conditions (e.g. via repeated large fetches) so that `waitForEvents`/`calibrateLimits` repeatedly triggers "Multiplicative decrease" (`internal/limiter/adaptive_calculator.go:271-287`); after `ceil(log2(20))` backoff cycles the limit reaches `0` and is clamped there by `Min`.
3. Once `AdaptiveLimit.Current()` returns `0`, `ConcurrencyLimiter.Limit` at `internal/limiter/concurrency_limiter.go:207-209` executes `return f()` unconditionally for every subsequent `PackObjectsHook` invocation, regardless of concurrency, exactly while the host is already under resource pressure — verified by the existing test case `"With a max concurrency of 0"` in `internal/grpc/middleware/limithandler/middleware_test.go:524-546`, which documents that `maxConcurrency: 0` results in zero throttling of any request.

// Update adjusts the current limit value and executes all registered update hooks.
func (l *AdaptiveLimit) Update(val int) {
	l.Lock()
	defer l.Unlock()

	if val != l.current {
		l.current = val
		for _, hook := range l.updateHooks {
			hook(val)
		}
	}
}
