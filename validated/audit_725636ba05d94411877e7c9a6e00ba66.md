## Finding: Multisig "Active" permission scoping is contract-type-only, not target/value-scoped — enabling unrestricted fund movement once a broad permission is authorized

### Title
Active Permission Bitmap Authorizes by ContractType Only, Not by Target Contract or Value — ([File: chainbase/src/main/java/org/tron/common/utils/WalletUtil.java])

### Summary
The ByBit incident succeeded because signers were shown a "masked" but plausible interface for a transaction while what they actually cryptographically authorized (a `sweepERC20`-capable implementation upgrade) had far broader effect than believed — the multisig approval was granted at too coarse a granularity to constrain the real operation. java-tron's on-chain multisig "Active" permission model has the analogous coarseness: an Active permission's authorization is encoded purely as a 32-byte bitmap over `ContractType` values, with no scoping to a target contract address, function selector, or value limit.

### Finding Description
`WalletUtil.checkPermissionOperations` is the sole gate that determines whether a given `Permission` allows a given contract to execute: [1](#0-0) 

It only inspects `contract.getTypeValue()` (e.g. `TriggerSmartContract`, `TransferContract`) against the permission's `operations` bitmap — it never inspects the contract's payload (target contract address, `data`/function selector, or `call_value`). This same check is used both when validating a broadcast transaction's signature weight and when actually authorizing it: [2](#0-1) [3](#0-2) 

Consequently, once an "Active" permission's bitmap enables `TriggerSmartContract` (a routine grant for hot-wallet operational keys, analogous to ByBit's cold→hot transfer signers), any transaction of that type — to *any* contract address, with *any* calldata and *any* `call_value` — satisfies the permission check as long as the aggregate signer weight reaches the threshold. There is no address allow-list, no per-operation-type value cap, and no calldata/selector restriction encoded in the `Permission` protobuf itself (`type`, `operations`, `threshold`, `keys` — see the protocol doc), so a permission intended for narrow operational use (e.g., routine transfers) cannot be constrained to prevent it from being used to call an attacker-controlled or malicious contract that drains funds via arbitrary logic, mirroring the "sweepERC20" surprise-scope escalation in the ByBit exploit.

### Impact Explanation
Any account (exchange hot wallet, custodial multisig, DAO treasury) using TRON's native Active-permission multisig for operational signing is only ever protecting against "wrong contract *type*," not "wrong contract *target* or *value*." If any single authorized-but-lower-trust signing path (compromised device, malicious co-signer, or masked signing UI as in the ByBit case) obtains the required threshold weight for an Active permission that includes `TriggerSmartContract`, the attacker can direct calls to any smart contract, moving unlimited value, with no on-chain constraint enforced by java-tron's permission subsystem. This is a direct analog to unauthorized account operation / theft of funds.

### Likelihood Explanation
This is reachable purely from a single, unprivileged, externally-signed transaction — no witness/committee/p2p involvement is required. Any account owner who configures an Active permission with `TriggerSmartContract` enabled (a very common, near-default operational configuration) is exposed. The attack surface is identical to real-world blind-signing incidents (ByBit, WazirX, Radiant, DMM) which have already demonstrated that multisig signers can be induced to approve transactions whose true effect differs from what they believe, and the chain-level permission model provides no additional backstop once threshold weight is met.

### Recommendation
Extend the `Permission` protobuf and `checkPermissionOperations`/`checkWeight` validation path to support optional finer-grained scoping for `Active` permissions used with `TriggerSmartContract` — e.g., an allow-listed set of target contract addresses and/or a per-permission maximum `call_value`, checked in `WalletUtil.checkPermissionOperations` (and consequently in `TransactionCapsule.checkPermission`/`addSign`, `TransactionUtil.getTransactionSignWeight`, and `Wallet.getTransactionApprovedList`) in addition to the existing contract-type bitmap check.

### Proof of Concept
1. Owner account creates an Active permission (`permissionId=2`) with `operations` bitmap enabling `TriggerSmartContract`, held by two operational keys with threshold 2 (a standard "hot wallet operational" setup).
2. Attacker compromises signing infrastructure enough to get both keys to sign a `TriggerSmartContract` transaction (permissionId=2) whose target is an attacker-deployed malicious contract with a drain function, and `call_value` equal to the account's full balance.
3. `WalletUtil.checkPermissionOperations` only checks that `ContractType.TriggerSmartContract`'s bit is set in the 32-byte `operations` field — it returns `true` regardless of the target address or `call_value`.
4. `TransactionCapsule.checkWeight` confirms threshold weight is met from the two signatures.
5. The transaction executes, transferring the full balance to the attacker's contract — no further on-chain permission check prevents this, exactly mirroring the ByBit scenario where a "correctly typed/permission-granted" transaction masked a fund-draining operation.

```java
  public static boolean checkPermissionOperations(Permission permission, Contract contract)
      throws PermissionException {
    ByteString operations = permission.getOperations();
    if (operations.size() != 32) {
      throw new PermissionException(String.format("operations size must 32, actual: %d",
          operations.size()));
    }
    int contractType = contract.getTypeValue();
    boolean b = (operations.byteAt(contractType / 8) & (1 << (contractType % 8))) != 0;
    return b;
  }
```
