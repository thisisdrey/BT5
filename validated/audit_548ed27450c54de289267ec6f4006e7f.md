### Title
`socialize-debt` omits `accrue`, causing loss write-down (`new-lindex`) to be computed against a stale `index`, understating socialized losses - ([File: mainnet/contracts/vault/v0-vault-ststx.clar])

### Summary
`socialize-debt` (lines 944-984) computes `old-total-assets` via `(total-assets)`, which reads the possibly-stale `var-get index`, without first calling `accrue` to checkpoint accrued interest into `index`/`lindex`, unlike every other principal-mutating entrypoint in the vault (`system-borrow`, `system-repay`, `flashloan`), all of which begin with `(u (try! (accrue)))`. Because both `old-total-assets` and `debt-reduction` are derived from the same stale `idx`, and the vault holds idle cash (`assets`) alongside borrowed principal, the resulting `new-lindex` write-down ratio is proportionally smaller than it would be if interest had first accrued, systematically understating the loss applied to remaining `zft` holders.

### Finding Description
`socialize-debt`'s `let` binds:
- `idx` = `(var-get index)` (line 947) — not refreshed via `accrue`
- `old-total-assets` = `(total-assets)` (line 950) — depends on the same stale `idx`
- `debt-reduction` = `scaled-amount * idx / INDEX-PRECISION` (line 951)
- `new-lindex` = `current-lindex * (old-total-assets - debt-reduction) / old-total-assets` (lines 956-958) [1](#0-0) 

Unlike `socialize-debt`, the other value-mutating public entrypoints explicitly re-checkpoint the index before using it: `system-borrow` and `system-repay` both call `(u (try! (accrue)))` as their first `let` binding. [2](#0-1) [3](#0-2) 

`accrue` itself computes a fresh `next` index representing accrued interest and only checkpoints it into the `index`/`lindex` state variables when called; if never invoked, `total-assets` (used at line 950) continues to read the older, smaller `index`. [4](#0-3) 

**Math confirming impact**: Let `B` = scaled principal, `C` = idle cash (`assets`), `A` = `scaled-amount` being socialized. Then `total-assets(idx) ≈ B*idx + C` and `debt-reduction(idx) = A*idx`. The remaining-value ratio is `1 - A*idx/(B*idx + C)`. Because `C > 0` in a live vault, this ratio is monotonically decreasing in `idx` — i.e., a *lower* (stale) `idx` produces a *larger* remaining-value ratio and hence a *smaller* write-down than the true, accrued `idx` would. Remaining `zft` holders' shares are therefore left overvalued relative to the real post-loss NAV.

The `check-caller-auth` gate (line 960) restricts direct calls to authorized callers (the market), but does not close the gap: the market's liquidation/bad-debt path invokes `socialize-debt` without the vault's `accrue` having run in the same transaction whenever no other vault-mutating call (borrow/repay/flashloan) has recently executed. An attacker cannot call `accrue` themselves to prevent this — the bug is a missing call, not something they can override — but they can pick the moment (a liquidation after a period of vault inactivity) to trigger `socialize-debt` while `index` is maximally stale via `liquidate-multi` on the market, maximizing the understatement.

### Impact Explanation
This is a Critical / protocol-insolvency issue: after a bad-debt socialization event, remaining `zft` share value is marked down by less than the true loss (unaccrued interest is excluded from the loss basis). Early redeemers can withdraw against the inflated post-loss share price, extracting more underlying per share than their fair claim, leaving later redeemers unable to redeem their full fair value — a direct undercollateralization/insolvency of the vault matching the "protocol insolvency" Critical category.

### Likelihood Explanation
No special privilege is required beyond what any user already has: liquidations are triggered by ordinary calls to the market's liquidation function, and the staleness of `index` grows passively whenever no borrow/repay/flashloan activity has recently touched the vault (accrue is not called on a timer). An attacker only needs to identify/await a liquidation opportunity following a quiet period for the specific vault, then trigger the liquidation (and be first to redeem afterward) to capture the mispriced difference. This is realistically repeatable across vaults/quiet periods and requires no unusual capital beyond normal liquidation/redeem flows.

### Recommendation
Add `(try! (accrue))` as the first action/binding in `socialize-debt`, exactly as done in `system-borrow`, `system-repay`, and `flashloan`, so that `old-total-assets` and `debt-reduction` are computed against a freshly checkpointed `index`/`lindex` that reflects all interest accrued up to the moment of the loss event.

### Proof of Concept
Clarinet/vitest simnet plan:
1. Deploy the vault + market, seed a supplier deposit (`assets` > 0) and a borrower position so `principal-scaled`/`total-borrowed` > 0.
2. Advance chain time significantly (no borrow/repay/flashloan calls in between) so real accrued interest diverges from the stale `index`.
3. Path A ("no accrue"): call `socialize-debt` directly (or via the market's liquidation flow) for a fixed `scaled-amount`; record `new-lindex`.
4. Path B ("with accrue"): reset state identically, call `accrue` explicitly, then call `socialize-debt` with the same `scaled-amount`; record `new-lindex`.
5. Assert `new-lindex` in Path A > `new-lindex` in Path B (less write-down under staleness).
6. Have a second supplier redeem immediately after Path A's `socialize-debt`; assert underlying received per share exceeds the fair value computed under Path B, demonstrating value extraction at the expense of later redeemers.

```text
(define-public (socialize-debt (scaled-amount uint))
  (let ((scaled-principal (var-get principal-scaled))
        (borrowed (var-get total-borrowed))
        (idx (var-get index))
        (current-assets (var-get assets))
        (current-lindex (var-get lindex))
        (old-total-assets (total-assets))
        (debt-reduction (mul-div-down scaled-amount idx INDEX-PRECISION))
        (principal-reduction (if (> scaled-principal u0)
                                (mul-div-down scaled-amount borrowed scaled-principal)
                                u0))
        ;; Write down lindex proportionally to loss in total-assets
        (new-lindex (if (and (> old-total-assets u0) (> old-total-assets debt-reduction))
                       (mul-div-down current-lindex (- old-total-assets debt-reduction) old-total-assets)
                       u0)))
```
