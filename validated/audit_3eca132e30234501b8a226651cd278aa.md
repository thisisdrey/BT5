The Go standard library's `crypto/internal/fips140/aes/gcm` CMAC implementation is stateless per-call and has no analog to ntpd's persistent key-file parsing that leaks memory when a CMAC-associated algorithm key is not freed. The `gcm.NewCMAC` constructor [1](#0-0)  simply derives subkeys from an already-allocated `aes.Block` and returns a `CMAC` struct with fixed-size array fields (`k1`, `k2` of `[aes.BlockSize]byte`), with no dynamic/heap allocation, no key-file parsing, and no code path where a "CMAC key associated with a CMAC algorithm" is left unfreed across requests. The ACVP test harness invocations of `gcm.NewCMAC` [2](#0-1)  and Wycheproof/self tests [3](#0-2)  are test-only, not production request-handling loops analogous to ntpd's config parser.

The reported CVE describes a config/key-file parsing bug in the C ntpd daemon (`ntp.keys` handling), not a Go standard library HTTP/TLS/crypto-acceptance/module/template/archive pathway. There is no unauthenticated, victim-workflow-reachable Go entry point in this repository that parses a persistent keys configuration and leaks memory per request in a way that matches this CVE's primitive.

func cmdCmacAesAft() command {
	return command{
		requiredArgs: 3, // Number of output bytes, key, message
		handler: func(args [][]byte) ([][]byte, error) {
			// safe to truncate to int based on our capabilities describing a max MAC output len of 128 bits.
			outputLen := int(binary.LittleEndian.Uint32(args[0]))
			key := args[1]
			message := args[2]

			blockCipher, err := aes.New(key)
			if err != nil {
				return nil, fmt.Errorf("creating AES block cipher with key len %d: %w", len(key), err)
			}

			cmac := gcm.NewCMAC(blockCipher)
			tag := cmac.MAC(message)

			if outputLen > len(tag) {
				return nil, fmt.Errorf("invalid output length: expected %d, got %d", outputLen, len(tag))
			}

			return [][]byte{tag[:outputLen]}, nil
		},
	}
}
