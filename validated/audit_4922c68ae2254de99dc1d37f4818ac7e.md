### Title
Pipeline lookahead never calls `submit()` for `GlobalContractDistribution` receipts, leaving `block_global_contracts` permanently unpopulated - (File: `runtime/runtime/src/pipelining.rs`)

### Summary
`ReceiptPreparationPipeline::submit` contains explicit logic (lines 165-168) to register a global contract identifier in `block_global_contracts` when it receives a `ReceiptEnum::GlobalContractDistribution` receipt, so that concurrently-scheduled `FunctionCall` preparation against accounts using that global contract is skipped. However, the only caller of `submit()`, `schedule_contract_preparation` in `runtime/runtime/src/lib.rs`, special-cases `ReceiptEnum::GlobalContractDistribution` receipts by returning `false` directly instead of delegating to `mgr.submit(...)`, so `submit()` is never actually invoked for this receipt kind and the blocklist is never populated through the normal chunk-processing path.

### Finding Description
The intended defense mechanism lives in `submit()`: [1](#0-0) 
This inserts the global contract's identifier into `self.block_global_contracts`, and later `FunctionCall` handling checks that set before submitting work: [2](#0-1) 

But the sole call site that drives the pipeline's lookahead, `schedule_contract_preparation`, explicitly short-circuits `GlobalContractDistribution` receipts without ever calling `submit()`: [3](#0-2) 

Note line 3342: `ReceiptEnum::GlobalContractDistribution(_) => false` returns immediately from `handle_receipt` — it never calls `mgr.submit(receipt, ...)` the way `ReceiptEnum::Action`/`ActionV2`/`PromiseYield` variants do at lines 3296-3304. As a result, the `block_global_contracts` insertion logic that exists in `submit()` (pipelining.rs:165-168) is unreachable dead code from this scheduling path, which is the only place `submit()` is invoked from the main `apply` loop (`lib.rs:2401-2405`, `2417-2427`, `2581-2617`).

Practical consequence: a `DeployGlobalContract` action (`action_deploy_global_contract` in `runtime/runtime/src/global_contracts.rs:24-62`) does not write contract bytes directly — it emits a `GlobalContractDistributionReceipt` (`initiate_distribution`, `global_contracts.rs:142-170`) which, when later processed via `apply_global_contract_distribution_receipt` / `apply_distribution_current_shard` (`global_contracts.rs:110-234`), overwrites the `TrieKey::GlobalContractCode` bytes for that identifier (notably for `GlobalContractDeployMode::AccountId`, where the identifier is stable across redeployments and code can be replaced under the same identifier within one chunk). Because `schedule_contract_preparation` never calls `submit()` for that distribution receipt, the pipelining subsystem's own designed safeguard against racing a deployment with a lookahead-prepared `FunctionCall` never engages for global contracts, unlike the equivalent (and functioning) `block_accounts` path for `Action::DeployContract`/`UseGlobalContract`/etc, which is correctly reached because those are plain `Action` receipts (handled at pipelining.rs:176-191 and reached via the `ReceiptEnum::Action`-style branch in `schedule_contract_preparation`).

I was not able to fully verify, within tool/time budget, whether the separate defense-in-depth check in `get_contract` (`expected_hash == identifier.hash()`, pipelining.rs:349-350) is sensitive to the *content* of a `GlobalByAccount`-identified contract's bytes, or only to the `AccountContract` enum variant/identifier itself (i.e., whether `RuntimeContractIdentifier::hash()` changes when the same account-id-addressed global contract's underlying bytes are redeployed without changing the identifier). This is material: if `identifier.hash()` is insensitive to a same-identifier code replacement, the dead blocklist is the only defense and the divergence described is real; if `identifier.hash()` is sensitive to code content, the stale-preparation is caught and discarded at `get_contract` time, and the practical impact is limited to wasted work rather than divergence. Because this determines whether the bug produces observable consensus divergence versus benign waste, and I could not inspect `runtime/runtime/src/contract_code.rs`'s `RuntimeContractIdentifier::hash()` implementation to resolve this, I cannot confirm end-to-end exploitability to a concrete state-root divergence.

### Impact Explanation
If the `expected_hash` check does not catch content-level staleness for `GlobalByAccount` contracts, this would be a state-root-divergence-class bug (Determinism invariant): different validators/threads could prepare a `FunctionCall` against different global-contract byte snapshots (pre- vs post-deployment), leading to divergent gas metering for loading/compilation and divergent `gas_burnt`, and thus a chain split disguised as a balance/refund discrepancy. If the hash check is content-sensitive, impact is limited to a performance regression (unnecessary re-preparation), which is out of scope per the audit rules (resource-hygiene only, no reachable mainnet scenario).

### Likelihood Explanation
Preconditions are attacker-reachable without privileges: any funded account can call `DeployGlobalContract` (mode `AccountId`) more than once, and any account can `UseGlobalContract` referencing that identifier and issue `FunctionCall`s in the same or adjacent chunk. No validator/node access is required. The code defect itself (`schedule_contract_preparation` bypassing `submit()` for `GlobalContractDistribution`) is unconditionally reachable whenever the pipelining lookahead scans past a distribution receipt, i.e., it does not depend on attacker skill beyond crafting the two transactions; it is fully repeatable.

### Recommendation
In `schedule_contract_preparation` (`runtime/runtime/src/lib.rs`), route `ReceiptEnum::GlobalContractDistribution` receipts through `mgr.submit(receipt, state_update, None)` (as is already done for `submit()`'s existing branch at pipelining.rs:165-168) instead of returning `false` directly, so the `block_global_contracts` blocklist is actually populated when a distribution receipt is scanned ahead of dependent `FunctionCall` receipts. Additionally, verify/strengthen `RuntimeContractIdentifier::hash()` so that `expected_hash` in `PrepareTask`/`get_contract` is sensitive to actual global-contract code content (not just the `AccountContract` identifier), providing a real defense-in-depth for the `AccountId` deploy mode where the identifier is stable across redeployments.

### Proof of Concept
1. Unit test in `runtime/runtime/src/pipelining.rs` (or an integration/test-loop test in `test-loop-tests`) that:
   - Deploys a global contract under `GlobalContractDeployMode::AccountId` for account `deployer.near` with contract A.
   - Creates account `user.near` with `AccountContract::GlobalByAccount("deployer.near")`.
   - In the same chunk, submits: (a) a `DeployGlobalContract` transaction from `deployer.near` redeploying different contract B under the same identifier, and (b) a `FunctionCall` transaction to `user.near` calling a method.
   - Instrument/assert that `ReceiptPreparationPipeline::submit` is invoked with the `GlobalContractDistribution` receipt (currently it is not, due to the `lib.rs:3342` short-circuit), by adding a counter/probe in `schedule_contract_preparation`'s handling of that branch.
   - Run `Runtime::apply` twice — once with pipelining's background thread artificially delayed vs. not delayed — and assert `gas_burnt` for the `FunctionCall` outcome is identical in both runs. Currently, this determinism is not enforced by any code path because the intended `block_global_contracts` guard is unreachable.
   - Expected fix outcome: after routing `GlobalContractDistribution` through `submit()`, the counter/probe shows registration in `block_global_contracts`, and the `FunctionCall` preparation is skipped for the racing case, restoring deterministic `gas_burnt` regardless of thread timing.
