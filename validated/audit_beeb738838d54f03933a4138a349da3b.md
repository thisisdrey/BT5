## Title
`claim_rewards_to` benchmark returns `None` for bridge-hub-rococo relayer reward instances, poisoning the extrinsic's weight and permanently blocking alternative-beneficiary reward claims - ([File: cumulus/parachains/runtimes/bridge-hubs/bridge-hub-rococo/src/lib.rs])

## Summary
Both `BridgeRelayersConfig` implementations for `RelayersForLegacyLaneIdsMessagesInstance` and `RelayersForPermissionlessLanesInstance` on bridge-hub-rococo unconditionally return `None` from `prepare_rewards_account`, causing the pallet's `claim_rewards_to` benchmark to be overridden with `Weight::MAX`. This value has already been baked into the committed, autogenerated weight files, meaning the live `claim_rewards_to` extrinsic for these two reward kinds is permanently undispatchable on bridge-hub-rococo.

## Finding Description
`pallet_bridge_relayers::benchmarking::Config::prepare_rewards_account` explicitly documents that returning `None` "causes `claim_rewards_to` to be assigned `Weight::MAX`" [1](#0-0) , and the `claim_rewards_to` benchmark implements exactly that fallback via `BenchmarkError::Override(BenchmarkResult::from_weight(Weight::MAX))` when `prepare_rewards_account` returns `None` [2](#0-1) .

On bridge-hub-rococo, both relevant trait implementations return `None` unconditionally: for `RelayersForLegacyLaneIdsMessagesInstance` [3](#0-2)  and for `RelayersForPermissionlessLanesInstance` [4](#0-3) .

This has already propagated into the committed, autogenerated weight files used by the live runtime: `pallet_bridge_relayers_legacy.rs` encodes `claim_rewards_to() -> Weight::from_parts(18_446_744_073_709_551_000, 0)` (i.e. `u64::MAX` ref time = `Weight::MAX`'s ref-time component) [5](#0-4) , and `pallet_bridge_relayers_permissionless_lanes.rs` encodes the identical `Weight::MAX` value [6](#0-5) . These `WeightInfo::claim_rewards_to()` implementations are consumed directly by the dispatchable's `#[pallet::weight(T::WeightInfo::claim_rewards_to())]` annotation in the pallet [7](#0-6) . A dispatchable whose declared weight equals `Weight::MAX` can never satisfy a block's maximum extrinsic or total block weight limits, so it is permanently excluded from inclusion by the transaction pool/block builder.

## Impact Explanation
Relayers who have accumulated rewards under `RelayerRewards` for either `RelayersForLegacyLaneIdsMessagesInstance` or `RelayersForPermissionlessLanesInstance` on bridge-hub-rococo have no functional way to redirect those rewards to an alternative beneficiary via `claim_rewards_to`, since its declared weight is `Weight::MAX` and the call can never be included in a block. This matches the "permanent user-fund lock" / "public overweight work that stalls processing" impact category in the accepted impact gate — legitimate, non-privileged relayers are permanently denied a documented protocol capability with no in-protocol workaround, though ordinary `claim_rewards` (payout to the caller itself) remains unaffected.

## Likelihood Explanation
This is not speculative: the identical bug was already found and fixed for bridge-hub-westend's Snowbridge reward instance in `pr_10952.prdoc`, whose fix pattern (return `Some((reward_kind, beneficiary))` with a funded beneficiary) was never applied to bridge-hub-rococo's two reward instances. No privileged action, malicious actor, or special conditions are required beyond an ordinary relayer calling the public `claim_rewards_to` extrinsic — the flaw is already baked into the committed weight tables, so it is deterministic and 100% reproducible on the current bridge-hub-rococo runtime.

## Recommendation
Update `bridge-hub-rococo`'s `prepare_rewards_account` implementations for both `RelayersForLegacyLaneIdsMessagesInstance` and `RelayersForPermissionlessLanesInstance` to return `Some((reward_kind, beneficiary))` with a properly funded beneficiary account (mirroring the westend fix), then regenerate and commit `pallet_bridge_relayers_legacy.rs` and `pallet_bridge_relayers_permissionless_lanes.rs` so `claim_rewards_to` gets a realistic, dispatchable weight. Add a CI check that fails if any generated `WeightInfo` weight approaches `Weight::MAX`, to catch this benchmark-helper-returns-`None` pattern across all bridge-hub runtimes automatically.

2. Trace this back to `bridges/modules/relayers/src/benchmarking.rs::claim_rewards_to`, which returns `BenchmarkResult::from_weight(Weight::MAX)` whenever `T::prepare_rewards_account` returns `None`.
3. Confirm both `BridgeRelayersConfig` impls in `cumulus/parachains/runtimes/bridge-hubs/bridge-hub-rococo/src/lib.rs` (lines 1383-1397 and 1414-1428) unconditionally return `None`.
4. At runtime, any relayer with a nonzero `RelayerRewards` entry under either instance who submits `claim_rewards_to(reward_kind, alternative_beneficiary)` will have the transaction rejected by the runtime's weight-limit checks, since the extrinsic's declared weight (`Weight::MAX`) exceeds the block's maximum weight — the call can never be included in any block.
