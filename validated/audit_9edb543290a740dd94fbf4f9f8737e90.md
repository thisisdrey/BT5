## Analog Found

### Title
Missing monotonicity check on peer-controlled handshake time allows replay to downgrade/poison an established hostmap tunnel - (File: `handshake_manager.go`)

### Summary
`HandshakeManager.CheckAndComplete` decides whether an incoming handshake should replace an existing tunnel for the same peer by comparing an attacker/peer-controlled `lastHandshakeTime` value. The "is this newer" guard is unconditionally skipped whenever the *existing* tunnel was locally initiated, letting a captured, stale (but validly-signed) handshake message override — i.e. downgrade — a currently active, more-recent tunnel, exactly mirroring the report's root cause: a sequential/ordering invariant that depends on an attacker-influenced value with no bound/monotonicity enforcement.

### Finding Description
`Payload.Time` is fully attacker-controlled wire data carried inside the (peer-authenticated but otherwise unchecked) handshake payload — it is a plain `uint64` parsed with no bounds or monotonicity validation: [1](#0-0) [2](#0-1) 

It flows unchanged into `Result.HandshakeTime` and then into `HostInfo.lastHandshakeTime`, which is explicitly documented as an anti-replay defense: [3](#0-2) [4](#0-3) 

The actual enforcement point is `CheckAndComplete`, which is supposed to reject an incoming handshake as stale ("`ErrExistingHostInfo`") when its `lastHandshakeTime` is not newer than the existing tunnel's. However, the check is gated by `!existingHostInfo.ConnectionState.initiator`: [5](#0-4) 

When the *local* node is the initiator of the currently active tunnel (`existingHostInfo.ConnectionState.initiator == true`), the time-ordering check is entirely bypassed — any incoming handshake for that same peer address that isn't a byte-identical replay of an already-stored packet (checked just above via `bytes.Equal` against `HandshakePacket[handshakePacket]`) is unconditionally accepted as "newer" and replaces the existing hostinfo, regardless of how stale its `lastHandshakeTime` actually is.

This is structurally identical to the reported bug class: a value that is supposed to enforce sequential/temporal ordering (`toBlock` in the report, `lastHandshakeTime` here) is accepted without a bound relative to the existing state, and the code path that is meant to prevent regression (`require(toBlock > fromBlock...)` / the `lastHandshakeTime >=` check) can be skipped, letting an attacker resurrect and substitute old state for current state.

### Impact Explanation
An attacker who has ever captured a valid stage-1 handshake packet sent to a node while that node was the initiator of its own tunnel to the same peer (a routine occurrence — such packets are visible on the wire, e.g. from an earlier reconnection/roaming attempt) can replay it later to force the node to tear down and replace its live tunnel's hostinfo with one built from stale handshake material. This is a remote state-poisoning/tunnel-downgrade primitive against the hostmap for an already-established session, achievable purely by a network-path attacker replaying previously observed traffic — no forging of a certificate or private key is required.

### Likelihood Explanation
Medium: exploitation requires the attacker to have captured at least one legitimate stage-1 handshake packet directed at the victim while the victim was the initiator of the resulting tunnel, and to replay it afterward. This is a realistic on-path/network condition (UDP handshake packets are observable) and does not require compromising any private key or CA-issued certificate.

### Recommendation
Remove the `!existingHostInfo.ConnectionState.initiator` exception, or otherwise apply the `lastHandshakeTime` freshness check unconditionally so a replayed/stale handshake can never supersede a fresher existing tunnel regardless of which side initiated it:
```go
if existingHostInfo.lastHandshakeTime >= hostinfo.lastHandshakeTime {
    return existingHostInfo, ErrExistingHostInfo
}
```

### Proof of Concept
1. Node A initiates a handshake to Node B; Node B's `HostInfo.ConnectionState.initiator` becomes `true` from B's perspective is not the relevant flag — rather, on Node A, `existingHostInfo.ConnectionState.initiator == true` for the tunnel A→B (A is initiator).
2. An on-path attacker captures a subsequent, distinct valid stage-1 handshake packet sent from B to A (e.g. from a legitimate reconnection attempt by B), differing in bytes from what's currently cached in A's `HandshakePacket[handshakePacketStage0]`.
3. After A's tunnel to B is active (A remains initiator on that entry), the attacker replays the captured stale stage-1 packet to A.
4. In `CheckAndComplete`, the `bytes.Equal` loop fails to match (different packet), and the staleness guard `existingHostInfo.lastHandshakeTime >= hostinfo.lastHandshakeTime && !existingHostInfo.ConnectionState.initiator` evaluates `false` solely because `existingHostInfo.ConnectionState.initiator` is `true` — the stale handshake is accepted ("Taking new handshake") and replaces the active, more current session state.
