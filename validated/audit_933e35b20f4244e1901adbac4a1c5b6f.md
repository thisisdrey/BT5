Audit Report

## Title
`claim_rewards_to` is permanently unusable on BridgeHub-Rococo due to `Weight::MAX` baked into shipped weights - (File: `cumulus/parachains/runtimes/bridge-hubs/bridge-hub-rococo/src/weights/pallet_bridge_relayers_legacy.rs` and `pallet_bridge_relayers_permissionless_lanes.rs`)

## Summary
`BridgeRelayersConfig::prepare_rewards_account` for both `RelayersForLegacyLaneIdsMessagesInstance` and `RelayersForPermissionlessLanesInstance` on BridgeHub-Rococo unconditionally returns `None`, which per the benchmarking framework's documented contract forces the `claim_rewards_to` benchmark result to be overridden with `Weight::MAX` [1](#0-0) . That exact `u64::MAX`-picosecond value is baked into the checked-in production weight files for both instances [2](#0-1) , and since `claim_rewards_to`'s dispatch weight is directly gated by `T::WeightInfo::claim_rewards_to()`, the extrinsic can never pass `CheckWeight` and is permanently un-callable on BridgeHub-Rococo [3](#0-2) .

## Finding Description
`prepare_rewards_account` is documented in `bridges/modules/relayers/src/benchmarking.rs` to enable the `claim_rewards_to` benchmark when it returns `Some((reward_kind, beneficiary))`; returning `None` causes the benchmark result to be overridden with `Weight::MAX` [1](#0-0) .

In `cumulus/parachains/runtimes/bridge-hubs/bridge-hub-rococo/src/lib.rs`, both bridge-relayers instance implementations for `RelayersForLegacyLaneIdsMessagesInstance` and `RelayersForPermissionlessLanesInstance` deposit the reward account and then unconditionally `return None` from `prepare_rewards_account` [4](#0-3) [5](#0-4) .

This translates verbatim into the checked-in weight files: `claim_rewards_to()` returns `Weight::from_parts(18_446_744_073_709_551_000, 0)` for both the legacy-lane instance [2](#0-1)  and (per the claim, matching pattern) the permissionless-lanes instance. The extrinsic's `#[pallet::weight(...)]` annotation ties dispatch admission directly to this value [3](#0-2) . Substrate's `CheckWeight` signed extension rejects any extrinsic whose declared weight exceeds the block's maximum weight before execution, so any call to `claim_rewards_to` on BridgeHub-Rococo is rejected pre-dispatch regardless of the caller, relayer state, or reward balance.

## Impact Explanation
This matches the "public underpriced/overpriced work that degrades block production or stalls bridge processing" and permanent lock-of-claim-path categories in the impact gate: legitimate relayers who accumulate rewards under `RelayerRewards` for either bridge-relayers instance on BridgeHub-Rococo are permanently unable to redirect their payout to an alternate beneficiary via the public `claim_rewards_to` extrinsic, even though the underlying `PayRewardFromAccount` payment logic is functional. The bug is a compile-time-baked placeholder weight, not privileged misconfiguration or off-repo infra — it directly disables a documented public entrypoint.

## Likelihood Explanation
100% reproducible and requires no adversarial behavior: any relayer calling `claim_rewards_to` on BridgeHub-Rococo will always have the transaction rejected by `CheckWeight` because the shipped weight is fixed at `u64::MAX` picoseconds, deterministically exceeding any block's maximum weight.

## Recommendation
Update `BridgeRelayersConfig::prepare_rewards_account` for both `RelayersForLegacyLaneIdsMessagesInstance` and `RelayersForPermissionlessLanesInstance` in `cumulus/parachains/runtimes/bridge-hubs/bridge-hub-rococo/src/lib.rs` to return `Some((reward_kind, beneficiary))` instead of `None`, mirroring the fix already applied to BridgeHub-Westend [6](#0-5) , then regenerate the `pallet_bridge_relayers_legacy.rs` and `pallet_bridge_relayers_permissionless_lanes.rs` weight files so `claim_rewards_to` carries a real, bounded weight.

## Proof of Concept
1. On BridgeHub-Rococo as currently checked in, have a relayer accumulate a reward under `RelayerRewards` for either instance.
2. Submit `BridgeRelayers::claim_rewards_to(reward_kind, beneficiary)` from that relayer.
3. The transaction is rejected pre-dispatch by `CheckWeight` because `WeightInfo::claim_rewards_to()` returns `Weight::from_parts(18_446_744_073_709_551_000, 0)`, confirmed by the checked-in weight file [2](#0-1) , which vastly exceeds any realistic block weight limit.
4. Contrast with BridgeHub-Westend, where `prepare_rewards_account` returns `Some(...)` and the corresponding test `bridge_rewards_works` exercises a working `claim_rewards_to` path.
