Based on my investigation, this repo's Atlas attachment downloader confirms that the requesting client never checks that the returned attachment's content actually hashes to the `content_hash` it requested.

### Title
Atlas attachment downloader accepts and stores attachments without verifying `Attachment::hash()` matches the requested `content_hash` - ([File: stackslib/src/net/atlas/download.rs])

### Summary
`AttachmentsBatchStateContext::extend_with_attachments` decodes a peer's HTTP `GET /v2/attachments/{content_hash}` response and inserts the returned `Attachment` into the batch's result set purely based on successful JSON decoding, without checking that the returned content's SHA/Hash160 digest equals the `content_hash` that was actually requested.

### Finding Description
The Atlas attachment fetch flow is: `AttachmentRequest { content_hash, sources, ... }` builds a GET request to `/v2/attachments/{content_hash}` [1](#0-0) . When the response comes back, `extend_with_attachments` simply does:

```
if let Ok(response) = response.decode_atlas_get_attachment() {
    self.attachments.insert(response.attachment);
    report.bump_successful_requests();
}
``` [2](#0-1) 

`decode_atlas_get_attachment` only performs JSON deserialization of the hex-encoded content into an `Attachment` — there is no comparison against `request.content_hash` [3](#0-2) .

Downstream, in `AttachmentsDownloader::run`, once the batch state machine reaches `Done`, every attachment in `context.attachments` is looked up by `attachment.hash()` (i.e., the hash of whatever content was actually returned, not the originally-requested hash) via `find_all_attachment_instances(&attachment.hash())`, then unconditionally persisted with `atlasdb.insert_instantiated_attachment(&attachment)` [4](#0-3) . The batch bookkeeping then calls `resolve_attachment(&attachment.hash())`, using the self-reported hash of the delivered bytes to decide whether the *originally-requested* content hash entry is considered resolved, rather than validating that the attacker-supplied bytes indeed hash to the value the request targeted.

Because the equality "the hash of the content I asked for" vs. "the hash of the content a possibly-malicious peer chose to send me" is never explicitly enforced by the client before insertion into `atlasdb`, a remote unauthenticated peer that a node queries for an attachment (any Atlas hint-replica/neighbor providing a data URL) can respond with arbitrary attachment content instead of the actual data behind the requested hash. That data gets committed to the local `AtlasDB` `attachments` table and is subsequently servable to other peers via the same `/v2/attachments/{hash}` endpoint (this node's own `find_attachment` lookup) as if it were validated data corresponding to whatever hash the malicious bytes happen to produce.

### Impact Explanation
This breaks the "authenticated vs. stored" equality for Atlas attachments: the node's Atlas subsystem is designed so `AttachmentInstance.content_hash` (extracted from on-chain contract calls) authenticates what content is allowed into local storage, yet the downloader path never re-derives the hash of the peer's response and compares it to `request.content_hash` before commit. Depending on how `insert_instantiated_attachment`'s `INSERT OR REPLACE ... VALUES (attachment.hash(), attachment.content, ...)` and the follow-on `find_all_attachment_instances(&attachment.hash())` interact with existing/queued instances, this allows an untrusted peer to poison a node's Atlas cache with attacker-chosen content under the key derived purely from the peer's own bytes; since serving nodes trust their local `AtlasDB` as canonical for any subsequent `/v2/attachments/{hash}` request, this is a "non-canonical state served as canonical" style defect matching the High-severity criteria in the ruleset (serving non-canonical/attacker-influenced data as if it had been validated against the expected commitment).

### Likelihood Explanation
Any Atlas hint-replica or outbound sync peer that a node queries for an attachment can trigger this by simply returning different content than the requested hash; no privileged position, no signing key, and no protocol violation beyond a normal HTTP 200 response is needed, matching the "unprivileged/remote" requirement.

### Recommendation
In `extend_with_attachments` (or immediately after `decode_atlas_get_attachment`), recompute the digest of the returned attachment content (`Attachment::hash()`/`MerkleHashFunc`) and compare it against `request.content_hash` before inserting into `self.attachments`; discard and mark the source unreliable (`report.bump_failed_requests()`) on mismatch instead of trusting whatever hash the response happens to produce.

### Proof of Concept
1. Configure a malicious Atlas peer (or hint-replica URL) that responds to `GET /v2/attachments/{requested_hash}` with an arbitrary JSON body `{"attachment": <hex of attacker-chosen bytes>}` regardless of the `requested_hash` in the path.
2. A victim node with a pending `AttachmentInstance` for `content_hash = requested_hash` queries this peer as part of `AttachmentsDownloader::run`.
3. `extend_with_attachments` accepts the response purely because it deserialized successfully [2](#0-1) , and the attacker-chosen content is committed via `insert_instantiated_attachment` [5](#0-4) , without ever verifying it hashes to `requested_hash`.
