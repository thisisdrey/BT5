### Title
`CreateRelayRequest`'s self-declared `RelayFromAddr` is never checked against the authenticated sender's certificate VPN address, allowing relay-state poisoning/impersonation - ([File: relay_manager.go])

### Summary
`relayManager.handleCreateRelayRequest` trusts the attacker-supplied `RelayFromAddr` field of an inbound `CreateRelayRequest` control message as the "identity" of the party the relay is being established for, without ever verifying that this field matches the actual authenticated VPN address(es) of the message sender (`h.vpnAddrs`). This is the same bug class as the reported "payer is not tied to msg.sender" issue: a protocol field that is supposed to represent an identity is user/peer-supplied and not cross-checked against the cryptographically authenticated identity of the entity making the request.

### Finding Description
When a node receives a `NebulaControl_CreateRelayRequest` message, `HandleControlMsg` dispatches to `handleCreateRelayRequest`: [1](#0-0) 

`from` is derived purely from `m.RelayFromAddr` — a field entirely controlled by the sender of the control message — and is never compared against `h.vpnAddrs` (the addresses that were cryptographically certified for `h` during the Noise handshake, see `validatePeerCert`/`beginHandshake` which populate `hostinfo.vpnAddrs` from the verified certificate): [2](#0-1) [3](#0-2) 

Back in `handleCreateRelayRequest`, once the "am I the target" branch is taken, the code installs new relay state keyed by the attacker-declared `from` address, tied to the already-authenticated `HostInfo h`: [4](#0-3) 

Nothing here enforces `from == h.vpnAddrs[0]` (or any address in `h.vpnAddrs`). Contrast this with the unrelated, but conceptually similar, self-connection check that *does* verify identity fields elsewhere in the handshake path (`validatePeerCert`, which checks the *certificate's* declared networks against the local address table). No equivalent verification exists here for the relay's `RelayFromAddr`, which is not a certificate field at all — it is arbitrary payload data in a `Control` message that only needs to arrive over an already-established (authenticated) tunnel from `h`.

This mirrors the "payer" bug precisely: the `Control` message's `RelayFromAddr`/`OldRelayFromAddr` fields are analogous to "payer" — a self-declared identity field that a malicious, but otherwise legitimately-tunneled, peer can set to any arbitrary VPN address (including a real victim's address) without the relay-target node ever checking it against `h`'s actual certified identity.

### Impact Explanation
An authenticated attacker host `h` (who has a valid cert and a legitimate tunnel to the victim/target node) can issue `CreateRelayRequest` messages claiming `RelayFromAddr` = an arbitrary/victim VPN address. The receiving node will create relay bookkeeping state (`AddRelay(..., from, ..., TerminalType, Established)`) associating that arbitrary address with the attacker's own `HostInfo`/tunnel index, and will reply with a `CreateRelayResponse` acknowledging that relay. This is remote state poisoning of the relay subsystem: relay state (`hostmap.Relays`, `relayState.relayForByAddr/relayForByIdx`) is populated with attacker-chosen identity data that was never authenticated, corrupting the receiver's view of which VPN address is reachable "from" `h`, and potentially causing the node to route relayed traffic on behalf of/through an unintended peer address, or to consume relay-index resources associated with a victim it never actually communicated with. It also degrades the reliability of the relay mesh (misdirected relay expectations, resource confusion, log/telemetry poisoning attributing traffic to the wrong VPN address).

### Likelihood Explanation
Requires only that the attacker be able to complete a normal Nebula handshake with the relay/target node (i.e., possess a valid cert signed by a CA the target trusts) — the same "no CA-signed certificate" reachability constraint noted in the rules is satisfied because the exploit path is reachable by anyone who already has cert-based access to send a `Control` message, and it exploits the *content* of that message, not certificate forgery. No additional secrets or races are required beyond crafting the `CreateRelayRequest` payload, making this straightforward to trigger once connected.

### Recommendation
In `relayManager.handleCreateRelayRequest` (and `handleCreateRelayResponse`), verify that `RelayFromAddr`/`OldRelayFromAddr` (the "from" identity declared in the control message) is contained within the sending `HostInfo`'s certified `h.vpnAddrs`, rejecting/logging-and-dropping the message otherwise, the same way `validatePeerCert` ties certificate-derived VPN networks to the actual authenticated peer before trusting them.

### Proof of Concept
1. Attacker establishes a normal, valid Nebula tunnel to node `T` (target/relay), using a legitimately-signed certificate for VPN address `A_attacker`.
2. Attacker sends a `Control` message of type `NebulaControl_CreateRelayRequest` over this authenticated tunnel with `RelayFromAddr` set to `A_victim` (any arbitrary/victim VPN address) and `RelayToAddr` set to `T`'s own VPN address.
3. `T` receives this on `HostInfo h` (whose real, certified address is `A_attacker`), and `handleCreateRelayRequest` executes the "target is me" branch, calling `AddRelay(rm.l, h, f.hostMap, A_victim, &m.InitiatorRelayIndex, TerminalType, Established)` — installing relay state that ties `A_victim` to the attacker's tunnel `h`, without ever checking `A_victim` against `h.vpnAddrs` (`[A_attacker]`).
4. `T` sends back a `CreateRelayResponse` confirming the (poisoned) relay association, completing the state corruption remotely.

*Note: I was unable to fully trace every downstream consumer of `relay.PeerAddr` (e.g., in `ForwardingType` lookup and connection-manager relay accounting) within the available tool budget to characterize the complete blast radius of the poisoned state; the finding is limited to demonstrating the missing sender-identity check on the `RelayFromAddr` field itself, which is the direct analog of the reported "payer" bug.*

// validatePeerCert checks the peer certificate for self-connection and remote allow list.
// Returns the VPN addrs, whether any of them fall within one of our own VPN
// networks, and true if valid; false if rejected.
func (hm *HandshakeManager) validatePeerCert(via ViaSender, remoteCert *cert.CachedCertificate) ([]netip.Addr, bool, bool) {
	f := hm.f
	vpnNetworks := remoteCert.Certificate.Networks()

	// The cert package rejects host certs with no networks at parse time, so
	// reaching this state would mean an invariant was bypassed elsewhere.
	// Refuse explicitly so downstream code (which indexes vpnAddrs[0]) can't
	// panic if that invariant ever changes.
	if len(vpnNetworks) == 0 {
		f.l.Info("No networks in certificate",
			"from", via, "cert", remoteCert)
		return nil, false, false
	}

	vpnAddrs := make([]netip.Addr, len(vpnNetworks))
	anyVpnAddrsInCommon := false

	for i, network := range vpnNetworks {
		if f.myVpnAddrsTable.Contains(network.Addr()) {
			f.l.Error("Refusing to handshake with myself",
				"vpnNetworks", vpnNetworks,
				"from", via,
				"certName", remoteCert.Certificate.Name(),
				"certVersion", remoteCert.Certificate.Version(),
				"fingerprint", remoteCert.Fingerprint,
				"issuer", remoteCert.Certificate.Issuer(),
			)
			return nil, false, false
		}
		vpnAddrs[i] = network.Addr()
		if f.myVpnNetworksTable.Contains(network.Addr()) {
			anyVpnAddrsInCommon = true
		}
	}

	if !via.IsRelayed {
		if !f.lightHouse.GetRemoteAllowList().AllowAll(vpnAddrs, via.UdpAddr.Addr()) {
			f.l.Debug("lighthouse.remote_allow_list denied incoming handshake",
				"vpnAddrs", vpnAddrs, "from", via)
			return nil, false, false
		}
	}

	return vpnAddrs, anyVpnAddrsInCommon, true
}
