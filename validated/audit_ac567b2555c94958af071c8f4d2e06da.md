Based on my analysis of the `near-wallet-contract` (the eth-implicit wallet contract), I found a concrete analog to the reported bug class. The report's root issue is: a mutable "in-progress" state guard that depends on an external/cross-contract call always executing to completion; if that call instead fails to run to completion (reverts/traps) without the guard being reset, the primary function becomes permanently blocked. The nearcore wallet contract has exactly this pattern with its `has_in_flight_tx` reentrancy-style guard.

### Title
Wallet Contract `has_in_flight_tx` guard can be stuck permanently `true` if a downstream promise callback panics, permanently freezing the eth-implicit account - (File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs)

### Summary
`WalletContract::rlp_execute` refuses to process any Ethereum-emulated transaction while `has_in_flight_tx == true`. The flag is committed to state as `true` by the *initiating* receipt and is only reset to `false` at the top of a later *callback* receipt (`address_check_callback`, `nep_141_storage_balance_callback`, `rlp_execute_callback`, `ban_relayer`). Because NEAR persists per-receipt state changes atomically only on successful completion of that receipt, if the callback receipt itself fails to run to completion (traps/panics — as opposed to the tracked cross-contract call merely returning `PromiseResult::Failed`, which is handled gracefully), the `has_in_flight_tx = false` assignment never commits, while the earlier `has_in_flight_tx = true` commit persists. The wallet is then permanently locked out of `rlp_execute`.

### Finding Description
`has_in_flight_tx` is documented as an invariant flag that must be `true` while a promise is outstanding and `false` otherwise: [1](#0-0) 

`rlp_execute` rejects any call while the flag is set, with no other way to clear it: [2](#0-1) 

For an `ERC20Transfer`, the flow schedules a `storage_balance_of` view call to the (attacker-controllable) `target` token contract and, in `.then()`, calls back into `nep_141_storage_balance_callback` with a *fixed* static gas budget (`NEP_141_STORAGE_BALANCE_CALLBACK_GAS`, 15 Tgas, plus `action.gas()` reserved for the *subsequent* chained calls, not for this callback's own compute): [3](#0-2) 

`nep_141_storage_balance_callback` unconditionally clears the flag as its first statement, then parses the (attacker-controlled) return value of `storage_balance_of` with `serde_json::from_slice`: [4](#0-3) 

The malicious `target` token contract fully controls the byte content and size of its `storage_balance_of` return value (up to the protocol's max return-value size). If that payload is crafted to make parsing/processing consume more compute than the fixed callback gas budget allows, the receipt traps with an out-of-gas/host error *after* the flag was already durably set to `true` by the prior (successfully committed) receipt, but *before* the in-memory `has_in_flight_tx = false` mutation in this receipt is persisted. Because `near-sdk`/`near_bindgen` only writes back mutated contract state when the method call completes without panicking, that reset is discarded along with the rest of the failed receipt's state changes, leaving `has_in_flight_tx == true` durably in the trie. This is structurally the same class of bug as the reported issue: an external/cross-contract interaction that can fail leaves a control-flow guard stuck, permanently blocking the primary operation (there `swap`, here `rlp_execute`) — except here the failure mode is a genuine trap rather than a benign `PromiseResult::Failed`, which the contract already handles correctly (that path resets the flag at the top of each callback exactly to avoid the naive-Solidity-style "swap stuck" problem).

The `address_check_callback` and `rlp_execute_callback` paths have analogous exposure: any trap inside those receipts, occurring after an earlier receipt already committed `has_in_flight_tx = true`, produces the same permanent-freeze outcome. `rlp_execute_callback`'s own comment underlines that `rlp_execute` "should never panic ... to ensure the contract's state can be changed even in error cases" — an invariant that is not actually enforced for the *callback* receipts, only informally intended for the top-level entrypoint: [5](#0-4) 

Existing tests confirm the flag-reset design intent and that ordinary handled failures (insufficient gas at the *outer* call, or a normal `PromiseResult::Failed`) do not brick the contract — but they do not cover a trap occurring inside a callback receipt after the flag has already been committed as `true`: [6](#0-5) [7](#0-6) 

### Impact Explanation
If triggered, the affected eth-implicit account's `WalletContract` becomes permanently unable to execute any further Ethereum-emulated transactions: every future `rlp_execute` call immediately short-circuits with "transaction already in progress" forever, since nothing in the contract's public interface can clear `has_in_flight_tx` except a callback receipt that must itself complete successfully to commit the reset — an invariant this bug breaks. This is a permanent freezing of the account's funds and key-management capability through this wallet interface (the owner can no longer transfer funds, call contracts, or rotate keys via the Ethereum-emulation path), matching the "permanent freezing of funds" acceptance criterion.

### Likelihood Explanation
The `target` (token contract) of an `ERC20Transfer`-kind Ethereum-emulated transaction is fully attacker/relayer-influenced deployment content — any account can deploy a NEP-141-look-alike contract whose `storage_balance_of` view method returns a large or expensive-to-process payload. Reaching this code path only requires an ordinary signed Ethereum transaction (from the wallet owner) directing an ERC-20-style transfer at such a malicious/crafted token contract, i.e., no privileged or validator-level access is required — an unprivileged external contract deployer plus normal wallet usage suffices to place the wallet into the trap-prone code path. Precisely tuning the payload/gas margin to force the failure inside the *callback* receipt after the flag commit (rather than during the earlier, gas-checked promise-creation step) requires some engineering effort but is a deterministic, protocol-level gas-accounting property, not a probabilistic race.

### Recommendation
Do not rely on unconditional state assignment inside callback methods to release the "in-flight" guard. Options: (1) reset `has_in_flight_tx` in a dedicated, minimal-gas, panic-proof step that is scheduled to run regardless of whether the main callback logic succeeds (e.g., structure the callback so the flag write is the very first and only Borsh-serialized/persisted action, with all fallible logic split into a separate, guaranteed-to-run follow-up receipt); (2) size all fixed callback gas budgets (`RLP_EXECUTE_CALLBACK_GAS`, `ADDRESS_CHECK_CALLBACK_GAS`, `NEP_141_STORAGE_BALANCE_CALLBACK_GAS`) to provably cover worst-case (maximum return-value size) parsing/processing cost, independent of what an untrusted `target`/token contract returns; (3) add a time/height-based escape hatch (e.g., allow clearing `has_in_flight_tx` if a sufficiently large number of blocks have passed since it was set) so a stuck flag cannot permanently brick the account.

### Proof of Concept
1. Deploy a malicious NEP-141-look-alike contract `evil.near` whose `storage_balance_of` method returns a maximum-size (or otherwise deserialization/compute-expensive) success payload.
2. From the wallet owner's Ethereum key, sign and submit (via any relayer) an RLP transaction encoding an ERC20-style transfer with `target = evil.near`.
3. `rlp_execute` → `inner_rlp_execute` schedules `Promise::new(evil.near).function_call("storage_balance_of", ...).then(ext.nep_141_storage_balance_callback(...))` and commits `has_in_flight_tx = true` (`lib.rs:271`/`118`).
4. When `nep_141_storage_balance_callback` executes with its fixed `NEP_141_STORAGE_BALANCE_CALLBACK_GAS` budget, parsing `evil.near`'s crafted return payload exhausts the remaining gas mid-function, after the in-memory `self.has_in_flight_tx = false` (line 202) but before the receipt completes and persists state.
5. The receipt traps; state changes (including the flag reset) are discarded; the trie retains `has_in_flight_tx = true` from step 3.
6. Any subsequent `rlp_execute` call on this account now immediately returns `"transaction already in progress, please try again later"` (`lib.rs:97-105`) forever — the wallet is permanently frozen.

async fn test_insufficient_gas() -> anyhow::Result<()> {

        action,
        &wallet_sk,

        .inner
        .call(crate::tests::RLP_EXECUTE)
        .args_json(serde_json::json!({
            "target": target,
            "tx_bytes_b64": codec::encode_b64(&codec::rlp_encode(&signed_transaction))

        .raw_bytes()

    );

    utils::deploy_and_call_hello(&worker, &wallet_contract, &wallet_sk, 0).await?;

    Ok(())

/// Only one transaction can be in flight at a time.
#[tokio::test]
async fn test_simultaneous_transactions() -> anyhow::Result<()> {
    let TestContext { worker, wallet_contract, wallet_sk, .. } = TestContext::new().await?;

    let receiver_account = worker.root_account().unwrap();

    let initial_receiver_balance = receiver_account.view_account().await.unwrap().balance;

    let receiver_id = receiver_account.id().as_str().into();
    let action = Action::Transfer { receiver_id, yocto_near: 1 };
    let signed_transaction =
        utils::create_signed_transaction(0, receiver_account.id(), Wei::zero(), action, &wallet_sk);
    let wallet_method_call_1 = near_workspaces::operations::Function::new("rlp_execute")
        .args_json(serde_json::json!({
            "target": receiver_account.id(),
            "tx_bytes_b64": codec::encode_b64(&codec::rlp_encode(&signed_transaction))
        }))
        .gas(near_workspaces::types::Gas::from_tgas(100));
    let wallet_method_call_2 = near_workspaces::operations::Function::new("rlp_execute")
        .args_json(serde_json::json!({
            "target": receiver_account.id(),
            "tx_bytes_b64": codec::encode_b64(&codec::rlp_encode(&signed_transaction))
        }))
        .gas(near_workspaces::types::Gas::from_tgas(100));

    let near_transaction = wallet_contract
        .inner
        .as_account()
        .batch(wallet_contract.inner.id())
        .call(wallet_method_call_1)
        .call(wallet_method_call_2)
        .transact()
        .await?;

    let result: ExecuteResponse = near_transaction.json()?;

    // The second transaction in the batch fails and this is returned as the
    // result of the Near transaction. But the first transaction in the batch
    // spawns promises that resolve, so the transfer was will successful.
    assert!(!result.success);
    assert!(result.error.unwrap().contains("transaction already in progress"));

    let final_receiver_balance = receiver_account.view_account().await.unwrap().balance;
    assert_eq!(final_receiver_balance.as_yoctonear() - initial_receiver_balance.as_yoctonear(), 1,);

    Ok(())
}
