### Title
Unauthenticated `RecvError` packets let an off-path attacker force tunnel teardown and delay reconnection - ([File: outside.go])

### Summary
Nebula's `RecvError` message is processed before any certificate or encryption validation, and the only binding check performed is that the packet's source UDP address matches the tunnel's *currently known* remote address. Because the Nebula wire header (which carries `RemoteIndex`) is never encrypted — even on ordinary `Message` packets — and UDP source addresses are trivially spoofable, an attacker holding no CA-signed certificate at all can forge a `RecvError` packet that tears down a victim's established tunnel and clears its pending-handshake state, forcing the victim to redo a full handshake. This is the same bug class as the reported `RLN.slashCommit` issue: a piece of shared per-victim state (a tunnel/hostinfo, analogous to `slashCommitments[account]`) can be mutated by a party that doesn't own it, without any check that the mutator is the legitimate counterpart, causing a delay/DoS to the legitimate party.

### Finding Description
In `outside.go`, `RecvError` is dispatched immediately, ahead of the `hostinfo == nil` / decryption checks that gate every other inbound packet type: [1](#0-0) 

`handleRecvError` resolves the tunnel purely from the plaintext `RemoteIndex` field via `QueryReverseIndex`, and the only authentication is a *comparison of the current known remote address* — not a cryptographic proof of identity: [2](#0-1) 

If the check passes, the code unconditionally tears the tunnel down and also purges it from the pending handshake manager "to allow for fast reconnect": [3](#0-2) 

The nebula packet header (which carries `RemoteIndex`) is not encrypted for any packet type, so an attacker positioned to observe traffic between two peers (or who can otherwise learn a live `RemoteIndex`) can forge this teardown packet. Combined with the ability to spoof a UDP source address (no certificate required to send a UDP datagram), the attacker never needs a CA-signed certificate to trigger this state mutation on the victim's tunnel — directly analogous to the RLN report, where any slasher (without any special relationship to the victim) could write into `slashCommitments[victimAccount][hash]` and delay the victim's ability to complete their own action. Here, an attacker without any credential can write into the victim's tunnel/hostinfo lifecycle state and force a delay (full re-handshake) instead of the intended fast, uninterrupted operation.

### Impact Explanation
A successful forgery causes:
- Local teardown of a legitimate, already-established tunnel (`f.closeTunnel(hostinfo)`), and
- Removal from the pending handshake manager, which is meant to speed up recovery but also means the attacker can repeat the attack against every fresh handshake attempt, effectively keeping the victim permanently unable to establish a stable tunnel to a given peer — a remote state-poisoning / DoS impact, matching the "significant delay to the victim, benefiting the attacker/others" pattern of the original report.

### Likelihood Explanation
Exploitability depends on two capabilities that are unrelated to holding a Nebula certificate: (1) discovering a live `RemoteIndex` value (visible in the cleartext header of every packet exchanged between the target peers — obtainable by anyone able to observe that traffic, e.g., an on-path or same-network attacker, or a malicious relay/lighthouse-adjacent observer), and (2) spoofing the legitimate remote's UDP source address so it matches `hostinfo.GetRemote()`. Both are classic off-path/on-path network attacker capabilities that do not require possessing a CA-signed certificate. I was not able to fully verify the rate-limiting behavior of `ShouldRecvError`/`acceptRecvErrorConfig` in `interface.go` within the available investigation — if these limits are strict per-source or per-index, they could reduce (but likely not eliminate) repeatability of the attack. This uncertainty should be resolved by reviewing `interface.go`'s `RecvErrorConfig`/`ShouldRecvError` implementation directly.

### Recommendation
Do not act on `RecvError` (or any other pre-authentication control message) based solely on a plaintext index and a same-address heuristic. Options:
- Require `RecvError` handling to only take effect after some additional per-tunnel secret/nonce check, or rate-limit/verify the packet count against something that isn't purely spoofable UDP source + observable index.
- Consider requiring a short authenticated proof (e.g., a MAC keyed by the tunnel's session key) instead of relying on address matching alone, similar to how the RLN fix bound the commitment to `msg.sender` rather than trusting an externally supplied hash/address pair.

### Proof of Concept
1. Establish a tunnel between "me" and "them" (both have valid nebula certs). This is the target state to disrupt.
2. An attacker (no valid cert, e.g., an on-path observer or someone able to sniff a single packet exchanged between "me" and "them") records the plaintext header of any packet to learn `RemoteIndex` for one direction of the tunnel.
3. The attacker crafts a `header.RecvError` packet with that `RemoteIndex` and sends it to "them", spoofing the UDP source address to equal "me"'s current known remote address (see the source-address check in `handleRecvError`, `outside.go:563-570`).
4. "them" tears down the tunnel to "me" and clears the corresponding pending handshake entry (`outside.go:572-575`), forcing "me" to redo a full handshake — a delay directly inflicted by a party holding no valid Nebula certificate, mirroring the RLN report's "any slasher can increase another one's reveal delay" bug class.

Note: I could not fully confirm within the available investigation how aggressively `ShouldRecvError`/`acceptRecvErrorConfig` (referenced in `interface.go`) throttles this path; a Devin session with full repo access should inspect `interface.go` to characterize exact rate limits and repeatability of the attack.

func (f *Interface) handleRecvError(addr netip.AddrPort, h *header.H) {
	if !f.acceptRecvErrorConfig.ShouldRecvError(addr) {
		f.l.Debug("Recv error received, ignoring",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
		return
	}

	if f.l.Enabled(context.Background(), slog.LevelDebug) {
		f.l.Debug("Recv error received",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
	}

	hostinfo := f.hostMap.QueryReverseIndex(h.RemoteIndex)
	if hostinfo == nil {
		f.l.Debug("Did not find remote index in main hostmap", "remoteIndex", h.RemoteIndex)
		return
	}

	hr := hostinfo.GetRemote()
	if hr.IsValid() && hr != addr {
		f.l.Info("Someone spoofing recv_errors?",
			"addr", addr,
			"hostinfoRemote", hr,
		)
		return
	}

	f.closeTunnel(hostinfo)
	// We also delete it from pending hostmap to allow for fast reconnect.
	f.handshakeManager.DeleteHostInfo(hostinfo)
}
