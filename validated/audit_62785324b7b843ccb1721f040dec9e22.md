### Title
Legacy (non-hardened) Bancor-style exchange math lacks denominator/overflow validation, allowing corrupted or bricked TRC10↔TRX exchange pools - (File: `chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java`)

### Summary
The Sherlock report describes a division whose denominator (`_currentLeverageRatio - (_leverageRatioFloor - _leverageRatioBuffer)`) is never checked against zero, letting an attacker steer a state variable that is fully controlled through normal user-facing calls (protection purchases) until the denominator collapses to zero, permanently reverting/bricking the function for everyone. The closest reachable analog in java-tron is the legacy TRC10 Bancor-relay exchange math in `ExchangeProcessor`, used by the actuators `ExchangeTransactionActuator`, `ExchangeInjectActuator`, and `ExchangeWithdrawActuator`. This code performs floating-point division on values (`newBalance`, `supply`) that are entirely derived from prior, attacker-controllable `ExchangeInject`/`ExchangeWithdraw`/`ExchangeTransaction` calls, with **no explicit check that the denominator is non-zero, non-negative, or that the result is finite**, unlike the newer `SafeExchangeProcessor` path which was hardened specifically to reject these cases.

### Finding Description
`ExchangeProcessor.exchangeToSupply` and `exchangeFromSupply` divide by `newBalance` and `supply` respectively: [1](#0-0) 

Neither method validates that `newBalance` or `supply` is non-zero/non-negative before dividing, and the result of `Math.pow`/multiplication is cast directly to `long` (`(long) issuedSupply`, `(long) exchangeBalance`), so `NaN`/`Infinity` silently truncate to `0` or `Long.MAX_VALUE`-adjacent values instead of raising an exception. This is invoked from `ExchangeCapsule.transaction`, which is reachable directly from `ExchangeTransactionActuator.execute`/`doValidate` on every `ExchangeTransactionContract` broadcast by any account: [2](#0-1) [3](#0-2) 

By contrast, the hardened path (`SafeExchangeProcessor`, selected only when `allowHardenExchangeCalculation()` / `allowHarden()` is enabled) explicitly throws `ArithmeticException` on the same edge cases, which is proven by the existing test `testSafeProcessorDivByZeroThrows`: [4](#0-3) [5](#0-4) [6](#0-5) 

This confirms the root cause the auditors identified for `RiskFactorCalculator`—an unchecked denominator reachable through user-driven state changes—exists in the legacy (`allowHarden() == false`) exchange path in java-tron: the pool balances (`firstTokenBalance`/`secondTokenBalance`, hence `newBalance`, and the ephemeral internal `supply` counter) are moved by ordinary `ExchangeInjectContract`/`ExchangeWithdrawContract`/`ExchangeTransactionContract` transactions, and no bound prevents them from reaching values that zero out or invert the divisor inside `exchangeToSupply`/`exchangeFromSupply` before the hardened guard was introduced.

### Impact Explanation
When the legacy (non-hardened) processor is in effect, a sequence of attacker-crafted `ExchangeInject`/`ExchangeWithdraw`/`ExchangeTransaction` transactions can push `newBalance` or the internal `supply` toward zero/negative, producing `NaN`/`Infinity` results that are silently truncated when cast to `long`. This can (a) corrupt the exchange's on-chain token balances (`ExchangeCapsule.setBalance`), creating an unbacked or negative-implied balance for one side of the pair, or (b) produce nonsensical `anotherTokenQuant` values that get transferred to accounts via `addAssetAmountV2`/`setBalance`, i.e., unbacked-balance creation/theft, or (c) leave the exchange pair in a state where every subsequent transaction against it throws/produces bad values, effectively bricking that exchange pair for all future users — directly mirroring the reported "denial of the system" impact.

### Likelihood Explanation
The legacy processor is only exercised while `allowHardenExchangeCalculation()` is not yet activated for a given deployment/chain state (this is a governance-controlled proposal flag), so exploitability depends on which processor is active at the time. Given that a distinct hardened path (`SafeExchangeProcessor`) was added specifically to close divide-by-zero/overflow gaps in this exact formula, this indicates the legacy path was previously exploitable in the same way, and any network/fork where the harden flag is not yet enabled remains exposed. All three actuators are directly reachable by any unprivileged account via ordinary broadcast transactions, requiring no special privileges — only a pre-existing exchange pair with a controllable token balance.

### Recommendation
- Always route exchange calculations through `SafeExchangeProcessor` (or equivalent overflow/zero-checked BigDecimal arithmetic) regardless of the `allowHardenExchangeCalculation` proposal state, rather than gating the fix behind a governance flag.
- In `ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply`, explicitly validate `newBalance != 0` and `supply > 0` before dividing, and reject/throw on `NaN`/`Infinite` results instead of silently truncating via `(long)` cast.
- Add pool-level invariant checks (e.g., minimum token balance, minimum supply) enforced in `doValidate()` for `ExchangeTransactionActuator`, `ExchangeInjectActuator`, and `ExchangeWithdrawActuator` to prevent balances/supply from approaching the values that trigger the unchecked division.

### Proof of Concept
Exact numeric parameters to zero the denominator cannot be confirmed without executing the formula against live/simulated pool state (this mirrors the original report's approach of describing the reachable code path rather than a concrete numeric exploit). The reachable path is:
1. Attacker creates or targets an existing TRC10↔TRX exchange pair with a very small balance on one side (achievable via repeated `ExchangeWithdrawContract` calls down to the validated minimum).
2. Attacker issues an `ExchangeTransactionContract` with `tokenQuant` sized relative to the depleted balance such that `quant / newBalance` in `exchangeToSupply` (or the derived `supply` in `exchangeFromSupply`) drives the `Math.pow` computation to `Infinity`/`NaN`.
3. Because the legacy `ExchangeProcessor` (invoked when `allowHarden()` is false) does not validate the divisor or the finiteness of the result before truncating to `long`, the resulting `anotherTokenQuant`/pool balances become corrupted, as demonstrated by the need for the separate `testSafeProcessorDivByZeroThrows` test to guard only the hardened processor: [5](#0-4)

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
  }

  private BigDecimal exchangeToSupply(long balance, long quant) {
    long newBalance = StrictMathWrapper.addExact(balance, quant);
    BigDecimal bdQuant = BigDecimal.valueOf(quant);
    BigDecimal bdNewBalance = BigDecimal.valueOf(newBalance);
    BigDecimal base = BigDecimal.ONE.add(
        bdQuant.divide(bdNewBalance, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 0.0005);
    return SUPPLY.negate().multiply(
        BigDecimal.ONE.subtract(BigDecimal.valueOf(powResult))).setScale(0, RoundingMode.DOWN);
  }

  private long exchangeFromSupply(long balance, BigDecimal supplyQuant) {
    BigDecimal bdBalance = BigDecimal.valueOf(balance);
    BigDecimal base = BigDecimal.ONE.add(
        supplyQuant.divide(SUPPLY, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 2000.0);
    BigDecimal exchangeBalance = bdBalance.multiply(
        BigDecimal.valueOf(powResult).subtract(BigDecimal.ONE));
    return exchangeBalance.setScale(0, RoundingMode.DOWN).longValueExact();
  }
