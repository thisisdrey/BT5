Confirmed: the `AddressRegistrar` contract has `register`, `lookup`, `get_address`, and `new` — no admin/owner withdrawal method exists anywhere in the contract or its global deployment story.### Title
Excess deposit permanently locked in AddressRegistrar `register()` on successful registration - ([File: runtime/near-wallet-contract/implementation/address-registrar/src/lib.rs])

### Summary
The `AddressRegistrar::register` method is `#[payable]` and accepts an attached NEAR deposit to cover the storage cost of a new `address -> account_id` mapping. When registration succeeds (the `Entry::Vacant` branch), any deposit amount above the exact storage cost is silently kept by the contract with no mechanism to return or withdraw it — analogous to a Solidity contract implementing `receive()` but providing no way to extract funds sent in by mistake.

### Finding Description
`register()` requires `given_deposit >= required_deposit` and panics if insufficient [1](#0-0) . On the collision path (`Entry::Occupied`), the code explicitly refunds the *entire* `given_deposit` back to the caller because no storage was written [2](#0-1) . However, on the success path (`Entry::Vacant`), the contract only consumes `required_deposit` worth of storage but never refunds the difference (`given_deposit - required_deposit`) back to the caller, nor does it return the exact amount actually needed — the whole `given_deposit` is retained by the contract's balance [3](#0-2) .

The contract exposes no owner, admin, or any privileged withdrawal method (`register`, `lookup`, `get_address`, `new` are the only public methods) [4](#0-3) . There is no `sweepTo`-style function, no owner field in the `AddressRegistrar` struct [5](#0-4) , and no code path anywhere else in the wallet-contract implementation that can extract funds from this specific contract's balance. This directly mirrors the reported Solidity finding: a `payable`/`receive()`-style entry point accepts funds, but excess/erroneous amounts sent in cannot ever be recovered — by the sender or any operator.

This contract is a production, in-scope component: it is called from `AddressRegistrar` cross-contract calls originating from the NEAR Wallet Contract's ETH-transaction-emulation flow (`inner_rlp_execute` and the `address_check_callback`/ERC-20 transfer paths call into `ADDRESS_REGISTRAR_ACCOUNT_ID`) [6](#0-5) , meaning it is reachable by ordinary users through Ethereum-compatible transactions relayed through the ETH-implicit account Wallet Contract, i.e. an ordinary, unprivileged signer path.

### Impact Explanation
Any caller who over-deposits when calling `register()` (e.g. attaching more than the exact storage byte cost, which is easy to do since callers typically round up or use a fixed convenience deposit) permanently loses the excess amount — it becomes stuck in the `AddressRegistrar` contract's balance with no code path to retrieve it. Over time and across many registrations this is a straightforward, permanent loss-of-funds bug for end users, matching the "permanent freezing of funds" acceptance criterion. It is a real but bounded impact — it does not directly enable theft of other users' funds, does not create protocol-level inflation, and does not affect consensus/state-root correctness; it only irreversibly locks each caller's own overpayment inside the contract.

### Likelihood Explanation
Likelihood is high in relative terms for triggering the loss (any caller attaching a deposit larger than the exact minimal computed storage cost loses the difference automatically, with no malicious action required — a simple UX/API mistake by a wallet, relayer, or user is sufficient), but the amounts lost per call are individually small (yoctoNEAR-per-byte storage cost differences), and users must specifically call `register` on this specific auxiliary registrar contract rather than the more commonly used core wallet paths.

### Recommendation
On the successful `Entry::Vacant` path, refund `given_deposit.saturating_sub(required_deposit)` back to `env::predecessor_account_id()` via a promise transfer, mirroring the refund logic already implemented in the `Entry::Occupied` branch. Additionally, consider adding an owner-only sweep/withdraw method for defense-in-depth in case deposits accumulate through other paths.

### Proof of Concept
1. Deploy `AddressRegistrar` and call `register({"account_id": "birchmd.near"})` attaching a deposit greater than `storage_byte_cost * (20 + len("birchmd.near"))`, e.g. attach `1 NEAR` when the required storage deposit is only a few hundred bytes' worth of yoctoNEAR.
2. The call succeeds (`Entry::Vacant` branch executes, `Some(address)` returned).
3. Observe that `address_registrar`'s account balance increases by the *entire* attached deposit, not just the computed `required_deposit`.
4. There is no method on the contract (and no other privileged path) to retrieve the excess `given_deposit - required_deposit`; it is permanently locked in the contract's balance. This is directly analogous to `test_register_without_deposit` in `runtime/near-wallet-contract/implementation/wallet-contract/src/tests/sanity.rs:249-296`, which already demonstrates (without flagging it as a bug) that a successful registration deposit is retained in full by the contract balance regardless of how much exceeds the storage requirement [7](#0-6) .

#[near_bindgen]
#[derive(PanicOnDefault, BorshDeserialize, BorshSerialize)]
#[borsh(crate = "near_sdk::borsh")]
pub struct AddressRegistrar {
    pub addresses: LookupMap<Address, AccountId>,
}

#[near_bindgen]
impl AddressRegistrar {
    #[init]
    pub fn new() -> Self {
        Self { addresses: LookupMap::new(StorageKey::Addresses) }
    }

    /// Computes the address associated with the given `account_id` and
    /// attempts to store the mapping `address -> account_id`. If there is
    /// a collision where the given `account_id` has the same address as a
    /// previously registered one then the mapping is NOT updated and `None`
    /// is returned. Otherwise, the mapping is stored and the address is
    /// returned as a hex-encoded string with `0x` prefix.
    #[payable]
    pub fn register(&mut self, account_id: AccountId) -> Option<String> {
        // It is not allowed to register eth-implicit accounts because the purpose
        // of the registry is to allow looking up the named account associated with
        // an address obtained via hashing, but eth-implicit accounts are already
        // parsable as addresses.
        if is_eth_implicit(&account_id) {
            let log_message = format!("Refuse to register eth-implicit account {account_id}");
            env::log_str(&log_message);
            return None;
        }

        // Must store the address and the account id
        let bytes_to_store = 20 + (account_id.len() as u128);
        let required_deposit =
            NearToken::from_yoctonear(env::storage_byte_cost().as_yoctonear() * bytes_to_store);
        let given_deposit = env::attached_deposit();
        // The caller must pay for the storage cost of registering.
        if given_deposit < required_deposit {
            let message = format!(
                "Insufficient deposit to cover storage cost. Given={} Expected={}",
                given_deposit.as_yoctonear(),
                required_deposit.as_yoctonear(),
            );
            env::panic_str(&message);
        }

        let address = account_id_to_address(&account_id);

        match self.addresses.entry(address) {
            Entry::Vacant(entry) => {
                let address = format!("0x{}", hex::encode(address));
                let log_message = format!("Added entry {} -> {}", address, account_id);
                entry.insert(account_id);
                env::log_str(&log_message);
                Some(address)
            }
            Entry::Occupied(entry) => {
                let log_message = format!(
                    "Address collision between {} and {}. Keeping the former.",
                    entry.get(),
                    account_id
                );
                env::log_str(&log_message);
                // Transfer the deposit back to the caller since no storage was updated.
                let refund_promise = env::promise_batch_create(&env::predecessor_account_id());
                env::promise_batch_action_transfer(refund_promise, given_deposit);
                None
            }
        }
    }

    /// Attempt to look up the account ID associated with the given address.
    /// If an entry for that address is found then the associated account id
    /// is returned, otherwise `None` is returned. Use the `register` method
    /// to add entries to the map.
    /// This function will panic if the given address is not the hex-encoding
    /// of a 20-byte array. The `0x` prefix is optional.
    pub fn lookup(&self, address: String) -> Option<AccountId> {
        let address = {
            let mut buf = [0u8; 20];
            hex::decode_to_slice(address.strip_prefix("0x").unwrap_or(&address), &mut buf)
                .unwrap_or_else(|_| env::panic_str("Invalid hex encoding"));
            buf
        };
        self.addresses.get(&address).cloned()
    }

    /// Computes the address associated with the given `account_id` and
    /// returns it as a hex-encoded string with `0x` prefix. This function
    /// does not update the mapping stored in this contract. If you want
    /// to register an account ID use the `register` method.
    pub fn get_address(&self, account_id: AccountId) -> String {
        let address = account_id_to_address(&account_id);
        format!("0x{}", hex::encode(address))
    }
}
