### Title
Unbounded attacker-controlled array length in TVM precompile signature/address extraction leads to uncaught exceptions (DoS) - ([File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java])

### Summary
`ValidateMultiSign` (address `0x...0a`) and `BatchValidateSign` (address `0x...09`) decode calldata by reading a length word directly from attacker-supplied `DataWord[]` and using it to allocate and index arrays, without validating it against the actual bounds of the `words` array, unless the `allowTvmOsaka` feature switch is active.

### Finding Description
`extractBytesArray`, `extractSigArray`, and `extractBytes32Array` read `len` from `words[offset].intValueSafe()` — fully attacker-controlled via the calldata of a `CALL` to the precompile address — and then allocate `new byte[len][]` and loop `for (int i = 0; i < len; i++)` indexing `words[offset + i + 1]` with no check that `offset + len` stays within `words.length`: [1](#0-0) 

This is the same bug class as CVE-2016-4330: a size/dimension value is read from untrusted input and used to allocate/index memory without validating it against the space actually available, producing out-of-bounds access (in Java, `ArrayIndexOutOfBoundsException` / `NegativeArraySizeException` / potential huge-allocation `OutOfMemoryError` rather than heap corruption, since the JVM has bounds-checked arrays).

The call sites in `ValidateMultiSign.execute` and `BatchValidateSign.doExecute` only apply a length-sanity check (`isValidAbiEncoding`) and a `MAX_SIZE` guard on `sigArraySize`/`addrArraySize` when `VMConfig.allowTvmOsaka()` is true: [2](#0-1) [3](#0-2) 

The project's own test suite documents this exact pre-activation gap: "before activation, malformed calldata reaches the legacy decoder... this precompile has no outer catch, so a too-short input raises inside the decoder; that is the documented pre-activation failure mode": [4](#0-3) 

`allowTvmOsaka` is a chain-parameter-gated feature flag (`VMConfig.allowTvmOsaka()` / `initAllowTvmOsaka`), meaning the guard only exists behind an activation switch that must be voted in by Super Representatives: [5](#0-4) [6](#0-5) 

Note: I could not determine from the indexed code whether `allowTvmOsaka` is currently activated on mainnet — that is chain-state, not something derivable from source. If it is not yet activated, the unguarded path in `ValidateMultiSign`/`BatchValidateSign` is reachable today from any contract call.

`BatchValidateSign.execute` wraps `doExecute` in a broad `catch (Throwable t)` that swallows any exception and returns a zero result, so this path largely degrades to a failed call rather than a crash: [7](#0-6) 
However, `ValidateMultiSign.execute` has no such outer catch around the array-extraction calls themselves (the `try/catch` only wraps the signature-weight loop after extraction succeeds): [8](#0-7) 

### Impact Explanation
When `allowTvmOsaka` is not active, a contract call to `ValidateMultiSign` with a crafted length word (`words[offset]`) that is larger than the remaining `words` array causes an uncaught `ArrayIndexOutOfBoundsException` (or `NegativeArraySizeException`/large-allocation stress if `len` is huge) inside `extractBytesArray`/`extractSigArray`. Since there is no local catch around this call in `ValidateMultiSign.execute`, the exception propagates out of the precompile into the TVM/`Program` execution path. Depending on how the caller (TVM opcode dispatch / `Program`) handles arbitrary `RuntimeException`s from precompiles, this is at minimum a reliable way to abort/fail a transaction (revert), and if any code path along the way does not defensively catch it, it risks destabilizing node execution for that transaction. This is a Medium-severity availability/robustness issue reachable by any unprivileged contract caller — not a memory-corruption/RCE issue as in the original HDF5 CVE, since Java's bounds-checked arrays prevent true heap overflow.

### Likelihood Explanation
High reachability: any account can deploy or call a contract that invokes the `ValidateMultiSign`/`BatchValidateSign` precompile addresses with attacker-chosen calldata; no special privilege is required. Whether it is actually exploitable depends entirely on whether `allowTvmOsaka` is enabled on the target network at the current block — this is the deciding factor and could not be verified from the source alone.

### Recommendation
- Make the `isValidAbiEncoding` / array-length bound checks (`sigArraySize > MAX_SIZE`, `addrArraySize > MAX_SIZE`) unconditional in `extractBytesArray`, `extractSigArray`, and `extractBytes32Array` themselves, rather than only under the `allowTvmOsaka` feature flag, so the fix applies to all chains/forks regardless of activation status.
- Add an explicit bounds check inside `extractBytesArray`/`extractSigArray`/`extractBytes32Array`: verify `offset + len < words.length` (and `len >= 0`) before allocating/looping, returning an empty array or failure result otherwise, matching the defensive pattern already used at the top of `extractBytesArray`/`extractSigArray` (`if (offset > words.length - 1) return new byte[0][];`).
- Wrap the array-extraction calls in `ValidateMultiSign.execute` in a try/catch (as already done in `BatchValidateSign.execute`) so any residual parsing exception degrades gracefully instead of propagating.

### Proof of Concept
1. Craft calldata for `ValidateMultiSign` (address `0x...0a`) with valid header words (`address`, `permissionId`, `data` hash, offset word) but set the value at the computed signature-array-length slot (`words[words[3].intValueSafe()/32]`) to a large value (e.g., `0x7fffffff` or a value such that `offset + len + 1 > words.length`), while keeping the raw calldata short.
2. Deploy/call a contract that performs a `STATICCALL`/`CALL` to this precompile address with the crafted calldata, on a network/fork where `allowTvmOsaka` is not yet activated.
3. Observe `extractBytesArray`/`extractSigArray` throwing `ArrayIndexOutOfBoundsException` (or attempting a huge/negative array allocation) with no enclosing catch in `ValidateMultiSign.execute`, propagating out of the precompile call — confirmed by the project's own test comment describing this exact "no outer catch... raises inside the decoder" pre-activation behavior in `ValidateMultiSignContractTest.testTip854PreActivationNoOp`.

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
