Based on my investigation, the claim is accurate. `system.rs` contains no `is_delegate_call()` guard anywhere in the file — the only state-changing check present is the `is_read_only()` guard on `terminate`, confirmed by reading the complete file [1](#0-0) , while `terminate` itself calls `env.terminate_caller(&h160)` unconditionally otherwise [2](#0-1) . This contrasts with `asset-conversion`'s precompile, which explicitly rejects delegate calls with `frame_support::ensure!(!env.is_delegate_call(), pallet_revive::Error::<Self::T>::PrecompileDelegateDenied)` [3](#0-2) , and the builtin `Storage` precompile, which inverts the check and *requires* delegate call [4](#0-3) . The prdocs `pr_11676.prdoc` and `pr_11715.prdoc` confirm this was a deliberate, repository-wide remediation pattern applied to the assets, asset-conversion, vesting, and XCM precompiles specifically because "there is no legitimate use case for delegatecalling into the [asset/precompile]," but `System` was never updated to match.

Audit Report

## Title
Missing `is_delegate_call` guard on `System` builtin precompile allows state-changing `terminate()` to execute in the caller's storage/value context via `DELEGATECALL` - (File: `substrate/frame/revive/src/precompiles/builtin/system.rs`)

## Summary
The `System` precompile at fixed address `0x900` guards `terminate` only against read-only (`STATICCALL`) context via `env.is_read_only()`, but never checks `env.is_delegate_call()` anywhere in the file, unlike every sibling precompile (`asset-conversion`, `assets`, `vesting`, `pallet-xcm`, and the builtin `Storage` precompile), which were all patched per `prdoc/stable2606/pr_11676.prdoc` and `prdoc/stable2606/pr_11715.prdoc` to explicitly reject or require delegate calls. Because `delegate_call` in `pallet-revive`'s execution stack pushes a frame that reuses the calling contract's `account_id` and `value_transferred` while only swapping executed code, a contract that is tricked or designed to `DELEGATECALL` into code reaching `System::terminate` will have `env.terminate_caller` operate on its own account, draining its native balance to an attacker-chosen `beneficiary` and scheduling its own destruction.

## Finding Description
`System::call()`'s only guard is `ISystemCalls::terminate(_) if env.is_read_only() => Err(...StateChangeDenied)`, with no `is_delegate_call()` check anywhere in the dispatcher. `terminate` unconditionally calls `env.terminate_caller(&h160)` when not read-only. Every other value-affecting precompile in the repository (`asset-conversion`, `assets`, `vesting`, `pallet-xcm`) has an explicit `ensure!(!env.is_delegate_call(), ...PrecompileDelegateDenied)` guard added specifically to prevent precompile logic from executing "in the caller's context" during a delegatecall, and the builtin `Storage` precompile inverts this to *require* delegate call for its own different reasons. `System` was not included in either remediation PR, leaving it as the only precompile with a state-mutating function reachable via delegatecall without any delegate-call-aware guard.

## Impact Explanation
This matches the Polkadot SDK impact gate's "permanent user-fund lock" / theft class: an attacker who gets any contract to delegatecall into code invoking `ISystem(0x900).terminate(beneficiary)` causes that contract's own account (not the precompile's) to have its full native balance transferred to an attacker-chosen address and be scheduled for destruction, since delegate-call frames retain the delegating contract's `account_id` and `value_transferred`.

## Likelihood Explanation
`DELEGATECALL` is a standard, freely available EVM primitive for any contract author, and the `System` precompile sits at a fixed, well-known, intentionally-reachable address (`0x900`). No privileged actor, governance, or off-chain compromise is required — only that some contract (e.g. a proxy/library pattern) delegates into attacker-influenced code that calls `terminate`, which is a common and realistic composability pattern in EVM-style ecosystems.

## Recommendation
Add the same `ensure!(!env.is_delegate_call(), pallet_revive::Error::<Self::T>::PrecompileDelegateDenied)` guard used by `asset-conversion`, `assets`, `vesting`, and `pallet-xcm` precompiles to the top of `System::call()` in `substrate/frame/revive/src/precompiles/builtin/system.rs`, and audit remaining builtin/external precompiles for the same omission.

## Proof of Concept
1. Deploy `VictimContract` holding native balance.
2. Deploy `MaliciousLib` whose code calls `ISystem(0x900).terminate(attackerAddress)`.
3. `VictimContract` performs `address(MaliciousLib).delegatecall(...)` targeting `ISystem.terminate`.
4. `pallet-revive`'s `delegate_call` pushes a frame with `dest: VictimContract.account_id`, reaching `System::call()` unguarded by any delegate-call check.
5. `terminate` executes `env.terminate_caller(&attackerAddress)` against `VictimContract`'s own account, transferring its full balance to `attacker` and scheduling it for deletion — reproducible as a Rust integration test analogous to `delegatecall_is_rejected` tests added for the other precompiles (e.g. `substrate/frame/vesting/precompiles/src/tests.rs`, `polkadot/xcm/pallet-xcm/precompiles/src/tests.rs`), but expected to fail for `System` since no such guard/test exists.
