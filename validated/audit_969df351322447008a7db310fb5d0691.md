### Title
Bancor-formula low-liquidity manipulation in TRC10 `Exchange` swap actuator - (File: `chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java`)

### Summary
`ExchangeCreateContract` lets any account permissionlessly create a Bancor-style TRC10↔TRC10/TRX liquidity pool with arbitrarily small (but non-zero) balances, and `ExchangeTransactionContract` lets any account trade against any existing pool without any external price reference, TWAP, or minimum-liquidity guard. This mirrors the TheStandard.io class of bug: a market whose price is derived solely from a thinly-funded internal pool can be moved by a single attacker-controlled transaction, then exploited via a follow-up trade (or via precision loss in the pricing math) to extract value at the expense of the other token's balance in the pool.

### Finding Description
`ExchangeCreateActuator.doValidate()` only requires `firstTokenBalance > 0` and `secondTokenBalance > 0` (up to `dynamicStore.getExchangeBalanceLimit()`), with no minimum-liquidity floor: [1](#0-0) 

Any unprivileged account can therefore create a pool such as 1 unit of TokenA vs 1 unit of TokenB (or TRX), i.e. the exact "low liquidity pool" precondition described in the report.

`ExchangeTransactionActuator` then lets any account swap against that pool. The exchange rate is computed purely internally by `ExchangeCapsule.transaction()`, which calls into a Bancor "relay-token" formula (`ExchangeProcessor`) using floating-point `Math.pow`: [2](#0-1) [3](#0-2) 

There is no oracle, no TWAP, and no minimum-liquidity/maximum-price-impact check in `ExchangeTransactionActuator.doValidate()` — the only guard is the caller-supplied `tokenExpected` slippage parameter, which the attacker fully controls and can set to `1`: [4](#0-3) 

Because the pool can be created with trivial liquidity and the swap price is a pure function of the two on-chain balances, a single attacker can:
1. Create (or find) an `Exchange` pool with tiny liquidity for a token pair they control interest in.
2. Execute an `ExchangeTransactionContract` to swap a comparatively large amount into the thin side of the pool, driving `exchange.secondTokenBalance`/`firstTokenBalance` to an extreme ratio in one atomic transaction (there's no per-block/price-impact cap beyond `getExchangeBalanceLimit()`).
3. Immediately reverse the trade or route further legitimate users through the pool to arbitrage the artificial price back to a favorable ratio, extracting more of the counter-asset than was deposited — the same "manipulate low-liquidity pool then extract funds" mechanism as the TheStandard.io PAXG pool incident, just implemented natively rather than via a smart contract/AMM.

The repository's own test suite acknowledges precision/overflow risk in this exact code path — it added a `allowHardenExchangeCalculation` flag and a `SafeExchangeProcessor` (BigDecimal-based) as a hardened alternative to the default floating-point `ExchangeProcessor`, and tests explicitly exercise overflow/precision edge cases: [5](#0-4) [6](#0-5) 

This confirms the double-based Bancor math (`exchangeToSupply`/`exchangeFromSupply` in `ExchangeProcessor`) is a recognized source of rounding/precision error, which becomes economically significant precisely when pool balances are small — i.e., exactly the low-liquidity condition from the report.

### Impact Explanation
An attacker can drain value from a thinly-liquidity `Exchange` pool by manipulating its internal price with a single or small number of self-controlled transactions, then extracting the counter-asset — a direct unauthorized-transfer-of-value / theft-of-funds outcome for TRC10 tokens or TRX held in `Exchange` pools, reachable from a single signed transaction with no special privilege.

### Likelihood Explanation
Likelihood is Medium: creating a pool and trading against it requires only a normal signed transaction (`ExchangeCreateContract`/`ExchangeTransactionContract`), no special permissions, and the balance/fee checks are trivial to satisfy. The primary constraint is that victims must have deposited liquidity into (or be induced to trade through) the manipulated pool; pools created solely by the attacker only harm the attacker unless a counterparty also supplies liquidity or the pool is later used by other users, similar to how TheStandard.io's PAXG pool required existing depositor liquidity to make the attack profitable.

### Recommendation
- Enforce a protocol-level minimum liquidity/balance floor in `ExchangeCreateActuator.doValidate()` (beyond `> 0`) so pools cannot be created with economically negligible reserves.
- Add a maximum single-transaction price-impact/slippage cap in `ExchangeTransactionActuator.doValidate()` independent of the caller-supplied `tokenExpected`, so a single trade cannot move the pool ratio beyond a bounded percentage.
- Make `SafeExchangeProcessor` (BigDecimal-based) the default/mandatory path instead of gating it behind `allowHardenExchangeCalculation`, removing floating-point precision risk from the exchange rate calculation entirely.

### Proof of Concept
1. Submit `ExchangeCreateContract` from account A with `firstTokenBalance=1`, `secondTokenBalance=1` (or similarly minimal values satisfying only `>0` and `< getExchangeBalanceLimit()`), creating pool `P` — see validation at `ExchangeCreateActuator.java:201-208`.
2. Have a victim (or a second attacker-controlled account) inject meaningful liquidity into `P` via `ExchangeInjectContract`.
3. From account A, submit `ExchangeTransactionContract` against `P` with `tokenId` set to the thin side and `quant` large relative to pool reserves, `expected=1` to bypass slippage protection — validated only by `ExchangeTransactionActuator.java:217-221` (`anotherTokenQuant < tokenExpected` check, trivially satisfied).
4. Observe `ExchangeCapsule.transaction()` (`ExchangeCapsule.java:124-169`) sharply repricing the pool via `ExchangeProcessor.exchange()`'s floating-point Bancor formula.
5. Submit a follow-up `ExchangeTransactionContract` reversing the trade direction to extract more of the counter-asset than originally supplied, profiting from the price impact/rounding introduced in step 3-4.

    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;

package org.tron.core.capsule;

import java.math.BigDecimal;
import java.math.RoundingMode;
import lombok.extern.slf4j.Slf4j;
import org.tron.common.math.StrictMathWrapper;

@Slf4j(topic = "capsule")
public class SafeExchangeProcessor implements ExchangeCapsule.Processor {

  private static final BigDecimal SUPPLY = BigDecimal.valueOf(1_000_000_000_000_000_000L);

  public static final SafeExchangeProcessor INSTANCE = new SafeExchangeProcessor();

  private SafeExchangeProcessor() {

  }

  private BigDecimal exchangeToSupply(long balance, long quant) {
    long newBalance = StrictMathWrapper.addExact(balance, quant);
    BigDecimal bdQuant = BigDecimal.valueOf(quant);
    BigDecimal bdNewBalance = BigDecimal.valueOf(newBalance);
    BigDecimal base = BigDecimal.ONE.add(
        bdQuant.divide(bdNewBalance, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 0.0005);
    return SUPPLY.negate().multiply(
        BigDecimal.ONE.subtract(BigDecimal.valueOf(powResult))).setScale(0, RoundingMode.DOWN);
  }

  private long exchangeFromSupply(long balance, BigDecimal supplyQuant) {
    BigDecimal bdBalance = BigDecimal.valueOf(balance);
    BigDecimal base = BigDecimal.ONE.add(
        supplyQuant.divide(SUPPLY, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 2000.0);
    BigDecimal exchangeBalance = bdBalance.multiply(
        BigDecimal.valueOf(powResult).subtract(BigDecimal.ONE));
    return exchangeBalance.setScale(0, RoundingMode.DOWN).longValueExact();
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    BigDecimal relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
}
