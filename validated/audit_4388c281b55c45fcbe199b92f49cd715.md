Audit Report

## Title
Public message-fee calculation can round `fee.remote` to `0` for valid, non-zero pricing parameters, underpricing Ethereum-bound message delivery - (File: `bridges/snowbridge/pallets/outbound-queue/src/lib.rs`)

## Summary
`Pallet::<T>::calculate_fee` computes the Ethereum-side gas cost portion of the outbound message fee (`fee.remote`) by taking a wei-scale amount, converting it through `FixedU128` multiplier/exchange-rate arithmetic, and then dividing by `10^(ETHER_DECIMALS - T::Decimals)` (e.g. `10^8` for a 10-decimal native currency) in `convert_from_ether_decimals`. Any wei-scale intermediate smaller than that divisor truncates to `0`, even though every individual `PricingParameters` field passed `validate()` and is non-zero, which lets messages be dispatched to Ethereum at real gas cost while charging the sender nothing for it.

## Finding Description
The bug is confirmed in the actual pallet code: [1](#0-0) 

`calculate_remote_fee` produces `fee_per_gas * gas_used_at_most + reward` in wei [2](#0-1) , which is then reinterpreted via `FixedU128::from_inner`, multiplied by `params.multiplier`, divided by `params.exchange_rate`, and finally passed to `convert_from_ether_decimals`, which does an integer division by `10^decimals` (`10^8` for 10-decimal chains) with no rounding-up or minimum floor: [3](#0-2) .

`PricingParameters::validate()` only checks that each raw field (`exchange_rate`, `fee_per_gas`, `rewards.local`, `rewards.remote`, `multiplier`) is individually non-zero — it never checks the derived `fee.remote` after the full pipeline: [4](#0-3) . This guard is provably insufficient: the pallet's own test, using fully valid (`validate()`-passing) parameters, demonstrates `fee.remote` computing to `0` from a non-zero wei amount.

This computation sits on the unprivileged hot path: `SendMessage::validate` calls `calculate_fee` with `gas_used_at_most` from `T::GasMeter::maximum_gas_used_at_most(&message.command)` and the current governance-set `PricingParameters`, for every outbound message (XCM exports, asset transfers, etc.) before enqueuing the message for Ethereum dispatch: [5](#0-4) . There is no post-computation check anywhere in this path rejecting a zero `fee.remote`; the message is queued and delivered regardless (`deliver` at lines 76–88 of the same file).

## Impact Explanation
This matches the "public underpriced work that degrades block production or stalls bridge processing" impact category. Since `fee.remote` is meant to cover the real ETH-denominated gas cost of dispatching the message on Ethereum, when it rounds to `0` the message is still enqueued and eventually executed on Ethereum at real gas cost, but the sender pays nothing toward that cost. Because `SendMessage::validate`/`calculate_fee` runs unconditionally on essentially every Snowbridge outbound message, any unprivileged sender whose message's `gas_used_at_most` combines with the currently active `PricingParameters` to produce a sub-denominator wei amount gets a free (remote-fee-cost) Ethereum dispatch, which can be repeated to degrade the bridge's economic sustainability or flood the outbound queue.

## Likelihood Explanation
High. This requires no privileged action or compromised infrastructure — only an ordinary user submitting a bridge-eligible message (e.g., a low-gas command) while the currently governance-set `PricingParameters` combine with that gas ceiling to make the wei-scale intermediate value smaller than `10^8` (for a 10-decimal chain). This is not a contrived edge case: it is exactly reproduced by the pallet's existing unit test using realistic, `validate()`-passing parameter values (`exchange_rate = 1`, `fee_per_gas = 1`, `rewards = {1,1}`, `multiplier = 1`), showing the rounding-to-zero condition is easily reachable within the parameter space that legitimately passes all existing guards.

## Recommendation
- Add a check after computing `fee.remote` in `calculate_fee` (or in `SendMessage::validate`) that rejects the send, or applies a minimum non-zero fee floor, whenever the derived `fee.remote` is `0` but the underlying wei-scale remote cost was non-zero.
- Perform the exchange-rate/multiplier/decimals conversion with higher intermediate precision, or round up (ceiling division) instead of truncating in `convert_from_ether_decimals`, so any non-zero wei-scale cost maps to at least `1` unit of native currency.
- Extend `PricingParameters::validate()` (or add a runtime-time assertion) to check that `fee.remote != 0` holds across the full range of `gas_used_at_most` values the `GasMeter` can produce, not just that each raw field is individually non-zero.

## Proof of Concept
The pallet's existing test demonstrates the exact reproduction: with `gas_used = 250000` and `PricingParameters { exchange_rate: 1/1, fee_per_gas: 1, rewards: {local:1, remote:1}, multiplier: 1/1 }` (all fields non-zero, passing `validate()`), `OutboundQueue::calculate_fee(gas_used, price_params)` yields `fee.local = 698000000` and `fee.remote = 0` [6](#0-5) . Any subsequent call through `SendMessage::validate` for a message with a similarly small `gas_used_at_most` under such parameters will enqueue the message for Ethereum dispatch while charging `fee.remote = 0`.

		pub(crate) fn calculate_fee(
			gas_used_at_most: u64,
			params: PricingParameters<T::Balance>,
		) -> Fee<T::Balance> {
			// Remote fee in ether
			let fee = Self::calculate_remote_fee(
				gas_used_at_most,
				params.fee_per_gas,
				params.rewards.remote,
			);

			// downcast to u128
			let fee: u128 = fee.try_into().defensive_unwrap_or(u128::MAX);

			// multiply by multiplier and convert to local currency
			let fee = FixedU128::from_inner(fee)
				.saturating_mul(params.multiplier)
				.checked_div(&params.exchange_rate)
				.expect("exchange rate is not zero; qed")
				.into_inner();

			// adjust fixed point to match local currency
			let fee = Self::convert_from_ether_decimals(fee);

			Fee::from((Self::calculate_local_fee(), fee))
		}

			return Err(InvalidPricingParameters);

	fn validate(
		message: &Message,
	) -> Result<(Self::Ticket, Fee<<Self as SendMessageFeeProvider>::Balance>), SendError> {
		// The inner payload should not be too large
		let payload = message.command.abi_encode();
		ensure!(
			payload.len() < T::MaxMessagePayloadSize::get() as usize,
			SendError::MessageTooLarge
		);

		// Ensure there is a registered channel we can transmit this message on
		ensure!(T::Channels::contains(&message.channel_id), SendError::InvalidChannel);

		// Generate a unique message id unless one is provided
		let message_id: H256 = message
			.id
			.unwrap_or_else(|| unique((message.channel_id, &message.command)).into());

		let gas_used_at_most = T::GasMeter::maximum_gas_used_at_most(&message.command);
		let fee = Self::calculate_fee(gas_used_at_most, T::PricingParameters::get());

		let queued_message: VersionedQueuedMessage = QueuedMessage {
			id: message_id,
			channel_id: message.channel_id,
			command: message.command.clone(),
		}
		.into();
		// The whole message should not be too large
		let encoded = queued_message.encode().try_into().map_err(|_| SendError::MessageTooLarge)?;

		let ticket = Ticket { message_id, channel_id: message.channel_id, message: encoded };

		Ok((ticket, fee))
	}

fn test_calculate_fees_with_valid_exchange_rate_but_remote_fee_calculated_as_zero() {

		let price_params: PricingParameters<<Test as Config>::Balance> = PricingParameters {

		// Though none zero pricing params the remote fee calculated here is invalid
		// which should be avoided
