### Title
`prunePatch` decrements `bytesProcessed` with the wrong quantity, corrupting the diff-parser byte budget - (File: internal/gitaly/diff/diff.go)

### Summary
`Parser.prunePatch()` in [1](#0-0)  reduces the running `bytesProcessed` counter by `len(parser.currentDiff.Patch)` instead of the quantity that was actually added to it (`parser.currentDiff.byteCount`). This mismatch corrupts the cumulative byte-budget used to enforce `MaxBytes`/`SafeMaxBytes` limits on diff output, analogous to the reported `Goldilend.repay()` bug where the wrong variable (`userLoan.interest` instead of `interest`) was used to update a running accounting total.

### Finding Description
When a diff is parsed, `Parse()` adds `parser.currentDiff.byteCount` to `parser.bytesProcessed`: [2](#0-1) 

`byteCount` is deliberately incremented only for content lines, not for hunk headers (`@@ ... @@`), per the explicit comment "Hunk headers do not count towards limits": [3](#0-2) [4](#0-3) 

However, `diff.Patch` (the raw byte buffer returned to clients and held in memory) accumulates hunk-header bytes too, since `consumeChunkLine` appends to `diff.Patch` for every consumed line, regardless of whether `updateStats` is true. As a result, `len(diff.Patch) >= diff.byteCount` for any diff containing hunk headers.

When `CollapseDiffs` and the safe limits are exceeded, `prunePatch()` is invoked to reverse the previous increment: [1](#0-0) 

It subtracts `len(parser.currentDiff.Patch)` — a value that is systematically larger than what was actually added (`byteCount`) — from `parser.bytesProcessed`. This is the same class of bug as the audited Solidity issue: an accounting variable is decremented using the wrong quantity, rather than the amount that was originally added.

### Impact Explanation
Because `bytesProcessed` is over-decremented every time a diff is pruned, the parser's cumulative byte counter drifts lower than the true amount of patch data it has buffered in memory. Since `EnforceLimits` gates `parser.finished = true` on `parser.bytesProcessed - parser.limits.MaxBytes >= 0` [5](#0-4) , an attacker who can shape a commit/diff (e.g., via a crafted push or a repo they can trigger `CommitDiff`/`RawDiff` RPCs against, through `internal/gitaly/service/diff/commit_diff.go` and `internal/gitaly/diff/diff.go`'s `NewDiffParser`) with many small hunks interleaved with content that trips `CollapseDiffs`/`SafeMaxBytes` repeatedly can cause the tracked `bytesProcessed` to fall increasingly behind the real memory retained in `Diff.Patch` buffers across many files. This weakens the intended memory/byte ceiling meant to bound gitaly's per-request memory usage while serving diff RPCs, contributing to a resource-exhaustion / DoS vector against the diff-serving handler.

### Likelihood Explanation
Triggering the drift only requires an ordinary caller of the diff RPCs (`CommitDiff`, `RawDiff`, `DiffBlobs`, etc., all going through `internal/gitaly/diff/diff.go`) with `CollapseDiffs` enabled and content whose diffs contain hunk headers — a very common and unprivileged shape of Git diff output (any file with more than one hunk). No special access beyond a normal Gitaly RPC call with attacker-influenced diff content is required, so the likelihood of an unprivileged user encountering or exploiting the drift is high, though the magnitude of drift per diff is bounded by the size of hunk headers (typically small, tens of bytes), meaning many diffs/files are needed to produce a meaningful cumulative effect.

### Recommendation
In `prunePatch()`, decrement `bytesProcessed` using the same quantity that was added — `parser.currentDiff.byteCount` — instead of `len(parser.currentDiff.Patch)`:
```go
func (parser *Parser) prunePatch() {
	parser.linesProcessed -= parser.currentDiff.lineCount
	parser.bytesProcessed -= parser.currentDiff.byteCount
	parser.currentDiff.ClearPatch()
}
```
This keeps the increment/decrement symmetric and ensures `bytesProcessed` accurately reflects the tracked byte budget used to bound memory consumption of the diff parser.

### Proof of Concept
Conceptual PoC (unit-test style), analogous to existing tests in [6](#0-5) :
1. Configure a `Parser` with `Limits{CollapseDiffs: true, SafeMaxBytes: N, EnforceLimits: true, MaxBytes: M}`.
2. Feed a diff stream consisting of many files, each with multiple hunk headers (`@@ ... @@`) but content lines kept just below `SafeMaxBytes` so that `prunePatch()` fires repeatedly (`isOverSafeLimits()` true, `lineCount > 0`).
3. After each `Parse()` call that triggers `prunePatch()`, assert `parser.bytesProcessed` against an independently computed expected byte count (sum of `byteCount` actually added, minus `byteCount` actually pruned).
4. Observe that `parser.bytesProcessed` diverges downward (becomes smaller than the true cumulative `byteCount`) proportional to the number of hunk headers pruned, demonstrating that the `MaxBytes` limit can be reached later than intended relative to actual buffered `Patch` memory, i.e., more memory is retained than the configured limit should allow before `parser.finished` is set.

```go
func consumeChunkLine(reader *bufio.Reader, diff *Diff, skipPatch, updateStats bool) error {
	// The code that follows would be much simpler if we used
	// bufio.Reader.ReadBytes, but that allocates an intermediate copy of
	// each line which adds up to a lot of allocations. By using ReadSlice we
	// can copy bytes into currentDiff.Patch without intermediate
	// allocations.
	var byteCount int
	for done := false; !done; {
		line, err := reader.ReadSlice('\n')
		if updateStats && byteCount == 0 && len(line) > 0 {
			if line[0] == '+' {
				diff.LinesAdded++
			} else if line[0] == '-' {
				diff.LinesRemoved++
			}
		}
		byteCount += len(line)

		switch {
		case errors.Is(err, bufio.ErrBufferFull):
			// long line: keep reading
		case err != nil && !errors.Is(err, io.EOF):
			return fmt.Errorf("read chunk line: %w", err)
		default:
			done = true
		}

		if !skipPatch {
			diff.Patch = append(diff.Patch, line...)
		}
	}

	if updateStats {
		diff.byteCount += byteCount
		diff.lineCount++
	}

	return nil
```
