## Finding: Credential Leakage in Logs via Unregistered `FindRemoteRootRef` RPC

### Title
Sensitive Credential Disclosure in Gitaly Logs via `FindRemoteRootRef` Remote URL — (File: `internal/gitaly/service/remote/find_remote_root_ref.go`)

### Summary
Gitaly has a dedicated log-sanitization mechanism, `URLSanitizerHook`, that scrubs embedded basic-auth credentials (`https://user:pass@host/...`) from log fields (`args`, `error`, message) — but only for gRPC methods explicitly registered on an allowlist. `FindRemoteRootRef` accepts a caller-controlled `remote_url` that can embed credentials, is not stripped of userinfo the way `CreateRepositoryFromURL` is, and is **not** included in the allowlist, so credentials embedded in this field can reach logs unsanitized.

### Finding Description
`URLSanitizerHook` only sanitizes log entries whose `grpc.method` field is one of the explicitly registered methods: [1](#0-0) 

The hook itself gates all sanitization behind this allowlist check: [2](#0-1) 

`FindRemoteRootRef` takes a `remote_url` field directly from the request and, unlike `cloneFromURLCommand` (used by `CreateRepositoryFromURL`, which explicitly strips `u.User` and converts credentials into a git `http.extraHeader` before ever touching the URL string), passes the URL string as-is into `remote.inmemory.url` git configuration: [3](#0-2) 

Compare with `CreateRepositoryFromURL`, where userinfo is deliberately stripped before the URL is used anywhere further: [4](#0-3) 

When the underlying `git remote show` subprocess fails or emits diagnostic stderr output (e.g. an unreachable host, TLS failure, or authentication failure containing the URL verbatim), `command.Command.logProcessComplete` logs that stderr content directly as the log message via `logLevel(ctx, c.stderrBuffer.String())`: [5](#0-4) 

Since `FindRemoteRootRef` is absent from the `AddPossibleGrpcMethod` allowlist configured in `serve.go`, log entries produced during this RPC's git subprocess execution are not passed through `sanitizeString`/`sanitizeErrorLog`, so any embedded `user:pass@host` in the URL that appears in git's stderr diagnostics (a well-known git behavior — see the sanitizer's own test fixtures reproducing `fatal: Authentication failed for 'https://foo_the_user:hUntEr1@gitlab.com/foo/bar'`) is written to the Gitaly log verbatim. [6](#0-5) 

Note: I was not able to conclusively confirm within the indexed code exactly where the `grpc.method` field gets attached to the per-request logger used for `logProcessComplete` (the middleware wiring for `requestinfohandler`/logging interceptor that would carry `grpc.method` into `c.logger`'s fields was not found in the indexed subset of `internal/middleware`). This is an assumption based on `methodFromContext` being derived from `requestinfohandler.Extract(ctx)` for metrics purposes in the same file, and the existing pattern (`URLSanitizerHook` design) clearly assumes `grpc.method` is present on relevant log entries elsewhere in the pipeline. If `grpc.method` is not actually attached to command-spawn log entries at all, then *no* RPC's git-subprocess stderr logging is currently sanitized by this hook, which would be an even broader instance of the same bug class (affecting `CreateRepositoryFromURL`, `FetchRemote`, `UpdateRemoteMirror` too, contradicting their explicit registration purpose) — but I could not verify this without further access to the middleware wiring, and I recommend it be checked directly.

### Impact Explanation
An ordinary Gitaly client (any actor with gRPC access, e.g. a GitLab Rails backend acting on behalf of a project, forwarding user-supplied `remote_url` values for mirror/import validation flows that call `FindRemoteRootRef`) can trigger this RPC with a URL containing embedded HTTP basic-auth credentials pointing to a remote git server they control or a failing target. If the resulting git error/stderr diagnostic includes the raw URL (common with libcurl/git http transport errors), those credentials for the *target remote* — which may be a legitimate third-party repository, a GitLab.com personal access token embedded in a mirror URL, or similar — get written into Gitaly's server-side logs, unfiltered. Anyone with log access (ops staff, log aggregation systems, or an attacker who compromises log storage) can recover these credentials and use them to access the remote repository they authenticate.

### Likelihood Explanation
Moderate. Exploitation requires:
1. Ability to invoke `FindRemoteRootRef` with an attacker-influenced `remote_url` (this RPC is typically invoked by GitLab Rails when validating/importing external mirrors, so the URL is often user-supplied indirectly through UI fields like "Mirror repository URL").
2. The underlying git command failing in such a way that stderr echoes back the URL with credentials (well-documented and easily reproducible git behavior).

No privileged access, MITM, or malicious-peer assumption is needed — a normal client-triggered RPC call with a crafted field is sufficient, matching the "crafted RPC field" reachability criterion.

### Recommendation
- Register `FindRemoteRootRef` (and any other RPC that accepts a caller-supplied remote URL that may embed userinfo) with `URLSanitizerHook.AddPossibleGrpcMethod` in `internal/cli/gitaly/serve.go`.
- Alternatively/additionally, strip userinfo from the URL in `findRemoteRootRefCmd` before using it (mirroring `cloneFromURLCommand`'s approach of converting embedded credentials into an `http.extraHeader` instead of leaving them in the URL string), so credentials never appear in any process argument, git config value, or potential error text in the first place.
- Consider making stderr/args sanitization apply universally to all RPCs handling remote URLs, rather than relying on a manually maintained allowlist, to avoid this class of omission recurring as new RPCs are added.

### Proof of Concept
1. Call `FindRemoteRootRef` with `remote_url = "https://attacker_user:attacker_pw@unreachable-or-erroring-host/repo.git"`.
2. The `git remote show inmemory` subprocess fails (e.g., DNS/connection/auth failure), and git's stderr diagnostic includes the full URL with embedded credentials. [7](#0-6) 
3. `logProcessComplete` logs the stderr content as-is at `Warn`/`Error` level because `FindRemoteRootRef` is not in the sanitizer's allowlist. [5](#0-4) 
4. Inspect Gitaly's log output — the `attacker_user:attacker_pw@...` credential pair (or any legitimate credential embedded by a caller, e.g., a mirror's real access token) appears in plaintext.

```go
func (s *server) findRemoteRootRefCmd(ctx context.Context, request *gitalypb.FindRemoteRootRefRequest) (*command.Command, error) {
	remoteURL := request.GetRemoteUrl()
	var config []gitcmd.ConfigPair

	if resolvedAddress := request.GetResolvedAddress(); resolvedAddress != "" {
		modifiedURL, resolveConfig, err := gitcmd.GetURLAndResolveConfig(remoteURL, resolvedAddress)
		if err != nil {
			return nil, structerr.NewInvalidArgument("couldn't get curloptResolve config: %w", err)
		}

		remoteURL = modifiedURL
		config = append(config, resolveConfig...)
	}

	config = append(config, gitcmd.ConfigPair{Key: "remote.inmemory.url", Value: remoteURL})

	if authHeader := request.GetHttpAuthorizationHeader(); authHeader != "" {
		config = append(config, gitcmd.ConfigPair{
			Key:   fmt.Sprintf("http.%s.extraHeader", request.GetRemoteUrl()),
			Value: "Authorization: " + authHeader,
		})
	}
```
