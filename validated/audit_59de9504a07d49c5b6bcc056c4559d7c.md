Audit Report

## Title
Fast-unstake's `force_unstake` path bypasses the pending-offence/slash withdrawal guard added to `withdraw_unbonded` - (File: `substrate/frame/staking-async/src/pallet/impls.rs`)

## Summary
`pallet-staking-async`'s `do_withdraw_unbonded` blocks fund release while offences reported for a prior era are still unprocessed, via `calculate_earliest_withdrawal_era`/`ensure_era_slashes_applied`. `force_unstake`/`kill_stash`, invoked by `pallet-fast-unstake`'s `on_idle`, performs no equivalent check, and `do_slash` silently no-ops if the ledger has already been killed, so a killed-stash's still-queued offence can never be applied.

## Finding Description
`do_withdraw_unbonded` explicitly halts if the previous era's slashes are not yet applied: `Self::ensure_era_slashes_applied(active_era.saturating_sub(1))?;` [1](#0-0) , and further caps withdrawal eligibility to the oldest fully-processed era via `calculate_earliest_withdrawal_era` [2](#0-1) .

`StakingInterface::force_unstake` for `pallet-staking-async` instead calls `Self::force_unstake(RawOrigin::Root.into(), who.clone(), 0)` [3](#0-2) , which dispatches straight into `Self::kill_stash(&stash)?` [4](#0-3) . `kill_stash` calls `StakingLedger::<T>::kill(&stash)` [5](#0-4) , which removes the `Ledger`/`Bonded`/`Payee` entries and releases the staking lock via `asset::kill_stake` [6](#0-5) . None of this path consults `OffenceQueueEras`, `calculate_earliest_withdrawal_era`, or `ensure_era_slashes_applied`.

This matters because `do_slash` (the function that actually applies a deferred/queued slash to a stash) fetches the ledger and returns immediately if it's missing: `Ok(ledger) => ledger, Err(_) => return, // nothing to do.` [7](#0-6) . So if `kill_stash` runs before a queued offence for that stash is computed and applied, the eventual `apply_slash`/`process_offence_queue` call for that stash becomes a silent no-op — the slash is lost, not deferred or retried.

`pallet-fast-unstake`'s `on_idle` reaches `force_unstake` through `unstake_stash` [8](#0-7) , gated only by `check_stash`, which tests `is_exposed_in_era` over `unchecked_eras_to_check` [9](#0-8) . Critically, `unchecked_eras_to_check` is derived from `current_era.saturating_sub(bonding_duration)..=current_era` [10](#0-9) , i.e. it is keyed purely on **era-exposure history** (`ErasStakersPaged`), not on `OffenceQueueEras`/unprocessed-offence state. `is_exposed_in_era` (the underlying check) only iterates `ErasStakersPaged` for that era [11](#0-10)  — exposure data exists for any era the stash was active in, regardless of whether an offence for that era has been reported/queued/computed. This is a materially different check than the offence-queue guard `pr_9079` added specifically to `withdraw_unbonded`.

However, in practice, if the offender was actually validating/nominating in era `e` (which is required for an offence to exist against them at all), `is_exposed_in_era(stash, e)` returns `true` for that era as long as `e` is still within the `bonding_duration` window scanned by fast-unstake, and `check_stash` correctly slashes the deposit and rejects the fast-unstake request. The exposure record for an era persists independent of whether the offence for that era has been *computed into a slash* yet — so the exposure-based check in fast-unstake and the offence-queue-based check in `withdraw_unbonded` are different mechanisms but target overlapping windows (both keyed off `BondingDuration`). I was not able to fully verify, within the scope of this investigation, a concrete scenario where an era is *outside* fast-unstake's `unchecked_eras_to_check` window (already fully scanned as "not exposed") while `OffenceQueueEras` still holds an unresolved offence for that stash from a still-in-window era — the `SlashDeferDuration`/`BondingDuration` relationship in `pallet-staking-async` (`OffenceQueueEras` processing happens well within `BondingDuration` per the `calculate_earliest_withdrawal_era` comment: "this situation is extremely unlikely, since offences have `SlashDeferDuration` eras to be processed") makes it plausible but not conclusively demonstrated that fast-unstake's exposure-window check and the offence-queue-processing lag can actually diverge in the way the claim requires.

## Impact Explanation
If the divergence window is real, `force_unstake` killing the ledger while an offence remains queued causes `do_slash` to silently no-op on that stash, permanently losing the intended slash — a fund-conservation/slashing-guarantee violation (an attacker escapes a legitimate penalty, at the cost of `T::Currency::slash_reserved` on future era pot distributions and honest reporters' expected rewards). This is a real class of bug, but the claim itself concedes uncertainty about whether the race window is actually reachable, since fast-unstake's exposure check and the offence-queue guard are keyed on overlapping but not identical windows (`BondingDuration` vs `SlashDeferDuration`-bounded processing).

## Likelihood Explanation
The claim does not establish a concrete, reachable sequence where an offence remains unresolved in `OffenceQueueEras` for an era that fast-unstake's `check_stash` has already fully scanned as "not exposed" (and thus considers clear). Given the `calculate_earliest_withdrawal_era` code comment explicitly stating offence-queue backlog beyond `SlashDeferDuration` eras is "extremely unlikely" and only occurs under offence-processing spam, and no PoC or test demonstrates the fast-unstake race concretely, likelihood of this specific bypass firing under normal permissionless usage is not established.

## Recommendation
This finding is speculative and unconfirmed. If pursued further, the reviewer should construct a concrete repro test in `substrate/frame/staking-async/src/tests/` combined with `pallet-fast-unstake`'s mock runtime showing: (1) a stash exits fast-unstake's `unchecked_eras_to_check` window as "not exposed," (2) an offence for that stash remains in `OffenceQueueEras` unresolved at that point, and (3) `force_unstake` kills the ledger before the offence is processed, causing `do_slash`'s early return to permanently drop the slash. Absent that reproduction, no code change should be made based on this claim alone.

## Proof of Concept
Not established. The claim's proof-of-concept section is explicitly conceptual/theoretical and the investigation could not confirm, with available evidence, that fast-unstake's era-exposure scan and `pallet-staking-async`'s offence-queue processing can diverge such that `force_unstake` executes while a real offence is still unresolved for a scanned-clear stash.

	/// Calculate the earliest era that withdrawals are allowed for, considering:
	/// - The current active era
	/// - Any unprocessed offences in the queue
	fn calculate_earliest_withdrawal_era(active_era: EraIndex) -> EraIndex {
		// get lowest era for which all offences are processed and withdrawals can be allowed.
		let earliest_unlock_era_by_offence_queue = OffenceQueueEras::<T>::get()
			.as_ref()
			.and_then(|eras| eras.first())
			.copied()
			// if nothing in queue, use the active era.
			.unwrap_or(active_era)
			// above returns earliest era for which offences are NOT processed yet, so we subtract
			// one from it which gives us the oldest era for which all offences are processed.
			.saturating_sub(1)
			// Unlock chunks are keyed by the era they were initiated plus their unbond duration.
			// We use full BondingDuration (validator duration) here because:
			// - For validators: this is their actual unbond duration
			// - For nominators: when slashable, they use full duration; when not slashable, their
			//   chunks already have shorter unlock eras (set during unbond), so this calculation
			//   still correctly allows their withdrawals.
			.saturating_add(T::BondingDuration::get());

		// If there are unprocessed offences older than the active era, withdrawals are only
		// allowed up to the last era for which offences have been processed.
		// Note: This situation is extremely unlikely, since offences have `SlashDeferDuration` eras
		// to be processed. If it ever occurs, it likely indicates offence spam and that we're
		// struggling to keep up with processing.
		active_era.min(earliest_unlock_era_by_offence_queue)
	}

	pub(crate) fn kill(stash: &T::AccountId) -> DispatchResult {
		let controller = <Bonded<T>>::get(stash).ok_or(Error::<T>::NotStash)?;

		<Ledger<T>>::get(&controller).ok_or(Error::<T>::NotController).map(|ledger| {
			Ledger::<T>::remove(controller);
			<Bonded<T>>::remove(&stash);
			<Payee<T>>::remove(&stash);

			// kill virtual staker if it exists.
			if <VirtualStakers<T>>::take(&ledger.stash).is_none() {
				// if not virtual staker, clear locks.
				asset::kill_stake::<T>(&ledger.stash)?;
			}
			Pallet::<T>::deposit_event(crate::Event::<T>::StakerRemoved {
				stash: ledger.stash.clone(),
			});
			Ok(())
		})?
	}
