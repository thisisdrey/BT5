### Title
Unvalidated attacker-controlled array-length in `ValidateMultiSign`/legacy `BatchValidateSign` precompile causes uncaught `OutOfMemoryError` and node crash - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The CVE-2019-20202 bug class is "an internal size/allocation-state value is trusted without validation, driving a memory operation that the code assumes is safe, resulting in a crash." The closest reachable analog in java-tron is in the `ValidateMultiSign` and `BatchValidateSign` TVM precompiled contracts, where a fully attacker-controlled 256-bit calldata word is converted to an `int` and used directly as an array-allocation size with no upper bound before the guard checks run, and the resulting `OutOfMemoryError` is an `Error`, not an `Exception`, so it is not caught anywhere in the VM's execution loop.

### Finding Description
`extractBytesArray` reads the array length straight from the caller-supplied `DataWord[]` and immediately allocates a `byte[][]` of that size: [1](#0-0) 

`extractSigArray` has the identical pattern: [2](#0-1) 

In `ValidateMultiSign.execute`, when `VMConfig.allowTvmSelfdestructRestriction()` is not active, `extractBytesArray` is invoked with the length taken from `words[3].intValueSafe()`-derived offset with **no bound check at all** before the allocation happens; the `MAX_SIZE` check only runs afterwards, on the already-allocated array: [3](#0-2) 

The same conditional-guard pattern exists in `BatchValidateSign.doExecute`: the `sigArraySize`/`addrArraySize` bound check is only performed when `allowTvmSelfdestructRestriction()` is enabled; otherwise `extractBytesArray`/`extractBytes32Array` run unguarded on attacker-supplied lengths: [4](#0-3) 

Because the length comes straight from calldata (`int len = words[offset].intValueSafe();`), a caller can set this word to a very large 32-bit value, causing `new byte[len][]` to request gigabytes of heap for object references alone. This throws `java.lang.OutOfMemoryError`, which is a `Error`, not a `RuntimeException`. The top-level VM opcode dispatch loop only catches `JVMStackOverFlowException`, `OutOfTimeException`, `RuntimeException`, and `StackOverflowError` — it does **not** catch generic `Error`/`OutOfMemoryError`: [5](#0-4) 

This mirrors the ezXML root cause conceptually: a size/length value that has not been validated against real bounds is trusted to drive a memory-allocation/operation, and the resulting failure (an invalid `realloc` there, an uncontrolled huge allocation here) is not handled by the surrounding code, producing a crash instead of a graceful error.

### Impact Explanation
An `OutOfMemoryError` thrown mid-transaction-execution and left uncaught by `VM.play()` propagates up through the actuator/runtime execution path. Depending on where (if anywhere) it is eventually caught higher in the call stack, this can either abort just the current transaction thread inconsistently or destabilize the whole node process (since `OutOfMemoryError` can leave the JVM heap in a degraded state and other threads may also start failing to allocate). This is reachable by any account issuing a normal contract call — no special privilege is required — making it a low-cost, broadcastable full-node availability/DoS vector.

### Likelihood Explanation
Both `ValidateMultiSign` and `BatchValidateSign` are ordinary precompiled contracts invokable via a plain `CALL`/`STATICCALL` from any smart contract by any unprivileged sender, provided the transaction supplies enough energy for the (attacker-chosen) `data.length`-based energy formula. The vulnerable path is gated by `VMConfig.allowTvmSelfdestructRestriction()`: on networks/forks where this flag has not yet been activated (or was never enabled), the unguarded legacy `extractBytesArray`/`extractSigArray` call path is fully reachable with attacker-controlled length. This should be confirmed against the current mainnet hard-fork configuration before treating it as immediately exploitable on production mainnet, since if the flag is already permanently enabled network-wide, the size check runs before the allocation and this specific path is closed.

### Recommendation
Validate array/list lengths derived from `DataWord.intValueSafe()` against a hard maximum (e.g., `MAX_SIZE`) and against the actual remaining `data`/`words` length **before** allocating `byte[len][]` in `extractBytesArray` and `extractSigArray`, independent of the `allowTvmSelfdestructRestriction` flag, so the bound check is unconditional rather than feature-gated. Additionally, broaden the top-level VM exception handling in `VM.java` to catch `OutOfMemoryError` (or wrap precompile execution with a resource-bounded allocation check) so that a single malicious transaction cannot escalate a bounded resource-exhaustion condition into a JVM-wide `Error`.

### Proof of Concept
1. Craft ABI-encoded calldata for `validatemultisign(address,uint256,bytes32,bytes[])` where the dynamic `bytes[]` "length" header word (at the offset pointed to by the 4th static word) is set to a very large value (e.g., `0x7FFFFFFF`), while leaving the actual bytes payload short/absent.
2. Deploy/call a contract that performs `CALL` to the `ValidateMultiSign` precompiled contract address with this calldata on a node/network where `allowTvmSelfdestructRestriction` is not enabled.
3. Execution reaches [6](#0-5)  and calls `extractBytesArray`, which executes `new byte[len][]` with `len ≈ 0x7FFFFFFF`, throwing `OutOfMemoryError`.
4. The error is not caught by `VM.play()`'s catch block [5](#0-4) , propagating uncaught and destabilizing/crashing the transaction-processing thread.

Note: I was not able to independently confirm from the indexed code whether `allowTvmSelfdestructRestriction` is currently force-enabled on java-tron mainnet (this would close the unguarded path). If confirmation of the current hard-fork activation state is needed, a Devin session with full repo/config access should verify `ForkController`/`ForkBlockVersionConsts` for this flag before treating this as exploitable on mainnet today.
