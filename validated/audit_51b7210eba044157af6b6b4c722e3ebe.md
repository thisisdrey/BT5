Audit Report

## Title
Permanent per-channel stall in Snowbridge V1 Inbound Queue when downstream XCM send fails — no bypass, funds/messages permanently blocked - (File: `bridges/snowbridge/pallets/inbound-queue/src/lib.rs`)

## Summary
`Pallet::submit` in the Snowbridge V1 inbound-queue pallet enforces a strictly sequential per-channel nonce via `Nonce<T>::try_mutate` and only reaches `send_xcm` after the nonce is bumped, all inside the same call. [1](#0-0)  Because every `#[pallet::call]` dispatchable is automatically wrapped in `frame_support::storage::with_storage_layer`, any `Err` returned by the call — including the `Error::<T>::Send` mapped from `XcmpSendError` — rolls back all storage writes made earlier in the same call, including the nonce increment. [2](#0-1) [3](#0-2)  Since `Nonce<T>` requires strict `+1` sequencing with no alternate path, a deterministic `send_xcm` failure for one message (e.g. `XcmpSendError::ExceedsMaxMessageSize`) permanently blocks that nonce and, transitively, every subsequent nonce on that channel via `Error::<T>::InvalidNonce`.

## Finding Description
The `submit` extrinsic performs nonce validation, fee burn, and `send_xcm` dispatch in one atomic scope: [4](#0-3)  `send_xcm` maps `XcmpSendError` variants (`NotApplicable`, `Unroutable`, `Transport`, `DestinationUnsupported`, `ExceedsMaxMessageSize`, `MissingArgument`, `Fees`) into a hard `Error::<T>::Send`. [5](#0-4) [6](#0-5)  This confirms the reported mechanism is real: because Substrate's pallet macro wraps every call body in `with_storage_layer` (a `with_transaction` that commits on `Ok` and rolls back on `Err`), the nonce bump at lines 257-267 is undone whenever the later `send_xcm` call fails, exactly as the claim describes. I verified this generic rollback behavior directly in `substrate/frame/support/src/storage/transactional.rs` and the pallet macro expansion in `substrate/frame/support/procedural/src/pallet/expand/call.rs`.

The V1 pallet's `Nonce<T>` storage map requires exact `+1` sequencing with no skip mechanism [7](#0-6) , so a permanently-failing `send_xcm` condition for one message (deterministic causes like `ExceedsMaxMessageSize`, as opposed to transient network transport errors that could succeed on retry) blocks that nonce forever, and `InvalidNonce` then rejects every later, otherwise-valid nonce for the same channel indefinitely.

By contrast, the V2 inbound-queue pallet was redesigned to avoid exactly this failure mode: it tracks processed nonces with a `SparseBitmapImpl` (`NonceBitmap`) rather than a strictly sequential counter, so nonces are order-independent and one message's permanent failure does not block delivery of other, unrelated nonces on the same channel. [8](#0-7) [9](#0-8)  This corroborates that the sequential-nonce design in V1 is the specific root cause, and it was a known enough limitation that the newer pallet does not replicate it. A related prdoc entry (`prdoc/stable2503-4/pr_8240.prdoc`) documents "a minor change to when the nonce is set in the Inbound Queue V2" as part of "Snowbridge V2 Audit Fixes," further suggesting this nonce/send-ordering interaction was already a known area of audit concern for the Snowbridge pallets.

## Impact Explanation
This matches the allowed impact "public underpriced work that... stalls bridge processing" and "permanent... bridge-state lock": a deterministic `send_xcm` failure (not requiring any malicious or privileged actor) permanently halts a specific channel's message delivery in the V1 inbound queue, since the strictly sequential nonce can never advance past the stuck message and no governance/backfill/skip mechanism exists in this pallet.

## Likelihood Explanation
`submit` is a permissionless, signed-origin extrinsic that any relayer can call, and the specific trigger condition (e.g., a message whose XCM payload size exceeds the destination channel's configured limit, yielding a deterministic `ExceedsMaxMessageSize`) is reachable purely from externally-controlled Ethereum event content translated via `MessageConverter`, without requiring any privileged or malicious party. Transient causes (e.g., temporary `Transport`/`Unroutable` congestion) are more likely to self-resolve on retry and would not by themselves constitute a *permanent* lock, but deterministic, payload-dependent failure modes do produce the permanent stall described.

## Recommendation
Decouple nonce commitment from delivery success — e.g., adopt the V2 pallet's non-sequential nonce tracking (`SparseBitmapImpl`) so a single message's send failure cannot block unrelated nonces, or route delivery through `pallet-message-queue` so that permanent vs. transient failures are distinguished and only the failing message is dropped/retried rather than the whole channel being frozen.

## Proof of Concept
Using the existing pallet test harness (`bridges/snowbridge/pallets/inbound-queue/src/mock.rs`, `test.rs`): configure a mock `XcmSender` that deterministically returns `XcmpSendError::ExceedsMaxMessageSize` for a given `para_id`; submit a valid event for nonce `N+1` on that channel and observe the call fails with `Error::<T>::Send(SendError::ExceedsMaxMessageSize)` while `Nonce::<T>::get(channel_id)` remains at `N`; submit a different valid event for nonce `N+2` and observe it is rejected with `Error::<T>::InvalidNonce`, confirming the channel is permanently stalled.

pub fn with_storage_layer<T, E, F>(f: F) -> Result<T, E>
where
	E: From<DispatchError>,
	F: FnOnce() -> Result<T, E>,
{
	with_transaction(|| {
		let r = f();
		if r.is_ok() {
			TransactionOutcome::Commit(r)
		} else {
			TransactionOutcome::Rollback(r)
		}
	})
}

	impl<T: Config> Pallet<T> {
		pub fn process_message(relayer: T::AccountId, message: Message) -> DispatchResult {
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == message.gateway, Error::<T>::InvalidGateway);

			let (nonce, relayer_fee) = (message.nonce, message.relayer_fee);

			// Verify the message has not been processed
			ensure!(!Nonce::<T>::get(nonce), Error::<T>::InvalidNonce);

			// Mark message as received
			Nonce::<T>::set(nonce);

			let message_id = T::MessageProcessor::process_message(relayer.clone(), message)
				.map_err(|e| match e {
					MessageProcessorError::ProcessMessage(e) => e,
					MessageProcessorError::ConvertMessage(e) => Error::<T>::from(e).into(),
					MessageProcessorError::SendMessage(e) => Error::<T>::from(e).into(),
				})?;

			// Pay relayer reward
			let tip = Tips::<T>::take(nonce).unwrap_or_default();
			let total_tip = relayer_fee.saturating_add(tip);
			if total_tip > 0 {
				T::RewardPayment::register_reward(&relayer, T::DefaultRewardKind::get(), total_tip);
			}

			// Emit event with the message_id
			Self::deposit_event(Event::MessageReceived { nonce, message_id });

			Ok(())
		}
