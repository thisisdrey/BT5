### Title
`VesperGateway.deposit` pulls `amount_` of underlying without a balance-delta check, so 1–2 wei-short transfers (e.g. stETH for vaSTETH collateral) make `vToken_.deposit(amount_)` revert - (File: contracts/VesperGateway.sol)

### Summary
`VesperGateway.deposit` performs `_underlying.safeTransferFrom(_msgSender, address(this), amount_)` and then calls `vToken_.deposit(amount_)` using the *requested* amount rather than the *received* amount. For rebasing/share-based tokens such as stETH, the recipient can receive 1–2 wei less than `amount_`, causing the subsequent Vesper pool deposit to revert on insufficient balance. Metronome's core `DepositToken.deposit` already defends against this with a treasury balance-delta measurement, but the Vesper gateway path reintroduces the same bug class one level up.

### Finding Description
In `VesperGateway.deposit` (contracts/VesperGateway.sol:44-65):

```solidity
IERC20 _underlying = IERC20(vToken_.token());
_underlying.safeTransferFrom(_msgSender, address(this), amount_);

_underlying.safeApprove(address(vToken_), 0);
_underlying.safeApprove(address(vToken_), amount_);
uint256 _balanceBefore = vToken_.balanceOf(address(this));
vToken_.deposit(amount_);   // uses requested amount_, not received
```

- Step 1 trusts that `amount_` tokens arrived. With stETH (the underlying of the deployed vaSTETH collateral, see `deploy/scripts/mainnet/pool1/24_vasteth_deposit_token.ts`), `transferFrom` internally converts the amount to shares with floor rounding, so the gateway can receive `amount_ - 1` or `amount_ - 2` wei (lidofinance/lido-dao#442).
- Step 2 then calls `vToken_.deposit(amount_)`, which pulls `amount_` of stETH from the gateway via `transferFrom`. The gateway only holds `amount_ - 1`, so the call reverts.
- Contrast with `DepositToken.deposit` (contracts/DepositToken.sol:225-227), which correctly rewrites `amount_` to `balanceOf(treasury) - balanceBefore`, and `SmartFarmingManager._safeTransferFrom` (contracts/SmartFarmingManager.sol:257-261), which also returns the actual delta. Only `VesperGateway.deposit` skips this pattern.

Note the gateway *does* use a balance delta for the vToken minted in step 2 (`_vTokenAmount`), so the msdToken minting downstream is safe — the break is between steps 1 and 2.

### Impact Explanation
Denial of service on the `VesperGateway.deposit` entry point for any vToken whose underlying rounds down on transfer (stETH/vaSTETH on mainnet). Every call where stETH delivers fewer wei than requested reverts, so users cannot onboard that collateral through the gateway. Because `deposit` has no `nonReentrant`/state changes before the revert, no funds are lost, but the affected collateral type is unusable via the intended UX path. Funds are not permanently frozen: a user can work around it by depositing stETH to the vToken directly or by pre-seeding the gateway with dust, so impact is limited to a temporary/conditional DoS rather than theft.

### Likelihood Explanation
- Reachable by any unprivileged EOA: `deposit(pool_, vToken_, amount_)` is a public function gated only by `isPoolRegistered`.
- Requires the pool to have a DepositToken whose underlying is a stETH-like token. vaSTETH is a configured collateral in the deploy scripts, and its `vToken_.token()` is stETH, which exhibits this rounding on roughly most transfers (probability depends on share price vs. pooled ETH ratio; historically frequent).
- Whether it reverts on *every* call or probabilistically depends on the stETH share rate; the failure is deterministic once `getPooledEthByShares(ethToShares(amount)) < amount`.
- No moderator, governor, or keeper involvement needed; modifiers (`SynthContext`, registration check) do not prevent it.

### Recommendation
Apply the same balance-delta (FoT) pattern used in `DepositToken.deposit` to the underlying pull in `VesperGateway.deposit`:

```solidity
uint256 _underlyingBefore = _underlying.balanceOf(address(this));
_underlying.safeTransferFrom(_msgSender, address(this), amount_);
uint256 _received = _underlying.balanceOf(address(this)) - _underlyingBefore;

_underlying.safeApprove(address(vToken_), 0);
_underlying.safeApprove(address(vToken_), _received);
uint256 _balanceBefore = vToken_.balanceOf(address(this));
vToken_.deposit(_received);
```

### Proof of Concept
Hardhat mainnet-fork sketch (requires real stETH/vaSTETH addresses):

```ts
it('reverts when stETH transfer delivers 1 wei less', async () => {
  const stEth = await ethers.getContractAt('IERC20', STETH);
  const vaSteth = await ethers.getContractAt('IVPool', VASTETH);
  const gateway = await ethers.getContractAt('VesperGateway', GATEWAY);
  const pool = await ethers.getContractAt('IPool', POOL1);

  const amount = parseEther('10');
  await stEth.connect(user).approve(gateway.address, amount);

  // With stETH, balanceOf(gateway) increases by amount or amount-1.
  // Pick an amount where floor rounding shortchanges the receiver:
  // received = stEth.getPooledEthByShares(stEth.getSharesByPooledEth(amount))
  const shares = await stEth.getSharesByPooledEth(amount);
  const received = await stEth.getPooledEthByShares(shares);
  expect(received).to.be.lt(amount); // amount-1

  await expect(
    gateway.connect(user).deposit(pool.address, vaSteth.address, amount)
  ).to.be.reverted; // vToken.deposit(amount) exceeds gateway's stETH balance
});
```

The test can be made deterministic by mocking stETH or by scanning `amount` values until `getPooledEthByShares(getSharesByPooledEth(amount)) < amount`, which occurs for most amounts on mainnet.
