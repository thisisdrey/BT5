### Title
Unauthenticated forgery of `BlockValidateResponse` via the signer's `/proposal_response` event-receiver port - ([File: libsigner/src/events.rs])

### Summary
The signer's HTTP event listener (`SignerEventReceiver::next_event` in `libsigner/src/events.rs`) accepts any POST to `/proposal_response` from any TCP peer able to reach the bound port and deserializes the body directly into a `BlockValidateResponse`, which `TryFrom<BlockValidateResponse> for SignerEvent<T>` forwards verbatim into the runloop's input channel with no signature, secret, or cross-check against a validation request the node actually issued. There is no authentication mechanism in `libsigner` for this path; the `auth_password`/`auth_token` pair documented in `docs/signing.md` secures the signer→node RPC direction, not this node→signer push endpoint.

### Finding Description
The claimed equality — "the `BlockValidateResponse` the runloop consumes == the response the node's actual validation logic produced" — is broken. `next_event` routes any POST to `/proposal_response` to `process_event::<T, BlockValidateResponse>` [5](#0-4) , which reads the raw body, JSON-deserializes it into `BlockValidateResponse`, and calls `.try_into()` with no other validation [6](#0-5) . `TryFrom<BlockValidateResponse> for SignerEvent<T>` performs zero cross-checking and wraps the attacker-supplied struct verbatim: `Ok(SignerEvent::BlockValidationResponse(block_validate_response))` [3](#0-2) . This is then handed to `forward_event`, which sends it into the channel consumed by the signer runloop [7](#0-6) . Nothing in `bind`/`next_event` checks a peer address, header, token, or any correlation ID tying the response to a proposal the node's validation logic actually processed — `bind` merely opens a plain `tiny_http::HttpServer` [8](#0-7) . On the legitimate node side, `dispatch_to_observer` in `stacks-node/src/event_dispatcher.rs` sends the payload with only URL/bytes/timeout — no auth header is attached to outbound event-observer POSTs [4](#0-3) , confirming the configured `auth_token`/`auth_password` pairing is for the separate signer→node RPC channel (documented in `docs/signing.md`), not for authenticating inbound pushes to the signer's event port. Any TCP peer that can reach the bound `endpoint` (e.g., `0.0.0.0:30000` per the sample configs) can therefore inject an arbitrary `BlockValidateResponse` claiming any `signer_sighash`/validity outcome that was never produced by the node's actual block-validation logic.

### Impact Explanation
An attacker able to connect to the signer's event-receiver port can inject a forged `BlockValidateResponse` — e.g., claiming a block/sighash as `Ok`/valid or `Reject`/invalid arbitrarily — directly into the signer runloop's decision-input stream, once per TCP POST, repeatably. This is unauthenticated write of forged data into the signer's internal state/decision pipeline, matching the "Critical — unauthenticated ... write to state" category. Note: the runloop's subsequent handling/decision logic based on this forged input is explicitly out of scope per the prompt; only the forged-data-delivery vulnerability at the transport/deserialization layer is being assessed here.

### Likelihood Explanation
Preconditions are minimal: the attacker needs only a direct TCP connection to the signer's bound event-receiver address (per sample configs, often bound to `0.0.0.0:<port>`, i.e., not restricted to loopback by anything in the code) and the ability to issue an HTTP POST. No secret, key, or privileged role is required anywhere in the `libsigner` event-receiver code path. The attack is trivially repeatable at negligible cost.

### Recommendation
Add authentication/authorization to the signer's event-receiver HTTP endpoints (e.g., require and verify a shared secret/token header on inbound requests in `SignerEventReceiver::next_event`, mirroring the `auth_token`/`auth_password` mechanism already used for the node-RPC direction), and/or bind the listener to loopback-only by default with an explicit opt-in warning for non-loopback binds, and where feasible bind a correlation identifier between an issued validation request and its response.

### Proof of Concept
Rust test outline using `tiny_http`/`SignerEventReceiver`:
1. Instantiate `SignerEventReceiver::<SomeT>::new(false)`, call `bind()` on `127.0.0.1:0` (or a fixed test port), and `add_consumer` with a channel.
2. Spawn a thread running `next_event()` (or `main_loop`).
3. From a plain `std::net::TcpStream::connect` (simulating an arbitrary remote peer, not the node), send a raw HTTP POST to `/proposal_response` with `Content-Type: application/json` and a body containing a crafted, valid `BlockValidateResponse` JSON (e.g., an `Ok`/accepted variant referencing an attacker-chosen `signer_sighash` that was never proposed).
4. Assert that the channel receives `SignerEvent::BlockValidationResponse(resp)` where `resp` matches the attacker-supplied fields exactly, proving injection succeeded with no authentication check performed anywhere in `libsigner/src/events.rs`.

fn process_event<T, E>(mut request: HttpRequest) -> Result<SignerEvent<T>, EventError>
where
    T: SignerEventTrait,
    E: serde::de::DeserializeOwned + TryInto<SignerEvent<T>, Error = EventError>,
{
    let mut body = String::new();

    if let Err(e) = request.as_reader().read_to_string(&mut body) {
        error!("Failed to read body: {:?}", &e);
        ack_dispatcher(request);
        return Err(EventError::MalformedRequest(format!(
            "Failed to read body: {:?}",
            e
        )));
    }
    // Regardless of whether we successfully deserialize, we should ack the dispatcher so they don't keep resending it
    ack_dispatcher(request);
    let json_event: E = serde_json::from_slice(body.as_bytes())
        .map_err(|e| EventError::Deserialize(format!("Could not decode body to JSON: {:?}", e)))?;

    let signer_event: SignerEvent<T> = json_event.try_into()?;

    Ok(signer_event)
}
