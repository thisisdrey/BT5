## Analysis

I traced the M02 (ERC20 allowance front-running) bug class to its closest analog in this repository: `TrustedSpender.sol`, which implements a custom ERC20/ERC721 allowance-and-delegate spending model for Safe accounts. [1](#0-0) 

`setAllowance` fully overwrites `_allowances[token][from][to]` in a single write, exactly the "full replace" pattern that causes the classic ERC20 `approve` race: if the Safe (or guardian) tries to *reduce* a delegate's spend cap (e.g., after detecting suspicious activity) rather than remove the delegate outright, a malicious/compromised delegate watching the mempool can front-run the `setAllowance` reduction with `executeTransfer` against the old (larger) amount, then also spend against the newly-set (smaller) amount once it lands — extracting `old + new` instead of being capped at the intended `new` value. [2](#0-1) 

The spec itself documents this as "fully overwrites any existing allowance," confirming the design intentionally lacks any zero-then-set or increase/decrease-style mitigation.

### Title
Allowance front-running in `TrustedSpender.setAllowance` lets a delegate double-spend past the Safe's intended cap - (File: contracts/TrustedSpender.sol)

### Summary
`TrustedSpender.setAllowance` unconditionally overwrites the stored `(token, from, to)` allowance amount rather than incrementing/decrementing it. This reproduces the well-known ERC20 `approve` front-running race: when a Safe or guardian reduces a delegate's spending cap, a delegate that already knows the reduction is pending can race to spend the full old allowance before the reduction lands, then spend up to the newly-set allowance on top of that.

### Finding Description
`setAllowance` is callable by the Safe itself or a guardian and always performs a full overwrite: [3](#0-2) 

`executeTransfer` is callable by any registered delegate and decrements the stored allowance (unless it is `type(uint208).max`): [4](#0-3) 

Because there is no "zero out first" step, no nonce/expected-old-value check, and no atomic decrement-only path for reductions, a delegate can:
1. Observe a Safe's pending `setAllowance(token, from, to, newAmount, ...)` transaction in the mempool that lowers its current allowance from `oldAmount` to `newAmount` (`newAmount < oldAmount`).
2. Front-run it with `executeTransfer(token, from, to, oldAmount)`, draining the full old allowance before the reduction is applied.
3. Let the Safe's `setAllowance` transaction land, setting the allowance to `newAmount`.
4. Call `executeTransfer(token, from, to, newAmount)` again, extracting an additional `newAmount`.

Total extracted: `oldAmount + newAmount`, exceeding both the Safe's final intended cap (`newAmount`) and matching the classic ERC20 approve race pattern cited in the external report.

### Impact Explanation
This breaks the "route allowances ... must never let [a party] spend [beyond its authorized amount] from another Safe" invariant for smart-account flows. The delegate is a party the Safe intentionally scoped to a bounded, revocable spending limit specifically so it *cannot* pull more than that limit out of the Safe's USDC/token balance. The race allows a delegate — particularly one that is being throttled or partially de-authorized after suspicious behavior — to extract materially more of the Safe's funds than the Safe's final on-chain state authorizes, resulting in direct theft/diversion of Safe-held USDC or other approved tokens.

### Likelihood Explanation
Exploitation requires the delegate to be actively monitoring the mempool for a `setAllowance` reduction targeting its own route, which is a realistic scenario precisely in the case this mechanism exists to protect against: revoking/throttling a delegate suspected of misbehavior. Since `setAllowance` and `executeTransfer` are both plain, non-private-mempool transactions with no commit-reveal or two-step reduction protection, the race is straightforward for any delegate with transaction-ordering capability (e.g., via a bundler, private RPC, or simple gas-price bump).

### Recommendation
Add an allowance-reduction-safe mechanism analogous to OpenZeppelin's `increaseAllowance`/`decreaseAllowance`, or require `setAllowance` reductions to be preceded by a zero-out step observed on-chain, or add an "expected current amount" parameter (compare-and-swap) to `setAllowance` so reductions can only be applied if the on-chain amount still matches what the Safe/guardian expected when submitting the transaction. Alternatively, favor `removeDelegate` (which fully clears authorization) over `setAllowance` for any urgent throttling of a suspected-compromised delegate, and document this front-running risk in `specs/trusted-spender.md`.

// Attacker (delegate) front-runs:
vm.prank(delegate1);
spender.executeTransfer(usdc, safe, recipient, 1000e6); // drains old allowance fully

// Safe's tx lands, setting allowance to 100e6

// Attacker spends again:
vm.prank(delegate1);
spender.executeTransfer(usdc, safe, recipient, 100e6); // extra 100e6

// Total extracted: 1100e6 instead of the Safe's intended cap of 100e6

  /// @inheritdoc ITrustedSpender
  function setAllowance(
    address token,
    address from,
    address to,
    uint208 amount,
    uint48 validUntil
  ) external safeOrGuardian(from) {
    require(token != address(0) && from != address(0) && to != address(0), ZeroAddress());
    require(validUntil > block.timestamp, InvalidAllowanceDeadline());

    _allowances[token][from][to] = Allowance({amount: amount, validUntil: validUntil});
    emit AllowanceSet(token, from, to, amount, validUntil);
  }

  /// @inheritdoc ITrustedSpender
  function executeTransfer(address token, address from, address to, uint256 amount) external whenNotPaused {
    // Verify sender is a delegate
    require(delegates[from][msg.sender], NotADelegate());

    // Check allowance exists, is sufficient, and has not expired
    Allowance storage allowance = _allowances[token][from][to];
    require(allowance.amount >= amount, InsufficientAllowance());
    require(block.timestamp <= allowance.validUntil, AllowanceExpired());

    // Update allowance if not infinite
    if (allowance.amount != type(uint208).max) {
      allowance.amount -= uint208(amount);
    }

    IERC20(token).safeTransferFrom(from, to, amount);
  }

  function test_ExecuteTransfer(uint48 validUntil, uint208 transferAmount) public {
    validUntil = uint48(bound(validUntil, timeNow + 1, type(uint48).max));
    transferAmount = uint208(bound(transferAmount, 1, 1000e6));

    vm.prank(safeAccount);
    spender.addDelegate(safeAccount, delegate1);

    vm.prank(safeAccount);
    spender.setAllowance(address(usdc), safeAccount, recipient, 1000e6, validUntil);

    uint256 recipientBalanceBefore = usdc.balanceOf(recipient);
    uint256 safeBalanceBefore = usdc.balanceOf(safeAccount);

    vm.prank(delegate1);
    spender.executeTransfer(address(usdc), safeAccount, recipient, transferAmount);

    assertEq(usdc.balanceOf(recipient), recipientBalanceBefore + transferAmount);
    assertEq(usdc.balanceOf(safeAccount), safeBalanceBefore - transferAmount);

    (uint256 remaining, ) = spender.getAllowance(address(usdc), safeAccount, recipient);
    assertEq(remaining, 1000e6 - transferAmount);
  }
