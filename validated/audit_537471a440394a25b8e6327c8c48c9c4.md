### Title
Oracle-update sandwich mints unbacked synthetic tokens via `Pool.swap` - (contracts/Pool.sol)

### Summary
`Pool.swap` converts one registered synthetic token into another at the current `MasterOracle` quote without using an AMM reserve, slippage bound, cooldown, or post-update price consistency check. Because `swap` burns the input token and mints the output token at the instantaneous oracle quote, an unprivileged borrower can sandwich a predictable oracle update between two swaps and leave the protocol with synthetic supply that is not backed by corresponding debt or collateral. The vulnerable conversion path is `Pool.swap`, which calls `quoteSwapOut`, while `quoteSwapOut` prices `amountIn_` directly through `masterOracle().quote`. [1](#0-0) [2](#0-1) 

### Finding Description
`DebtToken.issue` permits a collateralized account to mint synthetic tokens up to the USD issuable limit reported by `Pool.debtPositionOf`. [3](#0-2) 

`Pool.debtPositionOf` derives debt and collateral values independently from current oracle quotes, while `Pool.swap` performs an immediate mint-and-burn conversion using the same oracle but does not require the caller to maintain a position or lock the minted proceeds. [4](#0-3) [5](#0-4) 

Concretely, if a pending public oracle update decreases `msA`'s USD price relative to `msB` by more than the cumulative swap and repayment fees, the attacker can:

1. Deposit collateral through `DepositToken.deposit`, which transfers the underlying collateral to `Treasury` and mints deposit shares. [6](#0-5) 
2. Before the update, call `DebtToken.issue` and mint `X` units of `msA` against that collateral. [7](#0-6) 
3. Before the update, call `Pool.swap(msA, msB, X)`, burning `X` `msA` and minting the oracle-quoted amount of `msB`. [8](#0-7) 
4. Let the public oracle update transaction lower `msA`'s price.
5. After the update, call `Pool.swap(msB, msA, receivedMsB)`, which mints more `msA` than the original `X`. [9](#0-8) 
6. Repay the original `msA` debt with `DebtToken.repay` and retain the surplus `msA`, then withdraw collateral once the position is debt-free. [10](#0-9) 

For example, ignoring fees, suppose `msA` and `msB` initially both quote at `$1` and a scheduled update moves `msA` to `$0.50`. The attacker swaps `100 msA` into `100 msB`, waits for the update, then swaps `100 msB` into `200 msA`; repaying the original `100 msA` debt leaves `100 msA` minted without a matching outstanding debt. The extra `msA` is not redeemed from a counterparty reserve; it is newly minted by `SyntheticToken.mint` inside `Pool.swap`. [5](#0-4) 

### Impact Explanation
This breaks the protocol solvency invariant that circulating synthetic assets correspond to debt positions backed by collateral. The attacker ends with zero debt and retains newly minted synthetic tokens, while the protocol has released the collateral that originally backed the borrowed amount. The surplus can be sold on an external market or bridged, creating unbacked synthetic supply and imposing losses on remaining users and collateral holders. The same pattern applies whenever a relative oracle update exceeds fees, so each predictable update can be exploited repeatedly. [1](#0-0) [11](#0-10) 

### Likelihood Explanation
The attack only requires ordinary public entry points: deposit collateral, issue debt, call `Pool.swap` before and after a public oracle update, and repay. `swap` is enabled by default at initialization and is externally callable subject only to shutdown, reentrancy, registered-token, active-swap, and balance checks. [12](#0-11) [13](#0-12) 

The exploit does not require manipulating oracle data or a privileged oracle operator; it only requires observing a pending update or a publicly refreshable pull oracle and ordering transactions around it. Profitability requires the oracle's relative price move to exceed cumulative swap, issue, and repay fees, but the code has no freshness bounding, worst-price check, minimum-out parameter, delay, or minted-position lock to prevent the round trip. [9](#0-8) 

### Recommendation
Do not permit unrestricted atomic round trips through `Pool.swap` across oracle updates. Add user-supplied slippage protection and a price-age/staleness bound, and preferably settle oracle swaps through a delayed two-step process that uses a price committed before the swap request or an update-proof finalization window. At minimum, record the oracle round/timestamp used for an entry swap and prevent a profitable reverse swap from settling in the immediately following round; stronger designs should replace instant mint-and-burn conversion with an external-liquidity redemption path or enforce a minimum lock period for newly swapped synthetic balances. 

### Proof of Concept
The following Foundry-style sequence is reproducible against deployed pool, deposit-token, debt-token, synthetic-token, and master-oracle addresses. In a fork test, substitute a concrete supported collateral, two active synthetic tokens, and a pending oracle update that moves their relative price by more than all fees:

```solidity
function testOracleUpdateSwapSandwich() public {
    // Alice is an ordinary EOA and already owns `collateral`.
    uint256 collateralAmount = 10_000e18;
    uint256 issueAmount = 1_000e18;

    collateral.approve(address(msdCollateral), collateralAmount);
    msdCollateral.deposit(collateralAmount, attacker);
    msADebt.issue(issueAmount, attacker);

    uint256 msA0 = msA.balanceOf(attacker);
    pool.swap(msA, msB, msA0);
    uint256 msB0 = msB.balanceOf(attacker);

    // Reproduce the pending public oracle update on the fork:
    // msA old USD price -> new lower USD price.
    oracleUpdater.updatePriceFeeds(updateData);

    pool.swap(msB, msA, msB0);
    uint256 msA1 = msA.balanceOf(attacker);

    assertGt(msA1, msA0);

    msADebt.repay(attacker, msA0);
    uint256 collateralBefore = msdCollateral.balanceOf(attacker);
    msdCollateral.withdraw(collateralBefore, attacker);

    // Debt is fully repaid and collateral is withdrawable,
    // while `msA1 - msA0` remains as unbacked profit.
    assertEq(msADebt.balanceOf(attacker), 0);
    assertGt(msA.balanceOf(attacker), 0);
}
```

This works because `issue` creates the initial synthetic balance and debt, `swap` burns and mints synthetics at the oracle quote rather than exchanging against reserves, and `repay` removes the original debt once the post-update reverse swap has minted enough `msA`. [3](#0-2) [5](#0-4) [11](#0-10)
