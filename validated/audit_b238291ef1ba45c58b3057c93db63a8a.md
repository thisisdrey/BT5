## Analysis

The reported bug class is a **TOCTOU/ordering hazard**: an irrevocable action (`burn_position`) is decoupled from a guarded, revertible action (`remove_liquidity` with a slippage check), and a race lets the irrevocable step succeed while the guarded step fails, causing permanent loss. The Gitaly analog lives in the receive-pack hook pipeline that every ordinary user push exercises through `OperationService` RPCs (`UserDeleteBranch`, `UserUpdateBranch`, `UserMergeBranch`, etc.).

### Title
Irrevocable quarantine migration and hook side effects precede the race-checked reference update in `UpdaterWithHooks.UpdateReference` - (File: internal/gitaly/hook/updateref/update_with_hooks.go)

### Summary
`UpdateReference` runs the pre-receive hook (external Rails access-check call + admin custom hooks) and unconditionally migrates all quarantined objects into the main object directory **before** it ever takes the reference lock or verifies the expected old OID. [1](#0-0) 
Only afterwards does it start the low-level `updateref.New` updater, queue the update, and call `Prepare()`/`Commit()`, which is where the actual old-OID/lock race check happens. [2](#0-1) 

### Finding Description
The comment in the code explicitly acknowledges the ordering: "Now that Rails has told us that the change is okay via the pre-receive hook, we can migrate any potentially quarantined objects into the main repository. This must happen before we start updating the refs..." [3](#0-2) 
This means the "approval" (pre-receive hook / Rails `/internal/allowed` call, admin custom hooks, and object migration out of quarantine) is performed and made permanent before the safety check that actually matters — the atomic old-OID compare-and-swap done by `git-update-ref` — is executed. If a concurrent push races and changes the reference in between, `Commit()` fails with a lock/old-value mismatch, exactly as demonstrated by the existing test `TestUserDeleteBranch_concurrentUpdate`, which shows the RPC failing with "reference is already locked" after the pre-receive hook has already run. [4](#0-3) 
`UserDeleteBranch`'s optional `ExpectedOldOid` guard resolves the "current" OID once at request-validation time and hands it down as the presumed old value, again before the actual commit-time check. [5](#0-4) 
By the time the race is detected, the quarantined objects have already been unconditionally linked into the target repository's main object directory (`quarantineDir.Migrate(ctx)`), and Rails/custom hooks have already fired based on the payload of a change that ultimately never lands. [6](#0-5) 

### Impact Explanation
This is the same "irrevocable step precedes reverted guarded step" pattern as the Superposition finding: the quarantine directory (per-push staging area meant to keep unapproved objects out of the main store) is bypassed as a safety boundary once migration runs, regardless of whether the guarded reference update that was supposed to make those objects reachable ever succeeds. Concretely this leaves orphaned loose objects permanently in the main object store even for a rejected/raced update, and — more importantly for the "hook and quarantine gating" bug class — it means access-check and custom-hook side effects (which may have external, non-idempotent effects such as notifications, audit logging, or quota changes keyed off the presumed reference transition) are committed for a change that is subsequently rolled back at the Git layer. This is a design gap in the ordering guarantee between hook/quarantine gating and the actual atomic reference update, not a corruption of Git internals, so the severity is bounded (no cross-repo object exposure, no auth bypass), but it is a genuine unprivileged race reachable by any two concurrent pushes to the same branch.

### Likelihood Explanation
Any authenticated user who can push (or trigger `OperationService` RPCs like `UserDeleteBranch`/`UserUpdateBranch`/`UserMergeBranch`) to a branch that is concurrently being updated by another ordinary push can trigger this ordering gap — no privileged access or malicious peer/node is required, matching the analog constraints. The existing test suite already demonstrates the race window exists in production code (`TestUserDeleteBranch_concurrentUpdate`), though that test targets the non-WAL code path; the WAL-based path is explicitly skipped for this scenario (`testhelper.SkipWithWAL`), so the practical likelihood depends on whether WAL is enabled in the deployment — under the legacy/non-WAL configuration, the race is directly reachable.

### Recommendation
Defer irreversible side effects (quarantine migration, and ideally the pre-receive/custom-hook external calls' assumed outcome) until after the reference lock has been acquired and the old-OID has been verified, mirroring how `updater.Prepare()` already locks the reference before the `ReferenceTransactionHook`'s "prepared" phase runs. At minimum, quarantine migration should be moved to occur only after `updater.Prepare()` succeeds (i.e., after the lock and old-OID check), so that a losing race never causes objects to be migrated or hook side effects to be treated as final for a reference update that does not actually apply.

### Proof of Concept
1. Client A calls `UserDeleteBranch` (or `UserUpdateBranch`) on `refs/heads/foo`, currently at OID `X`.
2. `UpdaterWithHooks.UpdateReference` runs the pre-receive hook (Rails access check approves; custom hooks execute) and migrates quarantined objects into the main object directory. [1](#0-0) 
3. Before `updater.Prepare()`/`Commit()` runs, a concurrent client B updates/locks `refs/heads/foo` (e.g., another push), changing its value away from `X`. [7](#0-6) 
4. `updater.Commit()` fails with an "already locked" / "unexpected old value" error, so the ref update from step 1 never applies. [8](#0-7) 
5. However, the pre-receive hook has already executed (with any external, non-idempotent side effects) and, when a quarantine directory was present, migrated objects remain permanently in the main repository despite the guarded reference change never taking effect.
