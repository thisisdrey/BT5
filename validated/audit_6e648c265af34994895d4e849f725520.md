### Title
Dust transfers of `DepositToken` fill a victim's `MAX_TOKENS_PER_USER` list and DoS deposits/borrows — (`File: contracts/DepositToken.sol`)

### Summary
`Pool` keeps two per-account enumerable sets (`depositTokensOfAccount`, `debtTokensOfAccount`) capped at `MAX_TOKENS_PER_USER = 30` (`Pool.sol:79`, `Pool.sol:143-148`). Both `DepositToken._transfer`/`_mint` and `DebtToken` issuance call `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount`, which revert with `UserReachedMaxTokens` once the cap is hit. Because `DepositToken` implements unrestricted ERC-20 `transfer`/`transferFrom` (`DepositToken.sol:348-376`) and `_transfer` adds the recipient to the set whenever their prior balance was `0` (`DepositToken.sol:518-520`), an unprivileged attacker can permanently register arbitrary victim accounts into all 30 slots by sending dust amounts of every deposit token in the pool — no victim interaction required.

### Finding Description
Attack path (fully public, no privileged role):

1. Attacker calls `DepositToken.deposit(dust, attacker)` once per deposit token in the pool (`DepositToken.sol:211-237`).
2. Attacker calls `DepositToken.transfer(victim, 1 wei)` for each token. `_transfer` sees `balanceOf[victim] == 0` and calls `pool.addToDepositTokensOfAccount(victim)` (`DepositToken.sol:519`).
3. `Pool.addToDepositTokensOfAccount` enforces `onlyIfAdditionWillNotReachMaxTokens`, so each transfer consumes one of the victim's 30 combined slots (`Pool.sol:216-220`).

Once `debtTokensOfAccount.length(victim) + depositTokensOfAccount.length(victim) >= 30`, the following victim calls revert with `UserReachedMaxTokens` (`Pool.sol:144-145`):

- `DepositToken.deposit(..., onBehalfOf_ = victim)` for any deposit token the victim does not already hold — `_mint` → `addToDepositTokensOfAccount` fails (`DepositToken.sol:486-488`). Even deposits made *on behalf of* the victim by third parties are bricked.
- `DebtToken.issue`/`leverage` into any debt token the victim does not already hold — the mint path invokes `addToDebtTokensOfAccount` guarded by the same modifier (`Pool.sol:204-208`).

Nothing else stops this: `deposit` is only `whenNotPaused`/`nonReentrant`/`onlyIfDepositTokenExists`; `transfer` has no pause or allowlist; `SynthContext` meta-sender checks are irrelevant since the attacker calls directly. The attacker's cost is just dust underlying plus gas (≤ ~30 tokens exist per pool, bounded by `ReachedMaxDepositTokens`).

### Impact Explanation
This is an availability/DoS violation against a targeted victim. While the victim's set is saturated:

- They cannot open any new collateral type or borrow any new synthetic asset — a functional denial of core protocol features.
- Griefing can be combined with liquidation timing: a victim whose position is drifting unhealthy and who relies on depositing a *different* collateral (e.g., a less volatile asset) is blocked from doing so, enabling forced liquidation where the attacker profits as liquidator. (Depositing more of an already-held token still works, which limits — but does not eliminate — this vector for victims with a single held collateral.)
- Smart-contract integrators (zaps, routers, SmartFarming flows) depositing `onBehalfOf_` users are bricked for saturated accounts.

The attack is not permanently irreversible — the victim can `transfer`/`withdraw` each dust token to empty slots — but each cleanup costs the victim a transaction per token and requires the victim to hold/spend gas, and the attacker can re-saturate (griefing war) since dust costs are negligible relative to the denial window. This maps cleanly to the report's bug class: resource-exhaustion-style DoS of a protocol entry point, reachable by a low-privileged network attacker.

### Likelihood Explanation
Medium. Preconditions are trivially met on any live pool: attacker needs only dust collateral and gas. No privileged roles, no oracle manipulation, no front-running races required — the attacker's transactions are unconditional. The impact ceiling is bounded because the victim can self-heal by clearing slots and because already-held token types remain usable, keeping severity at Medium rather than High — consistent with the CVSS 4.9 availability-only profile of the reference CVE.

### Recommendation
- Do not let inbound `transfer`/`transferFrom` of dust automatically register the recipient in `depositTokensOfAccount`, or charge gas-neutral bookkeeping: e.g., remove the recipient-side `addToDepositTokensOfAccount` on `transfer` and lazily register on `deposit` only, or require a minimum registered-balance threshold before adding to the set.
- Alternatively, make `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` non-reverting at the cap for `transfer`-triggered adds (track only via `deposit`/`issue` paths where the caller opts in).
- Consider allowing victims/anyone to call a `removeFromDepositTokensOfAccount` cleanup for dust balances, or exempting transfers of tokens the pool has marked inactive.

### Proof of Concept
Reproducible Hardhat test sketch against the deployed setup (mirroring `test/Pool.test.ts` fixtures):

```ts
it('dust transfer griefing blocks victim deposits/borrows', async () => {
  // attacker deposits dust into every deposit token of the pool
  for (const dt of depositTokens) {
    await underlying[dt].connect(attacker).approve(dt.address, DUST);
    await dt.connect(attacker).deposit(DUST, attacker.address);
    // register dust on victim -> consumes a MAX_TOKENS_PER_USER slot
    await dt.connect(attacker).transfer(victim.address, 1);
  }
  // repeat with debt tokens via issue(victim, dust) if slots remain
  // victim's combined set is now at 30
  const len = (await pool.getDepositTokensOfAccount(victim.address)).length
            + (await pool.getDebtTokensOfAccount(victim.address)).length;
  expect(len).to.eq(30);

  // victim can no longer deposit a new collateral type
  const newDepositToken = await addNewDepositTokenToPool(); // fresh collateral
  await expect(
    newDepositToken.connect(victim).deposit(amount, victim.address)
  ).to.revertedWithCustomError(pool, 'UserReachedMaxTokens');

  // victim cannot issue a new synthetic debt type either
  await expect(
    newDebtToken.connect(victim).issue(victim.address, mintAmount)
  ).to.revertedWithCustomError(pool, 'UserReachedMaxTokens');
});
```

Fork-based variant: point at the deployed `Pool` on Base/Optimism/Hemi (`deployments/*/Pool.json`), enumerate deposit tokens via `getDepositTokens()`, fund an attacker EOA with dust underlying, execute the transfer loop against a chosen victim address, then assert `UserReachedMaxTokens` on that victim's next `deposit` of a token type they do not hold.

Uncertainties: the exact debt-token mint path that calls `addToDebtTokensOfAccount` (e.g., inside `DebtToken.issue`/`_mint`) was located only by grep and not read in full, so the precise function name/line in `DebtToken.sol` should be confirmed during PoC implementation; the number of configured deposit tokens per deployed pool also affects whether deposit-token dusting alone can fill all 30 slots or must be combined with debt-token mints.
