Based on the investigation, I found a strong local analog of the "cached vs. actual value" arbitrage pattern inside `pallet-nomination-pools`'s `DelegateStake` accounting model.

### Title
Points-derived cached member balance can diverge from actual held/delegated balance in `pallet-nomination-pools`, enabling stale-value settlement - (`substrate/frame/nomination-pools/src/lib.rs`)

### Summary
`pallet-nomination-pools` maintains two parallel notions of a pool member's stake, exactly mirroring the H-11 `totalAssets_cached` vs `totalAssets_actual` split: (1) the member's `expected_balance` derived from their `points` and the pool's points-to-balance ratio (a "cached" value stored in `PoolMembers`), and (2) the member's `actual_balance`, which is the real held/delegated balance tracked by `pallet-delegated-staking` via `T::StakeAdapter::member_delegation_balance`. The pallet itself computes this exact delta as `pending_slash`.

### Finding Description
`member_pending_slash` explicitly computes the divergence between the two values: [1](#0-0) 

This is the same structural pattern as the LMPVault bug: an "actual" value (real held balance in `pallet-delegated-staking`, reduced immediately when `pallet-staking` applies a slash) diverges from a "cached" value (`pool_member.total_balance()`, derived from `points` and the pool ratio, which is only reconciled lazily through the permissionless `apply_slash` extrinsic via `do_apply_slash`): [2](#0-1) 

Critically, the repository's own change history confirms this divergence class already produced a real, exploitable/incorrect-state bug in production logic — not merely a theoretical risk. The `pr_11018.prdoc` documents that a `CurrentEra` vs `ActiveEra` mismatch caused a pool member's cached points-derived balance and actual held balance to desync, trapping funds (points dissolved, held funds not released): [3](#0-2) 

The fix introduced was `do_claim_trapped_balance`, a targeted, one-time reconciliation function that compares `expected_balance` (points-based/cached) against `actual_balance` (held/actual) and releases the delta: [4](#0-3) 

This confirms the underlying invariant — that cached (points-ratio) balance must always equal actual held balance except for the explicitly-tracked `pending_slash` delta — is not structurally enforced at every state transition; it was corrected as a one-off migration for a specific known-affected member rather than via a systemic guard that reconciles cached and actual values before every deposit/withdraw/join, exactly the remediation Sherlock recommended for H-11 ("update totalAssets_cached to totalAssets_actual before any withdrawal or deposit"). The pallet's own `try_state` sanity check only *warns* (does not fail) when `total_balance < bonded_balance + sum_unbonding_balance`, further indicating the cached/actual mismatch is tolerated rather than prevented: [5](#0-4) 

### Impact Explanation
Any divergence between the points-derived cached balance and the actual delegated/held balance in `pallet-delegated-staking` — whether from era-accounting bugs (as already documented) or from timing windows before `apply_slash` is called — allows value to be misattributed between pool members: a member can retain a stale, more favorable balance snapshot while other members' shares of the same pool absorb the shortfall, or funds can become permanently trapped/inaccessible until a manual migration reconciles them. This directly maps to "theft or unbacked mint/unlock" and "permanent user-fund lock" impact categories.

### Likelihood Explanation
The divergence-tracking mechanism (`pending_slash`) is a core, always-active part of the `DelegateStake` strategy (the pool's `points` never change on slash while the real held balance does), so the gap between cached and actual values exists continuously in every `DelegateStake` pool between the time a slash is applied to the pool's aggregate stake and the time each individual member's `apply_slash` is invoked. The repository has already demonstrated in practice (via `pr_11018`) that era-accounting edge cases can turn this normally-transient gap into a persistent, unreconciled state requiring a hand migration, meaning the reconciliation logic is not proven complete for all code paths.

### Recommendation
Enforce reconciliation of cached (points-derived) and actual (delegated/held) balances atomically as part of every state-changing extrinsic that reads member balance (`join`, `bond_extra`, `unbond`, `withdraw_unbonded`), rather than relying on a permissionless-but-optional `apply_slash` call or one-off migrations. Promote `try_state`'s balance-consistency check from a warning to a hard invariant, and add regression coverage for `CurrentEra`/`ActiveEra` boundary conditions similar to the one that produced the trapped-balance bug.

### Proof of Concept
1. A `DelegateStake` pool is slashed; `pallet-staking`/`pallet-delegated-staking` immediately reflects the reduced actual bonded/delegated amount for the pool's stash, while `PoolMembers` point balances remain unchanged (`member_pending_slash` becomes non-zero), as shown in the delegated-staking test flow: [6](#0-5) 
2. Before `apply_slash` is called for a specific member, that member's `PoolMembers` entry (`total_balance()`) still reflects the pre-slash, cached value.
3. If any code path (or an era-boundary edge case, as in the `CurrentEra`/`ActiveEra` bug fixed by `pr_11018`) allows the member to act on this stale cached value (e.g., release/withdraw against it) before slash application forces reconciliation, the member extracts value that should have been distributed pro-rata to remaining pool participants — mirroring exactly the Bob-arbitrage scenario in the H-11 report.
4. The remediation for the known instance required an explicit `do_claim_trapped_balance` one-time migration, confirming no general per-transaction invariant currently guarantees `cached == actual` before settlement: [7](#0-6)

	pub fn do_claim_trapped_balance(member_account: &T::AccountId) -> DispatchResult {
		ensure!(
			T::StakeAdapter::strategy_type() == adapter::StakeStrategyType::Delegate,
			Error::<T>::NotSupported
		);

		// Apply any pending slash first. Ignore NothingToSlash and PoolMemberNotFound
		// (member existence is validated below).
		match Self::do_apply_slash(member_account, None, false) {
			Ok(_) => {},
			Err(e)
				if e == Error::<T>::NothingToSlash.into() ||
					e == Error::<T>::PoolMemberNotFound.into() => {},
			Err(_) => {
				return Err(Error::<T>::Defensive(DefensiveError::SlashNotApplied).into());
			},
		};

		let member = match PoolMembers::<T>::get(member_account) {
			Some(m) => m,
			None => return Ok(()),
		};

		let expected_balance = member.total_balance();
		let actual_balance =
			T::StakeAdapter::member_delegation_balance(Member::from(member_account.clone()))
				.unwrap_or_default();

		let trapped_amount = actual_balance.saturating_sub(expected_balance);

		if trapped_amount.is_zero() {
			return Ok(());
		}

		T::StakeAdapter::member_withdraw(
			Member::from(member_account.clone()),
			Pool::from(Self::generate_bonded_account(member.pool_id)),
			trapped_amount,
			0,
		)?;

	/// Slash member against the pending slash for the pool.
	fn do_apply_slash(
		member_account: &T::AccountId,
		reporter: Option<T::AccountId>,
		enforce_min_slash: bool,
	) -> DispatchResult {
		let member = PoolMembers::<T>::get(member_account).ok_or(Error::<T>::PoolMemberNotFound)?;

		let pending_slash =
			Self::member_pending_slash(Member::from(member_account.clone()), member.clone())?;

		// ensure there is something to slash.
		ensure!(!pending_slash.is_zero(), Error::<T>::NothingToSlash);

		if enforce_min_slash {
			// ensure slashed amount is at least the minimum balance.
			ensure!(pending_slash >= T::Currency::minimum_balance(), Error::<T>::SlashTooLow);
		}

		T::StakeAdapter::member_slash(
			Member::from(member_account.clone()),
			Pool::from(Pallet::<T>::generate_bonded_account(member.pool_id)),
			pending_slash,
			reporter,
		)
	}
