Based on my analysis, I found a concrete analog in `index/suffixarray` where an untrusted length field is used to index into a fixed-size buffer without bounds-checking against the buffer's capacity, causing a panic rather than the OOM described in the russh report (which the task rules exclude, but a parser panic is explicitly allowed).

### Title
Suffix Array Index Deserialization Panics via Unbounded Slice Length Field - ([File: src/index/suffixarray/suffixarray.go])

### Summary
`Index.Read` and its helper `readSlice` deserialize a suffix array index from an `io.Reader` using length fields taken directly from the untrusted input stream. `readSlice` reads a `size` value and then slices the caller's fixed 16 KiB scratch buffer as `buf[binary.MaxVarintLen64:size]` without ever checking `size` against `len(buf)`, so any `size` greater than the buffer's capacity causes an out-of-bounds slice panic on attacker-supplied data.

### Finding Description
`Index.Read(r io.Reader)` allocates a single scratch buffer `buf := make([]byte, bufSize)` (`bufSize = 16<<10`) and calls `readSlice(r, buf, sa, uint64(n))` in a loop [1](#0-0) . Inside `readSlice`, `size64` is read directly from the reader via `readInt`, and the only validation is `int64(int(size64)) != size64 || int(size64) < 0`, which merely guards against negative/overflowing values — it never checks `size` against `len(buf)` [2](#0-1) . The subsequent `io.ReadFull(r, buf[binary.MaxVarintLen64:size])` then performs a slice expression with an attacker-controlled upper bound `size` against a buffer whose fixed capacity is `bufSize` (16384 bytes); any `size` in `(bufSize, math.MaxInt]` panics with "slice bounds out of range" before any I/O occurs, i.e., before the read can even fail. This mirrors the russh flaw in kind: a length field parsed straight from untrusted bytes is used to drive a buffer operation with no upper-bound validation, except here the failure mode is a memory-safety panic rather than unbounded allocation.

### Impact Explanation
Any program that calls `(*Index).Read` on data originating from an external/untrusted source (e.g., a cached or transmitted suffix-array index file) can be crashed by a single corrupted or malicious length field, without needing to supply the corresponding amount of data. This is a reliable, deterministic panic (denial of service via process crash) triggerable with a handful of bytes, distinct from and stronger than a plain OOM — it is an out-of-bounds slice access reachable purely from parsed input length. On Go's severity tracks this would be assessed as a low/moderate PUBLIC-track parsing robustness bug (crash-on-malformed-input), not a memory-corruption or code-execution bug, since Go's runtime slice-bounds check safely panics rather than corrupting memory.

### Likelihood Explanation
The victim workflow is any caller that persists or exchanges a `suffixarray.Index` via `Write`/`Read` and later loads that serialized form from a location an attacker can influence (shared cache, downloaded artifact, etc.) — an "ordinary user data" / "published artifact consumed by a normal workflow" scenario. The attacker only needs to control the byte stream passed to `Read`; no authentication or privileged access is required, and the trigger requires just the first few bytes of a chunk header before more data is even read.

### Recommendation
In `readSlice` (and in `Index.Read`'s own `n64` handling), validate `size` (and `n`) against `len(buf)` (and against sane index-size limits) before using it in a slice expression, returning `errCorrupted` instead of allowing an out-of-range slice operation — analogous to how `encoding/gob` bounds lengths against `state.b.Len()`/`tooBig` and via `internal/saferio` before performing reads or allocations [3](#0-2) .

```go
package suffixarray

import (
	"bytes"
	"encoding/binary"
	"testing"
)

func TestReadPanicsOnOversizedChunkLength(t *testing.T) {
	var buf bytes.Buffer

	// Write a valid top-level length (n) so Index.Read proceeds into the
	// index-reading loop.
	tmp := make([]byte, binary.MaxVarintLen64)
	writeVarint := func(x int64) {
		n := binary.PutVarint(tmp, x)
		buf.Write(tmp[:n])
		// pad remaining bytes like writeInt does (writes full MaxVarintLen64)
		buf.Write(make([]byte, binary.MaxVarintLen64-n))
	}
	writeVarint(1) // n = 1 (need one index entry)

	// data bytes for len(x.data) == 1
	buf.WriteByte(0x41)

	// Now write a corrupted chunk-size header for readSlice: a size far
	// larger than suffixarray's internal 16KiB scratch buffer.
	writeVarint(1 << 20) // size = 1MB, exceeds bufSize (16<<10)

	defer func() {
		if r := recover(); r == nil {
			t.Fatalf("expected panic from out-of-range slice expression, got none")
		}
	}()

	x := new(Index)
	_ = x.Read(&buf) // should panic with "slice bounds out of range" instead of returning errCorrupted
}
```
Expected: without a fix, this test panics with a runtime slice-bounds error inside `readSlice`'s `buf[binary.MaxVarintLen64:size]` expression rather than returning the intended `errCorrupted` error.
