### Title
Unprivileged dust-deposit grief fills a victim's per-account token list, DoS-ing all new collateral deposits - (File: contracts/Pool.sol)

### Summary
`Pool` enforces `MAX_TOKENS_PER_USER = 30` combined deposit+debt tokens per account via `onlyIfAdditionWillNotReachMaxTokens` in `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` (contracts/Pool.sol:143-148, 204-220). `DepositToken._mint` and `DepositToken._transfer` add the recipient to this list whenever their balance goes 0 → >0 (contracts/DepositToken.sol:486-488, 518-520), and `deposit(amount_, onBehalfOf_)` lets anyone mint deposit tokens to an arbitrary `onBehalfOf_` address (contracts/DepositToken.sol:211-237). An unprivileged attacker can therefore deposit ~1 wei of every listed collateral (plus dust `transfer`s) on behalf of a victim until the victim's list hits 30, after which any deposit into a collateral type the victim does not already hold, and any inbound `transfer`/`seize` of a new deposit token to the victim, reverts with `UserReachedMaxTokens`/`DepositTokenAlreadyExists`.

### Finding Description
1. `DepositToken.deposit` has no restriction on `onBehalfOf_` other than non-zero and non-Treasury (DepositToken.sol:214-223). Minting calls `pool.addToDepositTokensOfAccount(onBehalfOf_)` on first receipt (DepositToken.sol:485-488).
2. `Pool.addToDepositTokensOfAccount` reverts once `debtTokensOfAccount.length + depositTokensOfAccount.length >= 30` (Pool.sol:143-148).
3. `transfer`/`seize`/`_transfer` apply the same hook to the recipient (DepositToken.sol:517-520), so liquidators paying out to the victim, and anyone sending the victim a new deposit token, also revert.
4. Debt-token slots count toward the same cap, and any `DebtToken` mint to a fresh account adds to `debtTokensOfAccount`, further constraining the victim.

The victim can only recover by manually emptying dust positions (each removal requires the balance to reach exactly 0, i.e. a transfer or withdraw tx per token — DepositToken.sol:460-462, 522-525), which costs the victim a transaction per slot while the attacker can re-fill slots again at near-zero cost (1 wei deposits), creating a repeatable DoS.

### Impact Explanation
Denial of service on deposits: while the victim's list is saturated, they cannot deposit any collateral type they do not already hold — i.e. they cannot add collateral to improve a degrading position unless it is one of the dusted token types. This is directly exploitable to time-block a victim from topping up collateral during a price move, keeping the account liquidatable while its owner is prevented from acting. It also breaks integrations/contracts that receive deposit tokens to fixed addresses (gateways, zaps) whose lists can be permanently saturated if they lack a way to dump arbitrary msdTOKEN balances.

### Likelihood Explanation
Fully permissionless: any EOA holding trivial amounts of each underlying can execute it through the public `deposit` entry point (or via `Operator.execute`). Cost is ~30 dust deposits/transfers; no privileged role, oracle manipulation, or governance action is needed. The only mitigation is victim-side manual cleanup, which the attacker can repeatedly undo.

### Recommendation
Decouple the accounting list from balance tracking, or make `addTo*TokensOfAccount` not revert on cap (e.g. lazily track or use `try` semantics in `_mint`/`_transfer`). Alternatively, allow users to permissionlessly remove tokens from their own list regardless of balance, or exempt `seize`/liquidation transfers from the cap so payouts are never blocked.
