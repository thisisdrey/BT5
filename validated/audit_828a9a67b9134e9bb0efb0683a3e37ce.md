### Title
Cost-blind FIFO eviction in the sigverify→banking-stage `EvictingSender` lets cheap self-signed garbage evict already-verified legitimate batches - ([File: core/src/sigverify.rs])

### Summary
`SigVerifyWorkerPool::run_transaction_task` pays the full dedup + `ed25519_verify_serial` cost for every non-vote/tpu-vote batch and only then pushes it onto the `banking_stage_sender` `EvictingSender` channel. Because `EvictingSender::try_send` evicts strictly the oldest queued batch on overflow with no notion of fee/priority, an attacker who floods with syntactically-valid, self-signed but semantically useless transactions can repeatedly evict older, already fully-verified legitimate batches out of this bounded queue before the banking-stage scheduler ever reads them, wasting both the sigverify CPU spent on the evicted batch and, symmetrically, forcing more sigverify+queue churn overall.

### Finding Description
The relevant code path is:
1. `SigVerifyWorkerPool::run_transaction_task` (`core/src/sigverify.rs:266-375`) dedups, applies the (optional) priority floor, and runs `sigverify::ed25519_verify_serial` on the batch — i.e. full CPU cost is paid up front.
2. Only after `num_valid_packets > 0` does it call `state.banking_stage_sender.send(banking_packet_batch.clone())` (`core/src/sigverify.rs:349-369`), sampling `max_pre_send_len` and `eviction_drops` purely as **post-hoc metrics**, not as any admission control.
3. `state.banking_stage_sender` is a `TracedSender` wrapping an `EvictingSender<BankingPacketBatch>` (`core/src/banking_trace.rs:391-428`), backed by a bounded crossbeam channel of capacity `NON_VOTE_CHANNEL_CAPACITY = 1024*16` / `VOTE_CHANNEL_CAPACITY = 1024*8` (`core/src/banking_trace.rs:25-31`).
4. `EvictingSender::try_send` (`streamer/src/evicting_sender.rs:41-66`) on `Full` unconditionally pops the single oldest queued item via `self.receiver.try_recv()` and drops it to make room for the newer message — "prefer newer messages over older messages," with **no comparison of fee/priority between the evicted and inserted item**.
5. The only fee/priority-aware defense in this pipeline, `SchedulerPriorityFloor` (`banking-stage-ingress-types/src/lib.rs:71-95`, applied in `apply_priority_floor_to_batch` in `core/src/sigverify.rs:407-439`), is published by the *scheduler's own retained buffer* (`update_scheduler_priority_floor`, `core/src/banking_stage/transaction_scheduler/scheduler_controller.rs:333-352`) — it protects the `TransactionStateContainer` downstream of this channel, not the `EvictingSender` queue itself. The floor only turns on when the scheduler's internal buffer nears its `SATURATION_BUFFER_PCT` watermark, and batches evicted from the `EvictingSender` queue never reach that container to be considered at all.

An attacker's transactions need only carry a valid ed25519 signature (self-signed over arbitrary/garbage instruction data is sufficient, since `ed25519_verify_serial` checks signature validity only, not instruction semantics or account balances) and unique bytes to survive the `Deduper`. Such packets pass steps 1–2 exactly like legitimate fee-paying transactions, consuming identical dedup/verify CPU, then land in the same `EvictingSender` queue where pure arrival-order (FIFO) governs which batch is sacrificed under load — with zero regard for fee/priority or whether the evicted batch already paid full verification cost.

### Impact Explanation
This is a QoS-evasion / grossly-underpriced-pre-fee-work condition: cheap, self-signed garbage that will be discarded at execution (insufficient balance, no-op instructions, etc.) can, under sustained flooding, systematically evict older verified legitimate batches from the bounded `non_vote`/`tpu_vote` channels between `SigVerifyStage` and `BankingStage`. This wastes the CPU the validator already spent on dedup+signature verification of the evicted legitimate batch, and reduces legitimate-transaction throughput/inclusion odds precisely during high-load periods when the channel is most likely to be near capacity — amplifying a base sigverify-cost DoS into an actual throughput-denial for fee-paying users, without requiring the attacker to be staked, to control any peer, or to spend more than the cost of a locally-generated signature.

### Likelihood Explanation
Preconditions are low: an unstaked remote client sending UDP/QUIC TPU traffic with self-signed, unique-per-packet (to survive dedup) garbage transactions. The attack is repeatable indefinitely as long as attacker throughput approaches sigverify-worker throughput and the downstream banking-stage scheduler intake lags momentarily (which is exactly when queue occupancy nears the 16K/8K capacity and evictions actually start happening) — i.e., feasibility scales with how close real network conditions already push this channel toward saturation, which is a realistic condition under any genuine load spike or targeted flood.

### Recommendation
Make the `EvictingSender` used for `banking_stage_sender` priority-aware rather than pure-FIFO: e.g., compare a cheap-to-compute priority/fee proxy of the incoming batch against the oldest queued batch (or track a max-priority-so-far marker) before evicting, or replace the FIFO eviction with a lightweight priority queue keyed by a per-batch priority proxy computed at sigverify time (reusing the same `calculate_priority_from_bytes` used for `apply_priority_floor_to_batch`). Alternatively, extend the `SchedulerPriorityFloor` (or an equivalent, cheaper coarse floor) so it also gates admission into the `EvictingSender` queue itself, not only the scheduler's internal buffer, closing the gap between "verified" and "admitted."

### Proof of Concept
Integration test plan (Rust, in `core/src/sigverify.rs` or `streamer/src/evicting_sender.rs` test modules):
```rust
#[test]
fn test_evicting_sender_drops_legitimate_batches_under_garbage_flood() {
    use solana_streamer::{evicting_sender::EvictingSender, streamer::ChannelSend};

    const CAPACITY: usize = 8;
    let (sender, receiver) = EvictingSender::new_bounded(CAPACITY);

    // Fill the channel with "legitimate" batches (simulated as tagged payloads).
    for i in 0..CAPACITY {
        sender.try_send(format!("legit-{i}")).unwrap();
    }
    assert_eq!(sender.len(), CAPACITY);

    // Attacker floods with cheap, unique "garbage" batches that each survive
    // dedup + verify (simulated as already having been verified prior to send,
    // mirroring run_transaction_task's post-verify send).
    let mut evicted_legit = 0;
    for i in 0..CAPACITY {
        match sender.try_send(format!("garbage-{i}")) {
            Err(crossbeam_channel::TrySendError::Full(_)) => unreachable!(),
            Ok(()) => {}
        }
        // With EvictingSender, Ok(()) may have internally evicted the oldest item.
    }

    // Drain and count how many of the original "legit-*" batches survived.
    let mut remaining_legit = 0;
    while let Ok(item) = receiver.try_recv() {
        if item.starts_with("legit-") {
            remaining_legit += 1;
        } else {
            evicted_legit += 1; // sanity: count garbage entries too
        }
    }

    // Expected/asserted: all legitimate batches were evicted (FIFO order),
    // demonstrating that fee/priority plays no role in what survives.
    assert_eq!(remaining_legit, 0, "all pre-existing legitimate batches were evicted by cheap garbage");
}
```

    fn try_send(&self, msg: T) -> std::result::Result<(), TrySendError<T>> {
        let Err(e) = self.sender.try_send(msg) else {
            return Ok(());
        };

        match e {
            // Prefer newer messages over older messages.
            TrySendError::Full(msg) => match self.receiver.try_recv() {
                Ok(older) => {
                    // Attempt to requeue the newer message.
                    // NB: if multiple senders are used, and another sender is faster than us to send() after we've popped `older`,
                    // our try_send() will fail with Full(msg), in which case we drop the new message.
                    self.sender.try_send(msg)?;
                    // Propagate the error _with the older message_.
                    Err(TrySendError::Full(older))
                }
                // Unlikely race condition -- it was just indicated that the channel is full.
                // Attempt to requeue the message.
                Err(TryRecvError::Empty) => self.sender.try_send(msg),
                // Unreachable in practice since we maintain a reference to both the sender and receiver.
                Err(TryRecvError::Disconnected) => unreachable!(),
            },
            // Unreachable in practice since we maintain a reference to both the sender and receiver.
            TrySendError::Disconnected(_) => unreachable!(),
        }
    }

    /// Update the scheduler priority floor.
    ///
    /// Semantics: when the retained scheduler buffer is nearly full, drop
    /// arrivals that are at-or-below the current queue-min priority, i.e. no
    /// better than what the bounded scheduler candidate set would evict.
    fn update_scheduler_priority_floor(&mut self, num_dropped_on_capacity: usize) {
        let buffer_size = self.container.buffer_size();
        let saturated = self
            .saturation_state
            .update(buffer_size, num_dropped_on_capacity);
        let priority_floor = if saturated {
            self.container
                .get_min_max_priority()
                .map_or(0, |(min, _)| min)
        } else {
            0
        };

        self.saturation_state.publish_floor(priority_floor);
    }

/// Priority floor shared from the banking-stage scheduler to sigverify.
///
/// When saturated, the scheduler publishes the queue-min transaction's
/// priority. Sigverify drops at-or-below-floor arrivals.
/// In practice, transactions always have non-zero priorities.
#[derive(Debug)]
pub struct SchedulerPriorityFloor(AtomicU64);

impl SchedulerPriorityFloor {
    pub fn new() -> Self {
        Self(AtomicU64::new(0))
    }

    pub fn set(&self, floor: u64) {
        self.0.store(floor, Ordering::Relaxed);
    }

    pub fn clear(&self) {
        self.set(0);
    }

    pub fn get(&self) -> u64 {
        self.0.load(Ordering::Relaxed)
    }
}
