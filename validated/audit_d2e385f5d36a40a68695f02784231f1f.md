### Title
Unbounded array allocation from attacker-controlled length word in TVM precompile ABI decoders causes node OOM crash - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
`PrecompiledContracts.extractBytesArray()`, `extractBytes32Array()`, and `extractSigArray()` read an array-length field directly from the ABI-encoded `data` payload of a TVM call and immediately use it to size a Java array (`new byte[len][]`), with no check that `len` is non-negative, bounded by the actual remaining input size, or bounded by any sane maximum, before allocation occurs.

### Finding Description
`extractBytes32Array` reads `len = words[offset].intValueSafe()` and allocates `new byte[len][]` before any bytes are copied or validated against the actual size of `words` [1](#0-0) . The sibling `extractBytesArray`, used by the `batchvalidatesign`/`validatemultisign` precompiles to decode signature/message arrays from the call data of any `TriggerSmartContract`, does the same: it only bounds-checks `offset` against `words.length`, then takes `len = words[offset].intValueSafe()` and allocates `new byte[len][]` with no upper bound on `len` and no verification that the declared count fits within the remaining `data` buffer [2](#0-1) . `extractSigArray` follows the identical unchecked pattern [3](#0-2) .

This is structurally the same bug class as the Pillow `GdImageFile` report: a size/length value taken straight from untrusted, attacker-supplied input is used to drive a memory allocation before any "decompression-bomb"-style sanity check (an upper bound on declared element count vs. actual available payload) is performed. `DataWord.intValueSafe()` is a safe-cast helper that clamps out-of-range 256-bit words rather than throwing, meaning a crafted call data word can yield a very large `int` (up to `Integer.MAX_VALUE`) that is passed straight into `new byte[len][]`/`new byte[len]` allocations — an array of `Integer.MAX_VALUE` object references alone would demand tens of gigabytes, triggering an immediate `OutOfMemoryError` in the node's single JVM process. Unlike the intentionally length-and-CPU-metered EVM memory expansion path, this allocation happens inside precompile execution logic, ahead of/independent from any data-length cross-check, and the resulting `OutOfMemoryError` is not degraded gracefully — it can bring down the whole node process, not just fail the single transaction.

### Impact Explanation
Any unprivileged account can invoke a smart contract that calls into the `batchvalidatesign`/`validatemultisign` precompiled contracts (reachable via a plain `TriggerSmartContract`) with crafted call data containing an inflated length word. This can force the FullNode/SR node executing the transaction to attempt an enormous heap allocation, risking `OutOfMemoryError` and process crash/halt — an availability impact consistent with the "node crash or halt" acceptance criterion.

### Likelihood Explanation
The precompiles are reachable by any account able to broadcast a `TriggerSmartContract` transaction (no special permission required), and the decoding functions perform no length-vs-payload validation prior to allocation, making exploitation straightforward given a contract that calls these precompiles.

### Recommendation
Before allocating in `extractBytesArray`, `extractBytes32Array`, and `extractSigArray`, validate that the decoded `len` is non-negative and does not exceed the number of elements that could plausibly fit within the remaining `data`/`words` buffer (mirroring the `verifyLength`-style bounds check already used elsewhere in the codebase, e.g. `RLP.verifyLength`), rejecting the call with an exception instead of allocating.

### Proof of Concept
Construct a `TriggerSmartContract` transaction invoking a contract that calls `batchvalidatesign`/`validatemultisign` with ABI-encoded input where the array-length word (consumed via `words[offset].intValueSafe()` in `extractBytesArray`) is set to a very large value (e.g., close to `Integer.MAX_VALUE`) while the actual `data` payload is short. On execution, `extractBytesArray` allocates `new byte[len][]` immediately, without checking the declared length against the actual remaining bytes, driving the node toward an `OutOfMemoryError`.     int len = words[offset].intValueSafe();
    byte[][] bytes32Array = new byte[len][];
    for (int i = 0; i < len; i++) {
      bytes32Array[i] = words[offset + i + 1].getData();

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
