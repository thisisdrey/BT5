### Title
USDC Blacklist or Zero-Address Recipient DoS in Loan Disbursement and Refunds - ([File: tare-io__tare-contracts/contracts/Loans.sol])

### Summary
A native analog to the `feeTo` zero-address DoS exists in the `Loans` contract where transfers to the `borrower` address (e.g., in `disburse` or `refundBorrower`) can revert if the address is the zero address or is blacklisted by the underlying `currency` (USDC). This results in a Denial of Service (DoS) that prevents loan activation or the return of overpaid funds, potentially locking investor or borrower assets.

### Finding Description
In `Loans.sol`, the `disburse` function [1](#0-0)  settles a loan by transferring the `netDisbursedAmount` to the borrower via `currency.safeTransfer(borrowers[loanId], ...)` [2](#0-1) . Similarly, `refundBorrower` [3](#0-2)  transfers funds to the borrower address.

If the `borrower` address is the zero address or becomes blacklisted by USDC (the protocol's primary currency), these transfers will revert. While `LoansLedger.sol` contains checks to prevent `address(0)` in `_deposit` and `_withdraw` [4](#0-3) , it does not (and cannot) account for USDC-level blacklisting. If a borrower address is blacklisted, the `disburse` function reverts, locking the investor's previously `fund()`-ed capital in the `ACC_CASH` account of the contract [5](#0-4) .

### Impact Explanation
The impact includes:
1. **Permanent/Practical Lock of Assets**: Investor principal is trapped in the `Loans` contract if `disburse` fails due to a blacklisted borrower.
2. **Material Production DoS**: Loan settlement is blocked across affected loans.
3. **Unauthorized State Transition**: The protocol relies on the `servicer` to update the borrower address to recover, but if the servicer is unavailable or malicious, there is no unprivileged path to rescue the funds.

### Likelihood Explanation
The likelihood is medium. While it requires a borrower to be blacklisted by USDC (or a zero-address to bypass initial registry checks), the protocol's reliance on a single `safeTransfer` call in a critical state-transition function (`disburse`) makes it vulnerable to the same root cause as the `RubiconMarket` report: an external call failure blocking core logic.

### Recommendation
Implement a "pull-payment" or "claim" pattern for disbursements and refunds, or add a check to ensure the recipient is not blacklisted/zero-address before attempting the transfer. Alternatively, provide a guardian-governed recovery path to redirect these funds if the primary transfer fails.

### Proof of Concept
1. An Originator creates a loan with a borrower address `B`.
2. An Investor funds the loan via `fund(loanId, ...)`. The funds move to `ACC_CASH` in the `Loans` contract.
3. Address `B` is added to the USDC blacklist.
4. The Originator calls `disburse(loanId, ...)`.
5. The call to `currency.safeTransfer(borrowers[loanId], ...)` [2](#0-1)  reverts because USDC reverts on transfers to blacklisted addresses.
6. The loan remains in `FullyFunded` status, and the investor's principal is stuck in the contract.

    uint64 loanId,
    int128 netDisbursedAmount,
    int128 originationFee,

    uint48 maturityDate,
    uint32 interestRate,
    int128 expectedMonthlyPayment,
    uint48 timestamp,
    bytes32 ref
  )
    external
    whenNotPaused
    nonReentrant
    loanExists(loanId)
    withLoanUpdate(loanId, timestamp)
    returns (uint128 entryIndex)
  {
    _requireCallerOrAdmin(originators[loanId]);
    require(netDisbursedAmount > 0, InvalidAmount());
    require(originationFee >= 0, InvalidAmount());

    LoanData storage loanData = data[loanId];
    require(loanData.status == LoanStatus.FullyFunded, InvalidStatus());

    // full amount committed = netDisbursedAmount + originationFee
    int128 commitment = -_getAccountBalance(loanId, ACC_UNFUNDED_COMMITMENT);
    require(netDisbursedAmount + originationFee == commitment, InvalidAmountDisbursed());

    // Verify investor funding actually reached the commitment.
    // Status alone is not authoritative because updateLoanData can set it directly.
    int128 funded = -_getAccountBalance(loanId, ACC_INVESTOR_PRINCIPAL_PAYABLE);
    require(funded == commitment, NotFullyFunded());

    _updateLoanData(loanId, LoanStatus.Active, nextDueDate, maturityDate);

    loanTerms[loanId] = LoanTerms({
      originationDate: originationDate,
      interestRate: interestRate,
      expectedMonthlyPayment: expectedMonthlyPayment
    });
    emit LoanTermsSet(loanId, originationDate, interestRate, expectedMonthlyPayment);

    return _disburse(loanId, netDisbursedAmount, originationFee, timestamp, ref);
  }
