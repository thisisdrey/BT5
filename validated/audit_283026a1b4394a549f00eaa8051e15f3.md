### Title
Unsynchronized lazy-singleton initialization in `ActuatorCreator` allows unsafe publication of a partially-constructed instance across threads - (File: `actuator/src/main/java/org/tron/core/actuator/ActuatorCreator.java`)

### Summary
`ActuatorCreator.getINSTANCE()` implements a lazy singleton with no `volatile` field, no `synchronized` block, and no double-checked locking:

```java
public static ActuatorCreator getINSTANCE() {
    if (ActuatorCreatorInner.instance == null) {
      ActuatorCreatorInner.instance = new ActuatorCreator(StoreFactory.getInstance());
    }
    return ActuatorCreatorInner.instance;
}
``` [1](#0-0) 

This is the same bug class as the reported `conquer-once` advisory: a "once"-style shared cell is published to multiple threads without a proper happens-before edge, so a racing thread can observe a reference to a not-yet-fully-constructed object (its `chainBaseManager`/`forkController` fields default/null), or two threads can each construct and use different, inconsistent `ActuatorCreator` instances.

### Finding Description
`ActuatorCreatorInner.instance` is a plain (non-`volatile`) static field, and the check-then-act sequence in `getINSTANCE()` is unguarded by any lock [1](#0-0) . Under the JMM, without `volatile`/`synchronized`, the JIT/compiler may reorder the constructor's field writes (`chainBaseManager = ...`, `forkController.init(...)`) relative to the assignment of `ActuatorCreatorInner.instance`, so a second thread can see a non-null `instance` reference whose `chainBaseManager` or `forkController` is still partially initialized. This is the classic "unsafe publication" defect — structurally identical to the `conquer-once` issue where a `Sync`-but-not-`Send` cell is exposed to concurrent readers before it is safe to do so.

Contrast this with every other singleton pattern in the same codebase, all of which use one of the correct idioms:
- `ChainBaseManager.chainBaseManager` is `volatile` [2](#0-1) 
- `consensus.base.Param` uses `volatile` + double-checked `synchronized` [3](#0-2) 
- `EventPluginLoader.getInstance()` uses `Objects.isNull` + `synchronized` double-checked locking [4](#0-3) 

`ActuatorCreator` has none of these protections, making it an outlier.

The class is reached on every transaction execution path that goes through `RuntimeImpl.execute()` for non-TVM contract types:
```java
default:
    actuatorList = ActuatorCreator.getINSTANCE().createActuator(context.getTrxCap());
``` [5](#0-4) 
`RuntimeImpl.execute()` is invoked from the transaction-trace/execution pipeline for every broadcast transaction and for constant-contract simulation calls served from the RPC/API layer, both of which can run on different worker threads than the block-application thread.

### Impact Explanation
If a thread observes a partially-constructed `ActuatorCreator` (e.g., with a `null` `chainBaseManager` or an uninitialized `forkController`), the subsequent `createActuator`/`getActuatorByContract` call will throw an unhandled `NullPointerException` while processing a user-submitted transaction or API call [6](#0-5) . Because this code executes inside the transaction-execution path invoked by the block-application/consensus flow, an uncaught exception here can abort transaction processing or destabilize the node process, i.e. a remotely triggerable crash/DoS of the API-serving/consensus node. In the more subtle case, a stale/incorrect `forkController` reference could be used to gate actuator validation logic tied to hard-fork checks, leading to inconsistent enforcement of fork-gated contract-type restrictions across actuators built from different `ActuatorCreator` instances.

### Likelihood Explanation
The race window is narrow — it exists only around the very first invocations of `getINSTANCE()`/`init()` before the field is stably published, and `ActuatorCreator.init()` is normally invoked once during single-threaded manager start-up. Triggering the race in production requires a genuine concurrent first-access scenario (e.g., a concurrent API-triggered constant-contract call landing at node start-up, or re-initialization paths), which I could not fully confirm occurs in practice within the time available — I was not able to verify from the indexed code whether `Manager` guarantees `ActuatorCreator.init()` completes strictly before any concurrent RPC traffic can reach `RuntimeImpl.execute()`. This uncertainty lowers confidence relative to a clearly always-reachable bug.

### Recommendation
Make `ActuatorCreatorInner.instance` `volatile` and guard the check-then-act sequence with `synchronized`/double-checked locking (matching the pattern already used in `ChainBaseManager`, `consensus.base.Param`, and `EventPluginLoader`), or switch to an `enum`-based singleton / eagerly-initialized `static final` field to guarantee safe publication.

### Proof of Concept
1. Start two threads that both call `ActuatorCreator.getINSTANCE()` for the first time concurrently (e.g., one via block application, one via a `triggerConstantContract`-style RPC call arriving immediately at node start-up before `Manager`'s single-threaded init completes).
2. Because `ActuatorCreatorInner.instance` is non-`volatile` and unguarded, thread B may see the reference written by thread A before thread A's constructor (`chainBaseManager = storeFactory.getChainBaseManager(); forkController.init(...)`) has fully completed, per the JMM's lack of ordering guarantees for plain field writes/reads.
3. Thread B calls `createActuator()` → `getActuatorByContract()` on the half-initialized instance, dereferencing a `null chainBaseManager`, causing an unhandled `NullPointerException` during transaction execution [6](#0-5) .
