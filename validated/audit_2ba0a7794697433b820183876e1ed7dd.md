### Title
Unstaked attacker can exhaust `max_concurrent_connections` capacity by stalling QUIC handshakes, because both the global and per-IP connection rate limiters are only charged on handshake success, not on connection attempts - (`streamer/src/nonblocking/quic.rs`)

### Summary
`run_server`/`setup_connection` reserve a `ClientConnectionTracker` slot (bounded by `qos.max_concurrent_connections()`) for every accepted `Incoming` connection *before* the TLS/QUIC handshake completes, but the overall and per-IP rate limiters that are supposed to bound the volume of such attempts are only consumed *after* a successful handshake. An attacker who never completes the handshake therefore never gets rate-limited, and can repeatedly acquire tracker slots up to the `QUIC_CONNECTION_HANDSHAKE_TIMEOUT` window, exhausting the shared connection capacity and starving legitimate senders.

### Finding Description
In `run_server` (`streamer/src/nonblocking/quic.rs:304-407`), for every incoming connection the code:
1. Peeks `overall_connection_rate_limiter.current_tokens() == 0` (a non-mutating read, `net-utils/src/token_bucket.rs:66-70`) — it does **not** consume a token here.
2. Calls `rate_limiter.is_allowed(&ip)` (`streamer/src/nonblocking/connection_rate_limiter.rs:34-40`), which for any IP that has never had a *registered* (successful) connection unconditionally returns `true` ("if we have not seen IP, allow connection request").
3. Calls `ClientConnectionTracker::new(stats.clone(), qos.max_concurrent_connections())` (`streamer/src/nonblocking/quic.rs:236-251`), which increments the shared `stats.open_connections` atomic and fails only once that count reaches `max_concurrent_connections()`. This slot is held for the entire lifetime of the `ClientConnectionTracker` (i.e., until the connection attempt is torn down).
4. Spawns `setup_connection` (`streamer/src/nonblocking/quic.rs:456-543`), which does `timeout(QUIC_CONNECTION_HANDSHAKE_TIMEOUT, connecting).await` (timeout constant = 2s, `streamer/src/nonblocking/quic.rs:80`).

Critically, `rate_limiter.register_connection(&from.ip())` and `overall_connection_rate_limiter.consume_tokens(1)` — the actual token-consuming calls for both the per-IP and global limiters — only execute in the `Ok(new_connection)` branch **after the handshake has already succeeded** (`streamer/src/nonblocking/quic.rs:483-508`). If the attacker never completes the handshake (deliberately stalling, or aborting just before completion), neither limiter is ever charged for that attempt. Consequently:
- The global `TokenBucket` (`TOTAL_CONNECTIONS_PER_SECOND = 2500`, `MAX_CONNECTION_BURST = 1000`, `streamer/src/nonblocking/quic.rs:73-76,277-281`) stays effectively full forever against a pure-stalling attacker, so the pre-accept peek at step 1 almost never blocks.
- The per-IP limiter's map entry is never created/consumed for a stalling IP, so `is_allowed` keeps returning `true` for that IP indefinitely (or for any number of fresh/rotated IPs).

The only real gate against this attack is `ClientConnectionTracker::new`'s comparison to `qos.max_concurrent_connections()` (which per `simple_qos.rs:422-425` / `swqos.rs:518-522` is `(max_staked_connections + max_unstaked_connections) * 5/4`). Since a slot is held for up to `QUIC_CONNECTION_HANDSHAKE_TIMEOUT` (2s) per stalled attempt, and neither rate limiter throttles the attacker's *attempt* rate, the attacker can repeatedly open new connections (from one IP or many, no stake needed) fast enough to keep `stats.open_connections` pinned at `max_concurrent_connections()`, causing subsequent legitimate connections (staked or unstaked) to be refused via `refused_connections_too_many_open_connections` (`streamer/src/nonblocking/quic.rs:374-379`).

### Impact Explanation
This is a QoS-evasion / capacity-starvation issue on the TPU QUIC ingress: an unstaked, unprivileged remote client can occupy up to `max_concurrent_connections()` connection-tracker slots almost continuously by stalling handshakes just under the 2-second timeout and reopening, denying legitimate staked/unstaked clients TPU connectivity (`refused_connections_too_many_open_connections`). This matches the "QoS evasion" bounty category — bounded ingress resources are supposed to remain fair regardless of packet/connection volume, but the rate limiters that are meant to bound attempt volume are bypassed entirely by never completing the handshake.

### Likelihood Explanation
No stake or special network position is required — only the ability to open TCP/UDP-level QUIC connections to the public TPU port and stall/abort the handshake before completion, which any unprivileged client can do (e.g., send the QUIC Initial packet and simply stop, or close the connection just before the crypto handshake finishes). Using a small number of rotating source IPs (or even a single IP, since `is_allowed` is permissive for un-registered IPs) is sufficient; this is easily automated and repeatable indefinitely.

### Recommendation
Rate-limit connection *attempts*, not just successful handshakes: consume from `overall_connection_rate_limiter` and register the per-IP `ConnectionRateLimiter` at accept time (before/when acquiring the `ClientConnectionTracker` slot) rather than only after a successful handshake. Alternatively/additionally, enforce a separate, tighter cap on `outstanding_incoming_connection_attempts` (already tracked in `StreamerStats`, `streamer/src/quic.rs:232`) independent of `max_concurrent_connections`, and/or per-IP cap on concurrent in-flight (not-yet-handshaked) connection attempts, so that a burst of never-completing handshakes cannot consume the full connection budget shared with legitimate, successfully-handshaked peers.

### Proof of Concept
Integration test plan (extends existing tests like `test_rate_limiting_establish_connection` in `tpu-client-next/tests/connection_workers_scheduler_test.rs:664-745`):
1. Spawn the QUIC streamer via `setup_quic_server` with a small `SwQosConfig` (`max_unstaked_connections` small, e.g. 10, `max_staked_connections = 0`) so `max_concurrent_connections()` is small and reachable quickly.
2. From N attacker tasks (using distinct loopback ports/`SocketAddr`s to simulate distinct IPs, or a single IP), repeatedly call `endpoint.connect(...)` but never drive the resulting `Connecting` future to completion (e.g., drop the client endpoint immediately after sending the Initial packet, or use a client config that never finishes the crypto handshake), and repeat this every < `QUIC_CONNECTION_HANDSHAKE_TIMEOUT` (2s).
3. Concurrently attempt a normal, well-behaved `make_client_endpoint` connection and try to send a transaction.
4. Assert that `stats.refused_connections_too_many_open_connections` increases and that the legitimate client's packet is never received by `receiver` within a bounded wait, while `stats.connection_rate_limited_across_all` and `stats.connection_rate_limited_per_ipaddr` remain at/near 0 (proving the rate limiters were never triggered by the stalling attempts), demonstrating that `ClientConnectionTracker` capacity was consumed by stalling connections that bypassed both rate limiters.     pub fn is_allowed(&self, ip: &IpAddr) -> bool {
        // Check if we have records in the rate limiter for the given IP address
        match self.limiter.current_tokens(ip) {
            Some(r) => r > 0, // we have a record, and rate is not exceeded
            None => true,     // if we have not seen IP, allow connection request
        }
    }

    pub fn register_connection(&self, ip: &IpAddr) -> bool {
        if self.limiter.consume_tokens(*ip, 1).is_ok() {
            debug!("Request from IP {ip:?} allowed");
            true // Request allowed
        } else {
            debug!("Request from IP {ip:?} blocked");
            false // Request blocked
        }
    }

    /// Return current amount of tokens in the bucket.
    /// This may be somewhat inconsistent across threads
    /// due to Relaxed atomics.
    #[inline]
    pub fn current_tokens(&self) -> u64 {
        let now = self.time_us();
        self.update_state(now);
        self.tokens.load(Ordering::Relaxed)
    }

    /// Attempts to consume tokens from bucket.
    ///
    /// On success, returns Ok(amount of tokens left in the bucket).
    /// On failure, returns Err(amount of tokens missing to fill request).
    #[inline]
    pub fn consume_tokens(&self, request_size: u64) -> Result<u64, u64> {
        let now = self.time_us();
        self.update_state(now);
        match self.tokens.fetch_update(
            Ordering::AcqRel,  // winner publishes new amount
            Ordering::Acquire, // everyone observed correct number
            |tokens| {
                if tokens >= request_size {
                    Some(tokens.saturating_sub(request_size))
                } else {
                    None
                }
            },
        ) {
            Ok(prev) => Ok(prev.saturating_sub(request_size)),
            Err(prev) => Err(request_size.saturating_sub(prev)),
        }
    }
