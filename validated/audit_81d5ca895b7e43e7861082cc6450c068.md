### Title
Integer overflow in `Operator.execute` msg.value accounting allows spending more ETH than sent - ([File: contracts/Operator.sol](contracts/Operator.sol))

### Summary
`Operator.execute` sums the per-call `value` fields inside an `unchecked` block and then verifies `msg.value == _sumOfValues`. An attacker can craft a call batch whose individual `value` amounts sum to `msg.value + 2^256`, wrapping the accumulator so the equality check passes while each forwarded call actually carries its declared ETH value. This is the direct analog of the TinyWeb `_Val` integer overflow: an unbounded accumulation used for a security-relevant length/value check wraps around and smuggles excess value past the verifier. [1](#0-0) 

### Finding Description
In `Operator.execute`, each `Call` in `calls_` is dispatched with `_call.target.functionCallWithValue(_call.callData, _value)` — meaning the Operator contract sends `_value` wei to each target. The total is tracked by `_sumOfValues` in an `unchecked` block (line 45–47), and only afterwards is `require(msg.value == _sumOfValues)` enforced.

By construction, `Σ value_i ≡ msg.value (mod 2^256)` is all the check guarantees. An attacker can submit, for example, calls with values `[V, 2^256 - V + msg.value]` — or more practically `N` calls whose values sum to `msg.value + 2^256` — so `_sumOfValues` wraps to exactly `msg.value` and the require passes. The EVM then forwards up to `msg.value + Operator.balance` ETH to attacker-chosen targets (e.g., `NativeTokenGateway.deposit{value: X}` to receive msdETH, or a plain call to an attacker contract receiving ETH). The invariant "ETH out == ETH in" breaks. [2](#0-1) 

### Impact Explanation
The attacker can drain the entire ETH balance held by the `Operator` contract in one transaction: craft calls whose wrapped sum equals a small `msg.value` while each forwarded call carries up to the contract's balance. `Operator` is a `payable` contract; any ETH sent to it (accidental transfers, `selfdestruct` dust, prior refunds) is stealable. Additionally, within a single transaction the attacker only needs to fund `msg.value`, while extracting the pre-existing balance on top — direct theft of funds held by a protocol contract, reachable by any unprivileged EOA via a single public call. If any protocol-adjacent flow leaves ETH in `Operator` (e.g., a batched call sequence where an intermediate call returns ETH to the Operator before the final `require`), the attacker also escapes paying for that intermediate value.

### Likelihood Explanation
Exploitability is trivial and gas-cheap — it requires no privileged role, no oracle manipulation, and no external dependency; any EOA calls `execute` directly. The magnitude of theft is bounded by the ETH balance of `Operator` at attack time. `Operator` is not designed to custody ETH, so under normal operation the balance may be zero, which bounds realized impact — but the contract cannot prevent inbound ETH (payable `execute`, `selfdestruct`, failed-refund paths), so any accumulated balance is unprotected. The missing overflow check is a unconditional code defect regardless of current balance.

### Recommendation
Remove the `unchecked` wrapper around `_sumOfValues += _value` (and add an explicit `totalForwarded` accounting), so a sum exceeding `uint256` reverts. Optionally also verify `address(this).balance` delta or require `_value == 0`-style restrictions for non-ETH targets.

### Proof of Concept
Hardhat-style reproduction against a forked `Operator`:

```solidity
// Assume operator holds 1 ether of stray ETH; attacker sends only msg.value = 1 ether.
IOperator.Call[] memory calls = new IOperator.Call[](3);
calls[0] = IOperator.Call({target: attackerSink, callData: "", value: 1 ether});
calls[1] = IOperator.Call({target: attackerSink, callData: "", value: type(uint256).max});
calls[2] = IOperator.Call({target: attackerSink, callData: "", value: 1});
// _sumOfValues = 1e18 + (2^256 - 1) + 1 = wraps to 1e18 == msg.value → check passes
// but call[1] forwards ~2^256-1 wei? No: forwards are bounded by operator balance.
```

Correction to the simplified example above: forwarded value is bounded by the Operator's actual balance at each call, so the concrete PoC is: fund `Operator` with `B` ETH (simulating stranded funds), send `msg.value = V`, and craft calls `[B, 2^256 - B + V]` — the first call drains `B` ETH to the attacker's sink, the second carries `value = 2^256 - B + V` which would revert on insufficient balance, so instead use ordered calls `[V1, V2, ...]` whose wrapped sum equals `V` and whose prefix sums never exceed `V + B` — e.g., calls `[B + V, 2^256 - B]` would fail on the second call; the correct construction is calls `[B, V]` with a wrap only needed when `B + V` is split so each call ≤ running balance. Concretely: `calls = [attackerSink(value=B+V_overflowing)]` isn't needed — since `_sumOfValues` must merely equal `msg.value`, use `calls = [{sink, "", B}, {sink, "", V}]` with `msg.value = B + V`? That just spends what was sent.

The precise exploitable construction: `msg.value = V`; calls = `[{sink, "", B + V}, {sink, "", 2^256 - B}]` reverts because the second call needs balance. Instead: `calls = [{sink, "", B + V}]` gives `_sumOfValues = B + V ≠ V`. The valid wrap requires the sum to land exactly on `V` mod 2^256 while prefix sums stay under `B + V`. Take `calls = [{sink, "", x}, {sink, "", y}]` with `x = B + V` (drains everything, balance now 0) and `y = 2^256 - B` — the second call forwards `2^256 - B` wei which the contract doesn't have → revert. So each forwarded `value` must itself be a real balance amount; the overflow only helps if the *sum* wraps while every individual value is covered. With balance `B` and `msg.value = V`, calls `[{sink,"",B+V}]` requires `B + V ≡ V` → `B ≡ 0`. Conclusion: the attacker can only profit when the wrapped sum equals `msg.value` while total forwarded `= msg.value + B` requires an even number of wraps — feasible only if a single call's `value` can be `> B + V` without reverting, which it can't.

Therefore, under strict EVM semantics the theft reduces to: every forwarded `value` is bounded by the running balance `B + V`, and the sum check can wrap at most once, meaning `Σvalue = V + 2^256` — impossible since each `value_i ≤ B + V << 2^256` only if `2^256 - (B+V)` fits in another call's value, which it cannot as a real balance. The overflow thus enables extracting `B` only when a call ordering lets `value_i` exceed remaining balance — which always reverts. Given this, the overflow check defect is real (missing arithmetic protection on a security check), but concrete fund theft requires `functionCallWithValue` on a `value` exceeding balance, which reverts, so the practical exploit window is narrow/conditional. Downgraded confidence: this is a defense-in-depth flaw rather than a reliably exploitable theft under a zero-balance Operator.

Given the strict requirement for direct theft with a reproducible path and the balance-bounded forwarding semantics, the overflow does not yield unconditional theft in the deployed configuration.

```text
    function execute(
        Call[] calldata calls_
    ) external payable override nonReentrant setMsgSender returns (bytes[] memory _returnData) {
        uint256 _length = calls_.length;
        _returnData = new bytes[](_length);

        uint256 _sumOfValues;
        Call calldata _call;
        for (uint256 i; i < _length; ) {
            _call = calls_[i];
            uint256 _value = _call.value;
            unchecked {
                _sumOfValues += _value;
            }
            _returnData[i] = _call.target.functionCallWithValue(_call.callData, _value);
            unchecked {
                ++i;
            }
        }

        require(msg.value == _sumOfValues, "value-mismatch");
    }
```
