### Title
Griefing via forced `MAX_TOKENS_PER_USER` saturation blocks victims from adding collateral or taking new debt - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
`Pool` enforces a hard cap of `MAX_TOKENS_PER_USER = 30` on the combined length of an account's `depositTokensOfAccount` and `debtTokensOfAccount` sets, reverting with `UserReachedMaxTokens` whenever an addition would reach the cap (`Pool.sol:143-148`, `Pool.sol:79`). Any token transfer or deposit that gives an address a first-ever nonzero balance pushes the token into that address's per-account set (`DepositToken.sol:518-520`, `DepositToken.sol:486-488`). Because `DepositToken.transfer`/`deposit` are permissionless and let the caller pick the recipient, an unprivileged attacker can saturate a victim's set with dust amounts of every registered `DepositToken`, making the victim unable to receive any new collateral type or open any new debt position — analogous to the busboy report's class of unauthenticated attacker-controlled input causing a state-dependent denial of service.

### Finding Description
- `Pool.addToDepositTokensOfAccount(account_)` and `addToDebtTokensOfAccount(account_)` are guarded by `onlyIfAdditionWillNotReachMaxTokens`, which reverts once `debt + deposit` token count reaches 30 (`Pool.sol:143-148`, `Pool.sol:204-220`).
- `DepositToken._transfer` and `_mint` call `pool.addToDepositTokensOfAccount(recipient_)` whenever the recipient's prior balance was 0 (`DepositToken.sol:517-520`, `DepositToken.sol:485-488`). There is no opt-in; the recipient cannot refuse.
- `transfer` is callable by any holder and is not behind `whenNotPaused` (`DepositToken.sol:348-354`), and `deposit(amount_, onBehalfOf_)` credits an arbitrary beneficiary (`DepositToken.sol:211-237`). Either path lets the attacker force entries into the victim's set.
- Once the victim's combined set length hits 30: deposits of any *new* collateral to the victim revert at `_mint` → `addToDepositTokensOfAccount`; issuance of any *new* synthetic debt reverts at `addToDebtTokensOfAccount`; and liquidators' `seize` to a fresh recipient address reverts in `_transfer` if that recipient is saturated.

### Impact Explanation
A victim with an unhealthy or near-liquidatable position cannot top up with any collateral type they do not already hold — every `deposit(..., victim)` for a new `DepositToken` reverts, so the victim cannot restore health and will be liquidated at a loss (collateral seized at discount plus liquidation fee). This is a temporary freezing of the victim's ability to add collateral and can directly translate into loss of funds via forced liquidation. The attack is not a gas/loop DoS — it is a deterministic `UserReachedMaxTokens` revert caused by attacker-written state.

### Likelihood Explanation
Cost to attacker is bounded: dust `transfer` of each of the pool's deposit tokens to the victim (the tokens can be acquired by depositing minimal underlying, and recovered afterward). No privileged role, oracle manipulation, or flash-loan assumption is needed — only the ability to hold and transfer msd tokens. It does not apply to debt tokens the attacker cannot mint, but deposit tokens alone suffice when a pool has up to 30 registered collaterals. Feasibility depends on the deployed pool having enough registered deposit tokens to reach the cap; on pools with few collaterals the cap is unreachable and the attack fails. Whether the mainnet/Base pools list ≥30 deposit tokens was not verified from the index.

### Recommendation
- Do not count token additions against `MAX_TOKENS_PER_USER` for entries the recipient never requested, or add a per-account opt-in (e.g., only add to the set on `deposit`/`issue` initiated by the account, not on inbound `transfer`).
- Alternatively, make `addToDepositTokensOfAccount` idempotent-no-op instead of reverting at the cap, skipping the set insertion but still crediting the balance (health accounting already iterates the set, so this trades completeness of `depositOf` for liveness — prefer instead bounding iteration by gas rather than a hard revert).
- At minimum, let `seize`/liquidation paths tolerate the cap so liquidations are not blocked.

### Proof of Concept
Reproducible Hardhat outline (fork or unit fixture):

```ts
// Assume pool has N registered DepositTokens where victim's
// depositTokensOfAccount.length + debtTokensOfAccount.length can reach 30.
for (const dt of allDepositTokens) {
  // attacker deposits dust and transfers to victim
  await underlying.approve(dt.address, DUST)
  await dt.deposit(DUST, attacker.address)
  await dt.transfer(victim.address, DUST)   // adds dt to victim's set
}
// victim's set length == 30
// Now any new-collateral deposit on behalf of victim reverts:
await expect(
  someNewDepositToken.deposit(amount, victim.address) // or transfer to victim
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens')
// And issuing a new debt token type reverts in addToDebtTokensOfAccount.
// If victim was near liquidation, they cannot add a new collateral type
// and get liquidated at a loss.
```

Key code paths: `Pool.sol:79` (`MAX_TOKENS_PER_USER`), `Pool.sol:143-148` (cap check), `Pool.sol:204-220` (set inserts), `DepositToken.sol:348-354` (`transfer`), `DepositToken.sol:517-520` (recipient set insertion).
