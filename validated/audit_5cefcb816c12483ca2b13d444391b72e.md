### Title
Unbounded `parent` header count in `ParseCommit` allows memory/CPU amplification per commit object - ([File: internal/git/catfile/parse_commit.go])

### Summary
`ParseCommit` appends every `parent <oid>` header line it encounters to `commit.ParentIds` with no upper bound on count, unlike the commit body which is explicitly capped by `helper.MaxCommitOrTagMessageSize` [1](#0-0) . An attacker who controls repository content (via `git hash-object`/push) can craft a single commit object containing many thousands of `parent` lines, causing one `ParseCommit` call to allocate a correspondingly large `ParentIds` slice that is then serialized into a `GitCommit` gRPC response.

### Finding Description
`ParseCommit` parses commit headers line by line in a state machine; every line beginning with `parent ` is unconditionally appended to `commit.ParentIds` [2](#0-1) . There is no cap on the number of `parent` headers processed, in contrast to the commit body/message, which is explicitly truncated at `helper.MaxCommitOrTagMessageSize` (10 KiB) before being placed on `commit.Body` [3](#0-2) [1](#0-0) .

`GetCommit` and `ListCommits`/`FindAllBranches`-style handlers call into this parser via `catfile.GetCommit` for arbitrary attacker-controlled revisions in a repository the attacker owns [4](#0-3) . Since git's object format does not restrict the number of `parent` header lines a commit object may declare, an attacker can use `git hash-object -t commit -w` to inject an object with many thousands of synthetic `parent <oid>` lines, point a ref at it, and then trigger `GetCommit`/`ListCommits` against that ref.

The overall commit object size is bounded only by how much data the attacker is willing to author/push (not by any explicit cap in this code path), so the size of `ParentIds` — and the resulting `GitCommit.ParentIds` field in the gRPC response — scales linearly with attacker-supplied header count. This is inconsistent with the deliberate capping applied to the commit body, indicating the parent-header path was not similarly hardened.

### Impact Explanation
Each request to `GetCommit`/`ListCommits` against such a crafted commit forces the Gitaly node to allocate memory proportional to the number of `parent` lines (each ~48 bytes minimum) and to marshal/transmit that entire list in a single `GitCommit` protobuf message. For `ListCommits`, this cost can repeat per commit walked. This maps to a resource-exhaustion (denial of service) impact on the RPC handler and shared Gitaly node memory/CPU, though the practical severity is bounded by how large a commit object the attacker can actually create and store (proportional to the pushed pack size), and by whatever gRPC message-size limits or timeouts apply upstream — no explicit `MaxRecvMsgSize`/`MaxSendMsgSize` override was found in this codebase, so default gRPC-Go limits (4 MiB) would likely bound the practical amplification for a single message.

### Likelihood Explanation
An unprivileged user who can push/import a repository they own can create arbitrary git objects, including a commit with an implausible number of `parent` headers (git's loose-object writer does not validate parent semantics). The exploit sequence (craft object → create ref → call `GetCommit`/`ListCommits`) requires no special privileges beyond normal repository write access, making it feasible and repeatable per-repository. However, the amplification factor is linear (not exponential), and default gRPC message-size limits likely cap the blast radius of a single response, reducing severity relative to a true unbounded-memory DoS.

### Recommendation
Apply a bound to the number of `parent` headers parsed per commit (e.g., cap `len(commit.ParentIds)` similar to how `commit.Body` is truncated with `helper.MaxCommitOrTagMessageSize`), and/or enforce an overall maximum commit header size before allocating `ParentIds`, returning a parse error or truncating with a documented limit once exceeded.

### Proof of Concept
```go
// Sketch: craft a commit object with N synthetic parent lines and parse it.
func BenchmarkParseCommitManyParents(b *testing.B) {
    const numParents = 100_000
    var buf bytes.Buffer
    buf.WriteString("tree " + strings.Repeat("0", 40) + "\n")
    for i := 0; i < numParents; i++ {
        buf.WriteString(fmt.Sprintf("parent %040d\n", i))
    }
    buf.WriteString("author a <a@a> 0 +0000\ncommitter a <a@a> 0 +0000\n\nsubject\n")

    // Write via `git hash-object -t commit -w --stdin` in a real repo,
    // then fetch it via ObjectReader and call parser.ParseCommit(object).
    // Assert: commit.ParentIds has numParents entries with no cap enforced,
    // and memory/time scale linearly with numParents (unlike commit.Body,
    // which is capped at helper.MaxCommitOrTagMessageSize).
}
```
Expected assertion: `len(commit.ParentIds) == numParents` with no truncation, demonstrating the absence of any cap analogous to the body-size cap.
