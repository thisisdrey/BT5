### Title
Rewards index overflow via SafeCast downcast can permanently freeze a deposit/debt token - (File: contracts/RewardsDistributor.sol)

### Summary
`RewardsDistributor` stores per-token and per-account reward indexes in narrow unsigned types (`uint128`/`uint224`) and uses `SafeCast` downcasts when updating them. Because reward indexes are monotonically increasing accumulator values (`index += deltaIndex`), once a token's index exceeds the storage type's max, every subsequent index update reverts. Since `updateBeforeMintOrBurn`/`updateBeforeTransfer` are called from `DepositToken`/`DebtToken` mint, burn, transfer, deposit, withdraw, issue, repay, and seize paths, a pushed-past-the-limit index permanently freezes the affected token's core accounting — an unrecoverable liveness break analogous to the reported "downcast halts execution on read" bug.

### Finding Description
`RewardsDistributor.sol` is the only production contract in the repo that (a) imports/uses `SafeCast` and (b) declares narrow-width state for accumulator values. The relevant mechanics:

- `supplyIndexOf(token)` / `accountIndexOf(account, token)` are `uint128`-style packed indexes that grow only upward: each update computes `index += (claimableRewards * 1e18) / totalSupply`.
- `updateBeforeMintOrBurn(token, account)` and `updateBeforeTransfer(token, from, to)` recompute and store the new index using a `SafeCast` downcast (e.g., `toUint128`), which reverts if the accumulated value no longer fits.
- `DepositToken` and `DebtToken` invoke these hooks inside `deposit`, `withdraw`, `transfer`, `transferFrom`, `seize`, `issue`, `burn`/`repay`, and related paths, so a reverting index update reverts the entire user-facing operation.

The index denominator is `totalSupply` of the reward-bearing token. On a newly registered or very thinly supplied `DepositToken`/`DebtToken`, `totalSupply` can be made arbitrarily small by an attacker (e.g., first depositor holding dust, or donating reward tokens to the distributor/distributor's balance accounting before supply grows). A large `claimableRewards / tinyTotalSupply` quotient in a single update can push the stored index past `type(uint128).max` (or the declared width), at which point the `SafeCast` downcast reverts on every subsequent call.

### Impact Explanation
Once the index overflows the storage width, every call path that touches `updateBeforeMintOrBurn`/`updateBeforeTransfer` for that token reverts permanently: deposits, withdrawals, transfers, mints, repays, and liquidations (`seize`) all halt for that market. This is permanent freezing of user funds in the affected `DepositToken`/`DebtToken` — matching the "downcasting can freeze the chain" liveness class — and additionally bricks `Pool.liquidate`, worsening solvency for underwater positions in that market. No privileged action can roll back a monotonically-grown index except a contract upgrade.

### Likelihood Explanation
Likelihood is low-to-moderate. It requires (1) a reward-bearing token whose distributor index can be inflated faster than its total supply grows — most feasible early in a market's life or on a low-supply token, and (2) a reward token the attacker can push into the distributor's claimable balance (donation of the reward ERC-20 to the distributor if accounting is balance-based, or griefing via reward-rate configuration on smaller tokens). It does not require any privileged role, oracle manipulation, or malicious bridge endpoint; it needs only public deposit/transfer calls and a donation. If reward deltas are bounded by a governor-set `rewardsSpeed` against fully-custodied balances, the attack may be infeasible in practice — that accounting detail should be verified against `RewardsDistributor._update`/`claimRewards` funding source before final severity assignment.

### Recommendation
- Store indexes in `uint256` (or at least `uint192`/`uint224` with headroom analysis), removing the `SafeCast` downcast on accumulator values.
- Alternatively, make index updates non-reverting: saturate or skip accrual instead of reverting, so token operations cannot be frozen by index growth.
- Cap the per-update delta (`deltaIndex`) and/or enforce a minimum `totalSupply` floor for accrual when supply is near zero.

### Proof of Concept
```solidity
// Foundry fork test sketch
// Setup: deploy pool, depositToken (vaX) with a RewardsDistributor configured
//        with a reward token R the attacker holds.

function test_indexOverflowFreezesToken() public {
    // 1. Attacker deposits a dust amount so totalSupply of depositToken is tiny.
    underlying.approve(address(pool), 1);
    pool.deposit(address(depositToken), 1);   // totalSupply ~= 1 wei

    // 2. Attacker inflates the pending reward delta: donate a huge amount of
    //    reward token R to the RewardsDistributor (or trigger accrual such that
    //    deltaIndex = donated * 1e18 / totalSupply > type(uint128).max).
    uint256 donated = uint256(type(uint128).max) + 1;
    rewardToken.transfer(address(rewardsDistributor), donated);

    // 3. Any touch that updates the index computes
    //    newIndex = oldIndex + donated*1e18/1  > uint128 max
    //    -> SafeCast.toUint128 reverts inside updateBeforeMintOrBurn.
    vm.expectRevert(); // "SafeCast: value doesn't fit in 128 bits"
    pool.deposit(address(depositToken), 1);

    // 4. Permanent freeze: withdraw/transfer/issue/repay/seize all revert too.
    vm.expectRevert();
    pool.withdraw(address(depositToken), 1);

    vm.expectRevert();
    depositToken.transfer(address(0xbeef), 1);
}
```

Expected result: after step 3, all state-changing entry points on the affected `DepositToken`/`DebtToken` revert inside `RewardsDistributor.updateBeforeMintOrBurn`/`updateBeforeTransfer`, permanently locking deposited collateral and blocking liquidations for that market. Caveat: confirm in `RewardsDistributor` that claimable rewards are computed from a balance the attacker can donate into (or a rate the attacker can influence); if accrual is strictly capped by a governor-managed `rewardsSpeed` escrow, likelihood drops further.
