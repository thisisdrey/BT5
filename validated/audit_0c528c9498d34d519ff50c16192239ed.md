### Title
Timing side-channel in RPC `Authorization` header comparison allows byte-by-byte recovery of `auth_token` - ([File: stackslib/src/net/api/postblock_proposal.rs])

### Summary
Several privileged Stacks node RPC endpoints authenticate the caller by comparing the request's `authorization` header directly against the configured `auth_token` using Rust's `!=` string comparison. This comparison is not constant-time: it short-circuits on the first mismatching byte, producing measurably different response latencies depending on how many leading bytes of the guess match the real secret. A remote, unauthenticated attacker can exploit this timing difference to recover the `auth_token` byte-by-byte and then use it to submit unauthenticated writes such as block proposals, forced broadcasts, or read-only/simulate calls — a direct analog of the "response time of login gives hint" side-channel flaw in the reported Sulu advisory (CVE-2020-15132, bug #3).

### Finding Description
The `auth_token` is intended to gate sensitive endpoints (`/v3/block_proposal`, `/v3/blocks/replay/:id`, `/v3/blocks/simulate/:id`, `/v3/contracts/fast-call-read/...`, `/v3/transactions/simulate`, and the `broadcast=1` path of `/v2/blocks`). Each of these handlers performs the check the same way: [1](#0-0) 

```rust
let Some(auth_header) = preamble.headers.get("authorization") else {
    return Err(Error::Http(401, "Unauthorized".into()));
};
if auth_header != password {
    return Err(Error::Http(401, "Unauthorized".into()));
}
```

The same pattern recurs verbatim in: [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4) [6](#0-5) 

`auth_header != password` compares `String`/`&str` values, which Rust implements via slice byte comparison (`[u8]::eq`), an operation that returns as soon as it finds a differing byte rather than always touching every byte. This breaks the equality the endpoint is meant to enforce ("submitted token == configured secret") into a *partial-prefix-match* oracle: the more leading bytes of a guess match the true secret, the longer (on average) the comparison — and therefore the request-handling path — takes before returning `401`.

This is architecturally identical to bug #3 in the referenced advisory ("Response time of login gives a hint if the username exists"), except here the compared secret is the node's `auth_token` rather than a username, and the exposed oracle is over an equality check performed remotely and unauthenticated for every request to these endpoints.

### Impact Explanation
An attacker with network access to a node's RPC endpoint but without knowledge of `auth_token` can iteratively guess the token byte-by-byte using timing measurements, given enough samples to average out network jitter. Recovering the token grants the attacker the ability to submit unauthenticated actions gated behind it, including posting block proposals to `/v3/block_proposal` (used by the signer/miner protocol) and forcing block broadcast via `/v2/blocks?broadcast=1`. This maps to the "auth bypass" category, which the grading rules list under Critical impact.

### Likelihood Explanation
Exploitation requires many timing samples per byte to overcome network noise and is easier over low-latency/local links (e.g. signer-to-node communication is often on the same host or LAN), which is a realistic deployment scenario for these `/v3/*` endpoints. The likelihood is moderate: it is a genuine, remotely reachable code defect, but practical extraction time depends on network conditions and token length/entropy.

### Recommendation
Replace all direct `!=`/`==` string comparisons of the `authorization` header against the configured secret with a constant-time comparison (e.g. `subtle::ConstantTimeEq`, or comparing SHA-256 digests of both values with a constant-time equality check) across `postblock_proposal.rs`, `blockreplay.rs`, `blocksimulate.rs`, `fastcallreadonly.rs`, `txsimulate.rs`, and `postblock_v3.rs`.

### Proof of Concept
1. Configure a node with `connection_options.auth_token = "<secret>"`.
2. Send repeated POST requests to `/v3/block_proposal` (or any of the other listed endpoints) with an `authorization` header consisting of a guessed prefix followed by all possible next bytes, e.g. guess `"a"`, `"b"`, ... for byte 0, then fix the correct byte and repeat for byte 1, etc.
3. Measure round-trip time for each guess; the byte value yielding the largest average latency (indicating the comparison advanced further before returning 401) is likely correct.
4. Repeat until the full `auth_token` is reconstructed, then use it to authenticate to the endpoint and submit an unauthenticated block proposal / forced broadcast.
