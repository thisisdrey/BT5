### Title
Exchange creator can front-run `ExchangeTransactionContract` swaps via `ExchangeWithdrawContract`/`ExchangeInjectContract` to drain counterparties despite the `expected` slippage guard - ([File: actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java])

### Summary
Java-tron's Bancor-style TRC10 Exchange (created by any account via `ExchangeCreateContract`) lets the pool's creator arbitrarily change the pool's token ratio at any time via `ExchangeWithdrawContract`/`ExchangeInjectContract`, exactly analogous to `LSSVMPair.changeSpotPrice()`/`changeDelta()` in the external report. A trader submitting an `ExchangeTransactionContract` swap sets `expected` as a minimum-output guard [1](#0-0) , but that check is only evaluated against whatever pool state exists at the moment the transaction actually executes in the block. The creator can broadcast a withdraw/inject transaction that gets ordered immediately before the victim's swap (same block), skewing the price so the victim still clears their `expected` floor yet receives dramatically less value than the price they observed when signing — the same "malicious owner front-runs by instantly repricing the pool" pattern flagged in the LSSVMPair report.

### Finding Description
The `Exchange` capsule stores a mutable `firstTokenBalance`/`secondTokenBalance` ratio that determines swap output via the Bancor-like `transaction()` formula [2](#0-1) . `ExchangeWithdrawActuator.execute()`/`ExchangeInjectActuator.execute()` allow only the `creatorAddress` (checked in `doValidate()`) to shift these balances instantaneously and without any delay or cooldown [3](#0-2) . `ExchangeInjectActuator`/`ExchangeWithdrawActuator` are ordinary broadcastable contracts, reachable by any unprivileged account that created the exchange pool — not a validator/SR-privileged action.

`ExchangeTransactionActuator.doValidate()` computes the expected output from the *current* `exchangeCapsule` state at validation time and only rejects if `anotherTokenQuant < tokenExpected` [1](#0-0) . Nothing prevents the creator from placing a withdraw/inject transaction ahead of a pending victim swap within the same block (transactions execute sequentially in the order committed by the block producer, and a normal account can influence ordering by fee/priority or by colluding/being the block producer itself is not required — simple mempool timing is sufficient since there's no anti-frontrunning mechanism at all). Because the victim's `expected` value was calculated off-chain against the pre-manipulation ratio, a modest, honest slippage tolerance (which most SDKs/wallets set close to the observed quote to avoid over-loosening the check) can still pass the `>= tokenExpected` check post-manipulation while the victim actually receives far less value than fair market price, with the surplus effectively flowing to the creator's reserves in the pool that they control and can subsequently withdraw.

This exactly mirrors the reported bug class: an "owner" of a trading venue (LSSVMPair owner / Exchange creator) can instantaneously reprice the venue right before a counterparty's trade executes, and the counterparty's slippage-protection parameter (`minExpectedTokenOutput` / `expected`) is an imperfect mitigation because users don't always set it optimally.

### Impact Explanation
This allows an Exchange creator to extract value from any trader who does not set an extremely tight `expected` value, resulting in unauthorized/unexpected loss of user funds (a form of theft via pool manipulation) at the actuator layer. Because `ExchangeInjectContract`/`ExchangeWithdrawContract`/`ExchangeTransactionContract` are all standard signed transactions reachable by any account, this is exploitable by an unprivileged malicious pool creator against any counterparty, satisfying "concrete unauthorized account operation / theft of funds."

### Likelihood Explanation
Medium: it requires the attacker to control an Exchange pool (trivial and permissionless via `ExchangeCreateActuator`) and to get a withdraw/inject transaction ordered immediately before a victim's swap in the same block, which is achievable through normal fee-based mempool ordering or by simply monitoring pending transactions and resubmitting with adequate bandwidth/energy priority — no special network-level or witness privilege is required. It depends on victims not setting extremely tight `expected` values, similar to the acknowledged caveat in the original LSSVMPair report.

### Recommendation
Introduce a similar mitigation to the one recommended for LSSVMPair: require Exchange balance-altering operations (`ExchangeWithdrawContract`/`ExchangeInjectContract`) to be delayed by at least one block after an "announce" step, or bound the maximum single-transaction shift in the pool ratio, or require `ExchangeTransactionActuator` to reference a maximum acceptable price-impact bound (not just an absolute `expected` amount) so it inherently detects abrupt ratio changes within the same block. Alternatively, disallow same-block ordering of withdraw/inject and swap transactions touching the same `exchange_id`.

### Proof of Concept
1. Attacker (creator) creates an Exchange pool for TRX/TokenA with `ExchangeCreateContract`, seeding an attractive ratio (e.g., 1 TRX : 1000 TokenA) to lure traders.
2. Victim observes the ratio, signs an `ExchangeTransactionContract` selling TRX for TokenA with `expected` set slightly below the quoted fair value (standard slippage tolerance, e.g., 1-2%).
3. Attacker broadcasts `ExchangeWithdrawContract` (or `ExchangeInjectContract`) withdrawing the bulk of TokenA reserves from the same `exchange_id`, drastically shifting the ratio unfavorably for sellers of TRX, and ensures it lands in the same block before the victim's transaction (via fee bump/timing).
4. Block executes attacker's withdraw first, mutating `exchangeCapsule` balances via `ExchangeCapsule.setBalance()` [4](#0-3) .
5. Victim's `ExchangeTransactionActuator.doValidate()` recomputes `anotherTokenQuant` against the new, worse ratio; since victim's `expected` tolerance still allows some slippage, the check `anotherTokenQuant < tokenExpected` passes [1](#0-0) , and the swap executes at the manipulated price, transferring excess value to the attacker's pool, which the attacker can then withdraw again via `ExchangeWithdrawContract`.

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
  }
