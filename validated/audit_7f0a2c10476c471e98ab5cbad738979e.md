### Title
Unauthenticated peer-controlled `data_url` drives blind SSRF-style outbound HTTP requests via block/microblock download path - (File: `stackslib/src/net/download/epoch2x.rs`, `stackslib/src/net/chat.rs`, `stackslib/src/net/httpcore.rs`)

### Summary
GitLab's SSRF bug let an unauthenticated caller redirect a server-initiated `Gitlab::HTTP.post` to an attacker-chosen host by manipulating request input (`Host` header / callback URL) that was trusted without restricting to safe network ranges. In stacks-core, the analogous trust boundary is the `data_url` field of `HandshakeData`, which is fully attacker-controlled by any unauthenticated/unprivileged peer performing a P2P handshake. This URL is later resolved and used verbatim to open outbound TCP/HTTP connections (block/microblock downloads, mempool sync, StackerDB/neighbor RPC) from the node's own network position, but only the mempool-sync path (`stackslib/src/net/mempool/mod.rs`) is gated against private/loopback destinations; the block-download path (`stackslib/src/net/download/epoch2x.rs`) and the neighbor-RPC / StackerDB HTTP path (`stackslib/src/net/neighbors/rpc.rs`, `stackslib/src/net/httpcore.rs`) are not.

### Finding Description
When a peer performs a handshake, it supplies a `data_url` (`HandshakeData::data_url`), which is fully attacker-chosen and is stored and later reused as the target of outbound HTTP requests: [1](#0-0) 

DNS/IP resolution of this attacker-supplied string happens in `ConversationP2P::try_decode_data_url_ipaddr`/`resolve_data_url` without any IP-range restriction: [2](#0-1) 

The resolved `(url, addr)` pair is later used directly to open sockets and issue HTTP requests: [3](#0-2) [4](#0-3) 

The block/microblock downloader consumes the same peer-declared `data_url` to schedule and issue anchored-block/microblock GET requests, with no check that the resolved address is non-private/non-loopback before connecting: [5](#0-4) [6](#0-5) 

By contrast, the mempool-sync state machine explicitly checks and skips private-range addresses derived from a peer's `data_url` unless `private_neighbors` is enabled: [7](#0-6) 

The neighbor-RPC HTTP helper (used for StackerDB/other neighbor RPCs) similarly resolves and connects to a peer's advertised `data_url`/`data_ip` with no private-range check: [8](#0-7) 

The only private-IP handling found elsewhere in the neighbor-walk code is a *heuristic substitution* (replace a private-looking handshake `addrbytes` with the observed connecting address) — it does not vet the `data_url` used for HTTP fetches, and only applies to the walk's `NeighborAddress`, not the download/RPC `data_url` flow: [9](#0-8) 

This is an equality/consistency break of the intended invariant "outbound HTTP requests derived from peer-declared endpoints must be restricted the same way everywhere" — the mempool path enforces it, but the block-download and neighbor-RPC paths do not, letting a remote unauthenticated peer steer the node's outbound HTTP client at internal/loopback services reachable from the node's process (e.g., internal RPC control planes, sidecar services, cloud metadata endpoints) by simply advertising a malicious `data_url` in its handshake.

### Impact Explanation
This matches the report's High-severity SSRF impact class: unauthenticated, blind request forgery that lets a remote party make the victim's server issue arbitrary HTTP requests into its own internal network. Here, any peer that can complete a handshake (an unauthenticated, low-privilege action inherent to P2P bootstrapping) can cause the node to issue attacker-directed block/microblock-download HTTP GETs — including `Host:`-targeted requests at addresses within the node's private network — because the block-downloader and neighbor-RPC HTTP paths don't apply the private/loopback filter that the mempool-sync code already applies. Depending on deployment (containerized nodes with internal-only management ports, sidecars, or cloud metadata services reachable from the node process), this can be used for internal service probing/blind SSRF from a remote, unauthenticated actor.

### Likelihood Explanation
Likelihood is high: forging a handshake with an arbitrary `data_url` requires no privilege beyond being able to open a P2P connection and complete a handshake, which is by design open to any peer. The vulnerable code paths (block/microblock download, neighbor RPC) are on the normal peer-crawling/sync hot path and get exercised automatically once a node begins tracking a malicious neighbor, without further attacker interaction.

### Recommendation
Apply the same private/loopback-range check used in `mempool_sync_send_query` (`PeerAddress::from_socketaddr(addr).is_in_private_range()` gated by `connection_opts.private_neighbors`) uniformly to every outbound-HTTP code path that consumes peer-declared `data_url`/resolved `data_ip`, specifically:
- `PeerNetwork::connect_or_send_http_request` / `HttpPeer::connect_http` in `stackslib/src/net/httpcore.rs` and `stackslib/src/net/server.rs`.
- The block/microblock download scheduler in `stackslib/src/net/download/epoch2x.rs` (`begin_request`, `BlockRequestKey` construction).
- `NeighborRPC::send_request` / `get_peer_host` in `stackslib/src/net/neighbors/rpc.rs`.

This centralizes the check so it can't be bypassed by simply routing through a different call path than mempool sync.

### Proof of Concept
1. Run a malicious peer that completes a valid P2P handshake with the target node, advertising `HandshakeData.data_url = "http://127.0.0.1:<internal-port>/"` (or an RFC1918/loopback address of an internal service reachable from the target node's network namespace).
2. Cause the target node to believe this peer has data worth fetching (e.g., advertise blocks/microblocks it doesn't yet have, or a StackerDB chunk inventory).
3. Observe that the target node's block-downloader resolves the private `data_url` via `try_decode_data_url_ipaddr`/DNS and issues an outbound HTTP GET to that internal address (`stackslib/src/net/download/epoch2x.rs` `begin_request` → `connect_or_send_http_request`), with no filtering — unlike the equivalent mempool-sync flow, which would have rejected it via the `is_in_private_range` check in `stackslib/src/net/mempool/mod.rs`.

    /// create the HTTP request.  Pops requests off the front of request_keys, and returns once it successfully
    /// sends out a request via the HTTP peer.  Returns the event ID in the http peer that's
    /// handling the request.
    pub fn begin_request<T: Requestable>(
        network: &mut PeerNetwork,
        dns_lookups: &HashMap<UrlString, Option<Vec<SocketAddr>>>,
        requestables: &mut VecDeque<T>,
    ) -> Option<(T, usize)> {
        loop {
            match requestables.pop_front() {
                Some(requestable) => {
                    if let Some(Some(ref sockaddrs)) = dns_lookups.get(requestable.get_url()) {
                        assert!(!sockaddrs.is_empty());

                        let peerhost = match PeerHost::try_from_url(requestable.get_url()) {
                            Some(ph) => ph,
                            None => {
                                warn!("Unparseable URL {:?}", requestable.get_url());
                                continue;
                            }
                        };

                        for addr in sockaddrs.iter() {
                            let request = requestable.make_request_type(peerhost.clone());
                            match network.connect_or_send_http_request(
                                requestable.get_url().clone(),
                                *addr,
                                request,
                            ) {
                                Ok(handle) => {
                                    debug!(
                                        "{:?}: Begin HTTP request {}",
                                        &network.local_peer, requestable
                                    );
                                    return Some((requestable, handle));
                                }
                                Err(e) => {
                                    debug!(
                                        "{:?}: Failed to connect or send HTTP request {}: {:?}",
                                        &network.local_peer, requestable, &e
                                    );
                                }
                            }
                        }

                        debug!(
                            "{:?}: Failed request for {} from {:?}",
                            &network.local_peer, requestable, sockaddrs
                        );

                            &network.local_peer, requestable
                        );
                    }
