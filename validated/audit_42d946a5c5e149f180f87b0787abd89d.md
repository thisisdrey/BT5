### Title
Dry-run/RPC CREATE1 address prediction diverges from on-chain deployment address due to unconditional nonce off-by-one - (File: substrate/frame/revive/src/exec.rs)

### Summary
`pallet-revive`'s `Stack::new_frame` derives the address of a contract created via `CREATE` (no salt) using `address::create1(deployer, nonce)` [1](#0-0) . For the outermost frame it always treats `origin_is_caller` as `true` [2](#0-1) , subtracting 1 from the current on-chain nonce on the theory that `CheckNonce` already incremented it pre-dispatch. That assumption is only true for a real, dispatched extrinsic. For a dry-run (`bare_instantiate` invoked from RPC/runtime-API simulation, e.g. `eth_estimateGas`/contract-address-prediction calls), the nonce has *not* been pre-incremented, so subtracting 1 computes the wrong (lower) nonce and thus the wrong CREATE1 address, while the real, later-dispatched transaction will use the correct (unshifted) nonce and land at a different address. The project's own changelog entry `prdoc/stable2506/pr_8504.prdoc` documents exactly this bug and describes a fix that adds an `ExecContext` check (`origin_is_caller && matches!(exec_context, ExecContext::Transaction)`), but that `ExecContext` type and condition do not exist anywhere in `exec.rs` in this codebase — only in the prdoc text. [3](#0-2) 

### Finding Description
- `Stack::new` always calls `new_frame` with `origin_is_caller = true` for the first frame regardless of whether the call originates from a dispatched extrinsic or a bare/dry-run call: [4](#0-3) 
- Inside `new_frame`, for `FrameArgs::Instantiate` without a salt (`CREATE1` semantics), the code computes: `if origin_is_caller { account_nonce - 1 } else { account_nonce }` and feeds that into `address::create1` [1](#0-0) .
- `bare_instantiate` (used by RPC/runtime API dry-run and gas-estimation flows) reads `T::AddressMapper::to_address(&sender)` and calls into `ExecStack::run_instantiate`, which ultimately reaches the same `new_frame` path with `origin_is_caller = true`, but crucially the account nonce has not been incremented by `CheckNonce` in this dry-run context [5](#0-4) .
- Consequently, the address computed and returned by the dry run (`InstantiateReturnValue.addr`) is `create1(deployer, real_nonce - 1)`, while the address actually produced when the corresponding real transaction (`instantiate_with_code`) is later submitted is `create1(deployer, real_nonce)` (since by then `CheckNonce` incremented the nonce first). These two addresses differ.
- The project's own prdoc `pr_8504` acknowledges this exact bug ("the returned address does not match the actual address that will be used when the transaction is submitted") and states the intended fix, but that fix's `ExecContext` gate is absent from `exec.rs`, indicating the fix documented in the changelog was not actually merged into the source shown here.

### Impact Explanation
Any tooling, wallet, or bridge component that relies on the runtime API/RPC dry-run of contract instantiation to predict the deployment address (a standard pattern for pre-funding a not-yet-deployed contract, similar to CREATE2-style counterfactual deployment used by the zkSync report) will compute and display/act on an incorrect address. Funds sent to the predicted (wrong) address before the real deployment transaction executes will not reach the actually deployed contract, resulting in **stuck/lost funds** for an unprivileged, ordinary user — no malicious peer, validator, relayer, or governance actor is required. This falls squarely within the "permanent user-fund lock" and "runtime bugs that compromise intended behavior" categories.

### Likelihood Explanation
This triggers deterministically for the common case of a signed CREATE1 (no-salt) instantiation dry-run followed by the actual dispatched instantiation, whenever a caller relies on the RPC/dry-run predicted address before submitting the real transaction — a normal, expected usage pattern (e.g., Ethereum-tooling-style “predict my contract address, then send it funds, then deploy”). No adversarial conditions are needed; a normal user following documented instantiate/CREATE semantics is directly affected.

### Recommendation
Implement the fix actually described in `prdoc/stable2506/pr_8504.prdoc`: thread an explicit execution-context flag (real dispatched transaction vs. dry-run/RPC simulation) into `new_frame`/`Stack::new`, and only subtract 1 from the nonce when `origin_is_caller` **and** the call is a genuine dispatched transaction (i.e., nonce was actually pre-incremented by `CheckNonce`). For dry-run/bare calls, use the un-decremented nonce so predicted addresses match real deployment addresses. Add a regression test (e.g., `nonce_not_incremented_in_dry_run`) asserting that `bare_instantiate`'s returned address equals the address obtained from the corresponding real `instantiate_with_code` dispatch.

### Proof of Concept
1. Fund account `ALICE` and note her current on-chain nonce `N`.
2. Call `Pallet::bare_instantiate` (the dry-run/RPC path) with `Code::Upload(some_code)` and `salt: None`. Record the returned `InstantiateReturnValue.addr` — internally this computes `create1(&deployer, N - 1)` because `origin_is_caller = true` unconditionally in `Stack::new`.
3. Now actually dispatch `Pallet::instantiate_with_code(...)` with the same code/salt as a real signed extrinsic. `CheckNonce` increments ALICE's nonce to `N+1` pre-dispatch, then `new_frame` computes `create1(&deployer, (N+1) - 1) = create1(&deployer, N)`.
4. Compare addresses from step 2 (`create1(deployer, N-1)`) and step 3 (`create1(deployer, N)`) — they differ, demonstrating the address returned to a caller relying on the dry-run/RPC prediction is not the address that will actually receive the deployed contract, matching the pattern already confirmed by the project's own (unimplemented-in-code) `pr_8504` changelog entry. [6](#0-5)

title: Fix generated address returned by Substrate RPC runtime call
doc:
- audience: Runtime Dev
  description: |-
    ## Description

    When dry-running a contract deployment through the runtime API, the returned address does not match the actual address that will be used when the transaction is submitted. This inconsistency occurs because the address derivation logic doesn't properly account for the difference between transaction execution and dry-run execution contexts.

    The issue stems from the `create1` address derivation logic in `exec.rs`:

    ```rust
    address::create1(
        &deployer,
        // the Nonce from the origin has been incremented pre-dispatch, so we
        // need to subtract 1 to get the nonce at the time of the call.
        if origin_is_caller {
            account_nonce.saturating_sub(1u32.into()).saturated_into()
        } else {
            account_nonce.saturated_into()
        },
    )
    ```

    The code correctly subtracts 1 from the account nonce during a transaction execution (because the nonce is incremented pre-dispatch), but doesn't account for execution context - whether it's a real transaction or a dry run through the RPC.

    ## Review Notes

    This PR adds a new condition to check for the `ExecContext` when calculating the nonce for address derivation:

    ```rust
    address::create1(
        &deployer,
        // the Nonce from the origin has been incremented pre-dispatch, so we
        // need to subtract 1 to get the nonce at the time of the call.
        if origin_is_caller && matches!(exec_context, ExecContext::Transaction) {
            account_nonce.saturating_sub(1u32.into()).saturated_into()
        } else {
            account_nonce.saturated_into()
        },
    )
    ```

    A new test `nonce_not_incremented_in_dry_run()` has been added to verify the behavior.

    ## Before Fix

    - Dry-run contract deployment returns address derived with nonce N
    - Actual transaction deployment creates contract at address derived with nonce N-1
    - Result: Inconsistent addresses between simulation and actual execution

    ## After Fix

    - Dry-run and actual transaction deployments both create contracts at the same address
    - Result: Consistent contract addresses regardless of execution context
    - Added test case to verify nonce handling in different execution contexts

    This fix ensures that users can rely on the address returned by a dry run to match the actual address that will be used when the transaction is submitted.

    Fixes https://github.com/paritytech/contract-issues/issues/37
```

	pub fn bare_instantiate(
		origin: OriginFor<T>,
		evm_value: U256,
		transaction_limits: TransactionLimits<T>,
		code: Code,
		data: Vec<u8>,
		salt: Option<[u8; 32]>,
		exec_config: &ExecConfig<T>,
	) -> ContractResult<InstantiateReturnValue, BalanceOf<T>> {
		let mut transaction_meter = match TransactionMeter::new(transaction_limits) {
			Ok(transaction_meter) => transaction_meter,
			Err(error) => return ContractResult { result: Err(error), ..Default::default() },
		};

		let mut storage_deposit = Default::default();

		let try_instantiate = || {
			let instantiate_account = T::InstantiateOrigin::ensure_origin(origin.clone())?;

			if_tracing(|t| t.instantiate_code(&code, salt.as_ref()));
			let executable = match code {
				Code::Upload(code) if code.starts_with(&polkavm_common::program::BLOB_MAGIC) => {
					let upload_account = T::UploadOrigin::ensure_origin(origin)?;
					let executable = Self::try_upload_code(
						upload_account,
						code,
						BytecodeType::Pvm,
						&mut transaction_meter,
						&exec_config,
					)?;
					executable
				},
				Code::Upload(code) => {
					if T::AllowEVMBytecode::get() {
						ensure!(data.is_empty(), <Error<T>>::EvmConstructorNonEmptyData);
						let origin = T::UploadOrigin::ensure_origin(origin)?;
						let executable = ContractBlob::from_evm_init_code(code, origin)?;
						executable
					} else {
						return Err(<Error<T>>::CodeRejected.into());
					}
				},
				Code::Existing(code_hash) => {
					let executable = ContractBlob::from_storage(code_hash, &mut transaction_meter)?;
					ensure!(executable.code_info().is_pvm(), <Error<T>>::EvmConstructedFromHash);
					executable
				},
			};
			let instantiate_origin = ExecOrigin::from_account_id(instantiate_account.clone());
			let result = ExecStack::<T, ContractBlob<T>>::run_instantiate(
				instantiate_account,
				executable,
				&mut transaction_meter,
				evm_value,
				data,
				salt.as_ref(),
				&exec_config,
			);

			storage_deposit = transaction_meter
				.execute_postponed_deposits(&instantiate_origin, &exec_config)
				.inspect_err(|err| {
					log::debug!(target: LOG_TARGET, "Failed to transfer deposit: {err:?}");
				})?;
			result
		};
