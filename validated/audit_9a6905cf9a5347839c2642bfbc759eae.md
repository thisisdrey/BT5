### Title
Integer overflow in `Operator.execute` value accounting lets an attacker drain ETH held by the Operator - (File: contracts/Operator.sol)

### Summary
The libgepub report describes an integer overflow during a size/value calculation that produces an incorrect allocation. The Metronome analog is in `Operator.execute`, which accumulates the per-call `value` fields inside an `unchecked` block and then only verifies `msg.value == _sumOfValues`. An attacker can craft a `Call[]` array whose `value` fields sum past `type(uint256).max`, wrapping the accumulator so the final equality check passes with a tiny `msg.value`, while each individual call still forwards its full (large) `value` of ETH out of the Operator contract's own balance.

### Finding Description
`Operator.execute` iterates over a user-supplied `Call[]` array. For each call it does `unchecked { _sumOfValues += _value; }` and then executes `_call.target.functionCallWithValue(_call.callData, _value)`, which sends `_value` wei from the Operator contract's balance to `target`. After the loop it enforces `require(msg.value == _sumOfValues, "value-mismatch")`.

Because `_sumOfValues` is accumulated in `unchecked` arithmetic, the attacker controls the wrap point. Example: two calls each with `value = type(uint256).max` produce `_sumOfValues = type(uint256).max * 2 mod 2^256 = type(uint256).max - 1`. More practically, `value1 = X` (all ETH held by the contract, sent to an attacker contract) plus `value2 = 2^256 - X` (sent to a reverting or attacker target) gives `_sumOfValues = 0`, so the attacker calls `execute{value: 0}(...)` and the check passes. The Operator still attempts to send `X` ETH from its own balance to `target`.

Any ETH sitting in the Operator contract (leftover refunds from prior `execute` calls, ETH accidentally sent to the payable function, or ETH the contract holds transiently) can be stolen by an unprivileged EOA in a single transaction. The `nonReentrant` guard and `setMsgSender` modifier do not prevent this — they only constrain re-entry and spoofed `msg.sender`, not the arithmetic.

### Impact Explanation
Direct theft of ETH held by the Operator contract. The attacker receives real ETH forwarded via `functionCallWithValue` while paying (nearly) nothing, because the wrapped accumulator satisfies the `msg.value` equality invariant. This is the same bug class as the reference: an overflowed size/value calculation produces an allocation/authorization far larger than what was actually supplied.

### Likelihood Explanation
Requires only that the Operator contract holds some ETH balance. That is plausible in practice: `execute` is payable, internal calls can leave change, users can force ETH in via `selfdestruct` or accidental transfers, and refund paths in downstream protocols can push ETH back to Operator. The attacker needs no privileges — `execute` is a public entry point callable by any EOA, and the `Call[]` arguments (targets, values, calldata) are fully attacker-controlled.

### Recommendation
Remove the `unchecked` on the `_sumOfValues` accumulation so the addition reverts on overflow, or accumulate with checked arithmetic and keep the final `msg.value == _sumOfValues` comparison. Alternatively, forward only `msg.value` pro-rata or require each call's `value` to be funded by tracking remaining balance: `require(msg.value >= _sumOfValues)` alone is insufficient unless the accumulation is checked.

Precise construction: choose `value1 = bal` (drain to attacker) and `value2 = type(uint256).max - bal + msg.value + 1` so `_sumOfValues` wraps to `msg.value`. To avoid call 2 failing on insufficient balance, instead point `target` of call 2 at the Operator itself or use three calls: `value1 = bal` to attacker, `value2` large with `target = address(op)` (funds return), and `value3` chosen so the sum wraps to `msg.value`. The invariant `msg.value == sum(call.value)` is broken because checked equality on a wrapped accumulator does not bound per-call outflow.
