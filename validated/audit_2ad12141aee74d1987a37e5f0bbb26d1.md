### Title
os.CopyFS creates symlinks with unsanitized targets, allowing an untrusted fs.FS to write outside the destination directory - ([File: src/os/dir.go])

### Summary
`os.CopyFS` walks a caller-supplied `fs.FS` and materializes it on disk. For `ModeSymlink` entries it calls `fs.ReadLink(fsys, path)` to get the link target and passes that target *verbatim* to `Symlink(target, newPath)` with no validation that the target stays inside `dir`. This mirrors the Kata Containers CopyFile bug: the *destination* location is checked/localized, but the symlink *target* (the "data" that determines what the link points to) is never checked, so an attacker-controlled filesystem (e.g., a hostile archive exposed via a custom `fs.FS`, such as a `zip.Reader`-derived wrapper) can plant a symlink anywhere on the host filesystem via `newPath`, and any code that subsequently reads/writes through the copied tree can be redirected outside `dir`.

### Finding Description
- Entry point: `os.CopyFS(dir string, fsys fs.FS)` in `src/os/dir.go`.
- The walk callback computes `fpath, err := filepathlite.Localize(path)` and `newPath := joinPath(dir, fpath)` — this only validates/sanitizes the *name* of the entry being materialized (the write location), analogous to Kata's `check_directory_traversal(input.path)` / regex match against `cpath`.
- For `case ModeSymlink`: `target, err := fs.ReadLink(fsys, path); return Symlink(target, newPath)` — `target` is taken directly from the (untrusted) `fs.FS` implementation and is never checked to be relative-and-contained, non-absolute, or free of `..` traversal, exactly like Kata's unchecked `data` field of `CopyFileRequest` that specifies the symlink target. [1](#0-0) 
- Sink: the created symlink on disk points wherever the attacker's `fsys` says, e.g. `/etc/passwd`, `../../../../root/.ssh`, or any absolute path. Because `CopyFS`'s own doc states "Symbolic links in dir are followed" for pre-existing links, and later `case 0` entries do `OpenFile(newPath, O_CREATE|O_EXCL|O_WRONLY, ...)` for regular files, a maliciously ordered `fsys` (symlink entry followed by a same-named nested "file" entry consumed by a directory-mode symlink) or any later consumer opening files inside `dir` through the tree can be redirected through the planted symlink to write/read outside the intended destination tree. [2](#0-1) 

### Impact Explanation
If an application uses `os.CopyFS` to extract/materialize an untrusted filesystem (e.g., a downloaded module, archive-backed `fs.FS`, or `zip.Reader`) into a directory it believes is sandboxed, a malicious archive can create a symlink escaping `dir`. Depending on how the destination tree is subsequently consumed (read, executed, or written to), this can lead to disclosure or corruption of files outside the intended directory — a material file write / integrity issue, matching CWE-61 (link following) and the same class as the reported Kata advisory (C:H/I:L style impact). This would likely be assessed on Go's PUBLIC track as a documentation/behavior hardening issue for `os.CopyFS`, since the target sanitization gap is real but requires an application to copy from an untrusted `fs.FS`.

### Likelihood Explanation
Victim workflow: any Go program that calls `os.CopyFS(dir, fsys)` where `fsys` is derived from unstrusted input (a downloaded archive, an in-memory `fs.FS` built from network-fetched data, etc.) is affected. The attacker only needs to control the contents of the `fs.FS` (e.g., craft a zip/tar-like archive with a symlink entry whose target is absolute or contains `..`), which is a normal "malicious archive consumed by a normal victim workflow" scenario, not a privileged or host-control premise.

### Recommendation
In `os.CopyFS`, validate the `target` returned by `fs.ReadLink` before calling `Symlink`: reject absolute targets and reject relative targets that, once resolved against `newPath`'s directory, escape `dir` (similar to the traversal check the Kata policy tries but fails to apply to the symlink target). Alternatively, document loudly (and provide an opt-out/opt-in flag) that `CopyFS` does not sanitize symlink targets from `fsys`, so callers must not use it with untrusted filesystems, or refuse to create symlinks whose target resolves outside `dir`.

### Proof of Concept
```go
package os_test

import (
	"io/fs"
	"os"
	"path/filepath"
	"testing"
	"testing/fstest"
)

// TestCopyFS_SymlinkEscape demonstrates that os.CopyFS does not validate
// symlink targets coming from an untrusted fs.FS, allowing a planted
// symlink to point outside the destination directory.
func TestCopyFS_SymlinkEscape(t *testing.T) {
	dst := t.TempDir()

	// Attacker-controlled fs.FS: a symlink named "evil" whose target
	// is an absolute path outside dst (e.g. pointing at a sensitive file).
	target := filepath.Join(t.TempDir(), "outside-target")
	if err := os.WriteFile(target, []byte("secret"), 0644); err != nil {
		t.Fatal(err)
	}

	fsys := fstest.MapFS{
		"evil": &fstest.MapFile{
			Mode: fs.ModeSymlink,
			Data: []byte(target), // absolute path, no containment check
		},
	}

	if err := os.CopyFS(dst, fsys); err != nil {
		t.Fatalf("CopyFS failed: %v", err)
	}

	link := filepath.Join(dst, "evil")
	resolved, err := os.Readlink(link)
	if err != nil {
		t.Fatal(err)
	}

	// BUG: the symlink target escapes dst entirely instead of being
	// rejected or contained.
	if resolved == target {
		t.Fatalf("os.CopyFS created a symlink pointing outside destination dir: %s -> %s", link, resolved)
	}
}
```
Expected (buggy) result: the test fails its containment assertion because `os.CopyFS` happily creates `dst/evil -> <absolute path outside dst>`, confirming the symlink-target sanitization gap analogous to the Kata `CopyFile` policy subversion.

func CopyFS(dir string, fsys fs.FS) error {
	return fs.WalkDir(fsys, ".", func(path string, d fs.DirEntry, err error) error {
		if err != nil {
			return err
		}

		fpath, err := filepathlite.Localize(path)
		if err != nil {
			return err
		}
		newPath := joinPath(dir, fpath)

		switch d.Type() {
		case ModeDir:
			return MkdirAll(newPath, 0777)
		case ModeSymlink:
			target, err := fs.ReadLink(fsys, path)
			if err != nil {
				return err
			}
			return Symlink(target, newPath)
