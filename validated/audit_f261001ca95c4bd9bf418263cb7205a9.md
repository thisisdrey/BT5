### Title
Unsanitized attacker-controlled length used directly as array-allocation size in BatchValidateSign precompile - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `BatchValidateSign` precompiled contract (address callable from any TVM contract via `CALL`) parses ABI-encoded input and extracts a signature-count field directly from attacker-supplied call data, then uses it unsanitized as the size argument to array allocation, mirroring the CHICKEN Scheme CVE-2017-6949 pattern where an unsanitized size value from user input is passed straight to an allocation primitive.

### Finding Description
In `extractBytesArray` / `extractBytes32Array` / `extractSigArray`, the `len` value is read directly from the ABI-encoded call data (`words[offset].intValueSafe()`) and used immediately as the size of a `byte[][]` allocation, with no upper bound: [1](#0-0) 

The `sigArraySize`/`addrArraySize` sanity check (`> MAX_SIZE`) that would bound this is only performed when `VMConfig.allowTvmSelfdestructRestriction()` is enabled, and even then only guards the `extractSigArray`/`extractBytes32Array` calls, not the legacy `extractBytesArray` path taken when that feature flag is off: [2](#0-1) 

This is the same bug class as CVE-2017-6949: a length taken from untrusted input is passed unsanitized as the size argument to a memory-allocation call (`malloc()` in CHICKEN Scheme, `new byte[len][]` here), allowing arbitrarily large or negative sizes to reach the allocator.

### Impact Explanation
An attacker can craft a contract call to the `BatchValidateSign` precompile address with a crafted ABI payload where the length word is close to `Integer.MAX_VALUE`. This triggers allocation of a huge `byte[][]` array (each element reference costing 4-8 bytes, so a few billion entries can request multi-gigabyte allocations), which can throw `OutOfMemoryError`/`NegativeArraySizeException`. The outer `execute()` wraps `doExecute()` in a `catch (Throwable t)` handler, which mitigates a hard node crash by swallowing the error and returning a zeroed result: [3](#0-2)  However, catching `OutOfMemoryError` in the JVM is inherently unreliable — heap exhaustion can affect concurrently executing transactions/threads in the same node process before or during the catch, degrading node availability under repeated invocation from a single or few transactions.

### Likelihood Explanation
Reaching this code only requires deploying/calling a contract that issues a `CALL`/`STATICCALL` to the `BatchValidateSign` precompile address with attacker-chosen call data — no special privileges, no reliance on malicious SR/witness/node behavior. The gating condition (`VMConfig.allowTvmSelfdestructRestriction()` being disabled) determines whether the bounded (`extractSigArray`) or unbounded (`extractBytesArray`) code path executes; I could not verify from the available index whether this flag is enabled by default on current mainnet/testnet hard-fork configuration, which affects real-world exploitability.

### Recommendation
Bound `len` in `extractBytesArray`, `extractBytes32Array`, and `extractSigArray` to a small constant (e.g., the existing `MAX_SIZE = 16`) unconditionally, before allocation, regardless of the `allowTvmSelfdestructRestriction` feature flag. Validate `len >= 0` and `len * WORD_SIZE` bounds against `data.length` before allocating.

### Proof of Concept
1. Deploy a contract that performs a low-level `call` to the `BatchValidateSign` precompile address.
2. Construct call data as raw ABI words matching the expected layout (`hash`, offset word 1 → signatures array, offset word 2 → addresses array), but set the "array length" word at the signatures-array offset to a very large value (e.g., `0x7FFFFFFF`).
3. Ensure `VMConfig.allowTvmSelfdestructRestriction()` is not active (older/default config), so the `MAX_SIZE` check at [4](#0-3)  is skipped and `extractBytesArray` is invoked directly.
4. Observe `new byte[len][]` at [5](#0-4)  attempting a massive allocation, causing memory pressure/`OutOfMemoryError` on the executing node.

**Uncertainty note:** I was unable to confirm within the indexed codebase (i) the current default value of `VMConfig.allowTvmSelfdestructRestriction()` on production networks, and (ii) the exact behavior of `DataWord.intValueSafe()` for out-of-int-range values (clamp vs. wrap), since the `DataWord.java` file's implementation of that method was not returned by search despite being referenced elsewhere. Confirming these would require a full Devin session with direct file access to validate exploitability precisely.

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
