### Title
No Two-Step Ownership/Permission Transfer in `AccountPermissionUpdateContract` Allows Irrecoverable Loss of Account Control - (File: actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java)

### Summary
`AccountPermissionUpdateActuator` lets an account owner atomically overwrite the account's `Owner`, `Witness`, and `Active` permissions in a single signed transaction, with no acknowledgment or acceptance step from the newly designated key holder(s). This mirrors the reported `CrossDomainOwnable3.transferOwnership()` pattern: ownership/permission control can be handed to a new address in one step, and if that address is invalid, mistyped, or not actually controlled by anyone, the account permanently loses the ability to satisfy its own `Owner` permission threshold.

### Finding Description
`AccountPermissionUpdateActuator.execute()` unconditionally replaces the account's stored permissions with whatever the caller supplies: [1](#0-0) 

`validate()` (and the helper `checkPermission()`) only checks structural correctness — key count bounds, address format validity via `DecodeUtil.addressValid`, weight/threshold arithmetic, and permission-name length: [2](#0-1) [3](#0-2) 

Nowhere does the actuator verify that the new `Owner`/`Active`/`Witness` keys are reachable, controllable, or have acknowledged the change (e.g., via a co-signature from the new key, or a pending/accept two-step flow). Once the transaction is applied, `accountStore.put(ownerAddress, account)` persists the new permission set as the sole source of authority for that account. Any subsequent `AccountPermissionUpdateContract` (or any contract requiring the `Owner`/relevant `Active` permission) is validated purely against the newly stored `Permission` via `TransactionCapsule.validateSignature()` / `checkWeight()`: [4](#0-3) 

If the owner supplies a syntactically-valid but uncontrolled address (typo, wrong network prefix within valid format, address generated without a known private key, or an address whose key is later lost) as the sole/majority-weight key of the new `Owner` permission, there is no path to recover: no `acceptOwnership()`-style function exists, and no old key retains override authority once the update is applied.

### Impact Explanation
Unlike a simple end-user mistake with a `TransferContract`, permission loss here is systemic: it disables the account's ability to issue *any* further `AccountPermissionUpdateContract`, `AccountUpdateContract`, or any contract type gated by the corrupted `Active`/`Owner` permission bitmap. This permanently freezes control over the account's assets and any contracts/resources whose management requires that permission (e.g., withdrawing balances, unfreezing resources, asset management, permission changes) — a permanent freezing-of-funds/loss-of-control condition matching the "No Transfer of Ownership" bug class. This is reachable by any single unprivileged, self-signed transaction from the account owner; no special privilege beyond normal account control is needed to trigger it (accidentally or via social engineering/phishing of a value proposed as a "new key").

### Likelihood Explanation
Likelihood is user-error/social-engineering driven rather than trivially exploitable by a third party without owner cooperation, since only the current permission holder(s) meeting the existing threshold can submit `AccountPermissionUpdateContract`. However, the actuator provides zero technical safeguard against catastrophic misconfiguration (unlike a two-step accept pattern), and TRON's own documentation/tooling exposes this contract broadly via `/wallet/accountpermissionupdate`-style APIs, making the mistake easy to make via API/CLI/dApp integrations. Given the audit precedent (analogous Optimism finding rated Medium) and the direct absence of any acceptance/verification step, this is assessed as Medium likelihood/impact combination.

### Recommendation
Introduce a two-step permission/ownership update flow for `AccountPermissionUpdateContract`:
1. First transaction stages proposed `Owner`/`Witness`/`Active` permissions (e.g., in a pending-permission field on `AccountCapsule`).
2. A second transaction, signed by keys satisfying the *proposed* new permission's threshold, must explicitly "accept" and commit the change.
Alternatively, at minimum require that any newly introduced address in the `Owner` permission co-sign the same transaction (proof-of-control) before the update actuator commits the change, preventing accidental or malicious lockout via a single-sided broadcast transaction.

### Proof of Concept
1. Attacker/careless owner controls account `A` with default `Owner` permission (`threshold=1`, single key = `A`).
2. Owner constructs `AccountPermissionUpdateContract` with `owner_address = A`, new `Owner` permission = `{threshold: 1, keys: [{address: X, weight: 1}]}` where `X` is a syntactically valid (`DecodeUtil.addressValid` passes) but uncontrolled/mistyped address, plus a valid `Active` permission list (required to pass `validate()`).
3. Owner signs and broadcasts the transaction with their current (still-valid) key satisfying the old `Owner` permission threshold.
4. `AccountPermissionUpdateActuator.execute()` at [5](#0-4)  commits the new permission unconditionally.
5. From this point on, `TransactionCapsule.validateSignature()` [6](#0-5)  requires a signature from `X` to satisfy the `Owner` permission for any further permission-gated action on account `A`, but no one holds `X`'s private key — permanently locking the account's `Owner`-gated capabilities.

  public static boolean validateSignature(Transaction transaction,
      byte[] hash, AccountStore accountStore, DynamicPropertiesStore dynamicPropertiesStore)
      throws PermissionException, SignatureException, SignatureFormatException {
    Transaction.Contract contract = transaction.getRawData().getContractList().get(0);
    int permissionId = contract.getPermissionId();
    byte[] owner = getOwner(contract);
    AccountCapsule account = accountStore.get(owner);
    Permission permission = null;
    if (account == null) {
      if (permissionId == 0) {
        permission = AccountCapsule.getDefaultPermission(ByteString.copyFrom(owner));
      }
      if (permissionId == 2) {
        permission = AccountCapsule
            .createDefaultActivePermission(ByteString.copyFrom(owner), dynamicPropertiesStore);
      }
    } else {
      permission = account.getPermissionById(permissionId);
    }
    if (permission == null) {
      throw new PermissionException("permission isn't exit");
    }
    checkPermission(permissionId, permission, contract);
    long weight = checkWeight(permission, transaction.getSignatureList(), hash, null);
    if (weight >= permission.getThreshold()) {
      return true;
    }
    return false;
  }
