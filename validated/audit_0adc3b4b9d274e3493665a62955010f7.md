## Analysis: Blind SSRF Analog in Gitaly's `FindRemoteRepository` RPC

The reported bug is a blind SSRF where a server-side HTTP client's differential responses ("timeout/host unreachable" vs. actual HTTP response) are used as an oracle to fingerprint open vs. closed internal ports. Gitaly has a directly analogous, unprivileged pattern in `FindRemoteRepository`. [1](#0-0) 

### Title
Blind SSRF port/service oracle via `FindRemoteRepository`'s unrestricted `remote` URL field - (File: internal/gitaly/service/remote/find_remote_repository.go)

### Summary
`RemoteService.FindRemoteRepository` accepts an attacker-supplied `remote` string and directly passes it as the target of `git ls-remote <remote> HEAD`, with no `resolved_address`/DNS-rebinding mitigation, no scheme allow-list, and no destination restriction, unlike sibling RPCs (`FindRemoteRootRef`, `FetchRemote`, `CreateRepositoryFromURL`, `UpdateRemoteMirror`) that at least support a `resolved_address` field for pinning.

### Finding Description
`FindRemoteRepository` only validates that `remote` is non-empty before invoking `git-ls-remote(1)` against it: [2](#0-1) 

The RPC then returns a differentiated boolean response depending on whether the target responded with a recognizable Git `HEAD` ref: [3](#0-2) 

Contrast this with `FindRemoteRootRef`, `FetchRemote`, `CreateRepositoryFromURL`, and `UpdateRemoteMirror`, which all accept an optional `resolved_address` to pin the DNS-resolved IP and mitigate DNS rebinding: [4](#0-3) [5](#0-4) 

The proto explicitly documents that `FindRemoteRepositoryRequest` is scoped at `STORAGE` level rather than `REPOSITORY`, meaning it is reachable without needing access to any specific target repository — only storage-level access: [6](#0-5) 

Because `git-ls-remote` will attempt a TCP connection to whatever host/port is embedded in the URL (`http://`, `https://`, `git://`, or SCP-style `ssh://` syntax), and Gitaly surfaces a binary `exists` signal (and, via error responses, further differentiation between connection failures, resets, and protocol failures), this endpoint functions as a blind SSRF oracle nearly identical in mechanics to the HackerOne report: the requester cannot see raw output, but the differential response (`Exists: true/false`, or gRPC error vs. success) reveals whether a given internal `host:port` is reachable and speaks (or can be coerced to look like) a Git-aware or arbitrary TCP service.

### Impact Explanation
An actor with only storage-level gRPC access (no target-repository permission) can use `FindRemoteRepository` to:
- Enumerate reachable internal hosts/ports (network/port scanning of Gitaly's internal network segment, including metadata services, internal admin panels, or other cluster nodes) by observing whether the RPC returns `Exists: true`, `Exists: false`, or an error.
- Because `git-ls-remote` supports `ssh://`, `git://`, and scp-like syntax in addition to `http(s)://`, the blast radius is broader than a pure HTTP SSRF: it can also probe SSH and the plaintext `git://` protocol port (9418), potentially interacting with non-Git services that happen to be listening there.

### Likelihood Explanation
This is directly reachable by any client permitted to call storage-scoped RPCs (used by GitLab's "import project by URL"/mirror-validation workflows), with no privileged access to the target repository required. No malicious peer, MITM, or leaked credentials are needed — a single crafted RPC field (`remote`) is sufficient, matching the reported bug class exactly (blind SSRF via a URL used for existence-checking).

### Recommendation
- Add the same `resolved_address` pinning pattern already used by `FindRemoteRootRef`/`FetchRemote`/`CreateRepositoryFromURL` to `FindRemoteRepositoryRequest`, requiring callers (GitLab Rails) to pre-resolve and validate the destination before Gitaly connects.
- Alternatively/additionally, restrict `FindRemoteRepository`'s destination to schemes and network ranges consistent with the application's outbound-request allow-list, or move URL validation earlier and enforce it in Gitaly rather than solely trusting the caller.

### Proof of Concept
1. As a client with `STORAGE`-scope access to a Gitaly node, call:
```
FindRemoteRepository(remote="http://<internal-host>:<port>/x.git", storage_name="<storage>")
```
2. Vary `<port>` across a target range (e.g., 22, 80, 443, 6379, 9200, 8080) on an internal-only host.
3. Observe the response: connection-refused/timeout paths return quickly with `Exists: false`/error, whereas a listening HTTP(S) service will produce a distinguishable delay/response (e.g., `404`/`400` from `git-ls-remote`'s HTTP smart protocol negotiation) even though it never returns `Exists: true` for a non-Git service — the differential timing/error behavior is sufficient to fingerprint open ports, exactly as in the original report's WARNING vs FAILURE distinction.

func (s *server) FindRemoteRepository(ctx context.Context, req *gitalypb.FindRemoteRepositoryRequest) (*gitalypb.FindRemoteRepositoryResponse, error) {
	if req.GetRemote() == "" {
		return nil, structerr.NewInvalidArgument("empty remote can't be checked.")
	}

	var output bytes.Buffer
	cmd, err := s.gitCmdFactory.NewWithoutRepo(ctx,
		gitcmd.Command{
			Name: "ls-remote",
			Args: []string{
				req.GetRemote(),
				"HEAD",
			},
		},
		gitcmd.WithStdout(&output),
	)
	if err != nil {
		return nil, structerr.NewInternal("error executing git command: %w", err)
	}

	if err := cmd.Wait(); err != nil {
		return &gitalypb.FindRemoteRepositoryResponse{Exists: false}, nil
	}

	// The output of git-ls-remote is expected to be of the format:
	//
	//	58fbff2e0d3b620f591a748c158799ead87b51cd	HEAD\n
	objectID, refname, ok := bytes.Cut(output.Bytes(), []byte("\t"))
	if !ok {
		return &gitalypb.FindRemoteRepositoryResponse{Exists: false}, nil
	}

	// We've asked for HEAD, so the refname should match that.
	if !bytes.Equal(refname, []byte("HEAD\n")) {
		return &gitalypb.FindRemoteRepositoryResponse{Exists: false}, nil
	}

	// We have no way to ask the remote's object format via git-ls-remote(1), so all we can do
	// is to verify that the object hash matches something we know.
	switch len(objectID) {
	case git.ObjectHashSHA1.EncodedLen():
		return &gitalypb.FindRemoteRepositoryResponse{Exists: true}, nil
	case git.ObjectHashSHA256.EncodedLen():
		return &gitalypb.FindRemoteRepositoryResponse{Exists: true}, nil
	default:
		return &gitalypb.FindRemoteRepositoryResponse{Exists: false}, nil
	}

// FindRemoteRepositoryRequest is a request for the FindRemoteRepository RPC.
message FindRemoteRepositoryRequest {
  // remote is the remote repository being checked. Because this RPC is not executed within a
  // repository, the remote parameter must specify a valid Git URL for the targeted repository.
  string remote = 1;
  // storage_name is used to redirect request to proper storage where it can be handled.
  // As of now it doesn't matter what storage will be used, but it still must be a valid.
  // For more details: https://gitlab.com/gitlab-org/gitaly/-/issues/2442
  string storage_name = 2 [(storage)=true];
}

// FindRemoteRepositoryResponse is a response for the FindRemoteRepository RPC. This might throw a
// GRPC Unavailable code to signal the request failure is transient.
message FindRemoteRepositoryResponse {
  // exists specifies if the remote repository exists.
  bool exists = 1;
}
