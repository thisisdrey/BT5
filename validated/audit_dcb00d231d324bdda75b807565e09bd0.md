### Title
Signature Malleability Enables Duplicate-Signer Weight Counting in `ValidateMultiSign` Precompile - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `ValidateMultiSign` TVM precompile (address `0x0a`) recovers signer addresses from raw ECDSA signatures via `recoverAddrBySign`, which — like standard `ecrecover` — accepts both the canonical low-`s` and the malleable high-`s` (`N - s`) form of the same signature as valid, distinct byte sequences. The weight-accumulation loop only skips a signature as "already used" when the exact recovered-address *and* exact signature bytes have both been seen before; it does not de-duplicate by recovered address alone when the signature bytes differ. This allows a single private key to be counted twice toward a multisig permission's weight threshold simply by submitting the original signature and its malleable variant.

### Finding Description
`recoverAddrBySign` builds a `SignatureInterface` from the raw `(r, s, v)` components and only calls `signature.validateComponents()`, which enforces range constraints on `r`/`s`/`v` but does not enforce the canonical (low-`s`) form: [1](#0-0) 

Because ECDSA signatures are malleable, for any valid `(r, s, v)` there exists a second valid signature `(r, N-s, v')` that recovers to the exact same address. Both signatures are byte-distinct.

The de-duplication check only `continue`s (skips weight addition) when **both** `recoveredAddr` and the exact `sign` bytes were previously seen. If an attacker supplies the original signature and then its malleable counterpart, `recoveredAddr` is flagged as already present, but the nested `matrixContains(executedSignList, sign)` check fails (different bytes), so execution falls through and adds `TransactionCapsule.getWeight(permission, recoveredAddr)` a second time for the same key.

This is directly analogous to the reported class of bug (unchecked `ecrecover`-based signature verification permitting multiple valid signatures for the same signer/message), except here it is reachable via a live, unauthenticated, general-purpose precompile rather than an unused Solidity helper.

### Impact Explanation
`ValidateMultiSign` is a documented TVM precompile intended for any deployed smart contract to implement account-permission-gated logic (e.g., custom multisig wallets, escrow, governance contracts) by checking whether a set of supplied signatures meets an account's permission threshold. If a contract relies on this precompile to gate a sensitive operation (fund transfer, account permission change, etc.) requiring `N` independent co-signers, an attacker who controls only one of the required keys (with sufficient partial weight) can synthesize a second, malleable variant of their own signature to inflate their counted weight and satisfy the `permission.getThreshold()` check without cooperation from the other legitimate co-signers. This is an unauthorized account operation / theft-of-funds primitive: a threshold-based access control can be bypassed by a single colluding or compromised key.

### Likelihood Explanation
Exploitation requires only: (1) knowledge of one valid signature under the target permission (which the "attacker" key holder trivially has, since they signed it), and (2) simple arithmetic (`s' = N - s`, flip recovery id) to derive the malleable counterpart — no cryptographic secret is needed. The precompile is callable from any contract via ordinary `CALL`/`STATICCALL` from any transaction, with no special privilege required. Exploitability depends on higher-level contracts actually using `ValidateMultiSign` to gate value-transferring or permission-changing logic with a >1 threshold, which is a realistic usage pattern for TRON smart contract multisig/account-abstraction wallets.

### Recommendation
In `ValidateMultiSign.execute` (and equally in `BatchValidateSign.execute`, which shares the same signature-recovery path via `recoverAddrBySign`), de-duplicate purely by `recoveredAddr` regardless of the exact signature bytes supplied — i.e., `continue`/skip weight addition whenever `recoveredAddr` has already contributed weight, instead of additionally requiring exact signature-byte equality: [3](#0-2) 
Additionally, `recoverAddrBySign`/`validateComponents()` should reject non-canonical (high-`s`) signatures outright, consistent with the OpenZeppelin `ECDSA` recommendation cited in the external report, to prevent malleable variants from validating at all.

### Proof of Concept
1. A contract-managed account has a permission with threshold `T` and two keys, `K1` (weight `w1 >= T`) and `K2` (weight `w2`), such that `w1 < T` alone but the design intends `K1` to need `K2`'s cooperation, or more simply, a permission where a single key's weight is intentionally capped below threshold and multiple *distinct* signatures are required.
2. Attacker holding only `K1` signs the message once, obtaining `(r, s, v)`, then computes the malleable counterpart `(r, N-s, v')` without needing the private key again.
3. Attacker calls a contract that invokes the `ValidateMultiSign` precompile (`0x0a`) with `signatures = [(r,s,v), (r,N-s,v')]`.
4. Inside `execute`, the first signature recovers `K1`'s address and adds `w1` to `totalWeight`; the second signature recovers the same address again but with different byte content, bypasses the `continue` skip, and adds `w1` again: [4](#0-3) 
5. `totalWeight` becomes `2*w1`, which can now meet or exceed `permission.getThreshold()` even though only one distinct signer actually authorized the action, returning `true`/`dataOne()` from the precompile and allowing the calling contract to proceed as if the multisig requirement were satisfied.

    byte[] out = null;

      return new byte[0];
    }
    try {
      Rsv rsv = Rsv.fromSignature(sign);
      SignatureInterface signature = SignUtils.fromComponents(rsv.getR(), rsv.getS(), rsv.getV(),
          CommonParameter.getInstance().isECKeyCryptoEngine());
      if (signature.validateComponents()) {
        out = SignUtils.signatureToAddress(hash, signature,
            CommonParameter.getInstance().isECKeyCryptoEngine());
      }
    } catch (Throwable any) {
      logger.info("ECRecover error", any.getMessage());
    }
    return out;
  }
