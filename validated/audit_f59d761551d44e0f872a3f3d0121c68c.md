### Title
Unvalidated attacker-controlled array length in precompiled-contract ABI unpacking helpers can throw uncontrolled `ArrayIndexOutOfBoundsException`/`OutOfMemoryError` - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
`PrecompiledContracts` contains several helper methods (`extractBytesArray`, `extractBytes32Array`, `extractSigArray`) that decode a caller-supplied ABI-encoded byte array by first reading a "length" word directly from attacker-controlled call data and then using that length to drive loops that index into the `words[]`/`data` buffers, without validating the length against the real size of those buffers. This mirrors the Pillow bug class: an untrusted "count"/structure field is trusted to size subsequent buffer accesses instead of being validated against the actual allocated buffer, leading to out-of-bounds access or oversized allocation.

### Finding Description
`extractBytesArray` and `extractSigArray` read `len = words[offset].intValueSafe()` from the caller-controlled input `data` and then loop `i` from `0` to `len`, accessing `words[offset + i + 1]` and `data` at computed offsets: [1](#0-0) [2](#0-1) 

`extractBytes32Array` does the same but does not even perform the `offset > words.length - 1` guard that the other two methods have before reading `words[offset]`: [3](#0-2) 

In all three cases, `len` is taken directly from calldata (via `DataWord.intValueSafe()`) with no check that `len` is consistent with the actual size of the `words` array (which is derived from the real length of the transaction's call data). If a caller supplies a large or crafted `len` value that does not match the actual data length, the loop will index past the end of `words`/`data`, causing an `ArrayIndexOutOfBoundsException`, or the intermediate `new byte[len][]` allocation (in `extractBytesArray`/`extractSigArray`) can be driven arbitrarily large, causing excessive heap allocation/`OutOfMemoryError`. This is analogous to the Pillow issue where a nested/malformed coordinate structure was trusted to be a flat pair and unpacked past the allocated buffer — here, an untrusted length header is trusted to describe the real array/byte-buffer extent without bounds verification.

### Impact Explanation
These helpers are used by precompiled-contract implementations that participate in TVM execution (e.g., shielded/verify-proof style precompiles that decode arrays of hashes/signatures from calldata). An attacker who can trigger a contract call reaching one of these precompiles supplies fully attacker-controlled `data`, and can craft a length word that is inconsistent with the actual calldata size. If the resulting exception (`ArrayIndexOutOfBoundsException`) or `OutOfMemoryError` is not caught cleanly by the surrounding TVM dispatch/exception handling, it can propagate and potentially crash or destabilize the node process handling the transaction — a "node crash or halt" outcome, which is within the accepted impact scope.

### Likelihood Explanation
Likelihood is uncertain because I was unable to confirm, within the available iterations, exactly which precompiled contract(s) invoke `extractBytesArray`/`extractBytes32Array`/`extractSigArray` and whether the TVM's top-level precompile dispatch already wraps `execute()` calls in a broad `try/catch (Throwable)` that would convert any such exception into a normal revert rather than a crash. If such a catch-all exists, this issue degrades to a contained revert (low impact); if it does not, it is a directly reachable, single-transaction-triggerable crash vector. This distinction could not be fully verified with the tools available in this session.

### Recommendation
Add explicit bounds validation of the decoded `len` against the actual size of `words`/`data` before using it to size allocations or drive loop indices in `extractBytesArray`, `extractBytes32Array`, and `extractSigArray`, and add the same `offset > words.length - 1` guard to `extractBytes32Array` that the sibling methods already have. Additionally, verify at the top-level precompiled-contract dispatch path that any exception thrown during `execute()` (including `ArrayIndexOutOfBoundsException` and `OutOfMemoryError`) is caught and converted into a graceful VM revert rather than propagating and destabilizing the node.

### Proof of Concept
Not independently verified end-to-end (caller chain and exception-handling behavior could not be confirmed with available tool calls). Conceptually: craft a contract call to a precompiled-contract address whose `execute(byte[] data)` path calls `extractBytesArray`/`extractSigArray`/`extractBytes32Array`, with `data` word at `offset` set to a very large integer (e.g., near `Integer.MAX_VALUE`) while the remainder of `data` is short/normal-sized calldata; this drives `new byte[len][]` toward an out-of-memory allocation or the subsequent loop to index past the actual `words`/`data` bounds.

    int len = words[offset].intValueSafe();
    byte[][] bytes32Array = new byte[len][];

      bytes32Array[i] = words[offset + i + 1].getData();

    }

  }
