## Analysis

The external report's core broken invariant is: **a value-moving ERC20-style call whose success/failure semantics are non-standard is trusted as ground truth for internal accounting, without validating that the actual amount moved matches the amount credited/debited.**

The closest live-scope analog is the `ERC20Transactor` used by Asset Hub's XCM configuration to move ERC20 tokens (contracts deployed under `pallet-revive`) into/out of XCM holding:

`ERC20Transactor::withdraw_asset_with_surplus` calls the `IERC20::transfer` function on the token contract for the exact requested `amount`, and — **regardless of what the contract actually moved** — credits `AssetsInHolding::new_from_fungible_credit(what.id.clone(), Box::new(Erc20Credit(amount)))` purely from the ABI-decoded `bool` success flag: [1](#0-0) 

The correlated deposit path calls `transfer` again from the `TransfersCheckingAccount` to the beneficiary for the same nominal `amount`, again trusting only the boolean return: [2](#0-1) 

The `Erc20Credit` imbalance type used to represent this value inside XCM holding explicitly documents that **"the actual balance constraints are enforced by the ERC20 smart contract itself rather than the runtime"**: [3](#0-2) 

This transactor is wired into Asset Hub Westend's production XCM configuration so that any ERC20 contract deployed via `pallet-revive` can be registered as an XCM-transactable asset: [4](#0-3) 

### Why this is the real gap (not the return-value decode, which is already handled)

Unlike the report's literal complaint, this code **does** correctly reject non-boolean returns and `false` returns (`abi_decode_returns_validate` + `did_revert()` checks, confirmed by the `smart_contract_does_not_return_bool_fails` test): [5](#0-4) 

The residual, un-mitigated variant of the bug class is: **a token that returns `true` but moves a different amount than requested** (fee-on-transfer / deflationary / rebasing ERC20s — a well-known non-standard-token category, the same family the report warns about). Because `withdraw_asset_with_surplus` and `deposit_asset_with_surplus` never compare `balanceOf(checking_account)` before/after against `amount`, the XCM holding register and the `TransfersCheckingAccount`'s real on-chain balance can silently diverge:

- On **withdraw**, if the token burns/taxes a portion, only `amount - fee` actually lands in `TransfersCheckingAccount`, but the code credits the *full* `amount` into `AssetsInHolding` — inflating value inside the XCM executor relative to what was actually escrowed.
- On **deposit**, the same call pattern debits the checking account nominally by `amount` while the beneficiary may receive less, and the transactor still reports `Ok(surplus)` (success) for the full amount.

Because the checking account is shared across all XCM operations for that asset (`TransfersCheckingAccount::get()`), repeatedly withdrawing fee-on-transfer tokens creates an accumulating deficit: the `AssetsInHolding`/onward-XCM-forwarded value exceeds what `TransfersCheckingAccount` can actually back, so a later, unrelated user's legitimate `deposit_asset` for the same asset can fail (checking account underfunded) — a form of value non-conservation and potential fund lock for other users of the same registered ERC20 asset, driven entirely by permissionless deployment/registration of a non-standard token contract, requiring no privileged actor.

## Impact / Likelihood

- **Impact:** Medium-High — breaks the "conserve value and settle exactly once" invariant for any parachain asset registered through `ERC20Transactor`; can strand legitimate holders' funds in the shared checking account once the backing balance is exhausted by fee-on-transfer tokens.
- **Likelihood:** Low-Medium — requires that a non-standard (fee-on-transfer/rebasing) ERC20 contract be registered as a transactable XCM asset for this transactor, which depends on asset-registration policy on the specific chain, but the transactor code itself provides no defense once such a contract is registered, and no privileged actor is needed to trigger the divergence (any holder of such a token can withdraw/deposit through XCM).

## Recommendation
Verify actual balance delta of `TransfersCheckingAccount` (via `balanceOf` before/after, as already implemented for `IERC20::Inspect::balance`) rather than trusting the boolean return value alone, and credit/debit `AssetsInHolding` with the *measured* delta, not the requested `amount`. Reject registration of, or explicitly disallow, non-conforming (fee-on-transfer/rebasing) ERC20 contracts for this transactor.

## Proof of Concept (conceptual)
1. Deploy an ERC20 contract whose `transfer` returns `true` but deducts a 5% fee from every transfer (burns it or sends to a fee sink), and register it as an XCM-transactable asset via `ERC20Transactor`.
2. User A executes an XCM program that `withdraw_asset`s 1000 units of this token. `withdraw_asset_with_surplus` calls `transfer(checking_account, 1000)`; only 950 actually lands in the checking account; `is_success == true`, so `AssetsInHolding` is credited 1000.
3. XCM `deposit_asset` for User A succeeds, transferring nominal 1000 from checking account to A (again taxed 5%, checking account debited by the same call), compounding the shortfall each round trip.
4. After repeated withdraw/deposit round trips, `TransfersCheckingAccount`'s real on-chain balance is depleted faster than the nominal ledger implies, causing subsequent unrelated users' `deposit_asset` calls for the same registered token to fail with `"ERC20 contract transfer failed"` due to insufficient checking-account balance — a chain-level, permissionless denial-of-service / fund-lock for all holders of that registered asset.

/// A minimal imbalance tracking type that holds an ERC20 token amount.
///
/// This type implements the necessary imbalance accounting traits but does not perform
/// runtime-level balance enforcement. It's used to track ERC20 token amounts within XCM
/// asset holdings, where the actual balance constraints are enforced by the ERC20 smart
/// contract itself rather than the runtime.
struct Erc20Credit(u128);
impl UnsafeConstructorDestructor<u128> for Erc20Credit {
	fn unsafe_clone(&self) -> Box<dyn ImbalanceAccounting<u128>> {
		Box::new(Erc20Credit(self.0))
	}
	fn forget_imbalance(&mut self) -> u128 {
		let amount = self.0;
		self.0 = 0;
		amount
	}
