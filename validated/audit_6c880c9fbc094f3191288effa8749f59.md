The `/v2/stackerdb/{address}/{contract}/chunks` endpoint is unauthenticated at the HTTP layer (no signature over the target contract itself is required to submit) and `try_replace_chunk`/`validate_received_chunk` verify only a per-slot signature that never binds to the StackerDB's contract identity.

### Title
Missing StackerDB contract-identity binding in `SlotMetadata` signature enables cross-StackerDB chunk replay - (File: `libstackerdb/src/libstackerdb.rs`)

### Summary
`SlotMetadata::auth_digest()` computes the signed digest over only `slot_id`, `slot_version`, and `data_hash`, omitting the `QualifiedContractIdentifier` (the specific StackerDB instance) that the chunk is destined for. Because slot ownership is scoped per-contract but the signature is not, a chunk legitimately signed and broadcast for StackerDB A can be replayed verbatim (same signature, slot id, slot version, data) against a different StackerDB B, and will pass `try_replace_chunk`'s signature check as long as the same signer address happens to own the identical `slot_id` in B. This is directly analogous to the reported bug class: a signed payload's hash/typehash omits a field that should have scoped the signature to a specific context (nonce/domain), breaking the intended equality between "authorized for X" and "accepted for X".

### Finding Description
`SlotMetadata::auth_digest()` at [1](#0-0)  hashes only `slot_id`, `slot_version`, and `data_hash`. `sign()`/`verify()` operate purely on this digest and a `StacksAddress` [2](#0-1) ; the destination StackerDB contract is never part of what is signed.

Slot ownership (`signer` address per slot) is stored and looked up per `QualifiedContractIdentifier` in `try_replace_chunk`, via `get_slot_validation(smart_contract, slot_desc.slot_id)`, and the returned signer is checked with `slot_desc.verify(&slot_validation.signer)` [3](#0-2) . Because `verify()` never looks at `smart_contract`, this check is satisfied by any signature that was ever produced for that address/slot_id/version/data_hash tuple in *any* StackerDB.

The unauthenticated HTTP write path `POST /v2/stackerdb/:address/:contract/chunks`, handled by `RPCPostStackerDBChunkRequestHandler`, accepts the `contract_identifier` from the URL and the `StackerDBChunkData` (containing the reused signature) from the body with no additional binding check [4](#0-3) , then calls `tx.try_replace_chunk(&contract_identifier, ...)` directly [5](#0-4) .

The same missing binding also affects the gossip/relay path: `validate_received_chunk` looks up `get_slot_signer(smart_contract_id, data.slot_id)` and then calls `slot_metadata.verify(&addr)` [6](#0-5) , again never checking that the signature was produced for `smart_contract_id`. This function backs both `PeerNetwork::handle_unsolicited_StackerDBPushChunk` and `StackerDBSync::validate_downloaded_chunk`, so a replayed cross-contract chunk can also be relayed onward through node gossip.

### Impact Explanation
This breaks the equality "signature valid for slot S ⇒ authorized write to *this* StackerDB" the same way the missing nonce in `LISTING_TYPEHASH` broke "signature valid for listing L ⇒ authorized sale of L" in the external report. Any remote, unprivileged party who observes a validly-signed `StackerDBChunkData` (trivial, since chunks are broadcast/queryable) can replay it into a different StackerDB contract where the same signer address is assigned the same `slot_id`, causing an unauthorized write to that DB's slot — a write the signer never authorized for that specific StackerDB/context. Multiple production StackerDB contracts (e.g. per-reward-cycle `signers-*` or other slot-indexed contracts) can plausibly assign the same signer to the same slot index across contracts, since slot ordering is frequently derived deterministically from the same signer set. This matches the "unauthenticated/unauthorized write to state or StackerDB" and "network-wide propagation of forged data" Critical-tier impacts.

### Likelihood Explanation
Likelihood is Medium: the attacker needs no keys and only needs to capture one legitimately broadcast chunk (chunks are gossiped to all replicating peers and queryable via `list_chunks`), but the attack requires that the target StackerDB happens to assign the identical signer address to the identical `slot_id`, and that the version/staleness constraints (`slot_version` > current version in target DB, `<= max_writes`) line up in the target DB. This is a plausible but configuration-dependent precondition rather than universally guaranteed.

### Recommendation
Bind the signature to the specific StackerDB instance by including the `QualifiedContractIdentifier` (or an equivalent stable contract-scoped domain separator) in `SlotMetadata::auth_digest()`, and thread the contract identifier through `sign()`/`verify()` so the digest committed to by the signer is `(smart_contract_id, slot_id, slot_version, data_hash)`. Update `try_replace_chunk`, `validate_received_chunk`, and any related test vectors in `libstackerdb/src/tests/mod.rs` and `stackslib/src/net/stackerdb/tests/db.rs` accordingly to pass the contract identifier into the signature check.

### Proof of Concept
1. Signer `S` owns slot `0` in StackerDB `A` and also owns slot `0` in StackerDB `B` (e.g. two contracts using the same ordered signer set).
2. `S` legitimately signs and pushes `StackerDBChunkData { slot_id: 0, slot_version: 5, sig, data }` for `A`; the node accepts it via `try_replace_chunk(&A, ...)` per [7](#0-6)  and gossips it to peers.
3. An unprivileged attacker observes this chunk (via gossip or `GET /v2/stackerdb/.../chunks/0`) and re-POSTs the identical `slot_id`, `slot_version`, `sig`, and `data` to `POST /v2/stackerdb/{B's address}/{B's contract}/chunks` as handled by [8](#0-7) .
4. Because `SlotMetadata::verify()` only checks `(slot_id, slot_version, data_hash)` against the recovered address [9](#0-8)  and never checks which contract it was signed for, `try_replace_chunk` for `B` succeeds (assuming `B`'s current slot-0 version is `< 5` and `5 <= B.max_writes`), writing data into `B` that `S` never authorized for `B`.

    pub fn sign(&mut self, privkey: &StacksPrivateKey) -> Result<(), Error> {
        let auth_digest = self.auth_digest();
        let sig = privkey
            .sign(&auth_digest.0)
            .map_err(|se| Error::SigningError(se.to_string()))?;

        self.signature = sig;
        Ok(())
    }

    /// Note that the address version is ignored.

            &self.signature,
