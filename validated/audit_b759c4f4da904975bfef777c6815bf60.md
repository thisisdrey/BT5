Based on my investigation, I found a concrete analog in `third_party/ijar/zip.cc`'s central directory parser, which lacks the bounds checking present in its local-file-header counterpart.

### Title
Heap buffer over-read in ijar's ZIP central directory parser due to missing bounds checks - (`third_party/ijar/zip.cc`)

### Summary
`InputZipFile::ProcessCentralDirEntry` reads a central directory entry from an mmap'd ZIP file (an interface JAR input) and copies `file_name_length` bytes from an attacker-influenced offset into a fixed buffer, without ever validating that these attacker-controlled length fields stay within the bounds of the mapped input file. [1](#0-0)  This mirrors the ANGLE heap-overflow class: parsing attacker-supplied structured binary data (a ZIP/JAR file) and trusting length fields to walk a buffer without a remaining-bytes check.

### Finding Description
`InputZipFile::ProcessLocalFileEntry` (used for local file headers) explicitly guards every variable-length read with `EnsureRemaining()`, which checks that `n <= input_file_->Length() - offset` before consuming file-name and extra-field bytes. [2](#0-1) 

By contrast, `ProcessCentralDirEntry`, used to parse the central directory (`InputZipFile::ProcessNext` calls it for every entry), performs no such check at all:

```
p += 16;
*compressed_size = get_u4le(p);
*uncompressed_size = get_u4le(p);
u2 file_name_length = get_u2le(p);
u2 extra_field_length = get_u2le(p);
u2 file_comment_length = get_u2le(p);
...
memcpy(reinterpret_cast<void*>(filename), p, len);
...
p += file_name_length;
const u1 *extra_p = p;
p += extra_field_length;
while (extra_p != p) {
  const u2 header_id = get_u2le(extra_p);
  const u2 data_size = get_u2le(extra_p);
  const u1 *extra = extra_p;
  extra_p += data_size;
  ...
}
p += file_comment_length;
``` [3](#0-2) 

Here `file_name_length`, `extra_field_length`, and `file_comment_length` are fully attacker-controlled 16-bit values read straight from the JAR's central directory bytes. There is no verification that `p + file_name_length`, `extra_p + data_size`, or `p + file_comment_length` remain inside `[zipdata_in_, zipdata_in_ + input_file_->Length())`. The `memcpy(filename, p, len)` at line 520 reads from `p` for `len` bytes — the write side is bounded by `filename_size` (`PATH_MAX`), but the *read* source `p` can already point near or past the end of the mmap'd region if a crafted central directory entry near the end of the file declares an oversized `file_name_length`. Similarly, the extra-field walk loop `while (extra_p != p)` can be driven arbitrarily far past the intended boundary if a crafted `data_size` causes `extra_p` to skip past `p` (an infinite/out-of-bounds walk reading and dereferencing `get_u2le`/`get_u8le` on unmapped memory), since there's no check that `extra_p <= p` on each iteration.

The invariant that should hold — "every field read from the ZIP is bounds-checked against the actual file length before being dereferenced" — is broken specifically for the central-directory path, even though the code explicitly does this for the local-file-header path just a few hundred lines away.

### Impact Explanation
An attacker who controls the contents of a ZIP/JAR file that Bazel's `ijar`/`zip.cc`-based tooling parses (e.g., a crafted interface-jar input or any binary consumed via `ZipExtractor::Create`) can trigger out-of-bounds reads past the end of the mmap'd input file. Depending on page alignment this can cause a SIGSEGV (crash/DoS) or, via the `memcpy`, leak adjacent heap/mapped memory into the `filename` buffer that is subsequently passed to `processor->Accept()`/`Process()` callbacks — a heap buffer over-read consistent with the CVE-2019-5836 bug class (an untrusted, crafted file causing out-of-bounds memory access during parsing).

### Likelihood Explanation
Reaching this code requires only that a maliciously crafted ZIP/JAR file be supplied as input to the `ZipExtractor`/`InputZipFile` central-directory parser — no sandbox bypass, credentials, or privileged access are needed, matching the "unprivileged attacker publishes content a victim's build consumes" threat model. The missing check is a straightforward oversight (the equivalent local-file-header path already implements it), making exploitation reliable once a crafted archive reaches this parser.

### Recommendation
Add the same `EnsureRemaining()`-style bounds validation used in `ProcessLocalFileEntry` to `ProcessCentralDirEntry`: before advancing `p` by `file_name_length`, `extra_field_length`, or `file_comment_length`, and before each extra-field sub-record advance by `data_size`, verify the resulting pointer does not exceed `zipdata_in_ + input_file_->Length()` (or the known central directory bounds), failing with an error instead of continuing to parse.

### Proof of Concept
I was unable to fully verify a working exploit end-to-end (e.g., via a `BuildIntegrationTestCase` or `src/test/shell/bazel` harness) within this investigation, and I could not confirm from the index whether `third_party/ijar/zip.cc`'s `ZipExtractor` is reachable from an untrusted `http_archive`/Bzlmod registry download path (the Java-side `DecompressorValue`/`ZipDecompressor` referenced in `tools/build_defs/repo/http.bzl` appears to be the actual extractor for `http_archive`, and I could not locate its Java source in the index to confirm whether it has an analogous flaw).
