### Title
Unbounded array-length taken directly from call data allows OOM crash in precompiled-contract array parsing - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
Several helper routines used by TVM precompiled contracts (`extractBytesArray`, `extractBytes32Array`, `extractSigArray`) read an array-length word straight from the caller-supplied `data`/`words` buffer and immediately allocate a Java array of that size, with no upper bound check against the actual size of the supplied calldata. This mirrors the CVE-2019-14295 root cause: a length/offset field taken from untrusted input is used to size a memory allocation without first checking it against the actual available data, allowing an attacker to trigger an excessive allocation and crash the process.

### Finding Description
`extractBytes32Array`, `extractBytesArray`, and `extractSigArray` all compute `len` from a single `DataWord` in the precompile's input words and then do `new byte[len][]`: [1](#0-0) 

`intValueSafe()` (used to derive `len`) clamps only against `Integer.MAX_VALUE`, not against the actual size of the supplied `data`/`words`: [2](#0-1) 

Because `len` can be up to `Integer.MAX_VALUE` (~2.1 billion) while the actual TVM calldata for the CALL is tiny, `new byte[len][]` (an object-reference array, 4/8 bytes per slot on a typical JVM) attempts to allocate multiple gigabytes of heap for a call whose real payload is only a few hundred bytes — exactly the "skewed offset/length larger than the actual data size triggers excessive allocation" pattern from the UPX CVE. `extractBytesArray`/`extractSigArray` do check `offset > words.length - 1` before reading the length word, but that only bounds where the length word is read from, not the value of `len` itself, so a small, well-formed `words` array with one word holding a large integer still triggers the oversized allocation.

### Impact Explanation
An `OutOfMemoryError` thrown deep inside a precompiled-contract execution path during TVM opcode processing (a `CALL`/`STATICCALL` to a fixed precompile address) is likely to escape normal `Program.Exception`/`BytecodeExecutionException` handling used for VM-level reverts, since `OutOfMemoryError` is an `Error`, not an `Exception`. Depending on where it propagates, this can abort transaction processing for the whole block/validator process rather than being cleanly caught and reverted, producing a node crash/instability triggerable by any account that can send or trigger a smart-contract transaction calling into the affected precompile — satisfying the "node crash or halt" impact bar required by the rules.

### Likelihood Explanation
The trigger requires only a normal `TriggerSmartContract` transaction (or constant call via `TriggerConstantContract`) that performs a `CALL` to the specific precompiled-contract address that uses `extractBytesArray`/`extractBytes32Array`/`extractSigArray`, with the relevant length word set to a large value (e.g., `0xffffffff`-style value clamped to `Integer.MAX_VALUE` by `intValueSafe()`). This is reachable by any unprivileged transaction broadcaster or contract deployer and requires no special privileges, only crafting the calldata bytes for the precompile call.

### Recommendation
Before allocating `new byte[len][]` in `extractBytesArray`, `extractBytes32Array`, and `extractSigArray`, validate `len` against the actual bounds of the input (`words.length - offset - 1` or the expected item count implied by `data.length`), rejecting/reverting the call if the declared length exceeds what the supplied data can actually contain, similar to the `verifyLength` bounds check already used in `RLP.java`: [3](#0-2) 

### Proof of Concept
Not independently verified end-to-end (the exact fixed precompile address/contract class that calls these three helper methods could not be located within the indexed portion of the repo in the time available — the grep only surfaced the definitions in `PrecompiledContracts.java`, not the call sites). Conceptually: deploy/trigger a contract that performs a `CALL` to the precompile address using these helpers, with the first `DataWord` at the relevant `offset` set to a large 4-byte value (e.g. `0x7fffffff`). `intValueSafe()` returns that value unchanged, and `new byte[len][]` attempts to allocate an array sized in the multi-gigabyte range, causing an `OutOfMemoryError` during precompile execution.

**Note:** Because the exact caller (which fixed precompiled-contract address dispatches to `extractBytesArray`/`extractBytes32Array`/`extractSigArray`) was not found within the available index, this finding should be verified by locating those call sites in the full repository (e.g., via a Devin session with full file access) to confirm reachability from an unauthenticated/unprivileged transaction before treating it as fully proven.

    int len = words[offset].intValueSafe();

  /**
   * In case of int overflow returns Integer.MAX_VALUE otherwise works as #intValue()
   */
  public int intValueSafe() {
    int bytesOccupied = bytesOccupied();
    int intValue = intValue();
    if (bytesOccupied > 4 || intValue < 0) {
      return Integer.MAX_VALUE;
    }
    return intValue;
  }
