### Title
Compromised module-extension `facts` entries persist forever with no per-key revocation - ([File: docs/rules/lib/builtins/module_ctx.mdx], mechanism implemented by module extension eval / lockfile handling)

### Summary
The `module_ctx.facts` / `extension_metadata(facts=...)` mechanism lets a non-reproducible module extension persist a dict of "universally true facts" (e.g. version → {url, checksum} mappings fetched from the network) into `MODULE.bazel.lock`, keyed by extension ID and then by an application-chosen string key (e.g. an SDK version number). Once a fact is written under a key, Bazel keeps re-using it forever on every future evaluation, and there is no mechanism to invalidate or remove a single stale/compromised entry — mirroring the reported class of bug ("once assigned to a key, it cannot be updated or deleted").

### Finding Description
`facts` is documented as a JSON-like dict "that is always persisted in the lockfile and available to future evaluations of the extension via `module_ctx.facts`" [1](#0-0) . It exists specifically to cache "effectively immutable data obtained from outside the build, most commonly from the network, but you don't have a checksum available to guard the download" [1](#0-0) , e.g. "a mapping from version numbers of some SDK to ... the download URL and checksum of that version" [2](#0-1) . Crucially, the value stored under a key is *not itself checksum-verified* — it is exactly the kind of unverified network response the mechanism exists to cache because no checksum is available.

Once written, "facts are not invalidated even when the code of your module extension changes" [3](#0-2) , and merges of facts dicts from different evaluations are only ever additive: "Bazel also assumes that two different facts dicts produced by two different evaluations of the same extension can be shallowly merged (i.e., as if by using the `|` operator on two dicts)" [4](#0-3) . `module_ctx.facts` intentionally supports only lookup by key, not enumeration or deletion [5](#0-4) , and the Starlark API surface for `facts` (`module_ctx.facts` / `extension_metadata(facts=...)`) has no "remove"/"invalidate single key" operation [6](#0-5) .

The *only* invalidation knob is `facts_version`, an extension-global integer: "Bazel persists `facts_version` in the lockfile alongside the facts and discards **any** persisted facts when the recorded version differs from the current one" [7](#0-6) . This is confirmed by the test `testFactsVersionDiscardedOnMismatch`, which shows bumping `facts_version` wipes every entry for the extension, not a single key [8](#0-7) . There is no supported way for a maintainer to surgically evict/replace one poisoned `facts` entry (e.g. `"1.26.1": {"hash": "hello"}` produced from an untrusted response) while keeping the rest of the cache — the only options are "trust it forever" or "nuke the whole extension's cache by bumping `facts_version`."

Additionally, the lockfile merge tooling (`scripts/bazel-lockfile-merge.jq`, used to resolve `MODULE.bazel.lock` merge conflicts in VCS) performs the same unconditional shallow union of `facts` per key across all input lockfiles, again with no removal semantics — a once-recorded fact key from any branch/lockfile survives the merge [9](#0-8) . `testExternallyUpdatedFactsKeptByUpdateModeForNonReproducibleExtension` further demonstrates that even `--lockfile_mode=update` preserves externally-injected fact keys as-is without re-verification [10](#0-9) .

### Impact Explanation
Attack surface: an unprivileged, remote party who controls the network resource that a non-reproducible extension queries (e.g. a metadata/registry endpoint returning `{"hash": ...}` for a version key, as in the "SDK version → checksum" example the docs themselves recommend). If that endpoint ever returns a malicious or wrong value for a given key (compromise, DNS/registry takeover at the time of first fetch, or a since-fixed bug on the origin server), the value is captured into `MODULE.bazel.lock` under that key and is trusted by Bazel on every subsequent build **indefinitely**, even after the origin is fixed, because facts for that key are never re-fetched or re-validated once cached, and there's no per-key removal API — only a global `facts_version` bump that a maintainer must proactively perform and that discards the whole cache. Because `facts` is explicitly recommended for values without a checksum, the mechanism has no independent integrity check to fall back on. This mirrors the report's "no way to update a Swap once assigned to a key" bug class: unprivileged/attacker-influenced content, once bound to a key, cannot be selectively revoked or corrected.

### Likelihood Explanation
This requires a module extension author to use the documented `facts` feature for unchecksummed network data (a pattern Bazel's own docs recommend), and for the attacker to control or compromise the queried endpoint at least once during a fact's first recording. Given `facts` are shared/merged across machines and preserved across lockfile "update" runs and merge-conflict resolution scripts, the poisoned value would silently propagate to every consumer's `MODULE.bazel.lock`. Likelihood is moderate: it depends on adoption of this newer facts mechanism by third-party extensions and on the value never having a checksum, but there is no mitigating control once a value is captured under a key.

### Recommendation
Provide a supported, per-key invalidation/removal primitive for `facts` (analogous to a `removeSwap()`-style call), e.g. a `bazel mod deps --lockfile_mode=refresh` behavior that can selectively drop or force re-fetch of specific fact keys for a specific extension, rather than only a blanket `facts_version` bump that discards the entire cache. At minimum, document and provide tooling to let users audit and selectively purge individual `facts` entries from `MODULE.bazel.lock`.

### Proof of Concept
Not independently reproduced as a JUnit/shell test in this exploration; existing tests in `bazel_lockfile_test.py` (`testFactsVersionDiscardedOnMismatch`, `_setUpExtensionWithFacts`/`_addFactToLockfile`) already demonstrate that (a) individual fact keys are permanently retained across evaluations, (b) the only invalidation path (`facts_version`) is all-or-nothing per extension, and (c) externally-modified/added fact entries are accepted verbatim by `--lockfile_mode=update` without re-verification [11](#0-10) . A concrete PoC would extend `testFactsInNonReproducibleExtension` to (1) record a fact for key `"v1"` from a first "malicious" server response, (2) fix the server response, (3) show that subsequent builds keep serving the original (malicious) fact for `"v1"` with no available API to purge just that key without discarding all facts via `facts_version`.

  def _addFactToLockfile(self, extension_id, fact_key, fact_value):
    """Adds a facts entry to the workspace lockfile."""
    # Simulates the workspace lockfile changing underneath a warm output base,
    # e.g. due to a branch switch or pull that brings in facts produced by an
    # evaluation of the extension on a different machine.
    with open(self.Path('MODULE.bazel.lock'), 'r') as f:
      lockfile = json.loads(f.read().strip())
    lockfile['facts'][extension_id][fact_key] = fact_value
    with open(self.Path('MODULE.bazel.lock'), 'w') as f:
      json.dump(lockfile, f, indent=2)

  def testDeletedFactsRegeneratedByUpdateMode(self):
    """Facts deleted from the workspace lockfile are restored by UPDATE mode.

    Regression test for https://github.com/bazelbuild/bazel/issues/29161. For a
    non-reproducible extension, the deleted facts are restored from the hidden
    lockfile's copy without rerunning the extension: its cached result is
    locked in the workspace lockfile, so a cold machine would not rerun it
    either.
    """
    extension_id = self._setUpExtensionWithFacts(reproducible=False)
    self._dropFactsFromLockfile(extension_id)

    _, _, stderr = self.RunBazel(
        ['build', '@hello//:all', '--lockfile_mode=update']
    )
    self.assertNotIn('lockfile_ext is being evaluated', '\n'.join(stderr))

    with open(self.Path('MODULE.bazel.lock'), 'r') as f:
      lockfile = json.loads(f.read().strip())
    self.assertEqual(
        lockfile['facts'][extension_id],
        {'1.25.0': {'hash': 'olleh'}, '1.26.1': {'hash': 'hello'}},
    )

  def testPartiallyDeletedFactsRegeneratedByUpdateMode(self):
    """Individual facts entries deleted from the lockfile are regenerated.

    Regression test for https://github.com/bazelbuild/bazel/issues/29161: the
    original report deleted a single entry (e.g. "1.25.0") from an extension's
    facts while keeping the others, so the extension's facts key itself is
    still present in the lockfile.
    """
    extension_id = self._setUpExtensionWithFacts(reproducible=True)
    self._dropFactsFromLockfile(extension_id, fact_key='1.25.0')

    self.RunBazel(['build', '@hello//:all', '--lockfile_mode=update'])

    with open(self.Path('MODULE.bazel.lock'), 'r') as f:
      lockfile = json.loads(f.read().strip())
    self.assertEqual(
        lockfile['facts'][extension_id],
        {'1.25.0': {'hash': 'olleh'}, '1.26.1': {'hash': 'hello'}},
    )

  def testDeletedFactsRegeneratedByUpdateModeAfterUnrelatedBuild(self):
    """Facts are regenerated even if an unrelated build runs after the edit.

    The unrelated build must not overwrite the hidden lockfile's record of the
    facts produced by the extension's most recent evaluation with the manually
    edited workspace facts, as that record is what allows a later build to
    detect that the extension has to be rerun.
    """
    extension_id = self._setUpExtensionWithFacts(reproducible=True)
    self._dropFactsFromLockfile(extension_id, fact_key='1.25.0')

    # This build does not evaluate the extension.
    self.RunBazel(['build', '//:unrelated', '--lockfile_mode=update'])

    self.RunBazel(['build', '@hello//:all', '--lockfile_mode=update'])

    with open(self.Path('MODULE.bazel.lock'), 'r') as f:
      lockfile = json.loads(f.read().strip())
    self.assertEqual(
        lockfile['facts'][extension_id],
        {'1.25.0': {'hash': 'olleh'}, '1.26.1': {'hash': 'hello'}},
    )

  def testExternallyUpdatedFactsKeptByUpdateModeForNonReproducibleExtension(
      self,
  ):
    """UPDATE mode keeps updated facts of a non-reproducible extension.

    The hidden lockfile records the facts produced by the most recent local
    evaluation of the extension. If the workspace lockfile's facts for a
    non-reproducible extension change without any of its inputs changing (e.g.
    a branch switch or pull brings in a re-pin performed on another machine),
    the cached result must be reused with the new facts as is: a cold machine
    would not rerun the extension either and a rerun could require network
    access or credentials that are only available to the person updating the
    pins.
    """
    extension_id = self._setUpExtensionWithFacts(reproducible=False)
    self._addFactToLockfile(extension_id, '1.27.0', {'hash': 'hola'})

    _, _, stderr = self.RunBazel(
        ['build', '@hello//:all', '--lockfile_mode=update']
    )
    self.assertNotIn('lockfile_ext is being evaluated', '\n'.join(stderr))

    with open(self.Path('MODULE.bazel.lock'), 'r') as f:
      lockfile = json.loads(f.read().strip())
    self.assertEqual(
        lockfile['facts'][extension_id],
        {
            '1.25.0': {'hash': 'olleh'},
            '1.26.1': {'hash': 'hello'},
            '1.27.0': {'hash': 'hola'},
        },
    )
