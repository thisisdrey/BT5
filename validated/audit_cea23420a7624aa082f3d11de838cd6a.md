Confirmed: `MappedFile::mapped(addr)` only validates that a **single address** falls within `[mapped_start_, mapped_end_)` — it does not verify that a subsequent struct read of arbitrary length starting at that address stays within the mapped region. [1](#0-0) 

### Title
Out-of-bounds read in `InputJar::NextEntry` / `CDH` parsing due to unvalidated field-derived offsets - (`src/tools/singlejar/input_jar.h`, `src/tools/singlejar/zip_headers.h`)

### Summary
`InputJar::NextEntry` walks the Central Directory of a JAR/ZIP by repeatedly computing `new_cdr = cdh_ + cdh_->size()`, where `CDH::size()` is `sizeof(CDH) + file_name_length() + extra_fields_length() + comment_length()` — three attacker-controlled 16-bit fields read directly from the untrusted, memory-mapped jar file. [2](#0-1) [3](#0-2) 

### Finding Description
The only bounds check performed is `mapped_file_.mapped(new_cdr)`, i.e. that the *start* address of the next CDH record is inside `[mapped_start_, mapped_end_)`. [4](#0-3) 
`MappedFile::mapped()` only tests a single address, not a range, so it never confirms that the fixed 46-byte `CDH` struct (and its `file_name_length_`, `extra_fields_length_`, `comment_length_` fields located at offsets 28, 30 and 32) actually fits before `mapped_end_`. [1](#0-0) [5](#0-4) 
Consequently, if a crafted JAR/ZIP places a CDH record so that its start address is validated as "mapped" but is within ~45 bytes of `mapped_end_`, every accessor call on that record (`cdh_->is()`, `cdh_->size()`, `file_name_length()`, `extra_fields_length()`, `comment_length()`, and the `Zip64ExtraField::find`/`UnixTimeExtraField::find` walks over `extra_fields()..extra_fields()+extra_fields_length()`) reads past the end of the mmap'd buffer. This is directly analogous to `CIccProfile::LoadTag`'s bug class: a length/offset field taken from untrusted tag-table data is used to compute a read range without validating that range stays inside the buffer, producing an out-of-bounds read / use of an out-of-range pointer offset.

The `Zip64ExtraField::find`/`ExtraField::find` walkers do bound their iteration against `extra_fields() + extra_fields_length()`, but that bound itself is derived from the unvalidated `extra_fields_length_` field, so if the field is corrupted the walk can still run past the actual mapped buffer before the loop's own `start < end` check catches up, because `end` is computed from attacker data rather than from `mapped_file_.end()`. [6](#0-5) [7](#0-6) 

### Impact Explanation
This code path is exercised by `singlejar`, which is invoked as part of normal Bazel build actions (e.g. Java rules combining/merging jars) on jar files that can originate from external dependencies — files an unprivileged attacker controls (a malicious jar served from a dependency URL/registry/mirror). An out-of-bounds read here can leak adjacent heap/mmap memory content into the crash, or (via `EnsureRemaining`-less reads of `extra_fields`) into copied output data, and can crash the build (`diag_errx`) — matching the "Out-of-bounds Read"/"Use of Out-of-range Pointer Offset" bug class from the referenced advisory, scoped to confidentiality/availability impact on data read from untrusted build inputs.

### Likelihood Explanation
Any attacker who can supply a jar/zip file that ends up as an input to `singlejar` (a normal build dependency) can trigger this by crafting a truncated file whose last Central Directory record is placed so its address passes the single-pointer `mapped()` check but whose declared `file_name_length`/`extra_fields_length`/`comment_length` make the struct read extend past the actual end of the mapped file. No credentials, sandbox escape, or root-repo Starlark execution is required — only a bytes/mmap-boundary condition in untrusted content the build already consumes.

### Recommendation
Change `InputJar::NextEntry` (and equivalently `CDH`/`LH`'s field accessors) to validate the **entire byte range** needed for a record — `[cdh_, cdh_ + sizeof(CDH))` before reading any field, and `[cdh_, cdh_ + cdh_->size())` before advancing — against `mapped_file_.end()`, not just the single address of the next record. Update `MappedFile` with a range-checking helper (e.g. `mapped_range(addr, len)`) and use it everywhere a length taken from untrusted zip metadata (`file_name_length`, `extra_fields_length`, `comment_length`, `local_header_offset`) is used to compute a pointer or a read length, mirroring the existing (but insufficient) checks already present for the central-directory location/size in `input_jar.cc`. [8](#0-7) 

### Proof of Concept
A `BuildIntegrationTestCase`/unit test analogous to `zip_headers_test.cc` should:
1. Allocate a small buffer via `mapped_file_.MapExisting` sized to end exactly `N` bytes after a placed `CDH` record whose start address is valid per `mapped()`.
2. Set `file_name_length_`/`extra_fields_length_`/`comment_length_` to values that make `cdh_->size()` extend well past `N` bytes beyond `mapped_end_`.
3. Call `InputJar::NextEntry` and observe (under ASan/valgrind) an out-of-bounds heap read when `cdh_->size()`/`extra_fields()` dereference bytes beyond the mapped region, rather than a controlled failure. [9](#0-8)

class ExtraField {
 public:
  static const ExtraField* find(uint16_t tag, const uint8_t* start,
                                const uint8_t* end) {
    while (start < end) {
      if (ziph::byte_ptr(start) + sizeof(ExtraField) > ziph::byte_ptr(end)) {
        break;
      }
      auto extra_field = reinterpret_cast<const ExtraField*>(start);
      if (ziph::byte_ptr(start) + extra_field->size() > ziph::byte_ptr(end)) {
        break;
      }
      if (extra_field->is(tag)) {
        return extra_field;
      }
      start = ziph::byte_ptr(start) + extra_field->size();
    }
    return nullptr;
  }
