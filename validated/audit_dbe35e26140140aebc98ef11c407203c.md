### Title
FetchRemote RPC allows indefinite resource-holding fetches via unset `Timeout` combined with a slow/hanging remote server, enabling DoS - ([File: internal/gitaly/service/repository/fetch_remote.go])

### Summary
`FetchRemote` only applies a `context.WithTimeout` when `req.GetTimeout() > 0`; when the caller supplies `Timeout=0` (the default/unset value) no deadline is applied, and the underlying `git fetch` against an attacker-controlled URL can block indefinitely on the network. Because the RPC allocates a quarantine directory and two `updateref.Updater` processes before/around the fetch, and concurrency limiting for this RPC is not enabled by default in Gitaly's configuration, a single unprivileged user can hold these resources open indefinitely and repeat the call to exhaust file descriptors, temp directories, and git subprocess slots.

### Finding Description
`FetchRemote` (`internal/gitaly/service/repository/fetch_remote.go:30-47`) validates the request via `validateFetchRemoteRequest`, which only checks that `Repository` and `RemoteParams.Url` are non-empty — it never enforces a minimum or default `Timeout` [1](#0-0) . The timeout is applied conditionally:

```go
if req.GetTimeout() > 0 {
    ctx, cancel = context.WithTimeout(ctx, time.Duration(req.GetTimeout())*time.Second)
    defer cancel()
}
``` [2](#0-1) 

If `Timeout` is omitted/zero, the only cancellation source left is the caller's own gRPC context, which the attacker fully controls and can simply never cancel (e.g., an unauthenticated long-lived HTTP/2 stream). `fetchRemoteAtomic` then:
- Sets up SSH invocation cleanup (`sshCleanup`, deferred) [3](#0-2) 
- Creates a quarantine directory (`quarantine.New`) with a deferred cleanup [4](#0-3) 
- Calls `quarantineRepo.FetchRemote(ctx, "inmemory", opts)`, which spawns `git fetch` against the attacker-supplied `RemoteParams.Url` [5](#0-4) 

Since `git fetch` over HTTP/SSH performs network I/O waiting on the remote's ref advertisement, a "slow-loris" style server that never completes the handshake will cause the `git fetch` subprocess — and therefore the whole RPC handler goroutine, its held quarantine directory, and any downstream `updateref.Updater` state — to block until the client-controlled context is cancelled or the TCP connection dies (which the attacker also controls).

Gitaly's only defense against this kind of resource exhaustion is the `[[concurrency]]` per-RPC/per-repo limiter, which is opt-in configuration and not enabled by default for `FetchRemote` [6](#0-5) [7](#0-6) . Only `ReplicateRepository` receives a hard-coded default limiter of 1; `FetchRemote` has no such default [7](#0-6) . Thus without explicit operator configuration, there is no cap on concurrent in-flight `FetchRemote` calls per repository, and no server-enforced deadline independent of the attacker-supplied `Timeout` field.

### Impact Explanation
An unprivileged user who can invoke `FetchRemote` (e.g., via a pull-mirror configuration or any GitLab feature that proxies this RPC with user-controlled `RemoteParams.Url`) can cause each call to hold a quarantine tempdir, an SSH invocation and cleanup handler, and a blocked `git fetch` subprocess (consuming an fd/process slot) open indefinitely. Repeating this concurrently exhausts Gitaly's file descriptors, temp directory inodes, and process table, degrading or crashing the Gitaly node for all repositories/users on it — a server-wide DoS matching GitLab's "Denial of Service" bounty impact class.

### Likelihood Explanation
Exploitability depends on whether GitLab Rails exposes `RemoteParams.Url` and `Timeout` to an unprivileged user (e.g., pull mirroring, repository import) without server-side enforcement of a non-zero timeout — this is a precondition outside of Gitaly's own code that this audit cannot fully verify from the Gitaly repo alone. Within Gitaly itself, there is no additional safety net: `validateFetchRemoteRequest` does not reject `Timeout=0`, and concurrency limiting is not enabled by default. If Rails or another gRPC client passes through the user-supplied timeout unmodified (or defaults it to 0), the attack is straightforward, repeatable, and requires no special privileges beyond the ability to configure a remote URL for fetch/mirror/import.

### Recommendation
Enforce a server-side maximum/default timeout for `FetchRemote` in Gitaly regardless of the client-supplied `Timeout` value (e.g., always apply `context.WithTimeout` with a sane default such as several minutes when `req.GetTimeout() <= 0`, and cap the maximum even when set). Additionally, ship a default `[[concurrency]]` limit for `FetchRemote` (as already done for `ReplicateRepository`) to bound concurrent per-repository fetches, and consider adding connect/read timeouts to the underlying `git fetch` invocation via git config (e.g., `http.lowSpeedLimit`/`http.lowSpeedTime`) so a stalled remote cannot block the process indefinitely.

```go
// PoC test sketch: internal/gitaly/service/repository/fetch_remote_test.go
func TestFetchRemote_HangingRemoteNoTimeout(t *testing.T) {
    // Start an HTTP server that accepts the connection but never
    // writes the initial ref advertisement (slow-loris style).
    ln, _ := net.Listen("tcp", "127.0.0.1:0")
    go func() {
        for {
            conn, err := ln.Accept()
            if err != nil {
                return
            }
            // Read the request but never respond.
            go io.Copy(io.Discard, conn)
        }
    }()
    defer ln.Close()

    cfg, repoProto, _ := setupRepositoryService(t)
    client := newRepositoryClient(t, cfg)

    ctx := testhelper.Context(t) // no deadline set on caller's side either

    req := &gitalypb.FetchRemoteRequest{
        Repository: repoProto,
        RemoteParams: &gitalypb.RemoteRepository{
            Url: "http://" + ln.Addr().String() + "/x.git",
        },
        Timeout: 0, // attacker omits timeout
    }

    start := time.Now()
    done := make(chan struct{})
    go func() {
        _, _ = client.FetchRemote(ctx, req)
        close(done)
    }()

    select {
    case <-done:
        t.Fatalf("expected FetchRemote to hang, but it returned after %s", time.Since(start))
    case <-time.After(10 * time.Second):
        // Confirms the RPC is still blocked after 10s with no server-side timeout,
        // holding its quarantine dir / git-fetch subprocess open.
    }
}
```
Running N of these concurrently (with `RemoteParams.Url` pointing at distinct hanging listeners) and observing Gitaly's open file descriptor count / process count grow unboundedly (via `lsof -p <gitaly-pid>` or `/proc/<pid>/fd`) demonstrates the resource exhaustion.

func (s *server) validateFetchRemoteRequest(ctx context.Context, req *gitalypb.FetchRemoteRequest) error {
	if err := s.locator.ValidateRepository(ctx, req.GetRepository()); err != nil {
		return structerr.NewInvalidArgument("%w", err)
	}

	if req.GetRemoteParams() == nil {
		return structerr.NewInvalidArgument("missing remote params")
	}

	if req.GetRemoteParams().GetUrl() == "" {
		return structerr.NewInvalidArgument("blank or empty remote URL")
	}

	return nil
}
