### Title
Unauthenticated hook/access-check bypass in `RefService.UpdateReferences` allows ref rewrites without Rails authorization - (File: internal/gitaly/service/ref/update_references.go)

### Summary
`UpdateReferences` builds a plain `updateref.New(ctx, repo)` updater and calls `updater.Commit()` directly, with no call to `updateref.UpdaterWithHooks` or the `HookService` at all. Any caller with gRPC access to this RPC and write permission on a repository can move or delete any reference — including protected branches — to any object ID that already exists in the repository's object database, without Rails' `/internal/allowed` check or custom pre-receive/update hooks ever running.

### Finding Description
The handler flow is: receive request → `s.locator.ValidateRepository` → build `localrepo.Repo` → `updateref.New(ctx, repo)` (internal/gitaly/service/ref/update_references.go:38) → per-update validation via `git.ValidateReference` and `objectHash.ValidateHex` (lines 59, 75, 81) → `updater.Update(...)` (line 85) → `updater.Commit()` (line 99). Contrast this with `updateref.UpdaterWithHooks.UpdateReference` (internal/gitaly/hook/updateref/update_with_hooks.go:167-244), which is the code path used by `OperationService` RPCs (e.g., branch/tag mutation, merge, cherry-pick) and by `git-receive-pack`: it constructs a hooks payload, calls `PreReceiveHook` (which posts to Rails `/internal/allowed`), migrates quarantined objects only after Rails approval, then runs the `update` hook and reference-transaction voting before finally updating the ref. `UpdateReferences` skips every one of these steps. The only checks performed are format/existence validation (`git.ValidateReference`, `objectHash.ValidateHex`) — neither of which perform authorization; they merely validate that the ref name and OID are syntactically well-formed. As long as the target object already exists in the repository (e.g., a commit reachable from a prior branch, an orphaned/pruned-but-not-yet-gc'd commit, or an object from a previous legitimate push the attacker made), `git-update-ref` will happily accept the update since it does not care how the object got there.

### Impact Explanation
This corresponds to GitLab's access-control-bypass class: an unprivileged repository writer can force-push/rewrite or delete protected refs while completely bypassing GitLab's protected-branch enforcement, push rules, and any custom server hooks that are normally guaranteed to run on every reference mutation. Since protected-branch policy enforcement in GitLab lives in Rails' `/internal/allowed` check (invoked only from the pre-receive hook), and this RPC never calls it, the security guarantee that "no ref update reaches disk without an authorization decision" is broken for any client that can call `RefService.UpdateReferences` directly.

### Likelihood Explanation
Exploitability depends entirely on whether GitLab Rails/Workhorse exposes `RefService.UpdateReferences` to authenticated non-admin users' gRPC traffic (versus restricting it to internal-only callers such as backup/restore, which is the only caller found in this codebase, at internal/backup/repository.go:417-458). I could not find any per-RPC ACL/scope annotation in `proto/ref.proto` restricting `UpdateReferences` to internal/admin callers, nor middleware in the reachable code that gates it beyond the standard repository-scoped gRPC interceptors (which only check that the caller holds a valid token for that repository, not user-level ref permissions — that authorization is normally deferred to the hook chain, which this RPC skips). If GitLab Rails does proxy or expose this RPC to regular user push/write flows (directly, or via a feature like repository mirroring/replication that a project owner can trigger), the exploit is fully reachable with only ordinary write access; if it is strictly Gitaly-internal/administrative in the currently deployed product surface, this is a defense-in-depth gap rather than a directly reachable bug for an unprivileged actor. I was not able to fully confirm from this repo's index which gRPC entry points/authorization scopes gate this RPC in production, so likelihood carries residual uncertainty.

### Recommendation
Route `UpdateReferences` through `updateref.UpdaterWithHooks` (or otherwise invoke `PreReceiveHook`/`UpdateHook`/reference-transaction voting) before committing changes, mirroring the flow already used by `OperationService` mutators, so that every reference update is subject to Rails' `/internal/allowed` check and custom hooks. At minimum, restrict this RPC's exposure so it can only be invoked by trusted internal callers (e.g., backup/restore tooling) and never by paths reachable from ordinary authenticated GitLab users.

- `pre-receive`: The pre-receive hook receives all reference updates as a whole
  via standard input, where each change is represented by one line with the old

  quarantine directory using the repository's alternative object directory

  objects. When the access checks succeed, any existing custom pre-receive hooks
