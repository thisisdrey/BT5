Confirmed: there is no limit in Gitaly on the number of reference-update commands a client can include in a single push, and each command triggers a synchronous, per-reference invocation of the `update` hook (and transitively any admin-installed custom hooks), all executed serially inside the RPC handler that also holds a write-ahead-log transaction / reference lock open for the whole duration.

### Title
Unbounded per-reference hook subprocess loop in proc-receive path allows a single push to DoS a Gitaly node - (File: internal/gitaly/hook/receivepack/receive_pack.go)

### Summary
The Code4rena finding describes `AuctionHouse::_settleAuction` looping over an attacker-controlled, unbounded list of "creators" and performing an expensive external call (ETH transfer / token buy) for every entry, so gas cost scales linearly with a value the attacker fully controls, risking hitting the block gas limit. The same structural pattern — an unbounded, client-controlled list iterated once per element with a costly external operation per iteration, inside a single unit of work that must complete atomically — exists in Gitaly's reference-update handling for `git-receive-pack`/proc-receive.

### Finding Description
When Git's `proc-receive` hook is active, `RegisterProcReceiveHook` hands control to `procReceiveHook`, which obtains the full, client-supplied list of reference updates via `handler.ReferenceUpdates()` [1](#0-0)  and passes it to `receivePackReferenceUpdates`. That function starts a reference-transaction updater and then, for **every single update in the list**, synchronously calls `hookManager.UpdateHook(...)` before queueing the ref update: [2](#0-1) 

`UpdateHook` in turn spawns a subprocess via `newCustomHooksExecutor` for every custom `update` hook script installed on the repository (project-level, project `.d` directory, and global directory), waiting for each one to finish before moving to the next reference: [3](#0-2) [4](#0-3) 

The reference-update command list itself (`old-oid new-oid ref-name` lines terminated by a flush packet) has no maximum-count enforcement anywhere in the request parsing/handling path — the stats parser explicitly just counts commands without capping them [5](#0-4) , and there is no analogous limit in the hook-execution path. A single push (SSH or HTTP, with or without a real object change per ref, e.g. touching thousands of lightweight tags/branches) can therefore enqueue an arbitrarily large number of reference updates, and Gitaly will synchronously spawn a subprocess and wait for it for each one, inside the same RPC call, while holding the ref-transaction/updater open (`updater.Start()` ... `updater.Commit()`), and — when Praefect/WAL voting is in play — while a write-ahead-log transaction is outstanding, per the documented per-reference execution loop [6](#0-5) .

This mirrors the AuctionHouse pattern precisely: an ordinary caller (any user with push access) supplies the size and content of the iterated list (number of refs to update) as part of a normal, unprivileged RPC (`SSHReceivePack`/`PostReceivePack`), and each iteration performs an expensive, externally-visible operation (subprocess spawn/exec/wait) whose count is fully attacker-chosen and unbounded.

### Impact Explanation
Because the per-reference hook execution is serial and synchronous within a single RPC handler, a push containing a very large number of small/no-op reference updates (e.g. tens of thousands of ref creations/deletions, which are cheap to construct and require no packfile objects for deletions) forces Gitaly to fork/exec/wait that many times sequentially before it can commit or reject the transaction. This ties up the RPC goroutine, the reference-transaction lock, and (with WAL) an open transaction for a duration proportional to the attacker-chosen ref count, degrading availability of the storage node for that repository and consuming CPU/process-table resources disproportionate to the size of the push. If custom hooks are installed (a normal supported GitLab admin feature, not an attacker capability), the cost per iteration is amplified further, similar to how the report's "malicious creator" `receive()` amplifies gas cost per iteration.

### Likelihood Explanation
Any authenticated user with push access to a repository can trigger this — no elevated privileges, leaked tokens, or malicious peers/nodes are required, satisfying the "ordinary user push" reachability requirement. The only precondition affecting severity (not reachability) is whether custom hooks are configured, which affects the per-iteration cost but not the fundamental unbounded-loop structure, which exists regardless (even with zero custom hooks, Gitaly still performs a hooksPayload lookup, gRPC round trip, and `updater.Update()` call per reference).

### Recommendation
- Enforce a configurable maximum number of reference-update commands accepted per `receive-pack`/proc-receive request, rejecting or chunking pushes that exceed it, analogous to limiting the "number of creators" recommended in the source report.
- Consider batching/parallelizing or bounding the aggregate time budget for the per-reference `update`-hook loop in `receivePackReferenceUpdates`, rather than looping without bound over `handler.ReferenceUpdates()`.
- Ensure any such limit is enforced before the reference-transaction/updater is started and before a WAL transaction is opened, so oversized requests are rejected cheaply.

### Proof of Concept
1. Prepare a `git-receive-pack` pkt-line command list containing N (e.g. 50,000) `zero-oid new-oid refs/tags/x-<i>` create commands (no packfile objects are strictly required for pure ref creation from an already-existing target, or use deletes of existing refs, which need no packfile at all), followed by a flush packet.
2. Send this via `SSHReceivePack`/`PostReceivePack` to a Gitaly node whose repository has the `proc-receive` path enabled (transactions/WAL enabled) so `procReceiveHook`/`receivePackReferenceUpdates` is exercised.
3. Observe that `receivePackReferenceUpdates` iterates all N updates, invoking `hookManager.UpdateHook` (and any custom `update` hook scripts) N times synchronously inside one RPC call [2](#0-1) , before the reference-transaction updater commits, and measure the wall-clock time and resource usage of the single RPC scaling linearly with N with no server-side rejection based on command count.

func (m *GitLabHookManager) updateHook(ctx context.Context, payload gitcmd.HooksPayload, repo *gitalypb.Repository, ref, oldValue, newValue string, env []string, stdout, stderr io.Writer) error {
	objectHash, err := git.ObjectHashByFormat(payload.ObjectFormat)
	if err != nil {
		return fmt.Errorf("looking up object hash: %w", err)
	}

	if ref == "" {
		return structerr.NewInternal("hook got no reference")
	}
	if err := objectHash.ValidateHex(oldValue); err != nil {
		return structerr.NewInternal("hook got invalid old value: %w", err)
	}
	if err := objectHash.ValidateHex(newValue); err != nil {
		return structerr.NewInternal("hook got invalid new value: %w", err)
	}
	if payload.UserDetails == nil {
		return structerr.NewInternal("payload has no receive hooks info")
	}

	executor, err := m.newCustomHooksExecutor(ctx, repo, "update")
	if err != nil {
		return structerr.NewInternal("%w", err)
	}

	customEnv, err := m.customHooksEnv(ctx, payload, nil, env)
	if err != nil {
		return structerr.NewInternal("constructing custom hook environment: %w", err)
	}

	if err = executor(
		ctx,
		[]string{ref, oldValue, newValue},
		customEnv,
		nil,
		stdout,
		stderr,
	); err != nil {
		return fmt.Errorf("executing custom hooks: %w", err)
	}

	return nil
}

// ReceivePack parses the request a Git client sends to git-receive-pack(1)
// (i.e. the client side of a push). The request consists of a list of
// reference-update commands in pkt-line format, terminated by a flush packet,
// optionally followed by a packfile.
//
// See https://git-scm.com/docs/pack-protocol#_reference_update_request_and_packfile_transfer.
type ReceivePack struct {
	// UserAgent is the user agent announced by the client, e.g. "git/2.53.0".
	UserAgent string
	// Capabilities announced by the client (report-status, side-band-64k, ...).
	Caps []string
	// Commands is the number of reference-update commands in the request.
	Commands int
	// Creates is the number of references the client wants to create.
	Creates int
	// Deletes is the number of references the client wants to delete.
	Deletes int
	// Updates is the number of references the client wants to update.
	Updates int
	// Objects is the number of objects in the packfile as announced by the
	// PACK header. A delete-only push carries no packfile
	// and leaves this at zero.
	Objects uint32
	// Packets is the total number of pktlines in the command list. It
	// distinguishes an empty request from one whose command list was
	// truncated.
	Packets int
}
