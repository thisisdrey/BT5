Based on my investigation, the strongest analog to the radare2 `dalvik_op` heap-over-read pattern (unbounded array indexing/allocation driven by attacker-controlled length fields inside a data blob) is the TVM `ValidateMultiSign`/`BatchValidateSign` precompile's ABI decoding helpers.

### Title
Unbounded attacker-controlled length in TVM `ValidateMultiSign` precompile signature decoding can trigger uncontrolled memory allocation / out-of-bounds array access - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
`PrecompiledContracts.extractSigArray` decodes a signature-count word directly from attacker-supplied calldata without validating it against any sane bound before using it to size a Java array, then computes byte offsets from further attacker-controlled words and passes them, unchecked, into `Arrays.copyOfRange` via `extractBytes`.

### Finding Description
`extractSigArray` reads the signature count from calldata and immediately allocates an array of that size: [1](#0-0) 
`len` comes straight from `words[offset].intValueSafe()`, an attacker-controlled 256-bit calldata word truncated to `int`, with no upper bound check (e.g., no cap like "max N signatures") before `new byte[len][]` is allocated. Each per-signature offset (`bytesOffset`) is also taken from calldata and used to compute a byte range that is copied via: [2](#0-1) 
`Arrays.copyOfRange(data, offset, offset+len)` throws `ArrayIndexOutOfBoundsException` if the computed `offset` is negative, and a crafted large `len` value in the outer function causes an attempted multi-gigabyte array allocation (`new byte[len][]`), which throws `OutOfMemoryError`. This is directly analogous to the reported CVE's bug class: a length/offset field taken from untrusted, crafted binary input is used to index/allocate memory without adequate bounds validation, producing a crash condition.

This is functionally comparable to `dalvik_op`'s heap-based buffer over-read from a crafted dex file — here, a crafted calldata blob to a reachable precompile drives unchecked array sizing/indexing.

### Impact Explanation
`OutOfMemoryError` and unhandled `Error` types are not caught by the VM's exception handling, which only catches `RuntimeException`, `JVMStackOverFlowException`/`OutOfTimeException`, and `StackOverflowError`: [3](#0-2) 
An `OutOfMemoryError` triggered mid-transaction-execution can propagate past this handler and potentially destabilize or crash the node process handling block application — a denial-of-service condition reachable by any account able to broadcast a contract call.

### Likelihood Explanation
I could not fully confirm, within the available tool budget, whether the precompile's `execute()` method (which calls `extractSigArray`) performs any upstream bound validation on the signature count/data length before reaching this code, nor whether newer TIP-854-related guards (referenced in `ValidateMultiSignContractTest`) fully close this specific gap for all code paths (pre- vs post-activation). The test file explicitly documents that pre-activation malformed calldata is expected to raise an exception as "the documented pre-activation failure mode the TIP explicitly preserves": [4](#0-3) 
This suggests the project is already aware that malformed/crafted calldata to this precompile causes an exception in certain configurations, and has treated it as accepted/known behavior for the ArrayIndexOutOfBoundsException class of failures — reducing confidence that this is an unreported issue, though the OutOfMemoryError-via-huge-`len` variant specifically was not something I could confirm is covered by that guard.

### Recommendation
Add explicit bounds validation for the signature count (`len`) against a small sane maximum (matching the protocol's expected max signer count) and validate all decoded byte offsets are within `[0, data.length]` before calling `Arrays.copyOfRange`, in both `extractSigArray` and `extractBytes`.

### Proof of Concept
Craft calldata to the `ValidateMultiSign`/`BatchValidateSign` precompile where the word at the "signature count" offset is set to a large value (e.g., `0x7FFFFFFF`), triggering `new byte[len][]` in `extractSigArray` and an `OutOfMemoryError`, or set a subsequent offset word to a negative-yielding value to trigger `ArrayIndexOutOfBoundsException` in `extractBytes`.

**Caveat**: Due to not being able to fully trace the precompile's calling `execute()` method and its potential pre-validation logic within my remaining tool budget, I cannot certify with full confidence that this path is unmitigated in the current codebase; the test evidence suggests partial/known mitigations already exist for related malformed-input cases.

    if (offset > words.length - 1) {

    byte[][] bytesArray = new byte[len][];

    }
    return bytesArray;
  }
