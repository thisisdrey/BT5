### Title
Attacker can dust-fill a victim's per-account token lists to `MAX_TOKENS_PER_USER`, permanently blocking deposits of new collateral and new debt issuance - ([File: contracts/Pool.sol])

### Summary
`Pool.addToDepositTokensOfAccount` / `addToDebtTokensOfAccount` revert with `UserReachedMaxTokens` once an account holds 30 distinct deposit/debt tokens [1](#0-0) . Because `DepositToken.transfer`/`transferFrom` forcibly registers the *recipient's* list entry via `_transfer` → `pool.addToDepositTokensOfAccount(recipient_)` with no opt-in and no minimum amount [2](#0-1) , an unprivileged attacker can dust-transfer all listed deposit tokens to a victim, filling the list and DoS-ing that account's ability to onboard new collateral — analogous to the wpa_supplicant flaw where unsanitized input caused a daemon outage.

### Finding Description
- `MAX_TOKENS_PER_USER = 30` is enforced on the combined length of `debtTokensOfAccount` + `depositTokensOfAccount` [3](#0-2) [1](#0-0) .
- `DepositToken._transfer` adds the token to the recipient's list whenever `recipient` balance was previously 0 [2](#0-1) ; there is no `to_` consent, no minimum transfer amount, and no way to reject the incoming registration.
- The same quota gates new debt positions: `DebtToken._mint` → `pool.addToDebtTokensOfAccount(account_)` reverts when the combined count is already 30 [4](#0-3) [5](#0-4) .
- Attack: for every deposit token `d_i` registered in the pool (`getDepositTokens()`), the attacker deposits a minimal amount to themselves (or buys dust via transfer), then calls `d_i.transfer(victim, 1)`. Each call pushes `d_i` into `depositTokensOfAccount[victim]`. After ~30 calls (fewer if the victim already holds positions), any further `deposit()` of a new collateral type, `DebtToken.issue()` in a new synthetic, `seize()` proceeds to that user, or incoming transfer of a new deposit token reverts with `UserReachedMaxTokens`.
- The victim cannot remove these dust entries cheaply either: removal requires burning the full balance, and while the victim *can* transfer the dust out (removing the entry when balance hits 0 [6](#0-5) ), each transfer is permissioned only by the lock check and the attacker can re-fill slots in the same block via flash-loaned capital — but more importantly the attack is repeatable and front-runs any remediation.

### Impact Explanation
Liveness/DoS of a victim's position management: the account is blocked from (a) depositing any new collateral type, (b) issuing any new synthetic debt type, and (c) receiving seized deposit tokens as a liquidator if its list is full (liquidation via `depositToken_.seize(account_, _msgSender, _toLiquidator)` reverts mid-call when `to_`'s list is full [7](#0-6) ). Combined with market moves, a victim whose existing collaterals cannot cover a worsening position and who needs a *new* collateral type to recapitalize can be pushed into liquidation — i.e., temporary freezing of the user's ability to rescue funds, potentially leading to forced loss.

### Likelihood Explanation
The attack needs only dust amounts (1 wei each) of up to 30 whitelisted collaterals, obtainable via `deposit(amount, attacker)` then `transfer(victim, dust)`; the attacker loses almost nothing since the rest can be withdrawn. No privileged role, no oracle manipulation, no governance action required. Success depends on the pool listing enough deposit tokens for the victim's list to reach 30 (pool itself caps registered deposit tokens at `MAX_TOKENS_PER_USER` [8](#0-7) , so on a fully populated pool this is always reachable). Impact is bounded — existing collateral slots keep working — so severity is medium.

### Recommendation
- Require recipient consent for first-time entries: register on `deposit()`/`issue()` only, and keep `transfer`/`seize` dust from counting by either (a) allowing transfers without list registration when the recipient list is full (track collateral via a different mechanism), or (b) enforcing a minimum meaningful first-transfer amount.
- Alternatively, in `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount`, don't revert on a full list for unsolicited registration — store the token anyway in an overflow structure, or let `MAX_TOKENS_PER_USER` apply only to position-critical operations (e.g., only count tokens with non-trivial balance/locked collateral in `depositOf`/`debtOf` loops).
- Provide a `sweepDust`/`removeIfZeroBalance` escape so users can cheaply evict 1-wei entries.

### Proof of Concept
Foundry/Hardhat sketch (Hardhat style, matching repo tests):

```ts
// victim = alice; pool has >=30 deposit tokens registered
for (const dt of depositTokens) {
  // attacker seeds own balance once
  await dt.connect(attacker).deposit(ethers.utils.parseUnits('1', decimals), attacker.address)
  // each first-time transfer pushes dt into depositTokensOfAccount[alice]
  await dt.connect(attacker).transfer(alice.address, 1)
}
expect(await pool.getDepositTokensOfAccount(alice.address)).to.have.lengthOf(30)

// alice tries to deposit a collateral she never held before -> reverts
await expect(
  newDepositToken.connect(alice).deposit(100, alice.address)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens')

// alice tries to issue a new synthetic debt type -> also reverts
await expect(
  newDebtToken.connect(alice).issue(100, alice.address)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens')

// liquidator with a full list cannot seize via Pool.liquidate
await expect(
  pool.connect(liquidator).liquidate(msAsset, borrower, repayAmt, depositToken)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens')
```

Reproduces on a fork using the deployed `Pool` (VERSION 1.3.2) and registered `DepositToken`s; `deposit` pulls underlying to the `Treasury` and mints transferable msdTOKEN with no lock for a debt-free attacker [9](#0-8) .
