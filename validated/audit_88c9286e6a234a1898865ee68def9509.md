### Title
Account deletion does not purge PostponedReceipt/PendingDataCount/PostponedReceiptId rows, letting arbitrarily large receipt state outlive `DeleteAccount` and later fire onto a re-created account of the same name - (`core/store/src/utils/mod.rs`, `runtime/runtime/src/actions.rs`)

### Summary
`action_delete_account` gates deletion only on `Account::storage_usage()` minus contract-code size, capped at `Account::MAX_ACCOUNT_DELETION_STORAGE_USAGE = 10_000` bytes, but `storage_usage` never accounts for `TrieKey::PostponedReceipt`/`PendingDataCount`/`PostponedReceiptId` rows keyed by the account. `remove_account` (called from `action_delete_account`) only clears `Account`, `ContractCode`, `AccessKey`/gas-key nonces, and `ContractData` - it never touches postponed-receipt bookkeeping. An account can therefore be deleted while it still has a postponed action receipt (with an arbitrarily large action list/args) parked under its name, and that receipt is later delivered and executed against whatever account subsequently takes that same `account_id`.

### Finding Description
`Account::MAX_ACCOUNT_DELETION_STORAGE_USAGE` (`core/primitives-core/src/account.rs:230`) bounds the size check performed in `action_delete_account` (`runtime/runtime/src/actions.rs:326-353`), which computes `account_storage_usage` purely from `account.storage_usage()` minus contract-code bytes via `get_contract_storage_usage`. This field is maintained incrementally by account/key/contract/data mutations (e.g. `access_keys.rs`, `action_deploy_contract` at `actions.rs:287-294`) but is never incremented when a receipt is postponed onto the account: `process_action_receipt` (`runtime/runtime/src/lib.rs:1593-1658`) and `set_postponed_receipt`/`PendingDataCount` writes (`core/store/src/utils/mod.rs:120-127`, `runtime/runtime/src/lib.rs:1645-1654`) write `TrieKey::PostponedReceipt`, `TrieKey::PendingDataCount`, and `TrieKey::PostponedReceiptId` rows keyed by `receiver_id` without touching `Account::storage_usage`.

When `action_delete_account` passes the size check, it calls `remove_account` (`core/store/src/utils/mod.rs:505-575`), which removes only `TrieKey::Account`, `TrieKey::ContractCode`, access keys/gas-key nonces, and `TrieKey::ContractData`. It never iterates or removes `TrieKey::PostponedReceipt`, `TrieKey::PendingDataCount`, or `TrieKey::PostponedReceiptId` for the account. Consequently, any postponed receipt already parked under the deleted account_id (which can carry a large `Action` list, e.g. a `FunctionCall` with large `args`) survives deletion untouched in the trie, entirely outside the byte accounting that gated the deletion.

Later, when the awaited `DataReceipt` for that postponed receipt arrives, `process_receipt` (`runtime/runtime/src/lib.rs:1367-1474`) looks it up purely by `receiver_id`/`data_id`/`receipt_id` - it has no notion of "this account was deleted and recreated." If a new account has since been created under the same `account_id` (top-level names and sub-accounts can be freely re-created once deleted), the runtime will fetch the orphaned `PostponedReceipt` (`get_postponed_receipt`, `lib.rs:1431-1437`) and execute it via `apply_action_receipt` against the *current* account state - i.e., the new, unrelated owner's account - executing the attacker's originally-queued, arbitrarily large action list against it.

### Impact Explanation
This is an apply-path resource/liveness and state-integrity issue: an attacker can leave megabyte-scale (or larger, bounded only by receipt/action size limits) receipt payloads keyed to an account name that no longer satisfies any storage-stake obligation (the account is deleted, so nobody pays for this data), and that payload is later delivered and applied to a completely different, unrelated account/tenant that later claims the same name - executing actions the new owner never agreed to, and consuming the new account's execution-time storage/trie footprint without consent. This falls under authorization escalation across accounts / promises (an action list is silently inherited by an account that never authorized it) as well as unbounded/unmetered state growth if the name is never reclaimed.

### Likelihood Explanation
Preconditions are fully within reach of an ordinary funded account: deploy a contract that issues a cross-contract promise chain whose callback (with large args) targets itself, ensuring the callback receipt is postponed (unmet `input_data_ids`) before the dependent data arrives; submit a `DeleteAccount` action for that account while the postponed receipt is still pending and the visible `storage_usage` is under 10,000 bytes. No validator, node-operator, or privileged access is needed - only standard transaction/receipt crafting. The remaining step (a third party recreating the same account name and being affected) depends on account-name reuse, which is a normal, permitted operation in NEAR (top-level/sub-account creation rules in `actions.rs:155`), making this reproducible and repeatable at attacker's discretion.

### Recommendation
Include the size of any pending `PostponedReceipt`/`PendingDataCount`/`PostponedReceiptId` rows for the account_id in the `DeleteAccountWithLargeState` check (or unconditionally forbid deletion while such rows exist for the account), and extend `remove_account` to enumerate and remove all `PostponedReceipt`, `PendingDataCount`, and `PostponedReceiptId` entries keyed by the account before allowing deletion to succeed.

### Proof of Concept
1. Unit/integration test (in `runtime/runtime/src/tests/apply.rs` style, similar to `test_delete_account_removes_gas_keys` / `test_promise_input_size_limit_exceeded_fails_and_cleans_up`):
   - Create account `alice` with `storage_usage` under `MAX_ACCOUNT_DELETION_STORAGE_USAGE`.
   - Insert a large `PostponedReceipt` for `receiver_id = alice` (e.g. via `set_postponed_receipt`/`set` for `PendingDataCount`) representing an `ActionReceipt` with a large `FunctionCall` action (e.g. 1 MB args), simulating an in-flight cross-contract callback awaiting a `DataReceipt`.
   - Call `action_delete_account` for `alice`; assert it succeeds (`result.result.is_ok()`), demonstrating the size check ignored the postponed receipt.
   - After committing, assert `get_postponed_receipt(state_update, &alice, receipt_id)` still returns `Some(..)` (i.e., `remove_account` left it behind) even though `get_account(state_update, &alice)` now returns `None`.
2. Follow-up integration step: recreate `alice` as a fresh account, then deliver the missing `DataReceipt` via `process_receipt`; assert the large postponed `ActionReceipt` executes against the newly created `alice` account (e.g. observe its state/storage mutated or gas consumed), proving cross-tenant inheritance of orphaned receipt state.
