Audit Report

## Title
Relayer reward paid and pending order settled without checking Ethereum execution success flag - (File: `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs`)

## Summary
`process_delivery_receipt` decodes a `DeliveryReceipt` containing a `success: bool` field sourced from the Ethereum Gateway's `InboundMessageDispatched` event, but never checks this flag before unconditionally paying the relayer's `order.fee` via `T::RewardPayment::register_reward` and removing the `PendingOrder` from storage. This allows a relayer to collect the full reward and have the pending order permanently cleared even when the corresponding command failed to execute on Ethereum.

## Finding Description
`submit_delivery_receipt` is a public extrinsic callable by any signed account; it verifies the event log/proof via `T::Verifier::verify`, decodes it into a `DeliveryReceipt` (which includes `success` decoded straight from the `InboundMessageDispatched(nonce, topic, success, reward_address)` event), and forwards it to `process_delivery_receipt`. Inside `process_delivery_receipt`, the code checks `receipt.gateway` against the configured gateway address, resolves the reward account, fetches the `PendingOrder` by `receipt.nonce`, and if `order.fee > 0` pays the reward, then unconditionally calls `<PendingOrders<T>>::remove(nonce)`. At no point is `receipt.success` inspected. Since proof verification only attests that the event genuinely occurred on Ethereum — not that the dispatched command succeeded — a genuine `success: false` event still passes verification and results in full reward payout and order removal, identical to a successful delivery.

## Impact Explanation
This violates the settlement invariant documented in the pallet's own module comment ("Fetch the pending order by nonce of the message, pay reward with fee attached in the order") which ties reward payment to successful message delivery. Paying the reward regardless of `success` results in unbacked/underpriced payout to relayers for failed deliveries, and removing `PendingOrders` on failure destroys the on-chain record that the message needs re-delivery, with no distinguishing event emitted (only `Event::MessageDelivered` is emitted regardless of outcome). This is a value-conservation and settlement-correctness violation for bridge rewards/state.

## Likelihood Explanation
Any unprivileged account holding a genuine event log + proof for a message whose Ethereum-side command execution failed (`success: false`, e.g., due to gas exhaustion or a reverting command) can call `submit_delivery_receipt` directly — no privileged relayer, validator, or governance role is required, making this fully attacker/relayer-reachable via a public extrinsic.

## Recommendation
Check `receipt.success` in `process_delivery_receipt`. Only invoke `T::RewardPayment::register_reward` when `success == true`. On `success == false`, still resolve the `PendingOrder` state (e.g., remove or mark for retry) but skip reward payment, and emit a distinct event (e.g., `MessageDeliveryFailed`) so downstream consumers of `PendingOrders` can differentiate successful settlement from failed execution.

## Proof of Concept
1. A message with `fee > 0` is enqueued via `do_process_message`, creating `PendingOrder { nonce, fee, block_number }` in `PendingOrders`.
2. On Ethereum, the corresponding command reverts/fails when executed on the Gateway, and the Gateway emits `InboundMessageDispatched(nonce, topic, success: false, reward_address)`.
3. Anyone with this log and a valid proof calls `submit_delivery_receipt(event)`.
4. `T::Verifier::verify` succeeds since the event genuinely occurred; `DeliveryReceipt::try_from` decodes `success: false` correctly.
5. `process_delivery_receipt` ignores `receipt.success`: `order.fee > 0` triggers `T::RewardPayment::register_reward(&reward_account, ..., order.fee)`, and `<PendingOrders<T>>::remove(nonce)` clears the entry as if delivery succeeded — verifiable by asserting reward issuance and storage removal in a unit test that constructs a `DeliveryReceipt` with `success: false` and calls `Pallet::<T>::process_delivery_receipt`.

		pub fn process_delivery_receipt(

			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });
