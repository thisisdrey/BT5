### Title
`expected` price guard in ExchangeTransactionContract can be bypassed via stale-state execution when `allowHardenExchangeCalculation` disables anti front-running exchange-transaction gating - (File: `framework/src/main/java/org/tron/core/db/Manager.java`)

### Summary
`ExchangeTransactionActuator` lets a sender set `expected`, the minimum amount of the other token they are willing to accept, and enforces it only inside `validate()` by simulating `exchangeCapsule.transaction(...)` against the pool state at validation time. `execute()` re-invokes `exchangeCapsule.transaction(...)` against the pool state at execution time but performs no re-check against `expected`. Under normal java-tron logic this TOCTOU gap is closed by `Manager.isExchangeTransaction`, which is used both to reject `ExchangeTransactionContract` transactions from `pushTransaction` (forcing them to only be included by `generateBlock`) and to allow at most one such transaction per block via the `continue` skip in `generateBlock`, guaranteeing the pool state seen at validate-time equals the state at execute-time. However, when `allowHardenExchangeCalculation()` is enabled, `isExchangeTransaction` unconditionally returns `false`, disabling both protections at once.

### Finding Description
- `ExchangeTransactionActuator.doValidate()` computes `anotherTokenQuant` from the current pool balances and requires `anotherTokenQuant >= tokenExpected` [2](#0-1) .
- `ExchangeTransactionActuator.execute()` independently recomputes `anotherTokenQuant` by calling `exchangeCapsule.transaction(...)` again and directly credits that recomputed amount to the account, with no comparison to `tokenExpected` at all [3](#0-2) [4](#0-3) .
- The pool's constant-product-style state (`firstTokenBalance`/`secondTokenBalance`) mutates with every trade, so if another transaction against the same `ExchangeCapsule` executes between this transaction's `validate()` and `execute()`, the amount actually received in `execute()` can be lower than what was checked in `validate()` — exactly mirroring the JUSDV1 issue where the price enforced at the check differs from the price realized at execution.
- Normally this window is closed structurally: `pushTransaction` calls `isExchangeTransaction` and throws `ContractValidateException("ExchangeTransactionContract is rejected")` for any exchange transaction submitted directly, forcing all such transactions through the pending pool/block-generation path [5](#0-4) ; and `generateBlock` uses the same check to `continue` (skip packing) any exchange transaction, in effect processing them serially/exclusively so that no other transaction touching the exchange pool executes between one exchange transaction's validate/execute pair [6](#0-5) .
- `isExchangeTransaction` itself short-circuits to `false` whenever `allowHardenExchangeCalculation()` is on, regardless of the actual contract type [1](#0-0) , which the test suite explicitly documents as bypass behavior: `isExchangeTransactionBypassedWhenHardenedEnabled` asserts `isExchangeTransaction` returns `false` once hardened mode is on [7](#0-6) . Once this returns `false`, both the `pushTransaction` rejection and the `generateBlock` exclusivity skip stop applying to `ExchangeTransactionContract`, so multiple exchange transactions against the same pool can now be pushed directly and packed together in the same block in any order the block producer/relayer chooses.

### Impact Explanation
With `allowHardenExchangeCalculation` enabled, a user's `expected` amount, the analog of JUSDV1's `expectPrice`, is only checked against a snapshot of the pool that can be stale by the time `execute()` actually runs, because other trades against the same pool can now be interleaved in the same block. A block producer (or any party able to influence transaction ordering within a block, e.g. via `rePush`/pending-pool ordering) can front-run a queued `ExchangeTransactionContract` with another trade that shifts the pool balance unfavorably, then let the original transaction execute; `execute()` will proceed and credit whatever the post-front-run pool state yields, without ever re-validating against the sender's originally specified `expected`. This lets an attacker extract value from exchange-pool traders exactly as described in the source report, where the price guard becomes irrelevant to the price actually realized.

### Likelihood Explanation
Reaching this requires only broadcasting a normal `ExchangeTransactionContract` (an unprivileged transaction any account can send) while `allowHardenExchangeCalculation` is enabled via committee proposal; no special permissions are needed, and exploitation only requires the ability to submit a second exchange transaction against the same pool positioned around the victim's transaction, which any transaction broadcaster can attempt.

### Recommendation
Re-validate `tokenExpected` against the amount actually computed inside `execute()` (not only in `validate()`), independent of whether `allowHardenExchangeCalculation` is enabled, so a stale-state execution cannot silently deliver less than the sender's specified minimum. Alternatively, do not let `allowHardenExchangeCalculation` disable the `isExchangeTransaction` exclusivity/rejection gating that keeps exchange transactions' validate/execute pairs atomic with respect to pool state.

### Proof of Concept
1. Enable `allowHardenExchangeCalculation` via committee proposal (`DynamicPropertiesStore.saveAllowHardenExchangeCalculation(1)`, exposed as a normal chain parameter).
2. Attacker submits Trade A against exchange pool `P`, and simultaneously the victim submits `ExchangeTransactionContract` Trade B against the same pool `P` with `expected = X`, computed against the pre-Trade-A pool state.
3. Because `isExchangeTransaction` now returns `false` (per `Manager.java:1809-1821`), `pushTransaction` no longer rejects either exchange transaction, and `generateBlock` no longer skips packing them for exclusivity, so both A and B can be included in the same block, with A processed before B.
4. When B's actuator executes, `ExchangeTransactionActuator.execute()` recomputes `anotherTokenQuant` against the pool state as mutated by A (per `ExchangeCapsule.transaction` in `ExchangeCapsule.java:124-168`) and credits it to the victim without ever comparing it back to `expected = X` (per `ExchangeTransactionActuator.java:64-98`), so the victim can receive less than `X` despite having explicitly specified `expected` to guard against exactly that outcome.
