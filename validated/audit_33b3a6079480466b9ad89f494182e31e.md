Found a concrete rounding-direction analog to the M-12 issue: `get_instructions_data_cost` in `CostModel` truncates (floors) the instruction-data-bytes cost instead of rounding up, which underprices the per-transaction cost used for block-limit/QoS accounting in the banking-stage scheduler.

### Title
Instruction data-bytes cost is rounded down, underpricing transactions against block/account cost limits - (File: cost-model/src/cost_model.rs)

### Summary
`CostModel::get_instructions_data_cost` computes the "data bytes" component of a transaction's cost by integer-dividing the raw instruction data length by `INSTRUCTION_DATA_BYTES_COST`, truncating any remainder. This mirrors the M-12 pattern (rounding a fee/cost-relevant quantity down instead of up per spec), except here the effect is on the transaction cost accounting that gates block/account CU limits and scheduler prioritization rather than bond price decay.

### Finding Description
`get_instructions_data_cost` is: [1](#0-0) 
```rust
fn get_instructions_data_cost(transaction: &impl TransactionMeta) -> u16 {
    transaction.instruction_data_len() / (INSTRUCTION_DATA_BYTES_COST as u16)
}
```
This is a floor (truncating) division: any instruction data length that is not an exact multiple of `INSTRUCTION_DATA_BYTES_COST` has its "fractional" cost silently dropped, rather than being rounded up. This value feeds directly into `data_bytes_cost` in `TransactionCost`, which is used by `calculate_transaction_cost` [2](#0-1)  to build the overall transaction cost recorded by `CostTracker` for block-cost and account-cost limit enforcement [3](#0-2) .

This contrasts with the other rounding computations in the same file, such as `calculate_pages_for_bytes`, which explicitly round up ("Just over one page should round up to 2 pages") [4](#0-3) , and `get_prioritization_fee` in the compute-budget crate, which explicitly rounds fees up to avoid underpricing [5](#0-4) . The instruction-data-bytes cost is the one place in the cost model that truncates instead of ceiling-rounds, which is inconsistent with the design intent visible elsewhere in the same module.

### Impact Explanation
Because the truncated remainder of instruction data length is never charged, an unprivileged transaction submitter can craft many small transactions whose instruction data length is just below a multiple of `INSTRUCTION_DATA_BYTES_COST`, each of which is under-costed relative to the actual bytes consumed. Aggregated across a block, this allows more "real" instruction-data-bytes work to be packed into the block/account cost limits than the cost model intends to allow — a mild, but real, QoS-evasion / underpriced-work effect analogous to M-12's "market price falls faster than expected" (here: "block accepts more raw work than its cost limit intends"). Note the `data_bytes_cost` field is `u16` and `INSTRUCTION_DATA_BYTES_COST` is a small constant, so the maximum truncation error per transaction is bounded and small — the severity is limited relative to overall block cost, which is likely why this has persisted, but it is a genuine deviation from "round up" cost-accounting semantics used elsewhere in the same file.

### Likelihood Explanation
This is trivially and deterministically reachable by any unprivileged user: they only need to control instruction data length in ordinary transactions submitted through banking stage, no special permissions required. It requires no crafted invalid state, only crafting the data length modulo `INSTRUCTION_DATA_BYTES_COST`.

### Recommendation
Change `get_instructions_data_cost` to round up (ceiling division), consistent with `calculate_pages_for_bytes` and `get_prioritization_fee`:
```rust
fn get_instructions_data_cost(transaction: &impl TransactionMeta) -> u16 {
    transaction
        .instruction_data_len()
        .div_ceil(INSTRUCTION_DATA_BYTES_COST as u16)
}
```

### Proof of Concept
1. Set `INSTRUCTION_DATA_BYTES_COST` to its configured constant value (defined in `cost-model/src/block_cost_limits.rs`, imported via `crate::block_cost_limits::*` at [6](#0-5) ).
2. Construct a transaction whose total instruction data length is `k * INSTRUCTION_DATA_BYTES_COST - 1` for some `k`.
3. Call `CostModel::calculate_cost` on it; observe `data_bytes_cost == k - 1` instead of the intended `k`, i.e. one unit of "page" cost worth of instruction bytes is never charged.
4. Repeat across many transactions packed into a block to accumulate additional uncosted instruction-data bytes beyond the intended `MAX_BLOCK_ACCOUNTS_DATA_SIZE_DELTA`/block cost accounting enforced by `CostTracker::would_fit` [7](#0-6) .

    fn would_fit(
        &self,
        tx_cost: &TransactionCost<impl TransactionWithMeta>,
    ) -> Result<(), CostTrackerError> {
        let cost: u64 = tx_cost.sum();

        if self.block_cost().saturating_add(cost) > self.limits.block_cost {
            // check against the total package cost
            return Err(CostTrackerError::WouldExceedBlockMaxLimit);
        }

        // check if the transaction itself is more costly than the account_cost_limit
        if cost > self.limits.account_cost {
            return Err(CostTrackerError::WouldExceedAccountMaxLimit);
        }

        let allocated_accounts_data_size =
            self.allocated_accounts_data_size + Saturating(tx_cost.allocated_accounts_data_size());

        if allocated_accounts_data_size.0 > self.limits.allocated_data_size {
            return Err(CostTrackerError::WouldExceedAccountDataBlockLimit);
        }

        // check each account against account_cost_limit,
        for account_key in tx_cost.writable_accounts() {
            match self.cost_by_writable_accounts.get(account_key) {
                Some(chained_cost) => {
                    if chained_cost.saturating_add(cost) > self.limits.account_cost {
                        return Err(CostTrackerError::WouldExceedAccountMaxLimit);
                    } else {
                        continue;
                    }
                }
                None => continue,
            }
        }

        Ok(())
    }

fn get_prioritization_fee(compute_unit_price: u64, compute_unit_limit: u64) -> u64 {
    let micro_lamport_fee: MicroLamports =
        (compute_unit_price as u128).saturating_mul(compute_unit_limit as u128);
    micro_lamport_fee
        .saturating_add(MICRO_LAMPORTS_PER_LAMPORT.saturating_sub(1) as u128)
        .checked_div(MICRO_LAMPORTS_PER_LAMPORT as u128)
        .and_then(|fee| u64::try_from(fee).ok())
        .unwrap_or(u64::MAX)
}
