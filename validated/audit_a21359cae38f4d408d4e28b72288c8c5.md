### Title
Missing slippage/minimum-amount protection in `ExchangeInjectActuator` allows exchange creator to lose funds from front-run ratio changes - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`)

### Summary
The `ExchangeInject` transaction, used by an exchange's creator to add liquidity to a TRX/TRC10 bancor-style `Exchange` pool, computes the required amount of the paired token purely from the pool's on-chain ratio at execution time, with no user-supplied bound on that amount. This is the same bug class as the reported Trident `addLiquidity` issue: the caller cannot express "the minimum/maximum amount of the other asset I'm willing to provide," so any ratio change between transaction broadcast and inclusion (e.g. a `ExchangeTransactionContract` trade against the same pool being mined first) silently changes how much of the paired asset is debited, without reverting.

### Finding Description
`ExchangeInjectContract` only carries `owner_address`, `exchange_id`, `token_id`, and `quant` [1](#0-0)  — unlike `ExchangeTransactionContract`, which additionally carries an `expected` field used as a slippage guard [2](#0-1) .

In `ExchangeTransactionActuator`, the validator explicitly protects the caller by rejecting the trade if the computed output is less than the caller-specified `expected`: `if (anotherTokenQuant < tokenExpected) { throw ... "token required must greater than expected"; }` [3](#0-2) .

`ExchangeInjectActuator` has no equivalent check. Both in `doValidate()` and in `execute()`, the amount of the paired token (`anotherTokenQuant`) is derived solely from the exchange's *current* on-chain balances and the supplied `tokenQuant`, with no user-provided minimum/maximum bound: [4](#0-3) 

The same unconstrained calculation is repeated in `execute()`: [5](#0-4) 

Because `anotherTokenQuant` is recomputed against whatever the pool ratio is at the moment the transaction is actually processed (not the ratio the creator observed when signing/broadcasting), and there is no analog of `tokenExpected`/`expected` to cap it, a ratio shift caused by an intervening `ExchangeTransactionContract` (a normal, permissionless trade against the same exchange) changes the amount of the paired asset that will be deducted from the creator's account. The creator has no way to bound this at submission time.

### Impact Explanation
This directly mirrors the reported bug class: the router/actuator does not let the liquidity provider specify acceptable bounds, so:
- If the ratio moves such that `anotherTokenQuant` grows beyond what the creator holds, the transaction fails at validation (`"balance is not enough"` / `"another token balance is not enough"`) [6](#0-5) , wasting the fee and forcing a retry under the same unresolved race.
- If the ratio moves such that the transaction still passes balance checks, the exchange creator ends up committing more (or a different proportion) of the paired asset to the pool than intended when they decided on the injection, with no reverting safeguard — an economic loss of funds relative to the terms the creator actually agreed to, since `ExchangeInjectActuator` provides no `expected`/minimum-amount parameter analogous to `ExchangeTransactionActuator`.

The exchange creator is a permissionless actor: any account that created an `Exchange` via `ExchangeCreateContract` can later call `ExchangeInject`, so this is reachable by an ordinary asset issuer without special privileges. The only access restriction is that the caller must be the exchange's own creator [7](#0-6) , which does not require any elevated role beyond having created the pool.

### Likelihood Explanation
Any user can submit a normal `ExchangeTransactionContract` trade against a public `Exchange` at any time, including immediately before a pending `ExchangeInjectContract` from the pool creator is packed into a block; block producers/other users can trivially reorder or race transactions targeting the same exchange ID. No special access or malicious-SR/witness behavior is required — this is reachable purely through the exchange/asset-issue query and transaction submission paths available to any unprivileged broadcaster.

### Recommendation
Add a caller-supplied bound to `ExchangeInjectContract` (and its actuator), analogous to the `expected` field already used in `ExchangeTransactionContract`, e.g. `min_another_token` (and optionally `max_another_token`), and enforce it in `ExchangeInjectActuator.doValidate()`/`execute()` by rejecting the transaction if the computed `anotherTokenQuant` falls outside the caller's specified bounds, rather than silently using whatever ratio exists at execution time.

### Proof of Concept
1. Exchange `E` holds `firstTokenBalance = 200000000`, `secondTokenBalance = 400000000` (ratio 1:2).
2. Creator observes this ratio off-chain and broadcasts `ExchangeInjectContract` with `token_id = first`, `quant = 100000000`, expecting `anotherTokenQuant ≈ 200000000` (per the ratio-based formula in `doValidate`/`execute`) [8](#0-7) .
3. Before the inject transaction is packed, another user submits `ExchangeTransactionContract` trading against the same exchange, shifting the ratio, e.g. to 1:3.
4. The pending Inject is then validated/executed against the new ratio, computing a materially different `anotherTokenQuant` than the creator expected — either causing the tx to fail (`"another token balance is not enough"`) or to succeed while debiting an amount the creator did not intend, since no `expected`/min bound exists to protect them [9](#0-8) .
