### Title
Missing bounds check on attacker-controlled word offset/length in `ValidateMultiSign` precompiled contract leads to out-of-bounds array access - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
`ValidateMultiSign.execute()` and its helpers `extractBytesArray` / `extractSigArray` derive array indices directly from attacker-controlled calldata words without validating that the computed index stays within the bounds of the `words` array parsed from that calldata. This mirrors the CVE-2018-11233 bug class: insufficient sanity-checking of an attacker-influenced offset/length before it is used to read memory, resulting in an out-of-bounds access.

### Finding Description
`ValidateMultiSign` is a precompiled contract reachable from any TVM `CALL`/`STATICCALL` a contract deployer or caller issues. Its `execute(byte[] rawData)`: [1](#0-0) 

`words = DataWord.parseArray(rawData)` builds an array sized to `rawData.length / WORD_SIZE`. `words[3]` is fully attacker-controlled 32-byte value. The code computes `words[3].intValueSafe() / WORD_SIZE` and uses it directly as an array index into `words` (`words[words[3].intValueSafe() / WORD_SIZE]`) with no check that this index is `< words.length`.

That same unchecked offset is then passed into `extractBytesArray` / `extractSigArray`: [2](#0-1) 

These helpers only guard the initial `offset > words.length - 1` case, but the length `len` read from `words[offset]` (also attacker-controlled) is never checked against the remaining size of the `words` array. The loop then reads `words[offset + i + 1]` for `i` up to `len - 1`, which can walk arbitrarily far past the end of the `words` array (an `ArrayIndexOutOfBoundsException`) — the Java analog of the native OOB read described in CVE-2018-11233, where a length/offset field derived from untrusted input was not sanity-checked before an array/memory read.

### Impact Explanation
A crafted `TriggerSmartContract`/`CreateSmartContract` calldata that invokes the `ValidateMultiSign` precompile address with a small `rawData` but a large `words[3]` or `words[offset]` value causes an uncaught `ArrayIndexOutOfBoundsException` deep inside TVM opcode/precompile execution. If this runtime exception is not caught by a generic handler somewhere in the `Program`/`Runtime` execution stack, it can escape transaction execution during block application in `Manager`, crashing or halting node processing for any node that must re-execute the same transaction (full nodes, SRs). This satisfies the "node crash or halt" impact bar. I was not able to fully trace whether an outer catch (e.g., a blanket `catch (Throwable)` in the VM `Program`/`Runtime` layer) converts this into a normal revert rather than crashing the node — this could not be verified within the available search budget, so the crash/halt impact should be confirmed against the exact exception-handling wrapper around precompiled contract execution before treating this as fully proven.

### Likelihood Explanation
The precompile is reachable by any unprivileged account that can deploy or call a smart contract and issue a low-level `CALL` to the `ValidateMultiSign` address with attacker-chosen calldata — no special privilege, ordering, or state precondition is required.

### Recommendation
In `extractBytesArray`/`extractSigArray`, validate that `len` and every derived index (`offset + i + 1`, `offset + bytesOffset + 1`) remain within `words.length` before use, returning an empty array (or failing the precompile call) otherwise. In `ValidateMultiSign.execute()`, validate that `words[3].intValueSafe() / WORD_SIZE` is `< words.length` before dereferencing `words[...]`, mirroring the existing `isValidAbiEncoding` guard used elsewhere in the same file.

### Proof of Concept
Craft a `TriggerSmartContract` calling the `ValidateMultiSign` precompiled address with `rawData` shorter than expected but with word[3] set to a very large value, e.g.:
- word0 (address) = valid 32-byte address slot
- word1 (permissionId) = 0
- word2 (data) = 0
- word3 (offset field) = `0x00000000000000000000000000000000000000000000000000000000FFFFFFF0` (huge offset)

Total `rawData` length kept at only 4 words (128 bytes) so `words.length == 4`. `words[3].intValueSafe() / WORD_SIZE` evaluates to an index far greater than `words.length`, causing `words[idx]` at PrecompiledContracts.java:1067 to throw `ArrayIndexOutOfBoundsException` during TVM execution of the triggered transaction.

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
