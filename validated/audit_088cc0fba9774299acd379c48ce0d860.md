### Title
`RPCCallReadOnlyRequestHandler` performs no authorization check on `/v2/contracts/call-read/:principal/:contract/:function`, unlike `RPCFastCallReadOnlyRequestHandler` on `/v3/contracts/fast-call-read/...` - ([File: stackslib/src/net/api/callreadonly.rs])

### Summary
`RPCCallReadOnlyRequestHandler::try_parse_request` in `stackslib/src/net/api/callreadonly.rs` contains no `auth` field and performs no authorization/header comparison before parsing and later executing the request, whereas its sibling `RPCFastCallReadOnlyRequestHandler::try_parse_request` in `stackslib/src/net/api/fastcallreadonly.rs` requires `self.auth` to be `Some` and the incoming `authorization` header to match it, returning `400`/`401` otherwise. This confirms the `/v2/contracts/call-read/:principal/:contract/:function` endpoint executes bounded-compute read-only Clarity calls for any remote, unauthenticated caller, regardless of node `auth_token` configuration, in contrast to the `/v3/contracts/fast-call-read` endpoint which enforces the auth header.

### Finding Description
The equality claimed by the question — that `RPCCallReadOnlyRequestHandler` has zero auth-gate while `RPCFastCallReadOnlyRequestHandler` requires header equality against `self.auth` — is confirmed by direct code inspection. `RPCCallReadOnlyRequestHandler` (struct at `stackslib/src/net/api/callreadonly.rs` lines 59-75) has fields for `maximum_call_argument_size`, cost/time/memory limits, and Clarity-call state, but no `auth` field at all. Its `try_parse_request` (lines 130-163) only validates content length, content type, parses contract/function from the path, and parses the JSON body via `parse_read_only_call_body` — there is no header comparison anywhere in the file.

By contrast, `RPCFastCallReadOnlyRequestHandler` (lines 44-73 and `try_parse_request` at lines 94-144 in `stackslib/src/net/api/fastcallreadonly.rs`) explicitly requires `self.auth` to be `Some(password)`, requires the `authorization` header to be present, and rejects the request with `400 Bad Request` (if no auth configured) or `401 Unauthorized` (if the header doesn't match) before any further parsing occurs.

This means that any remote, unprivileged client that can reach the RPC port can send a `POST /v2/contracts/call-read/:principal/:contract/:function` request with a JSON body naming any contract/function/args, and it will proceed straight into `try_handle_request`, which calls `chainstate.maybe_read_only_clarity_tx` at the resolved `TipRequest` and executes the target Clarity function under a bounded cost/time/memory budget (`read_only_call_limit`, `read_only_max_execution_time`, `read_only_call_max_mem_bytes`) — with **no** dependency on the node's configured `auth_token` whatsoever.

### Impact Explanation
Any unprivileged remote party can invoke arbitrary read-only Clarity contract-call execution (bounded by cost/time/memory limits) on a node without ever presenting any credential, regardless of whether the operator configured `auth_token`. This constitutes a bounded-compute-DoS surface on a read endpoint: repeated calls to expensive-but-within-limit read-only functions consume node CPU/memory cycles that an operator believed were access-controlled. It also represents a real inconsistency/security-expectation gap: the newer `/v3/contracts/fast-call-read` endpoint enforces `auth_token`, while the original `/v2/contracts/call-read` endpoint (which performs equivalent execution of arbitrary contract functions) does not, despite both reaching the same execution primitive (`maybe_read_only_clarity_tx` + `execute_contract`). This matches the "High — bounded compute DoS on a read endpoint" impact category, since the endpoint is unauthenticated by design (this is not a bug that bypasses a guard — the guard simply doesn't exist for this handler) rather than a crash or forged-data issue.

### Likelihood Explanation
No preconditions beyond normal RPC-port reachability: the attacker needs only to be able to send arbitrary HTTP requests to the node's RPC port, which unprivileged remote parties can always do. It requires no knowledge of `auth_token`, no privileged role, and no interaction with peer/StackerDB state. It's fully repeatable per request, and the endpoint is one of the standard historically-public V2 Stacks node RPC endpoints (call-read has always been documented as unauthenticated in stacks-core prior to the newer fast-call-read variant), so this is largely expected/by-design behavior rather than a newly introduced bug — but the specific claim in the question (that `auth_token` does not uniformly gate both call-read endpoints) is factually correct based on the code.

### Recommendation
If the intent is for `auth_token` to uniformly gate both read-only call endpoints, add an equivalent auth-header check to `RPCCallReadOnlyRequestHandler::try_parse_request` in `stackslib/src/net/api/callreadonly.rs`, mirroring the check in `RPCFastCallReadOnlyRequestHandler::try_parse_request` (`stackslib/src/net/api/fastcallreadonly.rs` lines 101-110). Alternatively, if `/v2/contracts/call-read` is intentionally meant to remain publicly accessible (as it has historically been part of the public V2 RPC surface), document this explicitly so operators do not assume `auth_token` restricts all read-only call endpoints uniformly.

### Proof of Concept
Rust net test outline (using existing `stackslib/src/net/api/tests/callreadonly.rs` and `fastcallreadonly.rs` test harnesses):
1. Construct a `TestRPC`/`StacksNodeState` fixture with `ConnectionOptions.auth_token = Some("secret".to_string())`.
2. Send a `POST /v2/contracts/call-read/<addr>/<contract>/<function>` request via `RPCCallReadOnlyRequestHandler` with no `authorization` header at all.
3. Assert the response is `200 OK` with a valid `CallReadOnlyResponse` — i.e., the call executes despite no auth header being sent.
4. Send the analogous unauthenticated `POST /v3/contracts/fast-call-read/<addr>/<contract>/<function>` request via `RPCFastCallReadOnlyRequestHandler` configured with `auth: Some("secret".to_string())`.
5. Assert this second request fails at `try_parse_request` with `Error::Http(401, "Unauthorized")`, confirming the asymmetry (`stackslib/src/net/api/fastcallreadonly.rs` lines 105-110 vs. the complete absence of such a check in `stackslib/src/net/api/callreadonly.rs` lines 130-163).     /// Try to decode this request.
    fn try_parse_request(
        &mut self,
        preamble: &HttpRequestPreamble,
        captures: &Captures,
        query: Option<&str>,
        body: &[u8],
    ) -> Result<HttpRequestContents, Error> {
        let content_len = preamble.get_content_length();
        if !(content_len > 0 && content_len < self.maximum_call_argument_size) {
            return Err(Error::DecodeError(format!(
                "Invalid Http request: invalid body length for CallReadOnly ({})",
                content_len
            )));
        }

        if preamble.content_type != Some(HttpContentType::JSON) {
            return Err(Error::DecodeError(
                "Invalid content-type: expected application/json".to_string(),
            ));
        }

        let contract_identifier = request::get_contract_address(captures, "address", "contract")?;
        let function = request::get_clarity_name(captures, "function")?;
        let parsed = parse_read_only_call_body(body, self.read_only_call_max_mem_bytes)?;

        self.contract_identifier = Some(contract_identifier);
        self.function = Some(function);
        self.sender = Some(parsed.sender);
        self.sponsor = parsed.sponsor;
        self.arguments = Some(parsed.arguments);
        self.parse_retained_mem_bytes = parsed.retained_mem_bytes;

        Ok(HttpRequestContents::new().query_string(query))
    }
