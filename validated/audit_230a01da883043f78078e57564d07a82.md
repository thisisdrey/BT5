### Title
Unbounded growth of `DelegatedResourceAccountIndexCapsule.fromAccountsList`/`toAccountsList` allows griefer-driven state bloat and DoS on unfreeze/delegate index maintenance - (File: actuator/src/main/java/org/tron/core/actuator/FreezeBalanceActuator.java, actuator/src/main/java/org/tron/core/actuator/UnfreezeBalanceActuator.java, chainbase/src/main/java/org/tron/core/capsule/DelegatedResourceAccountIndexCapsule.java)

### Summary
The Beanstalk report describes an attacker being able to spam small "plots" to a victim, causing an unbounded on-chain array (`plotIndexes`) to grow until removal operations (which linearly scan the array) revert with out-of-gas. java-tron's legacy resource-delegation index (`DelegatedResourceAccountIndexCapsule`) has the same architectural weakness: a per-account array (`fromAccounts`/`toAccounts`) that any unprivileged address can append entries to, with no cap on size, and whose removal/maintenance requires full-list operations.

### Finding Description
When `FreezeBalanceActuator.delegateResource()` handles a `FreezeBalanceContract` with a `receiverAddress` and delegation is enabled (`!dynamicStore.supportAllowDelegateOptimization()`, the pre-"delegate optimization" legacy index path), it fetches or creates a `DelegatedResourceAccountIndexCapsule` for both the owner and receiver and appends the counterparty address to `toAccounts`/`fromAccounts` if not already present: [1](#0-0) 

Because the de-duplication check (`!toAccountsList.contains(...)`) only prevents the *same* owner→receiver pair from being added twice, an attacker who controls many distinct addresses (Sybil addresses) can freeze the minimum required balance and delegate to a single victim receiver repeatedly from each address, each time appending a new, unique entry to the victim's `fromAccountsList` via `DelegatedResourceAccountIndexCapsule.addFromAccount`: [2](#0-1) 

There is no size cap or maximum-entry-count validation anywhere in `FreezeBalanceActuator.validate()`/`execute()` on the number of distinct delegators/delegatees that can be recorded for an account (confirmed by the absence of any `MAX_DELEGATE`/list-length-check constants comparable to the `Frozen supply list length is too long` guard that exists for `AssetIssueActuator`'s `frozenSupplyList`). This lets the victim's index array grow without bound.

Later, when resources are unfrozen and the delegation is fully cleared, `UnfreezeBalanceActuator.execute()` must locate and remove the counterpart entry from both the owner's and receiver's index lists by rebuilding an `ArrayList`, calling `List.remove(Object)` (an O(n) linear scan/removal), and writing the full array back to the store: [3](#0-2) 

Every write of the index capsule re-serializes the entire protobuf-backed list (`setAllToAccounts`/`setAllFromAccounts` rebuild the whole `toBuilder().clearToAccounts().addAllToAccounts(...)`), so both the ongoing appends and any later removal scale linearly (or worse, due to serialization) with the number of spammed entries.

### Impact Explanation
An attacker can grow a victim's `DelegatedResourceAccountIndexCapsule` to an arbitrarily large size using only the minimum permitted TRX freeze-and-delegate amount from many disposable addresses, at low cost. This:
- Bloats the size of the victim's `DelegatedResourceAccountIndexStore` entry, increasing the CPU/time cost of every subsequent legitimate `FreezeBalanceActuator`/`UnfreezeBalanceActuator` operation touching that account's index (each requires reading, scanning, and rewriting the full list).
- Degrades block processing time for transactions touching the victim account, since each `execute()` call in this path performs full-list rebuild and serialization proportional to attacker-controlled list size.
- Can be queried via the wallet API (`getDelegatedResourceAccountIndex`), amplifying the read/serialization cost for any client requesting that account's data, since the API returns the full list without pagination.

This is a resource-exhaustion / node-processing-degradation risk analogous to the reported DoS, though unlike the Beanstalk case it does not appear to cause a hard revert (Java `ArrayList.remove(Object)` silently no-ops if not found rather than throwing), so the "victim can never unfreeze" guarantee from the original report is not fully reproduced here — the impact is state bloat and processing-time degradation rather than a guaranteed transaction revert.

### Likelihood Explanation
This path is only reachable while `dynamicStore.supportAllowDelegateOptimization()` is false, i.e., on chains/forks that have not yet activated the delegate-optimization hard fork that migrated to the new keyed (`FROM_PREFIX`/`TO_PREFIX`) index model in `DelegatedResourceAccountIndexStore`, which avoids this array-growth pattern entirely (confirmed via `DelegateResourceActuator`/`DelegateResourceProcessor`, which always use the new per-pair-key model). On networks where this optimization is already enabled (which appears to be the case for the primary/new `DelegateResourceContract` flow), this specific array-growth vector is not exploitable. Exploitability therefore depends on chain configuration/fork status of `supportAllowDelegateOptimization`.

### Recommendation
- Enforce a maximum size on `toAccounts`/`fromAccounts` in the legacy `DelegatedResourceAccountIndexCapsule` (mirroring the `Frozen supply list length is too long` check pattern in `AssetIssueActuator`), or reject new legacy-format delegations once a threshold is reached.
- Ensure the new keyed delegation-index model (`FROM_PREFIX`/`TO_PREFIX`, per-pair storage) is the only path exercised on all networks (retire/disable the legacy array-based `DelegatedResourceAccountIndexCapsule` list mutation code once `supportAllowDelegateOptimization` is active everywhere).
- Add rate limiting or minimum economic cost per unique delegator/delegatee relationship to make Sybil-based array-growth attacks economically unattractive.

### Proof of Concept
1. Attacker generates N distinct addresses (A1...AN), each funded with the minimum TRX required to freeze and delegate (`frozenBalance` for `BANDWIDTH`/`ENERGY` via `FreezeBalanceContract` with `receiverAddress` = victim), while `dynamicStore.supportAllowDelegateOptimization()` is `false`.
2. For each Ai, submit a `FreezeBalanceContract` transaction delegating to the victim's address as `receiverAddress`.
3. Each transaction triggers `FreezeBalanceActuator.delegateResource()`, which appends Ai to the victim's `fromAccountsList` in `DelegatedResourceAccountIndexCapsule` (since Ai is never previously present) — [4](#0-3) .
4. Repeat for large N; the victim's index entry grows unbounded with no validation rejecting it.
5. Any subsequent `UnfreezeBalanceActuator` execution touching the victim's account, or any `getDelegatedResourceAccountIndex`/`getDelegatedResourceAccountIndexV2` API query against the victim, now incurs O(N) list scan/rebuild/serialization cost — [5](#0-4) .

  public void addFromAccount(ByteString fromAccount) {
    this.delegatedResourceAccountIndex = this.delegatedResourceAccountIndex.toBuilder()
        .addFromAccounts(fromAccount)
        .build();
  }

  public void removeFromAccount(ByteString fromAccount) {
    if (getFromAccountsList().contains(fromAccount)) {
      List<ByteString> fromList = new ArrayList<>(getFromAccountsList());
      fromList.remove(fromAccount);
      setAllFromAccounts(fromList);
    }
  }
