### Title
Multi-signature weight double-counting in `ValidateMultiSign` TVM precompile allows a single key to satisfy a multi-signer threshold - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The CVE describes an authorization/identity-verification routine (`SOA2Login::commented`) whose flawed comparison logic let one identity be accepted as another, bypassing intended access control. The closest reachable analog in java-tron is the signature/weight-accumulation loop of the `ValidateMultiSign` precompiled contract, which any smart contract can call via `TriggerSmartContract` to check on-chain multi-signature/multi-permission authorization. Its de-duplication check is built around comparing the *raw signature bytes* (via `executedSignList`), not around the *recovered signer address* alone, allowing the same private key to be counted multiple times toward the required threshold weight if it supplies more than one distinct valid ECDSA signature over the same hash.

### Finding Description
`PrecompiledContracts.ValidateMultiSign.execute` iterates the caller-supplied signature array and accumulates `totalWeight` for each recovered address against a permission's threshold: [1](#0-0) 

For each signature, it recovers the signer address and checks whether that address is already present in `executedSignList`:
- If the address is present **and** the exact same `sign` bytes (address+signature) were already seen, it `continue`s (true duplicate skip, for CPU accounting) - [2](#0-1) .
- If the address is present but the raw signature bytes differ (which happens naturally with standard non-deterministic ECDSA signing, since two signatures over the same hash by the same key normally have different nonces and therefore different byte encodings), the code does **not** skip weight accumulation - it only calls `MUtil.checkCPUTime()` (a CPU/DoS guard) and then falls through to add that address's weight to `totalWeight` again: [3](#0-2) .

Because ECDSA signing (absent RFC6979 deterministic nonces) yields different `(r, s)` byte values for repeated signs of the same message by the same key, an attacker who controls a single key that is a member of a `Permission` can generate several distinct valid signatures over the identical `hash` and submit them all as if they were independent signers. The threshold check `totalWeight >= permission.getThreshold()` then can be satisfied using only one real signer's weight repeated N times, instead of requiring N independent key holders as the permission model intends: [4](#0-3) .

This mirrors the CVE's bug class: a verification routine meant to authenticate/authorize based on distinct credentials fails to properly bind identity/authorization to a canonical, non-repeatable representation, letting one credential be replayed to impersonate multiple required approvers.

Note: the equivalent transaction-level weight check `TransactionCapsule.checkWeight` explicitly guards against this by keying its "already signed" map on the recovered `address` once `ForkController.instance().pass(VERSION_4_7_1)` is active [5](#0-4) , confirming this exact double-counting-by-address class of bug was previously recognized and patched for the transaction path. The `ValidateMultiSign` precompile, however, still uses a signature-bytes-based comparison (`executedSignList` containing `merge(recoveredAddr, sign)` tuples) rather than an address-based one, so it does not benefit from that fix.

### Impact Explanation
`ValidateMultiSign` (TVM precompile `0x66`... exposed to any Solidity contract) is designed to let smart contracts (e.g., custom multisig wallets, DAOs, exchange/order-approval contracts, or any contract that gates high-value operations behind an on-chain "M-of-N approved" check) verify multi-party authorization without needing a full transaction signature set. If a contract relies on this precompile to gate fund transfers, permission changes, or other privileged actions, an attacker holding just one of the required keys (e.g., a compromised/low-trust delegate key with non-zero weight) can forge the additional weight needed to reach the threshold by supplying multiple distinct signatures from that same key, bypassing the requirement for the other independent signers entirely. This can lead to unauthorized execution of privileged contract logic and theft/misuse of funds in any dependent contract that trusts this precompile's boolean result as proof of collective authorization.

### Likelihood Explanation
The precompile is reachable by any unprivileged account through a normal `TriggerSmartContract` call - no special privilege, staking, or witness status is required. Generating multiple distinct ECDSA signatures over the same hash from the same private key is trivial (just call `sign()` twice; unless the signing library enforces RFC6979 deterministic k, which is not guaranteed for external wallets/tools producing input to this precompile). No consensus/fork gate currently restricts this precompile's comparison logic the way `checkWeight` was hardened, so the flaw is present in the currently indexed code without needing a future hard fork to reach it.

### Recommendation
Change the duplicate-signer check in `ValidateMultiSign.execute` to key off the recovered `address` alone (not the raw signature bytes), matching the pattern already used in `TransactionCapsule.checkWeight`: once an address has been counted toward `totalWeight`, any further signature recovering to that same address must be skipped entirely (not merely CPU-rate-limited), regardless of whether the raw signature bytes differ.

### Proof of Concept
1. Deploy/prepare an account with an `Active` `Permission` requiring threshold weight 2, composed of two distinct keys `key1` (weight 1) and `key2` (weight 1), similar to the fixture in `ValidateMultiSignContractTest.testDifferentCase` [6](#0-5) .
2. Compute `toSign = sha256(merge(address, permissionId, sha256(data)))` as the precompile expects [7](#0-6) .
3. Using only `key1`'s private key, call `key1.sign(toSign)` twice, obtaining two syntactically different but both-valid signatures `sigA` and `sigB` (differing nonces produce differing byte encodings).
4. Submit `signatures = [sigA, sigB]` (no `key2` signature at all) to `ValidateMultiSign.execute`.
5. Trace: first signature recovers `key1`, `executedSignList` is empty so no skip; weight 1 added, total = 1. Second signature also recovers `key1`; `executedSignList` contains `key1`'s address but not this exact `sign` byte tuple, so the inner `continue` is not taken - `MUtil.checkCPUTime()` runs, then weight 1 is added again, total = 2 - `totalWeight (2) >= threshold (2)`, and the precompile returns `DataWord.ONE()` (success), even though only one real key ever authorized the action.
