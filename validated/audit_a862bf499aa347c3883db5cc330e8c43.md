### Title
Downloaded Atlas attachment content is stored without re-validating length against `attachments_max_size` - ([File: stackslib/src/net/atlas/download.rs])

### Summary
`AttachmentsDownloader::run`'s `Done` branch calls `AtlasDB::insert_instantiated_attachment` directly on every `Attachment` returned from a peer's `GetAttachmentResponse`, without calling the size-check helper `AtlasDB::should_keep_attachment` that exists specifically to enforce `attachments_max_size`. That helper is only used for attachments posted locally through transactions, not for attachments fetched from remote peers.

### Finding Description
`AtlasConfig::validate` only enforces that `attachments_max_size` is at least `ATTACHMENTS_MAX_SIZE_MIN` [1](#0-0) . The only place that actually compares an `Attachment`'s content length against `self.atlas_config.attachments_max_size` is `AtlasDB::should_keep_attachment`: [2](#0-1) 

In `download.rs`, the `AttachmentsDownloader::run` `Done` branch iterates `context.attachments.drain()` (populated from parsed `GetAttachmentResponse` bodies received from peers) and calls `network.atlasdb.insert_instantiated_attachment(&attachment)` directly — `should_keep_attachment` is never invoked on this path: [3](#0-2) 

`insert_instantiated_attachment` itself performs no length check; it just inserts `attachment.content` into the `attachments` table: [4](#0-3) 

On the wire-parsing side, `RPCGetAttachmentRequestHandler::try_parse_response`/`decode_atlas_get_attachment` deserialize the JSON body into a `GetAttachmentResponse` with no length cap tied to `attachments_max_size`; the only length bound applied is whatever the generic HTTP body/message-size limit is (a bound unrelated to the Atlas-specific `attachments_max_size` constant) [5](#0-4) .

### Impact Explanation
I was not able to fully trace the code path within `download.rs` between the HTTP response arriving and `context.attachments` being populated (this section of the file was outside what I could retrieve within the tool budget), so I cannot conclusively confirm whether an intermediate size check exists elsewhere in the state machine before an attachment reaches the `Done` branch. What is confirmed is that the storage call site itself (`insert_instantiated_attachment`) performs no `attachments_max_size` check, and the only helper that does (`should_keep_attachment`) is not called in this path.

### Likelihood Explanation
Uncertain — depends on whether generic HTTP body-size limits (unrelated to the named `attachments_max_size` constant) already bound the response before it reaches this code, which I could not verify within the available context.

### Recommendation
Call `AtlasDB::should_keep_attachment` (or an equivalent explicit `attachment.content.len() as u32 <= attachments_max_size` check) on every downloaded `Attachment` in the `Done` branch of `AttachmentsDownloader::run` before calling `insert_instantiated_attachment`, mirroring the check already applied to locally posted attachments.

    pub fn should_keep_attachment(
        &self,
        contract_id: &QualifiedContractIdentifier,
        attachment: &Attachment,
    ) -> bool {
        if !self.atlas_config.contracts.contains(contract_id) {
            info!(
                "Atlas: will discard posted attachment - {} not in supported contracts",
                contract_id
            );
            return false;
        }
        if attachment.content.len() as u32 > self.atlas_config.attachments_max_size {
            info!("Atlas: will discard posted attachment - attachment too large");
            return false;
        }
        true
    }

    pub fn insert_instantiated_attachment(
        &mut self,
        attachment: &Attachment,
    ) -> Result<(), db_error> {
        let now = util::get_epoch_time_secs() as i64;
        let tx = self.tx_begin()?;
        tx.execute(
            "INSERT OR REPLACE INTO attachments (hash, content, was_instantiated, created_at) VALUES (?, ?, 1, ?)",
            params![attachment.hash(), attachment.content, now],
        )?;
        tx.execute(
            "UPDATE attachment_instances SET is_available = 1 WHERE content_hash = ?1 AND status = ?2",
            params![attachment.hash(), AttachmentInstanceStatus::Checked],
        )?;
        tx.commit()?;
        Ok(())
    }
