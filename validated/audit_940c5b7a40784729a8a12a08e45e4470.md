## Title
Unbounded offset/length from attacker-controlled call data causes uncaught out-of-bounds array read in `ValidateMultiSign`/`BatchValidateSign` precompiles - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The vim CVE is a class of bug where an attacker-controlled offset/length pair, taken from untrusted structured data, is used to index into a buffer without validating that `offset`/`offset+length` stay within the buffer's actual bounds, causing an out-of-bounds read. The same pattern exists in java-tron's `ValidateMultiSign` and `BatchValidateSign` precompiled contracts, which are reachable by any TVM contract call (e.g., `abi.decode`/low-level `call` to precompile addresses) supplying attacker-controlled ABI-encoded `data`.

### Finding Description
`ValidateMultiSign.execute` and `BatchValidateSign.doExecute` parse caller-supplied call data into a `DataWord[] words` array and then compute array offsets directly from that untrusted data, e.g. `words[3].intValueSafe() / WORD_SIZE`, and pass them into `extractBytesArray`/`extractSigArray`: [1](#0-0) 

These helpers use the untrusted offset/length to slice into `words` and the raw `data` array without validating that the computed indices are within bounds: [2](#0-1) 

`extractBytes` calls `Arrays.copyOfRange(data, offset, offset + len)` directly with attacker-influenced `offset`/`len`: [3](#0-2) 

When `VMConfig.allowTvmOsaka()` is disabled (or when the caller crafts inputs that pass `isValidAbiEncoding` but contain fabricated internal offset words, since that check only validates the outer container's word-alignment, not the nested offsets derived from `words[3]`/`words[1]`/`words[2]`), a malicious offset value can push `offset + len` beyond `words.length` or `data.length`. This causes `ArrayIndexOutOfBoundsException` / `NegativeArraySizeException` at `extractBytes`, `extractBytesArray`, or `extractSigArray`, occurring **before** the `try { ... } catch (Throwable t) { ... }` block in `ValidateMultiSign.execute` (that catch only wraps the signature-recovery/weight-calculation loop, not the initial offset parsing and extraction calls) — see the surrounding method: [4](#0-3) 

`BatchValidateSign.execute` does wrap `doExecute` in a `try/catch Throwable`, but `ValidateMultiSign.execute` does not wrap the offset-parsing/extraction section, so an uncaught runtime exception can propagate out of the precompiled contract execution path.

### Impact Explanation
An uncaught `ArrayIndexOutOfBoundsException`/`NegativeArraySizeException` escaping precompile execution during transaction/contract execution can abort transaction processing unexpectedly or, depending on how far up the call stack it is caught (or not caught) in `Program`/`Runtime`/actuator execution, could cause inconsistent node behavior for that transaction, denial of service for the calling contract, or, if handling differs between nodes (e.g., a node crash vs. silent revert), a consensus/liveness risk. At minimum this is a reachable crash/DoS in a code path directly triggered by any contract call, matching the "node crash or halt" acceptance criterion.

### Likelihood Explanation
`ValidateMultiSign` and `BatchValidateSign` are TVM precompiled contracts callable by any deployed smart contract via a low-level `call`/`staticcall` to their designated addresses, meaning any unprivileged party who can deploy or invoke a contract can trigger this path with fully attacker-controlled `data`. No special privilege, whitelisting, or SR/witness status is required.

### Recommendation
Add explicit bounds validation in `extractBytesArray`, `extractSigArray`, and `extractBytes` (and at the point where `words[3].intValueSafe() / WORD_SIZE` etc. are computed) to ensure computed offsets/lengths do not exceed `words.length` or `data.length` before slicing, returning a failure `Pair.of(false, EMPTY_BYTE_ARRAY)` instead of throwing. Additionally, wrap the offset-parsing/extraction section of `ValidateMultiSign.execute` in the same defensive `try/catch` used later in the method, consistent with `BatchValidateSign.execute`'s outer `try/catch Throwable`.

### Proof of Concept
Deploy a contract that performs a `staticcall`/`call` to the `ValidateMultiSign` precompile address with ABI-encoded data where the 4th word (used as `words[3]`, the signature-array offset) is set to a very large value (e.g., `0xFFFFFFFF`). This causes `words[3].intValueSafe() / WORD_SIZE` to compute an out-of-range index into `words[]`, triggering an `ArrayIndexOutOfBoundsException` in the subsequent `extractBytesArray`/`extractSigArray` call before the existing `try/catch` block is reached, in the unpatched path where `VMConfig.allowTvmOsaka()`/`allowTvmSelfdestructRestriction()` gating does not prevent the malformed offset from reaching `extractBytes`.

**Caveat / uncertainty:** I could not fully trace the exact caller-level exception handling around `PrecompiledContract.execute(...)` (i.e., in `Program`/`VMActuatorImpl`/`Runtime`) within the available index to confirm definitively whether an uncaught exception here is swallowed at a higher layer (reverting only the current call frame) versus propagating to crash transaction processing entirely. If a background Devin session is available, tracing `Program`'s precompiled-contract invocation site and the top-level actuator's exception handling would confirm the precise blast radius (call-revert vs. node-level failure).

    if (offset > words.length - 1) {

    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
