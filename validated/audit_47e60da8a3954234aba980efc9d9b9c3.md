### Title
Exchange AMM pool `Inject`/`Withdraw` operations lack minimum-output (slippage) protection, unlike `ExchangeTransactionActuator` - ([File: actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java], [File: actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java])

### Summary
TRON's built-in `Exchange` (Bancor-style AMM) feature computes `anotherTokenQuant` for `ExchangeInjectContract` and `ExchangeWithdrawContract` purely from the pool's live reserve ratio at execution time, with no caller-supplied minimum-output bound. This mirrors the GMX report's root cause exactly (`minMarketTokens`/`minLongTokenAmount`/`minShortTokenAmount` hardcoded to 0): the amount actually received depends on the pool state *at the time the transaction executes*, not at the time it was signed, and nothing in validation enforces a floor on the received amount.

### Finding Description
`ExchangeTransactionActuator` (the "trade" operation) explicitly protects the caller from slippage: the contract carries a `tokenExpected` field, and `doValidate()` rejects the transaction if the computed output is below it: [1](#0-0) 

By contrast, `ExchangeInjectActuator` and `ExchangeWithdrawActuator` — the two operations that add/remove liquidity to the pool — compute the counter-token amount solely from the current on-chain reserve ratio, with no equivalent minimum/expected parameter in `ExchangeInjectContract`/`ExchangeWithdrawContract`: [2](#0-1) 
For withdraw, `anotherTokenQuant` is derived from `firstTokenBalance`/`secondTokenBalance` at execution time with no lower bound the caller can enforce: [3](#0-2) 
The same pattern exists for inject: [4](#0-3) 

Because `ExchangeTransactionContract` trades can be included in the same block (or even the same block window) as a pending `ExchangeInjectContract`/`ExchangeWithdrawContract`, an intervening trade can shift `firstTokenBalance`/`secondTokenBalance` before the inject/withdraw executes — exactly the "any deposits/orders that might get executed... before" scenario described in the GMX report. The pool creator who signed a withdraw/inject transaction has no way to bound the resulting counter-token amount, unlike the equivalent trade path which already has this protection via `tokenExpected`.

### Impact Explanation
An exchange creator submitting `ExchangeWithdrawContract`/`ExchangeInjectContract` can receive materially less of the counter-token than the pool ratio implied when they signed the transaction, if the ratio is moved by an intervening `ExchangeTransactionContract` (sandwich-style manipulation) before their transaction executes. This is a direct, unbacked-value/loss-of-funds condition for the affected account, structurally identical to the reported GMX issue, just missing the protective field that the sibling `ExchangeTransactionActuator` already implements.

### Likelihood Explanation
Only the pool creator can call `ExchangeInjectContract`/`ExchangeWithdrawContract` (enforced by `accountCapsule.getAddress().equals(exchangeCapsule.getCreatorAddress())`), so this cannot be triggered against arbitrary traders — but it is fully reachable by any account that created an exchange (an "asset issuer"/pool owner role) submitting an ordinary signed transaction, and requires only a same-block/adjacent trade to move the ratio, making it readily triggerable by anyone who front-runs the pending withdraw/inject.

### Recommendation
Add an `expected`/minimum-output field to `ExchangeInjectContract` and `ExchangeWithdrawContract` (mirroring `ExchangeTransactionContract.expected`), and validate the computed `anotherTokenQuant` against it in `ExchangeInjectActuator.doValidate()` and `ExchangeWithdrawActuator.doValidate()`, rejecting the transaction if the pool has moved unfavorably.

### Proof of Concept
1. Creator A creates an exchange pool and later signs `ExchangeWithdrawContract` to withdraw `X` of token1, expecting `Y` of token2 based on the current ratio.
2. Before A's transaction is packed into a block, attacker B submits `ExchangeTransactionContract` trades that shift the pool ratio in a way that reduces token2 payout for a given token1 withdrawal.
3. A's withdrawal executes using the manipulated ratio in `ExchangeWithdrawActuator.execute()` (`actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java:74-89`), and A receives less token2 than expected, with no validation check able to prevent it since no minimum bound exists in the contract or `doValidate()`.
