Based on what I was able to confirm, the strongest local analog to the "no way to cancel a signed message" bug is the `pallet-scarcity` NFT-purse transaction extension, `AsScarcity`, in `substrate/frame/scarcity/src/extension.rs`.

### Title
Purse authorization for a scarcity (NFT) transaction can only be cancelled by spending the purse, leaving a signed-but-unwanted transaction replayable for its entire mortal era - (File: `substrate/frame/scarcity/src/extension.rs`)

### Summary
The `AsScarcity` transaction extension authorizes an NFT-backed "purse" to execute a call by binding the purse's current state nonce into the signed payload, similarly to how `SessionOrderModule.sol` binds a session order's nonce into a signed message. [1](#0-0)  As documented in the module itself, purse authorization is **not** account-nonce-based, and the only stated mechanism to invalidate an outstanding signed authorization is for the holder to move the NFT (which bumps the state nonce). [1](#0-0) 

### Finding Description
The doc comments explicitly acknowledge: "a signed NFT transaction stays valid for as long as its purse still holds the named instance at the named state nonce" and "an unexecuted transaction is otherwise replayable by anyone who has seen it until its era expires," with the only cancellation path being to move the NFT, which "increments its state nonce." [2](#0-1)  This mirrors the external report's bug class exactly: a signed authorization (order/purse operation) has no dedicated, explicit cancellation primitive — the only remediation is an indirect side-effect (spending funds / moving the NFT) rather than a purpose-built "cancel my signature" call. Unlike `pallet_meta_tx`/`pallet_verify_signature`, which piggy-back on `frame_system::CheckNonce` and thus benefit from the account's monotonic nonce and standard `frame_system` nonce-bump mechanics for revocation, `pallet-scarcity`'s purse-state nonce has no standalone "invalidate/cancel" entrypoint independent of performing an actual NFT move.

### Impact Explanation
If a purse holder wants to revoke a previously signed but not-yet-submitted `AsScarcity` authorization (e.g., they mis-signed it, or their signing device is compromised), their only recourse is to execute an unrelated NFT move to bump the nonce — this requires them to have another valid destination/operation ready and to pay for a real state transition, rather than a lightweight, purpose-specific cancellation. During the window between "wants to cancel" and "successfully executes a cancelling move," any relayer holding the originally signed payload can still submit it and consume the purse under the stale intent, since validity is purely nonce+era based and not intent-based.

### Likelihood Explanation
This requires no privileged actor, malicious peer, or governance action — an unprivileged holder of a signed-but-regretted `AsScarcity` payload combined with any third-party relayer replaying that payload before the holder manages to bump the nonce via an unrelated move is sufficient to trigger it, matching the report's "signer wants to cancel, only indirect revocation available" bug class.

### Recommendation
Add an explicit, low-cost "cancel/invalidate" extrinsic to `pallet-scarcity` that lets the purse/NFT owner bump the state nonce directly (without requiring an actual NFT move), analogous to recommendation in the source report of "mark the nonce as used"; restrict this call so only the current NFT holder can invalidate outstanding authorizations for their purse.

### Proof of Concept
Conceptual sequence based on the documented behavior in `substrate/frame/scarcity/src/extension.rs` lines 41-56:
1. Holder signs an `AsScarcity`-wrapped mortal transaction to move NFT `X` from purse state nonce `N`.
2. Holder has a change of mind (e.g., wrong destination, or suspects payload leaked) and wants to cancel.
3. Holder has no dedicated cancel call; the only nonce-bump path is performing another real NFT move, which they may not have a valid destination/purpose for immediately.
4. Before the holder manages to bump the nonce, any relayer who saw the original signed payload submits it within its era — it validates successfully and executes.

I was not able to fully read `substrate/frame/scarcity/src/lib.rs` and the rest of `extension.rs` (calls after line 87, dispatchable functions, and `AUDIT_STATUS.md`) due to tool errors on the final iteration, so I cannot confirm with certainty whether a cancel-only extrinsic already exists elsewhere in the pallet that I missed. This should be verified by reading the full pallet before treating this as conclusively unpatched.

```rust
//! # Replay and mortality
//!
//! Purse authorization is not account-nonce-based: a signed NFT transaction stays valid for as
//! long as its purse still holds the named instance at the named state nonce. Two rules bound
//! stale intent, exactly as in Coinage:
//!
//! * Callers must sign **mortal** transactions with an era shorter than [`Config::LockPeriod`]. A
//!   successful move invalidates every outstanding authorization by incrementing the state nonce,
//!   but an unexecuted transaction is otherwise replayable by anyone who has seen it until its era
//!   expires.
//! * Because the era ends before the shortest failure lock does, a failed transaction can never
//!   re-enter a block: every retry after a failure is a fresh signing decision rather than a
//!   third-party replay of the old transaction.
//!
//! A holder can also cancel an outstanding authorization at any time by moving the NFT, which
//! increments its state nonce.
```
