I have enough evidence to confirm this analog: `AccountPermissionUpdateContract` performs a single-step, atomic overwrite of an account's `Owner`, `Witness`, and `Active` permissions, with no staged/pending state and no requirement that the new keys prove control before the change takes effect.

### Title
Single-step account permission (owner key) replacement can permanently brick a TRON account - (File: actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java)

### Summary
`AccountPermissionUpdateActuator.execute()` immediately overwrites an account's `Owner` permission (and optionally `Witness`/`Active` permissions) in a single atomic step based on values supplied by the caller, with no two-step "propose then claim" pattern and no proof that the new key(s) are controlled by anyone able to sign.

### Finding Description
When a transaction of type `AccountPermissionUpdateContract` is validated and executed, `execute()` directly calls `AccountCapsule.updatePermissions(owner, witness, actives)` and persists the new permission set to the `AccountStore` in one step: [1](#0-0) . The underlying capsule method simply replaces the stored `OwnerPermission`, `WitnessPermission`, and `ActivePermission` list with whatever was supplied: [2](#0-1) .

`validate()` only checks structural correctness of the new permission — key count, weight sum vs. threshold, address format, distinctness, operations bitmap for `Active` permissions — but never verifies that the new `Owner`/`Active` keys correspond to any reachable/controllable private key, nor does it require any acknowledgement/claim step from the new key holder: [3](#0-2) .

Any subsequent transaction from that account — including any future `AccountPermissionUpdateContract` to fix a mistake — must be signed under the `Owner` permission (`Permission_id = 0`), since permission id 0 is enforced by `TransactionCapsule.validateSignature`/`checkPermission` for owner-level operations: [4](#0-3)  and [5](#0-4) . If the owner permission's keys are set to an address (or set of addresses reaching the threshold) that nobody controls — e.g., a typo'd address, a non-existent key, or an address whose private key is lost — there is no recovery path: the account can never again satisfy the `Owner` permission threshold, permanently disabling owner-only ability to reconfigure permissions.

This directly mirrors the reported bug class: a single-step, irreversible "ownership transfer" (here, the account's `Owner`/`Active` signer set) with no pending/claim mechanism, so any mistaken value bricks the account's governance capability.

### Impact Explanation
If the `Owner` permission's key set is misconfigured (wrong address, insufficient combined weight, or an uncontrolled key), the account permanently loses the ability to execute any further `AccountPermissionUpdateContract` to correct itself, since that operation always requires the `Owner` permission. Any account whose critical operations rely on `Owner`-gated actions (e.g., proposal approvals, resource/asset management flows gated to owner, or future permission changes) becomes irrecoverably locked out — a permanent freezing of the account's administrative capability, matching the "protocol/account bricking" impact described in the source report.

### Likelihood Explanation
Low: it requires a signer to submit an `AccountPermissionUpdateContract` with an incorrect `Owner`/`Active` key set (e.g., a copy-paste/typo error, or reusing an address whose key was never generated/retained). This is a genuine user/API-client error path reachable by any account holder broadcasting a signed `AccountPermissionUpdateContract` transaction through the normal transaction/HTTP API (`AccountPermissionUpdateServlet` → `Wallet.createTransactionCapsule` → broadcast) with no confirmation or two-step claim safeguard: [6](#0-5) .

### Recommendation
Introduce a two-step permission-update flow for `Owner` (and ideally `Active`) permission changes: stage the proposed permission set, and require a transaction signed under the *new* permission's keys to "claim"/confirm before it becomes active, falling back to the current owner's control if never confirmed. At minimum, add validation that rejects owner-permission updates where none of the newly specified keys can be shown to be distinct from a burn/zero address, and consider requiring a companion signature from at least one new key as proof of possession before committing the change in `AccountPermissionUpdateActuator.execute()`.

### Proof of Concept
1. Attacker/user account `A` (with valid owner key `K0`) broadcasts a signed `AccountPermissionUpdateContract` transaction with `owner_address = A`, setting the `owner` `Permission` to a `Key` list containing only address `X` (a typo'd or otherwise uncontrolled address) with `threshold = 1`.
2. `AccountPermissionUpdateActuator.validate()` passes since `X` is a syntactically valid address, has non-zero weight, and threshold checks succeed: [7](#0-6) .
3. `execute()` commits the change via `account.updatePermissions(...)`, overwriting `OwnerPermission` in the `AccountStore`: [8](#0-7) .
4. Account `A` can no longer produce a transaction that satisfies the `Owner` permission (`Permission_id = 0`) since nobody controls `X`'s private key, so `TransactionCapsule.validateSignature` will always fail for any further owner-gated action, including any attempt to fix the permission via a new `AccountPermissionUpdateContract`: [4](#0-3) .

  public void updatePermissions(Permission owner, Permission witness, List<Permission> actives) {
    Builder builder = this.account.toBuilder();

    owner = owner.toBuilder().setId(0).build();
    builder.setOwnerPermission(owner);
    if (witness != null && builder.getIsWitness()) {
      witness = witness.toBuilder().setId(1).build();
      builder.setWitnessPermission(witness);
    }

    builder.clearActivePermission();
    if (actives != null) {
      for (int i = 0; i < actives.size(); i++) {
        Permission permission = actives.get(i).toBuilder().setId(i + 2).build();
        builder.addActivePermission(permission);
      }
    }

    this.account = builder.build();
  }
