## Title
Stale postponed receipt survives `DeleteAccount` and can execute privileged actions against a recreated account - (File: core/store/src/utils/mod.rs)

## Summary
`remove_account` cleans up `Account`, `ContractCode`, `AccessKey`/`GasKeyNonce`, and `ContractData` entries, but never removes `TrieKey::PostponedReceiptId`, `TrieKey::PendingDataCount`, or `TrieKey::PostponedReceipt` entries keyed by `receiver_id` for the deleted account. [1](#0-0)  The docstring even states the function only removes "account, code and all access keys and gas keys" — postponed-receipt bookkeeping is explicitly out of scope. [2](#0-1) 

## Finding Description
When an `ActionReceipt` with multiple `input_data_ids` arrives at `receiver_id = X` and not all data has arrived, `process_action_receipt` stores `TrieKey::PostponedReceiptId{receiver_id: X, data_id}`, `TrieKey::PendingDataCount{receiver_id: X, receipt_id}`, and `TrieKey::PostponedReceipt{receiver_id: X, receipt_id}` in the trie under `X`'s key-space. [3](#0-2)  If `X` is deleted via `DeleteAccountAction` before the missing `DataReceipt` arrives, `action_delete_account` calls `remove_account(state_update, account_id)`, which does not touch any `PostponedReceipt*` keys. [4](#0-3)  When the missing `DataReceipt` for `X` eventually arrives, `process_receipt`'s `Data` branch looks up `PostponedReceiptId`/`PendingDataCount`/`PostponedReceipt` purely by `receiver_id`+`data_id`/`receipt_id` with no check that `X` currently exists or that the account state matches what it was when the receipt was postponed, and executes the postponed `ActionReceipt` via `apply_action_receipt`. [5](#0-4) 

However, exploiting this to achieve **authorization escalation across accounts** additionally requires that account `X` can be re-created by someone other than the original creator/owner. Under NEAR's account model, `CreateAccountAction` only succeeds when the predecessor is either the registrar (for short top-level names) or the account is a subaccount of the predecessor (`sub.parent` requires predecessor `== parent`). This means for the "any third party recreates X" step to work, the attacker would either need to control a top-level name that a stranger can register (uncommon and requires very long/implicit names not subject to real "arbitrary third party" reuse), or X must be a subaccount of some parent that a third party independently controls — meaning the scenario requires the attacker to give up a namespace they controlled to a third party, or coordinate account naming collision with a genuinely independent actor, which is not a realistic reachable path for an "ordinary unprivileged attacker acting alone against an arbitrary victim." The postponed-receipt-survives-deletion bug is real and reproducible, but the "third party recreates the exact same account name and inherits attacker-controlled privileged actions" step is not generically reachable without additional cooperation or a naming collision that the rules of this scenario (unprivileged attacker only, no social engineering) do not establish as feasible against an arbitrary victim.

That said, the underlying storage-cleanup defect is real regardless of the second-order exploit chain: a stale `PostponedReceipt`/`PostponedReceiptId`/`PendingDataCount` for `X` remains in the trie permanently if `X` is never re-created, and if `X` *is* re-created (e.g., by its own original owner reusing the account, or a subaccount recreated by the same parent who deleted it), the surviving postponed receipt — with `predecessor_id == receiver_id == X` — will pass `check_actor_permissions` in `runtime/runtime/src/actions.rs` against the new account state and perform actions (e.g. `AddKey`) the new account holder never authorized in the context of that specific account generation.

## Impact Explanation
Where reachable — i.e., when the same entity (or the entity that legitimately controls the parent namespace) recreates the deleted account — this causes execution of privileged actions (`AddKey`/`DeleteKey`/`FunctionCall`) against the "new" account epoch without any fresh authorization, matching the "authorization escalation across accounts/promises" category. It does not directly cause fund theft by itself but bypasses the intended invariant that a promise's privileges are scoped to the account holder at delivery time.

## Likelihood Explanation
The precondition (delete an account with an outstanding multi-input-data postponed receipt, then recreate the identical account_id) is straightforward to construct for accounts the attacker controls or for subaccounts under a namespace the attacker still controls after deletion (parent account is unaffected by deleting a child). It is less clear that an *independent, unprivileged third party* can be made to recreate an arbitrary top-level account id on demand, which is required for the "victim inherits attacker's stale receipt" framing in the question. This weakens the cross-account-authorization-escalation framing to primarily a same-namespace / same-owner replay issue rather than a generalizable attack on arbitrary third parties.

## Recommendation
`remove_account` should also enumerate and remove `TrieKey::PostponedReceiptId`, `TrieKey::PendingDataCount`, and `TrieKey::PostponedReceipt` entries keyed by the deleted `account_id` as `receiver_id` (there are trie-key prefix helpers analogous to `get_raw_prefix_for_access_keys`/`get_raw_prefix_for_contract_data` that should be added for these columns), refunding any deposits/gas associated with those pending receipts as appropriate, consistent with how `ReceivedData` and other receiver-scoped state should be purged on account deletion.

## Proof of Concept
Runtime/test-loop integration test:
1. Create account `X`.
2. Submit an `ActionReceipt` targeting `X` with two `input_data_ids` and actions `[FunctionCall, AddKey]`; deliver one `DataReceipt` so the receipt is postponed (`PostponedReceipt`, `PendingDataCount==1` remain in state).
3. Submit `DeleteAccountAction` for `X` (from a key/actor authorized on `X`) and confirm `X`'s `Account` record is gone via `get_account`, while `TrieKey::PostponedReceipt{receiver_id: X, ..}` still exists via direct trie inspection.
4. Recreate `X` (e.g., re-issue `CreateAccountAction` from the same parent/owner) and add a fresh key that the new owner controls.
5. Deliver the second missing `DataReceipt` for the old `receipt_id`.
6. Assert that the postponed receipt executes and the `AddKey` action is applied to the recreated `X`, mutating its access-key set even though the new account instance never authorized that specific receipt — confirming the state leak/authorization bypass.

/// Removes account, code and all access keys and gas keys associated to it.
pub fn remove_account(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
) -> Result<RemoveAccountResult, StorageError> {
    state_update.remove(TrieKey::Account { account_id: account_id.clone() });
    state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });

    let mut gas_key_nonce_count: usize = 0;
    let mut gas_key_nonce_total_key_bytes: usize = 0;

    // Removing access keys and gas key nonces
    let lock = state_update.trie().lock_for_iter();
    let mut keys_to_remove: Vec<TrieKey> = Vec::new();
    for raw_key in state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_access_keys(account_id), &lock)?
    {
        let raw_key = raw_key?;
        let key_handle = trie_key_parsers::parse_key_handle_from_access_key_key(
            &raw_key, account_id,
        )
        .map_err(|_e| {
            StorageError::StorageInconsistentState(
                "Can't parse key handle from raw key for AccessKey".to_string(),
            )
        })?;
        let nonce_index =
            trie_key_parsers::parse_nonce_index_from_gas_key_key(&raw_key, account_id, &key_handle)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse nonce index from raw key for AccessKey".to_string(),
                    )
                })?;
        if let Some(index) = nonce_index {
            gas_key_nonce_count += 1;
            gas_key_nonce_total_key_bytes += raw_key.len();
            keys_to_remove.push(TrieKey::gas_key_nonce(
                account_id.clone(),
                key_handle.clone(),
                index,
            ));
        } else {
            keys_to_remove.push(TrieKey::access_key(account_id.clone(), key_handle.clone()));
        }
    }
    drop(lock);

    for trie_key in keys_to_remove {
        state_update.remove(trie_key);
    }

    // Removing contract data
    let lock = state_update.trie().lock_for_iter();
    let data_keys = state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_contract_data(account_id, &[]), &lock)?
        .map(|raw_key| {
            trie_key_parsers::parse_data_key_from_contract_data_key(&raw_key?, account_id)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse data key from raw key for ContractData".to_string(),
                    )
                })
                .map(Vec::from)
        })
        .collect::<Result<Vec<_>, _>>()?;
    drop(lock);

    for key in data_keys {
        state_update.remove(TrieKey::ContractData { account_id: account_id.clone(), key });
    }
    Ok(RemoveAccountResult { gas_key_nonce_count, gas_key_nonce_total_key_bytes })
}
