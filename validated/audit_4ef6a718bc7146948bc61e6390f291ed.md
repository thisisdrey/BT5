### Title
Emissions permanently lost when `RewardsDistributor` accrues rewards while a rewarded token has zero total supply — ([File: contracts/RewardsDistributor.sol](contracts/RewardsDistributor.sol))

### Summary
`RewardsDistributor` distributes `rewardToken` emissions to holders of `DepositToken`/`DebtToken` via a supply index that grows by `speed * elapsed / totalSupply`. When a rewarded token's `totalSupply()` is `0`, `_calculateTokenIndex` still advances `timestamp` but adds `0` to the index (the `_totalSupply > 0 ? ... : 0` branch). The emissions covering that interval are therefore never captured by any index and the corresponding `rewardToken` balance becomes permanently unclaimable — the exact analog of `Voter.notifyRewardAmount()` crediting emissions to a period with zero votes.

### Finding Description
The index update path is:

- `_calculateTokenIndex` at `contracts/RewardsDistributor.sol:197-212`: when `_deltaTimestamps > 0 && _speed > 0` it computes `_tokensAccrued = _deltaTimestamps * _speed`, but sets `_ratio = 0` if `token_.totalSupply() == 0`, while still returning `_newTimestamp = block.timestamp`.
- `_updateTokenIndex` at `contracts/RewardsDistributor.sol:271-282` persists the timestamp, so the zero-supply interval is permanently skipped and never re-accrued.
- Tokens only become claimable through index deltas in `_calculateTokenDelta` (`contracts/RewardsDistributor.sol:217-231`) and are paid out in `_transferRewardIfEnoughTokens` (`contracts/RewardsDistributor.sol:248-256`). Since skipped emissions never enter any index, the backing `rewardToken` stays in the contract forever.

Reachability: `updateBeforeMintOrBurn`/`updateBeforeTransfer` (`contracts/RewardsDistributor.sol:175-192`) are called on every `DepositToken`/`DebtToken` mint, burn, and transfer, so the timestamp advance is triggered by ordinary protocol use. A rewarded token reaching `totalSupply() == 0` is reachable by any unprivileged user: withdrawing the last deposit via `Pool`/`NativeTokenGateway`/`VesperGateway`, or repaying and burning the last `DebtToken` balance, while `tokenSpeeds[token_] > 0` (set by governor for listed tokens — normal deployed configuration, e.g. Vesper `rewardRates` syncing via `syncTokenSpeed`). No access control, pause flag, or supply floor prevents a token's supply hitting zero while its speed remains nonzero.

### Impact Explanation
Every reward token emitted during a zero-supply interval is locked in the `RewardsDistributor` permanently — no account index can ever claim it, and there is no sweep/recover function for `rewardToken`. This is permanent freezing of unclaimed yield belonging to the reward pool: emissions that should have accrued to suppliers/borrowers (or carried over) are lost. With speed streams running continuously, a pool that empties out (e.g. during a market wind-down or migration) burns the entire emission budget for that interval.

### Likelihood Explanation
Requires a rewarded `DepositToken`/`DebtToken` to have `totalSupply == 0` while `tokenSpeeds[token_] > 0`. This occurs whenever the last holder exits, at market launch before first deposit if speed is already set, or via an attacker who controls the entire supply withdrawing/repaying for a window. Any one of these is plausible but not attacker-guaranteed on a healthy pool — medium likelihood.

### Recommendation
Do not advance the token state's accounting when `totalSupply == 0`: either skip the timestamp update so the unaccrued interval is picked up once supply returns, or accumulate `_tokensAccrued` into a pending/undistributed bucket that is distributed (or carried into the next nonzero-supply index update) later — equivalent to carrying undistributed rewards to the next period.

### Proof of Concept
Hardhat sketch (mirroring `test/RewardDistributor.test.ts` setup with `speed = parseEther('1')`):

```ts
// governor sets speed on msMET DepositToken while totalSupply == 0
await rewardsDistributor.updateTokenSpeed(msdMET.address, parseEther('1'))
msdMET.totalSupply.returns(0) // or real: last depositor calls pool.withdraw()

// anyone touches the index via updateBeforeMintOrBurn / claimRewards
await rewardsDistributor.updateBeforeMintOrBurn(msdMET.address, alice.address)

// 10 seconds of emissions elapse with zero supply
await increaseTimeOfNextBlock(10)
await mine()

// alice deposits; index update triggered -> timestamp advances, index stays INITIAL_INDEX
await rewardsDistributor.updateBeforeMintOrBurn(msdMET.address, alice.address)
msdMET.totalSupply.returns(parseEther('100'))
msdMET.balanceOf.whenCalledWith(alice.address).returns(parseEther('100'))

const { index } = await rewardsDistributor.tokenStates(msdMET.address)
expect(index).to.eq(parseEther('1')) // INITIAL_INDEX: 10 reward tokens never accrued

// the 10 rewardToken skipped remain in the distributor forever, claimable by no one
expect(await rewardsDistributor.claimable(alice.address)).to.eq(0)
```

The gap between `rewardToken.balanceOf(rewardsDistributor)` and the sum of index-implied accruals grows by `speed * zeroSupplyDuration`, permanently.
