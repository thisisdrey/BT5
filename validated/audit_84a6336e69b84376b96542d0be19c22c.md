### Title
Vault `lindex` Permanently Zeroed by `socialize-debt` Bricks Oracle Price Resolution and Freezes All ztoken Positions - (File: mainnet/contracts/vault/v0-vault-stx.clar)

### Summary
The reported Zebra/Orchard bug is a class of "legal edge-case value not handled downstream" — the protocol spec allows an identity point for `rk`, but the verification code never expected it and blows up. The Zest analog is the vault `lindex` (liquidity index) state variable: `socialize-debt` explicitly permits `lindex` to become `u0` as a "legal" outcome of writing off bad debt, but every downstream consumer (`market.clar`'s ztoken price-resolution path) treats `lindex == 0` as an unrecoverable, permanently-illegal state, causing `price-resolve` to revert forever for that asset once it happens.

### Finding Description
In each vault contract's `socialize-debt`, `new-lindex` is computed as: [1](#0-0) 

```
(new-lindex (if (and (> old-total-assets u0) (> old-total-assets debt-reduction))
               (mul-div-down current-lindex (- old-total-assets debt-reduction) old-total-assets)
               u0))
...
(var-set lindex new-lindex)
```

When the bad debt being socialized consumes all (or more than) the vault's `total-assets` (a realistic outcome of an extreme under-collateralized liquidation event that fully exhausts a vault, reachable via the ordinary, in-scope `liquidate` → bad-debt-socialization path in `market.clar`), `lindex` is explicitly set to `u0`. This is treated as a legal, "identity"-like value by the vault code — same pattern as `rk` being a legal identity point in the Orchard spec.

This `lindex` value is cached and consumed by the market's ztoken price resolver: [2](#0-1) 

```
(define-private (resolve-ztoken (p uint) (aid uint))
  (let ((cached (unwrap! (get-cached-indexes aid) ERR-ORACLE-CALLCODE))
        (cached-lindex (get lindex cached))
        (scaled (* p cached-lindex)))
    (ok (div-down scaled INDEX-PRECISION))))
```

With `cached-lindex = 0`, `scaled` is always `0`, so the resolved ztoken price is permanently `0`. This zero price is then rejected by the freshness/legality assertion in `price-resolve`: [3](#0-2) 

```
(define-private (oracle-price-legal (p uint))
  (> p u0))
...
(asserts! (and (oracle-price-legal final-price) (oracle-timestamp-fresh timestamp last-update-time max-staleness))
          ERR-ORACLE-INVARIANT)
```

Because `lindex` is only ever scaled multiplicatively by subsequent accrual (`mul-div-down current-lindex ...`, i.e. `0 * anything / anything = 0`), there is no code path that can restore `lindex` above `0` once it hits zero. Every subsequent call to `price-resolve` for that asset's ztoken callcode (`CALLCODE-ZSTX`/`ZSBTC`/`ZSTSTX`/`ZUSDC`/`ZUSDH`/`ZSTSTXBTC`) will permanently revert with `ERR-ORACLE-INVARIANT`.

### Impact Explanation
Any function that needs to price that ztoken — health checks (`is-healthy`/`is-healthy-with-mask`), `get-asset-value`, `process-collateral-asset`/`process-debt-asset` in liquidation, and multi-asset price resolution used across `borrow`, `repay`, `collateral-remove`, and `liquidate` — will permanently fail for any position holding that ztoken as collateral or debt. This is a permanent, protocol-wide freeze of funds for all users positioned in that ztoken (they can no longer be liquidated, can no longer withdraw/borrow against it, and its collateral value can never again be assessed), which matches the in-scope "permanent freezing of funds" impact class. In the worst case it also blocks liquidation/health-check machinery for other positions that share the same asset, contributing to protocol insolvency risk.

### Likelihood Explanation
Triggering requires a genuine, extreme insolvency event in a single-asset vault (total socialized debt ≥ vault's `total-assets`), which is a tail-risk scenario but is reachable purely through the normal, unprivileged `liquidate`/bad-debt-socialization flow already exercised in the codebase's own tests (e.g. `ATK-LG-05` bad-debt socialization tests) — no DAO action or admin misconfiguration is required. A well-capitalized attacker could deliberately engineer this (e.g., via price manipulation of a debt asset combined with rapid borrowing to leave a vault's `total-borrowed` greater than its remaining `assets` right before triggering socialization), making the zero-lindex state achievable, not purely accidental.

### Recommendation
Guard `lindex == 0` (and equivalently the underlying `index`) explicitly wherever it's consumed downstream:
- In `resolve-ztoken`/`price-resolve`, detect `cached-lindex == u0` and either treat it as an explicit "asset insolvent" error distinct from `ERR-ORACLE-INVARIANT`, or provide a recovery/re-seeding mechanism (e.g., DAO-gated re-initialization of `lindex` after a socialized-debt event, or track insolvency explicitly instead of collapsing state into `0`).
- Alternatively, prevent `lindex` from ever reaching exactly `0` in `socialize-debt` (e.g., floor at some minimal positive value) so that price resolution degrades gracefully instead of becoming permanently unresolvable.

### Proof of Concept
1. Attacker/borrower opens a large debt position denominated in an asset routed through a single-asset vault (e.g., `v0-vault-usdc`), and/or manipulates conditions so that `total-borrowed` for that vault approaches or exceeds `total-assets`.
2. Attacker (as liquidator, or via price crash as in the existing `ATK-LG-05` test) triggers `liquidate`/`liquidate-multi` on a severely underwater position where collateral is fully exhausted, causing `no-collateral-left` and invoking `socialize-debt-asset` → `vault-socialize-debt` → the target vault's `socialize-debt`. [4](#0-3) 
3. If `debt-reduction >= old-total-assets` for that vault, `socialize-debt` sets `(var-set lindex u0)`. [5](#0-4) 
4. Any subsequent call requiring a price for the corresponding ztoken (e.g. another user's `borrow`, `repay`, `collateral-remove`, or `liquidate` involving that ztoken) calls `price-resolve` → `resolve-ztoken`, which computes price `0`, then fails `oracle-price-legal`, reverting with `ERR-ORACLE-INVARIANT` for every future transaction touching that ztoken's price — permanently freezing all positions using it.
