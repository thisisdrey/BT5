### Title
Unbounded attacker-controlled `bytes[]` array length causes OutOfMemoryError DoS in `ValidateMultiSign`/`BatchValidateSign` precompiles - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The FFmpeg report describes an integer overflow where an attacker-controlled length field from a crafted file is used without validation, leading to a crash. The analogous pattern in java-tron is `extractBytesArray`, which reads an attacker-controlled ABI array-length word directly from TVM call data and immediately allocates a Java array of that size, with no upper bound enforced on the legacy code path.

### Finding Description
`extractBytesArray` reads the declared array length straight out of caller-supplied `data`/`words` and uses it to allocate a reference array before any bounds/sanity check is applied: [1](#0-0) 

This helper is invoked from `ValidateMultiSign.execute()` and `BatchValidateSign.doExecute()`. Both precompiles only enforce a `MAX_SIZE` cap on the declared array length **when `VMConfig.allowTvmSelfdestructRestriction()` is enabled**, using the safer `extractSigArray`/pre-check path; when that feature flag is not active, `extractBytesArray` is called with the raw, attacker-controlled length with no cap: [2](#0-1) [3](#0-2) 

Because `DataWord.intValueSafe()` can return values up to `Integer.MAX_VALUE`, an attacker can craft the `bytes[]` length word (`words[offset].intValueSafe()`) in the ABI-encoded call data to a large value (e.g. close to `Integer.MAX_VALUE`). The subsequent `new byte[len][]` in `extractBytesArray` attempts to allocate hundreds of millions to billions of array-reference slots, which throws an uncontrolled `OutOfMemoryError` (or causes severe GC pressure) before any length-vs-payload-size validation occurs.

`ValidateMultiSign.execute()` has no surrounding try/catch for this failure mode, unlike `BatchValidateSign.execute()` which wraps `doExecute` in a `try { } catch (Throwable t)`; even that catch only prevents propagation but does not prevent the transient OOM condition/GC pause affecting the node process, since `OutOfMemoryError` can corrupt or destabilize the JVM heap state for other concurrently executing threads.

### Impact Explanation
This precompile is reachable by any address via a plain CALL from a smart contract to precompile address `0x9` (`batchValidateSign`) or `0xa` (`validateMultiSign`), both gated only behind `VMConfig.allowTvmSolidity059()`: [4](#0-3) 

An unprivileged transaction broadcaster who deploys or calls a contract invoking this precompile with crafted `bytes[]`/`address[]` length fields can trigger a large, uncontrolled memory allocation attempt on every full node/SR that executes the transaction, resulting in a node crash or severe denial-of-service via OutOfMemoryError, matching the report's "denial of service via crafted file/input with unchecked length field" bug class.

### Likelihood Explanation
Reachability requires only calling a deployed contract that performs a low-level `CALL` to precompile `0x9`/`0xa` with hand-crafted call data (this can be done directly from an EOA-invoked contract, no special privilege needed). The vulnerable path (`extractBytesArray`, non-`allowTvmSelfdestructRestriction` branch) is only live while that specific chain-parameter/feature switch is disabled on the network. I could not fully confirm the current default/activation status of `allowTvmSelfdestructRestriction` on mainnet within the available tool budget, so likelihood is somewhat uncertain and should be validated against current chain parameters before treating this as immediately exploitable in production.

### Recommendation
Validate the declared `bytes[]`/`address[]` length against a small fixed upper bound (matching each contract's existing `MAX_SIZE`) and against the remaining call-data size *before* calling `extractBytesArray`/`extractBytes32Array`, regardless of the `allowTvmSelfdestructRestriction` flag state, so the unguarded code path cannot be reached even on networks where that feature is not yet activated. Additionally, wrap `ValidateMultiSign.execute()` in the same defensive `try/catch` pattern used by `BatchValidateSign.execute()`.

### Proof of Concept
1. Deploy a contract that performs a raw `staticcall`/`call` to precompile address `0x000...00a` (`validateMultiSign`) or `0x000...009` (`batchValidateSign`).
2. Hand-craft the ABI call data so that the length word for the `bytes[]` parameter (at the offset pointed to by `words[3]` for `validateMultiSign`, or `words[1]` for `batchValidateSign`) is set to a very large value (e.g. `0x7FFFFFFF`), while running on a network configuration where `allowTvmSelfdestructRestriction` is disabled.
3. Send the transaction; `extractBytesArray` executes `new byte[len][]` with the attacker-supplied `len`, causing the executing node to throw `OutOfMemoryError` / experience severe GC stalls while processing the transaction, degrading or crashing node availability.

*Note: I was unable to verify within the available tool budget (a) the exact runtime value/default of `allowTvmSelfdestructRestriction` on current java-tron networks, and (b) whether `DataWord.intValueSafe()` applies any additional clamping beyond `Integer.MAX_VALUE`. These should be confirmed via a full read of `common/src/main/java/org/tron/common/runtime/vm/DataWord.java` and `core/vm/config/VMConfig.java` before treating this finding as fully confirmed.*

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
