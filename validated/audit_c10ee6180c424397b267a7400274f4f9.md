### Title
Permanent Denial-of-Service of the Eth-Implicit Wallet Contract via Callback Gas Griefing on the `has_in_flight_tx` Lock - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The `WalletContract` (the eth-implicit account's Near-native wrapper) uses a single boolean flag, `has_in_flight_tx`, to serialize execution of RLP-encoded Ethereum-style transactions. The flag is set to `true` when a promise chain is dispatched and is only reset to `false` inside the follow-up callback (`rlp_execute_callback`, `address_check_callback`, `nep_141_storage_balance_callback`, or `ban_relayer`). Because these callbacks are budgeted a small, fixed amount of static gas, an attacker who controls the destination contract of the emulated transaction can force the callback receipt itself to run out of gas. Per Near runtime semantics, a failed receipt rolls back *all* of its state writes, including the `has_in_flight_tx = false` reset, leaving the flag permanently stuck at `true`. From that point on, the guard at the top of `rlp_execute` unconditionally rejects every future call, permanently locking the wallet and freezing the owner out of ever sending another transaction (transfer, function call, key management, etc.) through this account.

### Finding Description
`rlp_execute` sets the lock before the async promise resolves and relies exclusively on the eventual callback to release it: [1](#0-0) 

The callback gas budgets are small fixed constants: [2](#0-1) 

The lock is only cleared as the first statement of the callbacks, e.g.: [3](#0-2) 

`rlp_execute_callback` reads the wrapped promise's result via `env::promise_result(0)` and, on success, embeds the returned bytes into `ExecuteResponse.success_value` before returning. The size of that value is controlled entirely by whatever contract the wallet owner's signed Ethereum-style transaction targets (an attacker-controlled or compromised destination contract). Gas is charged per-byte for reading promise result data and for serializing the return value; if that cost exceeds the fixed `RLP_EXECUTE_CALLBACK_GAS`/`ADDRESS_CHECK_CALLBACK_GAS`/`NEP_141_STORAGE_BALANCE_CALLBACK_GAS` budget, the callback function call itself aborts with `GasExceeded`.

The runtime's documented behavior confirms that a failed receipt discards all of its state changes: [4](#0-3) 

The project's own test explicitly demonstrates that when the *initial* `rlp_execute` call runs out of gas, no promise is dispatched and the contract remains usable ("the contract is still usable afterwards") — because the whole invocation, including the `has_in_flight_tx = true` write, is rolled back: [5](#0-4) 

However, this safety property only holds for the *initial* call. There is no analogous protection for the *callback* receipt: if the callback itself fails due to `GasExceeded` (rather than the promise it wraps merely returning `PromiseResult::Failed`), the earlier `self.has_in_flight_tx = true` commit (made when the promise was originally dispatched) is never undone, since the reset statement lives inside the very receipt that failed and was rolled back.

### Impact Explanation
Once `has_in_flight_tx` is stuck at `true`, every subsequent call to `rlp_execute` is rejected at the guard check with "transaction already in progress, please try again later," and there is no recovery path (`ban_relayer`/callbacks are the only writers of `false`, and none of them can run because the lock is only ever cleared from within a promise chain that was already exhausted). This permanently freezes the account: its owner can no longer move funds, call contracts, or manage keys through this Near-native representation of their Ethereum-style address, i.e., a permanent freezing of funds/control — the same impact class as the referenced report's "prevent deposits and withdrawals" DoS, since both stem from coupling a core user operation's completion to an unrelated payment/callback step that can be made to fail.

### Likelihood Explanation
Triggering this requires only that the account owner's signed RLP transaction targets a contract (for a `FunctionCall`, `ERC20Transfer`, or via the address-registrar lookup path) that returns an oversized successful payload — something entirely within the control of whichever contract is being called, which need not be the wallet owner nor require any privileged role. This is a normal, unprivileged cross-contract interaction pattern (a "gas-griefing" style attack via response size) reachable by any ordinary user/attacker operating a destination contract.

### Recommendation
Do not tie the reset of `has_in_flight_tx` to the success of the same gas-limited receipt that could itself run out of gas. Options include: reserving a much larger, size-independent gas budget for the callback's bookkeeping (clear the flag before processing/copying the promise result payload), splitting flag-clearing into its own minimal, guaranteed-to-succeed step, or bounding/rejecting oversized promise results before they are copied into `ExecuteResponse`.

### Proof of Concept
1. Deploy a malicious contract `evil.near` whose method (e.g. `some_method`) returns a very large byte blob (tens/hundreds of KB) as its successful return value.
2. Have the wallet owner sign (or be tricked into signing) an RLP transaction whose `target` invokes `evil.near::some_method`, dispatched via `rlp_execute` (see `inner_rlp_execute`, `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs:412-471`), which chains `.then(ext.rlp_execute_callback(...))` with only `RLP_EXECUTE_CALLBACK_GAS` (5 Tgas) reserved.
3. When `evil.near`'s call succeeds and returns the oversized value, `rlp_execute_callback` (lib.rs:276-317) attempts to read/serialize that value into `ExecuteResponse.success_value`; the per-byte gas cost exceeds the 5 Tgas reserved for the callback, causing the callback receipt to fail with `GasExceeded`.
4. Per the runtime's rollback semantics (`protocol-model/spec/runtime-execution.md:69-70`), the `self.has_in_flight_tx = false` write made at the top of the callback is discarded, leaving `has_in_flight_tx == true` in the persisted contract state.
5. Any subsequent call to `rlp_execute` (lib.rs:97-105) is now rejected forever with "transaction already in progress, please try again later," permanently freezing the wallet.

    pub fn rlp_execute_callback(
        &mut self,
        caller_deposit: Option<CallerDeposit>,
    ) -> ExecuteResponse {
        self.has_in_flight_tx = false;
        let n = env::promise_results_count();

        if n == 0 {
            // `rlp_execute_callback` is called directly in the case of an emulated self-transfer.
            return ExecuteResponse { success: true, success_value: None, error: None };
        } else if n > 1 {
            return ExecuteResponse {
                success: false,
                success_value: None,
                error: Some(format!(
                    "Invariant violation: this callback comes after a single promise. n={n}"
                )),
            };
        }

        match env::promise_result(0) {
            PromiseResult::Failed => {
                // The cross-contract call failed, refund the caller if needed
                if let Some(CallerDeposit { account_id, yocto_near }) = caller_deposit {
                    let refund_promise = env::promise_batch_create(&account_id);
                    env::promise_batch_action_transfer(
                        refund_promise,
                        NearToken::from_yoctonear(yocto_near.into()),
                    );
                }

                ExecuteResponse {
                    success: false,
                    success_value: None,
                    error: Some("Failed Near promise".into()),
                }
            }
            PromiseResult::Successful(value) => {
                ExecuteResponse { success: true, success_value: Some(value), error: None }
            }
        }
    }

#[tokio::test]
async fn test_insufficient_gas() -> anyhow::Result<()> {
    let TestContext { worker, wallet_contract, wallet_sk, .. } = TestContext::new().await?;

    // If not enough gas is attached to the `rlp_execute` call then the action fails.
    let target = "some.account.near".to_string();
    let action = Action::FunctionCall {
        receiver_id: target.clone(),
        method_name: "greet".into(),
        args: br#"{"name": "Aurora"}"#.to_vec(),
        gas: 5_000_000_000_000,
        yocto_near: 0,
    };
    let signed_transaction = utils::create_signed_transaction(
        0,
        &target.parse().unwrap(),
        Wei::zero(),
        action,
        &wallet_sk,
    );

    let error = wallet_contract
        .inner
        .call(crate::tests::RLP_EXECUTE)
        .args_json(serde_json::json!({
            "target": target,
            "tx_bytes_b64": codec::encode_b64(&codec::rlp_encode(&signed_transaction))
        }))
        .gas(near_gas::NearGas::from_tgas(7))
        .transact()
        .await
        .unwrap()
        .raw_bytes()
        .unwrap_err();

    assert!(
        error.to_string().contains("Exceeded the prepaid gas."),
        "Error should be that there was not enough gas"
    );

    // But the contract is still usable afterwards.
    utils::deploy_and_call_hello(&worker, &wallet_contract, &wallet_sk, 0).await?;

    Ok(())
}
