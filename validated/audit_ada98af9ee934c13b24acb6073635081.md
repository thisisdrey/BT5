Confirmed analog found. The signature-reuse bug class from the Gondi report — where the same signed struct can be authenticated under one context but stored/used under a different, unintended context — has a real analog in this repo's `SlotMetadata`/`StackerDBChunkData` signing scheme.

### Title
StackerDB chunk signatures do not bind to the target contract, enabling cross-contract signature/data replay - ([File: libstackerdb/src/libstackerdb.rs])

### Summary
`SlotMetadata::auth_digest()` computes the signed digest from only `(slot_id, slot_version, data_hash)`, never including the target `QualifiedContractIdentifier` (the specific StackerDB instance/contract). Because the same signer key/address frequently owns the identical `slot_id` across multiple distinct StackerDB contracts (e.g. different `.signers-<set>-<message_id>` lanes, or the `.miners` contract, or across reward cycles), a validly signed `StackerDBChunkData` produced for one contract can be replayed and accepted by `try_replace_chunk` in a *different* contract that the signer also owns the same slot in, as long as the version/size checks pass there too. [1](#0-0) 

### Finding Description
`SlotMetadata::sign`/`verify` operate over `auth_digest()`, which hashes only `slot_id`, `slot_version`, and `data_hash` — it never commits to *which* StackerDB contract the chunk belongs to: [2](#0-1) 

The chunk-write validation path, `StackerDBTx::try_replace_chunk`, is parameterized by `smart_contract` but the signature check delegates purely to `slot_desc.verify(&slot_validation.signer)`, which is oblivious to which contract the check occurs in: [3](#0-2) 

The same gap exists in `PeerNetwork::validate_received_chunk`, used for both StackerDB sync and unsolicited pushed chunks — it looks up the slot signer *for the given contract* but the signature itself never proves it was intended for that contract: [4](#0-3) 

This is structurally the same equality break as the Gondi H-17 issue: a signed struct/signature meant for one operation/context (`refinanceFull`) is accepted by a second operation/context (`addNewTranche`) because the signature does not bind the context. Here, the "context" is the specific StackerDB contract (e.g. `signers-0-1` vs `signers-0-2` vs `signers-1-1`), and the signer-key-to-slot-id mapping is shared across many contracts by design (miners and each signer own the same numeric slot index across all `.signers-X-Y` lanes for a reward cycle, and often the same index recurs across reward cycles).

Notably, the codebase already has partial, defense-in-depth awareness of this exact class of confusion on the *read* side: `signer_message_payload_matches_lane` in `libsigner/src/events.rs` explicitly rejects payload type-prefixes that don't match the consuming contract's expected `MessageSlotID` lane, specifically to stop cross-lane payload confusion: [5](#0-4) [6](#0-5) 

However, this check is only applied when the miner/signer node parses a `StackerDBChunksEvent` into a `SignerEvent` — it is not applied at the point the chunk is authenticated and *written* into StackerDB storage (`try_replace_chunk` / `validate_received_chunk`). Any node relaying or accepting a StackerDB chunk over the p2p network, or via the `POST /v2/stackerdb/{principal}/{contract_name}/chunks` RPC endpoint, will accept and store a chunk purely because the signature recovers to the slot's designated signer for *that* contract, regardless of whether that exact `(slot_id, slot_version, data)` tuple/signature was originally produced for an entirely different contract.

### Impact Explanation
An attacker who observes a legitimately signed `StackerDBChunkData` broadcast on one StackerDB contract (e.g. a `BlockPreCommit` chunk on `signers-0-3`) can, if the same signer owns the identical `slot_id` on another contract they can also reach (e.g. `signers-0-1`/BlockResponse, or the same lane in a different/future reward cycle contract, or the `.miners` contract if slot numbering coincides), replay that chunk (unmodified — same slot_id, slot_version, data, signature) into the other contract via `POST /v2/stackerdb/.../chunks` or via unsolicited `StackerDBPushChunk` gossip, and have it accepted as valid, authentic data for that unrelated contract — because `try_replace_chunk`/`validate_received_chunk` never check that the signature was scoped to that contract. This lets forged/misattributed data propagate as if it were legitimately written by the signer to that specific lane, potentially causing downstream signer/miner consumers (which do not always defensively check the lane, e.g. anything using `SignerMessage::consensus_deserialize` directly rather than the `SignerEvent` filter) to misinterpret bytes belonging to one message type as another, or to inject stale/duplicate data as though it were fresh for a different reward cycle/contract.

### Likelihood Explanation
Moderate: exploitation is remote and unprivileged (any peer able to observe StackerDB gossip and reach the target node's p2p or RPC endpoints), and requires only that a signer's numeric slot index coincide across two contracts it participates in — a condition that is structurally common by the `signers-<set>-<message_id>` numbering scheme and by signer-index continuity across reward cycles.

### Recommendation
Bind the signed digest to the target contract by including the `QualifiedContractIdentifier` (and ideally the reward cycle / message-id "lane") in `SlotMetadata::auth_digest()`, so a chunk's signature is only valid for the specific StackerDB instance it was produced for. Additionally, enforce the existing `signer_message_payload_matches_lane`-style lane check at the point chunks are validated/stored (`try_replace_chunk` / `validate_received_chunk`), not only when parsing `SignerEvent`s, so cross-lane/cross-contract replays are rejected before being persisted or gossiped further.

### Proof of Concept
Conceptual PoC (cannot be executed without a live two-node network, but the code paths are demonstrable):
1. Signer `S` owns `slot_id = 0` in both `signers-0-1` (BlockResponse) and `signers-0-3` (BlockPreCommit) contracts of the same reward cycle (per `NakamotoSigners::make_signers_db_contract_id` numbering).
2. `S` legitimately signs and pushes `StackerDBChunkData{slot_id:0, slot_version:1, data: <BlockPreCommit bytes>}` to `signers-0-3`.
3. An observer captures this chunk from p2p gossip (`StackerDBPushChunk`) or via `GET /v2/stackerdb/.../chunks/0`.
4. The observer re-submits the identical `(slot_id, slot_version, sig, data)` tuple to `signers-0-1` via `POST /v2/stackerdb/{S}/signers-0-1/chunks`.
5. `try_replace_chunk` (via `db.rs:411-423`) looks up the slot-1 signer for `signers-0-1` (which is also `S`), calls `slot_desc.verify(&S)`, which succeeds because `auth_digest()` never referenced the contract — the chunk is accepted and stored as if it were a legitimate BlockResponse-lane write, even though it is BlockPreCommit-typed data.
6. Downstream consumers that trust `try_replace_chunk`'s acceptance without re-checking `signer_message_payload_matches_lane` (unlike `SignerEvent::try_from`) will treat this as authentic data for the wrong lane.

    fn auth_digest(&self) -> Sha512Trunc256Sum {
        let mut hasher = Sha512_256::new();
        hasher.update(self.slot_id.to_be_bytes());
        hasher.update(self.slot_version.to_be_bytes());
        hasher.update(self.data_hash.0);
        Sha512Trunc256Sum::from_hasher(hasher)
    }

/// Whether a `SignerMessage` payload type is the one expected for the given contract message id.
///
/// `lane_message_id` is the trailing number in the `signers-X-{lane_message_id}` boot
/// contract. Each signer-message contract is dedicated to exactly one `SignerMessage`
/// variant, so the payload's type-prefix byte must map to the same numeric `MessageSlotID`.
///
/// Miner-only payloads (`BlockProposal`, `BlockPushed`, `MockProposal`, `MockBlock`) are not
/// written to a signer contract and never match.
fn signer_message_payload_matches_lane(
    payload_kind: SignerMessageTypePrefix,
    lane_message_id: u32,
) -> bool {
    payload_kind
        .msg_id()
        .is_some_and(|slot| slot.to_u32() == lane_message_id)
}
