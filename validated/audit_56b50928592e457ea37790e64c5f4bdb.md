### Title
Unprivileged attacker can force-fill a victim's token list to `MAX_TOKENS_PER_USER` via permissionless `deposit(amount_, onBehalfOf_)`, permanently blocking the victim from receiving any new collateral token — (File: contracts/DepositToken.sol)

### Summary
Metronome mirrors the USDM "source-only" restriction pattern: `DepositToken.deposit` and `_transfer`/`seize` only constrain the *sender* side (`_revertIfLocked(_msgSender)` / `onlyIfCanSeize`), while the *recipient* is never consulted. Because `deposit()` accepts an arbitrary `onBehalfOf_` beneficiary, an attacker can mint dust amounts of every registered `DepositToken` directly into a victim's account. Each first-time mint calls `Pool.addToDepositTokensOfAccount(victim)`, and once the victim's combined debt+deposit token count reaches `MAX_TOKENS_PER_USER` (30), `onlyIfAdditionWillNotReachMaxTokens` makes every subsequent mint/transfer/seize of a *new* token type to the victim revert with `UserReachedMaxTokens`. ### Finding Description
- `DepositToken.deposit(uint256 amount_, address onBehalfOf_)` is public, `whenNotPaused nonReentrant`, requires only `amount_ > 0` and `onBehalfOf_ != 0`, and mints msdTOKEN to an attacker-chosen beneficiary. [4](#0-3) 
- `_mint`/`_transfer` call `pool.addToDepositTokensOfAccount(recipient)` whenever the recipient's prior balance is `0`. [5](#0-4) 
- `Pool.addToDepositTokensOfAccount` enforces `debtTokensOfAccount.length + depositTokensOfAccount.length < MAX_TOKENS_PER_USER` (30) and reverts otherwise. [6](#0-5) 
- An EOA loops over all registered deposit tokens, acquiring a dust amount of each underlying (or routing through `NativeTokenGateway`/`Operator.execute`) and calling `deposit(dust_i, victim)`. After ~30 deposits the victim's list is full.
- From then on, any `_mint`/`_transfer` of a deposit token the victim does not already hold reverts at `addToDepositTokensOfAccount`, which is executed inside `deposit`, `transfer`, `transferFrom`, and `seize` — so the victim cannot receive new collateral types, cannot have third parties deposit on their behalf, and cannot be minted new collateral via SmartFarmingManager flows.
- The victim also cannot trivially remove the poisoned entries: removal requires their balance of that token to reach `0` (`_transfer` → `removeFromDepositTokensOfAccount`), and if the victim carries any debt, `_revertIfLocked` blocks transferring out the locked dust; the victim must first repay enough debt to unlock it. [7](#0-6) [8](#0-7) 

### Impact Explanation
Temporary-to-persistent freezing of a user's ability to receive collateral. The victim's existing positions are not stolen, but all inbound flows of new deposit-token types (deposits on their behalf, ordinary ERC20 transfers, liquidation-related `seize` proceeds routed to them, SmartFarmingManager position openings) revert. If the victim has outstanding debt such that the dust tokens are within their locked balance, they cannot clear the entries without repaying debt first — extending the freeze. The attacker bears only the cost of dust deposits of each underlying.

### Likelihood Explanation
Requires only an unprivileged EOA calling the public `deposit` on each `DepositToken` — no roles, no oracle manipulation, no privileged calls. Feasibility depends on the deployed pool having enough registered deposit tokens for the victim to reach `debt + deposit == 30` (the cap is shared across both lists, so existing debt positions reduce the number of deposits needed). Cost scales with the number of tokens needed and each token's minimum viable deposit.

### Recommendation
Either (a) only auto-add to `depositTokensOfAccount` on user-initiated deposits (`msg.sender == onBehalfOf_`) and require an explicit opt-in call for first-time token receipt, or (b) allow the account owner to call a `removeFromDepositTokensOfAccount`-style exit for zero-value/unwanted entries, or (c) bound the effect by skipping the add for balances below a dust threshold. Document that recipients cannot refuse inbound msdTOKEN mints.
