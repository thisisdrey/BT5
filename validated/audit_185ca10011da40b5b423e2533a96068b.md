## Analog Confirmed

### Title
Permissionless `lending_pool_emissions_deposit` lets a first depositor inflate `asset_share_value`, causing checked-math overflow/DoS or zero-share theft for later depositors - (File: `programs/marginfi/src/instructions/marginfi_group/configure_bank.rs`)

### Summary
`lending_pool_emissions_deposit` is a **permissionless** instruction — its `depositor` account is a plain `Signer`, with no admin/group-authority check — that directly rewrites `bank.asset_share_value` as `updated_total_assets / total_asset_shares`, where `total_asset_shares` is only guarded by a non-zero check. [1](#0-0) [2](#0-1) 

This is structurally identical to the Merit Circle bug class: a party who controls (nearly) 100% of the outstanding "shares" (`total_asset_shares`) can call a permissionless "distribute rewards"-style function to inflate the per-share value (`pointsPerShare` ↔ `asset_share_value`) to an arbitrary magnitude, because the function only requires `total_asset_shares > I80F48::ZERO`, not any minimum share supply. [3](#0-2) 

### Finding Description
1. An attacker opens a brand-new bank (or targets one that currently has a negligible `total_asset_shares`) and makes the first deposit of a dust amount (e.g. `1` native unit). Because the first deposit is issued 1:1 against `asset_share_value = I80F48::ONE` at bank creation, `total_asset_shares` becomes a tiny number that the attacker fully controls. [4](#0-3) 
2. The attacker then calls `lending_pool_emissions_deposit` (any signer can call it — it is meant for third parties to fund same-mint incentive campaigns) with a large `amount`, funded from their own `emissions_funding_account`. This transfers tokens into the liquidity vault and recomputes:
   `bank.asset_share_value = (total_assets + amount) / total_asset_shares`. [5](#0-4) 
   Since `total_asset_shares` is attacker-controlled and tiny, `asset_share_value` can be pushed to an arbitrarily large multiple of its previous value in one or a few calls (repeatable, since nothing prevents calling it again before any other depositor joins).
3. Because the attacker is (near) the sole holder of `total_asset_shares`, later withdrawal by the attacker recovers essentially all of the "donated" emissions back (self-funding, low net cost) — mirroring the Merit Circle PoC where the attacker deposits, locks, and distributes rewards to themselves before a victim arrives.
4. Once `asset_share_value` is inflated, two concrete failure modes are reachable for **later, unprivileged depositors**:
   - **Griefing/theft via rounding**: `get_asset_shares(value) = value / asset_share_value` — a legitimate depositor's real token deposit can round down toward a share count with negligible fractional precision relative to their contribution, effectively donating value to the pool/attacker's now-outsized share. [6](#0-5) 
   - **Permanent DoS via overflow**: `get_asset_amount(shares) = shares.checked_mul(asset_share_value)` and the interest-accrual math (`total_assets = get_asset_amount(total_asset_shares)`) both use `checked_mul`/`checked_div` over `I80F48` (80 integer bits, max ≈ 6.04e23). Once `asset_share_value` is inflated far enough (further compounded by subsequent legitimate deposits raising `total_asset_shares`), these multiplications overflow and return `math_error!()`, which propagates as a hard instruction failure. [7](#0-6) [8](#0-7) 
   `get_asset_amount` and `accrue_interest` are invoked on essentially every deposit, withdraw, borrow, repay, and health-check instruction that touches this bank, so once the overflow threshold is crossed, all depositors already holding a position in that bank become permanently unable to withdraw, borrow, or have their health computed — a lasting freeze of their funds, exactly matching the "users who deposited before will be unable to withdraw their funds" impact in the source report.

### Impact Explanation
This is a core-accounting/bank-path issue reachable by any unprivileged user with no special permissions: only a signer and real tokens are required. The impact ranges from siloed loss for individual later depositors (rounding-down theft) up to a bank-wide, unrecoverable freeze of all outstanding positions in that bank once `checked_mul`/`checked_div` overflow is triggered on the shared `asset_share_value`/`total_asset_shares` fields that every account-touching instruction reads.

### Likelihood Explanation
Likelihood is moderate-to-high for newly created or thinly-capitalized banks: creating a bank and being the first depositor is trivial and permissionless, and `lending_pool_emissions_deposit` has no minimum share-supply guard, no restriction tying the caller to being the group admin, and no cap relating `amount` to `total_asset_shares`. The only cost to the attacker is the capital transferred as "emissions," most of which is recoverable by withdrawing their own inflated share afterward.

### Recommendation
- Require a minimum `total_asset_shares` (or a minimum ratio of `amount` to `total_asset_shares`) before `lending_pool_emissions_deposit` is allowed to move `asset_share_value`, so a single near-zero-share depositor cannot dictate share-price growth.
- Alternatively/additionally, cap the per-call growth factor of `asset_share_value` (e.g., disallow more than an X% increase per call), and/or require group-admin authorization for `lending_pool_emissions_deposit` rather than an arbitrary signer.
- Add an explicit sanity ceiling on `asset_share_value` and reject state transitions that would push it near the `I80F48` overflow boundary, converting a silent future DoS into an immediate, informative rejection at the time of the manipulating call.

### Proof of Concept
1. Attacker creates (or targets) a bank and calls `lending_account_deposit` for `1` native unit — the first deposit — setting `total_asset_shares = 1`, `asset_share_value = 1`. [9](#0-8) 
2. Attacker calls `lending_pool_emissions_deposit` with a large `amount` funded from their own token account; since `total_asset_shares == 1`, `bank.asset_share_value` jumps to `(1 + amount)`. [10](#0-9) 
3. Repeat step 2 (or use a low-decimal, high-supply mint) to push `asset_share_value` toward the `I80F48` limit (~6e23).
4. A legitimate user deposits a normal amount into the same bank; on the next `accrue_interest` or any instruction that calls `get_asset_amount(total_asset_shares)`, the `checked_mul` overflows and returns `MarginfiError` via `math_error!()`, reverting the transaction and permanently blocking deposit/withdraw/health-check operations on that bank for every existing position holder. [8](#0-7)
