Audit Report

## Title
Snowbridge relayer reward XCM omits `AssetClaimer`, letting `DepositAsset` failures on AssetHub trap rewards under an unreachable origin after the reward record is already deleted - (`bridges/snowbridge/primitives/core/src/reward.rs`)

## Summary
`PayAccountOnLocation::pay_reward` builds an XCM to AssetHub consisting of `UnpaidExecution`, `DescendOrigin`, `UniversalOrigin`, `ReserveAssetDeposited`, `DepositAsset` and returns `Ok(())` as soon as the message is handed to `XcmSender::deliver`, without ever setting a `SetHints { hints: [AssetClaimer, ..] }` instruction. Meanwhile `pallet-bridge-relayers::do_claim_rewards` deletes the `RelayerRewards` storage entry and emits `RewardPaid` immediately upon `pay_reward` returning `Ok(())`, before the XCM has actually executed on AssetHub. If `DepositAsset` fails there (e.g., beneficiary frozen/filtered/below ED), `XcmExecutor::post_process` traps the holding assets under `self.asset_claimer.or(self.context.origin).unwrap_or(original_origin)` — since no claimer hint is set, this resolves to the descended bridge/Ethereum-universal origin rather than any account the relayer or beneficiary controls, and the reward record has already been irreversibly deleted on BridgeHub.

## Finding Description
`do_claim_rewards` uses `RelayerRewards::try_mutate_exists` and only rolls back the reward removal if `PaymentProcedure::pay_reward` itself returns an `Err`: [1](#0-0) 

`PayAccountOnLocation::pay_reward` (the `PaymentProcedure` used for `BridgeReward::Snowbridge`) constructs the XCM, validates/sends it, charges delivery fees, and calls `XcmSender::deliver(ticket)`, returning `Ok(())` the moment delivery succeeds — it has no visibility into whether `DepositAsset` will actually succeed on AssetHub: [2](#0-1) 

Notably, the XCM instruction list contains no `SetHints { hints: [AssetClaimer, ..] }` and no `ClearOrigin`, unlike the analogous inbound-queue-v2 message converter, which explicitly sets an `AssetClaimer` hint before placing assets in holding precisely so that a downstream failure traps funds under a reconstructible/signable claimer location. The XCM executor's fallback trap-claimer logic confirms that, absent an explicit `AssetClaimer` hint, trapped assets are attributed to `self.context.origin` (the descended/universal-origin context established by `DescendOrigin`/`UniversalOrigin` in this program) or the original sending origin — not a location the relayer or beneficiary can sign for on AssetHub.

This is the same class of defect the codebase has already remediated once, per `prdoc/stable2603-3/pr_11919.prdoc`, which fixed a mismatched fallback claimer network specifically because it made "default-claimer trapped funds effectively unrecoverable without a runtime upgrade" — demonstrating the project treats an unreachable/mismatched trap claimer as a genuine fund-lock bug, not merely a cosmetic one.

## Impact Explanation
If the beneficiary supplied to `claim_rewards_to` cannot accept the `DepositAsset` on AssetHub (frozen account, insufficient existential deposit, filtered asset, etc.), the reward asset is trapped under a system-level derived origin that the relayer cannot reconstruct as a signed origin, while `RelayerRewards` has already been cleared and `RewardPaid` already emitted on BridgeHub. This is a permanent fund-lock: the relayer's earned reward becomes unrecoverable via `pallet_xcm::claim_assets` because no signed account matches the trap key, satisfying the "permanent user-fund lock" impact category.

## Likelihood Explanation
Medium. It requires the caller-supplied `beneficiary: Location` for `claim_rewards_to(_, BridgeReward::Snowbridge, BridgeRewardBeneficiaries::AssetHubLocation(beneficiary))` to fail `DepositAsset` execution on AssetHub — e.g., a frozen/filtered account, an account below ED for the derivative WETH asset, or a location rejected by the destination's barrier/filter. This can be triggered by any relayer supplying (intentionally or by mistake) such a beneficiary; no privileged actor, off-chain compromise, or malicious peer is required, satisfying the "unprivileged external attacker using public extrinsics" bar. The condition is deterministic and repeatable given a suitable beneficiary.

## Recommendation
- Add `SetHints { hints: [AssetClaimer { location: beneficiary.clone() }] }` (or the relayer's own reconstructible account) to the XCM built in `PayAccountOnLocation::pay_reward`, mirroring the pattern already used in the inbound-queue-v2 converter, so that any `DepositAsset` failure traps the reward under a location the relayer/beneficiary can sign for and reclaim via `pallet_xcm::claim_assets`.
- Alternatively/additionally, avoid treating `XcmSender::deliver` success as final settlement in `do_claim_rewards`: require confirmation of remote execution (e.g., an XCM query/response) before permanently deleting the `RelayerRewards` entry, or provide a re-credit path if remote execution failure is later observed.

## Proof of Concept
1. A relayer accrues a reward for `BridgeReward::Snowbridge` via `register_reward`.
2. The relayer calls `claim_rewards_to(origin, BridgeReward::Snowbridge, BridgeRewardBeneficiaries::AssetHubLocation(beneficiary))` where `beneficiary` resolves on AssetHub to an account that will fail `TransactAsset::deposit_asset` for the reward asset (e.g., frozen, filtered, or below ED with the reward asset being the only one in the deposit).
3. `do_claim_rewards` calls `PayAccountOnLocation::pay_reward`, which builds the XCM (`UnpaidExecution`, `DescendOrigin`, `UniversalOrigin`, `ReserveAssetDeposited`, `DepositAsset`), successfully delivers it, and returns `Ok(())`; `RelayerRewards` is removed and `RewardPaid` is emitted on BridgeHub.
4. On AssetHub, the XCM executes: `ReserveAssetDeposited` succeeds, `DepositAsset` fails for the chosen beneficiary; since no `AssetClaimer` hint was set, `post_process` traps the holding under the descended/universal `context.origin`.
5. The relayer/beneficiary cannot construct a signed origin matching the trap key on AssetHub via `pallet_xcm::claim_assets`, so the reward is permanently lost despite `RewardPaid` already having fired. [3](#0-2) [2](#0-1)

	fn pay_reward(
		relayer: &Relayer,
		_: (),
		reward: RewardBalance,
		beneficiary: Self::Beneficiary,
	) -> Result<(), Self::Error> {
		let ethereum_location = Location::new(2, [GlobalConsensus(EthereumNetwork::get())]);
		let assets: Asset = (ethereum_location.clone(), reward.into()).into();

		let xcm: Xcm<()> = alloc::vec![
			UnpaidExecution { weight_limit: Unlimited, check_origin: None },
			DescendOrigin(InboundQueueLocation::get().into()),
			UniversalOrigin(GlobalConsensus(EthereumNetwork::get())),
			ReserveAssetDeposited(assets.into()),
			DepositAsset { assets: AllCounted(1).into(), beneficiary },
		]
		.into();

		let (ticket, fee) =
			validate_send::<XcmSender>(AssetHubLocation::get(), xcm).map_err(|_| XcmSendFailure)?;
		XcmExecutor::charge_fees(relayer.clone(), fee).map_err(|_| ChargeFeesFailure)?;
		XcmSender::deliver(ticket).map_err(|_| XcmSendFailure)?;

		Ok(())
	}
