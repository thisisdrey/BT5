### Title
Attachment content is stored and served without verifying it matches the requested content-hash - (File: stackslib/src/net/atlas/download.rs)

### Summary
When the `AttachmentsDownloader` finishes downloading an `/v2/attachments/{content_hash}` response from a peer, it inserts the returned `Attachment` bytes into the `AtlasDB` and pairs it with the pending `AttachmentInstance` **without ever checking that `Hash160::from_data(&content) == content_hash`**. The `content_hash` is the on-chain commitment (emitted by the BNS/Atlas smart contract) that is supposed to authenticate the attachment content; skipping this check breaks that equality and allows any remote peer serving `/v2/attachments/{hash}` to substitute arbitrary content for a legitimate attachment.

There is no comparison against the `content_hash` that was used to build the `AttachmentRequest` in the first place (`self.content_hash`, set in `get_prioritized_attachments_requests`, `stackslib/src/net/atlas/download.rs:404-479`). The request URL is built purely from the expected hash: [2](#0-1) 

But the *response* is trusted as-is. Later, in `AttachmentsDownloader::run`, the returned attachment is committed to disk and paired with every matching `AttachmentInstance` purely by re-hashing the *attacker-supplied* content and looking that up: [3](#0-2) 

```rust

        .find_all_attachment_instances(&attachment.hash())
        .map_err(net_error::DBError)?;
    network
        .atlasdb
        .insert_instantiated_attachment(&attachment)
        .map_err(net_error::DBError)?;
    ...
    context.attachments_batch.resolve_attachment(&attachment.hash())
}
```

`attachment.hash()` is computed from the content that was just received (`Hash160::from_data(&self.content)`), not compared against the `content_hash` that was actually requested. Practically, this only "works" (i.e. resolves the correct pending instance) if the attacker returns content whose hash happens to equal the expected `content_hash` — but that is exactly the property that should have been *enforced*, not merely *incidentally relied upon*. Crucially, nothing rejects a response whose declared/returned bytes don't hash-match the request; the code simply inserts whatever is returned and marks the batch entry "resolved" by hashing that same (attacker-controlled) content. Compare this to the correctly-guarded equivalent for `StackerDB`, where signature verification is checked with an explicit equality/verify call before storage (`stackslib/src/net/stackerdb/db.rs:398-439`) — Atlas has no analogous explicit check tying the stored bytes back to the authenticated on-chain `content_hash` before it's exposed via `GET /v2/attachments/{hash}`.

Once inserted via `insert_instantiated_attachment`, the content becomes servable to any client at `/v2/attachments/{content_hash}` (`stackslib/src/net/api/getattachment.rs`), and is looked up purely by the hash key in the `attachments` table (`find_attachment`, `stackslib/src/net/atlas/db.rs:641-648`), which trusts whatever was written under that key.

### Impact Explanation
This breaks the "committed-hash vs served content" equality that Atlas is supposed to guarantee: a malicious or compromised peer that returns arbitrary bytes as the "attachment" for a given `content_hash` request can have that data written into the local `AtlasDB` and subsequently served by the node as if it were the authentic, on-chain-committed attachment (e.g., BNS zonefile data). Any client or other peer fetching `GET /v2/attachments/{hash}` from this node would receive forged data as canonical, and the poisoned data would also propagate further since matched instances are marked resolved and reported through event dispatch (`observer.new_stackerdb_chunks`-style hooks are not used here, but `resolved_attachments` feeds into consumers that treat the pairing as validated). This matches the "serving non-canonical/mismatched data as canonical" category (High impact) — it is a BNS/attachment mismatch.

### Likelihood Explanation
Exploitation requires only that the attacker's node be selected as an Atlas peer to serve an attachment request — Atlas peer selection has no special trust requirement beyond running the P2P protocol and reporting a "reliable" peer profile, and this is a normal, unauthenticated HTTP GET. No signature, node key, or special role is required; it is directly reachable from the standard attachment-sync flow.

### Recommendation
In `AttachmentsBatchStateContext::extend_with_attachments` (or immediately in `AttachmentsDownloader::run` before insertion), verify `attachment.hash() == request.content_hash` for the specific `AttachmentRequest` that produced the response, and drop/penalize the peer (bump `report.bump_failed_requests()`) if the hash does not match, instead of unconditionally inserting the response's content.

### Proof of Concept
1. Configure a malicious Atlas peer that responds to `GET /v2/attachments/{content_hash}` with an HTTP 200 and an arbitrary `Attachment { content: <attacker bytes> }` whose `Hash160::from_data(content)` does **not** equal the requested `content_hash`.
2. Have a victim node queue an `AttachmentInstance` referencing that `content_hash` (e.g. via a legitimate BNS name-registration event) and select the malicious peer as a download source (achievable since peer selection only requires being an outbound Atlas-sync peer, `network.get_outbound_sync_peers()`).
3. Observe that `AttachmentsBatchStateContext::extend_with_attachments` accepts the response (`decode_atlas_get_attachment()` succeeds) and inserts it via `insert_instantiated_attachment` without ever checking equality against `content_hash`.
4. Query `GET /v2/attachments/{attacker's-content-hash}` on the victim node and observe it serves the attacker's forged content as if it were validated Atlas data (assuming the attacker sets their served content-hash to a value they control, they can arbitrarily poison the AtlasDB entry that later `find_attachment`/`find_all_attachment_instances` lookups will match on).

    pub fn extend_with_attachments(
        mut self,
        results: &mut BatchedRequestsResult<AttachmentRequest>,
    ) -> AttachmentsBatchStateContext {
        for (request, response) in results.succeeded.drain() {
            let report = self
                .peers
                .get_mut(request.get_url())
                .expect("Atlas: unable to retrieve reliability report for peer");

            let response = if let Some(r) = response {
                r
            } else {
                report.bump_failed_requests();
                continue;
            };

            if let Ok(response) = response.decode_atlas_get_attachment() {
                self.attachments.insert(response.attachment);
                report.bump_successful_requests();
            } else {
                report.bump_failed_requests();
            }
        }
        let mut events_ids = results.faulty_peers.keys().copied().collect::<Vec<usize>>();
        self.events_to_deregister.append(&mut events_ids);

        self
    }
