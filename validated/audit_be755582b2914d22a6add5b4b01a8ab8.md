Based on my investigation, I found a strong structural analog to the Umee rounding bug in java-tron's on-chain bancor-style **Exchange** (TRX/TRC10 AMM) subsystem.

### Title
Floating-point truncation in legacy `ExchangeProcessor` bonding-curve math allows value extraction from exchange pools via repeated `ExchangeTransactionContract` calls - (File: `chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java`)

### Summary
`ExchangeTransactionActuator`, `ExchangeInjectActuator`, and `ExchangeWithdrawActuator` let any account swap/inject/withdraw TRX and TRC10 tokens against an on-chain bancor-formula liquidity pool (`ExchangeCapsule`). The pool balance conversion is delegated to `ExchangeCapsule.transaction()`, which by default uses the legacy `ExchangeProcessor` implementation instead of the newer, safer `SafeExchangeProcessor`.

### Finding Description
`ExchangeCapsule.transaction()` selects between two math implementations based on the `hardenedCalc` (`allowHarden()`) flag: [1](#0-0) 

The legacy path, `ExchangeProcessor`, performs the Bancor-formula conversion using `double` arithmetic and truncates the result to `long` via a plain cast (`(long) issuedSupply`, `(long) exchangeBalance`), which always rounds toward zero regardless of which side the error favors: [2](#0-1) 

This is functionally identical to the Umee bug class: a fixed/floating precision calculation truncated to an integer, where the truncation direction is not deliberately chosen to always favor the pool ("module"). Because the conversion is a two-step process (`exchangeToSupply` then `exchangeFromSupply`), the compounded double-precision + truncation error is not analyzed for direction, and an attacker can perform many small trades in either direction to accumulate the truncation error in their own favor at the pool's expense.

This is contrasted by the hardened path, `SafeExchangeProcessor`, which uses `BigDecimal` with an explicit `RoundingMode.DOWN`/`HALF_UP` and correctly-scoped operations to avoid the imprecision — evidence that java-tron's own developers recognized and fixed this exact rounding-error class, but gated the fix behind the `allowHardenExchangeCalculation` dynamic parameter (activated via committee proposal): [3](#0-2) [4](#0-3) 

Similarly, `ExchangeInjectActuator.execute()` (non-hardened) computes the counter-token amount with plain integer `floorDiv`, while `doValidate()` uses `BigInteger` division truncated via `longValueExact()` — two different rounding computations for the same "another token quant," creating a mismatch surface between validation and execution: [5](#0-4) [6](#0-5) 

### Impact Explanation
If `allowHardenExchangeCalculation` is not yet activated on a given network (I could not verify its default/current activation state within available context — this would need to be confirmed against the live `DynamicPropertiesStore` default and any executed committee proposal), any unprivileged account holding an `ExchangeCreateContract`-created pool position can call `ExchangeTransactionContract` repeatedly with carefully chosen small `quant` values. Because the pool math floors/truncates a `double`-derived intermediate "relay" supply value in two chained conversions, an attacker can identify quant sizes where the compounded rounding error benefits the trader, extracting value from the pool balance (`firstTokenBalance`/`secondTokenBalance`) each time, similar to how the Umee attacker repaid slightly less than borrowed each iteration. Repeated automated execution (a single account issuing many transactions, or looping within available bandwidth/energy) can drain a pool's reserves over time — a direct funds-loss/unbacked-balance impact on the `ExchangeStore`/`ExchangeV2Store` capsule that other liquidity participants rely on to withdraw their share.

### Likelihood Explanation
Reaching this code path requires only a standard signed `ExchangeTransactionContract`/`ExchangeInjectContract`/`ExchangeWithdrawContract` transaction — no special privilege, SR/witness role, or contract deployment is needed, matching the "unprivileged transaction broadcaster" reachability bar. The likelihood is directly tied to whether `allowHardenExchangeCalculation` is enabled on the target network; if it is already enabled everywhere (superseding the vulnerable path), the practical exploitability is eliminated, which I was unable to conclusively confirm.

### Recommendation
- Confirm and, if not already done, activate `allowHardenExchangeCalculation` on all networks so `SafeExchangeProcessor`/`BigDecimal`-based paths are always used, removing the legacy `double`-based `ExchangeProcessor` and integer `floorDiv` paths from executable code entirely (rather than leaving them reachable via a toggle).
- Ensure the rounding direction in `SafeExchangeProcessor`/`ExchangeWithdrawActuator`/`ExchangeInjectActuator` always favors the pool (round down amounts paid out to the user, round up amounts taken from the user) rather than using symmetric `HALF_UP`/`DOWN` modes that can favor either side depending on operand signs.
- Add fuzz/property tests asserting that no sequence of exchange operations can result in a net increase of a user's combined token value without a corresponding decrease in the pool's reserves.

### Proof of Concept
A concrete PoC would require simulating repeated `ExchangeTransactionContract` calls against a freshly created pool with `allowHardenExchangeCalculation` disabled, choosing `tokenQuant` values near pool-balance ratios that maximize the double/truncation discrepancy in `ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply`, and observing that `sum(anotherTokenQuant received) - sum(tokenQuant paid)` trends positive for the attacker while the pool's `firstTokenBalance`/`secondTokenBalance` decreases beyond what the AMM formula intends — directly analogous to the `TestTruncationBug` test provided in the external report. I was not able to execute this simulation in this environment; a background Devin session with the ability to run the existing `ExchangeTransactionActuatorTest`/`ExchangeCapsuleTest` test harness would be needed to empirically measure the truncation drift and confirm the default value of `allowHardenExchangeCalculation`.

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }

  private BigDecimal exchangeToSupply(long balance, long quant) {
    long newBalance = StrictMathWrapper.addExact(balance, quant);
    BigDecimal bdQuant = BigDecimal.valueOf(quant);
    BigDecimal bdNewBalance = BigDecimal.valueOf(newBalance);
    BigDecimal base = BigDecimal.ONE.add(
        bdQuant.divide(bdNewBalance, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 0.0005);
    return SUPPLY.negate().multiply(
        BigDecimal.ONE.subtract(BigDecimal.valueOf(powResult))).setScale(0, RoundingMode.DOWN);
  }

  private long exchangeFromSupply(long balance, BigDecimal supplyQuant) {
    BigDecimal bdBalance = BigDecimal.valueOf(balance);
    BigDecimal base = BigDecimal.ONE.add(
        supplyQuant.divide(SUPPLY, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 2000.0);
    BigDecimal exchangeBalance = bdBalance.multiply(
        BigDecimal.valueOf(powResult).subtract(BigDecimal.ONE));
    return exchangeBalance.setScale(0, RoundingMode.DOWN).longValueExact();
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    BigDecimal relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
