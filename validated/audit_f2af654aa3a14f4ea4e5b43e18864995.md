### Title
Missing `chain_id` in `SignerCapabilityOfferProofChallengeV2` Enables Cross-Chain Replay of Signer Capability Offers — (`aptos-move/framework/aptos-framework/sources/account/account.move`)

---

### Summary

`SignerCapabilityOfferProofChallengeV2`, the struct signed to authorize `offer_signer_capability`, omits the `chain_id` field that its sibling struct `RotationCapabilityOfferProofChallengeV2` explicitly includes. Because the signed message contains no chain binding, a valid signature produced on one Aptos network (e.g., testnet) can be replayed verbatim on any other Aptos network (e.g., mainnet) where the victim's account has the same sequence number, granting the attacker a `SignerCapability` over the victim's account and full control of their assets.

---

### Finding Description

Two parallel V2 challenge structs exist in `account.move`:

```move
// RotationCapabilityOfferProofChallengeV2 — correctly includes chain_id
struct RotationCapabilityOfferProofChallengeV2 has drop {
    chain_id: u8,          // ← chain binding present
    sequence_number: u64,
    source_address: address,
    recipient_address: address,
}

// SignerCapabilityOfferProofChallengeV2 — chain_id is absent
struct SignerCapabilityOfferProofChallengeV2 has copy, drop {
    sequence_number: u64,
    source_address: address,
    recipient_address: address,  // ← no chain_id
}
``` [1](#0-0) 

The code comment on `RotationCapabilityOfferProofChallengeV2` explicitly states: *"This V2 struct adds the `chain_id` and `source_address` to the challenge message, which prevents replaying the challenge message."* The same protection was never applied to `SignerCapabilityOfferProofChallengeV2`.

`offer_signer_capability` constructs the challenge without `chain_id` and verifies it via `verify_signed_message` → `ed25519::signature_verify_strict_t`:

```move
let proof_challenge = SignerCapabilityOfferProofChallengeV2 {
    sequence_number: get_sequence_number(source_address),
    source_address,
    recipient_address,
};
verify_signed_message(
    source_address, account_scheme, account_public_key_bytes,
    signer_capability_sig_bytes, proof_challenge);
``` [2](#0-1) 

`signature_verify_strict_t` wraps the struct in `SignedMessage { type_info: type_info::type_of<T>(), inner: data }`:

```move
public fun signature_verify_strict_t<T: drop>(
    signature: &Signature, public_key: &UnvalidatedPublicKey, data: T): bool {
    let encoded = SignedMessage {
        type_info: type_info::type_of<T>(),
        inner: data,
    };
    signature_verify_strict_internal(signature.bytes, public_key.bytes, bcs::to_bytes(&encoded))
}
``` [3](#0-2) 

The `type_info` encodes `{account_address: 0x1, module_name: "account", struct_name: "SignerCapabilityOfferProofChallengeV2"}` — identical on every Aptos network. The only replay-prevention fields are `sequence_number` and `source_address`, neither of which is chain-specific.

By contrast, `offer_rotation_capability` reads `chain_id::get()` into its challenge struct before calling the same `verify_signed_message` path:

```move
let proof_challenge = RotationCapabilityOfferProofChallengeV2 {
    chain_id: chain_id::get(),
    sequence_number: account_resource.sequence_number,
    source_address: addr,
    recipient_address,
};
``` [4](#0-3) 

---

### Impact Explanation

An attacker who obtains a valid `offer_signer_capability` signature from a victim on any Aptos network can replay it on mainnet whenever the victim's mainnet account sequence number matches the one embedded in the signature. Once the signer capability is installed, the attacker calls `create_authorized_signer` to obtain a `signer` for the victim's address and can:

- Transfer all APT from the victim's account
- Transfer all fungible assets and token objects
- Execute arbitrary transactions as the victim [5](#0-4) 

This constitutes direct, unauthorized theft of user-controlled on-chain assets.

---

### Likelihood Explanation

The attack requires:
1. The victim has an account on both the source chain (e.g., testnet) and mainnet with the same address.
2. The victim's mainnet sequence number equals the sequence number embedded in the captured signature.

The most straightforward case: a victim whose mainnet account has sequence number 0 (never used) signs a testnet challenge at sequence number 0 — a common scenario for new users testing dapps on testnet before mainnet. A malicious dapp on testnet can silently request this signature. The attacker then replays it on mainnet before the victim ever transacts there.

---

### Recommendation

Add `chain_id: u8` to `SignerCapabilityOfferProofChallengeV2` and populate it in `offer_signer_capability`:

```move
struct SignerCapabilityOfferProofChallengeV2 has copy, drop {
    chain_id: u8,          // add this field
    sequence_number: u64,
    source_address: address,
    recipient_address: address,
}

// In offer_signer_capability:
let proof_challenge = SignerCapabilityOfferProofChallengeV2 {
    chain_id: chain_id::get(),   // populate it
    sequence_number: get_sequence_number(source_address),
    source_address,
    recipient_address,
};
```

This mirrors the fix already applied to `RotationCapabilityOfferProofChallengeV2`. [6](#0-5)

### Proof of Concept

**Setup:** Alice has address `0xALICE` on both testnet (chain_id=2) and mainnet (chain_id=1). Her mainnet account has sequence number 0 (never used). Attacker Bob has address `0xBOB` on both chains.

**Step 1 — Capture signature on testnet:**
A malicious testnet dapp asks Alice to sign `offer_signer_capability` granting Bob a signer capability. Alice's testnet sequence number is also 0. The signed message is:

```
BCS(SignedMessage {
  type_info: {0x1, "account", "SignerCapabilityOfferProofChallengeV2"},
  inner: {sequence_number: 0, source_address: 0xALICE, recipient_address: 0xBOB}
})
```

No chain ID appears anywhere in this byte string.

**Step 2 — Replay on mainnet:**
Bob submits a mainnet transaction calling:
```
0x1::account::offer_signer_capability(
    alice_sig_from_testnet,
    ED25519_SCHEME,
    alice_pubkey,
    0xBOB
)
```
The on-chain verifier constructs the identical `SignerCapabilityOfferProofChallengeV2` (sequence_number=0, source_address=0xALICE, recipient_address=0xBOB), wraps it in the same `SignedMessage`, and the signature verifies successfully.

**Step 3 — Drain Alice's mainnet account:**
```
0x1::account::create_authorized_signer(bob_signer, 0xALICE)
// → returns signer for 0xALICE
0x1::aptos_account::transfer(alice_signer, 0xBOB, alice_balance)
``` [7](#0-6) [8](#0-7)

    public entry fun offer_signer_capability(
        account: &signer,
        signer_capability_sig_bytes: vector<u8>,
        account_scheme: u8,
        account_public_key_bytes: vector<u8>,
        recipient_address: address
    ) acquires Account {
        let source_address = signer::address_of(account);
        ensure_resource_exists(source_address);
        assert!(exists_at(recipient_address), error::not_found(EACCOUNT_DOES_NOT_EXIST));

        // Proof that this account intends to delegate its signer capability to another account.
        let proof_challenge = SignerCapabilityOfferProofChallengeV2 {
            sequence_number: get_sequence_number(source_address),
            source_address,
            recipient_address,
        };
        verify_signed_message(
            source_address, account_scheme, account_public_key_bytes, signer_capability_sig_bytes, proof_challenge);

        // Update the existing signer capability offer or put in a new signer capability offer for the recipient.
        let account_resource = &mut Account[source_address];
        account_resource.signer_capability_offer.for.swap_or_fill(recipient_address);
    }
```

    public fun create_authorized_signer(account: &signer, offerer_address: address): signer acquires Account {

        // Check if there's an existing signer capability offer from the offerer.
