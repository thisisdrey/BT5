### Title
Unauthenticated Signer Event Receiver Allows Forged Block-Validation and StackerDB Event Injection - (File: libsigner/src/events.rs)

### Summary
`SignerEventReceiver::next_event` (the HTTP server a `stacks-signer` process runs to receive pushed events from its paired `stacks-node`) performs no authentication whatsoever on incoming requests. It only checks the HTTP method and URL path before parsing and forwarding the body as a trusted `SignerEvent`. Node-side documentation (`docs/signing.md`, `sample/conf/mainnet-signer.toml`, `sample/conf/testnet-signer.toml`) describes a shared-secret mechanism (`connection_options.auth_token` on the node must match `auth_password` on the signer) as the intended access control for this channel, but no code path enforces it: the node's outbound event dispatcher (`stacks-node/src/event_dispatcher/worker.rs::make_http_request`) never attaches any `Authorization`/token header, and the signer's receiver never checks for one.

### Finding Description
`SignerEventReceiver::next_event` dispatches based purely on URL: [1](#0-0) 

For each recognized path it calls `process_event`, which reads the body, JSON-deserializes it into the expected event type, and converts it into a `SignerEvent` with no signature or credential check on the HTTP request itself: [2](#0-1) 

The `/proposal_response` and `/new_burn_block` paths deserialize directly into `BlockValidateResponse` / `BurnBlockEvent` and forward them as ground truth to the signer run loop — these payloads carry no cryptographic authentication of their own; they are trusted purely because they are assumed to originate from the paired node: [3](#0-2) 

On the sending side, `EventDispatcherWorker::make_http_request` builds and sends the HTTP POST but never attaches any authentication header (no use of `auth_token`/`auth_password` anywhere in the dispatch path): [4](#0-3) 

This confirms the equality the docs assume ("auth_token" client credential == "auth_password" server credential, enforced end-to-end") does not hold: the credential is configured but never transmitted or checked. Any party able to reach the signer's bound HTTP port (`endpoint` in the signer config, e.g. `0.0.0.0:30000` is used as an example bind address in some sample configs) can POST directly to `/proposal_response`, `/new_burn_block`, `/new_block`, or `/stackerdb_chunks` and have the payload accepted exactly as if it came from the legitimate paired node.

Note: for `/stackerdb_chunks`, subsequent processing in `TryFrom<StackerDBChunksEvent> for SignerEvent` (in the same file) does perform `chunk.recover_pk()` and downstream signer-message consumers (e.g. `stacks-node/src/nakamoto_node/stackerdb_listener.rs`) verify signatures against the *known* registered signer public key before acting — so forged StackerDB chunk contents alone cannot be used to fabricate a valid signer vote. However, `BlockValidateResponse` (block proposal validation result) and `BurnBlockEvent` carry no such signature-based gate at all; they are consumed by the signer purely on the basis of "this arrived on my event-receiver socket."

### Impact Explanation
An attacker who can reach the signer's event-receiver port (misconfigured to bind non-loopback, exposed via port-forwarding, container networking, or a compromised adjacent host) can inject a forged `BlockValidateResponse` claiming a block proposal was accepted/rejected without that block ever having been validated by the signer's actual paired node, or inject forged `BurnBlockEvent`/`StackerDBChunksEvent` data to desynchronize the signer's local view. This is an unauthenticated write into the signer's trusted event stream — the exact class of "auth-gate that fails open" called out in scope, since a documented and configured credential (`auth_token`/`auth_password`) is never actually enforced by the code.

### Likelihood Explanation
Exploitation requires only network reachability to the signer's bound HTTP port and no possession of any node secret or signer private key — a plain HTTP POST with a crafted JSON body is sufficient, since the receiver performs zero authentication on any of its non-`/status` routes.

### Recommendation
Implement and enforce the documented shared-secret check in `SignerEventReceiver`/`process_event` (e.g., verify an `Authorization` header against the configured `auth_password` before accepting the request), and have `EventDispatcherWorker::make_http_request` actually send the configured `auth_token` as that header. Until fixed, operators must bind the signer's event endpoint strictly to loopback/private-only interfaces as the sole mitigation.

### Proof of Concept
1. Start a `stacks-signer` process with its event receiver bound to a reachable address (per sample config, `endpoint = "0.0.0.0:30000"`).
2. From any remote host with network access to that port, send:
```
POST /proposal_response HTTP/1.1
Host: <signer-ip>:30000
Content-Type: application/json
Content-Length: <n>

{ ... crafted BlockValidateResponse JSON ... }
```
3. Because `next_event`/`process_event` never check any credential, the payload is deserialized and forwarded to the signer run loop as if it came from the legitimate paired node — confirmed by the absence of any auth check in `libsigner/src/events.rs:413-542` and the absence of any outgoing auth header in `stacks-node/src/event_dispatcher/worker.rs:325-356`.

**Uncertainty:** I could not fully verify whether some other layer (e.g., a reverse proxy, TLS client-cert check, or a middleware not indexed) is expected to sit in front of this endpoint in production deployments, nor whether `auth_token`/`auth_password` are consumed anywhere else in the codebase outside the indexed portions of `stackslib/src/config/mod.rs` and `stackslib/src/net/httpcore.rs` (which appear to gate the *node's* RPC endpoints, a different channel, not the signer's event receiver). Given index size limits, some file contents may not be available; a full-repo Devin session could confirm there is no additional auth wiring for this specific socket.

        self.with_server(|event_receiver, http_server, _is_mainnet| {
            // were we asked to terminate?
            if event_receiver.is_stopped() {
                return Err(EventError::Terminated);
            }
            debug!("Request handling");
            let request = http_server.recv()?;
            debug!("Got request"; "method" => %request.method(), "path" => request.url());

            if request.url() == "/status" {
                request
                .respond(HttpResponse::from_string("OK"))
                .expect("response failed");
                return Ok(SignerEvent::StatusCheck);
            }

            if request.method() != &HttpMethod::Post {
                return Err(EventError::MalformedRequest(format!(
                    "Unrecognized method '{}'",
                    request.method(),
                )));

fn process_event<T, E>(mut request: HttpRequest) -> Result<SignerEvent<T>, EventError>
where
    T: SignerEventTrait,
    E: serde::de::DeserializeOwned + TryInto<SignerEvent<T>, Error = EventError>,
{
    let mut body = String::new();

    if let Err(e) = request.as_reader().read_to_string(&mut body) {
        error!("Failed to read body: {:?}", &e);
        ack_dispatcher(request);
        return Err(EventError::MalformedRequest(format!(
            "Failed to read body: {:?}",
            e
        )));
    }
    // Regardless of whether we successfully deserialize, we should ack the dispatcher so they don't keep resending it
    ack_dispatcher(request);
    let json_event: E = serde_json::from_slice(body.as_bytes())
        .map_err(|e| EventError::Deserialize(format!("Could not decode body to JSON: {:?}", e)))?;

    let signer_event: SignerEvent<T> = json_event.try_into()?;

    Ok(signer_event)
}
