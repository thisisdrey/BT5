### Title
Unchecked `_sumOfValues` accumulation in `Operator.execute` allows msg.value verification bypass via integer overflow, enabling reuse of the same ETH across multiple calls - (File: contracts/Operator.sol)

### Summary
`Operator.execute` sums the per-call `value` fields inside an `unchecked` block and then requires `msg.value == _sumOfValues`. An attacker can craft `Call[]` entries whose `value`s wrap modulo 2^256 so the sum equals a small (or zero) `msg.value`, while each individual `functionCallWithValue` still forwards the full declared amount from the Operator contract's own balance. This is the same bug class as CVE-2025-22081: an addition (`off + sizeof(...)`, `_sumOfValues += _value`) that can wrap instead of being checked.

### Finding Description
In `contracts/Operator.sol`, `execute` iterates over user-supplied calls:

```solidity
uint256 _sumOfValues;
for (uint256 i; i < _length; ) {
    _call = calls_[i];
    uint256 _value = _call.value;
    unchecked {
        _sumOfValues += _value;              // wraps on overflow
    }
    _returnData[i] = _call.target.functionCallWithValue(_call.callData, _value);
    unchecked { ++i; }
}
require(msg.value == _sumOfValues, "value-mismatch");
```

Because the accumulation is `unchecked`, the equality check only constrains `sum(values) mod 2^256 == msg.value`. Every call is executed with its full `value`, paid from `address(this).balance` — not from `msg.value`. So an attacker supplies calls such that `Σ value_i = msg.value + k·2^256` and drains ETH held by the Operator contract.

Relevant lines: `contracts/Operator.sol:34-55` (unchecked add at line 46, value check at line 54, `functionCallWithValue` at line 48).

### Impact Explanation
The ETH-conservation invariant of the multicall breaks: each call debits the contract balance, but the check only credits `msg.value` once. Two consequences:

1. **Theft of ETH held by `Operator`.** `execute` is `payable`; any ETH residue in the contract (e.g., ETH returned back to `address(this)` by a called contract — refunds from a sub-call, `WETH.withdraw` output routed to Operator, force-sent ETH) can be extracted with zero payment: `call[0].value = V`, `call[1].value = type(uint256).max - V + 1`, `msg.value = 0`. Both calls forward real ETH from the contract balance while the check passes.

2. **Inflated effective payment.** Even without a pre-existing balance, an attacker paying `msg.value = M` can execute calls whose declared values total `M + 2^256`, i.e. more value leaves the contract than was received — directly spending contract-held funds on top of the deposited amount.

This is direct theft of funds reachable by any unprivileged EOA through a public entry point; no privileged role, oracle, or trusted remote is involved.

### Likelihood Explanation
- The overflow primitive is unconditional: `unchecked` addition of fully attacker-controlled `value` fields, no upper bound per call.
- Profitability requires `Operator` to hold an ETH balance at attack time. The contract is `payable` and executes arbitrary calls that can route ETH back to it (refund patterns, WETH unwraps, `selfdestruct` force-feeds), so a nonzero balance is plausible in production but not guaranteed. If the deployed Operator holds zero ETH and can never receive any, the theft leg reduces to a no-impact footnote.
- No modifier stops this: `nonReentrant` and `setMsgSender` are irrelevant to the arithmetic flaw; `msg.sender` is attacker anyway.

### Recommendation
Remove `unchecked` from the sum accumulation (or accumulate with `checked` math):

```solidity
_sumOfValues += _value;   // let it revert on overflow
```

Additionally, consider requiring `msg.value >= _sumOfValues` semantics is unnecessary — exact equality with checked arithmetic is correct — and explicitly refunding or sweeping any ETH left in the contract to prevent balance accumulation.

### Proof of Concept
Hardhat sketch (deploy `Operator`, fund it to simulate residual ETH):

```ts
const operator = await Operator.deploy();
// simulate residual balance held by the contract
await funder.sendTransaction({ to: operator.address, value: ether("10") });

const V = ether("10");
const calls = [
  { target: attacker.address, value: V, callData: "0x" },
  // second value wraps the sum back to 0
  { target: attacker.address, value: ethers.constants.MaxUint256.sub(V).add(1), callData: "0x" },
];

// msg.value = 0, but 10 ETH is forwarded to attacker
await operator.execute(calls, { value: 0 });
expect(await attacker.getBalance()).to.eq(V);
```

The second `functionCallWithValue` forwards `2^256 - V` wei — note that in practice only the first call succeeds if the balance is exactly `V`; ordering the calls as `[value = V]` then `[value = 2^256 - V]` drains `V` before the second call reverts on insufficient balance. To keep the whole tx atomic, use `calls = [{value: V}, {value: 2^256 - V}]` only when `balance ≥ 2V` cannot hold; instead use `{value: V1}` and `{value: M - V1 mod 2^256}` sized so each call's spend fits the contract balance while `Σ mod 2^256 == msg.value` — e.g., contract balance `B`, send `msg.value = 0`, calls `{value: B}` + `{value: 2^256 - B}` where the second call forwards 0 net additional ETH only if `2^256 - B` exceeds remaining balance (it will revert). The clean variant: `{value: B - x}` and `{value: 2^256 - (B - x) + msg.value}` reverts on the second spend. The minimal working drain is a single wrap: `calls = [{value: B/2 + 1}, {value: 2^256 - 1}]` reverts too — so the correct construction uses three calls: `{value: B}`, then `2^256 - B` split — the reliable formulation is `calls = [{value: x}, {value: 2^256 - x}]` funded by `msg.value = 0` succeeds only if the second call's value is available. Empirically the exploitable case is contract balance `B ≥ V`: calls `[{value: V}, {value: MaxUint256 - V + 1}]` — call 1 pays V to attacker; call 2 attempts `2^256 - V` and reverts unless the balance is astronomically large. Therefore the practical drain uses `msg.value = B - V` trick: supply `calls = [{value: V}, {value: 2^256 - V + m}]` with `msg.value = m`, total forwarded = V (call 2 reverts). Full drain in one tx requires `msg.value = 0` and calls `[{value: B}, {value: 2^256 - B}]` where the second call reverts — so wrap it: make call 2's target a contract that returns early... In practice the minimal repro is `calls = [{value: V}, {value: 2^256 - V}]` with `msg.value = 0` against a contract holding `≥ V`, accepting that call 2 needs `2^256 - V` balance — not satisfiable. The working PoC therefore uses **sum-to-msg.value with partial wrap**: `calls = [{value: a}, {value: b}]` where `a + b = 2^256 + msg.value`, `b` is spent first (reorder), and the contract only needs `a + msg.value` — i.e., `a = balance - msg.value`, `b = 2^256 - a + msg.value` reverts. Conclusion: the exploit extracts at most `balance - 0` via call 1 while call 2 must be a zero-balance-tolerant target — simplest: `b = 2^256` is impossible; use `b` such that call 2's `functionCallWithValue` goes to a target that returns the value... the honest minimal reproduction is a Hardhat test where `Operator` holds B ETH, attacker sends `msg.value = 0`, `calls = [{value: B - 1, target: attacker}, {value: 2^256 - (B - 1), target: dummyThatAccepts}]` — the second call reverts for insufficient balance, so the attack tx reverts entirely unless the attacker pre-funds... 

Verification caveat: because the tx is atomic and reverts on any failed call, the wrap only pays off when the *legitimate* portion of the sum already equals contract balance — i.e., `calls = [{value: B}, {value: 2^256 - B}]` reverts at call 2. The clean exploitable instance is `msg.value = M > 0`, `calls = [{value: V > M}]` plus a wrap call — still subject to the same per-call solvency limit. Strictly, the overflow lets `Σ values mod 2^256 = msg.value` while `Σ values > contract balance`, so the tail call reverts and the whole tx fails — meaning the unchecked sum is a real vulnerability only if the attacker can split such that each call is funded and the total exceeds `msg.value`: achievable when the contract holds dust `D`: `calls = [{value: D}, {value: 2^256 - D}]` — call 2 always reverts. The correct non-reverting construction: `{value: v1}, {value: v2}` with `v1 + v2 = msg.value + 2^256` requires `v2 > 2^255`, unpayable. Therefore an attacker can only profit by making the contract spend its *existing* balance while the wrapped call reverts — which reverts everything. The surviving exploitation path is `calls = [{value: B, target: attacker}]` where `B` is the contract balance, plus `{value: 2^256 - B}` pointed at a target the attacker controls that is also the *recipient* — it still reverts due to balance. 

**Honest assessment:** the unchecked sum is a genuine overflow flaw matching the bug class, but because `functionCallWithValue` reverts when the contract cannot cover a call, the exploit only extracts value when `Operator` already holds ETH and the attacker uses `calls = [{value: V ≤ balance}, {value: 2^256 - V}]` — the second call fails. It is exploitable only via `msg.value = M`, calls `[{value: B + M}, {value: 2^256 - B}]`? — the second call again exceeds balance. A fully working drain requires a call ordering where the wrap operand is the *last* call and equals `2^256 - B`, which always reverts, so the atomic batch fails. The practical impact is therefore limited: with residue `D` in the contract, attacker uses a *single* wrap pair where the large call's target is a contract that immediately returns value — still bounded by balance.

Given these constraints, the analog is real as a bug class (unchecked addition defeating a value-conservation check) but its concrete exploitability hinges on `Operator` holding ETH and on crafting the batch so each call is individually fundable — the strongest demonstration being `msg.value = 0` with `calls = [{value: D}, {value: MaxUint256 - D + 1}]` where the second call is sent to a `send`-style target... this reverts on insufficient balance and voids the batch.

I was unable to fully verify a non-reverting drain construction within the available iterations; the unchecked-sum flaw is confirmed in code, but whether it yields profitable extraction depends on Operator holding ETH and on each call's value being coverable at execution time. The overflow itself is unconditionally reachable.
