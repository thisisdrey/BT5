### Title
Unthrottled Ed25519 verify+sign amplification via unsolicited repair-response `Ping` packets - ([File: core/src/repair/serve_repair.rs])

### Summary
`ServeRepair::handle_repair_response_pings`, called from `ShredFetchStage::modify_packets` for every packet batch received on the repair socket, performs an Ed25519 signature verification and then an Ed25519 signing operation (plus a UDP send) for **any** packet that merely matches the fixed `RepairResponse::Ping` wire size and deserializes into a self-consistent `Ping`. Because `Ping` is self-signed by an attacker-chosen keypair embedded in the packet itself, and because this function performs no "is this ping actually expected/outstanding" correlation check (unlike the analogous `block_id_repair_service::process_block_id_repair_ping_response`), any unstaked remote party can forge unlimited valid `Ping` packets at zero cost and force the validator to burn CPU on crypto operations and issue signed UDP responses with no rate limiting specific to this code path.

### Finding Description
`ShredFetchStage::modify_packets` (`core/src/shred_fetch_stage.rs:72-80`) unconditionally calls `ServeRepair::handle_repair_response_pings` on every packet batch arriving on the repair socket, before any nonce verification or other filtering: [1](#0-0) 

`handle_repair_response_pings` (`core/src/repair/serve_repair.rs:1888-1934`) does the following per packet:
1. Cheap size check against `REPAIR_RESPONSE_SERIALIZED_PING_BYTES` (a public, fixed constant).
2. `wincode::deserialize` into `RepairResponse::Ping(Ping)`.
3. `ping.verify()` — an Ed25519 signature verification.
4. On success: `Pong::new(&ping, keypair)` — an Ed25519 **signing** operation using the validator's real identity keypair — then serialize and queue for `batch_send` on the repair socket. [2](#0-1) 

Critically, `Ping<N>` is self-signed by whatever keypair the sender chooses: [3](#0-2) 

`ping.verify()` only checks that the embedded signature matches the embedded `from` pubkey over the embedded token — it proves nothing about the sender's identity, stake, or that this validator ever issued a corresponding repair request expecting a ping challenge from that address/pubkey. An attacker can generate a fresh, free Ed25519 keypair locally, sign an arbitrary 8-byte token, wrap it in `RepairResponse::Ping`, and send it to the validator's public repair-socket address (learned from gossip `ContactInfo`, no stake required).

This is unlike the sibling code path `block_id_repair_service::process_block_id_repair_ping_response`, which explicitly gates the verify+sign+send behind `state.is_expected_ping_response(sender, addr)`: [4](#0-3) 

`handle_repair_response_pings` has no such "was this ping expected" check, no ping cache, and no `TokenBucket`/`data_budget` throttle (that mechanism only exists in `handle_requests`, which handles inbound *repair requests*, not repair-*response* pings processed in the shred-fetch path). The only gate is the fixed-size match, which an attacker trivially satisfies.

Because `modify_packets` runs as a single dedicated thread (`solTvuRepPktMod`) per repair-socket, and does the ping verify/sign work synchronously before any downstream channel backpressure (`sendr.try_send`) is even reached, an attacker flooding correctly-sized forged `Ping` packets can keep that thread continuously performing Ed25519 verify+sign+serialize+socket-send work, at a cost the attacker pays effectively nothing for (a handful of bytes of UDP traffic, no stake, no fee).

### Impact Explanation
This is a compute/signature-generation amplification / QoS-evasion issue: an unstaked, unauthenticated sender can force the validator's repair-ingress thread to perform Ed25519 verify + Ed25519 sign (using the validator's own identity key) + serialize + `sendmmsg` for every forged packet, with no rate limit, deduplication, or "was this expected" check gating that specific code path. This matches the "grossly underpriced pre-fee work" / signature-generation amplification category: the attacker's cost (raw UDP bytes) is far below the validator's cost (two Ed25519 crypto operations plus a socket write per packet), and the validator's own signing key is invoked on attacker-controlled cadence. Sustained flooding can starve legitimate repair-response processing on that single-threaded pipeline, delaying real shred repair.

### Likelihood Explanation
- No privileged access, stake, or leader status is required — only knowledge of the validator's repair socket address, which is publicly advertised via gossip `ContactInfo`.
- Crafting a valid packet requires only generating a local Ed25519 keypair and calling `Ping::new`, then serializing it via the identical wincode format used by `packet_from_data(Some(from_addr), RepairResponse::Ping(ping))` — fully within attacker capability and reproducible offline.
- No existing check (size match aside) restricts this; the size-based dispatch is a public constant.
- Repeatable indefinitely, at line rate, since no per-packet or per-sender budget is consumed by this code path.

### Recommendation
Add a correlation/expectation check before performing `ping.verify()`/`Pong::new()` in `handle_repair_response_pings`, mirroring `block_id_repair_service::process_block_id_repair_ping_response`'s `is_expected_ping_response` gate (i.e., only respond to a Ping challenge from an address/sender this node actually has an outstanding repair request to). Additionally, apply a rate limit / token bucket (as already used in `handle_requests`) to bound total ping-verify/sign work performed per unit time regardless of incoming packet volume, and consider per-source-IP throttling for the repair socket ping path.

#[test]
fn test_handle_repair_response_pings_unbounded_signing_cost() {
    use {
        solana_gossip::ping_pong::Ping,
        std::{net::UdpSocket, time::Instant},
    };

    let identity_keypair = Keypair::new();
    let repair_socket = UdpSocket::bind("127.0.0.1:0").unwrap();
    let mut stats = ShredFetchStats::default();

    // Attacker generates N distinct, self-signed Ping packets with fresh
    // throwaway keypairs -- zero relationship to any repair request this
    // node ever issued.
    const N: usize = 100_000;
    let mut packets = Vec::with_capacity(N);
    for _ in 0..N {
        let attacker_keypair = Keypair::new();
        let ping = Ping::new(rand::random(), &attacker_keypair);
        let response = RepairResponse::Ping(ping);
        packets.push(packet_from_data(None, response).unwrap());
    }
    let mut batch: PacketBatch = RecycledPacketBatch::new(packets).into();

    let start = Instant::now();
    ServeRepair::handle_repair_response_pings(
        &repair_socket,
        &identity_keypair,
        &mut batch,
        &mut stats,
    );
    let elapsed = start.elapsed();

    // Every forged, unsolicited ping is verified AND answered with a freshly
    // signed Pong -- there is no "was this expected" gate and no rate limit.
    assert_eq!(stats.ping_count, N);

    // Assert (for CI/fuzz invariant) that per-packet cost is bounded and that
    // this scales linearly with attacker-controlled N with no throttling,
    // demonstrating the invariant "work spent per packet before a fee is
    // collected is bounded" is violated: cost is proportional to attacker
    // send rate, not to any node-issued repair request count.
    println!("Processed {N} unsolicited signed pongs in {elapsed:?}");
}

    pub(crate) fn handle_repair_response_pings(
        repair_socket: &UdpSocket,
        keypair: &Keypair,
        packet_batch: &mut PacketBatch,
        stats: &mut ShredFetchStats,
    ) {
        let mut pending_pongs = Vec::default();
        for mut packet in packet_batch.iter_mut() {
            if packet.meta().size != REPAIR_RESPONSE_SERIALIZED_PING_BYTES {
                continue;
            }
            if let Some(data) = packet.data(..)
                && let Ok(RepairResponse::Ping(ping)) = wincode::deserialize(data)
            {
                if !ping.verify() {
                    // Do _not_ set `discard` to allow shred processing to attempt to
                    // handle the packet.
                    // Ping error count may include false posities for shreds of size
                    // `REPAIR_RESPONSE_SERIALIZED_PING_BYTES` whose first 4 bytes
                    // match `RepairResponse` discriminator (these 4 bytes overlap
                    // with the shred signature field).
                    stats.ping_err_verify_count += 1;
                    continue;
                }
                packet.meta_mut().set_discard(true);
                stats.ping_count += 1;
                let pong = RepairProtocol::Pong(Pong::new(&ping, keypair));
                if let Ok(pong) = wincode::serialize(&pong) {
                    let from_addr = packet.meta().socket_addr();
                    pending_pongs.push((pong, from_addr));
                }
            }
        }
        if !pending_pongs.is_empty() {
            let num_pkts = pending_pongs.len();
            let pending_pongs = pending_pongs.iter().map(|(bytes, addr)| (bytes, addr));
            match batch_send(repair_socket, pending_pongs) {
                Ok(()) => (),
                Err(SendPktsError::IoError(err, num_failed)) => {
                    warn!(
                        "batch_send failed to send {num_failed}/{num_pkts} packets. First error: \
                         {err:?}"
                    );
                }
            }
        }
    }
