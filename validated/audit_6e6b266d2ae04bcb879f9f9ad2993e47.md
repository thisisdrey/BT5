### Title
Infinite loop in AIX big-archive member walk on malformed `Arnxtmem`/`Fllstmoff` fields - ([File: src/internal/xcoff/ar.go])

### Summary
`xcoff.NewArchive` walks an AIX "big archive" member list by trusting the `Arnxtmem` field of each member header as the offset of the next member, terminating only when the current offset equals the file header's `Fllstmoff` value. A crafted archive whose `Arnxtmem` chain never reaches `Fllstmoff` (e.g., it cycles back to an earlier, already-visited offset) causes the loop to run forever, growing `arch.Members` without bound and never returning to the caller — the same "record-size/offset not validated -> unbounded parser loop" primitive as the NetScaler capture-file bug in Wireshark.

### Finding Description
Attacker input is an AIX big-archive file (`<bigaf>` magic) supplied as an object/archive dependency. The entry point is `xcoff.NewArchive` (`src/internal/xcoff/ar.go:103`), reached in practice via `go/internal/gccgoimporter.aixBigArExportData` (`src/go/internal/gccgoimporter/ar.go:131-136`), which itself is called from `arExportData` when the gccgo importer encounters the `armagb` magic while resolving export data for a package built with gccgo — i.e., ordinary consumption of a package/archive during a build/import workflow, not a privileged or malicious-server scenario.

Inside `NewArchive`, the member-reading loop (`src/internal/xcoff/ar.go:149-211`) does:
```go
for {
    ... read member header at off ...
    if off == lastoff {
        break
    }
    off, err = parseDecimalBytes(mhdr.Arnxtmem[:])
    ...
}
```
`off` is taken directly from the untrusted `Arnxtmem` field with no check that it strictly progresses toward `lastoff`, no visited-offset tracking, and no bound on the number of iterations. If `Arnxtmem` points back to a previously visited offset (or to `off` itself) rather than eventually equaling `lastoff`, the loop never terminates, repeatedly re-reading headers and appending to `arch.Members` (`src/internal/xcoff/ar.go:163-164`) forever. This mirrors the NetScaler analog: a malformed record whose declared "next offset/size" field is never validated against progress, producing a parser infinite loop.

### Impact Explanation
An attacker-supplied archive can cause a Go process that imports gccgo export data (or any future/other consumer of `internal/xcoff.NewArchive`) to hang indefinitely and consume unbounded memory, denying service to a victim's build/analysis workflow. Per Go's security triage, an unbounded-memory/generic resource-exhaustion issue alone is explicitly out of scope, but this is a genuine parser infinite loop (non-terminating control flow) rather than plain large-input exhaustion, which the rules note "can qualify." However, because `internal/xcoff` is an internal package with a narrow, largely build-tooling-only reachability path (gccgo export-data import), and the attack requires the victim to specifically import a gccgo-produced archive, this would likely be assessed as a low-priority/PUBLIC-track hardening issue rather than urgent.

### Likelihood Explanation
Requires a victim to run a workflow that parses an AIX big archive via `go/internal/gccgoimporter` (i.e., using the gccgo import path) or any other future caller of `internal/xcoff.NewArchive`, and to be given a maliciously crafted `.a` file as a dependency/import source — a plausible but narrow scenario limited to AIX/gccgo interoperability tooling.

### Recommendation
In `src/internal/xcoff/ar.go`, validate that each parsed `off` (from `Arnxtmem`) is greater than the previous offset (or otherwise strictly progresses) and bound the loop by tracking visited offsets / a maximum iteration count derived from file size; return an error (e.g., wrapping `ErrHeader`-style) if the chain does not monotonically progress toward `lastoff` within the file bounds.

### Proof of Concept
```go
package xcoff

import (
    "bytes"
    "encoding/binary"
    "testing"
)

// TestNewArchiveInfiniteLoop constructs a minimal AIX big archive whose
// first member's Arnxtmem points back to itself instead of progressing
// toward Fllstmoff, which should be rejected rather than looping forever.
func TestNewArchiveInfiniteLoop(t *testing.T) {
    var buf bytes.Buffer
    buf.WriteString(AIAMAGBIG) // "<bigaf>\n"

    var fhdr bigarFileHeader
    copy(fhdr.Flfstmoff[:], []byte("128                 ")) // first member offset
    copy(fhdr.Fllstmoff[:], []byte("999                 ")) // never reached
    binary.Write(&buf, binary.BigEndian, &fhdr)

    buf.Write(make([]byte, 128-buf.Len())) // pad to member offset 128

    var mhdr bigarMemberHeader
    copy(mhdr.Arsize[:], []byte("0                   "))
    copy(mhdr.Arnxtmem[:], []byte("128                 ")) // points to itself, never == lastoff
    copy(mhdr.Arnamlen[:], []byte("0   "))
    binary.Write(&buf, binary.BigEndian, &mhdr)
    buf.WriteString(AIAFMAG)

    done := make(chan error, 1)
    go func() {
        _, err := NewArchive(bytes.NewReader(buf.Bytes()))
        done <- err
    }()

    select {
    case <-done:
        // Expected: NewArchive should return an error for a malformed
        // member chain instead of looping.
    case <-time.After(2 * time.Second):
        t.Fatal("NewArchive hung: malformed Arnxtmem chain caused an infinite loop")
    }
}
```
Expected assertion: `NewArchive` should return promptly with an error describing an invalid/non-progressing member chain; currently it hangs, demonstrating the unvalidated-offset infinite-loop primitive analogous to ALPINE-CVE-2017-6474.
