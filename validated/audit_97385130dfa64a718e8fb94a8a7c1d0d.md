### Title
Attacker can grief a victim's `depositTokensOfAccount` set via dust transfers, DoSing the victim's deposits and incoming token receipts - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
The Netty bug class is "unbounded buffering with no length cap → resource-exhaustion DoS." The Metronome analog is the per-account token lists in `Pool`: every time a `DepositToken` balance of an address goes from `0` to `>0` (including via a plain `transfer` of dust), the token is appended to `depositTokensOfAccount[account]` (`Pool.addToDepositTokensOfAccount`). Once `debtTokensOfAccount + depositTokensOfAccount` reaches `MAX_TOKENS_PER_USER = 30`, the add reverts with `UserReachedMaxTokens`, which makes any subsequent deposit or receipt of a *new* deposit token revert for that account.

### Finding Description
- `DepositToken._transfer` calls `pool.addToDepositTokensOfAccount(recipient_)` whenever the recipient's balance was zero and `amount_ > 0` (`contracts/DepositToken.sol:517-520`).
- `Pool.addToDepositTokensOfAccount` is gated only by `onlyIfAdditionWillNotReachMaxTokens`, which reverts once the combined count hits `30` (`contracts/Pool.sol:143-148`, `216-220`).
- `_mint` (deposit path) has the same hook (`contracts/DepositToken.sol:485-488`), so `Pool.deposit` → `DepositToken.deposit` → `_mint` reverts for the victim once their list is full.
- `seize` uses `_transfer` too (`contracts/DepositToken.sol:343-345`), so a liquidator whose own list is full cannot receive seized collateral in a token they don't already hold — though a rational liquidator just keeps their list clean, so this mainly affects victims receiving tokens.

Attack steps (unprivileged EOA only):
1. Attacker deposits a dust amount of every deposit token in the pool to obtain 1 wei of each `msdTOKEN`.
2. Attacker calls `DepositToken.transfer(victim, 1)` for each token until `depositTokensOfAccount[victim]` reaches 30 entries (combined with any debt tokens the victim already has).
3. Every subsequent `Pool.deposit`/`NativeTokenGateway.deposit`/`VesperGateway.deposit` by the victim into a token they don't already hold reverts with `UserReachedMaxTokens`, as does any transfer of a new deposit token to the victim.

### Impact Explanation
Temporary freezing of funds / griefing: the victim cannot deposit collateral into the pool (blocking new positions, and blocking adding collateral to rescue a position approaching liquidation) and cannot receive any new deposit token. The victim can recover by transferring the dust balances back out — entries are removed when a balance returns to zero (`DepositToken.sol:522-525`), and dust is unlocked when the victim has no debt — so the freeze is temporary and costs the victim gas to clean up. If the victim has outstanding debt, `_revertIfLocked` may prevent them from removing dust, extending the DoS while debt exists, though paying down debt restores the ability to clean the list.

### Likelihood Explanation
Feasibility depends on the deployed pool having enough registered deposit tokens to approach the 30-entry cap; debt-token entries cannot be forced on a victim because `DebtToken.issue` is restricted to the borrowing flow of the account itself. Each dust transfer costs the attacker only gas plus a 1-wei balance, so the attack is cheap but reversible by the victim. No modifier, guard, or pause flag prevents a `transfer` from triggering `addToDepositTokensOfAccount`.

### Recommendation
Only add a token to `depositTokensOfAccount` on mint (deposit) rather than on arbitrary `_transfer`, or track "registered" tokens separately from raw balances — e.g., set a minimum meaningful amount, or make `seize`/liquidation and deposit accounting independent of the transferable ERC20 list. Alternatively, allow `removeFromDepositTokensOfAccount` to be triggered by the account itself to self-clean the list.
