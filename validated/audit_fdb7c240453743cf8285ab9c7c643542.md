Both the actuator path (`WithdrawBalanceActuator`) and the HTTP API path (`GetRewardServlet` via `Wallet`) reach `MortgageService.queryReward`/`withdrawReward`, which for cycles before `NEW_REWARD_ALGORITHM_EFFECTIVE_CYCLE` fall back to `computeReward(long cycle, List<Pair<byte[], Long>> votes)`, a `double`-based proportional split that truncates on every cycle iteration — the same rounding-down bug class as the reported cvg issue.

### Title
Per-cycle double-precision truncation in legacy vote-reward computation causes cumulative staking reward loss - ([File: chainbase/src/main/java/org/tron/core/service/MortgageService.java])

### Summary
`MortgageService.computeReward(long cycle, List<Pair<byte[], Long>> votes)` computes a voter's share of a super representative's cycle reward using floating-point division and multiplication, then adds the result to a `long` accumulator, truncating any fractional token amount every single cycle. This is functionally identical to the reported precision-loss pattern (`amount * numerator / denominator` truncation), except it repeats the truncation once per cycle instead of once per claim, compounding the loss.

### Finding Description
`computeReward(long cycle, List<Pair<byte[], Long>> votes)` computes, for each vote: [1](#0-0) 

```
double voteRate = (double) userVote / totalVote;
reward += voteRate * totalReward;
```
Because `reward` is a `long`, each `voteRate * totalReward` (a `double`) is truncated toward zero when accumulated. This function is only invoked for cycles prior to `newRewardAlgorithmEffectiveCycle` via `getOldReward`, which loops per cycle and re-truncates on every iteration: [2](#0-1) 

This is reachable end-to-end:
- `computeReward(long beginCycle, long endCycle, AccountCapsule accountCapsule)` dispatches to the old algorithm for cycles below the effective-cycle threshold: [3](#0-2) 
- `withdrawReward(byte[] address)` and `queryReward(byte[] address)` call this path and are invoked from `WithdrawBalanceActuator.execute`, a normal broadcastable `WithdrawBalanceContract` transaction any staked/voting account can send: [4](#0-3) 
- The same `queryReward` is also exposed unauthenticated over HTTP via `GetRewardServlet.doGet`: [5](#0-4) 

Notably, java-tron's own developers recognized this exact truncation problem and replaced it for post-effective-cycle rewards with a fixed-point `BigInteger` VI (value-index) accumulator scaled by `DECIMAL_OF_VI_REWARD = 10^18` specifically to avoid rounding loss: [6](#0-5) [7](#0-6) . The legacy `double`-based `computeReward(long cycle, ...)` path, however, was left unpatched and remains reachable for any cycle prior to that migration point.

### Impact Explanation
Every voter whose reward is computed via the legacy path loses a small, non-refundable fraction of TRX reward on every cycle where `userVote/totalVote` does not divide evenly — which, given `totalVote` is typically an enormous aggregate vote count, is nearly always. Because the loop in `getOldReward` re-applies this truncation once per cycle rather than once per withdrawal, the loss compounds across the number of unclaimed cycles, unlike the single-claim truncation described in the original report. This is a direct, permanent loss of legitimately earned staking rewards for any voting account, matching the "unbacked balance / permanent freezing (loss) of funds" impact class.

### Likelihood Explanation
Likelihood is high for any account with unwithdrawn votes/rewards accrued before `NEW_REWARD_ALGORITHM_EFFECTIVE_CYCLE`: simply calling `WithdrawBalanceContract` (a standard, permissionless transaction type) or querying `/wallet/getReward` triggers the vulnerable computation with no special privilege required.

### Recommendation
Replace the `double`-based proportional calculation in `computeReward(long cycle, List<Pair<byte[], Long>> votes)` with the same `BigInteger`-scaled fixed-point approach already used by the VI-based algorithm (`DECIMAL_OF_VI_REWARD` scaling with `BigInteger.multiply`/`divide`), or otherwise carry forward truncated remainders across cycles so fractional rewards are not silently dropped.

### Proof of Concept
1. Set up a witness with `totalVote = 100000026` (or any value that does not evenly divide the reward) and `totalReward` at cycle `N` (pre-new-algorithm cycle), as in the existing test setup at [8](#0-7) .
2. Have a voter with `userVote` such that `userVote * totalReward` is not an exact multiple of `totalVote` (e.g., `userVote = 10000000`).
3. Call `MortgageService.queryReward(address)` (or send `WithdrawBalanceContract`/hit `GET /wallet/getReward`) and observe the returned reward is `floor(voteRate * totalReward)` per cycle — strictly less than the exact rational amount `userVote * totalReward / totalVote`, with the shortfall growing linearly with the number of unclaimed cycles.

      }

  public void accumulateWitnessVi(long cycle, byte[] address, long voteCount) {
    BigInteger preVi = getWitnessVi(cycle - 1, address);
    long reward = getReward(cycle, address);
    if (reward == 0 || voteCount == 0) { // Just forward pre vi
      if (!BigInteger.ZERO.equals(preVi)) { // Zero vi will not be record
        setWitnessVi(cycle, address, preVi);
      }
    } else { // Accumulate delta vi
      BigInteger deltaVi = BigInteger.valueOf(reward)
          .multiply(DECIMAL_OF_VI_REWARD)
          .divide(BigInteger.valueOf(voteCount));
      setWitnessVi(cycle, address, preVi.add(deltaVi));
    }
  }
