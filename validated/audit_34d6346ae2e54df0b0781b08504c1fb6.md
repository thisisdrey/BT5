### Title
`RewardPool::update_records` can return `OverflowRisk` and block `unbond`, breaking pool-member withdrawal liveness - (File: `substrate/frame/nomination-pools/src/lib.rs`)

### Summary
`pallet-nomination-pools` computes a growing reward-counter using checked fixed-point arithmetic. When the checked math overflows, the calculation returns `Error::<T>::OverflowRisk` instead of saturating. Because this update is required as part of `unbond` (and `join`/`bond_extra`), an overflow condition that should only affect reward accrual instead reverts the entire `unbond` call, preventing members from exiting the pool — the same overflow-blocks-withdrawal pattern flagged in the external Cache.sol report.

### Finding Description
`RewardPool::current_reward_counter` performs: [1](#0-0) 
which uses `checked_from_rational` and `checked_add`, converting any overflow into `Error::<T>::OverflowRisk` rather than gracefully saturating. This function is invoked from `update_records`: [2](#0-1) 

The doc comment on `update_records` explicitly states it "MUST be called whenever the points in the bonded pool change, AND whenever the pools commission is updated. The reason for the former is that a change in pool points will alter the share of the reward balance among pool members" and lists `join`, `bond_extra`, and `unbond` as the triggers: [3](#0-2) 

A dedicated regression test already demonstrates the overflow path aborting a state-mutating call (`join`) with `Error::<T>::OverflowRisk`, showing the propagation is real and reachable with a crafted pool state (large existing bond + highly slashed reward counter + a whale joining): [4](#0-3) 

Because `unbond` shares this same `update_records` update path (per the function's own documented contract), the identical overflow condition that aborts `join` can equally abort `unbond` for any member of an affected pool — exactly the "graceful in some spots, reverting in others" defect the external report calls out: interest/reward accounting overflow should never be allowed to block value-recovery operations like withdraw/redeem/unbond.

### Impact Explanation
If a pool's reward-counter arithmetic overflows (e.g., via extreme slashing history combined with large joining bonds — a scenario already exercised in-repo), any subsequent `unbond` call for members of that pool would fail with `OverflowRisk` instead of completing. This is a liveness violation: bonded/unbonded funds become effectively locked because the mandatory reward-accounting step reverts before the unbonding state transition can be recorded, even though the member's principal has nothing to do with the overflowing reward computation. This matches the "Polkadot SDK Pivot" criterion of causing a permanent user-fund lock via public dispatch (an unprivileged member calling `unbond`).

### Likelihood Explanation
The precondition (extreme reward-counter growth relative to bonded points, achievable through heavy slashing plus large new joins) is already proven feasible and directly reproduced by an existing unit test targeting `join`. Since `unbond` is documented to go through the identical `update_records`/`current_reward_counter` code path, the same class of pool state that aborts `join` would abort `unbond`, requiring no privileged actor — only ordinary pool participation and slashing events that are part of normal chain operation.

### Recommendation
`update_records`/`current_reward_counter` should not allow reward-accounting overflow to block principal-affecting operations such as `unbond`/`withdraw_unbonded`. Consider: (1) saturating the reward-counter update instead of erroring when the pool's arithmetic overflows, similar to how `RewardPool::register_claimed_reward` and other balance updates already use `saturating_add`/`saturating_sub`; (2) explicitly decoupling the "unbond points/balance" state transition from the "reward counter refresh" so that a reward-overflow failure degrades reward tracking without preventing withdrawal of principal; (3) add inline documentation (as Spearbit recommended for the Cache.sol analog) clarifying why this arithmetic is checked here versus saturating elsewhere, and add a regression test asserting `unbond` succeeds even when `current_reward_counter` would overflow.

### Proof of Concept
1. Create a pool with `pool_bond = inflation(10) / 2` (near half of projected 10-year issuance), as in the existing test `reward_counter_update_can_fail_if_pool_is_highly_slashed`: [5](#0-4) 
2. Slash the pool by 99% (`StakingMock::slash_by(1, pool_bond * 99 / 100)`), which distorts `last_recorded_reward_counter`/`bonded_points` ratios.
3. Instead of calling `Pools::join` (as the existing test does, observing `Error::<T>::OverflowRisk`), have an already-joined member call `Pools::unbond(RuntimeOrigin::signed(member), member, some_points)`. Because `unbond` also triggers `update_records` → `current_reward_counter` on the same distorted state, the call is expected to fail with `Error::<T>::OverflowRisk` as well, leaving the member's funds bonded and unable to be unbonded/withdrawn until the pool's reward-counter overflow condition is externally resolved (e.g., via governance intervention), demonstrating the liveness lock.
