Audit Report

## Title
Attacker-controlled remote fee amount is credited 1:1 as relayer reward without ETH→DOT conversion, draining the BridgeRelayers reward pot - ([File: bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs])

## Summary
The V2 Snowbridge outbound flow extracts the `fee` field directly from an unprivileged user's own XCM (`PayFees`/`WithdrawAsset` amount, in 18-decimal Ether units) with no exchange-rate or decimal conversion, stores it verbatim in `PendingOrder.fee`, and later passes it straight into `T::RewardPayment::register_reward(...)` as a native-currency (10/12-decimal) reward amount. This contrasts with the V1 `outbound-queue` pallet's `calculate_fee`, which explicitly applies `PricingParameters` (exchange rate, multiplier) and `convert_from_ether_decimals` before ever treating a value as payable local currency.

## Finding Description
`XcmConverter::extract_remote_fee` reads the fee straight out of the attacker-supplied `PayFees`/`WithdrawAsset` instructions and only checks that `reserved_fee_amount >= fee_amount` and that the asset is Ether-Here — no bound tied to real gas/DOT cost exists: [1](#0-0) 

This raw `fee_amount` is placed unmodified into the constructed `Message`: [2](#0-1) 

`SendMessage::validate`/`deliver` in `send_message_impl.rs` perform only a size check and enqueue the message unchanged — no fee recomputation happens at this stage: [3](#0-2) 

`do_process_message` decodes the `Message` and stores the same `fee` value verbatim into `PendingOrder`: [4](#0-3) 

When a delivery receipt is submitted, `process_delivery_receipt` pays this raw value out as a reward with no currency conversion: [5](#0-4) 

By contrast, V1's `calculate_fee` explicitly applies `params.exchange_rate`, `params.multiplier`, and `convert_from_ether_decimals` (dividing by `10^(18-local_decimals)`) before a remote Ether-denominated fee is ever used as a payable local-currency amount: [6](#0-5) 

The V2 pallet's `Config` trait has no `PricingParameters`, `exchange_rate`, or decimal-conversion type at all — confirmed by inspection of the pallet: [7](#0-6) 

I traced `register_reward` to the `RewardLedger` trait definition — it is a generic ledger-registration call that takes the `reward_balance` argument and records it as-is; there is no unit conversion built into the trait or its generic definition: [8](#0-7) 

I was not able to fully trace the concrete `RewardLedger` implementation used by `BridgeRelayers` in the BridgeHub-Westend runtime (i.e., whether `pallet-bridge-relayers`'s implementation of `register_reward` for the Snowbridge `RewardKind`/`u128` applies any further scaling before crediting `RelayerRewards` storage, or whether the eventual `pay_reward`/claim step, e.g. `PayRewardFromAccount`, performs a currency conversion). The `PaymentProcedure`/`PayRewardFromAccount` code I did inspect performs a straight `T::transfer` of the raw `reward_balance` with no rate conversion: [9](#0-8) 

This is consistent with the claim that no conversion exists anywhere downstream of the fee extraction in the V2 pipeline, but I could not exhaustively verify every intermediate storage/claim step in `bridges/modules/relayers/src/lib.rs` (the `RelayerRewards` map and `claim_rewards` extrinsic) within the available iterations. Nonetheless, every step I did verify — the XCM converter, `Message` construction, `PendingOrder` storage, and `process_delivery_receipt`'s call into `register_reward` — passes the raw user-declared Ether-denominated `fee` value through unmodified, exactly as claimed, and no `PricingParameters`/exchange-rate mechanism exists in this pallet unlike its V1 sibling.

## Impact Explanation
`order.fee`, sourced entirely from attacker-controlled XCM data denominated in 18-decimal Ether units, is registered as a reward via `T::RewardPayment::register_reward(&reward_account, T::DefaultRewardKind::get(), order.fee)` with no scaling to the native reward currency's decimals (typically 10–12 decimals for DOT/KSM). This matches the "public underpriced work" / duplicate-or-mis-scaled-payout impact class: a normal-looking Ether fee value (e.g., fractions of an ETH) becomes a vastly inflated native-currency reward once credited, threatening to drain the shared `BridgeRelayers` reward pot with value that was never actually backed 1:1 on the local chain.

## Likelihood Explanation
High. Constructing the required XCM (`WithdrawAsset` + `PayFees` with attacker-chosen Ether amounts, `AliasOrigin`, `DepositAsset`, `SetTopic`) requires no privileged origin — any account able to route a cross-chain transfer through `pallet-xcm`/`EthereumBlobExporter` can set the fee field to any Ether amount it holds a matching reserve for, and anyone can subsequently submit `submit_delivery_receipt` to trigger the reward payout once the message is processed on Ethereum. No malicious relayer, validator, or governance action is required.

## Recommendation
Apply the same currency-conversion/decimal-normalization logic used in V1's `calculate_fee` / `convert_from_ether_decimals` (via `PricingParameters` and an exchange rate) to the V2 pipeline before `order.fee` is ever stored or paid out, or independently recompute the reward from `T::GasMeter` output and governance-configured pricing parameters rather than trusting the attacker-declared `Message.fee` value. At minimum, cap `order.fee` to a sane maximum and require derivation from measured gas/weight rather than user-supplied XCM data.

## Proof of Concept
1. Attacker submits an XCM: `WithdrawAsset(Ether: 1_000_000_000_000_000_000) -> PayFees(Ether: 1_000_000_000_000_000_000) -> ... -> AliasOrigin -> DepositAsset -> SetTopic`.
2. `XcmConverter::convert` (`bridges/snowbridge/primitives/outbound-queue/src/v2/converter/convert.rs:218-317`) stores `fee: 1_000_000_000_000_000_000` unmodified in the `Message`.
3. `outbound-queue-v2::do_process_message` (`lib.rs:426-436`) stores `PendingOrder { fee: 1_000_000_000_000_000_000, .. }`.
4. Attacker (or a colluding relayer) obtains the Ethereum delivery proof and calls `submit_delivery_receipt`, triggering `process_delivery_receipt` (`lib.rs:462-473`), which calls `T::RewardPayment::register_reward(&reward_account, DefaultRewardKind, 1_000_000_000_000_000_000)` — crediting a reward denominated in the chain's native balance using a raw 18-decimal Ether figure with no conversion applied at any step observed in the pallet.

	/// Extract the fee asset item from PayFees(V5)
	fn extract_remote_fee(&mut self) -> Result<u128, XcmConverterError> {
		use XcmConverterError::*;
		let reserved_fee_assets = match_expression!(self.next()?, WithdrawAsset(fee), fee)
			.ok_or(WithdrawAssetExpected)?;
		ensure!(reserved_fee_assets.len() == 1, AssetResolutionFailed);
		let reserved_fee_asset =
			reserved_fee_assets.inner().first().cloned().ok_or(AssetResolutionFailed)?;
		let (reserved_fee_asset_id, reserved_fee_amount) = match reserved_fee_asset {
			Asset { id: asset_id, fun: Fungible(amount) } => Ok((asset_id, amount)),
			_ => Err(AssetResolutionFailed),
		}?;
		let fee_asset =
			match_expression!(self.next()?, PayFees { asset: fee }, fee).ok_or(InvalidFeeAsset)?;
		let (fee_asset_id, fee_amount) = match fee_asset {
			Asset { id: asset_id, fun: Fungible(amount) } => Ok((asset_id, *amount)),
			_ => Err(AssetResolutionFailed),
		}?;
		// Check the fee asset is Ether (XCM is evaluated in Ethereum context).
		ensure!(fee_asset_id.0 == Here.into(), InvalidFeeAsset);
		ensure!(reserved_fee_asset_id.0 == Here.into(), InvalidFeeAsset);
		ensure!(reserved_fee_amount >= fee_amount, InvalidFeeAsset);
		Ok(fee_amount)
	}

		/// Calculate total fee in native currency to cover all costs of delivering a message to the
		/// remote destination. See module-level documentation for more details.
		pub(crate) fn calculate_fee(
			gas_used_at_most: u64,
			params: PricingParameters<T::Balance>,
		) -> Fee<T::Balance> {
			// Remote fee in ether
			let fee = Self::calculate_remote_fee(
				gas_used_at_most,
				params.fee_per_gas,
				params.rewards.remote,
			);

			// downcast to u128
			let fee: u128 = fee.try_into().defensive_unwrap_or(u128::MAX);

			// multiply by multiplier and convert to local currency
			let fee = FixedU128::from_inner(fee)
				.saturating_mul(params.multiplier)
				.checked_div(&params.exchange_rate)
				.expect("exchange rate is not zero; qed")
				.into_inner();

			// adjust fixed point to match local currency
			let fee = Self::convert_from_ether_decimals(fee);

			Fee::from((Self::calculate_local_fee(), fee))
		}

		/// Calculate fee in remote currency for dispatching a message on Ethereum
		pub(crate) fn calculate_remote_fee(
			gas_used_at_most: u64,
			fee_per_gas: U256,
			reward: U256,
		) -> U256 {
			fee_per_gas.saturating_mul(gas_used_at_most.into()).saturating_add(reward)
		}

		/// The local component of the message processing fees in native currency
		pub(crate) fn calculate_local_fee() -> T::Balance {
			T::WeightToFee::weight_to_fee(
				&T::WeightInfo::do_process_message().saturating_add(T::WeightInfo::commit_single()),
			)
		}

		// 1 DOT has 10 digits of precision
		// 1 KSM has 12 digits of precision
		// 1 ETH has 18 digits of precision
		pub(crate) fn convert_from_ether_decimals(value: u128) -> T::Balance {
			let decimals = ETHER_DECIMALS.saturating_sub(T::Decimals::get()) as u32;
			let denom = 10u128.saturating_pow(decimals);
			value.checked_div(denom).expect("divisor is non-zero; qed").into()
		}
