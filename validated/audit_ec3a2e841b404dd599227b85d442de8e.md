### Title
Liquidation of under-`debtFloorInUsd` positions permanently reverts when `maxLiquidable < 100%`, creating unliquidatable bad debt - (File: contracts/Pool.sol)

### Summary
JLSEC-2026-576 describes a denial of service triggered by specially crafted input to a decryption routine. The Metronome analog is `Pool.liquidate`: a borrower can craft a debt position whose size makes *every* possible `amountToRepay_` revert — either via `AmountGreaterThanMaxLiquidable` (full repayment is > `maxLiquidable`) or via `RemainingDebtIsLowerThanTheFloor` (any partial repayment leaves dust below `debtFloorInUsd`). Once stuck, the position can never be liquidated, and the debt keeps accruing interest, permanently.

### Finding Description
`Pool.liquidate` applies two independent checks on the same `amountToRepay_`:

1. Cap check — `Pool.sol:567`: `if (amountToRepay_.wadDiv(_debtTokenBalance) > maxLiquidable) revert AmountGreaterThanMaxLiquidable()`. With the initialized default `maxLiquidable = 0.5e18` (`Pool.sol:181`), any repayment larger than 50% of the account's debt reverts. Repaying 100% always fails.
2. Floor check — `Pool.sol:571-579`: after a repay, if `0 < remainingDebtUsd < debtFloorInUsd`, the call reverts with `RemainingDebtIsLowerThanTheFloor`. So any allowed repayment must leave remaining debt either `== 0` or `>= debtFloorInUsd`.

Combining both: for a position whose debt `D` satisfies `D < debtFloorInUsd / (1 - maxLiquidable)` (e.g. `D < 2 × debtFloorInUsd` at 50%), a liquidator may repay at most `D - debtFloorInUsd` before hitting the floor. Repeating converges the account's debt to exactly `debtFloorInUsd`. From that state:
- any `amountToRepay_ < D` leaves `remainingDebtUsd` in `(0, debtFloorInUsd)` → `RemainingDebtIsLowerThanTheFloor`;
- `amountToRepay_ == D` gives `wadDiv == 1e18 > maxLiquidable` → `AmountGreaterThanMaxLiquidable`.

The position is therefore permanently unliquidatable. Note that the mint path (`DebtToken._mint`, `DebtToken.sol:583-588`) only enforces `balanceAfter >= debtFloorInUsd`, so `issue`/`SmartFarmingManager` can create debt just *above* the floor that drifts below it purely by interest accrual or collateral price movement — the attacker does not even need to size the debt precisely. The same floor check also exists in `DebtToken.repay` (`DebtToken.sol:442-451`), but `repayAll` (`DebtToken.sol:466-495`) always clears the full balance, so only `liquidate` is bricked (liquidators cannot choose "repay all" — it is capped by `maxLiquidable`).

### Impact Explanation
Broken invariant: liquidation bounds / liveness. An attacker creates many small positions each with debt in the dead zone (or lets interest push them there), then drives them underwater (normal price movement or same-transaction AMM manipulation). Their collateral can never be seized; the debt plus interest grows unbounded while backed by insufficient collateral — accumulating bad debt and, at scale, protocol insolvency for the pool. All attacker actions use only public entry points (`DebtToken.issue` → `Pool.liquidate`), no privileged role, no oracle corruption beyond permitted same-tx manipulation.

### Likelihood Explanation
- `maxLiquidable` defaults to 50% (`Pool.sol:181`) and `debtFloorInUsd` is a live pool parameter specifically intended to create exactly this "minimum debt" region (`Pool.sol:571`).
- No modifier prevents it: `liquidate` is `whenNotShutdown nonReentrant` only; the checks that brick it are the intended parameter checks themselves.
- Cost is one `issue` per position; Sybil scaling is within the allowed threat model (any EOA, own tokens/flash liquidity).
- Requires `debtFloorInUsd > 0` on the deployed pool and `maxLiquidable < 1e18`; both are the documented/default configuration (`maxLiquidable = 0.5e18`, and the floor exists precisely to keep liquidator incentive).

### Recommendation
Resolve the contradiction between the cap and the floor inside `Pool.liquidate`, e.g.:
- Exempt full repayments from `maxLiquidable`: `if (amountToRepay_ < _debtTokenBalance && amountToRepay_.wadDiv(_debtTokenBalance) > maxLiquidable) revert ...` (mirror the `repayAll` escape hatch), or
- Treat the floor as a minimum-*liquidation* amount instead of a minimum-*remaining-debt*: if the post-repay debt would fall below the floor, round `amountToRepay_` up to `D` (repay in full) rather than reverting, provided the seized collateral check at `Pool.sol:583` still passes.

### Proof of Concept
Reproducible on the existing Hardhat setup (`test/Pool.test.ts`, fork of `Pool`/`DebtToken`/`FeeProvider` mocks):

```ts
// Setup: pool initialized (maxLiquidable = 0.5e18), debtFloorInUsd = $2000
await pool.updateDebtFloor(parseEther('2000'));

// Alice deposits MET and issues ~$2500 of msETH debt (< 2 * floor)
await msdMET.connect(alice).deposit(collateral, alice.address); // e.g. $5000 worth
await msEthDebtToken.connect(alice).issue(debtAmount, alice.address); // $2500

// Price moves so the position is unhealthy
await masterOracle.updatePrice(met.address, lowerPrice);
expect((await pool.debtPositionOf(alice.address))._isHealthy).false;

// Liquidator tries to repay anything:
// 1) Full repay -> AmountGreaterThanMaxLiquidable (wadDiv = 1e18 > 0.5e18)
await expect(
  pool.connect(lqd).liquidate(msEth.address, alice.address, debt, msdMET.address)
).revertedWithCustomError(pool, 'AmountGreaterThanMaxLiquidable');

// 2) Max allowed partial repay (50% of debt = $1250) -> remaining $1250 < floor
await expect(
  pool.connect(lqd).liquidate(msEth.address, alice.address, debt.div(2), msdMET.address)
).revertedWithCustomError(pool, 'RemainingDebtIsLowerThanTheFloor');

// 3) Only repay <= debt - floor ($500) succeeds; iterate until debt == floor.
//    Then EVERY call reverts: partial -> floor error, full -> maxLiquidable error.
//    Position is permanently unliquidatable while interest accrues.
```

The dead zone scales with `debtFloorInUsd / (1 - maxLiquidable)`; repeating per-account lets an attacker park arbitrarily many underwater positions that liquidators can never close.
