### Title
`OutboundQueue::calculate_fee` accepts governance-valid pricing parameters that round the on-chain remote relayer reward to zero, permitting free/underpriced Ethereum-bound message dispatch - (File: bridges/snowbridge/pallets/outbound-queue/src/lib.rs)

### Summary
`PricingParameters::validate` only rejects a zero `exchange_rate`, `fee_per_gas`, `rewards.local`, `rewards.remote`, or `multiplier` [1](#0-0) . It never bounds the *computed* remote fee against a minimum, so parameter sets that pass validation can still produce a `fee.remote == 0` after integer-truncating decimal conversion in `Pallet::calculate_fee` / `convert_from_ether_decimals` [2](#0-1) . This is the same broken invariant as the Chainlink `minAnswer`/`maxAnswer` bug: a value that is nominally "checked" (non-zero) is accepted without validating it stays inside a meaningful operating range, and downstream logic (fee charged to the public `send_message`/`validate` path) silently treats the degenerate result as valid.

### Finding Description
`PricingParameters::validate()` is the only sanity gate applied to governance-set pricing data (`exchange_rate`, `fee_per_gas`, `rewards`, `multiplier`), and it merely checks each field is non-zero [1](#0-0) .

The public entrypoint for every outbound Ethereum message (`SendMessage::validate`, reachable by any account sending XCM through the Snowbridge exporter, or by `snowbridge-pallet-system`) calls `Self::calculate_fee(gas_used_at_most, T::PricingParameters::get())` to determine the fee charged to the sender before enqueueing the message [3](#0-2) .

`calculate_fee` computes:
```
fee = fee_per_gas * gas_used_at_most + reward         // U256, wei
fee = FixedU128::from_inner(fee) * multiplier / exchange_rate    // fixed-point local units
fee = convert_from_ether_decimals(fee)                 // integer division by 10^(18-Decimals)
``` [4](#0-3) 

`convert_from_ether_decimals` performs a plain integer `checked_div` with no minimum/rounding-up guard: any wei-denominated value smaller than `10^(18-Decimals)` (e.g. `10^8` on a 10-decimal chain like DOT) truncates to `0` [5](#0-4) . The pallet's own test suite documents this exact outcome as an accepted, "invalid" but unguarded state: with `exchange_rate = 1/1`, `fee_per_gas = 1`, `reward = 1`, `multiplier = 1/1` (all non-zero, thus `validate()`-passing), the computed `fee.remote` is `0` even though `fee.local` is non-zero [6](#0-5) . The comment in the test itself states: *"Though none zero pricing params the remote fee calculated here is invalid which should be avoided"* — i.e. the bug is known to exist but the fix (a floor/minimum check analogous to `minAnswer`) is not implemented.

`fee.remote` becomes the `reward` field embedded in the `CommittedMessage` sent to the Gateway contract on Ethereum, which is what relayers get reimbursed for delivering the message [7](#0-6) . A relayer reward that rounds to zero means the message enters the outbound queue, consumes on-chain storage/weight (`Messages`, `MessageLeaves`, merkle commitment) and headers digest space each block, but no economically rational relayer will deliver it to Ethereum — the message stalls indefinitely in queue while still having been "paid for" and accepted by the local sender-fee charge.

This exactly mirrors the ChainlinkOracle bug class: a numeric input that superficially satisfies a "non-zero"/existence check is not validated against the range required for the value to be *meaningful*, and the consuming logic (fee/queue acceptance) proceeds anyway.

### Impact Explanation
Because `calculate_fee` runs on the unprivileged public message-send path (any parachain/XCM sender or protocol using the outbound queue), an attacker who can influence `gas_used_at_most` (e.g. by choosing commands with small `GasMeter` weight) relative to the currently governance-set `fee_per_gas`/`reward`/`exchange_rate`/`multiplier` can systematically produce messages whose `fee.remote` rounds to zero while still being accepted, queued, and merkle-committed. This is "public underpriced work that degrades block production or stalls bridge processing" per the impact gate: messages consume `MaxMessagesPerBlock` slots, `on_finalize` merkle-commit weight, and header digest space, without providing the compensation relayers need to actually deliver them — degrading real bridge throughput and potentially permanently stalling delivery of legitimately-fee-paying messages behind the unrewarded ones in the same channel's nonce sequence.

### Likelihood Explanation
The likelihood is tied to real-world pricing-parameter values (governance sets these periodically per the module doc [8](#0-7) ), and the decimal-truncation divisor `10^(18-Decimals)` is large (`10^8` for 10-decimal DOT, `10^6` for 12-decimal chains), so any legitimate low-gas command combined with a modest `exchange_rate`/`multiplier` can realistically fall under this rounding threshold — the pallet's own unit test demonstrates it occurring with unremarkable, non-degenerate parameter values, not just extreme edge cases.

### Recommendation
Add a floor check in `calculate_fee`/`convert_from_ether_decimals` (or in `PricingParameters::validate`) that rejects or rounds up any computed `fee.remote` (and `fee.local`) that would truncate to zero, e.g. use `div_ceil`/saturating-up rounding instead of `checked_div`, and/or enforce `fee.remote > 0` before allowing `SendMessage::validate` to succeed, returning a `SendError` otherwise — analogous to enforcing a `minAnswer` floor on oracle price data before it is consumed.

### Proof of Concept
The existing regression test already demonstrates the corrupted value: `test_calculate_fees_with_valid_exchange_rate_but_remote_fee_calculated_as_zero` feeds fully non-zero, `validate()`-passing `PricingParameters` (`exchange_rate = 1/1`, `fee_per_gas = 1`, `rewards.remote = 1`, `multiplier = 1/1`) with `gas_used = 250000` into `OutboundQueue::calculate_fee`, and asserts `fee.remote == 0` while `fee.local == 698000000` [6](#0-5) . Because `calculate_fee` is invoked unconditionally from the public `SendMessage::validate` entrypoint [9](#0-8)  with no rejection when `fee.remote == 0`, any command whose `GasMeter`-measured gas cost, combined with currently-set governance pricing, produces this rounding will be queued and merkle-committed with an unpayable relayer reward, exactly reproducing the underpriced-work class of the Chainlink `minAnswer`/`maxAnswer` report.

		/// Calculate total fee in native currency to cover all costs of delivering a message to the
		/// remote destination. See module-level documentation for more details.
		pub(crate) fn calculate_fee(
			gas_used_at_most: u64,
			params: PricingParameters<T::Balance>,
		) -> Fee<T::Balance> {
			// Remote fee in ether
			let fee = Self::calculate_remote_fee(
				gas_used_at_most,
				params.fee_per_gas,
				params.rewards.remote,
			);

			// downcast to u128
			let fee: u128 = fee.try_into().defensive_unwrap_or(u128::MAX);

			// multiply by multiplier and convert to local currency
			let fee = FixedU128::from_inner(fee)
				.saturating_mul(params.multiplier)
				.checked_div(&params.exchange_rate)
				.expect("exchange rate is not zero; qed")
				.into_inner();

			// adjust fixed point to match local currency
			let fee = Self::convert_from_ether_decimals(fee);

			Fee::from((Self::calculate_local_fee(), fee))
		}

		/// Calculate fee in remote currency for dispatching a message on Ethereum
		pub(crate) fn calculate_remote_fee(
			gas_used_at_most: u64,
			fee_per_gas: U256,
			reward: U256,
		) -> U256 {
			fee_per_gas.saturating_mul(gas_used_at_most.into()).saturating_add(reward)
		}

		/// The local component of the message processing fees in native currency
		pub(crate) fn calculate_local_fee() -> T::Balance {
			T::WeightToFee::weight_to_fee(
				&T::WeightInfo::do_process_message().saturating_add(T::WeightInfo::commit_single()),
			)
		}

		// 1 DOT has 10 digits of precision
		// 1 KSM has 12 digits of precision
		// 1 ETH has 18 digits of precision
		pub(crate) fn convert_from_ether_decimals(value: u128) -> T::Balance {
			let decimals = ETHER_DECIMALS.saturating_sub(T::Decimals::get()) as u32;
			let denom = 10u128.saturating_pow(decimals);
			value.checked_div(denom).expect("divisor is non-zero; qed").into()
		}

#[test]
fn test_calculate_fees_with_valid_exchange_rate_but_remote_fee_calculated_as_zero() {
	new_tester().execute_with(|| {
		let gas_used: u64 = 250000;
		let price_params: PricingParameters<<Test as Config>::Balance> = PricingParameters {
			exchange_rate: FixedU128::from_rational(1, 1),
			fee_per_gas: 1_u32.into(),

			multiplier: FixedU128::from_rational(1, 1),

		let fee = OutboundQueue::calculate_fee(gas_used, price_params.clone());
		assert_eq!(fee.local, 698000000);
		// Though none zero pricing params the remote fee calculated here is invalid
		// which should be avoided
		assert_eq!(fee.remote, 0);
	});
