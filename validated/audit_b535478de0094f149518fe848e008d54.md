### Title
Archive extraction path traversal via untrusted tar stream - ([File: internal/gitaly/service/repository/create_repository_from_snapshot.go])

### Summary
`CreateRepositoryFromSnapshot` fetches an attacker-influenced tar stream from `in.GetHttpUrl()` and extracts it with a raw `tar -C path -xvf -` invocation, with no `--no-absolute-names`, no symlink/hardlink filtering, and no path-containment validation. The code comment itself acknowledges "the received archive is trusted *a lot*", confirming there is no defense against a malicious archive placing files outside the target repository directory.

### Finding Description
`s.untar` in [1](#0-0)  builds and runs the command `tar -C path -xvf -` piping in the HTTP response body directly, without `--no-absolute-names`, `--no-same-owner`, or any post-extraction verification that all extracted paths remain under `path`. GNU tar by default follows absolute path entries and TypeLink (hardlink) headers, writing/overwriting files outside the destination directory. This is invoked from `CreateRepositoryFromSnapshot` at [2](#0-1) , with an explicit code comment noting the archive is trusted "*a lot*" and needs hardening before being pointed at endpoints not under Gitaly's control — an implicit admission that no such hardening currently exists. `HttpUrl` and `HttpAuth` in the request are attacker-controlled fields; nothing in this handler validates the response content beyond the HTTP status code (`internal/gitaly/service/repository/create_repository_from_snapshot.go` lines 105-113). There is no allowlist enforcement, no relative-path checking (`storage.ValidateRelativePath` is not invoked on tar entry names — it's not even possible from Go since extraction is delegated to the external `tar` binary), and no `chroot`/sandboxing of the extraction. Any archive returned by the URL is trusted as-is.

### Impact Explanation
An attacker who can trigger this RPC with a URL they control (e.g., via an import/fork snapshot flow that surfaces `HttpUrl`) can supply a tar archive with absolute path entries (e.g. `/etc/cron.d/x`, or paths reaching other repositories/storages on disk) or hardlink entries pointing at existing files, causing Gitaly to write or overwrite files outside the newly created repository directory. This matches the GitLab bounty "archive extraction escape" impact class and could lead to file planting outside the repo (e.g. into a sibling repository's `hooks/` directory or `config`), which in Gitaly's model can lead to further code execution via custom hooks, or corruption/DoS of unrelated repositories/system files, depending on the process's file permissions.

### Likelihood Explanation
The precondition is that an unprivileged user can reach `CreateRepositoryFromSnapshot` with a controllable `HttpUrl` — this RPC exists specifically to import a repository snapshot from an HTTP endpoint supplied in the request, which is exactly the "project import" scenario described in the audit prompt. No special role, secret, or peer compromise is required — only the ability to supply a URL Gitaly will fetch and control the response body from an attacker-run server. The extraction logic performs no archive vetting and directly shells out to `tar`, so exploitation is deterministic and repeatable once the RPC is reachable with attacker-influenced input.

### Recommendation
Do not shell out to the system `tar` binary with untrusted input. Instead:
- Extract with Go's `archive/tar` package, rejecting/skipping any header whose cleaned `filepath.Join(path, header.Name)` does not have `path` as a prefix.
- Reject absolute paths, `..` components, symlinks (`TypeSymlink`), hardlinks (`TypeLink`), device/char/fifo special files, and enforce reasonable size/entry-count limits to bound resource use.
- If the external `tar` binary must be retained for compatibility, at minimum add `--no-absolute-names`, refuse archives containing `../`, and post-validate with `filepath.Walk` that no extracted file lies outside `path` (though this is race-prone compared to a manual Go implementation).
- Consider deprecating or gating this RPC behind an operator-controlled endpoint allowlist since the comment already signals this was a known, unresolved risk.

func TestCreateRepositoryFromSnapshot_pathTraversal(t *testing.T) {
    // Crafted tar with an absolute path escaping the destination directory.
    var buf bytes.Buffer
    tw := tar.NewWriter(&buf)
    require.NoError(t, tw.WriteHeader(&tar.Header{
        Name:     "/tmp/gitaly-poc-escape/pwned",
        Typeflag: tar.TypeReg,
        Mode:     0o644,
        Size:     int64(len("pwned")),
    }))
    _, err := tw.Write([]byte("pwned"))
    require.NoError(t, err)
    require.NoError(t, tw.Close())

    srv := httptest.NewServer(http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        w.Write(buf.Bytes())
    }))
    defer srv.Close()

    // ... construct CreateRepositoryFromSnapshotRequest with HttpUrl: srv.URL, call RPC ...

    // Expected (failing) result today: file exists outside the repo path.
    _, err = os.Stat("/tmp/gitaly-poc-escape/pwned")
    require.NoError(t, err, "archive escaped destination directory - path traversal confirmed")
}
