Based on the investigation, I found a genuine analog: an anonymous JSON-RPC client can create a log filter via `eth_newFilter` and then simply never call `eth_getFilterLogs`/`eth_getFilterChanges` to drain it, causing the filter's internal result queue to grow without bound (or until block-range/time expiry) exactly like the RakLib reliable-ordered queue that grows until a missing packet is delivered.

### Title
Unbounded per-filter result queue in JSON-RPC log/block filters allows memory exhaustion via `eth_newFilter` - (File: `framework/src/main/java/org/tron/core/services/jsonrpc/filters/LogFilterAndResult.java`)

### Summary
`eth_newFilter` creates a `LogFilterAndResult` whose `result` field is an unbounded `LinkedBlockingQueue<LogFilterElement>` [1](#0-0) . Every new block, `handleLogsFilter` matches logs against all live filters and calls `logFilterAndResult.getResult().addAll(localResults)` [2](#0-1) , appending to the queue regardless of whether the client has ever drained it with `popAll()`. While the total *count* of filters is capped (`maxLogFilterNum`, checked in `newFilter`) [3](#0-2) , there is no cap on the *size* of an individual filter's accumulated result queue. `BlockFilterAndResult` has the identical unbounded pattern [4](#0-3) .

### Finding Description
- `FilterResult` (the common base class) only tracks an `expireTimeStamp` used for eviction from the filter map, not for capping queue size [5](#0-4) .
- Any anonymous JSON-RPC client can call `eth_newFilter` with a wide/open block range (`fromBlock` omitted → tracks all future blocks, `toBlock` = `Long.MAX_VALUE`) [6](#0-5) , and match-all `address`/`topics` (both empty means match everything, per `LogFilter` semantics referenced by `matchBloom`/`LogMatch`).
- The default `EXPIRE_SECONDS` window keeps the filter alive for a fixed duration during which every matching event/log across every subsequent block is appended to `result` with no bound.
- Since the attacker never calls `eth_getFilterLogs`/`eth_getFilterChanges` (`popAll()`), the queue keeps growing every block until expiry, and the attacker can also repeat this with each of the (up to `maxLogFilterNum` = 20000 by default) filters, multiplying memory pressure.
- This is directly analogous to the RakLib bug: a queue that grows unbounded while waiting for a "missing packet" (here, the missing client poll) that a malicious/lazy client can simply never send.

### Impact Explanation
An anonymous, unauthenticated JSON-RPC caller (no signed transaction needed — this is a pure API-request path via `TronJsonRpcImpl`/`eth_newFilter`) can create filters that continuously accumulate matched log/block entries in server heap memory for the duration of the expire window, and can repeat/renew filters up to the configured cap, sustaining unbounded per-filter memory growth. On a busy chain (many transactions/logs per block), this can exhaust node memory, causing GC pressure, degraded API/RPC service, or a node crash — a concrete "node crash / API the node can no longer serve" outcome as required by the validation criteria.

### Likelihood Explanation
High likelihood: `eth_newFilter` is a standard, unauthenticated JSON-RPC method exposed whenever `node.jsonrpc.httpFullNodeEnable`/`httpSolidityNodeEnable` is turned on (a common FullNode configuration for wallets/explorers) [7](#0-6) . No signature, stake, or special permission is required — the caller only needs HTTP access to the JSON-RPC endpoint, and the exploit requires only creating a broad filter and not polling it.

### Recommendation
Cap the size of each `FilterResult.result` queue (e.g., via a configurable `maxFilterResultSize`), dropping/evicting oldest entries or rejecting/expiring filters that exceed the cap, similar to how `maxLogFilterNum`/`maxBlockFilterNum` cap the number of filters. Alternatively, track queue size per filter and terminate/expire filters early once they exceed a memory budget, and consider requiring periodic client polling to keep a filter alive (sliding expiry tied to `popAll()` activity) rather than a fixed time window that lets a queue grow unchecked in the meantime.

### Proof of Concept
1. Enable JSON-RPC (`node.jsonrpc.httpFullNodeEnable = true`).
2. Call `eth_newFilter` with `{"fromBlock": null, "toBlock": null, "address": null, "topics": null}` (or omit all fields) → creates a filter matching every future log with no upper block bound [8](#0-7) .
3. Never call `eth_getFilterChanges`/`eth_getFilterLogs` for that filter ID.
4. As new blocks with logs are produced, `handleLogsFilter`→`processLogFilterEntry` appends every matching log element into that filter's `result` queue every block [9](#0-8) , growing memory usage for the `EXPIRE_SECONDS` lifetime of the filter, unbounded by any per-queue size limit.
5. Repeat filter creation up to `maxLogFilterNum` times (renewing each before expiry) to sustain and multiply memory growth over time.

package org.tron.core.services.jsonrpc.filters;

import java.util.List;
import java.util.concurrent.BlockingQueue;
import lombok.Getter;
import org.tron.core.services.jsonrpc.TronJsonRpcImpl;

public abstract class FilterResult<T> {

  private long expireTimeStamp;

  @Getter
  protected BlockingQueue<T> result;

  public void updateExpireTime() {
    expireTimeStamp = System.currentTimeMillis() + TronJsonRpcImpl.EXPIRE_SECONDS * 1000;
  }

  public boolean isExpire() {
    return expireTimeStamp < System.currentTimeMillis();
  }

  public abstract void add(T t);

  public abstract List<T> popAll();
}
