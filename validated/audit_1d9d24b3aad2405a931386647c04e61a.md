Audit Report

## Title
`process_delivery_receipt` ignores the `success` field of the delivery receipt, allowing relayer rewards and order settlement for failed deliveries - (File: `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs`)

## Summary
`process_delivery_receipt` decodes a `DeliveryReceipt` containing a `success: bool` field sourced from the Ethereum `InboundMessageDispatched` event, but never inspects it before paying the relayer reward and removing the `PendingOrders` entry [1](#0-0) . This lets a relayer collect the full `order.fee` reward and permanently settle a message's pending order even when the Ethereum-side dispatch of that message actually failed.

## Finding Description
`submit_delivery_receipt` is a public, signed extrinsic that verifies a Merkle/beacon proof for an event log, decodes it into a `DeliveryReceipt` via `DeliveryReceipt::try_from`, and calls `process_delivery_receipt` [2](#0-1) . The `DeliveryReceipt` struct explicitly carries `success: bool`, decoded directly from the `InboundMessageDispatched` Solidity event (`event InboundMessageDispatched(uint64 indexed nonce, bytes32 topic, bool success, bytes32 reward_address)`) [3](#0-2) .

Inside `process_delivery_receipt`, the only checks performed are that `receipt.gateway` matches the configured `GatewayAddress` and that a `PendingOrders` entry exists for `receipt.nonce`; `reward_account` is derived from `receipt.reward_address` (falling back to the relayer). The function then unconditionally pays `order.fee` via `T::RewardPayment::register_reward` (when `fee > 0`) and removes the `PendingOrders` entry, emitting `MessageDelivered` — all without ever reading `receipt.success` [4](#0-3) . The module documentation itself frames the receipt submission as occurring "when the message has been verified **and executed**," implying execution success is intended to gate reward and settlement, but the implementation does not enforce this.

Existing guards (proof verification, gateway match, nonce existence) only validate that a real event was emitted by the correct contract for a known pending order — they say nothing about whether the dispatched command on Ethereum actually succeeded. Since `success` is decoded but discarded, these checks are insufficient to prevent reward payout and order settlement on a genuinely failed delivery.

## Impact Explanation
This breaks the invariant that "message queues, bridge markers, receipts, and payout state must only advance after decode, dispatch, execution, and settlement succeed atomically." A relayer can be rewarded with `order.fee` and have the `PendingOrders` entry for `nonce` permanently cleared for a message whose dispatch failed on Ethereum (`success = false`), which is an incorrect-payout / duplicate-or-improper-settlement condition: value is paid out and bridge state is finalized for an outcome that did not actually complete as intended.

## Likelihood Explanation
The only precondition is a genuine `InboundMessageDispatched(nonce, topic, success=false, reward_address)` event on Ethereum (e.g., a command reverting at the Gateway during normal operation) and a standard, unprivileged relayer submitting the corresponding valid proof via the public `submit_delivery_receipt` extrinsic [2](#0-1) . No malicious validator, governance action, or compromised infrastructure is required — any signed account acting as relayer can trigger this once a failed dispatch is emitted, which is part of normal bridge operation.

## Recommendation
Add an explicit `ensure!(receipt.success, Error::<T>::DeliveryFailed)` (or equivalent branching) in `process_delivery_receipt` before calling `T::RewardPayment::register_reward` and/or removing the `PendingOrders` entry, so failed deliveries do not trigger reward payout, and define explicit failure-path semantics (e.g., a distinct event, retry, or no-reward outcome) for `success == false`.

## Proof of Concept
1. `do_process_message` queues a message and inserts a `PendingOrder { nonce: N, fee: F, .. }` with `F > 0` [5](#0-4) .
2. On Ethereum, the Gateway processes the message but the dispatched command reverts, emitting `InboundMessageDispatched(nonce=N, topic, success=false, reward_address)`.
3. A relayer obtains a valid proof for this event and calls `submit_delivery_receipt`, which verifies the proof and decodes `receipt.success = false` [6](#0-5) .
4. `process_delivery_receipt` pays `order.fee` to `reward_account` and removes `PendingOrders[N]` without ever checking `receipt.success` [7](#0-6) .
5. A unit test asserting `PendingOrders::<T>::get(N).is_none()` and a non-zero reward event after calling `process_delivery_receipt` with a `DeliveryReceipt { success: false, .. }` confirms the reward/settlement occurs despite the failed dispatch.

sol! {
	event InboundMessageDispatched(uint64 indexed nonce, bytes32 topic, bool success, bytes32 reward_address);
}

/// Delivery receipt
#[derive(Clone, Debug)]
pub struct DeliveryReceipt {
	/// The address of the outbound queue on Ethereum that emitted this message as an event log
	pub gateway: H160,
	/// The nonce of the dispatched message
	pub nonce: u64,
	/// Message topic
	pub topic: H256,
	/// Delivery status
	pub success: bool,
	/// The reward address
	pub reward_address: [u8; 32],
}

#[derive(Copy, Clone, Encode, Decode, Eq, PartialEq, Debug, TypeInfo)]
pub enum DeliveryReceiptDecodeError {
	DecodeLogFailed,
	DecodeAccountFailed,
}

impl TryFrom<&Log> for DeliveryReceipt {
	type Error = DeliveryReceiptDecodeError;

	fn try_from(log: &Log) -> Result<Self, Self::Error> {
		let topics: Vec<B256> = log.topics.iter().map(|x| B256::from_slice(x.as_ref())).collect();

		let event = InboundMessageDispatched::decode_raw_log_validate(topics, &log.data)
			.map_err(|_| DeliveryReceiptDecodeError::DecodeLogFailed)?;

		Ok(Self {
			gateway: log.address,
			nonce: event.nonce,
			topic: H256::from_slice(event.topic.as_ref()),
			success: event.success,
			reward_address: event.reward_address.0,
		})
	}
