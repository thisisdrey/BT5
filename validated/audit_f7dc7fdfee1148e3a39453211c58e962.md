### Title
Multisig weight double-counting via ECDSA signature malleability in ValidateMultiSign precompile - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The GHSA-63m5-974w-448v analog is a signature/identity-claim verification bypass where a weak comparison lets an attacker satisfy an authorization threshold without independent, distinct approvals. The reachable java-tron equivalent is the `ValidateMultiSign` TVM precompile, which any contract call (i.e., any transaction broadcaster) can invoke. It recovers a signer address per submitted signature and sums permission weights, but its duplicate-detection only skips a signature when the *exact byte-for-byte signature blob* was already seen for that address — not when the *address* was already counted. Because ECDSA signatures are malleable (multiple distinct `(r, s, v)` byte encodings recover to the same address for the same message hash), a single key holder can submit two or more different-looking signatures over the same hash and have the *same address's weight added multiple times* to `totalWeight`, letting one signer satisfy a multi-key `permission.getThreshold()` alone.

### Finding Description
`ValidateMultiSign.execute` at [1](#0-0)  loops over attacker-supplied signatures, recovers an address for each via `recoverAddrBySign`, and only skips re-adding weight when `executedSignList` contains the exact merged `(recoveredAddr, sign)` byte sequence: [2](#0-1) 

If `recoveredAddr` was already seen but the raw `sign` bytes differ (achievable trivially via ECDSA `s`/`(N-s)` malleability and adjusted recovery id — the codebase does not enforce low-`s` or otherwise canonicalize signatures before this check, per `SignUtils`/`ECKey` handling used elsewhere: [3](#0-2) ), execution falls through to `MUtil.checkCPUTime()` and then unconditionally executes `totalWeight += weight;` again for the same address. This contrasts with the stricter, address-keyed dedup used in the on-chain transaction signature path `TransactionCapsule.checkWeight`, which maps the *recovered address* (not raw signature bytes) to weight and explicitly throws `"has signed twice!"` when an address repeats: [4](#0-3) . The precompile lacks this address-level guard, so it accepts a forged/duplicated identity claim (multiple sig encodings → one real signer) as if it were multiple independent approvals — directly analogous to Fleet accepting unverified/duplicate identity claims to satisfy an enrollment authorization check.

### Impact Explanation
Any smart contract can call the `ValidateMultiSign` precompile to check whether a set of signatures satisfies an account's multisig `Permission` threshold. If a downstream contract (e.g., a custodial/escrow/DEX contract gating a withdrawal or an on-chain multisig wallet built on this precompile) trusts a `true`/weight-≥-threshold result to authorize a fund-moving operation, a single colluding or compromised key can forge the appearance of multiple co-signers using malleable signature variants of its own signature, bypassing the intended N-of-M authorization and enabling unauthorized transfer/withdrawal of funds — a concrete theft-of-funds impact reachable from an unprivileged contract caller.

### Likelihood Explanation
High likelihood: `ValidateMultiSign` is a public precompile reachable from any TVM contract call (`TriggerSmartContract`), requiring no special privilege — only knowledge of one valid signature over the hash and the ability to derive a malleable variant, which is a standard, well-known ECDSA property (flip `s` to `N-s` and adjust `v`/recovery id), not requiring any private key beyond the one already used to sign.

### Recommendation
In `ValidateMultiSign.execute`, deduplicate on `recoveredAddr` alone (not the concatenation with raw signature bytes) — i.e., once an address has contributed weight, any further signature recovering to that same address must be skipped entirely (mirroring `TransactionCapsule.checkWeight`'s address-keyed `addMap`), or reject the call outright if a repeated address is observed, consistent with the "has signed twice" semantics enforced on the primary transaction-signing path.

### Proof of Concept
1. Deploy/call a contract that invokes the `ValidateMultiSign` precompile with an account address, `permissionId`, and `data` for an account whose Active permission requires 2 keys of weight 1 each (threshold 2), controlled by keys K1 and K2.
2. Attacker controls only K1. Compute `hash = sha256(address || permissionId || data)` as done in the precompile: [5](#0-4) .
3. Sign `hash` with K1 to get signature `sig1 = (r, s, v)`. Derive the malleable counterpart `sig2 = (r, N-s, v')` (standard secp256k1 malleability transform), which recovers to the same address as `sig1`.
4. Submit `signatures = [sig1, sig2]` to the precompile call. Because `sig1 != sig2` as raw bytes, the `executedSignList` exact-match check does not skip the second entry, so `totalWeight` becomes `weight(K1) + weight(K1) = 2`, meeting the threshold of 2 with only K1's key — bypassing the requirement for K2's independent approval.
5. Any consuming contract that gates a fund-moving action on this precompile returning `dataOne()` (threshold met) can be tricked into authorizing the action with only one real signer.
