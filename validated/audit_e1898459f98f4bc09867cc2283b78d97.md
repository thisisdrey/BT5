Audit Report

## Title
Reward-per-token truncated division permanently forfeits `pallet-asset-rewards` staker rewards - (File: substrate/frame/asset-rewards/src/lib.rs)

## Summary
`reward_per_token` in `substrate/frame/asset-rewards/src/lib.rs` scales the numerator `reward_rate_per_block * elapsed_blocks` by a fixed `PRECISION_SCALING_FACTOR` of only `4096` before dividing by `total_tokens_staked` [1](#0-0) . When the scaled numerator is smaller than `total_tokens_staked` (realistic for low-decimal reward assets paired with high-decimal/high-stake staked assets), integer division truncates to zero, and because `update_pool_rewards` unconditionally advances `last_update_block` to the current block regardless of whether `reward_per_token_stored` changed, that elapsed reward window is permanently forfeited [2](#0-1) .

## Finding Description
`reward_per_token` computes:
```rust
pool_info.reward_rate_per_block
    .ensure_mul(rewardable_blocks_elapsed.into())?
    .ensure_mul(PRECISION_SCALING_FACTOR.into())?
    .ensure_div(pool_info.total_tokens_staked)?
``` [3](#0-2) 

`ensure_mul`/`ensure_div` only guard against arithmetic overflow, not precision loss to zero. `derive_rewards` reverses the same scale factor when computing a staker's owed amount [4](#0-3) . `update_pool_and_staker_rewards` — invoked from every `stake`, `unstake`, and `harvest_rewards` call — calls `reward_per_token` then `update_pool_rewards`, which unconditionally sets `last_update_block = now` and `reward_per_token_stored = reward_per_token` even if the computed increment truncated to zero [5](#0-4) . Since `last_update_block` moves forward regardless, the elapsed-block window that produced a zero increment is consumed and can never again contribute to `reward_per_token` — the loss is permanent, not merely deferred. `stake` is a public, unprivileged extrinsic reachable by any signed account with no cooldown [6](#0-5) , and `harvest_rewards` is similarly public [7](#0-6) , so an attacker can trivially force many small `rewardable_blocks_elapsed` windows to maximize truncation-to-zero events. `PRECISION_SCALING_FACTOR = 4096` is a fixed `u16` constant with no accuracy proof, unlike `pallet-nomination-pools`'s `RewardCounter`, which uses `FixedU128` scaled by `10^18` with an explicit documented accuracy analysis [8](#0-7) .

## Impact Explanation
This violates the invariant that staking/reward-pool value must be conserved and settled exactly to the rightful beneficiary: reward tokens nominally due to stakers per `reward_rate_per_block * elapsed_blocks` are silently and unrecoverably dropped from `reward_per_token_stored` whenever the scaled numerator underflows relative to `total_tokens_staked`, while the corresponding reward-asset balance remains stranded in the pool account. On `cleanup_pool`, any residual pool balance — including this stranded, undistributed dust — is returned to the pool admin rather than the stakers who were entitled to it [9](#0-8) , misallocating value away from the intended beneficiaries. This aligns with the "conserve value and settle exactly once to the rightful beneficiary and amount" pivot and is a genuine runtime bug compromising intended reward-payout behavior.

## Likelihood Explanation
High. Triggering the bug requires only ordinary, unprivileged public extrinsics (`stake`, `unstake`, `harvest_rewards`) callable by any account, with no special timing, governance, or privileged access needed. The precondition — a reward asset with few decimals relative to a highly-decimaled/high-value staked asset — is a normal, foreseeable pool configuration, not an exotic adversarial setup, and any interested party (staker or third party) can repeatedly call these extrinsics to force small `rewardable_blocks_elapsed` windows and accumulate unbounded reward loss over the pool's lifetime.

## Recommendation
Increase `PRECISION_SCALING_FACTOR` to a much larger fixed-point base (e.g., `10^18`) or migrate `reward_per_token` to a proper fixed-point type (`FixedU128`/`Perquintill`) with a documented accuracy proof analogous to `pallet-nomination-pools`'s `RewardCounter`. Additionally, track and carry forward the truncated remainder of `reward_rate_per_block * elapsed_blocks * SCALE % total_tokens_staked` across updates instead of unconditionally advancing `last_update_block`, so fractional accrual is not permanently lost.

## Proof of Concept
1. `create_pool` with a `reward_asset_id` at 6 decimals, `reward_rate_per_block = 10`, and `staked_asset_id` at 18 decimals.
2. Account A calls `stake(pool_id, 100_000 * 10**18)` at block `N`.
3. One block later, any account calls `harvest_rewards` or `stake`, triggering `reward_per_token`: `10 * 1 * 4096 / (100_000 * 10**18) = 40960 / 10^23 = 0` due to integer truncation.
4. `reward_per_token_stored` stays unchanged while `last_update_block` advances to `N+1` [10](#0-9) , permanently losing the reward owed for block `N→N+1`.
5. Repeating every block (trivial for an unprivileged account) causes systematic, unbounded, unrecoverable under-payment of stakers relative to `reward_rate_per_block * total_elapsed_blocks`.

		pub fn harvest_rewards(
			origin: OriginFor<T>,
			pool_id: PoolId,
			staker: Option<T::AccountId>,
		) -> DispatchResult {
			let caller = ensure_signed(origin)?;
			let staker = staker.unwrap_or(caller.clone());

			// Always start by updating the pool and staker rewards.
			let pool_info = Pools::<T>::get(pool_id).ok_or(Error::<T>::NonExistentPool)?;
			let now = T::BlockNumberProvider::current_block_number();
			ensure!(now > pool_info.expiry_block || caller == staker, BadOrigin);

			let staker_info =
				PoolStakers::<T>::get(pool_id, &staker).ok_or(Error::<T>::NonExistentStaker)?;
			let (pool_info, mut staker_info) =
				Self::update_pool_and_staker_rewards(&pool_info, &staker_info)?;

			// Transfer unclaimed rewards from the pool to the staker.
			T::Assets::transfer(
				pool_info.reward_asset_id,
				&pool_info.account,
				&staker,
				staker_info.rewards,
				// Could kill the account, but only if the pool was already almost empty.
				Preservation::Expendable,
			)?;

			// Emit event.
			Self::deposit_event(Event::RewardsHarvested {
				caller,
				staker: staker.clone(),
				pool_id,
				amount: staker_info.rewards,
			});

			// Reset staker rewards.
			staker_info.rewards = 0u32.into();

			if staker_info.amount.is_zero() {
				PoolStakers::<T>::remove(&pool_id, &staker);
			} else {
				PoolStakers::<T>::insert(&pool_id, &staker, staker_info);
			}

			Ok(())

		pub(super) fn reward_per_token(
			pool_info: &PoolInfoFor<T>,
		) -> Result<T::Balance, DispatchError> {
			if pool_info.total_tokens_staked.is_zero() {
				return Ok(pool_info.reward_per_token_stored);
			}

			let rewardable_blocks_elapsed: u32 =
				match Self::last_block_reward_applicable(pool_info.expiry_block)
					.ensure_sub(pool_info.last_update_block)?
					.try_into()
				{
					Ok(b) => b,
					Err(_) => return Err(Error::<T>::BlockNumberConversionError.into()),
				};

			Ok(pool_info.reward_per_token_stored.ensure_add(
				pool_info
					.reward_rate_per_block
					.ensure_mul(rewardable_blocks_elapsed.into())?
					.ensure_mul(PRECISION_SCALING_FACTOR.into())?
					.ensure_div(pool_info.total_tokens_staked)?,
			)?)
		}
