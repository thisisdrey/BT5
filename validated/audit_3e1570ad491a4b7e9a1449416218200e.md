Confirmed: `initial_nonce_value` sets a re-added key's nonce floor to `(block_height - 1) * ACCESS_KEY_NONCE_RANGE_MULTIPLIER` [1](#0-0) , used both for regular keys via `add_regular_key` [2](#0-1)  and gas keys [3](#0-2) . `validate_delegate_action_key` allows any nonce that is strictly greater than the stored `current_nonce` and strictly less than `apply_state.block_height * ACCESS_KEY_NONCE_RANGE_MULTIPLIER` [4](#0-3) , and the nonce-vs-window design intent is explicitly documented as being "to avoid tx hash collision on access key re-creation," referencing near/nearcore#3779 [5](#0-4) .

### Title
DeleteKey+AddKey re-key at the same block height reopens the previous nonce window, enabling DelegateAction replay - (File: runtime/runtime/src/access_keys.rs, core/primitives-core/src/account.rs)

### Summary
When an access key is deleted and re-added with the same public key at block height `H`, the new key's nonce floor is initialized to `(H-1) * 1e6`, one window below the current height's upper bound `H * 1e6`. Any previously executed `DelegateAction` whose nonce falls in `((H-1)*1e6, H*1e6)` — the only legal range at height `H` — becomes valid again against the freshly re-created key, since the strictly-greater-than check compares only against the new key's floor, not against the set of nonces actually consumed by the old incarnation of the key.

### Finding Description
`validate_delegate_action_key` only enforces two conditions on `delegate_action.nonce`: it must be `> current_nonce` (the value stored on the access key) and `< apply_state.block_height * ACCESS_KEY_NONCE_RANGE_MULTIPLIER` [4](#0-3) . There is no per-nonce replay-protection set; the only state carried forward is the single scalar `current_nonce`, updated to the just-used nonce on success [6](#0-5) .

At block height `H`, the legal nonce range for any key is `(prev_nonce, H*1e6)`. An attacker (the account owner acting as its own relayer target, or a relayer that retains copies of `SignedDelegateAction`s it forwarded) can drive `current_nonce` up to just under `H*1e6` by submitting a rapid burst of DelegateActions with nonces packed near the top of the window — nothing rate-limits this, only the monotonic/upper-bound checks apply.

The attacker then submits `DeleteKey` followed by `AddKey` for the same public key, in the same block height `H` (both are ordinary, unprivileged actions the account owner can always perform on its own keys, subject to `check_actor_permissions` allowing `actor_id == account_id` [7](#0-6) ). `add_regular_key` (or `add_gas_key`) re-initializes the new key's nonce to `initial_nonce_value(H) = (H-1)*1e6` [1](#0-0) [2](#0-1) .

Any previously-consumed, previously-signed `SignedDelegateAction` with a nonce `N` satisfying `(H-1)*1e6 < N < H*1e6` (which is exactly the legal range the attacker filled up in the burst phase) now again satisfies `N > current_nonce = (H-1)*1e6` and `N < upper_bound = H*1e6` (or any later height's larger upper bound). Because the signature on `SignedDelegateAction` is over the original `DelegateAction` fields (including `nonce`) and does not encode any binding to the access key's "incarnation" or a global replay set, the old signed payload validates and executes again. The design intent stated in the code comment — using `(block_height-1)*1e6` "to avoid tx hash collision on access key re-creation" — does not account for the case where re-creation happens in the *same* window as the key's prior usage; it only prevents collision with nonces from *older* windows, not the currently active one.

### Impact Explanation
This permits replay of any DelegateAction whose payload had value-transferring or state-mutating effects (e.g., `Transfer`, `FunctionCall` triggering token movement) executed via that access key just before deletion, causing double execution of an already-settled action — a direct violation of value conservation. This maps to a "theft or permanent freezing of user funds" / "double-spend / replay" bounty category, since an entity holding a copy of an old signed meta-transaction (e.g., a relayer who was paid to forward it, or an attacker who intercepted it) can replay it against the account after it re-keys, extracting funds or effects the account owner did not intend to trigger again.

### Likelihood Explanation
The attack requires: (1) an entity possessing an old, already-executed `SignedDelegateAction` (any relayer that forwarded it, since relayers must have full copies to submit them), and (2) the targeted account performing an ordinary `DeleteKey`+`AddKey` re-key of the same public key at (or very near) the block height where nonces near the window ceiling were last used. Filling the nonce window near the ceiling is trivial (unprivileged, cheap, no rate limit beyond normal gas/tx fees). Re-keying with the identical public key is a normal user action (e.g., rotating access, or scripted key rotation) and is fully within attacker/victim control if the attacker is also the account owner colluding with a malicious relayer, or if a compromised/malicious relayer times its replay to coincide with the victim's re-key. This is repeatable for every re-key event and does not require any privileged role.

### Recommendation
Do not derive the new key's nonce floor purely from the current block height. Either (a) always initialize newly added regular/gas keys' nonce floor as `max(current_block_height, previous_deletion_height + 1) * ACCESS_KEY_NONCE_RANGE_MULTIPLIER` rather than `(block_height - 1)`, ensuring the new key's floor is always at least as high as the ceiling of the window active when the same public key was last deleted, or (b) track a per-account-and-public-key high-water-mark for consumed nonces that persists across delete/re-add cycles (e.g., store it keyed by the public key hash outside the access key record itself, so recreation cannot reset it), or (c) bump the floor by a full window (`block_height * 1e6` instead of `(block_height-1)*1e6`) so a re-created key's floor is never below the ceiling of the block height at which it is created.

### Proof of Concept
Rust unit/integration test plan (extending `runtime/runtime/src/access_keys.rs` and `runtime/runtime/src/actions.rs` test modules):
1. At block height `H`, create an access key with `nonce = (H-1)*1e6` (matching `initial_nonce_value(H)`).
2. Loop: construct and validate `SignedDelegateAction`s with strictly increasing nonces `N_1 < N_2 < ... < N_k`, all satisfying `(H-1)*1e6 < N_i < H*1e6`, via `validate_delegate_action_key`, asserting each succeeds and updates `access_key.nonce`.
3. Call `action_delete_key` for the same public key, then `action_add_key` with the same public key at the same `apply_state.block_height = H`.
4. Re-run `validate_delegate_action_key` for each previously-used nonce `N_i` (still `< H*1e6`) against the freshly re-created key.
5. Assert: expected behavior is `Err(DelegateActionInvalidNonce)` for all `N_i` (i.e., replay should be rejected); actual behavior with current code is `Ok(())` for every `N_i > (H-1)*1e6`, proving the replay succeeds — the count of nonces that validate again equals the full consumed set, not zero.

pub(crate) fn initial_nonce_value(block_height: BlockHeight) -> Nonce {
    // Set default nonce for newly created access key to avoid transaction hash collision.
    // See <https://github.com/near/nearcore/issues/3779>.
    (block_height - 1) * near_primitives::account::AccessKey::ACCESS_KEY_NONCE_RANGE_MULTIPLIER
}
