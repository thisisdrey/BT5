### Title
StackerDB chunk sync accepts replies for a different slot than requested (no requested-vs-returned slot binding) - (File: stackslib/src/net/stackerdb/sync.rs)

### Summary
`StackerDBSync::getchunks_try_finish` matches inbound `StackerDBChunk` replies to outstanding requests solely by `NeighborAddress`, not by the `slot_id` that was actually requested from that peer. A malicious replica can therefore answer a `StackerDBGetChunk` request for slot `Y` with a validly-signed `StackerDBChunkData` for a different slot `X` that it legitimately owns, and the node will accept and store it via `add_downloaded_chunk`.

### Finding Description
In `getchunks_begin` (stackslib/src/net/stackerdb/sync.rs:1082-1097), a `StackerDBGetChunk(chunk_request)` for a specific `slot_id`/`slot_version` is sent to `selected_neighbor`, and the reply handle is tracked keyed only by `NeighborAddress` via `self.comms.neighbor_send` → `add_batch_request` [1](#0-0) .

When replies are collected in `PeerNetworkComms::collect_replies` / `drive_socket_io`, the returned `(NeighborAddress, StacksMessage)` pairs are produced purely from the per-neighbor `ReplyHandleP2P` map — there is no correlation stored or checked against which `slot_id` was requested of that neighbor [2](#0-1) [3](#0-2) .

Back in `getchunks_try_finish`, the received `StackerDBChunk(data)` is validated only via `self.validate_downloaded_chunk(network, config, &data)`, which — per the question's provided scope and the code structure — checks `data.slot_id`'s version/signature against `self.expected_versions` (a per-contract slot table), not against the specific `slot_id` that was requested from that particular `naddr`. If validation passes, the chunk is stored immediately with `self.add_downloaded_chunk(naddr, data)` [4](#0-3) .

Because the binding is "any validly-signed slot in this contract" rather than "the exact slot asked of this peer," an attacker who legitimately owns slot `X` in the target StackerDB contract can respond to a `StackerDBGetChunk` for slot `Y` by returning a `StackerDBChunk` for slot `X` (signed by themselves, entirely valid for slot `X`). The signature/version check in `validate_downloaded_chunk` succeeds since it is evaluated using `data.slot_id` (`X`) against `expected_versions[X]`, not against the requested slot `Y`, so `getchunks_try_finish` accepts and stores the chunk.

### Impact Explanation
This does not let an attacker forge writes to a slot they don't own — the signature is still checked against the real owner of `data.slot_id`. The concrete effect is a mismatch/confusion in the chunk-download bookkeeping: the sync state machine's per-request/per-slot tracking can be satisfied by an unrelated (but validly signed) chunk, letting an attacker manipulate which chunks get "completed" during a sync round and interfere with the deterministic download schedule (e.g., causing legitimate slot `Y` to never be fetched while artificially satisfying bookkeeping with slot `X`'s data). This is a logic/availability degradation of the StackerDB replication protocol rather than an unauthenticated write of forged content into an unauthorized slot, since the data stored for slot `X` is genuinely signed by slot `X`'s real owner.

### Likelihood Explanation
The attacker must control a P2P-reachable node and legitimately own at least one slot in the same StackerDB contract, both of which are within the stated unprivileged-attacker capability (no secret, no other-owner key, no admin role required). The attack is fully remote, requires no bandwidth flooding, and is repeatable on every download round against any peer that queries the attacker as a replica.

### Recommendation
When collecting replies in `getchunks_try_finish`, bind the expected `slot_id` (and `slot_version`) to each in-flight request per neighbor (e.g., track `(NeighborAddress -> requested slot_id)` alongside the reply handle), and reject/drop any `StackerDBChunk` reply whose `data.slot_id` does not match the slot that was actually requested from that `naddr`, in addition to the existing version/signature checks in `validate_downloaded_chunk`.

### Proof of Concept
1. Set up a `StackerDBSync` instance with a mocked/test `PeerNetwork` and two slot owners: `slot_Y` (the node wants) and `slot_X` (attacker-controlled).
2. Populate `chunk_fetch_priorities` such that a `StackerDBGetChunk` request for `slot_id = Y` is sent to the attacker-controlled `NeighborAddress` via `getchunks_begin`.
3. Instead of driving real socket I/O, inject a crafted `StacksMessage` whose payload is `StacksMessageType::StackerDBChunk(data)` where `data.slot_id = X`, `data.slot_version` and `data.sig` are validly signed by `X`'s real private key, returned from the same `naddr` that was asked for slot `Y` (i.e., mock `comms.collect_replies` to return `(naddr_of_attacker, msg_with_slot_X)`).
4. Call `getchunks_try_finish(&mut network, &config)`.
5. Assert that `self.chunk_invs`/downloaded-chunks bookkeeping (`add_downloaded_chunk`) now contains an entry for slot `X` in response to a request that was issued for slot `Y`, demonstrating that `validate_downloaded_chunk` (stackslib/src/net/stackerdb/sync.rs:1164) accepted the mismatched slot and no code path compared `data.slot_id` against the specific slot requested of `naddr`.

    /// Drive socket I/O on all outstanding messages and gather up any received messages.
    /// Remove handled messages from `state`, and perform the polling (and bookkeeping of dead/broken neighbors) via `neighbor_set`
    fn drive_socket_io<NS: NeighborComms>(
        network: &mut PeerNetwork,
        state: &mut HashMap<NeighborAddress, ReplyHandleP2P>,
        neighbor_set: &mut NS,
    ) -> Vec<(NeighborAddress, StacksMessage)> {
        let mut inflight = HashMap::new();
        let mut ret = vec![];
        let stable_block_height = network.get_chain_view().burn_stable_block_height;
        for (naddr, rh) in state.drain() {
            let mut req_opt = Some(rh);
            let message = match neighbor_set.poll_next_reply(network, &naddr, &mut req_opt) {
                Ok(Some(msg)) => msg,
                Ok(None) => {
                    if let Some(rh) = req_opt {
                        // keep trying
                        debug!("{:?}: keep polling {}", network.get_local_peer(), naddr);
                        inflight.insert(naddr, rh);
                    }
                    continue;
                }
                Err(_e) => {
                    // peer was already marked as dead in the given network set
                    debug!(
                        "{:?}: peer {} is dead: {:?}",
                        network.get_local_peer(),
                        naddr,
                        &_e
                    );
                    continue;
                }
            };

            if NeighborCommsRequest::is_message_stale(&message, stable_block_height) {
                debug!(
                    "{:?}: Remote neighbor {:?} is still bootstrapping (at block {})",
                    &network.get_local_peer(),
                    &naddr,
                    message.preamble.burn_stable_block_height
                );
                continue;
            }

            ret.push((naddr, message));
        }
        state.extend(inflight);
        ret
    }
