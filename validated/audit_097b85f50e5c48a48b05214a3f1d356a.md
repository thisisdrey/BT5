### Title
Unauthenticated peer response accepted into `AttachmentsBatchStateContext::attachments` without content-hash verification - (File: stackslib/src/net/atlas/download.rs)

### Summary
`AttachmentsBatchStateContext::extend_with_attachments` decodes a peer's HTTP response and inserts `response.attachment` directly into `self.attachments` (a `HashSet<Attachment>`) with no check that `response.attachment.hash() == request.content_hash`. Since `Attachment`'s `Hash`/`Eq` are derived over the full byte content rather than the intended content hash, any peer answering an `AttachmentRequest` can supply arbitrary bytes and have them accepted as a "successful" response for that content hash.

### Finding Description
The claimed equality — "one `content_hash` maps to one canonical `Attachment`" — is not enforced at the point content is admitted into the download context. The relevant code: [1](#0-0) 

For every `(request, response)` pair in `results.succeeded`, once `response.decode_atlas_get_attachment()` succeeds, `self.attachments.insert(response.attachment)` runs unconditionally — there is no comparison of the decoded attachment's real hash against `request.content_hash`. Because `self.attachments` is a `HashSet<Attachment>` keyed by the full attachment content (not by the `content_hash` the request was made for), a malicious peer among `AttachmentsBatchStateContext::peers` can respond to a `GET /attachment/{content_hash}` request with any payload it likes: the decode step only validates HTTP/wire framing, not that the payload actually hashes to the requested `content_hash`. That forged `Attachment` is admitted into the set as if it were a validated, successful response, and `report.bump_successful_requests()` even rewards the malicious peer's reliability score.

### Impact Explanation
This allows an unprivileged remote peer that a node happens to query (selected from its own peer/inventory bookkeeping, not requiring any special role) to inject attacker-chosen bytes into the node's in-memory attachment/BNS content resolution pipeline for a given `content_hash`, without the framework verifying the content actually matches that hash at the point of ingestion into `self.attachments`. Multiple peers can supply different payloads for the same `content_hash`; because `HashSet<Attachment>` dedups on full content rather than on `content_hash`, distinct forged/legitimate attachments for the same request can co-exist in the set, and whichever entry downstream consumers pick up (e.g., by iteration order) becomes what the node treats as satisfying that `content_hash`. This is a BNS/attachment integrity break: content served/propagated for a name may not be the content actually committed on-chain, matching the "attachment/BNS mismatch" High-impact category.

### Likelihood Explanation
Any peer the node has in its `AttachmentsBatchStateContext::peers` map (built from its own peer inventory-tracking, reachable simply by being a P2P peer of the node) can trigger this by answering an outgoing attachment-fetch request with arbitrary content instead of the real attachment — no secret, StackerDB slot, or privileged role is required, just running a peer that responds to the node's HTTP GET for the attachment. The attack is repeatable per attachment fetch cycle.

### Recommendation
In `extend_with_attachments`, verify `response.attachment.hash() == request.content_hash` before calling `self.attachments.insert(...)`; on mismatch, treat it as a failed request (`report.bump_failed_requests()`), and consider penalizing/deregistering the offending peer. Additionally, key `self.attachments` (or an intermediate map) by `content_hash` rather than relying on `Attachment`'s derived `Hash`/`Eq` over raw content, so that lookups by `content_hash` cannot silently be satisfied by unverified content.

    pub fn extend_with_attachments(
        mut self,
        results: &mut BatchedRequestsResult<AttachmentRequest>,
    ) -> AttachmentsBatchStateContext {
        for (request, response) in results.succeeded.drain() {
            let report = self
                .peers
                .get_mut(request.get_url())
                .expect("Atlas: unable to retrieve reliability report for peer");

            let response = if let Some(r) = response {
                r
            } else {
                report.bump_failed_requests();
                continue;
            };

            if let Ok(response) = response.decode_atlas_get_attachment() {
                self.attachments.insert(response.attachment);
                report.bump_successful_requests();
            } else {
                report.bump_failed_requests();
            }
        }
        let mut events_ids = results.faulty_peers.keys().copied().collect::<Vec<usize>>();
        self.events_to_deregister.append(&mut events_ids);

        self
    }
