### Title
Arbitrary Git config injection via `git_config_options` enables `uploadpack.packObjectsHook` RCE when pack-objects cache is disabled - ([File: internal/git/gitcmd/command_options.go])

### Summary
Multiple gRPC RPCs (`PostUploadPackWithSidechannel`, `SSHUploadPackWithSidechannel`, `PostReceivePack`, `SSHReceivePack`, `InfoRefsUploadPack`/`InfoRefsReceivePack`) accept a client-controlled `repeated string git_config_options` field [1](#0-0) . These raw `key=value` strings are converted directly into `git -c` config pairs with no allow-list/deny-list of keys — only a generic syntax check is applied.

### Finding Description
`ConvertConfigOptions` splits each user-supplied string on `=` and builds a `ConfigPair` without checking the key against any denylist: [2](#0-1) 

The only validation applied later is `GitConfig.Validate()` / `ConfigPair.GlobalArgs()`, which merely enforces syntactic shape (must contain a dot, no `=`, no leading/trailing dot, matches a generic regex) — it never restricts *which* config keys are settable: [3](#0-2) 

These attacker-supplied `ConfigPair`s are merged with Gitaly's own internal "trusted" config pairs into the same `-c` argument list passed to `git upload-pack` / `git receive-pack`: [4](#0-3) [5](#0-4) 

Critically, `uploadpack.packObjectsHook` — the Git option that governs which external command is invoked to generate the pack for a fetch/clone — is set by Gitaly *only when the pack-objects cache feature is enabled*, via `WithPackObjectsHookEnv`, and this call happens *after* `WithConfig(gitConfig...)` in the option chain so it would normally override any duplicate key on the command line: [6](#0-5) [7](#0-6) 

If `PackObjectsCache.Enabled` is `false` (the default unless an administrator opts in), `WithPackObjectsHookEnv` returns immediately without appending any config pair at all: [8](#0-7) 

In that case, nothing overrides an attacker-supplied `uploadpack.packObjectsHook=<arbitrary command>` config pair injected through `GitConfigOptions`. Because Git treats `-c`/`GIT_CONFIG_*` (command-line) configuration as the highest-trust scope — the very scope Git normally uses to allow `uploadpack.packObjectsHook` at all, since it disallows this option from *repository*-level config for exactly this security reason — smuggling it through Gitaly's `-c` mechanism effectively bypasses Git's own protection against this option being set by an untrusted party. The result is that any ordinary client performing an upload-pack style operation (`git fetch`/`git clone` over SSH or HTTP, or even an `InfoRefsUploadPack` ref advertisement) can direct `git-upload-pack` to execute an arbitrary program on the Gitaly host during the pack-objects generation phase.

This is the direct structural analog of the reported lodash prototype-pollution class: an untrusted, attacker-controlled key/value pair is merged into a privileged object (here, Git's runtime configuration store for the spawned process) without validating that the key does not correspond to a security-sensitive property, ultimately allowing full compromise of behavior that only a trusted actor should control.

### Impact Explanation
If `uploadpack.packObjectsHook` (and similarly other repository-config-restricted options such as `core.fsmonitor`, `core.sshCommand`, `protocol.*.allow`, or `include.path`) can be forced onto the command line by an ordinary user performing a Git fetch/clone, this constitutes remote code execution on the Gitaly host, running as the `git` service user. This is a critical-impact analog of config/argument injection reachable from a completely ordinary, unprivileged client action (a `git clone`/`git fetch`).

### Likelihood Explanation
Exploitability is conditioned on `PackObjectsCache.Enabled = false` (a common/default state) so that the internal override in `WithPackObjectsHookEnv` never fires. I was not able to fully confirm from the indexed source whether `git-upload-pack` itself additionally restricts `uploadpack.packObjectsHook` when specified purely via `-c` scope from a non-interactive invocation (Git's own protected-config mechanism is nuanced, and Gitaly's process passes `-c` flags as if it were the trusted top-level Git invoker). This uncertainty should be validated experimentally against the actual Git behavior (e.g., does upstream Git honor `uploadpack.packObjectsHook` when only supplied via `-c`, or does it require it to originate from `$HOME/.gitconfig`/`/etc/gitconfig`?). If Git does honor it from `-c`, likelihood is high given the trivial reachability (a single crafted RPC field on a normal fetch). If Git refuses `-c`-scoped `uploadpack.packObjectsHook`, the primary residual risk narrows to lower-impact config injection (e.g., DoS via `receive.maxInputSize=1`-style keys, or ref-hiding/security-control bypass such as `uploadpack.hideRefs`/`transfer.hideRefs`, which the existing tests already demonstrate as intentionally client-controllable) rather than RCE.

### Recommendation
- Introduce an explicit allow-list (rather than a syntax-only validator) for keys permitted via `GitConfigOptions` in `ConvertConfigOptions`, restricting to the small set of options genuinely intended to be client-influenced (e.g., `uploadpack.hideRefs`, `transfer.hideRefs`, documented push/fetch negotiation knobs).
- Explicitly reject or strip any client-supplied config pair matching known security-sensitive keys (`uploadpack.packObjectsHook`, `core.fsmonitor`, `core.sshCommand`, `*.proxy`, `protocol.*.allow`, `include.path`, `core.hooksPath`, etc.) before merging with Gitaly's own trusted configuration.
- Ensure trusted, Gitaly-set config pairs (like `uploadpack.packObjectsHook`) are always applied last/authoritatively regardless of whether `PackObjectsCache.Enabled` is true, or otherwise ensure the attacker cannot set that key at all when the feature is off.

### Proof of Concept
Not executed against a live Gitaly instance (no filesystem/terminal access in this environment) — this requires a background Devin session to validate against real `git-upload-pack` behavior. Conceptually:
1. Configure a Gitaly instance with `pack_objects_cache.enabled = false` (default).
2. As an ordinary authenticated Git user, issue `SSHUploadPackWithSidechannel` or `PostUploadPackWithSidechannel` with:
   `GitConfigOptions: ["uploadpack.packObjectsHook=/bin/sh -c 'id > /tmp/pwned' #"]`
3. Perform a normal `git fetch`/`git clone` against the repository to trigger pack generation.
4. Observe whether `/tmp/pwned` is created on the Gitaly host, confirming command execution outside the sandboxed pack-objects hook path. [9](#0-8)

// ConvertConfigOptions converts `<key>=<value>` config entries into `ConfigPairs`.
func ConvertConfigOptions(options []string) ([]ConfigPair, error) {
	configPairs := make([]ConfigPair, len(options))

	for i, option := range options {
		configPair := strings.SplitN(option, "=", 2)
		if len(configPair) != 2 {
			return nil, fmt.Errorf("cannot convert invalid config key: %q", option)
		}

		configPairs[i] = ConfigPair{Key: configPair[0], Value: configPair[1]}
	}

	return configPairs, nil
}

		return cfgerror.NewValidationError(cfgerror.ErrNotSet, "key")

// WithPackObjectsHookEnv provides metadata for gitaly-hooks so it can act as a pack-objects hook.
func WithPackObjectsHookEnv(objectHash git.ObjectHash, repo *gitalypb.Repository, protocol string) CmdOpt {
	return func(ctx context.Context, cfg config.Cfg, gitCmdFactory CommandFactory, cc *cmdCfg) error {
		if !cfg.PackObjectsCache.Enabled {
			return nil
		}

		if repo == nil {
			return fmt.Errorf("missing repo: %w", ErrInvalidArg)
		}

		userDetails := &UserDetails{
			Protocol: protocol,
			UserID:   metadata.GetValue(ctx, "user_id"),
			Username: metadata.GetValue(ctx, "username"),
			RemoteIP: metadata.GetValue(ctx, "remote_ip"),
		}

		if err := cc.configureHooks(
			ctx,
			cfg,
			objectHash,
			repo,
			gitCmdFactory,
			userDetails,
			PackObjectsHook,
		); err != nil {
			return fmt.Errorf("pack-objects hook configuration: %w", err)
		}

		cc.globals = append(cc.globals, ConfigPair{
			Key:   "uploadpack.packObjectsHook",
			Value: cfg.BinaryPath("gitaly-hooks"),
		})

		return nil
	}
}
