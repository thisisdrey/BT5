### Title
Vault deposit/repay accounting trusts nominal transfer amount without verifying actual balance received, enabling asset-ledger inflation if the underlying token ever deducts a fee - (File: `mainnet/contracts/vault/v0-vault-usdh.clar`, and identically in `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-stx.clar`, `v0-vault-usdc.clar`, `v0-vault-ststxbtc.clar`)

### Summary
Every Zest vault's `deposit` and `system-repay` functions call `receive-underlying`, which does a SIP-010 `transfer` for the caller-supplied `amount`, and then unconditionally credits the vault's internal `assets` accounting variable (and mints shares) using that same nominal `amount` — with no check that the vault's actual token balance increased by `amount`.

### Finding Description
In `deposit`, the vault computes shares from the requested `amount` via `convert-to-shares-preview`, transfers `amount` in via `receive-underlying`, then does `(var-set assets (+ current-assets amount))` and `(ft-mint? zft inkind recipient)`, all without ever comparing against the actual token balance held by the vault: [1](#0-0) 

`receive-underlying` simply performs the transfer and returns `(ok true)`, with no balance-before/balance-after verification: [2](#0-1) 

Each vault defines a `ubalance` helper that reads the actual on-chain balance of the underlying token held by the vault, but this helper is never invoked anywhere in the codebase outside its own definition (confirmed by repo-wide search) — it is dead code, meaning the vault's real custodied balance is never cross-checked against the internal `assets`/`total-assets` bookkeeping used for pricing shares: [3](#0-2) 

`total-assets`, `total-assets-preview`, and `get-available-assets` (used to compute share price and redemption limits) are derived purely from the internal `assets` variable, not from the true on-chain balance: [4](#0-3) 

The same `system-repay` pattern applies: `capped-amount` is transferred in via `receive-underlying`, and `assets` is incremented by `interest-paid` computed from the nominal amount, again without verifying the actually received balance: [5](#0-4) 

If the underlying token (`sbtc-token`, `ststx-token`, `usdcx`, wrapped STX, `stSTXbtc`) ever deducts a transfer fee — either because such a fee already exists or is enabled later by that token's own upstream contract/bridge logic (which is external to Zest and not a DAO action on Zest's own registries) — the vault will (a) mint shares based on the full nominal amount even though fewer tokens actually arrived, and (b) permanently inflate its `assets` ledger above the real custodied balance. This is the same root-cause bug class as the referenced report (Vault trusts `amount` transferred rather than verifying tokens actually received), except unlike Sandclock's `_transferAndCheckUnderlying`, Zest performs **no check at all**, so the failure mode is not a revert/DoS but a silent, permanent over-crediting of the internal asset ledger and share-minting.

### Impact Explanation
Once `assets` is inflated relative to the vault's real token balance, every subsequent `redeem` computes `inkind` (the underlying amount to pay out) from the inflated `total-assets`/`total-supply` ratio via `convert-to-assets-preview`. Early redeemers can withdraw more real underlying than they are entitled to, draining the actual on-chain balance before all shares are redeemed. Later redeemers then find `available-assets`/`ubalance` (never even checked) insufficient, and the tail depositors' funds become permanently unrecoverable — this lands squarely on **permanent freezing of funds** and, since it also lets earlier actors extract more of the pooled underlying than they deposited, on **protocol insolvency / theft of funds at rest** for the remaining shareholders.

### Likelihood Explanation
The likelihood is inherently tied to whether any of the six hardcoded underlying tokens (`sbtc-token`, `ststx-token`, `usdcx`, wrapped-STX, `usdh`, `stSTXbtc`) ever charges a transfer fee — this is a property of those external token contracts, not something an attacker can trigger on demand within Zest's own code. I could not verify from the indexed contracts whether any of these specific tokens currently implement or could later implement such a fee; this is a precondition outside Zest's contracts. Given the rules exclude "external stablecoin depegs / third-party token issues the attacker did not cause through a bug here," and no in-scope Zest logic path lets an unprivileged principal cause the underlying token to apply a transfer fee, the actual exploitability strictly depends on external token behavior Zest does not control, so the likelihood of this being independently triggerable by an ordinary principal is low/uncertain.

### Recommendation
After calling `receive-underlying`, read the vault's actual token balance (e.g., via the existing but unused `ubalance` helper) before and after the transfer, and use the observed delta — not the nominal `amount` parameter — when computing `inkind` (shares to mint) and incrementing `assets`. Apply the same before/after balance-delta pattern in `system-repay`.

### Proof of Concept
1. Assume (hypothetically) the underlying SIP-010 token used by a Zest vault applies a transfer fee `f` (e.g., due to an upgrade of that external token contract).
2. Depositor calls `deposit` with `amount = A`, `min-out = 0`.
3. `convert-to-shares-preview A` computes shares based on the full `A`; `receive-underlying A account` transfers `A`, but the vault only actually receives `A - f`.
4. Vault executes `(ft-mint? zft inkind recipient)` for shares based on `A`, and `(var-set assets (+ current-assets A))`, crediting `A` instead of `A - f`.
5. `total-assets` is now `f` higher than the vault's real token balance (unverifiable since `ubalance` is never called).
6. Repeated deposits compound this drift; eventually a `redeem` call succeeds in minting a payout via `send-underlying` that the vault cannot actually cover from its real balance, causing later redeemers' transactions to fail permanently (funds frozen) once the real balance is exhausted.
