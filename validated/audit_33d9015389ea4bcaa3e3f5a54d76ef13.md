Audit Report

## Title
Delivery-receipt reward payout ignores `DeliveryReceipt.success`, closing `PendingOrder`s and rewarding relayers even when the bridged message failed on Ethereum - (File: `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs`)

## Summary
`process_delivery_receipt` decodes a `DeliveryReceipt` containing an explicit `success: bool` field (sourced from Ethereum's `InboundMessageDispatched` event) but never inspects it before calling `T::RewardPayment::register_reward` and removing the `PendingOrder` from storage. As a result, messages whose dispatched command reverted or failed on the Ethereum side are unconditionally treated as fully and successfully delivered.

## Finding Description
`submit_delivery_receipt` verifies the Ethereum event log/proof via `T::Verifier::verify`, decodes it into a `DeliveryReceipt` via `DeliveryReceipt::try_from`, and forwards it to `process_delivery_receipt` [1](#0-0) . The `DeliveryReceipt` struct is decoded directly from the Solidity `InboundMessageDispatched(uint64 indexed nonce, bytes32 topic, bool success, bytes32 reward_address)` event, explicitly carrying a `success` field populated from `event.success` [2](#0-1) .

`process_delivery_receipt` only checks the gateway address match and pending-nonce existence, then unconditionally pays `order.fee` to the reward account via `register_reward` and removes the order from `PendingOrders`, emitting `MessageDelivered` [3](#0-2) . A repository-wide search confirms `receipt.success` (or `.success` on this struct) is referenced nowhere else in the pallet or crate — it is decoded and then never read again. This violates the required invariant that message queues, bridge markers, receipts, and payout state must only advance after decode, dispatch, execution, and settlement succeed atomically.

## Impact Explanation
This directly matches the "duplicate settlement or payout" and "permanent... bridge-state lock" impact categories. The `PendingOrder` for a given `nonce` is irreversibly removed via `<PendingOrders<T>>::remove(nonce)` and the relayer reward is paid regardless of whether the corresponding command actually executed successfully on Ethereum. Since there is no other on-chain retry/reconciliation mechanism in this pallet once the order is removed, a legitimately failed cross-chain command (e.g., a reverted token unlock/mint or arbitrary command dispatch) is permanently recorded as "delivered" in parachain bookkeeping, with the relayer still fully rewarded, and no path to detect or correct the mismatch.

## Likelihood Explanation
This requires no privileged actor, malicious relayer, or compromised infrastructure — `submit_delivery_receipt` is an intentionally permissionless extrinsic callable by any signed account holding a valid Ethereum proof/log. A `success: false` outcome from the Gateway (e.g., due to out-of-gas or a reverted secondary command) is an expected, non-adversarial occurrence in cross-chain message passing, and any relayer submitting the resulting valid proof triggers the unconditional payout/removal path.

## Recommendation
Branch on `receipt.success` in `process_delivery_receipt` before finalizing settlement: on `true`, proceed as today; on `false`, avoid marking the order as fully settled — emit a distinct failure event, and ensure bookkeeping/retry logic reflects that the underlying command did not succeed rather than treating it identically to success.

## Proof of Concept
1. Ethereum Gateway dispatches a command for a given `nonce` but the command execution reverts, so the Gateway emits `InboundMessageDispatched(nonce, topic, success=false, reward_address)`.
2. Any unprivileged signed relayer builds an `EventProof` for this log and calls `submit_delivery_receipt` [1](#0-0) .
3. `DeliveryReceipt::try_from` decodes `success: false` into the receipt struct [4](#0-3) .
4. `process_delivery_receipt` ignores `receipt.success`, pays `order.fee`, removes `PendingOrders[nonce]`, and emits `MessageDelivered { nonce }` as if fully successful [5](#0-4) .
5. A unit test can construct a mock event log with `success: false`, call `submit_delivery_receipt`, and assert reward payment and order removal still occur — demonstrating the missing gate.

sol! {
	event InboundMessageDispatched(uint64 indexed nonce, bytes32 topic, bool success, bytes32 reward_address);
}

/// Delivery receipt
#[derive(Clone, Debug)]
pub struct DeliveryReceipt {
	/// The address of the outbound queue on Ethereum that emitted this message as an event log
	pub gateway: H160,
	/// The nonce of the dispatched message
	pub nonce: u64,
	/// Message topic
	pub topic: H256,
	/// Delivery status
	pub success: bool,
	/// The reward address
	pub reward_address: [u8; 32],
}

#[derive(Copy, Clone, Encode, Decode, Eq, PartialEq, Debug, TypeInfo)]
pub enum DeliveryReceiptDecodeError {
	DecodeLogFailed,
	DecodeAccountFailed,
}

impl TryFrom<&Log> for DeliveryReceipt {
	type Error = DeliveryReceiptDecodeError;

	fn try_from(log: &Log) -> Result<Self, Self::Error> {
		let topics: Vec<B256> = log.topics.iter().map(|x| B256::from_slice(x.as_ref())).collect();

		let event = InboundMessageDispatched::decode_raw_log_validate(topics, &log.data)
			.map_err(|_| DeliveryReceiptDecodeError::DecodeLogFailed)?;

		Ok(Self {
			gateway: log.address,
			nonce: event.nonce,
			topic: H256::from_slice(event.topic.as_ref()),
			success: event.success,
			reward_address: event.reward_address.0,
		})
	}
