### Title
Unverified attachment content is persisted to AtlasDB without checking `Attachment::hash()` against the requested `AttachmentInstance::content_hash` - (File: stackslib/src/net/atlas/download.rs)

### Summary
When `AttachmentsDownloader::run` reaches `AttachmentsBatchStateMachine::Done`, it iterates `context.attachments` and unconditionally calls `network.atlasdb.insert_instantiated_attachment(&attachment)` before checking whether `attachment.hash()` corresponds to any instance actually tracked in the batch. Because `extend_with_attachments` (lines 530-558) inserts whatever `Attachment` a peer returns into the `HashSet<Attachment>` without validating it against the `content_hash` of the `AttachmentRequest` that was sent, a malicious peer can serve arbitrary content for a requested hash and have it persisted verbatim.

### Finding Description
The claimed equality that should hold is: `Attachment::hash()` (hash of the bytes actually served by the remote peer) `== AttachmentInstance::content_hash` (the hash committed on-chain and tracked via `AttachmentsBatch::track_attachment`). Tracing the code:

- `AttachmentsBatchStateContext::extend_with_attachments` (`stackslib/src/net/atlas/download.rs:530-558`) takes an HTTP response from `decode_atlas_get_attachment()` and does `self.attachments.insert(response.attachment)` with no comparison of `response.attachment.hash()` to the `content_hash` field of the `AttachmentRequest` that produced this response. [1](#0-0) 

- In `AttachmentsDownloader::run`, once the FSM reaches `Done`, the code loops over the (unverified) attachments:
```
for attachment in context.attachments.drain() {
    let attachments_instances = network.atlasdb.find_all_attachment_instances(&attachment.hash())...;
    network.atlasdb.insert_instantiated_attachment(&attachment)...;
    for attachment_instance in attachments_instances.into_iter() { ... }
    context.attachments_batch.resolve_attachment(&attachment.hash())
}
``` [2](#0-1) 

`find_all_attachment_instances` and `resolve_attachment` are both keyed by `attachment.hash()` — the hash of the bytes the peer actually sent — not by the `content_hash` the request was originally made for. If the peer serves content whose hash differs from the requested `content_hash`, `find_all_attachment_instances(&attachment.hash())` returns an empty set (since no `AttachmentInstance` was ever tracked under that bogus hash) and `resolve_attachment` is effectively a no-op for that hash. However, `insert_instantiated_attachment(&attachment)` executes unconditionally *before* these lookups, so the bogus content is written to `AtlasDB` regardless of whether it pairs with any tracked instance.

The root cause is the complete absence of a hash-equality check between the served attachment and the specific `content_hash` the peer was asked to serve, anywhere along the `AttachmentRequest` → HTTP response → `extend_with_attachments` → `run` → `insert_instantiated_attachment` path.

### Impact Explanation
Any remote peer that a node queries for attachment content (an unprivileged outbound-sync peer serving the Atlas attachment HTTP endpoint) can return arbitrary bytes for a requested `content_hash` and have that content permanently written into `AtlasDB` via `insert_instantiated_attachment`, decoupled from any on-chain commitment. This breaks the served-hash == committed-content_hash invariant and results in state stored as if it were canonical/valid attachment data, while never being paired to the `AttachmentInstance` that justified downloading it in the first place. This is repeatable per attachment request across the peer's inventory responses, enabling incremental storage growth with content that was never validated against any contract-committed hash — matching the "High: attachment/BNS mismatch" impact category.

### Likelihood Explanation
- Preconditions: the node must have at least one unresolved `AttachmentInstance` it wants (normal operation), and the attacker must be selected as one of the `outbound_sync_peers` serving that URL/inventory (achievable simply by being a connected, gossiping peer offering the attachment in its `GetAttachmentsInvResponse`).
- Attacker cost: minimal — respond to a `GetAttachment` request with any payload; no secret, signature, or privileged role is required.
- Remote reachability: yes, via the standard Atlas attachment-fetch HTTP path over P2P/RPC.
- Repeatability: yes, on every attachment request the attacker's peer is selected for.

### Recommendation
In `AttachmentsBatchStateContext::extend_with_attachments`, verify `response.attachment.hash() == request.content_hash` before inserting into `self.attachments`; discard and treat as a faulty-peer response otherwise. As a defense-in-depth measure, also guard the `insert_instantiated_attachment` call in `AttachmentsDownloader::run` (`stackslib/src/net/atlas/download.rs:159-162`) so it only persists attachments whose hash matches an instance actually present in `attachments_instances` (i.e., move the insert after confirming `!attachments_instances.is_empty()` or that the hash was tracked in `attachments_batch.attachments_instances`).

### Proof of Concept
Rust test plan (in `stackslib/src/net/atlas/tests.rs` or a new test module in `download.rs`):
1. Build an `AttachmentsBatch` and call `track_attachment` with a real `AttachmentInstance` whose `content_hash = H_expected`.
2. Construct an `AttachmentsBatchStateContext` wrapped in `AttachmentsBatchStateMachine::Done`, and manually populate `context.attachments` with a forged `Attachment` whose `hash()` returns `H_forged != H_expected` (simulating a malicious `extend_with_attachments` result from a crafted HTTP response).
3. Call the body of `AttachmentsDownloader::run`'s `Done` branch logic (or invoke `run` end-to-end with a mocked `PeerNetwork`/`AtlasDB`).
4. Assert:
   - `network.atlasdb.find_attachment(&H_expected)` is `None` (the tracked instance was never satisfied).
   - `network.atlasdb.find_attachment(&H_forged)` returns `Some(forged_attachment)` — proving unpaired, unauthenticated content was persisted.
   - This demonstrates the BOUNDS/AUTHENTICATION violation: `AtlasDB` stores content under a hash with zero corresponding `AttachmentInstance`, contradicting the intended invariant enforced nowhere in the code path.
