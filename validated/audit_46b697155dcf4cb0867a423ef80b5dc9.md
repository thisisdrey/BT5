### Title
Gas key balance burn (`ActionResult::tokens_burnt`) is not rolled back with the trie state it was meant to reflect, when a later action in the same receipt fails - (File: `runtime/runtime/src/access_keys.rs`)

### Summary
`delete_gas_key` unconditionally adds a gas key's balance into `result.tokens_burnt` *before* any later action in the same receipt is processed, and this field lives on the in-memory `ActionResult` accumulator rather than in the `TrieUpdate`. If a receipt contains multiple `DeleteKeyAction`s and an earlier one succeeds while a later one hits the `GasKeyBalanceTooHigh` guard, `result.result` becomes `Err(...)` but `result.tokens_burnt` from the earlier successful deletion is never cleared.

### Finding Description
`delete_gas_key` (`runtime/runtime/src/access_keys.rs:93-134`) performs the `MAX_BALANCE_TO_BURN` check first [1](#0-0) , then, only for keys under the limit, adds the balance into the shared `result.tokens_burnt` accumulator and mutates the `TrieUpdate` (removing the gas key nonces and the access key itself) [2](#0-1) .

`action_delete_key` is invoked once per `DeleteKeyAction` in a receipt's action list [3](#0-2) . For a receipt with `[DeleteKeyAction(key1, under-limit), DeleteKeyAction(key2, over-limit)]`, processing key1 mutates `state_update` and adds `key1.balance` to `result.tokens_burnt`; processing key2 sets `result.result = Err(GasKeyBalanceTooHigh)` and returns without touching `tokens_burnt` or the trie for key2.

`result.tokens_burnt` is a plain struct field accumulated in-process (not something guarded by `TrieUpdate`'s prospective/committed distinction), so when the overall receipt is later marked as failed and the receipt-level state changes (the removal of key1's access key/nonces) are discarded/rolled back, there is no code path shown in `delete_gas_key`/`action_delete_key` that also resets `tokens_burnt` to reconcile it with the reverted trie state. This produces a divergence between "tokens counted as burnt" and "state that was actually changed" for key1: the key1 deletion (and its associated balance-in-storage) is rolled back, but the runtime has already recorded that its balance was burnt.

I was not able to fully trace, within this session's tool budget, the exact downstream code in `runtime/runtime/src/lib.rs` (`apply_action_receipt`/`ActionResult::merge`, and wherever `result.tokens_burnt` is folded into chunk-level supply/fee accounting or an explicit `state_update.rollback()` call) to confirm with certainty (a) whether the trie changes from key1 are indeed rolled back on receipt failure, and (b) whether `tokens_burnt` is unconditionally added to total-supply/burnt-balance accounting regardless of receipt success, the way gas fees are. Both of these are necessary to conclusively prove real token-supply corruption rather than an internal-only accounting artifact that is discarded along with the rest of the failed `ActionResult`.

### Impact Explanation
If confirmed, this would fall under token inflation/loss (permanent divergence between recorded "tokens burnt" and actual trie state) — a real value-conservation violation. However, I cannot certify the concrete loss without confirming the two open points above (state rollback scope and how/whether `tokens_burnt` is committed to supply accounting when the receipt as a whole fails).

### Likelihood Explanation
Preconditions are cheap and fully attacker-controlled: an ordinary account owner can create two or more of their own gas keys (one funded above `MAX_BALANCE_TO_BURN`, one funded below it) and submit a single receipt/transaction with `DeleteKeyAction`s ordered so the under-limit key is processed first. No special privileges are required.

### Recommendation
Given the uncertainty in fully verifying the downstream commit/rollback and supply-accounting interaction, the concrete fix — validating and moving forward with confidence — requires reviewing `apply_action_receipt` in `runtime/runtime/src/lib.rs` to confirm whether `TrieUpdate` prospective changes are discarded on receipt failure while `ActionResult::tokens_burnt`/`gas_burnt`-style fields are retained, and if so, either (a) validate all gas keys' balances against `MAX_BALANCE_TO_BURN` up front before processing any `DeleteKeyAction` in the receipt, or (b) ensure `tokens_burnt` accumulated so far is reset/reconciled whenever the receipt's trie changes are rolled back due to a later action failure.

### Proof of Concept
Not finalized — a definitive PoC requires first confirming, via `runtime/runtime/src/lib.rs`, whether (1) a failed action in a receipt actually triggers a rollback of previously-applied trie changes within that same receipt, and (2) whether `result.tokens_burnt` survives that rollback and is folded into total-supply/burnt-balance bookkeeping even when the receipt is reported as failed. I recommend a Devin session with full-repo access to trace `apply_action_receipt`, `ActionResult::merge`, and the receipt-failure handling path (including `TrieUpdate::rollback`/checkpoint usage) before writing the unit test, since the index available to me truncated `access_keys.rs` and did not surface the relevant `lib.rs` sections in full.

pub(crate) fn action_delete_key(
    config: &RuntimeConfig,
    state_update: &mut TrieUpdate,
    account: &mut Account,
    result: &mut ActionResult,
    account_id: &AccountId,
    delete_key: &DeleteKeyAction,
) -> Result<(), RuntimeError> {
    let access_key = get_access_key(state_update, account_id, &delete_key.public_key)?;
    if let Some(access_key) = access_key {
        if let Some(gas_key_info) = access_key.gas_key_info() {
            delete_gas_key(
                config,
                state_update,
                account,
                result,
                account_id,
                &delete_key.public_key,
                &access_key,
                gas_key_info,
            )?;
        } else {
            delete_regular_key(
                &config.fees,
                state_update,
                account,
                account_id,
                &delete_key.public_key,
                &access_key,
            );
        }
    } else {
        result.result = Err(ActionErrorKind::DeleteKeyDoesNotExist {
            public_key: delete_key.public_key.clone().into(),
            account_id: account_id.clone(),
        }
        .into());
    }
    Ok(())
}
