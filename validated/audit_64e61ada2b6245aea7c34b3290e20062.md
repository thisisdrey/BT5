### Title
Unbounded aggregation of child-bounty curator fees permanently strands treasury funds in the parent bounty account - (File: `substrate/frame/bounties/src/lib.rs`)

### Summary
The parent-bounty curator can set an unlimited number of child-bounty curator fees via `pallet_child_bounties::propose_curator`, each individually checked only against its own child-bounty value, never against the parent bounty's own `fee` budget. The cumulative sum (`ChildrenCuratorFees`) is later assumed to be `<= bounty.fee` inside `pallet_bounties::claim_bounty`, but that invariant is enforced only by a `debug_assert!`, which is compiled out in production (release) builds. When the invariant is violated, `claim_bounty` computes a `final_fee` of zero via `saturating_sub`, while the beneficiary `payout` is computed independently from the original `fee`, leaving the parent curator's fee amount permanently unaccounted for and stranded in the now-orphaned `bounty_account_id`.

### Finding Description
`propose_curator` for a child bounty only bounds the child fee against the child bounty's own value: [1](#0-0) 
There is no check anywhere that the running total in `ChildrenCuratorFees` stays below the parent bounty's `bounty.fee`. Because the parent curator (the same account that calls `propose_curator` for every child) can create as many child bounties as `MaxActiveChildBountyCount` allows and set each child's fee close to that child's own value, the accumulated `ChildrenCuratorFees::<T>::get(parent_bounty_id)` can exceed the parent's `bounty.fee` by an arbitrary margin — mirroring the external report's pattern of an unprivileged fee-setter combining values without an upper bound relative to the intended base allocation.

The only place this sum is checked against the parent fee is in `pallet_bounties::claim_bounty`: [2](#0-1) 
`debug_assert!(children_fee <= fee)` is a no-op in `--release`/`runtime-benchmarks`/production WASM builds because `debug-assertions` are disabled by default for release compilation. If the invariant is broken, `final_fee = fee.saturating_sub(children_fee)` silently becomes `0`, but `payout = balance.saturating_sub(fee)` was already computed using the original, larger `fee`, not accounting for the fact that `final_fee` collapsed to zero. The two transfers made are `final_fee` (0) to the curator and `payout` (`balance - fee`) to the beneficiary — the sum transferred is `balance - fee`, i.e., exactly `fee` short of the bounty account's actual `balance`. Immediately after, `*maybe_bounty = None;` removes the only on-chain reference to `bounty_account_id(bounty_id)`, so the stranded `fee` amount becomes permanently unreachable treasury-derived funds.

### Impact Explanation
This results in a permanent lock of treasury-sourced funds with no path to recovery, since the bounty record (and thus any future call referencing `bounty_id`) is deleted at the same time the shortfall occurs. This matches the explicitly accepted impact category "permanent user-fund or bridge-state lock." No malicious peer/validator/relayer/admin is required — only an ordinary bounty curator acting through the standard `propose_curator`/`accept_curator` child-bounty flow.

### Likelihood Explanation
Requires a bounty curator role (obtainable via normal `propose_curator`/`accept_curator` flow, not a privileged governance actor) and the ability to add multiple child bounties (bounded only by `MaxActiveChildBountyCount`), each with a fee set close to, but below, its own child-bounty value. This is entirely achievable with unprivileged, permissionless calls once a curator role is assigned by `T::SpendOrigin`/root through the bounty proposal flow; the exploit condition depends only on a release-mode build where `debug_assert!` is stripped, which is the standard configuration for production Substrate-based chains.

### Recommendation
Replace the `debug_assert!(children_fee <= fee)` in `claim_bounty` with a runtime-enforced invariant (`ensure!`/`saturating_sub` combined with clamping `payout` accordingly), and additionally enforce at `propose_curator` (child-bounties) time that `ChildrenCuratorFees::<T>::get(parent_bounty_id).saturating_add(fee) <= parent_bounty.fee`, mirroring the mitigation pattern of bounding an aggregated fee against its base allocation before it is committed.

### Proof of Concept
1. Create and fund a parent bounty with `value = 1000` and curator fee `bounty.fee = 100` (via `propose_curator`/`accept_curator`).
2. As the parent curator, call `add_child_bounty` several times to create child bounties whose combined `value` fits within the parent's remaining balance (e.g., 5 child bounties of `value = 150` each).
3. For each child bounty, call `propose_curator` with `fee` just under its own `value` (e.g., `fee = 140`), which passes `ensure!(fee < child_bounty.value, ...)` every time. Have each corresponding curator `accept_curator`.
4. `ChildrenCuratorFees::<T>::get(parent_bounty_id)` now accumulates to `5 * 140 = 700`, far exceeding the parent's `bounty.fee = 100`.
5. Award and claim the parent bounty via `award_bounty` → `claim_bounty`. In a release build, `debug_assert!(children_fee <= fee)` is skipped; `final_fee = 100.saturating_sub(700) = 0`; `payout` is computed as `balance - 100` (unaffected by the overrun). The transferred sum is short by `100` relative to `bounty_account`'s actual balance, and that amount is permanently stranded because the bounty record and its account reference are removed.
