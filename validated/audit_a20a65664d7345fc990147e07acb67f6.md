### Title
Optimistic StackerDB chunk-inventory advancement before durable storage creates a false-inventory / served-vs-committed mismatch - (File: `stackslib/src/net/stackerdb/mod.rs`)

### Summary
`PeerNetwork::handle_unsolicited_StackerDBPushChunk` builds a `StackerDBChunkInv` reply from the locally stored slot versions, then *patches that reply in memory* to reflect acceptance of a newly-pushed chunk — advancing the advertised slot version — before the chunk has actually been durably written via `StackerDBTx::try_replace_chunk`. The durable write only happens later, out-of-band, in the relayer (`process_stacker_db_chunks`/`process_pushed_stacker_db_chunks`). If that later write fails (e.g. the slot was concurrently updated to a version that makes this write stale), the peer has already told the network it holds a chunk version it never actually stored — an inventory pointer advanced ahead of, and potentially inconsistent with, verified persisted state.

### Finding Description
In `handle_unsolicited_StackerDBPushChunk` (stackslib/src/net/stackerdb/mod.rs:742-871):

1. `make_StackerDBChunksInv_or_Nack` builds `data.slot_versions` from the node's actual, currently-stored slot versions. [1](#0-0) 
2. The pushed chunk is validated only against this in-memory `data.slot_versions` snapshot via `validate_received_chunk` — a structural/signature/staleness check, not a persistence operation: [2](#0-1) 
3. On success, the reply's slot-version entry is optimistically mutated to the *pushed* chunk's version, with the comment explicitly noting "we'll accept this chunk" — before any call to `try_replace_chunk`: [3](#0-2) 
4. This function returns `(false, true)`, meaning: do not buffer, but forward to the relayer for actual processing — i.e., the durable write (`try_replace_chunk`) happens later, asynchronously, in `process_stacker_db_chunks` / `process_pushed_stacker_db_chunks`. [4](#0-3) 
5. The deferred write path independently re-validates freshness against the *current* DB state and can reject the chunk as stale if another chunk for the same slot was committed in the interim: [5](#0-4) 
6. When that rejection happens, `process_stacker_db_chunks` simply logs and `continue`s — it does not retract or correct the already-sent `StackerDBChunkInv` acknowledgment: [6](#0-5) 

The result is the same class of bug as the Taiko report: a pointer/index representing "the latest verified/committed state" (here, the advertised StackerDB slot version) is advanced based on an optimistic, not-yet-durable outcome, and can diverge from what is actually persisted if the later write does not land as expected.

### Impact Explanation
StackerDB inventory (`StackerDBChunkInvData`) is the mechanism peers use to decide what to fetch and relay (newest-first / rarest-first scheduling), as documented in the sync module. [7](#0-6) 
A node that advertises a chunk version it does not actually hold will cause: (a) inconsistent state across the replica set (a form of non-canonical state exposed as canonical for that slot/version), (b) neighbor download schedules built on the false inventory to under-fetch data they still need, delaying propagation of legitimate signer/miner coordination data carried over StackerDB, and (c) the remote peer that pushed the chunk to believe replication succeeded and stop retransmitting/broadcasting it, potentially causing legitimate chunk data to be lost from the network until the next independently-triggered chunk-inv exchange corrects the record. This matches the "steering a node off the tip via false inventory" / "serving non-canonical state as canonical" class explicitly called out as an in-scope High-severity impact for this hunt.

### Likelihood Explanation
This requires only an unprivileged remote peer to push two chunk updates for the same StackerDB slot with valid signer signatures in quick succession (e.g. exploiting normal contention between legitimate operators or an attacker replaying/racing writes for their own signing key), or triggering the deferred storage path's independent stale/max-writes checks to diverge from the in-memory snapshot used for the earlier optimistic ACK. No secret keys or privileged roles are required beyond authoring valid signer-key-signed chunks for a slot the peer legitimately owns (or a race window created by any two competing valid pushes to the same slot from different senders).

### Recommendation
Do not mutate/send the optimistic `StackerDBChunkInv` acknowledgment until after the chunk has been durably committed via `StackerDBTx::try_replace_chunk` succeeds. If the write pipeline must remain asynchronous (validate now, persist later in the relayer), track pending/unconfirmed slot versions separately from confirmed slot versions, and only patch/send the chunk-inv reply based on confirmed, persisted state — or defer sending the inv until the relayer's storage attempt result is known.

### Proof of Concept
1. Node A owns a StackerDB replica; slot `S` is currently at version `1`.
2. Peer B and Peer C independently (or a single attacker acting as two connections) each craft valid signer-signed `StackerDBPushChunkData` for slot `S`, versions `2` and `3` respectively.
3. Peer B's push (`v2`) arrives at Node A first: `handle_unsolicited_StackerDBPushChunk` validates it against the current inv (`v1`), passes, and immediately patches/sends back a `StackerDBChunkInv` claiming slot `S` is now at version `2` — before any DB write occurs.
4. Before the relayer processes and commits B's chunk, Peer C's push (`v3`) arrives and is fully processed end-to-end (validated + `try_replace_chunk` committed), advancing the DB to version `3`.
5. When the relayer later attempts to commit B's `v2` chunk via `try_replace_chunk`, it is rejected with `StaleChunk` (since stored version `3 > 2`) and silently dropped.
6. Net result: Node A already told Peer B (and any peer relaying that inv reply) that it holds version `2`, but it never actually stored version `2` at all — the advertised inventory pointer does not correspond to any committed chunk.
