### Title
Cross-repository object exposure via `LinkRepositoryToObjectPool` linking an arbitrary object pool to a caller-controlled repository - ([File: internal/gitaly/service/objectpool/link.go])

### Summary
`LinkRepositoryToObjectPool` accepts two independently-specified repository identifiers — `repository` (the pool member, `target_repository`) and `object_pool` (`additional_repository`) — and links the member's Git alternates to point at the pool's object directory. Gitaly's handler validates that `repository` is a legitimate repository and that `object_pool` is a *valid pool repository*, but it never verifies that the `object_pool` actually belongs to the same fork network / project as `repository`. This mirrors the reported bug class: a public operation acts on a caller-supplied resource identifier (an NFT id / here, an arbitrary pool relative path) without checking that the identifier is actually associated with the caller's own resource, allowing the caller to attach someone else's object store to their own.

### Finding Description
The RPC handler is: [1](#0-0) 

It calls `s.poolForRequest(ctx, req)` to resolve the `object_pool` field and then unconditionally links it: [2](#0-1) 

Resolution of the pool via `FromProto` only checks that the target path is a syntactically valid pool repository (path pattern / `IsValid`), not that it is the pool historically associated with the given `repository`: [3](#0-2) [4](#0-3) 

`Link` itself then simply writes the resolved pool's `objects` directory into the member repository's `objects/info/alternates` file, without any ownership/ancestry check between `pool` and `repo`: [5](#0-4) 

The proto definition confirms both fields are caller-supplied and only annotated for routing purposes (`target_repository` / `additional_repository`), not for cross-validation: [6](#0-5) 

Because Git alternates give full read access to every object in the alternate directory (this is precisely the mechanism the quarantine/alternates documentation describes as providing complete visibility into another object store), linking a repository to an arbitrary pool discloses that pool's entire object graph to anyone who can subsequently fetch/read from the member repository: [7](#0-6) 

### Impact Explanation
If a caller can invoke `LinkRepositoryToObjectPool` for a repository they control (e.g., their own project or fork) while supplying an `object_pool` value that resolves to a pool they do not own (which pools live in a predictable, discoverable `@pools/<hash>` layout, cf. `internal/gitaly/service/internalgitaly/scan_pool_metadata.go`), they can splice that pool's objects into their own repository via the alternates mechanism. All commits, blobs, and trees stored in that pool then become readable through the attacker's own repository — a direct cross-repository object disclosure of potentially private source code, independent of any subsequent repacking. This is the Gitaly-side equivalent of the reported issue: a destructive/state-changing operation is performed against a resource identifier supplied by the caller without validating that the identifier is actually tied to the resource the caller is authorized to act on.

### Likelihood Explanation
Exploitation requires only the ability to call the `ObjectPoolService.LinkRepositoryToObjectPool` mutator RPC for a repository the caller legitimately owns, plus knowledge (or brute-force enumeration) of another project's pool path. Gitaly itself performs no cross-repository ownership check at this layer, so the safety of this RPC depends entirely on an authorization check being enforced upstream (in GitLab Rails) that ties the two fields together — a check that is not visible in, or enforced by, the Gitaly codebase itself.

### Recommendation
Add a cross-check in `LinkRepositoryToObjectPool` (and `Link`) verifying that the resolved `object_pool` is actually the pool associated with `repository`'s own fork network/source project (e.g., via the same relative-path-derived pool mapping already used for other alternates checks, such as `storage.QuarantineDirectoryPrefix`-style provenance checks), rejecting the request if the two do not match, mirroring how `ObjectDirectoryPath` validates that a quarantine directory belongs to the requesting repository.

### Proof of Concept
1. Attacker has push/mutator access to `RepoA` (their own project), which has no pool yet.
2. Attacker discovers or guesses the relative path of `PoolB`, the object pool backing a private `RepoB` they do not have access to.
3. Attacker calls `LinkRepositoryToObjectPool(repository=RepoA, object_pool=PoolB)`.
4. Gitaly validates `RepoA` is a repo and `PoolB` is a valid pool repository, then writes `PoolB`'s `objects` path into `RepoA`'s `objects/info/alternates` (`internal/git/objectpool/link.go` lines 54–66).
5. Attacker fetches/reads from `RepoA`; any object hash from `PoolB` (i.e., from `RepoB`'s history) is now resolvable through `RepoA`, exposing `RepoB`'s private objects.

func (s *server) LinkRepositoryToObjectPool(ctx context.Context, req *gitalypb.LinkRepositoryToObjectPoolRequest) (*gitalypb.LinkRepositoryToObjectPoolResponse, error) {
	repository := req.GetRepository()
	if err := s.locator.ValidateRepository(ctx, repository); err != nil {
		return nil, structerr.NewInvalidArgument("%w", err)
	}

	pool, err := s.poolForRequest(ctx, req)
	if err != nil {
		return nil, err
	}

	repo := s.localRepoFactory.Build(repository)

	if err := pool.Link(ctx, repo); err != nil {
		return nil, structerr.NewInternal("%w", err)
	}

	return &gitalypb.LinkRepositoryToObjectPoolResponse{}, nil
}

// FromProto returns an object pool object from its Protobuf representation. This function verifies
// that the object pool exists and is a valid pool repository.
func FromProto(
	ctx context.Context,
	logger log.Logger,
	locator storage.Locator,
	gitCmdFactory gitcmd.CommandFactory,
	catfileCache catfile.Cache,
	txManager transaction.Manager,
	housekeepingManager housekeepingmgr.Manager,
	proto *gitalypb.ObjectPool,
) (*ObjectPool, error) {
	poolPath, err := locator.GetRepoPath(ctx, proto.GetRepository(), storage.WithRepositoryVerificationSkipped())
	if err != nil {
		return nil, err
	}

	if !storage.IsPoolRepository(proto.GetRepository()) {
		// When creating repositories in the ObjectPool service we will first create the
		// repository in a temporary directory. So we need to check whether the path we see
		// here is in such a temporary directory and let it pass.
		tempDir, err := locator.TempDir(proto.GetRepository().GetStorageName())
		if err != nil {
			return nil, fmt.Errorf("getting temporary storage directory: %w", err)
		}

		if !strings.HasPrefix(poolPath, tempDir) {
			return nil, ErrInvalidPoolDir
		}
	}

	pool := &ObjectPool{
		Repo:                localrepo.New(logger, locator, gitCmdFactory, catfileCache, proto.GetRepository()),
		logger:              logger,
		locator:             locator,
		gitCmdFactory:       gitCmdFactory,
		txManager:           txManager,
		housekeepingManager: housekeepingManager,
	}

	if !pool.IsValid(ctx) {
		return nil, ErrInvalidPoolRepository
	}

	return pool, nil
}

// FromRepo returns an instance of ObjectPool that the repository points to
func FromRepo(
	ctx context.Context,
	logger log.Logger,
	locator storage.Locator,
	gitCmdFactory gitcmd.CommandFactory,
	catfileCache catfile.Cache,
	txManager transaction.Manager,
	housekeepingManager housekeepingmgr.Manager,
	repo *localrepo.Repo,
) (*ObjectPool, error) {
	storagePath, err := locator.GetStorageByName(ctx, repo.GetStorageName())
	if err != nil {
		return nil, err
	}

	repoPath, err := repo.Path(ctx)
	if err != nil {
		return nil, err
	}

	altInfo, err := stats.AlternatesInfoForRepository(repoPath)
	if err != nil {
		return nil, fmt.Errorf("getting alternates info: %w", err)
	}

	if !altInfo.Exists || len(altInfo.ObjectDirectories) == 0 {
		return nil, ErrAlternateObjectDirNotExist
	}

	absolutePoolObjectDirPath := altInfo.AbsoluteObjectDirectories()[0]
	relativePoolObjectDirPath, err := filepath.Rel(storagePath, absolutePoolObjectDirPath)
	if err != nil {
		return nil, err
	}

	objectPoolProto := &gitalypb.ObjectPool{
		Repository: &gitalypb.Repository{
			StorageName:  repo.GetStorageName(),
			RelativePath: filepath.Dir(relativePoolObjectDirPath),
		},
	}

	if locator.ValidateRepository(ctx, objectPoolProto.GetRepository()) != nil {
		return nil, ErrInvalidPoolRepository
	}

	return FromProto(ctx, logger, locator, gitCmdFactory, catfileCache, txManager, housekeepingManager, objectPoolProto)
}

#### 1. Alternate object directories

The objects in a Git repository can be stored across multiple
directories: 1 main directory, usually `/objects`, and 0 or more
alternate directories. Together these act like a search path: when
looking for an object Git first checks the main directory, then each
alternate, until it finds the object.

#### 2. Config overrides via environment variables

Git can inject custom config into subprocesses via environment
variables. In the case of Git object directories, these are
`GIT_OBJECT_DIRECTORY` (the main object directory) and
`GIT_ALTERNATE_OBJECT_DIRECTORIES` (a search path of `:`-separated
alternate object directories).
