Based on my research, I found a valid analog in Gitaly's transaction manager. `internal/git/reference.go`'s `ValidateReference` function does not enforce any length limit on reference names, and the `TransactionManager.run()` loop treats any `applyLogEntry` failure as fatal to the entire partition.

### Title
Unvalidated reference-name length allows a committed WAL transaction to permanently stall an entire partition's TransactionManager - (File: internal/gitaly/storage/storagemgr/partition/transaction_manager.go)

### Summary
An ordinary user pushing a branch/tag with an excessively long but otherwise syntactically valid reference name can get the reference update accepted and durably committed to the write-ahead log (WAL), mirroring how Alice's bond is accepted by `createBondToken` in the reported ERC20 bug. When the `TransactionManager` later applies that committed log entry to disk (creating the hard link/file for the reference), the filesystem operation can fail (e.g. `ENAMETOOLONG`/permission edge cases), which is treated as a fatal error that stops the whole partition's transaction processing loop — analogous to `distributeBonds` reverting and trapping `BondTokenManager` for all further calls.

### Finding Description
`ValidateReference` in [1](#0-0)  performs syntax checks (no `HEAD`, must start with `refs/`, no `..`, no control characters, no `.lock` suffix, etc.) but never checks the overall length of the reference name or any path component. This validation is what gates whether a reference update is accepted at commit time in `Transaction.UpdateReferences` at [2](#0-1) , which only checks the `refs/` prefix, not length.

Once a transaction commits, its `ReferenceRecorder` stages the corresponding filesystem operations (directory creations and hard links) into the WAL entry, as seen in `RecordReferenceUpdates` [3](#0-2) . The manifest is written and durably synced in `commit()` [4](#0-3)  — at this point the transaction is considered "committed" from the client's perspective, exactly like `createBondToken` succeeding in the ERC20 report.

The actual filesystem mutation is deferred to `applyLogEntry`, which calls `applyOperations` to perform `os.Mkdir`/`os.Link` against the real repository path [5](#0-4) . If the destination path (built directly from the unvalidated, attacker-supplied reference name) exceeds OS/filesystem path or component limits, or otherwise fails, `applyOperations`/`applyLogEntry` returns an error.

Critically, `TransactionManager.run()` treats any `applyLogEntry` error as fatal to the entire run loop, not just to the offending transaction: [6](#0-5) . This causes the manager to exit, and since the WAL entry was already durably committed, the manager will hit the exact same failure again on every restart attempt (`initialize()`/replay), because `applyLogEntry` re-executes the same failing operation on start-up as documented for `TransactionRecoveryMiddleware`: "If a WAL entry can't be applied, the repositories on that partition will remain unavailable until the WAL entry can be successfully applied" [7](#0-6) . Since a partition can host multiple repositories, this affects every repository sharing that partition, not just the one the attacker targeted.

### Impact Explanation
This is a persistent, no-privilege-escalation-required denial of service. Once triggered, an entire storage partition's transaction processing halts, blocking reads and writes for every repository assigned to that partition until an operator manually intervenes (e.g. via the `gitaly recovery` tooling seen in [8](#0-7) , which explicitly acknowledges that a malformed log entry may need to be deleted and "the partition is broken completely" otherwise). This mirrors the "trapped contract" impact in the original report — the difference being partition-wide repository unavailability rather than a smart-contract-wide fund lock.

### Likelihood Explanation
Reachable by any user capable of pushing a branch/tag (a standard, unprivileged git operation). The precondition is a reference name long enough to pass Git's/Gitaly's syntactic `ValidateReference` checks (which impose no length bound) but which fails at the filesystem layer when materialized as a directory/file path (e.g. component or full-path length limits, depending on the underlying filesystem and how deeply nested the ref namespace is). I was not able to fully confirm from the indexed code what git's own `check-ref-format` or `git-update-ref` does with extremely long names before Gitaly's `ValidateReference` is invoked, nor the exact filesystem/backend (ext4, XFS, reftables vs. files backend) behavior in the deployed environment — this affects exploitability certainty and should be validated experimentally.

### Recommendation
Add an explicit length check to `ValidateReference` (and to individual path components) that rejects reference names exceeding a safe threshold well below common filesystem limits, so that invalid references are rejected at commit/admission time rather than being durably logged and only failing during `applyLogEntry`. Additionally, harden `TransactionManager.run()` so that a filesystem-application failure for a single log entry doesn't permanently wedge the partition — e.g., quarantine/skip the malformed entry with alerting rather than stopping the whole apply loop, or ensure such failures are caught earlier during commit-time staging (`RecordReferenceUpdates`/`applyOperations` dry-run) rather than after the WAL entry is already durably committed.

### Proof of Concept
1. As an unprivileged user with push access to a repository, push a branch with a reference name that is syntactically valid per `ValidateReference` (starts with `refs/`, no forbidden characters, no `..`, doesn't end in `.` or `/`, no `.lock` suffix) but is extremely long (e.g., a single path component of several thousand characters, or a deeply nested path whose total length exceeds the filesystem's path length limit).
2. The push's `UpdateReferences` call passes the `refs/` prefix check [9](#0-8)  and the transaction commits successfully, writing the WAL manifest.
3. When `TransactionManager` later calls `applyLogEntry` → `applyOperations` to hard-link/create the reference file at the corresponding path [10](#0-9) , the `os.Link`/`os.Mkdir` call fails due to filesystem path limits.
4. `applyLogEntry` returns an error, `TransactionManager.run()` returns fatally [11](#0-10) , and because the WAL entry is already durably committed, every restart of the manager for that partition re-attempts and re-fails the same operation, leaving all repositories on that partition unavailable until manual recovery.

func ValidateReference(name string) error {
	if name == "HEAD" {
		return fmt.Errorf("HEAD reference not allowed")
	}

	// TODO: this can eventually be converted to use `strings.CutPrefix()`.
	if !strings.HasPrefix(name, "refs/") {
		return fmt.Errorf("reference is not fully qualified")
	}
	name = name[len("refs/"):]

	if len(name) == 0 {
		return fmt.Errorf("refs/ is not a valid reference")
	}

	if strings.HasSuffix(name, "/") {
		return fmt.Errorf("reference must not end with slash")
	}

	if strings.HasSuffix(name, ".") {
		return fmt.Errorf("reference must not end with dot")
	}

	if strings.Contains(name, "@{") {
		return fmt.Errorf("reference must not contain @{")
	}

	if strings.Contains(name, "..") {
		return fmt.Errorf("reference must not contain double dots")
	}

	for _, c := range name {
		switch c {
		case ' ', '\t', '\n':
			return fmt.Errorf("reference must not contain space characters")
		case ':', '?', '[', '\\', '^', '~', '*', '\177':
			return fmt.Errorf("reference must not contain special characters")
		}

		// Note that we treat some of the characters below 32 specially in the switch above so
		// that we can report back more precise error messages.
		if c < 32 {
			return fmt.Errorf("reference must not contain control characters")
		}
	}

	// We need to check the components individually as components aren't allowed to have some specific constructs.
	for {
		component, tail, _ := strings.Cut(name, "/")

		if component == "" {
			if tail != "" {
				return fmt.Errorf("empty component is not allowed")
			}

			// Otherwise, if both component and tail are empty, we have fully verified the complete
			// reference and can thus return successfully.
			return nil
		}

		if strings.HasPrefix(component, ".") {
			return fmt.Errorf("component must not start with dot")
		}

		if strings.HasSuffix(component, ".lock") {
			return fmt.Errorf("component must not end with .lock")
		}

		name = tail
	}
}

	u := git.ReferenceUpdates{}

		// HEAD is a special case and refers to a default branch update.

func (r *ReferenceRecorder) RecordReferenceUpdates(ctx context.Context, refTX git.ReferenceUpdates) error {
	if len(refTX) == 0 {
		return nil
	}

	creations := reftree.New()
	deletions := reftree.New()
	defaultBranchUpdated := false
	preImagePaths := map[string]struct{}{}
	for reference, update := range refTX {
		if reference.String() == "HEAD" {
			defaultBranchUpdated = true
			continue
		}

		tree := creations
		if update.NewOID == r.zeroOID {
			tree = deletions
		}

		if err := tree.InsertReference(reference.String()); err != nil {
			return fmt.Errorf("insert into tree: %w", err)
		}

		for component, remainder, haveMore := "", reference.String(), true; haveMore; {
			var newComponent string
			newComponent, remainder, haveMore = strings.Cut(remainder, "/")

			component = filepath.Join(component, newComponent)
			if !r.preImage.Contains(component) {
				// The path did not exist before applying the transaction.
				// None of its children exist either.
				break
			}

			preImagePaths[component] = struct{}{}
		}
	}

// TransactionRecoveryMiddleware is a middleware that is used when transactions are disabled after being enabled. Interrupted WAL
// application can leave repositories in a corrupted state, for example if the old 'packed-refs' file was removed but the new one
// wasn't applied before Gitaly failed. If transactions are then disabled, the repository will be left in corrupted state as the WAL
// application won't be finished.
//
// This middleware ensures that if transactions are disabled, any already committed WAL entries will be applied before further
// access to the repositories is allowed. This ensures repositories that were in the middle of WAL application are made whole.
// If a WAL entry can't be applied, the repositories on that partition will remain unavailable until the WAL entry can be
