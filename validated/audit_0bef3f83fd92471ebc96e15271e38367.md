### Title
Heap buffer over-read parsing untrusted ZIP/JAR central directory entries in `InputZipFile::ProcessCentralDirEntry` - (File: `third_party/ijar/zip.cc`)

### Summary
`third_party/ijar/zip.cc` implements the `ijar` tool's ZIP/JAR reader, used by Bazel to build interface jars from prebuilt/imported jars (`java_import`, `deploy_jar` inputs, etc.). Unlike the local-file-header parser, the central-directory-entry parser advances a raw pointer through the memory-mapped archive using attacker-controlled 16-bit length fields with no bounds checking against the mapped buffer's end, allowing a crafted jar/zip to make the reader walk and `memcpy` past the end of the mapped file.

### Finding Description
`InputZipFile::ProcessLocalFileEntry` carefully bounds every variable-length read with `EnsureRemaining()` before advancing the cursor [1](#0-0) . In contrast, `InputZipFile::ProcessCentralDirEntry`, which parses each central directory header, reads `file_name_length`, `extra_field_length`, and `file_comment_length` directly off the wire and advances `p` by these attacker-supplied 16-bit values with no equivalent `EnsureRemaining`/bounds check against the actual size of the mapped input file: [2](#0-1) 

The only earlier validation is that `cd.central_dir_offset + cd.central_dir_size <= in_length` for the *aggregate* central directory region, performed once in `FindZipCentralDirectory` [3](#0-2) . Nothing constrains an individual crafted entry's `file_name_length`/`extra_field_length`/`file_comment_length` to stay within that aggregate region or within the mapped file bounds. A malicious jar can declare a central directory entry with a maximal `file_name_length` (up to `0xFFFF`) near the true end of the mapped file, causing:
- the `memcpy(filename, p, len)` at line 520 to read heap/mapped memory past the legitimate central directory content (and potentially past the end of the `mmap`'d region), and
- the subsequent extra-field walk loop (`while (extra_p != p) { ... get_u2le(extra_p) ... }`) to run over attacker-influenced/adjacent memory, since `data_size` there is likewise unchecked [4](#0-3) .

This mirrors the EDK2 `Tcg2MeasureGptTable()` bug class: a size/count field taken directly from untrusted, attacker-supplied table data is used to index/copy without validating it against the actual buffer extent, producing an out-of-bounds heap access.

### Impact Explanation
`ProcessCentralDirEntry`/`CalculateOutputLength` and the main extraction path (`ProcessNext` → `ProcessLocalFileEntry`) are invoked by `ijar`/`zip_main.cc`'s `extract()` and by Bazel's internal jar-interface-generation tooling whenever a jar file (including externally-fetched, attacker-influenced jars) is processed [5](#0-4) . Out-of-bounds reads of adjacent heap memory can crash the build (worker process) or, in the `memcpy` case, copy adjacent memory contents into the `filename[PATH_MAX]` buffer, which is subsequently used to construct output paths — a memory-safety violation consistent with C++ heap buffer over-read/overflow.

### Likelihood Explanation
Any project that consumes a prebuilt/third-party jar (e.g., via `java_import`, `deploy_jar` deps processed by `ijar`, or an `http_jar`/`http_file` whose author is malicious) triggers this code path automatically as part of normal Bazel Java-rule processing — no special flags or opt-in are required, and the vulnerable code executes with default settings on a current build.

### Recommendation
Add the same remaining-bytes validation used in `ProcessLocalFileEntry`'s `EnsureRemaining()` to `ProcessCentralDirEntry` before reading and copying `file_name_length`, `extra_field_length`, and `file_comment_length` bytes, and validate that each entry's cumulative advance stays within `[central_dir_, central_dir_ + central_dir_size]` and within the mapped file's total length before performing the `memcpy` and the extra-field walk.

### Proof of Concept
A `BuildIntegrationTestCase`/JUnit-style reproduction:
1. Build (or hand-craft bytes for) a minimal ZIP whose End-Of-Central-Directory record and one central directory entry validate `central_dir_offset + central_dir_size <= in_length`, but whose entry's `file_name_length` field is set to `0xFFFF` while only a few real bytes of filename data follow before the mapped file ends.
2. Feed this file to `devtools_ijar::ZipExtractor::Create()` and call `ProcessAll()` (as done in `zip_main.cc`'s `extract()`), or call `InputZipFile::CalculateOutputLength()` directly.
3. Observe (under ASan/Valgrind) a heap-buffer-overflow/over-read report inside `ProcessCentralDirEntry`'s `memcpy` at [6](#0-5) , or a SIGSEGV when `p`/`extra_p` walks past the mapped region.

// Execute the extraction (or just listing if just v is provided)
int extract(char *zipfile, char *exdir, char **files, bool verbose,
            bool extract, bool flatten) {
  std::string cwd = get_cwd();
  if (cwd.empty()) {
    return -1;
  }

  char output_root[PATH_MAX + 1];
  if (exdir != NULL) {
    if (!concat_path(output_root, sizeof(output_root), cwd.c_str(), exdir)) {
      return -1;
    }
  } else if (cwd.length() >= sizeof(output_root)) {
    fprintf(stderr, "current working directory path too long");
    return -1;
  } else {
    memcpy(output_root, cwd.c_str(), cwd.length() + 1);
  }

  UnzipProcessor processor(output_root, files, verbose, extract, flatten);
  std::unique_ptr<ZipExtractor> extractor(ZipExtractor::Create(zipfile,
                                                               &processor));
  if (extractor == NULL) {
    fprintf(stderr, "Unable to open zip file %s: %s.\n", zipfile,
            strerror(errno));
    return -1;
  }

  if (extractor->ProcessAll() < 0) {
    fprintf(stderr, "%s.\n", extractor->GetError());
    return -1;
  }
  return 0;
}
