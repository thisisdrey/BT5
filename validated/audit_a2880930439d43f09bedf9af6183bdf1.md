## Analysis

The reported bug class is: a **privileged, non-consensus actor** (the swapper owner) can front-run a victim's price-sensitive transaction by unilaterally changing the parameter that determines the exchange rate (`setOracle`), extracting value from the victim even though the victim believed the price was fixed.

The closest reachable analog in java-tron is the TRC10 **Exchange (bancor-style AMM pool)** subsystem, specifically the interaction between `ExchangeInjectActuator`/`ExchangeWithdrawActuator` (callable only by the pool's `creatorAddress`, i.e. the pool "owner") and `ExchangeTransactionActuator` (callable by any counterparty who wants to swap against the pool).

### Root cause

The exchange rate for a swap is derived purely from the pool's current `firstTokenBalance`/`secondTokenBalance` at the moment `ExchangeCapsule.transaction()` executes: [1](#0-0) 

Only the pool creator is authorized to call `ExchangeInjectContract`/`ExchangeWithdrawContract`, which directly rewrites `firstTokenBalance`/`secondTokenBalance` (i.e., the price) before any swap: [2](#0-1) [3](#0-2) 

A victim's `ExchangeTransactionContract` only protects against slippage via a caller-supplied `tokenExpected` minimum, checked against whatever the pool state is *at execution time* (not at the time the victim signed/broadcast the transaction): [4](#0-3) 

Because the pool creator can broadcast an `ExchangeInjectContract`/`ExchangeWithdrawContract` transaction and have it ordered immediately before the victim's `ExchangeTransactionContract` (block producers/relayers order transactions, and a privileged actor watching the mempool can craft or bribe such ordering), the creator can shift the bonding-curve ratio to a rate that still barely satisfies the victim's `tokenExpected` floor while capturing the rest of the value — the same "owner manipulates price parameter right before user's price-sensitive call" pattern as the reported `setOracle` front-run.

### Summary
The `ExchangeInjectActuator` and `ExchangeWithdrawActuator` let only the exchange's `creatorAddress` change the pool's `firstTokenBalance`/`secondTokenBalance`, which is the sole input to the bonding-curve price used by `ExchangeTransactionActuator.execute()`. A victim's only protection is a client-chosen minimum-received (`tokenExpected`) checked against live pool state at execution time, not a price locked at signing time.

### Finding Description
`ExchangeCapsule.transaction()` computes the swap output purely from the pool balances present in state when the transaction is processed: [5](#0-4) 

`ExchangeInjectActuator`/`ExchangeWithdrawActuator` validate only that the caller is the `creatorAddress` of the exchange — no cooldown, no commitment, and no restriction preventing large, one-shot rebalancing right before a pending swap: [6](#0-5) 

`ExchangeTransactionActuator.doValidate()` only guarantees `anotherTokenQuant >= tokenExpected`, a value chosen by the victim before broadcasting, using whatever pool state exists at validation time in the block being built: [4](#0-3) 

Because a single signed transaction from the creator (inject/withdraw) can shift the ratio arbitrarily (bounded only by `getExchangeBalanceLimit()` on the upper side, with no lower-side protection), the creator can order (or otherwise ensure) their manipulation transaction lands immediately before the victim's swap, deflating the rate the victim receives down to just above their `tokenExpected` floor and capturing the difference for themselves upon reversing the injection/withdrawal afterward — structurally identical to the reported "owner front-runs the price-setting call to deceive a user who expected a given price."

### Impact Explanation
The pool creator, an unprivileged-relative-to-consensus but authorized market participant, can extract value from any counterparty performing an `ExchangeTransactionContract` swap against their own pool, since the rate is entirely creator-controlled state that changes atomically with a single transaction and has no time-lock or price commitment. This is a direct theft-of-funds vector for any user who swaps against a TRC10 Exchange pool without setting a very tight `tokenExpected` (and even tight bounds only cap the loss, not prevent it).

### Likelihood Explanation
Requires only that the pool creator (any account that created an `ExchangeCreateContract` pool) hold assets to inject/withdraw and be able to sequence their transaction ahead of the victim's within the same or an adjacent block — a routine capability for any actor submitting transactions to the network, with no special validator/witness/SR privilege needed.

### Recommendation
Add a minimum time delay / cooldown between `ExchangeInjectContract`/`ExchangeWithdrawContract` executions and subsequent swaps, and/or require `ExchangeTransactionContract` callers to reference a maximum acceptable pool-state deviation (e.g., a "quoted-at" balance snapshot) so that any intervening inject/withdraw invalidates the swap rather than merely satisfying a loose `tokenExpected` floor.

### Proof of Concept
1. Creator (Owner) creates an exchange pool `A/B` via `ExchangeCreateContract`.
2. Victim broadcasts `ExchangeTransactionContract` selling `X` of `A` for `B`, computing off-chain that they should receive `Y` and setting `tokenExpected = Y * 0.98` (2% slippage tolerance) — reasonable given the pool state they observed.
3. Owner, seeing the pending transaction (mempool visibility) or simply controlling ordering as a witness/SR, submits `ExchangeWithdrawContract` withdrawing most of `B`'s balance immediately before the victim's transaction is packed, per [7](#0-6) .
4. Victim's swap executes against the now-skewed pool via [1](#0-0) , yielding just above `tokenExpected` instead of `Y`.
5. Owner submits `ExchangeInjectContract` to restore/rebalance the pool, having captured the spread from the victim's trade.

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
  }
