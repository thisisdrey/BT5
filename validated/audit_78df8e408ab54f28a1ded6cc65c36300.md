### Title
Division-before-multiplication precision loss in `MortgageService.payReward()` / brokerage & vote-reward computations - (File: `chainbase/src/main/java/org/tron/core/service/MortgageService.java`)

### Summary
`MortgageService.payReward()` computes the SR brokerage cut by first dividing the integer `brokerage` (0-100) by `100` into a `double`, and only then multiplying by `value` (the reward amount), truncating to `long` at the end. This is the exact "divide-then-multiply" ordering flagged in the external report (`targetCollateral = assets.sub(claimAmount).div(TWO)` then `.muldiv(...)`), which causes avoidable precision loss versus computing `brokerage * value / 100` with the multiplication performed first. The same anti-pattern recurs in the legacy vote-reward path `computeReward(long cycle, List<Pair<byte[], Long>> votes)`, where `voteRate = (double) userVote / totalVote` is divided first and then multiplied by `totalReward`.

### Finding Description
In `payReward`:
```java
private void payReward(byte[] witnessAddress, long value) {
  long cycle = dynamicPropertiesStore.getCurrentCycleNumber();
  int brokerage = delegationStore.getBrokerage(cycle, witnessAddress);
  double brokerageRate = (double) brokerage / 100;
  long brokerageAmount = (long) (brokerageRate * value);
  value -= brokerageAmount;
  delegationStore.addReward(cycle, witnessAddress, value);
  adjustAllowance(witnessAddress, brokerageAmount);
}
``` [1](#0-0) 

The division `brokerage / 100` is performed first (producing a `double` with binary-floating-point rounding of a value that in general cannot be represented exactly, e.g. `7/100`), and the result is then multiplied by `value` and truncated. Reordering to compute the multiplication first — e.g. `Math.floorDiv(brokerage * value, 100)` (or a `BigInteger`/hardened path analogous to what other resource/exchange calculations in this codebase already use) — avoids the extra rounding step and is strictly more precise, exactly mirroring the reported Perennial issue.

The same pattern exists in the legacy reward-splitting code:
```java
double voteRate = (double) userVote / totalVote;
reward += voteRate * totalReward;
``` [2](#0-1) 

Notably, the codebase already recognizes this class of bug and has introduced "hardened" BigInteger/BigDecimal replacement paths for other calculations that previously used the same divide-then-multiply-with-double pattern (e.g. `calculateGlobalLimitV2` in `ResourceProcessor.java` [3](#0-2) , and `SafeExchangeProcessor`/hardened exchange precision checks [4](#0-3) ), but `MortgageService.payReward` and its `computeReward` sibling were not hardened in the same way.

### Impact Explanation
`payReward` is invoked on every block reward and transaction-fee reward payout, and `payStandbyWitness`/`computeReward` on every reward withdrawal — i.e., on essentially every block applied by `Manager` and every `withdrawReward`/vote-reward query reachable from a normal account transaction. Because the division happens before the multiplication, and is done using floating point rather than integer/BigInteger math, the brokerage split computed for the block producer and the residual reward credited to voters can differ (by rounding) from the mathematically correct split. Repeated over many blocks/cycles, this can produce a divergence between amounts credited to different parties (over/under crediting brokerage vs. voter reward), i.e., value that is not accurately backed. This lines up with the Medium-severity impact category of "unbacked balance" from small, systematic reward-accounting drift, though the magnitude per call is small.

### Likelihood Explanation
Every block reward and transaction fee reward payment goes through `payReward`, and every reward withdrawal for accounts with pre-new-algorithm votes goes through the `voteRate` computation — so the code path is executed continuously and automatically as part of ordinary block production/reward accounting, with no special privilege required to trigger it (it's exercised by normal transaction processing and the maintenance/reward cycle). However, per-call drift is on the order of at most one integer unit of TRX-precision, so the practical value of this drift accumulated per party is small — this is why it's a Medium rather than High/Critical finding, matching the severity of the original report.

### Recommendation
Reorder the arithmetic to multiply before dividing, using integer/`BigInteger` math instead of `double`, mirroring the hardened patterns already used elsewhere in the codebase (`ResourceProcessor.calculateGlobalLimitV2`, `SafeExchangeProcessor`):
```java
long brokerageAmount = Math.floorDiv(Math.multiplyExact((long) brokerage, value), 100L);
```
and similarly for `voteRate`/`totalReward` in `computeReward`, e.g. using `BigInteger.valueOf(userVote).multiply(BigInteger.valueOf(totalReward)).divide(BigInteger.valueOf(totalVote))`.

### Proof of Concept
For `brokerage = 7`, `value = 100_000_007`:
- Current code: `brokerageRate = 7.0/100 = 0.07000000000000001` (binary float rounding) → `brokerageAmount = (long)(0.07000000000000001 * 100000007)` may truncate to a value that differs by 1 unit from the exact integer computation.
- Correct order: `(7L * 100000007L) / 100 = 700000049 / 100 = 7000000` exactly.
Any small mismatch here changes the exact split between `delegationStore.addReward` (voter pool) and `adjustAllowance` (witness brokerage), which is exactly the "correctness of downstream computation" impact called out in the source report.
