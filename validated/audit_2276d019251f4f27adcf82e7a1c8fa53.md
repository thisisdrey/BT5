## Analysis

The external report describes a bug class: a callback/handler trusts an **attacker-supplied identity field embedded in message data** (the `account` field of GMX's `Deposit.Props`) instead of validating it against the actual, cryptographically-verified initiator of the request. The strongest reachable analog in Nebula is in the relay-establishment control-message handler, where the "who is this relay for" identity is taken directly from attacker-controlled message fields rather than the authenticated peer identity.

### Title
Relay state is created for an arbitrary, attacker-supplied VPN address without validating it against the authenticated peer identity - (File: `relay_manager.go`)

### Summary
`relayManager.handleCreateRelayRequest` derives the identity of the peer being relayed for (`from`) directly from the `RelayFromAddr`/`OldRelayFromAddr` fields of an incoming `NebulaControl` message, and uses that unverified value as the key for creating persistent relay state (`AddRelay`) tied to the authenticated `HostInfo` `h` that delivered the Control message. There is no check that `from` matches any certificate, VPN network, or other property that ties it back to `h`'s cert-verified identity.

### Finding Description
`HandleControlMsg` in [1](#0-0)  only validates that `RelayFromAddr`/`RelayToAddr` are non-nil before dispatching to `handleCreateRelayRequest`. It never checks `from` against `h.vpnAddrs` or any certificate data of `h`.

Inside `handleCreateRelayRequest`, when the target of the relay request is the local node, the code does: [2](#0-1) 

Specifically, `from := protoAddrToNetAddr(m.RelayFromAddr)` (line 428) is fully attacker-controlled data carried inside the `Control` message payload of an already-established, authenticated tunnel `h`. The only sanity checks performed are:
- "is `from` one of *my* addresses" (line 441)
- "is `target` one of *my* addresses" (line 447)

There is no check that `from` corresponds to `h`'s own certified VPN address(es) (`h.vpnAddrs`), nor any other peer that `h` is legitimately authorized to relay for. When no existing relay state is found, `AddRelay(rm.l, h, f.hostMap, from, &m.InitiatorRelayIndex, TerminalType, Established)` (line 482) immediately installs `Established` relay state on `h`, associating `h` as a legitimate relay for whatever `from` address the attacker chose — this can be any arbitrary VPN address, including one belonging to another real peer on the network, not `h`'s own identity.

This mirrors the external report's root cause exactly: the callback (`afterDepositExecution`/here, `handleCreateRelayRequest`) trusts an identity/account field carried inside the message body (`deposit.account()` / `m.RelayFromAddr`) instead of validating it against the actual initiator of the flow, whose identity is otherwise cryptographically established (the `msg.sender` that started the deposit / the certificate-verified `HostInfo h` that completed the Noise handshake).

### Impact Explanation
An authenticated peer `h` (one that has completed a valid handshake and holds any valid certificate) can claim, via a single `CreateRelayRequest` Control message, to be a relay on behalf of an arbitrary victim VPN address that it does not own and has no relationship to. This poisons the local relay/hostmap state (`Established` state is granted immediately, bypassing the normal `Requested → Established` handshake-confirmed flow used elsewhere), causing the node to trust `h` as a relay path for a victim's address. This is remote state poisoning of the hostmap/relay trust structures reachable by any peer holding a valid (but otherwise unprivileged) certificate — no additional signed certificate for the impersonated address is required.

### Likelihood Explanation
Any node that completes a normal handshake with a target (which requires only a certificate signed by a trusted CA, not any special relay-specific certificate or privilege) can send a crafted `Control`/`CreateRelayRequest` message with a forged `RelayFromAddr`. `am_relay`/`use_relays` configuration only gates the *forwarding* branch (`target != me`); the vulnerable branch (`target == me`) is reached whenever *any* peer sends this control message to the local node, regardless of relay configuration, making this reachable by any connected peer.

### Recommendation
In `handleCreateRelayRequest` (and the corresponding logic in `handleCreateRelayResponse` / `EstablishRelay`), validate that `from` is consistent with the sending peer's authenticated identity — e.g., require `from` to be contained in `h.vpnAddrs` (the certificate-verified addresses of `h`) before treating `h` as the terminal/legitimate relay endpoint for that address, mirroring the check already done for `target` against `f.myVpnAddrsTable`. Reject the request otherwise instead of installing `Established` relay state.

### Proof of Concept
1. Node `A` (attacker) completes a normal, cert-valid handshake with node `Me`.
2. `A` sends a `Control` message of type `NebulaControl_CreateRelayRequest` with `RelayFromAddr` set to `Victim`'s VPN address (not `A`'s own) and `RelayToAddr` set to `Me`'s VPN address.
3. `Me` processes this in `handleCreateRelayRequest`: `target == Me`, no existing relay state for `Victim` on `A`'s `HostInfo`, so `AddRelay(..., h=A's HostInfo, from=Victim, ..., TerminalType, Established)` is called, immediately marking `A` as an `Established` relay for `Victim` in `Me`'s hostmap — without `A` ever proving any relationship to `Victim`'s certificate or address.
4. `Me` now trusts `A`'s `HostInfo` as a legitimate relay channel for traffic purportedly relating to `Victim`, corrupting relay/hostmap state based purely on an unauthenticated field inside the Control payload.

func (rm *relayManager) HandleControlMsg(h *HostInfo, d []byte, f *Interface) {
	msg := &NebulaControl{}
	err := msg.Unmarshal(d)
	if err != nil {
		h.logger(f.l).Error("Failed to unmarshal control message", "error", err)
		return
	}

	var v cert.Version
	if msg.OldRelayFromAddr > 0 || msg.OldRelayToAddr > 0 {
		v = cert.Version1

		b := [4]byte{}
		binary.BigEndian.PutUint32(b[:], msg.OldRelayFromAddr)
		msg.RelayFromAddr = netAddrToProtoAddr(netip.AddrFrom4(b))

		binary.BigEndian.PutUint32(b[:], msg.OldRelayToAddr)
		msg.RelayToAddr = netAddrToProtoAddr(netip.AddrFrom4(b))
	} else {
		v = cert.Version2
	}

	// validate:
	switch msg.Type {
	case NebulaControl_CreateRelayRequest, NebulaControl_CreateRelayResponse:
		if msg.RelayFromAddr == nil {
			if f.l.Enabled(context.Background(), slog.LevelDebug) {
				h.logger(f.l).Debug("Control message received with nil RelayFromAddr", "type", msg.Type)
			}
			return
		} else if msg.RelayToAddr == nil {
			if f.l.Enabled(context.Background(), slog.LevelDebug) {
				h.logger(f.l).Debug("Control message received with nil RelayToAddr", "type", msg.Type)
			}
			return
		}
	}

	switch msg.Type {
	case NebulaControl_CreateRelayRequest:
		rm.handleCreateRelayRequest(v, h, f, msg)
	case NebulaControl_CreateRelayResponse:
		rm.handleCreateRelayResponse(v, h, f, msg)
	}
}

func (rm *relayManager) handleCreateRelayRequest(v cert.Version, h *HostInfo, f *Interface, m *NebulaControl) {
	//nil-checks for protoAddrToNetAddr handled by caller
	from := protoAddrToNetAddr(m.RelayFromAddr)
	target := protoAddrToNetAddr(m.RelayToAddr)

	logMsg := rm.l.With(
		"relayFrom", from,
		"relayTo", target,
		"initiatorRelayIndex", m.InitiatorRelayIndex,
		"vpnAddrs", h.vpnAddrs,
	)

	logMsg.Info("handleCreateRelayRequest")
	// Is the source of the relay me? This should never happen, but did happen due to
	// an issue migrating relays over to newly re-handshaked host info objects.
	if f.myVpnAddrsTable.Contains(from) {
		logMsg.Error("Discarding relay request from myself", "myIP", from)
		return
	}

	// Is the target of the relay me?
	if f.myVpnAddrsTable.Contains(target) {
		existingRelay, ok := h.relayState.QueryRelayForByIp(from)
		if ok {
			switch existingRelay.State {
			case Requested:
				ok = h.relayState.CompleteRelayByIP(from, m.InitiatorRelayIndex)
				if !ok {
					logMsg.Error("Relay State not found")
					return
				}
			case Established:
				if existingRelay.RemoteIndex != m.InitiatorRelayIndex {
					// We got a brand new Relay request, because its index is different than what we saw before.
					// This should never happen. The peer should never change an index, once created.
					logMsg.Error("Existing relay mismatch with CreateRelayRequest",
						"existingRemoteIndex", existingRelay.RemoteIndex)
					return
				}
			case Disestablished:
				if existingRelay.RemoteIndex != m.InitiatorRelayIndex {
					// We got a brand new Relay request, because its index is different than what we saw before.
					// This should never happen. The peer should never change an index, once created.
					logMsg.Error("Existing relay mismatch with CreateRelayRequest",
						"existingRemoteIndex", existingRelay.RemoteIndex)
					return
				}
				// Mark the relay as 'Established' because it's safe to use again
				h.relayState.UpdateRelayForByIpState(from, Established)
			case PeerRequested:
				// I should never be in this state, because I am terminal, not forwarding.

					"state", existingRelay.State)
			}
		} else {
			_, err := AddRelay(rm.l, h, f.hostMap, from, &m.InitiatorRelayIndex, TerminalType, Established)

				logMsg.Error("Failed to add relay", "error", err)
