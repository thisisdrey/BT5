## Finding [1](#0-0) 

### Title
`claim_rewards_to` permanently deletes a relayer's reward entry on Bridge Hub before the cross‑chain settlement to AssetHub is confirmed, causing silent fund loss when the XCM payout fails remotely - (File: bridges/snowbridge/primitives/core/src/reward.rs, bridges/modules/relayers/src/lib.rs)

### Summary
`PayAccountOnLocation::pay_reward` (the `PaymentProcedure` used for `BridgeReward::Snowbridge`) returns `Ok(())` as soon as the payout XCM is *accepted into the outbound queue* (`XcmSender::deliver`), not once the WETH reward is actually deposited to the beneficiary on AssetHub. `do_claim_rewards` in `pallet-bridge-relayers` treats this `Ok` as final settlement and permanently removes the relayer's `RelayerRewards` entry via `try_mutate_exists`/`maybe_reward.take()`. This mirrors the `_sendValue` bug class: an accounting value (`s_clientOnlyClRewards` there, `RelayerRewards` here) is committed based on a call that can still fail after the local `Ok`, with no compensating mechanism if the remote leg reverts.

### Finding Description
`pay_reward` in `bridges/snowbridge/primitives/core/src/reward.rs` builds an `UnpaidExecution` XCM containing `ReserveAssetDeposited` + `DepositAsset { .. , beneficiary }`, then does: [2](#0-1) 
```
let (ticket, fee) = validate_send::<XcmSender>(AssetHubLocation::get(), xcm).map_err(|_| XcmSendFailure)?;
XcmExecutor::charge_fees(relayer.clone(), fee).map_err(|_| ChargeFeesFailure)?;
XcmSender::deliver(ticket).map_err(|_| XcmSendFailure)?;
Ok(())
```
`Ok(())` here only proves the message was enqueued for delivery (HRMP/XCMP), not that AssetHub actually executed the `DepositAsset` and credited the beneficiary. Because this XCM uses `UnpaidExecution`/no barrier check on the remote side, remote execution can still fail (unregistered foreign asset, beneficiary below ED, weight limit exceeded, asset trapped) independently of the successful send.

Back on Bridge Hub, `do_claim_rewards`: [3](#0-2) 
```
RelayerRewards::<T, I>::try_mutate_exists(&relayer, reward_kind, |maybe_reward| -> DispatchResult {
    let reward_balance = maybe_reward.take().ok_or(Error::<T, I>::NoRewardForRelayer)?;
    T::PaymentProcedure::pay_reward(&relayer, reward_kind, reward_balance, beneficiary.clone())
        .map_err(|e| { ... Error::<T, I>::FailedToPayReward })?;
    ...
    Ok(())
})
```
Since `pay_reward` returns `Ok` on send success alone, the closure returns `Ok(())`, and `try_mutate_exists` commits the removal of the reward entry. If the remote `DepositAsset` subsequently fails or the asset gets trapped on AssetHub, the relayer's reward is gone from Bridge Hub storage with nothing ever landing on AssetHub — an irrecoverable, unbacked write-off of relayer funds, exactly the "state updated even though the value transfer can still fail" pattern in the external report.

### Impact Explanation
This directly conserves-value-violates the "settle exactly once to the rightful beneficiary" invariant for bridge rewards: the relayer's claimable balance is destroyed on the source chain without a guaranteed corresponding credit on the destination chain, and there is no re-registration or refund path once `RelayerRewards` is cleared. Reward accounting integrity for the entire Snowbridge relayer incentive system is affected, and it requires no privileged actor — any relayer calling the public `claim_rewards_to` extrinsic can trigger it under adverse (but reachable) remote conditions.

### Likelihood Explanation
Triggering requires only a normal signed call to `claim_rewards_to`/`claim_rewards` for `BridgeReward::Snowbridge`, combined with a remote execution failure on AssetHub (e.g., transient AssetHub congestion, ED issues for a beneficiary account, or asset trapping — a scenario the test suite itself checks for via `assert!(!... AssetsTrapped ...)`), which is plausible in production without any malicious actor.

### Recommendation
Do not remove/finalize `RelayerRewards` on the basis of successful XCM *send* alone. Either (a) require an execution/delivery confirmation from AssetHub before clearing the reward entry (e.g., via a receipt/ack pattern), or (b) keep the reward entry pending and only clear it upon confirmed remote success, re-crediting it back into `RelayerRewards` if remote execution/settlement fails or an `AssetsTrapped` event is observed for that claim.

### Proof of Concept
1. Relayer accrues a `BridgeReward::Snowbridge` balance via `register_reward` (as in `bridges/modules/relayers/src/lib.rs`).
2. Relayer calls `claim_rewards_to` with a valid `AssetHubLocation` beneficiary whose account does not yet exist / is below ED on AssetHub, or with a foreign asset not yet fully registered/reachable in a way that only fails at remote `DepositAsset` time (see `cumulus/parachains/integration-tests/.../snowbridge_v2_rewards.rs` fixtures for the happy path).
3. `PayAccountOnLocation::pay_reward` validates and delivers the XCM successfully → returns `Ok(())`.
4. `do_claim_rewards`'s `try_mutate_exists` commits, deleting the `RelayerRewards` entry and emitting `RewardPaid`.
5. On AssetHub, the `DepositAsset` instruction fails (trapped asset / ED violation) — the WETH is never credited to the beneficiary.
6. Result: relayer's reward balance is permanently zero on Bridge Hub, and nothing was received on AssetHub — a duplicate-free but total loss of the reward.

			reward_kind: T::Reward,
