## Analysis: Integer overflow in `expireTime` computation reachable from TVM `freezeBalance` precompile/opcode [1](#0-0) 

### Title
Unchecked `frozenDuration` allows `long` overflow of freeze `expireTime`, bypassing the resource-freeze lock period - (File: actuator/src/main/java/org/tron/core/vm/nativecontract/FreezeBalanceProcessor.java)

### Summary
The CVE-2017-20005 bug class is an integer overflow that occurs when an attacker-influenced numeric field (a year/date value) is combined arithmetically without bounds checking, producing a corrupted (wrapped) time value. The same bug-class pattern exists in java-tron's native `FreezeBalanceProcessor`, which is invoked by the TVM `freezeBalance` contract call path. Unlike the legacy `FreezeBalanceActuator`, this processor's `validate()` never bounds-checks `frozenDuration`, and `execute()` computes `expireTime = nowInMs + param.getFrozenDuration() * FROZEN_PERIOD` with plain `long` arithmetic (no overflow guard), unlike other date-math paths in the codebase (e.g. `AssetIssueActuator`) that were hardened with `StrictMathWrapper.addExact`/`LongMath.checkedAdd` specifically to prevent this class of bug.

### Finding Description
`FreezeBalanceProcessor.validate` [2](#0-1)  validates `frozenBalance`, `frozenCount`, `resourceType`, and the receiver address, but never checks `param.getFrozenDuration()` against any minimum/maximum bound. This is in stark contrast to the legacy `FreezeBalanceActuator.validate()`, which explicitly enforces `frozenDuration >= minFrozenTime && frozenDuration <= maxFrozenTime` [3](#0-2) .

`FreezeBalanceProcessor.execute` then computes:
```
long expireTime = nowInMs + param.getFrozenDuration() * FROZEN_PERIOD;
``` [4](#0-3) 

Since `frozenDuration` is fully attacker-controlled (sourced from `FreezeBalanceParam`, populated from TVM opcode/precompile input in `Program.java`), a sufficiently large value causes `frozenDuration * FROZEN_PERIOD` to overflow `long`, and the subsequent addition with `nowInMs` can wrap the result into a value less than or equal to `nowInMs` (or even negative). The codebase already recognizes and mitigates this exact overflow pattern elsewhere — `AssetIssueActuator` added an explicit `StrictMathWrapper.addExact` overflow check for the analogous `startTime + frozenDays*FROZEN_PERIOD` computation specifically to prevent `FrozenSupply.expireTime` overflow [5](#0-4) , and `WithdrawExpireUnfreezeProcessor`/`UnfreezeBalanceV2Actuator` use `LongMath.checkedAdd` for balance overflow checks. `FreezeBalanceProcessor` was not hardened the same way.

### Impact Explanation
If `expireTime` wraps to a value `<= now`, the frozen balance/delegated resource entry is stored with an already-"expired" unlock time. This corrupts the on-chain resource/lock-duration invariant that the freeze mechanism is designed to enforce (funds must remain locked for a configured minimum period while granting bandwidth/energy weight). An account (or delegatee) could then immediately unfreeze via `UnfreezeBalanceActuator`/`UnfreezeBalanceProcessor`, whose checks rely on `expireTime > now` to reject early unfreeze [6](#0-5) . This is a direct, unauthorized bypass of a core account-state invariant (the freeze lock), reachable purely through a signed TVM contract call with attacker-chosen `frozenDuration`.

### Likelihood Explanation
The path is reachable by any address that can execute a smart contract invoking the `freezeBalance` native contract via the TVM (an unprivileged, permissionless action). No special permission or witness/SR privilege is required — only crafting a large `frozenDuration` value in the call parameters. The absence of any bound check in `FreezeBalanceProcessor.validate()` (compared to the parallel, hardened `FreezeBalanceActuator.validate()`) makes this trivial to trigger once the overflow arithmetic is confirmed to be reachable with attacker-supplied `frozenDuration`.

### Recommendation
Add the same `minFrozenTime`/`maxFrozenTime` bound check present in `FreezeBalanceActuator.validate()` to `FreezeBalanceProcessor.validate()`, and/or wrap the `expireTime` computation in `FreezeBalanceProcessor.execute()` with an overflow-safe operation (e.g., `LongMath.checkedAdd`/`checkedMultiply` as already used elsewhere in the codebase), rejecting the transaction if the computation would overflow.

### Proof of Concept
1. Deploy/call a contract that invokes the `freezeBalance` TVM native contract with `frozenDuration` set to a very large value (e.g., close to `Long.MAX_VALUE / FROZEN_PERIOD`).
2. `FreezeBalanceProcessor.validate` performs no bound check on `frozenDuration`, so the call passes validation.
3. `FreezeBalanceProcessor.execute` computes `expireTime = nowInMs + frozenDuration * FROZEN_PERIOD`, which overflows `long` and wraps to a value `<= nowInMs`.
4. The account's frozen balance is stored with the corrupted `expireTime`.
5. Immediately call `unfreezeBalance` (or the V2 unfreeze path); since `expireTime <= now`, the unfreeze check passes and funds are released without the intended lock period, defeating the freeze-duration invariant.

**Note on verification limits:** I was unable to fully confirm within this session which exact TVM opcode/precompile invokes `FreezeBalanceProcessor` and whether it is gated behind a specific hard-fork flag (partial evidence was found in `Program.java` referencing `FreezeBalanceParam`, but I did not have remaining tool budget to read that method in full). This should be double-checked against `actuator/src/main/java/org/tron/core/vm/program/Program.java` before treating the reachability as fully confirmed.

  public void validate(FreezeBalanceParam param, Repository repo) throws ContractValidateException {
    if (repo == null) {
      throw new ContractValidateException(STORE_NOT_EXIST);
    }

    // validate arg @frozenBalance
    byte[] ownerAddress = param.getOwnerAddress();
    AccountCapsule ownerCapsule = repo.getAccount(ownerAddress);
    long frozenBalance = param.getFrozenBalance();
    if (frozenBalance <= 0) {
      throw new ContractValidateException("FrozenBalance must be positive");
    } else if (frozenBalance < TRX_PRECISION) {
      throw new ContractValidateException("FrozenBalance must be greater than or equal to 1 TRX");
    } else if (frozenBalance > ownerCapsule.getBalance()) {
      throw new ContractValidateException("FrozenBalance must be less than or equal to accountBalance");
    }

    // validate frozen count of owner account
    int frozenCount = ownerCapsule.getFrozenCount();
    if (frozenCount != 0 && frozenCount != 1) {
      throw new ContractValidateException("FrozenCount must be 0 or 1");
    }

    // validate arg @resourceType
    switch (param.getResourceType()) {
      case BANDWIDTH:
      case ENERGY:
        break;
      default:
        throw new ContractValidateException(
            "Unknown ResourceCode, valid ResourceCode[BANDWIDTH、ENERGY]");
    }

    // validate for delegating resource
    byte[] receiverAddress = param.getReceiverAddress();
    if (!FastByteComparisons.isEqual(ownerAddress, receiverAddress)) {
      param.setDelegating(true);

      // check if receiver account exists. if not, then create a new account
      AccountCapsule receiverCapsule = repo.getAccount(receiverAddress);
      if (receiverCapsule == null) {
        receiverCapsule = repo.createNormalAccount(receiverAddress);
      }

      // forbid delegating resource to contract account
      if (receiverCapsule.getType() == Protocol.AccountType.Contract) {
        throw new ContractValidateException(
            "Do not allow delegate resources to contract addresses");
      }
    }
  }
