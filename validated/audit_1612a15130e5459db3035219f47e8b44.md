Confirmed key facts:

- `check_actor_permissions` at `runtime/runtime/src/actions.rs:739-785` gates administrative actions (`DeployContract`, `Stake`, `AddKey`, `DeleteKey`, `DeployGlobalContract`, `UseGlobalContract`, `WithdrawFromGasKey`, `DeleteAccount`) on `actor_id == account_id`. `actor_id` is seeded from `receipt.predecessor_id()` at `runtime/runtime/src/lib.rs:855` and is never re-derived from any "account incarnation" concept — only from the raw `AccountId` string.
- `promise_yield_create` (`runtime/near-vm-runner/src/logic/logic.rs:3660`) always creates the receipt with `receiver_id = self.context.current_account_id` (self-receipt), and the resulting `PromiseYield` receipt's `predecessor_id` is likewise the same account (self-callback pattern) — so on resume, `actor_id == account_id == the recreated account`, i.e., owner-level permission.
- `set_promise_yield_receipt` stores the parked receipt at `TrieKey::PromiseYieldReceipt{receiver_id, data_id}` [1](#0-0) , and `enqueue_promise_yield_timeout` records `{account_id, data_id, expires_at}` in the per-shard `PromiseYieldTimeout` queue [2](#0-1) .
- `remove_account` only clears `Account`, `ContractCode`, `AccessKey`/gas-key-nonce, and `ContractData` keys for the account — it does **not** touch `PromiseYieldReceipt`, `PromiseYieldStatus`, `YieldIdToDataId`/`DataIdToYieldId`, or dequeue any `PromiseYieldTimeout` entries [3](#0-2) .
- `resolve_promise_yield_timeouts` fires a `PromiseResume{data: None}` purely based on `state_update.contains_key(&promise_yield_key)` where `promise_yield_key = TrieKey::PromiseYieldReceipt{receiver_id: queue_entry.account_id, data_id}` — it never checks that the account still exists, was not deleted/recreated, or matches any incarnation marker [4](#0-3) .
- On the resume path (whether via real `promise_yield_resume` or the timeout), `process_receipt`'s `PromiseResume` arm fetches the stale `get_promise_yield_receipt(state_update, account_id, data_id)` and executes it via `apply_action_receipt` [5](#0-4) , with `actor_id` seeded from that stale receipt's `predecessor_id` (same account) at `apply_action_receipt` entry [6](#0-5) .
- `action_delete_account` never removes or invalidates the yield receipt / status / queue entry, and it explicitly permits deletion once `actor_id == account_id`, no locked stake, storage-usage below `MAX_ACCOUNT_DELETION_STORAGE_USAGE`, and gas-key burn below the cap — none of which reference pending yields [7](#0-6) .

This matches the described attack path and is a genuine gap: deleting an account does not purge its `PromiseYieldReceipt`/`PromiseYieldStatus`/queued `PromiseYieldTimeout` entries, so a stale self-callback (created before deletion, with attacker-chosen method/args/gas) can later be delivered against a freshly re-created account of the same name, executing with `actor_id == account_id` (i.e., full self/owner trust) regardless of who now controls that account or what code is deployed on it.

### Title
Stale PromiseYieldReceipt/PromiseYieldStatus/PromiseYieldTimeout survive account deletion and execute against a re-created account with owner-level actor_id - ([File: core/store/src/utils/mod.rs])

### Summary
`remove_account` (invoked by `action_delete_account`) removes `Account`, `ContractCode`, `AccessKey`/gas-key, and `ContractData` trie entries for a deleted account, but never clears any pending `TrieKey::PromiseYieldReceipt`, `TrieKey::PromiseYieldStatus`, `TrieKey::YieldIdToDataId`/`DataIdToYieldId`, or dequeues the account's `TrieKey::PromiseYieldTimeout` entry. If the same account name is subsequently re-created, either an attacker-issued `promise_yield_resume` or the automatic timeout-queue processing (`resolve_promise_yield_timeouts`) will deliver the stale, pre-deletion `PromiseYield` action receipt against the new account, executing it with `actor_id == account_id` (self/owner-level trust), since neither check re-validates account identity/incarnation.

### Finding Description
An unprivileged attacker who fully controls an account `A` (as owner and as the deployer of `A`'s contract) can:

1. From `A`'s own contract, call `promise_yield_create(method_name, arguments, gas, ...)` (host function at `runtime/near-vm-runner/src/logic/logic.rs:3660`). Because `create_promise_yield_receipt` always uses `receiver_id = current_account_id` (`runtime/runtime/src/ext.rs:353-369`), this creates a self-targeted `PromiseYield` action receipt with attacker-chosen `method_name`/`arguments`/`gas`. When this receipt is delivered/processed, it is persisted via `set_promise_yield_receipt` at `TrieKey::PromiseYieldReceipt{receiver_id: A, data_id}` (`core/store/src/utils/mod.rs:200-212`), its status is `PromiseYieldStatus::Yielded` at `TrieKey::PromiseYieldStatus{A, data_id}`, and a `TrieKey::PromiseYieldTimeout{index}` queue entry `{account_id: A, data_id, expires_at}` is enqueued (`core/store/src/utils/mod.rs:181-198`).
2. In a subsequent receipt, `A` (as its own predecessor/actor) issues `DeleteAccountAction`. `check_actor_permissions` allows this because `actor_id == account_id == A`, and `action_delete_account` (`runtime/runtime/src/actions.rs:314-390`) checks only storage size, locked stake, and gas-key burn cap — none related to pending yields — then calls `remove_account(state_update, A)`, which deletes `Account`/`ContractCode`/`AccessKey`/`ContractData` but leaves the `PromiseYieldReceipt`, `PromiseYieldStatus`, and queued `PromiseYieldTimeout` entries intact in the trie (`core/store/src/utils/mod.rs:504-575`).
3. The attacker (who controls the parent namespace, e.g. `A = "x.attacker.near"`) re-creates `A` via `CreateAccountAction`, receiving a fresh, empty account.
4. Either the attacker submits `promise_yield_resume` for the recorded `data_id`, or waits for `resolve_promise_yield_timeouts` (`runtime/runtime/src/lib.rs:3009-3105`) to fire automatically once `expires_at <= block_height`. That function only checks `state_update.contains_key(&promise_yield_key)` — true, since it was never cleared — and synthesizes a `PromiseResume{data: None}` destined to `queue_entry.account_id == A`.
5. `process_receipt`'s `PromiseResume` handling (`runtime/runtime/src/lib.rs:1500-1562`) fetches the still-present stale `PromiseYield` receipt via `get_promise_yield_receipt(state_update, account_id, data_id)` and runs it through `apply_action_receipt`. There, `actor_id` is initialized from `receipt.predecessor_id()` (`runtime/runtime/src/lib.rs:855`), which for this self-yield receipt equals `A` — the same as `account_id`. The attacker-chosen `FunctionCall` action executes on the newly re-created `A`, with `check_actor_permissions`/host-function logic treating it as `actor_id == account_id`, i.e., full self/owner trust — even though the account was destroyed and re-created in between and may now run entirely different code/ownership than what existed when the yield was created.

Existing checks (nonce, access-key permission, storage-staking, gas metering, size limits) do not stop this because the yield-create and delete-account transactions are each individually valid; the bug is a missing cleanup step in `remove_account`, and a missing incarnation/liveness check in `resolve_promise_yield_timeouts`/the `PromiseResume` handler.

### Impact Explanation
This is an authorization-escalation / stale-state-execution bug (NEAR bounty category: authorization escalation across promises / stale-state execution on a re-created account). A stale, attacker-crafted callback with owner-level (`actor_id == account_id`) trust executes against a re-created account whose new state/contract/ownership never consented to or expected this call. If the re-created account is later transferred, sold, or independently re-registered by a different party who deploys a contract with "self-call only" privileged methods (a common pattern, e.g. `assert_eq!(env::predecessor_account_id(), env::current_account_id())`), the attacker's pre-planted yield resume can trigger those privileged methods, potentially draining funds or corrupting the new owner's contract state. It also generally violates value/authorization conservation: state associated with a deleted identity (`A`'s pending promise) persists and gets misattributed as a legitimate self-call on the new identity sharing that name.

### Likelihood Explanation
Fully attacker-reachable with only unprivileged, self-owned resources: the attacker needs to own account `A` (or a namespace under which they can freely create/delete/re-create a sub-account), deploy their own contract, call `promise_yield_create` on themselves, then self-delete and self-recreate the account — all standard, permitted actions. No validator/node/RPC privilege is required. The only extra requirement for meaningful escalation is that the re-created account later come under the control of a party who deploys code trusting self-calls, which is a realistic and common scenario in NEAR contract architecture (subaccount factories, marketplaces for named subaccounts, etc.); even without that, it demonstrates a stale-state execution and violates the account-deletion cleanliness invariant. The bug is deterministic and repeatable, gated only by the fixed yield timeout window (or explicit resume).

### Recommendation
In `remove_account` (`core/store/src/utils/mod.rs`), also iterate and remove all `PromiseYieldReceipt`, `PromiseYieldStatus`, `YieldIdToDataId`, and `DataIdToYieldId` trie entries keyed under the deleted `account_id` (these all carry the account id in their key prefix per `TrieKey::COLUMNS_WITH_ACCOUNT_ID_IN_KEY`). Additionally, in `resolve_promise_yield_timeouts` and the `PromiseResume` branch of `process_receipt`, invalidate/skip queued timeouts and resumes whose target account no longer exists (or was deleted and re-created since the yield was scheduled), e.g. by checking account existence or an account-incarnation/nonce marker before treating the resume as belonging to the current account.

### Proof of Concept
Test-loop integration test (extending `test-loop-tests/src/tests/yield_timeouts.rs` patterns):
1. Deploy a contract to account `A = "x.attacker.near"` with a `main` method that calls `promise_yield_create` on `env::current_account_id()` with `method_name = "priv_action"`, storing the returned `data_id`.
2. In a subsequent transaction, have `A` submit `Action::DeleteAccount { beneficiary_id: attacker.near }`.
3. Assert via `get_yield_data_ids_in_state`-style helper that the `PromiseYieldReceipt`/`PromiseYieldStatus` entries for `A`/`data_id` are still present in state after deletion (proving `remove_account` did not clean them).
4. Re-create `A` via `Action::CreateAccount` from `attacker.near`, and deploy a *different* contract exposing `priv_action` that checks `predecessor_account_id() == current_account_id()` before performing a privileged effect (e.g., transferring balance or setting an owner field).
5. Advance blocks until `resolve_promise_yield_timeouts` fires the synthetic `PromiseResume` for the stale `data_id` (per `TEST_CONFIG_YIELD_TIMEOUT_LENGTH`), or directly submit `promise_yield_resume`.
6. Assert the recreated `A`'s `priv_action` executed successfully (i.e., the privileged effect took place) despite the account having been deleted and freshly re-created with unrelated code — proving the stale callback ran with owner-level `actor_id == A` trust it should never have been granted against the new incarnation.

/// Removes account, code and all access keys and gas keys associated to it.
pub fn remove_account(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
) -> Result<RemoveAccountResult, StorageError> {
    state_update.remove(TrieKey::Account { account_id: account_id.clone() });
    state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });

    let mut gas_key_nonce_count: usize = 0;
    let mut gas_key_nonce_total_key_bytes: usize = 0;

    // Removing access keys and gas key nonces
    let lock = state_update.trie().lock_for_iter();
    let mut keys_to_remove: Vec<TrieKey> = Vec::new();
    for raw_key in state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_access_keys(account_id), &lock)?
    {
        let raw_key = raw_key?;
        let key_handle = trie_key_parsers::parse_key_handle_from_access_key_key(
            &raw_key, account_id,
        )
        .map_err(|_e| {
            StorageError::StorageInconsistentState(
                "Can't parse key handle from raw key for AccessKey".to_string(),
            )
        })?;
        let nonce_index =
            trie_key_parsers::parse_nonce_index_from_gas_key_key(&raw_key, account_id, &key_handle)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse nonce index from raw key for AccessKey".to_string(),
                    )
                })?;
        if let Some(index) = nonce_index {
            gas_key_nonce_count += 1;
            gas_key_nonce_total_key_bytes += raw_key.len();
            keys_to_remove.push(TrieKey::gas_key_nonce(
                account_id.clone(),
                key_handle.clone(),
                index,
            ));
        } else {
            keys_to_remove.push(TrieKey::access_key(account_id.clone(), key_handle.clone()));
        }
    }
    drop(lock);

    for trie_key in keys_to_remove {
        state_update.remove(trie_key);
    }

    // Removing contract data
    let lock = state_update.trie().lock_for_iter();
    let data_keys = state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_contract_data(account_id, &[]), &lock)?
        .map(|raw_key| {
            trie_key_parsers::parse_data_key_from_contract_data_key(&raw_key?, account_id)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse data key from raw key for ContractData".to_string(),
                    )
                })
                .map(Vec::from)
        })
        .collect::<Result<Vec<_>, _>>()?;
    drop(lock);

    for key in data_keys {
        state_update.remove(TrieKey::ContractData { account_id: account_id.clone(), key });
    }
    Ok(RemoveAccountResult { gas_key_nonce_count, gas_key_nonce_total_key_bytes })
}

pub(crate) fn action_delete_account(
    state_update: &mut TrieUpdate,
    account: &mut Option<Account>,
    actor_id: &mut AccountId,
    receipt: &Receipt,
    result: &mut ActionResult,
    account_id: &AccountId,
    delete_account: &DeleteAccountAction,
    config: &RuntimeConfig,
    current_protocol_version: ProtocolVersion,
) -> Result<(), StorageError> {
    let account_ref = account.as_ref().unwrap();
    let account_storage_usage = if ProtocolFeature::FixDeleteAccountGlobalContractStorageUsage
        .enabled(current_protocol_version)
    {
        let contract_storage = get_contract_storage_usage(state_update, account_id, account_ref)?;
        account_ref.storage_usage().saturating_sub(contract_storage)
    } else {
        // Legacy behavior: only subtracts local contract code, misses the
        // global contract identifier overhead.
        let account_storage_usage = account_ref.storage_usage();
        let code_len = get_code_len_or_default(
            state_update,
            account_id.clone(),
            account_ref.local_contract_hash().unwrap_or_default(),
        )?;
        debug_assert!(
            code_len == 0 || account_storage_usage > code_len,
            "account storage usage should be larger than code size. storage usage: {}, code size: {}",
            account_storage_usage,
            code_len
        );
        account_storage_usage.saturating_sub(code_len)
    };
    if account_storage_usage > Account::MAX_ACCOUNT_DELETION_STORAGE_USAGE {
        result.result =
            Err(ActionErrorKind::DeleteAccountWithLargeState { account_id: account_id.clone() }
                .into());
        return Ok(());
    }
    let gas_key_balance_to_burn = compute_gas_key_balance_sum(state_update, account_id)?;
    if gas_key_balance_to_burn > GasKeyInfo::MAX_BALANCE_TO_BURN {
        result.result = Err(ActionErrorKind::GasKeyBalanceTooHigh {
            account_id: account_id.clone(),
            public_key: None,
            balance: gas_key_balance_to_burn,
        }
        .into());
        return Ok(());
    }
    // We use current amount as a pay out to beneficiary.
    let account_balance = account_ref.amount();
    if account_balance > Balance::ZERO {
        result
            .new_receipts
            .push(Receipt::new_balance_refund(&delete_account.beneficiary_id, account_balance));
    }
    let remove_result = remove_account(state_update, account_id)?;
    result.tokens_burnt =
        result.tokens_burnt.checked_add(gas_key_balance_to_burn).ok_or_else(|| {
            StorageError::StorageInconsistentState("tokens_burnt overflow".to_string())
        })?;
    if remove_result.gas_key_nonce_count > 0 {
        let compute = storage_removes_compute(
            &config.wasm_config.ext_costs,
            remove_result.gas_key_nonce_count,
            remove_result.gas_key_nonce_total_key_bytes,
            AccessKey::NONCE_VALUE_LEN * remove_result.gas_key_nonce_count,
        );
        result.compute_usage = safe_add_compute(result.compute_usage, compute).map_err(|_| {
            StorageError::StorageInconsistentState("compute_usage overflow".to_string())
        })?;
    }
    *actor_id = receipt.predecessor_id().clone();
    *account = None;
    Ok(())
}
