### Title
Unbounded array allocation from unchecked ABI-encoded length field in precompiled contract input parsing — Denial of Service - ([File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java])

### Summary
The reported Pillow CVE is a classic "attacker-controlled size field drives an unbounded memory allocation" bug: a container declares an image size that is never checked against the actual payload before memory is reserved for it. `PrecompiledContracts.java` contains the same bug-class pattern in its ABI-array extraction helpers used when parsing the raw `data` blob passed to certain precompiled contracts.

### Finding Description
`extractBytes32Array`, `extractBytesArray`, and `extractSigArray` read an array-length word directly from attacker-supplied `DataWord[]` (i.e., the 32-byte words of the precompile call's input `data`) and immediately allocate a Java array sized by that value, with no upper bound check against the actual size of `data`: [1](#0-0) [2](#0-1) [3](#0-2) 

In each case, `len` comes from `words[offset].intValueSafe()` — a value fully controlled by the calldata a contract caller supplies to invoke the precompile — and is used verbatim as the size of a newly allocated array (`new byte[len][]`), with no comparison to `words.length`, `data.length`, or any energy-derived cap before the allocation happens. This mirrors the Pillow BLP flaw: the declared "size" of a nested structure is trusted and used to size a buffer before the actual bytes backing that size are verified to exist.

Energy for these precompiles is computed from the actual size of the supplied `data` (e.g. the generic pattern seen in `Identity`/`Sha256` energy costs at [4](#0-3) ), not from the decoded `len` value used inside `extractBytesArray`/`extractBytes32Array`/`extractSigArray`. This means a caller can submit a tiny amount of calldata (a handful of 32-byte words) that is cheap in energy, yet encodes a length word close to `Integer.MAX_VALUE`, forcing the node to attempt to allocate an array of that many elements while executing the precompiled contract on behalf of the transaction.

### Impact Explanation
An out-of-bounds/huge `len` value passed to `new byte[len][]` throws `OutOfMemoryError` (or, depending on JVM heap headroom, causes severe GC pressure and heap exhaustion) inside precompiled-contract execution, which runs as part of ordinary TVM contract-call processing during block application. If this error is not caught at a sufficiently high layer around precompile execution, it can propagate out of the TVM execution path used by `Manager`'s block-application logic, potentially crashing or stalling the node process handling that block — a denial-of-service condition triggerable by any account able to broadcast a contract-calling transaction that reaches one of these precompiled contracts.

### Likelihood Explanation
This is reachable by an unprivileged party: any account can send a `TriggerSmartContract` transaction (or have a deployed contract) that calls a precompiled contract using these helpers, supplying a crafted length word in the input `data`. No special privileges, staking, or SR/witness status are required — a single signed transaction with attacker-chosen ABI-encoded calldata is sufficient to reach `extractBytesArray`/`extractBytes32Array`/`extractSigArray`.

### Recommendation
Before allocating arrays sized by `len` in `extractBytes32Array`, `extractBytesArray`, and `extractSigArray`, validate `len` against the actual bounds of `words`/`data` (e.g., reject if `len` would require reading beyond `words.length` or `data.length`, similar to the bounds checks already present in `RLP.calcLength`/`RLP.verifyLength`, see [5](#0-4)  for the existing pattern to replicate). Additionally, ensure energy costs charged for these precompiles scale with the decoded `len`, not just the raw `data.length`, so oversized declared lengths cannot be processed cheaply.

### Proof of Concept
Craft `data` for a precompile call that invokes `extractBytesArray`/`extractBytes32Array`/`extractSigArray` such that the word at the expected `offset` (attacker-controlled) is set to a large value (e.g. `0x000000000000000000000000000000000000000000000000000000FFFFFFFF` or similar, whatever `intValueSafe()` returns as its clamp/near-max value) while the rest of `data` is only a few words long. Invoke the precompile via a `TriggerSmartContract` transaction. During execution, `new byte[len][]` in the corresponding helper attempts to allocate an array sized by the crafted `len`, independent of the small actual `data.length`, causing `OutOfMemoryError`/severe memory pressure on the executing node.

Note: I was unable to fully confirm from the index which specific precompiled contract(s) call `extractBytesArray`/`extractSigArray` at their call sites (only the definitions and 3 call-site matches were located, and the surrounding call context — the precompile name and exact `offset` semantics — could not be retrieved within the available tool calls), nor the exact clamp behavior of `DataWord.intValueSafe()`. I recommend a Devin session with full filesystem access to confirm the exact call sites, `intValueSafe()` semantics, and whether the resulting `OutOfMemoryError` is caught anywhere in the TVM execution wrapper before it can affect block processing.

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
