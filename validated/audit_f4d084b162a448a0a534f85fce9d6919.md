### Title
Unstaked attackers can indefinitely occupy the 25% connection-admission headroom by stalling post-handshake, starving legitimate new-connection admission - (File: streamer/src/nonblocking/quic.rs)

### Summary
`ClientConnectionTracker::new` increments `stats.open_connections` at accept-time and only decrements it on `Drop`, but a connection is only inserted into a `ConnectionTable` (and thus becomes prunable/evictable) after `qos.try_add_connection` succeeds later in `setup_connection`. An attacker that completes the QUIC handshake and then never opens a stream (so `try_add_connection` never resolves/succeeds) keeps its `ClientConnectionTracker` alive and its slot counted in `open_connections` indefinitely, without ever appearing in `staked_connection_table`/`unstaked_connection_table`, so it is invisible to the eviction/pruning logic that operates on `ConnectionTable::total_size`.

### Finding Description
In the accept loop (`streamer/src/nonblocking/quic.rs`), for each incoming connection the server calls: [1](#0-0) 
`ClientConnectionTracker::new` is the *only* gate on `max_concurrent_connections()`, and it increments `stats.open_connections` immediately: [2](#0-1) 
The count is decremented only in `Drop`: [3](#0-2) 
`max_concurrent_connections()` for `SwQos`/`SimpleQos` is deliberately set to `(max_staked + max_unstaked) * 5 / 4`, i.e. only 25% headroom over the "real" capacity: [4](#0-3) 
That headroom is intended to absorb legitimate in-flight handshakes before they are admitted into a `ConnectionTable` via `try_add_connection` (`streamer/src/nonblocking/quic.rs:1008-1051`, `streamer/src/nonblocking/simple_qos.rs:182-234`, `streamer/src/nonblocking/swqos.rs:182-239`). Only connections that have entered a `ConnectionTable` are visible to/prunable by `prune_oldest`/`prune_random` (`streamer/src/nonblocking/quic.rs:982-1006` and `ConnectionTable::total_size`). Because `ClientConnectionTracker` is created and counted *before* `try_add_connection` resolves, and it is handed off into `setup_connection` (spawned as a task) without any global timeout that force-drops it if the client never opens a stream, an attacker can:
1. Open a QUIC handshake to the leader's public TPU port (no stake/config required).
2. Complete the handshake so `ClientConnectionTracker::new` succeeds and `open_connections` increments.
3. Never open a stream / never let `qos.try_add_connection` resolve to success or failure (e.g., stall or keep the connection idle without triggering QUIC idle timeout, since QUIC connections can be kept alive via keep-alive packets well within `QUIC_MAX_TIMEOUT`).
4. Repeat with just enough connections/rate to keep `open_connections` pinned near `max_concurrent_connections() - 1`, without any of these attacker connections ever being inserted into `staked_connection_table`/`unstaked_connection_table` and hence never being subject to `prune_oldest`/`prune_random` eviction (which only prunes entries already in a `ConnectionTable`).
5. Legitimate new handshakes then hit the `ClientConnectionTracker::new` check, get `Err(())`, and increment `refused_connections_too_many_open_connections`: [1](#0-0) 

The per-IP and overall connection-attempt rate limiters (`rate_limiter`, `overall_connection_rate_limiter`) only throttle the *rate* of new incoming attempts, not the *duration* an already-accepted connection tracker can occupy the counted slot; they do not address a slow/low-rate but persistent occupation strategy. There is no independent timeout in the accept path that forcibly drops `ClientConnectionTracker` for connections that stall between accept and successful `try_add_connection`, so headroom capacity reserved for legitimate handshake concurrency can be squatted on indefinitely by attacker-controlled, un-admitted connections.

### Impact Explanation
This is a QoS/DoS-style capacity-exhaustion bug: legitimate new connection attempts are refused (`refused_connections_too_many_open_connections`) purely due to attacker connections that were never staked, never authenticated beyond a raw handshake, and never actually admitted into any `ConnectionTable`. This matches the stated scope: "an unprivileged client can bypass or unfairly capture connection, stream, or per-IP QoS limits and starve legitimate senders of TPU capacity," causing degraded TPU availability for legitimate stake-weighted or unstaked senders during the attack window.

### Likelihood Explanation
Feasible with only unprivileged network access to the public TPU QUIC port — no stake, keys, or special config needed. The attacker only needs to complete QUIC handshakes (cheap, and per-IP/overall rate limiters only throttle burst rate, not standing occupancy) and hold connections open without opening streams. Using multiple source IPs (or a slow-but-steady handshake rate under the rate limiter) an attacker can sustain occupation of the ~25% headroom slots indefinitely, since nothing else forces `ClientConnectionTracker` to drop before the QUIC idle timeout, and stalling before `try_add_connection` means the attacker never needs to satisfy any stream-based limits.

### Recommendation
Add a bounded timeout in the accept/`setup_connection` path that guarantees a `ClientConnectionTracker` is dropped (freeing its `open_connections` slot) within a short deadline if `qos.try_add_connection` has not resolved (success or failure) by then — independent of QUIC idle-timeout/keep-alive behavior. Alternatively, track "pending admission" connections separately from admitted ones with their own bounded queue/timeout so that stalled pending connections cannot indefinitely consume the shared 25% headroom meant for genuine in-flight handshakes.

### Proof of Concept
Integration test plan (extending the existing test harness in `streamer/src/nonblocking/quic.rs` / `simple_qos.rs`, using `setup_quic_server` and `make_client_endpoint`):
1. Configure a test QoS with small `max_staked_connections`/`max_unstaked_connections` (e.g., 4 total → `max_concurrent_connections() == 5`).
2. Spawn `N = max_concurrent_connections() - 1` client endpoints that connect via `quinn::Endpoint::connect` to the server and, after the handshake completes, do **not** open any uni/bi stream and do not close the connection (hold it open, relying on QUIC keep-alives to stay under idle timeout).
3. Assert `stats.open_connections.load(Ordering::Relaxed) == N` while asserting each attacker's `staked_connection_table`/`unstaked_connection_table` (`ConnectionTable::total_size`) remains `0` for these attacker connections (i.e., they never got admitted).
4. Attempt one more legitimate client connection (opens a stream immediately after connecting).
5. Assert `stats.refused_connections_too_many_open_connections.load(Ordering::Relaxed) >= 1` for this legitimate client, while confirming the attacker connections are still holding their slots and are absent from `ConnectionTable::total_size`.
6. Optionally wait near `QUIC_MAX_TIMEOUT` and show attacker connections remain alive (keep-alive/no idle timeout triggered), continuing to refuse legitimate connections.

impl ClientConnectionTracker {
    /// Check the max_concurrent_connections limit and if it is within the limit
    /// create ClientConnectionTracker and increment open connection count. Otherwise returns Err
    fn new(stats: Arc<StreamerStats>, max_concurrent_connections: usize) -> Result<Self, ()> {
        let open_connections = stats.open_connections.fetch_add(1, Ordering::Relaxed);
        if open_connections >= max_concurrent_connections {
            stats.open_connections.fetch_sub(1, Ordering::Relaxed);
            debug!(
                "There are too many concurrent connections opened already: open: \
                 {open_connections}, max: {max_concurrent_connections}"
            );
            return Err(());
        }

        Ok(Self { stats })
    }
