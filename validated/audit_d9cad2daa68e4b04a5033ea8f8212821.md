### Title
DSA signature forgery via missing domain-parameter validation in `crypto/dsa.Verify` and `x509.parsePublicKey` - (File: src/crypto/dsa/dsa.go, src/crypto/x509/parser.go)

### Summary
`crypto/dsa.Verify` implements only the FIPS 186-3 §4.7 arithmetic checks on `r` and `s` but never validates that the domain parameters `(P, Q, G)` and public value `Y` form a well-formed DSA group (e.g., that `G` has order `Q` mod `P`, or that `Y = G^X mod P` for some `X`). `x509.parsePublicKey` for `oidPublicKeyDSA` similarly only rejects non-positive `P, Q, G, Y` and performs no primality or group-membership checks. An attacker who supplies a DSA public key/certificate with degenerate parameters such as `G=1, Y=1` can make the verification equation `v = (G^u1 * Y^u2 mod P) mod Q` collapse to `1` for any hash, and by also choosing `r=1` (a valid value satisfying `0 < r < Q`), any signature with an `s` invertible mod `Q` will verify as valid regardless of the hashed message.

### Finding Description
Attacker input: a crafted DSA public key (raw `dsa.PublicKey` or an X.509 certificate encoding `oidPublicKeyDSA` SPKI) with `P` prime-looking but `G=1`, `Y=1`.
Go entry points:
- `crypto/x509.ParsePKIXPublicKey` / `parsePublicKey` (src/crypto/x509/parser.go:396-421) parses the DSA `P, Q, G, Y` from ASN.1 and only checks `Sign() <= 0`, never that `G` is a generator of order `Q` mod `P` or that `Y = G^X mod P`. [1](#0-0) 
- `crypto/dsa.Verify` (src/crypto/dsa/dsa.go:290-330) computes `w = s^-1 mod Q`, `u1 = hash*w mod Q`, `u2 = r*w mod Q`, then `v = (G^u1 * Y^u2 mod P) mod Q`, and accepts iff `v == r`. [2](#0-1) 

Failed check: neither function verifies `G^Q mod P == 1` and `G != 1`, nor that `Y` lies in the subgroup generated by `G`. With `G=1, Y=1`, `G^u1 mod P = 1` and `Y^u2 mod P = 1` for any `u1, u2`, so `v` collapses to `1 mod P mod Q = 1` independent of the hash or `s`. Choosing `r=1` (which passes the `0 < r < Q` range check at src/crypto/dsa/dsa.go:301) and any `s` in `(0, Q)` with `gcd(s,Q)=1` makes `Verify` return `true` for an arbitrary hash — an unconditional forgery, structurally identical to the jsrsasign `g=1, y=1, r=1` bypass described in the advisory.

Sink: `dsa.Verify` return value is relied upon by callers (e.g., `crypto/x509` certificate/CRL signature checks and any application directly calling `dsa.Verify`) as proof of authenticity.

### Impact Explanation
If a certificate authority or self-signed certificate encodes a DSA public key with degenerate parameters (`G=1, Y=1`), any consumer that parses it via `x509.ParsePKIXPublicKey`/`ParseCertificate` and later checks a DSA signature against that key via `dsa.Verify` will accept an arbitrary, attacker-forged signature over any message/hash — a straightforward authentication/integrity bypass (CWE-347) matching the CVE's class. This is a legitimate PUBLIC-track class of issue in `crypto/dsa`, though its practical blast radius is small because DSA is deprecated (the package doc already marks it `Deprecated`, `L1024N160` weak) and is not used by the standard TLS certificate-verification chain-building logic for trusted default roots.

### Likelihood Explanation
Exploitability requires a victim workflow that (a) accepts an attacker-supplied DSA public key or DSA-signed X.509 artifact, and (b) calls `dsa.Verify` (directly or via `crypto/x509`) on attacker-controlled signature data without first validating parameter well-formedness (which Go's `dsa` package documents as the caller's own responsibility only implicitly, and does not enforce). This matches an ordinary "verify a signature/certificate from an untrusted party" workflow, unauthenticated by an unprivileged attacker who controls only the key/cert/signature bytes — consistent with the required "no privileged/trusted premise."

### Recommendation
In `crypto/dsa.Verify` (src/crypto/dsa/dsa.go), reject degenerate domain parameters before computing `v`: require `G > 1`, `G < P`, `G^Q mod P == 1` (order check), and `Y != 1` / `Y < P`. Optionally also validate primality of `P` and `Q` where feasible for the caller's threat model, or add a `Parameters.Validate()`/documented precondition and enforce it in both `dsa.Verify` and `crypto/x509` DSA public-key parsing (`parsePublicKey`, src/crypto/x509/parser.go:396-421), rejecting keys/certs with `G` or `Y` equal to 0 or 1.

### Proof of Concept

```go
package dsa_test

import (
	"crypto/dsa"
	"math/big"
	"testing"
)

// TestDSAForgeryDegenerateParams demonstrates that dsa.Verify accepts an
// arbitrary signature/hash when domain parameters are degenerate (G=1, Y=1),
// analogous to CVE-2026-4600 in jsrsasign.
func TestDSAForgeryDegenerateParams(t *testing.T) {
	p := new(big.Int).SetInt64(23) // toy "prime" for illustration
	q := new(big.Int).SetInt64(11) // toy subgroup order
	g := big.NewInt(1)             // degenerate generator
	y := big.NewInt(1)             // degenerate public value

	pub := &dsa.PublicKey{
		Parameters: dsa.Parameters{P: p, Q: q, G: g},
		Y:          y,
	}

	r := big.NewInt(1) // forged r, passes 0 < r < Q
	s := big.NewInt(3) // any s with gcd(s, Q) == 1

	hash := []byte("attacker chosen message, never signed")

	if !dsa.Verify(pub, hash, r, s) {
		t.Fatal("expected forged signature to be accepted due to missing domain-parameter validation")
	}
	// If this assertion passes, Verify incorrectly accepted a forged
	// signature for an arbitrary hash using degenerate G=1, Y=1 parameters.
}
```
Expected result on the current implementation: `dsa.Verify` returns `true`, confirming the forgery succeeds because `G^u1 * Y^u2 mod P` is always `1` when `G=Y=1`, matching `r=1` regardless of `hash` or `s`.
