### Title
Floating-point precision loss in the legacy Bancor exchange formula allows drain of `Exchange`/`ExchangeV2` liquidity pools - ([File: chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java])

### Summary
The WGPT Token incident is a classic AMM/liquidity-pool draining exploit where an attacker manipulates a bonding-curve price calculation within a small number of transactions to extract more value than the pool should allow. The java-tron on-chain TRX/TRC10 "bancor-style" exchange (`ExchangeCreateContract`/`ExchangeInjectContract`/`ExchangeTransactionContract`, reachable by any signed transaction from an unprivileged account) contains an analogous weakness: by default it prices trades using IEEE-754 `double` arithmetic and unchecked `long` addition/subtraction, rather than the newly-added, but off-by-default, `BigDecimal`-based "hardened" processor.

### Finding Description
`ExchangeCapsule.transaction()` selects the pricing engine based on the `hardenedCalc` flag: [1](#0-0) 

`hardenedCalc` is derived from `AbstractExchangeActuator.allowHarden()`, which reads the `ALLOW_HARDEN_EXCHANGE_CALCULATION` dynamic property — a committee-controlled proposal flag: [2](#0-1) 

Unless the committee has explicitly activated this proposal (tests in the repo consistently set it to `1` and reset it to `0` in `finally`, confirming `0`/disabled is the baseline state), every `ExchangeTransactionActuator`/`ExchangeInjectActuator`/`ExchangeWithdrawActuator` call routes through the legacy `ExchangeProcessor`, which computes the Bancor relay-token conversion using `double` math and `Math.pow`: [3](#0-2) 

and the surrounding balance bookkeeping in the actuators uses plain, non-overflow-checked `long` arithmetic in the non-hardened branch: [4](#0-3) 

Floating-point `pow`/division introduces rounding error on every trade. The project's own regression test explicitly demonstrates that the legacy (`double`) processor and the strict/BigDecimal processor diverge on identical inputs: [5](#0-4) 

Because `ExchangeCapsule.transaction()` is called on live pool reserves (`firstTokenBalance`/`secondTokenBalance`) that any account can move via `ExchangeTransactionContract`/`ExchangeInjectContract`, an attacker can chain a sequence of carefully-sized buy/sell (and inject/withdraw) calls within one or a few blocks to repeatedly harvest the double-precision rounding bias in their favor — the same "manipulate an on-chain bonding-curve price within a short transaction window to extract more value than deposited" pattern used in the WGPT flash-loan incident, except here the manipulated primitive is java-tron's own AMM-style `Exchange` reserve rather than an external token contract.

### Impact Explanation
Repeated exploitation lets an attacker extract TRX/TRC10 tokens from the `Exchange`/`ExchangeV2` pool reserves beyond what the bonding curve should yield, i.e. theft of pooled funds contributed by other users, and can also push pool reserves toward zero/underflow, effectively breaking price discovery ("closing" the exchange for legitimate users) — an unauthorized asset-transfer / fund-theft impact from an unprivileged, self-signed transaction.

### Likelihood Explanation
Any account can create an exchange pair and repeatedly call `ExchangeInjectContract`/`ExchangeTransactionContract`/`ExchangeWithdrawContract` with no special permission — this is a fully public, unprivileged transaction path with fee-only cost. Because the hardened math path is opt-in via committee proposal, most networks that have not activated `ALLOW_HARDEN_EXCHANGE_CALCULATION` remain on the vulnerable legacy `double`-based processor at all times, keeping likelihood non-trivial. Exploitation requires the attacker to script many small, carefully computed trades, which raises the bar somewhat but is well within reach of an automated bot, consistent with how the referenced flash-loan-style incident was executed.

### Recommendation
- Make `SafeExchangeProcessor` (BigDecimal-based, overflow-checked) the default/mandatory pricing engine rather than gating it behind an opt-in proposal, or set `ALLOW_HARDEN_EXCHANGE_CALCULATION` to `1` by default on new/existing chains.
- Add strict pool-invariant checks (e.g., constant-product/relay-supply monotonicity assertions) in `ExchangeCapsule.transaction()` for the legacy path so that rounding bias cannot compound over repeated calls.
- Consider deprecating the `double`-based `ExchangeProcessor` entirely and removing the fork/toggle once the hardened path is proven stable.

### Proof of Concept
1. Create an `Exchange` pair with a small `firstTokenBalance`/`secondTokenBalance` via `ExchangeCreateContract`.
2. Repeatedly submit `ExchangeTransactionContract` trades alternating direction with quantities chosen to maximize the double-precision rounding bias in `ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply` (see divergence demonstrated in `ExchangeProcessorTest.testStrictMath`, where the legacy and BigDecimal-based results differ for identical inputs — `Assert.assertNotEquals(anotherTokenQuant, result)` at line 278).
3. Because `ALLOW_HARDEN_EXCHANGE_CALCULATION` defaults to `0`, every trade uses the vulnerable `ExchangeProcessor`, letting the attacker accumulate the per-trade rounding advantage across many transactions to drain the pool's reserve of TRX/TRC10 tokens contributed by other liquidity providers.

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
