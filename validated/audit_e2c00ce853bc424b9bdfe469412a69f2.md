### Title
Oversized `Attachment.content` from a remote peer's `GetAttachmentResponse` is committed to the AtlasDB BLOB table without any `attachments_max_size` check - ([File: stackslib/src/net/atlas/download.rs], [File: stackslib/src/net/atlas/mod.rs])

### Summary
The download-response path for Atlas attachments (`AttachmentsBatchStateContext::extend_with_attachments` → `AttachmentsBatchStateMachine::run_once` → `AtlasDB::insert_instantiated_attachment`) never checks `Attachment.content.len()` against `AtlasConfig.attachments_max_size` before writing the content into the SQLite `attachments` BLOB column. The only size guard, `AtlasDB::should_keep_attachment`, is wired into the locally-submitted-transaction path (`posttransaction.rs`), not into the peer-download path, so a malicious peer serving a `GetAttachmentResponse` can push an arbitrarily large blob through unauthenticated download traffic.

### Finding Description
`GetAttachmentResponse` is deserialized from hex-encoded JSON with no length limit: [1](#0-0) 

When a remote peer's HTTP response to an `AttachmentRequest` arrives, `extend_with_attachments` decodes it and inserts the attachment directly into the in-memory `attachments: HashSet<Attachment>` with no size check: [2](#0-1) 

Once the sub-state-machine reaches `Done`, every attachment collected this way is committed via `insert_instantiated_attachment`: [3](#0-2) 

`AtlasDB::insert_instantiated_attachment` computes `attachment.hash()` (i.e., `Hash160::from_data(&self.content)`) only as a primary key for the INSERT and writes `attachment.content` straight into the BLOB column, with no length check anywhere in this function: [4](#0-3) [5](#0-4) 

The only place `attachments_max_size` is enforced is `AtlasDB::should_keep_attachment`: [6](#0-5) 
That function is invoked solely from the locally-submitted-mempool-transaction path in `posttransaction.rs`, i.e., it never guards the P2P/RPC attachment-download path in `download.rs`. There is also no verification anywhere in `extend_with_attachments`/`run_once` that `Hash160::from_data(&response.attachment.content)` equals the `content_hash` that was actually requested (`AttachmentRequest.content_hash`), so the response content is trusted purely on the peer's say-so before both the missing size check and the missing hash check.

### Impact Explanation
A single unprivileged remote peer that is selected as an outbound sync source (any peer the node dials for Atlas sync, which requires no authentication or secret) can respond to an `AttachmentRequest` with a `GetAttachmentResponse` whose `content` is arbitrarily large (bounded only by the HTTP/message-size limits of the underlying transport, not by `attachments_max_size`). This content is written as a BLOB into the node's local SQLite `attachments` table via `insert_instantiated_attachment`, breaking the invariant `bytes_written_to_attachments_table <= attachments_max_size`. This is an unauthenticated storage/memory amplification: a single crafted response inflates local disk/DB storage far past the configured cap, and since attachments are not size-checked or hash-verified, this is repeatable per attachment request and can be triggered by any peer the node happens to sync attachments from.

### Likelihood Explanation
Preconditions: the target node must have Atlas/BNS attachment sync enabled and must select the attacker as one of its outbound sync peers for at least one attachment request (a routine condition for any participating peer, not a privileged state). The attacker needs no secret, no valid slot, and no prior trust — it merely needs to be an addressable peer the node queries. Attacker cost is a single crafted HTTP response per attachment request; the flaw is fully remote and requires no elevated port access beyond ordinary Atlas/RPC download traffic.

### Recommendation
In `AttachmentsBatchStateContext::extend_with_attachments` (stackslib/src/net/atlas/download.rs), before inserting `response.attachment` into `self.attachments`, validate that `response.attachment.content.len() as u32 <= atlas_config.attachments_max_size` and that `response.attachment.hash() == request.content_hash`; reject and penalize (via `report.bump_failed_requests()`) responses that fail either check instead of accepting them. Additionally, consider adding a defensive size (and optionally hash) check directly inside `AtlasDB::insert_instantiated_attachment` so the DB-write boundary itself enforces the bound regardless of caller.

### Proof of Concept
```rust
// stackslib/src/net/atlas/tests.rs (new test)
#[test]
fn test_oversized_attachment_accepted_without_size_check() {
    let atlas_config = AtlasConfig {
        contracts: HashSet::new(),
        attachments_max_size: 16, // small cap for the test
        max_uninstantiated_attachments: 10,
        uninstantiated_attachments_expire_after: 10,
        unresolved_attachment_instances_expire_after: 10,
        genesis_attachments: None,
    };
    let mut atlas_db = AtlasDB::connect_memory(atlas_config.clone()).unwrap();

    // Simulate a GetAttachmentResponse from a malicious peer with oversized content
    let oversized_content = vec![0xAA; 1024]; // >> attachments_max_size = 16
    let attachment = Attachment::new(oversized_content.clone());

    // Directly exercise the write path used by download.rs::run_once
    // (extend_with_attachments -> insert_instantiated_attachment)
    let result = atlas_db.insert_instantiated_attachment(&attachment);

    // No size check exists on this path: the write succeeds despite exceeding attachments_max_size
    assert!(result.is_ok(), "expected write to succeed, demonstrating missing size check");

    let stored = atlas_db.find_attachment(&attachment.hash()).unwrap().unwrap();
    assert!(
        stored.content.len() as u32 > atlas_config.attachments_max_size,
        "BOUNDS violated: bytes_written_to_attachments_table ({}) > attachments_max_size ({})",
        stored.content.len(),
        atlas_config.attachments_max_size
    );
}
```
This confirms `insert_instantiated_attachment` (and by extension the `extend_with_attachments`/`run_once` download-response path that calls it with peer-supplied `Attachment` data) commits content exceeding `AtlasConfig.attachments_max_size` with no rejection.

    pub fn extend_with_attachments(
        mut self,
        results: &mut BatchedRequestsResult<AttachmentRequest>,
    ) -> AttachmentsBatchStateContext {
        for (request, response) in results.succeeded.drain() {
            let report = self
                .peers
                .get_mut(request.get_url())
                .expect("Atlas: unable to retrieve reliability report for peer");

            let response = if let Some(r) = response {
                r
            } else {
                report.bump_failed_requests();
                continue;
            };

            if let Ok(response) = response.decode_atlas_get_attachment() {
                self.attachments.insert(response.attachment);
                report.bump_successful_requests();
            } else {
                report.bump_failed_requests();
            }
        }
        let mut events_ids = results.faulty_peers.keys().copied().collect::<Vec<usize>>();
        self.events_to_deregister.append(&mut events_ids);

        self
    }

    pub fn should_keep_attachment(
        &self,
        contract_id: &QualifiedContractIdentifier,
        attachment: &Attachment,
    ) -> bool {
        if !self.atlas_config.contracts.contains(contract_id) {
            info!(
                "Atlas: will discard posted attachment - {} not in supported contracts",
                contract_id
            );
            return false;
        }
        if attachment.content.len() as u32 > self.atlas_config.attachments_max_size {
            info!("Atlas: will discard posted attachment - attachment too large");
            return false;
        }
        true
    }

    pub fn insert_instantiated_attachment(
        &mut self,
        attachment: &Attachment,
    ) -> Result<(), db_error> {
        let now = util::get_epoch_time_secs() as i64;
        let tx = self.tx_begin()?;
        tx.execute(
            "INSERT OR REPLACE INTO attachments (hash, content, was_instantiated, created_at) VALUES (?, ?, 1, ?)",
            params![attachment.hash(), attachment.content, now],
        )?;
        tx.execute(
            "UPDATE attachment_instances SET is_available = 1 WHERE content_hash = ?1 AND status = ?2",
            params![attachment.hash(), AttachmentInstanceStatus::Checked],
        )?;
        tx.commit()?;
        Ok(())
    }
