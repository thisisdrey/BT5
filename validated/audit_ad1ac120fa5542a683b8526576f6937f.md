### Title
Attacker can dust-fill a victim's per-account token list via `DepositToken.deposit(..., onBehalfOf)` and `transfer`, permanently blocking the victim from any new collateral/deposit-token or debt-token position - ([File: contracts/Pool.sol])

### Summary
The `Pool` tracks two per-account sets — `depositTokensOfAccount` and `debtTokensOfAccount` — and reverts with `UserReachedMaxTokens` whenever their combined length would reach `MAX_TOKENS_PER_USER` (30). `DepositToken.deposit(uint256,address)` accepts an arbitrary `onBehalfOf_` beneficiary and `DepositToken.transfer` is unrestricted; both paths mint/move dust `msdToken`s to a victim and call `pool.addToDepositTokensOfAccount(victim)`, which reverts once the victim's combined set length hits the cap. Because `addDepositToken` itself caps the pool-level `depositTokens` list at `MAX_TOKENS_PER_USER`, an attacker can unilaterally saturate a victim's account list with dust of every listed collateral. ### Finding Description
- `Pool.onlyIfAdditionWillNotReachMaxTokens` reverts `UserReachedMaxTokens` when `debtTokensOfAccount.length(account) + depositTokensOfAccount.length(account) >= 30`. It guards `addToDepositTokensOfAccount` and `addToDebtTokensOfAccount`, which are only callable by registered `DepositToken`/`DebtToken` contracts (`SenderIsNotDepositToken`/`SenderIsNotDebtToken` checks).
- `DepositToken.deposit(amount_, onBehalfOf_)` pulls `underlying` from the caller via `safeTransferFrom` into `Treasury` and then `_mint`s `msdToken` to `onBehalfOf_` — there is no signature/consent check on the beneficiary. `_mint` calls `pool.addToDepositTokensOfAccount(account_)` whenever `balanceBefore == 0`.
- `DepositToken.transfer`/`transferFrom`/`seize` route through `_transfer`, which likewise adds the token to the recipient's list on a zero-to-nonzero balance transition. `_revertIfLocked` only constrains the sender's unlocked balance, not the recipient's list capacity.
- Once the victim's combined set is at 30, every subsequent operation that would add a *new* token to either set reverts: depositing a collateral type they don't yet hold, minting a synthetic/debt token type they don't yet hold (`DebtToken` mint → `addToDebtTokensOfAccount`), receiving a `transfer`/`seize` of a token type they don't hold, and leverage/`SmartFarmingManager` flows that deposit a new collateral on their behalf. This is the Metronome analog of the OpenQ issue: attacker-injected asset state makes subsequent protocol operations revert for that account.

### Impact Explanation
Liveness/griefing analogous to "bounty not claimable": the victim is DoS'd from opening positions in any collateral or synthetic type not already in their set, and inbound `msdToken` transfers (including liquidation `seize` proceeds directed at an account, or donations/gifts) revert. The victim can generally recover by removing dust entries — transferring or `withdraw`ing the dust — because dust balances are normally unlocked per `unlockedBalanceOf`. However, if the victim's position is at maximum utilization (`_issuableInUsd == 0`), `unlockedBalanceOf` returns 0 for every token, so they cannot move/burn the dust to free a slot until they first repay debt; the freeze persists as long as the position stays fully locked, and front-running re-dusting can re-saturate the list after each removal (deposit tokens are permissionlessly transferable). Funds are not directly stolen, but position management is forcibly blocked, which fits the "temporary freezing of funds / liveness" acceptance criteria.

### Likelihood Explanation
- Requires only an unprivileged EOA holding dust amounts of each whitelisted underlying (or dust `msdToken`s obtained by depositing once to self). No governor/keeper/oracle involvement.
- Cost scales with the number of listed deposit tokens; the pool-level cap is exactly `MAX_TOKENS_PER_USER` (30), so on a deployment with many listed collaterals the victim's list can be fully saturated by deposit-token dust alone. With fewer listed collaterals the attacker still consumes all free slots, blocking any new debt/collateral type.
- No existing guard prevents it: `nonReentrant`, `whenNotPaused`, `_revertIfLocked` (sender-side only), and `SynthContext` sender resolution do not stop a dust `deposit`/`transfer` to a third party.
- Residual weakness: because removal frees a slot, a determined victim can usually self-unblock; impact is strongest against fully-leveraged positions and recipients that cannot easily transact (contracts, SmartFarmingManager-mediated flows, liquidation-receiver paths).

### Recommendation
Do not let arbitrary callers add entries to another account's token sets without consent. Concretely:
- In `DepositToken._mint`/`_transfer`, skip `pool.addToDepositTokensOfAccount` (or the corresponding `onlyIfAdditionWillNotReachMaxTokens` revert) for recipient-initiated-vs-forced flows — e.g., allow the recipient list to be capped gracefully (return early instead of reverting) so dust transfers can't weaponize the revert, while still enforcing the cap on value-accruing operations; or
- Add a per-account opt-in/whitelist for `onBehalfOf_` deposits and inbound transfers of new token types; or
- Track entries by a different trigger (e.g., only add on `deposit` initiated via `Pool` for `msg.sender`, not on plain ERC20 `transfer`), and make `seize`/reward pushes tolerant of the cap.

### Proof of Concept
Foundry/Hardhat fork sketch against deployed `Pool`/`DepositToken`s:

```solidity
// victim: any EOA; attacker: any EOA holding dust of each listed underlying
IPool pool = IPool(POOL);
uint256 listed = pool.getDepositTokens().length; // up to MAX_TOKENS_PER_USER = 30

for (uint256 i; i < listed; ++i) {
    IDepositToken dt = IDepositToken(pool.getDepositTokens()[i]);
    IERC20 under = dt.underlying();
    deal(address(under), attacker, 1); // or attacker pre-deposits and uses dt.transfer(victim, 1)
    vm.prank(attacker);
    under.approve(address(dt), 1);
    vm.prank(attacker);
    dt.deposit(1, victim); // _mint(victim) -> pool.addToDepositTokensOfAccount(victim)
}

// victim's depositTokensOfAccount + debtTokensOfAccount now == 30

// any of these now revert with UserReachedMaxTokens():
// 1) debtToken.mint to victim for a synthetic they don't hold  -> addToDebtTokensOfAccount
vm.prank(victim);
vm.expectRevert(IPool.UserReachedMaxTokens.selector);
pool.mint(newSyntheticToken, amount); // via DebtToken -> addToDebtTokensOfAccount(victim)

// 2) deposit of a collateral type victim doesn't hold (only possible if a 31st existed;
//    otherwise demonstrate via a fresh deposit token added by governor or via inbound transfer)
vm.prank(attacker);
vm.expectRevert(IPool.UserReachedMaxTokens.selector);
IDepositToken(otherMsdToken).transfer(victim, 1); // _transfer -> addToDepositTokensOfAccount
```

The test asserts `UserReachedMaxTokens` reverts for all "new token type" operations on the victim after the dust loop, and that re-dusting after the victim withdraws one dust entry re-saturates the list. Caveat: exact repro depends on the number of listed collaterals on the target deployment; with fewer than 30 deposit tokens the attack fills all remaining free slots rather than the full cap.
