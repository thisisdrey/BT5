## Title
Entry Bytes Budget Reservation Is Never Released on Non-Terminal PoH Recording Failures, Permanently Shrinking a Leader's Block Capacity - (File: core/src/banking_stage/consumer.rs)

### Summary
`EntryBytesBudget::reserve()` optimistically pre-deducts a batch's serialized size from the per-slot `max_entry_bytes_per_slot` budget before the batch is actually recorded into PoH. If the subsequent recording attempt fails for a reason that does **not** end the slot (`PohRecorderError::ChannelFull` / `ChannelDisconnected`), the transactions are correctly marked retryable and their *cost-tracker* costs are rolled back via `remove_added_transaction_costs`, but the bytes already reserved from `entry_bytes_budget` are never given back. This is structurally the same bug class as the Kinetiq report: a resource ("buffer") is decremented in anticipation of a successful operation, the operation is aborted/retried, and nothing restores the decremented resource, permanently "locking" capacity that is never actually used.

### Finding Description
`EntryBytesBudget` only exposes a monotonic `reserve()` method with no `release`/`unreserve` counterpart: [1](#0-0) 

In `Consumer::execute_and_commit_transactions_locked`, bytes are reserved *before* the recording result is known: [2](#0-1) 

When recording fails, the code only rolls back cost-tracker state and marks transactions retryable — it never touches `entry_bytes_budget`: [3](#0-2) 

Critically, `record_transactions` can fail with `PohRecorderError::ChannelFull` (or `ChannelDisconnected`) — errors that are distinct from `MaxHeightReached` and do **not** imply the slot/bank is finished: [4](#0-3) 

`ChannelFull` occurs whenever the bounded record channel's `allowed_insertions` budget is momentarily exhausted (e.g., PohService is briefly behind while multiple banking-stage worker threads finish batches concurrently) — a condition reachable simply from ordinary high transaction throughput, not from any privileged operation: [5](#0-4) 

The `entry_bytes_budget` is only reset once per slot boundary in `apply_slot_time_runtime_changes`: [6](#0-5) 

so any bytes reserved-but-not-recorded due to `ChannelFull`/`ChannelDisconnected` remain permanently "consumed" for the rest of that slot, exactly like the Kinetiq buffer being decremented for a withdrawal that never completes and never gets credited back.

### Impact Explanation
Because the leaked reservation is never restored, the effective `max_entry_bytes_per_slot` limit shrinks with every retryable, non-terminal recording failure. As this leakage accumulates during a slot (batches are retried and may again be reserved on top of the stale reservation), legitimate, otherwise-committable transactions later in the same slot can begin failing `reserve()` with `EntryBytesReserveError::ExceedsSlotLimit`, which is mapped straight to `PohRecorderError::MaxHeightReached` — prematurely truncating the leader's block well below its intended capacity. This is a throughput-degrading, unprivileged-reachable resource-loss bug: any burst of transaction traffic that causes transient banking-stage/PohService backpressure can permanently and silently reduce the amount of chain data a leader can pack into its slot, with no accounting mechanism to reclaim the lost budget.

### Likelihood Explanation
`ChannelFull` requires no special privilege — it is a normal consequence of concurrent banking-stage worker threads finishing batches while PohService is momentarily saturated, which becomes more likely precisely when transaction volume (including load generated by ordinary/unprivileged users) is high. No malicious construction of packets or accounts is needed; it is a natural race under load.

### Recommendation
Add a `release`/`unreserve` method to `EntryBytesBudget` that atomically decrements `consumed` by the previously reserved amount, and call it in `execute_and_commit_transactions_locked` whenever `recording_result` is an `Err` that is not `MaxHeightReached` (i.e., the slot is still active and the reservation was wasted), mirroring the existing `remove_added_transaction_costs` rollback pattern used for the cost tracker.

### Proof of Concept
1. Configure/observe a slot with legitimate concurrent banking-stage throughput such that multiple worker threads' `record_transactions` calls race against a momentarily-full record channel (bounded by `BankIdAllowedInsertions::MAX_ALLOWED_INSERTIONS`), producing `RecordSenderError::Full` → `PohRecorderError::ChannelFull` for some batches, as in `poh/src/transaction_recorder.rs:78-84`.
2. Observe that `Consumer::execute_and_commit_transactions_locked` (`core/src/banking_stage/consumer.rs:397-414`) rolls back cost-tracker costs and marks transactions retryable but does not call any release on `bank.entry_bytes_budget()`.
3. Repeat this several times within the same slot (retried transactions may reserve again on retry, further compounding the leak). Track `EntryBytesBudget.consumed` (via a debug hook/log) versus the actual bytes sent through `record_receiver` — `consumed` will exceed the true recorded byte total by the sum of all failed reservations.
4. Once `consumed` (inflated by leaked reservations) approaches `slot_limit`, subsequent legitimate `reserve()` calls fail with `ExceedsSlotLimit`, causing `MaxHeightReached` and ending block-packing early even though the actual PoH stream contains far fewer bytes than `max_entry_bytes_per_slot` allows.

    pub fn reserve(&self, bytes: u64) -> std::result::Result<(), EntryBytesReserveError> {
        loop {
            let current = self.consumed.load(Ordering::Acquire);
            let next = current.saturating_add(bytes);
            if next > self.slot_limit {
                return Err(EntryBytesReserveError::ExceedsSlotLimit);
            }

            if self
                .consumed
                .compare_exchange(current, next, Ordering::AcqRel, Ordering::Acquire)
                .is_ok()
            {
                return Ok(());
            }
        }
    }
