### Title
Firewall per-routine `ConntrackCache` bypasses rule-version revalidation - (File: `firewall.go`)

### Summary
`Firewall.inConns` has two code paths for deciding whether a packet's flow tuple is "already established" and therefore allowed: (1) the authoritative `Conntrack.Conns` map, which re-validates a flow against the *current* rule set whenever `c.rulesVersion != f.rulesVersion`, and (2) a per-goroutine `localCache` (`firewall.ConntrackCache`, built by `ConntrackCacheTicker`) that is checked first and, on a hit, returns `true` immediately with no rule-version check at all. This mirrors the reported `viewPrice`/`getPrice` divergence pattern: a "fast/local view" path that skips the freshness/validation logic performed by the authoritative path.

### Finding Description
`inConns` starts with an unconditional short-circuit: [1](#0-0) 
Only if `localCache` misses does the code fall through to the authoritative conntrack table, which explicitly re-checks the ruleset version and removes/rejects the entry if it no longer matches: [2](#0-1) 
After the authoritative check succeeds, the tuple is written into `localCache` so subsequent packets in the same batch skip straight to the fast path: [3](#0-2) 

The `localCache` itself is a `ConntrackCacheTicker`-backed map that is only reset when a background ticker crosses a time boundary (`d` duration), not when the firewall ruleset changes: [4](#0-3) [5](#0-4) 

Nothing in this reset logic is tied to `Firewall.rulesVersion` (incremented on `AddRule`/reload), so a hot-reload of the firewall config that would otherwise invalidate/re-test an existing conntrack entry does not invalidate entries already cached in a routine's `localCache`. As long as the cache ticker hasn't fired, `inConns` returns `true` for previously-seen flows purely from `localCache[fp]` presence, bypassing the `table.match(...)` re-validation that the authoritative path performs at line 536.

This is the direct analog of the reported issue: `viewPrice` returned the undampened value because it lacked the "clamp to today's low" logic that `getPrice` applied, causing external callers (`getCollateralValue`, `getCreditLimit`, etc.) to act on stale/incorrect state. Here, the fast-path `localCache` lookup lacks the "revalidate against current ruleset" logic that the authoritative `Conntrack.Conns` lookup applies, causing the firewall's per-packet decision (`Drop`/allow) to act on a stale authorization decision.

### Impact Explanation
If an operator tightens or removes a firewall rule (e.g. revokes access for a group/CIDR) via a live config reload, packets belonging to already-cached flows can continue to be allowed through `inConns`'s fast path until the `ConntrackCacheTicker` happens to roll over, regardless of the new, stricter ruleset. This is a firewall bypass: traffic that should be dropped under the current rules is instead passed because the decision was cached before the reload and the cache invalidation is time-based rather than rules-version-based.

### Likelihood Explanation
This path is reachable by any already-established remote peer sending ordinary data traffic during/after a firewall rule reload — no malicious peer certificate or lighthouse tampering is required, and it triggers in the normal packet-processing hot path (`Drop` → `inConns`) used for every inbound/outbound packet. The window of exposure depends on the configured `ConntrackCacheTimeout`/ticker interval, but during that window the bypass is deterministic for any cached flow.

### Recommendation
Tie `localCache` validity to `Firewall.rulesVersion` the same way `Conntrack.Conns` entries are tied to it: either (a) store the `rulesVersion` alongside each `localCache` entry and re-validate/evict on mismatch before returning `true`, or (b) reset/clear all in-flight `localCache` instances whenever `f.rulesVersion` changes (e.g., via a shared atomic version counter checked in `ConntrackCacheTicker.Get()`), rather than relying solely on the time-based ticker in `firewall/cache.go`.

### Proof of Concept
Conceptual reproduction (would need to be implemented as a Go test similar to `firewall_test.go`):
1. Create a `Firewall` with a rule allowing group `A`, obtain a `localCache` via `NewConntrackCacheTicker`.
2. Send a packet from a host in group `A`; `Drop` succeeds, `addConn` records it in `Conntrack.Conns`, and `inConns` populates `localCache[fp] = struct{}{}`.
3. Reload the firewall config removing the rule for group `A` (bumping `f.rulesVersion`).
4. Send the same packet tuple again before the `ConntrackCacheTicker`'s ticker fires: `inConns` hits `localCache[fp]` at line 507 and returns `true` immediately, bypassing the `table.match` re-validation at line 536 that would otherwise reject it — the packet is allowed even though the current ruleset no longer permits it.

type ConntrackCacheTicker struct {
	cacheV    uint64
	cacheTick atomic.Uint64

	l     *slog.Logger
	cache ConntrackCache
}

func NewConntrackCacheTicker(ctx context.Context, l *slog.Logger, d time.Duration) *ConntrackCacheTicker {
	if d == 0 {
		return nil
	}

	c := &ConntrackCacheTicker{
		l:     l,
		cache: ConntrackCache{},
	}

	go c.tick(ctx, d)

	return c
}

// Get checks if the cache ticker has moved to the next version before returning
// the map. If it has moved, we reset the map.
func (c *ConntrackCacheTicker) Get() ConntrackCache {
	if c == nil {
		return nil
	}
	if tick := c.cacheTick.Load(); tick != c.cacheV {
		c.cacheV = tick
		if ll := len(c.cache); ll > 0 {
			if c.l.Enabled(context.Background(), slog.LevelDebug) {
				c.l.Debug("resetting conntrack cache", "len", ll)
			}
			c.cache = make(ConntrackCache, ll)
		}
	}

	return c.cache
}
