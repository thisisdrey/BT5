## #Vulnerability found for this question.

### Title
Missing length limits on V1 certificate `Name`/`Groups`/`Issuer` fields enable a handshake-time parsing/verification DoS - (`cert/cert_v1.go`)

### Summary
Nebula's ASN.1-based V2 certificate format enforces a `MaxNameLength = 253` cap on the `Name` field (and reuses that same `Name` type for `Groups`) and a `MaxNetworkLength = 17` cap on network entries during `unmarshalDetails` [1](#0-0) . The legacy protobuf-based V1 certificate parser, `unmarshalCertificateV1`, has no equivalent bound: `Name`, every entry of `Groups`, and `Issuer` are copied straight from the wire without any length check [2](#0-1) . This is directly analogous to the reported `Hats.uri` issue, where an unbounded `details`/`imageURI` string let an attacker impose disproportionate downstream processing cost on every party that later has to read/re-serialize the value.

### Finding Description
`cert.Recombine` dispatches V1/pre-V1 certificate bytes straight to `unmarshalCertificateV1` [3](#0-2) , which is reached from `handshake.Machine.validateCert` while processing an *inbound, unauthenticated* handshake packet — i.e. before any CA signature has been checked [4](#0-3) . `unmarshalCertificateV1` only validates parity of the `Ips`/`Subnets` arrays; it applies no length limit to `Name`, `Groups`, or `Issuer` [5](#0-4) .

Once `Recombine` succeeds, the certificate is handed to the verifier, `CAPool.VerifyCertificate`, which:
1. Computes `c.Fingerprint()` — a `sha256.Sum256` over the *entire* re-marshaled certificate, including the attacker-controlled `Name`/`Groups`/`Issuer` bytes [6](#0-5) [7](#0-6) .
2. Calls `ncp.verify`, which — because this is a fresh (non-cached) certificate — calls `c.CheckSignature(signer.Certificate.PublicKey())` [8](#0-7) . `CheckSignature` re-serializes the full details structure via `proto.Marshal` before running the ed25519/ECDSA verification [9](#0-8) .

All of this parsing/marshaling/hashing work happens for *every* inbound handshake attempt, regardless of whether the presented certificate is ultimately trusted — the attacker does not need a CA-signed certificate to reach this code path; an unsigned/garbage-signed V1 certificate blob is sufficient to drive the parser and the pre-signature-check marshaling/hashing logic. Because no field-length cap exists for V1 (unlike V2's explicit 253/17-character caps), an attacker can inflate `Name` and `Groups` up to the size of a single handshake payload, forcing the responder to repeatedly re-marshal and hash that oversized data on every handshake attempt before rejection.

### Impact Explanation
Each malicious handshake packet forces the responder to perform proportional extra CPU work (protobuf unmarshal, `sha256` fingerprinting, and a full details re-marshal for signature checking) driven entirely by attacker-controlled field sizes, with no cap analogous to V2's `MaxNameLength`/`MaxNetworkLength`. Because certificate verification/failure logging also happens per-attempt (e.g. `beginHandshake`), an attacker can repeatedly resend oversized, unsigned certificates to amplify CPU consumption on any Nebula node accepting V1 handshakes — a remote resource-exhaustion/DoS vector directly analogous to the `Hats.uri` gas-DoS bug class, but expressed as CPU/memory cost instead of gas cost.

### Likelihood Explanation
No CA-signed certificate or prior authentication is required: the vulnerable code path (`Recombine` → `unmarshalCertificateV1` → `VerifyCertificate` → `Fingerprint`/`CheckSignature`) executes for any inbound handshake stage-0/stage-1/stage-2 packet before signature validation completes. Any peer able to send UDP packets to a Nebula node's listener can trigger the oversized-field parsing/hashing/marshaling cost repeatedly, making this straightforward to reach and repeat.

### Recommendation
Enforce explicit length limits on V1 certificate `Name`, each `Groups` entry, and `Issuer` in `unmarshalCertificateV1`/`certificateV1.validate()`, mirroring the `MaxNameLength`/`MaxNetworkLength` constants already used for V2 certificates in `cert/cert_v2.go`, and reject certificates exceeding those limits before any hashing/marshaling/signature-check work is performed.

### Proof of Concept
1. Craft a raw `RawNebulaCertificate` protobuf message (as consumed by `unmarshalCertificateV1`) with `Details.Name` set to a large string (bounded only by the maximum handshake payload size the transport allows) and/or `Details.Groups` populated with many large strings, and an arbitrary (invalid) `Signature`.
2. Embed this in a `NebulaHandshakeDetails.Cert` field and send it as a handshake stage-0 packet to a victim Nebula node, as `beginHandshake` → `machine.ProcessPacket` → `validateCert` will call `cert.Recombine` on the raw bytes [4](#0-3) .
3. Observe that `unmarshalCertificateV1` accepts the oversized `Name`/`Groups` without complaint [2](#0-1) , and that `CAPool.VerifyCertificate` subsequently performs a full `Fingerprint()` (sha256 over the whole cert) and `CheckSignature()` (full protobuf re-marshal) on the oversized data before ultimately rejecting the bad signature [10](#0-9) .
4. Repeat with many such packets to demonstrate cumulative CPU cost imposed on the responder, disproportionate to the attacker's own negligible cost of constructing the packet.

func (ncp *CAPool) VerifyCertificate(now time.Time, c Certificate) (*CachedCertificate, error) {
	if c == nil {
		return nil, fmt.Errorf("no certificate")
	}
	fp, err := c.Fingerprint()
	if err != nil {
		return nil, fmt.Errorf("could not calculate fingerprint to verify: %w", err)
	}

	signer, err := ncp.verify(c, now, fp, "")
	if err != nil {
		return nil, err
	}

	// Pre nebula v1.10.3 could generate signatures in either high or low s form and validation
	// of signatures allowed for either. Nebula v1.10.3 and beyond clamps signature generation to low-s form
	// but validation still allows for either. Since a change in the signature bytes affects the fingerprint, we
	// need to test both forms until such a time comes that we enforce low-s form on signature validation.
	fp2, err := CalculateAlternateFingerprint(c)
	if err != nil {
		return nil, fmt.Errorf("could not calculate alternate fingerprint to verify: %w", err)
	}
	if fp2 != "" && ncp.IsBlocklisted(fp2) {
		return nil, ErrBlockListed
	}

	cc := CachedCertificate{
		Certificate:       c,
		InvertedGroups:    make(map[string]struct{}),
		Fingerprint:       fp,
		fingerprint2:      fp2,
		signerFingerprint: signer.Fingerprint,
	}

	for _, g := range c.Groups() {
		cc.InvertedGroups[g] = struct{}{}
	}

	return &cc, nil
}

// VerifyCachedCertificate is the same as VerifyCertificate other than it operates on a pre-verified structure and
// is a cheaper operation to perform as a result.
func (ncp *CAPool) VerifyCachedCertificate(now time.Time, c *CachedCertificate) error {
	// Check any available alternate fingerprint forms for this certificate, re P256 high-s/low-s
	if c.fingerprint2 != "" && ncp.IsBlocklisted(c.fingerprint2) {
		return ErrBlockListed
	}

	_, err := ncp.verify(c.Certificate, now, c.Fingerprint, c.signerFingerprint)
	return err
}

func (ncp *CAPool) verify(c Certificate, now time.Time, certFp string, signerFp string) (*CachedCertificate, error) {
	if ncp.IsBlocklisted(certFp) {
		return nil, ErrBlockListed
	}

	signer, err := ncp.GetCAForCert(c)
	if err != nil {
		return nil, err
	}

	if signer.Certificate.Curve() != c.Curve() {
		return nil, ErrCurveMismatch
	}

	if signer.Certificate.Expired(now) {
		return nil, ErrRootExpired
	}

	if c.Expired(now) {
		return nil, ErrExpired
	}

	// If we are checking a cached certificate then we can bail early here
	// Either the root is no longer trusted or everything is fine
	if len(signerFp) > 0 {
		if signerFp != signer.Fingerprint {
			return nil, ErrFingerprintMismatch
		}
		return signer, nil
	}
	if !c.CheckSignature(signer.Certificate.PublicKey()) {
		return nil, ErrSignatureMismatch
	}
