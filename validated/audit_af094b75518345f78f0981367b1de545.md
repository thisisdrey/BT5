### Title
Improper input-length validation in `ValidateMultiSign`/`BatchValidateSign` TVM precompiles allows attacker-controlled `ArrayIndexOutOfBoundsException` (uncaught) - ([File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java])

### Summary
`PrecompiledContracts.ValidateMultiSign.execute()` and `PrecompiledContracts.BatchValidateSign.doExecute()` decode raw TVM call data into a `DataWord[]` array and then immediately index into fixed positions (`words[0]`, `words[1]`, `words[2]`, and conditionally `words[3]`) without first checking that `words.length` is large enough. The only defense against malformed/short call data is `isValidAbiEncoding(...)`, and that check is gated behind the hard-fork flag `VMConfig.allowTvmOsaka()`. Any contract deployer or unprivileged transaction sender who calls these precompiles (`validatemultisign(...)`, `batchvalidatesign(...)`) with too-short `rawData` on a network/version where `allowTvmOsaka()` is `false` triggers an unbounded, unguarded array index access. This is directly analogous to CVE-2018-1000205's root cause (CWE-20: improper input validation of an untrusted, structured payload before it is consumed by a verification routine).

### Finding Description
In `ValidateMultiSign.execute()`: [1](#0-0) 
the guard `isValidAbiEncoding(rawData, ABI_HEADER_WORDS, ABI_ITEM_WORDS)` is only invoked when `VMConfig.allowTvmOsaka()` is true. Immediately afterward, `DataWord.parseArray(rawData)` produces an array whose length is `rawData.length / 32`, with no minimum-size guarantee. The code then unconditionally reads `words[0]`, `words[1]`, `words[2]`, and (if `allowTvmSelfdestructRestriction()` is active) `words[3]` — all of which throw `ArrayIndexOutOfBoundsException` if the caller supplies fewer than 3 or 4 32-byte words. Crucially, this indexing happens *before* the method's own `try { ... } catch (Throwable t) { ... }` block, which only wraps the `AccountCapsule` lookup logic starting at line 1080: [2](#0-1) 
so any exception thrown while parsing the header words is not caught inside this method at all.

`BatchValidateSign.doExecute()` has the identical pattern (`words[0]`, `words[1]`, `words[2]` accessed unconditionally, `isValidAbiEncoding` gated the same way): [3](#0-2) 
though in this case the outer `execute()` wrapper does catch `Throwable` and returns a zero result: [4](#0-3) 
`ValidateMultiSign` has no equivalent outer safety net — the vulnerable array access sits completely outside any try/catch in that class.

A dedicated regression test explicitly documents that this "outer-frame containment" behavior for malformed calldata is a TIP-854 property, activated together with `VMConfig.initAllowTvmOsaka(1)`: [5](#0-4) 
This confirms that prior to/without the Osaka hard-fork flag being active, malformed/short calldata to these precompiles is not defended against, matching the CVE's theme of a verification routine failing to validate a specially crafted, size-manipulated input before processing it.

### Impact Explanation
`ValidateMultiSign` and `BatchValidateSign` are reachable by any account or contract that can issue a `TriggerSmartContract` (a standard, unprivileged, broadcastable contract type) targeting the precompile address. Because TVM execution is deterministic and replicated by every full node/witness during block application, an uncaught `ArrayIndexOutOfBoundsException` escaping `ValidateMultiSign.execute()` (when `allowTvmOsaka()` is false) risks propagating past the immediate precompile call into the surrounding TVM dispatch/opcode-handling code. Depending on how far up the call stack the exception is finally caught, this can manifest as: (a) an unexpected/undocumented failure mode diverging from the intended "return false/zero" semantics of these signature-verification precompiles, or (b) in the worst case, an unhandled exception during block/transaction processing on every synchronized node, which is a chain-halt/DoS condition since the fault is 100% reproducible from the transaction's raw bytes. This qualifies as a Medium-severity "node crash or halt" concern per the scope rules, directly mirroring the CVE's "improper input validation in signature validation logic, exploitable via a specially crafted structured payload."

### Likelihood Explanation
Likelihood is high for triggering the code path: constructing a `TriggerSmartContract` with call data shorter than 4 words (128 bytes) to the `validatemultisign` precompile address requires no special privilege, no multi-sig setup, and no valid signatures — it is a single, cheaply-broadcastable transaction from any account. The only precondition is that the network has not yet activated the `allowTvmOsaka` (TIP-854) hard fork feature, which is the exact state the added regression tests were written to guard against — i.e., this is a genuine, previously-real gap that the codebase's own tests treat as security-relevant.

### Recommendation
Make the length/shape validation of precompile call data unconditional (not gated behind `VMConfig.allowTvmOsaka()`), and/or wrap the entirety of `ValidateMultiSign.execute()` (not just the account-lookup portion) in a `try/catch(Throwable)` that returns `DATA_FALSE` on any parsing failure, consistent with `BatchValidateSign.execute()`'s existing outer wrapper. Validate `words.length` against the minimum required header size before indexing `words[0..3]` in both precompiles, independent of hard-fork activation state.

### Proof of Concept
1. On a java-tron node/network where `VMConfig.allowTvmOsaka()` currently evaluates to `false` (pre-TIP-854 activation), deploy or use any contract.
2. Issue a `TriggerSmartContract` transaction (signed by any funded account) that performs a `CALL`/`STATICCALL` to the `validatemultisign` precompiled contract address with `rawData` shorter than 96 bytes (i.e., fewer than 3 32-byte words) — e.g., 32 bytes of arbitrary data.
3. Execution reaches `words[2].getData()` in `ValidateMultiSign.execute()` with `words.length == 1`, throwing an uncaught `ArrayIndexOutOfBoundsException` outside any try/catch in that method, deterministically on every node that processes the transaction/block.
