### Title
Attacker can fill a victim's `MAX_TOKENS_PER_USER` slots with dust deposit-token transfers, permanently blocking collateral top-ups and new debt issuance so the victim cannot rescue an unhealthy position - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
`Pool` enforces a hard cap of `MAX_TOKENS_PER_USER = 30` on the combined length of an account's `depositTokensOfAccount` and `debtTokensOfAccount` sets. Any holder of a `DepositToken` (msdTOKEN) can `transfer` a dust amount to any address, and `DepositToken._transfer` unconditionally calls `pool.addToDepositTokensOfAccount(recipient_)` when the recipient's balance goes from `0` to `>0` (`DepositToken.sol:517-520`). Because `transfer` only checks `_revertIfLocked` on the *sender*, an attacker can grief an arbitrary victim by dust-transferring every listed deposit token to them. Once `debtTokensOfAccount.length + depositTokensOfAccount.length >= 30`, every subsequent `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` reverts with `UserReachedMaxTokens` (`Pool.sol:143-148`), which reverts `DepositToken.deposit`, `DebtToken.issue`/`flashIssue` (via `_mint` → `addToDebtTokensOfAccount`, `DebtToken.sol:597-600`), and blocks removal of dust slots when the victim's balances are locked — a liveness/availability break matching the DoS bug class of CVE-2021-2384.

### Finding Description
- `Pool.addToDepositTokensOfAccount` / `addToDebtTokensOfAccount` are permissionless callbacks gated only by `_revertIfSenderIsNotDepositToken/_revertIfSenderIsNotDebtToken`; the `account_` argument is attacker-chosen and never authenticated (`Pool.sol:204-220`).
- `DepositToken._transfer` adds the token to the recipient's set on first receipt; the recipient never consents (`DepositToken.sol:498-525`).
- `DepositToken.seize` and `DebtToken._burn`/`_mint` remove entries only when a balance goes to zero; a dust `balanceOf > 0` keeps the slot occupied.
- Cleanup is blocked precisely when it matters: `unlockedBalanceOf` returns `0` for an account whose `debtPositionOf` shows `_issuableInUsd == 0` with `_debtInUsd > 0` (`DepositToken.sol:383-398`), so `_revertIfLocked` makes `transfer`/`transferFrom`/`withdraw` of the dust entries revert. The victim cannot free a slot while their position is unhealthy.
- Attack path: attacker deposits dust underlying into each of the pool's deposit tokens (or buys msdTOKEN balances), then calls `transfer(victim, 1 wei)` for each distinct `DepositToken` until the victim's set reaches 30 entries (victim's own positions count toward the cap, so fewer than 30 attacker transfers are needed).
- Consequence: when the victim's position turns unhealthy, `DepositToken.deposit` of a new collateral reverts inside `_mint` → `pool.addToDepositTokensOfAccount` → `UserReachedMaxTokens`, and `DebtToken.issue`/`SmartFarmingManager.leverage` revert the same way. The victim's only remaining lever is repaying debt with held synths; if they can't, they are force-liquidated. The dust amounts also inflate `depositOf`/`debtPositionOf` negligibly, so this isn't solved by the lock check.
- Reentrancy/pause flags do not help: `transfer` is not `nonReentrant` on the direct path and is available whenever deposit tokens are active; nothing rate-limits first-time additions.

### Impact Explanation
Denial of service of the rescue path for a targeted account: an unhealthy victim cannot add new collateral or issue/leverage to deleverage, and locked dust slots cannot be removed, so liquidation proceeds with the attacker (or any liquidator) seizing collateral plus incentive. This is an availability violation with downstream loss of user funds, analogous to the CVE's "complete DOS" outcome.

### Likelihood Explanation
Cost is bounded by acquiring dust balances of each listed `DepositToken` plus one cheap `transfer` per token; no privileged role, oracle manipulation, or governance action is needed. It requires pools to list enough deposit tokens (or the victim already consuming slots) to reach 30 combined entries, and is most profitable when a target position is near the liquidation threshold.

### Recommendation
Don't register tokens in the per-account set as a side effect of unsolicited transfers: either exempt `transfer`/`transferFrom` from `addToDepositTokensOfAccount` (track positions only on `deposit`/`issue`), let users opt in, or allow anyone to `removeFromDepositTokensOfAccount` entries with `balanceOf == 0`-equivalent dust below a threshold. Alternatively, sweep dust slots by permitting `seize`-style removal of locked-but-de-minimis balances, or raise/decouple the cap so slot exhaustion cannot block rescues.

// victim: alice deposits MET and issues msETH
await met.connect(alice).approve(metDepositToken.address, amount);

// attacker deposits dust underlying in each deposit token, then fills alice's slots

// repeat until pool.getDepositTokensOfAccount(alice) + getDebtTokensOfAccount(alice) == 30
