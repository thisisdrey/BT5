### Title
Authorization Bypass via Permission-ID/Type Confusion in `ValidateMultiSign` Precompile - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The `ValidateMultiSign` TVM precompile lets any on-chain contract verify an off-chain signature set against an account's on-chain `Permission`. Unlike every other permission-checking code path in java-tron, this precompile never verifies that the caller-supplied `permissionId` actually resolves to the intended `PermissionType.Active` slot, nor does it enforce the operation-scope bitmap. An attacker can therefore satisfy a contract's "elevated permission" check by supplying signatures valid under a different, lower-assurance permission slot (e.g. the single-key `Witness` permission, id=1) that was never meant to authorize the calling contract's business logic — directly analogous to the WhatsApp bug class where a group identifier satisfies a check meant only for an individually-vetted, elevated sender ID.

### Finding Description
`PrecompiledContracts.ValidateMultiSign.execute` resolves the permission purely by numeric id and checks only signature weight vs. threshold: [1](#0-0) 

Compare this to every transaction-level equivalent, which explicitly rejects any non-owner permission whose type is not `Active` and additionally checks the operations bitmap before accepting it as authorization: [2](#0-1) [3](#0-2) [4](#0-3) 

`AccountCapsule.getPermissionById` treats id `0` as `Owner`, id `1` as `Witness`, and any other id as an `Active` slot — these are three semantically distinct trust domains with different intended scopes (global account control, block-production credential, and app-scoped multisig, respectively): [5](#0-4) 

Because `ValidateMultiSign` skips the `permission.getType() != PermissionType.Active` guard and the `checkPermissionOperations` bitmap check that all other verification paths enforce, a contract that relies on this precompile as its authorization primitive (e.g. "requires the account's app-scoped Active permission with threshold N") can be satisfied instead by signatures collected under the account's `Owner` permission (id 0) or `Witness` permission (id 1) — slots with entirely different key sets, thresholds, and intended purposes, effectively letting a narrower/different-purpose credential (the "group ID") satisfy a check meant for the elevated, application-scoped credential (the "individual sender ID").

### Impact Explanation
Any deployed smart contract using `validatemultisign(address,uint256,bytes32,bytes[])` as an authorization gate for value-moving or privileged operations (escrow release, custody approval, on-chain order execution, etc.) can have that gate bypassed by presenting signatures for a different permission id than the one the contract's designer intended, provided that alternate permission slot has a lower/simpler threshold. This can result in unauthorized approval of account/contract operations and consequent theft or misdirection of funds, without requiring compromise of the intended multisig keys.

### Likelihood Explanation
Exploitation only requires deploying or calling any smart contract that invokes this always-available TVM precompile and supplying an attacker-controlled `permissionId`; no special privileges beyond normal contract deployment/invocation are needed. The precondition is that the target account has a lower-threshold permission slot (Owner or Witness) whose keys the attacker controls or can obtain independently of the intended Active multisig set — a realistic scenario for accounts that separate roles across permission ids, which is exactly the feature `AccountPermissionUpdateActuator` is designed to support.

### Recommendation
Add the same enforcement present in `TransactionCapsule.checkPermission`/`TransactionUtil.checkPermissionOperations` to `PrecompiledContracts.ValidateMultiSign` (and any sibling precompile such as `BatchValidateSign` that resolves permissions by id): reject non-zero `permissionId` whose resolved `Permission.getType()` is not `Active`, and require the operations bitmap to authorize the calling contract/context, so the precompile's guarantees match the rest of the permission-verification model.

### Proof of Concept
1. Owner sets up an account with `AccountPermissionUpdateContract`: `Owner` permission (3-of-5 keys), `Active` permission id=2 scoped only to specific contract types (intended as the "elevated" multisig for a custody contract), and, if the account is a witness, a `Witness` permission (single key, id=1).
2. A custody/escrow contract calls `validatemultisign(accountAddr, 2, hash, sigs)` expecting only the Active id=2 signers to satisfy release conditions.
3. Because the precompile does not check `permission.getType()==Active` (see `PrecompiledContracts.ValidateMultiSign.execute`), an attacker who controls only the Witness key can instead invoke with `permissionId=1`; `account.getPermissionById(1)` returns the Witness permission, and if its threshold (1) is met by the single witness key signature, the precompile returns `DataWord.ONE()`—a passing result the custody contract never intended to accept as proof of Active-permission approval.

  public Permission getPermissionById(int id) {
    if (id == 0) {
      if (this.account.hasOwnerPermission()) {
        return this.account.getOwnerPermission();
      }
      return getDefaultPermission(this.account.getAddress());
    }
    if (id == 1) {
      if (this.account.hasWitnessPermission()) {
        return this.account.getWitnessPermission();
      }
      return null;
    }
    for (Permission permission : this.account.getActivePermissionList()) {
      if (id == permission.getId()) {
        return permission;
      }
    }
    return null;
