## No Vulnerability found for this question.

**Binding claimed broken:** `sum_of_deltas_for_token_T_across_the_call == 0` AND `external_asset_released == balance_backed_by_custodied_assets`. The question asks whether an `FtWithdraw`'s already-`.then()`-chained `Promise` survives (dispatches as a real outgoing receipt) even when the same top-level call later panics due to `finalize()` returning `Err(InvariantViolated)`.

**Trace:**
- `Engine::execute_signed_intents` iterates every signed payload, applying each intent's state mutation (including `ft_withdraw`, which calls `internal_sub_balance` and then schedules the `ft_transfer` `Promise` via `internal_ft_withdraw(...).detach()`), and only calls `self.finalize()` (i.e. `TransferMatcher::finalize()`) once, after the whole loop [1](#0-0) .
- The top-level entry point `Contract::execute_intents` invokes `Engine::execute_signed_intents(signed).unwrap_or_else(|e| e.panic())` — any `Err` (including `DefuseError::InvariantViolated` from a mismatched/unmatched `TokenDiff`) causes the whole function call to **panic** [2](#0-1) .
- NEAR's function-call execution model is atomic: state writes and any `Promise`/`.then()` chains created during a function call are only committed as part of that execution's outcome (state trie update + outgoing receipts) if the function returns without panicking. A panic discards the entire outcome — no state changes are persisted and no outgoing receipts (including any pending `ft_transfer` promise) are generated. This is not something the contract code itself needs to implement; it's the underlying NEAR runtime guarantee for `FunctionCall` actions.
- This is exactly what the repo's own test demonstrates: two `TokenDiff` intents are crafted to leave `unmatched_deltas` (mirroring the exact scenario in the question), `simulate_intents` reports `invariant_violated`, `execute_intents` is asserted to return an error via `unwrap_err()`, and the test then asserts **balances stay exactly the same as before the call** [3](#0-2) . If a promise/state change created earlier in the batch (analogous to an `FtWithdraw`) had survived the later panic, this assertion would fail.
- The same reasoning applies to `FtWithdraw` specifically: `internal_ft_withdraw` calls `self.withdraw(...)` (mutating balances) and then chains `.then(...ft_resolve_withdraw...)` on the `Promise` before returning it up the call stack [4](#0-3) ; but this `Promise` object is merely a Rust-level near_sdk construct queued for inclusion in the outgoing receipts of *this* execution outcome — it is not "fired" independently of the enclosing `execute_intents` call succeeding.

Because promise scheduling and balance mutation are bound to the same atomic execution outcome as `finalize()`'s result, an `Err(InvariantViolated)` from an unmatched `TokenDiff` in the same batch causes the entire call — including any already-`.then()`-chained `ft_transfer` for an `FtWithdraw` earlier in the batch — to revert with no receipts dispatched. The equality holds both before and after tracing the code; no divergence exists.

#[near]
impl Intents for Contract {
    #[pause(name = "intents")]
    fn execute_intents(&mut self, signed: Vec<MultiPayload>) {
        if let Some(event) = Engine::new(self, ExecuteInspector::default())
            .execute_signed_intents(signed)
            .unwrap_or_else(|e| e.panic())
            .as_mt_event()
        {
            // NOTE: Not all `mt_transfer` events are refundable, but it's safe to check them
            // all at once since non-refundable transfers only increase the potential refund
            // log size without affecting correctness. This can actually prevent resolve transfer
            // from failing due to too long event log !!!
            event
                .check_refund()
                .unwrap_or_else(|err| err.panic())
                .emit();
        }
    }

async fn invariant_violated(#[future(awt)] env: Env) {

    pub(crate) fn internal_ft_withdraw(
        &mut self,
        owner_id: AccountId,
        withdraw: FtWithdraw,
        force: bool,
    ) -> Result<PromiseOrValue<U128>> {
        self.withdraw(
            &owner_id,
            iter::once((
                Nep141TokenId::new(withdraw.token.clone()).into(),
                withdraw.amount,
            ))
            .chain(withdraw.storage_deposit.map(|amount| {
                (
                    Nep141TokenId::new(self.wnear_id().into_owned()).into(),
                    amount.as_yoctonear(),
                )
            })),
            Some("withdraw"),
            force,
        )?;

        let is_call = withdraw.is_call();
        Ok(if let Some(storage_deposit) = withdraw.storage_deposit {
            ext_wnear::ext(self.wnear_id.clone())
                .with_attached_deposit(NearToken::from_yoctonear(1))
                .with_static_gas(NEAR_WITHDRAW_GAS)
                // do not distribute remaining gas here
                .with_unused_gas_weight(0)
                .near_withdraw(U128(storage_deposit.as_yoctonear()))
                .then(
                    // schedule storage_deposit() only after near_withdraw() returns
                    Self::ext(env::current_account_id())
                        .with_static_gas(
                            Self::DO_FT_WITHDRAW_GAS
                                .checked_add(withdraw.min_gas())
                                .ok_or(DefuseError::GasOverflow)
                                .unwrap_or_else(|err| err.panic()),
                        )
                        .do_ft_withdraw(withdraw.clone()),
                )
        } else {
            Self::do_ft_withdraw(withdraw.clone())
        }
        .then(
            Self::ext(env::current_account_id())
                .with_static_gas(Self::FT_RESOLVE_WITHDRAW_GAS)
                // do not distribute remaining gas here
                .with_unused_gas_weight(0)
                .ft_resolve_withdraw(withdraw.token, owner_id, withdraw.amount.into(), is_call),
        )
        .into())
    }
