### Title
Re-freezing a resource overwrites the existing lock's expiry with a shorter one, unlocking already-frozen TRX earlier than promised - (File: actuator/src/main/java/org/tron/core/actuator/FreezeBalanceActuator.java)

### Summary
The reported Truflation `extendLock` bug allows a user to recompute a lock's `end` timestamp from the *previous* end rather than from "now" plus a genuinely new full duration, letting the position accrue extra ve-points/weight while the *effective* additional lock time is shorter than what the points imply. The closest reachable analog in java-tron is in `FreezeBalanceActuator.execute()` (and the identical logic in `FreezeBalanceProcessor.execute()` used by the TVM `freeze` opcode), where re-freezing additional TRX for an already-frozen resource **unconditionally overwrites** the stored `expireTime` with `now + newDuration`, regardless of the previously stored (possibly longer) expiry.

### Finding Description
When a user freezes additional TRX for BANDWIDTH or ENERGY on top of an existing frozen balance, `FreezeBalanceActuator.execute()` computes: [1](#0-0) 

```
long expireTime = now + duration;
...
accountCapsule.setFrozenForBandwidth(newFrozenBalanceForBandwidth, expireTime);
```

This new `expireTime` is stored as the single expiry for the *entire combined* frozen balance (old + newly added), replacing whatever expiry was previously set — there is no check that the new `expireTime` is not less than the account's already-recorded (and potentially farther in the future) expiry. The identical pattern exists in the TVM-reachable `FreezeBalanceProcessor.execute()`: [2](#0-1) 

This mirrors the root cause of the reported issue: a lock-extension/relock operation that derives a new unlock time without properly reconciling it against the position's true remaining lock commitment, so a party can manipulate the effective lock duration relative to the weight/points/resource credited.

By contrast, java-tron's own `DelegateResourceActuator` explicitly guards against this exact class of bug via `validRemainTime()`, which rejects a new lock period shorter than the remaining time of the existing lock: [3](#0-2) 

No equivalent check exists in `FreezeBalanceActuator`/`FreezeBalanceProcessor` for the plain (non-delegated) freeze-for-self path.

### Impact Explanation
An account holder who already froze TRX for BANDWIDTH/ENERGY with a long-duration expiry can call `FreezeBalanceContract` (or the TVM `freeze` opcode) again with the network minimum `frozenDuration` (as low as `minFrozenTime`, and even `0` when `getCheckFrozenTime() != 1` in the TVM path) to add a tiny additional amount to the same resource bucket. Because `setFrozenForBandwidth`/`setFrozenForEnergy` overwrite the stored `expireTime` for the *whole* combined balance with `now + duration`, this shortens the unlock time for the entire previously-frozen (larger) balance, letting the owner call `UnfreezeBalanceActuator` and reclaim TRX earlier than the original freeze duration promised — while it kept counting toward `TotalNetWeight`/`TotalEnergyWeight` (bandwidth/energy point weight) for the full original duration. This is a resource-accounting/lock-integrity violation analogous to the reported "extendLock" issue: the position is not genuinely locked for as long as its weight/points implied.

### Likelihood Explanation
Reachable by any unprivileged account holding frozen TRX by broadcasting a second `FreezeBalanceContract` transaction (or invoking the TVM `freeze` precompile from a contract) with a minimal duration on the same resource type — no special privileges required, and the transaction is a normal, common operation type (`freeze`) that many accounts perform routinely to top up resources.

### Recommendation
In `FreezeBalanceActuator.execute()` and `FreezeBalanceProcessor.execute()`, when adding to an already-frozen balance, take `expireTime = Math.max(now + duration, existingExpireTime)` instead of unconditionally overwriting with the newly computed `now + duration`, so a fresh freeze operation can never shorten a previously committed lock period.

### Proof of Concept
1. Account A freezes 1,000,000 sun for BANDWIDTH with `frozenDuration = 3` days → `expireTime = now + 3*FROZEN_PERIOD`.
2. After 2 days, A submits another `FreezeBalanceContract` for BANDWIDTH with the network minimum `frozenDuration` (e.g., 3 days again, or less if the min allows), while `getCheckFrozenTime()==0` bypassing duration checks, adding only 1 sun.
3. `FreezeBalanceActuator.execute()` recomputes `expireTime = now(day2) + duration`, and calls `accountCapsule.setFrozenForBandwidth(oldFrozenBalance + 1, expireTime)`, replacing the original day-3-based expiry with a new one computed from day 2 — for the combined (near-original) balance.
4. If the second freeze used a shorter allowable duration than the remainder of the first lock, A can call `UnfreezeBalanceActuator` and withdraw the full frozen balance earlier than the first freeze's 3-day commitment, despite having accrued bandwidth weight for the full original period.   private void validRemainTime(ResourceCode resourceCode, long lockPeriod, long expireTime,
      long now) throws ContractValidateException {
    long remainTime = expireTime - now;
    if (lockPeriod * BLOCK_PRODUCED_INTERVAL < remainTime) {
      throw new ContractValidateException(
          "The lock period for " + resourceCode.name() + " this time cannot be less than the "
              + "remaining time[" + remainTime + "ms] of the last lock period for "
              + resourceCode.name() + "!");
    }
  }
