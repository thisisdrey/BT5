Unprivileged dust transfers fill an account's token list, causing `UserReachedMaxTokens` DoS on deposits, issuance, withdrawals and liquidations - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
The Metronome analog of a remote DoS (CVE-2017-3644, complete hang of a server component) is griefing via `MAX_TOKENS_PER_USER`. Any EOA can transfer dust amounts of `DepositToken` shares to a victim or to the `feeCollector`. Each first-time receipt permanently adds an entry to that account's per-account set in `Pool`, and once `debtTokensOfAccount + depositTokensOfAccount >= 30`, several core user and protocol flows revert with `UserReachedMaxTokens`.

### Finding Description
`DepositToken._transfer` adds the token to the recipient's per-account list whenever the recipient's prior balance was zero and `amount_ > 0` (`DepositToken.sol:517-520`), and `DepositToken._mint` does the same on deposit (`DepositToken.sol:485-488`). Both calls hit `Pool.addToDepositTokensOfAccount` / `addToDebtTokensOfAccount`, which are gated by `onlyIfAdditionWillNotReachMaxTokens` and revert with `UserReachedMaxTokens` at 30 combined entries (`Pool.sol:143-148, 204-220`).

Attacker trace (no privileged role needed):
1. Acquire dust of each listed deposit token (deposit 1 wei of underlying, or receive via transfers).
2. Call `depositToken.transfer(victim, 1)` for every listed deposit token the victim does not already hold. Each call succeeds and permanently appends an entry to `depositTokensOfAccount[victim]`.
3. Once the victim reaches 30 combined entries, the following revert mid-transaction:
   - `deposit()` of any collateral type the victim doesn't already hold (`_mint` → `addToDepositTokensOfAccount` reverts).
   - `DebtToken.issue`/`mint` of any new synthetic (`_mint` → `addToDebtTokensOfAccount` reverts), blocking new borrowing.
   - `depositToken.withdraw` when `withdrawFee > 0` and the fee-collector's list is also full (`_withdraw` → `_transfer(account, feeCollector, _fee)` → `addToDepositTokensOfAccount(feeCollector)` reverts; `DepositToken.sol:545-551`).
   - `Pool.liquidate` whenever `_fee > 0` and the seized deposit token isn't already in `feeCollector`'s list (`Pool.liquidate` → `depositToken_.seize(account_, feeCollector, _fee)` → `seize` → `_transfer` → revert; `Pool.sol:581-593`, `DepositToken.sol:343-345`). The revert happens *after* `syntheticToken_.burn` and `_debtToken.burn`, reverting the entire liquidation.

`transfer`/`transferFrom`/`seize`/`_withdraw` all funnel through `_transfer`, so the revert propagates through public entry points (`withdraw`, `withdrawFrom`, `flashWithdraw`, `Pool.liquidate`, `NativeTokenGateway`, `VesperGateway`, `SmartFarmingManager.leverage`/`flashRepay` deposit legs). No modifier prevents it: `onlyIfAdditionWillNotReachMaxTokens` is precisely the check the attacker weaponizes, and `nonReentrant`, `whenNotShutdown`, and health checks are orthogonal.

### Impact Explanation
- **Liquidation DoS → insolvency**: if the `feeCollector` account's list is filled (by dust transfers to it, or naturally by collecting fees across many listed tokens), every liquidation charging a protocol fee in a deposit token not already in the collector's set reverts. Unhealthy positions cannot be liquidated, leading to bad-debt accumulation / protocol insolvency while the condition persists.
- **Temporary freezing of funds**: a victim pushed to the cap cannot deposit new collateral types to improve an unhealthy position, cannot issue new synths, and (when `withdrawFee > 0` and the collector is full) cannot withdraw at all.
- Recovery requires the victim (or the fee collector operator) to transfer out full dust balances to free slots — the attacker can cheaply re-grief, mirroring the "frequently repeatable crash" of the reference DoS.

### Likelihood Explanation
- Cost is dust-priced (1 wei per token per target) and requires only an EOA.
- The pool allows up to `MAX_TOKENS_PER_USER = 30` deposit tokens (`Pool.sol:703`), so on deployments listing many collaterals the attacker can fill an account purely with deposit-token dust. On sparser deployments the attack only DoSes accounts already near the cap — most notably `feeCollector`, which accumulates entries automatically every time fees are collected in a new token.
- Liquidator accounts can protect themselves by using fresh accounts, but `feeCollector` is a fixed protocol address, making the liquidation path the highest-impact target.

### Recommendation
- Do not enforce `MAX_TOKENS_PER_USER` for the `feeCollector`, or skip adding protocol fee recipients to `depositTokensOfAccount` (the fee path does not need position tracking).
- Prefer a push-to-pull pattern for the protocol fee (accrued balance claimed later) so `liquidate`/`withdraw` cannot revert on the collector's list state.
- Alternatively, make `addTo*TokensOfAccount` non-reverting for recipients: cap enforcement only matters for the account's own health computations, so a `try/catch` or silent skip on `add` for the *receiving* side of `_transfer` removes the forced-revert vector while preserving the cap for the sender's own positions.
