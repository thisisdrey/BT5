### Title
Unauthenticated `RelayFromAddr` claim lets any peer poison another host's relay state for an arbitrary victim address - ([File: relay_manager.go])

### Summary
The external report describes `Lender#buyLoan` trusting an attacker-supplied `poolId` as proof of pool ownership instead of checking it against the caller's real identity (`msg.sender != pool.lender`). The same access-control gap exists in Nebula's relay-establishment control channel: `relayManager.handleCreateRelayRequest` trusts the wire-supplied `RelayFromAddr` field as if it were the caller's own verified overlay identity, without ever checking it against `h.vpnAddrs[0]` (the identity actually established for `h` during its own certificate-authenticated handshake).

### Finding Description
`handleCreateRelayRequest` is reached from `relayManager.HandleControlMsg`, which is invoked for any `header.Control` message received over an already-established (and therefore certificate-authenticated) tunnel with peer `h`: [1](#0-0) 

Inside the handler, `from` and `target` are taken directly from the attacker-controlled `NebulaControl` payload with no cross-check against `h`'s actual, cert-verified `vpnAddrs`: [2](#0-1) 

Only a self-reference check (`from == me`) exists; there is no check that `from == h.vpnAddrs[0]`. When the relay target is not the local node and this node is acting as a relay (`am_relay`), the attacker-claimed `from` value is used, unverified, to create and mutate relay routing state on a third, uninvolved peer's `HostInfo` (`peer.relayState`), and an attacker-chosen `InitiatorRelayIndex` is embedded in the resulting request sent to that third peer: [3](#0-2) 

This mirrors the `buyLoan` flaw: the protocol authenticates *who is talking to you* (`h`, via the Noise handshake and certificate verification in `handshake_manager.go`'s `certVerifier`/`validateCert`), but a downstream state-mutating operation (`AddRelay`, `UpdateRelayForByIpState`) is keyed off a self-declared field (`RelayFromAddr`) that is never checked to equal that authenticated identity — exactly like trusting a self-declared `poolId` instead of verifying `msg.sender == pool.lender`.

### Impact Explanation
A fully authenticated but otherwise unprivileged peer can send `CreateRelayRequest` control messages claiming to be relaying "from" an arbitrary victim VPN address it does not own. Any node configured with `relay.am_relay = true` will act on this claim and create/mutate relay routing entries (`ForwardingType`, state `Requested`/`Established`) for that victim address on a legitimate third-party peer's hostmap, using attacker-chosen indices. This is remote state poisoning of another host's relay routing table by an entity with no legitimate claim to that address, and can interfere with or collide with the victim's own legitimate relay establishment through that relay node (denial-of-service / relay-path confusion for the victim).

### Likelihood Explanation
Any node that (a) has completed a normal handshake with a relay (thus is a fully authenticated peer) and (b) is talking to a node with `relay.am_relay = true` can trigger this path with a single crafted `NebulaControl_CreateRelayRequest` message; no special privileges beyond a valid certificate for the attacker's own identity are required, and the victim address is never validated to belong to the sender.

### Recommendation
In `relayManager.handleCreateRelayRequest` (and symmetrically in `handleCreateRelayResponse`), reject the message unless the claimed `RelayFromAddr` matches one of `h.vpnAddrs` (the sender's certificate-verified overlay addresses), analogous to adding `if msg.sender != pool.lender { revert Unauthorized(); }` in the original report — e.g. `if !slices.Contains(h.vpnAddrs, from) { drop and log; return }` before using `from` to mutate any hostmap/relay state.

### Proof of Concept
1. Attacker `A` completes a normal, cert-authenticated handshake with relay node `R` (`relay.am_relay=true`).
2. `A` sends `R` a `header.Control` / `NebulaControl_CreateRelayRequest` with `RelayFromAddr = Victim` (an address `A` does not own) and `RelayToAddr = Target` (some other peer of `R`).
3. `R`'s `handleCreateRelayRequest` (target-is-not-me branch) calls `AddRelay(..., peer=Target's HostInfo, from=Victim, ForwardingType, Requested)` and sends `Target` a `CreateRelayRequest`, all without ever verifying `Victim == A.vpnAddrs[0]`.
4. `Target`'s relay state for `Victim` is now seeded/mutated based solely on `A`'s unverified claim, before `Victim` ever participates in the exchange — demonstrating remote state poisoning of a peer that never sent any packet in this flow. [2](#0-1) [3](#0-2)

func (rm *relayManager) handleCreateRelayRequest(v cert.Version, h *HostInfo, f *Interface, m *NebulaControl) {
	//nil-checks for protoAddrToNetAddr handled by caller
	from := protoAddrToNetAddr(m.RelayFromAddr)
	target := protoAddrToNetAddr(m.RelayToAddr)

	logMsg := rm.l.With(
		"relayFrom", from,
		"relayTo", target,
		"initiatorRelayIndex", m.InitiatorRelayIndex,
		"vpnAddrs", h.vpnAddrs,
	)

	logMsg.Info("handleCreateRelayRequest")
	// Is the source of the relay me? This should never happen, but did happen due to
	// an issue migrating relays over to newly re-handshaked host info objects.
	if f.myVpnAddrsTable.Contains(from) {
		logMsg.Error("Discarding relay request from myself", "myIP", from)
		return
	}
