Audit Report

## Title
Reward pool state (`stake`/`unstake`/`harvest_rewards`) permanently DoS'd when a non-monotonic `BlockNumberProvider` regresses, locking staked funds and unclaimed rewards - (File: `substrate/frame/asset-rewards/src/lib.rs`)

## Summary
`pallet-asset-rewards` computes reward accrual using `Self::last_block_reward_applicable(pool_info.expiry_block).ensure_sub(pool_info.last_update_block)?` in `reward_per_token`, and `update_pool_rewards` unconditionally overwrites `last_update_block` with the current `T::BlockNumberProvider::current_block_number()` on every successful call. If the configured `BlockNumberProvider` ever returns a value lower than the previously stored `last_update_block`, this subtraction underflows and returns a hard error via `ensure_sub`, aborting the extrinsic.

## Finding Description
The elapsed-blocks computation is: [1](#0-0) 

`last_block_reward_applicable` returns `min(now, expiry_block)` where `now = T::BlockNumberProvider::current_block_number()`: [2](#0-1) 

`update_pool_rewards` unconditionally stores the current provider value as the new `last_update_block`: [3](#0-2) 

This is called from `update_pool_and_staker_rewards`, which is invoked by every state-changing entry point (`stake`, `unstake`, `harvest_rewards`): [4](#0-3) 

`RelaychainStateProvider::current_relay_chain_state` (which underlies relay-chain-backed `BlockNumberProvider` implementations usable by this pallet per its own type alias `BlockNumberFor<T>`) is explicitly documented as not guaranteed to return monotonically increasing values: [5](#0-4) 

If `now` regresses below the stored `last_update_block`, `ensure_sub` returns `Err`, propagated via `?`, aborting `reward_per_token` and, transitively, `stake`/`unstake`/`harvest_rewards`. Because a successful call is required to advance `last_update_block`, and no call can succeed once the regression has occurred, the failure recurs identically forever for that pool.

## Impact Explanation
This matches the "permanent user-fund … lock" impact category: stakers would be unable to `unstake` frozen tokens or `harvest_rewards` for the affected pool since both entry points unconditionally call the failing update path first.

## Likelihood Explanation
I was unable to fully verify from the index whether any production runtime (`asset-hub-westend-runtime`, `asset-hub-rococo-runtime`, or `pallet-staking-async-parachain-runtime`) actually configures `pallet_asset_rewards::Config::BlockNumberProvider` to a relay-chain-backed, non-monotonic provider (e.g., `RelaychainDataProvider`) as opposed to the default `frame_system::Pallet<Self>` (which is strictly monotonic and would not trigger this issue at all). The grep against `cumulus/parachains/runtimes/assets/asset-hub-westend/src/lib.rs` found `BlockNumberProvider` references but I could not read the actual `impl pallet_asset_rewards::Config for Runtime` block before running out of tool iterations to confirm which concrete provider type is wired in.

This is material to validity: the claim's likelihood hinges entirely on the pallet being deployed with a non-monotonic provider. If deployed runtimes use `frame_system::Pallet<Self>` (the default, monotonic behavior preserving prior semantics per the changelog note: "For most cases setting the type `BlockNumber = frame_system::Pallet<Self>;` will maintain the previous behaviour"), the vulnerability is not reachable in any current production configuration, making this a configuration-dependent latent code weakness rather than a currently exploitable issue against a live deployed chain.

Regardless of that unresolved configuration question, the underlying code pattern (`ensure_sub` instead of `saturating_sub`) is a real, demonstrable weakness in the pallet's generic logic, and the sibling `pallet-society` fix confirms non-monotonic/repeated relay-derived block numbers are a recognized real-world occurrence for parachains using relay-backed providers, not a purely theoretical concern.

## Recommendation
Replace `ensure_sub` with `saturating_sub` (clamping elapsed blocks to zero) in `reward_per_token`, mirroring `pallet-vesting`'s `locked_at` saturating pattern. Additionally, `update_pool_rewards` should avoid regressing `last_update_block` when `now < last_update_block`.

## Proof of Concept
1. Configure a runtime's `pallet_asset_rewards::Config::BlockNumberProvider` to a relay-chain-backed provider whose underlying `RelaychainStateProvider::current_relay_chain_state` is not guaranteed monotonic.
2. Call `stake` to set `Pools::<T>::get(pool_id).last_update_block = N`.
3. Have the provider's observed value regress below `N` on a subsequent parachain block (a scenario the provider's documented contract does not exclude).
4. Call `unstake` or `harvest_rewards`; `reward_per_token`'s `ensure_sub` underflows and returns `Err`, aborting the extrinsic permanently for that pool.

Note: full confirmation that a shipped production runtime actually selects a non-monotonic provider for this pallet (as opposed to the monotonic `frame_system` default) could not be completed within the available tool budget; this should be verified against the live `impl pallet_asset_rewards::Config for Runtime` blocks in `asset-hub-westend-runtime`, `asset-hub-rococo-runtime`, and `pallet-staking-async-parachain-runtime` before treating this as confirmed against a currently deployed chain.
