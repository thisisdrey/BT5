### Title
Unauthenticated Nakamoto block upload is unconditionally relayed to the P2P network regardless of `broadcast`/auth gate - ([File: stackslib/src/net/api/postblock_v3.rs])

### Summary
`RPCPostBlockRequestHandler::try_parse_request` only rejects a request when `broadcast=1` is requested without valid authentication; it happily accepts an unauthenticated, non-broadcast upload and stores it in `self.block`/`self.broadcast = Some(false)`. In `try_handle_request`, network-wide relay via `node.set_relay_message(...)` is gated solely on `data_resp.accepted` (i.e., whether the block validated), not on `self.broadcast` or authentication state, so any accepted block reaches the P2P relay path even when the client never requested (and was never authorized to request) broadcast.

### Finding Description
The intended equality per the endpoint's documented design is: *blocks queued for P2P relay via `node.set_relay_message` == blocks whose upload request set `broadcast=1` and passed the `authorization` check*. The code does not implement this equality.

- `try_parse_request` (`stackslib/src/net/api/postblock_v3.rs:99-135`) only enforces `if broadcast && !authenticated { return Err(...) }` (line 120). If the attacker sends the request with no `authorization` header and no `broadcast=1` query param, both `broadcast` and `authenticated` are `false`, so this check is skipped entirely, and the request proceeds to `self.broadcast = Some(false)` (line 134) with the block stored.
- `try_handle_request` (lines 147-207) passes `self.broadcast.unwrap_or(false)` into `Relayer::process_new_nakamoto_block_ext` (line 172), which is only a parameter to the *validation/storage* function, not to the relay decision.
- The actual P2P propagation trigger, `node.set_relay_message(StacksMessageType::NakamotoBlocks(...))` (lines 198-202), is gated only by `if data_resp.accepted`, i.e., purely on whether the block validated against chainstate - completely independent of `self.broadcast` or authentication.

Consequently, the `broadcast=1` + `authorization` gate does not actually gate network propagation at all; it only gates whether the *client's own request* is allowed to ask for broadcast (a no-op distinction, since a `false` broadcast value is never even read for that purpose downstream). Any remote, unauthenticated attacker can submit `POST /v3/blocks/upload/` with a valid/acceptable Nakamoto block body, no `authorization` header, and no `broadcast` query string. If `Relayer::process_new_nakamoto_block_ext` accepts the block (i.e., it is a valid Nakamoto block for a burn view/tenure the node already knows), `data_resp.accepted` is `true` and the block is unconditionally queued via `set_relay_message`, which downstream broadcasts it to the node's P2P peers as if it had arrived through normal consensus/relay channels.

### Impact Explanation
This meets the "network-wide propagation of forged data" / "unauthenticated write" Critical category: any block accepted by validation - regardless of upload authorization - is relayed by the victim node to its full P2P peer set. Since block acceptance requires the block to be a legitimately valid Nakamoto block (this is enforced by `process_new_nakamoto_block_ext`'s consensus validation, which is out of scope to bypass), the practical impact is that the authorization/broadcast gate provides no actual security control over relay: any actor with a valid block (which they could otherwise gossip via P2P) can instead push it through the unauthenticated RPC endpoint of any node, using that node as a free unauthenticated relay/amplification point, defeating the endpoint's documented intent that broadcast requires a shared secret. This is repeatable per node, per interval, for each new valid block the attacker manages to construct/observe.

### Likelihood Explanation
- Preconditions: the node must be running RPC with a `RPCPostBlockRequestHandler` configured with `self.auth = Some(password)` (a secret is configured, i.e., the operator expects unauthenticated broadcast to be blocked).
- Attacker cost: trivial - a single unauthenticated HTTP POST to `/v3/blocks/upload/` with a syntactically/consensus-valid Nakamoto block body and `Content-Type: application/octet-stream`.
- Remote reachability: the RPC port is remotely reachable by any unprivileged peer, matching the threat model exactly.
- Repeatable for any block the attacker can obtain or construct that validates.

### Recommendation
Gate `node.set_relay_message(...)` on `self.broadcast.unwrap_or(false)` (and therefore on successful authentication, since `broadcast=1` already requires `authenticated`) in addition to `data_resp.accepted`, e.g.:
```rust
if data_resp.accepted && self.broadcast.unwrap_or(false) {
    node.set_relay_message(...);
}
```
This restores the equality that only explicitly authorized (`broadcast=1` + valid `authorization`) uploads are relayed to the P2P network.
