Audit Report

## Title
V2 Snowbridge outbound converter binds `Message.origin` to an attacker-supplied `AliasOrigin` location instead of the authenticated sender, letting any AssetHub XCM caller impersonate another chain's agent - (File: `bridges/snowbridge/primitives/outbound-queue/src/v2/converter/convert.rs`)

## Summary
The V2 `XcmConverter::convert` derives the outbound `Message.origin` (which selects the Ethereum-side agent contract that the Gateway executes commands as) directly from the `AliasOrigin` instruction embedded in the caller-supplied XCM payload, validating it only against `AllowedAliasOrigin = EverythingBut<Equals<AssetHubLocation>>` — a denylist that blocks exactly one location and permits every other `Location` to be claimed as the origin. Since the authenticated sender (`para_id` derived from `universal_source` in `EthereumBlobExporter::validate`) is never bound to or compared with the claimed `AliasOrigin`, any signed AssetHub account can impersonate another registered agent (e.g. a sibling parachain or BridgeHub's own governance agent) and cause the Gateway to execute `CallContract` commands using that victim agent's held Ether/authority.

## Finding Description
In `bridges/snowbridge/primitives/outbound-queue/src/v2/converter/mod.rs:114-125`, `EthereumBlobExporter::validate` establishes the authenticated caller's `para_id` from `universal_source` and requires it to equal `AssetHubParaId`, but this verified identity is never threaded into the `XcmConverter` (`mod.rs:149-150` constructs `XcmConverter::new(&message, expected_network)` with no `agent_id`/`source_location` parameter). Instead, `XcmConverter::convert` at `bridges/snowbridge/primitives/outbound-queue/src/v2/converter/convert.rs:246-256` extracts `origin_location` directly from the `AliasOrigin` instruction inside the XCM payload — fully attacker-controlled data — and checks it only via `ensure!(AllowedAliasOrigin::contains(origin_location), InvalidOrigin)`. The runtime configures `AllowedAliasOrigin` as `EverythingBut<Equals<AssetHubLocation>>` in `cumulus/parachains/runtimes/bridge-hubs/bridge-hub-westend/src/bridge_to_ethereum_config.rs:80`, which is a denylist for a single location, not an allowlist tied to the true sender. The resulting `origin = AgentIdOf::convert_location(origin_location)` (line 256) is placed directly into `Message.origin` at `convert.rs:312-317`. This origin selects the Gateway agent that will execute `Command::CallContract { target, calldata, gas, value }`, where `value` can draw on Ether held by that agent. No code path compares the claimed `AliasOrigin` against the authenticated `para_id` established in `validate()`, so any location other than AssetHub's own sovereign location can be freely claimed by an unprivileged AssetHub-signed account.

## Impact Explanation
This allows unauthorized execution/origin escalation: an unprivileged AssetHub account can cause the Gateway to execute arbitrary `CallContract` commands "as" any other registered agent (sibling parachain's agent, or BridgeHub's own agent at `Location::here()`), potentially spending/draining Ether held by that agent's contract on Ethereum. This matches the Polkadot SDK Impact Gate categories of "unauthorized execution or origin escalation" and "theft ... or unlock" of bridge-held funds, reachable via a public extrinsic (`pallet_xcm::execute`) without governance, relayer, or validator compromise.

## Likelihood Explanation
The exploit only requires a signed AssetHub account able to call `pallet_xcm::execute` — a public entrypoint — and knowledge of the target agent's `Location`, which is predictable/derivable for many agents (e.g., `Location::here()` for BridgeHub, or `Location::new(1,[Parachain(id)])` for any sibling parachain). This is directly demonstrated feasible by the in-repo regression test `signed_assethub_user_cannot_bypass_origin_alteration_when_routing_to_ethereum` at `cumulus/parachains/integration-tests/emulated/tests/bridges/bridge-hub-westend/src/tests/snowbridge_v2_outbound_edge_case.rs:436-498`, which only proves the AssetHub-impersonation case is blocked but leaves every other location's impersonation unguarded.

## Recommendation
Bind `Message.origin` to the authenticated sender established during `EthereumBlobExporter::validate` (the `para_id`/derived `agent_id`), analogous to the v1 exporter, rather than trusting the payload's `AliasOrigin` value checked only against a denylist. If `AliasOrigin` is to be supported at all in v2, it should only be permitted to further restrict/refine within the authenticated sender's own authority (e.g., require it to equal or be a sub-location of the true sender's location), replacing `EverythingBut<Equals<AssetHubLocation>>` with logic that validates the claimed origin against the actual authenticated `para_id`/agent for that message.

## Proof of Concept
1. As any signed AssetHub account, call `PolkadotXcm::execute` with an XCM containing `InitiateTransfer { remote_xcm: [..., AliasOrigin(Location::new(1, [Parachain(<victim_para_id>)])), DepositAsset{...}, Transact{ call: CallContract{ target: <attacker_addr>, value: <agent_balance>, ...} }, SetTopic(..)] }`, following the pattern in `signed_assethub_user_cannot_bypass_origin_alteration_when_routing_to_ethereum` but substituting a sibling parachain (or BridgeHub's own) location instead of the AssetHub-forging location.
2. Because `AllowedAliasOrigin = EverythingBut<Equals<AssetHubLocation>>` only excludes AssetHub's own location, the `ensure!(AllowedAliasOrigin::contains(origin_location), InvalidOrigin)` check in `convert.rs:254` passes for the victim's location.
3. `AgentIdOf::convert_location(origin_location)` derives the victim's real agent id, which is placed into `Message.origin` at `convert.rs:312-317`, and the message is queued/committed for Ethereum execution as that agent.
