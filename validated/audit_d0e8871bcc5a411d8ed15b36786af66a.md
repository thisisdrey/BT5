I found a direct analog. The `withdraw_stake` helper in `vesting.move` reads the **full account balance** of the vesting contract's resource account instead of using only the coins actually returned by `staking_contract::distribute()`. This is the same root cause as the Forta bug: an externally-manipulable balance is used in place of the actual return value from a withdrawal function.

### Title
`withdraw_stake` Uses Full Account Balance Instead of Distributed Amount, Enabling Vesting Distribution Inflation — (`aptos-move/framework/aptos-framework/sources/vesting.move`)

### Summary

The internal `withdraw_stake` function in `vesting.move` calls `staking_contract::distribute()` to push withdrawable stake to the vesting contract's resource account, then reads `coin::balance<AptosCoin>(contract_address)` — the **entire** APT balance of that account — rather than the amount actually distributed. Because the vesting contract's resource account is registered for APT and is a publicly-known deterministic address, any unprivileged actor can send APT to it. The next call to `distribute()` or `admin_withdraw()` will sweep up those externally-injected coins and distribute them to shareholders as if they were legitimate staking rewards, breaking the vesting accounting invariant.

### Finding Description

`withdraw_stake` is defined as: [1](#0-0) 

```move
fun withdraw_stake(vesting_contract: &VestingContract, contract_address: address): Coin<AptosCoin> {
    staking_contract::distribute(contract_address, vesting_contract.staking.operator);
    let withdrawn_coins = coin::balance<AptosCoin>(contract_address);   // ← full balance, not return value
    let contract_signer = &get_vesting_account_signer_internal(vesting_contract);
    coin::withdraw<AptosCoin>(contract_signer, withdrawn_coins)
}
```

`staking_contract::distribute_internal` withdraws inactive stake from the underlying stake pool and deposits it into the vesting contract's account: [2](#0-1) 

After that deposit, `withdraw_stake` does not use the amount that `distribute` just deposited. Instead it reads `coin::balance<AptosCoin>(contract_address)`, which is the **total** APT balance of the resource account — including any coins that were already sitting there or were sent by a third party.

The vesting contract's resource account is registered for APT at creation time: [3](#0-2) 

This means any account can transfer APT to the vesting contract address at any time. The address is deterministic (derived from admin address + nonce + salt), so it is predictable before or after deployment.

`withdraw_stake` is called from both `distribute` and `admin_withdraw`: [4](#0-3) [5](#0-4) 

### Impact Explanation

An unprivileged attacker can:

1. Compute or observe the vesting contract's resource account address.
2. Transfer an arbitrary amount of APT directly to that address.
3. Call the permissionless `distribute(contract_address)` entry function.
4. `withdraw_stake` reads the inflated balance and returns a `Coin` that includes the attacker's injected APT.
5. The full inflated amount is distributed to shareholders proportionally via `pool_u64::shares_to_amount_with_total_coins`.

This causes **unauthorized reassignment of vesting balances**: coins that are not staking rewards are distributed to shareholders as if they were, breaking the invariant that only legitimately earned and unlocked stake flows through `distribute`. The `remaining_grant` counter is not updated to reflect this extra distribution, creating a permanent accounting inconsistency in the vesting contract state.

In the `admin_withdraw` path (post-termination), the same inflation causes the withdrawal address to receive more APT than the terminated contract legitimately holds from staking.

### Likelihood Explanation

- The vesting contract address is deterministic and publicly derivable.
- The `distribute` entry function is permissionless — anyone can call it.
- Sending APT to any registered account requires no special privilege.
- The attack requires only two transactions (transfer + distribute) and no privileged access.

### Recommendation

Track only the coins actually returned by `staking_contract::distribute`. Since `distribute_internal` deposits coins into the staker's account and returns nothing, the fix is to snapshot the balance **before** calling distribute and compute the delta:

```move
fun withdraw_stake(vesting_contract: &VestingContract, contract_address: address): Coin<AptosCoin> {
    let balance_before = coin::balance<AptosCoin>(contract_address);
    staking_contract::distribute(contract_address, vesting_contract.staking.operator);
    let balance_after = coin::balance<AptosCoin>(contract_address);
    let distributed_amount = balance_after - balance_before;
    let contract_signer = &get_vesting_account_signer_internal(vesting_contract);
    coin::withdraw<AptosCoin>(contract_signer, distributed_amount)
}
```

Alternatively, refactor `staking_contract::distribute` to return the distributed `Coin<AptosCoin>` directly so the caller does not need to read the balance at all.

### Proof of Concept

1. Admin creates a vesting contract for shareholders S1 (50%) and S2 (50%) with a 100 APT grant. The resource account address `V` is deterministic.
2. Staking rewards of 10 APT accumulate and become withdrawable.
3. Attacker calls `aptos_account::transfer(attacker, V, 1000_APT)` — sends 1000 APT to the vesting contract address.
4. Attacker (or anyone) calls `vesting::distribute(V)`.
5. `staking_contract::distribute` deposits 10 APT into `V`. Balance of `V` is now 1010 APT.
6. `withdraw_stake` reads `coin::balance(V) = 1010`, withdraws all 1010 APT.
7. S1 receives 505 APT, S2 receives 505 APT — 1000 APT more than they earned.
8. The `remaining_grant` field is unchanged, so the vesting contract believes the full grant is still outstanding, while 1000 extra APT have already been distributed. All future `vest`/`distribute` accounting is permanently corrupted.
