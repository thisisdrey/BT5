Confirmed: ETH-implicit accounts can never have their code redeployed or an access key added — this is enforced at the protocol level (`OnlyImplicitAccountCreationAllowed`/rejecting non-transfer actions on non-existent implicit accounts, and the fact that the account has no access key at all so any later transaction, including `DeployContract`, fails with `AccessKeyNotFound`). This makes the compile-time-baked `ADDRESS_REGISTRAR_ACCOUNT_ID` truly permanent and non-recoverable for every already-created wallet contract instance, which is a stronger, protocol-level analog of the Aave "hardcoded pool address" bug class (an immutable dependency address that cannot be rotated if the depended-on contract is migrated/compromised).

### Title
Wallet Contract's address registrar account ID is permanently hardcoded at compile time and can never be updated for already-deployed ETH-implicit accounts - (File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs)

### Summary
The `WalletContract` (the code deployed as a global contract on every ETH-implicit account) resolves the "Address Registrar" contract it depends on via a compile-time constant baked into the WASM binary, with no way to update it afterwards, analogous to the reported Aave issue of hardcoding a pool address instead of dynamically resolving it.

### Finding Description
`WalletContract` hardcodes the address registrar's account ID as a build-time constant: [1](#0-0) 
This value is read from a static file included via `include_str!`: [2](#0-1) 

The registrar's account ID is used, without any on-chain override mechanism, every time the wallet contract needs to check whether an ETH address maps to a named NEAR account (e.g. to decide whether a base-token transfer target should be redirected to a registered account instead of the raw ETH-implicit account): [3](#0-2) 

Unlike a typical NEAR contract (which can normally be redeployed by its own access key to point at a new dependency), an ETH-implicit account can never be updated after creation: it is created without any access key, and the protocol explicitly rejects any action other than the initial creating `Transfer` on such accounts, and any subsequent `DeployContract`/`AddKey` fails with `AccessKeyNotFound` because there is no key to sign with: [4](#0-3) [5](#0-4) 

The wallet contract code itself is shared as a `Global` contract keyed by a fixed code hash for the chain, and is baked in with the registrar ID at build time: [6](#0-5) [7](#0-6) 

Because every already-created ETH-implicit account is permanently bound to whatever global-contract code hash (and therefore whatever registrar account ID) was in effect when it was created, and because there is no mechanism to migrate an individual account to new code, if the `address-map.near` registrar account is ever deprecated, needs replacing due to a bug, or (worst case) becomes available for re-registration by an unrelated party, every already-deployed wallet contract instance permanently and un-fixably calls that fixed account ID with no way to redirect it — exactly the "hardcoded dependency address" flaw pattern from the report, but here it is enforced by the protocol's access-key rules rather than by a mere Solidity `immutable`.

### Impact Explanation
If the registrar account referenced by `ADDRESS_REGISTRAR_ACCOUNT_ID` ever needs to be migrated (bug fix, key compromise, or any reason) or if the account is ever deleted and its name becomes available for re-registration by anyone, all previously created ETH-implicit accounts (potentially every ETH wallet ever onboarded to NEAR) remain hardwired to the old ID. A malicious actor controlling that fixed account name could return crafted `lookup` results to the address-check callback, causing base-token transfers intended for a named account (because its ETH address is registered) to instead be silently redirected to the raw ETH-implicit account rather than the intended named recipient, or vice versa — since the wallet contract's own transfer-target routing decision hinges entirely on the registrar's response: [8](#0-7) 
This is a fund-misdirection vector that cannot be fixed for existing accounts since the code (and constant) cannot be redeployed once an ETH-implicit account exists.

### Likelihood Explanation
Low-to-medium: it requires the registrar account to change hands or be redeployed under a different identity, which is not an everyday occurrence, but the design provides no recovery path whatsoever if that ever happens — same likelihood/severity profile as the underlying Aave report, which is rated Medium because pool migrations, while infrequent, do happen and there is no mitigation once they do.

### Recommendation
Do not bake the registrar account ID into the wallet-contract WASM as an immutable compile-time constant with no override. Instead, either resolve the registrar dynamically through a stable, protocol-level indirection (e.g., a well-known system account or protocol config value that can be governed/upgraded), or ensure the registrar account name itself is permanently reserved/undeletable so it can never be recreated by another party, removing the "stale hardcoded address" risk described in the analogous Aave finding.

### Proof of Concept
Not applicable in the traditional sense (requires the registrar account's real-world migration/takeover to trigger); the structural proof is the combination of the constant embed at [1](#0-0)  with the protocol-enforced permanent immutability of ETH-implicit accounts shown in [4](#0-3) .
