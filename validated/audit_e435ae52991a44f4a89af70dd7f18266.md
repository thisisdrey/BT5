## Analysis

The Sherlock bug's root cause is a **check‑then‑mutate ordering flaw**: a piece of per‑request accounting state is read to make a decision, but the actual state mutation that should make that decision non‑repeatable happens too late (or is applied to a value that was already reset), so the same input can be "credited" more than once.

The closest reachable analog in this Nebula build is the anti‑replay window handling in `ConnectionState.Decrypt` / `ConnectionState.VerifyRelay`, which reproduces the same check‑then‑mutate race: the "used" marking of a message counter (`Bits.Update`) is deferred until *after* decryption, and the lock protecting the window is released in between, so two concurrent deliveries of the same ciphertext can both pass the "not yet seen" check before either one records it as seen.

### Title
Anti-replay window Check/Update race allows a captured ciphertext to be accepted twice - (File: connection_state.go)

### Summary
`ConnectionState.Decrypt` and `ConnectionState.VerifyRelay` split the anti-replay decision into two separately-locked steps: `window.Check()` (read-only "have we seen this counter" test) and `window.Update()` (the mutation that actually marks the counter as consumed). The `decryptLock` is released after `Check()` and only re-acquired after decryption completes, right before `Update()` runs. [1](#0-0) 

### Finding Description
The state that prevents replay (the `Bits` sliding window) is only mutated by `Update()`, and `Check()` never mutates it — it only tests the current bit. [2](#0-1) 

Because `decryptLock` is dropped between `Check` and the decryption call, and only re-acquired for the trailing `Update`, two goroutines processing the same captured/duplicated UDP datagram concurrently (Nebula runs multiple `listenOut`/`listenIn` reader routines when `tun.routines`/`listen.batch` > 1) can both:
1. Call `Check(messageCounter)` — both see the counter as unused (window bit not yet set) and both get `true`.
2. Both proceed to `dKey.DecryptDanger(...)` — since it is a byte-for-byte replay of a previously valid ciphertext, decryption succeeds for both.
3. Both then call `Update(messageCounter)` — the first call sets the bit and returns `true`; but by then both packets have already been fully decrypted and, critically, the first one has already been delivered to the tun device / control-message handler before the second's `Update` call even determines duplication.

This is the same bug class as the audit finding: a value meant to gate a one-time effect (`userRewardDebts`/anti-replay bit) is consulted for a decision, but the authoritative mutation of that value is deferred past the point where the "payout" (reward credit / packet delivery) already happened, and the lock scope does not span the whole check-act-mutate sequence. [3](#0-2) [4](#0-3) 

### Impact Explanation
This lets a network-adjacent attacker (no CA-signed certificate needed — only the ability to duplicate/replay an already-observed on-wire UDP datagram, e.g. by resending a captured packet to the target's UDP socket twice in quick succession) cause the same encrypted payload to be decrypted and delivered twice:
- For data-plane packets, this reintroduces the exact replay Nebula's anti-replay window is designed to prevent (duplicate delivery to the tun device).
- For relay/control payloads processed via `VerifyRelay`, a duplicated `NebulaControl` message (e.g. relay create/teardown) could be processed twice before the window records it as seen, since `VerifyRelay` has the identical Check/decrypt/Update split. [5](#0-4) 

### Likelihood Explanation
Requires precise packet duplication and a race window between two reader goroutines processing the same connection concurrently; Nebula's multi-routine UDP readers make this feasible when `listen.batch`/`tun.routines` are configured above 1, and simple duplicate-send timing from an attacker positioned to capture and resend a UDP datagram is sufficient — no cryptographic material or valid certificate is required.

### Recommendation
Hold `decryptLock` across the entire check-decrypt-update sequence (or fold `Check` and `Update` into a single atomic "check-and-mark" operation performed once and only released after decryption success/failure is known), so a second concurrent delivery of the same counter cannot pass `Check` before the first delivery's `Update` has recorded it.

### Proof of Concept
1. Establish a tunnel and capture one valid encrypted data or relay-control UDP packet destined for a host running with `listen.batch > 1` (or `tun.routines > 1`), so multiple reader goroutines can service the same `ConnectionState` concurrently.
2. Resend (replay) the identical captured UDP datagram to the target twice, back-to-back, timed so both reads are dispatched to different reader goroutines before either finishes `Decrypt`/`VerifyRelay`.
3. Both goroutines independently call `cs.window.Check(l, messageCounter)` while `decryptLock` is unheld between calls; both observe the counter unseen and proceed to `dKey.DecryptDanger`, which succeeds twice for the same ciphertext.
4. Both decrypted payloads are delivered/processed before the second `Update` call detects the duplicate, resulting in the replayed packet being accepted twice instead of once.

func (cs *ConnectionState) VerifyRelay(l *slog.Logger, messageCounter uint64, packet []byte, nb []byte) error {
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	signedPayload := packet[:len(packet)-cs.dKey.Overhead()]
	signatureValue := packet[len(packet)-cs.dKey.Overhead():]
	_, err := cs.dKey.DecryptDanger(nil, signedPayload, signatureValue, messageCounter, nb)
	if err != nil {
		return err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	return nil

// Check returns true if i is within (or way out in front of) the window, and not a replay
func (b *Bits) Check(l *slog.Logger, i uint64) bool {
	// If i is the next number, return true.
	if i > b.current {
		return true
	}

	if b.strictlyWithinWindow(i) {
		return !b.get(i)
	}

	// Not within the window
	if l.Enabled(context.Background(), slog.LevelDebug) {
		l.Debug("rejected a packet (top)", "current", b.current, "incoming", i)
	}
	return false
}
