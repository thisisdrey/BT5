## Analysis

The reported Arrakis bug class is "unbounded slippage when providing liquidity, because the actuator does not let the caller specify a minimum acceptable counter-asset amount." The direct analog in java-tron is `ExchangeInjectActuator`, which implements TRON's Bancor-style TRC10 exchange liquidity-injection path.

### Title
Unbounded slippage on `ExchangeInjectContract` allows sandwich-attack theft of exchange-creator funds - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`)

### Summary
`ExchangeInjectActuator` lets an exchange creator add liquidity to a TRC10 Bancor-style exchange pair by specifying one token's quantity; the contract computes the required amount of the paired token from the *current* pool ratio and pulls it from the creator's account. Unlike `ExchangeTransactionContract`, which carries an `expected` field enforced in `ExchangeTransactionActuator`, `ExchangeInjectContract` has no minimum/maximum bound on the derived `anotherTokenQuant`, so the creator is exposed to unbounded slippage that another account can manipulate.

### Finding Description
`ExchangeInjectContract` only carries `owner_address`, `exchange_id`, `token_id`, and `quant` — no expected/min amount for the paired token: [1](#0-0) 

In execution, the paired-token amount is derived purely from the exchange's live balances at execution time: [2](#0-1) 

The same unconstrained calculation is repeated in `doValidate()`, with no comparison against any caller-supplied bound: [3](#0-2) 

By contrast, `ExchangeTransactionActuator` (the trade/swap path) does enforce a caller-specified minimum via the `expected` field: [4](#0-3) 

Because `ExchangeTransactionContract` is broadcastable by any account holding the relevant tokens, an attacker can submit a large trade that skews the pool's `firstTokenBalance`/`secondTokenBalance` ratio immediately before the exchange creator's pending `ExchangeInjectContract` executes. Since `anotherTokenQuant` in the inject path is `floorDiv(otherBalance * tokenQuant, sameBalance)`, a ratio distorted by the attacker's front-run trade forces the creator's account to be debited far more of the paired asset than intended for the same declared `quant`. The attacker then submits a reverse trade to restore the ratio, capturing the excess value that was effectively transferred into the pool by the creator at the manipulated rate, and can withdraw it via a subsequent `ExchangeTransactionContract`/`ExchangeWithdrawContract`. This mirrors the Arrakis pattern precisely: the depositor (here, the exchange owner performing an inject) has no way to bound how much of the counter-asset gets locked in for the amount of the declared asset, so a front-run/back-run sandwich around the inject transaction extracts value from the depositor.

### Impact Explanation
An exchange creator who injects liquidity can be forced to give up a disproportionate amount of one of their two TRC10/TRX asset balances to a sandwiching attacker, resulting in a direct, quantifiable loss of funds equivalent to the price impact created by the attacker's bracketing trades. This is a theft-of-funds vector reachable purely through ordinary signed transactions (`ExchangeTransactionContract` calls sandwiching an `ExchangeInjectContract`), requiring no special privilege beyond holding tokens tradeable on that exchange pair.

### Likelihood Explanation
Likelihood is moderate-to-high in adversarial mempool/block-producer environments: any account can watch for pending `ExchangeInjectContract` transactions (or simply attempt opportunistic ordering around routine exchange-creator liquidity top-ups) and bracket them with `ExchangeTransactionContract` trades, since exchange pair ids and balances are all public on-chain state and the actuator performs no price-deviation or minimum-received check to block it.

### Recommendation
Add a caller-specified bound to `ExchangeInjectContract` (e.g., a `min_another_token_quant` or `max_another_token_quant` field), and enforce it in `ExchangeInjectActuator.doValidate()`/`execute()` analogous to the `expected` check already present in `ExchangeTransactionActuator`. Alternatively, restrict injections to be time-locked or add price-deviation checks similar to safeguards used elsewhere in the codebase for exchange operations.

### Proof of Concept
1. Exchange creator prepares `ExchangeInjectContract{exchange_id, token_id=A, quant=Q}` expecting the pool's current ratio to require `B_expected` of the paired token.
2. Attacker observes the pending inject transaction and submits `ExchangeTransactionContract` trades that shift `firstTokenBalance`/`secondTokenBalance` so that the ratio used by `ExchangeInjectActuator.execute()` (`floorDiv(secondTokenBalance * tokenQuant, firstTokenBalance)`) now computes a much larger `anotherTokenQuant` than `B_expected`. [5](#0-4) 
3. The creator's inject transaction executes at the distorted ratio, debiting far more of token B from the creator's account than intended (no `expected`/min check exists to block this, unlike in `ExchangeTransactionActuator`).
4. Attacker submits a reverse trade restoring the original ratio, then trades against the now-inflated pool via `ExchangeTransactionContract` to extract the excess value deposited by the creator.
