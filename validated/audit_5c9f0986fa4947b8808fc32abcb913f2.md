### Title
Missing negotiation-phase deadline in `PostUploadPackWithSidechannel` allows TOCTOU authorization bypass / connection-hold DoS - (File: internal/gitaly/service/smarthttp/upload_pack.go)

### Summary
The externally reported bug is about a Uniswap-style function that sets a swap `deadline` to `block.timestamp`, effectively disabling deadline enforcement and letting a malicious actor hold the transaction open indefinitely to their advantage. The Gitaly analog is the same "no expiration/deadline enforcement lets an attacker hold an operation open" bug class, reachable via `SmartHTTPService.PostUploadPackWithSidechannel`, which streams `git-upload-pack --stateless-rpc` and never bounds how long it will wait for the client's negotiation input.

### Finding Description
Gitaly has a known, explicitly documented mitigation for this exact class of bug in the SSH transport. `runUploadCommand` in [1](#0-0)  wraps `git-upload-pack`/`git-upload-archive` invocations with a `pktline.ReadMonitor` that cancels the command's context if the client does not send the negotiation-terminating packet (`done`/flush) within a configured timeout. The rationale is spelled out directly in `internal/git/pktline/read_monitor.go`: [2](#0-1)  — without this timeout, "the access check for a git command is run before the command itself. The user has control of stdin for the git command, and if they can delay input for an arbitrarily long time, they can gain access days or weeks after the access check has completed."

This timeout is wired up via `s.uploadPackRequestTimeoutTickerFactory()`/`s.uploadArchiveRequestTimeoutTickerFactory()` in `internal/gitaly/service/ssh/upload_pack.go` [3](#0-2)  and `internal/gitaly/service/ssh/upload_archive.go` [4](#0-3) , and is backed by the `Timeout.UploadPackNegotiation`/`Timeout.UploadArchiveNegotiation` config defaults in `internal/gitaly/config/config.go` [5](#0-4) .

However, the SmartHTTP RPC that performs the functionally identical operation — `PostUploadPackWithSidechannel` → `runUploadPack` — does **not** apply this protection. It executes `git-upload-pack --stateless-rpc` directly against client-controlled `stdin` with no read monitor and no negotiation deadline: [6](#0-5) . The `UploadPackNegotiation`/`RequestTimeoutTickerFactory` machinery is referenced only from the `ssh` package (`internal/gitaly/service/ssh/server.go`, `upload_pack.go`, `upload_archive.go`) and is absent from the `smarthttp` package entirely, confirmed by searching the whole codebase for these symbols.

### Impact Explanation
Access-control checks for Gitaly RPCs (e.g. GitLab Rails authorizing a user's read access to a project before the RPC is dispatched, or a `PreReceive`/custom hook style check gating the call) happen once, before/at the start of the RPC. Because `PostUploadPackWithSidechannel` places no upper bound on how long it will wait for the client to finish sending "want"/"have"/"done" packets, an ordinary authenticated user with a valid fetch/clone connection can keep the negotiation phase open indefinitely (e.g., by slow-streaming or deliberately withholding the terminating packet) while their access is later revoked (project made private, user removed from project, token revoked). When they finally complete the negotiation, `git-upload-pack` proceeds to generate and stream the packfile with no further authorization re-check, exactly the "no expiration deadline" flaw described in the source report — the operation is executed at a time the actor chooses, after the access check window, rather than being bound to it. Separately, this also allows an unauthenticated/low-privilege connection to hold a gRPC handler and its spawned `git-upload-pack` process open indefinitely, tying up a git subprocess/goroutine/socket resource per connection (DoS of the handler), which is the resource the SSH path explicitly protects against.

### Likelihood Explanation
The `PostUploadPackWithSidechannel` RPC is directly reachable by any client capable of performing a `git fetch`/`git clone` over HTTP against Gitaly (standard, everyday usage) — no special privileges beyond ordinary fetch access are needed to control the pacing of stdin during negotiation. The vulnerable code path (`runUploadPack`) is exercised on every HTTP-based fetch, and the missing mitigation is a straightforward code-path omission (not requiring any race with a third party), so exploitability is high given attacker control of the request timing.

### Recommendation
Apply the same negotiation-phase deadline/read-monitor mechanism used by `internal/gitaly/service/ssh/upload_command.go` to the SmartHTTP `runUploadPack` path in `internal/gitaly/service/smarthttp/upload_pack.go`: wrap the client-controlled `stdin` in a `pktline.NewReadMonitor` keyed on the pack-protocol "done" packet, cancel the command context if the boundary packet is not observed within a configured timeout (reusing/extending `Timeout.UploadPackNegotiation`), and surface a `DeadlineExceeded` error consistent with the SSH implementation.

### Proof of Concept
1. As an authenticated user with fetch access to a repository, initiate `git fetch` (or a raw HTTP POST to `/info/refs?service=git-upload-pack` followed by `POST /git-upload-pack`) against a GitLab/Gitaly SmartHTTP endpoint, which invokes `PostUploadPackWithSidechannel`.
2. Send the `want`/`have` lines but deliberately stall before sending the `done` packet/flush (e.g., trickle bytes with long delays, or simply stop sending).
3. Because `runUploadPack` in `internal/gitaly/service/smarthttp/upload_pack.go` has no read-monitor/timeout analogous to `runUploadCommand` in `internal/gitaly/service/ssh/upload_command.go`, the spawned `git-upload-pack --stateless-rpc` process and the RPC handler remain blocked indefinitely (limited only by the overall gRPC/HTTP connection timeout, if any, which is far coarser and not designed for this purpose).
4. While stalled, have the project's visibility changed to private or the user's access revoked out-of-band.
5. Resume sending `done` — `git-upload-pack` proceeds to build and stream the packfile with no re-authorization, and/or the held connection consumes a `git-upload-pack` process/goroutine for the entire stall duration, demonstrating both the TOCTOU authorization gap and the resource-hold DoS potential.

Note: I could not find any additional gRPC-level deadline enforcement specific to `PostUploadPackWithSidechannel` beyond generic connection/keepalive settings, so I cannot rule out that an operator-configured gRPC/HTTP proxy timeout partially mitigates the DoS aspect in some deployments; however, no such mitigation exists in the Gitaly source itself for this RPC.
