### Title
`action_delete_account` deletes accounts whose `PostponedReceipt`/`PromiseYieldReceipt`/`ReceivedData` trie storage is never accounted or removed, permanently orphaning that trie storage - (File: `runtime/runtime/src/actions.rs`)

### Summary
`action_delete_account` (`runtime/runtime/src/actions.rs:314-353`) bounds deletion using `account_ref.storage_usage()` minus contract-code bytes, capped at `Account::MAX_ACCOUNT_DELETION_STORAGE_USAGE` (10,000 bytes). This field never reflects `PostponedReceipt`, `PromiseYieldReceipt`, `ReceivedData`, `PostponedReceiptId`, or `PendingDataCount` trie rows belonging to the account, and `remove_account` (`core/store/src/utils/mod.rs:505-575`) never deletes those rows either. An account can be deleted while such rows remain permanently orphaned in the trie.

### Finding Description
`Account.storage_usage` is a plain field maintained incrementally by explicit action handlers (key add/remove, contract deploy, data-record writes) but is never touched by the receipt-matching/postponed-receipt/promise-yield code paths. Confirmed directly:
- `process_action_receipt` (`runtime/runtime/src/lib.rs:1593-1658`) calls `set(state_update, TrieKey::PendingDataCount {...}, ...)` and `set_postponed_receipt` when input data is missing — neither touches the account's `storage_usage`.
- `process_receipt`'s `Data` branch (`runtime/runtime/src/lib.rs:1386-1474`) calls `set_received_data` — again no `storage_usage` update.
- `set_promise_yield_receipt` / `set_promise_yield_status` (`core/store/src/utils/mod.rs:200-271`) write `PromiseYieldReceipt`/`PromiseYieldStatus` rows with no account mutation.
- Genesis's own `StorageComputer::process_record` (`core/store/src/genesis/state_applier.rs:41-77`) explicitly maps `StateRecord::PostponedReceipt(_) => None` and `StateRecord::ReceivedData { .. } => None`, confirming by design that these record kinds are *not* counted toward any account's storage usage.

`action_delete_account` computes its size check purely from `account_ref.storage_usage()` (minus contract bytes for the `FixDeleteAccountGlobalContractStorageUsage`-gated subtraction) — see `runtime/runtime/src/actions.rs:326-347` — and compares it against `Account::MAX_ACCOUNT_DELETION_STORAGE_USAGE = 10_000` (`actions.rs:348`). None of the postponed/received-data/yield keys factor into this number.

On the deletion path itself, `remove_account` (`core/store/src/utils/mod.rs:505-575`) removes only: the `Account` row, `ContractCode`, all `AccessKey`/gas-key-nonce rows, and `ContractData` rows. It does **not** iterate or remove `PostponedReceipt`, `PostponedReceiptId`, `PendingDataCount`, `ReceivedData`, `PromiseYieldReceipt`, or `PromiseYieldStatus` keys for the account.

Exploit flow (fully reachable by an ordinary account holder with no special privileges):
1. Attacker's account `A` deploys a small contract and, from ordinary signed transactions, issues many cross-contract calls with unresolved `input_data_ids` (e.g., a batch of calls that await callback data that will never arrive, or many outstanding `promise_yield_create` calls that are never resumed). Each produces a `PostponedReceipt`/`PendingDataCount`/`PostponedReceiptId` or `PromiseYieldReceipt`/`PromiseYieldStatus`/timeout-queue entry keyed to `A`, none of which touch `A.storage_usage`.
2. `A.storage_usage` stays small (its own `Account` record plus whatever keys/contract it explicitly tracks), so it easily remains under 10,000 bytes even though many kilobytes/megabytes of postponed-receipt state sit in the trie under `A`'s key prefix.
3. Attacker submits `DeleteAccountAction` on `A`. `action_delete_account` computes `account_storage_usage` from the small `storage_usage` field, passes the `MAX_ACCOUNT_DELETION_STORAGE_USAGE` check, and calls `remove_account`, which deletes the `Account` record and its access keys/contract data but leaves the postponed/received-data/yield rows untouched in the trie.
4. `A`'s remaining NEAR balance is refunded to `beneficiary_id` (`actions.rs:364-370`), completing the storage-staking payout, while the corresponding trie bytes for the orphaned rows are never refunded nor reachable/removable (no account exists anymore to re-delete or reclaim them through, and `remove_account` never visits these key prefixes).

None of the existing checks stop this: the deletion-size cap only inspects `storage_usage`, which by design excludes these key classes; `check_storage_stake` similarly only staking-backs `storage_usage`-tracked bytes; there is no invariant tying postponed/yield/received-data bytes to the deleting account's payable balance.

### Impact Explanation
This is a value-conservation violation: storage-staking is meant to ensure the account's locked balance backs exactly the trie bytes it owns, and that balance is refunded/burned in proportion when the account or its state is removed. Here, an attacker can leave arbitrarily large volumes of un-owned, unreachable trie state (`PostponedReceipt`, `PromiseYieldReceipt`, `ReceivedData`, and their indices) permanently in the state trie after the owning account disappears — with no storage-stake balance backing them and no way for anyone to ever remove them (no account context to run a corresponding cleanup action against). This matches "permanent storage-stake fund freezing / unaccounted trie bloat": network state trie size grows unboundedly and permanently at zero ongoing cost to the attacker, degrading state size/growth guarantees that storage staking is designed to enforce.

### Likelihood Explanation
Preconditions are minimal and fully within reach of an unprivileged user: deploy a contract, issue transactions that create unresolved cross-contract-call data dependencies or abandoned yields, then submit a `DeleteAccountAction`. The attacker pays ordinary gas/storage-staking fees for the initial calls (bounded by attached gas per receipt), but can repeat this from many accounts and receipts over time, and the per-attempt cost is far lower than the eventual permanent trie bloat produced (postponed receipts can embed the full serialized `ActionReceipt`, including its `actions` list, giving an attacker control over the size of each orphaned entry). This is trivially repeatable by any account, requiring no validator/node control, no race conditions, and no unusual protocol version dependencies (the underlying `storage_usage` exclusion behavior is confirmed in the current base protocol).

### Recommendation
Either (a) account for `PostponedReceipt`/`PromiseYieldReceipt`/`ReceivedData`/index-row bytes in `Account.storage_usage` as they are created (mirroring how other stateful additions like access keys/contract data are tracked), and include them in the `MAX_ACCOUNT_DELETION_STORAGE_USAGE` check and in `remove_account`'s cleanup pass, or (b) have `action_delete_account` reject deletion (or force it to iterate and drain) whenever any outstanding `PostponedReceipt`, `PendingDataCount`, `PostponedReceiptId`, `ReceivedData`, or `PromiseYieldReceipt`/`PromiseYieldStatus` rows exist for the account, similar to how staking-lock (`DeleteAccountStaking`) currently blocks deletion. `remove_account` should be extended to iterate and remove these key prefixes (analogous to the existing access-key and contract-data iteration) so that no orphaned rows survive account deletion regardless of the storage-usage bound.

### Proof of Concept
Integration test plan (extending the existing `runtime/runtime/src/tests/apply.rs` harness, which already has helpers like `create_receipt_with_actions`, `action_receipt_awaiting`, and `get_postponed_receipt`):
1. Create account `A` with a small `Account.storage_usage` (well under 10,000 bytes) and no contract.
2. Apply a receipt to `A` with `input_data_ids` referencing a `data_id` that is never delivered (using `action_receipt_awaiting`-style construction), causing `process_action_receipt` to persist a `PostponedReceipt` and `PendingDataCount`/`PostponedReceiptId` for `A`. Assert via `get_postponed_receipt` that the row exists, and assert `A`'s stored `Account.storage_usage` is unchanged from before this receipt.
3. Repeat step 2 N times (or with a large embedded `ActionReceipt` payload) to accumulate significant orphaned trie bytes under `A`, while confirming `Account::storage_usage(&A) <= MAX_ACCOUNT_DELETION_STORAGE_USAGE`.
4. Submit a `DeleteAccountAction` receipt for `A` with a `beneficiary_id`. Assert the action succeeds (`ActionResult::result.is_ok()`, no `DeleteAccountWithLargeState`).
5. After applying and committing trie changes, assert `get_account(&state, &A_id)` returns `None` (account gone) **and** `get_postponed_receipt(&state, &A_id, receipt_id)` (and `get(state, &TrieKey::PendingDataCount{...})`) still return `Some(..)` — proving the postponed-receipt bytes survive account deletion, are never refunded to the beneficiary, and are permanently unreachable/unremovable trie state.
