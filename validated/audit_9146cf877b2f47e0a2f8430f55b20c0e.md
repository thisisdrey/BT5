### Title
Unvalidated `refund_to` destination causes permanent burning of refunded deposits - (File: `runtime/near-vm-runner/src/logic/logic.rs`)

### Summary
The Across V2 report describes a relayer-supplied `repaymentChainId` that is never validated against a set of acceptable values, so an invalid choice silently results in the relayer/user losing the repayment. The nearcore analog is the `promise_set_refund_to` host function, which lets a contract redirect the balance refund of an outgoing promise to an arbitrary `AccountId` that is validated only for *syntax*, never for *existence or reachability*. Because refund receipts are explicitly barred from triggering implicit account creation, redirecting a refund to a non-existent account causes the refund transfer to fail and the deposit to be permanently burned instead of returned to anyone.

### Finding Description
A contract creates an outgoing promise/receipt and can call `promise_set_refund_to` to change where any deposit/gas refund for that receipt is sent: [1](#0-0) 

The only check performed on the supplied account id is `read_and_parse_account_id`, i.e. NEAR account-id syntax validation. There is no check that the account exists, is not empty, or is capable of receiving a transfer. This propagates into `ActionReceiptV2.refund_to`: [2](#0-1) 

`validate_action_receipt`, which is the only validation step run on new receipts (including refund-target receipts) before they are queued for execution, again only validates syntax: [3](#0-2) 

When the refund is actually executed, the runtime explicitly disallows implicit account creation for refund receipts: [4](#0-3) 

If the target account does not exist and cannot be implicitly created, the transfer action fails with `AccountDoesNotExist`, causing the entire (free, no-gas) refund receipt to fail. Per the protocol's own documentation, a failed refund's balance is not retried or returned anywhere — it is burnt: [5](#0-4) 

This is functionally identical to the reported bug class: a value supplied by an untrusted/semi-trusted party (here, the contract executing `promise_set_refund_to`, analogous to the relayer choosing `repaymentChainId`) determines where funds are repaid/refunded, is not validated against any "acceptable" or reachable set, and an invalid value results in unrecoverable loss of the funds rather than a safe fallback (e.g., back to the receipt's real predecessor).

### Impact Explanation
Deposits attached to promises can be substantial (e.g., cross-contract calls forwarding user-supplied deposits, or meta-transaction flows where `refund_to` exists specifically to redirect a refund away from the nominal `predecessor_id` back to the entity that actually funded the transfer, per `docs/architecture/how/meta-tx.md`). If the intermediate contract (whether by bug or malice) sets `refund_to` to a mistyped, stale, or otherwise non-existent account, any deposit refund generated on failure of that promise is permanently burned rather than returned to the legitimate party (the true payer or the predecessor). This is a permanent loss of user funds with no on-chain recovery path, matching the "concrete... permanent freezing/loss of funds" acceptance criterion.

### Likelihood Explanation
Triggering this requires only a normal contract call using standard, unprivileged host functions (`promise_batch_action_function_call` with a deposit + `promise_set_refund_to`) — no elevated privileges, no validator/node compromise, and no protocol bypass are needed. Any contract author (or an attacker who can get a victim to interact with a malicious/careless contract that forwards deposits) can set an arbitrary `refund_to` value. The failure mode is deterministic: whenever the underlying promise fails and the configured `refund_to` account does not exist, the deposit is burned every time.

### Recommendation
Before accepting a `refund_to` value in `promise_set_refund_to` (or at receipt-validation time in `validate_action_receipt`), require that the target account actually exists (or fall back to normal implicit-account-creation rules for refunds), or alternatively fall back to the original refund target (`predecessor_id`) whenever the configured `refund_to` account cannot receive the transfer, instead of silently burning the balance. At minimum, this behavior (irrecoverable burn on invalid `refund_to`) should be prominently documented as a foot-gun for contract developers, similar to what UMA/Across committed to doing for `repaymentChainId`.

### Proof of Concept
1. Deploy contract `C`. `C` receives an attached deposit `D` from account `P` via a `FunctionCall`.
2. `C` creates a new promise batch toward some account `T`, attaches deposit `D` to a `FunctionCall` action that is guaranteed to fail (e.g., calling a non-existent method on `T`), then calls `promise_set_refund_to(promise_idx, "definitely-nonexistent-account.near")`, exactly as demonstrated by the existing test harness pattern: [6](#0-5) 
3. The function call to `T` fails as designed, generating a deposit-refund receipt targeting `definitely-nonexistent-account.near` instead of `C`/`P`.
4. Because it's a refund receipt, implicit-account creation is skipped (`runtime/runtime/src/actions.rs:857-877`), the `Transfer` action fails with `AccountDoesNotExist`, and the deposit `D` is burned per `docs/RuntimeSpec/Refunds.md:10-13` rather than returned to `C` or `P` — a permanent, irrecoverable loss of `D`.

```rust
    pub fn promise_set_refund_to(
        &mut self,
        promise_idx: u64,
        account_id_len: u64,
        account_id_ptr: u64,
    ) -> Result<()> {
        self.result_state.gas_counter.pay_base(base)?;
        if self.context.is_view() {
            return Err(HostError::ProhibitedInView {
                method_name: "promise_set_refund_to".to_string(),
            }
            .into());
        }
        let refund_to = self.read_and_parse_account_id(account_id_ptr, account_id_len)?;
        let promise = self
            .promises
            .get(promise_idx as usize)
            .ok_or(HostError::InvalidPromiseIndex { promise_idx })?;

        let receipt_idx = match &promise {
            Promise::Receipt(receipt_idx) => Ok(*receipt_idx),
            Promise::NotReceipt(_) => Err(HostError::CannotSetRefundToOnJointPromise),
        }?;

        self.ext.set_refund_to(receipt_idx, refund_to);
        Ok(())
    }
```

**File:** docs/RuntimeSpec/Refunds.md (L10-13)
```markdown
Refund receipts are identified by having `predecessor_id == "system"`. They are also special because they don't cost any gas to generate or execute. As a result, they also do not contribute to the block gas limit.

If the execution of a refund fails, the refund amount is burnt.
The refund receipt is an `ActionReceipt` that consists of a single action `Transfer` with the `deposit` amount of the refund.
```
