### Title
Insecure-by-default `pki.disconnect_invalid` allows continued communication with hosts holding expired/revoked/blocklisted certificates - (File: connection_manager.go, interface.go)

### Summary
The external report flags the router's `confirmations` config defaulting to an unsafe minimum (`1`), which can leave the system trusting stale/unsafe state after a chain re-org. The closest reachable analog in this Nebula codebase is the `pki.disconnect_invalid` configuration flag, which controls whether Nebula proactively tears down tunnels once a peer's certificate becomes invalid (expired, or its issuing CA is removed/blocklisted from the trust store). This flag defaults to `false`.

### Finding Description
`pki.disconnect_invalid` is documented as a config option that "will tear down tunnels when they become invalid (through expiry or removal of root trust)" with a stated **default of `false`**, as noted in the CHANGELOG: [1](#0-0) 

This value is read via `config.C` and referenced in both `interface.go` and `connection_manager.go`, matching the `DisconnectInvalid` field/flag used to gate reconnection logic: [2](#0-1) [3](#0-2) 

(Note: I confirmed the grep hits for `disconnect_invalid`/`DisconnectInvalid` in `interface.go` and `connection_manager.go`, but was not able to pull the exact surrounding line ranges/logic in this pass due to running out of tool iterations — the precise call sites and the exact conditional logic gating rehandshake/teardown behavior in those files should be verified directly before remediation.)

Because the default is `false`, a Nebula node will **not** automatically disconnect from a peer whose certificate has expired or whose issuing CA has since been removed from the trust pool (`pki.ca`) or added to a blocklist, unless the operator explicitly opts in. This is directly analogous to the router's `confirmations: 1` issue: a "safe" behavior (verifying continued validity/trust before continuing to act) exists in the code, but is not the default, silently leaving deployments in a less-secure posture unless they know to change it.

Separately, `firewall.default_local_cidr_any` similarly defaults to `false` in recent releases specifically to close a prior unsafe default (v1.10.0 changelog), which shows the project has previously recognized and fixed this exact bug class for other settings — but `pki.disconnect_invalid` was not brought into line with that pattern: [4](#0-3) [5](#0-4) 

### Impact Explanation
If a CA is revoked/removed from the trust pool (e.g., due to key compromise) or a peer's certificate expires while a tunnel is already established, a node running with default settings will continue to trust and communicate over the existing tunnel rather than immediately tearing it down. This extends the window during which a compromised or revoked identity can continue sending/receiving encrypted traffic over the overlay network, undermining the certificate-based trust model that is central to Nebula's security guarantees.

### Likelihood Explanation
This requires no attacker action beyond already possessing a certificate that later becomes invalid (e.g., an insider whose cert is revoked, or an attacker who compromised a CA key that is subsequently rotated). Because the unsafe behavior is the out-of-the-box default, any deployment that doesn't explicitly set `pki.disconnect_invalid: true` is affected, making this a config-class weakness with broad reach across default deployments — mirroring the router report's core complaint about unsafe defaults being silently shipped.

### Recommendation
- Change the default of `pki.disconnect_invalid` to `true`, or at minimum emit a startup warning when it is left unset, similar to the precedent already set for `firewall.default_local_cidr_any`.
- Document prominently in the example config and README that leaving `disconnect_invalid` at its default can allow continued communication with hosts whose trust has been revoked.
- Confirm the exact enforcement path in `interface.go`/`connection_manager.go` (not fully re-verified in this pass) to ensure the flag is checked on every relevant certificate-state transition (CA removal, blocklist update, expiry), not just at initial handshake.

### Proof of Concept
Conceptual (config-only) PoC:
1. Deploy two Nebula nodes with a CA and issue certs to both.
2. Establish a tunnel between them.
3. Revoke/remove the peer's CA from `pki.ca` (or add the peer cert's fingerprint to a blocklist) on node A, then trigger a config reload (SIGHUP).
4. With default settings (`pki.disconnect_invalid` unset/`false`), observe that the existing tunnel to the now-untrusted peer remains active and traffic continues to flow, rather than being torn down.
5. Repeat with `pki.disconnect_invalid: true` set explicitly and observe the tunnel is torn down — demonstrating the default configuration is the less-safe behavior.

*Caveat: I was unable to fully trace the exact conditional branches in `interface.go` and `connection_manager.go` that consume `DisconnectInvalid` within the remaining tool budget; the finding is grounded in the documented default and the confirmed presence of the flag in both files, but the precise mechanics of enforcement should be validated directly in code before treating this as fully proven.*
