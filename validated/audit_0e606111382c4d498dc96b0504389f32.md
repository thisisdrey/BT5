### No vulnerability found for this question.

**Rationale:**

The premise of the question — that a re-entrant call into `execute_intents` can observe or spend balances "before" the withdraw resolves — does not hold under NEAR's execution model, and even if it did, the described scenario involves no unauthorized balance change.

**Binding checked:** *balance change for token T == signer's own valid signature for T's exact amount*, evaluated for both the withdrawn token (`T1`) and the "different token" (`T2`) spent from within `ft_on_transfer`.

1. **No actual reentrancy window exists.** `Contract::internal_ft_withdraw` calls `self.withdraw(...)`, which synchronously executes `internal_sub_balance` for the withdrawn token *before* any `Promise` is scheduled: [1](#0-0) . This state mutation is committed to contract storage when the enclosing `execute_intents` receipt finishes executing — Promises in NEAR (`ft_transfer_call`, and its downstream `ft_on_transfer` on the attacker's malicious receiver contract) are scheduled as separate, later receipts, not synchronous callbacks. By the time the malicious `ft_on_transfer` runs and calls back into `execute_intents`, the original receipt that debited `T1` has already fully completed and its state changes are already final. There is no overlapping/concurrent mutable state to race against.

2. **`ft_resolve_withdraw` reading `promise_result_checked_json::<U128>(0)`** only determines whether a *refund* of the already-debited `T1` amount is credited back via `self.deposit(...)`, based on how much the token contract reports as actually transferred: [2](#0-1) . This callback operates strictly on `T1`'s balance for `sender_id`; it never touches any other `TokenId`, so a second signed intent on `T2` cannot interact with or corrupt this refund computation.

3. **The "different token" spend is fully authorized.** The scenario requires the attacker to sign a *second*, valid `MultiPayload` for `T2` with their own key. This is not a forged or unauthorized balance change — it is the attacker spending their own remaining `T2` balance with their own valid signature, which `execute_intents` is designed to allow via `MultiPayload::verify` and nonce commitment regardless of call ordering. Two independent, individually-authorized spends on two independent `TokenId` maps (`internal_sub_balance` operates per-`TokenId` on the `Amounts` map) cannot produce a double-count or an unauthorized credit — each token's ledger is updated exactly once per authorized intent, matching `AUTHORISATION`.

Since there is no synchronous reentrancy possible in NEAR's receipt-based execution, no shared read/write of `T1`'s or `T2`'s balance is observed inconsistently, and the second spend is signer-authorized on the signer's own funds, there is no violation of the balance/authorization equality and no path to unauthorized value leaving the Verifier.

    #[private]
    fn ft_resolve_withdraw(
        &mut self,
        token: AccountId,
        sender_id: AccountId,
        amount: U128,
        is_call: bool,
    ) -> U128 {
        let used = if is_call {
            // `ft_transfer_call` returns successfully transferred amount
            match promise_result_checked_json::<U128>(0) {
                Ok(Ok(used)) => used.0.min(amount.0),
                Ok(Err(_deserialize_err)) => 0,
                // do not refund on failed `ft_transfer_call` due to
                // NEP-141 vulnerability: `ft_resolve_transfer` fails to
                // read result of `ft_on_transfer` due to insufficient gas
                Err(_) => amount.0,
            }
        } else {
            // `ft_transfer` returns empty result on success
            if promise_result_checked_void(0).is_ok() {
                amount.0
            } else {
                0
            }
        };

        let refund = amount.0.saturating_sub(used);
        if refund > 0 {
            self.deposit(
                sender_id,
                [(Nep141TokenId::new(token).into(), refund)],
                Some(REFUND_MEMO),
            )
            .unwrap_or_else(|err| err.panic());
        }

        U128(used)
    }
