## Title
Wallet‑contract callback panic permanently bricks `has_in_flight_tx`, freezing the eth‑implicit account - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
`WalletContract` (the eth-implicit account contract) uses a boolean guard `has_in_flight_tx` to serialize Ethereum-style transactions submitted through `rlp_execute`. This flag is only ever reset to `false` inside privileged `#[private]` callback methods that run as part of the promise chain kicked off by `rlp_execute`. If one of those callbacks fails to complete (panics) for any reason before reaching its `self.has_in_flight_tx = false` reset, NEAR's receipt-atomicity guarantee rolls back *all* state changes for that receipt — permanently leaving the flag `true` with no other code path able to clear it, since `rlp_execute` immediately rejects every future transaction while the flag is set.

### Finding Description
`WalletContract::rlp_execute` (`runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs:89-128`) is the sole entry point for a user to act through their eth-implicit account. It refuses to do anything while `has_in_flight_tx` is `true`: [1](#0-0) 

The flag is set `true` right before returning a `Promise`, and is only ever reset to `false` at the very top of the private callback methods `address_check_callback`, `nep_141_storage_balance_callback`, `rlp_execute_callback`, and `ban_relayer`: [2](#0-1) [3](#0-2) 

These callbacks are invoked as the target of a `.then()` continuation with a fixed, hard-coded gas budget for their own logic (`ADDRESS_CHECK_CALLBACK_GAS`, `NEP_141_STORAGE_BALANCE_CALLBACK_GAS`), on top of whatever gas the (attacker/relayer-controlled) Ethereum transaction requests for the downstream action: [4](#0-3) 

Per nearcore's receipt-execution model, a FunctionCall receipt that fails for *any* reason (including running out of gas, i.e. `GasExceeded`) has **all** of its state changes rolled back — it does not partially commit the `has_in_flight_tx = false` line that already executed: [5](#0-4) 

This is also documented as an architectural invariant of the runtime: [6](#0-5) 

Because `address_check_callback`/`nep_141_storage_balance_callback` only reset the flag as their first statement and then go on to do further gas-consuming work (JSON deserialization of attacker-supplied data, `format!` string construction, additional cross-contract promise scheduling) using a small fixed gas overhead, any panic in that remaining logic — most notably exceeding the attached gas — reverts the flag reset along with everything else. Since these methods are `#[private]` (callable only by the contract itself as predecessor, i.e. only reachable via the promise chain the contract itself created) and there is no other method to clear `has_in_flight_tx`, the account becomes permanently unable to process any further Ethereum-style transaction via `rlp_execute`.

This is the structural analog of the ArtGobblers `randProvider` brick: a boolean "waiting" flag that can only be cleared by a specific privileged callback path, with no owner/administrative override, and a channel by which the callback can permanently fail to run to completion.

### Impact Explanation
Once `has_in_flight_tx` becomes permanently stuck `true`, the affected eth-implicit account's `WalletContract` can never again execute a user's signed Ethereum-style transaction — `rlp_execute` unconditionally short-circuits with an error and never even attempts to reach `inner_rlp_execute` or increment the nonce. Since this wallet contract is the only mechanism through which the corresponding ETH-style private key can act on NEAR, this constitutes a permanent freezing of that account's ability to spend or otherwise use its NEAR balance and any tokens routed through it (matching the "permanent freezing of funds" impact bar).

### Likelihood Explanation
Triggering this requires a callback receipt (`address_check_callback` or `nep_141_storage_balance_callback`) to fail after having reset the flag but before completing — e.g. by exhausting the small fixed gas overhead allotted to that callback's own bookkeeping logic when handling attacker/relayer-controlled inputs (arbitrarily large `action` payloads, long account IDs used in `format!`, or an NEP‑141 contract returning a very large `storage_balance_of` response). This is not an everyday occurrence, but it is reachable by an ordinary, unprivileged transaction signer/relayer without needing any special node or validator behavior, which is why the original ArtGobblers report was rated Medium — contingent on an edge condition, but capable of denying a core function of the contract with no recovery path.

### Recommendation
Do not gate irreversibility on a flag that is reset only inside the very receipt that might panic. Instead:
- Reset `has_in_flight_tx` in a step that is guaranteed to run regardless of the callback's own success/failure (e.g., a `.then()` continuation with a large enough hard-coded gas reservation that is *not* shared with attacker-controlled/variable-size work), or
- Bound/validate attacker-controlled inputs (target account id length, args size) before scheduling callbacks so the fixed gas budget is provably sufficient, and/or add an explicit, unprivileged fallback (e.g., a self-only "unstick" callback guaranteed minimal gas, scheduled unconditionally as a final step of every promise chain) so `has_in_flight_tx` cannot remain stuck.

### Proof of Concept
1. Deploy an eth-implicit `WalletContract`.
2. Craft an RLP-encoded ERC20-style transfer transaction whose `action` payload (method name/args) is large, or target an NEP-141 token contract engineered/compromised to return an oversized `storage_balance_of` response.
3. Submit via `rlp_execute`; it schedules `nep_141_storage_balance_callback` with gas `NEP_141_STORAGE_BALANCE_CALLBACK_GAS.saturating_add(action.gas())` (`lib.rs:39-41`, `440-442`).
4. If the deserialization/promise-construction logic inside `nep_141_storage_balance_callback` (`lib.rs:194-273`) consumes more than the fixed `NEP_141_STORAGE_BALANCE_CALLBACK_GAS` overhead before completing, the receipt fails with a gas error.
5. Per the runtime's failed-receipt-atomicity rule (`runtime-execution.md:149`), the `self.has_in_flight_tx = false;` write at line 202 is rolled back along with everything else, leaving `has_in_flight_tx == true` in persisted state.
6. Every subsequent call to `rlp_execute` now returns the "transaction already in progress" error (`lib.rs:97-105`) forever, since no other method can reset the flag.
