### Title
Unwrapped token transfer in `send-underlying` uses the wrong `tx-sender` context, permanently freezing all redemptions/borrows in the sBTC, USDC and USDH vaults - ([File: mainnet/contracts/vault/v0-vault-sbtc.clar], [File: mainnet/contracts/vault/v0-vault-usdc.clar], [File: mainnet/contracts/vault/v0-vault-usdh.clar])

### Summary
The `send-underlying` helper in the sBTC, USDC and USDH vault contracts calls the underlying SIP-010 token's `transfer` with `current-contract` as the `sender` argument, but does **not** wrap the call in `as-contract?`. Because `tx-sender` is not switched to the contract's own principal, `tx-sender` remains the calling end-user, while the declared `sender` argument is the vault contract itself. Per the SIP-010 standard, the token contract must reject any transfer where `sender` != `tx-sender`. This is the same class of bug as the reported issue: the wrong authority/principal is used for a token transfer, so every outbound transfer from the vault fails, freezing user funds.

### Finding Description
`receive-underlying` correctly matches `sender` (the user, `account`) with the actual `tx-sender` when a user deposits, so no wrapping is needed: [1](#0-0) 

However `send-underlying`, used to push the vault's own held tokens *out* to a user, sets `sender` to `current-contract` while never entering an `as-contract?` context, so `tx-sender` at the time of the CPI is still the calling user, not the vault: [2](#0-1) 

The same unwrapped pattern exists in the sBTC and USDH vaults: [3](#0-2) [4](#0-3) 

Contrast this with the STX, stSTX and stSTXbtc vaults, which correctly wrap the outbound transfer in `as-contract?` (which temporarily makes `tx-sender` equal to `current-contract`) and use `tx-sender` as the sender argument inside that context: [5](#0-4) [6](#0-5) 

The SIP-010 standard referenced by this codebase requires the token's `transfer` function to enforce `sender == tx-sender` (error `u4` otherwise): [7](#0-6) 

`send-underlying` is called directly from unprivileged, user-reachable entry points such as `redeem` (share redemption) and from `system-borrow` (borrow payout): [8](#0-7) [9](#0-8) 

Because the outbound `sender` (`current-contract`) never equals the effective `tx-sender` (the calling user) in these three vaults, the underlying token contract should reject the transfer, causing `redeem`/`withdraw`/`borrow` to revert every time they attempt to pay out underlying assets.

### Impact Explanation
This lands squarely in the "permanent freezing of funds" Critical/High impact category: user principal and accrued yield deposited into the sBTC, USDC, and USDH vaults become permanently unredeemable via `redeem`, and borrowers can never receive borrowed principal via `system-borrow`, since the outbound underlying-asset transfer required by both paths always fails authority validation.

### Likelihood Explanation
This triggers deterministically on the very first ordinary user's call to `redeem` (or any code path relying on `send-underlying`, including borrow disbursement) for these three vaults — no special conditions, privileges, or timing are required, making likelihood high assuming the underlying SIP-010 token contracts (`sbtc-token`, `usdcx`, `usdh-token-v1`) enforce the standard `sender == tx-sender` check as documented in this repo's own SIP-010 reference.

### Recommendation
Wrap the outbound transfer in `send-underlying` in `as-contract?` and use `tx-sender` (which becomes the vault's own principal inside that context) as the `sender` argument, mirroring the pattern already used in `v0-vault-stx.clar`, `v0-vault-ststx.clar`, and `v0-vault-ststxbtc.clar`:
```clarity
(define-private (send-underlying (amount uint) (account principal))
  (begin
    (try! (as-contract? ((with-ft UNDERLYING "..." amount))
      (try! (contract-call? 'SM3VDXK3WZZSA84XXFKAFAF15NNZX32CTSG82JFQ4.sbtc-token transfer amount tx-sender account none))
      true))
    (ok true)))
```

### Proof of Concept
1. A user deposits underlying sBTC/USDC/USDH into the respective vault via `deposit` (succeeds because `receive-underlying` correctly uses the user as sender, matching `tx-sender`).
2. The same user (or any user) calls `redeem` to withdraw their share of the underlying asset.
3. Inside `redeem`, `send-underlying` issues `contract-call? <token> transfer amount current-contract recipient none` while `tx-sender` is still the calling user's principal, not the vault's principal, because no `as-contract?` wrapper is used.
4. The token contract's SIP-010 `transfer` implementation checks `sender == tx-sender`, finds `current-contract != tx-sender`, and returns `(err u4)`.
5. The `try!` in `send-underlying` propagates the error, aborting the entire `redeem` transaction — the shares were already burned in a `let`-scoped uncommitted state (no persistent state change occurs since the transaction aborts), but the withdrawal itself never succeeds, permanently freezing funds in these vaults. The identical failure occurs for `system-borrow` payouts.

```markdown
Contract implementers should take note to perform authorization of the `transfer` method. For example, a fungible token contract that wants to make sure that only the transaction's sender is able to move the requested tokens might first check that the sender argument is equal to tx-sender.

When returning an error in this function, the error codes should follow the same patterns as the built-in `ft-transfer?` and `stx-transfer?` functions.

| error code | reason                                          |
| ---------- | ----------------------------------------------- |
| u1         | `sender` does not have enough balance           |
| u2         | `sender` and `recipient` are the same principal |
| u3         | `amount` is non-positive                        |
| u4         | `sender` is not the same as `tx-sender`         |
```
