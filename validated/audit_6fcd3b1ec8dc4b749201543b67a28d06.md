I found a critical pattern. The `vesting.move` `set_beneficiary` function explicitly guards against this with `assert_account_is_registered_for_apt(new_beneficiary)`, but `staking_contract.move`'s `set_beneficiary_for_operator` has no such guard, creating the exact analog of the original bug.

---

### Title
Operator can permanently block staker's `unlock_stake` and `switch_operator` by setting a non-APT-receivable beneficiary address — (`staking_contract.move`)

### Summary

`staking_contract::distribute_internal` loops over all distribution-pool shareholders and calls `aptos_account::deposit_coins<AptosCoin>` for each, including the operator's commission redirected to `beneficiary_for_operator(operator)`. The `set_beneficiary_for_operator` entry function accepts any address as the new beneficiary without validating that it can receive APT. An operator can set their beneficiary to an address that has `allow_arbitrary_coin_transfers = false` and no `CoinStore<AptosCoin>`, causing `deposit_coins` to abort with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS`. Because `distribute_internal` is called unconditionally inside `unlock_stake` and `switch_operator`, the staker is permanently unable to unlock their staked APT or change operators until the malicious operator voluntarily corrects the beneficiary.

### Finding Description

**Root cause — missing beneficiary validation in `set_beneficiary_for_operator`:**

`staking_contract::set_beneficiary_for_operator` accepts any address without checking whether it can receive APT: [1](#0-0) 

Compare this with `vesting::set_beneficiary`, which explicitly guards against exactly this scenario: [2](#0-1) 

The comment in `vesting.move` reads: *"Verify that the beneficiary account is set up to receive APT. This is a requirement so distribute() wouldn't fail and block all other accounts from receiving APT if one beneficiary is not registered."* The identical guard is absent from `staking_contract.move`.

**Failure path — `distribute_internal` aborts on commission deposit:**

Inside `distribute_internal`, when the current recipient is the operator, the commission is redirected to the operator's beneficiary and then deposited: [3](#0-2) 

`aptos_account::deposit_coins<AptosCoin>` aborts when the target account exists, has no `CoinStore<AptosCoin>` (e.g., only the APT primary fungible store created by `register_apt`), and has `allow_arbitrary_coin_transfers = false`: [4](#0-3) 

`can_receive_direct_coin_transfers` returns `false` when the account has explicitly set `allow_arbitrary_coin_transfers = false`: [5](#0-4) 

**Blocked entry points:**

`distribute_internal` is called unconditionally at the start of both `unlock_stake` and `switch_operator`: [6](#0-5) [7](#0-6) 

If `distribute_internal` aborts, neither `unlock_stake` nor `switch_operator` can proceed. The staker's APT remains locked in the stake pool with no recourse.

### Impact Explanation

The staker's APT staking balance is effectively frozen. They cannot:
- Call `unlock_stake` to begin the unbonding process.
- Call `switch_operator` or `switch_operator_with_same_commission` to escape the malicious operator.
- Call the public `distribute` entry, which also invokes `distribute_internal` and will abort identically.

The only recovery path is the operator voluntarily changing their beneficiary back to a valid address — a condition entirely under the attacker's control. This constitutes a permanent freezing of staking balances, which is within the Aptos bounty's allowed impact scope.

### Likelihood Explanation

The operator is a distinct, semi-trusted party from the staker. The `operator_beneficiary_change_enabled` feature flag is a production feature. Setting a bad beneficiary requires only two cheap transactions (create/configure the blocking address, then call `set_beneficiary_for_operator`). Any operator who wishes to hold a staker's funds hostage — e.g., to extract a ransom or prevent a competitor from switching — can execute this with no special privileges beyond being the registered operator.

### Recommendation

Add the same guard that `vesting::set_beneficiary` uses:

```move
public entry fun set_beneficiary_for_operator(
    operator: &signer, new_beneficiary: address
) acquires BeneficiaryForOperator {
    assert!(
        features::operator_beneficiary_change_enabled(),
        std::error::invalid_state(EOPERATOR_BENEFICIARY_CHANGE_NOT_SUPPORTED)
    );
+   // Ensure the beneficiary can receive APT so distribute_internal cannot be blocked.
+   aptos_account::assert_account_is_registered_for_apt(new_beneficiary);
    ...
}
```

Alternatively, separate the commission payment from the distribution loop so that a failed commission deposit does not prevent the staker's own funds from being unlocked.

### Proof of Concept

1. **Attacker setup** — Operator creates (or reuses) an address `bad_addr` that was initialized via `aptos_account::create_account` (giving it only the APT primary fungible store, not `CoinStore<AptosCoin>`). `bad_addr` calls `set_allow_direct_coin_transfers(false)`.

2. **Poison the beneficiary** — Operator calls:
   ```
   set_beneficiary_for_operator(operator_signer, bad_addr)
   ```
   No validation occurs; `BeneficiaryForOperator` is updated to `bad_addr`. [8](#0-7) 

3. **Commission accrues** — After one or more epochs, the operator calls `request_commission`, moving commission into the `pending_inactive` bucket. After the lockup expires, the commission becomes `inactive`.

4. **Staker attempts to unlock** — Staker calls `unlock_stake(staker_signer, operator_addr, amount)`.
   - `distribute_internal` is called.
   - `stake::withdraw_with_cap` returns the inactive commission coins (`distribution_amount > 0`).
   - The loop reaches the operator recipient, redirects to `bad_addr`.
   - `aptos_account::deposit_coins<AptosCoin>(bad_addr, commission_coins)` is called.
   - `coin::is_account_registered<AptosCoin>(bad_addr)` → `false` (no CoinStore).
   - `can_receive_direct_coin_transfers(bad_addr)` → `false`.
   - **Aborts** with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS`.
   - The entire `unlock_stake` transaction is reverted. [9](#0-8) 

5. **Staker attempts to switch operators** — Same abort occurs inside `switch_operator` → `distribute_internal`. [10](#0-9) 

6. **Result** — The staker's APT is permanently locked until the operator cooperates.

    public entry fun set_beneficiary_for_operator(
        operator: &signer, new_beneficiary: address
    ) acquires BeneficiaryForOperator {
        assert!(
            features::operator_beneficiary_change_enabled(),
            std::error::invalid_state(EOPERATOR_BENEFICIARY_CHANGE_NOT_SUPPORTED)
        );
        // The beneficiay address of an operator is stored under the operator's address.
        // So, the operator does not need to be validated with respect to a staking pool.
        let operator_addr = signer::address_of(operator);
        let old_beneficiary = beneficiary_for_operator(operator_addr);
        if (exists<BeneficiaryForOperator>(operator_addr)) {
            borrow_global_mut<BeneficiaryForOperator>(operator_addr).beneficiary_for_operator =
                new_beneficiary;

            move_to(
                operator,
                BeneficiaryForOperator { beneficiary_for_operator: new_beneficiary }
            );
        };

        emit(
            SetBeneficiaryForOperator {
                operator: operator_addr,
                old_beneficiary,
                new_beneficiary
            }
        );
    }
