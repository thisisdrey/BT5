### Title
Unvalidated withdrawal-address memo causes irrecoverable token burn - ([File: contracts/poa/token/src/contract.rs])

### Summary
The POA-wrapped fungible token contract burns tokens whenever `ft_transfer` is called with a memo prefixed by `WITHDRAW_TO:`, without validating that the destination-chain address encoded after the prefix is well-formed for the external chain it represents. This mirrors the SUI-receiver bug class: a value-changing action (burn/withdraw) is executed based on an address string that is only stored/emitted, never validated, and the debit is irreversible because the tokens are destroyed on-chain before any off-chain relayer attempts delivery.

### Finding Description
`Contract::ft_transfer` in [1](#0-0)  special-cases transfers to the token contract itself with a memo starting with `WITHDRAW_MEMO_PREFIX` ("WITHDRAW_TO:") and routes them into `ft_withdraw`: [2](#0-1) 

`ft_withdraw` only checks `amount.0 > 0`, then unconditionally calls `self.token.internal_withdraw(account_id, amount.into())` and emits `FtBurn` with the raw `memo` (containing the destination address string) — it never parses or validates the address portion of the memo against the format expected by the external chain (length, charset, checksum, etc.), exactly analogous to `"0x" + hex.EncodeToString(b)` in the Zetachain report being encoded without validating length/format.

This path is directly reachable from the Defuse intents engine: `FtWithdraw.memo` is a free-form `Option<String>` [3](#0-2)  that is passed straight through to `ft_transfer` in `do_ft_withdraw`: [4](#0-3) .

The binding broken is **value debited versus value delivered plus refunded**: `internal_withdraw` unconditionally destroys the user's balance the moment the memo prefix matches, with no on-chain verification that the encoded destination is a deliverable address on the target chain and no mechanism to cancel/refund if the off-chain bridge relayer cannot parse or deliver to that address (unlike the Zetachain fix, which added receiver validation *before* burning/locking and would cancel/refund on failure).

### Impact Explanation
Because the burn (`internal_withdraw`) happens synchronously and irreversibly inside the same call that only checks `amount.0 > 0`, any malformed or unroutable address string placed after `WITHDRAW_TO:` results in permanent, un-refundable loss of the withdrawn tokens for the user — the off-chain bridge component has no on-chain record to trigger a refund since the balance is already destroyed and no error was ever raised on-chain. This is a stronger outcome than the referenced report (which caused stuck withdrawals): here, funds are unconditionally destroyed rather than reversibly stuck, i.e. tokens are withdrawn/burned without a valid, deliverable destination — a critical value-loss condition.

### Likelihood Explanation
Any unprivileged holder of the POA token (or any signer of a `FtWithdraw` intent through Defuse) can trigger this by supplying an arbitrary string after `WITHDRAW_TO:` — no special privileges, roles, or race conditions are required. Malformed input can occur both from attacker intent and from ordinary client bugs, but from a security standpoint it means the contract accepts and destroys value against a completely unvalidated custody target.

### Recommendation
Validate the destination address format for the specific external chain (length, encoding, checksum where applicable) before calling `internal_withdraw`/emitting `FtBurn` in `ft_withdraw` (`contracts/poa/token/src/contract.rs`). If validation cannot be done fully on-chain (e.g., chain-specific rules), consider a two-phase design (lock-then-confirm, as Zetachain's fix did) so that a malformed-address withdrawal can be cancelled and refunded instead of immediately and irreversibly burning the tokens.

### Proof of Concept
1. User (or an intent signer) holds POA-wrapped tokens tracking an external chain (e.g. BTC/SUI) balance in the `contracts/poa/token` contract.
2. User calls `ft_transfer` (directly, or indirectly via `FtWithdraw` intent through `defuse`) with `receiver_id = <poa-token-contract>` and `memo = "WITHDRAW_TO:<malformed-or-oversized-address>"`.
3. `Contract::ft_transfer` detects the prefix and calls `ft_withdraw`, which passes the `amount.0 > 0` check and unconditionally calls `internal_withdraw`, burning the tokens and emitting `FtBurn` with the malformed address in `memo`.
4. The off-chain bridge/relayer that watches `FtBurn` events cannot construct a valid withdrawal transaction on the destination chain from the malformed address (analogous to the SUI `buildWithdrawTx` failure in the referenced report).
5. The user's tokens are already destroyed on NEAR with no on-chain trace to trigger any refund — permanent loss of funds.

impl FungibleTokenCore for Contract {
    #[payable]
    fn ft_transfer(&mut self, receiver_id: AccountId, amount: U128, memo: Option<String>) {
        // A special case we created to handle withdrawals:
        // If the receiver id is the token contract id, we burn these tokens by calling ft_withdraw,
        // which will reduce the balance and emit an FtBurn event.
        if receiver_id == env::current_account_id()
            && memo
                .as_deref()
                .is_some_and(|memo| memo.starts_with(WITHDRAW_MEMO_PREFIX))
        {
            self.ft_withdraw(&env::predecessor_account_id(), amount, memo.as_deref());
        } else {
            self.token.ft_transfer(receiver_id, amount, memo);
        }
    }

impl Contract {
    fn ft_withdraw(&mut self, account_id: &AccountId, amount: U128, memo: Option<&str>) {
        assert_one_yocto();
        require!(amount.0 > 0, "zero amount");
        self.token.internal_withdraw(account_id, amount.into());
        FtBurn {
            owner_id: account_id,
            amount,
            memo,
        }
        .emit();
    }
}
