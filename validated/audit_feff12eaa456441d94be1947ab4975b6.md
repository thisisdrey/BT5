### Title
Unprivileged dust-deposit griefing fills a victim's `MAX_TOKENS_PER_USER` slot list and blocks new collateral deposits and new debt positions - (File: contracts/Pool.sol)

### Summary
`Pool` enforces a hard cap of `MAX_TOKENS_PER_USER = 30` on the combined size of `debtTokensOfAccount` and `depositTokensOfAccount` via `onlyIfAdditionWillNotReachMaxTokens`. Entries are added to `depositTokensOfAccount` whenever an account's balance of a `DepositToken` goes from 0 to non-zero — and this happens not only on `transfer`/`transferFrom`, but also inside `deposit(uint256 amount_, address onBehalfOf_)`, where the minted `msdTOKEN` is credited to an attacker-chosen `onBehalfOf_`. An unprivileged EOA can therefore deposit 1 wei of every registered collateral `onBehalfOf_ = victim`, filling the victim's account list with tokens they never wanted. Once the victim's combined list reaches 30, every subsequent `deposit`/`transfer`/`issue` involving a token not already in the victim's list reverts with `UserReachedMaxTokens`, blocking the victim from onboarding new collateral types or opening new debt positions. ### Finding Description
- `Pool.MAX_TOKENS_PER_USER = 30` (contracts/Pool.sol:79). The modifier `onlyIfAdditionWillNotReachMaxTokens` reverts when `debtTokensOfAccount.length(account) + depositTokensOfAccount.length(account) >= 30` (contracts/Pool.sol:143-148).
- `DepositToken._mint` adds the token to the recipient's list whenever `_balanceBefore == 0 && amount_ > 0` (contracts/DepositToken.sol:486-488). `deposit()` calls `_mint(onBehalfOf_, _deposited)` with a fully attacker-controlled `onBehalfOf_` and no consent check (contracts/DepositToken.sol:211-234).
- `DepositToken._transfer` does the same for `transfer`/`transferFrom` recipients (contracts/DepositToken.sol:518-520), so both donation-style deposit and direct dust transfer work.
- The analogous hook on the debt side (`DebtToken._mint` → `pool.addToDebtTokensOfAccount`, contracts/DebtToken.sol:598-600) only affects the caller's own list since `issue` mints debt to `_msgSender` (contracts/DebtToken.sol:262), so the deposit-token side is the griefing surface.
- Removal exists (`removeFromDepositTokensOfAccount` on burn/zero-balance transfer, contracts/DepositToken.sol:460-462, 523-525), so the victim can evict entries by withdrawing or transferring out the dust — but each eviction consumes victim gas and reverts their pending transactions in the meantime.

### Impact Explanation
Temporary freezing of funds / liveness violation. A victim whose list is saturated cannot:
- `deposit()` into any `DepositToken` they don't already hold (the `_mint` → `addToDepositTokensOfAccount` path reverts `UserReachedMaxTokens`), including deposits made on their behalf by integrations or `SmartFarmingManager` zaps.
- `issue()` a new synthetic asset (debt mint triggers `addToDebtTokensOfAccount`, reverting once the cap is hit).
- Receive `msdTOKEN` transfers of any new deposit token (`_transfer` → `addToDepositTokensOfAccount` reverts), which can also cause third-party flows (liquidation `seize` pays the liquidator via `_transfer`, so a saturated liquidator sees `liquidate` revert — minor secondary griefing).

The DoS is reversible only by the victim actively cleaning entries (withdraw/transfer dust), imposing gas cost and failed transactions until cleanup — matching the "temporary freezing of funds" impact class of the DDoS bug family.

### Likelihood Explanation
Likelihood is bounded by the pool configuration: the attacker can only occupy as many slots as there are registered `DepositToken`s in the pool, and the cap is shared with the victim's existing positions and debt tokens. The attack fully locks a victim when `(registered deposit tokens) + (victim's existing debt/deposit entries) >= 30`. On pools with fewer registered deposit tokens, the attack consumes only part of the allowance and reduces — but does not eliminate — the victim's headroom. Cost to the attacker is dust-sized deposits plus any deposit fee per token, making it cheap where feasible. No privileged role, oracle manipulation, or timing assumption is required; `deposit` is permissionless and `whenNotPaused`.

### Recommendation
- Do not auto-register tokens on behalf of an account the caller does not control. Add a per-account opt-in (e.g., `enableDepositToken(token)` set by the account itself) or track list membership in a way that ignores balances below a meaningful threshold.
- Alternatively, count only entries the account explicitly activated, or replace the `MappedEnumerableSet` revert with graceful handling that does not block mints (e.g., allow the balance but exclude unregistered dust tokens from `depositOf`/health computation until opted in).
- At minimum, skip `addToDepositTokensOfAccount` when the minted amount is below a dust threshold, and/or allow anyone to remove dust entries for other accounts when the balance is below that threshold.

### Proof of Concept
Hardhat-style test (adapt to the deployed pool's registered deposit tokens; on a fork, iterate `pool.depositTokens()`):

```solidity
// test/grief/MaxTokensGrief.test.ts (pseudocode, follows existing Pool.test.ts patterns)
it('fills victim token list via dust deposits onBehalfOf', async () => {
  // given: pool with D registered deposit tokens; victim has K existing entries
  // attacker deposits 1 wei of each collateral to victim
  for (const dt of depositTokens) {
    const underlying = await ethers.getContractAt('IERC20', await dt.underlying());
    await underlying.approve(dt.address, 1);
    await dt.deposit(1, victim.address); // mints msdTOKEN to victim, adds entry
  }

  // when victim (or anyone) tries to deposit a deposit token the victim doesn't hold
  const tx = newDepositToken.deposit(amount, victim.address);

  // then once list reaches MAX_TOKENS_PER_USER it reverts
  await expect(tx).revertedWithCustomError(pool, 'UserReachedMaxTokens');

  // and victim cannot issue a new synthetic debt token either
  const tx2 = newDebtToken.connect(victim).issue(amount, victim.address);
  await expect(tx2).revertedWithCustomError(pool, 'UserReachedMaxTokens');
});
```

Note: the Hardhat suite already exercises the cap mechanics (`should revert when reach max tokens`, test/Pool.test.ts:1386-1416); the PoC differs only in that entries are added non-consensually via `deposit(_, onBehalfOf_ = victim)` and dust `transfer`s. A fork PoC requires the deployed pool to have enough registered deposit tokens that `registeredTokens + victimExistingEntries >= 30` — if the live pool has fewer, the attack degrades to consuming the victim's remaining headroom rather than a full lock.
