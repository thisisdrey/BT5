### Title
Lazy, attacker-timed `oldTronPower` snapshot lets a delegatee permanently lock in inflated legacy voting power - (File: chainbase/src/main/java/org/tron/core/capsule/AccountCapsule.java)

### Summary
Similar to the `importScore` issue (a permissionless, one-time, asynchronous import of a value that can be triggered at attacker-chosen timing to "freeze" a favorable historical value forever), java-tron's resource-model migration uses a permissionless, one-time, lazily-triggered snapshot of legacy TRON Power (`oldTronPower`) that is taken at whatever moment an account happens to call any freeze/unfreeze/vote transaction after the "new resource model" activates. Because the account itself chooses exactly when that first transaction fires, it can arrange to have an inflated (but transient) old-style delegated frozen balance in place at that moment, lock it in as a permanent voting-power floor, and then let the inflating condition disappear without the snapshot ever being corrected.

### Finding Description
`AccountCapsule.getTronPower()` sums up all legacy (v1) frozen-for-bandwidth/energy balances, including balances *delegated to the account by others* (`getDelegatedFrozenBalanceForBandwidth()`, `getDelegatedFrozenBalanceForEnergy()`): [1](#0-0) 

`oldTronPowerIsNotInitialized()`/`initializeOldTronPower()` implement a one-time, permissionless "import" of this value into a persistent `oldTronPower` field, guarded only by a `== 0` check, exactly analogous to `m_v3_scoreImported` in the referenced report: [2](#0-1) 

This snapshot is taken lazily on the *first* call to any of `FreezeBalanceActuator`, `FreezeBalanceV2Actuator`, `VoteWitnessActuator`, `UnfreezeBalanceActuator`, or `UnfreezeBalanceV2Actuator` after the network enables `AllowNewResourceModel`, e.g.: [3](#0-2) 

Once set, `getAllTronPower()` uses that frozen snapshot (plus current v1/v2 TRON_POWER-type frozen amounts) as the account's voting power, instead of recomputing legacy power live: [4](#0-3) 

The snapshot is only cleared (`invalidateOldTronPower()`, set to `-1`) when the account itself performs an `UnfreezeBalance`/`UnfreezeBalanceV2` action: [5](#0-4) 

Crucially, `getTronPower()` (and thus the snapshot) includes balances *delegated to the account by a third party* via the legacy `FreezeBalanceContract` receiver mechanism. Delegation and revocation of that delegated stake are actions taken on the *delegator's* account (`UnfreezeBalanceActuator`, receiver-address branch), not the delegatee's, so revoking a delegation never touches the delegatee's `oldTronPower` field or its initialization state: [6](#0-5) 

As a result, an account can:
1. Receive a large legacy delegated freeze from a colluding/temporary counterparty (inflating `getTronPower()`).
2. While that inflated delegation is in place, fire any of the freeze/unfreeze/vote actuators for the first time after migration, causing `initializeOldTronPower()` to permanently snapshot the inflated value into `oldTronPower`.
3. Have the counterparty revoke the delegation (which does not touch the delegatee's `oldTronPower`), so the account's real stake drops back down while its `oldTronPower`-derived voting power remains inflated indefinitely (it is never re-derived from live state, only wiped to `-1` by the account's own future `UnfreezeBalance`/`UnfreezeBalanceV2` call, which it can simply avoid).

### Impact Explanation
`getAllTronPower()` is the value used to gate and weight governance actions: `VoteWitnessActuator`/`Wallet`/`RpcApiService.checkVoteWitnessAccount` validate that vote counts do not exceed `getAllTronPower()`, and the `TotalVoteCount` precompiled contract exposes it to on-chain contracts: [7](#0-6) [8](#0-7) 

An account can therefore permanently cast more Super Representative votes than it actually has real stake backing, distorting SR elections/witness selection without holding the corresponding frozen TRX — an unbacked-power condition directly comparable to the reputation-reset issue in the original report, but affecting on-chain governance weight instead of a worker reputation score.

### Likelihood Explanation
This requires two colluding accounts (or self-controlled accounts) and only legacy (v1) freeze/delegate/unfreeze contracts, all of which remain enabled and reachable by any ordinary signed transaction; no privileged role is needed. The attacker fully controls the timing of the one-time snapshot trigger, making the attack reliably reproducible.

### Recommendation
Do not persist a stale legacy snapshot that can be inflated by third-party delegation timing. Either (a) always derive `oldTronPower` live from `getTronPower()` excluding delegated-in balances, (b) recompute/invalidate the snapshot whenever delegated balances backing it change (i.e., have the delegator's unfreeze also invalidate the delegatee's snapshot), or (c) require the snapshot import to occur atomically/synchronously at the exact migration block for all accounts rather than lazily on an attacker-chosen future transaction.

### Proof of Concept
1. Before/soon-after `AllowNewResourceModel` activation, account B (colluding delegator) calls `FreezeBalanceContract` with `receiverAddress = A`, delegating a large legacy BANDWIDTH/ENERGY freeze to A. This raises `A.getDelegatedFrozenBalanceForBandwidth()`/energy, inflating `A.getTronPower()`.
2. Account A calls any first post-migration action (e.g., `FreezeBalanceV2Contract` freezing 1 TRX) — `oldTronPowerIsNotInitialized()` is true, so `initializeOldTronPower()` snapshots A's currently inflated `getTronPower()` into `A.oldTronPower` (see `FreezeBalanceV2Actuator.java:52-55`).
3. Account B calls `UnfreezeBalanceContract` with `receiverAddress = A` to revoke the delegation. This only updates B's and the `DelegatedResourceStore`/`DelegatedResourceAccountIndexStore` state (`UnfreezeBalanceActuator.java:86-94`); A's `oldTronPower` is untouched.
4. A's `getAllTronPower()` still returns the inflated snapshot plus any TP-frozen amount (`AccountCapsule.java:637-646`), letting A submit `VoteWitnessContract` votes exceeding its real current stake, validated only against the stale `getAllTronPower()` value (`RpcApiService.java:1142-1148`).

    return this.account.getOldTronPower() == 0;

  public boolean oldTronPowerIsInvalid() {

  public void initializeOldTronPower() {
    long value = getTronPower();
    if (value == 0) {
      value = -1;
    }
    setInstance(getInstance().toBuilder()
        .setOldTronPower(value)
        .build());
  }
