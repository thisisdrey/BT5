### Title
Trust-based Quarantine Bypass Allows Cross-Repository Path Rewrite - (File: internal/gitaly/storage/storagemgr/middleware.go)

### Summary
Similar to the ERC20 authorization overlap in the external report — where two independent authorization mechanisms were expected to be mutually exclusive but neither enforced that boundary, letting a caller pick the weaker path — Gitaly's gRPC transaction middleware has two independent request-handling paths for repository-scoped RPCs that are only *assumed* to be mutually exclusive by convention, not enforced. An ordinary client that supplies a normally Rails-internal-only combination of request fields can steer any Accessor RPC into the untrusted "quarantine loopback" path, which skips the validation the normal path performs.

### Finding Description
`beginTransactionForRepository` branches into two mutually-assumed-exclusive paths based solely on whether the client-supplied `Repository.GitObjectDirectory`/`GitAlternateObjectDirectories` fields are set: [1](#0-0) 

The comment makes the intended trust boundary explicit — it assumes these fields are only ever set by Rails' `/internal/allowed` access-check loopback calls, and that this property is only violated by tests: [2](#0-1) 

However, `GitObjectDirectory`/`GitAlternateObjectDirectories` are ordinary fields on the `Repository` message that any authenticated Gitaly client can populate on any request — there is no cryptographic or structural mechanism distinguishing a genuine Rails loopback call from an ordinary client request that happens to set these fields. When they are non-empty and the RPC is an Accessor (mutators are rejected via `ErrQuarantineConfiguredOnMutator`), the request is routed to `restoreSnapshotRelativePath`: [3](#0-2) 

This function blindly overwrites `targetRepo.RelativePath` with whatever value the attacker supplies in the `relative-path-bin` gRPC metadata header, and returns the result as a `nonTransactionalRequest` — entirely skipping `locator.ValidateRepository`, which is the check performed on the normal path just a few lines later: [4](#0-3) 

This is the direct analog of the reported bug class: two independent "authorizers" (the transactional/validated path vs. the quarantine-loopback/unvalidated path) exist for the same RPC surface, selection between them is based on attacker-controllable request fields, and one of the two paths omits validation logic that the other enforces — exactly the "overlap that can lead to an inconsistent state" pattern described in the report.

### Impact Explanation
By setting the quarantine object-directory fields plus a crafted `relative-path-bin` metadata value, a client can cause an Accessor RPC (e.g., any repository read RPC) to operate on an arbitrary relative path within the storage shard, without the repository-path/existence validation (`locator.ValidateRepository`) that is normally mandatory. This enables cross-repository object access — reading data from a repository the caller was not authorized to target — bypassing the storage-path resolution safeguards that gate ordinary repository access.

### Likelihood Explanation
The precondition is only crafting two request-visible values: (1) non-empty `GitObjectDirectory`/`GitAlternateObjectDirectories` on the target `Repository` in an Accessor RPC, and (2) an arbitrary `relative-path-bin` gRPC metadata header. Neither requires elevated privilege beyond the standard Gitaly auth token used for normal RPC calls; the check that gates this branch relies purely on message-field presence, not on caller identity/provenance. This makes the bypass reachable from any ordinary authenticated Gitaly client issuing a crafted RPC.

### Recommendation
Do not use client-suppliable fields (`GitObjectDirectory`/`GitAlternateObjectDirectories`) as an implicit authorization signal for skipping repository-path validation. Enforce that the quarantine-loopback path is only reachable in contexts that are otherwise provably an access-check callback (e.g., via a signed/verified transaction/quarantine token established by the RPC that originated the quarantine, rather than by re-inspecting mutable request fields), and always route the rewritten relative path from `restoreSnapshotRelativePath` through the same `locator.ValidateRepository` validation used by the normal transactional path.

### Proof of Concept
1. Obtain a valid Gitaly auth token (the one used for any ordinary client, e.g., a token available to Workhorse/gitlab-shell or any direct client of Gitaly's gRPC API).
2. Issue a repository-scoped Accessor RPC (e.g., `CommitService/FindCommit`) targeting `Repository{StorageName: "default", RelativePath: "<attacker's own repo>", GitObjectDirectory: "objects", GitAlternateObjectDirectories: []string{"objects"}}` — non-empty dummy values suffice.
3. Attach the gRPC metadata header `relative-path-bin` set to the relative path of a repository the attacker does not own (e.g., `@hashed/other-repo.git`).
4. Because `GetGitObjectDirectory() != ""`, `beginTransactionForRepository` routes into `restoreSnapshotRelativePath`, which sets `targetRepo.RelativePath` to the attacker-supplied header value and returns a non-transactional request — `locator.ValidateRepository` is never invoked.
5. The RPC handler executes against the victim repository path, returning data the attacker was not authorized to access.

func restoreSnapshotRelativePath(ctx context.Context, methodInfo protoregistry.MethodInfo, req proto.Message) (proto.Message, error) {
	// Rails sends RPCs from its access checks with quarantine applied. The quarantine paths are relative to the
	// snapshot repository of the original transaction. While the relative path of the request is the original relative
	// path of the repository before snapshotting, Rails sends the snapshot repository's path in a header. For the
	// quarantine paths to apply correctly, we must thus rewrite the request to point to the snapshot repository here.
	snapshotRelativePath := metadata.GetValue(ctx, MetadataKeySnapshotRelativePath)
	if snapshotRelativePath == "" {
		return nil, ErrQuarantineWithoutSnapshotRelativePath
	}

	rewrittenReq, targetRepo, err := rewritableRequest(methodInfo, req)
	if err != nil {
		return nil, fmt.Errorf("rewritable request: %w", err)
	}

	targetRepo.RelativePath = snapshotRelativePath

	return rewrittenReq, nil
}
