### Title
Incorrect lock-expiry boundary locks airdrop claims at the exact unlock timestamp - (File: `contracts/MetAirdrop.sol`)

### Summary
`MetAirdrop._transferReward()` treats `updatedAt + lockPeriod == block.timestamp` as still locked because it transfers unlocked MET only when `_end < block.timestamp`. As a result, a valid claimant calling `claim()` at the exact configured unlock timestamp has the claimed MET deposited into `esMET` for `MINIMUM_LOCK_PERIOD + 1` instead of receiving a direct MET transfer. [1](#0-0) [2](#0-1) 

### Finding Description
`RecurringAirdrop.claim()` is a public, unprivileged entry point that verifies a Merkle leaf for `(msg.sender, amount_)` and invokes `_transferReward(msg.sender, _claimable)`. [2](#0-1) 

`MetAirdrop` defines the end of the locking window as `updatedAt + lockPeriod`, where `updatedAt` is set to the timestamp of the latest Merkle-root update. [3](#0-2) [4](#0-3) 

At `_end == block.timestamp`, `_end < block.timestamp` is false, so execution falls through to the esMET-locking path and computes `_remainLockPeriod` as `MINIMUM_LOCK_PERIOD + 1`. The function then approves esMET and calls `ESMET.lockFor(to_, amount_, _remainLockPeriod)`, locking the claimed amount. [5](#0-4) [6](#0-5) 

The boundary is inverted relative to normal expiry semantics: once `lockPeriod` seconds have elapsed, the reward should be transferable directly. The test suite only exercises the case one day after the boundary and therefore misses the exact-boundary behavior. [7](#0-6) 

### Impact Explanation
A claimant with a valid Merkle allocation who calls `claim()` when `block.timestamp == updatedAt + lockPeriod` does not receive transferable MET. Instead, the MET is moved into `esMET` and locked for `MINIMUM_LOCK_PERIOD + 1`, causing temporary freezing of the user’s unclaimed airdrop proceeds. [1](#0-0) 

This affects the production `MetAirdrop` deployment listed at `0x265714B10B9309a8A7A505DBFA6Cb6c39b842309`. [8](#0-7) 

### Likelihood Explanation
The issue requires a claimant transaction to execute at the exact block timestamp equal to `updatedAt + lockPeriod`. That is a narrow one-second boundary, but it is externally reachable: `updatedAt` and `lockPeriod` are public values, the claimant can monitor them, and `claim()` is callable directly by the allocated `msg.sender`. No privileged action is needed for the affected claim itself. [9](#0-8) [2](#0-1) 

### Recommendation
Treat the configured end timestamp as expired when `block.timestamp` reaches it:

```solidity
// contracts/MetAirdrop.sol
if (_end <= block.timestamp) {
    MET.safeTransfer(to_, amount_);
    return;
}
```

Alternatively, if the intended invariant is that the reward remains locked for the entire `[updatedAt, _end]` interval and unlocks only strictly afterward, document that explicitly and add a boundary test asserting the current behavior. The existing after-lock test should also be extended to cover `_end`, `_end - 1`, and `_end + 1`. [1](#0-0) [7](#0-6) 

### Proof of Concept
The following Hardhat fork test can be added inside the existing `describe('claim')` block in `test/MetAirdrop.test.ts`. It demonstrates that a valid claim at the exact expiry timestamp is locked in esMET rather than transferred as MET:

```typescript
it('locks MET instead of transferring it at the exact lock expiry', async function () {
  // Arrange the exact boundary timestamp.
  const boundary = (await airdrop.updatedAt()).add(await airdrop.lockPeriod())
  await time.increaseTo(boundary)

  const amount = rewards0[alice.address]
  const leaf = generateLeaf(alice.address, amount)
  const proof = merkleTree0.getHexProof(leaf)
  const positionId = await esMET721.nextTokenId()

  // The public claim succeeds, but routes through the esMET lock path.
  const tx = await airdrop.connect(alice).claim(amount, proof)
  const receipt = await tx.wait()
  const block = await ethers.provider.getBlock(receipt.blockNumber)

  // Alice did not receive liquid MET.
  expect(await met.balanceOf(alice.address)).eq(0)

  // Her MET was locked in a new esMET position.
  const position = await esMET.positions(positionId)
  const minimumLock = await esMET.MINIMUM_LOCK_PERIOD()
  expect(position.lockedAmount).eq(amount)
  expect(position.unlockTime).eq(
    BigNumber.from(block.timestamp).add(minimumLock).add(1)
  )
})
```

The key assertion is `position.lockedAmount == amount` together with `met.balanceOf(alice) == 0`; under correct expiry semantics, the claim at `updatedAt + lockPeriod` should perform `MET.safeTransfer()` and not create the esMET lock. [1](#0-0) [10](#0-9)

```text
    /// @notice For how long `MET` tokens will be locked
    uint256 public lockPeriod = 7 days;

    constructor() RecurringAirdrop(MET) {}

    /**
     * @inheritdoc RecurringAirdrop
     * @dev Locks the `MET` into `esMET` on user's behalf.
     * The `lockPeriod` starts from the current merkle root update (i.e. `updatedAt`)
     */
    function _transferReward(address to_, uint256 amount_) internal override {
        uint256 _end = updatedAt + lockPeriod;

        if (_end < block.timestamp) {
            MET.safeTransfer(to_, amount_);
            return;
        }

        uint256 _min = ESMET.MINIMUM_LOCK_PERIOD() + 1;
        uint256 _max = ESMET.MAXIMUM_LOCK_PERIOD();

        // Ensures valid lock period
        uint256 _remainLockPeriod = Math.min(Math.max(_end - block.timestamp, _min), _max);

        token.safeApprove(address(ESMET), 0);
        token.safeApprove(address(ESMET), amount_);
        ESMET.lockFor(to_, amount_, _remainLockPeriod);
```
