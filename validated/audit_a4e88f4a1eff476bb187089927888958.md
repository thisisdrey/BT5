### Title
`socialize-debt` writes down the liquidity index using a stale, unaccrued `total-assets` value, causing depositors to absorb more loss than warranted - (File: `mainnet/contracts/vault/v0-vault-stx.clar` and mirrored vault contracts)

### Summary
The reported Compound V2 bug uses `exchangeRateStored()` (a lagging, pre-accrual exchange rate) instead of `exchangeRateCurrent()` when converting shares to assets, understating the true redeemable value. The Zest vault contracts have the exact same class of bug: `socialize-debt` computes `old-total-assets` via `total-assets()`, which reads the **stored** `index` var instead of the freshly-accrued `next-index()` used everywhere else (deposit/redeem call `accrue` first; `socialize-debt` does not). This stale value is fed directly into the liquidity-index (`lindex`) write-down formula that determines how much value all zToken holders lose during a bad-debt event.

### Finding Description
In `v0-vault-stx.clar` (and identically in `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`, `v0-vault-ststxbtc.clar`): [1](#0-0) 

`total-debt` uses the *stored* `index` var (`(var-get index)`), while `debt-preview`/`total-assets-preview` use the *freshly computed* `next-index()`, which accounts for interest accrued since `last-update`: [2](#0-1) 

Every state-mutating vault entry point that changes share pricing (`deposit`, `redeem`, `accrue`, `system-borrow`, `system-repay`) calls `(try! (accrue))` first, which updates `index`/`lindex` to their fresh values before using `total-assets`/`total-debt`, so those callers never observe stale data: [3](#0-2) [4](#0-3) 

`socialize-debt`, however, is the one exception: it never calls `accrue`, and computes `old-total-assets` via the stale, non-preview `total-assets()`: [5](#0-4) 

Because `total-debt()` (stored `index`) is always ≤ `debt-preview()` (fresh `next-index()`) — interest only accrues upward — `total-assets()` is always understated relative to the true, up-to-date value whenever time has passed since the last `accrue()` call, exactly mirroring the `exchangeRateStored` vs `exchangeRateCurrent` discrepancy in the external report.

This understated `old-total-assets` (denominator `S`, true value `T`, with `S < T`) is plugged into:
```
new-lindex = current-lindex * (old-total-assets - debt-reduction) / old-total-assets   (if old-total-assets > debt-reduction)
```
The function `f(x) = (x - D)/x = 1 - D/x` is monotonically increasing in `x` for `x, D > 0`. Since `S < T`, `f(S) < f(T)`, meaning the ratio computed with the stale value is *smaller* than the ratio that would be computed with the true, fully-accrued value. The result is that `new-lindex` is written down **more aggressively than the bad debt event actually warrants**, imposing an incorrect, excess haircut on `lindex`.

`lindex` is not an internal-only bookkeeping value — it is consumed directly by the oracle price-resolution logic to price zTokens used as collateral market-wide: [6](#0-5) 

So an incorrect write-down of `lindex` directly and permanently misprices every zToken holder's collateral/balance across the whole protocol, not just the position being socialized.

### Impact Explanation
This lands in **Permanent freezing of funds** territory (and can bleed into **theft of unclaimed yield**): the erroneous extra reduction in `lindex` permanently destroys value for all outstanding zToken holders beyond what the actual bad debt requires — the excess amount is not recoverable by depositors because it's baked directly into the on-chain liquidity index used pervasively for share pricing and oracle collateral valuation. Because `lindex` also feeds the market oracle's collateral pricing (`get-asset-price`), the mispricing can additionally distort liquidation thresholds and LTV calculations for every position holding that zToken as collateral, compounding the fund-safety impact.

### Likelihood Explanation
`socialize-debt` fires whenever a market-side bad-debt/write-down event occurs (a normal, expected operational path of the protocol, not requiring DAO compromise) and the magnitude of the discrepancy grows with the elapsed time since the last `accrue()` call on the vault (i.e., with `time-delta` in `next-index()`). Since `accrue()` can be delayed by long periods of low activity (no deposit/redeem/borrow/repay calls), the staleness — and thus the miscalculated write-down — can be made arbitrarily large by simply waiting, making the bug reliably triggerable whenever any bad-debt socialization is required.

### Recommendation
Call `accrue()` (or use `debt-preview()`/`total-assets-preview()`, matching what `deposit`/`redeem`/`accrue` already do) inside `socialize-debt` before computing `old-total-assets`, so the liquidity-index write-down is based on the fully-accrued asset/debt state rather than the last-persisted, stale `index`.

### Proof of Concept
1. Let a vault accumulate outstanding debt with `principal-scaled > 0` and let a meaningful amount of time (`time-delta`) pass without any `deposit`, `redeem`, `system-borrow`, `system-repay`, or explicit `accrue()` call, so `index` (stored) diverges from what `next-index()` would compute.
2. Trigger a bad-debt event so the market calls `socialize-debt(scaled-amount)` on the vault (an ordinary, expected liquidation-shortfall handling path).
3. Inside `socialize-debt`, `old-total-assets = total-assets()` uses the stale stored `index`, producing `S < T` (true value).
4. Compute `new-lindex = current-lindex * (S - debt-reduction) / S`, which is provably smaller than the fair value `current-lindex * (T - debt-reduction) / T` that would result from an accrued state.
5. `lindex` is persisted and subsequently read by `get-liquidity-index`/`get-asset-price` (`v0-1-data.clar`), permanently propagating the excess write-down to every zToken holder's collateral valuation and share price, with no way to reclaim the difference.

(define-public (socialize-debt (scaled-amount uint))
  (let ((scaled-principal (var-get principal-scaled))
        (borrowed (var-get total-borrowed))
        (idx (var-get index))
        (current-assets (var-get assets))
        (current-lindex (var-get lindex))
        (old-total-assets (total-assets))
        (debt-reduction (mul-div-down scaled-amount idx INDEX-PRECISION))
        (principal-reduction (if (> scaled-principal u0)
                                (mul-div-down scaled-amount borrowed scaled-principal)
                                u0))
        ;; Write down lindex proportionally to loss in total-assets
        (new-lindex (if (and (> old-total-assets u0) (> old-total-assets debt-reduction))
                       (mul-div-down current-lindex (- old-total-assets debt-reduction) old-total-assets)
                       u0)))

    (try! (check-caller-auth))
    (asserts! (> scaled-amount u0) ERR-AMOUNT-ZERO)

    (var-set lindex new-lindex)
    (var-set principal-scaled (if (> scaled-principal scaled-amount) (- scaled-principal scaled-amount) u0))
    (var-set total-borrowed (if (> borrowed principal-reduction) (- borrowed principal-reduction) u0))
    (var-set assets (if (> current-assets principal-reduction) (- current-assets principal-reduction) u0))
