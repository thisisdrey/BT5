### Title
DoS of block/maintenance processing via unbounded `VotesStore` iteration in `MaintenanceManager.doMaintenance` / `Wallet.countVote` - (File: `consensus/src/main/java/org/tron/consensus/dpos/MaintenanceManager.java`)

### Summary
The GG-1 report describes a DoS caused by an unbounded `for` loop over a list (`usersBridges`) that any user can cheaply grow by depositing a tiny amount, eventually causing the loop-driven function to exceed the gas/processing limit and halt dividend distribution for everyone. The closest reachable analog in java-tron is the vote-tallying loop in `MaintenanceManager.countVote(VotesStore)` / `doMaintenance()`, and the duplicate logic in `Wallet.countVote` used by `getPaginatedNowWitnessList`. Both iterate over the entire `VotesStore`, whose keys are created by any account that casts a vote via `VoteWitnessActuator`/`VoteWitnessProcessor` — an operation reachable from ordinary signed transactions or TVM `vote` native contract calls, requiring only a minimal frozen stake.

### Finding Description
`VoteWitnessActuator.countVoteAccount` creates a new `VotesCapsule` entry keyed by the voter's address in `VotesStore` whenever an account casts a vote for the first time in an epoch [1](#0-0) . Any account with even a small amount of TRON Power (obtained by freezing a small balance via `FreezeBalanceV2Actuator`, which does not appear to enforce any economically significant minimum beyond a positive balance check) [2](#0-1)  can call `VoteWitnessContract` to add itself to `VotesStore`.

At every maintenance cycle, `MaintenanceManager.doMaintenance()` calls `countVote(votesStore)`, which opens a full iterator over `VotesStore` and, for every single entry, iterates its `oldVotes`/`newVotes` lists, unconditionally deleting each entry as it goes [3](#0-2) . This loop has no batching, no cap on the number of distinct voter entries, and runs synchronously as part of block/maintenance processing that every full node and witness must execute deterministically, exactly mirroring the unbounded `usersBridges` loop in the reported bug class [4](#0-3) .

A second, independently reachable copy of the identical unbounded pattern exists in `Wallet.countVote`, invoked synchronously on every call to the `getPaginatedNowWitnessList` gRPC/HTTP API, meaning an attacker-inflated `VotesStore` also degrades a public query path used by ordinary API clients [5](#0-4) .

### Impact Explanation
Because `doMaintenance()` executes deterministically as part of consensus/block processing on every node, an attacker who cheaply generates many addresses, freezes a minimal balance on each, and casts one vote per address can inflate `VotesStore` to a size that makes `countVote`'s per-entry, per-vote iteration exceed the time budget for maintenance processing on all full nodes and witnesses simultaneously. This can stall or desynchronize witness reward/vote tallying and the corresponding `getPaginatedNowWitnessList` API path, i.e., a network-wide DoS / halt condition of a core consensus routine rather than a localized single-transaction failure.

### Likelihood Explanation
Uncertain / not fully confirmed. I was not able to conclusively determine within the available search iterations (a) the concrete minimum frozen-balance/economic cost enforced by `FreezeBalanceV2Actuator.validate()` beyond the snippet shown, (b) whether `VotesStore` entries are pruned/limited elsewhere (e.g., a maximum number of distinct voters or existing gas/time budget protections in `doMaintenance`), and (c) the real-world wall-clock cost of iterating a `VotesStore` inflated to millions of entries versus the maintenance interval length. Without confirming the actual minimum stake cost and absence of any existing size cap, I cannot assert this rises to a definite, currently-exploitable Critical/High severity bug with certainty — it should be verified against the live `FreezeBalanceV2Actuator.validate()` full body and any store-level entry limits before treating this as confirmed.

### Recommendation
Bound the maintenance-time vote-tally loop: process `VotesStore` in fixed-size batches per maintenance cycle, cap the number of distinct voter entries considered, or migrate to a "vote-weight accumulator" (points-per-share-style) update model where votes update aggregate witness tallies incrementally at vote time rather than requiring a full-store scan at maintenance time. Apply the same batching/cap fix to `Wallet.countVote` used by `getPaginatedNowWitnessList`.

### Proof of Concept
1. Generate N new accounts; for each, submit a `FreezeBalanceV2Contract` transaction with a minimal frozen amount to obtain TRON Power.
2. For each account, submit a `VoteWitnessContract` transaction voting for any witness — this creates a new entry in `VotesStore` via `VoteWitnessActuator.countVoteAccount` [6](#0-5) .
3. Repeat for a large N (bounded only by transaction fees, which are minimal per vote).
4. At the next maintenance cycle, `MaintenanceManager.doMaintenance()` invokes `countVote(votesStore)`, iterating all N entries and their vote lists [3](#0-2) ; measure processing time growth as N increases to confirm the unbounded-scaling DoS vector, and separately call `getPaginatedNowWitnessList` to observe the same effect on `Wallet.countVote` [7](#0-6) .

  private void countVoteAccount(VoteWitnessContract voteContract) {
    AccountStore accountStore = chainBaseManager.getAccountStore();
    VotesStore votesStore = chainBaseManager.getVotesStore();
    MortgageService mortgageService = chainBaseManager.getMortgageService();
    byte[] ownerAddress = voteContract.getOwnerAddress().toByteArray();

    VotesCapsule votesCapsule;

    //
    mortgageService.withdrawReward(ownerAddress);

    AccountCapsule accountCapsule = accountStore.get(ownerAddress);

    DynamicPropertiesStore dynamicStore = chainBaseManager.getDynamicPropertiesStore();
    if (dynamicStore.supportAllowNewResourceModel()
        && accountCapsule.oldTronPowerIsNotInitialized()) {
      accountCapsule.initializeOldTronPower();
    }

    if (!votesStore.has(ownerAddress)) {
      votesCapsule = new VotesCapsule(voteContract.getOwnerAddress(),
          accountCapsule.getVotesList());
    } else {
      votesCapsule = votesStore.get(ownerAddress);
    }

    accountCapsule.clearVotes();
    votesCapsule.clearNewVotes();

    voteContract.getVotesList().forEach(vote -> {
      logger.debug("countVoteAccount, address[{}]",
          ByteArray.toHexString(vote.getVoteAddress().toByteArray()));

      votesCapsule.addNewVotes(vote.getVoteAddress(), vote.getVoteCount());
      accountCapsule.addVotes(vote.getVoteAddress(), vote.getVoteCount());
    });

    accountStore.put(accountCapsule.createDbKey(), accountCapsule);
    votesStore.put(ownerAddress, votesCapsule);
  }

  private Map<ByteString, Long> countVote(VotesStore votesStore) {
    final Map<ByteString, Long> countWitness = Maps.newHashMap();
    Iterator<Entry<byte[], VotesCapsule>> dbIterator = votesStore.iterator();
    long sizeCount = 0;
    while (dbIterator.hasNext()) {
      Entry<byte[], VotesCapsule> next = dbIterator.next();
      VotesCapsule votes = next.getValue();
      votes.getOldVotes().forEach(vote -> {
        ByteString voteAddress = vote.getVoteAddress();
        long voteCount = vote.getVoteCount();
        if (countWitness.containsKey(voteAddress)) {
          countWitness.put(voteAddress, countWitness.get(voteAddress) - voteCount);
        } else {
          countWitness.put(voteAddress, -voteCount);
        }
      });
      votes.getNewVotes().forEach(vote -> {
        ByteString voteAddress = vote.getVoteAddress();
        long voteCount = vote.getVoteCount();
        if (countWitness.containsKey(voteAddress)) {
          countWitness.put(voteAddress, countWitness.get(voteAddress) + voteCount);
        } else {
          countWitness.put(voteAddress, voteCount);
        }
      });
      sizeCount++;
      votesStore.delete(next.getKey());
    }
    logger.info("There is {} new votes in this epoch", sizeCount);
    return countWitness;
  }

  private Map<ByteString, Long> countVote(VotesStore votesStore) {
    // Initialize a result map to store vote changes for each witness
    Map<ByteString, Long> countWitness = Maps.newHashMap();

    // VotesStore is a key-value store, where the key is the address of the voter
    Iterator<Entry<byte[], VotesCapsule>> dbIterator = votesStore.iterator();

    while (dbIterator.hasNext()) {
      Entry<byte[], VotesCapsule> next = dbIterator.next();
      VotesCapsule votes = next.getValue();

      /**
       * VotesCapsule contains two lists:
       * - Old votes: Last votes from the previous epoch, updated in maintenance period
       * - New votes: Latest votes in current epoch, updated after each vote transaction
       */
      votes.getOldVotes().forEach(vote -> {
        ByteString voteAddress = vote.getVoteAddress();
        long voteCount = vote.getVoteCount();
        countWitness.put(voteAddress,
            countWitness.getOrDefault(voteAddress, 0L) - voteCount);
      });
      votes.getNewVotes().forEach(vote -> {
        ByteString voteAddress = vote.getVoteAddress();
        long voteCount = vote.getVoteCount();
        countWitness.put(voteAddress,
            countWitness.getOrDefault(voteAddress, 0L) + voteCount);
      });
    }
    return countWitness;
