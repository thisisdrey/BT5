**No vulnerability found for this question.**

Investigation confirms the claimed fault does not exist: `restart()` is unconditionally invoked at exactly the two points that bracket every request lifecycle in `ConnectionHttp`'s state machine, so `parse_retained_mem_bytes` cannot leak across requests on a reused handler.

- On a parse failure, `try_parse_request` in `stackslib/src/net/httpcore.rs` calls `request.restart()` immediately before returning the error, both in the production path and the `#[cfg(test)]` `handle_try_parse_request` path. [1](#0-0) [2](#0-1) 

- On a successful parse+handle, `try_handle_request` calls `request_handler.restart()` right after `try_handle_request` returns, before the connection can process another request on the same handler. [3](#0-2) 

- Additionally, even disregarding `restart()`, `RPCCallReadOnlyRequestHandler::try_parse_request` unconditionally overwrites `self.parse_retained_mem_bytes = parsed.retained_mem_bytes` on every successful parse before `execution_resource_limiter()` is ever constructed for that request, so a stale value from a prior request cannot survive into the current request's budget computation. [4](#0-3) [5](#0-4) 

There is no code path in this repository where a second `try_parse_request` call executes on the same `RPCCallReadOnlyRequestHandler` instance without either (a) `restart()` having been called after the prior request's handling completed, or (b) the field being freshly overwritten by the new parse. The "error path skips reset" premise in the question does not correspond to any actual branch in `try_parse_request`/`handle_try_parse_request`/`try_handle_request` — every exit path (success or failure) calls `restart()` before the connection is available to parse another request.
