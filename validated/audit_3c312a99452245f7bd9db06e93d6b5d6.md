### Title
Unbounded array allocation in `BatchValidateSign`/`ValidateMultiSign` precompiled contracts from attacker-controlled length words causes memory exhaustion (OOM) - ([File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java])

### Summary
The CVE describes unbounded memory allocation driven directly by an attacker-supplied size field in untrusted input (a crafted STL file), with no upper bound before the allocation happens. The same bug class exists in java-tron's `BatchValidateSign` precompiled contract (and the sibling `ValidateMultiSign`), reachable through a normal `CALL`/`STATICCALL` from any smart contract triggered by an unprivileged transaction. Array sizes used to allocate `byte[][]` buffers are read directly from calldata words and, on chains/paths where the length-limiting guard has not been activated, are used to allocate arrays with no cap on the number of elements.

### Finding Description
`BatchValidateSign.doExecute` parses the ABI-encoded input into `DataWord[] words` and computes offsets/lengths straight out of attacker-controlled calldata: [1](#0-0) 

The `MAX_SIZE` (16) bound on `sigArraySize`/`addrArraySize` is only enforced when `VMConfig.allowTvmSelfdestructRestriction()` is true: [2](#0-1) 

`allowTvmSelfdestructRestriction` is a governance-activated chain parameter (a `ProposalUtil`/`DynamicPropertiesStore` toggle, not a hard-coded constant), so any deployment where that proposal has not been passed executes `extractBytesArray`/`extractBytes32Array` without any bound check: [3](#0-2) 

Both helpers do `int len = words[offset].intValueSafe();` followed immediately by `new byte[len][...]`, where `len` is an arbitrary 256-bit value truncated to a Java `int` and fully controlled by the calldata the caller crafts — it is never cross-checked against the real size of `data`. A `len` close to `Integer.MAX_VALUE` triggers an allocation of a multi-gigabyte array of references before any other validation or energy-bounded work is performed, mirroring the `PerimeterGenerator` pattern in the CVE where a size field taken from untrusted input drives an allocation with no sanity bound.

The related `isValidAbiEncoding` check (gated separately behind `VMConfig.allowTvmOsaka()`) only validates that the *overall* `data.length` is consistent with a header/item-word layout; it does not validate the embedded `len` word used for the allocation, so it does not close the gap either.

### Impact Explanation
A successful trigger causes a Java `OutOfMemoryError` inside the TVM execution thread. Depending on JVM heap pressure this can abort only the current transaction (as already observed and asserted for the unrelated TVM `outOfMemTest` OOM case) or destabilize the FullNode/witness process handling many concurrent transactions, since the huge intermediate allocations occur before energy for that specific allocation is charged. Because this is reachable by anyone submitting a `TriggerSmartContract` transaction that performs a `CALL` to the `BatchValidateSign`/`ValidateMultiSign` precompiled address, it fits the "node crash or halt" impact bucket required by scope rules — but only on networks/paths where the `allowTvmSelfdestructRestriction` proposal has not been activated.

### Likelihood Explanation
Likelihood is limited by two factors that reduce confidence this is currently exploitable on the target chain:
1. The bound was intentionally added under the `TIP-854`/`allowTvmSelfdestructRestriction` proposal — indicating the java-tron team already identified and fixed exactly this class of issue, and it is very likely enabled on mainnet given the accompanying regression tests (`testTip854OuterFrameContainment`).
2. On networks where the proposal is active, the guard fully mitigates the allocation before it happens.

The remaining exposure is any deployment (private chain, sidechain, fork, or a mainnet window before the proposal activation) that has not yet flipped `allowTvmSelfdestructRestriction` to true.

### Recommendation
Bound `len` unconditionally (not just behind the `allowTvmSelfdestructRestriction` flag) in `extractBytesArray` and `extractBytes32Array` before allocating, and make the bound check independent of any activation-gated proposal so all deployments are protected regardless of hard-fork status.

### Proof of Concept
Not fully verifiable statically because reachability depends on the runtime value of `VMConfig.allowTvmSelfdestructRestriction()`, which is a governance-controlled parameter I cannot confirm the activation state of for the target deployment. Conceptually: deploy a contract that performs
`CALL(gas, <BatchValidateSign precompile address>, 0, inOffset, inSize, outOffset, outSize)`
with calldata where `words[1]` points to an offset whose word value (`sigArraySize`) is set to a very large integer (e.g., `0x7FFFFFFF`), while the surrounding `data` buffer is small. On a node where the length guard is inactive, this reaches `extractBytesArray`/`extractBytes32Array` and attempts `new byte[0x7FFFFFFF][]`, triggering an `OutOfMemoryError` in the executing node.

    int len = words[offset].intValueSafe();
    byte[][] bytes32Array = new byte[len][];
    for (int i = 0; i < len; i++) {
      bytes32Array[i] = words[offset + i + 1].getData();
    }
    return bytes32Array;
  }

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
