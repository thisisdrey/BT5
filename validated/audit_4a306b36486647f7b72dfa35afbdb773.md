### Title
Permission name length check uses UTF-16 char count instead of byte length, allowing oversized names to be permanently stored - (File: actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java)

### Summary
`AccountPermissionUpdateActuator.checkPermission` bounds the `permission_name` field with `name.length() > 32`, where `name` is a Java `String` decoded from the protobuf `string` field. [1](#0-0)  `String.length()` counts UTF-16 code units, not the number of UTF-8 bytes that will actually be serialized and persisted on-chain. This is the same class of bug as the reported Ash issue: a size constraint that counts the wrong unit relative to what gets stored, letting an attacker smuggle more bytes past the check than the limit implies.

### Finding Description
Elsewhere in the codebase, string-like fields on actuators (asset name, description, url, account id, account name) are validated by first converting to `byte[]` and comparing `bytes.length <= maxLength`, which correctly bounds on-disk size, as seen in `TransactionUtil.validBytes`/`validReadableBytes` and their use in `AssetIssueActuator.validate`. [2](#0-1) [3](#0-2) 

`AccountPermissionUpdateActuator.checkPermission`, however, does the check on the decoded `String` directly:
```java
String name = permission.getPermissionName();
if (!StringUtils.isEmpty(name) && name.length() > 32) {
  throw new ContractValidateException("permission's name is too long");
}
``` [1](#0-0) 

Because protobuf `string` fields are UTF-8 encoded on the wire and on disk, but `String.length()` counts UTF-16 code units, a name composed of characters that encode to 2–4 UTF-8 bytes per code unit (e.g. CJK ideographs, most non-Latin scripts) passes the "≤32" check while consuming up to ~96–128 bytes on disk (up to 4 bytes/char for BMP characters that map to a single UTF-16 unit, or up to 4 bytes per 2 code units for supplementary-plane characters via surrogate pairs). This mismatched counting unit is exactly the bug class in the external report: validation measures the wrong unit relative to what is durably persisted.

The oversized name is then written into `owner`/`witness`/each of up to 8 `active` `Permission` protobuf structures via `AccountCapsule.updatePermissions`, which is committed into `AccountStore` (part of persistent chain state) in `execute()`. [4](#0-3)  Because `checkPermission` is invoked once per permission (`owner`, optional `witness`, and up to 8 `actives`), a single `AccountPermissionUpdateContract` transaction can inflate up to 10 name fields simultaneously. [5](#0-4) 

### Impact Explanation
Any account owner (an unprivileged, anonymous transaction broadcaster who owns/controls an address) can broadcast an `AccountPermissionUpdateContract` and multiply the effective size of each permission name beyond the intended 32-unit cap by using multi-byte UTF-8 characters, inflating the persisted state (`AccountStore`, replicated on every full node) for a single flat `UpdateAccountPermissionFee`. [6](#0-5)  Because the fee is fixed and independent of the resulting byte size, this can be repeated (re-issuing `AccountPermissionUpdateContract` transactions, subject to bandwidth/fee costs of the transaction itself) to grow chain state disproportionately to the paid fee, degrading node storage/sync economics. This does not directly enable fund theft or unauthorized transfers, and the amplification factor is bounded (roughly 2–4x per name field, not unbounded like the Ash grapheme case), which limits severity relative to the original report.

### Likelihood Explanation
The path is trivially reachable: any account can self-issue an `AccountPermissionUpdateContract` as long as `AllowMultiSign` is enabled, requiring only a valid signature over their own account — no special privilege, node, or witness role is needed. [7](#0-6)  Constructing a permission name with multi-byte UTF-8 characters requires no special tooling.

### Recommendation
Change the length check in `checkPermission` to measure the UTF-8 byte length of the name (e.g., `permission.getPermissionNameBytes().size()` from the protobuf `ByteString`, mirroring the pattern already used by `TransactionUtil.validBytes`/`validReadableBytes` for other name/description fields) rather than `String.length()`, and enforce the byte-based bound of 32 consistently.

### Proof of Concept
1. Attacker controls an account with `AllowMultiSign` enabled.
2. Attacker builds an `AccountPermissionUpdateContract` where `owner.permission_name` (and optionally `witness`/each `actives` permission name) is set to 32 repetitions of a 3-byte UTF-8 character (e.g., a CJK ideograph such as `"合"`), yielding a Java `String` with `length() == 32` (passing the check) but `getPermissionNameBytes().size() == 96` bytes.
3. Attacker signs and broadcasts the transaction, paying the normal flat `UpdateAccountPermissionFee`.
4. `checkPermission` passes since `name.length() == 32`, and `execute()` persists the 96-byte name into `AccountCapsule`/`AccountStore` for the owner permission — 3x the byte size the 32-unit constraint was intended to enforce — and can be repeated across `witness` and up to 8 `actives` permissions in the same transaction for further amplification.

  private static boolean validBytes(byte[] bytes, int maxLength, boolean allowEmpty) {
    if (ArrayUtils.isEmpty(bytes)) {
      return allowEmpty;
    }
    return bytes.length <= maxLength;
  }

  private static boolean validReadableBytes(byte[] bytes, int maxLength) {
    if (ArrayUtils.isEmpty(bytes) || bytes.length > maxLength) {
      return false;
    }
    // b must be readable
    for (byte b : bytes) {
      if (b < 0x21) {
        return false; // 0x21 = '!'
      }
      if (b > 0x7E) {
        return false; // 0x7E = '~'
      }
    }
    return true;
  }
