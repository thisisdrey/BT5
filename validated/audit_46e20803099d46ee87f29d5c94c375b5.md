### Title
Unbounded array allocation in `BatchValidateSign` precompile allows OOM-based node crash - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The `BatchValidateSign` precompiled contract (invoked via TVM `CALL`/`STATICCALL` to its reserved address) decodes attacker-supplied ABI header words as array lengths and allocates Java arrays sized directly from those lengths before performing any bound check, mirroring the CVE-2023-50008 pattern of allocating memory from an unvalidated, attacker-controlled size field.

### Finding Description
`BatchValidateSign.doExecute` reads two length fields straight from calldata and only bounds them when the `allowTvmSelfdestructRestriction` chain parameter is active: [1](#0-0) 

When that parameter is not enabled, the `MAX_SIZE` (16) check is skipped entirely, yet `extractBytes32Array` (for `addresses`) and `extractBytesArray` (for `signatures`, in the non-restriction branch) are still invoked. Both helpers allocate a two-dimensional array whose outer dimension equals a value read directly from calldata with no upper bound: [2](#0-1) 

`words[offset].intValueSafe()` can be driven up to `Integer.MAX_VALUE` by crafting the corresponding 32-byte word in calldata. `new byte[len][]` with `len` near `Integer.MAX_VALUE` attempts to allocate an array of ~2.1 billion object references (~17 GB on a 64-bit JVM with compressed oops disabled, ~8.6 GB with them enabled) in a single statement, before any element is read and before energy accounting for this internal size has occurred — `getEnergyForData` only charges based on `data.length`, not on this internally decoded array length: [3](#0-2) 

This is the same bug class as the FFmpeg `av_malloc` issue: a size value taken from untrusted input is used to allocate memory without validating it against any sane bound, causing memory-consumption denial of service.

### Impact Explanation
`BatchValidateSign` is reachable from any smart contract via a plain `CALL`, meaning any unprivileged address can broadcast a transaction that triggers this precompile with crafted calldata. Because transaction execution is deterministic, every full node/SR that processes the transaction (mempool validation and block application) executes the same allocation, so a single transaction can induce an `OutOfMemoryError`/heap exhaustion across the entire validating network simultaneously, which is a node crash/halt condition, and potentially a chain-halting event if only a subset of implementations/configurations are vulnerable (chain split risk between nodes with differing `allowTvmSelfdestructRestriction` activation state, e.g. during a hard-fork rollout window or on a still-unupgraded fork of java-tron).

### Likelihood Explanation
Exploitation only requires constructing calldata for the `BatchValidateSign` precompile address with an inflated array-length word; no special privileges, signatures, or account state are required beyond broadcasting a standard TVM transaction. The condition is gated only by whether `allowTvmSelfdestructRestriction` is enabled on the target chain — any deployment where this parameter has not yet been activated (new networks, private/enterprise chains built on this codebase, or during the activation window of an upgrade) remains fully exposed.

### Recommendation
Enforce the `MAX_SIZE` bound on the decoded `sigArraySize`/`addrArraySize` (and any other length fields consumed by `extractBytes32Array`/`extractBytesArray`/`extractSigArray`) unconditionally, not only when `allowTvmSelfdestructRestriction` is active. Additionally, validate lengths derived from calldata against `data.length` (or a fixed small ceiling) before performing any array allocation inside these helper methods.

### Proof of Concept
1. Craft calldata for `BatchValidateSign` where the ABI header word pointed to by `words[2]` (the address-array length slot consumed by `extractBytes32Array`) is set to `0x7FFFFFFF`.
2. On a java-tron network/config where `allowTvmSelfdestructRestriction()` has not been activated, submit a transaction whose contract performs a `CALL` to the `BatchValidateSign` precompile address with this calldata.
3. `extractBytes32Array` executes `new byte[0x7FFFFFFF][]` at PrecompiledContracts.java:392, attempting a multi-gigabyte allocation on every node that executes the transaction, exhausting heap and triggering `OutOfMemoryError`/node instability across the network.

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {

    }

          bytesLen);
    }

  }
