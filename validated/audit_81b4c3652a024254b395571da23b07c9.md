### Title
Access key nonce reseeding on recreation does not carry forward the deleted key's prior nonce, enabling replay of previously-signed transactions - (File: `runtime/runtime/src/access_keys.rs`)

### Summary
This is the closest legitimate analog to the Sherlock M-13 bug class ("state associated with an identity is not reset/carried across a re-registration event, letting stale state be exploited against a lower threshold/baseline than intended"). In `QVBaseStrategy`, the per-status vote counter `reviewsByStatus[recipientId][status]` survives a recipient's re-registration, letting a re-registered application reach `Accepted` with fewer new votes than `reviewThreshold`. In nearcore, the analogous per-identity "counter" is an access key's `nonce`, and the analogous re-registration event is deleting and re-adding an access key with the *same public key*. The code's own design comment states that on recreation the new key's nonce "should be equal to the nonce of the old access key ... to avoid replaying old transactions again" [1](#0-0) , but the actual implementation does not carry forward the old nonce — it always reseeds from the current block height.

### Finding Description
When a regular access key is created via `add_regular_key`, its nonce is unconditionally set to `initial_nonce_value(block_height)`, with no check for whether a key with the same public key existed and was deleted before: [2](#0-1) 

`initial_nonce_value` computes a purely block-height-derived seed: [3](#0-2) 

`action_delete_key` simply removes the access key record from state, discarding its stored nonce entirely — no trace of the old nonce is kept anywhere for future recreation to consult: [4](#0-3)  and `delete_regular_key`: [5](#0-4) 

During normal transaction processing, an access key's stored nonce is advanced to whatever value the *user* chose for that transaction (any value greater than the current nonce, up to the protocol-enforced upper bound `block_height * ACCESS_KEY_NONCE_RANGE_MULTIPLIER`), as documented: `verify_nonce` enforces `tx_nonce > current_nonce` (Monotonic) and an upper bound of `block_height * 1_000_000` [6](#0-5) .

Because `AddKey`/`DeleteKey`/other actions in the *same transaction* execute against the *same* `apply_state.block_height`, a single transaction containing `[DeleteKey(pk), AddKey(pk, ...)]` reseeds the new key's nonce to `(block_height-1) * 1_000_000` regardless of how high the just-deleted key's nonce had been advanced to (up to `block_height * 1_000_000 - 1`). This means the freshly recreated key's nonce baseline can end up **lower** than the nonce of a transaction that was previously signed (and possibly never broadcast, or broadcast but not yet included) under the old key instance. Replay protection is nonce-monotonicity based (`verify_nonce`) [7](#0-6) , so once the baseline drops below a previously-valid signed nonce, that old signed transaction becomes replayable again — exactly mirroring the Sherlock bug's pattern of a per-identity threshold-tracking value not being reset/carried across a "re-registration" (key delete+recreate) event.

The existing regression test only exercises the **account** re-creation path (`send_money` triggering NEAR-implicit account creation, delete, recreate) and confirms the current design intentionally accepts that stale high nonces from *before* deletion become replayable after recreation, since the check explicitly expects `InvalidTxError::InvalidNonce` only when using the *old, too-small* nonce, and a transaction using the new low baseline succeeds: [8](#0-7) 

This test demonstrates the acknowledged, but not fully mitigated, tension between "avoid tx-hash collision" (why nonce reseeds from block height) and "avoid replaying old signed transactions" (why the doc says the nonce should carry forward on same-key recreation).

### Impact Explanation
If a user (or an application acting on the user's behalf, e.g. a relayer holding previously signed-but-unbroadcast transactions) deletes and re-adds the same public key within a narrow block-height window (including atomically in one transaction), any previously valid but unexecuted signed transaction with a nonce below the new reseeded baseline can be replayed. Depending on what that stale transaction authorizes (a `Transfer`, `FunctionCall`, `Stake`, or another `DeleteKey`/`AddKey`), this can result in unauthorized funds transfer, unintended function-call execution, or unexpected privilege changes on the account — i.e., double-spend/replay of an authorization the signer believed was withdrawn when they deleted the key. This is reachable by any ordinary account holder issuing standard `DeleteKey`+`AddKey` actions; no privileged or validator/network role is required.

### Likelihood Explanation
Likelihood is **low-to-moderate**: exploitation requires (a) a previously signed, still-nonce-valid transaction that was withheld from inclusion (e.g., a relayer/dApp holding a batch of pre-signed transactions, or a user signing multiple transactions with high nonces in advance), and (b) the account holder subsequently deleting and re-adding the same public key within a block-height window small enough that `(new_block_height - 1) * ACCESS_KEY_NONCE_RANGE_MULTIPLIER` is still below the old signed nonce. This is a realistic pattern for wallets/relayers that pre-sign transactions with high nonces for scheduling, or key-rotation flows that reuse the same public key. It is not exploitable by an attacker without possession of at least one previously-signed transaction from the victim, so it is not a fully-arbitrary "anyone can steal funds" bug, but it is a genuine, protocol-documented gap between intended and implemented behavior.

### Recommendation
When recreating a regular access key with a public key that was previously deleted, the new key's nonce should be seeded from `max(initial_nonce_value(block_height), previous_nonce_of_this_public_key)` rather than unconditionally from `initial_nonce_value(block_height)`. This requires either (a) not fully removing the nonce record on `DeleteKey` (retaining a tombstone of the last nonce per `(account_id, public_key)`), or (b) requiring `AddKey` to look up and honor any tombstoned prior nonce for that exact public key before reseeding, consistent with the documented invariant in `docs/DataStructures/AccessKey.md`.

### Proof of Concept
1. Account `A` has access key `pk` with a small nonce.
2. `A`'s wallet/relayer pre-signs `Tx1 = Transfer(..., nonce = N)` where `N` is close to the current upper bound `block_height_0 * 1_000_000`, but does not broadcast it yet.
3. `A` submits a transaction at height `H` containing `[DeleteKey(pk), AddKey(pk, new_permission)]` in one transaction (single block/receipt, same `apply_state.block_height = H`).
4. The new key's nonce is reseeded to `(H-1) * 1_000_000` via `add_regular_key`/`initial_nonce_value` [9](#0-8) , which is lower than `N` if `N` was chosen close to `block_height_0 * 1_000_000` and `H` is only slightly larger than `block_height_0`.
5. The withheld `Tx1` (nonce `N`) is now broadcast; `verify_nonce`'s Monotonic check (`tx_nonce > current_nonce`) passes because `N > (H-1) * 1_000_000`, and `Tx1` executes — replaying an authorization the user believed was revoked when the key was deleted.

**Uncertainty note**: I could not fully verify from the index whether any additional out-of-band protection (e.g., a global per-account nonce watermark independent of per-key nonce, or mempool/relay-level de-duplication) exists elsewhere in the codebase that might further mitigate this scenario beyond what's shown in `verifier.rs`/`access_keys.rs`; the index's coverage of `verifier.rs` internals (e.g. exact `verify_nonce` implementation body) was only available via the derived spec document, not the raw source. A Devin session with full repository access would be needed to inspect `runtime/runtime/src/verifier.rs` line-by-line and confirm there is no additional safeguard.

    // Set default nonce for newly created access key to avoid transaction hash collision.

fn add_regular_key(
    fee_config: &RuntimeFeesConfig,
    state_update: &mut TrieUpdate,
    account: &mut Account,
    account_id: &AccountId,
    public_key: &PublicKey,
    access_key: &AccessKey,
    block_height: BlockHeight,
) -> Result<(), StorageError> {
    let mut access_key = access_key.clone();
    access_key.nonce = initial_nonce_value(block_height);
    set_access_key(state_update, account_id.clone(), public_key.clone(), &access_key);

    account.set_storage_usage(
        account
            .storage_usage()
            .checked_add(access_key_storage_usage(fee_config, public_key, &access_key))
            .ok_or_else(|| {
                StorageError::StorageInconsistentState(format!(
                    "Storage usage integer overflow for account {}",
                    account_id
                ))
            })?,
    );
    Ok(())
}
