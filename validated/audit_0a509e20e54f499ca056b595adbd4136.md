### Title
Locked User Redemptions via Asset Diversion in Rescuable Flow - ([File: tare-io__tare-contracts/contracts/PortfolioVault.sol])

### Summary
The `PortfolioVault` contract implements an asynchronous redemption flow (ERC-7540) where assets are committed to users upon approval. However, the contract inherits `Rescuable`, which allows a `Guardian` to withdraw any ERC20 token, including the vault's underlying `assetToken`. If the operational currency is "rescued," the assets previously approved for user redemptions become locked in the accounting state but physically absent from the contract, preventing users from claiming their funds.

### Finding Description
In `PortfolioVault.sol`, when a manager calls `approveRedemption`, the contract calculates the equivalent assets for the shares being redeemed and updates the `claimableRedeemAssets[controller]` mapping and the global `totalClaimableRedeemAssets` counter [5](#0-4) . These assets are now "owned" by the users and are expected to be available in the contract's balance.

The contract also inherits `Rescuable.sol`, which provides the `rescueERC20Tokens` function [6](#0-5) . This function does not exclude the vault's `assetToken`. If a `Guardian` executes a rescue of the `assetToken`, the physical balance of the contract decreases, but the `claimableRedeemAssets` and `totalClaimableRedeemAssets` remain unchanged [7](#0-6) .

When a user subsequently calls `redeem()` or `withdraw()`, the internal `_claimRedeem` function attempts to transfer the assets:
`assetToken.safeTransfer(receiver, assets);` [8](#0-7) .
This call will revert due to insufficient balance, effectively locking the user's claimable rewards despite the protocol acknowledging the debt.

### Impact Explanation
This leads to a practical lock of USDC and other claimable assets for honest users. Even if the `Guardian` is trusted, the lack of an exclusion list for the operational currency allows for accidental or malicious diversion of funds that have already been legally/contractually assigned to shareholders during the approval phase. This violates the core protocol invariant that `assetToken.balanceOf(vault) >= totalClaimableRedeemAssets + totalPendingDepositAssets`.

### Likelihood Explanation
The likelihood is considered medium-low as it requires a `Guardian` action. However, the impact is high because it bricks the primary exit mechanism for investors and corrupts the vault's NAV accounting, which relies on the balance minus reserved assets [9](#0-8) .

### Recommendation
Modify the `rescueERC20Tokens` function in `Rescuable.sol` (or override it in `PortfolioVault`) to explicitly revert if the `token` address matches the `assetToken` address. This ensures that the operational currency, which is critical for fulfilling user redemptions, cannot be diverted through the rescue mechanism.

### Proof of Concept
1. A user requests a redemption of 100,000 shares.
2. The `INVESTOR_MANAGER` calls `approveRedemption`, which sets `claimableRedeemAssets[user] = 100,000 USDC` and increments `totalClaimableRedeemAssets` by 100,000.
3. The `Guardian` calls `rescueERC20Tokens(USDC_ADDRESS, balance)`. The contract's USDC balance is now 0.
4. The user calls `redeem(100,000, user, user)`.
5. The transaction reverts at `assetToken.safeTransfer(receiver, assets)` because the contract balance is 0, but the user's `claimableRedeemAssets` is still 100,000. The user's funds are now trapped until the `Guardian` returns the USDC.

```markdown
### 2 — `Rescuable.rescueERC20Tokens` can drain the operational currency, breaking core accounting invariants

**Where:** [`Rescuable.rescueERC20Tokens`](contracts/misc/Rescuable.sol), inherited by [`Loans`](contracts/Loans.sol) and [`PortfolioVault`](contracts/PortfolioVault.sol)

`Rescuable` has no token allowlist or exclusion of the contract's configured `currency` / `assetToken`. Guardian can move the operational currency out of either contract, with no on-chain reconciliation to internal accounting.

- **On `Loans`**: every loan's cash bucket (`ACC_CASH`) is custodied in the same contract. The invariant `currency.balanceOf(loans) >= Σ ACC_CASH[loanId]` underpins per-loan cash segregation. Rescuing `currency` silently violates this invariant: subsequent withdrawals either revert (insufficient balance) or — worse — succeed by drawing against another loan's cash, cross-contaminating loan segregation.
- **On `PortfolioVault`**: `updateNav` finalization computes `lastNav = assetToken.balanceOf(this) − totalPendingDepositAssets − totalClaimableRedeemAssets + adjustedNav`. Rescuing `assetToken` lowers the balance without touching the counters; the next finalize underflow-reverts and bricks NAV until the rescued amount is returned.

**Impact:** Guardian compromise (or honest mistake) of `rescueERC20Tokens` on `Loans` permits arbitrary loss of loan custody funds. On the vault, NAV becomes unupdatable until reconciled off-chain.
```
