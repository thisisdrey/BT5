### Title
Unauthenticated address/key binding forgery via unsolicited `Handshake` on outbound connection before public key is established - (File: stackslib/src/net/chat.rs)

### Summary
`ConversationP2P::validate_handshake` only enforces that `HandshakeData.addrbytes/port` matches the socket address that was actually dialed (`self.peer_addrbytes`/`self.peer_port`) when the connection already has a known public key (`self.connection.get_public_key().is_some()`). On the very first `Handshake` message received on an outbound connection (when no public key is yet known), only the Secp256k1 signature over the message is checked, not the claimed address. This allows a peer we dial at address A to sign a `Handshake` claiming an arbitrary `addrbytes`/`port` B, which then gets persisted into the frontier table via `Neighbor::load_and_update` + `Neighbor::save_update`, binding the peer's real (signature-proven) public key to an attacker-chosen, unproven network address.

### Finding Description
The claimed equality — "the `NeighborKey{addrbytes,port}` written to the frontier equals the address the local node actually dialed" — does **not** hold on the first handshake of an outbound connection.

- `validate_handshake` (`stackslib/src/net/chat.rs:1047-1127`) branches on `self.connection.get_public_key()`:
  - `None` branch (line 1058-1071): only calls `message.verify_secp256k1(&handshake_data.node_public_key)`. No check that `handshake_data.addrbytes/port` equals `self.peer_addrbytes/self.peer_port`.
  - `Some(_)` branch (line 1072-1091): enforces `self.peer_addrbytes == handshake_data.addrbytes && self.peer_port == handshake_data.port` when `self.stats.outbound` (unless the peer reports the "anynet" address). This is the only place the address/socket binding is checked, and it is skipped entirely when no key is yet known.
- `handle_handshake` (`stackslib/src/net/chat.rs:1214-1333`) calls `validate_handshake`, then `update_from_handshake_data` (sets `updated = true` when `old_pubkey_opt.is_none()`, i.e. first handshake), and if `updated && self.stats.outbound` (line 1275), it does:
  - `Neighbor::load_and_update(&tx, ..., &handshake_data)` (`stackslib/src/net/chat.rs:475-516`), which builds `let addr = NeighborKey::from_handshake(peer_version, network_id, handshake_data)` — i.e., `addrbytes`/`port` taken verbatim from the attacker-controlled `HandshakeData` (`stackslib/src/net/chat.rs:411-423`), not from the socket address actually dialed.
  - `neighbor.save_update(&tx, None)` (`stackslib/src/net/neighbors/neighbor.rs:50-61`), which calls `PeerDB::update_peer` (`stackslib/src/net/db.rs:1286-1334`) writing `neighbor.addr.addrbytes`/`port` (attacker-chosen B) together with `neighbor.public_key` (verified real key of the peer at A) into the `frontier` table.

Exploit flow: outbound convo dials peer at address A and sends its own `Handshake`. Before the peer replies with a `HandshakeAccept`, the peer instead (or in addition) sends an unsolicited, signed `Handshake` message whose `HandshakeData.addrbytes/port = B` (an arbitrary IP, e.g. a victim's address, unrelated to A). Since `handle_unauthenticated_control_message` dispatches any `StacksMessageType::Handshake` to `handle_handshake` regardless of connection direction (`stackslib/src/net/chat.rs:2617-2624`), and this is the first handshake on this convo (`self.connection.get_public_key()` is `None`), `validate_handshake` only checks the signature (valid, since attacker signs with their real key) and does not check the claimed address against A. `update_from_handshake_data` marks `updated = true`, and since `self.stats.outbound` is true, the frontier row gets written with `addr = B`, `public_key = attacker's real pubkey`.

This is distinct from the `HandshakeAccept` path in `stackslib/src/net/neighbors/walk.rs::handle_handshake_accept` (line 705-715), which explicitly checks `neighbor_from_handshake.addr != self.cur_neighbor.addr` for outbound walks and rejects mismatches — that guard does not exist in `chat.rs::handle_handshake`'s direct-Handshake save path.

### Impact Explanation
An unprivileged remote peer can cause a node to write an unauthenticated, attacker-chosen `(addrbytes, port)` into its persistent frontier/PeerDB table, bound to the attacker's real (proven) public key. This corrupts the node's view of the P2P topology (identity != network address), and this corrupted entry can subsequently be picked up by neighbor-walk logic, gossiped, or used to direct connection attempts at the forged address (e.g., targeting a victim IP, or third-party amplification/reflection via connection attempts). This is an unauthenticated write to persistent node state and matches the "Critical: unauthenticated write to state" category.

### Likelihood Explanation
Preconditions: the attacker only needs to run a normal peer that a target node connects to (or is willing to connect outbound to), and race/send a crafted `Handshake` message before or instead of a normal `HandshakeAccept`. No secrets, no privileged role, and no special network position are required — any P2P-reachable node that the target dials outbound is enough. This is repeatable per outbound connection attempt (each fresh reconnect resets `self.connection.get_public_key()` to `None` for that convo), so the attacker can repeatedly poison entries pointing at different targets.

### Recommendation
In `validate_handshake` (`stackslib/src/net/chat.rs`), remove the exemption for the `None`-public-key branch: always enforce, for outbound connections, that `handshake_data.addrbytes/port` matches `self.peer_addrbytes/self.peer_port` (modulo the "anynet" self-unaware-IP exception), regardless of whether a public key is already known. Only skip the address check for inbound connections, where the dialed address is not authoritative for the peer's public address.

### Proof of Concept
Rust net test plan (in `stackslib/src/net/chat.rs` tests, alongside existing `convo_handshake_*` tests):
1. Set up `convo_1` (outbound, dialing "peer_2" at address A, port P) and `convo_2` representing the real remote peer at A:P, per existing test harness patterns (`test_convo_handshake_accept` style, e.g. `stackslib/src/net/chat.rs:3485+`).
2. Instead of having `convo_2` send back a `HandshakeAccept`, have it send a fresh, signed `Handshake` message with `HandshakeData.addrbytes` set to an unrelated IP `B` (e.g., `10.9.8.7`) and `port` different from A:P, before `convo_1`'s public key has been set (`convo_1.connection.get_public_key()` is `None`).
3. Feed this message into `convo_1.chat(...)` (which will hit `handle_unauthenticated_control_message` → `handle_handshake`).
4. Assert that `validate_handshake` does not return `Err(InvalidHandshake)` despite `handshake_data.addrbytes != convo_1.peer_addrbytes`.
5. After `handle_handshake` runs (with `updated=true && convo_1.stats.outbound=true`), query `PeerDB::get_peer(peerdb_conn, network_id, &B, port_B)` and assert a row now exists with `public_key` equal to convo_2's real public key but `addrbytes/port == B`, proving the frontier table now binds a proven key to an unproven, attacker-chosen address — while no row for the actually-dialed address A necessarily reflects this key.
