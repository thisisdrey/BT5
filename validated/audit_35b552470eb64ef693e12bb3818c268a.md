## Analysis

The Sherlock report on `getSupplyRate()` describes a **missing zero-check before division** that lets a boundary value of an on-chain parameter (`reserveFactorMantissa == 1e18`) make the denominator zero and the call revert.

The same bug class exists in `EnergyProcessor.calculateGlobalEnergyLimit()`, which is reachable from any smart-contract execution (`TriggerSmartContract`), since it is invoked from `useEnergy()` on every energy-consuming transaction.

### Title
Division-by-zero guard bypassed in `EnergyProcessor.calculateGlobalEnergyLimit()` when `allowNewReward` is disabled - (File: `chainbase/src/main/java/org/tron/core/db/EnergyProcessor.java`)

### Summary
`calculateGlobalEnergyLimit()` is supposed to guard against `totalEnergyWeight == 0` before dividing by it, but the guard is only active when `dynamicPropertiesStore.allowNewReward()` is true. In the `false` branch it falls back to a Java `assert`, which is a no-op in production JVMs (assertions are disabled by default), so execution proceeds straight into a division by `totalEnergyWeight` even if it is zero.

### Finding Description [1](#0-0) 

```java
public long calculateGlobalEnergyLimit(AccountCapsule accountCapsule) {
    long frozeBalance = accountCapsule.getAllFrozenBalanceForEnergy();
    if (dynamicPropertiesStore.supportUnfreezeDelay()) {
      return calculateGlobalEnergyLimitV2(frozeBalance);
    }
    if (frozeBalance < TRX_PRECISION) {
      return 0;
    }

    long totalEnergyLimit = dynamicPropertiesStore.getTotalEnergyCurrentLimit();
    long totalEnergyWeight = dynamicPropertiesStore.getTotalEnergyWeight();
    if (dynamicPropertiesStore.allowNewReward() && totalEnergyWeight <= 0) {
      return 0;
    } else {
      assert totalEnergyWeight > 0;
    }
    if (hardenCalculation()) {
      return calculateGlobalLimitV1(frozeBalance, totalEnergyLimit, totalEnergyWeight);
    }
    long energyWeight = frozeBalance / TRX_PRECISION;
    return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
}
```

- When `allowNewReward()` is `false`, the `if` branch is skipped and only `assert totalEnergyWeight > 0` runs — a statement that is compiled out / disabled unless the JVM is started with `-ea`, which production nodes are not. This mirrors the union report's missing `require` before the division.
- If `hardenCalculation()` is enabled, `calculateGlobalLimitV1()` performs a `BigInteger` division by `totalEnergyWeight`, which throws `ArithmeticException` (`/ by zero`) when the weight is zero — directly analogous to `getSupplyRate()` reverting. This is confirmed by `RepositoryImplHardenTest.testUsageToBalanceOverflowDetectedWithHardening` demonstrating the hardened math path throws `ArithmeticException` on similar zero/overflow inputs: [2](#0-1) 
- When `hardenCalculation()` is disabled, the fallback `double` arithmetic `(double) totalEnergyLimit / totalEnergyWeight` with `totalEnergyWeight == 0` evaluates to `Infinity` (not an exception), and the subsequent cast `(long)` truncates `Infinity` to `Long.MAX_VALUE`. `calculateGlobalEnergyLimit()` is called directly from `useEnergy()`: [3](#0-2) 

`useEnergy()` is executed on every smart-contract call, and any account with `getAllFrozenBalanceForEnergy() >= TRX_PRECISION` reaches this code path. Note the sibling function `calculateGlobalEnergyLimitV2` (used when `supportUnfreezeDelay()` is active) properly guards with an unconditional `if (totalEnergyWeight == 0) return 0;` before any math, confirming that the guard in the legacy `calculateGlobalEnergyLimit()` is the outlier: [4](#0-3) 

The V1 (non-V2) path is exercised whenever `dynamicPropertiesStore.supportUnfreezeDelay()` is not yet active, i.e., in the current/legacy freeze model still in production use by many accounts that froze balance before the V2 unfreeze-delay feature was proposed.

### Impact Explanation
- Hardened-math nodes: an `ArithmeticException` is thrown mid-transaction-execution inside `useEnergy()`, which is called from the actuator/TVM execution pipeline for any `TriggerSmartContract` transaction from an unprivileged account, potentially causing unhandled exceptions to propagate through block application (`Manager`), which is a node-crash / chain-halt risk if not caught uniformly across all callers.
- Non-hardened nodes: the resulting `energyLimit` of `Long.MAX_VALUE` effectively removes the resource limit for that account inside `useEnergy()`'s check `energy > (energyLimit - newEnergyUsage)`, letting the account consume unbounded energy without ever falling back to burning TRX for energy overage — an unbacked resource/accounting break in the fee model.

### Likelihood Explanation
Requires `totalEnergyWeight == 0` while an individual account still has `frozenBalance >= TRX_PRECISION` in the legacy (non-V2) freeze model with `allowNewReward()` false and `supportUnfreezeDelay()` false. This is a narrow, state-dependent edge case (mainnet has long since activated `allowNewReward`/`supportUnfreezeDelay`), so likelihood is low on current mainnet but the code path remains live and reachable by any regular account transaction if that network state combination recurs (e.g., private/test chains, or future proposal rollbacks).

### Recommendation
Move the zero-check for `totalEnergyWeight` outside the `allowNewReward()` condition, i.e., unconditionally `if (totalEnergyWeight <= 0) { return 0; }` before any division, matching the pattern already used in `calculateGlobalEnergyLimitV2` and `BandwidthProcessor.calculateGlobalNetLimit`. Do not rely on `assert` for correctness in production code paths.
