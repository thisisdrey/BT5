## Title
Committee-gated `CancelAllUnfreezeV2` governance flag is enforced in the transaction actuator but not in the TVM native-contract path, letting any smart contract bypass the governance lock - (File: actuator/src/main/java/org/tron/core/vm/nativecontract/CancelAllUnfreezeV2Processor.java)

### Summary
Java-tron gates the `CancelAllUnfreezeV2` capability behind a committee-controlled dynamic property, `AllowCancelAllUnfreezeV2`, which must be explicitly turned on by a committee proposal before ordinary users can broadcast the corresponding transaction type. This mirrors the JupyterLab advisory's "administrator lock rule" concept — a feature that is supposed to remain disabled/restricted until an authority (the committee) permits it. However, the check for this specific flag exists only in the transaction-level actuator, not in the TVM native-contract processor that implements the same logic for smart-contract callers.

### Finding Description
`CancelAllUnfreezeV2Actuator.validate()` explicitly checks the committee-controlled flag before allowing the operation: [1](#0-0) 

This is the "lock rule" set by the administrator/committee — the same pattern as JupyterLab's plugin lock, where an authority must explicitly enable a capability before ordinary clients can use it.

The same feature is also reachable from any deployed smart contract via a TVM native/precompiled action, `Program.cancelAllUnfreezeV2Action()`, which delegates directly to `CancelAllUnfreezeV2Processor`: [2](#0-1) 

But `CancelAllUnfreezeV2Processor.validate()` never checks `dynamicStore.supportAllowCancelAllUnfreezeV2()` — it only validates the address, account existence, and the invalid-delegated-V2 fork guard: [3](#0-2) 

Compare this directly with the sibling `CancelAllUnfreezeV2Actuator.validate()` which is the only place that references `supportAllowCancelAllUnfreezeV2()` in the whole codebase's cancel-all-unfreeze logic path (per the enumeration of references, the flag only appears in the actuator, the dynamic-properties store, `ProposalService`, and tests — never in the VM processor). This is exactly the same bug class as GHSA-h5v5-8746-g7mm: an authority-set restriction is enforced at one API entry point (the ordinary `CancelAllUnfreezeV2Contract` transaction / actuator) but not at another functionally-equivalent entry point (the TVM opcode reachable by any contract), letting an unprivileged caller circumvent it.

### Impact Explanation
If the committee has not yet passed the `AllowCancelAllUnfreezeV2` proposal (i.e., the feature is intentionally disabled network-wide), any contract can still invoke this state-changing native action through the VM opcode, canceling pending unfreeze operations and re-locking/rewarding balances that should not be movable through this mechanism yet. This creates a governance bypass where a smart-contract caller gets access to functionality the network operators have deliberately withheld from regular accounts, and could alter total resource weight accounting (`addTotalNetWeight`/`addTotalEnergyWeight`) and account state (`clearUnfrozenV2`, balance credits) in ways inconsistent with the intended hard-fork/feature rollout, potentially causing divergent behavior between the actuator-only expectations and TVM-reachable outcomes. This is a Medium-severity integrity/authorization gap, consistent with the CWE-863 classification in the analog advisory.

### Likelihood Explanation
Any account can deploy a contract that calls the corresponding precompile/opcode to invoke `Program.cancelAllUnfreezeV2Action()`, requiring no special privileges — only that the general `supportDR`/`supportUnfreezeDelay`-style hardfork gating for the opcode itself (checked elsewhere at the VM operation level) is active, which is a broader, unrelated activation than the specific `AllowCancelAllUnfreezeV2` committee toggle. During any window where the general freeze-v2/stake-v2 VM features are enabled but the specific `AllowCancelAllUnfreezeV2` proposal has not yet passed, this path is exploitable by any caller with no signature/permission requirements beyond normal contract execution.

### Recommendation
Add the same `dynamicStore.supportAllowCancelAllUnfreezeV2()` check to `CancelAllUnfreezeV2Processor.validate()` that exists in `CancelAllUnfreezeV2Actuator.validate()`, throwing `ContractValidateException` when the committee has not enabled the feature — mirroring how `supportDR()`/`supportUnfreezeDelay()` are duplicated between `DelegateResourceActuator` and `DelegateResourceProcessor`.

### Proof of Concept
1. Deploy a contract that invokes the TVM `CANCELALLUNFREEZEV2` operation (reaching `Program.cancelAllUnfreezeV2Action()`).
2. On a network/state where `DynamicPropertiesStore.supportAllowCancelAllUnfreezeV2()` returns false (committee proposal not yet enabled) but the underlying freeze-v2 VM opcode set is otherwise active.
3. Observe that `CancelAllUnfreezeV2Actuator`-based transactions are rejected with `"Not support CancelAllUnfreezeV2 transaction, need to be opened by the committee"` per [1](#0-0) , while the contract call to `cancelAllUnfreezeV2Action()`/`CancelAllUnfreezeV2Processor.validate()` succeeds because it never inspects this flag, per [3](#0-2) , demonstrating the bypass of the committee-imposed restriction.

    if (Objects.isNull(accountCapsule)) {
