### Title
Unbounded array allocation in `ValidateMultiSign` precompile causes uncaught `OutOfMemoryError` / node crash - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The Mealie report describes a DoS where an attacker-controlled size value drives an unbounded resource fetch that OOMs the process. The direct java-tron analog is the `ValidateMultiSign` TVM precompile (address `0x…0a`), reachable from any smart-contract `CALL`, which allocates a `byte[len][]` array sized directly from attacker-controlled calldata **before** any size validation or exception handling is in place, when the `allowTvmSelfdestructRestriction` chain parameter is not active.

### Finding Description
`ValidateMultiSign.execute()` extracts the signature array from the caller-supplied calldata: [1](#0-0) 

When `VMConfig.allowTvmSelfdestructRestriction()` is `false` (its default/pre-activation state on any chain — public or private — that has not yet enabled the corresponding TIP), the `sigArraySize` bound check is skipped entirely, and `signatures` is built by `extractBytesArray`, not the safer `extractSigArray`: [2](#0-1) 

`extractBytesArray` reads `len` straight from a `DataWord` under full attacker control (`words[offset].intValueSafe()`) and immediately allocates `new byte[len][]` with **no upper bound**:
```
int len = words[offset].intValueSafe();
byte[][] bytesArray = new byte[len][];
```
`intValueSafe()` clamps overflowing 256-bit values to `Integer.MAX_VALUE` rather than rejecting them, so an attacker can set this length word to `0x7fffffff`, forcing an attempted allocation of ~2^31 object references (tens of gigabytes on a 64-bit JVM) in a single statement.

Crucially, unlike the sibling precompile `BatchValidateSign` — whose entire `doExecute()` body is wrapped in `catch (Throwable t)`: [3](#0-2) 

`ValidateMultiSign.execute()` has **no such outer guard**. Its only `try/catch` wraps the later permission-weight-calculation block, not the `extractBytesArray` call that performs the allocation: [4](#0-3) 

The subsequent length check (`signatures.length == 0 || signatures.length > MAX_SIZE`) executes only *after* the array has already been allocated, so it cannot prevent the OOM — the allocation attempt has already occurred.

### Impact Explanation
An `OutOfMemoryError` thrown from a precompile executed inside `Program.callToPrecompiledAddress` is an `Error`, not an `Exception`. It is not guaranteed to be caught by the generic `catch (Exception e)` handlers used throughout the actuator/transaction-processing pipeline (contract validate/execute, `TransactionTrace`, `Runtime`), so it can propagate up into block application in `Manager`, terminating the block-processing thread or destabilizing/crashing the entire node JVM. Because the trigger only requires deploying/calling a contract that issues a single `CALL` to precompile address `0x…0a` with crafted calldata, it is reachable by any unprivileged contract deployer or transaction broadcaster — no special permissions required. This matches the Mealie DoS impact class: an unauthenticated/low-privilege actor can force resource exhaustion severe enough to crash the target service.

### Likelihood Explanation
Exploitation requires only:
1. Deploying (or reusing) a contract that performs a `CALL` to the `validateMultiSign` precompile address.
2. Crafting the ABI-encoded calldata so the "signature array length" word decodes to a very large 32-byte integer.
3. Sending this as a normal `TriggerSmartContract` transaction while the chain has not yet activated `allowTvmSelfdestructRestriction` (the pre-TIP-854/selfdestruct-restriction hard-fork state).

No privileged role, race condition, or complex setup is needed — a single crafted transaction is sufficient, making this straightforward for any transaction broadcaster to trigger on affected chains/heights.

### Recommendation
- In `extractBytesArray`/`extractBytes32Array`/`extractSigArray`, validate `len` against a hard maximum (e.g., `MAX_SIZE`) **before** allocating any array, regardless of the `allowTvmSelfdestructRestriction` flag state.
- Move the `sigArraySize`/length bound check in `ValidateMultiSign.execute()` outside the `allowTvmSelfdestructRestriction` gate so it always runs prior to array extraction.
- Wrap precompile execution (or at minimum the array-extraction call sites) in a `catch (Throwable)` boundary consistent with `BatchValidateSign`, ensuring any allocation failure degrades to a safe revert/false-result rather than propagating an `Error` up through block application.

### Proof of Concept
1. On a network/height where `allowTvmSelfdestructRestriction` is not yet enabled, deploy a minimal contract that performs:
   ```solidity
   address(0x000000000000000000000000000000000000000a).call(payload);
   ```
2. Build `payload` as ABI-encoded input matching `validatemultisign(address,uint256,bytes32,bytes[])` where the dynamic-array length word for the `bytes[]` parameter is set to `0x7fffffff` instead of a real array length.
3. Broadcast a `TriggerSmartContract` transaction invoking this call.
4. Inside `ValidateMultiSign.execute()`, `extractBytesArray` computes `len = 0x7fffffff` and executes `new byte[len][]`, triggering an uncaught `OutOfMemoryError` that propagates out of the precompile call with no surrounding `catch(Throwable)`, exactly as shown at [5](#0-4) .
