### Title
Global concurrent-connection budget can be exhausted by an attacker holding many stalled QUIC handshakes open for just under the 2s handshake timeout, starving legitimate connection acceptance - (File: streamer/src/nonblocking/quic.rs)

### Summary
The QUIC accept path in `run_server`/`setup_connection` reserves a slot from a single, IP-agnostic `ClientConnectionTracker`/`max_concurrent_connections()` budget for every incoming connection attempt before the TLS handshake completes, and neither the per-IP `ConnectionRateLimiter` nor the global `overall_connection_rate_limiter` throttle attempts that never finish handshaking. An attacker who opens many parallel QUIC connections and deliberately stalls each handshake for just under `QUIC_CONNECTION_HANDSHAKE_TIMEOUT` (2s) can keep the shared concurrent-connection budget pinned, causing `ClientConnectionTracker::new` to fail for legitimate incoming connections from any IP.

### Finding Description
In `run_server` (`streamer/src/nonblocking/quic.rs:304-411`), each incoming `Incoming` first passes two rate checks and then reserves a global slot: [1](#0-0) 

- The global `overall_connection_rate_limiter` (a `TokenBucket`) is only checked for `current_tokens() == 0`; its tokens are consumed only in `setup_connection` after a *successful* handshake (`overall_connection_rate_limiter.consume_tokens(1)` at line 495 of `setup_connection`). A stalled/never-completing handshake never consumes a token, so this limiter provides no throttling against attempt floods that don't finish. [2](#0-1) 

- The per-IP `ConnectionRateLimiter::is_allowed` (`streamer/src/nonblocking/connection_rate_limiter.rs:34-40`) only checks the token bucket associated with an IP that has previously *registered* a completed connection; for an IP with no such record it unconditionally returns `true`. `register_connection` (which is the only thing that decrements this bucket) is called only after a successful handshake in `setup_connection` (line 483). A stalled handshake therefore never registers and never trips this limiter either, no matter how many parallel stalled handshakes are opened from the same source IP. [3](#0-2) 

- The only actual admission control that gates before the handshake completes is `ClientConnectionTracker::new(stats.clone(), qos.max_concurrent_connections())`, which compares a single global atomic `stats.open_connections` counter against `qos.max_concurrent_connections()` — a value derived from `(max_staked_connections + max_unstaked_connections) * 5 / 4` (SWQoS) shared across *all* IPs and connection states (in-flight handshakes and fully-open connections alike). [4](#0-3) [5](#0-4) 

- `setup_connection` waits up to `QUIC_CONNECTION_HANDSHAKE_TIMEOUT` (2 seconds) for the handshake, holding the `ClientConnectionTracker` (and thus the global slot) the whole time, before decrementing `outstanding_incoming_connection_attempts` and finally releasing the slot on `Drop`. [6](#0-5) 

Because the global slot count is not partitioned per IP, an attacker only needs to keep enough concurrent half-open QUIC handshakes in flight (each individually below 2s) to reach `max_concurrent_connections()`. Once reached, `ClientConnectionTracker::new` returns `Err`, and every subsequent `incoming` (from any IP, staked or unstaked) is refused via `incoming.refuse()`, incrementing `refused_connections_too_many_open_connections`. The per-IP and global rate limiters, which are the documented mitigation ("cap total connections per-peer/ip", comment at lines 332-341), never fire because they key off successfully completed handshakes, not attempts.

### Impact Explanation
This is a pre-authentication resource-exhaustion / denial-of-service vector on the TPU QUIC endpoint: an unstaked, unprivileged remote attacker can starve legitimate transaction-submission connections (staked and unstaked) from reaching the leader, without needing to pass sigverify, staking, or any privileged state. It matches the Agave "node liveness/DoS" bounty category for network-facing ingress components (resource exhaustion causing legitimate traffic starvation), scoped strictly to `streamer/src/nonblocking/quic.rs` connection admission logic.

### Likelihood Explanation
Feasibility is high: the attacker needs no stake, no keys, and no special network position — only the ability to open many parallel QUIC connections to the leader's public TPU port and intentionally stall each TLS handshake (e.g., send only an Initial packet and never complete the flight, or delay the final handshake packet) for slightly less than 2 seconds, then repeat. The attack is trivially repeatable and only bounded by the attacker's own connection/bandwidth capacity to keep `max_concurrent_connections()` worth of handshakes perpetually "almost done." No cluster-wide coordination or multiple distinct IPs are strictly required if the per-IP limiter doesn't block pending (unregistered) attempts, though spreading across many source ports/IPs further avoids any peripheral per-IP behavior.

### Recommendation
Bound the number of concurrent *in-flight, unauthenticated* handshakes per source IP (not just per completed connection), e.g., by tracking pending accepts in the `ConnectionRateLimiter` (or a separate concurrency-limited map) keyed by IP and decrementing on both success and timeout/failure, so a single IP cannot occupy an unbounded/majority share of the global `max_concurrent_connections()` budget. Additionally, make the `overall_connection_rate_limiter` consume a token at accept time (before handshake) rather than only on success, so stalled attempts are throttled just like completed ones.

### Proof of Concept
Integration test plan (using existing `setup_quic_server`/`make_client_endpoint` test harness in `streamer/src/nonblocking/quic.rs` tests):
1. Configure `SwQosConfig` with a small `max_unstaked_connections`/`max_staked_connections` (e.g., 4) so `max_concurrent_connections()` is small and reachable.
2. From "attacker" client endpoints, open `max_concurrent_connections()` QUIC connections to the server but withhold completion of the TLS handshake (e.g., use a client `Connecting` future without awaiting it to completion, or inject artificial delay via a custom transport that never sends the final Handshake packet) — keep them pending just under 2s, then repeat in a loop for several seconds.
3. Concurrently, from a distinct "legitimate" client IP/socket, attempt to `make_client_endpoint` and complete a real handshake.
4. Assert: while the attacker's stalled connections are cycling, `stats.refused_connections_too_many_open_connections` increases and the legitimate client's connection either times out or is refused (`incoming.refuse()`), demonstrating the completion rate for the legitimate IP drops to zero/below an acceptable floor despite it never violating `ConnectionRateLimiter::is_allowed` or `register_connection` itself.

impl ClientConnectionTracker {
    /// Check the max_concurrent_connections limit and if it is within the limit
    /// create ClientConnectionTracker and increment open connection count. Otherwise returns Err
    fn new(stats: Arc<StreamerStats>, max_concurrent_connections: usize) -> Result<Self, ()> {
        let open_connections = stats.open_connections.fetch_add(1, Ordering::Relaxed);
        if open_connections >= max_concurrent_connections {
            stats.open_connections.fetch_sub(1, Ordering::Relaxed);
            debug!(
                "There are too many concurrent connections opened already: open: \
                 {open_connections}, max: {max_concurrent_connections}"
            );
            return Err(());
        }

        Ok(Self { stats })
    }

    /// Check if the connection from the said `ip` is allowed.
    /// Here we assume that only IPs with actual confirmed connections are stored in it,
    /// since we should only modify server state once source IP is verified
    pub fn is_allowed(&self, ip: &IpAddr) -> bool {
        // Check if we have records in the rate limiter for the given IP address
        match self.limiter.current_tokens(ip) {
            Some(r) => r > 0, // we have a record, and rate is not exceeded
            None => true,     // if we have not seen IP, allow connection request
        }
    }

    pub fn register_connection(&self, ip: &IpAddr) -> bool {
        if self.limiter.consume_tokens(*ip, 1).is_ok() {
            debug!("Request from IP {ip:?} allowed");
            true // Request allowed
        } else {
            debug!("Request from IP {ip:?} blocked");
            false // Request blocked
        }
    }
