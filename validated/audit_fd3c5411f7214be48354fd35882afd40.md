### Title
Attacker can dust-fill a victim's per-account token list to `MAX_TOKENS_PER_USER`, DoS-ing deposits, issuance, and collateral top-ups during liquidation - (File: contracts/Pool.sol)

### Summary
`Pool` tracks every `DepositToken`/`DebtToken` an account has ever touched in `depositTokensOfAccount` / `debtTokensOfAccount`, capped at `MAX_TOKENS_PER_USER = 30`. `DepositToken._transfer` calls `pool.addToDepositTokensOfAccount(recipient_)` whenever a recipient's balance goes from `0` to non-zero, and `Pool.addToDepositTokensOfAccount` hard-reverts with `UserReachedMaxTokens` once the combined list length reaches 30. Since `DepositToken.transfer`/`transferFrom` are permissionless and anyone can transfer msdTokens to an arbitrary victim, an unprivileged attacker can dust-spam a victim with 1-wei transfers across all listed deposit tokens, filling their list and bricking every subsequent action that would add a new token type to the account. ### Finding Description
1. `DepositToken._transfer` adds the token to `pool.depositTokensOfAccount[recipient]` whenever `_recipientBalanceBefore == 0 && amount_ > 0` (DepositToken.sol:518-520). There is no minimum amount and no opt-in on the recipient side — `transfer(to, 1)` suffices.
2. `Pool.addToDepositTokensOfAccount` enforces `debtTokensOfAccount.length(account_) + depositTokensOfAccount.length(account_) >= MAX_TOKENS_PER_USER` → `UserReachedMaxTokens` (Pool.sol:143-146, 216-220).
3. The same cap guards `addToDebtTokensOfAccount` (Pool.sol:204-208), which `DebtToken` calls on `issue`/transfer minting paths, and `_mint` in `DepositToken` likewise registers the token for first-time recipients.
4. The pool's deposit token list itself is capped at `MAX_TOKENS_PER_USER` (`addDepositToken`, Pool.sol:703), so an attacker only needs ~30 distinct dust transfers — one per registered deposit token — costing a handful of wei of each underlying.

Once the victim's list is full:
- `DepositToken.deposit(amount, onBehalfOf_ = victim)` for any *new* collateral type reverts inside `_mint`/`addToDepositTokensOfAccount`, and `transfer`/`transferFrom` of any new deposit token to the victim reverts in `addToDepositTokensOfAccount`. The victim (or a rescuer) cannot top up the position with a different collateral while it approaches liquidation.
- `DebtToken.issue`/`DebtToken.mint` for a debt-token type not already in the victim's list reverts via `addToDebtTokensOfAccount`, blocking new borrowing and `SmartFarmingManager.leverage` flows that mint a new debt token type.
- Removal requires the victim to transfer out the *entire* dust balance of each poisoned token (`removeFromDepositTokensOfAccount` only fires when `balanceOf[sender] == 0`, DepositToken.sol:522-525), and each such removal itself is exposed to re-filling in the same block.

No governor/guardian action is needed, and none of `whenNotPaused`, `whenNotShutdown`, `nonReentrant`, `SynthContext` forwarding, or supply caps mitigate it: the check is executed inside the token's own transfer path.

### Impact Explanation
Temporary freezing of funds / griefing DoS against a targeted account (the analog of the CVE's "complete DoS of the server" for a victim's position). Concretely: a victim approaching liquidation cannot receive a rescue deposit of a different collateral type (`deposit(x, victim)` and `transfer(victim, x)` revert), and cannot issue a different synthetic to repay or hedge, while `Pool.liquidate` still works — the attacker's dust positions don't impede `seize` because seizure transfers *from* the victim. The victim can only escape by locating and fully zeroing each dust balance, paying gas per token and racing re-griefing. Positions using only already-listed tokens remain partially functional, so impact is bounded to new-token-type operations, matching a Medium availability finding.

### Likelihood Explanation
The attack is fully permissionless: it requires only public `DepositToken.transfer`/`transferFrom`/`deposit(amount, victim)` calls with dust amounts of whitelisted collateral tokens. Cost is ~30 low-value transfers; no privileged role, no oracle manipulation, no timing dependency. The only prerequisites are that the pool has multiple deposit tokens registered (the deployed configuration lists several) and the victim hasn't already filled their own list. A rational attacker gains by blocking a competitor's/refinancer's rescue deposit during a liquidation cascade, or griefing leveraged-position users of `SmartFarmingManager`.

### Recommendation
- Do not add a token to `depositTokensOfAccount`/`debtTokensOfAccount` for de-minimis amounts, or allow the *account itself* to remove entries (e.g., a `Pool.removeTokenFromAccount(token)` that verifies `balanceOf == 0`-equivalent semantics or lets users force-remove dust under a threshold).
- Alternatively, make `transfer`/`transferFrom`/`deposit` not register the recipient unless the recipient opts in (pull-based registration on `issue`), or decouple the list-cap revert from the token transfer so dust receipts never brick an account.
- At minimum, let `seize`/liquidation-path transfers bypass the cap so griefing cannot interfere with solvency-critical flows.

### Proof of Concept
Hardhat (fork or local deployment) sketch — reproducible with the existing `test/DepositToken.test.ts` fixture style (real `Pool`, real `DepositToken`s, `feeProvider`):

```ts
// setup: pool with >=2 registered DepositTokens msdA, msdB (up to 30);
// victim has an open position (deposit + issued debt) but <30 list entries.

// 1) Attacker dust-fills victim's list
for (const dt of depositTokens) {
  // dt = each registered DepositToken
  await dt.connect(attacker).deposit(10, attacker.address)   // tiny amount
  await dt.connect(attacker).transfer(victim.address, 1)     // 1 wei dust
}
const len = (await pool.getDepositTokensOfAccount(victim.address)).length
          + (await pool.getDebtTokensOfAccount(victim.address)).length;
expect(len).to.eq(await pool.MAX_TOKENS_PER_USER());

// 2) Victim (or rescuer) tries to add a new collateral type -> reverts
await underlying.msdNew.mint(rescuer.address, parseEther('10'));
await underlying.connect(rescuer).approve(msdNew.address, MaxUint256);
await expect(msdNew.connect(rescuer).deposit(parseEther('10'), victim.address))
  .to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens'); // bubbles up through _mint/add

// transfer of a new deposit token to the victim also reverts
await expect(msdNew.connect(attacker).transfer(victim.address, 1))
  .to.be.reverted; // addToDepositTokensOfAccount -> UserReachedMaxTokens

// 3) Victim cannot issue a new synthetic debt type either
await expect(msXDebt.connect(victim).issue(1, victim.address))
  .to.be.reverted; // addToDebtTokensOfAccount -> UserReachedMaxTokens

// 4) Meanwhile liquidation still functions: position is unhealthy, liquidator seizes
await pool.connect(liquidator).liquidate(msUSD.address, victim.address, repayAmt, msdA.address);
// succeeds -> victim's collateral is lost while rescue/top-up path was bricked
```

Note: only the `deposit`/`transfer` registration path was fully traced; the exact `_mint`-time registration call in `DepositToken._mint` (line ~469+) was partially shown in the index — the PoC should confirm whether it calls `addToDepositTokensOfAccount` directly or relies on `_transfer`-equivalent logic, but either way the cap revert is reachable from `deposit` for first-time recipients.
