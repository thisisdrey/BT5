### Title
Out-of-bounds panic in `readArmap` when parsing a malformed archive symbol table - ([File: src/cmd/link/internal/ld/ar.go])

### Summary
`cmd/link`'s `readArmap` in `ar.go` parses the archive symbol map (`armap`) of a host archive (e.g. a `.a` static library) without validating that each embedded name string is NUL-terminated within the bounds of the buffer. Similar to the Chainlink `getStartingRoundId` bug — which assumes every intermediate "phase" is well-formed and reverts/DOSes when it is not — `readArmap` assumes every one of the `c` symbol-name entries is properly NUL-terminated inside `contents`, and has no bounds check while scanning for the terminator.

### Finding Description
`hostArchive` (`src/cmd/link/internal/ld/ar.go:103`) opens a host archive file supplied to the linker (for example a static library referenced via cgo `LDFLAGS`/`-l` linking, which can originate from a module's own source tree) and, upon finding an armap member (`"/"` or `"/SYM64/"`), calls `readArmap` [1](#0-0) .

Inside `readArmap`, the code reads a symbol count `c`, then walks `names`, scanning byte-by-byte for a `0` terminator with no bound on `n`:
```go
names := contents[c*uint64(wordSize):]
for i := uint64(0); i < c; i++ {
    n := 0
    for names[n] != 0 {
        n++
    }
    name := string(names[:n])
    names = names[n+1:]
    ...
}
``` [2](#0-1) 

If the attacker-crafted archive declares a symbol count `c` (e.g. `1`) but the corresponding name bytes in `contents` never contain a `0` byte before the slice ends, the inner `for names[n] != 0` loop runs past the end of `names` and Go's runtime bounds check panics with `index out of range` — an uncontrolled crash of the `go build`/linker process. This mirrors the analog bug class: code that assumes structural well-formedness of intermediate/embedded data (Chainlink assumed intermediate phases are valid; here the linker assumes every symbol name is properly NUL-terminated) and has no defensive check, causing failure/DOS instead of a graceful error.

### Impact Explanation
A malicious module/package that ships a crafted static archive (`.a` file) consumed via cgo host-object linking can crash the `go build` process with an unrecoverable panic when the linker parses the archive's symbol map. This is a build-time DoS of the toolchain when processing untrusted source/build artifacts — analogous to, though less severe than, the original finding's application-wide DOS. Under Go's vulnerability policy this would likely be treated as a low-severity toolchain robustness issue (a crash, not code execution or data corruption), so I'd flag it PUBLIC/low rather than urgent, given `go build` is documented to only compile trusted source but is still expected not to crash ungracefully on malformed auxiliary binary inputs it chooses to parse.

### Likelihood Explanation
The victim workflow is `go build` (or `go test`) on a package that uses cgo external linking against a static archive under the attacker's control (e.g., a vendored `.a` file inside a dependency's directory, referenced via `#cgo LDFLAGS: -L. -lfoo`). The attacker only needs to control the archive's bytes — no privileged access, network position, or execution required; the object-file/archive header fields (`size`, name-table bytes) are attacker-controlled inputs consumed directly by `readArmap`.

### Recommendation
Add explicit bounds checking while scanning for the NUL terminator in `readArmap`, and fail with a clear `Exitf`/error (matching the existing error-handling style in `ar.go`) instead of allowing an unchecked out-of-bounds slice access, e.g.:
```go
for n < len(names) && names[n] != 0 {
    n++
}
if n >= len(names) {
    Exitf("%s: malformed archive symbol map", filename)
}
```
Apply the same bound check to the surrounding `contents`/`off` reads in the loop.

### Proof of Concept
```go
package ld

import (
	"encoding/binary"
	"os"
	"testing"

	"cmd/internal/bio"
)

// TestReadArmapPanicsOnUnterminatedName demonstrates that readArmap panics
// with an out-of-bounds slice access when the archive's symbol name table
// lacks a NUL terminator for a declared symbol count.
func TestReadArmapPanicsOnUnterminatedName(t *testing.T) {
	var buf []byte

	// symbol count = 1
	countBytes := make([]byte, 4)
	binary.BigEndian.PutUint32(countBytes, 1)
	buf = append(buf, countBytes...)

	// one offset entry
	offBytes := make([]byte, 4)
	binary.BigEndian.PutUint32(offBytes, 100)
	buf = append(buf, offBytes...)

	// name bytes with NO NUL terminator before the buffer ends
	buf = append(buf, []byte("foo")...)

	f, err := os.CreateTemp(t.TempDir(), "ar")
	if err != nil {
		t.Fatal(err)
	}
	if _, err := f.Write(buf); err != nil {
		t.Fatal(err)
	}
	f.Seek(0, 0)
	rdr := bio.NewReader(f)

	defer func() {
		if r := recover(); r == nil {
			t.Fatalf("expected panic (index out of range) due to unterminated symbol name, got none")
		}
	}()

	hdr := ArHdr{name: "/", size: "7"} // len(buf) == 4+4+3 == 11 in real case; adjust to match crafted size
	readArmap("malformed.a", rdr, hdr)
}
```
Expected result: the call to `readArmap` panics with `runtime error: index out of range` instead of returning a clean error, confirming the missing bounds check on the name-table scan.
