### Title
Uncaught `ArrayIndexOutOfBoundsException` in `ValidateMultiSign` precompile crashes/aborts transaction execution on malformed calldata pre-TIP-854 activation - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `ValidateMultiSign` precompiled contract (address reachable via TVM `CALL`/`STATICCALL`/`DELEGATECALL` from any deployed smart contract) parses its input into a `DataWord[]` array and immediately indexes into it (`words[0]`, `words[1]`, `words[2]`, `words[3]`, and later `words[words[3]...]`) without verifying the array is long enough, unless the `allowTvmOsaka` (TIP-854) hard-fork flag is active. Any transaction that supplies calldata shorter than the minimum required header (5 words) triggers an uncaught `ArrayIndexOutOfBoundsException` that propagates out of `execute()` with no local `try/catch`, unlike its sibling `BatchValidateSign`, which wraps the equivalent logic in `try { doExecute(...) } catch (Throwable t) { ... }`.

### Finding Description
`ValidateMultiSign.execute()` [1](#0-0)  only performs the ABI-length sanity check `isValidAbiEncoding(...)` when `VMConfig.allowTvmOsaka()` is enabled:
```
if (VMConfig.allowTvmOsaka()
    && !isValidAbiEncoding(rawData, ABI_HEADER_WORDS, ABI_ITEM_WORDS)) {
  return Pair.of(false, EMPTY_BYTE_ARRAY);
}
DataWord[] words = DataWord.parseArray(rawData);
byte[] address = words[0].toTronAddress();
int permissionId = words[1].intValueSafe();
byte[] data = words[2].getData();
...
int sigArraySize = words[words[3].intValueSafe() / WORD_SIZE].intValueSafe();
```
When Osaka is not active (the pre-hardfork/legacy configuration), any caller who invokes the precompile with fewer than 5 32-byte words of calldata causes `words` to be shorter than 4 elements, and the unconditional `words[3]` (or `words[1]`) access throws `ArrayIndexOutOfBoundsException`. There is no local `catch` in this method — contrast with `BatchValidateSign.execute()` at lines 1144-1154, which explicitly wraps the equivalent logic in `try { return doExecute(data); } catch (Throwable t) { ... return Pair.of(true, new byte[WORD_SIZE]); }`.

The unguarded exception then propagates to `Program.callToPrecompiledAddress()` [2](#0-1) , which calls `contract.execute(data)` with no surrounding try/catch of its own around this specific invocation.

This is directly acknowledged by the project's own test `testTip854PreActivationNoOp` in `ValidateMultiSignContractTest.java`, which documents: "this precompile has no outer catch, so a too-short input raises inside the decoder; that is the documented pre-activation failure mode" [3](#0-2) .

This is structurally analogous to the Yauaa `ArrayIndexOutOfBoundsException` advisory: attacker-controlled/short input reaches array indexing code without a length guard, and the resulting runtime exception is not defensively caught at the point of use.

### Impact Explanation
Whether this results in node-level impact depends on whether some outer frame (e.g., `VM.java`'s opcode dispatch loop, or `Runtime.java`) wraps arbitrary `Throwable`/`RuntimeException` during contract execution and converts it into a reverted transaction rather than letting it propagate further (e.g., into block application in `Manager`). I found `catch (Throwable...)` handling inside `VM.java` generically, which is the standard TVM safety net for turning unexpected exceptions into a reverted/failed transaction rather than a node crash — this generic catch is what the `outOfIndexTest`-style tests rely on for other assert-style Solidity errors. If that catch-all in `VM.java` is exhaustive and applies to `CALL` execution of precompiles as well, the practical effect is limited to the calling transaction reverting/failing (denial of service against that single transaction, wasted energy) rather than a node crash. I was not able to fully trace whether `VM.java`'s catch-all specifically wraps the `callToPrecompiledAddress` → `contract.execute()` call chain, or whether some code path (e.g. a constant call / `TriggerConstantContractServlet` via `Wallet`, executed outside the normal VM opcode loop's exception handling) invokes `ValidateMultiSign.execute()` directly without that protection.

Given this uncertainty, the concretely provable impact is: an unauthenithenticated caller (any account able to broadcast a `TriggerSmartContract` transaction, or any deployed contract that forwards a `CALL` to the `ValidateMultiSign` precompile address) can force an `ArrayIndexOutOfBoundsException` deep inside actuator/VM code with a single crafted transaction and minimal energy expenditure, when the `allowTvmOsaka` proposal is not yet activated on the network. This is, at minimum, a reliable "revert everyone's expectations" / unhandled-exception bug in a reachable execution path (matching the CWE-755 "improper handling of exceptional conditions" classification of the reference advisory); whether it escalates to a node crash or halt requires verifying the exact call path used by constant-call (view) invocations of this precompile, which may bypass the VM's opcode-level exception funnel.

### Likelihood Explanation
High likelihood of triggering the underlying defect: constructing calldata shorter than 160 bytes (5×32) is trivial and can be done by any account via a simple `CALL` to the `ValidateMultiSign` precompile address from a contract, or in principle via a constant/view call. The guard exists but is explicitly gated behind the `allowTvmOsaka` feature flag, meaning any network/chain configuration where that proposal has not been activated is exposed by design (this is called out as "legacy/pre-activation behavior" in the maintainers' own tests).

### Recommendation
Remove the `VMConfig.allowTvmOsaka()` gate around the ABI-length validation in `ValidateMultiSign.execute()` so the bounds check `isValidAbiEncoding(...)` (or an equivalent length check before indexing `words[0..3]`) is unconditional, matching `BatchValidateSign`'s defensive pattern. Additionally, wrap `ValidateMultiSign.execute()`'s body in a `try { ... } catch (Throwable t) { return Pair.of(true, DATA_FALSE); }` (mirroring `BatchValidateSign`) so that any future parsing defect fails closed instead of throwing, regardless of hard-fork activation state. Confirm and, if necessary, harden the call path from constant/view RPC calls (`TriggerConstantContract` / `Wallet` / `TronJsonRpcImpl`) into precompiled contracts to guarantee they route through the same exception-catching frame as full transaction execution.

### Proof of Concept
1. On a network/config where `allowTvmOsaka` (TIP-854) is not enabled (the historical default until that proposal activates):
2. Deploy or use any contract that performs `CALL` to the `ValidateMultiSign` precompile address with calldata shorter than 160 bytes (5 words), e.g. `data.length == 32` or `data.length == 0`.
3. `ValidateMultiSign.execute(rawData)` calls `DataWord.parseArray(rawData)`, producing a `words` array with fewer than 4 elements, then executes `words[1].intValueSafe()` / `words[3].intValueSafe()`, throwing `ArrayIndexOutOfBoundsException` with no local catch.
4. This matches the existing repository test `testTip854PreActivationNoOp` [4](#0-3) , which calls `contract.execute(new byte[(5 + 1) * 32])` and explicitly expects/allows a `RuntimeException` to propagate as "the existing behaviour" pre-activation.
