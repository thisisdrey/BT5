### Title
Unsolicited StackerDB chunk push lets a remote peer advertise a slot version as stored before it is actually committed - (File: stackslib/src/net/stackerdb/mod.rs)

### Summary
`PeerNetwork::handle_unsolicited_StackerDBPushChunk` patches the local, in‑memory `StackerDBChunkInvData` (the inventory that this node hands back to the sender) to reflect the pushed chunk's new `slot_version` *before* that chunk has actually been committed to the on‑disk StackerDB. Real persistence only happens later and asynchronously, in the relayer (`Relayer::process_pushed_stacker_db_chunks` → `process_stacker_db_chunks` → `StackerDBTx::try_replace_chunk`). Between "advertise" and "commit" there is a window in which the node's advertised inventory does not match its actual stored state.

### Finding Description
The write path is split across two asynchronous stages:

1. `handle_unsolicited_StackerDBPushChunk` (p2p thread) validates the pushed chunk with `validate_received_chunk` and, if it passes, mutates the outgoing `StackerDBChunkInvData.slot_versions` entry to the new version and immediately sends that inventory back to the peer as the "acknowledgement" — before any DB write occurs: [1](#0-0) 
2. It then only *optionally* forwards the chunk to the relayer (`Ok((false, true))`), where the actual, durable write happens: [2](#0-1) 
3. The durable write and the deduplication/staleness check occur independently and later, inside `Relayer::process_stacker_db_chunks`, which calls `try_replace_chunk` and can `continue` past a chunk on failure (e.g. `StaleChunk`, DB error) without any coordination back to the inventory that was already advertised in step 1: [3](#0-2) 

`validate_received_chunk` itself does not check the DB's `write_freq` limit and explicitly documents that omission ("does not check write frequency, since the caller has different ways of doing this"): [4](#0-3) [5](#0-4) 

This means the equality that should hold — "advertised slot version == durably committed slot version" — is broken during the interval between the p2p‑thread's inventory patch and the relayer's actual commit. A node's peers may momentarily believe (via `StackerDBChunkInvData`) that a given slot has already reached a newer version, even though the on‑disk state (and thus what will actually be served to a `GetChunk` request) has not advanced yet. If the relayer's later `try_replace_chunk` call fails or races with another actually-newer write, the advertised inventory can end up permanently ahead of, or inconsistent with, the truth on disk for that round, which can cause neighbors relying on that inventory value to skip re-requesting/re-pushing the chunk (since they believe it is already replicated), potentially delaying propagation of that chunk version across the network.

### Impact Explanation
This is a "served vs. committed" equality break inside the StackerDB replication protocol (`stackslib/src/net/stackerdb/**`), which the rules explicitly call out as an in‑scope analog class ("bytes vs length" / "served as canonical" type equality violations). The concrete effect is a node telling its peers a stale/false inventory value for a slot it has not actually persisted yet, which can steer peers away from re-fetching/re-relaying that chunk (a "false inventory" condition), delaying propagation of legitimately signed StackerDB data (e.g., signer messages) across the network. It does not require any privileged access — the caller only needs a validly signed chunk for a slot it does not need to own the DB itself, and can push it unsolicited to any peer's p2p port.

### Likelihood Explanation
Likelihood is moderate: exploiting this in a way that measurably delays propagation requires (a) sending a legitimately signed chunk (so an attacker must possess a signer's actual private key for one of the DB's slots, or use their own controlled/legit slot), and (b) hitting the race window between the inventory-patch and the relayer's later commit (e.g., relayer being busy, or the write later failing as `StaleChunk`). This is a genuine, reachable code path (`handle_unsolicited_StackerDBPushChunk` is called directly off unauthenticated-but-connected p2p unsolicited message handling), but it is a narrower "delay propagation" issue rather than a full unauthenticated write or crash, so it sits at the lower end of the accepted impact bracket.

### Recommendation
Only patch/advertise the local inventory's `slot_version` for a pushed chunk after the chunk has actually been durably committed by the relayer (or synchronously commit it inline before responding), rather than optimistically updating the in‑memory `StackerDBChunkInvData` at validation time. Alternatively, make the inventory-patch step contingent on a subsequent confirmation callback from the relayer so that the advertised inventory can never outrun what is actually stored on disk.

### Proof of Concept
Not independently reproduced (no execution environment). Conceptual reproduction based on code paths cited above:
1. Peer A creates a StackerDB with slot 0 owned by a known signer key `sk`.
2. Attacker (or benign but adversarial-timing peer) sends an unsolicited `StackerDBPushChunk` for slot 0, version N, correctly signed with `sk`, to Peer A over the p2p connection.
3. `handle_unsolicited_StackerDBPushChunk` validates the chunk (`validate_received_chunk` returns `Ok(true)`), patches `data.slot_versions[0] = N`, and immediately replies with this patched `StackerDBChunkInvData` to the sender (and any other peer querying inventory in that instant) — before the chunk is durably written.
4. Concurrently, the relayer's `process_pushed_stacker_db_chunks` → `try_replace_chunk` call for that chunk fails (e.g., a competing write already advanced the slot to version N first, yielding `StaleChunk`), so the actual on-disk `slot_version` never reaches N via this push.
5. Any peer that received the advertised inventory in step 3 believes slot 0 is already at version N and will not attempt to fetch/re-push it, even though Peer A's true stored state disagrees — an inventory/state mismatch that can persist until the next legitimate write cycle.
