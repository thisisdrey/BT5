### Title
Stale `PromiseYieldReceipt` self-callbacks survive `remove_account` and execute privileged self-actions against a recreated account of the same id - (File: core/store/src/utils/mod.rs / runtime/runtime/src/lib.rs)

### Summary
`remove_account` deletes `Account`, `ContractCode`, access keys, gas-key nonces, and `ContractData`, but never removes `TrieKey::PromiseYieldReceipt` entries keyed by `(receiver_id, data_id)`. The paired `PromiseYieldTimeout` queue entry is global and account-agnostic by design, but it still stores the same `account_id`/`data_id` pair, so when the timeout eventually fires, `resolve_promise_yield_timeouts` looks up the `PromiseYieldReceipt` purely by account id and executes it if found - even if the account was deleted and a completely different owner has since recreated an account with the same id.

### Finding Description
A `PromiseYield` receipt is always self-directed: `receiver_id == predecessor_id == account_id` of the account that called the yield host function (`is_instant_receipt` doc, `core/primitives/src/receipt.rs:474-479`; queue enqueue uses the *executing* `account_id`, `runtime/runtime/src/function_call.rs:152-169`). Because predecessor equals receiver, when the receipt eventually executes, action-level actor checks trivially pass "self" authorization without any access-key check — this is intentional for legitimate resume flows (`runtime/runtime/src/actions.rs`, `action_delete_account` etc. checking `actor_id == account_id`).

The flaw is in cleanup: `remove_account` (core/store/src/utils/mod.rs:505-575) removes `Account`, `ContractCode`, access keys, gas-key nonces, and `ContractData`, but never issues `state_update.remove(TrieKey::PromiseYieldReceipt { .. })`. [1](#0-0) [2](#0-1) 

Meanwhile `resolve_promise_yield_timeouts` (runtime/runtime/src/lib.rs:3009-3104) walks the global `PromiseYieldTimeout` queue by `expires_at`, and for each expired entry checks only `contains_key(PromiseYieldReceipt{receiver_id: queue_entry.account_id, data_id})` — with no check that the account is "the same" account (e.g., no creation nonce/version binding): [3](#0-2) 

If that key still exists it synthesizes a `PromiseResume` receipt with `predecessor_id = receiver_id = queue_entry.account_id` and forwards it; the runtime then re-executes the stored yield receipt's action list against whatever account currently occupies that id. [4](#0-3) 

Exploit flow:
1. Attacker (or a colluding pair) controls account `X`, deploys a contract, and calls the yield host function to create a self-callback (`create_promise_yield_receipt`, `runtime/runtime/src/receipt_manager.rs:148-165`), then appends privileged actions to that pending self-receipt (e.g., `AddKey` with an attacker key, or `DeleteAccount{beneficiary_id: attacker}`), exactly as with any promise batch.
2. `X` then calls `DeleteAccount` on itself. `action_delete_account` → `remove_account` removes the `Account`/keys/code/data, but leaves the `PromiseYieldReceipt{receiver_id: X, data_id: D}` and the still-pending `PromiseYieldTimeout{account_id: X, data_id: D, expires_at}` entry untouched.
3. A new, unrelated party later creates a fresh account with the same id `X` (account ids are free to reuse once deleted) and funds/deploys their own contract.
4. Once chain height reaches `expires_at` (bounded by the fixed protocol parameter `yield_timeout_length_in_blocks`, `runtime/runtime/src/function_call.rs:167-168`), `resolve_promise_yield_timeouts` finds the stale `PromiseYieldReceipt` still present under `X`, synthesizes the timeout `PromiseResume`, and the runtime executes the old actions with `predecessor_id == receiver_id == X` against the new account's live state — including balance-draining or key-injecting actions the new owner never authorized.

This bypasses the new owner's consent because self-directed receipts are trusted implicitly (no access-key check on receipt execution) and no code ties the `PromiseYieldReceipt`/`PromiseYieldTimeout` pair to a specific account "generation."

### Impact Explanation
An action such as `Action::DeleteAccount{beneficiary_id: attacker}` embedded in the stale self-receipt would delete the new owner's freshly funded account and transfer its entire balance to the attacker-chosen beneficiary; `Action::AddKey` would silently grant the old (attacker) owner a full-access key on the new account. This is authorization escalation across accounts leading to theft/freezing of user funds — matching the "authorization escalation across accounts or promises" / "theft of user funds" bounty categories.

### Likelihood Explanation
The attack requires: (a) the attacker to fully control the "donor" account `X` and pre-stage a malicious self-callback and then delete `X`; (b) an unrelated party to independently create a new account with the exact same id `X` before the queued timeout's `expires_at` height passes. `expires_at` is bounded by the fixed protocol constant `yield_timeout_length_in_blocks` (not attacker-extendable to "very long" as hypothesized — it is a short, fixed window), which limits the race window and thus practical exploitability against an arbitrary third-party victim. The scenario is fully feasible and repeatable in a test-loop/unit environment (attacker fully controls both "old" and "new" account creation in a PoC), but achieving it against a real, un-coordinated victim in production requires the victim to recreate the exact same account id within the short fixed timeout window, which is a meaningful but non-trivial precondition.

### Recommendation
- `remove_account` (core/store/src/utils/mod.rs) should also enumerate and remove any `PromiseYieldReceipt`/`PromiseYieldStatus`/yield-id-mapping entries scoped to the account being deleted (analogous to how it already sweeps access keys and contract data by prefix).
- Alternatively/additionally, `resolve_promise_yield_timeouts` (and the `PromiseResume` execution path) should verify the account still exists in a state consistent with when the yield was created (e.g., bind the timeout/receipt pair to an account "epoch"/nonce, or simply drop the timeout if the account existed-then-was-deleted since creation) before re-injecting the resume receipt.

### Proof of Concept
Test-loop integration test:
1. Create account `X`, deploy a test contract exposing a method that calls the yield-create host function and appends a `DeleteAccount{beneficiary_id: attacker}` action to the pending yield receipt (or `AddKey` for a milder PoC).
2. Submit `DeleteAccount` from `X` to itself; confirm via store inspection that `TrieKey::PromiseYieldReceipt{receiver_id: X, ..}` and `TrieKey::PromiseYieldTimeout{..}` are still present after deletion (`remove_account` gap).
3. Submit a `CreateAccount` transaction (from an unrelated funding account) to recreate `X` with new funds and a new access key, before `expires_at`.
4. Advance the chain to `expires_at` height; assert that a `PromiseResume` receipt is produced for `(X, D)`, and that it executes the stale malicious action (e.g., assert new `X`'s balance is drained to the attacker's beneficiary, or that the attacker's public key was silently added to new `X`), despite the new owner never having authorized it.
