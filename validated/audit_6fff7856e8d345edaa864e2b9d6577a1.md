Confirmed. `process_delivery_receipt` in `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs` never inspects `receipt.success` before paying the relayer and removing the `PendingOrder`.Audit Report

## Title
Outbound bridge delivery receipts finalize relayer reward and close pending orders without checking dispatch `success`, permanently losing funds on failed Ethereum-side execution - (File: bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs)

## Summary
`Pallet::process_delivery_receipt` in `snowbridge-pallet-outbound-queue-v2` decodes a `DeliveryReceipt` whose `success` field reflects whether the Ethereum Gateway actually executed the bridged command, but never inspects that flag before paying the relayer and permanently removing the `PendingOrder` for the message. This is analogous to an outer settlement step committing regardless of whether the inner cross-chain action actually succeeded.

## Finding Description
`do_process_message` computes a static, worst-case gas estimate per command via `T::GasMeter::maximum_dispatch_gas_used_at_most(&command)` and stores a `PendingOrder { nonce, fee, block_number }` keyed by nonce [1](#0-0) . `DeliveryReceipt::try_from` decodes the Ethereum `InboundMessageDispatched(nonce, topic, success, reward_address)` event, explicitly carrying a `success: bool` that reflects whether the Gateway's dispatch of the command succeeded on Ethereum <cite repo="Kohvert/polkadot-sdk--013" path="bridges/snowbridge/primitives/outbound-queue/src/v2/delivery_receipt.rs" start="10-27" end="35-51" />. `submit_delivery_receipt` verifies the proof, decodes the receipt, and forwards it unconditionally to `process_delivery_receipt` [2](#0-1) . `process_delivery_receipt` only checks the gateway address and looks up `PendingOrders[nonce]`; it pays `order.fee` to the relayer and unconditionally calls `<PendingOrders<T>>::remove(nonce)` without ever branching on `receipt.success` [3](#0-2) . No other storage item records a failed dispatch, so once the `PendingOrder` is removed there is no path to retry or refund.

## Impact Explanation
Since assets moved to Ethereum are withdrawn/reserved on the Polkadot side at enqueue time (before Ethereum-side confirmation), and the gas budget used on the Ethereum Gateway is a static heuristic estimate (`ConstantGasMeter::maximum_dispatch_gas_used_at_most`) rather than a value verified against actual execution cost [4](#0-3) , a truthful, cryptographically verified `success=false` receipt (e.g. from an underestimated gas budget) still results in the relayer being rewarded and the order irreversibly closed, permanently stranding the corresponding Polkadot-side funds with no refund or retry path. This matches the "permanent user-fund or bridge-state lock" impact category in the allowed impact gate.

## Likelihood Explanation
No compromised relayer, admin, or governance action is required — the relayer submits a truthful, verified proof of a real Ethereum event log. Any outbound command whose actual on-chain Ethereum execution cost exceeds the corresponding static gas figure in `ConstantGasMeter` (or otherwise fails Gateway-side dispatch) will deterministically trigger `success=false` once relayed and processed via this path, since `process_delivery_receipt` treats `success=true` and `success=false` identically.

## Recommendation
Branch on `receipt.success` in `process_delivery_receipt`: on failure, do not treat the `PendingOrder` as fully resolved — instead transition it to a distinct failed/replayable state, or trigger a refund path crediting the original sender/claimer, so assets already withdrawn on the Polkadot side are not permanently stranded.

## Proof of Concept
1. Send an outbound message from AssetHub to Ethereum, causing `do_process_message` to create `PendingOrders[nonce]` with `gas` from `T::GasMeter::maximum_dispatch_gas_used_at_most`.
2. On the Ethereum Gateway, the actual gas required for the command's execution exceeds the pre-computed static estimate (e.g. `UnlockNativeToken` requires more than the hardcoded `200_000`), causing the inner dispatch to revert while the surrounding transaction still emits `InboundMessageDispatched(nonce, topic, success=false, reward_address)`.
3. A relayer submits this event log and proof via `submit_delivery_receipt`.
4. `process_delivery_receipt` pays the relayer and removes `PendingOrders[nonce]` unconditionally — confirmed by code inspection showing no check on `receipt.success` [5](#0-4) ; existing integration/unit tests (e.g. `submit_delivery_receipt_succeeds_after_unhalt`, and the emulated `snowbridge_v2_outbound` test) only exercise `success: true` [6](#0-5) [7](#0-6) , with no test asserting refund/retry behavior for `success: false`.
5. The originally withdrawn Polkadot-side asset is unrecoverable, as no storage records the failed dispatch for reissue or refund.

		/// Process a delivery receipt from a relayer, to allocate the relayer reward.
		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}

pub trait GasMeter {
	/// Measures the maximum amount of gas a command payload will require to *dispatch*, NOT
	/// including validation & verification.
	fn maximum_dispatch_gas_used_at_most(command: &Command) -> u64;
}

/// A meter that assigns a constant amount of gas for the execution of a command
///
/// The gas figures are extracted from this report:
/// > forge test --match-path test/Gateway.t.sol --gas-report
///
/// A healthy buffer is added on top of these figures to account for:
/// * The EIP-150 63/64 rule
/// * Future EVM upgrades that may increase gas cost
pub struct ConstantGasMeter;

impl GasMeter for ConstantGasMeter {
	fn maximum_dispatch_gas_used_at_most(command: &Command) -> u64 {
		match command {
			Command::SetOperatingMode { .. } => 40_000,
			Command::Upgrade { initializer, .. } => {
				// total maximum gas must also include the gas used for updating the proxy before
				// the the initializer is called.
				50_000 + initializer.maximum_required_gas
			},
			Command::UnlockNativeToken { .. } => 200_000,
			Command::RegisterForeignToken { .. } => 1_200_000,
			Command::MintForeignToken { .. } => 100_000,
			Command::CallContract { gas: gas_limit, .. } => *gas_limit,
		}
	}
}

#[test]
fn submit_delivery_receipt_succeeds_after_unhalt() {
	new_tester().execute_with(|| {
		let nonce = 0;
		let fee: u128 = 1_000_000;
		let order = PendingOrder { nonce, fee, block_number: System::block_number() };
		PendingOrders::<Test>::insert(nonce, order);

		let relayer: AccountId32 = [7u8; 32].into();
		let origin = RuntimeOrigin::signed(relayer);
		let event = Box::new(mock_valid_event_proof());

		// Bridge halted — receipt rejected, order untouched.
		set_verifier_halted(true);
		assert_noop!(
			OutboundQueue::submit_delivery_receipt(origin.clone(), event.clone()),
			Error::<Test>::Verification(VerificationError::Halted)
		);
		assert!(PendingOrders::<Test>::get(nonce).is_some());

		// Bridge resumed — same receipt succeeds and the order is settled.
		set_verifier_halted(false);
		assert_ok!(OutboundQueue::submit_delivery_receipt(origin, event));
		assert!(PendingOrders::<Test>::get(nonce).is_none());

		System::assert_has_event(mock::RuntimeEvent::OutboundQueue(Event::MessageDelivered {
			nonce,
		}));
	});
}
