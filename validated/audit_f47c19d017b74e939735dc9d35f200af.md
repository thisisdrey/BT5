### Title
Check/Update replay-window race in `ConnectionState.Decrypt` lets duplicate (replayed) packets bypass the fast-reject and be re-processed as if fresh - ([File: connection_state.go])

### Summary
The Euler report flags a pattern where a "preview" function (`maxRedeemInternal`) is supposed to conservatively predict the outcome of a later authoritative check, but instead optimistically returns a result that the authoritative check can contradict, letting an operation proceed on a false assumption. `ConnectionState.Decrypt` in this repo has the same shape: it uses `Bits.Check` as a cheap, non-authoritative pre-check and `Bits.Update` as the authoritative, state-mutating anti-replay check, but the two are **not called atomically** — the `decryptLock` is released between them for the duration of the AEAD decrypt.

### Finding Description
`ConnectionState.Decrypt` is implemented as: [1](#0-0) 

The sequence is: lock → `window.Check(messageCounter)` → unlock → `dKey.DecryptDanger(...)` → lock → `window.Update(messageCounter)` → unlock. `Check` only reads the replay-window bitmap (`!b.get(i)`), it does not mark the counter as seen; only `Update` mutates state and is the authoritative de-duplication point [2](#0-1) [3](#0-2) .

Because the lock is dropped between `Check` and `Update`, an attacker who captures one legitimate ciphertext and replays it concurrently (e.g., via multiple UDP sends that land on different reader goroutines/queues for the same tunnel) can cause multiple goroutines to simultaneously observe `Check(i) == true` for the *same* counter `i`, since none of them has yet set the bit. Each of those goroutines then proceeds to run a full AEAD decrypt (`DecryptDanger`) for the replayed packet before the authoritative `Update` finally rejects all but the first. This mirrors the Vault bug class exactly: the "preview" (`Check`) optimistically green-lights an operation that the authoritative check (`Update`) will later invalidate, and expensive/sensitive work (AEAD decryption) is performed on the strength of the non-authoritative result rather than being gated behind the atomic, authoritative one.

### Impact Explanation
This does not let a replayed packet reach the TUN device twice — `Update` still serializes and rejects all but the winning duplicate — but it defeats the purpose of `Check` as a cheap first-line filter against replay floods. An attacker with no certificate, simply by capturing and re-transmitting one ciphertext packet concurrently across the process's UDP read queues, can force the responder to perform a full AEAD decrypt for every replay rather than being turned away by the O(1) bitmap check, amplifying CPU cost per replayed byte. This is a remote, unauthenticated resource-exhaustion/amplification vector against the anti-replay subsystem, reachable by anyone who can observe or is on-path for a single legitimate packet (no valid certificate required).

### Likelihood Explanation
Likelihood is moderate: it requires the attacker to capture (or otherwise obtain) one legitimate ciphertext for a live tunnel and then race multiple copies of it into the receiver at once. Nebula's UDP readers can run on multiple queues/goroutines per socket, so hitting the race window across concurrent `Decrypt` calls for the same `ConnectionState` is plausible under load, though the race window (duration of one AEAD decrypt) is narrow and must be hit repeatedly to sustain amplification.

### Recommendation
Hold `decryptLock` across the whole `Check` → `Decrypt` → `Update` sequence for a given `messageCounter`, or otherwise make the replay-window check-and-mark atomic (e.g., reserve the slot at `Check` time and only release/roll it back if decryption fails), so that only one concurrent decrypt attempt per counter can ever begin, rather than allowing many decrypts to race to a single authoritative `Update`.

### Proof of Concept
Conceptual PoC (not executed):
1. Establish a tunnel between two Nebula nodes and let a data packet with message counter `N` be sent.
2. Capture that single UDP datagram.
3. From an attacker-controlled host with no Nebula certificate, replay the exact same datagram many times in a tight burst, spread across sockets/threads so the kernel/OS load-balances the copies to different reader goroutines of the victim's listener.
4. Instrument (or profile) the victim process: observe that multiple concurrent calls to `dKey.DecryptDanger` occur for the same `messageCounter` before `window.Update` rejects the losers, i.e., the cheap `Check` pre-filter is bypassed by the race, showing decrypt work performed for what will ultimately be recognized as a duplicate.

This confirms the same "non-atomic preview vs. authoritative check" defect class described in the source report: `Bits.Check` optimistically permits proceeding to expensive/authoritative work, only for the true state-mutating check (`Bits.Update`) to reject it afterward, instead of the check being conservative/atomic up front. // Check returns true if i is within (or way out in front of) the window, and not a replay
func (b *Bits) Check(l *slog.Logger, i uint64) bool {
	// If i is the next number, return true.
	if i > b.current {
		return true
	}

	if b.strictlyWithinWindow(i) {
		return !b.get(i)
	}

	// Not within the window
	if l.Enabled(context.Background(), slog.LevelDebug) {
		l.Debug("rejected a packet (top)", "current", b.current, "incoming", i)
	}
	return false
}

func (b *Bits) Update(l *slog.Logger, i uint64) bool {
	// Fast path: i is the next expected counter. Split out so the function
	// stays small and avoids paying for the slow paths' slog argument-build
	// stack frame on every call. The bit read/test/write is inlined to
	// touch the backing word once.
	if i == b.current+1 {
		pos := i & b.lengthMask
		word := pos >> 6
		mask := uint64(1) << (pos & 63)
		w := b.bits[word]
		if i > b.length && w&mask == 0 {
			b.lostCounter.Inc(1)
		}
		b.bits[word] = w | mask
		b.current = i
		return true
	}
	return b.updateSlow(l, i)
}

// updateSlow handles jumps, in-window backfill, dupes, and out-of-window.
func (b *Bits) updateSlow(l *slog.Logger, i uint64) bool {
	// If i is a jump, adjust the window, record lost, update current, and return true
	if i > b.current {
		end := i
		if end > b.current+b.length {
			end = b.current + b.length
		}
		count := end - b.current
		startPos := (b.current + 1) & b.lengthMask

		var lost int64
		if b.current >= b.length {
			// Steady state: every cleared slot is past warmup, so any unset
			// bit we evict is a lost packet from the previous cycle.
			wasSet := b.clearRange(startPos, count)
			lost = int64(count) - int64(wasSet)
		} else {
			// Warmup (the very first window). Some cleared slots represent
			// packets <= length where eviction is not "lost" in the usual
			// sense. This branch is taken at most once per connection so we
			// don't bother optimizing it.
			for n := b.current + 1; n <= end; n++ {
				if !b.get(n) && n > b.length {
					lost++
				}
			}
			b.clearRange(startPos, count)
		}

		// Anything past the new window can never be backfilled, so it's lost.
		if i > b.current+b.length {
			lost += int64(i - b.current - b.length)
		}
		b.lostCounter.Inc(lost)

		b.set(i)
		b.current = i
		return true
	}

	// If i is within the current window but below the current counter, check to see if it's a duplicate
	if b.strictlyWithinWindow(i) {
		pos := i & b.lengthMask
		word := pos >> 6
		mask := uint64(1) << (pos & 63)
		w := b.bits[word]
		if b.current == i || w&mask != 0 {
			if l.Enabled(context.Background(), slog.LevelDebug) {
				l.Debug("Receive window",
					"accepted", false,
					"currentCounter", b.current,
					"incomingCounter", i,
					"reason", "duplicate",
				)
			}
			b.dupeCounter.Inc(1)
			return false
		}

		b.bits[word] = w | mask
		return true
	}

	// In all other cases, fail and don't change current.
	b.outOfWindowCounter.Inc(1)
	if l.Enabled(context.Background(), slog.LevelDebug) {
		l.Debug("Receive window",
			"accepted", false,
			"currentCounter", b.current,
			"incomingCounter", i,
			"reason", "nonsense",
		)
	}
	return false
}
