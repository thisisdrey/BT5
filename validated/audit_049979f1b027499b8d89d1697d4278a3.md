## Analysis

The Plonk CRS report's core broken invariant: a zk proof system relies on a "trusted setup" reference string, and if that reference string is not produced via a proper multi-party ceremony, its trapdoor (toxic waste) can be derived by whoever generated it, letting them forge proofs that the verifier still accepts as valid.

The polkadot-sdk analog is in the Sassafras consensus pallet's Bandersnatch Ring-VRF setup, which uses exactly the same class of construction (a KZG-style Updatable Universal Reference String for a ring proof system) but derives it from a fixed, publicly known, zero-entropy seed instead of a proper ceremony.

### Title
Sassafras ring-VRF "Updatable Universal Reference String" can be built from a public, zero-entropy seed, allowing forged ticket/slot-claim proofs - (File: `substrate/frame/sassafras/src/lib.rs`)

### Summary
`RingContext<R>`, the pallet's storage value described in code as "Updatable Universal Reference String and the seed" used to build the ring verifier for Sassafras's anonymized VRF ticket system, can be populated at genesis with `RingContext::new_testing()`, which deterministically derives the reference string from the fixed public seed `[0; 32]`. [1](#0-0) [2](#0-1) 

### Finding Description
`RingContext<const R: usize>` wraps `RingSetup`, described as an Updatable Universal Reference String (URS/CRS analog) used for building both provers and verifiers for the ring-VRF scheme (KZG-style PCS with G1/G2 points), the same cryptographic pattern as Plonk's CRS. [3](#0-2) 

The pallet's genesis build routine, gated by the `construct-dummy-ring-context` Cargo feature, populates the on-chain `RingContext` storage item with this deterministic, all-zero-seed setup and immediately derives the epoch's `RingVerifierData` from it: [4](#0-3) 

This `RingVerifierData` is subsequently the sole authority used to accept or reject ring-VRF proofs submitted via the public, unsigned `submit_tickets` extrinsic: [5](#0-4) 

Because the seed `[0; 32]` is hardcoded and public, anyone can regenerate byte-for-byte the same `RingSetup`/URS offline via `RingSetup::from_seed(R, [0; 32])`, exactly the scenario the external report warns against: a CRS whose generation secret ("toxic waste") is known, rather than discarded via an MPC ceremony. With the same reference string and its underlying trapdoor derivable off-chain, ring-membership proofs can potentially be forged, i.e., an attacker who is not part of the authority ring could construct a ring-VRF proof that `ring_vrf_verify` (called from `submit_tickets`) accepts as valid. [6](#0-5) 

Unlike `RingContext::verifier_no_context`'s doc, which only concerns performance trade-offs, there is no separate guard preventing `construct-dummy-ring-context` from being compiled into a production runtime; it is purely a build-time Cargo feature flag with no other consensus-level safety check that a genuine ceremony-derived context was used instead. [7](#0-6) 

### Impact Explanation
If a chain's runtime is built with `construct-dummy-ring-context` (documented as "mostly used for testing and development", but with no on-chain enforcement preventing production use), the ticket-based leader-election mechanism at the heart of Sassafras block production could accept forged ring proofs. This directly threatens block-production integrity — a false/forged proof would be accepted as legitimate on-chain state (ticket data, epoch randomness derivation), which can compromise chain liveness/consensus, matching the "forged or mis-bound proof or state acceptance" impact category.

### Likelihood Explanation
This does not require a malicious validator, collator, leaked key, or governance actor — the vulnerability is purely a matter of which build-time feature flags are compiled into the runtime binary. Any chain (or misconfigured build pipeline) that ships with `construct-dummy-ring-context` enabled in a production runtime is exposed by design, since the seed is committed in the open-source code itself.

### Recommendation
Never allow `construct-dummy-ring-context` (or any deterministic/fixed-seed `RingSetup`) to be compiled into a production runtime. Enforce this at compile time (e.g., fail the build unless a separate `std`+`test`-only cfg gate is present) and require that any real Sassafras deployment obtain its `RingContext` from a properly executed, audited multi-party trusted-setup ceremony analogous to a Powers-of-Tau MPC, with the derived URS committed to genesis storage through a verified, non-testing code path.

### Proof of Concept
1. Build a Sassafras-enabled runtime with the `construct-dummy-ring-context` feature active.
2. At genesis, `GenesisConfig::build` calls `vrf::RingContext::new_testing()`, storing a `RingContext` derived from `RingSetup::from_seed(RING_SIZE, [0; 32])`.
3. Anyone (attacker) independently runs `RingSetup::from_seed(RING_SIZE, [0; 32])` off-chain to reconstruct the identical Updatable Universal Reference String and its underlying secret parameters, exactly as this call would produce.
4. Using the reconstructed reference string's trapdoor, the attacker crafts a ring-VRF proof that `RingVrfSignature::ring_vrf_verify` (invoked in `submit_tickets`) validates as a legitimate ring member, despite not holding a genuine authority position in the ring.
