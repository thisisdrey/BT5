### Title
Per-Peer QUIC Stream Throttle Uses Non-Atomic Check-Then-Act, Allowing Stake-Weighted QoS Evasion via Concurrent Connections - ([File: streamer/src/nonblocking/stream_throttle.rs])

### Summary
The reported bug class is a missing invariant check that lets a cumulative claim exceed an allocated budget because the check and the state update are not atomic/coupled. The Agave analog is in the QUIC TPU streamer's per-peer stream-rate throttle: the "is this peer over quota" check and the "record this stream against the quota" update are two separate, non-atomic operations performed across independently-scheduled async tasks that share the same counter, letting an unprivileged peer exceed its allotted stream quota by opening multiple concurrent connections.

### Finding Description
`throttle_stream` in `streamer/src/nonblocking/stream_throttle.rs` decides whether to delay a stream based on a `load()` of `stream_counter.stream_count` compared against `max_streams_per_throttling_interval`: [1](#0-0) 

The actual increment of that same counter happens in a separate call, `on_stream_accepted`, invoked immediately after the throttle check in the connection's stream-accept loop: [2](#0-1) [3](#0-2) 

Critically, this `ConnectionStreamCounter` is not per-connection — it is shared across all connections opened by the same peer key (IP/pubkey). When a new connection is admitted for a peer that already has an entry in the connection table, the existing `stream_counter` is reused rather than a new one being created: [4](#0-3) 

Each connection is driven by its own independently spawned async task (`tasks.spawn(handle_connection(...))`), and `QuicStreamerConfig`/`SwQosConfig` explicitly allow multiple concurrent connections per peer (e.g. `DEFAULT_MAX_QUIC_CONNECTIONS_PER_STAKED_PEER = 16`, `DEFAULT_MAX_QUIC_CONNECTIONS_PER_UNSTAKED_PEER = 8`): [5](#0-4) 

Because the check (`load`) and the update (`fetch_add`) of the shared counter are split across time and across concurrently-running per-connection tasks, several of a peer's connections can each observe a stale (pre-increment) `stream_count` value that is still under the quota and all proceed to accept/accumulate streams before any of their increments become visible to the others' checks. This mirrors the PoolTogether root cause: an amount is computed/checked against a supposed cap, but the bookkeeping used to enforce that cap is not applied atomically with the check, so the aggregate action can exceed the intended allocation.

### Impact Explanation
A peer (staked or unstaked, no special privileges required — this is TPU packet ingestion reachable by any client) can open the maximum allowed number of concurrent connections and race streams across them, causing the effective aggregate stream rate for that peer to exceed `max_streams_per_throttling_interval` — the mechanism that implements the stake-weighted QoS fairness guarantee (`available_load_capacity_in_throttling_duration`). This is a QoS-evasion vector: it lets a peer consume more than its fair share of validator TPU stream-processing capacity, and in aggregate (with `DEFAULT_MAX_QUIC_CONNECTIONS_PER_STAKED_PEER`/`_UNSTAKED_PEER` connections raced simultaneously) can multiply the effective throughput admitted from a single low-stake or unstaked peer well beyond its intended allocation, at the expense of other peers' fair-share bandwidth on a leader's TPU ingestion path.

### Likelihood Explanation
Reaching this code path requires no special role — any TPU client establishing QUIC connections triggers it, and the number of connections per peer and the throttling interval are validator-configurable defaults, not protocol-consensus-relevant, making it directly exploitable by ordinary network peers. The race window is bounded by the throttling interval (`STREAM_THROTTLING_INTERVAL_MS = 100ms`) and requires opening the max allowed concurrent connections and bursting streams across them near-simultaneously, which is straightforward for an attacker but only yields a bounded, per-interval multiplier (roughly bounded by `max_connections_per_peer`), not an unbounded resource exhaustion.

### Recommendation
Make the check-and-reserve atomic: use a single atomic `fetch_add`-then-compare (or `compare_exchange` loop) on `stream_count` so that admission decisions and quota consumption happen as one operation, similar to the compare-and-swap pattern already used in `EntryBytesBudget::reserve`: [6](#0-5) 
Alternatively, ensure the throttle decision and the increment for a given `ConnectionStreamCounter` are serialized (e.g., via a mutex or single-writer task) when multiple connections from the same peer can share the counter concurrently.

### Proof of Concept
1. Configure/observe defaults allowing multiple connections per peer (`DEFAULT_MAX_QUIC_CONNECTIONS_PER_STAKED_PEER`/`_UNSTAKED_PEER`).
2. From a single peer identity, open the maximum number of allowed concurrent QUIC connections to the validator's TPU endpoint; per `try_add_connection`, all connections for this peer key share one `ConnectionStreamCounter`.
3. On each connection concurrently, open unidirectional streams as fast as possible. Each connection's async task independently calls `throttle_stream` (reads the shared counter) before `on_stream_accepted` (increments it) — both illustrated in `streamer/src/nonblocking/quic.rs` lines 624-627 and `streamer/src/nonblocking/swqos.rs` lines 445-454.
4. Because the reads on different connections can race ahead of the corresponding increments becoming visible, the aggregate number of streams admitted within one `STREAM_THROTTLING_INTERVAL` for that peer can exceed `max_streams_per_throttling_interval`, evading the intended per-peer/stake-weighted quota.

    pub fn reserve(&self, bytes: u64) -> std::result::Result<(), EntryBytesReserveError> {

                .consumed
                .compare_exchange(current, next, Ordering::AcqRel, Ordering::Acquire)
                .is_ok()

                return Ok(());

        }
