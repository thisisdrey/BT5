### Title
Missing size limits on `GetFileAttributesRequest.Paths`/`Attributes` allow unbounded serial `git check-attr` processing per RPC - (File: internal/gitaly/service/repository/file_attributes.go)

### Summary
`validateGetFileAttributesRequest` only checks that `Paths` and `Attributes` are non-empty, with no upper bound on their length. Since `GetFileAttributes` spawns a single `git check-attr --stdin -z` subprocess and then walks `in.GetPaths()` serially, invoking `checkAttrCmd.Check` (a synchronous write+read round trip through the subprocess pipe) for every path, an attacker-controlled repository owner can submit requests with very large `Paths`/`Attributes` lists to make one RPC handler goroutine and one git subprocess run for an extended time, and can repeat this concurrently to consume many goroutines/processes.

### Finding Description
`GetFileAttributes` in [1](#0-0)  builds a `CheckAttrCmd` via `gitattributes.CheckAttr` and then loops over every entry in `in.GetPaths()`, calling `checkAttrCmd.Check(path)` for each one. `Check` in [2](#0-1)  performs a blocking `stdin.WriteString` + `stdin.Flush` followed by a blocking `stdout.ReadBytes` loop that reads `3 * len(names)` NUL-delimited tokens from the `git check-attr --stdin -z` subprocess for every single path. This is a strictly serial, per-path round trip with no batching, so total handler time scales linearly with `len(Paths) * len(Attributes)`.

`validateGetFileAttributesRequest` in [3](#0-2)  only rejects empty `Paths`/`Attributes`/`Revision`/invalid repository — there is no cap on the number of paths or attributes, and no check on individual path/attribute length. The only externally enforced ceiling on the whole request is the gRPC server's default max receive message size (4 MiB, since no explicit `MaxRecvMsgSize` grpc.ServerOption was found configured), which is large enough to carry hundreds of thousands of short path strings in a single call. Per-RPC concurrency limiting exists in the codebase (`internal/grpc/middleware/limithandler`, `WithConcurrencyLimiters`) but is opt-in via `cfg.Concurrency` configuration and not applied to `GetFileAttributes` by default, so nothing in the reachable code path bounds either the size of a single request or the number of concurrent such requests from one repository owner.

An attacker who owns (or has pushed/imported) a repository can call `GetFileAttributes` with a `Revision` they control and a `Paths` list of hundreds of thousands of entries, tying up one Gitaly goroutine and one `git check-attr` subprocess for the duration of the serial loop, and can issue many such calls concurrently to multiply the effect across goroutines and processes.

### Impact Explanation
This is bounded, request-scoped resource consumption (one extra goroutine + one extra git subprocess per call, each running for longer than a well-formed baseline request) rather than storage escape, injection, or auth bypass. Concurrent abuse by a single unprivileged, repo-owning attacker can increase process count, memory, and CPU on the Gitaly node, corresponding to a DoS-of-RPC-handler impact class, but it does not achieve node-wide outage on its own without sustained concurrency and is mitigated somewhat by the ~4 MiB gRPC message cap and by GitLab Rails-side request timeouts.

### Likelihood Explanation
The attacker needs only an owned/importable repository and the ability to call `GetFileAttributes` — no special privilege is required, and the RPC is reachable from any unprivileged GitLab user with a project. Constructing a request with hundreds of thousands of short path strings fitting under the default 4 MiB gRPC message limit is straightforward, and repeating the call concurrently multiplies the effect, making this fully repeatable.

### Recommendation
Add explicit upper bounds in `validateGetFileAttributesRequest` on `len(in.GetPaths())` and `len(in.GetAttributes())` (and optionally per-string length), returning `InvalidArgument` when exceeded, and/or batch multiple paths into fewer `check-attr` round trips instead of one write/read cycle per path. Additionally, configure per-RPC concurrency limits (`WithConcurrencyLimiters`) for `GetFileAttributes` by default so a single repository/user cannot hold an unbounded number of concurrent handler goroutines and git subprocesses.

```go
func TestGetFileAttributes_LargePathsDoS(t *testing.T) {
    ctx := testhelper.Context(t)
    cfg, repo, repoPath := setupRepositoryService(t)
    client := newRepositoryClient(t, cfg, ...)

    // Build a commit with .gitattributes and many small files/paths not required —
    // paths need not exist in the tree for check-attr to process them.
    paths := make([]string, 300000)
    for i := range paths {
        paths[i] = fmt.Sprintf("f%d", i)
    }

    req := &gitalypb.GetFileAttributesRequest{
        Repository: repo,
        Revision:   []byte("HEAD"),
        Paths:      paths,
        Attributes: []string{"text"},
    }

    start := time.Now()
    _, err := client.GetFileAttributes(ctx, req)
    require.NoError(t, err)
    t.Logf("single oversized request took %s", time.Since(start))
    // Assert: request should be rejected with InvalidArgument once a size cap is added;
    // currently it succeeds but consumes a long-lived git subprocess and goroutine.
}
```
Run this concurrently (e.g., 50 goroutines) against a Gitaly instance and observe elevated `git check-attr` process count and handler goroutine count for the duration, compared to a single small baseline request.

```go
func (s *server) GetFileAttributes(ctx context.Context, in *gitalypb.GetFileAttributesRequest) (*gitalypb.GetFileAttributesResponse, error) {
	if err := validateGetFileAttributesRequest(ctx, s.locator, in); err != nil {
		return nil, structerr.NewInvalidArgument("%w", err)
	}

	repo := s.localRepoFactory.Build(in.GetRepository())

	checkAttrCmd, finishAttr, err := gitattributes.CheckAttr(ctx, repo, git.Revision(in.GetRevision()), in.GetAttributes())
	if err != nil {
		return nil, structerr.New("check attr: %w", err)
	}

	defer finishAttr()

	var attrValues []*gitalypb.GetFileAttributesResponse_AttributeInfo

	for _, path := range in.GetPaths() {
		attrs, err := checkAttrCmd.Check(path)
		if err != nil {
			return nil, structerr.New("check attr: %w", err)
		}

		for _, attr := range attrs {
			attrValues = append(attrValues, &gitalypb.GetFileAttributesResponse_AttributeInfo{Path: path, Attribute: attr.Name, Value: attr.State})
		}
	}

	return &gitalypb.GetFileAttributesResponse{AttributeInfos: attrValues}, nil
}
```

```go
func validateGetFileAttributesRequest(ctx context.Context, locator storage.Locator, in *gitalypb.GetFileAttributesRequest) error {
	if err := locator.ValidateRepository(ctx, in.GetRepository()); err != nil {
		return err
	}

	if len(in.GetRevision()) == 0 {
		return errors.New("revision is required")
	}

	if len(in.GetPaths()) == 0 {
		return errors.New("file paths are required")
	}

	if len(in.GetAttributes()) == 0 {
		return errors.New("attributes are required")
	}

	return nil
```

```go
func (c CheckAttrCmd) Check(path string) (Attributes, error) {
	if strings.Contains(path, "\000") {
		return nil, fmt.Errorf("path with NUL byte not allowed")
	}

	c.m.Lock()
	defer c.m.Unlock()

	if _, err := c.stdin.WriteString(path + "\000"); err != nil {
		return nil, fmt.Errorf("write path: %w", err)
	}
	if err := c.stdin.Flush(); err != nil {
		return nil, fmt.Errorf("flush: %w", err)
	}

	attrs := Attributes{}
	buf := make([]string, 0, 3)

	// Using git-check-attr(1) with -z will return data in the format:
	// <path> NUL <attribute> NUL <info> NUL ...
	for i := 0; i < c.count; {
		word, err := c.stdout.ReadBytes('\000')
		if err != nil {
			return nil, fmt.Errorf("read line: %w", err)
		}

		buf = append(buf, string(bytes.TrimSuffix(word, []byte{0})))

		if len(buf) < 3 {
			continue // Keep going until we have 3 words
		}

		if buf[0] != path {
			return nil, fmt.Errorf("wrong path name detected, expected %q, got %q", path, buf[0])
		}
		if buf[2] != Unspecified {
			attrs = append(attrs, Attribute{Name: buf[1], State: buf[2]})
		}

		i++
		buf = buf[:0]
	}

	return attrs, nil
```
