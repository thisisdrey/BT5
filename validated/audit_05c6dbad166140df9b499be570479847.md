### Title
DebtToken interest accrual bypasses reward sync, inflating borrower rewards retroactively - (File: contracts/RewardsDistributor.sol)

### Summary
`RewardsDistributor._calculateTokenDelta` credits rewards as `token_.balanceOf(account_) * (currentIndex - accountIndex)` — i.e. the account's **current** balance is applied to the entire elapsed index window. This is only correct if every balance change is preceded by an `updateBeforeMintOrBurn`/`updateBeforeTransfer` hook. `DepositToken` hooks all mint/burn/transfer/seize paths, and `DebtToken` hooks `_mint`/`_burn`. However, `DebtToken.balanceOf` grows continuously via accrued interest (`principalOf * debtIndex / debtIndexOf`) with **no** hook firing — the analog of the missing user-liquidity sync in `TimeWeightedIncentiveLogic::_updateAllUserState`. A borrower who lets debt interest accumulate and then triggers a single late sync is paid borrower incentives as if the post-interest balance existed for the whole window, over-claiming reward tokens from the distributor at the expense of other claimers.

### Finding Description
In `contracts/RewardsDistributor.sol:217-231`:

```solidity
uint256 _deltaIndex = _tokenIndex - _accountIndex;
_tokensDelta = token_.balanceOf(account_).wadMul(_deltaIndex);
```

The index delta is time-based (`_calculateTokenIndex` accrues `deltaTimestamps * speed / totalSupply`, lines 200-212), but the account delta multiplies the *current* `balanceOf` by the full `_deltaIndex`. Correctness therefore requires the stored `accountIndexOf` to be refreshed before every balance change.

`DebtToken.balanceOf` (`contracts/DebtToken.sol:196-206`) is a lazily-computed value:

```solidity
return (_principal * _debtIndex) / debtIndexOf[account_];
```

where `_debtIndex` grows every second via `_calculateInterestAccrual` (lines 551-566). Interest accrual is not a mint/burn event — `accrueInterest()` (lines 156-180) bumps `totalSupply_` and `debtIndex` but never calls `updateBeforeMintOrBurn` for any account. So a borrower's reward-accruing balance silently drifts upward with zero reward-state synchronization — precisely the "state used in reward computation without prior sync" bug class, except here the staleness favors the holder instead of the pool.

Note `totalSupply()` (lines 500-503) also includes pending interest, which slightly deflates the index and partially offsets the inflation, but the two effects are not equal: an attacker whose share of total debt is large captures most of the offset back anyway, and the net effect is strictly an over-credit for the syncing account.

### Impact Explanation
Theft of unclaimed yield. The rewards contract holds a finite `rewardToken` balance and pays out via `_transferRewardIfEnoughTokens` (lines 248-256) to whoever syncs first. An attacker whose `accountIndexOf` is stale receives `interestAccrued * deltaIndex` extra reward tokens they were never entitled to, permanently reducing what honest users can claim (later claimers may even be unable to claim if the balance is drained). The unclaimed excess is not recoverable.

### Likelihood Explanation
Requires a `DebtToken` to have `tokenSpeed > 0` (borrower incentives — governor-configured, historically used) and a nonzero `interestRate`. The attacker needs only to hold debt: deposit collateral, call `DebtToken.issue`, wait while interest compounds their `balanceOf`, then call `claimRewards` (or permissionless `updateBeforeMintOrBurn`) once. No privileged role, oracle manipulation, or flash loan is needed. The per-period magnitude equals `debt * interestRate * elapsed / rewardWindow`, so it is small per second but continuously repeatable and scales with debt size and sync latency; users who simply never interact also silently over-accrue.

### Recommendation
Before crediting reward delta for a debt token, force interest into a consistent state — e.g., have `RewardsDistributor.updateBeforeMintOrBurn`/`_updateTokensAccruedOf` call `DebtToken.accrueInterest()` first, or compute the reward delta against the balance as of the last `debtIndexOf` snapshot (principal-only) rather than the interest-inflated `balanceOf`. Alternatively, exclude `DebtToken` balances' interest component from reward weighting entirely.

### Proof of Concept
Foundry fork test sketch against a deployed pool where a DebtToken (e.g., msUSD debt) has nonzero `tokenSpeed` and `interestRate > 0`:

```solidity
function test_InterestInflatesRewards() public {
    // setup: alice deposits collateral, issues max debt on incentivized DebtToken
    depositToken.deposit(collateralAmount, alice);
    debtToken.issue(issueAmount, alice);

    // rewards + debt interest accrue for T seconds
    skip(T);

    // two claims for identical economic position:
    // path A: bob syncs alice's index every block via updateBeforeMintOrBurn (keeps delta small)
    // path B: nobody syncs for T, then alice claims once
    uint256 claimableA = projectedWithPeriodicSync(); // recompute per-block in a loop
    uint256 accruedB;
    rewardsDistributor.claimRewards(alice);           // single late sync
    accruedB = rewardToken.balanceOf(alice);

    // path B credits interestAccrued * fullDeltaIndex extra rewards
    assertGt(accruedB, claimableA);
}
```

Concretely: `balanceOf(alice)` at claim time includes `T * interestRatePerSecond * principal` of interest that did not exist during most of the accrual window, yet `_updateTokensAccruedOf` multiplies that inflated balance by the entire `_deltaIndex`. The difference between `accruedB` and the per-block-synced accrual is the excess drained from the distributor's `rewardToken` balance.
