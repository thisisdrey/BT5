### Title
Attacker can fill a victim's per-account token list to `MAX_TOKENS_PER_USER` via dust DepositToken transfers, DoSing the victim from opening new collateral/debt positions - ([File: contracts/Pool.sol])

### Summary
`Pool` tracks each account's collateral and debt positions in two bounded per-account sets, `depositTokensOfAccount` and `debtTokensOfAccount` (`MappedEnumerableSet.AddressSet`), capped at `MAX_TOKENS_PER_USER = 30` (`contracts/Pool.sol:79`). The cap is enforced by `onlyIfAdditionWillNotReachMaxTokens` on `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` (`contracts/Pool.sol:143-148, 204-220`). These functions are permissionlessly callable — the only check is that `msg.sender` is a registered DepositToken/DebtToken — and they take an arbitrary `account_` argument. Whenever a `DepositToken` balance goes 0→nonzero (e.g., via `deposit` or a plain ERC20 `transfer` in `DepositToken.sol`, which calls `addToDepositTokensOfAccount`), the recipient's set grows. An attacker can therefore push entries into any victim's set without consent — the same bug class as the Convergence `veCvgDelegatees` spam-delegation finding.

### Finding Description
- Attacker deposits dust amounts of each registered collateral into the corresponding `DepositToken`, then `transfer`s 1 wei of each deposit token to the victim. Each transfer triggers `Pool.addToDepositTokensOfAccount(victim)`, filling `depositTokensOfAccount[victim]` up to 30 entries.
- Once the combined length of `debtTokensOfAccount` + `depositTokensOfAccount` reaches 30, any `deposit()` into a *new* collateral type reverts with `UserReachedMaxTokens`, and `DebtToken.issue` for a *new* synthetic also reverts (the `addToDebtTokensOfAccount` call fails).
- To recover, the victim must transfer out the dust tokens one at a time (each `removeFromDepositTokensOfAccount` costs gas — storage writes + a cross-contract call), after which the attacker can re-fill the freed slot in the same or following block (front-run/back-run), mirroring the original report's permanent-DoS scenario at ~1:1 cost/damage ratio.
- Caveat: the attack is bounded by the number of distinct deposit + debt tokens registered in the pool (`ReachedMaxDepositTokens` also caps deposit offerings at 30). On deployments with few offerings the set cannot be completely filled; on pools approaching 30 offerings the full DoS applies. DebtToken entries cannot be force-added since debt tokens are non-transferable (`TransferNotSupported` in `DebtToken.sol`).

### Impact Explanation
Liveness DoS identical in spirit to the source finding: a victim is prevented from adding new collateral types to their position, which blocks top-ups needed to stay healthy (risking liquidation of an existing position) and blocks all new borrowing on new synthetics. Recovery costs the victim gas per spam entry while the attacker pays comparable gas — the same gas-griefing asymmetry. Fits "temporary freezing of funds / liveness" acceptance criteria.

### Likelihood Explanation
Requires only an unprivileged EOA, public `DepositToken.transfer`/`deposit` calls, and dust amounts of underlying collateral. No privileged role, oracle manipulation, or governance interaction is needed. Feasibility depends on the deployed pool having enough distinct collateral offerings to meaningfully fill the 30-slot cap.

### Recommendation
Move the `onlyIfAdditionWillNotReachMaxTokens` check so it only constrains actions initiated by the account owner (e.g., enforce the cap inside `deposit()`/`issue()` on `_msgSender()` rather than inside the token-reported bookkeeping functions), or remove the bounded-list architecture in favor of iterating offerings directly. Alternatively, allow any account to prune its own list cheaply and make spam entries removable in batch.

### Proof of Concept
A Hardhat test would: (1) register N deposit tokens via governor `addDepositToken`; (2) attacker deposits 1 wei underlying into each and calls `depositToken.transfer(victim, 1)`; (3) assert `pool.getDepositTokensOfAccount(victim).length == MAX_TOKENS_PER_USER - debtTokens.length`; (4) assert `depositToken.deposit(1)` / `debtToken.issue(...)` for a new token by the victim reverts with `UserReachedMaxTokens`. Note: I verified the cap, the permissionless `account_` parameter, and the caller checks in `Pool.sol`, but did not fully read `DepositToken.sol`'s transfer hook (only confirmed the 12 references to these functions exist there) — the exact hook wiring should be confirmed when writing the PoC.
