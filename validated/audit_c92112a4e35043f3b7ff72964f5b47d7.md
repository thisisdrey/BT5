### Title
Precision Loss from Division-Before-Multiplication in Legacy Vote Reward Calculation (`MortgageService.computeReward`) - (File: chainbase/src/main/java/org/tron/core/service/MortgageService.java)

### Summary
`MortgageService.computeReward(long cycle, List<Pair<byte[], Long>> votes)` (the "old algorithm" reward path used before `NewRewardAlgorithmEffectiveCycle`) computes each voter's share of a standing reward pool by dividing `userVote` by `totalVote` first (as a `double`) and only then multiplying by `totalReward`, exactly matching the "multiplication after division" bug class from the external report.

### Finding Description
In `computeReward`: [1](#0-0) 
the code does:
```java
double voteRate = (double) userVote / totalVote;
reward += voteRate * totalReward;
```
This divides `userVote` by `totalVote` before multiplying by `totalReward`, using floating-point `double` arithmetic rather than performing the multiplication first (`userVote * totalReward / totalVote`) or using integer/BigInteger arithmetic guarded against truncation, as the report recommends. This is invoked from `withdrawReward`/`queryReward` via `getOldReward`, which is reachable whenever a voter's reward spans cycles prior to `getNewRewardAlgorithmEffectiveCycle()`: [2](#0-1) [3](#0-2) 

This differs from the newer reward path (`deltaVi.multiply(BigInteger.valueOf(userVote)).divide(DECIMAL_OF_VI_REWARD)`), which correctly multiplies before dividing using `BigInteger`: [4](#0-3) 

The affected `computeReward(cycle, votes)` method is reachable from an ordinary, unprivileged signed transaction: `WithdrawBalanceActuator.execute()`/`validate()` call `chainBaseManager.getMortgageService().withdrawReward(...)` and `queryReward(...)`, which any account can invoke via a `WithdrawBalanceContract` transaction. [5](#0-4) [6](#0-5) 

Note: I was unable to verify within the index whether `computeReward(long cycle, ...)` (the old, pre-VI, per-cycle path) is still actually exercised on current mainnet given `getNewRewardAlgorithmEffectiveCycle()` was likely activated long ago; if `beginCycle >= newAlgorithmCycle` always holds in practice, this branch is dead code on mainnet but remains live logic for any chain/testnet where the new-reward-algorithm cycle has not yet been set, and is unconditionally compiled and reachable.

### Impact Explanation
Floating-point division-before-multiplication systematically loses precision (rounding down fractional vote shares before scaling by the reward), which can cause the sum of individually computed per-voter rewards to diverge from the true `totalReward`, and by extension can allow small but repeated skew in `AccountCapsule.allowance` credited via `WithdrawBalanceActuator`. Over many cycles/accounts, this is an "unbacked balance" / accounting-drift class issue: a voter's computed reward may not match their proportional entitlement, and dust may be lost or misallocated. This is intrinsically a Medium-severity precision defect, not a High-impact drain because typical vote/reward magnitudes and `double` precision (53-bit mantissa) limit the drift to marginal wei-level truncation per computation rather than large diversion of funds, similar to the original Sherlock finding's assessed severity.

### Likelihood Explanation
The code path is reached automatically any time an account with pre-new-algorithm-cycle vote history withdraws or queries rewards via a standard `WithdrawBalanceContract`, which is an ordinary user transaction requiring no special privilege. On networks/environments where the "new reward algorithm" has not yet taken effect (`newRewardCalStartCycle == Long.MAX_VALUE`, i.e., `getNewRewardAlgorithmEffectiveCycle()` unset) this legacy path is exercised on every relevant reward computation. On mainnet, since the new algorithm was activated a long time ago, historical windows using this old formula are effectively closed, reducing current real-world exploitability, but the code remains present and would affect any chain where the switch has not occurred or is reset (e.g., private/test networks derived from this codebase).

### Recommendation
Refactor `computeReward(long cycle, List<Pair<byte[], Long>> votes)` to multiply before dividing and to use integer (or `BigInteger`) arithmetic consistent with the newer VI-based reward calculation, e.g.:
```java
long reward = (long) (BigInteger.valueOf(userVote)
    .multiply(BigInteger.valueOf(totalReward))
    .divide(BigInteger.valueOf(totalVote)).longValueExact());
```
This mirrors the safe pattern already used in the "new algorithm" branch in the same class and file (`deltaVi.multiply(...).divide(...)`), eliminating the double-precision truncation-before-scaling issue.

### Proof of Concept
Given `totalReward = 100`, `totalVote = 3`, and three voters each with `userVote = 1`:
- Correct proportional split: `100 * 1 / 3 = 33` (integer floor) per voter, total `99` (acceptable, standard integer truncation).
- With the current `double` division-first formula: `voteRate = 1.0/3 = 0.3333333333333333`; `reward = 0.3333333333333333 * 100 = 33.33333333333333` truncated to `long` → `33` per voter — in this simple case the values match, but for larger `totalReward`/`totalVote` values near the edge of `double` precision (`totalReward` or `totalVote` beyond `2^53`, i.e. > ~9×10^15, which is plausible given TRX's 6-decimal SUN denomination and multi-year TRX vote/reward accumulation), `(double) userVote / totalVote` loses low-order bits before the multiplication amplifies the error, producing off-by-more-than-1 discrepancies compared to the exact integer/BigInteger calculation used elsewhere in the same file (`chainbase/src/main/java/org/tron/core/service/MortgageService.java:215-227`) and in `RewardViCalService`/`VoteRewardUtil`.   private long computeReward(long cycle, List<Pair<byte[], Long>> votes) {
    long reward = 0;
    for (Pair<byte[], Long> vote : votes) {
      byte[] srAddress = vote.getKey();
      long totalReward = delegationStore.getReward(cycle, srAddress);
      if (totalReward <= 0) {
        continue;
      }
      long totalVote = delegationStore.getWitnessVote(cycle, srAddress);
      if (totalVote == DelegationStore.REMARK || totalVote == 0) {
        continue;
      }
      long userVote = vote.getValue();
      double voteRate = (double) userVote / totalVote;
      reward += voteRate * totalReward;
    }
    return reward;
  }

  private long computeReward(long beginCycle, long endCycle, AccountCapsule accountCapsule) {
    if (beginCycle >= endCycle) {
      return 0;
    }

    long reward = 0;
    long newAlgorithmCycle = dynamicPropertiesStore.getNewRewardAlgorithmEffectiveCycle();
    List<Pair<byte[], Long>> srAddresses = accountCapsule.getVotesList().stream()
        .map(vote -> new Pair<>(vote.getVoteAddress().toByteArray(), vote.getVoteCount()))
        .collect(Collectors.toList());
    if (beginCycle < newAlgorithmCycle) {
      long oldEndCycle = min(endCycle, newAlgorithmCycle,
          dynamicPropertiesStore.disableJavaLangMath());
      reward = getOldReward(beginCycle, oldEndCycle, srAddresses);
      beginCycle = oldEndCycle;
    }
    if (beginCycle < endCycle) {
      for (Pair<byte[], Long>  vote : srAddresses) {
        byte[] srAddress = vote.getKey();
        BigInteger beginVi = delegationStore.getWitnessVi(beginCycle - 1, srAddress);
        BigInteger endVi = delegationStore.getWitnessVi(endCycle - 1, srAddress);
        BigInteger deltaVi = endVi.subtract(beginVi);
        if (deltaVi.signum() <= 0) {
          continue;
        }
        long userVote = vote.getValue();
        reward += deltaVi.multiply(BigInteger.valueOf(userVote))
            .divide(DelegationStore.DECIMAL_OF_VI_REWARD).longValue();
      }
    }
    return reward;
  }
