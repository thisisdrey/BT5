### Title
Reentrant XCM execution via `ERC20Transactor`+`IXcm` precompile during `WithdrawAsset`/`DepositAsset` corrupts holding-register/asset-accounting invariants - (File: `cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs`)

### Summary
`ERC20Transactor::withdraw_asset_with_surplus` and `deposit_asset_with_surplus` execute a synchronous, attacker-controlled contract call (`pallet_revive::Pallet::<T>::bare_call`) as part of processing a single XCM instruction (`WithdrawAsset`/`DepositAsset`). The asset id (`AccountKey20`) is fully attacker-chosen — no registry/governance gate is required, as shown by the permissionless test paths (`weight_of_message_increases_when_dealing_with_erc20s`, `non_existent_erc20_will_error`, `smart_contract_not_erc20_will_error`) that accept arbitrary `[u8;20]` contract addresses. Because `pallet-revive` also exposes the `IXcm` precompile (`polkadot/xcm/pallet-xcm/precompiles/src/lib.rs`) which calls straight into `pallet_xcm::Pallet::<Runtime>::execute` → `XcmExecutor::prepare_and_execute`, the attacker's ERC20 contract code invoked from inside `withdraw_asset_with_surplus`/`deposit_asset_with_surplus` can call the precompile and trigger a second, fully nested XCM program execution while the outer XCM instruction is mid-flight — i.e., before `self.holding.subsume_assets(...)` records the withdrawn/deposited amount in the outer executor's holding register (`polkadot/xcm/xcm-executor/src/lib.rs:947-970`).

### Finding Description
`process_instruction`'s `WithdrawAsset` handler calls `Config::AssetTransactor::withdraw_asset_with_surplus` and only subsumes the returned credit into `self.holding` **after** the call returns: [1](#0-0) 

For ERC20-typed assets, that transactor call synchronously executes attacker-supplied bytecode via `pallet_revive::Pallet::<T>::bare_call`: [2](#0-1) 

The asset id (`asset_id`/`asset_contract_id`) is obtained from `Matcher::matches_fungibles(what)`, matching an `AccountKey20` junction — i.e. an arbitrary H160 supplied by whoever authored the XCM. Tests confirm this is not gated by any asset registry: the weight/negative-path tests pass a raw `[u8;20]` address with no prior registration step (`weight_of_message_increases_when_dealing_with_erc20s`, `non_existent_erc20_will_error`, `smart_contract_not_erc20_will_error`). [3](#0-2) 

Because the withdraw path runs inside `pallet_revive`'s VM, the attacker's contract code executing `transfer()` can itself call the `IXcm` precompile fixed at address `0xA0000`, which forwards straight into `pallet_xcm::Pallet::<Runtime>::execute` and then `T::XcmExecutor::prepare_and_execute` — a brand-new, fully independent XCM VM run with its own holding register, executed synchronously as a nested call inside the outer instruction's transactional scope: [4](#0-3) [5](#0-4) 

The corrupted value is the outer XCM executor's holding register / asset-accounting state during `WithdrawAsset`/`DepositAsset`: the outer message's `WithdrawAsset` has already caused `T::Currency`/`checking-account` state to move (via the ERC20 `transfer` to `ERC20TransfersCheckingAccount`) but the outer holding has not yet been credited, so anything the attacker's contract does via the nested XCM (e.g. spending, transferring, or querying the *same* `checking_account`/`origin` balances that the outer message is about to rely on) observes and can act on a transiently inconsistent ledger — mirroring exactly the BunniHub bug where the fulfiller acted between the pre-hook debit and the post-hook credit.

`Config::TransactionalProcessor::process(...)` wraps the whole `WithdrawAsset` instruction so storage changes roll back atomically on outer failure, but it does **not** prevent the nested XCM program from *executing to completion* and mutating global state (balances, other pallets, further nested Transacts) mid-instruction — the guard is about atomicity of the outer instruction, not about excluding reentrant, attacker-triggered XCM execution while the outer holding is incomplete. `ReentrancyProtection` in `pallet-revive` guards contract-to-contract call reentry, but the precompile path calls into `pallet_xcm`, not back into the calling contract, so that guard does not apply either.

### Impact Explanation
An unprivileged user can submit an XCM message (via `pallet_xcm::execute`, callable by any signed account) containing a `WithdrawAsset`/`DepositAsset` for a self-deployed "ERC20" whose `transfer()` implementation calls the `IXcm` precompile to run a second XCM program from the same account/origin while the outer message's holding is not yet settled. This lets the attacker interleave asset movements (e.g. drain the `ERC20TransfersCheckingAccount` or manipulate fee/holding accounting) across the two XCM executions before the outer instruction observes its own expected post-state, enabling double-use of momentarily-uncommitted value or accounting drift in the shared checking account — the same class of impact ("arbitrate the temporary discrepancy" / mint more value than deposited) as the reference report, scoped here to Asset Hub's `pallet-revive`/XCM integration.

### Likelihood Explanation
High: no privileged actor, relayer, or governance action is required. Any signed account can call `pallet_xcm::execute` with a message referencing a self-deployed contract as the ERC20 asset id (permissionless per the test suite), and pallet-revive/pallet-xcm ship the `IXcm` precompile enabling exactly this reentrant call pattern by design (it exists specifically so contracts can call `pallet_xcm::execute`).

### Recommendation
Disallow (or explicitly reason about) reentrant XCM execution triggered from within an `AssetTransactor` call that is itself invoked mid-instruction by the XCM executor: e.g., set a reentrancy flag in the XCM executor context before calling into `pallet_revive::bare_call` from `ERC20Transactor`, and have the `IXcm` precompile's `execute`/`send` reject calls when that flag is set (analogous to the `lockForRebalance`/`unlockForRebalance` mitigation in the reference report), so that a nested XCM program cannot run while an outer XCM instruction's holding/asset state is incomplete.

### Proof of Concept
1. Deploy a malicious "ERC20" contract via `pallet_revive` whose `transfer(to, value)` function, instead of (or in addition to) moving its own storage-tracked balance, ABI-encodes and calls the `IXcm` precompile at `0xA0000` with a second XCM program (`execute`) that withdraws/deposits real balances from/to the caller's account or the `ERC20TransfersCheckingAccount`.
2. Submit `PolkadotXcm::execute` (any signed origin) with:
   ```
   WithdrawAsset((Parent, fee))
   BuyExecution { fees: fee, .. }
   WithdrawAsset(AccountKey20 { key: malicious_erc20_address, .. }, amount)   // triggers ERC20Transactor::withdraw_asset_with_surplus
   DepositAsset { .. }
   ```
   as demonstrated feasible by the existing `withdraw_and_deposit_erc20s` test harness pattern.
3. During step 3's `pallet_revive::bare_call` into the malicious contract, its `transfer()` calls the `IXcm` precompile to run a nested `pallet_xcm::execute` that manipulates the same accounts (e.g. `ERC20TransfersCheckingAccount` balance) before the outer `WithdrawAsset` instruction's holding is credited, allowing the attacker to observe/exploit the inconsistent intermediate ledger state analogous to the BunniHub `sourceConsideration` callback exploit. [6](#0-5)
