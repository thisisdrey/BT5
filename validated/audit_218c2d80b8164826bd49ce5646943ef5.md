### Title
Missing L2 sequencer downtime grace period allows unfair liquidations on Optimism/Base - (File: contracts/Pool.sol)

### Summary
Metronome is deployed on sequencer-based L2s (`deployments/optimism/`, `deployments/base/`). Every price-dependent action — collateral valuation, debt valuation, health-factor checks, and `Pool.liquidate` — routes through `masterOracle.getPriceInUsd`, which is consumed raw with no check of L2 sequencer liveness and no grace period after the sequencer comes back up. A grep of the entire repo shows zero references to a sequencer uptime feed (`sequencer`/`Sequencer` has no matches). While the sequencer is down, Chainlink rounds stop updating; when it returns, the backlog of price updates lands almost at once, and a liquidator can call `Pool.liquidate` in the very first blocks, before regular users (who typically cannot use the L1 delayed-inbox path) can add collateral or repay.

### Finding Description
`Pool.sol` computes `debtPositionOf`/`_liquidate` solely from `masterOracle.getPriceInUsd` (24 call sites in `Pool.sol`, including the `liquidate`/`quoteLiquidate*`/`maxLiquidable` path and the `onlyIfHealthy`-style checks on `deposit`/`withdraw`/`mint`). Neither `Pool` nor `PoolRegistry` references an L2 sequencer uptime feed, and there is no "sequencer restart + grace period" gate anywhere in `contracts/`. Because the oracle contract (`IMasterOracle`, deployed externally per chain) only enforces a staleness threshold, an up-to-date-looking price pushed right after sequencer recovery is accepted instantly, so `liquidate` succeeds the moment the price crosses the liquidation threshold.

### Impact Explanation
Users on Optimism/Base can be liquidated unfairly: during sequencer downtime they cannot act (and the forced-inclusion path via L1 is impractical for ordinary users), and on recovery all pending feed updates make new prices effective within seconds. Liquidators front-run the recovery window and seize collateral via `Pool.liquidate`/`DepositToken.seize` before depositors can react — direct loss of user funds matching the accepted Medium bug class.

### Likelihood Explanation
Requires an L2 sequencer outage followed by a price move that pushes accounts below the liquidation threshold — rare but real (Arbitrum/Optimism/Base have all experienced outages), and identical reasoning was accepted as a valid Medium for Perennial (issue #37, fate aligned with #190). It is a protocol design gap present by default on every sequencer-based deployment (`optimism`, `base`).

### Recommendation
Gate liquidation and other health-dependent paths in `Pool.liquidate` (or in `MasterOracle` at the price layer) on the Chainlink Sequencer Uptime Feed: revert while the sequencer is down, and enforce a `GRACE_PERIOD` after `startedAt` before liquidations can proceed, per Chainlink's L2 sequencer feed documentation. Apply on `optimism` and `base` deployments.

### Proof of Concept
Foundry fork on Base or Optimism:
1. Deploy/connect `Pool`, `DepositToken`, `DebtToken`; deposit collateral, mint synth debt so account is near the liquidation threshold.
2. Simulate sequencer downtime: `vm.warp`/feed manipulation so the underlying Chainlink `updatedAt` is stale — `getPriceInUsd` reverts `price-too-behind` (as seen in `test/E2E.mainnet.next.test.ts` pull-oracle staleness tests).
3. Push the fresh (lower) collateral price; `vm.warp` past staleness with zero grace period elapsed.
4. Liquidator calls `Pool.liquidate(victim, collateral, debt)` in the same block the fresh price lands — succeeds; victim had no window to deposit/repay. No sequencer check anywhere in `contracts/` prevents this.

Note: the oracle implementation itself is external to this repo (only `contracts/interfaces/external/IMasterOracle.sol` is in scope), so the exact staleness internals cannot be cited; the demonstrated gap is the absence of any sequencer-liveness or grace-period logic in the in-scope liquidation path.
