### Title
Shareholder Can Permanently Block `vesting::distribute()` via User-Controlled `allow_arbitrary_coin_transfers` Flag — (File: `aptos-move/framework/aptos-framework/sources/vesting.move`)

---

### Summary

`vesting::distribute()` iterates over all shareholders and calls `aptos_account::deposit_coins` for each recipient. `deposit_coins` aborts with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS` if the recipient account exists but is not registered for APT and has explicitly set `allow_arbitrary_coin_transfers = false`. A single shareholder can set this flag on their account, causing the entire `distribute()` transaction to revert and permanently blocking all other shareholders from receiving their vested APT.

---

### Finding Description

`vesting::distribute()` loops over all shareholders and calls `aptos_account::deposit_coins(recipient_address, share_of_coins)` for each one inside a `for_each_ref` closure: [1](#0-0) 

`aptos_account::deposit_coins` contains the following guard: [2](#0-1) 

If the recipient account exists but is **not registered for `AptosCoin`**, the function asserts `can_receive_direct_coin_transfers(to)`. This returns `false` when the account has explicitly called `set_allow_direct_coin_transfers(false)`: [3](#0-2) 

Any account can call `set_allow_direct_coin_transfers(false)` at any time: [4](#0-3) 

The developers were aware of this risk for **beneficiaries** and added a guard in `set_beneficiary`: [5](#0-4) 

However, **no equivalent guard exists** for the shareholder address itself at contract creation time, and `reset_beneficiary` removes the beneficiary mapping without checking whether the shareholder is registered for APT: [6](#0-5) 

After `reset_beneficiary`, distributions revert to the shareholder address directly. If that address is not registered for APT and has `allow_arbitrary_coin_transfers = false`, every call to `distribute()` aborts.

The same root cause exists in `staking_contract::distribute_internal`, which also calls `aptos_account::deposit_coins` for each recipient in a loop: [7](#0-6) 

---

### Impact Explanation

A single shareholder whose account is not registered for APT and has `allow_arbitrary_coin_transfers = false` causes every `distribute()` call to revert. Because coins are extracted from the pool inside the loop before the abort, the transaction rolls back entirely. All other shareholders are permanently blocked from receiving their vested APT until the blocking shareholder's state is resolved — which they fully control. This constitutes permanent freezing of other users' on-chain APT balances.

---

### Likelihood Explanation

- Shareholder addresses are set at vesting contract creation with no APT-registration check.
- Accounts created via `account::create_resource_account` or lower-level `account::create_account` are not automatically registered for APT.
- `set_allow_direct_coin_transfers(false)` is an unprivileged, publicly callable entry function.
- `reset_beneficiary` is callable by the admin or a designated resetter role, and removes the beneficiary guard without re-checking the shareholder.
- The attack requires no special privilege and is reachable from a standard unprivileged transaction.

---

### Recommendation

1. Add `assert_account_is_registered_for_apt(shareholder)` for every shareholder address at vesting contract creation time (mirroring the existing guard in `set_beneficiary`).
2. In `reset_beneficiary`, assert that the shareholder address is registered for APT before removing the beneficiary mapping.
3. Alternatively, use `aptos_account::deposit_fungible_assets` (FA path) instead of `deposit_coins` for APT distributions, which does not have the `can_receive_direct_coin_transfers` gate.

---

### Proof of Concept

1. Deploy a vesting contract with shareholder address `S` where `S` is a resource account created via `account::create_resource_account` (not registered for APT).
2. From `S`, call `aptos_account::set_allow_direct_coin_transfers(false)`.
3. Optionally, if a beneficiary was set for `S`, call `reset_beneficiary` to revert distributions to `S` directly.
4. After the lockup expires, call `vesting::distribute(contract_address)`.
5. Observe: the transaction aborts with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS` when attempting to deposit to `S`, and no shareholder receives any distribution.
6. Repeat step 4 indefinitely — the result is always the same abort, permanently freezing all shareholders' vested APT.

```text
    public entry fun set_allow_direct_coin_transfers(
        account: &signer, allow: bool
    ) acquires DirectTransferConfig {
        let addr = signer::address_of(account);
        if (exists<DirectTransferConfig>(addr)) {
            let direct_transfer_config = borrow_global_mut<DirectTransferConfig>(addr);
            // Short-circuit to avoid emitting an event if direct transfer config is not changing.
            if (direct_transfer_config.allow_arbitrary_coin_transfers == allow) { return };

            direct_transfer_config.allow_arbitrary_coin_transfers = allow;
```
