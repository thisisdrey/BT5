## Analysis

The reported bug class is: an off-chain signature scheme used to authorize a sensitive action does not bind the message to a specific chain (no `block.chainid` in the signed payload), so a valid signature on one chain can be replayed on any fork/other chain sharing the same address space.

Java-tron has a directly analogous native primitive: the `ValidateMultiSign` precompiled contract, exposed to every TVM contract as `validatemultisign(address,uint256,bytes32,bytes[])`. It lets *any* deployed contract verify that a TRON account's permission holders signed an arbitrary `bytes32 data` value, by internally reconstructing the message to be signed and checking the recovered signer weights against the account's permission threshold. [1](#0-0) 

The message hash is built purely from `address`, `permissionId`, and the caller-supplied `data` — with `SHA256`, no chain identifier, genesis hash, or any other domain separator mixed in: [2](#0-1) 

Signature recovery and weight-threshold checking then rely solely on this hash: [3](#0-2) 

This is the same class of bug reported for Mover's `constructMsg`: any contract built on top of `validatemultisign` for meta-transaction/permit-style authorization inherits a message format that is identical on mainnet, on public testnets (Nile/Shasta), and on any private fork, because permission address, permission id and `data` are all attacker/dApp-controlled and none of them are chain-scoped. A signature a user produces to authorize an action on one TRON-compatible network remains valid and can be replayed verbatim on another network using the same account/permission — this is a native, always-available replay-primitive rather than an application bug that individual Solidity contracts could work around, since the hash construction is fixed inside the Java precompile implementation, not exposed for the calling contract to extend with `CHAINID`.

### Title
Native `ValidateMultiSign` precompile signs messages without chain binding, enabling cross-fork/cross-network signature replay - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The `ValidateMultiSign` TVM precompile (`validatemultisign(address,uint256,bytes32,bytes[])`), used by any smart contract to verify off-chain permission signatures, constructs the signed message hash from `address || permissionId || data` only. No chain id, genesis block hash, or other network-specific value is included.

### Finding Description
`ValidateMultiSign.execute` builds `combine = address ++ permissionId ++ data` and hashes it with SHA-256 to get the message that user signatures are checked against, then verifies the recovered signer addresses' cumulative weight meets the permission threshold. [4](#0-3)  None of the inputs to this hash are chain-specific: the account address and permission structure are portable across any TRON-protocol chain that shares account state (mainnet, official testnets, or any hard/soft fork), and `data` is fully attacker/application controlled. Consequently, a valid signature authorizing an action via this precompile on one network is inherently valid on every other network running the same protocol and sharing the same account/permission configuration — there is no way for a calling contract to force chain-scoping because the hash is computed entirely inside the native precompile, unlike Solidity code where a developer could mix in `block.chainid`.

### Impact Explanation
Any contract that relies on `validatemultisign` to implement meta-transactions, permit-style approvals, or multisig-authorized fund movement (a common pattern for gasless/relayed operations on TRON) is exposed to signature replay if the chain ever forks or if the same account/permission setup is deployed/mirrored on another TRON-compatible network. An attacker holding a previously-valid signed authorization can replay it on the forked/alternate chain to move funds or execute privileged operations without the signer's renewed consent — a direct unauthorized-operation/fund-theft outcome, matching the High severity of the original report.

### Likelihood Explanation
Exploitation requires only a chain split or the existence of another TRON-protocol chain sharing account state (e.g., a hard fork, or an environment where the same private keys/permission setups are reused, which is common practice for testnets mirroring mainnet accounts). No special privilege is needed by the attacker beyond capturing/observing a previously broadcast/off-chain signature and its associated `data`, then resubmitting the same `validatemultisign` call on the second chain.

### Recommendation
Include a chain-binding value (e.g., the dynamic-properties-stored chain id, or `genesis block hash`) as part of the `combine` buffer hashed inside `ValidateMultiSign.execute`, analogous to EIP-712/EIP-1344 domain separation, so a signature produced for one chain cannot be replayed on another. Alternatively, expose the chain id to calling contracts and document that any `data` passed into `validatemultisign` must itself embed a chain-specific domain separator, though hard-coding it precompile-side is more robust since it protects all existing/future callers uniformly.

### Proof of Concept
1. Deploy identical contract state (same account address and `Permission` with the same keys/threshold) on two TRON-protocol networks that diverge from a common history or are independently initialized with the same genesis-style accounts (e.g., mainnet vs. a fork, or two networks intentionally mirroring the same address space).
2. A permission holder signs `data` (e.g., authorizing a token transfer) intended only for use on network A via a contract that calls `validatemultisign(address, permissionId, data, signatures)`.
3. An attacker captures this authorization (`data` + `signatures`) and submits the identical call to the same contract bytecode deployed on network B.
4. Because `PrecompiledContracts.ValidateMultiSign.execute` computes `hash = SHA256(address || permissionId || data)` with no chain-specific component [5](#0-4) , the precompile returns success on network B as well, letting the attacker execute the authorized action there without the signer's consent for that network.
