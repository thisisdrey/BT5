### Title
Unconditional relayer fee payment before validating action execution enables replayable fund drain in the ETH-implicit Wallet Contract - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The reported bug class ("ignoring the result of a transfer, causing undefined/unsafe behavior when the operation actually fails") maps onto `inner_rlp_execute` in the NEAR Wallet Contract. The function dispatches the relayer's compensation fee as an independent `Transfer` promise *before* it knows whether the action the fee is supposedly paying for will actually be validated and executed successfully. Because the fee payment and the actual action execution are not chained together (no `.then()`), and because the nonce is deliberately *not* incremented for the specific case where this decoupling matters most, a dishonest relayer can collect the fee repeatedly without ever delivering the requested action.

### Finding Description
In `inner_rlp_execute` [1](#0-0) , when the parsed transaction is an `EOABaseTokenTransfer` targeting another eth-implicit account (`address_check: Some(address)`), nonce incrementing is deliberately skipped: [2](#0-1) 

Immediately after, regardless of that branch, if the transaction carries a non-zero relayer `fee`, an independent `Transfer` promise to the predecessor (the relayer) is fired unconditionally: [3](#0-2) 

This fee-payment promise is *not* attached via `.then()` to the promise chain that actually performs the address-registrar lookup and the subsequent action (`address_check_callback` → `action_to_promise`). It executes independently of whether the downstream validation succeeds.

The downstream validation, in `address_check_callback` [4](#0-3) , only bans the relayer (deletes its access key) `if env::signer_account_id() == current_account_id`. When the relayer instead calls `rlp_execute` directly from its own external account (the documented "gasless relayer" flow, exercised by `rlp_execute_from` in tests), `env::signer_account_id()` is the relayer's own account, not `current_account_id`, so the ban branch is skipped entirely; the call simply returns a failure `ExecuteResponse` with no on-chain penalty to the relayer: [5](#0-4) 

Because (a) the fee was already sent, (b) the nonce was never incremented for this branch, and (c) the relayer suffers no penalty when it calls from an external account, the exact same signed Ethereum transaction can be resubmitted by the relayer arbitrarily many times, always triggering the "target corresponds to an existing named account" failure path (which is entirely under the relayer's control since it decides which `target` account id to pass in to `rlp_execute`), and each time collecting the `fee` from the wallet contract's balance while never completing the user's intended transfer.

The analogous decoupling exists for the `ERC20Transfer` branch as well: the fee is paid unconditionally before the `ft_transfer`/`storage_deposit` sequence is attempted, so a relayer can also be paid once without delivering a successful token transfer, though in that branch the nonce is incremented so it cannot be repeated on the same signed transaction.

### Impact Explanation
This is a concrete theft-of-funds vector: an unprivileged relayer (any account, no special permission needed beyond being willing to call `rlp_execute` on behalf of a user, which is the intended trust-minimized design of the Wallet Contract per NEP-518) can drain the target eth-implicit account's NEAR balance by repeatedly resubmitting one user-signed transaction and collecting the relayer fee each time without ever performing the requested transfer, because the fee payment ignores the eventual success/failure "result" of the action it is meant to compensate.

### Likelihood Explanation
The attack requires only a single validly-signed Ethereum transaction with a non-zero fee from a user of an ETH-implicit account, and a `target` chosen by the relayer that resolves (via the address registrar) to an existing named account. The relayer fully controls the `target` parameter passed to `rlp_execute`, and controls whether to call from its own account (bypassing the ban mechanism). No cooperation from the user beyond signing one ordinary transaction with a nonzero fee is needed, and the attack can be repeated in a tight loop until the wallet's balance is exhausted, so likelihood is high once such a signed transaction with fee is broadcast to any relayer.

### Recommendation
Chain the relayer-fee transfer to the actual action execution outcome (e.g., issue the fee payment only from within `rlp_execute_callback`/`address_check_callback` after confirming success), or otherwise ensure the nonce is always consumed (and/or the relayer's access, if any, revoked) before any fee is disbursed, so that a given signed transaction cannot be resubmitted to repeatedly extract the fee without delivering the corresponding action.

### Proof of Concept
1. User creates an ETH-implicit account and signs (off-chain) a single Ethereum-encoded `EOABaseTokenTransfer` transaction with `to` = some eth-address, and a nonzero `gas_price` (mapped to relayer `fee`).
2. A malicious relayer calls `rlp_execute(target, tx_bytes_b64)` directly from its own account (as in `rlp_execute_from`), choosing `target` to be an eth-implicit-looking account id that the address registrar actually recognizes as mapping to an existing named account (`maybe_account_id.is_some()`).
3. `inner_rlp_execute` immediately fires the fee `Transfer` promise to the relayer's account and does not increment the nonce (per lines 358-365, 374-385).
4. The registrar lookup resolves and `address_check_callback` runs; because the relayer called from its own account, `env::signer_account_id() != current_account_id`, so no ban occurs — the call simply reports failure.
5. The relayer repeats step 2 with the exact same `tx_bytes_b64` (nonce unchanged, no consequence), collecting the fee again on every call, draining the wallet's balance. [6](#0-5)

    pub fn address_check_callback(
        &mut self,
        target: AccountId,
        action: near_action::Action,
        caller_deposit: Option<CallerDeposit>,
    ) -> PromiseOrValue<ExecuteResponse> {
        self.has_in_flight_tx = false;
        let maybe_account_id: Option<AccountId> = match env::promise_result(0) {
            PromiseResult::Failed => {
                return PromiseOrValue::Value(ExecuteResponse {
                    success: false,
                    success_value: None,
                    error: Some("Call to Address Registrar contract failed".into()),
                });
            }
            PromiseResult::Successful(value) => match serde_json::from_slice(&value) {
                Ok(x) => x,
                Err(_) => {
                    return PromiseOrValue::Value(ExecuteResponse {
                        success: false,
                        success_value: None,
                        error: Some("Unexpected response from account registrar".into()),
                    });
                }
            },
        };
        let current_account_id = env::current_account_id();
        let promise = if maybe_account_id.is_some() {
            // We intentionally do not increment the nonce in this case because the
            // error is caused by a faulty relayer, not the user. An honest relayer
            // may still be able to successfully send the user's intended transaction.
            if env::signer_account_id() == current_account_id {
                create_ban_relayer_promise(current_account_id)
            } else {
                return PromiseOrValue::Value(ExecuteResponse {
                    success: false,
                    success_value: None,
                    error: Some("Invalid target: target is address corresponding to existing named account_id".into()),
                });
            }
        } else {
            // We must increment the nonce at this point to prevent replay of the transaction.
            // Recall that the nonce was not incremented in `inner_rlp_execute` in the case that
            // the registrar contract was called (i.e. in the case we end up inside this callback).
            self.nonce = self.nonce.saturating_add(1);
            let ext =
                WalletContract::ext(current_account_id).with_static_gas(RLP_EXECUTE_CALLBACK_GAS);
            match action_to_promise(target, action)
                .map(|p| p.then(ext.rlp_execute_callback(caller_deposit)))
            {
                Ok(p) => p,
                Err(e) => {
                    return PromiseOrValue::Value(e.into());
                }
            }
        };
        self.has_in_flight_tx = true;
        PromiseOrValue::Promise(promise)
    }

fn inner_rlp_execute(
    current_account_id: AccountId,
    predecessor_account_id: AccountId,
    target: AccountId,
    tx_bytes_b64: String,
    nonce: &mut u64,
) -> Result<Promise, Error> {
    if *nonce == u64::MAX {
        return Err(Error::AccountNonceExhausted);
    }
    let context = ExecutionContext::new(
        current_account_id.clone(),
        predecessor_account_id,
        env::attached_deposit(),
    )?;
    let caller_deposit = CallerDeposit::new(&context);

    let parsing_result = internal::parse_rlp_tx_to_action(&tx_bytes_b64, &target, &context, *nonce);
    let (action, transaction_kind) = match parsing_result {
        Ok((action, transaction_kind)) => {
            // Increment nonce for all cases where the registrar contract is not needed
            // to prevent replay of those transactions. For transactions that go through
            // the registrar we still do not know if the transaction has a relayer error
            // or not, therefore we must delay incrementing the nonce.
            //
            // Note: relayers with access keys cannot use this delay to needlessly spend
            // the users tokens because only one transaction is allowed to be in-flight
            // at a time.
            if let TransactionKind::EthEmulation(EthEmulationKind::EOABaseTokenTransfer {
                address_check: Some(_),
                ..
            }) = &transaction_kind
            {
            } else {
                *nonce = nonce.saturating_add(1);
            }

            // If the action is an emulated base token or ERC-20 transfer with a non-zero fee then
            // create a promise to send the refund to the relayer. This allows any relayer
            // to safely serve base token transfers from any wallet without additional
            // on-boarding because the relayer will receive some compensation for sending
            // the transaction. Users should always verify the fee before signing a base token
            // transfer. Relayers should also verify the fee before sending to make sure the
            // user's signed transaction will refund enough to cover the relayer's gas costs.
            if let TransactionKind::EthEmulation(EthEmulationKind::EOABaseTokenTransfer {
                fee,
                ..
            })
            | TransactionKind::EthEmulation(EthEmulationKind::ERC20Transfer { fee, .. }) =
                &transaction_kind
            {
                if !fee.is_zero() && context.predecessor_account_id != context.current_account_id {
                    let refund_promise = env::promise_batch_create(&context.predecessor_account_id);
                    env::promise_batch_action_transfer(refund_promise, *fee);
                }
            }

            (action, transaction_kind)
        }
        Err(err @ Error::User(_)) => {
            // Increment nonce on all user errors to prevent replay.
            *nonce = nonce.saturating_add(1);
            return Err(err);
        }
        Err(err) => {
            // Do not increment nonce on Relayer or AccountId errors.
            // The latter error is an issue in the deployment (so the nonce is meaningless).
            // The former arises from the relayer itself doing something wrong and thus the
            // user's transaction could still be valid and potentially submitted properly by
            // another relayer. To allow this we do not increment the nonce.
            //
            // Note: if a relayer is using an access key for this wallet then that key will
            // still be revoked (in the main logic of `rlp_execute`). This fact together with
            // the condition that there only be one in-flight transaction at a time implies
            // that a relayer cannot maliciously burn a large portion of the user's tokens.
            // If the relayer is not using an access key then they are spending their own
            // resources on the gas and therefore we do not care if the relayer submits
            // the same faulty transaction multiple times.
            return Err(err);
        }
    };

    let promise = match transaction_kind {
        TransactionKind::EthEmulation(EthEmulationKind::EOABaseTokenTransfer {
            address_check: Some(address),
            ..
        }) => {
            let callback_gas = ADDRESS_CHECK_CALLBACK_GAS.saturating_add(action.gas());
            let ext = WalletContract::ext(current_account_id).with_static_gas(callback_gas);
            let address_registrar = {
                let account_id = ADDRESS_REGISTRAR_ACCOUNT_ID
                    .trim()
                    .parse()
                    .unwrap_or_else(|_| env::panic_str("Invalid address registrar"));
                ext_registrar::ext(account_id).with_static_gas(REGISTRAR_LOOKUP_GAS)
            };
            let address = format!("0x{}", hex::encode(address));
            address_registrar.lookup(address).then(ext.address_check_callback(
                target,
                action,
                caller_deposit,
            ))
