### Title
`SwapFirstAssetTrader::refund_weight` swaps fee refunds back to the client asset with no `amount_out_min`, letting sandwiching drain the value owed to the XCM sender - (File: `cumulus/primitives/utility/src/lib.rs`)

### Summary
`SwapFirstAssetTrader` is the `WeightTrader` used to let XCM programs pay execution fees with any asset that has a pool with the native fee asset (`Target`). When `buy_weight` runs, it swaps the user's asset into `Target` using `swap_tokens_for_exact_tokens`, which is bounded (the caller specifies the exact `fee` output amount, so no slippage risk there). But when the executor later calls `refund_weight` to return the unused portion of the fee, the surplus `Target`-asset credit is swapped back into the original client asset using `SwapCredit::swap_exact_tokens_for_tokens` with `amount_out_min` hardcoded to `None`: [3](#0-2) 

This is structurally identical to the Badger `Zap.sol#redeem()` bug: an intermediate withdraw/swap step whose output is credited straight to the beneficiary without any `minOut`/slippage bound.

### Finding Description
`refund_weight` is invoked automatically by the XCM executor (`RefundSurplus`, or implicitly at the end of instruction execution) whenever an XCM program overpaid for weight and used a non-native asset via `SwapFirstAssetTrader`. The refund path:

1. Extracts `refund_amount` (a `Target`-asset credit) from `self.total_fee`.
2. Calls `SwapCredit::swap_exact_tokens_for_tokens(vec![Target::get(), refund_swap_asset], refund, None)` — the `None` disables any minimum-output check.
3. Whatever `AssetConversion` pool returns (which can be reduced arbitrarily far by pool-price manipulation) is wrapped back into the XCM holding and eventually returned to the original sender/beneficiary.

Because `AssetConversion` pools are ordinary on-chain AMM pools that anyone can trade against in the same block (e.g., via `swap_exact_tokens_for_tokens`/`swap_tokens_for_exact_tokens` extrinsics or another XCM program), an attacker can:
- Submit a large swap that moves the `(Target, refund_swap_asset)` pool price against the refund swap immediately before the refunding XCM message executes,
- Let the refund execute at the manipulated price, receiving far less `refund_swap_asset` than the fair-value refund,
- Reverse their manipulating trade afterward, capturing the spread that should have gone back to the XCM sender.

This differs from `swap_tokens_for_exact_tokens` used in `buy_weight`, which is safe because the caller fixes the *output* amount and only risks paying more input (bounded by whatever `credit_in` it holds) — worst case the swap simply fails. `refund_weight`, by contrast, fixes the *input* (the surplus fee) and accepts any output, which is exactly the unmitigated-slippage pattern flagged in the report.

### Impact Explanation
Any parachain wiring `SwapFirstAssetTrader` into its `Trader` (Asset Hub Rococo/Westend, Penpal, and the staking-async parachain runtime all do this in this repo) exposes users who pay XCM fees in a non-native, pool-backed asset to value loss on every fee refund. This is a direct value-conservation violation ("Balances ... must conserve value and settle exactly once to the rightful beneficiary and amount"): the XCM sender does not receive the correct refunded amount, and the shortfall is extractable by anyone able to move the relevant `AssetConversion` pool in the same block, i.e., ordinary sandwiching, no privileged relayer/validator/governance role required.

### Likelihood Explanation
Likelihood is moderate-to-high in practice: any low-liquidity or thin `AssetConversion` pool (which is common for pools between native and foreign/local assets on Asset Hub or Penpal) makes the price highly sensitive to a single large trade, and pool manipulation via ordinary signed extrinsics is fully permissionless and requires no special access — it is squarely within normal transaction-ordering capabilities of any user, not a "malicious validator/relayer" scenario the program excludes.

### Recommendation
Bound the refund swap with a real minimum-output, e.g. compute an acceptable floor from `QuotePrice::quote_price_exact_tokens_for_tokens` (already used elsewhere in this file for `quote_weight`) before calling `swap_exact_tokens_for_tokens`, and treat a shortfall as "refund not possible" (keep the `Target` asset credit rather than force a bad swap), mirroring the `minOut` fix recommended in the source report:
```rust
let expected = SwapCredit::quote_price_exact_tokens_for_tokens(
    Target::get(), refund_swap_asset, refund_amount, true,
);
let min_out = expected.map(|e| e.saturating_sub(e / 100)); // e.g. 1% tolerance
let refund = match SwapCredit::swap_exact_tokens_for_tokens(
    vec![Target::get(), refund_swap_asset],
    refund,
    min_out,
) { ... };
```

### Proof of Concept
1. Deploy/parachain with `SwapFirstAssetTrader` configured (as in `asset-hub-rococo`/`penpal` `xcm_config.rs`), with a thin `AssetConversion` pool between `Target` (native) and asset `X`.
2. Attacker, in the same block, front-runs by swapping a large amount into the pool to move the `Target -> X` price sharply.
3. Victim sends an XCM program that pays fees in `X` with `BuyExecution` overestimating the needed weight, triggering `SwapFirstAssetTrader::buy_weight` then `refund_weight` at the end of execution.
4. `refund_weight` calls `swap_exact_tokens_for_tokens(vec![Target, X], refund, None)` — accepts the manipulated, unfavorable rate, returning far less `X` than fair value to the victim's holding/beneficiary.
5. Attacker back-runs by reversing their initial swap, pocketing the difference extracted from the victim's refund. [4](#0-3)
