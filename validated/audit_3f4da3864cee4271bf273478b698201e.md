### Title
Partition assignment for not-yet-created repositories is written to the KV store before the repository itself exists, allowing an unprivileged caller to pre-poison the partition mapping of a predictable future repository path - ([File: internal/gitaly/storage/storagemgr/partition_assigner.go])

### Summary
Repository-creating RPCs (`CreateRepository`, `CreateFork`, `CreateObjectPool`, `CreateRepositoryFromURL`, etc.) are allowed to begin a transaction and write a `(relative_path, partition_id)` mapping into the embedded key-value store **before** the repository is actually created on disk. This is analogous to the ProfilePicture bug class: an identifier ("name"/relative path) is bound in a registry (the partition-assignment table) independently of, and prior to, the entity it is meant to describe being durably created, and the binding is not atomic with respect to that entity. Because the two steps race, an attacker who can predict the relative path a future repository will occupy (Praefect's replica/pool paths are deterministically derived from a sequential integer repository ID via `DeriveReplicaPath`/`DerivePoolPath`) can win the assignment race and force that path into a partition of their choosing before the legitimate owner ever creates it there.

### Finding Description
`beginTransactionForRepository` in [1](#0-0)  explicitly documents that "the partition assignments are created before the repository is created and are thus not atomic. Failed creations may leave stale partition assignments in the key-value store," referencing tracked GitLab issue #5957.

The actual assignment logic lives in `partitionAssigner.getPartitionID` / `getPartitionIDRecursive` / `assignPartitionID`, [2](#0-1) . When `isRepositoryCreation` is true, the code explicitly tolerates the target relative path not existing yet (`fs.ErrNotExist` is not fatal for creation RPCs), acquires a per-relative-path lock, and then persists a partition-ID assignment (`pa.partitionAssignmentTable.setPartitionID(relativePath, ptnID)`) for a path that has no repository on disk at all. Critically, if a hint from an "alternate" repository is supplied (used for `CreateFork`'s origin repo or `CreateObjectPool`'s pool), the not-yet-existing target path is assigned into the **same partition as the attacker-controlled alternate** (`partitionHint`, lines 156-190).

This assignment happens purely against the transaction-manager's KV store keyed by the string relative path - there is no verification that the caller is (or will become) the actual owner of that relative path, nor is the assignment rolled back atomically together with the eventual `repoutil.Create` call (which does perform its own locking/atomic rename, see [3](#0-2)  and [4](#0-3) ). The partition assignment step and the repository-creation step are two independent critical sections guarded by different locks (`partitionAssigner.acquireRepositoryLock` vs. `repoutil.Lock`), so the "registration" (partition binding) can complete and persist even though the "deployment" (actual repository) never gets created by that caller - exactly mirroring the ProfilePicture pattern where the name registration and the constructor-bound name can diverge.

Because relative paths for repositories and pools created through Praefect are `sha256(repositoryID)`-derived and therefore forward-guessable from the monotonically increasing repository ID sequence (`DeriveReplicaPath`/`DerivePoolPath`, [5](#0-4) , and demonstrated directly in test helpers that compute "the next replica path" `storage.DeriveReplicaPath(2)`, [6](#0-5) ), an attacker who can trigger repository-creation RPCs against Gitaly (e.g. via GitLab's fork/import/object-pool flows) can predict the relative path that the *next* legitimately created repository/fork/pool will occupy, and race a `CreateFork`/`CreateObjectPool`-style call that supplies that same predicted path together with an attacker-controlled "alternate" repository as the partition hint. If the attacker's request reaches `partitionAssigner.getPartitionID` first, the target path is pinned into the attacker's partition in the persistent KV table before the legitimate creation ever runs `repoutil.Create`.

### Impact Explanation
When the legitimate repository is later actually created at that same relative path, `repoutil.Create`'s own atomic-rename logic will still work (since it doesn't consult partition assignment), but the transaction that ultimately writes it operates against the partition ID **already fixed by the attacker** rather than a fresh, independently-allocated one. Consequences:
- The victim's repository is durably and permanently tied to the attacker's chosen partition (partition assignments are never deleted, even when repositories are removed, per the accompanying documentation), sharing the single-writer `TransactionManager` goroutine, WAL, and reference-transaction ordering scope with a partition an attacker also occupies.
- If the resulting assignment conflicts with the partition-consistency checks performed for object pools/forks (`ErrRepositoriesAreInDifferentPartitions`, [7](#0-6) ), subsequent legitimate `CreateFork`/`CreateObjectPool`/`LinkRepositoryToObjectPool` calls that expect their own alternate-based colocation will fail, causing a denial of service for the legitimate owner's repository-management operations.
- More broadly, this breaks the intended isolation goal of partitioning ("Transactions always operate against a single partition ... never across them"), permanently and unremovably associating an unrelated victim repository with an attacker-influenced partition.

### Likelihood Explanation
Exploitation requires: (1) the ability to trigger repository-creation RPCs (forks, object pool creation, imports) which is available to any ordinary authenticated GitLab/Gitaly user who can fork projects or create/import repositories; (2) predicting the next sequential repository ID, which is a well-known, previously exploited class of weakness in ID-based path derivation and is realistically guessable/brute-forceable given the small, deterministic SHA256-prefix + sequential-ID scheme; and (3) winning a narrow race window between partition-assignment and the eventual `repoutil.Create` call for the victim's operation. This is a race condition with a non-trivial but not negligible window, and the underlying design flaw is explicitly acknowledged by Gitaly maintainers as tracked technical debt (issue #5957) rather than remediated.

### Recommendation
Make partition assignment atomic with repository creation: only persist a partition-ID mapping for a not-yet-existing repository as part of the same transaction/lock that performs the actual repository creation (`repoutil.Create`'s locked, post-lock-stat-verified critical section), or roll back the assignment if creation ultimately fails/targets a different caller. Alternatively, bind the partition assignment to a repository-existence check performed under the same lock used by `repoutil.Lock`, and reject/ignore alternate-hinted assignments for paths that do not yet have a verified, authorized creator.

### Proof of Concept
Conceptual sequence (exact gRPC harness not verified against a running cluster, but each step is grounded in the cited code):
1. Attacker observes/derives the current maximum Praefect repository ID (e.g., by creating their own repository and reading back its ID/relative path) and computes `nextPath = DeriveReplicaPath(currentMaxID + 1)`.
2. Attacker issues a `CreateFork`/`CreateObjectPool`-style RPC (or otherwise a transaction `Begin` with `AllowPartitionAssignmentWithoutRepository: true`) targeting `RelativePath = nextPath` and `AlternateRelativePath` set to a repository the attacker owns, per `beginTransactionForRepository` (`internal/gitaly/storage/storagemgr/middleware.go:359-386`).
3. This causes `partitionAssigner.getPartitionID(ctx, nextPath, attackerAlternatePath, true)` to run before `nextPath` exists on disk, and `assignPartitionID` persists `nextPath -> attacker's partition ID` in the KV store (`internal/gitaly/storage/storagemgr/partition_assigner.go:234-315`).
4. Shortly after, the intended legitimate fork/import lands on `nextPath` via the normal flow and `repoutil.Create` succeeds (its own locking only prevents concurrent *disk* creation collisions, not partition-table poisoning), but the transaction that creates it is now bound to the attacker's previously-assigned partition ID.

This PoC could not be executed against a live Gitaly cluster in this environment; the analysis is based entirely on the cited source and the maintainers' own acknowledgment comment referencing gitlab-org/gitaly#5957 in `internal/gitaly/storage/storagemgr/middleware.go:363-371`.

func (pa *partitionAssigner) getPartitionIDRecursive(ctx context.Context, relativePath string, recursiveCall bool, partitionHint storage.PartitionID, isRepositoryCreation bool) (storage.PartitionID, error) {
	// Check first whether the repository is already assigned into a partition. If so, just return the assignment.
	ptnID, err := pa.partitionAssignmentTable.getPartitionID(relativePath)
	if err != nil {
		if !errors.Is(err, storage.ErrPartitionAssignmentNotFound) {
			return 0, fmt.Errorf("get partition: %w", err)
		}

		// Repository wasn't yet assigned into a partition. This is the slow path. Requests attempting
		// to get or assign a partition ID concurrently are serialized.

		releaseLock, err := pa.acquireRepositoryLock(ctx, relativePath)
		if err != nil {
			return 0, fmt.Errorf("acquire repository lock: %w", err)
		}

		defer releaseLock()

		// With the repository locked, check first whether someone else assigned it into a partition
		// while we weren't holding the lock between the first failed attempt getting the assignment
		// and locking the repository.
		ptnID, err = pa.partitionAssignmentTable.getPartitionID(relativePath)
		if !errors.Is(err, storage.ErrPartitionAssignmentNotFound) {
			if err != nil {
				return 0, fmt.Errorf("recheck partition: %w", err)
			}

			// Some other goroutine assigned a partition between the failed attempt and locking the
			// repository.
			return ptnID, nil
		}

		// With the repository under lock, verify it is a Git directory before we assign it into a partition.
		// It's okay if the repository doesn't yet exist as this transaction may be about to create it.
		if err := storage.ValidateGitDirectory(filepath.Join(pa.storagePath, relativePath)); err != nil {
			if errors.Is(err, fs.ErrNotExist) {
				if !isRepositoryCreation {
					return 0, relativePathNotFoundError(relativePath)
				}

				// Repository creations are allowed to target non-existing repositories. They create the partition
				// where the repository is to be created.
			} else {
				return 0, fmt.Errorf("validate git directory: %w", err)
			}
		}

		ptnID, err = pa.assignPartitionID(ctx, relativePath, recursiveCall, partitionHint)
		if err != nil {
			return 0, fmt.Errorf("assign partition ID: %w", err)
		}
	}

	return ptnID, nil
}

func (pa *partitionAssigner) assignPartitionID(ctx context.Context, relativePath string, recursiveCall bool, partitionHint storage.PartitionID) (storage.PartitionID, error) {
	// Check if the repository has an alternate. If so, it needs to go into the same
	// partition with it.
	ptnID, err := pa.getAlternatePartitionID(ctx, relativePath, recursiveCall, partitionHint)
	if err != nil {
		if !errors.Is(err, gitstorage.ErrNoAlternate) {
			return 0, fmt.Errorf("get alternate partition ID: %w", err)
		}

		ptnID = partitionHint
		if ptnID == invalidPartitionID {
			// The repository has no alternate. Unpooled repositories go into their own partitions.
			// Allocate a new partition ID for this repository.
			ptnID, err = pa.allocatePartitionID()
			if err != nil {
				return 0, fmt.Errorf("acquire partition id: %w", err)
			}
		}
	}

	if err := pa.partitionAssignmentTable.setPartitionID(relativePath, ptnID); err != nil {
		return 0, fmt.Errorf("set partition: %w", err)
	}

	return ptnID, nil
}

// DeriveReplicaPath derives a repository's disk storage path from its repository ID. The repository ID
// is hashed with SHA256 and the first four hex digits of the hash are used as the two subdirectories to
// ensure even distribution into subdirectories. The format is @cluster/repositories/ab/cd/<repository-id>.
func DeriveReplicaPath(repositoryID int64) string {
	return deriveDiskPath(praefectRepositoryPathPrefix, repositoryID)
}

// DerivePoolPath derives an object pools's disk storage path from its repository ID. The repository ID
// is hashed with SHA256 and the first four hex digits of the hash are used as the two subdirectories to
// ensure even distribution into subdirectories. The format is @cluster/pools/ab/cd/<repository-id>. The pools
// have a different directory prefix from other repositories so Gitaly can identify them in OptimizeRepository
// and avoid pruning them.
func DerivePoolPath(repositoryID int64) string {
	return deriveDiskPath(praefectPoolPathPrefix, repositoryID)
}

func deriveDiskPath(prefixDir string, repositoryID int64) string {
	hasher := sha256.New()
	// String representation of the ID is used to make it easier to derive the replica paths with
	// external tools. The error is ignored as the hash.Hash interface is documented to never return
	// an error.
	hasher.Write([]byte(strconv.FormatInt(repositoryID, 10)))
	hash := hasher.Sum(nil)
	return filepath.Join(prefixDir, fmt.Sprintf("%x/%x/%d", hash[0:1], hash[1:2], repositoryID))
