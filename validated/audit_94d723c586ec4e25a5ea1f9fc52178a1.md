### Title
Arbitrary local-filesystem disclosure via forced `protocol.file.allow=always` in Git submodule fetch — (File: `tools/build_defs/repo/git_worker.bzl`)

### Summary
`git_repository`'s submodule handling unconditionally re-enables Git's `file://` submodule protocol, which upstream Git disabled by default specifically to stop a malicious repository's `.gitmodules` from making Git clone an arbitrary local directory into the submodule checkout path.

### Finding Description
`update_submodules()` always calls `git ... submodule update --init [--recursive] --checkout --force` with the flag `-c protocol.file.allow=always` hard-coded, for both the recursive and non-recursive branches: [1](#0-0) 

The comment explains the intent is only to let *local-directory* remotes (used e.g. in Bazel's own tests) work with submodules, referencing bazelbuild/bazel#17040, but the override is applied for every `git_repository` invocation regardless of whether the top-level `remote` is local or a normal `https://` URL: [2](#0-1) [3](#0-2) 

Git's own default since 2.38.1 for `protocol.file.allow` is `user` (deny for automated operations like submodule fetches) precisely to close the class of bug where a hostile repository ships a `.gitmodules` entry such as `url = file:///home/victim/.ssh` and, upon `git submodule update --init`, Git clones that arbitrary local path into the submodule directory. Bazel's `git_repository`/`new_git_repository` rules set `init_submodules`/`recursive_init_submodules` from rule attributes controlled by the invoking `MODULE.bazel`, but the *content* fetched — including `.gitmodules` — comes entirely from the untrusted `remote` the rule points at. An attacker who controls (or compromises) that remote — a fork, a mirror, a dependency the victim adds, or a branch merged into a project that Bazel's CI checks out — fully controls `.gitmodules` and can point any submodule at `file:///<arbitrary local path>`.

Because Bazel forces `protocol.file.allow=always`, this attacker-controlled `.gitmodules` is honored: Git clones the attacker-chosen local directory (any path readable by the build user — SSH keys, other checked-out repositories, CI secrets mounted on disk, cloud-credential files, etc.) into the submodule path inside the fetched external repository. That content is then treated as ordinary fetched-repository content — hashed/watched by the repository-fetch machinery and exposed to that same external repository's (attacker-authored) `BUILD` files, which can subsequently copy/`genrule` it into build outputs, an uploaded remote-cache artifact, or any other externally observable location, exfiltrating local files the attacker never had permission to read.

This is not a bare MITM: the attacker does not need control of the network path or the victim's machine — only the ability to publish/serve a git repository or a branch that the victim's build fetches (exactly the analog to the "malicious commit author metadata" pattern used by the reference OpenClaw bug, except here the untrusted field is `.gitmodules`'s `url` value rather than a commit-author email). No pinned checksum, lockfile entry, or containment check in `git_worker.bzl` restricts where `protocol.file.allow=always` lets Git read from — the flag is unconditional, so there is nothing in Bazel's own logic guarding this local-path read.

### Impact Explanation
An attacker who can publish or serve a git repository (or a branch merged/served for CI) that a victim references via `git_repository(..., init_submodules = True)` or `recursive_init_submodules = True` can cause the victim's Bazel invocation to read arbitrary local files/directories reachable by the build user (SSH keys, other project checkouts, credential files, CI secrets) into the fetched external repository tree, where attacker-controlled BUILD logic in that same repository can exfiltrate or otherwise expose the content. This is a containment break: fetched, "controlled" content is supposed to originate only from the declared, then-pinned `remote`/`commit`, not from Git being redirected to arbitrary local paths.

### Likelihood Explanation
`init_submodules`/`recursive_init_submodules` are ordinary, commonly-used attributes of `git_repository`; many real-world Bazel projects set them to pull in git submodules of third-party dependencies. Any dependency whose upstream (or a malicious fork/PR/mirror pinned by tag or branch rather than exact commit, or supply-chain compromise of the pinned commit's tree) can supply a hostile `.gitmodules`. Because the protocol override is unconditional and undocumented to callers, most users have no way to know they are exposed, and there is no flag to opt out at the `git_repository`/`git_worker.bzl` level.

### Recommendation
- Do not force `protocol.file.allow=always` unconditionally. Only enable it when the top-level `remote` itself is a local file path (the scenario #17040 was fixed for), e.g. by checking `git_repo.remote` against a `file://`/local-path pattern before adding the override, or by scoping the override to `--config` applied only to `origin`'s own protocol rather than globally for all submodule protocols.
- Alternatively, explicitly set `protocol.file.allow=user` (Git's own safe default) unless the rule attributes indicate the caller intentionally trusts local submodule URLs.
- Add a `git_repository` test asserting that submodules referencing `file://` URLs pointing outside the fetched repository's own remote tree are rejected by default.

### Proof of Concept
Extend the existing submodule test harness pattern (`src/test/shell/bazel/starlark_git_repository_test.sh`, which already exercises `git_repository` with `commit`/`strip_prefix`) with a case that demonstrates disclosure:

1. Create `secret_dir/marker.txt` outside the workspace containing sentinel content (simulating a sensitive local path such as `~/.ssh`).
2. Create `victim.git` repo whose `.gitmodules` declares:
   ```
   [submodule "leak"]
     path = leak
     url = file:///abs/path/to/secret_dir
   ```
   and commit it (this git repo represents attacker-controlled content that a victim adds as `git_repository(remote=..., recursive_init_submodules=True)`).
3. In a `main` workspace, define:
   ```
   git_repository(
       name = "victim",
       remote = "<path or URL to victim.git>",
       commit = "<pinned commit>",
       recursive_init_submodules = True,
   )
   ```
4. Add a `genrule` in `@victim//leak:...` (attacker-controlled `BUILD` inside `victim.git`) that copies `marker.txt` into a build output.
5. Run `bazel build //:leak_out` and observe that the sentinel content from `secret_dir` (outside the fetched repo and outside the workspace) appears in the build output, proving Git cloned an arbitrary local directory chosen by the "attacker" (author of `victim.git`) due to the forced `protocol.file.allow=always` in `update_submodules()`. def update_submodules(ctx, git_repo, recursive = False):
    if recursive:
        # "protocol.file.allow=always" allows the submodule command clone from a local directory.
        # It's necessary for Git 2.38.1 and assoicated backport versions.
        # See https://github.com/bazelbuild/bazel/issues/17040
        _git_maybe_shallow(ctx, git_repo, "-c", "protocol.file.allow=always", "submodule", "update", "--init", "--recursive", "--checkout", "--force")
    else:
        _git_maybe_shallow(ctx, git_repo, "-c", "protocol.file.allow=always", "submodule", "update", "--init", "--checkout", "--force")
