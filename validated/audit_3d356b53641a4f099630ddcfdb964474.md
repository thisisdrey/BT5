### Title
Single-asset oracle failure via `unwrap-panic` in `get-assets` blocks borrow/withdraw AND liquidation for all positions holding that asset - ([File: mainnet/contracts/market/v0-4-market.clar])

### Summary
`get-assets` (mirrored in `local-testing/contracts/market/market.clar`) resolves prices for every collateral/debt asset in a user's position mask via `price-multi-resolve`, then unwraps the result with `unwrap-panic` instead of propagating a controlled error. If price resolution for even one asset in the mask fails (stale timestamp, invalid callcode/z-token cache miss, illegal price), the entire call panics and aborts the transaction — this is the same structural flaw as the reported `get_vault_borrowing_power()` issue: a revert deep inside a per-asset loop kills the whole health-check/valuation path, including the liquidation path.

### Finding Description
`get-assets` builds the oracle/asset list for a position and resolves all prices in one shot: [1](#0-0) 

`price-multi-resolve`/`iter-price-multi` fold over each asset's oracle data and call `price-resolve`, which enforces staleness/legality invariants and resolves z-token/callcode transforms via cached indexes: [2](#0-1) 

`price-resolve` reverts with `ERR-ORACLE-INVARIANT` if `oracle-price-legal` or `oracle-timestamp-fresh` fails, and `resolve-callcode`/`resolve-ztoken` revert with `ERR-ORACLE-CALLCODE` if the per-block index cache for a z-token was not populated: [3](#0-2) 

`price-multi-resolve` correctly captures any single-asset failure into a controlled `(err ERR-ORACLE-MULTI)` response — but `get-assets` immediately discards that error handling by wrapping the call in `unwrap-panic`, turning a recoverable error into a hard runtime abort of the whole transaction: [1](#0-0) 

`get-assets` is invoked from `liquidate` (and from borrow/withdraw health-check flows) to compute `total-collateral-usd`/`total-debt-usd` before the liquidation health check and liquidation-parameter calculation: [4](#0-3) 

Consequently, if any single asset that a borrower holds as collateral (or owes as debt) has its oracle temporarily fail the staleness/legality invariant (e.g., a Pyth/DIA feed stops updating, or a z-token's per-block index cache was never populated in that block via `accrue-and-cache`), the panic prevents not only new borrows/withdrawals but also **liquidation** of that exact position — exactly the scenario described in the external report, where a single misbehaving oracle/asset disables both borrowing against and liquidating affected vaults.

### Impact Explanation
While the borrower cannot open new debt (an acceptable, deliberate safety block), the same panic also blocks `liquidate`, meaning an undercollateralized position holding the failing asset cannot be liquidated while the failure persists. If the underlying collateral price crashes during that window, the position can become insolvent with no way for liquidators to intervene, exactly mirroring the original report's conclusion of potential protocol insolvency (bad debt exceeding vault reserves). This falls under the in-scope Critical impact category of protocol insolvency / permanent freezing of at-risk collateral during the outage window.

### Likelihood Explanation
The failure mode requires an oracle feed to genuinely go stale/invalid or a z-token's cache to be temporarily unpopulated for the block in question — not a purely attacker-triggered exploit, similar to the original finding, which was accepted as a design-level risk rather than mitigated. It is nonetheless a code-level design defect (use of `unwrap-panic` instead of `try!`/graceful per-asset fallback) rather than solely "incorrect third-party oracle data," since the flaw is in how the market contract propagates the resulting error.

### Recommendation
Replace `unwrap-panic` in `get-assets` with `try!`/explicit error propagation so callers (especially `liquidate`) can decide how to handle a failed price resolution — e.g., allow liquidation to proceed using the last known-good/cached price for the failing asset only, or isolate the failing asset's valuation without reverting the whole notional evaluation for unrelated assets in the same position.

### Proof of Concept
1. A borrower opens a position with collateral asset A (e.g., `zstSTXbtc`) and normal debt in asset B.
2. Asset A's Pyth feed stops publishing updates for longer than its configured `max-staleness`, or its per-block index cache (`accrue-and-cache`) is not populated in the current block for that z-token.
3. Asset A's price drops sharply and the position becomes eligible for liquidation.
4. A liquidator calls `liquidate` on the borrower; `get-assets` is invoked, `price-resolve` for asset A fails `oracle-timestamp-fresh` and returns `ERR-ORACLE-INVARIANT`, `price-multi-resolve` returns `(err ERR-ORACLE-MULTI)`, and `unwrap-panic` in `get-assets` aborts the entire `liquidate` transaction.
5. The position remains open and undercollateralized until the oracle recovers, during which further price decline can leave the protocol with unrecoverable bad debt.

(define-private (oracle-price-legal (p uint))
  (> p u0))

(define-private (oracle-timestamp-fresh (ts uint) (prev uint) (max-staleness uint))
  (let ((delta (if (> ts stacks-block-time)
                   u0
                   (- stacks-block-time ts))))
    (and
      (<= delta max-staleness)
      (>= ts prev))))

(define-private (price-resolve
  (data { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint }))
  (let ((type (get type data))
        (ident (get ident data))
        (key { type: type, ident: ident })
        (resolution (try! (resolve-price-feed type ident)))
        (price (get value resolution))
        (callcode (get callcode data))
        (final-price (try! (resolve-callcode price callcode)))
        (last-update-time (oracle-last-update key))
        (timestamp (get timestamp resolution))
        (max-staleness (get max-staleness data)))

    ;; validate price and timestamp using max-staleness from oracle data
    (asserts! (and (oracle-price-legal final-price) (oracle-timestamp-fresh timestamp last-update-time max-staleness))
              ERR-ORACLE-INVARIANT)

    ;; update timestamp if newer
    (if (> timestamp last-update-time)
        (map-set last-update key timestamp)
        false)

    (ok final-price)))

(define-private (price-multi-resolve
  (data (list 64 { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint }))
  (aids (list 64 uint)))

        (response (fold iter-price-multi data init)))
    (asserts! (get valid response) ERR-ORACLE-MULTI)
