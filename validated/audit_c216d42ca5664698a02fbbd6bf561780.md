### Title
Missing content-hash verification when ingesting downloaded Atlas attachments allows an attacker peer to plant arbitrary content that `RPCGetAttachmentRequestHandler` later serves as validated - ([File: stackslib/src/net/atlas/download.rs])

### Summary
`AttachmentsBatchStateContext::extend_with_attachments` accepts any `Attachment` returned by a remote peer for an `AttachmentRequest` without checking that the returned content's hash matches the `content_hash` that was actually requested. The unverified attachment is then unconditionally persisted via `AtlasDB::insert_instantiated_attachment`, after which `RPCGetAttachmentRequestHandler::try_handle_request` (`stackslib/src/net/api/getattachment.rs`) will serve it to any unauthenticated HTTP client that queries `GET /v2/attachments/<hash160(content)>`, even though no `AttachmentInstance` (i.e., no confirmed on-chain BNS/contract event) ever referenced that hash.

### Finding Description
The equality that should hold is: *bytes served under a hash by `/v2/attachments/:hash` == bytes whose hash a confirmed on-chain name/contract operation committed to (`AttachmentInstance.content_hash`)*. This equality is broken because attachment ingestion from peers never cross-checks the returned bytes against the hash that was requested.

- When the local node needs an attachment, it builds an `AttachmentRequest{ content_hash: X, ... }` from a real, on-chain `AttachmentInstance` (`get_prioritized_attachments_requests`, `stackslib/src/net/atlas/download.rs:404-478`).
- The response is decoded and stored with **no comparison to `request.content_hash`**:
```
// stackslib/src/net/atlas/download.rs:530-558
pub fn extend_with_attachments(...) {
    for (request, response) in results.succeeded.drain() {
        ...
        if let Ok(response) = response.decode_atlas_get_attachment() {
            self.attachments.insert(response.attachment);   // no check against request.content_hash
            report.bump_successful_requests();
        }
        ...
    }
}
```
- In `AttachmentsDownloader::run` (`download.rs:152-169`), every attachment collected this way is unconditionally written to disk:
```
for attachment in context.attachments.drain() {
    ...
    network.atlasdb.insert_instantiated_attachment(&attachment)...  // stores under hash160(attachment.content)
    context.attachments_batch.resolve_attachment(&attachment.hash())
}
```
- `AtlasDB::insert_instantiated_attachment` (`stackslib/src/net/atlas/db.rs:576-592`) does `INSERT OR REPLACE INTO attachments (hash, content, was_instantiated=1, ...)` keyed by `attachment.hash()` (locally recomputed hash160 of the attacker-supplied bytes) — it performs no check that this hash equals any `content_hash` field of an existing `AttachmentInstance`, only opportunistically flipping `is_available=1` for rows that happen to match.
- `AtlasDB::find_attachment` (`db.rs:641-648`) simply looks up any row with `was_instantiated = 1`, with no join/requirement that a corresponding `AttachmentInstance` exists.
- `RPCGetAttachmentRequestHandler::try_handle_request` (`stackslib/src/net/api/getattachment.rs:93-129`) calls exactly this `find_attachment` and serves the content directly with no additional validation.

Attacker's exact message/flow:
1. Attacker runs a Stacks P2P peer, gets selected as one of the victim's `get_outbound_sync_peers()`.
2. Attacker answers a `GetAttachmentsInvResponse` claiming (falsely) to have the requested attachment in its inventory, so it is picked as a source for an `AttachmentRequest{content_hash: X}`.
3. When asked `GET /v2/attachments/X` on the attacker's own server, attacker returns `GetAttachmentResponse{attachment: Attachment{content: C}}` for **arbitrary bytes `C`** of the attacker's choosing (`C` need not hash to `X`).
4. The victim's `extend_with_attachments` accepts this response unconditionally and stores it via `insert_instantiated_attachment(&C)`, keyed by `hash160(C)` — a hash that was never the `content_hash` of any confirmed on-chain `AttachmentInstance`.
5. Any remote unprivileged client can now `GET /v2/attachments/hash160(C)` on the victim node and receive `C`, i.e., data planted by the attacker with no on-chain backing at all.

Existing guards do not stop this: there is no signature check on Atlas HTTP responses, no cross-check between requested `content_hash` and returned content hash, and `insert_instantiated_attachment` performs an unconditional `INSERT OR REPLACE` keyed purely by the locally recomputed hash of attacker-controlled bytes. ### Impact Explanation
This lets a remote, unprivileged peer plant arbitrary attacker-chosen (hash, content) pairs into a victim node's AtlasDB and have them served over the public, unauthenticated `/v2/attachments/:hash` RPC endpoint (`security: []` per `docs/rpc/openapi.yaml:1569-1598`) as if they were validated Atlas data. This matches the "High - serving non-canonical state as canonical / attachment-BNS mismatch" category: a client trusting that data returned by `/v2/attachments/<hash>` corresponds to something a confirmed on-chain operation committed to is misled, because the hash-content pairing was never checked against `AttachmentInstance.content_hash`. It is repeatable per Atlas sync round the attacker peer participates in, and does not require the node's RPC secret or any privileged role — only that the attacker's node be selected as an outbound Atlas sync peer.

### Likelihood Explanation
Preconditions: attacker must run an ordinary P2P peer that the victim selects via `get_outbound_sync_peers()` and must be able to respond to Atlas inventory/attachment HTTP requests the victim issues to it — both routine, low-cost, unprivileged actions available to any peer. The victim must have at least one real unresolved `AttachmentInstance` in its queue (a common ongoing situation for any Atlas-enabled node following BNS activity). No secret, signature, or privileged role is required, and the attack is repeatable with each attachment-sync round.

### Recommendation
In `AttachmentsBatchStateContext::extend_with_attachments`, verify `response.attachment.hash() == request.content_hash` before inserting into `self.attachments`; drop/penalize (bump_failed_requests) any peer whose response does not match. Additionally, harden `AtlasDB::insert_instantiated_attachment` to only mark data as validated ("instantiated") when it is being inserted in direct response to a matched, requested `content_hash`, and never accept unsolicited/mismatched content as validated.

### Proof of Concept
Rust test plan (in `stackslib/src/net/atlas/tests.rs` or a new test alongside `download.rs`):
1. Construct a `PeerNetwork`/`AtlasDB` test harness with an `AttachmentsBatch` containing one real `AttachmentInstance{content_hash: X, ...}` (simulating a confirmed on-chain BNS name-update event).
2. Build an `AttachmentsBatchStateContext` and directly call `extend_with_attachments` with a `BatchedRequestsResult` where the `succeeded` map contains the `AttachmentRequest{content_hash: X}` paired with a crafted HTTP response decoding to `GetAttachmentResponse{attachment: Attachment{content: vec![0xAA; 8]}}` (whose `hash160` is `Y != X`).
3. Assert that after `extend_with_attachments`, `context.attachments` contains the attacker's `Attachment` despite `Y != X` — proving the missing check.
4. Drive `AttachmentsDownloader::run` to completion (or call `atlas_db.insert_instantiated_attachment(&attacker_attachment)` directly, mirroring the actual code path) and confirm no `AttachmentInstance` row exists with `content_hash = Y` in the DB.
5. Instantiate `RPCGetAttachmentRequestHandler`, call `try_handle_request` with `attachment_hash = Y`, and assert the response is `200 OK` with `GetAttachmentResponse{attachment.content == vec![0xAA; 8]}` — i.e., the handler serves attacker-controlled bytes for a hash that no `AttachmentInstance`/on-chain operation ever referenced.

    pub fn extend_with_attachments(
        mut self,
        results: &mut BatchedRequestsResult<AttachmentRequest>,
    ) -> AttachmentsBatchStateContext {
        for (request, response) in results.succeeded.drain() {
            let report = self
                .peers
                .get_mut(request.get_url())
                .expect("Atlas: unable to retrieve reliability report for peer");

            let response = if let Some(r) = response {
                r
            } else {
                report.bump_failed_requests();
                continue;
            };

            if let Ok(response) = response.decode_atlas_get_attachment() {
                self.attachments.insert(response.attachment);
                report.bump_successful_requests();

                report.bump_failed_requests();
            }
        }
        let mut events_ids = results.faulty_peers.keys().copied().collect::<Vec<usize>>();

    }

            "UPDATE attachment_instances SET is_available = 1 WHERE content_hash = ?1 AND status = ?2",
            params![attachment.hash(), AttachmentInstanceStatus::Checked],
        )?;
        tx.commit()?;
        Ok(())
    }
