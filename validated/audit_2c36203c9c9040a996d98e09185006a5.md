### Title
Unbounded Array Allocation Before Length Validation in TVM `ValidateMultiSign` Precompile - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `ValidateMultiSign` precompiled contract (address `0x66...`, reachable via a `STATICCALL`/`CALL` from any smart contract executed by an unprivileged transaction) allocates a `byte[][]` array whose size is taken directly from attacker-controlled call data **before** any bound is enforced. This mirrors the iText `readStreamBytesRaw` bug class (CWE-770): a length value taken from untrusted input is used to size a memory allocation before it is validated against a sane maximum or the actual available data, allowing a small transaction payload to trigger a disproportionately large memory allocation.

### Finding Description
`ValidateMultiSign.execute` parses the raw call data into `DataWord[] words` and then extracts the signature array: [1](#0-0) 

The size check (`sigArraySize > MAX_SIZE`) is only performed inside the `VMConfig.allowTvmSelfdestructRestriction()` branch, and even in that branch it is a check on `words[...]`, not a protection on the *legacy* code path. When that hard-fork flag is not enabled, `extractBytesArray` is called directly with no prior bound: [2](#0-1) 

Inside `extractBytesArray` (and identically in `extractSigArray` and `extractBytes32Array`), the array length `len` is read straight from a single 32-byte word via `intValueSafe()`: [3](#0-2) 

`intValueSafe()` clamps overflow to `Integer.MAX_VALUE` rather than rejecting the value: [4](#0-3) 

Because `words` is only a parsed view of the call data, a caller can supply a tiny call-data buffer (a few 32-byte words) that contains one word with the value `0x7FFFFFFF` (or any large 31-bit value) at the "array length" offset. `new byte[len][]` is then executed with `len` up to `Integer.MAX_VALUE`, allocating an array of up to ~2^31 object references (up to ~16 GB on a 64-bit JVM for the reference array alone) **before** the subsequent `signatures.length > MAX_SIZE` check at line 1076 has any chance to reject it — the allocation already happened. The energy charged for this call (`getEnergyForData`) is computed from `data.length` (the actual small call-data size), not from the declared array length, so the attacker pays for a tiny data length while the node performs a huge allocation.

### Impact Explanation
A successful trigger causes an `OutOfMemoryError` in the TVM execution thread. Depending on JVM heap configuration and concurrency, this can:
- Crash or destabilize the FullNode/SR process handling the transaction (denial of service), and
- If triggered during block application by validating/executing nodes, cause divergent behavior between nodes with different heap limits, risking a chain halt or split.

This satisfies the "node crash or halt" / "API the node can no longer serve" acceptance criteria, reachable directly from a single signed smart-contract-invoking transaction — no privileged role required.

### Likelihood Explanation
Likelihood is high for any node that has not yet activated the `allowTvmSelfdestructRestriction` hard fork (the branch that adds an early `sigArraySize > MAX_SIZE` guard). Even where that hard fork is active, the identical unguarded pattern (`new byte[len][]` sized from a single attacker word before any bound check) exists in `extractBytes32Array` and is structurally repeated in `BatchValidateSign`'s ABI extraction (same `ABI_HEADER_WORDS`/`ABI_ITEM_WORDS` pattern), so exposure may extend beyond the single reviewed path. Exploitation requires only deploying/calling a contract that invokes the precompile address with a crafted 32-byte word — a trivial, cheap, and repeatable operation for any account.

### Recommendation
- Validate the declared array/signature count against `MAX_SIZE` (and against the actual number of words available in `data`) **before** allocating `bytesArray`/`bytes32Array`/`signatures` in `extractBytesArray`, `extractSigArray`, and `extractBytes32Array`.
- Apply the same upfront bound unconditionally, not only when `VMConfig.allowTvmSelfdestructRestriction()` is enabled.
- Reject any declared length that is inconsistent with the actual `rawData`/`words` length rather than clamping via `intValueSafe()` to `Integer.MAX_VALUE`.

### Proof of Concept
1. Deploy a contract that performs a `staticcall`/`call` to the `ValidateMultiSign` precompiled address.
2. Construct call data as: `address(32B) | permissionId(32B) | dataOffset(32B) | sigArrayOffset(32B) | signHashOrPad | ...` such that the word at the computed `sigArrayOffset` equals `0x7FFFFFFF`.
3. Send the total call data as only a few actual 32-byte words (small transaction payload / low energy cost as computed by `getEnergyForData`).
4. On a node where `allowTvmSelfdestructRestriction` is not yet active, `extractBytesArray` executes `new byte[0x7FFFFFFF][]` before the `MAX_SIZE` check is reached, causing an `OutOfMemoryError` in the executing node.

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }

   * In case of int overflow returns Integer.MAX_VALUE otherwise works as #intValue()

  public int intValueSafe() {
    int bytesOccupied = bytesOccupied();
    int intValue = intValue();
    if (bytesOccupied > 4 || intValue < 0) {
      return Integer.MAX_VALUE;
