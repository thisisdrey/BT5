### Title
Git submodule fetch in `git_repository`/`new_git_repository` forces `protocol.file.allow=always`, re-enabling local-path submodule clones for attacker-controlled repository content - (`File: tools/build_defs/repo/git_worker.bzl`)

### Summary
`update_submodules` in [1](#0-0)  unconditionally passes `-c protocol.file.allow=always` to every `git submodule update --init` invocation, for both the plain and recursive submodule paths. This overrides Git's own hardened default (`protocol.file.allow=user`), which upstream Git introduced specifically to stop a cloned/fetched repository's own data (its `.gitmodules` file) from causing local (`file://` / bare-path) submodule clones. Because Bazel forces the permissive value on every `git_repository`/`new_git_repository` fetch that uses `init_submodules` or `recursive_init_submodules`, the content of the fetched remote - which is attacker-influenced whenever the tracked `remote`/`tag`/`branch` points at a repository an attacker can push to or a mutable ref that gets updated upstream - directly controls whether Git performs a local-disk clone as part of the build.

### Finding Description
`git_repo(ctx, directory)` builds up fetch parameters from rule attributes and calls `_update`, which after `fetch`/`reset`/`clean` runs `update_submodules(ctx, git_repo, recursive=...)` whenever `init_submodules` or `recursive_init_submodules` is set [2](#0-1) . Both branches of `update_submodules` add `-c protocol.file.allow=always` to the `git submodule update --init [--recursive] --checkout --force` command [1](#0-0) .

`protocol.file.allow=always` is exactly the setting Git added (as a fix for the local-clone hardlink/data-exfiltration issue commonly tracked as CVE-2022-39253) to gate whether Git will honor a submodule URL that resolves to a local filesystem path (`file://...` or a bare local path) rather than a network transport. The submodule URLs live in `.gitmodules`, which is ordinary tracked content of the fetched repository - i.e., data supplied by whoever controls the commit/tag/branch that `git_repository.remote` currently resolves to. Once fetched, that data is fed straight into `git submodule update`, and with the override in place Git will happily perform a "local clone" of whatever path the attacker wrote into `.gitmodules`, including hard-linking git objects from that path into the new submodule's object database and then checking them out into the workspace.

Note that this override is not confined to the one Bazel issue (#17040) it was intended to fix (submodule paths that are themselves local mirrors added deliberately by the repo owner). It applies uniformly to every submodule fetch, so a compromised or malicious upstream that a build depends on via `git_repository(..., init_submodules = True)` or `recursive_init_submodules = True` can smuggle a `.gitmodules` entry pointing at an arbitrary local path on the machine performing the build (e.g. another checked-out repository, a CI cache directory, or any other `.git` directory reachable on disk) and have Bazel's own `git` invocation clone it, exfiltrating its history/objects into the external repository that later becomes part of the build.

### Impact Explanation
This breaks the containment invariant that fetched repository content should stay confined to the sandboxed external-repository checkout: an attacker who controls the content of a `remote` (or a ref within it) that a `git_repository`/`new_git_repository` rule tracks can, via `.gitmodules`, force Bazel's own git process to read and copy the contents of another local Git repository/directory on the build machine into the checkout, when `init_submodules`/`recursive_init_submodules` is enabled. That leaked content then flows into the build (via generated files/targets) and can be exfiltrated in build outputs - a read outside the intended repository/exec-root boundary triggered purely by attacker-controlled repository data.

### Likelihood Explanation
Requires `init_submodules = True` or `recursive_init_submodules = True` on the `git_repository`/`new_git_repository` rule (both legitimate, commonly used options, not attacker controlled) and requires the tracked remote/ref to be one an attacker can influence (a compromised upstream, a malicious fork used as a mirror, or a mutable branch/tag). No local machine access, no MITM, and no modification of trusted root BUILD/MODULE files is needed by the attacker - only write access to the content of the dependency being fetched.

### Recommendation
Do not globally force `protocol.file.allow=always` for submodule updates. Scope the override narrowly to the specific, intentional Bazel use case (bazel issue #17040), or better, drop the override entirely and let the default `protocol.file.allow=user` semantics stand, so a fetched repository's own `.gitmodules` cannot silently upgrade itself to permission for local-path clones.

### Proof of Concept
A `src/test/shell/bazel/starlark_git_repository_test.sh`-style integration test can reproduce this: create an "attacker" git repository containing a `.gitmodules` file with a submodule URL pointing at a local path outside the intended checkout (e.g. another pre-existing `.git` repository on disk containing a marker file), commit/tag it, then define
```
git_repository(
    name = "victim",
    remote = "<attacker_repo>",
    tag = "malicious",
    recursive_init_submodules = True,
)
```
Building a target depending on `@victim` will invoke `update_submodules` with `protocol.file.allow=always` [1](#0-0) , causing Git to locally clone the attacker-specified path and materialize the marker file's contents inside the `@victim` checkout, demonstrating exfiltration of files outside the repository the rule author intended to fetch.

def _update(ctx, git_repo):
    ctx.delete(git_repo.directory)

    init(ctx, git_repo)
    add_origin(ctx, git_repo, ctx.attr.remote)
    fetch(ctx, git_repo)
    reset(ctx, git_repo)
    clean(ctx, git_repo)

    if git_repo.recursive_init_submodules:
        ctx.report_progress("Updating submodules recursively")
        update_submodules(ctx, git_repo, recursive = True)
    elif git_repo.init_submodules:
        ctx.report_progress("Updating submodules")
        update_submodules(ctx, git_repo)

def update_submodules(ctx, git_repo, recursive = False):
    if recursive:
        # "protocol.file.allow=always" allows the submodule command clone from a local directory.
        # It's necessary for Git 2.38.1 and assoicated backport versions.
        # See https://github.com/bazelbuild/bazel/issues/17040
        _git_maybe_shallow(ctx, git_repo, "-c", "protocol.file.allow=always", "submodule", "update", "--init", "--recursive", "--checkout", "--force")
    else:
        _git_maybe_shallow(ctx, git_repo, "-c", "protocol.file.allow=always", "submodule", "update", "--init", "--checkout", "--force")
