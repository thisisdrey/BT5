### Title
Unbounded Dangling-Reference Growth in Object Pool Enables Housekeeping DoS - ([File: internal/git/objectpool/fetch.go])

### Summary
`FetchIntoObjectPool` fetches from a pool member's repository into the shared object pool and then calls `rescueDanglingObjects`, which parses `git fsck --connectivity-only --dangling` output and creates one `refs/dangling/$OID` reference per dangling object found via `updater.Create` [1](#0-0)  so that no object is ever pruned from the pool [2](#0-1) .

### Finding Description
Any ordinary user who owns a fork linked to an object pool can repeatedly push and then force-update/delete their own branches (a normal, unprivileged Git operation). Each such push causes objects to become unreferenced in the pool member; on the next `FetchIntoObjectPool` housekeeping run (triggered automatically after pushes), every one of those now-unreachable objects gets a permanent `refs/dangling/$OID` reference created in the shared pool repository, one `updateref` "create" call per dangling object, with no cap on how many can be added [3](#0-2) . This is architecturally the same defect as the reported contract bug: an attacker-controlled, unbounded per-victim list (`delegatesOf[_depositorAddress]` there; `refs/dangling/*` in the shared pool here) is grown by an unprivileged actor and then iterated by a routine operation that legitimate users/administrators depend on. The Gitaly documentation explicitly acknowledges the resulting cost: "For busy repositories, we generate loads of dangling references... Fetches into the object pool and repacking of references can thus become quite expensive" [4](#0-3) . Because the object pool is shared across all forks/members, one abusive member's push pattern degrades `FetchIntoObjectPool`, `git-pack-refs`, and `git-repack` housekeeping performance for the entire pool, not just their own repository — the pool's `for-each-ref` and repack operations must walk all dangling refs on every future housekeeping cycle [5](#0-4) .

### Impact Explanation
Because dangling references are never removed (by design, to avoid corrupting other pool members), an unprivileged user can cause monotonic, permanent growth of the reference count in a repository shared by potentially many other users/tenants. This increases the CPU/time cost of every subsequent `FetchIntoObjectPool` call (and its internal `git-pack-refs`, `git-repack`, and `for-each-ref` invocations) for that pool, degrading or effectively denying housekeeping for legitimate members — a resource-exhaustion/DoS class impact analogous to the reported gas-exhaustion DoS, but scoped to Gitaly's housekeeping RPC handler rather than an entire deposit function.

### Likelihood Explanation
Triggering this requires no special privileges: a user only needs push access to their own fork that is a member of an object pool (a standard GitLab fork workflow), and to repeatedly force-push/delete branches to generate unreachable objects. This is a normal, expected Git workflow abused at scale, making the likelihood of accidental or intentional triggering non-trivial, though the severity growth is gradual (proportional to the number of pushes/unreachable objects generated) rather than instantaneous.

### Recommendation
Consider bounding the number of dangling references created per `rescueDanglingObjects` run (e.g., a configurable cap with logging/alerting when exceeded), rate-limiting or batching housekeeping cost per pool member's contribution, or exploring alternative retention mechanisms (e.g., time-boxed generation-based retention combined with cross-member reachability checks) so that a single member cannot unilaterally and permanently inflate the shared pool's reference count.

### Proof of Concept
1. Create an object pool and link a fork (`repo`) to it via the standard fork/object-pool workflow.
2. As the fork owner, repeatedly: push a new commit reachable from a branch, run/trigger `FetchIntoObjectPool` (housekeeping), then force-delete or force-update that branch so the commit's objects become unreachable in the pool member.
3. Repeat step 2 N times; each cycle causes `rescueDanglingObjects` to add new `refs/dangling/$OID` entries permanently to the pool, as demonstrated by the existing test that shows one dangling ref created per dangling object on each `FetchFromOrigin` call [6](#0-5) .
4. Observe that subsequent `FetchIntoObjectPool` calls take increasingly longer as `git fsck --dangling`, `git-pack-refs`, and `git-repack` must process the ever-growing `refs/dangling/*` namespace, degrading housekeeping for all pool members.
