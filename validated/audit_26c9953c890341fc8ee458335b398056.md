### Title
DelegateAction replay after sender rotates (deletes+re-adds) the authorizing access key - ([File: runtime/runtime/src/actions.rs, runtime/runtime/src/access_keys.rs])

### Finding Description
`apply_delegate_action` validates a `DelegateAction`'s nonce against the account's `AccessKey.nonce` field and rejects it with `DelegateActionInvalidNonce` only if `delegate_action.nonce <= access_key.nonce`; on success it stores `access_key.nonce = delegate_action.nonce` back into the same `AccessKey` record used for ordinary transactions [1](#0-0) . When an access key is deleted and later re-added under the same public key, `action_add_key` → `add_regular_key` does not preserve the previous nonce; instead it reseeds it via `initial_nonce_value(block_height) = (block_height - 1) * AccessKey::ACCESS_KEY_NONCE_RANGE_MULTIPLIER` [2](#0-1) [3](#0-2) . Because NEAR's block-height-multiplier nonce convention derives each height's nonce range from `(height-1)*MULTIPLIER`, a `DelegateAction` nonce `D` signed and consumed at height `H0` (typically `D ≈ H0*MULTIPLIER + offset`) can legitimately exceed the reseeded nonce produced when the same key is deleted and re-added at the very next height `H1 = H0+1`, since `(H1-1)*MULTIPLIER = H0*MULTIPLIER < D`. In that case, `current_nonce` (the freshly reseeded `AccessKey.nonce`) drops below `D`, so the `delegate_nonce.nonce() <= current_nonce` guard in `apply_delegate_action` no longer blocks the already-consumed `SignedDelegateAction`, and resubmitting the exact same signed bytes causes it to execute a second time.

### Impact Explanation
If the relayer (or anyone who retained the `SignedDelegateAction` bytes, since the sender or the relayer necessarily possesses them to submit it) resubmits it after the sender's own key rotation, the delegated action(s) — e.g., a transfer/withdrawal or privileged contract call — execute twice, resulting in double-debit/double-credit or double execution of a privileged, single-authorization action. This falls under NEAR's double-spend/replay and authorization-exactness bounty category.

### Likelihood Explanation
The window is narrow: it requires (a) a DelegateAction execute at height `H0` with nonce `D` not at the very bottom of its per-height nonce range, and (b) the account owner deleting and re-adding the exact same public key at height `H0+1` (i.e., immediately next produced block/height touching that account) for unrelated reasons (e.g., key rotation), and (c) the original relayer or another party retaining and resubmitting the identical signed bytes. This does not require attacker privilege over the victim's account — only an unprivileged relayer retaining previously relayed transaction bytes — but it does depend on the victim performing a specific, narrowly-timed self-inflicted key rotation, which the attacker cannot force. This significantly limits real-world repeatability compared to an attacker-triggerable exploit.

### Recommendation
Do not reseed the nonce purely from block height on key re-add when the intent is only to avoid transaction-hash collisions (see near/nearcore#3779); instead persist or otherwise ratchet the previous maximum nonce ever seen for reused public keys, or bind `DelegateAction` nonce validation to a monotonic, per-account (not purely per-key) nonce counter that is never rolled back by delete/add-key cycles.

### Proof of Concept
Test-loop integration test:
1. Create account `alice` with a `FullAccess` key `pk`.
2. Have `alice` sign `SignedDelegateAction` with nonce `D = H0*MULTIPLIER + 1` targeting a transfer to `bob`, submit via relayer at height `H0`; assert it executes once and `access_key.nonce == D`.
3. At height `H0+1`, have `alice` submit `DeleteKey(pk)` followed by `AddKey(pk, FullAccess)` in the same or next receipt.
4. Assert the re-added key's `access_key.nonce == (H0+1-1)*MULTIPLIER == H0*MULTIPLIER`, which is `< D`.
5. Resubmit the identical `SignedDelegateAction` bytes from step 2 via the relayer.
6. Assert it is accepted (no `DelegateActionInvalidNonce` error) and the transfer to `bob` executes a second time — confirming double execution.

```rust
pub(crate) fn initial_nonce_value(block_height: BlockHeight) -> Nonce {
    // Set default nonce for newly created access key to avoid transaction hash collision.
    // See <https://github.com/near/nearcore/issues/3779>.
    (block_height - 1) * near_primitives::account::AccessKey::ACCESS_KEY_NONCE_RANGE_MULTIPLIER
}
```

```rust
fn add_regular_key(
    fee_config: &RuntimeFeesConfig,
    state_update: &mut TrieUpdate,
    account: &mut Account,
    account_id: &AccountId,
    public_key: &PublicKey,
    access_key: &AccessKey,
    block_height: BlockHeight,
) -> Result<(), StorageError> {
    let mut access_key = access_key.clone();
    access_key.nonce = initial_nonce_value(block_height);
    set_access_key(state_update, account_id.clone(), public_key.clone(), &access_key);

    account.set_storage_usage(
        account
            .storage_usage()
            .checked_add(access_key_storage_usage(fee_config, public_key, &access_key))
            .ok_or_else(|| {
                StorageError::StorageInconsistentState(format!(
                    "Storage usage integer overflow for account {}",
                    account_id
                ))
            })?,
    );
    Ok(())
}
```
