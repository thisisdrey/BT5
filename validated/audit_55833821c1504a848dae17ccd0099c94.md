### Title
Snowbridge relayer reward crediting trusts reported `relayer_fee`/tip values without any reserve-backing check before minting foreign ETH on AssetHub - (File: `bridges/snowbridge/pallets/inbound-queue-v2/src/lib.rs`, `bridges/snowbridge/primitives/core/src/reward.rs`)

### Summary
The external report's core invariant break is: a contract credits/mints reward amounts based on a reported number, with no check that the underlying balance actually backs that number, risking an uncontrolled supply increase. The closest analog in this repository is the Snowbridge V2 relayer-reward pipeline, where `relayer_fee`/tip amounts taken from inbound message processing are registered as rewards and later paid out via an XCM instruction that has AssetHub mint/deposit a foreign-asset representation of Ether to the beneficiary — with no on-chain reconciliation against the Ethereum-side locked Ether backing those numbers.

### Finding Description
In `Pallet::process_message`, the pallet takes `relayer_fee` straight from the decoded `Message` and adds any previously-registered `tip` for that nonce, then unconditionally calls `T::RewardPayment::register_reward` to credit the relayer: [1](#0-0) 

Separately, `AddTip::add_tip` lets a tip amount be attached to a not-yet-processed nonce with only two checks — `amount > 0` and the nonce not yet consumed — with no check tying the tip to any specific locked/reserved balance for that nonce: [2](#0-1) 

When the registered reward is later claimed, `BridgeRewardPayer::pay_reward` for the `Snowbridge` reward kind routes to `PayAccountOnLocation::pay_reward`, which constructs an XCM instructing AssetHub to `ReserveAssetDeposited` + `DepositAsset` the reward amount as Ether-denominated foreign asset directly to the beneficiary — i.e., BridgeHub tells AssetHub to deposit (effectively mint into the ForeignAssets pallet) an amount of wrapped ETH with no accompanying proof or check that this amount is actually backed by real Ether locked on the Ethereum side for this specific reward: [3](#0-2) [4](#0-3) 

This is structurally the same defect pattern as the reported `supplyReward()` issue: a numeric "reward owed" value flows from message processing (and, in the `add_tip` case, from an additional caller-supplied number) straight into a mint/deposit instruction with no invariant check comparing total rewards registered/paid against actual backing reserves.

### Impact Explanation
If the numeric fee/tip values that feed `register_reward` and `PayAccountOnLocation::pay_reward` can diverge from real backing Ether (e.g. through a bug in how `add_tip` is invoked from the `system-v2`/`system-frontend` pallets, or a message-processing edge case), the pipeline would mint foreign ETH into `pallet-assets` on AssetHub in excess of what's actually locked on Ethereum, i.e. an uncontrolled increase in the wrapped-ETH total supply — a direct fund-conservation break for the bridge.

### Likelihood Explanation
Likelihood is not fully established: the numbers used (`relayer_fee`, `message.value`, `execution_fee`) are decoded from a `Message` that has already passed through `T::Verifier::verify` against the Ethereum light-client proof, so an unprivileged attacker cannot directly forge them without breaking the light-client/verifier assumption (out of scope per the task's exclusions). The `add_tip` path is more concerning because it is a second, independent numeric input (a tip) merged into the same reward-crediting logic; however, I could not fully verify within the available search budget whether the pallets that expose `add_tip` externally (`system-v2`/`system-frontend`) actually deduct/lock a matching amount from the caller before calling `add_tip`, which is the deciding factor for whether this is exploitable by an ordinary user. This is a gap in my verification, not a confirmed exploit.

### Recommendation
Add an explicit invariant check before crediting or paying out Snowbridge relayer rewards: cross-check accumulated `relayer_fee`/tip amounts (and any `add_tip`-sourced amounts) against a tracked "total Ether locked/received" counter for the bridge, and reject or cap reward registration/payment that would push total registered-but-unclaimed rewards above that backing figure. For `add_tip` specifically, require that the caller's amount be atomically withdrawn/burned (or reserved) from a real balance at the point of calling `add_tip`, rather than trusting a bare `u128` argument.

### Proof of Concept
Not producible with full certainty — the concrete exploit path depends on how `system-v2`/`system-frontend` invoke `AddTip::add_tip` (specifically, whether they deduct real funds from the caller before calling it), which I was unable to fully inspect before the tool budget was exhausted. The concrete, verifiable code pattern demonstrated above is:
1. `process_message` merges `relayer_fee` (from a verified Ethereum message) with `Tips::take(nonce)` and calls `register_reward` unconditionally: `bridges/snowbridge/pallets/inbound-queue-v2/src/lib.rs:234-239`.
2. `add_tip` only checks `amount > 0` and that the nonce isn't consumed — no balance/reserve check: `bridges/snowbridge/pallets/inbound-queue-v2/src/lib.rs:248-258`.
3. Claimed rewards for `BridgeReward::Snowbridge` are paid via an XCM `ReserveAssetDeposited`/`DepositAsset` sequence that has AssetHub deposit the reward amount as foreign ETH with no backing check: `bridges/snowbridge/primitives/core/src/reward.rs:127-151`.

Given the unresolved uncertainty about whether `add_tip`'s caller-side path enforces a matching balance deduction, I present this as the best-supported local analog, but flag that full confirmation would require an engineer to trace the `system-v2`/`system-frontend` call sites of `AddTip::add_tip`.

	impl<T: Config> AddTip for Pallet<T> {
		fn add_tip(nonce: u64, amount: u128) -> Result<(), AddTipError> {
			ensure!(amount > 0, AddTipError::AmountZero);
			// If the nonce is already processed, return an error
			ensure!(!Nonce::<T>::get(nonce.into()), AddTipError::NonceConsumed);
			// Otherwise add the tip.
			Tips::<T>::mutate(nonce, |tip| {
				*tip = Some(tip.unwrap_or_default().saturating_add(amount));
			});
			return Ok(());
		}

	fn pay_reward(
		relayer: &Relayer,
		_: (),
		reward: RewardBalance,
		beneficiary: Self::Beneficiary,
	) -> Result<(), Self::Error> {
		let ethereum_location = Location::new(2, [GlobalConsensus(EthereumNetwork::get())]);
		let assets: Asset = (ethereum_location.clone(), reward.into()).into();

		let xcm: Xcm<()> = alloc::vec![
			UnpaidExecution { weight_limit: Unlimited, check_origin: None },
			DescendOrigin(InboundQueueLocation::get().into()),
			UniversalOrigin(GlobalConsensus(EthereumNetwork::get())),
			ReserveAssetDeposited(assets.into()),
			DepositAsset { assets: AllCounted(1).into(), beneficiary },
		]
		.into();

		let (ticket, fee) =
			validate_send::<XcmSender>(AssetHubLocation::get(), xcm).map_err(|_| XcmSendFailure)?;
		XcmExecutor::charge_fees(relayer.clone(), fee).map_err(|_| ChargeFeesFailure)?;
		XcmSender::deliver(ticket).map_err(|_| XcmSendFailure)?;

		Ok(())
	}
