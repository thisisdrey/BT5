### Title
Uninitialized `accountIndexOf` rewards pre-existing holders `INITIAL_INDEX × balance` while token index is still `INITIAL_INDEX` — (File: contracts/RewardsDistributor.sol)

### Summary
`RewardsDistributor._calculateTokenDelta` treats an `accountIndexOf == 0` account as having accrued rewards since index 0, but only applies the `INITIAL_INDEX` fallback when the global token index is *strictly greater* than `INITIAL_INDEX`. Whenever `tokenStates[token].index == INITIAL_INDEX` (token just registered, or speed is 0 so the index never advances), any account holding a balance of that DepositToken/DebtToken receives `tokensDelta = balance × 1e18`, which can be claimed for the distributor's entire reward-token balance.

### Finding Description
The relevant logic:

```solidity
// contracts/RewardsDistributor.sol:221-231
_tokenIndex = _tokenState.index;
uint256 _accountIndex = accountIndexOf[token_][account_];

if (_accountIndex == 0 && _tokenIndex > INITIAL_INDEX) {
    _accountIndex = INITIAL_INDEX;
}

uint256 _deltaIndex = _tokenIndex - _accountIndex;
_tokensDelta = token_.balanceOf(account_).wadMul(_deltaIndex);
```

When a token is added via `_updateTokenSpeed`, its state is initialized to `index = INITIAL_INDEX` (line 298). The index only moves past `INITIAL_INDEX` in `_calculateTokenIndex` when both `_deltaTimestamps > 0` and `_speed > 0` (lines 203–208). Two reachable windows therefore exist where `index == INITIAL_INDEX`:

1. **Same-block window**: `updateTokenSpeed`/`syncTokenSpeed` registers the token; any interaction in the same block (`deltaTimestamps == 0`) leaves `index == INITIAL_INDEX`.
2. **Zero-speed window**: if speed is set to `0` (or set to `0` later via `updateTokenSpeed`), `_calculateTokenIndex` only bumps the timestamp and the index stays at `INITIAL_INDEX` indefinitely.

During either window, `updateBeforeMintOrBurn` (explicitly permissionless per its docstring) or `claimRewards` calls `_updateTokensAccruedOf`, which computes `_deltaIndex = INITIAL_INDEX - 0 = 1e18` for any account that never interacted with this token, crediting `tokensAccruedOf[account] += balanceOf(account).wadMul(1e18)`. `_transferRewardIfEnoughTokens` then pays out `tokensAccruedOf[account]` up to the full reward-token balance of the distributor.

This is the analog of the CVE-2023-29543 bug class: a stale/dangling global index (`accountIndexOf == 0`, "no recorded position") is dereferenced against the global `INITIAL_INDEX` baseline without being normalized, producing a massive bogus accrual — analogous to reading a freed global-vector pointer as if it were still valid.

### Impact Explanation
Direct theft of unclaimed yield: the first attacker to trigger the path drains the distributor's entire reward-token balance (`amount_ <= _balance` check at line 251), stealing rewards owed to all legitimate depositors/borrowers. With a modest token balance, `balance × 1e18` far exceeds the distributor balance, so payout is capped only by available rewards.

### Likelihood Explanation
Requires no privileged attacker action: `updateBeforeMintOrBurn` is callable by anyone, and `claimRewards(account)` is callable for any account (payout goes to `account`, so the attacker uses their own address holding the deposit/debt token). The exploit needs the token index to equal `INITIAL_INDEX`, which occurs (a) in the same block the governor/keeper registers a token or sets its speed to 0 — attacker can back-run `updateTokenSpeed`/`syncTokenSpeed` in the same block, and (b) persistently whenever a registered token has `tokenSpeeds == 0`, since the index then never advances past `INITIAL_INDEX`. Condition (b) makes the window effectively permanent for paused reward tokens.

### Recommendation
In `_calculateTokenDelta`, treat any `_tokenIndex` at or below `INITIAL_INDEX` as "no accrual yet": change the fallback to `_accountIndex == 0 && _tokenIndex >= INITIAL_INDEX` (or set `_accountIndex = _tokenIndex`), so a never-initialized account starts at the current global index rather than 0. Alternatively, skip accrual when `_tokenIndex <= INITIAL_INDEX`.

### Proof of Concept
Hardhat sketch:

```ts
// Prerequisites: pool, depositToken, rewardsDistributor (rewardToken funded), governor
// 1. Attacker holds depositToken balance B (deposited before reward token registration).
// 2. Governor calls rewardsDistributor.updateTokenSpeed(depositToken, 0)
//    -> token pushed with index = INITIAL_INDEX, speed 0.
// 3. Attacker (same or any later block):
await rewardsDistributor.updateBeforeMintOrBurn(depositToken.address, attacker.address);
//    tokenStates.index == INITIAL_INDEX -> _tokenIndex = 1e18
//    accountIndexOf == 0, and 1e18 > 1e18 is false -> _accountIndex stays 0
//    tokensDelta = B * 1e18 -> tokensAccruedOf[attacker] = B * 1e18
// 4. Attacker claims:
const bal = await rewardToken.balanceOf(rewardsDistributor.address);
await rewardsDistributor.claimRewards(attacker.address);
expect(await rewardToken.balanceOf(attacker.address)).to.eq(bal); // drained
```

Same result in the same block as `updateTokenSpeed(token, speed > 0)` since `deltaTimestamps == 0` prevents the index from advancing past `INITIAL_INDEX`.
