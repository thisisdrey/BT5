### Title
`disable_inv_chat` does not gate `make_tenure_bitvector` computation in `handle_getnakamotoinv`, allowing bounded compute DoS on read endpoint - ([File: stackslib/src/net/chat.rs])

### Finding Description
In `ConversationP2P::handle_getnakamotoinv`, the response to a `GetNakamotoInv` message is built by first calling the tenure-bitvector computation (which performs a disk/chain-state scan via `make_tenure_bitvector` in `stackslib/src/net/inv/nakamoto.rs`) and only afterward checking `self.connection.options.disable_inv_chat` to clear the `tenures` field of the already-constructed `NakamotoInvData`. Because the clearing (`tenure_inv_data.tenures.clear()`) happens strictly after the expensive computation has already run to completion, the `disable_inv_chat` option — whose evident purpose is to cheapen inventory responses — does not prevent the underlying disk scan/compute work from occurring. A remote, unprivileged peer that is already connected can repeatedly send `GetNakamotoInv` requests over a single connection and force the node to redo the full tenure-bitvector computation for each request, with the config flag only discarding the result rather than skipping the computation.

### Impact Explanation
Each `GetNakamotoInv` message forces the target node to perform the full bitvector computation regardless of `disable_inv_chat`, and this can be repeated per message on an already-established connection, giving an attacker a way to burn a bounded amount of CPU/disk I/O on the node's read (inventory) path per message sent. This matches the "bounded compute DoS on a read endpoint" category since the node's own configuration option meant to cheapen these responses provides no actual cost reduction, and the work is proportional to chain-history size rather than gated by the flag.

### Likelihood Explanation
The attacker only needs to be a normal remote P2P peer capable of completing a handshake and sending well-formed `GetNakamotoInv` messages — no secret, StackerDB ownership, or admin role is required. The cost to the attacker is a single small message per request while the node performs disk/computation work per response, making the attack cheap and repeatable as long as the connection remains open (the connection-slot/flood-volume itself is out of scope, but the point here is that even a *single* connection sending sequential requests defeats the intended cost-reduction of `disable_inv_chat`).

### Recommendation
Check `self.connection.options.disable_inv_chat` before invoking `make_tenure_bitvector` (or the equivalent tenure-inventory computation) so that when the option is enabled, the node returns an empty/short-circuited `NakamotoInvData` without performing the underlying scan, rather than computing the full result and discarding it afterward.

### Proof of Concept
Add a benchmark-style test under `stackslib/src/net/tests/inv/nakamoto.rs` that:
1. Constructs a `ConversationP2P` with a `PeerNetwork`/chain state containing many tenures.
2. Sends repeated `GetNakamotoInv` messages, once with `connection.options.disable_inv_chat = false` and once with `= true`.
3. Times `handle_getnakamotoinv` invocations in both cases.
4. Asserts that wall-clock time (or an instrumented call counter on `make_tenure_bitvector`) is not meaningfully reduced when `disable_inv_chat = true`, demonstrating that the computation still runs and only the final `tenures` vector is cleared post-hoc.
