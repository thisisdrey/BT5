### Title
Remote unauthenticated DNS-resolver thread exhaustion via attacker-controlled `data_url` in P2P handshake - (File: `stackslib/src/net/dns.rs`, `stackslib/src/net/chat.rs`)

### Summary
The Stacks P2P `Handshake` message lets any remote peer supply an arbitrary `data_url` hostname, which the node later resolves via a single-threaded, blocking `DNSResolver`. Because DNS resolution runs serially on one dedicated thread (`DNSResolver::thread_main`) and each lookup performs a blocking `to_socket_addrs()` call, an attacker can supply many distinct unresolvable/slow-to-resolve domain names across a small number of handshakes and stall or delay resolution for the whole node — the same class of bug as the Keycloak advisory, where untrusted proxy-supplied values (there `X-Forwarded-*` values, here a peer-supplied `data_url`) trigger costly, unvalidated DNS resolution that ties up limited processing resources.

### Finding Description
`Conversation::try_resolve_data_url_host` in [1](#0-0)  is invoked for every conversation whose `data_url` has not yet been resolved. If `try_decode_data_url_ipaddr` fails to parse the URL as a literal IP address ( [2](#0-1) ), the code proceeds to queue a DNS lookup for the domain name found in the (attacker-supplied) `data_url` field via `dns_client.queue_lookup(domain, port, deadline)` ( [3](#0-2) ).

That request is serviced by `DNSResolver`, which is a **single background thread** that pulls requests off a shared queue and resolves them one at a time using a blocking OS call: [4](#0-3) [5](#0-4) 

There is no validation that the hostname is "reasonable" (no length/charset/rate limiting beyond the existing `max_inflight` in-flight cap, and no per-peer quota) before it is handed to `to_socket_addrs()`, which for a non-existent or slow-responding authoritative server can block for the OS resolver's full timeout (which can be tens of seconds depending on the platform's `resolv.conf`/`getaddrinfo` retry behavior). Because the resolver drains and processes requests **serially in one thread** (`for _ in 0..self.max_inflight { ... handle_query ... }`), a handful of malicious peers that each present handshake data with distinct malicious/black-holed domain names can occupy every in-flight slot with slow lookups, delaying or starving legitimate DNS resolutions needed for real functionality (e.g., mempool sync data-URL resolution in `mempool_sync_begin_resolve_data_url`, [6](#0-5) , and Atlas attachment download URL resolution in `BatchedDNSLookupsState::try_proceed`, [7](#0-6) ).

This breaks the same equality/assumption as the Keycloak advisory: an unauthenticated, remote, attacker-controlled value (there, a proxy header; here, the P2P handshake's `data_url`) is trusted enough to trigger a costly, blocking network operation (DNS resolution) without rate-limiting or sanity-checking the value first, tying up a shared, limited resource (the sole DNS worker thread) and causing degraded service for legitimate lookups.

### Impact Explanation
This is a bounded compute/availability DoS on a background service (DNS resolution for peer/mempool/Atlas data URLs), reachable from a small number of unauthenticated handshake messages rather than requiring high traffic volume — it fits the "High - bounded compute DoS" category referenced in scope. It does not corrupt consensus state or allow unauthorized writes, so it is not Critical.

### Likelihood Explanation
Handshake messages are processed before authentication of any kind is meaningfully imposed on peer identity (any peer can complete a handshake and advertise a `data_url`), so the `data_url` field is fully attacker-controlled. The DNSResolver design (single thread, serial processing, blocking resolve call) has been unchanged in the reviewed code, meaning the exploitation only requires establishing a modest number of P2P connections and sending handshakes with adversarial hostnames (e.g., domains delegated to a non-responsive nameserver) — low complexity, no special privileges.

### Recommendation
- Impose a hard timeout on individual DNS resolutions performed in `DNSResolver::resolve` (e.g., via a timeout wrapper around `to_socket_addrs()`), rather than relying solely on request queue-level `is_timed_out()` bookkeeping which does not preempt an in-progress blocking call.
- Rate-limit and cap the number of distinct domains resolved per peer/IP for `data_url` handling in `Conversation::try_resolve_data_url_host`.
- Consider validating hostnames against a basic sanity policy (length, format) and/or performing resolution with a bounded number of concurrent worker threads instead of a single thread, so that one slow lookup cannot block all others.

### Proof of Concept
1. Start several TCP connections to the target Stacks node's p2p port.
2. Complete a valid `Handshake` on each connection, setting `HandshakeData.data_url` to a distinct hostname whose authoritative DNS server is configured to never respond (black-holed) — one hostname per connection, up to (and beyond) `DNSResolver`'s `max_inflight` limit.
3. Observe that the single `DNSResolver` thread (`stackslib/src/net/dns.rs::DNSResolver::thread_main`) is occupied processing these slow/blocking lookups serially, delaying legitimate DNS lookups needed by other parts of the node (mempool sync `mempool_sync_begin_resolve_data_url`, Atlas `BatchedDNSLookupsState`) until the blocking calls exhaust their OS-level timeout.

    /// Begin resolving the DNS host of a data URL for mempool sync.
    /// Returns Ok(None) if we're done syncing the mempool.
    /// Returns Ok(Some(..)) if we're not done, and can proceed
    /// Returns the new sync state -- either ResolveURL if we need to resolve a data URL,
    /// or SendQuery if we got the IP address and can just issue the query.
    #[cfg_attr(test, mutants::skip)]
    fn mempool_sync_begin_resolve_data_url(
        &self,
        network: &PeerNetwork,
        url_str: UrlString,
        dns_client_opt: &mut Option<&mut DNSClient>,
        page_id: &Txid,
    ) -> Result<Option<MempoolSyncState>, NetError> {
        // start resolving
        let url = url_str.parse_to_block_url()?;
        let port = match url.port_or_known_default() {
            Some(p) => p,
            None => {
                warn!("Unsupported URL {:?}: unknown port", &url);
                return Ok(None);
            }
        };

        // bare IP address?
        if let Some(addr) = PeerNetwork::try_get_url_ip(&url_str)? {
            return Ok(Some(MempoolSyncState::SendQuery(
                url_str,
                addr,
                page_id.clone(),
            )));
        } else if let Some(url::Host::Domain(domain)) = url.host() {
            if let Some(ref mut dns_client) = dns_client_opt {
                // begin DNS query
                match dns_client.queue_lookup(
                    domain,
                    port,
                    get_epoch_time_ms() + network.get_connection_opts().dns_timeout,
                ) {
                    Ok(_) => {}
                    Err(_) => {
                        warn!("Failed to queue DNS lookup on {}", &url_str);
                        return Ok(None);
                    }
                }
                return Ok(Some(MempoolSyncState::ResolveURL(
                    url_str,
                    DNSRequest::new(domain.to_string(), port, 0),
                    page_id.clone(),
                )));
            } else {
                // can't proceed -- no DNS client
                return Ok(None);
            }
        } else {
            // can't proceed
            return Ok(None);
        }
    }
