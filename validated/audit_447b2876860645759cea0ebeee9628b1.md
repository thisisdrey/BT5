### Title
Handshake re-key path skips signature verification of the new claimed public key - ([File: stackslib/src/net/chat.rs])

### Summary
`ConversationP2P::validate_handshake` only calls `message.verify_secp256k1(&handshake_data.node_public_key)` in the `None` branch (i.e., when no public key is yet bound to the connection). In the `Some(_)` branch — reached when a peer re-sends a `Handshake` on an already-authenticated connection — the function performs only an address/port sanity check and never verifies that the newly-claimed `node_public_key` actually signed the message. `update_from_handshake_data` then unconditionally adopts the new key via `self.connection.set_public_key(Some(pubk))`, allowing an attacker to swap their identity mid-session without ever proving possession of the new private key.

### Finding Description
The broken equality: after a "re-key", the public key bound to the conversation (`self.connection`'s stored public key, later used for all future signature checks and for identity in `Neighbor`/PeerDB) should equal the public key that cryptographically produced the handshake message's signature. This equality is not enforced for the `Some(_)` branch.

Code path:
- `handle_handshake` (chat.rs:1214-1296) calls `validate_handshake` (chat.rs:1227).
- `validate_handshake` (chat.rs:1047-1127):
  - `None` branch (chat.rs:1059-1071): calls `message.verify_secp256k1(&handshake_data.node_public_key)` — proves the message (and therefore the claimed key) is self-signed.
  - `Some(_)` branch (chat.rs:1072-1091): only checks `self.peer_addrbytes`/`self.peer_port` against `handshake_data.addrbytes`/`port` for outbound connections. It never calls `verify_secp256k1` against either the old or the new key.
- After `Ok(())` is returned, `handle_handshake` calls `update_from_handshake_data` (chat.rs:1131-1167), which does:
  ```
  let pubk = handshake_data.node_public_key.to_public_key()...
  ...
  self.connection.set_public_key(Some(pubk.clone()));
  ```
  unconditionally replacing the previously-bound key with the attacker-claimed key, and even flags `updated = true` used later (chat.rs:1275-1295) to persist the new key into the `Neighbor` record in PeerDB for outbound connections.

The message-level signature check that authenticates the byte-stream against the peer's currently known key is a separate, prior step (outside `validate_handshake`) that validates the message was signed by the connection's *current* stored key (K1) — this is what sets the `authenticated` flag passed into `handle_handshake`. That outer check only proves the sender still holds K1; it does not, and cannot, prove that the newly-claimed `node_public_key` field (K2) is owned by the sender, because `validate_handshake`'s `Some(_)` branch never performs the K2-ownership check that the `None` branch performs for first-time handshakes.

Attacker exploit flow: attacker completes handshake 1 honestly using key K1 (establishing `self.connection.get_public_key() == Some(K1)`), then crafts handshake 2 whose `Preamble` is signed with K1 (passing the outer per-message authentication) but whose `HandshakeData.node_public_key` field is set to an arbitrary K2 for which the attacker has no private key at all. `validate_handshake` returns `Ok(())` because the `Some(_)` branch does no cryptographic check on K2. `update_from_handshake_data` then rebinds the conversation's identity to K2.

### Impact Explanation
This is an unauthenticated identity takeover mid-session on the P2P port: the node will subsequently treat the conversation/peer entry as belonging to public key K2, without K2 ever having signed anything. For outbound connections, this corruption is persisted to the peer database (`Neighbor::load_and_update` / `neighbor.save_update`, chat.rs:1277-1286), causing this forged identity to be stored and potentially gossiped/relayed to other parts of the network state (peer tables, neighbor walk, StackerDB peer-list logic keyed off peer identity). This matches the Critical category: "unauthenticated ... write to state" and forged data persisted from a single crafted message, repeatable at will by any remote peer that has completed one legitimate handshake.

### Likelihood Explanation
Preconditions are trivial and require no privilege: any unprivileged remote party can open a P2P connection, complete a normal handshake with its own real key K1, and then send a second handshake with the same preamble-signing key K1 but an arbitrary `node_public_key = K2` in the payload. No secret, no privileged role, and no interaction with the signer/consensus/mempool/StackerDB path is needed — this is purely within `stackslib/src/net/chat.rs`'s handshake handling, fully attacker-reachable and repeatable per connection.

### Recommendation
In `validate_handshake`'s `Some(_)` branch, require `message.verify_secp256k1(&handshake_data.node_public_key)` to succeed whenever the claimed `node_public_key` differs from `self.connection.get_public_key()`, exactly mirroring the ownership proof performed in the `None` branch, before allowing `update_from_handshake_data` to rebind the conversation's key.

### Proof of Concept
Rust unit test (in `stackslib/src/net/chat.rs` test module) plan:
1. Build a `ConversationP2P` with `self.connection.set_public_key(Some(K1_pubkey))` to simulate an already-established, authenticated connection.
2. Construct a `StacksMessage` with `StacksMessageType::Handshake(HandshakeData { node_public_key: K2_pubkey_buffer, addrbytes: <matching self.peer_addrbytes>, port: <matching self.peer_port>, expire_block_height: <future>, .. })`.
3. Sign the message's preamble/payload with `K1_privkey` (i.e., call `message.sign(seq, &K1_privkey)` or equivalent used for outer authentication), NOT with `K2_privkey`.
4. Call `conversation.validate_handshake(&local_peer, &chain_view, &mut message)`.
5. Assert the call returns `Ok(())` despite `K2_privkey` never having signed anything.
6. Call `conversation.update_from_handshake_data(&message.preamble, &handshake_data)` and assert `conversation.connection.get_public_key() == Some(K2_pubkey)`, proving the connection's identity was rebound to a key that never produced a valid signature.
