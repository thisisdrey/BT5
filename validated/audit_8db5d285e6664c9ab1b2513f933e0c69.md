## Title
`process_delivery_receipt` pays relayer reward without checking `DeliveryReceipt.success` - ([File: bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs])

### Summary
The Lombard finding boils down to: an async reply/result handler keyed by an ID accepts and acts on that reply without checking whether the reply actually represents a valid/successful outcome for the tracked state. The Snowbridge `outbound-queue-v2` pallet has the same class of gap: `process_delivery_receipt` looks up the `PendingOrder` purely by `nonce`, and unconditionally pays out the relayer fee — it never inspects the `DeliveryReceipt.success` field that the Ethereum Gateway event actually reports.

### Finding Description
`DeliveryReceipt` decoded from the Ethereum `InboundMessageDispatched` event explicitly carries a `success: bool` field indicating whether message dispatch on Ethereum actually succeeded: [1](#0-0) 

`process_delivery_receipt` verifies only the gateway address and that a `PendingOrder` exists for the nonce, then pays the reward and removes the order — the `success` field is read from the log but never checked before paying: [2](#0-1) 

This is exactly the "reply does not match the currently tracked state" bug class from the external report: the reply (`DeliveryReceipt`) is accepted and acted upon (a payout) purely based on its ID (`nonce`) matching an outstanding request (`PendingOrder`), without verifying that the reply's own payload attests to the outcome that justifies the payout (`success == true`).

### Impact Explanation
This falls squarely within the required impact categories: "duplicate settlement or payout" / "message queues, bridge markers, receipts, and payout state must only advance after decode, dispatch, execution, and settlement succeed atomically." Because `success` is ignored, a relayer who submits a valid, verified receipt for a message whose Ethereum-side dispatch actually *failed* still receives full payment of `order.fee`, and the `PendingOrder` is removed as if delivery had succeeded. This misallocates bridge reward funds (funded from the parachain's Ether-fee pool) to relayers for undelivered/failed messages, and permanently discards the pending-order record, precluding any future correct accounting or retry logic keyed off `PendingOrders`.

### Likelihood Explanation
The path is reachable by any unprivileged relayer: `submit_delivery_receipt` is a public, signed extrinsic. The only gates are proof verification (`T::Verifier::verify`) and gateway-address matching — both of which are satisfied by legitimate, correctly-proven Ethereum events, including ones reporting `success = false`. No malicious peer, validator, or governance actor is required — an honest relayer submitting a real (but "success: false") receipt, or forwarding it opportunistically, is sufficient to trigger the incorrect payout.

### Recommendation
In `process_delivery_receipt`, branch on `receipt.success`: only call `T::RewardPayment::register_reward` when the receipt reports `success == true`. When `success == false`, still remove/settle the `PendingOrder` (to avoid indefinite accumulation) but do not pay any reward, and consider emitting a distinct event (e.g. `MessageDeliveryFailed`) so downstream governance/monitoring can react.

### Proof of Concept
1. A message is queued via the outbound-queue-v2 pipeline; a `PendingOrder { nonce, fee, .. }` with `fee > 0` is recorded.
2. The message is delivered to the Ethereum Gateway but its execution reverts/fails; the Gateway still emits an `InboundMessageDispatched(nonce, topic, success=false, reward_address)` event (this is by protocol design — the receipt is emitted regardless of dispatch outcome).
3. A relayer obtains proof of this event and calls `submit_delivery_receipt(event)`.
4. `T::Verifier::verify` succeeds (the proof is legitimate), `DeliveryReceipt::try_from` decodes `success: false`.
5. `process_delivery_receipt` checks `gateway` match and `PendingOrders::get(nonce)` — both pass — and pays `order.fee` to `reward_account` via `T::RewardPayment::register_reward`, then removes the `PendingOrder`, exactly as in the success case shown in `submit_delivery_receipt_succeeds_after_unhalt` test flow: [3](#0-2) 
6. Result: reward paid despite failed delivery, and the pending-order settlement state is finalized incorrectly.

		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}

#[test]
fn submit_delivery_receipt_succeeds_after_unhalt() {
	new_tester().execute_with(|| {
		let nonce = 0;
		let fee: u128 = 1_000_000;
		let order = PendingOrder { nonce, fee, block_number: System::block_number() };
		PendingOrders::<Test>::insert(nonce, order);

		let relayer: AccountId32 = [7u8; 32].into();
		let origin = RuntimeOrigin::signed(relayer);
		let event = Box::new(mock_valid_event_proof());

		// Bridge halted — receipt rejected, order untouched.
		set_verifier_halted(true);
		assert_noop!(
			OutboundQueue::submit_delivery_receipt(origin.clone(), event.clone()),
			Error::<Test>::Verification(VerificationError::Halted)
		);
		assert!(PendingOrders::<Test>::get(nonce).is_some());

		// Bridge resumed — same receipt succeeds and the order is settled.
		set_verifier_halted(false);
		assert_ok!(OutboundQueue::submit_delivery_receipt(origin, event));
		assert!(PendingOrders::<Test>::get(nonce).is_none());

		System::assert_has_event(mock::RuntimeEvent::OutboundQueue(Event::MessageDelivered {
			nonce,
		}));
	});
}
