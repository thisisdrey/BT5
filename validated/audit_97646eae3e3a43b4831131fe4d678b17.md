### Title
Unrate-limited dust transfers let an attacker fill a victim's per-account token list (`MAX_TOKENS_PER_USER`), blocking deposits/borrows of new token types - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
Analogous to CVE-2023-3153 (missing rate limiting → denial of service), `Pool.addToDepositTokensOfAccount` enforces a hard cap of `MAX_TOKENS_PER_USER = 30` combined deposit+debt tokens per account, but there is no rate limit, minimum amount, or opt-in on the path that populates this list. Any holder of a whitelisted `DepositToken` can `transfer` a single wei to a victim, and `DepositToken._transfer` unconditionally calls `pool.addToDepositTokensOfAccount(recipient_)` on a 0→nonzero balance change. Once the victim's list reaches 30 entries, every further first-time deposit, first-time borrow (`DebtToken` calls `addToDebtTokensOfAccount`), and every `transfer`/`seize` of a not-yet-held deposit token to that address reverts with `UserReachedMaxTokens`.

### Finding Description
- `Pool.sol:79` sets `MAX_TOKENS_PER_USER = 30`; `Pool.sol:143-148` reverts in `onlyIfAdditionWillNotReachMaxTokens` when `debtTokensOfAccount.length + depositTokensOfAccount.length >= 30`.
- `DepositToken.sol:498-526` `_transfer` calls `pool.addToDepositTokensOfAccount(recipient_)` whenever `balanceOf[recipient_] == 0 && amount_ > 0` — no minimum amount, no recipient consent.
- `DepositToken.sol:348-354` `transfer` is permissionless; only `_revertIfLocked` checks the *sender*, and dust is always unlocked.
- `DebtToken` performs the symmetric add on issue/mint, so a filled list also blocks `Pool.issue`/`DebtToken.issue` for a synthetic the victim doesn't already hold.
- Nothing else stops this: `transfer` is not behind `whenNotShutdown` restrictions that matter, `nonReentrant` is irrelevant, and the cap check is exactly what the attacker exploits. The attacker only needs dust balances of the whitelisted deposit tokens (obtainable by depositing minimum amounts) — no privileged role.

The one-way asymmetry is the point: the *attacker* adds entries at dust cost, while the *victim* must spend gas per fake entry (transfer dust out to zero the balance, or fully withdraw) before the protocol will accept a new token type — and the attacker can re-grief any slot the victim frees, since they still hold the dusting tokens' supply is not needed: they only need one wei per distinct whitelisted token.

### Impact Explanation
Temporary freezing of funds / liveness: a victim whose list is filled cannot (a) deposit a collateral type they don't already hold, (b) open a debt position in a synthetic they don't already have, or (c) receive transfers of a new msdTOKEN. Practically, an attacker can front-run a victim's `deposit()` of a new collateral — including a rescue deposit intended to heal an unhealthy position and avoid `Pool.liquidate` — by dusting the last free slot, forcing the deposit to revert and exposing the victim to liquidation. The freeze lasts until the victim manually clears dust entries (unbounded griefing is cheap to repeat).

### Likelihood Explanation
Any EOA can execute this with only dust amounts of whitelisted deposit tokens (up to 30 minus the victim's existing entries). No governor, oracle manipulation, flash loan, or malicious infrastructure is required — just repeated calls to `DepositToken.transfer(victim, 1)` (or `transferFrom` with approval). The victim's only mitigations (deposit existing collateral types, repay existing debt) don't always exist, making the griefing reliably exploitable against fresh accounts or accounts near the cap.

### Recommendation
- Gate `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` on a minimum amount or require the action to originate from a deposit/issue context rather than bare `transfer` (e.g., only add on `_mint`, and revert or no-op on incoming transfers — though that changes seize semantics).
- Alternatively, allow recipients to remove entries: expose a `removeFromDepositTokensOfAccount`-style path callable by the account when its balance is dust, or make the cap apply only to tokens minted via `deposit`, not received via `transfer`.
- Document and front-run-protect the rescue path: allow `deposit` into an existing token to bypass the cap (already true) and consider letting liquidations proceed when `seize` would hit the cap by skipping the list add.

### Proof of Concept
```solidity
// SPDX-License-Identifier: MIT
// Foundry-style PoC: dust-fill victim's token list, then their new-collateral deposit reverts
pragma solidity ^0.8.0;

import "forge-std/Test.sol";
import {Pool} from "../contracts/Pool.sol";
import {DepositToken} from "../contracts/DepositToken.sol";
import {IERC20} from "../contracts/dependencies/openzeppelin/token/ERC20/IERC20.sol";

contract MaxTokensGriefingTest is Test {
    Pool pool;
    DepositToken[] depositTokens; // all whitelisted DepositTokens of the pool
    address attacker = address(0xA11CE);
    address victim = address(0xB0B);

    function test_DustFillBlocksNewDeposit() public {
        uint256 max = pool.MAX_TOKENS_PER_USER(); // 30
        uint256 n = depositTokens.length;

        // Attacker obtains dust (1 wei of each msdTOKEN) by depositing minimum
        // underlying into each DepositToken, then dusts the victim.
        for (uint256 i; i < n && i < max; ++i) {
            vm.startPrank(attacker);
            // attacker holds >= 2 wei of depositTokens[i] from an earlier deposit
            depositTokens[i].transfer(victim, 1); // adds depositTokens[i] to victim's list
            vm.stopPrank();
        }

        // Fill any remaining slots with more whitelisted tokens if n < max.
        assertEq(
            pool.getDepositTokensOfAccount(victim).length +
                pool.getDebtTokensOfAccount(victim).length,
            max
        );

        // Victim now tries to deposit a collateral type they don't already hold
        // (e.g., to rescue an unhealthy position). The mint inside deposit()
        // calls addToDepositTokensOfAccount -> UserReachedMaxTokens.
        DepositToken newCollateral = depositTokens[n - 1]; // one not yet held if reserved
        vm.prank(victim);
        vm.expectRevert(Pool.UserReachedMaxTokens.selector);
        // pool.deposit(underlying, amountIn, newCollateral, minOut) — reverts in _mint path
        newCollateral.deposit(1, 0);

        // Any external transfer of a not-held deposit token to victim also reverts:
        vm.expectRevert(Pool.UserReachedMaxTokens.selector);
        vm.prank(attacker);
        newCollateral.transfer(victim, 1);
    }
}
```

Run: `forge test --fork-url <mainnet/base rpc> --match-test test_DustFillBlocksNewDeposit`, using the deployed `Pool` and its whitelisted `DepositToken` addresses from `deployments/mainnet/` or `deployments/base/`. Note the victim can recover by sending the dust back out (zeroing balances triggers `removeFromDepositTokensOfAccount`), so the impact is temporary freezing of the deposit/borrow path plus forced-liquidation risk, not permanent loss — consistent with a Medium-severity liveness analog of the missing-rate-limit bug class.
