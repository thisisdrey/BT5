### Title
Attacker can fill a victim's per-account token lists with dust `DepositToken` transfers to block deposits, borrows and inbound transfers - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
`Pool` enforces a hard cap of `MAX_TOKENS_PER_USER = 30` across `depositTokensOfAccount` + `debtTokensOfAccount` via `onlyIfAdditionWillNotReachMaxTokens` (`Pool.sol:143-148`). `DepositToken.transfer`/`transferFrom`/`seize` and `_mint` call `pool.addToDepositTokensOfAccount(recipient_)` whenever the recipient's balance goes 0 → >0 (`DepositToken.sol:517-520`, `:485-488`). An unprivileged attacker can deposit dust into every listed `DepositToken` (the pool itself caps deposit tokens at 30, `Pool.sol:703`) and transfer 1 wei of each to a victim, permanently occupying all 30 slots. Any subsequent action that would add a new entry for the victim — depositing a new collateral type, issuing a new synthetic (`DebtToken.issue` → `addToDebtTokensOfAccount`), or receiving a `transfer`/`seize` of a token they don't already hold — reverts with `UserReachedMaxTokens`.

### Finding Description
Analogous to the h2 RST_STREAM bug (resources allocated per stream not released), `Pool` allocates a per-account enumerable-set slot on every 0→positive balance transition and only releases it on an explicit balance-to-zero transition initiated by the holder. The attacker controls allocation (permissionless `transfer`), but release requires the victim to move the dust out — which is impossible while the victim's entire balance is locked by an unhealthy position (`_revertIfLocked` / `unlockedBalanceOf`, `DepositToken.sol:383-398`) since the received dust becomes locked too. Nothing in `transfer`, `_transfer`, `addToDepositTokensOfAccount`, or `seize` checks the recipient's slot usage or lets the recipient opt out.

### Impact Explanation
- Victim cannot deposit a collateral type they don't already hold (`_mint` → `addToDepositTokensOfAccount` reverts) and cannot mint a new synthetic (`DebtToken.issue` path reverts).
- Victim cannot receive any deposit token they don't already hold, including via liquidation `seize` (`DepositToken.sol:343-345`), which also makes the victim unattractive/impossible to liquidate into new collateral — a liveness break of liquidation bounds.
- For a victim whose whole balance is locked (`_issuableInUsd == 0`), the dust cannot be transferred out, so the blocking state persists until they repay debt or get liquidated — temporary freezing of funds, matching the accepted impact class. Cost to the attacker is only dust-sized deposits across the pool's deposit tokens.

### Likelihood Explanation
Fully permissionless: only needs public `DepositToken.deposit` + `transfer` calls, no privileged role. Effectiveness depends on how many of the 30 slots the victim already occupies and how many deposit tokens the pool lists (each chain deployment lists several). It is a griefing attack with no direct profit, and the victim can eventually clear slots by repaying/transferring dust when unlocked, so impact is bounded — consistent with a Medium DoS analog.

### Recommendation
- Drop the global `MAX_TOKENS_PER_USER` revert on the recipient side, or exempt inbound `transfer`/`seize` additions while keeping the cap on user-initiated deposits/borrows.
- Alternatively let a recipient remove entries regardless of lock status (e.g., a `Pool`-level `removeFromDepositTokensOfAccount` callable by the account), or skip list insertion for dust amounts below a threshold.

### Proof of Concept
Hardhat sketch (pattern follows `test/Pool.test.ts:1386-1416`):

```ts
// attacker deposits 1 wei of underlying into each listed DepositToken
for (const dt of depositTokens) {
  await underlying.connect(attacker).approve(dt.address, 1);
  await dt.connect(attacker).deposit(1);          // attacker mints dust msdTOKEN
  await dt.connect(attacker).transfer(victim.address, 1); // occupies victim slot
}
// victim now has depositTokensOfAccount.length == MAX_TOKENS_PER_USER
await expect(newDepositToken.connect(victim).deposit(amount))
  .revertedWithCustomError(pool, 'UserReachedMaxTokens');
await expect(debtToken.connect(victim).issue(...)) // via Pool.borrow path
  .revertedWithCustomError(pool, 'UserReachedMaxTokens');
await expect(existingDt.connect(attacker2).transfer(victim.address, 1))
  .revertedWithCustomError(pool, 'UserReachedMaxTokens'); // if not already held
```

Note: severity is mitigated because the victim can free slots by transferring dust back out when their position is healthy, and the attack costs the attacker dust deposits in every listed collateral. If your threat model treats self-recoverable griefing as out of scope (and this cap behavior is a documented design choice from prior audits), this may be judged a known issue — I could not confirm audit history from the repo alone.
