### Title
Unbounded recursion in `debug/dwarf` type parsing allows stack-overflow crash on malicious DWARF data - ([File: src/debug/dwarf/type.go])

### Summary
`Data.readType` in `src/debug/dwarf/type.go` recursively resolves DWARF type DIEs (`TagPointerType`, `TagConstType`, `TagVolatileType`, `TagRestrictType`, `TagArrayType`, `TagTypedef`, `TagSubroutineType`, etc.) by calling itself through the `typeOf` closure for every `AttrType` reference. The function guards against *cycles* via a `typeCache` keyed by DIE offset, but it has no maximum recursion-depth counter, so a long, non-cyclic chain of distinct type DIEs (e.g. thousands of chained `const`/`volatile`/pointer wrapper types, each at a unique offset) drives unbounded Go-stack recursion and can crash the process with a stack overflow. This mirrors the USBX bug class: recursive descent over attacker-supplied nested structure with cycle detection but no depth bound.

### Finding Description
Attacker input: a crafted ELF/Mach-O/PE (or raw `.debug_info`) binary containing a deeply nested, acyclic type-DIE chain (distinct offsets, so `typeCache[off]` never short-circuits).

Entry points: `debug/elf.(*File).DWARF()`, `debug/macho.(*File).DWARF()`, or `debug/pe.(*File).DWARF()`, all of which construct a `dwarf.Data` and eventually call `(*Data).Reader()` / `(*Data).Type(off)`.

Sink: `(*Data).readType` [1](#0-0)  recurses via the `typeOf` closure [2](#0-1)  for every wrapped type such as `TagConstType`/`TagVolatileType`/`TagRestrictType` [3](#0-2) , `TagPointerType` [4](#0-3) , and `TagArrayType`/`TagTypedef`/`TagSubroutineType`. Only cycle protection exists (`typeCache[off]`, checked at line 408); there is no analogue of the depth counters used elsewhere in the standard library (`asn1`'s `maxDecodeDepth`, `encoding/xml`'s `maxUnmarshalDepth`, `encoding/json`'s `maxNestingDepth`, `encoding/gob`'s `maxIgnoreNestingDepth`, `go/parser`'s `maxNestLev`). A chain of N distinct wrapper DIEs therefore produces O(N) Go stack frames with no cutoff, unlike every other recursive-descent parser in this codebase, all of which were hardened after prior CVEs (CVE-2022-30632 for `path/filepath.Glob`, CVE-2022-24675 for `encoding/pem`, etc., visible in the surrounding test files).

### Impact Explanation
A sufficiently deep type chain causes a Go runtime stack-overflow fatal error (`runtime: goroutine stack exceeds … limit`), crashing the process. Any tool built on `debug/dwarf`/`debug/elf`/`debug/macho`/`debug/pe` to introspect an untrusted binary (symbolizers, crash-dump analyzers, container/malware scanners, `go tool` utilities, delve-style debuggers) is affected. This is a denial-of-service via a crafted file consumed in a normal victim workflow — this would land on Go's PUBLIC track as a low/medium-severity crash bug (not memory corruption, no code execution), analogous to the historical fixes already applied to `encoding/asn1`, `encoding/xml`, `encoding/gob`, `encoding/json`, and `path/filepath` for the same bug class.

### Likelihood Explanation
The victim workflow is: load an attacker-supplied compiled object/binary with `debug/elf.NewFile` (or macho/pe), call `.DWARF()`, then iterate via `Reader()`/`Type()`. This is unauthenticated/ordinary in the sense that the attacker only needs to control the input binary, not any host or credentials — the same premise as parsing an untrusted disk image in the USBX case. Constructing valid-but-deeply-chained DWARF DIEs is straightforward with a raw `.debug_info` byte builder (no compiler needed), and DWARF abbreviation/entry parsing itself imposes no depth limit before `readType` is reached.

### Recommendation
Add an explicit recursion-depth counter (threaded through `readType`/`typeOf`, similar to `maxDecodeDepth` in `encoding/asn1` or `maxNestLev` in `go/parser`) and return a `DecodeError` once a reasonable maximum (e.g., a few thousand) is exceeded, independent of the existing cycle-detection cache.
