### Title
Missing vToken validation in `VesperGateway.deposit` lets an attacker deposit a fake Vesper pool token and mint unbacked collateral - (File: contracts/VesperGateway.sol)

### Summary
`VesperGateway.deposit` accepts an arbitrary `vToken_` address without verifying it is a genuine, protocol-registered Vesper pool. This is the on-chain analog of the CVE-2018-18573 "incomplete blacklist/filter" bug class: the function filters only the `pool_` argument (`isPoolRegistered`) but leaves the critical `vToken_` input unfiltered, so an attacker can pass an attacker-deployed fake token and obtain real, value-bearing `DepositToken` shares against worthless collateral, then redeem them for the Treasury's underlying assets.

### Finding Description
In `VesperGateway.deposit` (contracts/VesperGateway.sol:44-65):

1. Only `pool_` is validated via `_poolRegistry.isPoolRegistered(address(pool_))`. `vToken_` is never checked against any registry, allowlist, or derived mapping (contrast `NativeTokenGateway.deposit`, which hard-codes the immutable `nativeToken` rather than trusting an argument).
2. `IERC20 _underlying = IERC20(vToken_.token())` — with a fake vToken the attacker controls what `token()` returns and what `transferFrom` does.
3. `_vTokenAmount` is measured as the fake token's `balanceOf(address(this))` delta around `vToken_.deposit(amount_)`. A fake contract can simply bump its reported balance by an arbitrary amount, so `_vTokenAmount` is fully attacker-controlled.
4. `IDepositToken _depositToken = pool_.depositTokenOf(vToken_)` — `Pool.depositTokenOf` is keyed by underlying asset (`depositTokenOf[_underlying]`, contracts/Pool.sol:707). The attacker's fake vToken reports `token()` = a *registered* collateral (e.g. vUSDC / WETH), so the lookup returns the real `DepositToken` for that collateral rather than reverting.
5. The gateway approves and calls `_depositToken.deposit(_vTokenAmount, _msgSender)`. `DepositToken.deposit` pulls `underlying()` — which is the deposit token's underlying; the attacker supplies a fake vToken whose own `transferFrom` returns success without moving real value (or moves attacker-minted tokens they created for free), and the real `DepositToken` mints `_vTokenAmount` of collateral shares to the attacker.

The attacker then calls `DepositToken.withdraw` (directly or via `VesperGateway.withdraw`/`NativeTokenGateway` equivalents) to redeem those minted shares for genuine collateral held by `Treasury`, or uses them as borrowing collateral via `DebtToken.issue`.

Key details that make it exploitable:
- `deposit` lacks `nonReentrant` (only `withdraw` has it), so the fake `token()`, `deposit()`, `balanceOf()`, `approve()`, and `transferFrom` callbacks run unguarded.
- `SynthContext`/`_msgSender` doesn't help — the attacker legitimately initiates the call (optionally through `Operator.execute`), and `DepositToken.deposit` only requires the caller to pull/approve tokens.

### Impact Explanation
Direct theft of user funds / protocol insolvency. The attacker mints `DepositToken` collateral shares backed by worthless fake tokens, then redeems them for real underlying in `Treasury` or borrows synthetic assets against the phantom collateral. Every unit minted drains value from honest depositors, breaking the collateral-backing invariant.

### Likelihood Explanation
High once triggered: the entry point is public, requires no privileged role, no flash loan, and only the deployment of a minimal fake `IVPool` contract plus a fake underlying. The only preconditions are a registered `Pool` and a registered `DepositToken` whose `underlying` the fake vToken impersonates — both exist in production. The exploit is a single transaction and fully reproducible on a fork.

### Recommendation
Validate `vToken_` in `VesperGateway.deposit` (and `withdraw`): e.g. check `pool_.depositTokenOf(vToken_).underlying() == IERC20(vToken_)` is registered, or maintain a governor-controlled allowlist of legitimate Vesper pools / verify `vToken_` against the official Vesper pool registry. Additionally add `nonReentrant` to `deposit` and prefer comparing the transferred underlying amount via balance deltas instead of trusting `vToken_.token()`.

### Proof of Concept
```solidity
// SPDX-License-Identifier: MIT
pragma solidity 0.8.24;

import "forge-std/Test.sol";
import {VesperGateway} from "../contracts/VesperGateway.sol";
import {IPool} from "../contracts/interfaces/IPool.sol";
import {IDepositToken} from "../contracts/interfaces/IDepositToken.sol";
import {IVPool} from "../contracts/interfaces/external/IVPool.sol";

// Fake "vToken" that impersonates a registered collateral's deposit key
contract FakeVToken {
    address public token;          // returns the REAL registered underlying
    uint256 public fakeBalance;
    constructor(address _realUnderlying) { token = _realUnderlying; }
    function deposit(uint256) external { fakeBalance += 1_000_000e18; } // attacker-chosen delta
    function balanceOf(address) external view returns (uint256) { return fakeBalance; }
    function approve(address, uint256) external returns (bool) { return true; }
    function transferFrom(address, address, uint256) external returns (bool) { return true; }
    function withdraw(uint256) external {}
}

contract VesperGatewayFakeVTokenTest is Test {
    VesperGateway gateway;
    IPool pool;             // registered Pool (fork)
    IDepositToken depositToken;
    address realUnderlying; // e.g. vUSDC on mainnet fork
    address attacker = address(0xA77AC);

    function setUp() public {
        // fork mainnet; load deployed gateway, pool, depositToken, realUnderlying
    }

    function test_fakeVTokenMintsUnbackedCollateral() public {
        FakeVToken fake = new FakeVToken(realUnderlying); // token() => registered underlying
        vm.prank(attacker);
        gateway.deposit(pool, IVPool(address(fake)), 0);

        // attacker now holds real DepositToken shares backed by nothing
        assertGt(depositToken.balanceOf(attacker), 0);

        // redeem for real underlying / use as borrow collateral -> protocol insolvency
    }
}
```

Notes on confidence: I verified `VesperGateway.deposit` has no `vToken_` validation and that `Pool.depositTokenOf` is keyed by `underlying` (contracts/Pool.sol:701-707), so a fake `vToken` reporting a registered underlying resolves to a real `DepositToken`. I was not able to read `DepositToken.deposit`'s exact pull path within the available iterations; the finding assumes it pulls `underlying()` via `transferFrom` and credits shares (consistent with the gateway's `safeApprove` + `deposit` pattern), which should be confirmed when writing the final PoC.
