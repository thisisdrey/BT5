Audit Report

## Title
Relayer reward is irrecoverably burned when the cross-chain `PayAccountOnLocation` reward XCM fails to execute on AssetHub - (File: `bridges/snowbridge/primitives/core/src/reward.rs`)

## Summary
`pallet-bridge-relayers::do_claim_rewards` removes the relayer's accumulated reward from `RelayerRewards` storage and treats the claim as final once `T::PaymentProcedure::pay_reward` returns `Ok(())`. For Snowbridge rewards, `PayAccountOnLocation::pay_reward` only validates and delivers a fire-and-forget XCM to AssetHub — it returns success once the message is queued for delivery, not once the remote `DepositAsset` has actually executed, so a remote execution failure permanently destroys the reward with no compensation path.

## Finding Description
`do_claim_rewards` in `bridges/modules/relayers/src/lib.rs` uses `RelayerRewards::try_mutate_exists` and calls `maybe_reward.take()`, unconditionally removing the reward entry from storage before invoking the payment procedure; only an `Err` return from the closure rolls the mutation back. [1](#0-0) 

For `BridgeReward::Snowbridge`, the beneficiary must be an `AssetHubLocation`, dispatched to `PayAccountOnLocation::pay_reward`, which builds an XCM program of `UnpaidExecution`, `DescendOrigin(InboundQueueLocation)`, `UniversalOrigin(GlobalConsensus(Ethereum))`, `ReserveAssetDeposited`, and `DepositAsset { beneficiary }`, and returns `Ok(())` as soon as `XcmSender::deliver` succeeds — i.e., once the message is handed to the outbound queue, not once `DepositAsset` executes on AssetHub. [2](#0-1)  No `SetAssetClaimer` instruction is included in this program.

If `DepositAsset` fails on AssetHub (e.g., beneficiary does not satisfy ED for the newly reserve-deposited foreign asset, or execution is otherwise rejected), the XCM executor's `post_process`/`deposit_assets_with_retry` path traps the undeposited holding via `Config::AssetTrap::drop_assets`, keyed by the effective origin at that point — which, due to the preceding `DescendOrigin`/`UniversalOrigin` instructions, is a virtual, Ethereum/InboundQueue-anchored interior location rather than a location the relayer or beneficiary can produce a matching signed origin for via `pallet_xcm::claim_assets`. [3](#0-2) [4](#0-3) 

Meanwhile, on BridgeHub the `RelayerRewards` entry is already gone and `RewardPaid` has already fired by the time this remote failure could occur, and there is no receipt/confirmation mechanism analogous to `process_delivery_receipt`'s pending-order pattern to detect the failure and re-credit the reward. [5](#0-4) 

## Impact Explanation
A relayer that has legitimately earned a Snowbridge reward can permanently lose it if the `DepositAsset` on AssetHub fails for the chosen beneficiary — for example, an unfunded/fresh account not meeting the existential deposit for the minted foreign asset, or an account reaped between claim submission and remote execution. The reward is not restored on BridgeHub (already debited) and not claimable on AssetHub (trap origin is not the beneficiary/relayer's controllable origin). This matches the "permanent user-fund or bridge-state lock" impact category since bridge relayer reward funds are irrecoverably destroyed with no retry or undo path.

## Likelihood Explanation
This is triggerable without any malicious actor: `claim_rewards_to` is a public, unprivileged extrinsic (`ensure_signed`), and any legitimate relayer choosing (or having) a beneficiary account that fails ED/registration checks on AssetHub deterministically hits this path. [6](#0-5)  No privileged access, leaked keys, or malicious infrastructure is required — only ordinary operational conditions on the remote chain at the time of XCM execution.

## Recommendation
- Do not finalize removal of the `RelayerRewards` entry until remote settlement on AssetHub is confirmed; use a pending/in-flight marker analogous to the `PendingOrders` pattern used in `outbound-queue-v2`, finalized only upon a delivery/execution confirmation.
- Always include a `SetAssetClaimer` instruction (pinned to the relayer or beneficiary's real, reachable origin) in the `PayAccountOnLocation` XCM program so a failed `DepositAsset` traps assets under a claimable origin.
- Alternatively, wire a response/error-handling callback that credits the reward back into `RelayerRewards` on observed remote failure.

## Proof of Concept
1. Relayer accrues a Snowbridge reward via `register_reward`; `RelayerRewards::<T,I>::get(relayer, Snowbridge)` returns the balance.
2. Relayer calls `claim_rewards_to(BridgeReward::Snowbridge, BridgeRewardBeneficiaries::AssetHubLocation(beneficiary))` where `beneficiary` has no existing entry (fails ED) for the minted foreign asset on AssetHub.
3. `do_claim_rewards` removes the `RelayerRewards` entry, calls `PayAccountOnLocation::pay_reward`, which validates/delivers the XCM and returns `Ok(())`; `RewardPaid` fires on BridgeHub.
4. On AssetHub, `DepositAsset` fails ED check; the holding is trapped under the `DescendOrigin(InboundQueueLocation)+UniversalOrigin(Ethereum)` virtual origin.
5. Verify `RelayerRewards::<T,I>::get(relayer, Snowbridge)` is `None` on BridgeHub, and confirm via `pallet_xcm::claim_assets` from any real signed origin that the trapped assets cannot be recovered (`UnknownClaim` due to origin mismatch).

	fn pay_reward(
		relayer: &Relayer,
		_: (),
		reward: RewardBalance,
		beneficiary: Self::Beneficiary,
	) -> Result<(), Self::Error> {
		let ethereum_location = Location::new(2, [GlobalConsensus(EthereumNetwork::get())]);
		let assets: Asset = (ethereum_location.clone(), reward.into()).into();

		let xcm: Xcm<()> = alloc::vec![
			UnpaidExecution { weight_limit: Unlimited, check_origin: None },
			DescendOrigin(InboundQueueLocation::get().into()),
			UniversalOrigin(GlobalConsensus(EthereumNetwork::get())),
			ReserveAssetDeposited(assets.into()),
			DepositAsset { assets: AllCounted(1).into(), beneficiary },
		]
		.into();

		let (ticket, fee) =
			validate_send::<XcmSender>(AssetHubLocation::get(), xcm).map_err(|_| XcmSendFailure)?;
		XcmExecutor::charge_fees(relayer.clone(), fee).map_err(|_| ChargeFeesFailure)?;
		XcmSender::deliver(ticket).map_err(|_| XcmSendFailure)?;

		Ok(())
	}

impl<T: Config> DropAssets for Pallet<T> {
	fn drop_assets(origin: &Location, holding: AssetsInHolding, _context: &XcmContext) -> Weight {
		if holding.is_empty() {
			return Weight::zero();
		}
		let assets: Vec<Asset> = holding.assets_iter().collect();
		// SAFETY: "forget" about any fungible imbalances so that they are not dropped/resolved
		// here. The mirrored asset claiming operation will "recover" the imbalances by minting
		// back into holding, effectively duplicating the imbalance and only then dropping the
		// duplicate. As a result, total issuance doesn't change.
		holding.fungible.into_iter().for_each(|(_, mut accounting)| {
			accounting.forget_imbalance();
		});
		let versioned = VersionedAssets::from(Assets::from(assets));
		let hash = BlakeTwo256::hash_of(&(&origin, &versioned));
		AssetTraps::<T>::mutate(hash, |n| *n += 1);
		Self::deposit_event(Event::AssetsTrapped {
			hash,
			origin: origin.clone(),
			assets: versioned,
		});
		// TODO #3735: Put the real weight in there.
		Weight::zero()
	}
