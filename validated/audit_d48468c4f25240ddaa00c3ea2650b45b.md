### Title
Precision loss from division-before-multiplication in legacy vote-reward calculation - (File: `chainbase/src/main/java/org/tron/core/service/MortgageService.java`)

### Summary
`MortgageService.computeReward(long cycle, List<Pair<byte[], Long>> votes)` computes a voter's per-cycle SR reward using floating point division followed by multiplication, then truncates to `long`, causing systematic rounding-down precision loss on every legacy-cycle reward calculation, analogous to the reported `Cooler.interestFor()` div-before-mul issue.

### Finding Description
The vulnerable code: [1](#0-0) 

```java
private long computeReward(long cycle, List<Pair<byte[], Long>> votes) {
  ...
  double voteRate = (double) userVote / totalVote;
  reward += voteRate * totalReward;
  ...
}
```
This divides `userVote` by `totalVote` first (producing a `double` with limited precision, and losing exact integer semantics), then multiplies by `totalReward`, and the accumulated `double` result is implicitly cast to `long` when returned — truncating any fractional remainder toward zero rather than rounding correctly. This is the exact same anti-pattern the external report flags: dividing before multiplying, using floating point instead of exact integer/`BigInteger` arithmetic, and truncating down instead of rounding up in favor of the party providing capital (here, the voter/staker delegating TRON Power).

This function is reached via `computeReward(beginCycle, endCycle, accountCapsule)` at [2](#0-1)  → `getOldReward` at [3](#0-2)  which loops per-cycle and repeatedly accumulates the truncated `double` reward — compounding the loss across many cycles for accounts that voted before `newRewardAlgorithmEffectiveCycle`.

This is directly reachable by any account via a single signed `WithdrawBalanceContract` transaction: `WithdrawBalanceActuator.execute` calls `mortgageService.withdrawReward(...)`, which calls `computeReward(beginCycle, endCycle, accountCapsule)` for the caller's own vote list. [4](#0-3) 

By contrast, the newer reward algorithm (`RewardViCalService`/`VoteRewardUtil`) correctly performs multiply-then-divide using `BigInteger`, avoiding this precision loss: [5](#0-4) 

### Impact Explanation
Each per-cycle reward computed via the legacy path can lose a fractional unit of TRX due to the double-precision division-before-multiplication and truncating cast to `long`. Over many cycles (an account can accumulate up to `newRewardAlgorithmEffectiveCycle` legacy cycles of unclaimed rewards), the cumulative underpayment grows, permanently under-crediting voters relative to their proportional share of `totalReward`. This is a fund-accounting precision/rounding defect in the on-chain reward ledger reachable by any ordinary account that delegated votes before the new algorithm took effect — matching the Medium severity and rounding-direction concern of the original report (rounding should favor the capital provider, i.e., the voter, not be silently truncated toward the protocol).

### Likelihood Explanation
Any account that voted for SRs prior to the `newRewardAlgorithmEffectiveCycle` and calls `WithdrawBalanceContract` (or any code path invoking `withdrawReward`/`queryReward`) will trigger this computation. Because this is the historical/legacy code path still present and reachable, and the effective cycle is a per-network parameter, this is deterministically triggered on every affected withdrawal — not a rare edge case.

### Recommendation
Replace the double-based `voteRate` computation in `computeReward(long cycle, List<Pair<byte[], Long>> votes)` with exact integer arithmetic that multiplies before dividing (mirroring the fix already applied in the new algorithm), e.g. using `BigInteger`:
```java
BigInteger reward = BigInteger.valueOf(userVote)
    .multiply(BigInteger.valueOf(totalReward))
    .divide(BigInteger.valueOf(totalVote));
```
and accumulate as `long`/`BigInteger` without ever converting through `double`, consistent with how `VoteRewardUtil.computeReward` and `RewardViCalService.getNewRewardAlgorithmReward` already do it.

### Proof of Concept
1. Set up an SR with `totalVote = 3`, `totalReward = 10` (from `delegationStore.getReward(cycle, srAddress)`), and a voter with `userVote = 1`.
2. Exact proportional share is `10 * 1 / 3 = 3.333...`; ideally the voter should receive `3` (floor) or `4` (ceiling favoring voter) consistently, matching integer math.
3. With the current code: `voteRate = (double)1/3 = 0.3333333333333333`; `reward += voteRate * 10 = 3.333333333333333`; after accumulation across multiple cycles and the final truncating cast to `long` in `withdrawReward`/`queryReward`, small fractional losses occur per cycle and compound, versus the exact `BigInteger` computation `1*10/3 = 3` used consistently by the new algorithm — demonstrating the same class of precision defect as the reported `interestFor()` issue.
