### Title
Remote panic via `assert!(preamble.payload_len > 1)` in `ConversationP2P::validate_stackerdb_push` - (File: `stackslib/src/net/chat.rs`)

### Summary
`ConversationP2P::validate_stackerdb_push` unconditionally asserts that the message preamble's `payload_len` is greater than 1 before doing any bandwidth/relay bookkeeping for a pushed StackerDB chunk: [1](#0-0) 

This mirrors the reported bug class: an operation is executed unconditionally assuming a precondition ("there's always at least 1 byte of payload beyond the type prefix") that a remote, unprivileged sender fully controls and can violate, causing the assumed-safe path to fail catastrophically (a Rust `assert!` panic aborts/crashes the process) instead of gracefully rejecting the malformed input, exactly as the Convex Solidity code assumed "the reward delta is never legitimately zero" and reverted on the edge case.

### Finding Description
`preamble.payload_len` is a field of the wire `Preamble` that is populated directly from an untrusted peer's message before dispatch to message-specific handlers such as `validate_stackerdb_push`. The function relies on `payload_len` correctly reflecting the serialized payload size (a StackerDB chunk push message must be at least 1 byte for its type prefix plus data), and instead of validating this defensively with a runtime check that returns `Err(net_error::...)`, it uses a hard Rust `assert!`, which will `panic!` and unwind/abort the thread if a malicious peer crafts (or a malformed/short) a `StackerDBPushChunk` message whose preamble declares `payload_len <= 1`.

Unlike the length/size gates seen elsewhere in the same subsystem — e.g. `StackerDBs::try_replace_chunk`'s explicit `chunk.len() as u64 > self.config.chunk_size` check that returns an `Err`, and `PeerNetwork::validate_received_chunk`'s explicit oversize/size checks that return `Ok(false)` — this one code path substitutes a debug-style assertion for a proper validation-and-reject flow: [2](#0-1) [3](#0-2) 

If the decoder that constructs/validates `Preamble.payload_len` for incoming P2P messages does not itself independently enforce `payload_len > 1` specifically for the `StackerDBPushChunk`/data-message type before `validate_stackerdb_push` is invoked, then a remote peer that is otherwise unauthenticated w.r.t. this specific check (any connected P2P peer, since this runs on the "unsolicited" push-chunk path) can trigger the assertion failure with a single crafted message.

### Impact Explanation
An assertion panic in a message-handling hot path is a remote, unauthenticated (or only network-connection-authenticated, not StackerDB-signer-authenticated) crash vector reachable with a single malformed/crafted P2P message — this matches the "Critical: remote crash / unauthenticated DoS from few messages" bucket in the rules. It is a direct architecture-level analog of the Convex bug: code assumes an invariant ("payload always has content beyond the 1-byte discriminator") holds for all valid protocol traffic and enforces it via an unconditional hard-fail primitive (`assert!`/revert-on-empty-transfer) rather than a graceful, per-message validation-and-reject, so a caller who legitimately (or maliciously) triggers the edge case brings down the operation instead of being cleanly rejected.

### Likelihood Explanation
Reaching `validate_stackerdb_push` requires only an established P2P connection and sending a `StackerDBPushChunk` message; I could not, within the available tool budget, conclusively verify whether the shared preamble/message decoder in `stackslib/src/net/codec.rs` already enforces `payload_len > 1` uniformly for every message type before dispatch (my search for `payload_len` usage in `codec.rs` returned matches, but I was not able to inspect them in the final iteration). This is the key uncertainty: if the general decoder already rejects `payload_len <= 1` for all message types before any handler runs, this specific `assert!` is dead code and unreachable from an attacker's perspective; if the decoder only enforces a lower bound of `payload_len >= 1` (i.e., allows exactly 1), or if this check can be bypassed for certain message framing paths, the assert is directly reachable by a remote peer.

### Recommendation
Replace the `assert!(preamble.payload_len > 1, ...)` in `validate_stackerdb_push` with an explicit fallible check that returns `Err(net_error::InvalidMessage)` (or similar) when the condition is not met, consistent with how `try_replace_chunk` and `validate_received_chunk` reject malformed/oversized chunks by returning typed errors instead of panicking. Additionally, verify in `codec.rs` that `payload_len` bounds are enforced uniformly and defensively at deserialization time for every message variant, not assumed by individual handlers.
