### No vulnerability found for this question.

The `execute_extension` function in `contracts/wallet/src/contract.rs` enforces both required guards before reaching `execute_request`: it rejects a zero attached deposit and validates that `env::predecessor_account_id()` is present in the wallet's own `extensions` set via `check_extension_enabled` [1](#0-0) . The `w_execute_extension` trait method requires a `#[payable]` call and delegates directly to `execute_extension`, so there is no alternate no-sign entry point that skips these checks [2](#0-1) , and the generated contract wrapper via the `wallet!` macro also marks the method `#[payable]` without bypassing the guard [3](#0-2) .

Regarding the "no-sign" schema and "sibling subwallet deployment" angle: the `NoSign` schema always returns `false` from `verify_request_msg`/`verify_offchain_msg`, which only affects `w_execute_signed` (blocking that path entirely, per `execute_signed`'s `is_signature_allowed` check) — it has no effect on `execute_extension`, which never invokes signature verification in the first place [4](#0-3) [5](#0-4) . The `w_init` for the no-sign variant explicitly disables signature and enables only the current account itself as extension, and this is by design, documented as a "1-of-M multisig"/"fan-out" pattern [6](#0-5) .

Each wallet instance (including subwallets derived from the same public key with different `subwallet_id`) is a separate on-chain contract with its own independent state, including its own `extensions: BTreeSet<AccountId>` [7](#0-6) . There is no message replay mechanism for extension requests — authorization is derived purely from `env::predecessor_account_id()` checked against that specific instance's own stored extension set at call time, not from any signed/replayable payload. Consequently, "replaying" a request against a sibling subwallet deployment does not bypass the `check_extension_enabled` check: the attacker's account would still need to be present in that particular sibling's extension set, which requires legitimate prior authorization (by the signer or another enabled extension) via `add_extension` [8](#0-7) .

The fast-validation scenario described (calling `w_execute_extension` from a non-enabled predecessor, or with zero deposit) is exactly what the existing guards in `execute_extension` reject.

    fn execute_extension(&mut self, request: Request) -> Result<()> {
        if env::attached_deposit().is_zero() {
            return Err(Error::InsufficientDeposit);
        }

        // check whether extension is enabled
        let extension_id = env::predecessor_account_id();
        self.check_extension_enabled(&extension_id)?;

        // maybe cleanup nonces from the storage as best-effort to make it
        // available for further applying wallet-ops below
        self.0.nonces.check_cleanup();

        self.execute_request(request, &Actor::Extension(extension_id.into()))
    }

impl Contract {
    /// Initialize a wallet contract on the existing account
    /// with authentication by signature disabled and
    /// add the current account as an extension.
    ///
    /// This method is allowed to be called only by the current
    /// account itself. It's recommended to call this method
    /// in the same receipt right after `UseGlobalContract` action.
    ///
    /// MUST attach at least 1yN for security reasons.
    #[cfg_attr(not(near), allow(dead_code))]
    #[allow(clippy::use_self)]
    #[private]
    #[payable]

    pub fn w_init() -> Self {
        if env::attached_deposit().is_zero() {
            // reject FunctionCall access keys
            Error::InsufficientDeposit.panic();
        }

        let mut s = State::new(NoPublicKey)
            // Add self as the only extension
            .extensions([env::current_account_id()]);

        // Disable signature verification completely,
        // so that accidently removing self from extensions
        // would result into lockout error.
        s.signature_enabled = false;

        Self(s.into())
    }
