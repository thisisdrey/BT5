### Title
`native_withdraw` burns signer's wNEAR with no refund on failed NEAR transfer - ([File: contracts/defuse/src/contract/tokens/nep141/native.rs])

### Summary
`Contract::do_native_withdraw` unwraps wNEAR into NEAR via `near_withdraw` and then executes `Promise::new(withdraw.receiver_id).transfer(withdraw.amount)` with no callback to check the outcome of the transfer and no refund path back to the signer's Defuse balance. If the transfer fails (e.g., `receiver_id` is a non-existent account), the already-debited wNEAR is gone and the unwrapped NEAR is refunded by the NEAR runtime to the *contract's own account*, not credited back to the signer.

### Finding Description
The claimed binding is: `signer_id`'s `Nep141TokenId(wnear_id)` balance debited by `withdraw()` in `Contract::native_withdraw` (contracts/defuse/src/contract/intents/state.rs:212-221) must equal NEAR delivered to `withdraw.receiver_id` OR refunded back into `signer_id`'s Defuse-tracked balance.

Trace:
1. `native_withdraw` calls `self.withdraw(owner_id, [(Nep141TokenId(wnear_id), amount)], ...)`, which performs `internal_sub_balance` immediately, permanently removing the wNEAR from the signer's ledger entry inside the Verifier. [1](#0-0) 
2. It then chains `ext_wnear::near_withdraw` followed by `Self::do_native_withdraw(withdraw)` as a callback, both detached with no result inspection at the `native_withdraw` call site. [2](#0-1) 
3. `do_native_withdraw` only asserts that `near_withdraw` itself succeeded, then issues `Promise::new(withdraw.receiver_id).transfer(withdraw.amount)` as the final, un-awaited action of the function - there is no further `.then(...)` callback checking whether this transfer receipt succeeds, and no logic anywhere to re-credit the signer if it fails. [3](#0-2) 

Root cause: unlike token withdrawals (`ft_withdraw`/`nft_withdraw`/`mt_withdraw`), which resolve through NEP-141/171/245 `resolve_transfer` callbacks that re-credit the owner on failure, `native_withdraw`'s final `Promise::transfer` has no resolution step. On NEAR, a `Transfer` action targeting an account ID that does not exist fails during receipt application, and the deposit is refunded to the *predecessor of that failed receipt* — the Defuse contract's own account balance — not to any account inside the Defuse internal ledger. The signer's internal wNEAR balance was already permanently subtracted in step 1 and is never restored, so the value is lost to the signer with no way to reclaim it through the contract's public interface.

Existing guards do not catch this: `promise_result_checked_void` only checks the `near_withdraw` unwrap step, not the subsequent transfer; there is no `#[private]` resolve callback wrapping the transfer to allow re-crediting; and `withdraw()`'s `is_call` flag (`false`) means this isn't treated as a revertible token transfer with resolver semantics the way FT/NFT/MT withdrawals are.

### Impact Explanation
Any signer can destroy their own wNEAR balance inside the Verifier by naming a `receiver_id` whose `Transfer` action reverts (non-existent account, or an account requiring more attached balance than the transfer provides for storage), with no NEAR reaching the intended receiver and no re-credit to the signer's Defuse balance. This is a case of "user funds permanently frozen" — the wNEAR debited from the Verifier's books is not matched by any recorded liability discharge, and the underlying NEAR ends up stranded in the contract account, inaccessible via any signed intent. This directly matches the Critical impact category for user funds permanently frozen. The bug is repeatable per-account/per-attempt since any signer can trigger it against their own balance at will.

### Likelihood Explanation
Preconditions are minimal and entirely within an unprivileged attacker's control: hold a wNEAR balance inside Defuse (via ordinary deposit), sign a `NativeWithdraw` intent naming a `receiver_id` guaranteed to make the final transfer revert (e.g., an account ID with no matching NEAR account, which is trivial and free to choose). No privileged role, relayer key, or victim key is required — the attacker only harms themselves, but the finding is about the missing refund safety net, which equally exposes any legitimate user who makes a typo or targets a deleted/never-created account, and it demonstrates the Verifier's balance-sheet invariant (all debits match a delivered credit or a refund) is violated by design for this specific withdrawal path.

### Recommendation
Add a `#[private]` resolver callback after the `Promise::transfer` in `do_native_withdraw` that inspects the transfer's promise result, and on failure re-credits `withdraw.amount` of `Nep141TokenId(wnear_id)` back to the original owner's Defuse balance (mirroring the refund pattern already used for `ft_withdraw`/`nft_withdraw`/`mt_withdraw`). Since a failed `Transfer` action returns the NEAR to the contract account itself, the contract additionally needs to re-wrap that NEAR into wNEAR (or otherwise account for it) before crediting it back internally, to keep the wNEAR supply backing consistent.

### Proof of Concept
```rust
// near-workspaces sandbox test, contracts/defuse (test crate, outside src/)
#[tokio::test]
async fn native_withdraw_to_nonexistent_account_burns_wnear() {
    // setup: deploy defuse contract + wnear contract
    // signer deposits `amount` wNEAR into their own Defuse balance
    let signer_balance_before = get_defuse_wnear_balance(&signer_id).await;
    let contract_near_before = get_account_near_balance(&defuse_id).await;

    // signer signs & submits execute_intents with:
    // NativeWithdraw { receiver_id: "zzz.near" (no such account exists), amount }
    execute_intents(vec![payload_with_native_withdraw(
        signer_id.clone(),
        "zzz.near".parse().unwrap(),
        amount,
    )]).await;

    // wait for all promises/callbacks to settle

    let signer_balance_after = get_defuse_wnear_balance(&signer_id).await;
    let receiver_balance = get_account_near_balance("zzz.near").await; // 0, account doesn't exist
    let contract_near_after = get_account_near_balance(&defuse_id).await;

    // Binding under test:
    // signer_balance_before - signer_balance_after (debited)
    //   == receiver_balance_delta + refund_credited_to_signer
    let debited = signer_balance_before - signer_balance_after;
    let refund_credited_to_signer = signer_balance_after_recovery_attempt(); // via any subsequent intent, should be 0

    assert_eq!(debited, amount);
    assert_eq!(receiver_balance, 0); // no NEAR delivered
    assert_eq!(refund_credited_to_signer, 0); // no refund to signer's Defuse ledger

    // demonstrates: debited (amount) != delivered (0) + refunded (0)
    assert_ne!(debited, 0 + refund_credited_to_signer);
}
```
