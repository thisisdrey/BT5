### Title
TokenDiff fee exemption for NEP-245/IMT amounts ≤ 1 allows fee-free atomization of larger trades - (File: `contracts/defuse/core/src/intents/token_diff.rs`)

### Summary
`TokenDiff::token_fee` returns `Pips::ZERO` for any `Nep245`/`Imt` `TokenId` whenever the per-intent delta magnitude is `<= 1`, and the fee is computed strictly per `TokenDiff` intent rather than per aggregate token movement across a batch. An unprivileged signer can therefore split one intended transfer/swap of `A` units of a divisible MT/IMT asset into `A` separate `TokenDiff` intents of `delta == -1` (matched by corresponding `+1` deposits, e.g. from a second account they control), collecting `0` total fees instead of `Pips::fee_ceil(fee, A)`.

### Finding Description
The broken binding is:
`sum(fees_collected for token T across all TokenDiff intents in a batch) == protocol_fee.fee_ceil(sum(|negative deltas of T|))`

In `TokenDiff::execute_intent` (`contracts/defuse/core/src/intents/token_diff.rs:56-78`), for each negative delta the fee is computed independently per intent:
```
let amount = delta.unsigned_abs();
let fee = Self::token_fee(token_id, amount, protocol_fee).fee_ceil(amount);
```
`Self::token_fee` (`contracts/defuse/core/src/intents/token_diff.rs:206-216`) explicitly zeroes the fee for `Nep245`/`Imt` when `amount <= 1`:
```rust
TokenIdType::Nep245 | TokenIdType::Imt if amount > 1 => {}
// do not take fees on NFTs and MTs with |delta| <= 1
TokenIdType::Nep171 | TokenIdType::Nep245 | TokenIdType::Imt => return Pips::ZERO,
```
This check is scoped to the *single intent's* `amount`, not to the total quantity of the token moved across the whole `execute_intents` batch. Since `TransferMatcher::finalize` (`contracts/defuse/core/src/engine/state/deltas.rs:267-283`) only enforces that the sum of all deltas across the batch nets to zero per token (no per-intent minimum size or per-token aggregate fee check), an attacker can post `A` intents each with `delta = -1` on the same `TokenId`, each matched by a corresponding `+1` deposit (which they can supply themselves via a second account they control, since positive deltas never incur fees either). Each of the `A` legs individually satisfies `amount == 1`, so `token_fee` returns `Pips::ZERO` for every leg, and `fees_collected` for that token across the batch is `0`, versus `protocol_fee.fee_ceil(A) > 0` if the same net movement had been expressed as one `TokenDiff` intent with `delta == -A`.

No existing guard prevents this: `MultiPayload::verify`, nonce/salt checks, and `#[pause]`/`access_control_any` guard signature/replay/authorization, not per-token fee aggregation; `TransferMatcher::finalize` only guarantees balance conservation, not fee correctness.

### Impact Explanation
Protocol fee revenue owed to `engine.state.fee_collector()` is under-collected/bypassed entirely for the atomized token, while the net balance change for all parties (including the fee-collector) is identical to the unsplit case minus the fee. This falls into the explicitly listed Critical category "protocol fees bypassed or over-collected." It is repeatable for any account, any `Nep245`/`Imt` `TokenId` with `ContractState.fees.fee > Pips::ZERO`, and any batch size, and does not require any privileged role — only two accounts the attacker controls (or a cooperative/oblivious counterparty) and gas to submit `2A` intents.

### Likelihood Explanation
Preconditions: the token must be a NEP-245/IMT `TokenId`, deposited/held in the Defuse balance, and `fees.fee > Pips::ZERO`. The attacker needs no special role — any two accounts they control (or any willing counterparty) and enough NEAR to pay for `2A` signed intents in the batch. Cost scales with `A` (gas and payload size), which bounds the practicality for very large `A`, but the exploit is fully general and profitable whenever the saved fee (`fee.fee_ceil(A)`) exceeds the marginal gas cost of splitting, which is trivially true for moderate `A` and non-trivial fee rates.

### Recommendation
Compute and enforce `token_fee`/`fee_ceil` based on the aggregate negative delta observed per `TokenId` across the whole batch (i.e., inside `TransferMatcher`/`finalize`, after summing withdrawals per token), rather than per individual `TokenDiff` intent. Alternatively, remove or tighten the NEP-245/IMT `amount <= 1` fee exemption so it only applies to token ids that are provably non-fungible (e.g., `Nep171`), not to semi-fungible NEP-245/IMT balances that can be freely fragmented into unit-sized legs.

    // Finalizes all transfers, or returns unmatched deltas.
    // If unmatched deltas overflow, then Err(None) is returned.
    pub fn finalize(self) -> Result<Transfers, InvariantViolated> {
        let mut transfers = Transfers::default();
        let mut deltas = TokenDeltas::default();
        for (token_id, transfer_matcher) in self.0 {
            if let Err(unmatched) = transfer_matcher.finalize_into(&token_id, &mut transfers)
                && (unmatched == 0 || deltas.apply_delta(token_id, unmatched).is_none())
            {
                return Err(InvariantViolated::Overflow);
            }
        }
        if !deltas.is_empty() {
            return Err(InvariantViolated::UnmatchedDeltas {
                unmatched_deltas: deltas,
            });
        }
        Ok(transfers)
    }
