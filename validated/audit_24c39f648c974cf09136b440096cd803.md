### Title
Race between `ProcReceiveRegistry.Transmit` and waiter cleanup can hang the `ProcReceiveHook` RPC and its backing git-receive-pack process - ([File: internal/gitaly/hook/procreceive_registry.go])

### Summary
`ProcReceiveRegistry` implements a rendezvous between (a) the receive-pack RPC (SSH/HTTP push) that registers a waiter for a `storage.TransactionID` and (b) the `ProcReceiveHook` RPC invoked back into Gitaly by git's `proc-receive` hook subprocess, which calls `Transmit()` to hand off the `ProcReceiveHandler`. The handoff uses an unbuffered channel guarded by a map, and the "give up waiting" path (`cleanup()`+closing `receiveDoneCh`) is not synchronized against `Transmit()` reading that same channel from the map, mirroring the discv5 class of bug where a message can arrive at the exact moment the receiving side decides it is done waiting and tears down its side of the rendezvous, leaving the sender blocked.

### Finding Description
`RegisterWaiter` stores a channel in `r.waiters[id]` and returns a `cleanup` func that deletes the map entry: [1](#0-0) 

`Transmit` looks the channel up under the mutex, releases the mutex, and then blocks trying to send on it (bounded only by the *hook RPC's own context*, not by the waiter's lifecycle): [2](#0-1) 

The receive-pack side spawns a goroutine that races three cases — context cancellation, an explicit "receive done" signal, or actually consuming the handler — and its cleanup callback first unregisters the waiter, then closes `receiveDoneCh`, then waits for `handlerErrCh`: [3](#0-2) 

There is a window between `Transmit()` reading `ch, ok := r.waiters[...]` (line 104) and actually sending on `ch` (line 116), during which `cleanup()`/`close(receiveDoneCh)` (lines 63/66 of `receive_pack.go`) can run concurrently. If the waiter goroutine's `select` (lines 51–58 of `receive_pack.go`) picks the `<-receiveDoneCh` branch instead of `case handler := <-handlerCh`, the goroutine exits and nobody will ever read from `ch` again. `Transmit()` is then stuck in its `select` at lines 113–117, with only `<-ctx.Done()` as an escape — and that `ctx` is the *`ProcReceiveHook` stream's own context*, tied to the git `proc-receive` subprocess connection, not to the (already-finished) receive-pack RPC.

This is structurally the same defect class as the referenced discv5 fix: a response ("the handler") can arrive at `Transmit()` after the consumer has already decided it received "enough" (i.e., invoked its cleanup/done path), and the dispatch/rendezvous mechanism has no synchronization to prevent the resulting deadlock.

### Impact Explanation
If triggered, `Transmit()` blocks until the `ProcReceiveHook` gRPC stream's context is cancelled. That context is only torn down when the underlying git `proc-receive` hook process/connection ends — but that process (`git-receive-pack`'s proc-receive hook) is itself blocked inside the `ProcReceiveHook` RPC call waiting for `Transmit` to return, creating a stuck git subprocess for the duration of an ordinary push. This ties up a worker goroutine, the receive-pack execution pipeline, and any repository-level locks/references held by the in-flight `git-receive-pack` process, until the client eventually times out or disconnects. This is a resource-exhaustion/DoS vector reachable from an ordinary authenticated push using the proc-receive/transactional path, not a privileged or malicious-peer scenario.

### Likelihood Explanation
This requires the race window between `Transmit()`'s map lookup and channel send to overlap with `cleanup()`+`close(receiveDoneCh)` in `RegisterProcReceiveHook`. That cleanup path fires whenever the receive-pack RPC finishes or errors out before proc-receive hands off its handler (e.g., early client disconnect, a race between hook process startup and receive-pack completion, timeout). Because this is a benign timing race under ordinary operation (no attacker control needed beyond normal push behavior/timing), it is plausible but not trivially/deterministically reproducible — I could not fully verify from the indexed code how often/whether `git-receive-pack` actually invokes the `proc-receive` hook concurrently with the RPC's completion path in practice, nor examine the full callers in `internal/gitaly/service/ssh/receive_pack.go` and `internal/gitaly/service/smarthttp/receive_pack.go` due to the search cutting off before the file content was returned.

### Recommendation
Synchronize `Transmit()` and waiter teardown under a single critical section: e.g., have `Transmit()` and `cleanup()` both `select`/act while holding `r.m` so that once a waiter is removed, any prior `Transmit()` call fails fast instead of blocking, or make the removal itself close the channel so `Transmit()`'s send unblocks immediately with an error. Alternatively, give `Transmit()` a bound tied to the *waiter's* lifecycle (e.g., pass in the receive-pack `ctx`/`receiveDoneCh` via the registry) rather than relying solely on the unrelated `ProcReceiveHook` stream context.

### Proof of Concept
Not independently reproducible from the indexed code alone; the race requires precise interleaving between `ProcReceiveRegistry.Transmit` (internal/gitaly/hook/procreceive_registry.go:102-120) and `RegisterProcReceiveHook`'s cleanup path (internal/gitaly/hook/receivepack/receive_pack.go:50-72), i.e. cleanup()/close(receiveDoneCh) executing concurrently with a Transmit() call for the same transaction ID such that the waiter goroutine selects the receiveDoneCh branch instead of consuming from handlerCh. A background Devin session with access to a full checkout and a running test harness would be needed to construct a deterministic repro (e.g., a targeted unit test in `internal/gitaly/hook/procreceive_registry_test.go` that forces this interleaving with synchronization channels, similar to existing tests in that package).

```go
func (r *ProcReceiveRegistry) RegisterWaiter(id storage.TransactionID) (<-chan ProcReceiveHandler, func(), error) {
	r.m.Lock()
	defer r.m.Unlock()

	if _, ok := r.waiters[id]; ok {
		return nil, nil, fmt.Errorf("cannot register id: %d again", id)
	}

	ch := make(chan ProcReceiveHandler)
	r.waiters[id] = ch

	cleanup := func() {
		r.m.Lock()
		defer r.m.Unlock()

		delete(r.waiters, id)
	}

	return ch, cleanup, nil
}
```

```go
// Transmit transmits a handler to its waiter.
func (r *ProcReceiveRegistry) Transmit(ctx context.Context, handler ProcReceiveHandler) error {
	r.m.Lock()
	ch, ok := r.waiters[handler.TransactionID()]
	r.m.Unlock()

	if !ok {
		return fmt.Errorf("no waiters for id: %d", handler.TransactionID())
	}

	// It is possible that the RPC (waiter) returned because receive-pack
	// returned an error. In such scenarios, we don't want to block indefinitely.
	select {
	case <-ctx.Done():
		return ctx.Err()
	case ch <- handler:
	}

	return nil
}
```
