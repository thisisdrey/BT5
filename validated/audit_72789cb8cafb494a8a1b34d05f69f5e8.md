### Title
`StackerDBTx::try_replace_chunk` invokes expensive ECDSA-recovery `verify()` before the cheap version-staleness check, enabling per-message compute-DoS amplification - (File: stackslib/src/net/stackerdb/db.rs)

### Summary
`try_replace_chunk` checks chunk size and slot existence first, but then calls the expensive `slot_desc.verify(&slot_validation.signer)?` (secp256k1 signature recovery) *before* comparing `slot_desc.slot_version` against the already-known `slot_validation.version`. Since the version comparison is a cheap integer check that requires no cryptography, doing it after the signature-recovery step forces the node to spend non-trivial CPU on every rejected chunk (whether the signature is invalid or the chunk is simply stale), instead of rejecting cheaply first.

### Finding Description
The relevant ordering in `try_replace_chunk` is: [1](#0-0) 

1. `chunk.len() as u64 > self.config.chunk_size` — cheap size cap check.
2. `get_slot_validation(...)` — cheap SQLite lookup returning the slot's `signer` and current `version`.
3. `slot_desc.verify(&slot_validation.signer)?` — **expensive** secp256k1 public-key recovery over attacker-controlled `slot_desc`/signature bytes.
4. `slot_desc.slot_version <= slot_validation.version` — cheap integer comparison ("stale chunk") check, performed **after** step 3.

Because step 4 (version-staleness rejection) only needs `slot_validation.version` (already fetched in step 2) and the wire-supplied `slot_desc.slot_version`, it could be evaluated immediately after step 2, without ever touching the signature. Instead, the current code unconditionally performs the ECDSA-recovery `verify()` call on every incoming chunk that passes the size and slot-existence checks, regardless of whether the supplied version is stale or the signature is bogus. This means a message that would be trivially rejectable via version comparison alone still pays the full cost of signature recovery.

An attacker (a legitimate slot owner, or even any peer submitting slot_id/slot_version pairs for an existing slot with an arbitrary or replayed signature) can flood the chunk-push path with messages carrying:
- an existing `slot_id` (passes existence check),
- an old/stale `slot_version` (would fail the cheap version check),
- any signature bytes (valid or garbage).

Every such message forces one secp256k1 recovery operation in `verify()` before being rejected by the version check, instead of being rejected immediately by the cheap version comparison.

### Impact Explanation
This does not result in forged/stored state — `insert_chunk` is never reached for these malicious inputs since `verify()` or the version check will reject them. The impact is purely computational: each message costs one non-trivial ECDSA-recovery operation that could have been avoided by reordering checks. This matches the "bounded compute DoS" category: a remote, unprivileged party who can reach the StackerDB chunk-push path can force repeated signature-recovery work on the node with low-cost, easily-repeatable messages (stale-but-signed or arbitrary-signature chunks against real slot IDs).

### Likelihood Explanation
- Preconditions: attacker needs to know or discover a valid `smart_contract` and `slot_id` for an existing StackerDB (these are generally public/discoverable via the contract and inv-message metadata), and can supply arbitrary/replayed signature bytes and a stale `slot_version`.
- No secret, no privileged role, and no prior successful write is required — only the ability to submit a chunk-push message (P2P or RPC) that reaches `try_replace_chunk`.
- Fully repeatable: attacker can flood such messages continuously since each one is cheap to construct but forces a fixed CPU cost (signature recovery) on the receiving node before rejection.
- Remote reachability: reachable by any unprivileged peer able to gossip/push StackerDB chunks, matching the specified threat model.

### Recommendation
Reorder the checks in `try_replace_chunk` so that the cheap, wire-derived comparisons are evaluated before the costly cryptographic verification:
1. size cap check,
2. slot existence check (`get_slot_validation`),
3. version-staleness check (`slot_desc.slot_version <= slot_validation.version`),
4. `max_writes` check,
5. only then call `slot_desc.verify(&slot_validation.signer)?`,
6. then `insert_chunk`.

This ensures that a flood of stale-version chunks (with or without valid signatures) is rejected via a cheap integer comparison instead of paying for ECDSA recovery on every message.
