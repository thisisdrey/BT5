### Title
Unprivileged attacker can saturate a victim's per-account token list (`depositTokensOfAccount` / `debtTokensOfAccount`) to DoS deposits, transfers and debt issuance — (File: contracts/Pool.sol, contracts/DepositToken.sol)

### Summary
Analogous to the unsynchronized shared-map crash in the reference report, Metronome maintains a shared per-account enumerable set (`MappedEnumerableSet.AddressSet depositTokensOfAccount` / `debtTokensOfAccount`) that is mutated as a side effect of ordinary token flows, and whose cardinality is hard-capped at `MAX_TOKENS_PER_USER = 30` (combined deposit + debt tokens). An unprivileged attacker can force entries into a victim's set without the victim's consent, causing subsequent `addToDepositTokensOfAccount` / `addToDebtTokensOfAccount` calls to revert with `UserReachedMaxTokens`, denying service.

### Finding Description
`Pool.sol` enforces `MAX_TOKENS_PER_USER = 30` across the combined per-account deposit and debt token lists, reverting with `UserReachedMaxTokens` when the cap is reached [1](#0-0) . Entries are added to a victim's set as a side effect of receiving any `msdTOKEN` balance:

- `DepositToken._transfer` calls `pool.addToDepositTokensOfAccount(recipient_)` whenever the recipient's balance was previously zero [2](#0-1) .
- `DepositToken._mint` does the same on the recipient of a `deposit(amount_, onBehalfOf_)`, where `onBehalfOf_` is attacker-chosen [3](#0-2) , and `deposit` only checks `onBehalfOf_ != 0` [4](#0-3) .

So the attacker can fill the victim's list by either:

1. Calling `depositToken.deposit(dustAmount, victim)` on each of the pool's supported deposit tokens (up to `MAX_TOKENS_PER_USER` distinct collaterals; cost is dust collateral + gas), or
2. Acquiring a small balance of each `msdTOKEN` and calling `transfer(victim, 1 wei)` — the same `addToDepositTokensOfAccount` path is hit on first receipt, and the sender's list entry is removed only if their balance hits zero [5](#0-4) .

Once the victim's combined deposit/debt token count reaches 30:

- Any deposit of a **new** collateral type reverts (its `_mint` → `addToDepositTokensOfAccount` hits `UserReachedMaxTokens`).
- Receiving any `msdTOKEN` the victim doesn't already hold reverts (`transfer`, `transferFrom`, and liquidation `seize` → `_transfer` all go through the same hook [6](#0-5) ), which also makes the victim's position unliquidatable for collateral types they don't already hold — a liveness break for liquidations.
- Issuing debt in a synthetic asset the victim doesn't already hold reverts via `addToDebtTokensOfAccount` (same cap, `contracts/storage/PoolStorage.sol` [7](#0-6) ).

Existing balances are not frozen — `withdraw`/`transfer` of tokens already held still works because `_burn`/transfer removes entries only at zero balance — so the correct impact classification is **temporary freezing of funds / reachable denial of service** on new deposits, new debt, transfers-in, and liquidations.

### Impact Explanation
The shared-state invariant broken is liveness: per-account list cardinality is attacker-mutable without the account's consent. Concretely: (a) victim cannot onboard new collateral or borrow new synthetics until they manually clear dust positions (each `transfer`/`withdraw` to zero out a dust token costs gas and requires acquiring knowledge of which tokens were injected); (b) `seize` during `Pool.liquidate` reverts if the seized collateral isn't already in the liquidator's/victim's set, degrading liquidation availability; (c) the attack can be re-applied cheaply whenever the victim cleans up. This matches the accepted impact "temporary freezing of funds."

### Likelihood Explanation
Fully unprivileged: the only capabilities needed are a public `deposit()`/`transfer()` call and dust amounts of each supported underlying — no privileged role, oracle manipulation, or malicious infrastructure required. On pools with many listed collaterals the cost is bounded by ~30 dust deposits/transfers. Mitigating factor: recovery is possible (transfer dust out to shrink the set), which is why impact is temporary rather than permanent freezing.

### Recommendation
- Check the cap only on the **acting** account (e.g. enforce the limit in `deposit`/`issue` against `onBehalfOf_`/recipient rather than inside the token-transfer hook), or only count entries added via `deposit`, not inbound `transfer`s.
- Alternatively, allow anyone to call `removeFromDepositTokensOfAccount(account)`-style cleanup for dust balances, or exempt zero-value/dust receipts from adding entries (e.g. minimum threshold).
- Ensure `seize`/liquidation paths cannot revert due to the recipient list cap — liquidations should not be gated on `MAX_TOKENS_PER_USER`.

### Proof of Concept
Reproducible on a Hardhat/Foundry fork of a deployed pool with ≥2 listed deposit tokens:

```solidity
// Fork mainnet Pool with N deposit tokens listed
IPool pool = IPool(POOL);
address victim = makeAddr("victim");
address[] memory dts = pool.getDepositTokens();

// Attacker fills victim's list to MAX_TOKENS_PER_USER with dust
uint256 max = pool.MAX_TOKENS_PER_USER();
for (uint256 i; i < dts.length && pool.getDepositTokensOfAccount(victim).length < max; ++i) {
    IERC20 underlying = IDepositToken(dts[i]).underlying();
    deal(address(underlying), attacker, 1);
    IERC20(underlying).approve(dts[i], 1);
    IDepositToken(dts[i]).deposit(1, victim); // onBehalfOf = victim
}
// Or equivalently: depositToken.transfer(victim, 1) per token

assertEq(pool.getDepositTokensOfAccount(victim).length +
         pool.getDebtTokensOfAccount(victim).length, max);

// Victim's deposit of a collateral type not already held reverts
vm.prank(victim);
vm.expectRevert(Pool.UserReachedMaxTokens.selector);
IDepositToken(newDepositToken).deposit(100e18, victim);

// Inbound transfer of a not-yet-held msdTOKEN also reverts
vm.prank(attacker);
vm.expectRevert(Pool.UserReachedMaxTokens.selector);
IDepositToken(newDepositToken).transfer(victim, 1);
```

Note: I did not verify whether `DebtToken.issue(amount_, to_)` lets an attacker register debt entries directly on a victim; if it does, the attack extends to the debt-token half of the cap as well.

    ) private updateRewardsBeforeTransfer(sender_, recipient_) {

        if (recipient_ == address(0)) revert TransferToTheZeroAddress();

        uint256 _senderBalanceBefore = balanceOf[sender_];
        if (_senderBalanceBefore < amount_) revert TransferAmountExceedsBalance();
        uint256 _recipientBalanceBefore = balanceOf[recipient_];

        unchecked {
            balanceOf[sender_] = _senderBalanceBefore - amount_;
            balanceOf[recipient_] += amount_;
        }

        emit Transfer(sender_, recipient_, amount_);

        // Add this token to the deposit tokens list if the recipient is receiving it for the 1st time
        if (_recipientBalanceBefore == 0 && amount_ > 0) {
            pool.addToDepositTokensOfAccount(recipient_);
        }

        // Remove this token from the deposit tokens list if the sender's balance goes to zero
        if (amount_ > 0 && balanceOf[sender_] == 0) {
            pool.removeFromDepositTokensOfAccount(sender_);
        }
    }
