## Title
Unbounded array allocation from unauthenticated `DataWord` length in TVM precompile helpers `extractBytesArray`/`extractBytes32Array`/`extractSigArray` — Denial-of-Service via excessive memory allocation - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The CVE describes an integer-signedness bug in `StringUtils_createStringFromBuffer` where an attacker-controlled length is used to allocate a buffer without adequate bounds validation, causing an oversized allocation and DoS. The analogous pattern exists in java-tron's precompiled-contract helper methods, which take a length value straight from smart-contract call data (a `DataWord`) and use it to size a Java array before any validation against the actual remaining call-data size.

### Finding Description
`extractBytes32Array` and `extractBytesArray` read a length directly from the calldata-derived `DataWord[] words` array via `intValueSafe()` and immediately allocate an array of that size: [1](#0-0) 

`intValueSafe()` is the safety net meant to avoid `NegativeArraySizeException`/overflow-driven undersized allocations by clamping out-of-range or negative values to `Integer.MAX_VALUE`: [2](#0-1) 

That clamping behavior is precisely the signedness-adjacent issue class in the CVE: instead of rejecting an out-of-range/negative-looking length, the code coerces it to the maximum positive `int` and proceeds to allocate `new byte[len][]` (an array-of-arrays sized up to `Integer.MAX_VALUE`) with no check against the actual length of `data` or `words`. There is no upstream validation before this allocation — the only bound check present is `offset > words.length - 1` for `extractBytesArray`/`extractSigArray`, which does not bound `len` itself.

This differs from the properly-guarded `ModExp` precompile in the same file, which explicitly checks `baseLen > UPPER_BOUND`, etc., before parsing: [3](#0-2) 

### Impact Explanation
An oversized `len` (up to `Integer.MAX_VALUE`) passed into `new byte[len][]` attempts to allocate up to ~2^31 array-reference slots (16 GB+ on a 64-bit JVM), which can throw `OutOfMemoryError` inside the TVM execution path. Because TVM opcode/precompile execution runs inside the node's block-processing/transaction-execution thread, an uncontrolled `OutOfMemoryError` in this path risks destabilizing or crashing the node process, which is a node-crash/halt-class impact within the accepted analog scope.

### Likelihood Explanation
Reaching these helpers requires only that a caller (contract deployer, or any account broadcasting a transaction that invokes the associated precompiled contract) supplies crafted call data with a large length word at the relevant offset. This is a standard, low-privilege interaction — invoking a TVM precompiled contract via a normal contract call — so the reachability bar is low. The main uncertainty is which precompiled contract(s) currently call `extractBytesArray`/`extractBytes32Array`/`extractSigArray` at runtime and whether energy metering for that call adequately bounds the value before the allocation executes; I was not able to fully trace the exact call site (energy cost function) that gates the length within the available index in this session, so the actual exploitability depends on whether an energy-cost pre-check elsewhere effectively bounds `len` before these helpers are invoked.

### Recommendation
Before allocating arrays sized by `intValueSafe()`-derived lengths in `extractBytesArray`, `extractBytes32Array`, and `extractSigArray`, validate `len` against a sane upper bound (e.g., against `words.length` or a fixed maximum signature/array count) and reject the call (return `Pair.of(false, ...)`) if the length is inconsistent with the actual supplied call-data size, mirroring the `UPPER_BOUND` guard already used in `ModExp.execute`.

### Proof of Concept
Craft a transaction that calls a smart contract invoking the precompiled contract that uses `extractBytesArray`/`extractBytes32Array`/`extractSigArray`, placing a maximal 32-byte word (e.g. `0xFFFFFFFF...`) at the length-offset position in the call data so `intValueSafe()` returns `Integer.MAX_VALUE`; this drives `new byte[Integer.MAX_VALUE][]` (or similarly sized `byte[len]` in the array-of-arrays), which is expected to throw `OutOfMemoryError` during TVM execution of that transaction.

**Note on completeness:** I could not verify within the indexed content exactly which precompiled contract(s) invoke these three helper methods at runtime or whether an energy-cost precheck elsewhere bounds `len` before invocation; confirming the exact call chain and any existing energy-based bound would require reading the full `PrecompiledContracts.java` file (which the index only partially covers) or starting a full Devin session to load the complete file.

    int len = words[offset].intValueSafe();
    byte[][] bytes32Array = new byte[len][];

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {

      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
