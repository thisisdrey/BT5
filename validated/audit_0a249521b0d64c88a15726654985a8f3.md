### Title
Object pool metadata store never updated by ObjectPoolService RPCs, causing permanently stale pool/member tracking - (File: internal/gitaly/storage/relational/state_manager.go)

### Summary
`ObjectPoolStateManager` (backed by `PoolStore`/`SQLitePoolStore`) is designed to track object-pool lifecycle (pool creation/deletion, member linking/unlinking) in a relational store separate from the actual on-disk `objects/info/alternates` state [1](#0-0) . However, grepping the codebase shows the `Notify*` methods are exercised only by `state_manager_test.go`; the real mutating RPC handlers for object pools (`CreateObjectPool`, `DeleteObjectPool`, `LinkRepositoryToObjectPool`, `DisconnectGitAlternates` in `internal/gitaly/service/objectpool/`) never call into this manager. This mirrors the reported bug class exactly: an authoritative balance/state field (`d3Vault` reserve balance / here, pool membership metadata) is left unmodified after the real underlying operation (`withdrawReserves` / here, alternates link-unlink) completes.

### Finding Description
`Disconnect` in `internal/git/objectpool/disconnect.go` performs the real, disk-level unlinking of a repository from an object pool: it hard-links objects back into the member and removes `objects/info/alternates` after a successful `git-fsck` [2](#0-1) [3](#0-2) . The gRPC handler wrapping it, `DisconnectGitAlternates`, calls `objectpool.Disconnect` directly and returns without any interaction with `ObjectPoolStateManager` [4](#0-3) . Similarly, `LinkRepositoryToObjectPool`, `CreateObjectPool`, and `DeleteObjectPool` mutate on-disk alternates/pool state but there is no evidence of any call to `NotifyCreatePool`, `NotifyDeletePool`, `NotifyLinkRepository`, or `NotifyUnlinkRepository` outside of the manager's own unit tests. As a result, `PoolStore` records (`pools`, `pool_members` tables in `internal/gitaly/storage/relational/sqlite.go`) never reflect the true, current membership of any pool created through the public ObjectPoolService, exactly as the vault's on-chain reserve `balance` remained un-incremented/decremented in `withdrawReserves()` while the underlying transfer of funds still occurred.

### Impact Explanation
Any component that later relies on the `PoolStore` for pool-membership accounting (e.g. detecting orphaned/broken pools via `RecordBrokenPool`, safe deletion checks, deduplication/quota bookkeeping, or fleet-wide pool inventory reporting) will operate on permanently stale or empty data, since the store is never populated or cleaned up during the entire real lifecycle of pools. This can cause pools to be reported as having no members when they still do (risking an operator or automated job calling `DeleteObjectPool` — which "has no safety checks in place" per its own doc comment [5](#0-4)  — against a pool with live members), corrupting those members' repositories, or conversely leaving phantom membership records that never get cleaned up, causing resource-accounting/DoS-style drift over time. This is a data-integrity/DoS class issue reachable purely through ordinary, unprivileged `ObjectPoolService` RPC usage (fork/create/link/unlink/delete flows), matching the "no state update after mutating operation, wrong downstream calculation" bug class of the reference report.

### Likelihood Explanation
High: any ordinary user or GitLab Rails workflow that forks a repository (`CreateObjectPool` + `LinkRepositoryToObjectPool`) or unforks/privatizes a repository (`DisconnectGitAlternates`/`DeleteObjectPool`) exercises this code path unconditionally on every call, with no privileged access or special conditions required — the disconnect is between production wiring and the metadata layer.

### Recommendation
Wire the `ObjectPoolStateManager.Notify*` calls into the actual mutating handlers in `internal/gitaly/service/objectpool/` (and `internal/git/objectpool/disconnect.go`) so that every successful on-disk pool create/delete/link/unlink operation is paired, atomically or within the same transaction boundary, with the corresponding `PoolStore` update. Add integration tests asserting that after invoking the public RPCs, `PoolStore.ListPoolMembers`/`GetPoolByDiskPath` reflect the change, not just the internal `ObjectPoolStateManager` unit tests.

### Proof of Concept
1. Call `CreateObjectPool` then `LinkRepositoryToObjectPool` to link `member1.git` to `pool1.git` through the public gRPC API.
2. Query `SQLitePoolStore.ListPoolMembers(ctx, "pool1.git")` (or any downstream consumer of `PoolStore`) — it returns empty/no record, because no production code path calls `NotifyLinkRepository`.
3. Call `DisconnectGitAlternates` for `member1.git` — the on-disk alternates file is removed and objects are hard-linked back [3](#0-2) , but no `NotifyUnlinkRepository` is invoked, so any stale record (if ever created by other means) is never cleared either.
4. This demonstrates the metadata store can never be kept in sync with real pool state through normal, unprivileged API usage — identical in class to the vault balance field never being updated in `withdrawReserves()` despite funds actually moving.

func (s *server) DisconnectGitAlternates(ctx context.Context, req *gitalypb.DisconnectGitAlternatesRequest) (*gitalypb.DisconnectGitAlternatesResponse, error) {
	repository := req.GetRepository()
	if err := s.locator.ValidateRepository(ctx, repository); err != nil {
		return nil, structerr.NewInvalidArgument("%w", err)
	}

	repo := s.localRepoFactory.Build(repository)

	storageRoot, err := s.locator.GetStorageByName(ctx, repo.GetStorageName())
	if err != nil {
		return nil, fmt.Errorf("storage by name: %w", err)
	}

	f := storage.NewNoopFS(storageRoot)
	if tx := storage.ExtractTransaction(ctx); tx != nil {
		f = tx.FS()
	}

	if err := objectpool.Disconnect(ctx, f, repo, s.logger, s.txManager); err != nil {
		return nil, structerr.NewInternal("%w", err)
	}

	return &gitalypb.DisconnectGitAlternatesResponse{}, nil
}
