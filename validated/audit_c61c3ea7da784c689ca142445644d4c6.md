Audit Report

## Title
Permanent DoS in `pallet-asset-rewards`: `reward_per_token` multiply-before-divide overflow reverts `stake`/`unstake`/`harvest_rewards` for all stakers - (File: `substrate/frame/asset-rewards/src/lib.rs`)

## Summary
`reward_per_token` computes `reward_rate_per_block.ensure_mul(rewardable_blocks_elapsed)?.ensure_mul(PRECISION_SCALING_FACTOR)?.ensure_div(total_tokens_staked)?`, performing both multiplications before dividing by `total_tokens_staked`. [1](#0-0)  Because this function is called unconditionally at the start of `stake`, `unstake`, and `harvest_rewards` via `update_pool_and_staker_rewards`, an intermediate-product overflow (even when the final divided result would fit in `T::Balance`) causes every subsequent call for that pool to revert for all stakers. [2](#0-1) 

## Finding Description
`reward_per_token` first checks `total_tokens_staked.is_zero()` and returns early if so, otherwise it computes `rewardable_blocks_elapsed` from block-number arithmetic and then chains `ensure_mul` → `ensure_mul` → `ensure_div`. [3](#0-2)  This is confirmed as-written in the current codebase: the multiply-multiply-divide ordering means that if `reward_rate_per_block * rewardable_blocks_elapsed * PRECISION_SCALING_FACTOR` overflows `T::Balance` before the division by `total_tokens_staked` is applied, `ensure_mul` returns `ArithmeticError::Overflow` even in cases where the true, correctly-ordered result (product-then-divide) would fit comfortably in `T::Balance`.

`update_pool_and_staker_rewards` calls `reward_per_token` as its first statement and propagates the error with `?`, and this function is itself called as the first step of `stake`, `unstake`, and `harvest_rewards`. [4](#0-3)  Because the overflow depends on pool-level state (`reward_rate_per_block`, elapsed blocks since `last_update_block`, `total_tokens_staked`) that is not reset by a failed call, once the intermediate product exceeds `T::Balance::MAX`, the failure recurs on every future call to any of these three extrinsics for that pool — there is no code path in the pallet that resets `reward_rate_per_block` downward or otherwise bypasses this calculation to unstick the pool.

## Impact Explanation
This matches the "permanent user-fund lock" category in the impact gate: stakers with assets frozen via `AssetsFreezer` in an affected pool would be permanently unable to call `unstake` or `harvest_rewards` once the pool's reward-per-token computation enters the overflow state, and new `stake` calls into that pool would also fail. The corrupted value is the intermediate arithmetic result inside `reward_per_token` (specifically `reward_rate_per_block * rewardable_blocks_elapsed * PRECISION_SCALING_FACTOR` prior to the division by `total_tokens_staked`), which exceeds `T::Balance::MAX` and causes `ensure_mul` to return `ArithmeticError::Overflow`, propagated as a `DispatchError` that reverts the whole extrinsic.

## Likelihood Explanation
Reaching the overflow does not require any privileged or malicious action beyond ordinary pool usage: any account can call `stake` to establish a low `total_tokens_staked`, and the mere passage of blocks without further interaction (or a legitimate admin increase of `reward_rate_per_block`) causes `rewardable_blocks_elapsed` and the resulting product to grow monotonically for that pool. Given `T::Balance` is commonly `u128` in production runtimes, the threshold for the un-divided intermediate product to overflow is lower than `T::Balance::MAX` divided by the (potentially small) `total_tokens_staked` value, which is a real and reachable scenario for low-activity or low-liquidity pools, and it is fully attacker/user reachable via public `stake`/`unstake`/`harvest_rewards` calls once the state is set up.

## Recommendation
Reorder the arithmetic in `reward_per_token` (`substrate/frame/asset-rewards/src/lib.rs`) to avoid requiring the un-divided intermediate product to fit in `T::Balance`. Options include: performing the computation in a wider intermediate type (e.g., `u256`/`U256`-style arithmetic) before downcasting to `T::Balance`, or restructuring the multiply/divide steps so partial results are divided down before the next multiplication where mathematically safe, ensuring only the final, correctly-scaled result needs to fit in `T::Balance`.

## Proof of Concept
1. Admin creates a pool with `create_pool` and configures a `reward_rate_per_block` sized relative to `PRECISION_SCALING_FACTOR` such that `reward_rate_per_block * PRECISION_SCALING_FACTOR` is a large fraction of `T::Balance::MAX`.
2. A staker calls `stake` once to set `total_tokens_staked` to a small nonzero value, then the pool goes unused for enough blocks that `rewardable_blocks_elapsed` (computed at `reward_per_token`, lines 794-801) grows large.
3. Once `reward_rate_per_block.ensure_mul(rewardable_blocks_elapsed.into())?.ensure_mul(PRECISION_SCALING_FACTOR.into())?` (lines 803-808) exceeds `T::Balance::MAX`, this returns `Err(ArithmeticError::Overflow)`.
4. Any subsequent call to `stake`, `unstake`, or `harvest_rewards` for this pool by any staker fails via `update_pool_and_staker_rewards` → `reward_per_token`, with no recovery path, permanently locking staked/frozen assets in that pool. This can be reproduced as a Rust unit test in `substrate/frame/asset-rewards/src/tests.rs` by setting up a pool with a large `reward_rate_per_block`, staking a small amount, advancing blocks (`run_to_block` or similar helper), and asserting that `unstake`/`harvest_rewards` return `Err(ArithmeticError::Overflow.into())`.

		pub(super) fn reward_per_token(
			pool_info: &PoolInfoFor<T>,
		) -> Result<T::Balance, DispatchError> {
			if pool_info.total_tokens_staked.is_zero() {
				return Ok(pool_info.reward_per_token_stored);
			}

			let rewardable_blocks_elapsed: u32 =
				match Self::last_block_reward_applicable(pool_info.expiry_block)
					.ensure_sub(pool_info.last_update_block)?
					.try_into()
				{
					Ok(b) => b,
					Err(_) => return Err(Error::<T>::BlockNumberConversionError.into()),
				};

			Ok(pool_info.reward_per_token_stored.ensure_add(
				pool_info
					.reward_rate_per_block
					.ensure_mul(rewardable_blocks_elapsed.into())?
					.ensure_mul(PRECISION_SCALING_FACTOR.into())?
					.ensure_div(pool_info.total_tokens_staked)?,
			)?)
