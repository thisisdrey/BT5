### Title
Unbounded `read_to_end` in `run_http_request`/`decode_http_body` allows unauthenticated memory-exhaustion DoS on the signer process - (File: libsigner/src/http.rs)

### Summary
`run_http_request` reads an entire HTTP response into memory with `sock.read_to_end(&mut buf)` with no size cap, and for non-chunked bodies `decode_http_body` further copies the unbounded slice via `buf.to_vec()` with no `Content-Length`/`MAX_MESSAGE_LEN` check. Any node the signer's `StackerDBSession` talks to can stream an arbitrarily large, non-chunked response to force unbounded allocation in the signer client.

### Finding Description
In `libsigner/src/http.rs`, `run_http_request` does:
```
let mut buf = vec![];
sock.read_to_end(&mut buf)?;
``` [1](#0-0) 
This call has no upper bound whatsoever — it accumulates bytes from the socket into `buf` until EOF (or error), regardless of chunked or non-chunked framing, and regardless of `Content-Length`. Only after this unbounded read completes does the code call `decode_http_response` and then `decode_http_body`.

In `decode_http_body`, the chunked path is capped:
```
let mut fd = HttpChunkedTransferReader::from_reader(ptr, MAX_MESSAGE_LEN.into());
``` [2](#0-1) 
but the non-chunked (`Transfer-Encoding` absent) branch just does:
```
buf.to_vec()
``` [3](#0-2) 
with no length check against `MAX_MESSAGE_LEN` or the previously-parsed `Content-Length` header.

Because the socket-level `read_to_end` at line 251 already has no cap, a malicious server does not even need to worry about tripping the chunked-path limit — it simply omits `Transfer-Encoding: chunked` and streams data continuously (staying under the per-read `socket_timeout`, which only bounds inter-read stalls, not total transfer size/time). Every `read()` call in the loop succeeds and `buf` keeps growing without any size check until the process runs out of memory or the OS kills it.

This is reachable from `StackerDBSession::rpc_request` → `run_http_request`, which is invoked whenever the signer performs any StackerDB operation (`list_chunks`, `get_chunks`, `get_latest_chunks`, `put_chunk`) against the node it is configured to talk to: [4](#0-3) 
The connecting party in the threat model is "any remote party who can connect to a node's ... RPC port" — here the roles are reversed: the signer is the client connecting out to a node's RPC endpoint. Any endpoint the signer queries (including a malicious/compromised node the signer is pointed at, or a MITM/rogue responder impersonating that node) can serve an oversized, non-chunked response and trigger unbounded memory growth in the signer.

### Impact Explanation
A single crafted HTTP response with a large or infinite non-chunked body causes the stacks-signer process's `StackerDBSession` client to allocate unbounded memory in `run_http_request`'s `buf`, leading to OOM/crash (or severe memory pressure) of the signer process. This matches the Critical category "remote crash/unauthenticated DoS from few messages" — a single response is sufficient, and it's repeatable on every RPC call the signer makes to that host.

### Likelihood Explanation
Preconditions: the signer must be configured to talk to a node at `host` (a normal configuration), and that node (or something able to respond on that connection, e.g. a compromised/malicious configured node) sends back a non-chunked, oversized response. No secrets, signatures, or privileged roles are required — the attacker only needs to be the HTTP server the signer's `StackerDBSession` connects to and control the response bytes. Every `rpc_request` call (`list_chunks`, `get_chunks`, `get_latest_chunks`, `put_chunk`) is a repeatable trigger point.

### Recommendation
Bound the initial socket read in `run_http_request` (e.g., using a length-limited reader capped at `MAX_MESSAGE_LEN`, or reading headers first and then reading at most `Content-Length` bytes) instead of unconditional `read_to_end`. Additionally, in `decode_http_body`'s non-chunked branch, enforce a `MAX_MESSAGE_LEN` (or `Content-Length`-derived) cap before calling `buf.to_vec()`, returning an error if the body exceeds the limit.

### Proof of Concept
Rust test in `libsigner`:
1. Spin up a `TcpListener` on `127.0.0.1:0`.
2. In an accept thread, read the request, then write `"HTTP/1.1 200 OK\r\n\r\n"` (no `Content-Length`, no `Transfer-Encoding`) followed by an infinite/very large loop writing e.g. 1 MiB chunks of `0xFF` bytes repeatedly without ever closing the socket, with small delays under the client's configured `socket_timeout`.
3. Call `run_http_request(&mut TcpStream::connect(addr)?, host, "GET", "/", None, &[])`.
4. Assert that memory usage of `buf` inside `run_http_request` (or process RSS) grows without bound / exceeds `MAX_MESSAGE_LEN`, demonstrating the missing cap at `sock.read_to_end(&mut buf)` (`libsigner/src/http.rs:251`) and the unguarded `buf.to_vec()` fallback (`libsigner/src/http.rs:213`).
