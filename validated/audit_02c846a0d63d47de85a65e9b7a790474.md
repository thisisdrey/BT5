## Title
Unbounded growth of `TransactionManager.committedEntries` causes O(n) `walkCommittedEntries` scans on every write commit, DoSing the partition's serialized transaction processing - (File: internal/gitaly/storage/storagemgr/partition/transaction_manager.go)

### Summary
`TransactionManager` maintains an in-memory, singly-processed linked list `committedEntries` used for conflict detection between concurrently open write transactions and newly committed ones. A new entry is pinned in this list every time a write transaction begins (`updateCommittedEntry`), and entries are only removable from the *front* of the list once the transaction holding the *oldest* snapshot finishes (`cleanCommittedEntry`). Every subsequent write transaction's verification step (`verifyKeyValueOperations`, `verifyHousekeeping`/`verifyPackRefs`, and reference-conflict verification) must call `walkCommittedEntries`, which iterates the **entire list from the front** under the partition-wide `mgr.mutex`. If a single write transaction remains open for a long time (e.g. blocked in a slow/custom hook, a stalled streaming RPC, or a client that doesn't promptly commit/rollback) while other ordinary pushes keep committing to the same partition, the list can grow without bound, and every later commit pays an ever-increasing, serialized O(n) cost to walk it — closely mirroring the reported bug class of an unbounded "pending" collection lacking a batch/cap that is processed in full during a mandatory, shared finalize step.

### Finding Description
- A write transaction pins a `committedEntry` at `Begin()` time via `updateCommittedEntry`, which either increments `snapshotReaders` on the current tail entry or creates a new one and appends it with `PushBack` [1](#0-0) .
- `cleanCommittedEntry`, invoked when a write transaction finishes, decrements the reader count and can only remove entries starting at `Front()` while their reader count is zero; if the transaction with the *oldest* pinned snapshot (at the front) never finishes, none of the newer entries behind it can ever be pruned, regardless of how many additional transactions commit and finish [2](#0-1) .
- `walkCommittedEntries` walks the list from `Front()` to `Back()` on **every** invocation, under the shared `mgr.mutex` (the same lock used for `Begin()`), with no batching, pagination, or cap on the number of entries traversed [3](#0-2) .
- This function is called for essentially every committing write transaction to perform conflict checks: key-value read-set conflicts (`verifyKeyValueOperations`) [4](#0-3) , and housekeeping conflict checks (`verifyHousekeeping`/`verifyPackRefsFiles`) [5](#0-4) [6](#0-5) .
- `TransactionManager.Run()` is the single writer goroutine for an entire partition, which may include multiple repositories (a repo and its object-pool members/forks), so this cost is not confined to a single repository [7](#0-6) .

This is the closest analog in Gitaly to the reported `_processPendingRemovals` bug class: a collection (`committedEntries`, analogous to `pendingRemovals`) that grows with every write transaction and must be walked in full — without a batch argument or size cap — by a mandatory, serialized step (`walkCommittedEntries`) that every future write transaction depends on to make progress.

### Impact Explanation
If an ordinary, unprivileged client can cause a write transaction to remain open for an extended period (for example, by relying on a slow custom `pre-receive`/`update` hook, a stalled streaming RPC that keeps its transaction alive, or simply repeatedly beginning writes and delaying completion) while other legitimate pushes continue to commit against the same partition, `committedEntries` grows unbounded because the front-pruning logic in `cleanCommittedEntry` is blocked by the stalled transaction. Every subsequent write commit on that partition then pays an increasing O(n) cost inside `walkCommittedEntries`, executed while holding the partition-wide mutex. As the list grows, this degrades and can eventually stall all write-transaction processing (reference updates, key-value writes, housekeeping/pack-refs) for every repository sharing that partition, effectively denying service to legitimate users of those repositories, similar to how the reported bug allowed `Voter::finalize()` to be permanently DoSed by an ever-growing, unbatched pending-removal list.

### Likelihood Explanation
Reaching this condition requires an attacker (or even an unintentional slow client) to keep at least one write transaction open on a partition for a sustained period while inducing/observing continued commit activity on the same partition. Because `TransactionManager` intentionally allows write transactions to span RPC-controlled operations (including custom hook execution, which is user-configurable and not always tightly time-bounded), and because there is no explicit cap or timeout enforced on `committedEntries` length or on how long a transaction may pin the front of the list, this is plausible from ordinary push/hook activity without any special privileges. However, the exact bound on how long a write transaction can remain open (RPC/context timeouts, hook execution limits) was not fully verified within the scope of this review, so the ease of sustaining the condition long enough to cause a severe, user-visible DoS is not fully proven and would benefit from further testing (e.g., measuring `walkCommittedEntries` latency growth under a large `committedEntries` list with a pinned front entry).

### Recommendation
- Bound the size/age of `committedEntries` independent of whether the oldest-snapshot transaction has finished (e.g., enforce a maximum list length or maximum snapshot age, aborting/erroring out transactions that would exceed it).
- Avoid holding `mgr.mutex` for the full duration of `walkCommittedEntries`; consider chunked/batched traversal, or maintain an index/side-structure so that conflict checks are O(1)/O(log n) with respect to relevant changes instead of O(n) over the whole outstanding history.
- Impose stricter timeouts on write transactions' lifetime (from `Begin()` to `Commit()`/`Rollback()`), including bounding hook execution time, so a single stalled transaction cannot indefinitely block pruning of `committedEntries`.
- Add metrics/alerts on `committedEntries` length so operators can detect pathological growth before it becomes a full DoS.

### Proof of Concept
Not independently reproduced; based on static code analysis of `updateCommittedEntry`, `cleanCommittedEntry`, and `walkCommittedEntries` in `internal/gitaly/storage/storagemgr/partition/transaction_manager.go`, and their usage in `verifyKeyValueOperations`/`verifyHousekeeping`. A concrete PoC would require: (1) starting a write transaction and stalling it before commit/rollback (e.g., via a slow custom hook), (2) concurrently issuing many additional writes to the same partition to grow `committedEntries`, and (3) measuring increasing latency/CPU in subsequent commits' `walkCommittedEntries` calls until the stalled transaction finishes. // verifyKeyValueOperations checks the key-value operations of the transaction for conflicts and includes
// them in the log entry. The conflict checking ensures serializability. Transaction is considered to
// conflict if it read a key a concurrently committed transaction set or deleted. Iterated key prefixes
// are predicate locked.
func (mgr *TransactionManager) verifyKeyValueOperations(ctx context.Context, tx *Transaction) error {
	defer trace.StartRegion(ctx, "verifyKeyValueOperations").End()

	if readSet := tx.recordingReadWriter.ReadSet(); len(readSet) > 0 {
		if err := mgr.walkCommittedEntries(tx, func(entry *gitalypb.LogEntry, _ map[git.ObjectID]struct{}) error {
			for _, op := range entry.GetOperations() {
				var key []byte
				switch op := op.GetOperation().(type) {
				case *gitalypb.LogEntry_Operation_SetKey_:
					key = op.SetKey.GetKey()
				case *gitalypb.LogEntry_Operation_DeleteKey_:
					key = op.DeleteKey.GetKey()
				}

				stringKey := string(key)
				if _, ok := readSet[stringKey]; ok {
					return newConflictingKeyValueOperationError(stringKey)
				}

				for prefix := range tx.recordingReadWriter.PrefixesRead() {
					if bytes.HasPrefix(key, []byte(prefix)) {
						return newConflictingKeyValueOperationError(stringKey)
					}
				}
			}

			return nil
		}); err != nil {
			return fmt.Errorf("walking committed entries: %w", err)
		}
	}

// updateCommittedEntry updates the reader counter of the committed entry of the snapshot that this transaction depends on.
func (mgr *TransactionManager) updateCommittedEntry(snapshotLSN storage.LSN) *committedEntry {
	// Since the goroutine doing this is holding the lock, the snapshotLSN shouldn't change and no new transactions
	// can be committed or added. That should guarantee .Back() is always the latest transaction and the one we're
	// using to base our snapshot on.
	if elm := mgr.committedEntries.Back(); elm != nil {
		entry := elm.Value.(*committedEntry)
		entry.snapshotReaders++
		return entry
	}

	entry := &committedEntry{
		lsn:             snapshotLSN,
		snapshotReaders: 1,
	}

	mgr.committedEntries.PushBack(entry)

	return entry
}

// walkCommittedEntries walks all committed entries after input transaction's snapshot LSN. It loads the content of the
// entry from disk and triggers the callback with entry content.
func (mgr *TransactionManager) walkCommittedEntries(transaction *Transaction, callback func(*gitalypb.LogEntry, map[git.ObjectID]struct{}) error) error {
	mgr.mutex.Lock()
	defer mgr.mutex.Unlock()

	for elm := mgr.committedEntries.Front(); elm != nil; elm = elm.Next() {
		committed := elm.Value.(*committedEntry)
		if committed.lsn <= transaction.snapshotLSN {
			continue
		}

		if committed.entry == nil {
			return errCommittedEntryGone
		}
		// Transaction manager works on the partition level, including a repository and all of its pool
		// member repositories (if any). We need to filter log entries of the repository this
		// transaction targets.
		if committed.entry.GetRelativePath() != transaction.relativePath {
			continue
		}
		if err := callback(committed.entry, committed.objectDependencies); err != nil {
			return fmt.Errorf("callback: %w", err)
		}
	}
	return nil
}

// cleanCommittedEntry reduces the snapshot readers counter of the committed entry. It also removes entries with no more
// readers at the head of the list.
func (mgr *TransactionManager) cleanCommittedEntry(entry *committedEntry) bool {
	entry.snapshotReaders--

	removedAnyEntry := false
	elm := mgr.committedEntries.Front()
	for elm != nil {
		front := elm.Value.(*committedEntry)
		if front.snapshotReaders > 0 {
			// If the first entry had still some snapshot readers, that means
			// our transaction was not the oldest reader. We can't remove any entries
			// as they'll still be needed for conflict checking the older transactions.
			return removedAnyEntry
		}

		mgr.committedEntries.Remove(elm)

		// It's safe to drop the transaction from the conflict detection history as there are no transactions
		// reading at an older snapshot. Since the changes are already in the transaction's snapshot, it would
		// already base its changes on them.
		mgr.conflictMgr.EvictLSN(mgr.ctx, front.lsn)
		mgr.fsHistory.EvictLSN(front.lsn)

		removedAnyEntry = true
		elm = mgr.committedEntries.Front()
	}
	return removedAnyEntry
}

func (mgr *TransactionManager) verifyHousekeeping(ctx context.Context, transaction *Transaction, refBackend git.ReferenceBackend, zeroOID git.ObjectID) (*gitalypb.LogEntry_Housekeeping, error) {
	defer trace.StartRegion(ctx, "verifyHousekeeping").End()

	span, ctx := tracing.StartSpanIfHasParent(ctx, "transaction.verifyHousekeeping", nil)
	defer span.End()

	finishTimer := mgr.metrics.housekeeping.ReportTaskLatency("total", "verify")
	defer finishTimer()

	// Check for any concurrent housekeeping between this transaction's snapshot LSN and the latest appended LSN.
	if err := mgr.walkCommittedEntries(transaction, func(entry *gitalypb.LogEntry, objectDependencies map[git.ObjectID]struct{}) error {
		if entry.GetHousekeeping() != nil {
			return errHousekeepingConflictConcurrent
		}
		if entry.GetRepositoryDeletion() != nil {
			return errConflictRepositoryDeletion
		}

		// Applying a repacking operation prunes all loose objects on application. If loose objects were concurrently introduced
		// in the repository with the repacking operation, this could lead to corruption if we prune a loose object that is needed.
		// Transactions in general only introduce packs, not loose objects. The only exception to this currently is alternate
		// unlinking operations where the objects of the alternate are hard linked into the member repository. This can technically
		// still introduce loose objects into the repository and trigger this problem as the pools could still have loose objects
		// in them until the first repack.
		//
		// Check if the repository was unlinked from an alternate concurrently.
		for _, op := range entry.GetOperations() {
			switch op := op.GetOperation().(type) {
			case *gitalypb.LogEntry_Operation_RemoveDirectoryEntry_:
				if string(op.RemoveDirectoryEntry.GetPath()) == stats.AlternatesFilePath(transaction.relativePath) {
					return errConcurrentAlternateUnlink
				}
			}
		}

		return nil
	}); err != nil {
		return nil, fmt.Errorf("walking committed entries: %w", err)
	}

func (mgr *TransactionManager) verifyPackRefsFiles(ctx context.Context, transaction *Transaction, zeroOID git.ObjectID) (*gitalypb.LogEntry_Housekeeping_PackRefs, error) {
	packRefs := transaction.runHousekeeping.packRefs

	// Check for any concurrent ref deletion between this transaction's snapshot LSN to the end.
	if err := mgr.walkCommittedEntries(transaction, func(entry *gitalypb.LogEntry, objectDependencies map[git.ObjectID]struct{}) error {
		for _, refTransaction := range entry.GetReferenceTransactions() {
			for _, change := range refTransaction.GetChanges() {
				// We handle HEAD updates through the git-update-ref, but since
				// it is not part of the packed-refs file, we don't need to worry about it.
				if bytes.Equal(change.GetReferenceName(), []byte("HEAD")) {
					continue
				}

				if git.ObjectID(change.GetNewOid()) == zeroOID {
					// Oops, there is a reference deletion. Bail out.
					return errPackRefsConflictRefDeletion
				}
				// Ref update. Remove the updated ref from the list of pruned refs so that the
				// new OID in loose reference shadows the outdated OID in packed-refs.
				delete(packRefs.PrunedRefs, git.ReferenceName(change.GetReferenceName()))
			}
		}
		return nil
	}); err != nil {
		return nil, fmt.Errorf("walking committed entries: %w", err)
	}

### Transaction Manager

`TransactionManager` is the component responsible for managing transactions and write-ahead log application of single partition.

A partition is started by `StorageManager` by [launching a goroutine](https://gitlab.com/gitlab-org/gitaly/-/blob/7c0f925b3df33c77de8c124b5f89447a13da3059/internal/gitaly/storage/storagemgr/partition_manager.go#L555) running [`TransactionManager.Run()`](https://gitlab.com/gitlab-org/gitaly/-/blob/7c0f925b3df33c77de8c124b5f89447a13da3059/internal/gitaly/storage/storagemgr/partition/transaction_manager.go#L1670).
This goroutine is the partition's single writer, and is the only one operating on the actual state of the partition. This goroutine runs a loop to [apply the write-ahead log](https://gitlab.com/gitlab-org/gitaly/-/blob/7c0f925b3df33c77de8c124b5f89447a13da3059/internal/gitaly/storage/storagemgr/partition/transaction_manager.go#L1705) and [process transactions](https://gitlab.com/gitlab-org/gitaly/-/blob/7c0f925b3df33c77de8c124b5f89447a13da3059/internal/gitaly/storage/storagemgr/partition/transaction_manager.go#L1711)
that are ready to commit. It also synchronizes access to the partition's state between applying the log, and creating transaction snapshots.
