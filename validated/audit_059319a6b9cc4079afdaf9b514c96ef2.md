Audit Report

## Title
Bounty record deleted before payout success is verified, permanently locking curator/beneficiary funds - (File: substrate/frame/bounties/src/lib.rs)

## Summary
`Pallet::claim_bounty` in `substrate/frame/bounties/src/lib.rs` unconditionally clears the bounty's on-chain record (`*maybe_bounty = None`, `BountyDescriptions::remove`) after only checking the two payout transfers to curator and beneficiary via `debug_assert!(res.is_ok())`, which is a no-op in release builds. If either transfer fails (e.g. due to a destination account being below `ExistentialDeposit`), funds remain stranded in the bounty's `PalletId`-derived sub-account with no remaining storage record to reference or recover them.

## Finding Description
`claim_bounty` is a publicly callable, unprivileged extrinsic — any signed account can invoke it once a bounty is `BountyStatus::PendingPayout` and the unlock block has passed, as confirmed by `ensure_signed(origin)?; // anyone can trigger claim` and the `Self::treasury_block_number() >= unlock_at` check.

Inside `Bounties::<T, I>::try_mutate_exists`, the bounty is taken via `maybe_bounty.take()`, and two `T::Currency::transfer` calls move `final_fee` to the `curator` and `payout` to the `beneficiary` from `bounty_account_id(bounty_id)`. Both calls are only checked with `debug_assert!(res.is_ok())`, which compiles to a no-op in `--release`/production builds — the configuration actually run by on-chain nodes. Execution proceeds unconditionally to `*maybe_bounty = None` and `BountyDescriptions::<T, I>::remove(bounty_id)`, deleting the only on-chain record referencing the bounty sub-account and its owed balance, and then emits `Event::BountyClaimed` regardless of whether the transfers actually succeeded.

`Currency::transfer` with `ExistenceRequirement::AllowDeath` can return `Err` when the destination account does not already exist and the credited amount is below `ExistentialDeposit`. Both `final_fee` (a curator fee settable arbitrarily low via the bounty proposal/curator-assignment flow) and `payout` (the balance remainder after fee) can fall under ED for small bounties or fresh, unfunded beneficiary/curator addresses. [1](#0-0) 

## Impact Explanation
If either transfer silently fails, the `final_fee`/`payout` funds remain locked in `bounty_account_id(bounty_id)` with no dispatchable able to recover them, since the `Bounties` storage entry — the sole handle to that sub-account and the amount owed — has already been deleted. This matches the in-scope "permanent user-fund lock" / "value not conserved on settlement" impact class, since curator or beneficiary funds become permanently unrecoverable and `Event::BountyClaimed` misreports that the payout succeeded.

## Likelihood Explanation
`claim_bounty` is fully unprivileged and callable by any signed account; no governance, admin, or malicious-peer capability is required to trigger it. The precondition — a curator fee or payout remainder below `ExistentialDeposit` credited to a fresh, unfunded account — is a normal, attacker-controllable parameterization (e.g., a curator/proposer choosing a small fee and a brand-new beneficiary address), making the bug both feasible and repeatable in production, since `debug_assert!` is stripped in release builds.

## Recommendation
Replace the `debug_assert!(res.is_ok())` checks on both `T::Currency::transfer` calls in `claim_bounty` with proper `?`/`ensure!` error propagation, so the bounty record (`*maybe_bounty = None`, `BountyDescriptions::remove`) is only cleared after both transfers succeed; on failure, abort and preserve the record so funds and accounting remain recoverable — consistent with the payment-status tracking pattern used elsewhere in the treasury/bounties ecosystem.

## Proof of Concept
1. Governance approves a bounty and assigns a curator with a very small `fee` (e.g., `fee = 1`, below `ExistentialDeposit`).
2. The curator calls `award_bounty` naming a brand-new, never-funded `beneficiary`, with a bounty `value` such that `payout = balance - fee` also lands below `ExistentialDeposit` for that address.
3. After the payout delay elapses, any signed account calls `claim_bounty(bounty_id)`.
4. `T::Currency::transfer(&bounty_account, &curator, final_fee, AllowDeath)` and/or `T::Currency::transfer(&bounty_account, &beneficiary, payout, AllowDeath)` return `Err(Error::ExistentialDeposit)` since the destination has no existing balance and the credited amount is under ED.
5. Because the checks are only `debug_assert!` (no-op in release), execution continues: `*maybe_bounty = None`, `BountyDescriptions::remove(bounty_id)` execute, and `Event::BountyClaimed` fires as if payout succeeded.
6. The `final_fee`/`payout` tokens remain stuck in `bounty_account_id(bounty_id)` with no bounty record left to reference or reclaim them, permanently locking the curator/beneficiary funds.

		pub fn claim_bounty(
			origin: OriginFor<T>,
			#[pallet::compact] bounty_id: BountyIndex,
		) -> DispatchResult {
			ensure_signed(origin)?; // anyone can trigger claim

			Bounties::<T, I>::try_mutate_exists(bounty_id, |maybe_bounty| -> DispatchResult {
				let bounty = maybe_bounty.take().ok_or(Error::<T, I>::InvalidIndex)?;
				if let BountyStatus::PendingPayout { curator, beneficiary, unlock_at } =
					bounty.status
				{
					ensure!(Self::treasury_block_number() >= unlock_at, Error::<T, I>::Premature);
					let bounty_account = Self::bounty_account_id(bounty_id);
					let balance = T::Currency::free_balance(&bounty_account);
					let fee = bounty.fee.min(balance); // just to be safe
					let payout = balance.saturating_sub(fee);
					let err_amount = T::Currency::unreserve(&curator, bounty.curator_deposit);
					debug_assert!(err_amount.is_zero());

					// Get total child bounties curator fees, and subtract it from the parent
					// curator fee (the fee in present referenced bounty, `self`).
					let children_fee = T::ChildBountyManager::children_curator_fees(bounty_id);
					debug_assert!(children_fee <= fee);

					let final_fee = fee.saturating_sub(children_fee);
					let res =
						T::Currency::transfer(&bounty_account, &curator, final_fee, AllowDeath); // should not fail
					debug_assert!(res.is_ok());
					let res =
						T::Currency::transfer(&bounty_account, &beneficiary, payout, AllowDeath); // should not fail
					debug_assert!(res.is_ok());

					*maybe_bounty = None;

					BountyDescriptions::<T, I>::remove(bounty_id);
					T::ChildBountyManager::bounty_removed(bounty_id);

					Self::deposit_event(Event::<T, I>::BountyClaimed {
						index: bounty_id,
						payout,
						beneficiary,
					});
					Ok(())
				} else {
					Err(Error::<T, I>::UnexpectedStatus.into())
				}
			})?;
			Ok(())
		}
