Now I have enough to construct a concrete, reachable analog: `FreezeBalanceActuator.delegateResource()` (old freeze model, still reachable via the deprecated `FreezeBalanceContract` and via the TVM `freezeBalance()` opcode path in `FreezeBalanceProcessor.delegateResource()`) unconditionally overwrites `DelegatedResourceCapsule`'s `expireTimeForBandwidth`/`expireTimeForEnergy` with the newly-supplied `expireTime` on every call, without checking whether the previously stored expire time was later than the new one.

### Title
Delegated resource expiration can be shortened by re-delegating with a shorter freeze duration, allowing premature unfreeze of previously delegated balance - ([File: chainbase/src/main/java/org/tron/core/capsule/DelegatedResourceCapsule.java])

### Summary
`DelegatedResourceCapsule.addFrozenBalanceForBandwidth(long, long)` and `addFrozenBalanceForEnergy(long, long)` add the new balance to the existing frozen balance but unconditionally *overwrite* the stored `expireTimeForBandwidth`/`expireTimeForEnergy` with whatever `expireTime` is passed in the current call, instead of keeping the later (larger) of the old and new expire times, analogous to the reported Carapace bug where the "last write" of an expiration-related field clobbers a value that should have been the maximum. [1](#0-0) 

### Finding Description
`FreezeBalanceActuator.delegateResource()` (old, but still-live `FreezeBalanceContract` actuator) and its TVM counterpart `FreezeBalanceProcessor.delegateResource()` compute a fresh `expireTime = now + frozenDuration * FROZEN_PERIOD` for every `FreezeBalanceContract`/`freezeBalance()` transaction and pass it straight into `addFrozenBalanceForBandwidth`/`addFrozenBalanceForEnergy`: [2](#0-1) [3](#0-2) 

The capsule setter simply sums the balances but replaces the expire time field with the new value regardless of the previous one: [1](#0-0) 

Because `UnfreezeBalanceActuator`/`UnfreezeBalanceProcessor` gate the ability to reclaim a delegated resource solely on `delegatedResourceCapsule.getExpireTimeForBandwidth()`/`getExpireTimeForEnergy()` being `<= now`, and treat the delegated balance as a single aggregate number (not per-freeze-event), an attacker who is the owner of a delegation to a given receiver can: [4](#0-3) [5](#0-4) 

1. Delegate a large balance to `receiver` with a long `frozenDuration` (e.g., 30 days), setting `expireTimeForBandwidth = now+30d`.
2. Later delegate an additional (even tiny) amount to the same `receiver` with the minimum `frozenDuration` (3 days, the minimum allowed by `FreezeBalanceActuator`/`FreezeBalanceProcessor`), which calls `addFrozenBalanceForBandwidth(smallBalance, now+3d)` — this overwrites `expireTimeForBandwidth` to `now+3d` for the *entire combined* balance.
3. After 3 days (instead of the originally committed 30 days), call `UnfreezeBalanceContract`/`unfreezeBalance()` and reclaim the *entire* combined delegated balance, because the validation only checks the single (now-shortened) expire time field.

This is the same bug class as the reported issue: an expiration-tracking field is overwritten by the "most recent" operation rather than preserving the correct (larger/legitimate) value, breaking the invariant that a resource remains locked for its originally committed duration.

### Impact Explanation
This lets a resource owner escape the intended freeze/lock period of previously delegated TRX, reclaiming staked balance (and thus resource weight backing bandwidth/energy given to the receiver) earlier than protocol rules intend. Since total network bandwidth/energy weight accounting and delegate-receiver resource allocation depend on the committed freeze duration, this allows early unstaking of funds that should remain locked, which is a fund-freezing/accounting-integrity violation reachable by any account issuing ordinary `FreezeBalanceContract`/`UnfreezeBalanceContract` transactions or the corresponding TVM opcodes — no special privileges required.

### Likelihood Explanation
Any account can trigger this with two ordinary freeze transactions (or TVM `freezeBalance`/`unfreezeBalance` calls) to the same receiver with different `frozenDuration` values, then a later `unfreezeBalance` transaction. It requires only knowledge of the resource delegation contracts (public API/ABI), no elevated permissions, and no race condition — a deterministic sequence of self-issued transactions.

### Recommendation
In `DelegatedResourceCapsule.addFrozenBalanceForBandwidth`/`addFrozenBalanceForEnergy`, only update the stored expire time if the newly computed expire time is greater than (or the existing balance is zero), i.e. `setExpireTimeForBandwidth(Math.max(existingExpireTime, newExpireTime))`, rather than unconditionally overwriting it. Apply the same fix to the V2 delegate-with-lock path (`DelegateResourceActuator`) for consistency.

### Proof of Concept
1. Owner freezes 1,000 TRX to `receiver` for bandwidth with `frozen_duration = 30` (30 days) via `FreezeBalanceContract` → `DelegatedResourceCapsule{frozenBalanceForBandwidth=1000, expireTimeForBandwidth = t0+30d}`.
2. Owner freezes 1 TRX to `receiver` for bandwidth with `frozen_duration = 3` (minimum) via another `FreezeBalanceContract` → `addFrozenBalanceForBandwidth(1, t0+3d)` sets `frozenBalanceForBandwidth=1001`, `expireTimeForBandwidth = t0+3d` (overwritten, shortened from 30d to 3d).
3. At `t0+3d < t0+30d`, owner submits `UnfreezeBalanceContract` targeting `receiver`/BANDWIDTH; `UnfreezeBalanceActuator.validate()` checks only `delegatedResourceCapsule.getExpireTimeForBandwidth() > now` (now false) and allows reclaiming the full 1001 TRX, three days early relative to the originally committed 30-day lock.
