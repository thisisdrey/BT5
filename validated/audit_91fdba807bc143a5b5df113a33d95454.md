### Title
`MarketSellAssetActuator` self-trade causes maker-side proceeds to be silently lost when taker and maker orders belong to the same account - ([File: actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java])

### Summary
`MarketSellAssetActuator.execute()` matches a taker's `MarketSellAssetContract` against resting maker orders in the on-chain order book. Nothing in `validate()` or `matchOrder()`/`matchSingleOrder()` prevents an account from matching against its own resting order (self-trade), analogous to the reported "sender == recipient" scenario where a code path assumes two distinct parties but the same account can occupy both roles. When taker and maker are the same account, the actuator applies the taker-side and maker-side balance/asset updates through two different, unsynchronized `AccountCapsule` object instances for the same address, and the later write silently overwrites the earlier one.

### Finding Description
In `execute()`, the taker's account is loaded once into `accountCapsule` and passed by reference through the whole flow: [1](#0-0) 

`matchOrder()`/`matchSingleOrder()` credit the taker's buy-side token to this same in-memory `takerAccountCapsule` reference (not persisted immediately): [2](#0-1) [3](#0-2) 

But the maker-side credit is computed with a *separate* `addTrxOrToken(makerOrderCapsule, num)` overload that independently re-fetches the maker's `AccountCapsule` from `accountStore`, mutates it, and immediately calls `accountStore.put(...)`: [4](#0-3) 

If the maker order's owner address equals the taker's address (self-trade — nothing in `validate()`/`matchOrder()` forbids this), this second call fetches a *stale* copy of the account from the store (missing the not-yet-persisted taker-side changes already applied to `accountCapsule`/`takerAccountCapsule`), applies the maker credit to that stale copy, and persists it. Then, at the end of `execute()`, the original in-memory `accountCapsule` (which reflects only the fee deduction, sell-side debit, and taker-side buy credit, but not the maker-side credit just written to the store) is persisted again: [5](#0-4) 

This final `accountStore.put()` overwrites the intermediate write from the maker-credit path, permanently discarding the maker-side proceeds that were just credited to the same account.

### Impact Explanation
For a self-matching order pair, part of the trade proceeds (the maker-side token/TRX credit) is computed, temporarily written to the account store, and then unconditionally overwritten and lost when the taker's final account state is persisted. This is a permanent, unrecoverable loss of TRC10 token/TRX balance for the account that placed both the maker and taker orders — a concrete "loss of funds" impact reachable purely by an unprivileged user broadcasting two market order transactions (`MarketSellAssetContract`) that happen to cross with each other. Because `matchOrder()` can match a taker order against multiple maker price levels/orders in one call (`MAX_MATCH_NUM`), it's also possible for a user to unknowingly self-match part of a larger order and lose only that portion's maker proceeds, making the bug subtle and hard to detect by the affected user.

### Likelihood Explanation
Likelihood is limited by the fact that a single account must have two resting/incoming orders that are direct token-pair opposites and cross in price (e.g., sell A for B, and sell B for A at compatible prices). This is achievable deliberately (e.g., a bot providing liquidity on both sides of a market, or a user attempting wash trading/self-fills for volume) or accidentally by a market maker who runs both buy and sell orders on the same account. There is no explicit safeguard in `validate()` preventing a taker's own resting maker orders from being matched, so this is trivially triggerable by any account willing to place two crossing orders.

### Recommendation
Detect the self-trade case (`Arrays.equals(takerOrderCapsule.getOwnerAddress().toByteArray(), makerOrderCapsule.getOwnerAddress().toByteArray())`) in `matchSingleOrder()`/`addTrxOrToken` and route the maker-side credit through the same in-memory `takerAccountCapsule` reference used for the taker side (rather than re-reading/re-writing via `accountStore` for the maker), or fully commit the taker's account object to the store before doing subsequent maker-side reads to guarantee reads always see the freshest state for the same address. Alternatively, refuse to match an order against another order owned by the same account.

### Proof of Concept
1. Account `A` places `MarketSellAssetContract` selling token `X` for token `Y` (order O1), which rests in the order book (no immediate match).
2. Account `A` places a second `MarketSellAssetContract` selling token `Y` for token `X` (order O2) at a compatible price, so `matchOrder()` matches O2 (taker) against O1 (maker) — both owned by `A`.
3. During `matchSingleOrder()`, `addTrxOrToken(takerOrderCapsule, takerBuyTokenQuantityReceive, takerAccountCapsule)` credits token `X` to the in-memory `takerAccountCapsule` for `A` (not yet persisted).
4. `addTrxOrToken(makerOrderCapsule, makerBuyTokenQuantityReceive)` re-fetches `A`'s account from `accountStore` (a stale copy missing step 3's changes), credits token `Y`, and calls `accountStore.put()` immediately — this write is visible in the DB at this point.
5. `execute()` finishes and calls `accountStore.put(accountCapsule.createDbKey(), accountCapsule)` using the original `accountCapsule` reference for `A`, which reflects the fee deduction and step-3 credit but NOT the token `Y` credit written in step 4 — overwriting it.
6. Final result: account `A` never receives the token `Y` credit from the maker side of the self-trade, even though the order book state (`MarketOrderCapsule`) reflects the trade as fully executed — a silent, permanent loss of funds.
