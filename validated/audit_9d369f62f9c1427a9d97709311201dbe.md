### Title
Permissionless dust deposits/transfers fill a victim's deposit-token list to `MAX_TOKENS_PER_USER`, permanently DoS-ing all new collateral positions - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
Analogous to the Particle `addCredit()` griefing (anyone can modify state at ~zero cost to make a victim's transactions revert), any unprivileged account can call `DepositToken.deposit(amount, onBehalfOf_ = victim)` or `DepositToken.transfer(victim, dust)` with arbitrarily small amounts of every deposit token in the pool. Each first-time token receipt calls `Pool.addToDepositTokensOfAccount(victim)`, which reverts with `UserReachedMaxTokens` once the victim's combined deposit/debt token list hits `MAX_TOKENS_PER_USER`. From then on, every action that would add a new deposit token to the victim's list — deposits, transfers-in, liquidation seizes in the victim's favor — reverts. This can also be front-run per-transaction: the attacker fills the victim's last free slot just before the victim's deposit of a new collateral type lands, making it revert.

### Finding Description
`DepositToken.deposit` is public, `whenNotPaused`, and accepts an `onBehalfOf_` beneficiary, so the attacker can mint dust deposit tokens directly to the victim at a cost bounded only by gas plus dust of each underlying ( [1](#0-0) ). Alternatively the attacker deposits once and `transfer()`s dust to the victim; `transfer` only checks the sender's unlocked balance, not the recipient's consent ( [2](#0-1) ). Both paths reach `_mint`/`_transfer`, which call `pool.addToDepositTokensOfAccount(recipient_)` on any balance change from zero ( [3](#0-2)  and [4](#0-3) ). `addToDepositTokensOfAccount` enforces `onlyIfAdditionWillNotReachMaxTokens`, reverting when `debtTokensOfAccount.length + depositTokensOfAccount.length >= MAX_TOKENS_PER_USER` ( [5](#0-4)  and [6](#0-5) ).

### Impact Explanation
Once the victim's list is full, any deposit, incoming `transfer`, or liquidation `seize` credit of a deposit token they do not already hold reverts — the victim is frozen out of opening new collateral positions and cannot be deposited-to or liquidated in their favor for new token types. The only escape is for the victim to burn/transfer out a full balance to free a slot (`_burn`/`_transfer` remove entries at zero balance), which is the same class of forced, attacker-controllable liveness loss as the original report: cheap permissionless state mutation that makes a victim's otherwise-valid transaction fail. This is a temporary freezing of position-management capability (existing balances and withdrawals still work).

### Likelihood Explanation
Fully unprivileged: requires only dust amounts of each listed underlying (or one deposit followed by dust transfers), no privileged roles, no oracle manipulation. Cost scales with the number of registered deposit tokens; on deployments with many collaterals the attack may only be practical against victims already near the cap, but the front-running variant works whenever the victim has exactly one free slot. Note: I could not confirm the exact `MAX_TOKENS_PER_USER` constant value or the per-chain deposit-token count within this search session; if the deployed pools have fewer tokens than the cap, the attack is only reachable for near-cap victims and the finding weakens accordingly.

### Recommendation
Require recipient consent for adding to `depositTokensOfAccount` (e.g., only the beneficiary may open a new position via an `acceptPosition` flow or a per-account whitelist), or charge/store positions so unsolicited dust cannot consume list slots. Short-term mitigations mirroring the original report: make `deposit` only allow `onBehalfOf_ == _msgSender()` for new positions, enforce a minimum meaningful first-deposit amount, and exempt the transfer path from list insertion when the recipient is at the cap (leave tokens uncredited or revert only the sender's actions).

### Proof of Concept
Hardhat/Foundry fork sketch:

```solidity
// victim currently holds 0 positions; pool has N deposit tokens
for each depositToken in pool.depositTokens():
    underlying.approve(depositToken, dust);
    depositToken.deposit(dust, victim);   // adds token to victim's list

// victim's list now at MAX_TOKENS_PER_USER
vm.prank(victim);
usdcDepositToken.deposit(amount, victim); // reverts UserReachedMaxTokens

// front-run variant: victim tx pending to deposit a new token
depositToken.transfer(victim, dust);      // attacker fills last slot
// victim's pending deposit now reverts
```

Expected revert: `UserReachedMaxTokens()` from `Pool.onlyIfAdditionWillNotReachMaxTokens` inside `addToDepositTokensOfAccount`.
