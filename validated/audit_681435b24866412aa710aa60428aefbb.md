### Title
Client-Controlled `remote_ip` Metadata Enables Bypass of Pack-Objects Concurrency Limiter, Allowing Resource-Exhaustion Flooding - (File: internal/gitaly/service/hook/pack_objects.go)

### Summary
The reported bug class describes a rate/anti-flood control that is derived from a value the actor can freely control, so the limiting key never actually constrains the actor, enabling cheap resource-exhaustion flooding. Gitaly's pack-objects concurrency limiter has the same structural weakness: the per-caller "remote IP" key used to throttle concurrent `git-pack-objects` invocations is taken verbatim from a client-supplied gRPC metadata/request field rather than from a trusted, connection-derived source.

### Finding Description
The `packObjectsHook` handler derives its concurrency-limiting key directly from `req.GetRemoteIp()`: [1](#0-0) 

`RemoteIp` is a plain string field of `PackObjectsHookWithSidechannelRequest`: [2](#0-1) 

This value is populated from the gRPC metadata key `"remote_ip"` on the *original* upload-pack/receive-pack RPC via `metadata.GetValue(ctx, "remote_ip")`, with no verification against the actual TCP peer address: [3](#0-2) 

The same unauthenticated, unvalidated pass-through pattern is used generally for metadata extraction in `requestinfohandler`, where `remote_ip`, `user_id`, `username`, and `caller_id` are read straight out of incoming gRPC metadata: [4](#0-3) 

The concurrency limiter itself (`limiter.TypePackObjects`) is documented to use "request information (RemoteIP/Repository/User)" as its limiting key: [5](#0-4) 

and the handler only applies the limiter (`runPackObjectsLimited`) when the parsed IP is non-empty and non-loopback; otherwise it runs `git-pack-objects` completely unthrottled: [6](#0-5) 

Because the key is self-reported metadata rather than a value bound to the transport-level connection, any caller able to set (or vary, or omit) this metadata on their gRPC calls can make every request appear to originate from a distinct "remote IP" — or from the loopback address, which is explicitly excluded from limiting. This mirrors the reported bug class: the guard exists, but it is enforced on a value that the very actor being throttled fully controls, so it provides no real protection against flooding.

### Impact Explanation
The pack-objects concurrency limiter exists specifically as a backpressure/DoS-protection mechanism, gating expensive `git-pack-objects` invocations that materialize large pack streams from repository data. Bypassing its limiting key allows an attacker to run an unbounded number of concurrent, expensive `git-pack-objects` processes against a repository (or across repositories) by simply rotating or blanking the `remote_ip` value per request, exhausting Gitaly server CPU, memory, and disk I/O and causing denial of service for the shared node.

### Likelihood Explanation
Exploitation only requires the ability to set or omit outgoing gRPC metadata alongside otherwise-normal, protocol-valid upload-pack/fetch requests — no special privileges beyond ordinary authenticated access to the Gitaly RPC surface are needed, and the test suite itself demonstrates that `RemoteIp` values are taken as-is from the request (including empty-string and loopback cases that are deliberately excluded from limiting): [7](#0-6) 

### Recommendation
Do not derive the pack-objects (or any resource-limiting) key from client/request-supplied metadata alone. Bind the limiting key to a trusted, transport-derived value (e.g., the actual peer address from the gRPC connection/peer info, or an authenticated principal identifier established during auth), and treat the `remote_ip` metadata field as untrusted auxiliary/logging information only. Additionally, avoid a design where a missing/unparseable/loopback-classified IP causes the limiter to be skipped entirely — fail closed (still limit) rather than fail open.

### Proof of Concept
1. As an authenticated Gitaly client, issue repeated `git-upload-pack`/`SSHUploadPack` (or equivalent) requests against the same repository, each time setting a distinct value of `remote_ip` in the outgoing gRPC metadata (or omitting it, or setting it to `127.0.0.1`).
2. Each request results in a `PackObjectsHookWithSidechannelRequest.RemoteIp` that differs (or is loopback/empty), so `packObjectsHook` computes a different — or entirely bypassed — limiting key per request: [1](#0-0) 
3. The shared `packObjectsLimiter` (configured with `MaxPerRepo`/adaptive limits) never accumulates concurrent calls under a single key, so an arbitrary number of concurrent `git-pack-objects` processes run simultaneously, unconstrained by the intended per-caller concurrency cap.
