### Title
Dust-transfer griefing fills a victim's `MAX_TOKENS_PER_USER` slots, blocking collateral top-ups and mints, forcing liquidation - (File: contracts/Pool.sol)

### Summary
Analogous to CVE-2017-7520 (unprivileged, remote-triggered denial of service), an unprivileged attacker can grief any account by transferring dust amounts of many distinct `DepositToken`s to it. Each first-time receipt calls `Pool.addToDepositTokensOfAccount`, which enforces `MAX_TOKENS_PER_USER = 30`. Once the victim's combined deposit+debt token list is full, every path that would add a new token to their list reverts with `UserReachedMaxTokens` — including `deposit`, leveraged deposits via `SmartFarmingManager`, and receiving transfers/seizes of new collateral types. A victim with an unhealthy position cannot deposit a new collateral type to restore health and is forced into liquidation.

### Finding Description
`DepositToken._transfer` adds the token to the recipient's per-account list on first receipt:

```solidity
// contracts/DepositToken.sol:517-520
if (_recipientBalanceBefore == 0 && amount_ > 0) {
    pool.addToDepositTokensOfAccount(recipient_);
}
```

`Pool.addToDepositTokensOfAccount` (and the debt-token equivalent) is gated by `onlyIfAdditionWillNotReachMaxTokens`:

```solidity
// contracts/Pool.sol:143-148, 204-219
if (debtTokensOfAccount.length(account_) + depositTokensOfAccount.length(account_) >= MAX_TOKENS_PER_USER) {
    revert UserReachedMaxTokens();
}
```

The attacker deposits dust of each registered collateral through `DepositToken.deposit(1, attacker)` (their balance is unlocked since they hold no debt), then calls `transfer(victim, 1)`. No modifier (`_revertIfLocked`, `nonReentrant`, pause flags, `SynthContext`) prevents this: transfers of unlocked balances are a public ERC20 entry point, and the victim has no way to opt out of receiving `DepositToken`s. Once `depositTokensOfAccount[victim] + debtTokensOfAccount[victim]` reaches 30, all of the following revert for the victim:

- `deposit(amount, victim)` for any collateral the victim doesn't already hold (`_mint` → `addToDepositTokensOfAccount` reverts)
- `DebtToken.issue/mint` of any new synthetic (`addToDebtTokensOfAccount` reverts)
- `SmartFarmingManager.leverage`/`flashRepay` flows that mint new tokens to the victim
- `Pool.liquidate` if the victim is the liquidator's counterparty... more precisely, `depositToken_.seize(account_, liquidator, ...)` succeeds, but the victim cannot be topped up.

### Impact Explanation
Temporary freezing of funds / forced liquidation. If the victim has an open debt position that drifts toward the liquidation threshold (e.g., via normal price movement), they cannot deposit a new collateral type to restore health — every rescue deposit reverts. They can only add to collateral types already in their list or repay debt; if they lack the synthetic tokens to repay, they are liquidated and lose the liquidator incentive + protocol fee. The attacker can also front-run a victim's first-ever deposit into a new market, DoSing their entry. Cleanup (transferring dust out to free slots) requires the victim to actively send 1 wei of each dust token away — possible, but the attacker can refill slots again at dust cost.

### Likelihood Explanation
Attack cost is bounded by the number of registered deposit/debt tokens in the pool (cap is 30 combined). Each step requires only a dust deposit plus a 1-wei transfer — all public, unprivileged entry points. No privileged role, oracle manipulation, or timing dependency is needed. The attack is limited to pools with enough registered tokens to reach 30 combined slots and is most damaging against leveraged positions near liquidation.

### Recommendation
- Don't count tokens with dust/negligible balances, or only add to `depositTokensOfAccount` when the received amount exceeds a minimum threshold.
- Alternatively, allow removal-into-add: let `addToDepositTokensOfAccount` succeed by evicting zero-value or dust entries.
- Or exempt `deposit`/`issue` from the cap by letting users always add tokens for positions they intentionally open, restricting only unsolicited `transfer`-based additions.
