## Analysis

The binding under test is: `p.receiver_id != env::current_account_id()` for all `external` promises. Tracing `WalletImpl::build_promise`: [1](#0-0) 

```rust
fn build_promise(p: NearPromise) -> Result<Promise> {
    // check for no self-calls
    if p.receiver_id == env::current_account_id() {
        return Err(Error::SelfCallsNotAllowed);
    }
```

This check is applied unconditionally to every `NearPromise` in `Request::external`, regardless of whether the request originated from `execute_signed` or `execute_extension`, since both paths funnel through the shared `execute_request` -> `build_promise` call: [2](#0-1) 

There is no branch, extension bypass, or "trusted actor" exception around this check — it runs before the actions are inspected and before the promise is built, for every promise regardless of `actor` (`Actor::SignedRequest` or `Actor::Extension`).

Separately, `add_extension` indeed contains no explicit check that `account_id != env::current_account_id()`: [3](#0-2) 

So a wallet can technically add itself as an "enabled extension" in its `extensions` set. However, this has no exploitable effect: the only way `w_execute_extension` checks authorization is via `env::predecessor_account_id()` being in the enabled extension set: [4](#0-3) 

To reach `w_execute_extension` with `predecessor_account_id() == current_account_id()`, the wallet would need to schedule a cross-contract call promise targeting itself — and that is exactly what `build_promise` unconditionally rejects with `Error::SelfCallsNotAllowed`, closing the only reachable path (there is no synchronous self-invocation mechanism in NEAR; it must go through a `Promise`, and all promises are filtered through `build_promise`).

The existing test suite (`crates/wallet/sdk/tests/test.rs`) confirms extension mechanics work via genuine distinct-account extensions, and the `w_init` test even demonstrates the `RemoveExtension` path for `near.account_id()` (self) fails only because it's not present in the set, not because of a self-check — consistent with `add_extension` lacking a self-account guard, but this gap is inert given the unconditional self-call block in `build_promise`. [5](#0-4) 

Both sides of the binding match: `receiver_id != current_account_id()` holds for every path that could reach `w_execute_extension` (or any other wallet method) via a `Promise`, so the self-call bypass of nonce/signature checks described in the question is not reachable.
