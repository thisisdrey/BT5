### Title
Unbounded in-memory buffering of non-LFS-pointer blob content in git-filter-process smudge handler causes DoS - ([File: cmd/gitaly-lfs-smudge/smudge.go])

### Summary
`gitaly-lfs-smudge`'s long-running filter-process implementation (`process()` in `cmd/gitaly-lfs-smudge/smudge.go`) buffers the entire content of every smudged blob into an unbounded `bytes.Buffer` before it can determine whether the blob is a real LFS pointer. An unprivileged user who owns a repository can mark an arbitrary large blob as LFS-filtered via `.gitattributes` and later trigger `RepositoryService.GetArchive` with `IncludeLfsBlobs=true`, causing the Gitaly host to allocate memory proportional to the attacker-chosen blob size with no upper bound.

### Finding Description
`internal/gitaly/service/repository/archive.go`'s `handleArchive` wires up `filter.lfs.process` to run `gitaly-lfs-smudge` whenever `GetArchiveRequest.IncludeLfsBlobs` is set [1](#0-0) . Git then drives the long-running filter protocol against `gitaly-lfs-smudge`, whose `process()` function reads pktlines via `pktline.NewScanner(from)` [2](#0-1) .

Each 64 KiB-max pktline packet of blob content received in `processStateSmudgeContent` is appended to an in-memory `bytes.Buffer` (`content.Write(data)`) with no cap on total accumulated size, and only once a flush packet is seen is `smudgeOneObject`/`lfs.DecodeFrom` called to check whether the buffered content is actually a valid LFS pointer [3](#0-2) . `pktline.NewScanner` itself only bounds the size of a single packet (`MaxPktSize = 65520`) via `scanner.Buffer`, not the total number of packets/overall stream size [4](#0-3) . The code comment explicitly acknowledges the design fully materializes non-pointer content in memory before it can be echoed back [5](#0-4) .

An attacker who owns a repository controls both the `.gitattributes` filter assignment (to route an arbitrary blob through `filter.lfs.process`) and the blob content itself (a non-pointer blob of arbitrary size). Requesting `GetArchive` with `IncludeLfsBlobs=true` on that ref forces `git archive` to invoke the smudge filter for that blob, which slurps the full blob into RAM inside the `gitaly-lfs-smudge` child process.

### Impact Explanation
Memory usage of the `gitaly-lfs-smudge` subprocess (and transitively affects the parent Gitaly host, since child processes share host memory) scales linearly with attacker-controlled blob size with no cap, matching a DoS-of-RPC-handler impact class. Because storage nodes are typically shared across tenants, sufficiently large attacker blobs can exhaust host memory during archive/export operations, potentially impacting co-located repositories/tenants.

### Likelihood Explanation
The attacker only needs standard push/repo-owner capability (create `.gitattributes` entry marking a path `filter=lfs`, push a large non-pointer blob under that path) and the ability to trigger an archive/export RPC with `IncludeLfsBlobs=true` on their own repository — both are standard, unprivileged, self-service GitLab actions (repository archive download / project export). The practical bound on exploitation is the size of blob the attacker can push into their own repository (subject to any repository size quota enforced by GitLab Rails, not by Gitaly), so likelihood is moderate and scales with whatever storage quota the attacker's namespace has.

### Recommendation
Cap the total size buffered per smudge object (e.g., limit `content` to the LFS pointer maximum size — a few hundred bytes — using a peek/limited reader before deciding whether to fall back to streaming the remainder directly to the client rather than buffering it entirely in memory). Alternatively, stream non-pointer content back to git incrementally instead of fully materializing it, or enforce a configurable maximum blob size for filter-processed content that aborts the operation early with an explicit error when exceeded.

### Proof of Concept
```go
// cmd/gitaly-lfs-smudge/smudge_memory_test.go
func TestProcess_UnboundedMemoryForNonPointerBlob(t *testing.T) {
    var in bytes.Buffer
    // simulate git-filter-process handshake
    writePkt(&in, "git-filter-client\n")
    writePkt(&in, "version=2\n")
    writeFlush(&in)
    writePkt(&in, "capability=smudge\n")
    writeFlush(&in)
    writePkt(&in, "command=smudge\n")
    writePkt(&in, "pathname=huge.bin\n")
    writeFlush(&in)

    // 500MB of non-LFS-pointer content, split into MaxPktSize chunks
    chunk := bytes.Repeat([]byte("A"), pktline.MaxPktSize-4)
    for i := 0; i < (500*1024*1024)/len(chunk); i++ {
        writePkt(&in, string(chunk))
    }
    writeFlush(&in)

    var out bytes.Buffer
    var m1, m2 runtime.MemStats
    runtime.ReadMemStats(&m1)
    err := process(context.Background(), smudge.Config{}, &out, &in, testLogger)
    runtime.ReadMemStats(&m2)
    require.NoError(t, err)
    // Observed: m2.Alloc - m1.Alloc grows proportionally to injected content size,
    // confirming content bytes.Buffer has no upper bound.
}
```
Combined with `RepositoryService.GetArchive{IncludeLfsBlobs: true}` against a repository containing a `.gitattributes` entry `huge.bin filter=lfs` and a large non-pointer blob at that path, this reproduces the unbounded buffering at the RPC level.

func NewScanner(r io.Reader) *bufio.Scanner {
	scanner := bufio.NewScanner(r)
	scanner.Buffer(make([]byte, MaxPktSize), MaxPktSize)
	scanner.Split(pktLineSplitter)
