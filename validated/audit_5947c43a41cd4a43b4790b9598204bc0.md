### Title
Wallet-contract relayer fee is paid before the async registrar address-check resolves, allowing unlimited replay-drain of the eth-implicit account's balance - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The `[M02]` report describes a class of bug where a fee-collecting effect and the validation/finalization of the associated transfer are split across a cross-contract call boundary, so an in-contract `nonReentrant`-style guard cannot enforce the invariant that the fee is only paid for a transaction the protocol actually validated. The eth-implicit `WalletContract` has the same structural defect: it unconditionally pays out a relayer `fee` from its own balance *before* an asynchronous cross-contract registrar lookup confirms the transaction is valid, and the failure branch of that lookup neither reverses the fee payment nor consumes the nonce, so the same signed transaction can be resubmitted indefinitely to keep collecting the fee.

### Finding Description
`inner_rlp_execute` computes the relayer `fee` from the parsed Ethereum transaction and, for `EOABaseTokenTransfer`/`ERC20Transfer` kinds, immediately schedules a NEAR transfer of `fee` to `predecessor_account_id` — this happens synchronously, before the actual target action is confirmed to succeed: [1](#0-0) 

For the `EOABaseTokenTransfer { address_check: Some(address), .. }` case specifically, the nonce increment is deliberately deferred until the async registrar lookup resolves in `address_check_callback`, because at fee-payment time the contract does not yet know whether the transaction is legitimate: [2](#0-1) 

When the registrar lookup returns `Some` (i.e., the “address check” proves the relayer’s `target` argument was wrong / the address is actually a registered named account), the callback bans the relayer *only if* the caller used the wallet contract's own access key (`signer_account_id == current_account_id`). Otherwise, it simply returns an error response, with **no nonce increment and no penalty**: [3](#0-2) 

Because `rlp_execute` is a public, `#[payable]` method that anyone can call directly as `predecessor_account_id` (not necessarily via a granted access key), an attacker who obtains a validly RLP-signed transaction (which by design is meant to be shareable with "any relayer", per the code comment at lines 367–373) can:
1. Call `rlp_execute` themselves with `target` set so that `address_check` triggers and resolves to `Some` (a genuinely registered account).
2. Collect the unconditionally-sent `fee` from the wallet's own balance (`predecessor_account_id` is the attacker's own account, not a bystander).
3. Receive an error result with the nonce left unchanged and no key banned (since they did not authenticate via the wallet's own access key), allowing the exact same call to be repeated.

This lets an attacker drain the wallet's NEAR balance in the amount of `fee` per call, repeated as many times as they can pay for gas, all without needing any access-key grant and without the intended "one faulty attempt bans the relayer" safeguard ever engaging.

### Impact Explanation
This results in direct, repeatable theft of NEAR funds from an ordinary user's eth-implicit wallet-contract account — an unprivileged, ordinary-transaction-reachable path involving the eth-implicit wallet contract, which is explicitly in-scope. The loss is bounded only by attacker gas cost and the wallet's balance, and the intended mitigation (revoking the offending relayer) never triggers because the exploiting caller is not using a granted access key.

### Likelihood Explanation
Exploitation requires the attacker to possess one validly RLP-signed transaction of `EOABaseTokenTransfer` kind with a non-zero `fee` whose `to` address happens to correspond to (or can be crafted/found to correspond to, e.g., via front-running relayer traffic which is explicitly designed to be observable/shareable by "any relayer") a registered named account in the address registrar. Since relayer infrastructure is designed around openly rebroadcasting user-signed transactions to any relayer, and the fee is only usefully non-zero when a relayer is expected to be compensated, a signed transaction that hits this edge case is plausible to obtain by simply observing relayer traffic; the replay itself requires no special privilege, just direct calls to `rlp_execute`.

### Recommendation
Do not send the relayer `fee` until the target action (and, for the address-check path, the registrar confirmation) has actually completed successfully — move the fee transfer into `rlp_execute_callback`/`address_check_callback` success paths only, gated on the final `ExecuteResponse::success`. Additionally, ensure that any invalid/replayable relayer-error branch either consumes the nonce or is otherwise made non-replayable, regardless of whether the caller used a granted access key, so that repeated submission of the same signed transaction cannot repeatedly trigger fee payment.

### Proof of Concept
1. Obtain (e.g., by observing relayer network traffic, which by design is meant to be shareable, per the code's own comment) a validly RLP-signed Ethereum-style transaction for a `WalletContract`, structured as an `EOABaseTokenTransfer` with non-zero `fee`, whose `to` address is one that is registered in the address registrar contract.
2. As an arbitrary NEAR account (attacker), call `rlp_execute(target, tx_bytes_b64)` directly on the victim's wallet contract, setting `target` to an eth-implicit-looking account ID that triggers the `address_check: Some(address)` branch (per `internal.rs` target-kind logic).
3. Observe: `inner_rlp_execute` immediately creates and sends the `fee` transfer to the attacker (`predecessor_account_id`).
4. The registrar lookup resolves, finds the address is registered, and since the attacker did not sign via the wallet's own access key, `address_check_callback` returns a failure `ExecuteResponse` without banning any key and without incrementing `self.nonce`.
5. Repeat step 2 with the same unmodified transaction bytes indefinitely, draining `fee` from the wallet contract's balance each time.
