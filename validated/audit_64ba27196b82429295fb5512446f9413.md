## Analysis Result

I found a strong local analog to the StableMath rounding bug in `pallet-psm`'s `mint`/`redeem` decimal-conversion round-trip logic, specifically in the `redeem` extrinsic's use of `internal_to_external` followed by `external_to_internal` to compute `effective_internal_net`.

### Title
PSM `redeem` under-burns internal asset relative to external asset paid out when `ext_decimals > internal_decimals` (round-trip truncation asymmetry) - (File: `substrate/frame/psm/src/lib.rs`)

### Summary
`Pallet::redeem` computes `external_out = internal_to_external(internal_net, ...)` (floor division when scaling down) and then re-derives `effective_internal_net = external_to_internal(external_out, ...)` (floor division again, in the *same* direction) to decide how much internal asset to actually burn and how much debt to relieve [1](#0-0) . Because both conversions floor-round in the same direction (down when converting to fewer decimals), each round-trip can lose fractional units of debt tracking versus the external asset actually transferred out of the reserve, similarly to how StableMath's chained rounding in `_calculateInvariant` → `_getTokenBalanceGivenInvariantAndAllOtherBalances` let a swapper accumulate free value through directionally-inconsistent rounding across chained operations.

### Finding Description
`external_to_internal` floor-divides when `ext_decimals > internal_decimals` [2](#0-1) . In `redeem`, the flow is: burn `effective_internal_net` (derived via a *second* floor-round trip of `external_out`) rather than `internal_net` itself, while the user has already been charged `fee` on the full `internal_amount` and receives `external_out` in full [3](#0-2) . The dust from `internal_net - effective_internal_net` is intentionally left in the user's internal balance per the code comment ("Any truncation dust stays in the caller's internal balance, symmetric with mint") [4](#0-3) . This design assumes the dust is bounded to at most `10^diff - 1` external-asset base units per call — negligible for a single call. However, unlike an AMM swap (bounded by pool liquidity and price impact), a PSM redeem is a 1:1 fixed-rate conversion with no slippage, and `min_swap_amount` is denominated in internal-asset units, not external-asset units after conversion, so an attacker can call `redeem` with `internal_amount` values chosen to repeatedly land favorably on rounding boundaries.

### Impact Explanation
Each redemption transfers real external-asset reserve out of the PSM while the tracked internal debt (`PsmDebt`) is decremented by a value that can be smaller than what was economically extracted, because `effective_internal_net` is derived through a double-floor round-trip rather than being tied directly to the burned amount actually reflecting `external_out`'s exact economic value. Over many repeated redemptions (dust accumulation), this can allow extraction of external reserve in excess of debt reduction, degrading the PSM's peg backing — analogous to the "attacker accumulating dust through repeated calls" scenario described in the original StableMath report.

### Likelihood Explanation
The `redeem` extrinsic is public/unprivileged (`ensure_signed`), requires no special origin, and can be called at will subject only to `min_swap_amount` and the circuit breaker [5](#0-4) . Exploitability depends on how large `10^diff - 1` is relative to `min_swap_amount` and gas/weight cost per call — for common decimal differences (e.g., 12 vs 6, `diff=6`), the per-call dust ceiling (`10^6 - 1` external base units) could be economically significant relative to transaction fees when repeated. This mirrors the "medium severity... not able to generate free tokens with large balances... but might still be possible in certain edge cases" characterization from the original report.

### Recommendation
Do not re-derive `effective_internal_net` via a second independent floor conversion of `external_out`. Instead, burn exactly `internal_net` (the amount already computed and fee-adjusted) and decrement debt by `internal_net`, using ceiling-rounding only for the *fee* computation (which is already `mul_ceil`), while ensuring the external leg (`external_out`) is derived with a rounding direction that never lets the external amount transferred out exceed what `internal_net` warrants (i.e., floor when converting internal→external, floor when external→internal, and use the *same single* conversion result consistently for both debt accounting and asset movement — never a second independent round-trip). Add invariant tests asserting that cumulative external outflow never exceeds cumulative internal debt reduction across many small redemptions.

### Proof of Concept
Concrete numeric reproduction requires knowing the configured `ext_decimals`/`internal_decimals`/`min_swap_amount` for a live PSM instance, which are governance-configured values not fully enumerated in the indexed code (test file `substrate/frame/psm/src/tests.rs` contains relevant round-trip tests for `external_to_internal`/`internal_to_external`, but full test bodies were not retrieved due to iteration limits). Conceptually: with `internal_decimals = 6`, `ext_decimals = 12` (`diff = 6`), redeeming `internal_amount` values chosen so `internal_net` maps to an `external_out` whose re-conversion back floors down by up to `10^6 - 1` internal units per call, repeated `N` times, extracts `~N * (10^6 - 1)` internal-unit-equivalent of external reserve beyond what `PsmDebt` reflects as repaid.

**Uncertainty note:** I was unable to fully verify the exact numeric magnitude of exploitable dust or confirm whether `min_swap_amount` and per-instance decimal configurations in shipped runtimes (e.g., asset-hub) make this economically viable, since I ran out of tool iterations before reading `substrate/frame/psm/src/tests.rs` in full and before checking whether any runtime configures PSM instances with decimal differences large enough to matter. A Devin session with full file access would be needed to confirm exact exploitability bounds and existing test coverage of this round-trip.

		pub fn redeem(
			origin: OriginFor<T>,
			internal_asset: T::AssetId,
			external_asset: T::AssetId,
			internal_amount: BalanceOf<T>,
			max_fee: Permill,
		) -> DispatchResult {
			let who = ensure_signed(origin)?;
			let info = Psm::<T>::get(&internal_asset).ok_or(Error::<T>::PsmNotFound)?;

			let external = ExternalAssets::<T>::get(&internal_asset, &external_asset)
				.ok_or(Error::<T>::UnsupportedAsset)?;
			ensure!(external.status.allows_redemption(), Error::<T>::AllSwapsStopped);

			let ext_decimals = external.decimals;
			let internal_decimals = info.internal_decimals;

			ensure!(internal_amount >= info.min_swap_amount, Error::<T>::BelowMinimumSwap);

			let fee_rate = RedemptionFee::<T>::get(&internal_asset, &external_asset);
			ensure!(fee_rate <= max_fee, Error::<T>::FeeTooHigh);
			let fee = fee_rate.mul_ceil(internal_amount);
			let internal_net = internal_amount.saturating_sub(fee);

			let external_out =
				Self::internal_to_external(internal_net, ext_decimals, internal_decimals)?;
			ensure!(
				internal_net.is_zero() || !external_out.is_zero(),
				Error::<T>::AmountTooSmallAfterConversion
			);
			// `effective_internal_net` is the internal value that round-trips to `external_out`;
			// it is what we actually burn and what the tracked debt decreases by. Any truncation
			// dust stays in the caller's internal balance, symmetric with `mint`, which takes
			// only the round-tripped share of the external amount.
			let effective_internal_net =
				Self::external_to_internal(external_out, ext_decimals, internal_decimals)?;
