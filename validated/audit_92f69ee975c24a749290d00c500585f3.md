### Title
Remote panic via `assert!(preamble.payload_len > 5)` on empty `Blocks`/`Microblocks` push — ([File: stackslib/src/net/chat.rs])

### Summary
`ConversationP2P::validate_blocks_push` and `validate_microblocks_push` assert that `preamble.payload_len > 5`, assuming any legitimate `BlocksData`/`MicroblocksData` payload must contain at least one element. An empty vector (`0` blocks/microblocks) is a fully valid, codec-accepted payload that serializes to exactly `1` (type byte) + `4` (vector length prefix) = `5` bytes, so `payload_len == 5` is a reachable, legal value that violates the assertion.

### Finding Description
`validate_blocks_push` and `validate_microblocks_push` both begin with: [1](#0-0) [2](#0-1) 

The comment `// don't count 1-byte type prefix + 4 byte vector length` reveals the intended invariant: at least one payload byte beyond the type tag and vector-length prefix. But this invariant is not enforced anywhere in the wire codec — a `BlocksData { blocks: vec![] }` or `MicroblocksData { microblocks: vec![] }` is a perfectly valid, zero-element vector that consensus-serializes to exactly 5 bytes (1-byte message-type discriminant + 4-byte length-prefix `0u32`), and `Preamble` deserialization only requires `payload_len >= 5` as a floor, not `> 5`. Since `StacksMessage::consensus_deserialize` reads exactly `payload_len` bytes and does not re-derive or validate `payload_len` against "must contain ≥1 element," an attacker-supplied message with an empty blocks/microblocks vector and `payload_len == 5` passes deserialization cleanly and is routed to `handle_data_message`, which dispatches to `validate_blocks_push`/`validate_microblocks_push`, hitting the `assert!` and panicking the thread handling that peer's connection.

### Impact Explanation
A single crafted P2P message (an empty `BlocksData` or `MicroblocksData` push) causes an unhandled Rust `assert!` panic in the peer-network conversation handler. Depending on panic-handling configuration this can unwind/abort the P2P networking thread, denying service to that node from a single unauthenticated, unprivileged remote peer — repeatable indefinitely and trivially cheap to construct (no valid block/microblock data or private keys required). This matches the Critical category: remote crash/unauthenticated DoS from a single message.

### Likelihood Explanation
Precondition is only a working P2P handshake (the same low bar any peer must clear to gossip data at all) — no signer role, no RPC secret, no StackerDB ownership, and no privileged key material are needed. The attacker only needs to emit one message with a well-formed `Preamble` (`payload_len = 5`) and a payload consisting of the message type byte followed by a zero-length vector prefix. This is fully attacker-constructible from scratch, is deterministic, and can be repeated against the same or additional peers.

### Recommendation
Replace the `assert!(preamble.payload_len > 5)` calls in both `validate_blocks_push` and `validate_microblocks_push` with a graceful check that returns `Err(net_error::InvalidMessage)` (or simply treats an empty vector as a no-op success) instead of panicking, since an empty vector is a legitimate codec-level value and should not crash the node.

### Proof of Concept
In `stackslib/src/net/chat.rs` tests (alongside the existing `test_validate_block_push`/`test_validate_microblocks_push` harness):
1. Build a `StacksMessage` with `payload = StacksMessageType::Blocks(BlocksData { blocks: vec![] })` (or `Microblocks(MicroblocksData { microblocks: vec![] })`).
2. Sign/serialize it normally through `StacksMessage::sign`/`consensus_serialize`, confirming the serialized payload is exactly 5 bytes and `preamble.payload_len == 5` after this natural construction (no artificial post-hoc mutation needed, since an empty vector genuinely serializes to 5 bytes).
3. Feed the bytes through `StacksMessage::consensus_deserialize` to confirm it succeeds and yields `preamble.payload_len == 5`.
4. Call `conversation.validate_blocks_push(&network, &preamble, relayers)` (respectively `validate_microblocks_push`) directly and observe the process panic at the `assert!(preamble.payload_len > 5)` line, confirming the DoS.
