## Analog Vulnerability Found

### Title
Permanent DoS of a TRC10 trading pair via dust orders filling the fixed per-pair order-count cap — ([File: actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java])

### Summary
`MarketSellAssetActuator` enforces a fixed capacity of `MAX_ACTIVE_ORDER_NUM = 100` open orders per maker side of a token pair [1](#0-0) . Any unprivileged account holding a TRC10 asset can call `MarketSellAsset` repeatedly with minimal (dust) `sellTokenQuantity`/`buyTokenQuantity` values on the same `(sellTokenId, buyTokenId)` pair to fill all 100 slots, after which `validate()` rejects any further sell order on that pair with `"Maximum number of orders exceeded，100"` [2](#0-1) . This mirrors the reported Lottery LP bug in structure: a fixed-capacity, permissionlessly-fillable list (`lpLimit` vs. `MAX_ACTIVE_ORDER_NUM`) that a low-cost attacker can occupy to block all other legitimate participants from using the feature, at negligible cost, with no requirement for privileged access.

### Finding Description
The order book for a given TRC10-TRC10 (or TRX-TRC10) pair tracks the number of resting orders and enforces a cap via `MAX_ACTIVE_ORDER_NUM` before allowing a new sell order to be created [3](#0-2) . The maker-side price/order lists are tracked per pair in `MarketPairToPriceStore` and `MarketPairPriceToOrderStore`, which store a running count of prices/orders for the pair [4](#0-3) . There is no minimum order size enforced beyond the order quantities being positive integers, and no requirement that orders come from distinct or economically meaningful positions — an attacker only needs enough of a self-issued or cheaply acquired TRC10 asset to place 100 orders of quantity 1 (plus the market sell fee for each transaction). Once the cap is reached, `validate()` throws and blocks all further sell-side order creation on that specific pair for every other account, until the attacker voluntarily cancels their orders via `MarketCancelOrderActuator` — which the attacker has no incentive to do, exactly as in the original report where the LP attacker has no incentive to un-DoS the pool.

### Impact Explanation
**Medium/High**: The affected trading pair becomes permanently unusable for placing new sell orders by any other user (a concrete "API/feature the node can no longer serve" for that market), since the only way to free a slot is for the attacker (who controls the blocking orders) to cancel them. Existing buy-side liquidity and any user wanting to sell into that pair is denied service indefinitely, at the attacker's discretion — closely analogous to the LP-stake-to-zero DoS in the original report where the Lottery's LP deposit function became permanently unusable until the attacker withdrew.

### Likelihood Explanation
**Low-Medium**: Similar to the original finding, the attacker gains no direct profit and must pay the `MarketSellFee` (`calcFee()` returns `dynamicStore.getMarketSellFee()`) for each of the up to 100 dust orders [5](#0-4) , plus needs at least 100 units of the sell-side TRC10 token (or TRX), which is cheap to acquire or self-issue. This is a low-cost, no-special-privilege griefing attack reachable by any transaction broadcaster.

### Recommendation
Introduce per-account order limits on a given pair (in addition to, or instead of, a single global pair cap), and/or allow governance/administrators to purge stale dust orders, and/or scale the effective order cap or apply a minimum order value threshold so that filling all 100 slots requires meaningful economic commitment rather than dust-sized orders.

### Proof of Concept
1. Attacker acquires (or issues) a TRC10 token `T` and holds at least 100 units of it, plus enough TRX to cover 100 `MarketSellFee` payments.
2. Attacker calls `MarketSellAsset` 100 times with `sellTokenId = T`, `buyTokenId = TRX` (or any other token), `sellTokenQuantity = 1`, `buyTokenQuantity = 1` for each call, each creating a new resting order on the pair (see order construction in `MarketSellAssetActuatorTest.exceedMakerBuyOrderNumLimit`, which reproduces the exact cap check with 100 dust-sized orders from a single account) [2](#0-1) .
3. Any other user attempting to place a sell order on the same `(T, TRX)` pair now receives `ContractValidateException("Maximum number of orders exceeded，100")` and cannot place new orders on that pair.
4. The pair remains DoS'd until the attacker voluntarily cancels their 100 orders via `MarketCancelOrder`, which they have no incentive to do.

**Note on completeness**: due to the limited number of iterations available, I was not able to fully read the entirety of `MarketSellAssetActuator.validate()` to confirm the exact code path checking `MAX_ACTIVE_ORDER_NUM` against the pair's order count (only the constant declaration and the confirming unit test were retrieved). The test `exceedMakerBuyOrderNumLimit` strongly corroborates the described behavior, but reviewing the full `validate()` method directly would be needed to state the precise line range of the cap check.

  @Test
  public void exceedMakerBuyOrderNumLimit() throws Exception {

    InitAsset();

    //(sell id_1  and buy id_2)
    String sellTokenId = TOKEN_ID_ONE;
    long sellTokenQuant = 100L;
    String buyTokenId = TOKEN_ID_TWO;
    long buyTokenQuant = 200L;

    long orderNum = 100L;

    byte[] ownerAddress = ByteArray.fromHexString(OWNER_ADDRESS_FIRST);
    AccountCapsule accountCapsule = dbManager.getAccountStore().get(ownerAddress);
    accountCapsule.addAssetAmountV2(sellTokenId.getBytes(), sellTokenQuant * orderNum,
        dbManager.getDynamicPropertiesStore(), dbManager.getAssetIssueStore());
    dbManager.getAccountStore().put(ownerAddress, accountCapsule);
    Assert.assertEquals(sellTokenQuant * orderNum,
        (long) accountCapsule.getAssetV2MapForTest().get(sellTokenId));

    // Initialize the order book

    //add three order(sell id_2 and buy id_1) with different price by the same account
    //TOKEN_ID_TWO is twice as expensive as TOKEN_ID_ONE
    for (int i = 0; i < orderNum; i++) {
      addOrder(TOKEN_ID_ONE, sellTokenQuant, TOKEN_ID_TWO,
          buyTokenQuant, OWNER_ADDRESS_FIRST);
    }

    // do process
    MarketSellAssetActuator actuator = new MarketSellAssetActuator();
    actuator.setChainBaseManager(dbManager.getChainBaseManager()).setAny(getContract(
        OWNER_ADDRESS_FIRST, sellTokenId, sellTokenQuant, buyTokenId, buyTokenQuant));

    String errorMessage = "Maximum number of orders exceeded，100";
    try {
      actuator.validate();
      fail(errorMessage);
    } catch (ContractValidateException e) {
      Assert.assertEquals(errorMessage, e.getMessage());
    }
  }
