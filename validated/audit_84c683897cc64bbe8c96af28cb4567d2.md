### Title
Legacy per-cycle vote-reward computation can exceed block/CPU limits, permanently freezing withdrawable rewards - ([File: chainbase/src/main/java/org/tron/core/service/MortgageService.java])

### Summary
`MortgageService.computeReward()` / `getOldReward()` recomputes historical witness-vote rewards by iterating **once per unclaimed cycle** (rather than using a O(1) delta computed from a cumulative index) whenever the governance flag `allowOldRewardOpt` is disabled. Any account (voter or witness) that lets `beginCycle` fall far behind `currentCycle` before it ever withdraws will force this actuator to loop over every intervening cycle — the same "unbounded loop scaling with unclaimed history" pattern described in the Sherlock report for `SdtStakingPositionService.claimCvgSdtRewards()`.

### Finding Description
`withdrawReward()` / `queryReward()` in `MortgageService` compute the reward for the gap between `beginCycle` and `endCycle` via: [1](#0-0) 

Inside `computeReward(beginCycle, endCycle, accountCapsule)`, cycles below `newRewardAlgorithmEffectiveCycle` are routed to the legacy `getOldReward` path: [2](#0-1) 

`getOldReward` falls back to a per-cycle loop unless the committee-controlled `allowOldRewardOpt` flag is enabled: [3](#0-2) 

Each iteration of that loop calls `computeReward(cycle, votes)`, which itself iterates over every SR address the account voted for and performs a `DelegationStore` DB read (`getReward`, `getWitnessVote`) per vote per cycle: [4](#0-3) 

This is reachable directly from an unprivileged, signed `WithdrawBalanceContract` transaction: [5](#0-4) 

The number of loop iterations is `min(endCycle, newRewardAlgorithmEffectiveCycle) - beginCycle`, i.e. proportional to how long the caller has waited before withdrawing/re-voting, multiplied by the number of SRs voted for — exactly the same growth pattern (`unclaimed_periods * per_period_cost`) flagged in the external report as causing block-gas-limit exhaustion. The repo's own benchmark test acknowledges the performance cliff of the old algorithm relative to the new VI-based one: [6](#0-5) 

### Impact Explanation
If `allowOldRewardOpt` has not been enabled by committee proposal (it is a governable/optional parameter, not hard-coded on), any voter/witness who accumulates a large gap between `beginCycle` and `newRewardAlgorithmEffectiveCycle` (e.g. inactive since genesis, or one that keeps voting for many SRs each cycle without ever calling `WithdrawBalanceContract`) will need `energy`/CPU proportional to the unclaimed cycle count times the number of votes when they finally try to withdraw. Once this exceeds the block's execution-time/energy budget, the transaction can never complete in a single block, permanently freezing that account's `allowance` (unbacked/undelegated reward balance) — a **permanent freezing of funds** condition matching the report's impact category.

### Likelihood Explanation
Likelihood is data/configuration dependent: the loop range is capped at `newRewardAlgorithmEffectiveCycle`, a fixed historical cutoff, so the maximum possible number of iterations is bounded and finite rather than growing indefinitely over the life of the chain (unlike the original Sherlock report, where the unclaimed window is unbounded and keeps growing). Exploitability further depends on whether `allowOldRewardOpt` has already been enabled on the target network (if enabled, the O(1) VI-based `RewardViCalService` path is used instead and this issue does not manifest). I was not able to fully confirm from the indexed code whether `allowOldRewardOpt` is enabled by default in mainnet configuration, since `common/src/main/resources/reference.conf` and `DynamicPropertiesStore`'s default-value logic for this flag were not fully retrievable within the indexing limits — this should be verified in a full checkout.

### Recommendation
- Ensure `allowOldRewardOpt` (and thus the cached `RewardViCalService`/VI-based O(1) reward computation) is unconditionally enabled for all cycles, removing the legacy per-cycle `getOldReward` fallback entirely, or
- Add a bound/paging mechanism so `withdrawReward`/`queryReward` can process a capped number of cycles per transaction, allowing users with a large unclaimed backlog to withdraw incrementally across multiple transactions instead of requiring a single all-or-nothing computation.

### Proof of Concept
Conceptual steps to reproduce, given `allowOldRewardOpt` disabled:
1. Create an account, vote for the maximum allowed number of SR addresses (e.g. up to 27), then never call `WithdrawBalanceContract`, letting many maintenance cycles elapse.
2. Have this repeat while `currentCycle` grows to be `newRewardAlgorithmEffectiveCycle - N` for large `N` (thousands of cycles).
3. Broadcast a `WithdrawBalanceContract` transaction for this account. `MortgageService.withdrawReward()` → `computeReward()` → `getOldReward()` executes `N * votesCount` DB reads and arithmetic operations in a single actuator execution, matching the growth demonstrated by the repository's own `testRewardAlgorithmBenchmark` in `VoteTest.java` (lines 774-824), which measures the cost blow-up of the old per-cycle algorithm versus the new VI-based one across 73,000 cycles.
4. If the resulting execution time/energy exceeds the block production time limit or the account's energy limit, the withdraw transaction cannot succeed, permanently freezing the account's `allowance`.

  private long computeReward(long cycle, List<Pair<byte[], Long>> votes) {
    long reward = 0;
    for (Pair<byte[], Long> vote : votes) {
      byte[] srAddress = vote.getKey();
      long totalReward = delegationStore.getReward(cycle, srAddress);
      if (totalReward <= 0) {
        continue;
      }
      long totalVote = delegationStore.getWitnessVote(cycle, srAddress);
      if (totalVote == DelegationStore.REMARK || totalVote == 0) {
        continue;
      }
      long userVote = vote.getValue();
      double voteRate = (double) userVote / totalVote;
      reward += voteRate * totalReward;
    }
    return reward;
  }

  private long computeReward(long beginCycle, long endCycle, AccountCapsule accountCapsule) {
    if (beginCycle >= endCycle) {
      return 0;
    }

    long reward = 0;
    long newAlgorithmCycle = dynamicPropertiesStore.getNewRewardAlgorithmEffectiveCycle();
    List<Pair<byte[], Long>> srAddresses = accountCapsule.getVotesList().stream()
        .map(vote -> new Pair<>(vote.getVoteAddress().toByteArray(), vote.getVoteCount()))
        .collect(Collectors.toList());
    if (beginCycle < newAlgorithmCycle) {
      long oldEndCycle = min(endCycle, newAlgorithmCycle,
          dynamicPropertiesStore.disableJavaLangMath());
      reward = getOldReward(beginCycle, oldEndCycle, srAddresses);
      beginCycle = oldEndCycle;
    }
    if (beginCycle < endCycle) {
      for (Pair<byte[], Long>  vote : srAddresses) {
        byte[] srAddress = vote.getKey();
        BigInteger beginVi = delegationStore.getWitnessVi(beginCycle - 1, srAddress);
        BigInteger endVi = delegationStore.getWitnessVi(endCycle - 1, srAddress);
        BigInteger deltaVi = endVi.subtract(beginVi);
        if (deltaVi.signum() <= 0) {
          continue;
        }
        long userVote = vote.getValue();
        reward += deltaVi.multiply(BigInteger.valueOf(userVote))
            .divide(DelegationStore.DECIMAL_OF_VI_REWARD).longValue();
      }
    }
    return reward;
  }

  private long getOldReward(long begin, long end, List<Pair<byte[], Long>> votes) {
    if (dynamicPropertiesStore.allowOldRewardOpt()) {
      return rewardViCalService.getNewRewardAlgorithmReward(begin, end, votes);
    }
    long reward = 0;
    for (long cycle = begin; cycle < end; cycle++) {
      reward += computeReward(cycle, votes);
    }
    return reward;
  }
