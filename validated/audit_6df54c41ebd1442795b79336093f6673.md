## Finding

### Title
Unbounded iteration over the entire `VotesStore` during consensus maintenance causes DOS risk on block application - (`consensus/src/main/java/org/tron/consensus/dpos/MaintenanceManager.java`)

### Summary
`MaintenanceManager.doMaintenance()` calls `countVote()`, which does a **full linear scan and per-entry delete of the entire `VotesStore`** every maintenance cycle. `VotesStore` grows by one entry per distinct account that ever casts a `VoteWitnessContract`, and nothing bounds the number of distinct voting accounts an attacker can create. This is directly analogous to the reported Hubble issue: an unbounded, attacker-influenced collection is iterated inside a periodic, mandatory piece of block-application logic that every full node must execute deterministically, risking exceeding the per-block processing budget.

### Finding Description
`VoteWitnessActuator.countVoteAccount()` creates exactly one new `VotesCapsule` entry per unique owner address the first time that address votes: [1](#0-0) 

Any account that holds even a small amount of frozen TRX (TRON Power) can call `VoteWitnessContract`. There is no cap on the number of distinct addresses that can vote, and only a cap on the number of candidates a single vote can target (`MAX_VOTE_NUMBER`): [2](#0-1) 

At every maintenance boundary, `MaintenanceManager.doMaintenance()` invokes `countVote(votesStore)`, which iterates **every** entry currently in `VotesStore` via a raw DB iterator, and deletes each entry as it goes: [3](#0-2) 

This call is unconditional and happens inside `doMaintenance()`: [4](#0-3) 

`doMaintenance()` in turn is invoked from `MaintenanceManager.applyBlock()` whenever the maintenance time boundary is crossed: [5](#0-4) 

And `MaintenanceManager.applyBlock()` executes deterministically as part of normal block processing on every full node/witness via `consensus.applyBlock(block)`, called from `Manager.processBlock()`: [6](#0-5) 

Because a `VoteWitnessContract` transaction is broadcastable by any unprivileged account (validated purely against the sender's own account/TRON Power, no admin permission required), an attacker can:
1. Create a large number of accounts (cheap `AccountCreateContract` fee).
2. Freeze a minimal amount of TRX per account to obtain non-zero TRON Power.
3. Submit one `VoteWitnessContract` transaction per account.

Each such transaction inserts one persistent entry into `VotesStore` that is never removed until the next maintenance cycle. As the attacker keeps repeating this before each maintenance window, `VotesStore` size (and thus the cost of the mandatory `countVote()` full-table scan+delete) grows roughly linearly with attacker spend and is entirely unbounded by protocol logic.

### Impact Explanation
`countVote()` runs synchronously inside block application on **every node** (since `consensus.applyBlock()`/`doMaintenance()` must produce identical deterministic state across the network). If `VotesStore` is inflated to a very large size, the maintenance-boundary block's processing time balloons for all nodes simultaneously, which can:
- Cause block-production/validation to miss the fixed block interval, leading to missed blocks or validation timeouts (`BadBlockException`/schedule violations),
- Degrade or halt normal chain progress network-wide at every maintenance boundary (this happens repeatedly, once per maintenance interval, not just once),
- Create a persistent, recurring network-wide DOS surface, since the bloated `VotesStore` is not naturally garbage collected except by fully re-scanning/deleting it in this same expensive loop.

This matches the "node crash or halt / chain split" impact bar, since it can desynchronize nodes that fail to keep up with block timing at maintenance boundaries.

### Likelihood Explanation
The attack path requires only ordinary, permissionless transactions (`AccountCreateContract`, `FreezeBalanceV2Contract`/freeze, `VoteWitnessContract`) — no special privileges, no malicious SR/witness/node role, and no p2p exploitation. The cost scales with the number of accounts an attacker is willing to fund (account creation fee + minimal freeze amount), making it an economic-cost DOS rather than a free one, but the cost per malicious "state-bloat unit" (one `VotesStore` entry) is small and there is no protocol-level cap preventing it.

### Recommendation
- Bound `VotesStore` growth, e.g. by requiring a minimum TRON Power/stake threshold to create a persistent vote entry, or by charging an ongoing/decaying fee for maintaining a vote record.
- Refactor `countVote()` to process votes incrementally (e.g., maintain a running vote-delta index keyed by witness rather than scanning/deleting the entire `VotesStore` every cycle), so maintenance cost does not scale with the total historical number of distinct voters.
- Add a cap on the number of entries processed per maintenance cycle, deferring excess processing to subsequent cycles, to keep per-block processing time bounded.

### Proof of Concept
1. Fund an attacker-controlled wallet with enough TRX to repeatedly pay `CREATE_ACCOUNT_FEE`.
2. Script the creation of N new accounts (N large, e.g. hundreds of thousands), each freezing a minimal amount of TRX via `FreezeBalanceV2Contract` to obtain non-zero TRON Power.
3. From each new account, submit one `VoteWitnessContract` transaction (validated purely by `VoteWitnessActuator.validate()` against the sender's own balance/power, no special permission needed) — see [7](#0-6) .
4. Each transaction inserts a new key into `VotesStore` as shown in `countVoteAccount()`.
5. Observe that at the next maintenance boundary, `MaintenanceManager.doMaintenance()` → `countVote()` must scan and delete every one of these N entries synchronously inside `Manager.processBlock()`, increasing the wall-clock time of that specific block's processing on every node proportionally to N.

  private Map<ByteString, Long> countVote(VotesStore votesStore) {
    final Map<ByteString, Long> countWitness = Maps.newHashMap();
    Iterator<Entry<byte[], VotesCapsule>> dbIterator = votesStore.iterator();
    long sizeCount = 0;
    while (dbIterator.hasNext()) {
      Entry<byte[], VotesCapsule> next = dbIterator.next();
      VotesCapsule votes = next.getValue();
      votes.getOldVotes().forEach(vote -> {
        ByteString voteAddress = vote.getVoteAddress();
        long voteCount = vote.getVoteCount();
        if (countWitness.containsKey(voteAddress)) {
          countWitness.put(voteAddress, countWitness.get(voteAddress) - voteCount);
        } else {
          countWitness.put(voteAddress, -voteCount);
        }
      });
      votes.getNewVotes().forEach(vote -> {
        ByteString voteAddress = vote.getVoteAddress();
        long voteCount = vote.getVoteCount();
        if (countWitness.containsKey(voteAddress)) {
          countWitness.put(voteAddress, countWitness.get(voteAddress) + voteCount);
        } else {
          countWitness.put(voteAddress, voteCount);
        }
      });
      sizeCount++;
      votesStore.delete(next.getKey());
    }
    logger.info("There is {} new votes in this epoch", sizeCount);
    return countWitness;
  }
