### Title
Replay-window check/commit split allows message replay bypass in `ConnectionState.Decrypt`/`VerifyRelay` - (File: connection_state.go)

### Summary
`ConnectionState.Decrypt` and `ConnectionState.VerifyRelay` split the anti-replay logic into two separately-locked steps around an unlocked AEAD decrypt: `window.Check` (verify not-yet-seen) is locked and released, then `dKey.DecryptDanger` runs with no lock held, and only afterward is `window.Update` (commit as seen) locked and released.

### Finding Description
`Decrypt` performs:
1. Lock `decryptLock`, call `cs.window.Check(l, messageCounter)`, unlock.
2. If `Check` passed, call `cs.dKey.DecryptDanger(...)` with **no lock held**.
3. Lock `decryptLock` again, call `cs.window.Update(l, messageCounter)`, unlock. [3](#0-2) 

`VerifyRelay` follows the identical pattern for relay frames [4](#0-3) .

This mirrors the report's bug class exactly: the "reserve check" (`Check`) is evaluated against state that does not yet reflect an in-flight "pending" consumption (the decrypt-in-progress message counter), and the "commit" (`Update`) that would actually mark the counter as consumed happens only after the expensive/slow operation completes. Because nebula's `Interface.activate`/`run` intentionally launches multiple independent reader goroutines (`f.routines`, backed by `SO_REUSEPORT` sockets) that each call `readOutsidePackets` and thus `ConnectionState.Decrypt` concurrently [5](#0-4) , two copies of the *same* captured ciphertext (same `messageCounter`) can be delivered to two different reader queues in parallel (e.g., by varying only the UDP source port an attacker controls, which the kernel uses to select the `SO_REUSEPORT` socket, without altering the inner Nebula payload/nonce at all). Both copies can pass step 1 (`Check`) before either performs step 3 (`Update`), so both successfully decrypt via `dKey.DecryptDanger`, i.e., the replay-window ("remaining budget") is bypassed and the message is accepted twice, with only one of the two racing `Update` calls failing after the fact — too late to prevent the duplicate decryption/delivery.

### Impact Explanation
This defeats Nebula's anti-replay protection for the data plane and for relay frames, which is a core security property. A remote attacker with no CA-signed certificate who can observe/capture one legitimate on-the-wire packet (already possible for any UDP-visible party) can force reprocessing/replay of that exact message by racing it across reader queues, resulting in duplicate delivery of tunnel traffic to the destination `tun` device or duplicate relay forwarding — a concrete "traffic replay" bypass matching the accepted impact categories (`e2e/tunnels_test.go`'s `TestRelayReplayProtection` explicitly documents that replay protection on relay frames was previously broken for a related reason: the window wasn't advanced at all [6](#0-5) , showing this exact subsystem is a known target for replay-bypass regressions).

### Likelihood Explanation
Requires the interface to run with more than one queue (`f.routines > 1`, a supported and commonly enabled configuration on Linux/multiqueue platforms) and requires winning a narrow race window between `Check` and `Update` across two reader goroutines. This is a genuine race condition, not a deterministic bypass, so likelihood is moderate rather than certain — but it is entirely triggerable by an unauthenticated network observer replaying captured ciphertext, with no valid certificate or private key needed.

### Recommendation
Hold `decryptLock` for the entire duration of `Check` → `DecryptDanger` → `Update` for a given `messageCounter`, or otherwise treat "passed Check" as provisionally reserved (e.g., insert a placeholder into the window bitmap before decrypting and roll it back on decrypt failure) so that no second goroutine can observe an un-committed slot as available. This exactly mirrors the recommended fix pattern in the original report: account for the in-flight/pending state before allowing the check to pass, not after.

### Proof of Concept
1. Configure a nebula node with `f.routines` ≥ 2 (multiqueue-capable OS + `SupportsMultipleReaders`).
2. Capture one legitimate UDP packet destined for that node's tunnel.
3. Simultaneously send two copies of the identical byte-for-byte payload from two different local UDP source ports, timed so the OS's `SO_REUSEPORT` hash routes them to two different reader queues (`listenOut` goroutines) at effectively the same time.
4. Both goroutines call `readOutsidePackets` → `ConnectionState.Decrypt(f.l, h.MessageCounter, ...)` concurrently; both can pass `cs.window.Check` before either calls `cs.window.Update`, so both successfully call `cs.dKey.DecryptDanger` and the message is delivered/forwarded twice despite the replay window (analogous to `TestRelayReplayProtection`'s scenario, but exploiting the Check/Update race rather than a missing `Update` call entirely) [3](#0-2) .

func (cs *ConnectionState) VerifyRelay(l *slog.Logger, messageCounter uint64, packet []byte, nb []byte) error {

	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()

	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	return nil
}
