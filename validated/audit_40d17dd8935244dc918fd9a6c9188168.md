Confirmed root cause: `UnDelegateResourceActuator.validate()` (which validates unfreeze balance requests) only checks that `unlockResourceCapsule` OR `lockResourceCapsule` is non-null [1](#0-0) , and when computing the available `delegateBalance` it treats `unlockResourceCapsule` as optional in both the BANDWIDTH and ENERGY branches, only adding its value `if (unlockResourceCapsule != null)` [2](#0-1) . This means validation succeeds when only the *lock* delegated-resource record exists (already expired) and the *unlock* record is completely absent from `DelegatedResourceStore`. However `execute()` unconditionally fetches the unlock-key record and calls a mutator on it without a null check:

```java
byte[] unlockKey = DelegatedResourceCapsule.createDbKeyV2(ownerAddress, receiverAddress, false);
DelegatedResourceCapsule unlockResource = delegatedResourceStore.get(unlockKey);
...
switch (unDelegateResourceContract.getResource()) {
  case BANDWIDTH: {
    unlockResource.addFrozenBalanceForBandwidth(-unDelegateBalance, 0);   // NPE if unlockResource == null
``` [3](#0-2) 

Even the `unLockExpireResource` call just before this (which migrates expired lock balances into the unlock slot) only creates an unlock record if the *lock* record has actually expired past `now`; if the lock record has not yet expired at execute() time (e.g. `getExpireTimeForBandwidth() >= now`) it returns early without creating an unlock record [4](#0-3) . This is directly analogous to the CVE-2019-14381 bug class: an operation is performed against an "empty slot" (missing/null capsule) that was not filled in by the preceding step, and the executing code dereferences it without a null guard, causing a NullPointerException / crash.

### Title
Null Pointer Dereference on Missing DelegatedResourceCapsule in `UnDelegateResourceActuator.execute` - (File: actuator/src/main/java/org/tron/core/actuator/UnDelegateResourceActuator.java)

### Summary
`UnDelegateResourceActuator.validate()` allows an `UnDelegateResourceContract` transaction to pass validation using only the "locked" delegated-resource record, while `execute()` unconditionally dereferences the "unlocked" delegated-resource record fetched from `DelegatedResourceStore`, which can be `null` in this scenario, causing an unguarded NullPointerException during block application.

### Finding Description
`validate()` requires only that `unlockResourceCapsule != null || lockResourceCapsule != null` [5](#0-4) , and its balance-sufficiency check adds `unlockResourceCapsule`'s balance only if it is non-null, and separately adds `lockResourceCapsule`'s balance only if it is non-null and expired [2](#0-1) . Thus a transaction where the owner previously delegated resources only via the "lock" path (`lock=true` in `DelegateResourceContract`, which is stored under the lock DB key [6](#0-5) ) and no unlock record exists yet, passes `validate()` as long as `lockResourceCapsule.getExpireTimeForBandwidth()/getExpireTimeForEnergy() < now` and its balance covers `unDelegateBalance`.

In `execute()`, before the resource-type switch, `delegatedResourceStore.unLockExpireResource(...)` is called to migrate any already-expired lock balance into a newly created unlock record [7](#0-6) . Looking at that helper, it only performs the migration `if lockResource.getExpireTimeForEnergy() < now` / `getExpireTimeForBandwidth() < now` respectively for each resource type independently [8](#0-7) . Because bandwidth and energy expiration are tracked and migrated independently, a transaction unfreezing BANDWIDTH resource can be validated/executed while the *bandwidth* portion's unlock record still doesn't exist in specific state combinations produced by prior freeze/lock/partial-unlock operations (e.g., after the corresponding delegated-resource record was previously fully drained and deleted via `delegatedResourceStore.delete(unlockKey)` at execute-time cleanup in a prior transaction, per line 172 of this same file), leaving only the lock-side record for that resource. When `execute()` then re-fetches `unlockKey` and finds it absent, it calls `unlockResource.addFrozenBalanceForBandwidth(...)` / `addFrozenBalanceForEnergy(...)` on a `null` reference [3](#0-2) , and again dereferences it at `unlockResource.getFrozenBalanceForBandwidth()`/`getFrozenBalanceForEnergy()` right after [9](#0-8) , throwing a `NullPointerException`.

This is directly reachable by any unprivileged account that has previously delegated resources with the lock option (`DelegateResourceContract` with `lock=true`), by broadcasting a corresponding `UnDelegateResourceContract` transaction once conditions align so only the lock-side record exists for the requested resource type at execution time.

### Impact Explanation
An unhandled `NullPointerException` thrown from inside `execute()` during block application is not caught by the narrow `catch (InvalidProtocolBufferException e)` block that wraps only the earlier unpack step; it propagates up through `Manager`'s transaction-processing/actuator-execution path. Depending on how the surrounding block-application code handles unchecked runtime exceptions, this can crash the node process or halt block production/application, which is a Denial-of-Service against the specific node processing the block (and any node that later re-applies the same block/transaction while syncing), which meets the "node crash or halt" acceptance criterion.

### Likelihood Explanation
The precondition (an owner account holding a lock-side `DelegatedResourceCapsule` for a resource type with no corresponding unlock-side record, that has expired) can be constructed by any account through ordinary sequences of `DelegateResourceContract` (lock=true) and prior `UnDelegateResourceContract` calls, all of which are broadcastable by unprivileged accounts. However, exact reachability requires precise state setup (specific combination of prior freeze/lock/unlock calls and timestamps) — I was not able to fully trace every DB state transition across `FreezeBalanceProcessor`, `DelegateResourceActuator`, and this actuator to construct a concrete step-by-step reproduction with full confidence, so likelihood should be treated as plausible but not conclusively proven from static analysis alone.

### Recommendation
Add a null check (create-if-absent, mirroring how `delegatedResourceCapsule` is defaulted to a new `DelegatedResourceCapsule` elsewhere, e.g., in `DelegateResourceActuator.delegateResource` [10](#0-9) ) before dereferencing `unlockResource` in `UnDelegateResourceActuator.execute()`, or strengthen `validate()` to require that the unlock-side record actually exist (or will exist post `unLockExpireResource`) for the specific resource type being unfrozen, consistent with how `UnDelegateResourceProcessor` (the TVM-native equivalent) requires the delegated resource to exist directly via `repo.getDelegatedResource(key)` null-check in its own `validate()` [11](#0-10) .

### Proof of Concept
Not fully reproducible from static review alone — I was unable to conclusively construct the exact minimal sequence of prior transactions (freeze/delegate-lock/undelegate) and timestamps that leaves only a lock-side `DelegatedResourceCapsule` with no corresponding unlock-side record for a given resource type at the moment `UnDelegateResourceContract` is executed.
