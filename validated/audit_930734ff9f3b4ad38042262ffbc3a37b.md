### Title
Cross-StackerDB replay of signed chunks due to missing contract binding in the chunk-authentication digest - (File: `libstackerdb/src/libstackerdb.rs`)

### Summary
`SlotMetadata::auth_digest()` — the digest that is signed and verified for every StackerDB chunk — commits only to `slot_id`, `slot_version`, and `data_hash`. It never commits to the target smart contract (`QualifiedContractIdentifier`) that the chunk is being written to. Because the same signer key is frequently assigned the same `slot_id` across multiple StackerDB replicas belonging to the same signer set, an unprivileged network relayer can replay a validly-signed chunk from one StackerDB contract into a different StackerDB contract, and it will pass signature verification and be stored/gossiped as authentic.

### Finding Description
`SlotMetadata::sign`/`verify` compute the authenticated digest as: [1](#0-0) 

and verification only checks that this digest was signed by the expected principal for that `(contract, slot_id)`: [2](#0-1) 

Both write paths — the local `try_replace_chunk` and the network-facing `validate_received_chunk` — look up the expected signer *per contract*, but then verify a digest that says nothing about which contract it belongs to: [3](#0-2) [4](#0-3) 

The equality that should hold is: *"a chunk accepted for slot `X` in contract `C` was signed by the authorized signer specifically authorizing `(C, X, version, hash)`."* What is actually checked is only `(X, version, hash)` — the contract identity is dropped from the signed material. Slot-to-signer assignment is derived once per reward cycle from the same reward/signer set and pushed into the `.signers` contract via `stackerdb-set-signer-slots`, using the same per-signer `StacksAddress` ordering for every StackerDB replica of that cycle: [5](#0-4) 

This means the same signer key legitimately owns the same `slot_id` across multiple distinct StackerDB contracts (e.g. sibling replicas for the same reward cycle). An attacker who observes (or is one of the many unprivileged peers that relay) a legitimately-signed `StackerDBChunkData` for contract `A`/slot `k`/version `v` can resubmit that exact same message, unmodified, as a `StackerDBPushChunk` targeting contract `B`. `handle_unsolicited_StackerDBPushChunk` resolves the config/signer purely from `contract_id` in the message and then calls `validate_received_chunk`, which will accept it because the signature check only re-derives `(slot_id, slot_version, data_hash)`, all of which match: [6](#0-5) 

If contract `B`'s stored version for that slot is lower than `v`, the replayed (out-of-context) chunk is accepted, stored, and gossiped to the rest of the network via the chunk-inventory update path, exactly as if it were legitimate data for contract `B`.

### Impact Explanation
This is a forged-data propagation vulnerability: content that was never authored for a given StackerDB replica is written into it and relayed network-wide as authentic, because the authentication scheme fails to bind the signature to the destination contract. This matches the "network-wide propagation of forged data" Critical-impact category — any unprivileged network peer that can observe or relay one legitimately-signed chunk can inject it as valid data into a sibling replica, corrupting consensus-adjacent signer-message state (e.g., block proposals/responses) without holding any signer's private key or any special role.

### Likelihood Explanation
Likelihood is high for the mechanics (no special access needed — just replaying an already-observed valid message to a different contract endpoint) but depends on the specific deployment: it requires the target contract to expect the same signer at the same slot index and to currently hold a lower/no stored version for that slot. Given that signer slot assignment is derived once per reward cycle and reused across all `.signers-*` sibling contracts for that cycle, this precondition is commonly satisfied in production topology.

### Recommendation
Include the destination `QualifiedContractIdentifier` (or equivalently a domain-separation tag identifying the StackerDB) in `SlotMetadata::auth_digest()`, so that a signature is only valid for the specific `(contract, slot_id, slot_version, data_hash)` tuple it was created for. This requires a protocol/version bump since it changes the signed payload format; both `sign` and `verify` in `libstackerdb/src/libstackerdb.rs`, and all callers in `stackslib/src/net/stackerdb/db.rs` and `stackslib/src/net/stackerdb/mod.rs`, must be updated to pass and check the contract identifier as part of the digest.

### Proof of Concept
1. Reward cycle `N` initializes two StackerDB replicas sharing the same signer set/slot assignment, e.g. contract `A` (`.signers-N-0`) and contract `B` (`.signers-N-1`), both giving signer key `K` slot `5`.
2. Signer `K` legitimately signs and pushes chunk `{slot_id: 5, slot_version: 3, data_hash: H}` to contract `A`. A relaying peer observes this valid `StackerDBPushChunkData` message.
3. The relaying peer (no signer key required) resends the identical `sig`/`slot_id`/`slot_version`/`data` payload but with `contract_id` set to `B` via `StackerDBPushChunkData`.
4. `handle_unsolicited_StackerDBPushChunk` → `validate_received_chunk` looks up the expected signer for `(B, 5)` — which is also `K` — and verifies `slot_metadata.verify(&addr)` using `auth_digest()` that only covers `(5, 3, H)`; verification succeeds because it never checked contract `B` vs `A`.
5. If `B`'s currently stored version for slot 5 is `< 3`, the chunk (originally authored for `A`) is accepted and stored under `B`, then relayed to the rest of the network as if it were genuine data for `B`.

    /// Get the digest to sign that authenticates this chunk data and metadata
    fn auth_digest(&self) -> Sha512Trunc256Sum {
        let mut hasher = Sha512_256::new();
        hasher.update(self.slot_id.to_be_bytes());
        hasher.update(self.slot_version.to_be_bytes());
        hasher.update(self.data_hash.0);
        Sha512Trunc256Sum::from_hasher(hasher)
    }

    /// Note that the address version is ignored.
    pub fn verify(&self, principal: &StacksAddress) -> Result<bool, Error> {
        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )
        .map_err(|ve| Error::VerifyingError(ve.to_string()))?;

        let pubkh = Hash160::from_node_public_key(&pubk);
        Ok(pubkh == *principal.bytes())
    }
