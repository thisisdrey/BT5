Based on my investigation, I found a discrepancy in the JSON-RPC transaction receipt status calculation that is analogous to the Vegas Town "hard_fail" pattern: a client-facing API reports a transaction as *successful* even when the actual execution result was a failure.

### Title
JSON-RPC `eth_getTransactionReceipt` reports incorrect success status for non-DEFAULT/SUCCESS `contractResult` codes - ([File: framework/src/main/java/org/tron/core/services/jsonrpc/types/TransactionReceipt.java])

### Summary
`TransactionReceipt` derives the Ethereum-style `status` field from the raw ordinal value of the `contractResult` enum stored in the resource receipt, rather than from the actual `TransactionInfo.result` (SUCCESS/FAILED) code, potentially mis-reporting failed transactions as successful to any client that relies on `eth_getTransactionReceipt`.

### Finding Description
The `TransactionReceipt` constructor sets the Ethereum-compatible status field with: [1](#0-0) 

`this.status = txInfo.getReceipt().getResultValue() <= 1 ? "0x1" : "0x0";` treats any `contractResult` enum ordinal of `0` or `1` as success. This is fragile because it depends entirely on the exact numeric ordering of the `contractResult` protobuf enum (`DEFAULT`, `SUCCESS`, and then various failure codes such as `REVERT`, `OUT_OF_ENERGY`, `OUT_OF_TIME`, `TRANSFER_FAILED`, etc., as consumed in `RuntimeImpl.setResultCode`) [2](#0-1) . Any future reordering, insertion, or renumbering of this enum (e.g., adding a new failure code with ordinal `1`, or reordering `SUCCESS`/`DEFAULT`) silently flips the reported status for real transactions, without any code path failing loudly — this is exactly analogous to the EOS Vegas Town flaw where an external observer (the game backend) trusted an intermediate/derived success signal instead of validating the actual final execution outcome. This function is reachable purely via an unauthenticated JSON-RPC query (`eth_getTransactionReceipt`) exposed by `TronJsonRpcImpl.getTransactionReceipt` [3](#0-2) , which any anonymous API client can call for any transaction ID.

Separately, `TransactionInfo` already carries an explicit, purpose-built `result` code field (`SUCESS = 0`/`FAILED = 1`) intended exactly for this purpose [4](#0-3) , but `TransactionReceipt` does not use it — it derives status from the lower-level TVM `contractResult` ordinal instead of this authoritative field.

### Impact Explanation
Wallets, exchanges, and DApp backends that integrate against TRON's EVM-compatible JSON-RPC surface (many third-party services do, to reuse standard Ethereum tooling) rely on the `status` field of `eth_getTransactionReceipt` to decide whether a transaction (e.g., a token transfer, deposit, or contract call funding a game/exchange) actually succeeded. If the ordinal-based heuristic ever diverges from the true success/failure outcome — which can happen through legitimate future protobuf enum changes, since protobuf enum values are a supported extension point and no test enforces the invariant `SUCCESS == 1 && DEFAULT == 0 && all other results > 1` — a reverted/failed transaction (e.g., `REVERT`, `OUT_OF_ENERGY`) could be reported as `0x1` (success) via this API, or vice versa. Given the game/exchange industry pattern shown in the Vegas Town incident, an integrator trusting this status field to credit funds could be tricked into crediting for a transaction that never actually transferred value on-chain, or a legitimate transaction could be wrongly treated as failed, causing service disruption.

### Likelihood Explanation
This is a data-integrity/logic bug reachable by any unauthenticated JSON-RPC caller with no special privileges — simply query `eth_getTransactionReceipt` for any transaction hash. It doesn't require crafting a malicious transaction; it's a passive query bug. The risk materializes fully whenever the underlying `contractResult` enum ordinals do not strictly preserve the `<=1 ⇒ success` invariant, which is not enforced by any type or test in the code I found, making it a latent but concretely exploitable trust boundary violation for any integrator using ordinal semantics instead of the canonical `TransactionInfo.result` field.

### Recommendation
Change `TransactionReceipt` to derive `status` from the canonical `TransactionInfo.result` (`SUCESS`/`FAILED`) field, or explicitly compare against the named `contractResult.SUCCESS` (and treat only `SUCCESS`/`DEFAULT` as success by name, not by numeric threshold), and add a regression test asserting that every failing `contractResult` value (`REVERT`, `OUT_OF_ENERGY`, `OUT_OF_TIME`, `TRANSFER_FAILED`, etc.) yields `status = "0x0"`.

### Proof of Concept
1. Deploy/trigger a smart contract call that reverts (as in `EnergyWhenRequireStyleTest.revertTest`, which yields `result.isRevert() == true` and a non-SUCCESS `contractResult`) [5](#0-4) .
2. Query `eth_getTransactionReceipt` for that transaction hash via `TronJsonRpcImpl.getTransactionReceipt`.
3. Inspect the constructed `TransactionReceipt.status`; because it is computed only from `getResultValue() <= 1` rather than the authoritative FAILED/SUCCESS result code, verify whether the ordinal of the contract's failure/revert code could be `≤1` under any current or future enum arrangement — confirming the API's status field is not derived from a stable, semantically-checked source of truth.

**Note on confidence**: I was unable to directly inspect the numeric ordinal values assigned to each `contractResult` enum member in the `.proto` definition (the file appeared empty/truncated in the index), so I could not conclusively determine whether a *currently* mislabeled ordinal exists today, or if this is purely a latent maintainability/robustness bug. Given index size limits, some `.proto` file contents may not be fully available — I recommend starting a full Devin session to inspect `protocol/src/main/protos/core/Tron.proto` directly for the exact `contractResult` enum ordinal ordering to confirm present-day exploitability versus latent risk.

  private void setResultCode(ProgramResult result) {
    RuntimeException exception = result.getException();
    if (Objects.isNull(exception) && StringUtils
        .isEmpty(result.getRuntimeError()) && !result.isRevert()) {
      result.setResultCode(contractResult.SUCCESS);
      return;
    }
    if (result.isRevert()) {
      result.setResultCode(contractResult.REVERT);
      return;
    }

      return;

  public TransactionReceipt getTransactionReceipt(String txId)
      throws JsonRpcInvalidParamsException {
    TransactionInfo transactionInfo =
        wallet.getTransactionInfoById(ByteString.copyFrom(hashToByteArray(txId)));
    if (transactionInfo == null) {
      return null;
    }

    Block block = wallet.getBlockByNum(transactionInfo.getBlockNumber());
    if (block == null) {
      return null;
    }

    BlockCapsule blockCapsule = new BlockCapsule(block);
    long blockNum = blockCapsule.getNum();
    TransactionInfoList transactionInfoList = wallet.getTransactionInfoByBlockNum(blockNum);
    long energyFee = wallet.getEnergyFee(blockCapsule.getTimeStamp());

    // Find transaction context
    TransactionReceipt.TransactionContext context
        = findTransactionContext(transactionInfoList,
          transactionInfo.getId());

    if (context == null) {
      return null; // Transaction not found in block
    }

    return new TransactionReceipt(blockCapsule, transactionInfo, context, energyFee);
  }
