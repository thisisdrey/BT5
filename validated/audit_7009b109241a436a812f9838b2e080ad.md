### Title
Repair request replay amplification via missing nonce/replay-cache in `ServeRepair::verify_signed_packet` - ([File: core/src/repair/serve_repair.rs])

### Summary
`ServeRepair::verify_signed_packet` only validates recipient identity, a wall-clock timestamp window (`SIGNED_REPAIR_TIME_WINDOW` = 10 minutes), and the Ed25519 signature over the packet bytes; it performs no nonce or per-request replay-cache check. Combined with the fact that `check_ping_cache` grants a long-lived (`REPAIR_PING_CACHE_CAPACITY`/`REPAIR_PING_CACHE_TTL` = ~21 min) trust window per `(sender_pubkey, source_addr)` tuple, a single captured valid signed repair packet can be replayed unlimited times from a spoofed UDP source address matching an already-trusted sender for the full `SIGNED_REPAIR_TIME_WINDOW`, with each replay independently triggering `handle_repair` and a response.

### Finding Description
In `core/src/repair/serve_repair.rs`, `decode_request` calls `Self::verify_signed_packet(my_id, remote_request.buffer(), &request)` [1](#0-0) . `verify_signed_packet` checks only recipient match, a timestamp skew window, and the signature over the fixed header/body bytes — there is no nonce uniqueness check or replay cache: [2](#0-1) .

The nonce embedded in `RepairRequestHeader` is only used by the *requester* to correlate responses (`OutstandingRequests`/`OutstandingShredRepairs`) — the server side (`ServeRepair`) never records or checks it for uniqueness, so the exact same signed bytes decode and verify successfully every time they are resent within `SIGNED_REPAIR_TIME_WINDOW` (10 minutes) [3](#0-2) .

The only per-sender gating happens in `check_ping_cache`, which is keyed by `(sender pubkey, from_addr)` and, once a Pong challenge is answered, marks that tuple as trusted for `REPAIR_PING_CACHE_TTL` (1280s) without requiring further challenge-response for subsequent requests: [4](#0-3) [5](#0-4) . Since UDP allows arbitrary source-address spoofing at the application layer, and repair responses are addressed using `from_addr` taken straight from packet metadata, an attacker who intercepts one legitimate signed request from a genuinely-trusted validator can spoof that validator's source IP and resend the identical captured bytes many times; each replay bypasses the ping challenge (the `(sender, addr)` tuple is already cache-trusted) and passes `verify_signed_packet` because only wall-clock freshness — not nonce novelty — is enforced.

The remaining backstop is a single shared, per-node `TokenBucket` (`data_budget`, `MAX_BYTES_PER_SECOND = 12_000_000`) that limits total repair response bytes/sec globally, not per-sender or per-nonce [6](#0-5) [7](#0-6) . Thus replaying one captured packet at high rate can exhaust this shared budget, denying repair service to legitimate staked peers, while responses are reflected to the spoofed (real) address, producing bandwidth amplification against a third party.

### Impact Explanation
This is a repair-response amplification / denial-of-service: a single captured signed repair packet can be replayed indefinitely (bounded only by the 10-minute `SIGNED_REPAIR_TIME_WINDOW`, refreshable by re-capturing traffic) to (a) exhaust the node's shared 12 MB/s repair response bandwidth budget, denying repair service to legitimate validators, and (b) reflect amplified repair-shred responses toward a spoofed victim address. This falls under the DoS-via-network-amplification bounty category rather than requiring consensus/vote manipulation.

### Likelihood Explanation
Feasibility requires: (1) passive interception of one valid signed repair packet — feasible on any network path between validators or via a validator the attacker is peered with; (2) the ability to spoof the UDP source address as the original (trusted) sender, which is blocked by egress/ingress BCP38 filtering on many networks but is not universally enforced, especially on validator hosting providers; (3) the target's `check_ping_cache` entry for that `(sender, addr)` tuple must already be trusted (true for any actively-repairing pair of validators, refreshed roughly every `REPAIR_PING_CACHE_TTL` ~21 minutes). Given these are network/infrastructure preconditions rather than requiring stake or key compromise, likelihood is moderate and repeatable within each capture-and-replay window.

### Recommendation
Add a server-side replay-protection mechanism in `verify_signed_packet`/`decode_request`, e.g., an LRU/time-bounded cache keyed by `(sender, nonce)` or `(sender, signature)` that rejects previously-seen nonces/signatures within `SIGNED_REPAIR_TIME_WINDOW`, and/or shrink `SIGNED_REPAIR_TIME_WINDOW` and re-validate the ping-cache trust more frequently (e.g., re-challenge periodically instead of granting a long unconditional trust window), decoupling response bandwidth budget accounting from spoofable `from_addr`.

### Proof of Concept
Integration test plan (`core/src/repair/serve_repair.rs` test module):
1. Construct a valid signed `RepairProtocol::WindowIndex` packet from keypair `A` addressed to node `my_id`, and drive a `PingCache` state so `(A.pubkey(), addr)` is already trusted (simulate a completed ping/pong as in existing `check_ping_cache` tests).
2. Call `ServeRepair::decode_request` and `handle_requests` repeatedly (N times, e.g., 10,000) with the exact same captured packet bytes and `from_addr`, all within `SIGNED_REPAIR_TIME_WINDOW`.
3. Assert that `ServeRepairStats::processed` / `total_response_packets` grows linearly with N (i.e., every replay is served) instead of being capped by a nonce/replay cache — demonstrating no bound other than the wall-clock window and the shared bandwidth token bucket.
4. Expected (fixed) behavior: after adding a nonce/signature replay cache, `processed` should plateau at 1 for repeated identical packets within the window, with subsequent replays rejected via a new `RepairVerifyError::Replayed` (or similar) variant.
