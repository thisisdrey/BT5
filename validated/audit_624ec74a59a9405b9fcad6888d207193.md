### Title
QUIC per-IP connection rate limiter is bypassable via TOCTOU race between `is_allowed` and `register_connection` - ([File: streamer/src/nonblocking/connection_rate_limiter.rs])

### Finding Description
`ConnectionRateLimiter::is_allowed` and `ConnectionRateLimiter::register_connection` are two separate, non-atomic operations on the same underlying `KeyedRateLimiter<IpAddr>` token bucket: [1](#0-0) 

`is_allowed` only *peeks* at `current_tokens(ip)` without consuming anything, and returns `true` for any IP with remaining tokens (or an IP never seen before). The actual token consumption happens later in a completely separate call, `register_connection`, which calls `consume_tokens`. Because these are two independent calls rather than a single atomic check-and-consume operation, any number of concurrently spawned `setup_connection` tasks for the same source IP can each observe `is_allowed() == true` before any of them has called `register_connection()` to actually deduct a token. Each concurrent handshake task races through the check independently, so the serialization the limiter is meant to provide (one token consumed per accepted connection, gating subsequent connections) does not actually bound concurrent admissions — it only bounds the *rate at which tokens are consumed after the fact*, not the number of connections that can be inspected/admitted in the same instant.

This is a textbook time-of-check-to-time-of-use (TOCTOU) gap: the "check" (`is_allowed`) and "use" (`register_connection`) are decoupled across async tasks with no shared lock or single atomic operation covering both steps.

### Impact Explanation
This maps to the "QoS evasion" category referenced in the question: an unstaked attacker opening several QUIC connections back-to-back from a single source IP can have multiple `setup_connection` tasks all pass `is_allowed` before any of them calls `register_connection`, allowing a burst of accepted connections beyond the configured `max_connections_per_ipaddr_per_min` limit. This degrades the effectiveness of the per-IP unstaked connection throttle that is meant to prevent a single IP from monopolizing TPU connection slots.

### Likelihood Explanation
The race requires only that an unprivileged, unstaked attacker open two or more QUIC connections from the same IP back-to-back so their `setup_connection` tasks are scheduled concurrently on the tokio runtime before either completes `register_connection`. This is easily achievable — no special timing beyond ordinary concurrent connection establishment, no privileged access, and no cluster state manipulation needed — making it fully attacker-controllable and repeatable.

### Recommendation
Merge the check-and-consume into a single atomic operation, e.g. have `register_connection` alone perform the atomic `consume_tokens` call and use its boolean result as the sole admission decision (removing the separate advisory `is_allowed` pre-check from the accept-path critical section), or wrap the check-then-consume sequence in a per-IP lock/mutex so no two tasks can interleave between the peek and the consume for the same key.

### Proof of Concept
Integration test plan (`streamer/src/nonblocking/quic.rs` test harness using `setup_quic_server`):
1. Configure `max_connections_per_ipaddr_per_min` to a small burst value (e.g., 1) via server config.
2. From a single test process/IP, spawn N (e.g., 10) concurrent tasks each calling `make_client_endpoint` and completing a QUIC handshake against the server almost simultaneously (e.g., via `tokio::join!` or `futures::join_all` with no artificial delay).
3. Assert that the number of successfully accepted connections is bounded by the configured burst limit.
4. Expected (bug present): more than the configured limit of connections succeed, because multiple `setup_connection` tasks observe `is_allowed() == true` concurrently prior to any `register_connection` call.
5. Unit-level reproduction without networking: spawn multiple concurrent `tokio::spawn` tasks that all call `limiter.is_allowed(&ip)` before any calls `limiter.register_connection(&ip)` (using a barrier/channel to force the race window), and assert that the total number of tasks observing `is_allowed() == true` can exceed the token bucket's configured burst size.

    pub fn is_allowed(&self, ip: &IpAddr) -> bool {
        // Check if we have records in the rate limiter for the given IP address
        match self.limiter.current_tokens(ip) {
            Some(r) => r > 0, // we have a record, and rate is not exceeded
            None => true,     // if we have not seen IP, allow connection request
        }
    }

    pub fn register_connection(&self, ip: &IpAddr) -> bool {
        if self.limiter.consume_tokens(*ip, 1).is_ok() {
            debug!("Request from IP {ip:?} allowed");
            true // Request allowed
        } else {
            debug!("Request from IP {ip:?} blocked");
            false // Request blocked
        }
    }
