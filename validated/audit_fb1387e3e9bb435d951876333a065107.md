### Title
Division-before-multiplication in legacy per-cycle vote reward computation causes systematic reward underpayment - (File: chainbase/src/main/java/org/tron/core/service/MortgageService.java)

### Summary
`MortgageService.computeReward(long cycle, List<Pair<byte[], Long>> votes)` computes a voter's share of a standby-witness's total reward by first dividing `userVote` by `totalVote` as a `double`, then multiplying by `totalReward`, before truncating to a `long`. This is the same division-before-multiplication pattern as the reported `SolverVaults::requestWithdraw` bug: performing the division first truncates precision before the multiplication can restore it, causing systematic under-computation of the reward owed to delegators.

### Finding Description
In the legacy (pre "new reward algorithm") reward-computation path: [1](#0-0) 

```java
private long computeReward(long cycle, List<Pair<byte[], Long>> votes) {
  long reward = 0;
  for (Pair<byte[], Long> vote : votes) {
    ...
    long userVote = vote.getValue();
    double voteRate = (double) userVote / totalVote;   // division first
    reward += voteRate * totalReward;                  // multiplication second, then truncated to long
  }
  return reward;
}
```

This is invoked, cycle by cycle, from the legacy fallback path `getOldReward` when the "new reward algorithm" optimization is not active for the relevant cycle range: [2](#0-1) 

By contrast, the newer per-cycle reward computation path (`computeReward(long beginCycle, long endCycle, AccountCapsule accountCapsule)`) correctly performs the multiplication before the division using `BigInteger` arithmetic: [3](#0-2) 

```java
reward += deltaVi.multiply(BigInteger.valueOf(userVote))
    .divide(DelegationStore.DECIMAL_OF_VI_REWARD).longValue();
```

This shows the correct multiply-then-divide idiom is already known and used elsewhere in the same file, confirming that the legacy `computeReward(long cycle, ...)` path is the outlier vulnerable to the div-before-mul precision-loss class described in the external report. The identical logic and bug exist in the duplicated TVM-vote reward path `VoteRewardUtil`, but that class only implements the BigInteger-based (correct) computation and does not contain the vulnerable double-based per-cycle sum, so the vulnerable code is isolated to `MortgageService`.

### Impact Explanation
`computeReward(long cycle, votes)` is reached whenever an account withdraws or queries its delegation/vote reward and any part of its unclaimed cycle range falls before `getNewRewardAlgorithmEffectiveCycle()` and `allowOldRewardOpt()` is not enabled (`getOldReward` → per-cycle `computeReward`). This is triggered by ordinary, unprivileged account operations: `WithdrawBalanceActuator` (broadcastable `WithdrawBalanceContract`), `queryReward`, and the TVM vote-withdraw path. Because `voteRate = userVote/totalVote` is truncated as a double *before* being multiplied by `totalReward`, small vote shares (or the interaction of floating point rounding across many cycles/votes) systematically shave fractional TRX off each user's reward, which is silently lost rather than carried forward — a form of permanent (if usually small per-call) fund loss/underpayment affecting any delegator claiming rewards through this legacy code path.

### Likelihood Explanation
The bug is triggered deterministically any time a user calls a withdraw/query-reward operation whose cycle range still requires the legacy per-cycle computation (i.e., prior to the new reward algorithm's effective cycle for that account, or when `allowOldRewardOpt` is disabled). No special privileges or race conditions are needed — a single signed `WithdrawBalanceContract` transaction from any voting account is sufficient to realize the loss.

### Recommendation
Replace the double-based division-then-multiplication in `MortgageService.computeReward(long cycle, List<Pair<byte[], Long>> votes)` with an integer/`BigInteger` multiply-then-divide, mirroring the pattern already used in `computeReward(long beginCycle, long endCycle, AccountCapsule accountCapsule)`:

```java
long userVote = vote.getValue();
reward += BigInteger.valueOf(userVote)
    .multiply(BigInteger.valueOf(totalReward))
    .divide(BigInteger.valueOf(totalVote))
    .longValue();
```

This performs the multiplication first, preserving full precision until the final division, eliminating the systematic underpayment.

### Proof of Concept
Given `userVote = 1`, `totalVote = 3`, `totalReward = 2`:
- Current code: `voteRate = 1.0/3.0 = 0.333...`; `reward += 0.333... * 2 = 0.666...` truncated to `long` → `0`.
- Correct (multiply-first) computation: `1 * 2 / 3 = 0` as well in this trivial example, but for larger, less "nice" values (e.g., `userVote = 2`, `totalVote = 3`, `totalReward = 3`): current code gives `voteRate = 0.666...`; `0.666... * 3 = 1.9999...` → truncates to `1`, whereas multiply-first gives `2*3/3 = 2`, an exact and correct result — demonstrating the precision loss from the div-before-mul ordering, matching the pattern in the referenced `SolverVaults` finding. This loss accumulates per vote/witness/cycle for every legacy-path reward withdrawal, as shown by the existing repository test asserting on the same `double`-based formula: [4](#0-3)
