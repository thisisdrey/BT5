## Title
Unprivileged `TransferToGasKey` action lets anyone permanently brick a victim's gas key and block account deletion - ([File: runtime/runtime/src/access_keys.rs])

### Summary
`action_transfer_to_gas_key` credits an arbitrary caller's deposit into any account's gas key balance without checking that the sender is the account owner. Because deletion of a gas key (and of the whole account) is refused once a gas key's balance exceeds `GasKeyInfo::MAX_BALANCE_TO_BURN`, any unprivileged account can grief a victim by transferring a small amount to a victim's gas key, permanently blocking the victim's ability to delete that key or their account — the same "attacker calls a public state-mutating entrypoint with the victim's identifier and a token amount to lock the victim out of a withdrawal/removal action" pattern described in the St1inch report (frontrunning `depositFor`/`depositForWithPermit` with amount 0 to extend the victim's lock and block `withdraw`).

### Finding Description
`action_transfer_to_gas_key` only checks that `account_id` (the receipt's receiver) owns a gas key matching `action.public_key`; it never checks the receipt's predecessor (the actual sender/payer of the deposit) against the account owner: [1](#0-0) 

Because `TransferToGasKey` is a normal `Action` executed against the receiver account of a receipt, **any account** can send a receipt to the victim's account containing this action with an arbitrary `deposit`, paid from the attacker's own balance, as with an ordinary `Transfer`. This lets an attacker unilaterally increase `GasKeyInfo.balance` on a gas key it does not own.

That balance later gates two operations:
- `delete_gas_key` refuses to delete the key if `gas_key_info.balance > GasKeyInfo::MAX_BALANCE_TO_BURN`, returning `GasKeyBalanceTooHigh` and leaving the key intact: [2](#0-1) 
- `action_delete_account` sums all of an account's gas-key balances and refuses to delete the whole account if the sum exceeds the same threshold: [3](#0-2) 

`MAX_BALANCE_TO_BURN` is a small, fixed cap (documented as ~1 NEAR): "Gas-key deletion burns ≤ 1 NEAR: `delete_gas_key` errors `GasKeyBalanceTooHigh` and aborts if `balance > MAX_BALANCE_TO_BURN`" [4](#0-3) . An attacker only needs to push a single yoctoNEAR over that threshold on a victim's gas key to make the condition permanently unsatisfiable — the victim cannot lower the balance themselves (`WithdrawFromGasKey` reduces balance, but the attacker can keep re-topping it up faster/cheaper than the victim can withdraw, or simply front-run the victim's delete transaction the same way the St1inch attacker front-runs `withdraw`).

This directly mirrors the reported bug class: an unprivileged actor calls a public "deposit"-style entrypoint (`TransferToGasKey`, analogous to `depositFor`) naming the victim's account, to force a state condition (balance above burn threshold, analogous to extending the lock duration) that blocks the victim's own withdrawal/removal action (`delete_gas_key`/`action_delete_account`, analogous to `withdraw`/`withdrawTo`).

### Impact Explanation
This is a **permanent freezing of funds/functionality** vector, not merely gas griefing:
- The victim's gas key can never be deleted while its balance exceeds `MAX_BALANCE_TO_BURN`, and neither can the whole account if the attack is repeated against multiple gas keys.
- Since account deletion also refunds the account's NEAR balance to a beneficiary (`Receipt::new_balance_refund` in `action_delete_account`), this blocks the ability to fully close/reclaim funds from the account, functionally freezing the account-deletion/refund path.
- The attack cost to the attacker is tiny (over `MAX_BALANCE_TO_BURN` by a minimal margin), while the victim cannot unilaterally clear it without racing/being faster than the attacker, and the funds deposited by the attacker into the gas key are eventually burned (not refunded to attacker or victim) if deletion is ever forced through some other path, or otherwise remain stuck.

### Likelihood Explanation
The action requires no special permission: any account can construct a `Transfer`-class receipt with a `TransferToGasKey` action targeting a known public key on the victim's account (gas key public keys are visible via `view_access_keys`/`view_access_key` RPCs). No signature from the victim is required for this action to execute against them — only knowledge of the target account id and gas key public key, both discoverable on-chain. This makes exploitation straightforward and cheap; likelihood is high wherever gas keys (a v85+ feature, NEP for meta-tx-style gas keys) are used.

### Recommendation
Add an authorization check to `action_transfer_to_gas_key` (and audit `action_withdraw_from_gas_key` similarly) so that only the account itself (i.e., `receipt.predecessor_id() == account_id`, or equivalently only self-originated transactions/receipts) — or another explicitly authorized principal — may increase a gas key's balance. Alternatively, decouple the `MAX_BALANCE_TO_BURN` deletion gate from externally-toppable balances, e.g. by refunding/burning any excess above the cap automatically at delete time instead of hard-failing the deletion, so a third party cannot make the balance permanently un-deletable.

### Proof of Concept
1. Victim account `alice.near` has a `GasKeyFullAccess` key added via `AddKey` (`add_gas_key`, `runtime/runtime/src/access_keys.rs:194`), balance starts at `0`.
2. Attacker `mallory.near`, with no relation to `alice.near`, submits a transaction/receipt to `alice.near` containing `Action::TransferToGasKey(TransferToGasKeyAction { public_key: <alice's gas key>, deposit: MAX_BALANCE_TO_BURN + 1 })`. This succeeds because `action_transfer_to_gas_key` performs no predecessor/owner check (`runtime/runtime/src/access_keys.rs:257-288`).
3. Alice later attempts `DeleteKey` on that gas key. `action_delete_key` → `delete_gas_key` sees `gas_key_info.balance (MAX_BALANCE_TO_BURN + 1) > GasKeyInfo::MAX_BALANCE_TO_BURN` and returns `ActionErrorKind::GasKeyBalanceTooHigh`, leaving the key intact (`runtime/runtime/src/access_keys.rs:103-111`).
4. Alice attempts `DeleteAccount`; `compute_gas_key_balance_sum` includes the poisoned key's balance, exceeding the threshold, and `action_delete_account` returns `GasKeyBalanceTooHigh` as well (`runtime/runtime/src/actions.rs:354-363`), permanently blocking account deletion/refund unless Alice can withdraw the excess balance before Mallory (who can repeat the deposit cheaply) tops it back up.

*Note: I was not able to fully trace the deposit/fee-charging path that confirms `TransferToGasKey`'s `deposit` is charged to the predecessor's balance the same way as `Transfer` (this appears consistent with the codebase's cost model in `runtime/runtime/src/config.rs`/`lib.rs`, but I did not locate and read that exact charging code in this session). This does not affect the core finding — the missing ownership check on the receiver side — but is noted as unverified in full detail.*

pub(crate) fn action_transfer_to_gas_key(
    state_update: &mut TrieUpdate,
    result: &mut ActionResult,
    account_id: &AccountId,
    action: &TransferToGasKeyAction,
) -> Result<(), RuntimeError> {
    let Some(mut access_key) = get_access_key(state_update, account_id, &action.public_key)? else {
        result.result = Err(ActionErrorKind::GasKeyDoesNotExist {
            account_id: account_id.clone(),
            public_key: Box::new(action.public_key.clone()),
        }
        .into());
        return Ok(());
    };
    let Some(gas_key_info) = access_key.gas_key_info_mut() else {
        // Key exists but is not a gas key
        result.result = Err(ActionErrorKind::GasKeyDoesNotExist {
            account_id: account_id.clone(),
            public_key: Box::new(action.public_key.clone()),
        }
        .into());
        return Ok(());
    };

    gas_key_info.balance = gas_key_info.balance.checked_add(action.deposit).ok_or_else(|| {
        RuntimeError::StorageError(StorageError::StorageInconsistentState(
            "gas key balance integer overflow".to_string(),
        ))
    })?;
    set_access_key(state_update, account_id.clone(), action.public_key.clone(), &access_key);
    Ok(())
}
