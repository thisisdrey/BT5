Tracing `try_parse_request` in `stackslib/src/net/api/blocksimulate.rs`, the auth checks execute and return early via `?`/`Err` *before* any field mutation occurs. The password-not-configured check (line 153-155), missing-header check (line 156-158), and password-mismatch check (line 159-161) all `return Err(...)` immediately — control never reaches `self.block_id = Some(block_id)` (line 173), the `profiler` query loop (lines 175-184), or the `self.transactions`/`self.mint` assignment (line 198), which occur strictly afterward in program order. [1](#0-0) 

Since Rust executes this function sequentially and none of the three early-return auth paths fall through to the mutation statements, an unauthenticated or wrong-password request cannot mutate `self.block_id`, `self.profiler`, `self.transactions`, or `self.mint` — the claimed equality (mutation only after `auth_header == password` succeeds) holds for every early-return path. The premise that the profiler loop runs "before" the auth gate in terms of control flow is incorrect; it is textually below the auth gate and only reached once auth succeeds, since the auth-gate branches all `return` unconditionally. [2](#0-1) 

The only pre-existing behavior worth noting is that `restart()` only resets `block_id`, not `profiler`/`transactions`/`mint` [3](#0-2) , but reaching a state where these fields are stale requires a prior *successful* authenticated call to have set them — which requires possession of the RPC secret, out of scope for an unprivileged remote attacker per the rules. No auth-bypass or state corruption is reachable by an unauthenticated party.
