### Title
Unbounded resource-delegation fan-in enables read-amplification DoS via `DelegatedResourceAccountIndexStore.getWithPrefix` - ([File: chainbase/src/main/java/org/tron/core/store/DelegatedResourceAccountIndexStore.java])

### Summary
`DelegateResourceActuator`/`DelegateResourceProcessor` allow any funded account to delegate as little as 1 TRX of frozen BANDWIDTH/ENERGY to an arbitrary receiver, with no limit on the number of distinct delegator addresses that may point to the same receiver (or vice versa). Every such delegation is indexed as a separate LevelDB/RocksDB key under a `V2_FROM_PREFIX`/`V2_TO_PREFIX` scan range in `DelegatedResourceAccountIndexStore`. The read path `getWithPrefix()` (used by `getIndex`/`getV2Index`, in turn exposed by the `GetDelegatedResourceAccountIndex`/`GetDelegatedResourceAccountIndexV2` HTTP/gRPC APIs and by `UnDelegateResourceActuator`/`FreezeBalanceActuator`/`UnfreezeBalanceActuator` execution paths) performs an unbounded `prefixQuery` over all entries for that address, materializes them into a `List`, and sorts by timestamp — with no cap analogous to Alchemix's `MAX_DELEGATES`. This mirrors the reported bug class: an attacker can cheaply fan-in an unbounded number of delegation relationships to a single victim address, then any account operation or unauthenticated API query touching that address's delegation index becomes O(n) in the number of attacker-created relations.

### Finding Description
`DelegateResourceActuator.execute()`/`DelegateResourceProcessor.execute()` create a new delegation index entry via `DelegatedResourceAccountIndexStore.delegateV2()` for every call, with the only economic gate being a minimum 1 TRX (`TRX_PRECISION`) delegated balance: [1](#0-0) 
There is no check anywhere in `validate()` capping how many distinct owner addresses may delegate to the same `receiverAddress`, nor how many distinct receivers a single owner may delegate to — unlike VotingEscrow's `MAX_DELEGATES` guard.

Each such delegation is persisted under a prefix-keyed index: [2](#0-1) 

The read path that reconstructs the full list of delegators/receivers for an address performs an unbounded prefix scan, materializes all matching capsules into memory, and sorts them: [3](#0-2) 

This method is reachable in two ways an unprivileged actor controls:
1. Directly via the anonymous HTTP/gRPC query APIs `GetDelegatedResourceAccountIndex`/`GetDelegatedResourceAccountIndexV2`, which take an arbitrary address parameter and call `wallet.getDelegatedResourceAccountIndexV2(address)` → `getV2Index()` → `getWithPrefix()`: [4](#0-3) 
2. Indirectly, via the legacy (non-optimized) index path used by `FreezeBalanceActuator`/`UnfreezeBalanceActuator`, whose `toAccountsList`/`fromAccountsList` grow unbounded in a single capsule and are rewritten/scanned on every subsequent freeze/unfreeze touching that address: [5](#0-4) 

Because there is no per-address cap on the number of delegation relationships (analogous to `MAX_DELEGATES`), an attacker can cheaply create a very large number of funded accounts (each only needs the minimum frozen balance to delegate 1 TRX) and have each of them delegate to a single victim address. Every subsequent query of that victim's delegation index (a public, unauthenticated read) forces the node to scan, deserialize, and sort the entire (attacker-inflated) key range, and every on-chain operation from the victim that touches this index (delegate/undelegate/freeze/unfreeze) does the same server-side work synchronously inside block/transaction processing.

### Impact Explanation
This is a griefing/DoS vector reachable purely through standard, unprivileged, broadcastable `DelegateResourceContract` transactions plus unauthenticated API queries — no special privilege is required. A well-resourced attacker can force disproportionate CPU/IO cost on full nodes (and potentially other users' subsequent transactions/actuator executions touching the victim address), degrading the affected query API's/service's availability and slowing down transaction processing for the targeted account. This matches the Medium-severity classification of the original report (griefing / degraded availability of a core operation), though it stops short of directly stealing funds or corrupting balances.

### Likelihood Explanation
Likelihood is moderate: creating many accounts and issuing many `DelegateResourceContract` transactions costs bandwidth/energy and requires funding many addresses with at least the minimal frozen balance, but there is no protocol-level cap preventing an attacker from doing so at scale, and the vulnerable read path (`getWithPrefix`) is reachable by anyone via a public query API without needing to sign any transaction.

### Recommendation
- Introduce an explicit cap (e.g., a `MAX_DELEGATE_ACCOUNTS`-style dynamic parameter) on the number of distinct delegation relationships allowed per address in `DelegateResourceActuator.validate()`/`DelegateResourceProcessor`, similar to Alchemix's `MAX_DELEGATES` mitigation.
- Add pagination/limits to `DelegatedResourceAccountIndexStore.getWithPrefix()` (and the corresponding gRPC/HTTP servlets) so a single query cannot force an unbounded prefix scan and sort.
- Consider deprecating/hardening the legacy (`supportAllowDelegateOptimization() == false`) list-based index path in `FreezeBalanceActuator`/`UnfreezeBalanceActuator`, which stores unbounded `toAccountsList`/`fromAccountsList` inside a single capsule value.

### Proof of Concept
Not executed against a live node; root cause identified via static review:
1. Fund N attacker-controlled accounts with the minimal frozen BANDWIDTH/ENERGY balance (≥1 TRX).
2. From each attacker account, broadcast a `DelegateResourceContract` transaction delegating to the same `receiverAddress` (victim), succeeding validation because there is no per-address relationship cap (`DelegateResourceActuator.validate()`).
3. Repeat for a large N (e.g., tens of thousands), each creating a new key under `V2_TO_PREFIX + receiverAddress + ownerAddress`.
4. Query `GetDelegatedResourceAccountIndexV2` (HTTP/gRPC) for `receiverAddress`; the node executes an unbounded `prefixQuery` + in-memory sort over all N entries in `getWithPrefix()`, and any subsequent freeze/unfreeze/delegate touching `receiverAddress` incurs the same cost inline in actuator execution.

  private DelegatedResourceAccountIndexCapsule getWithPrefix(byte[] fromPrefix, byte[] toPrefix, byte[] address) {
    DelegatedResourceAccountIndexCapsule tmpIndexCapsule =
        new DelegatedResourceAccountIndexCapsule(ByteString.copyFrom(address));

    byte[] key = Bytes.concat(fromPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpToList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpToList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    List<ByteString> list = tmpToList.stream()
        .map(DelegatedResourceAccountIndexCapsule::getAccount).collect(Collectors.toList());
    tmpIndexCapsule.setAllToAccounts(list);

    key = Bytes.concat(toPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpFromList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpFromList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    list = tmpFromList.stream().map(DelegatedResourceAccountIndexCapsule::getAccount).collect(
        Collectors.toList());
    tmpIndexCapsule.setAllFromAccounts(list);
    return tmpIndexCapsule;
  }
