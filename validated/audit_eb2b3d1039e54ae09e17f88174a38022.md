### Title
Missing hash verification of downloaded attachment content in `AttachmentsBatchStateContext::extend_with_attachments` - ([File: stackslib/src/net/atlas/download.rs])

### Summary
When downloading a BNS attachment for a pending `AttachmentRequest{content_hash: H1}`, the response body from `/v2/attachments/H1` is decoded via `decode_atlas_get_attachment()` and the resulting `Attachment` is inserted into `self.attachments` without ever checking that `Attachment::hash()` of the returned content equals the requested `content_hash`. This lets any peer serving the request substitute arbitrary content, which then gets permanently written to the node's `attachments` table keyed on the wrong hash.

### Finding Description
`AttachmentsBatchStateContext::extend_with_attachments` iterates over `results.succeeded`, decodes each HTTP response with `response.decode_atlas_get_attachment()`, and does `self.attachments.insert(response.attachment)` with no comparison against `request.content_hash`: [1](#0-0) 

The request itself is built in `get_prioritized_attachments_requests`, carrying `content_hash` from the on-chain `AttachmentInstance`: [2](#0-1) 

The HTTP path used, `/v2/attachments/<attachment_hash>`, is handled server-side by `RPCGetAttachmentRequestHandler`, which looks up the attachment strictly by the hash embedded in the URL via `find_attachment(&attachment_hash)` — this is correct for a well-behaved node, since `AtlasDB` only stores attachments that were already hash-validated on insertion. But this server-side behavior only constrains *honest* nodes; it does not constrain what bytes a malicious/adversarial peer chosen from `self.peers` (any outbound sync peer, no special privilege required) actually returns for that URL: [3](#0-2) 

`decode_atlas_get_attachment` simply parses the JSON body into a `GetAttachmentResponse`/`Attachment` with no built-in hash check: [4](#0-3) [5](#0-4) 

Once inserted into `context.attachments`, `AttachmentsDownloader::run` unconditionally persists it: for every attachment drained from `context.attachments`, it calls `atlasdb.insert_instantiated_attachment(&attachment)` (storing content keyed by its own derived hash, i.e., `H2 = Hash160::from_data(B2)`), then tries to resolve pending instances via `resolve_attachment(&attachment.hash())`. Since no instance has `content_hash == H2`, nothing is resolved for the forged data, while the real pending request for `H1` is left unmet and the batch is bumped for retry: [6](#0-5) 

Because there is no equality check `Attachment::hash(&B2) == request.content_hash` anywhere between the wire response and the persisted store, a peer can answer *any* attachment request with unrelated bytes B2, and those bytes will be durably written into the node's Atlas attachment table keyed on `H2`, a hash no on-chain BNS operation ever committed to.

### Impact Explanation
An unprivileged peer that the victim node selects as an outbound sync/data peer (this requires no special role — just being a P2P/RPC-reachable peer that the target dials for Atlas data) can force the victim to durably store arbitrary attacker-chosen content in `atlasdb`'s `attachments` table under a hash of the attacker's choosing, with no corresponding on-chain `AttachmentInstance`. Each successful HTTP 200 in the download batch stores one attachment (bounded by `attachments_max_size`), and this is repeatable across retries/batches, enabling storage bloat with content that was never authorized by any name operation — this matches the "attachment/BNS mismatch" High-impact category (serving/storing state that no canonical block committed).

### Likelihood Explanation
Preconditions are modest: the attacker must be selected as one of the node's outbound Atlas sync peers (a normal, permissionless condition since `get_outbound_sync_peers`/`get_data_url` only requires being a connected peer with an advertised data URL), and the node must have at least one pending `AttachmentInstance` referencing content the attacker doesn't have (trivially true for any BNS churn). The attacker's cost is a single crafted HTTP response per request; no cryptographic material, secret, or privileged role is needed, and the attack is repeatable on every attachment poll cycle.

### Recommendation
In `AttachmentsBatchStateContext::extend_with_attachments`, after `decode_atlas_get_attachment()`, verify `response.attachment.hash() == request.content_hash` before inserting into `self.attachments`; if the hash doesn't match, treat it as a failed request (`report.bump_failed_requests()`) rather than storing the content, and optionally penalize/deregister the offending peer.

### Proof of Concept
Unit test plan (in `stackslib/src/net/atlas/tests.rs`, alongside existing `download.rs` tests):
1. Build an `AttachmentsBatchStateContext` with a single peer and an `AttachmentRequest { content_hash: H1, .. }` in a `BatchedRequestsResult::succeeded` map.
2. Construct a `StacksHttpResponse` whose body is a JSON-encoded `GetAttachmentResponse { attachment: Attachment::new(B2) }` where `Hash160::from_data(&B2) = H2 != H1`.
3. Call `context.extend_with_attachments(&mut results)`.
4. Assert `context.attachments` contains an `Attachment` with `.hash() == H2` (not `H1`), demonstrating the unchecked substitution — then simulate `AttachmentsDownloader::run`'s `Done` branch and assert `atlasdb.find_attachment(&H2)` returns `Some(_)` while `atlasdb.find_attachment(&H1)` remains `None`, confirming persistence of unauthorized content keyed on the wrong hash.

    pub fn extend_with_attachments(

    ) -> AttachmentsBatchStateContext {

            let report = self
                .peers
                .get_mut(request.get_url())
                .expect("Atlas: unable to retrieve reliability report for peer");

            let response = if let Some(r) = response {
                r
            } else {
                report.bump_failed_requests();
                continue;
            };

            if let Ok(response) = response.decode_atlas_get_attachment() {
                self.attachments.insert(response.attachment);
                report.bump_successful_requests();
            } else {
                report.bump_failed_requests();
            }
        }
