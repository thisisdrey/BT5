### Title
Front-runnable contract-deployment griefing via account-existence check instead of contract-existence check - (File: `actuator/src/main/java/org/tron/core/actuator/VMActuator.java`)

### Summary
For top-level `CreateSmartContract` transactions, `VMActuator.create()` rejects deployment whenever *any* `AccountCapsule` already exists at the deterministically-computed contract address, rather than checking whether a contract actually exists there. Since the address is derivable ahead of time from the transaction's raw-data hash and owner address, an attacker who observes a pending deployment in the mempool can front-run it with a plain TRX transfer to that address, causing the legitimate deployment to permanently fail — the exact "empty account" ambiguity described in the Fastlane `Factory.sol` report, but manifesting as a validate-time rejection based on account presence rather than code presence.

### Finding Description
`VMActuator.create()` computes the deterministic deployment address and validates it like this: [1](#0-0) 

```java
byte[] contractAddress = WalletUtil.generateContractAddress(trx);
// insure the new contract address haven't exist
if (rootRepository.getAccount(contractAddress) != null) {
  throw new ContractValidateException(
      "Trying to create a contract with existing contract address: " + StringUtil
          .encode58Check(contractAddress));
}
```

`generateContractAddress` derives the address purely from the transaction's raw-data hash (txid) and the owner address: [2](#0-1) 

Because the transaction id (and thus the future contract address) is fixed as soon as the deploy transaction is signed/broadcast — before it is packed into a block — any observer of the mempool can compute the target address and send it a minimal TRX transfer first. Once any `AccountCapsule` exists at that address (even a plain `Normal` account holding balance with zero code), the `rootRepository.getAccount(contractAddress) != null` check trips and the legitimate `CreateSmartContract` transaction is rejected with a `ContractValidateException`, permanently preventing that specific deployment (the deployer would have to resubmit with a different nonce/txid to get a new address, but the same griefing can be repeated).

This mirrors the reported Solidity bug precisely: the report notes that `codehash == 0` is not equivalent to "no contract will ever be deployable here," because a bare balance transfer changes the "emptiness" state used for the check. Here the java-tron analog is worse in effect than the Solidity original in one respect (it's a full validate-time revert instead of a silent skip), but the same root cause exists: the code conflates "an account entry exists" with "a contract exists," which is exactly the ambiguity the recommendation ("check code length/contract presence instead") is meant to fix.

Notably, the codebase already fixes this correctly elsewhere: the internal `CREATE`/`CREATE2` opcode path in `Program.createContractImpl` uses `isContractExist()`, which checks `deposit.getContract(existingAddr.getAddress().toByteArray()) != null` rather than merely `existingAccount != null`: [3](#0-2) [4](#0-3) 

This confirms the correct pattern is already known/used for `CREATE`/`CREATE2` opcodes, but the top-level `VMActuator.create()` path for user-submitted `CreateSmartContract` transactions still uses the vulnerable `getAccount() != null` check.

### Impact Explanation
This is a griefing/denial-of-service vector reachable by any unprivileged account with a trivial amount of TRX: an attacker can permanently block a specific, targeted contract deployment by front-running it with a 1-sun transfer to the precomputed address. This is a "denial of node service for a specific transaction" class issue — it does not steal funds or crash the node, but it lets any actor deterministically and cheaply deny a competitor's contract deployment (e.g., blocking a time-sensitive DeFi launch, an auction contract, a competing exchange listing, etc.), which is a concrete availability/integrity impact on contract deployment as a service.

### Likelihood Explanation
Likelihood is high for any attacker who can observe the mempool for `CreateSmartContract` transactions (a routine capability for any node operator or public full-node API consumer) and race a cheap transfer transaction ahead of it. No special privileges, staking, or witness/SR status are required — it only needs the ability to submit an ordinary `TransferContract` transaction, i.e., it is reachable purely from a single unprivileged signed transaction.

### Recommendation
In `VMActuator.create()`, replace the account-existence check with a contract-existence check consistent with the `isContractExist()` pattern already used in `Program.createContractImpl`, e.g. check `rootRepository.getContract(contractAddress) != null` (and/or `getCode(contractAddress)` non-empty) instead of `rootRepository.getAccount(contractAddress) != null`. If an account exists but has no code, the code should proceed with deployment, upgrading the account's type to `Contract` in place (mirroring the pattern already implemented for CREATE2 collisions and for `HistoryBlockHashUtil.deploy`, which explicitly upgrades a pre-existing `Normal` account to `Contract` while preserving balance).

### Proof of Concept
1. Attacker monitors the mempool/broadcast network for a pending `CreateSmartContract` transaction from victim `V`.
2. Attacker computes `contractAddress = sha3omit12(txRawDataHash || ownerAddress)` exactly as `WalletUtil.generateContractAddress` does, using the observed pending transaction's raw data.
3. Attacker submits a plain `TransferContract` sending a minimal amount of TRX to `contractAddress`, and gets it included in an earlier or the same block (front-running via fee/ordering).
4. This causes `rootRepository.getAccount(contractAddress)` to return a non-null `AccountCapsule` (type `Normal`, no code, no `ContractCapsule`) by the time `V`'s `CreateSmartContract` transaction executes.
5. `VMActuator.create()` at `actuator/src/main/java/org/tron/core/actuator/VMActuator.java:360` throws `ContractValidateException("Trying to create a contract with existing contract address: ...")`, so `V`'s deployment fails, even though no actual contract code exists at that address.

```java
  public static byte[] generateContractAddress(Transaction trx) {

    CreateSmartContract contract = ContractCapsule.getSmartContractFromTransaction(trx);
    byte[] ownerAddress = contract.getOwnerAddress().toByteArray();
    TransactionCapsule trxCap = new TransactionCapsule(trx);
    byte[] txRawDataHash = trxCap.getTransactionId().getBytes();

    byte[] combined = new byte[txRawDataHash.length + ownerAddress.length];
    System.arraycopy(txRawDataHash, 0, combined, 0, txRawDataHash.length);
    System.arraycopy(ownerAddress, 0, combined, txRawDataHash.length, ownerAddress.length);

    return Hash.sha3omit12(combined);

  }
```
