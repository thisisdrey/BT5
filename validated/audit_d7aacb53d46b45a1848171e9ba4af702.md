### Title
Unbounded array allocation from attacker-controlled length in `ValidateMultiSign` precompile causes `OutOfMemoryError` denial of service - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `ValidateMultiSign` TVM precompiled contract extracts a signature-array length directly from attacker-supplied call data and uses it to allocate a two-dimensional `byte[][]` array before any bound is enforced, mirroring the LibTIFF `tif_pixarlog.c` pattern where an unchecked, crafted length drives a memory allocation that can fail catastrophically and abort the process.

### Finding Description
`extractBytesArray` reads the array length straight from the caller-controlled word at `offset` and immediately allocates a reference array of that size, with no upper bound check inside the helper itself: [1](#0-0) 

`ValidateMultiSign.execute` calls this helper via `extractBytesArray(words, words[3].intValueSafe() / WORD_SIZE, rawData)` whenever `VMConfig.allowTvmSelfdestructRestriction()` is disabled. The size validation (`sigArraySize > MAX_SIZE`) is only performed on the alternate `extractSigArray` branch, gated behind that same flag: [2](#0-1) 

Because `words[offset].intValueSafe()` is derived from a fully attacker-controlled `DataWord`, a caller can set it to a very large value (up to `Integer.MAX_VALUE`), independent of the real size of `rawData`. `new byte[len][]` at line 404 then attempts to allocate an array of up to ~2^31 references (≈17 GB of pointers on a 64-bit JVM), which throws `OutOfMemoryError`. Unlike the `Program.OutOfMemoryException` path used for VM memory expansion (guarded by `checkMemorySize`/`MEM_LIMIT` in `EnergyCost.calcMemEnergy` and caught inside `Program`), this JVM-level `OutOfMemoryError` is raised in `PrecompiledContracts` code that sits outside the local `try { ... } catch (Throwable t)` block guarding only the permission-weight-calculation section: [3](#0-2) 
The extraction call (and thus the OOM) happens before this guarded region, so it is not locally contained and propagates up through the interpreter's precompile-dispatch call stack.

### Impact Explanation
An `OutOfMemoryError` thrown from deep inside TVM execution is a JVM `Error`, not a checked/normal exception; depending on how the outer runtime/interpreter loop and JVM heap state react, this can destabilize or crash the node process handling the transaction (or degrade all concurrently executing threads/contracts due to heap pressure), producing a denial-of-service condition reachable by any account able to broadcast a `TriggerSmartContract` transaction that calls this precompile with crafted call data. This matches the "node crash or halt" acceptance criterion.

### Likelihood Explanation
Reachability requires only a signed transaction invoking the `ValidateMultiSign` precompile address with crafted calldata, i.e., no special privilege. The vulnerable path is exercised only when `VMConfig.allowTvmSelfdestructRestriction()` is `false`; on networks/genesis states where this proposal has not yet been activated (or forks/private chains built on this code that never enable it), the unchecked `extractBytesArray` branch remains live. I could not confirm from the available index whether this flag is unconditionally enabled on the current production mainnet genesis, so likelihood is contingent on that configuration state — treat as Medium confidence pending confirmation of the flag's default/activation status in the target deployment.

### Recommendation
Enforce the `MAX_SIZE` (or equivalent sane) upper bound on the parsed array length inside `extractBytesArray` and `extractBytes32Array` themselves (not only in the caller's optional branch), before allocating any array, and validate that `len` is non-negative and within the bounds implied by `words.length`/`rawData.length` before allocation, regardless of `VMConfig.allowTvmSelfdestructRestriction()` state.

### Proof of Concept
1. Deploy/call the precompile address handling `ValidateMultiSign` via a `TriggerSmartContract` transaction on a chain/state where `VMConfig.allowTvmSelfdestructRestriction()` is `false`.
2. Craft `rawData` so that `words[3]` points to an offset whose word value (`len`) is a very large integer (e.g., `0x7FFFFFFF`), while the rest of the payload is arbitrary/short.
3. Broadcasting this transaction causes `ValidateMultiSign.execute` to invoke `extractBytesArray(words, offset, rawData)`, which executes `new byte[len][]` at [4](#0-3)  and throws `OutOfMemoryError`, uncaught by the narrow `try/catch(Throwable t)` block that only wraps the later permission logic.

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
