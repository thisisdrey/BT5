### Title
Pending Commission Percentage Not Applied in `calculate_stake_pool_drift` After Lockup Cycle Ends — (`File: aptos-move/framework/aptos-framework/sources/delegation_pool.move`)

---

### Summary

In `delegation_pool.move`, the `calculate_stake_pool_drift` function reads `pool.operator_commission_percentage` directly from the stored `DelegationPool` struct. It never checks whether a pending `NextCommissionPercentage` has become effective (i.e., the lockup cycle has ended). This is the exact analog of the external bug: a pending value that has passed its timeout is not flushed to storage before being used in a calculation, causing the stale stored value to be applied instead.

---

### Finding Description

The `NextCommissionPercentage` resource stores a pending commission rate and the timestamp after which it becomes effective: [1](#0-0) 

The view function `operator_commission_percentage` correctly checks whether the pending value is effective and returns it: [2](#0-1) 

However, `calculate_stake_pool_drift` — the internal function that computes how much commission the operator is owed for accumulated rewards — reads `pool.operator_commission_percentage` directly from the struct, bypassing this check entirely: [3](#0-2) 

`synchronize_delegation_pool` calls `calculate_stake_pool_drift` first, distributes commission at the stale rate, and only **afterwards** updates `pool.operator_commission_percentage` to the effective pending value: [4](#0-3) 

The update happens at lines 1988–1992, **after** commission has already been distributed using the old rate at lines 1945–1956. [5](#0-4) 

---

### Impact Explanation

After a lockup cycle ends and `NextCommissionPercentage` becomes effective, any rewards accumulated between the lockup cycle boundary and the next `synchronize_delegation_pool` call are taxed at the **old** stored commission rate, not the new effective one.

- **If commission decreased** (e.g., 20% → 10%): rewards earned after lockup cycle end are still taxed at 20%. The operator extracts more commission than entitled; delegators receive less stake than they should. This is a direct, if bounded, theft from delegator staking balances.
- **If commission increased** (e.g., 10% → 20%): rewards are taxed at 10% instead of 20%. The operator is underpaid; delegators benefit.

The harmful case for delegators is a commission decrease. The magnitude is bounded by: `(rewards since lockup end) × (old_commission − new_commission)`. For a large pool with a significant commission decrease and a delay of several epochs before the next sync, this can be a non-trivial amount of APT.

---

### Likelihood Explanation

Every user operation (`add_stake`, `unlock`, `reactivate_stake`, `withdraw`) triggers `synchronize_delegation_pool`, so the window is typically short. However:

1. The operator controls when they call `synchronize_delegation_pool` directly.
2. If the pool is temporarily inactive (no user operations), the window can extend for multiple epochs.
3. The operator can set a low commission for the next lockup cycle, wait for it to become effective, then delay syncing to continue collecting the old higher commission on accumulated rewards.

---

### Recommendation

In `calculate_stake_pool_drift`, replace the direct read of `pool.operator_commission_percentage` with a check that also considers `NextCommissionPercentage` if it has become effective. Concretely, before computing `commission_active` and `commission_pending_inactive`, resolve the effective commission rate using the same logic as `operator_commission_percentage` (the view function):

```move
let effective_commission = if (is_next_commission_percentage_effective(get_pool_address(pool))) {
    borrow_global<NextCommissionPercentage>(get_pool_address(pool)).commission_percentage_next_lockup_cycle
} else {
    pool.operator_commission_percentage
};
```

Then use `effective_commission` in place of `pool.operator_commission_percentage` at lines 1894 and 1904.

---

### Proof of Concept

1. Operator creates a delegation pool with 20% commission.
2. Owner calls `update_commission_percentage(0)` → `NextCommissionPercentage { commission_percentage_next_lockup_cycle: 0, effective_after_secs: lockup_end }`.
3. Lockup cycle ends. `is_next_commission_percentage_effective` now returns `true`. `operator_commission_percentage(pool_address)` returns `0`.
4. Several epochs pass with no user operations. Rewards accumulate. The operator does **not** call `synchronize_delegation_pool`.
5. Eventually a user calls `add_stake` or `unlock`, triggering `synchronize_delegation_pool`:
   - `calculate_stake_pool_drift` reads `pool.operator_commission_percentage = 20` (stale stored value).
   - Commission is computed and distributed at 20% for **all** accumulated rewards, including those earned after the lockup cycle ended.
   - Only then is `pool.operator_commission_percentage` updated to `0`.
6. Delegators receive less stake than they are entitled to for the post-lockup-end reward period. The operator receives excess commission.

The existing test at line 3838–3840 confirms that `get_add_stake_fee` correctly uses the new commission via `operator_commission_percentage(pool_address)`, but `calculate_stake_pool_drift` does not — demonstrating the inconsistency within the same codebase. [6](#0-5)

    public entry fun synchronize_delegation_pool(
        pool_address: address
    ) acquires DelegationPool, GovernanceRecords, BeneficiaryForOperator, NextCommissionPercentage {
        assert_delegation_pool_exists(pool_address);
        let pool = borrow_global_mut<DelegationPool>(pool_address);
        let (
            lockup_cycle_ended,
            active,
            pending_inactive,
            commission_active,
            commission_pending_inactive
        ) = calculate_stake_pool_drift(pool);

        // zero `pending_active` stake indicates that either there are no `add_stake` fees or
        // previous epoch has ended and should release the shares owning the existing fees
        let (_, _, pending_active, _) = stake::get_stake(pool_address);
        if (pending_active == 0) {
            // renounce ownership over the `add_stake` fees by redeeming all shares of
            // the special shareholder, implicitly their equivalent coins, out of the active shares pool
            redeem_active_shares(pool, NULL_SHAREHOLDER, MAX_U64);
        };

        // distribute rewards remaining after commission, to delegators (to already existing shares)
        // before buying shares for the operator for its entire commission fee
        // otherwise, operator's new shares would additionally appreciate from rewards it does not own

        // update total coins accumulated by `active` + `pending_active` shares
        // redeemed `add_stake` fees are restored and distributed to the rest of the pool as rewards
        pool.active_shares.update_total_coins(active - commission_active);
        // update total coins accumulated by `pending_inactive` shares at current observed lockup cycle
        pending_inactive_shares_pool_mut(pool).update_total_coins(pending_inactive - commission_pending_inactive);

        // reward operator its commission out of uncommitted active rewards (`add_stake` fees already excluded)
        buy_in_active_shares(pool, beneficiary_for_operator(stake::get_operator(pool_address)), commission_active);
        // reward operator its commission out of uncommitted pending_inactive rewards
        buy_in_pending_inactive_shares(
            pool,
            beneficiary_for_operator(stake::get_operator(pool_address)),
            commission_pending_inactive
        );

        event::emit_event(
            &mut pool.distribute_commission_events,
            DistributeCommissionEvent {
                pool_address,
                operator: stake::get_operator(pool_address),
                commission_active,
                commission_pending_inactive,
            },
        );

        emit(DistributeCommission {
            pool_address,
            operator: stake::get_operator(pool_address),
            beneficiary: beneficiary_for_operator(stake::get_operator(pool_address)),
            commission_active,
            commission_pending_inactive,
        });

        // advance lockup cycle on delegation pool if already ended on stake pool (AND stake explicitly inactivated)
        if (lockup_cycle_ended) {
            // capture inactive coins over all ended lockup cycles (including this ending one)
            let (_, inactive, _, _) = stake::get_stake(pool_address);
            pool.total_coins_inactive = inactive;

            // advance lockup cycle on the delegation pool
            pool.observed_lockup_cycle.index += 1;
            // start new lockup cycle with a fresh shares pool for `pending_inactive` stake
            pool.inactive_shares.add(pool.observed_lockup_cycle, pool_u64::create_with_scaling_factor(SHARES_SCALING_FACTOR));
        };

        if (is_next_commission_percentage_effective(pool_address)) {
            pool.operator_commission_percentage = borrow_global<NextCommissionPercentage>(
                pool_address
            ).commission_percentage_next_lockup_cycle;
        }
    }
