### Title
Missing enforcement of `write-freq` rate-limit on direct StackerDB chunk writes allows an authenticated signer to bypass the contract-mandated write-frequency gate - (File: `stackslib/src/net/stackerdb/db.rs`)

### Summary
This is the correct analog of the report's bug class: a timestamp-derived constraint that is defined and *supposed* to be enforced, but is not actually checked at the point where it matters, letting the effect the constraint was meant to prevent occur anyway. In VTVLVesting the missing check was `_startTimestamp > block.timestamp`; here the missing check is the StackerDB contract's `write-freq` (a `write_time`/wall-clock timestamp gate), which is validated on the *download/rate-limiting* path but never enforced on the actual chunk-write path (`StackerDBTx::try_replace_chunk`), which is reachable by any address holding a valid slot-signer key via the unauthenticated `POST /v2/stackerdb/:principal/:contract/chunks` RPC endpoint.

### Finding Description
Each StackerDB smart contract can declare a `write-freq` value that is meant to throttle how often a given slot may be rewritten (`stackslib/src/net/stackerdb/config.rs:422-437`, loaded into `StackerDBConfig.write_freq`). The `chunks` table stores a `write_time` UNIX timestamp per slot (`stackslib/src/net/stackerdb/db.rs:70-71`), updated on every successful write via `get_epoch_time_secs()` in `insert_chunk` (`stackslib/src/net/stackerdb/db.rs:374-396`).

The only place `write_freq` is actually consulted is `StackerDBSync::getchunks` in `stackslib/src/net/stackerdb/sync.rs:332-352`, where a node throttles which chunks it will *request* from peers based on `write_ts + self.write_freq > now`. This is purely a downloader-side/self-protective decision about what to fetch; it has no bearing on write acceptance.

The actual write-gating function, `StackerDBTx::try_replace_chunk` (`stackslib/src/net/stackerdb/db.rs:400-438`), only checks:
1. chunk size vs `config.chunk_size`
2. slot exists
3. `slot_desc.verify(&slot_validation.signer)` (signature check)
4. `slot_version <= slot_validation.version` (staleness)
5. `slot_version > config.max_writes` (write-count cap)

There is no check comparing `get_epoch_time_secs()` against `slot_validation.write_time + config.write_freq`. This function is invoked directly by the `POST /v2/stackerdb/:principal/:contract/chunks` HTTP handler (`stackslib/src/net/api/poststackerdbchunk.rs:197-201`), which is reachable by any remote, unprivileged client that merely knows a signer's private key for one slot (the same threat model as any legitimate StackerDB writer, e.g. a stacks-signer). It is also invoked from `PeerNetwork::process_stacker_db_chunks` (`stackslib/src/net/relay.rs:2406-2455`) when storing chunks obtained via sync, so even the sync path's own throttling in `getchunks` is not backed up by a hard gate at the point of storage — it is advisory only, and is bypassed entirely by the direct HTTP write path.

This breaks the intended equality "chunk write timestamp is at least `write_freq` seconds after the previous write" — the field exists, is loaded from the contract, is stored per-write, but is asserted nowhere on the write path itself.

### Impact Explanation
An authenticated StackerDB slot owner (a valid signer for a slot, e.g. any registered signer or hint-replica-fed writer) can write to their own slot at unbounded frequency regardless of the contract's declared `write-freq`, defeating the DoS/anti-spam control the field was designed to provide. Each accepted write is re-broadcast via `StackerDBPushChunk` to the whole network (`poststackerdbchunk.rs:315-324`, `relay.rs:2445-2452`), so a signer can flood the p2p network with an unbounded rate of legitimate, correctly-signed StackerDB chunk broadcasts, consuming bandwidth/storage across all replicating nodes and directly undermining the write-frequency-based DoS mitigation the contract configuration is documented to provide. Because any node that stores the chunk will forward it, this converts a single authenticated writer's disregard for `write_freq` into network-wide amplified propagation of chunk updates faster than the protocol/contract intends.

Severity is bounded by the requirement that the caller already hold a legitimate signer key for at least one slot (not a fully unauthenticated attacker), and the direct consequence is a control-bypass/DoS-amplification issue rather than an authentication bypass or data corruption, but it is a genuine violation of a documented remote/networked invariant enforceable purely by an in-scope, unprivileged (from the write-frequency-control perspective) party.

### Likelihood Explanation
High likelihood of triggering: no special conditions are needed beyond having a valid slot-signer keypair (a normal, expected StackerDB participant, e.g. a stacks-signer instance), and simply submitting `POST /v2/stackerdb/.../chunks` requests back-to-back with monotonically increasing `slot_version` values. There is no rate limiter, cooldown, or timestamp check anywhere in `try_replace_chunk`/`insert_chunk` to stop this, and the existing test suite (`stackslib/src/net/stackerdb/tests/db.rs::test_stackerdb_insert_query_chunks`, whose doc comment even claims it "verifies that they cannot exceed the config-given wall-clock write frequency") does not actually assert this on `try_replace_chunk` — it only exercises `StaleChunk`, `TooManySlotWrites`, and `BadSlotSigner`, confirming the check truly does not exist on the write path.

### Recommendation
In `StackerDBTx::try_replace_chunk` (`stackslib/src/net/stackerdb/db.rs`), before calling `self.insert_chunk(...)`, fetch the existing `slot_validation.write_time` and reject the write if `get_epoch_time_secs() < slot_validation.write_time + self.config.write_freq` (mirroring the logic already present in `StackerDBSync::getchunks`), returning a new `net_error` variant (e.g. `TooFrequentWrite`) that the `poststackerdbchunk.rs` handler maps to a dedicated `StackerDBErrorCodes` entry, so both the RPC endpoint and the sync-storage path in `relay.rs::process_stacker_db_chunks` enforce `write_freq` uniformly.

### Proof of Concept
1. Configure a StackerDB smart contract with `write-freq: u3600` (writes to a slot allowed at most once per hour) and one signer slot owned by key `K`.
2. Using `K`, sign and `POST` a valid chunk to `/v2/stackerdb/<addr>/<contract>/chunks` with `slot_version = 1`. The write succeeds and is broadcast via `StackerDBPushChunk`.
3. Immediately (same second) sign and `POST` a second chunk to the same slot with `slot_version = 2`. Per `try_replace_chunk` (`stackslib/src/net/stackerdb/db.rs:400-438`), the only checks are signature validity, staleness (`2 > 1`, passes), and `max_writes` — there is no `write_freq`/`write_time` check, so this write is accepted and re-broadcast, despite occurring far sooner than the contract's declared 3600-second minimum interval.
4. Repeat step 3 in a tight loop with incrementing `slot_version`: every request succeeds and is re-broadcast, demonstrating that `write_freq` is unenforceable on the actual write path, unlike what `StackerDBSync::getchunks` (`stackslib/src/net/stackerdb/sync.rs:340`) and the test docstring in `stackslib/src/net/stackerdb/tests/db.rs:328` imply.     pub fn try_replace_chunk(
        &self,
        smart_contract: &QualifiedContractIdentifier,
        slot_desc: &SlotMetadata,
        chunk: &[u8],
    ) -> Result<(), net_error> {
        // Check per-replica chunk-size cap.
        if (chunk.len() as u64) > self.config.chunk_size {
            return Err(net_error::StackerDBChunkTooBig(chunk.len()));
        }

        let slot_validation = self
            .get_slot_validation(smart_contract, slot_desc.slot_id)?
            .ok_or(net_error::NoSuchSlot(
                smart_contract.clone(),
                slot_desc.slot_id,
            ))?;

        if !slot_desc.verify(&slot_validation.signer)? {
            return Err(net_error::BadSlotSigner(
                slot_validation.signer,
                slot_desc.slot_id,
            ));
        }
        if slot_desc.slot_version <= slot_validation.version {
            return Err(net_error::StaleChunk {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
            });
        }
        if slot_desc.slot_version > self.config.max_writes {
            return Err(net_error::TooManySlotWrites {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
                max_writes: self.config.max_writes,
            });
        }
        self.insert_chunk(smart_contract, slot_desc, chunk)
    }
