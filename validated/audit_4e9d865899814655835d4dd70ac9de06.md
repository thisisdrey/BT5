### Title
Vote-only-bank enforcement may not be applied to transactions processed through the scheduler-aged path in `Consumer` - (File: core/src/banking_stage/consumer.rs)

### Summary
The external report describes a case where a security guard (`onlySequencer`) present in the single-transaction path is missing from a similarly-purposed batch path (`batchProcessTransaction`), allowing an attacker to bypass the check by routing through the alternate code path. Looking for the same bug class in Agave, `Consumer::process_and_record_transactions` (used for newly-received, freshly-sanitized transactions) explicitly rejects non-vote transactions when the bank is in vote-only mode: [1](#0-0) . The sibling entry point `Consumer::process_and_record_aged_transactions`, which is used to (re)process previously-sanitized/queued transactions (e.g. via the scheduler's aged-transaction recheck/consume flow), does not perform this same `vote_only_bank`/`is_valid_vote_only_transaction` check — it only re-validates nonce/blockhash-age via `resanitize_transaction_minimally`: [2](#0-1) .

### Finding Description
`process_and_record_transactions` builds `check_results` and layers an explicit vote-only-bank filter on top of `bank.check_transactions`, rejecting any non-vote transaction with `TransactionError::SanitizeFailure` when `bank.vote_only_bank()` is true. `process_and_record_aged_transactions`, by contrast, derives its `pre_results` solely from `bank.resanitize_transaction_minimally`, with no equivalent vote-only-mode filter, before calling the same underlying `process_and_record_transactions_with_pre_results`. Both entry points ultimately record into the same PoH/committer path via `process_and_record_transactions_with_pre_results` (`core/src/banking_stage/consumer.rs:199-232`). I was unable to fully confirm, within the remaining tool budget, whether `process_and_record_aged_transactions` is reachable with attacker-supplied non-vote transactions while a bank is actually in vote-only mode (i.e., during the Alpenglow migration window), or whether some earlier stage (e.g. `receive_and_buffer.rs`, which does reference `is_valid_vote_only_transaction`) already filters these out before transactions reach this path.

### Impact Explanation
If reachable, a leader could produce a block during a vote-only-bank window containing non-vote transactions that were never checked against `is_valid_vote_only_transaction`, which — per the consensus rule enforced during replay (`ledger/src/blockstore_processor.rs:1475-1502` and `BlockstoreProcessorError::UserTransactionsInVoteOnlyBank`) — will be rejected by other validators when replaying that block, causing the block to be marked dead. That is a real "invalid recorded block" consequence per the validation criteria.

### Likelihood Explanation
Uncertain/low-to-unproven. Vote-only-bank mode is tied to a narrow, transient window (the Alpenglow migration boundary) rather than being a general steady-state condition, and I could not verify from available context whether `receive_and_buffer.rs`'s existing `is_valid_vote_only_transaction` reference already filters transactions upstream of `process_and_record_aged_transactions`, which would make this a non-issue. Given the rules exclude bootstrap/migration-phase-only issues and I cannot confirm attacker reachability or the absence of an upstream filter, I cannot assert this rises to a concrete, provable vulnerability.

### Recommendation
This is not something I can confidently confirm as exploitable without further code tracing (specifically whether `receive_and_buffer.rs` or the scheduler's container/filtering logic already enforces vote-only-bank restrictions before transactions reach `process_and_record_aged_transactions`). If Devin session access is available, it would be worth verifying this call chain and, if a gap is confirmed, adding the same `bank.vote_only_bank()` / `is_valid_vote_only_transaction` filter to `process_and_record_aged_transactions` as exists in `process_and_record_transactions`.

### Proof of Concept
Not established — reachability and absence of upstream filtering were not confirmed within the available investigation budget.

        &self,
        bank: &Bank,
        txs: &[impl TransactionWithMeta],
        max_ages: &[MaxAge],
        flags: &ExecutionFlags,
    ) -> ProcessTransactionBatchOutput {
        // Need to filter out transactions since they were sanitized earlier.
        // This means that the transaction may cross and epoch boundary (not allowed),
        //  or account lookup tables may have been closed.
        let pre_results = txs.iter().zip(max_ages).map(|(tx, max_age)| {

                tx,
                max_age.sanitized_epoch,
                max_age.alt_invalidation_slot,
            )
        });
        self.process_and_record_transactions_with_pre_results(bank, txs, pre_results, flags)
    }
