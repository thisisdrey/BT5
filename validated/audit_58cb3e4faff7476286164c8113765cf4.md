### Title
Attacker-controlled repository can spoof `@pools/xx/yy/<hex64>.git` naming to be misidentified as a Rails object pool - ([File: internal/gitaly/storage/repository_path.go])

### Summary
`storage.IsRailsPoolRepository` treats any repository whose `RelativePath` matches `@pools/([0-9a-f]{2})/([0-9a-f]{2})/([0-9a-f]{64})\.git$` and whose 64-hex segment starts with the same two 2-hex-byte pairs as a legitimate Rails-managed object pool. Because `CreateRepository` (`internal/gitaly/service/repository/create_repository.go`) only calls `s.locator.ValidateRepository`, which validates path traversal but does not restrict the `@pools/...` naming scheme (that check only exists in the separate `CreateObjectPool` RPC path via `errInvalidPoolDir`), an attacker who can choose an arbitrary `relative_path` in `CreateRepository` can fabricate a path satisfying the regex and prefix check without it ever being a real GitLab-managed pool.

### Finding Description
`IsRailsPoolRepository` (`internal/gitaly/storage/repository_path.go:26-33`) is a naming-convention check, not a check that a repository was actually derived via the Rails pool-creation flow:
```go
func IsRailsPoolRepository(repo Repository) bool {
	matches := railsPoolDirRegexp.FindStringSubmatch(repo.GetRelativePath())
	if matches == nil || !strings.HasPrefix(matches[3], matches[1]+matches[2]) {
		return false
	}
	return true
}
```
An attacker only needs to craft a 64-hex-char string whose first 4 hex chars equal the two 2-hex path segments, e.g. `@pools/ab/cd/abcd<60 more hex chars>.git`, which is trivial to construct deterministically (no cryptographic hash relationship is verified—only a literal prefix match of caller-supplied path components against a substring of the same caller-supplied path).

The actual gatekeeping against this naming scheme exists only in the `CreateObjectPool` RPC's `poolForRequest`/`objectpool.FromProto` path (`internal/gitaly/service/objectpool/util.go`, `errInvalidPoolDir`), not in the generic `CreateRepository` RPC (`internal/gitaly/service/repository/create_repository.go:15-24`), which merely calls `storage.ValidateRepository` (path-traversal/existence checks) before calling `repoutil.Create`. There is no check in `CreateRepository` that rejects `@pools/...`-shaped relative paths for non-pool creation.

### Impact Explanation
`IsPoolRepository` (which OR's `IsRailsPoolRepository` and `IsPraefectPoolRepository`) is consumed by housekeeping's `HeuristicalOptimizationStrategy.ShouldPruneObjects` (`internal/git/housekeeping/optimization_strategy.go:289-297`), which unconditionally skips pruning stale/unreachable loose objects when `IsObjectPool` is true, and by `PruneUnreachableObjects` RPC handling logic that treats object pools specially. An attacker-owned repository disguised via a spoofed `@pools/...` path can permanently opt itself out of garbage collection of unreachable objects, allowing unbounded accumulation of loose objects (storage/resource abuse, DoS via disk exhaustion) and confusing pool bookkeeping/metadata scanning that enumerates paths under `@pools/`.

### Likelihood Explanation
The precondition is that `relative_path` is attacker-influenced when creating a repository via `CreateRepository`, which is plausible in scenarios where relative-path derivation is not fully server-controlled (e.g. custom RPC callers, internal tooling, or non-Rails clients that pass through `relative_path`). Crafting a matching 64-hex string that starts with the required 4-hex prefix is trivial and fully deterministic — no brute-forcing, secret, or race condition needed. Repeatability is total: this always succeeds given the crafted string.

### Recommendation
Do not rely purely on filename convention to determine pool status for housekeeping/pruning decisions. Either: (1) restrict `CreateRepository` (and any other repo-creation path) to reject `relative_path` values matching the reserved `@pools/` naming convention when not going through the dedicated object-pool creation path, mirroring the `errInvalidPoolDir` validation already used by `CreateObjectPool`; and/or (2) have `stats.RepositoryInfoForRepository`/`IsObjectPool` determination rely on an authoritative marker (e.g. a persisted pool record, an on-disk marker file, or database-tracked pool relationship) instead of solely trusting the relative path's naming pattern.

### Proof of Concept
```go
func TestIsRailsPoolRepository_SpoofedNonPoolPath(t *testing.T) {
	crafted := "@pools/ab/cd/" + "abcd" + strings.Repeat("0", 60) + ".git"
	repo := &gitalypb.Repository{RelativePath: crafted}

	// Attacker-created repository (e.g. via CreateRepository with attacker-chosen
	// relative_path) is misidentified as a Rails-managed pool.
	require.True(t, storage.IsRailsPoolRepository(repo))
	require.True(t, storage.IsPoolRepository(repo))
}
```
Follow-on housekeeping test: create a repository through `CreateRepository` with `RelativePath` set to the crafted string, write more than `LooseObjectLimit` stale loose objects into it, run `OptimizeRepository`, and assert (per `HeuristicalOptimizationStrategy.ShouldPruneObjects`) that `pruned_objects` never appears in the logged optimizations, confirming the fabricated path caused pruning to be permanently skipped despite the repository not being an actual Rails pool.
