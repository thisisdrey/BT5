### Title
Heap out-of-bounds read via unchecked extra-field length in ijar central directory parsing - (File: `third_party/ijar/zip.cc`)

### Summary
`InputZipFile::ProcessCentralDirEntry` in `third_party/ijar/zip.cc` parses a ZIP central-directory entry from a memory-mapped, attacker-supplied archive without validating that the declared `extra_field_length` (and the per-record `data_size` inside the Zip64 extra field sub-record) stays within the bounds of the mapped file, unlike the parallel local-file-header path (`ProcessLocalFileEntry`) which calls `EnsureRemaining()` before advancing the cursor.

### Finding Description
`ProcessCentralDirEntry` reads `file_name_length`, `extra_field_length`, and `file_comment_length` directly from attacker-controlled bytes and immediately advances the cursor `p` by these amounts with no check against the mapped file's length: [1](#0-0) 

It then walks the extra-fields region reading a 2-byte `header_id` and a 2-byte `data_size` per record and, for the Zip64 tag, dereferences 8 bytes at `extra` via `get_u8le`, again with no bound check that `extra_p + data_size` (or `extra + 8`) is still inside the mapped extra-fields buffer or the mapped file at all: [2](#0-1) 

Contrast this with the analogous local-file-header parser, which explicitly calls `EnsureRemaining()` before trusting `file_name_length_` / `extra_field_length_` and advancing the pointer: [3](#0-2) 

Because `ProcessCentralDirEntry` has no equivalent `EnsureRemaining` calls, a crafted central directory record with an oversized `extra_field_length` or a Zip64 extra-field `data_size` that exceeds the remaining space of the extra fields (or the whole mmap'd file) causes `get_u2le`/`get_u4le`/`get_u8le` to read past the end of the memory-mapped archive buffer — a heap/mmap out-of-bounds read, the same bug class as CVE-2020-21836 (LibreDWG's `read_2004_section_preview` reading a length-prefixed section without bounds validation).

This code path is reachable whenever ijar (`third_party/ijar/zip_main.cc`'s `extract`/`zipper` tool, or the `PartialZipExtractor` used by the Bazel client's self-extracting installer / `ijar` interface-jar generation in `src/main/cpp/archive_utils.cc`) opens and scans an untrusted ZIP/JAR file supplied via a URL, dependency archive, or similar externally-controlled input.

### Impact Explanation
An out-of-bounds read in a memory-mapped file can crash the process (SIGSEGV) if it crosses a page boundary not mapped, causing denial of service of the build/extraction step, and in principle could leak adjacent heap/mmap memory content into subsequently processed fields (e.g., interpreted as compressed/uncompressed sizes or offsets) if the read stays within a mapped page but past the logical end of file content, though the mapping is normally exactly the file's length via `mmap`, so most overreads are a crash rather than a byte-limited leak.

### Likelihood Explanation
This requires an attacker to supply a malicious ZIP/JAR file (e.g., a compromised `http_archive`/`http_jar` payload before checksum verification runs, or a locally built jar) that is subsequently scanned by the ijar/zipper central-directory parser. Since checksum enforcement in `http_archive` happens on the downloaded byte stream (integrity/sha256) prior to any archive-content trust decisions, and ijar's own parser does not itself validate the byte lengths against the mapped buffer, the flaw is present at the C++ archive-parsing layer whenever it is invoked on adversarial content, independent of whether the download was verified.

### Recommendation
Add `EnsureRemaining`-style bounds checks in `ProcessCentralDirEntry` before trusting `file_name_length`, `extra_field_length`, `file_comment_length`, and before advancing `p`/`extra_p`, mirroring the checks already present in `ProcessLocalFileEntry`. Additionally validate that each extra-field sub-record's `data_size` does not exceed the remaining bytes of the extra-fields region, and that Zip64 8-byte reads stay within that validated region.

### Proof of Concept
A concrete JUnit/`BuildIntegrationTestCase`/shell reproduction was not constructed here; further verification would require building a minimal ZIP with a central-directory record whose `extra_field_length` (or an embedded Zip64 extra-field `data_size`) exceeds the file's actual remaining bytes, then invoking the `zipper`/ijar extraction path (e.g., via `third_party/ijar/test/zip_test.sh`) to confirm a crash or OOB read under ASan. This should be validated by a background engineer with build/test tooling access, since I could not execute code in this environment.
