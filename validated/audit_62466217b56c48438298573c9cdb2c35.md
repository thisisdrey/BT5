### Title
Receipts can be created above `max_receipt_size` after the size check, breaking the size-limit invariant relied on for cross-shard delivery - (File: runtime/runtime/src/congestion_control.rs)

### Summary
This is the same bug class as the External Report: a size cap that is supposed to be enforced end-to-end (there, `MAX_ROLLUP_TX_SIZE` for both L1-enqueued and Sequencer-originated transactions; here, `max_receipt_size` for both the "receipt at creation" path and the "receipt as later mutated/forwarded" path) is only enforced at one point, letting an object that should never exceed the limit slip through and break assumptions made downstream.

### Finding Description
NEAR enforces a hard `max_receipt_size` limit so no single receipt exceeds the configured cap (4 MiB), documented as an invariant in `docs/misc/state_witness_size_limits.md`: "All receipts must be below 4 MiB, otherwise they'll be considered invalid and rejected" [1](#0-0) , with the dedicated error variant `ReceiptValidationError::ReceiptSizeExceeded` [2](#0-1) .

However, the runtime itself acknowledges that receipts can be produced that violate this invariant after the initial size check — e.g. a promise's `output_data_receivers` are attached, or a returned value is wrapped into a data receipt, *after* the size that was validated at creation time, pushing the final on-chain receipt above `max_receipt_size`. The test suite documents this directly: `test_max_receipt_size_promise_return` and `test_max_receipt_size_value_return` are titled "the receipt's size will go above max_receipt_size... The receipt should be rejected, but currently isn't because of a bug" and reference tracked issue near/nearcore#12606 [3](#0-2) [4](#0-3) .

The congestion-control forwarding logic (`try_forward`) explicitly works around this by clamping any oversized receipt's accounted size down to `max_receipt_size` before checking it against the shard's outgoing bandwidth grant, rather than rejecting the oversized receipt: [5](#0-4) 

This mirrors the OP bug exactly: one code path (the initial receipt construction check) enforces the `max_receipt_size` bound, but a second path (post-construction mutation via promise/data-receiver attachment) does not, so an over-limit object reaches the point where hard-limit invariants are assumed to hold (bandwidth accounting for cross-shard forwarding).

### Impact Explanation
Because `try_forward` only *pretends* the receipt is `max_receipt_size` for bandwidth-accounting purposes rather than actually shrinking it, an oversized receipt is still queued and eventually transmitted at its true (larger) size. This can push the real wire size of outgoing receipts for a block past `outgoing_receipts_usual_size_limit` / `outgoing_receipts_big_size_limit`, and past the total `ChunkStateWitness` size budget documented in `docs/misc/state_witness_size_limits.md`, which chunk validators use to decide whether to endorse a chunk. If the actual data size diverges from what accounting assumed, this can produce witness/state divergence between chunk producer and validators, or cause a receipt (and any deposit/token amount carried by it) to remain stuck in the outgoing/buffered-receipt queue indefinitely if it can never fit any bandwidth grant — a permanent-freezing-of-funds scenario analogous to the original "cannot enqueue" bug.

### Likelihood Explanation
This does not require a malicious actor with special privileges — any ordinary contract deployer can trigger it deterministically by writing a contract that returns a large value or creates a promise DAG with an `output_data_receivers` attachment sized close to `max_receipt_size`, exactly as the existing (currently-skipped/failing-assumption) tests `test_max_receipt_size_promise_return` and `test_max_receipt_size_value_return` do. The bug is already known and tracked internally (issue #12606) and partially mitigated at the forwarding layer, but the root cause — receipts being mutated post-size-check — is not fixed at the source.

### Recommendation
Re-validate receipt size after all post-construction mutations (attaching `output_data_receivers`, wrapping returned values into `DataReceipt`) and reject/fail the action if the final receipt exceeds `max_receipt_size`, instead of only clamping the accounted size during forwarding. This restores the invariant "no receipt exceeds `max_receipt_size`" everywhere it's relied upon, rather than patching around it in `try_forward`.

### Proof of Concept
Use the existing repository tests as the PoC, since they already reproduce the condition end-to-end: [6](#0-5) [7](#0-6) 
Both construct a receipt whose validated size is exactly at `max_receipt_size`, then attach additional data (`output_data_receivers` or a returned value) that pushes the final receipt above the limit; the test comments confirm this currently succeeds instead of being rejected. Combined with `try_forward`'s clamp-to-limit workaround for bandwidth accounting [5](#0-4) , the oversized receipt can be forwarded across shards while being accounted as smaller than it truly is.

// A function call will generate a new receipt. Size of this receipt will be equal to
// `max_receipt_size`, it'll pass validation, but then `output_data_receivers` will be modified and
// the receipt's size will go above max_receipt_size. The receipt should be rejected, but currently
// isn't because of a bug (See https://github.com/near/nearcore/issues/12606)
// Runtime shouldn't die when it encounters a receipt with size above `max_receipt_size`.
#[test]
fn test_max_receipt_size_promise_return() {
    init_test_logger();

    let account = create_account_id("account0");
    let account_signer = create_user_test_signer(&account);
    let mut env = TestLoopBuilder::new()
        .enable_rpc()
        .add_user_account(&account, Balance::from_near(10_000))
        .build();

    // Deploy the test contract
    let deploy_contract_tx = SignedTransaction::deploy_contract(
        101,
        &account,
        near_test_contracts::rs_contract().into(),
        &account_signer,
        env.rpc_node().head().last_block_hash,
    );
    env.rpc_runner().run_tx(deploy_contract_tx, Duration::seconds(5));

    // User calls a contract method
    // Contract method creates a DAG with two promises: [A -then-> B]
    // When promise A is executed, it creates a third promise - `C` and does a `promise_return`.
    // The DAG changes to: [C ->then-> B]
    // The receipt for promise C is a maximum size receipt.
    // Adding the `output_data_receivers` to C's receipt makes it go over the size limit.
    let base_receipt_template = Receipt::V0(ReceiptV0 {
        predecessor_id: account.clone(),
        receiver_id: account.clone(),
        receipt_id: CryptoHash::default(),
        receipt: ReceiptEnum::Action(ActionReceipt {
            signer_id: account.clone(),
            signer_public_key: account_signer.public_key().into(),
            gas_price: Balance::ZERO,
            output_data_receivers: vec![],
            input_data_ids: vec![],
            actions: vec![Action::FunctionCall(Box::new(FunctionCallAction {
                method_name: "noop".into(),
                args: vec![],
                gas: Gas::ZERO,
                deposit: Balance::ZERO,
            }))],
        }),
    });
    let base_receipt_template = action_receipt_v1_to_latest(&base_receipt_template);
    let base_receipt_size = borsh::object_length(&base_receipt_template).unwrap();
    let max_receipt_size = 4_194_304;
    let args_size = max_receipt_size - base_receipt_size;

    // Call the contract
    let large_receipt_tx = SignedTransaction::call(
        102,
        account.clone(),
        account.clone(),
        &account_signer,
        Balance::ZERO,
        "max_receipt_size_promise_return_method1".into(),
        format!("{{\"args_size\": {}}}", args_size).into(),
        Gas::from_teragas(300),
        env.rpc_node().head().last_block_hash,
    );
    env.rpc_runner().run_tx(large_receipt_tx, Duration::seconds(5));

    // Make sure that the last promise in the DAG was called
    let assert_test_completed = SignedTransaction::call(
        103,
        account.clone(),
        account,
        &account_signer,
        Balance::ZERO,
        "assert_test_completed".into(),
        "".into(),
        Gas::from_teragas(300),
        env.rpc_node().head().last_block_hash,
    );
    env.rpc_runner().run_tx(assert_test_completed, Duration::seconds(5));

    assert_oversized_receipt_occurred(&env.validator());
}
