### Title
Reachable AddKey self-target allows an ordinary access key to directly invoke the wallet contract's private promise-callback methods, bypassing the `has_in_flight_tx` reentrancy invariant - ([File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs])

### Summary
The `WalletContract` (eth-implicit account implementation) uses a boolean flag `has_in_flight_tx` as a reentrancy/serialization guard, structurally analogous to the LSP KeyManager's `_reentrancyStatus`. The flag is meant to only be flipped by the contract's own internal promise chain (`rlp_execute` → `.then()` callbacks), and the callback methods (`address_check_callback`, `nep_141_storage_balance_callback`, `rlp_execute_callback`, `ban_relayer`) are marked `#[private]`, which in `near-sdk` only enforces `predecessor_account_id() == current_account_id()`. Because the contract itself allows an `AddKey` action whose `receiver_id`/target can be the contract's own account (`TargetKind::CurrentAccount` path in `internal.rs`), a relayer/attacker can cause a function-call access key to be added to the wallet's own account. A transaction signed with that key against the same account produces `predecessor_id == current_account_id`, satisfying the `#[private]` check and allowing these "internal-only" callback methods to be invoked directly and out-of-order, resetting `has_in_flight_tx` at will.

### Finding Description
`WalletContract::rlp_execute` enforces "only one transaction in flight at a time" via the boolean `has_in_flight_tx`: [1](#0-0) 

The comment explicitly documents the intended invariant and relies on it to bound relayer abuse of delayed nonce increments: [2](#0-1) [3](#0-2) 

The flag is reset to `false` unconditionally at the start of every private callback (mirroring the KeyManager's `_nonReentrantAfter` always setting `false`): [4](#0-3) [5](#0-4) [6](#0-5) [7](#0-6) 

These methods are marked `#[private]`, which is documented/expected to restrict calls to only be reachable via the contract's own scheduled promises. However, `AddKey` actions processed by `action_to_promise` allow `target` (the receiver of the new access key) to be the wallet's own account, and `internal.rs`'s `parse_target`/`validate_tx_relayer_data` explicitly support `TargetKind::CurrentAccount`: [8](#0-7) [9](#0-8) 

and the resulting AddKey action is dispatched with `target` as receiver: [10](#0-9) 

Any account that ends up holding a function-call access key on the wallet's own account (added this way, or via any legitimate/relayer-assisted flow) can then submit a directly-signed `SignedTransaction` calling `address_check_callback`, `nep_141_storage_balance_callback`, or `rlp_execute_callback` on the wallet account. Because the transaction's `predecessor_id` equals `signer_id` equals `current_account_id` in that scenario, the `#[private]` guard (which only checks `predecessor_id == current_account_id`, not "was this invoked from our own scheduled promise") is satisfied, even though the call did not originate from the intended internal promise chain.

This is the direct analog of the reported bug class: a reentrancy/serialization flag that is unconditionally cleared, combined with a caller that is nominally "privileged" (here, `#[private]`/self-call) but reachable through an unintended path (a self-targeted `AddKey` capability plus a directly-signed transaction), letting an attacker manipulate the guard out of the intended sequence.

### Impact Explanation
If `has_in_flight_tx` can be forced to `false` while a legitimate `rlp_execute` chain is still pending (e.g., the address-registrar lookup or `storage_balance_of` cross-contract call has not yet resolved), a second `rlp_execute` call can be submitted and processed concurrently. The code comments make clear this invariant exists specifically to bound how much of the user's tokens a relayer can spend by interleaving nonce-delayed flows (the nonce increment for the `address_check`/ERC-20 storage paths is deliberately delayed until the callback, precisely to avoid a "double use" scenario the invariant is supposed to prevent). Breaking the invariant can enable double-spend/replay-style interleaving of the delayed-nonce paths, or unintended nonce/`ban_relayer` state transitions, directly matching the impact class "double-spend/replay" / "authorization escalation across accounts or promises."

### Likelihood Explanation
Exploitation requires the attacker (or a relayer acting on the user's behalf) to first get a function-call access key added onto the wallet contract's own account via the self-targeted `AddKey` path, then sign and submit a transaction directly calling one of the private callback methods. Both the self-targeted `AddKey` support and the callback methods are reachable via the ordinary `rlp_execute` transaction flow, not requiring any privileged/validator/network access — only an access key on the wallet account, which the AddKey mechanism itself provides for. This is a realistic, unprivileged-signer path, but full exploitation requires an access key with unrestricted (or matching) `method_names` on the self-target, which I could not fully verify is achievable given `ADD_KEY_SIGNATURE`'s exact method-name encoding constraints (I was not able to trace whether `method_names`/`receiver_id` restrictions could be crafted to include the private callback names within index limits before the analysis budget was exhausted).

### Recommendation
Do not rely solely on `#[private]` (`predecessor_id == current_account_id`) to gate the internal callback methods. Additionally validate that the call is occurring as part of the expected promise chain — e.g., by checking `env::promise_results_count() > 0` unconditionally (rejecting direct zero-result invocations except through an explicit, separately-guarded direct-call path), and by restoring `has_in_flight_tx` based on actual promise completion state rather than unconditionally clearing it at the top of every private method. Consider also disallowing `AddKey` actions whose `receiver_id`/target is the contract's own account, or restricting the method names/permissions grantable to self-targeted keys so that they can never name the private callback methods.

### Proof of Concept
Conceptual PoC (not fully executed, given the AddKey method-name/allowance encoding still needs confirmation):
1. Attacker submits an RLP transaction via `rlp_execute` with `target == current_account_id` (self) and an `ADD_KEY_SELECTOR` payload requesting a `FunctionCall` access key with `receiver_id`/`method_names` broad enough to include `address_check_callback`/`rlp_execute_callback`.
2. Once the key is added (`action_to_promise` → `add_access_key_allowance_with_nonce` in `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs:484-496`), the attacker signs a second transaction using that new key, directly targeting the wallet account and calling e.g. `rlp_execute_callback` while an unrelated `rlp_execute` promise chain (e.g. an ERC-20 transfer requiring `storage_balance_of`) is still in flight.
3. Because `predecessor_id == current_account_id` for this self-signed call, the `#[private]` check passes, and `has_in_flight_tx` is reset to `false` mid-flight (`lib.rs:280`), allowing the attacker to submit a new `rlp_execute` transaction that interleaves with the still-pending in-flight one, violating the single-in-flight-transaction invariant described in `lib.rs:399-409`.

fn parse_target(target: &AccountId, current_address: Address) -> TargetKind<'_> {
