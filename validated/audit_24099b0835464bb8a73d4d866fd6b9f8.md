### Title
Remotely-reachable `assert!` panic in `validate_blocks_push` on `payload_len == 5` - (File: `stackslib/src/net/chat.rs`)

### Summary
`ConversationP2P::validate_blocks_push` at `chat.rs:2095` starts with a hard `assert!(preamble.payload_len > 5)`, but the wire-level `Preamble` codec only enforces `payload_len >= 5`, leaving a one-value gap (`payload_len == 5`) that is both a valid, fully-deserializable message and a value that fails the assertion. A `StacksMessageType::Blocks(BlocksData{blocks: vec![]})` payload serializes to exactly 5 bytes (1-byte type tag + 4-byte zero-length vector prefix), so an attacker can construct a signed/relayed `StacksMessage` whose preamble declares `payload_len = 5` and whose body is an empty `Blocks` push, which will deserialize successfully and then panic the P2P handling thread when routed to `validate_blocks_push`.

### Finding Description
The broken invariant is between two boundary checks that should agree but don't:
- `Preamble::consensus_deserialize` (`stackslib/src/net/codec.rs:171`) rejects only `payload_len < 5`, explicitly documenting 5 as the legal minimum ("a zero-length vector (4 bytes of 0) plus a type identifier (1 byte)"). [1](#0-0) 
- `validate_blocks_push` (`stackslib/src/net/chat.rs:2095`) requires strictly `payload_len > 5` via a hard `assert!`, not a returned `Err`. [2](#0-1) 

A `BlocksData` payload with an empty `blocks` vector is a completely valid `StacksMessageType::Blocks` value (`StacksMessageID::Blocks = 11`) whose serialized body is exactly 5 bytes: 1 byte for the `Blocks` type discriminant plus a 4-byte zero-length-vector prefix. [3](#0-2) [4](#0-3) 

This message passes every wire-level guard: `Preamble::consensus_deserialize` accepts `payload_len == 5` (not `< 5`), `StacksMessage::consensus_deserialize` only checks an upper bound (`payload_len > MAX_MESSAGE_LEN - PREAMBLE_ENCODED_SIZE`), and `ProtocolFamily::read_payload`/`verify_payload_bytes` only slice exactly `payload_len` bytes and check the signature over those bytes — none of these paths reject `payload_len == 5`. [5](#0-4) [6](#0-5) 

Once such a message is fully parsed and signature-verified as a legitimate relayed/pushed `Blocks` message, the conversation handler routes it to `validate_blocks_push`, which immediately executes `assert!(preamble.payload_len > 5)`. Because `payload_len == 5` satisfies every prior check but fails this strict inequality, the assertion fails and unwinds/aborts the calling thread — a hard panic rather than the graceful `net_error::InvalidMessage` that the rest of the function (and its microblocks twin `validate_microblocks_push`, same pattern at `chat.rs:2135`) is otherwise designed to return. [7](#0-6) 

The existing guards (signature verification, `MAX_MESSAGE_LEN` checks, relay-cycle checks) all operate on values that are agnostic to this specific off-by-one boundary; none of them special-case `payload_len == 5`, so nothing intercepts this crafted message before it reaches the assert.

### Impact Explanation
Any remote peer that can complete a handshake (or relay through an already-connected peer) can send one `StacksMessage` carrying `preamble.payload_len = 5` and `payload = StacksMessageType::Blocks(BlocksData{blocks: vec![]})`. This triggers a Rust `assert!` panic inside the conversation's message-processing routine, crashing/aborting the thread handling that P2P connection (and, depending on panic-handling configuration, potentially the whole process). This is a single-message, repeatable remote crash / unauthenticated DoS, matching the "Critical - remote crash/unauthenticated DoS from few messages" category.

### Likelihood Explanation
- No privileged role, secret, or special peer state is required — only a completed P2P handshake with the target node (as needed for any post-handshake message, e.g. `Blocks` push).
- The attacker fully controls `preamble.payload_len` and the payload bytes, and can trivially construct the 5-byte `Blocks` body.
- Signature verification does not filter on `payload_len` value, only that the signature matches the bytes actually sent, so a properly signed message with `payload_len == 5` is accepted as authentic.
- The attack is a single message and is deterministically repeatable against any listening P2P peer.

### Recommendation
Replace the hard `assert!(preamble.payload_len > 5)` in both `validate_blocks_push` (`chat.rs:2095`) and `validate_microblocks_push` (`chat.rs:2135`) with a graceful check that returns `Err(net_error::InvalidMessage)` (incrementing `self.stats.msgs_err` as done elsewhere in these functions) when `payload_len <= 5`, consistent with how other malformed-message conditions in this file are handled.

### Proof of Concept
In `stackslib::net::chat::tests`, construct a `StacksMessage` via the existing `sign_relay_message` helper (as used in nearby tests around `chat.rs:7008`) with payload `StacksMessageType::Blocks(BlocksData{blocks: vec![]})`, then force `msg.preamble.payload_len = 5` (matching the true encoded length of the empty-blocks body) instead of an invalid value like `10`. Feed this preamble/relayers into `convo.validate_blocks_push(&net, &msg.preamble, msg.relayers.clone())` wrapped in `std::panic::catch_unwind`, and assert that the call panics with the message `"assertion failed: preamble.payload_len > 5"` at `chat.rs:2095`, in contrast to the existing test at `chat.rs:7016-7021` which expects a graceful `net_error::InvalidMessage` for other malformed lengths.
