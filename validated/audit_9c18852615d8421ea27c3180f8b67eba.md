### Title
Anti-replay window `Check`-then-`Update` race allows a captured packet to be decrypted and processed twice before replay protection lands — ([File: connection_state.go])

### Summary
The external report describes a fee calculation that trusts a value (`PeerPoolInfo.balance`) which can be stale by the time it is actually used, because there is a time gap between reading the value and the moment the destination state is truly known ("asynchronicity"). The reachable analog in nebula is the anti-replay window in `ConnectionState.Decrypt`/`VerifyRelay`: the window state is read (`Check`) and released, an expensive decrypt runs unlocked, and only afterward is the window updated (`Update`). Between the `Check` and `Update` calls the "already seen" bit for that message counter has not yet been committed, so a second copy of the same on-wire packet arriving in that gap sees the same stale (not-yet-updated) window state and is treated as fresh.

### Finding Description
`ConnectionState.Decrypt` in [1](#0-0)  performs the anti-replay check and the anti-replay commit as two separate, unlocked-in-between operations:

1. `cs.decryptLock.Lock(); result := cs.window.Check(l, messageCounter); cs.decryptLock.Unlock()`
2. AEAD decrypt (`cs.dKey.DecryptDanger`) runs with no lock held.
3. `cs.decryptLock.Lock(); result = cs.window.Update(l, messageCounter); cs.decryptLock.Unlock()`

`Bits.Check` only inspects whether the counter's bit is already set [2](#0-1) ; the bit is only actually marked as seen inside `Update` [3](#0-2) . Because `Check` and `Update` are not committed atomically as a single locked operation, an attacker who captures one legitimate ciphertext packet on the wire (fully possible without holding any CA-signed certificate — this is exactly the passive-capture/replay threat the anti-replay window exists to defend against) can inject a duplicate of that packet concurrently with the original still in flight through the network stack. If the two copies are processed on different goroutines (readOutsidePackets is invoked per receive, and Interface read paths can run packet processing in parallel across workers), both copies can pass `Check` before either calls `Update`, since `Check` only reads state that `Update` — not yet called by the other goroutine — would have set. Both goroutines then successfully call `DecryptDanger` with the same valid nonce/counter and get a valid plaintext (replay of a genuine packet decrypts correctly), and both proceed into `readOutsidePackets`'s post-decrypt logic (`handleHostRoaming`, `connectionManager.In`, and dispatch by `h.Type`, including delivery to the tun device for `header.Message`) at [4](#0-3) . Only one of the two `Update` calls will return `true`; the other returns `false` and its own `Decrypt` call returns `ErrAlreadySeen`, but that happens *after* the vulnerable goroutine already decrypted and, depending on timing, may have already delivered the plaintext.

This exactly mirrors the report's "eqFee calculated with potentially outdated balance deficit zone" root cause: a decision (the replay-window admission decision) is made against state that can become stale by the time the actual state-changing operation is confirmed, because the check and the commit are not atomic with respect to the actual protected action.

### Impact Explanation
Successful exploitation lets an attacker replay one previously-observed, legitimately-encrypted packet so that it is decrypted and delivered a second time despite Nebula's anti-replay window being designed specifically to prevent this. This is a genuine replay bypass of the anti-replay/authentication guarantees of the transport (not merely a performance or accounting bug): a captured control-plane packet (e.g., `header.Test`/`TestRequest` triggering an echoed reply, or a `header.CloseTunnel`) or a data-plane packet could be re-delivered into the tunnel's processing pipeline. The severity is bounded by the fact that this only works on a race window and only replays a packet the attacker already captured (it does not forge new plaintext or break confidentiality), but it is a concrete violation of the anti-replay contract that the `Bits` window and `ReplayWindow` constant exist to enforce [5](#0-4) .

### Likelihood Explanation
Requires the attacker to be positioned to capture and near-simultaneously re-inject a ciphertext packet over UDP (no valid certificate needed — this is purely an outsider-observer capability against already-established tunnels) and requires the two copies to be processed by the interface's packet-reading goroutines close enough in time to land inside the unlocked gap between `Check` and `Update`. This is a narrow race window per attempt, but the attacker can retry/duplicate injection repeatedly to increase the chance of hitting the window, and Nebula explicitly runs multiple reader routines per interface, making concurrent processing of duplicate packets plausible.

### Recommendation
Make the replay-window admission check-and-commit atomic with respect to decryption: either (a) hold `decryptLock` across the full `Check` → `Decrypt` → `Update` sequence (accepting the reduced parallelism), or (b) provide a single combined `Bits` primitive (e.g., `CheckAndReserve`) that atomically marks the counter as "provisionally consumed" before decryption begins, rolling it back only on decrypt failure, so that a second copy of the same counter can never pass admission while the first is still being processed.

### Proof of Concept
1. Establish a tunnel between two peers and let one legitimate data-plane packet be captured off the wire (e.g. via router/tap in the e2e test harness, similar to `TestRelayReplayProtection` in `e2e/tunnels_test.go` which already demonstrates capture-and-reinject tooling for relay frames [6](#0-5) , but targeting a direct (non-relay) tunnel instead of a relay).
2. Inject two copies of the exact same captured UDP packet at (as close to) the same instant, from two separate goroutines, targeting the interface's UDP receive path so that both invoke `readOutsidePackets` → `ConnectionState.Decrypt` concurrently.
3. Instrument/patch `ConnectionState.Decrypt` (or add a test-only delay in `DecryptDanger`) to widen the window between `Check` and `Update` to reliably demonstrate that both concurrent calls return a non-error, valid plaintext (i.e., both pass `Check` before either calls `Update`), proving the window is not atomically consulted-and-committed.

Note: verifying the exact reachable degree of goroutine concurrency on the UDP receive path (number of reader workers per `Interface`, and whether they can dispatch the same connection's packets to different goroutines simultaneously) was not conclusively confirmed within the available context; a full confirmation would require inspecting the UDP listener/reader setup code, which was not retrieved in this session.

func (cs *ConnectionState) Decrypt(l *slog.Logger, messageCounter uint64, out []byte, packet []byte, nb []byte) ([]byte, error) {
	var err error
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}

	out, err = cs.dKey.DecryptDanger(out, packet[:header.Len], packet[header.Len:], messageCounter, nb)
	if err != nil {
		return nil, err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}
	return out, nil
}

// Check returns true if i is within (or way out in front of) the window, and not a replay
func (b *Bits) Check(l *slog.Logger, i uint64) bool {
	// If i is the next number, return true.
	if i > b.current {
		return true
	}

	if b.strictlyWithinWindow(i) {
		return !b.get(i)
	}

	// Not within the window
	if l.Enabled(context.Background(), slog.LevelDebug) {
		l.Debug("rejected a packet (top)", "current", b.current, "incoming", i)
	}
	return false
}

func (b *Bits) Update(l *slog.Logger, i uint64) bool {
	// Fast path: i is the next expected counter. Split out so the function
	// stays small and avoids paying for the slow paths' slog argument-build
	// stack frame on every call. The bit read/test/write is inlined to
	// touch the backing word once.
	if i == b.current+1 {
		pos := i & b.lengthMask
		word := pos >> 6
		mask := uint64(1) << (pos & 63)
		w := b.bits[word]
		if i > b.length && w&mask == 0 {
			b.lostCounter.Inc(1)
		}
		b.bits[word] = w | mask
		b.current = i
		return true
	}
	return b.updateSlow(l, i)
}
