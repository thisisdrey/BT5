### Title
Dust-transfer griefing fills victim's `depositTokensOfAccount`/`debtTokensOfAccount` up to `MAX_TOKENS_PER_USER`, blocking all new collateral deposits and debt positions - (File: contracts/Pool.sol)

### Summary
Analogous to CVE-2022-0396 — where crafted TCP streams leave connections in `CLOSE_WAIT` indefinitely, consuming slots that are never cleaned up — `Pool` keeps a per-account enumerable set of deposit/debt tokens that is only cleaned when the balance reaches exactly zero. An unprivileged attacker can "half-close" a victim's account by transferring 1 wei of each `DepositToken` to them, permanently occupying slots in `depositTokensOfAccount`. Once `debtTokensOfAccount.length + depositTokensOfAccount.length >= MAX_TOKENS_PER_USER (30)`, the `onlyIfAdditionWillNotReachMaxTokens` modifier makes `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` revert with `UserReachedMaxTokens`, DoS-ing every code path that registers a new token for the victim — just as BIND never releases the lingering connection.

### Finding Description
`Pool.addToDepositTokensOfAccount` and `addToDebtTokensOfAccount` are gated by `onlyIfAdditionWillNotReachMaxTokens`, which reverts once the account holds 30 distinct tokens (`contracts/Pool.sol:143-148`). Registration is triggered unconditionally on the recipient side whenever a balance goes from 0 to positive:

- `DepositToken._transfer` calls `pool.addToDepositTokensOfAccount(recipient_)` when `_recipientBalanceBefore == 0 && amount_ > 0` (`contracts/DepositToken.sol:517-520`). `_transfer` only enforces `_revertIfLocked` on the sender — there is no opt-in, no minimum amount, and no way for a recipient to refuse an incoming transfer.
- `DepositToken._mint` performs the same registration on fresh deposits (`contracts/DepositToken.sol:485-488`), as does `DebtToken` issuance for new debt tokens.

Attack steps:
1. Attacker deposits a minimal amount of collateral into each of the pool's deposit tokens (or acquires dust balances otherwise), obtaining `msdTOKEN` balances.
2. Attacker calls `depositToken.transfer(victim, 1)` for each token. Each call passes `_revertIfLocked` (attacker has no debt) and appends the token to the victim's `depositTokensOfAccount` via `addToDepositTokensOfAccount`.
3. After ~30 dust transfers (attacker may need to leave the victim's existing token count room), the victim's combined list length hits `MAX_TOKENS_PER_USER`.
4. Every subsequent action that would register a *new* token for the victim reverts: `deposit()` into a collateral the victim doesn't already hold, `mint()`/`issue()` of a new synthetic (which registers the `DebtToken` via `addToDebtTokensOfAccount`), `SmartFarmingManager.leverage` depositing a new collateral on the victim's behalf, `NativeTokenGateway`/`VesperGateway` deposits to the victim, and even a liquidator's `seize` if routed such that a new token is credited — all revert with `UserReachedMaxTokens`.

Like the CVE's `CLOSE_WAIT` sockets, these slots are never released by the flow that created them: the entries persist until the victim expends gas to transfer each dust balance back out to zero (or an admin removes a token).

### Impact Explanation
Temporary freezing of funds / liveness degradation of the victim's position. While the cap is saturated, the victim cannot:
- deposit any new collateral type (including to rescue an underwater position with a different asset),
- open a debt position in a new synthetic asset,
- receive any new deposit token (all incoming `transfer`/`deposit` of a token they don't already hold revert),
- use leverage/one-click flows that would credit a new token.

If the victim's position is near liquidation, this can prevent them from topping up with a different collateral and force an avoidable liquidation. The attacker cost is only the dust value plus gas; the victim must pay gas to manually clean up to 30 entries (each requiring the balance to hit exactly 0) before normal operation resumes.

### Likelihood Explanation
- Fully permissionless: `DepositToken.transfer` is a public ERC-20 path; any EOA can execute it with no privileged role.
- No timing, oracle, or flash-loan requirement; the attack is persistent once executed and can be front-run/renewed after the victim cleans up.
- Cost scales with the number of registered deposit tokens the victim doesn't already hold (≤ 30 dust deposits + transfers). On pools with several collaterals and debt tokens, saturation is cheap.
- Limitation: the victim can self-recover by zeroing out dust balances (each dust token's `unlockedBalanceOf` is essentially the full dust amount since it contributes to issuable capacity), so it is a temporary rather than permanent freeze — matching the Medium (5.3) severity of the source CVE.

### Recommendation
- Only register tokens in `depositTokensOfAccount`/`debtTokensOfAccount` on protocol-initiated actions (e.g., inside `deposit()`/`_mint` and debt issuance), not on plain ERC-20 `transfer`/`transferFrom` to arbitrary recipients; or
- Introduce a minimum (non-dust) threshold for auto-registration, or an opt-in/whitelist mechanism for receiving new deposit tokens; or
- Allow anyone to call a `removeFromDepositTokensOfAccount(account, token)`-style cleanup that sweeps dust balances so recovery isn't per-victim interactive; at minimum, document the attack so integrators can batch-clean accounts.

### Proof of Concept
Hardhat-style reproduction (fork or local deployment with ≥2 registered `DepositToken`s):

```ts
// attacker: acquire dust of each deposit token
for (const dt of depositTokens) {
  await dt.deposit(1, attacker.address);          // 1 wei collateral -> 1 wei msdTOKEN
}
const victimCount = await pool.getDepositTokensOfAccount(victim.address);
const free = (await pool.MAX_TOKENS_PER_USER())
  .sub(victimCount)
  .sub(await pool.getDebtTokensOfAccount(victim.address).then(a => a.length));

// saturate victim's per-account set
for (let i = 0; i < free.toNumber(); i++) {
  await depositTokens[i].connect(attacker).transfer(victim.address, 1);
}

// victim can no longer deposit a collateral type they don't already hold
await expect(
  newDepositToken.connect(victim).deposit(parseEther('10'), victim.address)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');

// nor open a new debt position (addToDebtTokensOfAccount reverts inside issue)
await expect(
  newDebtToken.connect(victim).issue(1, victim.address)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');

// recovery requires victim to sweep each dust balance to zero
await depositTokens[0].connect(victim).transfer(attacker.address, 1);
```
