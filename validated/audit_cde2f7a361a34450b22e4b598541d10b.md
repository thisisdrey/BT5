### Title
Floating-point precision loss in legacy `ExchangeProcessor` allows repeated small `ExchangeTransactionContract` trades to drain a TRX/TRC10 exchange pair below its true invariant - (File: `chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java`)

### Summary
The EOSreel report describes an attacker deploying an attack contract and combining multiple accounts to repeatedly interact with the victim contract, exploiting an accumulation/rounding weakness rather than a single-shot logic flaw. The closest reachable analog in java-tron is the on-chain Bancor-style token exchange (`ExchangeCreate`/`ExchangeInject`/`ExchangeTransaction` contracts), whose default ("legacy") pricing math uses `double` arithmetic with no post-condition invariant check, unlike the newer "hardened" `BigDecimal`-based path.

### Finding Description
`ExchangeTransactionActuator.execute` computes the output amount via `ExchangeCapsule.transaction(tokenID, tokenQuant, useStrictMath, hardenedCalc)` [1](#0-0) . Inside `ExchangeCapsule.transaction`, when `hardenedCalc` is false (the legacy/default processor), the code updates `newFirstTokenBalance`/`newSecondTokenBalance` with plain `long` arithmetic and — critically — the non-negative invariant check is gated behind `hardenedCalc`: [2](#0-1) 

The legacy `ExchangeProcessor.exchange` computes the relay/output quantities using `double` and `Math.pow`, an inherently imprecise floating-point Bancor-like formula: [3](#0-2) 

By contrast, the "hardened" `SafeExchangeProcessor` uses `BigDecimal` with explicit rounding and `StrictMathWrapper.addExact/subtractExact`, and `ExchangeCapsule.transaction` only enforces `newFirstTokenBalance < 0 || newSecondTokenBalance < 0` validation in that hardened branch [4](#0-3) . The test `testTransactionLegacyVsHardenedProcessorSelection` explicitly documents that legacy and hardened results can differ by ±1 unit due to "BigDecimal vs double precision" [5](#0-4) , confirming the legacy path is measurably imprecise and, by design of the code, unguarded against balance depletion.

Whether hardened mode is enabled is governed by a dynamic/committee-proposal flag (`AllowHardenExchangeCalculation`), meaning on any deployment where this proposal has not been activated, every `ExchangeTransactionContract`/`ExchangeInjectContract` execution uses the unguarded, floating-point legacy path [6](#0-5) . Because a single unprivileged transaction broadcaster can create an exchange pair (or interact with an existing one) and repeatedly issue small `ExchangeTransactionContract` trades — optionally split across multiple colluding accounts to stay under any spam/anti-sniping heuristics — repeated floating-point truncation across `exchangeToSupply`/`exchangeFromSupply` (both cast final results to `long` via `(long) issuedSupply` / `(long) exchangeBalance`, discarding fractional remainders each call) can be exploited over many iterations to skew the pool's `firstTokenBalance`/`secondTokenBalance` state away from the true invariant, similar in spirit to the "combine multiple accounts, many small operations" pattern described in the EOSreel report.

### Impact Explanation
If repeated legacy-path trades can be steered to consistently favor the attacker (via rounding direction bias in the `double`-based power function), the attacker can extract more value from the pool than they deposit, progressively depleting the counterparty token's balance in the exchange — an unbacked-balance / fund-drain condition affecting all liquidity in that TRX/TRC10 exchange pair. This is a Medium-severity issue since it requires attacker-controlled capital-in-the-loop (self-funded round trips) and many transactions to accumulate meaningfully, but it is a real reachable resource-theft path on any actuator invocation with `hardenedCalc=false`.

### Likelihood Explanation
Reachable by any unprivileged account with enough TRX to pay a trivial exchange fee (`calcFee()` returns 0 for `ExchangeTransactionActuator`) [7](#0-6) , requiring only that `AllowHardenExchangeCalculation` remains unset (the historical/default state before the hardening was introduced). Splitting activity across multiple accounts (as in the EOSreel pattern) also avoids single-account balance/order-book heuristics.

### Recommendation
- Make the `BigDecimal`/`StrictMathWrapper`-based `SafeExchangeProcessor` (hardened) path the mandatory, non-optional computation for all exchange contracts, removing the legacy `double`-based `ExchangeProcessor` entirely, or
- Enforce the same non-negative post-condition invariant check (`newFirstTokenBalance < 0 || newSecondTokenBalance < 0`) unconditionally, regardless of `hardenedCalc`, in `ExchangeCapsule.transaction`.
- Add cumulative invariant/reserve monitoring (e.g., constant-product-style checks) independent of the specific relay math used, so precision drift cannot silently deplete a pool over many transactions.

### Proof of Concept
Conceptual, not executable against a live network without further verification of exact rounding bias:
1. Create (or select) a low-liquidity `Exchange` pair via `ExchangeCreateContract`.
2. From account A, repeatedly submit small `ExchangeTransactionContract` trades (sell token X, buy token Y) sized to maximize floor/truncation loss in `exchangeToSupply`/`exchangeFromSupply`.
3. From account B (colluding), submit the reverse trade to restore the price, again benefiting from truncation bias.
4. Repeat over many transactions/blocks; measure whether the sum of `firstTokenBalance + secondTokenBalance` value extracted by A+B exceeds the theoretical invariant compared to running the same sequence with `hardenedCalc=true`, using `ExchangeCapsuleTest.testTransactionLegacyVsHardenedProcessorSelection`-style harnesses as a template [5](#0-4)  to quantify the per-call ±1-unit drift and its cumulative effect over N iterations.

Note: I was not able to fully confirm within the available index whether `AllowHardenExchangeCalculation` is enabled by default on current mainnet/production configurations (the default value in `DynamicPropertiesStore` was not directly inspected). This affects whether the legacy unguarded path is actually reachable today versus only historically; a Devin session with full repo/config access would be needed to verify the current default and any already-deployed committee proposal activating hardening.

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }

  @Test
  public void testTransactionLegacyVsHardenedProcessorSelection() throws Exception {
    // Same input produces deterministic results in both modes.
    ExchangeCapsule legacy = new ExchangeCapsule(
        ByteString.copyFromUtf8("owner"), 100L, 0L,
        "abc".getBytes(), "def".getBytes());
    legacy.setBalance(100_000_000L, 100_000_000L);
    long legacyResult = legacy.transaction("abc".getBytes(), 1_000_000L, true, false);

    ExchangeCapsule hardened = new ExchangeCapsule(
        ByteString.copyFromUtf8("owner"), 101L, 0L,
        "abc".getBytes(), "def".getBytes());
    hardened.setBalance(100_000_000L, 100_000_000L);
    long hardenedResult = hardened.transaction("abc".getBytes(), 1_000_000L, true, true);

    Assert.assertTrue("Both must return positive", legacyResult > 0 && hardenedResult > 0);
    Assert.assertTrue("Hardened must not exceed pool",
        hardenedResult <= 100_000_000L);
    // Allow ±1 difference due to BigDecimal vs double precision
    Assert.assertTrue("Results should be within 1 unit",
        StrictMathWrapper.abs(legacyResult - hardenedResult) <= 1);
  }
