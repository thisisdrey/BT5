### Title
Unbounded array allocation from attacker-controlled DataWord length in TVM precompile input parsing causes OOM node crash - ([File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java])

### Summary
`PrecompiledContracts.extractBytesArray()` and `extractBytes32Array()` read an array-length field directly out of the raw calldata `DataWord` supplied by the caller and immediately allocate a Java array sized by that untrusted value — with no upper bound check and no energy/resource accounting performed before the allocation happens. This mirrors the Netty SNI bug class: a tiny, cheaply-crafted input field drives an enormous, unconditional pre-allocation performed before any validation or size limiting.

### Finding Description
`extractBytesArray` takes the array length straight from decoded calldata words and allocates a Java object array of that size before doing anything else: [1](#0-0)

```java
  }
  int len = words[offset].intValueSafe();
  byte[][] bytesArray = new byte[len][];
  ...
```

and `extractBytes32Array` does the same thing one level earlier: [2](#0-1) 

```java
private static byte[][] extractBytes32Array(DataWord[] words, int offset) {
  int len = words[offset].intValueSafe();
  byte[][] bytes32Array = new byte[len][];
  ...
```

`len` comes from `DataWord.intValueSafe()`, which converts an attacker-controlled 32-byte calldata word into a safely-clamped `int`, i.e. it can return values as large as `Integer.MAX_VALUE`. Nothing in either method bounds `len` against the actual size of `words`/`data`, against a configured maximum, or against the gas/energy already charged for the precompile call before the array is allocated. A single 32-byte calldata word (the length slot) is enough to request an array with up to ~2.1 billion reference slots (~17 GB on a 64-bit JVM for the reference array alone), analogous to the Netty case where a handful of attacker bytes (`handshakeLength`) drove an eager, unguarded `ctx.alloc().buffer(handshakeLength)` allocation before any timeout/limit was enforced.

These helpers are used to decode the batched-signature/multi-signature inputs consumed by the `BatchValidateSign`/`ValidateMultiSign` precompiled contracts that are reachable from ordinary smart-contract execution (any contract that calls the corresponding precompile address via a normal TVM `CALL`), i.e. from a single signed, unprivileged transaction.

### Impact Explanation
Because full nodes deterministically execute every contract-invoking transaction to validate and apply blocks, a malicious contract call that reaches `extractBytesArray`/`extractBytes32Array` with an oversized length word forces every validating node to attempt the same huge allocation. On a JVM this either throws `OutOfMemoryError` (crashing/halting the node process for the block-application/TVM execution thread) or induces severe GC pressure/DoS across all nodes that process the transaction, i.e., every full node and witness that must apply the block. This is a node crash/halt reachable from a single unprivileged contract call, matching the "node crash or halt" acceptance criterion.

### Likelihood Explanation
The call path requires only deploying/invoking a contract that calls the `BatchValidateSign`/`ValidateMultiSign` precompiled contract address with crafted calldata setting the length word to a large value — no special privileges, no SR/witness/peer position, and no network-level access are needed, only the ability to broadcast a normal signed transaction that triggers a `CALL` to the precompile. The attack input itself is tiny (well under the transaction size limits), so the cost/attempt ratio strongly favors the attacker, analogous to the "nine attacker bytes" characteristic of the original CVE.

### Recommendation
Bound `len` in both `extractBytesArray` and `extractBytes32Array` against a sane maximum (e.g., the remaining `words`/`data` length, or a hard cap consistent with the maximum calldata size already enforced elsewhere) before performing the allocation, and reject/charge energy proportional to the requested size prior to allocating memory, mirroring the fix pattern of validating length against a configured limit before buffer allocation (as done for the Netty `maxClientHelloLength` guard).

### Proof of Concept
1. Deploy or call a contract that performs a `CALL`/`STATICCALL` to the `BatchValidateSign` (or `ValidateMultiSign`) precompiled contract address.
2. Craft calldata so that the length word consumed at the `offset` used by `extractBytesArray`/`extractBytes32Array` decodes (via `DataWord.intValueSafe()`) to a very large value (e.g., close to `Integer.MAX_VALUE`).
3. Broadcast the transaction; when nodes execute the TVM call and reach `new byte[len][]`, the JVM attempts a multi-gigabyte allocation, producing `OutOfMemoryError`/severe resource exhaustion on every node that validates/applies the transaction. [3](#0-2)
