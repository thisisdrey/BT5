### Title
Unauthenticated remote DoS via `POST /shutdown` to signer event-listener endpoint - ([File: libsigner/src/events.rs])

### Summary
The signer's `SignerEventReceiver::next_event` handles `POST /shutdown` by unconditionally setting the stop signal and terminating the event loop, with no authentication, secret, or source-address check. Any party able to reach the bound event-listener endpoint can send this exact request and permanently stop the signer's event-processing loop.

### Finding Description
`SignerStopSignaler::send` (the legitimate internal caller) simply connects to `self.local_addr` and issues `POST /shutdown HTTP/1.1` with no signature, token, or shared secret in the request [1](#0-0) . On the receiving side, `next_event` dispatches purely on `request.url() == "/shutdown"` with no verification of any credential, caller identity, or origin before calling `event_receiver.stop_signal.store(true, Ordering::SeqCst)` and returning `Err(EventError::Terminated)` [2](#0-1) . That `Terminated` error is treated by `main_loop` as an intentional, unrecoverable exit condition, causing the entire event-receiver loop (and thus the thread that translates node HTTP events into signer messages) to break for good [3](#0-2) . There is no equality check tying the request to the specific stop-signaler instance, no secret comparison, and no restriction to loopback — the only "gate" is a string comparison on the URL path, which any TCP client that completes the HTTP request can satisfy.

### Impact Explanation
Any remote/unprivileged party that can open a TCP connection to the signer's event-listener bind address can send a single, trivially crafted `POST /shutdown` request and permanently disable that signer's event-receiver thread, cutting it off from further block proposals, burn-block events, and StackerDB chunk notifications until the operator restarts the signer process. This is a repeatable, single-message, unauthenticated DoS against a signer node, which matches the "Critical - remote crash/unauthenticated DoS from few messages" category if the endpoint is reachable by an untrusted network party.

### Likelihood Explanation
Exploitability is entirely gated on network reachability of the event-receiver bind address configured for the signer (`node.event_observer`/signer event endpoint). I was unable to fully confirm within this session, from the available code/context, what the default bind address is for this endpoint in the shipped configuration (e.g., whether it is restricted to `127.0.0.1` by default or can be configured to listen on a non-loopback interface) — the config lookup in `stacks-signer/src/config.rs` and monitoring server code turned up in search results but I did not get to inspect the exact default/bind logic before running out of iterations. If the endpoint is bound to loopback only by default, this finding is not remotely exploitable by an unprivileged network attacker per the threat model, since local access is out of scope. If the endpoint can be/is configured to listen on a non-loopback address reachable by other network participants, the attack requires no credentials and costs a single TCP connection plus one HTTP request.

### Recommendation
Require a shared secret/token (or restrict the listener to loopback and rely on an authenticated reverse proxy) before honoring `/shutdown`; e.g., generate a random per-process token at `bind()` time, include it in `SignerStopSignaler`, and check it (constant-time) in `next_event` before storing the stop signal.

### Proof of Concept
Because the reachability of the event-listener bind address could not be confirmed in this session, a definitive PoC demonstrating remote (non-loopback) exploitability cannot be produced with confidence. A conceptual Rust test would: bind a `SignerEventReceiver` via `bind()`, spawn `main_loop()` in a thread, open a raw `TcpStream` from a "remote" socket to the bound address, write the literal bytes `POST /shutdown HTTP/1.1\r\nHost: ...\r\nConnection: close\r\nContent-Length: 0\r\n\r\n`, and then assert `is_stopped() == true` and that a subsequent legitimate `POST /stackerdb_chunks` is no longer processed — confirming that an unauthenticated actor can end the loop. Whether this constitutes a network-relevant vulnerability depends on confirming the listener is remotely bindable/reachable, which requires further investigation into `stacks-signer/src/config.rs` bind-address defaults that I did not complete.
