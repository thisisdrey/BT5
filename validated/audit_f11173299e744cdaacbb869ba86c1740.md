### Title
Silent BigInteger-to-`long` truncation in `MarketUtils.multiplyAndDivide` can corrupt market order settlement amounts - ([File: chainbase/src/main/java/org/tron/core/capsule/utils/MarketUtils.java])

### Summary
`MarketUtils.multiplyAndDivide(a, b, c, disableMath)` mirrors the reported Opyn bug (`(_quantity * 1e18) / _price` overflow): when `a * b` overflows a `long`, the method falls back to `BigInteger` arithmetic, but converts the final `BigInteger` result back to `long` using `.longValue()` instead of `.longValueExact()`. `BigInteger.longValue()` silently truncates/wraps out-of-range values instead of throwing, so a legitimately huge intermediate product divided by a very small divisor can produce an incorrect (wrapped, even negative) `long` result with no exception raised.

### Finding Description
`multiplyAndDivide` is defined at: [1](#0-0) 

```
public static long multiplyAndDivide(long a, long b, long c, boolean disableMath) {
  try {
    long tmp = multiplyExact(a, b, disableMath);
    return floorDiv(tmp, c, disableMath);
  } catch (ArithmeticException ex) {
    // do nothing here, because we will use BigInteger to compute again
  }
  BigInteger aBig = BigInteger.valueOf(a);
  BigInteger bBig = BigInteger.valueOf(b);
  BigInteger cBig = BigInteger.valueOf(c);
  return aBig.multiply(bBig).divide(cBig).longValue();
}
```

This function is called by `MarketSellAssetActuator.matchSingleOrder` — the core settlement routine invoked whenever a `MarketSellAssetContract` transaction matches against resting orders — to compute both the taker's and maker's fill amounts: [2](#0-1) [3](#0-2) [4](#0-3) 

The only bound placed on the operands is `dynamicStore.getMarketQuantityLimit()`, enforced in `validate()`: [5](#0-4) 

That bound only limits each individual order's `sellTokenQuantity`/`buyTokenQuantity`; nothing prevents a low value for `makerBuyQuantity` (`c`) combined with high values for `a`/`b` up to the quantity limit each — I was unable to confirm the exact numeric value of `getMarketQuantityLimit()` (grep found no literal default assignment in the indexed portion of `DynamicPropertiesStore.java`), so I cannot state with certainty whether the configured limit alone makes `a*b` exceed `Long.MAX_VALUE` (~9.22e18) in production. If the limit is large enough (e.g. any value above roughly 3.03e9, since limit² would then exceed Long.MAX_VALUE) this overflow path becomes reachable through ordinary, unprivileged order placement.

Contrast this with the sibling exchange actuators, which use the *exact* variant correctly and thus fail safe: [6](#0-5) 

`MarketComparator.comparePrice`, used for price comparisons only (not settlement amounts), correctly uses `.compareTo()` on `BigInteger`, so it does not suffer this specific truncation bug: [7](#0-6) 

### Impact Explanation
`multiplyAndDivide`'s result directly becomes `takerBuyTokenQuantityReceive` / `makerBuyTokenQuantityReceive`, which are then credited to accounts via `accountCapsule.addAssetAmountV2` / balance adjustments in `matchSingleOrder`. If the `BigInteger` result wraps around `long` bounds, the resulting fill amount can be arbitrarily wrong: too small (loss of funds to the maker/taker), too large (unbacked token/TRX credited to an account beyond what the counter-order truly backs), or negative (potentially bypassing quantity checks like `== 0`/`< 0` that guard against no-op fills). This can lead to unauthorized creation of unbacked balance or theft of funds during on-chain order matching — a High-severity issue matching the accepted impact categories (unbacked balance / theft of funds).

### Likelihood Explanation
The path is reachable purely by a normal, unprivileged account: submit a `MarketSellAssetContract` (sell order) that matches an existing resting order, or place two crafted resting orders and then a triggering sell order, choosing quantities so that `a*b` overflows a `long` in `multiplyAndDivide`. No special permissions, SR/witness role, or off-chain compromise are needed — it is directly reachable via `MarketSellAssetActuator.execute()`, i.e., a single broadcast transaction. Likelihood is currently rated as plausible but not fully confirmed, because I could not verify the concrete value of `dynamicStore.getMarketQuantityLimit()` in this indexed snapshot to prove the overflow threshold is actually attainable under the deployed default configuration.

### Recommendation
Replace `.longValue()` with `.longValueExact()` in `MarketUtils.multiplyAndDivide`, and ensure the resulting `ArithmeticException` is handled the same way overflow is handled elsewhere in the market/exchange actuators (i.e., treated as a validation failure / reverted transaction rather than silently truncated). Additionally, audit `getMarketQuantityLimit()`'s configured value to confirm whether `limit * limit` can exceed `Long.MAX_VALUE`, and consider tightening the limit or adding an explicit check on `c` (the divisor) to prevent pathological low-divisor/high-numerator combinations.

### Proof of Concept
1. Attacker (or attacker using two colluding/self-controlled accounts) places a maker sell order with `sellTokenQuantity = S` (large, near `getMarketQuantityLimit()`) and `buyTokenQuantity = 1` (minimum allowed, `> 0`), creating a maker order with an extreme price ratio.
2. Attacker places (or a victim naturally places) a taker `MarketSellAssetContract` with `sellTokenQuantityRemain = R` also large, matching this maker order.
3. In `matchSingleOrder`, `MarketUtils.multiplyAndDivide(R, S, 1, ...)` is invoked (or the `makerBuyQuantity`-denominated calls at lines 427/462). If `R * S` exceeds `Long.MAX_VALUE`, `multiplyExact` throws, and the code falls into the `BigInteger` path: `BigInteger.valueOf(R).multiply(BigInteger.valueOf(S)).divide(BigInteger.ONE).longValue()`. Because the true product vastly exceeds `Long.MAX_VALUE` and `.longValue()` performs modular truncation rather than throwing, the computed fill quantity is an incorrect (and unpredictable, potentially negative or far too small/large) `long` value.
4. This corrupted quantity is then used to credit/debit `accountCapsule` balances/assets in `matchSingleOrder`, allowing the attacker to receive an incorrect (potentially inflated) amount of tokens/TRX relative to what was actually deposited into the matching orders, or to cause maker/taker order state (`SellTokenQuantityRemain`) to become inconsistent with actual asset transfers.

Note: I was unable to directly execute or unit-test this scenario in this environment, and could not confirm the exact configured value of `MarketQuantityLimit`, so the concrete overflow trigger values should be validated against the live default before treating this as fully confirmed exploitable in the current default configuration.
