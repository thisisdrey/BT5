### Title
Stale `PromiseYieldStatus`/`PromiseYieldReceipt`/`PromiseYieldTimeout` entries survive `DeleteAccount` and auto-fire an attacker-chosen self-call against a recreated account - ([File: core/store/src/utils/mod.rs], [File: runtime/runtime/src/actions.rs], [File: runtime/runtime/src/lib.rs])

### Summary
`remove_account` only deletes `Account`, `ContractCode`, access/gas keys and `ContractData`; it never clears `PromiseYieldStatus`, `PromiseYieldReceipt`, `PromiseYieldTimeout` queue entries, or `YieldIdToDataId` mappings created via `promise_yield_create`. When the same `AccountId` is deleted and later recreated, these leftover entries are still keyed only by `AccountId`/`data_id`, so a still-pending yield created by the *old* account owner is resumed (either via `promise_yield_resume` on the new contract, or automatically via the timeout queue) and executes against the *new* account's contract/state, with `predecessor_id == receiver_id == A` (a self-call), incorrectly satisfying `assert_self()`-style authorization checks in the new contract.

### Finding Description
`create_promise_yield_receipt` writes `PromiseYieldStatus::Yielded` for `(receiver_id, data_id)` and creates a self-directed `PromiseYield` action receipt whose `receiver_id` equals the calling account itself: [1](#0-0) 

`action_delete_account` calls `remove_account` and has no logic that checks for or clears any pending `PromiseYield*` state for the account being deleted: [2](#0-1) 

`remove_account` removes only `Account`, `ContractCode`, access keys/gas-key nonces, and `ContractData` - it never touches `TrieKey::PromiseYieldStatus`, `TrieKey::PromiseYieldReceipt`, `TrieKey::PromiseYieldTimeout`, or `TrieKey::YieldIdToDataId`: [3](#0-2) 

`check_account_existence` (called before `CreateAccount`) only checks whether an `Account` record exists; it does not check for leftover promise-yield state under the same id, so account recreation does not clear it either: [4](#0-3) 

When a `PromiseResume` receipt is later delivered for that `data_id`, `process_receipt` looks up `get_promise_yield_receipt`/`get_promise_yield_status` keyed purely by `(account_id, data_id)` - with no binding to *which* account incarnation created the yield - and, if found, executes the stored `yield_receipt`'s actions via `apply_action_receipt` against whatever state currently exists at that account id: [5](#0-4) 

Critically, this does not require any attacker interaction after account recreation: `resolve_promise_yield_timeouts` automatically synthesizes a `PromiseResume(data: None)` receipt once the timeout height passes, as long as `TrieKey::PromiseYieldReceipt` is still present for that `(account_id, data_id)` - which it is, since deletion/recreation never cleared it: [6](#0-5) 

Exploit flow:
1. Attacker (parent-account owner) creates subaccount `A`, deploys a contract, and calls a method that invokes `promise_yield_create` with a `method_name`/`arguments` callback of the attacker's choosing (e.g. targeting a privileged `assert_self()`-gated method name that a *future* contract at `A` might expose). This commits `PromiseYieldStatus::Yielded` and a `PromiseYieldReceipt` for `A`/`data_id`, plus a `PromiseYieldTimeout` queue entry.
2. Attacker issues `DeleteAccount(A, beneficiary=attacker)`. `remove_account` wipes `Account`/`ContractCode`/keys/`ContractData` but leaves the `PromiseYieldStatus`, `PromiseYieldReceipt`, and `PromiseYieldTimeout` entries intact in the trie.
3. An unrelated party later creates account `A` again (as a subaccount of the same parent, or the attacker itself resells/hands over the parent-controlled namespace) and deploys a legitimate contract with privileged self-only logic.
4. At the pre-recorded timeout height, `resolve_promise_yield_timeouts` automatically emits a `PromiseResume` for the stale `data_id`; `process_receipt` finds the stale `yield_receipt` and executes its attacker-chosen `FunctionCall` against the *new* account's contract, with `predecessor_id == A == receiver_id`, i.e. a self-call - bypassing any `assert_self()`/owner-only guard in the new contract that was never designed to be reachable by third parties.

No signature, nonce, access-key, or storage-staking check intervenes because the resumed receipt is generated internally by the runtime (`resolve_promise_yield_timeouts`) or by any exposed method on the new contract that forwards `promise_yield_resume`, and none of these paths re-validate that the recreated account is the same "owner" that created the yield.

### Impact Explanation
This is an authorization-escalation bug: a promise/callback created under one incarnation of an account is executed against a completely unrelated, later incarnation of the same `AccountId`, with `predecessor_id == receiver_id`, i.e. it appears as a legitimate self-call to the new contract. Any privileged logic in the new contract gated on "only callable by myself" (a common and idiomatic NEAR pattern, e.g. `assert_self()`/owner checks used for callbacks, admin functions, or resolve-style methods) can be triggered by an attacker who no longer controls the account, using arguments and a method name chosen entirely by the attacker back when they owned the (now-deleted) account.

### Likelihood Explanation
Preconditions: the attacker must own/control the parent account that can later create/recreate subaccount `A` again, or otherwise arrange for `A` to be reused by a victim contract deployer. This is somewhat constrained (subaccount creation is gated by the parent account, so a truly "unrelated party" recreating `A` requires it to be a top-level account or requires the attacker to give up/relinquish/sell the parent namespace), but the core state-hygiene bug (stale yield state never cleared on deletion) is unconditionally reachable by any unprivileged account: `CreateAccount` → `DeployContract` → `FunctionCall(promise_yield_create)` → `DeleteAccount` is composed entirely of ordinary, permissionless actions signed by the account owner, costs only standard gas/storage fees, and is fully repeatable.

### Recommendation
When executing `action_delete_account`/`remove_account`, also enumerate and remove any `PromiseYieldStatus`, `PromiseYieldReceipt`, `YieldIdToDataId`/`DataIdToYieldId` entries for the account, and either forbid deleting an account that still has pending yields or ensure any associated `PromiseYieldTimeout` queue entries are invalidated/skipped once the account no longer exists (e.g. check account existence, not just `PromiseYieldReceipt` presence, before firing the timeout resume; and have `apply_action_receipt` verify the yield receipt's origin against the current account state before execution).

### Proof of Concept
Integration/runtime test-loop plan:
1. Create account `A` (subaccount of a test signer), deploy a contract exposing a method that calls `promise_yield_create` with `method_name = "privileged_callback"` and attacker-chosen `arguments`, and register a short-lived yield (rely on `yield_timeout_length` config).
2. Assert `get_promise_yield_status`/`get_promise_yield_receipt` for `(A, data_id)` return `Some` right after the yield-create receipt is applied (per `set_promise_yield_status` in `ext.rs`).
3. Send `DeleteAccount(A, beneficiary=attacker)`; after it commits, directly query the trie (as `test-loop-tests/src/tests/yield_timeouts.rs::get_promise_yield_statuses_in_state` does) and assert the `PromiseYieldStatus`/`PromiseYieldReceipt` rows for `(A, data_id)` are still present, proving `remove_account` did not clear them.
4. Recreate account `A` and deploy a new contract exposing `privileged_callback` gated by `assert_self()` (only callable when `predecessor_account_id() == env::current_account_id()`).
5. Advance blocks past the yield timeout height (or directly deliver a `PromiseResume` for the stale `data_id`) and assert that `privileged_callback` on the *new* contract executes successfully (state mutation observed), demonstrating that a callback the attacker embedded under the deleted account was executed with self-call privileges against the unrelated recreated account.

/// Removes account, code and all access keys and gas keys associated to it.
pub fn remove_account(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
) -> Result<RemoveAccountResult, StorageError> {
    state_update.remove(TrieKey::Account { account_id: account_id.clone() });
    state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });

    let mut gas_key_nonce_count: usize = 0;
    let mut gas_key_nonce_total_key_bytes: usize = 0;

    // Removing access keys and gas key nonces
    let lock = state_update.trie().lock_for_iter();
    let mut keys_to_remove: Vec<TrieKey> = Vec::new();
    for raw_key in state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_access_keys(account_id), &lock)?
    {
        let raw_key = raw_key?;
        let key_handle = trie_key_parsers::parse_key_handle_from_access_key_key(
            &raw_key, account_id,
        )
        .map_err(|_e| {
            StorageError::StorageInconsistentState(
                "Can't parse key handle from raw key for AccessKey".to_string(),
            )
        })?;
        let nonce_index =
            trie_key_parsers::parse_nonce_index_from_gas_key_key(&raw_key, account_id, &key_handle)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse nonce index from raw key for AccessKey".to_string(),
                    )
                })?;
        if let Some(index) = nonce_index {
            gas_key_nonce_count += 1;
            gas_key_nonce_total_key_bytes += raw_key.len();
            keys_to_remove.push(TrieKey::gas_key_nonce(
                account_id.clone(),
                key_handle.clone(),
                index,
            ));
        } else {
            keys_to_remove.push(TrieKey::access_key(account_id.clone(), key_handle.clone()));
        }
    }
    drop(lock);

    for trie_key in keys_to_remove {
        state_update.remove(trie_key);
    }

    // Removing contract data
    let lock = state_update.trie().lock_for_iter();
    let data_keys = state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_contract_data(account_id, &[]), &lock)?
        .map(|raw_key| {
            trie_key_parsers::parse_data_key_from_contract_data_key(&raw_key?, account_id)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse data key from raw key for ContractData".to_string(),
                    )
                })
                .map(Vec::from)
        })
        .collect::<Result<Vec<_>, _>>()?;
    drop(lock);

    for key in data_keys {
        state_update.remove(TrieKey::ContractData { account_id: account_id.clone(), key });
    }
    Ok(RemoveAccountResult { gas_key_nonce_count, gas_key_nonce_total_key_bytes })
}
