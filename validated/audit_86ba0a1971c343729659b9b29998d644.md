This is a direct structural analog to the reported "token0 == token1" class of bug: a field that is implicitly expected to be distinct from the acting entity is never checked for equality.

### Title
Self-beneficiary `DeleteAccount` permanently burns the account's remaining balance - ([File: runtime/runtime/src/action_validation.rs])

### Summary
`DeleteAccountAction::beneficiary_id` is validated only for account-id syntax, never for inequality with the account being deleted. When a contract or user submits `DeleteAccount { beneficiary_id: <self> }`, the account is removed from state before the refund receipt executes, so the refund's `Transfer` targets an account that no longer exists and cannot be auto-created, causing the full remaining balance to be burned.

### Finding Description
`validate_delete_action` performs no equality check between `beneficiary_id` and the account being deleted: [1](#0-0) . Execution in `action_delete_account` unconditionally queues a `Receipt::new_balance_refund(&delete_account.beneficiary_id, account_balance)` and then wipes the account (`*account = None`, `remove_account`) in the very same step, regardless of whether `beneficiary_id` equals `account_id`: [2](#0-1) [3](#0-2) . When that refund receipt later executes as a `Transfer` to the (now-deleted) `beneficiary_id`, `check_transfer_to_nonexisting_account` rejects it because refunds are deliberately excluded from implicit account creation ("Refunds don't automatically create accounts, because refunds are free and we don't want some type of abuse"): [4](#0-3) . A refund receipt is identified by `predecessor_id().is_system()`, and the runtime explicitly burns the deposit on refund failure rather than retrying or re-crediting it: [5](#0-4) . This is the exact "token0 == token1"-style unhandled edge case: the protocol lets an actor name itself as the target of an action whose semantics implicitly assume a distinct recipient, and no guard exists to prevent or special-case it.

### Impact Explanation
Any remaining NEAR balance on an account that self-targets `DeleteAccount` (directly via a `SignedTransaction`, or via `promise_batch_action_delete_account` from a deployed contract) is irrecoverably burned instead of being transferred, refunded, or kept. This is a permanent, protocol-level loss of user/contract funds triggered purely by an unhandled edge case in an ordinary account-deletion transaction — no privileged access or malicious node/peer behavior is required.

### Likelihood Explanation
Reachable by any account holder or any deployed contract issuing a batched `DeleteAccount` action through the public NEAR JSON-RPC/host-function surface (`promise_batch_action_delete_account`) documented at [6](#0-5) . It requires no special conditions beyond setting `beneficiary_id` equal to the deleting account's own id, which is trivial for a wallet UI, SDK, or contract author to do accidentally (e.g., a naive `beneficiary_id: env::current_account_id()` pattern) or for an attacker to induce in a contract they control.

### Recommendation
Add an explicit check in `validate_delete_action` (`runtime/runtime/src/action_validation.rs`) rejecting `DeleteAccountAction` where `beneficiary_id == account_id`/`predecessor_id` (the account being deleted), analogous to how the report recommends `require(token0 != token1)`. Alternatively/additionally, guard in `action_delete_account` (`runtime/runtime/src/actions.rs`) to detect self-beneficiary before emitting the balance-refund receipt and route the funds elsewhere (e.g., reject the action, or transfer immediately instead of via a refund receipt that cannot recreate the account).

### Proof of Concept
1. Deploy any contract (or use a full-access key) on account `A` holding a non-zero balance.
2. Submit a `DeleteAccount { beneficiary_id: "A" }` action as the final/only action of the receipt/transaction (this passes `validate_delete_action` since `"A"` is a syntactically valid account id) — see the accepted pattern in [7](#0-6)  which only tests "final action" ordering, not self-beneficiary.
3. `action_delete_account` runs: it computes `account_balance = account_ref.amount()` and pushes `Receipt::new_balance_refund(&"A", account_balance)`, then deletes `A` from state (`runtime/runtime/src/actions.rs:364-371,386-388`).
4. The refund receipt (predecessor `"system"`) attempts a `Transfer` to `"A"`, which no longer exists; `check_transfer_to_nonexisting_account` returns `AccountDoesNotExist` because refunds are excluded from implicit account creation (`runtime/runtime/src/actions.rs:857-877`).
5. Per `runtime/runtime/src/lib.rs:993-1000`, since `result.result.is_err()` and `predecessor_id().is_system()`, the deposit amount is added to `other_burnt_amount` instead of being returned — the account's entire remaining balance is permanently burned.

Note: I was not able to execute this end-to-end in a live test-loop within this session; the analysis is based on static tracing of the validation, action-execution, and refund code paths cited above, which show no path that special-cases or blocks `beneficiary_id == account_id`. A Devin session with runtime access could add a regression test (e.g., in `runtime/runtime/src/tests/apply.rs` or `test-loop-tests/src/tests/create_delete_account.rs`) to confirm the balance is burned rather than preserved.
