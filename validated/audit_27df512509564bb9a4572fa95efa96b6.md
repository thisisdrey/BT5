### Title
Pingback handshake acceptance stores attacker-forged `addrbytes`/`port` into PeerDB instead of the verified dial address - (File: stackslib/src/net/neighbors/walk.rs)

### Summary
`pingback_handshakes_try_finish` verifies only that the responder's public key hashes to the expected `naddr.public_key_hash` via `check_handshake_pubkey_hash`, but then stores the neighbor using `data.handshake.addrbytes`/`data.handshake.port` — fields the responder freely sets inside its own payload — rather than the `naddr` address that the walker actually dialed out to during the pingback probe. This allows an attacker who legitimately owns a pingback-eligible inbound connection (and thus controls the `naddr.public_key_hash` seed) to redirect the stored `NeighborKey` to an arbitrary victim IP/port.

### Finding Description
The pingback mechanism exists specifically to *verify* that an inbound peer is reachable at a given address: the walker dials out to `naddr` (an address derived from the real, TCP-verified source of an earlier inbound connection) and expects a `HandshakeAccept` back confirming reachability [1](#0-0) .

When the response arrives, `check_handshake_pubkey_hash` only checks that `Hash160::from_node_public_key_buffer(&data.handshake.node_public_key)` equals `naddr.public_key_hash` [2](#0-1) . It performs no check that `data.handshake.addrbytes`/`data.handshake.port` matches `naddr`, or the actual socket the reply arrived on.

Immediately after this check, `peer_nk` is derived from `message.to_neighbor_key(&data.handshake.addrbytes, data.handshake.port)` — entirely attacker-controlled payload fields — and `&data.handshake` (carrying those same forged address fields) is handed to `add_or_schedule_replace_neighbor`, which persists a `Neighbor` entry keyed on that address [3](#0-2) .

Because the pubkey-hash check is the *only* guard, and the attacker legitimately controls the private key whose hash was recorded as `naddr.public_key_hash` (the walker learned this hash from a prior inbound connection the attacker itself made), the attacker trivially satisfies the guard while freely setting `data.handshake.addrbytes`/`port` to any victim IP/port. The equality the pingback is meant to enforce — "the address stored in PeerDB equals the address that was actually dialed and proven reachable" — is broken.

### Impact Explanation
This results in an unauthenticated write of an attacker-chosen `(victim_ip, victim_port) -> attacker_pubkey` mapping into the node's `PeerDB` frontier via `add_or_schedule_replace_neighbor`. Any other peer that later requests this node's neighbor list can receive and further propagate this forged `NeighborAddress`, causing network-wide propagation of a spoofed address record and directing other nodes' connection attempts at the victim's IP/port under the attacker's identity. This matches the "unauthenticated/unauthorized write to state" / "network-wide propagation of forged data" Critical categories. The attack is repeatable per pingback cycle at negligible attacker cost.

### Likelihood Explanation
Preconditions: the attacker must get its inbound connection classified as "pingback-eligible" (a new/unknown peer that the walker chooses to verify), which is a normal, unprivileged occurrence for any remote peer connecting to the node's P2P port. The attacker then simply crafts the `HandshakeAccept` response to the walker's outbound pingback probe with real key material (satisfying the hash check) but forged `addrbytes`/`port`. No secrets, privileged roles, or victim cooperation are required, and the P2P port is remotely reachable by design.

### Recommendation
In `pingback_handshakes_try_finish`, ignore `data.handshake.addrbytes`/`data.handshake.port` for storage purposes when finalizing a pingback; use the `naddr`/`peer_nk` that was actually dialed (the address whose reachability the pingback round-trip verified) when calling `add_or_schedule_replace_neighbor`, or explicitly validate that `data.handshake.addrbytes`/`port` match `naddr` before accepting the handshake.

### Proof of Concept
Rust test in `stackslib::net::neighbors::walk`:
1. Construct a `NeighborWalk` with `network_pingbacks` containing a `naddr` (real attacker IP `A`, pubkey hash `H(attacker_key)`).
2. Simulate `pingback_handshakes_begin` dialing out to `naddr`.
3. Inject a `StacksMessageType::HandshakeAccept` reply via `self.comms` whose `handshake.node_public_key` is the attacker's real key (hash matches `naddr.public_key_hash`) but whose `handshake.addrbytes`/`port` are set to a victim address `V` distinct from `A`.
4. Call `pingback_handshakes_try_finish`.
5. Assert that the resulting entry written via `add_or_schedule_replace_neighbor` (inspect `self.neighbor_replacements` / `PeerDB`) has address `V` (attacker-forged) rather than `A` (the address actually dialed/verified), proving the stored frontier entry does not correspond to the connection's true origin.

    /// Does a given handshakedata represent an expected public key hash?
    fn check_handshake_pubkey_hash(
        nk: &NeighborKey,
        data: &HandshakeAcceptData,
        naddr: &NeighborAddress,
    ) -> bool {
        let neighbor_pubkey_hash =
            Hash160::from_node_public_key_buffer(&data.handshake.node_public_key);
        if neighbor_pubkey_hash != naddr.public_key_hash {
            debug!(
                "Neighbor {:?} had an unexpected pubkey hash: expected {:?} != {:?}",
                nk, &naddr.public_key_hash, &neighbor_pubkey_hash
            );
            return false;
        }

        true
    }
