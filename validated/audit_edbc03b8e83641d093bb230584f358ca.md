### Title
Unrestricted Unicode/confusable and bidirectional-override characters permitted in on-chain Asset URL fields enable domain/identity spoofing - (File: `actuator/src/main/java/org/tron/core/utils/TransactionUtil.java`)

### Summary
CVE-2018-18355 describes Chrome's `URL Formatter` failing to reject confusable Unicode characters, letting an attacker spoof a domain name shown in the address bar. The equivalent bug class in java-tron is present in the on-chain asset-issuance path: the `url` (and `description`) fields of an `AssetIssueContract` are validated only for byte-length, with no restriction on which Unicode code points are allowed, unlike the `name`/`abbr` fields which are restricted to printable ASCII.

### Finding Description
`TransactionUtil.validUrl()` delegates to `validBytes()`, which only checks length (`<= MAX_URL_LEN`, 256 bytes) and does not run the "readable" character filter that `validAssetName`/`validTokenAbbrName` use via `validReadableBytes()`: [1](#0-0) 

`AssetIssueActuator.validate()` calls `TransactionUtil.validUrl()` on the attacker-supplied `url` field of the `AssetIssueContract`, but performs no confusable-character, bidi-control-character, or homograph filtering: [2](#0-1) 

Because `validBytes()` only bounds length and `allowEmpty`, an unprivileged asset issuer can freely include arbitrary UTF-8 code points in the `url`/`description` fields — including Unicode confusable characters (Cyrillic/Greek look-alikes of Latin letters) and bidirectional-override control characters (e.g. U+202E RIGHT-TO-LEFT OVERRIDE) that visually reorder or disguise displayed text. This value is persisted verbatim in `AssetIssueCapsule` and served back unmodified through the HTTP/gRPC Wallet query paths (`GetAssetIssueList`, `GetAssetIssueByAccount`, etc.), and the JSON HTTP formatter explicitly preserves valid UTF-8 rather than restricting to a safe character set: [3](#0-2) 

An attacker can therefore issue a token whose `url` renders — in wallets, block explorers, or any client consuming the java-tron Wallet API — as a domain visually indistinguishable from a legitimate exchange or project site (e.g. `bіnance.com` using Cyrillic `і`), or use a bidi override to make a malicious URL/description display as benign text.

### Impact Explanation
This is a spoofing/deception primitive analogous to the CVE's own severity classification (Medium, low-integrity impact, no direct compromise). The node itself is not compromised, no funds are directly moved by this bug, and no consensus/state corruption occurs — the deceptive string is faithfully stored and returned as designed. Any downstream harm (e.g., users being phished into sending TRX/tokens to a malicious address believing it belongs to a legitimate project) requires additional user action outside the node's control, consistent with the original CVE's classification as a UI-spoofing issue rather than a memory-safety or authorization bypass.

### Likelihood Explanation
Trivial to trigger: any account with sufficient balance to pay the asset-issuance fee can call `AssetIssueContract` with a crafted `url`/`description` containing confusable or bidi-control characters, since `validUrl`/`validAssetDescription` never reject them.

### Recommendation
Extend `TransactionUtil.validUrl()` and `validAssetDescription()` to reject or normalize dangerous Unicode categories in user-displayed fields — at minimum strip/disallow bidirectional-control code points (U+202A–U+202E, U+2066–U+2069) and consider applying a confusable-skeleton check (similar to Unicode TR39) before accepting the value, mirroring the stricter `validReadableBytes()` already used for `name`/`abbr`.

### Proof of Concept
1. Construct an `AssetIssueContract` transaction with `url` set to a UTF-8 string containing a Cyrillic homoglyph domain, e.g. `https://bіnance-support.com` (with U+0456 Cyrillic `і`), or embed U+202E before a fake-safe suffix so the rendered text is reversed/misleading.
2. Broadcast the transaction; `AssetIssueActuator.validate()` accepts it because `TransactionUtil.validUrl()` only checks length.
3. Query the asset via `Wallet.getAssetIssueList`/HTTP `getassetissuebyid`; the spoofed `url` is returned verbatim and rendered by wallets/explorers as the project's official link.

  private static boolean validBytes(byte[] bytes, int maxLength, boolean allowEmpty) {
    if (ArrayUtils.isEmpty(bytes)) {
      return allowEmpty;
    }
    return bytes.length <= maxLength;
  }

  private static boolean validReadableBytes(byte[] bytes, int maxLength) {
    if (ArrayUtils.isEmpty(bytes) || bytes.length > maxLength) {
      return false;
    }
    // b must be readable
    for (byte b : bytes) {
      if (b < 0x21) {
        return false; // 0x21 = '!'
      }
      if (b > 0x7E) {
        return false; // 0x7E = '~'
      }
    }
    return true;
  }
