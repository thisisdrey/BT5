### Title
Replay-window check-then-act race allows a captured packet to be decrypted and delivered twice - ([File: connection_state.go])

### Summary
`ConnectionState.Decrypt` and `ConnectionState.VerifyRelay` validate an inbound message counter against the anti-replay bitmap (`Bits`) by calling `window.Check` and `window.Update` as two separate, independently-locked operations, with decryption of the packet happening in between while the lock is released. This mirrors the reported bug class: a value used to authorize an action (here, "has this counter already been consumed?") is read at one point in time, the actual state mutation that would prevent a second consumer from succeeding happens later, and the gap between the two lets a second, concurrent instance of the same input pass the same check before the first instance's mutation lands.

### Finding Description
`Decrypt` reads and finalizes replay-window state in two separate critical sections: [1](#0-0) 

```
cs.decryptLock.Lock()
result := cs.window.Check(l, messageCounter)
cs.decryptLock.Unlock()
if !result { return nil, ErrAlreadySeen }

out, err = cs.dKey.DecryptDanger(...)   // no lock held here
...

cs.decryptLock.Lock()
result = cs.window.Update(l, messageCounter)
cs.decryptLock.Unlock()
if !result { return nil, ErrAlreadySeen }
```

`Check` only *reads* the bitmap state and returns whether `messageCounter` looks unseen; it does not mark it as seen. `Update` is the operation that actually stomps/marks the bit for that counter, and is only invoked after decryption completes: [2](#0-1) [3](#0-2) 

Because the lock is released between `Check` and `Update`, and because `AEAD` decryption of the packet (`DecryptDanger`) happens with no lock held at all, two goroutines processing two copies of the exact same wire packet (i.e., a literal replay of a previously-observed ciphertext + counter, which any on-path/network attacker can capture and resend without holding any certificate or trust relationship) can both call `Check` before either calls `Update`. Both `Check` calls will return `true` (not yet marked), so both goroutines will proceed to call `DecryptDanger` and succeed, and only the second call to `Update` will report a duplicate — but by then the first (and possibly second) decrypted plaintext has already been handed back to the caller and delivered/processed as legitimate application traffic. `VerifyRelay` has the exact same structural race: [4](#0-3) 

The CHANGELOG shows the replay window has already been the subject of two related, narrower fixes — advancing the window for relayed packets (#1751) and locking updates so concurrent readers can't corrupt the bitmap itself (#1802) — but neither of those addresses the check-then-act gap between `Check` and `Update` in `Decrypt`/`VerifyRelay`. [5](#0-4) 

This is directly reachable by an unauthenticated network attacker via `readOutsidePackets`, which routes any UDP packet whose header parses and whose `RemoteIndex` maps to an existing hostinfo straight into `Decrypt`/`VerifyRelay` — no certificate ownership is required, only capture-and-resend of ciphertext belonging to an already-established tunnel between two other legitimate peers: [6](#0-5) 

### Impact Explanation
This breaks the intended guarantee of the anti-replay window: a replayed data-plane (or relay) message can be processed by the receiver more than once instead of being deterministically rejected. For relayed traffic this directly reintroduces the double-forwarding condition that #1751 was meant to prevent (a relay re-forwarding a replayed frame), and for direct tunnels it allows an attacker who can race UDP delivery (e.g., duplicate the same UDP datagram at the network layer, which is trivial and doesn't require decrypting or forging anything) to cause the same application-layer packet to be delivered to the tun device twice. This is a genuine replay-protection bypass with remote, unauthenticated reach — it does not require possession of any CA-signed certificate, only the ability to observe/duplicate packets on the path between two already-paired peers.

### Likelihood Explanation
Likelihood is moderate-to-low but non-negligible: the attacker must win a real, but narrow, race between two lock/unlock cycles on `decryptLock`, which is more feasible with local UDP duplication (loopback replays, or an attacker close to one endpoint) than over long network paths. No cryptographic material or trust is needed; the attacker only replays previously observed valid ciphertext, which is trivially obtainable by anyone who can sniff or duplicate the encrypted UDP stream.

### Recommendation
Perform the replay-window check-and-mark as a single atomic operation under one lock acquisition, mirroring how staking-reward accounting needed to update `totalPoints`/reward-per-token atomically with each state-changing action rather than as two disjoint reads/writes. Concretely, decrypt only after the counter has been provisionally marked (or hold `decryptLock` across `Check`+`Update`, rolling back the mark if `DecryptDanger` fails), so no other caller can observe the same counter as "unseen" until the first attempt has fully committed or failed.

### Proof of Concept
1. Two peers complete a handshake and establish a `ConnectionState` with an active replay `Bits` window.
2. An attacker captures one valid encrypted data-plane UDP packet (header + ciphertext) sent from peer A to peer B.
3. The attacker sends two (or more) copies of that exact packet to peer B in rapid succession (e.g., back-to-back `sendto` calls, or via loopback duplication), such that both are read by two different UDP reader goroutines (`f.readers[q]` fan-out) before either finishes processing.
4. Goroutine 1 calls `cs.window.Check(l, messageCounter)` → `true`, releases the lock.
5. Before goroutine 1 calls `Update`, goroutine 2 also calls `cs.window.Check(l, messageCounter)` → still `true` (not yet marked), releases the lock.
6. Both goroutines call `cs.dKey.DecryptDanger(...)` and succeed, both returning decrypted plaintext to their callers.
7. Only when both later call `cs.window.Update(l, messageCounter)` does the bitmap register the duplicate for the second one — but the first (and second, up to the successful `DecryptDanger`) plaintext has already been forwarded/processed, demonstrating that the replayed packet was accepted more than once despite the anti-replay window being present.

func (cs *ConnectionState) Decrypt(l *slog.Logger, messageCounter uint64, out []byte, packet []byte, nb []byte) ([]byte, error) {
	var err error
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}

	out, err = cs.dKey.DecryptDanger(out, packet[:header.Len], packet[header.Len:], messageCounter, nb)
	if err != nil {
		return nil, err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}
	return out, nil
}

// VerifyRelay verifies AEAD protected (but not encrypted) relay frames. packet must be length-checked by the caller.
func (cs *ConnectionState) VerifyRelay(l *slog.Logger, messageCounter uint64, packet []byte, nb []byte) error {
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	signedPayload := packet[:len(packet)-cs.dKey.Overhead()]
	signatureValue := packet[len(packet)-cs.dKey.Overhead():]
	_, err := cs.dKey.DecryptDanger(nil, signedPayload, signatureValue, messageCounter, nb)
	if err != nil {
		return err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	return nil
}

// Check returns true if i is within (or way out in front of) the window, and not a replay
func (b *Bits) Check(l *slog.Logger, i uint64) bool {
	// If i is the next number, return true.
	if i > b.current {
		return true
	}

	if b.strictlyWithinWindow(i) {
		return !b.get(i)
	}

	// Not within the window
	if l.Enabled(context.Background(), slog.LevelDebug) {
		l.Debug("rejected a packet (top)", "current", b.current, "incoming", i)
	}
	return false
}

func (b *Bits) Update(l *slog.Logger, i uint64) bool {
	// Fast path: i is the next expected counter. Split out so the function
	// stays small and avoids paying for the slow paths' slog argument-build
	// stack frame on every call. The bit read/test/write is inlined to
	// touch the backing word once.
	if i == b.current+1 {
		pos := i & b.lengthMask
		word := pos >> 6
		mask := uint64(1) << (pos & 63)
		w := b.bits[word]
		if i > b.length && w&mask == 0 {
			b.lostCounter.Inc(1)
		}
		b.bits[word] = w | mask
		b.current = i
		return true
	}
	return b.updateSlow(l, i)
}
