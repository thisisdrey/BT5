### Title
`TransferToNewAccount` / `TransferToNewAccountPda` do not reject `Pubkey::default()` as `new_authority`, permanently locking migrated funds - ([File: programs/marginfi/src/instructions/marginfi_account/transfer_account.rs])

### Summary
`transfer_to_new_account` and `transfer_to_new_account_pda` let any `MarginfiAccount` authority migrate their account's positions to a brand-new account under a caller-supplied `new_authority`, but the program never validates that `new_authority != Pubkey::default()`. This is the same missing-zero-address-check bug class described in the external `MainToken.set_mint_multisig()` report, reachable here by an ordinary unprivileged user rather than an admin.

### Finding Description
`TransferToNewAccount` and `TransferToNewAccountPda` accept `new_authority` as a completely unchecked account: [1](#0-0) [2](#0-1) 

The instruction logic (`transfer_to_new_account` / `transfer_to_new_account_pda`) only checks flashloan/receivership/order-execution state and that the old account hasn't already migrated; it never checks `new_authority` for the zero pubkey before calling `initialize_migrated_account`, which sets the new account's `authority` field directly to whatever was passed: [3](#0-2) [4](#0-3) 

Immediately afterward, the old account is disabled and marked `migrated_to = new_account_key`, and the check that blocks re-migration (`old_account.migrated_to == Pubkey::default()`) guarantees the old account can never be migrated again: [5](#0-4) 

If `new_authority` is passed as `Pubkey::default()`, the newly created account (which now holds all the migrated `lending_account` balances/positions) ends up with `authority == Pubkey::default()`. Since `is_signer_authorized` requires the signer to equal `marginfi_account.authority` (or be the group admin if frozen), no wallet can ever sign as `Pubkey::default()`, so the new account — and everything transferred into it — becomes permanently uncontrollable, while the old account is simultaneously disabled and barred from re-migration.

Notably, off-chain tooling for this exact instruction explicitly guards against this: the CLI wrapper rejects a zero `new_authority` before submitting the transaction, confirming the maintainers recognize this as an unsafe input, yet the on-chain instruction performs no equivalent check: [6](#0-5) 

The test suite even documents the unrestricted nature of this field with a "WARN" comment, but only exercises non-zero authorities: [7](#0-6) 

### Impact Explanation
Any account authority who invokes `transfer_to_new_account` or `transfer_to_new_account_pda` with an accidental or malformed `new_authority == Pubkey::default()` (e.g. an integrator bug, malformed client input, or a phished/blind-signed transaction) permanently and irrecoverably locks all of that account's lending/borrowing positions in a new account nobody can ever control, with no admin recovery path exposed by this instruction and no ability to reverse the migration (the old account's `migrated_to` field permanently blocks retry). This is a permanent lock/freeze of user funds, matching the accepted impact category.

### Likelihood Explanation
The instruction is fully permissionless from the account-authority's perspective — no admin approval or special privilege is required, only the account's own signature — and the vulnerable field is directly attacker/user-controlled with zero on-chain validation. The existing off-chain CLI explicitly protects against this exact input, implying it is a recognized, realistic failure mode (e.g., front-end bug, malformed integration parameters, or blind-signing) rather than a purely theoretical edge case.

### Recommendation
Add an explicit check in `transfer_to_new_account` and `transfer_to_new_account_pda` that `ctx.accounts.new_authority.key() != Pubkey::default()`, returning an error (e.g. a new `InvalidAuthority`/`IllegalAction` variant) before any state mutation occurs, mirroring the existing off-chain CLI guard in `p0-cli/src/processor/account.rs`.

### Proof of Concept
1. Create a `MarginfiAccount` with some active deposit/borrow positions.
2. Call `transfer_to_new_account` (or `transfer_to_new_account_pda`), passing `new_authority = Pubkey::default()`.
3. The instruction succeeds: `old_account` is disabled and its `migrated_to` is set to the new account's key (blocking any retry), while `new_account.authority` is set to `Pubkey::default()`.
4. Because `is_signer_authorized` can never match `Pubkey::default()` as a signer, no one can ever operate on `new_account` again — all migrated balances are permanently locked with no recovery mechanism in this instruction.
