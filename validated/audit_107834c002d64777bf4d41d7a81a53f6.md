### Title
Uninstantiated-attachment eviction in `AtlasDB` is oldest-first with no protection for attachments still referenced by a pending `AttachmentInstance`, letting an attacker evict a legitimately-committed but not-yet-downloaded attachment - ([File: stackslib/src/net/atlas/db.rs])

### Summary
`AtlasDB::insert_uninstantiated_attachment` and `evict_k_oldest_uninstantiated_attachments` evict the oldest rows of the `attachments` table purely by `created_at` whenever the row count reaches `AtlasConfig::max_uninstantiated_attachments`, with no check for whether a pending `AttachmentInstance.content_hash` still references that row. `should_keep_attachment` only checks contract-id membership and size, never verifying the content actually corresponds to any on-chain-emitted `AttachmentInstance.content_hash`, so an attacker can seed the table with attacker-chosen "junk" attachments that will never be claimed, occupying slots and aging out legitimately-fetched-but-unresolved attachments ahead of schedule.

### Finding Description
The equality the design relies on — "every uninstantiated row in `attachments` corresponds to a real, on-chain-committed `content_hash`" — is not enforced anywhere on the insert path.

`should_keep_attachment` only checks contract membership and byte-size limits: [1](#0-0) 

`insert_uninstantiated_attachment` counts current uninstantiated rows and, once at/above `max_uninstantiated_attachments`, calls `evict_k_oldest_uninstantiated_attachments` before inserting the new row: [2](#0-1) 

Eviction is a pure `DELETE ... ORDER BY created_at ASC LIMIT k` over `was_instantiated = 0` rows, with no join/filter against `attachment_instances` to protect rows a pending, unresolved `AttachmentInstance.content_hash` still needs: [3](#0-2) 

`find_uninstantiated_attachment`, used by the download machinery to check whether a needed attachment is already locally cached, simply does a hash lookup with no distinction between "junk" and "real" rows — once evicted, it returns `None`: [4](#0-3) 

The reachable path from a remote, unprivileged peer is `POST /v2/transactions` → `PostTransactionRequestHandler::try_handle_request`. After the transaction is admitted to the mempool, if it is a `ContractCall` targeting a contract in `AtlasConfig.contracts` (e.g. BNS) and carries an attachment, `should_keep_attachment` is checked and, if it passes, `insert_uninstantiated_attachment` is called unconditionally — with no verification that the attachment's hash matches any `AttachmentInstance.content_hash` ever emitted by a real BNS operation: [5](#0-4) 

This exact eviction behavior (oldest-first regardless of consumer state) is confirmed by the existing unit test, which shows the 1st/5th inserted attachment silently disappearing purely due to insertion order once `max_uninstantiated_attachments` is reached: [6](#0-5) 

### Impact Explanation
An attacker who can get valid `ContractCall` transactions targeting a tracked contract (e.g. `bns`) admitted into a victim node's mempool can attach distinct attacker-chosen content that passes `should_keep_attachment` (size ≤ `attachments_max_size`) but corresponds to no real on-chain commitment. Once the number of uninstantiated rows reaches `max_uninstantiated_attachments`, each further attacker insert evicts the single oldest uninstantiated row — including rows belonging to real attachments a node is still waiting to serve/resolve for an outstanding, unresolved `AttachmentInstance`. The victim's `find_uninstantiated_attachment` lookup for that legitimate hash then returns `None`, and the attachment must be re-fetched from the network (or is lost if no peer still serves it), delaying/DoS'ing resolution of a legitimately committed BNS attachment. This matches the "attachment/BNS mismatch" High-severity category in scope.

### Likelihood Explanation
Preconditions: the target's `AtlasConfig.contracts` must include a contract the attacker can freely call (BNS is default), and attacker must produce `max_uninstantiated_attachments` (minimum `MAX_UNINSTANTIATED_ATTACHMENTS_MIN = 50_000`, default higher) distinct, mempool-admissible transactions — each requiring a valid signature, sufficient fee, and a fresh nonce, i.e., real economic cost, not free spam. This significantly bounds the attack rate/cost compared to a trivial single-message DoS, but it requires no privileged role, no RPC secret, and is fully achievable by any funded remote account through the public `/v2/transactions` endpoint, and is repeatable indefinitely as long as the attacker keeps paying fees.

### Recommendation
Change eviction to skip/exclude rows whose `hash` is currently referenced by an unresolved (`is_available = 0`) row in `attachment_instances` (i.e., only evict uninstantiated attachments that no pending `AttachmentInstance` needs), or maintain a separate size-bounded quarantine/cache for unsolicited POSTed attachments distinct from the pool that backs `find_uninstantiated_attachment` lookups used by the download resolution path. Additionally, consider not persisting POST-supplied attachments as "uninstantiated" until their hash is confirmed to match a real, currently-unresolved `AttachmentInstance.content_hash` in the database.

### Proof of Concept
Extend `stackslib/src/net/atlas/tests.rs::test_evict_k_oldest_uninstantiated_attachments` (db.rs:511-547) style test:
1. Configure `AtlasDB` with a small `max_uninstantiated_attachments` (e.g. 10) for test purposes.
2. Insert one real attachment (`insert_uninstantiated_attachment`) and simultaneously `queue_attachment_instance`/`mark_attachment_instance_checked(..., false)` an `AttachmentInstance` whose `content_hash` matches it, leaving it unresolved.
3. Insert 9 more distinct attacker-content attachments via `insert_uninstantiated_attachment` (simulating repeated `/v2/transactions` POSTs with distinct ContractCall attachments to the tracked contract) to fill the table to `max_uninstantiated_attachments`.
4. Insert one more attacker attachment, triggering `evict_k_oldest_uninstantiated_attachments(1)`.
5. Assert `atlas_db.find_uninstantiated_attachment(&real_attachment.hash())` now returns `Ok(None)`, despite `find_unresolved_attachment_instances()` still containing the corresponding `AttachmentInstance` — demonstrating the real, still-needed attachment was evicted purely due to insertion order.

    pub fn should_keep_attachment(
        &self,
        contract_id: &QualifiedContractIdentifier,
        attachment: &Attachment,
    ) -> bool {
        if !self.atlas_config.contracts.contains(contract_id) {
            info!(
                "Atlas: will discard posted attachment - {} not in supported contracts",
                contract_id
            );
            return false;
        }
        if attachment.content.len() as u32 > self.atlas_config.attachments_max_size {
            info!("Atlas: will discard posted attachment - attachment too large");
            return false;
        }
        true
    }

    pub fn insert_uninstantiated_attachment(
        &mut self,
        attachment: &Attachment,
    ) -> Result<(), db_error> {
        // Insert the new attachment
        let uninstantiated_attachments = self.count_uninstantiated_attachments()?;
        if uninstantiated_attachments >= self.atlas_config.max_uninstantiated_attachments {
            let to_delete =
                1 + uninstantiated_attachments - self.atlas_config.max_uninstantiated_attachments;
            self.evict_k_oldest_uninstantiated_attachments(to_delete)?;
        }

        let tx = self.tx_begin()?;
        let now = util::get_epoch_time_secs() as i64;
        let res = tx.execute(
            "INSERT OR REPLACE INTO attachments (hash, content, was_instantiated, created_at) VALUES (?, ?, 0, ?)",
            params![
                attachment.hash(),
                attachment.content,
                now,
            ],
        );
        res.map_err(db_error::SqliteError)?;
        tx.commit().map_err(db_error::SqliteError)?;
        Ok(())
    }

    pub fn evict_k_oldest_uninstantiated_attachments(&mut self, k: u32) -> Result<(), db_error> {
        let tx = self.tx_begin()?;
        let res = tx.execute(
            "DELETE FROM attachments WHERE hash IN (SELECT hash FROM attachments WHERE was_instantiated = 0 ORDER BY created_at ASC LIMIT ?)",
            params![k],
        );
        res.map_err(db_error::SqliteError)?;
        tx.commit().map_err(db_error::SqliteError)?;
        Ok(())
    }
