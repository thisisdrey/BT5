### Title
Attacker can permanently fill the fee collector's `depositTokensOfAccount` set with dust, DoSing all fee-bearing deposits and withdrawals via `UserReachedMaxTokens` - ([File: contracts/Pool.sol])

### Summary
`Pool` enforces a hard cap of `MAX_TOKENS_PER_USER = 30` on the combined number of per-account deposit/debt token entries (`Pool.sol:79`, `Pool.sol:143-148`). `DepositToken._mint` and `_transfer` unconditionally call `pool.addToDepositTokensOfAccount(recipient)` whenever the recipient's balance moves from zero (`DepositToken.sol:486-488`, `DepositToken.sol:518-520`), and the internal call inside `addToDepositTokensOfAccount` reverts with `UserReachedMaxTokens` once the recipient's set is full (`Pool.sol:216-220`). Since `deposit()` mints the deposit fee to `feeCollector()` and `_withdraw()` transfers the withdraw fee to `feeCollector()` (`DepositToken.sol:230-231`, `DepositToken.sol:546-547`), an attacker who dust-transfers all 30 deposit tokens to the fee collector causes every fee-bearing `deposit()` and `withdraw()` to revert — a griefing/DoS analog of a missing-entry crash (CVE-2016-8652).

### Finding Description
The bug class is "operation crashes because a required entry cannot be recorded" — in Dovecot, aborting auth without a username crashed the auth-policy path; here, receiving a fee cannot be recorded because the recipient's account set is full, and the revert propagates to the user's deposit/withdrawal.

Attack path (fully unprivileged):
1. Attacker deposits a small amount of each of the pool's deposit tokens (deployed pools have up to `MAX_TOKENS_PER_USER` deposit tokens; `addDepositToken` itself caps the pool-level list at 30 — `Pool.sol:703`), receiving transferable msdTOKENs.
2. Attacker calls `depositToken.transfer(feeCollector, 1)` for each of the 30 deposit tokens. Each first-time receipt executes `pool.addToDepositTokensOfAccount(feeCollector)` until the set hits 30 entries.
3. Any subsequent `deposit(amount, onBehalfOf)` with `depositFee > 0` reverts at `_mint(feeCollector, _fee)` → `addToDepositTokensOfAccount` → `UserReachedMaxTokens`. Any `withdraw`/`flashWithdraw`/`withdrawFrom` with `withdrawFee > 0` reverts at `_transfer(account, feeCollector, _fee)` for the same reason.
4. Users' collateral becomes temporarily frozen: withdrawals always revert as long as the fee collector's set stays full and fees are nonzero. Only a privileged actor (the fee collector's owner / governor-controlled sweep via `TokenHolder`, or the fee collector transferring the dust out) can free slots — the victim cannot self-remedy.

No guard stops this: `transfer` only checks `_revertIfLocked` on the sender (`DepositToken.sol:348-353`), `addToDepositTokensOfAccount` has no opt-out, and the fee collector is a normal recipient. `nonReentrant`, pause flags, and `SynthContext` checks are all satisfied.

### Impact Explanation
Temporary freezing of funds (protocol-wide): with `withdrawFee > 0`, every user withdrawal across every deposit token reverts, so all deposited collateral is locked until governance intervenes. With `depositFee > 0`, all deposits revert. Additionally, liquidation `seize` to a liquidator whose set is full can revert, degrading liquidation liveness. Cost to the attacker is 30 dust deposits + 30 dust transfers; recovery requires privileged action, making the freeze asymmetric.

### Likelihood Explanation
Requires fee-bearing deposits/withdrawals to be configured (deployed fee providers do charge fees), an attacker willing to buy dust amounts of up to 30 collaterals, and the fee collector not already holding all tokens. No privileged role, oracle manipulation, or special timing is needed; it is repeatable on any pool.

### Recommendation
Exclude fee transfers/mints to `feeCollector` from the per-account token-list accounting (e.g., skip `addToDepositTokensOfAccount` when the recipient is `pool.feeCollector()`, or let `addToDepositTokensOfAccount` silently no-op for the fee collector). Alternatively, allow recipients to remove dust entries themselves, or bound only per-account entries that actually affect health-factor loops (e.g., ignore tokens whose balance is below a threshold) instead of reverting.

### Proof of Concept
Hardhat fork-style sketch against a deployed pool where `withdrawFee > 0` and `feeCollector` holds < 30 deposit tokens:

```ts
// feeCollector = await poolRegistry.feeCollector()
const depositTokens: string[] = await pool.getDepositTokens(); // up to 30

// 1) Attacker seeds dust balances and fills feeCollector's set
for (const dt of depositTokens) {
  const token = await ethers.getContractAt("DepositToken", dt);
  const underlying = await ethers.getContractAt("IERC20", await token.underlying());
  await underlying.connect(attacker).approve(dt, dust);
  await token.connect(attacker).deposit(dust, attacker.address); // mints msdTOKEN to attacker
  await token.connect(attacker).transfer(feeCollector, 1);       // +1 entry in feeCollector's set
}
expect(await pool.getDepositTokensOfAccount(feeCollector)).to.have.length(30);

// 2) Any user deposit with depositFee > 0 reverts
await expect(
  token.connect(user).deposit(amount, user.address)
).to.be.revertedWithCustomError(pool, "UserReachedMaxTokens");

// 3) Any user withdraw with withdrawFee > 0 reverts -> collateral frozen
await expect(
  token.connect(user).withdraw(amount, user.address)
).to.be.revertedWithCustomError(pool, "UserReachedMaxTokens");
```

Reproduction steps: deploy/fork a pool with nonzero `depositFee`/`withdrawFee`, run the loop above, then attempt `deposit`/`withdraw` as a normal user; both revert inside `Pool.addToDepositTokensOfAccount` (`Pool.sol:143-148`, `Pool.sol:216-220`) reached via `DepositToken._mint` (`DepositToken.sol:486`) and `DepositToken._transfer` (`DepositToken.sol:518`).
