## Title
Unbounded array allocation from attacker-controlled length in `PrecompiledContracts.extractBytesArray`/`extractSigArray`/`extractBytes32Array` allows single-transaction memory exhaustion (node crash / DoS) — (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
`PrecompiledContracts.extractBytesArray`, `extractSigArray`, and `extractBytes32Array` allocate a Java array `new byte[len][...]` where `len` comes directly from `words[offset].intValueSafe()` — a 32-byte word taken from attacker-supplied smart contract calldata — before any upper bound on `len` is validated in some code paths. [1](#0-0) 

### Finding Description
`extractBytes32Array` has no length check at all:
```
private static byte[][] extractBytes32Array(DataWord[] words, int offset) {
  int len = words[offset].intValueSafe();
  byte[][] bytes32Array = new byte[len][];
  ...
}
``` [2](#0-1) 

`extractBytesArray` and `extractSigArray` only bound-check the `offset` index into `words`, not the derived `len` used for the array allocation: [3](#0-2) 

`DataWord.intValueSafe()` returns `Integer.MAX_VALUE` whenever the word occupies more than 4 bytes, so an attacker can trivially force `len` to be `Integer.MAX_VALUE` (~2.1 billion) by placing a 32-byte word with any high value at the appropriate ABI offset: [4](#0-3) 

These helpers are invoked from the `ValidateMultiSign` and `BatchValidateSign` TVM precompiled contracts. In `BatchValidateSign.doExecute`, the `MAX_SIZE` bound (`sigArraySize > MAX_SIZE || addrArraySize > MAX_SIZE`) is only evaluated when `VMConfig.allowTvmSelfdestructRestriction()` is enabled; if that feature flag is not active, `extractBytesArray`/`extractSigArray`/`extractBytes32Array` are called with the raw, unbounded `len` and the size check that follows (`signatures.length == 0 || signatures.length > MAX_SIZE`) happens only *after* the (potentially huge) array has already been allocated: [5](#0-4) 

The same pattern applies to `ValidateMultiSign.execute`, where the pre-check on `sigArraySize` is likewise gated behind `VMConfig.allowTvmSelfdestructRestriction()`: [6](#0-5) 

I could not confirm from the indexed code whether `allowTvmSelfdestructRestriction()` is unconditionally enabled/hardcoded true on current mainnet (I could not locate the `DynamicPropertiesStore`/`VMConfig` getter definitions or their default values in the index), so I cannot definitively state whether this specific gated path is reachable today. This is a real gap in my verification, not a claim I can make with full confidence.

### Impact Explanation
If reachable (i.e., if the guarding feature flag is disabled, not yet activated, or bypassable), a single crafted contract call to a fixed precompile address (`ValidateMultiSign` / `BatchValidateSign`) with small actual calldata but a maliciously large encoded "array length" word would cause the executing JVM to attempt an allocation of up to ~2^31 array slots. This throws `OutOfMemoryError`/triggers heavy GC pressure during transaction execution inside the TVM, which is executed identically by every full node/witness validating the transaction — a denial-of-service / node-crash condition matching the CVE-2024-30253 bug class (untrusted length field driving unbounded memory allocation, leading to memory exhaustion and loss of availability).

### Likelihood Explanation
The energy cost for these precompiles (`getEnergyForData`) is computed from the actual `data.length` of the calldata, not from the encoded `len` value used for array allocation, so an attacker can keep the real payload small (and thus cheap in energy) while encoding an oversized length field inside it. This decouples the fee/energy metering from the actual memory cost of the operation, making the attack cheap to attempt via any account able to call a smart contract that invokes the precompile (or, since precompiles live at fixed reachable addresses, a directly crafted `TriggerSmartContract`). Likelihood is High only if the `allowTvmSelfdestructRestriction` guard is not universally active; this could not be confirmed with the available tools.

### Recommendation
- Move the `MAX_SIZE` bound check unconditionally before calling `extractBytesArray`/`extractSigArray`/`extractBytes32Array`, independent of the `allowTvmSelfdestructRestriction()` flag.
- Add an explicit upper bound check on `len` inside `extractBytesArray`, `extractSigArray`, and `extractBytes32Array` themselves (defense in depth), rejecting/erroring before allocating `new byte[len][]`.
- Ensure `len` is also validated against the actual remaining `words.length` to prevent both OOM and out-of-bounds/exception-based DoS.

### Proof of Concept
Conceptual PoC (cannot be executed here, described for a background engineer to reproduce/confirm):
1. Deploy a contract (or use `TriggerSmartContract` directly) targeting the `BatchValidateSign` precompile address.
2. Craft calldata following the ABI header layout expected by `BatchValidateSign.doExecute` (`hash`, offset word 1 for signatures, offset word 2 for addresses) such that `words[2]` (the addresses length field) is `0xFFFFFFFFFFFFFFFF...` (32 bytes of `0xFF`), so `intValueSafe()` returns `Integer.MAX_VALUE`.
3. Keep the rest of calldata minimal (a handful of words) so `getEnergyForData` reports low/negative `cnt` and the transaction fits within a normal fee limit.
4. Send the transaction; if `VMConfig.allowTvmSelfdestructRestriction()` is not active for the executing node's ruleset, `extractBytes32Array(words, ...)` executes `new byte[Integer.MAX_VALUE][]` before any size check, causing `OutOfMemoryError` during transaction execution on every node processing/replaying the block.

Note: full confirmation requires checking the current mainnet-activated value of `allowTvmSelfdestructRestriction()` (in `DynamicPropertiesStore`/`VMConfig`), which was not found in the indexed portion of the codebase — this should be verified in a live/full checkout before treating this as confirmed-exploitable in production.

    int len = words[offset].intValueSafe();

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
