### Title
Unauthenticated `RecvError` packets allow spoof-based teardown of established Nebula tunnels - (File: `outside.go`)

### Summary
`f.handleRecvError` in `outside.go` tears down an active tunnel (`f.closeTunnel(hostinfo)` + `hm.DeleteHostInfo(hostinfo)`) in response to a plaintext, unauthenticated `header.RecvError` packet. The only "authentication" performed is comparing the packet's UDP source address to the last known remote address stored for that `HostInfo`. Since UDP source addresses are attacker-controllable (spoofable) and this comparison happens before any certificate/handshake/AEAD verification, an attacker who possesses no CA-signed certificate at all can trigger termination of a legitimate tunnel between two authenticated peers by guessing/observing a 32-bit `RemoteIndex` and sending a single unauthenticated 8-byte header packet from a spoofed source.

### Finding Description
`readOutsidePackets` dispatches `header.RecvError` packets before any decryption or certificate check: [1](#0-0) 

`handleRecvError` then performs the "authentication": [2](#0-1) 

The logic is:
1. `hostinfo := f.hostMap.QueryReverseIndex(h.RemoteIndex)` — look up the tunnel purely by the attacker-supplied 32-bit index carried in the plaintext header.
2. `hr := hostinfo.GetRemote(); if hr.IsValid() && hr != addr { ... return }` — the *only* check that the sender is legitimate is that the UDP source address of the received packet matches the address Nebula believes the peer to be at.

This check is not cryptographic: the UDP source address is fully attacker-controlled on most networks (source-IP spoofing over UDP), and the `RemoteIndex` value is a per-tunnel identifier that is not secret — it is transmitted in the clear in the header of every ordinary data/handshake packet for that tunnel and can be observed by any on-path or off-path attacker who can see traffic (or who is co-located on a NAT'd network, etc.). No portion of the certificate, PSK, or Noise session state is checked before `closeTunnel` runs.

This is the same bug class as the referenced report: an operation that affects an existing, authorized relationship between two parties is executed based on an attacker-supplied identifier/address, with the "permission" check binding to the wrong thing (a spoofable UDP source address / an observable index) rather than to cryptographic proof of authorization (a valid Noise/cert-derived session). In the H-35 report, `from`/`to` addresses controlled by the attacker were trusted without an allowance check; here, the `RemoteIndex` + source-address pair controlled/observable by the attacker is trusted without any cryptographic proof, letting an outsider with zero certificate manipulate an established relationship between two legitimately certified peers.

### Impact Explanation
An attacker with no CA-signed certificate at all can force teardown of any established Nebula tunnel they can identify the `RemoteIndex` for (e.g., by sniffing/observing UDP traffic between the two victims, or via a MITM/NAT vantage point), by spoofing the UDP source to match (or when `hr` is not yet valid, without even needing to match) the peer's address and sending a bare `RecvError` header. This directly causes:
- Remote state poisoning / unauthorized termination of an authenticated session between two legitimate, cert-holding peers.
- Denial of service: repeated spoofed `RecvError` packets can be used to continuously disrupt tunnels, forcing costly re-handshakes and disrupting the overlay network's availability.

This matches the accepted "remote state poisoning" / "remote crash (of the tunnel) impact" categories.

### Likelihood Explanation
Exploitability depends on:
- The attacker learning a valid `RemoteIndex` for a target tunnel (observable in cleartext in every packet header of that tunnel, so any attacker with visibility into traffic between the peers, or a compromised/malicious network segment, can harvest it).
- The ability to spoof the UDP source address to match the recorded peer address (feasible on many network paths lacking egress/ingress filtering; note that when `hr.IsValid()` is false — e.g. relay-only tunnels without a direct remote yet established — no address check is performed at all).

Given the acceptance rules require reachability by an attacker without any CA-signed certificate, and the entire check here is a plaintext header value plus a spoofable UDP address (never anything cryptographically bound to the peers' certificates or Noise keys), likelihood is meaningful in typical unfiltered/UDP-spoofable network environments, though not universal (BCP38-compliant networks reduce viability).

### Recommendation
Do not act on `RecvError` (or any pre-handshake/plaintext control message) using only a UDP source-address comparison. Bind acceptance of `RecvError` to something cryptographically verifiable, e.g.:
- Require `RecvError` handling to be based on a MAC/token derived from the current session key (similar in spirit to the `VerifyRelay` authentication used for relay message types), rather than only index lookup + address match.
- Alternatively, only ignore/rate-limit `RecvError`-driven teardown, and require an authenticated `CloseTunnel` (already sent post-handshake, protected by AEAD) as the sole mechanism for peer-initiated teardown, rather than allowing an unauthenticated pre-handshake message to tear down an established, authenticated tunnel.

### Proof of Concept
1. Establish a legitimate Nebula tunnel between hosts A and B (both with valid CA-signed certs).
2. As an attacker with no certificate, observe/derive the `RemoteIndex` A uses for the tunnel to B (visible in cleartext in the Nebula header of any packet A sends/receives for that tunnel).
3. Craft an 8-byte `header.RecvError` packet: `header.Encode(buf, header.Version, header.RecvError, 0, remoteIndex, 0)`.
4. Send this packet via UDP to A, spoofing the source address to match B's known UDP endpoint (or, if the tunnel currently has no established direct remote — e.g. mid-handshake or relay-only — no spoofing is even required since `hr.IsValid()` is false).
5. A's `handleRecvError` (`outside.go:541-575`) will look up the hostinfo by `RemoteIndex`, pass the (spoofable) address check, and call `f.closeTunnel(hostinfo)` plus `hm.DeleteHostInfo(hostinfo)`, tearing down the legitimate tunnel without any cryptographic proof of authorization from the attacker.

Note: I was not able to fully verify the exact runtime constraints of `f.acceptRecvErrorConfig.ShouldRecvError(addr)` (rate limiting only, not authentication, based on the code read) nor how difficult `RemoteIndex` discovery is in a specific deployment; these are noted as areas of residual uncertainty that a full engagement/PoC run would need to confirm empirically.

func (f *Interface) handleRecvError(addr netip.AddrPort, h *header.H) {
	if !f.acceptRecvErrorConfig.ShouldRecvError(addr) {
		f.l.Debug("Recv error received, ignoring",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
		return
	}

	if f.l.Enabled(context.Background(), slog.LevelDebug) {
		f.l.Debug("Recv error received",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
	}

	hostinfo := f.hostMap.QueryReverseIndex(h.RemoteIndex)
	if hostinfo == nil {
		f.l.Debug("Did not find remote index in main hostmap", "remoteIndex", h.RemoteIndex)
		return
	}

	hr := hostinfo.GetRemote()
	if hr.IsValid() && hr != addr {
		f.l.Info("Someone spoofing recv_errors?",
			"addr", addr,
			"hostinfoRemote", hr,
		)
		return
	}

	f.closeTunnel(hostinfo)
	// We also delete it from pending hostmap to allow for fast reconnect.
	f.handshakeManager.DeleteHostInfo(hostinfo)
}
