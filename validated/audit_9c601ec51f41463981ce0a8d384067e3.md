### Title
Fixed-window stream throttle reset in `ConnectionStreamCounter::reset_throttling_params_if_needed` allows boundary-straddling clients to burst ~2x `max_streams_per_throttling_interval` streams per connection - ([File: streamer/src/nonblocking/stream_throttle.rs])

### Summary
`reset_throttling_params_if_needed` implements a fixed (non-sliding) window counter that zeroes `stream_count` only when elapsed time since `last_throttling_instant` strictly exceeds `STREAM_THROTTLING_INTERVAL`. An unstaked/unauthenticated QUIC client can open the maximum allowed streams at the very end of window N and immediately open another full allotment at the start of window N+1, doubling its effective stream rate for a short interval around each window boundary, which is exactly the failure mode the invariant is meant to prevent.

### Finding Description
`throttle_stream` (streamer/src/nonblocking/stream_throttle.rs:233-271) calls `stream_counter.reset_throttling_params_if_needed()` and then compares `stream_count` against `max_streams_per_throttling_interval` to decide whether to sleep the connection. The reset function uses a double-checked read/write lock: [1](#0-0) 

The counter and `last_throttling_instant` are only reset when `duration_since(last_throttling_instant) > STREAM_THROTTLING_INTERVAL`. This is a fixed-window rate limiter: it counts streams from the moment of the last reset to `last_throttling_instant + STREAM_THROTTLING_INTERVAL`, not over any rolling `STREAM_THROTTLING_INTERVAL`-length window. An attacker controlling the timing of stream opens on a single connection can:
1. Wait until just before the window boundary (`last_throttling_instant + STREAM_THROTTLING_INTERVAL - ε`) and open `max_streams_per_throttling_interval` streams, all counted against window N without triggering throttling.
2. Immediately after the boundary passes, the next call to `throttle_stream` triggers the reset (`stream_count.store(0, ...)`, `last_throttling_instant` updated to "now"), starting window N+1, and the attacker opens another `max_streams_per_throttling_interval` streams.

Within an actual elapsed time close to `2ε` (arbitrarily small), the connection is allowed roughly `2 * max_streams_per_throttling_interval` streams, violating the intended per-connection bound that should hold over any `STREAM_THROTTLING_INTERVAL`-length span of wall-clock time, regardless of when the attacker chooses to send packets.

### Impact Explanation
This is a QoS-evasion bug: the per-connection stream cap in `streamer/src/nonblocking/stream_throttle.rs`, which is the primary defense that bounds how much TPU stream-processing work an unstaked/unauthenticated remote client can push through a single QUIC connection, can be evaded by a factor of ~2x through pure timing of packet transmission — no cryptographic bypass, no need for elevated stake, and no special protocol trick, just controlling send timing. Since an attacker can open many connections (up to whatever the unstaked connection limit allows) and repeat this boundary-straddling technique on each of them independently, and repeat it at every subsequent window boundary for the life of each connection, this multiplies unstaked TPU stream ingestion capacity beyond the intended `max_streams_per_throttling_interval` design limit, unfairly capturing more of the leader's QUIC/TPU stream-processing budget than legitimate staked/unstaked senders following the intended cadence.

### Likelihood Explanation
Fully reachable by any unstaked remote client that can open a QUIC connection to a leader's public TPU port; no special privileges, keys, or peer/gossip control needed. The only requirement is timing stream opens relative to the (client-observable) throttling window edges, which is feasible since the attacker controls its own packet cadence and `STREAM_THROTTLING_INTERVAL_MS` is a fixed, public constant (100ms). The attacker can probe/calibrate the window boundary empirically (e.g., via induced throttling/backoff behavior) and then repeat the double-burst on every window transition, making the bug easily and repeatedly triggerable, not just a one-off race.

### Recommendation
Replace the fixed-window reset with a sliding-window or token-bucket algorithm so that at any instant, the number of streams accepted from a connection over the trailing `STREAM_THROTTLING_INTERVAL` never exceeds `max_streams_per_throttling_interval`. For example, track individual stream timestamps (or a leaky-bucket counter that decays continuously rather than resetting to zero at a hard boundary) instead of a single `stream_count` that is zeroed atomically once per interval.

### Proof of Concept
```rust
// streamer/src/nonblocking/stream_throttle.rs (test module)
#[tokio::test(start_paused = true)]
async fn test_fixed_window_boundary_burst_exceeds_limit() {
    let stats = Arc::new(StreamerStats::default());
    let counter = Arc::new(ConnectionStreamCounter::new());
    let max_streams: u64 = 10;
    let peer_type = ConnectionPeerType::Unstaked;
    let addr = "127.0.0.1:0".parse().unwrap();

    // Burst 1: consume the full allotment just before the window boundary.
    for _ in 0..max_streams {
        counter.stream_count.fetch_add(1, Ordering::Relaxed);
    }
    tokio::time::advance(STREAM_THROTTLING_INTERVAL - Duration::from_millis(1)).await;
    // No throttle should trigger yet since window hasn't elapsed.
    throttle_stream(&stats, peer_type, addr, &counter, max_streams).await;

    // Cross the boundary by 1ms -> reset triggers, window N+1 starts.
    tokio::time::advance(Duration::from_millis(2)).await;

    // Burst 2: immediately consume another full allotment in the new window.
    for _ in 0..max_streams {
        counter.stream_count.fetch_add(1, Ordering::Relaxed);
    }
    // total streams accepted within ~2ms of wall-clock time:
    let total_accepted = 2 * max_streams;
    // Assert violation: total streams over a real elapsed span << STREAM_THROTTLING_INTERVAL
    // exceeds max_streams_per_throttling_interval by more than a 1-stream tolerance.
    assert!(total_accepted > max_streams + 1,
        "fixed-window reset allowed {total_accepted} streams within a single throttling interval, expected <= {}",
        max_streams + 1);
}
```
Expected result: the assertion fails to hold under the intended invariant (streams over any rolling `STREAM_THROTTLING_INTERVAL` ≤ `max_streams_per_throttling_interval` + 1), demonstrating the boundary-straddling double-burst.

    pub(crate) fn reset_throttling_params_if_needed(&self) -> tokio::time::Instant {
        let last_throttling_instant = *self.last_throttling_instant.read().unwrap();
        if tokio::time::Instant::now().duration_since(last_throttling_instant)
            > STREAM_THROTTLING_INTERVAL
        {
            let mut last_throttling_instant = self.last_throttling_instant.write().unwrap();
            // Recheck as some other thread might have done throttling since this thread tried to acquire the write lock.
            if tokio::time::Instant::now().duration_since(*last_throttling_instant)
                > STREAM_THROTTLING_INTERVAL
            {
                *last_throttling_instant = tokio::time::Instant::now();
                self.stream_count.store(0, Ordering::Relaxed);
            }
            *last_throttling_instant
        } else {
            last_throttling_instant
        }
    }
