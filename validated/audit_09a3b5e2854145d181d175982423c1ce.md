### Title
Recipients can front-run `updateMerkleRoot()` to claim soon-to-be-removed rewards - ([File: contracts/utils/RecurringAirdrop.sol](contracts/utils/RecurringAirdrop.sol))

### Summary
`MetAirdrop` claims are authorized solely by the currently stored Merkle root, while `updateMerkleRoot()` replaces that root and updates `updatedAt` in the same privileged transaction. An eligible recipient under the outgoing root can observe a pending root update and front-run it with `claim()`, receiving the old allocation immediately before the new root can revoke or reduce it. [1](#0-0) [2](#0-1) 

### Finding Description
`RecurringAirdrop.claim()` builds the leaf from `msg.sender` and the supplied cumulative `amount_`, verifies it against the current `merkleRoot`, increments `claimed[msg.sender]`, and transfers the difference. [1](#0-0) 

The governor updates the authorization root by assigning `merkleRoot = merkleRoot_`; there is no grace-period bypass protection, pending-root mechanism, claim deadline, or revocation marker. [2](#0-1) 

For the deployed `MetAirdrop`, `_transferReward()` either sends liquid `MET` when `updatedAt + lockPeriod < block.timestamp`, or locks the claimed tokens in `esMET` for the remaining period. A front-run claim can therefore also receive treatment based on the old `updatedAt`, rather than the new distribution timestamp. [3](#0-2) 

### Impact Explanation
If a new distribution removes or reduces an account's allocation, the old root remains valid until `updateMerkleRoot()` executes. The targeted account can claim the outgoing allocation first, causing `claimed[msg.sender]` to be increased and the tokens to be transferred before the administrative update takes effect. [4](#0-3) 

This can cause direct loss of airdrop funds when the update is intended to revoke an outstanding entitlement. Even where the new root is cumulative, the attacker may obtain a shorter lock or immediate liquid `MET` by claiming under the old `updatedAt` boundary instead of waiting for the reset performed by the pending update. [3](#0-2) 

### Likelihood Explanation
The attack requires only a public `claim()` call by an account that has a valid proof under the currently active root. The governor transaction is visible in the public mempool, and no modifier on `claim()` prevents execution immediately before the root update. [5](#0-4) [6](#0-5) 

The only precondition is a pending update that changes the attacker's entitlement or distribution timing. Ordinary airdrop corrections and recurring allocations create such transitions; once observed, the attack is a single transaction.

### Recommendation
Make revocation/removal atomic with the authorization transition, or stop treating root replacement as a revocation boundary. Options include:

- Include a distribution identifier or expiry in each leaf and update `claimed` per distribution, rather than globally.
- Add a separate privileged pause/claim-disable step and activate the new root only after claims are disabled.
- Use a two-phase root update with an explicit activation timestamp, while defining whether the old root remains claimable during the transition.
- If the intent is that allocations are never revoked, document that behavior and do not rely on root replacement for revocation.
- In `MetAirdrop`, base the lock start on the distribution that authorized the claimed amount, or on `block.timestamp`, rather than a mutable global `updatedAt` shared across distributions. [7](#0-6)

```ts
  // 1. governor broadcasts updateMerkleRoot(rootWithoutAlice)
  // 2. alice inserts claim() before it.
```

```text
    function claim(uint256 amount_, bytes32[] calldata proof_) external nonReentrant {
        if (merkleRoot == bytes32(0)) revert NothingToClaim();

        bytes32 _leaf = keccak256(abi.encodePacked(msg.sender, amount_));
        if (!MerkleProof.verify(proof_, merkleRoot, _leaf)) revert InvalidProof();

        uint256 _claimable = amount_ - claimed[msg.sender];
        if (_claimable == 0) revert NothingToClaim();

        claimed[msg.sender] += _claimable;

        _transferReward(msg.sender, _claimable);
```

```text
    function updateMerkleRoot(bytes32 merkleRoot_, bytes32 proofsFileHash_) external onlyGovernor {
        if (merkleRoot_ == merkleRoot) revert NewMerkleRootSameAsCurrent();
        if (proofsFileHash_ == bytes32(0)) revert ProofsFileIsNull();

        merkleRoot = merkleRoot_;
        updatedAt = block.timestamp;
        proofsFileHash = proofsFileHash_;

        emit MerkleRootUpdated(merkleRoot_, block.timestamp);
```

```text
    function _transferReward(address to_, uint256 amount_) internal override {
        uint256 _end = updatedAt + lockPeriod;

        if (_end < block.timestamp) {
            MET.safeTransfer(to_, amount_);
            return;
        }

        uint256 _min = ESMET.MINIMUM_LOCK_PERIOD() + 1;
        uint256 _max = ESMET.MAXIMUM_LOCK_PERIOD();

        // Ensures valid lock period
        uint256 _remainLockPeriod = Math.min(Math.max(_end - block.timestamp, _min), _max);

        token.safeApprove(address(ESMET), 0);
        token.safeApprove(address(ESMET), amount_);
        ESMET.lockFor(to_, amount_, _remainLockPeriod);
```
