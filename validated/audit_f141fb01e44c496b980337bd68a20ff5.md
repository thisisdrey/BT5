### Title
Unchecked `reduceAssetAmountV2`/`addAssetAmountV2` return value in Exchange actuators can desynchronize TRC10 asset accounting - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeTransactionActuator.java`, `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`)

### Summary
`AccountCapsule.reduceAssetAmountV2`/`addAssetAmountV2` return a `boolean` that indicates whether the balance mutation actually succeeded, exactly like an ERC-20 `transfer` that "returns a Boolean on failure." Some call sites in java-tron correctly check this return value before proceeding (e.g. `TransferAssetActuator`, `Commons.adjustAssetBalanceV2`), but `ExchangeTransactionActuator.execute` and `ExchangeInjectActuator.execute` call these same methods and silently ignore the boolean result, exactly mirroring the "inconsistent use of safeTransfer" bug class described in the external report.

### Finding Description
`AccountCapsule.reduceAssetAmountV2` returns `false` (and performs no state change) when the current asset amount is `null` or insufficient: [1](#0-0) 

The correct, defensive pattern used elsewhere in the codebase checks this return value and aborts the transaction on failure: [2](#0-1) [3](#0-2) 

However, `ExchangeTransactionActuator.execute` calls `reduceAssetAmountV2`/`addAssetAmountV2` without checking the returned boolean, after having already computed and applied the exchange-pool balance update (`exchangeCapsule.transaction(...)` and `Commons.putExchangeCapsule(...)`): [4](#0-3) 

The same unchecked pattern exists in `ExchangeInjectActuator.execute`, where the exchange pool balances (`exchangeCapsule.setBalance(...)`) are updated first, and only afterward are `reduceAssetAmountV2` calls made without verifying success: [5](#0-4) 

Because the exchange-pool bookkeeping (`ExchangeCapsule`/`ExchangeV2Capsule`) and the account bookkeeping (`AccountCapsule` asset maps) are updated independently, and only the account-side mutation has a fallible boolean return that is discarded, any code path in which `reduceAssetAmountV2` fails after `validate()` has passed would leave the exchange pool state updated (reflecting tokens received) while the caller's account balance is left unchanged — a state desynchronization between the pool and the account ledger.

### Impact Explanation
If this silent-failure path is reachable, it produces an unbacked/duplicated balance: the caller keeps their original TRC10 tokens while the exchange pool simultaneously credits them as if received, and the pool's paired token balance is paid out to the caller. This is a fund-accounting integrity issue matching the report's class (loss/duplication of value due to unchecked balance-mutation status), reachable directly via a signed `ExchangeTransactionContract` or `ExchangeInjectContract` transaction from any unprivileged account holding TRC10 balances and access to an existing Exchange pair.

### Likelihood Explanation
Likelihood is **uncertain/likely low** in the current codebase because `validate()`/`doValidate()` in both actuators appears intended to pre-check sufficient asset balance before `execute()` runs (as is typical for these actuators, matching `TransferAssetActuator`'s validate flow), which would normally make `reduceAssetAmountV2` succeed deterministically whenever `execute()` is reached, since actuator execution is single-threaded and validate/execute operate on the same immutable object references within one transaction. I was not able to fully re-verify the complete body of `doValidate()` for `ExchangeTransactionActuator` and `ExchangeInjectActuator` within this session (tool call to read the full validate method failed before the session ended), so I cannot confirm with certainty whether there exists a discrepancy between the balance check performed in `validate()` (e.g., checking `assetBalanceEnoughV2` against a *different* token/amount combination than what's later reduced, or a same-token-name v1/v2 mismatch) that would allow `reduceAssetAmountV2` to fail after validation passes. This gap must be confirmed by tracing `doValidate()` in both actuators against the exact asset IDs used in `execute()`, and by checking whether `getAllowSameTokenName()` can change value between validate and execute of the same transaction (it cannot within one transaction, but historical fork-migration edge cases around V1/V2 asset maps are a known source of subtle inconsistencies in this codebase, as reflected in the extensive `SameTokenNameOpen/Close` test suites for these very actuators).

### Recommendation
- **Short term**: In `ExchangeTransactionActuator.execute` and `ExchangeInjectActuator.execute`, check the boolean return value of `reduceAssetAmountV2`/`addAssetAmountV2` (as already done in `TransferAssetActuator` and `Commons.adjustAssetBalanceV2`) and throw `ContractExeException` on failure, ensuring the exchange-pool balance mutation is not committed when the account-side mutation fails. Prefer performing the account-side mutation and its checks *before* mutating/persisting the exchange pool capsule, so a failed account update never leaves pool state inconsistent.
- **Long term**: Audit all call sites of `reduceAssetAmountV2`/`addAssetAmountV2`/`reduceAssetAmount`/`addAssetAmount` codebase-wide for consistent error checking, and add targeted unit tests that force a `reduceAssetAmountV2`/`addAssetAmountV2` failure inside `execute()` after `validate()` has passed, to confirm no such TOCTOU-style gap exists.

### Proof of Concept
Not independently confirmed as directly exploitable in this session. The suggested reproduction path for a follow-up engineer:
1. Set up an `ExchangeTransactionContract` (or `ExchangeInjectContract`) test using the existing `ExchangeTransactionActuatorTest`/`ExchangeInjectActuatorTest` harnesses.
2. Attempt to construct a scenario where `doValidate()`'s balance check and `execute()`'s `reduceAssetAmountV2` call operate on divergent token identifiers or amounts (e.g., exploiting `getAllowSameTokenName()` V1/V2 asset map inconsistencies, per the extensive `SameTokenNameOpen`/`SameTokenNameClose` test variants already present for these actuators).
3. If `reduceAssetAmountV2` returns `false` in `execute()` while the exchange pool balance and paired-asset credit have already been applied via `exchangeCapsule.transaction(...)`/`Commons.putExchangeCapsule(...)`, confirm the account's asset balance is unchanged while the exchange pool reflects the trade — demonstrating the accounting desynchronization.

  public boolean reduceAssetAmountV2(byte[] key, long amount,
                                     DynamicPropertiesStore dynamicPropertiesStore, AssetIssueStore assetIssueStore) {
    importAsset(key);
    //key is token name
    boolean disableJavaLangMath = dynamicPropertiesStore.disableJavaLangMath();
    if (dynamicPropertiesStore.getAllowSameTokenName() == 0) {
      Map<String, Long> assetMap = this.account.getAssetMap();
      AssetIssueCapsule assetIssueCapsule = assetIssueStore.get(key);
      String tokenID = assetIssueCapsule.getId();
      String nameKey = ByteArray.toStr(key);
      Long currentAmount = assetMap.get(nameKey);
      if (amount > 0 && null != currentAmount && amount <= currentAmount) {
        this.account = this.account.toBuilder()
                .putAsset(nameKey, subtractExact(currentAmount, amount, disableJavaLangMath))
                .putAssetV2(tokenID, subtractExact(currentAmount, amount, disableJavaLangMath))
                .build();
        return true;
      }
    }
    //key is token id
    if (dynamicPropertiesStore.getAllowSameTokenName() == 1) {
      String tokenID = ByteArray.toStr(key);
      Map<String, Long> assetMapV2 = this.account.getAssetV2Map();
      Long currentAmount = assetMapV2.get(tokenID);
      if (amount > 0 && null != currentAmount && amount <= currentAmount) {
        this.account = this.account.toBuilder()
                .putAssetV2(tokenID, subtractExact(currentAmount, amount, disableJavaLangMath))
                .build();
        return true;
      }
    }

    return false;
  }
