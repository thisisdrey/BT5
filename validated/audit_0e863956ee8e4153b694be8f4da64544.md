### Title
Cost model's `allocated_accounts_data_size` (used to enforce the per-block accounts-data-growth limit) ignores account resizing performed by non-System-program instructions, letting real data growth evade the block-level cap - ([File: cost-model/src/cost_model.rs])

### Summary
The cost model computes `TransactionCost::allocated_accounts_data_size`, which `CostTracker::would_fit()` uses to enforce `MAX_BLOCK_ACCOUNTS_DATA_SIZE_DELTA` (`WouldExceedAccountDataBlockLimit`). This estimate is derived *only* by statically parsing `system_program` instructions (`CreateAccount`, `Allocate`, etc.); any other program id yields `SystemProgramAccountAllocation::None`, contributing zero to the estimate. However, actual account data growth enforced at execution time (`can_data_be_resized` in `transaction-context`) applies to *any* program that reallocates account data (e.g., BPF programs calling `realloc`/CPI into System, or CPI-ed allocations), up to a much larger per-transaction cap. This mirrors the reported pattern: the admission/limit-check function (`maxDeposit`-analog: `would_fit`/`calculate_allocated_accounts_data_size`) uses a narrower, stricter-looking check than what the actual operation (`mint`-analog: real account resizing during execution) permits, so the enforced block-level resource budget can be silently exceeded by transactions the checker scored as consuming ~0 bytes of "allocated accounts data size."

### Finding Description
`CostModel::calculate_allocated_accounts_data_size` iterates the transaction's instructions and only recognizes allocation-causing instructions when the target `program_id` is the System program: [1](#0-0) 
For every other instruction (i.e., any CPI-driven or BPF-program-initiated account resize), the function returns `SystemProgramAccountAllocation::None` and contributes nothing to the estimate: [2](#0-1) 
The function's own doc comment acknowledges the gap: *"eventually, potentially determine account data size of all writable accounts / at the moment, calculate account data size of account creation."* [3](#0-2) 

This estimated value feeds `TransactionCost.allocated_accounts_data_size`, which `CostTracker::would_fit()` checks against `self.limits.allocated_data_size` (backed by `MAX_BLOCK_ACCOUNTS_DATA_SIZE_DELTA`), returning `CostTrackerError::WouldExceedAccountDataBlockLimit` when exceeded: [4](#0-3) 

Meanwhile, the actual enforcement of account-data growth during transaction execution is entirely separate and much more permissive: `TransactionAccounts::can_data_be_resized` allows any account resize (regardless of which program performed it) up to `MAX_ACCOUNT_DATA_GROWTH_PER_TRANSACTION`: [5](#0-4) 

Because these two paths are decoupled — one gating block admission based on a System-program-only static scan, the other permitting real resizing for any program at runtime — a transaction that resizes accounts exclusively via a non-System program (e.g., a BPF/CPI-based reallocation, or a CPI into System from a custom program where the cost model's static per-instruction `program_id` check does not attribute the allocation to System) is scored as allocating 0 bytes by the cost model while still being permitted to grow account data up to the real per-transaction cap during execution. Stacking many such transactions in one block lets the block's actual total account-data growth vastly exceed `MAX_BLOCK_ACCOUNTS_DATA_SIZE_DELTA` (100,000,000 bytes) without the `would_fit`/`WouldExceedAccountDataBlockLimit` gate ever tripping, since the tracker's bookkeeping variable (`allocated_accounts_data_size`) never reflects the true growth.

### Impact Explanation
This is analogous to the report's "grossly underpriced pre-fee work" pattern: the resource actually consumed by execution (real per-account data growth, up to `MAX_ACCOUNT_DATA_GROWTH_PER_TRANSACTION` per transaction) is not priced/limited by the mechanism meant to bound it at the block level. This allows an unprivileged transaction submitter to cause a leader's produced block to grow account data storage far beyond the intended per-block budget (`MAX_BLOCK_ACCOUNTS_DATA_SIZE_DELTA`), which is meant to bound the rate of new on-disk/in-memory account storage growth per slot across the cluster. Uncapped growth here increases disk usage, snapshot size, and replay load for every downstream validator that must replay the block, and defeats the specific QoS control designed to prevent this class of storage-growth abuse.

### Likelihood Explanation
Reachable by any unprivileged user submitting ordinary transactions through banking stage: any transaction whose account-data growth is driven by a non-System-program instruction (CPI-based reallocation, e.g. a program that itself calls `system_instruction::allocate`/`realloc` as an inner instruction, or any BPF program using account `realloc`) is scored as `allocated_accounts_data_size == 0` by the static cost model, regardless of how much data it actually grows at execution time up to the per-tx cap. No special privileges, malicious snapshots, or multi-client coordination are required — only crafting instructions whose top-level `program_id` (as seen by `calculate_account_data_size_on_instruction`) is not `system_program::id()`.

### Recommendation
Extend the cost-model's static allocation estimate (or add an execution-time reconciliation similar to `calculate_cost_for_executed_transaction`'s use of actual `loaded_accounts_data_size`) so that `allocated_accounts_data_size` used for block-level budgeting reflects real account-data growth performed by any program, not only top-level System-program instructions. At minimum, feed the real `resize_delta` tracked in `transaction-context/src/transaction_accounts.rs` back into the cost tracker's `allocated_data_size` accounting after execution, the same way `get_transaction_costs` already reconciles CU and loaded-account-size costs post-execution in `runtime/src/transaction_execution.rs`.

### Proof of Concept
1. Deploy (or use an existing) BPF program `P` that, when invoked, calls `AccountInfo::realloc` (or CPIs into the System program's `Allocate`/`CreateAccount` instruction as an *inner* instruction) to grow an account's data by close to `MAX_ACCOUNT_DATA_GROWTH_PER_TRANSACTION` bytes per transaction.
2. Submit a transaction whose top-level instruction invokes `P` (program_id ≠ `system_program::id()`).
3. Observe that `CostModel::calculate_account_data_size_on_instruction` returns `SystemProgramAccountAllocation::None` for this instruction (per [1](#0-0) ), so `calculate_allocated_accounts_data_size` computes `0` for the transaction.
4. `CostTracker::would_fit` never rejects the transaction for `WouldExceedAccountDataBlockLimit` since its recorded `allocated_accounts_data_size` contribution is `0` (per [4](#0-3) ).
5. During execution, `can_data_be_resized` still permits the real resize up to `MAX_ACCOUNT_DATA_GROWTH_PER_TRANSACTION` (per [5](#0-4) ), so the account genuinely grows.
6. Repeat across many transactions packed into one block; the cost tracker's block-level `allocated_accounts_data_size` total remains near `0` while the block's real accumulated account-data growth can approach `(num_transactions * MAX_ACCOUNT_DATA_GROWTH_PER_TRANSACTION)`, exceeding `MAX_BLOCK_ACCOUNTS_DATA_SIZE_DELTA` (100,000,000 bytes) with no rejection from the cost-model gate.

Note: I was unable to fully verify (due to reaching the tool-call limit) whether some other independent, block-level hard check on total on-chain accounts-data-size delta exists outside the cost-tracker path that would also need to be bypassed; `Bank::load_accounts_data_size_delta_on_chain` tracks a running total but I could not confirm within this session whether any hard per-block cap is enforced against it separately from the cost model discussed here.

    /// eventually, potentially determine account data size of all writable accounts
    /// at the moment, calculate account data size of account creation
    fn calculate_allocated_accounts_data_size<'a>(
        instructions: impl Iterator<Item = (&'a Pubkey, SVMInstruction<'a>)>,
        feature_set: &FeatureSet,
    ) -> u64 {
        let mut tx_attempted_allocation_size = Saturating(0u64);
        for (program_id, instruction) in instructions {
            match Self::calculate_account_data_size_on_instruction(
                program_id,
                instruction,
                feature_set,
            ) {
                SystemProgramAccountAllocation::Failed => {
                    // If any system program instructions can be statically
                    // determined to fail, no allocations will actually be
                    // persisted by the transaction. So return 0 here so that no
                    // account allocation budget is used for this failed
                    // transaction.
                    return 0;
                }
                SystemProgramAccountAllocation::None => continue,
                SystemProgramAccountAllocation::Some(ix_attempted_allocation_size) => {
                    tx_attempted_allocation_size += ix_attempted_allocation_size;
                }
            }
        }

        // The runtime prevents transactions from allocating too much account
        // data so clamp the attempted allocation size to the max amount.
        //
        // Note that if there are any custom bpf instructions in the transaction
        // it's tricky to know whether a newly allocated account will be freed
        // or not during an intermediate instruction in the transaction so we
        // shouldn't assume that a large sum of allocations will necessarily
        // lead to transaction failure.
        (MAX_PERMITTED_ACCOUNTS_DATA_ALLOCATIONS_PER_TRANSACTION as u64)
            .min(tx_attempted_allocation_size.0)
    }

    fn would_fit(
        &self,
        tx_cost: &TransactionCost<impl TransactionWithMeta>,
    ) -> Result<(), CostTrackerError> {
        let cost: u64 = tx_cost.sum();

        if self.block_cost().saturating_add(cost) > self.limits.block_cost {
            // check against the total package cost
            return Err(CostTrackerError::WouldExceedBlockMaxLimit);
        }

        // check if the transaction itself is more costly than the account_cost_limit
        if cost > self.limits.account_cost {
            return Err(CostTrackerError::WouldExceedAccountMaxLimit);
        }

        let allocated_accounts_data_size =
            self.allocated_accounts_data_size + Saturating(tx_cost.allocated_accounts_data_size());

        if allocated_accounts_data_size.0 > self.limits.allocated_data_size {
            return Err(CostTrackerError::WouldExceedAccountDataBlockLimit);
        }

    pub(crate) fn can_data_be_resized(
        &self,
        old_len: usize,
        new_len: usize,
    ) -> Result<(), InstructionError> {
        // The new length can not exceed the maximum permitted length
        if new_len > MAX_ACCOUNT_DATA_LEN as usize {
            return Err(InstructionError::InvalidRealloc);
        }
        // The resize can not exceed the per-transaction maximum
        let length_delta = (new_len as i64).saturating_sub(old_len as i64);
        if self.resize_delta.get().saturating_add(length_delta)
            > MAX_ACCOUNT_DATA_GROWTH_PER_TRANSACTION
        {
            return Err(InstructionError::MaxAccountsDataAllocationsExceeded);
        }
        Ok(())
    }
