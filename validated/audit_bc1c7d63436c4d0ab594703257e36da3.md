### Title
`ParticipateAssetIssueActuator` reverts legitimate participation for low-priced assets due to `multiplyExact` overflow before precision downscaling - (File: `actuator/src/main/java/org/tron/core/actuator/ParticipateAssetIssueActuator.java`)

### Summary
`ParticipateAssetIssueActuator.validate()` and `execute()` compute the exchanged asset amount as `exchangeAmount = multiplyExact(cost, assetIssueCapsule.getNum())` followed by `floorDiv(exchangeAmount, trxNum)`, mirroring the reported pattern of doing full-precision multiplication before dividing down. Because `multiplyExact` throws `ArithmeticException` on overflow rather than downscaling precision first, any user attempting to participate with a `cost` (TRX amount) large enough that `cost * num` exceeds `Long.MAX_VALUE` will have their transaction rejected, even though the final `exchangeAmount` (after division by `trxNum`) would fit well within valid bounds.

### Finding Description
In `execute()`: [1](#0-0) 

and identically in `validate()`: [2](#0-1) 

`multiplyExact(long, int)` delegates to `AbstractActuator.multiplyExact` which uses `Maths.multiplyExact` and throws `ArithmeticException` on overflow: [3](#0-2) 

This is the same root-cause pattern as the referenced Yieldoor `Vault::_calcDeposit()` issue: the code multiplies two large user/config-controlled quantities (`cost` and `num`) to full precision *before* dividing by `trxNum`, instead of scaling down first (e.g., using `BigInteger`, as is done elsewhere in the codebase such as `ExchangeInjectActuator` and `ExchangeWithdrawActuator`, which use `BigInteger` multiply/divide specifically to avoid this class of overflow): [4](#0-3) 

For an asset issue with a "low priced" ratio (`num` large relative to `trxNum`, i.e. attacker/issuer sets `num` near `Integer.MAX_VALUE` while `trxNum` is small, meaning few TRX buy many tokens), any `cost` exceeding `Long.MAX_VALUE / num` overflows. This is directly analogous to the tests already present in the repo demonstrating this exact overflow (`sameTokenNameCloseMultiplyOverflowTest`, `sameTokenNameOpenMultiplyOverflowTest`): [5](#0-4) 

### Impact Explanation
When `cost * num` overflows, `validate()` catches the `ArithmeticException` and converts it into a `ContractValidateException`, causing the transaction to fail: [6](#0-5) 

This is a denial-of-service against legitimate participation in low-priced asset issues: any unprivileged transaction broadcaster attempting to buy a reasonably large (but otherwise valid) amount of a low-priced token via `ParticipateAssetIssueContract` is unconditionally blocked, even though the true `exchangeAmount` after dividing by `trxNum` would be within `long` bounds. This matches the reported impact class ("users miss out on favorable pricing / lose ability to participate") for a broadcastable, unprivileged transaction type — `ParticipateAssetIssueContract` is a standard actuator reachable by any account with sufficient TRX balance.

### Likelihood Explanation
Reachable by any account that constructs a `ParticipateAssetIssueContract` with a `cost` (TRX) and targets an asset with a large `num`/small `trxNum` ratio — issuers of asset offerings routinely set arbitrary `num`/`trxNum` ratios up to `int` range, and users choosing to invest a large TRX amount into a "cheap" token will trigger the overflow deterministically. No malicious/privileged setup is required beyond an asset issuer choosing a low price ratio (a normal, permitted operation via `AssetIssueContract`), making this straightforward to reach in production without any adversarial node behavior.

### Recommendation
Replace the `multiplyExact`/`floorDiv` sequence in both `validate()` and `execute()` of `ParticipateAssetIssueActuator` with a `BigInteger`-based (or otherwise overflow-safe, precision-preserving) computation of `exchangeAmount = cost * num / trxNum`, following the same pattern already used in `ExchangeInjectActuator`/`ExchangeWithdrawActuator`, so legitimate large-`cost` participations against low-priced assets are not rejected due to intermediate overflow.

### Proof of Concept
Given an asset issued with `trxNum = 1` and `num = Integer.MAX_VALUE` (2147483647), a user calling `ParticipateAssetIssueContract` with `cost` just above `Long.MAX_VALUE / Integer.MAX_VALUE` (~4.3 billion sun, i.e. ~4300 TRX) causes `multiplyExact(cost, num)` to throw `ArithmeticException`, rejecting the transaction in `validate()` despite `exchangeAmount = cost * num / trxNum` being a valid representable value conceptually. This mirrors the existing repo test `sameTokenNameOpenMultiplyOverflowTest`/`sameTokenNameCloseMultiplyOverflowTest`, which already document this overflow occurring for realistic `num`/`trxNum`/`cost` combinations: [7](#0-6)
