### Title
Unbounded array allocation from attacker-controlled length field in TVM precompile ABI decoding leads to Denial-of-Service (OOM crash) - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The CVE describes an integer-overflow-driven unchecked array allocation while parsing an untrusted length field from a crafted file (`value` array in GTKWave's LXT2 parser). The closest reachable analog in java-tron is the ABI-array decoding helpers in `PrecompiledContracts.java`, which take a length word directly from attacker-supplied contract call data and use it to size a Java array **before** validating it against the actual size of the remaining call data.

### Finding Description
`extractBytesArray`, `extractSigArray`, and `extractBytes32Array` read an unvalidated length from the decoded `DataWord[] words` array (which is built directly from the raw calldata bytes an EOA or contract sends to a precompiled contract address) and immediately allocate a Java array of that size: [1](#0-0) [2](#0-1) [3](#0-2) 

The `len` value is obtained via `words[offset].intValueSafe()`. Unlike a bounds-checked or overflow-rejecting parse, `intValueSafe()` only guards against values that don't fit in a Java `int`/negative results — it can still legitimately return a value as large as `Integer.MAX_VALUE`. None of the three helper methods check `len` against `words.length` or against the actual remaining calldata before doing `new byte[len][]`. This mirrors the CVE's root cause: a size value taken from untrusted input is used to allocate an array without validating it against the bounds of the actual backing buffer, so a single crafted call can request an allocation of `Integer.MAX_VALUE` pointer-sized array slots.

### Impact Explanation
Any unprivileged account able to broadcast a `TriggerSmartContract` transaction (or any contract that internally issues a call/staticcall) to the precompiled address that uses these helpers can force the node to attempt an extremely large heap allocation. Because this is a `new byte[len][]`/array-of-arrays allocation, it will typically throw `OutOfMemoryError`, which is an `Error`, not an `Exception` — most defensive `catch (Exception e)` wrappers around contract execution paths do not catch `Error`, so this can propagate and terminate/destabilize the node process handling the transaction, resulting in denial of service (node crash/halt) for a single crafted transaction. This falls squarely in the "TVM opcodes, precompiles and energy metering" reachable-surface bucket allowed by the rules and matches the "node crash or halt" impact criterion.

### Likelihood Explanation
Any transaction broadcaster or contract deployer can invoke a precompiled contract by address with arbitrary calldata; no special privilege, node control, or witness/committee role is required. The malicious length only needs to appear at the expected offset in the ABI-decoded words for these helper methods to be invoked with attacker-chosen `len`.

### Recommendation
Bound-check `len` immediately after reading it from calldata in `extractBytesArray`, `extractSigArray`, and `extractBytes32Array` — reject (return empty/throw a caught `Program.Exception`) whenever `len` exceeds a sane maximum (e.g., the number of remaining `words`, or a fixed precompile-specific cap) before allocating any array, mirroring the CVE fix pattern of validating supplied length against available data length (as already done elsewhere in the codebase, e.g. `RLP.verifyLength`) [4](#0-3) .

### Proof of Concept
1. Deploy or call an existing contract that performs a `STATICCALL`/`CALL` to the precompiled contract address whose `execute()` implementation uses `extractBytesArray`/`extractSigArray`/`extractBytes32Array` for ABI decoding of an array parameter.
2. Craft the calldata so the length word at the expected array-length offset is set to a very large value (e.g., `0x7FFFFFFF`), while keeping the word syntactically valid so `intValueSafe()` returns that large `int` rather than clamping to an error.
3. Broadcast the transaction; the node attempts `new byte[0x7FFFFFFF][]` (or `byte[len][32]`/`byte[len][64]` variants), driving an out-of-memory condition that can crash or hang the executing node.

Note: I was not able to fully trace, within the available search budget, exactly which precompiled contract(s) invoke `extractBytesArray`/`extractSigArray`/`extractBytes32Array` at their call sites, nor confirm whether an outer `catch (Throwable)` wraps precompile execution somewhere in `Program`/`OperationActions` that might catch the resulting `OutOfMemoryError` before it destabilizes the whole node. This should be verified by a background agent with full grep/build access before treating the DoS impact as fully confirmed.

    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;

          bytesLen);
    }
    return bytesArray;
  }
