Audit Report

## Title
Unbounded, unmetered `receipt_proof` in Snowbridge `EthereumInboundQueueV2::submit` allows fixed-fee, CPU-underpriced spam of Merkle-Patricia proof verification - ([File: bridges/snowbridge/pallets/inbound-queue-v2/src/lib.rs])

## Summary
`submit()` charges the flat weight `T::WeightInfo::submit()` regardless of the size of the caller-supplied `Proof.receipt_proof: Vec<Vec<u8>>`, which is decoded and Merkle-verified via `verify_receipt_proof` before the nonce/gateway checks reject the call. Since `receipt_proof` carries no `BoundedVec`/length cap and the benchmark used a single small fixture (309 bytes measured), a funded account can submit `receipt_proof` vectors far larger than the benchmarked fixture (up to the extrinsic/block length limit) while paying the same fixed weight fee, letting the pallet under-charge for CPU spent in trie-node decoding/hashing.

## Finding Description
`submit()` is a public, any-signed-account extrinsic that first calls `T::Verifier::verify(&event.event_log, &event.proof)` before any cheap nonce/gateway check in `process_message` runs: [1](#0-0) 

`Verifier::verify` (implemented in `pallet-ethereum-client`) first runs `verify_execution_proof`, whose cost is bounded (fixed-depth ancestry/execution-header Merkle branches against on-chain finalized state), and only then calls `verify_receipt_inclusion` → `verify_receipt_proof`, whose cost scales with the caller-supplied `receipt_proof` node count/size: [2](#0-1) 

`receipt_proof` is a plain `Vec<Vec<u8>>` with no length bound or `MaxEncodedLen`: [3](#0-2) 

`verify_receipt_proof` iterates/decodes/hashes over exactly the nodes supplied by the caller: [4](#0-3) 

The weight annotation is a single flat constant derived from one small benchmarked fixture, not scaled to `receipt_proof` size: [5](#0-4) [6](#0-5) 

Because `verify_execution_proof` only checks the beacon-header/execution-header linkage (fixed-depth, does not touch `receipt_proof`), an attacker can reuse a genuinely valid `ExecutionProof` (obtainable from any real relayed message, since finalized beacon data is public) and pad `receipt_proof` with additional/larger byte vectors. `verify_proof` from `alloy_trie` will still decode and hash every supplied node before failing, so cost grows with attacker-chosen `receipt_proof` size while the extrinsic still only pays the fixed ~60µs weight fee.

## Impact Explanation
This matches the allowed impact "public underpriced work that degrades block production or stalls bridge processing." An unprivileged, funded signed account (no relayer, validator, or governance role needed) can submit `submit()` calls with reused valid execution proofs and inflated `receipt_proof` vectors to force CPU consumption disproportionate to the fixed weight fee actually charged, potentially delaying legitimate relayer message processing on BridgeHub. The severity is capped by two factors not fully accounted for in the original claim: (1) `verify_execution_proof` runs first and is cheap/fixed-cost, so it does not itself amplify cost; (2) the maximum size of `receipt_proof` is ultimately bounded by the runtime's extrinsic/block length limit, and larger encodings already cost proportionally more in the transaction length fee — meaning the true "under-pricing" is limited to the weight-fee component, not an unbounded resource sink. I could not verify the exact magnitude of the mismatch (worst-case proof size × per-node decode/hash cost vs. benchmarked 60µs) since no worst-case benchmark exists in this session/repo state.

## Likelihood Explanation
Likelihood is moderate: any funded account can perform this without special privilege, and the flat weight lets a crafted proof consume more CPU than what is billed to the weight budget. However, exploitation requires (a) obtaining a currently-valid `ExecutionProof` for a finalized header (public data, not privileged, but adds a small barrier), and (b) accepting the length-based transaction fee cost for large proofs, which does scale with size and partially offsets the incentive. The core gap — `submit()`'s weight not scaling with `receipt_proof` length/size, and no `BoundedVec`/`MaxEncodedLen` cap on `Proof.receipt_proof` — is real and verifiable in the current code.

## Recommendation
- Bound `receipt_proof` (and each node) with an explicit maximum length/size, rejecting oversized proofs before verification, e.g., wrap in a `BoundedVec` with a constant sized to the deepest realistic Ethereum receipts-trie proof.
- Benchmark and charge `submit()`'s weight as a function of `receipt_proof.len()`/total encoded size (or at minimum benchmark against a worst-case bounded proof), rather than a single small fixture-derived constant.
- Consider capping total proof node count/size checked in `verify_receipt_proof` explicitly, independent of the pallet-level bound, so the underlying primitive is robust even if reused elsewhere.

## Proof of Concept
1. Take any genuinely valid `EventProof` (e.g., from a real relayed Ethereum event) so `verify_execution_proof` passes cheaply.
2. Replace `proof.receipt_proof` with a much larger `Vec<Vec<u8>>` (many maximally-sized byte vectors, up to the extrinsic/block length limit) that is syntactically decodable but fails the actual trie path match.
3. Call `InboundQueue::submit(origin, Box::new(event))` from a funded signed account repeatedly; each call pays the fixed `T::WeightInfo::submit()` fee (~60µs benchmarked from a 309-byte fixture, per `bridges/snowbridge/pallets/inbound-queue-v2/src/benchmarking.rs` and the generated weights file) while `verify_receipt_proof` performs decode/hash work proportional to the actual, much larger, supplied proof.
4. Compare wall-clock execution time against the benchmarked weight to demonstrate the CPU/weight mismatch (not empirically measured in this session — the finding rests on the fixed-weight annotation versus the unbounded `Vec<Vec<u8>>` input to `verify_proof`).

```rust
	fn verify(event_log: &Log, proof: &Proof) -> Result<(), VerificationError> {
		// Refuse to verify any Ethereum-side proof while the beacon light client is halted.
		// Governance halts the light client when it suspects a compromise (e.g. sync committee
		// takeover), at which point any signed headers/receipts must be treated as untrusted.
		// Covers every Verifier consumer, including `inbound_queue_v2::submit` and
		// `outbound_queue_v2::submit_delivery_receipt` (which would otherwise still drain
		// pending relayer rewards while the bridge is halted).
		ensure!(!Self::operating_mode().is_halted(), VerificationError::Halted);

		Self::verify_execution_proof(&proof.execution_proof)
			.map_err(|e| InvalidExecutionProof(e.into()))?;

		Self::verify_receipt_inclusion(
			proof.execution_proof.execution_header.receipts_root(),
			event_log.tx_index,
			&proof.receipt_proof,
			event_log,
		)?;

		Ok(())
	}
```

```rust
pub fn verify_receipt_proof(
	receipts_root: H256,
	tx_index: u64,
	proof: &[Vec<u8>],
) -> Option<ReceiptEnvelope> {
	let key = receipt_trie_key(tx_index);
	let root = B256::from_slice(receipts_root.as_bytes());
	let proof_nodes: Vec<Bytes> = proof.iter().map(|node| Bytes::copy_from_slice(node)).collect();

	// Call verify_proof with None to extract the value from an inclusion proof. For inclusion
	// proofs, alloy_trie returns ValueMismatch with the extracted value in `got`. The proof is
	// already cryptographically verified during this traversal.
	let value = match verify_proof(root, key, None, proof_nodes.iter()) {
		Ok(()) => return None, // Exclusion proof - key does not exist
		Err(ProofVerificationError::ValueMismatch { path, got: Some(v), expected: None })
			if path == key =>
		{
			v.to_vec()
		},
		Err(_) => return None,
	};

	ReceiptEnvelope::decode(&mut value.as_slice()).ok()
}
```
