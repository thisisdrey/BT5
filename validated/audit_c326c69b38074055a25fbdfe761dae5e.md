### Title
Attacker can permanently squat a victim's bounded per-account token list via dust `DepositToken` transfers, blocking new deposits - ([File: contracts/DepositToken.sol](contracts/DepositToken.sol), [File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
Analogous to CVE-2017-8934 — where an unprivileged local user pre-creates a predictable `/tmp` socket file so the legitimate application cannot acquire it — `Pool` gives each account a **bounded, first-come resource** (`depositTokensOfAccount` + `debtTokensOfAccount`, capped at `MAX_TOKENS_PER_USER = 30`) that **any** holder of a listed `DepositToken` can append to *on behalf of a victim* simply by `transfer`ring dust to them. Once the victim's combined list reaches 30 entries, every mint of a new collateral type reverts with `UserReachedMaxTokens`, denying the victim the ability to deposit new collateral (or be seized a new collateral type), i.e. a denial of service on a resource the victim never chose to occupy.

### Finding Description
`Pool` enforces a hard per-account cap:

```solidity
// contracts/Pool.sol
uint256 public constant MAX_TOKENS_PER_USER = 30; // L79

modifier onlyIfAdditionWillNotReachMaxTokens(address account_) {
    if (debtTokensOfAccount.length(account_) + depositTokensOfAccount.length(account_) >= MAX_TOKENS_PER_USER) {
        revert UserReachedMaxTokens();
    }
    _;
}
```

The cap is enforced inside `addToDepositTokensOfAccount` / `addToDebtTokensOfAccount` (confirmed by the repo's own test `should revert when reach max tokens` in `test/Pool.test.ts:1386-1416`).

Critically, entries are added on **any** balance-creation event, including permissionless ERC-20-style transfers the recipient never consented to:

```solidity
// contracts/DepositToken.sol
function _transfer(address sender_, address recipient_, uint256 amount_) private ... {
    ...
    // Add this token to the deposit tokens list if the recipient is receiving it for the 1st time
    if (_recipientBalanceBefore == 0 && amount_ > 0) {
        pool.addToDepositTokensOfAccount(recipient_);   // L518-520
    }
    ...
}
```

`transfer` (L348-354) and `transferFrom` (L357-376) are callable by any EOA. An attacker who deposits once into each of the pool's `DepositToken`s (or dust `transferFrom`s after acquiring approval-free balances via `deposit`) can then send 1 wei of each distinct `DepositToken` to the victim, filling the victim's list to 30. Thereafter:

- `DepositToken.deposit(amount, onBehalfOf = victim)` → `_mint` → `pool.addToDepositTokensOfAccount(victim)` reverts for any collateral the victim does not already hold (L486-488).
- `DebtToken.issue` paths that add a new debt token likewise revert.
- `Pool.liquidate` → `seize` → `_transfer` reverts if the seized collateral is a token the victim-liquidator doesn't already hold — this also **griefs liquidations**: a liquidator whose own list is full cannot receive a new collateral type via `seize` (L343-345 routes through `_transfer`), weakening the liquidation market. An attacker can deliberately pre-fill their own counterparty's — or a known active liquidator bot's — list to reduce liquidation competition, though this secondary effect is opportunistic.

The victim's *existing* balances remain withdrawable (`_withdraw` removes entries, L460-462, and does not consult the cap), and the victim can self-recover by transferring the dust balances onward (which pops the entry when the balance hits zero). The denial therefore persists only until the victim detects the squatting entries and clears them — identical in character to the CVE: the legitimate user's operation fails because an attacker occupied a predictable bounded resource, and service resumes only after manual cleanup the victim may not know is needed (the revert gives no indication of which token is the squatter).

### Impact Explanation
- **Temporary freezing of protocol functionality / griefing**: targeted users cannot onboard new collateral types or new debt instruments until they diagnose and evict dust entries. For a user racing to add collateral against a deteriorating position, each forced eviction costs a transaction and can be continuously re-squatted by the attacker (attacker re-sends dust after each eviction), sustaining the DoS against that account for as long as the attacker funds the attack.
- **Liquidation interference**: filling a liquidator's account list prevents `seize` of collateral types they don't hold, reducing effective liquidation coverage for positions collateralized by those tokens.

No modifier stops this: `transfer`/`transferFrom` are unguarded (only `_revertIfLocked` on the *sender*), `addToDepositTokensOfAccount` trusts the caller `DepositToken`, and pause/shutdown flags are irrelevant to the deposit path while the pool is live.

### Likelihood Explanation
Low-to-moderate. The attack is permissionless and deterministic, but costs the attacker real deposits across up to 30 distinct collateral tokens (plus gas) and yields no direct profit — it is pure griefing/DoS against a specific victim, matching the Medium-severity local-DoS profile of CVE-2017-8934. The victim can self-remediate, which keeps impact below fund-freezing thresholds, but remediation requires off-chain awareness and repeated transactions that the attacker can continually undo.

### Recommendation
- Do not add `DepositToken`s to `depositTokensOfAccount` on plain `transfer`/`transferFrom`; only track tokens the account explicitly `deposit`ed (or was `seize`d), or gate additions behind a minimum balance threshold.
- Alternatively, cap enforcement should apply per token *kind* the account consented to (e.g., only count entries where the account has performed a deposit), or provide a `removeTokenFromAccount(token)` escape that burns/donates dust on the victim's behalf in one call.
- Document the eviction path (`transfer` full dust balance to self/other) if the design is kept.

### Proof of Concept
Hardhat sketch (mirroring `test/Pool.test.ts` helpers):

```typescript
// given: pool with >= 30 enabled DepositTokens d1..d30 and a DebtToken
// attacker deposits dust into each deposit token
for (const dt of depositTokens) {
  await underlying(dt).mint(attacker.address, dust);
  await underlying(dt).connect(attacker).approve(dt.address, dust);
  await dt.connect(attacker).deposit(dust, attacker.address); // attacker gets msdToken_i
}

// attacker squats victim's list
for (const dt of depositTokens) {
  await dt.connect(attacker).transfer(victim.address, 1); // adds entry via _transfer -> addToDepositTokensOfAccount
}
expect(await pool.getDepositTokensOfAccount(victim.address)).to.have.lengthOf(30);

// victim tries to deposit a NEW collateral type -> reverts
await expect(newDepositToken.connect(victim).deposit(amount, victim.address))
  .revertedWithCustomError(pool, 'UserReachedMaxTokens');

// victim evicts one squatter -> deposit succeeds again
await firstDepositToken.connect(victim).transfer(attacker.address, 1); // balance 0 -> removed
await newDepositToken.connect(victim).deposit(amount, victim.address); // succeeds
// attacker immediately re-squats
await firstDepositToken.connect(attacker).transfer(victim.address, 1); // list back to 30
```

Note on confidence: the exact body of `Pool.addToDepositTokensOfAccount` was not fully read (the grep confirmed its existence and the tests confirm it enforces `UserReachedMaxTokens` and `DepositTokenAlreadyExists`); the claim that `transfer`-triggered additions consume the victim's cap follows directly from `_transfer` calling the same capped function.
