### Title
Points dissolved without matching sub-pool balance released when withdrawal-time era diverges from unbond-time era in nomination pools - (File: `substrate/frame/nomination-pools/src/lib.rs`)

### Summary
`Pallet::withdraw_unbonded` in `pallet-nomination-pools` dissolves a member's unbonding points and removes their `unbonding_eras` entry based on one era value (`T::StakeAdapter::current_era()`), then attempts to pull the corresponding balance out of `SubPools::with_era`, which was populated at `unbond()` time keyed by whatever era the pool computed for that unbond. If the era used to *release points* diverges from the era used to *locate the balance bucket*, the code falls back to `no_era.dissolve(...)`, silently succeeding even when `no_era` holds no matching balance for those points — permanently losing the member's funds while marking them as withdrawn. This is the exact bug class as the reported EigenPod issue: two co-dependent state machines (pool accounting vs. staking-era accounting) that must be read at a **single, consistently-bound point in time**, but are read from different sources with a boundary mismatch.

### Finding Description
In `withdraw_unbonded`: [1](#0-0) 
the member and `active_era` are loaded, then: [2](#0-1) 
`member.withdraw_unlocked(active_era)` removes any `unbonding_eras` entries whose key is `<= active_era` (strict `>` retains, everything else is dissolved and returned as `withdrawn_points`): [3](#0-2) 

The corresponding balance is then pulled out of `sub_pools.with_era` keyed by the *same* era values that were removed from `unbonding_eras`: [4](#0-3) 
If no entry exists in `with_era` for that era key (because it was already merged, or because the era used at unbond-time — governed by `active_era` at the time of `unbond()`/`try_unbond` — does not line up with the era read here from `T::StakeAdapter::current_era()`), the code falls back to `sub_pools.no_era.dissolve(*unlocked_points)`. `UnbondPool::dissolve` computes `balance * points / total_points` — if `no_era.points` doesn't actually include this member's points (e.g., because `maybe_merge_pools` merges based on a different era boundary than the one used for `withdraw_unlocked`), the result can be far less than owed, or the points removed here silently exceed what `no_era` was ever credited with, corrupting the points/balance ratio for all remaining members.

This is precisely the "boundary occurring at the watermark" pattern from the report: `withdraw_unlocked`'s cutoff (`chunk.era > active_era` retained) and `maybe_merge_pools`'s cutoff (`*k > newest_era_to_remove` retained) are two independently-computed era boundaries feeding the same balance pool, and a documented incident already showed they can disagree.

### Impact Explanation
A real occurrence of this exact bug class was already found and patched via a one-off data migration, described as a "CurrentEra vs ActiveEra mismatch" that "caused one pool member's balance to become trapped: their points were dissolved but the held funds weren't released": [5](#0-4) 
This confirms the pattern is not theoretical — it has caused permanent user-fund lock in production-adjacent state (Asset Hub Westend). Because the fix shipped is a **one-time migration for the single known affected member**, not a structural invariant enforced at every `withdraw_unbonded` call, the same divergence between the pool's own era bookkeeping (`with_era`/`unbonding_eras`) and the staking adapter's era source (`current_era()`/`active_era()`) can recur for any member whenever those two sources disagree at the moment of withdrawal, silently and permanently trapping bonded funds.

### Likelihood Explanation
Nomination pools now sit atop `pallet-staking-async`, which explicitly distinguishes `CurrentEra` (planned) from `ActiveEra` (activated), and recently changed unbonding chunks "to be keyed by active era instead of current era": [6](#0-5) 
Any adapter/version skew, migration window, or code path in `pallet-nomination-pools` that still reads `T::StakeAdapter::current_era()` (as `withdraw_unbonded` does) while `unbond()`/pool merging use the era value returned at a different rotation point creates exactly the divergence that already caused a real, documented fund-trapping incident. No malicious actor or privileged role is required — an ordinary member calling `withdraw_unbonded` at an era boundary is sufficient to trigger it, mirroring the EigenPod scenario where an ordinary user action executed exactly at a watermark update caused fund loss.

### Recommendation
- Ensure `withdraw_unbonded`, `try_unbond`, and `maybe_merge_pools` all derive their era boundary from a single, atomically-consistent source (the same call/value) rather than independently invoking `T::StakeAdapter::current_era()`/`active_era()` at different points.
- When `sub_pools.with_era.get_mut(era)` misses, do not silently fall back to `no_era.dissolve` unconditionally — assert/verify that the point/balance accounting is conserved, and prefer failing safe (defensive error) over dissolving points against a pool that cannot back them.
- Add an explicit invariant check (as is done elsewhere with `debug_assert!`/`defensive!`) that `sum_unlocked_points` withdrawn always corresponds to a `balance_to_unbond` bound by the *actual* balance credited to that era's bucket, not merely the pool's `transferable_balance` minimum, which can mask a zero-balance dissolve.
- Broaden the one-time migration fix in `pr_11018` into a permanent guard so future era-source divergences cannot again trap member funds.

### Proof of Concept
1. Member unbonds while `pallet-staking-async`'s planned/active era bookkeeping is in a transitional state, causing the pool's `try_unbond` to record `unbonding_era = X` in `member.unbonding_eras` and `sub_pools.with_era[X]`.
2. Before the member withdraws, `maybe_merge_pools` runs using a different era boundary computation (e.g., driven by a later `active_era()` read), merging era `X`'s pool into `no_era` — or, conversely, the member's `withdraw_unlocked(active_era)` uses an `active_era` value that has *not yet* advanced past `X` under one era source, while `with_era`'s cutoff has advanced under another, removing the `X` bucket first.
3. Member calls `withdraw_unbonded`: `member.withdraw_unlocked(active_era)` dissolves the member's points for era `X` (removes from `unbonding_eras`, adds to `withdrawn_points`), but `sub_pools.with_era.get_mut(&X)` returns `None` because it was already merged/removed under the other era source.
4. Balance is drawn from `sub_pools.no_era.dissolve(points)` instead, which is not actually backed 1:1 for those specific points, and/or `T::StakeAdapter::transferable_balance(...)` — the `min(...)` clamp described in the code comment at lines 2486-2496 — silently caps the payout to less than what was owed.
5. Result: `PoolMembers::<T>::remove` / points update happen (member is marked as fully withdrawn), but the transferred balance is less than (or zero relative to) what was actually owed — exactly the outcome later confirmed and remediated by the one-time migration in `pr_11018.prdoc`. [4](#0-3)
