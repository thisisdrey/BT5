### Title
Nonce-floor reset on DeleteKey+AddKey enables replay of a future-nonce transaction/DelegateAction, allowing double execution of relayed actions - ([File: runtime/runtime/src/access_keys.rs, runtime/runtime/src/verifier.rs, runtime/runtime/src/actions.rs])

### Summary
`initial_nonce_value` resets a recreated access key's nonce floor to `(block_height-1) * ACCESS_KEY_NONCE_RANGE_MULTIPLIER` with no memory of nonces the same account+pubkey pair already consumed under the deleted key instance. Because the per-block upper-bound nonce check (`verify_nonce` in `verifier.rs`, and the equivalent check in `validate_delegate_action_key` in `actions.rs`) only bounds nonces relative to the *current* block height at validation time (not at signing time), an attacker can pre-sign a transaction/DelegateAction with a nonce belonging to a future height window, get it executed once, then delete and re-add the same public key within the same block height so the new floor still sits below that already-used nonce — enabling the identical signed payload to be validated and executed a second time.

### Finding Description
`initial_nonce_value(block_height)` seeds a freshly (re)created access key's nonce at `(block_height - 1) * ACCESS_KEY_NONCE_RANGE_MULTIPLIER`: [1](#0-0) 

This value is used both for plain `AddKey` (`add_regular_key`) and gas keys, and is written unconditionally on every `AddKey`, discarding any memory of the nonce state of a previous key instance that occupied the same `(account_id, public_key)` slot before `DeleteKey` removed it: [2](#0-1) [3](#0-2) 

Nonce validation for ordinary transactions is done in `verify_nonce`, which enforces monotonicity against the access key's current nonce and an *upper bound* tied to the current block height: [4](#0-3) 

The same pattern is used for DelegateActions (relayed meta-transactions) in `validate_delegate_action_key`, where the nonce must exceed the access key's current nonce and stay below `apply_state.block_height * ACCESS_KEY_NONCE_RANGE_MULTIPLIER`: [5](#0-4) 

Crucially, this upper bound is checked only at the height the transaction/action is *applied*, not at signing time. An attacker who controls the FullAccess key is free to sign a nonce arbitrarily far into a future height's window (e.g., `N = h * MULTIPLIER + 500`) at any time and hold it until that window becomes reachable.

**Exploit flow (relayed DelegateAction, third-party impact):**
1. Attacker signs a `DelegateAction` with nonce `N = W*MULTIPLIER + 500` where `W` is a future height index, while the access key's on-chain nonce is still low.
2. Once the chain reaches height `H = W+1` (the minimum height for which the upper-bound check `H*MULTIPLIER > N` passes), the attacker forwards this DelegateAction to Relayer A, which wraps it in a `SignedTransaction` and gets it included/executed in that block's chunk — this advances the on-chain access key nonce to `N` and executes the DelegateAction's actions against the receiver contract (e.g., claiming a reward, transferring tokens, calling a privileged method the relayer is authorized to trigger).
3. Within the *same* block height `H`, the attacker submits (via a second access key on the same account so it isn't nonce-blocked by the first) a transaction containing `DeleteKeyAction` followed by `AddKeyAction` for the *same public key* used to sign the DelegateAction. `action_delete_key` removes the access key entry entirely (`remove_access_key`), and `action_add_key`/`add_regular_key` recreates it with nonce floor `initial_nonce_value(H) = (H-1)*MULTIPLIER = W*MULTIPLIER`, which is still `< N`.
4. The attacker then forwards the *identical* previously-signed DelegateAction bytes to Relayer B (at height `H` or any subsequent height, as long as nothing else has advanced the new key's nonce past `N`). The nonce check `delegate_nonce.nonce() <= current_nonce` passes because the freshly reset `current_nonce = W*MULTIPLIER < N`, and the upper-bound check also passes since block height has only increased. The DelegateAction is validated as "fresh" and its actions are executed a second time against the receiver.

This is only possible because `H` must simultaneously satisfy `H >= W+1` (for the first execution to be valid) and `H <= W+1` (for the post-recreation floor to remain below `N`), i.e., both the original execution and the DeleteKey/AddKey sequence must land in the same block height — a narrow but attacker-controllable timing condition since the attacker fully controls when to submit both transactions and can retry until they land in the same chunk.

Existing protections do not stop this: the per-chunk duplicate-transaction-hash filter (`skip_duplicate_txs`/`seen_tx_hashes`) only deduplicates within a single chunk's own transaction list, not across the two different relayer submissions/chunks: [6](#0-5) 
and there is no persistent chain-wide "seen nonce" record independent of the mutable `AccessKey.nonce` field, so once that field is reset by key recreation, prior high nonces become valid again.

### Impact Explanation
This enables double execution of a signer-authorized DelegateAction relayed by two different (or the same) relayer/gateway, without any additional signature from the signer for the second execution. If the DelegateAction's actions perform a value-transferring or state-mutating call (e.g., claim/transfer/withdraw against a receiver contract, or a relayer-subsidized action), the receiver contract or relayer can be tricked into processing the same authorized instruction twice — a double-spend/replay of user-authorized action, and a fee-griefing/double-cost issue for the relayer as an unprivileged third party. This falls under the "double-spend/replay" bounty category referenced in the audit rules.

### Likelihood Explanation
Preconditions: attacker needs to be the account owner of a FullAccess key (or a key otherwise permitted to sign both the target DelegateAction and a DeleteKey+AddKey transaction), and needs the original relayed-execution transaction and the DeleteKey+AddKey transaction to land in the exact same block height, with the former ordered before the latter. This is a real but narrow timing constraint achievable by a patient attacker using a second access key to avoid nonce contention, resubmitting/retrying transactions with refreshed `block_hash` until the desired co-location occurs, and pre-computing the nonce to align with the target height window. Cost is limited to normal gas fees and repeated submission attempts; the attack is repeatable per relayer interaction.

### Recommendation
Do not derive the new access key's nonce floor purely from the current block height; instead, when recreating a key for an `(account_id, public_key)` pair that previously existed, ensure the new floor is at least as high as any nonce previously used for that pair (e.g., by retaining a tombstone of the maximum nonce ever used, or by using a monotonically increasing global counter per account instead of a height-derived floor), so a nonce spent under a deleted key instance can never become valid again after key recreation.

### Proof of Concept
Runtime/integration test plan:
1. Set up an account with a FullAccess key `K` at some low nonce, and a second FullAccess key `K2` on the same account.
2. At height `H`, sign and submit a `DelegateAction` (or plain `SignedTransaction`) with `public_key = K`, `nonce = H*MULTIPLIER - MULTIPLIER + 500` (i.e., inside the window that becomes valid exactly at height `H`), targeting a receiver contract method that has an observable side effect (e.g., increments a counter or transfers a token). Assert it succeeds and the receiver's state reflects one execution.
3. In the same height `H`'s chunk (immediately after step 2 in test-loop ordering), submit (signed by `K2`) a transaction containing `DeleteKeyAction { public_key: K }` followed in a later action/tx by `AddKeyAction { public_key: K, access_key: FullAccess }`. Assert the new key's nonce equals `initial_nonce_value(H)`.
4. Resubmit the exact same signed DelegateAction/transaction bytes from step 2 at height `H+1` (or later). Assert that it is accepted (nonce check passes) and the receiver contract's side effect is applied a second time — demonstrating double execution.
5. Assert this violates the expected invariant that a signed authorization can only ever be executed once.

pub(crate) fn initial_nonce_value(block_height: BlockHeight) -> Nonce {
    // Set default nonce for newly created access key to avoid transaction hash collision.
    // See <https://github.com/near/nearcore/issues/3779>.
    (block_height - 1) * near_primitives::account::AccessKey::ACCESS_KEY_NONCE_RANGE_MULTIPLIER
}

/// Verify that the transaction nonce is valid.
fn verify_nonce(
    tx_nonce: Nonce,
    current_nonce: Nonce,
    block_height: Option<BlockHeight>,
    nonce_mode: NonceMode,
) -> Result<(), InvalidTxError> {
    match nonce_mode {
        NonceMode::Monotonic => {
            if tx_nonce <= current_nonce {
                return Err(InvalidTxError::InvalidNonce { tx_nonce, ak_nonce: current_nonce });
            }
        }
        NonceMode::Strict => {
            if !current_nonce.checked_add(1).is_some_and(|expected| tx_nonce == expected) {
                return Err(InvalidTxError::InvalidNonce { tx_nonce, ak_nonce: current_nonce });
            }
        }
    }
    if let Some(height) = block_height {
        let upper_bound = height
            .saturating_mul(near_primitives::account::AccessKey::ACCESS_KEY_NONCE_RANGE_MULTIPLIER);
        if tx_nonce >= upper_bound {
            return Err(InvalidTxError::NonceTooLarge { tx_nonce, upper_bound });
        }
    }
    Ok(())
}
