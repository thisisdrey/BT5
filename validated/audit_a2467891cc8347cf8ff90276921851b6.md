## Finding

### Title
Relayer reward paid on failed Ethereum delivery due to unchecked `receipt.success` flag - (File: `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs`)

### Summary
The external report describes an IBC/CosmWasm access-control flaw where a malicious contract can bypass invariant checks in the message-processing keeper, leading to unauthorized fund movement. The local analog is in Snowbridge's outbound queue v2: the `submit_delivery_receipt` extrinsic decodes a `DeliveryReceipt` that carries an explicit `success` field describing whether the Ethereum-side dispatch actually succeeded, but `process_delivery_receipt` never reads that field before releasing the relayer reward and clearing the pending order.

### Finding Description
`DeliveryReceipt` is decoded from the `InboundMessageDispatched(uint64 indexed nonce, bytes32 topic, bool success, bytes32 reward_address)` Ethereum event: [1](#0-0) 

The `submit_delivery_receipt` call verifies the beacon/receipt proof and the emitting gateway address, then hands off to `process_delivery_receipt`: [2](#0-1) 

`process_delivery_receipt` only checks the gateway address and the presence of a `PendingOrder` for the nonce. It pays out the reward whenever `order.fee > 0`, and unconditionally removes the order — `receipt.success` is decoded but never inspected: [3](#0-2) 

The module-level pivot invariant states that "message queues, bridge markers, receipts, and payout state must only advance after decode, dispatch, execution, and settlement succeed atomically." Here, settlement (reward payout + order removal) advances purely on proof validity and nonce match, independent of whether the underlying dispatch actually executed successfully on Ethereum. `PendingOrder` itself only stores `nonce`, `fee`, and `block_number`, with no field to record or gate on delivery outcome, so there is no later corrective mechanism either.

### Impact Explanation
An account that relays (or arranges to relay) a message whose Ethereum-side execution predictably fails (e.g. a destination XCM/asset transfer crafted to revert, or supplied with insufficient execution gas) can still submit a valid receipt proof for that failed dispatch and collect the full relayer fee attached to the `PendingOrder`, because `success=false` is silently ignored. This lets an unprivileged, permissionless caller extract the fee pool meant to incentivize successful delivery without providing the corresponding value (successful message execution), draining bridge reward funds over repeated cycles. This matches the "public underpriced work" / "payout state advances without settlement succeeding" impact category for BridgeHub/Snowbridge scope.

### Likelihood Explanation
Moderate: any signed account can call `submit_delivery_receipt` with a genuine Ethereum receipt proof (no special relayer permission is enforced — it is `ensure_signed`, not a permissioned relayer set), and causing execution failure on the Ethereum destination side for a self-controlled message is a normal capability of anyone constructing the outbound message payload/commands, not requiring an admin, validator, or compromised relayer role.

### Recommendation
Gate the reward payment on `receipt.success`. If `success == false`, either withhold the reward entirely, refund/return the fee to the original sender, or route it to a different settlement path (e.g. retry allowance), and only pay the relayer fee when the receipt confirms successful execution. Ensure the `PendingOrder` removal and event emission also reflect the failure case distinctly (e.g. a `MessageDeliveryFailed` event) so downstream systems don't treat failed and successful deliveries identically.

### Proof of Concept
1. Attacker sends an outbound message via the normal path so a `PendingOrder{nonce, fee, ..}` is created with `fee > 0` (`bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs:426-438`).
2. Attacker ensures the corresponding Ethereum-side dispatch reverts/fails by design (e.g., malformed XCM payload/command that is valid enough to be included but fails at execution), so the Gateway emits `InboundMessageDispatched(nonce, topic, success=false, reward_address=attacker)`.
3. Attacker (or any relaying account) submits `submit_delivery_receipt` with a valid Merkle/receipt proof for that event.
4. `T::Verifier::verify` succeeds (proof is genuine), `DeliveryReceipt::try_from` decodes `success=false` but `process_delivery_receipt` never checks it — `order.fee > 0` triggers `T::RewardPayment::register_reward` and the order is removed as if delivery succeeded.
5. Attacker has collected the reward fee for a message whose Ethereum-side effect never actually succeeded, repeatable across nonces to drain the reward pool.

		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}
