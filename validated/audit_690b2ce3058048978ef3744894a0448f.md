## Analysis: Trapped Ether on Snowbridge `CreateAsset` Registration Due to Missing Error-Handling Around `ExchangeAsset`

The GMX report's core flaw is: an exact-output operation (`swapTokensForExactTokens`) can revert when the input balance is insufficient, and the calling code has **no fallback/refund path** for that failure — leaving state (and funds) permanently stuck. The Polkadot-SDK analog is in Snowbridge's V2 inbound-queue asset-registration XCM program, which uses the XCM `ExchangeAsset` command (an exact-output-style swap) with **no error handler**, unlike the V1 flow which explicitly guards this exact scenario with `SetAppendix`.

### Title
Snowbridge V2 `CreateAsset` registration traps bridged Ether irrecoverably when `ExchangeAsset` fails to cover the exact DOT deposit - (File: `bridges/snowbridge/primitives/inbound-queue/src/v2/converter.rs`)

### Summary
`MessageToXcm::make_create_asset_xcm_for_polkadot` builds an XCM program that uses `ExchangeAsset { give: eth_asset, want: dot_fee_asset, maximal: false }` to convert bridged Ether into the exact DOT amount required to pay the `ForeignAssets::create` deposit [1](#0-0)  The refund logic (`RefundSurplus` + `DepositAsset` to the claimer) is placed as ordinary trailing instructions in the same linear program, not inside a `SetAppendix` block [2](#0-1) .

### Finding Description
`ExchangeAsset` with `maximal: false` behaves exactly like `swapTokensForExactTokens`: it tries to acquire an *exact* `want` amount using the `give` assets, and returns `XcmError::NoDeal` if the give amount/available liquidity is insufficient [3](#0-2) . In the XCM executor, when an instruction returns `Err` and no `SetErrorHandler`/`SetAppendix` was set for that path, execution of the *rest of the program* halts immediately, and whatever remains in the holding register gets trapped by `post_process` (an `AssetsTrapped` event), not automatically returned to any specific beneficiary [4](#0-3) .

In `make_create_asset_xcm_for_polkadot`, `ExchangeAsset` is the very first instruction of the program, and the refund fallback (`RefundSurplus`, `DepositAsset { ..., beneficiary: claimer }`) is only reachable if `ExchangeAsset` and all subsequent `Transact` calls succeed — it is not wrapped in an appendix that runs unconditionally, unlike the V1 asset-registration flow, which explicitly uses `SetAppendix` to guarantee unspent fees are deposited to the bridge sovereign "regardless of `Transact` success or not" [5](#0-4) .

The `want` amount (`CreateAssetDeposit`) is a fixed on-chain constant, while the `give` amount is `message.value` — the amount of Ether the user chose to bridge, computed off-chain on Ethereum at message-construction time [6](#0-5) . Any adverse price movement of the ETH/DOT pool on Asset Hub between message construction and execution (or simply an underestimate by the user/relayer) makes the `give` insufficient to reach the exact `want`, causing `ExchangeAsset` to return `NoDeal` and the whole program to abort before the fallback deposit-to-claimer instructions run.

### Impact Explanation
This corrupts the intended invariant that bridged funds either land at the correct beneficiary or are refunded to the specified claimer — a "message queues, bridge markers, receipts, and payout state must only advance after decode, dispatch, execution, and settlement succeed atomically" requirement. Instead, the bridged Ether becomes trapped under the XCM origin context active at the point of failure (the descended `InboundQueueLocation` + `UniversalOrigin(Ethereum)`, and possibly the sender's `AccountKey20`), not the `claimer` location the user specified. Reclaiming trapped assets via `claim_assets` requires reproducing that exact origin in a fresh XCM program, which is not something an ordinary Polkadot-side claimer can construct — it effectively requires re-driving another message through the bridge with the identical origin context. This constitutes a permanent (or practically unrecoverable) user-fund lock, matching the accepted impact class.

### Likelihood Explanation
No malicious actor is required. Any legitimate user registering a new ERC-20 token via `Payload::CreateAsset` on Ethereum is exposed whenever the DOT-denominated cost of `CreateAssetDeposit` at execution time exceeds the Ether value they supplied — a routine consequence of AMM price movement on Asset Hub's swap pool, or of `CreateAssetDeposit`/pool price changing between message construction and Bridge Hub/Asset Hub execution. This is a public, unprivileged, naturally-occurring failure path, directly analogous to the original report's insufficient-balance revert in `swapTokensForExactTokens`.

### Recommendation
Wrap the fallback instructions in a `SetAppendix` (as V1 already does) so that `RefundSurplus` and `DepositAsset { beneficiary: claimer }` execute unconditionally regardless of whether `ExchangeAsset`/`Transact` succeed, e.g.:
```
SetAppendix(Xcm(vec![
    RefundSurplus,
    DepositAsset { assets: Wild(AllCounted(2)), beneficiary: claimer },
])),
ExchangeAsset { give: eth_asset.into(), want: dot_fee_asset.clone().into(), maximal: false },
...
```
Additionally, consider using `maximal: true` or computing `want` with a slippage buffer so a minor price shift does not abort registration outright, and/or catching the failure to still route bridged Ether back to the `claimer` on Asset Hub rather than the low-level XCM origin.

### Proof of Concept
1. On Ethereum, a user sends a `CreateAsset` message with `message.value` computed to just cover `CreateAssetDeposit` at current AH pool price.
2. Before the message is relayed/executed, the DOT/ETH pool price on Asset Hub shifts (normal AMM activity) such that the same Ether amount no longer buys enough DOT to reach `CreateAssetDeposit`.
3. `MessageToXcm::convert` produces the program from `make_create_asset_xcm_for_polkadot`; on execution, `ExchangeAsset { want: dot_fee_asset, maximal: false }` returns `XcmError::NoDeal` [7](#0-6) .
4. Execution halts; `DepositAsset { beneficiary: bridge_owner }`, both `Transact` calls, `RefundSurplus`, and the final `DepositAsset { beneficiary: claimer }` never run.
5. The bridged Ether (and any remaining reserve-deposited assets) end up trapped via `AssetsTrapped` under the pallet's descended/universal origin rather than deposited to `claimer`, and cannot be practically reclaimed from the Polkadot side.
