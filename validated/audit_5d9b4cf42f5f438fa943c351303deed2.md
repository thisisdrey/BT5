### Title
Witness rewards get permanently stuck when a top witness has zero votes during a maintenance cycle - (File: chainbase/src/main/java/org/tron/core/store/DelegationStore.java)

### Summary
`DelegationStore.accumulateWitnessVi()` (and its duplicate in `RewardViCalService.accumulateWitnessVi()`) silently discards a witness's accrued block/transaction-fee rewards for a cycle whenever that witness's recorded `voteCount` is `0`, instead of carrying the undistributed reward forward so it can eventually be paid out. This mirrors the reported `VirtualStakingRewards.rewardPerToken()` bug where rewards accrued while `_totalSupply == 0` are permanently lost because the accumulator returns the stored value unchanged instead of preserving the un-distributed reward for later distribution.

### Finding Description
Block rewards and transaction-fee rewards earned by an active witness are credited per cycle via `MortgageService.payReward()`, which calls `delegationStore.addReward(cycle, witnessAddress, value)`: [1](#0-0) 

At the start of every maintenance cycle, `MaintenanceManager.doMaintenance()` iterates all witnesses and calls `delegationStore.accumulateWitnessVi(curCycle, witness, witness.getVoteCount())` to convert that cycle's `reward` into a per-vote reward index (`Vi`, analogous to `rewardPerToken`): [2](#0-1) 

The accumulation logic is:
```java
public void accumulateWitnessVi(long cycle, byte[] address, long voteCount) {
  BigInteger preVi = getWitnessVi(cycle - 1, address);
  long reward = getReward(cycle, address);
  if (reward == 0 || voteCount == 0) { // Just forward pre vi
    if (!BigInteger.ZERO.equals(preVi)) {
      setWitnessVi(cycle, address, preVi);
    }
  } else { // Accumulate delta vi
    ...
  }
}
``` [3](#0-2) 

This is functionally identical to the `VirtualStakingRewards.rewardPerToken()` bug: when `voteCount == 0` (the "total supply" of stake behind a witness for that cycle), the accumulated `reward` for the cycle is thrown away — `rewardPerTokenStored`/`Vi` is simply forwarded unchanged, and the `reward` value already recorded via `addReward` is never folded into any voter's payout. Because voters compute their share strictly from the delta of `Vi` between cycles (`MortgageService.computeReward()`), any reward earned while `voteCount == 0` becomes permanently unclaimable — not to the witness, not to any voter, and not carried forward to a future cycle.

This can occur naturally in the reward lifecycle: a witness is part of the active/standby set (elected from votes as of the previous cycle) and earns block/tx-fee rewards for the current cycle via `payBlockReward`/`payTransactionFeeReward`, but if all voters withdraw their votes from that witness during the same cycle (e.g., via `WithdrawBalanceContract`/vote-clearing/`VoteWitnessProcessor`) before the next `doMaintenance()` snapshot, `witness.getVoteCount()` recorded for that cycle is `0`, and the reward already credited for that cycle is lost rather than being redistributed or refunded.

### Impact Explanation
TRX allocated as witness block/transaction-fee rewards for a cycle can become permanently stuck/unaccounted-for tokens: they are removed from the reward pool bookkeeping (`addReward`) but never actually paid to any account's `allowance`, and there is no path to reclaim or redistribute them. This is a permanent loss of funds bug in the consensus-level reward accounting, matching the "permanent freezing/loss of funds" impact class.

### Likelihood Explanation
Reachable purely through normal, unprivileged user actions (vote/unvote/withdraw transactions) combined with ordinary block production by an elected witness — no privileged or malicious-SR behavior is required. It only requires that all voters unvote a witness within the same maintenance cycle in which that witness still produces blocks and earns fees, which is a realistic and common on-chain scenario (voters can freely move votes at any time via `VoteWitnessContract`).

### Recommendation
When `voteCount == 0` but `reward > 0` in `accumulateWitnessVi`, do not discard the reward. Instead, carry the un-distributed reward amount forward (e.g., add it to the next cycle's `reward` for that witness, or return it to the reward pool) so that once the witness regains voters, the accumulated reward is correctly reflected in `Vi`, or explicitly return it to a recoverable pool instead of silently dropping it.

### Proof of Concept
1. Witness `W` is actively voted for with non-zero `voteCount` and produces blocks, so `MortgageService.payReward()` calls `delegationStore.addReward(cycle, W, value)` for cycle `N`, crediting a non-zero reward for `W` in cycle `N`.
2. Before the maintenance boundary snapshot for cycle `N` is taken, all voters withdraw/change their votes away from `W` (e.g., via unfreeze / vote-clear operations), so `WitnessCapsule.getVoteCount()` for `W` becomes `0` by the time `MaintenanceManager.doMaintenance()` runs `delegationStore.accumulateWitnessVi(N, W, 0)`.
3. Inside `accumulateWitnessVi`, since `voteCount == 0`, the branch `if (reward == 0 || voteCount == 0)` is taken and only `preVi` is forwarded — the reward recorded in step 1 is never folded into `Vi`.
4. No voter can ever claim this reward via `MortgageService.computeReward()`/`withdrawReward()`, since those functions compute payouts strictly from `Vi` deltas, and `Vi` for cycle `N` never reflects the reward. The TRX credited in step 1 is permanently stuck.
