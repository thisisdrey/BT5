### Title
`account_creation_charge` is skipped when `DeleteAccount` + `CreateAccount` target the same account within a single receipt - (`runtime/runtime/src/lib.rs`)

### Summary
`apply_action_receipt` snapshots `account_did_not_exist` **once**, before any of the receipt's actions run, and only re-checks the final `account` state after the whole action list executes. A receipt whose action list is `[DeleteAccount, CreateAccount]` targeting the same receiver therefore ends with `account_did_not_exist == false` (the account existed when the receipt started) even though the account was genuinely destroyed and re-created inside that very receipt, so `created_new_account` is computed as `false` and `account_creation_charge` is never levied.

### Finding Description
`apply_action_receipt` fetches the account and captures existence exactly once: [1](#0-0) 

The same mutable `account: &mut Option<Account>` is threaded through every action of the receipt's action list in the execution loop: [2](#0-1) 

`action_delete_account` sets `*account = None` in place and keeps `actor_id == account_id` (self-delete), so a following `CreateAccount` action in the same action list passes `check_account_existence` (account is `None`) and re-creates the account: [3](#0-2) 

At the end of `apply_action_receipt`, `created_new_account` is derived from the *pre-receipt* snapshot, not from what actually happened during the receipt: [4](#0-3) 

Since `account_did_not_exist` was `false` (the account existed before this receipt began), `created_new_account` evaluates to `false` even though the account was destroyed and rebuilt from scratch inside the receipt, so `refund_unspent_gas_and_deposits`'s `created_account` branch never fires and `create_account_charge` stays `Balance::ZERO`: [5](#0-4) 

**Attacker path:** an attacker deploys their own wasm contract to their own account `X`. In a `FunctionCall` executed on `X` (i.e. `predecessor_id == receiver_id == X`, which is required so `actor_id == account_id` and `DeleteAccount` passes `check_actor_permissions`), the contract issues a single promise batch on itself containing `DeleteAccount(beneficiary)` followed by `CreateAccount()`. Both actions execute as one `ActionReceipt` with one shared `account_did_not_exist` snapshot. No signature/nonce/access-key/storage-staking check inspects intra-receipt account lifecycle, so nothing intercepts this.

Note: the multi-receipt variant described in the question (`CreateAccount(X)` receipt → `DeleteAccount(X)` receipt → `CreateAccount(X)` receipt, each a separate `apply_action_receipt` call) does **not** reproduce the bug: `account_did_not_exist` is re-fetched fresh from the trie at the start of each receipt (state commits between receipts), so each of the two `CreateAccount` receipts is correctly and independently charged once. The only reachable variant is the single-receipt, same-batch delete-then-recreate.

### Impact Explanation
This lets an attacker evade the `account_creation_charge` (mainnet `account_creation_charge` ≈ 0.007 NEAR under `AccountCostIncrease`, PV 85) for an otherwise genuine account re-creation, meaning the protocol burns strictly less than the value-conservation invariant intends ("`create_account_charge` must be billed exactly once per genuine creation"). It does not steal funds from other users, does not cause double-spend/replay, authorization escalation, or a shard-halting panic — the only affected value is the attacker's own would-be burnt fee. The economic effect is a small, self-serving under-burn per delete/recreate-in-one-receipt cycle, not fund theft or freezing of user assets.

### Likelihood Explanation
Fully reachable by an ordinary, unprivileged account: it only requires owning an account, deploying an attacker-controlled contract to it, and having that contract issue a self-targeting promise batch (`DeleteAccount` + `CreateAccount`). It is repeatable per chunk/cycle. However, each cycle costs the attacker gas fees for `DeleteAccount`'s exec fee, `CreateAccount`'s exec/send fees, and the `FunctionCall` itself, all of which are burnt regardless — the amount evaded (~0.007 NEAR) may be comparable to or smaller than the actual gas cost of executing the cycle, capping the profitability of repeated abuse.

### Recommendation
Compute `created_account` from the transition that actually happened within the receipt rather than only from the pre-receipt snapshot: track whether the account was deleted and then re-created during the action loop (e.g., set a `was_deleted_and_recreated` flag inside `apply_action`/`action_delete_account`/`action_create_account`, or re-derive `account_did_not_exist` immediately before evaluating `created_new_account`, using a running "existed at receipt start XOR net created" state that accounts for intra-receipt delete+recreate cycles).

### Proof of Concept
Integration/test-loop test:
1. Deploy a contract to account `X` that, when called, issues one promise batch targeting `env::current_account_id()` with actions `[DeleteAccount(beneficiary), CreateAccount]`.
2. Fund `X`, call the method, run one chunk apply so the whole promise batch executes as a single `ActionReceipt`.
3. Assert the account `X` exists afterward (genuine re-creation happened) but sum `create_account_charge` (via `GasRefundResult`/outcome `tokens_burnt` deltas, akin to `total_tokens_burnt` in `test-loop-tests/src/tests/account_cost_increase.rs`) across all receipts in the chunk and assert it is `0`, whereas the expected invariant (per the question) requires it to equal exactly `1 * account_creation_charge`. This demonstrates the discrepancy: the attacker's genuine re-creation is billed `0` instead of `account_creation_charge`.
