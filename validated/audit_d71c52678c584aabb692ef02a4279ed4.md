### Title
Quarantine object directory ownership check is bypassed for any path ending in `quarantine`, enabling cross-repository/cross-transaction object access - ([File: internal/git/localrepo/paths.go])

### Summary
`Repo.ObjectDirectoryPath` is supposed to bind an attacker/caller-supplied `GitObjectDirectory` value to the specific repository (and, for quarantine directories, to the specific transaction) that requested it. Instead, any relative path whose final component is literally named `quarantine` (or `quarantine/tmp_objdir-*`) is accepted outright, skipping the per-repository ownership check entirely. This is directly analogous to the reported `deliverMarketplaceWithSignatures` issue: in both cases a resource-granting verification step checks only a generic, unauthenticated "shape" of the request instead of cryptographically/structurally binding it to the specific actor (mech vs. repository/transaction) that is supposed to be entitled to it, letting an unrelated party consume the resource meant for someone else.

### Finding Description
`ObjectDirectoryPath` resolves the caller-controlled `Repository.GitObjectDirectory` field: [1](#0-0) 

After validating only that the joined path stays inside the *storage* (not the repository, and not a specific transaction), it computes:

```go
isTransactionQuarantineDir := (baseDir == "quarantine") || ((parentDir == "quarantine") && strings.HasPrefix(baseDir, "tmp_objdir"))
```

and if this is `true`, it **skips** the block that verifies the directory carries the repository-specific `QuarantineDirectoryPrefix` (a SHA1 hash of the repository's relative path): [2](#0-1) 

The prefix-based ownership check exists precisely to guarantee "that a given quarantine object directory indeed belongs to the repository at hand": [3](#0-2) 

But that guarantee is void whenever the path's basename is `quarantine`. This is proven directly by the repository's own test suite: a `GitObjectDirectory` pointing at an arbitrary directory named `tx-tmp/quarantine` — unrelated to the target repository's `QuarantineDirectoryPrefix` — is accepted with **no error**: [4](#0-3) 

The `GitObjectDirectory`/`GitAlternateObjectDirectories` fields on `Repository` are legitimate, client-settable proto fields that Rails is expected to loop back only for Accessor RPCs that were already authorized via the quarantine mechanism, as enforced in the transaction middleware: [5](#0-4) 

That middleware only prevents **Mutator** RPCs from carrying an object-directory override; **Accessor** RPCs (e.g. commit/ref/blob read RPCs) are allowed straight through with whatever object directory the caller supplies, relying entirely on `ObjectDirectoryPath`'s validation to keep the read scoped to the right repository/transaction. Because that validation is bypassed for any `.../quarantine` (or `.../quarantine/tmp_objdir-*`) suffixed path, an Accessor request whose target repository has its `GitObjectDirectory` pointed at a *different* repository's or a *different* concurrent transaction's quarantine directory in the shared storage temp area will be treated as valid, and Git will search that unrelated quarantine directory for objects.

### Impact Explanation
This breaks quarantine/alternates isolation between repositories and between concurrent transactions on the same storage, exactly the class of issue flagged as acceptable ("cross-repository object access", "object-pool and alternates isolation") in scope. An attacker able to reach an Accessor RPC with a crafted `Repository.GitObjectDirectory`/`GitAlternateObjectDirectories` (or an intermediary such as Rails/gitlab-shell relaying a stale/foreign value) can read objects that are still quarantined as part of another, unrelated push — i.e., objects belonging to a different repository, or belonging to another user's push that has not yet been accepted/merged into the target repository. This is a confidentiality violation and undermines the entire purpose of the quarantine mechanism described in `doc/object_quarantine.md`.

### Likelihood Explanation
Exploitation requires the caller to know (or be able to influence) the concrete path of another repository's or transaction's quarantine directory within the shared storage temporary directory tree — this is not fully attacker-chosen from nothing, but the check that was specifically designed to prevent exactly this kind of guessing/reuse (the per-repository SHA1 prefix) is disabled for the common "quarantine" naming pattern, which is also the exact pattern used by real transactions and by `git-receive-pack`'s own `tmp_objdir-incoming-*` quarantine subdirectories. Any component in the call chain that is allowed to set `GitObjectDirectory` on an Accessor request (Rails' access-check loopback path is the intended and only sanctioned user of this field) can trivially trigger this if it is ever handed, reuses, or miscomputes a quarantine path belonging to a different repository/transaction, since Gitaly itself performs no additional binding.

### Recommendation
Do not special-case `isTransactionQuarantineDir` to skip ownership verification. Always require that the resolved quarantine directory carries the calling repository's `storage.QuarantineDirectoryPrefix(repo)` (or, better, is bound to the exact transaction/quarantine handle created for the current request), the same way the marketplace fix bound `requestId` to the specific priority mech's address. Concretely, in `internal/git/localrepo/paths.go`, apply the prefix check unconditionally (adjusting it to also accept the nested `tmp_objdir-*` suffix case) rather than bypassing it whenever the basename happens to be `quarantine`.

### Proof of Concept
`TestRepo_ObjectDirectoryPath`'s "repo quarantined by transaction manager" case demonstrates the bypass: a repository object is given a `GitObjectDirectory` pointing to `tx-tmp/quarantine`, a directory manually created outside of that repository's actual `QuarantineDirectoryPrefix`-scoped location, and `ObjectDirectoryPath` returns it successfully instead of rejecting it: [4](#0-3) 

This same code path is reachable from any Accessor RPC because the transaction middleware only blocks Mutator RPCs from carrying quarantine overrides, leaving Accessor RPCs to rely solely on the (bypassable) check in `ObjectDirectoryPath`: [5](#0-4)

func (repo *Repo) ObjectDirectoryPath(ctx context.Context) (string, error) {
	repoPath, err := repo.Path(ctx)
	if err != nil {

		return "", fmt.Errorf("get storage by name: %w", err)

	baseDir := filepath.Base(relativeObjectDirectoryPath)

// QuarantineDirectoryPrefix returns a prefix for use in the temporary directory. The prefix is
// based on the relative repository path and will stay stable for any given repository. This allows
// us to verify that a given quarantine object directory indeed belongs to the repository at hand.
// Ideally, this function would directly be located in the quarantine module, but this is not
// possible due to cyclic dependencies.
func QuarantineDirectoryPrefix(repo Repository) string {
	hash := [20]byte{}
	if repo != nil {
		hash = sha1.Sum([]byte(repo.GetRelativePath()))
	}
	return fmt.Sprintf("quarantine-%x-", hash[:8])
}
