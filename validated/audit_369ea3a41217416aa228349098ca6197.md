### Title
Reward-per-token computation in `pallet-asset-rewards` can permanently round to zero, silently withholding staker rewards when stake or reward-rate has low precision - (File: `substrate/frame/asset-rewards/src/lib.rs`)

### Summary
`pallet_asset_rewards::Pallet::reward_per_token` mirrors the Derby `Vault.storePriceAndRewards()` pattern exactly: it computes a per-token reward increment as `numerator / denominator` using a fixed, small scaling constant (`PRECISION_SCALING_FACTOR = 4096`) instead of a sufficiently large fixed-point base (e.g. `1e18`). When `reward_rate_per_block * blocks_elapsed * 4096 < total_tokens_staked`, integer division truncates the result to `0`, and because `last_update_block`/`reward_per_token_stored` are unconditionally advanced on every call, the truncated remainder is never recovered — rewards for that window are permanently lost. [1](#0-0) [2](#0-1) 

### Finding Description
The core broken invariant in the Derby report was: `rewardPerLockedToken = nominator / denominator` uses a scaling factor too small relative to the token's decimal precision, so genuine positive yield rounds down to `0`, and the loss is never re-accrued because `lastPrices` is unconditionally advanced.

`reward_per_token` in `pallet-asset-rewards` reproduces this precisely:

```rust
pub(super) fn reward_per_token(
    pool_info: &PoolInfoFor<T>,
) -> Result<T::Balance, DispatchError> {
    ...
    Ok(pool_info.reward_per_token_stored.ensure_add(
        pool_info
            .reward_rate_per_block
            .ensure_mul(rewardable_blocks_elapsed.into())?
            .ensure_mul(PRECISION_SCALING_FACTOR.into())?
            .ensure_div(pool_info.total_tokens_staked)?,
    )?)
}
``` [3](#0-2) 

`PRECISION_SCALING_FACTOR` is a fixed constant of only `4096` (2^12), an extremely small fixed-point base compared to typical on-chain balance precision (many pallets use `1e12`–`1e18`): [1](#0-0) 

`update_pool_and_staker_rewards` calls this function and then unconditionally commits the result via `update_pool_rewards`, which advances `last_update_block` to "now" regardless of whether the computed increment was truncated to zero:

```rust
pub fn update_pool_and_staker_rewards(...) -> Result<...> {
    let reward_per_token = Self::reward_per_token(&pool_info)?;
    let pool_info = Self::update_pool_rewards(pool_info, reward_per_token)?;
    ...
}

pub fn update_pool_rewards(
    pool_info: &PoolInfoFor<T>,
    reward_per_token: T::Balance,
) -> Result<PoolInfoFor<T>, DispatchError> {
    let mut new_pool_info = pool_info.clone();
    new_pool_info.last_update_block = T::BlockNumberProvider::current_block_number();
    new_pool_info.reward_per_token_stored = reward_per_token;
    Ok(new_pool_info)
}
``` [4](#0-3) 

Because `last_update_block` is reset on every JIT recomputation (triggered by any staker action such as `stake`, `unstake`, or `harvest_rewards`, all of which are unprivileged public extrinsics that any account can call for the pool they interact with), the elapsed-block window used in the next computation restarts from zero. There is no accumulator that carries forward the fractional/truncated remainder across calls — unlike `substrate/primitives/arithmetic/src/per_things.rs`'s `rational_mul_correction`, which explicitly computes and re-adds the truncation remainder for `PerThing` multiplications to avoid this exact class of loss. `reward_per_token` performs a raw, uncorrected integer division with no remainder-carry mechanism, so any window where `reward_rate_per_block * blocks_elapsed * 4096 < total_tokens_staked` yields a real `0` reward increment that is silently absorbed and never recovered.

This condition is easily reached in realistic pools:
- Low `reward_rate_per_block` (e.g. a modest reward APR spread over many blocks with a low-decimal reward asset).
- Large `total_tokens_staked` (e.g. an actively staked pool with many participants, or a staking asset with high decimals/large supply).
- Frequent staker interactions (stake/unstake/harvest by any user) that repeatedly reset `last_update_block` before `blocks_elapsed` can grow large enough for the product to exceed `total_tokens_staked`.

Since `total_tokens_staked` and `reward_rate_per_block` are both attacker-influenceable via the public `stake`/`unstake` calls (any unprivileged account can join/leave the pool, changing `total_tokens_staked`), an attacker or even ordinary usage pattern can keep the pool permanently in the "truncate-to-zero" regime, causing genuine reward accrual to be silently and irrecoverably withheld from all stakers in favor of the pool remaining "topped up" in the pool account, effectively becoming stuck/unclaimable funds (the reward asset sits in the pool's account, `Pools::<T>::get(pool_id).account`, and is never distributed).

### Impact Explanation
This is a direct analog of the accepted-as-High Derby finding: stakers who are entitled to real positive rewards receive `0` due to arithmetic precision loss in the pallet's public reward-accrual code path, not due to any admin/governance misconfiguration once the pool is created with realistic economically-sane parameters. Reward assets remain locked in the pool account indefinitely with no path to distribute the truncated remainder, constituting a permanent, unbacked loss of user funds within a FRAME pallet shipped in this repository — matching the "permanent user-fund lock" / "runtime bug that compromises intended behavior" impact class in the gate.

### Likelihood Explanation
- The vulnerable code path (`reward_per_token` → `update_pool_and_staker_rewards` → `update_pool_rewards`) is exercised on every ordinary staker interaction (`stake`, `unstake`, `harvest_rewards`), which are unprivileged public extrinsics.
- `PRECISION_SCALING_FACTOR` is a fixed, non-configurable constant (`4096`) baked into the pallet, so the truncation threshold is fixed regardless of the asset decimals chosen by the pool admin at pool creation.
- No malicious peer, validator, collator, governance actor, or leaked key is required — an ordinary set of stakers using the pool with common reward-rate/stake-size ratios reliably triggers the zero-reward condition, and repeated staker interactions (which reset `last_update_block`) prevent any accumulation of a fractional carry that might eventually round up.

### Recommendation
Increase `PRECISION_SCALING_FACTOR` to a substantially larger fixed-point base (e.g. `1e18`) consistent with typical Substrate balance precision, and/or apply the same remainder-carry technique used in `rational_mul_correction` (`substrate/primitives/arithmetic/src/per_things.rs`) so that truncated fractional reward is not lost across successive `update_pool_rewards` calls. Alternatively, track an explicit remainder field in `PoolInfo` that accumulates the truncated portion of `reward_rate_per_block * blocks_elapsed * PRECISION_SCALING_FACTOR % total_tokens_staked` and adds it back into the next computation, guaranteeing conservation of reward tokens over time regardless of pool size or asset decimals.

### Proof of Concept
1. Create a pool with `reward_asset_id` = a 6-decimal asset, `reward_rate_per_block` = `10` (i.e. `0.00001` reward token per block), via `create_pool` (permissioned call, but parameters are otherwise unconstrained w.r.t. decimals/scale).
2. Have unprivileged accounts `stake` a combined `total_tokens_staked` = `1_000_000_000` (a realistic staked amount for an 12/18-decimal staking asset).
3. Let 1 block elapse, then call `harvest_rewards` (or any staker action) to trigger `update_pool_and_staker_rewards`.
4. Compute `reward_rate_per_block (10) * blocks_elapsed (1) * PRECISION_SCALING_FACTOR (4096) = 40_960`, then `40_960 / total_tokens_staked (1_000_000_000) = 0` (integer division). `reward_per_token_stored` remains unchanged at `0`, and `last_update_block` is advanced to the current block.
5. Repeat step 3 every block indefinitely (e.g. via routine staker activity): the pool's `reward_per_token_stored` never increases, so `derive_rewards` always yields `0` extra reward for stakers, even though the pool account continues to receive/hold the reward asset intended for distribution over the pool's `expiry_block` lifetime — funds become effectively stranded in the pool account. 		/// Derives the current reward per token for this pool.
		pub(super) fn reward_per_token(
			pool_info: &PoolInfoFor<T>,
		) -> Result<T::Balance, DispatchError> {
			if pool_info.total_tokens_staked.is_zero() {
				return Ok(pool_info.reward_per_token_stored);
			}

			let rewardable_blocks_elapsed: u32 =
				match Self::last_block_reward_applicable(pool_info.expiry_block)
					.ensure_sub(pool_info.last_update_block)?
					.try_into()
				{
					Ok(b) => b,
					Err(_) => return Err(Error::<T>::BlockNumberConversionError.into()),
				};

			Ok(pool_info.reward_per_token_stored.ensure_add(
				pool_info
					.reward_rate_per_block
					.ensure_mul(rewardable_blocks_elapsed.into())?
					.ensure_mul(PRECISION_SCALING_FACTOR.into())?
					.ensure_div(pool_info.total_tokens_staked)?,
			)?)
		}

			reward_per_token: &T::Balance,

			Ok(staker_info
				.amount
				.ensure_mul(reward_per_token.ensure_sub(staker_info.reward_per_token_paid)?)?
