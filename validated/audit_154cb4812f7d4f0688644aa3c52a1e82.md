## Analog Identified: Snowbridge Ethereum light-client permanently stalls once the finalized-header gap exceeds `SLOTS_PER_HISTORICAL_ROOT`

### Title
Permanent bridge halt when the sync-committee light client's finalized-header gap exceeds `SLOTS_PER_HISTORICAL_ROOT`, with no permissionless recovery path - (File: `bridges/snowbridge/pallets/ethereum-client/src/lib.rs`)

### Summary
The Unitas report's core broken invariant is: a bound check on external data (`minPrice <= price <= maxPrice`) is enforced as a hard `require`; once real-world conditions push the value outside the bound, the check fails deterministically for every future call, and no permissionless action can restore normal operation, freezing user funds until a privileged party intervenes. The exact same pattern exists in Snowbridge's `pallet-ethereum-client`, where the "price bound" is replaced by a slot-gap bound between the stored `latest_finalized_state.slot` and an incoming `update.finalized_header.slot`.

### Finding Description
`Pallet::verify_update` in `bridges/snowbridge/pallets/ethereum-client/src/lib.rs` enforces: [1](#0-0) 

```
ensure!(
    latest_finalized_state.slot.saturating_add(config::SLOTS_PER_HISTORICAL_ROOT as u64) >=
        update.finalized_header.slot,
    Error::<T>::InvalidFinalizedHeaderGap
);
```

This is the on-chain "bound check" — analogous to `_checkPrice`'s `minPrice <= price <= maxPrice`. `SLOTS_PER_HISTORICAL_ROOT` is a fixed constant (8192 slots, ~27 hours at 12s/slot). The comment in the error definition confirms the design intent: [2](#0-1) .

The `submit` extrinsic is permissionless (any signed account, no relayer allow-list check visible in `verify_update`/`apply_update`), and it is the *only* path that advances `LatestFinalizedBlockRoot`/`FinalizedBeaconState`. If, for any non-malicious reason — relayer downtime, network partition, a temporary lack of economic incentive to relay, or simply nobody bothering to submit an update for slightly over 8192 slots — the gap between the last stored finalized header and the current chain head grows past the threshold, then:

1. Any `submit` carrying a `finalized_header.slot` that is fresh enough to close the gap will itself be *further* than `SLOTS_PER_HISTORICAL_ROOT` from the stale `latest_finalized_state.slot`, so `verify_update` rejects it with `InvalidFinalizedHeaderGap`.
2. There is no incremental "step-by-step" catch-up path visible for `submit` in this snippet that lets a relayer walk the gap down slot-by-slot within the bound (each single valid `Update` must reference an execution period tied to `store_period`/`store_period+1`, and the concrete finalized-header advance is bound by the same slot-gap check).
3. The only other path that writes `LatestFinalizedBlockRoot`/`FinalizedBeaconState` is `process_checkpoint_update`, invoked via a forced/checkpoint call — which the pallet's own PR history confirms is the recovery mechanism, and which is governance/root-gated rather than a permissionless retry.

This is exactly the reported bug class: a hard bound-check on externally supplied, naturally drifting data (price in the original report, slot-gap here) that — once violated by ordinary real-world conditions, not by a malicious peer/relayer/validator — makes the *legitimate*, unprivileged recovery path permanently fail, and only a privileged/governance action can restore service. Two related, corroborating fixes in the repo's own history reinforce that this exact failure surface has already caused real stalls: [3](#0-2) [4](#0-3) 

The second prdoc is particularly telling: it shows the team had to explicitly patch `Verifier::verify` to short-circuit on `Halted` mode because previously *even after the light client was known to be broken/stalled*, downstream inbound/outbound queues kept trying to use it and pay out rewards — i.e., the "disabled swaps"-style cascading failure across dependent pallets (inbound_queue_v2::submit, outbound_queue_v2::submit_delivery_receipt) is a documented real occurrence of this exact bug class in this codebase.

### Impact Explanation
Once the gap condition is tripped:
- All Ethereum→Polkadot message verification relying on this light client (via `inbound_queue_v2::submit` and related consumers) is permanently blocked — no proof of any Ethereum execution header can be accepted, because the ancestry proofs depend on being within `SLOTS_PER_HISTORICAL_ROOT` of a stored finalized state.
- All pending relayer rewards / delivery-receipt settlement that depend on the beacon client's verification path stall, and any user funds in transit that require Ethereum-side proof verification are locked until governance issues a fresh `process_checkpoint_update`.
- This matches the "permanent user-fund or bridge-state lock" and "public underpriced/stalled bridge processing" impact categories directly, mirroring the original report's "freeze user funds" and "swaps disabled" consequence of a stale/out-of-bounds price.

### Likelihood Explanation
No malicious actor, compromised relayer, or governance misbehavior is required — only the ordinary, foreseeable circumstance that no relayer submits a beacon update for slightly over ~27 hours (a single extended outage, lack of relayer profitability, or a temporary halt of the `snowbridge-relay` operator population is sufficient). This is a realistic operational condition for a bridge that depends on off-chain relayers continuously feeding data, directly parallel to the "feeder doesn't update the price quickly enough" scenario in the original report, which Sherlock judges accepted as Medium severity precisely because market/data conditions — not attacker action — are the trigger.

### Recommendation
- Add a permissionless, bounded "re-checkpoint via longer/valid proof chain" path, or allow `submit` to walk forward using intermediate historical roots so a large-but-recoverable gap can be closed without a privileged checkpoint.
- Alternatively, allow the `SLOTS_PER_HISTORICAL_ROOT` bound to be satisfied through chained partial ancestry proofs rather than a single hard cutoff, so temporary relayer inactivity cannot cause a permanent halt.
- At minimum, make the recovery `process_checkpoint_update`/`force_checkpoint` callable through a lower-friction, non-emergency-governance path (e.g., a scheduled or time-locked call that doesn't require full governance turnaround), given the demonstrated real-world impact already documented in `pr_4478` and `pr_11856`.

### Proof of Concept
Conceptual reproduction (matches existing test harness in `bridges/snowbridge/pallets/ethereum-client/src/tests.rs`, e.g. `submit_finalized_header_update_with_too_large_gap`):
1. Bootstrap the light client via `process_checkpoint_update` with a valid checkpoint at slot `S0`.
2. Do not submit any further `submit` calls until wall-clock/chain time advances past `S0 + SLOTS_PER_HISTORICAL_ROOT` slots (achievable simply by relayer inactivity — no attacker action needed).
3. Attempt `submit` with a legitimately signed, cryptographically valid `Update` whose `finalized_header.slot` is the current real Ethereum finalized slot (necessarily beyond the gap since no closer update exists).
4. `verify_update` returns `Error::<T>::InvalidFinalizedHeaderGap` (as already demonstrated in `submit_finalized_header_update_with_too_large_gap`, `bridges/snowbridge/pallets/ethereum-client/src/tests.rs` lines 622-651) for every subsequent valid update, since `latest_finalized_state.slot` can never advance without first passing this same check — a deadlock.
5. Bridge message verification (and dependent inbound/outbound queue settlement) is now stuck until a governance-issued forced checkpoint update is executed. [5](#0-4)

/// Check that a gap of more than 8192 slots between finalized headers is not allowed.
#[test]
fn submit_finalized_header_update_with_too_large_gap() {
	let checkpoint = Box::new(load_checkpoint_update_fixture());
	let update = Box::new(load_sync_committee_update_fixture());
	let mut next_update = Box::new(load_next_sync_committee_update_fixture());

	// Adds 8193 slots, so that the next update is still in the next sync committee, but the
	// gap between the finalized headers is more than 8192 slots.
	let slot_with_large_gap = checkpoint.header.slot + SLOTS_PER_HISTORICAL_ROOT as u64 + 1;

	next_update.finalized_header.slot = slot_with_large_gap;
	// Adding some slots to the attested header and signature slot since they need to be ahead
	// of the finalized header.
	next_update.attested_header.slot = slot_with_large_gap + 33;
	next_update.signature_slot = slot_with_large_gap + 43;

	new_tester().execute_with(|| {
		assert_ok!(EthereumBeaconClient::process_checkpoint_update(&checkpoint));
		let result = EthereumBeaconClient::submit(RuntimeOrigin::signed(1), update.clone());
		assert_ok!(result);
		assert_eq!(result.unwrap().pays_fee, Pays::No);
		assert!(<NextSyncCommittee<Test>>::exists());

		let second_result =
			EthereumBeaconClient::submit(RuntimeOrigin::signed(1), next_update.clone());
		assert_err!(second_result, Error::<Test>::InvalidFinalizedHeaderGap);
		assert_eq!(second_result.unwrap_err().post_info.pays_fee, Pays::Yes);
	});
}
