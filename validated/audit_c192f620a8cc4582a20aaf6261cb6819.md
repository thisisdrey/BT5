### Title
Attacker can permanently fill a victim's deposit-token list via dust transfers, DoSing all future deposits/seizes into new collateral types - ([File: contracts/DepositToken.sol])

### Summary
Analogous to CVE-2020-15564 (a missing validation check on user-supplied input allowing an unprivileged guest to crash the hypervisor), `DepositToken._transfer` and `_mint` unconditionally call `Pool.addToDepositTokensOfAccount` for any first-time recipient, with no minimum-amount check, no per-recipient opt-in, and no way for the recipient to remove entries. An unprivileged attacker can therefore grief any account by sending 1 wei of every deposit token in the pool, filling the victim's per-account token list up to `MAX_TOKENS_PER_USER` and reverting all subsequent operations that would add a new token.

### Finding Description
`DepositToken` is a custom ERC20 where every balance-affecting operation synchronizes a per-account list in `Pool`:

- `transfer` / `transferFrom` only validate the *sender's* unlocked balance via `_revertIfLocked(sender_, amount_)` — there is no check that `amount_` is economically meaningful and no restriction on who `recipient_` may be [1](#0-0) 
- `_transfer` appends the token to the recipient's pool-side list whenever the recipient's prior balance was zero [2](#0-1) 
- `_mint` does the same for deposit/mint recipients [3](#0-2) 
- Entries are only removed when a balance is driven to zero *by the account itself* (`removeFromDepositTokensOfAccount` is called for the sender on burn/full-transfer-out, never for recipients) [4](#0-3) 

`Pool.sol` maintains `depositTokensOfAccount` via `MappedEnumerableSet` bounded by `MAX_TOKENS_PER_USER` (grep confirms `addToDepositTokensOfAccount`/`MAX_TOKENS_PER_USER` in `contracts/Pool.sol`). Once the list is full, `addToDepositTokensOfAccount` reverts, so any call path that mints or transfers a *new* deposit token to the victim reverts: `deposit(onBehalfOf = victim)`, liquidation `seize` credits to the victim, `flashRepay`/`leverage` proceeds, and reward-bearing mints.

The attacker's cost is dust amounts of each registered deposit token (obtainable by depositing the cheapest collateral or via `Pool.swap`-acquired positions), and the missing check — validating a minimum amount or allowing recipients to prune their own list — is exactly the bug class of the Xen advisory: an unchecked, attacker-controlled input that crashes a core state transition.

### Impact Explanation
- **Temporary/permanent freezing of funds**: the victim cannot receive any deposit token they don't already hold — blocking deposits of new collateral types, blocking rescue via `deposit(..., onBehalfOf=victim)`, and blocking liquidation seizes that would credit a new token. Because a recipient cannot trigger `removeFromDepositTokensOfAccount` for themselves (removal is sender-side only), the victim cannot clear the griefed entries by transferring dust out unless they fully zero each token — but the attacker can simply re-send dust. If the victim's existing positions become liquidatable while a seize would add a new token to the liquidator's or victim's list, liquidation paths can also revert, degrading to insolvency risk.
- No governance, keeper, or privileged role is needed; any EOA executes this via public `transfer`/`transferFrom` or through `Operator.execute` batching all dust sends in one transaction.

### Likelihood Explanation
- Reachability: `DepositToken.transfer`/`transferFrom` are unprivileged public entry points (`_msgSender()`-compatible, callable directly or through `Operator.execute`).
- No existing guard stops it: `nonReentrant`, `whenNotPaused`, and `_revertIfLocked` only constrain the *sender*; the recipient is fully attacker-chosen. `MAX_TOKENS_PER_USER` exists as a bound but the protocol treats hitting it as a revert rather than handling it.
- Cost scales linearly with the number of deposit tokens (typically a handful of registered collaterals per pool), making the attack cheap and repeatable against liquidators, large depositors, or addresses the attacker front-runs.
- Uncertainty: I confirmed the add/remove logic and the missing recipient/minimum checks in `DepositToken.sol`; the exact revert behavior inside `Pool.addToDepositTokensOfAccount` at the `MAX_TOKENS_PER_USER` bound is inferred from the constant's presence and the enumerable-set pattern — the specific lines in `Pool.sol` were not read before the iteration limit.

### Recommendation
- Enforce a minimum transfer/mint amount that makes list-filling economically irrational, or skip `addToDepositTokensOfAccount` for sub-threshold (dust) credits.
- Allow an account to prune its own list: expose a `Pool` function that calls `removeFromDepositTokensOfAccount` when `balanceOf[account] == 0` for that token, so dust entries can be self-cleaned.
- Alternatively, make `addToDepositTokensOfAccount` idempotent/no-revert when the cap is reached (store position accounting so health checks don't depend on list membership for unlock calculation), or gate recipient list insertion behind the recipient having a nonzero existing balance plus explicit deposit intent.

### Proof of Concept
Hardhat fork sketch (reproducible against the repo's existing fixture pattern in `test/VesperGateway.test.ts`):

```ts
// Fork mainnet/Base at a block where Pool has N registered DepositTokens.
// attacker = fresh EOA, victim = target address.

const pool = await ethers.getContractAt('Pool', POOL_ADDRESS)
const depositTokens: string[] = await pool.getDepositTokens() // or equivalent getter

// 1. Attacker acquires dust of each deposit token:
for (const dt of depositTokens) {
  const dToken = await ethers.getContractAt('DepositToken', dt)
  // deposit 1 wei underlying of each collateral to mint dust msdTOKEN
  await underlying.approve(dToken.address, 1)
  await dToken.deposit(1, attacker.address)
}

// 2. Attacker dust-transfers 1 wei of each deposit token to the victim
//    (single tx via Operator.execute, or sequential transfers).
for (const dt of depositTokens) {
  const dToken = await ethers.getContractAt('DepositToken', dt)
  await dToken.transfer(victim.address, 1) // fills victim's depositTokensOfAccount
}
// Assert: (await pool.depositTokensOfAccount(victim.address)).length === MAX_TOKENS_PER_USER

// 3. Victim (or anyone on their behalf) attempts to deposit a collateral
//    type the victim doesn't hold yet:
const newDepositToken = await ethers.getContractAt('DepositToken', SOME_OTHER_DT)
await newDepositToken.connect(victim).deposit(amount, victim.address)
// Expected: reverts inside Pool.addToDepositTokensOfAccount (MaxTokensPerUserReached)

// 4. Optional: victim tries to clear an entry by transferring dust out —
//    list entry persists for recipient-side accounting; attacker re-sends dust
//    to re-fill the slot, sustaining the DoS.
```

The PoC demonstrates an unprivileged attacker forcing a persistent revert on the victim's deposit/mint/seize paths for any new collateral type, satisfying the "missing input validation → denial of service" analog with concrete state changes (list saturation) rather than gas-cost-only DoS.
