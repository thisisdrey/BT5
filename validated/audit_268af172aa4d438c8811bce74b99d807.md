### Title
RecurringAirdrop merkle leaf lacks chainId/contract domain — same proof is replayable across chains and instances — (File: contracts/utils/RecurringAirdrop.sol)

### Summary
`RecurringAirdrop.claim` builds the merkle leaf as `keccak256(abi.encodePacked(msg.sender, amount_))` — it commits only to the account and amount, with no `chainId`, contract address, or nonce. Metronome is explicitly multichain (deployments on mainnet, base, optimism, hemi, plasma, swell). If the same distribution (same merkle root) is published for `RecurringAirdrop` instances on multiple chains — which is the natural way to run a recurring multichain airdrop — the same proof is valid on every chain, letting an account claim its allocation once per chain and drain funds reserved for other claimants.

### Finding Description
The claim path is:
- `claim(uint256 amount_, bytes32[] calldata proof_)` at `RecurringAirdrop.sol:52`
- Leaf construction: `bytes32 _leaf = keccak256(abi.encodePacked(msg.sender, amount_))` at `RecurringAirdrop.sol:55`
- `MerkleProof.verify(proof_, merkleRoot, _leaf)` at `RecurringAirdrop.sol:56`
- Replay protection is only `claimed[msg.sender]` (line 34, 58–61), a per-chain mapping.

Nothing binds the leaf to `block.chainid` or `address(this)`. A proof generated for the deployment on chain A verifies identically on chain B whenever the same `merkleRoot` was set via `updateMerkleRoot` (which is plausible and likely for a "recurring" multichain airdrop where the same snapshot drives all chains). The attacker needs no privileges: they are the legitimate leaf holder and simply reuse their own proof on each chain. Only an account in the tree can do this, but the bug class (cross-chain replay due to missing domain separator) matches the reference issue exactly, and no modifier (`nonReentrant`, `Governable.onlyGovernor` on the root update) prevents it.

### Impact Explanation
Each `RecurringAirdrop` instance holds its own `token` balance meant to fund that chain's distribution. If roots are shared, eligible accounts can withdraw up to `amount_ - claimed` on every chain, i.e., claim N× their intended allocation. This either directly steals tokens earmarked for other recipients or permanently freezes the unclaimed yield of later claimants when the contract balance is exhausted — both are in-scope impact classes.

### Likelihood Explanation
Medium-low. Exploitation requires (a) the same merkle root being set on multiple chain deployments — a reasonable operational assumption for a recurring airdrop, but a configuration dependency, and (b) the attacker being an eligible leaf (which grants free access anyway, so cost is zero). It does not require any privileged actor to misbehave; it only requires the normal multichain deployment pattern.

### Recommendation
Bind the leaf to the deployment domain, e.g. `keccak256(abi.encode(block.chainid, address(this), msg.sender, amount_))`, or embed a per-deployment salt/identifier in the root-generation spec so proofs are single-chain. Document that each chain must use a distinct root if the leaf format is not changed.
