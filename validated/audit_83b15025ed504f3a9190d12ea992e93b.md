### Title
`Pool.quoteLiquidateMax` returns repay amounts that `Pool.liquidate` rejects due to the `debtFloorInUsd` check - ([File: contracts/Pool.sol])

### Summary
`Pool.quoteLiquidateMax` is the view function integrators and liquidator bots call to determine the maximum synthetic token amount that can be repaid when liquidating an unhealthy account. It mirrors the `maxLiquidable` cap and collateral-balance constraint enforced in `Pool.liquidate`, but it does not mirror the `debtFloorInUsd` check. As a result, it can return a `_maxAmountToRepay` value that `liquidate` will always revert on with `RemainingDebtIsLowerThanTheFloor`, reporting an incorrect liquidatable state — the same inconsistency class as `payoutFor` returning a payout that `purchaseBond` cannot fulfill.

### Finding Description
`liquidate` enforces four constraints that a quote must reflect:

1. Position is unhealthy (`PositionIsHealthy`)
2. `amountToRepay_.wadDiv(_debtTokenBalance) <= maxLiquidable` (`AmountGreaterThanMaxLiquidable`) — Pool.sol:567
3. Remaining debt must be zero or >= `debtFloorInUsd` (`RemainingDebtIsLowerThanTheFloor`) — Pool.sol:571-579
4. Seized collateral must fit the account's deposit token balance (`AmountIsTooHigh`) — Pool.sol:583

`quoteLiquidateMax` reproduces constraints 1, 2, and 4: it returns 0 for healthy positions, caps at `debtToken.balanceOf(account_).wadMul(maxLiquidable)`, and clamps to the amount repayable against the account's `depositToken_` balance via `quoteLiquidateIn` (Pool.sol:419-440).

However, it never applies the `debtFloorInUsd` rule:

```solidity
// Pool.sol:435-439
_maxAmountToRepay = debtTokenOf[syntheticToken_].balanceOf(account_).wadMul(maxLiquidable);
if (_amountToRepay < _maxAmountToRepay) {
    _maxAmountToRepay = _amountToRepay;
}
```

Contrast with `liquidate` (Pool.sol:571-579):

```solidity
if (debtFloorInUsd > 0) {
    uint256 _newDebtInUsd = masterOracle().quoteTokenToUsd(
        address(syntheticToken_),
        _debtTokenBalance - amountToRepay_
    );
    if (_newDebtInUsd > 0 && _newDebtInUsd < debtFloorInUsd) {
        revert RemainingDebtIsLowerThanTheFloor();
    }
}
```

Concrete example: `debtFloorInUsd = $100`, `maxLiquidable = 50%`, an account with `debtToken.balanceOf = $150` of msUSD debt, and collateral worth far more than the debt. `quoteLiquidateMax` returns `$75` (the `maxLiquidable` cap). But repaying `$75` leaves `$75` residual debt — nonzero and below the `$100` floor — so `liquidate(msUSD, account, 75e18, depositToken)` reverts with `RemainingDebtIsLowerThanTheFloor`. The only valid repay amounts are `<= $50` or the full `$150`; `quoteLiquidateMax` advertises a value in the forbidden range.

The same gap exists implicitly in `quoteLiquidateIn`/`quoteLiquidateOut`, which compute repay/seize amounts with no floor awareness.

### Impact Explanation
External liquidation bots and third-party integrations rely on `quoteLiquidateMax` to size repayments. Whenever the quoted max leaves residual debt in the `(0, debtFloorInUsd)` band, every liquidation attempted at that quoted amount reverts. During volatile markets this causes failed liquidation transactions precisely when speed matters — positions that could have been partially liquidated remain untouched, increasing the window in which collateral value can fall below debt and produce protocol bad debt (insolvency). It also wastes liquidator gas on reverted transactions. This is a reachable public-path inconsistency: any EOA can call `quoteLiquidateMax` and then `liquidate`.

### Likelihood Explanation
Likelihood depends on `debtFloorInUsd > 0` (a governor-set anti-dust parameter; it exists to prevent dust debt positions, so it is plausibly nonzero in production) and on `maxLiquidable < 1e18` (a partial-liquidation cap, standard in such systems). Whenever `debt * maxLiquidable` lands the remaining debt inside the `(0, floor)` band — i.e., whenever `debt * (1 - maxLiquidable)` in USD is nonzero and below the floor, or when collateral-balance-clamped amounts do — the quoted max is unusable. This occurs naturally for small positions near the floor, which are also the positions most in need of liquidation.

### Recommendation
Make `quoteLiquidateMax` floor-aware so it never returns a repay amount that `liquidate` would reject. After computing the candidate `_maxAmountToRepay`, check the residual debt in USD; if `0 < residualUsd < debtFloorInUsd`, clamp the quote to either the largest repay that keeps residual debt at/above the floor (`debt - floorEquivalent`) or the full debt if the position cannot satisfy the floor at all:

```solidity
// in quoteLiquidateMax, after computing _maxAmountToRepay
if (debtFloorInUsd > 0) {
    uint256 _balance = debtTokenOf[syntheticToken_].balanceOf(account_);
    uint256 _residualInUsd = masterOracle().quoteTokenToUsd(
        address(syntheticToken_), _balance - _maxAmountToRepay);
    if (_residualInUsd > 0 && _residualInUsd < debtFloorInUsd) {
        // clamp to full repay, or reduce so residual >= floor
        _maxAmountToRepay = _balance; // if full repay is allowed by collateral balance
    }
}
```

Alternatively, relax `liquidate`'s floor check to allow partial repays that leave sub-floor debt when `amountToRepay_` equals the amount needed to fully close but is capped by `maxLiquidable` — but whichever direction is chosen, quote and execution must agree on every revert condition.

### Proof of Concept
Hardhat/Foundry fork-style reproduction against the deployed `Pool`:

```solidity
function test_quoteLiquidateMax_inconsistentWithLiquidate() public {
    // Setup: pool with debtFloorInUsd = 100e18, maxLiquidable = 0.5e18
    // victim: healthy deposit made, borrows 150 msUSD, price move makes position unhealthy
    // liquidator holds >= 150 msUSD

    uint256 quoted = pool.quoteLiquidateMax(msUSD, victim, depositToken);
    // quoted == 75e18 (debt * maxLiquidable), > 0

    vm.prank(liquidator);
    vm.expectRevert(IPool.RemainingDebtIsLowerThanTheFloor.selector);
    pool.liquidate(msUSD, victim, quoted, depositToken);
    // remaining debt = 75 msUSD in USD terms -> 0 < 75 < 100 floor -> revert,
    // despite quoteLiquidateMax reporting 75e18 as the max repayable
}
```

The revert is deterministic given the quoted value: `quoteTokenToUsd(synthetic, debt - quoted)` lands strictly inside `(0, debtFloorInUsd)`, hitting the `RemainingDebtIsLowerThanTheFloor` branch in `Pool.liquidate` (Pool.sol:571-579) that `quoteLiquidateMax` never models.
