### Title
Unrestricted `DeleteObjectPool` RPC allows destruction of shared object pool while member repositories still depend on it - (File: internal/gitaly/service/objectpool/delete.go)

### Summary
Gitaly's `ObjectPoolService.DeleteObjectPool` RPC unconditionally removes an object pool repository from disk without checking whether any repositories are still linked to it as an alternate. Because object pools are shared storage used by potentially many fork/member repositories, deleting the pool while members remain linked leaves every dependent repository unable to resolve objects it does not store locally, corrupting them. This mirrors the reported HyVM issue in structure: a single unrestricted destructive primitive on a *shared* resource that unrelated consumers depend on, with no ownership or reference check gating the destructive action.

### Finding Description
The `DeleteObjectPool` handler calls `repoutil.Remove` directly on the pool repository with no check for existing pool members: [1](#0-0) 

The proto-level documentation for the service explicitly acknowledges the lack of safety checks and places the burden entirely on the caller: [2](#0-1) [3](#0-2) 

Object pools exist specifically to deduplicate objects shared across many fork/member repositories via the `objects/info/alternates` mechanism, as documented in `doc/object_pools.md`: [4](#0-3) 

Any member repository still linked to the pool (via `Link` in `internal/git/objectpool/link.go`, which writes the pool's path into the member's `objects/info/alternates` file) relies on the pool for objects it does not itself store: [5](#0-4) 

If the pool is deleted while members are still linked, those members lose access to any objects that only exist in the pool — this is the exact "unrestricted destructive primitive breaks dependents relying on shared state" pattern in the source report (there, `callcode`→`selfdestruct` destroying HyVM broke `delegatecall`ing Nested wallets; here, an unchecked `DeleteObjectPool` destroys a pool that member repositories `delegatecall`-style depend on via alternates).

Praefect's routing layer (`internal/praefect/delete_object_pool.go`) similarly performs no member-count check before fanning the deletion out to every backing Gitaly node — it only validates that the target path is structurally a pool directory (`storage.IsRailsPoolRepository`), not that the pool is unused: [6](#0-5) 

### Impact Explanation
Any caller with access to invoke `DeleteObjectPool` (an ordinary "crafted RPC field" call, requiring only a valid repository path/storage name pointing at an existing object pool) can silently corrupt every repository still linked to that pool, without any ownership check that the caller is the pool's only remaining member or has authority to retire it. Because object pools back many forks of a source repository, deleting a shared pool can affect users/repositories unrelated to the caller's own project, causing missing-object errors or data loss across an unbounded set of member repositories — a direct cross-repository object-access/DoS impact.

### Likelihood Explanation
The RPC is a standard, first-class part of `ObjectPoolService` and is reachable through the normal object-pool lifecycle (fork/pool creation and teardown flows). No `LinkRepositoryToObjectPool`/`DisconnectGitAlternates` state is checked before deletion, so triggering the corruption requires nothing more than issuing `DeleteObjectPool` for a pool that still has members — a plausible operational or intentionally malicious sequencing given the API imposes no server-side ordering guarantee.

### Recommendation
- **Short term:** Before removing the pool repository in `DeleteObjectPool` (`internal/gitaly/service/objectpool/delete.go`), verify that no repositories are still linked as alternates to the pool (e.g., consult the transaction/partition metadata or member records) and reject the deletion (or require an explicit force flag) if members remain.
- **Long term:** Track pool membership explicitly (rather than relying purely on caller discipline documented in comments) so that `DeleteObjectPool` can enforce a "zero members" invariant server-side, consistent with how `Link`/`Disconnect` already track alternate state transactionally.

### Proof of Concept
1. Create a source repository and an object pool from it via `CreateObjectPool`.
2. Link a second repository to the pool via `LinkRepositoryToObjectPool`, causing objects unique to the pool to be deduplicated out of the member (its `objects/info/alternates` now points at the pool, per `internal/git/objectpool/link.go`).
3. Without disconnecting the member, call `DeleteObjectPool` against the pool. The call succeeds unconditionally, per `internal/gitaly/service/objectpool/delete.go`, which invokes `repoutil.Remove` with no membership check.
4. Attempt to read an object in the member repository that only existed in the now-deleted pool (e.g., via `git cat-file` or an RPC like `GetBlob`): the object is unresolvable, demonstrating repository corruption of a repository the caller may not even own.

func DeleteObjectPoolHandler(rs datastore.RepositoryStore, logger log.Logger, conns Connections) grpc.StreamHandler {
	return removeRepositoryHandler(rs, logger, conns,
		func(stream grpc.ServerStream) (*gitalypb.Repository, error) {
			var req gitalypb.DeleteObjectPoolRequest
			if err := stream.RecvMsg(&req); err != nil {
				return nil, fmt.Errorf("receive request: %w", err)
			}

			repo, err := objectpoolsvc.ExtractPool(&req)
			if err != nil {
				return nil, err
			}

			if !storage.IsRailsPoolRepository(repo) {
				return nil, structerr.NewInvalidArgument("%w", objectpool.ErrInvalidPoolDir)
			}

			return repo, nil
		},
