### Title
`tokens_burnt` from a rolled-back `DeleteAccount` survives into `tx_burnt_amount` even though the account/gas-keys are never actually removed - ([File: runtime/runtime/src/actions.rs] / [File: runtime/runtime/src/lib.rs])

### Summary
`action_delete_account` unconditionally increments the shared `result.tokens_burnt` for burned gas-key balances and mutates the shared `ActionResult` directly (not a per-action struct that gets merged/rolled back). If a later action in the same receipt's action list fails, `TrieUpdate::rollback()` discards the account removal (and the queued beneficiary refund receipt), but nothing resets `result.tokens_burnt`, so the gas-key-burn amount is still added to `tx_burnt_amount` at `lib.rs:1048` and reported/accounted as burnt even though the account and its gas keys remain fully intact in committed state.

### Finding Description
`action_delete_account` computes `gas_key_balance_to_burn` and adds it directly into the shared, receipt-wide `result: &mut ActionResult` accumulator: [1](#0-0) 

This same `result` object is passed by mutable reference across every action in the receipt's action list (not a fresh per-action struct that later gets merged with rollback-aware accounting). If a subsequent action (e.g. a `FunctionCall`) fails, that failure sets `result.result = Err(...)`, and `Runtime::apply_action_receipt` decides purely from `result.result` whether to commit or roll back the `TrieUpdate`: [2](#0-1) 

`state_update.rollback()` discards all trie-level mutations for the receipt — including `remove_account`'s removal of the account and its gas keys, and the queued beneficiary-refund receipt in `result.new_receipts` (already established behavior). However, between the rollback decision (line 1032) and the point where `result.tokens_burnt` is folded into `tx_burnt_amount` (line 1048), there is no code path that clears, discounts, or gates `tokens_burnt` on `result.result` being `Err`. The value flows straight through: [3](#0-2) 

So the gas-key burn — which is only semantically valid because the account and its gas keys are supposed to be actually deleted — gets attributed to `tx_burnt_amount` (and hence to the receipt's reported burnt tokens / total-supply deduction) even though the account, its gas keys, and their un-burnt balances remain fully present in the committed trie state. This breaks value conservation: tokens are recorded/accounted as burnt with no corresponding decrease in any real account balance.

### Impact Explanation
This is a token-loss / inflation-accounting bug (`VALUE_CONSERVATION` invariant violation): the network's burnt-token accounting (which feeds into total-supply reduction) is decremented for value that was never actually removed from any account, since the account and its gas keys survive the rollback intact. This does not directly hand funds to the attacker, but it causes a permanent, unrecoverable divergence between total token supply accounting and the actual sum of on-chain balances, which is the "token inflation or loss" bounty category.

### Likelihood Explanation
Preconditions: an attacker needs to submit (or have their contract emit via promise batch) a receipt whose action list contains `DeleteAccount` followed by another action that is made to fail (e.g., a `FunctionCall` to a contract that deliberately panics, or one crafted to run out of gas), and the account being deleted must own a "gas key" with positive `gas_key_balance_to_burn`. This is achievable by an ordinary, unprivileged account: no special permissions, validator access, or leaked keys are required — only a self-controlled account and a self-deployed contract. The main open question (not fully verifiable from the code inspected) is whether transaction/receipt-action validation elsewhere in the codebase enforces that `DeleteAccount` must be the last action in an action list; if that ordering restriction exists, it would need to be bypassed via a promise-batch-produced receipt rather than a direct signed transaction. This ordering-validation aspect could not be confirmed with the available tool calls and should be verified before treating this as fully exploitable end-to-end.

### Recommendation
Reset or discount `result.tokens_burnt` (and any other DeleteAccount-specific token-burn contributions) whenever `result.result` transitions to `Err` from a later action in the same receipt, mirroring the existing handling that already clears `new_receipts` on error (`set_error`/`merge`). Alternatively, defer the `tokens_burnt` increment for gas-key burning until after all actions in the receipt have succeeded and the `TrieUpdate` is about to be committed, rather than mutating the shared accumulator eagerly inside `action_delete_account`.

### Proof of Concept
1. Runtime integration test (in `runtime/runtime/src/tests/` or via `runtime/runtime/src/lib.rs::apply_action_receipt` unit test):
   - Create an account with a gas key that has a positive `gas_key_balance_to_burn`.
   - Construct a `Receipt`/`ActionReceipt` whose `actions` are `[Action::DeleteAccount(DeleteAccountAction { beneficiary_id }), Action::FunctionCall(...)]` where the `FunctionCall` is engineered to fail (e.g., call a non-existent method, or exceed gas).
   - Call `Runtime::apply_action_receipt` (or the higher-level `apply` entry point) with this receipt.
   - Assert: `result.result` is `Err(...)`.
   - Assert: the account and its gas key still exist in `state_update`/final trie state with their original (un-burnt) balances (i.e., `remove_account`'s effect was rolled back).
   - Assert (bug reproduction): `result.tokens_burnt > 0` and/or the returned execution outcome's `tokens_burnt`/`tx_burnt_amount` is non-zero, despite the account never having been deleted — expected correct behavior is `tokens_burnt == 0` in this case.
