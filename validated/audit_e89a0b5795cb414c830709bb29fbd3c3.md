### Title
DeleteObjectPool has no membership check, corrupting active pool members and causing DoS to their fetch/read/reference operations - (File: internal/gitaly/service/objectpool/delete.go)

### Summary
`DeleteObjectPool` unconditionally removes the object-pool repository from disk regardless of whether other repositories are still linked to it as alternates. This mirrors the reported `asdUSDC` bug class: removing a shared backing resource (a whitelisted USDC version / here, the shared object pool) while dependent accounting (token supply / here, member repositories' alternates) still relies on it, leaving the dependents permanently unable to fully satisfy requests — a resource-availability DoS.

### Finding Description
The `ObjectPoolService` proto explicitly documents the danger: [1](#0-0) 

which states "DeleteObjectPool deletes the object pool. There are no safety checks in place, so if any repository is still using this object pool it will become corrupted." The Go server implementation confirms there is no check for remaining pool members before removal — it simply resolves the pool and calls `repoutil.Remove`: [2](#0-1) 

Object pools exist precisely so that multiple fork member repositories can deduplicate objects via `objects/info/alternates` pointing at the pool [3](#0-2) . Any member repository still linked (via `LinkRepositoryToObjectPool`) depends on the pool's objects to be complete — Git needs the alternate to resolve objects that were deduplicated out of the member repo. If the pool is deleted while a member is still linked (e.g., a member link created after a stale `GetObjectPool` check, a race between `LinkRepositoryToObjectPool` and `DeleteObjectPool`, or an operator/API caller invoking `DeleteObjectPool` without first disconnecting all members via `DisconnectGitAlternates`), all subsequent git operations on the member repositories (fetch, clone, cat-file, fsck) will fail because they cannot resolve objects that only existed in the now-deleted pool. This exactly parallels the `asdUSDC.withdraw` situation where remaining `usdc1` couldn't back all outstanding `asdUSDC` after `usdc2` was delisted — here, a resource (object pool) that other entities still depend on is removed with no dependency/reference check, producing broken/inaccessible state for the dependents.

### Impact Explanation
Once a linked member repository's object pool is deleted, the member repository becomes irreparably broken: reads for objects that were deduplicated into the pool return "not found," `git fsck` fails, and any push/fetch/clone against the member repository will error out or serve corrupted history. Because Gitaly RPCs are called under the standard shared auth token without a stronger per-object-pool ownership check, any caller (or a race between two legitimate, otherwise-unprivileged mutator RPCs — `LinkRepositoryToObjectPool` and `DeleteObjectPool`) can trigger this DoS against unrelated fork member repositories. This is a persistent denial of service, requiring repository recovery/re-clone rather than a transient failure.

### Likelihood Explanation
`DeleteObjectPool` is a standard, always-available mutator RPC with no membership validation, so the unsafe path is reached on every invocation, not just an edge case. The scenario is realistic in normal fork lifecycle operations: pool creation, linking members, unlinking, and deletion are separate RPC calls with no atomic cross-check, so a caller (or concurrent callers) issuing `DeleteObjectPool` without first successfully calling `DisconnectGitAlternates` on every member — including due to a race, a stale membership list, or simple misuse — reliably reproduces the corruption. The doc comment itself acknowledges this is a known, intentional gap ("no safety checks in place").

### Recommendation
Before deleting an object pool, verify there are no remaining members (e.g., check the pool store `ListPoolMembers`/`GetPoolForMember` state introduced in [4](#0-3) , or scan repositories for alternates pointing at the pool) and reject the RPC with a `FailedPrecondition` error if any members remain, analogous to removing the unsafe assumption in the `asdUSDC.withdraw` fix but in the opposite direction — add the missing safety check rather than removing an existing one, since here the missing check (not an overly strict one) is what causes the DoS.

### Proof of Concept
1. Create an object pool from repository A and link repository A as a member via `LinkRepositoryToObjectPool` (deduplicating objects out of A into the pool).
2. Call `DeleteObjectPool` on the pool while A is still linked — `internal/gitaly/service/objectpool/delete.go` performs no membership check and deletes the pool directory.
3. Attempt to fetch/clone/`git fsck` repository A: operations fail or return corrupted results because objects previously deduplicated into the deleted pool are unrecoverable, reproducing the "insufficient backing resource for dependents" DoS described in the source report.

```go
func (s *server) DeleteObjectPool(ctx context.Context, in *gitalypb.DeleteObjectPoolRequest) (*gitalypb.DeleteObjectPoolResponse, error) {
	pool, err := s.poolForRequest(ctx, in)
	if err != nil {
		if errors.Is(err, objectpool.ErrInvalidPoolRepository) {
			// TODO: we really should return an error in case we're trying to delete an
			// object pool that does not exist.
			return &gitalypb.DeleteObjectPoolResponse{}, nil
		}

		return nil, err
	}

	if err := repoutil.Remove(ctx, s.logger, s.locator, nil, s.repositoryCounter, pool); err != nil {
		return nil, fmt.Errorf("remove: %w", err)
	}
```

```markdown
# Object Pools

When creating forks of a repository, most of the objects for forked repository
and the repository it forked from are shared. Storing those shared objects
multiple times is a waste of disk space and also of CPU time, given that those
shared objects would have to be repacked for both repositories. To fix this
waste of resources, we use object pools, which are essentially a repository
which holds the shared objects of both repositories.

The sharing of objects for a given repository and its object pool is done via
alternate object directories which Gitaly sets up when linking a repository to
an object pool by writing the `objects/info/alternates` file.
```
