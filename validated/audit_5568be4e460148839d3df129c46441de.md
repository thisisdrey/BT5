I have enough evidence to finalize the finding. `ProcessCentralDirEntry` in `third_party/ijar/zip.cc` is the only zip-record parser in the codebase with no shell/JUnit-level bounds test and no `EnsureRemaining` calls, confirming the asymmetry with `ProcessLocalFileEntry`.

### Title
Heap buffer over-read parsing untrusted ZIP/JAR central-directory records - (File: third_party/ijar/zip.cc)

### Summary
`InputZipFile::ProcessCentralDirEntry` in ijar's ZIP reader deserializes central-directory-header fields (`file_name_length`, `extra_field_length`, `file_comment_length`, and the ZIP64 extra-field sub-records) directly from an attacker-controlled, memory-mapped `.jar`/`.zip` file without validating that the declared lengths actually fit within the mapped input before advancing the read cursor or dereferencing memory — the same bug class as HDF5's `H5HL__fl_deserialize` heap-based buffer over-read from an unvalidated length field in a deserialized on-disk record.

### Finding Description
`InputZipFile::ProcessCentralDirEntry` reads the fixed part of a Central Directory Header, then: [1](#0-0) 
It reads `file_name_length`/`extra_field_length`/`file_comment_length` straight off the mapped bytes and immediately `memcpy`s and advances `p` by those attacker-supplied 16-bit counts with **no check that the counts fit within the remaining mapped region**. This is unlike its sibling `ProcessLocalFileEntry`, which explicitly guards every variable-length read with `EnsureRemaining()`: [2](#0-1) [3](#0-2) 

The extra-field walking loop compounds the problem — it derives `header_id`/`data_size` from the untrusted bytes and advances `extra_p` by the attacker-chosen `data_size` with no bound against the declared `extra_field_length` or the end of the mapped file, and then reads a ZIP64 8-byte value (`get_u8le(extra)`) at that unchecked offset: [4](#0-3) 

Because `zipdata_in_`/`central_dir_` are backed by a fixed-size `mmap` of the input file (see `MappedInputFile` usage), advancing `p`/`extra_p` past the end of the mapped region and then dereferencing it (`get_u2le`, `get_u4le`, `get_u8le`, `memcpy`) reads adjacent process memory or an unmapped page — a classic CWE-125 heap/mmap buffer over-read triggered purely by attacker-chosen length fields in a deserialized record, mirroring the HDF5 free-list deserialization bug. `FindZipCentralDirectory` only validates that the *aggregate* `central_dir_offset + central_dir_size <= in_length`; it never validates individual per-entry field lengths against the remaining bytes: [5](#0-4) 

This code path is reached by `ijar`, the Bazel-shipped tool that strips a `.jar` to its interface for Java compilation caching, invoked via `run_ijar`/`stamp_jar`/implicit ijar actions on `java_import`, `http_jar`, and generally any `.jar` dependency a build consumes: [6](#0-5) 
An unprivileged attacker who controls the bytes of a downloaded jar (`http_jar`/`http_archive` without/with a mismatched-but-attacker-crafted sha256, or a malicious jar committed on an untrusted branch that CI builds) fully controls this central-directory content and can set arbitrary `file_name_length`/`extra_field_length`/ZIP64 sub-field sizes to trigger the over-read the moment Bazel processes the jar with ijar.

By contrast, Bazel's other JAR-header parser (`singlejar`'s `zip_headers.h`) already recognizes this exact hazard and bounds-checks extra-field walking against the declared buffer end, and even has a dedicated regression test (`CreateZipWithMalformedExtraField`) for a malformed/oversized extra-field payload: [7](#0-6) [8](#0-7) 
`ijar/zip.cc`'s central-directory reader has no equivalent protection.

### Impact Explanation
A successful over-read causes ijar (running inside the Bazel build, in-process with the action, no sandbox escape needed since it's a legitimate spawned tool reading attacker content) to read out-of-bounds memory adjacent to the mmap'd file. Depending on layout this manifests as a crash (denial of the specific build action) or, when the leaked bytes are subsequently copied into the interface jar's filename buffer (`memcpy` into `filename[PATH_MAX]`) or used to compute buffer offsets for later writes, an information disclosure of adjacent process memory into build outputs. This is a genuine memory-safety violation in code parsing untrusted, attacker-supplied dependency content — not a third-party CVE, not a sandbox issue, and not DoS-only, since it also yields a concrete out-of-bounds read whose content can flow into the tool's output.

### Likelihood Explanation
Any target with a `java_import`/`http_jar`/downloaded `.jar` dependency that flows through `run_ijar` triggers this parser. An attacker only needs to control the bytes of one such jar (a public dependency, a compromised mirror serving a "matching-hash" malicious artifact, or a jar committed to an untrusted branch that CI builds) — no MITM, no credential access, and no root-repo Starlark execution is required. The vulnerable fields (`file_name_length`, `extra_field_length`, ZIP64 payload sizes) are single `uint16`/`uint16` values fully controlled by whoever authored the jar.

### Recommendation
Add `EnsureRemaining`-style bounds checks to `InputZipFile::ProcessCentralDirEntry` for `file_name_length`, `extra_field_length`, and `file_comment_length` before advancing `p`, and bound the extra-field walking loop (`extra_p`/`data_size`) so that `extra_p + 4 <= p_end` and `extra_p + data_size <= p_end` are enforced before every read, mirroring the checks already present in `ExtraField::find` in `src/tools/singlejar/zip_headers.h`.

### Proof of Concept
Craft a minimal ZIP/JAR whose Central Directory Header near the very end of the mapped file declares `file_name_length` (or `extra_field_length`) far larger than the bytes actually remaining before EOF (analogous to `CreateZipWithMalformedExtraField` in `src/tools/singlejar/output_jar_simple_test.cc`, but targeting `ProcessCentralDirEntry`'s missing checks instead of the already-guarded `zip_headers.h` path). Feed it to `ijar` (e.g., via a `BuildIntegrationTestCase`/shell test invoking `run_ijar` on the crafted jar, similar to `third_party/ijar/test/zip_test.sh`) and observe the out-of-bounds read/crash (e.g., under ASan) when `memcpy`/`get_u2le`/`get_u8le` dereference past the mmap'd region's end.
