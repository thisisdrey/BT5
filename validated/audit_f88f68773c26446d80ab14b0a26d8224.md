### Title
Unvalidated `GitAlternateObjectDirectories` field bypasses quarantine/path validation applied to `GitObjectDirectory` - (File: internal/git/gitcmd/command_factory.go)

### Summary
`gitalypb.Repository` carries two related, attacker/Rails-influenced fields describing where Git should look for objects: `git_object_directory` and `git_alternate_object_directories`. The former is put through strict quarantine/path validation before being trusted, but the latter is injected straight into the Git subprocess environment without going through the equivalent validation, mirroring the Ethena bug pattern where one entry path enforces an invariant (`SOFT_RESTRICTED_STAKER_ROLE` check) and a parallel entry path to the same sensitive operation (`_withdraw`) does not.

### Finding Description
`internal/git/localrepo/paths.go`'s `ObjectDirectoryPath` performs careful validation of `repo.GetGitObjectDirectory()`: it resolves the path relative to the storage root, rejects traversal, and requires the value to either point inside the repository or match the expected quarantine-directory prefix under the storage's temp directory. [1](#0-0) [2](#0-1) 

However, when Gitaly actually spawns a `git` subprocess for the repository, `internal/git/gitcmd/command_factory.go`'s `newCommand` builds the process environment by calling `alternates.Env(repoPath, repo.GetGitObjectDirectory(), repo.GetGitAlternateObjectDirectories())` and prepending the result to the command's env — using the raw, request-supplied `GetGitAlternateObjectDirectories()` value directly, with none of the storage-root/quarantine-prefix checks that `ObjectDirectoryPath` applies to the sibling field. [3](#0-2) 

This is architecturally the same class of bug as the Ethena finding: two fields/entrypoints that are supposed to be governed by the same "must be a legitimate quarantine directory belonging to this repository" invariant, but the invariant is enforced on only one of them. `GIT_ALTERNATE_OBJECT_DIRECTORIES` is exactly the mechanism Gitaly's own object-quarantine design relies on to let Rails "see" pushed-but-not-yet-merged objects during `pre-receive` access checks — the field is populated from data that flows back from Rails/HTTP loopback requests, i.e. it is not purely internal, trusted data. [4](#0-3) [5](#0-4) 

### Impact Explanation
If the `git_alternate_object_directories` value on a `Repository` message reaching `newCommand` is not otherwise constrained by an earlier validation layer (e.g. transaction middleware's quarantine checks, which only special-case when `GitObjectDirectory`/`GitAlternateObjectDirectories` is non-empty but do not themselves validate the alternates paths' contents against storage boundaries the way `ObjectDirectoryPath` does), an attacker-influenced value here could point `GIT_ALTERNATE_OBJECT_DIRECTORIES` at another repository's object directory or a location outside the storage root, letting subsequent Git subprocess invocations (e.g. `cat-file`, `rev-parse`, `pack-objects`) resolve/disclose objects that do not belong to the target repository — a cross-repository object access analogous in kind (though not identical in mechanism) to the "shared internal function missing the guard applied on the sibling path" root cause of the referenced report.

### Likelihood Explanation
Reachability depends on whether an ordinary caller (a push that triggers Rails access-check loopback, or any RPC that lets a `Repository` protobuf carry non-empty `git_alternate_object_directories`) can supply this field with a value that escapes the intended quarantine directory. I was not able to fully confirm within the available tool budget whether `internal/git/alternates/alternates.go`'s `Env` function, or an earlier middleware layer, re-validates the alternates paths before they reach `newCommand`; I could only confirm that `ObjectDirectoryPath` (used for `GitObjectDirectory`) contains this validation and that `newCommand` calls `alternates.Env` with the raw alternates field. This is a caveat on confidence, not a claim that the path is exploitable end-to-end.

### Recommendation
Route `repo.GetGitAlternateObjectDirectories()` through the same validation used for `GitObjectDirectory` in `ObjectDirectoryPath` (storage-root containment plus the quarantine-prefix / in-repository check) before it is used to construct `GIT_ALTERNATE_OBJECT_DIRECTORIES`, so both fields governing object visibility for a given repository enforce an identical invariant instead of only one of them being checked.

### Proof of Concept
Not independently reproduced; the analog is derived from static comparison of `ObjectDirectoryPath` (internal/git/localrepo/paths.go) versus the alternates-environment construction in `newCommand` (internal/git/gitcmd/command_factory.go), showing the guard applied to `GitObjectDirectory` is absent for the sibling `GitAlternateObjectDirectories` field at the point where both are consumed to build the Git subprocess environment.

func (repo *Repo) ObjectDirectoryPath(ctx context.Context) (string, error) {
	repoPath, err := repo.Path(ctx)
	if err != nil {
		return "", err
	}

	objectDirectoryPath := repo.GetGitObjectDirectory()
	if objectDirectoryPath == "" {
		return "", structerr.NewInvalidArgument("object directory path is not set")

		return "", structerr.NewInvalidArgument("validate relative path: %w", err)
