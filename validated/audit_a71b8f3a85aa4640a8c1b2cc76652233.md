### Title
Unsafe downcast to `long` via `BigInteger.longValue()` in market order matching can silently corrupt settled quantities - (File: `chainbase/src/main/java/org/tron/core/capsule/utils/MarketUtils.java`)

### Summary
`MarketUtils.multiplyAndDivide`, used by `MarketSellAssetActuator` to compute the amount of tokens exchanged when matching taker/maker orders, falls back to `BigInteger` arithmetic on overflow but then downcasts the result to `long` using `longValue()` instead of `longValueExact()`. This is the same unsafe-downcast bug class as the referenced Sherlock report (`uint256` -> `uint96` truncation): a value that legitimately exceeds the target type's range is silently wrapped/truncated instead of causing the transaction to fail, which can corrupt token balances credited to market participants.

### Finding Description
`MarketUtils.multiplyAndDivide` first attempts safe `long` arithmetic (`multiplyExact`/`floorDiv`), and only on `ArithmeticException` falls back to `BigInteger`: [1](#0-0) 

Note the final line: `return aBig.multiply(bBig).divide(cBig).longValue();` — `longValue()` does **not** check whether the `BigInteger` result actually fits in a `long`; it truncates to the low 64 bits, silently producing an incorrect (and potentially negative or drastically smaller) value instead of throwing, unlike `longValueExact()` which is used consistently elsewhere in the same class for exchange calculations (e.g. `ExchangeInjectActuator`/`ExchangeWithdrawActuator` use `.longValueExact()`): [2](#0-1) 

This function is called directly from `matchSingleOrder` in `MarketSellAssetActuator`, using quantities that come straight from the taker's `MarketSellAssetContract` and stored maker orders: [3](#0-2) [4](#0-3) [5](#0-4) 

The resulting (possibly truncated) quantity is then directly credited to accounts via `addTrxOrToken`/`addAssetAmountV2` with no additional sanity check against the truncated value: [6](#0-5) 

The only bound on the input order quantities is `dynamicStore.getMarketQuantityLimit()`, checked in `validate()`: [7](#0-6) 

I was unable to fully confirm within this session the exact configured/default value of `getMarketQuantityLimit()` in `DynamicPropertiesStore.java` (multiple references exist but I could not read the constant's numeric value before running out of tool calls), so I cannot definitively prove that the product of two allowed quantities can exceed `Long.MAX_VALUE` (~9.22×10^18) under default configuration. If the limit is configured (via proposal) at or near a large value such as `1_000_000_000_000_000_000L` (a magnitude already used elsewhere in the codebase, e.g. `supply` in `ExchangeCapsule.transaction`), two such quantities multiplied together would overflow well past `Long.MAX_VALUE`, and even the `BigInteger` fallback path would then silently truncate via `longValue()`.

### Impact Explanation
If triggered, `takerBuyTokenQuantityReceive` or `makerBuyTokenQuantityReceive` computed by `multiplyAndDivide` would be a truncated/incorrect `long` value that no longer reflects the actual mathematical result of the trade. Because this value is used both to update in-memory order remainders (`setSellTokenQuantityRemain`) and to credit token/TRX balances to accounts, a truncated value can result in a party receiving far less (or, depending on truncation, potentially a corrupted/incorrect) token amount than the order math dictates, causing an unbacked accounting mismatch between what was debited from the counterparty and what was credited to the recipient — a fund-loss/inconsistency scenario analogous to the H-9 finding.

### Likelihood Explanation
Reachable via a single signed `MarketSellAssetContract` transaction (an order placer / market participant), requiring no privileged role — matching the required threat model (unprivileged transaction broadcaster). Likelihood depends on whether `dynamicStore.getMarketQuantityLimit()` is configured high enough that `makerSellQuantity * makerBuyQuantity` (or similar cross products in `multiplyAndDivide`) can exceed `Long.MAX_VALUE`; I could not verify the exact deployed value of this limit in the available time, so likelihood should be treated as **uncertain/unconfirmed** pending that check, though the pattern itself (unchecked `BigInteger.longValue()` downcast on a user-influenced computation) is a clear code-level defect regardless.

### Recommendation
Replace `.longValue()` with `.longValueExact()` in `MarketUtils.multiplyAndDivide` (as is already done in `ExchangeInjectActuator`/`ExchangeWithdrawActuator`) so that an out-of-range result throws `ArithmeticException` and causes transaction/order-matching failure instead of silently producing a truncated quantity. Additionally, confirm and, if necessary, tighten `DynamicPropertiesStore`'s market quantity limit to guarantee `sellTokenQuantity * buyTokenQuantity` (and all cross-multiplications performed in matching) cannot exceed `Long.MAX_VALUE`.

### Proof of Concept
Not independently verified with a runnable reproduction in this session due to inability to confirm the exact runtime value of `getMarketQuantityLimit()`. Conceptually:
1. Attacker (or two colluding accounts) create a maker order with `sellTokenQuantity` and `buyTokenQuantity` near the configured `marketQuantityLimit`.
2. A taker order is placed such that `matchSingleOrder` invokes `MarketUtils.multiplyAndDivide(a, b, c, ...)` where `a * b` exceeds `Long.MAX_VALUE` even as a `BigInteger` product exceeding 64-bit range.
3. The fallback path computes `aBig.multiply(bBig).divide(cBig)`, and if this quotient still exceeds `Long.MAX_VALUE`/is negative when truncated, `.longValue()` silently returns a wrong value that is then credited via `addTrxOrToken`, producing an accounting mismatch instead of a reverted transaction.

This should be confirmed with a unit test analogous to `MarketSellAssetActuatorTest` using boundary quantities at `dynamicStore.getMarketQuantityLimit()`.

  public static long multiplyAndDivide(long a, long b, long c, boolean disableMath) {
    try {
      long tmp = multiplyExact(a, b, disableMath);

  }
