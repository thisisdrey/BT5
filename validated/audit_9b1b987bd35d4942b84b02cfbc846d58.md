### Title
Integer overflow in ijar's ZIP central-directory bounds check allows out-of-bounds read past the mmap'd file - (File: `third_party/ijar/zip.cc`)

### Summary
`FindZipCentralDirectory()` validates the central-directory location using an unchecked addition, mirroring the AFBC bug class (offset + size added without overflow checking, allowing an undersized/invalid region to pass validation).

### Finding Description
`FindZipCentralDirectory()` reads `central_dir_offset` and `central_dir_size` and validates them with: [1](#0-0) 

These fields are populated either from the 32-bit (≤4GB-bounded) fields of the classic EOCD record, or — when a Zip64 EOCD is present — from fully attacker-controlled 64-bit values read via `get_u8le()` in `MaybeReadZip64CentralDirectory()`: [2](#0-1) 

The bounds check `cd.central_dir_offset + cd.central_dir_size > in_length` (line 766) performs the addition on `u8` (`uint64_t`) values without any `check_add_overflow`-equivalent guard. If an attacker crafts a Zip64 EOCD record where `central_dir_offset` and `central_dir_size` are both large enough that their sum wraps around `UINT64_MAX` back to a value ≤ `in_length`, the check incorrectly succeeds even though `central_dir_offset` itself points far outside the mmap'd buffer.

The validated (but invalid) offset then propagates into `InputZipFile::Open()`: [3](#0-2) 

Here `zipdata_start + central_dir_offset` performs pointer arithmetic with an attacker-controlled huge 64-bit offset, which is undefined behavior and computes an out-of-bounds pointer used to derive `in_offset_`. That value is later added to the input cursor `p` in `InputZipFile::ProcessNext()`: [4](#0-3) 

Subsequent reads (`get_u4le`, `EnsureRemaining`, etc.) operate on this corrupted cursor, and `EnsureRemaining()` itself computes `remaining = input_file_->Length() - in_offset` without checking that `in_offset` is within bounds first: [5](#0-4) 

If `in_offset` (derived from the attacker-controlled offset) exceeds `input_file_->Length()`, this subtraction itself underflows (both are `size_t`), making `remaining` wrap to a huge value and defeating the very bounds check meant to prevent reading past the end of the mmap'd input file — leading to an out-of-bounds read of process memory adjacent to the mapping (`mapped_file_unix.cc`'s `mmap`-backed buffer).

### Impact Explanation
The ZIP parser in `third_party/ijar/zip.cc` is exercised by the `ijar` tool (`third_party/ijar/ijar.cc`, invoked via `OpenFilesAndProcessJar`), which Bazel runs on JAR files during Java interface-jar generation. A JAR is just a ZIP file, so a crafted `.jar` supplied as a build input (e.g., a prebuilt jar dependency fetched over the network) can trigger this parser. A successful overflow bypass turns the central-directory bounds check into a no-op, letting `central_dir_offset`/`central_dir_size` values that should have been rejected as "invalid" flow into pointer arithmetic and subsequent reads. This can cause an out-of-bounds read of heap/mmap-adjacent memory (crash or potential information disclosure) during a routine build step, matching the "read outside... output base" impact bar (Confidentiality/Availability impact, no code-exec proven here).

### Likelihood Explanation
Exploitation requires the attacker to control the full byte content of a `.jar`/`.zip` file that Bazel's `ijar` tool processes (e.g., an externally hosted precompiled jar). It requires crafting a Zip64 EOCD record with two 64-bit values summing to overflow — a straightforward, deterministic byte-pattern construction, not a race or timing issue. No existing overflow guard exists on this addition (verified: no `check_add_overflow`, `__builtin_add_overflow`, or manual overflow test is present around lines 744–769). This makes the likelihood **plausible but bounded by the reach of `ijar` to attacker-influenced jar bytes**, and I could not fully verify within this pass whether Bazel's Java toolchain always requires a pinned integrity hash on jar inputs before invoking `ijar`, which would reduce (but not eliminate, since the pinned bytes are still attacker-authored and unsafe to parse) the practical blast radius.

### Recommendation
Add explicit overflow-checked arithmetic (e.g., compare `central_dir_size > in_length - central_dir_offset` after confirming `central_dir_offset <= in_length`, or use a 128-bit/saturating add helper) in `FindZipCentralDirectory()` before comparing against `in_length`. Additionally, harden `EnsureRemaining()` to explicitly reject `in_offset > input_file_->Length()` before computing `remaining`, rather than relying on the underflow-prone subtraction.

### Proof of Concept
A minimal reproduction (as a `src/test/shell/bazel` or C++ unit test against `third_party/ijar/zip.cc`) would:
1. Construct a small in-memory buffer representing a ZIP file's tail containing a normal EOCD record immediately preceded by a Zip64 EOCD Locator and Zip64 EOCD record.
2. In the Zip64 EOCD record, set `central_dir_size` to a large value close to `UINT64_MAX` and `central_dir_offset` to a value chosen so `central_dir_offset + central_dir_size` overflows `uint64_t` and wraps to a value `<= in_length`.
3. Call `FindZipCentralDirectory(bytes, in_length, &offset, &central_dir)` directly and assert it returns `true` with an `offset` that is actually `> in_length` (demonstrating the check is bypassed).
4. Feed the crafted buffer through `ZipExtractor::Create`/`InputZipFile::Open()` and observe a segfault or ASan-reported out-of-bounds read when `ProcessNext()` dereferences the corrupted cursor.

I was not able to execute this PoC (no sandbox/tooling access in this pass); the trace above is based purely on static code reading of `third_party/ijar/zip.cc` and `mapped_file_unix.cc`.
