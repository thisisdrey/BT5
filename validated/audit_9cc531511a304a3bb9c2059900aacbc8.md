### Title
Unchecked array length in `extractBytes32Array` causes out-of-bounds read / DoS in TVM precompiled contract input parsing - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
CVE-2016-5033 is a libdwarf bug where `print_exprloc_content` reads a length/count field from attacker-supplied data and then loops through subsequent bytes without validating that the declared length stays within the buffer bounds, producing an out-of-bounds read. The same bug class exists in java-tron's precompiled-contract input decoding: `extractBytes32Array` reads an attacker-controlled length word and then indexes into the `words` array that many times with no bounds check, unlike its sibling helper functions in the same file which do perform this check.

### Finding Description
`PrecompiledContracts.extractBytes32Array` decodes an ABI-style dynamic array of 32-byte words from precompile call data: [1](#0-0) 

```java
private static byte[][] extractBytes32Array(DataWord[] words, int offset) {
  int len = words[offset].intValueSafe();
  byte[][] bytes32Array = new byte[len][];
  for (int i = 0; i < len; i++) {
    bytes32Array[i] = words[offset + i + 1].getData();
  }
  return bytes32Array;
}
```

`len` is taken directly from attacker-controlled calldata (`words[offset].intValueSafe()`) with no validation against `words.length`. The subsequent loop reads `words[offset + i + 1]` for `i` up to `len - 1` without ever checking that `offset + i + 1 < words.length`, so a crafted call can make the loop index run past the end of the `words` array and throw an `ArrayIndexOutOfBoundsException`.

This is directly analogous to the sibling functions `extractBytesArray` and `extractSigArray` in the same file, which parse similar attacker-controlled length-prefixed arrays but explicitly guard against out-of-range offsets before indexing: [2](#0-1) 

```java
private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
  if (offset > words.length - 1) {
    return new byte[0][];
  }
  int len = words[offset].intValueSafe();
  ...
```

`extractBytes32Array` omits this bounds check entirely, which is the exact "read a length, then loop without validating bounds" pattern that caused CVE-2016-5033.

### Impact Explanation
`words` is derived from the raw `data` payload passed to a precompiled contract's `execute(byte[] data)` method, which is fully attacker-controlled via a smart contract call (e.g. a `STATICCALL`/`CALL` from a deployed TVM contract to one of the precompile addresses that use this helper). An out-of-range `offset`/`len` combination throws an unhandled `ArrayIndexOutOfBoundsException` deep inside precompile execution. Depending on how the calling precompile contract's exception handling wraps this call, this can surface as an uncaught runtime exception during transaction execution, causing a node processing crash or an execution path that diverges from other nodes that handle the exception differently, both of which are unacceptable in a consensus-critical VM component (node crash / potential chain-halt class impact).

### Likelihood Explanation
Reaching this code only requires deploying/calling a smart contract that invokes the specific precompiled contract using `extractBytes32Array` with crafted calldata (an out-of-range `offset` or an oversized `len` field), which is achievable by any unprivileged contract caller — no special privileges are required, only a transaction that triggers a call into this precompile.

### Recommendation
Add the same bounds validation used in `extractBytesArray`/`extractSigArray` to `extractBytes32Array`: verify `offset` is within `words.length`, validate `len` is non-negative and that `offset + len` does not exceed `words.length` before allocating `bytes32Array` and looping, returning an empty/failure result instead of throwing when the input is malformed.

### Proof of Concept
Note: the exact precompiled contract(s) that call `extractBytes32Array` could not be confirmed in this pass (only the definition and one other reference were located in `PrecompiledContracts.java`); a full PoC requires identifying the specific ABI encoding expected by that precompile's `execute` entry point.

Conceptually: craft calldata to the affected precompile such that the DataWord at the parsed `offset` decodes to a very large `len` (e.g., `Integer.MAX_VALUE` or a `len` such that `offset + len + 1 > words.length`), while providing only a short `data` array (few words). When `PrecompiledContracts` decodes calldata into `DataWord[] words` and invokes `extractBytes32Array(words, offset)`, the loop will attempt `words[offset + i + 1]` beyond the array bounds and throw `ArrayIndexOutOfBoundsException`, since no `offset > words.length - 1` guard (as present in `extractBytesArray`) exists for this function.
