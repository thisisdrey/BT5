DoS via Remote-IP-Keyed Pack-Objects Concurrency Limiter Bypass Through IP Fan-Out - (File: internal/gitaly/service/hook/pack_objects.go)

### Summary
Gitaly's `PackObjectsHook` concurrency limiter admits requests based only on how many concurrent `git-pack-objects` invocations exist for a *given* `RemoteIp` key, but never checks the aggregate resource cost (total number of concurrently running expensive `git-pack-objects` processes) across all keys. This mirrors the reported bug class exactly: the system validates only a per-actor quantity ("shares owned" / "requests from this one IP") instead of the actual capacity/cost that matters to the shared resource ("vault liquidity" / "total concurrent CPU/memory-heavy git processes"). An attacker who simply issues clones/fetches that appear to originate from many distinct IPs can obtain an unbounded number of concurrent, independently-quota'd `git-pack-objects` processes, exhausting Gitaly node CPU/memory despite each individual per-IP bucket staying within its configured limit.

### Finding Description
`packObjectsHook` derives the concurrency-limiting key purely from `req.GetRemoteIp()`: [1](#0-0) 

This value is passed straight into `s.packObjectsLimiter.Limit(ctx, limitkey, ...)`: [2](#0-1) 

The underlying `ConcurrencyLimiter` implementation only maintains independent semaphores *per key* (`limitsByKey map[string]*keyedConcurrencyLimiter`), each sized to the configured `MaxConcurrency`/`MaxPerRepo`. There is no global semaphore capping the sum of in-flight `git-pack-objects` invocations across all keys: [3](#0-2) [4](#0-3) 

The proto documentation itself confirms `remote_ip` is the concurrency-limiting key, and that it is attacker-influenced client-request metadata ("the original IP of the initiator of the fetch"): [5](#0-4) 

Because each unique `RemoteIp` value gets its own independently-sized concurrency bucket, a client that fans out clone/fetch requests across many distinct source IPs (trivially achievable with cloud egress addresses, proxy pools, or IPv6 address rotation) causes Gitaly to spin up as many concurrently-running `git-pack-objects` subprocesses as there are distinct IPs used — each of which is individually "compliant" with the per-key limit, but whose sum is entirely unbounded. This directly parallels the vault bug: per-actor validation (shares owned / requests-per-IP) is checked, but the aggregate demand against the shared, finite resource (vault liquidity / node CPU-memory capacity) is never checked, forcing the system into an emergency, costly response (forced position liquidation / process/resource exhaustion).

This gap is also implicitly acknowledged in Gitaly's own architecture documentation, which notes that admission control "treats every request as equally expensive" and does not yet factor in aggregate cost across the fleet of concurrent operations — this is precisely the missing "value vs count" check from the reported bug class: [6](#0-5) 

### Impact Explanation
`git-pack-objects` is one of the most CPU- and memory-intensive operations Gitaly performs (walking/compressing objects for a repository). Bypassing the per-key concurrency limiter by fanning out across IPs lets a single unprivileged client (via ordinary `git fetch`/`git clone` traffic routed with attacker-controlled apparent source IPs) trigger many simultaneous heavyweight pack-objects processes on one Gitaly node, exhausting CPU and memory and degrading or denying service for all other repositories/tenants hosted on that node — a direct DoS of an RPC handler's resource limits, matching the "DoS of a handler" acceptance criterion.

### Likelihood Explanation
The `remote_ip` field is populated from ordinary git-fetch/clone traffic observed by gitlab-shell/workhorse and forwarded to Gitaly as part of the standard fetch pipeline; an attacker only needs the ability to make concurrent fetch/clone requests appear to originate from distinct source addresses (e.g., via IP rotation, proxy pools, IPv6 subnets), a low-cost and commonly available capability, requiring no special privilege or compromise of Gitaly internals. This makes the likelihood at least moderate for any environment where per-IP address diversity is not otherwise constrained upstream (e.g. by network/edge rate limiting).

### Recommendation
Add a global/aggregate cap on the total number of concurrent `git-pack-objects` invocations (independent of the per-`RemoteIp` bucketing), so that per-key admission cannot be used to circumvent node-wide resource ceilings — analogous to requiring the vault to check total requested value against actual liquid capacity, not just the individual user's share balance. This could be implemented as an additional global semaphore wrapping `packObjectsLimiter`, or by having the concurrency limiter track/limit based on a cost-aware metric (e.g., estimated pack size or number of objects) as already outlined by the in-progress "cost-aware admission" work referenced in `doc/load-management-architecture.md`.

### Proof of Concept
1. Configure Gitaly with `[pack_objects_limiting]` `max_concurrency` (or `max_per_repo`) set to a small number, e.g. 2.
2. From a single client, issue many concurrent `git clone`/`git fetch` requests against the same repository, routing each connection so that gitlab-shell/workhorse records a distinct `remote_ip` per request (e.g., using different source addresses from a NAT pool, proxy chain, or IPv6 rotation).
3. Observe via the `gitaly_pack_objects_in_progress` Prometheus metric (labeled per auth type, not per key) that the number of concurrently running `git-pack-objects` processes on the node grows in proportion to the number of distinct IPs used, far exceeding the configured `max_concurrency`, since each IP obtains its own independent quota bucket as shown in the test harness's per-key limiting behavior: [7](#0-6) 

4. With enough distinct IPs, CPU/memory on the Gitaly node saturates, denying service to other RPCs/repositories on that node — confirming the DoS.

type ConcurrencyLimiter struct {
	// limit is the adaptive maximum number of concurrent calls to the limited function. This limit is
	// calculated adaptively from an outside calculator.
	limit *AdaptiveLimit
	// maxQueueLength is the maximum number of operations allowed to wait in a queued state.
	// This limit is global and applies before the concurrency limit. Subsequent incoming

	maxQueueLength int
	// maxQueueWait is a time duration of an operation allowed to wait in the queue.
	maxQueueWait time.Duration
	// SetWaitTimeoutContext is a function for setting up timeout context. If this is nill, context.WithTimeout is
	// used. This function is for internal testing purpose only.

// getConcurrencyLimit retrieves the concurrency limit for the given key. If no such limiter exists
// it will be lazily constructed.
func (c *ConcurrencyLimiter) getConcurrencyLimit(limitingKey string) *keyedConcurrencyLimiter {
	c.m.Lock()
	defer c.m.Unlock()

	if c.limitsByKey[limitingKey] == nil {
		// Set up the queue tokens in case a maximum queue length was requested. As the
		// queue tokens are kept during the whole lifetime of the concurrency-limited
		// function we add the concurrency tokens to the number of available token.
		var queueTokens semaphorer
		if c.maxQueueLength > 0 {
			queueTokens = c.createSemaphore(uint(c.currentLimit() + c.maxQueueLength))
		}

		c.limitsByKey[limitingKey] = &keyedConcurrencyLimiter{
			monitor:               c.monitor,
			maxQueueWait:          c.maxQueueWait,
			setWaitTimeoutContext: c.SetWaitTimeoutContext,
			concurrencyTokens:     c.createSemaphore(uint(c.currentLimit())),
			queueTokens:           queueTokens,
		}
	}

	c.limitsByKey[limitingKey].refcount++

	return c.limitsByKey[limitingKey]
}

The concurrency limiter today treats every request as equally expensive. In
practice, requests served from cache consume minimal resources (disk streaming)
while cache misses run full Git subprocess pipelines. Rather than feeding the
limiter a cost hint (which still consumes a limiter slot), cache-hit requests
skip the limiter entirely — keeping the concurrency limiter pure and ensuring
limits designed for expensive operations do not penalize cheap ones.

request that reaches it is treated as expensive.
