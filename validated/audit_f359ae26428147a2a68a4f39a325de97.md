## Title
Replay window bypass via unlocked decrypt gap in `ConnectionState.Decrypt`/`VerifyRelay` allows duplicate packet acceptance - (File: `connection_state.go`)

### Summary
`ConnectionState.Decrypt` (and its relay counterpart `VerifyRelay`) split the anti-replay bookkeeping into two separately-locked operations — `window.Check` and `window.Update` — with the actual AEAD decryption performed *outside* the lock, in between them. This is structurally the same root cause as the reported `mintFee`/`shareRatio` bug: a decision (accept/act on a packet) is derived from state (`window.Check`) that is *not yet updated* (`window.Update`) before the "value" is used (decryption/delivery), leaving a window in which the state-mutating step lags behind the read that gated the action.

### Finding Description
`ConnectionState.Decrypt` in `connection_state.go`: [1](#0-0) 

```
cs.decryptLock.Lock()
result := cs.window.Check(l, messageCounter)   // read-only test against replay window
cs.decryptLock.Unlock()
...
out, err = cs.dKey.DecryptDanger(...)          // expensive AEAD open, NOT holding decryptLock
...
cs.decryptLock.Lock()
result = cs.window.Update(l, messageCounter)   // state-mutating: marks counter as seen
cs.decryptLock.Unlock()
```

`Check` only tests whether `messageCounter` has already been marked in the sliding-window bitmap (`bits.go`); it does not mutate any state. `Update` is the only call that actually marks the counter as consumed: [2](#0-1) [3](#0-2) 

Because the lock is released between `Check` and `Update`, and the intervening `DecryptDanger` call is comparatively expensive, two goroutines that receive the *same* ciphertext (e.g. a replayed/duplicated UDP datagram, which any network path attacker can trivially produce since UDP has no delivery-uniqueness guarantee) at nearly the same time can both pass `Check` before either calls `Update`. Both then proceed to decrypt and deliver the packet to the tun device / firewall pipeline, i.e. the same message counter is accepted twice. This is exactly analogous to the reported bug: the amount to accept (packet processing) is computed/decided from a value (`window.Check`) that is stale relative to the update (`window.Update`) that should have gated it, and the "profit" (excess acceptance) grows with how long the gap between read and write lasts.

`VerifyRelay` (used by relay-forwarding nodes to authenticate frames before re-forwarding them) has the identical structure: [4](#0-3) 

Notably, the project's own test suite documents that this exact class of bug ("replay window not advanced/consulted atomically with the action it gates") has caused a real regression before, on the relay path: [5](#0-4) 

That test (`TestRelayReplayProtection`) only exercises the sequential case (replays arrive strictly after the original has been fully processed) — it does not exercise the concurrent race where two copies of the same counter are in flight simultaneously and both pass `Check` before either reaches `Update`. The unlocked gap between `Check` and `Update` in `Decrypt`/`VerifyRelay` is precisely the reachable, remote-triggerable structural flaw of the same "stale-check, late-update" class as the report.

### Impact Explanation
An attacker who can duplicate/replay a single captured ciphertext datagram to the target listener (a standard network-position capability, requiring no valid certificate) can cause the same encrypted packet to be decrypted and forwarded to the tun device / relay target twice (or more) instead of exactly once, if the duplicates race concurrently against multiple I/O routines processing the same `HostInfo`. This defeats the anti-replay guarantee the `Bits` sliding window is supposed to provide and can result in duplicate delivery of application traffic through the tunnel, or duplicate re-forwarding through a relay node — matching the "traffic decryption/forgery/replay" impact category for this scan.

### Likelihood Explanation
Exploitability depends on winning a race: the attacker's duplicate packet must arrive and be scheduled onto a different processing goroutine while the original's decrypt is still in flight (between the unlocked `Check` and the later `Update`). Nebula's design (`tun.routines`/multi-reader UDP listeners) makes concurrent processing of packets for the same `HostInfo` plausible, and `DecryptDanger` (AEAD open) is non-trivial work that widens the race window compared to the lock-protected bookkeeping calls. This is a genuine, network-triggerable race rather than a purely theoretical one, though it is probabilistic rather than deterministic, so likelihood is assessed as moderate.

### Recommendation
Hold `decryptLock` across the entire `Check` → `Decrypt` → `Update` sequence (or, more precisely, make the "reserve this counter" step atomic with the check), so that a second concurrent copy of the same counter cannot pass `Check` until the first copy has already committed its `Update`. Concretely: acquire `decryptLock` before `Check`, keep it held through `DecryptDanger`, and only release it after `Update` completes (or use a compare-and-set style single atomic window operation that both checks and marks in one critical section). Apply the same fix to `VerifyRelay`.

### Proof of Concept
Conceptual PoC (race, not guaranteed-deterministic without instrumentation):
1. Establish a tunnel between two nebula nodes so a `ConnectionState` exists with a live replay window.
2. Capture one legitimate data-plane (or relay) ciphertext frame with message counter `N`.
3. Re-inject two (or more) identical copies of that captured frame into the target's UDP listener at nearly the same instant, ideally when the target is configured with multiple reader routines (`listen.batch`/`tun.routines` > 1) so the duplicates can be scheduled onto different goroutines calling `readOutsidePackets` concurrently.
4. Observe whether both copies pass `cs.window.Check(l, N)` (both see "not yet seen") before either finishes `cs.window.Update(l, N)`, resulting in the tun device / relay target receiving the payload for counter `N` more than once.

This mirrors the referenced e2e test's intent, but targets the concurrent race rather than the sequential replay already covered by `TestRelayReplayProtection`: [6](#0-5)

func (cs *ConnectionState) VerifyRelay(l *slog.Logger, messageCounter uint64, packet []byte, nb []byte) error {
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()

	}

// Check returns true if i is within (or way out in front of) the window, and not a replay
func (b *Bits) Check(l *slog.Logger, i uint64) bool {
	// If i is the next number, return true.
	if i > b.current {
		return true
	}

	if b.strictlyWithinWindow(i) {
		return !b.get(i)
	}

	// Not within the window
	if l.Enabled(context.Background(), slog.LevelDebug) {
		l.Debug("rejected a packet (top)", "current", b.current, "incoming", i)
	}
	return false
}

func (b *Bits) Update(l *slog.Logger, i uint64) bool {
	// Fast path: i is the next expected counter. Split out so the function
	// stays small and avoids paying for the slow paths' slog argument-build
	// stack frame on every call. The bit read/test/write is inlined to
	// touch the backing word once.
	if i == b.current+1 {
		pos := i & b.lengthMask
		word := pos >> 6
		mask := uint64(1) << (pos & 63)
		w := b.bits[word]
		if i > b.length && w&mask == 0 {
			b.lostCounter.Inc(1)
		}
		b.bits[word] = w | mask
		b.current = i
		return true
	}
	return b.updateSlow(l, i)
}
