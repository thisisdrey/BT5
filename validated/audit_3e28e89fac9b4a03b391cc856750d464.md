Audit Report

## Title
`ItemAttributesApprovalsOf` is not cleared on NFT ownership transfer, allowing a stale delegate approved by the previous owner to keep mutating the item's attributes after transfer - ([File: substrate/frame/nfts/src/features/transfer.rs])

## Summary
`pallet-nfts` maintains two independent per-item approval structures: `Item::approvals` (transfer approvals) and `ItemAttributesApprovalsOf` (delegates allowed to set attributes in the `Account(delegate)` namespace). `do_transfer()` explicitly clears the first via `details.approvals.clear()` but never touches the second, so an attribute delegate approved by the *previous* owner keeps write access to the item's attributes after the item is transferred to a new, non-consenting owner.

## Finding Description
`do_transfer()` in `substrate/frame/nfts/src/features/transfer.rs` updates `Account` ownership storage and clears `details.approvals` with an explicit comment about preventing a pre-approve attack, but it performs no operation on `ItemAttributesApprovalsOf`: [1](#0-0) 

`ItemAttributesApprovalsOf` is populated by `do_approve_item_attributes`, which only validates that the *current* owner at approval time is `check_origin`, with no binding of the approval to that specific owner instance: [2](#0-1) 

The permission check for the `Account(delegate)` namespace, used by both `set_attribute` and `clear_attribute` via `is_valid_namespace`, relies purely on membership in this stale map plus caller identity — it never re-validates against the item's current owner: [3](#0-2) 

The only code path that removes entries from `ItemAttributesApprovalsOf` for a delegate is `do_cancel_item_attributes_approval`, which can only be invoked by the item's *current* owner (`check_origin == details.owner`): [4](#0-3) 

Consequently, once ownership transfers from A to B, `delegate` (approved by A) remains in `ItemAttributesApprovalsOf` and is never automatically revoked; B has no visibility into this dangling grant and cannot even discover it without off-chain tooling, only cancel it manually via `cancel_item_attributes_approval`.

## Impact Explanation
The stale delegate can continue calling `set_attribute` with `AttributeNamespace::Account(delegate)` to write or update metadata on the item after it has changed hands, without the new owner's consent — this corrupts the intended `owner`-scoped trust boundary of the `Account(delegate)` attribute namespace, since the map is keyed only by `(collection, item)` and never re-bound to `details.owner` after a transfer. It also occupies a slot in the `MaxAttributesApprovals`-bounded set indefinitely unless the new owner proactively discovers and cancels it. This matches the "runtime bugs that compromise intended behavior" / unauthorized-execution class of impact: an account retains write-execution rights over an item's state after the controlling owner changes, without the new owner's authorization. It does not, however, escalate to fund theft, double settlement, or origin-widening on privileged calls — it is confined to attribute metadata within the pallet's own designed (if flawed) namespace.

## Likelihood Explanation
Fully reachable by ordinary, unprivileged users through public extrinsics (`approve_item_attributes`, `transfer`, `set_attribute`) with no special permissions required. It requires only that (1) an owner previously approved an attribute delegate and (2) the item is later transferred without the old or new owner explicitly cancelling that approval — both are realistic, unenforced preconditions in normal NFT trading/marketplace flows.

## Recommendation
Clear `ItemAttributesApprovalsOf` for the item inside `do_transfer()` — mirroring the `details.approvals.clear()` treatment — including draining and unreserving any deposits tied to attributes set under the removed delegate approvals (as already done in `do_cancel_item_attributes_approval`). Alternatively, bind the approval record to the owner at approval time (e.g., store `(delegate, owner_at_approval)`) and have `is_valid_namespace` additionally check that `details.owner == owner_at_approval`, so the approval is implicitly invalidated when `details.owner` changes.

## Proof of Concept
1. Owner A mints item `#42` in collection `0`, calls `Nfts::approve_item_attributes(A, 0, 42, delegate)` — `ItemAttributesApprovalsOf(0, 42) = {delegate}`.
2. A transfers `#42` to B via `Nfts::transfer(0, 42, B)`. `do_transfer` clears `Item::approvals` but `ItemAttributesApprovalsOf(0, 42)` remains `{delegate}`.
3. `delegate` calls `Nfts::set_attribute(0, Some(42), AttributeNamespace::Account(delegate), key, value)`. `is_valid_namespace` returns true because `approvals.contains(&origin)` still holds, so the write succeeds against B's item without B's consent, verifiable via a unit test in `substrate/frame/nfts/src/tests.rs` asserting `Attribute::<Test>::get((0, Some(42), AttributeNamespace::Account(delegate), key))` is set after the transfer.

		ensure!(

			Error::<T, I>::MethodDisabled
		);

		let details = Item::<T, I>::get(&collection, &item).ok_or(Error::<T, I>::UnknownItem)?;
		ensure!(check_origin == details.owner, Error::<T, I>::NoPermission);

		ItemAttributesApprovalsOf::<T, I>::try_mutate(collection, item, |approvals| {
			approvals
				.try_insert(delegate.clone())
				.map_err(|_| Error::<T, I>::ReachedApprovalLimit)?;

			Self::deposit_event(Event::ItemAttributesApprovalAdded { collection, item, delegate });
			Ok(())
		})
	}

	pub(crate) fn do_cancel_item_attributes_approval(
		check_origin: T::AccountId,
		collection: T::CollectionId,
		item: T::ItemId,
		delegate: T::AccountId,
		witness: CancelAttributesApprovalWitness,
	) -> DispatchResult {
		ensure!(
			Self::is_pallet_feature_enabled(PalletFeature::Attributes),
			Error::<T, I>::MethodDisabled
		);

		let details = Item::<T, I>::get(&collection, &item).ok_or(Error::<T, I>::UnknownItem)?;
		ensure!(check_origin == details.owner, Error::<T, I>::NoPermission);

		ItemAttributesApprovalsOf::<T, I>::try_mutate(collection, item, |approvals| {
			approvals.remove(&delegate);

			let mut attributes: u32 = 0;
			let mut deposited: DepositBalanceOf<T, I> = Zero::zero();
			for (_, (_, deposit)) in Attribute::<T, I>::drain_prefix((
				&collection,
				Some(item),
				AttributeNamespace::Account(delegate.clone()),
			)) {
				attributes.saturating_inc();
				deposited = deposited.saturating_add(deposit.amount);
			}
			ensure!(attributes <= witness.account_attributes, Error::<T, I>::BadWitness);

			if !deposited.is_zero() {
				T::Currency::unreserve(&delegate, deposited);
			}

			Self::deposit_event(Event::ItemAttributesApprovalRemoved {
				collection,
				item,
				delegate,
			});
			Ok(())
		})
	}
