## Finding: Griefing/precision-loss vector in vault `accrue()` causes permanent loss of supplier (liquidity) yield

### Title
Shared `last-update` checkpoint in vault `accrue()` discards unaccrued liquidity-index precision residue, permanently reducing supplier yield - (File: `mainnet/contracts/vault/v0-vault-usdc.clar` and equivalent vault-* contracts)

### Summary
Each Zest vault (`v0-vault-usdc.clar`, `v0-vault-sbtc.clar`, `v0-vault-stx.clar`, `v0-vault-usdh.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`) tracks two independent accumulators — the debt index `index` and the liquidity/supply index `lindex` — but advances a *single shared* timestamp `last-update` whenever **either** accumulator changes. [1](#0-0)  Because the debt index almost always changes (its scaling precision `INDEX-PRECISION` is `1e12`, so `mul-div-down` on the borrow-rate side essentially never rounds to zero) while the liquidity index update is subject to a separate multiplicative rounding (`calc-liquidity-rate`, chained `mul-bps-down` truncations), any time window in which `lindex` doesn't change but `index` does causes `last-update` to be advanced anyway. That silently discards the unaccrued time delta for the liquidity index calculation, exactly mirroring the reported `MultiRewards.updateReward` precision-loss/griefing class where `lastUpdateTime` advances even though the associated stored accumulator did not, permanently losing the yield for that interval.

### Finding Description
`accrue()` computes both the next debt index and next liquidity index from the same `time-delta = stacks-block-time - last-update`: [2](#0-1) 

Both `next-index` and `next-liquidity-index` use `calc-multiplier-delta`, which truncates via `mul-div-down`/`mul-div-up`: [3](#0-2) 

`accrue()` then updates `index` and `lindex` **independently** (only if each individually changed), but updates the single shared `last-update` timestamp if **either** one changed: [1](#0-0) 

Because `calc-liquidity-rate` applies utilization and reserve-factor discounts on top of the borrow rate (`calc-liquidity-rate` = `borrow_rate * util / BPS * (1-reserve_factor) / BPS`) it truncates to zero far more readily than the plain borrow-rate multiplier used for the debt index: [4](#0-3) 

Whenever a call to `accrue()` (which is public/permissionless and is also invoked as part of every `system-borrow`/`system-repay`/deposit/redeem operation, e.g. via `try! (accrue))` in `system-borrow`) lands in a window where the debt-index multiplier rounds to a nonzero delta but the liquidity-index multiplier rounds down to zero, `last-update` is advanced to the current block time even though `lindex` did not move. The unaccrued liquidity time for that window is discarded forever — the next `accrue()` call starts its `time-delta` from the new `last-update`, so the lost interval can never be recovered, unlike a design that would only reset the checkpoint once both accumulators have advanced (or that stores/reapplies the truncated residual).

An attacker can amplify this loss by repeatedly invoking `accrue()` (directly, since it is `define-public` with no caller restriction) with a small block cadence, keeping `time-delta` per call small so the liquidity-rate side is more likely to round to zero relative to the borrow-rate side, systematically suppressing `lindex` growth over an extended period while `index` (and thus interest actually charged to borrowers) keeps accruing normally.

### Impact Explanation
This causes permanent, unrecoverable loss of unclaimed yield owed to liquidity suppliers (zft holders), since `lindex` underlies the vault's `total-assets-preview`/conversion-rate logic that determines how much underlying asset each zft share is redeemable for. Borrowers are still charged interest (debt index keeps advancing), but the corresponding supplier-side yield accrual is dropped whenever it falls below the liquidity-index's coarser truncation threshold. This matches the in-scope **High** impact category: permanent freezing/loss of unclaimed yield.

### Likelihood Explanation
Medium: this occurs naturally over time whenever utilization/reserve-factor combinations make the liquidity-rate multiplier round to zero within the elapsed window while the debt-rate multiplier does not — a common state at low-to-moderate utilization. It can also be actively amplified by any ordinary principal since `accrue()` is a permissionless public function that can be called at high frequency at no cost beyond gas.

### Recommendation
Decouple the `last-update` checkpoint per accumulator (track separate `last-update-index` and `last-update-lindex` timestamps), or only advance the shared checkpoint once both `index` and `lindex` have progressed, or store and re-apply the truncated remainder for each accumulator on the next `accrue()` call (as recommended in the original report) so residual sub-precision liquidity accrual is never permanently discarded.

### Proof of Concept
Conceptually mirroring the referenced PoC: repeatedly call `accrue()` (or any market operation that triggers it) at a cadence `dt` chosen so that `mul-div-down(liquidity_rate, dt*INDEX-PRECISION, SECONDS-PER-YEAR-BPS) == 0` while `mul-div-down(borrow_rate, dt*INDEX-PRECISION, SECONDS-PER-YEAR-BPS) > 0`. Each such call leaves `lindex` unchanged but still sets `last-update` to the current block time [5](#0-4) , so the un-accrued liquidity-yield interval for that call is permanently lost and cannot be recovered on subsequent calls, while borrowers continue to be charged interest that accrues to `index`.
