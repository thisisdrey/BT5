### Title
Permissionless `lending_pool_emissions_deposit` Allows MEV Sniping of Same-Bank Reward Distributions - ([File: programs/marginfi/src/instructions/marginfi_group/configure_bank.rs])

### Summary
The `lending_pool_emissions_deposit` instruction lets anyone permissionlessly inject reward tokens into a bank's liquidity vault, instantly raising `asset_share_value` proportionally to whoever holds `total_asset_shares` at that exact moment. [1](#0-0)  Because deposits and withdrawals are otherwise unrestricted and instantaneous, an attacker can deposit a large sum immediately before this reward injection and withdraw immediately after, capturing a disproportionate share of the reward without having provided liquidity for any meaningful duration — the same "flash-stake, snipe reward, flash-unstake" pattern described in the `VAIVault` report.

### Finding Description
`lending_pool_emissions_deposit` computes the post-reward `asset_share_value` purely from the ratio `(total_assets + amount) / total_asset_shares`, where `total_asset_shares` is whatever it happens to be at the instant the instruction executes: [2](#0-1) 

There is no time-weighting, vesting, or minimum holding-period requirement tying a depositor's share of the reward to how long they actually held their position. `lending_account_deposit` and `lending_account_withdraw` are permissionless, unrestricted operations available to any unprivileged user, requiring only interest accrual and a (trivially passing, since it's the same collateral) health check: [3](#0-2) [4](#0-3) 

This mirrors the root cause in the `VAIVault` report: a reward-injection event whose accounting benefit is captured by whoever holds shares "at the moment," combined with unrestricted deposit/withdraw, lets an attacker capture rewards intended for genuine long-term depositors by only being present for the instant of distribution.

Unlike the per-position `emissions_rate` system (which accrues rewards over elapsed time per `Balance.last_update`, and is not vulnerable to instant sniping) [5](#0-4) , and unlike the Juplend/Kamino integrations where reward realization is tied to externally-managed, slower-moving exchange rates, the `lending_pool_emissions_deposit` path is a single-shot, atomic, pro-rata distribution based solely on instantaneous share balance.

### Impact Explanation
This results in a direct transfer of value (theft) from legitimate long-term depositors of a bank to an opportunistic depositor who has no genuine economic exposure to the bank beyond the transaction(s) needed to deposit-then-withdraw around the reward injection. If reward amounts are large relative to normal bank TVL (e.g. an announced incentive campaign), the attacker can extract a large fraction of intended incentives, diluting rewards for real depositors — a concrete unauthorized value transfer within the core deposit/accounting path.

### Likelihood Explanation
Likelihood is moderate: the attack requires the attacker to time their deposit/withdraw around a `lending_pool_emissions_deposit` call. Since it's a permissionless, non-privileged instruction usable by anyone (community incentive funders, protocol partners, etc.), and Solana transactions can be observed/sequenced by leaders/searchers (Jito bundles), an attacker monitoring for known reward-distribution events (which are often publicly announced in advance, e.g. incentive campaigns) can reliably front-run them. No cooldown, lockup, or time-weighting mechanism currently prevents this.

### Recommendation
Consider one or more of the following:
- Require a minimum holding period before a deposit becomes eligible for `lending_pool_emissions_deposit` benefit (e.g., snapshot eligible shares prior to the reward transaction, or exclude balances created within the same slot/transaction).
- Convert `lending_pool_emissions_deposit` into a time-weighted/streamed distribution (similar to the existing `emissions_rate` mechanism) rather than an instantaneous share-value bump.
- Restrict who can call `lending_pool_emissions_deposit` (e.g., admin-only or admin-scheduled) so that timing cannot be gamed by unprivileged actors monitoring for these events, or add a same-block/same-transaction guard preventing deposit-then-withdraw sandwiching of the reward instruction.

### Proof of Concept
1. Bank has 1,000 USDC in total deposits from real depositors (`total_asset_shares` corresponding to 1,000 USDC of value).
2. A protocol/community member funds an announced incentive: they prepare a `lending_pool_emissions_deposit` transaction for 100 USDC of rewards.
3. Attacker observes the pending transaction (or knows the scheduled reward time) and, in a preceding transaction/slot, calls `lending_account_deposit` with 9,000 USDC (fresh, uncommitted capital).
4. The reward transaction executes: `asset_share_value` increases by `100 / (1,000 + 9,000) = 1%`; attacker's 9,000 USDC deposit share is credited a $90 portion of the $100 reward pool while genuine depositors of the original 1,000 USDC only get $10 combined — see the reward math implemented at [6](#0-5) .
5. Attacker immediately calls `lending_account_withdraw` (`withdraw_all: true`) to exit with 9,090 USDC, having captured 90% of the reward pool despite contributing 0 economic risk-time to the bank.

```rust
/// Permissionlessly deposit same-mint emissions directly into the bank liquidity vault,
/// increasing depositor value through asset share value.
pub fn lending_pool_emissions_deposit(
    ctx: Context<LendingPoolEmissionsDeposit>,
    amount: u64,
) -> MarginfiResult {
    if amount == 0 {
        return Ok(());
    }

    let clock = Clock::get()?;
    let mut bank = ctx.accounts.bank.load_mut()?;
    let group = ctx.accounts.group.load()?;

    utils::validate_bank_state(&bank, utils::InstructionKind::FailsIfPausedOrReduceState)?;

    // Reject mints with non-zero transfer fees or active transfer hooks.
    let mint_ai = ctx.accounts.mint.to_account_info();
    check!(
        !utils::nonzero_fee(mint_ai.clone(), clock.epoch)?,
        MarginfiError::InvalidTransfer
    );
    check!(
        !utils::has_transfer_hook(mint_ai)?,
        MarginfiError::InvalidTransfer
    );

    let total_asset_shares = I80F48::from(bank.total_asset_shares);
    check!(
        total_asset_shares > I80F48::ZERO,
        MarginfiError::EmissionsUpdateError
    );

    bank.accrue_interest(
        clock.unix_timestamp,
        &group,
        #[cfg(not(feature = "client"))]
        ctx.accounts.bank.key(),
    )?;

    transfer_checked(
        CpiContext::new(
            ctx.accounts.token_program.key(),
            TransferChecked {
                from: ctx.accounts.emissions_funding_account.to_account_info(),
                to: ctx.accounts.liquidity_vault.to_account_info(),
                authority: ctx.accounts.depositor.to_account_info(),
                mint: ctx.accounts.mint.to_account_info(),
            },
        ),
        amount,
        ctx.accounts.mint.decimals,
    )?;

    let total_assets = bank.get_asset_amount(total_asset_shares)?;
    let updated_total_assets = total_assets
        .checked_add(I80F48::from_num(amount))
        .ok_or_else(math_error!())?;

    bank.asset_share_value = updated_total_assets
        .checked_div(total_asset_shares)
        .ok_or_else(math_error!())?
        .into();
```
