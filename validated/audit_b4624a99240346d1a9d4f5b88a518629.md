### Title
Stale `PromiseYieldReceipt`/`PromiseYieldStatus` state survives `DeleteAccount`, letting a resumed yield execute privileged actions against a re-created account under the same `AccountId` - ([File: core/store/src/utils/mod.rs])

### Summary
`remove_account` (called by `action_delete_account`) deletes `Account`, `ContractCode`, access keys/gas keys and `ContractData`, but never removes `TrieKey::PromiseYieldReceipt`, `PromiseYieldStatus`, `YieldIdToDataId` or `DataIdToYieldId` entries for the deleted account. Because `PromiseResume`/timeout processing looks these up purely by the `AccountId` string, a `PromiseYieldReceipt` created before deletion can be resumed later and its queued actions executed with full permission against whatever account currently occupies that `AccountId`, even a completely different owner.

### Finding Description
`promise_yield_create` builds a `PromiseYield` receipt with `predecessor_id == receiver_id == A` and queues actions (via the returned promise index, e.g. `promise_batch_action_add_key_with_full_access`) that will run when the yield resumes. [1](#0-0) 
The runtime stores this pending receipt keyed only by `(receiver_id, data_id)`: [2](#0-1) 

`action_delete_account` refunds the balance and calls `remove_account`, which removes `Account`, `ContractCode`, access/gas keys and `ContractData` — but has no logic to scan/remove `PromiseYieldReceipt`, `PromiseYieldStatus`, `YieldIdToDataId`, or `DataIdToYieldId` rows for the account: [3](#0-2) [4](#0-3) 
Note the `DeleteAccountWithLargeState` guard checks `account.storage_usage()`, which is not incremented by promise-yield bookkeeping, so a lingering yield entry doesn't block deletion.

After deletion, the `AccountId` string `A` becomes available for `CreateAccount` (subject to normal naming/parent rules), and a third party (or the same actor acting as the immediate parent domain) can recreate an account with that exact name for a different beneficiary.

When the yield resumes — either via an explicit `PromiseResume` or via the timeout path — the runtime fetches the receipt purely by account-id string match, with no check that the account is "the same" account that created it: [5](#0-4) [6](#0-5) 

The recovered `yield_receipt` is then executed via `apply_action_receipt`, which initializes `actor_id = receipt.predecessor_id().clone()` — and since this is a self-targeted yield, `predecessor_id == receiver_id == account_id` by construction: [7](#0-6) 
`check_actor_permissions` for privileged actions (e.g. `AddKey`, `DeleteKey`, `DeployContract`, `DeleteAccount`) is satisfied purely by `actor_id == account_id` string equality — it never verifies that the account is the same "generation" that originally authorized the queued action: [8](#0-7) 

Because the trie has no per-account "generation"/owner identity beyond the raw `AccountId` string, and the promise-yield bookkeeping is never purged on deletion, the queued privileged actions execute successfully against the new tenant of the name.

### Impact Explanation
This is an authorization escalation / account-hijack primitive: an attacker who controls an account (or controls the parent used to recreate a specific sub-account name) can plant a self-targeted `promise_yield_create` carrying privileged actions (e.g. `AddKey` with a full-access key, `DeleteKey`, `DeployContract`, or even `DeleteAccount`), delete that account, and have those actions replay — with full authorization — against whoever legitimately re-obtains that account name later (e.g. via a subaccount-recycling service/dApp). This matches the "authorization escalation across accounts or promises" bounty category and can lead to theft of funds/control of the recreated account.

### Likelihood Explanation
Preconditions: the attacker must be able to (a) call `promise_yield_create` self-targeted with attacker-controlled queued actions, (b) delete that account, and (c) arrange for the exact same `AccountId` string to be recreated later for a victim. Condition (c) is the main constraint — top-level account recreation is restricted to the registrar account, but sub-account name reuse under a shared/parent-controlled naming scheme (common in NEAR dApps that create/delete per-user sub-accounts) is realistically attacker-influenceable. All steps are reachable purely through ordinary signed transactions and standard host functions (`promise_yield_create`, `promise_batch_action_add_key_with_full_access`, `DeleteAccount`, `CreateAccount`) with no validator/node privileges required, no existing check blocks it, and it is fully repeatable.

### Recommendation
When removing an account in `remove_account` (core/store/src/utils/mod.rs), also scan and remove all `PromiseYieldReceipt`, `PromiseYieldStatus`, `YieldIdToDataId`, and `DataIdToYieldId` entries keyed by that `account_id` (and, ideally, drop/neutralize any outstanding `PromiseYieldTimeout` queue entries referencing it, or make `resolve_promise_yield_timeouts`/the `PromiseResume` handler validate that the receiving account is unchanged since the yield was created, e.g. via a per-account generation counter or by hashing account creation metadata into the yield key).

### Proof of Concept
Integration test (test-loop, modeled on `test-loop-tests/src/tests/yield_timeouts.rs`):
1. Deploy a contract to sub-account `sub.parent.near` (created by `parent.near`), granting it a full-access key controlled by the attacker.
2. From `sub.parent.near`, call a method that invokes `promise_yield_create` (self-targeted: predecessor=receiver=`sub.parent.near`) and, before dispatching, appends `AddKey(attacker_key_2, full_access)` to the same promise index.
3. From `sub.parent.near`, send `DeleteAccount { beneficiary_id: sub.parent.near }` (self-delete), while the yield is still pending; assert the `PromiseYieldReceipt`/`PromiseYieldStatus` entries still exist in state (via `get_yield_data_ids_in_state`, as in `test-loop-tests/src/tests/yield_timeouts.rs:122-151`).
4. From `parent.near`, send `CreateAccount` for `sub.parent.near` again with a *victim's* access key (simulating account-name reuse), and fund it.
5. Advance blocks until `resolve_promise_yield_timeouts` fires the timeout resume (or explicitly call `promise_yield_resume` with the known `data_id`).
6. Assert that `attacker_key_2` now exists as a full-access key on the recreated `sub.parent.near` account, despite never having been authorized by the victim — confirming the authorization bypass.

        VersionedReceiptEnum::PromiseYield(action_receipt) => {
            assert!(action_receipt.input_data_ids().len() == 1);
            let key = TrieKey::PromiseYieldReceipt {
                receiver_id: receipt.receiver_id().clone(),
                data_id: action_receipt.input_data_ids()[0],
            };
            set(state_update, key, receipt);
        }
        _ => unreachable!("Expected PromiseYield receipt"),
    }

/// Removes account, code and all access keys and gas keys associated to it.
pub fn remove_account(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
) -> Result<RemoveAccountResult, StorageError> {
    state_update.remove(TrieKey::Account { account_id: account_id.clone() });
    state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });

    let mut gas_key_nonce_count: usize = 0;
    let mut gas_key_nonce_total_key_bytes: usize = 0;

    // Removing access keys and gas key nonces
    let lock = state_update.trie().lock_for_iter();
    let mut keys_to_remove: Vec<TrieKey> = Vec::new();
    for raw_key in state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_access_keys(account_id), &lock)?
    {
        let raw_key = raw_key?;
        let key_handle = trie_key_parsers::parse_key_handle_from_access_key_key(
            &raw_key, account_id,
        )
        .map_err(|_e| {
            StorageError::StorageInconsistentState(
                "Can't parse key handle from raw key for AccessKey".to_string(),
            )
        })?;
        let nonce_index =
            trie_key_parsers::parse_nonce_index_from_gas_key_key(&raw_key, account_id, &key_handle)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse nonce index from raw key for AccessKey".to_string(),
                    )
                })?;
        if let Some(index) = nonce_index {
            gas_key_nonce_count += 1;
            gas_key_nonce_total_key_bytes += raw_key.len();
            keys_to_remove.push(TrieKey::gas_key_nonce(
                account_id.clone(),
                key_handle.clone(),
                index,
            ));
        } else {
            keys_to_remove.push(TrieKey::access_key(account_id.clone(), key_handle.clone()));
        }
    }
    drop(lock);

    for trie_key in keys_to_remove {
        state_update.remove(trie_key);
    }

    // Removing contract data
    let lock = state_update.trie().lock_for_iter();
    let data_keys = state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_contract_data(account_id, &[]), &lock)?
        .map(|raw_key| {
            trie_key_parsers::parse_data_key_from_contract_data_key(&raw_key?, account_id)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse data key from raw key for ContractData".to_string(),
                    )
                })
                .map(Vec::from)
        })
        .collect::<Result<Vec<_>, _>>()?;
    drop(lock);

    for key in data_keys {
        state_update.remove(TrieKey::ContractData { account_id: account_id.clone(), key });
    }
    Ok(RemoveAccountResult { gas_key_nonce_count, gas_key_nonce_total_key_bytes })
}
