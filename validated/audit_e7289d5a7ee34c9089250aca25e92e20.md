### Title
Uninitialized `accountIndexOf` defaults to 0 instead of `INITIAL_INDEX` when token index equals `INITIAL_INDEX`, crediting a full-balance reward - ([File: contracts/RewardsDistributor.sol](contracts/RewardsDistributor.sol))

### Summary
The RewardsDistributor's reward-accounting fallback in `_calculateTokenDelta` only corrects an uninitialized per-account index (`accountIndexOf == 0`) when the global token index is *strictly greater* than `INITIAL_INDEX` (1e18). When a reward speed is first set, `tokenStates[token].index` is initialized to exactly `INITIAL_INDEX`, so during that window the account index is treated as `0`, the delta index becomes `1e18`, and `_tokensDelta` equals the account's entire token balance. Any unprivileged user can harvest rewards equal to their deposit/debt token balance via the public `claimRewards` or `updateBeforeMintOrBurn` entry points.

### Finding Description
In `contracts/RewardsDistributor.sol`:

- `_updateTokenSpeed` initializes a new token with `tokenStates[token_] = TokenState({index: INITIAL_INDEX, timestamp: block.timestamp.toUint32()})` (lines ~296-299).
- `_calculateTokenDelta` reads `accountIndexOf[token_][account_]`; for a first-time account this is `0`. The correction `if (_accountIndex == 0 && _tokenIndex > INITIAL_INDEX) { _accountIndex = INITIAL_INDEX; }` (lines ~225-227) uses a strict `>` comparison.
- When `_tokenIndex == INITIAL_INDEX` (freshly enabled token, before `_updateTokenIndex` has accrued any delta), `_accountIndex` remains `0`, so `_deltaIndex = 1e18` and `_tokensDelta = token_.balanceOf(account_).wadMul(1e18) = balanceOf(account_)`.
- `_updateTokensAccruedOf` then sets `tokensAccruedOf[account_] += balanceOf(account_)`, and the public `claimRewards(address[], IERC20[])` path calls `_transferRewardIfEnoughTokens`, which transfers `rewardToken` to the account if the distributor holds sufficient balance.

Entry points reachable by any EOA: `claimRewards(account_)`, `claimRewards(account_, tokens_)`, `claimRewards(accounts_, tokens_)`, and `updateBeforeMintOrBurn(token_, account_)` (all public/external, guarded only by `nonReentrant` where present). The attacker only needs a nonzero `DepositToken`/`DebtToken` balance, obtainable through normal public deposit/issue flows.

### Impact Explanation
Theft of unclaimed yield / direct theft of protocol-held reward tokens. An account with balance `B` in a reward-bearing token is credited `B` reward units while never having accrued any time-based reward. By depositing a large amount of collateral (or via Operator.execute batched flows) the attacker can mint `tokensAccruedOf` up to the distributor's entire `rewardToken` balance and withdraw it through `claimRewards`, draining rewards owed to legitimate users.

### Likelihood Explanation
The window is bounded by the token index being exactly `INITIAL_INDEX`: it exists from the `updateTokenSpeed`/`syncTokenSpeed` transaction that initializes `tokenStates` until the first index update after `block.timestamp` advances with `speed > 0`. An attacker monitoring the mempool can back-run the governor/keeper speed-setting transaction in the same block (`_deltaTimestamps == 0` keeps the index pinned at `INITIAL_INDEX`), making exploitation deterministic. No privileged role, oracle manipulation, or external dependency is required. Confidence in arithmetic: `wadMul(1e18)` returns the balance itself, so the credited amount is `balanceOf(account_)` in reward-token units, subject to the distributor holding enough `rewardToken` for `_transferRewardIfEnoughTokens` to pay out.

### Recommendation
Change the fallback condition to `_accountIndex == 0 && _tokenIndex >= INITIAL_INDEX`, or initialize `accountIndexOf[token_][account_]` to the current global index (`tokenStates[token_].index`) rather than `INITIAL_INDEX` on first touch, so an uninitialized account can never realize a positive delta when the global index has not yet grown.

### Proof of Concept
```solidity
// Foundry fork-style test sketch (contracts/RewardsDistributor.sol)
// Setup: pool registered, depositToken added, rewardToken funded into RewardsDistributor.

// 1. Governor enables rewards for the deposit token.
vm.prank(governor);
distributor.updateTokenSpeed(depositToken, speed); // tokenStates.index = 1e18

// 2. Same block: attacker holds a depositToken balance.
//    (deposit via DepositToken.deposit or VesperGateway.deposit beforehand)
uint256 bal = depositToken.balanceOf(attacker);
assertGt(bal, 0);

// 3. Attacker claims immediately while index == INITIAL_INDEX.
IERC20[] memory toks = new IERC20[](1);
toks[0] = IERC20(address(depositToken));
vm.prank(attacker);
distributor.claimRewards(attacker, toks);

// Expected buggy result:
// _deltaIndex = 1e18 - 0 = 1e18  ->  tokensDelta = bal * 1e18 / 1e18 = bal
assertEq(rewardToken.balanceOf(attacker), bal); // stole bal worth of rewards
```
