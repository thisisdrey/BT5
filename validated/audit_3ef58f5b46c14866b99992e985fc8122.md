### Title
Missing `accountIndexOf` initialization lets a pre-existing holder instantly accrue rewards equal to their full balance when `tokenStates.index == INITIAL_INDEX` - (File: contracts/RewardsDistributor.sol)

### Summary
`RewardsDistributor._calculateTokenDelta` treats a missing account index (stored default `0`) as "new user" only when the token index is strictly greater than `INITIAL_INDEX`. When the token index equals `INITIAL_INDEX` exactly — the state right after a token is added via `updateTokenSpeed`/`syncTokenSpeed` and before any time has elapsed — an account whose `accountIndexOf` is still `0` (because it held a balance before the token was registered) is assigned `_deltaIndex = INITIAL_INDEX - 0 = 1e18`, accruing `balance * 1` reward tokens with zero elapsed time.

### Finding Description
In `_calculateTokenDelta` (`contracts/RewardsDistributor.sol:217-231`):

```solidity
_tokenIndex = _tokenState.index;
uint256 _accountIndex = accountIndexOf[token_][account_];

if (_accountIndex == 0 && _tokenIndex > INITIAL_INDEX) {
    _accountIndex = INITIAL_INDEX;
}

uint256 _deltaIndex = _tokenIndex - _accountIndex;
_tokensDelta = token_.balanceOf(account_).wadMul(_deltaIndex);
```

The fallback that normalizes an unset (zero) account index to `INITIAL_INDEX` only fires when `_tokenIndex > INITIAL_INDEX`. `tokenStates[token_]` is initialized to exactly `INITIAL_INDEX` when a speed is first set (`_updateTokenSpeed`, line 298). If `_updateTokensAccruedOf` runs while the index is still `INITIAL_INDEX` for an account with `accountIndexOf == 0` and a nonzero token balance, then:

- `_deltaIndex = 1e18 - 0 = 1e18`
- `_tokensDelta = balanceOf(account).wadMul(1e18) = balanceOf(account)`

`updateBeforeMintOrBurn` and `updateBeforeTransfer` are gated only by `tokenStates[token_].index > 0` (lines 176, 187) and `updateBeforeMintOrBurn` is explicitly callable by anyone. Accounts that obtained `DepositToken`/`DebtToken` balances *before* the token was registered (hooks no-op while `index == 0`, so `accountIndexOf` stays `0`) satisfy both conditions.

An attacker deposits collateral before the reward token is registered, then — in the same block as the governor's `updateTokenSpeed` (same `block.timestamp`, so `_updateTokenIndex` cannot grow the index past `INITIAL_INDEX`) — calls `updateBeforeMintOrBurn(token, attacker)` and then `claimRewards`, receiving `rewardToken` equal to their full deposit balance.

### Impact Explanation
Direct theft of unclaimed yield / reward-token funds held by the `RewardsDistributor`. `_transferRewardIfEnoughTokens` pays out `tokensAccruedOf[account]` up to the distributor's whole `rewardToken` balance, so an attacker can scale the theft by deposit size and drain rewards owed to all legitimate suppliers/borrowers.

### Likelihood Explanation
Requires a same-timestamp window between token registration (index set to `INITIAL_INDEX`) and the first index update with `deltaTimestamps > 0`. The attacker can (1) hold a deposit balance in advance (index-0 hooks never set `accountIndexOf`), and (2) back-run the governor/keeper `updateTokenSpeed` or `syncTokenSpeed` transaction in the same block via standard bundling, then claim in a subsequent tx. No privileged access is needed for any step after the speed is set. Note `syncTokenSpeed` is keeper-gated but `updateTokenSpeed` is governor-gated — the attacker only needs to be included in the same block, which is achievable on chains with public mempools/bundles.

### Recommendation
Change the fallback to cover the equality case so an unset account index is never interpreted as `0`:

```solidity
if (_accountIndex == 0 && _tokenIndex >= INITIAL_INDEX) {
    _accountIndex = INITIAL_INDEX;
}
```

or unconditionally `if (_accountIndex == 0) _accountIndex = _tokenIndex;` so a first-time accrual always snapshots the current index rather than the zero default.

### Proof of Concept
Hardhat-style sketch (matches existing mocks in `test/RewardDistributor.test.ts`):

```ts
// Setup: pool, depositToken (msdTOKEN1), rewardDistributor initialized with rewardToken
// 1. Attacker deposits BEFORE the token has a speed:
msdTOKEN1.balanceOf.returns(parseEther('1000'))
msdTOKEN1.totalSupply.returns(parseEther('1000'))
// accountIndexOf[msdTOKEN1][attacker] == 0 because hooks no-op while index == 0

// 2. Governor sets speed -> tokenStates[msdTOKEN1] = {index: 1e18, timestamp: now}
await rewardDistributor.updateTokenSpeed(msdTOKEN1.address, parseEther('1'))

// 3. Same block (same timestamp): attacker updates their own accrual
await rewardDistributor.updateBeforeMintOrBurn(msdTOKEN1.address, attacker.address)

// 4. tokensAccruedOf[attacker] == 1000e18 (full balance), not 0
expect(await rewardDistributor.tokensAccruedOf(attacker.address)).to.eq(parseEther('1000'))

// 5. Attacker claims, draining rewardToken
await rewardDistributor.claimRewards(attacker.address)
```

The delta emerges purely from the uninitialized (zero) `accountIndexOf` being treated as a valid index when `tokenStates.index == INITIAL_INDEX`.
