### Title
Tar member path traversal via `custom_hooks/../` escapes tmp/repo directory in `SetCustomHooks`/`RestoreCustomHooks` - ([File: internal/gitaly/repoutil/custom_hooks.go])

### Summary
`ExtractHooks` extracts an attacker-supplied tar stream by shelling out to the system `tar -xf - -C <dir> --strip-components N custom_hooks` without validating individual member names inside the archive. An attacker who owns a repository can call `SetCustomHooksRequest`/`RestoreCustomHooksRequest` with a crafted tar whose member name is `custom_hooks/../../../outside/evil`, which satisfies tar's `custom_hooks` prefix-based member selection but contains embedded `..` components that are not stripped by GNU tar's leading-`..`/absolute-path sanitization, letting the write escape `tmpDir.Path()`.

### Finding Description
`ExtractHooks` (`internal/gitaly/repoutil/custom_hooks.go:55-95`) builds `cmdArgs := []string{"-xf", "-", "-C", path, "--strip-components", stripComponents, CustomHooksDir}` and pipes the raw request bytes straight to the `tar` binary via `command.WithStdin(buf)` [1](#0-0) . The trailing `custom_hooks` positional argument only makes GNU tar select archive members whose name is exactly `custom_hooks` or begins with the prefix `custom_hooks/`; it does not canonicalize or reject `..` components that appear after that prefix. GNU tar's built-in safety logic (`safer_name_suffix`) only strips a leading absolute slash or a leading run of `../` segments at the very start of the member name — it does not sanitize `..` components embedded later in the path (e.g. `custom_hooks/../../../outside/evil`), so such members are extracted using ordinary relative-path semantics that the kernel resolves upward past `-C <path>`.

The RPC handlers `SetCustomHooks`/`RestoreCustomHooks` (`internal/gitaly/service/repository/set_custom_hooks.go:13-42, 47-76`) only validate the `Repository` message field via `s.locator.ValidateRepository` and stream the raw tar bytes into `repoutil.SetCustomHooks` unchanged — there is no inspection of tar member names before extraction [2](#0-1) . `SetCustomHooks` then calls `ExtractHooks(ctx, logger, reader, tmpDir.Path(), false)` [3](#0-2) , so a crafted member is written outside `tmpDir.Path()` and is not cleaned up by the deferred `os.RemoveAll(tmpDir.Path())` [4](#0-3) , since that removal only targets the intended temp directory.

Notably, the codebase already contains a hardened, Go-native tar extractor elsewhere (`extractTarToDirectory` in `internal/gitaly/service/repository/replicate.go:314-406`) that explicitly checks `strings.HasPrefix(targetPath, targetDir+string(os.PathSeparator))` for regular files/dirs and validates symlink/hardlink targets against the extraction boundary [5](#0-4) [6](#0-5) , demonstrating the project is aware of exactly this class of tar-slip risk, yet `custom_hooks.go`'s extraction path does not apply equivalent protection.

### Impact Explanation
An unprivileged repository owner can achieve an arbitrary file write on the Gitaly node outside the intended temporary/hooks directory, limited by the OS-level write permissions of the Gitaly process user and the number of `..` segments needed to escape the storage root. This can lead to corruption or planting of files elsewhere on the storage filesystem (e.g., other repositories' data under the same storage root), which maps to GitLab's "Path Traversal" / "arbitrary file write" bounty impact class, and could plausibly escalate to persistence or repository corruption depending on filesystem layout.

### Likelihood Explanation
Preconditions are minimal: the attacker only needs to own a repository and be able to invoke `SetCustomHooksRequest`/`RestoreCustomHooksRequest`, both of which are exposed to any authenticated repository owner through GitLab Rails (no admin/operator role, no secret, no MITM required). Crafting a tar with a malicious `Name` field is trivial with Go's `archive/tar` package, so the exploit is straightforward and repeatable.

### Recommendation
Replace the shell-out to system `tar` in `ExtractHooks` with a Go-native extractor (similar to `extractTarToDirectory`) that: (1) parses each header with `archive/tar`, (2) rejects/cleans any member whose resolved path (via `filepath.Join` + prefix check against the destination directory) escapes the destination, (3) rejects absolute paths and symlink/hardlink targets that escape the boundary, before writing any file to disk.

### Proof of Concept
```go
func TestExtractHooks_PathTraversal(t *testing.T) {
    ctx := testhelper.Context(t)
    tmpDir := t.TempDir()
    outsideDir := t.TempDir() // sibling directory, simulating "outside" storage path

    var buf bytes.Buffer
    tw := tar.NewWriter(&buf)
    payload := []byte("evil content")
    require.NoError(t, tw.WriteHeader(&tar.Header{
        // crafted to match the "custom_hooks" prefix filter used by tar's
        // positional member argument, then escape via embedded ".."
        Name: fmt.Sprintf("custom_hooks/../../../../..%s/evil", outsideDir),
        Mode: 0o644,
        Size: int64(len(payload)),
    }))
    _, _ = tw.Write(payload)
    require.NoError(t, tw.Close())

    err := repoutil.ExtractHooks(ctx, testhelper.NewLogger(t), &buf, tmpDir, false)
    require.NoError(t, err)

    // Assert the file was NOT written outside tmpDir; if this fails,
    // the traversal succeeded.
    _, statErr := os.Stat(filepath.Join(outsideDir, "evil"))
    require.True(t, os.IsNotExist(statErr), "file escaped extraction directory: %v", statErr)
}
```
Expected (vulnerable) result: the file is found at `outsideDir/evil`, proving escape outside `tmpDir`; a hardened implementation should make the assertion pass by rejecting the malicious member during extraction.
