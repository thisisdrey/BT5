Audit Report

## Title
Snowbridge `OutboundQueueV2::process_delivery_receipt` pays relayer reward without checking dispatch `success` flag - (File: `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs`)

## Summary
`DeliveryReceipt` decoded from the Ethereum `InboundMessageDispatched` event carries a `success: bool` field indicating whether the outbound command actually executed successfully on the Gateway contract [1](#0-0) . `Pallet::process_delivery_receipt` never reads or checks `receipt.success` before releasing the reward tied to the `PendingOrder`; it only validates `gateway` and looks up the order by `nonce` before paying based solely on `order.fee > 0` [2](#0-1) .

## Finding Description
The pallet's doc comment explicitly states the intended flow: reward should be paid "when the message has been verified **and executed**" [3](#0-2) . The implementation in `submit_delivery_receipt` calls `T::Verifier::verify` (authenticating that the log genuinely came from the Gateway) and decodes the `DeliveryReceipt` from the event log, including `success`, but only forwards `relayer` and `receipt` to `process_delivery_receipt` [4](#0-3) . Inside `process_delivery_receipt`, the code checks `receipt.gateway`, resolves `reward_account`, fetches the `PendingOrder` by `nonce`, and pays `order.fee` via `T::RewardPayment::register_reward` purely on the condition `order.fee > 0` — `receipt.success` is never referenced [5](#0-4) . A grep across the pallet's `lib.rs` confirms `success` does not appear anywhere in the reward-gating logic, only in the primitive struct definition and decode logic in `delivery_receipt.rs` [6](#0-5) . The `T::Verifier::verify` check authenticates that the event genuinely occurred on Ethereum, but it does not — and cannot — assert anything about the semantic value of the `success` field it authenticates; it is up to the pallet logic to branch on that field, which it fails to do.

## Impact Explanation
Any relayer submitting a real, valid Merkle/receipt proof of an `InboundMessageDispatched(success=false)` event (e.g., produced by an out-of-gas or reverted command execution on the Gateway contract) will still have `process_delivery_receipt` pay out the full `order.fee` from `PendingOrders`, exactly as though delivery succeeded [7](#0-6) . This is a public, underpriced-work path: relayers can claim fees for messages that were never successfully executed on the destination chain, and the fee pre-paid by the sender in `PendingOrders` (populated in `do_process_message`) [8](#0-7)  is irrevocably spent since `<PendingOrders<T>>::remove(nonce)` runs unconditionally regardless of `success` [9](#0-8) .

## Likelihood Explanation
No privileged actor or off-chain infrastructure compromise is required — any permissionless relayer, the same actor already expected to call `submit_delivery_receipt`, can trigger this by relaying real, provably-valid but execution-failed events, a normal occurrence on any EVM chain (out-of-gas or reverted commands). The `T::Verifier::verify` proof check is satisfied because the event is genuine; it simply does not gate on the semantic `success` value.

## Recommendation
In `process_delivery_receipt`, only call `T::RewardPayment::register_reward` when `receipt.success == true`; for `success == false`, remove the `PendingOrder` without payout (or route to a distinct, smaller "attempted delivery" compensation mechanism), aligning the implementation with the "verified and executed" language in the pallet's own documentation.

## Proof of Concept
1. A message with `fee > 0` is queued via `do_process_message`, creating `PendingOrders[nonce] = { fee, ... }` [10](#0-9) .
2. The relayer submits the message to the Ethereum Gateway with insufficient gas or a reverting command, producing `InboundMessageDispatched(nonce, topic, success=false, reward_address)`.
3. The relayer calls `submit_delivery_receipt` with a valid proof; `T::Verifier::verify` succeeds and `DeliveryReceipt::try_from` decodes `success=false` [11](#0-10) .
4. `process_delivery_receipt` pays out `order.fee` unconditionally since it only checks `order.fee > 0`, ignoring `receipt.success` [12](#0-11) .
5. `PendingOrders[nonce]` is removed, permanently rewarding the relayer for a failed execution.

```rust
/// Delivery receipt
#[derive(Clone, Debug)]
pub struct DeliveryReceipt {
	/// The address of the outbound queue on Ethereum that emitted this message as an event log
	pub gateway: H160,
	/// The nonce of the dispatched message
	pub nonce: u64,
	/// Message topic
	pub topic: H256,
	/// Delivery status
	pub success: bool,
	/// The reward address
	pub reward_address: [u8; 32],
}

#[derive(Copy, Clone, Encode, Decode, Eq, PartialEq, Debug, TypeInfo)]
pub enum DeliveryReceiptDecodeError {
	DecodeLogFailed,
	DecodeAccountFailed,
}

impl TryFrom<&Log> for DeliveryReceipt {
	type Error = DeliveryReceiptDecodeError;

	fn try_from(log: &Log) -> Result<Self, Self::Error> {
		let topics: Vec<B256> = log.topics.iter().map(|x| B256::from_slice(x.as_ref())).collect();

		let event = InboundMessageDispatched::decode_raw_log_validate(topics, &log.data)
			.map_err(|_| DeliveryReceiptDecodeError::DecodeLogFailed)?;

		Ok(Self {
			gateway: log.address,
			nonce: event.nonce,
			topic: H256::from_slice(event.topic.as_ref()),
			success: event.success,
			reward_address: event.reward_address.0,
		})
	}
```

```rust
		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}
```
