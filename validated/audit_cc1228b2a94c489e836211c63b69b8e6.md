## Title
Unauthenticated `RecvError` can tear down relayed tunnels with no address verification - (File: outside.go)

### Summary
`handleRecvError` in `outside.go` is reached directly from `readOutsidePackets` for the plaintext, unauthenticated `header.RecvError` packet type — no certificate, handshake, or encryption is required to reach it. [1](#0-0)  Inside it, the only anti-spoofing check compares the UDP source address of the incoming packet against `hostinfo.GetRemote()`, and that check is skipped entirely when the hostinfo has no valid remote address recorded.

### Finding Description
`readOutsidePackets` dispatches `header.RecvError` packets straight to `f.handleRecvError(via.UdpAddr, h)` before any decryption, certificate check, or handshake state is required — this is one of the few code paths reachable by a fully unauthenticated attacker (no CA-signed certificate needed): [1](#0-0) 

`handleRecvError` looks up the target `hostinfo` purely by the attacker-supplied `RemoteIndex` field via `QueryReverseIndex`, and then attempts to validate the sender: [2](#0-1) 

The validation is:
```go
hr := hostinfo.GetRemote()
if hr.IsValid() && hr != addr {
    f.l.Info("Someone spoofing recv_errors?", ...)
    return
}
f.closeTunnel(hostinfo)
```
This only rejects the packet when `hr` (the hostinfo's recorded direct remote UDP address) is *valid and mismatched*. For relayed hostinfos, `SetRemote(via.UdpAddr)` is explicitly skipped — the handshake path only calls `hostinfo.SetRemote(via.UdpAddr)` when `!via.IsRelayed`; for relayed connections it instead records `relayState.InsertRelayTo(...)` and leaves the hostinfo's direct remote unset/invalid: [3](#0-2) 

Consequently, for any tunnel established via a relay, `hostinfo.GetRemote()` is invalid, `hr.IsValid()` is `false`, the address-match guard is bypassed unconditionally, and `handleRecvError` proceeds to `f.closeTunnel(hostinfo)` plus `f.handshakeManager.DeleteHostInfo(hostinfo)` for *any* attacker who can merely guess/observe the numeric `RemoteIndex` and send one unauthenticated UDP packet from an arbitrary source address — no valid signed certificate, no CA-pool verification, and no handshake participation are required.

This is the same class of bug as the referenced Aave finding: a function trusts an externally supplied value (there, an arbitrary payout address; here, an arbitrary/spoofed source address is implicitly trusted because the "does this match the real remote" check silently no-ops) to perform a privileged, state-changing action — remote state poisoning of the tunnel/hostmap.

### Impact Explanation
An attacker with no certificate at all can force the teardown of any relayed Nebula tunnel by sending a single spoofed `RecvError` packet carrying a guessed/observed `RemoteIndex`. This is a remote, unauthenticated denial-of-service against overlay connectivity for relayed peers (a common topology for hosts behind NAT/firewalls that must use relays), directly poisoning both the active hostmap entry and the pending handshake state (`DeleteHostInfo`).

### Likelihood Explanation
`RemoteIndex` values are 32-bit random values, but they are transmitted in the clear in every packet header on the wire (including relayed data-plane traffic, which per `SendVia`/`VerifyRelay` is authenticated for the encrypted core but headers remain visible), making them observable to a network-adjacent or on-path attacker without needing to break any cryptography. Combined with the fact that no certificate or handshake participation is required to send the `RecvError` packet, likelihood is moderate to high for an attacker positioned to observe relay traffic (e.g., a peer on the shared relay path, or the relay operator itself with no elevated privilege besides packet visibility).

### Recommendation
Do not skip the source-address verification when `hr.IsValid()` is false. For relayed hostinfos, verify the `RecvError` sender against the set of known relay peers (`relayState`) or against the `via.UdpAddr`/relay hostinfo actually associated with the session, rather than allowing an unconditional pass-through when no direct remote is recorded. At minimum, require that a `RecvError` for a relayed hostinfo be delivered `via.IsRelayed == true` and match one of the hostinfo's established relay peers before tearing down the tunnel.

### Proof of Concept
1. Establish (or observe) a relayed tunnel between two Nebula nodes A and B through relay R (as in `TestRelays`/`TestReestablishRelays`, which set up exactly this relayed topology). [4](#0-3) 
2. Observe/guess the `RemoteIndex` value B uses for the tunnel to A (visible in cleartext packet headers).
3. As an attacker with no Nebula certificate, craft a bare `header.RecvError` packet (`header.Encode(..., header.RecvError, 0, index, 0)`, the exact format `sendRecvError` itself produces) with that `RemoteIndex`, from any UDP source address, and send it directly to A's UDP listener.
4. On A, `readOutsidePackets` routes it to `handleRecvError`; since the hostinfo for the relayed tunnel to B has no valid direct remote (`hr.IsValid()` is false because `SetRemote` was never called for the relayed path), the spoofing check is bypassed and `f.closeTunnel(hostinfo)` plus `DeleteHostInfo` execute, tearing down the tunnel.

**Uncertainty note:** I was not able to fully trace every code path that might set a hostinfo's remote to a valid value after relay establishment (e.g., whether some later roaming/promotion logic eventually populates `remote` for relayed hostinfos too, which would narrow the exploitable window). This should be verified by a Devin session with full repository access before treating this as a confirmed, unconditional bypass in all relay lifecycle states.

```go
func (f *Interface) handleRecvError(addr netip.AddrPort, h *header.H) {
	if !f.acceptRecvErrorConfig.ShouldRecvError(addr) {
		f.l.Debug("Recv error received, ignoring",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
		return
	}

	if f.l.Enabled(context.Background(), slog.LevelDebug) {
		f.l.Debug("Recv error received",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
	}

	hostinfo := f.hostMap.QueryReverseIndex(h.RemoteIndex)
	if hostinfo == nil {
		f.l.Debug("Did not find remote index in main hostmap", "remoteIndex", h.RemoteIndex)
		return
	}

	hr := hostinfo.GetRemote()
	if hr.IsValid() && hr != addr {
		f.l.Info("Someone spoofing recv_errors?",
			"addr", addr,
			"hostinfoRemote", hr,
		)
		return
	}

	f.closeTunnel(hostinfo)
	// We also delete it from pending hostmap to allow for fast reconnect.
	f.handshakeManager.DeleteHostInfo(hostinfo)
```
