## Finding

### Title
`SwapFirstAssetTrader::refund_weight` swaps XCM fee-refund credit with no slippage bound - ([File: cumulus/primitives/utility/src/lib.rs])

### Summary
`SwapFirstAssetTrader` (used as a `WeightTrader` in the XCM executor's `buy_weight`/`refund_weight` flow) swaps a user's non-native asset into the pallet's `Target` fee asset for weight purchase, and swaps the unused portion back on refund. The refund path calls `SwapCredit::swap_exact_tokens_for_tokens` with `amount_out_min` hard-coded to `None`, meaning the mandatory refund swap can execute at any price, including one degraded by slippage or pool manipulation, with no protection.

### Finding Description
In `refund_weight`, once the unused weight fee is extracted from `self.total_fee` (denominated in `Target`), it is converted back to the asset the user originally paid with: [1](#0-0) 

```rust
let refund = self.total_fee.extract(refund_amount);
let refund = match SwapCredit::swap_exact_tokens_for_tokens(
    vec![Target::get(), refund_swap_asset],
    refund,
    None,
) {
```

Compare this to `buy_weight`, which uses `swap_tokens_for_exact_tokens` where the desired output (`fee`) is fixed and the risk is bounded on the input side [2](#0-1) . The refund path is the inverse operation and swaps an *exact* input for a *variable* output, which is exactly the shape of operation that needs a minimum-out bound — yet none is supplied.

This mirrors the underlying `pallet_asset_conversion` `Swap`/`SwapCredit` trait design, which explicitly documents and enforces `amount_out_min` when provided: [3](#0-2) . The pallet-level guard `ProvidedMinimumNotSufficientForSwap` only protects callers that actually pass a `Some(min)`; passing `None`, as `refund_weight` does, disables it entirely.

Unlike `pallet_asset_conversion`'s directly-dispatchable extrinsics (which require the caller to explicitly supply `amount_out_min`), this swap is triggered implicitly and automatically by the XCM executor for *any* XCM program containing a `BuyExecution` instruction that ends up with unused weight — i.e., it is a public, unprivileged, permissionlessly-triggerable code path. `pallet_asset_conversion` pools are themselves permissionless to create and to trade against, so an attacker can create a thin pool for the `(Target, refund_swap_asset)` pair, or manipulate an existing pool's spot price with their own capital immediately before submitting (or having someone submit) the XCM message whose refund will be swapped.

### Impact Explanation
Because the refund swap has no minimum-out protection, an attacker who moves the pool price unfavorably immediately before the refund executes causes the refund credit conversion to return substantially less of `refund_swap_asset` than the amount actually owed to the message's beneficiary. The lost value accrues to the pool's liquidity providers/counter-party of the swap rather than to the rightful beneficiary of the refunded weight fee — a fund-loss condition triggerable by an ordinary user without needing a malicious validator, collator, or relayer, matching the "public underpriced work" / "conserve value and settle exactly once to rightful beneficiary" impact categories.

### Likelihood Explanation
Medium: the trader must actually be configured as a `WeightTrader` in a runtime (it's provided as reusable primitive under `cumulus/primitives/utility`), and an attacker needs to influence the specific pool's price in the same block/execution window as the victim's refund. This is directly analogous to the referenced 0x52/Alchemix finding, where the harvest/keeper deposit was "acknowledged" as real but rated Medium because it requires the caller to be sandwiched during an unfavorable window rather than an outright unconditional theft.

### Recommendation
Compute a slippage-bounded `amount_out_min` for the refund swap (e.g., derive it from a recent quote via `QuotePrice::quote_price_exact_tokens_for_tokens`, mirroring how `buy_weight`/`quote_weight` already use `QuotePrice`), and fall back to keeping the unswapped `Target` credit (or forgoing the refund) if the swap cannot meet that bound, instead of passing `None`.

### Proof of Concept
1. Configure a runtime with `SwapFirstAssetTrader<Target, AssetConversion, ..>` as its `WeightTrader`.
2. Create/thin the `(Target, AssetX)` pool in `pallet_asset_conversion` so it has low liquidity (permissionless via `create_pool`/`add_liquidity`).
3. Submit an XCM message that pays weight fees in `AssetX` via `BuyExecution`, using more `AssetX` than the program actually consumes so a refund is triggered.
4. In the same block, execute a large swap against the `(Target, AssetX)` pool to move the price unfavorably for the refund direction (`Target` → `AssetX`).
5. Observe `refund_weight` at `cumulus/primitives/utility/src/lib.rs:540-544` executing `swap_exact_tokens_for_tokens(..., None)` and returning far less `AssetX` than `WeightToFee::weight_to_fee(&weight)` was actually worth, with no error raised because there is no minimum-out check to fail against.
