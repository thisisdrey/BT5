Found a strong analog: `PrecompiledContracts.extractBytes32Array` and `extractBytesArray`/`extractSigArray` in `ValidateMultiSign` allocate a `byte[][]` array whose length comes directly from attacker-controlled ABI-encoded input, mirroring the Pillow bug class (unvalidated size field from external data used to size an allocation before validation).

### Title
Unvalidated attacker-controlled array length used for allocation before size check in `ValidateMultiSign` precompile - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
`PrecompiledContracts.ValidateMultiSign.execute` reads a signature-count word straight out of caller-supplied `data`, and — when the `allowTvmSelfdestructRestriction` fork is *not* active — calls `extractBytesArray(words, offset, rawData)` before any bound is checked against `MAX_SIZE`.

### Finding Description
In `execute()`: [1](#0-0) 
the `MAX_SIZE` (5) check on `sigArraySize` is only performed inside the `if (VMConfig.allowTvmSelfdestructRestriction())` branch. When that fork/config flag is off, `extractBytesArray` is invoked directly: [2](#0-1) 
`extractBytesArray` reads `len = words[offset].intValueSafe()` — a 32-byte word fully controlled by the caller's `data` — and immediately does `new byte[len][]` and then, per element, extracts `bytesLen` (also attacker controlled) via `extractBytes`, which does `Arrays.copyOfRange(data, offset, offset + len)`: [3](#0-2) 
`intValueSafe()` clamps to `Integer.MAX_VALUE`, so `len` can be up to ~2^31-1, causing `new byte[len][]` to attempt to allocate billions of array-reference slots (or an `OutOfMemoryError`) before the length is ever validated against `MAX_SIZE = 5`. This directly parallels the Pillow `FpxImagePlugin` bug: an oversized, attacker-supplied "count" field is passed straight into an allocation/range construct without a bounds check, causing a JVM-level OOM.

Additionally, even in the "protected" path, `sigArraySize` is only checked against `MAX_SIZE`, not checked to be non-negative or sane against `words.length`, so `words[words[3].intValueSafe() / WORD_SIZE]` could itself index out of bounds or wrap, but the primary DoS vector is the unguarded `extractBytesArray` path.

### Impact Explanation
This precompile (address for `ValidateMultiSign`) is reachable from any TVM contract call (e.g. via a `staticcall`/`call` from a smart contract invoked by any transaction sender), i.e. from an unprivileged, unauthenticated caller broadcasting a transaction that triggers a contract call to this precompiled address. Triggering the huge-allocation path can throw `OutOfMemoryError`/exhaust heap on the node processing the transaction, potentially crashing or destabilizing the full node (denial of service), matching the CVE's "process terminated by OOM killer" impact class.

### Likelihood Explanation
Likelihood is moderate-to-high: reaching this code only requires deploying/calling a trivial contract that invokes the `ValidateMultiSign` precompile with crafted calldata where the signature-count word is a very large value, and requires that `allowTvmSelfdestructRestriction` config/fork is not yet active on the target network (this flag gates the size check). On networks/forks where `allowTvmSelfdestructRestriction` is already active, the `MAX_SIZE` guard is present and this specific path is closed — but the guard itself is a fork-gated bugfix, implying the underlying unguarded code exists and is exploitable pre-fork or on any client build with the flag off.

### Recommendation
Move the `MAX_SIZE` bound check (and a check that `len >= 0` and `len` doesn't exceed remaining `words.length`) to unconditionally execute before calling `extractBytesArray`/`extractSigArray`/`extractBytes32Array`, independent of `VMConfig.allowTvmSelfdestructRestriction()`. Validate `len` against `MAX_SIZE` inside `extractBytesArray` and `extractBytes32Array` themselves so all callers are protected regardless of config gating, and validate `bytesLen`/`bytesOffset` against `data.length` before calling `Arrays.copyOfRange`.

### Proof of Concept
1. Deploy any contract that performs a `call`/`staticcall` to the `ValidateMultiSign` precompiled address (e.g. `0x0...gap` per `getContractForAddress`), passing raw calldata constructed as ABI-encoded `(address, uint256 permissionId, bytes32 hash, bytes[] signatures)` where the signatures-array length word is crafted to be a very large integer (e.g. `0x7fffffff`) rather than the real number of following words.
2. Ensure the calldata offset words (`words[3]`) point to this crafted length word.
3. On a node/build where `VMConfig.allowTvmSelfdestructRestriction()` is disabled, invoke the contract; `extractBytesArray` executes `new byte[len][]` with `len` ≈ 2^31−1 before any `MAX_SIZE` check, causing the node's JVM to attempt a multi-GB allocation, resulting in `OutOfMemoryError` / node instability while processing that single transaction.   private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
