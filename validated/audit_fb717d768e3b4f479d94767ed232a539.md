### Title
Missing Cross-Repository Relationship Check in `LinkRepositoryToObjectPool` Allows Unauthorized Object Disclosure via Alternates - (File: internal/gitaly/service/objectpool/link.go)

### Summary
`LinkRepositoryToObjectPool` accepts any `Repository` and any `ObjectPool` in the request and links them by writing an `objects/info/alternates` file, without verifying that the two repositories are actually related (e.g., that the pool was created from that repository's fork network). This mirrors the reported bug class of "missing authorization/ownership check before a privileged cross-entity operation": just as `WERC7575Vault.withdraw`/`redeem` let a caller act on any `owner`'s shares without validating the caller-owner relationship, `LinkRepositoryToObjectPool` lets a caller link *any* target repository to *any* object pool without validating the repository-pool relationship.

### Finding Description
`LinkRepositoryToObjectPool` only validates that the `repository` path is well-formed via `s.locator.ValidateRepository` and that the pool can be resolved via `s.poolForRequest`, but never checks whether `repository` is a legitimate member of the pool's fork network: [1](#0-0) 

The underlying `objectpool.Link` function only checks whether the repository is *already* linked to some pool (and rejects only if linked to a *different* pool); it never verifies that `pool` is the pool that was originally created from `repo`, or that they belong to the same project/fork network: [2](#0-1) [3](#0-2) 

Once linked, Git will resolve any object ID missing from the member repository via the pool's `objects/info/alternates` search path, as documented for the underlying mechanism: [4](#0-3) 

`poolForRequest`/`ExtractPool` merely extract and instantiate the pool object from the request, performing no ownership or membership validation: [5](#0-4) 

### Impact Explanation
If an attacker-controlled or over-broadly-scoped caller can invoke `LinkRepositoryToObjectPool` (e.g. through a compromised/limited internal caller, a bug in a higher-level authorization layer, or any component with generic RPC access but without object-pool-specific business logic authorization), they can link a victim repository they have no relationship to into an object pool containing objects from an unrelated (potentially private) repository. This would make objects from the unrelated pool retrievable through the victim repository's Git object resolution (alternates), and vice versa, causing unauthorized cross-repository object disclosure — a direct violation of repository isolation. This corresponds to the "cross-repository object access" and "object-pool and alternates isolation" bug classes explicitly in scope.

### Likelihood Explanation
This RPC is a `MUTATOR` operation reachable through the standard `ObjectPoolService` gRPC surface: [6](#0-5) 
Gitaly's threat model generally assumes higher-layer (Rails) authorization decides *whether* a given repository/pool pair should be linked before calling this RPC, and Gitaly itself is only reachable via authenticated internal callers. I was not able to fully verify within the available index whether GitLab Rails (out of scope here) enforces the repository-pool relationship before calling this RPC, or whether any other in-scope Gitaly-side guard exists elsewhere (e.g., in `CreateObjectPool` or fork-network validation) that would prevent an arbitrary pairing. Given Gitaly's general design principle of trusting the caller for higher-level authorization decisions, this is likely an intentional trust boundary rather than an unpatched bug — this materially lowers confidence that this constitutes an exploitable vulnerability purely from an "ordinary user" RPC surface, as opposed to requiring a privileged/internal caller (which the analog rules ask to reject).

### Recommendation
Add an explicit Gitaly-side check in `LinkRepositoryToObjectPool` (and `objectpool.Link`) that the target `repository` belongs to the same fork network / project family as the object pool's origin repository (e.g., by recording and verifying the origin repository at `CreateObjectPool` time and requiring all subsequent `LinkRepositoryToObjectPool` calls to reference a repository within that recorded relationship), rather than relying solely on an external caller to have made that determination.

### Proof of Concept
Not constructed — this analysis is based on static code review of `internal/gitaly/service/objectpool/link.go` and `internal/git/objectpool/link.go` only; no dynamic PoC was run, and I could not confirm within this session whether an authorization gate exists upstream (e.g., in GitLab Rails or Praefect routing) that would prevent unrelated repository/pool pairs from ever reaching this RPC in practice.

func (s *server) LinkRepositoryToObjectPool(ctx context.Context, req *gitalypb.LinkRepositoryToObjectPoolRequest) (*gitalypb.LinkRepositoryToObjectPoolResponse, error) {
	repository := req.GetRepository()
	if err := s.locator.ValidateRepository(ctx, repository); err != nil {
		return nil, structerr.NewInvalidArgument("%w", err)
	}

	pool, err := s.poolForRequest(ctx, req)
	if err != nil {
		return nil, err
	}

	repo := s.localRepoFactory.Build(repository)

	if err := pool.Link(ctx, repo); err != nil {
		return nil, structerr.NewInternal("%w", err)
	}

	return &gitalypb.LinkRepositoryToObjectPoolResponse{}, nil

// path relative to the repository into the repository's "alternates" file. This does not trigger
// deduplication, which is the responsibility of the caller.
func Link(ctx context.Context, pool, repo *localrepo.Repo, txManager transaction.Manager) (returnedErr error) {
	altPath, err := repo.InfoAlternatesPath(ctx)
	if err != nil {
		return err
	}

	expectedRelPath, err := getRelativeObjectPath(ctx, pool, repo)
	if err != nil {
		return err
	}

	linked, err := linkedToRepository(ctx, pool, repo)
	if err != nil {
		return err
	}

		// When the repository is already linked to the repository, cast a vote to ensure the
		// repository is consistent with the other replicas.

			return fmt.Errorf("vote on linked repository: %w", err)
		}

		return nil
	}

// linkedToRepository tests if a repository is linked to an object pool
func linkedToRepository(ctx context.Context, pool, repo *localrepo.Repo) (bool, error) {
	poolPath, err := pool.Path(ctx)
	if err != nil {
		return false, fmt.Errorf("getting object pool path: %w", err)
	}

	repoPath, err := repo.Path(ctx)
	if err != nil {
		return false, fmt.Errorf("getting repo path: %w", err)
	}

	altInfo, err := stats.AlternatesInfoForRepository(repoPath)
	if err != nil {
		return false, fmt.Errorf("getting alternates info: %w", err)
	}

	if !altInfo.Exists || len(altInfo.ObjectDirectories) == 0 {
		return false, nil
	}

	relPath := altInfo.ObjectDirectories[0]
	expectedRelPath, err := getRelativeObjectPath(ctx, pool, repo)
	if err != nil {
		return false, err
	}

	if relPath == expectedRelPath {
		return true, nil
	}

	if filepath.Clean(relPath) != filepath.Join(poolPath, "objects") {
		return false, fmt.Errorf("unexpected alternates content: %q", relPath)
	}

	return false, nil
}

```markdown
# Object Pools

When creating forks of a repository, most of the objects for forked repository
and the repository it forked from are shared. Storing those shared objects
multiple times is a waste of disk space and also of CPU time, given that those
shared objects would have to be repacked for both repositories. To fix this
waste of resources, we use object pools, which are essentially a repository
which holds the shared objects of both repositories.

The sharing of objects for a given repository and its object pool is done via
alternate object directories which Gitaly sets up when linking a repository to
an object pool by writing the `objects/info/alternates` file.
```

func ExtractPool(req PoolRequest) (*gitalypb.Repository, error) {
	poolRepo := req.GetObjectPool().GetRepository()
	if poolRepo == nil {
		return nil, errMissingPool
	}

	return poolRepo, nil
}

func (s *server) poolForRequest(ctx context.Context, req PoolRequest) (*objectpool.ObjectPool, error) {
	pool, err := objectpool.FromProto(ctx, s.logger, s.locator, s.gitCmdFactory, s.catfileCache, s.txManager, s.housekeepingManager, req.GetObjectPool())
	if err != nil {
		if errors.Is(err, objectpool.ErrInvalidPoolDir) {
			return nil, errInvalidPoolDir
		}

		if errors.Is(err, objectpool.ErrInvalidPoolRepository) {
			return nil, structerr.NewFailedPrecondition("%w", err)
		}

		return nil, structerr.NewInternal("%w", err)
	}

	return pool, nil
