## Title
Missing Refund of Excess Attached Deposit in `AddressRegistrar::register()` — Permanent Loss of User Funds - (File: `runtime/near-wallet-contract/implementation/address-registrar/src/lib.rs`)

### Summary
The `register()` method of the `AddressRegistrar` contract (used by the ETH-implicit Wallet Contract system) only validates that the attached deposit is *at least* the required storage cost, but never returns any surplus when registration succeeds. This is the exact "excess Ether not refunded" bug class from the external report, translated to NEAR's `attached_deposit`/`#[payable]` model.

### Finding Description
`register()` computes a `required_deposit` based on the storage bytes needed and checks: [1](#0-0) 

If `given_deposit >= required_deposit` the check passes, and execution proceeds to the `Vacant` branch (successful new registration) where the entry is inserted but **no refund logic runs at all**: [2](#0-1) 

Note that the refund-to-caller logic (`promise_batch_action_transfer`) exists only in the `Occupied` (collision) branch, which returns the *entire* deposit — it is never used to return the *difference* between `given_deposit` and `required_deposit` in the success path: [3](#0-2) 

This mirrors the reported pattern precisely: `require(msg.value >= totalRoseAmount)` with no branch handling `msg.value > totalRoseAmount`.

Because this happens inside a *successful* function call, NEAR's protocol-level deposit-refund mechanism does not intervene. `nearcore`'s deposit refunds are only generated when a receipt execution **fails**; a successful receipt keeps whatever balance was transferred to the receiver account, per `docs/RuntimeSpec/Refunds.md`: [4](#0-3) 

and confirmed in the runtime execution spec (`refund_unspent_gas_and_deposits` only refunds the deposit `if result.result.is_err()`): [5](#0-4) 

So once `register()` returns successfully with a `Vacant` entry, any excess deposit above `required_deposit` is permanently credited to the `AddressRegistrar` account with no method exposed by the contract to withdraw or reclaim it (only `register`, `lookup`, and `get_address` are public methods).

### Impact Explanation
Any user (or, more commonly, the ETH-implicit Wallet Contract acting on behalf of an Ethereum-style user via `rlp_execute`, as exercised in `test_register_without_deposit`) who attaches more than the exact storage-byte cost to `register()` permanently loses the difference — it becomes stuck in the `AddressRegistrar` contract's balance with no code path to recover it. This is a permanent freezing/loss of user funds, satisfying the "concrete theft or permanent freezing of funds" bar. Given that computing the *exact* required deposit (`storage_byte_cost() * (20 + account_id.len())`) client-side is error-prone (and the ABI-encoded Ethereum transaction path in the Wallet Contract truncates/derives values with lossy conversions elsewhere in that codebase), overpayment is a realistic, easy-to-trigger user mistake rather than a contrived edge case.

### Likelihood Explanation
Reachable by any ordinary account with a plain `FunctionCall` action carrying a deposit larger than needed (e.g., a wallet UI/relayer padding the deposit for safety margin), or via the Wallet Contract's `rlp_execute` emulation flow used for ETH-style registration calls. No special privileges are required, and this is demonstrated as a supported, tested user flow in `test_register_without_deposit`: [6](#0-5) 

### Recommendation
In `register()`, after computing `required_deposit` and confirming `given_deposit >= required_deposit`, refund the excess (`given_deposit - required_deposit`) back to `env::predecessor_account_id()` in the `Vacant` branch, mirroring the refund logic already present in the `Occupied` branch. Alternatively, require `given_deposit == required_deposit` (exact match) and reject overpayment outright.

### Proof of Concept
1. Deploy `AddressRegistrar` and call `new()`.
2. Call `register(account_id: "alice.near")` with `attached_deposit` set to, say, `2 * required_deposit` (e.g. call with more NEAR than the storage cost, such as 1 NEAR when only a few hundred yoctoNEAR-per-byte × ~30 bytes is required).
3. Observe the call succeeds (`Vacant` branch), the mapping is inserted, and `Some(address)` is returned.
4. Query the `AddressRegistrar` account balance before/after: the balance increased by the *full* attached deposit rather than just `required_deposit`.
5. There is no method on the contract to withdraw the surplus — the excess deposit is permanently locked in the contract, unlike the `Occupied`-branch collision case which fully refunds the caller.

#[tokio::test]
async fn test_register_without_deposit() -> anyhow::Result<()> {
    let TestContext { worker, address_registrar, .. } = TestContext::new().await?;

    let method = "register";
    let args = br#"{"account_id": "birchmd.near"}"#;
    let result = address_registrar.call(method).args(args.to_vec()).transact().await?;
    assert!(result.is_failure(), "Call without deposit must fail");

    let pre_tx_account_balance = address_registrar.as_account().view_account().await?.balance;
    let deposit_amount = NearToken::from_yoctonear(320000000000000000000);
    let result = worker
        .root_account()?
        .call(address_registrar.id(), method)
        .args(args.to_vec())
        .deposit(deposit_amount)
        .transact()
        .await?;

    let output: Option<String> = result.json()?;
    assert_eq!(output.as_deref(), Some("0x4bfcff9a964925adf801c866f6ada98bd7ec40ca"));
    let post_tx_account_balance = address_registrar.as_account().view_account().await?.balance;
    assert!(
        post_tx_account_balance.as_yoctonear() - pre_tx_account_balance.as_yoctonear()
            >= deposit_amount.as_yoctonear()
    );
