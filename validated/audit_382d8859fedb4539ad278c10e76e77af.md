### Title
Unbounded `pages_indexes` parsing before `MAX_ATTACHMENT_INV_PAGES_PER_REQUEST` cap enables bounded compute DoS - (File: stackslib/src/net/api/getattachmentsinv.rs)

### Summary
`RPCGetAttachmentsInvRequestHandler::try_parse_request` parses every comma-separated entry of the `pages_indexes` query parameter into a `HashSet<u32>` and then sorts the collected `Vec<u32>`, with no limit on the number of entries. The `MAX_ATTACHMENT_INV_PAGES_PER_REQUEST` (8) cap is only enforced afterward, in `try_handle_request`, so a single crafted GET request forces the server to do unbounded parsing/hashing/allocation/sorting work before that request is ultimately rejected.

### Finding Description
In `try_parse_request` [1](#0-0) , the handler iterates the entire `pages_indexes` value, splitting on `,` and inserting every parsed `u32` into a `HashSet` with no count limit. It then collects the set into a `Vec<u32>` and sorts it [2](#0-1) . Only afterward, in `try_handle_request`, is `page_indexes.len() > MAX_ATTACHMENT_INV_PAGES_PER_REQUEST` checked and the request rejected with `HttpBadRequest` [3](#0-2) . The comment explicitly documents that the 8-page cap is meant to bound work, but the implementation only applies it post-parse, not during parsing.

Because the query string is delivered as part of the HTTP request line/headers, its size is bounded only by whatever generic preamble/header-size limit the HTTP layer enforces (not by any endpoint-specific cap on the number of `pages_indexes` entries). Any number of comma-separated integers that fits within that generic size budget will be fully parsed, hashed, collected, and sorted by this handler before the 8-item check rejects the request. This is a real gap between "parsed count" and "bounded count during parsing" as claimed in the question.

### Impact Explanation
An attacker can send a single `GET /v2/attachments/inv?index_block_hash=<64 hex>&pages_indexes=<N comma-separated u32s>` request. The node performs O(N) string splitting, O(N) `u32` parsing, O(N) `HashSet` insertions, and O(N log N) sorting before rejecting the request for exceeding `MAX_ATTACHMENT_INV_PAGES_PER_REQUEST`. This is a bounded (not disk/memory-unbounded) but avoidable CPU/allocation cost imposed on a read endpoint reachable by any unauthenticated remote client, matching the "bounded compute DoS on a read endpoint" High-impact category. It is trivially repeatable — each request costs the attacker only the bytes of one HTTP request but forces parsing work on the node that scales with N, up to whatever the generic HTTP request/header size limit permits.

### Likelihood Explanation
No authentication or special role is required — `/v2/attachments/inv` is a public RPC GET endpoint. The attacker only needs network reachability to the node's RPC port, which matches the "remote unprivileged client" threat model. The attack is cheap to construct (build a long comma-separated numeric string) and can be repeated at will, limited only by the generic HTTP request-size ceiling enforced by the framing/header-parsing layer (not something specific to this handler).

### Recommendation
Enforce `MAX_ATTACHMENT_INV_PAGES_PER_REQUEST` while parsing in `try_parse_request`, e.g., break out of the loop (or return an early `Error::DecodeError`) as soon as the number of unique parsed entries (or even the raw number of comma-separated tokens) exceeds `MAX_ATTACHMENT_INV_PAGES_PER_REQUEST`, instead of collecting an unbounded set first and checking the limit later in `try_handle_request`.

### Proof of Concept

```rust
// stackslib/src/net/api/tests/getattachmentsinv.rs
#[test]
fn test_try_parse_request_unbounded_pages_indexes() {
    let mut handler = RPCGetAttachmentsInvRequestHandler::new();
    let ibh = "00".repeat(32); // 64 hex chars
    // Build a huge comma-separated list of page indexes (e.g. hundreds of thousands)
    let huge_list: String = (0..1_000_000u32)
        .map(|i| i.to_string())
        .collect::<Vec<_>>()
        .join(",");
    let query = format!("index_block_hash={}&pages_indexes={}", ibh, huge_list);

    let preamble = /* build a well-formed 0-length-body GET preamble */;
    let captures = Regex::new("^/v2/attachments/inv$").unwrap().captures("/v2/attachments/inv").unwrap();

    let start = std::time::Instant::now();
    let result = handler.try_parse_request(&preamble, &captures, Some(&query), &[]);
    let elapsed = start.elapsed();

    // try_parse_request succeeds and has already done O(N) hashing/sorting work
    assert!(result.is_ok());
    assert_eq!(handler.page_indexes.as_ref().unwrap().len(), 1_000_000);
    // Only later, in try_handle_request, is the 8-item cap enforced and the request rejected.
    println!("parse time for 1M entries: {:?}", elapsed);
}
```
This demonstrates that `try_parse_request` fully materializes and sorts an arbitrarily large `page_indexes` collection regardless of `MAX_ATTACHMENT_INV_PAGES_PER_REQUEST`, with rejection only happening afterward in `try_handle_request`.
