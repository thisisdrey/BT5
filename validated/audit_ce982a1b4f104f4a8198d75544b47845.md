Audit Report

## Title
Pre-funding the deterministic AMM pool account desynchronizes the "first deposit" branch from LP-supply state in `pallet-asset-conversion` - (File: `substrate/frame/asset-conversion/src/lib.rs`)

## Summary
`do_create_pool`/`do_add_liquidity` derive the pool account deterministically from the asset pair via `T::PoolLocator::address`, and `do_add_liquidity` selects its deposit-amount branch based on the live balances of that account (`reserve1.is_zero() || reserve2.is_zero()`) rather than on the LP token's `total_supply`, which is the value actually used by the minting formula. Since the pool account is a pure, publicly-computable function of `(asset1, asset2)` and `do_create_pool` never inspects or resets any pre-existing balance on it, an attacker can transfer a small, skewed ratio of both assets to the not-yet-created pool account before `create_pool`/`add_liquidity` is ever called, forcing subsequent legitimate deposits through the `quote()`-based branch against a pathological ratio.

## Finding Description
`T::PoolLocator::address`/`pool_address` computes the pool account purely from the asset pair [1](#0-0) , and this is exposed publicly via `get_reserves` [2](#0-1) . `get_balance` reads the account's live, unrestricted balance with no notion of "has the pool officially started" [3](#0-2) . `do_create_pool` checks only `Pools::<T>::contains_key` for a duplicate pool id and never inspects or clears any pre-existing balance on `pool_account` before registering the pool [4](#0-3) .

In `do_add_liquidity`, the branch selection between "first deposit" (straight desired amounts) and "ratio-matched deposit" (via `quote`) is driven by `reserve1.is_zero() || reserve2.is_zero()` — i.e., by live account balances — while the LP-minting formula is separately driven by `T::PoolAssets::total_issuance(pool.lp_token)` being zero [5](#0-4) . These two checks are intended to move together (empty pool ⇔ zero LP supply), but an attacker can decouple them by donating non-zero, skewed-ratio balances of `asset1`/`asset2` directly to the not-yet-created `pool_account` prior to any `create_pool`/`add_liquidity` call.

I verified this code path is present exactly as described and traced the resulting exploit mechanics: with a poisoned reserve ratio, `do_add_liquidity` takes the `quote()` branch even though `total_supply == 0`. Depending on the exact ratio and the legitimate depositor's chosen amounts, `quote()`'s integer division can round the computed optimal amount down to `0`. If that occurs, `calc_lp_amount_for_zero_supply` (invoked because `total_supply.is_zero()`) computes a minted-LP amount that also rounds to `0`, which then fails the `lp_token_amount > T::MintMinLiquidity::get()` check with `InsufficientLiquidityMinted` [6](#0-5) . Depending on rounding, the earlier `amount1_optimal >= amount1_min` / `amount2_optimal >= amount2_min` checks or the minimum-balance checks at lines 846-853 can also fail [7](#0-6) . Because the pool is already registered in `Pools::<T>` with zero LP supply and an attacker-controlled skewed reserve ratio, and no pallet extrinsic resets the account's balances or forces the reserve-based branch back to "first deposit," this is a genuine, reachable state-desynchronization bug rooted in using externally-influenceable account balances (rather than pallet-owned `total_supply`/storage state) as the source of truth for a protocol-critical branch decision.

However, the claim's assertion that the pool becomes "permanently unusable" for all subsequent liquidity provisioning is not fully substantiated: a sufficiently well-capitalized user who chooses `amount1_desired`/`amount2_desired` matching the poisoned ratio precisely enough to avoid rounding to zero (which may require depositing amounts proportional to the attacker's skewed ratio, potentially very large for one side) can still successfully add liquidity through the `quote()` branch and mint LP tokens. The practical severity therefore depends on how extreme a ratio the attacker chooses and the decimals/precision of the assets involved — it is a real griefing/DoS vector against the "first deposit" invariant and a genuine mismatch between the reserve-based branch check and the LP-supply-based mint check, but full permanent bricking (as opposed to griefing that raises the cost/precision bar for legitimate first liquidity provisioning) is not guaranteed in all cases and depends on parameters not fixed by the code itself.

## Impact Explanation
This is a public, unprivileged griefing/DoS vector against `pallet-asset-conversion`, usable by any account able to send a small transfer of `asset1`/`asset2` to a publicly-computable address before a pool's first liquidity provisioning. It can force legitimate first-liquidity-provider transactions to fail (`InsufficientLiquidityMinted`, `AmountOneLessThanMinimal`/`AmountTwoLessThanMinimal`, or `OptimalAmountLessThanDesired`/`*DepositDidNotMeetMinimum`) and, for sufficiently extreme attacker-chosen ratios relative to realistic deposit sizes, can make a specific asset pair's pool practically unusable through the standard pallet API, aligning with the "public underpriced work that … stalls" / degraded-availability impact class for that trading pair. It requires no governance, validator, relayer, or malicious-node assumption.

## Likelihood Explanation
High feasibility of triggering the branch-mismatch: the attack requires only computing `T::PoolLocator::address(asset1, asset2)` (a pure, public function) and sending ordinary token transfers to it before the pool's first real deposit succeeds — no special privileges or timing relative to block production beyond acting before the legitimate first liquidity provider. However, achieving a fully unrecoverable "permanent lock" (rather than a griefing effect that can eventually be worked around by a well-funded, precisely-calculated deposit) depends on the specific ratio chosen and asset decimals, which is not something the code itself guarantees to be unrecoverable in all cases.

## Recommendation
Use `T::PoolAssets::total_issuance(pool.lp_token) == 0` (already computed later in the function) as the single source of truth for the "first deposit" branch in `do_add_liquidity`, instead of `reserve1.is_zero() || reserve2.is_zero()`, so the branch decision is consistent with the minting formula and cannot be desynchronized by externally-donated balances. Additionally, consider having `do_create_pool` reject creation (or sweep/quarantine) when the derived `pool_account` already holds a non-zero balance of either asset, preventing pre-funding from having any effect on pool initialization.

## Proof of Concept
1. Compute `pool_account = PoolLocator::address(asset1, asset2)` for a not-yet-created pair.
2. Attacker transfers a small amount of `asset1` and a much larger amount of `asset2` directly to `pool_account` via `Assets::transfer`/`Balances::transfer` (no pallet call needed).
3. Attacker or anyone calls `create_pool(asset1, asset2)` — succeeds, since `do_create_pool` never inspects `pool_account`'s balances (`substrate/frame/asset-conversion/src/lib.rs` lines 729-788).
4. A legitimate user calls `add_liquidity(asset1, asset2, amount1_desired, amount2_desired, ...)`. Since `reserve1`/`reserve2` are both non-zero, `do_add_liquidity` takes the `quote()` branch (lines 813-844) instead of the "first deposit" branch, even though `total_supply == 0`.
5. Depending on the chosen ratio and deposit sizes, the computed optimal amount rounds to `0` via integer division in `quote()`, causing `calc_lp_amount_for_zero_supply` to also compute `0`, which fails `InsufficientLiquidityMinted` at lines 874-877 — demonstrating the reserve/total_supply desynchronization described above as a reproducible integration-test scenario.

		pub(crate) fn do_create_pool(
			creator: &T::AccountId,
			asset1: T::AssetKind,
			asset2: T::AssetKind,
			initial_fee: Option<Permill>,
		) -> Result<T::PoolId, DispatchError> {
			ensure!(asset1 != asset2, Error::<T>::InvalidAssetPair);
			if let Some(fee) = initial_fee {
				ensure!(fee <= T::MaxSwapFee::get(), Error::<T>::FeeTooHigh);
			}

			// prepare pool_id
			let pool_id = T::PoolLocator::pool_id(&asset1, &asset2)
				.map_err(|_| Error::<T>::InvalidAssetPair)?;
			ensure!(!Pools::<T>::contains_key(&pool_id), Error::<T>::PoolExists);

			let pool_account =
				T::PoolLocator::address(&pool_id).map_err(|_| Error::<T>::InvalidAssetPair)?;

			// pay the setup fee
			let fee =
				Self::withdraw(T::PoolSetupFeeAsset::get(), creator, T::PoolSetupFee::get(), true)?;
			T::PoolSetupFeeTarget::on_unbalanced(fee);

			if T::Assets::should_touch(asset1.clone(), &pool_account) {
				T::Assets::touch(asset1.clone(), &pool_account, creator)?
			};

			if T::Assets::should_touch(asset2.clone(), &pool_account) {
				T::Assets::touch(asset2.clone(), &pool_account, creator)?
			};

			let lp_token = NextPoolAssetId::<T>::get()
				.or(T::PoolAssetId::initial_value())
				.ok_or(Error::<T>::IncorrectPoolAssetId)?;
			let next_lp_token_id = lp_token.increment().ok_or(Error::<T>::IncorrectPoolAssetId)?;
			NextPoolAssetId::<T>::set(Some(next_lp_token_id));

			T::PoolAssets::create(lp_token.clone(), pool_account.clone(), false, 1u32.into())?;
			if T::PoolAssets::should_touch(lp_token.clone(), &pool_account) {
				T::PoolAssets::touch(lp_token.clone(), &pool_account, creator)?
			};

			let pool_info = PoolInfo { lp_token: lp_token.clone() };
			Pools::<T>::insert(pool_id.clone(), pool_info);

			Self::deposit_event(Event::PoolCreated {
				creator: creator.clone(),
				pool_id: pool_id.clone(),
				pool_account,
				lp_token,
			});

			if let Some(fee) = initial_fee {
				PoolFees::<T>::insert(&pool_id, fee);
				Self::deposit_event(Event::PoolFeeSet { pool_id: pool_id.clone(), fee });
			}

			Ok(pool_id)
		}
