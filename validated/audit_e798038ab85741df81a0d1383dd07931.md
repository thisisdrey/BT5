### Title
Sending TRX value to a precompiled contract address via `CALL`/`CALLCODE` permanently locks funds - (File: `actuator/src/main/java/org/tron/core/vm/program/Program.java`)

### Summary
`Program.callToPrecompiledAddress` unconditionally transfers the call's `endowment` (TRX value) into the target precompiled contract's account balance before invoking the precompiled logic, regardless of whether the target address corresponds to a real, controllable account. Precompiled contracts (`ecRecover`, `sha256`, `rewardBalance`, `voteCount`, the FreezeV2 helper precompiles, etc.) have no private key and no withdraw/forwarding logic, so any TRX sent to them becomes permanently stranded — structurally the same failure mode as the Rio `RioLRTRewardDistributor` bug: value is credited to an address outside of any distribution/accounting path that can move it back out.

### Finding Description
Precompiled contracts live at fixed, hard-coded addresses (e.g. `0x1`…`0xa`, `0x1000001`…`0x1000015`, `0x20003`, `0x20009`, `0x100`), enumerated in `PrecompiledContracts.getContractForAddress`. [1](#0-0) [2](#0-1) 

When TVM executes a `CALL`/`CALLCODE`/`DELEGATECALL` whose target resolves to one of these addresses, `Program.callToPrecompiledAddress` runs. It computes the `endowment` from the message value and, if non-zero and sender != context address, performs an unconditional TRX transfer into the precompile's balance via `MUtil.transfer(deposit, senderAddress, contextAddress, endowment)` before the precompiled contract's `execute(data)` is even invoked: [3](#0-2) 

There is no check that the precompile is "payable", no path returning the value if execution fails, and no logic in any `PrecompiledContract` implementation to move, forward, or make that balance spendable/withdrawable — unlike normal contract accounts, precompiles have no bytecode, no owning key, and no accounted redistribution mechanism (analogous to `RioLRTRewardDistributor` only accounting value through its `receive()` while direct/coinbase-style credits bypassed it entirely). Balance credited to a precompile address is functionally identical to sending funds to a burn address, except it is not intentional and is reachable by anyone calling a contract that forwards TRX with a crafted target address (`CALL` opcode allows arbitrary `codeAddress` and `value`).

### Impact Explanation
Any unprivileged account can trigger a smart contract (their own or any deployed contract that performs an externally-controllable `CALL` with value, e.g., a generic multisend/proxy/forwarder pattern) targeting a precompile address with non-zero `value`. The TRX is unconditionally deducted from the caller/contract and credited to the fixed precompile address. Since that address is not a real controllable account, the TRX becomes permanently frozen and effectively removed from circulation without any burn/blackhole accounting — an unbacked, permanently locked balance, matching the "permanent freezing of funds" impact criterion.

### Likelihood Explanation
Reachable purely through a single `TriggerSmartContract` transaction from any unprivileged caller — no special permission, staking, or witness role required. It only requires a contract issuing a `CALL` (or similar `value`-carrying opcode) to a low/fixed address, something that can happen accidentally (bad address input, off-by-one/truncated address computation, typos in target address parameters of proxy/router contracts) or be triggered deliberately by an attacker who wants to grief/burn value sent through such a contract path. No mempool timing or race condition is needed, making this consistently and trivially reachable.

### Recommendation
In `Program.callToPrecompiledAddress`, reject (revert/refund) any call carrying non-zero `endowment` directed at a precompiled contract address instead of unconditionally crediting its balance — mirroring the recommended fix pattern from the referenced report (add an explicit, safe path for value instead of relying on an implicit/",silent" credit with no distribution mechanism). Concretely: check `PrecompiledContracts.getContractForAddress(codeAddress) != null` before performing the `MUtil.transfer` call at line 1717, and if the target is a precompile and `endowment > 0`, fail the call (push zero / throw, as is already done for other invalid-call conditions in this method) rather than transferring value.

### Proof of Concept
1. Deploy a simple contract with a function:
```solidity
function drain(address payable target, uint256 tokenId) external payable {
    // e.g., target = address(0x1) (ecRecover), or address(0x1000005) (rewardBalance)
    target.call{value: msg.value}("");
}
```
2. From any unprivileged account, call `drain{value: X}(address(0x1), 0)` via `TriggerSmartContract`.
3. In `Program.callToPrecompiledAddress`, `codeAddress` resolves to the `ecRecover` precompile via `PrecompiledContracts.getContractForAddress`; `endowment = X > 0`; the code executes `MUtil.transfer(deposit, senderAddress, contextAddress, endowment)` at line 1717, crediting `X` TRX to address `0x1`.
4. `ecRecover.execute(data)` runs and returns normally (unrelated to the value transfer).
5. Query `getAccount(0x1).getBalance()` — the TRX is now permanently held at an address with no private key, no owning contract logic, and no withdrawal path, i.e. permanently lost.

Note: I was unable to execute the actual PoC in a live node/testnet within this environment; the analysis is based on static code review of `Program.java` and `PrecompiledContracts.java`. If further certainty is needed (e.g., confirming no upstream validation elsewhere blocks value transfers to precompile addresses), a Devin session with full repo/test access should be used to run/extend the existing `PrecompiledContractsTest` or `EnergyWhenSendAndTransferTest` suites to confirm the balance ends up stuck at the precompile address.
