### Title
Fixed-window per-connection stream throttling in `ConnectionStreamCounter` allows ~2x burst around `STREAM_THROTTLING_INTERVAL` boundaries - ([File: streamer/src/nonblocking/stream_throttle.rs])

### Summary
`ConnectionStreamCounter::reset_throttling_params_if_needed` implements a fixed (non-sliding) window rate limiter: it resets `stream_count` and `last_throttling_instant` only once more than `STREAM_THROTTLING_INTERVAL` has elapsed since the last reset. An unstaked (or staked) attacker who times stream opens to straddle a reset boundary can consume close to `max_streams_per_throttling_interval` twice in quick succession — once just before the window resets and once immediately after — getting up to ~2x the intended per-connection stream throughput in a short wall-clock span.

### Finding Description
`throttle_stream` (streamer/src/nonblocking/stream_throttle.rs:233-271) is invoked from `SwQos::on_new_stream` (streamer/src/nonblocking/swqos.rs:496-516) for every new QUIC unidirectional stream a peer opens. It calls `stream_counter.reset_throttling_params_if_needed()` [1](#0-0)  which only resets the per-connection `stream_count` and window anchor `last_throttling_instant` when `Instant::now().duration_since(last_throttling_instant) > STREAM_THROTTLING_INTERVAL`. This is a fixed-window counter anchored to the previous reset time, not a sliding window.

Because the reset is edge-triggered on elapsed time relative to the *last reset instant* (not a rolling STREAM_THROTTLING_INTERVAL-wide lookback), an attacker who:
1. Waits until just before the window boundary (`last_throttling_instant + STREAM_THROTTLING_INTERVAL - ε`) and opens streams up to `max_streams_per_throttling_interval` (e.g., 20 for the default unstaked cap, computed from `MAX_UNSTAKED_TPS * STREAM_THROTTLING_INTERVAL_MS / 1000` in `StakedStreamLoadEMA::new`, streamer/src/nonblocking/stream_throttle.rs:64-68),
2. Then immediately after the boundary (`last_throttling_instant + STREAM_THROTTLING_INTERVAL + ε`) triggers the reset via the next `on_new_stream` call, which zeroes `stream_count` and moves the anchor forward — allowing another full burst of `max_streams_per_throttling_interval`,

can push close to `2 * max_streams_per_throttling_interval` streams through in roughly `2ε` wall-clock time, well under the nominal per-`STREAM_THROTTLING_INTERVAL` cap enforced by the design. `throttle_stream` itself only compares `streams_read_in_throttle_interval >= max_streams_per_throttling_interval` against the counter that was just reset [2](#0-1) , so it has no memory of streams consumed in the prior window and cannot detect this straddling pattern. `on_stream_accepted` unconditionally increments `stream_count` on every accepted stream with no cross-window accounting [3](#0-2) .

This is reachable by any remote unstaked peer with `max_unstaked_load_in_throttling_window > 0` (the default configuration allows unstaked connections), requiring no privileges, staked keys, or validator control — only precisely timed stream opens on an otherwise normal QUIC connection to the TPU port.

### Impact Explanation
This is a QoS evasion: the per-connection stream cap intended to bound a single connection's share of leader ingestion capacity (`max_streams_per_throttling_interval`, derived from `StakedStreamLoadEMA`) can be doubled for short bursts by boundary-aligned timing, degrading fairness for other unstaked/staked connections competing for the same shared `max_unstaked_load_in_throttling_window`/`max_staked_load_in_throttling_window` budget. It does not cause a panic, deadlock, unbounded memory growth, or verification bypass; the impact is confined to a temporary, bounded (≈2x, not unbounded) throughput/fairness degradation per malicious connection.

### Likelihood Explanation
Fully feasible with a single unstaked QUIC client and precise local timing of `open_uni()` calls relative to observed throttling behavior (e.g., inferring the last reset instant from received `stream_count`-triggered backpressure/sleep responses, or simply free-running two bursts spaced by `STREAM_THROTTLING_INTERVAL` (100ms) plus a small margin). No cluster state, stake, or coordination with other nodes is required, making this repeatable per-connection at will.

### Recommendation
Replace the fixed reset-window logic in `ConnectionStreamCounter::reset_throttling_params_if_needed` with a sliding-window or token-bucket-style accounting (similar to the `TokenBucket` already used in `simple_qos.rs`) that decays/allows tokens continuously over time rather than snapping the counter to zero at discrete edges, so that no `STREAM_THROTTLING_INTERVAL`-wide sliding window can ever exceed `max_streams_per_throttling_interval`.

### Proof of Concept
```rust
// streamer/src/nonblocking/stream_throttle.rs (test module)
#[tokio::test(start_paused = true)]
async fn test_boundary_straddle_doubles_effective_throughput() {
    use tokio::time::{advance, Duration};

    let stats = Arc::new(StreamerStats::default());
    let counter = Arc::new(ConnectionStreamCounter::new());
    let max_streams = 20u64; // default unstaked cap

    // Burst 1: consume full quota just before window boundary.
    for _ in 0..max_streams {
        throttle_stream(&stats, ConnectionPeerType::Unstaked, "127.0.0.1:0".parse().unwrap(), &counter, max_streams).await;
        counter.stream_count.fetch_add(1, Ordering::Relaxed);
    }
    // Advance to just before STREAM_THROTTLING_INTERVAL elapses.
    advance(STREAM_THROTTLING_INTERVAL - Duration::from_millis(1)).await;

    // Advance past the boundary to trigger reset on next call.
    advance(Duration::from_millis(2)).await;

    let mut accepted_in_window2 = 0;
    for _ in 0..max_streams {
        throttle_stream(&stats, ConnectionPeerType::Unstaked, "127.0.0.1:0".parse().unwrap(), &counter, max_streams).await;
        counter.stream_count.fetch_add(1, Ordering::Relaxed);
        accepted_in_window2 += 1;
    }

    // Total streams accepted within ~STREAM_THROTTLING_INTERVAL wall time:
    let total = max_streams + accepted_in_window2;
    // Assert the sliding-window invariant is violated (demonstrating the bug):
    assert!(total > max_streams + 1, "burst near boundary exceeded single-window cap by more than 1: total={total}");
}
```
Expected result: `total` reaches close to `2 * max_streams` (≈40) within a single `STREAM_THROTTLING_INTERVAL`-sized wall-clock span, violating the intended sliding-window invariant of at most `max_streams_per_throttling_interval` (+1) streams per any `STREAM_THROTTLING_INTERVAL` window.

    pub(crate) fn reset_throttling_params_if_needed(&self) -> tokio::time::Instant {
        let last_throttling_instant = *self.last_throttling_instant.read().unwrap();
        if tokio::time::Instant::now().duration_since(last_throttling_instant)
            > STREAM_THROTTLING_INTERVAL
        {
            let mut last_throttling_instant = self.last_throttling_instant.write().unwrap();
            // Recheck as some other thread might have done throttling since this thread tried to acquire the write lock.
            if tokio::time::Instant::now().duration_since(*last_throttling_instant)
                > STREAM_THROTTLING_INTERVAL
            {
                *last_throttling_instant = tokio::time::Instant::now();
                self.stream_count.store(0, Ordering::Relaxed);
            }
            *last_throttling_instant
        } else {
            last_throttling_instant
        }
    }
