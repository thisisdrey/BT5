### Title
`action_create_account` omits an `AccountType`/implicit-account check, allowing pre-creation of key-less accounts at implicit-account addresses, permanently freezing subsequent transfers - ([File: runtime/runtime/src/actions.rs])

### Summary
`action_create_account` only validates the top-level/sub-account naming rules and never checks `account_id.get_account_type()`. [1](#0-0)  Any account whose 64-hex-character name would normally be an implicit account (`NearImplicitAccount`) is instead treated as an ordinary long top-level name and can be created by an arbitrary predecessor with `CreateAccount`, producing an account with zero access keys.

### Finding Description
`derive_near_implicit_account_id` produces a plain hex-encoded ED25519 public key string as an `AccountId`. [2](#0-1)  Such a string contains no dot, so in `action_create_account` it is classified as a "top-level" name; the only gate for top-level names is a minimum-length/registrar check (`min_allowed_top_level_account_length`), and hex-encoded public keys (64 chars) comfortably exceed that minimum, so any predecessor account can create it without being the registrar: [3](#0-2) 

`validate_action_with_mode` performs no additional restriction for `Action::CreateAccount`, trivially returning `Ok(())`: [4](#0-3) 

Nowhere in this path is `account_id.get_account_type()` consulted to reject account IDs that are `NearImplicitAccount`/`EthImplicitAccount`-shaped, unlike `account_is_implicit`, which exists specifically to distinguish these cases. [5](#0-4)  As a result, `action_create_account` creates a bare `Account` (zero balance, no keys) at that address: [6](#0-5) 

This differs from the only intended way to create an implicit account, `action_implicit_account_creation_transfer`, which is invoked exclusively by the `Transfer` action path when the target account does not exist and always installs the corresponding full-access key. [7](#0-6)  Once an attacker races ahead and creates the account via `CreateAccount` first, the account already exists, so any later `Transfer` to that same address will not go through the implicit-creation-with-key path — it just credits the existing key-less account. Since no `AccessKey` was ever registered, no one (not even the holder of the corresponding private key) can subsequently sign a transaction from that account to move the funds.

### Impact Explanation
Funds sent by any third party to an implicit-account address that was pre-empted this way become permanently unspendable, since there is no code path that lets a key-less account authorize any outgoing action. This is a genuine "permanent freezing of user funds" impact. It does not require social engineering of the victim: implicit-account addresses are public by construction (derived deterministically from a public key), so an attacker only needs to observe or predict a target public key/address that a legitimate user or service intends to fund and front-run the first `CreateAccount` receipt at that address before the legitimate funding transfer.

### Likelihood Explanation
Preconditions: the attacker only needs an existing named account to act as predecessor (any funded NEAR account) and knowledge of the target implicit account-id string (derivable from any public key, which is inherently public information, not a secret). Cost is a single `CreateAccount` transaction against the target account_id — cheap and fully repeatable for any target implicit address not yet created. No validator/node privilege, no leaked keys required. The main constraint is timing: the attacker must create the account before the legitimate implicit-account transfer lands, which is feasible when target addresses are publicized in advance (e.g., posted for a deposit) or observable via a pending transaction in the public mempool.

### Recommendation
In `action_create_account`, reject the action outright if `account_id.get_account_type()` is not `AccountType::NamedAccount` (mirroring the intent of `account_is_implicit`), returning an error such as `OnlyImplicitAccountCreationAllowed`/`CreateAccountOnlyByRegistrar` regardless of predecessor, so implicit/eth-implicit-shaped account IDs can only be created through the `Transfer`-triggered `action_implicit_account_creation_transfer` path that always attaches the mandated access key.

### Proof of Concept
Add a unit test in `runtime/runtime/src/actions.rs` (or extend the existing `action_create_account` test module) analogous to `test_action_create_account`:
1. Choose `account_id` = `derive_near_implicit_account_id(pubkey)` (a 64-hex-char string, `get_account_type() == AccountType::NearImplicitAccount`).
2. Set `predecessor_id` to an arbitrary named account (e.g., `"attacker.near"`), not the registrar.
3. Call `action_create_account(...)` and assert that, with the current code, `result.result` is `Ok(())` and `*account` is `Some(Account{ amount: 0, ... })` with no corresponding access key stored — demonstrating the account is created key-less.
4. Follow up with an integration/test-loop scenario: after account creation, execute a `Transfer` action to the same `account_id`; assert the account balance increases but no `AccessKey` exists in state for that account (`get_access_key` returns `None`), proving the deposited funds are unspendable.
5. After applying the fix, the same test should instead assert `ActionErrorKind::OnlyImplicitAccountCreationAllowed` (or equivalent) is returned regardless of predecessor identity.

pub(crate) fn action_create_account(
    fee_config: &RuntimeFeesConfig,
    account_creation_config: &AccountCreationConfig,
    account: &mut Option<Account>,
    actor_id: &mut AccountId,
    account_id: &AccountId,
    predecessor_id: &AccountId,
    result: &mut ActionResult,
) {
    if account_id.is_top_level() {
        if account_id.len() < account_creation_config.min_allowed_top_level_account_length as usize
            && predecessor_id != &account_creation_config.registrar_account_id
        {
            // A short top-level account ID can only be created registrar account.
            result.result = Err(ActionErrorKind::CreateAccountOnlyByRegistrar {
                account_id: account_id.clone(),
                registrar_account_id: account_creation_config.registrar_account_id.clone(),
                predecessor_id: predecessor_id.clone(),
            }
            .into());
            return;
        } else {
            // OK: Valid top-level Account ID
        }
    } else if !account_id.is_sub_account_of(predecessor_id) {
        // The sub-account can only be created by its root account. E.g. `alice.near` only by `near`
        result.result = Err(ActionErrorKind::CreateAccountNotAllowed {
            account_id: account_id.clone(),
            predecessor_id: predecessor_id.clone(),
        }
        .into());
        return;
    } else {
        // OK: Valid sub-account ID by proper predecessor.
    }

    *actor_id = account_id.clone();
    *account = Some(Account::new(
        Balance::ZERO,
        Balance::ZERO,
        AccountContract::None,
        fee_config.storage_usage_config.num_bytes_account,
    ));
}
