This means *any* signer/predecessor can send a `TransferToGasKeyAction` receipt to *any* account's existing gas key — `action_transfer_to_gas_key` (`runtime/runtime/src/access_keys.rs:257-288`) only checks that the named `public_key` resolves to an existing gas key on that account; it does not check who the caller is.

### Title
Unprivileged `TransferToGasKey` griefing can force `DeleteAccount` to permanently fail - ([File: runtime/runtime/src/actions.rs])

### Summary
`TransferToGasKeyAction` can be sent by *any* account to *any* other account's gas key, since `check_actor_permissions` exempts it from the actor==account check [1](#0-0) . `action_delete_account` sums all gas-key balances on the target account and rejects the deletion outright with `GasKeyBalanceTooHigh` if that sum exceeds `GasKeyInfo::MAX_BALANCE_TO_BURN` (1 NEAR) [2](#0-1) . An attacker can front-run (or simply race) a victim's legitimate `DeleteAccount` action by sending small `TransferToGasKeyAction`s to the victim's own gas keys, pushing the aggregate gas-key balance above the 1 NEAR threshold, causing the victim's `DeleteAccount` action to fail every time it is retried — an unprivileged-signer analog of the reported `assert`/precondition-griefing bug class ("any user can top up shared state right before an operation that hard-fails on that state").

### Finding Description
`action_delete_account` computes `gas_key_balance_to_burn = compute_gas_key_balance_sum(state_update, account_id)` and returns a hard error (not a warning, not recoverable within the same receipt) if it exceeds 1 NEAR: [2](#0-1) 
This sum is over *all* gas keys on the account, and any of those keys can be topped up by an unrelated third party because `TransferToGasKeyAction` bypasses the actor-permission gate: [1](#0-0) 
`action_transfer_to_gas_key` itself performs no caller/actor check, only validating that the target public key exists and is a gas key on `account_id`: [3](#0-2) 
The spec confirms this design: gas-key balance is moved only via `TransferToGasKeyAction`/`WithdrawFromGasKeyAction`, and account deletion sums all gas-key balances against the 1 NEAR burn cap, returning `GasKeyBalanceTooHigh` and leaving the account intact on overflow [4](#0-3) . This is directly analogous to the tempus `depositAndFix` bug: a state precondition ("total burnable gas-key balance ≤ 1 NEAR") that a legitimate operation (account deletion) depends on can be violated by an unprivileged third party through an otherwise-benign, permissionless action (`TransferToGasKeyAction`), causing the legitimate operation to fail deterministically and repeatably.

### Impact Explanation
Any account holder wishing to delete their account (e.g., to reclaim locked storage stake via the beneficiary refund) can be permanently blocked by an attacker who watches the mempool/chain for `DeleteAccount` transactions/receipts and repeatedly funds a small amount into any of the victim's gas keys, keeping the aggregate above 1 NEAR. Since gas-key balance burned on deletion is **burned, not refunded** to the account owner (per `access_keys.rs:112` semantics referenced in the spec), the attacker only spends however much it costs to push the cumulative gas-key balance above the (relatively low) 1 NEAR cap, which can be done in small increments across multiple gas keys and re-applied after each failed deletion attempt. The victim's `DeleteAccount` action fails with `ActionErrorKind::GasKeyBalanceTooHigh`, and the account state is left unchanged (`test_delete_account_over_limit_leaves_account_unchanged`-style behavior), meaning the account can be indefinitely prevented from being deleted — a persistent griefing/denial-of-service on this specific operation, though it does not by itself cause fund freezing of the account's main balance (only prevents deletion) and it is a soft protocol error rather than a shard-halting panic.

### Likelihood Explanation
Likelihood is high for an attacker who wants to specifically target a known account: `TransferToGasKeyAction` is a permissionless, cheap, always-available action requiring only knowledge of the victim's account id and one of its gas-key public keys (which are visible on-chain via `ViewGasKeyNonces`/access-key queries). No special privileges, timing races beyond simple front-running, or contract deployment are required. The condition is deterministic (`balance > GasKeyInfo::MAX_BALANCE_TO_BURN`), so a single well-funded attacker transaction executed before the victim's `DeleteAccount` receipt is processed within the same or an earlier block is sufficient, and this can be repeated on every retry.

### Recommendation
Do not let unrelated third parties directly increase gas-key balances that gate the victim's own account-management actions. Consider requiring `TransferToGasKeyAction`'s actor to be the account owner (i.e., add it to the actor-permission-checked group, similar to `DeleteKey`/`DeleteAccount`/`Stake`), or decouple `DeleteAccount`'s hard `GasKeyBalanceTooHigh` failure from attacker-controllable balances (e.g., cap only self-funded/owner-attributable gas-key deposits, or allow deletion to proceed by force-burning above-cap balances rather than aborting the whole action).

### Proof of Concept
1. Victim account `alice.near` has an existing gas key (added via `AddKeyAction` with `AccessKey::gas_key_full_access(..)`), with balance below 1 NEAR.
2. Attacker `mallory.near` observes alice's `DeleteAccount` transaction (or simply targets alice preemptively) and submits `Action::TransferToGasKey(TransferToGasKeyAction { public_key: alice_gas_key_pubkey, deposit: enough_to_exceed_1_near })` as a `mallory.near`-signed transaction/receipt targeting `alice.near`. This succeeds because `check_actor_permissions` does not gate `TransferToGasKey` on `actor_id == account_id` [1](#0-0)  and `action_transfer_to_gas_key` performs no ownership check [3](#0-2) .
3. When alice's `DeleteAccount` action then executes, `compute_gas_key_balance_sum` now exceeds `GasKeyInfo::MAX_BALANCE_TO_BURN`, and `action_delete_account` returns `ActionErrorKind::GasKeyBalanceTooHigh`, leaving alice's account undeleted [2](#0-1) ; this exact scenario is exercised (without the adversarial framing) by `test_delete_account_gas_key_balance_too_high` [5](#0-4) .
4. Mallory can repeat step 2 after every retry by alice, indefinitely blocking account deletion.

pub(crate) fn action_transfer_to_gas_key(
    state_update: &mut TrieUpdate,
    result: &mut ActionResult,
    account_id: &AccountId,
    action: &TransferToGasKeyAction,
) -> Result<(), RuntimeError> {
    let Some(mut access_key) = get_access_key(state_update, account_id, &action.public_key)? else {
        result.result = Err(ActionErrorKind::GasKeyDoesNotExist {
            account_id: account_id.clone(),
            public_key: Box::new(action.public_key.clone()),
        }
        .into());
        return Ok(());
    };
    let Some(gas_key_info) = access_key.gas_key_info_mut() else {
        // Key exists but is not a gas key
        result.result = Err(ActionErrorKind::GasKeyDoesNotExist {
            account_id: account_id.clone(),
            public_key: Box::new(action.public_key.clone()),
        }
        .into());
        return Ok(());
    };

    gas_key_info.balance = gas_key_info.balance.checked_add(action.deposit).ok_or_else(|| {
        RuntimeError::StorageError(StorageError::StorageInconsistentState(
            "gas key balance integer overflow".to_string(),
        ))
    })?;
    set_access_key(state_update, account_id.clone(), action.public_key.clone(), &access_key);
    Ok(())
}
