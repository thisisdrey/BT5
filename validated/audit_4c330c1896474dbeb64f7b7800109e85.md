### Title
Dust-transfer griefing fills victim's `depositTokensOfAccount` to `MAX_TOKENS_PER_USER`, blocking all new deposits/transfers to the victim - (File: contracts/Pool.sol)

### Summary
Any unprivileged account can push an arbitrary victim's per-account token set to the hard cap of `MAX_TOKENS_PER_USER` (30) by sending dust amounts of every registered `DepositToken` via plain `transfer`/`transferFrom`. Once the combined `depositTokensOfAccount` + `debtTokensOfAccount` count reaches the cap, `Pool.addToDepositTokensOfAccount` reverts with `UserReachedMaxTokens`, which makes `DepositToken._mint` and `DepositToken._transfer` revert for any token the victim does not already hold. This mirrors the reported bug class: an unauthenticated, attacker-chosen value (the recipient address) is used as a key in an internal index lookup/mutation, and the resulting state causes a denial of service for a third party who never interacted with the attacker.

### Finding Description
- `Pool` enforces a shared cap: `uint256 public constant MAX_TOKENS_PER_USER = 30` [1](#0-0) .
- Per-account holdings are tracked in `MappedEnumerableSet.AddressSet depositTokensOfAccount` / `debtTokensOfAccount` [2](#0-1) .
- `DepositToken._transfer` calls `pool.addToDepositTokensOfAccount(recipient_)` whenever the recipient's prior balance was zero [3](#0-2) . `transfer`/`transferFrom` are public and only require the *sender's* unlocked balance, not the recipient's consent [4](#0-3) .
- `Pool.addToDepositTokensOfAccount` reverts `UserReachedMaxTokens` once the combined set length hits 30 (confirmed by test at `test/Pool.test.ts` lines 1386-1416, where filling half the cap with deposit tokens and half with debt tokens makes the next add revert).
- The same revert fires inside `_mint` (i.e., `deposit(..., onBehalfOf_ = victim)`) and inside `_transfer` [5](#0-4) .
- Entries are only removed when a balance goes to zero via `removeFromDepositTokensOfAccount` [6](#0-5) , so the attacker can cheaply re-add dust after the victim clears an entry, and can front-run victim deposits to keep the set full.

### Impact Explanation
Temporary freezing of deposits/transfers for a targeted victim: while the victim's set is saturated, (a) the victim cannot deposit any collateral type they don't already hold (`_mint` reverts), (b) no one can `deposit(..., onBehalfOf = victim)` a new collateral (blocking integrations/smart-farming flows that deposit on behalf), and (c) transfers of any new `DepositToken` to the victim revert. Since the cap counts debt tokens too, a victim who legitimately holds some debt positions needs fewer than 30 dust transfers to be fully blocked. No funds are stolen, but this satisfies the "temporary freezing of funds / liveness" acceptance criterion and matches the advisory's impact profile (unauthenticated input → state-corrupting lookup → DoS).

### Likelihood Explanation
- Fully permissionless: `transfer` is a standard public ERC20 entry point; the attacker only needs dust balances of each registered `DepositToken`, obtainable by depositing minimal underlying into each collateral market.
- No privileged role, oracle manipulation, or victim interaction is required.
- Cost scales with the number of registered deposit tokens (governor-capped, so finite and typically small); on low-fee chains the griefing is cheap and repeatable.
- Caveat: the victim can recover by transferring dust balances back out (each zeroed balance removes an entry), so this is a persistent-but-correctable DoS rather than permanent freezing; on chains with higher gas costs, forced gas spend adds to the griefing cost asymmetry in the attacker's favor.

### Recommendation
- Do not revert on set saturation for incoming transfers/mints; instead cap enforcement should apply only to actions that increase the user's *own* risk surface (e.g., only check the cap in paths that create a borrowable position), or allow overflow entries for purely-received balances.
- Alternatively, track account token lists without a hard cap for passive receipts, or make `addToDepositTokensOfAccount` a no-op (return false) instead of reverting when the cap is reached for unsolicited receipts, and compute `debtPositionOf`/collateral over the recorded set with the understanding that unrecorded dust contributes negligible collateral value.
- Note the tradeoff: entries added by received dust do increase `debtPositionOf` iteration cost, so the fix should bound iteration (e.g., ignore dust below a threshold) rather than remove the cap entirely.

### Proof of Concept
Foundry fork/hardhat-style reproduction:

```solidity
// SPDX-License-Identifier: MIT
pragma solidity 0.8.24;

// Assumes a deployed Pool with >= 1 DepositToken (msdX) and the victim
// holding no balance of a second DepositToken (msdY).
function test_dustGriefingBlocksVictimDeposit() public {
    // 1. Attacker deposits a minimal amount of underlying into each of the
    //    pool's deposit tokens to obtain msdToken dust, cycling through
    //    freshly-derived attacker EOAs only if needed (not required here).
    //    For each DepositToken dt_i (i = 1..N where N >=
    //    MAX_TOKENS_PER_USER - victimDebtTokenCount):
    //        dt_i.transfer(victim, 1 wei);

    for (uint256 i; i < depositTokens.length; ++i) {
        DepositToken dt = depositTokens[i];
        underlying[i].approve(address(dt), 1);
        dt.deposit(1, attacker);          // mint dust to attacker
        dt.transfer(victim, 1);           // adds dt to victim's set
    }

    // victim's set is now at MAX_TOKENS_PER_USER
    assertEq(pool.getDepositTokensOfAccount(victim).length +
             pool.getDebtTokensOfAccount(victim).length, 30);

    // 2. Victim tries to deposit a collateral type they do not hold yet:
    //    reverts inside _mint -> addToDepositTokensOfAccount
    vm.expectRevert(UserReachedMaxTokens.selector);
    newDepositToken.deposit(amount, victim);   // or deposit(amount, onBehalfOf=victim) from anyone

    // 3. A plain transfer of a new deposit token to the victim also reverts:
    vm.expectRevert(UserReachedMaxTokens.selector);
    newDepositToken.transfer(victim, 1);
}
```

Validation notes:
- Confirmed reachable: `DepositToken.transfer` → `_transfer` → `pool.addToDepositTokensOfAccount(recipient_)` with an attacker-chosen `recipient_`.
- `addToDepositTokensOfAccount` is gated `onlyDepositToken` (caller must be a registered deposit token — satisfied automatically since the call originates inside the token itself), and `transfer` only checks the sender's `unlockedBalanceOf`, so no guard stops the griefing.
- Only uncertainty: exact revert path inside `Pool.addToDepositTokensOfAccount` (combined deposit+debt set check) was inferred from the test at `test/Pool.test.ts:1386-1416` rather than a direct line read of the function body; behavior is confirmed by that test.
