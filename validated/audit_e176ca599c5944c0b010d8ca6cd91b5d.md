### Title
`remove_account` fails to clean up `PostponedReceipt`/`PendingDataCount`/`PostponedReceiptId` rows, allowing a stale postponed receipt to execute against a recreated account - (File: core/store/src/utils/mod.rs, runtime/runtime/src/actions.rs, runtime/runtime/src/lib.rs)

### Summary
`remove_account` deletes the `Account`, `ContractCode`, access keys, gas-key nonces, and `ContractData` rows for a deleted account, but never enumerates or removes `TrieKey::PostponedReceipt`, `TrieKey::PendingDataCount`, or `TrieKey::PostponedReceiptId` rows keyed by that account's `receiver_id`. If a multi-dependency promise (`promise_and`) is outstanding when the account is deleted and then recreated, the still-pending `DataReceipt` later completes the dependency count and dequeues the stale postponed `ActionReceipt`, which then executes against the freshly created account.

### Finding Description
`action_delete_account` (`runtime/runtime/src/actions.rs:314-390`) calls `remove_account` and simply sets `*account = None`: [1](#0-0) 

`remove_account` (`core/store/src/utils/mod.rs:504-575`) only removes `Account`, `ContractCode`, access keys / gas-key nonces, and `ContractData`: [2](#0-1) 

It does not touch `TrieKey::PostponedReceipt`, `TrieKey::PendingDataCount`, or `TrieKey::PostponedReceiptId` (trie columns 4, 5, 6, see `core/primitives/src/trie_key.rs:33-41`). These rows are keyed by `{receiver_id, receipt_id}` / `{receiver_id, data_id}` and were written earlier by `process_action_receipt` when a `FunctionCall` triggers `promise_and` with unmet `input_data_ids`: [3](#0-2) 

When a `DataReceipt` later arrives, `process_receipt` looks up `PostponedReceiptId` purely by `receiver_id`+`data_id`, decrements `PendingDataCount`, and once it reaches zero, fetches and executes the stored postponed `ActionReceipt` unconditionally — there is no check that the account named by `receiver_id` is the same account (by any generation/creation marker) that existed when the receipt was postponed: [4](#0-3) 

Exploit flow:
1. Attacker's contract on account `X` issues two cross-contract calls via `promise_and`, creating a postponed `ActionReceipt` with `PendingDataCount = 2` for `X` (`lib.rs:1608-1655`).
2. One `DataReceipt` arrives, decrementing the count to 1 (`lib.rs:1456-1472`); the postponed receipt row persists.
3. Attacker (owning `X`'s full access key) submits `DeleteAccountAction` on `X`, which runs `remove_account` — this leaves the `PostponedReceipt`/`PendingDataCount`/`PostponedReceiptId` rows for `X` untouched (`core/store/src/utils/mod.rs:504-575`).
4. Attacker submits `CreateAccountAction` recreating `X` (fresh storage, potentially with different keys, or grabbed by a different account holder since the name became available after deletion).
5. The second `DataReceipt` arrives; `pending_data_count` reaches 0, the stale postponed receipt (whose actions/predecessor were fixed at step 1, before deletion) is fetched and executed via `apply_action_receipt` against the newly created account's storage/state (`lib.rs:1442-1455`).

No existing check in `process_receipt`/`process_action_receipt`/`remove_account` verifies account continuity, so the postponed receipt's actions run with its original privileges (e.g. a self-callback receipt trusted as coming from `predecessor_id == account_id`) against an account that may be under different control after recreation.

### Impact Explanation
This breaks the "authorization exactness" and "determinism" invariants: a receipt created under one incarnation of account `X` is delivered to and executed against a later, unrelated incarnation of the same account ID. Because NEAR treats an action receipt whose `predecessor_id == receiver_id` as a privileged self-call, the stale receipt can carry over self-call-level privileges (e.g. `AddKey`, `DeleteKey`, `Transfer`, `FunctionCall`) into the new account context — enabling authorization escalation across account "generations," and, if a different party recreates the account name after it becomes available, escalation across accounts/promises. This corresponds to the "authorization escalation across accounts or promises" bounty category. There is also a latent apply-path panic/inconsistency risk if any resolve logic implicitly assumes the account existed continuously, though the retrieved code paths (`get_postponed_receipt`/`remove_postponed_receipt`) do not themselves panic on this scenario since they don't check account continuity — they merely execute the receipt unconditionally.

### Likelihood Explanation
- Preconditions are ordinary, unprivileged actions: deploying a contract that calls `promise_and`, and issuing `DeleteAccountAction`/`CreateAccountAction` transactions signed with the account's own full access key — no validator/node/network privilege required.
- Feasibility depends on real-world timing: the attacker needs the account deletion+recreation to complete in the window between the first and second `DataReceipt` arriving, which is plausible for cross-shard/cross-contract calls that can span multiple blocks.
- Repeatable: the attacker fully controls when to issue the two cross-contract calls and can engineer arbitrary delay on the second callback (e.g., an intermediate contract that defers its response), maximizing the window.
- Cost is limited to gas and the account recreation/storage-staking deposit, both of which are typical low-value transaction costs.

### Recommendation
`remove_account` should enumerate and remove all `TrieKey::PostponedReceipt`, `TrieKey::PendingDataCount`, and `TrieKey::PostponedReceiptId` rows whose `receiver_id` matches the account being deleted (mirroring the existing access-key/gas-key/contract-data cleanup loops), and any output `DataReceipt`s destined to complete those postponed receipts should either be dropped or the postponed receipt discarded when its receiver account no longer exists.

### Proof of Concept
Unit test on `remove_account`:
- Set up `state_update` with `Account`, and a `PostponedReceipt`/`PendingDataCount` pair for `account_id` (via `set_postponed_receipt`/`set` as in `core/store/src/genesis/state_applier.rs:373-412`).
- Call `remove_account(state_update, &account_id)`.
- Assert `get_postponed_receipt(state_update, &account_id, receipt_id)` returns `None` and the `PendingDataCount`/`PostponedReceiptId` rows are gone (currently they will still be present, showing the bug).

Integration test (runtime apply-loop, modeled on `test_promise_input_size_limit_exceeded_fails_and_cleans_up` in `runtime/runtime/src/tests/apply.rs:5038-5096`):
1. Apply an `ActionReceipt` on `alice_account()` with `promise_and`-style `input_data_ids: [data_id_1, data_id_2]` and a self-callback action list (e.g. `AddKey`).
2. Apply `data_id_1`'s `DataReceipt`; assert `PendingDataCount == 1` and postponed receipt still present.
3. Apply `DeleteAccountAction` then `CreateAccountAction` on `alice_account()` in subsequent receipts/blocks.
4. Apply `data_id_2`'s `DataReceipt`.
5. Assert that the callback (e.g. `AddKey`) does NOT execute against the newly created account, or that the postponed receipt is discarded rather than applied — currently it will execute, demonstrating the vulnerability.

/// Removes account, code and all access keys and gas keys associated to it.
pub fn remove_account(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
) -> Result<RemoveAccountResult, StorageError> {
    state_update.remove(TrieKey::Account { account_id: account_id.clone() });
    state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });

    let mut gas_key_nonce_count: usize = 0;
    let mut gas_key_nonce_total_key_bytes: usize = 0;

    // Removing access keys and gas key nonces
    let lock = state_update.trie().lock_for_iter();
    let mut keys_to_remove: Vec<TrieKey> = Vec::new();
    for raw_key in state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_access_keys(account_id), &lock)?
    {
        let raw_key = raw_key?;
        let key_handle = trie_key_parsers::parse_key_handle_from_access_key_key(
            &raw_key, account_id,
        )
        .map_err(|_e| {
            StorageError::StorageInconsistentState(
                "Can't parse key handle from raw key for AccessKey".to_string(),
            )
        })?;
        let nonce_index =
            trie_key_parsers::parse_nonce_index_from_gas_key_key(&raw_key, account_id, &key_handle)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse nonce index from raw key for AccessKey".to_string(),
                    )
                })?;
        if let Some(index) = nonce_index {
            gas_key_nonce_count += 1;
            gas_key_nonce_total_key_bytes += raw_key.len();
            keys_to_remove.push(TrieKey::gas_key_nonce(
                account_id.clone(),
                key_handle.clone(),
                index,
            ));
        } else {
            keys_to_remove.push(TrieKey::access_key(account_id.clone(), key_handle.clone()));
        }
    }
    drop(lock);

    for trie_key in keys_to_remove {
        state_update.remove(trie_key);
    }

    // Removing contract data
    let lock = state_update.trie().lock_for_iter();
    let data_keys = state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_contract_data(account_id, &[]), &lock)?
        .map(|raw_key| {
            trie_key_parsers::parse_data_key_from_contract_data_key(&raw_key?, account_id)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse data key from raw key for ContractData".to_string(),
                    )
                })
                .map(Vec::from)
        })
        .collect::<Result<Vec<_>, _>>()?;
    drop(lock);

    for key in data_keys {
        state_update.remove(TrieKey::ContractData { account_id: account_id.clone(), key });
    }
    Ok(RemoveAccountResult { gas_key_nonce_count, gas_key_nonce_total_key_bytes })
}
