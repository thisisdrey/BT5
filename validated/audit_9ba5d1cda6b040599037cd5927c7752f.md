### Title
Legacy (non-hardened) AMM exchange math allows a trader to drive a bancor-exchange token reserve negative, minting unbacked tokens — `ExchangeCapsule.transaction` / `ExchangeProcessor` - (File: chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java)

### Summary
The audited dForce bug is a utilization-rate formula that implicitly assumes `reserves <= cash`; when that invariant is not enforced, the ratio can exceed its intended bound (`>1`), corrupting downstream logic. java-tron's TRX/TRC10 bancor-style `Exchange` market has the analogous unenforced invariant: the AMM balances (`firstTokenBalance`, `secondTokenBalance`) are assumed to always stay `>= 0`, but this is only checked in an opt-in "hardened" code path. In the default/legacy path, a single `ExchangeTransactionContract` (or `ExchangeInjectContract`/`ExchangeWithdrawContract`) from any unprivileged account can push a pool balance negative without any validation, corrupting the pool's internal reserve accounting.

### Finding Description
`ExchangeCapsule.transaction()` computes new pool balances using the bancor-style `Processor` (`ExchangeProcessor`/`SafeExchangeProcessor`) and only validates non-negativity when `hardenedCalc` is true: [1](#0-0) 

```
if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
  throw new ContractValidateException("Exchange balance must be >=0 after transaction");
}
```
When `hardenedCalc` is false (the default/legacy math path, `allowHarden()` off), the computed `newFirstTokenBalance`/`newSecondTokenBalance` are persisted unconditionally, with **no** check that they remain non-negative: [2](#0-1) 

The legacy `ExchangeProcessor` computes the traded amount via floating-point power functions: [3](#0-2) 

For a sufficiently large `sellTokenQuant` relative to the pool's `sellTokenBalance`, `exchangeToSupply` (using `Math.pow(1+quant/newBalance, 0.0005)`) and `exchangeFromSupply` (using `Math.pow(1+supplyQuant/supply, 2000)`) can produce a `buyTokenQuant` that exceeds the actual `buyTokenBalance` held by the pool, especially given floating point/precision effects around the exponent 2000. Because the legacy path never validates `newSecondTokenBalance >= 0` (unlike the hardened path added later, mirroring the analogous dForce fix), this "cash minus reserves went negative" analog is fully reachable.

`ExchangeTransactionActuator.execute()`/`doValidate()` call `exchangeCapsule.transaction(tokenID, tokenQuant, dynamicStore.allowStrictMath(), allowHarden())` and, on the non-hardened path, unconditionally credit the trader with `anotherTokenQuant` via `addAssetAmountV2`/`setBalance`, then persist the (now negative-balance) exchange capsule: [4](#0-3) [5](#0-4) 

Neither `doValidate()` nor `execute()` independently checks that the counter-token balance in the pool is sufficient to cover `anotherTokenQuant` before crediting the trader — the only safety net is the `hardenedCalc` branch in `ExchangeCapsule.transaction()`, which is gated by `allowHarden()`.

### Impact Explanation
If `allowHarden()`/the hardened exchange-calculation flag is not active for a given exchange path, an unprivileged trader can broadcast a normal `ExchangeTransactionContract` transaction that:
1. Drains more of the counter-token from the pool than the pool actually holds (analogous to `UR > 1`, i.e., "reserves > cash").
2. Credits their own account (`addAssetAmountV2`/`setBalance`) with tokens/TRX that are not backed by the pool's real balance — an unbacked-balance/theft condition for whichever asset the pool is shorted on.
3. Persists a permanently corrupted `ExchangeCapsule` (negative `firstTokenBalance`/`secondTokenBalance`), which is stored via `Commons.putExchangeCapsule`, breaking all subsequent trades, injects, and withdrawals on that exchange (a de-facto permanent halt of that exchange, and permanent freezing of the other liquidity providers' funds in the pool since it can no longer function coherently).

This satisfies the "unbacked balance" and "permanent freezing of funds" criteria called for by the validation rules.

### Likelihood Explanation
The trigger condition is entirely a function of the caller-supplied `tokenQuant` and the current pool balances; both are attacker/user controlled or observable via public state, and the only actuator-level checks are `tokenQuant > 0`, `tokenExpected > 0`, `balanceLimit` on the *sold* side, and asset-balance sufficiency on the *trader's own* account for the token being sold — none of which bound `anotherTokenQuant` against the buy-side pool's actual balance in the non-hardened path. Reaching this requires only a single signed `ExchangeTransactionContract` (or Inject/Withdraw variants using the same `transaction()`/AMM math) from any account, with no special permission — matching the in-scope class of "exchange and market order handling" reachable by any order placer.

### Recommendation
Make the non-negativity/invariant check in `ExchangeCapsule.transaction()` unconditional rather than gated behind `hardenedCalc`/`allowHarden()`, i.e., always reject a trade/inject/withdraw that would drive `firstTokenBalance` or `secondTokenBalance` negative, matching recommendation (2) from the referenced report: clamp/bound the computed reserve values so an unenforced arithmetic assumption cannot silently produce out-of-range (negative) pool state. Additionally, add an explicit actuator-level check in `ExchangeTransactionActuator`/`ExchangeInjectActuator`/`ExchangeWithdrawActuator` that `anotherTokenQuant <= currentAnotherTokenBalance` before crediting the trader, independent of which math path computed it.

### Proof of Concept
Conceptual PoC (requires confirming exact overflow/precision constants against `ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply`, which could not be fully re-derived analytically in this review):
1. Create/observe an `Exchange` with small `secondTokenBalance` (e.g., near the minimum permitted) and much larger `firstTokenBalance`.
2. As any account holding the first token, broadcast `ExchangeTransactionContract` selling a large `tokenQuant` of the first token, with `allowHarden()`/the hardened exchange flag disabled for the deployment (legacy default), relying on the `Math.pow(..., 2000)` blow-up in `ExchangeProcessor.exchangeFromSupply` to compute `anotherTokenQuant > secondTokenBalance`.
3. `ExchangeTransactionActuator.execute()` calls `exchangeCapsule.transaction(...)`, which (legacy path) sets `newSecondTokenBalance = secondTokenBalance - buyTokenQuant` without a negativity check, persists it via `Commons.putExchangeCapsule`, and credits the trader's account with `anotherTokenQuant` — tokens not actually backed by the pool.

Because I could not execute the JVM arithmetic directly to confirm the precise input magnitudes that trigger the overshoot in this environment, this PoC is described at the logic level; a background engineering session with code-execution access is needed to construct concrete numeric inputs (`sellBalance`, `buyBalance`, `sellQuant`) that reproduce `newSecondTokenBalance < 0` under the legacy (non-hardened) `ExchangeProcessor` path and confirm end-to-end exploitability against `ExchangeTransactionActuator`.

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
