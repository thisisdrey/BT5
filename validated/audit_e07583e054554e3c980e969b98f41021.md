### Title
Unbounded array allocation from attacker-controlled length word in `ValidateMultiSign`/`BatchValidateSign` precompiles - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The ALPINE-CVE-2021-32762 root cause is that hiredis/redis-cli allocates a buffer with `calloc()` sized from an attacker-supplied length field taken directly off the wire, without checking that the length is sane/bounded before allocating. `PrecompiledContracts.extractBytesArray` and `extractSigArray` in java-tron have the same pattern: a length is read from calldata and used to size a Java array before any check that the calldata actually contains that many elements.

### Finding Description
`extractBytesArray` and `extractSigArray` read a length word directly from the decoded `DataWord[] words` array (itself parsed from the raw TVM calldata) and immediately allocate an array of that size: [1](#0-0) [2](#0-1) 

`len` comes from `words[offset].intValueSafe()`, which is fully attacker-controlled via the calldata word at that offset — it does not have to correspond to the actual amount of bytes present in the call. The allocation `new byte[len][]` happens **before** any bounds check against the real size of `words`/`data`.

These helpers are invoked from `ValidateMultiSign.execute()` and `BatchValidateSign.doExecute()`: [3](#0-2) [4](#0-3) 

Note that the `MAX_SIZE` guard (`sigArraySize > MAX_SIZE`) that limits the length before extraction is only applied `if (VMConfig.allowTvmSelfdestructRestriction())`. When that specific hard-fork flag is not active, both precompiles fall back to calling `extractBytesArray`/`extractSigArray` directly with **no bound whatsoever** on the attacker-supplied `len`, exactly mirroring the hiredis pattern of allocating from an unchecked size field before validating it against actual available data.

The energy charged for the call is computed from `data.length` only (`getEnergyForData`), not from the claimed `len` inside the calldata words, so a caller can submit a short, cheap calldata blob whose embedded length word claims an enormous array size (up to `Integer.MAX_VALUE`), and the JVM will attempt to allocate a correspondingly huge object-reference array (`new byte[len][]`) before any subsequent index check has a chance to fail.

### Impact Explanation
A crafted contract call to the `ValidateMultiSign` (address `0x...a`) or `BatchValidateSign` (address `0x...9`) precompile with `len` set near `Integer.MAX_VALUE` forces the node to attempt an allocation on the order of gigabytes for a single, cheaply-energy-charged call. This can trigger `OutOfMemoryError` on the executing node. In `ValidateMultiSign.execute()`, the extraction call at lines 1072-1074 sits **outside** any try/catch (the try/catch only wraps the later permission-check block), so an `OutOfMemoryError` thrown there is not gracefully handled and propagates, which can destabilize or crash the block-processing thread/node — a node-crash/halt condition.

### Likelihood Explanation
Reachable by any unprivileged account that can call a contract invoking the `batchvalidatesign`/`validatemultisign` precompiles (address `0x9`/`0xa`), which are exposed once `VMConfig.allowTvmSolidity059()` is enabled — this has long been active on mainnet, so the precompiles themselves are reachable by any contract call. The severity of this specific analog, however, is conditional on `VMConfig.allowTvmSelfdestructRestriction()` being disabled, since that flag gates the `MAX_SIZE` check that was added specifically to bound `len` before calling `extractBytesArray`/`extractSigArray`. I could not confirm from the available code whether this flag defaults to enabled on all currently running production networks (it is a governance-activated hard-fork switch); on networks/chains where it has not yet been activated (e.g., new private/consortium chains bootstrapped from this code, or during the window before mainnet activation), the unbounded path is directly reachable.

### Recommendation
- Move the `MAX_SIZE` bound check (`sigArraySize`/`addrArraySize`/`len`) so it applies unconditionally, not only under `allowTvmSelfdestructRestriction()`.
- Validate `len` against the real size of the `words` array (or `data.length`) inside `extractBytesArray`/`extractSigArray`/`extractBytes32Array` *before* allocating `new byte[len][]`, e.g. `if (len < 0 || len > (words.length - offset - 1)) return new byte[0][];`.
- Wrap the extraction calls in `ValidateMultiSign.execute()` in the same defensive try/catch used elsewhere in the file, converting unexpected `Throwable`/`OutOfMemoryError` into a safe `DATA_FALSE` result rather than letting it propagate.

### Proof of Concept
1. Build calldata for `validatemultisign(address,uint256,bytes32,bytes[])` where the dynamic `bytes[]` array's length-prefix word (at the offset pointed to by `words[3]`) is set to `0x7FFFFFFF` instead of the real number of signatures, while keeping the rest of the calldata minimal (few hundred bytes).
2. With `VMConfig.allowTvmSelfdestructRestriction()` disabled (its default/pre-activation state on a fresh network), invoke this precompile via a contract `staticcall`/`call` to address `0x000...a`.
3. `ValidateMultiSign.execute()` calls `extractBytesArray(words, offset, rawData)`, which executes `new byte[0x7FFFFFFF][]`, attempting an allocation of over a billion object references, causing `OutOfMemoryError` outside any surrounding try/catch, propagating up through TVM execution.

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
