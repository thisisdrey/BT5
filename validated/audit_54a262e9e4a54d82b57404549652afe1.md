### Title
Unguarded BigInteger division by zero in `EnergyProcessor.calculateGlobalEnergyLimit()` can throw an uncaught `ArithmeticException` during TVM contract execution - (File: chainbase/src/main/java/org/tron/core/db/EnergyProcessor.java)

### Summary
The CVE describes a division-by-zero crash in UPX's ELF parser (`PackLinuxElf64::invert_pt_dynamic()`), a classic "unchecked divisor from attacker-influenced state" bug class. The closest reachable analog in java-tron is in the resource-accounting code that computes an account's energy limit whenever a smart contract is invoked: `EnergyProcessor.calculateGlobalEnergyLimit()` relies on a Java `assert` statement — which is compiled out and never executes unless the JVM is started with `-ea` — to guard against a zero divisor before performing a `BigInteger` division.

### Finding Description
`calculateGlobalEnergyLimit()` reads `totalEnergyWeight` from `DynamicPropertiesStore` and only skips the division when `dynamicPropertiesStore.allowNewReward()` is true: [1](#0-0) 

```
long totalEnergyWeight = dynamicPropertiesStore.getTotalEnergyWeight();
if (dynamicPropertiesStore.allowNewReward() && totalEnergyWeight <= 0) {
  return 0;
} else {
  assert totalEnergyWeight > 0;
}
if (hardenCalculation()) {
  return calculateGlobalLimitV1(frozeBalance, totalEnergyLimit, totalEnergyWeight);
}
```

When `allowNewReward()` is false, the only protection against `totalEnergyWeight == 0` is the `assert` statement, which by default is a no-op in a production JVM (assertions are disabled unless `-ea` is explicitly passed). If `hardenCalculation()` (i.e. `allowHardenResourceCalculation`) is enabled and `totalEnergyWeight` is `0`, execution falls through to `calculateGlobalLimitV1`, which performs an unguarded `BigInteger` division: [2](#0-1) 

```
protected long calculateGlobalLimitV1(long frozeBalance,
    long totalLimit, long totalWeight) {
  long weight = frozeBalance / TRX_PRECISION;
  return BigInteger.valueOf(weight)
      .multiply(BigInteger.valueOf(totalLimit))
      .divide(BigInteger.valueOf(totalWeight))
      .longValueExact();
}
```

`BigInteger.divide()` with a zero divisor throws `ArithmeticException`, which is not caught anywhere in this path. `calculateGlobalEnergyLimit()` is invoked from `EnergyProcessor.useEnergy()`, which is reached on every single call/creation of a smart contract that consumes energy: [3](#0-2) 

By contrast, the sibling method `calculateGlobalEnergyLimitV2` (used when `supportUnfreezeDelay()` is enabled) does have an explicit runtime check (`if (totalEnergyWeight == 0) return 0;`), confirming that the missing check in the V1/legacy path is an oversight rather than an intentional invariant: [4](#0-3) 

`totalEnergyWeight` is a globally shared chain state value (`DynamicPropertiesStore.TOTAL_ENERGY_WEIGHT`) that is incremented and decremented by ordinary, unprivileged freeze/unfreeze/delegate resource transactions network-wide: [5](#0-4) 

On a network/shard where total frozen-for-energy balance can reach exactly zero (e.g., private/test networks, new sidechains, or after coordinated mass-unfreezing under `supportAllowCancelAllUnfreezeV2`), any subsequent `TriggerSmartContract`/`CreateSmartContract` transaction that reaches `useEnergy()` with `hardenCalculation()` enabled and `allowNewReward()` disabled would throw an uncaught `ArithmeticException`.

### Impact Explanation
An uncaught `ArithmeticException` thrown during `useEnergy()`/`calculateGlobalEnergyLimit()` is not a normal EVM revert path guarded by the VM's opcode-level try/catch (unlike `DataWord.div`/`sDiv`, which explicitly check `isZero()` before dividing — see `common/src/main/java/org/tron/common/runtime/vm/DataWord.java:353-362`). Because this check occurs in resource accounting *before* the TVM interpreter loop even begins (called from actuator-level code, not `VM.play()`'s opcode dispatch), the exception is a `RuntimeException` outside the sandboxed opcode execution try/catch, and it is unclear whether it is caught by the surrounding transaction-processing try/catch in `Manager.processTransaction`/actuator `execute()`. If unhandled at that layer, it would propagate to `Manager.processBlock()`, potentially causing a node to fail to apply a block (denial of service / chain halt for that node), which matches the CVE's "crash leading to denial of service" impact class.

### Likelihood Explanation
This requires a specific but not implausible network state: `totalEnergyWeight == 0` combined with `hardenCalculation()` (`allowHardenResourceCalculation`) enabled and `allowNewReward()` disabled. This is a config-dependent, state-dependent condition rather than something a single unprivileged transaction can force directly, so likelihood on a mature mainnet with active frozen balances is low, but is plausible on smaller/private/test networks or transitional periods around feature-flag rollouts.

### Recommendation
Replace the `assert totalEnergyWeight > 0;` guard in `EnergyProcessor.calculateGlobalEnergyLimit()` with an explicit runtime check (`if (totalEnergyWeight <= 0) return 0;`), matching the pattern already used in `calculateGlobalEnergyLimitV2` and in `BandwidthProcessor`'s equivalent checks, so that a zero divisor never reaches `calculateGlobalLimitV1`'s `BigInteger.divide()`.

### Proof of Concept
Not independently executable from the index alone (requires driving live chain state to `totalEnergyWeight == 0` under `allowHardenResourceCalculation=1` and `allowNewReward=0`, then submitting a `TriggerSmartContract`); this mirrors the existing repo test `CalculateGlobalLimitHardenTest` pattern (which already demonstrates `ArithmeticException` being thrown by the hardened path under an overflow condition), but a dedicated test setting `totalEnergyWeight=0` and `allowNewReward=0` would need to be run to confirm whether the resulting exception is caught gracefully or propagates to `Manager.processBlock()`.   public long calculateGlobalEnergyLimit(AccountCapsule accountCapsule) {
    long frozeBalance = accountCapsule.getAllFrozenBalanceForEnergy();
    if (dynamicPropertiesStore.supportUnfreezeDelay()) {
      return calculateGlobalEnergyLimitV2(frozeBalance);
    }
    if (frozeBalance < TRX_PRECISION) {
      return 0;
    }

    long totalEnergyLimit = dynamicPropertiesStore.getTotalEnergyCurrentLimit();
    long totalEnergyWeight = dynamicPropertiesStore.getTotalEnergyWeight();
    if (dynamicPropertiesStore.allowNewReward() && totalEnergyWeight <= 0) {
      return 0;
    } else {
      assert totalEnergyWeight > 0;
    }
    if (hardenCalculation()) {
      return calculateGlobalLimitV1(frozeBalance, totalEnergyLimit, totalEnergyWeight);
    }
    long energyWeight = frozeBalance / TRX_PRECISION;
    return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
  }
