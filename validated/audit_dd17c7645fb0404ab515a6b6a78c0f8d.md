Based on my investigation, the strongest analog to the reported bug class ("callback trusts caller-supplied identity/parameters without verifying the call was actually initiated by the entity it expects") in this Gitaly codebase is in the `ObjectPoolService.LinkRepositoryToObjectPool` RPC.

### Title
Missing ownership/ correlation check in `LinkRepositoryToObjectPool` allows cross-repository object pool linking - (File: internal/gitaly/service/objectpool/link.go)

### Summary
`LinkRepositoryToObjectPool` accepts a `Repository` and an `ObjectPool` from the request and links them via Git alternates without ever verifying that the two are supposed to belong together (e.g., that the pool was created from, or is otherwise associated with, the target repository). The only checks performed are that the target repository is a valid, existing repository and that the object pool is a *valid pool repository* — not that the caller/repository is authorized to join *that specific* pool.

### Finding Description
`LinkRepositoryToObjectPool` validates only structural well-formedness of its inputs: [1](#0-0) 

`s.poolForRequest` in turn only checks that the pool repository is a syntactically valid pool (exists, lives under the pools directory, passes `locator.ValidateRepository`): [2](#0-1) [3](#0-2) 

Nowhere in this call chain is there a check correlating the `ObjectPool` with the `Repository` being linked — e.g., that the pool was created via `CreateObjectPool` *from* this repository, that the pool belongs to the same project/namespace, or that a partitioning hint ties them together. The actual linking (`Link`) simply writes the given pool's path into the repository's `objects/info/alternates` file: [4](#0-3) 

This mirrors the reported bug class: just as `executeOperation`/`onFlashLoan` trusted that `params`/`data` (containing sensitive `msg.sender`-equivalent data) could only have been set by a legitimate call chain (`swapCollateral` → flash loan provider → callback) but never checked `initiator == address(this)`, Gitaly's `LinkRepositoryToObjectPool` trusts that the caller (GitLab Rails) would only ever supply a `Repository`/`ObjectPool` pair that are legitimately related, but performs no such verification itself. Any caller capable of invoking this RPC with an arbitrary, but *structurally valid*, `ObjectPool` value can link an unrelated repository to it.

Design documentation confirms pools are meant to be tied to specific member repositories and that member management is described as caller-trusted, not enforced by Gitaly: [5](#0-4) 

### Impact Explanation
Git alternates grant the linked repository full read access to every object in the alternate (pool) repository's object database — this is how "deduplication" works, but it is also a direct object-access primitive. If a caller can supply an object pool relative path that belongs to a different, unrelated (and potentially private) repository, the target repository gains permanent read access to all of that pool's objects (commits, blobs, trees) through normal Git operations (`git cat-file`, `git log`, clone/fetch of the linked repo), constituting a cross-repository private-object disclosure. This aligns with the "cross-repository object access" and "object-pool and alternates isolation" categories explicitly in scope.

### Likelihood Explanation
Exploitability depends entirely on whether the caller of this Gitaly RPC (normally GitLab Rails, acting on behalf of a user action like fork creation) can be induced to send an `ObjectPool` value that does not correspond to the target repository — e.g., through a crafted/replayed internal API request or a Rails-side bug that reuses a stale/guessable pool relative path. Because Gitaly itself performs no cross-check between `Repository` and `ObjectPool`, any weakness or oversight in the calling layer's parameter construction directly translates into a security bypass at the Gitaly layer with no defense-in-depth. I could not fully verify within this codebase whether GitLab Rails enforces strict ownership checks before calling this RPC (that logic lives outside this repository), which limits my confidence in the concrete end-to-end reachability from an "ordinary user" fork/import action; I flag this as unresolved uncertainty.

### Recommendation
Add an explicit check in `LinkRepositoryToObjectPool` (or in `poolForRequest`) that the object pool is actually associated with the target repository — for example, verifying the pool's storage/partition assignment matches the repository's expected partition (as is already computed by `beginTransactionForRepository`'s "additional repository" partitioning logic), or requiring an explicit, previously recorded pool-membership record rather than trusting the request's `ObjectPool` field outright. This is the direct analog of "requiring `initiator == address(this)`" — verify the relationship was legitimately established by Gitaly itself rather than trusting caller-supplied identifiers.

### Proof of Concept
Not independently reproducible from static analysis alone since it requires control over, or a bug in, the internal API layer (GitLab Rails) that issues `LinkRepositoryToObjectPoolRequest`. Conceptually: call `LinkRepositoryToObjectPool` with `Repository = <attacker's repo>` and `ObjectPool = <existing pool belonging to a private, unrelated repository>`; Gitaly will accept it (both pass their independent validity checks) and write the pool's path into the attacker repo's `objects/info/alternates`, after which `git cat-file`/`git log` against any object ID from the private pool succeeds from the attacker's repository.

**Caveat:** I was not able to confirm from the Gitaly repository alone whether GitLab Rails independently enforces ownership before issuing this RPC, since that logic is outside this codebase. This is flagged as an open uncertainty rather than a confirmed end-to-end exploit.

func (s *server) LinkRepositoryToObjectPool(ctx context.Context, req *gitalypb.LinkRepositoryToObjectPoolRequest) (*gitalypb.LinkRepositoryToObjectPoolResponse, error) {
	repository := req.GetRepository()
	if err := s.locator.ValidateRepository(ctx, repository); err != nil {
		return nil, structerr.NewInvalidArgument("%w", err)
	}

	pool, err := s.poolForRequest(ctx, req)
	if err != nil {
		return nil, err
	}

	repo := s.localRepoFactory.Build(repository)

	if err := pool.Link(ctx, repo); err != nil {
		return nil, structerr.NewInternal("%w", err)
	}

	return &gitalypb.LinkRepositoryToObjectPoolResponse{}, nil

func (s *server) poolForRequest(ctx context.Context, req PoolRequest) (*objectpool.ObjectPool, error) {
	pool, err := objectpool.FromProto(ctx, s.logger, s.locator, s.gitCmdFactory, s.catfileCache, s.txManager, s.housekeepingManager, req.GetObjectPool())
	if err != nil {
		if errors.Is(err, objectpool.ErrInvalidPoolDir) {
			return nil, errInvalidPoolDir
		}

		if errors.Is(err, objectpool.ErrInvalidPoolRepository) {
			return nil, structerr.NewFailedPrecondition("%w", err)
		}

		return nil, structerr.NewInternal("%w", err)
	}

	return pool, nil

// FromProto returns an object pool object from its Protobuf representation. This function verifies
// that the object pool exists and is a valid pool repository.
func FromProto(
	ctx context.Context,
	logger log.Logger,
	locator storage.Locator,
	gitCmdFactory gitcmd.CommandFactory,
	catfileCache catfile.Cache,
	txManager transaction.Manager,
	housekeepingManager housekeepingmgr.Manager,
	proto *gitalypb.ObjectPool,
) (*ObjectPool, error) {
	poolPath, err := locator.GetRepoPath(ctx, proto.GetRepository(), storage.WithRepositoryVerificationSkipped())
	if err != nil {
		return nil, err
	}

	if !storage.IsPoolRepository(proto.GetRepository()) {
		// When creating repositories in the ObjectPool service we will first create the
		// repository in a temporary directory. So we need to check whether the path we see
		// here is in such a temporary directory and let it pass.
		tempDir, err := locator.TempDir(proto.GetRepository().GetStorageName())
		if err != nil {
			return nil, fmt.Errorf("getting temporary storage directory: %w", err)
		}

		if !strings.HasPrefix(poolPath, tempDir) {
			return nil, ErrInvalidPoolDir
		}
	}

	pool := &ObjectPool{
		Repo:                localrepo.New(logger, locator, gitCmdFactory, catfileCache, proto.GetRepository()),
		logger:              logger,
		locator:             locator,
		gitCmdFactory:       gitCmdFactory,
		txManager:           txManager,
		housekeepingManager: housekeepingManager,
	}

	if !pool.IsValid(ctx) {
		return nil, ErrInvalidPoolRepository
	}

	return pool, nil
}

// Link will link the given repository to the object pool. This is done by writing the object pool's
// path relative to the repository into the repository's "alternates" file. This does not trigger
// deduplication, which is the responsibility of the caller.
func Link(ctx context.Context, pool, repo *localrepo.Repo, txManager transaction.Manager) (returnedErr error) {
	altPath, err := repo.InfoAlternatesPath(ctx)
	if err != nil {
		return err
	}

	expectedRelPath, err := getRelativeObjectPath(ctx, pool, repo)
	if err != nil {
		return err
	}

	linked, err := linkedToRepository(ctx, pool, repo)
	if err != nil {
		return err
	}

	if linked {
		// When the repository is already linked to the repository, cast a vote to ensure the
		// repository is consistent with the other replicas.
		if err := transaction.VoteOnContext(ctx, txManager, voting.VoteFromData([]byte("repository linked")), voting.Synchronized); err != nil {
			return fmt.Errorf("vote on linked repository: %w", err)
		}

		return nil
	}

	alternatesWriter, err := safe.NewLockingFileWriter(altPath)
	if err != nil {
		return fmt.Errorf("creating alternates writer: %w", err)
	}
	defer func() {
		if err := alternatesWriter.Close(); err != nil && returnedErr == nil {
			returnedErr = fmt.Errorf("closing alternates writer: %w", err)
		}
	}()

	if _, err := io.WriteString(alternatesWriter, expectedRelPath); err != nil {
		return fmt.Errorf("writing alternates: %w", err)
	}

// ObjectPoolService is a service that manages the lifetime of object pools.
//
// An object pool is a separate repository that can be linked to from multiple object pool members
// in order to deduplicate common objects between them. This is mostly used in the context of
// repository forks.
//
// The typical lifetime of an object pool is as follows:
//
// 1. An object pool is created via CreateObjectPool from its primary pool member. Typically this
//    would be the repository that gets forked.
// 2. One or more repositories are linked to the object pool via LinkRepositoryToObjectPool. Each
//    object pool member linked to the repository will have its objects deduplicated when its
//    objects get repacked the next time.
// 3. The object pool is regularly updated via FetchIntoObjectPool. This is typically only done from
//    the primary object pool member.
// 4. Repositories may leave the object pool via DisconnectGitAlternates. There is not much of a
//    reason to do this for any repositories except for the primary object pool member in case it
//    for example becomes private.
// 5. When the object pool does not have any members anymore it gets deleted via DeleteObjectPool.
//    It is the responsibility of the caller to ensure that it really has no members left, else
//    any existing member will become corrupt.
