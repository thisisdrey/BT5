Based on the investigation, the clearest local analog to the GMX "missing validation before trusting user-supplied identifiers" bug class is in the Snowbridge `snowbridge-pallet-system-v2::register_token` extrinsic.

### Title
`register_token` in `snowbridge-pallet-system-v2` accepts an unverified `sender` location, allowing origin/fee misattribution - (File: `bridges/snowbridge/pallets/system-v2/src/lib.rs`)

### Summary
The GMX report's core defect is that a public entry point accepts caller-supplied identifiers (`longToken`/`shortToken`/`initialCollateralToken`) without validating them against the authenticated context (the `market`), letting a caller misdirect funds/state that should be scoped to the real, verified participant. The `register_token` call in `pallet-system-v2` [1](#0-0)  exhibits the same pattern: it authenticates the caller via `T::FrontendOrigin::ensure_origin(origin)?`, which only proves the *call* originated from a permitted XCM location, but then trusts a completely separate, caller-supplied `sender: Box<VersionedLocation>` parameter as the effective identity for message origin and fee attribution, without checking that `sender` matches (or is a descendant of) the actual authenticated origin.

### Finding Description
`register_token` does: [2](#0-1) 
`T::FrontendOrigin::ensure_origin(origin)?` only verifies that *some* permitted XCM origin issued the call (e.g. the system-frontend pallet's sovereign/descend-origin on Asset Hub, which proxies calls for arbitrary end users). The `sender` argument is decoded from raw bytes supplied in the call payload and used directly as `sender_location`, which is then converted via `Self::location_to_message_origin(sender_location)?` and passed to `Self::send(message_origin, command, amount)`. There is no assertion binding `sender` to the identity that actually authorized the underlying user-level transaction on the frontend chain (e.g. no check that `sender` equals the descended/derived account matching the real caller who paid `amount`). This mirrors the GMX bug exactly: a "market"-scoped resource (`longToken`) was accepted without checking it matches the caller-supplied context; here a fee/origin-scoped resource (`sender`) is accepted without checking it matches the authenticated origin context.

### Impact Explanation
Because `FrontendOrigin` is satisfied by the proxy call from the system-frontend pallet on Asset Hub (which any signed account can invoke for itself, per `register_token` in `system-frontend`) [3](#0-2) , an attacker able to reach this BridgeHub-side call (directly, or if the frontend proxy forwards attacker-controlled bytes for `sender` without re-deriving it) can set `sender` to an arbitrary `Location`, causing the outbound message/token registration to be attributed to, and any associated fee-bearing message to be billed against, a victim's agent/account rather than the real caller's. This breaks the "settle to the rightful beneficiary" invariant for governance/registration-fee flows.

### Likelihood Explanation
Exploitability depends on whether the concrete `FrontendOrigin` implementation used in the runtime re-derives `sender` from the XCM origin itself rather than trusting the call argument. From the pallet code alone, no such binding exists inside `register_token`; the check is delegated entirely to the `FrontendOrigin`/frontend pallet wiring, which is a defense-in-depth gap consistent with the "missing validation" class in the report, but I could not fully verify within the available index whether the concrete frontend pallet always overwrites/validates `sender` before dispatch to BridgeHub.

### Recommendation
In `register_token`, derive `sender_location` from the authenticated `origin` (the `Location` returned by `T::FrontendOrigin::ensure_origin`) rather than trusting the caller-supplied `sender` parameter, or explicitly assert that the supplied `sender` is contained within / equal to the authenticated origin before using it for fee attribution and message origin.

### Proof of Concept
Conceptual: any account able to invoke the BridgeHub `register_token` extrinsic (call index 2) with a valid `FrontendOrigin`-satisfying XCM origin can pass `sender = Box::new(VersionedLocation::from(victim_location))`. The pallet never checks `sender_location == origin_location`; it proceeds to `Self::location_to_message_origin(sender_location)` and charges/attributes the resulting message using that victim-controlled location, exactly as GMX's report showed unchecked `longToken`/`initialCollateralToken` being accepted and used to move/store value without matching to the authenticated `market`/context. 		pub fn register_token(
			origin: OriginFor<T>,
			sender: Box<VersionedLocation>,
			asset_id: Box<VersionedLocation>,
			metadata: AssetMetadata,
			amount: u128,
		) -> DispatchResult {
			T::FrontendOrigin::ensure_origin(origin)?;

			let sender_location: Location =
				(*sender).try_into().map_err(|_| Error::<T>::UnsupportedLocationVersion)?;
			let asset_location: Location =
				(*asset_id).try_into().map_err(|_| Error::<T>::UnsupportedLocationVersion)?;

			let location = Self::reanchor(asset_location)?;
			let token_id = TokenIdOf::convert_location(&location)
				.ok_or(Error::<T>::LocationConversionFailed)?;

			if !ForeignToNativeId::<T>::contains_key(token_id) {
				ForeignToNativeId::<T>::insert(token_id, location.clone());
			}

			let command = Command::RegisterForeignToken {
				token_id,
				name: metadata.name.into_inner(),
				symbol: metadata.symbol.into_inner(),
				decimals: metadata.decimals,
			};

			let message_origin = Self::location_to_message_origin(sender_location)?;
			Self::send(message_origin, command, amount)?;
