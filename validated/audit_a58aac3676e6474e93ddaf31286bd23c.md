### Title
Attacker can fill a victim's `depositTokensOfAccount` list via dust `DepositToken` transfers, blocking deposits, borrows, and collateral top-ups (DoS) - (File: contracts/Pool.sol)

### Summary
`Pool` enforces `MAX_TOKENS_PER_USER = 30` across the combined `debtTokensOfAccount` + `depositTokensOfAccount` lists, and `addToDepositTokensOfAccount` reverts with `UserReachedMaxTokens` once the cap is hit. `DepositToken._transfer` calls `pool.addToDepositTokensOfAccount(recipient_)` whenever the recipient's balance goes from 0 to non-zero — including on plain `transfer`/`transferFrom`, not just deposits. An unprivileged attacker can therefore permissionlessly "push" dust balances of many distinct `DepositToken`s onto any victim, exhausting their 30 slots. After that, any operation that would add a *new* token to the victim's lists reverts.

### Finding Description
- `Pool.addToDepositTokensOfAccount` / `addToDebtTokensOfAccount` are gated by `onlyIfAdditionWillNotReachMaxTokens(account_)`, which reverts when `debtTokensOfAccount.length + depositTokensOfAccount.length >= MAX_TOKENS_PER_USER` (30). [1](#0-0) [2](#0-1) 
- `DepositToken._transfer` unconditionally calls `pool.addToDepositTokensOfAccount(recipient_)` when the recipient had a zero balance. There is no opt-in; any holder of a `DepositToken` can force a slot onto any address by transferring 1 wei of the msdTOKEN. [3](#0-2) 
- Attack (no privileged role, no oracle manipulation):
  1. Attacker deposits a minimal amount of collateral into each `DepositToken` registered in the pool (or buys dust amounts) — the pool typically has many deposit tokens; attacker needs at most `30 - (victim's current count)` distinct ones.
  2. Attacker calls `msdToken_i.transfer(victim, 1)` for each token. Each call adds that token to `depositTokensOfAccount[victim]` until the list hits 30.
  3. From then on, `victim` cannot: deposit any collateral type they don't already hold (`DepositToken.mint → _transfer → addToDepositTokensOfAccount` reverts), mint a synthetic whose `DebtToken` they don't already hold (`DebtToken.issue/mint → addToDebtTokensOfAccount` reverts), use `SmartFarmingManager.leverage`, or receive any new msdTOKEN/debt-token (transfers to them revert).
- If the victim's position is drifting toward liquidation and the collateral token needed to restore health is not already in their list, `deposit` reverts and the position is forcibly liquidated — converting a gas-cost grief into real loss. `liquidate` itself still works for the liquidator, so the protocol is not harmed, but the user is.
- The victim can recover slots by transferring each dust token out (`_transfer` → `removeFromDepositTokensOfAccount`), but this costs the victim gas per token, requires them to notice and act, and does not help within the same transaction as an emergency deposit (attacker can re-grief, or time the attack around a price move). The slot-clearing path also fails if the dust token is locked by `debtPositionOf`/`unlockedBalanceOf` accounting — locked collateral cannot be transferred out, so a slot may be un-clearable while debt is outstanding.

### Impact Explanation
Temporary freezing of user funds / denial of service on core protocol entry points: `deposit`, `mint`/borrow, `leverage`, and inbound msdTOKEN transfers all revert for the victim. Combined with an adverse price move, this prevents adding collateral and results in liquidation of the victim's position — a direct, attacker-induced loss enabled by resource exhaustion of the per-account token list (CWE-400 analog: uncontrolled resource consumption via forced storage entries).

### Likelihood Explanation
Any EOA can execute this. Cost is bounded by acquiring dust balances in N distinct pool `DepositToken`s plus N transfer calls — no privileged role, no oracle manipulation, no governance action required. The attack is fully permissionless and repeatable after the victim clears slots. Likelihood is gated mainly by how many deposit/debt tokens the pool has registered and the attacker's capital for dust deposits; on pools with ≥30 registered tokens it is cheap.

### Recommendation
- Do not add to `depositTokensOfAccount` on incoming `transfer`/`transferFrom` of msdTOKENs (track the list only on `deposit`/`mint` initiated paths), or make adding a slot opt-in.
- Alternatively, check `unlockedBalanceOf`/lock status or apply a minimum-amount threshold before registering a token in the per-account list.
- Consider raising/removing `MAX_TOKENS_PER_USER` since loops over the lists are bounded by registered pool tokens anyway, or let users remove entries even when locked.

### Proof of Concept
Hardhat fork sketch (mainnet/Base pool):

```ts
// victim has e.g. 2 tokens registered
const pool = await ethers.getContractAt("Pool", POOL_PROXY);
const depositTokens = await pool.getDepositTokens(); // registered list
const attacker = signers[1];

for (const addr of depositTokens.slice(0, 30)) {
  const msd = await ethers.getContractAt("DepositToken", addr);
  // acquire dust: deposit minimal underlying or buy msd on market
  await underlying.approve(msd.address, dust);
  await msd.deposit(dust); // attacker now holds msd
  await msd.transfer(victim.address, 1n); // forces slot onto victim
}

expect(await pool.getDepositTokensOfAccount(victim.address)).length
  .to.be.gte(29);

// victim tries to deposit a new collateral type to save unhealthy position
await expect(
  newDepositToken.connect(victim).deposit(amount)
).to.be.revertedWithCustomError(pool, "UserReachedMaxTokens");

// victim tries to mint a new synthetic
await expect(
  pool.connect(victim).mint(newSynthetic, amount, victim.address)
).to.be.revertedWithCustomError(pool, "UserReachedMaxTokens");
```

The revert propagates because `DepositToken._mint`/`_transfer` and `DebtToken.issue` reach `addTo*TokensOfAccount`, guarded by `onlyIfAdditionWillNotReachMaxTokens`.

            balanceOf[sender_] = _senderBalanceBefore - amount_;
            balanceOf[recipient_] += amount_;
