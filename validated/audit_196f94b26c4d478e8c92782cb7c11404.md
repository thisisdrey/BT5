Audit Report

## Title
Reward payout in `process_delivery_receipt` ignores the decoded `success` flag, settling relayer rewards for failed message deliveries - (File: bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs)

## Summary
`DeliveryReceipt::try_from` decodes the real `InboundMessageDispatched` event emitted by the Ethereum Gateway, which includes a `success: bool` field describing whether the message execution on Ethereum actually succeeded. `Pallet::process_delivery_receipt` only checks `receipt.gateway` and looks up the `PendingOrder` by `receipt.nonce`; it never reads or enforces `receipt.success` (or binds `receipt.topic`) before paying the reward and removing the order.

## Finding Description
`submit_delivery_receipt` verifies the event log/proof via `T::Verifier::verify`, decodes it into a `DeliveryReceipt` (which includes `success`), and forwards it to `process_delivery_receipt`: [1](#0-0) 

`process_delivery_receipt` then only validates the gateway address and resolves the reward account/order by nonce, paying the reward and removing the order unconditionally with respect to `success`: [2](#0-1) 

`DeliveryReceipt` decodes `success` (and `topic`) directly from the verified `InboundMessageDispatched` Ethereum event, so this information is genuinely available at the point of settlement but is discarded: [3](#0-2) 

`PendingOrder` itself stores only `nonce`, `block_number`, and `fee` — it has no field to record or cross-check the message topic, so `receipt.topic` binding is likewise impossible with current storage: [4](#0-3) 

This breaks the invariant that bridge receipts and payout state must only advance after execution and settlement succeed atomically — settlement (reward payment + order removal) proceeds regardless of whether Ethereum-side execution (`success`) actually succeeded.

## Impact Explanation
Any relayer can submit a legitimately-proved `InboundMessageDispatched` event where `success == false` (execution reverted on the Ethereum Gateway) and still receive full payment of `order.fee`, with `PendingOrder` deleted as though delivery fully succeeded. This decouples relayer reward economics from actual message execution outcome, letting relayers collect fees for messages that never took effect on Ethereum — a duplicate/incorrect settlement of bridge reward payout state (`order.fee` paid to `reward_account`) that the target scopes explicitly call out as needing to remain conditioned on successful execution.

## Likelihood Explanation
This requires only an ordinary, unprivileged relayer submitting a real, correctly-proved event log where the emitted `success` field is `false` — a normal outcome achievable by causing an outbound command to revert on the Ethereum Gateway (e.g., a rejecting recipient contract) — and calling the already-public `submit_delivery_receipt` extrinsic. No proof forgery, malicious peer, or privileged role is needed, making this fully reachable by an external attacker using a public extrinsic.

## Recommendation
In `process_delivery_receipt`, branch on `receipt.success`: only call `T::RewardPayment::register_reward` when `receipt.success` is `true`; when `success == false`, still remove/resolve the `PendingOrder` to prevent replay but skip payment (or route to a distinct no-reward/penalty path). Additionally, extend `PendingOrder` (or a related storage item) to record the committed message `topic`, and validate `receipt.topic` against it before settlement, so a receipt cannot be matched to an unrelated nonce's order purely by numeric nonce collision.

## Proof of Concept
1. A message is enqueued and processed by `do_process_message`, creating `PendingOrders[nonce] = { nonce, fee>0, block_number }` (see `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs` lines 426-436).
2. The command dispatched to Ethereum reverts on execution, so the real Gateway contract emits `InboundMessageDispatched(nonce, topic, success=false, reward_address)`.
3. A relayer obtains a valid proof for this genuine event and calls `submit_delivery_receipt(origin, event)`.
4. `T::Verifier::verify` succeeds (proof is real); `DeliveryReceipt::try_from` decodes `success=false`, but `process_delivery_receipt` never inspects it — `order.fee > 0` still triggers `register_reward`, and `PendingOrders::remove(nonce)` fires `Event::MessageDelivered`.
5. The relayer is paid identically to a genuinely successful delivery despite `success == false`, which can be demonstrated with a unit test in `bridges/snowbridge/pallets/outbound-queue-v2/src/test.rs` asserting reward registration occurs even when a mocked `DeliveryReceipt.success` field is set to `false`.

sol! {
	event InboundMessageDispatched(uint64 indexed nonce, bytes32 topic, bool success, bytes32 reward_address);

/// Delivery receipt
#[derive(Clone, Debug)]
pub struct DeliveryReceipt {
	/// The address of the outbound queue on Ethereum that emitted this message as an event log
	pub gateway: H160,
	/// The nonce of the dispatched message
	pub nonce: u64,
	/// Message topic
	pub topic: H256,
	/// Delivery status
	pub success: bool,
	/// The reward address
	pub reward_address: [u8; 32],
}

#[derive(Copy, Clone, Encode, Decode, Eq, PartialEq, Debug, TypeInfo)]
pub enum DeliveryReceiptDecodeError {
	DecodeLogFailed,
	DecodeAccountFailed,
}

impl TryFrom<&Log> for DeliveryReceipt {
	type Error = DeliveryReceiptDecodeError;

	fn try_from(log: &Log) -> Result<Self, Self::Error> {
		let topics: Vec<B256> = log.topics.iter().map(|x| B256::from_slice(x.as_ref())).collect();

		let event = InboundMessageDispatched::decode_raw_log_validate(topics, &log.data)
			.map_err(|_| DeliveryReceiptDecodeError::DecodeLogFailed)?;

		Ok(Self {
			gateway: log.address,
			nonce: event.nonce,
			topic: H256::from_slice(event.topic.as_ref()),
			success: event.success,
			reward_address: event.reward_address.0,
		})
	}
