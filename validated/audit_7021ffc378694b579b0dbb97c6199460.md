## Analysis

The Sherlock report describes a DoS pattern: a public read function whose internal loop/array size is derived from external input with **no upper bound**, so a single call can force unbounded computation/allocation.

The closest reachable analog in java-tron is the **`GetAssetIssueList` API path**, which — unlike essentially every other list-returning API in `Wallet` — has no cap on the amount of work/data it processes per call.

### The unbounded function

`Wallet.getAssetIssueList()` iterates **every** asset issue ever created on-chain and, for each one, runs bandwidth-usage accounting before adding it to the response: [1](#0-0) 

This reads from `AssetIssueStore.getAllAssetIssues()`, which streams the *entire* underlying RocksDB column family into memory with no limit: [2](#0-1) 

This is exposed directly and unauthenticated over HTTP (`/wallet/getassetissuelist`) and gRPC (`GetAssetIssueList`): [3](#0-2) 

### Why this is the DOS analog

Every comparable list API in the codebase enforces a hard cap on the amount of work done per request:
- `getAssetIssueList(offset, limit)` caps `limit` at `ASSET_ISSUE_COUNT_LIMIT_MAX`: [4](#0-3) 
- `getBlockByLimitNext` caps the range at `BLOCK_LIMIT_NUM = 100`: [5](#0-4) 
- `getPaginatedNowWitnessList` caps `limit` at `WITNESS_COUNT_LIMIT_MAX`: [6](#0-5) 
- shielded-transaction scans cap the block range to 1000: [7](#0-6) 

`getAssetIssueList()` (the no-argument/`EmptyMessage` variant) is the outlier: it has **no limit at all**. Its cost scales linearly with the total number of `AssetIssueContract`s ever issued on the chain — a quantity that grows monotonically and can be inflated by any account willing to pay the `CreateAssetIssue` fee (asset-issue creation is a permissionless, fee-gated transaction, not privileged). Once enough asset issues accumulate (organically or via an attacker deliberately issuing many low-value assets), every subsequent unauthenticated call to `/wallet/getassetissuelist` (and its Solidity/PBFT mirrors) forces the node to materialize the full list, run bandwidth accounting on every entry, and serialize the entire result — repeatable by anonymous API clients with no rate-limit-independent cost bound, directly analogous to the `getAuctionData` unbounded-loop/array-size issue in the report.

### Title
Unbounded `getAssetIssueList()` API allows CPU/memory exhaustion DoS via unauthenticated query - (File: framework/src/main/java/org/tron/core/Wallet.java)

### Summary
`Wallet.getAssetIssueList()` (no-arg overload) returns and processes **all** asset issues stored on-chain with no size cap, unlike every other paginated/limited list API in the codebase.

### Finding Description
`getAssetIssueList()` calls `getAllAssetIssues()`, which streams every record from the `AssetIssueStore` RocksDB column family into a `List`, and then runs `BandwidthProcessor.updateUsage()` on each entry before building the response [1](#0-0) . This is exposed via the HTTP endpoint `/wallet/getassetissuelist`/`/walletsolidity/getassetissuelist`/`/walletpbft/getassetissuelist` and the gRPC `GetAssetIssueList` RPC on both full node and solidity/PBFT wallets [3](#0-2) , all reachable by any unauthenticated client. Asset issuance itself is a normal, permissionless, fee-paying transaction type, so the size of the underlying dataset is attacker-influenceable over time.

### Impact Explanation
Repeated calls to this endpoint force the node to enumerate and process the entire asset-issue set on every single request. As the number of issued assets grows, per-request CPU/memory/serialization cost grows unbounded, degrading or halting the node's ability to serve this and other API requests — a resource-exhaustion DoS against the API service, matching the "node can no longer serve" impact criterion.

### Likelihood Explanation
High: the endpoint requires no authentication or special privilege, can be invoked freely and repeatedly, and its cost is tied directly to a value (`total asset issues`) that grows monotonically and can be inflated by any paying account issuing many assets, unlike bounded siblings such as `getAssetIssueList(offset,limit)`, `getBlockByLimitNext`, or `getPaginatedNowWitnessList`, all of which cap work per call.

### Recommendation
Apply the same pagination/limit discipline used elsewhere in `Wallet` (e.g., `ASSET_ISSUE_COUNT_LIMIT_MAX` as used in `getAssetIssuesPaginated`) to the unbounded `getAssetIssueList()` path, or deprecate/remove the unbounded variant in favor of the paginated one, and enforce a hard maximum result size independent of caller-supplied or store-derived parameters.

### Proof of Concept
1. Issue (or wait for the network to accumulate) a large number of `AssetIssueContract`s.
2. Repeatedly call `GET/POST /wallet/getassetissuelist` (or the gRPC `GetAssetIssueList`) with no rate limiting bypass required.
3. Each call forces full enumeration and bandwidth-usage processing of the entire asset-issue set, consuming CPU/memory proportional to the store size, degrading node responsiveness for all clients.
