### Title
Anti-replay window Check/Update split allows redundant decryption of replayed ciphertext across the unlock gap - (File: connection_state.go)

### Summary
`ConnectionState.Decrypt` and `ConnectionState.VerifyRelay` validate an incoming message counter against the anti-replay window in two separate, individually-locked steps: `window.Check()` runs and releases `decryptLock`, then the AEAD decryption runs *outside* the lock, and only afterward is `window.Update()` called under the lock to actually reserve/mark the counter. This mirrors the Ajna `moveQuoteToken()` root cause: an invariant is checked against an intermediate state (the window state *before* the operation's effect is committed) rather than against the final, authoritative state, leaving a window where the check no longer reflects reality by the time the sensitive operation runs.

### Finding Description
`Decrypt` performs:
```
cs.decryptLock.Lock()
result := cs.window.Check(l, messageCounter)   // step 1: check
cs.decryptLock.Unlock()
...
out, err = cs.dKey.DecryptDanger(...)          // step 2: expensive AEAD op, unlocked
...
cs.decryptLock.Lock()
result = cs.window.Update(l, messageCounter)   // step 3: commit
cs.decryptLock.Unlock()
``` [1](#0-0) 

The same two-step Check/Update pattern is used again in `VerifyRelay`, which authenticates relay-forwarded AEAD frames. [2](#0-1) 

`Bits.Check` only *reads* the window state without reserving the slot; the slot is only actually marked as consumed by `Bits.Update`, which is a distinct call guarded by its own separate lock acquisition. [3](#0-2) 

Because `Check` and `Update` are not atomic with respect to each other (the lock is dropped between them, and the costly `DecryptDanger` call runs entirely unlocked), any number of concurrently-delivered copies of the exact same captured ciphertext packet will all pass `Check` (since none of them has reserved the counter yet) and all proceed to perform a full AEAD decryption operation before any of them commits via `Update`. Only after decryption does the code serialize on `Update`, at which point all but the first caller are told `ErrAlreadySeen` and their decrypted output is discarded.

This is structurally identical to the Ajna bug class: a boundary condition ("is this counter already consumed?") is evaluated against a state snapshot taken *before* the operation that depends on it completes, rather than against the state as it exists when the operation's result is actually used/committed. In Ajna this let an over-permissive/-restrictive invariant slip through; here it lets replayed/duplicated ciphertext bypass the "reject before we do expensive crypto work" intent of the anti-replay check, because the reservation of the counter slot is deferred to a second, independent locked operation.

### Impact Explanation
An attacker who has observed (sniffed) or otherwise obtained a single legitimate encrypted UDP packet — which requires no CA-signed certificate of their own, only network position between two already-handshaken peers — can retransmit that captured packet concurrently many times. Each concurrent copy passes the `Check` step (the slot is not yet marked) and triggers a full, independent `DecryptDanger` AEAD invocation before `Update` finally deduplicates them. This converts a single captured packet into an amplified number of expensive decrypt operations per node, and does so entirely on the strength of a replayed frame — no valid certificate or handshake participation by the attacker is required, satisfying "traffic decryption/replay" impact and remote resource-exhaustion/DoS impact for both regular data-plane packets (`Decrypt`) and relay-forwarded frames (`VerifyRelay`), the latter being especially significant because relay nodes process AEAD frames on behalf of two other peers without terminating the tunnel themselves.

### Likelihood Explanation
Likelihood is high: capturing and replaying an encrypted UDP datagram is trivial for any attacker positioned on the path (or who can flood the wire with a previously observed packet), UDP has no built-in ordering guarantees preventing concurrent delivery, and Nebula's outside packet reader dispatches inbound UDP reads to worker goroutines, making concurrent invocation of `Decrypt`/`VerifyRelay` for identical duplicate packets a realistic condition rather than a purely theoretical race.

### Recommendation
Reserve the message-counter slot atomically with the check, before performing the AEAD decryption, rather than after. Concretely, hold `decryptLock` for the combined "check-and-tentatively-reserve" step (e.g., have `Bits` expose an atomic `CheckAndReserve` that fails closed if the slot is already taken, only rolling back the reservation if the subsequent `DecryptDanger` call fails), so that only one concurrent caller for a given counter ever proceeds to the expensive decrypt path. This closes the amplification/TOCTOU window while preserving current single-request-path correctness (a decrypt failure should still free the slot, since Nebula intentionally treats decrypt failure as non-fatal/retriable).

### Proof of Concept
1. Two nebula nodes complete a handshake and exchange one data packet; the ciphertext for messageCounter=N is captured on the wire (no certificate access needed).
2. The attacker floods the victim node's UDP socket with, e.g., 100 concurrent copies of the exact captured packet.
3. Each of the concurrently-dispatched goroutines calling `ConnectionState.Decrypt` observes `cs.window.Check(l, N)` returning `true` (nobody has called `Update` yet) and proceeds to call `cs.dKey.DecryptDanger(...)`, performing a full AEAD decrypt.
4. Only when each goroutine subsequently calls `cs.window.Update(l, N)` (serialized by `decryptLock`) does exactly one succeed and the rest receive `ErrAlreadySeen` — but by then all N decrypt operations have already executed, demonstrating the amplification/TOCTOU gap. (Note: exact observable amplification depends on the UDP read worker pool size and scheduler timing; this was derived by code inspection of `connection_state.go`/`bits.go` rather than by running the flood against a live instance, since only static repository access was available.)

func (cs *ConnectionState) VerifyRelay(l *slog.Logger, messageCounter uint64, packet []byte, nb []byte) error {
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	signedPayload := packet[:len(packet)-cs.dKey.Overhead()]
	signatureValue := packet[len(packet)-cs.dKey.Overhead():]
	_, err := cs.dKey.DecryptDanger(nil, signedPayload, signatureValue, messageCounter, nb)
	if err != nil {
		return err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	return nil
}

// Check returns true if i is within (or way out in front of) the window, and not a replay
func (b *Bits) Check(l *slog.Logger, i uint64) bool {
	// If i is the next number, return true.
	if i > b.current {
		return true
	}

	if b.strictlyWithinWindow(i) {
		return !b.get(i)
	}

	// Not within the window
	if l.Enabled(context.Background(), slog.LevelDebug) {
		l.Debug("rejected a packet (top)", "current", b.current, "incoming", i)
	}
	return false
}

// Update has three branches:
//   - i == b.current+1: fast path; advance the cursor by one and lose-count
//     the slot we just stomped (only past warmup; see the i > b.length guard
//     below).
//   - i  >  b.current+1: jump path; clear all slots between current and i
//     (or up to a full window's worth, whichever is smaller) via clearRange,
//     then mark i. Two arms here: a warmup arm that handles the very first
//     window before the cursor has slid, and a steady-state arm that treats
//     every cleared empty slot as a lost packet.
//   - i  <= b.current: in-window check for duplicates; out-of-window otherwise.
//
// NewBits seeds bits[0]=1 so counter 0 looks "received" — Update never
// clears that marker during warmup (clearRange skips position 0 when
// startPos=1), and once b.current >= b.length the marker is no longer
// consulted. The marker prevents a fictitious "lost" hit on the first real
// counter.
func (b *Bits) Update(l *slog.Logger, i uint64) bool {
	// Fast path: i is the next expected counter. Split out so the function
	// stays small and avoids paying for the slow paths' slog argument-build
	// stack frame on every call. The bit read/test/write is inlined to
	// touch the backing word once.
	if i == b.current+1 {
		pos := i & b.lengthMask
		word := pos >> 6
		mask := uint64(1) << (pos & 63)
		w := b.bits[word]
		if i > b.length && w&mask == 0 {
			b.lostCounter.Inc(1)
		}
		b.bits[word] = w | mask
		b.current = i
		return true
	}
	return b.updateSlow(l, i)
}
