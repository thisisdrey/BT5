### Title
Out-of-bounds read via unchecked array offset in `ValidateMultiSign` precompile signature-array parsing - ([File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java])

### Summary
The `ValidateMultiSign` precompiled contract (invoked from Solidity via the TVM) parses ABI-encoded calldata using helper methods `extractBytesArray`/`extractSigArray`/`extractBytes32Array` that read attacker-controlled offset and length words from the `DataWord[]` array without validating that the derived index stays within array bounds. This mirrors the wolfSSL ALPN bug class: a length/offset field taken from untrusted input is used to index into a buffer with "incomplete validation," producing an out-of-bounds read (here, an uncaught `ArrayIndexOutOfBoundsException`/`NegativeArraySizeException`) instead of a bounds-checked failure.

### Finding Description
`extractBytesArray` and `extractSigArray` only validate the *initial* offset (`if (offset > words.length - 1) return new byte[0][];`) but then compute `len` and per-element `bytesOffset`/`bytesLen` directly from attacker-supplied `DataWord`s and index `words[offset + i + 1]` / `words[offset + bytesOffset + 1]` without re-checking those derived indices against `words.length`: [1](#0-0) 

`extractBytes32Array` has no bounds check at all on `offset`, `len`, or `offset + i + 1`: [2](#0-1) 

In `ValidateMultiSign.execute`, the extraction call happens **before** the method's only `try`/`catch` block (which starts later, around the account/permission logic), so any `ArrayIndexOutOfBoundsException`/`NegativeArraySizeException` thrown here is unhandled inside this method: [3](#0-2) 

By contrast, `BatchValidateSign.execute` wraps the equivalent call in a `try { return doExecute(data); } catch (Throwable t) { ... }`, so that path is defensively guarded: [4](#0-3) 

An attacker who deploys/calls a contract invoking the `ValidateMultiSign` precompile can craft calldata where:
- the offset word (`words[3]`) points past the end of the `words` array, or
- the length word at that offset is negative or huge, or
- per-item `bytesOffset`/`bytesLen` words push the read index beyond `words.length`,

causing an unguarded runtime exception during precompile execution.

### Impact Explanation
An unhandled `RuntimeException` thrown mid-opcode-execution inside a precompiled contract call is a robustness bug in the deterministic execution path shared by every full node. Because it occurs before the local try/catch in `ValidateMultiSign.execute`, whether this is caught higher up (e.g., in `Program`'s call-to-precompile wrapper) determines whether the effect is limited to "this one transaction reverts" or something more severe (thread/task failure during block application). I was not able to fully verify, within the available tool budget, how far up the call stack this exception propagates and whether it is uniformly caught by the VM's opcode dispatcher for precompiled calls elsewhere in the codebase — this is the main open uncertainty in this finding. At minimum this is an availability/robustness defect reachable by any contract caller; if the exception is not caught in the precompile-call wrapper, it could interrupt transaction/block processing for that specific malicious call.

### Likelihood Explanation
High reachability: the `ValidateMultiSign` precompile is callable by any account via a normal smart-contract `CALL`/`STATICCALL`, requiring no special privilege — matching the "unprivileged transaction broadcaster / contract deployer" reachability bar. Crafting the malicious offset/length words is trivial ABI manipulation, analogous to crafting a malformed ALPN extension list.

### Recommendation
Add strict bounds validation in `extractBytes32Array`, `extractBytesArray`, and `extractSigArray` before every array access (validate `offset`, `offset + len + 1`, and each per-item derived index against `words.length`), returning an empty/invalid result rather than indexing out of range. Additionally, wrap the extraction calls in `ValidateMultiSign.execute` in a try/catch (as already done in `BatchValidateSign.execute`) so any residual parsing exception is converted into a graceful `DATA_FALSE` / revert result rather than propagating as an unchecked exception.

### Proof of Concept
Deploy a helper contract that calls the `ValidateMultiSign` precompiled contract address with calldata shaped as:
```
[address (32B)] [permissionId (32B)] [data offset (32B)] [signatures-array offset (32B) = e.g. 0xFFFFFFFF or a value pointing past calldata length]
```
so that `words[3].intValueSafe() / WORD_SIZE` resolves to an index `>= words.length`, causing `words[offset]` inside `extractBytesArray`/`extractSigArray` (called at PrecompiledContracts.java:1072-1074) to throw `ArrayIndexOutOfBoundsException` before the method's try/catch block is reached.

Note: I could not confirm, given the remaining tool budget, whether a higher-level wrapper around precompiled-contract invocation in the TVM catches this exception generically (which would downgrade this to a per-transaction revert rather than a broader node-level fault). This should be verified against `Program`'s precompiled-call invocation logic before treating this as more than a transaction-scoped robustness issue.

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
