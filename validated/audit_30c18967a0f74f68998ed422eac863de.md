Audit Report

## Title
ERC20 asset-precompile state-changing calls do not reject non-zero native `value`, permanently locking mistakenly-sent native funds - (File: `substrate/frame/assets/precompiles/src/lib.rs`)

## Summary
The `pallet-assets` ERC20 precompile's `transfer`, `transferFrom`, `approve`, and `permit` entry points never validate that the native value attached to a `pallet_revive` call is zero before executing an asset-only operation. Because `HAS_CONTRACT_INFO` is `false` for this precompile, its synthetic address never receives a contract-info/consumer setup, so any native value routed into it via `transfer_from_origin` has no reachable withdrawal path, permanently stranding user funds.

## Finding Description
`ERC20::call` matches on the decoded `IERC20Calls` variant and only guards against delegate-calls and read-only-state violations before dispatching to `Self::transfer`, `Self::approve`, `Self::transfer_from`, and `Self::permit`; it never inspects the call's native value [1](#0-0) . `HAS_CONTRACT_INFO` for this precompile is `false` [2](#0-1) .

In `pallet_revive`'s `Stack::run`, any non-delegate call unconditionally transfers `frame.value_transferred` from the caller into the callee account via `Self::transfer_from_origin` before the callee's logic (including precompile logic) runs [4](#0-3) . The subsequent step that mints the minimum balance and adds a consumer reference — the mechanism that establishes a reachable, alive account for a precompile — is gated on `precompile.has_contract_info()`, which is `false` for the ERC20 precompile, meaning this step is skipped entirely for it [5](#0-4) .

Since the ERC20 precompile has no payable/withdraw entry point and no contract-info-backed account management, native value credited to its synthetic address during a `transfer`/`transferFrom`/`approve`/`permit` call cannot be moved back out through any public interface.

## Impact Explanation
This matches the permanent user-fund-lock impact category: an unprivileged caller who attaches non-zero native value to an ERC20-precompile state-changing call loses that value irrecoverably, since the underlying account has no code or capability to move it elsewhere.

## Likelihood Explanation
This requires only a normal, unprivileged caller (EOA or dApp/wallet with buggy `msg.value` defaults) invoking `pallet_revive::Pallet::call`/`bare_call` against the precompile's address with non-zero value — no malicious peer, relayer, or privileged actor is needed, making this a realistic operational/tooling-mistake scenario.

## Recommendation
Add an explicit guard in `ERC20::call` (or in each of `transfer`, `approve`, `transfer_from`, `permit`) that reverts when the call's native value is non-zero, and apply the same guard to other `HAS_CONTRACT_INFO = false` precompiles lacking any means to reclaim credited native value.

## Proof of Concept
1. Deploy the ERC20 precompile for an asset id, yielding synthetic address `P`.
2. From a funded EOA, call `pallet_revive::Pallet::<Runtime>::call` targeting `P` with `IERC20::transferCall` input and non-zero native `value`.
3. `Stack::run` moves the native value into `P`'s account via `transfer_from_origin`; since `HAS_CONTRACT_INFO` is `false`, no mint/consumer step runs, and `ERC20::transfer` executes and returns success with no value check.
4. The native balance at `P`'s account is now unreachable since there is no withdraw path in `ERC20::call` and no contract exists at `P` to move it.
