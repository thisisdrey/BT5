### Title
Order-execution authorization bypass allows fund redirection via unbound "any signer" grant - (File: programs/marginfi/src/state/marginfi_account.rs)

### Summary
`is_signer_authorized` grants blanket authorization to *any* signer whenever a marginfi account carries the `ACCOUNT_IN_ORDER_EXECUTION` flag, without checking that the signer matches the specific `executor` that legitimately started the order-execution session. Combined with `StartExecuteOrder`'s intentionally unchecked `executor` field, this reproduces the analog bug class from the FloodPlain/BunniZone report: authorization is validated against a coarse state/identity signal ("is this account currently in an authorized mode?") rather than against the specific actor and action being performed, allowing an unrelated party to piggyback on a legitimately-triggered privileged session and redirect withdrawn funds to themselves.

### Finding Description
`is_signer_authorized` explicitly documents and implements: "If `allow_order_execution` is true and the account is in order execution → `true`" with no further restriction on which signer is permitted: [1](#0-0) 

This mirrors the root cause in the external report: `BunniZone.validate()` checks only the *fulfiller* identity/state (whitelist or am-AMM manager) and never inspects the *content* of the hooks being executed, letting anyone splice a legitimate rebalance hook into an order they control. Here, `is_signer_authorized` checks only the *account's* mode flag (`ACCOUNT_IN_ORDER_EXECUTION`) and never checks *which* signer is entitled to act in that mode — any signer passes.

The flag is set by `start_execute_order`, which is a permissionless keeper instruction: [2](#0-1) 

Critically, the `executor` account in `StartExecuteOrder` has "no checks whatsoever, executor decides this without restriction": [3](#0-2) 

Once `ACCOUNT_IN_ORDER_EXECUTION` is set on the victim's `MarginfiAccount`, `lending_account_withdraw`/`lending_account_repay` (and the Kamino/Drift/Juplend/Solend equivalents) skip the normal `has_one = authority` style check in favor of `is_signer_authorized(.., allow_order_execution = true)`, per the grep-confirmed call sites in `withdraw.rs`, `repay.rs`, `borrow.rs`, `deposit.rs`, `close_balance.rs`, and the corresponding integration modules (kamino/drift/juplend/solend `withdraw.rs`/`deposit.rs`). Health/state checks during order execution are deferred to `EndExecuteOrder`, which only validates account health and slippage — not who received the withdrawn tokens: [4](#0-3) [5](#0-4) 

Because the `withdraw` instruction lets the caller specify an arbitrary `destination_token_account`, and because "any signer" is authorized during order execution, an attacker who is not the intended keeper/executor can supply themselves as the `authority` on a `lending_account_withdraw` instruction included in the same order-execution window and redirect the liquidated collateral to their own token account, as long as the post-execution health/slippage constraints in `check_health_and_verify_unchanged` are satisfied (which they can be, since these constraints govern account health and balance bookkeeping, not the recipient of transferred tokens).

### Impact Explanation
This allows unauthorized transfer/theft: funds belonging to a marginfi account whose stop-loss/take-profit order has become triggerable can be withdrawn by an attacker-controlled signer instead of the legitimate keeper or the account authority, redirecting proceeds to an address of the attacker's choosing. This is a concrete theft/unauthorized-transfer impact within the order/margin-account accounting path, directly analogous to the "steal tokens from other users" impact described in the source report.

### Likelihood Explanation
Exploitation requires only that a user's placed `Order` (stop-loss/take-profit) reach its trigger condition — a normal, expected market event — after which `StartExecuteOrder` is permissionless and its `executor` field is unchecked, so any party (not just a designated keeper) can open the order-execution window on the victim's account. From that point, any signer is authorized to issue withdraw/repay instructions against the account per `is_signer_authorized`. This does not require admin privileges, a compromised keeper, or any social engineering, making it directly reachable by an unprivileged attacker monitoring for triggerable orders.

### Recommendation
Bind authorization during order execution to the specific `executor` recorded in the `ExecuteOrderRecord` (or require the `executor` in `StartExecuteOrder` to be a signer and thread that identity through to `is_signer_authorized`), rather than granting blanket authorization to any signer whenever the `ACCOUNT_IN_ORDER_EXECUTION` flag is set. Additionally, consider validating or constraining `destination_token_account`/`fee_recipient` for withdrawals performed during order execution so that liquidated proceeds cannot be routed to an arbitrary address unrelated to the account authority or the legitimate executor.

### Proof of Concept
1. Monitor on-chain `Order` accounts for one whose stop-loss/take-profit trigger condition (`net <= stop_loss` or `net >= take_profit`) has just become true.
2. Build and submit a single transaction as an unrelated attacker:
   - `MarginfiAccountStartExecuteOrder` for the victim's `marginfi_account`/`order`, setting `executor` to the attacker's own arbitrary pubkey (no signature/ownership check enforced on this field: [6](#0-5) ).
   - `lending_account_withdraw` (or `lending_account_repay`) against the same `marginfi_account`, with `authority` set to the attacker's own signer and `destination_token_account` set to an attacker-owned token account. This passes `is_signer_authorized` because `ACCOUNT_IN_ORDER_EXECUTION` is set and any signer is accepted ( [7](#0-6) ).
   - `MarginfiAccountEndExecuteOrder`, signed by the same attacker-controlled `executor` key (matches `execute_record.executor` since the attacker set it in step 1), satisfying `check_health_and_verify_unchanged`.
3. The withdrawn/repaid collateral ends up in the attacker's token account rather than being routed to the legitimate keeper/fee_recipient, while the account's health-check invariants at `EndExecuteOrder` are still satisfied.

pub fn is_signer_authorized(
    marginfi_account: &MarginfiAccount,
    group_admin: Pubkey,
    signer: Pubkey,
    allow_receivership: bool,
    allow_order_execution: bool,
) -> bool {
    if allow_receivership && marginfi_account.get_flag(ACCOUNT_IN_RECEIVERSHIP) {
        return marginfi_account.authority != signer; // forbidden to take receivership of your own account
    }

    if allow_order_execution && marginfi_account.get_flag(ACCOUNT_IN_ORDER_EXECUTION) {
        return true;
    }

    if marginfi_account.get_flag(ACCOUNT_FROZEN) {
        return group_admin == signer;
    }

    marginfi_account.authority == signer
}
