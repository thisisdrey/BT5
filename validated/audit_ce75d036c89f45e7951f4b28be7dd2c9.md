### Title
Out-of-bounds heap/mmap read when parsing a crafted Zip64 extra field in singlejar's Central/Local Header parsing - (File: `src/tools/singlejar/zip_headers.h`)

### Summary
`CDH::compressed_file_size()`, `CDH::uncompressed_file_size()`, `CDH::local_header_offset()` and the equivalent `LH` accessors compute an index into a `Zip64ExtraField`'s `attr64()` array purely from the 32-bit size/offset fields of the (attacker-controlled) header, without ever checking that the field actually contains that many 64-bit attributes (`attr_count()`). A crafted zip/jar Central Directory Header can set a 32-bit field to `0xFFFFFFFF` (the Zip64 "escape" sentinel) while attaching a Zip64 extra field with `payload_size` too small (e.g. 0) to hold the implied attribute, causing `attr64(index)` to read 8 bytes past the field's declared/verified boundary.

### Finding Description
`Zip64ExtraField::find()` (via `ExtraField::find`, `src/tools/singlejar/zip_headers.h:99-115`) only validates that the extra-field *header + declared payload_size* fits inside the CDH's `extra_fields` region — it does not validate the number of 64-bit attributes actually present against what callers intend to read. [1](#0-0) 

`Zip64ExtraField::attr64()` performs an unchecked array read at the given index: [2](#0-1) 

`CDH::compressed_file_size()`, `CDH::uncompressed_file_size()` and `CDH::local_header_offset()`/`LH::compressed_file_size()`/`LH::uncompressed_file_size()` derive the `attr64` index from the *other* 32-bit fields' "is this 0xFFFFFFFF" flags, never from `zip64_ef->attr_count()`: [3](#0-2) [4](#0-3) 

If an attacker crafts a CDH/LH where `compressed_file_size32` (or `uncompressed_file_size32`, or `local_header_offset32`) equals `0xFFFFFFFF` but supplies a Zip64 extra field with `payload_size` smaller than required (e.g. `payload_size = 0`, i.e. `attr_count() == 0`), `attr64(index)` reads `attr_[index]` — 8 bytes located past the field's actually-verified 4-byte header, i.e. outside the region `ExtraField::find` checked. Depending on layout this lands in adjacent extra-field bytes, the comment field, or past the end of the mmap'd input file / heap allocation (in `OutputJar::AppendToDirectoryBuffer`, the CDH is first `memcpy`'d into a freshly `malloc`'d buffer sized from the *attacker-controlled* `cdh->size()`, so the OOB read can also occur against that heap buffer). This is the direct analog of `MagickCore/profile.c`'s trusting a declared profile/tag length without validating the actual buffer length before reading — CVE-2016-7799's bug class.

The values produced (`compressed_file_size()`, `uncompressed_file_size()`, `local_header_offset()`) are used downstream: `local_header_offset()` feeds `InputJar::LocalHeader()` (`ziph::byte_ptr`/`mapped_file_.address(...)`, `src/tools/singlejar/input_jar.h:94-97`) to compute a pointer into the mapped input file, and `compressed_file_size()`/`uncompressed_file_size()` drive decompression/copy sizes in `output_jar.cc`. I could not fully verify (within available iterations) whether `MappedFile::address()`/`mapped()` perform a strict bounds check before this pointer is dereferenced elsewhere in `input_jar.cc`/`output_jar.cc`; this is a gap in my verification and would need to be confirmed by a Devin session with full file access.

### Impact Explanation
Singlejar is Bazel's internal jar-merging tool, invoked as a build action on jar files that can originate from untrusted sources reachable by an unprivileged attacker (e.g., a `.jar`/`.srcjar` inside an `http_archive` fetched from a URL/mirror the attacker controls, or files on an attacker-influenced branch that CI builds). The checksum (`sha256`/`integrity`) on `http_archive` only pins the *archive* bytes; it does not validate the internal semantic well-formedness of a nested jar's zip structure, so a byte-for-byte pinned archive can still contain a maliciously malformed CDH/Zip64 extra field. Successfully triggering the OOB read leads to reading adjacent heap or mmap'd-file memory as if it were 64-bit size/offset data — at minimum a crash (process death on unmapped page), and at worst leaked heap bytes are used as bogus offsets/sizes that get copied into other computations or (via `AppendToDirectoryBuffer`) potentially into the output CDH.

### Likelihood Explanation
The attacker only needs to control the *contents* of an archive/jar consumed during a Bazel build (a very common trust boundary: `http_archive`, `.srcjar` inputs, generated jars from external code). No access to the victim's machine, credentials, or trusted root-repo Starlark is required — only the ability to publish or influence content the build will process with singlejar. Crafting the required CDH/Zip64 extra-field mismatch is a purely mechanical binary-format manipulation.

### Recommendation
In `Zip64ExtraField::attr64()` (or at each call site in `CDH`/`LH`), validate `index < attr_count()` before reading, and fail the archive read (`diag_errx`) analogous to the existing malformed-extra-field checks in `OutputJar::AppendToDirectoryBuffer` (`src/tools/singlejar/output_jar.cc:936-940`), rather than trusting the 32-bit sentinel fields alone to determine how many 64-bit attributes are present.

### Proof of Concept
A reproducible JUnit/`src/test/shell/bazel` proof would need to:
1. Build a minimal ZIP with one entry whose CDH sets `compressed_file_size32 = 0xFFFFFFFF` and `uncompressed_file_size32` to a normal 32-bit value.
2. Attach a Zip64 extra field (tag `0x0001`) with `payload_size = 0` (no attributes).
3. Run `InputJar::Open`/`NextEntry` (or `singlejar` binary) against this file and observe the OOB read via ASan (`heap-buffer-overflow` / `SEGV`) when `CDH::compressed_file_size()` calls `attr64(0)`.

I was not able to fully execute or verify this PoC or the downstream pointer-dereference path (`MappedFile::address`) within the current investigation; a background Devin session with full repository/tooling access would be needed to build and run this exploit and confirm ASan-detectable OOB access end-to-end.

  static const ExtraField* find(uint16_t tag, const uint8_t* start,
                                const uint8_t* end) {
    while (start < end) {
      if (ziph::byte_ptr(start) + sizeof(ExtraField) > ziph::byte_ptr(end)) {
        break;
      }
      auto extra_field = reinterpret_cast<const ExtraField*>(start);
      if (ziph::byte_ptr(start) + extra_field->size() > ziph::byte_ptr(end)) {
        break;
      }
      if (extra_field->is(tag)) {
        return extra_field;
      }
      start = ziph::byte_ptr(start) + extra_field->size();
    }
    return nullptr;
  }
