### Title
Disabling `allowShieldedTransactionApi` does not prevent shielded (Sapling/zk-SNARK) transfers — the restriction is bypassable by broadcasting a crafted `ShieldedTransferContract` transaction directly - (File: `framework/src/main/java/org/tron/core/Wallet.java`, `actuator/src/main/java/org/tron/core/actuator/ShieldedTransferActuator.java`)

### Summary
The `allowShieldedTransactionApi` node configuration flag is intended to let an operator disable the shielded-transaction (zk-SNARK) feature at the node/API level via `checkAllowShieldedTransactionApi()` gates in `Wallet.java`. However, this check is only enforced in the high-level wallet helper methods (`createShieldedTransaction`, `createShieldedTransactionWithoutSpendAuthSig`, `getShieldTransactionHash`, `createShieldedContractParameters*`, `getTriggerInputForShieldedTRC20Contract`, etc.), not in the actual transaction-processing path (`ShieldedTransferActuator.validate()`/`execute()`) that is invoked when a client submits an already-built, signed transaction (e.g., via `BroadcastTransaction` gRPC/HTTP). This is structurally identical to the reported analog: a "disable feature X" setting that is enforced only at a convenience API layer, while a lower-level/direct API call bypasses it entirely.

### Finding Description
`Wallet.createShieldedTransaction()` and its sibling helper methods call `checkAllowShieldedTransactionApi()` as their first statement [1](#0-0) , and other shielded helper entry points do the same [2](#0-1) [3](#0-2) [4](#0-3) .

But the actual on-chain validation and execution of a `ShieldedTransferContract` transaction — the code path reached when a client independently constructs a shielded transaction (off-node, using the public Zcash/Sapling libraries or any compatible tooling) and submits it via a plain broadcast call — is implemented entirely in `ShieldedTransferActuator.validate()` and `execute()`, neither of which calls or is gated by `checkAllowShieldedTransactionApi()`. The only enforced gates in the actuator are `ALLOW_SAME_TOKEN_NAME` and `supportShieldedTransaction()` (i.e., `ALLOW_SHIELDED_TRANSACTION`), which are separate, committee-controlled consensus parameters, not the node-operator's `allowShieldedTransactionApi` switch [5](#0-4) . `execute()` likewise performs the balance/pool adjustments unconditionally [6](#0-5) .

This is explicitly confirmed by a test in the repository itself, `shieldedTransferValidationWorksWhenApiDisabled`, whose doc comment states: "Test that shielded transfer transaction validation works even when allowShieldedTransactionApi is disabled. This verifies that the API flag only gates wallet/helper APIs, not the core transaction validation logic," and it asserts `actuator.validate()` succeeds with `allowShieldedTransactionApi` set to `false` [7](#0-6) .

### Impact Explanation
An operator who disables `allowShieldedTransactionApi` (e.g., for regulatory/compliance reasons, to prevent their node from being used to construct/relay privacy-preserving transactions, or to reduce exposure to zk-SNARK proof-verification cost/attack surface on their infrastructure) gets no actual protection: any external, unprivileged client can still submit a fully-formed `ShieldedTransferContract` transaction through the node's ordinary broadcast path, and the node will validate and execute it as long as the consensus-level `ALLOW_SHIELDED_TRANSACTION` and `ALLOW_SAME_TOKEN_NAME` parameters are enabled network-wide. This defeats the purpose of the node-level control, matching the analog report's bug class (an "instance-level disable" setting bypassed via direct/crafted API usage). Severity is Medium: it does not directly cause fund loss or consensus failure, but it is a genuine security-control bypass on a broadcastable-transaction path, allowing unauthorized use of a feature the operator explicitly disabled, potentially with compliance/legal or resource-exhaustion consequences (SNARK proof verification is comparatively CPU-expensive) for the node operator.

### Likelihood Explanation
High likelihood of exploitation if relied upon: any client capable of running the open-source Sapling transaction-building code (as java-tron's own test suite does, via `ZenTransactionBuilder`) can build a valid `ShieldedTransferContract` without ever calling the gated `Wallet` helper methods, then submit it through the standard broadcast RPC. No special privileges, keys, or node access are required — only a validly signed transaction, matching the "unprivileged transaction broadcaster" reachability required by the scope of this analysis.

### Recommendation
Enforce `checkAllowShieldedTransactionApi()` (or an equivalent operator-level check) inside `ShieldedTransferActuator.validate()`/`execute()` (and any other shielded-related actuators such as `ShieldedTransferTRC20` handling), not only in the `Wallet` convenience methods, so that disabling the setting truly blocks all shielded transaction processing on that node, consistent with the documented intent of the flag.

### Proof of Concept
1. On a java-tron full node, set `node.rpc.allowShieldedTransactionApi = false` (or the equivalent `Args.getInstance().setAllowShieldedTransactionApi(false)`), while the network-wide `ALLOW_SHIELDED_TRANSACTION` dynamic parameter remains `1`.
2. As an external client, use standalone Sapling/zk-SNARK libraries (independent of this node's Wallet API, i.e., not calling `createShieldedTransaction`) to build a valid, signed `ShieldedTransferContract` transaction, exactly as demonstrated by `ShieldedTransferActuatorTest.shieldedTransferValidationWorksWhenApiDisabled` [8](#0-7) .
3. Broadcast the transaction to the node via the standard `BroadcastTransaction` RPC.
4. Observe that `ShieldedTransferActuator.validate()` and `execute()` succeed and the shielded transfer is processed, despite `allowShieldedTransactionApi` being disabled on that node — confirming the setting is bypassed.

  public boolean execute(Object result)

    }

    DynamicPropertiesStore dynamicStore = chainBaseManager.getDynamicPropertiesStore();
    try {
      shieldedTransferContract = any.unpack(ShieldedTransferContract.class);
    } catch (InvalidProtocolBufferException e) {
      logger.debug(e.getMessage(), e);
      throw new ContractExeException(e.getMessage());
    }

    long fee = calcFee(shieldedTransferContract);
    try {
      if (shieldedTransferContract.getTransparentFromAddress().toByteArray().length > 0) {
        executeTransparentFrom(shieldedTransferContract.getTransparentFromAddress().toByteArray(),
            shieldedTransferContract.getFromAmount(), ret, fee);
      }
      Commons.adjustAssetBalanceV2(accountStore.getBlackhole(),
          CommonParameter.getInstance().getZenTokenId(), fee,
          accountStore, assetIssueStore, dynamicStore);
    } catch (BalanceInsufficientException e) {
      logger.debug(e.getMessage(), e);
      ret.setStatus(0, code.FAILED);
      ret.setShieldedTransactionFee(fee);
      throw new ContractExeException(e.getMessage());
    }

    executeShielded(shieldedTransferContract.getSpendDescriptionList(),
        shieldedTransferContract.getReceiveDescriptionList(), ret, fee);

    if (shieldedTransferContract.getTransparentToAddress().toByteArray().length > 0) {
      executeTransparentTo(shieldedTransferContract.getTransparentToAddress().toByteArray(),
          shieldedTransferContract.getToAmount(), ret, fee);
    }

    //adjust and verify total shielded pool value
    try {
      Commons.adjustTotalShieldedPoolValue(addExact(subtractExact(
          shieldedTransferContract.getToAmount(),
          shieldedTransferContract.getFromAmount()), fee), dynamicStore);
    } catch (ArithmeticException | BalanceInsufficientException e) {
      logger.debug(e.getMessage(), e);
      ret.setStatus(0, code.FAILED);
      ret.setShieldedTransactionFee(fee);
      throw new ContractExeException(e.getMessage());
    }

    ret.setStatus(0, code.SUCESS);
    ret.setShieldedTransactionFee(fee);
    return true;
  }

  /**
   * Test that shielded transfer transaction validation works even when
   * allowShieldedTransactionApi is disabled. This verifies that the API flag
   * only gates wallet/helper APIs, not the core transaction validation logic.
   */
  @Test
  public void shieldedTransferValidationWorksWhenApiDisabled() {
    boolean orig = Args.getInstance().isAllowShieldedTransactionApi();
    // Disable the shielded API (this should NOT affect transaction validation)
    Args.getInstance().setAllowShieldedTransactionApi(false);

    dbManager.getDynamicPropertiesStore().saveAllowShieldedTransaction(1);
    dbManager.getDynamicPropertiesStore().saveTotalShieldedPoolValue(AMOUNT);

    try {
      ZenTransactionBuilder builder = new ZenTransactionBuilder(wallet);
      SpendingKey sk = SpendingKey.random();
      ExpandedSpendingKey expsk = sk.expandedSpendingKey();
      PaymentAddress address = sk.defaultAddress();
      Note note = new Note(address, AMOUNT);
      IncrementalMerkleVoucherContainer voucher = createSimpleMerkleVoucherContainer(note.cm());
      byte[] anchor = voucher.root().getContent().toByteArray();
      dbManager.getMerkleContainer()
          .putMerkleTreeIntoStore(anchor, voucher.getVoucherCapsule().getTree());
      builder.addSpend(expsk, note, anchor, voucher);

      addZeroValueOutputNote(builder);

      long fee = dbManager.getDynamicPropertiesStore().getShieldedTransactionCreateAccountFee();
      String addressNotExist =
          Wallet.getAddressPreFixString() + "8ba2aaae540c642e44e3bed5522c63bbc21f0000";

      builder.setTransparentOutput(ByteArray.fromHexString(addressNotExist), AMOUNT - fee);

      TransactionCapsule transactionCap = builder.build();
      Contract contract =
          transactionCap.getInstance().toBuilder().getRawDataBuilder().getContract(0);
      ShieldedTransferActuator actuator = new ShieldedTransferActuator();
      actuator.setChainBaseManager(dbManager.getChainBaseManager()).setContract(contract)
          .setTx(transactionCap);

      // Validation should succeed even when API is disabled
      actuator.validate();
    } catch (ContractValidateException e) {
      Assert.fail("Shielded transfer validation should not throw ContractValidateException: "
          + e.getMessage());
    } catch (Exception e) {
      Assert.fail("Shielded transfer should not throw Exception: " + e.getMessage());
    } finally {
      Args.getInstance().setAllowShieldedTransactionApi(orig);
    }
  }
