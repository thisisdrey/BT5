### Title
FetchRemoteRequest.timeout has no upper bound, allowing indefinite-duration Gitaly RPCs / resource exhaustion - (File: internal/gitaly/service/repository/fetch_remote.go)

### Summary
`FetchRemoteRequest.timeout` is an unauthenticated-adjacent, ordinary-user-controlled field (set by any caller of the `FetchRemote` RPC) that is used directly to build a `context.WithTimeout` without any upper-bound (or even sane range) validation, mirroring the `queryDeadlineInterval` bug class: a numeric duration/deadline parameter that is fully attacker/caller controlled and unbounded on the high end.

### Finding Description
In `internal/gitaly/service/repository/fetch_remote.go`:

```go
func (s *server) FetchRemote(ctx context.Context, req *gitalypb.FetchRemoteRequest) (*gitalypb.FetchRemoteResponse, error) {
	if err := s.validateFetchRemoteRequest(ctx, req); err != nil {
		return nil, err
	}

	if req.GetTimeout() > 0 {
		var cancel context.CancelFunc
		ctx, cancel = context.WithTimeout(ctx, time.Duration(req.GetTimeout())*time.Second)
		defer cancel()
	}
	...
``` [1](#0-0) 

The field is only checked for `> 0`, i.e. any positive value is accepted, with no ceiling. This is directly analogous to the reported `queryDeadlineInterval` issue: a caller-supplied numeric duration parameter lacking an upper bound is fed straight into a deadline/timeout calculation.

Two concrete problems follow the same shape as the report:
1. **Unbounded resource hold / DoS surface**: `req.GetTimeout()` is an `int32` value from the request. Multiplying it by `time.Second` (`time.Duration`, itself an `int64` of nanoseconds) can produce extremely large or overflowed duration values when a caller supplies a large `int32` (up to `2147483647`). `2147483647 * time.Second` far exceeds `time.Duration`'s max representable value (~292 years, but a `int32` seconds value of ~2.1 billion seconds is only ~68 years, which does not overflow `time.Duration` itself, but it does create an effectively unbounded remote-fetch operation). A caller can force Gitaly to hold the goroutine, the underlying `git fetch` subprocess, the quarantine directory, and any acquired concurrency-limiter slot open for the full duration of that timeout, since there is no server-side maximum cap on this externally supplied value.
2. **No sanity/DoS guard analogous to the report's Recommendation**: The Spearbit fix for the AxiomV2Query issue was to add an explicit upper bound (e.g., one week) to the affected field. Gitaly's `FetchRemote` handler performs no equivalent bound check — it only guards against `<= 0`, not against unreasonably large values.

### Impact Explanation
An authenticated Gitaly RPC caller (e.g., a GitLab backend request forwarding user-initiated mirror/pull-mirror fetches) can set an arbitrarily large `timeout` value on `FetchRemoteRequest`. This ties up:
- A `git-fetch(1)` subprocess and its quarantine directory for the full timeout duration if the remote hangs or is slow/unresponsive.
- Any concurrency-limiter slot/queue entries associated with the RPC method, since the RPC will not return (success or failure) until either the fetch completes or the (attacker-controlled, effectively unbounded) timeout elapses.
- Server resources (goroutines, subprocess handles) for a duration entirely dictated by the caller rather than the operator, which is the same root cause pattern as the report: a caller-controlled numeric duration parameter with no server-enforced ceiling, leading to funds/requests being “locked” for excessive periods (in Gitaly's case, RPC slots/resources being tied up for excessive periods), enabling resource-exhaustion-style DoS against the Gitaly node.

### Likelihood Explanation
Reachability requires only invoking the `FetchRemote` RPC with a crafted `timeout` field, which is a standard, documented request field exposed to any client authorized to call `RepositoryService`. No privileged access, MITM, or malicious-peer position is required — it is a normal RPC input from an ordinary caller. The only gating factor is standard Gitaly RPC auth (shared token), which is the normal caller of this RPC (e.g., a GitLab Rails/Sidekiq worker requesting a repository mirror fetch), not a privileged operator; a request whose `timeout` value is influenced by user-controllable settings (e.g., mirror configuration) increases exploitability, though I could not fully verify from the indexed code whether the `timeout` value is ever derived from truly untrusted end-user input further up the call chain (this would require confirming how GitLab Rails populates `FetchRemoteRequest.timeout`, which is outside the scope of the indexed Gitaly repo).

### Recommendation
Add an explicit upper bound to `FetchRemoteRequest.timeout` validation in `validateFetchRemoteRequest` (or in `FetchRemote` itself before the `context.WithTimeout` call), e.g., reject or clamp values above a defined maximum (such as a configurable maximum fetch timeout, analogous to Gitaly's existing `[timeout]` configuration section used for `UploadPackNegotiation`/`UploadArchiveNegotiation`) rather than accepting any `> 0` value unconditionally.

### Proof of Concept
Because the exact upstream range/enforcement of the `timeout` field in `proto/repository.proto` could not be fully confirmed within the available tool budget (the proto excerpt for `FetchRemoteRequest.timeout` was not retrieved before the iteration limit), a definitive numeric PoC value cannot be given with full confidence. Conceptually, the PoC is:

```go
client.FetchRemote(ctx, &gitalypb.FetchRemoteRequest{
    Repository: repo,
    RemoteParams: &gitalypb.Remote{Url: "https://example.com/slow-or-unresponsive.git"},
    Timeout: 2147483647, // int32 max seconds ≈ 68 years — no upper bound enforced
})
```
This request is accepted by `validateFetchRemoteRequest` (which only checks `> 0`) and results in `context.WithTimeout` being created with an effectively unbounded deadline, holding the RPC, subprocess, and quarantine resources open for the caller-chosen duration. [1](#0-0)
