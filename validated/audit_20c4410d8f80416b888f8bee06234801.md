### Title
Uncontrolled Backtracking DoS via Unbounded PCRE Query in `SearchFilesByContent` - (File: internal/gitaly/service/repository/search_files.go)

### Summary
`SearchFilesByContent` forwards the RPC's `query` field directly, unvalidated and unbounded, into `git grep --perl-regexp -e <query>`. Because `--perl-regexp` invokes a backtracking regex engine (PCRE) rather than Git's default linear-time engines, an ordinary authenticated user can submit a pathological regular expression that triggers catastrophic backtracking, hanging the `git grep` child process and consuming CPU — the same bug class as CVE-2023-28755 (uncontrolled resource consumption from a backtracking regex applied to attacker-controlled input), just moved from Ruby's `URI` regex to Git's PCRE engine.

### Finding Description
In `internal/gitaly/service/repository/search_files.go`, `SearchFilesByContent` builds the grep command as follows: [1](#0-0) 

The `-e` value comes straight from `req.GetQuery()` with `--perl-regexp` enabled, and `validateSearchFilesRequest` only checks that the query is non-empty — it enforces no length limit and performs no complexity/compile-time check: [2](#0-1) 

This is notably inconsistent with the sibling `SearchFilesByName` RPC in the same file, which treats its `Filter` field as untrusted regex input: it caps the pattern length via `searchFilesFilterMaxLength` (1000 chars) and compiles it with Go's `regexp` package (RE2, a linear-time, backtracking-free engine that is immune to ReDoS by construction): [3](#0-2) 

No equivalent length cap or safe-engine substitution exists for the `Query` field consumed by `--perl-regexp` in `SearchFilesByContent`. PCRE, like Ruby's `Regexp`/`URI` engine exploited in CVE-2023-28755, resolves ambiguous quantifier nesting via backtracking, so crafted patterns (e.g., nested/overlapping quantifiers) can produce super-linear or exponential match time on adversarial input strings, exactly the bug class described in the external report.

### Impact Explanation
Any user able to invoke `SearchFilesByContent` (a normal, non-privileged accessor RPC available to any client with repository access) can spawn a `git grep --perl-regexp` process with an attacker-chosen pattern that never terminates promptly, pinning a CPU core for the lifetime of the request. Repeated invocation multiplies the effect across the Gitaly node's `git` process pool, degrading or denying service for all repositories served by that Gitaly node — a DoS of an RPC handler through git command construction, one of the explicitly accepted analog categories.

### Likelihood Explanation
The RPC is reachable by any actor authorized to read the repository (the same trust level as a normal fetch/browse operation) and requires no privileged access, leaked tokens, or a malicious peer — only a single crafted `query` string. The precondition (non-empty query, valid ref) is trivial to satisfy, and the underlying PCRE backtracking behavior is a well-known, reliably reproducible property of the regex engine, making exploitation straightforward and repeatable.

### Recommendation
- Apply the same safeguards used for `SearchFilesByName`'s `Filter` to `SearchFilesByContent`'s `Query`: enforce a maximum length (e.g., reuse `searchFilesFilterMaxLength` or a dedicated constant) before passing it to `git grep`.
- Consider validating/pre-compiling the pattern with Go's RE2-based `regexp` package (rejecting constructs unsupported by RE2) to detect obviously malicious patterns before invoking `--perl-regexp`, or dropping `--perl-regexp` in favor of Git's default (non-backtracking) grep engine unless PCRE features are actually required.
- If PCRE semantics must be kept, bound `git grep` execution time/CPU (e.g., via context timeout combined with process cancellation) so a hung match cannot indefinitely occupy a worker.

### Proof of Concept
1. As an authenticated client with access to a repository, call `SearchFilesByContent` with `Ref` set to a valid branch and `Query` set to a classic catastrophic-backtracking PCRE pattern combined with a long non-matching input line committed to the repository, e.g. pattern:
   `(a+)+$` (or `(a|aa)+$`, `(a|a?)+$`)
   against a tracked file containing a long line of `a` characters followed by a non-matching character (`aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaX`).
2. Observe that the spawned `git grep --perl-regexp -e "(a+)+$" <ref>` process's CPU time grows super-linearly with the length of the offending line, analogous to the `Benchmark.bm` scaling demonstrated in the original CVE-2023-28755 report, hanging the RPC and consuming a CPU core until the process is killed or context deadline is reached.

func validateSearchFilesRequest(ctx context.Context, locator storage.Locator, req searchFilesRequest) error {
	if err := locator.ValidateRepository(ctx, req.GetRepository()); err != nil {
		return err
	}

	if len(req.GetQuery()) == 0 {
		return errors.New("no query given")
	}

	if len(req.GetRef()) == 0 {
		return errors.New("no ref given")
	}

	if bytes.HasPrefix(req.GetRef(), []byte("-")) {
		return errors.New("invalid ref argument")
	}

	return nil
}
