### Title
NullPointerException in `UpdateAssetActuator.execute` from unchecked V2 asset-store lookup - (File: actuator/src/main/java/org/tron/core/actuator/UpdateAssetActuator.java)

### Summary
`UpdateAssetActuator.execute` unconditionally looks up the caller's asset in `AssetIssueV2Store` and immediately calls setters on the result without checking for `null`, mirroring the ALPINE-CVE-2023-33461 pattern where `iniparser_getstring`'s possible `NULL` return is dereferenced by `iniparser_getlongint` without a check.

### Finding Description
In `execute()`, the code does: [1](#0-0) 
```java
AssetIssueStore assetIssueStoreV2 = assetIssueV2Store;
assetIssueCapsuleV2 = assetIssueStoreV2.get(accountCapsule.getAssetIssuedID().toByteArray());

assetIssueCapsuleV2.setFreeAssetNetLimit(newLimit);
```
This lookup and dereference happen unconditionally, regardless of the `allowSameTokenName` mode.

However, `validate()` only guards the *matching* branch: when `dynamicStore.getAllowSameTokenName() == 0` (the "closed"/legacy mode), it checks only `assetIssueStore.get(account.getAssetIssuedName())` (the V1 store, keyed by name) and never checks `assetIssueV2Store.get(account.getAssetIssuedID())`: [2](#0-1) 

If a token-issuing account's `AssetIssuedID` field (the V2 key) is absent/empty or does not resolve to an entry in `AssetIssueV2Store` — a legitimate legacy-mode scenario where only the V1 name-keyed record exists — `validate()` passes, but `execute()` performs `assetIssueStoreV2.get(...)` which returns `null` (per the store's `getUnchecked`-style `get()`, consistent with `ContractStore.get()` returning `getUnchecked`), and the immediate `assetIssueCapsuleV2.setFreeAssetNetLimit(...)` call throws a `NullPointerException`. This is exactly the CVE's bug class: a getter (`getAssetIssuedID`/`store.get`) can legitimately return an empty/absent value, and the consumer does not check for it before dereferencing.

### Impact Explanation
`UpdateAssetContract` is a normal, broadcastable transaction any account that has issued an asset can submit. An uncaught `RuntimeException` (NPE) thrown from `execute()` is not one of the caught exception types (`InvalidProtocolBufferException`) in the actuator, so it propagates up through actuator execution during block application in `Manager`, which can crash/halt transaction processing for the node applying that block — a node availability/consensus-processing impact reachable from a single signed transaction.

### Likelihood Explanation
Likelihood depends on whether the described state (V1-issued asset with missing/empty V2 `AssetIssuedID`) is actually reachable in the current codebase and the exact null-return semantics of `AssetIssueV2Store.get()`; I was not able to fully verify the store's exact behavior (whether `get()` truly returns `null` versus throwing, or whether `AssetIssuedID` is always populated regardless of legacy mode) before running out of tool budget. This should be validated against `AssetIssueV2Store`/`AssetIssueStore` implementations and asset-issuance actuator logic (`AssetIssueActuator`) to confirm whether `AssetIssuedID` can legitimately be empty while `allowSameTokenName == 0`.

### Recommendation
In `UpdateAssetActuator.execute()`, only perform the `assetIssueV2Store` lookup/update within the branch that actually requires it (mirroring `validate()`'s branching), and add an explicit `null`/not-found check before dereferencing `assetIssueCapsuleV2`, throwing a handled `ContractExeException` instead of allowing an NPE to propagate.

### Proof of Concept
Conceptual PoC (unverified against runtime store semantics):
1. Operate the chain with `AllowSameTokenName == 0` (legacy V1 mode).
2. Have an account issue an asset via the legacy flow such that `AccountCapsule.getAssetIssuedName()` is set but `getAssetIssuedID()` remains empty/unset or does not map to any `AssetIssueV2Store` entry.
3. Submit an `UpdateAssetContract` transaction from that account. `validate()` passes because it only checks the V1 `assetIssueStore` in this mode.
4. During `execute()`, `assetIssueStoreV2.get(accountCapsule.getAssetIssuedID().toByteArray())` returns `null`; the subsequent `assetIssueCapsuleV2.setFreeAssetNetLimit(newLimit)` throws `NullPointerException`, which is uncaught by the actuator's `catch (InvalidProtocolBufferException e)` block.
