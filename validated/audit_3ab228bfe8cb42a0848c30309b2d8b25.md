Audit Report

## Title
Native value sent to `HAS_CONTRACT_INFO = false` precompiles (ERC20/XCM) is silently accepted and permanently locked - (File: `substrate/frame/revive/src/exec.rs`)

## Summary
`pallet-revive`'s `Stack::run` transfers any attached native `value` from caller to the callee's mapped account unconditionally for non-delegate calls via `Self::transfer_from_origin` [1](#0-0) , with no distinction for precompiles, while the account-creation/consumer-protection logic that follows only runs `if precompile.has_contract_info()` [2](#0-1) . Built-in precompiles such as `ERC20` and `XcmPrecompile` declare `HAS_CONTRACT_INFO = false` and never read, forward, or reject `value_transferred`, so any value attached to a call targeting them is credited to an address with no spending logic or consumer protection and no way to move the balance back out.

## Finding Description
The generic `transfer` helper pulls a nonexistent destination account into existence by paying the ED from the origin and crediting the value whenever `value > 0`, regardless of whether the destination is a contract, EOA, or precompile: `if <System<T>>::account_exists(to) { ... } else { pay ED, credit value }` [3](#0-2) . This runs unconditionally before the precompile's handler executes [1](#0-0) .

The `Precompile` trait documents that when `HAS_CONTRACT_INFO = false`, "No account or any other state will be created for the address" and "Only `call` should be implemented" [4](#0-3) , but there is no enforcement of this contract at the trait or dispatch level — no `is_zero()` check on `value_transferred()` exists anywhere in `precompiles.rs` or in the `call()` implementations of `ERC20` or `XcmPrecompile`. `ERC20::call` dispatches directly on the ABI-decoded call variant without inspecting `env.value_transferred()` [5](#0-4) , and `XcmPrecompile::call` likewise never inspects it [6](#0-5) .

Because these precompiles have `HAS_CONTRACT_INFO = false`, the mint/consumer-protection block that would apply to `has_contract_info()` precompiles is skipped [7](#0-6) , and — more importantly — there is no dispatchable, precompile function, or code path that lets value be withdrawn from these precompiles' mapped accounts, since their `call()` implementations never reference the destination account's balance at all. The test `pure_precompile_works` empirically demonstrates the exact mechanism: attaching value to a call against a `HAS_CONTRACT_INFO = false` precompile causes `Pallet::<Test>::evm_balance(&precompile_addr)` to reflect the transferred amount [8](#0-7) , confirming the transfer happens and persists at that address with no accounting for retrieval.

## Impact Explanation
This is a permanent user-fund lock: any value sent alongside a call to a `HAS_CONTRACT_INFO = false` precompile (e.g., the `ERC20` asset precompile, or the fixed-address `XcmPrecompile` at address `10`) is credited into an account that no EOA key or contract logic can spend from, since the precompile's `call()` implementation neither uses nor forwards `value_transferred()` and no governance or system call exists to reclaim it. This matches the "permanent user-fund or bridge-state lock" category in the impact gate.

## Likelihood Explanation
Any unprivileged caller can trigger this by attaching non-zero `value` to a transaction/call targeting a well-known, discoverable precompile address (fixed XCM precompile address, or ERC20 asset precompile addresses) — no privileged access, malicious peer, or governance action is required. Standard ERC20 tooling/wallets may not always guarantee `msg.value = 0`, making accidental loss realistically reachable, and the bug is deterministically reproducible via `bare_call`.

## Recommendation
Enforce the "no state, no value" contract for `HAS_CONTRACT_INFO = false` precompiles: either add a check in `Stack::run`/`do_transaction` that rejects a nonzero `frame.value_transferred` when calling into a precompile that returns `false` for `has_contract_info()` unless the precompile explicitly opts in to receiving value, or require each `HAS_CONTRACT_INFO = false` precompile implementation (e.g. `ERC20::call`, `XcmPrecompile::call`) to explicitly `ensure!(env.value_transferred().is_zero(), ...)` at the top of `call()`.

## Proof of Concept
1. In a test using `ExtBuilder`, fund an account and use `builder::bare_call` to invoke the `XcmPrecompile` fixed address `10` (or an `ERC20` asset precompile address) with a nonzero `evm_value`/`native_value` and a valid ABI-encoded `IXcmCalls::send`/`IERC20Calls::transfer` payload.
2. Observe the call succeeds and executes the XCM/ERC20 logic normally, ignoring the value.
3. Assert `Pallet::<Test>::evm_balance(&precompile_addr)` equals the transferred amount, mirroring the pattern already demonstrated in `pure_precompile_works` [8](#0-7) .
4. Confirm no extrinsic, precompile function, or governance call exists that can move balance out of the precompile's mapped account — the funds remain permanently stranded.
