### Title
Non-Constant-Time Authorization Token Comparison Enables Remote `auth_token` Recovery via Timing Side-Channel - (File: `stackslib/src/net/api/postblock_proposal.rs`)

### Summary
Six RPC request handlers in `stackslib/src/net/api/` authenticate privileged, state-mutating and compute-intensive endpoints by comparing the client-supplied `authorization` header against the node's configured secret using Rust's native string inequality operator (`auth_header != password`). This is a byte-wise comparison that short-circuits on the first mismatching byte, leaking timing information proportional to the length of the correct-byte prefix an attacker has guessed, analogous to the Umbraco CVE-2025-46736 timing side-channel (CWE-204).

### Finding Description
Each of the following handlers gates access with the identical pattern: [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4) [6](#0-5) 

`password` is the node's `connection_options.auth_token`, documented as a plain-text secret that "must exactly equal the node's configured password" [7](#0-6)  and is also used to gate `/v2/blocks?broadcast=1` [8](#0-7) .

Rust's `String`/`&str` `PartialEq` implementation compares underlying byte slices, which returns as soon as a length mismatch or a differing byte is found — it is not constant-time. A remote, unauthenticated attacker can measure response latency across many requests with different candidate token prefixes; requests whose prefix matches more bytes of the real secret take measurably longer to reject (more comparisons performed before divergence), enabling classic byte-at-a-time timing recovery of `auth_token`. I confirmed by grepping the repository that no constant-time comparison primitive (e.g., `subtle::ConstantTimeEq`, `ring::constant_time`, or an internal helper) is used anywhere in the codebase — every one of these six handlers uses the same vulnerable `!=` pattern with no alternative implementation to fall back on.

Once the token is recovered, the attacker gains full write access to `/v3/block_proposal` (block proposal submission consumed by the signer, `stackslib/src/net/api/postblock_proposal.rs`), the authenticated `broadcast=1` path of `/v2/blocks` (`stackslib/src/net/api/postblock_v3.rs`), plus `/v3/blocks/simulate`, `/v3/blocks/replay`, `/v3/contracts/fast-call-read`, and `/v3/transactions/simulate` — breaking the "authenticated vs stored secret" equality that these RPC gates are meant to enforce.

### Impact Explanation
This breaks the auth-gate equality on multiple privileged endpoints. Recovering `auth_token` grants unauthorized write access analogous to a full auth bypass: an attacker could submit forged/invalid block proposals to `/v3/block_proposal` (impersonating the miner-signer channel) or broadcast blocks via the authenticated `/v2/blocks?broadcast=1` path. This aligns with the "Critical — unauthenticated/unauthorized write to state... auth bypass" bucket, since possession of the shared secret is the only gate protecting these endpoints and a network-observable timing channel undermines it.

### Likelihood Explanation
Exploitation requires many network round-trips (timing attacks against secrets of realistic length typically need thousands of samples per byte over a network, more with jitter), which lowers practical likelihood on high-latency/variance networks, but the vulnerability is trivially remote and unauthenticated — no credentials, node secret, or privileged role are required to begin probing. The consistent absence of any constant-time comparison utility across all six handlers indicates this is a systemic pattern rather than an isolated oversight.

### Recommendation
Replace all six `auth_header != password` string comparisons with a constant-time comparison (e.g., via the `subtle` crate's `ConstantTimeEq`, or `ring::constant_time::verify_slices_are_equal`), applied uniformly across `postblock_proposal.rs`, `postblock_v3.rs`, `blocksimulate.rs`, `blockreplay.rs`, `fastcallreadonly.rs`, and `txsimulate.rs`. Consider factoring this into a single shared helper (e.g., `fn check_auth_token(header: &str, expected: &str) -> bool`) to avoid future re-introduction of the vulnerable pattern.

### Proof of Concept
1. Configure a node with `connection_options.auth_token = "<N-character-secret>"`.
2. From a remote unauthenticated client, repeatedly POST to `/v3/block_proposal` (or any of the other five endpoints) with `authorization` headers consisting of a guessed prefix followed by all possible next bytes, holding the total header length constant.
3. For each candidate byte, measure the average round-trip time to receive the `401 Unauthorized` response over many trials (to average out network/jitter noise).
4. The candidate byte yielding the (statistically) largest response latency is the correct next byte of the secret, because the comparison proceeds one byte further before the mismatch is detected.
5. Repeat byte-by-byte until the full `auth_token` is recovered, then use it to submit unauthorized block proposals or broadcast blocks.
