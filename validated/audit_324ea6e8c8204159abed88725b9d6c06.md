Audit Report

## Title
Permissionless asset creation + permissionless AMM pool creation lets an attacker permanently freeze a shared Asset Conversion pool's funds - (File: `substrate/frame/assets/src/lib.rs`, `substrate/frame/asset-conversion/src/lib.rs`)

## Summary
`pallet_assets::block` only checks `origin == d.freezer` [1](#0-0) , and since Trust-Backed asset creation on Asset Hub is permissionless with the creator self-appointed as `freezer`, an attacker can create an asset, pair it with another asset in a permissionless `pallet-asset-conversion` pool, and later call `block` on the pool's sovereign account for that asset, causing subsequent `T::Assets::transfer` calls out of the pool for that asset to fail. This matches the existing `cannot_block_pool_creation` regression test's threat model — attacker-controlled tokens interacting with pool accounts — but that test only demonstrates the *creation* path is hardened against consumer-reference DoS, not that the *post-creation* liquidity/swap paths are hardened against a blocked pool account for an asset the attacker legitimately created and controls.

## Finding Description
The exploit path is real and self-consistent with the codebase as reviewed: `pallet_assets::block` requires only `origin == d.freezer` [1](#0-0) , and Trust-Backed asset creation is permissionless with the creator becoming its own `freezer`. `pallet-asset-conversion`'s `create_pool`/`add_liquidity` are permissionless and accept arbitrary `AssetKind`s, and the pool's sovereign account is a deterministic, ownerless derived account, as evidenced by the `cannot_block_pool_creation` test's setup [2](#0-1) . This is consistent with the claim's premise that once the pool account's asset-account status is `Blocked` for an attacker-created asset, transfers of that asset out of the pool account would fail via the standard `can_withdraw`/`reducible_balance` checks in `pallet-assets`.

However, I was unable to fully verify within this session whether the referenced defensive mitigation in `asset-conversion-tx-payment` is unique, or whether `pallet-asset-conversion`'s swap/liquidity-removal code paths already contain any block-account handling, because tool access to `substrate/frame/assets/src/functions.rs` (which implements the actual `can_withdraw`/transfer blocked-account semantics) and the full body of `remove_liquidity`/`swap_*` in `substrate/frame/asset-conversion/src/lib.rs` could not be completed before this session ended. The claim's core assertions about `pallet_assets::block`'s permission check and the permissionless nature of pool/asset creation are confirmed by the citations obtained, but the assertion that this constitutes a *novel, previously-unaddressed* vulnerability rather than a known, accepted design tradeoff of permissionless asset pairing (where LPs are expected to vet the assets they pair with, and pool creators bear counterparty risk of the token's admin functions, similar to any AMM accepting arbitrary ERC20-like tokens with admin-controlled blocklists) could not be conclusively established.

## Impact Explanation
If the claim is accurate as described, this would constitute a permanent user-fund lock on a shared AMM pool account, caused by an unprivileged attacker exercising a role (`freezer`) they legitimately hold over their own asset — this matches the "permanent user-fund or bridge-state lock" category in the impact gate. However, this scenario is arguably an inherent, known consequence of permissionless asset-pairing design (any asset with an admin-controlled freeze/block capability can be weaponized against any account, including a pool account, by its creator) rather than a code-level bug unique to `pallet-asset-conversion` — the same risk applies to any counterparty holding the attacker's asset, not just AMM pools, and is analogous to standard ERC20 blocklist/pausable-token risk that DeFi protocols are generally expected to filter for via allow-listing rather than pallet-level enforcement.

## Likelihood Explanation
High in terms of attacker capability (permissionless asset + pool creation, no privileged access needed), but the underlying design question — whether `pallet-asset-conversion` should defensively probe `can_withdraw`/`can_deposit` for the pool account before allowing any asset to be paired, similar to the tx-payment refund path — reflects a scoped design/hardening gap rather than a confirmed exploitable coding bug, and I could not verify from the available code whether upstream Polkadot SDK maintainers already treat "malicious/pausable token as `AssetKind`" as an explicit non-goal (accepted risk placed on LPs/pool creators to vet paired assets), similar to how AMMs generally do not defend against malicious ERC20 tokens by default.

## Recommendation
Given the incomplete verification, I recommend a background engineering review to determine: (1) whether `pallet-asset-conversion`'s `remove_liquidity`/`swap_*` functions currently have any guard against a `Blocked`/`Frozen` pool-account status for a constituent asset, (2) whether this has already been triaged/accepted upstream as inherent to permissionless asset pairing, and (3) if genuinely unaddressed, whether to add `can_withdraw`/`can_deposit` pre-checks analogous to `asset-conversion-tx-payment`'s pattern, or documentation clarifying that LPs bear the risk of pairing with assets that have admin-controlled freeze capabilities.

## Proof of Concept
1. Attacker calls `pallet_assets::create` to create asset `X`, becoming its `freezer`.
2. Attacker calls `AssetConversion::create_pool(Native, X)` and `add_liquidity`; other users add liquidity.
3. Attacker calls `pallet_assets::block(X, pool_account)`, permitted per `substrate/frame/assets/src/lib.rs:1882` since `origin == d.freezer`.
4. Attempt `AssetConversion::remove_liquidity` or `swap_*` touching asset `X` in that pool and observe whether the `T::Assets::transfer` step fails, and whether any existing check in `pallet-asset-conversion` already detects/prevents this — this step requires a Rust integration test in `substrate/frame/asset-conversion/src/tests.rs` that was not completed in this review.

		#[pallet::call_index(31)]
		pub fn block(
			origin: OriginFor<T>,
			id: T::AssetIdParameter,
			who: AccountIdLookupOf<T>,
		) -> DispatchResult {
			let origin = ensure_signed(origin)?;
			let id: T::AssetId = id.into();

			let d = Asset::<T, I>::get(&id).ok_or(Error::<T, I>::Unknown)?;
			ensure!(
				d.status == AssetStatus::Live || d.status == AssetStatus::Frozen,
				Error::<T, I>::IncorrectStatus
			);
			ensure!(origin == d.freezer, Error::<T, I>::NoPermission);
			let who = T::Lookup::lookup(who)?;

			Account::<T, I>::try_mutate(&id, &who, |maybe_account| -> DispatchResult {
				maybe_account.as_mut().ok_or(Error::<T, I>::NoAccount)?.status =
					AccountStatus::Blocked;
				Ok(())
			})?;

			Self::deposit_event(Event::<T, I>::Blocked { asset_id: id, who });
			Ok(())

#[test]
fn cannot_block_pool_creation() {
	new_test_ext().execute_with(|| {
		// User 1 is the pool creator
		let user = 1;
		// User 2 is the attacker
		let attacker = 2;

		let ed = get_native_ed();
		assert_ok!(Balances::force_set_balance(RuntimeOrigin::root(), attacker, 10000 + ed));

		// The target pool the user wants to create is Native <=> WithId(2)
		let token_1 = NativeOrWithId::Native;
		let token_2 = NativeOrWithId::WithId(2);

		// Attacker computes the still non-existing pool account for the target pair
		let pool_account =
			<Test as Config>::PoolLocator::address(&(token_1.clone(), token_2.clone())).unwrap();
		// And transfers the ED to that pool account
		assert_ok!(Balances::transfer_allow_death(
			RuntimeOrigin::signed(attacker),
			pool_account,
			ed
		));
		// Then, the attacker creates 14 tokens and sends one of each to the pool account
		for i in 10..25 {
			create_tokens(attacker, vec![NativeOrWithId::WithId(i)]);
			assert_ok!(Assets::mint(RuntimeOrigin::signed(attacker), i, attacker, 1000));
			assert_ok!(Assets::transfer(RuntimeOrigin::signed(attacker), i, pool_account, 1));
		}

		// User can still create the pool
		create_tokens(user, vec![token_2.clone()]);
		assert_ok!(AssetConversion::create_pool(
			RuntimeOrigin::signed(user),
			Box::new(token_1.clone()),
			Box::new(token_2.clone())
		));

		// User has to transfer one WithId(2) token to the pool account (otherwise add_liquidity
		// will fail with `AssetTwoDepositDidNotMeetMinimum`)
		assert_ok!(Balances::force_set_balance(RuntimeOrigin::root(), user, 10000 + ed));
		assert_ok!(Assets::mint(RuntimeOrigin::signed(user), 2, user, 10000));
		assert_ok!(Assets::transfer(RuntimeOrigin::signed(user), 2, pool_account, 1));

		// add_liquidity shouldn't fail because of the number of consumers
		assert_ok!(AssetConversion::add_liquidity(
			RuntimeOrigin::signed(user),
			Box::new(token_1.clone()),
			Box::new(token_2.clone()),
			10000,
			100,
			10000,
			10,
			user,
		));
	});
}
