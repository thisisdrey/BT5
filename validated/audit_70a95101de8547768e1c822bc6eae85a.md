### Title
Deflationary/Fee-on-Transfer/Rebasing NEP-141 Tokens Break Ledger-vs-Reserve Conservation in `Contract::deposit` - (File: contracts/defuse/src/contract/tokens/nep141/deposit.rs)

### Summary
`Contract::ft_on_transfer` credits a depositor's internal balance and the protocol's `total_supplies` ledger with the full nominal `amount` reported by the NEP-141 token contract's `ft_transfer_call`, without any verification that this amount corresponds to tokens actually held in reserve by the Defuse contract. For deflationary/fee-on-transfer or rebasing NEP-141 tokens, the value credited to the internal multi-token ledger can permanently exceed the real balance available in the underlying token, breaking the conservation invariant that `total_supplies[token] == actual reserve held for token`.

### Finding Description
On deposit, `ft_on_transfer` receives `amount: U128` — the value the token contract asserts it has moved to the receiver (Defuse) — and immediately calls `self.deposit(receiver_id, [(token_id, amount.0)], ...)`, which increments both the depositor's `token_balances` and the global `total_supplies` for that `TokenId` by the full `amount`: [1](#0-0) 

The `deposit` implementation performs no comparison against the contract's actual on-chain balance of the underlying token; it purely trusts the `amount` value: [2](#0-1) 

`TokenId::Nep141` is derived only from `env::predecessor_account_id()` — i.e., any NEP-141-compliant contract can be used as a payment/deposit asset without restriction: [3](#0-2) 

There is no token whitelist or fee/rebase awareness anywhere in `contracts/defuse`. If the token is:
- **Fee-on-transfer/deflationary**: the token's own `ft_transfer_call` implementation may still report the pre-fee `amount` to `ft_on_transfer` (or, even if it reports the post-fee amount honestly, any subsequent transfer *out* of the vault, e.g. paying another user via `mt_transfer`, does not re-verify the real reserve either — see `internal_mt_batch_transfer`, which only manipulates the internal ledger, never touching the real token contract until withdrawal), so the ledger balance overstates real backing.
- **Rebasing (negative rebase)**: the real token balance of the Defuse contract can decrease after deposit without the ledger being adjusted, again leaving `total_supplies` overstating real reserve.

This breaks the equality that should hold for a custodial ledger: `Σ internal token_balances(token) == real reserve of token held by contract`. Once broken, honest users' internally recorded balances for that `TokenId` are not fully redeemable — the last withdrawer(s) via `ft_withdraw`/`mt_transfer_call` for that asset will find the vault's real balance insufficient, causing failed/reverted withdrawals (and any refund mechanism in `ft_resolve_withdraw`, which re-deposits into the internal ledger and increases `total_supplies` again on failure) can never restore the lost real value: [4](#0-3) 

Additionally, because the internal ledger is fungible and tradable via `Transfer`/`TokenDiff` intents, an attacker who deposits a deflationary token gets credited more ledger balance than real value delivered, and can immediately use that inflated ledger balance in intents (transfers, swaps via `TokenDiff`) to extract genuine value from other users/tokens before anyone attempts to redeem the deflationary token itself.

### Impact Explanation
This is a Critical-class issue: it allows tokens to be credited to the internal ledger (`total_supplies`/`token_balances`) that are not backed by an equivalent real reserve, i.e., value is credited without valid backing. Since `total_supplies` is fungible and immediately spendable/transferable/tradeable within the protocol (e.g., via `Transfer` and `TokenDiff` intents), an attacker can convert this "phantom" balance into real assets belonging to other users before the shortfall is discovered, and ultimately funds for legitimate holders of that `TokenId` become permanently unredeemable (frozen/lost) once the real reserve is depleted.

### Likelihood Explanation
Likelihood is not purely theoretical for this repo because the protocol places no restriction on which NEP-141 contracts can be deposited — `TokenId::Nep141(Nep141TokenId::new(env::predecessor_account_id()))` accepts any caller as a valid token, and there is no fee/rebase detection, balance reconciliation, or whitelist anywhere in `contracts/defuse`. Any account owner of a subdomain-style community/pool who chooses (or is tricked into accepting) a deflationary or rebasing NEP-141 token as a deposit asset exposes all depositors of that specific `TokenId` to this risk, with no protocol-level safeguard or even a documented warning in this repository.

### Recommendation
Either:
1. Reconcile ledger credit against actual balance delta: after `ft_transfer_call` completes, compare the Defuse contract's real `ft_balance_of(self)` before and after the transfer and credit only the actual delta received, instead of trusting the caller-supplied `amount`; or
2. Introduce an explicit allow-list/registration step for NEP-141 tokens that verifies (or requires attestation) that the token is not fee-on-transfer/rebasing before it can be used as a `TokenId::Nep141` asset; or
3. Periodically/on-withdrawal reconcile `total_supplies[token]` against the real token balance and socialize any shortfall rather than allowing a first-come-first-served drain.

### Proof of Concept
1. Deploy (or use) a NEP-141 token contract `FeeToken` whose `ft_transfer_call` deducts a 10% fee on every transfer but still calls `ft_on_transfer(sender_id, amount=1000, msg)` on the Defuse contract, while only 900 `FeeToken` units are actually moved into the Defuse contract's `FeeToken` account.
2. User A calls `FeeToken::ft_transfer_call(defuse.near, 1000, msg="")`. Defuse's `ft_on_transfer` executes `self.deposit(user_a, [(Nep141(FeeToken), 1000)], ...)`, crediting User A's internal balance and `total_supplies[Nep141(FeeToken)]` with `1000`, while Defuse's real `FeeToken` balance only increased by `900`.
3. User A immediately submits a `Transfer` intent moving the full `1000` internal `FeeToken` balance to User B, or a `TokenDiff` intent swapping it for `1000` worth of a genuine, fully-backed token from a counterparty/solver.
4. When User B (or any holder of `FeeToken` `TokenId`) later attempts `ft_withdraw` for the full recorded ledger amount, the Defuse contract's real `FeeToken` reserve is insufficient by the accumulated fee shortfall, causing later withdrawals to fail/lose funds — demonstrating `Σ token_balances(FeeToken) > real FeeToken reserve held by contract`.     fn ft_on_transfer(
        &mut self,
        sender_id: AccountId,
        amount: U128,
        msg: String,
    ) -> PromiseOrValue<U128> {
        require!(amount.0 > 0, "zero amount");

        let token_id = TokenId::Nep141(Nep141TokenId::new(env::predecessor_account_id()));

        let DepositMessage {
            receiver_id,
            action,
        } = if msg.is_empty() {
            DepositMessage::new(sender_id.clone())
        } else {
            msg.parse().unwrap_or_else(|e| panic!("{e}"))
        };

        self.deposit(
            receiver_id.clone(),
            [(token_id.clone(), amount.0)],
            Some("deposit"),
        )
        .unwrap_or_else(|err| err.panic());

    pub(crate) fn deposit(
        &mut self,
        owner_id: AccountId,
        tokens: impl IntoIterator<Item = (TokenId, u128)>,
        memo: Option<&str>,
    ) -> Result<()> {
        let owner = self
            .storage
            .accounts
            .get_or_create(owner_id.clone())
            // deposits are allowed for locked accounts
            .as_inner_unchecked_mut();

        let mut mint_event = MtMintEvent {
            owner_id: owner_id.into(),
            token_ids: Vec::new().into(),
            amounts: Vec::new().into(),
            memo: memo.map(Into::into),
        };

        for (token_id, amount) in tokens {
            if amount == 0 {
                return Err(DefuseError::InvalidIntent);
            }

            mint_event.token_ids.to_mut().push(token_id.to_string());
            mint_event.amounts.to_mut().push(amount);

            let total_supply = self
                .storage
                .state
                .total_supplies
                .add(token_id.clone(), amount)
                .ok_or(DefuseError::BalanceOverflow)?;
            match token_id {
                TokenId::Nep171(ref tid) => {
                    if total_supply > 1 {
                        return Err(DefuseError::NftAlreadyDeposited(tid.clone()));
                    }
                }
                TokenId::Nep141(_) | TokenId::Nep245(_) | TokenId::Imt(_) => {}
            }

            owner
                .token_balances
                .add(token_id, amount)
                .ok_or(DefuseError::BalanceOverflow)?;
        }
