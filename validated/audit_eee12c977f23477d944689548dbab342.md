### Title
FREEZE/UNFREEZE TVM opcodes can mutate state inside STATICCALL because the static-call guard is gated behind the unrelated `allowTvmVote` flag - (File: actuator/src/main/java/org/tron/core/vm/OperationActions.java)

### Summary
The TVM's `FREEZE` and `UNFREEZE` opcode handlers are supposed to reject execution when invoked from a `STATICCALL` context, since these opcodes mutate account/resource state. Instead of unconditionally checking `program.isStaticCall()`, the guard is incorrectly conditioned on an unrelated feature flag, `VMConfig.allowTvmVote()`. On any chain where `ALLOW_TVM_FREEZE` is active but `ALLOW_TVM_VOTE` has not been separately activated by the committee (the two proposals are independent), the static-call check is silently skipped, allowing a contract to freeze/unfreeze balances while nested inside a `STATICCALL`.

### Finding Description
`freezeAction` and `unfreezeAction` are the handlers for the `FREEZE`/`UNFREEZE` TVM opcodes: [1](#0-0) 

Both start with:
```java
if (VMConfig.allowTvmVote() && program.isStaticCall()) {
  throw new Program.StaticCallModificationException();
}
```
i.e., the exception that is supposed to enforce the STATICCALL invariant ("no state modification") is only thrown when `allowTvmVote()` is also true. Every other state-mutating opcode handler in the same file checks `program.isStaticCall()` unconditionally — e.g. `sStoreAction`, `logAction`, `freezeBalanceV2Action`, `unfreezeBalanceV2Action`, `delegateResourceAction`, `unDelegateResourceAction`, `voteWitnessAction`, `withdrawRewardAction`, `createAction`, `suicideAction`: [2](#0-1) 

The `FREEZE`/`UNFREEZE` opcodes are activated purely by the `allowTvmFreeze` proposal, independent of `allowTvmVote`: [3](#0-2) 

`ALLOW_TVM_FREEZE` requires `ALLOW_DELEGATE_RESOURCE`, `ALLOW_MULTI_SIGN`, `ALLOW_TVM_CONSTANTINOPLE`, and `ALLOW_TVM_SOLIDITY_059` to be approved first, but has no dependency on `ALLOW_TVM_VOTE`: [4](#0-3) 

This is confirmed by a unit test that enables `allowTvmFreeze` while leaving vote-related config at its default (unset/false): [5](#0-4) 

Since `FREEZE`/`UNFREEZE` internally call `program.freeze(...)`/`program.unfreeze(...)`, which invoke `FreezeBalanceProcessor`/`UnfreezeBalanceProcessor` to commit real changes to the `Repository` (frozen balance, delegated resource records), invoking these opcodes from a `STATICCALL` context — when `allowTvmVote` is false but `allowTvmFreeze` is true — bypasses the fundamental EVM/TVM guarantee that `STATICCALL` cannot alter state: [6](#0-5) 

### Impact Explanation
`STATICCALL` is a core TVM safety primitive relied upon by contracts, wallets, and off-chain tooling (e.g., `eth_call`/`triggerconstantcontract` equivalents, view-function safety, and reentrancy-guard patterns that rely on staticcall purity) to guarantee no state change occurs. A contract that nested-calls into an untrusted contract via `STATICCALL` — expecting no side effects — could have its balance frozen/unfrozen and its bandwidth/energy delegation state modified without its consent, on any network where `ALLOW_TVM_FREEZE` is enabled without `ALLOW_TVM_VOTE`. This breaks accounting/permission assumptions for any protocol relying on `STATICCALL` purity, and can be used to unexpectedly move a victim account's resources into a frozen state or unfreeze delegated resources as a side channel, undermining "unbacked balance"/resource accounting guarantees the pause/staticcall invariant is meant to protect.

### Likelihood Explanation
Exploitation only requires deploying a contract that performs `STATICCALL` (directly via low-level assembly, since Solidity's implicit `view`/`pure` calls compile to `STATICCALL`) to a target that executes `FREEZE`/`UNFREEZE` bytecode, then broadcasting a `TriggerSmartContract` transaction — fully reachable by any unprivileged transaction broadcaster/contract deployer. The only network-state precondition is `ALLOW_TVM_FREEZE == 1 && ALLOW_TVM_VOTE == 0`, a configuration that is plausible since the two proposals are governed independently by the committee and nothing in `ProposalUtil` enforces `ALLOW_TVM_VOTE` as a prerequisite for `ALLOW_TVM_FREEZE`.

### Recommendation
Change the guard in both `freezeAction` and `unfreezeAction` to unconditionally check `program.isStaticCall()` (matching every other state-mutating opcode handler in `OperationActions.java`), i.e.:
```java
if (program.isStaticCall()) {
  throw new Program.StaticCallModificationException();
}
```
Additionally, add a regression test that activates `allowTvmFreeze` while `allowTvmVote` is disabled and asserts that invoking `FREEZE`/`UNFREEZE` from within a `STATICCALL` reverts with `StaticCallModificationException`.

### Proof of Concept
1. On a network/testnet where the committee has approved `ALLOW_TVM_FREEZE` but not `ALLOW_TVM_VOTE` (independent proposals per `ProposalUtil`), deploy a contract (`Attacker`) with a `view`-declared function that internally issues `address(target).staticcall(...)` (or raw `STATICCALL` opcode) calling into a contract that executes Solidity's `target.freeze(amount, resourceType)` (compiles to the `FREEZE` opcode, opcode `0xd5`) — as demonstrated by the existing `FreezeContract.freeze` helper used in `FreezeTest.java`: [7](#0-6) 
2. Broadcast a `TriggerSmartContract` transaction (a normal, unprivileged transaction) invoking `Attacker`'s static-call wrapper.
3. Because `VMConfig.allowTvmVote()` is false, the check in `freezeAction`/`unfreezeAction` (`OperationActions.java:791-822`) never throws `StaticCallModificationException`, and `program.freeze(...)` proceeds to commit a real balance-freeze via `FreezeBalanceProcessor`, despite the outer call chain being a `STATICCALL`.
4. Observe the victim/target account's frozen balance and delegated resource records change even though the invoking context was static — verifying the STATICCALL state-mutation-prevention guarantee is broken.

Note: I could not execute this PoC in a live node (no filesystem/terminal access in this mode); the analysis is based on static code review of the cited files, which shows the guard condition, the opcode registration flags, and the proposal dependency graph.

  public static void freezeAction(Program program) {
    // after allow vote, check static
    if (VMConfig.allowTvmVote() && program.isStaticCall()) {
      throw new Program.StaticCallModificationException();
    }
    // 0 as bandwidth, 1 as energy
    DataWord resourceType = program.stackPop();
    DataWord frozenBalance = program.stackPop();
    DataWord receiverAddress = program.stackPop();

    if (VMConfig.allowTvmFreezeV2()) {
      // after v2 activated, we just push zero to stack and do nothing
      program.stackPush(DataWord.ZERO());
    } else {
      boolean result = program.freeze(receiverAddress, frozenBalance, resourceType );
      program.stackPush(result ? DataWord.ONE() : DataWord.ZERO());
    }
    program.step();
  }

  public static void unfreezeAction(Program program) {
    if (VMConfig.allowTvmVote() && program.isStaticCall()) {
      throw new Program.StaticCallModificationException();
    }

    DataWord resourceType = program.stackPop();
    DataWord receiverAddress = program.stackPop();

    boolean result = program.unfreeze(receiverAddress, resourceType);
    program.stackPush(result ? DataWord.ONE() : DataWord.ZERO());
    program.step();
  }

  public boolean freeze(DataWord receiverAddress, DataWord frozenBalance, DataWord resourceType) {
    Repository repository = getContractState().newRepositoryChild();
    byte[] owner = getContextAddress();
    byte[] receiver = receiverAddress.toTronAddress();

    increaseNonce();
    InternalTransaction internalTx = addInternalTx(null, owner, receiver,
        frozenBalance.longValue(), null,
        "freezeFor" + convertResourceToString(resourceType), nonce, null);

    FreezeBalanceParam param = new FreezeBalanceParam();
    param.setOwnerAddress(owner);
    param.setReceiverAddress(receiver);
    boolean needCheckFrozenTime = CommonParameter.getInstance()
        .getCheckFrozenTime() == 1; // for test
    param.setFrozenDuration(needCheckFrozenTime
        ? repository.getDynamicPropertiesStore().getMinFrozenTime() : 0);
    param.setResourceType(parseResourceCode(resourceType));
    try {
      FreezeBalanceProcessor processor = new FreezeBalanceProcessor();
      param.setFrozenBalance(frozenBalance.sValue().longValueExact());
      processor.validate(param, repository);
      processor.execute(param, repository);
      repository.commit();
      return true;
    } catch (ContractValidateException e) {
      logger.warn("TVM Freeze: validate failure. Reason: {}", e.getMessage());
    } catch (ArithmeticException e) {
      logger.warn("TVM Freeze: frozenBalance out of long range.");
    }
    if (internalTx != null) {
      internalTx.reject();
    }
    return false;
  }
