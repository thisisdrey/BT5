### Title
Delegates Can Front-Run `TrustedSpender.setAllowance()` Allowance Reductions To Drain USDC Beyond The Safe's Intended Cap - (File: `contracts/TrustedSpender.sol`)

### Summary
`TrustedSpender.setAllowance()` fully overwrites the stored `(amount, validUntil)` for a `(token, from, to)` route in a single write, exactly like the classic vulnerable ERC20 `approve()` pattern. Because the old allowance remains spendable until the new value lands on-chain, a delegate can observe a pending allowance-reduction (or revocation) transaction in the mempool, front-run it with `executeTransfer()` to drain the full old allowance, and then spend again once the new (lower, but non-zero) allowance is set — extracting more USDC from the Safe than the Safe/guardian ever intended to expose. This mirrors the root cause of the C4 `updateRewardsMetadata()` finding: a privileged batch/state update that recomputes a claimable/spendable quantity can be front-run by the party whose claim/spend right is being changed, letting them capture both the old and new value.

### Finding Description
`setAllowance` stores a single `Allowance{amount, validUntil}` struct per `(token, from, to)` and "Fully overwrites any existing allowance" on every call: [1](#0-0) 

`executeTransfer` is callable at any time by any registered delegate of `from`, consuming from whatever allowance is currently stored: [2](#0-1) 

There is no mechanism requiring the allowance to be drawn down to zero (or the delegate's spend to be capped) before a new value is written, and no `previousAmount` check analogous to OpenZeppelin's mitigation for the ERC20 approve race (`safeIncreaseAllowance`/`decreaseAllowance`, or "approve to zero first"). The spec confirms this overwrite semantics is intentional design, not an oversight: [3](#0-2) 

`SECURITY.md` documents adjacent, but different, trust assumptions about `TrustedSpender` (unlimited per-recipient defaults, unlimited ERC-20 approvals to the module, and asymmetric `addDelegate`/`removeDelegate` privilege), but none of these entries cover the transaction-ordering race on `setAllowance` itself: [4](#0-3) 

This is precisely the "smart-account path" invariant the audit brief calls out — route allowances must never let an unprivileged/semi-trusted actor spend beyond what the Safe currently authorizes.

### Impact Explanation
A delegate is a semi-trusted actor: the Safe (or guardian) grants it the right to move funds only up to the currently configured allowance, and the Safe's ability to reduce or revoke that allowance is the primary control against a delegate going rogue or being compromised. By exploiting transaction ordering, a delegate can:
1. Spend the full old allowance immediately before a reduction/revocation transaction is mined, and
2. Spend again once the new allowance is set,

extracting `oldAmount + newAmount` in USDC from the Safe — strictly more than the Safe/guardian intended to expose at any point in time. In the worst case (the Safe attempting to revoke a compromised delegate entirely, i.e., setting `amount = 0`), the delegate still captures the entire old allowance that the revocation was meant to prevent from being spent. This is a direct, unauthorized diversion of USDC from a shared protocol Safe account by a party whose trust was being actively curtailed, matching the "unauthorized reassignment of USDC ... from ... shared protocol state" and "unauthorized state transition ... that lets an unprivileged actor act for another ... Safe" impact categories.

### Likelihood Explanation
Exploitation requires only a delegate address monitoring the public mempool and reacting to a `setAllowance` transaction that reduces (or revokes) its own allowance — a realistic scenario whenever an operator reduces/rotates a delegate's spending limit for routine risk management, or urgently revokes a suspected-compromised delegate key. No special privileges beyond being an already-registered delegate are needed, and the attack is a standard front-run (no flash loans, no oracle manipulation, single transaction pair). Given that `SECURITY.md` already documents that TrustedSpender routes carry unlimited or large allowances by default (items 12–13), the realistic amount at risk per race is significant.

### Recommendation
Apply the standard ERC20-approve-race mitigation to `setAllowance`/`setNFTAllowance`:
- Require the caller to first reduce the allowance to `0` before setting a new non-zero value (mirrors "approve to zero first"), or
- Add `increaseAllowance`/`decreaseAllowance`-style deltas instead of absolute overwrites, or
- Track a `nonce`/`expectedCurrentAmount` parameter in `setAllowance` so the update reverts if the on-chain allowance has changed since the caller last read it (optimistic-concurrency guard), preventing the delegate from spending against a stale value right before the update lands.

### Proof of Concept
1. Guardian calls `spender.addDelegate(safe, delegate)` and `spender.setAllowance(USDC, safe, recipient, 1_000e6, NO_EXPIRY)`.
2. Guardian, suspecting the delegate key is compromised, submits `spender.setAllowance(USDC, safe, recipient, 0, NO_EXPIRY)` to revoke it.
3. Delegate observes the pending revocation in the mempool and front-runs it with `spender.executeTransfer(USDC, safe, recipient, 1_000e6)`, which succeeds against the still-live `1_000e6` allowance (see `executeTransfer` check at [5](#0-4) ).
4. The guardian's `setAllowance(..., 0, ...)` then lands, but the delegate has already extracted the full `1_000e6` the guardian intended to freeze — demonstrating that the revocation-race lets the delegate capture value the update was designed to prevent. (If the guardian instead reduces to a non-zero value `X`, the delegate can additionally spend `X` after the update, for a total of `1_000e6 + X`.)

```text
  function setAllowance(
    address token,
```

```text
  /// @inheritdoc ITrustedSpender
  function executeTransfer(address token, address from, address to, uint256 amount) external whenNotPaused {
    // Verify sender is a delegate
    require(delegates[from][msg.sender], NotADelegate());

    // Check allowance exists, is sufficient, and has not expired
    Allowance storage allowance = _allowances[token][from][to];
    require(allowance.amount >= amount, InsufficientAllowance());
    require(block.timestamp <= allowance.validUntil, AllowanceExpired());

    // Update allowance if not infinite
    if (allowance.amount != type(uint208).max) {
      allowance.amount -= uint208(amount);
    }

    IERC20(token).safeTransferFrom(from, to, amount);
  }
```
