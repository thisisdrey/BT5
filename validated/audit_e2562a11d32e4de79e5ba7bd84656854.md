## Title
Stale postponed/promise-yield self-receipts survive `DeleteAccount` and execute privileged self-actions against a re-created account with a different owner — (`core/store/src/utils/mod.rs`, `runtime/runtime/src/actions.rs`, `runtime/runtime/src/lib.rs`)

### Summary
`remove_account` only deletes 4 of the 12 account-scoped trie columns (`Account`, `ContractCode`, `AccessKey`/gas-key nonces, `ContractData`); it never purges `PostponedReceiptId`, `PendingDataCount`, `PostponedReceipt`, `PromiseYieldReceipt`, `PromiseYieldStatus`, `ReceivedData`, `YieldIdToDataId`, or `DataIdToYieldId` rows scoped to the deleted account [1](#0-0) . `action_create_account` performs no scan or cleanup of these leftover rows when the account id is reused [2](#0-1) . Because `apply_action_receipt` derives the actor for a stored receipt purely from the receipt's baked-in `predecessor_id()` — not from any live re-validation of who currently controls the account — a self-targeted postponed/promise-yield receipt created before deletion will still pass `check_actor_permissions` and execute privileged self-actions once its account id is recreated by an unrelated party.

### Finding Description
`check_actor_permissions` gates privileged self-actions (`DeployContract`, `Stake`, `AddKey`, `DeleteKey`, `DeployGlobalContract`, `UseGlobalContract`, `WithdrawFromGasKey`, `DeleteAccount`) purely on `actor_id == account_id` [3](#0-2) . `actor_id` is initialized in `apply_action_receipt` directly from the persisted receipt's `predecessor_id()` [4](#0-3) , with no re-check that the entity currently occupying `account_id` authorized this action.

Exploit flow:
1. Account X (a self-receipt-capable account, e.g. a sub-account or implicit account) is controlled by owner A. A causes X to send itself an `ActionReceipt` with `predecessor_id == receiver_id == X` whose actions include a privileged self-action (e.g. `AddKey` with full access, or `DeployContract`) and which has an unmet `input_data_id`. This gets persisted as a `TrieKey::PostponedReceipt`/`PendingDataCount`/`PostponedReceiptId` (or, via `promise_yield_create`, a `TrieKey::PromiseYieldReceipt`) keyed on `X` [5](#0-4) .
2. A (holding X's key) signs `DeleteAccount(X)` with beneficiary A. `action_delete_account` calls `remove_account`, which removes `Account`/`ContractCode`/`AccessKey`/`ContractData` but leaves the postponed/promise-yield receipt rows untouched [6](#0-5) .
3. Later, an unrelated party Y (e.g. via a permissionless factory contract, or via NEAR/ETH-implicit-account creation-by-transfer) causes `CreateAccount(X)` (or an implicit transfer) to succeed for the same account id `X`. `action_create_account` simply installs a fresh, empty `Account` — it does not check for or clear any leftover `PostponedReceipt`/`PromiseYieldReceipt` entries for `X` [7](#0-6) .
4. When the originally-missing input data (or the yield's `PromiseResume`) finally arrives, `process_receipt` looks up the stored `PostponedReceipt`/`PromiseYieldReceipt` for `X` and calls `apply_action_receipt` on it [8](#0-7) . `actor_id` is set to the old receipt's `predecessor_id()` (still `X`), which trivially equals `account_id` (`X`), so `check_actor_permissions` passes and the privileged self-action executes on Y's brand-new account, with no signature or authorization from Y (or from A after A relinquished/deleted the account).

### Impact Explanation
This is an authorization-escalation-across-accounts bug: a stranger's freshly created account can be involuntarily mutated by a privileged self-action (full-access key injection, contract deployment, stake proposal, key deletion, or even a follow-up `DeleteAccount`) that was authorized only by a previous, unrelated occupant of the same account id. Depending on the injected action, this enables theft/hijack of the newly created account (e.g. `AddKey` full access lets the original party seize control) or forced funds loss (a stale `DeleteAccount` self-action drains the new account to a beneficiary chosen by the old owner). This matches the "authorization escalation across accounts/promises" bounty category.

### Likelihood Explanation
The prerequisite is that an account id gets deleted and later reused by a different transaction signer while a self-targeted postponed/yield receipt for that id is still pending — achievable by any ordinary account owner with only client-side transaction signing (self-receipt with a pending `input_data_id` created via a normal cross-contract callback, followed by a self-signed `DeleteAccount`). Reuse of the account id by an unrelated party is natural in permissionless flows such as NEAR/ETH-implicit account creation-by-transfer, or sub-account name reuse via public factory contracts. No validator, node, or protocol-privileged capability is required.

### Recommendation
On `remove_account`, also purge all remaining account-scoped columns for that account id (`PostponedReceiptId`, `PendingDataCount`, `PostponedReceipt`, `PromiseYieldReceipt`, `PromiseYieldStatus`, `ReceivedData`, `YieldIdToDataId`, `DataIdToYieldId`), or alternatively re-validate at receipt-execution time that the account existed continuously (e.g. compare an account-generation/nonce recorded when the receipt/account was created) before honoring `actor_id == account_id` for self-privileged actions.

### Proof of Concept
Runtime/test-loop integration test plan:
1. Create account `x.near` (or an implicit account) funded and controlled by signer A.
2. Have `x.near` issue a self `FunctionCall` promise chain such that the final batch action (`AddKey` full-access with attacker-chosen public key, or `DeployContract`) is sent as a self receipt with an unresolved `input_data_id` (e.g., a `promise_then` awaiting a cross-shard/contract callback), causing it to be persisted via `set_postponed_receipt`/`PendingDataCount`.
3. Before the dependent data arrives, submit `DeleteAccount(x.near)` signed by A with beneficiary A; assert the account is deleted while the `TrieKey::PostponedReceipt`/`PendingDataCount`/`PostponedReceiptId` rows for `x.near` still exist in the trie.
4. Submit `CreateAccount(x.near)` + `Transfer` funded and signed by unrelated signer Y (or trigger implicit-account creation by transfer to the same id).
5. Deliver the missing `Data` receipt so `pending_data_count` reaches 0.
6. Assert the stale `AddKey`/`DeployContract` action executes successfully against the newly created `x.near` account (e.g. `get_access_key` now returns the old attacker's public key, or the new account's contract hash matches the old deployment) without any transaction signed by Y authorizing it.

/// Removes account, code and all access keys and gas keys associated to it.
pub fn remove_account(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
) -> Result<RemoveAccountResult, StorageError> {
    state_update.remove(TrieKey::Account { account_id: account_id.clone() });
    state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });

    let mut gas_key_nonce_count: usize = 0;
    let mut gas_key_nonce_total_key_bytes: usize = 0;

    // Removing access keys and gas key nonces
    let lock = state_update.trie().lock_for_iter();
    let mut keys_to_remove: Vec<TrieKey> = Vec::new();
    for raw_key in state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_access_keys(account_id), &lock)?
    {
        let raw_key = raw_key?;
        let key_handle = trie_key_parsers::parse_key_handle_from_access_key_key(
            &raw_key, account_id,
        )
        .map_err(|_e| {
            StorageError::StorageInconsistentState(
                "Can't parse key handle from raw key for AccessKey".to_string(),
            )
        })?;
        let nonce_index =
            trie_key_parsers::parse_nonce_index_from_gas_key_key(&raw_key, account_id, &key_handle)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse nonce index from raw key for AccessKey".to_string(),
                    )
                })?;
        if let Some(index) = nonce_index {
            gas_key_nonce_count += 1;
            gas_key_nonce_total_key_bytes += raw_key.len();
            keys_to_remove.push(TrieKey::gas_key_nonce(
                account_id.clone(),
                key_handle.clone(),
                index,
            ));
        } else {
            keys_to_remove.push(TrieKey::access_key(account_id.clone(), key_handle.clone()));
        }
    }
    drop(lock);

    for trie_key in keys_to_remove {
        state_update.remove(trie_key);
    }

    // Removing contract data
    let lock = state_update.trie().lock_for_iter();
    let data_keys = state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_contract_data(account_id, &[]), &lock)?
        .map(|raw_key| {
            trie_key_parsers::parse_data_key_from_contract_data_key(&raw_key?, account_id)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse data key from raw key for ContractData".to_string(),
                    )
                })
                .map(Vec::from)
        })
        .collect::<Result<Vec<_>, _>>()?;
    drop(lock);

    for key in data_keys {
        state_update.remove(TrieKey::ContractData { account_id: account_id.clone(), key });
    }
    Ok(RemoveAccountResult { gas_key_nonce_count, gas_key_nonce_total_key_bytes })
}

pub(crate) fn check_actor_permissions(
    action: &Action,
    account: &Option<Account>,
    actor_id: &AccountId,
    account_id: &AccountId,
) -> Result<(), ActionError> {
    match action {
        Action::DeployContract(_)
        | Action::Stake(_)
        | Action::AddKey(_)
        | Action::DeleteKey(_)
        | Action::DeployGlobalContract(_)
        | Action::UseGlobalContract(_)
        | Action::WithdrawFromGasKey(_) => {
            if actor_id != account_id {
                return Err(ActionErrorKind::ActorNoPermission {
                    account_id: account_id.clone(),
                    actor_id: actor_id.clone(),
                }
                .into());
            }
        }
        Action::DeleteAccount(_) => {
            if actor_id != account_id {
                return Err(ActionErrorKind::ActorNoPermission {
                    account_id: account_id.clone(),
                    actor_id: actor_id.clone(),
                }
                .into());
            }
            let account = account.as_ref().unwrap();
            if !account.locked().is_zero() {
                return Err(ActionErrorKind::DeleteAccountStaking {
                    account_id: account_id.clone(),
                }
                .into());
            }
        }
        Action::CreateAccount(_)
        | Action::FunctionCall(_)
        | Action::Transfer(_)
        | Action::TransferToGasKey(_) => (),
        Action::Delegate(_) | Action::DelegateV2(_) => (),
        Action::DeterministicStateInit(_) => (),
    };
    Ok(())
}
