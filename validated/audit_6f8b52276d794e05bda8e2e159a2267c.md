### Title
Unbounded array allocation from attacker-controlled length field in `extractBytesArray`/`extractBytes32Array` causes node OOM/crash - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The `ValidateMultiSign` (address `0x...0a`) and `BatchValidateSign` (address `0x...09`) TVM precompiled contracts decode dynamic `bytes[]`/`address[]` ABI arguments using `extractBytesArray` and `extractBytes32Array`. Both helpers read an array-length word directly from attacker-controlled call data and use it, unvalidated, to allocate a Java array (`new byte[len][]`), without first checking that `len` is bounded or consistent with the actual call-data size. This mirrors the Bento4 `AP4_Stz2Atom` bug class: a length/count field taken straight from untrusted input drives a buffer/array allocation without a sanity bound, before any consistency check against the real payload size.

### Finding Description
`extractBytesArray` and `extractBytes32Array` take `len` from `words[offset].intValueSafe()` and immediately allocate `new byte[len][]`: [1](#0-0) 

Only the newer `extractSigArray` code path, used exclusively when `VMConfig.allowTvmSelfdestructRestriction()` is enabled, is preceded by a `MAX_SIZE` bound check on the same length word: [2](#0-1) [3](#0-2) 

When `allowTvmSelfdestructRestriction()` is not enabled (legacy path, still selectable via a simple ternary at every call site), `extractBytesArray`/`extractBytes32Array` are invoked directly with no cap on `len`. The only other guard, `isValidAbiEncoding`, is gated behind `VMConfig.allowTvmOsaka()` and merely checks that the *overall* call-data length is congruent with `(headerWords + k*itemWords)*32`; it does not constrain the value of the length word read from an attacker-chosen offset inside the payload, since that offset (`words[1]`/`words[2]`/`words[3]`) and its target word are fully attacker-controlled and independent of the outer shape check: [4](#0-3) [5](#0-4) 

Consequently, a crafted call to `ValidateMultiSign` or `BatchValidateSign` can set the embedded array-length word to a very large value (e.g. `Integer.MAX_VALUE`), causing `new byte[len][]` to request an outsized array of object references, throwing `OutOfMemoryError`. `ValidateMultiSign.execute` calls `extractBytesArray` before entering any try/catch block, so the resulting `OutOfMemoryError` propagates out of the precompile call uncaught at that layer: [6](#0-5) 

### Impact Explanation
An `OutOfMemoryError` triggered inside TVM execution can exhaust heap for the whole node process (not just the current thread), because the JVM must attempt to satisfy the huge allocation request before failing. Depending on GC behavior and concurrent load, this can degrade or crash the full node, halting block processing/serving of RPC and API requests — matching the “node crash or halt” impact category. It only requires an unprivileged actor to deploy or call a contract that issues a single `CALL` (or `STATICCALL`) to precompile address `0x9` (BatchValidateSign) or `0xa` (ValidateMultiSign) with crafted calldata.

### Likelihood Explanation
Reachability requires only that `allowTvmSelfdestructRestriction()` is not active on the target chain (its default/rollout state must be confirmed against the live network configuration) — the length-word extraction code itself is otherwise unconditionally reachable via `execute()` from any transaction/internal call that reaches these two precompiles. No special privilege, stake, or witness role is needed; a plain contract call from any account can trigger it.

### Recommendation
Bound the length word read in `extractBytesArray` and `extractBytes32Array` (and any other unrestricted callers) the same way `extractSigArray`'s callers already do — validate `len` against a fixed `MAX_SIZE` and against the actual remaining `words.length`/`data.length` before allocating, independent of the `allowTvmSelfdestructRestriction` feature flag, and ensure the check happens unconditionally rather than being feature-gated.

### Proof of Concept
Craft calldata for `validatemultisign(address,uint256,bytes32,bytes[])` (or `batchvalidatesign(bytes32,bytes[],address[])`) where the dynamic `bytes[]` offset points to a word set to `0x7FFFFFFF` (interpreted via `intValueSafe()` as `Integer.MAX_VALUE`) while keeping the outer `isValidAbiEncoding` shape check satisfied by making the offset target an unrelated position within a correctly-shaped larger blob. Invoke this via a `CALL` from any contract with `allowTvmSelfdestructRestriction` disabled; `extractBytesArray`/`extractBytes32Array` will attempt `new byte[Integer.MAX_VALUE][]`, triggering `OutOfMemoryError` before any bound is enforced.

  private static byte[][] extractBytes32Array(DataWord[] words, int offset) {
    int len = words[offset].intValueSafe();
    byte[][] bytes32Array = new byte[len][];
    for (int i = 0; i < len; i++) {
      bytes32Array[i] = words[offset + i + 1].getData();
    }
    return bytes32Array;
  }

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }

    if (data == null || data.length % WORD_SIZE != 0) {
      return false;
    }
    long tail = subtractExact(data.length, multiplyExact(headerWords, WORD_SIZE));
    return tail > 0 && tail % multiplyExact(itemWords, WORD_SIZE) == 0;
