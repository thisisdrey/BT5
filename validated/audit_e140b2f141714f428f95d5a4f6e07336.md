Based on my analysis, I found a concrete analog: an unguarded rounding-to-zero case in the market order matching logic that lets a taker acquire a maker's full remaining sell-token balance while paying zero of the maker's requested buy-token.### Title
Missing zero-check in "taker == maker" branch of `matchSingleOrder` lets a taker acquire a maker's full remaining sell-token order for zero payment - (File: actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java)

### Summary
`MarketSellAssetActuator.matchSingleOrder` computes how much of the maker's requested buy token the maker should receive using integer division via `MarketUtils.multiplyAndDivide`, which floors the result. In the `taker > maker` branch this result is explicitly checked for `== 0` and handled safely by returning the residue to the maker without executing a trade. The `taker == maker` branch performs the exact same floor-division computation (`makerBuyTokenQuantityReceive`) but has **no such zero-check**, unconditionally executing the trade regardless of the computed value.

### Finding Description
In `matchSingleOrder` [1](#0-0) , when `takerBuyTokenQuantityRemain == makerOrderCapsule.getSellTokenQuantityRemain()`, the code computes:

```
makerBuyTokenQuantityReceive = MarketUtils.multiplyAndDivide(makerSellRemainQuantity, makerBuyQuantity, makerSellQuantity, ...);
takerBuyTokenQuantityReceive = makerOrderCapsule.getSellTokenQuantityRemain();
long takerSellTokenLeft = takerOrderCapsule.getSellTokenQuantityRemain() - makerBuyTokenQuantityReceive;
```

`MarketUtils.multiplyAndDivide` performs `floorDiv(a*b, c)` [2](#0-1) . When `makerBuyQuantity < makerSellQuantity` (i.e., the maker's exchange rate implies less than 1 unit of buy token per unit of sell token) and `makerSellRemainQuantity` is small enough, `makerBuyTokenQuantityReceive` can floor to `0`.

Unlike the parallel `taker > maker` branch, which explicitly guards this exact same computation with `if (makerBuyTokenQuantityReceive == 0) { ... return; }` and an inline comment acknowledging the rounding risk [3](#0-2) , the `taker == maker` branch has no equivalent check. Consequently:
- `takerSellTokenLeft` is reduced by `0`, so the taker's remaining sell-token balance is unaffected (the taker pays nothing for this fill).
- `makerOrderCapsule.setSellTokenQuantityRemain(0)` fully consumes the maker's order.
- `addTrxOrToken(takerOrderCapsule, takerBuyTokenQuantityReceive, takerAccountCapsule)` credits the taker with the maker's entire remaining sell-token balance [4](#0-3) .
- `addTrxOrToken(makerOrderCapsule, makerBuyTokenQuantityReceive)` credits the maker with `0`.

This exactly mirrors the audited bug class (rounding-down in a price/quantity conversion producing a free transfer) but here it manifests as complete, unguarded theft of a maker's remaining order balance rather than a 1-wei leak.

### Impact Explanation
This is a direct theft-of-funds vulnerability reachable by any unprivileged account submitting a `MarketSellAssetContract` transaction (`MarketSellAssetActuator`). By carefully sizing a taker order's sell-token quantity so that `takerBuyTokenQuantityRemain` exactly equals a target maker order's remaining sell quantity, and by choosing/waiting for a maker order whose price ratio (`makerBuyQuantity/makerSellQuantity < 1`) and remaining quantity floor the buy-side computation to zero, an attacker can drain a maker's entire remaining order balance while paying nothing in return. This is unbacked balance creation / theft of funds from the market order book, satisfying Medium/High severity criteria.

### Likelihood Explanation
Exploitability requires the attacker to control/observe order parameters and possibly partially fill a maker order down to a small remainder (via repeated smaller taker orders) to engineer the rounding condition, then execute the final matching trade in the `taker == maker` branch. This is achievable purely through normal `MarketSellAssetContract` transactions with no special privileges, making it a realistic and repeatable attack for any market pair where the maker's rate implies fractional buy-token amounts per sell-token unit.

### Recommendation
Add the same zero-check to the `taker == maker` branch as exists in the `taker > maker` branch: if `makerBuyTokenQuantityReceive == 0`, do not execute a fill that gives the taker the full maker remainder for free — either round up (ceiling) the payment so the maker receives at least 1 unit, or reject/return the trade increment analogous to the other rounding-to-zero handling paths in this file (`takerBuyTokenQuantityRemain == 0` and `makerBuyTokenQuantityReceive == 0` in the `taker > maker` branch).

### Proof of Concept
1. Maker A places a sell order via `MarketSellAssetContract`: sell 200 of token A for 100 TRX (`makerSellQuantity = 200`, `makerBuyQuantity = 100`), i.e., rate 0.5 TRX per token A.
2. Through prior partial fills (or by placing the order with an initial small remainder), the maker order's `sellTokenQuantityRemain` is reduced to `1` (this is achievable because partial fills use the `taker < maker` / `taker > maker` branches which don't require the remainder to be a "clean" multiple).
3. Attacker (taker) submits a `MarketSellAssetContract` selling TRX and buying token A, sized so that `takerBuyTokenQuantityRemain` (computed in `matchSingleOrder` at line 402-404) equals exactly `1`, matching the maker's remaining sell quantity — placing execution into the `taker == maker` branch (line 418).
4. `makerBuyTokenQuantityReceive = multiplyAndDivide(1, 100, 200) = floor(100/200) = 0`.
5. `takerSellTokenLeft = takerOrderCapsule.getSellTokenQuantityRemain() - 0` → taker's sell-token balance is unchanged (attacker pays 0 TRX for this fill).
6. `addTrxOrToken(takerOrderCapsule, 1, takerAccountCapsule)` credits the attacker with 1 unit of token A; `addTrxOrToken(makerOrderCapsule, 0)` credits maker A with nothing — maker's order is fully consumed, and 1 unit of token A is transferred to the attacker for free.
7. Repeating this pattern against multiple orders/pairs (or engineering larger remainders under the same floor-to-zero condition where the divisor `makerSellQuantity` is much larger than `makerBuyQuantity`) magnifies the stolen amount beyond dust.

  public static long multiplyAndDivide(long a, long b, long c, boolean disableMath) {
    try {
      long tmp = multiplyExact(a, b, disableMath);
      return floorDiv(tmp, c, disableMath);
    } catch (ArithmeticException ex) {
      // do nothing here, because we will use BigInteger to compute again
    }

    BigInteger aBig = BigInteger.valueOf(a);
    BigInteger bBig = BigInteger.valueOf(b);
    BigInteger cBig = BigInteger.valueOf(c);

    return aBig.multiply(bBig).divide(cBig).longValue();
  }
