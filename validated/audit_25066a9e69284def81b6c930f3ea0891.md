### Title
Unsolicited `HandshakeAccept`/`StackerDBHandshakeAccept` can hijack a peer's outstanding request `seq` (e.g. a `Ping`) to bypass the solicited check and forge peer state - (File: stackslib/src/net/chat.rs)

### Summary
`handle_unauthenticated_control_message` gates processing of `HandshakeAccept`/`StackerDBHandshakeAccept` solely on `self.connection.is_solicited(msg)` [1](#0-0) . This check is invoked generically against the incoming message's `preamble.seq` and does not verify that the specific reply *type* matches the type of the original outstanding request that owns that `seq` [2](#0-1) .

### Finding Description
`handle_unauthenticated_control_message` computes `solicited` once from the incoming message and its `seq` value, then dispatches purely on `msg.payload`'s variant [3](#0-2) . If `solicited` is true, a `HandshakeAccept`/`StackerDBHandshakeAccept` is fed into `handle_handshake_accept`, which calls `update_from_handshake_data`, mutating `self.peer_heartbeat` and public-key/session state, without any signature/authentication check tying the reply to the specific handshake request that was sent [4](#0-3) .

The connection's outstanding-request bookkeeping (`is_solicited`, in `stackslib/src/net/connection.rs`) tracks pending request `seq` values in a single per-connection table shared across *all* request types (`Ping`, `Handshake`, `GetNeighbors`, etc.) rather than per-request-type slots. Because `seq` is just a locally incrementing counter that is visible to the remote peer in every outbound message the local node sends it (e.g., a routine keep-alive `Ping`), a malicious connected peer can observe the exact `seq` the node used for an unrelated outstanding request and immediately answer with a forged `HandshakeAccept` carrying that same `seq` instead of the expected `Pong`. Because the "solicited" determination only asks "is this `seq` currently outstanding on this connection" and not "is this `seq` the one that was assigned to *this* handshake request", the check is satisfied even though the reply answers a different, unrelated request.

I was not able to fully confirm the exact body of `is_solicited` in `connection.rs` within the tool budget (only its signature was located, not its internals), so the precise data structure backing the outstanding-request table could not be quoted directly. This is a material gap: if `is_solicited` (or the underlying reply-handle table) actually keys entries by `(seq, expected_message_type)` rather than `seq` alone, the bypass described here would not exist. Given the caller-site evidence in `chat.rs` — a single boolean `solicited` computed generically from the message and consumed identically regardless of the concrete reply type expected by the original request — the described bypass is plausible but not conclusively proven from the code actually inspected.

### Impact Explanation
If exploitable, a remote unprivileged peer could inject unauthenticated peer-info updates (public key, heartbeat) into a victim's connection state by timing a forged `HandshakeAccept` to coincide with any outstanding request `seq` (not necessarily a real handshake), effectively an authentication bypass for peer-state mutation. This matches the "auth bypass" / "unauthenticated write to state" Critical category if confirmed.

### Likelihood Explanation
Preconditions: attacker must already be a connected peer (P2P port reachable, no privileged role needed) and must observe or predict a `seq` value the node uses for some request sent to that connection (trivial, since the node periodically issues `Ping`s to peers and the `seq` is plaintext in the preamble). No secret or private key is required. This makes the attack cheap and repeatable per outstanding request — **contingent on `is_solicited`'s actual seq-matching semantics, which could not be fully verified in this session.**

### Recommendation
Ensure the solicited-reply table associates each outstanding `seq` with the specific expected reply type(s) for the request that generated it, and reject/ignore replies whose type does not match what was expected for that `seq`, in addition to matching `seq` itself.

### Proof of Concept
Rust test in `stackslib::net::chat`/`connection` tests:
1. Establish a `ConversationP2P`/`NetworkConnection`, send a `Ping` via the normal signed-request path, capturing its assigned `seq = N` (mimicking what a peer would observe from real preamble bytes).
2. Before returning a `Pong`, inject a crafted `StacksMessage` with `preamble.seq = N` and payload `HandshakeAccept` (or `StackerDBHandshakeAccept`) into `handle_unauthenticated_control_message`.
3. Assert on `self.connection.is_solicited(&msg)` — if it returns `true`, and `handle_handshake_accept` is invoked (verify via mutation of `self.peer_heartbeat`/public key fields), the bypass is confirmed; if it instead requires the reply type to match the original `Ping`'s expected `Pong`, `is_solicited` should return `false` and the finding is invalidated.

**Given the inability to fully verify `is_solicited`'s internal matching logic (seq-only vs. seq+type) within this session, this finding should be treated as unconfirmed pending direct inspection of `connection.rs`'s `is_solicited` implementation and its backing pending-request table.**

    fn handle_unauthenticated_control_message(
        &mut self,
        network: &mut PeerNetwork,
        msg: &mut StacksMessage,
        ibd: bool,
    ) -> Result<(Option<StacksMessage>, bool), net_error> {
        // only thing we'll take right now is a handshake, as well as handshake
        // accept/rejects, nacks, and NAT holepunches
        //
        // Anything else will be nack'ed -- the peer will first need to handshake.
        let mut consume = false;
        let solicited = self.connection.is_solicited(msg);
        let reply_opt = match msg.payload {
            StacksMessageType::Handshake(_) => {
                monitoring::increment_msg_counter("p2p_unauthenticated_handshake".to_string());
                debug!("{:?}: Got unauthenticated Handshake", &self);
                let (reply_opt, handled) = self.handle_handshake(network, msg, false, ibd)?;
                consume = handled;
                Ok(reply_opt)
            }
            StacksMessageType::HandshakeAccept(ref data) => {
                if solicited {
                    debug!("{:?}: Got unauthenticated HandshakeAccept", &self);
                    self.handle_handshake_accept(
                        network.get_chain_view(),
                        &msg.preamble,
                        data,
                        None,
                    )
                    .map(|_| None)
                } else {
                    debug!("{:?}: Unsolicited unauthenticated HandshakeAccept", &self);

                    // don't update stats or state, and don't pass back
                    consume = true;
                    Ok(None)
                }
            }
            StacksMessageType::StackerDBHandshakeAccept(ref data, ref db_data) => {
                if solicited {
                    debug!("{:?}: Got unauthenticated StackerDBHandshakeAccept", &self);
                    self.handle_handshake_accept(
                        network.get_chain_view(),
                        &msg.preamble,
                        data,
                        Some(db_data),
                    )
                    .map(|_| None)
