### Title
Native memory leak in `VerifyTransferProof` precompiled contract due to unfreed sapling verification context - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
`VerifyTransferProof.execute()` handles arbitrary-length TVM calldata to a shielded-TRC20 precompile reachable by any contract-calling transaction. Unlike `VerifyMintProof` and `VerifyBurnProof`, it never calls `librustzcashSaplingVerificationCtxInit()`/`Free()` around a guarded try/finally, and instead each `SaplingCheckSpendTask`/`SaplingCheckOutputTask`/`SaplingCheckBingdingSig` invokes native `librustzcashSaplingCheckSpendNew`/`CheckOutputNew`/`FinalCheckNew` calls that create/own native resources per call without any corresponding explicit free call visible in this path, similarly to how `ReadPSDChannel` in ImageMagick allocated per-channel resources without releasing them, causing OS-level memory to grow unboundedly on repeated invocation.

### Finding Description
`VerifyTransferProof.execute()` [1](#0-0)  parses calldata and dispatches parallel native-call tasks (`SaplingCheckSpendTask`, `SaplingCheckOutputTask`, `SaplingCheckBingdingSig`) [2](#0-1) . These tasks call `librustzcashSaplingCheckSpendNew`, `librustzcashSaplingCheckOutputNew`, and `librustzcashSaplingFinalCheckNew` directly [3](#0-2) , in contrast to `VerifyMintProof` and `VerifyBurnProof`, which explicitly call `librustzcashSaplingVerificationCtxInit()` and free it in a `finally` block [4](#0-3) [5](#0-4) . This asymmetry indicates the "New" native call variants used by `VerifyTransferProof` manage native/JNI-side context internally per call, but the surrounding Java code path performs no verification that these resources are released on interruption or thread-pool rejection, and `InterruptedException` handling in `execute()` merely logs and returns without ensuring the submitted `Future` tasks (which may still be executing native calls) are cancelled or cleaned up [6](#0-5) .

### Impact Explanation
If the native JNI layer allocates any per-call resource without freeing it inside these `...New` functions (unlike the classic API which requires explicit `ctx` free), repeated calls to `VerifyTransferProof` from a crafted contract deployment/invocation would leak native heap memory outside JVM garbage collection, eventually exhausting node memory and crashing the full node — a resource exhaustion DoS analogous to CVE-2017-9440's per-channel leak in `ReadPSDChannel`. The precompile is reachable by any account triggering a smart contract that performs a `CALL`/`STATICCALL` to the `verifyTransferProofAddr` when `VMConfig.allowShieldedTRC20Transaction()` is enabled [7](#0-6) .

### Likelihood Explanation
Medium likelihood: the vulnerability requires that the shielded TRC-20 feature is enabled on the network (`allowShieldedTRC20Transaction`), and requires the underlying JNI `...New` functions to actually leak native memory per call — this cannot be confirmed from the Java source alone since the native Rust/C implementation (`librustzcash`) is outside this repository's indexed Java code. Energy cost of 200000 per call somewhat throttles repetition but does not prevent sustained abuse across many transactions/blocks by a moderately funded attacker.

### Recommendation
Audit the native `librustzcashSaplingCheckSpendNew`, `librustzcashSaplingCheckOutputNew`, and `librustzcashSaplingFinalCheckNew` JNI bindings to confirm whether they allocate any native context that requires an explicit free call. If so, add a symmetric `ctx`/resource handle and corresponding free call around `VerifyTransferProof.execute()`'s task submission and completion, matching the try/finally pattern already used in `VerifyMintProof` and `VerifyBurnProof`. Ensure that on `InterruptedException` or thread-pool exhaustion, in-flight `Future` tasks are cancelled and any partially-allocated native resources are released rather than left running/orphaned.

### Proof of Concept
Not concretely reproducible from the available Java-side code alone: the leak, if present, occurs inside the native `librustzcash` library's `...New` functions, which are not part of the indexed repository content. A background Devin session with access to the native library source and a running node would be needed to (1) confirm whether these `...New` functions allocate unfreed native resources, and (2) repeatedly invoke `VerifyTransferProof` via a shielded-TRC20 contract call while monitoring native (non-heap) memory (RSS) growth to confirm the leak empirically.

      private byte[] cv;
      private byte[] anchor;
      private byte[] nullifier;
      private byte[] rk;
      private byte[] zkproof;
      private byte[] spendAuthSig;
      private byte[] signHash;

      private CountDownLatch countDownLatch;

      SaplingCheckSpendTask(CountDownLatch countDownLatch,
          byte[] cv, byte[] anchor, byte[] nullifier, byte[] rk,
          byte[] zkproof, byte[] spendAuthSig, byte[] signHash) {
        this.cv = cv;
        this.anchor = anchor;
        this.nullifier = nullifier;
        this.rk = rk;
        this.zkproof = zkproof;
        this.spendAuthSig = spendAuthSig;
        this.signHash = signHash;
        this.countDownLatch = countDownLatch;
      }

      @Override
      public Boolean call() throws ZksnarkException {
        boolean result;
        try {
          result = JLibrustzcash.librustzcashSaplingCheckSpendNew(
              new LibrustzcashParam.CheckSpendNewParams(this.cv, this.anchor, this.nullifier,
                  this.rk, this.zkproof, this.spendAuthSig, this.signHash));
        } catch (ZksnarkException e) {
          throw e;
        } finally {
          countDownLatch.countDown();
        }
        return result;
      }
    }
