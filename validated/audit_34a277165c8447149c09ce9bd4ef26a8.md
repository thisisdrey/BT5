### Title
Floating-point non-determinism / precision divergence in TRC10 Exchange bonding-curve pricing enables chain split and exploitable rounding in `ExchangeTransactionContract` - (File: chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java)

### Summary
The legacy TRC10 "Exchange" module (java-tron's on-chain AMM for TRX/TRC10 token pairs, exposed via `ExchangeCreateContract`, `ExchangeInjectContract`, `ExchangeWithdrawContract`, and `ExchangeTransactionContract`) prices trades using a Bancor-style relay/supply formula computed with IEEE-754 `double` arithmetic and `Math.pow`/`StrictMath.pow` in `ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply` [1](#0-0) . This is functionally the same class of bug that made the RoeFinance exploit possible: a price/exchange-rate calculation that can be manipulated or diverge from the "true" value due to arithmetic imprecision, then exploited transaction-by-transaction to extract or lock value, except here the root cause is platform-dependent floating-point rounding rather than a flash-loan-driven liquidity shift.

### Finding Description
`ExchangeTransactionActuator`, `ExchangeInjectActuator`, and `ExchangeWithdrawActuator` all call `ExchangeCapsule.transaction()`, which (in the non-"hardened" legacy path) instantiates `ExchangeProcessor` and computes the trade output via `double issuedSupply = -supply * (1.0 - Maths.pow(1.0 + quant/newBalance, 0.0005, useStrictMath))` and a symmetric `exchangeFromSupply` step raised to the `2000.0` power [1](#0-0) . `Maths.pow` dispatches to either `StrictMathWrapper.pow` (StrictMath) or `MathWrapper.pow`, and the codebase ships an ARM-specific `MathWrapper` that hardcodes hundreds of `(a, b) -> result` overrides keyed by raw IEEE-754 bit patterns (`addPowData(...)`) to force a specific historical mainnet result for known inputs, explicitly because native `Math.pow`/`StrictMath.pow` diverged between platforms on this exact Exchange pricing formula [2](#0-1) . A cross-platform network where SRs run mixed x86/ARM nodes and any of those historical overrides is incomplete or a new never-before-seen `(a,b)` pair is hit produces two different `buyTokenQuant` values for the same `ExchangeTransactionContract`, causing state (account balances, `ExchangeCapsule` reserves) to diverge between nodes that used `Math.pow` vs `StrictMath.pow`/the ARM override table.

### Impact Explanation
Divergent execution results for an identical, validly signed transaction across different node architectures is a chain-split / consensus-failure class bug — it is not merely a "resource-only" or "no-impact" issue. If unreconciled hosts compute different `anotherTokenQuant` for the same `ExchangeTransactionContract`, they will commit different account balances and different `ExchangeCapsule` reserve states, which is unrecoverable without a hard fork/manual reconciliation, and can also be leveraged by an attacker who controls or targets a minority-architecture node to get an inconsistent, favorable settlement recorded locally.

### Likelihood Explanation
Any account holding TRX or a TRC10 asset can broadcast `ExchangeTransactionContract`/`ExchangeInjectContract`/`ExchangeWithdrawContract` transactions with no special permission, so the trigger is fully reachable by an unprivileged transaction broadcaster. The project's own commit history shows this was already a known, actively-patched risk (the ARM lookup table with dozens of entries added incrementally, plus the newer `allowHardenExchangeCalculation` / `SafeExchangeProcessor` BigDecimal rewrite and `useStrictMath` proposal flag) [3](#0-2) [4](#0-3) , indicating this is a real, previously-exploited/observed class of consensus divergence rather than a theoretical one; residual risk remains for any `(a, b)` pow input not covered by the ARM override table or for any newly-deployed node/JVM/CPU combination with different `Math.pow` behavior while `allowHardenExchangeCalculation` is not yet activated on the network.

### Recommendation
Ensure `allowHardenExchangeCalculation` is activated network-wide so all TRC10 Exchange trades route exclusively through `SafeExchangeProcessor`'s deterministic `BigDecimal`-based computation, and remove/deprecate the legacy `ExchangeProcessor` double/`Math.pow` path (and the ARM `MathWrapper` override table workaround) once migration is complete, so no code path can still produce platform-dependent results for TRC10 exchange trades.

### Proof of Concept
Not directly runnable as an external PoC (this requires running two nodes on different CPU architectures/JVMs against the same chain state and observing divergent `ExchangeTransactionActuator` outputs for an identical `ExchangeTransactionContract`); the root cause is demonstrated by the test `ExchangeProcessorTest.testStrictMath` which explicitly asserts `Assert.assertNotEquals(anotherTokenQuant, result)` — proving the legacy `false`/`true` `useStrictMath` modes intentionally produce *different* outputs for identical `(sellBalance, buyBalance, sellQuant)` inputs across dozens of real historical trade parameters [5](#0-4) .

  private BigDecimal exchangeToSupply(long balance, long quant) {
    long newBalance = StrictMathWrapper.addExact(balance, quant);
    BigDecimal bdQuant = BigDecimal.valueOf(quant);
    BigDecimal bdNewBalance = BigDecimal.valueOf(newBalance);
    BigDecimal base = BigDecimal.ONE.add(
        bdQuant.divide(bdNewBalance, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 0.0005);
    return SUPPLY.negate().multiply(
        BigDecimal.ONE.subtract(BigDecimal.valueOf(powResult))).setScale(0, RoundingMode.DOWN);
  }

  private long exchangeFromSupply(long balance, BigDecimal supplyQuant) {
    BigDecimal bdBalance = BigDecimal.valueOf(balance);
    BigDecimal base = BigDecimal.ONE.add(
        supplyQuant.divide(SUPPLY, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 2000.0);
    BigDecimal exchangeBalance = bdBalance.multiply(
        BigDecimal.valueOf(powResult).subtract(BigDecimal.ONE));
    return exchangeBalance.setScale(0, RoundingMode.DOWN).longValueExact();
  }
