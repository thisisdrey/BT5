## Title
Spoofed-IP QUIC Initial-packet flood defeats `overall_connection_rate_limiter` and `ConnectionRateLimiter`, exhausting `max_concurrent_connections` slots and denying legitimate connections - (File: streamer/src/nonblocking/quic.rs)

## Summary
An unstaked/unprivileged attacker who spoofs source IPs on QUIC Initial (UDP) packets sent to the public TPU port can consume all `ClientConnectionTracker` slots for up to `QUIC_CONNECTION_HANDSHAKE_TIMEOUT` (2s) per attempt because the per-IP rate limiter is trivially defeated by fresh IPs and the "global" rate limiter only consumes tokens after a full handshake completes, which spoofed connections never do. Continuous re-flooding with new spoofed source addresses can keep `open_connections` pinned at `qos.max_concurrent_connections()`, causing `refused_connections_too_many_open_connections` for real clients.

## Finding Description
In `run_server` (`streamer/src/nonblocking/quic.rs:254-412`), for every `Incoming` connection the following gates are applied in order before a `ClientConnectionTracker` slot is reserved:

1. `overall_connection_rate_limiter.current_tokens() == 0` (line 347) — a non-consuming peek check on the shared `TokenBucket` (`MAX_CONNECTION_BURST=1000`, `TOTAL_CONNECTIONS_PER_SECOND=2500`).
2. `rate_limiter.is_allowed(&incoming.remote_address().ip())` (line 359) — per-IP check in `ConnectionRateLimiter::is_allowed` (`streamer/src/nonblocking/connection_rate_limiter.rs:34-40`), which explicitly returns `true` for any IP never seen before ("if we have not seen IP, allow connection request").
3. `ClientConnectionTracker::new(stats.clone(), qos.max_concurrent_connections())` (line 371-372) — the only hard, atomic cap on concurrent connection state (`streamer/src/nonblocking/quic.rs:236-252`).

Critically, `overall_connection_rate_limiter.consume_tokens(1)` and `rate_limiter.register_connection(&from.ip())` are only invoked **after** the QUIC handshake succeeds, inside `setup_connection` (`streamer/src/nonblocking/quic.rs:483-508`). Because spoofed-source Initial packets can never receive the server's handshake response, `connecting` never resolves successfully and neither limiter's token/record is ever actually consumed — it just times out after `QUIC_CONNECTION_HANDSHAKE_TIMEOUT = Duration::from_secs(2)` (line 80) via the `timeout()` wrapper (`streamer/src/nonblocking/quic.rs:472`).

This means:
- The per-IP limiter is a no-op against spoofing, since each spoofed packet presents a "new" IP that is always allowed at step 2, and never gets registered (consumed) since the handshake never completes.
- The "global" `overall_connection_rate_limiter` peek at step 1 never actually depletes for these failed attempts, so it does not bound the rate of spoofed Initial packets that reach `ClientConnectionTracker::new`.
- The only real bound left is the atomic `open_connections` counter versus `qos.max_concurrent_connections()` in `ClientConnectionTracker::new`. Once an attacker fills this pool with half-open connections (each held for up to 2 seconds due to the handshake timeout, and continuously refreshed by sending new spoofed-source Initial packets faster than the timeout), legitimate clients hitting `ClientConnectionTracker::new` receive `Err(())`, incrementing `stats.refused_connections_too_many_open_connections` and calling `incoming.refuse()` (lines 371-379), denying them service for as long as the flood continues.

The code comment at lines 331-340 acknowledges the general spoofing risk pre-retry-challenge and states the mitigation policy is to "shed fast and bound resource consumption," relying on (a) a handshake-attempt timeout, (b) the global rate-limiter, (c) per-IP rate-limiting, and (d) a per-peer connection cap. However, (b) and (c) are ineffective specifically against a spoofed-source flood because their consumption is gated on handshake completion, leaving only (a)+(d) as the actual bound — and that bound is the shared `max_concurrent_connections` resource itself, so it is exactly what is exhausted by the attack.

## Impact Explanation
This is a resource-exhaustion / QoS-evasion issue on the TPU QUIC ingress path: an unstaked, unprivileged remote attacker can deny new (including staked) connections to a leader's public TPU port by keeping `open_connections` saturated with never-completing spoofed handshakes, without needing to consume any actual per-IP or global connection budget as intended. This falls into the "Critical ingress DoS" scope described (QUIC connection admission), matching Agave's networking/DoS bounty category for unbounded resource consumption via unauthenticated ingress.

## Likelihood Explanation
Preconditions are minimal: the attacker only needs the ability to send raw spoofed-source UDP/QUIC Initial packets to the leader's public TPU port, which is explicitly the permitted "unprivileged attacker" model. No staking, gossip, or validator control is required. The attack is easily repeatable and sustainable as long as the attacker can generate new source IPs (or rely on egress filtering not blocking spoofed traffic) faster than the 2-second handshake timeout, which is a low bar for even modest bandwidth/packet-per-second capability.

## Recommendation
Do not treat `overall_connection_rate_limiter`/`ConnectionRateLimiter` accounting and the accept-time admission slot (`ClientConnectionTracker`) as independent defenses when one is gated on a post-handshake event that an attacker can prevent from ever occurring. Concretely:
- Consume overall/global rate-limiter tokens (and register an initial per-IP hit) at Incoming/accept time (pre-handshake), not only after successful handshake, so spoofed floods actually deplete the bucket and get throttled.
- Reserve a separate, smaller "pending/half-open" quota distinct from `max_concurrent_connections`, so half-open (unauthenticated) connections cannot starve the pool that legitimate fully-authenticated connections rely on.
- Consider enabling QUIC address validation / Retry (stateless retry token) for Initial packets before allocating any per-connection state, which is quinn's standard SYN-cookie-equivalent defense against exactly this spoofing scenario, before falling back to the current post-hoc timeout-based reclamation.

```rust
#[tokio::test(flavor = "multi_thread")]
async fn test_spoofed_initial_flood_exhausts_connection_slots() {
    // Configure a small max_concurrent_connections via SwQosConfig/SimpleQosConfig
    // (e.g. max_connections_per_unstaked_peer small, but crucially a small overall
    // max_concurrent_connections so the PoC completes quickly).
    let SpawnTestServerResult { join_handle, server_address, stats, cancel, .. } =
        setup_quic_server(None, QuicStreamerConfig::default_for_tests(), SwQosConfig::default());

    // Send N (> max_concurrent_connections) raw UDP QUIC Initial-shaped packets,
    // each from a distinct spoofed source SocketAddr (using a raw UDP socket with
    // IP_HDRINCL, or a mock UdpSocket wrapper if raw sockets are unavailable in test
    // sandbox) to server_address, without completing the QUIC handshake.
    // (Using quinn::Endpoint::connect() but never polling to completion, and dropping
    // the future immediately, simulates similarly non-responsive/incomplete handshakes
    // from the server's perspective without needing raw-socket spoofing.)

    // Wait slightly less than QUIC_CONNECTION_HANDSHAKE_TIMEOUT (2s) and repeatedly
    // resend fresh "connections" from new fake source addrs to keep the pool full.

    // Assert: stats.open_connections stays pinned at max_concurrent_connections
    // Assert: stats.refused_connections_too_many_open_connections > 0
    // Assert: a legitimate, real client (make_client_endpoint) attempting to connect
    // during the flood window fails / times out, proving denial of service:
    let legit = make_client_endpoint(&server_address, None).await;
    // expect timeout/refusal while flood is ongoing
    assert!(stats.refused_connections_too_many_open_connections.load(Ordering::Relaxed) > 0);

    cancel.cancel();
    join_handle.await.unwrap();
}
```
Expected result: `open_connections`/`outstanding_incoming_connection_attempts` remain saturated at `max_concurrent_connections` throughout the flood, and legitimate connection attempts are refused via `refused_connections_too_many_open_connections`, while `stats.connection_rate_limited_across_all` and `stats.connection_rate_limited_per_ipaddr` stay near zero — demonstrating that the rate limiters never actually engage against the spoofed flood.     /// Check if the connection from the said `ip` is allowed.
```rust
    /// Here we assume that only IPs with actual confirmed connections are stored in it,
    /// since we should only modify server state once source IP is verified
    pub fn is_allowed(&self, ip: &IpAddr) -> bool {
        // Check if we have records in the rate limiter for the given IP address
        match self.limiter.current_tokens(ip) {
            Some(r) => r > 0, // we have a record, and rate is not exceeded
            None => true,     // if we have not seen IP, allow connection request
```
