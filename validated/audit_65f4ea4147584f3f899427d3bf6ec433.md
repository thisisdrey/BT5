### Title
Unbounded body read in `process_event` allows single-request memory-exhaustion DoS on signer event endpoint - (File: libsigner/src/events.rs)

### Summary
`SignerEventReceiver::next_event` accepts any TCP client on the bound event port and dispatches POST bodies for `/proposal_response`, `/stackerdb_chunks`, `/new_burn_block`, and `/new_block` straight into `process_event`, which calls `request.as_reader().read_to_string(&mut body)` with no cap on the number of bytes read before allocating. Since the tiny_http server is created with a bare `HttpServer::http(listener)` and no content-length/body-size limit is configured anywhere in `libsigner`, a remote unauthenticated client can send a POST with an attacker-controlled `Content-Length` (or chunked body) of arbitrary size and force the process to allocate a `String` sized to that request, unbounded by any `MAX_MESSAGE_LEN`/`MAX_HTTP_HEADER_LEN`-style pre-allocation check.

### Finding Description
The claimed equality — "bytes read for the event body == a validated maximum body length before allocation" — does not hold. `process_event` at [1](#0-0)  reads the whole body via `read_to_string` before any deserialization or size check is performed, and there is no line anywhere in this function or its caller that compares the declared/streamed body length against a maximum prior to allocating `body: String`.

The server itself is bound with no limiting wrapper: `self.http_server = Some(HttpServer::http(listener).expect(...))` at [2](#0-1) , and the dispatch loop in `next_event` simply calls `http_server.recv()` and forwards the raw `HttpRequest` to `process_event` for any of the `/stackerdb_chunks`, `/proposal_response`, `/new_burn_block`, `/new_block` routes without inspecting `Content-Length` or capping the reader: [3](#0-2) .

Notably, `libsigner/src/http.rs` *does* define exactly the kind of caps the question is asking about (`MAX_HTTP_HEADERS`, `MAX_HTTP_HEADER_LEN`, and use of `MAX_MESSAGE_LEN` in `decode_http_body`'s chunked reader) — [4](#0-3)  and [5](#0-4)  — but that module is only used for the *client-side* parsing of node-originated HTTP responses/requests processed manually via `httparse`. It is not wired into the `SignerEventReceiver`'s tiny_http-based server path that `process_event` uses, so those guards do not apply to this endpoint.

Attack message: a single HTTP POST to `/proposal_response` (or any of the other three routes) with a `Content-Length` header declaring many megabytes/gigabytes and a body of that size (or a chunked-encoded body with no framework-level cap on the tiny_http side). `request.as_reader().read_to_string(&mut body)` will attempt to read and buffer all of it into memory, growing the `String` on demand with no early rejection.

### Impact Explanation
The signer's event-receiver thread (and hence the resident process, since `next_event` runs in a loop that a single thread services synchronously) can be driven to allocate memory proportional to attacker-supplied request size, with no configured cap. Repeated requests amplify this into sustained memory pressure or an OOM kill of the signer process, which is a single-process DoS reachable by any unauthenticated party able to reach the bound signer event port — matching the "remote crash/unauthenticated DoS from few messages" Critical category, or at minimum a bounded/unbounded compute-and-memory DoS on this endpoint. It does not forge, corrupt, or persist any chain state; it is a resource-exhaustion issue local to the signer process. This is repeatable per TCP connection.

### Likelihood Explanation
The signer event server listens on a configured TCP port that, per the threat model, any remote unprivileged party who can connect to it may reach (no signature, secret, or StackerDB slot ownership is required to reach `process_event` — the dispatch in `next_event` only branches on URL path and HTTP method, not on any authentication). Attacker cost is a single TCP connection and enough outbound bandwidth to transmit the oversized body once; no privileged role, secret, or protocol handshake is required. This is directly repeatable and does not depend on any specific chain/peer state.

### Recommendation
Add an explicit content-length/body-size cap before reading the request body in `process_event` (e.g., check `request.body_length()`/`Content-Length` header against a `MAX_MESSAGE_LEN`-style constant and reject with 4xx before calling `read_to_string`), and use a bounded reader (`Read::take(max_len)`) instead of `read_to_string` on an unbounded reader, mirroring the caps already defined in `libsigner/src/http.rs`.

### Proof of Concept
Rust integration test in `libsigner`:
1. Bind a `SignerEventReceiver` via `bind()` as in existing tests (`libsigner/src/tests/mod.rs`/`http.rs` patterns).
2. Open a raw `TcpStream` to the bound address and send:
   `POST /proposal_response HTTP/1.1\r\nHost: 127.0.0.1\r\nContent-Length: <huge_N>\r\nContent-Type: application/json\r\n\r\n` followed by `huge_N` bytes (or use `Transfer-Encoding: chunked` with an unbounded chunk stream) without ever closing the connection early.
3. Call `next_event()` on the receiver in a separate thread and observe process RSS growth unbounded/proportional to `huge_N` via `/proc/self/status` sampling, or drive `huge_N` large enough to trigger an allocation failure/OOM abort, asserting that no rejection occurs before the read completes (i.e., `process_event`/`read_to_string` at [6](#0-5)  does not short-circuit on size).

```rust
fn process_event<T, E>(mut request: HttpRequest) -> Result<SignerEvent<T>, EventError>
where
    T: SignerEventTrait,
    E: serde::de::DeserializeOwned + TryInto<SignerEvent<T>, Error = EventError>,
{
    let mut body = String::new();

    if let Err(e) = request.as_reader().read_to_string(&mut body) {
        error!("Failed to read body: {:?}", &e);
        ack_dispatcher(request);
        return Err(EventError::MalformedRequest(format!(
            "Failed to read body: {:?}",
            e
        )));
    }
    // Regardless of whether we successfully deserialize, we should ack the dispatcher so they don't keep resending it
    ack_dispatcher(request);
    let json_event: E = serde_json::from_slice(body.as_bytes())
        .map_err(|e| EventError::Deserialize(format!("Could not decode body to JSON: {:?}", e)))?;
```

```rust
/// Decode an HTTP body, given the headers.
pub fn decode_http_body(headers: &HashMap<String, String>, mut buf: &[u8]) -> io::Result<Vec<u8>> {
    let chunked = if let Some(val) = headers.get("transfer-encoding") {
        val == "chunked"
    } else {
        false
    };

    let body = if chunked {
        // chunked encoding
        let ptr = &mut buf;
        let mut fd = HttpChunkedTransferReader::from_reader(ptr, MAX_MESSAGE_LEN.into());
        let mut decoded_body = vec![];
        fd.read_to_end(&mut decoded_body)?;
        decoded_body
    } else {
        // body is just as-is
        buf.to_vec()
    };

    Ok(body)
}
```
