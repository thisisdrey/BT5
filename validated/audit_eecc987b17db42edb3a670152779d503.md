### Title
Unverified `RelayFromAddr` in `CreateRelayRequest` allows relay-identity spoofing / remote relay-state poisoning - (File: relay_manager.go)

### Summary
`relayManager.handleCreateRelayRequest` accepts a `RelayFromAddr` field directly from an attacker-controlled `NebulaControl` message and uses it, unverified, as the identity that a relay entry is created and keyed for on the receiving node. Nothing ties the claimed `from` address to the actual certified `vpnAddrs` of the authenticated peer `h` who sent the control message, mirroring the Beedle `buyLoan()` flaw where a caller-supplied identifier (`poolId`) was never checked for consistency with the entity it was being used to act on behalf of (the loan's `loanToken`/`collateralToken`).

### Finding Description
`HandleControlMsg` unmarshals a `NebulaControl` message coming from an already-authenticated tunnel peer `h`, and for `CreateRelayRequest`/`CreateRelayResponse` only checks that `RelayFromAddr`/`RelayToAddr` are non-nil before dispatching to `handleCreateRelayRequest`: [1](#0-0) 

Inside `handleCreateRelayRequest`, `from` and `target` are taken straight from the message. The only address-based check performed is that `from` is not one of my own addresses (self-relay guard) and that `target` is/`isn't` me — there is no check that `from` corresponds to `h`'s own certified `vpnAddrs`: [2](#0-1) 

When "I am the target" branch runs, relay state (`AddRelay` / `CompleteRelayByIP`) is created and keyed by the attacker-supplied `from` address on `h.relayState`, and a `CreateRelayResponse` is sent back claiming that relay path is now established for `from`: [3](#0-2) 

Similarly, in the "I am a forwarding relay" branch, `AddRelay(..., from, ...)` and `peer.relayState.UpdateRelayForByIpState(from, Requested)` install relay-routing state under an address that was never validated against `h`'s certificate/vpnAddrs: [4](#0-3) 

This is structurally the same root cause as the Beedle report: an operation is performed using a caller-supplied identifier (`poolId` in Beedle, `RelayFromAddr` here) that is expected to be consistent with another already-verified entity (the loan's token pair in Beedle, the sending HostInfo's certified `vpnAddrs` here), but that consistency is never checked. Just as an attacker in Beedle could point `poolId` at an unrelated (forged) pool to steal a loan, here an authenticated-but-malicious peer can point `RelayFromAddr` at an arbitrary victim address to have relay/forwarding state installed and keyed under that victim's identity, without ever proving control of it.

### Impact Explanation
Relay state (`RelayState.relayForByAddr` / `relayForByIdx`) drives which encrypted tunnel a relay-tagged packet is treated as belonging to, and which `HostInfo` (and therefore firewall certificate context) governs delivery of relayed traffic (see `hostmap.go` `RelayState` and `QueryRelayForByIdx`/`QueryVpnAddrsRelayFor`). Poisoning this state with an attacker-chosen `from` address that does not match the sender's real certificate identity lets a malicious-but-authenticated peer:
- register itself (or coerce a relay/target node) into believing traffic on a given relay index originates from/targets an address it does not own, and
- potentially get relayed traffic delivered/attributed under a victim's `vpnAddr`, subverting the address-to-certificate binding the firewall (`firewall.go` `Drop`, which trusts `h.vpnAddrs`/certificate networks) and hostmap logic rely on for authorization decisions.

This is a remote state-poisoning vector reachable by any peer that can complete a normal handshake (no CA-signed certificate needed beyond the attacker's own, valid, cert), and can be leveraged to build broader spoofing/DoS or misrouting/traffic-forgery scenarios against victims whose addresses are referenced this way.

### Likelihood Explanation
Likelihood is high for any deployment using `relay.use_relays`/`relay.am_relay`: the control channel path is reachable by any peer that has completed a legitimate handshake with the relay-capable node, and the message fields (`RelayFromAddr`, `RelayToAddr`) are fully attacker-controlled with only a "not myself" self-check, no cross-check against the sending HostInfo's own certified addresses.

### Recommendation
In `handleCreateRelayRequest` (and correspondingly in `handleCreateRelayResponse`/`EstablishRelay`), verify that the claimed `RelayFromAddr` is consistent with the sending peer `h`'s actual authenticated identity where applicable — i.e., when `h` is asserting relay state for itself as the originator, `from` must be checked against `h.vpnAddrs`/`h.GetCert().Certificate.Networks()`. Where `h` is a legitimate intermediate/forwarding relay for a third party, that authorization should be explicit (e.g., only accept a claimed `from` that was actually established via a prior verified relay chain step) rather than trusted at face value from the message payload.

### Proof of Concept
Not independently verified end-to-end (would require reproducing on a running relay setup); the vulnerable code path is:
1. Attacker `A` completes a normal (valid, non-forged) handshake with relay node `R` (`relay.am_relay: true`).
2. `A` sends a `CreateRelayRequest` control message to `R` over its own authenticated tunnel, but sets `RelayFromAddr = V` (a victim address `A` does not own) and `RelayToAddr = B` (some real target `R` can also reach).
3. `R`'s `HandleControlMsg` → `handleCreateRelayRequest` runs; since `f.myVpnAddrsTable.Contains(from)` is false (V isn't R's own address) and `target` (`B`) is not `R` itself, `R` proceeds to the "forwarding relay" branch, calling `AddRelay(rm.l, peer, f.hostMap, from=V, ...)` — installing relay state on `peer` (B's HostInfo) keyed by `V`, and forwarding a `CreateRelayRequest` to `B` claiming `RelayFromAddr = V`.
4. `B` now creates/updates its own relay state believing address `V` is relaying through `R`, even though `V` never participated in any handshake with `R` or `B` — poisoning `B`'s relay routing/attribution for `V` at `R`'s (attacker `A`'s) direction.

func (rm *relayManager) HandleControlMsg(h *HostInfo, d []byte, f *Interface) {
	msg := &NebulaControl{}
	err := msg.Unmarshal(d)
	if err != nil {
		h.logger(f.l).Error("Failed to unmarshal control message", "error", err)
		return
	}

	var v cert.Version
	if msg.OldRelayFromAddr > 0 || msg.OldRelayToAddr > 0 {
		v = cert.Version1

		b := [4]byte{}
		binary.BigEndian.PutUint32(b[:], msg.OldRelayFromAddr)
		msg.RelayFromAddr = netAddrToProtoAddr(netip.AddrFrom4(b))

		binary.BigEndian.PutUint32(b[:], msg.OldRelayToAddr)
		msg.RelayToAddr = netAddrToProtoAddr(netip.AddrFrom4(b))
	} else {
		v = cert.Version2
	}

	// validate:
	switch msg.Type {
	case NebulaControl_CreateRelayRequest, NebulaControl_CreateRelayResponse:
		if msg.RelayFromAddr == nil {
			if f.l.Enabled(context.Background(), slog.LevelDebug) {
				h.logger(f.l).Debug("Control message received with nil RelayFromAddr", "type", msg.Type)
			}
			return
		} else if msg.RelayToAddr == nil {
			if f.l.Enabled(context.Background(), slog.LevelDebug) {
				h.logger(f.l).Debug("Control message received with nil RelayToAddr", "type", msg.Type)
			}
			return
		}
	}

	switch msg.Type {
	case NebulaControl_CreateRelayRequest:
		rm.handleCreateRelayRequest(v, h, f, msg)
	case NebulaControl_CreateRelayResponse:
		rm.handleCreateRelayResponse(v, h, f, msg)
	}
}
