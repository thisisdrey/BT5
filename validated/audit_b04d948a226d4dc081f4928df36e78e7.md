### Title
`ExchangeInjectActuator` rounds the counter-asset requirement down, letting the exchange creator underpay when adding liquidity and skew the pooled TRC10↔TRX exchange rate at the vault's expense - ([File: actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java])

### Summary
`ExchangeInjectActuator` computes the amount of the paired token (`anotherTokenQuant`) that must be deposited alongside the user-specified `tokenQuant` in order to keep the bancor-style exchange's price ratio unchanged. Both the `execute()` path and the `doValidate()` path use integer floor division to derive this amount, which always rounds down. This means the caller (the exchange's creator, an otherwise unprivileged account that only needed to broadcast an `ExchangeCreateContract` to obtain that role) systematically pays less of the second asset than the exact ratio requires, shifting the pool's internal exchange rate in their favor on every call — the same "round in favor of the user instead of the vault" defect described in the external report.

### Finding Description
In `execute()`: [1](#0-0) 

and in `doValidate()`: [2](#0-1) 

`anotherTokenQuant` is derived as `floorDiv(balanceB * tokenQuant, balanceA)` (execute) / `BigInteger.divide()` (validate) — both perform floor division toward negative infinity/zero for positive operands. Whenever `balanceB * tokenQuant` is not exactly divisible by `balanceA`, the fractional remainder is silently dropped, so the depositor contributes strictly less of the paired asset than the exact proportional amount needed to preserve the pool's price. After the balances are updated with `exchangeCapsule.setBalance(...)`, the resulting ratio `secondTokenBalance/firstTokenBalance` (or its inverse) is shifted slightly away from its pre-injection value, in the direction that favors the depositor.

This differs from `ExchangeWithdrawActuator`, which performs the analogous computation but additionally enforces a "Not precise enough" bound via `BigDecimal` scaled division and a 0.01% tolerance check: [3](#0-2) 
`ExchangeInjectActuator` has no equivalent precision check — it accepts the floor-divided value unconditionally, as long as it is `> 0` (line 229 of the validate snippet above).

Since any account can permissionlessly become the "creator" of its own exchange pool (via `ExchangeCreateContract`) and that pool is then used by arbitrary third parties trading through `ExchangeTransactionActuator`, the creator can call `ExchangeInjectContract` repeatedly with small `tokenQuant` values chosen so that `balanceB * tokenQuant` is not evenly divisible by `balanceA`, systematically underfunding the counter-asset side and nudging the AMM price in a favorable direction before executing a trade via `ExchangeTransactionActuator` against the now-mispriced pool, or before other traders unknowingly transact at the skewed rate.

### Impact Explanation
This is a rounding-direction defect in a Medium-severity value-leak class: it lets a shared liquidity pool ("vault" analog for the on-chain TRC10↔TRX exchange) be nudged away from its fair price on every `ExchangeInjectContract` call, at the exchange's expense rather than the depositor's. Repeated over many transactions/automation, this results in a continuous, quantifiable drift of the pool's exchange rate that benefits the calling account, matching the "slow and continuous loss of value from the vault" impact described in the analog report. It does not require any privileged role beyond self-creating an exchange pool, which any account can do.

### Likelihood Explanation
High reachability/likelihood for triggering the rounding: any account can create an exchange with `ExchangeCreateContract` and then call `ExchangeInjectContract` with attacker-chosen `tokenQuant` values to force non-exact division, since `calcFee()` returns `0` there is no fee friction discouraging repeated small injections, and `doValidate()` only rejects the computed `anotherTokenQuant` if it is `<= 0` — it does not reject imprecise (rounded) results the way `ExchangeWithdrawActuator` does.

### Recommendation
Mirror the fix pattern from the external report: make `ExchangeInjectActuator`'s rounding direction favor the pool, not the caller (e.g., round `anotherTokenQuant` up, `Math.ceilDiv`/`BigInteger` with `RoundingMode.CEILING`), or add the same "Not precise enough" tolerance check that `ExchangeWithdrawActuator` already applies, so the injector cannot supply less than the fair proportional amount.

### Proof of Concept
1. Attacker calls `ExchangeCreateContract` to create an exchange with `firstTokenBalance = 3`, `secondTokenBalance = 10` (ratio 10/3 ≈ 3.333).
2. Attacker (now the exchange's `creatorAddress`) calls `ExchangeInjectContract` with `tokenId = firstTokenID`, `quant = 1`.
3. In `doValidate()`/`execute()`, `anotherTokenQuant = floor(10 * 1 / 3) = 3` (fair value would be 3.33). The attacker deposits only `1` of the first token and `3` of the second token instead of the ~3.33 needed to preserve the ratio.
4. New balances become `(4, 13)`; ratio drops from `3.333` to `3.25`, shifting the AMM price in the attacker's favor at negligible cost.
5. Attacker repeats steps 2–4 with new `tokenQuant` values chosen to always produce a non-exact division, and/or immediately trades via `ExchangeTransactionActuator` against the now-skewed pool to realize the mispricing, draining value from the shared exchange over many iterations.
