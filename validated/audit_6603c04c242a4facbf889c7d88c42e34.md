### Title
Precision-loss due to division-before-multiplication in witness/transaction-fee reward brokerage calculation - (File: `chainbase/src/main/java/org/tron/core/service/MortgageService.java`)

### Summary
`MortgageService.payReward()` computes the super representative's brokerage cut by first dividing the integer `brokerage` percentage by `100` into a `double`, then multiplying that fraction by the reward `value`, instead of multiplying first and dividing afterward. This is the exact division-before-multiplication anti-pattern described in the external report (dividing then multiplying instead of multiplying then dividing), and it operates on values (`value` up to SUN-denominated TRX amounts, i.e., potentially > 2^53) that exceed the 53-bit mantissa of a `double`, causing systematic, silent precision loss in every block/transaction-fee reward distribution.

### Finding Description
`payReward()` is:
```java
private void payReward(byte[] witnessAddress, long value) {
    long cycle = dynamicPropertiesStore.getCurrentCycleNumber();
    int brokerage = delegationStore.getBrokerage(cycle, witnessAddress);
    double brokerageRate = (double) brokerage / 100;
    long brokerageAmount = (long) (brokerageRate * value);
    value -= brokerageAmount;
    delegationStore.addReward(cycle, witnessAddress, value);
    adjustAllowance(witnessAddress, brokerageAmount);
}
``` [1](#0-0) 

`brokerage / 100` is computed first as a `double`, which is exactly the "downscale first, upscale/multiply later" pattern flagged in the report. Because `double` only carries 53 bits (~15-17 significant decimal digits) of mantissa precision, and TRX reward `value` (denominated in SUN, 1e6 per TRX) routinely exceeds 2^53 (~9.007e15) for large block-reward pools, the multiplication `brokerageRate * value` loses precision relative to the mathematically equivalent `brokerage * value / 100` performed with integer/`BigInteger` arithmetic.

The same anti-pattern also appears in `payStandbyWitness()`:
```java
double eachVotePay = (double) totalPay / voteSum;
long pay = (long) (w.getVoteCount() * eachVotePay);
``` [2](#0-1) 
and in the legacy vote-reward algorithm `computeReward(long cycle, List<Pair<byte[], Long>> votes)`:
```java
double voteRate = (double) userVote / totalVote;
reward += voteRate * totalReward;
``` [3](#0-2) 

`payReward()` is invoked from `payBlockReward()` and `payTransactionFeeReward()`, both called from `Manager` during block application for every block produced and for transaction fees paid by ordinary transaction senders — i.e., the reward math runs on every block/transaction, not just in an edge case. [4](#0-3) 

### Impact Explanation
Because the brokerage/vote-share fraction is computed and truncated to a `double` before being multiplied by the (potentially very large) reward value, the `brokerageAmount` credited to the SR's allowance and the residual `value` credited to the delegation reward pool can systematically diverge from the mathematically correct integer split. Over the lifetime of the chain, across every block reward and every transaction fee, this compounds into a real accounting drift between SR brokerage allowance and voter reward pool balances — a form of under/over-crediting of funds that is deterministic and reproducible, not merely a rounding artifact of one-off computations. This falls under the disclosed "unbacked balance"/"theft or permanent freezing of funds" class since value silently leaks or is stuck in the wrong balance bucket depending on rounding direction.

### Likelihood Explanation
This code executes unconditionally on every block reward and every transaction fee distribution via `Manager`'s calls to `payBlockReward`/`payTransactionFeeReward`/`payStandbyWitness`, requiring no privileged actor — it is triggered purely by normal transaction and block processing. The precision-loss magnitude is proportional to `value`, so it is most pronounced for high-value blocks/fee pools, which occur naturally as chain usage grows.

### Recommendation
Replace the `double`-based fraction computation with integer/`BigInteger` arithmetic that multiplies before dividing, mirroring the fix already applied elsewhere in the codebase's "hardened" calculation paths (e.g. `SafeExchangeProcessor`, `RewardViCalService`/`DelegationStore` which use `BigInteger.multiply(...).divide(...)`):
```java
long brokerageAmount = BigInteger.valueOf(value)
    .multiply(BigInteger.valueOf(brokerage))
    .divide(BigInteger.valueOf(100))
    .longValueExact();
```
Apply the same multiply-then-divide correction to `payStandbyWitness()`'s `eachVotePay` computation and to the legacy `computeReward(long cycle, ...)` vote-rate computation.

### Proof of Concept
1. Assume a block/period where `totalPay` (or transaction-fee `value`) equals a large SUN amount, e.g. `9_007_199_254_740_993L` (2^53 + 1, exceeding double's exact integer range), and `brokerage = 33` (33%).
2. Correct value: `value * brokerage / 100 = 9_007_199_254_740_993 * 33 / 100 = 2_972_375_753_064_527` (via BigInteger, exact).
3. Actual code path: `brokerageRate = (double) 33 / 100 = 0.33` (already an inexact double), then `brokerageRate * value` is computed in double precision, losing bits from `value` because `value` itself cannot be exactly represented as a `double` beyond 2^53, and the multiplication further compounds rounding error before the final cast to `long`.
4. The resulting `brokerageAmount` and `value -= brokerageAmount` diverge from the exact integer split by an amount that grows with the size of `value`, and this discrepancy is applied on every reward payment call (`payBlockReward`/`payTransactionFeeReward`/`payStandbyWitness`) system-wide.

  private long computeReward(long cycle, List<Pair<byte[], Long>> votes) {
    long reward = 0;
    for (Pair<byte[], Long> vote : votes) {
      byte[] srAddress = vote.getKey();
      long totalReward = delegationStore.getReward(cycle, srAddress);
      if (totalReward <= 0) {
        continue;
      }
      long totalVote = delegationStore.getWitnessVote(cycle, srAddress);
      if (totalVote == DelegationStore.REMARK || totalVote == 0) {
        continue;
      }
      long userVote = vote.getValue();
      double voteRate = (double) userVote / totalVote;
      reward += voteRate * totalReward;
    }
    return reward;
  }
