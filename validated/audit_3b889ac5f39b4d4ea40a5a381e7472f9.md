Found it: `Rsv.fromSignature` is called with an attacker-supplied, arbitrary-length signature byte array without any prior length validation in `TransactionResult.parseSignature`, and `Rsv.fromSignature` itself performs unchecked fixed-offset copies that assume a signature of at least 65 bytes.

#### Title
Unvalidated fixed-offset signature parsing causes crash (DoS) in `eth_getTransactionByHash`/block JSON-RPC query path - (File: `framework/src/main/java/org/tron/core/services/jsonrpc/types/TransactionResult.java`)

### Summary
`Rsv.fromSignature` copies fixed byte ranges `[0,32)`, `[32,64)`, and reads index `64` from the input `sign` array with no length check [1](#0-0) . Most callers (e.g. `PrecompiledContracts.recoverAddrBySign`) guard this by checking `sign.length < 65` before calling it [2](#0-1) . However, `TransactionResult.parseSignature` calls `Rsv.fromSignature(signature.toByteArray())` directly on the raw transaction signature bytes with **no length check at all** [3](#0-2) .

### Finding Description
A `Transaction`'s signature field is an arbitrary-length `bytes` field in the protobuf and is not constrained to 65 bytes at the protobuf/deserialization layer. Transaction signature validation elsewhere in the codebase (`TransactionCapsule`) does perform its own checks before invoking crypto recovery, but the JSON-RPC transaction-formatting path (`TransactionResult`, used to build `eth_getTransactionByHash`/`eth_getBlockByNumber` style responses) reformats *already-persisted* transactions and blindly calls `Rsv.fromSignature(signature.toByteArray())` on `tx.getSignature(0)` without checking `signature.size() >= 65` first [4](#0-3) . If a signature shorter than 65 bytes ever reaches this code path (e.g., a broadcast transaction whose signature array is short but which still passes whatever check gates block/tx storage, or a transaction constructed via a code path where signature-length enforcement is weaker than in the primary broadcast validator), `Arrays.copyOfRange(sign, 0, 32)` / `copyOfRange(sign, 32, 64)` will throw `ArrayIndexOutOfBoundsException`, and `sign[64]` will throw the same for anything under 65 bytes.

This mirrors the CVE-2005-3185 bug class: a fixed-size buffer/offset operation performed on attacker-influenced input without validating that the input is at least as long as the offsets being read — in Java this manifests as an unhandled exception rather than memory corruption, but it is a reachable unauthenticated crash trigger via the JSON-RPC query surface rather than actual RCE.

### Impact Explanation
If reachable, this throws an unhandled `ArrayIndexOutOfBoundsException` while serving a JSON-RPC query for a transaction/block, potentially crashing or repeatedly failing that request-handling thread — a node-level denial-of-service against the JSON-RPC query API (an anonymous API client entry point explicitly in scope). I was **not able to confirm** whether the exception is caught by an outer JSON-RPC error handler (which would downgrade this from a crash to a harmless error response) or whether it is possible today for a transaction with a <65-byte signature to actually be persisted/queryable, since `TransactionCapsule`'s primary signature-length enforcement (`PER_SIGN_LENGTH`/`truncateSignatures`) appears to target oversized signatures rather than undersized ones [5](#0-4) . This uncertainty means the finding should be treated as a likely-but-unconfirmed reachable crash path rather than a proven exploit.

### Likelihood Explanation
Likelihood is uncertain/Medium: the vulnerable code (`Rsv.fromSignature`) has no defensive length check, but the surrounding signature-validation pipeline that runs at broadcast time (in `TransactionCapsule`) may already reject or normalize undersized signatures before they can be stored and later queried through `TransactionResult`. Without further confirmation of whether an under-length signature can survive into stored/query-able state, this cannot be rated High with confidence.

### Recommendation
Add an explicit length guard in `Rsv.fromSignature` (reject/throw a clear exception for `sign.length < 65`) so all callers, including `TransactionResult.parseSignature`, fail safely instead of relying on each call site to remember to pre-check length, and ensure the JSON-RPC handler wraps per-transaction formatting in a try/catch so a single malformed persisted record cannot take down a query response.

### Proof of Concept
Not independently verified end-to-end (would require confirming a signature shorter than 65 bytes can be persisted and later retrieved via `eth_getTransactionByHash`/block query); conceptually: craft/store a `Transaction` whose `signature[0]` is fewer than 65 bytes, then query it through the JSON-RPC transaction/block endpoint that constructs a `TransactionResult`, triggering `Rsv.fromSignature` on the short array and throwing `ArrayIndexOutOfBoundsException`.
