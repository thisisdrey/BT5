### Title
Pending Commission Redirected to New Beneficiary When `set_beneficiary_for_operator` Is Called Without Prior Distribution — (`staking_contract.move` / `delegation_pool.move`)

### Summary

`staking_contract::set_beneficiary_for_operator` and `delegation_pool::set_beneficiary_for_operator` both allow an operator to atomically replace the commission recipient without first flushing accrued-but-undistributed commission. Any commission that was earned under the old beneficiary's tenure is silently redirected to the new beneficiary, causing a direct, permanent loss of APT for the old beneficiary.

### Finding Description

In `staking_contract.move`, `set_beneficiary_for_operator` simply overwrites the `BeneficiaryForOperator` resource: [1](#0-0) 

The code's own comment acknowledges the problem but does not enforce the fix:

> "Any existing unpaid commission rewards will be paid to the new beneficiary. **To ensures payment to the current beneficiary, one should first call `distribute` before switching the beneficiary.**" [2](#0-1) 

The same pattern exists in `delegation_pool::set_beneficiary_for_operator`, which similarly documents but does not enforce a prior `synchronize_delegation_pool` call: [3](#0-2) 

By contrast, `staking_contract::switch_operator` (which replaces the operator, not the beneficiary) correctly calls both `distribute_internal` and `request_commission_internal` before making the switch: [4](#0-3) 

And `delegation_pool::set_operator` correctly calls `synchronize_delegation_pool` first: [5](#0-4) 

The inconsistency is clear: operator-replacement paths flush pending state; beneficiary-replacement paths do not.

### Impact Explanation

Commission accrues inside the stake pool as unlocked-but-undistributed APT. When `distribute_internal` is called, it reads `beneficiary_for_operator` at that moment to determine where to send the funds: [6](#0-5) 

If the operator calls `set_beneficiary_for_operator` before `distribute` is called, all previously accrued commission is paid to the **new** beneficiary when `distribute` eventually runs. The old beneficiary receives nothing for the period they were entitled to. This is a direct, permanent loss of APT for the old beneficiary — funds that were economically theirs are permanently redirected to a different address.

### Likelihood Explanation

- `set_beneficiary_for_operator` is a public entry function callable by any operator on mainnet (gated by `features::operator_beneficiary_change_enabled()` in `staking_contract`, ungated in `delegation_pool`).
- Commission accumulates continuously between `distribute` calls; the window of exposure is the entire lockup cycle (typically weeks).
- A malicious operator can deliberately time the beneficiary switch to capture the old beneficiary's accumulated commission.
- Even without malice, an operator who changes beneficiaries without reading the warning comment causes the same loss.

### Recommendation

Mirror the pattern used by `switch_operator` and `delegation_pool::set_operator`: call `distribute_internal` (or `synchronize_delegation_pool`) atomically inside `set_beneficiary_for_operator` before overwriting the beneficiary address. This ensures all commission earned under the old beneficiary is settled before the new beneficiary takes effect.

### Proof of Concept

1. Operator `O` has beneficiary `B_old`. Staking rewards accumulate for one epoch; commission of X APT is now pending but not yet distributed.
2. Operator `O` calls `staking_contract::set_beneficiary_for_operator(B_new)`. No distribution occurs.
3. Anyone calls `staking_contract::distribute(staker, O)`. `distribute_internal` reads `beneficiary_for_operator(O)` → returns `B_new`. All X APT commission is sent to `B_new`.
4. `B_old` receives 0 APT despite having been the designated beneficiary when the commission was earned.

    /// Allows an operator to change its beneficiary. Any existing unpaid commission rewards will be paid to the new
    /// beneficiary. To ensures payment to the current beneficiary, one should first call `distribute` before switching
    /// the beneficiary. An operator can set one beneficiary for staking contract pools, not a separate one for each pool.
    public entry fun set_beneficiary_for_operator(
        operator: &signer, new_beneficiary: address
    ) acquires BeneficiaryForOperator {
        assert!(
            features::operator_beneficiary_change_enabled(),
            std::error::invalid_state(EOPERATOR_BENEFICIARY_CHANGE_NOT_SUPPORTED)
        );
        // The beneficiay address of an operator is stored under the operator's address.
        // So, the operator does not need to be validated with respect to a staking pool.
        let operator_addr = signer::address_of(operator);
        let old_beneficiary = beneficiary_for_operator(operator_addr);
        if (exists<BeneficiaryForOperator>(operator_addr)) {
            borrow_global_mut<BeneficiaryForOperator>(operator_addr).beneficiary_for_operator =
                new_beneficiary;
        } else {
            move_to(
                operator,
                BeneficiaryForOperator { beneficiary_for_operator: new_beneficiary }
            );
        };

        emit(
            SetBeneficiaryForOperator {
                operator: operator_addr,
                old_beneficiary,
                new_beneficiary
            }
        );
    }
