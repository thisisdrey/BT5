### Title
Unsigned integer underflow in packfile bookkeeping causes forced/erroneous repack decisions - ([File: internal/git/housekeeping/optimization_strategy.go])

### Summary
The DYAD finding is a Solidity underflow (`tvl - dyad.totalSupply()`) that reverts/misbehaves whenever a subtrahend can exceed the minuend. Gitaly's housekeeping heuristic performs an analogous unchecked `uint64` subtraction on repository-derived counters that are not validated to be internally consistent, and one of the operands (`MultiPackIndex.PackfileCount`) is read verbatim from an on-disk file header without cross-checking it against the actual number of packfiles present.

### Finding Description
In `HeuristicalOptimizationStrategy.ShouldRepackObjects`, Gitaly computes:

```go
untrackedPackfiles := s.info.Packfiles.Count - s.info.Packfiles.MultiPackIndex.PackfileCount
``` [1](#0-0) 

Both operands are `uint64`. `Packfiles.Count` is derived by counting `*.pack` files found on disk in `PackfilesInfoForRepository` [2](#0-1) , while `MultiPackIndex.PackfileCount` is parsed directly from the 4-byte "number of packfiles" field of the `multi-pack-index` file header, with **no validation** that this value matches the number of packfiles the MIDX actually indexes:

```go
packfileCount := binary.BigEndian.Uint32(midxHeader[8:12])
midx := MultiPackIndexInfo{
    Exists:        true,
    Version:       version,
    PackfileCount: uint64(packfileCount),
}
``` [3](#0-2) 

If a `multi-pack-index` file is placed on disk whose header advertises a `PackfileCount` larger than the number of real `.pack` files in `objects/pack`, the subtraction underflows silently (Go wraps unsigned integers rather than panicking, unlike the reverting behavior in the original Solidity report), producing a value near `math.MaxUint64`. This value is then compared against `actualLimit`:

```go
if untrackedPackfiles > uint64(actualLimit) {
    return true, geometricRepackCfg
}
``` [4](#0-3) 

which will always evaluate `true`, forcing a full geometric repack decision on every housekeeping evaluation regardless of the repository's real state.

The same unvalidated field is also exported via metrics (`multi_pack_index_packfile_count`) and via the `RepositoryInfo` RPC response (`MultiPackIndex.PackfileCount`), so any inconsistency propagates to monitoring and to callers of the RPC. [5](#0-4) [6](#0-5) 

A `multi-pack-index` file with an attacker-influenced header can reach a repository's `objects/pack` directory through `CreateRepositoryFromSnapshot`, which extracts a caller-supplied TAR archive (fetched over HTTP with caller-controlled URL/auth) directly into a freshly created repository with only minimal validation, and explicitly documents that "the received archive is trusted a lot": [7](#0-6) 

### Impact Explanation
Because the subtraction wraps around instead of reverting, the practical impact differs from the original report's fund-lockup: here it causes the housekeeping heuristic to permanently conclude that a geometric repack is always required, defeating the intended heuristic that avoids expensive repack operations. Repeated/forced invocation of expensive repack strategies on a repository (potentially large ones) consumes disproportionate CPU/IO resources on the Gitaly node, degrading service for other repositories/tenants sharing that node — a resource-exhaustion / DoS-style effect on the housekeeping subsystem. It also pollutes exported statistics (`RepositoryInfo` RPC, Prometheus metrics) with self-inconsistent values (`MultiPackIndex.PackfileCount` in `RepositoryInfoResponse` can be inconsistent with `PackfileCount` shown for actual packfiles), potentially misleading capacity planning/alerting.

### Likelihood Explanation
Reaching this requires the ability to place an arbitrary/crafted `multi-pack-index` file inside a repository's `objects/pack` directory. Ordinary `git push`/`fetch` traffic through `receive-pack`/`upload-pack` does not allow writing arbitrary raw files (only actual pack/object data via `index-pack`), so this is not reachable from a simple push. It is reachable through repository-import-style RPCs that extract externally supplied archives verbatim onto disk (`CreateRepositoryFromSnapshot`), which the code itself flags as under-hardened. Likelihood is therefore moderate and depends on whether that RPC (or an equivalent snapshot/replication import path) is exposed to a caller who does not fully control the destination Gitaly node already.

### Recommendation
- Treat `MultiPackIndex.PackfileCount` (and any other header-derived counters) as untrusted input: validate it against the number of pack entries actually referenced by the MIDX's `PNAM`/object-count chunks, or at minimum clamp it to `Packfiles.Count` before use.
- Replace the raw subtraction in `ShouldRepackObjects` with a saturating/guarded subtraction, e.g. `if s.info.Packfiles.Count > s.info.Packfiles.MultiPackIndex.PackfileCount { untrackedPackfiles = ... } else { untrackedPackfiles = 0 }`.
- Harden `CreateRepositoryFromSnapshot`/similar archive-import paths to validate or regenerate derived Git metadata files (bitmaps, MIDX) rather than trusting extracted content verbatim, consistent with the TODO already present in that file.

### Proof of Concept
1. Create (or import via `CreateRepositoryFromSnapshot`) a repository whose `objects/pack` directory contains:
   - Zero or one real `pack-*.pack` file.
   - A `multi-pack-index` file whose header bytes 8-12 (big-endian `uint32`) are set to a large value (e.g. `0xFFFFFFFF`), while its TOC/chunk data is otherwise minimally valid enough to pass `MultiPackIndexInfoForPath`'s parsing.
2. Call `RepositoryInfo` RPC or trigger housekeeping (`OptimizeRepository`) against this repository.
3. Observe that `PackfilesInfoForRepository` returns `Packfiles.Count` (e.g. `1`) and `Packfiles.MultiPackIndex.PackfileCount` (e.g. `4294967295`), and that `HeuristicalOptimizationStrategy.ShouldRepackObjects` computes `untrackedPackfiles = 1 - 4294967295`, which underflows to `18446744069414584322` (as `uint64`), unconditionally triggering `geometricRepackCfg` on every evaluation.
