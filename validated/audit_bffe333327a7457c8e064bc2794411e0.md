### Title
Unconfirmed tenure downloader trusts peer-supplied `tip_height` for early-termination decision instead of the true height of `tip_block_id` - ([File: stackslib/src/net/download/nakamoto/tenure_downloader_unconfirmed.rs])

### Summary
`NakamotoUnconfirmedTenureDownloader::try_accept_tenure_info` decides whether the node is already caught up with a peer's unconfirmed tenure by comparing its own `highest_processed_block_height` against the peer-supplied `remote_tenure_tip.tip_height`, without ever validating that this integer actually corresponds to the chain length of `remote_tenure_tip.tip_block_id`. A malicious peer can supply a real/canonical `tip_block_id` together with a deflated `tip_height`, forcing the node to conclude `self.state = Done` and abandon fetching new unconfirmed blocks it hasn't seen yet.

### Finding Description
In `try_accept_tenure_info` [1](#0-0) , once `self.highest_processed_block_id` is set, the code loads the locally-known highest-processed block, computes its `chain_length`, and then does:

```
if &remote_tenure_tip.tip_block_id == highest_processed_block_id
    || highest_processed_block_height > remote_tenure_tip.tip_height
{
    ...
    self.state = NakamotoUnconfirmedDownloadState::Done;
}
```

The first disjunct (`tip_block_id == highest_processed_block_id`) is a legitimate identity check. The second disjunct, however, is a bare numeric comparison against `remote_tenure_tip.tip_height`, which is a field taken verbatim from the peer's `/v3/tenures/info` response body (decoded via `decode_nakamoto_tenure_info()` and passed straight into this function from `handle_next_download_response`, see [2](#0-1) ). Nowhere in `try_accept_tenure_info` is `tip_height` cross-checked against the actual chain length of `tip_block_id` — the block referenced by `tip_block_id` is precisely the ongoing/unconfirmed tip that the node has *not yet downloaded*, so it has no independent way to verify the claimed height at this point in the protocol. The consensus-hash/sortition checks performed earlier (lines 176–257) validate that `consensus_hash` and `parent_consensus_hash` are canonical and that the parent-tenure-start commitment matches, but none of that touches `tip_height`.

Exploit flow: a malicious peer responds to `GET /v3/tenures/info` with a real, canonical `tip_block_id` (so the consensus-hash and commitment checks pass) but sets `tip_height` far lower than the true chain length of that block (e.g., 0 or 1). If the requesting node has already processed at least one earlier round (`highest_processed_block_id`/`highest_processed_block_height` set from a previous successful poll), the condition `highest_processed_block_height > remote_tenure_tip.tip_height` becomes trivially true regardless of the real state of the tenure. The state machine sets `self.state = Done`, only fetches/validates the tenure-start block (not the actually-new unconfirmed blocks), and returns — silently dropping any newer unconfirmed blocks that peer holds.

### Impact Explanation
Per malicious peer, this causes the node to falsely conclude it is already at or ahead of that peer's unconfirmed chain tip, causing it to skip fetching new unconfirmed Nakamoto blocks from that peer for that polling round. This is a "steer off the tip via false inventory"-style issue confined to the unconfirmed/mempool-adjacent tip-tracking path (not confirmed/canonical chain state, and not consensus block validation). Because a fresh `NakamotoUnconfirmedTenureDownloader` is created and a new `/v3/tenures/info` request is issued on subsequent polling rounds (per the state-machine's periodic re-polling design), the effect is repeatable every round the attacker is queried, but bounded to degraded/delayed unconfirmed-block visibility from that specific malicious peer rather than a durable or network-wide compromise — the node still has other honest peers supplying the same tenure via inventory/tenure downloads, and the confirmed/canonical chain-processing path is unaffected.

### Likelihood Explanation
Preconditions: attacker must be an already-connected peer serving `/v3/tenures/info` to the victim, and the victim must have already completed at least one prior polling round against this peer (`highest_processed_block_id` set) — both are ordinary, attacker-reachable states requiring no privileged role or secret. The attack is cheap (single crafted RPC response) and repeatable every polling interval.

### Recommendation
Do not use the peer-reported `tip_height` as authoritative for the early-termination decision. Either (a) drop the `highest_processed_block_height > remote_tenure_tip.tip_height` short-circuit entirely and rely solely on the `tip_block_id == highest_processed_block_id` identity check plus normal downstream chain-length checks performed once blocks are actually fetched (as already done for streamed blocks at lines 566–576), or (b) require the downloader to fetch/verify `tip_block_id`'s actual header (and thus its true `chain_length`) before allowing this height-based short-circuit to skip block retrieval.
