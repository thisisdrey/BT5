### Title
Wallet Contract pays the relayer's fee refund before the async faulty-relayer check completes - ([File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs])

### Summary
`inner_rlp_execute` fires an unconditional fee-refund transfer to the transaction's predecessor (the relayer) as soon as it classifies the transaction as an `EOABaseTokenTransfer`/`ERC20Transfer` with a non-zero fee, without waiting for the outcome of the asynchronous "faulty relayer" validation (`address_check`) that determines whether the relayer-supplied `target` was actually valid. This mirrors the Connext `_handleExecuteLiquidity` pattern: an early decision is gated on an incomplete/partial condition, while the "real" eligibility (validated later, asynchronously) is checked too late to prevent the payout.

### Finding Description
In `parse_rlp_tx_to_action` (`runtime/near-wallet-contract/implementation/wallet-contract/src/internal.rs:107-122`), when the parsed action is an Ethereum-emulation transfer whose `target_kind` is `EthImplicit(address)`, the code produces `TransactionKind::EthEmulation(EthEmulationKind::EOABaseTokenTransfer { address_check: Some(address), fee: tx_fee })`. The `address_check: Some(_)` marks that the relayer's claim (that `target` is *not* a registered named account) has **not yet been verified** — verification only happens later via an async cross-contract call to the address registrar (`address_check_callback`, `lib.rs:130-192`).

Back in `inner_rlp_execute` (`lib.rs:330-472`):
1. Nonce increment is correctly deferred for this `address_check: Some(_)` case (lines 358-365) — the code recognizes that a faulty relayer here should not consume the user's nonce.
2. However, immediately afterward (lines 374-385), the code checks only whether the transaction kind is `EOABaseTokenTransfer { fee, .. }` (matching **any** `address_check` value, `Some` or `None`) or `ERC20Transfer { fee, .. }`, and if `fee != 0` and `predecessor != current_account`, it unconditionally fires `env::promise_batch_create(&predecessor_account_id)` + `promise_batch_action_transfer(fee)` — a stand-alone promise, independent of the promise chain that performs the actual registrar lookup and action execution.

The registrar lookup and the "is this relayer faulty" determination only complete afterward, in `address_check_callback` (`lib.rs:134-192`). If the registrar responds with `maybe_account_id.is_some()` (i.e., the "eth-implicit" target the relayer used is actually a registered named account — meaning the relayer's classification was wrong/faulty), the callback bans the relayer or returns a failure **without ever executing the intended action** (lines 161-173). But by that point the fee-refund transfer promise has already been dispatched independently and cannot be reverted.

This is structurally the same bug class as the reported Connext issue: the code branches on a partial signal (`fee != 0`, ignoring `address_check`'s pending/undetermined state) to authorize a payout, while the authoritative check for whether the payout is actually warranted (the registrar-based faulty-relayer determination) is evaluated later and can invalidate the premise — but the payout has already happened.

### Impact Explanation
An unprivileged relayer (or the account owner acting as their own relayer) fully controls the `target` argument passed to `rlp_execute`/`rlp_execute` and thus controls whether `address_check` ends up `Some`. By crafting a transaction that:
- parses as an Ethereum-emulation base-token transfer to some `target`,
- specifies a `target` that is classified as `EthImplicit` but which the registrar will resolve to an existing named account,
- carries a non-zero `tx_fee` (attacker-chosen via `gas_price`/`gas_limit` on the signed inner Ethereum tx),

can trigger the immediate fee-refund transfer to the relayer/predecessor from the wallet contract's own balance, while the actual requested action is aborted (banned relayer / failure) in `address_check_callback` once the registrar responds. This results in a direct, unrecoverable loss of the wallet owner's NEAR balance to a relayer who performed no valid work — concrete theft of funds from the eth-implicit wallet contract, which is explicitly in scope.

### Likelihood Explanation
The eth-implicit wallet contract is a core, reachable production surface (any ordinary transaction can call `rlp_execute` against a deployed wallet). Triggering the vulnerable path requires no special privilege — a relayer only needs to submit an RLP transaction with a `target` value that the registrar will resolve to a real account and a nonzero attached fee. The "single in-flight transaction" guard (`has_in_flight_tx`) limits how often this can be repeated concurrently but does not prevent it from happening at all; each faulty-relayer cycle still leaks the computed `fee` from the wallet before being detected. Because the fee amount is derived from attacker-controlled Ethereum-tx fields (`max_fee_per_gas`/`gas_limit`, capped by `VALUE_MAX`), the attacker has direct control over how much is drained per attempt, and the sequence can be repeated across multiple wallet interactions over time.

### Recommendation
Do not dispatch the fee-refund transfer until the relayer's target has been confirmed valid. Specifically, when `TransactionKind::EthEmulation(EthEmulationKind::EOABaseTokenTransfer{ address_check: Some(_), fee, .. })`, defer creating the refund promise from `inner_rlp_execute` and instead perform the transfer only inside `address_check_callback`'s "honest relayer" branch (the `else` branch at `lib.rs:174-189`, after confirming `maybe_account_id.is_none()`), mirroring how nonce incrementing is already correctly deferred for this case. This ensures the fee payment is gated on the same authoritative check (`address_check` resolution) that determines whether the relayer/transaction is legitimate, rather than on the coarser, premature `fee != 0` condition.

### Proof of Concept
Conceptual PoC (cannot be executed without a live sandbox in this environment, but the code path is directly traceable):
1. Deploy a Wallet Contract instance for eth-implicit account `W`, funded with NEAR.
2. Register an ordinary named account `victim.near` as `target` candidate in the address registrar with an address `A`.
3. Sign, as `W`'s owner, an Ethereum-style transaction (calldata parseable as `SelfNearNativeAction`/emulation) whose `to` = `A`, `gas_price`/`gas_limit` chosen to yield a non-trivial `tx_fee`, and call `rlp_execute(target = <eth-implicit-account-id derived from A>, tx_bytes_b64)` from a relayer account `R` (`predecessor_account_id = R`).
4. `parse_rlp_tx_to_action` classifies this as `EOABaseTokenTransfer { address_check: Some(A), fee }` because `target_kind == EthImplicit(A)`.
5. `inner_rlp_execute` immediately schedules `promise_batch_transfer(fee)` to `R` (lines 374-385), independent of the registrar lookup promise chain.
6. The registrar lookup (queued via `.then(ext.address_check_callback(...))`) resolves with `Some(victim.near)` because `A` is in fact a registered address.
7. `address_check_callback` observes `maybe_account_id.is_some()` and either bans the relayer or returns a failure (`lib.rs:161-173`) — the intended transfer action to `victim.near`/the emulated recipient never executes.
8. Net effect: `R` has already received `fee` from `W`'s balance in step 5, despite the action failing/being rejected as a faulty-relayer case in step 7 — funds are permanently transferred out of the wallet with no corresponding valid action performed.
