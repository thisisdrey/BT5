The `SignerEventReceiver`'s HTTP server has no authentication check whatsoever on any endpoint, including `/proposal_response`, and it's explicitly designed to bind to a configurable, non-loopback address (e.g. `endpoint = "0.0.0.0:30000"` in the sample configs) with an explicit warning in `stacks-signer/src/lib.rs` about the risk of exposing this to external networks.### Title
Unauthenticated `/proposal_response` endpoint allows forging `SignerEvent::BlockValidationResponse` - ([File: libsigner/src/events.rs])

### Summary
`SignerEventReceiver::next_event` dispatches any POST to `/proposal_response` straight into `process_event::<T, BlockValidateResponse>` with no signature, shared-secret, or origin check at the HTTP layer, identical to the unauthenticated `/stackerdb_chunks` path. Since the signer's event port is bound to a configurable, often non-loopback address (`0.0.0.0:30000` per sample configs), any remote TCP client that can reach that port can forge a `BlockValidateResponse` and have it delivered to the signer runloop as if the signer's own configured node had validated a block.

### Finding Description
`next_event` (libsigner/src/events.rs:413-459) routes based purely on URL path and HTTP method — there is no authentication check anywhere in this function or in `process_event` (events.rs:519-542). For `/proposal_response`, the body is read, JSON-deserialized into `BlockValidateResponse`, and converted via `TryFrom<BlockValidateResponse> for SignerEvent<T>` (events.rs:627-635), which unconditionally wraps it as `SignerEvent::BlockValidationResponse(block_validate_response)` — no cross-check against a pending proposal, no signature, no auth token.

The `auth_password`/`auth_token` pair documented in `docs/signing.md` and used in `stacks-signer/src/client/stacks_client.rs` only authenticates *outbound* signer→node RPC requests (e.g. `submit_block_proposal`); it plays no role in the *inbound* HTTP server (`SignerEventReceiver`) that the node uses to push `/proposal_response`, `/stackerdb_chunks`, `/new_burn_block`, `/new_block` events to the signer. This is confirmed by the fact that `auth_password` never appears in `libsigner/` at all — no grep hits in the crate that implements the event receiver.

The bind address is fully attacker-reachable in typical deployments: the sample signer config sets `endpoint = "0.0.0.0:30000"` (`sample/conf/signer/mainnet-signer-conf.toml:39`), and `stacks-signer/src/lib.rs:125-132` explicitly warns operators that the signer is "primarily designed for use with a local or subnet network stacks node" and that exposing it to external networks "could potentially expose sensitive data or functionalities to security risks if additional proper security checks are not integrated." This is a direct admission that the HTTP event-receiver endpoints (including `/proposal_response`) carry no built-in authentication and rely entirely on network-level isolation that is not enforced by any code in this repo.

An attacker with TCP reachability to the bound port can simply POST a crafted JSON body matching `BlockValidateResponse`'s schema to `/proposal_response` and have `next_event` return `Ok(SignerEvent::BlockValidationResponse(attacker_controlled))`, which `forward_event` (events.rs:469-490) sends unmodified to the signer runloop.

### Impact Explanation
This breaks the equality the question poses: the runloop is supposed to receive validation responses that reflect what *this signer's configured node* actually validated, but any remote party reaching the event port can inject arbitrary accept/reject verdicts. Because the signer's block-acceptance/rejection decisions and subsequent StackerDB signature broadcasts are driven by this event, a forged `BlockValidationResponse` lets a remote attacker manipulate a signer's local decision-making about block validity — e.g., forcing a false "reject" to stall block acceptance, or a false "accept" bypassing genuine node validation for that signer's vote. This is repeatable per message and matches "unauthenticated/unauthorized write to state" — here, forged input directly driving the signer's internal consensus-relevant state.

### Likelihood Explanation
Preconditions: the attacker needs plain TCP reachability to the signer's bound event-receiver port. No secret, peer identity, StackerDB slot ownership, or admin role is required — this matches the allowed "unprivileged remote party" threat model. The likelihood in default/sample deployments is elevated because the documented default binds to `0.0.0.0` rather than `127.0.0.1`, and the codebase itself warns operators about this exposure rather than enforcing it via code (no auth check exists to enforce even if an operator wanted one). Any operator who does not additionally firewall this port off is exposed; the attack costs one crafted HTTP POST and is trivially repeatable.

### Recommendation
Add authentication to the signer's HTTP event-receiver endpoints (`/proposal_response`, `/stackerdb_chunks`, `/new_burn_block`, `/new_block`) — e.g., require the same shared secret (`auth_password`/`auth_token`) as a header/Bearer token checked in `next_event` before dispatching to `process_event`, and reject requests without a valid token. Alternatively/additionally, bind the event receiver to loopback only by default and require explicit opt-in plus mandatory auth for non-loopback binding.

        self.with_server(|event_receiver, http_server, _is_mainnet| {
            // were we asked to terminate?
            if event_receiver.is_stopped() {

            }

            debug!("Got request"; "method" => %request.method(), "path" => request.url());

            if request.url() == "/status" {
                request
                .respond(HttpResponse::from_string("OK"))
                .expect("response failed");
                return Ok(SignerEvent::StatusCheck);
            }

            if request.method() != &HttpMethod::Post {
                return Err(EventError::MalformedRequest(format!(
                    "Unrecognized method '{}'",
                    request.method(),
                )));

                process_event::<T, StackerDBChunksEvent>(request)

fn process_event<T, E>(mut request: HttpRequest) -> Result<SignerEvent<T>, EventError>
where
    T: SignerEventTrait,
    E: serde::de::DeserializeOwned + TryInto<SignerEvent<T>, Error = EventError>,
{
    let mut body = String::new();

    if let Err(e) = request.as_reader().read_to_string(&mut body) {
        error!("Failed to read body: {:?}", &e);
        ack_dispatcher(request);
        return Err(EventError::MalformedRequest(format!(
            "Failed to read body: {:?}",
            e
        )));
    }
    // Regardless of whether we successfully deserialize, we should ack the dispatcher so they don't keep resending it
    ack_dispatcher(request);
    let json_event: E = serde_json::from_slice(body.as_bytes())
        .map_err(|e| EventError::Deserialize(format!("Could not decode body to JSON: {:?}", e)))?;

    let signer_event: SignerEvent<T> = json_event.try_into()?;

    Ok(signer_event)
}
