Audit Report

## Title
Child-bounty curator can be instantly slashed via a stale parent `update_due` inherited without any per-child timer initialization - (File: `substrate/frame/child-bounties/src/lib.rs`)

## Summary
`accept_curator` in `pallet-child-bounties` moves a child bounty to `ChildBountyStatus::Active { curator }` without recording any per-child timer, and the permissionless "inactive curator" branch of `unassign_curator` gates the slash on the *parent* bounty's `update_due` obtained via `Self::ensure_bounty_active(parent_bounty_id)` rather than any child-specific value. Since the parent's `update_due` is set once when the parent curator accepted and is refreshed only by the parent curator calling `extend_bounty_expiry` on the parent bounty, it can already be in the past when a brand-new child curator accepts, allowing any unprivileged account to immediately slash that child curator's freshly reserved deposit.

## Finding Description
`accept_curator` reserves the curator deposit and sets `child_bounty.status = ChildBountyStatus::Active { curator }` with no timestamp/`update_due` field stored on the child bounty itself. [1](#0-0) 

`unassign_curator`'s permissionless branch for `ChildBountyStatus::Active` reads the parent's `update_due` (not any child-specific value) and slashes the child curator's deposit if `sender == parent_curator || update_due < Self::treasury_block_number()`. [2](#0-1) 

Crucially, the pallet's own doc comment on `unassign_curator` explicitly documents this as the intended mechanism: *"the origin can be anyone iff the child-bounty curator is 'inactive'. Expiry update due of parent bounty is used to estimate inactive state of child-bounty curator."* [3](#0-2) 

By contrast, `pallet-bounties::accept_curator` computes its own `update_due = now + BountyUpdatePeriod` when the *parent's own* curator accepts. [4](#0-3) 

`ensure_bounty_active(parent_bounty_id)` only checks that the parent bounty status is `Active` and returns the parent curator and `update_due`; it does not check whether `update_due` has already elapsed. This means nothing in `add_child_bounty` or `propose_curator` prevents new child bounties/curators from being created under a parent bounty whose `update_due` has already passed (e.g., because nobody has yet called `unassign_curator` on the stale parent curator, or the parent curator simply has not called `extend_bounty_expiry`). Consequently, a child curator who accepts the role at that moment inherits a stale, already-expired deadline instead of getting a fresh grace period, and any unrelated account can call `unassign_curator` immediately afterward to trigger `slash_curator`, forfeiting the child curator's deposit via `T::Currency::slash_reserved` + `T::OnSlash::on_unbalanced`.

## Impact Explanation
This allows an unprivileged, unrelated account to permissionlessly force the loss of a legitimate child-bounty curator's reserved deposit through a public entrypoint (`unassign_curator`), with no real "inactivity" period elapsed for the child curator specifically. The corrupted/misused value is the child bounty's inherited "activity gate," which is actually the parent's `update_due` field rather than any dedicated per-child timer.

## Likelihood Explanation
Exploitation requires only observing a public on-chain value (a parent bounty whose `update_due` has already elapsed while it remains nominally `Active`) and calling a public extrinsic (`unassign_curator`) immediately after a new child curator accepts. No privileged role, capital, or race against block production is needed beyond ordinary transaction submission, making repeat exploitation straightforward wherever a parent bounty's curator has been inactive in extending `update_due`.

However, this exact mechanism — reusing the parent bounty's `update_due` as an inactivity heuristic for child-bounty curators — is explicitly documented in the pallet's own function-level doc comments as the intended design, not an unnoticed defect. `pallet-child-bounties` has no independent "update"/"extend" extrinsic for child bounties at all, so the parent's cadence is the only inactivity signal the pallet was designed to use. This weakens (but does not fully eliminate) the claim that this is an unintended state-machine defect versus a known, accepted design simplification/limitation of the child-bounties feature.

## Recommendation
Introduce a dedicated `update_due` (or `accepted_at`) field on `ChildBounty`, initialized in `accept_curator` to `now + BountyUpdatePeriod` independent of the parent's timer, and use that value — not the parent's — in the permissionless-inactivity branch of `unassign_curator`. Optionally add a per-child `extend_bounty_expiry`-equivalent call.

## Proof of Concept
1. Parent bounty `B` is `Active`; its curator accepted long ago and never called `extend_bounty_expiry`, so `update_due` for `B` has already elapsed while `B` is still nominally `Active` (nobody has called `unassign_curator` on the parent curator yet).
2. The parent curator adds a child bounty and proposes curator `C`.
3. `C` calls `accept_curator(parent_bounty_id, child_bounty_id)`; the child bounty becomes `Active { curator: C }` with no per-child timer stored.
4. Any unrelated account `X` immediately calls `unassign_curator(parent_bounty_id, child_bounty_id)`; inside, `ensure_bounty_active(parent_bounty_id)` returns the already-stale `update_due`, so the `Some(sender)` branch's `update_due < Self::treasury_block_number()` condition is true and `slash_curator` burns `C`'s just-reserved deposit one block after acceptance.
