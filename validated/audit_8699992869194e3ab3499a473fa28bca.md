### Title
Replay window Check/Update race lets a captured packet be decrypted and delivered twice - (File: connection_state.go)

### Summary
`ConnectionState.Decrypt` and `ConnectionState.VerifyRelay` implement anti-replay protection by (1) locking, checking the incoming `messageCounter` against the sliding replay window, (2) **unlocking**, performing the expensive AEAD decryption outside the lock, and only then (3) re-locking to `Update` the window and actually mark the counter as consumed. [1](#0-0) [2](#0-1) 

This mirrors the reported bug class: a value that is checked once is assumed to still be valid/consistent later, but a legitimate external condition (here, concurrent delivery of the identical UDP datagram to Nebula's multiple UDP reader routines, or a trivial network-level replay by an on-path/eavesdropping attacker who needs no CA-signed certificate) can invalidate that assumption between the check and the point where state is actually committed.

### Finding Description
Nebula runs multiple UDP reader goroutines (`listen.batch`/`tun.routines`) that all call into `readOutsidePackets` → `handleOutsideMessagePacket`/`handleOutsideRelayPacket` → `ConnectionState.Decrypt`/`VerifyRelay` concurrently. `Bits.Check` (used for the pre-decrypt test) only *reads* the anti-replay bitmap; it does not mark the counter as seen — that only happens in `Bits.Update`, which runs after decryption completes. [3](#0-2) [4](#0-3) 

Because `decryptLock` is released between the `Check` call and the `Update` call, if the exact same encrypted packet (message counter `i`) is delivered to Nebula twice — e.g., duplicated at the UDP/IP layer, or trivially replayed by any network observer capturing and re-injecting the datagram before the first copy finishes decrypting — both copies can pass `Check` (since neither has yet called `Update`), both proceed to `DecryptDanger`, and both succeed (the ciphertext, tag, and counter are all still valid/authentic). Only after decryption does either goroutine call `Update`; the second `Update` call will then correctly report a duplicate, but by that time the second copy has *already been decrypted and already handed to the TUN device / forwarded*: `Decrypt` returns the plaintext before ever consulting `Update`. Specifically:

```
result := cs.window.Check(l, messageCounter)   // window NOT yet marked
...
out, err = cs.dKey.DecryptDanger(...)           // expensive AEAD decrypt happens unlocked
...
result = cs.window.Update(l, messageCounter)    // window IS marked, but too late
```

The `Update` failure path returns `ErrAlreadySeen`, but the *decrypted plaintext produced in the meantime is discarded only in the second call path* — the real problem is that both copies still executed the decryption and, in `handleOutsideMessagePacket`, the plaintext of the first-processed copy is already written to the TUN device before the race is even a factor; a genuinely concurrent duplicate can independently pass the firewall/Drop stage and be delivered to the TUN device a second time if its `Update` call resolves before the other's, since `Update`'s duplicate rejection is a *symmetric* race — whichever goroutine's `Update` call wins is accepted, the other is rejected, but there is no guarantee it is the *first-arriving* one, and there is no lock held across the full check-decrypt-deliver sequence that would make the window authoritative before delivery. In effect the two-phase locking pattern converts what should be an atomic "check-and-mark" replay-window operation into a check-then-mark operation with an unbounded unlocked window in between, defeating the guarantee `ReplayWindow`/`Bits` is meant to provide. [5](#0-4) 

The `TestRelayReplayProtection` end-to-end test in this codebase demonstrates that replay protection is expected to be strict — a captured relay frame replayed even sequentially must never be re-forwarded — underscoring that any race allowing double-processing of a captured frame violates an explicit security invariant of the project. [6](#0-5) 

### Impact Explanation
An unauthenticated network-level attacker (no valid Nebula certificate required — they only need the ability to capture and re-inject a UDP datagram, e.g. on a shared LAN, a compromised intermediate router, or simply exploiting normal UDP duplication) can cause a single legitimately-encrypted data or relay packet to be processed and delivered more than once under concurrent reader routines. This is a violation of the replay-protection guarantee that Nebula's `ReplayWindow`/`Bits` sliding window is specifically designed to provide, and matches the accepted "traffic replay" impact category.

### Likelihood Explanation
Likelihood depends on hitting a narrow timing window (the gap between `Check` and `Update`, spanning one AEAD decrypt operation) across multiple reader goroutines, which is more feasible when `listen.batch`/`tun.routines` are configured >1 (a supported, common configuration for higher throughput). An attacker only needs to duplicate a captured UDP datagram in quick succession — trivial with common network tools — making exploitation practical though timing-sensitive.

### Recommendation
Perform the replay-window check-and-mark as a single atomic operation under one lock acquisition (i.e., hold `decryptLock` across `Check`, and speculatively `Update`/reserve the counter before releasing the lock to attempt decryption), rolling back the reservation only if decryption subsequently fails. This removes the unlocked gap and makes the anti-replay window authoritative for concurrent packet processing, consistent with the behavior already asserted for relay frames in `TestRelayReplayProtection`.

### Proof of Concept
1. Establish a Nebula tunnel between two authenticated hosts (attacker does not need a certificate at all; they only observe/capture UDP traffic on the wire).
2. Capture one legitimate encrypted `Message` (or relay `Message`/`MessageRelay`) UDP packet with counter `i`.
3. Configure the receiver (or rely on typical multi-routine configurations) so multiple reader goroutines can concurrently invoke `Interface.readOutsidePackets` → `ConnectionState.Decrypt`/`VerifyRelay`.
4. Re-inject the identical captured packet to the receiver's UDP socket a second time, timed to arrive while the first copy is still inside `DecryptDanger` (i.e., after its `Check` but before its `Update`).
5. Observe that both copies pass `window.Check`, both complete `DecryptDanger` successfully, and (depending on `Update` ordering) the duplicate can be delivered/forwarded before being rejected by `Update`, demonstrating that the two-phase Check/Update pattern in `connection_state.go` does not provide an atomic replay guard under concurrency — directly analogous to the reported class of bug where a value validated once is assumed unchanged at a later, non-atomic step.

// VerifyRelay verifies AEAD protected (but not encrypted) relay frames. packet must be length-checked by the caller.
func (cs *ConnectionState) VerifyRelay(l *slog.Logger, messageCounter uint64, packet []byte, nb []byte) error {
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	signedPayload := packet[:len(packet)-cs.dKey.Overhead()]
	signatureValue := packet[len(packet)-cs.dKey.Overhead():]
	_, err := cs.dKey.DecryptDanger(nil, signedPayload, signatureValue, messageCounter, nb)
	if err != nil {
		return err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	return nil
}

}

func (b *Bits) Update(l *slog.Logger, i uint64) bool {
	// Fast path: i is the next expected counter. Split out so the function
	// stays small and avoids paying for the slow paths' slog argument-build
	// stack frame on every call. The bit read/test/write is inlined to
	// touch the backing word once.
	if i == b.current+1 {
		pos := i & b.lengthMask
		word := pos >> 6
		mask := uint64(1) << (pos & 63)
		w := b.bits[word]
		if i > b.length && w&mask == 0 {
			b.lostCounter.Inc(1)
		}
		b.bits[word] = w | mask
		b.current = i
		return true
	}
	return b.updateSlow(l, i)
}
