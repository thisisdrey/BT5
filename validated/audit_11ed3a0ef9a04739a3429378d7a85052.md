Based on my investigation, I found a strong analog in Gitaly's ObjectPoolService.

### Title
Cross-repository object pool poisoning via unauthenticated `LinkRepositoryToObjectPool` — any linkable repository can share/pollute a shared object pool without ownership verification - ([File: internal/gitaly/service/objectpool/link.go])

### Summary
The Sherlock finding describes a vault that has no check tying a "sell" action to the vault where the tokens were actually "minted," letting any user manipulate shared vault liquidity across unrelated vaults. The structural analog in Gitaly is `LinkRepositoryToObjectPool`, which links an arbitrary target repository to an arbitrary object pool with no verification that the pool actually originated from (or is otherwise authorized to be associated with) that repository.

### Finding Description
`LinkRepositoryToObjectPool` only validates that the `Repository` argument is a well-formed/existing repository via `s.locator.ValidateRepository` and that the pool exists via `poolForRequest`; it performs no check that the pool was created from, or is otherwise legitimately related to, the given repository: [1](#0-0) 

The underlying `Link` function then simply writes the pool's path into the repository's `objects/info/alternates` file after checking only that the file is unset or already points to the same pool, using a pure string/path comparison (`linkedToRepository`) — not any provenance or ownership check between the pool and the repository: [2](#0-1) [3](#0-2) 

Since object pools are shared, mutable resources (their objects are deduplicated/garbage-collected together, and `FetchIntoObjectPool` performs bulk fetch/repack/housekeeping across all linked members), any repository that can be linked to a given pool becomes able to affect the shared resource state seen by every other member of that pool — this mirrors the report's "sell tokens in any vault regardless of origin" pattern, where a shared resource lacks provenance tracking between the acting party and the resource instance: [4](#0-3) 

The proto-level documentation itself acknowledges this is an unverified, caller-trusted operation: `DeleteObjectPool` explicitly states "There are no safety checks in place, so if any repository is still using this object pool it will become corrupted," and pool membership lifecycle is entirely caller-managed: [5](#0-4) 

### Impact Explanation
Because Gitaly's `ObjectPoolService` RPCs assume the caller (Rails/GitLab) has already performed authorization to ensure the pool and repository are legitimately related (e.g., fork/parent), Gitaly itself performs no cross-check. If this assumption is violated — e.g., through a caller bug, an internal API misuse, or a scenario where a malicious/compromised actor can invoke Gitaly's internal RPCs directly — an attacker-controlled repository could be linked to an unrelated pool. This would let that repository's future repacks deduplicate against, and its `FetchIntoObjectPool`/housekeeping interact with, objects and references belonging to unrelated repositories, potentially causing pool bloat, dangling-reference explosion (a documented cost driver per `doc/object_pools.md`), or corrupting shared pool state that other legitimate members depend on — a soft DoS closely analogous to the reported vault-bricking-via-dust attack.

### Likelihood Explanation
Likelihood is low-to-moderate: Gitaly's `ObjectPoolService` RPCs are internal, gRPC-only endpoints that are expected to be invoked exclusively by trusted GitLab Rails application code after it performs the actual authorization/ownership checks (fork relationship, permissions, etc.). Gitaly does not enforce this itself, so the finding depends on the calling layer (Rails) never sending a `LinkRepositoryToObjectPool` request for an unrelated repository/pool pair. This is a defense-in-depth gap rather than a directly externally-triggerable bug from an ordinary Git push/fetch, since ordinary git protocol operations do not expose this RPC to end users directly.

### Recommendation
Add a provenance/ownership check in Gitaly's `Link` (and `CreateObjectPool`) path — e.g., verify that the object pool's recorded origin/upstream repository actually corresponds to the repository being linked (similar to the existing `ListPoolUpstreams`/pool-metadata mechanism used elsewhere in the codebase), and reject linking attempts where no such relationship can be established, rather than relying solely on the calling application layer for this guarantee.

### Proof of Concept
Not applicable — no runnable PoC was produced, as reachability from an ordinary Git push/fetch is not directly demonstrated; the RPC in question is an internal gRPC endpoint, and the report is provided as a defense-in-depth structural analog only.

```go
func (s *server) LinkRepositoryToObjectPool(ctx context.Context, req *gitalypb.LinkRepositoryToObjectPoolRequest) (*gitalypb.LinkRepositoryToObjectPoolResponse, error) {
	repository := req.GetRepository()
	if err := s.locator.ValidateRepository(ctx, repository); err != nil {
		return nil, structerr.NewInvalidArgument("%w", err)
	}

	pool, err := s.poolForRequest(ctx, req)
	if err != nil {
		return nil, err
	}

	repo := s.localRepoFactory.Build(repository)

	if err := pool.Link(ctx, repo); err != nil {
		return nil, structerr.NewInternal("%w", err)
	}

	return &gitalypb.LinkRepositoryToObjectPoolResponse{}, nil
}
```

```go
func Link(ctx context.Context, pool, repo *localrepo.Repo, txManager transaction.Manager) (returnedErr error) {

		return err
```

```go
// linkedToRepository tests if a repository is linked to an object pool
func linkedToRepository(ctx context.Context, pool, repo *localrepo.Repo) (bool, error) {
	poolPath, err := pool.Path(ctx)
	if err != nil {
		return false, fmt.Errorf("getting object pool path: %w", err)
	}

	repoPath, err := repo.Path(ctx)
	if err != nil {
		return false, fmt.Errorf("getting repo path: %w", err)
	}

	altInfo, err := stats.AlternatesInfoForRepository(repoPath)
	if err != nil {
		return false, fmt.Errorf("getting alternates info: %w", err)
	}

	if !altInfo.Exists || len(altInfo.ObjectDirectories) == 0 {
		return false, nil
	}

	relPath := altInfo.ObjectDirectories[0]
	expectedRelPath, err := getRelativeObjectPath(ctx, pool, repo)
	if err != nil {
		return false, err
	}

	if relPath == expectedRelPath {
		return true, nil
	}

	if filepath.Clean(relPath) != filepath.Join(poolPath, "objects") {
		return false, fmt.Errorf("unexpected alternates content: %q", relPath)
	}

	return false, nil
}
```

```markdown
## Dangling Objects

When fetching from pool members into the object pool, then any force-updated
references may cause objects in the pool to not be referenced anymore. For
normal repositories, it is perfectly fine to delete those references after a
certain time. In the context of object pools, any other member of the pool may
still use any of those unreferenced objects. Deleting them would thus
potentially cause corrupt repositories.

This issue is kind of unsolvable: there is no point in time where it's safe to
delete objects from the object pool, as we do not know which repositories may be
linked to it. And even if we knew, we cannot determine all references of all
repositories at once in a race-free manner. We thus must consider each object to
still be referenced somewhere.

As a safeguard to not lose any objects by accident, we thus create dangling
references in the object pool after the fetch in `FetchIntoObjectPool`. For each
dangling object, a reference `refs/dangling/$OID` is created which points into
the object. This assures that each object is still referenced.
```
