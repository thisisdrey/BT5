### Title
Contract self-destruct with frozen-balance inheritance transfers TRON_POWER stake to inheritor without transferring the corresponding votes - ([File: actuator/src/main/java/org/tron/core/vm/program/Program.java])

### Summary
The reported Truflation bug is that `migrateVestingLock` moves a stake/lock to a new user without delegating votes to that user, leaving the receiver without voting power. The analogous java-tron mechanism is the `SUICIDE`/self-destruct opcode flow, where a contract's TRON_POWER (and other frozen) balance is transferred to an "inheritor" address via `transferFrozenV2BalanceToInheritor`, but the votes cast using that TRON_POWER are cleared/withdrawn from the *original* owner rather than being transferred or re-delegated to the inheritor.

### Finding Description
When a contract self-destructs, `Program.transferFrozenV2BalanceToInheritor(ownerAddr, inheritorAddr, repo)` moves all of the owner's `FrozenV2` balances (BANDWIDTH, ENERGY, and TRON_POWER) to the inheritor account: [1](#0-0) 

Separately, `withdrawRewardAndCancelVote(owner, repo)` clears the owner's votes and invalidates the owner's `oldTronPower`, but it never grants any corresponding voting power/delegation to the inheritor that just received the TRON_POWER stake: [2](#0-1) 

This mirrors the reported bug class exactly: stake/frozen-balance (the equivalent of the "vesting lock") is migrated from one account to another, but the vote/delegation state that should follow the stake is not migrated with it — the receiving account ends up holding TRON_POWER-backing balance without the votes/power that this balance is supposed to represent, while the original owner's votes are simply zeroed out rather than reassigned.

By contrast, in the normal freeze/vote actuators (`FreezeBalanceV2Actuator`, `UnfreezeBalanceV2Actuator`), vote accounting is carefully kept in sync with the TRON_POWER frozen balance change on the *same* account: [3](#0-2) 

But the inheritance path in `Program.java` has no equivalent logic to move votes to the inheritor, breaking the invariant that TRON_POWER balance and vote weight for that balance stay consistent for whichever account currently holds it.

### Impact Explanation
This is a bookkeping/vote-power inconsistency, not a fund-theft bug. It could allow a contract owner to intentionally self-destruct a contract holding TRON_POWER, transferring the underlying frozen TRX to an inheritor address, while the previous witness votes recorded on-chain against the destroyed contract's address are simply wiped instead of being reassigned — meaning voting weight is effectively lost from the system state (the inheritor doesn't get it, and it's not recoverable by the original owner). This affects witness election vote counting/state integrity, which is a core consensus-adjacent function reachable by any account deploying and self-destructing a TVM contract.

### Likelihood Explanation
Reachable by any unprivileged account: deploy a contract, freeze balance for TRON_POWER via that contract (`FreezeBalanceV2Contract` with `TRON_POWER` resource, possible since `supportAllowNewResourceModel`), cast votes, then trigger `SUICIDE`/self-destruct specifying an inheritor address. This is a straightforward, permissionless sequence of transactions requiring no special privileges.

### Recommendation
When migrating FrozenV2 TRON_POWER balance to the inheritor in `transferFrozenV2BalanceToInheritor` (or in the broader suicide flow), either (a) transfer/re-delegate the owner's existing votes to the inheritor proportionally to the migrated TRON_POWER balance, mirroring the vote-rebalancing logic already implemented in `UnfreezeBalanceV2Actuator.updateVote`/`UnfreezeBalanceV2Processor.updateVote`, or (b) explicitly document/enforce that votes must be withdrawn before self-destruct and reject self-destruct while votes are outstanding, consistent with how other pre-migration invariants (e.g., unDelegateResourceWithException checks) are enforced elsewhere in the codebase.

### Proof of Concept
1. Deploy a contract `C`.
2. From `C`, call `freezeBalanceV2(amount, TRON_POWER)` to freeze TRX for `TRON_POWER`.
3. Cast a witness vote using `C`'s address, consuming the TRON_POWER as vote weight (as exercised in `FreezeV2Test.testUnfreezeVotes`, which manually sets votes on the frozen account) [4](#0-3) .
4. Trigger `SUICIDE` from `C` with an inheritor address `I` that is not `C`.
5. Observe: `I` now holds the migrated `TRON_POWER` FrozenV2 balance (`transferFrozenV2BalanceToInheritor`), but `C`'s votes are cleared via `withdrawRewardAndCancelVote` and `I` receives no corresponding vote/delegation — the migrated stake's voting power is lost rather than transferred, matching the "receiver doesn't have voting power" impact from the original report.

  private long transferFrozenV2BalanceToInheritor(byte[] ownerAddr, byte[] inheritorAddr, Repository repo) {
    AccountCapsule ownerCapsule = repo.getAccount(ownerAddr);
    AccountCapsule inheritorCapsule = repo.getAccount(inheritorAddr);
    long now = repo.getHeadSlot();

    // transfer frozen resource
    ownerCapsule.getFrozenV2List().stream()
        .filter(freezeV2 -> freezeV2.getAmount() > 0)
        .forEach(
            freezeV2 -> {
              switch (freezeV2.getType()) {
                case BANDWIDTH:
                  inheritorCapsule.addFrozenBalanceForBandwidthV2(freezeV2.getAmount());
                  break;
                case ENERGY:
                  inheritorCapsule.addFrozenBalanceForEnergyV2(freezeV2.getAmount());
                  break;
                case TRON_POWER:
                  inheritorCapsule.addFrozenForTronPowerV2(freezeV2.getAmount());
                  break;
              }
            });

  private void updateVote(AccountCapsule accountCapsule,
                          final UnfreezeBalanceV2Contract unfreezeBalanceV2Contract,
                          byte[] ownerAddress) {
    DynamicPropertiesStore dynamicStore = chainBaseManager.getDynamicPropertiesStore();
    VotesStore votesStore = chainBaseManager.getVotesStore();

    if (accountCapsule.getVotesList().isEmpty()) {
      return;
    }
    if (dynamicStore.supportAllowNewResourceModel()) {
      if (accountCapsule.oldTronPowerIsInvalid()) {
        switch (unfreezeBalanceV2Contract.getResource()) {
          case BANDWIDTH:
          case ENERGY:
            // there is no need to change votes
            return;
          default:
            break;
        }
      } else {
        // clear all votes at once when new resource model start
        VotesCapsule votesCapsule;
        if (!votesStore.has(ownerAddress)) {
          votesCapsule = new VotesCapsule(
              unfreezeBalanceV2Contract.getOwnerAddress(),
              accountCapsule.getVotesList()
          );
        } else {
          votesCapsule = votesStore.get(ownerAddress);
        }
        accountCapsule.clearVotes();
        votesCapsule.clearNewVotes();
        votesStore.put(ownerAddress, votesCapsule);
        return;
      }
