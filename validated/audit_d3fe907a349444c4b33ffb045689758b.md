Audit Report

## Title
Reward-asset funds accrued while `total_tokens_staked == 0` are permanently unclaimable and stranded in the pool account - (File: `substrate/frame/asset-rewards/src/lib.rs`)

## Summary
`reward_per_token()` short-circuits and returns the unchanged `reward_per_token_stored` whenever `pool_info.total_tokens_staked.is_zero()`, but `update_pool_rewards()` unconditionally advances `last_update_block` to the current block on every call, including the very call that brings the pool from zero stake to non-zero stake. This silently discards the reward budget that would have accrued for the zero-stake interval, and that budget is never credited to any staker's `PoolStakerInfo`, yet the corresponding reward-asset balance is already sitting in the pool's dedicated account (fundable by anyone via the permissionless `deposit_reward_tokens` call). The funds become permanently stranded for as long as the pool has any staker at all, since the only recovery path, `cleanup_pool`, requires `PoolStakers` to be completely empty.

## Finding Description
The reward accounting flow is:
1. `stake()`/`unstake()`/`harvest_rewards()` all call `update_pool_and_staker_rewards`, which calls `reward_per_token(&pool_info)` using the pre-mutation `pool_info` (i.e., before the current call's stake/unstake delta is applied) [4](#0-3) .
2. `reward_per_token` returns the stored value unchanged when `total_tokens_staked == 0` [5](#0-4) .
3. However, `update_pool_rewards` (called right after, using the result of `reward_per_token`) unconditionally sets `new_pool_info.last_update_block = T::BlockNumberProvider::current_block_number()` [6](#0-5) .
4. Because `last_update_block` is advanced regardless of whether `total_tokens_staked` was zero, the elapsed "silent" blocks are never revisited — the next time `reward_per_token` is computed, `rewardable_blocks_elapsed` is calculated from the new `last_update_block`, permanently skipping the zero-stake window's `reward_rate_per_block` allotment [7](#0-6) .

The reward asset is transferred into the pool's dedicated account via the fully permissionless `deposit_reward_tokens` extrinsic, unrelated to whether the pool has any stakers. Once a staker exists, `cleanup_pool` cannot be invoked because it strictly requires `PoolStakers::<T>::iter_key_prefix(pool_id).next().is_none()` [8](#0-7) , leaving the stranded reward budget permanently locked.

## Impact Explanation
This is a permanent, protocol-level fund lock affecting the reward-asset balance intended for stakers: value is neither returned to depositors of `deposit_reward_tokens` nor claimable by any staker nor recoverable by the admin while any staker remains bonded, matching the "permanent user-fund lock" impact category. No malicious actor, privileged party, or off-repo assumption is required — normal chain operation triggers the loss automatically.

## Likelihood Explanation
High likelihood: pool creation (`create_pool`, which initializes `total_tokens_staked: 0` and `last_update_block: 0`) and the first `stake()` call are virtually always separate transactions/blocks, so every pool incurs at least one block of loss by default. `deposit_reward_tokens` is callable by any signed account irrespective of pool stake state, and any pool that transiently reaches zero total stake (all stakers unstake) reopens the same window.

## Recommendation
Only advance `last_update_block` when `total_tokens_staked` is non-zero (mirroring the corrected Synthetix pattern), or track the last-reward-eligible block separately from the general update timestamp, so the elapsed zero-stake interval's reward budget is not silently skipped once staking resumes. Consider also allowing admin recovery of provably orphaned reward-asset balance even while some stakers exist.

## Proof of Concept
1. `create_pool` initializes `total_tokens_staked: 0u32.into()`, `last_update_block: 0u32.into()` [9](#0-8) .
2. Any signed account calls `deposit_reward_tokens(pool_id, amount)` to fund the pool's reward account [10](#0-9) .
3. `N` blocks pass with no stakers.
4. The first staker calls `stake(pool_id, amount)`; `update_pool_and_staker_rewards` computes `reward_per_token` with `total_tokens_staked == 0` (unchanged), then `update_pool_rewards` sets `last_update_block = current_block`, silently consuming the `N` blocks' reward budget [11](#0-10) .
5. The `N * reward_rate_per_block` budget is unrecoverable via `cleanup_pool` once `PoolStakers` is non-empty.
