### Title
Exchange creator can instantly manipulate TRC10 AMM pool price via `ExchangeInjectContract`/`ExchangeWithdrawContract` to front-run/sandwich `ExchangeTransactionContract` trades - (File: actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java)

### Summary
The TRC10 bancor-style AMM exchange (`ExchangeCapsule`) lets its creator inject or withdraw liquidity at any time, which instantly changes the pool's `firstTokenBalance`/`secondTokenBalance` ratio (i.e., the trading price) with no timelock, no cooldown, and no per-block price-impact cap. This is the same "administrator can change system state immediately without warning" class of issue described in the report: a privileged actor (here, the exchange creator, not a witness/SR/committee) can front-run an ordinary trader's incoming `ExchangeTransactionContract` by injecting/withdrawing liquidity just before it executes, then reversing the position afterward — a classic sandwich attack — extracting value from unprivileged traders.

### Finding Description
`ExchangeInjectActuator.execute()`/`doValidate()` and `ExchangeWithdrawActuator.execute()`/`doValidate()` allow only the exchange's `creatorAddress` to change pool balances [1](#0-0) , but that check is the only gate — there is no time delay, no per-transaction/per-block maximum price-impact limit, and no cooldown between successive inject/withdraw calls by the creator [2](#0-1) [3](#0-2) .

Meanwhile, an ordinary trader submits an `ExchangeTransactionContract` specifying `quant` and a minimum `expected` output computed against the current on-chain balances [4](#0-3) . Because the pool balances can be changed atomically and immediately by the creator in a preceding transaction within the same or an adjacent block, the creator can:
1. Inject/withdraw to shift the price against the pending trader.
2. Let the trader's `ExchangeTransactionContract` execute at the now-worse price (still valid as long as `anotherTokenQuant >= tokenExpected`, which many callers set loosely).
3. Reverse the inject/withdraw afterward, capturing the price difference from the trader.

This is directly analogous to the report's example of `TBTCSystem.setSignerFeeDivisor`/`setLotSizes` taking effect immediately and letting an owner "interfere with other participants['] deposit creation attempts" or "craft a series of transactions that allow the owner to set parameters that are more beneficial to them" — except here the "owner" is the exchange creator and the "system parameter" is the AMM price.

### Impact Explanation
Any unprivileged account can create a TRC10 exchange pool via `ExchangeCreateContract` and become its "creator", then use `ExchangeInjectContract`/`ExchangeWithdrawContract` to grief or extract value from other unprivileged traders who submit `ExchangeTransactionContract` orders against that pool. This results in a direct, unauthorized transfer of economic value from the trader to the creator (a form of fund theft via price manipulation), reachable purely through normal signed transactions with no need for SR/committee/witness collusion.

### Likelihood Explanation
Likelihood is Medium: it requires the attacker to control (or be) the pool creator and to observe/predict incoming trades (e.g., via mempool monitoring or by being both the liquidity provider and counter-party), and the effectiveness depends on the victim's `expected` slippage bound being loose. This is a design gap rather than requiring any privileged network role, and is reachable by any user who creates or trades against a TRC10 exchange.

### Recommendation
Follow the same remediation direction the external report recommends: require price-impact caps per inject/withdraw call, and/or a mandatory time delay (or minimum number of blocks) between a creator's liquidity change and its effect on trade pricing, and/or restrict a single account from performing inject/withdraw and trade actions on the same pool within the same block. At minimum, emit/enforce a maximum allowed price deviation per `ExchangeInjectContract`/`ExchangeWithdrawContract` transaction so pool ratio cannot move arbitrarily in a single privileged action.

### Proof of Concept
1. Attacker calls `ExchangeCreateActuator` to create pool P(A, TRX) and becomes `creatorAddress`.
2. Victim broadcasts `ExchangeTransactionContract` to sell A for TRX with a loosely-set `expected`.
3. Attacker observes the pending transaction and broadcasts `ExchangeWithdrawContract` (or `ExchangeInjectContract`) with a higher energy fee/priority so it is included in the block just before the victim's transaction — see `ExchangeWithdrawActuator.execute()` [5](#0-4)  — shifting the pool ratio unfavorably for the victim.
4. Victim's `ExchangeTransactionActuator.execute()` completes at the manipulated ratio via `exchangeCapsule.transaction(...)` [6](#0-5) , since it still clears the loose `expected` check.
5. Attacker follows up with `ExchangeInjectContract` (or a second `ExchangeTransactionContract`) to restore/rebalance the pool and lock in the profit extracted from the victim's worse execution price.
