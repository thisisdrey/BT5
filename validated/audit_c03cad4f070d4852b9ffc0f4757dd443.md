## Title
Floating-point division-then-multiplication in `MortgageService#computeReward` causes vote-reward rounding losses reachable via `WithdrawBalanceContract` - (File: `chainbase/src/main/java/org/tron/core/service/MortgageService.java`)

### Summary
The pre-"new reward algorithm" voting-reward computation in `MortgageService.computeReward(long cycle, List<Pair<byte[], Long>> votes)` computes a voter's share of a standby-witness's cycle reward by first performing a floating-point division (`voteRate = userVote / totalVote`) and then multiplying the *already-rounded* double by `totalReward`, instead of performing the mathematically equivalent single integer operation `userVote * totalReward / totalVote`. This mirrors the reported `RioLRTAssetRegistry._normalizeDecimals` pattern: an intermediate division is performed where it is unnecessary, introducing avoidable floating-point rounding error before the final multiply/cast, so the withdrawer receives less than the exact entitled amount.

### Finding Description
`computeReward(long cycle, List<Pair<byte[], Long>> votes)`: [1](#0-0) 

```java
double voteRate = (double) userVote / totalVote;
reward += voteRate * totalReward;
```

`userVote`, `totalVote`, and `totalReward` are all integer (`long`) quantities. The correct, precision-preserving computation is `userVote * totalReward / totalVote` performed as one integer (or `BigInteger`) operation. Instead, the code divides first (`userVote / totalVote`), converting to a `double` with limited (53-bit) mantissa precision, and only afterward multiplies by `totalReward` and implicitly truncates when accumulated into the `long reward`. This is functionally the same class of bug as `_normalizeDecimals`: an unnecessary intermediate division causes information loss that a single fused multiply-divide would have avoided.

This method is invoked from `computeReward(long beginCycle, long endCycle, AccountCapsule accountCapsule)` for all cycles prior to `newRewardAlgorithmEffectiveCycle`: [2](#0-1) 

which is in turn reached from `withdrawReward(byte[] address)`: [3](#0-2) 

`withdrawReward` is called by `WithdrawBalanceActuator` on transaction execution — i.e., directly triggered by any unprivileged, signed `WithdrawBalanceContract` transaction that any TRON account can broadcast.

### Impact Explanation
Because the ratio is rounded during the division step rather than at the very end of a single integer computation, the resulting `reward` can be systematically smaller than the mathematically exact entitlement (`userVote * totalReward / totalVote`), for the same reason described in the source report: rounding twice (once implicitly via double precision loss in the division, once via the final `long` truncation/accumulation) loses more value than a single truncation would. This causes voters to receive a smaller amount of reward TRX than they are legitimately owed when withdrawing via `WithdrawBalanceContract` — a form of permanent underpayment/loss of funds for the affected account, repeated every reward withdrawal for cycles before the new reward algorithm became effective.

### Likelihood Explanation
This code path executes automatically and deterministically whenever any account broadcasts a `WithdrawBalanceContract` and has un-withdrawn rewards accrued in cycles predating `newRewardAlgorithmEffectiveCycle`. No special privileges or race conditions are required — it is a normal-usage financial computation.

### Recommendation
Replace the floating-point division-then-multiply with a single precision-preserving integer operation, matching the general pattern already used elsewhere in the same class for the "new reward algorithm" (`BigInteger` multiply-then-divide), e.g.:
```java
reward += BigInteger.valueOf(userVote)
    .multiply(BigInteger.valueOf(totalReward))
    .divide(BigInteger.valueOf(totalVote))
    .longValue();
```
This removes the unnecessary intermediate division and the associated double-precision rounding loss, analogous to removing `_normalizeDecimals`'s unnecessary `priceScale` divide/multiply round-trip in the original report.

### Proof of Concept
1. Set up a cycle where `totalVote = 3`, `userVote = 1`, `totalReward = 100`.
2. Exact expected share: `1 * 100 / 3 = 33` (integer division).
3. With the current code: `voteRate = (double) 1 / 3 = 0.3333333333333333`; `reward += voteRate * 100 = 33.33333333333333`, which when accumulated/truncated into the `long reward` field yields `33` in this specific example, but for values with more significant digits (e.g., `totalVote` and `totalReward` in the 10^9–10^15 range typical of TRX reward pools), the double-precision division loses low-order bits before multiplication, producing off-by-more-than-one results versus the exact `BigInteger` computation — verifiable by comparing `(long)((double)userVote/totalVote*totalReward)` against `BigInteger.valueOf(userVote).multiply(BigInteger.valueOf(totalReward)).divide(BigInteger.valueOf(totalVote)).longValue()` for large `userVote`/`totalVote`/`totalReward` triples; the two diverge, and the divergence is realized for real users through `WithdrawBalanceActuator.execute()` → `MortgageService.withdrawReward()` → `computeReward(cycle, votes)`.   private long computeReward(long cycle, List<Pair<byte[], Long>> votes) {
    long reward = 0;
    for (Pair<byte[], Long> vote : votes) {
      byte[] srAddress = vote.getKey();
      long totalReward = delegationStore.getReward(cycle, srAddress);
      if (totalReward <= 0) {
        continue;
      }
      long totalVote = delegationStore.getWitnessVote(cycle, srAddress);
      if (totalVote == DelegationStore.REMARK || totalVote == 0) {
        continue;
      }
      long userVote = vote.getValue();
      double voteRate = (double) userVote / totalVote;
      reward += voteRate * totalReward;
    }
    return reward;
  }
