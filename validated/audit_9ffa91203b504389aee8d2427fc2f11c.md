### Title
Heap buffer over-read in `InputZipFile::ProcessCentralDirEntry` while parsing untrusted ZIP central directory entries - (File: third_party/ijar/zip.cc)

### Summary
`InputZipFile::ProcessCentralDirEntry` reads fixed-size and variable-length fields (compressed/uncompressed size, filename, extra fields, comment) directly from the memory-mapped input without any `EnsureRemaining`-style bounds check before advancing the cursor `p`, unlike its sibling `ProcessLocalFileEntry`, which does call `EnsureRemaining` before each variable-length read.

### Finding Description
`ProcessLocalFileEntry` guards every variable-length read with `EnsureRemaining()`, comparing the requested length against `input_file_->Length() - in_offset` before advancing the pointer [1](#0-0) . `ProcessCentralDirEntry`, however, only checks the entry signature and then unconditionally advances `p` by 16 bytes, reads 32-bit sizes, 16-bit filename/extra/comment lengths, external attributes, and offset, and finally walks the extra-field list based on `extra_field_length` and `data_size` values taken straight from the (attacker-controlled) file, with no equivalent `EnsureRemaining` calls anywhere in the function [2](#0-1) . This function is invoked in a loop by `CalculateOutputLength()` (and by `ProcessNext()`) that walks the central directory of the input zip until `ProcessCentralDirEntry` returns false [3](#0-2) . A crafted zip whose central directory entry declares an oversized `file_name_length`, `extra_field_length`, or `file_comment_length` (or a Zip64 extra field whose declared `data_size` exceeds what remains in the extra-field block) will cause `p`/`extra_p` to be advanced, and `memcpy`/`get_u2le`/`get_u4le`/`get_u8le` to read, past the end of the mmapped input file — a heap/mmap-region buffer over-read analogous to the GPAC `gf_m2ts_process_pmt` bug, where fields parsed from an untrusted MPEG-TS PMT table are trusted without a length check against the buffer bound.

### Impact Explanation
This is reached whenever `ijar`/`zipper`-family tooling (used by `singlejar`/`ijar` build actions such as processing `.jar`/`.srcjar` archives, including those fetched via `http_archive` or produced from untrusted sources) parses a zip file that a build consumes. An out-of-bounds read of adjacent heap/mapped memory can crash the tool (denial of service) and, depending on what memory follows the mapping, could leak adjacent process memory contents into copied `filename` buffers or comparisons, which is a confidentiality-relevant over-read rather than a benign parse failure.

### Likelihood Explanation
Likelihood is limited by the fact that ijar operates on a memory-mapped file; on most platforms a read slightly past the mapped region will either land within the same page (returning stale/adjacent heap data — an over-read with no crash) or fault at a page boundary (crash). Triggering it requires only supplying a specially crafted zip/jar file as input to the ijar toolchain component, which is plausible when consuming untrusted `http_archive`/build artifacts that get processed by `ijar` in the build graph. No cryptographic bypass is needed since this is a pure parsing bug, not an integrity check.

### Recommendation
Add `EnsureRemaining`-equivalent bounds checks in `ProcessCentralDirEntry` before every fixed-field skip (`p += 16`, `p += 4`) and before advancing by `file_name_length`, `extra_field_length`, and `file_comment_length`, mirroring the checks already present in `ProcessLocalFileEntry`. Additionally validate that each extra-field's `data_size` does not exceed the bytes remaining within the extra-field block (`extra_p + data_size <= p`) before dereferencing `extra` in the Zip64 branch.

### Proof of Concept
A JUnit/gtest-style reproduction (extending the existing `third_party/ijar/*_test.cc` infrastructure) would: build a minimal zip buffer containing a valid EOCD pointing to a single central directory header, set that header's `file_name_length` (or `extra_field_length`/`file_comment_length`) to a value larger than the remaining bytes in the buffer, feed it to `InputZipFile::Open`/`ProcessCentralDirEntry` (via the public `ZipExtractor` interface used by `ijar.cc`), and run under ASan to observe a heap-buffer-overflow (read) report inside `ProcessCentralDirEntry`. I could not directly confirm the presence or absence of an existing regression test for this exact code path within the indexed content, since the index surfaced only the `zip_headers_test.cc`/`output_jar_simple_test.cc` tests for the `singlejar` header classes, not for `third_party/ijar/zip.cc`'s `ProcessCentralDirEntry`; a Devin session with full repository access would be needed to confirm test coverage and validate a concrete crash/ASan reproduction.

bool InputZipFile::ProcessCentralDirEntry(const u1 *&p, u8 *compressed_size,
                                          u8 *uncompressed_size, char *filename,
                                          size_t filename_size, u4 *attr,
                                          u8 *offset) {
  u4 signature = get_u4le(p);

  if (signature != CENTRAL_FILE_HEADER_SIGNATURE) {
    if (signature != DIGITAL_SIGNATURE && signature != EOCD_SIGNATURE &&
        signature != ZIP64_EOCD_SIGNATURE) {
      error("invalid central file header signature: 0x%x\n", signature);
    }
    return false;
  }

  p += 16;  // skip to 'compressed size' field
  *compressed_size = get_u4le(p);
  *uncompressed_size = get_u4le(p);
  u2 file_name_length = get_u2le(p);
  u2 extra_field_length = get_u2le(p);
  u2 file_comment_length = get_u2le(p);
  p += 4;  // skip to external file attributes field
  *attr = get_u4le(p);
  *offset = get_u4le(p);
  {
    size_t len = (file_name_length < filename_size)
      ? file_name_length
      : (filename_size - 1);
    memcpy(reinterpret_cast<void*>(filename), p, len);
    filename[len] = 0;
  }
  p += file_name_length;
  const u1 *extra_p = p;
  p += extra_field_length;
  while (extra_p != p) {
    const u2 header_id = get_u2le(extra_p);
    const u2 data_size = get_u2le(extra_p);
    const u1 *extra = extra_p;
    extra_p += data_size;
    if (header_id == ZIP64_EXTRA_FIELD_TAG) {
      if (*uncompressed_size == U4_MAX) {
        *uncompressed_size = get_u8le(extra);
      }
      if (*compressed_size == U4_MAX) {
        *compressed_size = get_u8le(extra);
      }
      if (*offset == U4_MAX) {
        *offset = get_u8le(extra);
      }
    }
  }
  p += file_comment_length;
  return true;
}
