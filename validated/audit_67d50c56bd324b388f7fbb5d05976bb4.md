### Title
Unprivileged dust transfers permanently occupy `depositTokensOfAccount` slots, blocking victims from adding new positions until manually cleared - (File: contracts/Pool.sol)

### Summary
`Pool.addToDepositTokensOfAccount` enforces `MAX_TOKENS_PER_USER` as a combined cap on a user's deposit + debt token lists, but slots are granted to any recipient the first time they receive a deposit token, with no minimum-amount check and no opt-in. An unprivileged attacker can fill a victim's list by transferring dust (1 wei) of every whitelisted `DepositToken` to the victim's address, causing `UserReachedMaxTokens` reverts on any subsequent new deposit or borrow position.

### Finding Description
On every `DepositToken._transfer`, the pool appends the token to the recipient's enumerable set the first time their balance is nonzero:

- `DepositToken._transfer` calls `pool.addToDepositTokensOfAccount(recipient_)` when `_recipientBalanceBefore == 0 && amount_ > 0` — `contracts/DepositToken.sol:518-520`.
- The same happens on `_mint` — `contracts/DepositToken.sol:486-488`.
- `Pool.addToDepositTokensOfAccount` is gated by `onlyIfAdditionWillNotReachMaxTokens`, which reverts with `UserReachedMaxTokens` once `debtTokensOfAccount.length + depositTokensOfAccount.length >= MAX_TOKENS_PER_USER` — `contracts/Pool.sol:143-148` and `contracts/Pool.sol:216-220`.
- `DebtToken` mint/burn (`issue`, `mint`, `flashIssue`) perform the same accounting through `addToDebtTokensOfAccount`, which shares the same combined counter — `contracts/Pool.sol:204-208`. Debt tokens are non-transferable, so the victim has no way to receive debt-token slots without debt, but debt issuance itself reverts once the cap is hit.

Attack path (all public, unprivileged):

1. Attacker deposits a small amount of each whitelisted collateral via `DepositToken.deposit` (or obtains the tokens on the market).
2. For each deposit token `i`, attacker calls `depositToken_i.transfer(victim, 1)`. Each transfer lands a new entry in `depositTokensOfAccount[victim]` regardless of amount.
3. Repeat until the combined list reaches `MAX_TOKENS_PER_USER`.
4. Any subsequent call that would add a *new* deposit or debt token for the victim reverts with `UserReachedMaxTokens`: `deposit` into a collateral type the victim has never held, `DebtToken.issue`/`mint`/`flashIssue` for a synth the victim hasn't borrowed, and `SmartFarmingManager.leverage` flows that mint new positions.

### Impact Explanation
Temporary freezing of funds / position-griefing: the victim is blocked from opening any *new* collateral type or debt position. Transfers of the dust tokens are unrestricted (`_revertIfLocked` only limits amounts above the unlocked balance), so the victim's existing balances and withdrawals are not locked — but anyone mid-flow is affected. Notably, `Operator.execute` batches can be front-run: a victim's multicall depositing a new collateral can be front-run with a dust transfer that pushes them over the cap, reverting the whole batch. The griefer only spends dust amounts of each deposit token plus gas; on cheap L2s (Base, Optimism, Swell, Plasma, Hemi — all deployed) this costs cents per victim. Recovery requires the victim to transfer out the full dust balance of each spammed token to trigger `removeFromDepositTokensOfAccount`, which costs the victim gas proportional to the number of slots and can be re-griefed continuously by the attacker depositing fresh dust — i.e., persistent liveness degradation of new-position creation rather than a one-time freeze.

### Likelihood Explanation
Medium. No privileged role is needed: `DepositToken.transfer` is a public ERC20 entry point, and `addToDepositTokensOfAccount` is permissionlessly reachable through it (`onlyIfDepositTokenExists` only restricts the *caller* to be a registered token, which the deposit token itself satisfies). The attacker only needs dust of each whitelisted deposit token, obtainable by depositing minimal collateral themselves. The main mitigants are (a) it only blocks *new* token types — topping up an already-held collateral still works; (b) the victim can self-heal by fully transferring out each spammed token, though this races with further dust. The cap makes this a griefing/DoS-class issue rather than theft; severity is bounded but the attack is fully permissionless and repeatable across all deployed chains.

### Recommendation
Add a minimum-amount threshold before registering a token in an account's set (e.g., require `amount_ >= DUST_THRESHOLD` or a `MIN_POSITION_VALUE_USD` quoted via `MasterOracle` in `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount`), or decouple the per-account cap: count debt and deposit lists separately and only enforce the cap for tokens that actually back debt (`debtPositionOf`/`unlockedBalanceOf` loops), so spam deposit tokens cannot block debt issuance. Alternatively, allow `removeFromDepositTokensOfAccount` to be initiated by the account owner for zero-value positions.

### Proof of Concept
Hardhat sketch (pool with ≥2 whitelisted deposit tokens `msdA`, `msdB`, ... up to `MAX_TOKENS_PER_USER`):

```typescript
// attacker deposits dust into every whitelisted deposit token
for (const dt of allDepositTokens) {
  await underlying(dt).approve(dt.address, 1);
  await dt.deposit(1, attacker.address);          // mint 1 wei msdToken to attacker
  await dt.transfer(victim.address, 1);           // victim list += 1 entry
}
// victim now has depositTokensOfAccount.length == MAX_TOKENS_PER_USER

// victim tries to deposit a NEW collateral type -> reverts
await expect(
  newDepositToken.connect(victim).deposit(amount, victim.address)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');

// victim tries to borrow a NEW synth -> reverts in DebtToken.issue
await expect(
  newDebtToken.connect(victim).issue(1, victim.address) // via pool-authorized path
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');
```

The revert path: `deposit → _mint → balanceBefore == 0 → pool.addToDepositTokensOfAccount → onlyIfAdditionWillNotReachMaxTokens` reverts because `debtTokensOfAccount.length(victim) + depositTokensOfAccount.length(victim) == MAX_TOKENS_PER_USER` (`contracts/Pool.sol:143-146`).
