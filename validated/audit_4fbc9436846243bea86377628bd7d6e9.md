### Title
`AttachmentsBatchStateContext::extend_with_attachments` accepts and stores attacker-served attachment content without verifying it matches the requested `content_hash` - ([File: stackslib/src/net/atlas/download.rs])

### Summary
`AttachmentRequest` carries the demanded `content_hash: Hash160` [1](#0-0)  but `extend_with_attachments`, which processes the peer's `GetAttachmentResponse`, never checks `response.attachment.hash() == request.content_hash` before treating the request as successful and inserting the attachment into `self.attachments` [2](#0-1) . A malicious peer that is a legitimate inventory source for `content_hash = H` can return arbitrary bytes whose `Attachment::hash()` (`Hash160::from_data`) equals some `H' != H` [3](#0-2) , and the code accepts it as a "successful" download, bumping that peer's reliability score.

### Finding Description
The invariant that should hold is: for `AttachmentRequest{content_hash: H, ...}`, the resolved `Attachment` must satisfy `attachment.hash() == H`. Tracing the code:

1. `AttachmentsBatchStateContext::get_prioritized_attachments_requests` builds an `AttachmentRequest` keyed by the on-chain-committed `content_hash` [4](#0-3) .
2. The request is sent via `AttachmentRequest::make_request_type`, hitting `GET /v2/attachments/{content_hash}` on the chosen peer [5](#0-4) .
3. When the response comes back, `extend_with_attachments` only checks that the JSON decodes successfully via `decode_atlas_get_attachment` — it never compares `response.attachment.hash()` to `request.content_hash`; on success it inserts the attachment into a hash-set (`self.attachments: HashSet<Attachment>`, decoupled from the originating request) and bumps the peer's `successful_requests` reliability counter [6](#0-5) .
4. Later, in `AttachmentsDownloader::run`, resolution is driven by the *attachment's own* hash, not the request's hash: `network.atlasdb.find_all_attachment_instances(&attachment.hash())` and `context.attachments_batch.resolve_attachment(&attachment.hash())` [7](#0-6) . `resolve_attachment` only removes entries whose tracked `content_hash` equals the passed hash [8](#0-7) .

Because forged content hashes to `H'`, `resolve_attachment(&H')` will not match the real pending instance for `H` (baring a Hash160 collision). The pending `AttachmentInstance` for `H` is never resolved by this exchange, yet the round is recorded as a peer success (not a failure), so:
- The malicious peer's `ReliabilityReport` score increases (`bump_successful_requests`), making it *more* likely to be chosen as a preferred source in future rounds (test `test_downloader_context_attachment_requests` shows higher-reliability peers are picked first) [9](#0-8) .
- The batch is not marked fully succeeded, so it's bumped and re-queued until `max_attachment_retry_count` is exceeded, after which it is permanently dropped [10](#0-9) .

No code path anywhere in `extend_with_attachments`, `AttachmentsBatchStateMachine::try_proceed`, or the `run` resolution logic checks `attachment.hash() == request.content_hash`. Note that the atlas DB itself stays internally consistent (attachments are always looked up/stored keyed by their own computed hash, e.g. `insert_uninstantiated_attachment` uses `attachment.hash()` as the key) [11](#0-10) , so the RPC endpoint `find_attachment` cannot be tricked into serving wrong bytes for an existing hash key — the flaw is specifically in the requester-side acceptance/accounting logic, not in data-integrity of the local store.

### Impact Explanation
This is a High-severity issue matching "attachment/BNS mismatch" and inventory-poisoning categories, but the mechanism is narrower than full content forgery being served under the correct hash: the attacker cannot make the node serve `H`'s content as something else (DB integrity holds), but the attacker can:
- Repeatedly force a bounded number of futile retries and reliability-score inflation for itself with a single malicious response per round, causing the pending on-chain-committed attachment instance for `H` to remain permanently unresolved (marked unavailable) once `max_attachment_retry_count` is exceeded — legitimate BNS zonefile data becomes unreachable/unresolved on the victim node despite being genuinely committed and available from honest peers, if the malicious peer keeps winning selection due to inflated reliability.
- This is a repeatable griefing vector against any node's Atlas downloader as long as the attacker's peer URL remains in the victim's outbound-peer/data-URL set and its inventory claims to have `H`.

### Likelihood Explanation
Preconditions: attacker only needs to run a normal P2P peer that the victim has as an outbound sync peer with a resolvable data URL, and needs to claim (via `GetAttachmentsInvResponse`) that it has the target attachment in its inventory — both are within the unprivileged remote-peer threat model (no secret/admin role required). Cost per exploit round is a single crafted HTTP response with mismatching content; it's fully repeatable across retry cycles.

### Recommendation
In `AttachmentsBatchStateContext::extend_with_attachments`, verify `response.attachment.hash() == request.content_hash` before accepting the download as successful; on mismatch, treat it as a failed request (`report.bump_failed_requests()`) and do not insert the attachment into `self.attachments`. Optionally, also flag/deregister peers that repeatedly serve hash-mismatched content instead of rewarding them with a higher reliability score.

### Proof of Concept
Rust test plan in `stackslib::net::atlas::tests`:
1. Build an `AttachmentsBatchStateContext` with one `AttachmentRequest{ content_hash: H, ... }` (using `new_attachment_instance_from` helpers already in `tests.rs`).
2. Construct a `BatchedRequestsResult` where `succeeded` maps that request to a `StacksHttpResponse` decoding to `GetAttachmentResponse{ attachment: Attachment{ content: b"wrong-bytes".to_vec() } }` whose `Attachment::hash()` == `H' != H`.
3. Call `context.extend_with_attachments(&mut results)` and assert:
   - `context.attachments` contains the forged attachment (demonstrating no hash check).
   - The peer's `ReliabilityReport` in `context.peers` was bumped via `bump_successful_requests` rather than `bump_failed_requests`.
4. Run the `AttachmentsBatchStateMachine::Done` branch logic (as in `AttachmentsDownloader::run`) and assert `context.attachments_batch.resolve_attachment(&H)` is never effectively triggered for `H` (the instance for `H` remains in `attachments_instances`), confirming the batch is retried/eventually dropped without ever resolving the genuinely committed hash `H`.

    pub fn get_prioritized_attachments_requests(&self) -> BinaryHeap<AttachmentRequest> {
        let mut queue = BinaryHeap::new();
        let mut enqueued = HashSet::new();
        for ((contract_id, pages, _), peers_responses) in self.inventories.iter() {
            let missing_attachments = match self
                .attachments_batch
                .attachments_instances
                .get(contract_id)
            {
                None => continue,
                Some(missing_attachments) => missing_attachments,
            };
            // Note: we're getting missing_attachments (attachment_id: content_hash)
            for (attachment_index, content_hash) in missing_attachments.iter() {
                let page_index = attachment_index / AttachmentInstance::ATTACHMENTS_INV_PAGE_SIZE;
                // Since there's a limit in the number of pages that a node can request,
                // we can potentially have multiple inventory request at once.
                if !pages.contains(&page_index) {
                    continue;
                }

                if enqueued.contains(content_hash) {
                    debug!("Atlas: {} already enqueued", content_hash);
                    continue;
                }

                let mut sources = HashMap::new();
                let position_in_page =
                    attachment_index % AttachmentInstance::ATTACHMENTS_INV_PAGE_SIZE;

                for (peer_url, response) in peers_responses.iter() {
                    // Considering the response, look for the page with the index
                    // we're looking for.
                    let search_page = response.pages.iter().find(|page| page.index == page_index);

                    let has_attachment = search_page
                        .and_then(|search_page| {
                            search_page.inventory.get(position_in_page as usize)
                        })
                        .map(|result| *result == 1)
                        .unwrap_or(false);

                    if !has_attachment {
                        debug!(
                            "Atlas: peer does not have attachment ({}, {}) in its inventory {:?}",
                            page_index, position_in_page, response.pages
                        );
                        continue;
                    }

                    let report = self
                        .peers
                        .get(peer_url)
                        .expect("Atlas: unable to retrieve reliability report for peer");
                    sources.insert(peer_url.clone(), report.clone());
                }

                if sources.is_empty() {
                    warn!("Atlas: could not find a peer including attachment in its inventory");
                    continue;
                }

                // Success, we found at least one inventory including the attachment we're looking for.
                let request = AttachmentRequest {
                    sources,
                    content_hash: content_hash.clone(),
                    stacks_block_height: self.attachments_batch.stacks_block_height,
                    canonical_stacks_tip_height: self.attachments_batch.canonical_stacks_tip_height,
                };
                enqueued.insert(content_hash);
                queue.push(request);

    pub fn extend_with_attachments(
        mut self,
        results: &mut BatchedRequestsResult<AttachmentRequest>,
    ) -> AttachmentsBatchStateContext {
        for (request, response) in results.succeeded.drain() {
            let report = self
                .peers
                .get_mut(request.get_url())
                .expect("Atlas: unable to retrieve reliability report for peer");

            let response = if let Some(r) = response {
                r
            } else {
                report.bump_failed_requests();
                continue;
            };

            if let Ok(response) = response.decode_atlas_get_attachment() {
                self.attachments.insert(response.attachment);
                report.bump_successful_requests();
            } else {
                report.bump_failed_requests();
            }
        }
        let mut events_ids = results.faulty_peers.keys().copied().collect::<Vec<usize>>();
        self.events_to_deregister.append(&mut events_ids);

        self
    }

    pub fn resolve_attachment(&mut self, content_hash: &Hash160) {
        for missing_attachments in self.attachments_instances.values_mut() {
            let mut keys = vec![];
            for (k, hash) in missing_attachments.iter() {
                if hash == content_hash {
                    keys.push(*k);
                }
            }
            for key in keys {
                missing_attachments.remove(&key);
            }
        }
    }

    pub fn insert_uninstantiated_attachment(
        &mut self,
        attachment: &Attachment,
    ) -> Result<(), db_error> {
        // Insert the new attachment
        let uninstantiated_attachments = self.count_uninstantiated_attachments()?;
        if uninstantiated_attachments >= self.atlas_config.max_uninstantiated_attachments {
            let to_delete =
                1 + uninstantiated_attachments - self.atlas_config.max_uninstantiated_attachments;
            self.evict_k_oldest_uninstantiated_attachments(to_delete)?;
        }

        let tx = self.tx_begin()?;
        let now = util::get_epoch_time_secs() as i64;
        let res = tx.execute(
            "INSERT OR REPLACE INTO attachments (hash, content, was_instantiated, created_at) VALUES (?, ?, 0, ?)",
            params![
                attachment.hash(),
                attachment.content,
                now,
            ],
        );
        res.map_err(db_error::SqliteError)?;
        tx.commit().map_err(db_error::SqliteError)?;
        Ok(())
    }
