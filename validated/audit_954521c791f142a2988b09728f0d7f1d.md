### Title
Manifest pointer is advanced to an attacker-influenced hash without verifying the content-addressing invariant - ([File: internal/git/mvcc/cache.go])

### Summary
The ZK advisory concerns a value (`cumulative_sum`) that is used as trust input to a security-critical decision (sampling the Fiat-Shamir challenge `zeta`) without first being bound/verified against what was actually computed. The structural analog here is Gitaly's experimental MVCC reference backend: `LocalCache.Commit` reads a `newHash` string produced by the Git process and immediately uses it as the new canonical manifest pointer via a compare-and-swap, without ever verifying that `newHash` is the actual SHA-256 digest of the manifest body it names.

### Finding Description
`LocalCache.Commit` reads the "new" manifest hash from the temp `GIT_MVCC_MANIFEST_PATH` file that Git wrote during the mutator RPC: [1](#0-0) 

This `newHash` is then used both to locate the manifest file to upload (`putNewArtifacts`) and, critically, as the `newHash` parameter passed straight into `ObjectStorage.Commit`, which performs a compare-and-swap of the manifest pointer file: [2](#0-1) 

Nowhere in this path is the manifest's self-naming invariant enforced in production code — i.e., that the hex string used as the manifest's filename/pointer value actually equals `sha256(manifest body)`. This invariant is documented and asserted only in test helpers (`assertManifestSelfNamed`), never during `Commit`: [3](#0-2) 

`ParseManifest` does validate an internal trailing checksum against the manifest body it parses, but this only proves internal self-consistency of a file's *content* — it never compares that checksum to the *hash value being used as the pointer/filename* (`newHash`): [4](#0-3) 

The design docs for this MVCC RPC flow independently note that this section is unfinished, POC-quality code: [5](#0-4) 

Because `Commit` trusts the `newHash` string read from disk as the pointer value without validating it against the actual manifest content hash, and `LocalStorage.Commit` performs no independent validation either (it only compares `current != baseHash`, not that `newHash` is well-formed/content-addressed), the "observation" that should bind the pointer to the content it names is missing — mirroring the missing cumulative-sum observation in the ZK bug: a value is trusted and committed to storage without incorporating a check that would prevent it from diverging from the real underlying state.

### Impact Explanation
If the reference-backend Git binary (or any component populating `GIT_MVCC_MANIFEST_PATH`) can be made to write a `newHash` value that does not match the content it is supposed to name — whether through a bug in that unreviewed/experimental Git fork, a race, or a corrupted/truncated write — Gitaly will atomically publish that value as the canonical manifest pointer for the repository. Since this pointer is later read back by all read-only RPCs and other mutators as the authoritative repository state (`ReadManifestPointer` → `prepareManifestFile`), an unverified pointer value can cause the repository to permanently reference a manifest that doesn't exist, is stale, or (depending on how the pointer's hash is used for artifact addressing elsewhere in the storage backend) collides with unrelated content. This is a data-integrity/availability issue (repository could become permanently unreadable via `ErrManifestPointerConflict`-free but incorrect state) rather than a straightforward cross-tenant object access, because `repositoryID`-scoped paths still confine the blast radius to the single repository.

### Likelihood Explanation
This code path is explicitly labeled POC/experimental (per `doc/mvcc_rpc_flow.md`), gated behind the MVCC reference backend feature flag (`ReferenceBackendMVCC`), and requires that backend to be enabled. It is reachable from an ordinary user's mutating RPC (e.g. a push) once MVCC is active, since `Commit` runs unconditionally at the end of every mutator RPC using that backend. However, exploiting the missing check requires the underlying Git binary/backend to actually produce a mismatched hash, which is not something an ordinary Gitaly-level attacker can directly control through gRPC input alone — the vulnerability is a missing defense-in-depth verification rather than a proven, directly triggerable exploit from crafted RPC fields.

### Recommendation
In `LocalCache.Commit` (or in `ObjectStorage.Commit` implementations), before advancing the pointer, re-parse the manifest at `manifests/<newHash>` and verify that `sha256(body without trailer) == newHash`, rejecting the commit (and not advancing the pointer) if they disagree — analogous to observing the full committed value before trusting it. This closes the same class of gap as SP1's fix: don't let unverified values participate in a subsequent trust decision (challenge sampling there; canonical-pointer CAS here).

### Proof of Concept
Not independently reproducible from the available code/tests: the mismatch would need to originate from the unreviewed MVCC-enabled Git fork writing an incorrect hash into `GIT_MVCC_MANIFEST_PATH`, which is outside the scope of what can be demonstrated purely via gRPC-level Gitaly inputs in this codebase. The finding is based on static code-path analysis showing the missing verification, not a confirmed working exploit.

```go
func (l *LocalStorage) Commit(ctx context.Context, repositoryID, baseHash string, newHash string) error {
	pointerPath := filepath.Join(l.storageRoot, repositoryID, mvccCacheDir, manifestPointer)

	lockedFile, err := safe.NewLockingFileWriter(pointerPath, safe.LockingFileWriterConfig{
		FileWriterConfig: safe.FileWriterConfig{
			FileMode: mode.File,
		},
	})
	if err != nil {
		return fmt.Errorf("creating file writer: %w", err)
	}
	defer func() {
		_ = lockedFile.Close()
	}()

	if _, err := io.Copy(lockedFile, strings.NewReader(newHash)); err != nil {
		return fmt.Errorf("copy to writer: %w", err)
	}
	if err := lockedFile.Lock(); err != nil {
		if errors.Is(err, safe.ErrFileAlreadyLocked) {
			return fmt.Errorf("manifest pointer locked: %w", ErrManifestPointerConflict)
		}
		return fmt.Errorf("lock manifest pointer: %w", err)
	}

	current, err := l.ReadManifestPointer(ctx, repositoryID)
	if err != nil {
		return fmt.Errorf("read current pointer: %w", err)
	}
	if current != baseHash {
		return fmt.Errorf("base manifest pointer changed: %w, base %q current %q",
			ErrManifestPointerConflict, baseHash, current)
	}
	if err := lockedFile.Commit(ctx); err != nil {
		return fmt.Errorf("commit writer: %w", err)
	}

	return nil
```

```go
// assertManifestSelfNamed checks the manifest spec's content-addressing
// invariant: the 32-byte trailer is the SHA-256 of everything preceding it, and
// its hex form is the body's filename under manifests/.
func assertManifestSelfNamed(t *testing.T, body []byte, wantName string) {
	t.Helper()
	payload := body[:len(body)-trailerSize]
	sum := sha256.Sum256(payload)
	require.Equal(t, body[len(body)-trailerSize:], sum[:])
	require.Equal(t, wantName, fmt.Sprintf("%x", sum))
}
```
