### Title
Unbounded array-length field in shielded-TRC20 precompile ABI decoding allows a single crafted contract call to trigger a multi-gigabyte allocation and crash the node - ([File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java])

### Summary
The PostgreSQL advisory describes a bug class where an attacker-controlled length field is used to size an allocation without adequate bounds checking, causing memory corruption/crash. `java-tron`'s TVM precompiled-contract ABI decoders for the shielded TRC20 verification functions (`VerifyMintProof`, `VerifyBurnProof`, `VerifyTransferProof`, etc.) read a "count" word directly from unauthenticated call data and use it to size a Java array before any correlation with the actual call-data length or energy/memory limit is enforced, via the shared helper `extractBytesArray`/`extractSigArray`/`extractBytes32Array`.

### Finding Description
`PrecompiledContracts.extractBytesArray` and its siblings take a `DataWord[] words` array (parsed from raw call data with `DataWord.parseArray`) and an `offset`, then do: [1](#0-0) 

The `len` value is `words[offset].intValueSafe()`, which is fully attacker-controlled (any unprivileged caller can supply arbitrary call data to a contract invoking these precompiled addresses). `intValueSafe()` clamps only overflow/negative cases to `Integer.MAX_VALUE`, it does not validate the value against the actual size of `words`/`data`: [2](#0-1) 

Because `len` can be set to `Integer.MAX_VALUE` (or any large value up to it) regardless of how small the actual call data is, the statement `byte[][] bytesArray = new byte[len][];` (and the analogous array allocations in `extractBytes32Array`/`extractSigArray`) attempts to allocate an array of up to ~2^31 object references (many GB of heap) before any subsequent bounds check on `data`/`words` length is performed. This mirrors the reported bug class: a length taken from untrusted input is used to size a memory allocation without first validating it against the real available data size, leading to a grossly oversized allocation request.

### Impact Explanation
A single transaction that calls a contract invoking one of the shielded-TRC20 precompiles (reachable by any unprivileged transaction broadcaster/contract deployer) can force the executing node to attempt an allocation on the order of gigabytes. This will throw `OutOfMemoryError` in the JVM, which — depending on how deep in the call stack it propagates and what state has already been mutated — can crash the node process or destabilize the JVM (GC thrashing/OOM kill), denying block production/service to that node without requiring any special privilege, matching the "node crash or halt" acceptance criterion.

### Likelihood Explanation
Likelihood is high for triggering the oversized allocation attempt: it requires only a single, unprivileged smart-contract call with crafted call data (no signature/authorization beyond a normal broadcast transaction), and no existing energy/memory-size gate (such as the `MEM_LIMIT` check used for VM memory expansion in `EnergyCost.checkMemorySize`) protects this specific array-sizing path, since it operates on Java heap object arrays outside the metered VM memory model.

### Recommendation
Before allocating `bytesArray`/`bytes32Array` in `extractBytesArray`, `extractSigArray`, and `extractBytes32Array`, validate that `len` is consistent with the actual size of `words`/`data` (e.g., `len <= (words.length - offset - 1)`) and reject the call (return failure) rather than allocate, mirroring the `verifyLength` bounds check already used elsewhere in the codebase (e.g., `RLP.verifyLength`).

### Proof of Concept
Not independently executed; based on static analysis only. A conceptual PoC: deploy a contract that calls the shielded-TRC20 verify-proof precompile address with call data crafted so that the word at the expected "count" offset (e.g., the `spendCount`/`recvCount`/signature-count slot consumed by `extractBytesArray`/`extractSigArray`) is set to a very large value (up to `Integer.MAX_VALUE`) while keeping the rest of the call data minimal in size, then broadcast the transaction. This is unverified against a running node in this session; further confirmation of exact caller entry points (e.g., which `VerifyXProof` functions map to `extractBytesArray` vs `extractSigArray`) would require reading the surrounding `PrecompiledContracts.java` methods not fully captured by these searches.

    if (offset > words.length - 1) {

          bytesLen);
    }
    return bytesArray;
  }

   * In case of int overflow returns Integer.MAX_VALUE otherwise works as #intValue()

  public int intValueSafe() {
    int bytesOccupied = bytesOccupied();
    int intValue = intValue();
    if (bytesOccupied > 4 || intValue < 0) {
      return Integer.MAX_VALUE;
