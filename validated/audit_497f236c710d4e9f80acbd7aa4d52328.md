### Title
Missing bounds check on attacker-controlled offset in `PrecompiledContracts.extractBytes32Array` can throw an uncaught `ArrayIndexOutOfBoundsException` inside `BatchValidateSign` - ([File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java])

### Summary
CVE-2017-7304 is a binutils bug where `copy_special_section_fields` follows an attacker-influenced `sh_link` field without validating it against the actual section count, producing an out-of-bounds/invalid read that crashes the tool. The analogous pattern in java-tron is `extractBytes32Array`, a helper used by the `BatchValidateSign` TVM precompile, which uses an attacker-supplied word (`offset`, ultimately derived from calldata a contract/tx sender fully controls) to index into a `DataWord[]` array without validating that the offset (or the derived length) stays within the array bounds.

### Finding Description
`extractBytes32Array` reads a length word and then walks `words[offset + i + 1]` for `i` in `[0, len)`, with no upper-bound check on `offset` or `offset + len`: [1](#0-0) 

This is inconsistent with the sibling helpers `extractBytesArray` and `extractSigArray`, which both explicitly guard the offset before indexing (`if (offset > words.length - 1) return new byte[0][];`): [2](#0-1) 

`extractBytes32Array` is reachable from the `BatchValidateSign` precompile's `doExecute`, where the offset passed in is computed directly from attacker-supplied calldata words (`words[2].intValueSafe() / WORD_SIZE`), with only a length-vs-`MAX_SIZE` sanity check applied to the *signature* array size when `allowTvmSelfdestructRestriction()` is enabled — no check bounds `addrArraySize`'s offset against `words.length`: [3](#0-2) 

Any contract calling this precompile with crafted calldata (a small `words` array combined with a large or out-of-range offset value at `words[2]`) can drive `offset` (or `offset + i + 1`) past `words.length`, producing an `ArrayIndexOutOfBoundsException` inside `extractBytes32Array`.

### Impact Explanation
`BatchValidateSign.execute` wraps `doExecute` in a `catch (Throwable t)` that swallows the exception and returns `(true, new byte[WORD_SIZE])`: [4](#0-3) 

Because the outer `execute` method catches `Throwable`, the resulting `ArrayIndexOutOfBoundsException` from the unguarded `extractBytes32Array` call does not propagate to the VM interpreter or crash the node — it is contained to a wrong/degenerate return value from the precompile. This significantly limits the practical severity compared to the original CVE's crash-inducing invalid read: there is no evidence in the explored code paths that this exception escapes to cause a node crash, chain halt, or unauthorized fund movement.

### Likelihood Explanation
An unprivileged contract deployer/caller can trivially construct calldata to trigger this code path (any TVM contract invoking the `BatchValidateSign` precompile address with malformed input), but given the surrounding `catch (Throwable)` in `execute`, the exception is caught and converted into an incorrect precompile result rather than an unhandled crash.

I was not able to fully verify all downstream call sites of `extractBytes32Array` (only two matches were found, both inside `PrecompiledContracts.java`) or the exact caller chain/other precompiles that might invoke it without an equivalent catch-all, due to the final-iteration cutoff before I could inspect the surrounding code around lines 950–1123 (e.g., a `ValidateMultiSign` variant) that the earlier search suggested exists. That code was not retrieved successfully, so I cannot confirm whether that alternate call path has the same `catch (Throwable)` containment.

### Recommendation
Add an explicit bounds check in `extractBytes32Array` mirroring `extractBytesArray`/`extractSigArray` (`if (offset > words.length - 1) return new byte[0][];`), and additionally validate that `offset + len` does not exceed `words.length` before the loop, returning a safe empty/degenerate result instead of relying on exception containment at the caller.

### Proof of Concept
Conceptual PoC (not executed): deploy a contract that performs a low-level `CALL` to the `BatchValidateSign` precompile address with calldata shaped so that `words[2].intValueSafe() / WORD_SIZE` (the address-array offset) is a value close to or exceeding `words.length`, while `words[1]` (signature offset) is validly small enough to satisfy the `MAX_SIZE` gate. This drives `extractBytes32Array(words, offset)` to index past the end of the `words` array, throwing `ArrayIndexOutOfBoundsException`, which is caught by `BatchValidateSign.execute`'s `catch (Throwable t)` and converted to a `(true, zero-bytes)` result — demonstrating the missing-bounds-check root cause without an observable crash in the paths I was able to confirm.

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }

  private static byte[][] extractSigArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();

      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          SIG_LENGTH);
    }
    return bytesArray;
  }
