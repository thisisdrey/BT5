### Title
`Pool.liquidate` enforces `maxLiquidable` per call, not per position/transaction — a liquidator can drain nearly 100% of collateral in one transaction by batching repeated calls - ([File: contracts/Pool.sol])

### Summary
`Pool.liquidate` caps each repayment at `maxLiquidable` *of the current debt balance*, but the check reads the freshly-reduced balance on every call. Since `liquidate` is permissionless and re-callable (directly, via an attacker contract, or batched through `Operator.execute` which forwards an arbitrary list of calls in one transaction), a liquidator can call it repeatedly until the victim's collateral is exhausted — geometrically bypassing the intended close-factor bound within a single transaction.

### Finding Description
In `Pool.liquidate`, the close-factor check is:

```solidity
uint256 _debtTokenBalance = _debtToken.balanceOf(account_);
if (amountToRepay_.wadDiv(_debtTokenBalance) > maxLiquidable) {
    revert AmountGreaterThanMaxLiquidable();
}
``` [1](#0-0) 

`_debtTokenBalance` is read *after* each prior call already burned part of the debt (`_debtToken.burn(account_, amountToRepay_)`). [2](#0-1)  With `maxLiquidable = 0.5e18`, call 1 repays 50% of the debt, call 2 repays 50% of the *remaining* 50% (75% cumulative), call 3 reaches 87.5%, etc. — asymptotically approaching 100% of the debt, each iteration seizing `repayment * (1 + liquidatorIncentive) + protocolFee` worth of the victim's `DepositToken` via `depositToken_.seize`. [3](#0-2) 

The two guards that could limit this don't:
- `whenNotShutdown` / `nonReentrant` only stop reentrancy *within* one `liquidate` frame; sequential calls in the same transaction are fine. [4](#0-3) 
- `debtFloorInUsd` reverts only if the *remaining* debt lands in `(0, debtFloorInUsd)`; the liquidator simply stops at the last call that leaves debt above the floor, or wipes it to exactly 0 (which is allowed). [5](#0-4) 
- `Operator.execute` iterates an attacker-supplied `Call[]` with no target allowlist, so batching dozens of `liquidate` calls into one transaction is a supported public path. [6](#0-5) 

This is the direct analog of the report's invariant #9 ("impossible to liquidate more than the `closeFactor` in a single liquidation transaction ... a single transaction can include more than one message"): the invariant is checked per message and never in aggregate.

### Impact Explanation
A borrower whose position tips below the collateral factor loses up to ~100% of their collateral in one block instead of the `maxLiquidable` fraction the parameter intends. Because `_toLiquidator = seized * (1 + liquidatorIncentive)` and the protocol fee scale with the seized amount, [7](#0-6)  each extra call transfers additional collateral value out of the victim's position at a bonus to the liquidator — a direct, irreversible loss of user funds beyond the designed liquidation bound. It also means a single malicious liquidator can seize the entire liquidation bonus pie before competing liquidators or a price recovery can intervene, defeating the purpose of a close factor (giving the borrower time to re-collateralize and capping per-event loss).

### Likelihood Explanation
- Fully permissionless: any EOA holding the required synthetic token can call `liquidate`; the only prerequisites are that the position is unhealthy and the liquidator doesn't liquidate their own position. [8](#0-7) 
- No privileged actor, oracle manipulation, or governance action required — only a normal market downturn that makes a position unhealthy, plus enough synth (flash-swappable via `Pool.swap` from other synth holdings) to cover the repayments.
- Trigger condition is whenever `maxLiquidable < 1e18` (the close-factor cap only binds in that configuration; e.g., 50% as exercised in `test/Pool.test.ts` at line 439-450). [9](#0-8) 
- Each loop iteration is profitable (liquidator incentive on every seized tranche), so a rational liquidator is incentivized to loop until the victim's `depositToken_.balanceOf` hits the `AmountIsTooHigh` bound or the debt floor stops the loop. [10](#0-9) 

### Recommendation
Enforce the liquidation bound per transaction rather than per call:
- Track cumulative liquidated debt per `(account_, syntheticToken_)` using a transient-storage slot (the codebase already uses `TransientSlot` in `Operator` and `ReentrancyGuardTransient`), reset at transaction end, and revert when `cumulativeRepaid / debtAtTxStart > maxLiquidable`. Alternatively snapshot `_debtTokenBalance` from the first liquidation of the account in the transaction.
- Or document that `maxLiquidable` is intentionally per-call and bound the per-tx damage differently (e.g., cap `_totalSeized` against the account's pre-transaction deposit balance with a stricter factor).

### Proof of Concept
Foundry test sketch (deploys standard `Pool` + `DepositToken` + `DebtToken` fixtures as in `test/Pool.test.ts`; assumes `maxLiquidable = 0.5e18`, `debtFloorInUsd = 0`):

```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity ^0.8.24;

import {Test} from "forge-std/Test.sol";
import {Pool} from "../contracts/Pool.sol";
import {DepositToken} from "../contracts/DepositToken.sol";
import {DebtToken} from "../contracts/DebtToken.sol";
import {SyntheticToken} from "../contracts/SyntheticToken.sol";

contract MaxLiquidableBypass is Test {
    Pool pool;               // initialized pool, maxLiquidable = 0.5e18, debtFloorInUsd = 0
    DepositToken msdWETH;    // victim's collateral token
    DebtToken msUsdDebt;
    SyntheticToken msUSD;
    address victim = address(0xA11CE);
    address liquidator = address(0xB0B);

    function test_liquidateMoreThanCloseFactorInOneTx() public {
        // setup: victim deposits WETH, issues msUSD; price moves -> unhealthy
        // liquidator holds enough msUSD to repay the full debt (e.g. own position)

        uint256 debtBefore = msUsdDebt.balanceOf(victim);
        uint256 collateralBefore = msdWETH.balanceOf(victim);

        vm.startPrank(liquidator);
        // Naive single call would revert:
        // pool.liquidate(msUSD, victim, debtBefore, msdWETH); // AmountGreaterThanMaxLiquidable

        // Batched loop in ONE transaction (same as Operator.execute(calls)):
        for (uint256 i; i < 20 && msUsdDebt.balanceOf(victim) > 0; ++i) {
            uint256 bal = msUsdDebt.balanceOf(victim);
            uint256 repay = bal / 2; // == maxLiquidable fraction of CURRENT balance
            if (repay == 0) repay = bal; // final call wipes dust (allowed: wadDiv == 1e18 <= maxLiquidable)
            try pool.liquidate(msUSD, victim, repay, msdWETH) {} catch { break; }
        }
        vm.stopPrank();

        uint256 repaidTotal = debtBefore - msUsdDebt.balanceOf(victim);

        // Invariant broken: repaidTotal >> debtBefore * maxLiquidable in a single transaction
        assertGt(repaidTotal * 1e18 / debtBefore, 0.99e18);
        // Victim lost ~all collateral at liquidation bonus prices:
        assertLt(msdWETH.balanceOf(victim), collateralBefore / 20);
    }
}
```

Equivalent via the deployed multicall path: `Operator.execute` with `calls_` = N encodings of `Pool.liquidate(msUSD, victim, remaining/2, msdWETH)` — each sub-call re-reads the shrunken `balanceOf` and passes the `maxLiquidable` check. A fork test only needs: an unhealthy victim position (post-price-move), `maxLiquidable < 1e18`, and a liquidator holding ≥ victim's debt in the synthetic token (obtainable via the attacker's own mint or `Pool.swap`). No privileged role, oracle write, or mock-only path is involved.
