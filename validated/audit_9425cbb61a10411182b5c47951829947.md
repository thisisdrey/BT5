### Title
Unlimited unauthenticated handshake-initiation (stage-1/msg1) processing with no per-source cooldown or rate limit - ([File: handshake_manager.go])

### Summary
`recoverUnstaking()` had no cooldown, letting an actor repeat a normally-bounded, cheap action ("unstake ⇄ restake") without limit, turning a benign recovery mechanism into a tool for griefing (denying other delegators) and reward theft. The analogous condition in nebula is `HandshakeManager.HandleIncoming` / `beginHandshake` in `handshake_manager.go`: any peer that can reach the UDP listener — with no CA-signed certificate at all — can send an unlimited stream of stage-1 (`msg1`) handshake packets, each of which is fully processed through the Noise handshake machine before any deduplication or throttling is applied, and there is no per-source cooldown, retry cap, or rate limit gating this path.

### Finding Description
`HandleIncoming` accepts any packet whose header type is a handshake and whose subtype is `header.HandshakeIXPSK0`. For a `MessageCounter == 1` packet (the initiator's first message) it only checks that `RemoteIndex == 0` and that the sender passes the coarse `remote_allow_list` IP/CIDR check, then unconditionally calls `beginHandshake`: [1](#0-0) 

`beginHandshake` allocates a brand-new responder `handshake.Machine`, and unconditionally calls `machine.ProcessPacket`, which performs the Noise/DH cryptographic handshake processing for every single incoming packet: [2](#0-1) 

Only *after* this expensive crypto work completes, and after certificate/peer validation, does `CheckAndComplete` perform a byte-equality check against previously seen handshake packets to detect a literal retransmit (`ErrAlreadySeen`): [3](#0-2) 

There is no mechanism anywhere in this path — nor in `HandleIncoming`, `beginHandshake`, or the `HandshakeManager` struct — that limits how many distinct (non-identical) stage-1 packets a single unauthenticated source can send per unit time. A codebase-wide search confirms there is no rate-limiting construct (`RateLimit`, "per second", "flood", "too many") anywhere in production code; the only hits are in test files and design notes. The remote_allow_list check is a static IP allow/deny table, not a rate limiter, and does nothing to bound repeat attempts from an allowed address (which, for hosts without `remote_allow_list` configured at all, is every address).

This directly mirrors the `recoverUnstaking()` defect: a state-changing operation (here, "spend CPU/allocate a pending hostinfo + index by running a full handshake") that should be bounded/cooled-down is instead unboundedly repeatable by an attacker who pays essentially nothing (a UDP packet) while the victim pays a real, non-trivial cost (asymmetric elliptic-curve crypto + memory) every time, with no certificate required to reach this code path at all.

### Impact Explanation
An attacker with no CA-signed certificate can:
- Send an unbounded stream of distinct stage-1 packets (varying the ephemeral key/index each time so `ErrAlreadySeen` never triggers) to force the target to repeatedly perform full Noise handshake crypto and allocate pending-handshake state (`hm.indexes`, `hm.vpnIps` entries via `allocateIndex`/pending `HostInfo`), exhausting CPU and memory on the victim node.
- Because this is the pre-authentication entry point for every real handshake, this also crowds out or delays legitimate handshakes/rehandshakes for actual mesh peers — a direct availability/DoS impact on the node's ability to establish or maintain tunnels, analogous to the "denying delegators" griefing vector in the original report (cheap repeated action denies a legitimate resource to others).
- This is remotely triggerable pre-certificate, satisfying the "no CA-signed certificate" reachability requirement, and constitutes a remote resource-exhaustion / crash-adjacent (denial of service) condition consistent with the accepted impact categories.

### Likelihood Explanation
High. The path requires only UDP reachability to a nebula node's listen port; no handshake completion, no valid certificate, and no prior trust relationship are needed. The only gate (`remote_allow_list`) is off by default and, even when configured, is a static allow-list, not a request-rate control, so any allowed source (including "allow all" default) can still flood indefinitely.

### Recommendation
Introduce a per-source (and/or global) rate limit / cooldown on unauthenticated stage-1 handshake processing before invoking `beginHandshake`'s cryptographic work — e.g., a token bucket keyed by source `netip.Addr` (or `/24`/`/64` prefix to resist trivial IP rotation) inside `HandleIncoming`, dropping or delaying excess `MessageCounter == 1` packets from a given source within a short window. This bounds the cost asymmetry the same way the sherlock fix added a cooldown to `recoverUnstaking()`.

### Proof of Concept
Conceptual (matches existing test patterns such as `TestHandshakeMessageCounter0Dropped` / `TestHandshakeRetransmitDuplicate` in `e2e/handshake_manager_test.go`, which already exercise this exact ingress path):
1. Attacker (no cert, no CA) crafts N distinct valid-format stage-1 `HandshakeIXPSK0` packets (`RemoteIndex = 0`, `MessageCounter = 1`, each with a fresh ephemeral keypair so bytes differ) targeting a victim node's UDP listener.
2. Send all N packets in rapid succession via `myControl.InjectUDPPacket(...)`-style delivery (or raw UDP in a real deployment).
3. Observe: `HandleIncoming` → `beginHandshake` → `machine.ProcessPacket` runs full DH/crypto for every packet with no throttling; `hm.indexes`/pending `vpnIps` grow with each; CPU usage scales linearly with attacker-controlled N at negligible attacker cost, with no cooldown or rate limiter anywhere in the call path to bound it.
