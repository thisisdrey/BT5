Audit Report

## Title
Unchecked `repatriate_reserved` remainder in `pallet-nfts`/`pallet-uniques` `transfer_ownership` desyncs recorded deposit from actually-reserved funds - ([File: substrate/frame/nfts/src/features/transfer.rs])

## Summary
`pallet-nfts::do_transfer_ownership` and `pallet-uniques::transfer_ownership` call `T::Currency::repatriate_reserved(&details.owner, &new_owner, deposit, Reserved)?` and then unconditionally flip collection ownership, discarding the `Balance` remainder that `repatriate_reserved` returns on a partial (`BestEffort`/`Polite`) move. `pallet-assets::transfer_ownership` had the identical defect but was fixed by capturing the remainder and rejecting with `Error::IncompleteDepositTransfer` if non-zero; that fix was never ported to `pallet-nfts` or `pallet-uniques`.

## Finding Description
`ReservableCurrency::repatriate_reserved` is explicitly documented as best-effort: "As much funds up to `value` will be deducted as possible. If this is less than `value`, then `Ok(non_zero)` will be returned." [1](#0-0)  The concrete Balances implementation performs the move with `BestEffort` precision and `Polite` fortitude, then returns `value.saturating_sub(actual)` as the leftover that could not be moved: [2](#0-1) 

In `pallet-nfts::do_transfer_ownership`, the call site only propagates a hard error via `?` and ignores the returned `Balance` remainder, then immediately flips `CollectionAccount` and `details.owner` to the new owner: [3](#0-2) 

The structurally identical pattern exists in `pallet-uniques::transfer_ownership`: [4](#0-3) 

By contrast, `pallet-assets::transfer_ownership` captures the remainder and rejects the dispatch (rolling back the `try_mutate` transactional storage) when it is non-zero: [5](#0-4)  This exact fix is documented in `prdoc/pr_12366.prdoc`: [6](#0-5)  A repo-wide search confirms `IncompleteDepositTransfer` exists only in `pallet-assets` and its tests, not in `pallet-nfts` or `pallet-uniques`.

## Impact Explanation
When a lock/freeze on the old collection owner's account overlaps their reserved deposit under `Polite` fortitude, `repatriate_reserved` will move less than the full `owner_deposit`/`total_deposit`, yet `pallet-nfts`/`pallet-uniques` still commit `details.owner = new_owner` unconditionally. This leaves `CollectionDetails.owner_deposit` (nfts) or `CollectionDetails.total_deposit` (uniques) attributed to the new owner while part of the actual reserved balance remains stuck on the old owner, with no code path referencing the old owner for that remainder going forward — a permanent user-fund lock, which is a listed accepted impact category (permanent user-fund or bridge-state lock).

## Likelihood Explanation
`transfer_ownership`/`do_transfer_ownership` are public, unprivileged extrinsics callable by any current collection owner against any account that has called `set_accept_ownership`. The triggering condition — an overlapping lock or freeze on the old owner's balance (e.g., from staking, vesting, or another lock/freeze consumer) — is a routine, attacker-controllable state that requires no privileged role, malicious validator, or off-chain infrastructure compromise, matching the required threat model of an unprivileged external actor using public extrinsics.

## Recommendation
Port the `pallet-assets` fix (`prdoc/pr_12366.prdoc`) to `pallet-nfts::do_transfer_ownership` and `pallet-uniques::transfer_ownership`: capture the `Balance` remainder returned by `repatriate_reserved`, add an `IncompleteDepositTransfer` error variant, and `ensure!(remaining.is_zero(), Error::<T, I>::IncompleteDepositTransfer)` before committing the ownership change, relying on the existing `try_mutate` transactional context to roll back partial moves.

## Proof of Concept
1. Owner `A` creates an NFT collection via `pallet-nfts`, reserving `owner_deposit` D.
2. `A` acquires a lock/freeze (e.g., via `pallet-vesting` or a staking bond) overlapping enough of `A`'s balance that, under `Polite` fortitude, `repatriate_reserved` cannot move the full `D` to a new owner `B`.
3. `B` calls `set_accept_ownership(collection)`; `A` calls `transfer_ownership(collection, B)`.
4. `repatriate_reserved` returns `Ok(remainder > 0)` (no error) inside `do_transfer_ownership`; execution proceeds, updating `CollectionAccount` and `details.owner` to `B` and emitting `OwnerChanged`, even though only `D - remainder` was actually moved [3](#0-2) .
5. `A` retains `remainder` reserved with no subsequent code path attributing it to `A`, while accounting now attributes the full `D` to `B` — the remainder becomes permanently stranded.
