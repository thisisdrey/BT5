### Title
Unconditional forwarding of outgoing receipts despite receipt-level failure and state rollback in `apply_action_receipt` enables token duplication - (File: runtime/runtime/src/lib.rs)

### Summary
In `Runtime::apply_action_receipt`, the post-execution `check_storage_stake` check (lines 954-977) can fail *after* a `FunctionCall` action has already succeeded and generated outgoing receipts (e.g., a `Transfer` promise). When this happens, `result.result` is set to `Err(LackBalanceForState)`, causing `state_update.rollback()` (line 1032) to discard the trie mutations (including the never-yet-persisted balance deduction on the sender account, since `set_account` at line 959 only runs on the success path). However, the receipt-forwarding loop at lines 1140-1184 iterates over `result.new_receipts` and calls `receipt_sink.forward_or_buffer_receipt` unconditionally, without checking `result.result.is_ok()`.

### Finding Description
The relevant control flow is: [1](#0-0) 
executes the action list sequentially, merging each action's `new_receipts` into the shared `result: ActionReceiptResult`.

After all actions complete successfully, the receiver account balance is checked for storage staking sufficiency: [2](#0-1) 
Note that `set_account(state_update, account_id.clone(), account)` — which persists any balance changes on `account` (including deposit deductions made when the FunctionCall created outgoing Transfer/promise receipts) — is only invoked in the `Ok(())` branch. If `check_storage_stake` fails, `result.set_error(...)` flips `result.result` to `Err`, and the in-memory `account` mutations are simply discarded (never written to `state_update`).

Immediately after, state is committed or rolled back strictly based on `result.result`: [3](#0-2) 
`state_update.rollback()` on the `Err` path discards trie changes (e.g. `storage_write` calls, and — since it was never even written — the sender's balance decrement never lands in the persisted state either).

However, the receipt-emission loop that follows does not gate on `result.result`: [4](#0-3) 
Every entry in `result.new_receipts` — populated by the successful `FunctionCall` action before the failure was detected — is forwarded to `receipt_sink.forward_or_buffer_receipt` regardless of whether `result.result` is `Ok` or `Err`.

Consequently, an attacker's contract can, within a single `FunctionCall` action:
1. Call `promise_batch_create` + `promise_batch_action_transfer` to schedule an outgoing `Transfer` receipt to a third-party (attacker-controlled) account, consuming/deducting balance only from the in-memory `account` object (not yet persisted to `state_update`).
2. Perform a large `storage_write` that pushes the account below the storage staking threshold.

The `FunctionCall` action itself succeeds (its individual `ActionResult` is `Ok`), so its `new_receipts` (the Transfer) get merged into `result.new_receipts`. Only afterward does the receipt-level `check_storage_stake` fail. Because `set_account` is skipped and `state_update.rollback()` discards the storage write, the sender's on-chain balance is left completely untouched (no deduction ever landed in the trie) — yet the Transfer receipt is still forwarded via `receipt_sink` and will credit the destination account when it executes. Net effect: new tokens materialize at the destination with no corresponding debit anywhere in persisted state.

### Impact Explanation
This is a token-inflation / value-duplication bug: value is created out of nothing because an outgoing `Transfer` (or any other value-bearing outgoing action) that was produced by an action which is subsequently deemed failed at the receipt level still gets sent and executed, while the corresponding balance debit — which existed only in an unpersisted in-memory `Account` struct — is discarded by `rollback()`. This matches NEAR's "token inflation or loss" bounty category and could allow an unprivileged attacker to mint unbacked NEAR tokens repeatedly (a single narrow but fully attacker-controlled account/contract, deployed and called from a public RPC, with no special privileges needed).

### Likelihood Explanation
Preconditions are entirely attacker-controlled: any account can deploy a WASM contract, deposit enough NEAR to fund the initial account creation, and craft a `FunctionCall` that (a) creates an outgoing promise/Transfer, then (b) writes state until the account balance dips under the storage-staking minimum. No special access keys, validator status, or timing races are required, and the exploit is repeatable per receipt (bounded only by mitigation of `check_storage_stake` triggering deterministically based on `storage_write` size vs. remaining balance, both of which the attacker fully controls).

### Recommendation
Gate the receipt-forwarding loop (and any state changes emitted from `result.new_receipts`) on `result.result.is_ok()`, mirroring the `state_update.commit()`/`rollback()` split — i.e., only forward `new_receipts` to `receipt_sink`/`instant_receipts` when the overall action-receipt result succeeds; otherwise, drop/refund them consistently with the deposit-and-state rollback so that no outgoing receipt escapes with value that was never actually debited from the failing receiver.

### Proof of Concept
Integration test plan (`runtime/runtime/src/tests/apply.rs`-style, using the runtime test harness):
1. Deploy a test contract to account `A` with a method that: (a) creates a promise `promise_batch_create(B)` and appends `promise_batch_action_transfer(deposit)` sending funds to account `B`; (b) then calls `storage_write` with a large enough key/value to make `A`'s resulting effective balance (after the deposit deduction and storage cost) fall below `check_storage_stake`'s required minimum.
2. Fund `A` with just enough balance so the FunctionCall succeeds but the post-action storage check fails with `LackBalanceForState`.
3. Apply the receipt via the runtime test harness (`Runtime::apply`), and assert:
   - The execution outcome for `A`'s receipt has `status = Failure(ActionError(LackBalanceForState))`.
   - `A`'s persisted account state (post-apply) shows the `storage_write` was rolled back (key absent) and `A`'s balance is unchanged from before the receipt (deposit not actually debited).
   - Despite the failure, an outgoing `Transfer` receipt to `B` was generated/forwarded (present in `receipt_sink`'s outgoing receipts / next block's incoming receipts), and applying it credits `B`'s balance by `deposit`.
   - Assert this constitutes value duplication: `B`'s balance increased by `deposit` while `A`'s balance was never reduced anywhere in persisted state — i.e., total supply invariant is violated across the two applied chunks.
