### Title
Authorization escalation via stale self-authorized delayed receipts surviving account delete+recreate - (File: `runtime/runtime/src/actions.rs`, `runtime/runtime/src/lib.rs`, `core/store/src/utils/mod.rs`)

### Summary
Actor permission checks for privileged actions (`AddKey`, `DeleteKey`, `DeployContract`, `Stake`, `DeployGlobalContract`, `UseGlobalContract`, `WithdrawFromGasKey`) authorize purely by comparing the receipt's `predecessor_id` string to the `receiver_id` string (self-call check), with no binding to a specific account "incarnation." Because `TrieKey::DelayedReceipt`/`DelayedReceiptIndices` are shard-global FIFO queues untouched by `remove_account`, a self-targeted privileged receipt enqueued while an attacker owned account `X` remains in the backlog after `X` is deleted, and will execute with full self-authorization against whatever new account is later created under the same name `X`.

### Finding Description
`apply_action_receipt` sets `let mut actor_id = receipt.predecessor_id().clone();` [1](#0-0)  and this `actor_id` is later checked in `check_actor_permissions`, which for `AddKey`/`DeleteKey`/`DeployContract`/`Stake`/etc. only requires `actor_id == account_id` [2](#0-1) . This check has no notion of "which incarnation" of the account authorized the receipt — it is purely a string comparison between the receiver's account name and the receipt's predecessor name.

`remove_account` (invoked from `action_delete_account`) deletes `TrieKey::Account`, `TrieKey::ContractCode`, access keys, gas-key nonces, and contract data for the account, but never touches `TrieKey::DelayedReceipt`/`TrieKey::DelayedReceiptIndices`, since those are shard-global structures, not account-scoped [3](#0-2) . A delayed receipt with `receiver_id == X` and `predecessor_id == X` already sitting in the queue is completely unaffected by `X`'s deletion.

`process_delayed_receipts` dequeues receipts strictly by FIFO position/index and re-validates only structural/size constraints via `validate_receipt(..., ExistingReceipt)`, not ownership continuity, before dispatching to `apply_action_receipt` [4](#0-3) . At the time this receipt is finally applied, `apply_action_receipt` loads whatever account currently exists at `X` (`get_account(state_update, account_id)`) and executes the privileged action, since `check_actor_permissions` only checks name equality with the stale `predecessor_id`.

Exploit flow:
1. Attacker owns account `X` (or registers a fresh top-level/sub-account `X` that they control).
2. Attacker sends a self-receipt (`predecessor_id == X`, `receiver_id == X`) carrying a privileged action (e.g., `AddKey` with a full-access key, or `DeployContract`).
3. Attacker floods shard `S`'s delayed-receipt backlog with many low-priority receipts (congestion control admits this via `process_incoming_receipts` pushing overflow receipts into the delayed queue, `lib.rs:2578`) so the malicious receipt is pushed deep into the FIFO backlog and will only execute several blocks/chunks later.
4. Attacker calls `DeleteAccount` on `X`, refunding balance to a beneficiary and removing the account, access keys, and contract — but not the still-queued delayed receipt.
5. A new, unrelated party later creates a fresh account named `X` (e.g., re-registering an available top-level name, or reusing a name pattern the attacker vacated) and funds/deploys a legitimate contract on it.
6. When the delayed receipt is eventually dequeued, `apply_action_receipt` executes the `AddKey`/`DeployContract` action against the new account, and `check_actor_permissions` passes because `actor_id (== old predecessor "X") == account_id (== "X")` — granting the attacker a full-access key or replacing the code on an account they no longer legitimately own.

Existing checks that fail to prevent this: `validate_receipt` on dequeue only checks structural validity (size/action limits), not that the account referenced still exists in the same "generation" it was created under [5](#0-4) ; `check_account_existence` only checks whether *some* account currently exists at that name, not whether it is the same account the receipt was authorized against [6](#0-5) .

### Impact Explanation
This is authorization escalation across accounts/promises: a stale, self-authorized privileged receipt from a deleted account's former owner executes against a completely different party's newly created account of the same name, allowing unauthorized key addition or contract redeployment without the new owner's consent. This matches the NEAR bounty category "authorization escalation across accounts or promises."

### Likelihood Explanation
Preconditions: the attacker must (a) control account `X` momentarily, (b) succeed in delaying their self-receipt long enough to survive a delete, and (c) have some other party recreate an account with the exact same name `X` afterward. Steps (a) and (b) are fully within reach of an unprivileged attacker (self-transactions plus queue-flooding via ordinary transactions/receipts, which is a known, already-documented congestion-control admission path). Step (c) is the limiting factor: for sub-accounts, only the parent account can create `child.parent` names, so cross-owner exploitation there is restricted to cases where the attacker also controls or influences reacquisition of the parent; for top-level names, whether recreation is fully permissionless depends on the registrar/creation rules in effect, which were not fully traced in this investigation. This introduces genuine uncertainty about the practical repeatability of step (c) in the current protocol configuration, even though the underlying code-level gap (no generation-binding in the authorization check, delayed queue not account-scoped) is concretely reproducible and confirmed in code.

### Recommendation
Bind privileged self-authorization checks to a persistent account identity/generation counter (e.g., increment a per-account "epoch"/nonce on every `CreateAccount` and store it in receipts derived from that account, or drop/execute-as-failed any queued action receipt whose receiver account was deleted and recreated since the receipt was created). Alternatively, when `action_delete_account` runs, proactively invalidate (or flag for skip) any still-queued delayed/postponed receipts whose `receiver_id` matches the deleted account, or refuse to let `check_actor_permissions` pass for `predecessor_id == account_id` unless a generation marker recorded at receipt-creation time still matches the current account's generation marker.

### Proof of Concept
Extend the existing apply-path test harness (as used in `runtime/runtime/src/tests/apply.rs`, e.g. `test_function_call_after_same_chunk_delete_recreate_resolves_fresh_code`) with a new test:
1. Create account `X`, deploy no contract.
2. Build a self-targeted `ActionReceipt` `{ predecessor_id: X, receiver_id: X, actions: [AddKey(full_access_key)] }` and submit it in a chunk with a very low `gas_limit`/many filler receipts targeting other receivers so it is pushed into `TrieKey::DelayedReceipt` (assert it appears in the delayed queue via `DelayedReceiptIndices` and not yet processed).
3. In a subsequent chunk, submit `DeleteAccount { beneficiary_id: <other> }` self-receipt for `X`; assert `TrieKey::Account { X }` is removed while `TrieKey::DelayedReceipt` entries remain (`get_delayed_receipt_indices` unchanged).
4. In a further chunk, submit `CreateAccount` for `X` from a different predecessor (or simulate the underlying reuse condition) and deploy a distinct contract/deposit funds.
5. Drain the gas limit budget across subsequent chunks until the queued `AddKey` delayed receipt is dequeued and applied.
6. Assert that the new account `X` now has the attacker's full-access key installed (`get_access_key` returns `Some`), demonstrating that a privileged self-receipt from the old owner executed against the new owner's account without their authorization — violating "authorization exactness."

pub(crate) fn check_account_existence(
    action: &Action,
    account: &Option<Account>,
    account_id: &AccountId,
    config: &RuntimeConfig,
    implicit_account_creation_eligible: bool,
) -> Result<(), ActionError> {
    match action {
        Action::CreateAccount(_) => {
            if account.is_some() {
                return Err(ActionErrorKind::AccountAlreadyExists {
                    account_id: account_id.clone(),
                }
                .into());
            } else {
                if account_is_implicit(account_id, config.wasm_config.eth_implicit_accounts) {
                    // If the account doesn't exist and it's implicit, then you
                    // should only be able to create it using single transfer action.
                    // Because you should not be able to add another access key to the account in
                    // the same transaction.
                    // Otherwise you can hijack an account without having the private key for the
                    // public key. We've decided to make it an invalid transaction to have any other
                    // actions on the implicit hex accounts.
                    // The easiest way is to reject the `CreateAccount` action.
                    // See https://github.com/nearprotocol/NEPs/pull/71
                    return Err(ActionErrorKind::OnlyImplicitAccountCreationAllowed {
                        account_id: account_id.clone(),
                    }
                    .into());
                }
            }
        }
        Action::Transfer(_) => {
            if account.is_none() {
                return check_transfer_to_nonexisting_account(
                    config,
                    account_id,
                    implicit_account_creation_eligible,
                );
            }
        }
        Action::DeterministicStateInit(_) => {
            // Existing and non existing is valid for DeterministicStateInit.
            // Does not exist => The account will be created by the action.
            // Does exist => Nothing happens but the receipt is not aborted to
            // allow optional init before other actions.
        }
        Action::DeployContract(_)
        | Action::FunctionCall(_)
        | Action::Stake(_)
        | Action::AddKey(_)
        | Action::DeleteKey(_)
        | Action::DeleteAccount(_)
        | Action::Delegate(_)
        | Action::DelegateV2(_)
        | Action::DeployGlobalContract(_)
        | Action::UseGlobalContract(_)
        | Action::TransferToGasKey(_)
        | Action::WithdrawFromGasKey(_) => {
            if account.is_none() {
                return Err(ActionErrorKind::AccountDoesNotExist {
                    account_id: account_id.clone(),
                }
                .into());
            }
        }
    };
    Ok(())
}

/// Removes account, code and all access keys and gas keys associated to it.
pub fn remove_account(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
) -> Result<RemoveAccountResult, StorageError> {
    state_update.remove(TrieKey::Account { account_id: account_id.clone() });
    state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });

    let mut gas_key_nonce_count: usize = 0;
    let mut gas_key_nonce_total_key_bytes: usize = 0;

    // Removing access keys and gas key nonces
    let lock = state_update.trie().lock_for_iter();
    let mut keys_to_remove: Vec<TrieKey> = Vec::new();
    for raw_key in state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_access_keys(account_id), &lock)?
    {
        let raw_key = raw_key?;
        let key_handle = trie_key_parsers::parse_key_handle_from_access_key_key(
            &raw_key, account_id,
        )
        .map_err(|_e| {
            StorageError::StorageInconsistentState(
                "Can't parse key handle from raw key for AccessKey".to_string(),
            )
        })?;
        let nonce_index =
            trie_key_parsers::parse_nonce_index_from_gas_key_key(&raw_key, account_id, &key_handle)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse nonce index from raw key for AccessKey".to_string(),
                    )
                })?;
        if let Some(index) = nonce_index {
            gas_key_nonce_count += 1;
            gas_key_nonce_total_key_bytes += raw_key.len();
            keys_to_remove.push(TrieKey::gas_key_nonce(
                account_id.clone(),
                key_handle.clone(),
                index,
            ));
        } else {
            keys_to_remove.push(TrieKey::access_key(account_id.clone(), key_handle.clone()));
        }
    }
    drop(lock);

    for trie_key in keys_to_remove {
        state_update.remove(trie_key);
    }

    // Removing contract data
    let lock = state_update.trie().lock_for_iter();
    let data_keys = state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_contract_data(account_id, &[]), &lock)?
        .map(|raw_key| {
            trie_key_parsers::parse_data_key_from_contract_data_key(&raw_key?, account_id)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse data key from raw key for ContractData".to_string(),
                    )
                })
                .map(Vec::from)
        })
        .collect::<Result<Vec<_>, _>>()?;
    drop(lock);

    for key in data_keys {
        state_update.remove(TrieKey::ContractData { account_id: account_id.clone(), key });
    }
    Ok(RemoveAccountResult { gas_key_nonce_count, gas_key_nonce_total_key_bytes })
}
