### Title
Missing Restriction on Self-Referential AccountPermissionUpdateContract Grants Enables Active-Key Privilege Escalation to Full Account Ownership - (File: actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java)

### Summary
`AccountPermissionUpdateActuator` lets an account's `Owner` permission redefine the account's entire permission set (Owner, Witness, Active[]) in one transaction. The bit-mask validation in `checkPermission()` only confirms that an Active permission's `operations` bitmap is a subset of the chain-wide "available contract types" — it never excludes `AccountPermissionUpdateContract` (type 46) itself from being one of the operations an Active permission is allowed to authorize. [1](#0-0) 

### Finding Description
Tron's multisig model separates `Owner` permission (full control) from `Active` permissions (scoped, lower-trust keys restricted to a bitmap of allowed contract types). The intent is that an `Active` key should only be able to sign for the specific contract types the account owner enabled for it, while only the `Owner` permission should be able to rewrite permissions via `AccountPermissionUpdateContract`.

However, `checkPermission()` in `AccountPermissionUpdateActuator` validates an Active permission's `operations` bytestring solely against `dynamicStore.getAvailableContractType()` (the globally-enabled contract type bitmap), with no additional rule preventing `AccountPermissionUpdateContract` (contract type 46) from being included in that bitmap: [2](#0-1) 

Separately, `TransactionCapsule.checkPermission()` — the runtime signature/permission gate used both for signing and for `Wallet.broadcastTransaction`/`getTransactionSignWeight` — only rejects a contract when `permissionId != 0` and the requested contract type bit is absent from the Active permission's operations bitmap; if the bit is present, the Active-key holder is authorized to execute that contract type just like the Owner: [3](#0-2) [4](#0-3) 

The project's own test fixture confirms that the "default"/typical operations bitmap enumerates essentially all `ContractType` values (only `ClearABIContract` and `UpdateBrokerageContract` are explicitly excluded) — `AccountPermissionUpdateContract` is not excluded: [5](#0-4) 

Consequently, once an account owner grants (or accepts a template that grants) an Active permission with `AccountPermissionUpdateContract` set in its operations bitmap, any key holder in that Active permission — regardless of how low its `weight`/`threshold` was meant to be relative to the true Owner key — can broadcast a new `AccountPermissionUpdateContract` transaction (signed only with that Active permission, `permission_id` = the active permission's id) that completely replaces the `Owner` permission with keys of the attacker's choosing, replaces or drops other Active permissions, and even sets a Witness permission if applicable. This is a full transfer of account control performed by a party that was only supposed to hold narrow, delegated authority — the actuator never validates that the caller already possesses Owner-level authority independent of the very permission being rewritten, nor does it forbid a permission from authorizing its own escalation vector.

This mirrors the Wiki.js flaw precisely: a resolver/actuator accepts an attacker-influenced list (there: `groups[]`; here: the `operations` bitmap of an Active permission, and the new `owner`/`active` permission definitions themselves) and applies it to the account record with only shallow, structural validation (key count, weight sums, address format, bitmap size) — never validating that the entity performing the sensitive privilege-defining operation is actually entitled to grant itself that scope.

### Impact Explanation
An attacker who compromises or is intentionally issued only an Active key (with the commonly-used broad default operations bitmap, or any bitmap that was not carefully hand-pruned to exclude type 46) can escalate from "restricted, delegated signer" to full unilateral control of the victim account: rewriting the Owner permission to attacker-controlled keys, removing the legitimate owner's ability to sign at all, and subsequently draining funds, voting power, or contract control tied to that account. This is a concrete unauthorized-account-takeover / theft-enabling primitive reachable purely by broadcasting a single signed transaction — no consensus, node, or peer compromise required.

### Likelihood Explanation
Exploitability depends on the account's Active permission having `AccountPermissionUpdateContract` in its operations bitmap. This is not blocked by the actuator, is not flagged as disallowed anywhere in validation, and the codebase's own reference "default"/all-inclusive operations template (used in tests to describe expected behavior) includes this bit. Any wallet, exchange custody setup, DApp, or multisig tooling that grants a broad "all contract types" Active permission to a delegated/lower-trust key (a very natural template to reach for, given TRON's own reference bitmap) is directly exposed. Given TRON's account-permission model is documented and used for real custodial/delegated key setups, the likelihood of at least some in-the-wild accounts having such an over-broad Active permission is Medium-to-High.

### Recommendation
In `AccountPermissionUpdateActuator.checkPermission()`, explicitly forbid `AccountPermissionUpdateContract` (and any other contract type capable of self-escalating permission control) from being set in the `operations` bitmap of any permission whose `type != Owner`. Enforce this both at validate-time (reject the contract) and, defense-in-depth, in `TransactionCapsule.checkPermission()`/`WalletUtil.checkPermissionOperations()` so that non-Owner permission IDs can never authorize `AccountPermissionUpdateContract` regardless of what bitmap is stored on-chain (protecting already-misconfigured accounts).

### Proof of Concept
1. Account `A` sets up an Active permission (id=2) for delegated key `K` using a broad/default operations bitmap that includes bit 46 (`AccountPermissionUpdateContract`), via a normal `AccountPermissionUpdateContract` signed by `A`'s Owner key. This is accepted because `checkPermission()` only checks the bitmap against `getAvailableContractType()`, which includes type 46.
2. Attacker who controls `K` (holding only the Active permission, with weight below the true Owner threshold) constructs a new `AccountPermissionUpdateContract` for account `A`, setting `permission_id = 2` and defining a brand-new `Owner` permission consisting solely of attacker-controlled keys, and an `Active` list of the attacker's choosing.
3. Attacker signs with `K` only. `TransactionCapsule.checkPermission()` permits this because `permissionId != 0` but `AccountPermissionUpdateContract`'s bit is set in `K`'s permission operations bitmap. [3](#0-2) 
4. `AccountPermissionUpdateActuator.execute()` applies `account.updatePermissions(...)` unconditionally, overwriting Owner/Witness/Active permissions with the attacker's chosen values. [6](#0-5) 
5. Account `A` is now fully controlled by the attacker; the original Owner key is locked out.
