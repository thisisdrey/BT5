### Title
Anti-replay window `Check`/`Update` race in `ConnectionState.Decrypt` allows a captured packet to be delivered to the tunnel twice - (File: `connection_state.go`)

### Summary
The external report's bug class is: a security-critical accounting update (marking a token transfer as accounted for) happens *after* the externally-observable action (the reward transfer) with a lock/state gap in between, letting a reentrant caller repeat the action before the accounting catches up. Nebula's `ConnectionState.Decrypt` has the same shape: it releases `decryptLock` between the anti-replay **check** (`window.Check`) and the anti-replay **commit** (`window.Update`), with the actual AEAD decrypt happening in that unlocked gap. Because Nebula dispatches inbound UDP packets to multiple concurrent reader/worker goroutines, two copies of the same captured ciphertext (a trivially producible condition for a remote attacker who merely records and replays UDP datagrams - no CA-signed certificate required) can race through `Check` before either has `Update`-marked the counter, defeating the replay window.

### Finding Description
`ConnectionState.Decrypt` in `connection_state.go` performs the check, the decrypt, and the window update as three separate critical sections instead of one atomic operation: [1](#0-0) 

```
func (cs *ConnectionState) Decrypt(...) ([]byte, error) {
    cs.decryptLock.Lock()
    result := cs.window.Check(l, messageCounter)
    cs.decryptLock.Unlock()
    if !result { return nil, ErrAlreadySeen }

    out, err = cs.dKey.DecryptDanger(...)   // <-- lock NOT held here
    ...

    cs.decryptLock.Lock()
    result = cs.window.Update(l, messageCounter)
    cs.decryptLock.Unlock()
    if !result { return nil, ErrAlreadySeen }
    return out, nil
}
```

`Bits.Check` only reads the bitmap to see whether `messageCounter` was already marked seen; it does not itself mark anything. Only `Bits.Update` (called afterward, under a freshly-acquired lock) actually sets the bit: [2](#0-1) 

Because `decryptLock` is released between the `Check` and the `Update`, if two goroutines call `Decrypt` concurrently for the **same `messageCounter`** (i.e., the same captured/replayed ciphertext delivered twice), both can pass `Check` (neither has set the bit yet), both proceed to `DecryptDanger` successfully (AEAD decryption with a given counter/nonce is a deterministic, side-effect-free operation and can succeed for both callers), and both then call `Update`. This defeats the purpose of the anti-replay window: the "duplicate" detection is a two-step check-then-act sequence that is not executed atomically, so a second/concurrent instance of the same wire packet is not guaranteed to be rejected.

This is directly reachable by a network-level attacker without a CA-signed certificate: any observer of the encrypted UDP stream between two legitimate peers can capture one datagram and re-inject it (twice, on separate sockets/paths, or via a second host that forwards to a different inbound queue) while the first copy is still executing between its `Check` and `Update` calls. Nebula's UDP receive path fans inbound packets out over multiple reader/worker goroutines (`interface.go`'s multi-routine listen loop feeding `readOutsidePackets`, which calls into `ConnectionState.Decrypt` via `outside.go`), so genuinely concurrent processing of duplicate wire packets for the same tunnel is an expected runtime condition, not a contrived corner case. [3](#0-2) 

### Impact Explanation
Anti-replay protection is a core security property of the Noise-based transport: it prevents a network observer from re-injecting a previously captured, still-valid ciphertext to have it decrypted and delivered to the TUN device again. The race window here means the replay window's protection can be bypassed for concurrently-delivered duplicates, resulting in:
- Duplicate delivery of attacker-replayed application traffic to the inside (TUN) interface, undermining the confidentiality/integrity guarantee that a captured packet cannot be reprocessed.
- Corruption of replay/loss accounting metrics (`lostCounter`, `dupeCounter`) used for diagnostics, though the primary concern is the security bypass itself.

The severity is bounded by the fact that only *concurrently in-flight* duplicates within the narrow window between `Check` and `Update` are affected (not an arbitrary indefinite replay), but this is squarely a remote-attacker-controllable condition (packet duplication/relay is trivial on unreliable UDP networks and easily amplified by an attacker), matching the "nonce/replay handling" bug class called out in the rules.

### Likelihood Explanation
An attacker with access to the wire (no valid Nebula certificate needed) can capture one ciphertext and transmit multiple copies of it in quick succession, or route copies to arrive on different reader goroutines of the victim's UDP listener, increasing the likelihood that two `Decrypt` calls execute concurrently for the same `messageCounter` and race through the unlocked gap. The existing e2e test suite already demonstrates the project's awareness of replay-window correctness requirements for relay frames (`TestRelayReplayProtection`), but that test does not exercise the concurrent/racy check-then-act path in `ConnectionState.Decrypt` itself. [4](#0-3) 

### Recommendation
Hold `decryptLock` across the entire check-decrypt-update sequence (or restructure `Bits` so that a single atomic "check-and-reserve" operation marks the counter as claimed before decryption begins, rolling back only on decrypt failure). This removes the window during which two concurrent callers can both observe an "unseen" counter and both proceed to decrypt and deliver the same packet.

### Proof of Concept
Conceptual/logical PoC (race condition, not a deterministic single-threaded PoC):
1. Two peers establish a tunnel; attacker passively captures one `header.Message` ciphertext with `MessageCounter = N`.
2. Attacker replays the exact same UDP datagram twice in rapid succession, timed to land on two different reader/worker goroutines of the victim's `Interface.readOutside` pipeline.
3. Goroutine A calls `ConnectionState.Decrypt(..., N, ...)`: acquires `decryptLock`, `window.Check(N)` returns true (unseen), releases lock, begins `DecryptDanger`.
4. Before goroutine A reaches `window.Update(N)`, goroutine B calls `Decrypt(..., N, ...)` for the duplicate packet: acquires `decryptLock`, `window.Check(N)` still returns true (bit not yet set), releases lock, begins `DecryptDanger`.
5. Both A and B successfully decrypt (same deterministic AEAD operation) and both eventually call `window.Update(N)`; the second `Update` call returns `false` (duplicate) but by then the plaintext from B has already been produced and, depending on the caller's handling of the decrypted output, may be delivered to the TUN device before the `ErrAlreadySeen` check on `Update` even runs, since `Decrypt`'s caller only inspects the *return value*, not a pre-decrypt guarantee of exclusivity. 	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}

}

}
