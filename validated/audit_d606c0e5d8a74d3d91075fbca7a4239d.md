### Title
Fee-on-transfer collateral breaks msdTOKEN-to-underlying solvency: `Treasury.pull` / `DepositToken._withdraw` credit full amount while delivering less - ([File: contracts/Treasury.sol])

### Summary
The Allo report describes a bug class where token transfers that burn/deduct a fee in transit desynchronize internal accounting from actual token balances. Metronome already applies the recommended fix on the **deposit** side (`DepositToken.deposit` measures `balanceAfter - balanceBefore`), but the symmetric vulnerability remains on the **withdraw** side: `DepositToken._withdraw` burns the full `_withdrawn` msdTOKEN amount and `Treasury.pull` executes a plain `safeTransfer(to_, amount_)`, so a fee-on-transfer underlying delivers strictly less than what the protocol accounts for.

### Finding Description
`DepositToken._withdraw` (contracts/DepositToken.sol:536-554) quotes the withdraw fee in **msdTOKEN units**, burns `_withdrawn` from the user, and calls `Treasury.pull(to_, _withdrawn)`:

```solidity
_burn(account_, _withdrawn);
_pool.treasury().pull(to_, _withdrawn);
```

`Treasury.pull` (contracts/Treasury.sol:66-72) then does:

```solidity
IDepositToken(_msgSender).underlying().safeTransfer(to_, amount_);
```

It transfers `amount_` but never verifies how much `to_` actually received. If the whitelisted collateral token charges a transfer fee (e.g. USDT-style fee tokens, deflationary tokens), the recipient gets `amount_ - fee` while the protocol permanently records a withdrawal of `amount_` (msdTOKEN burned, `totalSupply` reduced, `pool.removeFromDepositTokensOfAccount` bookkeeping done).

The same class appears in `VesperGateway.deposit` (contracts/VesperGateway.sol:51-57): it pulls `amount_` of the Vesper underlying with `safeTransferFrom` without a balance delta, then calls `vToken_.deposit(amount_)`, which will attempt to pull the full `amount_` from the gateway — reverts when only `amount_ - fee` arrived (or pulls the surplus if the gateway holds a prior balance). Contrast with the properly handled inbound path at `DepositToken.deposit` (contracts/DepositToken.sol:225-227) and `SmartFarmingManager._safeTransferFrom` (contracts/SmartFarmingManager.sol:257-261), which both measure balance deltas.

### Impact Explanation
Each withdrawal of a fee-on-transfer collateral leaves the Treasury holding fewer underlying tokens than `DepositToken.totalSupply` claims. The deficit accumulates silently; eventually `underlying.balanceOf(treasury) < totalSupply`, and the last withdrawers' `Treasury.pull` reverts on insufficient balance — a permanent freezing of user funds and a break of the msdTOKEN⇄underlying solvency invariant. It also breaks `Treasury.claimFromVesper`'s surplus calculation (`_amount -= _depositToken.totalSupply()`), which over-counts "excess" rewards and can sweep collateral backing. Alternatively, if a FoT token's fee is high, `VesperGateway.deposit` reverts entirely, making the collateral path unusable (liveness).

### Likelihood Explanation
Likelihood is conditional on governance whitelisting a fee-on-transfer or rebasing token as collateral — collateral onboarding is a governor action, but nothing in `addDepositToken` or `DepositToken.initialize` restricts token behavior, and the codebase explicitly anticipates arbitrary ERC20s (balance-delta handling in `deposit`, gateway helpers for any registered pool). Once such a collateral exists, no privileged action is needed: ordinary users calling `depositToken.withdraw(amount, to)` trigger the accounting drift on every transfer out.

### Recommendation
Mirror the inbound fix on the outbound path. In `Treasury.pull`, measure the recipient's balance delta and either (a) revert if `received < amount_`, or (b) propagate the received amount back so `DepositToken._withdraw` only burns what was actually delivered (requires returning a value from `pull` / adjusting the `_burn` order). In `VesperGateway.deposit`, replace `amount_` with the actual received delta (`balanceOf(gateway)` before/after the pull) before approving and calling `vToken_.deposit`. Alternatively, document/enforce that only non-fee tokens may be registered as collateral.

### Proof of Concept
Hardhat sketch (assumes a `FeeTokenMock` that burns `FEE_BPS` on every transfer, deployed and registered via `pool.addDepositToken`):

```ts
// 1. Register FoT token as collateral and deposit
await feeToken.mint(alice.address, parseEther('100'))
await feeToken.connect(alice).approve(msdFoT.address, MaxUint256)
await msdFoT.connect(alice).deposit(parseEther('100'), alice.address)
// deposit() measures delta -> alice gets ~99 msdFoT, treasury holds ~99

// 2. alice withdraws everything
await msdFoT.connect(alice).withdraw(await msdFoT.balanceOf(alice.address), alice.address)

// 3. Assert: alice received less than burned; treasury still holds the missing fee amount
//    Repeat with more users: eventually underlying.balanceOf(treasury) < totalSupply
//    and the final user's withdraw() reverts inside Treasury.pull.
expect(await feeToken.balanceOf(treasury.address)).to.be.gt(0) // unclaimable residue
expect(await msdFoT.totalSupply()).to.be.gt(await feeToken.balanceOf(treasury.address)) // insolvency
```
