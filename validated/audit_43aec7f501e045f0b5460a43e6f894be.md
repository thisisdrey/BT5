### Title
Dangling `PostponedReceipt`/`PendingDataCount` trie entries survive `remove_account`, enabling privilege injection into a recreated account - (File: core/store/src/utils/mod.rs)

### Summary
`remove_account` in `core/store/src/utils/mod.rs` deletes the `Account`, `ContractCode`, `AccessKey`/gas-key, and contract-data trie entries for an account, but never touches `TrieKey::PostponedReceipt` or `TrieKey::PendingDataCount` entries keyed by that same `receiver_id`. Because these keys are addressed purely by `AccountId` and not by any per-incarnation identifier, a postponed receipt armed before deletion remains latent in state and will fire against whatever new account later reuses the same `AccountId`.

### Finding Description
`remove_account` (`core/store/src/utils/mod.rs:505`) explicitly enumerates the state it clears: [1](#0-0) 
It iterates and removes access keys/gas keys and contract data, but there is no corresponding removal of `TrieKey::PostponedReceipt { receiver_id }` or `TrieKey::PendingDataCount { receiver_id }` records for the account being deleted.

Postponed receipts are created when an `ActionReceipt` is delivered to an account but has an unresolved `input_data_id`; the runtime persists the receipt under `TrieKey::PostponedReceipt{receiver_id}` and tracks the number of outstanding data dependencies under `TrieKey::PendingDataCount{receiver_id}`, both keyed solely by `AccountId` (`core/primitives/src/trie_key.rs`). When the matching `DataReceipt` is later delivered, the runtime (`runtime/runtime/src/lib.rs`) decrements the pending count and, once it reaches zero, resurrects the postponed `ActionReceipt` and executes its actions against whatever account currently exists at `receiver_id` — it does not re-validate that the account is the same incarnation that originally received the postponed receipt.

Exploit flow:
1. Attacker controls account `A` and sends itself (`predecessor_id == receiver_id == A`) an `ActionReceipt` containing `AddKey(FullAccess, attacker_key)`, with an artificially unresolved `input_data_id` (e.g. via a cross-contract call whose callback never completes), causing it to be stored as `PostponedReceipt{receiver_id: A}` / `PendingDataCount{receiver_id: A}`.
2. Attacker submits `DeleteAccount` for `A` with a different beneficiary. `action_delete_account` calls `remove_account`, which clears the `Account`/keys/code but leaves the postponed receipt and pending-count rows intact.
3. A third party (unaware of the dangling state) later recreates an account named `A` — e.g., a registrar creating a fresh top-level account, or the original parent creating the sub-account again — and deploys a benign contract.
4. Attacker (holding the original `data_id`) delivers the matching `DataReceipt`.
5. The runtime resolves the pending count to zero and executes the resurrected `ActionReceipt` against the new `A`. Since the receipt's `predecessor_id == receiver_id == A`, `check_actor_permissions` in `runtime/runtime/src/actions.rs` treats this as a self-call and authorizes `AddKey(FullAccess)` unconditionally, inserting the attacker's key into the new owner's account.

This breaks the stated invariant that a promise never carries privileges its creator did not hold and that only the account's own key set is ever inserted — here, a *former* owner's manufactured promise is granted against a *new*, unrelated owner purely because `AccountId` was reused and identity was not scoped to account existence/incarnation.

### Impact Explanation
This is authorization escalation across accounts: an attacker can plant a "time bomb" `AddKey(FullAccess)` promise, delete the account, and have it detonate against any future, unrelated party who reuses the same `AccountId`, granting the attacker full control of that account. This matches the "authorization escalation across accounts / theft of account control" bounty category.

### Likelihood Explanation
Preconditions are attacker-controlled: creating an unresolved cross-contract dependency, self-delivering an `ActionReceipt` with `AddKey`, and deleting one's own account are all ordinary unprivileged operations available to any funded account. The only external dependency is a third party recreating the exact same `AccountId` later (plausible for short/desirable top-level names via the registrar, or for sub-accounts recreated by the same parent). Cost to the attacker is limited to storage staking/gas for the setup steps. It is repeatable for any account name the attacker can arrange to have reused.

### Recommendation
`remove_account` should also purge all `TrieKey::PostponedReceipt{receiver_id}` and `TrieKey::PendingDataCount{receiver_id}` entries for the account being deleted (and refund/burn associated deposits as appropriate), mirroring how it already clears access keys and contract data, so that no dangling authorized action can be resurrected against a differently-owned future account with the same name.

### Proof of Concept
Runtime/test-loop integration test:
1. Create account `A` with owner key `K1`.
2. From `A`, send an `ActionReceipt` to `A` (`predecessor_id == receiver_id == A`) containing `AddKey(FullAccess, attacker_key)` with an `input_data_id` for which no `DataReceipt` has been delivered yet, forcing it to be stored as postponed (`PostponedReceipt`/`PendingDataCount` present in state — verifiable via `TrieUpdate` inspection or `state-viewer`).
3. Submit `DeleteAccount(A, beneficiary=other)` signed by `K1`; confirm `Account`, `AccessKey` records for `A` are gone, but query state directly (or via `tools/state-viewer`) to confirm `PostponedReceipt{A}`/`PendingDataCount{A}` still exist.
4. Recreate account `A` under a different actor/key `K2` (e.g. via `CreateAccount` from the registrar or original parent), and deploy a benign contract.
5. Deliver the matching `DataReceipt` for the earlier `input_data_id`.
6. Assert `get_access_key(A, attacker_key)` returns `Some(FullAccess)`, proving the attacker gained a full-access key on the new account never authorized by `K2`.
