Found it: `handleRecvError` in `outside.go` is a strong analog to the price-deviation bug. Both are "sanity checks meant to prevent spoofing/manipulation that are too permissive to actually stop an attacker."

### Title
Unauthenticated `RecvError` packet can tear down an established tunnel via an insufficient source-check - (File: outside.go)

### Summary
`RecvError` (`header.RecvError`) is processed entirely unauthenticated — it arrives before any certificate, HMAC, or AEAD check, exactly like the `MAX_PRICE_DEVIATION_FROM_PREVIOUS_ROUND` check that ran on unvalidated/attacker-influenced input. The only "sanity check" guarding it is a same-as-recorded-source-IP comparison, which is spoofable over UDP and provides a far weaker guarantee than the comment ("Someone spoofing recv_errors?") implies — mirroring the price-deviation bug's false sense of security from a check that looks protective but leaves a wide bypass window.

### Finding Description
`readOutsidePackets` dispatches `header.RecvError` packets straight to `f.handleRecvError` with zero authentication — no HMAC, no cert, no AEAD tag: [1](#0-0) 

`handleRecvError` looks up the hostinfo by `h.RemoteIndex` (an attacker-guessable/observable 32-bit value carried unencrypted on every packet) and performs a single "sanity" check: does the packet's source address equal the address currently recorded for that hostinfo: [2](#0-1) 

This is analogous to the `_chainlinkPriceChangeAboveMax()` bug: a check is present that looks like it defends against manipulation ("Someone spoofing recv_errors?"), but the guard is checking the wrong/insufficient property. UDP source addresses are trivially spoofable by any off-path or on-path attacker who can send a packet with a forged source IP toward the target's listen port; there is no cryptographic binding between the `RemoteIndex` and the sender the way `MAX_PRICE_DEVIATION_FROM_PREVIOUS_ROUND` claims to bind consecutive rounds but actually leaves a 49% gap. Here, the "check" leaves a 100% gap for any attacker who can spoof the peer's known IP:port (which is not secret — it's visible in traffic, in lighthouse announcements, etc.), or who is on-path/can race a legitimate response.

If the spoofed source matches the currently recorded remote (`hr == addr`), the check passes and:
```go
f.closeTunnel(hostinfo)
f.handshakeManager.DeleteHostInfo(hostinfo)
```
executes — tearing down a live, authenticated tunnel and forcing a full re-handshake, with zero possession of any credential, exactly as the price-deviation bug allowed an attacker with a plausible-but-manipulated value to bypass validation and disrupt price integrity.

### Impact Explanation
An attacker with no CA-signed certificate can remotely disrupt any established Nebula tunnel by spoofing a single unauthenticated UDP packet whose source address matches the known remote endpoint of a target hostinfo. This is a remote state-poisoning / denial-of-service impact: it forcibly tears down the connection-state (`closeTunnel` + `DeleteHostInfo`) and invalidates the handshake state, requiring a full re-handshake and causing traffic loss/tunnel flapping. Repeated spoofed `RecvError` floods can be used to persistently deny service on a target tunnel. This is consistent with the categories accepted by the validation rules (remote state poisoning / firewall-adjacent authentication bypass at the transport layer), because the entire code path executes before any cert or AEAD verification.

### Likelihood Explanation
Likelihood is elevated by:
- `RemoteIndex` is transmitted in the clear on every packet, making it observable to any on-path attacker and guessable/brute-forceable off-path (32-bit space, but only ~random values are actually allocated so entropy is meaningful but not decisive against a targeted flood).
- The remote UDP `addr:port` of a peer is not secret information (it appears in lighthouse responses and in any observed traffic), so spoofing the expected source is straightforward for both on-path and off-path (source-IP-spoofing capable) attackers.
- `f.acceptRecvErrorConfig` defaults can allow `RecvError` handling broadly (`recvErrorAlways`), and the code explicitly documents this as a known trade-off in `recvErrorConfig`, but the source-IP equality check is the only defense and is not a strong authentication mechanism.
- The code path requires no valid Nebula certificate, no handshake completion, and no CA trust — it is reachable by a completely unauthenticated party.

### Recommendation
Do not rely on UDP source-IP equality as an anti-spoofing control for a state-destroying operation. Either:
1. Remove/deprecate `RecvError`-triggered `closeTunnel` entirely (or gate it strictly behind `recvErrorConfig`'s most conservative setting) and instead rely on the connection manager's existing dead-tunnel detection (test packets / timeouts), which already tolerates loss without needing an unauthenticated fast path; or
2. Require a lightweight authenticated proof (e.g., an HMAC keyed by the still-known session key associated with `RemoteIndex`) before honoring a `RecvError`, rather than trusting the observed source address; or
3. At minimum, rate-limit and require multiple corroborating recv-errors from otherwise-consistent traffic before tearing down state, similar to raising `MAX_PRICE_DEVIATION_FROM_PREVIOUS_ROUND` to a tighter, harder-to-satisfy bound in the original report.

### Proof of Concept
1. Attacker observes (or learns via a lighthouse query, which is also largely unauthenticated for unknown-vpn-addr lookups) the current UDP `ip:port` that node A uses to reach node B, and B's `RemoteIndex` value for the tunnel with A (visible in any packet header exchanged, e.g. by passively sniffing traffic on the path or by triggering a handshake/test packet).
2. Attacker crafts a UDP packet with header `Version=1, Type=header.RecvError, RemoteIndex=<observed index>`, and spoofs the IP source to match A's known address (`hr`), sending it to B's listen port.
3. B's `readOutsidePackets` dispatches to `handleRecvError` without any certificate/HMAC/AEAD check, looks up the hostinfo by `RemoteIndex`, compares the spoofed source to `hr`, finds them equal, and calls `f.closeTunnel(hostinfo)` plus `hm.DeleteHostInfo(hostinfo)`.
4. The legitimate A↔B tunnel is torn down and must fully re-handshake, achieved entirely by an attacker holding no CA-signed certificate and no cryptographic material for the tunnel.

func (f *Interface) handleRecvError(addr netip.AddrPort, h *header.H) {
	if !f.acceptRecvErrorConfig.ShouldRecvError(addr) {
		f.l.Debug("Recv error received, ignoring",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
		return
	}

	if f.l.Enabled(context.Background(), slog.LevelDebug) {
		f.l.Debug("Recv error received",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
	}

	hostinfo := f.hostMap.QueryReverseIndex(h.RemoteIndex)
	if hostinfo == nil {
		f.l.Debug("Did not find remote index in main hostmap", "remoteIndex", h.RemoteIndex)
		return
	}

	hr := hostinfo.GetRemote()
	if hr.IsValid() && hr != addr {
		f.l.Info("Someone spoofing recv_errors?",
			"addr", addr,
			"hostinfoRemote", hr,
		)
		return
	}

	f.closeTunnel(hostinfo)
	// We also delete it from pending hostmap to allow for fast reconnect.
	f.handshakeManager.DeleteHostInfo(hostinfo)
}
