### Title
Unsolicited StackerDB push chunk is ACKed via patched `ChunksInv` before the chunk is actually persisted, breaking the "advertised == stored" equality - (File: `stackslib/src/net/stackerdb/mod.rs`)

### Summary
`PeerNetwork::handle_unsolicited_StackerDBPushChunk` validates an unsolicited `StackerDBPushChunkData` (signature, size, staleness, write-count) and, on success, optimistically patches the in-memory `StackerDBChunkInvData.slot_versions` entry to the *pushed* `slot_version`, signs and immediately sends this patched inventory back to the sender as a positive acknowledgment — all before the chunk is ever handed off to the storage layer. Actual persistence (`try_replace_chunk`) only happens afterward, when the message is forwarded to the relayer (`Ok((false, true))`). This is structurally the same class of bug as the Paladin finding: a quantity ("accepted"/"allocated") is recorded and advertised as final while the real state-changing operation (actual write / actual allocation) is deferred and not guaranteed to match.

### Finding Description
In `stackslib/src/net/stackerdb/mod.rs`: [1](#0-0) 
the `StackerDBChunkInv` branch runs `validate_received_chunk` (which only checks signature/size/version/max-writes — explicitly *not* write frequency, per the doc comment) and then does:
```
*slot_version = chunk_data.chunk_data.slot_version;
```
directly mutating the reply payload's inventory to claim the new version is now held, before any DB write occurs.

Then, back in the caller: [2](#0-1) 
if `send_reply` is true, this patched, "accepted" inventory is signed and sent straight back to the peer that pushed the chunk — and the function returns `Ok((false, true))`, meaning "forward the chunk to the relayer for eventual storage." The actual write into the StackerDB slot (`StackerDBTx::try_replace_chunk`, in `stackslib/src/net/stackerdb/db.rs:400-438`) happens later, asynchronously, in the relay pipeline, and is subject to independent failure modes (stale version race against a concurrent write, DB error, contract/config having changed between validation and commit, etc.): [3](#0-2) 

Because the acknowledgment/inventory update is emitted based purely on `validate_received_chunk`'s in-memory judgement rather than on a confirmed, committed write, the peer receiving the ACK has no guarantee that the local node's `StackerDB` slot actually reflects the advertised `slot_version`. This is the direct analog of the Paladin bug: an amount ("the chunk is now this version, held by me") is counted/advertised as finalized while the corresponding "commit" step (the real DB transaction) is decoupled and may never happen or may fail — a duplication/inconsistency between the *advertised* ledger state and the *actual* ledger state.

### Impact Explanation
This breaks the "served == committed" invariant needed for `StackerDBChunkInv` correctness. `StackerDBChunkInv` inventories are used by `StackerDBSync` to build the rarest-first / newest-first download schedule and to decide which neighbors already hold which slot version. A node that advertises a version it does not yet (or may never) actually hold can:
- cause peers to treat this node as an already-up-to-date source and de-prioritize/skip re-fetching that slot version from other replicas, letting the update quietly fail to propagate network-wide, and
- serve stale/non-canonical slot data as canonical in subsequent `StackerDBChunk` reply/download-schedule bookkeeping, since `stacker_db_sync.wakeup()` is triggered assuming the store succeeded.

This matches the "High: serving non-canonical state as canonical / steering peers via false inventory" impact category — it does not require any secret key, admin role, or traffic volume; a single properly-signed push chunk racing a legitimate concurrent write (or hitting any transient storage error) is sufficient to desynchronize advertised vs. actual state.

### Likelihood Explanation
Any unauthenticated (but must be signed by the slot's registered signer — remote/unprivileged, no node secret needed) peer can push a `StackerDBPushChunkData` chunk. The race window between validation and the deferred relay-driven commit is a normal, always-present code path (not a rare edge case), so the mismatch condition is reachable by ordinary network conditions (e.g., two writers racing to update the same slot, or one write closely following another so the "stale version" check fails at commit time after the optimistic ACK already went out).

### Recommendation
Do not patch and send the `ChunksInv` acknowledgment optimistically. Either (a) perform/attempt the actual `try_replace_chunk` write synchronously before constructing/sending the ACK inventory (and only advertise the version that was actually committed), or (b) make the relayer's actual commit path notify back with a corrected/authoritative inventory if the deferred write fails, so peers can recover instead of trusting a stale ACK indefinitely.

### Proof of Concept
1. Node `A` connects to `B`, and both host StackerDB contract `SC` with slot `S` currently at version `V`.
2. Attacker (holder of slot `S`'s signing key) sends `B` two valid, signed `StackerDBPushChunkData` messages for slot `S`: chunk1 with version `V+1`, chunk2 with version `V+1` (duplicate) or `V+2`, nearly simultaneously.
3. `B::handle_unsolicited_StackerDBPushChunk` runs `validate_received_chunk` for both against the same `expected_versions` snapshot (both pass, since neither has yet been committed), patches its outgoing `ChunksInv` for each to claim `slot_version = V+1` (and `V+2`), and sends both ACKs back to the attacker/relaying peer.
4. Both chunks are forwarded to the relayer for actual storage; only one write can win (`try_replace_chunk` rejects the second with `StaleChunk` per `stackslib/src/net/stackerdb/db.rs:424-429`).
5. `B` has already advertised (via signed `ChunksInv`) that it holds version `V+2` (or both versions at different times), while its committed DB state only ever reaches `V+1`. Any third node querying `B`'s inventory based on that advertisement will believe `B` is caught up to `V+2` and skip fetching the real update from elsewhere, propagating stale/non-canonical inventory data.

    /// Add or replace a chunk for a given reward cycle, if it is valid
    /// Otherwise, this errors out with Error::StaleChunk
    pub fn try_replace_chunk(
        &self,
        smart_contract: &QualifiedContractIdentifier,
        slot_desc: &SlotMetadata,
        chunk: &[u8],
    ) -> Result<(), net_error> {
        // Check per-replica chunk-size cap.
        if (chunk.len() as u64) > self.config.chunk_size {
            return Err(net_error::StackerDBChunkTooBig(chunk.len()));
        }

        let slot_validation = self
            .get_slot_validation(smart_contract, slot_desc.slot_id)?
            .ok_or(net_error::NoSuchSlot(
                smart_contract.clone(),
                slot_desc.slot_id,
            ))?;

        if !slot_desc.verify(&slot_validation.signer)? {
            return Err(net_error::BadSlotSigner(
                slot_validation.signer,
                slot_desc.slot_id,
            ));
        }
        if slot_desc.slot_version <= slot_validation.version {
            return Err(net_error::StaleChunk {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
            });
        }
        if slot_desc.slot_version > self.config.max_writes {
            return Err(net_error::TooManySlotWrites {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
                max_writes: self.config.max_writes,
            });
        }
        self.insert_chunk(smart_contract, slot_desc, chunk)
    }
