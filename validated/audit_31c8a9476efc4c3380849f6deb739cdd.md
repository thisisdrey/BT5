### Title
Colluding peers with forged inventory bits and inflated reliability scores are preferentially selected as attachment sources with no content-hash cross-validation - (File: stackslib/src/net/atlas/download.rs)

### Summary
`AttachmentsBatchStateContext::get_prioritized_attachments_requests` builds the `sources` map for a missing attachment purely from peer-advertised inventory bits in `GetAttachmentsInvResponse`, with no check against actual attachment content. `AttachmentRequest::get_most_reliable_source`/`get_url` then picks the source with the highest `ReliabilityReport::score()`, and the resulting response is merged into `self.attachments` by `extend_with_attachments` with no hash-equality check against `content_hash`.

### Finding Description
In `get_prioritized_attachments_requests` (stackslib/src/net/atlas/download.rs:404-478), for each missing `(attachment_index, content_hash)`, the code iterates `peers_responses` and adds `peer_url` to `sources` solely because `response.pages[...].inventory[position_in_page] == 1` [1](#0-0) . This bit comes straight from an unauthenticated peer's `GET /v2/attachments/inv` response and is never checked against real attachment bytes. Any independent, unprivileged peer can serve this endpoint and set the bit for a slot it doesn't actually hold correct content for.

`AttachmentRequest::get_most_reliable_source` (download.rs:1074-1079) then does `self.sources.iter().max_by_key(|(_, v)| v.score())`, and `Requestable::get_url` for `AttachmentRequest` (download.rs:1104-1108) uses this to pick which peer's URL the follow-up `GET /v2/attachments/<hash>` is sent to. `ReliabilityReport::score()` is derived purely from the local `reliability_reports` history of successful/failed *requests* (bumped in `extend_with_inventories`/`extend_with_attachments` on request success/failure, not on content correctness), so a peer can build up a high score by simply always answering promptly and validly-formatted (even if with wrong bytes).

Finally, `extend_with_attachments` (download.rs:530-558) takes the response from whichever peer was selected, decodes it via `decode_atlas_get_attachment()`, and unconditionally does `self.attachments.insert(response.attachment)` [2](#0-1)  — there is no comparison of `Attachment::hash()` against `request.content_hash` anywhere in this function. This confirms the equality the question is probing (`Attachment::hash() == content_hash`) is never checked at the point of merging the downloaded attachment into local state, and source selection upstream is entirely decoupled from any correctness signal.

### Impact Explanation
An attacker who runs one or more independent peer processes (no privileged role required — any P2P-reachable peer that a node syncs Atlas attachments with) can: (1) advertise a forged "have it" bit for the specific missing `(page_index, position_in_page)` slot via `/v2/attachments/inv`; (2) build/maintain a favorable `ReliabilityReport` score simply by answering requests promptly; (3) be selected via `get_most_reliable_source` as the request target; (4) respond to `GET /v2/attachments/<hash>` with attacker-chosen bytes whose Hash160 does not match `content_hash`. Because `extend_with_attachments` never checks `Attachment::hash() == content_hash`, wrong attachment content is persisted/associated with the legitimate `content_hash`/BNS name commitment. This is a High-severity "attachment/BNS mismatch" — the node ends up treating attacker-supplied content as if it corresponds to a canonical name/zonefile commitment, without ever verifying the cryptographic binding that the whole Atlas attachment design depends on.

### Likelihood Explanation
Preconditions are minimal: the attacker needs to run one or more peers that the victim node includes in `get_outbound_sync_peers()`/considers for Atlas inventory sync — no secret, no StackerDB ownership, no privileged role. The attacker only needs to answer HTTP requests correctly-formatted enough to avoid `bump_failed_requests()`, and to serve a forged inventory bit and mismatched attachment bytes. This is fully repeatable per missing attachment slot and requires no special network position; it is a natural consequence of decoupled selection (best-reported peer) from content verification (never done).

### Recommendation
In `extend_with_attachments`, after `decode_atlas_get_attachment()` succeeds, compute `response.attachment.hash()` and compare it to `request.content_hash` before inserting into `self.attachments`; on mismatch, call `report.bump_failed_requests()` and drop the attachment (and consider deregistering/penalizing the offending peer). Optionally, cross-validate inventory-bit claims by fetching from multiple sources when available and preferring/only accepting a response once hash-verified, rather than relying solely on `ReliabilityReport::score()` for source trust.

### Proof of Concept
Rust test plan (in `stackslib/src/net/atlas/tests.rs` or a new test module):
1. Construct an `AttachmentsBatchStateContext` with two peers, `peer_good` and `peer_evil`, and a `ReliabilityReport` for `peer_evil` with a higher `score()` (e.g., more `bump_successful_requests()` calls) than `peer_good`.
2. Populate `self.inventories` so both peers report `inventory[position_in_page] == 1` for the target `(page_index, position_in_page)` mapping to a known `content_hash`.
3. Call `get_prioritized_attachments_requests()` and assert the returned `AttachmentRequest.get_most_reliable_source()` returns `peer_evil`'s URL (confirming selection is driven purely by score, not correctness).
4. Simulate `BatchedRequestsState::Done` with `results.succeeded` containing a response from `peer_evil` whose `Attachment` bytes hash to a value `!= content_hash`.
5. Call `extend_with_attachments(&mut results)` and assert that `context.attachments` now contains the forged `Attachment` (i.e., `context.attachments.iter().any(|a| a.hash() != content_hash)` is true) — demonstrating the missing equality check at the exact site `stackslib/src/net/atlas/download.rs:547-552`.
