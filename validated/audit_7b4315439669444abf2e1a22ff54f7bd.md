### Title
Non-constant-time authorization comparison enables timing side-channel to recover RPC broadcast secret - (File: stackslib/src/net/api/postblock_v3.rs)

### Summary
`RPCPostBlockRequestHandler::try_parse_request` compares the client-supplied `authorization` header against the configured secret using Rust's built-in `String`/`&str` `PartialEq` (`auth_header != password`), which is not guaranteed constant-time and can short-circuit on the first mismatching byte. A remote, unauthenticated attacker who can reach the `/v3/blocks/upload/?broadcast=1` RPC endpoint can exploit per-byte timing differences to incrementally reconstruct the secret without ever possessing it.

### Finding Description
The equality check occurs at: [1](#0-0) 

```rust
if let Some(password) = &self.auth {
    if let Some(auth_header) = preamble.headers.get("authorization") {
        if auth_header != password {
            return Err(Error::Http(401, "Unauthorized".into()));
        }
        authenticated = true;
    }
}
```

`auth_header != password` invokes the standard `str`/`String` equality implementation, which is a byte-wise comparison that is free to return as soon as a mismatch is found (it is not designed nor documented to run in constant time, unlike e.g. `subtle::ConstantTimeEq`). This means the wall-clock time to reject an incorrect `authorization` header can depend on how many of its leading bytes match `self.auth`. An attacker who can query this endpoint repeatedly (no credential needed to send the request — the endpoint is reachable pre-authentication, since the auth check itself is what's being probed) can use statistical timing analysis to determine the secret byte-by-byte, eventually constructing a value that satisfies `auth_header == password` and passes the `broadcast=1` authenticated gate at line 120, granting them the ability to force this node to relay/broadcast attacker-supplied Nakamoto blocks it would otherwise reject as unauthenticated.

No other guard in this path (content-length checks, `MAX_PAYLOAD_LEN` check, content-type check) touches the comparison itself, so once the timing side-channel yields the secret, `authenticated = true` is set and `broadcast && !authenticated` no longer trips, bypassing the intended authorization gate at lines 120-122.

### Impact Explanation
Successful exploitation lets an unprivileged remote attacker recover the RPC broadcast secret (`self.auth`) and then submit unauthenticated data as if authenticated, gaining the ability to force block broadcast/relay via `node.set_relay_message` at line 199 through a path intended to require the secret. This is an auth-bypass primitive against a specific RPC gate, matching the Critical category ("...auth bypass") in the rules. It is repeatable indefinitely (each probe request costs the attacker only a new HTTP POST) and the endpoint is remotely reachable with no privileged role required to send the initial probing traffic.

### Likelihood Explanation
Preconditions: the node must have `self.auth` (a broadcast secret) configured — this is normal deployment configuration for nodes exposing `/v3/blocks/upload/`, and the endpoint must be reachable over the network, which it is by design (it's the block-upload RPC). No peer/config/tip state beyond a running node with `auth` set is required. Cost to the attacker is bandwidth and time for many timing-sampled requests; classic remote timing side-channels against short secrets over HTTP are non-trivial due to network jitter but are an established, real class of attack (well documented, e.g. against string-compare-based token checks), and the underlying code fault (`!=` on secret material) is unambiguous and directly present in the reachable handler.

### Recommendation
Replace the direct `!=`/`==` comparison on `auth_header` and `password` with a constant-time comparison, e.g. using the `subtle` crate's `ConstantTimeEq` on the byte representations (after first checking length in constant time or padding), or `ring::constant_time::verify_slices_are_equal`. Apply the same fix to the structurally identical pattern in `postblock_proposal.rs`, `fastcallreadonly.rs`, `blockreplay.rs`, `blocksimulate.rs`, and `txsimulate.rs`, all of which perform the same non-constant-time secret comparison.

### Proof of Concept
In `stackslib/src/net/api/tests/postblock_v3.rs` (or a new integration test under `stackslib::net`):
1. Construct an `RPCPostBlockRequestHandler::new(Some("correct_secret_of_length_N".to_string()))`.
2. Build a `HttpRequestPreamble` with an `authorization` header set to strings with 0, 1, 2, ..., N-1 correct leading bytes followed by incorrect bytes (e.g. `"Xorrect_secret..."`, `"cXrrect_secret..."`, etc.), each fed to `try_parse_request`.
3. Measure wall-clock time (using `std::time::Instant`) for many repetitions of each candidate, discard outliers, and compute mean/median per candidate.
4. Assert (or, without timing infra, statically assert via code inspection) that time increases monotonically with the number of correct leading bytes, demonstrating the `auth_header != password` branch at `stackslib/src/net/api/postblock_v3.rs:106` is the non-constant-time comparison responsible — the exploitable code path is this exact `!=` operator on `self.auth`/`auth_header`.
