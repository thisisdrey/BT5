Based on my investigation, the qutebrowser advisory describes a URL-handler argument-injection flaw (CWE-88): a crafted `qutebrowser://` URL passed to the browser binary is misparsed as command-line flags, letting an attacker who can get the victim to click a link achieve code execution. To find an analog in `Kohvert/go--017`, I looked for any Go entry point that (a) receives untrusted/attacker-influenced data and (b) forwards it as a bare argument to an external browser/VCS/tool process without an explicit `--` separator or validation that it can't be interpreted as a flag.

The closest candidates I found were:

- `src/cmd/internal/browser/browser.go` `Open(url string)` [1](#0-0) , which builds `exec.Command(args[0], append(args[1:], url)...)` and appends the URL as the last, unguarded argument.
- Its callers: `src/cmd/go/internal/web/http.go`'s `openBrowser`, `src/cmd/trace/main.go` (`browser.Open(addr)`), and `src/cmd/cover/html.go`, plus `cmd/go/internal/web/api.go`'s `OpenBrowser` wrapper used by `cmd/go/internal/bug/bug.go` [2](#0-1) .
- `src/cmd/go/internal/vcs/vcs.go` `run1`, which builds VCS command arguments from a template plus caller-supplied key/value substitutions and executes them via `exec.Command(v.Cmd, args...)` [3](#0-2) .

However, in every case I could inspect, the "untrusted" value involved (`addr` in `cmd/trace`, local file paths in `cmd/cover`, the fixed `pkgsite`/bug-report URL in `cmd/go/internal/bug`, or VCS-defined repo root URLs) is either generated locally by the Go tool itself or is a value the user already explicitly supplied on their own command line — not data supplied by a remote, unprivileged third party consumed through an ordinary passive workflow (e.g., visiting a webpage or opening a received file), which is the premise required by the report (an attacker crafting a URL that an unsuspecting victim opens). I could not identify a Go standard-library or `cmd/go` entry point where a remote/unauthenticated party's input flows unvalidated into `browser.Open` or an equivalent `exec.Command` argument list under a normal victim workflow. `net/url.parse` and `html/template`'s `isSafeURL`/`urlFilter` [4](#0-3)  correctly implement scheme allow-listing and don't exhibit an analogous flaw — they are the *type* of code that would need to be bypassed for this bug class, not the vulnerable sink itself.

Given the scope of files actually indexed for this repo, I was unable to fully trace every caller chain into `openBrowser`/`browser.Open` (e.g., `cmd/go/internal/web/bootstrap.go`) to rule out all reachability paths with full confidence; if a deeper audit is desired, a Devin session with full filesystem access to `Kohvert/go--017` would be needed to trace every call site and confirm none involve attacker-controlled URLs from an untrusted network peer.

### No vulnerability found for this question.

func Open(url string) bool {

}

// isSafeURL is true if s is a relative URL or if URL has a protocol in
// (http, https, mailto).
func isSafeURL(s string) bool {
	if protocol, _, ok := strings.Cut(s, ":"); ok && !strings.Contains(protocol, "/") {
		if !strings.EqualFold(protocol, "http") && !strings.EqualFold(protocol, "https") && !strings.EqualFold(protocol, "mailto") {
			return false
		}
	}
	return true
}
