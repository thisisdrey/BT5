Based on the investigation, java-tron is written in Java, which is memory-safe — a literal "global buffer overflow" resulting in RCE (as in the TightVNC C code) cannot occur. The closest reachable analog is an **unchecked/attacker-controlled offset used directly in `System.arraycopy`**, which is the same bug class (missing bounds validation on network-supplied length/offset fields before a raw memory copy) but manifests in Java as an uncaught `ArrayIndexOutOfBoundsException`/`IndexOutOfBoundsException` rather than corrupting memory.

### Title
Unchecked attacker-controlled offsets in `VerifyTransferProof.execute` cause out-of-bounds array access - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The shielded-transfer verification precompile (`VerifyTransferProof`) parses three "unfixed field offsets" (`spendOffset`, `spendAuthSigOffset`, `receiveOffset`) directly from the caller-supplied `data` byte array and then uses them, without any bounds check against `data.length`, to index into `data` for further `parseInt`/`System.arraycopy` calls.

### Finding Description
`execute(byte[] data)` only validates that `data.length` is one of four fixed sizes (`{2080, 2368, 2464, 2752}`) via the `SIZE` array check [1](#0-0) . It then reads three offsets directly from attacker-controlled data: [2](#0-1) 
These offsets (`spendOffset`, `spendAuthSigOffset`, `receiveOffset`) are used unchecked as array indices to call `parseInt(data, spendOffset)` etc., and subsequently as the base for `System.arraycopy(data, spendOffset + 320 * i, ...)` in a loop: [3](#0-2) 
The only validation performed is on the *values* read from those offsets (`spendCount`, `receiveCount` bounded to 1–2) — never on whether the offsets themselves fall within `data.length`. A caller can supply any 2080/2368/2464/2752-byte blob with `spendOffset`/`spendAuthSigOffset`/`receiveOffset` set to out-of-range (including negative) values, causing `parseInt`/`System.arraycopy` to throw `ArrayIndexOutOfBoundsException`. This directly mirrors the CVE-2019-8287 root cause: length/offset fields taken from untrusted input are used to drive raw buffer/array operations without range validation.

### Impact Explanation
This precompile is reached via a normal TVM contract call (any transaction invoking the shielded-TRC20/Sapling `verifyTransferProof` precompiled contract address) — i.e., it is reachable by an unprivileged transaction broadcaster or contract caller. The immediate effect is an unhandled exception during precompile execution. I was not able to fully verify, within the available index, whether this exception is caught by an outer TVM dispatch handler (which would only revert the call, a low-impact outcome) or propagates further; I could not locate a `try/catch` wrapping this specific `execute` method in the snippet retrieved, unlike the other precompiles in the same file (e.g., `VerifyMintProof`, `ECRecover`) which explicitly wrap their bodies in `catch (Throwable any)`. This lack of a visible catch block around `VerifyTransferProof.execute`'s array-index logic is the main uncertainty — if uncaught by the TVM opcode dispatcher, this could crash the node's transaction-processing thread or halt block application; if caught, this is only a reverted/failed contract call (low impact, out of scope per the report's severity floor).

### Likelihood Explanation
Trivial to trigger: any account can craft a transaction invoking the Sapling verify-transfer precompile with a correctly-sized but malformed payload containing out-of-range offset fields. No special privileges are required.

### Recommendation
Validate `spendOffset`, `spendAuthSigOffset`, and `receiveOffset` against `data.length` (and against the minimum required trailing space, i.e., `offset + 320*spendCount <= data.length`, etc.) before performing any `parseInt`/`System.arraycopy` calls, mirroring the bounds checks already present elsewhere in the codebase (e.g., `RLP.verifyLength` at `framework/src/main/java/org/tron/core/capsule/utils/RLP.java:612-617`). Additionally, confirm/add an explicit `catch` around the whole `VerifyTransferProof.execute` body so malformed input cannot escape as an uncaught exception.

### Proof of Concept
Construct a 2080-byte `data` array (smallest valid `SIZE` entry) where the first three 32-byte big-endian integers (`spendOffset`, `spendAuthSigOffset`, `receiveOffset`) are set to a very large value (e.g., `0x7FFFFFFF`) or a value close to `data.length` such that `spendOffset + 320*i` exceeds `data.length`. Submit a transaction/contract call invoking the shielded-transfer verify precompile with this payload; `parseInt(data, spendOffset)` or the subsequent `System.arraycopy` calls at lines 1514-1518 throw `ArrayIndexOutOfBoundsException`.

**Caveat**: Due to index size limits, I could not fully confirm the exception-handling wrapper (or lack thereof) around this exact method body, nor trace the full TVM call-dispatch exception propagation path. Starting a Devin session with full repository access would allow verifying whether this exception is caught at the precompile-dispatch layer (downgrading this to a low-impact revert) or propagates to crash/halt block processing (which would raise this to Critical).
