### Title
Floating-point Bancor-relay math and rounding-down bias in TRC10 Exchange (`ExchangeInjectActuator`/`ExchangeWithdrawActuator`/`ExchangeProcessor`) enable invariant manipulation on low-liquidity pools - ([File: chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java])

### Summary
java-tron's built-in TRC10 "Exchange" (Bancor-style AMM, distinct from any external DEX) computes swap outputs with IEEE‑754 `double` arithmetic by default, and computes liquidity inject/withdraw amounts with a fixed floor-rounding direction that always favors the caller. Both mechanisms are reachable by any unprivileged account through fully permissionless, signed transactions (`ExchangeCreateContract`, `ExchangeInjectContract`, `ExchangeWithdrawContract`, `ExchangeTransactionContract`). This is structurally the same bug class as the Balancer V2 incident: rounding/precision errors in an invariant-based pricing formula, amplified when pool liquidity is extremely low, distort the true exchange rate and can be used to extract value disproportionate to what was deposited.

### Finding Description
1. **Default swap path uses floating-point math.** `ExchangeCapsule.transaction()` selects between `SafeExchangeProcessor` (BigDecimal-based, exact) and `ExchangeProcessor` (double-based) purely based on the `hardenedCalc` flag, which is derived from the chain parameter `allowHardenExchangeCalculation()`: [1](#0-0) 
The unhardened path performs the Bancor relay formula with `double`/`Math.pow`: [2](#0-1) 
Every actuator that invokes a trade forwards `allowHarden()` (a store-level feature flag gated behind a governance proposal) as the `hardenedCalc` argument: [3](#0-2) [4](#0-3) 
This mirrors the Balancer root cause: a pricing/invariant calculation whose precision degrades under floating-point/rounding error, rather than being computed with exact integer/BigDecimal arithmetic end-to-end.

2. **Rounding direction in liquidity inject/withdraw always favors the caller.** `ExchangeInjectActuator` computes the paired-token amount required with plain integer/`floorDiv` truncation, which always rounds the *required* payment down, i.e., in favor of the depositor: [5](#0-4) 
The same floor-division pattern (`BigInteger.divide()` / `BigDecimal.divideToIntegralValue()`, both truncate-toward-zero for positive operands) is used to compute payouts in `ExchangeWithdrawActuator`: [6](#0-5) [7](#0-6) 

3. **No minimum-liquidity floor.** `ExchangeCreateActuator` only requires `firstTokenBalance > 0` and `secondTokenBalance > 0` — there is no minimum-liquidity/dead-shares protection comparable to what most AMMs enforce: [8](#0-7) 
Since `ExchangeCreateContract` is unprivileged (any funded account can call it, and it can pair TRX with any TRC10 the caller has, including self-issued tokens), an attacker can trivially create an extremely low-liquidity pool. `ExchangeTransactionActuator`, which performs the actual swap, does not check pool ownership, so any unprivileged account can subsequently trade against that pool: [9](#0-8) 

Combined, this is exactly the Balancer bug class: a formula whose rounding/precision behavior is only "close enough" under normal liquidity, but whose error term becomes a significant fraction of trade size at very low balances, allowing the invariant/price to be distorted through crafted small transactions that a single unprivileged transaction broadcaster can construct end-to-end (create pool → inject/withdraw to bias ratio → trade against the distorted price).

### Impact Explanation
If the floating-point drift or rounding bias can be driven to systematically extract more of the counter-token than is economically justified (verifiable only through exact numerical/differential testing of `ExchangeProcessor` vs. the true Bancor formula at boundary values, which requires runtime experimentation not possible from static review alone), the impact is direct value extraction from Exchange pool balances — i.e., unauthorized draining of asset/TRX balances the pool holds, which fits "theft of funds" / "unbacked balance" per the validation criteria. Because `ExchangeCreateContract`/`ExchangeInjectContract`/`ExchangeWithdrawContract`/`ExchangeTransactionContract` are all ordinary signed transactions with no special privilege requirement (beyond being the pool's own creator for inject/withdraw, which the attacker controls by being the creator), this is reachable purely through the transaction-broadcasting attack surface named in scope.

### Likelihood Explanation
Medium. All preconditions (permissionless pool creation, no minimum liquidity, unprivileged trading against any pool, floor-rounding on inject/withdraw, double-precision swap math on the default/legacy path) are directly confirmed in code. What is **not** independently confirmed in this review is (a) the compile-time/genesis default value of the `allowHardenExchangeCalculation` dynamic parameter (only that it is a governance-gated flag with a hardened alternative path, and that tests explicitly must call `saveAllowHardenExchangeCalculation(1)` to exercise the safe path, implying it is off by default), and (b) a concrete numeric proof-of-concept showing the accumulated rounding/float error crossing a profitable threshold at realistic pool sizes. These require running the exact `ExchangeProcessor`/`SafeExchangeProcessor` code paths with controlled inputs, which is outside static analysis.

### Recommendation
- Confirm the genesis/mainnet default of `allowHardenExchangeCalculation`; if disabled by default, migrate all Exchange math (`ExchangeProcessor`) to the exact `SafeExchangeProcessor` (BigDecimal) path unconditionally, removing the double-precision fallback entirely.
- Enforce a minimum initial liquidity and minimum post-trade/post-withdraw balance for both tokens in `ExchangeCreateActuator`/`ExchangeWithdrawActuator`, analogous to standard AMM "minimum liquidity lock" protections, to prevent extreme low-liquidity pools that amplify rounding error.
- Make inject/withdraw rounding conservative in both directions consistently (round in favor of the pool, not the caller) and add symmetric precision/slippage checks (as already partially present via the `allowHarden` precision check in `ExchangeWithdrawActuator`) to the unhardened path as well, rather than only under a feature flag.
- Add differential/fuzz tests comparing `ExchangeProcessor` (double) output against `SafeExchangeProcessor` (BigDecimal) across a wide range of low-balance inputs to quantify worst-case divergence.

### Proof of Concept
Not independently runnable in this review; the following describes the reachable call sequence that would need to be exercised in a testnet/framework test to confirm exploitability:
1. Attacker calls `AssetIssueContract` (permissionless) to mint a low-supply TRC10 token, then `ExchangeCreateContract` pairing TRX with 1–2 units of that token — passes validation since only `balance > 0` is required [8](#0-7) .
2. Attacker (as pool creator) repeatedly calls `ExchangeInjectContract` with crafted small `quant` values chosen so `floorDiv(secondTokenBalance * tokenQuant, firstTokenBalance)` truncates in the attacker's favor each time [5](#0-4) .
3. Any account (attacker or third party) calls `ExchangeTransactionContract` to trade against the now-skewed pool, with the payout computed via the unhardened `ExchangeProcessor` double-precision formula [2](#0-1) .
4. Repeat at scale to accumulate rounding/precision-derived surplus, mirroring the Balancer "exact-out" rounding-direction exploit amplified by low liquidity.
