Based on my research, I identified a concrete analog of the "partially implemented safeguard due to a field being treated as an on/off switch instead of being properly enforced" bug class in Gitaly's pack-objects resource-limiting path.

### Title
Pack-objects concurrency limiter is bypassed whenever `RemoteIp` is empty, malformed, or resolves to loopback - (File: internal/gitaly/service/hook/pack_objects.go)

### Summary
`packObjectsHook` only routes a `git pack-objects` invocation through the configured concurrency limiter (`runPackObjectsLimited`) when it can parse a non-loopback IP out of the client-supplied `RemoteIp` field of the request. In every other case — empty string, unparsable value, or a loopback address — it falls through to `runPackObjects`, which runs completely unlimited.

### Finding Description
The relevant logic is: [1](#0-0) 

```
ipAddr := net.ParseIP(req.GetRemoteIp())
if ipAddr == nil {
    // Best effort, maybe the remote IP includes source port
    if ip, _, err := net.SplitHostPort(req.GetRemoteIp()); err == nil {
        ipAddr = net.ParseIP(ip)
    }
}
// Ignore loop-back IPs
if ipAddr != nil && !ipAddr.IsLoopback() {
    return s.runPackObjectsLimited(...)
}
return s.runPackObjects(ctx, w, req, args, stdin, cacheKey)
```

This mirrors the reported bug class exactly: a resource/limit-enforcement feature (`PackObjectsLimiting` concurrency limiter, configured server-wide to bound concurrent `git-pack-objects` processes spawned per fetch/clone) is only "partially implemented" — it is gated on a request field (`RemoteIp`) that is not guaranteed to be populated or well-formed for every legitimate call path, rather than being unconditionally applied. Just as the Solidity report's `initialize`/`deployAccount` silently dropped the `value` parameter instead of always forwarding it, this code silently drops the concurrency-limiting parameter whenever the IP heuristic fails, defaulting to the unlimited/no-safeguard code path instead of the safe one.

`RemoteIp` is populated by `gitaly-hooks` (invoked by `git` itself as the `uploadpack.packObjectsHook`) from metadata injected via `WithPackObjectsHookEnv`: [2](#0-1) 

The value is threaded through per-connection/per-request metadata rather than being a hard requirement validated at RPC entry, so any transport or call path where this metadata is absent, empty, or is a loopback address (e.g., a local/relayed connection) causes the limiter to be skipped entirely for that fetch.

### Impact Explanation
`PackObjectsLimiting`/`pack_objects_cache` concurrency limiting exists specifically to bound the number of parallel `git-pack-objects` processes an administrator allows, since these processes are CPU- and memory-intensive (this is the entire rationale documented in `doc/design_pack_objects_cache.md`). If the limiter can be bypassed by any request whose `RemoteIp` cannot be parsed to a non-loopback address, an ordinary user with fetch/clone access can repeatedly trigger unlimited concurrent `git-pack-objects` invocations against a repository, exhausting Gitaly server CPU/memory — a denial-of-service of the RPC handler that the concurrency limit was meant to prevent.

### Likelihood Explanation
Likelihood is Medium: exploitation requires only ordinary fetch/clone privileges (no special access), but it depends on the runtime population of `RemoteIp` actually being empty/unparseable/loopback for a given deployment's transport (e.g., internal/local connections, certain proxy or sidechannel configurations). I could not fully verify from the indexed code whether external, network-originated fetches can reliably produce such a value; this would need to be confirmed by tracing the exact metadata plumbing for each transport (SSH sidechannel vs. smart HTTP) in a running/test environment.

### Recommendation
Do not treat the parseability/loopback-ness of `RemoteIp` as the condition for enabling resource limiting. Concurrency limiting should be applied unconditionally to every `git-pack-objects` invocation dispatched through this hook (using a fallback lock key, such as the repository identity, when no usable per-IP key is available), rather than defaulting to an unlimited execution path when the IP heuristic fails.

### Proof of Concept
Not independently reproduced in this review. The code path enabling the bypass is exactly as cited above; confirming exploitability requires demonstrating, in a live Gitaly deployment, a request/transport for which `req.GetRemoteIp()` is empty, unparsable, or loopback for a client-triggered clone/fetch, then showing that concurrently issuing many such fetches spawns more simultaneous `git pack-objects` processes than `PackObjectsLimiting.MaxConcurrency` allows.
