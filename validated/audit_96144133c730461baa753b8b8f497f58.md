### Title
Bancor-formula floating-point rounding in the TRC10 Exchange lets an attacker drain a pool by swapping back and forth - (File: chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java)

### Summary
The TRC10 `Exchange` feature (an on-chain bancor-style AMM reachable via `ExchangeTransactionContract`) computes swap output using `double`-precision floating point Bancor power functions in `ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply` [1](#0-0) . This is exactly the bug class described in the external report: a swap function whose rounding behavior lets a user profit by swapping asset→quote and quote→asset back, draining the pool. A hardened, `BigDecimal`-based replacement (`SafeExchangeProcessor`) exists [2](#0-1) , but it is only used when the `allowHardenExchangeCalculation` dynamic property/proposal is enabled [3](#0-2) [4](#0-3) , i.e. it is a committee-controlled opt-in, so by default the vulnerable floating-point path remains live.

### Finding Description
`ExchangeCapsule.transaction()` selects between the legacy `ExchangeProcessor` (double math) and `SafeExchangeProcessor` (BigDecimal, "hardened") purely based on the `hardenedCalc`/`allowHarden()` flag [5](#0-4) . The default (non-hardened) `ExchangeProcessor.exchangeToSupply` computes:

```
double issuedSupply = -supply * (1.0 - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, useStrictMath));
long out = (long) issuedSupply;
``` [6](#0-5) 

and `exchangeFromSupply` computes the inverse with exponent `2000.0` [7](#0-6) . Both truncate a `double` to `long`. This is the same numerical pattern (power-law bonding-curve math done in floating point with truncation) that the external report flags as the root cause of asymmetric "swap-in-then-swap-back" profit — floating-point `pow` is not guaranteed to be exactly invertible, and for extreme balance ratios/very small trade quantities the truncation/precision loss can make `exchange(A,B,sell)` followed by `exchange(B,A,buy)` return more than the amount originally sold, letting balances that should be conserved leak in the attacker's favor.

This function is reached directly from a single signed transaction: `ExchangeTransactionContract` → `ExchangeTransactionActuator.execute()/doValidate()` call `exchangeCapsule.transaction(tokenID, tokenQuant, ...)` [8](#0-7) [9](#0-8) . Any account holder with enough balance/fee for a TRX/TRC10 pair can create the exchange (`ExchangeCreateActuator`), inject imbalanced liquidity (`ExchangeInjectActuator`), and then submit two `ExchangeTransactionContract`s in either the same transaction batch or consecutive blocks — sell direction, then buy direction — to attempt to extract more tokens than deposited, draining the pool's TRX/TRC10 balances that back real user funds.

The codebase evidently already recognizes floating-point risk in this exact formula (hence the `SafeExchangeProcessor`/`allowHardenExchangeCalculation` hardening effort), but since that hardening is gated by a committee proposal rather than being the default, the floating-point code path in `ExchangeProcessor` is still reachable and exploitable on any deployment where the proposal has not been activated.

### Impact Explanation
If the rounding asymmetry can be triggered (as the external fuzzing report demonstrated for an analogous bonding-curve swap function), an attacker can repeatedly sell a token into the exchange and buy it back, extracting more of the paired token (potentially TRX) than was deposited, draining the exchange pool's balance and causing an unbacked-balance/theft-of-funds condition for other participants who hold shares in or trade through that exchange. This qualifies as theft of funds / unbacked balance under the validation criteria.

### Likelihood Explanation
Reachable from an ordinary, unprivileged account with only a `ExchangeCreateContract`, `ExchangeInjectContract`, and two `ExchangeTransactionContract` transactions — no special privileges required. Likelihood of exploitability depends on finding specific balance/quantity combinations (as the external fuzzer needed) that trigger a favorable rounding error in the `pow`-based Bancor formula; this requires the same kind of targeted fuzzing that found the original bug, but the code path (double-precision `pow` with truncation, no monotonicity/invariant check between sell and buy directions) is structurally identical to the reported vulnerable pattern.

### Recommendation
Make the `SafeExchangeProcessor` (BigDecimal, `RoundingMode.DOWN` bias against the trader) the default and only implementation instead of a proposal-gated opt-in, removing the double-precision `ExchangeProcessor` path entirely from production use. Additionally, add an explicit invariant check in `ExchangeCapsule.transaction()`/actuators that a round-trip (sell then buy back) can never return more of a token than was paid in, and add fuzz tests across the actuator that specifically attempt sell-then-buy-back sequences with extreme balances/quantities (mirroring the report's `1 asset -> 1 quote -> 10000000001 asset` scenario) to catch any remaining rounding-based value leaks in `SafeExchangeProcessor` as well.

### Proof of Concept
Conceptual reproduction path (requires targeted parameter search analogous to the external fuzz case, since exact triggering balances for `ExchangeProcessor`'s formula were not enumerated here):
1. Attacker broadcasts `ExchangeCreateContract` to create a TRX/TRC10 exchange with a skewed `firstTokenBalance`/`secondTokenBalance` ratio.
2. Attacker (or exchange creator) broadcasts `ExchangeInjectContract` to further tune balances into a ratio that stresses the `pow(1 + quant/newBalance, 0.0005)` / `pow(1 + supplyQuant/supply, 2000.0)` round trip in `ExchangeProcessor` [1](#0-0) .
3. Attacker broadcasts `ExchangeTransactionContract` selling a very small quantity (e.g. `1`) of the asset token, receiving the quote token via `exchangeCapsule.transaction()` [10](#0-9) .
4. Attacker immediately broadcasts a second `ExchangeTransactionContract` selling the received quote token back for the asset token.
5. If the double-precision truncation in steps 3–4 rounds in the attacker's favor (as in the external report's `1 wei in / 10000000001 wei out` case), the attacker receives more asset tokens than originally sold, draining `firstTokenBalance`/`secondTokenBalance` of the exchange capsule.

Exact triggering parameters for `ExchangeProcessor` were not derived in this analysis (the external report itself states the root cause of the analogous bug was not located), so this should be validated by running the same style of fuzz testing described in the report against `ExchangeTransactionActuator`/`ExchangeCapsule.transaction()`.

  private BigDecimal exchangeToSupply(long balance, long quant) {
    long newBalance = StrictMathWrapper.addExact(balance, quant);
    BigDecimal bdQuant = BigDecimal.valueOf(quant);
    BigDecimal bdNewBalance = BigDecimal.valueOf(newBalance);
    BigDecimal base = BigDecimal.ONE.add(
        bdQuant.divide(bdNewBalance, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 0.0005);
    return SUPPLY.negate().multiply(
        BigDecimal.ONE.subtract(BigDecimal.valueOf(powResult))).setScale(0, RoundingMode.DOWN);
  }

  private long exchangeFromSupply(long balance, BigDecimal supplyQuant) {
    BigDecimal bdBalance = BigDecimal.valueOf(balance);
    BigDecimal base = BigDecimal.ONE.add(
        supplyQuant.divide(SUPPLY, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 2000.0);
    BigDecimal exchangeBalance = bdBalance.multiply(
        BigDecimal.valueOf(powResult).subtract(BigDecimal.ONE));
    return exchangeBalance.setScale(0, RoundingMode.DOWN).longValueExact();
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    BigDecimal relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
