### Title
Quadratic CPU blow-up in TVM `Memory` chunk access via `LinkedList.get(chunkIndex)` during memory read/write - (File: `actuator/src/main/java/org/tron/core/vm/program/Memory.java`)

### Summary
The TVM byte-addressable `Memory` implementation stores its backing chunks in a `java.util.LinkedList<byte[]>` and accesses a chunk by numeric index (`chunkIndex = address / CHUNK_SIZE`) on every `read`/`write` operation. `LinkedList.get(index)` is an O(n) sequential-traversal operation, not O(1). Any TVM opcode that touches memory at growing offsets (`MLOAD`, `MSTORE`, `CALLDATACOPY`, `CODECOPY`, `RETURNDATACOPY`, `CALL`/`STATICCALL` output copies, etc.) therefore pays hidden O(chunks) traversal cost per access, on top of the already-quadratic energy charge for memory expansion. A contract that repeatedly accesses memory across a large, previously-expanded region forces the node to re-traverse the growing `LinkedList` on every single access, yielding true O(n²) CPU cost for n memory accesses — mirroring the Bandit bug class where a growing buffer is fully re-walked on every incremental operation.

### Finding Description
`Memory.read` and `Memory.write` compute `chunkIndex` and then call `grabMax`/`captureMax`, both of which do `chunks.get(chunkIndex)`: [1](#0-0) 

`chunks` is declared as a `LinkedList<byte[]>`: [2](#0-1) 

`LinkedList.get(index)` in the JDK is a doubly-linked-list traversal from whichever end (head/tail) is closer — it is linear, not constant time. `read()` and `write()` invoke this indexed lookup once per 1 KB (`CHUNK_SIZE`) chunk touched by the access: [3](#0-2) [4](#0-3) 

New chunks are appended cheaply (`addChunks` calls `LinkedList.add`, which is O(1) at the tail): [5](#0-4) [6](#0-5) 

so growth itself is fine — but every *subsequent read/write at a high offset* has to walk the list from an end up to `chunkIndex` positions. This is directly analogous to the Bandit issue: a data structure that is repeatedly, incrementally grown, and then repeatedly *fully re-traversed* on subsequent operations, produces quadratic aggregate work as the structure size increases.

Reachability: `Memory` backs `Program.memorySave`, `Program.memoryLoad`, `Program.memoryChunk`, and `Program.memoryCopy`, which are invoked directly by opcode handlers such as `callDataCopyAction` and `codeCopyAction` in `OperationActions.java`: [7](#0-6) [8](#0-7) 

Any account can deploy or call a contract with a `MLOAD`/`MSTORE`/`CALLDATACOPY`/`CODECOPY` loop, so this is reachable by any unprivileged contract deployer or caller.

Energy metering for memory growth is quadratic in memory *words* by design (Yellow-Paper-style memory expansion cost): [9](#0-8) 

That model assumes O(1) random-access cost per word/chunk once memory has been expanded (as in a real random-access array). Because `Memory` instead uses an indexed `LinkedList`, actual per-access CPU cost is O(chunks) rather than O(1), so the true computational cost of a sequence of memory accesses across an already-large memory region is asymptotically worse than what the energy model charges for. This mismatch lets a contract execute far more raw CPU work per unit of energy than intended once memory has grown into many chunks — the same "size guard bounds total size but not per-operation traversal cost" pattern described in the report.

### Impact Explanation
A malicious contract can allocate a large memory region (paying quadratic energy for expansion, as intended) and then, within the same energy budget, issue many small `MLOAD`/`MSTORE`/`CALLDATACOPY` operations at growing offsets across that region. Each such operation is charged O(1) or small linear energy per the cost model, but its actual CPU cost is O(chunks-to-index) due to `LinkedList.get`. Aggregated over many such calls this produces O(n²) real CPU work for O(n) charged energy, allowing a single transaction (or a modest number of transactions) to pin CPU on validating/executing nodes for a duration disproportionate to the energy paid. Because contract execution happens synchronously as part of transaction processing/block application, sustained abuse can degrade node responsiveness and block processing throughput, a Medium-severity CPU-exhaustion / DoS impact matching the CVE-2026-65623 class.

### Likelihood Explanation
The path is trivially reachable: any address can deploy a contract or call an existing address with attacker-controlled bytecode using ordinary opcodes (`MLOAD`, `MSTORE`, `CALLDATACOPY`, `CODECOPY`) — no special privilege, SR/witness status, or network position is required. The only cost to the attacker is the TRX/frozen-resource cost of energy for the transaction, and the underlying complexity mismatch (energy model assumes O(1) chunk access; implementation gives O(n)) is a structural code property, not a fragile race condition, making the amplification reliably reproducible.

### Recommendation
Replace the `LinkedList<byte[]> chunks` backing store in `Memory` with an `ArrayList<byte[]>` (or equivalent random-access structure), so that `chunks.get(chunkIndex)` is true O(1), matching the O(1)-per-word assumption baked into the existing quadratic memory-expansion energy model in `EnergyCost.calcMemEnergy`. This removes the extra traversal factor without needing to change the energy/gas schedule.

### Proof of Concept
1. Deploy a contract whose runtime bytecode first expands memory to a large size, e.g. via a single `CALLDATACOPY`/`MSTORE` at a high offset (paying the quadratic memory-expansion energy cost once, as designed) — see `Memory.extend`: [5](#0-4) .
2. Follow with a tight loop (bounded by the contract's remaining energy) of `MLOAD`/`MSTORE` opcodes at offsets stepping across the full expanded memory range (e.g., every 1 KB boundary, matching `CHUNK_SIZE`), so each access resolves to a different, increasing `chunkIndex`.
3. Because `read`/`write` call `grabMax`/`captureMax` → `chunks.get(chunkIndex)` on the `LinkedList`, each iteration's cost grows linearly with `chunkIndex`, producing O(n²) total chunk-traversal work for n iterations: [1](#0-0) .
4. Measure wall-clock execution time of this transaction versus a linear-access baseline (e.g., accessing the same offset repeatedly) to observe the quadratic blow-up in CPU time for the same amount of energy consumed.

  public byte[] read(int address, int size) {
    if (size <= 0) {
      return EMPTY_BYTE_ARRAY;
    }

    extend(address, size);
    byte[] data = new byte[size];

    int chunkIndex = address / CHUNK_SIZE;
    int chunkOffset = address % CHUNK_SIZE;

    int toGrab = data.length;
    int start = 0;

    while (toGrab > 0) {
      int copied = grabMax(chunkIndex, chunkOffset, toGrab, data, start);

      // read next chunk from the start
      ++chunkIndex;
      chunkOffset = 0;

      // mark remind
      toGrab -= copied;
      start += copied;
    }

    return data;
  }

  public void write(int address, byte[] data, int dataSize, boolean limited) {

    if (data.length < dataSize) {
      dataSize = data.length;
    }

    if (!limited) {
      extend(address, dataSize);
    }

    int chunkIndex = address / CHUNK_SIZE;
    int chunkOffset = address % CHUNK_SIZE;

    int toCapture = 0;
    if (limited) {
      toCapture = (address + dataSize > softSize) ? softSize - address : dataSize;
    } else {
      toCapture = dataSize;
    }

    int start = 0;
    while (toCapture > 0) {
      int captured = captureMax(chunkIndex, chunkOffset, toCapture, data, start);

      // capture next chunk
      ++chunkIndex;
      chunkOffset = 0;

      // mark remind
      toCapture -= captured;
      start += captured;
    }

    if (programListener != null) {
      programListener.onMemoryWrite(address, data, dataSize);
    }
  }

  private int captureMax(int chunkIndex, int chunkOffset, int size, byte[] src, int srcPos) {

    byte[] chunk = chunks.get(chunkIndex);
    int toCapture = min(size, chunk.length - chunkOffset, VMConfig.disableJavaLangMath());

    System.arraycopy(src, srcPos, chunk, chunkOffset, toCapture);
    return toCapture;
  }

  private int grabMax(int chunkIndex, int chunkOffset, int size, byte[] dest, int destPos) {

    byte[] chunk = chunks.get(chunkIndex);
    int toGrab = min(size, chunk.length - chunkOffset, VMConfig.disableJavaLangMath());

    System.arraycopy(chunk, chunkOffset, dest, destPos, toGrab);

    return toGrab;
  }

  public static void codeCopyAction(Program program) {
    byte[] fullCode = program.getCode();

    int memOffset = program.stackPop().intValueSafe();
    int codeOffset = program.stackPop().intValueSafe();
    int lengthData = program.stackPop().intValueSafe();

    int sizeToBeCopied = lengthData;
    if ((long) codeOffset + lengthData > fullCode.length) {
      sizeToBeCopied = fullCode.length < codeOffset ? 0 : fullCode.length - codeOffset;
    }

    byte[] codeCopy = new byte[lengthData];

    if (codeOffset < fullCode.length) {
      System.arraycopy(fullCode, codeOffset, codeCopy, 0, sizeToBeCopied);
    }

    program.memorySave(memOffset, codeCopy);
    program.step();
  }

  private static long calcMemEnergy(long oldMemSize, BigInteger newMemSize,
                             long copySize, int op) {
    long energyCost = 0;

    checkMemorySize(op, newMemSize);

    // memory SUN consume calc
    long memoryUsage = (newMemSize.longValueExact() + 31) / 32 * 32;
    if (memoryUsage > oldMemSize) {
      long memWords = (memoryUsage / 32);
      long memWordsOld = (oldMemSize / 32);
      long memEnergy = (MEMORY * memWords + memWords * memWords / 512)
          - (MEMORY * memWordsOld + memWordsOld * memWordsOld / 512);
      energyCost += memEnergy;
    }

    if (copySize > 0) {
      long copyEnergy = COPY_ENERGY * ((copySize + 31) / 32);
      energyCost += copyEnergy;
    }
    return energyCost;
  }
