### Title
Stale postponed-receipt trie entries survive `remove_account`, letting a self-authorized receipt execute privileged actions against a re-created account of the same name - (File: core/store/src/utils/mod.rs)

### Summary
`remove_account` (core/store/src/utils/mod.rs:505-575) only clears `TrieKey::Account`, `TrieKey::ContractCode`, `TrieKey::AccessKey`/`GasKeyNonce`, and `TrieKey::ContractData`, but `TrieKey::COLUMNS_WITH_ACCOUNT_ID_IN_KEY` (core/primitives/src/trie_key.rs:89-102) lists 12 account-keyed columns, leaving `PostponedReceiptId`, `PendingDataCount`, and `PostponedReceipt` behind when an account self-deletes with an outstanding unresolved `input_data_ids` dependency. Because `check_actor_permissions` (runtime/runtime/src/actions.rs:739-785) authorizes privileged actions purely by string-comparing `actor_id == account_id` (which is set from `receipt.predecessor_id()`, actions.rs:387 in `action_delete_account`, and analogously from the receipt at execution time), a postponed self-receipt created before deletion can later be delivered and executed against a *newly created, differently-owned* account bearing the same name, granting it `AddKey`/`DeployContract`/`DeleteKey`/`Stake`/`DeleteAccount` privileges it never authorized.

### Finding Description
`process_action_receipt` (runtime/runtime/src/lib.rs:1593-1658) stores a `TrieKey::PostponedReceiptId{receiver_id, data_id}`, `TrieKey::PendingDataCount{receiver_id, receipt_id}`, and `TrieKey::PostponedReceipt{receiver_id, receipt_id}` when a receipt's `input_data_ids` are not all resolved yet. All three are keyed by `receiver_id` = the account under attack (here `sub.p.near`), not by any account "generation" or creation nonce.

An account owner can self-issue an `ActionReceipt` (predecessor_id == receiver_id == `sub.p.near`) carrying privileged actions (e.g. `AddKey`, `DeployContract`) with `input_data_ids = [D]`, where `D` is produced by a promise the owner controls and can choose to fire at will (i.e., delayed, not literally permanent). This receipt `R` gets postponed under `sub.p.near`.

The owner then submits `DeleteAccountAction` on `sub.p.near` from a full-access key they hold. `check_actor_permissions` passes because `actor_id == account_id` (self-delete, actions.rs:761-768), and `locked == 0` satisfies the staking check. `action_delete_account` (runtime/runtime/src/actions.rs:314-390) calls `remove_account` (core/store/src/utils/mod.rs:505-575), which deletes `Account`, `ContractCode`, `AccessKey`/`GasKeyNonce`, and `ContractData` — but never touches `PostponedReceiptId`, `PendingDataCount`, or `PostponedReceipt`. Those three trie entries for `sub.p.near` remain live in state.

A third party entitled to the name (the parent account `p.near`, per `action_create_account`'s sub-account rule, actions.rs:155-192) later creates a fresh `sub.p.near` account with its own keys/balance — unaware of the dangling postponed receipt.

The original attacker then triggers delivery of the `Data` receipt for `data_id = D` (they control its production). `process_receipt`'s `Data` arm (runtime/runtime/src/lib.rs:1386-1455) finds the matching `PostponedReceiptId`, decrements `PendingDataCount` to 0, fetches `R` via `get_postponed_receipt`, removes the postponed bookkeeping, and calls `apply_action_receipt` against the *current* state of `sub.p.near` — which is now the newly created, differently owned account. Because `actor_id` derived from `R.predecessor_id()` is still the literal string `sub.p.near`, and `account_id` is also `sub.p.near`, `check_actor_permissions` treats this as a legitimate self-action regardless of which "incarnation" of the account currently exists, letting `R`'s privileged actions (e.g., adding a full-access key controlled by the original attacker) execute against the new owner's account.

No existing check validates that the account executing a postponed receipt is the same account (by creation event/nonce) that originally authorized it; account identity in this codebase is purely the `AccountId` string, and the postponed-receipt cleanup gap is what keeps the authorization chain alive across a delete/recreate cycle.

### Impact Explanation
This breaks the "authorization exactness" invariant: a promise created by one account instance (before deletion) can carry privileges into a subsequent, distinct owner's identically-named account. Concretely, `AddKey`/`DeployContract`/`Stake`/`DeleteKey` actions in the released postponed receipt can grant the original attacker full control of the new account (adding their own access key, redeploying a malicious contract, or restaking to their benefit), i.e., authorization escalation across accounts and potential theft of the new account's funds — matching the NEP bounty category "authorization escalation across accounts" and, transitively, "theft of user funds."

### Likelihood Explanation
Preconditions: attacker needs to own the target account before self-deleting it, be able to construct a postponed receipt with a data dependency it controls the timing of, and needs a name-reuse event to occur (a third party — typically the parent account — creating the exact same sub-account name again). The last precondition is the main limiting factor: it requires the deleted name to actually be recreated, which is not attacker-controlled and may not happen in practice for arbitrary sub-account names (an attacker would need to pick a name that the parent account is likely to reissue, or convince/wait for the parent to do so). This makes the attack conditionally feasible rather than trivially repeatable against arbitrary victims, but it is fully reachable through ordinary transactions (no validator/node privilege needed) and costs only the gas/storage of a few actions.

### Recommendation
Extend `remove_account` (or `action_delete_account`) to also purge any outstanding `TrieKey::PostponedReceiptId`, `TrieKey::PendingDataCount`, and `TrieKey::PostponedReceipt` entries (and ideally `ReceivedData`, `PromiseYieldReceipt`/`PromiseYieldStatus`, `YieldIdToDataId`/`DataIdToYieldId`) associated with the account being deleted, mirroring the full `COLUMNS_WITH_ACCOUNT_ID_IN_KEY` set, or alternatively reject `DeleteAccountAction` while any postponed receipt/pending data count still references the account as `receiver_id`.

### Proof of Concept
Integration test (runtime/runtime/src/tests/apply.rs style, using `create_receipt_with_actions`/`create_receipt_for_create_account`):
1. Create `sub.p.near` under `p.near`.
2. Submit an `ActionReceipt` to `sub.p.near` (predecessor = `sub.p.near`) with `input_data_ids = [D]` and actions `[AddKey(attacker_pubkey, FullAccess)]`; assert it is stored as `PostponedReceipt`/`PostponedReceiptId`/`PendingDataCount`.
3. Submit `DeleteAccountAction` on `sub.p.near` (beneficiary = attacker); assert account is deleted while `get_postponed_receipt`, `TrieKey::PostponedReceiptId`, and `TrieKey::PendingDataCount` for `sub.p.near` still return `Some`.
4. Re-create `sub.p.near` via `CreateAccountAction` from `p.near`, funded independently.
5. Deliver a `DataReceipt{data_id: D}` to `sub.p.near`; assert the postponed `AddKey` action executes and `attacker_pubkey` is now a full-access key on the newly created account, despite never being authorized by its actual creator/owner.
