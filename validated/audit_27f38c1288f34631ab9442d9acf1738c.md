This is important: `RegisterAll` registers `HookService` (via `gitalypb.RegisterHookServiceServer(srv, hook.NewServer(deps))`) on the *same* gRPC server instance as all other services (`RepositoryService`, `SmartHTTPService`, etc.), with no separate ACL scoping visible in `internal/gitaly/service/setup/register.go`. [1](#0-0)  This means `ProcReceiveHook` is reachable by any client holding a valid Gitaly auth token — the same token used for ordinary push/fetch RPCs — not gated behind an additional "only-the-real-hook-process" check.

### Title
Unauthenticated Hijack of `ProcReceiveHook` via Transaction-ID Guessing Allows Cross-Push Reference Injection - (File: internal/gitaly/service/hook/proc_receive.go)

### Summary
`ProcReceiveHook` is a standard gRPC RPC on `HookService` that any client with a valid Gitaly bearer token can call directly, bypassing the actual `git-receive-pack(1)`/`gitaly-hooks` invocation path. Its only binding to a specific in-flight push is a caller-supplied `storage.TransactionID`, transmitted inside the request's `EnvironmentVariables` blob and matched against `ProcReceiveRegistry.waiters`. There is no verification that the caller is the legitimate `gitaly-hooks` process for that transaction, mirroring the `onAfterRemoveLiquidity` bug class where a function meant to be invoked only by a trusted internal actor (the Vault) lacked a caller-identity check and instead trusted attacker-suppliable arguments.

### Finding Description
`ProcReceiveHook` reads the first request's `EnvironmentVariables`, builds a `ProcReceiveHandler`, and calls `registry.Transmit(ctx, handler)`, which looks the handler up by `handler.TransactionID()` in the `waiters` map and hands it to whichever RPC (`PostReceivePack`/`SSHReceivePack`) registered a waiter for that same ID: [2](#0-1) [3](#0-2) 

The receiving RPC (`postReceivePack`) registers a waiter for the transaction only after it has extracted `transactionID := storage.ExtractTransactionID(ctx)` from context and calls `RegisterProcReceiveHook`, then blocks waiting for a handler to arrive on the channel and, once matched, treats the pkt-line reference-update stream from the handler as authoritative input to commit to the write-ahead log: [4](#0-3) [5](#0-4) 

The registry's `Transmit` performs no authentication of the caller beyond a successful gRPC auth token check — it does not verify that the handler actually originated from the `gitaly-hooks` subprocess spawned for that specific push, nor that the connecting client is the internal Gitaly process rather than an arbitrary external client holding a valid Gitaly token. Compare this to `SignalPostReceiveReady`, where the maintainers explicitly added an internal-caller check ("can only be called via Praefect backchannel") for a similarly sensitive internal handshake RPC: [6](#0-5)  — no equivalent check exists for `ProcReceiveHook`.

The pkt-line protocol carries the reference updates (`old-oid new-oid ref-name`) and any attacker-controlled client can craft this stream freely, just as `attackerUnlockCallBack()` in the reference bug crafted `RemoveLiquidityKind`/`bptAmountIn`/`userData` to target Bob's data instead of the attacker's own.

### Impact Explanation
If an attacker can predict or brute-force a live `storage.TransactionID` for a concurrent legitimate push (transaction IDs are sequential/monotonic per `storage.TransactionID`, not randomized secrets) and race to call `ProcReceiveHook` before the real `gitaly-hooks` subprocess does for that transaction, they can inject an attacker-chosen `ReferenceUpdate` set that gets accepted and committed to the target repository's write-ahead log in place of the legitimate push's own updates. This can corrupt or hijack another user's push — e.g., silently rewriting `refs/heads/main` to attacker-controlled content, or causing legitimate pushes to write to different refs than intended — a direct object/reference-integrity compromise analogous to the "delete all user liquidity" impact (irrecoverable data corruption) in the original report, except the impacted asset here is repository state rather than token balances.

### Likelihood Explanation
Exploitation requires: (1) network/API access to Gitaly with a valid auth token (an "ordinary" authenticated caller, not root/admin), and (2) winning a race against the legitimate `gitaly-hooks` proc-receive invocation for a transaction ID that is guessable because it is sequential and only valid for a narrow window during an in-flight push. This is a non-trivial race condition, but it is a fully unprivileged-from-Gitaly's-perspective network-reachable path (any client with the same access as one that can push), consistent with the "crafted RPC field" analog class in the report's rules.

### Recommendation
Add an internal-caller check to `ProcReceiveHook` (and to `ProcReceiveRegistry.Transmit`) analogous to what `SignalPostReceiveReady` already does — verify the RPC is only invoked from the trusted internal `gitaly-hooks` process for the specific transaction (e.g., by requiring the internal socket token and/or binding the waiter registration to a per-transaction unpredictable secret/nonce that must be echoed back by the real hook invocation, not just the transaction ID).

### Proof of Concept
Not independently reproducible from this index — the concrete PoC would require constructing a gRPC client that: (1) obtains a valid Gitaly auth token, (2) observes/guesses an in-flight `storage.TransactionID` for a target push, (3) calls `HookService.ProcReceiveHook` directly with a crafted `EnvironmentVariables`/pkt-line payload containing that transaction ID before the legitimate `gitaly-hooks proc-receive` subprocess does, per the flow in [7](#0-6) . Due to index size limits, some runtime/config details (e.g., exact transaction-ID predictability windows) could not be fully verified here; a Devin session with full repository and runtime access is recommended to build and validate an end-to-end exploit.

```go
func (s *server) ProcReceiveHook(stream gitalypb.HookService_ProcReceiveHookServer) error {
	ctx := stream.Context()

	firstRequest, err := stream.Recv()
	if err != nil {
		return structerr.NewInternal("receiving first request: %w", err)
	}

	stdin := streamio.NewReader(func() ([]byte, error) {
		req, err := stream.Recv()
		return req.GetStdin(), err
	})

	var m sync.Mutex
	stdout := streamio.NewSyncWriter(&m, func(p []byte) error {
		return stream.Send(&gitalypb.ProcReceiveHookResponse{Stdout: p})
	})

	stderr := streamio.NewSyncWriter(&m, func(p []byte) error {
		return stream.Send(&gitalypb.ProcReceiveHookResponse{Stderr: p})
	})

	handler, doneCh, err := gitalyhook.NewProcReceiveHandler(
		firstRequest.GetEnvironmentVariables(), stdin, stdout, stderr,
	)
	if err != nil {
		return structerr.NewInternal("creating handler: %w", err)
	}

	registry := s.manager.ProcReceiveRegistry()
	if err := registry.Transmit(ctx, handler); err != nil {
		return sendProcReceiveHookResponse(stream, 1, fmt.Sprintf("transmitting handler: %s", err))
	}

	if err := <-doneCh; err != nil {
		return sendProcReceiveHookResponse(stream, 1, fmt.Sprintf("handler finished: %s", err.Error()))
	}

	return sendProcReceiveHookResponse(stream, 0, "")
```

```go
// Transmit transmits a handler to its waiter.
func (r *ProcReceiveRegistry) Transmit(ctx context.Context, handler ProcReceiveHandler) error {
	r.m.Lock()
	ch, ok := r.waiters[handler.TransactionID()]
	r.m.Unlock()

	if !ok {
		return fmt.Errorf("no waiters for id: %d", handler.TransactionID())
	}

	// It is possible that the RPC (waiter) returned because receive-pack
	// returned an error. In such scenarios, we don't want to block indefinitely.
	select {
	case <-ctx.Done():
		return ctx.Err()
	case ch <- handler:
	}

	return nil
}
```
