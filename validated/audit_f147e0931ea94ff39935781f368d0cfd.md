## Finding

The `pallet-asset-rewards` pallet (explicitly modeled on Synthetix's `StakingRewards.sol`, per its own doc comments) reproduces the exact "rewards lost before first depositor" bug class from the Velocimeter report. [1](#0-0) 

### Title
Reward-asset funds accrued while `total_tokens_staked == 0` are permanently unclaimable and stranded in the pool account - (File: `substrate/frame/asset-rewards/src/lib.rs`)

### Summary
`reward_per_token()` short-circuits and returns the unchanged `reward_per_token_stored` whenever `pool_info.total_tokens_staked.is_zero()`, but `update_pool_rewards()` unconditionally advances `last_update_block` to the current block on every call, including the very call that brings the pool from zero stake to non-zero stake. This silently discards the reward budget that "would have" accrued for the zero-stake interval — that budget is never credited to any staker's `PoolStakerInfo`, yet the corresponding reward-asset balance is already sitting in the pool's dedicated account (fundable by anyone via the permissionless `deposit_reward_tokens` call). The funds become permanently stranded for as long as the pool has any staker at all, since the only recovery path, `cleanup_pool`, requires `PoolStakers` to be completely empty. [2](#0-1) [3](#0-2) 

### Finding Description
The reward accounting flow is:
1. `stake()`/`unstake()`/`harvest_rewards()` all call `update_pool_and_staker_rewards`, which calls `reward_per_token(&pool_info)` using the **pre-mutation** `pool_info` (i.e., before the current call's stake/unstake delta is applied). [4](#0-3) 
2. `reward_per_token` returns the stored value unchanged when `total_tokens_staked == 0`, i.e., no reward-per-token accrues for that period — by design, since there is no one to attribute it to.
3. However, `update_pool_rewards` (called right after, using the *result* of `reward_per_token`) unconditionally sets `new_pool_info.last_update_block = T::BlockNumberProvider::current_block_number()`.
4. Because `last_update_block` is advanced regardless of whether `total_tokens_staked` was zero, the elapsed "silent" blocks are never revisited — the next time `reward_per_token` is computed (once someone has staked), `rewardable_blocks_elapsed` is computed from the *new* `last_update_block`, permanently skipping the zero-stake window's `reward_rate_per_block` allotment.

Meanwhile, the reward asset itself is transferred into the pool's dedicated account (`pool_info.account`) independently, either at pool creation planning or via the fully permissionless `deposit_reward_tokens` extrinsic: [5](#0-4) 

So any reward-asset balance corresponding to blocks where `total_tokens_staked == 0` (pool freshly created and awaiting its first staker, or a period after all stakers fully `unstake()` to zero) is left in the pool account with no staker ever entitled to claim it via `harvest_rewards`. The only way to recover it is `cleanup_pool`, which explicitly requires the pool to have zero stakers: [6](#0-5) 

Once even a single staker exists and holds a nonzero balance, `cleanup_pool` cannot be called (`Error::<T>::NonEmptyPool`), so those stranded funds are permanently locked as long as the pool remains active with any staker — matching precisely the "rewards supplied to a gauge, prior to its first depositor, will be permanently lost" invariant from the source report, and the report's own recommended fix ("revert in case current supply is 0") was never applied here for the reward-emission side.

### Impact Explanation
This is a permanent, protocol-level fund lock affecting the reward-asset balance intended for stakers: value is neither returned to depositors of `deposit_reward_tokens` nor claimable by any staker nor recoverable by the admin while any staker remains bonded. No malicious actor, admin, or privileged party is required — normal, expected chain operation (pool creation followed by a natural delay before the first `stake()`, or a temporary lull where all stakers fully unstake) triggers the loss automatically and permissionlessly.

### Likelihood Explanation
High likelihood in practice: pool creation and the first stake are two separate transactions that will virtually never land in the same block, so every pool created via `create_pool` incurs at least one block's worth of loss by default. Additionally, `deposit_reward_tokens` is callable by any signed account with no relation to whether the pool currently has stakers, making it trivial to inflate the lost amount, and any pool that transiently reaches zero total stake (e.g., all LPs unstake simultaneously) reopens the same window.

### Recommendation
Track the last-update block separately from the reward-per-token computation, or only advance `last_update_block` when `total_tokens_staked` is non-zero (mirroring the corrected Synthetix pattern), so that no reward-rate budget is silently skipped over. Alternatively, when `total_tokens_staked.is_zero()`, do not advance `last_update_block`, ensuring that once staking resumes, the full elapsed interval (including the zero-stake gap) is correctly excluded from `reward_rate_per_block` accrual, and consider allowing the admin to reclaim genuinely orphaned reward-asset balance even while some stakers exist.

### Proof of Concept
1. `create_pool` with `reward_rate_per_block = R`, `expiry_block` far in the future; `last_update_block` initialized to `0` and `total_tokens_staked = 0`. [7](#0-6) 
2. Anyone calls `deposit_reward_tokens(pool_id, amount)` to fund the pool's reward account (or the pool is pre-funded at creation time by the operator). [5](#0-4) 
3. `N` blocks pass with no stakers (`total_tokens_staked` stays `0`).
4. The first staker calls `stake(pool_id, amount)`. Internally, `update_pool_and_staker_rewards` computes `reward_per_token` using `total_tokens_staked == 0`, returning `reward_per_token_stored` unchanged; `update_pool_rewards` then sets `last_update_block = current_block`, silently consuming/skipping the `N` blocks. [8](#0-7) 
5. The `N * R` reward-asset budget that was nominally allocated for those blocks is never reflected in any `PoolStakerInfo.rewards`, is not returned to the depositor, and cannot be recovered by `cleanup_pool` once the staker's balance is non-zero (`Error::<T>::NonEmptyPool`). [6](#0-5)

		pub fn stake(origin: OriginFor<T>, pool_id: PoolId, amount: T::Balance) -> DispatchResult {
			let staker = ensure_signed(origin)?;

			// Always start by updating staker and pool rewards.
			let pool_info = Pools::<T>::get(pool_id).ok_or(Error::<T>::NonExistentPool)?;
			let staker_info = PoolStakers::<T>::get(pool_id, &staker).unwrap_or_default();
			let (mut pool_info, mut staker_info) =
				Self::update_pool_and_staker_rewards(&pool_info, &staker_info)?;

			T::AssetsFreezer::increase_frozen(
				pool_info.staked_asset_id.clone(),
				&FreezeReason::Staked.into(),
				&staker,
				amount,
			)?;

			// Update Pools.
			pool_info.total_tokens_staked.ensure_add_assign(amount)?;

			Pools::<T>::insert(pool_id, pool_info);

			// Update PoolStakers.
			staker_info.amount.ensure_add_assign(amount)?;
			PoolStakers::<T>::insert(pool_id, &staker, staker_info);

			// Emit event.
			Self::deposit_event(Event::Staked { staker, pool_id, amount });

			Ok(())
		}

		/// Derives the current reward per token for this pool.
		pub(super) fn reward_per_token(
			pool_info: &PoolInfoFor<T>,
		) -> Result<T::Balance, DispatchError> {
			if pool_info.total_tokens_staked.is_zero() {
				return Ok(pool_info.reward_per_token_stored);
			}

			let rewardable_blocks_elapsed: u32 =
				match Self::last_block_reward_applicable(pool_info.expiry_block)
					.ensure_sub(pool_info.last_update_block)?
					.try_into()
				{
					Ok(b) => b,
					Err(_) => return Err(Error::<T>::BlockNumberConversionError.into()),
				};

			Ok(pool_info.reward_per_token_stored.ensure_add(
				pool_info
					.reward_rate_per_block
					.ensure_mul(rewardable_blocks_elapsed.into())?
					.ensure_mul(PRECISION_SCALING_FACTOR.into())?
					.ensure_div(pool_info.total_tokens_staked)?,
			)?)
		}
