Audit Report

## Title
Unchecked balance transfer in `claim_child_bounty` causes silent-failure payouts and permanent fund lock - (File: `substrate/frame/child-bounties/src/lib.rs`)

## Summary
`pallet-child-bounties::claim_child_bounty` performs the curator-fee and beneficiary payout transfers from the child-bounty's sovereign account and only checks their results with `debug_assert!`, which is compiled out in release builds. If either transfer fails (e.g., due to an account being unable to receive funds below the existential deposit, or hitting consumer/provider-ref limits), the extrinsic still succeeds, the `Claimed` event is still emitted, and the child-bounty storage is unconditionally deleted, permanently severing the link between the still-held funds and their intended recipients.

## Finding Description
In `claim_child_bounty`, both the curator-fee transfer and beneficiary transfer are checked only via `debug_assert!`: [1](#0-0) 

`debug_assert!` compiles to a no-op when `debug_assertions` is disabled, which is the case for standard `--release` runtime builds used on production chains. Consequently, the `Result<_, DispatchError>` returned by `T::Currency::transfer` is discarded outside debug builds. If a transfer fails — for instance because the destination is a fresh account and the transferred amount is below the `ExistentialDeposit`, or because of consumer-ref limits on account creation — execution proceeds unaffected:

- The `Claimed` event is deposited with the full intended `payout` and `beneficiary`, falsely indicating a successful settlement.
- `ParentChildBounties` is decremented and `ChildBountyDescriptionsV1`/`ChildBounties` entries are removed unconditionally right after the transfer attempts, deleting the only on-chain record connecting the still-resident funds in `child_bounty_account_id(parent_bounty_id, child_bounty_id)` to the beneficiary/curator.

The same discard-on-release anti-pattern also exists in `pallet-tips::payout_tip`: [2](#0-1) 

confirming this is a systemic pattern rather than an isolated typo, and that the codebase already demonstrates the correct alternative elsewhere (propagating the error via `.defensive().map_err(...)?` before mutating state), as in `cumulus/pallets/ah-ops/src/lib.rs`: [3](#0-2) 

The existing "should not fail" comments in `claim_child_bounty` are insufficient guards: while `curator_fee <= balance` is mathematically guaranteed by the `min()`/`saturating_sub()` computation at lines 717-719, the transfer can still fail on *account-creation* grounds (destination below ED, or provider/consumer-ref exhaustion) — a failure mode unrelated to the fee/payout arithmetic bound.

## Impact Explanation
This maps directly to the "permanent user-fund or bridge-state lock" and "settle exactly once to the rightful beneficiary" impact classes: on transfer failure, the child-bounty sovereign account retains the funds, but the on-chain storage proving entitlement (`ChildBounties` entry, description, counters) is deleted and a `Claimed` event falsely reports the payout as delivered. There is no remaining pallet-level mechanism to re-attempt or reclaim the stranded balance from the now-untracked sovereign account, and downstream consumers of the `Claimed` event (indexers, treasuries, automation) will record an incorrect settlement.

## Likelihood Explanation
`claim_child_bounty` is callable by any signed account (`ensure_signed(origin)?` only) once a child bounty reaches `PendingPayout`, so the trigger step itself requires no privilege. However, engineering the actual transfer failure requires influencing the beneficiary/payout parameters via `award_child_bounty`, which is restricted to the parent bounty's curator. A curator role is attainable by community-approved/governance-accepted curators rather than being fully open to an arbitrary unprivileged attacker, which somewhat bounds direct exploitability, but the underlying guard failure (silent-no-op `debug_assert!` in release builds) applies unconditionally regardless of how the failure condition arises (e.g., a legitimately small child-bounty payout to a fresh account below the existential deposit).

## Recommendation
Replace both `debug_assert!(...)` checks in `claim_child_bounty` with proper error propagation (e.g., `.map_err(|_| Error::<T>::PayoutFailed)?` or `.defensive().map_err(...)?`), ensuring the storage removal and `Claimed` event only occur after both transfers are confirmed to succeed. Apply the same fix to `pallet-tips::payout_tip`.

## Proof of Concept
1. Configure a runtime where `T::Currency` is `pallet-balances` with a non-trivial `ExistentialDeposit`.
2. Create and approve a parent bounty, assign a curator, and have that curator call `add_child_bounty` and `award_child_bounty` with a `beneficiary` that is a brand-new account (zero balance) and a bounty value split such that the resulting `payout` (balance minus curator fee) is below `ExistentialDeposit`.
3. Wait for `unlock_at` to elapse and call `claim_child_bounty(origin, parent_bounty_id, child_bounty_id)` from any signed account, in a release-profile build (`debug_assertions` disabled).
4. Observe: `T::Currency::transfer` to `beneficiary` returns `Err(_)` (new account below ED), yet the call returns `Ok(())`, emits `Event::Claimed { payout, beneficiary, .. }`, and deletes the `ChildBounties`/`ChildBountyDescriptionsV1` entries — while the funds remain stuck in `child_bounty_account_id(parent_bounty_id, child_bounty_id)` with no further on-chain record connecting them to `beneficiary`.
