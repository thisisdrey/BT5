### Title
`ValidateMultiSign` Precompile's Signed-Data Hash Lacks Domain Separation, Enabling Cross-Chain/Cross-Contract Signature Replay - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The `ValidateMultiSign` precompiled contract (address `0x...a`) lets any TVM contract verify an off-chain-signed authorization against an account's on-chain `Permission`. The hash it builds to compare against the recovered signer omits `block.chainid` and the calling contract's `address(this)`, so a signature that authorizes an action for one contract/chain is verbatim valid for any other contract or TRON-compatible chain sharing the same account address and permission id — the exact "signature lacks domain separation" bug class described in the external report.

### Finding Description
`ValidateMultiSign.execute()` recovers the signer for a hash computed purely from the target account address, the permission id, and an application-chosen `data` blob:

```java
byte[] combine = ByteUtil.merge(address, ByteArray.fromInt(permissionId), data);
byte[] hash = Sha256Hash.hash(CommonParameter
    .getInstance().isECKeyCryptoEngine(), combine);
``` [1](#0-0) 

then recovers each signature against that `hash` and checks weight/threshold from the account's `Permission`:

```java
for (byte[] sign : signatures) {
  byte[] recoveredAddr = recoverAddrBySign(sign, hash);
  ...
  long weight = TransactionCapsule.getWeight(permission, recoveredAddr);
  ...
}
if (totalWeight >= permission.getThreshold()) {
  return Pair.of(true, dataOne());
}
``` [2](#0-1) 

There is no `block.chainid`, no invoking contract address, and no nonce/session identifier folded into `hash`. TRON account addresses are derived deterministically from the private key with the same 21-byte scheme on every TRON-based network (mainnet, testnet, and any private chain launched from this codebase), so `address` is identical across deployments for a given key. Consequently, any off-chain-signed authorization built as `(address, permissionId, data)` — the exact pattern the precompile encourages application (dApp) contracts to use for account-abstraction style approvals — is directly reusable:
- across different TVM contracts on the same chain that happen to consume the same `data` encoding for a different purpose,
- across independent TRON-compatible chains/deployments sharing the same signer key and permission id.

This mirrors the reported `Revolver.joinGame()` flaw precisely: the signed preimage fails to commit to any deployment/chain-specific domain value, so the java-tron-provided verification primitive itself propagates the vulnerability into every dApp built on top of it, unless the dApp manually adds domain separation into its own `data` payload (which the precompile does nothing to enforce or even document as required).

### Impact Explanation
Any smart contract using `ValidateMultiSign` for authorization (e.g., account-abstraction wallets, gasless meta-transaction relayers, multisig-gated withdrawal/order execution) can have a legitimately-issued signature replayed on a different contract or chain that consumes the same `(address, permissionId, data)` triple, since the account address and permission structure are chain-agnostic. This can lead to unauthorized execution of privileged operations (e.g., replaying a withdrawal/approval authorization intended for one context in a different context), i.e., unauthorized account operation / theft of funds, without requiring any bug in the calling contract beyond following the precompile's documented usage pattern.

### Likelihood Explanation
Reachable by any unprivileged contract deployer or transaction sender: an attacker only needs to observe a previously broadcast signature/`data` pair (public on-chain) and replay it against any other deployed contract or chain reachable via `STATICCALL`/`CALL` to the `ValidateMultiSign` precompile address with the same `address`/`permissionId`/`data`. No special privileges, node compromise, or malicious-SR/witness cooperation is required — only a standard contract call, matching the in-scope "TVM opcodes, precompiles" and "signature and permission verification" categories.

### Recommendation
Bind the precompile's hash to a domain: include `block.chainid` (or a TRON-specific network id/genesis hash already tracked by `DynamicPropertiesStore`) and clearly document that callers must additionally include their own contract address / nonce / session id inside `data`. Alternatively, add chain id and the calling contract address directly into the `combine` buffer before hashing:

```java
byte[] combine = ByteUtil.merge(
    ByteArray.fromLong(chainId), callerAddress, address,
    ByteArray.fromInt(permissionId), data);
```

so that signatures produced for one deployment/chain cannot be verified as valid on another.

### Proof of Concept
1. Deploy the same contract bytecode (or two different contracts consuming the same `data` encoding) on two TRON-compatible networks (e.g., mainnet and a private java-tron-based chain), both invoking `ValidateMultiSign` to authorize a withdrawal for account `A` with `permissionId=2`.
2. Account `A` (same private key, hence identical address on both chains per TRON's address derivation) signs `sha256(A_address || permissionId || data)` once, authorizing withdrawal `data` on chain 1.
3. Submit the exact same signature and `data` to the contract on chain 2 (or to a second contract on chain 1 expecting the same `data` format). `ValidateMultiSign` recomputes the identical `hash` (no chain id/contract binding), recovers the same signer, finds sufficient permission weight, and returns `dataOne()` (success), authorizing the replayed operation without a fresh signature from `A`.
