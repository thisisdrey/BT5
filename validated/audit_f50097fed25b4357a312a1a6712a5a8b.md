### Title
Unbounded reference-update accumulation in `UpdateReferences` client-streamed RPC enables DoS - ([File: internal/gitaly/service/ref/update_references.go])

### Summary
The `UpdateReferences` RPC accepts a client-streamed sequence of `UpdateReferencesRequest` messages, each carrying a `repeated Update updates` field, and queues every single update into one `git update-ref --stdin` transaction with no cap on the total number of updates before finally calling `Commit()` once at the end of the stream. This mirrors the `withdraw()` bug class: an unbounded loop that performs per-item work (writing to and later flushing an external process/transaction) driven entirely by attacker-controlled input length, with no batching, chunk limit, or backpressure enforced server-side.

### Finding Description
`UpdateReferences` receives the client stream in a `for {}` loop and, for every request, iterates `request.GetUpdates()` and calls `updater.Update(...)` for each one, which writes a command line into the `git update-ref --stdin` process's stdin buffer: [1](#0-0) 

There is no limit on the number of `Update` messages accepted across the entire stream (unlike client-side helper tooling in the repo which self-imposes 100-per-message / batch-size chunking as a courtesy, not as a server-side enforced limit): [2](#0-1) 

Each `Update()` call performs an unbounded `write()` into the same underlying `update-ref --stdin` process: [3](#0-2) 

Only after the entire client stream is drained does the handler call `updater.Commit()`, which flushes the "commit" command to the subprocess and waits for git to process the whole batch atomically: [4](#0-3) [5](#0-4) 

Because gRPC streams allow effectively unbounded numbers of messages, a client can enqueue an arbitrarily large number of ref updates into a single transaction. This is functionally analogous to the reported bug: an external-process-driving loop (`transfer()` calls in the original report; `git update-ref --stdin` command writes here) whose iteration count is fully attacker-controlled and unbounded, risking exhaustion of memory/CPU, oversized `update-ref` stdin buffers, and prolonged holding of reference locks (via `Prepare`/`Commit`) for the entire duration of an enormous single transaction — a resource-limit DoS of the RPC handler.

### Impact Explanation
An unprivileged (or low-privileged) gRPC client that can reach `RefService.UpdateReferences` can submit an extremely large number of ref updates in one logical transaction. This can:
- Cause the `git update-ref --stdin` subprocess and the Gitaly process to consume excessive memory/CPU while queuing and processing the transaction.
- Hold reference-transaction locks (once `Prepare`/`Commit` executes) for an extended period, blocking other concurrent operations on the same repository (pushes, fetches, other ref updates) — a repository-level denial of service.
- Potentially trigger the same kind of gas/time-limit-analogous failure noted in the original report: transaction size/time exceeding acceptable bounds and failing non-deterministically depending on system load, forcing retries that repeat the same expensive, unbounded work.

### Likelihood Explanation
`UpdateReferences` is a standard, directly callable Gitaly RPC (not gated behind admin-only tooling); any client with repository RPC access (which in GitLab's architecture can include automated internal callers, but the RPC itself performs no batch-size validation) can send a stream with an unbounded number of `Update` messages. There is no explicit maximum enforced in the handler or in `updateref.Updater`, so exploitation requires only crafting a long-lived stream — no race condition or privileged access is needed to trigger the unbounded accumulation.

### Recommendation
Enforce a maximum number of updates (and/or a maximum aggregate stdin payload size) per `UpdateReferences` transaction in `internal/gitaly/service/ref/update_references.go`, rejecting or automatically batching requests that exceed the limit before invoking `Prepare`/`Commit`. Consider streaming intermediate `Prepare`/partial commits for very large update sets, or documenting/enforcing a hard cap analogous to the client-side `listPoolUpstreamsBatchSize` / `batch_size` pattern already used elsewhere in this codebase.

### Proof of Concept
1. Open an `UpdateReferences` streaming RPC against a target repository.
2. Send an initial request with `Repository` set and one `Update`.
3. Continue sending a very large number of subsequent `UpdateReferencesRequest` messages, each containing many `Update` entries (e.g., millions of distinct valid or dummy reference names), without ever closing the stream until the total queued update count is very large.
4. Close the send side, triggering `updater.Commit()` on the server, which must process the entire accumulated batch as a single `git update-ref --stdin` transaction — consuming proportionally large memory/CPU and holding reference locks for the full duration, degrading or denying service to concurrent repository operations.

// Update commands the reference to be updated to point at the object ID specified in newOID. If
// newOID is the zero OID, then the branch will be deleted. If oldOID is a non-empty string, then
// the reference will only be updated if its current value matches the old value. If the old value
// is the zero OID, then the branch must not exist.
//
// A reference transaction must be started before calling Update.
func (u *Updater) Update(reference git.ReferenceName, newOID, oldOID git.ObjectID) error {
	if err := u.expectState(stateStarted); err != nil {
		return err
	}

	return u.write("update %s\x00%s\x00%s\x00", reference.String(), newOID, oldOID)
}

// Commit applies the commands specified in other calls to the Updater. Commit finishes the
// reference transaction and another one must be started before further changes can be staged.
func (u *Updater) Commit() error {
	// Commit can be called without preparing the transactions.
	if err := u.checkState(statePrepared); err != nil {
		if err := u.expectState(stateStarted); err != nil {
			return err
		}
	}

	u.state = stateIdle

	if err := u.setState("commit"); err != nil {
		return err
	}

	return nil
}
