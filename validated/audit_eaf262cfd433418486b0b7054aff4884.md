Audit Report

## Title
Stranded funds in closed `pallet-child-bounties` accounts have no reclaim path, unlike parent bounties - (File: `substrate/frame/child-bounties/src/lib.rs`)

## Summary
`pallet-bounties` was fixed via `reclaim_bounty_funds` to permissionlessly sweep any balance/assets stranded in a closed bounty account back to the treasury, but this call only targets `Self::bounty_account_id(bounty_id)` for parent bounties. [1](#0-0)  `pallet-child-bounties` manages an analogous deterministic sub-account per `(parent_bounty_id, child_bounty_id)` pair that is drained via plain `Currency::transfer` in `claim_child_bounty` and `impl_close_child_bounty`, and the storage record is deleted immediately after, with no equivalent sweep dispatchable ever added to this pallet. [2](#0-1) [3](#0-2) 

## Finding Description
The child-bounty sub-account (`child_bounty_account_id(parent, child)`) remains a stable, computable account after the `ChildBounties` storage entry is removed on claim or close. [4](#0-3) [5](#0-4)  Any balance sent to that address afterward (accidental transfer, dust, or a transfer landing right after the sweep) has no dispatchable path out: `claim_child_bounty`/`close_child_bounty` require a live `ChildBounties` entry, and `pallet-bounties::reclaim_bounty_funds` explicitly operates only on `Self::bounty_account_id(bounty_id)` — the parent bounty account — not on any child-bounty sub-account. [6](#0-5)  The PR that introduced `reclaim_bounty_funds` for `pallet-bounties` only bumped `pallet-child-bounties` as a `patch` (dependency version bump), confirming no equivalent logic was added to the child-bounties pallet. [7](#0-6)  A search of `pallet-child-bounties`'s dispatchable calls confirms there is no `reclaim_bounty_funds`-style extrinsic in that pallet.

## Impact Explanation
This matches the "permanent user-fund lock" impact category in the gate: funds sent to a closed/claimed child-bounty sub-account are permanently unrecoverable through any exposed extrinsic, with no signed, root, or permissionless call in `pallet-child-bounties` able to move balance out of an account no longer tracked by a live `ChildBounties` entry.

## Likelihood Explanation
The condition is reachable via an ordinary, unprivileged `Balances::transfer` to a deterministic, publicly computable account address (`child_bounty_account_id(parent, child)`) after the child bounty has been claimed or closed — no malicious validator, governance, or leaked-key assumption is required, satisfying the "public entrypoint / unprivileged attacker" bar. It requires either an accidental transfer or a transfer that lands after the balance sweep in the claim/close transaction, which is plausible but not the default/likely path (self-inflicted or race-condition dependent), making likelihood moderate rather than high.

## Recommendation
Add a permissionless `reclaim_bounty_funds`-style extrinsic to `pallet-child-bounties`, mirroring `pallet-bounties::reclaim_bounty_funds`, that for a `(parent_bounty_id, child_bounty_id)` no longer present in `ChildBounties` storage sweeps any remaining balance from `child_bounty_account_id(parent_bounty_id, child_bounty_id)` to the parent bounty account or treasury, using the same `Pays::No`-on-success/`Pays::Yes`-on-no-op pattern to prevent griefing.

## Proof of Concept
1. Create and fund a parent bounty; add, accept, and award a child bounty; call `claim_child_bounty`. The `ChildBounties` entry for `(parent_id, child_id)` is removed [4](#0-3)  but `child_bounty_account_id(parent_id, child_id)` remains a valid account.
2. Any account calls `Balances::transfer(child_bounty_account_id(parent_id, child_id), X)`.
3. No extrinsic in `pallet-child-bounties` can move `X` out: `claim_child_bounty`/`close_child_bounty` require a live storage entry (`InvalidIndex` otherwise), and `pallet-bounties::reclaim_bounty_funds` only targets `bounty_account_id(parent_id)`. [6](#0-5)  `X` is permanently stranded.

		#[pallet::call_index(11)]
		#[pallet::weight(<T as Config<I>>::WeightInfo::reclaim_bounty_funds())]
		pub fn reclaim_bounty_funds(
			origin: OriginFor<T>,
			#[pallet::compact] bounty_id: BountyIndex,
		) -> DispatchResultWithPostInfo {
			ensure_signed(origin)?;

			// A live bounty still manages its account, so leave it untouched.
			ensure!(!Bounties::<T, I>::contains_key(bounty_id), Error::<T, I>::BountyStillActive);

			debug_assert!(
				T::ChildBountyManager::child_bounties_count(bounty_id) == 0,
				"child bounties should not exist for a closed bounty"
			);

			let bounty_account = Self::bounty_account_id(bounty_id);
			let treasury_account = Self::account_id();

			let transferred = T::TransferAllAssets::force_transfer_all_assets(
				&bounty_account,
				&treasury_account,
			)?;

			// Free only if something moved, otherwise paid to prevent griefing.
			if !transferred {
				return Ok(Pays::Yes.into());
			}

			Self::deposit_event(Event::<T, I>::BountyFundsReclaimed { bounty_id });

			Ok(Pays::No.into())
		}
