### Title
Unsigned Integer Underflow in Reftable Block Parsing Leads to Out-of-Bounds Read / Panic (DoS) - (File: internal/git/reftable/reftable.go)

### Summary
`internal/git/reftable/reftable.go`'s `parseRefBlock` computes `b.RestartStart` using unsigned (`uint`) subtraction on values partially derived from the reftable file's own bytes (`currentBS`, and `b.RestartCount` which is read directly off disk via `binary.Read`). There is no check that `currentBS - 2 - 3*RestartCount` cannot go negative before the subtraction is performed on `uint`, mirroring the audited Solidity bug class of subtracting an attacker/data-controlled operand from a balance without a `>=` sanity check first.

### Finding Description
In `parseRefBlock`: [1](#0-0) 

`currentBS` comes from `extractBlockLen`, which reads 3 bytes straight out of the reftable data as a big-endian integer: [2](#0-1) 

`b.RestartCount` is a `uint16` read directly from the block trailer: [3](#0-2) 

All of `blockStart`, `currentBS`, and `RestartCount` are `uint`/`uint16` types. The expression `blockStart + currentBS - 2 - 3*uint(b.RestartCount)` is unsigned arithmetic. If a crafted or corrupted `.ref` table has a small `currentBS` (or `currentBS < 2`) combined with a large `RestartCount` (up to 65535), `3*RestartCount` can exceed `blockStart+currentBS-2`, causing the subtraction to wrap around to a value near `math.MaxUint64` instead of erroring out. This is functionally identical to the reported Solidity bug class: an unchecked subtraction of a data-controlled value from another value, performed in an unsigned/unsigned-like domain, with no `if a >= b` guard before subtracting.

The resulting corrupted `b.RestartStart` is then used as the loop bound and as the `blockEnd` parameter passed into `getVarInt` in `getRefsFromBlock`: [4](#0-3) 

Because `getVarInt`'s only sanity check is `start > blockEnd` (line 211), and `blockEnd` (i.e., the wrapped `RestartStart`) is now enormous, this check is effectively disabled. Parsing continues walking `idx` far past the true end of the `src` byte slice loaded into memory via `io.ReadAll` in `GetReferences`: [5](#0-4) 

Eventually a slice expression such as `src[start]`, `prefix[:prefixLength]`, `src[idx:idx+suffixLength]`, or `src[idx:idx+uint(hashSize)]` will index past `len(src)`, producing a Go runtime "slice bounds out of range" panic.

### Impact Explanation
This is reached whenever Gitaly parses a reftable-backend `.ref` file, e.g. during replication/backup validation, transaction-manager reference bookkeeping, and other paths that call `reftable.ParseTable(...).GetReferences()` on tables under `<repo>/reftable/`. If such a table can be corrupted or crafted (e.g., through repository restore/import flows, replication of a maliciously crafted repository, or any RPC path that ends up parsing an untrusted reftable file), the panic causes a crash of the goroutine handling the RPC — a denial-of-service condition against the handler processing that repository's references. This matches the "DoS of a handler" acceptance criterion for this scan: an unprivileged, data-driven arithmetic bug reachable through repository content that Gitaly parses on behalf of ordinary storage/replication/fetch operations, not requiring a privileged actor.

### Likelihood Explanation
Likelihood depends on whether the `.ref` table content is attacker-influenceable (e.g. via `FetchRemote`, repository restore, or replication of another node's on-disk reftable data) versus being always locally generated by trusted `git` internals. Given the constraints of this scan (no filesystem/browser access, index-only view), I could not fully trace every RPC-reachable caller of `reftable.ParseTable`/`GetReferences` to confirm an unprivileged, network-triggerable path with full certainty — callers found in the index are primarily in `internal/gitaly/storage/storagemgr/partition/reftable.go`, `transaction_manager.go`, `backup/repository.go`, and test helpers. This should be validated further with full repository access, but the underflow itself is a clear, unguarded root-cause bug matching the reported bug class.

### Recommendation
Add explicit bounds checks before the subtraction in `parseRefBlock`, refusing to parse (returning an error) if `currentBS < 2` or if `3*uint(b.RestartCount) > blockStart+currentBS-2`, analogous to the suggested `if (usdBalance[msg.sender] >= _amount)` guard in the original finding:
```go
if currentBS < 2 || 3*uint(b.RestartCount) > blockStart+currentBS-2 {
    return nil, fmt.Errorf("invalid restart count %d for block length %d", b.RestartCount, currentBS)
}
b.RestartStart = blockStart + currentBS - 2 - 3*uint(b.RestartCount)
```
Additionally, harden `getVarInt` and the slicing operations in `getRefsFromBlock` to check `idx`/`idx+len` against `len(src)` before slicing, so any remaining corrupted offsets return a parse error instead of panicking.

### Proof of Concept
Construct a `.ref` reftable file where a ref block's length field (read by `extractBlockLen`) is a small value (e.g., 4) and whose 2-byte restart-count trailer at `blockStart+currentBS-2` encodes a `RestartCount` of 65535 (`0xFFFF`). Then:
1. `currentBS = 4`
2. `b.RestartStart = blockStart + 4 - 2 - 3*65535` → since this is `uint` arithmetic, `3*65535 = 196605 > blockStart+2`, so the subtraction underflows to a value near `math.MaxUint64`.
3. Calling `Table.GetReferences()` on this table will enter `getRefsFromBlock` with `b.RestartStart` ≈ `math.MaxUint64`, causing `getVarInt`'s bound check to never trigger, and the loop will index `src` past its length, panicking with "slice bounds out of range" once `idx` exceeds `len(src)`.

```go
func (t *Table) parseRefBlock(src []byte, headerOffset, blockStart, blockEnd uint) ([]git.Reference, error) {
	currentBS := t.extractBlockLen(src, blockStart+headerOffset)

	fullBlockSize := t.blockSize
	if fullBlockSize == 0 {
		fullBlockSize = currentBS
	} else if currentBS < fullBlockSize && currentBS < (blockEnd-blockStart) && src[blockStart+currentBS] != 0 {
		fullBlockSize = currentBS
	}

	b := &block{
		BlockStart:    blockStart + headerOffset,
		FullBlockSize: fullBlockSize,
	}

	if err := binary.Read(bytes.NewBuffer(src[blockStart+currentBS-2:]), binary.BigEndian, &b.RestartCount); err != nil {
		return nil, fmt.Errorf("reading restart count: %w", err)
	}

	b.RestartStart = blockStart + currentBS - 2 - 3*uint(b.RestartCount)

	return t.getRefsFromBlock(src, b)
```
