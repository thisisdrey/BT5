### Title
Floor-sized debt positions can never be liquidated when `maxLiquidable < 100%` - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
`Pool.liquidate` enforces two independent bounds on `amountToRepay_`: (1) it must be `<= maxLiquidable` fraction of the account's debt, and (2) the remaining debt must be either zero or `>= debtFloorInUsd`. For any account whose debt value lies in the range `[debtFloorInUsd, debtFloorInUsd / (1 - maxLiquidable))`, both bounds fail simultaneously: a partial repayment leaves sub-floor debt (`RemainingDebtIsLowerThanTheFloor`), while a full repayment exceeds the `maxLiquidable` cap (`AmountGreaterThanMaxLiquidable`). Every `liquidate` call against such a position reverts unconditionally, permanently blocking liquidation of an entire class of positions — a liveness/availability failure analogous to the MySQL repeatable-crash DoS class.

### Finding Description
In `Pool.liquidate`:

```solidity
// contracts/Pool.sol
if (amountToRepay_.wadDiv(_debtTokenBalance) > maxLiquidable) {
    revert AmountGreaterThanMaxLiquidable();          // line 567-569
}
if (debtFloorInUsd > 0) {
    uint256 _newDebtInUsd = masterOracle().quoteTokenToUsd(
        address(syntheticToken_),
        _debtTokenBalance - amountToRepay_
    );
    if (_newDebtInUsd > 0 && _newDebtInUsd < debtFloorInUsd) {
        revert RemainingDebtIsLowerThanTheFloor();    // line 576-578
    }
}
```

Let `D` = account debt in USD and `m` = `maxLiquidable` (e.g., `0.5e18`). A valid liquidation amount `a` must satisfy both `a <= m*D` and (`D - a >= floor` or `a == D`). When `floor <= D < floor / (1 - m)`:
- `a = D` (full close) requires `D <= m*D`, false since `m < 1`.
- Any `a <= m*D` leaves `D - a >= D - m*D = D(1-m) < floor` while `> 0`, so it reverts.

There is no valid `a`, so the position is unliquidatable by construction.

Such debts are reachable by an unprivileged user: `DebtToken._mint` only enforces the *lower* bound `balanceBefore + amount >= debtFloorInUsd` (contracts/DebtToken.sol:583-588), so borrowing exactly at the floor is permitted. Once any of these positions becomes unhealthy (collateral price decline, accrued interest pushing debt up is not required — the band already holds at mint time), no liquidator can ever clear it. `quoteLiquidateMax`/`quoteLiquidateOut` cannot help because the failure is in `liquidate`'s own guard clauses. The same dead band affects `DebtToken.repay` (contracts/DebtToken.sol:442-450), which also blocks partial repayments that would leave sub-floor debt, though `repayAll` still works for the borrower.

### Impact Explanation
Permanent freezing of funds and protocol insolvency: collateral backing a floor-band unhealthy position can never be seized by liquidators, so bad debt accrues in the `DebtToken`/`SyntheticToken` accounting while the collateral is locked in `Treasury`. An attacker can deliberately manufacture this state — deposit minimum collateral, `issue` exactly `debtFloorInUsd` worth of synth (`DebtToken.issue`, callable by anyone with collateral), then wait for or force the position unhealthy via same-transaction price moves — creating unliquidatable bad debt at will and repeatedly across accounts. Availability of the liquidation function for the whole floor range is permanently lost, matching the "repeatable, unconditional denial of the affected operation" bug class.

### Likelihood Explanation
High whenever both parameters are active: `debtFloorInUsd > 0` (the feature exists specifically for deployed pools; `updateDebtFloor` exists and tests exercise `$3,000` floors) and `maxLiquidable < 1e18` (test suite uses `0.5`). No privileged role, external oracle failure, or victim interaction is needed: `issue` is permissionless given collateral, and the band boundary is a pure arithmetic consequence of the two checks. The attacker cost is just the collateral for a floor-sized position, which is intentionally the cheapest possible borrow.

### Recommendation
In `Pool.liquidate` (and equivalently in `DebtToken.repay`), permit a repayment that leaves sub-floor debt when it is the *maximum allowed* partial close, or clamp `amountToRepay_`/`maxLiquidable` so that debts in `[floor, floor/(1-m))` can be fully closed. Concretely, compute the remaining-debt floor check as:

```solidity
uint256 _maxRepay = _debtTokenBalance.wadMul(maxLiquidable);
uint256 _remaining = _debtTokenBalance - amountToRepay_;
if (_newDebtInUsd > 0 && _newDebtInUsd < debtFloorInUsd
        && amountToRepay_ < _maxRepay) { // allow closing when capped
    revert RemainingDebtIsLowerThanTheFloor();
}
```

or simply allow full close (`amountToRepay_ == _debtTokenBalance`) to bypass the `maxLiquidable` cap when the resulting remainder would otherwise violate the floor.

### Proof of Concept
Hardhat sketch (extends existing `Pool.test.ts` fixtures — `pool`, `msEth`, `msEthDebtToken`, `msdMET`, `liquidator`, `alice`):

```ts
it('floor-band debt is unliquidatable', async function () {
  const FLOOR = parseEther('2000');            // $2,000
  await pool.updateDebtFloor(FLOOR);
  await pool.updateMaxLiquidable(parseEther('0.5')); // 50%

  // alice deposits just enough MET and borrows exactly the floor
  // issue() passes: balanceBefore + amount == floor (DebtToken._mint, line 583)
  await depositToken.connect(alice).deposit(collateralFor2000Usd, alice.address);
  await msEthDebtToken.connect(alice).issue(FLOOR.div(ethPrice), alice.address);

  // oracle pushes MET price down -> alice is unhealthy
  await masterOracle.updatePrice(met.address, droppedPrice);
  const { _isHealthy } = await pool.debtPositionOf(alice.address);
  expect(_isHealthy).false;

  const debt = await msEthDebtToken.balanceOf(alice.address);

  // full close: exceeds maxLiquidable
  await expect(
    pool.connect(liquidator).liquidate(msEth.address, alice.address, debt, msdMET.address)
  ).revertedWithCustomError(pool, 'AmountGreaterThanMaxLiquidable');

  // max allowed partial close (50%): leaves debt < floor
  await expect(
    pool.connect(liquidator).liquidate(msEth.address, alice.address, debt.div(2), msdMET.address)
  ).revertedWithCustomError(pool, 'RemainingDebtIsLowerThanTheFloor');

  // any a < 50% also leaves sub-floor remainder -> every liquidate() reverts;
  // alice's collateral and bad debt are permanently locked in the pool.
});
```

Uncertain aspects: the deployed on-chain values of `debtFloorInUsd` and `maxLiquidable` per pool were not confirmed from `deployments/` in this review; the finding is valid whenever `debtFloorInUsd > 0` and `maxLiquidable < 1e18`, both of which are supported, tested configurations. If a production pool runs with `maxLiquidable == 1e18`, the dead band collapses and the issue does not manifest there.
