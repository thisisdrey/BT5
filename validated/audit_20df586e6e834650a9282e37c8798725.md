### Title
Snowbridge `outbound-queue-v2` accepts and enqueues Ethereum-bound messages with no operating-mode / halt gate, unlike v1's `Halted` check - ([File: bridges/snowbridge/pallets/outbound-queue-v2/src/send_message_impl.rs])

### Summary
The v1 Snowbridge outbound queue gates message delivery on an `OperatingMode` "halted" check so governance can stop processing during an incident, mirroring the missing-`unpaused` pattern in the source report. The v2 outbound queue pallet keeps the `Halted` error variant and an `OperatingModeChanged` event, but never wires an `OperatingMode` storage item, `set_operating_mode` extrinsic, or any halt check into its `deliver`/`do_process_message`/`submit_delivery_receipt` paths — the pause mechanism is declared but not enforced, exactly analogous to `authRedeem` missing `unpaused(p)`.

### Finding Description
In `bridges/snowbridge/pallets/outbound-queue/src/send_message_impl.rs`, the v1 `deliver` function explicitly checks the pallet's halt state before enqueueing a message (except for the primary governance channel): [1](#0-0) 

The v1 pallet doc also states this halt mechanism is its governance safety valve: `[Call::set_operating_mode]: Set the operating mode` [2](#0-1) .

The v2 pallet (`bridges/snowbridge/pallets/outbound-queue-v2`) was built with the same conceptual halt support — it defines `Error::Halted` and `Event::OperatingModeChanged`: [3](#0-2) [4](#0-3) 

However, there is no `OperatingMode` storage item, no `set_operating_mode` call, and no `is_halted()` check anywhere in the pallet. The `deliver` implementation in `send_message_impl.rs` unconditionally enqueues the message: [5](#0-4) 

Likewise `do_process_message` (which converts, commits, and creates the `PendingOrder` for relayer rewards) and `submit_delivery_receipt` (which pays out relayer rewards) perform no halt check: [6](#0-5) [7](#0-6) 

The `Error::Halted` variant is therefore dead code — it is declared but never returned by any code path in this pallet, confirming the guard exists in name only.

### Impact Explanation
This maps directly to the "Message queues, bridge markers, receipts, and payout state must only advance after decode, dispatch, execution, and settlement succeed atomically" pivot and the "public underpriced work that degrades block production or stalls bridge processing" gate. If governance (or an automated incident response, e.g., after a bug discovered in AssetHub's V2 XCM converter or gateway contract) intends to halt Snowbridge V2 outbound processing during an emergency, they have no functional lever for this pallet: messages keep being accepted, converted, committed into the Merkle root, and relayed to Ethereum, and relayer rewards keep being paid out via `process_delivery_receipt`, even though the pallet's own error/event types imply a halt capability exists. This can allow continued unauthorized/incorrect bridge settlement during exactly the window an operator believes the bridge is paused, contradicting expected chain behavior and potentially compounding a live incident (duplicate/erroneous settlement continuing unabated).

### Likelihood Explanation
High confidence this is a real code gap, not a design choice, because: (1) v1 explicitly implements and documents halting as the safety mechanism for the identical message-queue architecture that v2 reuses; (2) v2's own `Error`/`Event` enums retain `Halted`/`OperatingModeChanged` — a strong signal that a halt gate was intended for parity with v1 but never implemented after the outbound-queue-v2 refactor; (3) `grep` across the whole `outbound-queue-v2` crate shows zero occurrences of `operating_mode`, `is_halted`, or `set_operating_mode` outside the two textual mentions in `lib.rs`.

### Recommendation
Add an `OperatingMode` storage item and a `set_operating_mode` governance extrinsic to `outbound-queue-v2::Pallet` (mirroring v1), and gate `SendMessage::deliver` in `send_message_impl.rs`, `do_process_message`, and `submit_delivery_receipt` on `!Self::operating_mode().is_halted()` (with a governance-channel bypass equivalent to v1's `PRIMARY_GOVERNANCE_CHANNEL` carve-out), returning `Error::<T>::Halted` / `SendError::Halted` when halted, so the pallet's own declared halt semantics are actually enforced.

### Proof of Concept
1. Assume Snowbridge V2 governance wants to halt outbound processing (e.g., because of a discovered flaw in the V2 XCM converter or Ethereum gateway) via whatever admin path exists for `outbound-queue-v2`.
2. Because no `OperatingMode` storage/extrinsic exists in this pallet, there is no way to set a halted state at all — any attempt to "pause" outbound-queue-v2 as done for v1 is a no-op.
3. An attacker or any user can continue calling into the V2 outbound path (e.g., via XCM `ExportMessage`/`snowbridge_pallet_system_v2::send`), and `Pallet::deliver` in `bridges/snowbridge/pallets/outbound-queue-v2/src/send_message_impl.rs` (lines 34-43) enqueues it unconditionally.
4. `do_process_message` (lib.rs lines 343-443) processes it into `Messages`/`MessageLeaves`/`PendingOrders` regardless of any intended halt, and `submit_delivery_receipt`/`process_delivery_receipt` (lines 293-480) continue to pay relayer rewards from `PendingOrders`, so bridge processing and payout continue unabated during what should be a halted state.

	fn deliver(ticket: Self::Ticket) -> Result<H256, SendError> {
		let origin = AggregateMessageOrigin::Snowbridge(ticket.channel_id);

		if ticket.channel_id != PRIMARY_GOVERNANCE_CHANNEL {
			ensure!(!Self::operating_mode().is_halted(), SendError::Halted);
		}

		let message = ticket.message.as_bounded_slice();

		T::MessageQueue::enqueue_message(message, origin);
		Self::deposit_event(Event::MessageQueued { id: ticket.message_id });
		Ok(ticket.message_id)
	}
