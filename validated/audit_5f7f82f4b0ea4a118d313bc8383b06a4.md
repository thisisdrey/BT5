## Title
`DeleteAccountAction` does not validate `beneficiary_id` against the account being deleted or its existence, permanently burning the account's balance instead of refunding it - (File: `runtime/runtime/src/actions.rs`)

### Summary
The `DeleteAccount` action lets the account owner specify an arbitrary `beneficiary_id` to receive the account's remaining balance. Neither `validate_action`/`validate_actions` nor `action_delete_account` nor `check_actor_permissions` verify that `beneficiary_id` is distinct from the account being deleted, or that it refers to an account that actually exists. Because balance payouts are sent as a "refund" receipt, and refund receipts are explicitly barred from creating new (named) accounts, a `beneficiary_id` that does not resolve to an existing account causes the whole balance to be irrecoverably burned rather than delivered anywhere.

### Finding Description
`action_delete_account` unconditionally builds a refund receipt addressed to `delete_account.beneficiary_id` and then deletes the account: [1](#0-0) 

There is no check anywhere in the delete-account path comparing `beneficiary_id` to `account_id`:
- `check_actor_permissions` only verifies `actor_id == account_id` and that `locked` is zero for `DeleteAccount`; it never inspects `beneficiary_id`. [2](#0-1) 
- `validate_action`/`validate_actions` only enforce that `DeleteAccount` is the last action in the list; no test or code path checks `beneficiary_id` against `account_id` or account existence. [3](#0-2) 

The payout is produced via `Receipt::new_balance_refund`, which is treated as a **refund** receipt (`predecessor_id == "system"`). Refund receipts are explicitly documented and coded to *not* be eligible for implicit account creation: [4](#0-3) 

If the `Transfer` action inside the refund receipt targets a non-existing account (which is exactly what happens when `beneficiary_id` equals the very account being deleted — since that account no longer exists once `action_delete_account` runs `remove_account` — or when `beneficiary_id` is any other non-existent/mistyped account), `check_account_existence` returns `AccountDoesNotExist` for the refund's `Transfer` action. Because the receipt is a system/refund receipt, its failure is converted into a **burn** rather than a retry or bounce-back: [5](#0-4) 

This burn-on-failed-refund behavior is also documented generally: [6](#0-5) 

### Impact Explanation
Any ordinary account owner who submits (or whose wallet/front-end submits due to a bug) a `DeleteAccount` action with `beneficiary_id` set to:
1. the same account being deleted (a very natural mistake, since the common "delete my own account" helper defaults the beneficiary to the signer, and self-delete implies signer == account == beneficiary), or
2. any account id that does not currently exist (typo, stale reference, front-end default/placeholder value),

will have their entire remaining account balance permanently burned instead of transferred to any recipient. This is a direct, permanent loss of user funds triggered purely by a missing sanity check on a user-supplied parameter — the same bug class as the external report's "missing zero checks," where an unchecked destination parameter (here, `beneficiary_id`) causes irrecoverable loss of funds when it is invalid/self-referential. Unlike a normal `Transfer` to a bad address (which fails the whole transaction/receipt and refunds the sender), here the "refund" mechanism itself is the vector, and refunds-of-refunds are not attempted — the deposit is unconditionally burnt on failure.

### Likelihood Explanation
This requires no privileged access and is reachable by any signer deleting their own account — it is a completely ordinary, unprivileged client transaction (`DeleteAccountAction`). The most likely trigger is a client/SDK/wallet bug (e.g., an uninitialized or mis-defaulted `beneficiary_id` variable pointing back at the account itself, or at an account that doesn't exist), exactly mirroring the exploit scenario in the source report ("a bug in the front end ... uses the value of an uninitialized variable to construct the transaction"). Since the protocol performs no defensive validation, such a bug in any calling layer directly and silently destroys user funds with no way to detect or reverse it before the account is deleted.

### Recommendation
- **Short term**: In `action_delete_account` (or in `validate_action`/`check_actor_permissions`), reject `DeleteAccountAction` when `beneficiary_id == account_id`, and/or require that `beneficiary_id` resolve to an existing account before performing the deletion (looking it up the same way `check_account_existence` does for other receiver accounts), returning a clear `ActionError` instead of silently burning funds via a failed refund.
- **Long term**: Audit all code paths that route balance payouts through the "refund" receipt mechanism (which intentionally cannot create accounts) to ensure that a user-controlled destination parameter can never be silently swallowed/burned; consider making beneficiary payouts a first-class `Transfer` receipt (which does support implicit account creation and produces a proper failure/refund cycle to the predecessor) rather than a refund receipt, or explicitly validate the beneficiary before scheduling the deletion.

### Proof of Concept
1. Alice funds and owns account `alice.near` with a non-zero balance.
2. Alice submits a transaction with `signer_id = alice.near`, `receiver_id = alice.near`, and a single `DeleteAccount(DeleteAccountAction { beneficiary_id: "alice.near".parse().unwrap() })` action (i.e., `beneficiary_id == account_id`), analogous to how `delete_account_with_beneficiary_set`/`delete_account` helpers are invoked in the test-suite (`integration-tests/src/user/mod.rs:249-268`).
3. `action_delete_account` executes: `account_balance > 0` → pushes `Receipt::new_balance_refund(&"alice.near", account_balance)`, then calls `remove_account`, deleting `alice.near` from state. [1](#0-0) 
4. The generated balance-refund receipt (predecessor `"system"`) is later processed against `alice.near`, which no longer exists. `check_account_existence` sees `account.is_none()` for a `Transfer` action and calls `check_transfer_to_nonexisting_account`, which — because refund receipts are not implicit-account-creation eligible and `alice.near` is a named (non-implicit) account — returns `AccountDoesNotExist`. [4](#0-3) 
5. Because the receipt's predecessor is `"system"` and it fails, the runtime burns the deposit instead of refunding it: [5](#0-4) 
6. Result: Alice's entire remaining account balance is permanently destroyed with no recipient, purely because `beneficiary_id` was not validated against the account being deleted (or its existence) before scheduling the payout.

```rust
        // - Transfer action has to be the only action in the transaction to avoid
```

```markdown
Refund receipts are identified by having `predecessor_id == "system"`. They are also special because they don't cost any gas to generate or execute. As a result, they also do not contribute to the block gas limit.

If the execution of a refund fails, the refund amount is burnt.
The refund receipt is an `ActionReceipt` that consists of a single action `Transfer` with the `deposit` amount of the refund.
```
