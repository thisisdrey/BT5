### Title
All-or-nothing multi-asset price resolution in `get-assets`/`price-multi-resolve` freezes unrelated positions on a single stale oracle - (File: mainnet/contracts/market/v0-4-market.clar)

### Summary
`get-assets` prices every collateral asset that a user has *enabled* (union of the market's enabled bitmap and the user's own mask) in a single `fold` via `price-multi-resolve`/`iter-price-multi`. If resolution of any single asset in that combined list fails (stale timestamp, oracle error, confidence check failure), the accumulator sets `valid: false` and the whole call aborts with `ERR-ORACLE-MULTI`, even though the user's actual action (e.g. `borrow`, `withdraw`, `liquidate` health check) may be entirely unrelated to the asset that failed to price.

### Finding Description
`price-multi-resolve` batches price resolution for the full asset list and short-circuits the entire batch to failure the moment one entry fails: [1](#0-0) 

`get-assets` builds this batch from the *enabled* bitmap merged with the caller's own position mask — i.e. all collateral types the user has ever enabled, not just the assets touched by the current operation: [2](#0-1) 

This mirrors exactly the SeaportProxy `_executeNonAtomicOrders` bug class: fee transfers were batched across independent per-order operations, so a failure attributable to one order caused the whole batch to revert and undo otherwise-valid, independent orders. Here, price resolution is batched across independent per-asset oracle reads inside a health-check/valuation routine consumed by market entry points (`borrow`, `withdraw`, `liquidate`), so a stale/invalid price on *one* enabled collateral asset the user isn't even interacting with in the current call aborts the *entire* transaction for that user, blocking legitimate operations on other, perfectly healthy assets.

### Impact Explanation
A user with multiple enabled collateral types (e.g. STX + sBTC + USDC) who only wants to `withdraw` STX or check health for a `borrow` is blocked entirely if the sBTC or USDC oracle feed becomes stale (exceeds `max-staleness`) or fails confidence checks — conditions entirely outside the user's control and unrelated to the asset they are actually operating on. This is a temporary freezing of the user's own funds/collateral, since no workaround exists within the contract to price only the assets relevant to the current operation; the user must wait for the third-party oracle feed for an unrelated asset to refresh before they can act on their own healthy position.

### Likelihood Explanation
Any user enabling more than one collateral asset is exposed. Oracle staleness or confidence-check failures are routine occurrences (feed downtime, low liquidity spikes, network congestion delaying price pushes) and are explicitly anticipated by the protocol's own `max-staleness`/confidence-ratio checks, meaning this all-or-nothing batching failure mode is reachable during normal, non-adversarial operation — not merely a contrived edge case.

### Recommendation
Only resolve/require prices for assets actually relevant to the operation and its health check (i.e. assets with nonzero collateral/debt balances in the user's specific position, or only the assets being deposited/withdrawn/borrowed/repaid), rather than pricing the full enabled-bitmap union unconditionally. Alternatively, allow `price-multi-resolve` to skip/zero-out entries whose failure does not affect the specific check being performed (e.g., partial price lists per operation) instead of failing the entire fold on a single entry.

### Proof of Concept
1. User enables STX and USDC as collateral, and has healthy positions in both.
2. USDC's Pyth/DIA feed becomes stale beyond `max-staleness` (a routine feed outage) or fails the confidence-ratio check in `check-confidence`.
3. User calls `withdraw` (or `borrow`) against their STX collateral only — an operation that does not logically require the USDC price.
4. `get-assets` is invoked as part of the health check, which calls `price-multi-resolve` over the full enabled mask (STX + USDC).
5. `iter-price-multi` hits the USDC entry, `price-resolve` fails the staleness/confidence assertion, `valid` flips to `false`, and `price-multi-resolve` returns `ERR-ORACLE-MULTI`.
6. The entire `withdraw`/`borrow` call reverts, even though the user's STX position and the operation itself never needed the USDC price — freezing the user's ability to manage their STX collateral until the unrelated USDC feed recovers.

(define-private (price-multi-resolve
  (data (list 64 { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint }))
  (aids (list 64 uint)))
  (let ((init { output: (list), valid: true, aids: aids, idx: u0 })
        (response (fold iter-price-multi data init)))
    (asserts! (get valid response) ERR-ORACLE-MULTI)
    (ok (get output response))))

(define-private (iter-price-multi
  (oracle-data { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint })
  (acc { output: (list 64 uint), valid: bool, aids: (list 64 uint), idx: uint }))
  (let ((valid (get valid acc))
        (skip? (asserts! valid acc))
        (asset-ids (get aids acc))
        (idx (get idx acc))
        ;; resolve price - will use cache for ztokens
        (price (unwrap! (price-resolve oracle-data) (merge acc { valid: false })))
        (next (unwrap-panic (as-max-len? (append (get output acc) price) u64))))
    { output: next,
      valid: true,
      aids: asset-ids,
      idx: (+ idx u1) }))

(define-private (user-safe-mask (mask-user uint) (mask-enabled uint))
  (let ((enabled-collateral (bit-and mask-enabled MAX-U64))
        (user-collateral (bit-and mask-user MAX-U64))
        (user-debt (/ (bit-and mask-user DEBT-MASK) (pow u2 DEBT-OFFSET)))
        (collateral-match (bit-and user-collateral enabled-collateral)))
    (bit-or collateral-match user-debt)))

(define-private (mask-to-list-internal (mask uint) (offset uint) (iter-list (list 64 uint)))
  (let ((init { mask: mask, offset: offset, result: (list) })
        (out (fold mask-to-list-iter iter-list init)))
    (get result out)))

(define-private (mask-to-list-iter (p uint) (acc {mask: uint, offset: uint, result: (list 64 uint)}))
  (let ((mask (get mask acc))
        (offset (get offset acc))
        (has? (asserts! (> (bit-and mask (pow u2 p)) u0) acc))
        (result (get result acc))
        (value (if (is-eq offset u0) p (- p offset)))
        (new (as-max-len? (append result value) u64)))
    (merge acc { result: (unwrap-panic new) })))

(define-private (mask-to-list-collateral (mask uint))
  (mask-to-list-internal mask u0 ITER-UINT-64))
