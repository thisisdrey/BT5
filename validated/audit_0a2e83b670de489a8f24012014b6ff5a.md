Audit Report

## Title
Snowbridge V1 inbound token transfer permanently locks Ethereum-side funds on destination XCM execution failure, with no refund path - ([File: bridges/snowbridge/primitives/inbound-queue/src/v1.rs])

## Summary
`Pallet::submit` in `bridges/snowbridge/pallets/inbound-queue/src/lib.rs` irreversibly advances the per-channel `Nonce`, rewards the relayer, and burns the XCM teleport fee before the resulting XCM program is actually executed on AssetHub. The XCM programs built by `convert_send_token` and `convert_send_native_token` in `bridges/snowbridge/primitives/inbound-queue/src/v1.rs` place no `SetAssetClaimer`/appendix protection for the *principal* bridged asset, so if the destination-side program fails at or before `BuyExecution`/`ReserveAssetDeposited`/`WithdrawAsset` (e.g. due to an underfunded fee), the principal value is never even placed into the XCM holding register — it is simply lost, with the Ethereum-side lock already irreversible and the nonce already consumed.

## Finding Description
`Pallet::submit` performs, strictly in order: nonce advancement via `<Nonce<T>>::try_mutate` (guarded against replay by `InvalidNonce`), relayer reward transfer from the destination-parachain sovereign account, `do_convert` to build the XCM, `Self::burn_fees` (irreversibly burning/checking-out the referenced teleport fee asset), and finally `Self::send_xcm` to enqueue the message. [1](#0-0) 

Once `send_xcm` succeeds, none of this can be undone: the nonce cannot be resubmitted, and the fee has already been burned. The actual value transfer depends entirely on asynchronous processing of the enqueued XCM by `pallet_message_queue` on AssetHub, which can independently fail and simply emits `Event::Processed { success: false, .. }` with no compensating action. [2](#0-1) 

Examining `convert_send_token`, the instruction sequence is `ReceiveTeleportedAsset(fee)`, `BuyExecution(fee)`, `DescendOrigin`, `UniversalOrigin`, `ReserveAssetDeposited(asset)`, `ClearOrigin`, then a destination-dependent tail. [3](#0-2)  Critically, `ReserveAssetDeposited(asset)` — the instruction that actually credits the principal token into the XCM holding register — executes only *after* `BuyExecution`. If `BuyExecution` fails (e.g., because the Ethereum-side `fee` parameter is insufficient to cover AssetHub XCM execution), the XCM aborts before `ReserveAssetDeposited` ever runs. In that case the principal asset is never placed into holding at all, so it cannot even be "trapped" and later claimed via `pallet_xcm::claim_assets`; it is unconditionally unaccounted for on the Polkadot side. Any `SetAppendix` protection that exists is registered *only after* `ReserveAssetDeposited`/`ClearOrigin` in the `Some(dest_para_id)` branch, so it does not cover failures occurring at or before `BuyExecution`. [4](#0-3)  The same structural gap exists in `convert_send_native_token`, whose sequence is `ReceiveTeleportedAsset`, `BuyExecution`, `DescendOrigin`, `UniversalOrigin`, `WithdrawAsset`, `DepositAsset`, with no claimer or appendix at all. [5](#0-4) 

This is a materially weaker design than the V2 converter, which explicitly inserts a `SetHints { hints: [AssetClaimer { location: claimer }] }` instruction *before* `PayFees`/execution-fee spending specifically so that if fees are insufficient, the claimer can still recover the funds — and defaults the claimer to the bridge-owner sovereign account when none is supplied by the message. [6](#0-5)  No equivalent claimer hint exists anywhere in the V1 `convert_send_token`/`convert_send_native_token` paths for the principal asset.

## Impact Explanation
When `BuyExecution` (or any instruction preceding `ReserveAssetDeposited`/`WithdrawAsset`) fails on AssetHub for a `SendToken`/`SendNativeToken` V1 message, the bridged principal value is neither delivered nor trappable/claimable, while: (1) the corresponding Ethereum-side Gateway lock/burn has already occurred, (2) the channel `Nonce` has already been irreversibly advanced so the message cannot be resubmitted, and (3) the fee has already been burned. This is a permanent, unrecoverable loss of user funds with no governance or user-accessible recovery path, matching the "permanent user-fund ... lock" impact category and violating the invariant that bridge settlement should not advance irreversible state (nonce, fee burn) ahead of destination-side execution success.

## Likelihood Explanation
No privileged actor is needed. Any ordinary Ethereum-side bridge user choosing (or being tricked by tooling/fee-market drift into choosing) an AssetHub `fee` value in `SendToken`/`SendNativeToken` that is insufficient to cover the `BuyExecution` step on AssetHub triggers this path directly. The relayer merely needs to submit the already-proven Ethereum event via `InboundQueue::submit`, which is a routine, permissionless action. The repository's own test suite (`register_weth_token_in_asset_hub_fail_for_insufficient_fee`) already demonstrates that an insufficient-fee AssetHub XCM execution failure is a reachable, ordinary condition producing `MessageQueue::Processed { success: false, .. }`. [7](#0-6) 

## Recommendation
In `convert_send_token`/`convert_send_native_token` (`bridges/snowbridge/primitives/inbound-queue/src/v1.rs`), insert a `SetHints { hints: [AssetClaimer { .. }] }` (or `SetAppendix`) instruction anchored to a deterministic, user-recoverable location *before* `BuyExecution` and before any instruction that can fail (mirroring the V2 fix), so that any asset already delivered into holding prior to a failure remains claimable. Additionally, ensure `ReserveAssetDeposited`/`WithdrawAsset` for the principal asset happens before fee-dependent instructions that can abort, or otherwise guarantee that a failure at any point in the program still results in the principal being trappable and claimable by the original sender's derived account, consistent with the V2 `PreparedMessage::claimer` model.

## Proof of Concept
1. Ethereum user submits a `SendToken` message (destination `AccountId32` on AssetHub) via the Gateway with a `fee` value insufficient to cover AssetHub `BuyExecution`, analogous to `INSUFFICIENT_XCM_FEE` used in `register_weth_token_in_asset_hub_fail_for_insufficient_fee`.
2. A relayer calls `InboundQueue::submit`; `Nonce` advances, relayer is rewarded, `do_convert` builds the `convert_send_token` XCM, `burn_fees` burns the referenced fee, `send_xcm` enqueues the message — all per `Pallet::submit`. [8](#0-7) 
3. On AssetHub, `pallet_message_queue` processes the message; `BuyExecution` fails due to insufficient fee before `ReserveAssetDeposited` executes, so the principal asset is never credited into holding; `Event::Processed { success: false, .. }` is emitted with no compensating trap/claim for the principal.
4. The Ethereum-side lock/burn stands permanently, the nonce cannot be resubmitted, and the principal value is unrecoverable — no claimer, appendix, or governance path exists to reclaim it in the V1 converter, unlike the `AssetClaimer`-protected V2 flow. [6](#0-5)
