Based on the code and the repo's own test suite, this claimed vulnerability does not hold up.

**The claimed binding:** wNEAR debited from signer via `Contract::withdraw` == NEAR value of an `on_auth` call that "actually completed" post state-init.

**Why it does not break:**

1. `p.state_init(state_init, NearToken::ZERO)` deploys via a Zero-Balance-Account (ZBA), which NEP-591/616 caps at a hard protocol-level payload limit (~770 bytes total, referenced directly in the `STATE_INIT_GAS` doc comment and encoded in the test helper `ZERO_BALANCE_ACCOUNT_PAYLOAD_LEN = 770 - 100 - 40`). An attacker cannot craft a state_init "close to the 770B limit" that both (a) passes zero deposit and (b) exceeds what the protocol allows for a ZBA — exceeding it causes the state_init action itself to fail outright at the protocol level, not a silent gas-starvation of the subsequent `on_auth` call. The repo's own test `test_auth_call_state_init_via_do_auth_call` (and its execute_intents counterpart) explicitly benchmarks exactly this edge, sweeping key counts/value lengths up to the ZBA boundary and asserting `ExecutionStatus::SuccessValue` for every case within the limit, and failure only for the case that intentionally exceeds it (`ExpectStateInitExceedsZeroBalanceAccountStorageLimit(17)`). [1](#0-0) [2](#0-1) 

2. `STATE_INIT_GAS` (15 TGas) is empirically benchmarked against the maximum-size ZBA state_init and is documented as being scoped precisely to that bound ("Only accounts for deploying via Global Contract ref (NEP-591) with <770B storage which doesn't require storage staking"), and the benchmark tests exercise this max case with varying `min_gas` values, all succeeding. [3](#0-2) [4](#0-3) 

3. Even setting aside the gas math, the `AuthCall` struct explicitly documents that failure does **not** refund the debited wNEAR — this is intended, disclosed behavior, not an unauthorized-fund-movement bug: "NOTE: the `wNEAR` will not be refunded in case of fail." [5](#0-4) 

4. Critically, the scenario requires the **signer themselves** to author the `AuthCall` (including its own `state_init`, `attached_deposit`, and `min_gas`) and sign it — there is no victim whose funds are moved without their own valid signature. The rules require impact of "tokens moved... without the owner's valid signature or authorisation," but here the owner is the one constructing and signing the payload that spends their own wNEAR, with the non-refund risk explicitly documented in the code they are interacting with.

No vulnerability found for this question.
