### Title
Stale `PromiseYieldReceipt` survives `DeleteAccount` and executes against a re-created account, enabling authorization escalation - ([File: runtime/runtime/src/lib.rs])

### Summary
`remove_account` in [1](#0-0)  deletes the `Account`, `ContractCode`, access keys, gas-key nonces and contract data for an account, but never removes any `PromiseYieldReceipt`, `PromiseYieldStatus`, or `YieldIdToDataId`/`DataIdToYieldId` entries keyed to that account. The `PromiseResume` handler in `process_receipt` unconditionally looks up and executes the stored yield receipt against whatever account currently exists at that `account_id`, with no check that the account is the same one that created the yield [2](#0-1) .

### Finding Description
When a contract at account `V` calls `promise_yield_create`, the runtime stores a full serialized `Receipt` (`PromiseYieldReceipt`) keyed by `(receiver_id=V, data_id)` via `set_promise_yield_receipt` [3](#0-2) . This receipt contains the action list (which can include `AddKey`, `Transfer`, `FunctionCall`, etc.) that `V`'s contract chose at creation time.

If `V` subsequently submits a `DeleteAccount` action, `remove_account` clears the account, code, keys, and contract data, but leaves the `PromiseYieldReceipt`, `PromiseYieldStatus`, and yield/data-id mapping trie entries completely untouched [1](#0-0) .

If account name `V` is later re-registered by anyone (e.g., a fresh sub-account under an open top-level account), and a `PromiseResume` receipt for the original `data_id` is later delivered (the original attacker still holds `data_id`, which was returned to them at yield-creation time), `process_receipt` retrieves the stale `PromiseYieldReceipt` via `get_promise_yield_receipt(state_update, account_id, data_receipt.data_id)` using only the current `account_id` — with no check of account continuity, creation height/nonce, or code hash — and unconditionally executes its actions via `apply_action_receipt` against the new account's live state [4](#0-3) .

Because action-receipt execution does not re-validate signer permission (that check only happens at transaction-to-receipt conversion time), an `AddKey(FullAccess)` action embedded in the stale yield receipt will succeed against the new account owner's state without their consent.

### Impact Explanation
This is an authorization-escalation primitive: an attacker can pre-plant an `AddKey(FullAccess)` (or other privileged action) inside a `PromiseYieldReceipt` targeting an account name they control, delete that account, and later — once a different, unrelated party re-registers the same account id — trigger the resume to silently grant themselves a full-access key (or execute other actions) on the new owner's account, without the new owner ever authorizing it. This matches the "authorization escalation across accounts/promises" bounty category.

### Likelihood Explanation
The preconditions are attacker-controlled and cheap: create an account, call `promise_yield_create` from an owned contract to obtain a `data_id`, delete the account, wait for a third party to claim the same account id (feasible for open-registration namespaces), then call `promise_yield_resume` with the retained `data_id`. No validator, RPC operator, or leaked-key access is required — only ordinary signed transactions from an unprivileged account. The attack is repeatable for any account name the attacker can vacate and expect to be re-claimed.

### Recommendation
On `DeleteAccount`, `remove_account` should also enumerate and remove all `PromiseYieldReceipt`, `PromiseYieldStatus`, and `YieldIdToDataId`/`DataIdToYieldId` entries associated with the account (and any corresponding `PromiseYieldTimeout` queue entries), or the `PromiseResume` path should reject/no-op resumes when the yield's original account has been deleted/recreated (e.g., by recording and checking an account creation nonce/incarnation id).

### Proof of Concept
Runtime apply-path integration test (in the style of `test-loop-tests/src/tests/yield_resume.rs` / `yield_timeouts.rs`):
1. Deploy a contract at account `V` that calls `promise_yield_create` with an action list containing `AddKey(FullAccess, attacker_pubkey)`, capturing `data_id`.
2. Submit `DeleteAccount(V, beneficiary)`.
3. Submit `CreateAccount(V)` from a different, unrelated signer (simulating re-registration), deploying new code / keys.
4. Submit a transaction invoking `promise_yield_resume(data_id, payload)` targeting `V` using the originally captured `data_id`.
5. Assert that the resume does **not** execute the stale actions against the new `V` (no `AddKey` added, i.e., `get_access_key(new_V, attacker_pubkey)` returns `None`), or that the resume is rejected outright. Currently, the AddKey action succeeds, demonstrating the vulnerability.

pub fn set_promise_yield_receipt(state_update: &mut TrieUpdate, receipt: &Receipt) {
    match receipt.versioned_receipt() {
        VersionedReceiptEnum::PromiseYield(action_receipt) => {
            assert!(action_receipt.input_data_ids().len() == 1);
            let key = TrieKey::PromiseYieldReceipt {
                receiver_id: receipt.receiver_id().clone(),
                data_id: action_receipt.input_data_ids()[0],
            };
            set(state_update, key, receipt);
        }
        _ => unreachable!("Expected PromiseYield receipt"),
    }
}

pub fn remove_account(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
) -> Result<RemoveAccountResult, StorageError> {
    state_update.remove(TrieKey::Account { account_id: account_id.clone() });
    state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });

    let mut gas_key_nonce_count: usize = 0;
    let mut gas_key_nonce_total_key_bytes: usize = 0;

    // Removing access keys and gas key nonces
    let lock = state_update.trie().lock_for_iter();
    let mut keys_to_remove: Vec<TrieKey> = Vec::new();
    for raw_key in state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_access_keys(account_id), &lock)?
    {
        let raw_key = raw_key?;
        let key_handle = trie_key_parsers::parse_key_handle_from_access_key_key(
            &raw_key, account_id,
        )
        .map_err(|_e| {
            StorageError::StorageInconsistentState(
                "Can't parse key handle from raw key for AccessKey".to_string(),
            )
        })?;
        let nonce_index =
            trie_key_parsers::parse_nonce_index_from_gas_key_key(&raw_key, account_id, &key_handle)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse nonce index from raw key for AccessKey".to_string(),
                    )
                })?;
        if let Some(index) = nonce_index {
            gas_key_nonce_count += 1;
            gas_key_nonce_total_key_bytes += raw_key.len();
            keys_to_remove.push(TrieKey::gas_key_nonce(
                account_id.clone(),
                key_handle.clone(),
                index,
            ));
        } else {
            keys_to_remove.push(TrieKey::access_key(account_id.clone(), key_handle.clone()));
        }
    }
    drop(lock);

    for trie_key in keys_to_remove {
        state_update.remove(trie_key);
    }

    // Removing contract data
    let lock = state_update.trie().lock_for_iter();
    let data_keys = state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_contract_data(account_id, &[]), &lock)?
        .map(|raw_key| {
            trie_key_parsers::parse_data_key_from_contract_data_key(&raw_key?, account_id)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse data key from raw key for ContractData".to_string(),
                    )
                })
                .map(Vec::from)
        })
        .collect::<Result<Vec<_>, _>>()?;
    drop(lock);

    for key in data_keys {
        state_update.remove(TrieKey::ContractData { account_id: account_id.clone(), key });
    }
    Ok(RemoveAccountResult { gas_key_nonce_count, gas_key_nonce_total_key_bytes })
}
