### Title
Interest under-accrued for all borrowers due to division-before-multiplication precision loss in `interestRatePerSecond()` - (File: contracts/DebtToken.sol)

### Summary
The M-13 bug class — truncating integer division performed *before* multiplication — is present in Metronome's `DebtToken._calculateInterestAccrual()`. The per-second rate is computed once as `interestRate / SECONDS_PER_YEAR` (division first, discarding the remainder) and only afterwards multiplied by the elapsed time in `_calculateInterestAccrual()`. Because the remainder of `interestRate % 31,557,600` is silently dropped on every accrual, the protocol systematically accrues less interest than it should. The result is that every borrower pays less debt than the configured APR implies, and `pool.feeCollector()` is minted less synthetic-token interest than owed — a permanent, repeatable loss of protocol yield in favor of debtors.

### Finding Description
In `contracts/DebtToken.sol`:

```solidity
function interestRatePerSecond() public view override returns (uint256) {
    return interestRate / SECONDS_PER_YEAR;   // L320: divide first, remainder truncated
}
```

which is then consumed at L560:

```solidity
uint256 _interestRateToAccrue = interestRatePerSecond() * (block.timestamp - _lastTimestampAccrued);
```

and multiplied against supply/index at L562-L563:

```solidity
_interestAmountAccrued = _interestRateToAccrue.wadMul(totalSupply_);
_debtIndex += _interestRateToAccrue.wadMul(_debtIndex);
```

This is exactly the anti-pattern from the source report: `(interestRate / SECONDS_PER_YEAR) * delta` truncates up to `SECONDS_PER_YEAR - 1 = 31,557,599` wei of rate-per-second on every accrual window. The loss compounds because `debtIndex` and `totalSupply_` are permanently updated from the truncated value in `accrueInterest()` (L167-L171), and `balanceOf()` (L202-L205) computes each user's repayable debt from that same understated index.

The function is reachable from every unprivileged public path that touches debt: `DebtToken.issue()` (L248), `repay()` (L431), `repayAll()` (L476), `balanceOf()` (L202), `Pool.liquidate()` via `_debtToken.accrueInterest()`, `SmartFarmingManager.leverage()`/`flashRepay()` via `mint`/`flashIssue`/`repay`. No privileged role is needed to benefit — any borrower automatically pays less. The correct formulation multiplies first: `interestRate * elapsed / SECONDS_PER_YEAR`, which has no truncation beyond the unavoidable final division.

### Impact Explanation
`debtIndex` and `totalSupply_` permanently understate accrued interest, so:

- `balanceOf()` returns less debt for every account → borrowers repay/burn fewer synths in `repay()`/`repayAll()` and liquidators burn fewer synths in `Pool.liquidate()` for the same collateral seized → direct loss of unclaimed yield owed to `feeCollector()` and under-repayment of the debt pool (solvency-side leak).
- Magnitude: the truncation error is bounded by `SECONDS_PER_YEAR - 1` wei of rate-per-second. For a 5% APR (`interestRate = 5e16`), the true per-second rate is ~1.585e9, so loss is up to ~2% of interest. For low-APR debt tokens (e.g., `interestRate ≈ 3e15`, ~0.1% APR, a plausible config for stable synths), the dropped remainder is comparable to the quotient itself — up to ~50% of all interest is silently never accrued, mirroring the 27.5% magnitude class demonstrated in the source report. Since this loss recurs on every accrual for the lifetime of the debt token, it is a continuous bleed rather than dust rounding.

### Likelihood Explanation
The defect triggers deterministically on every call to `accrueInterest()`/`_calculateInterestAccrual()` whenever `interestRate % SECONDS_PER_YEAR != 0` — i.e., for virtually every non-zero configured APR. No attacker action, timing, or market condition is required; every borrower benefits passively. The only mitigating factor is a governance-set `interestRate` of exactly 0 (in which case no interest exists to lose) or `interestRate` being an exact multiple of 31,557,600 (practically never). No guard, cap, pause flag, or health check compensates for the truncation.

### Recommendation
Multiply before dividing, and cache nothing that assumes the truncated rate:

```solidity
// contracts/DebtToken.sol
function _calculateInterestAccrual() private view returns (...) {
    ...
    if (block.timestamp > _lastTimestampAccrued) {
        uint256 _interestRateToAccrue =
            interestRate * (block.timestamp - _lastTimestampAccrued) / SECONDS_PER_YEAR;
        ...
    }
}
```

`interestRatePerSecond()` should likewise return `(interestRate * 1e18) / SECONDS_PER_YEAR` (or the wad equivalent) if kept for external callers. Note `interestRate * elapsed` cannot overflow for any realistic APR and time window; alternatively use `Math.mulDiv(interestRate, elapsed, SECONDS_PER_YEAR)`.

### Proof of Concept
Hardhat-style test against a deployed `DebtToken` with `interestRate = 3e15` (~0.0948% APR) and `totalSupply_ = 1e24` (1M synths):

```typescript
// Accrue exactly 1 day
await time.increase(86400);
await debtToken.accrueInterest();

// Implementation: rate/sec = 3e15 / 31557600 = floor(95,063,851.17) = 95_063_851
// accrued_actual   = wadMul(95_063_851 * 86400, 1e24)   ≈ 8.2135e18
// accrued_expected = 3e15 * 86400 * 1e24 / (31557600 * 1e18) ≈ 8.2136e18
// Loss scales with remainder: worst case ~95e6 of ~95e6+31.5e6 → up to ~50% of interest
// never minted to feeCollector, and balanceOf(alice) is correspondingly understated.
```

Concrete check: choose `interestRate` such that `interestRate % SECONDS_PER_YEAR` is close to `SECONDS_PER_YEAR - 1` (e.g., `interestRate = 2 * 31557600 + 31557599`-style values scaled into wad). Then `interestRatePerSecond()` loses ~1/3 of the intended rate on every accrual, `debtIndex` grows slower, and `debtToken.repayAll(alice)` burns measurably less synthetic token than the true accrued debt — reproducible on a mainnet fork against any live `DebtToken` with non-zero APR.

**Uncertainty note:** I could not inspect `MasterOracle` implementation files (no `Oracle*.sol` matched in the indexed scope — the oracle is external) or `DepositToken.seize`/`VesperGateway` internals in the iterations available, so a higher-impact div-before-mul inside oracle price chaining cannot be ruled out. Within indexed production code, `AMO.sol`'s `pricePerShare` divisions are keeper-gated and therefore out of scope; all `Pool.sol` quote functions and `WadRayMath` itself use correctly-ordered mul-before-div. The `DebtToken` path above is the strongest reachable analog.
