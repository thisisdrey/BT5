**Reasoning:** `ReshardingEventType::from_shard_layout` in `chain/chain/src/resharding/event_type.rs` is a pure function that only inspects the protocol-level `ShardLayout` definition (produced by the epoch manager/validators during consensus-driven resharding) to determine parent/child shard IDs and the boundary account. [1](#0-0) 

It takes no receipts, no account state, and no transaction-derived data as input — its only inputs are `next_shard_layout` and `resharding_block` (a block hash/height marker), both of which come from consensus-validated epoch configuration, not from any attacker-controlled cross-shard promise or gas parameter. There is no code path by which an unprivileged account's transactions, `promise_batch_action_function_call_weight` usage, or gas-limit-adjacent transaction costs can reach or influence this function's execution or output.

The actual account/receipt migration logic that determines which child shard retains which keys is handled separately in the trie-splitting code (e.g., `boundary_account_to_intervals` in `core/store/src/trie/ops/resharding.rs`), which deterministically partitions all account-keyed columns by the single `boundary_account` and copies shard-global (non-account-keyed) data to both children. [2](#0-1) 

The codebase also contains explicit test-loop coverage for exactly the boundary-straddling receipt scenarios described (buffered/delayed receipts at the parent shard during a split, large cross-shard receipts near gas/bandwidth limits), which assert that such receipts remain retrievable/redeliverable after the split rather than being stranded. [3](#0-2) [4](#0-3) 

Since the targeted function has no reachable path from an attacker's transaction/contract inputs, and no account/receipt data flows through it at all, the described exploit chain (attacker contract → gas-limit-adjacent promises → stranded funds via `from_shard_layout`) is not supported by the code.

fn boundary_account_to_intervals(
    boundary_account: &AccountId,
    retain_mode: RetainMode,
) -> Vec<Range<Vec<u8>>> {
    let mut intervals = vec![];
    for (prefix, name) in col::ALL_COLUMNS_WITH_NAMES {
        // Here we are handling all the keys that have the account_id prefix.
        // These are considered to be the `green` keys in resharding design.
        if col::COLUMNS_WITH_ACCOUNT_ID_IN_KEY.contains(&(prefix, name)) {
            intervals.push(get_interval_for_split_keys(boundary_account, &retain_mode, prefix));
            continue;
        }
        // Here we are handling all the keys that DO NOT have the account_id prefix.
        // These are the `red` and `yellow` keys in resharding design.
        // They are handled by either copying the keys to both shards or only to the lower index shard.
        match prefix {
            col::DELAYED_RECEIPT_OR_INDICES
            | col::PROMISE_YIELD_INDICES
            | col::PROMISE_YIELD_TIMEOUT
            | col::BANDWIDTH_SCHEDULER_STATE
            | col::GLOBAL_CONTRACT_CODE
            | col::GLOBAL_CONTRACT_NONCE => {
                // This section contains the keys that we need to copy to both shards.
                intervals.push(get_interval_for_copy_to_both_children(prefix))
            }
            col::BUFFERED_RECEIPT_INDICES
            | col::BUFFERED_RECEIPT
            | col::BUFFERED_RECEIPT_GROUPS_QUEUE_DATA
            | col::BUFFERED_RECEIPT_GROUPS_QUEUE_ITEM => {
                // This section contains the keys that we only copy to the lower index shard.
                if let Some(interval) = get_interval_for_copy_to_one_child(&retain_mode, prefix) {
                    intervals.push(interval);
                }
            }
            // Poor man's exhaustive check for handling all column types.
            _ => panic!("Unhandled trie key type: {}", name),
        }
