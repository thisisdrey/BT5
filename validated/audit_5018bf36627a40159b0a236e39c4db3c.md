### Title
`transfer_assert_minimum_deposit` Checks Raw `fungible_asset::balance` Instead of `derived_balance`, Breaking the Minimum-Deposit Guarantee for Dispatchable Tokens — (File: `aptos-move/framework/aptos-framework/sources/dispatchable_fungible_asset.move`)

---

### Summary

`dispatchable_fungible_asset::transfer_assert_minimum_deposit` is documented to guarantee the recipient receives at least `expected` units of a fungible asset. However, both the pre- and post-transfer balance snapshots are taken with `fungible_asset::balance()` — the raw stored balance — while the actual `withdraw` and `deposit` calls go through the dispatchable hooks. For any fungible asset that registers a `derived_balance_function` hook (making its user-visible balance differ from its raw stored balance), the assertion `end - start >= expected` operates on the wrong quantity and can silently pass even when the recipient received fewer derived-balance units than `expected`.

---

### Finding Description

The vulnerable function is:

```move
// dispatchable_fungible_asset.move lines 136-148
public entry fun transfer_assert_minimum_deposit<T: key>(
    sender: &signer,
    from: Object<T>,
    to: Object<T>,
    amount: u64,
    expected: u64
) acquires TransferRefStore {
    let start = fungible_asset::balance(to);   // ← raw stored balance
    let fa = withdraw(sender, from, amount);   // ← goes through dispatchable withdraw hook
    deposit(to, fa);                           // ← goes through dispatchable deposit hook
    let end = fungible_asset::balance(to);     // ← raw stored balance
    assert!(end - start >= expected, error::aborted(EAMOUNT_MISMATCH));
}
``` [1](#0-0) 

`fungible_asset::balance()` reads the raw `FungibleStore.balance` field directly. `dispatchable_fungible_asset::derived_balance()` (defined at line 154) calls the registered `derived_balance_function` hook, which can return an entirely different value — for example, 10× the raw balance for `ten_x_token`, or a fraction for a rebasing/fee-on-deposit token. [2](#0-1) 

The `withdraw` and `deposit` calls inside `transfer_assert_minimum_deposit` both go through the dispatchable hooks, so the actual amount the recipient "sees" (derived balance) can differ from the raw balance delta. The assertion therefore checks the wrong quantity.

The same pattern is present in `primary_fungible_store.move`, which also exposes a `transfer_assert_minimum_deposit` wrapper. [3](#0-2) 

This is structurally identical to the OCY_Convex_C bug: that contract called `rewardToken.balanceOf()` on a `StashTokenWrapper` address (the intermediate/wrapper layer) instead of calling `.token().balanceOf()` on the actual underlying token. Here, the code calls `fungible_asset::balance()` on the raw storage layer instead of `derived_balance()` on the hook-computed layer that represents the token's actual user-visible value.

---

### Impact Explanation

**Broken minimum-deposit guarantee (user-funds impact):**

For a fungible asset with a `derived_balance_function` where `derived_balance < raw_balance` (e.g., a rebasing token or a token with a fee-on-deposit hook that burns part of the deposited amount):

- `start` and `end` are raw balances.
- The raw delta `end - start` can be ≥ `expected` even when the recipient's derived-balance increase is < `expected`.
- The assertion passes, but the recipient received fewer visible tokens than the caller guaranteed.

Any DeFi protocol or user relying on `transfer_assert_minimum_deposit` to enforce a minimum received amount for dispatchable fungible assets has that guarantee silently violated. This enables slippage attacks or under-delivery of assets with no on-chain revert.

**DoS for tokens where `derived_balance > raw_balance`:**

For tokens like `ten_x_token` (derived = 10× raw), the raw delta is much smaller than the derived delta. A caller setting `expected` based on derived balance would see the assertion fail even though the recipient received more than enough derived tokens, causing legitimate transfers to revert. [4](#0-3) 

---

### Likelihood Explanation

- `transfer_assert_minimum_deposit` is a `public entry fun` callable by any account on mainnet.
- The dispatchable fungible asset system (AIP-73) explicitly supports custom `derived_balance_function` hooks as a first-class feature.
- `primary_fungible_store.move` also exposes this function, broadening the attack surface.
- Any token issuer can register a `derived_balance_function` that diverges from raw balance, making this exploitable without privileged access.

---

### Recommendation

Replace both `fungible_asset::balance()` calls in `transfer_assert_minimum_deposit` with `dispatchable_fungible_asset::derived_balance()`:

```move
public entry fun transfer_assert_minimum_deposit<T: key>(
    sender: &signer,
    from: Object<T>,
    to: Object<T>,
    amount: u64,
    expected: u64
) acquires TransferRefStore {
    let start = derived_balance(to);   // ← use derived balance
    let fa = withdraw(sender, from, amount);
    deposit(to, fa);
    let end = derived_balance(to);     // ← use derived balance
    assert!(end - start >= expected, error::aborted(EAMOUNT_MISMATCH));
}
```

The same fix must be applied to the `transfer_assert_minimum_deposit` wrapper in `primary_fungible_store.move`.

### Proof of Concept

1. Deploy a fungible asset with:
   - A `derived_balance_function` hook returning `raw_balance / 2` (1 raw unit = 0.5 visible units).
   - A `deposit_function` hook that burns 10% of deposited tokens (fee-on-deposit).

2. Sender has 100 raw tokens. Recipient has 0.

3. Call `transfer_assert_minimum_deposit(sender, from, to, 100, 50)`.
   - Caller expects recipient to receive ≥ 50 visible tokens (= 100 raw / 2).

4. Execution:
   - `start = fungible_asset::balance(to)` = **0** (raw)
   - `withdraw` removes 100 raw tokens → `fa` holds 100 raw tokens
   - `deposit` hook burns 10 raw tokens → **90** raw tokens deposited
   - `end = fungible_asset::balance(to)` = **90** (raw)
   - `end - start = 90 ≥ 50` → **assertion PASSES**

5. Recipient's actual derived balance increase = `90 / 2` = **45 visible tokens**, not 50.

6. The minimum-deposit guarantee is silently violated: the transaction succeeds, but the recipient received 10% fewer visible tokens than the caller guaranteed. [5](#0-4)
