### Title
Missing Minimum-Duration Validation for Firewall Conntrack Timeouts Causes Divide-by-Zero Crash - (File: `firewall.go`)

### Summary
`NewFirewall` accepts `firewall.conntrack.tcp_timeout`, `firewall.conntrack.udp_timeout`, and `firewall.conntrack.default_timeout` from config with no minimum-value enforcement, exactly the bug class described in the external report (a security-relevant configurable delay accepted with no floor check). The code itself flags the gap with `//TODO: error on 0 duration`, and a `0` value flows straight into `NewTimerWheel`, where it is used as an integer divisor, causing a runtime divide-by-zero panic that crashes the whole node instead of merely "collapsing protection" the way an unbounded `delayBlocks` would.

### Finding Description
`NewFirewall` computes `tmin`/`tmax` from the three configured timeout durations and passes them unchecked into `NewTimerWheel`: [1](#0-0) 

`NewTimerWheel` then divides `max` by `min` to size the wheel, with no guard against `min == 0`: [2](#0-1) 

`NewFirewallFromConfig` reads these three durations straight from the config with defaults, but does not clamp or validate a minimum, and the constructor it calls carries an explicit acknowledgment of the missing check: [3](#0-2) [4](#0-3) 

This is structurally identical to the reported bug class: a security-relevant timing/threshold parameter (`delayBlocks` in the report, conntrack timeout here) is settable to an unsafe value (`0`) with no `minDelay`/minimum enforcement anywhere in the validation path, and the resulting value directly gates a protective control (fraud-protection delay in the report; firewall connection-tracking state expiry here).

### Impact Explanation
If any of `firewall.conntrack.tcp_timeout`, `udp_timeout`, or `default_timeout` is set to `0` (or omitted from a config context where it resolves to `0`), `tmin` becomes `0`, and `int((max / min) + 2)` in `NewTimerWheel` panics with an integer divide-by-zero at firewall construction time in `Main()`. Because `NewFirewallFromConfig` runs unconditionally during startup, the node fails to come up entirely — a full denial of service of the tunnel/firewall subsystem, not merely a degraded fraud-protection window as in the original report.

### Likelihood Explanation
Triggering the crash requires only a configuration change (setting one of the three timeout keys to `0`), with no additional validation anywhere on the config-load path to reject it. The code's own `//TODO: error on 0 duration` comment confirms the omission is a known, unaddressed gap rather than an intentionally accepted design tradeoff.

### Recommendation
Add explicit minimum-duration validation in `NewFirewallFromConfig` (and/or `NewFirewall`) that rejects or clamps `tcpTimeout`, `UDPTimeout`, and `defaultTimeout` values below a safe floor (e.g., non-zero and at least the timer wheel's minimum tick resolution), returning a configuration error instead of allowing a `0` value to reach `NewTimerWheel`. This mirrors the recommended fix in the original report: enforce a `minDelay`-equivalent for any configurable value that a downstream security/availability mechanism divides or schedules by.

### Proof of Concept
1. Configure `firewall.conntrack.tcp_timeout: 0s` (leaving `udp_timeout`/`default_timeout` at their defaults).
2. Start the node; `Main()` calls `NewFirewallFromConfig`, which calls `NewFirewall(l, 0, defaultUDP, defaultDefault, cert)`.
3. `tmin` resolves to `0`; `NewTimerWheel(0, tmax)` executes `wLen := int((max / min) + 2)`, dividing by zero.
4. The Go runtime panics, crashing the node before it can process any traffic — confirmable directly from `NewFirewall`/`NewTimerWheel` reachability shown above without needing further live testing.

	wLen := int((max / min) + 2)

	tw := TimerWheel[T]{

	}

		tw.wheel[i] = &TimeoutList[T]{}
	}
