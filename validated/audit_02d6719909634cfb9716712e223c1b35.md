### Title
`FreezeBalanceProcessor.validate()` fails to reject legacy `freezeBalance` operations after FreezeV2 is enabled, unlike the corresponding actuator - (File: actuator/src/main/java/org/tron/core/vm/nativecontract/FreezeBalanceProcessor.java)

### Summary
`FreezeBalanceActuator.validate()` explicitly forbids the legacy freeze-balance operation once the network has migrated to FreezeV2 (`dynamicStore.supportUnfreezeDelay()`), but the parallel native-contract implementation used by TVM (`FreezeBalanceProcessor.validate()`, invoked via `Program.freezeBalance`) omits this check entirely, mirroring the reported pattern where a validation function fails to invalidate one specific case that its sibling correctly rejects.

### Finding Description
`FreezeBalanceActuator.validate()` contains a mandatory guard: [1](#0-0) 
that unconditionally rejects any old-style freeze transaction once `supportUnfreezeDelay()` (FreezeV2) is active on-chain — this is the "committee-controlled disable switch" for the legacy freeze mechanism.

The TVM-reachable equivalent, `FreezeBalanceProcessor.validate()`, is invoked from the smart-contract native/precompiled freeze-balance opcode path (`Program.java` calls into `FreezeBalanceParam`/`FreezeBalanceProcessor`): [2](#0-1) 
It performs balance, frozen-count, and resource-type checks but has **no check at all** for `dynamicStore.supportUnfreezeDelay()`. Any smart contract can therefore continue to invoke the legacy freeze-balance native operation and successfully create old-style `Frozen`/`AccountResource.frozen_balance_for_energy` entries and delegated resources even after the committee has switched the network to FreezeV2 and disabled the legacy path for ordinary transactions.

This is directly analogous to the reported `validateCommitment()` bug: a validation routine correctly implements one enumerated/guarded branch (the actuator) while an alternate code path exercising the same business object (the native-contract processor) omits the check that should invalidate a now-forbidden state, allowing state to be created that the protocol intends to be impossible.

Separately, `FreezeBalanceProcessor.validate()` also dereferences `ownerCapsule.getBalance()` at line 34 without first checking `ownerCapsule == null`, unlike the actuator and the sibling `FreezeBalanceV2Processor.validate()` which explicitly null-check the owner account: [3](#0-2) 

### Impact Explanation
Bypassing the FreezeV2 migration guard lets contracts keep creating legacy frozen balances/delegations after the committee intended to retire that mechanism. This can:
- Produce state inconsistent with the new resource-accounting model (old `Frozen`/`DelegatedResource` entries alongside V2 balances), potentially corrupting bandwidth/energy weight bookkeeping (`addTotalNetWeight`/`addTotalEnergyWeight`) that is shared between the two systems.
- Allow indefinite freezing of TRX under the old unfreeze rules (fixed `FROZEN_PERIOD`, no delayed-unfreeze accounting) instead of the V2 rules, effectively creating funds that are frozen/locked outside the governance-approved model — a form of permanent or protocol-inconsistent freezing of funds.
- The missing null check on `ownerCapsule` is a straightforward NPE/crash vector reachable from a contract call with a non-existent owner address.

This satisfies the Medium bar: an unauthorized state transition reachable by any account issuing a contract call, bypassing a should-be-invalidating condition, with concrete resource-accounting/freezing impact.

### Likelihood Explanation
Reachable by any contract (deployer/caller) invoking the TVM freeze-balance native operation — no special privilege required. It requires the network to have already activated FreezeV2 (`supportUnfreezeDelay()==true`), which is the deployed default on current mainnet/most testnets, making the missing-guard path realistically triggerable at any time post-migration.

### Recommendation
Add the same guard used in `FreezeBalanceActuator.validate()` to `FreezeBalanceProcessor.validate()`:
```java
if (repo.getDynamicPropertiesStore().supportUnfreezeDelay()) {
  throw new ContractValidateException("freeze v2 is open, old freeze is closed");
}
```
Also add a null check for `ownerCapsule` before dereferencing it, mirroring `FreezeBalanceV2Processor.validate()`.

### Proof of Concept
1. Network has `supportUnfreezeDelay()` (FreezeV2) enabled by committee proposal (current production state).
2. A user deploys/invokes a smart contract that calls the native freeze-balance opcode (via `Program.java`'s freeze-balance native contract path) with a valid `ownerAddress`/`frozenBalance`/`resourceType` (BANDWIDTH or ENERGY).
3. `FreezeBalanceProcessor.validate()` runs all of its checks and returns successfully because it never checks `supportUnfreezeDelay()` — contrast with calling `FreezeBalanceContract` directly via a normal transaction, which is correctly rejected by `FreezeBalanceActuator.validate()` with "freeze v2 is open, old freeze is closed".
4. `execute()` proceeds to create legacy `Frozen` balance entries and update total net/energy weight using the old model, even though the protocol intends this path to be fully retired.

Note: I could not fully trace every caller/opcode wiring for `Program.java` invoking `FreezeBalanceProcessor` (only grep hits were found, not the full opcode dispatch), so the exact TVM opcode/precompile name that exposes this to a raw transaction sender was not independently confirmed within the available index; this should be verified in a live session before remediation.

  public void validate(FreezeBalanceParam param, Repository repo) throws ContractValidateException {
    if (repo == null) {
      throw new ContractValidateException(STORE_NOT_EXIST);
    }

    // validate arg @frozenBalance
    byte[] ownerAddress = param.getOwnerAddress();
    AccountCapsule ownerCapsule = repo.getAccount(ownerAddress);
    long frozenBalance = param.getFrozenBalance();
    if (frozenBalance <= 0) {
      throw new ContractValidateException("FrozenBalance must be positive");
    } else if (frozenBalance < TRX_PRECISION) {
      throw new ContractValidateException("FrozenBalance must be greater than or equal to 1 TRX");
    } else if (frozenBalance > ownerCapsule.getBalance()) {
      throw new ContractValidateException("FrozenBalance must be less than or equal to accountBalance");
    }

    // validate frozen count of owner account
    int frozenCount = ownerCapsule.getFrozenCount();
    if (frozenCount != 0 && frozenCount != 1) {
      throw new ContractValidateException("FrozenCount must be 0 or 1");
    }

    // validate arg @resourceType
    switch (param.getResourceType()) {
      case BANDWIDTH:
      case ENERGY:
        break;
      default:
        throw new ContractValidateException(
            "Unknown ResourceCode, valid ResourceCode[BANDWIDTH、ENERGY]");
    }
