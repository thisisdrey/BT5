### Title
Intra-batch write/write and write/read account-lock conflicts are silently granted due to a two-pass check/lock ordering bug - ([File: accounts-db/src/account_locks.rs])

### Finding Description
`AccountLocks::try_lock_transaction_batch` validates and locks a batch of transactions in two **separate** passes:

1. A read-only validation pass calls `can_lock_accounts` for every transaction in the batch, checking each transaction's keys against `self` (the lock table) as it stood **before the batch started**. Because `can_lock_accounts` never mutates `self`, none of the "would-be" locks from earlier transactions in the *same* batch are visible to later transactions in the validation pass.
2. A second, unconditional pass calls `lock_accounts` for every transaction whose validation passed, which increments `write_locks`/`readonly_locks` counters with no re-check against locks acquired by earlier transactions processed in the same second pass. [1](#0-0) 

`lock_write`/`lock_readonly` are unconditional counter increments with no exclusivity check: [2](#0-1) 

`can_write_lock`/`can_read_lock` (used only in the first, batch-blind pass) are what implement the exclusivity invariant: [3](#0-2) 

Consequence: if a batch contains two transactions, A and B, that both write the same account key K (no prior locks on K exist before the batch), the first pass evaluates `can_lock_accounts` for A and for B **against the same unmodified `self`**, so both report `Ok`. The second pass then calls `lock_write(K)` for A and, unconditionally, `lock_write(K)` again for B, incrementing the write-lock counter to 2 with no error returned for B. Both transactions are reported as successfully locked (`Ok(())`) even though they conflict on a writable account — violating the fundamental invariant that a write lock is exclusive (`can_write_lock` requires no existing readonly or write lock).

This function is reached from `Accounts::lock_accounts` [4](#0-3) , which is called for every leader transaction batch via `Bank::prepare_sanitized_batch_with_results` → `TransactionBatch::new`, invoked from banking stage's `process_and_record_transactions_with_pre_results` on arbitrary buffered non-vote transactions [5](#0-4) . Non-vote transactions reaching this path originate from arbitrary TPU clients (no staked-node control is required to submit ordinary transactions), and an attacker fully controls which account keys and writable flags its own transactions declare, and can freely craft multiple transactions in the same buffered batch that write the same account.

The existing test suite masks this gap: `test_accounts_locks_intrabatch_conflicts` labels a second case "ww conflict in-batch succeeds" but actually reuses the same `w_tx`/`r_tx` pair from the prior (write+read) case rather than testing two write-conflicting transactions, so a genuine write-write intra-batch scenario is never exercised. [6](#0-5) 

### Impact Explanation
This breaks the core LOCK_CORRECTNESS invariant that account locks prevent transactions with conflicting writable accounts from being considered concurrently "locked"/schedulable within one processing unit. Batches are the unit that `bank.load_and_execute_transactions` operates on, and downstream processing (and the accounting for retry/commit, e.g. `execute_and_commit_transactions_locked`) assumes lock results correctly express serialization constraints; a spurious pair of `Ok` results for two writers of the same account undermines the guarantee that the recorded entry's transaction ordering/state is what the lock manager vouches for, matching the scope description of "an invalid block/entry that does not match transactions actually executed." This falls under the correctness/consensus-safety class of Agave's bounty categories (state-divergence / invalid-block-producing bug), scoped specifically to `accounts_db::account_locks::AccountLocks::try_lock_transaction_batch`.

### Likelihood Explanation
- No stake or special privileges are required: any client can submit ordinary transactions to a leader's TPU.
- The attacker only needs two (or more) sanitized transactions that write the same account key and that land together within one banking-stage processing batch — an easily controllable condition since the attacker crafts the transactions and their account key sets.
- The bug is fully deterministic given the code shown (not a probabilistic timing race in the lock function itself): the two-pass check-then-lock structure guarantees the false-positive whenever intra-batch conflicting writers are present.
- The gap is unguarded by sigverify, QoS, or dedup logic; those check different properties (signature validity, duplicate signatures, and cost limits, respectively) and do not perform the equivalent per-account exclusivity check that `try_lock_transaction_batch` is supposed to enforce.

### Recommendation
Merge the validation and locking passes into a single sequential pass over `validated_batch_keys`, so that each transaction's `can_lock_accounts` check is performed against the mutated state that includes locks already granted to earlier transactions in the same batch, e.g.:
```rust
validated_batch_keys
    .into_iter()
    .map(|available_keys| {
        available_keys.and_then(|keys| {
            self.can_lock_accounts(keys.clone())?;
            self.lock_accounts(keys);
            Ok(())
        })
    })
    .collect()
```
This restores the intended semantics that a lock granted to one transaction in the batch is visible to `can_lock_accounts` checks for subsequent transactions in the same batch.

### Proof of Concept
Add an accounts-db unit test that exercises two write-conflicting transactions within a single batch and asserts that exactly one is granted the lock:

```rust
#[test]
fn test_accounts_locks_intrabatch_ww_conflict_invariant() {
    let pubkey = Pubkey::new_unique();
    let account_data = AccountSharedData::new(1, 0, &Pubkey::default());
    let accounts_db = Arc::new(AccountsDb::default_for_tests());
    accounts_db.store_for_tests((0, [(&pubkey, &account_data)].as_slice()));

    let w_tx_a = sanitized_tx_from_metas(vec![AccountMeta {
        pubkey, is_writable: true, is_signer: false,
    }]);
    let w_tx_b = sanitized_tx_from_metas(vec![AccountMeta {
        pubkey, is_writable: true, is_signer: false,
    }]);

    let accounts = Accounts::new(accounts_db);
    let results = accounts.lock_accounts(
        [w_tx_a, w_tx_b].iter(),
        [Ok(()), Ok(())].into_iter(),
        MAX_TX_ACCOUNT_LOCKS,
    );

    // LOCK_CORRECTNESS: only one writer may hold the write lock at a time.
    let ok_count = results.iter().filter(|r| r.is_ok()).count();
    assert_eq!(ok_count, 1, "two conflicting writers were both granted locks: {results:?}");
}
```
With the current code, this test fails because both results are `Ok(())`. As an invariant/fuzz extension, generate adversarially ordered batches of transactions with overlapping writable/readonly key sets and assert, after calling `try_lock_transaction_batch`, that no two `Ok` entries share a writable key and that no `Ok` writable entry shares a key with any other `Ok` entry (readonly or writable).

    pub fn try_lock_transaction_batch<'a>(
        &mut self,
        mut validated_batch_keys: Vec<
            TransactionResult<impl Iterator<Item = (&'a Pubkey, bool)> + Clone>,
        >,
    ) -> Vec<TransactionResult<()>> {
        validated_batch_keys.iter_mut().for_each(|validated_keys| {
            if let Ok(keys) = validated_keys.as_ref()
                && let Err(e) = self.can_lock_accounts(keys.clone())
            {
                *validated_keys = Err(e);
            }
        });

        validated_batch_keys
            .into_iter()
            .map(|available_keys| available_keys.map(|keys| self.lock_accounts(keys)))
            .collect()
    }

    pub fn lock_accounts<'a>(
        &self,
        txs: impl Iterator<Item = &'a (impl SVMMessage + 'a)>,
        results: impl Iterator<Item = Result<()>>,
        tx_account_lock_limit: usize,
    ) -> Vec<Result<()>> {
        // Validate the account locks, then get keys and is_writable if successful validation.
        // We collect to fully evaluate before taking the account_locks mutex.
        let validated_batch_keys = txs
            .zip(results)
            .map(|(tx, result)| {
                result
                    .and_then(|_| validate_account_locks(tx.account_keys(), tx_account_lock_limit))
                    .map(|_| TransactionAccountLocksIterator::new(tx).accounts_with_is_writable())
            })
            .collect::<Vec<_>>();

        let account_locks = &mut self.account_locks.lock().unwrap();
        account_locks.try_lock_transaction_batch(validated_batch_keys)
    }
