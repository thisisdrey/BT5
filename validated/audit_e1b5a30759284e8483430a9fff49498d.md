### Title
Unhardened `double`-to-`long` narrowing cast in resource-delegation validation allows precision loss / overflow in `netUsage`/`energyUsage` accounting - ([File: actuator/src/main/java/org/tron/core/actuator/DelegateResourceActuator.java])

### Summary
The CVE-2017-7596 report describes LibTIFF crashing/misbehaving due to undefined behavior when a floating-point value is cast to an integer type outside its representable range. The java-tron codebase has, in most resource-accounting paths (`EnergyProcessor`, `ResourceProcessor`, `RepositoryImpl`), already migrated away from raw `double` arithmetic to `BigInteger`-based "hardened" calculations guarded by `hardenResourceCalculation()`/`hardenCalculation()`, with dedicated overflow tests (`CalculateGlobalLimitHardenTest`, `RepositoryImplHardenTest`) that throw `ArithmeticException` on overflow. However, `DelegateResourceActuator.validate()` and its TVM analog `DelegateResourceProcessor.validate()` still perform the legacy unguarded `double` computation with a raw narrowing cast to `long`, with no BigInteger/overflow-safe alternative and no bounds check on the multiplication.

### Finding Description
In `DelegateResourceActuator.validate()`: [1](#0-0) 
```
long netUsage = (long) (accountNetUsage * TRX_PRECISION * ((double)
    (dynamicStore.getTotalNetWeight()) / dynamicStore.getTotalNetLimit()));
```
and [2](#0-1) 
```
long energyUsage = (long) (ownerCapsule.getEnergyUsage() * TRX_PRECISION * ((double)
    (dynamicStore.getTotalEnergyWeight()) / dynamicStore.getTotalEnergyCurrentLimit()));
```
The identical pattern is duplicated in the TVM-reachable `DelegateResourceProcessor.validate()`: [3](#0-2) [4](#0-3) 

This computed `netUsage`/`energyUsage` is fed into `getV2NetUsage`/`getV2EnergyUsage`, whose result directly gates whether the delegate amount is accepted: [5](#0-4) 

Elsewhere in the codebase the identical class of bug (long-range `double` multiplication truncated with a `(long)` cast) was explicitly identified as a correctness/overflow hazard and hardened, e.g. in `EnergyProcessor.calculateGlobalEnergyLimit`/`calculateGlobalEnergyLimitV2` and `ResourceProcessor.calculateGlobalLimitV2`, which switch to `BigInteger` exact arithmetic under `hardenCalculation()` and are covered by dedicated overflow tests (`testGlobalEnergyLimitOverflowDetectedWithHardening`, `testCalculateGlobalEnergyLimitHardenedOverflowDetected`): [6](#0-5) [7](#0-6) 

`DelegateResourceActuator`/`DelegateResourceProcessor`, by contrast, never call into the hardened BigInteger path for this specific computation — they keep the legacy `double`-cast arithmetic unconditionally, regardless of the `allowHardenResourceCalculation`/`disableJavaLangMath` flags. Because `accountNetUsage`/`ownerCapsule.getEnergyUsage()` and `TRX_PRECISION` are `long`, and the ratio term is a `double`, the multiplication is promoted to `double`; for large usage/weight values this can lose precision (mantissa is only 52 bits) or, for sufficiently large ratios, produce a value that truncates unexpectedly when narrowed back to `long`, silently altering the computed usage rather than throwing (Java `(long)` cast of an out-of-range double clamps to `Long.MAX_VALUE`/`MIN_VALUE` rather than raising a fault, but it is still an unconditional bug-prone divergence from the intended integer accounting used by the rest of the resource subsystem).

### Impact Explanation
This computation directly gates the sanity check `ownerCapsule.getFrozenV2BalanceForBandwidth()/ForEnergy() - v2NetUsage/v2EnergyUsage < delegateBalance` used both by the wallet-facing `DelegateResourceContract` actuator and by the TVM `delegateResource` opcode (`Program.delegateResource` → `DelegateResourceProcessor.validate`). A miscomputed (undercounted) usage value can cause this validation to accept a `delegateBalance` larger than what is actually safely delegatable, letting a caller-controlled transaction or contract call delegate resource amounts inconsistent with the account's real frozen/usage state. This falls squarely within the "unauthorized account operation" / "unbacked balance" categories called out in scope, since it affects bandwidth/energy accounting reachable from an unprivileged transaction sender or contract deployer.

### Likelihood Explanation
Reachable directly by any account holder broadcasting a `DelegateResourceContract` transaction, or by any smart contract invoking the TVM `delegateResource` native opcode — no special privilege required. Triggering an actual miscalculation requires large usage/weight/limit values (to induce double-precision loss or overflow of the intermediate `double`), which is plausible on a long-running high-throughput network where `totalNetWeight`/`totalEnergyWeight`/usage counters can grow into large `long` ranges over time.

### Recommendation
Replace the raw `double`-based `netUsage`/`energyUsage` computations in `DelegateResourceActuator.validate()` and `DelegateResourceProcessor.validate()` with the same `BigInteger`-exact, overflow-checked pattern already used in `EnergyProcessor`/`ResourceProcessor` (i.e., `BigInteger.valueOf(...).multiply(...).divide(...).longValueExact()`), gated consistently with `hardenResourceCalculation()`/`disableJavaLangMath()` so the same hardening guarantees apply uniformly across all resource-delegation code paths.

### Proof of Concept
Not independently reproducible from the index alone (requires a running node with large enough `totalNetWeight`/`totalEnergyWeight`/usage state to demonstrate an actual precision-loss/overflow divergence); the divergence pattern mirrors the already-fixed bug demonstrated by the project's own regression tests for the parallel hardened functions, e.g. `testCalculateGlobalEnergyLimitHardenedParityWithNonIntegerRatio` and `testGlobalEnergyLimitOverflowDetectedWithHardening` in `framework/src/test/java/org/tron/core/db/CalculateGlobalLimitHardenTest.java`, which show the un-hardened `double` formula diverging from the exact integer result for realistic weight/limit magnitudes. A Devin session with repo access could construct an analogous `DelegateResourceActuatorTest` case using large `totalNetWeight`/`totalNetLimit`/`accountNetUsage` values to confirm concretely whether the validate() check can be bypassed.

    long frozeBalance = accountCapsule.getAllFrozenBalanceForEnergy();

    }
    if (frozeBalance < TRX_PRECISION) {
      return 0;
    }

    long totalEnergyLimit = dynamicPropertiesStore.getTotalEnergyCurrentLimit();
    long totalEnergyWeight = dynamicPropertiesStore.getTotalEnergyWeight();
    if (dynamicPropertiesStore.allowNewReward() && totalEnergyWeight <= 0) {
      return 0;
    } else {
      assert totalEnergyWeight > 0;
    }
    if (hardenCalculation()) {
      return calculateGlobalLimitV1(frozeBalance, totalEnergyLimit, totalEnergyWeight);
    }
    long energyWeight = frozeBalance / TRX_PRECISION;
    return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
  }

  protected long calculateGlobalLimitV2(long frozeBalance,
      long totalLimit, long totalWeight) {
    return BigInteger.valueOf(frozeBalance)
        .multiply(BigInteger.valueOf(totalLimit))
        .divide(BigInteger.valueOf(TRX_PRECISION)
            .multiply(BigInteger.valueOf(totalWeight)))
        .longValueExact();
  }
