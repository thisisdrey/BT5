## Analysis

Confirmed: `validate_delegate_action_key` persists the executed nonce back into the access key state (`access_key.nonce = delegate_nonce.nonce()` at [1](#0-0) ), so a `DelegateAction` nonce, once successfully executed, becomes the new watermark and cannot be reused **as long as the same access key row persists**. The vulnerability requires that watermark to be reset to something *below* an already-used-or-crafted nonce via `DeleteKey` + `AddKey`.

The reseed formula on `AddKey` is purely a function of the current block height at the moment of re-creation — `initial_nonce_value(block_height) = (block_height - 1) * ACCESS_KEY_NONCE_RANGE_MULTIPLIER` [2](#0-1) [3](#0-2)  — and does **not** consult the nonce the deleted key held before deletion. The `DelegateAction` upper-bound check likewise depends only on `apply_state.block_height` at the time of the *replay* attempt [4](#0-3) , not on the height at which the delegate action was originally signed/valid.

Because `(block_height-1)*1e6` is strictly less than `block_height*1e6` (the upper bound for that same height), any nonce `X` in the half-open interval `((H-1)*1e6, H*1e6)` remains a "legal-looking" nonce for a key freshly recreated at height `H`. The design note in `docs/DataStructures/AccessKey.md` states the *intended* invariant — "the nonce of the new access key should be equal to the nonce of the old access key… required to avoid replaying old transactions again" [5](#0-4)  — but the actual implementation does not enforce equality to the old nonce; it only uses the block-height formula, which can undercut a nonce that was valid/used against the key **before** deletion, provided the delete+recreate transaction lands at the *same or an earlier block height* than the one for which the stale nonce was valid (`H_reset ≤ H_sign`).

This is exploitable by an ordinary account owner fully in control of both the timing of `DeleteKey`+`AddKey` and the choice of the stale `DelegateAction` nonce: choose `X` close to `H_sign * 1e6` (but still `< H_sign * 1e6`), get the `DeleteKey`/`AddKey` transaction included at block height `H_reset ≤ H_sign`, then submit/replay the old `DelegateAction` — it passes both the `<=` check (against the new, lower seed) and the upper-bound check (against the block height at replay time, which only grows). Since the nonce is persisted back into state on successful execution (line 715), if that exact `DelegateAction` had *already been executed once* before deletion, this allows a genuine **double execution/replay of the same signed delegated action** after key deletion+recreation — a nonce-monotonicity break scoped to the `DelegateAction` path (and structurally the same weakness applies to regular transaction nonces via `verify_nonce` in `runtime/runtime/src/verifier.rs:210-237`, which uses the identical block-height-based upper bound formula).

I could not find any mechanism in `access_keys.rs`/`actions.rs` that preserves or floors the new nonce at the old key's last-used value across deletion — no "last nonce" is carried in `Account` or elsewhere; deletion (`remove_access_key`/`delete_regular_key`, lines 136-147) fully discards the row and the new `AddKey` seeding logic (lines 230-255) is agnostic of the previous key state. This matches the question's second (race) hypothesis rather than the first: the reseed **can** land below a previously-valid/used nonce, and replay succeeds instead of being rejected, specifically when the recreation happens at a block height no greater than the height for which the stale nonce was valid.

### Title
DelegateAction/AccessKey nonce watermark reset on key delete+recreate allows replay of a stale/previously-used nonce - ([File: runtime/runtime/src/access_keys.rs], [File: runtime/runtime/src/actions.rs])

### Summary
`AddKey` reseeds an access key's nonce solely from `(block_height-1)*ACCESS_KEY_NONCE_RANGE_MULTIPLIER`, ignoring the nonce the previously-deleted key held. If the delete+recreate transaction is processed at a block height `H_reset` no greater than the height `H_sign` for which a previously valid/used `DelegateAction` nonce `X` was chosen (with `X` in `((H_reset-1)*1e6, H_sign*1e6)`), the new watermark `(H_reset-1)*1e6` is lower than `X`, letting that stale `DelegateAction` pass both the `<=` monotonicity check and the block-height upper-bound check, causing it to execute (or re-execute) after the key was supposedly reset.

### Finding Description
`validate_delegate_action_key` rejects a delegate nonce only if `delegate_nonce.nonce() <= current_nonce` [6](#0-5)  and only if it is `>= apply_state.block_height * ACCESS_KEY_NONCE_RANGE_MULTIPLIER` [7](#0-6) . On success it writes `access_key.nonce = delegate_nonce.nonce()` back to state [1](#0-0) , which is the only mechanism preventing that exact nonce (or anything ≤ it) from being reused — **as long as the same key row survives**.

`DeleteKey` fully removes the access key row (`remove_access_key`) [8](#0-7) , and a subsequent `AddKey` for the same public key re-seeds the nonce purely from `initial_nonce_value(apply_state.block_height)` = `(block_height-1)*1e6` [2](#0-1) [9](#0-8) , with no reference to the old key's prior nonce value. Because `(H-1)*1e6 < H*1e6` for the same height `H`, and the upper-bound check for a `DelegateAction` re-submission only depends on the block height at the time of *re-submission* (not the height at which the nonce was originally crafted/used), a `DelegateAction` nonce `X` satisfying `(H_reset-1)*1e6 < X < H_sign*1e6` for `H_reset ≤ H_sign` will pass validation against the freshly reseeded key even though `X` was already valid (or already used/executed) prior to deletion. This directly contradicts the documented intended invariant that "the nonce of the new access key should be equal to the nonce of the old access key… to avoid replaying old transactions again" [5](#0-4) , which the actual block-height-based reseed does not implement.

### Impact Explanation
This is a nonce-monotonicity/replay violation scoped to a delegated action being executed a second time (or an old, intentionally-abandoned signed `DelegateAction` becoming valid again) after the signer deleted and recreated the same public key — falling under the "double-spend/replay" bounty category. Concrete fund loss depends on the semantics of the replayed `DelegateAction`'s inner actions (e.g., re-triggering a `FunctionCall` to a third-party contract that assumes one-time execution, or a `Transfer`), but the underlying protocol invariant break (nonce watermark can be lowered by the key owner below previously-authorized/used values) is demonstrable purely within `runtime/runtime` unit/integration tests. The identical weakness exists in `verify_nonce` for plain transactions [10](#0-9) , broadening the scope beyond `DelegateAction` alone.

### Likelihood Explanation
Fully attacker-controlled: requires only a full-access key on the sender's own account, no privileged role. The attacker must land a `DeleteKey`+`AddKey` transaction (or two sequential txs) at a block height no greater than the height implied by a previously crafted/used nonce. Precise same-block timing is not strictly required — the attacker has a margin of up to `ACCESS_KEY_NONCE_RANGE_MULTIPLIER` (1,000,000) nonce values and can choose `X` generously within that band, and can retry across multiple blocks if a specific height is missed, making this readily repeatable at negligible cost (a few transaction fees).

### Recommendation
When re-adding an access key with a public key that was deleted, floor the reseeded nonce at `max((block_height-1)*ACCESS_KEY_NONCE_RANGE_MULTIPLIER, last_known_nonce_for_this_public_key)`. Since the trie key is removed on deletion, this requires either (a) persisting the last nonce for a `(account_id, public_key)` pair across deletion (e.g., a tombstone value), or (b) enforcing that `AddKey` nonce seeding is monotonic on-chain per public key. Alternatively, disallow `DeleteKey` immediately followed by `AddKey` of the exact same public key within the same or an earlier-implied nonce window, or bind `DelegateAction`/transaction upper-bound checks to the height recorded on the access key at its most recent creation rather than solely the current block height.

### Proof of Concept
Integration/runtime test plan (extending `runtime/runtime/src/actions.rs` test module, using `apply_delegate_action`/`validate_delegate_action_key` and `action_add_key`/`action_delete_key` harnesses already present, e.g. `create_apply_state`, `setup_account`, `create_delegate_action_receipt`):
1. Create account with full-access key `pk`; set its stored nonce to `X = H_sign*1e6 - 500000` for a chosen future height `H_sign` (simulating a previously-signed-but-unsubmitted `DelegateAction` with nonce `X`, or simulating that `X` was already consumed by a prior successful `DelegateAction` execution).
2. Call `action_delete_key` for `pk`, then `action_add_key` for `pk` with `apply_state.block_height = H_reset` where `H_reset ≤ H_sign` (e.g., `H_reset = H_sign`).
3. Assert the access key's nonce is now `(H_reset-1)*1e6`, which is `< X`.
4. Call `validate_delegate_action_key` / `apply_delegate_action` with a `DelegateAction` carrying `nonce = X` and `apply_state.block_height = H_sign` (or later).
5. Expected (buggy) result: `result.result` is `Ok`, i.e., the action succeeds — whereas the invariant "delegate nonce monotonicity survives key deletion/recreation" would require `Err(ActionErrorKind::DelegateActionInvalidNonce { .. })`. The test should assert the latter to demonstrate the current code fails to reject the stale nonce.

/// Verify that the transaction nonce is valid.
fn verify_nonce(
    tx_nonce: Nonce,
    current_nonce: Nonce,
    block_height: Option<BlockHeight>,
    nonce_mode: NonceMode,
) -> Result<(), InvalidTxError> {
    match nonce_mode {
        NonceMode::Monotonic => {
            if tx_nonce <= current_nonce {
                return Err(InvalidTxError::InvalidNonce { tx_nonce, ak_nonce: current_nonce });
            }
        }
        NonceMode::Strict => {
            if !current_nonce.checked_add(1).is_some_and(|expected| tx_nonce == expected) {
                return Err(InvalidTxError::InvalidNonce { tx_nonce, ak_nonce: current_nonce });
            }
        }
    }
    if let Some(height) = block_height {
        let upper_bound = height
            .saturating_mul(near_primitives::account::AccessKey::ACCESS_KEY_NONCE_RANGE_MULTIPLIER);
        if tx_nonce >= upper_bound {
            return Err(InvalidTxError::NonceTooLarge { tx_nonce, upper_bound });
        }
    }
    Ok(())
}
