### Title
Unprivileged dust-fill of `depositTokensOfAccount` blocks victim from adding new collateral and forces liquidation - (File: contracts/DepositToken.sol)

### Summary
`Pool` caps each account's combined deposit/debt token list at `MAX_TOKENS_PER_USER = 30` via `onlyIfAdditionWillNotReachMaxTokens` in `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` (contracts/Pool.sol:143-148, 204-220). `DepositToken._transfer` and `DepositToken._mint` unconditionally push the token into the recipient's per-account list whenever the recipient's balance goes from 0 to >0 (contracts/DepositToken.sol:517-525, 485-488). Crucially, `deposit(amount_, onBehalfOf_)` mints to an arbitrary `onBehalfOf_` (contracts/DepositToken.sol:211-237), so anyone can add entries to a victim's list without consent — mirroring CVE-2025-21503's "easily exploitable, complete loss of availability" bug class on Metronome's own accounting surface.

### Finding Description
1. Attacker calls `depositToken_i.deposit(dust, victim)` for every listed `DepositToken` the victim does not yet hold (and/or `transfer(victim, dust)`), filling `depositTokensOfAccount[victim]` + `debtTokensOfAccount[victim]` to 30.
2. Once at the cap, any subsequent action that would add a new token to the victim's list reverts with `UserReachedMaxTokens`: `deposit` of a new collateral type to the victim, `transfer`/`transferFrom` of a new `DepositToken` to the victim, `DebtToken` issuance paths that add a new debt token, and `seize` during `Pool.liquidate` if it would add a new token to the liquidated account's list.
3. Removal of an entry requires the balance to go to zero via `_transfer`/`_burn`, but `transfer` and `withdraw` gate on `_revertIfLocked` → `unlockedBalanceOf` (contracts/DepositToken.sol:180-182, 348-412). When the victim carries debt, `unlockedBalanceOf` returns 0 or a capped amount (contracts/DepositToken.sol:383-398), so the victim may be unable to clear the dust entries precisely when they need to.
4. Result: a victim whose position is approaching the liquidation threshold cannot deposit additional collateral of a new type to restore health, and cannot remove the blocking dust entries because they are locked. The position is forced into liquidation, converting a liveness failure into a direct loss (liquidator incentive + protocol fee taken from the victim's collateral).

### Impact Explanation
Availability-style analog of the CVE: an unprivileged attacker causes a repeatable, state-level denial of service against a targeted account. The victim's ability to add collateral (the primary defense against liquidation) is disabled while their balances are locked by debt, producing forced liquidation and loss of collateral value equal to the seized amount including incentives/fees. In pools with few listed collaterals the impact degrades to a temporary freeze the victim can clear once balances are unlocked.

### Likelihood Explanation
Feasible for any EOA at the cost of dust deposits; no privileged role needed since `deposit(amount_, onBehalfOf_)` accepts an arbitrary beneficiary and `transfer` is permissionless. The precondition is that enough distinct `DepositToken`s (or a mix with `DebtToken`s minted to the victim via public issue paths where the attacker fronts debt) exist in the pool to reach the 30-slot cap, and that the victim holds debt so the dust is locked. Both are realistic for mature pools with many listed collaterals.

### Recommendation
Decouple the cap from unsolicited receipt: e.g. let `addToDepositTokensOfAccount` skip (rather than revert) at the cap and iterate actual balances via token enumeration, exempt `seize`/liquidation paths, or make `deposit` revert/redirect when `onBehalfOf_` is already at the cap with no balance in that token. Alternatively allow forced removal of dust entries by anyone via a pull pattern.

### Proof of Concept
Hardhat fork outline:
```ts
// setup: pool P lists deposit tokens D[0..N-1]; victim has debt so unlockedBalanceOf == 0
for (const d of depositTokens) {
  if ((await d.balanceOf(victim)) === 0) {
    await underlying.approve(d.address, 1);
    await d.deposit(1, victim.address); // adds d to victim's list
  }
}
// victim's combined list now == MAX_TOKENS_PER_USER
await expect(newDepositToken.deposit(amount, victim.address))
  .revertedWithCustomError(pool, 'UserReachedMaxTokens');
await expect(dustToken.connect(victim).transfer(attacker.address, 1))
  .revertedWithCustomError(dustToken, 'NotEnoughFreeBalance'); // locked by debt
// oracle moves victim below healthy; pool.liquidate succeeds — victim could not de-risk
```
