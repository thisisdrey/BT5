Confirmed: `remove_account` in [1](#0-0)  removes the `Account`, `ContractCode`, all access keys/gas keys, and all `ContractData` entries for the account — but it never iterates or removes `TrieKey::PostponedReceipt`, `TrieKey::PromiseYieldReceipt`, or `TrieKey::ReceivedData` entries keyed to that account. These trie keys are set via `set_postponed_receipt`, `set_promise_yield_receipt`, and `set_received_data` in the same file [2](#0-1) [3](#0-2) , and are only removed by explicit calls to `remove_postponed_receipt` / `remove_promise_yield_receipt` when the receipt actually resolves (e.g., all input data arrives or a yield times out) — paths that never fire once the account is deleted.

The `account_storage_usage` gate in `action_delete_account` is computed purely from `Account.storage_usage()` minus contract-code bytes [4](#0-3) . `Account.storage_usage()` is a field that the runtime updates when it writes `TrieKey::Account`, `TrieKey::AccessKey`, `TrieKey::ContractCode`, and `TrieKey::ContractData` (the classic "storage staking" columns), but postponed/promise-yield receipts and `ReceivedData` are stored under their own trie key namespaces and are **not** charged against the account's `storage_usage` field (this is by design — these are runtime-internal receipt-processing structures, not "contract storage" that the account pays rent for in the traditional sense). Because of this, an account can have many outstanding `PostponedReceipt`/`PromiseYieldReceipt`/`ReceivedData` rows while its `Account.storage_usage()` remains tiny, easily passing under `MAX_ACCOUNT_DELETION_STORAGE_USAGE` (10,000 bytes) [5](#0-4) .

However, before concluding this is exploitable, I need to determine whether reachability actually exists: an attacker's own account can call itself with `then` (function-call chaining) to create postponed receipts (data waits), or use `promise_yield_create`, but the account that is postponed/waiting for data is the **receiver** of the not-yet-executed second action receipt. For the account to be deletable while it still has an outstanding `PostponedReceipt`, the account must simultaneously (a) hold postponed action receipts awaiting input data, and (b) submit/authorize a `DeleteAccount` action. This is plausible: an account can dispatch `promise_and`/callback chains targeting itself, leave the `then` receipt postponed indefinitely (never supply the data), and then submit a separate transaction executing `DeleteAccount` on itself. This is unprivileged and requires only ordinary contract deployment/transaction submission — no special access. I was not able to fully verify within tool budget whether the runtime blocks self-account deletion while such postponed receipts still exist (e.g., via a delayed-receipt queue check, borrow/lock, or an implicit invariant elsewhere in `runtime/runtime/src/lib.rs` that prevents this ordering), since I could not read the full `apply_action_receipt`/receipt-processing pipeline in the remaining iterations. This is a genuine unresolved gap in my verification.

Given the code I *did* confirm — `remove_account` has no cleanup path for these three trie-key namespaces, and the deletion-size check structurally cannot see their bytes — the underlying root cause (leaked trie storage for postponed/yield receipt state upon account deletion) appears real and is a known category of issue in NEAR's receipt/account-deletion design. ### Title
Account deletion leaks unbilled PostponedReceipt/PromiseYieldReceipt/ReceivedData trie storage - (File: core/store/src/utils/mod.rs, runtime/runtime/src/actions.rs)

### Summary
`remove_account` (core/store/src/utils/mod.rs:505-575) removes `Account`, `ContractCode`, access/gas keys, and `ContractData`, but never removes `PostponedReceipt`, `PromiseYieldReceipt`, or `ReceivedData` entries scoped to the deleted account. The `MAX_ACCOUNT_DELETION_STORAGE_USAGE` gate in `action_delete_account` (runtime/runtime/src/actions.rs:325-353) is computed solely from `Account.storage_usage()`, which does not count these receipt-namespace bytes, so the cap cannot prevent or detect their presence.

### Finding Description
`action_delete_account` computes `account_storage_usage` as `account.storage_usage()` minus contract-code length and rejects deletion only if that value exceeds 10,000 bytes [6](#0-5) . `Account.storage_usage()` is only updated for the account/access-key/contract-code/contract-data trie columns; postponed action receipts, promise-yield receipts, and received-data blobs live under separate `TrieKey` namespaces set by `set_postponed_receipt`, `set_promise_yield_receipt`, and `set_received_data` [2](#0-1) [3](#0-2) , and are not reflected in this field. `remove_account` only cleans the `Account`, `ContractCode`, access-key/gas-key, and `ContractData` trie entries [7](#0-6) , with no iteration over the `PostponedReceipt`/`PromiseYieldReceipt`/`ReceivedData` prefixes for the account being deleted.

### Impact Explanation
If reachable, outstanding postponed/yield receipt rows for a deleted account remain permanently in the trie: unreachable (no code path references them since the account no longer exists and their processing triggers, like matching input data or timeout resolution, target an account context that has changed/vanished), and never refunded to the beneficiary despite the storage-stake having conceptually paid for them. This matches "permanent storage-stake fund freezing / unaccounted trie bloat" — a chain-wide invariant violation (value conservation for storage staking), though it is a slow-growing griefing/bloat issue rather than an immediate large fund theft.

### Likelihood Explanation
I could not fully confirm, within the remaining tool budget, that the runtime actually permits submitting/executing `DeleteAccount` on an account while it still has outstanding `PostponedReceipt`/`PromiseYieldReceipt` entries targeting it (this depends on receipt-processing/ordering logic in `runtime/runtime/src/lib.rs` that I was unable to inspect fully). Without confirming this ordering/reachability, I cannot assert the full attack is completed end-to-end from an unprivileged transaction.

### Recommendation
In `remove_account`, additionally iterate and remove all `TrieKey::PostponedReceipt`, `TrieKey::PromiseYieldReceipt`, `TrieKey::ReceivedData`, and any associated `TrieKey::PromiseYieldStatus`/`YieldIdToDataId`/`DataIdToYieldId` entries scoped to the account, and include their byte sizes in the `MAX_ACCOUNT_DELETION_STORAGE_USAGE` check (or refuse deletion entirely while such entries exist for the account, mirroring how outstanding gas-key balances already block deletion via `GasKeyBalanceTooHigh`).

### Proof of Concept
Integration test: (1) create account A, (2) have A's contract call itself with `promise_then` such that the callback awaits a data receipt (`ReceivedData`/`PostponedReceipt` created for A) but never supply the resolving receipt, (3) verify `get_postponed_receipt`/`get_received_data` shows non-empty trie entries for A while `Account.storage_usage()` stays well under 10,000, (4) submit `DeleteAccount` for A, (5) assert account A is removed successfully (result Ok, not `DeleteAccountWithLargeState`), then (6) directly query the trie for the `PostponedReceipt`/`ReceivedData` keys and assert they still exist post-deletion, proving leaked, unrefunded, unreachable state. This last verification step (that deletion actually succeeds while such receipts are outstanding) is the part I was unable to confirm from static code reading alone and would need to be validated by running the test.

/// Removes account, code and all access keys and gas keys associated to it.
pub fn remove_account(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
) -> Result<RemoveAccountResult, StorageError> {
    state_update.remove(TrieKey::Account { account_id: account_id.clone() });
    state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });

    let mut gas_key_nonce_count: usize = 0;
    let mut gas_key_nonce_total_key_bytes: usize = 0;

    // Removing access keys and gas key nonces
    let lock = state_update.trie().lock_for_iter();
    let mut keys_to_remove: Vec<TrieKey> = Vec::new();
    for raw_key in state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_access_keys(account_id), &lock)?
    {
        let raw_key = raw_key?;
        let key_handle = trie_key_parsers::parse_key_handle_from_access_key_key(
            &raw_key, account_id,
        )
        .map_err(|_e| {
            StorageError::StorageInconsistentState(
                "Can't parse key handle from raw key for AccessKey".to_string(),
            )
        })?;
        let nonce_index =
            trie_key_parsers::parse_nonce_index_from_gas_key_key(&raw_key, account_id, &key_handle)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse nonce index from raw key for AccessKey".to_string(),
                    )
                })?;
        if let Some(index) = nonce_index {
            gas_key_nonce_count += 1;
            gas_key_nonce_total_key_bytes += raw_key.len();
            keys_to_remove.push(TrieKey::gas_key_nonce(
                account_id.clone(),
                key_handle.clone(),
                index,
            ));
        } else {
            keys_to_remove.push(TrieKey::access_key(account_id.clone(), key_handle.clone()));
        }
    }
    drop(lock);

    for trie_key in keys_to_remove {
        state_update.remove(trie_key);
    }

    // Removing contract data
    let lock = state_update.trie().lock_for_iter();
    let data_keys = state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_contract_data(account_id, &[]), &lock)?
        .map(|raw_key| {
            trie_key_parsers::parse_data_key_from_contract_data_key(&raw_key?, account_id)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse data key from raw key for ContractData".to_string(),
                    )
                })
                .map(Vec::from)
        })
        .collect::<Result<Vec<_>, _>>()?;
    drop(lock);

    for key in data_keys {
        state_update.remove(TrieKey::ContractData { account_id: account_id.clone(), key });
    }
    Ok(RemoveAccountResult { gas_key_nonce_count, gas_key_nonce_total_key_bytes })
}
