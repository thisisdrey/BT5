Audit Report

## Title
Unbacked/lost user funds from `snowbridge-pallet-system-frontend::add_tip` when destination tip crediting fails - (File: `bridges/snowbridge/pallets/system-frontend/src/lib.rs`)

## Summary
`SystemFrontend::add_tip` on AssetHub swaps the user's tip asset for Ether and irrevocably burns it via `burn_for_teleport` before sending an unpaid, best-effort `Transact` XCM to BridgeHub to credit the tip to the referenced `Inbound`/`Outbound` message. If the nonce/order has already been consumed by ordinary relayer processing by the time the XCM arrives, `EthereumSystemV2::add_tip` fails and the amount is only recorded into `LostTips` with no refund or recovery mechanism, permanently destroying the user's value.

## Finding Description
`add_tip` is a public, unprivileged, signed extrinsic on AssetHub. It calls `swap_fee_asset_and_burn`, which swaps the supplied asset for Ether and burns it via `burn_for_teleport::<T::AssetTransactor>` unconditionally and before any destination-side confirmation. It then sends a best-effort `Transact` XCM containing `EthereumSystemCall::AddTip { sender, message_id, amount }` to BridgeHub.

On BridgeHub, `EthereumSystemV2::add_tip` dispatches to `InboundQueue::add_tip(nonce, amount)` or `OutboundQueue::add_tip(nonce, amount)` depending on `message_id`. `InboundQueue::add_tip` fails with `AddTipError::NonceConsumed` if `Nonce::<T>::get(nonce)` is already `true` — which happens whenever `process_message` (triggered by any relayer's normal `submit` call) has already run and executed `Nonce::<T>::set(nonce)`. `OutboundQueue::add_tip` fails with `AddTipError::UnknownMessage` if `PendingOrders::<T>::get(nonce)` returns `None`, which happens once `process_delivery_receipt` removes the order after normal delivery-receipt processing.

Both failure paths are caught in `EthereumSystemV2::add_tip`, which does not propagate the error to fail the call — it only records the lost amount into `LostTips::<T>` for bookkeeping, per the pallet's own doc comment: "Capturing the lost tips here supports implementing a recovery method in the future." No such recovery method currently exists in the repository, so the burned Ether is unconditionally and permanently lost with no path back to the user.

The root cause is a lack of atomicity between the two-chain protocol steps: consumption of value (burn) on AssetHub happens unconditionally before the destination-side crediting is known to succeed, and the destination check inherently races against ordinary relayer message/receipt processing (an expected concurrent activity, not an attack).

## Impact Explanation
This matches the "permanent user-fund lock" / underpriced-work impact category: an ordinary unprivileged user calling the public, non-privileged `add_tip` extrinsic can permanently lose real burned Ether value with zero recovery path, purely as a consequence of normal bridge operation timing (a relayer processing the underlying message before the tip XCM lands). No malicious relayer, validator, or governance action is required — the loss occurs under expected, everyday usage patterns since tips are explicitly meant to be added to already-submitted, not-yet-processed messages.

## Likelihood Explanation
High. The race between a user's tip submission and normal relayer message/receipt processing is not a contrived edge case — it is the expected use case for tips (incentivizing processing of a message that a relayer hasn't picked up yet). Given XCM's asynchronous, best-effort, unpaid delivery model between AssetHub and BridgeHub, this race is likely to occur regularly in production without requiring any adversarial behavior.

## Recommendation
- Avoid burning/consuming the tip asset on AssetHub before destination-side crediting is confirmed successful; hold or reserve the asset and finalize the burn only upon confirmed success (e.g., via an XCM response/receipt).
- Implement the recovery method referenced in the `LostTips` doc comment now, allowing the original `sender` to reclaim their recorded `LostTips` balance.
- Add a compensating XCM/message from BridgeHub back to AssetHub to refund equivalent value to `sender` when `add_tip` fails.

## Proof of Concept
1. User observes a pending Ethereum→Polkadot message with nonce `N` not yet processed in `EthereumInboundQueueV2`.
2. User calls `SystemFrontend::add_tip(origin, MessageId::Inbound(N), asset)` on AssetHub; `swap_fee_asset_and_burn` swaps and burns the asset for Ether immediately.
3. A relayer submits the proof for nonce `N` first, causing `process_message` to run `Nonce::<T>::set(nonce)` before the tip's `Transact` XCM arrives at BridgeHub.
4. The tip's `Transact` dispatches `EthereumSystemV2::add_tip`, which calls `InboundQueue::add_tip(nonce, amount)`; since `Nonce::<T>::get(nonce)` is now `true`, it returns `AddTipError::NonceConsumed`.
5. `EthereumSystemV2::add_tip` catches the error, records it into `LostTips::<T>` for `sender`, and emits `TipProcessed { success: false }` — matching the existing test `add_tip_inbound_fails_when_nonce_is_consumed`, which asserts `lost_tip == 1000` with no refund issued.
6. The user's burned Ether is permanently lost; `LostTips` provides no recovery mechanism.

			fee_asset: Asset,
		) -> Result<u128, DispatchError> {

			let (fee_asset_location, fee_amount) = match fee_asset {

					return Err(Error::<T>::UnsupportedAsset.into());

				return Ok(0);
			}

					.map_err(|_| Error::<T>::BurnError)?;
				fee_amount
			};
			Ok(ether_gained)

	impl<T: Config> Pallet<T> {
		pub fn process_message(relayer: T::AccountId, message: Message) -> DispatchResult {
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == message.gateway, Error::<T>::InvalidGateway);

			let (nonce, relayer_fee) = (message.nonce, message.relayer_fee);

			// Verify the message has not been processed
			ensure!(!Nonce::<T>::get(nonce), Error::<T>::InvalidNonce);

			// Mark message as received
			Nonce::<T>::set(nonce);

			let message_id = T::MessageProcessor::process_message(relayer.clone(), message)
				.map_err(|e| match e {
					MessageProcessorError::ProcessMessage(e) => e,
					MessageProcessorError::ConvertMessage(e) => Error::<T>::from(e).into(),
					MessageProcessorError::SendMessage(e) => Error::<T>::from(e).into(),
				})?;

			// Pay relayer reward
			let tip = Tips::<T>::take(nonce).unwrap_or_default();
			let total_tip = relayer_fee.saturating_add(tip);
			if total_tip > 0 {
				T::RewardPayment::register_reward(&relayer, T::DefaultRewardKind::get(), total_tip);
			}

			// Emit event with the message_id
			Self::deposit_event(Event::MessageReceived { nonce, message_id });

			Ok(())
		}
	}

		fn add_tip(nonce: u64, amount: u128) -> Result<(), AddTipError> {
