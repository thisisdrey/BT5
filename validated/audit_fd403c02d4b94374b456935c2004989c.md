## Title
`ft_on_transfer` credits the nominal transfer amount instead of the tokens actually received, allowing fee-on-transfer/deflationary NEP-141 tokens to inflate `defuse`'s internal ledger beyond real custody - (File: `contracts/defuse/src/contract/tokens/nep141/deposit.rs`)

### Summary
`Contract::ft_on_transfer` mints multi-token balance equal to the raw `amount` parameter supplied in the NEP-141 callback, without ever comparing it to the actual balance change on the token contract. Any account can permissionlessly deploy or use a fee-charging/deflationary NEP-141 token and deposit it into `defuse`, causing the internal ledger (`total_supplies` / `token_balances`) for that `TokenId` to exceed the real tokens the contract custodies on-chain.

### Finding Description
`ft_on_transfer` calls `self.deposit(receiver_id, [(token_id, amount.0)], ...)` directly using the `amount` value passed by the predecessor FT contract: [1](#0-0) 

`deposit()` unconditionally adds this `amount` to both `total_supplies` (the ledger's claim on how much of that token the contract holds) and the recipient's `token_balances`: [2](#0-1) 

There is no verification anywhere in this path (nor in the `nep245`/`nep171` analogs) that the contract's actual token balance increased by `amount.0`. For a NEP-141 token that charges a transfer fee (a common pattern for deflationary/tax tokens), the value reported in the `ft_on_transfer` callback (per NEP-141, decided entirely by the token contract implementation) can be the nominal pre-fee amount while the real balance increase on `defuse`'s account is smaller. This breaks the intended invariant: `total_supplies[TokenId::Nep141(token)]` (what the ledger says users are owed) must equal the real NEP-141 balance `defuse` holds on that `token` contract (the asset the `TokenId` names versus the asset actually moved into custody).

Because `ft_on_transfer` is reachable by any account calling `ft_transfer_call` on any NEP-141 contract they control (deploying such a token is fully permissionless), an attacker can trigger this mismatch without any privileged role, relayer, or victim action.

### Impact Explanation
Once the ledger for a given `TokenId::Nep141` is over-credited relative to real custody, the pool becomes under-collateralized: some users who legitimately deposited that token will be unable to fully withdraw their credited balance once the shortfall is realized (later withdrawers effectively have their funds permanently frozen/lost, since `ft_withdraw`/`do_ft_withdraw` attempts to move the credited amount out of a contract account that does not actually hold it). This matches the "funds permanently frozen" / ledger-imbalance impact class: the sum of internally tracked balances for a `TokenId` no longer equals the actual custodied asset amount.

### Likelihood Explanation
High for any deployment that accepts arbitrary/unwhitelisted NEP-141 tokens as deposit assets, since nothing in `ft_on_transfer`, `deposit()`, or `resolve_deposit_internal` measures actual balance delta — the trust is placed entirely in the caller-supplied `amount`. No privileged role, governance action, or victim cooperation is required; the attacker only needs to deploy (or use) a fee-on-transfer NEP-141 token and call `ft_transfer_call` into `defuse`.

### Recommendation
Before crediting `amount.0` in `ft_on_transfer` (and the `nep171`/`nep245` equivalents), measure the actual balance change of the token by querying `ft_balance_of(current_account_id())` on the token contract immediately before and after the transfer (or, at minimum, use the token's own `ft_transfer_call`/resolve semantics to bound credited amounts by actually-received value), and only credit the delta actually observed rather than the caller-declared `amount`.

### Proof of Concept
1. Deploy a NEP-141 contract `feetoken.near` whose `ft_transfer`/`ft_transfer_call` implementation deducts, e.g., a 5% fee on every transfer (burns or redirects it), but still invokes the receiver's `ft_on_transfer(sender_id, amount=<pre-fee amount>, msg)` per NEP-141.
2. Attacker calls `feetoken.ft_transfer_call(defuse.near, 1000, "", msg)`.
3. `defuse`'s real NEP-141 balance on `feetoken` increases by only 950, but `ft_on_transfer` executes `self.deposit(receiver_id, [(TokenId::Nep141(feetoken), 1000)], ...)`, crediting 1000 units into the internal ledger.
4. Repeat/scale across multiple depositors of `feetoken`; eventually the sum of ledger balances for that `TokenId` exceeds the real balance `defuse` holds on `feetoken`.
5. When users attempt to withdraw their full credited balances via `ft_withdraw`, the last withdrawer(s) find the underlying token transfer cannot be satisfied from the real (smaller) custodied balance, demonstrating the ledger/custody mismatch and resulting loss.

```rust
    fn ft_on_transfer(
        &mut self,
        sender_id: AccountId,
        amount: U128,
        msg: String,
    ) -> PromiseOrValue<U128> {
        require!(amount.0 > 0, "zero amount");

        let token_id = TokenId::Nep141(Nep141TokenId::new(env::predecessor_account_id()));

        let DepositMessage {
            receiver_id,
            action,
        } = if msg.is_empty() {
            DepositMessage::new(sender_id.clone())
        } else {
            msg.parse().unwrap_or_else(|e| panic!("{e}"))
        };

        self.deposit(
            receiver_id.clone(),
            [(token_id.clone(), amount.0)],
            Some("deposit"),
        )
        .unwrap_or_else(|err| err.panic());
```
