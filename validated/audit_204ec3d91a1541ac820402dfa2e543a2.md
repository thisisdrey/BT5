## Analysis

The external report's core broken invariant: **an unauthenticated/low-privilege actor can submit a message whose verification cost scales with attacker-controlled proof size, while the runtime charges a fixed weight/fee unrelated to that cost** — enabling public underpriced work that degrades block production.

I traced this pattern to Snowbridge's `inbound-queue-v2` pallet.

### Title
Underpriced, unbounded proof-size public dispatch enables block-production DoS in Snowbridge inbound queue - (File: `bridges/snowbridge/pallets/inbound-queue-v2/src/lib.rs`)

### Summary
`Pallet::submit` is a `Signed`-origin (any funded account, not a permissioned relayer) extrinsic charged a single **fixed** weight, `T::WeightInfo::submit()`, which in the current implementation is a hard-coded constant (`Weight::from_parts(60_000_000, 0)` plus fixed DB weight) [1](#0-0) . This weight does not scale with the size of the caller-supplied `EventProof`, whose `Proof.receipt_proof: Vec<Vec<u8>>` and `ExecutionProof.execution_branch: Vec<H256>` / `AncestryProof.header_branch: Vec<H256>` fields are unbounded `Vec`s with no `BoundedVec`/`MaxEncodedLen` constraint [2](#0-1) [3](#0-2) .

### Finding Description
`submit` is defined as:
```rust
#[pallet::weight(T::WeightInfo::submit())]
pub fn submit(origin: OriginFor<T>, event: Box<EventProof>) -> DispatchResult {
    let who = ensure_signed(origin)?;
    ...
    T::Verifier::verify(&event.event_log, &event.proof)...
``` [4](#0-3) 

`ensure_signed` accepts **any** signed account — this is not restricted to a registered/bonded relayer set, so it is a fully public entry point.

The verification path invoked before any economic penalty is applied is:
1. `verify_execution_proof` — walks `ancestry_proof.header_branch` (`Vec<H256>`, attacker-supplied length) through `verify_ancestry_proof`, and separately verifies the `execution_branch` merkle branch against `header.body_root` [5](#0-4) .
2. `verify_receipt_inclusion` → `verify_receipt_proof`, which iterates the caller-supplied `receipt_proof: Vec<Vec<u8>>` (also unbounded) through `alloy_trie::proof::verify_proof`, decoding and hashing each RLP trie node [6](#0-5) .

Both loops perform SHA-256/keccak hashing and RLP/SSZ decoding work proportional to the number and size of the supplied proof nodes/branches, yet the pallet's declared weight is the single constant from the `WeightInfo::submit()` benchmark (`60ms` fixed cost, `3774` bytes fixed PoV) with no per-item multiplier for `receipt_proof.len()`, `execution_branch.len()`, or `header_branch.len()`. There is no top-level bound (e.g., a `MaxProofItems` constant enforced via `ensure!`) rejecting oversized `EventProof` values before the expensive verification runs — the code goes straight from decoding the extrinsic into `T::Verifier::verify(...)` [7](#0-6) .

Because a failing/invalid proof (`InvalidProof`, `HeaderNotFinalized`, etc.) still returns a normal `DispatchResult` error (not `BadOrigin` and not classified `Pays::No`/fee-adjusted for cost), the caller pays only the fixed declared transaction fee for `submit()` regardless of how large the `Vec<Vec<u8>>`/`Vec<H256>` payload was, while the validating collator/node performed unbounded verification work. This is the direct on-chain analog of the report's "Merkle Proof CPU Exhaustion" vector: attacker-controlled proof depth/size drives real CPU cost that is not reflected in the metered/charged weight.

### Impact Explanation
An attacker (no validator, relayer, or governance privilege — only needs a funded signed account) can submit repeated `submit` extrinsics with maximally-sized `receipt_proof` vectors and `execution_branch`/`header_branch` arrays. Each is processed (decode → verify) inside block execution before failing, at CPU cost far exceeding what the fixed benchmarked weight accounts for. Since this dispatch is `Signed`/public (not `Pays::No`, not gated to a bounded relayer set, not size-bounded), sustained submission degrades BridgeHub block production / stalls bridge processing — an in-scope impact under "public underpriced work that degrades block production or stalls bridge processing."

### Likelihood Explanation
Likelihood is high for the underpricing itself: constructing an oversized `EventProof` (large `Vec<Vec<u8>>`/`Vec<H256>`) requires no special access — any signed account can call `submit`, and the transaction only needs to pass basic SCALE decoding to reach the verifier. It does not require a malicious validator, collator, relayer, or governance actor, distinguishing it from the discarded "malicious peer/validator" root causes in the External Report.

### Recommendation
- Bound `receipt_proof`, `execution_branch`, and `header_branch` with `BoundedVec<_, MaxProofLen>` enforced at decode time (SCALE bounded types), matching real Ethereum trie-proof depth expectations.
- Make `WeightInfo::submit` a function of proof length (`submit(receipt_proof_len: u32, branch_len: u32)`) and benchmark it accordingly, consistent with how `pallet-xcmp-queue` scales weight with decoded XCM length (`T::WeightInfo::take_first_concatenated_xcm(xcm_data.len())`) [8](#0-7) .
- Reject `EventProof`s exceeding a configured maximum proof size via a cheap `ensure!` check before invoking `T::Verifier::verify`.

	pub(crate) fn verify_execution_proof(execution_proof: &ExecutionProof) -> DispatchResult {
		let latest_finalized_state =
			FinalizedBeaconState::<T>::get(LatestFinalizedBlockRoot::<T>::get())
				.ok_or(Error::<T>::NotBootstrapped)?;
		// Checks that the header is an ancestor of a finalized header, using slot number.
		ensure!(
			execution_proof.header.slot <= latest_finalized_state.slot,
			Error::<T>::HeaderNotFinalized
		);

		let beacon_block_root: H256 = execution_proof
			.header
			.hash_tree_root()
			.map_err(|_| Error::<T>::HeaderHashTreeRootFailed)?;

		match &execution_proof.ancestry_proof {
			Some(proof) => {
				Self::verify_ancestry_proof(
					beacon_block_root,
					execution_proof.header.slot,
					&proof.header_branch,
					proof.finalized_block_root,
				)?;
			},
			None => {
				// If the ancestry proof is not provided, we expect this beacon header to be a
				// finalized beacon header. We need to check that the header hash matches the
				// finalized header root at the expected slot.
				let state = <FinalizedBeaconState<T>>::get(beacon_block_root)
					.ok_or(Error::<T>::ExpectedFinalizedHeaderNotStored)?;
				if execution_proof.header.slot != state.slot {
					return Err(Error::<T>::ExpectedFinalizedHeaderNotStored.into());
				}
			},
		}

		// Gets the hash tree root of the execution header, in preparation for the execution
		// header proof (used to check that the execution header is rooted in the beacon
		// header body.
		let execution_header_root: H256 = execution_proof
			.execution_header
			.hash_tree_root()
			.map_err(|_| Error::<T>::BlockBodyHashTreeRootFailed)?;

		let execution_header_gindex = Self::execution_header_gindex();
		ensure!(
			verify_merkle_branch(
				execution_header_root,
				&execution_proof.execution_branch,
				subtree_index(execution_header_gindex),
				generalized_index_length(execution_header_gindex),
				execution_proof.header.body_root
			),
			Error::<T>::InvalidExecutionHeaderProof
		);
		Ok(())

```rust
pub fn verify_receipt_proof(
	receipts_root: H256,
	tx_index: u64,
	proof: &[Vec<u8>],
) -> Option<ReceiptEnvelope> {
	let key = receipt_trie_key(tx_index);
	let root = B256::from_slice(receipts_root.as_bytes());
	let proof_nodes: Vec<Bytes> = proof.iter().map(|node| Bytes::copy_from_slice(node)).collect();

	// Call verify_proof with None to extract the value from an inclusion proof. For inclusion
	// proofs, alloy_trie returns ValueMismatch with the extracted value in `got`. The proof is
	// already cryptographically verified during this traversal.
	let value = match verify_proof(root, key, None, proof_nodes.iter()) {
		Ok(()) => return None, // Exclusion proof - key does not exist
		Err(ProofVerificationError::ValueMismatch { path, got: Some(v), expected: None })
			if path == key =>
		{
			v.to_vec()
		},
		Err(_) => return None,
	};

	ReceiptEnvelope::decode(&mut value.as_slice()).ok()
}
