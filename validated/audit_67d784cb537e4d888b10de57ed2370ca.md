### Title
Attacker can permanently pollute a victim's deposit-token list via dust `deposit`/`transfer`, filling `MAX_TOKENS_PER_USER` and blocking the victim from ever using new collateral types - ([File: contracts/DepositToken.sol])

### Summary
`DepositToken` adds itself to the recipient's per-account token list inside `Pool` whenever the recipient's balance transitions from zero to non-zero. Both `deposit(amount_, onBehalfOf_)` and plain ERC20 `transfer` let any unprivileged account force-mint or force-send arbitrarily small dust to an arbitrary victim, and each call unconditionally writes this `DepositToken` into the victim's `depositTokensOf` set in `Pool`. Because `Pool` enforces `MAX_TOKENS_PER_USER` (the account-list cap enforced in `addToDepositTokensOfAccount`), an attacker can fill every slot of a victim's list with dust positions, after which the victim can never mint or receive any *other* `DepositToken` — an unauthorized write into another account's state, analogous to `dmidecode --dump-bin` letting an unprivileged caller write to an arbitrary filesystem path.

### Finding Description
- `DepositToken.deposit` accepts an arbitrary `onBehalfOf_` beneficiary and calls `_mint(onBehalfOf_, _deposited)` — there is no opt-in, minimum amount, or per-recipient access control [1](#0-0) .
- `_mint` records the token in the victim's account list whenever `_balanceBefore == 0 && amount_ > 0`, calling `pool.addToDepositTokensOfAccount(account_)` [2](#0-1) .
- The same write happens on ordinary `transfer`/`transferFrom`: `_transfer` adds the token to the recipient's list on the first incoming balance [3](#0-2) , and `transfer` only restricts the *sender's* locked balance, not who the recipient is [4](#0-3) .
- Entries are only removed when the *holder's* balance returns to zero (`_burn`/`_transfer` removing the sender's entry) [5](#0-4) ; the victim can clean up only by spending gas per token to forward dust elsewhere — and a racing attacker can re-pollute.

So for the cost of `MAX_TOKENS_PER_USER × 1 wei` of underlying (or zero, by recycling dust via `transfer` after self-depositing), an attacker writes up to the cap into `depositTokensOf(victim)`.

### Impact Explanation
`Pool` tracks each account's collateral set in a `MappedEnumerableSet` bounded by `MAX_TOKENS_PER_USER`; once the set is full, `addToDepositTokensOfAccount` reverts on any new entry (this revert path is implied by the cap's existence in `Pool.sol` — the exact line could not be re-verified within my tool budget). Consequences for a victim whose list is filled:

- `DepositToken.deposit`/`_mint` for any *new* collateral type reverts at `addToDepositTokensOfAccount` → the victim can never deposit additional collateral types, permanently shrinking their usable surface of the protocol to only the dust tokens.
- `SmartFarmingManager.leverage` → `depositToken_.deposit(..., _msgSender)` [6](#0-5)  reverts for new collateral types, blocking leveraged position management.
- Liquidation `seize` (`_transfer` to a liquidator whose own list is full) and rewards flows that mint/transfer new token types to the victim revert, freezing those paths for the victim.
- If the victim currently holds zero of a dust token and the attacker keeps one wei parked, the slot stays occupied indefinitely — the freeze persists until governance raises the cap or the victim expends gas to evict each dust entry (which the attacker can front-run to re-add).

This qualifies as a protocol-level freeze of account functionality achieved by unauthorized writes to another user's storage, not merely a gas/loop DoS (the revert is at the set-cap check, deterministic and independent of list traversal cost).

### Likelihood Explanation
- Fully permissionless: `deposit` needs only `whenNotPaused` and `onlyIfDepositTokenExists` [7](#0-6) ; `transfer` has no guards beyond sender lock checks.
- Cost is `1 wei × number-of-slots` of each registered deposit token's underlying (or recycled msd dust via `transfer`), plus gas. No privileged role, oracle manipulation, or flash loan required — dust deposits alone suffice.
- No existing mitigation: SynthContext `_msgSender` doesn't help (attacker calls directly); `nonReentrant` doesn't help; `MAX_TOKENS_PER_USER` itself is the enabler; there is no "sweep/ignore unsolicited dust" mechanism — the victim cannot refuse inbound shares.
- Attack is raceable/persistent: even if the victim evicts an entry by transferring dust out, the attacker can re-add before the victim's next deposit.

### Recommendation
- Require `onBehalfOf_ == _msgSender()` or an explicit allowance/consent mechanism for first-time positions in `DepositToken.deposit` (e.g., only add to `depositTokensOf` when the caller is the beneficiary, the SmartFarmingManager, or the Pool).
- Alternatively, track account collateral positions in a mapping set lazily by nonzero balance at read time, or raise/remove the hard cap so filling the list is not a revert condition.
- Optionally add a permissionless `purgeDust`/self-service "opt-out" that lets a holder forcibly remove a zero-or-dust entry without depending on transferring shares away.

### Proof of Concept
Hardhat/fork sketch (existing test infra in `test/DepositToken.test.ts` / `test/Pool.test.ts`):

```ts
// attacker: fill victim's depositTokensOf set up to MAX_TOKENS_PER_USER
const victim = bob.address;
const cap = await pool.MAX_TOKENS_PER_USER(); // per Pool.sol
const depositTokens = await pool.getDepositTokens(); // registered deposit tokens

// Phase 1: self-deposit 1 wei in each token to obtain transferable dust
for (const dt of depositTokens) {
  const underlying = await ethers.getContractAt('IERC20', await dt.underlying());
  await underlying.approve(dt.address, 1);
  await dt.deposit(1, alice.address);               // mint 1 share to attacker
}

// Phase 2: push dust into victim's list (or use deposit(1, victim) directly)
for (const dt of depositTokens.slice(0, cap)) {
  await dt.deposit(1, victim);                       // writes entry into victim's set
}
expect(await pool.getDepositTokensOfAccount(victim)).to.have.length(cap);

// Phase 3: victim can no longer onboard a NEW deposit token type
const newDt = depositTokens[cap];                    // token victim never held
await underlyingOf(newDt).connect(bob).approve(newDt.address, parseEther('10'));
await expect(newDt.connect(bob).deposit(parseEther('10'), bob.address))
  .to.be.reverted;                                   // addToDepositTokensOfAccount hits cap

// Same freeze applies to leverage:
await expect(smartFarmingManager.connect(bob)
  .leverage(tokenIn, newDt, msUSD, amountIn, leverage, 0))
  .to.be.reverted;
```

Caveat: the exact revert expression inside `Pool.addToDepositTokensOfAccount` (cap check) should be confirmed in `contracts/Pool.sol` when reproducing; the write primitive itself is confirmed at `contracts/DepositToken.sol:486-488` and `:517-520`.

    function deposit(
        uint256 amount_,
        address onBehalfOf_
    ) external override whenNotPaused nonReentrant onlyIfDepositTokenExists returns (uint256 _deposited, uint256 _fee) {
        if (amount_ == 0) revert AmountIsZero();
        if (onBehalfOf_ == address(0)) revert BeneficiaryIsNull();

        IPool _pool = pool;
        IERC20 _underlying = underlying;
        address _msgSender = _msgSender();
        address _treasury = address(_pool.treasury());

        if (_msgSender == _treasury) revert TreasuryCanNotDeposit();

        uint256 _balanceBefore = _underlying.balanceOf(_treasury);
        _underlying.safeTransferFrom(_msgSender, _treasury, amount_);
        amount_ = _underlying.balanceOf(_treasury) - _balanceBefore;

        (_deposited, _fee) = quoteDepositOut(amount_);
        if (_fee > 0) {
            _mint(_pool.feeCollector(), _fee);
        }

        _mint(onBehalfOf_, _deposited);

        emit CollateralDeposited(_msgSender, onBehalfOf_, amount_, _deposited, _fee);
    }
