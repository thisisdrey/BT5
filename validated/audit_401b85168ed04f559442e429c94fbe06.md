### Title
Zero-payment token theft in Market order matching due to missing zero-check in the "taker == maker" branch of `matchSingleOrder` - (File: actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java)

### Summary
`MarketSellAssetActuator.matchSingleOrder` computes the amount a maker receives using integer ratio division (`MarketUtils.multiplyAndDivide`). Two of the three branches in this method explicitly guard against the computed amount being `0` (a near-zero/zero price outcome), but the "taker == maker" branch does not, allowing a taker to fully consume a maker's remaining sell-token quantity while paying zero of the buy token.

### Finding Description
`matchSingleOrder` derives the quantity to be transferred between a taker and maker order using the maker's price ratio via integer division: [1](#0-0) 

When `takerBuyTokenQuantityRemain == 0`, the code explicitly guards against a zero-value fill by returning the sell token to the taker instead of trading: [2](#0-1) 

Similarly, in the "taker > maker" branch, the code explicitly checks for `makerBuyTokenQuantityReceive == 0` and, if so, returns the maker's remaining sell tokens instead of letting the trade complete at zero cost: [3](#0-2) 

However, the "taker == maker" branch computes `makerBuyTokenQuantityReceive` with the exact same `multiplyAndDivide` ratio calculation but has **no such zero check**. It unconditionally zeroes out the maker's remaining sell quantity (fully consuming/closing the maker order) and transfers `takerBuyTokenQuantityReceive = makerOrderCapsule.getSellTokenQuantityRemain()` (the maker's full remaining sell-token balance) to the taker, regardless of whether `makerBuyTokenQuantityReceive` rounded down to `0`: [4](#0-3) 

Because `sellTokenQuantity`/`buyTokenQuantity` for orders are attacker-controlled (there is no minimum-price or minimum-ratio check in `validate()`, only `sellTokenQuantity <= 0 || buyTokenQuantity <= 0`): [5](#0-4) 

an attacker can construct a maker order whose remaining sell quantity, when multiplied by `makerBuyQuantity` and divided (integer division, truncating) by `makerSellQuantity`, evaluates to `0` for a particular remainder value (e.g. `makerSellRemainQuantity=1, makerBuyQuantity=1, makerSellQuantity=1_000_000` → `1*1/1_000_000 = 0`). By crafting a taker order whose `takerBuyTokenQuantityRemain` exactly equals that maker's remaining sell quantity, the "taker == maker" branch triggers, and the maker's entire remaining balance is transferred to the taker for `0` of the buy token — an exact-zero-price acquisition, directly analogous to the near-zero `purchasePrice` scenario described in the CGDA report where a ratio-based/exponential pricing formula can be driven to (near) zero by parameter selection, and where the report's own recommended mitigation is to assert the computed payment amount is `> 0` before allowing the trade.

### Impact Explanation
This is a concrete unauthorized-value-extraction bug reachable by any account submitting `MarketSellAssetContract` transactions (order placer, no special privilege required). A maker's remaining token balance can be drained for zero payment, i.e., theft of funds from the maker and an unbacked/free-token gain for the taker, without either party's consent that a zero-cost trade occur. This matches the "concrete unauthorized account operation / theft of funds" impact bar.

### Likelihood Explanation
Exploitation requires the attacker to control both the maker order (or wait for a naturally occurring small remainder from prior partial fills) and craft a matching taker order whose remaining sell quantity exactly equals the maker's remaining sell quantity, and choose a sell/buy ratio such that integer division of `makerSellRemainQuantity * makerBuyQuantity / makerSellQuantity` truncates to zero. Since order quantities and ratios are fully attacker-controlled and orders can be intentionally partially filled to leave a specific small remainder, an attacker acting as both maker and taker (or coordinating two addresses) can reliably engineer this condition. Likelihood is assessed as Medium-High given full control over the relevant inputs.

### Recommendation
Add a `makerBuyTokenQuantityReceive == 0` guard in the "taker == maker" branch of `matchSingleOrder`, symmetric to the existing guard in the "taker > maker" branch, and treat it identically: return the maker's remaining sell tokens instead of consuming the maker order and transferring value for zero payment. More generally, enforce that any computed transfer amount from `MarketUtils.multiplyAndDivide` is non-zero before finalizing a fill in all three branches of `matchSingleOrder`.

### Proof of Concept
1. Attacker address A places a maker sell order: `sellTokenId=A_token`, `sellTokenQuantity=1_000_000`, `buyTokenId=TRX`, `buyTokenQuantity=1` (price ratio 1,000,000 A : 1 TRX).
2. Through prior partial fills (or by directly constructing the scenario via a sequence of smaller matching taker orders), reduce `makerOrderCapsule.getSellTokenQuantityRemain()` to `1`.
3. Attacker (or colluding address B) submits a taker order buying exactly `1` unit of `A_token` for TRX such that `takerBuyTokenQuantityRemain` (computed via `MarketUtils.multiplyAndDivide`) equals `1`, matching the maker's remaining quantity exactly, triggering the "taker == maker" branch in: [4](#0-3) 
4. `makerBuyTokenQuantityReceive = multiplyAndDivide(1, 1, 1_000_000) = 0` (integer truncation). The maker order is fully closed (`setSellTokenQuantityRemain(0)`, state `INACTIVE`) while the taker receives `takerBuyTokenQuantityReceive = 1` unit of `A_token` for `0` TRX, with no error, no revert, and no return of the maker's asset — a confirmed zero-price token transfer at the maker's expense.
