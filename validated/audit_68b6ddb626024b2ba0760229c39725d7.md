### Title
Relayer reward paid on `submit_delivery_receipt` regardless of the on-chain `success` flag in the `DeliveryReceipt` - (File: `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs`)

### Summary
The Snowbridge outbound-queue-v2 pallet settles relayer rewards for delivered messages without inspecting whether the Ethereum-side execution of the delivered message actually succeeded. The `DeliveryReceipt` decoded from the Ethereum `InboundMessageDispatched` event log carries an explicit `success: bool` field, but `process_delivery_receipt` never reads or branches on it before paying out the reward and clearing the pending order. This mirrors the reported bug class: state (spent/settled amount) is advanced based on an event being observed, not on the underlying operation's actual success.

### Finding Description
The `DeliveryReceipt` struct decoded from the Ethereum event explicitly encodes delivery status: [1](#0-0) 

However, in `process_delivery_receipt`, the pallet looks up the `PendingOrder` by nonce, pays the reward, and removes the order — with no reference to `receipt.success` anywhere in the flow: [2](#0-1) 

The only checks performed are: verifier proof validity, gateway address match, and existence of the `PendingOrder` for the nonce. None of these validate that the message was actually executed successfully on the Ethereum Gateway contract. The `success` field is decoded from the log but silently discarded.

This is structurally the same pattern as the reported vulnerability: an outcome-independent state update (there: `allowance.spent += transferAmount_` regardless of transfer outcome; here: reward payout + `PendingOrders::remove` regardless of `receipt.success`) is performed purely because an event/log was observed, not because the underlying effect actually happened as intended.

### Impact Explanation
If `success: false` deliveries are paid the same reward as `success: true` deliveries, relayers face no economic penalty for failed executions, undermining the incentive design of the receipt/reward mechanism (an unpriced or mispriced settlement condition affecting bridge reward payouts, which the task scope explicitly calls out — "duplicate settlement or payout" / "public underpriced work"). It also means the pallet's `MessageDelivered` event and reward settlement do not distinguish delivery outcomes, contradicting the intended semantics implied by tracking `success` at all in the ABI/event and struct.

### Likelihood Explanation
This is triggerable by any relayer submitting a legitimate delivery receipt for a message whose remote execution reverted/failed on Ethereum (an event that can occur without any malicious actor — legitimate contract-level failures, gas exhaustion of the dispatched command, revert in Transact, etc.), and it is a public, permissionless, unprivileged extrinsic (`submit_delivery_receipt`) requiring only a valid Merkle/Ethereum proof of the log — not a malicious node, prover, or governance actor.

### Recommendation
Branch on `receipt.success` in `process_delivery_receipt`: only pay the full reward (or pay a reduced/no reward) when `success == true`, and record the failure outcome distinctly (e.g. a `MessageDeliveryFailed` event) so downstream logic (and any dependent XCM-side failure handling / asset claim flows) can react correctly to failed remote execution.

### Proof of Concept
1. A message is queued and gets a `PendingOrder { nonce, fee, .. }` via `do_process_message`. [3](#0-2) 
2. The message is executed on Ethereum but reverts/fails, causing the Gateway to emit `InboundMessageDispatched(nonce, topic, success=false, reward_address)`.
3. A relayer submits a valid proof of this event via `submit_delivery_receipt`.
4. `T::Verifier::verify` succeeds (proof is valid), `DeliveryReceipt::try_from` decodes `success: false` correctly, but `process_delivery_receipt` never checks this field — it proceeds to `T::RewardPayment::register_reward(..., order.fee)` and removes the `PendingOrder`, exactly as it would for `success: true`. [4](#0-3) 

I was not able to fully confirm from the index whether `success == false` case is exercised by an existing unit test in `bridges/snowbridge/pallets/outbound-queue-v2/src/test.rs` (only a partial view of the file was retrieved), so I cannot state with certainty whether this omission was already known/accepted as intended design (e.g., rewarding relayers purely for delivery effort independent of execution outcome, analogous to Ethereum gas). A Devin session with full repository access would be needed to check the complete test suite and any related PRDoc discussion for this specific behavior before treating it as a confirmed defect versus accepted design.

		/// Process a delivery receipt from a relayer, to allocate the relayer reward.
		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}
