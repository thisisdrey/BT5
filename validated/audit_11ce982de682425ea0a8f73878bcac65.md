### No vulnerability found for this question.

**Reasoning:**

The claimed binding — "sum(all token_balances deltas for wNEAR across the batch) == 0" — is not an actual invariant of this code, and the described divergence is explicitly documented, intended behavior rather than a bug.

For `native_withdraw`, `storage_deposit`, and `auth_call`, the doc comments on the corresponding intent types state the design explicitly: *"NOTE: the `wNEAR` will not be refunded in case of fail"* [1](#0-0) . Unlike `ft_withdraw`/`nft_withdraw`/`mt_withdraw`, which have `*_resolve_withdraw` callbacks that credit back unused amounts on partial/failed transfer completion (e.g. `mt_resolve_withdraw` re-deposits unsent amounts) [2](#0-1) , `native_withdraw` and `storage_deposit` intentionally have no such resolver — `do_native_withdraw` simply panics (reverting only that receipt) if `near_withdraw` failed, with no re-credit path [3](#0-2) .

Tracing the actual mechanics: `internal_sub_balance` debits the signer's wNEAR ledger balance synchronously and atomically per intent within the same receipt [4](#0-3) . This is a real, permanent debit — the wNEAR is genuinely converted via `near_withdraw` into native NEAR held by the Verifier contract's own account before the outbound `transfer()` is attempted [5](#0-4) . If the final `Promise::new(receiver_id).transfer(...)` to a "doomed" receiver fails, the NEAR does not vanish from total protocol holdings — it remains parked in the Verifier contract's own NEAR balance, simply unreachable by the original signer since no refund credit exists. There is no case where NEAR "never left/arrived" while double-counted elsewhere: the debit is real, singular, and matches an actual (if user-unfavorable) conversion.

Critically, this only affects the signer's own funds: the attacker chooses their own `receiver_id` for `NativeWithdraw`, so any loss from an unrefunded failed transfer is self-inflicted, not value extracted from other users or the Verifier's solvency. Batching an independent `StorageDeposit` succeeding in the same `MultiPayload` does not couple the two debits into any "matched pair" requiring net-zero settlement — each is an independent authorized withdrawal by the same signer of their own balance. No other party's balance is affected, no signature is bypassed, no intent replays, and total NEAR custodied by the contract is never less than what it owes across all accounts (the unrefunded NEAR sits in the contract's own account, if anything *increasing* the surplus, not creating a deficit).

Since this is (a) explicitly documented as accepted behavior in the source, (b) does not move value out of the Verifier belonging to another signer, and (c) does not create an under-collateralization (the NEAR remains held by the contract, just non-refunded to the ledger), it does not meet the Critical/High impact bar defined in the rules (no unauthorized fund movement, no batch imbalance where the Verifier owes more than it custodies, and no other party's funds are at risk).

impl MultiTokenWithdrawResolver for Contract {
    #[private]
    fn mt_resolve_withdraw(
        &mut self,
        token: AccountId,
        sender_id: AccountId,
        token_ids: Vec<defuse_nep245::TokenId>,
        amounts: Vec<U128>,
        is_call: bool,
    ) -> Vec<U128> {
        require!(
            token_ids.len() == amounts.len() && !amounts.is_empty(),
            "invalid args"
        );

        let mut used = if is_call {
            // `mt_batch_transfer_call` returns successfully transferred amounts
            match promise_result_checked_json_with_len::<Vec<U128>>(0, amounts.len()) {
                Ok(Ok(used)) if used.len() == amounts.len() => used,
                Ok(_) => vec![U128(0); amounts.len()],
                // do not refund on failed `mt_batch_transfer_call` due to
                // NEP-141 vulnerability: `mt_resolve_transfer` fails to
                // read result of `mt_on_transfer` due to insufficient gas
                Err(_) => amounts.clone(),
            }
        } else {
            // `mt_batch_transfer` returns empty result on success
            if promise_result_checked_void(0).is_ok() {
                amounts.clone()
            } else {
                vec![U128(0); amounts.len()]
            }
        };

        self.deposit(
            sender_id,
            token_ids
                .into_iter()
                .zip(amounts)
                .zip(&mut used)
                .filter_map(|((token_id, amount), used)| {
                    // update min during iteration
                    used.0 = used.0.min(amount.0);
                    let refund = amount.0.saturating_sub(used.0);
                    if refund > 0 {
                        Some((Nep245TokenId::new(token.clone(), token_id).into(), refund))
                    } else {
                        None
                    }
                }),
            Some(REFUND_MEMO),
        )
        .unwrap_or_else(|err| err.panic());

    fn internal_sub_balance(
        &mut self,
        owner_id: &AccountIdRef,
        tokens: impl IntoIterator<Item = (TokenId, u128)>,
    ) -> Result<()> {
        let owner = self
            .accounts
            .get_mut(owner_id)
            .ok_or_else(|| DefuseError::AccountNotFound(owner_id.to_owned()))?
            .get_mut()
            .ok_or_else(|| DefuseError::AccountLocked(owner_id.to_owned()))?;

        for (token_id, amount) in tokens {
            if amount == 0 {
                return Err(DefuseError::InvalidIntent);
            }

            owner
                .token_balances
                .sub(token_id.clone(), amount)
                .ok_or(DefuseError::BalanceOverflow)?;
        }

        Ok(())
    }
