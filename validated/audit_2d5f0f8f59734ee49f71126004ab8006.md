### Title
Uncaught precompile exception in `ValidateMultiSign` allows a crafted low-level `CALL` to force an entire transaction/call frame to revert instead of returning a graceful failure — ([File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java])

### Summary
The `ValidateMultiSign` precompiled contract decodes attacker-controlled `bytes` calldata directly (`DataWord.parseArray`, indexing `words[0..4]`, `extractBytesArray`) with **no outer try/catch** around the decode path. Unlike its sibling `BatchValidateSign`, which wraps the whole body in `try { return doExecute(data); } catch (Throwable t) { return Pair.of(true, new byte[WORD_SIZE]); }`, `ValidateMultiSign.execute()` only wraps the *permission-weight* computation in a try/catch — the initial parsing of `rawData` into `DataWord[] words` and the subsequent array indexing is unguarded. When `VMConfig.allowTvmOsaka()` (TIP-854) is not yet activated, the shape-validation guard `isValidAbiEncoding` is skipped entirely, so malformed/too-short calldata throws an uncaught `RuntimeException` (e.g. `ArrayIndexOutOfBoundsException`) straight out of `execute()`.

### Finding Description
`Program.callToPrecompiledAddress()` invokes the precompile directly with no try/catch of its own: [1](#0-0) 

`ValidateMultiSign.execute()` parses the raw calldata before any exception boundary exists: [2](#0-1) 

Only the inner permission-lookup/signature-recovery loop is defended: [3](#0-2) 

Contrast with `BatchValidateSign`, which explicitly wraps its *entire* body (including the decode step) in a catch-all, exactly the defensive pattern the external report recommends for `getUSDPrice`: [4](#0-3) 

The repository's own test suite documents this asymmetry as the "pre-activation legacy behaviour": before TIP-854/Osaka activation, malformed calldata to `ValidateMultiSign` "raises inside the decoder" and "this precompile has no outer catch": [5](#0-4) 

And the outer-frame containment test proves that, when the CALL to this precompile fails via exception (rather than a controlled `Pair.of(false, ...)`), the caller's stack does **not** simply receive a `0` — the exception instead escapes and aborts the outer frame; the TIP-854 fix (`allowTvmOsaka`) is what makes the outer frame safely continue: [6](#0-5) 

This mirrors the reported bug class precisely: an external/oracle-like dependency (`ValidateMultiSign` acting as a "trusted" signature-verification oracle for calling contracts, e.g. multisig wallets) is called without a defensive try/catch, so instead of returning a benign `false` on bad input, the entire calling transaction/contract call reverts unexpectedly.

### Impact Explanation
Any TRON smart contract that performs a low-level `CALL`/`STATICCALL` to the `validateMultiSign` precompile address (e.g. wallet/proxy/multisig contracts forwarding externally-supplied signature bytes for verification) can be forced into an uncontrolled revert of the entire outer transaction by an unprivileged party supplying malformed calldata, whenever `allowTvmOsaka` is not active on the network. Contracts written assuming "low-level call never throws, only returns false" (the idiom explicitly tested in `EnergyWhenRequireStyleTest`) will misbehave: their own revert-handling logic is bypassed and the whole transaction (and all its side effects) aborts with full energy consumption, instead of the intended graceful-failure path. This is a availability/DoS impact against any contract depending on the precompile's graceful-failure contract, reachable by any unprivileged transaction broadcaster who can trigger a contract call that forwards attacker data to this precompile.

### Likelihood Explanation
Reachable directly from an ordinary `TriggerSmartContract` transaction — no special privilege needed. The only precondition is that `VMConfig.allowTvmOsaka()` is not enabled (i.e., the TIP-854/Osaka hard fork has not been activated on the target network/chain state) — the test suite explicitly frames this as "pre-activation" behavior, implying it is a real, currently-reachable state on any chain where the fork has not yet switched on. Given `BatchValidateSign` already received the defensive fix and `ValidateMultiSign` did not, this looks like an incomplete/inconsistent application of the TIP-854 hardening across the two related precompiles.

### Recommendation
Apply the same catch-all pattern used in `BatchValidateSign.execute()` to `ValidateMultiSign.execute()`: wrap the entire body (including calldata parsing/decoding, not just the permission-weight loop) in a top-level `try { ... } catch (Throwable t) { return Pair.of(true/false, EMPTY_or_DATA_FALSE); }`, mirroring the report's recommendation to guard external/untrusted-data-dependent calls so a single malformed input cannot escalate into an uncontrolled revert of the entire call frame, independent of `allowTvmOsaka` activation state.

### Proof of Concept
1. On a node/network where `VMConfig.allowTvmOsaka()` is disabled (pre-TIP-854), deploy or use any contract that performs `address(VALIDATE_MULTISIGN_PRECOMPILE).call(shortMalformedBytes)`.
2. Send a `TriggerSmartContract` transaction invoking that contract with calldata shorter than the required 5-word ABI header (as reproduced in `ValidateMultiSignContractTest.testTip854PreActivationNoOp`, which executes `contract.execute(new byte[(5 + 1) * 32])` and shows the decoder "may throw" in this configuration): [7](#0-6) 
3. The uncaught exception propagates out of `contract.execute(data)` in `Program.callToPrecompiledAddress`, escaping the outer call frame rather than pushing `0`, aborting the whole transaction/contract call rather than allowing the calling contract's own revert-handling to run.

Note: I was unable to fully trace `DataWord.parseArray`'s exact exception type/behavior for under-length input within the available index (only its signature was located), so the precise Java exception class thrown could not be independently confirmed beyond what the test comments describe ("decoder may throw" / "RuntimeException"). This should be verified directly in `common/src/main/java/org/tron/common/runtime/vm/DataWord.java` before remediation.
