### Title
Unauthenticated POST to `/v3/blocks/upload/` triggers unconditional P2P relay of the block, bypassing the `broadcast`/`authenticated` gate - (File: `stackslib/src/net/api/postblock_v3.rs`)

### Summary
`RPCPostBlockRequestHandler::try_parse_request` only rejects a request with `Error::Http(401, ...)` when `broadcast=1` is requested without authentication; if `broadcast` is omitted (default `false`), no auth is required at all. `try_handle_request` then relays the block to the P2P network via `node.set_relay_message(StacksMessageType::NakamotoBlocks(...))` purely based on whether `Relayer::process_new_nakamoto_block_ext` returned `accepted == true`, completely ignoring `self.broadcast`/`authenticated`.

### Finding Description
The intended invariant is: *a block is relayed to the P2P network only if the caller supplied the correct secret AND explicitly requested `broadcast=1`*. The code as written enforces a different, weaker invariant: *a block is relayed if it is accepted by the chainstate*, independent of authentication or the `broadcast` flag.

Concretely, in `try_parse_request` (`stackslib/src/net/api/postblock_v3.rs:99-122`):
```rust
let mut broadcast = false;
let mut authenticated = false;
// authenticated set true only if auth header matches password
...
if broadcast && !authenticated {
    return Err(Error::Http(401, "Unauthorized".into()));
}
``` [1](#0-0) 

When an attacker omits both the `authorization` header and the `broadcast` query arg, `broadcast` stays `false`, so the `broadcast && !authenticated` check is never triggered, and the request passes with `authenticated == false`. `self.broadcast` is then stored as `Some(false)`.

In `try_handle_request` (`stackslib/src/net/api/postblock_v3.rs:159-202`), `self.broadcast.unwrap_or(false)` (i.e. `false`) is passed into `Relayer::process_new_nakamoto_block_ext` merely as a parameter to that function - it does not gate the subsequent relay call. After computing `data_resp.accepted`, the handler does:
```rust
if data_resp.accepted {
    node.set_relay_message(StacksMessageType::NakamotoBlocks(NakamotoBlocksData {
        blocks: vec![block],
    }));
}
``` [2](#0-1) 

This relay call is unconditional with respect to `self.broadcast` and `authenticated` - it only checks `data_resp.accepted`. Since `data_resp.accepted` is determined by chainstate acceptance of the block (not by any authorization decision), any unauthenticated caller who submits a block that the tip accepts causes the node to gossip that block to its P2P peers via `set_relay_message`, exactly as if they had passed a correct secret with `broadcast=1`.

The existing 401 guard at line 120 only prevents the narrow case of `broadcast=1` without auth; it does nothing to prevent the relay path, because the relay decision in `try_handle_request` was never wired to `broadcast`/`authenticated` at all - it only checks acceptance.

### Impact Explanation
Any unprivileged remote attacker who can reach the RPC port of a node configured with `self.auth = Some(password)` (i.e., the operator intentionally locked down block uploads/broadcast) can submit a valid, tip-accepted Nakamoto block without any credentials and force that node to relay/gossip the block to the wider P2P network. This is unauthenticated/unauthorized network-wide propagation of data through a node whose owner explicitly configured it to require a secret for broadcasting, matching the Critical impact category ("network-wide propagation of forged data" / "unauthenticated write/relay"). The attack is repeatable for every valid block the attacker can construct or replay.

### Likelihood Explanation
Preconditions: the target node must be configured with `self.auth = Some(password)` (attacker doesn't need to know it), have a reachable RPC port, and be at a tip that will accept the submitted block (e.g., a legitimately valid block the attacker obtained elsewhere, or one they are otherwise entitled to submit as a miner/signer but not entitled to force-broadcast). No privileged role, secret, or special network position is required by the attacker - just the ability to POST bytes to `/v3/blocks/upload/`. This is a single HTTP request with no cost beyond constructing/obtaining a valid block, making it trivially repeatable.

### Recommendation
Gate the `set_relay_message` call in `try_handle_request` on `self.broadcast.unwrap_or(false)` (which is already enforced to require `authenticated` when true), e.g.:
```rust
if data_resp.accepted && self.broadcast.unwrap_or(false) {
    node.set_relay_message(...);
}
```
This restores the intended invariant that relay only happens when the caller was authenticated and explicitly requested broadcast.

### Proof of Concept
Add a test in `stackslib/src/net/api/tests/postblock_v3.rs`:
1. Construct an `RPCPostBlockRequestHandler` with `auth = Some("secret".into())`.
2. Build an `HttpRequestPreamble` for `POST /v3/blocks/upload/` with no `authorization` header and no `broadcast` query string, and a body containing a validly-serialized `NakamotoBlock` that the test chainstate/tip will accept.
3. Call `try_parse_request` and assert it returns `Ok(..)` (not a 401) with `self.broadcast == Some(false)`.
4. Call `try_handle_request` against a `StacksNodeState` wired to a mock/stub `Relayer::process_new_nakamoto_block_ext` (or a real chainstate fixture) that returns `accepted == true`.
5. Assert that `node.set_relay_message` was invoked with `StacksMessageType::NakamotoBlocks` containing the block, despite `authenticated == false` and `broadcast == false` - demonstrating the auth/broadcast bypass.
