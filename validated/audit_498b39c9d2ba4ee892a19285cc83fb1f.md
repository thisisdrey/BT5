This confirms the pattern: `initialize()` in the vault contracts has no caller/DAO-auth check — it only asserts `(not (var-get initialized))` before setting `initialized true` and depositing `MINIMUM-LIQUIDITY`. The DAO proposal (`local-testing/contracts/proposals/proposal-init-vaults.clar`, mirrored on mainnet by the deployed init proposal) calls `initialize` on every vault as one step inside a larger atomic `try!` chain executed via `dao-executor.execute-proposal`.

### Title
Unauthenticated vault `initialize()` allows front-running that reverts and blocks the atomic DAO protocol-initialization proposal - (mainnet/contracts/vault/v0-vault-sbtc.clar, v0-vault-usdh.clar, v0-vault-usdc.clar, v0-vault-ststx.clar, v0-vault-stx.clar, v0-vault-ststxbtc.clar)

### Summary
`initialize()` in every vault contract is a public function guarded only by a one-time flag, with no `check-dao-auth` or caller restriction: `(asserts! (not (var-get initialized)) ERR-ALREADY-INITIALIZED) (var-set initialized true) (try! (deposit MINIMUM-LIQUIDITY u0 NULL-ADDRESS))` [1](#0-0) . Any ordinary principal can call it before the DAO does.

### Finding Description
The vault contracts (`v0-vault-sbtc.clar`, `v0-vault-usdh.clar`, `v0-vault-usdc.clar`, and their siblings) expose `initialize` as a public function protected solely by the `initialized` data-var guard, unlike every other privileged setter in the same file which calls `(try! (check-dao-auth))` first (e.g. `set-cap-supply`, `set-authorized-contract`) [2](#0-1) . Since `initialize` lacks that check, this is functionally the same class of bug as the external report's "init function frontrun": the intended flow is that a privileged actor (the DAO) initializes the vault as part of a scripted setup, but any unprivileged principal can call it first.

The vault's own `deposit` requires `(asserts! (var-get initialized) ERR-INIT)` [3](#0-2) , so `initialize` is the sole gate that flips the vault from "not usable" to "usable," and it also performs the one-time `MINIMUM-LIQUIDITY` mint to `NULL-ADDRESS` that seeds share-price math (`convert-to-shares-preview`/`convert-to-assets-preview`) [4](#0-3) .

Crucially, the DAO's own bootstrap proposal calls `initialize` on all vaults back-to-back inside one atomic `try!` chain: `(try! (contract-call? .vault-sbtc initialize)) (try! (contract-call? .vault-usdh initialize)) (try! (contract-call? .vault-usdc initialize)) ...` [5](#0-4) . Because `initialize` reverts with `ERR-ALREADY-INITIALIZED` if already initialized, an attacker who front-runs even one vault's `initialize` call (by monitoring the mempool/chain for the DAO's setup transaction, or simply calling it themselves as soon as the vault is deployed but before the DAO executes its proposal) causes that single `contract-call?` to fail, which via `try!` aborts the entire proposal transaction. This blocks the whole multi-step DAO initialization script (asset registration, cap-setting, market authorization, egroup creation elsewhere in the flow) from ever completing, since it is designed to run as one atomic unit.

### Impact Explanation
This lands on **temporary freezing of funds**: the vault (and thus the market that depends on it) cannot be brought online while the DAO must redeploy/re-script initialization around the front-run vault, delaying the point at which any user can deposit/borrow. It does not enable direct fund theft, since `deposit` pulls `MINIMUM-LIQUIDITY` from the *caller* themselves and mints the resulting shares to `NULL-ADDRESS`, not to the attacker — the attacker gains no ownership or funds from calling `initialize` early, unlike the StarBase `_PROXY_`-hijack scenario in the external report. The impact is limited to griefing the atomic setup transaction and delaying protocol launch/vault availability.

### Likelihood Explanation
High likelihood if vaults are deployed before the DAO's initialization proposal transaction is broadcast and confirmed, since `initialize` is a plain public call requiring no special permission, only a mempool-visible transaction against a known contract address, mirroring the exact bug class from the report ("attacker could monitor the blockchain for bytecode that matches... and front-run the init() transaction").

### Recommendation
Restrict `initialize()` in every vault (`v0-vault-sbtc.clar`, `v0-vault-usdh.clar`, `v0-vault-usdc.clar`, `v0-vault-ststx.clar`, `v0-vault-stx.clar`, `v0-vault-ststxbtc.clar`) with the same `(try! (check-dao-auth))` gate used by `set-cap-supply`/`set-authorized-contract`, or otherwise ensure deployment and initialization occur atomically in the deploying transaction, consistent with how `dao-executor.init` and `dao-multisig.init` correctly gate on `DEPLOYER`/`tx-sender` [6](#0-5) .

### Proof of Concept
1. Vault contracts are deployed to mainnet (public, uninitialized state `initialized = false`).
2. Before the DAO submits/confirms its `v0-init`/`proposal-init-vaults`-style bootstrap transaction, an attacker submits a plain call to `(contract-call? .v0-vault-sbtc initialize)` from their own principal.
3. This succeeds (`initialized` was `false`), setting `initialized = true` and minting `MINIMUM-LIQUIDITY` shares to `NULL-ADDRESS` funded from the attacker's own `sbtc-token` balance.
4. The DAO's proposal transaction now executes `(try! (contract-call? .v0-vault-sbtc initialize))` as one step among many chained `try!` calls; this call now returns `ERR-ALREADY-INITIALIZED`, and the `try!` causes the entire proposal transaction to abort, so no other step in that same transaction (asset registration, other vault initializations, cap-setting, market authorization) takes effect.
5. The DAO must detect the failure and re-script/redeploy its initialization flow around the already-initialized vault, delaying protocol launch — a temporary freeze of the vault/market functionality for all users.
