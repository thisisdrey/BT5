### Title
`liquidate-multi` batch liquidation can be fully reverted by a single non-liquidatable/edge-case position, blocking liquidation of all other insolvent positions - (File: `mainnet/contracts/market/v0-4-market.clar` / `local-testing/contracts/market/market.clar`)

### Summary
`liquidate-multi` is explicitly documented as designed to avoid the exact bug class described in the M-17 report: "Prevents front-running attacks that prevent bad debt socialization... Failed liquidations return error codes but don't revert entire batch." [1](#0-0) . However, the implementation relies on `map call-liquidate positions`, and the underlying `liquidate`/`socialize-debt-asset` call chain contains multiple `unwrap-panic` calls that are NOT recoverable `(err ...)` responses but hard runtime aborts, which propagate up and abort the *entire* enclosing transaction rather than just the failing element of the `map`.

### Finding Description
`liquidate-multi` maps `call-liquidate` over a caller-supplied list of up to 64 positions, each potentially belonging to a different borrower: [2](#0-1) [3](#0-2) .

`call-liquidate` in turn invokes the private `liquidate` function with `price-feeds` set to `none` — batch liquidation explicitly does not support submitting fresh price feeds per position ("price-feeds not supported in batch - update prices separately or use individual liquidate()"). This means every position in the batch is liquidated using only whatever price/index state is already resolvable at the time.

Deep in this call chain there are several `unwrap-panic` calls operating on data that depends on the specific borrower's position and asset state, e.g.:
- `remove-if-match`, used by `filter-out-debt-asset` during bad-debt socialization: [4](#0-3) 
- The bad-debt socialization append during liquidation cleanup: [5](#0-4) 
- `process-debt-asset` (`unwrap-panic (find-asset debt-aid assets)`) and `process-collateral-asset` (`unwrap-panic (price-resolve oracle-data)` for disabled collateral): [6](#0-5) [7](#0-6) 
- `scale-debt-for-liquidation` (`unwrap-panic (get-cached-indexes asset-id)`): [8](#0-7) 
- `get-assets`'s price resolution (`unwrap-panic (price-multi-resolve oracles-list asset-ids)`): [9](#0-8) 

Unlike `(err ...)` responses produced via `try!`/`asserts!`, which `call-liquidate` returns as a normal `(response ...)` value that `map` collects without aborting the transaction, a Clarity `unwrap-panic` failure is a **runtime abort**. When it occurs anywhere in the call graph rooted at `map call-liquidate positions`, it aborts the whole top-level `liquidate-multi` transaction — it is not caught or isolated per-element by `map`, contradicting the function's own documented "atomic-per-element, not atomic-per-batch" design intent.

An ordinary borrower — an unprivileged principal with their own position — can arrange for their own position to be in a state that triggers one of these `unwrap-panic` paths when included as one of the 64 entries in someone else's `liquidate-multi` call (e.g., an asset that a disabled-collateral price resolution cannot resolve, or an edge-case bad-debt socialization append that hits a hard failure). Because a rational liquidator/bot batches multiple simultaneously-liquidatable positions together for gas efficiency, one attacker-crafted position mixed into that batch is sufficient to abort processing of every other (genuinely insolvent, unrelated) position included in the same call.

### Impact Explanation
This is a direct analog of the M-17 "malicious pool owner blocks tax withdrawal" bug: a single caller-influenced entry in a shared/batched loop, that is documented to be fault-isolated but is not in practice, causes the entire operation to revert and blocks the legitimate operation for **other, unrelated users' positions** included in the same call. Here the consequence is delayed/blocked liquidation of otherwise-liquidatable borrower positions, which is a temporary freezing of protocol funds (undercollateralized debt cannot be liquidated/socialized in time), and increases the risk of protocol insolvency if the delay is exploited repeatedly to keep bad debt unresolved during adverse price movements. This lands on the in-scope **High — temporary freezing of funds** impact category (and, at increased likelihood/scale, contributes to protocol-insolvency risk).

### Likelihood Explanation
Likelihood is Medium: it requires (a) a liquidator to batch multiple positions together (an expected/incentivized usage pattern given the function exists specifically for gas efficiency), and (b) an attacker to have at least one position among those batched that triggers one of the `unwrap-panic` failure paths (e.g., through disabled-collateral edge cases or asset-list edge cases reachable purely through the attacker's own borrowing/collateral choices, without needing DAO or oracle compromise). Since `liquidate-multi` explicitly disallows submitting price feeds per batch, any position whose necessary price/index data is not already resolvable via the existing panic-based helpers is a candidate trigger, making this more reachable than a typical contrived edge case.

### Recommendation
Wrap each `call-liquidate` invocation's execution in a way that isolates panics per element — e.g., replace all `unwrap-panic` calls in the reachable code path from `liquidate`/`socialize-debt-asset`/`process-debt-asset`/`process-collateral-asset`/`scale-debt-for-liquidation`/`get-assets` with `try!`/`asserts!` propagating explicit `(err ...)` values so that `call-liquidate` can genuinely return an error response instead of aborting the whole transaction, fulfilling the batch function's documented guarantee. Alternatively, since Clarity offers no in-language try/catch around panics from within the same execution context, consider requiring `liquidate-multi` to invoke each liquidation via a genuine external `contract-call?` boundary (e.g., to a dedicated liquidation-executor contract) so that a panic in one call does not abort the outer transaction, or add explicit precondition checks (asset resolvability, price cache freshness, and bad-debt list capacity) before attempting each position's liquidation so panics cannot occur mid-batch.

### Proof of Concept
1. Attacker opens a borrow position designed so that, at some future point, either (a) their collateral becomes "disabled" and the fallback price resolution branch in `process-collateral-asset` panics (`unwrap-panic (price-resolve oracle-data)`), or (b) their debt-asset list state causes the bad-debt-socialization append path (`unwrap-panic (as-max-len? (append ...) u64)`) to fail during full-liquidation cleanup, or (c) their position references a debt/collateral asset id not present in the batch's pre-resolved `assets` list causing `process-debt-asset`'s `unwrap-panic (find-asset debt-aid assets)` to fail.
2. A liquidator bot, scanning for liquidatable positions, includes the attacker's position along with several other genuinely liquidatable borrowers' positions in a single `liquidate-multi` call (this is the expected/intended usage pattern for the function, since it exists purely for gas-efficient batch liquidation).
3. When `map call-liquidate positions` reaches the attacker's crafted position, the `unwrap-panic` failure aborts the whole transaction.
4. None of the other borrowers in that batch get liquidated in that transaction, despite being genuinely insolvent — the liquidator must detect the failure and retry individually per-position, and during that window bad debt for the other borrowers remains unresolved (temporary freezing of funds / delayed loss socialization), exactly mirroring the M-17 pattern where one bad entry blocks legitimate processing of all others sharing the same loop.

*Note: I was unable to fully confirm, from the indexed code alone, the precise concrete sequence of state transitions (e.g., how "disabled collateral" status is reached, or the exact conditions under which the bad-debt-socialization append can exceed the 64-entry cap) that trigger each specific `unwrap-panic`, since some surrounding logic (asset registry rules for enabling/disabling collateral) was outside the indexed excerpts. A Devin session with full repository access would be needed to construct and validate an exact reproducible test case.*

;; Prevents front-running attacks that prevent bad debt socialization
