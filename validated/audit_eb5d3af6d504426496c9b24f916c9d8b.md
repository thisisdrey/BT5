### Title
Unvalidated COFF symbol `SectionNumber` causes index-out-of-range panic in the PE object loader - ([File: src/cmd/link/internal/loadpe/ldpe.go])

### Summary
When the Go linker loads a Windows COFF/PE object file (e.g. a `.syso` file bundled in a Go module, or a host object produced during cgo linking), it reads relocation entries and resolves the referenced `pe.COFFSymbol` via `readpesym`. If that symbol looks like a "section symbol" (`StorageClass == IMAGE_SYM_CLASS_STATIC`, `Type == 0`, name starting with `.`), the loader indexes `f.Sections` using `pesym.SectionNumber-1` without ever validating that `SectionNumber` is within `[1, len(f.Sections)]`. A crafted object file with such a symbol and an out-of-range `SectionNumber` (0, negative, or too large) causes an out-of-range slice access panic in the linker, mirroring the unvalidated-index defect (`coff_pointerize_aux`) described in CVE-2018-7208 for `libbfd`.

### Finding Description
Attacker input is a crafted COFF/PE object file (e.g. a malicious `.syso` file shipped inside a Go module, or a host object consumed by the linker's PE loader). It enters via `loadpe.Load` in [1](#0-0) , which parses the file with `debug/pe.NewFile` — a parser that reads raw `COFFSymbol.SectionNumber` values with no range checking, as seen in `readCOFFSymbols`/`FullName` in [2](#0-1) .

During relocation processing, the loader looks up the target symbol purely by the relocation's `SymbolTableIndex` bound (checked against `len(f.COFFSymbols)`) and immediately calls `readpesym` on it, with no validation of that symbol's `SectionNumber`: [3](#0-2) 

Inside `readpesym`, if the symbol satisfies `issect(pesym)` (`StorageClass == IMAGE_SYM_CLASS_STATIC && Type == 0 && Name[0] == '.'`), the code directly indexes `state.f.Sections[pesym.SectionNumber-1]` with the raw, attacker-controlled `SectionNumber`: [4](#0-3) 

There is no check here (unlike the later "enter sub-symbols" loop, which does validate `pesym.SectionNumber` against `len(f.Sections)` before calling `readpesym`, see [5](#0-4) ). A relocation whose target symbol is a fake "section" symbol with `SectionNumber == 0`, negative, or larger than the actual number of sections drives `pesym.SectionNumber-1` to `-1` or an out-of-bounds positive index into `f.Sections`, causing a runtime slice-index panic.

### Impact Explanation
This is a linker-side denial of service: a crafted COFF object embedded in an otherwise ordinary Go module/package (most plausibly a `.syso` file, which the Go toolchain links in verbatim without compiling from source) can crash `go build`/`go link` with an unrecoverable panic when a victim builds the module. This matches the CVE-2018-7208 primitive (index derived from untrusted binary object-file data used without bounds validation, leading to a crash) but manifests in Go's own PE/COFF object loader rather than in `libbfd`. Per Go's security triage, a reproducible parser panic on malicious input in a real build path qualifies as a legitimate (likely PUBLIC-track) issue, distinct from generic resource exhaustion.

### Likelihood Explanation
The victim workflow is simply running `go build`/`go install` on a module that contains (or vendors) an attacker-supplied `.syso`/COFF object file — no special privileges, network position, or unusual toolchain flags are required beyond normal cgo/Windows-target linking. The attacker only needs to control the bytes of one object file consumed by the module, which is a realistic "malicious module" supply-chain scenario.

### Recommendation
Validate `pesym.SectionNumber` in `readpesym` (and any other unguarded call sites) before using it to index `state.f.Sections`, e.g. bail out with an error such as `"%s: invalid section number %d"` when `SectionNumber <= 0 || int(SectionNumber) > len(state.f.Sections)`, mirroring the check already applied later in the "enter sub-symbols" loop at [5](#0-4) .

func readCOFFSymbols(fh *FileHeader, r io.ReadSeeker) ([]COFFSymbol, error) {
	if fh.PointerToSymbolTable == 0 {
		return nil, nil
	}
	if fh.NumberOfSymbols <= 0 {
		return nil, nil
	}
	_, err := r.Seek(int64(fh.PointerToSymbolTable), io.SeekStart)
	if err != nil {
		return nil, fmt.Errorf("fail to seek to symbol table: %v", err)
	}
	c := saferio.SliceCap[COFFSymbol](uint64(fh.NumberOfSymbols))
	if c < 0 {
		return nil, errors.New("too many symbols; file may be corrupt")
	}
	syms := make([]COFFSymbol, 0, c)
	naux := 0
	for k := uint32(0); k < fh.NumberOfSymbols; k++ {
		var sym COFFSymbol
		if naux == 0 {
			// Read a primary symbol.
			err = binary.Read(r, binary.LittleEndian, &sym)
			if err != nil {
				return nil, fmt.Errorf("fail to read symbol table: %v", err)
			}
			// Record how many auxiliary symbols it has.
			naux = int(sym.NumberOfAuxSymbols)
		} else {
			// Read an aux symbol. At the moment we assume all
			// aux symbols are format 5 (obviously this doesn't always
			// hold; more cases will be needed below if more aux formats
			// are supported in the future).
			naux--
			aux := (*COFFSymbolAuxFormat5)(unsafe.Pointer(&sym))
			err = binary.Read(r, binary.LittleEndian, aux)
			if err != nil {
				return nil, fmt.Errorf("fail to read symbol table: %v", err)
			}
		}
		syms = append(syms, sym)
	}
	if naux != 0 {
		return nil, fmt.Errorf("fail to read symbol table: %d aux symbols unread", naux)
	}
	return syms, nil
}
