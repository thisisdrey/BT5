### Title
Missing compute-usage accounting in `add_gas_key` enables uncompensated O(num_nonces) trie writes vs. metered `delete_gas_key` - ([File: runtime/runtime/src/access_keys.rs])

### Summary
`add_gas_key` writes up to `MAX_NONCES_FOR_GAS_KEY` (1024) gas-key-nonce trie entries via `set_gas_key_nonce` in a loop but never calls `safe_add_compute`/records any `result.compute_usage`, unlike its counterpart `delete_gas_key`, which explicitly meters the symmetric removal loop with `storage_removes_compute` + `safe_add_compute`. The exec/send fees for adding a gas key (`gas_key_add_key_exec_fee`/`gas_key_add_key_send_fee`) are flat and not scaled by `num_nonces`, so the compute cost of the write loop is entirely unaccounted for.

### Finding Description
In `runtime/runtime/src/access_keys.rs`, `add_gas_key` (lines 194-228) performs: [1](#0-0) 
for `num_nonces` up to `GasKeyInfo`/`AccessKeyPermission::MAX_NONCES_FOR_GAS_KEY`, with zero calls to `safe_add_compute` or any compute-tracking helper anywhere in the function.

By contrast, `delete_gas_key` performs the symmetric removal loop and explicitly charges compute for it: [2](#0-1) 

The exec fee applied on the add path, `permission_exec_fees`, calls `gas_key_add_key_exec_fee(fees, sender_is_receiver)` / the exec-side equivalent with no `num_nonces` parameter, i.e., it is a flat, fixed cost regardless of whether `num_nonces` is 1 or 1024: [3](#0-2) [4](#0-3) 

An unprivileged, funded account can submit a single `AddKeyAction` with `AccessKeyPermission::GasKeyFullAccess(GasKeyInfo{num_nonces: 1024, ..})` targeting a public key with no existing access key. `action_add_key` (lines 149-192) routes it to `add_gas_key` because `add_key.access_key.gas_key_info()` is `Some`: [5](#0-4) 
This performs 1024 trie writes while incrementing `result.compute_usage` by 0, whereas deleting the same key would charge `nonce_remove_compute` for the equivalent 1024 trie removals. No existing check (signature, nonce, access-key permission, or gas fee) closes this gap, since the flat `gas_key_add_key_exec_fee` gas charge is unrelated to the chunk's compute budget accounting, which is meant to be enforced independently of gas price/gas burnt.

### Impact Explanation
This is a metering-totality violation on the write path of gas-key creation: the chunk-level compute budget (a resource-consumption/DoS control distinct from gas accounting) is not charged for up to 1024 real trie writes per `AddKeyAction`, while the symmetric delete path is properly charged. An attacker can chain many such `AddKeyAction`s (each on a distinct, cheaply-fundable/implicit account or distinct new public key) across receipts in a chunk to perform large amounts of uncompensated trie-write work without it counting against the chunk compute budget, which is the mechanism meant to bound per-chunk real execution time regardless of how gas is paid. This falls under a chunk-processing resource-exhaustion / compute-budget-bypass class of issue rather than direct fund theft, token inflation, or state-root divergence.

### Likelihood Explanation
Preconditions are minimal: a funded account, an ordinary signed transaction, and a single `AddKeyAction` with `GasKeyFullAccess(num_nonces=1024)` targeting an unused public key — fully within unprivileged capability (no validator/node access needed). The attacker pays only the flat `gas_key_add_key_exec_fee`/`add_full_access_key` gas fees, not a compute charge proportional to `num_nonces`, making the attack cheap and trivially repeatable across many keys/accounts.

### Recommendation
In `add_gas_key`, compute the analogous `storage_writes_compute`-style cost for the `num_nonces` `set_gas_key_nonce` writes (mirroring `storage_removes_compute` used in `delete_gas_key`) and add it to `result.compute_usage` via `safe_add_compute`, ensuring the write path is metered symmetrically with the delete path. Also thread `result: &mut ActionResult` into `add_gas_key`'s signature (currently absent) so the compute usage can be recorded, and confirm `gas_key_add_key_exec_fee` intentionally accounts for the base-fee-only assumption or is likewise scaled if the fee model requires it.

### Proof of Concept
Unit test in `runtime/runtime/src/access_keys.rs` tests module:
1. Call `add_gas_key_to_account` (or `action_add_key`) with `AccessKey::gas_key_full_access(1024)` and assert on the returned `ActionResult` that `result.compute_usage == 0` (currently true because `add_gas_key` never touches it and the caller `action_add_key` doesn't pass a mutable `ActionResult` into `add_gas_key`).
2. In a parallel test, add the same gas key then delete it via `action_delete_key`, capturing `result.compute_usage`, and compute `expected_nonce_remove_compute(&account_id, &public_key, 1024)` using the existing test helper (lines 373-386).
3. Assert `delete_result.compute_usage == expected_nonce_remove_compute(...)` while `add_result.compute_usage == 0`, demonstrating the asymmetry described, for equivalent O(1024) trie-write workloads.
