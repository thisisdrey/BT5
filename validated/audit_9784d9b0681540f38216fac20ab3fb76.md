### Title
`all_or_nothing` batch execution lets one unprivileged transaction poison and cancel unrelated users' committed work - ([File: svm/src/transaction_processor.rs])

### Summary
The Astaria `LienToken` bug is a "forced-push" griefing pattern: an unprivileged party engineers one sub-operation to always fail, and because the surrounding logic is wired so that this single failure aborts/blocks the shared settlement for everyone else, the attacker can destroy value for other honest participants while walking away ahead. The closest reachable analog in agave lives in the banking-stage/scheduler `all_or_nothing` batch-execution path: a single transaction crafted by any unprivileged sender to reliably fail can force the runtime to retroactively discard the results of every other, unrelated transaction that was packed into the same execution batch.

### Finding Description
`TransactionBatchProcessor::load_and_execute_sanitized_transactions` iterates through a batch and, when `config.all_or_nothing` is set, treats *any* single transaction failure as a reason to roll back and mark all prior and subsequent transactions in the batch as `TransactionError::CommitCancelled`, discarding their already-computed results: [1](#0-0) 

This flag is plumbed from `ExecutionFlags::all_or_nothing` in `core/src/banking_stage/consumer.rs`, which documents exactly this behavior — "If any transaction in the batch is not committed then the entire batch should not be committed": [2](#0-1) 

`execute_and_commit_transactions_locked` forwards this flag straight into `load_and_execute_transactions`, and the batch itself is produced by `prepare_sanitized_batch_with_results`, which simply groups whatever transactions were handed to it (independent, from potentially unrelated fee payers) under one `TransactionBatch`/lock set: [3](#0-2) [4](#0-3) 

Critically, the `all_or_nothing` flag on a batch of externally-supplied transactions is not decided by the runtime/leader itself — it is a bit set by the external scheduler/packer client in `PackToWorkerMessage.flags` and merely validated for shape by `ExternalWorker::execute_batch`: [5](#0-4) 

Nothing in this path requires that the transactions batched together under one `ALL_OR_NOTHING` flag originate from the same signer, or that all included fee payers consented to being bundled atomically with an unrelated, deliberately-poisoned transaction. Any account owner can guarantee their own transaction fails deterministically (e.g., insufficient funds, `BlockhashNotFound`, an instruction that always errors) — that is unprivileged, always-available behavior, exactly analogous to a lender in the Astaria report transferring their `LienToken` to a blocklisted address to guarantee a downstream push-payment reverts. If such a transaction is combined into an `ALL_OR_NOTHING` batch alongside other unrelated, honestly-paying transactions (e.g., by a searcher/packer role that groups transactions for atomic bundling), the poison transaction's guaranteed failure causes `CommitCancelled` to be stamped on every other transaction in that batch, per the loop at `svm/src/transaction_processor.rs:632-645`, even though those other transactions executed successfully and had no relationship to the failing one.

This mirrors the Astaria bug class precisely: a single, cheaply-guaranteed failure by an unprivileged actor is used as a lever to force a shared "all-or-nothing" commit path to discard value/output belonging to other, unrelated parties (auction bids in Astaria; committed, fee-paying, successfully-executed transactions here).

### Impact Explanation
If exploited, this allows an unprivileged transaction sender to reliably force the cancellation of other, unrelated users' transactions that end up grouped into the same `all_or_nothing` batch (e.g., via a bundling/packing service), even when those other transactions executed successfully and consumed compute/fee budget. This is a QoS-evasion/griefing primitive: the attacker's transaction costs them nothing more than a normal guaranteed-fail transaction, but it can suppress inclusion of arbitrarily many honest, higher-value transactions bundled alongside it, denying those senders block space and any assurance that a successfully-executed transaction will actually land. It does not corrupt bank state (the abort path correctly avoids committing the cancelled transactions), so it is not a consensus-safety bug, but it is a legitimate DoS/fairness vector reachable by any unprivileged transaction submitter through the scheduler batching mechanism.

### Likelihood Explanation
Likelihood depends entirely on whether any component that produces `ALL_OR_NOTHING`-flagged batches (external scheduler / packer) ever groups transactions from different, non-consenting fee payers into one atomic batch (e.g., an MEV-style bundle that intentionally back-runs or sandwiches a victim's already-submitted transaction). The `ExternalWorker`/`consume_worker.rs` code shown does not itself enforce single-sender-only batches for `ALL_OR_NOTHING`; it only validates flag bit shape and count. Whether an actual deployed packer enforces such consent is outside the scope of what could be verified purely from this index (the packer/scheduler-bindings client implementation is external, per `scheduler-bindings` being out of security scope). Given that constraint, likelihood is assessed as plausible-but-unconfirmed: the runtime-side mechanism unconditionally supports the griefing pattern once such batches are formed; whether it is currently reachable end-to-end with fully unprivileged inputs could not be fully confirmed from this codebase alone.

### Recommendation
- Restrict `ALL_OR_NOTHING` semantics so that only transactions sharing the same fee payer/signer (or otherwise pre-consenting to atomic bundling) can be grouped in one `all_or_nothing` batch, enforced on the runtime side rather than trusted purely to the external packer.
- Alternatively, do not retroactively cancel already-successfully-executed, unrelated transactions on later failures within the same physical batch; instead scope "all-or-nothing" abort semantics to sub-groups explicitly marked as atomic by the transactions themselves (e.g., via a shared bundle/group id enforced by SVM), so a single unrelated failure cannot unwind unrelated senders' work.
- Add server-side (banking-stage) validation rejecting `ALL_OR_NOTHING` batches whose constituent transactions have differing fee payers unless an explicit atomic-bundle authorization is present.

### Proof of Concept
1. Have the external scheduler/packer construct a batch of N transactions and set `PackToWorkerMessage.flags` to include `execution_flags::ALL_OR_NOTHING`, where transaction 0 belongs to victim A (a normal, funded transfer) and transaction 1 belongs to attacker B, deliberately built to fail deterministically (e.g., referencing `Hash::default()` so it is `BlockhashNotFound`, or a fee payer with insufficient lamports).
2. Submit this batch through `ExternalWorker::execute_batch` (`core/src/banking_stage/consume_worker.rs:404-433`), which forwards to `Consumer::process_and_record_aged_transactions` → `execute_and_commit_transactions_locked` with `flags.all_or_nothing = true` (`core/src/banking_stage/consumer.rs:268-287`).
3. Inside `TransactionBatchProcessor::load_and_execute_sanitized_transactions`, transaction 0 executes successfully and is staged as `ProcessedTransaction::Executed`; transaction 1 fails. Because `config.all_or_nothing` is true, the loop at `svm/src/transaction_processor.rs:632-645` overwrites transaction 0's result (and any others) with `TransactionError::CommitCancelled`, discarding victim A's already-successful execution.
4. Victim A's transaction is reported back to the packer as not included (`ALL_OR_NOTHING_BATCH_FAILURE`, per `scheduling-utils/src/error.rs:96-104` and the test at `core/src/banking_stage/consume_worker.rs:1956-1990` which demonstrates exactly this "one bad transaction poisons the whole all-or-nothing batch" behavior), even though A's transaction was fully valid and executed correctly, while attacker B paid nothing beyond the cost of a normal failing transaction.

                // Abort prior transactions.
                for res in processing_results.iter_mut() {
                    *res = Err(TransactionError::CommitCancelled);
                }

                // Preserve the failure that triggered the batch to abort.
                processing_results.push(processing_result);

pub struct ExecutionFlags {
