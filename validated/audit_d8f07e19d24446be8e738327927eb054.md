### Title
EIP-712 permit domain separator binds only a static config constant, not genesis hash — fork replay of gasless approvals - (File: `substrate/frame/assets/precompiles/src/permit.rs`)

### Summary
`pallet-assets-precompiles`'s EIP-2612 `permit` implementation computes the EIP-712 domain separator's `chainId` field from `T::ChainId::get()`, a compile-time `#[pallet::constant]` baked into the runtime, rather than from any value tied to the chain's actual live identity (e.g. genesis hash or spec version). This mirrors exactly the reported bug class: a cached/immutable chain identifier used inside an EIP-712 domain separator, independent of the chain's real, forkable identity, enabling replay of signed off-chain approvals across a forked/cloned network.

### Finding Description
`compute_domain_separator` builds the EIP-712 `DOMAIN_SEPARATOR` using `DOMAIN_TYPEHASH`, token name hash, a hard-coded version hash, `T::ChainId::get()`, and `verifying_contract`: [1](#0-0) 

`T::ChainId` is declared as a `#[pallet::constant]` in the pallet `Config`: [2](#0-1) 

This value is fixed by the runtime source code, exactly like a Solidity `immutable` set once at deployment — it is never re-derived from anything that uniquely and dynamically identifies the running chain instance. Substrate's own replay-protection primitive for extrinsics, `CheckGenesis`, by contrast explicitly reads the live genesis block hash at validation time to bind signatures to a specific chain instance: [3](#0-2) 

The `permit` flow has no equivalent binding. `use_permit`/`do_verify_permit` only checks `deadline`, `owner`/`spender` non-zero, and the nonce — the digest itself is fully reproducible from `(verifying_contract, name, owner, spender, value, nonce, deadline)` plus the static `T::ChainId` constant: [4](#0-3) 

Because `T::ChainId` is a runtime-code constant rather than something cryptographically tied to the specific chain instance (its genesis hash), any Substrate chain that runs the same runtime WASM/binary and therefore configures the identical `ChainId::get()` value — e.g. a forked network, a test/staging clone of the runtime, or a future chain that copy-pastes the same EVM-style chain id constant — will compute byte-identical domain separators and therefore byte-identical permit digests for the same `(verifying_contract, owner, spender, value, nonce, deadline)` tuple. A permit signature valid on the canonical chain is therefore also valid on any forked/cloned instance, with no on-chain state (genesis hash, spec version, para ID) mixed into the signed payload to distinguish them.

### Impact Explanation
Combined with off-chain relaying of gasless approvals (the entire purpose of EIP-2612 permits is that signed messages are broadcast and later submitted by third parties), an attacker who captures a permit signed by a victim on the canonical Asset Hub can replay it verbatim against a forked or cloned deployment sharing the same `ChainId` constant, granting the same spender the same allowance there without the owner's consent on that network. If the permit approves a large/unbounded `value`, this becomes theft of approved assets on the forked chain, matching the exact risk the original report calls out ("combined with unlimited approvals, orders placed on one network could be replayed on a forked network").

### Likelihood Explanation
Exploitation requires: (1) a second chain instance running the same runtime code with the same `T::ChainId` value (a fork, a chain-spec clone, or a network that reuses the constant), and (2) an attacker capturing a previously-signed, still-unconsumed permit (nonce not yet incremented). No malicious validator, collator, relayer, or governance action is required — the only actor needed is whoever submits the previously observed permit to the second chain, which any unprivileged party can do via the public precompile call. Likelihood is moderate: it depends on chain-fork/clone scenarios rather than day-to-day mainnet operation, but this is precisely the scenario EIP-712 domain separation is designed to prevent, and the current design provides no defense against it beyond the constant itself.

### Recommendation
Do not rely solely on a static `Get<u64>` constant for the EIP-712 domain separator's chain binding. Mix in a value that is unique to the live chain instance and cannot be reproduced by copying the runtime code alone — e.g. incorporate `frame_system::Pallet::<T>::block_hash(Zero::zero())` (the genesis hash, as `CheckGenesis` does) and/or the runtime `spec_version`/`transaction_version` into the domain separator or digest, so that forked/cloned chains sharing the same runtime binary cannot reproduce valid signatures from the canonical chain.

### Proof of Concept
1. Runtime `R` configures `pallet_assets_precompiles::Config::ChainId = X` (see `substrate/frame/assets/precompiles/src/permit.rs:83-85`).
2. Alice signs an EIP-2612 permit for `(verifying_contract=A, owner=Alice, spender=Bob, value=MAX, nonce=0, deadline=T)`; the digest is `keccak256(0x1901 || domain_separator(A, name, X) || struct_hash(...))` per `permit_digest` (`permit.rs:220-238`).
3. A forked/cloned deployment `R'` runs the identical runtime code, hence also has `ChainId = X`, the same precompile address `A` for the equivalent asset, and `Nonces[A][Alice] = 0`.
4. On `R'`, anyone calls the `permit` precompile with the same `(owner, spender, value, deadline, v, r, s)`; `do_verify_permit` recomputes the identical digest (chain id `X` matches) and `ecrecover` returns Alice — `use_permit` succeeds and grants Bob the allowance on `R'` without Alice ever having authorized anything on `R'`.
5. If `value == type(uint256).max`, Bob (or an attacker controlling the spender key) can now drain Alice's balance on `R'`.

		/// Compute the EIP-712 domain separator for a given verifying contract.
		///
		/// DOMAIN_SEPARATOR = keccak256(abi.encode(
		///   keccak256("EIP712Domain(string name,string version,uint256 chainId,address
		/// verifyingContract)"),
		///   keccak256(name),
		///   keccak256("1"),
		///   chainId,
		///   verifyingContract
		/// ))
		///
		/// The `name` parameter should be the token name per EIP-2612 specification.
		pub fn compute_domain_separator(verifying_contract: &H160, name: &[u8]) -> H256 {
			let name_hash = keccak_256(name);
			let version_hash = keccak_256(b"1");
			let chain_id = T::ChainId::get();

			// Encode: typehash || name_hash || version_hash || chainId || verifyingContract
			let mut data = Vec::with_capacity(DOMAIN_SEPARATOR_ENCODED_LEN);
			data.extend_from_slice(&DOMAIN_TYPEHASH);
			data.extend_from_slice(&name_hash);
			data.extend_from_slice(&version_hash);
			// Pad chain_id to 32 bytes (big-endian)
			data.extend_from_slice(&[0u8; 24]);
			data.extend_from_slice(&chain_id.to_be_bytes());
			// Pad address to 32 bytes
			data.extend_from_slice(&[0u8; 12]);
			data.extend_from_slice(verifying_contract.as_bytes());

			H256(keccak_256(&data))
		}

		///
		/// digest = keccak256("\x19\x01" || domainSeparator || structHash)
		///
		/// The `name` parameter should be the token name per EIP-2612 specification.
		pub fn permit_digest(
			verifying_contract: &H160,
			name: &[u8],
			owner: &H160,
			spender: &H160,
			value: &[u8; 32],
			nonce: &U256,
			deadline: &[u8; 32],
		) -> [u8; 32] {
			let domain_separator = Self::compute_domain_separator(verifying_contract, name);
			let struct_hash = Self::permit_struct_hash(owner, spender, value, nonce, deadline);

			let mut data = Vec::with_capacity(DIGEST_PREFIX_LEN);
			data.extend_from_slice(&[0x19, 0x01]);
			data.extend_from_slice(domain_separator.as_bytes());
			data.extend_from_slice(struct_hash.as_bytes());

			keccak_256(&data)
		}
