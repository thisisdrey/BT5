### Title
Treasury fee share on accrued debt interest is permanently lost when vault's LP `total-supply` is zero - ([File: mainnet/contracts/vault/v0-vault-*.clar])

### Summary
In all v0 vault contracts (`v0-vault-usdc.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`, `v0-vault-usdh.clar`, `v0-vault-stx.clar`), the protocol's fee share on accrued interest (`treasury-lp`) is computed proportionally to the vault's LP token `total-supply`. Debt (`principal-scaled`) accrues interest independent of `total-supply`, since borrowing does not require a borrower to hold shares — only depositors mint shares via `deposit`, while borrowed funds leave the vault via `system-borrow` without any corresponding share issuance. If `total-supply` is (temporarily) zero while debt is still outstanding, the treasury's fee for that accrual period is computed as zero and is irrecoverably lost, analogous to the reported `StakedEXA::globalIndex()` bug where rewards computed relative to a zero denominator are dropped rather than deferred.

### Finding Description
`accrue()` and its preview helper `calc-treasury-lp-preview` compute the protocol's cut of interest as follows: [1](#0-0) 

```
(define-private (calc-treasury-lp-preview)
  (let ((scaled-principal (var-get principal-scaled))
        (idx (var-get index))
        (next (next-index))
        (old-debt (mul-div-down scaled-principal idx INDEX-PRECISION))
        (new-debt (mul-div-down scaled-principal next INDEX-PRECISION))
        (debt-delta (if (> new-debt old-debt) (- new-debt old-debt) u0))
        (reserve-inc (mul-div-down debt-delta (var-get fee-reserve) BPS))
        (ta-preview (total-assets-preview)))
    (if (> reserve-inc u0)
        (mul-div-down reserve-inc (total-supply) (- ta-preview reserve-inc))
        u0)))
``` [2](#0-1) 

`reserve-inc` (the protocol's share of newly-accrued interest, `rate x deltaTime` on outstanding debt) is correctly computed from `debt-delta` regardless of `total-supply`. However, to convert this fee into mintable LP shares for the treasury, the formula multiplies `reserve-inc` by `total-supply`. If `total-supply` is `0` (e.g. because all depositors have redeemed their shares while a separate outstanding loan created via `system-borrow` still exists and continues to accrue interest), the multiplication collapses `treasury-lp` to `0`:

```
(mul-div-down reserve-inc (total-supply) (- ta-preview reserve-inc))  ;; = reserve-inc * 0 / X = 0
```

`accrue()` then unconditionally advances `idx` to `next` and only mints `treasury-lp` when it is `> 0`: [3](#0-2) 

```
(let ((next (next-index)) ...
      (treasury-lp (if (> reserve-inc u0) (mul-div-down reserve-inc (total-supply) (- (total-assets-preview) reserve-inc)) u0)))
  (if (not (is-eq idx next))
      (var-set index next)
      false)
  ...
  (if (> treasury-lp u0)
      (try! (ft-mint? zft treasury-lp .dao-treasury))
      false)
  ...)
```

Because `idx` is advanced to `next` regardless of whether the treasury fee was captured, the `old-debt`/`new-debt` baseline for the *next* accrual call starts from the new `idx`. The interest that accrued during the zero-`total-supply` window is baked into depositors'/borrowers' debt/interest index permanently, but the treasury's proportional cut of that specific window is never recovered — unlike depositor yield (tracked via `index`/`total-assets`), which is unaffected and continues to compound correctly. This exactly mirrors the reported bug class: a per-period reward/fee quantity computed as `rate x deltaTime` divided or scaled by a supply value that can be transiently zero, causing that period's fee to be dropped instead of deferred to savings/treasury.

The precondition (`total-supply == 0` while `principal-scaled > 0`) is reachable because `deposit`/`redeem` (share issuance/burn) and `system-borrow`/interest accrual (debt tracking) are decoupled state machines: `redeem` only checks the caller's own share balance and available liquidity, not whether other borrowers still owe outstanding principal: [4](#0-3) 

### Impact Explanation
This causes permanent loss of the protocol's fee/yield share (`fee-reserve` cut, minted as `zft` treasury LP tokens to `.dao-treasury`) on any interest accrued during a period when the LP token's `total-supply` is zero. This is unclaimed protocol yield that becomes permanently unrecoverable once `idx` advances past that window, matching the "theft/permanent freezing of unclaimed yield" High-impact category.

### Likelihood Explanation
Requires only an ordinary sequence of unprivileged actions: depositors fully redeeming while a borrower's loan (opened via `system-borrow`, which is decoupled from share issuance) remains outstanding and interest continues to accrue via any subsequent `accrue()`-triggering call (deposit, redeem, transfer, borrow, repay). No privileged role or DAO action is needed to trigger the loss — it can occur naturally whenever vault liquidity fully drains of LP holders temporarily.

### Recommendation
When computing `treasury-lp` in `calc-treasury-lp-preview`/`accrue`, if `total-supply` is `0` at the time `reserve-inc > 0`, do not silently drop the fee. Instead, either (a) block advancing `idx`/`last-update` until `total-supply > 0` again so the debt-delta window is preserved for later fee capture, or (b) accumulate the un-mintable `reserve-inc` in a running "pending treasury fee" variable that gets converted to `zft` (using the `total-supply` at the time it becomes nonzero again) rather than being computed and discarded per-call.

### Proof of Concept
1. Vault is initialized; a depositor deposits `X` underlying, minting `zft` shares (`total-supply = S`).
2. The DAO/borrower calls `system-borrow` to draw down the deposited liquidity as debt (`principal-scaled > 0`), independent of share ownership.
3. The depositor calls `redeem` to withdraw all remaining liquid `assets`, burning all `zft` shares (`total-supply -> 0`); this succeeds as long as `available-assets >= inkind`, which is unaffected by the outstanding borrowed principal.
4. Time passes; interest accrues on `principal-scaled` per `next-index`.
5. Any state-changing call (e.g. a `system-repay`, or another `deposit`) triggers `accrue()`. `debt-delta` and `reserve-inc` are computed as `> 0`, but `total-supply == 0`, so `treasury-lp = reserve-inc * 0 / (...) = 0` — no `zft` is minted to `.dao-treasury`.
6. `idx` is advanced to `next` regardless, so this window's fee-reserve share is permanently unrecoverable even though depositor-side interest/debt accounting is unaffected.
