### Title
Unbounded recursion in cmd/compile/internal/syntax parser expression grammar can cause stack overflow (fatal, unrecoverable) when compiling deeply-nested Go source - ([File: src/cmd/compile/internal/syntax/parser.go])

### Summary
The Go compiler's own frontend parser (`cmd/compile/internal/syntax`) parses unary/binary/primary expressions via mutually-recursive functions `unaryExpr`, `binaryExpr`, `pexpr`, and `operand` with no recursion-depth guard, unlike the sibling `go/parser` package, which explicitly added `incNestLev`/`decNestLev`/`maxNestLev` protection to `parseUnaryExpr`, `parsePrimaryExpr`, `parseBinaryExpr`, and `parseLiteralValue` to defend against exactly this class of stack-exhaustion bug. A source file with deeply nested unary operators or parentheses (e.g. `^^^^^...^1` or `((((...1...))))`) drives unbounded recursion through `unaryExpr` → `pexpr`/`operand` → `expr` → `binaryExpr` in `src/cmd/compile/internal/syntax/parser.go`, with no depth counter comparable to `maxNestLev`.

### Finding Description
Attacker-controlled input: a `.go` source file (e.g., a third-party module, generated code, or code shared with a victim who runs `go build`/`go vet`/`gofmt`-like tooling that uses this parser) → entry point `cmd/compile/internal/syntax.Parse` → `(*parser).fileOrNil` → statement/declaration parsing → `(*parser).expr()` → `(*parser).binaryExpr(nil, 0)` → `(*parser).unaryExpr()`, which for tokens `Mul, Add, Sub, Not, Xor, Tilde, And` recurses directly: `x.X = p.unaryExpr()` [1](#0-0) . `unaryExpr` falls through to `p.pexpr(nil, true)` → `p.operand(keep_parens)`, and for `_Lparen` tokens `operand` recurses back into `p.expr()` [2](#0-1) , forming a cycle `expr → binaryExpr → unaryExpr → pexpr → operand → expr`. None of these functions (`expr`, `binaryExpr`, `unaryExpr`, `pexpr`, `operand`) contains a nesting counter check — a `grep` for `nestLev` in `src/cmd/compile/internal/syntax/parser.go` returns no matches, confirming the guard present in `go/parser` (`p.nestLev`, `incNestLev`, `maxNestLev = 1e5`) was never ported to the compiler's own parser [3](#0-2) [4](#0-3) . A sufficiently deep nesting (tens of thousands of unary operators or nested parens) exhausts the goroutine stack, causing a fatal, unrecoverable runtime stack-overflow crash of the `go` toolchain process — Go stack overflows cannot be caught by `recover()`.

### Impact Explanation
This causes a compiler-process crash (denial of service) whenever `go build`/`go vet`/`gofmt` or any tool embedding `cmd/compile/internal/syntax` parses a maliciously crafted `.go` file with pathologically nested unary/parenthesized expressions. This falls squarely within the accepted "build-time handling of untrusted source" category (parsing a downloaded module or victim-authored file is expected, not "malicious source execution"), so it is a legitimate PUBLIC/DoS-track candidate rather than out-of-scope resource exhaustion, since Go's stated policy explicitly allows "a real server panic or plausible malicious-input parser panic" to qualify. However, since it requires attacker-supplied *source code* to be fed into the local build toolchain (a build-time/dev-tooling context rather than a live network service), the practical exposure is lower than a hosted HTTP/TLS parser bug.

### Likelihood Explanation
Victim workflow: cloning/downloading a Go source file or module and running `go build`/`go vet` on it (an entirely ordinary, expected workflow for any Go developer or CI system). Attacker capability: merely craft a `.go` file with deep nesting; no privileges, credentials, or special access required — this matches the "ordinary user data" / "published module/archive/source consumed by a normal victim workflow" threat model from the rules.

### Recommendation
Port the same recursion-depth defense that `go/parser` already uses to `cmd/compile/internal/syntax/parser.go`: add a `nestLev`/`incNestLev`/`decNestLev`/`maxNestLev` mechanism (mirroring `src/go/parser/parser.go` lines 123–139) into `unaryExpr`, `binaryExpr`, `pexpr`, and `operand`, panicking via the existing `bailout` mechanism (which `cmd/compile/internal/syntax` already uses for error recovery) once a safe nesting limit is exceeded, so that pathological input produces a clean parse error instead of a fatal stack overflow.

### Proof of Concept

package syntax_test

import (
	"strings"
	"testing"

	"cmd/compile/internal/syntax"
)

// TestDeepUnaryNestingCausesStackOverflow demonstrates unbounded recursion
// in cmd/compile/internal/syntax's expression parser. Unlike go/parser,
// this parser has no nestLev/maxNestLev guard, so sufficiently deep
// nesting exhausts the goroutine stack and crashes the process fatally
// (unrecoverable via recover()).
func TestDeepUnaryNestingCausesStackOverflow(t *testing.T) {
	// Construct a source file whose expression is deeply nested via
	// unary operators, e.g. ^^^^....^1
	const depth = 5_000_000 // depth chosen to exceed default goroutine stack limits
	src := "package p\nvar x = " + strings.Repeat("^", depth) + "1\n"

	errh := func(err error) { t.Log(err) }
	// syntax.Parse recurses through expr -> binaryExpr -> unaryExpr -> pexpr
	// -> operand with no depth limit, unlike go/parser's maxNestLev guard.
	_, _ = syntax.Parse(syntax.NewFileBase("t.go"), strings.NewReader(src), errh, nil, 0)
	// Expected (buggy) behavior: process crashes with "fatal error: stack overflow"
	// before this line is ever reached, instead of returning a syntax error.
}
```

**Note on confidence:** I was unable to directly compare `cmd/compile/internal/syntax/parser.go`'s complete `fileOrNil`/`Parse` entry point and confirm there is no external `debug.SetMaxStack` or goroutine-stack-size mitigation elsewhere in the compiler driver (`cmd/compile/internal/gc` or `main.go`) within the tool's search results; this would need to be checked in a full session before treating the finding as fully proven, since a caller-side stack size limit or existing depth check outside the searched file could change the conclusion.

// maxNestLev is the deepest we're willing to recurse during parsing
const maxNestLev int = 1e5

func incNestLev(p *parser) *parser {
	p.nestLev++
	if p.nestLev > maxNestLev {
		p.error(p.pos, "exceeded max nesting depth")
		panic(bailout{})
	}
	return p
}

// decNestLev is used to track nesting depth during parsing to prevent stack exhaustion.
// It is used along with incNestLev in a similar fashion to how un and trace are used.
func decNestLev(p *parser) {
	p.nestLev--
}
```

func (p *parser) parseUnaryExpr() ast.Expr {
	defer decNestLev(incNestLev(p))

	if p.trace {
		defer un(trace(p, "UnaryExpr"))
	}

	switch p.tok {
	case token.ADD, token.SUB, token.NOT, token.XOR, token.AND, token.TILDE:
		pos, op := p.pos, p.tok
		p.next()
		x := p.parseUnaryExpr()
		return &ast.UnaryExpr{OpPos: pos, Op: op, X: x}
