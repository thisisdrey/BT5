### Title
Signature-malleability signer confusion lets `ValidateMultiSign` TVM precompile double-count one key's weight - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `ValidateMultiSign` precompile (TVM opcode `validatemultisign`), reachable by any account/contract that calls it from a smart contract, aggregates weights of recovered signer addresses to check against a `Permission` threshold. Its duplicate-signature detection binds an approval to the exact `(recoveredAddr, signatureBytes)` pair instead of binding it to the signer identity alone, so a second, ECDSA-malleable variant of the same signature (same signer, different `s`/`v` encoding) is not recognized as a repeat and is credited as an independent approval.

### Finding Description
`TransactionCapsule.checkWeight` (used for on-chain transaction multisig, `chainbase/src/main/java/org/tron/core/capsule/TransactionCapsule.java:233-270`) deduplicates strictly by recovered *address* via `addMap.containsKey(base64)`, so multiple signatures recovering to the same key can only count once.

The TVM precompile `PrecompiledContracts.ValidateMultiSign.execute` (`actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java:1052-1120`) implements the equivalent multisig-threshold check differently: [1](#0-0) 

For each supplied signature it recovers `recoveredAddr`, then checks whether `executedSignList` already contains that *address*. If it does, it only `continue`s (skips) when the exact merged `(recoveredAddr + signature bytes)` tuple was already seen; otherwise it falls through, computes the key's `weight` again via `TransactionCapsule.getWeight`, and adds it a second time to `totalWeight`. Because ECDSA signatures are malleable (a signature `(r, s, v)` and its low-/high-`s` counterpart `(r, n-s, v')` both recover to the same address for the same message hash), an attacker holding one valid signature from a single permission key can derive a second, byte-different, still-valid signature that resolves to the identical address. Feeding both into `validatemultisign` causes the same signer's weight to be counted twice, letting a caller satisfy a permission `threshold` with fewer genuinely distinct co-signers than the permission requires — i.e., the signature is not correctly bound to a single accounted-for signer instance, matching the "signer confusion" bug class in the report (forged/duplicate signature variant accepted as if it were an additional, independent approval).

### Impact Explanation
Any active/multisig `Permission` on an account can be spoofed via a smart contract calling the `validatemultisign` precompile: an attacker who obtains just one of the N required co-signers' signatures (e.g., a single leaked or maliciously obtained key with lower weight than the threshold) can synthesize a malleated duplicate and pass the multisig `totalWeight >= permission.getThreshold()` check without collecting signatures from the other required keys. Contracts relying on this precompile to gate privileged operations (fund releases, governance actions, withdrawal approvals) can be tricked into treating a single-key approval as a fully co-signed one, resulting in unauthorized account operations / theft of funds gated by that contract logic.

### Likelihood Explanation
Reachable from any TVM contract execution (`TriggerSmartContract`) by an ordinary, unprivileged account; no special witness/committee/peer privilege is required. It requires the attacker to control (or obtain) at least one of the permission's keys and be able to derive its malleated counterpart signature, which is a standard ECDSA operation (flip `s` to `n-s` and adjust recovery `v`). No cryptographic break of the underlying keys is needed.

### Recommendation
In `PrecompiledContracts.ValidateMultiSign.execute`, deduplicate strictly by `recoveredAddr` (as `TransactionCapsule.checkWeight` already does), rejecting or skipping any second signature whose recovered address was already counted, regardless of whether the raw signature bytes differ. Additionally, normalize/reject non-canonical `s` values (enforce low-`s`) before address recovery to eliminate signature malleability at the source, consistent with typical `ecrecover`-style canonicalization.

### Proof of Concept
1. Create an account with an `Active` permission containing keys `K1` (weight 1) and `K2` (weight 1), threshold 2.
2. Sign the precompile's message hash with `K1` only, obtaining signature `S1 = (r, s, v)`.
3. Derive the malleated signature `S1' = (r, n-s, v')` for the same key `K1` (standard secp256k1 malleability transform) — both `S1` and `S1'` recover to `K1`'s address for the same hash.
4. Call `validatemultisign(address, permissionId, hash, [S1, S1'])`.
5. In `ValidateMultiSign.execute`, the first iteration adds weight 1 for `K1`. The second iteration recovers the same `recoveredAddr` for `K1`; since the merged `(addr+sign)` bytes differ from the first entry, the `continue` skip is not triggered, so weight 1 is added again — `totalWeight` reaches 2, meeting the threshold using signatures from only one real key (`K1`), never obtaining `K2`'s signature.
