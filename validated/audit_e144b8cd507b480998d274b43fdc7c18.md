### Title
`matchSingleOrder` skips persisting maker order's `INACTIVE` state and quantity update on the "too small" edge case, leaving a fully-consumed order visible as `ACTIVE` in storage - ([File: actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java])

### Summary
In `MarketSellAssetActuator.matchSingleOrder`, when a taker order is larger than the maker's remaining amount and the computed `makerBuyTokenQuantityReceive` rounds to `0` (the "quantity too small" branch), the method mutates `makerOrderCapsule`'s in-memory state (`updateOrderState(..., State.INACTIVE, ...)` and `setSellTokenQuantityReturn()`) and then returns early - but the `orderStore.put(makerOrderCapsule...)` call that persists these changes is only reached on the non-early-return path.

### Finding Description
`matchSingleOrder` (invoked from `matchOrder`) computes fill amounts between a taker and a maker order. In the "taker > maker" branch: [1](#0-0) 

`MarketUtils.updateOrderState(makerOrderCapsule, State.INACTIVE, marketAccountStore)` is called unconditionally, which (a) sets the in-memory `makerOrderCapsule`'s state to `INACTIVE`, and (b) removes the order from the owner's `MarketAccountOrderCapsule` order list in `marketAccountStore` (this side effect IS persisted): [2](#0-1) 

If `makerBuyTokenQuantityReceive == 0`, the code calls `makerOrderCapsule.setSellTokenQuantityReturn()` and the actuator's private `returnSellTokenRemain(makerOrderCapsule)` helper, then `return`s immediately: [3](#0-2) 

That helper only persists the maker's `accountStore` balance update - it never calls `orderStore.put` for the order itself. The only place that persists the maker order object is further down, right after the `if/else` block, and it is skipped by the early `return`: [4](#0-3) 

The result: `orderStore` still contains the maker order with its old `State.ACTIVE`/pre-match state and its stale `sellTokenQuantityRemain` (never zeroed, since `MarketUtils.returnSellTokenRemain` sets `sellTokenQuantityRemain` to `0` only on the *local* capsule object that is discarded, not the stored one). Meanwhile `MarketAccountOrderCapsule.removeOrder` has already stripped the order ID from the owner's active-order list in `marketAccountStore`, so the order becomes orphaned: still `ACTIVE` and non-zero remain in `MarketOrderStore`, but no longer reachable/cancelable through the owner's order list, and its linked-list position in `MarketOrderIdListCapsule`/`MarketPairPriceToOrderStore` is also never unlinked (the `removeOrder` call in `matchOrder` that unlinks the price-order list is gated on `makerOrderCapsule.getSellTokenQuantityRemain() == 0`, which is never true for the stored capsule since only the discarded local copy has it zeroed via `setSellTokenQuantityReturn()`—wait, `setSellTokenQuantityReturn` does not zero `sellTokenQuantityRemain`, it only records the return amount, so `getSellTokenQuantityRemain()` still returns the pre-match value seen by `matchOrder`'s empty-check after the call returns).

This is directly analogous to the reported `fillOrder` bug: a struct/capsule's status field is updated only on the transient copy, while the copy actually written back to persistent storage is stale, causing the visible on-chain order state to diverge from the intended "closed"/"cancelled" state.

### Impact Explanation
An order that should be considered consumed/inactive remains `ACTIVE` with stale `sellTokenQuantityRemain` in `MarketOrderStore`, while it has been silently removed from the owner's active order list in `marketAccountStore`. This produces persistent inconsistent/corrupted state in the exchange order book reachable by any account issuing `MarketSellAssetContract` transactions that trigger this specific rounding edge case as a maker match. Downstream code that trusts `orderStore` order state (e.g. `MarketCancelOrderActuator`, further `matchOrder` calls that read this maker order from the price-list) can behave incorrectly against a corrupted/stuck order, and the mismatch between `marketAccountStore` bookkeeping and `orderStore` truth is a permanent state inconsistency in the order book (medium severity, consistent with the judge's medium ruling on the analogous finding, since it is a state-correctness bug reachable by ordinary users but does not directly enable outright theft in the one-line early-return path shown).

### Likelihood Explanation
Reachable by any unprivileged account broadcasting `MarketSellAssetContract` transactions; the triggering condition (`makerBuyTokenQuantityReceive == 0` due to integer division rounding when `makerSellQuantity < makerBuyQuantity`) is a legitimate, reachable numeric edge case documented in the code's own comments, not a contrived scenario, making it plausible in real trading pairs with certain price ratios and small remaining quantities.

### Recommendation
In `matchSingleOrder`, persist the maker order's updated state before returning in the `makerBuyTokenQuantityReceive == 0` branch, e.g. add `orderStore.put(makerOrderCapsule.getID().toByteArray(), makerOrderCapsule);` immediately before the `return;` statement (or restructure the method so all exit points funnel through the single `orderStore.put` call at the end).

### Proof of Concept
1. Craft two `MarketSellAssetContract` orders for a token pair such that the maker's `sellTokenQuantity`/`buyTokenQuantity` ratio and remaining quantity, when multiplied against the taker's requested amount via `MarketUtils.multiplyAndDivide`, yields `makerBuyTokenQuantityReceive == 0` in the "taker > maker" branch of `matchSingleOrder` (per the code's own worked example: `sellQuantity=200, buyQuantity=100, sellRemain=1`).
2. Submit the taker's `MarketSellAssetContract` so it matches against this maker order through `MarketSellAssetActuator.matchOrder` → `matchSingleOrder`.
3. After execution, query `MarketOrderStore` for the maker order: its `state` remains `ACTIVE` (or whatever pre-match state) and `sellTokenQuantityRemain` is unchanged from before the match, contradicting the fact that `marketAccountStore`'s `MarketAccountOrderCapsule` for the maker no longer lists this order ID (it was removed by `MarketUtils.updateOrderState`), demonstrating the divergence between actual persisted order state and the account's bookkeeping.

  public static void updateOrderState(MarketOrderCapsule orderCapsule,
      State state, MarketAccountStore marketAccountStore) throws ItemNotFoundException {
    orderCapsule.setState(state);

    // remove from account order list
    if (state == State.INACTIVE || state == State.CANCELED) {
      MarketAccountOrderCapsule accountOrderCapsule = marketAccountStore
          .get(orderCapsule.getOwnerAddress().toByteArray());
      accountOrderCapsule.removeOrder(orderCapsule.getID());
      marketAccountStore.put(accountOrderCapsule.createDbKey(), accountOrderCapsule);
    }
  }
