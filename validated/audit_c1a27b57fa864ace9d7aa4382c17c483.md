### Title
HTTP request smuggling (TE.CL) via inconsistent Content-Length/Transfer-Encoding validation in `HttpRequestPreamble` — ([File: stackslib/src/net/http/request.rs])

### Summary
`HttpRequestPreamble::consensus_deserialize` in `stackslib/src/net/http/request.rs` parses `Content-Length` but never inspects `Transfer-Encoding` at all, and it silently converts a malformed `Content-Length` value into `None` rather than rejecting the request. This is the same bug class as CVE-2024-6827 (gunicorn TE.CL smuggling): the request-framing logic can disagree with any front-end/reverse-proxy or intermediate Stacks node that also parses the request and gives priority to `Transfer-Encoding` per RFC 9112, letting an attacker desynchronize the two parsers and smuggle a second, attacker-controlled request/response into the stream.

### Finding Description
In `HttpRequestPreamble::consensus_deserialize` (`stackslib/src/net/http/request.rs:355-422`), each header is matched against `"host"`, `"content-type"`, `"content-length"`, `"connection"`, and `"set-cookie"`. There is no `"transfer-encoding"` branch at all — a header named `Transfer-Encoding: chunked` simply falls into the generic `else` branch and is stored as an ordinary opaque header: [1](#0-0) 

Contrast this with `HttpResponsePreamble::consensus_deserialize` (`stackslib/src/net/http/response.rs:561-586`), which explicitly parses `transfer-encoding`, and hard-fails if both `Content-Length` and `Transfer-Encoding: chunked` are present, or if neither is present: [2](#0-1) 

No equivalent guard exists for requests. Consequently:
1. An inbound request with **both** `Content-Length: N` and `Transfer-Encoding: chunked` is accepted without error, unlike the symmetric response path.
2. `HttpRequestPreamble::get_content_length()` always returns `content_length.unwrap_or(0)` [3](#0-2) , and `ProtocolFamily::payload_len` for requests always returns `Some(get_content_length())` [4](#0-3) , meaning **stacks-core always frames the request body strictly by Content-Length and never honors Transfer-Encoding on the request side** — the code comment even says "HTTP requests can't be chunk-encoded, so this should never be reached" [5](#0-4) .
3. If a malformed `Content-Length` value is supplied, it is coerced to `None` rather than causing a parse error: `content_length = match value.parse::<u32>() { Ok(len) => Some(len), Err(_) => None }` [6](#0-5) , which then resolves to a body length of `0` via `get_content_length`, silently truncating the framed body length to zero instead of rejecting the malformed message.

This breaks the framing equality that any two HTTP-speaking components in the path (e.g., a reverse proxy such as nginx/gunicorn placed in front of the RPC endpoint, or a peer Stacks node relaying the request) are expected to agree on. Since RFC 9112 mandates that `Transfer-Encoding` take priority when both headers are present, a front-end that follows the RFC will treat the request as chunked while stacks-core treats it strictly as `Content-Length`-framed (or as zero-length, in the malformed-length case) — the classic TE.CL desynchronization primitive.

### Impact Explanation
This maps to the "request smuggling" impact class explicitly called out in the assessment criteria. In any deployment where the node's RPC HTTP interface (`stackslib/src/net/http`, `stackslib/src/net/httpcore.rs`) sits behind a load balancer, reverse proxy, or is chained through another HTTP-aware component, an attacker can smuggle a hidden request that the front-end considers part of one message boundary while stacks-core parses it as a second, independent request on the same connection. This can be leveraged for cache poisoning, bypassing access-control checks performed by the front-end (e.g., IP allow-lists or auth performed by a reverse proxy in front of admin RPC endpoints), or response queue poisoning against other legitimate clients sharing the connection pool.

### Likelihood Explanation
The request preamble parser is reachable by any remote, unauthenticated client able to send raw bytes to the node's RPC HTTP listener — no privileged key or role is required. The only precondition is that the node be deployed behind some intermediary that also parses HTTP framing and prefers `Transfer-Encoding` (a common production topology for exposing Stacks RPC endpoints). No exotic timing or race condition is needed; the two conflicting headers can be sent in a single, ordinary crafted request.

### Recommendation
Add an explicit `"transfer-encoding"` branch to `HttpRequestPreamble::consensus_deserialize` mirroring the response-side logic in `stackslib/src/net/http/response.rs`: reject any request that specifies `Transfer-Encoding` (since chunked requests are unsupported) or that specifies both `Content-Length` and `Transfer-Encoding`. Additionally, treat a malformed `Content-Length` value as a hard parse error (`CodecError::DeserializeError`) instead of silently coercing it to `None`/`0`, so ambiguous or invalid framing is rejected outright rather than resolved via a permissive default.

### Proof of Concept
Send the following raw bytes to the node's RPC HTTP listener (`stackslib/src/net/http/request.rs` parsing path) through a front-end proxy that prioritizes `Transfer-Encoding`:
```
POST /v2/transactions HTTP/1.1
Host: victim-node:20443
Content-Type: application/octet-stream
Content-Length: 4
Transfer-Encoding: chunked

0

GET /admin/secret-endpoint HTTP/1.1
Host: victim-node:20443

```
- The front-end proxy, following RFC 9112, treats this as one chunked request that terminates at the `0\r\n\r\n` chunk terminator and treats the smuggled `GET /admin/...` bytes as the start of the *next* pipelined request on the connection.
- `HttpRequestPreamble::consensus_deserialize` in stacks-core ignores `Transfer-Encoding` entirely and instead frames the request body using `Content-Length: 4`, consuming only 4 bytes of body (`"0\r\n\r"`) and treating everything after (including the smuggled `GET /admin/...` line) as the next request on the wire — producing a desynchronized view of the request stream relative to the proxy, enabling the smuggling of the second request.
