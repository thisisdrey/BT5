### Title
Loss of TRX/TRC10 tokens when transferred to the all-zero address due to missing zero-address validation - (File: `actuator/src/main/java/org/tron/core/actuator/TransferActuator.java`, `actuator/src/main/java/org/tron/core/actuator/TransferAssetActuator.java`)

### Summary
`TransferActuator.validate()` and `TransferAssetActuator.validate()` only validate `toAddress` via `DecodeUtil.addressValid()`, which checks the address length and the single-byte network prefix, but never rejects the degenerate "zero address" (prefix byte followed by 20 zero bytes) [1](#0-0) . As a result, a user can send TRX or TRC10 tokens to this unowned address, and since no private key exists for it, the funds are permanently and irrecoverably lost, mirroring the "loss of tokens sent to a zero address" bug class described in the ERC20/BentoBox report.

### Finding Description
`TransferActuator.validate()` performs `DecodeUtil.addressValid(toAddress)` and a self-transfer check (`Arrays.equals(toAddress, ownerAddress)`), but does not check whether `toAddress` is the reserved all-zero address [2](#0-1) . In `execute()`, if no account exists at `toAddress`, a brand-new `AccountCapsule` is silently created at that address and the TRX balance is credited to it [3](#0-2) .

The same pattern exists in `TransferAssetActuator.validate()`, which validates address format and self-transfer but not the zero address, before crediting TRC10 asset balance to a newly created account at that address [4](#0-3) .

Unlike the chain's official burn destination — the "black hole" address used deliberately for burning TRX (e.g., via `AccountStore.getBlackhole()` referenced in `TransferActuator`/`TransferAssetActuator`) — the raw zero address (`0x41` + 20 zero bytes) is not the sanctioned burn address, has no known private key, and is reachable by simple user/API error (e.g., malformed `toAddress` encoding, default/zero-initialized byte arrays in client SDKs, or malicious front-end injection tricking a user into signing a transfer to an all-zero destination).

### Impact Explanation
Any TRX or TRC10 token sent to the unvalidated zero address becomes permanently unrecoverable, constituting a permanent freezing/loss of user funds. This matches the accepted impact category of "permanent freezing of funds," since neither the user nor any protocol actor can retrieve tokens sent to that address.

### Likelihood Explanation
Any unprivileged transaction broadcaster can trigger this by submitting a signed `TransferContract` or `TransferAssetContract` with `toAddress` set to the zero-padded address — it requires no special privileges, only a single signed transaction, making it trivially reachable, though it typically requires a client bug, wallet integration defect, or social engineering to cause a real transfer to that destination rather than being a directly profitable attack vector for the attacker themselves.

### Recommendation
Add an explicit check in `validate()` of `TransferActuator` and `TransferAssetActuator` (and any other actuator/VM validation path such as `VMUtils.validateForSmartContract`) rejecting `toAddress` equal to the all-zero-payload address, analogous to the existing self-transfer check, e.g. reject if `Arrays.equals(toAddress, zeroAddressWithPrefix)`.

### Proof of Concept
1. Construct a `TransferContract` with a valid `ownerAddress` and `toAddress = 0x41` followed by 20 zero bytes (this passes `DecodeUtil.addressValid` since only length/prefix are checked).
2. Submit the transaction; `TransferActuator.validate()` passes (not equal to owner address, valid format) and `execute()` creates a new account at the zero address and credits the transferred amount [5](#0-4) .
3. The tokens are now held by an address with no corresponding private key, permanently lost. The same PoC applies to `TransferAssetActuator` for TRC10 tokens.
