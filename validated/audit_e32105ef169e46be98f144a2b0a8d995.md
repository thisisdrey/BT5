Based on the investigation, the closest local analog to the Chainlink `latestAnswer()`-without-freshness-check pattern is in `pallet-oracle` (`substrate/frame/honzon/oracle/src/lib.rs`), which is used as a generic price/data-feed source for consuming pallets in the runtime.

### Title
`DataProvider::get` in pallet-oracle silently drops price freshness, letting stale oracle data reach dependent runtime pallets - (File: `substrate/frame/honzon/oracle/src/lib.rs`)

### Summary
The oracle pallet stores every submitted value with a timestamp in `TimestampedValue` and aggregates it into `Values<T, I>` [1](#0-0) . However, the `DataProvider` trait implementation — the interface most consumer pallets are expected to use for price data — unconditionally strips the timestamp and returns only the raw value, exactly mirroring Chainlink's deprecated `latestAnswer()` pattern that returns "the last value" with no way to check freshness:

```rust
impl<T: Config<I>, I: 'static> DataProvider<T::OracleKey, T::OracleValue> for Pallet<T, I> {
	fn get(key: &T::OracleKey) -> Option<T::OracleValue> {
		Self::get(key).map(|timestamped_value| timestamped_value.value)
	}
}
``` [2](#0-1) 

### Finding Description
`Values<T, I>` is only ever refreshed inside `do_feed_values`, and it is never expired or invalidated by elapsed time — `RawValues` entries persist until an operator is removed from the membership set via `change_members_sorted` [3](#0-2) , not due to staleness. If oracle operators stop submitting updates (network partition, censorship, operator downtime, or simply market volatility outpacing submission cadence), `Values::<T,I>::get(key)` keeps returning the last combined price indefinitely.

The pallet does expose freshness metadata through `TimestampedValueOf` and the `DataProviderExtended::get_all_values` interface, which is the equivalent of Chainlink's `latestRoundData()` (it returns `(key, Option<TimestampedValue>)` pairs so a caller *could* check `timestamp`) [4](#0-3) . But the plain `DataProvider::get` — the interface that most trait bounds like `T::Source: DataProvider<...>` are written against in downstream pallets — throws away that information entirely, exactly as `latestAnswer()` throws away `updatedAt`.

Any downstream pallet in a runtime built with this oracle (e.g. a collateral-pricing, liquidation, or stablecoin pallet configured with `type PriceSource: DataProvider<CurrencyId, Price>`) that calls `T::PriceSource::get(&currency_id)` has no means, at that call site, to detect that the returned price is stale. There is no `staleThreshold`/`subtract(now, timestamp) <= threshold` guard anywhere in this pallet or enforced by the trait contract — the freshness check is fully optional and must be independently re-implemented by every consumer, and the widely-used simpler trait (`DataProvider`) makes that impossible.

### Impact Explanation
A consumer pallet relying on `DataProvider::get` for asset valuation (collateral pricing, liquidation triggers, exchange-rate-based fee/reward calculations) would silently use an arbitrarily old price once oracle feeders stop updating, producing incorrect collateralization/liquidation decisions or mispriced settlements — the same "affects an account's health and leads to incorrect liquidation prices" outcome described in the source report. This is a runtime-behavior-compromising bug rather than a fund-custody bug directly in this pallet, since pallet-oracle itself does not move funds, but any pallet built on top of `DataProvider` inherits the flaw with no opt-out short of bypassing the standard trait.

### Likelihood Explanation
Likelihood is moderate: no malicious actor is required — a benign operator outage, membership churn, or normal light-traffic period (few oracle feeds submitted) is sufficient to let `Values` go stale while still being reported as valid, because the pallet has no on-chain concept of "stale" at all. The bug is triggered purely by ordinary/degraded operation, not adversarial input, which matches the "reduces risk of using stale prices" concern in the original report.

### Recommendation
Add a staleness parameter (analogous to Chainlink's `staleThreshold`) to `pallet-oracle`, and change the `DataProvider::get` implementation to return `None` (or propagate the timestamp) when `now - value.timestamp > MaxStaleness`, forcing consumers to handle absence of fresh data explicitly — mirroring the `H2O` team's fix of moving off `latestAnswer` onto `latestRoundData` plus an explicit freshness `require`.

### Proof of Concept
1. Configure a runtime with `pallet-oracle` and a downstream pricing pallet using `type PriceSource: DataProvider<OracleKey, OracleValue> = pallet_oracle::Pallet<T>`.
2. Feed valid prices from the minimum quorum of members once at block N (`feed_values`) [5](#0-4) , populating `Values<T,I>`.
3. Stop all further `feed_values` calls (simulating operator downtime) for an arbitrarily long period (many blocks/eras).
4. Call `pallet_oracle::Pallet::<T>::get(&key)` (or the downstream pallet's `DataProvider::get`) at a much later block — it still returns the original combined value with `Pays::No` success and no error, with no way for the caller to know it is stale, since the timestamp was already discarded in the `DataProvider` implementation [6](#0-5) .

	fn do_feed_values(who: T::AccountId, values: Vec<(T::OracleKey, T::OracleValue)>) {
		let now = T::Time::now();
		for (key, value) in &values {
			let timestamped = TimestampedValue { value: value.clone(), timestamp: now };
			RawValues::<T, I>::insert(&who, key, timestamped);

			// Update `Values` storage if `combined` yielded result.
			if let Some(combined) = Self::combined(key) {
				<Values<T, I>>::insert(key, combined);
			}

			T::OnNewData::on_new_data(&who, key, value);
		}
		Self::deposit_event(Event::NewFeedData { sender: who, values });
	}
