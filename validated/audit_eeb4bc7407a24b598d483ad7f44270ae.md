Based on my investigation, I found a strong analog to the `DaoFactory`/`Pausable` bug class in java-tron's market/DEX feature toggle.

### Title
Market order placement bypasses the committee-controlled `ALLOW_MARKET_TRANSACTION` governance gate - (File: `actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java`)

### Summary
Java-tron implements a committee-governed "kill switch" pattern for optional protocol features: a `DynamicPropertiesStore` flag (e.g. `getAllowMarketTransaction()`) must be checked by the relevant actuator's `validate()` before the feature-specific state transition is permitted [1](#0-0) . This is the java-tron analog of Solidity's `Pausable`/`whenNotPaused` — the committee can enable or gate a feature (analogous to "unpause"), and every actuator that performs the gated operation is expected to enforce it, exactly as `AccountPermissionUpdateActuator.validate()` enforces `getAllowMultiSign()` and `ShieldedTransferActuator.validate()` enforces `supportShieldedTransaction()`. [2](#0-1) [3](#0-2) 

### Finding Description
`MarketSellAssetActuator` — the actuator that places a TRC10 sell/buy order on the on-chain order book (`MarketOrderStore`, `MarketPairToPriceStore`, `MarketPairPriceToOrderStore`) — never checks `dynamicStore.getAllowMarketTransaction()` anywhere in its `validate()`/`execute()` path. I confirmed via direct search of the file that no reference to `getAllowMarketTransaction` exists in `MarketSellAssetActuator.java`, even though `execute()` fully performs order creation and store mutation. [4](#0-3) 

This mirrors the reported bug exactly: `getAllowMarketTransaction` exists as a governance toggle (referenced in `DynamicPropertiesStore`, `ProposalService`, `Wallet`, and `Args`) intended to let the committee gate the market/DEX feature [5](#0-4) , but the primary actuator that performs the state-changing operation (order placement) never enforces it — analogous to `DaosFactory.create()` never calling `whenNotPaused`. Other actuators in the same codebase consistently apply this pattern (`UnfreezeBalanceV2Actuator.validate()` checks `supportUnfreezeDelay()`, `AccountPermissionUpdateActuator.validate()` checks `getAllowMultiSign()`), which shows the intended design: every feature-gated actuator must check its corresponding dynamic-property flag before the feature can be reached from a signed transaction. [6](#0-5) 

### Impact Explanation
If `ALLOW_MARKET_TRANSACTION` defaults to disabled (as is standard for committee-gated features at genesis/upgrade rollout) and the committee has not yet enabled it, any unprivileged transaction broadcaster can still submit `MarketSellAssetContract` transactions and have them fully executed — creating/matching orders, moving TRC10 balances between the order book escrow and accounts — bypassing the intended governance gate entirely. This undermines the committee's ability to keep the DEX feature disabled/paused network-wide (e.g., during a discovered matching-engine bug or economic exploit), and lets order matching mutate account balances via a feature path the network operators believe to be turned off.

### Likelihood Explanation
Likelihood is high for any network state where `ALLOW_MARKET_TRANSACTION` is `0`: any account with sufficient TRC10 balance can submit a `MarketSellAssetContract` directly, since `ActuatorCreator` dispatches to `MarketSellAssetActuator` purely based on contract type with no external gate check outside the actuator itself. No special privileges or malicious-SR/witness behavior are required — a single ordinary signed transaction reaches the vulnerable code path. [7](#0-6) 

### Recommendation
Add an explicit `dynamicStore.getAllowMarketTransaction() != 1` check (throwing `ContractValidateException`) at the top of `MarketSellAssetActuator.validate()`, matching the pattern used in `UnfreezeBalanceV2Actuator.validate()` and `AccountPermissionUpdateActuator.validate()`. The same check should be audited/added to any sibling market actuator (`MarketCancelOrderActuator`) that performs state-changing order-book operations, to ensure the DEX feature can actually be disabled by committee governance as intended.

### Proof of Concept
1. Deploy/observe a java-tron network where `ALLOW_MARKET_TRANSACTION` is `0` (feature not yet enabled by committee proposal).
2. As any unprivileged account, submit a `MarketSellAssetContract` transaction via the standard transaction broadcast API.
3. Observe that `MarketSellAssetActuator.validate()` performs no check on `getAllowMarketTransaction()` and the transaction proceeds to `execute()`, creating a live order in `MarketOrderStore`/`MarketPairToPriceStore` and debiting the seller's TRC10 balance — despite the committee never having enabled the market feature. [4](#0-3) 

**Caveat:** I was not able to fully inspect the entire `validate()` body of `MarketSellAssetActuator.java` or the sibling `MarketCancelOrderActuator.java` (tool budget exhausted), nor the exact default value/mutability semantics of `ALLOW_MARKET_TRANSACTION` in `DynamicPropertiesStore` (i.e., whether the committee can toggle it back to `0` after enabling it, which would make this a true "pause", or whether it is a one-way genesis flag). This should be verified in a follow-up session before treating this as fully confirmed.

  private Actuator getActuatorByContract(Contract contract,

      throws IllegalAccessException, InstantiationException, ContractValidateException {
    Class<? extends Actuator> clazz = TransactionFactory.getActuator(contract.getType());
    if (clazz == null) {
      throw new ContractValidateException("not exist contract " + contract);
