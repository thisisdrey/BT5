### Title
Unvalidated self-declared priority lets fee-free doomed transactions evict payable ones from the forwarding buffer - (File: `core/src/forwarding_stage.rs`)

### Summary
`ForwardingStage::buffer_packet_batches` computes eviction priority purely from a packet's self-declared compute-unit price and estimated cost via `calculate_priority`, without any check that the transaction's blockhash is valid or that its fee payer can actually pay. An attacker can therefore craft transactions guaranteed to be worthless (stale/invalid blockhash, unfunded fee payer) but with a maximal declared `compute_unit_price`, causing them to repeatedly win `packet_container.pop_min()` evictions against a victim's genuinely payable, lower-fee transaction.

### Finding Description
In `buffer_packet_batches` (`core/src/forwarding_stage.rs:270-336`), each incoming packet is only run through `SanitizedTransactionView::try_new_sanitized` and `RuntimeTransaction::<SanitizedTransactionView<_>>::try_new` before `calculate_priority` is invoked: [1](#0-0) 
These are purely static/structural sanitization checks — they do not verify blockhash freshness against the bank's blockhash queue, nor do they check that the declared fee payer holds sufficient lamports. `calculate_priority` (`core/src/forwarding_stage.rs:601-640`) derives the priority solely from the attacker-controlled `compute_unit_price` (via `transaction_configuration.priority_fee_lamports`), signature count, and a cost-model estimate: [2](#0-1) 
When the buffer is full, the lowest-priority entry is evicted via `packet_container.pop_min()` and replaced unconditionally whenever the new packet's computed priority is higher: [3](#0-2) 
`PacketContainer` (`core/src/forwarding_stage/packet_container.rs:1-58`) is a fixed-capacity `MinMaxHeap` ordered strictly by this self-reported `priority`, with no secondary validity signal: [4](#0-3) 
Because a real blockhash-age check and fee-payer balance check are only performed later in `BankingStage`'s `TransactionViewReceiveAndBuffer::try_handle_packet` / `working_bank.check_transaction_without_status_cache` — never in `ForwardingStage` — an attacker can submit transactions with a stale/invalid `recent_blockhash` or an empty fee-payer account, set `ComputeBudgetInstruction::set_compute_unit_price` to a very large value, and pass all forwarding-stage checks with an artificially inflated priority at zero real cost (no funds required, and no chance the transaction is ever included or fee-collected).

### Impact Explanation
This is grossly underpriced pre-fee work / QoS evasion of the forwarding ingress buffer: the attacker forces eviction of a legitimate, fee-paying transaction that would have been forwarded to the next leader, using packets that can never generate any actual fee. Repeating this against a full buffer (`PacketContainer::with_capacity(4 * 4096)`, `core/src/forwarding_stage.rs:218`) lets an unstaked remote client deny forwarding service to real users for the cost of generating and sending garbage-but-well-formed transactions.

### Likelihood Explanation
Preconditions are trivial for an unstaked attacker: craft syntactically valid transactions (any signature is fine, no on-chain state needed) with an inflated `compute_unit_price`, and flood the TPU so the forwarding buffer stays at `is_full()`. No staking, gossip, or validator control is required — only standard QUIC/UDP submission to the public TPU port, and repeatability is limited only by attacker bandwidth/CPU to sign packets.

### Recommendation
Before admitting a packet into the forwarding buffer (or before it is allowed to evict an existing entry), cross-check against bank state that would materially bound the attacker's ability to fabricate "free" priority — e.g., verify the transaction's `recent_blockhash` is within `max_processing_age` using the bank's blockhash queue, and/or require a minimal-balance check on the declared fee payer, similar to what `TransactionViewReceiveAndBuffer::try_handle_packet` already performs for the banking-stage buffer, so that only transactions with a realistic chance of executing (and thus paying fees) can command high eviction priority.

```rust
fn calculate_priority(
    transaction: &RuntimeTransaction<SanitizedTransactionView<&[u8]>>,
    bank: &Bank,
) -> Option<u64> {
    let transaction_configuration = transaction
        .transaction_configuration(&bank.feature_set)
        .ok()?;

    // Manually estimate fee here since currently interface doesn't allow a on SVM type.
    // Doesn't need to be 100% accurate so long as close and consistent.
    let prioritization_fee = transaction_configuration.priority_fee_lamports;
    let signature_details = transaction.signature_details();
    let signature_fee = signature_details
        .total_signatures()
        .saturating_mul(bank.fee_structure().lamports_per_signature);
    let fee_details = FeeDetails::new(signature_fee, prioritization_fee);

    let reward = bank
        .calculate_reward_and_burn_fee_details(&CollectorFeeDetails::from(fee_details))
        .get_deposit();

    let cost = CostModel::estimate_cost(
        transaction,
        transaction.program_instructions_iter(),
        transaction.num_requested_write_locks(),
        &bank.feature_set,
    );

    // We need a multiplier here to avoid rounding down too aggressively.
    // For many transactions, the cost will be greater than the fees in terms of raw lamports.
    // For the purposes of calculating prioritization, we multiply the fees by a large number so that
    // the cost is a small fraction.
    // An offset of 1 is used in the denominator to explicitly avoid division by zero.
    const MULTIPLIER: u64 = 1_000_000;
    Some(
        MULTIPLIER
            .saturating_mul(reward)
            .wrapping_div(cost.sum().saturating_add(1)),
    )
```
