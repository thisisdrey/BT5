### Title
StackerDB slot-signature digest omits the target contract, enabling cross-contract chunk replay into a differently-typed StackerDB replica - ([File: libstackerdb/src/libstackerdb.rs])

### Summary
`SlotMetadata::auth_digest()` binds a StackerDB chunk's signature only to `(slot_id, slot_version, data_hash)` and never to the StackerDB smart contract (`QualifiedContractIdentifier`) the chunk is destined for. Because the Nakamoto signer set deploys multiple StackerDB contracts (`signers-0-1`, `signers-0-2`, `signers-0-3`, and the `signers-1-*` equivalents) that all derive their slot-to-signer assignment from the *same* underlying page in `.signers` (`stackerdb-get-signer-slots-page`), the same signer address owns the same `slot_id` across all of them. A chunk that a signer legitimately signed and broadcast for one contract (e.g. `signers-0-1`, the `BlockResponse` lane) can be resubmitted verbatim to a different contract at the same slot index (e.g. `signers-0-2`, the `StateMachineUpdate` lane) and will pass all node-side validation, because that validation never checks which contract the signature was actually produced for. This is directly analogous to the Keycloak flaw: a "verification proof" (signature) keyed by an insufficiently scoped identifier `(slot_id, slot_version, data_hash)` is accepted outside the context it was actually verified for.

### Finding Description
`SlotMetadata::auth_digest()` computes the signed digest as: [1](#0-0) 

This digest — and therefore the signature over it — never includes the StackerDB's `QualifiedContractIdentifier`. `SlotMetadata::verify()` only checks that the signature recovers to the expected principal: [2](#0-1) 

The node-side write path, `StackerDBTx::try_replace_chunk`, looks up the expected signer for `(smart_contract, slot_desc.slot_id)` and calls `slot_desc.verify(&slot_validation.signer)`, but this lookup and check are entirely local to the contract passed in — nothing in the signed payload itself proves the chunk was produced *for that contract*: [3](#0-2) 

The same gap exists in the P2P push-chunk validation path used for gossip-relayed and unsolicited chunks: [4](#0-3) 

The reason this is exploitable in practice is that the Nakamoto signer-set boot contracts intentionally reuse identical slot ordering across multiple StackerDB contracts. Each signer-message-type gets its own contract (`signers-{set}-{message_id}`), but all of them read the same signer-slot page: [5](#0-4) [6](#0-5) 
and these contracts are instantiated for every `message_id` in `SIGNER_SLOTS_PER_USER` for each signer set: [7](#0-6) 

So a given signer address owns the identical `slot_id` in `signers-0-1` (`BlockResponse`), `signers-0-2` (`StateMachineUpdate`), and `signers-0-3` (`BlockPreCommit`) simultaneously. An attacker who observes (via legitimate P2P gossip or a plain `GET /v2/stackerdb/.../chunks/...` request) a validly-signed chunk broadcast for `signers-0-1` slot `k` can resubmit the identical `(slot_id, slot_version, sig, data)` tuple to `signers-0-2` slot `k` via `POST /v2/stackerdb/{address}/signers-0-2/chunks`, handled by: [8](#0-7) 
The signature check passes because the digest never encoded which contract it was for, and the write proceeds and is subsequently gossiped network-wide via `StackerDBPushChunk`: [9](#0-8) 

Note there is a downstream mitigation, but only in the signer client's local event-conversion code (`libsigner/src/events.rs`), which cross-checks the payload's declared type-prefix against the contract's expected message lane before accepting it into `SignerEvent`: [10](#0-9) 
This filter runs only when a signer process consumes its own node's event-observer stream — it does not exist in the StackerDB storage/relay layer itself, so the forged write and its network-wide propagation still occur regardless.

### Impact Explanation
This breaks the intended equality "signed and authorized for contract X" == "accepted and stored as valid for contract X". An unprivileged network participant can force a node's StackerDB replica for one contract to store attacker-selected (but validly-signed-elsewhere) data that was never actually produced for that contract, and can cause that forged-context chunk to be relayed network-wide via `StackerDBPushChunk`. This is an unauthorized write to StackerDB state that other software (beyond the specific `libsigner` event-conversion consumer, which happens to filter by payload-type) may rely on as canonical for that contract — e.g. any custom StackerDB application or future signer-message lane that does not perform the same type/lane cross-check would process the misrouted data as if it were legitimately produced for that contract.

### Likelihood Explanation
No privileged access or private key is required: the attacker only needs to observe one legitimately-broadcast chunk (StackerDB chunks are, by design, publicly readable/replicated) and replay it verbatim to a sibling contract sharing the same signer/slot assignment. The Nakamoto signer-set deployment structure (`signers-0-1/2/3`, `signers-1-1/2/3`) guarantees this precondition (identical slot ownership across contracts) holds for every reward cycle on every network.

### Recommendation
Include the target `QualifiedContractIdentifier` (or a contract-specific domain separator) inside `SlotMetadata::auth_digest()` so a chunk signature is cryptographically bound to the specific StackerDB it was authorized for, preventing cross-contract replay even when slot ownership happens to coincide across contracts.

### Proof of Concept
1. Observe (via `GET /v2/stackerdb/{signer_addr}/signers-0-1/chunks/{slot_id}/{version}` or via P2P `StackerDBChunkInvData`/`StackerDBGetChunkData` exchange) a validly-signed chunk `C = (slot_id=k, slot_version=v, sig, data)` broadcast by signer `S` for `signers-0-1`.
2. Confirm via `.signers` (`stackerdb-get-signer-slots-page`) that `S` also owns `slot_id=k` in `signers-0-2` for the same signer set (guaranteed by the shared page lookup in `signers-0-xxx.clar` / `signers-1-xxx.clar`).
3. Submit `POST /v2/stackerdb/{S}/signers-0-2/chunks` with the same body `C`, unmodified, to any target node.
4. `RPCPostStackerDBChunkRequestHandler::try_handle_request` → `StackerDBTx::try_replace_chunk` → `SlotMetadata::verify` succeeds (digest only covers `slot_id`,`slot_version`,`data_hash`), the chunk is stored under `signers-0-2`, and the node relays a `StackerDBPushChunk` for `signers-0-2` to the network — all without the attacker ever possessing `S`'s private key.

        &self,
        smart_contract: &QualifiedContractIdentifier,
        slot_desc: &SlotMetadata,
        chunk: &[u8],
    ) -> Result<(), net_error> {
        // Check per-replica chunk-size cap.
        if (chunk.len() as u64) > self.config.chunk_size {
            return Err(net_error::StackerDBChunkTooBig(chunk.len()));
        }

        let slot_validation = self
            .get_slot_validation(smart_contract, slot_desc.slot_id)?
            .ok_or(net_error::NoSuchSlot(
                smart_contract.clone(),
                slot_desc.slot_id,
            ))?;

        if !slot_desc.verify(&slot_validation.signer)? {
            return Err(net_error::BadSlotSigner(
                slot_validation.signer,
                slot_desc.slot_id,
            ));
        }
        if slot_desc.slot_version <= slot_validation.version {
            return Err(net_error::StaleChunk {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
            });
        }
        if slot_desc.slot_version > self.config.max_writes {
            return Err(net_error::TooManySlotWrites {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
                max_writes: self.config.max_writes,
            });
        }
        self.insert_chunk(smart_contract, slot_desc, chunk)
    }
