### Title
`RepositoryImpl#calculateGlobalEnergyLimit` divides by `totalEnergyWeight` guarded only by a no-op `assert`, risking division-by-zero in TVM energy accounting - (File: `actuator/src/main/java/org/tron/core/vm/repository/RepositoryImpl.java`)

### Summary
`RepositoryImpl.calculateGlobalEnergyLimit` divides `energyWeight * totalEnergyLimit` by `totalEnergyWeight`, guarding only with a Java `assert` statement, which is compiled out and disabled at runtime unless the JVM is started with `-ea` (not the case in production nodes). This mirrors the reported Astaria pattern where a fee ratio denominator that can be zero is guarded by nothing effective, leading to a division-by-zero exception on the reachable code path.

### Finding Description
`RepositoryImpl#calculateGlobalEnergyLimit` reads `totalEnergyWeight` from `DynamicPropertiesStore` and immediately divides by it, with only an `assert totalEnergyWeight > 0;` statement as protection: [1](#0-0) 

By contrast, the analogous method `EnergyProcessor#calculateGlobalEnergyLimit` (and `BandwidthProcessor#calculateGlobalNetLimit`) explicitly checks `totalEnergyWeight <= 0` and returns `0` before falling back to the same `assert`: [2](#0-1) 

The `assert` keyword in Java is a no-op unless assertions are explicitly enabled with `-ea` at JVM startup, which is not standard for production `FullNode`/`java-tron` deployments. This means the effective guard that exists in `EnergyProcessor` (`if (dynamicPropertiesStore.allowNewReward() && totalEnergyWeight <= 0) return 0;`) is absent from `RepositoryImpl`, which is the version used inside TVM contract execution via the `Repository` interface (`calculateGlobalEnergyLimit` declared in `Repository.java`, implemented in `RepositoryImpl.java`): [3](#0-2) 

This is directly analogous to the Astaria `getBuyoutFee` bug: a denominator (`buyoutFeeDenominator` there, `totalEnergyWeight` here) that is expected to always be positive but is only weakly protected, resulting in an unhandled `ArithmeticException: / by zero` when the value is actually zero.

### Impact Explanation
If `totalEnergyWeight` reaches `0` (e.g., a chain state where no account currently has frozen balance for energy — plausible early-chain state, after mass unfreezing under Stake 1.0/2.0 transitions, or any bug that decrements the counter to zero via `addTotalEnergyWeight`/`saveTotalEnergyWeight`), any code path invoking `RepositoryImpl#calculateGlobalEnergyLimit` during TVM execution throws an uncaught `ArithmeticException`. Because this function is reached during the execution of any smart-contract-calling transaction (`TriggerSmartContract`), an unprivileged transaction broadcaster could cause repeated node execution failures during block application whenever such a call is processed, since it executes inside the deterministic transaction/VM execution path rather than validation. This can manifest as unexpected transaction execution failures or crash paths in the energy-accounting logic, which is normally expected to gracefully degrade to `0`, not throw.

### Likelihood Explanation
Likelihood depends on whether `totalEnergyWeight` can practically become `0` on a live network. On an established public/mainnet-like network, this is unlikely because SRs/witnesses generally have non-zero frozen balances. However, on a fresh/private/test network shortly after genesis, or in scenarios following complete migration/unfreezing under Stake 2.0 semantics before new freezes are recorded, `totalEnergyWeight` can legitimately be `0`. The fact that the sibling implementation in `EnergyProcessor` explicitly added a defensive `<= 0` check strongly suggests this exact zero-weight condition was previously identified as reachable and was patched there but not in `RepositoryImpl`.

### Recommendation
Add the same explicit `totalEnergyWeight <= 0` (and equivalently a `totalEnergyLimit <= 0`, if applicable) guard to `RepositoryImpl#calculateGlobalEnergyLimit` that already exists in `EnergyProcessor#calculateGlobalEnergyLimit`/`calculateGlobalEnergyLimitV2`, returning `0` instead of relying on the disabled `assert` statement. This mirrors the sherlock-audit fix recommendation of validating fee/weight denominators before use rather than trusting they are always non-zero.

### Proof of Concept
1. Bring `totalEnergyWeight` dynamic property to `0` (via genesis/fresh state, or a sequence of unfreeze operations reducing it to zero, as seen in `UnfreezeBalanceProcessor#execute`, which calls `repo.addTotalEnergyWeight(-unfreezeBalance / TRX_PRECISION)`): [4](#0-3) 
2. Have an account with `AllFrozenBalanceForEnergy >= TRX_PRECISION` (frozen energy balance) trigger a smart contract call (`TriggerSmartContract`), which invokes VM execution paths that call into `Repository#calculateGlobalEnergyLimit`.
3. Because `totalEnergyWeight == 0`, the division `... / BigInteger.valueOf(totalEnergyWeight)` (or the non-hardened `totalEnergyLimit / totalEnergyWeight`) throws `ArithmeticException: / by zero` at runtime, since the `assert totalEnergyWeight > 0;` line does not execute (assertions disabled by default).

Note: I was not able to fully trace every call site that ultimately invokes `RepositoryImpl#calculateGlobalEnergyLimit` from `ContractState.java`/`VMActuator.java` within the available search budget, nor confirm definitively that mainnet operational conditions can drive `totalEnergyWeight` to exactly zero in practice; this should be verified with a live/testnet reproduction before treating severity as confirmed High.

  public long calculateGlobalEnergyLimit(AccountCapsule accountCapsule) {
    long frozeBalance = accountCapsule.getAllFrozenBalanceForEnergy();
    if (frozeBalance < TRX_PRECISION) {
      return 0;
    }
    long energyWeight = frozeBalance / TRX_PRECISION;
    long totalEnergyLimit = getDynamicPropertiesStore().getTotalEnergyCurrentLimit();
    long totalEnergyWeight = getDynamicPropertiesStore().getTotalEnergyWeight();

    assert totalEnergyWeight > 0;

    if (hardenResourceCalculation()) {
      return BigInteger.valueOf(energyWeight)
          .multiply(BigInteger.valueOf(totalEnergyLimit))
          .divide(BigInteger.valueOf(totalEnergyWeight))
          .longValueExact();
    }
    return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
  }

  public long calculateGlobalEnergyLimit(AccountCapsule accountCapsule) {
    long frozeBalance = accountCapsule.getAllFrozenBalanceForEnergy();
    if (dynamicPropertiesStore.supportUnfreezeDelay()) {
      return calculateGlobalEnergyLimitV2(frozeBalance);
    }
    if (frozeBalance < TRX_PRECISION) {
      return 0;
    }

    long totalEnergyLimit = dynamicPropertiesStore.getTotalEnergyCurrentLimit();
    long totalEnergyWeight = dynamicPropertiesStore.getTotalEnergyWeight();
    if (dynamicPropertiesStore.allowNewReward() && totalEnergyWeight <= 0) {
      return 0;
    } else {
      assert totalEnergyWeight > 0;
    }
    if (hardenCalculation()) {
      return calculateGlobalLimitV1(frozeBalance, totalEnergyLimit, totalEnergyWeight);
    }
    long energyWeight = frozeBalance / TRX_PRECISION;
    return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
  }
