Based on the investigation, I found a structurally analogous issue in the legacy vote-processing path of java-tron.

### Title
Duplicate witness entries in `VoteWitnessContract.votes` are not deduplicated in `VoteWitnessActuator`, unlike the VM equivalent - ([File: actuator/src/main/java/org/tron/core/actuator/VoteWitnessActuator.java])

### Summary
`VoteWitnessActuator`, which processes a plain signed `VoteWitnessContract` transaction from any account holding TRX power, iterates the `votes` list and pushes every `Vote` entry into the account's and witness's accounting structures without checking whether the same witness address already appears earlier in the same list [1](#0-0) . In `countVoteAccount`, each `Vote` in `voteContract.getVotesList()` is applied individually via `votesCapsule.addNewVotes(...)` and `accountCapsule.addVotes(...)`, again with no merging or duplicate check [2](#0-1) .

This is directly analogous to the reported bug class: pushing new entries (reward tokens / votes) into a list keyed by an address without checking for a pre-existing duplicate entry.

### Finding Description
Notably, java-tron's own TVM-native implementation of the same feature — `VoteWitnessProcessor` (used when voting is triggered from within a smart contract) — explicitly recognizes and fixes this class of problem: it builds a `Map<ByteString, Long> voteMap` and merges vote counts for the same witness address before applying them, with the comment "merge vote for same witness" [3](#0-2) . The legacy `VoteWitnessActuator.validate()` only sums the vote counts across all entries to check against `tronPower` [4](#0-3) , but `countVoteAccount()` does not perform the same merge — it applies `addVotes`/`addNewVotes` once per list entry, meaning duplicate witness addresses in a single `VoteWitnessContract` transaction are not consolidated into a single ledger entry the way the VM path does.

The existing unit test `vote1WitnssOneMoreTiems` demonstrates this: a single transaction lists the same witness 30 times with `voteCount=1` each, and the total tallied witness vote count becomes `10 + 30 = 40` [5](#0-4) . This proves the sum-based tally is achievable, but does not confirm whether the underlying `accountCapsule`/`votesCapsule` internal list ends up with 30 separate `Vote` entries for the same witness (unlike the VM path, which is guaranteed to produce exactly one merged entry per witness). I was unable to fully inspect `AccountCapsule.addVotes` / `VotesCapsule.addNewVotes` internals within the available tool budget to confirm whether they append or merge by key, so this specific mechanical detail is unverified.

### Impact Explanation
If duplicate witness entries are stored as separate list items rather than merged by witness address, any downstream logic that iterates `accountCapsule.getVotesList()` or `votesCapsule.getNewVotes()` assuming one entry per witness (e.g., reward/withdrawal accounting in `MortgageService`, or maintenance-cycle vote tallying) could double-process the same witness, leading to incorrect reward distribution or vote bookkeeping. This mirrors the original report's core concern: unchecked duplicate entries causing miscalculation of rewards/shares for other participants.

### Likelihood Explanation
Low-to-medium likelihood: it only manifests if a user deliberately (or a wallet bug) constructs a `VoteWitnessContract` with repeated witness addresses in the `votes` list, which is trivially achievable by any transaction broadcaster since there is no validation rejecting duplicates.

### Recommendation
Add duplicate-detection/merging logic to `VoteWitnessActuator.validate()` and `countVoteAccount()` analogous to what `VoteWitnessProcessor` already does (merge vote counts per witness address using a map before persisting), or explicitly reject transactions containing duplicate witness addresses in the `votes` list.

### Proof of Concept
1. Construct a `VoteWitnessContract` with `votes` containing the same `witnessCandidate` address N times, each with `voteCount = 1` (as done in `getRepeateContract` in the test suite) [6](#0-5) .
2. Submit via `VoteWitnessActuator.validate()` + `execute()`. Validation only checks `sum <= tronPower` and does not reject duplicates [1](#0-0) .
3. `countVoteAccount` applies each of the N duplicate `Vote` entries independently to `accountCapsule` and `votesCapsule` [2](#0-1) , unlike the merged behavior guaranteed by `VoteWitnessProcessor` for the TVM path.

*Caveat: full confirmation that this results in incorrect on-chain state (vs. correctly-summed final storage) would require inspecting `AccountCapsule.addVotes`/`VotesCapsule.addNewVotes` implementations directly, which I was unable to retrieve within the available search budget.*

  private Any getRepeateContract(String address, String voteaddress, Long value, int times) {
