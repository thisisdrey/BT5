### Title
Per-connection stake-weighted stream quota floors let many small-stake connections collectively exceed the intended staked stream budget - (File: streamer/src/nonblocking/stream_throttle.rs)

### Summary
`StakedStreamLoadEMA::available_load_capacity_in_throttling_duration` computes each staked connection's per-interval stream quota independently as `max_staked_load_in_throttling_window * stake / total_stake`, but floors this value at `max_unstaked_load_in_throttling_window + 1` for *every* staked connection regardless of its true stake share [1](#0-0) . This mirrors the PoolTogether `DrawManager` bug where independently-computed reward "fractions" for multiple participants are never checked to sum to ≤ 1.0 against the shared reserve — here, per-connection quota "fractions" of the shared `max_staked_load_in_throttling_window` budget are never normalized to sum to the total budget.

### Finding Description
The QUIC stake-weighted QoS server enforces a global staked-stream budget, `max_staked_load_in_throttling_window`, meant to bound total staked stream throughput per `STREAM_THROTTLING_INTERVAL` [2](#0-1) . Each connection is allotted a quota independently via:

```rust
self.max_staked_load_in_throttling_window
    .saturating_mul(stake)
    .checked_div(total_stake)
    .unwrap_or(self.max_unstaked_load_in_throttling_window + 1)
    .max(self.max_unstaked_load_in_throttling_window + 1)
``` [3](#0-2) 

The `.max(max_unstaked_load_in_throttling_window + 1)` guarantees every staked connection at least `max_unstaked_load_in_throttling_window + 1` streams per throttling interval, even when its proportional stake share would otherwise allot far less. This per-connection floor is a fixed "fraction" that is never validated against the sum of all other connections' floors — exactly the same class of bug as the PoolTogether report, where independently-computed reward fractions (each individually reasonable) are never checked to sum to ≤ 1.0 of the shared reserve.

Because the server can admit up to `max_staked_connections` distinct staked connections (bounded by `SwQosConfig::max_staked_connections`, default `DEFAULT_MAX_STAKED_CONNECTIONS`) [4](#0-3) , an attacker controlling many low-stake validator identities (or many connections admitted via `try_add_connection`'s staked-table logic) can each be granted the floor quota. The total streams admitted in a throttling interval is then `num_staked_connections * (max_unstaked_load_in_throttling_window + 1)`, which can vastly exceed the intended `max_staked_load_in_throttling_window` budget once the number of low-stake connections is large — the sum of the individual quotas is never capped to the shared budget.

### Impact Explanation
This allows grossly underpriced/over-quota admission of staked QUIC streams (transaction packets) into the TPU pipeline: the per-connection quotas collectively evade the stake-weighted QoS budget meant to prioritize genuinely high-stake senders and bound total staged load. This is a QoS-evasion condition in the unprivileged-facing QUIC streamer (any client that can obtain even minimal stake, or exploit the treat-as-unstaked path inconsistently, can multiply its effective quota by opening more distinct staked connections up to `max_staked_connections`), consistent with the "QoS evasion" / "grossly underpriced pre-fee work" acceptance criteria for this scan.

### Likelihood Explanation
Likelihood is constrained by needing many distinct staked identities/connections (bounded by `max_staked_connections`) and stake-weighted admission is only exploitable when the fixed floor exceeds the true proportional share, i.e., during periods with many low-stake connections relative to `max_streams_per_ms`. It requires no privileged validator/operator role — a staked but low-stake client is sufficient to trigger the floor — but scaling the exploit to a large aggregate over-quota requires controlling or coordinating a nontrivial number of low-stake connections/pubkeys.

### Recommendation
Ensure the sum of per-connection quotas cannot exceed `max_staked_load_in_throttling_window`: e.g., track total streams already allotted this window and clamp remaining allotments accordingly, or normalize each connection's floor-adjusted quota by the count of currently active staked connections receiving the floor, rather than applying `.max(max_unstaked_load_in_throttling_window + 1)` unconditionally to every connection irrespective of aggregate outstanding allotments.

### Proof of Concept
Existing unit tests already demonstrate the floor behavior in isolation, confirming the mechanism (not the aggregate multiplication, which follows directly from allowing many connections each hitting the floor): [5](#0-4) 

With `max_staked_load_in_throttling_window = 100` and `max_unstaked_load_in_throttling_window = 20`, a single low-stake connection (`stake=10` of `total_stake=100`) is granted `21` streams instead of its proportional `10` — over double its fair share. Admitting `N` such connections (bounded by `max_staked_connections`, default value not confirmed in this pass due to index truncation of `streamer/src/quic.rs`) yields total staked throughput of `N * 21`, which for `N ≥ 5` already exceeds the intended `100`-stream budget for the interval, i.e., the sum of per-connection "fraction" allotments exceeds `1.0 * max_staked_load_in_throttling_window`.

Note: I was unable to confirm the exact numeric value of `DEFAULT_MAX_STAKED_CONNECTIONS` in `streamer/src/quic.rs` within the available tool budget (the grep only returned a match count, not the constant's value); the multiplicative over-allotment mechanism itself, however, is confirmed directly from the code cited above.
