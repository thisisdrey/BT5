### Title
Unhandled `IndexOutOfBoundsException` from empty `Contract` list in `Manager.pushTransaction` crashes broadcast path - (File: `framework/src/main/java/org/tron/core/db/Manager.java`)

### Summary
`Manager.pushTransaction()` calls `isShieldedTransaction()` and `isExchangeTransaction()` on the raw transaction *before* any structural validation of the contract list is performed. Both helper methods unconditionally call `transaction.getRawData().getContract(0)` with no bounds check. A transaction crafted with zero entries in `raw.contract` (a field that protobuf allows to be empty, analogous to a missing required field in the CVE-2023-37018 ASN.1 message) causes an `IndexOutOfBoundsException` that is not declared or caught anywhere in the call chain, crashing the processing thread.

### Finding Description
`pushTransaction` is the single entry point that all unprivileged transaction broadcasts go through (via `Wallet.broadcastTransaction`/HTTP/gRPC and via `TronNetDelegate.pushTransaction`): [1](#0-0) 

Before the transaction's structure is checked (that check only happens later, inside `processTransaction`, at line 1518), `pushTransaction` calls: [2](#0-1) 

Both `isShieldedTransaction` and `isExchangeTransaction` call `transaction.getRawData().getContract(0)` directly, with no check that `getContractList()` is non-empty:

- `isShieldedTransaction`: `Contract contract = transaction.getRawData().getContract(0);`
- `isExchangeTransaction`: same pattern.

Only much later, inside `processTransaction`, does the code validate the invariant that exactly one contract is present: [3](#0-2) 

By the time this check runs, `isShieldedTransaction`/`isExchangeTransaction` have already been called unconditionally in `pushTransaction` on an attacker-supplied transaction whose `raw.contract` repeated field is empty. Since these are `com.google.protobuf.Message` list accessors, `getContract(0)` on an empty list throws `IndexOutOfBoundsException`, an unchecked `RuntimeException`. This exception type is not part of `pushTransaction`'s declared `throws` clause: [4](#0-3) 

and is not caught by any of its callers. For example `TronNetDelegate.pushTransaction` only catches the checked exceptions declared by `Manager.pushTransaction`: [5](#0-4) 

This is structurally identical to the Open5GS bug class described in CVE-2023-37018: a message that omits a value the code implicitly assumes is always present triggers an unhandled crash condition (there, an assertion; here, an unchecked `IndexOutOfBoundsException`) in a path reachable by any unauthenticated/unprivileged sender.

### Impact Explanation
An uncaught `RuntimeException` thrown from `pushTransaction` propagates up through the broadcast-handling code path. Depending on which thread invokes it (HTTP/gRPC request thread that calls `Wallet.broadcastTransaction` → `dbManager.pushTransaction`, or the `pushTransactionQueue` processing thread), an unhandled runtime exception can terminate the request-processing/queue thread, disrupt the transaction pool processing loop, and cause repeated failures/service degradation for the node — a remotely triggerable denial-of-service against the transaction broadcast path, matching the "node crash / API the node can no longer serve" impact bar.

### Likelihood Explanation
This is trivially reachable by any unprivileged client that can broadcast a transaction: an attacker only needs to submit a `Transaction` protobuf whose `raw.contract` field is empty (zero contracts) via `BroadcastTransaction`. No signature over a valid contract, no special permissions, and no chain state are required to reach the vulnerable code, since the vulnerable calls happen before contract-count and signature validation complete.

### Recommendation
Add an explicit non-empty/size==1 check on `transaction.getRawData().getContractList()` at the very start of `Manager.pushTransaction` (before `isShieldedTransaction`/`isExchangeTransaction`/`isMultiSignTransaction` are invoked), throwing the existing `ContractSizeNotEqualToOneException` (or a `ContractValidateException`) instead of letting an `IndexOutOfBoundsException` escape. Alternatively, harden `isShieldedTransaction`, `isExchangeTransaction`, and `isMultiSignTransaction` themselves to check `getContractList().isEmpty()` first and return `false`/throw a checked exception rather than indexing directly.

### Proof of Concept
1. Construct a `Transaction` protobuf where `raw` is set (with valid `timestamp`/`expiration`/`ref_block` fields to pass earlier structural checks if needed) but `raw.contract` is left empty (no `Contract` entries added).
2. Sign/submit this transaction via the broadcast API (`wallet/broadcasttransaction` HTTP endpoint or gRPC `BroadcastTransaction`), which calls into `Wallet.broadcastTransaction` → `Manager.pushTransaction(trx)`.
3. Inside `pushTransaction`, `isShieldedTransaction(trx.getInstance())` executes `transaction.getRawData().getContract(0)` on the empty list, throwing `IndexOutOfBoundsException`.
4. This unchecked exception is not declared by `pushTransaction` and not caught by any caller in the broadcast path, propagating up and terminating the handling thread — reproducible on every submission of such a transaction.

        return true;
      }

        return false;
