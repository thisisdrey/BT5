### Title
Stack overflow via deeply nested binary/unary expressions in the Go compiler's syntax parser (`cmd/compile/internal/syntax`) - (File: src/cmd/compile/internal/syntax/parser.go)

### Summary
The compiler front-end's expression parser (`binaryExpr` / `unaryExpr`) recurses once per nested operator or unary prefix with no depth limiting, unlike the sibling `go/parser` package which was hardened against exactly this class of bug. A `.go` source file containing a sufficiently long chain of nested unary or binary operators can drive unbounded recursion and crash `go build`/`cmd/compile` with a stack overflow.

### Finding Description
An attacker supplies a `.go` source file (e.g., inside a published module or package that a victim later builds) containing a deeply nested expression such as `a+a+a+a+...` or a long run of unary operators (`----...-a`). When `cmd/compile` parses this file, `p.expr()` calls `p.binaryExpr(nil, 0)` [1](#0-0)  which recurses via `t.Y = p.binaryExpr(nil, tprec)` for each higher-precedence operator encountered, and `unaryExpr` recurses via `x.X = p.unaryExpr()` for each prefix operator [2](#0-1) . Neither function tracks or bounds the recursion depth. This is in stark contrast to `go/parser.parseBinaryExpr`, which explicitly guards against this exact failure mode using `incNestLev`/`decNestLev` and a `maxNestLev` constant (`1e5`), panicking with a clean `bailout` and "exceeded max nesting depth" error instead of overflowing the goroutine stack [3](#0-2) [4](#0-3) . The absence of the equivalent guard in `cmd/compile/internal/syntax/parser.go` means the compiler's own parser has no protective check for this failure mode.

### Impact Explanation
An uncontrolled crash (fatal `runtime: goroutine stack exceeds ... stack overflow`) of `cmd/compile` while compiling attacker-supplied source is a Denial of Service against the build process — a normal victim workflow (`go build`/`go vet`/`go install` on a downloaded module) is what triggers parsing. This falls under the same primitive as the referenced MJS CVE (unbounded recursive-descent parsing of `+`/`-` chains causing stack overflow), and Go itself previously treated this exact defect class in `go/parser` as worth a hardening fix (`maxNestLev`/`incNestLev`), evidenced by the dedicated regression test `TestParseDepthLimit` [5](#0-4) . This would likely be assessed on Go's PUBLIC track as a low/medium-severity DoS in the toolchain, since it crashes the build tool rather than compromising the compiled binary or leaking data.

### Likelihood Explanation
Reachability requires only that a victim run `go build` (or another command that parses source, e.g. `go vet`, `gofmt`-like tools using the compiler's parser) on untrusted or third-party source, which is an ordinary, unprivileged workflow — no special build tags, cgo, or code execution is needed to trigger the crash, only parsing. There is precedent: `test/fixedbugs/issue2615.go` documents a prior, similar parser-stack-overflow bug fixed in the recursive-descent parser for long `if`/`else if` chains [6](#0-5) , and `go/parser` received depth-limiting specifically for expression nesting, confirming this is a recognized, previously-exploited bug class in Go's parsers.

### Recommendation
Add the same nesting-depth tracking used in `go/parser` (an `incNestLev`/`decNestLev` pair with a `maxNestLev` bound, converted to a syntax error via the existing `p.syntaxError`/error-handling path) to `cmd/compile/internal/syntax`'s `binaryExpr` and `unaryExpr` functions, so pathologically deep expressions are rejected with a normal parse error rather than crashing the compiler process.

```go
	var b strings.Builder
	b.WriteString("package p\nvar x = a")
	for i := 0; i < n; i++ {
		b.WriteString("+a")
	}
	src := b.String()

	defer func() {
		if r := recover(); r != nil {
			t.Fatalf("parser crashed/panicked instead of returning a syntax error: %v", r)
		}
	}()

	_, err := syntax.Parse(syntax.NewFileBase("x.go"), strings.NewReader(src), nil, nil, 0)
	// Expected (after fix): a bounded syntax error, e.g. "exceeded max nesting depth".
	// Actual (current code): unbounded recursion in binaryExpr crashes the process
	// with "runtime: goroutine stack exceeds ... stack overflow" (a fatal error,
	// not a recoverable panic), which cannot be caught by defer/recover above and
	// aborts the test binary/build process entirely.
	_ = err
}
```
Expected assertion (post-fix): `err` is a bounded `syntax.Error` mentioning nesting depth, and the test process does not fatally crash. Currently, deep enough input causes an unrecoverable runtime stack-overflow fatal error in the compiler's parser.

```go
// Expression = UnaryExpr | Expression binary_op Expression .
func (p *parser) binaryExpr(x Expr, prec int) Expr {
	// don't trace binaryExpr - only leads to overly nested trace output

	if x == nil {
		x = p.unaryExpr()
	}
	for (p.tok == _Operator || p.tok == _Star) && p.prec > prec {
		t := new(Operation)
		t.pos = p.pos()
		t.Op = p.op
		tprec := p.prec
		p.next()
		t.X = x
		t.Y = p.binaryExpr(nil, tprec)
		x = t
	}
	return x
}
```

```go
// maxNestLev is the deepest we're willing to recurse during parsing
const maxNestLev int = 1e5

func incNestLev(p *parser) *parser {
	p.nestLev++
	if p.nestLev > maxNestLev {
		p.error(p.pos, "exceeded max nesting depth")
		panic(bailout{})
	}
	return p
}

// decNestLev is used to track nesting depth during parsing to prevent stack exhaustion.
// It is used along with incNestLev in a similar fashion to how un and trace are used.
func decNestLev(p *parser) {
	p.nestLev--
}
```

```go
func (p *parser) parseBinaryExpr(x ast.Expr, prec1 int) ast.Expr {
	if p.trace {
		defer un(trace(p, "BinaryExpr"))
	}

	if x == nil {
		x = p.parseUnaryExpr()
	}
	// We track the nesting here rather than at the entry for the function,
	// since it can iteratively produce a nested output, and we want to
	// limit how deep a structure we generate.
	var n int
	defer func() { p.nestLev -= n }()
	for n = 1; ; n++ {
		incNestLev(p)
		op, oprec := p.tokPrec()
		if oprec < prec1 {
			return x
		}
		pos := p.expect(op)
		y := p.parseBinaryExpr(nil, oprec+1)
		x = &ast.BinaryExpr{X: x, OpPos: pos, Op: op, Y: y}
	}
}
```

```go
func TestParseDepthLimit(t *testing.T) {
	if testing.Short() {
		t.Skip("test requires significant memory")
	}
	for _, tt := range parseDepthTests {
		for _, size := range []string{"small", "big"} {
			t.Run(tt.name+"/"+size, func(t *testing.T) {
				n := maxNestLev + 1
				if tt.parseMultiplier > 0 {
					n /= tt.parseMultiplier
				}
				if size == "small" {
					// Decrease the number of statements by 10, in order to check
					// that we do not fail when under the limit. 10 is used to
					// provide some wiggle room for cases where the surrounding
					// scaffolding syntax adds some noise to the depth that changes
					// on a per testcase basis.
					n -= 10
				}

				pre, mid, post := split(tt.format)
				if strings.Contains(mid, "«") {
					left, base, right := split(mid)
					mid = strings.Repeat(left, n) + base + strings.Repeat(right, n)
				} else {
					mid = strings.Repeat(mid, n)
				}
				input := pre + mid + post

				fset := token.NewFileSet()
				_, err := ParseFile(fset, "", input, ParseComments|SkipObjectResolution)
				if size == "small" {
					if err != nil {
						t.Errorf("ParseFile(...): %v (want success)", err)
					}
				} else {
					expected := "exceeded max nesting depth"
					if err == nil || !strings.HasSuffix(err.Error(), expected) {
						t.Errorf("ParseFile(...) = _, %v, want %q", err, expected)
					}
				}
			})
		}
	}
}
```
