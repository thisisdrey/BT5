### Title
Path traversal via `VanityRepository` in server-side backup/restore RPCs bypasses relative-path validation - ([File: internal/gitaly/service/repository/restore_repository.go])

### Summary
`validateRestoreRepositoryRequest` (and the analogous `validateBackupRepositoryRequest`) validate `VanityRepository` with `storage.WithSkipStorageExistenceCheck()`, which causes `configLocator.ValidateRepository` to return `nil` immediately after only checking that `RelativePath` is non-empty, entirely skipping the `storage.ValidateRelativePath` traversal check. Because `VanityRepository.StorageName`/`RelativePath` are later joined directly into backup object keys/filesystem paths by `backup.ManifestLocator`, an attacker-controlled `VanityRepository` containing `../` sequences can make backup reads/writes (manifest, bundle, refs, custom-hooks tar) escape the intended per-repository subtree of the backup bucket/root.

### Finding Description
`validateRestoreRepositoryRequest` calls: [1](#0-0) 

which invokes `configLocator.ValidateRepository` with `SkipStorageExistenceCheck`. In that implementation, the function checks only that `RelativePath` is non-empty, then returns `nil` *before* ever calling `storage.ValidateRelativePath`, which is the actual traversal-prevention logic: [2](#0-1) 

`StorageName` is not checked at all in this path (not even for emptiness), and `RelativePath` is only checked for non-emptiness — no rejection of `..` components.

The unchecked `VanityRepository` is then passed straight through to `backup.Manager.Restore`/`Create` as `RestoreRequest.VanityRepository`: [3](#0-2) 

`backup.ManifestLocator` builds the actual backup storage keys/paths by directly joining `StorageName`/`RelativePath` (and the already-validated `PathPrefix`) with `filepath.Join`/`path.Join`, without any further sanitization: [4](#0-3) [5](#0-4) 

`backup.ValidatePathPrefix` correctly blocks traversal in `PathPrefix`: [6](#0-5) 

but this only covers `PathPrefix`, not `VanityRepository`. Since the `WithSkipStorageExistenceCheck` short-circuit in `configLocator.ValidateRepository` bypasses `storage.ValidateRelativePath` (which is the mechanism used elsewhere, e.g. for the `Repository` field validated without that option, to reject `..` per the tests) entirely for `VanityRepository`, `..`-laden `StorageName`/`RelativePath` values pass validation and are used verbatim to compose backup file paths.

### Impact Explanation
An attacker who can invoke `RestoreRepository`/`BackupRepository` (or the equivalent `gitalybackup` server-side path) for a repository they own can set `VanityRepository.RelativePath` (and/or `StorageName`) to a value containing `../` sequences. Because these values are joined unchecked into the backup sink's manifest/bundle/refs/custom-hooks paths, this allows:
- Reading manifests/bundles belonging to other projects' backups (`Find`/`FindLatest`, cross-tenant backup content disclosure), and
- Writing (during `Create`, which shares the identical unvalidated `VanityRepository` check) manifest/bundle/refs/custom-hooks files outside the intended per-repository directory within the backup root/bucket, potentially overwriting another repository's backup artifacts or, with a local filesystem sink and sufficiently deep traversal, files outside the backup root altogether.

This corresponds to a storage-path-escape / cross-repository data disclosure impact class.

### Likelihood Explanation
Preconditions per the scope are met: the `RestoreRepository`/`BackupRepository` RPCs must be reachable with server-side backups configured (`s.backupSink`/`s.backupLocator` set), which is the intended production configuration for server-side backups, not a non-default hardening flag. The attacker only needs to control the `VanityRepository` field of a request for a repository they nominally own — no elevated privileges are required, and the bug is fully reproducible via a direct gRPC call or `gitalybackup` server-side invocation.

### Recommendation
Do not allow `ValidateRepository`'s `SkipStorageExistenceCheck` path to bypass `storage.ValidateRelativePath`. At minimum, `validateRestoreRepositoryRequest`/`validateBackupRepositoryRequest` should independently validate `VanityRepository.GetRelativePath()` (and `StorageName`) for traversal (e.g., reuse the same clean-relative-path logic as `backup.ValidatePathPrefix`/`storage.ValidateRelativePath`) before passing it to `backup.Manager`.

### Proof of Concept
```go
func TestRestoreRepository_vanityPathTraversal(t *testing.T) {
    // configLocator.ValidateRepository with WithSkipStorageExistenceCheck
    // returns nil for a RelativePath containing traversal sequences.
    vanity := &gitalypb.Repository{
        StorageName:  "default",
        RelativePath: "../../../other-namespace/other-project.git",
    }
    err := locator.ValidateRepository(ctx, vanity, storage.WithSkipStorageExistenceCheck())
    require.NoError(t, err) // BUG: should reject traversal, mirrors ErrRelativePathEscapesRoot
}
```
Equivalent RPC-level PoC: send `RestoreRepositoryRequest{Repository: <owned repo>, VanityRepository: {StorageName: "default", RelativePath: "../../../victim-namespace/victim-project.git"}, BackupId: "...", PathPrefix: ""}` — `manifestPath`/`ManifestLocator.Find` will resolve to `manifests/default/../../../victim-namespace/victim-project.git/<backupID>.toml`, reading/affecting the victim project's backup artifacts instead of the caller's own.

```go
func ValidatePathPrefix(prefix string) error {
	if prefix == "" {
		// Empty prefix is allowed
		return nil
	}

	if filepath.IsAbs(prefix) {
		return fmt.Errorf("%w: must be a relative path", ErrInvalidPathPrefix)
	}

	for _, part := range strings.Split(prefix, "/") {
		if part == "" || strings.Trim(part, ".") == "" {
			return fmt.Errorf("%w: must be a clean relative path without traversal", ErrInvalidPathPrefix)
		}
	}

	return nil
}
```
