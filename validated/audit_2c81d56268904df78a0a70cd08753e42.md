### Title
Deleting an Account Permanently Burns Funds When the `beneficiary_id` Does Not Exist - (File: `runtime/runtime/src/actions.rs`)

### Summary
`action_delete_account` unconditionally schedules a balance-refund receipt to `delete_account.beneficiary_id` without ever verifying that the beneficiary account exists. If the beneficiary account is missing (typo, never created, or since deleted), the refund receipt fails validation and the entire account balance is permanently burned instead of being locked or returned to the sender — a stronger, unrecoverable version of the "transfer to an unusable address" bug class described in the external report.

### Finding Description
`action_delete_account` reads the account's balance and pushes a refund receipt to the caller-supplied `beneficiary_id` with no existence check on that id: [1](#0-0) 

The only validation performed on `beneficiary_id` anywhere in the stack is a syntactic `AccountId` format check (documented in `docs/RuntimeSpec/Actions.md`), never an existence check: [2](#0-1) 

The generated receipt (`Receipt::new_balance_refund`) is a system-originated ("refund") receipt. When such a receipt is applied to a receiver that does not exist, `check_account_existence` explicitly disallows implicit-account creation for refunds (`is_refund` forces `implicit_account_creation_eligible = false`): [3](#0-2) [4](#0-3) 

so the Transfer action inside the refund fails with `AccountDoesNotExist`. Crucially, the runtime treats a failed refund receipt as burnt tokens rather than as a bounce-back or a blocked/pending state: [5](#0-4) 

This is the same root-cause pattern as the reported bug (`transfer()` in `BeraBitcoin.sol` omits validation of the recipient before moving funds), except that here nearcore's design goes further: instead of merely locking the funds at an unusable/blacklisted address, the funds are destroyed outright (burned), because refund receipts cannot recreate an account and any failure on a refund is defined as burn.

### Impact Explanation
Any unprivileged account holder who submits a `DeleteAccount` action (directly, or via a smart contract building a batch promise, or via a NEP-366 meta-transaction/`Delegate` action) with a `beneficiary_id` that does not currently exist on chain permanently and irrecoverably destroys their entire remaining account balance. There is no local simulation/dry-run requirement forcing wallets to check beneficiary existence beforehand, and a beneficiary that exists at transaction-construction time can be deleted by a third party before the `DeleteAccount` receipt executes (a race that a normal, unprivileged user cannot fully control), turning an intended transfer into a total loss of funds. This satisfies the "permanent freezing/loss of funds" impact criterion for an unprivileged-signer analog in action execution and refunds.

### Likelihood Explanation
Reachable purely with an ordinary, unprivileged transaction/action (`DeleteAccountAction` with attacker/user-chosen `beneficiary_id`), with no special permissions, hooks, or validator/operator collusion required. The failure path is deterministic: any `beneficiary_id` that does not resolve to an existing account at execution time (typo, deleted, or never created) reliably triggers the burn path. The only mitigating factor is that this requires either user error (typo/staleness) or a beneficiary account being deleted in a race window, so it is not exploitable for arbitrary third-party theft, but it is a straightforward, easily triggered fund-loss bug for the signer's own funds.

### Recommendation
Before scheduling the `DeleteAccount` refund receipt (or before executing the `DeleteAccount` action), verify that `beneficiary_id` corresponds to an existing account in `state_update` (an extra trie lookup, consistent with existing account-existence checks used elsewhere in `actions.rs`/`check_account_existence`). If the beneficiary account does not exist, the action should fail with an explicit `ActionErrorKind` (e.g., a new `BeneficiaryAccountDoesNotExist`) rather than silently deleting the source account and burning the balance. Alternatively, disallow implicit-account creation exception removal for this specific refund type only if a corresponding NEP change is acceptable, or require any implicit `beneficiary_id` to be pre-verified/created similarly to how `Transfer` handles implicit account creation for ordinary (non-refund) receipts.

### Proof of Concept
1. Create account `alice.near` with a non-zero balance.
2. From `alice.near`, submit a transaction with a single `DeleteAccount { beneficiary_id: "nonexistent123.near" }` action, where `nonexistent123.near` has never been created (or was deleted between construction and execution of the receipt).
3. Runtime executes `action_delete_account`, which unconditionally removes `alice.near` and enqueues `Receipt::new_balance_refund(&"nonexistent123.near", account_balance)` [1](#0-0) .
4. The refund receipt (predecessor is system) is applied against `nonexistent123.near`; `check_account_existence` rejects it (`AccountDoesNotExist`) because refunds cannot implicitly create accounts [4](#0-3) .
5. Because `result.result` is `Err` and `receipt.predecessor_id().is_system()` is true, the runtime adds the entire deposited amount to `stats.balance.other_burnt_amount` [5](#0-4) , permanently removing it from `alice.near`'s control with no recipient ever receiving it — an irreversible loss, worse than the "locked at recipient" scenario from the referenced report.
