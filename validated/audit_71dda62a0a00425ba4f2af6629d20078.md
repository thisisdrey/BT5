### Title
Missing `AllowTvmCompatibleEvm`/legacy-contract check in `TransferAssetActuator` allows TRC10 tokens to be sent to version-1 smart contracts, bypassing the governance-controlled restriction enforced on TRX transfers - (File: `actuator/src/main/java/org/tron/core/actuator/TransferAssetActuator.java`)

### Summary
`TransferActuator.validate()` (plain TRX transfers) enforces two governance-controlled restrictions before allowing a transfer to a contract account: (1) `ForbidTransferToContract`, and (2) when `AllowTvmCompatibleEvm` is enabled, a specific block on sending value to legacy "version 1" smart contracts, directing callers to use `TriggerSmartContract` instead. `TransferAssetActuator.validate()` (TRC10 asset transfers) only implements the first restriction and omits the second, so the exact same governance-approved "don't send value directly to a version-1 contract" rule can be trivially bypassed by using a TRC10 asset transfer instead of a TRX transfer.

### Finding Description
In `TransferActuator.java`, `validate()` contains: [1](#0-0) 

This shows two independent governance checks gating value transfers to contract accounts: the `ForbidTransferToContract` flag and, when `AllowTvmCompatibleEvm` is on, an explicit rejection of transfers to contracts whose `getContractVersion() == 1`.

`TransferAssetActuator.validate()`, which handles TRC10 token transfers (`TransferAssetContract`), only re-implements the first check: [2](#0-1) 

There is no corresponding check against `dynamicStore.getAllowTvmCompatibleEvm()` and `ContractCapsule.getContractVersion()` in this actuator. The `execute()` method then unconditionally credits the asset balance to the contract account: [3](#0-2) 

This is the same missing-restriction pattern as the referenced Aave Lens finding: one transfer/value-moving code path (`TransferContract`) enforces a governance-mandated safety gate, while a sibling path performing an equivalent operation (`TransferAssetContract`) omits it entirely, letting an unprivileged transaction sender bypass the intended restriction.

### Impact Explanation
The `AllowTvmCompatibleEvm`/version-1 restriction exists specifically because version-1 contracts are not expected to correctly receive value transfers outside of `TriggerSmartContract` semantics under EVM-compatible mode (their fallback/receive handling and value-accounting assumptions differ). Because `TransferAssetActuator` does not enforce this check, any unprivileged account holding a TRC10 asset can send it directly to a version-1 contract even after governance has enabled `AllowTvmCompatibleEvm` specifically to prevent this class of unsafe transfer. Depending on the target contract's logic, this can result in TRC10 token balances becoming stranded/inaccessible in a contract that has no code path to account for or return them (permanent freezing of the sender's funds), or in inconsistent internal accounting for the contract if it assumes it can only receive value via `TriggerSmartContract`.

### Likelihood Explanation
High reachability: any account holding the asset can construct a `TransferAssetContract` transaction (a normal, unprivileged, broadcastable transaction type) targeting any version-1 contract address. No special permissions, timing, or cooperation from other actors are required, and the condition (`AllowTvmCompatibleEvm == 1` and a version-1 contract existing) is an ordinary, expected mainnet configuration state once that proposal is activated.

### Recommendation
Add the same `AllowTvmCompatibleEvm`/`getContractVersion() == 1` check present in `TransferActuator.validate()` to `TransferAssetActuator.validate()`, rejecting `TransferAssetContract` transactions whose `toAddress` is a version-1 smart contract when `AllowTvmCompatibleEvm` is enabled, mirroring the TRX-transfer restriction: [4](#0-3) 

### Proof of Concept
1. Governance activates the `ALLOW_TVM_COMPATIBLE_EVM` proposal (`ProposalService` sets `saveAllowTvmCompatibleEvm(1)`, see [5](#0-4) ), and a version-1 contract exists on chain (deployed while `allowTvmCompatibleEvm` was active, see version tagging in `VMActuator.create()`, [6](#0-5) ).
2. An attacker/unprivileged holder of a TRC10 token submits a `TransferAssetContract` transaction with `toAddress` set to that version-1 contract address and a non-zero token amount.
3. `TransferAssetActuator.validate()` only checks `ForbidTransferToContract`; since that flag is independent from `AllowTvmCompatibleEvm`, the transaction passes validation even though an equivalent `TransferContract` (plain TRX) transaction to the same address would be rejected with "Cannot transfer TRX to a smartContract which version is one."
4. `execute()` credits the TRC10 balance to the version-1 contract account, which — unlike TRX handled by `TriggerSmartContract` — has no code path to process or return the received asset, resulting in the transferred TRC10 tokens becoming permanently stuck in the contract.
