## Title
Missing RequestsHash presence check allows a post-Prague block header to omit the EIP-7685 requestsHash field - (`consensus/beacon/consensus.go`)

### Summary
Geth's PoS header validator (`Beacon.verifyHeader`) explicitly checks for the presence/absence of fork-gated header fields for Shanghai (`WithdrawalsHash`), Cancun (`ExcessBlobGas`, `BlobGasUsed`, `ParentBeaconRoot`), and Amsterdam (`BlockAccessListHash`, `SlotNumber`), but contains **no equivalent check for Prague's `RequestsHash` field**. [1](#0-0)  This is the same bug class fixed in Besu via `RequestsHashPresentValidationRule` (besu-eth/besu PR #10891).

### Finding Description
EIP-7685 requires every post-Prague block header to carry a `requestsHash` field, using `EmptyRequestsHash` when there are no execution-layer requests. In `verifyHeader`, the fork-conditional checks cover Shanghai, Cancun, and Amsterdam fields:

```go
// Verify existence / non-existence of withdrawalsHash.
shanghai := chain.Config().IsShanghai(header.Number, header.Time)
if shanghai && header.WithdrawalsHash == nil { ... }
...
// Verify the existence / non-existence of Amsterdam-specific header fields
amsterdam := chain.Config().IsAmsterdam(header.Number, header.Time)
if amsterdam { ... } else { ... }
return nil
``` [2](#0-1) 

There is no corresponding `prague := chain.Config().IsPrague(...)` block enforcing `header.RequestsHash != nil` after Prague or `== nil` before it. The struct itself documents `RequestsHash` as an optional post-Prague field: [3](#0-2) 

The only other place `RequestsHash` is touched during import is `BlockValidator.ValidateState`, which is a post-execution check comparing the header's hash against locally computed request data — but it only fires a validation error when `header.RequestsHash != nil` (mismatch case) or when `header.RequestsHash == nil` but `res.Requests != nil` (unexpected requests present). If a Prague block simply has no requests and the header carries `RequestsHash == nil` instead of `EmptyRequestsHash`, both `header.RequestsHash` and `res.Requests` are nil, so the check silently passes:

```go
if header.RequestsHash != nil {
    reqhash := types.CalcRequestsHash(res.Requests)
    if reqhash != *header.RequestsHash { ... }
} else if res.Requests != nil {
    return errors.New("block has requests before prague fork")
}
``` [4](#0-3) 

So a maliciously or buggy-crafted post-Prague header that omits `requestsHash` entirely (leaves it `nil`) and carries no execution requests passes both `verifyHeader` and `ValidateState` unmodified.

### Impact Explanation
This breaks the equality that every post-Prague header must contain `requestsHash` (EIP-7685). A block header omitting the field would be computed with a different RLP encoding/hash than a spec-compliant client (which would reject the header, or a producer would always populate `EmptyRequestsHash`), creating a **cross-client consensus divergence**: a header lacking `requestsHash` is accepted by this Geth build while a strictly spec-compliant/other client implementation that enforces field presence per fork would reject it (or vice versa, depending on which side is stricter). This maps to the "Critical — consensus split" / "High — persistence divergence" categories, matching the referenced Besu advisory's characterization ("Severity: Catastrophic, Probability: Remote").

### Likelihood Explanation
Requires a block producer/miner (or malicious peer relaying a header) to build a post-Prague header with `RequestsHash` unset while including no requests, and requires no other validation layer to reject the header before/at import — the code paths above show no such rejection exists in `verifyHeader` or `ValidateState`. Likelihood is low (needs a non-conforming header producer) but the consequence, if triggered on mainnet, is a deterministic acceptance vs. rejection divergence across implementations.

### Recommendation
Add a Prague fork-gated existence check inside `Beacon.verifyHeader`, mirroring the Shanghai/Cancun/Amsterdam pattern:
```go
prague := chain.Config().IsPrague(header.Number, header.Time)
if prague && header.RequestsHash == nil {
    return errors.New("missing requestsHash")
}
if !prague && header.RequestsHash != nil {
    return fmt.Errorf("invalid requestsHash: have %x, expected nil", *header.RequestsHash)
}
```
placed in `consensus/beacon/consensus.go`, near the existing Amsterdam block. [5](#0-4) 

### Proof of Concept
1. Construct a post-Prague block header with `Difficulty = 0`, all required fields set per fork, but leave `RequestsHash = nil`, and ensure the block body contains no deposit/withdrawal/consolidation requests (so `res.Requests` is `nil` after execution).
2. Call `Beacon.VerifyHeader` (→ `verifyHeader`) on this header — observe it returns `nil` (no error), despite EIP-7685 requiring `requestsHash` to be present (as `EmptyRequestsHash`) for every post-Prague header.
3. Insert the block via `BlockChain.InsertChain`; `BlockValidator.ValidateState` (`core/block_validator.go:176-184`) also passes because both `header.RequestsHash` and `res.Requests` are `nil`.
4. Compare against the genesis-block helper `toBlockWithRoot`, which correctly always sets `head.RequestsHash = &types.EmptyRequestsHash` when `IsPrague` [6](#0-5)  — demonstrating the codebase's own convention that `RequestsHash` must never be `nil` post-Prague, a convention not enforced by header validation for blocks received from peers or produced by non-standard software.
