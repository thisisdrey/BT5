### Title
Fetch error misclassification lets a malicious remote corrupt reference state via quarantine bypass in `FetchRemote` - ([File: internal/gitaly/service/repository/fetch_remote.go])

### Summary
`fetchRemoteAtomic` treats any `git-fetch` failure that produces empty `stderr` and an error string equal to `"exit status 1"` as a benign "some references failed to update" condition, and unconditionally proceeds to parse `stdout`, queue reference updates, migrate the quarantine directory, and commit the updates — mirroring the reported `StakeVault.leave()` pattern where a caught revert is treated as a harmless failure and the code proceeds as if the risky operation had succeeded.

### Finding Description
`FetchRemote` runs `git-fetch --dry-run --porcelain` into a quarantine directory so that reference updates can be applied atomically afterward via `git-update-ref(1)`: [1](#0-0) 

When the dry-run fetch itself errors, the handler does not halt processing unless `stderr` is non-empty or the error text differs from the generic `"exit status 1"`. It explicitly documents the assumption that such failures are only failed reference updates that can be safely ignored while still trusting the emitted porcelain `stdout`: [2](#0-1) 

Execution then continues to scan `stdout`, queue reference updates from it, migrate the quarantine directory into the main object store, and commit the reference transaction, all based on the assumption that the tolerated error was benign: [3](#0-2) 

This is the exact bug class from the report: an operation that is expected to either fully succeed or fully (and safely) fail is instead handled by a heuristic "catch" that assumes a specific, narrow failure mode (only some ref updates failed) whenever the observable signals (empty stderr, generic exit code) match — but those same signals can also occur for unrelated failure modes (a remote that hangs, is killed, sends truncated/corrupt data, or otherwise dies non-gracefully without writing to stderr). In those cases the code still trusts and applies the porcelain output and migrates the quarantine directory, exactly the same way `StakeVault.leave()` still transferred tokens whenever `stakeManager.leave()` reverted for any reason, not just the intended one.

Because the remote URL and mirror configuration in `FetchRemoteRequest.RemoteParams` are attacker-influenced/user-controlled (this is exactly the "remote URL handling" surface), an attacker controlling the remote endpoint can trigger a `git-fetch` failure that satisfies the empty-`stderr`/`"exit status 1"` heuristic while emitting crafted, incomplete, or inconsistent porcelain `stdout`, causing Gitaly to migrate a quarantine directory and apply reference updates that do not correspond to a genuinely completed fetch.

### Impact Explanation
If the porcelain output does not correspond to a fully successful and complete fetch, references can be updated to point at objects that were incompletely fetched or otherwise inconsistent with the true state of the remote, while Gitaly still reports success (`RepoChanged`/`TagsChanged`). This is a quarantine/atomicity-guarantee bypass on the exact boundary the quarantine mechanism (`internal/git/quarantine`) is meant to protect: objects/refs are supposed to only be migrated into the main repository when the whole operation is known-good. Instead, an ambiguous failure signal is treated as good enough to migrate anyway.

### Likelihood Explanation
`FetchRemote` is a standard mutator RPC used for repository mirroring/import and is driven by request-supplied remote parameters, so a caller-configured or attacker-controlled remote endpoint is a very plausible way to influence this code path with a rejection strategy of causing `git-fetch` to exit non-gracefully with empty `stderr`.

### Recommendation
Do not conflate "some references failed to update" with "any failure that happens to have empty stderr and exit status 1." Only tolerate `git-fetch` errors when the porcelain output can be independently proven complete and consistent (e.g., verify the fetch process terminated normally and produced a fully-formed status stream), and otherwise abort before calling `quarantineDir.Migrate` and committing reference updates — mirroring the report's recommendation to remove speculative error tolerance rather than trying to interpret ambiguous failure states as safe.

### Proof of Concept
1. Configure a `FetchRemoteRequest` pointing `RemoteParams.Url` at an attacker-controlled Git server.
2. Have the malicious server begin responding to the fetch as normal, then abruptly terminate the connection/process after emitting partial, crafted porcelain-format lines to stdout but before writing anything to stderr, such that the client-side `git-fetch` process exits with a bare `exit status 1`.
3. Observe that `fetchRemoteAtomic` treats this as a benign partial-failure case (`errMsg == ""` and `err.Error() == "exit status 1"`), proceeds to queue reference updates from the crafted `stdout`, migrates the quarantine directory, and commits the updates rather than aborting the operation. 	// Parse stdout to identify required reference updates. Reference updates are queued to the
	// respective updater based on type.
	scanner := gitcmd.NewFetchPorcelainScanner(&stdout, objectHash)
	for scanner.Scan() {
		status := scanner.StatusLine()

		switch status.Type {
		// Failed and unchanged reference updates do not need to be applied.
		case gitcmd.RefUpdateTypeUpdateFailed, gitcmd.RefUpdateTypeUnchanged:
		// Queue pruned references in a separate transaction to avoid F/D conflicts.
		case gitcmd.RefUpdateTypePruned:
			if err := prunedUpdater.Delete(git.ReferenceName(status.Reference)); err != nil {
				return false, false, fmt.Errorf("queueing pruned ref for deletion: %w", err)
			}
			referencesUpdated = true
		// Queue all other reference updates in the same transaction.
		default:
			if err := refUpdater.Update(git.ReferenceName(status.Reference), status.NewOID, status.OldOID); err != nil {
				return false, false, fmt.Errorf("queueing ref to be updated: %w", err)
			}
			referencesUpdated = true

			// While scanning reference updates, check if any tags changed.
			if wereTagsChanged(status) {
				tagsChanged = true
			}

			// While scanning reference updates, check if repo was changed.
			if changeTypes[status.Type] {
				repoChanged = true
			}
		}
	}
	if scanner.Err() != nil {
		return false, false, fmt.Errorf("scanning fetch output: %w", scanner.Err())
	}

	// Prepare pruned references in separate transaction to avoid F/D conflicts.
	if err := prunedUpdater.Prepare(); err != nil {
		return false, false, fmt.Errorf("preparing reference prune: %w", err)
	}

	// Commit pruned references to complete transaction and apply changes.
	if err := prunedUpdater.Commit(); err != nil {
		return false, false, fmt.Errorf("committing reference prune: %w", err)
	}

	// Prepare the remaining queued reference updates.
	if err := refUpdater.Prepare(); err != nil {
		return false, false, fmt.Errorf("preparing reference update: %w", err)
	}

	// Before committing the remaining reference updates, fetched objects must be migrated out of
	// the quarantine directory.
	if err := quarantineDir.Migrate(ctx); err != nil {
		return false, false, fmt.Errorf("migrating quarantined objects: %w", err)
	}

	// Commit the remaining queued reference updates so the changes get applied.
	if err := refUpdater.Commit(); err != nil {
		return false, false, fmt.Errorf("committing reference update: %w", err)
	}
