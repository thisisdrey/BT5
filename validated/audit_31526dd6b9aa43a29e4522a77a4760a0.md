### Title
Positions with debt below `2 * debtFloorInUsd` can never be liquidated — `maxLiquidable` cap makes the "repay-in-full" escape unreachable - (File: contracts/Pool.sol)

### Summary
`Pool.liquidate` enforces two mutually exclusive constraints on the repaid amount: (1) `amountToRepay_ / debtBalance ≤ maxLiquidable` (initialized to `0.5e18`), and (2) if `debtFloorInUsd > 0`, the post-liquidation remaining debt must be either `0` or `≥ debtFloorInUsd`. Because `maxLiquidable < 1`, a liquidator can never repay 100% of a position, so the `remaining == 0` branch is unreachable and every liquidation must leave `≥ debtFloorInUsd` behind. For any unhealthy position whose debt `D` satisfies `debtFloorInUsd ≤ D < 2 * debtFloorInUsd`, no `amountToRepay_` satisfies both constraints simultaneously — every liquidation call reverts.

### Finding Description
In `Pool.liquidate` (`contracts/Pool.sol:537`):

```solidity
if (amountToRepay_.wadDiv(_debtTokenBalance) > maxLiquidable) {
    revert AmountGreaterThanMaxLiquidable();   // line 567-569
}
...
if (_newDebtInUsd > 0 && _newDebtInUsd < debtFloorInUsd) {
    revert RemainingDebtIsLowerThanTheFloor(); // line 576-578
}
```

With `maxLiquidable = 0.5e18` (`initialize`, line 181) and `debtFloorInUsd = F > 0`:

- Full repayment `amountToRepay_ = D` gives ratio `1e18 > 0.5e18` → `AmountGreaterThanMaxLiquidable`.
- Partial repayment `a` must satisfy `a ≤ 0.5·D` and `D - a ≥ F`, i.e. `a ≤ D - F`.
- Both are satisfiable only if `D - F ≥ a_min > 0` **and** `D - F ≤ 0.5·D` is not required — actually we need any `a` with `a ≤ min(0.5·D, D - F)` and `a > 0`. Feasibility requires `D - F > 0`, but seizing `a` collateral must also cover the position; critically, once `D < 2F`, even repaying the maximum `0.5·D` leaves `0.5·D < F`, which is `> 0` → `RemainingDebtIsLowerThanTheFloor`.

So for `F ≤ D < 2F` every `amountToRepay_` reverts: amounts `≤ D - F` leave remainder `≥ F` (ok) but repaying down to exactly `F` is only possible while `D - F ≤ 0.5·D` i.e. `D ≤ 2F`... precisely: allowed `a ≤ min(0.5D, D − F)`. When `D` approaches `F` from above, `D − F → 0`, so only dust repayments are allowed, and once `D − F <` the minimum seizable unit / once `D ≤ F` is reached (interest can never reduce debt, but each partial liquidation's remainder must itself be `≥ F`), the position converges to a state where `a ≤ D − F` permits only amounts that seize negligible collateral while the position remains unhealthy. Once `D` (in USD terms after each liquidation) lands in `(F, F + ε)`, further liquidation is impossible until interest grows `D ≥ 2F` again — and during that window the position can be deeply underwater.

An unprivileged attacker can deliberately manufacture this: open a position with debt `D` slightly above `F`, donate/swap to make it unhealthy (or wait for interest accrual via `DebtToken.accrueInterest` raising `debtIndex`), and the position sits in the unliquidatable band `D < 2F`. Any liquidator call reverts.

### Impact Explanation
Liveness invariant break: unhealthy positions in the `[F, 2F)` debt band cannot be liquidated by anyone. If collateral value drops faster than interest accrues (pushing the debt past `2F`), the position accrues bad debt while liquidation is blocked — protocol insolvency risk. Attacker-cost is only the collateral of one deliberately toxic position; there is no privileged role involved.

### Likelihood Explanation
Requires `debtFloorInUsd > 0` on the deployed pool (a configured value — unverified against deployment configs in this analysis; if `0`, the check is skipped and there is no issue). Assuming a nonzero floor is configured (its purpose is precisely to bound dust debt), any small position naturally enters the unliquidatable band as interest accrues or prices move. No privileged action needed.

### Recommendation
In `liquidate`, allow full repayment to bypass `maxLiquidable` when `amountToRepay_ == _debtTokenBalance` (or when the remaining debt would be `< debtFloorInUsd`), e.g.:

```solidity
if (amountToRepay_ != _debtTokenBalance &&
    amountToRepay_.wadDiv(_debtTokenBalance) > maxLiquidable) {
    revert AmountGreaterThanMaxLiquidable();
}
```

Alternatively, exempt liquidations from the debt floor entirely (the floor exists to prevent users *opening* dust debt, not to trap closing liquidations).

### Proof of Concept
Foundry fork sketch (mainnet pool, assuming `debtFloorInUsd() > 0`):

```solidity
// Fork mainnet; pick pool, depositToken (msdTOKEN), debtToken (msUSD debt), synth (msUSD)
uint256 F = pool.debtFloorInUsd();              // e.g. > 0
// 1. Attacker deposits collateral and issues debt D with F < D < 2*F
//    via debtToken.issue(...) after depositToken.deposit(...)
// 2. Move price/time so position is unhealthy but debt stays < 2*F
//    (warp time -> accrueInterest, or mock oracle price dip)
// 3. Liquidator tries every amountToRepay:
vm.expectRevert(); // either AmountGreaterThanMaxLiquidable or RemainingDebtIsLowerThanTheFloor
pool.liquidate(msUSD, attacker, /* any a */, msdToken);
// - a = balance           -> ratio 1e18 > maxLiquidable (0.5e18) reverts
// - a <= 0.5*balance      -> remaining = balance - a >= 0.5*balance;
//   since balance < 2F, any a that leaves remainder >0 and <F reverts;
//   remainder >= F requires a <= balance - F, and for balance ~ F this
//   permits only dust repays; at balance <= F no valid a exists.
assert(pool.debtPositionOf(attacker)._isHealthy == false); // stuck unhealthy
```

Key assertion: after the position's debt is `≤ F` (or in `(F, 2F)` where only dust repays are permitted), successive `liquidate` calls always revert, so the unhealthy position's collateral is permanently unseizable via liquidation.

Caveat: this hinges on `debtFloorInUsd` being nonzero in the target deployment — verify `pool.debtFloorInUsd()` on-chain; if `0`, this finding does not apply.
