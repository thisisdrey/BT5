### Title
Unauthenticated peer can poison AtlasDB's `attachments` table with arbitrary, never-committed blobs via unchecked `insert_instantiated_attachment` - (File: stackslib/src/net/atlas/download.rs)

### Summary
When resolving an `AttachmentRequest`, `AttachmentsBatchStateContext::extend_with_attachments` accepts whatever `Attachment` payload the responding peer sends without verifying that its content hash matches the `content_hash` that was actually requested. The resulting `Attachment` is then unconditionally persisted via `AtlasDB::insert_instantiated_attachment`, which — unlike the uninstantiated-attachment path — has no size cap or eviction policy, allowing an attacker peer to grow the `attachments` table indefinitely with data that never corresponds to any on-chain `AttachmentInstance.content_hash`.

### Finding Description
`AttachmentRequest::make_request_type` builds a GET to `/v2/attachments/{content_hash}` [1](#0-0) , but when the response comes back, `extend_with_attachments` only decodes it and inserts it into the in-memory `attachments: HashSet<Attachment>` — there is no comparison between `Hash160(response.attachment.content)` and `request.content_hash`: [2](#0-1) 

`GetAttachmentResponse`'s deserializer simply wraps whatever hex bytes the peer sent into an `Attachment` with no hash binding to the request at all: [3](#0-2) 

In the `Done` branch of `AttachmentsDownloader::run`, every attachment collected this way is persisted unconditionally, regardless of whether it resolves any known `AttachmentInstance`: [4](#0-3) 

`AtlasDB::insert_instantiated_attachment` (called both from the `Done` path and from `check_attachment_instances`) performs an unconditional `INSERT OR REPLACE` keyed on the locally-computed `attachment.hash()`, with no size limit or count cap: [5](#0-4) 

This is in sharp contrast to the uninstantiated-attachment insert path, which explicitly checks `count_uninstantiated_attachments()` against `atlas_config.max_uninstantiated_attachments` and evicts the oldest entries before inserting: [6](#0-5) 

Only `evict_expired_uninstantiated_attachments` (which only ever targets `was_instantiated = 0` rows) is called in the `Done` handler; there is no equivalent eviction for `was_instantiated = 1` rows: [7](#0-6) 

**Exploit flow**: an attacker runs a peer that a victim node selects as an attachment source (via its normal inventory-advertisement flow, `get_prioritized_attachments_requests`). For every `AttachmentRequest` the victim sends (each keyed by a distinct `content_hash` corresponding to a real, unresolved `AttachmentInstance` from `find_unresolved_attachment_instances`/`queued_attachments`), the attacker peer can respond with `HTTP 200` and an arbitrary byte blob whose actual hash does not equal `content_hash` at all. The blob passes through `decode_atlas_get_attachment` unchecked, is inserted into `context.attachments`, and is persisted with `was_instantiated = 1` forever — it never matches the instance it was supposedly answering (`find_all_attachment_instances(&attachment.hash())` will simply return empty for it), yet it still occupies a permanent row in `attachments`.

### Impact Explanation
Each malicious response the attacker's peer serves for a legitimately outstanding attachment request results in one permanent, unbounded-size row in AtlasDB's `attachments` table that is never tied to any real BNS name-attachment commitment (`was_instantiated=1` count grows independent of `AttachmentInstance` rows with a genuinely matching `content_hash`). Because there is no cap analogous to `max_uninstantiated_attachments` for instantiated rows and no periodic eviction for them, repeated exploitation across the lifetime of outstanding/incoming attachment requests causes unbounded disk growth on the victim node — an attachment/BNS mismatch and storage-exhaustion condition, matching the "attachment/BNS mismatch" High-impact category.

### Likelihood Explanation
The precondition (the node has unresolved/queued `AttachmentInstance`s, which occur naturally as part of ordinary BNS name-registration activity, or the attacker can induce them) is explicitly allowed by the question. The attacker needs only to run a normal peer that advertises inventory and gets selected as a download source — no privileged role, secret, or special access is required; this is fully reachable over the ordinary p2p/HTTP attachment-fetch flow. The attack is trivially repeatable: one poisoned row per malicious response, and multiple content_hash requests can be answered simultaneously (bounded only by `max_inflight_attachments`/retry limits, which throttle rate but not total accumulation over time).

### Recommendation
In `extend_with_attachments` (`stackslib/src/net/atlas/download.rs`), verify that `Hash160::from_data(&response.attachment.content) == request.content_hash` before accepting the response; discard and treat as a failed/faulty peer response otherwise. Additionally, enforce `atlas_config.attachments_max_size` on the downloaded content before insertion, and add a cap/eviction policy for `was_instantiated = 1` rows in `AtlasDB::insert_instantiated_attachment`/a corresponding `evict_expired_instantiated_attachments`, similar to the existing uninstantiated-attachment bookkeeping.

### Proof of Concept
Rust test in `stackslib::net::atlas::download` (or `tests.rs`):
1. Set up an `AtlasDB` (`connect_memory`) and seed N `AttachmentInstance` rows via `insert_attachment_instance`/`insert_initial_attachment_instance` with distinct `content_hash` values (simulating legit committed instances), leaving them unresolved (`is_available = 0`).
2. Construct an `AttachmentsBatchStateContext` with a mock peer, and drive `extend_with_attachments` with `BatchedRequestsResult::succeeded` populated by, for each `AttachmentRequest`, a crafted `StacksHttpResponse` whose `decode_atlas_get_attachment()` yields an `Attachment` with content whose hash does **not** equal the corresponding `request.content_hash` (e.g., random bytes each time).
3. Drive the state machine to `Done` and invoke the equivalent of the `AttachmentsDownloader::run` `Done`-branch logic (calling `atlasdb.insert_instantiated_attachment` for each drained attachment).
4. Assert: `SELECT COUNT(*) FROM attachments WHERE was_instantiated = 1` == N, while `atlas_db.find_all_attachment_instances(&hash)` for each inserted attachment's hash returns empty (proving none of these rows correspond to any real `AttachmentInstance.content_hash`), demonstrating the unbounded, uncommitted growth of the `attachments` table.

    pub fn extend_with_attachments(
        mut self,
        results: &mut BatchedRequestsResult<AttachmentRequest>,
    ) -> AttachmentsBatchStateContext {
        for (request, response) in results.succeeded.drain() {
            let report = self
                .peers
                .get_mut(request.get_url())
                .expect("Atlas: unable to retrieve reliability report for peer");

            let response = if let Some(r) = response {
                r
            } else {
                report.bump_failed_requests();
                continue;
            };

            if let Ok(response) = response.decode_atlas_get_attachment() {
                self.attachments.insert(response.attachment);
                report.bump_successful_requests();
            } else {
                report.bump_failed_requests();
            }
        }
        let mut events_ids = results.faulty_peers.keys().copied().collect::<Vec<usize>>();
        self.events_to_deregister.append(&mut events_ids);

        self
    }

    pub fn insert_uninstantiated_attachment(
        &mut self,
        attachment: &Attachment,
    ) -> Result<(), db_error> {
        // Insert the new attachment
        let uninstantiated_attachments = self.count_uninstantiated_attachments()?;
        if uninstantiated_attachments >= self.atlas_config.max_uninstantiated_attachments {
            let to_delete =
                1 + uninstantiated_attachments - self.atlas_config.max_uninstantiated_attachments;
            self.evict_k_oldest_uninstantiated_attachments(to_delete)?;
        }

        let tx = self.tx_begin()?;
        let now = util::get_epoch_time_secs() as i64;
        let res = tx.execute(
            "INSERT OR REPLACE INTO attachments (hash, content, was_instantiated, created_at) VALUES (?, ?, 0, ?)",
            params![
                attachment.hash(),
                attachment.content,
                now,
            ],
        );
        res.map_err(db_error::SqliteError)?;
        tx.commit().map_err(db_error::SqliteError)?;
        Ok(())
    }

    pub fn insert_instantiated_attachment(
        &mut self,
        attachment: &Attachment,
    ) -> Result<(), db_error> {
        let now = util::get_epoch_time_secs() as i64;
        let tx = self.tx_begin()?;
        tx.execute(
            "INSERT OR REPLACE INTO attachments (hash, content, was_instantiated, created_at) VALUES (?, ?, 1, ?)",
            params![attachment.hash(), attachment.content, now],
        )?;
        tx.execute(
            "UPDATE attachment_instances SET is_available = 1 WHERE content_hash = ?1 AND status = ?2",
            params![attachment.hash(), AttachmentInstanceStatus::Checked],
        )?;
        tx.commit()?;
        Ok(())
    }
