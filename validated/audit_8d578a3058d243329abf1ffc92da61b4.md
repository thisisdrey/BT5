### Title
Git-transport argument/protocol injection via unsanitized `remote` field in `git_repository`/`new_git_repository` - (File: tools/build_defs/repo/git_worker.bzl)

### Summary
`git_repository` (and its bzlmod `source.json` `git_repository` backing type) forwards the attacker-influenceable `remote`, `commit`, `tag`, and `branch` string attributes verbatim into `git` subcommand argv without any scheme/format validation or `GIT_ALLOW_PROTOCOL` restriction. Because Git itself interprets certain `remote` values as directives (e.g. the `ext::<command>` remote-helper syntax, which spawns an arbitrary shell command), an attacker who controls the value of `remote` reaching this code path can achieve command execution during repository fetch — the same bug class as the CVE's "unsanitized field value flows unfiltered into an interpreter that treats it as executable syntax" (CSV field → SQL statement there; registry/module `remote` string → Git transport helper here).

### Finding Description
`git_repo()` in [1](#0-0)  builds a `_GitRepoInfo` directly from `ctx.attr.remote`, `ctx.attr.commit`, `ctx.attr.tag`, and `ctx.attr.branch` with no validation of their contents (no scheme allow-list, no rejection of values starting with `-` or containing `::`).

`add_origin()` then passes this value straight to Git: [2](#0-1) , and `_execute()` runs `git -c core.fsmonitor=false <args>` with the caller's full environment merged in, without setting `GIT_ALLOW_PROTOCOL` or `protocol.ext.allow=never` to disable dangerous transport helpers: [3](#0-2) .

Git natively supports the `ext::<command>` remote helper, in which the remote URL itself is a shell command line that Git executes to perform the transport (this is the exact mechanism behind the well-known Git "remote helper" command-injection class, e.g. CVE-2017-1000117). Because `ctx.execute` passes argv elements without a shell, ordinary shell metacharacters in `remote`/`commit`/`tag` are not exploitable by themselves — but `ext::` is a value Git itself parses as an executable directive, so the injection happens one layer down, inside Git's own argument parser, exactly analogous to how the CVE's unsanitized CSV field was parsed as SQL syntax by MySQL rather than by the vulnerable component itself.

The `remote` (and `commit`/`tag`) values are attacker-reachable through:
- The `type: "git_repository"` variant of a Bazel registry's `source.json`, which forwards `remote`, `commit`, `tag`, `branch`, `shallow_since` fields directly to the `git_repository` repo rule (documented at `docs/*/external/registry.mdx`, "the following fields are... directly forwarded to the underlying `git_repository` repo rule").
- Non-bzlmod `WORKSPACE`/`MODULE.bazel` `git_repository` calls whose `remote` may itself be derived from external, less-trusted data (e.g. templated from a dependency file).

Unlike `http_archive`, `git_repository` has **no integrity/checksum mechanism** at all for its inputs (the docs explicitly call this out as a reason to prefer `http_archive`: "`http_archive` works with the repository cache… but not `git_repository`"). So there is no sha256/integrity/lockfile check that "should stop it" the way there is for archive URLs — a hostile/compromised registry serving a `source.json` with a crafted `remote` value is not intercepted by any pinning mechanism the first time that module version's registry file is fetched (before it's recorded in `MODULE.bazel.lock`'s `registryFileHashes`).

### Impact Explanation
A malicious or compromised index registry (or a malicious `git_repository`/`new_git_repository` remote value sourced from otherwise-untrusted data) can cause Bazel to execute arbitrary commands on the machine performing the fetch, by supplying a `remote` value of the form `ext::sh -c "..."` (or similar Git transport-helper syntax). This is full command execution in the context of the Bazel client performing the build/fetch — a critical impact matching the CVE's "manipulation leads to injection with critical impact" class.

### Likelihood Explanation
Likelihood is moderate: it requires either (a) a compromised/malicious registry entry using the `git_repository` `source.json` type, exploitable on first fetch before lockfile pinning, or (b) a build that constructs `git_repository(remote=...)` from external, attacker-influenced data. `git_repository` is a less common path than `http_archive`, and Bazel's own docs steer users toward `http_archive`, somewhat reducing exposure, but the lack of any protocol allow-list or checksum on this attribute makes exploitation straightforward whenever this path is reached.

### Recommendation
- Reject `remote` values that use non-network schemes (e.g., disallow `ext::`, `fd::`, and other Git transport-helper syntaxes) or explicitly set `GIT_ALLOW_PROTOCOL`/`protocol.ext.allow=never` (and similarly restrict `file`/other helpers as appropriate) in the environment passed to `_execute()` in `git_worker.bzl`.
- Validate `remote`/`commit`/`tag`/`branch` values against an expected format before use, rejecting values that don't match expected URL schemes or ref-name syntax.
- Consider adding an integrity-verification mechanism for `git_repository` similar to `http_archive`'s `sha256`/`integrity`, so registry compromise cannot silently substitute a malicious `remote`.

### Proof of Concept
In the style of existing tests such as `src/test/shell/bazel/starlark_git_repository_test.sh` [4](#0-3) , add a `MODULE.bazel` entry:
```
git_repository = use_repo_rule('@bazel_tools//tools/build_defs/repo:git.bzl', 'git_repository')
git_repository(
    name = "pwned",
    remote = "ext::sh -c \"touch /tmp/bazel_pwned\"",
)
```
Running `bazel fetch //...` invokes `add_origin()` → `git remote add origin 'ext::sh -c "touch /tmp/bazel_pwned"'` [2](#0-1) , followed by `fetch()`, causing Git to invoke the embedded shell command as its "transport helper," creating `/tmp/bazel_pwned` outside any sandbox/containment the repository fetch is supposed to have. A JUnit/shell-integration test should assert this file is *not* created (i.e., the fetch fails closed) once the fix (protocol allow-listing/validation) is applied.

def git_repo(ctx, directory):
    """ Fetches data from git repository and checks out file tree.

    Called by git_repository rule.

    Args:
        ctx: Context of the calling rules, for reading the attributes.
        Please refer to the git_repository rule for the description.
        directory: Directory where to check out the file tree.
    Returns:
        The struct with the following fields:
        commit: Actual HEAD commit of the checked out data.
        shallow_since: Actual date and time of the HEAD commit of the checked out data.
    """
    if ctx.attr.shallow_since:
        if ctx.attr.tag:
            fail("shallow_since not allowed if a tag is specified; --depth=1 will be used for tags")
        if ctx.attr.branch:
            fail("shallow_since not allowed if a branch is specified; --depth=1 will be used for branches")

    # Use shallow-since if given
    if ctx.attr.shallow_since:
        shallow = "--shallow-since=%s" % ctx.attr.shallow_since
    else:
        shallow = "--depth=1"

    reset_ref = ""
    fetch_ref = ""
    if ctx.attr.commit:
        reset_ref = ctx.attr.commit
        fetch_ref = ctx.attr.commit
    elif ctx.attr.tag:
        reset_ref = "tags/" + ctx.attr.tag
        fetch_ref = "tags/" + ctx.attr.tag + ":tags/" + ctx.attr.tag
    elif ctx.attr.branch:
        reset_ref = "origin/" + ctx.attr.branch
        fetch_ref = ctx.attr.branch + ":origin/" + ctx.attr.branch
    else:
        reset_ref = "origin/HEAD"
        fetch_ref = "HEAD:refs/remotes/origin/HEAD"

    git_repo = _GitRepoInfo(
        directory = ctx.path(directory),
        shallow = shallow,
        reset_ref = reset_ref,
        fetch_ref = fetch_ref,
        remote = str(ctx.attr.remote),
        init_submodules = ctx.attr.init_submodules,
        recursive_init_submodules = ctx.attr.recursive_init_submodules,
    )

def _execute(ctx, git_repo, args):
    # "core.fsmonitor=false" disables git from spawning a file system monitor which can cause hangs when cloning a lot.
    # See https://github.com/bazelbuild/bazel/issues/21438
    start = ["git", "-c", "core.fsmonitor=false"]
    return ctx.execute(
        start + args,
        environment = ctx.os.environ | _GIT_LOCAL_ENV_VARS,
        working_directory = str(git_repo.directory),
    )
