### Title
Anti-replay window check-then-update race allows replayed packets to bypass the nonce window - (File: connection_state.go)

### Summary
`ConnectionState.Decrypt` and `ConnectionState.VerifyRelay` split the anti-replay window enforcement into two separately-locked operations (`window.Check` then, after decryption, `window.Update`) with the AEAD decrypt call sitting unlocked in between. Under multi-routine UDP dispatch (`routines > 1`), an attacker who captures and duplicates a single ciphertext packet can get it processed concurrently by two reader goroutines before either commits the counter via `Update`, defeating the replay window.

### Finding Description
`Decrypt` locks `decryptLock`, calls `cs.window.Check(l, messageCounter)`, unlocks, performs the (unlocked, relatively expensive) `DecryptDanger` AEAD operation, then re-locks and calls `cs.window.Update(l, messageCounter)` to actually commit the counter as seen: [1](#0-0) 

The same pattern exists for relay frames in `VerifyRelay`: [2](#0-1) 

`Bits.Check` only tests whether a counter is unseen; the counter is not marked as seen until `Bits.Update` runs: [3](#0-2) [4](#0-3) 

This is architecturally identical to the report's bug class: a security-relevant value (here, "has this nonce/counter been consumed?") is computed once for validation, an expensive/interruptible operation happens in between, and the actual state-commit re-derives/re-checks the value a second time — leaving a window where an attacker-controlled duplicate can slip through before the first commit lands, exactly as the royalty amount was computed once, changed via an intervening external call, and re-derived differently before payout.

The receive path fans packets out to `routines` independent goroutines, each with its own read buffer, that all call into the same per-hostinfo `ConnectionState`: [5](#0-4) [6](#0-5) 

So a captured Message or Relay-forward frame from an already-established tunnel, replayed twice (e.g., duplicated by an on-path attacker or reflected by network equipment) so that both copies land in different reader queues at nearly the same time, can result in both goroutines observing `Check()==true` before either calls `Update()`, causing the second (replayed) copy to be decrypted and delivered/forwarded a second time instead of being rejected as a duplicate.

### Impact Explanation
This breaks Nebula's nonce/anti-replay guarantee for the data plane and for relay-forwarded frames. For `Decrypt`, a successfully-decrypted duplicate is handed to `handleOutsideMessagePacket`, meaning application-layer traffic (e.g., a single captured TUN payload) can be delivered/processed twice, which is a state-poisoning/replay impact at the tunnel layer. For `VerifyRelay`, the impact is worse: `handleOutsideRelayPacket` re-forwards or re-processes the duplicated frame through the relay/onward path, meaning a relay node (which does not decrypt payloads, only authenticates the AEAD tag) can be tricked into re-forwarding a captured relay frame — a traffic replay across the relay boundary that the relay's own trust model assumes is prevented by the replay window (per the project's own `TestRelayReplayProtection` regression test intent, which currently only tests strictly sequential replays, not concurrent ones under `routines>1`): [7](#0-6) 

### Likelihood Explanation
Requires `routines > 1` (a supported, documented performance configuration, and the default when multiple CPUs are available per `main.go`), plus the ability to duplicate/replay a captured ciphertext UDP datagram to the target's listen socket(s)/relay path with tight timing so two reader goroutines process it concurrently. No CA-signed certificate or handshake participation is needed — only observation/duplication of already-transmitted ciphertext, which is achievable by any on-path or off-path attacker capable of UDP packet injection (a classic replay-attacker capability, independent of holding valid credentials). [8](#0-7) 

### Recommendation
Perform the Check-decrypt-Update sequence atomically with respect to the replay window: hold `decryptLock` across the entire operation (accepting the cost of serializing decrypts per hostinfo), or use a single atomic "test-and-set" primitive on `Bits` that both validates and marks the counter as consumed before decryption begins, only unmarking it on decrypt failure. Apply the same fix to both `Decrypt` and `VerifyRelay`.

### Proof of Concept
1. Configure a Nebula node with `routines: 2` (or more) so multiple independent UDP reader goroutines exist per `f.listenOut(i)`.
2. Establish a tunnel and capture one legitimate encrypted `Message` (or relay-forwarded) packet with counter `N`.
3. Send two copies of that exact captured packet to the node's listen port at nearly the same instant (e.g., using two sockets bound so the OS/SO_REUSEPORT dispatches them to different reader queues, or via a burst that lands in different batches under `recvmmsg`).
4. Observe that both copies can pass `cs.window.Check(l, N)` before either calls `cs.window.Update(l, N)`, resulting in the payload being decrypted and delivered to `handleOutsideMessagePacket` (or forwarded via `handleOutsideRelayPacket`) twice instead of the second copy being rejected with `ErrAlreadySeen`. The existing `TestRelayReplayProtection` test only exercises strictly sequential re-injection and would not catch this concurrent race, so a new test injecting the same captured frame concurrently from two goroutines while `routines>1` is needed to reproduce it.

func (b *Bits) Check(l *slog.Logger, i uint64) bool {
	// If i is the next number, return true.
	if i > b.current {
		return true
	}

		return !b.get(i)
	}

	// Not within the window
	if l.Enabled(context.Background(), slog.LevelDebug) {

	}
	return false
}

func (b *Bits) Update(l *slog.Logger, i uint64) bool {
	// Fast path: i is the next expected counter. Split out so the function
	// stays small and avoids paying for the slow paths' slog argument-build
	// stack frame on every call. The bit read/test/write is inlined to
	// touch the backing word once.
	if i == b.current+1 {
		pos := i & b.lengthMask
		word := pos >> 6
		mask := uint64(1) << (pos & 63)
		w := b.bits[word]
		if i > b.length && w&mask == 0 {
			b.lostCounter.Inc(1)
		}
		b.bits[word] = w | mask
		b.current = i
		return true
	}
	return b.updateSlow(l, i)
}
