### Title
Missing zero-check on maker fill amount in equal-quantity order match branch causes maker to lose sell tokens for free - ([File: actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java])

### Summary
`MarketSellAssetActuator.matchSingleOrder` computes fill amounts using integer division via `MarketUtils.multiplyAndDivide`, which truncates toward zero. Two of the three match branches ("taker < maker" implicitly, and "taker > maker") guard against the computed amount rounding down to `0`, but the "taker == maker" branch does not, allowing a maker's order to be fully consumed while the maker receives zero tokens in return.

### Finding Description
In `matchSingleOrder` [1](#0-0) , the taker's expected receive amount is checked for zero and refunded if so. Likewise, in the "taker > maker" branch, `makerBuyTokenQuantityReceive == 0` is explicitly checked and the maker's remaining sell tokens are returned [2](#0-1) .

However, in the "taker == maker" branch, `makerBuyTokenQuantityReceive` is computed by the same `multiplyAndDivide` call but is **never checked for zero** before the maker's order is fully closed: [3](#0-2) 

`MarketUtils.multiplyAndDivide` performs `floorDiv(a*b, c)`, which truncates to `0` whenever `a*b < c` [4](#0-3) . With crafted order sell/buy ratios and remaining quantities (e.g. maker order `sellTokenQuantity=10, buyTokenQuantity=3`, remaining sell `=3`, matched against a taker order whose computed `takerBuyTokenQuantityRemain` floors to the same value `3`), `makerBuyTokenQuantityReceive = floor(3*3/10) = 0`.

When this happens:
- `makerOrderCapsule.setSellTokenQuantityRemain(0)` fully closes the maker's order and marks it `INACTIVE` (line 434, 439), permanently consuming the maker's remaining sell-token balance.
- `addTrxOrToken(makerOrderCapsule, makerBuyTokenQuantityReceive)` is called with `0`, crediting the maker with nothing (line 490).
- Meanwhile the taker receives `takerBuyTokenQuantityReceive = makerOrderCapsule.getSellTokenQuantityRemain()` (the maker's full remaining sell amount) at line 429, while the taker's own remaining sell balance is reduced by only `makerBuyTokenQuantityReceive` (`0`), i.e., the taker pays nothing for tokens received (line 431-433).

This is the same bug class as the referenced report: an integer-division rounding-to-zero result is used to finalize a balance transfer without verifying the transferred amount is non-zero, resulting in one party's asset being burned/consumed without any compensating credit.

### Impact Explanation
This is directly reachable by any unprivileged account placing TRC10 market sell orders (`MarketSellAssetContract`), which any address can broadcast. The maker permanently and unrecoverably loses their remaining sell-token balance (their order is force-closed with zero payout) — a concrete theft/permanent loss of funds. Simultaneously the taker obtains the maker's full remaining sell-token amount while paying nothing (their own remaining balance is left unreduced), effectively creating unbacked value for the taker. Both effects constitute direct fund-safety violations reachable from a single pair of market orders.

### Likelihood Explanation
Exploitation requires an attacker (as taker) to place an order whose sell/buy ratio is crafted, combined with an existing (or attacker-placed as maker under a second address) maker order with a specific remaining-quantity/ratio combination, such that both `multiplyAndDivide` computations land exactly on the equal-quantity branch and the maker computation floors to zero. Since order quantities, sell/buy ratios, and (via partial fills) the exact remaining quantity are all attacker-controllable/predictable, an attacker can deliberately construct both orders (potentially self-matching with two of their own addresses, with a victim maker order as the target) to trigger this deterministically. No special privileges or timing races are needed beyond normal transaction submission.

### Recommendation
Add the same zero-check used elsewhere in the function to the "taker == maker" branch: if `makerBuyTokenQuantityReceive == 0` (after computing it in the `taker == maker` branch), do not close the maker order/zero its remaining balance — instead return the sell-token remainder to the maker (as done in `returnSellTokenRemain`) and mark the order inactive without loss, mirroring the handling already implemented for the "taker > maker" branch.

### Proof of Concept
1. Maker (address A) creates a sell order: `sellToken=X, sellTokenQuantity=10, buyToken=TRX, buyTokenQuantity=3`. Assume, via a prior partial fill (or direct construction), the order's `sellTokenQuantityRemain = 3`.
2. Taker (address B) creates a sell order: `sellToken=TRX, sellTokenQuantityRemain=1, buyToken=X, buyTokenQuantity` chosen so its effective price matches/exceeds maker's price, matching against maker's order via `matchOrder`/`matchSingleOrder`.
3. In `matchSingleOrder`, `takerBuyTokenQuantityRemain = multiplyAndDivide(1, 10, 3) = floor(10/3) = 3`, which equals `makerOrderCapsule.getSellTokenQuantityRemain() = 3` → enters the "taker == maker" branch [3](#0-2) .
4. `makerBuyTokenQuantityReceive = multiplyAndDivide(3, 3, 10) = floor(9/10) = 0`.
5. Maker order's `sellTokenQuantityRemain` is set to `0` and marked `INACTIVE`, permanently losing the 3 units of token X; `addTrxOrToken(makerOrderCapsule, 0)` credits the maker nothing.
6. Taker receives `takerBuyTokenQuantityReceive = 3` units of token X (line 489, `addTrxOrToken(takerOrderCapsule, 3, ...)`), while taker's own `sellTokenQuantityRemain` is reduced from `1` to `1 - 0 = 1` (unchanged) — the taker pays nothing for the 3 units received.

  public static long multiplyAndDivide(long a, long b, long c, boolean disableMath) {
    try {
      long tmp = multiplyExact(a, b, disableMath);
      return floorDiv(tmp, c, disableMath);
    } catch (ArithmeticException ex) {
      // do nothing here, because we will use BigInteger to compute again
    }

    BigInteger aBig = BigInteger.valueOf(a);
    BigInteger bBig = BigInteger.valueOf(b);
    BigInteger cBig = BigInteger.valueOf(c);

    return aBig.multiply(bBig).divide(cBig).longValue();
  }
