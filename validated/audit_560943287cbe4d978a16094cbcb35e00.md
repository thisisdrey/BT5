### Title
`pallet_oracle`'s median aggregation degenerates to `max()` for small/even submission counts, letting a single oracle operator dictate the committed price - (File: `substrate/frame/honzon/oracle/src/default_combine_data.rs`)

### Summary
The generic `pallet-oracle` module (used as the runtime's on-chain price oracle, wired up in `substrate/bin/node/runtime/src/lib.rs`) is documented and intended to resist a single bad data provider by combining operator submissions with a median. Its default combiner, `DefaultCombineData`, does not compute a true median: for any *even* number of fresh submissions it picks the upper-middle element via `select_nth_unstable_by`, which for the smallest and most common such case (exactly two fresh values) is mathematically identical to `max(a, b)`. This reproduces exactly the bug class from the external report — the aggregated value can be dictated by a single compromised/malicious data feeder — but here it is a deterministic, provable implementation defect rather than an off-chain provider assumption.

### Finding Description
`DefaultCombineData::combine_data` in [1](#0-0)  filters out expired submissions, checks the remaining `count` against `MinimumCount`, and then does:

```rust
let mid_index = count / 2;
let (_, value, _) = values.select_nth_unstable_by(mid_index as usize, |a, b| a.value.cmp(&b.value));
Some(value.clone())
```

For an odd `count` this correctly returns the true median. For an **even** `count`, `mid_index = count/2` selects the `(count/2 + 1)`-th smallest element (1-indexed), i.e. the *upper* median rather than an average of the two middle values. In the degenerate but common case of exactly two fresh submissions (`count == 2`), `mid_index = 1`, so the "median" returned is simply `max(a, b)`. Any single operator among the two active feeders can therefore force the committed value to their own submission by pricing it above the honest operator's value — the honest operator's submission is completely ignored.

This is reachable whenever the number of live (non-expired) values for a key equals the configured `MinimumCount` (or any even number above it), which happens naturally with small oracle-committee configurations, membership churn, or expiry-driven drop-outs. The docstring in the pallet (`traits.rs`, `lib.rs`) explicitly claims median aggregation is used "to resist outliers and manipulation attempts," so downstream consumers relying on `DataProvider::get`/`Pallet::get` reasonably assume outlier resistance that the code does not actually provide for even-sized submission sets. The pallet is generic and reusable (`OracleKey`/`OracleValue` are runtime-configurable, `Members` is any `SortedMembers` set), so any chain or pallet built on top of it (via the `DataProvider`/`DataFeeder` traits, see [2](#0-1)  ) that consumes `pallet_oracle::Pallet::get` for pricing, collateral valuation, liquidation thresholds, or swap rates inherits this manipulation path without any extra guard.

The dispatchable entrypoint that drives this path is unprivileged for any registered oracle member (not root/governance): [3](#0-2) 

And the combination is triggered on every feed: [4](#0-3) 

The runtime wiring shows this pallet is live with `MinimumCount = 5`: [5](#0-4) 
but nothing in the pallet enforces an odd `MinimumCount`, and the guard only checks `count < minimum_count`, not parity — so any downstream integrator (or any drop in live feeders down to an even number ≥ `MinimumCount`) reintroduces the max()-degeneration.

### Impact Explanation
Any pallet consuming `pallet_oracle` values for financial decisions (collateral valuation, liquidation, minting/redemption pricing, swap rates) would accept a price dictated by a single participating oracle operator whenever the fresh-submission count is even, rather than a manipulation-resistant median. This directly maps to the reported class: "asset price could easily be manipulated by only one compromised or malfunctioning ... provider," here realized as a single dishonest oracle operator (a data-feeder role, not an admin/governance/validator actor) fully controlling the on-chain value and enabling downstream fund extraction from any dependent pallet.

### Likelihood Explanation
No node, validator, relayer, or admin compromise is required — only one signed account already in the `Members` set (the oracle-operator/feeder role, analogous to a compromised third-party price provider in the original report) needs to submit an extreme value while the number of live submissions happens to be even (a very plausible steady state, e.g. `MinimumCount` itself being even, or one of an odd `MinimumCount+1` set of feeders going briefly stale/expiring). The call path (`feed_values`) is a standard signed extrinsic with no additional bounds/deviation checks against `prev_value` or peer submissions.

### Recommendation
Fix `DefaultCombineData::combine_data` to compute a true statistical median for even counts (average the two middle elements, or otherwise avoid always favoring the larger of a pair), and additionally add a deviation/outlier guard (e.g., reject or discount submissions that deviate beyond a configurable threshold from `prev_value` or from the rest of the batch) so that a single operator cannot swing the aggregate purely by submitting an extreme value, matching the mitigation recommended in the original report for the x/oracle-analogous case.

### Proof of Concept
1. Configure `pallet_oracle::Config::CombineData = DefaultCombineData<Self, ConstU32<2>, ExpiresIn>` (or let churn/expiry reduce live feeders for a key to exactly 2 while `MinimumCount` is even).
2. Honest operator A calls `feed_values(key, honest_price)` where `honest_price` reflects the real market value.
3. Malicious/compromised operator B calls `feed_values(key, extreme_price)` with `extreme_price >> honest_price`.
4. `combined()` computes `count = 2`, `mid_index = 1`; `select_nth_unstable_by(1, ...)` returns the larger of the two values — i.e. `extreme_price` — as the new `Values[key]`, matching the `values_are_updated_on_feed`-style test pattern already present in [6](#0-5)  but with only 2 feeders instead of 3.
5. Any downstream consumer reading `Pallet::get(key)` now sees `extreme_price` as the trusted "median," fully attacker-controlled by operator B alone.

	fn combine_data(
		_key: &<T as Config<I>>::OracleKey,
		mut values: Vec<TimestampedValueOf<T, I>>,
		prev_value: Option<TimestampedValueOf<T, I>>,
	) -> Option<TimestampedValueOf<T, I>> {
		let expires_in = ExpiresIn::get();
		let now = T::Time::now();

		values.retain(|x| x.timestamp.saturating_add(expires_in) > now);

		let count = values.len() as u32;
		let minimum_count = MinimumCount::get();
		if count < minimum_count || count == 0 {
			return prev_value;
		}

		let mid_index = count / 2;
		// Won't panic as `values` ensured not empty.
		let (_, value, _) =
			values.select_nth_unstable_by(mid_index as usize, |a, b| a.value.cmp(&b.value));
		Some(value.clone())
	}
