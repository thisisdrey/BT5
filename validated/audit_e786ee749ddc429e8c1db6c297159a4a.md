### Title
Permanent DoS of a TRON DEX token-pair order book via `MAX_MATCH_NUM` order-count spam - (File: `actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java`)

### Summary
`MarketSellAssetActuator.matchOrder()` walks the maker order linked-list for a given price level and matches the incoming taker order against consecutive maker orders. It counts matches with `matchOrderCount` and aborts the whole transaction with a `ContractValidateException` once more than `MAX_MATCH_NUM` orders would need to be traversed. [3](#0-2)  Because the whole `execute()` call runs inside a single revocable session, throwing this exception rolls back *all* partial matches/removals performed earlier in the same loop, so the head-of-list maker orders that would need to be consumed to get past the limit are never removed from the order book. [1](#0-0) 

### Finding Description
A malicious "asset issuer/order placer" (any unprivileged account able to submit a `MarketSellAssetContract` transaction) can place `MAX_MATCH_NUM + 1` (or more) tiny maker orders at the best price for a given `(sellTokenID, buyTokenID)` pair. [4](#0-3)  This is confirmed to be enforced/tested by `exceedMaxMatchNumLimit` in the actuator test suite, which shows that once the taker's counterparty walk exceeds `MAX_MATCH_NUM`, the transaction fails with "Too many matches." [5](#0-4) 

Once that many small maker orders occupy the best price for a pair, **any** subsequent taker (`MarketSellAssetActuator`) whose order needs to walk through more than `MAX_MATCH_NUM` maker orders at that price to be filled will always throw and have the entire transaction reverted (the session `revoke()`s), leaving the spam orders untouched at the head of the price-level linked list. Because the head orders can never be fully consumed without triggering the limit again, the price level becomes permanently stuck: legitimate takers who would need to traverse past the spammed head orders can never successfully match at that price, and their fee-paying transactions are wasted repeatedly. This mirrors the Y2K `mintRollovers()` issue where a single malicious recipient's transfer failure permanently blocks a shared, ordered processing queue for all other participants, because the queue processing here is likewise all-or-nothing per transaction and the "blocking" element cannot be skipped or evicted independently.

### Impact Explanation
This is a persistent denial of service against TRON's built-in exchange (Market) subsystem for a specific token pair/price level: legitimate users lose transaction fees on reverted matches and cannot trade through the network's on-chain order book at that price, effectively freezing liquidity/funds routing for that market without freezing any single account's balance directly. This qualifies as "an API/feature the node can no longer serve" for that trading pair, meeting the required Medium-severity bar for node-service denial.

### Likelihood Explanation
Likelihood is high: creating many small `MarketSellAssetContract` orders only costs the `MarketSellFee` per order (a normal, unprivileged, low-cost transaction), and no special permission is required. An attacker only needs to seed slightly more than `MAX_MATCH_NUM` orders at the best price to lock the level.

### Recommendation
Instead of aborting the entire transaction when `MAX_MATCH_NUM` is exceeded, either (a) partially fill the taker's order up to the limit and leave the remainder resting in the book rather than reverting the whole transaction, or (b) allow evicting/expiring stale small maker orders independently of a taker's ability to fully traverse them, so a single price level cannot be wedged open by cheap spam orders.

### Proof of Concept
1. Attacker submits `MAX_MATCH_NUM + 1` `MarketSellAssetContract` orders selling token A for token B at the same (best) price, each with minimal quantity, populating the head of the `pairPriceToOrderStore` linked list for that pair. [6](#0-5) 
2. A legitimate user submits a `MarketSellAssetContract` order for token B/A that would need to match against more than `MAX_MATCH_NUM` of the attacker's orders to fill (as demonstrated by the `exceedMaxMatchNumLimit` test, which reproduces exactly this scenario and confirms the resulting `ContractExeException`). [7](#0-6) 
3. The legitimate transaction reverts entirely (fee paid, order not placed/filled) because `matchOrder` throws before completing the walk, and the revoking session rolls back any partial state. [8](#0-7) 
4. The attacker's spam orders remain at the head of the list indefinitely, since no other actor's transaction can successfully traverse/consume them, permanently blocking matching at that price for the pair.

**Uncertainty:** I could not fully confirm from static analysis whether there is any existing mitigation elsewhere (e.g., minimum order size checks, price-level order count caps at insertion time, or fee-based economic deterrents) that might make sustained spam economically infeasible; a Devin session with the ability to run/trace live transactions against a testnet would be needed to conclusively validate the persistence and cost of this DoS end-to-end.
