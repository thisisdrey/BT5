### Title
`nft_resolve_withdraw` treats a JSON-deserialization failure from a malicious `nft_transfer_call` as "not delivered" and re-credits `token_balances` even when the NFT was actually transferred - ([File: contracts/defuse/src/contract/tokens/nep171/withdraw.rs])

### Summary
An attacker who deploys their own NFT ("token") contract, deposits an NFT from it into the Verifier, and then withdraws it with `msg` set (`is_call = true`) can implement `nft_transfer_call` to actually move the token while returning a JSON payload that isn't a valid `bool`. `nft_resolve_withdraw` reads this as `Ok(Err(_deserialization_err)) => false` and refunds the withdrawn NFT back into `token_balances`, even though the NFT already left the Verifier's custody. This creates a duplicate claim on one NFT: a real copy at the attacker's chosen `receiver_id` and a phantom, spendable balance re-credited inside Defuse.

### Finding Description
The broken invariant is: `value debited == value delivered + value re-credited by resolver`. For the `NftWithdraw` intent with `msg` set, `internal_nft_withdraw` debits the sender's balance for the `Nep171TokenId` immediately via `self.withdraw(...)` [1](#0-0) , then schedules `do_nft_withdraw` followed by `nft_resolve_withdraw(withdraw.token, owner_id, withdraw.token_id, is_call)` [2](#0-1) . `do_nft_withdraw` calls `nft_transfer_call` on the attacker-controlled `token` account when `withdraw.msg` is `Some` [3](#0-2) .

The resolver decides whether the NFT was "used" (delivered) purely from the raw return bytes of that external call:
```rust
let used = if is_call {
    match promise_result_checked_json::<bool>(0) {
        Ok(Ok(used)) => used,
        Ok(Err(_deserialization_err)) => false,
        Err(_) => true,
    }
} ...
``` [4](#0-3) 

`promise_result_checked_json` only differentiates "promise execution failed" (`Err`) from "promise succeeded, but body didn't parse as the expected type" (`Ok(Err(...))`) — the latter is unconditionally mapped to `false` (not delivered) [5](#0-4) .

Because `token` is an arbitrary `AccountId` the attacker deploys and fully controls, `nft_transfer_call` on that account is not the standard `near-contract-standards` implementation — the attacker writes it themselves. They can implement it to genuinely commit an internal state change (moving the NFT to `receiver_id`, e.g., a second account they own) and then return any JSON value that is not a `bool` (e.g., a string, number, or object). Since the function returns `Ok` (no panic), the state change is committed by NEAR's execution model; only the *return value* is misleading. The resolver then sees `Ok(Err(_deserialization_err))`, sets `used = false`, and calls `self.deposit(sender_id, [(Nep171TokenId::new(token, token_id).into(), 1)], REFUND_MEMO)`, re-crediting the withdrawn NFT's balance [6](#0-5) .

The existing guard comment only addresses the case `Err(_) => true` (promise failed due to gas exhaustion reading `nft_on_transfer`'s result — a known NEP-141-style issue) [7](#0-6) ; it does not address a successfully-returning, attacker-controlled payload that fails to parse as `bool` while the transfer genuinely occurred.

Exploit flow:
1. Attacker deploys malicious NFT contract `evil.nft` they fully control.
2. Attacker deposits an NFT from `evil.nft` into the Verifier (standard `nft_transfer_call` deposit flow), crediting `token_balances[attacker][Nep171(evil.nft, id)] = 1`.
3. Attacker signs/executes `NftWithdraw { token: evil.nft, receiver_id: attacker_alt, token_id: id, msg: Some("x") }`, forcing `is_call = true`.
4. `evil.nft::nft_transfer_call` reassigns internal ownership to `attacker_alt` and returns e.g. `"1"` (valid JSON, not a `bool`).
5. `nft_resolve_withdraw` gets `Ok(Err(deser_err))`, sets `used = false`, and re-credits `token_balances[attacker][Nep171(evil.nft, id)] = 1` again.
6. Attacker now holds a real NFT at `attacker_alt` on `evil.nft`, plus a spendable Verifier balance entry claiming the same NFT is still custodied by Defuse.

### Impact Explanation
The Verifier's internal accounting (`token_balances`) now asserts custody of an NFT it no longer holds. The attacker can subsequently withdraw or trade that phantom balance again (e.g., transfer it via intents to another party, or withdraw it a second time), extracting value the Verifier never actually possesses. This matches the Critical category: "a refund or resolver credit that does not match what failed to settle," causing the Verifier to owe more than it custodies. The attack is repeatable per attacker-controlled token contract and per NFT deposited/withdrawn this way, and it requires no privileged role — only the ability to deploy a contract and sign one's own withdraw intent.

### Likelihood Explanation
Preconditions are entirely within an unprivileged attacker's control: deploying an arbitrary NFT contract, depositing from it, and withdrawing with `msg` set is a normal, permitted user flow (`nft_withdraw`/`NftWithdraw` intent). No relayer key, DAO role, or victim key is needed. The only "skill" required is writing a non-standard `nft_transfer_call` implementation that both mutates state and returns non-boolean JSON — trivial in a contract the attacker authors. It is fully repeatable across tokens/accounts the attacker controls.

### Recommendation
Do not trust an unparsable-but-successful return value as proof of non-delivery. Either (a) treat `Ok(Err(_deserialization_err))` the same as `Err(_)` (i.e., assume delivered / do not refund) consistent with the rationale already applied for promise failures, or (b) independently verify actual token custody after the call (e.g., query `nft_token`/ownership on `token` before crediting a refund) rather than relying solely on the callee-controlled return payload.

### Proof of Concept
`cargo test` plan (near-workspaces sandbox, e.g. under `tests/src/tests/defuse/tokens/nep171.rs`):
1. Deploy a malicious NFT contract exposing `nft_transfer_call` that: internally reassigns the token's owner to the specified `receiver_id`, then returns a JSON string (not `bool`), e.g. `"ok"`.
2. Deposit an NFT from this contract into `env.defuse` for `attacker`, assert `mt_balance_of(attacker, nft_token_id) == 1`.
3. Sign and execute an `NftWithdraw` with `msg: Some("x")`, `receiver_id: attacker_alt`.
4. Assert on both sides of the binding:
   - Actual custody: query the malicious NFT contract and assert `owner_id == attacker_alt` (delivered).
   - Verifier accounting: assert `mt_balance_of(attacker, nft_token_id) == 1` again (re-credited), i.e. `value debited (1) != value delivered (1) + value re-credited (0)` is violated — the sum of delivered + re-credited is `2`, not `1`.
5. Optionally withdraw the phantom balance a second time to a fresh receiver, and assert the malicious contract rejects it (token already moved) while the Verifier still allowed the second withdraw attempt to be scheduled from a positive balance — demonstrating the accounting divergence directly caused the double-existence.

#[inline]
pub fn promise_result_checked_json_with_args<T: MaxJsonLength>(
    result_idx: u64,
    args: T::Args,
) -> PromiseJsonResult<T> {
    let value = env::promise_result_checked(result_idx, T::max_json_length_root(args))?;
    Ok(serde_json::from_slice::<T>(&value))
}

#[inline]
pub fn promise_result_checked_json<T: MaxJsonLength<Args = ()>>(
    result_idx: u64,
) -> PromiseJsonResult<T> {
    promise_result_checked_json_with_args::<T>(result_idx, ())
}

#[inline]
pub fn promise_result_checked_json_with_len<T: MaxJsonLength<Args = (usize, ())>>(
    result_idx: u64,
    length: usize,
) -> PromiseJsonResult<T> {
    let max_len = T::max_json_length_root((length, ()));
    let value = env::promise_result_checked(result_idx, max_len)?;
    Ok(serde_json::from_slice::<T>(&value))
}

/// Returns `Ok(())` if the promise at `result_idx` succeeded with an empty result.
/// This is the expected outcome for void-returning cross-contract calls
/// (e.g. `ft_transfer`, `nft_transfer`, `mt_batch_transfer`).
#[inline]
pub fn promise_result_checked_void(result_idx: u64) -> PromiseResult<()> {
    let data = env::promise_result_checked(result_idx, 0)?;
    debug_assert!(data.is_empty());
    Ok(())
}
