Audit Report

## Title
`do_transfer_ownership`/`do_force_collection_owner` discard the `repatriate_reserved` remainder, permanently desyncing NFT collection deposit accounting - ([File: substrate/frame/nfts/src/features/transfer.rs])

## Summary
`pallet-nfts`'s collection-ownership transfer path calls `T::Currency::repatriate_reserved(&details.owner, &new_owner, details.owner_deposit, Reserved)?` in both `do_transfer_ownership` and `do_force_collection_owner`, and discards the returned `Balance` value. Because `repatriate_reserved` (as implemented in `substrate/frame/balances/src/impl_currency.rs`) returns `Ok(remainder)` for a partial (best-effort, `Polite`) move rather than erroring, a lock/freeze on the old owner's account can leave part of the deposit un-moved while `details.owner` and `details.owner_deposit` are still unconditionally committed as if the full deposit backs the new owner.

## Finding Description
Both call sites are confirmed in the code exactly as claimed: [1](#0-0) [2](#0-1) 

`repatriate_reserved`'s documented and implemented semantics confirm the return value is the *unmoved* remainder, and it is `Ok` even on a partial move (only failing hard for unrelated destination-account errors): [3](#0-2) 

The only guard present, `ensure!(origin == details.owner, ...)`, checks caller identity, not deposit-move completeness: [4](#0-3) 

Immediately after the unchecked `repatriate_reserved` call, `details.owner = new_owner.clone()` is committed unconditionally in both functions, permanently recording `owner_deposit` against the new owner even if only part of it was actually moved. This is structurally identical to the bug already found and fixed in `pallet-assets::transfer_ownership`, documented in `prdoc/pr_12366.prdoc`, which added an `IncompleteDepositTransfer` error specifically because "the previous code discarded the remainder returned by `repatriate_reserved`": [5](#0-4) 

That fix was applied only to `pallet-assets`; `pallet-nfts`'s equivalent call sites remain unpatched.

## Impact Explanation
This corrupts the recorded `owner_deposit` value against `Balances::reserved_balance` for the new/old owner in a public, unprivileged extrinsic path (`transfer_ownership`), directly matching the "Balances/NFTs/... must conserve value and settle exactly once to the rightful beneficiary and amount" pivot. Once desynced, subsequent unreserve/repatriate operations (destroy, further transfers) act on a stale `owner_deposit` figure, either permanently locking part of a user's funds on the old owner or crediting the new owner with an unbacked deposit obligation.

## Likelihood Explanation
Medium: any unprivileged account can self-lock part of their free balance (e.g. via `pallet_balances::set_lock` or any lock-imposing pallet) before calling the public `Nfts::transfer_ownership` extrinsic on their own collection, reproducing the exact condition already demonstrated for the analogous `pallet-assets` bug (`transfer_ownership_fails_when_deposit_is_locked`). No privileged actor, validator, or governance action is required.

## Recommendation
Apply the same fix as `pallet-assets` (`pr_12366`): capture the `Balance` returned by `repatriate_reserved` at both call sites in `do_transfer_ownership` and `do_force_collection_owner`, and reject the dispatch (adding an `IncompleteDepositTransfer`-style error) when the remainder is non-zero, ensuring `Collection` storage rolls back rather than committing a mismatched `owner`/`owner_deposit` state.

## Proof of Concept
1. Account `A` owns an NFT collection with `owner_deposit = D` reserved from `A`.
2. `A` applies `pallet_balances::set_lock` on itself so that a `Polite`/`BestEffort` `repatriate_reserved` can only move part of `D`.
3. `A` calls `Nfts::transfer_ownership(collection, B)`, invoking `do_transfer_ownership`, which calls `repatriate_reserved(&A, &B, D, Reserved)` — see `substrate/frame/nfts/src/features/transfer.rs` lines 142-148.
4. The call returns `Ok(remainder > 0)`; the remainder is discarded, and `details.owner = B` with `details.owner_deposit = D` is committed even though `Balances::reserved_balance(B) < D`.
5. A follow-up unit/integration test mirroring `substrate/frame/assets/src/tests.rs::transfer_ownership_fails_when_deposit_is_locked` (adapted to `pallet-nfts`) demonstrates the reserved-balance mismatch after `transfer_ownership` succeeds.

```rust
	/// Move the reserved balance of one account into the balance of another, according to `status`.
	///
	/// Is a no-op if:
	/// - the value to be moved is zero; or
	/// - the `slashed` id equal to `beneficiary` and the `status` is `Reserved`.
	///
	/// This is `Polite` and thus will not repatriate any funds which would lead the total balance
	/// to be less than the frozen amount. Returns `Ok` with the actual amount of funds moved,
	/// which may be less than `value` since the operation is done on a `BestEffort` basis.
	fn repatriate_reserved(
		slashed: &T::AccountId,
		beneficiary: &T::AccountId,
		value: Self::Balance,
		status: Status,
	) -> Result<Self::Balance, DispatchError> {
		let actual =
			Self::do_transfer_reserved(slashed, beneficiary, value, BestEffort, Polite, status)?;
		Ok(value.saturating_sub(actual))
	}
```
