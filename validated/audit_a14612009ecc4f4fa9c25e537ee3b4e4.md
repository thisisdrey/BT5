The premise of the question already contains its own refutation: `TokenId::to_string()` is not simply the concatenation of the variant's inner `Display` — it always prepends the enum variant's type tag via `TokenId`'s own `Display`/`Debug` implementation, which delegates to `write!(f, "{}:{}", TokenIdType::Nep141, token_id)` (and the analogous `Nep171`/`Nep245` arms) rather than calling the inner type's `Display` alone.### No vulnerability found for this question.

**Reasoning:** The claimed collision cannot occur because `TokenId::to_string()` does not simply forward to the inner `Nep141TokenId`/`Nep171TokenId` `Display` impls — it goes through `TokenId`'s own `Debug`/`Display` impl, which always prepends the discriminant tag before delegating: `write!(f, "{}:{}", TokenIdType::Nep141, token_id)` for the `Nep141` arm and `write!(f, "{}:{}", TokenIdType::Nep171, token_id)` for the `Nep171` arm. [1](#0-0) 

So for any contract id `C` and `C2`:
- `TokenId::Nep141(Nep141TokenId{contract_id:C}).to_string()` == `"nep141:" + C` (the inner `Nep141TokenId::Display` is just `contract_id`, no colon added). [2](#0-1) 
- `TokenId::Nep171(Nep171TokenId{contract_id:C2, nft_token_id:""}).to_string()` == `"nep171:" + C2 + ":"` (the inner `Nep171TokenId::Display` is `"{contract}:{subid}"`, yielding a trailing colon for empty subid). [3](#0-2) 

The literal prefixes `"nep141:"` and `"nep171:"` are always distinct strings (they differ at the 5th/6th character, `41` vs `71`), so the two outputs can **never** be equal regardless of `C`/`C2` — the outer `TokenId` `Display` is not merely "guarding" the inner ambiguity as the question implies; it structurally makes the ambiguity impossible in the first place, since the discriminant is embedded in the same top-level format call, not appended separately afterward. This is directly exercised by the repo's own existing test comparing `"nep141:abc"` vs `"nep171:abc:xyz"`. [4](#0-3) 

Additionally, valid NEAR `AccountId` strings cannot contain a `:` character, so even the inner segments (`C`, `C2`) could never themselves introduce a spurious `:` that shifts the parse boundary. The binding `TokenId::Nep141(...).to_string() != TokenId::Nep171(...).to_string()` holds unconditionally by construction, not by any fragile "outer prefix" convention that could be bypassed.
