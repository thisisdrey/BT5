## Analysis

This confirms a real structural gap. `check_actor_permissions` and `check_account_existence` (`runtime/runtime/src/actions.rs:739-785`, `:787-855`) authorize privileged actions (`AddKey`, `DeleteKey`, `Stake`, `DeployContract`, `DeleteAccount`, etc.) purely by comparing `actor_id != account_id` (a string/`AccountId` equality), with `actor_id` initialized from `receipt.predecessor_id()`. [1](#0-0) [2](#0-1) 

There is no notion of "account generation" or key-set epoch tied into this check — it is satisfied whenever an account named `A` exists at execution time and the receipt's `predecessor_id` string equals `A`, regardless of whether that `A` is the same account (same keys/state) that produced the receipt.

`remove_account` (`core/store/src/utils/mod.rs:504-575`) only clears `Account`, `ContractCode`, `AccessKey`/gas-key rows, and `ContractData` — it deliberately does not touch `TrieKey::BufferedReceipt` rows, which are correctly non-account-keyed (shard-scoped congestion buffer). [3](#0-2) 

Outgoing receipts (including same-shard self-receipts created mid-execution) are routed through `ReceiptSink::forward_or_buffer_receipt`/`try_forward`, which can buffer a receipt due to a *size* (bandwidth-grant) shortfall even when the *gas* limit is `Gas::MAX` for same-shard delivery, since `OutgoingLimit.size` is set from the bandwidth-scheduler grant regardless of same-shard-ness. [4](#0-3) [5](#0-4) 

Buffered receipts are drained later purely FIFO by `forward_from_buffer_to_shard`, with no re-validation against the current identity/generation of the receiver account — they are simply forwarded once bandwidth/gas allow, then applied through the normal `apply_action_receipt` → `apply_action` → `check_actor_permissions` path once received. [6](#0-5) 

I could not fully trace, within the tool budget, the exact code that decides whether same-shard self-receipts always go through `ReceiptSink` (vs. being routed to the `instant_receipts` local queue that bypasses buffering entirely) — this is the crucial precondition and I was unable to confirm the precise conditions governing when a *same-account, self-directed* receipt is "instant" (bypasses the buffer, per the cross-shard-congestion spec's mention of `PromiseYield`) versus queued through `ReceiptSink`. Ordinary asynchronous promise-based self-calls (`Promise::create(env::current_account_id())` from a `FunctionCall`, non-instant) do appear to go through `ReceiptSink::forward_or_buffer_receipt` per `runtime/runtime/src/lib.rs:1104-1116` per the execution spec, which would make this reachable, but I was not able to fully verify the shard-index / bandwidth-grant behavior for a shard sending to itself (whether `apply_state.congestion_info` map even contains a self-entry, and whether `is_link_allowed` permits/denies self-links) to be certain congestion can actually stall a same-shard receipt in practice versus the buffer being effectively unlimited for same-shard delivery.

### Title
Authorization bypass via congestion-buffered self-receipt surviving account deletion/recreation - (`runtime/runtime/src/actions.rs`, `core/store/src/utils/mod.rs`)

### Summary
`remove_account` intentionally does not purge `TrieKey::BufferedReceipt` entries (correct, since they are shard-global congestion state, not account state), but `check_actor_permissions`/`check_account_existence` authorize privileged actions solely by `actor_id == account_id` string equality with no binding to the account's identity/generation at receipt-creation time. If a self-directed action receipt (`predecessor_id == receiver_id == A`) becomes stuck in the outgoing/buffered-receipt congestion queue, and account `A` is deleted and later recreated (by anyone) before the buffer drains, the stale receipt is eventually forwarded and applied against the new `A` and passes the actor-permission check as if it were a legitimate self-call by the new account.

### Finding Description
`check_actor_permissions` (`runtime/runtime/src/actions.rs:739-785`) gates `AddKey`, `DeleteKey`, `Stake`, `DeployContract`, `DeployGlobalContract`, `UseGlobalContract`, `WithdrawFromGasKey`, and `DeleteAccount` purely on `actor_id != account_id`. For an action receipt whose `predecessor_id` equals its own `receiver_id` (a "self-call" produced by a contract issuing a promise to itself), `actor_id` starts as `receipt.predecessor_id()` and this check passes trivially. Crucially, nothing in this check consults access keys, storage roots, or any generation marker of the account — it is a pure account-id string comparison.

`remove_account` (`core/store/src/utils/mod.rs:504-575`) clears `Account`, `ContractCode`, `AccessKey`, gas-key nonces, and `ContractData` for the deleted account, but never inspects or removes rows under `TrieKey::BufferedReceipt`/`TrieKey::BufferedReceiptIndices` (`core/store/src/trie/receipts_column_helper.rs:285-334`), which are keyed by `(receiving_shard, index)`, not by account — by design, since they are the shard-wide congestion buffer.

The buffer is drained later purely FIFO/bandwidth-gated in `forward_from_buffer_to_shard`/`try_forward` (`runtime/runtime/src/congestion_control.rs:338-462`), with no re-check of receiver identity/generation. Once forwarded, the receipt is applied through the ordinary `apply_action_receipt`/`apply_action` path (`runtime/runtime/src/lib.rs:718-955`), re-running `check_account_existence` and `check_actor_permissions` against whatever account currently occupies `A` in state — which, if recreated, is a semantically unrelated account.

Attack outline: an account owner controlling `A` deploys a contract on `A` that issues an asynchronous self-promise receipt (`predecessor_id == receiver_id == A`) carrying a sensitive action (e.g., `AddKey` for an attacker-chosen public key, or `DeployContract`/`Stake`). If that receipt is stuck in the shard's outgoing/incoming congestion buffer (bandwidth-scheduler backpressure), the owner then submits a normal `DeleteAccount` transaction on `A` (self-authorized: `predecessor_id == account_id == A`, satisfying the same `actor_id == account_id` check legitimately) to remove `A` from state, refunding balance to a beneficiary. `remove_account` leaves the buffered self-receipt intact. Later, once `A` is deleted, `A`'s account name becomes available; an unrelated party creates a new account named `A` (fresh keys/state). When bandwidth eventually permits, the stale buffered receipt is forwarded and applied against the new `A`. `check_account_existence` passes because `A` exists again; `check_actor_permissions` passes because `predecessor_id` ("A") still equals `account_id` ("A"). The privileged action executes against the new owner's account without their consent — e.g., silently adding the original attacker's access key to the new owner's account, or staking/locking the new owner's funds.

### Impact Explanation
This is a genuine authorization-escalation-across-accounts bug: a privileged action authorized under one account's lifecycle (and its previous owner/contract) is later executed against a semantically distinct account that happens to reuse the same `AccountId` string, without any check tied to the new account's actual key set or generation. Depending on the buffered action, impact ranges from unauthorized key grants (full account takeover of the new owner) to unauthorized `Stake`/`DeployContract`/`DeployGlobalContract` on the new account — matching the "authorization escalation across accounts" bounty category. It does not directly cause double-spend or state-root divergence (all validators execute the same replay deterministically), so it is not a consensus-split bug, but is a confidentiality/integrity violation against the new account's funds and control.

### Likelihood Explanation
Feasibility is uncertain and non-trivial:
- The attacker must fully control the timing and reachability window: they need a self-directed action receipt to sit in the congestion/bandwidth buffer for long enough to delete and let someone else recreate the same account name, which is largely outside a single unprivileged actor's control (bandwidth backpressure is network/shard-load dependent, not attacker-triggerable on demand for their own shard link).
- It further requires a third party to voluntarily re-register the exact deleted account name before the buffer drains — an assumption that is speculative and not attacker-controlled, significantly reducing real-world exploitability, though not impossible for the attacker to combine with a Sybil/self-triggered congestion attempt or a namesquatting scheme (deleting and quickly re-creating `A` themselves, which would only self-target and not be a genuine victim-facing escalation).
- I was unable to verify within the available tool budget whether same-shard self-receipts are actually routed through the bufferable `ReceiptSink` path versus an "instant receipt" fast path that bypasses buffering, which is the key precondition for reachability.

### Recommendation
Bind authorization for buffered/forwarded receipts to account identity beyond the bare `AccountId` string — e.g., include an account "epoch"/creation nonce in `Account` (bumped on every `CreateAccount`) and validate that self-authorizing buffered receipts were created against the same account epoch, or purge/invalidate any buffered/postponed/delayed receipts addressed to an account when that account is deleted (scan and drop entries whose `receiver_id == predecessor_id == deleted account` from the relevant queues, or tag such receipts so they can be detected and rejected on execution if the account was ever deleted in the interim).

### Proof of Concept
Test-loop integration test:
1. Create account `A` with a contract that, on a specific call, issues a `Promise::create(env::current_account_id())` self-receipt containing `AddKey(attacker_pubkey)`.
2. Engineer congestion/bandwidth backpressure on `A`'s shard-to-self link (e.g., by saturating the bandwidth scheduler grant with other large receipts targeting the same shard) so the self-receipt lands in `TrieKey::BufferedReceipt` rather than being applied immediately; assert via `ShardsOutgoingReceiptBuffer::buffer_len` that it is buffered.
3. Submit `DeleteAccount` from `A`'s owner key, refunding to a beneficiary; assert `A`'s `Account`/`AccessKey` rows are gone but the `BufferedReceipt` entry persists.
4. Have a different signer submit `CreateAccount` for `A` with a fresh key.
5. Drive chunk application forward (reducing congestion) until the buffered receipt is forwarded and applied.
6. Assert (documenting current buggy behavior) that the `AddKey(attacker_pubkey)` action succeeds against the new `A`, i.e., `get_access_key(new_A, attacker_pubkey)` returns `Some`, and that the desired fix would instead reject/drop this receipt (e.g., via `ActionErrorKind::ActorNoPermission` or an explicit "stale receipt" error) so `attacker_pubkey` is never added to the new account.

/// Removes account, code and all access keys and gas keys associated to it.
pub fn remove_account(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
) -> Result<RemoveAccountResult, StorageError> {
    state_update.remove(TrieKey::Account { account_id: account_id.clone() });
    state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });

    let mut gas_key_nonce_count: usize = 0;
    let mut gas_key_nonce_total_key_bytes: usize = 0;

    // Removing access keys and gas key nonces
    let lock = state_update.trie().lock_for_iter();
    let mut keys_to_remove: Vec<TrieKey> = Vec::new();
    for raw_key in state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_access_keys(account_id), &lock)?
    {
        let raw_key = raw_key?;
        let key_handle = trie_key_parsers::parse_key_handle_from_access_key_key(
            &raw_key, account_id,
        )
        .map_err(|_e| {
            StorageError::StorageInconsistentState(
                "Can't parse key handle from raw key for AccessKey".to_string(),
            )
        })?;
        let nonce_index =
            trie_key_parsers::parse_nonce_index_from_gas_key_key(&raw_key, account_id, &key_handle)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse nonce index from raw key for AccessKey".to_string(),
                    )
                })?;
        if let Some(index) = nonce_index {
            gas_key_nonce_count += 1;
            gas_key_nonce_total_key_bytes += raw_key.len();
            keys_to_remove.push(TrieKey::gas_key_nonce(
                account_id.clone(),
                key_handle.clone(),
                index,
            ));
        } else {
            keys_to_remove.push(TrieKey::access_key(account_id.clone(), key_handle.clone()));
        }
    }
    drop(lock);

    for trie_key in keys_to_remove {
        state_update.remove(trie_key);
    }

    // Removing contract data
    let lock = state_update.trie().lock_for_iter();
    let data_keys = state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_contract_data(account_id, &[]), &lock)?
        .map(|raw_key| {
            trie_key_parsers::parse_data_key_from_contract_data_key(&raw_key?, account_id)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse data key from raw key for ContractData".to_string(),
                    )
                })
                .map(Vec::from)
        })
        .collect::<Result<Vec<_>, _>>()?;
    drop(lock);

    for key in data_keys {
        state_update.remove(TrieKey::ContractData { account_id: account_id.clone(), key });
    }
    Ok(RemoveAccountResult { gas_key_nonce_count, gas_key_nonce_total_key_bytes })
}

    fn forward_from_buffer_to_shard(
        &mut self,
        buffer_shard_id: ShardId,
        state_update: &mut TrieUpdate,
        apply_state: &ApplyState,
        shard_layout: &ShardLayout,
    ) -> Result<(), RuntimeError> {
        let mut num_forwarded = 0;
        let mut outgoing_metadatas_updates: Vec<(ByteSize, Gas)> = Vec::new();
        for receipt_result in
            self.outgoing_buffers.to_shard(buffer_shard_id).iter(&state_update.trie, true)
        {
            let receipt = receipt_result?;
            let gas = receipt_congestion_gas(&receipt, &apply_state.config)?;
            let size = receipt_size(&receipt)?;
            let should_update_outgoing_metadatas = receipt.should_update_outgoing_metadatas();
            let receipt = receipt.into_receipt();
            let target_shard_id = receipt.receiver_shard_id(&shard_layout)?;

            match Self::try_forward(
                receipt,
                gas,
                size,
                target_shard_id,
                &mut self.outgoing_limit,
                &mut self.outgoing_receipts,
                apply_state,
                &mut self.stats,
            )? {
                ReceiptForwarding::Forwarded => {
                    self.own_congestion_info.remove_receipt_bytes(size)?;
                    self.own_congestion_info.remove_buffered_receipt_gas(gas.as_gas().into())?;
                    if should_update_outgoing_metadatas {
                        // Can't update metadatas immediately because state_update is borrowed by iterator.
                        outgoing_metadatas_updates.push((ByteSize::b(size), gas));
                    }
                    // count how many to release later to avoid modifying
                    // `state_update` while iterating based on
                    // `state_update.trie`.
                    num_forwarded += 1;
                }
                ReceiptForwarding::NotForwarded(_) => {
                    break;
                }
            }
        }

        self.outgoing_buffers.to_shard(buffer_shard_id).pop_n(state_update, num_forwarded)?;
        for (size, gas) in outgoing_metadatas_updates {
            self.outgoing_metadatas.update_on_receipt_popped(
                buffer_shard_id,
                size,
                gas,
                state_update,
            )?;
        }
        Ok(())
    }

    fn try_forward(
        receipt: Receipt,
        gas: Gas,
        mut size: u64,
        shard: ShardId,
        outgoing_limit: &mut HashMap<ShardId, OutgoingLimit>,
        outgoing_receipts: &mut Vec<Receipt>,
        apply_state: &ApplyState,
        stats: &mut ReceiptSinkStats,
    ) -> Result<ReceiptForwarding, RuntimeError> {
        // There is a bug which allows to create receipts that are above the size limit. Receipts
        // above the size limit might not fit under the maximum outgoing size limit. Let's pretend
        // that all receipts are at most `max_receipt_size` to avoid receipts getting stuck.
        // See https://github.com/near/nearcore/issues/12606
        let max_receipt_size = apply_state.config.wasm_config.limit_config.max_receipt_size;
        if size > max_receipt_size {
            tracing::debug!(
                target: "runtime",
                receipt_id=?receipt.receipt_id(),
                size,
                max_receipt_size,
                "try_forward observed a receipt with size exceeding the size limit",
            );
            size = max_receipt_size;
        }

        // Default case set to `Gas::MAX`: If no outgoing limit was defined for the receiving
        // shard, this usually just means the feature is not enabled. Or, it
        // could be a special case during resharding events. Or even a bug. In
        // any case, if we cannot know a limit, treating it as literally "no
        // limit" is the safest approach to ensure availability.
        let default_gas_limit = Gas::MAX;

        // Since bandwidth scheduler, a shard is not allowed to send any receipts if it doesn't have a grant.
        let default_size_limit = 0;

        let default_outgoing_limit =
            OutgoingLimit { gas: default_gas_limit, size: default_size_limit };
        let forward_limit = outgoing_limit.entry(shard).or_insert(default_outgoing_limit);

        let admission_gas = if ProtocolFeature::ClampOutgoingGasAdmission
            .enabled(apply_state.current_protocol_version)
        {
            gas.min(apply_state.config.congestion_control_config.allowed_shard_outgoing_gas)
        } else {
            gas
        };

        if forward_limit.gas >= admission_gas && forward_limit.size >= size {
            tracing::trace!(target: "runtime", ?shard, receipt_id=?receipt.receipt_id(), "forwarding buffered receipt");
            outgoing_receipts.push(receipt);
            forward_limit.gas = forward_limit.gas.saturating_sub(gas);
            forward_limit.size -= size;
            stats.forwarded_receipts.entry(shard).or_default().add_receipt(size, gas);

            Ok(ReceiptForwarding::Forwarded)
        } else {
            tracing::trace!(target: "runtime", ?shard, receipt_id=?receipt.receipt_id(), "not forwarding buffered receipt");
            Ok(ReceiptForwarding::NotForwarded(receipt))
        }
