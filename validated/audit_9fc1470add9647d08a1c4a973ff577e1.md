### Title
Trusted call whitelisting binds only `(target, selector)` and omits calldata arguments, letting a delegate redirect funds to any recipient/amount - ([File: tare-io__tare-contracts/contracts/TrustedCalls.sol])

### Summary
`TrustedCalls.executeTrustedCall` / `executeTrustedCallBatch` authorize a delegate-supplied call against a Safe purely on the basis of a `(target, selector)` pair (`getTrustKey`). None of the actual calldata arguments — recipient, amount, token id, etc. — are part of the "trust" verification, so a whitelisted call pattern (e.g. an ERC20 `transfer(address,uint256)` on a specific token) authorizes the delegate to invoke it with *arbitrary* parameters. This is the same root cause as the reported `MerkleDistributor` bug: a security-critical field (there, the reward token; here, the call's actual arguments) is left out of the data that is verified/whitelisted, letting the caller substitute a different value than the one the trust decision was meant to cover.

### Finding Description
`trustedCalls[key]` is keyed only by `keccak256(abi.encodePacked(target, selector))`: [1](#0-0) 

`addTrustedCall`/`addTrustedCalls` (guardian-only) register this key: [2](#0-1) 

`executeTrustedCall` then lets *any per-Safe delegate* (a much lower-privileged, unprivileged-by-audit-scope role — added by the Safe itself or a guardian, see `addDelegate`) execute the whitelisted `(target, selector)` with calldata the delegate fully controls: [3](#0-2) 

Because only the 4-byte selector is checked (`data[:4]`), the remaining ABI-encoded arguments (e.g., `to` and `amount` for `transfer(address,uint256)`, or `spender`/`amount` for `approve`) are never bound to the trust decision. If the guardian ever whitelists a state-changing selector on a value-bearing target (an ERC20 token held by the Safe, an `approve`, a `transfer`, a DeFi deposit/withdraw function, etc.) so that delegates can perform some narrow, intended operation, every delegate for that Safe can instead call the same selector with a different recipient or a larger amount than intended — moving the Safe's tokens to an address of their choosing.

This directly parallels the external report: `MerkleDistributor.verifyClaim()` verified `<account, accountIndex, windowIndex, amount>` but omitted `token`, letting the claimant substitute the token field to redirect value; here, `TrustedCalls` verifies `<target, selector>` but omits the call's actual arguments, letting the delegate substitute the argument bytes to redirect value.

By contrast, the sibling module `TrustedSpender` correctly scopes allowances by the full economically-relevant tuple `(token, from, to)` plus an `amount` cap and expiry, so a delegate cannot exceed the Safe-set bounds: [4](#0-3) 

`TrustedCalls` has no equivalent per-parameter binding at all.

### Impact Explanation
If the guardian ever whitelists a value-moving selector (transfer/approve/withdraw-style function) on a target the Safe holds funds in or has approved, every delegate of every Safe using that global whitelist entry can call it with attacker-chosen parameters (recipient, amount, spender) instead of the parameters implicitly intended when the entry was added. This is a diversion/theft of Safe-held assets triggered by an "unprivileged" actor (a delegate, which per the audit's Safe-account invariant must never be able to "spend from another Safe" or exceed its intended scope) — this is in-scope under "Theft, diversion, or unauthorized reassignment of ... assets" and the Smart-account-path invariant that trusted-call surfaces must never let an unprivileged actor spend beyond intended limits.

### Likelihood Explanation
The likelihood depends entirely on which `(target, selector)` combinations guardians register. Because the contract's whole purpose is to let delegates call otherwise-restricted functions on behalf of Safes, and because the interface/spec advertises this as a generic mechanism (not restricted to read-only or non-value-bearing calls), it is reasonably foreseeable that a guardian will whitelist an ERC20 `transfer`/`approve` or a protocol `withdraw` function to enable some specific delegate workflow (e.g., paying a specific counterparty). The moment that happens, every delegate for the Safe — not just the intended calling context — can call that function with fully attacker-controlled arguments.

### Recommendation
Bind the trust decision to the value-determining call parameters, not just `(target, selector)`. Options:
- Include a hash of fixed/allowed argument templates (e.g., allow only a specific `to` and/or capped `amount`) in the trust key, analogous to fixing the missing `token` field in the Merkle leaf.
- Or route value-bearing whitelisted calls through `TrustedSpender`-style allowances (per-route amount caps and expiry) instead of raw arbitrary calldata execution.
- At minimum, document/restrict `TrustedCalls` to non-value-moving (view-safe or parameterless) selectors, and add an explicit require that argument bytes match an approved pattern for any call capable of moving assets.

### Proof of Concept
1. Guardian calls `addTrustedCall(USDC, IERC20.transfer.selector)` intending to let a delegate pay a specific vendor a specific amount from `safeA`.
2. `safeA` (or guardian) adds `delegate` via `addDelegate(safeA, delegate)`.
3. Delegate calls:
```solidity
trustedCalls.executeTrustedCall(
  safeA,
  address(USDC),
  abi.encodeWithSelector(IERC20.transfer.selector, attacker, USDC.balanceOf(safeA))
);
```
4. `getTrustKey(USDC, IERC20.transfer.selector)` is `true`, so the check at `TrustedCalls.sol:115` passes, and `execTransactionFromModuleReturnData` executes the call exactly as encoded — transferring the Safe's entire USDC balance to `attacker`, not the intended vendor/amount.

  /// @inheritdoc ITrustedCalls
  function addTrustedCall(address target, bytes4 selector) external whenNotPaused onlyRole(GUARDIAN_ROLE) {
    require(selector != bytes4(0), InvalidSelector());

    bytes32 key = getTrustKey(target, selector);
    trustedCalls[key] = true;

    emit TrustedCallAdded(target, selector);
  }

  /// @inheritdoc ITrustedCalls
  function addTrustedCalls(
    address[] calldata targets,
    bytes4[] calldata selectors
  ) external whenNotPaused onlyRole(GUARDIAN_ROLE) {
    uint256 length = targets.length;
    require(length == selectors.length, LengthMismatch());
    require(length > 0, EmptyBatch());

    for (uint256 i = 0; i < length; ++i) {
      require(selectors[i] != bytes4(0), InvalidSelector());

      bytes32 key = getTrustKey(targets[i], selectors[i]);
      trustedCalls[key] = true;

      emit TrustedCallAdded(targets[i], selectors[i]);
    }
  }

  /// @inheritdoc ITrustedCalls
  function executeTrustedCall(
    address safe,
    address target,
    bytes calldata data
  ) external whenNotPaused returns (bool success, bytes memory returnData) {
    // Verify sender is delegate for this Safe
    require(delegates[safe][msg.sender], NotADelegate());

    // Extract function selector (first 4 bytes)
    require(data.length >= 4, InvalidSelector());
    bytes4 selector = bytes4(data[:4]);

    // Verify call is trusted
    bytes32 key = getTrustKey(target, selector);
    require(trustedCalls[key], CallNotTrusted());

    // Execute call via Safe
    (success, returnData) = IModuleManager(payable(safe)).execTransactionFromModuleReturnData(
      target,
      0, // value: no ETH sent
      data,
      Enum.Operation.Call
    );

    require(success, ExecutionFailed());
  }

  /// @inheritdoc ITrustedSpender
  function executeTransfer(address token, address from, address to, uint256 amount) external whenNotPaused {
    // Verify sender is a delegate
    require(delegates[from][msg.sender], NotADelegate());

    // Check allowance exists, is sufficient, and has not expired
    Allowance storage allowance = _allowances[token][from][to];
    require(allowance.amount >= amount, InsufficientAllowance());
    require(block.timestamp <= allowance.validUntil, AllowanceExpired());

    // Update allowance if not infinite
    if (allowance.amount != type(uint208).max) {
      allowance.amount -= uint208(amount);
    }

    IERC20(token).safeTransferFrom(from, to, amount);
  }
