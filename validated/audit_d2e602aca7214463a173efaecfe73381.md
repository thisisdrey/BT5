## Analysis

The claimed fault is real, but the actual root cause is broader than the question assumes: the vulnerability isn't that "no pending `content_hash` matches" — it's that the downloader **never verifies** the returned `Attachment` content matches the `content_hash` it originally requested, before persisting it via `insert_instantiated_attachment` with `was_instantiated=1`.

Trace:
1. `AttachmentRequest.content_hash` is the wire-controlled hash the node is trying to resolve [1](#0-0) .
2. The HTTP response is decoded by `decode_atlas_get_attachment`, which only base64/hex-decodes the body into an `Attachment` — **no comparison to the requested `content_hash` is performed anywhere**: [2](#0-1) [3](#0-2) .
3. `extend_with_attachments` blindly inserts `response.attachment` into `self.attachments` (a `HashSet<Attachment>`, keyed by content bytes, not by the original `request.content_hash`): [4](#0-3) .
4. In the `Done` state, every attachment in `context.attachments.drain()` is **unconditionally** persisted via `insert_instantiated_attachment`, regardless of whether `find_all_attachment_instances(&attachment.hash())` found any matching pending instance (an empty `Vec` is not treated as an error/skip condition): [5](#0-4) .
5. `insert_instantiated_attachment` writes the row with `was_instantiated=1`: [6](#0-5) .
6. `evict_expired_uninstantiated_attachments` only deletes rows `WHERE was_instantiated = 0`, so these bogus rows are never reclaimed: [7](#0-6) .

Reachability: a malicious peer only needs to (a) legitimately hold a slot in the node's peer inventory response for a given `index_block_hash`/page (i.e., claim in `/v2/attachments/inv` to have an attachment the node is genuinely trying to resolve, which is normal, unprivileged peer behavior), and (b) when the node subsequently issues `GET /v2/attachments/{content_hash}` to that peer, respond with arbitrary distinct byte content instead of the correct content. This requires no secret, no admin role, and no special permissions — just running a peer node and answering HTTP requests dishonestly, which is exactly the unprivileged threat model in scope.

### Title
Unbounded disk growth via unverified attachment content in `AttachmentsBatchStateContext::extend_with_attachments` / `AttachmentsDownloader::run` - ([File: stackslib/src/net/atlas/download.rs])

### Summary
The Atlas attachment downloader never checks that an `Attachment` returned by a peer in response to a `GET /v2/attachments/{content_hash}` request actually hashes to the requested `content_hash` before persisting it. Any attachment content a malicious peer sends back is unconditionally written to the `attachments` SQLite table with `was_instantiated=1`, and rows with `was_instantiated=1` are never touched by `evict_expired_uninstantiated_attachments` or `evict_k_oldest_uninstantiated_attachments`, causing unbounded permanent disk growth.

### Finding Description
The broken invariant: stored attachment content is supposed to satisfy `Hash160::from_data(&content) == content_hash` for some confirmed on-chain `AttachmentInstance`. This equality is never checked on the download path.

- `AttachmentRequest` carries a `content_hash` the node wants resolved [1](#0-0) .
- The peer's HTTP response is parsed by `decode_atlas_get_attachment`/`GetAttachmentResponse::deserialize`, which just hex-decodes arbitrary bytes into `Attachment` content with no hash check [2](#0-1) .
- `extend_with_attachments` inserts the returned `Attachment` into a `HashSet<Attachment>` keyed by content, completely decoupled from which `content_hash` was requested [4](#0-3) .
- In `run`, for every attachment drained from that set, `insert_instantiated_attachment` is called unconditionally, even when `find_all_attachment_instances(&attachment.hash())` returns an empty vector (meaning nothing on-chain actually points to this content) [5](#0-4) .
- `insert_instantiated_attachment` writes `(hash, content, was_instantiated=1, created_at)` into the `attachments` table [6](#0-5) .
- `evict_expired_uninstantiated_attachments` and `evict_k_oldest_uninstantiated_attachments` both filter `WHERE was_instantiated = 0`, so `was_instantiated=1` rows are permanent regardless of whether any confirmed name operation actually points to that content [8](#0-7) .

Attacker flow: run a peer, respond to the node's `/v2/attachments/inv` polling by marking bits as available for attachments the node is genuinely trying to resolve (a normal, allowed peer action), then when the node issues `GET /v2/attachments/{content_hash}`, return distinct bogus content each time (up to `attachments_max_size`, default 1 MiB) instead of content matching the hash. Each such response becomes a permanent, un-evictable row in `attachments`.

### Impact Explanation
Each malicious response results in up to `attachments_max_size` (min 1 MiB) bytes permanently written to the node's Atlas SQLite database with no eviction path, since only `was_instantiated=0` rows are ever cleaned. This is repeatable per distinct pending `AttachmentInstance` the node is resolving, and an attacker can keep generating fresh `AttachmentInstance`s to resolve against (e.g., BNS `name-update` operations they submit themselves) to keep the attack going indefinitely, leading to unbounded disk exhaustion — matching the "attachment/BNS mismatch" High-severity category (content stored does not correspond to what any committed name operation's `content_hash` points to).

### Likelihood Explanation
- No privileged role, secret, or slot ownership is required — only running an ordinary P2P/RPC-reachable peer.
- The attacker must be selected as a `source` for the request, which only requires answering `/v2/attachments/inv` truthfully-looking (claiming to have the bit set) — this is normal peer behavior, not a bypassed guard.
- Cost to the attacker is minimal (serving HTTP responses); cost to the victim is proportional to `attachments_max_size` per malicious response and fully attacker-controlled.
- Repeatable indefinitely as long as new `AttachmentInstance`s exist to be resolved (attacker can create their own via low-cost BNS transactions).

### Recommendation
In `AttachmentsBatchStateContext::extend_with_attachments` (or in `AttachmentsDownloader::run` before calling `insert_instantiated_attachment`), verify `response.attachment.hash() == request.content_hash` before accepting/storing the attachment; discard and penalize (`bump_failed_requests`) any response whose content hash does not match the requested hash instead of inserting it into `self.attachments`.

### Proof of Concept
Rust test plan (extending `stackslib/src/net/atlas/tests.rs`):
1. Construct an `AtlasDB` and a `BatchedRequestsResult<AttachmentRequest>` where `succeeded` contains N distinct `AttachmentRequest`s (real `content_hash` values corresponding to queued `AttachmentInstance`s), each paired with a `GetAttachmentResponse` whose `attachment.content` produces a **different** `Hash160` that does **not** equal the requested `content_hash`.
2. Call `AttachmentsBatchStateContext::extend_with_attachments` with these results, then simulate the `Done` branch logic (`insert_instantiated_attachment` for each drained attachment).
3. Assert `atlas_db.count_uninstantiated_attachments()` stays `0`.
4. Assert `SELECT COUNT(*) FROM attachments WHERE was_instantiated = 1` grows to N.
5. Call `atlas_db.evict_expired_uninstantiated_attachments()` and re-assert the row count is unchanged (still N), proving the rows are never reclaimed despite matching no confirmed on-chain `content_hash`.

    pub fn extend_with_attachments(
        mut self,
        results: &mut BatchedRequestsResult<AttachmentRequest>,
    ) -> AttachmentsBatchStateContext {
        for (request, response) in results.succeeded.drain() {
            let report = self
                .peers
                .get_mut(request.get_url())
                .expect("Atlas: unable to retrieve reliability report for peer");

            let response = if let Some(r) = response {
                r
            } else {
                report.bump_failed_requests();
                continue;
            };

            if let Ok(response) = response.decode_atlas_get_attachment() {
                self.attachments.insert(response.attachment);
                report.bump_successful_requests();
            } else {
                report.bump_failed_requests();
            }
        }
        let mut events_ids = results.faulty_peers.keys().copied().collect::<Vec<usize>>();
        self.events_to_deregister.append(&mut events_ids);

        self
    }
