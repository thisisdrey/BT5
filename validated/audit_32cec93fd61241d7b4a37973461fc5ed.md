### Title
Checks-Effects-Interactions violation in `collateral-add` credits collateral before token transfer, enabling reentrant withdrawal of uncollateralized funds - (File: mainnet/contracts/market/v0-market-vault.clar)

### Summary
In `v0-market-vault.clar`'s `collateral-add`, the `collateral` map is incremented via `add-user-collateral` inside the function's `let` bindings — which Clarity evaluates immediately, before the body executes — while `receive-tokens` (the actual token pull via `contract-call? ft transfer`) only happens later in the function body. This means the internal collateral balance is credited *before* the tokens are actually received, and a malicious `<ft-trait>` implementation can reenter during `transfer` to withdraw the freshly-credited (but not yet paid-in) collateral.

### Finding Description
`collateral-add` is defined as: [1](#0-0) 

Key ordering issue:
1. The `let` bindings compute `entry`, `updated-mask`, `updated-entry`, and crucially `result (add-user-collateral user-id asset-id amount)`. `add-user-collateral` performs `map-set collateral key updated-collateral-amount` as a side effect at binding-evaluation time [2](#0-1) . This means the `collateral` map already reflects the new, larger balance before any of the function's guard checks or the token transfer occur.
2. Only after this map mutation does the function run `check-impl-auth`, the pause check, the amount check, and then `(try! (receive-tokens ft amount account))`, which performs `(contract-call? asset transfer amount account current-contract none)` [3](#0-2) .
3. Only after the transfer returns does `(insert updated-entry)` persist the updated `mask`/registry entry [4](#0-3) .

Because `ft` is an attacker-supplied `<ft-trait>` principal, the attacker's `transfer` implementation can call back into the market before returning to `v0-market-vault`. Since `check-impl-auth` only asserts `contract-caller == impl` (the `v0-4-market` contract) [5](#0-4) , a reentrant call routed back through the legitimate `v0-4-market` public functions (e.g. `collateral-remove`) still satisfies that check, since `contract-caller` from the vault's perspective is still `v0-4-market`.

During the reentrant `collateral-remove` call on the same `asset-id`, `remove-user-collateral` reads the `collateral` map [6](#0-5)  — which already includes the amount just credited by the outer `collateral-add`, even though those tokens were never actually transferred into the vault (the transfer that would have moved them is still executing, mid-callback). The attacker can therefore remove/withdraw collateral value that was never deposited, receiving real tokens via `send-tokens` while the outer `collateral-add`'s token pull either has not yet executed or is executed with attacker-controlled semantics.

This is a straightforward Checks-Effects-Interactions (CEI) violation: state effects (`add-user-collateral`'s `map-set`) occur before the external interaction (`receive-tokens`), and the registry `mask` commit (`insert`) also occurs after the interaction rather than before, widening the reentrancy window further.

### Impact Explanation
This allows direct theft of protocol/user funds: an attacker can synthesize collateral credit without ever transferring real tokens in, and drain it via a reentrant `collateral-remove` (or use the phantom collateral to inflate borrowing power via `borrow`, since debt operations rely on the same `collateral` map that is prematurely mutated). This matches the Critical severity category "direct theft of user funds at rest or in motion" / protocol insolvency, since the vault's covered collateral no longer matches the collateral actually backing debt across all users.

### Likelihood Explanation
The preconditions are fully within an unprivileged attacker's control: deploy a malicious contract implementing `<ft-trait>` and pass it as `ft` to `v0-4-market`'s collateral-add/supply-collateral-add entrypoint, which is a normal public call. No DAO, oracle, or privileged role is needed. Capital cost is only the STX transaction fee (and possibly a real initial collateral deposit to establish a tracked position via `resolve-or-create`, but the exploited amount need not be fully backed). The attack is repeatable every block since it depends only on contract-call ordering, not on chain state races or miner cooperation.

### Recommendation
Reorder `collateral-add` (and audit `collateral-remove`, `debt-add-scaled`, `debt-remove-scaled` similarly) to follow strict Checks-Effects-Interactions: perform `receive-tokens` (the external call) first, and only mutate the `collateral` map and call `insert` to commit the updated registry entry after the transfer has successfully completed. Concretely, move `(add-user-collateral ...)` out of the `let` header and into the function body after `(try! (receive-tokens ft amount account))` succeeds, and ensure `insert updated-entry` also happens only after the token transfer confirms. Consider adding an explicit reentrancy guard (e.g. a `bool` lock data-var checked/set/cleared around state-mutating public entrypoints) as defense in depth.

### Proof of Concept
Clarinet simnet test plan:
1. Deploy a malicious `<ft-trait>` contract `evil-ft` whose `transfer` function, when called with a specific trigger amount/sender, calls back into `v0-4-market.collateral-remove` (or `borrow`) for the same `asset-id` before returning `(ok true)`.
2. Set up attacker account with an existing tracked position (`resolve-or-create` via a legitimate small deposit) so `entry`/`mask` pre-exist.
3. Call `v0-4-market.collateral-add` (or `supply-collateral-add`) with `ft = evil-ft`, `amount = X`, `asset-id = A`.
4. Inside `evil-ft`'s `transfer`, reenter `v0-4-market.collateral-remove` for asset `A` with `amount = X`, `recipient = attacker`.
5. Assert:
   - The reentrant `collateral-remove` call succeeds and transfers real underlying tokens to the attacker (via `send-tokens`), even though `evil-ft`'s transfer never actually moved value into the vault.
   - After both calls complete, `map-get? collateral { id: user-id, asset: A }` in `v0-market-vault` does NOT equal the sum of legitimate deposits minus legitimate removals — it is inflated/depleted incorrectly relative to real token flows, i.e., the vault's tracked collateral diverges from actual token custody.
   - Compare against expected behavior: the reentrant call should either see pre-`collateral-add` balances (blocking the free withdrawal) or the whole transaction should abort; the observed behavior (success with phantom balance) demonstrates the vulnerability.
