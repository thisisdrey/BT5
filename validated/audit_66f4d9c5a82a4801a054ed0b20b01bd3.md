Based on my research, I found a genuine structural analog to the reported bug in the `PendingTransactionQueue` / `PendingTxSession` mechanism, which was clearly built for the same class of problem the report describes: tracking "pending" (not-yet-certified) resource commitments per-account without atomically reserving them, then gating a critical decision on the aggregate pending state.

### Title
Race Between `get_pending_constraints()` Snapshot and Chunk Inclusion Allows Multiple Transactions to Pass Balance Validation Against the Same Unreserved Funds - (File: `chain/client/src/pending_transaction_queue.rs`)

### Summary
The vault bug lets a user create a withdrawal "reservation" (`totalPendingShares += shares`) without actually locking the underlying shares, so the same balance can be referenced by multiple pending requests and validated only against a stale, non-atomic snapshot (`balanceOf(msg.sender)`). `nearcore`'s new pending-transaction-queue subsystem, added to support optimistic multi-transaction admission ahead of certification (used by `PendingTxSession::check_pending` during chunk production, and by `PendingTransactionQueue::get_pending_constraints` for RPC-side balance/nonce checks), has the analogous shape: a per-account `paid_from_balance`/`paid_from_gas_key` aggregate is only updated when a transaction is actually included in a chunk (`add_chunk_transactions`), not at the moment a transaction is admitted/broadcast via the RPC path.

### Finding Description
`PendingTransactionQueue::get_pending_constraints()` reads a snapshot of `paid_from_balance` for a signer purely from `pending_accounts`, which is populated only by `add_chunk_transactions()` when transactions are already included in a block's chunk: [1](#0-0) 

The per-account balance commitment is only added to the queue once a chunk containing the transaction is produced: [2](#0-1) 

Contrast this with the in-chunk-production path, `PendingTxSession::check_pending`, which explicitly tracks a *session-local* optimistic reservation (`session_access_key_tx_counts`, `session_deploy_tx_counts`, `session_gas_key_withdrawals`) to account for multiple transactions being admitted within the same chunk-production pass before they're committed to the shared queue: [3](#0-2) [4](#0-3) 

This session-local tracking exists precisely because the authors recognized that reading a shared "pending" aggregate without reserving against it invites double-counting of the *same* underlying balance across multiple transactions admitted before certification — the same root cause as the vault's `requestWithdrawal()`, which checks `balanceOf(msg.sender)` without subtracting already-pending requests. However, this mitigation is scoped only to a single `PendingTxSession` (one chunk-production pass on one shard). The RPC admission path (`get_pending_constraints`, consumed in `chain/client/src/rpc_handler.rs` and enforced against account balance in `runtime/runtime/src/verifier.rs`) has no equivalent session/reservation: it takes a snapshot under a brief lock, releases it, and the actual reservation into `pending_accounts` only happens later, when the transaction is included in a chunk via `add_chunk_transactions`.

Because there is a window between "transaction accepted by RPC and forwarded to be included in some chunk" and "transaction actually appears in `add_chunk_transactions`", concurrently submitted transactions from the same signer (whether via the same RPC node or different equally-valid RPC/validator paths) can each independently read the same `paid_from_balance` snapshot that has not yet accounted for the other's pending cost — mirroring exactly how the vault's `requestWithdrawal()` validates `shares` against `balanceOf(msg.sender)` without subtracting prior in-flight (but not-yet-executed) requests. I was not able to fully trace the exact call site of `get_pending_constraints` inside `chain/client/src/rpc_handler.rs` or the precise point where `PendingConstraints` is combined with account balance inside `runtime/runtime/src/verifier.rs` (grep only, not fully read due to iteration limits), so the exact severity of the race (e.g., whether the underlying `TrieUpdate`/ephemeral state still provides a secondary, authoritative balance check at actual execution time) is not fully confirmed from this pass.

### Impact Explanation
If the RPC/mempool admission snapshot is the only gate preventing an account from having more pending cost admitted than its real balance can cover, an attacker could submit many transactions in rapid succession before any of them are aggregated into `pending_accounts`, each individually validated as affordable, inflating the effective "pending" balance commitment beyond the account's actual balance. Depending on whether a stricter, atomic check exists later at actual chunk-inclusion/execution time, this could result in transactions being wrongly admitted (analogous to inflating `totalPendingShares`) and/or wasted chunk space/gas being consumed on transactions that will ultimately fail at execution — a resource-exhaustion / correctness gap in the balance-reservation invariant the new gas-key/pending-transaction-queue feature depends on.

### Likelihood Explanation
This requires an ordinary signer to simply submit multiple transactions in quick succession from the same account/access key — no privileged access, no validator/node compromise, and no reliance on network-layer attacks. This is a very low-cost, easily reproducible action for any client, matching the low-cost/low-skill nature of the original report's exploit.

### Recommendation
- Ensure that the RPC-side admission check (`get_pending_constraints`) atomically reserves the committed balance the moment a transaction is accepted for propagation, not only when it's later aggregated via `add_chunk_transactions`, so concurrently-submitted transactions from the same account cannot each be validated against the same stale balance snapshot.
- Confirm and, if necessary, strengthen a second authoritative balance check at actual chunk-inclusion/execution time (in the ephemeral `TrieUpdate` or equivalent) so that even if the pre-admission snapshot is stale, an account can never have its total pending cost exceed its real balance across all in-flight-but-uncertified transactions.
- Apply the same per-session reservation discipline already used in `PendingTxSession` (session-local optimistic counters) to the RPC admission path.

### Proof of Concept
1. An account holds just enough balance for one transaction of cost `C`.
2. The attacker rapidly submits N transactions (each with cost `C`) from that account via RPC before any of them is included in a chunk (before `add_chunk_transactions` runs for any of them).
3. Each of the N `get_pending_constraints()` calls reads a `pending_accounts` snapshot that reflects none of the other N-1 in-flight transactions' cost, since `pending_accounts` is only updated by `add_chunk_transactions` upon actual chunk inclusion.
4. All N transactions could pass the balance-sufficiency check performed with `PendingConstraints`, exceeding the account's real balance in aggregate — unless a separate, atomic execution-time check in the runtime's `TrieUpdate`/`verifier.rs` independently rejects the excess (this final safety net was not fully confirmed within the scope of this review).

    pub fn add_chunk_transactions(
        &mut self,
        block_hash: CryptoHash,
        transactions: &[SignedTransaction],
        config: &RuntimeConfig,
        gas_price: Balance,
    ) {
        let mut chunk_data = PendingChunkData {
            accounts: HashMap::new(),
            nonces: HashMap::new(),
            gas_key_costs: HashMap::new(),
        };

        for signed_tx in transactions {
            let tx = &signed_tx.transaction;
            let signer_id = tx.signer_id().clone();
            let public_key = tx.public_key().clone();
            let nonce_index = tx.nonce().nonce_index();
            let nonce = tx.nonce().nonce();
            let is_gas_key_tx = nonce_index.is_some();

            let cost = match tx_cost(config, tx, gas_price) {
                Ok(cost) => cost,
                Err(e) => {
                    tracing::warn!(
                        target: "client",
                        ?e,
                        "tx_cost failed for block transaction in pending transaction queue"
                    );
                    continue;
                }
            };

            // Update per-account aggregates.
            let chunk_account = chunk_data.accounts.entry(signer_id.clone()).or_default();
            if is_gas_key_tx {
                // Gas key tx: only deposit_cost is paid from account balance.
                chunk_account.paid_from_balance =
                    chunk_account.paid_from_balance.saturating_add(cost.deposit_cost);
            } else {
                // Access key tx: total_cost is paid from account balance.
                chunk_account.access_key_tx_count += 1;
                chunk_account.paid_from_balance =
                    chunk_account.paid_from_balance.saturating_add(cost.total_cost);
            }
