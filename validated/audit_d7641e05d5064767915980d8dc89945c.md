### Title
Stale `PromiseYieldReceipt` action list (including `DeleteAccount`) survives account deletion and executes against the recreated account, draining its funds - (File: `core/store/src/utils/mod.rs`)

### Summary
`remove_account` fails to purge `TrieKey::PromiseYieldReceipt` / `TrieKey::PromiseYieldTimeout` (and postponed-receipt bookkeeping) associated with a deleted account. If a pending yield's action list contains a `DeleteAccount{beneficiary}` action created before deletion, the timeout resume mechanism will later replay that action against the same account name once it is recreated and funded, transferring the new balance to the attacker-chosen `beneficiary_id` without any authorization from the new incarnation of the account.

### Finding Description
1. A contract on account `A` calls `promise_yield_create(...)`, which creates a `PromiseYield` receipt with a mandatory `FunctionCall` callback action and enqueues a timeout entry (`enqueue_promise_yield_timeout`, `runtime/runtime/src/function_call.rs:161-169`).
2. Using the returned `promise_idx`, the contract calls `promise_batch_action_delete_account(promise_idx, beneficiary_id)` to append `DeleteAccount{beneficiary_id}` as the (final) action of that same receipt — allowed since `DeleteActionMustBeFinal` only requires it be last in the list (`runtime/runtime/src/action_validation.rs:99-103`).
3. The `PromiseYield` receipt is stored under `TrieKey::PromiseYieldReceipt{receiver_id: A, data_id}` and awaits resume (`runtime/runtime/src/lib.rs:1495-1499`).
4. The account `A` is deleted via a normal `DeleteAccount` transaction. `action_delete_account` → `remove_account` clears `Account`, `ContractCode`, access keys, and `ContractData`, but leaves `PromiseYieldReceipt`/`PromiseYieldTimeout` entries untouched (`core/store/src/utils/mod.rs:505-575`).
5. Account `A` is later (re)created — by the same signer or, in principle, by anyone able to construct that account id — and funded with a fresh deposit.
6. Before the funding party notices, `resolve_promise_yield_timeouts` reaches the entry's `expires_at` block height. It checks only `state_update.contains_key(&promise_yield_key)` (still true, since it was never cleaned up) and synthesizes a `PromiseResume` receipt destined for `A` (`runtime/runtime/src/lib.rs:3046-3097`), independent of any current owner action.
7. When this `PromiseResume` is applied, the runtime looks up and executes the stale `PromiseYieldReceipt`'s action list against the now-recreated `A` (`runtime/runtime/src/lib.rs:1511-1562`): the `FunctionCall` callback runs (or fails harmlessly), followed by the still-final `DeleteAccount{beneficiary_id}` action, which pays out `A`'s *current* (fresh) balance to the attacker's `beneficiary_id` and deletes the account (`runtime/runtime/src/actions.rs:364-389`).

No check anywhere ties the receipt's authorization to the specific "incarnation" of the account (e.g., a generation counter, or purging pending yields on deletion), so a privileged action queued under the old incarnation is blindly replayed against the new one.

### Impact Explanation
This is a value-conservation / authorization-exactness violation: funds deposited into a freshly (re)created account can be unilaterally redirected to a beneficiary chosen by whoever controlled the account before its deletion, without any signature or consent from the new account state. This matches the NEAR "theft of user funds" bounty category. The practical blast radius depends on who can be induced to fund the exact deleted account name (see Likelihood); the underlying state-hygiene defect is unconditionally present and reproducible in a runtime/apply-based test.

### Likelihood Explanation
- Cost to the attacker is minimal: a single contract deployment and a couple of self-calls (`promise_yield_create` + `promise_batch_action_delete_account`), then a normal `DeleteAccount` transaction. No validator/node access required — fully reachable by an ordinary funded account and its own contract.
- The mechanism is deterministic and fully reproducible: the attacker controls the yield timeout length (bounded by `yield_timeout_length_in_blocks`) and the exact block height at which the stale action fires.
- The scenario is unconditionally demonstrable when the same party performs both the delete and the later recreate/fund steps (which is sufficient to prove the underlying bug — the runtime does not distinguish "my own funds, moved to my own account with my consent" from "arbitrary future funds sent to this account name"). Extending this to an unrelated victim requires that victim to independently choose to (re)create and fund the exact same account id within the timeout window — feasible mainly for reclaimable/registrar-mediated (e.g., top-level `.near`) names, but this leg is harder to force without cooperation from the new owner and is not required to establish the vulnerability itself.

### Recommendation
On account deletion (`remove_account` / `action_delete_account`), purge all pending state tied to the account's identity that could later be replayed with stale authority, specifically:
- Any `TrieKey::PromiseYieldReceipt` entries for `receiver_id == account_id` (and their `PromiseYieldStatus` / yield-id mappings), plus removing (or invalidating) the corresponding `TrieKey::PromiseYieldTimeout` queue entries so `resolve_promise_yield_timeouts` cannot resurrect them.
- Any `TrieKey::PostponedReceipt` / `TrieKey::PostponedReceiptId` / `TrieKey::PendingDataCount` entries for the account.
Alternatively/additionally, bind yield receipts to an account "incarnation" (e.g., store and check a creation nonce/generation on the account, and drop yields whose recorded generation doesn't match the current account's generation) so that even if cleanup is missed, replay against a different incarnation is rejected.

### Proof of Concept
Runtime/apply integration test outline (similar style to `runtime/runtime/src/tests/apply.rs` / `test-loop-tests/src/tests/yield_timeouts.rs`):
1. Deploy a test contract (e.g., `rs_contract`) to account `A` funded with balance `B1`.
2. Call a method that invokes `promise_yield_create(method_name="noop_callback", ...)` to obtain `promise_idx`/`data_id`, then calls `promise_batch_action_delete_account(promise_idx, beneficiary_id=ATTACKER)` to append the action to the same receipt. Assert the `PromiseYieldReceipt` for `(A, data_id)` exists in state and its action list is `[FunctionCall, DeleteAccount{ATTACKER}]`.
3. Submit `DeleteAccount{beneficiary_id=A_OWNER}` on `A` (from `A` itself) and apply it. Assert `A`'s `Account` entry is gone, but `TrieKey::PromiseYieldReceipt{A, data_id}` and the corresponding `PromiseYieldTimeout` entry are still present in the trie.
4. Recreate `A` via `CreateAccount` + `Transfer` with fresh deposit `B2` (a materially different amount than `B1`, from a different funding transaction), asserting `A.amount == B2`.
5. Advance `block_height` past the yield's `expires_at` and run `process_receipts`/`resolve_promise_yield_timeouts` followed by the resulting `PromiseResume` application.
6. Assert: `A`'s account is deleted again, `ATTACKER`'s balance increased by `B2` (via a `Receipt::new_balance_refund`), and this occurred without any `DeleteAccount` transaction signed against the new incarnation of `A`.

/// Removes account, code and all access keys and gas keys associated to it.
pub fn remove_account(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
) -> Result<RemoveAccountResult, StorageError> {
    state_update.remove(TrieKey::Account { account_id: account_id.clone() });
    state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });

    let mut gas_key_nonce_count: usize = 0;
    let mut gas_key_nonce_total_key_bytes: usize = 0;

    // Removing access keys and gas key nonces
    let lock = state_update.trie().lock_for_iter();
    let mut keys_to_remove: Vec<TrieKey> = Vec::new();
    for raw_key in state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_access_keys(account_id), &lock)?
    {
        let raw_key = raw_key?;
        let key_handle = trie_key_parsers::parse_key_handle_from_access_key_key(
            &raw_key, account_id,
        )
        .map_err(|_e| {
            StorageError::StorageInconsistentState(
                "Can't parse key handle from raw key for AccessKey".to_string(),
            )
        })?;
        let nonce_index =
            trie_key_parsers::parse_nonce_index_from_gas_key_key(&raw_key, account_id, &key_handle)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse nonce index from raw key for AccessKey".to_string(),
                    )
                })?;
        if let Some(index) = nonce_index {
            gas_key_nonce_count += 1;
            gas_key_nonce_total_key_bytes += raw_key.len();
            keys_to_remove.push(TrieKey::gas_key_nonce(
                account_id.clone(),
                key_handle.clone(),
                index,
            ));
        } else {
            keys_to_remove.push(TrieKey::access_key(account_id.clone(), key_handle.clone()));
        }
    }
    drop(lock);

    for trie_key in keys_to_remove {
        state_update.remove(trie_key);
    }

    // Removing contract data
    let lock = state_update.trie().lock_for_iter();
    let data_keys = state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_contract_data(account_id, &[]), &lock)?
        .map(|raw_key| {
            trie_key_parsers::parse_data_key_from_contract_data_key(&raw_key?, account_id)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse data key from raw key for ContractData".to_string(),
                    )
                })
                .map(Vec::from)
        })
        .collect::<Result<Vec<_>, _>>()?;
    drop(lock);

    for key in data_keys {
        state_update.remove(TrieKey::ContractData { account_id: account_id.clone(), key });
    }
    Ok(RemoveAccountResult { gas_key_nonce_count, gas_key_nonce_total_key_bytes })
}
