### Title
`LinkRepositoryToObjectPool` links a repository to an arbitrary, unrelated object pool without verifying a fork/ownership relationship, enabling cross-repository object disclosure - ([File: internal/gitaly/service/objectpool/link.go])

### Summary
`CLGauge.deposit()` failed to verify that the staked LP position actually belongs to the pool the gauge is bound to, letting an attacker stake liquidity from a fake/unrelated pool and drain rewards meant for the real pool's providers. The analogous root cause exists in Gitaly's Git object pool subsystem: `LinkRepositoryToObjectPool` links any `repository` to any `object_pool` supplied in the same RPC request, without checking that the pool was actually derived from (or is otherwise legitimately associated with) that repository.

### Finding Description
`LinkRepositoryToObjectPool` accepts two independent repository identifiers in the request — `repository` (`target_repository`) and `object_pool` (`additional_repository`) [1](#0-0) . The handler only validates that `repository` is a well-formed, existing repository via `s.locator.ValidateRepository`, and resolves the `object_pool` via `poolForRequest`; it performs no check that the pool was created from this repository (e.g. via `CreateObjectPool`) or is otherwise a legitimate ancestor/fork relative: [2](#0-1) 

The lower-level `Link` function similarly only checks whether the repository's `objects/info/alternates` file already points at *some* pool; if not linked yet, it unconditionally writes the given pool's path into the alternates file: [3](#0-2) 

Once a repository's `alternates` file references an unrelated pool's `objects` directory, standard Git object lookup will transparently read objects from that pool for any operation on the member repository (clone, blob/commit/tree access, etc.), because Git treats alternates as extensions of the local object store.

The comment for `QuarantineDirectoryPrefix` explicitly documents the general design principle that is missing here — that quarantine/alternate directories must be provably tied to the repository they're used with: [4](#0-3) 

But this "ownership" verification pattern is not applied to `LinkRepositoryToObjectPool`'s pool argument. There is no `CLGauge`-style check (equivalent to comparing `token0`/`token1`/`tickSpacing` against the gauge's pool) that the `object_pool` being linked is the one that was actually created from `repository`'s origin, or belongs to the same fork network.

### Impact Explanation
If an attacker can invoke `LinkRepositoryToObjectPool` (directly, or indirectly through any code path that forwards attacker-influenced repository/pool identifiers — e.g., a compromised or buggy caller passing user-controlled `object_pool` fields), they can attach a victim's private repository to a pool the attacker controls, or attach a repository they control to a private object pool (which was created from a private "primary" repository) to read that pool's objects. Because pool objects become part of the effective object database of the linked repository, any subsequent `Clone`/`Fetch`/blob-read RPC against the attacker's linked repository would expose commits, trees, and blobs — including all history — of the pool's private objects. This is a cross-repository object disclosure vulnerability, matching the analog class explicitly called out as acceptable in the validation criteria ("concrete... cross-repository object access").

### Likelihood Explanation
Exploitability depends on whether an ordinary/unprivileged caller can reach this RPC with attacker-chosen `object_pool` and `repository` values. In the intended GitLab architecture this RPC is invoked internally by Rails only in fork-creation flows where the pool is derived from `CreateObjectPool` on the correct origin, so a compromise typically requires either (a) a caller elsewhere in the stack forwarding user-influenced identifiers into this RPC, or (b) direct gRPC access (e.g., a malicious/compromised Praefect node or an internal actor with API access). I could not fully verify from the indexed code where/whether GitLab Rails validates the pool-repository relationship before calling this RPC (that logic lives outside Gitaly, in gitlab-org/gitlab), so likelihood is uncertain without that context, but Gitaly itself provides no server-side enforcement of the relationship, which is the crux of the reported analog.

### Recommendation
Add a check in `LinkRepositoryToObjectPool` (and/or the lower-level `Link`) requiring that the requested `object_pool` is provably associated with the `repository`, analogous to the Velodrome fix of validating `token0`/`token1`/`tickSpacing` against the gauge's recorded pool. Concretely:
- Persist pool provenance when `CreateObjectPool` is invoked (e.g., a stored primary/origin repository reference for the pool), and verify at link-time that `repository`'s fork network / origin matches that provenance, or
- Require that the pool already contains repository-specific metadata (e.g., a marker written during `CreateObjectPool`) that `Link` checks against before creating or trusting the alternates entry.

### Proof of Concept
1. Attacker has write access to `repoA` (their own repository) and knows the storage-relative path of `objectPoolB`, a private object pool created from a victim's private repository `repoB` (pool paths are deterministic/discoverable relative paths under a storage, as seen in tests such as `internal/git/objectpool/link_test.go` which reference an object pool by a computed relative path).
2. Attacker calls `LinkRepositoryToObjectPool` with `repository = repoA` and `object_pool = objectPoolB`.
3. `link.go`'s handler validates only that `repoA` is a valid repository and that the pool resolves; it never checks that `objectPoolB` was actually created from `repoA` [2](#0-1) .
4. `Link` writes `objectPoolB`'s objects path into `repoA/objects/info/alternates` since `repoA` was not previously linked [5](#0-4) .
5. Attacker then clones/fetches `repoA`, and Git transparently serves objects reachable via the alternates directory (i.e., `repoB`'s deduplicated objects in the pool), disclosing private repository content.

func (s *server) LinkRepositoryToObjectPool(ctx context.Context, req *gitalypb.LinkRepositoryToObjectPoolRequest) (*gitalypb.LinkRepositoryToObjectPoolResponse, error) {
	repository := req.GetRepository()
	if err := s.locator.ValidateRepository(ctx, repository); err != nil {
		return nil, structerr.NewInvalidArgument("%w", err)
	}

	pool, err := s.poolForRequest(ctx, req)
	if err != nil {
		return nil, err
	}

	repo := s.localRepoFactory.Build(repository)

	if err := pool.Link(ctx, repo); err != nil {
		return nil, structerr.NewInternal("%w", err)
	}

	return &gitalypb.LinkRepositoryToObjectPoolResponse{}, nil

// QuarantineDirectoryPrefix returns a prefix for use in the temporary directory. The prefix is
// based on the relative repository path and will stay stable for any given repository. This allows
// us to verify that a given quarantine object directory indeed belongs to the repository at hand.
// Ideally, this function would directly be located in the quarantine module, but this is not
// possible due to cyclic dependencies.
func QuarantineDirectoryPrefix(repo Repository) string {
	hash := [20]byte{}
	if repo != nil {
		hash = sha1.Sum([]byte(repo.GetRelativePath()))
	}
	return fmt.Sprintf("quarantine-%x-", hash[:8])
}
