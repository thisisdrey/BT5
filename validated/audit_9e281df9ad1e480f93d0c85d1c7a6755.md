### Title
Integer overflow in `FindCommits` limit/offset arithmetic allows negative `--max-count` and unbounded response streaming - ([File: internal/gitaly/service/commit/find_commits.go])

### Summary
The `FindCommitsRequest.Limit` and `FindCommitsRequest.Offset` fields (`int32`, fully client-controlled, reachable via the unprivileged `CommitService.FindCommits` RPC) are combined via unchecked addition when `calculateOffsetManually` returns true, mirroring the unbounded-config-arithmetic pattern from the referenced report (`slippageThresholdGmxBps` with no upper bound feeding into `MAX_BPS - slippageThresholdGmxBps`).

### Finding Description
In `getLogCommandSubCmd`, when `git-log --follow` is combined with explicit paths, Gitaly cannot use `--skip` for the offset (documented as incompatible with `--follow`) and instead folds the offset into the count: [1](#0-0) 

Both `req.GetLimit()` and `req.GetOffset()` are attacker-controlled `int32` values sent directly in the `FindCommitsRequest` protobuf message, with no visible upper-bound clamping before this arithmetic. The only guard present is `req.GetOffset() > 0`; there is no check that `limit + offset` stays within `int32` range. Supplying `Limit` and `Offset` values that sum past `math.MaxInt32` causes silent `int32` wraparound in Go, producing a negative `limit`. That negative value is then interpolated directly into a git CLI flag:
```go
subCmd.Flags = append(subCmd.Flags, gitcmd.Flag{Name: fmt.Sprintf("--max-count=%d", limit)})
```
This is structurally identical to the reported bug class: an unbounded/unvalidated numeric quantity is used in arithmetic feeding directly into a downstream operation (there, an on-chain slippage calculation; here, a `git log` argument), with no bound placed on the input prior to the computation.

### Impact Explanation
`git log`/`git-log(1)` treats a negative `--max-count` as "no limit" rather than raising an error (unlike the Solidity case, which reverts). Consequently, a value that the caller intended as an upper bound on returned commits can be silently converted into an unbounded request, causing `FindCommits` to stream the entire history of the (potentially huge) repository instead of the small page the client expected. This is a resource-exhaustion / DoS vector against the `CommitService.FindCommits` RPC handler: an ordinary, authenticated Gitaly client can trigger effectively unbounded CPU/memory/I/O usage server-side by choosing `Limit`/`Offset` values that overflow the addition, all without any special privilege beyond normal RPC access.

### Likelihood Explanation
The RPC is reachable by any client authorized to call Gitaly (which, in GitLab's architecture, includes ordinary users through Workhorse/API proxied calls). Triggering the overflow only requires setting `Follow=true`, non-empty `Paths`, and large `Limit`/`Offset` values — no repository state, timing, or race condition is needed, making this straightforward and reliably reproducible.

### Recommendation
Validate `Limit` and `Offset` in `validateFindCommitsRequest` (or equivalent) to reject negative values and to cap their sum below `math.MaxInt32`, or perform the addition using a wider integer type (`int64`) and clamp the result before formatting the `--max-count` flag. Reject or clamp any resulting non-positive `limit` explicitly rather than passing it through to `git log`.

### Proof of Concept
1. Call `CommitService.FindCommits` against any non-trivial repository with:
   - `Follow = true`
   - `Paths = ["some/path"]` (forces `calculateOffsetManually` to return true)
   - `Limit = 2147483000` (near `math.MaxInt32`)
   - `Offset = 2147483000`
2. `limit := req.GetLimit(); limit += req.GetOffset()` overflows `int32`, wrapping to a negative number.
3. Gitaly issues `git log --max-count=<negative> --follow ... -- some/path`, which git treats as unlimited, causing the full commit history to be walked and streamed back, exhausting handler resources for what the client believed was a small, paginated request. [2](#0-1)

```go
func getLogCommandSubCmd(req *gitalypb.FindCommitsRequest) gitcmd.Command {
	logFormatOption := "--format=%H"
	// To split the commits by '\x01' instead of '\n'
	if req.GetIncludeShortstat() {
		logFormatOption = "--format=%x01%H"
	}
	if req.GetTrailers() {
		logFormatOption += "%x00%(trailers:unfold,separator=%x00)"
	}

	if len(req.GetIncludeReferencedBy()) > 0 {
		// Delimit ref names with '\x02' to avoid confusing with trailers
		logFormatOption += "%x02%D"
	}

	subCmd := gitcmd.Command{Name: "log", Flags: []gitcmd.Option{gitcmd.Flag{Name: logFormatOption}}}

	//  We will perform the offset in Go because --follow doesn't play well with --skip.
	//  See: https://gitlab.com/gitlab-org/gitlab-ce/issues/3574#note_3040520
	if req.GetOffset() > 0 && !calculateOffsetManually(req) {
		subCmd.Flags = append(subCmd.Flags, gitcmd.Flag{Name: fmt.Sprintf("--skip=%d", req.GetOffset())})
	}
	limit := req.GetLimit()
	if calculateOffsetManually(req) {
		limit += req.GetOffset()
	}
	subCmd.Flags = append(subCmd.Flags, gitcmd.Flag{Name: fmt.Sprintf("--max-count=%d", limit)})
```
