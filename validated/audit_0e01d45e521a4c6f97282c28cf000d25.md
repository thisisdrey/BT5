Audit Report

## Title
Coretime sale pricing derives `sellout_price`/`target_price` from a single, timing-manipulable purchase rather than a genuine market-wide observation - (File: `substrate/frame/broker/src/utility_impls.rs`)

## Summary
`purchase_core` sets `sale.sellout_price` to the price of whichever single purchase happens to be the one that brings `cores_sold` up to (or just under) `ideal_cores_sold`, rather than any averaged or aggregated signal. This single value is then fed unmodified into `AdaptPrice::adapt_price` at `rotate_sale`, setting `end_price`/`target_price` for the entire next sale period and every lease renewal (`PotentialRenewalRecord.price`) generated during that rotation.

## Finding Description
`purchase_core` overwrites `sale.sellout_price` on every purchase while `cores_sold <= ideal_cores_sold` (or if no price has been set yet), so the final stored value is simply the price of the last such transaction: [1](#0-0) 

`do_purchase` is a public, unprivileged extrinsic: any signed account can call it with a self-chosen `price_limit`, and the call succeeds as long as `price_limit >= sale_price` (the current leadin-decayed price, a deterministic function of elapsed time within the sale): [2](#0-1) 
Because the price at any moment is fully deterministic (`sale_price` = `leadin_factor_at(elapsed) * end_price`, no auction/randomness), an attacker can observe `cores_sold` and simply submit the purchase that lands as `cores_sold == ideal_cores_sold`, fixing `sellout_price` to a price of their choosing (bounded only by the deterministic curve at that moment, which they can time precisely).

At `rotate_sale`, this single `sellout_price` observation is passed to `AdaptPrice::adapt_price` to compute `end_price`/`target_price` for the entire next sale: [3](#0-2) 
`CenterTargetPrice::adapt_price` (the shipped implementation, wrapped by `MinimumPrice`) sets `target_price = sellout_price` directly and `end_price = sellout_price / 10`: [4](#0-3) 
`new_prices.target_price` is then stamped into every `PotentialRenewalRecord` for leases expiring into the new region, at the moment of rotation: [5](#0-4) 

**Existing mitigations are insufficient to fully close this:** `MinimumPrice::adapt_price` only clamps the *floor* of `end_price`/`target_price`, it does not change the fact that a single purchase is the sole observation: [6](#0-5)  Separately, `do_renew` applies a `renewal_bump`/`price_cap` on subsequent renewals of the *same* core, which limits how fast renewal prices can climb release-to-release for a given core, but that only affects the *next* renewal step for cores already renewing — it does nothing to prevent the initial `target_price` for a whole region (used for new renewals coming online, and as the reference for `sale_price`/leadin curve of the whole next sale) from being set by one purchase: [7](#0-6) 

The `prdoc/1.13.0/pr_4521.prdoc` history confirms this is a known price-manipulation vector class that was previously addressed (moving from a cores-sold-based controller to a price-based one) but the residual single-observation dependency was not eliminated, only dampened via the 10x/0.1x scaling and floor clamp.

## Impact Explanation
This is a real, reproducible economic manipulation of `pallet-broker`'s pricing mechanism, matching the impact-gate category "public underpriced work that degrades block production or stalls bridge processing" analog for the coretime market — more precisely it falls under "runtime bugs that compromise intended behavior" since price discovery (an intended invariant: prices should reflect aggregate demand) is corrupted by a single transaction. The blast radius, however, is bounded: `MinimumPrice` enforces a floor on `end_price`, `CenterTargetPrice`'s 10x/0.1x split limits the amplitude of a single swing to one order of magnitude per rotation (not unbounded), and `do_renew`'s `price_cap` bounds how fast subsequent renewals for the same core can be bumped further. The corrupted value is `SaleInfoRecord.sellout_price` → `AdaptedPrices.target_price`/`end_price` → `PotentialRenewalRecord.price`, affecting coretime pricing/allocation efficiency for one region, but it does not create unbacked mint, theft of funds, double-settlement, origin escalation, or chain-halting behavior. It is a legitimate economic/design flaw in price-discovery robustness rather than a fund-theft or consensus-safety bug.

## Likelihood Explanation
Fully feasible for any unprivileged account: the attacker only needs to observe on-chain `SaleInfo::cores_sold` and submit a normal `purchase` extrinsic with a self-chosen `price_limit`, timed to be the transition purchase around `ideal_cores_sold`. No relayer, validator, or governance capability is required, and the attack is repeatable every sale rotation. The claim's PoC steps are directly supported by the code (`purchase_core`'s `cores_sold <= ideal_cores_sold` branch condition).

## Recommendation
Compute the pricing signal fed into `AdaptPrice` from an aggregate (e.g., volume-weighted average price of purchases near the `ideal_cores_sold` threshold, or a windowed average over the last N purchases) instead of trusting the single transaction that happens to cross the threshold. Additionally, consider bounding how much `target_price`/`end_price` can move per rotation across multiple sale periods (a multi-period dampening factor) so that one manipulated sale cannot fully determine the next region's baseline price.

## Proof of Concept
1. Monitor `SaleInfo::cores_sold` as it approaches `ideal_cores_sold` for the active sale.
2. Call `Broker::purchase(price_limit)` with `price_limit` equal to the currently deterministic `sale_price` (`Pallet::sale_price`), timed so this purchase is the one where `cores_sold` transitions to `ideal_cores_sold` (or the next one, still covered by `cores_sold <= ideal_cores_sold`).
3. `purchase_core` records this purchase's `price` as `sale.sellout_price` (`substrate/frame/broker/src/utility_impls.rs:87-89`).
4. At the next `rotate_sale`, `AdaptPrice::adapt_price` derives `end_price`/`target_price` for the entire next sale solely from this `sellout_price` (`substrate/frame/broker/src/tick_impls.rs:178`, `substrate/frame/broker/src/adapt_price.rs:119-136`), and `target_price` is written into every `PotentialRenewalRecord` created during that rotation (`substrate/frame/broker/src/tick_impls.rs:230-241`), demonstrating that a single transaction fixed the pricing baseline for the subsequent region.

		who: &T::AccountId,
		price: BalanceOf<T>,
		sale: &mut SaleInfoRecordOf<T>,
	) -> Result<CoreIndex, DispatchError> {
		Self::charge(who, price)?;
		log::debug!("Purchased core at: {:?}", price);
		let core = sale.first_core.saturating_add(sale.cores_sold);
		sale.cores_sold.saturating_inc();
		if sale.cores_sold <= sale.ideal_cores_sold || sale.sellout_price.is_none() {
			sale.sellout_price = Some(price);
		}
		Ok(core)
	}

	pub(crate) fn do_purchase(
		who: T::AccountId,
		price_limit: BalanceOf<T>,
	) -> Result<RegionId, DispatchError> {
		let status = Status::<T>::get().ok_or(Error::<T>::Uninitialized)?;
		let mut sale = SaleInfo::<T>::get().ok_or(Error::<T>::NoSales)?;
		Self::ensure_cores_for_sale(&status, &sale)?;

		let now = RCBlockNumberProviderOf::<T::Coretime>::current_block_number();
		ensure!(now > sale.sale_start, Error::<T>::TooEarly);
		let price = Self::sale_price(&sale, now);
		ensure!(price_limit >= price, Error::<T>::Overpriced);

		let core = Self::purchase_core(&who, price, &mut sale)?;

		SaleInfo::<T>::put(&sale);
		let id = Self::issue(
			core,
			sale.region_begin,
			CoreMask::complete(),
			sale.region_end,
			Some(who.clone()),
			Some(price),
		);
		let duration = sale.region_end.saturating_sub(sale.region_begin);
		Self::deposit_event(Event::Purchased { who, region_id: id, price, duration });
		Ok(id)
	}

	fn adapt_price(performance: SalePerformance<Balance>) -> AdaptedPrices<Balance> {
		let Some(sellout_price) = performance.sellout_price else {
			return AdaptedPrices {
				end_price: performance.end_price,
				target_price: FixedU64::from(10).saturating_mul_int(performance.end_price),
			};
		};

		let price = FixedU64::from_rational(1, 10).saturating_mul_int(sellout_price);
		let price = if price == Balance::zero() {
			// We could not recover from a price equal 0 ever.
			sellout_price
		} else {
			price
		};

		AdaptedPrices { end_price: price, target_price: sellout_price }
	}

	fn adapt_price(performance: SalePerformance<Balance>) -> AdaptedPrices<Balance> {
		let mut proposal = CenterTargetPrice::<Balance>::adapt_price(performance);
		let min_price = MinPrice::get();
		if proposal.end_price < min_price {
			proposal.end_price = min_price;
		}
		// Fix target price if necessary:
		if proposal.target_price < proposal.end_price {
			proposal.target_price = proposal.end_price;
		}
		proposal
	}
