### Title
GetArchive cache key is derived from client-controlled `GlProjectPath` metadata, not repository identity, allowing cross-repository archive cache poisoning/disclosure - (File: internal/gitaly/service/repository/archive.go)

### Summary
The `GetArchive` RPC caches its output in a shared streaming cache (`s.archiveCache`) using a key computed from `repo.GetGlProjectPath()`, the `git archive` args, and pathspecs, but does not tie the key to the repository's actual storage name/relative path or any server-verified identity. `GlProjectPath` is client-supplied metadata that travels on the `gitalypb.Repository` message and is not validated against the physical repository being archived, only `StorageName`/`RelativePath` are checked by the locator.

### Finding Description

and `createArchiveCacheKey` hashes only the project path string plus the `git archive` args/pathspecs: [2](#0-1) 

Crucially, `GetArchive`'s request validation only checks the repository's `StorageName`/`RelativePath` via `s.locator.ValidateRepository`, and validates the `Path`/`Exclude` fields as relative paths inside that concrete repository: [3](#0-2) 

Nowhere is `GlProjectPath` cross-checked against the repository's real relative path/storage. Since `GlProjectPath` is only informational metadata (normally forwarded by Rails/gitlab-shell), an ordinary user issuing a raw `GetArchive` RPC (e.g., via a crafted client or through any path where this field is attacker-influenced) can set `Repository.GlProjectPath` to any string of their choosing while pointing `StorageName`/`RelativePath` at their own, legitimately-accessible repository.

This is the direct analog of the HackerOne report: the underlying storage object (here, a cached archive entry keyed by `sha256(gitLabProjectPath || args || pathspecs)`) is addressed by an attacker-influenced, predictable "filename" instead of a value bound to the true owning resource. Just like the S3 attachment path in the report was derived only from a client-supplied filename with no ownership check, the archive cache entry is addressed only by a client-supplied project-path string with no ownership/identity check.

### Impact Explanation
Because `s.archiveCache.Fetch` implements the classic "cache-aside" pattern (return cached content on hit, otherwise generate and store), an attacker who knows or guesses a victim project's `GlProjectPath`, target `CommitId`, `Path`, and `Exclude` values can:
- **Overwrite/poison**: craft a `GetArchive` request against their own repository but with `GlProjectPath` set to the victim's project path (and matching commit/path/exclude parameters that a legitimate victim request would also use), causing their own archive content to populate the cache slot that a subsequent legitimate request for the victim project would read from — this is a direct analog of "replacing other user's file" from the HackerOne report.
- **Read/disclosure**: if the victim's request already populated that cache slot, the attacker can retrieve the victim's archived repository content by supplying the same `GlProjectPath`/commit/path values, without ever having access to the victim repository via `StorageName`/`RelativePath`.

This is a cross-repository object/cache access issue (IDOR analog) with content-integrity impact (serving forged repository content to legitimate downstream consumers, e.g. GitLab Rails' archive download feature) as well as confidentiality impact (disclosure of another project's file listing/content through the cache).

### Likelihood Explanation
Exploitation requires the attacker to guess or otherwise learn the victim's `GlProjectPath`, `CommitId`, requested archive `Path`, and `Exclude` list — GitLab project paths are frequently public/predictable strings (namespace/project), and default archive requests typically use `Path=""`/`.`, no `Exclude`, and a specific ref/commit which may also be discoverable (e.g., default branch HEAD). This significantly lowers the bar versus a fully random secret. Any client capable of issuing `GetArchive` gRPC calls directly to Gitaly (bypassing normal Rails-mediated authorization checks that would tie the repository to the requesting project) can attempt this; it does not require any privileged or leaked credential beyond what any authenticated Gitaly client already has.

### Recommendation
Do not use client-supplied `GlProjectPath` as part of the cache key. Derive the cache key from server-verified repository identity (`StorageName` + `RelativePath`, or the resolved repository storage path) instead of, or in addition to being cryptographically bound to, the `GlProjectPath` metadata field. If a human-readable/project-scoped disambiguator is desired for observability, it must never be trusted as the sole discriminator that isolates one repository's cache namespace from another's.

### Proof of Concept
1. Attacker has access to repository A (their own) and knows target repository B's `GlProjectPath` (e.g., `"victim-group/victim-project"`), and a commit ID / path / exclude combination that a legitimate `GetArchive` request for B would use (e.g. default branch tip, `Path=""`, no excludes).
2. Attacker issues `GetArchive` on Gitaly directly with:
   - `Repository.StorageName` / `RelativePath` pointing at repository A (their own, legitimately accessible repo).
   - `Repository.GlProjectPath = "victim-group/victim-project"`.
   - `CommitId`, `Path`, `Exclude`, `Format` matching what a normal request for B would use.
3. `createArchiveCacheKey(repo.GetGlProjectPath(), args, pathspecs)` computes the same key that a legitimate request for repository B (with the same commit/path/exclude) would compute, since the key ignores `StorageName`/`RelativePath`.
4. The archive cache (`s.archiveCache.Fetch`) stores the attacker's generated archive (built from repository A) under that shared key.
5. When repository B's legitimate `GetArchive` request later runs with the same computed key, it receives a cache hit and streams back the attacker's (repository A's) archive content instead of repository B's actual content — demonstrating cross-repository cache poisoning.

Note: I was unable to directly verify at what layer (Rails vs. raw gRPC) `GlProjectPath` is populated/trusted for `GetArchive`, since that logic lives outside this repository (in GitLab Rails/gitlab-shell) and is not visible in the indexed Gitaly code. If GitLab Rails always sets `GlProjectPath` from a value it has already authorized for the given `StorageName`/`RelativePath` on every code path that calls `GetArchive`, then the practical exploitability depends on whether an attacker can reach this RPC through any path where `GlProjectPath` is attacker-influenced (e.g., a custom or malicious client bypassing Rails' access checks but still holding a valid Gitaly auth token for some repository). This should be confirmed by a background engineer with full repository/index access before treating this as fully proven end-to-end.

// createArchiveCacheKey creates a cache key using the GitLab project's path, the `git archive`
// command arguments and the pathspecs. The goal is to create a key that is unique not only
// across repository, but also across the content of each archive within the same repository.
func createArchiveCacheKey(gitLabProjectPath string, args []string, pathspecs []string) string {
	cacheKeyHash := sha256.New()
	cacheKeyHash.Write([]byte(gitLabProjectPath))
	cacheKeyHash.Write([]byte(strings.Join(args, ",")))
	cacheKeyHash.Write([]byte(strings.Join(pathspecs, ",")))
	return hex.EncodeToString(cacheKeyHash.Sum(nil))
}
