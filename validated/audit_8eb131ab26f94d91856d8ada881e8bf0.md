### Title
Unauthenticated QUIC handshake churn can pin `open_connections` at the global cap via `ClientConnectionTracker`, starving legitimate staked/unstaked clients - ([File: streamer/src/nonblocking/quic.rs])

### Summary
`ClientConnectionTracker::new` enforces a single global cap (`max_concurrent_connections()` = `(max_staked_connections + max_unstaked_connections) * 5/4`) on in-flight connections *before* peer type/stake is known, and the per-IP/global rate limiters only debit tokens *after* a handshake successfully completes. An attacker can therefore open many parallel QUIC connections, never complete the handshake, and hold slots for up to `QUIC_CONNECTION_HANDSHAKE_TIMEOUT` each — repeating this in a loop keeps `open_connections` pinned near the cap and causes `refused_connections_too_many_open_connections` for all other clients, staked or unstaked.

### Finding Description
In `run_server`, for every accepted `Incoming`, the server checks the per-IP rate limiter and the global rate limiter using non-consuming reads:
- `overall_connection_rate_limiter.current_tokens() == 0` [1](#0-0) 
- `rate_limiter.is_allowed(&incoming.remote_address().ip())` [2](#0-1) 

Both of these only *check* levels; they do not consume/register a token. Actual token consumption (`rate_limiter.register_connection` and `overall_connection_rate_limiter.consume_tokens(1)`) happens only in `setup_connection` **after** the QUIC handshake completes successfully [3](#0-2) .

Immediately after the (non-consuming) rate-limit checks, the server creates a `ClientConnectionTracker`, which increments `stats.open_connections` and enforces the *only* hard cap that applies before a handshake completes: [4](#0-3) 

This cap is `qos.max_concurrent_connections()`, which for `SwQos` is a single number shared across staked and unstaked peers, computed with only a 25% margin over the sum of configured connection limits: [5](#0-4) 

The tracker (and thus the `open_connections` slot) is held for the entire in-flight handshake window, bounded by `QUIC_CONNECTION_HANDSHAKE_TIMEOUT`, regardless of whether the client ever finishes the handshake: [6](#0-5) 

If the handshake never completes (attacker sends an Initial packet and then goes silent, or slow-drips just enough to avoid quinn's internal idle timeout until `QUIC_CONNECTION_HANDSHAKE_TIMEOUT` fires), the connection attempt is counted in `outstanding_incoming_connection_attempts`/`open_connections` for up to that timeout, then the tracker is dropped, decrementing the counter: [7](#0-6) [8](#0-7) 

Critically, since the per-IP and global rate limiters are *not* charged for abandoned/incomplete handshakes (only for connections that complete the handshake), an attacker's incomplete-handshake attempts are never throttled by `ConnectionRateLimiter` or the overall `TokenBucket`. The only throttle on abandoned handshakes is the shared `ClientConnectionTracker` cap itself. By opening new connection attempts at a rate that matches slot expiry (bounded by `QUIC_CONNECTION_HANDSHAKE_TIMEOUT`), an attacker can keep `stats.open_connections` pinned near `max_concurrent_connections()` indefinitely. Once at cap, every other incoming connection — including from staked validators who have not yet been peer-type-classified (classification happens only after a successful handshake, in `build_connection_context`) — is refused via `incoming.refuse()` and counted as `refused_connections_too_many_open_connections`: [9](#0-8) 

This violates the intended invariant that per-IP/global connection churn should be rate-limited before consuming the shared concurrent-connection budget, and that the cap should not be trivially exhaustible by unauthenticated, stake-less clients performing incomplete handshakes.

### Impact Explanation
This is a cluster-wide TPU-ingress denial-of-service: while the attack is sustained, legitimate staked validators' vote/transaction traffic and legitimate unstaked client traffic to the leader's TPU port are refused at the QUIC accept layer before any sigverify/scheduling logic even runs, which can halt or degrade block production for the leader under attack. This matches the "ingress/QUIC connection-layer QoS evasion causing block-production halt" category referenced in the audit scope.

### Likelihood Explanation
Feasible for an unprivileged remote attacker with no stake and no validator identity: it only requires the ability to open many parallel QUIC connections to the public TPU port and let them idle without completing the handshake, looping at roughly the handshake-timeout cadence. No spoofing is required (spoofed source IPs cannot complete a real handshake but don't need to — the exploit relies on the pre-handshake tracker cap, not on completing anything). The main practical constraint is that any single source IP is limited by OS/socket resources and NIC bandwidth, but the per-IP rate limiter provides no defense here since it's not charged for incomplete handshakes, so a modest number of source IPs/sockets suffices to sustain the churn.

### Recommendation
- Charge (or partially charge) the per-IP and global `TokenBucket` rate limiters at connection-attempt time (before/at accept), not only after a successful handshake, so abandoned handshakes are throttled the same as completed ones.
- Reserve a portion of `max_concurrent_connections()` capacity specifically for staked/known peers, or perform lightweight address validation (e.g., QUIC Retry) before allocating a `ClientConnectionTracker` slot, so unauthenticated clients cannot exhaust the shared budget with abandoned handshakes.
- Consider shrinking `QUIC_CONNECTION_HANDSHAKE_TIMEOUT` or applying a stricter per-IP concurrent-in-flight-handshake cap (distinct from the completed-connection cap) to bound how many slots a single IP/source can occupy simultaneously.

### Proof of Concept
Integration test plan (using the existing `setup_quic_server` test harness in `streamer/src/nonblocking/quic.rs` tests):
1. Configure `SwQosConfig` with small `max_staked_connections`/`max_unstaked_connections` (e.g., 4 total) so `max_concurrent_connections()` = `(4)*5/4` = 5.
2. Spawn N "attacker" QUIC client endpoints (N ≈ cap) that connect to the server and, instead of completing the handshake, hold the connection attempt open (e.g., connect via a raw UDP socket sending only an Initial packet, or use quinn's `connect` future without awaiting completion) — repeat opening a new attempt every time an old one is about to expire (~`QUIC_CONNECTION_HANDSHAKE_TIMEOUT`).
3. Concurrently, spawn a "legitimate" client using `make_client_endpoint` that performs a full handshake and sends a packet.
4. Assert that `stats.refused_connections_too_many_open_connections.load(Ordering::Relaxed) > 0` while the legitimate client's connection attempt fails or is delayed beyond an acceptable bound, and that `stats.open_connections` stays pinned near `max_concurrent_connections()` throughout the attack window — demonstrating the legitimate client's success rate is driven toward zero by attacker churn despite never exceeding the per-IP/global rate limiters.

impl ClientConnectionTracker {
    /// Check the max_concurrent_connections limit and if it is within the limit
    /// create ClientConnectionTracker and increment open connection count. Otherwise returns Err
    fn new(stats: Arc<StreamerStats>, max_concurrent_connections: usize) -> Result<Self, ()> {
        let open_connections = stats.open_connections.fetch_add(1, Ordering::Relaxed);
        if open_connections >= max_concurrent_connections {
            stats.open_connections.fetch_sub(1, Ordering::Relaxed);
            debug!(
                "There are too many concurrent connections opened already: open: \
                 {open_connections}, max: {max_concurrent_connections}"
            );
            return Err(());
        }

        Ok(Self { stats })
    }
}
