### Title
Division-before-multiplication precision loss in `MortgageService.computeReward()` reward payout for standby-witness voters - (File: `chainbase/src/main/java/org/tron/core/service/MortgageService.java`)

### Summary
`MortgageService.computeReward(long cycle, List<Pair<byte[], Long>> votes)` — the "old" (pre-new-reward-algorithm) per-cycle reward computation used when withdrawing a voter's SR voting reward — computes `voteRate = (double) userVote / totalVote` and then multiplies it by `totalReward`, i.e. it divides before multiplying, exactly the pattern flagged in the referenced Nounsdao Sherlock finding (M-1) for `Stream.sol::_recipientBalance()`. [1](#0-0) 

### Finding Description
`computeReward` is reached from `queryReward()` and `withdrawReward()`, both of which are invoked when any account withdraws its SR-vote reward (via `WithdrawBalanceContract`/reward-withdraw actuator flow, reachable by any unprivileged account that has voted for a witness). [2](#0-1) [3](#0-2) 

Inside `computeReward`, the vote-rate is first computed via floating-point division (`userVote / totalVote`), then multiplied by `totalReward`:
```java
double voteRate = (double) userVote / totalVote;
reward += voteRate * totalReward;
```
This is mathematically equivalent to `userVote * totalReward / totalVote`, but performing the division first (using a `double`, which has only ~15-17 significant decimal digits) discards precision before the multiplication is applied, exactly like the unnecessary precision loss identified in the Sherlock/Nounsdao report for `Stream.sol::_recipientBalance()` (`elapsedTime_ * (RATE_DECIMALS_MULTIPLIER * tokenAmount_ / duration) / RATE_DECIMALS_MULTIPLIER` vs the corrected `elapsedTime_ * tokenAmount_ / duration`).

By contrast, the codebase's own "new reward algorithm" path (`computeReward(long beginCycle, long endCycle, ...)` and `RewardViCalService`) explicitly avoids this pattern by using `BigInteger` and performing `multiply(...).divide(...)` in the correct order (multiply first, then divide), showing that java-tron engineers were already aware that reward math needs multiply-before-divide to avoid precision loss. [4](#0-3) [5](#0-4) 

The old-algorithm path in `computeReward(cycle, votes)`, however, was left with the div-then-mul double-based formula, and is still executed for any cycle prior to `newRewardAlgorithmEffectiveCycle` (i.e., for networks/periods where the new algorithm has not yet activated, and for historical cycle reward computation done via `getOldReward` in `chainbase/src/main/java/org/tron/core/service/MortgageService.java:199-214`).

### Impact Explanation
Precision loss in `voteRate` causes rounding error in the computed reward amount credited to a voter's allowance for that cycle. Depending on rounding direction, this can systematically under- or over-pay individual voters relative to their true proportional share of `totalReward`, and because rewards are summed per-cycle across many voters, the aggregate error can leave a persistent mismatch between rewards allocated and the pooled `totalReward`, i.e., unbacked or lost balance in the reward allowance accounting. This is a fund-accounting correctness issue (medium severity) rather than a crash or authentication bypass.

### Likelihood Explanation
This code path executes on every normal, unprivileged `withdrawReward`/`queryReward` invocation for any cycle prior to the new-reward-algorithm activation cycle, so it is reachable by any account that has voted for a standby witness — no special privilege is required. The precision loss occurs deterministically whenever `userVote`/`totalVote` do not divide evenly, which is the common case, though the per-call magnitude is typically small (bounded by the double's relative error, roughly 1 part in 10^15 of the reward involved).

### Recommendation
Refactor `computeReward(long cycle, List<Pair<byte[], Long>> votes)` to compute the reward using integer/`BigInteger` multiplication before division (mirroring the pattern already used in the new-algorithm path):
```java
long userVote = vote.getValue();
reward += BigInteger.valueOf(totalReward)
    .multiply(BigInteger.valueOf(userVote))
    .divide(BigInteger.valueOf(totalVote))
    .longValueExact();
```
This eliminates the intermediate `double` division and matches the multiply-before-divide fix recommended in the referenced report.

### Proof of Concept
1. Configure two voters for the same SR in the same reward cycle: voter A with `userVote = 1`, voter B with `userVote = 2`, `totalVote = 3` (i.e., `totalVote` not evenly divisible by either share).
2. Set `totalReward` for that SR/cycle to a value not a multiple of 3 (e.g., `totalReward = 10`).
3. Call `withdrawReward`/`queryReward` for both voters and observe that `voteRate * totalReward` for each, computed via double division `1/3` and `2/3` respectively, yields cumulative rounding error versus the exact integer computation `userVote * totalReward / totalVote` (which would yield `3` and `6` respectively, summing to `9` out of `10`, versus the double path which can differ due to floating-point rounding at scale, especially with large `totalReward`/`totalVote` values near `Long.MAX_VALUE` where double's 52-bit mantissa cannot exactly represent the fraction).   private long computeReward(long cycle, List<Pair<byte[], Long>> votes) {
    long reward = 0;
    for (Pair<byte[], Long> vote : votes) {
      byte[] srAddress = vote.getKey();
      long totalReward = delegationStore.getReward(cycle, srAddress);
      if (totalReward <= 0) {
        continue;
      }
      long totalVote = delegationStore.getWitnessVote(cycle, srAddress);
      if (totalVote == DelegationStore.REMARK || totalVote == 0) {
        continue;
      }
      long userVote = vote.getValue();
      double voteRate = (double) userVote / totalVote;
      reward += voteRate * totalReward;
    }
    return reward;
  }
