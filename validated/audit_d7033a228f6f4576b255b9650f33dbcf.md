## Audit Report

## Title
Relayer/user fees held in `PendingOrders` become permanently unrecoverable if the Ethereum verifier remains `Halted`, with no expiry, refund, or governance override - (File: `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs`)

## Summary
`Pallet::do_process_message` collects a user-supplied `fee` and stores it in `PendingOrders<T>` keyed by `nonce` [1](#0-0) . The only exit from `PendingOrders` is `submit_delivery_receipt`, which unconditionally requires `T::Verifier::verify()` to succeed before any state mutation occurs [2](#0-1) . If the verifier deterministically returns `VerificationError::Halted` (e.g., an Ethereum beacon light client falling irrecoverably behind), the fee tied to that nonce can never be paid to a relayer nor refunded to the sender, and no alternate code path exists to reclaim it.

## Finding Description
The pallet's `Error` enum contains a `Halted` variant and the `Event` enum contains `OperatingModeChanged`, but there is no `OperatingMode` storage item, no `set_operating_mode` extrinsic, and no admin/root/expiry extrinsic anywhere in this pallet [3](#0-2) . This was confirmed by inspecting the file: the only occurrences of `OperatingMode`-related tokens in `outbound-queue-v2/src/lib.rs` are the unused `Error::Halted` variant, the `Event::OperatingModeChanged` declaration, and the `BasicOperatingMode` import — none of them wired to a callable extrinsic or storage item, unlike `inbound-queue-v2`, `outbound-queue` v1, and `system-v2`, which all implement `set_operating_mode`.

`process_delivery_receipt` is the sole mutator that removes a `PendingOrders` entry and pays the fee, and it is only reachable through `submit_delivery_receipt`'s mandatory `T::Verifier::verify()` gate [4](#0-3) . There is no `PendingOrders` expiry, no timeout-based auto-refund to the sender, and no privileged force-settle path independent of `T::Verifier`. The existing unit test `poc_m1` in the repository directly demonstrates that once the verifier is forced into a `Halted` state, `submit_delivery_receipt` fails deterministically and the `PendingOrder` fee remains untouched in storage [5](#0-4) .

## Impact Explanation
Fees paid up front by message senders to incentivize Ethereum-side delivery are escrowed in `PendingOrders`. If the underlying Ethereum light client verifier becomes permanently unable to produce valid proofs (a liveness condition entirely external to this pallet and requiring no malicious actor), every outstanding nonce's fee is trapped indefinitely: it is never paid to the relayer that performed delivery, and it is never refunded to the original sender. This matches the "permanent user-fund or bridge-state lock" impact class, since the pallet itself provides no mechanism — governance or otherwise — to settle or release value already committed to `PendingOrders` once the verifier gate can no longer be satisfied.

## Likelihood Explanation
No attacker action or malicious relayer/prover behavior is needed to trigger the root condition: this is a design gap that manifests purely from the liveness properties of `T::Verifier` (the Ethereum beacon/light client), which is an operational risk inherent to any light-client-based bridge (e.g., missed sync-committee updates or a resync gap exceeding what the light client can bridge). Once triggered, the lock is deterministic and total for every affected nonce — repeated calls to `submit_delivery_receipt` will always fail with `Error::Verification(VerificationError::Halted)` as shown by `poc_m1`, and there is no alternate recovery path coded into the pallet.

## Recommendation
Add a governance-callable emergency settlement/refund path for `PendingOrders` entries that is independent of `T::Verifier::verify()` succeeding (e.g., a privileged `force_process_pending_order` or a time-bound expiry that reverts the collected fee to the original sender if no delivery receipt is submitted within an SLA window measured from `PendingOrder::block_number`). This decouples fund recovery from the liveness of the external light client.

## Proof of Concept
The repository's own test `poc_m1` reproduces the exact scenario: it inserts a `PendingOrder` with a non-zero fee, forces the mock verifier into a `Halted` state, and shows that `submit_delivery_receipt` fails with `Error::Verification(VerificationError::Halted)` while the `PendingOrders` entry (and its fee) remains present in storage with no code path to release or refund it [5](#0-4) .

		/// Process a delivery receipt from a relayer, to allocate the relayer reward.
		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}

// Reward processing must be blocked while the bridge is halted: `submit_delivery_receipt`
// should not pay out `PendingOrder` fees if the verifier reports the bridge as halted.
#[test]
fn poc_m1() {
	new_tester().execute_with(|| {
		let nonce = 1;
		let fee: u128 = 1_000_000;
		let order = PendingOrder { nonce, fee, block_number: System::block_number() };
		PendingOrders::<Test>::insert(nonce, order);

		let relayer: AccountId32 = [7u8; 32].into();
		let origin = RuntimeOrigin::signed(relayer);
		let event = Box::new(mock_event_proof());

		set_verifier_halted(true);

		assert_noop!(
			OutboundQueue::submit_delivery_receipt(origin.clone(), event.clone()),
			Error::<Test>::Verification(VerificationError::Halted)
		);

		let order_after = PendingOrders::<Test>::get(nonce).expect("order still present");
		assert_eq!(order_after.fee, fee);

		set_verifier_halted(false);
	});
}
