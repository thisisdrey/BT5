### Title
Permanent StackerDB slot bricking via `slot_version = u32::MAX`, network-wide, once a signer writes the maximum Lamport-clock value — ([File: stackslib/src/net/stackerdb/db.rs])

### Summary
The signer coordination StackerDB (`.signers-*` contracts) configures `max-writes` to `u32::MAX` (`4294967295`) with no additional bound on slot-version growth. Because `try_replace_chunk` requires a strictly increasing `slot_version` (a `u32` Lamport clock) and rejects any value `> max_writes`, a slot owner who once signs and submits a chunk with `slot_version == u32::MAX` makes every future write to that slot impossible for the remainder of the network's life, on every replica that stores or syncs it.

### Finding Description
`try_replace_chunk` enforces that a new chunk's version is strictly greater than the currently stored version and no larger than `config.max_writes`: [2](#0-1) 

`slot_version` is a `u32`, and the `.signers` boot contract sets `MAX_WRITES` to `u32::MAX`, so the max-writes gate never rejects the highest possible version: [1](#0-0) 

If a legitimate slot owner (any signer, using their own valid key for their own assigned slot — no admin role required) submits one validly-signed chunk with `slot_version = u32::MAX`, `try_replace_chunk` accepts it (it is `> latest_version` and not `> max_writes`) and stores it. From that point forward, `slot_desc.slot_version <= slot_validation.version` is always true for any subsequent chunk (since `u32::MAX` is the maximum representable `u32`), so every future write to that slot is permanently rejected as `StaleChunk`: [3](#0-2) 

This exactly mirrors the report's bug class: a caller-controlled sequence number set to the type's maximum value permanently defeats the "must be greater than the last value" comparison used to gate future writes.

The same validation logic is duplicated in the p2p push/sync path (`validate_received_chunk`), so the poisoned max-version chunk is treated as valid data to relay and store on every peer that replicates the DB: [4](#0-3) 

Once stored, the chunk is broadcast to the peer's neighbors via `process_stacker_db_chunks`, so the bricked-version state propagates network-wide to every replica of that StackerDB, not just the attacker's own node: [5](#0-4) 

### Impact Explanation
This permanently disables further writes to a specific signer's StackerDB slot across the entire network — the slot can never again be updated by anyone, including the legitimate signer, because the Lamport-clock comparison against `u32::MAX` can never be satisfied. Since the `.signers` StackerDB slots carry signer coordination/voting messages used in the Nakamoto consensus signing protocol, permanently blinding one signer's slot degrades the signer set's ability to communicate for that reward cycle, and the corrupted (unwritable-forever) state propagates to every replica in the network via normal gossip/sync, matching the "network-wide propagation" and "unauthorized/permanent denial of write to state" impact tier.

### Likelihood Explanation
Any party who is a valid signer (i.e., holds a private key mapped to a StackerDB slot for the current/next reward cycle — a role many independent operators hold, not a privileged admin) can trigger this with a single, cheaply-constructed, validly-signed HTTP `POST` (via `RPCPostStackerDBChunkRequestHandler`) or p2p `StackerDBChunk`/`StackerDBPushChunk` message. No race condition, timing, or repeated flooding is needed — one message with `slot_version = u32::MAX` suffices, and the production `.signers` contract's `MAX_WRITES` constant makes the check pass.

### Recommendation
Bound the maximum acceptable `slot_version` to something strictly less than `u32::MAX` in `try_replace_chunk`/`validate_received_chunk` (e.g., reserve the top of the range, or require `slot_version < u32::MAX`), independent of the contract-configured `max_writes`, so a `max-writes` value equal to the type's maximum cannot brick the slot. Alternatively, change the boot contract's `MAX_WRITES` to a value with headroom below `u32::MAX`, and/or reject contract configs that set `max-writes` to the type's maximum.

### Proof of Concept
1. Obtain the private key for any slot owner registered in the `.signers-N-M` StackerDB contract (a normal, non-admin signer role).
2. Construct a `StackerDBChunkData` for that slot with `slot_version = u32::MAX` (`4294967295`), sign it with the owner's key, and submit via `POST /v2/stackerdb/.../chunks` (handled by `RPCPostStackerDBChunkRequestHandler` in `stackslib/src/net/api/poststackerdbchunk.rs`) or as an unsolicited `StackerDBPushChunk` p2p message.
3. `try_replace_chunk` accepts it because `4294967295 > latest_version` and `4294967295 <= max_writes (== u32::MAX)`: [2](#0-1) 
4. The node relays/broadcasts the accepted chunk to peers (`process_stacker_db_chunks`), so every replica adopts `slot_version = u32::MAX` for that slot: [5](#0-4) 
5. Any subsequent attempt (by anyone, including the legitimate owner) to write a new chunk to that slot fails with `StaleChunk`/`DataAlreadyExists` forever, since no `u32` value can exceed `u32::MAX`.
