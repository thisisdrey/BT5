### Title
Unguarded out-of-bounds array access in `ValidateMultiSign` precompile before TIP-854/Osaka activation - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `ValidateMultiSign` precompiled contract (invoked via `CALL`/`STATICCALL` to its reserved TVM address from any smart contract) parses attacker-controlled `rawData` word-by-word without bounds checks unless the Osaka/TIP-854 hard fork is active. This mirrors the OpenSC CVE-2018-16427 pattern: untrusted, attacker-crafted input is used to compute array indices/offsets that are then dereferenced without validating them against the buffer length, producing an out-of-bounds read.

### Finding Description
`ValidateMultiSign.execute` at [1](#0-0)  only calls `isValidAbiEncoding(rawData, ABI_HEADER_WORDS, ABI_ITEM_WORDS)` when `VMConfig.allowTvmOsaka()` is true. When that condition is false (pre-activation, or on networks/paths where the flag is not yet enabled), the method proceeds directly to `DataWord.parseArray(rawData)` and then computes offsets such as `words[3].intValueSafe() / WORD_SIZE` and uses them to index into `words[]` at [2](#0-1) , and `extractBytesArray`/`extractSigArray` further index into the `data` byte array using attacker-controlled offsets/lengths with only partial safety (`extractBytesArray` checks `offset > words.length - 1` but not the derived `bytesOffset`/`bytesLen` combinations against `data.length`) as seen at [3](#0-2) . Unlike its sibling `BatchValidateSign`, whose public `execute` wraps everything in `try { doExecute(data); } catch (Throwable t) { ... }` at [4](#0-3) , `ValidateMultiSign.execute` has no such catch-all — the only try/catch present covers just the permission-weight loop at [5](#0-4) , not the earlier parsing/decoding steps. This is confirmed intentional-but-risky legacy behavior by the project's own test comment in `ValidateMultiSignContractTest.testTip854PreActivationNoOp` at [6](#0-5) .

### Impact Explanation
A malformed/short `rawData` payload causes an unhandled `ArrayIndexOutOfBoundsException` (or similar `RuntimeException`) to propagate out of the precompile's `execute` method during TVM execution of a `CALL` to the `ValidateMultiSign` precompiled address. Any account can trigger this by deploying or calling a contract that performs this precompile call with attacker-chosen calldata — no special privileges are needed. Depending on how the TVM interpreter's call-dispatch layer handles this exception, this at minimum aborts/reverts the triggering transaction; if the exception is not caught at a level appropriate for isolating a single internal call (i.e., escapes the per-transaction execution sandbox), it can propagate into `Runtime`/`Manager` block-application code and crash the node process or halt block processing for any node that has to re-execute the transaction (e.g., during sync or when it appears in a broadcast block), which is a Medium-severity node-crash/DoS impact analogous to the OpenSC CVE.

### Likelihood Explanation
The precompile is directly reachable by any unprivileged account through a single crafted contract call (`STATICCALL`/`CALL` to the precompile address with truncated/malformed input), requiring no special TVM permissions and only minimal energy (bounded by the `getEnergyForData` cost formula). The vulnerable code path is only present pre-Osaka/TIP-854 activation, so the current live-network likelihood depends on whether `VMConfig.allowTvmOsaka()` is already active on the target chain; if not yet activated, likelihood is high since it's a single, cheaply reproducible transaction.

### Recommendation
Make the `isValidAbiEncoding` bounds validation (or equivalent length/offset checks) unconditional in `ValidateMultiSign.execute`, rather than gating it behind `VMConfig.allowTvmOsaka()`, and wrap the full body of `execute` (parsing included) in a catch-all similar to `BatchValidateSign.execute` so any decoding exception fails safely (returns `DATA_FALSE`) instead of propagating.

### Proof of Concept
Call the `ValidateMultiSign` precompiled contract address from a deployed contract (or via `TriggerConstantContract`/`TriggerSmartContract` API) with `rawData` shorter than 5 words (e.g., `rawData = new byte[3 * 32]`) while the network has not activated TIP-854/Osaka (`VMConfig.allowTvmOsaka() == false`). `DataWord.parseArray`/subsequent `words[3]` access or `extractBytesArray` offset math will throw `ArrayIndexOutOfBoundsException`, matching the exact scenario the project's own test `testTip854PreActivationNoOp` documents at [7](#0-6) .
