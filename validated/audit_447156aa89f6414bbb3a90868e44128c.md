## Analysis

The report's bug class — an ordinary, expected failure of *one item* in a batch causes the *entire* transaction to revert, blocking otherwise-valid processing of the rest — maps most directly onto Zest's bad-debt socialization path inside `liquidate()`, not onto `liquidate-multi` (which already isolates per-position failures via `(map call-liquidate positions)` and is not vulnerable to this class).

### Title
Bad-debt socialization for one debt asset reverts the entire liquidation, permanently blocking liquidation of positions with multiple debt assets - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
When a liquidation empties a borrower's last collateral, `liquidate()` tries to socialize (write off) *all* of the borrower's remaining debts across every debt asset the borrower holds, using `fold socialize-debt-asset ...` followed by `(asserts! (get success socialization-result) ERR-BAD-DEBT-SOCIALIZATION-FAILED)`. This mirrors the reported analog: a single failing sub-action in a list (there: a Solver settling gas; here: socializing one specific debt asset) is allowed to abort the whole outer call instead of being isolated, so an ordinary liquidator cannot make progress at all.

### Finding Description
In `liquidate()`, once collateral for the position is exhausted (`no-collateral-left`), the market builds `fresh-debt-list` (the borrower's remaining scaled debts across possibly several assets) and folds `socialize-debt-asset` over it: [1](#0-0) 

`socialize-debt-asset` performs, per debt entry, three chained cross-contract calls — `vault-socialize-debt`, a `vault-accrue` cache refresh, and `debt-remove-scaled` on `v0-market-vault` — each guarded with `unwrap!` that turns *any* failure into `{ success: false }`, short-circuiting the fold via the "early return if previous socialization failed" check: [2](#0-1) 

Back in `liquidate()`, if that fold ever returns `success: false` for *any one* of the borrower's debt assets, the `asserts!` fires and the entire `liquidate()` call reverts: [3](#0-2) 

Because Clarity transactions are atomic, this revert unwinds everything already performed earlier in the same call — the debt repayment (`vault-system-repay`) and the collateral seizure (`collateral-remove`) that had already succeeded: [4](#0-3) 

This is structurally identical to the reported Atlas issue: `_settle()` failing for one Solver blocks/reverts the whole `metacall()`, when the expected behavior is to isolate the failure and continue processing the rest. Here, the failure to socialize debt for one asset in the borrower's debt list blocks/reverts the whole liquidation, instead of, e.g., socializing the assets that can succeed and only failing (or logging) the one that cannot.

Each per-asset vault call has real failure conditions that are not attacker-exotic:
- `vault-socialize-debt`/`socialize-debt` on the underlying vault asserts `scaled-amount > 0` (`ERR-AMOUNT-ZERO`), so any stale/zero-scaled residual entry for an asset causes failure.
- `debt-remove-scaled` on `v0-market-vault` can fail if the scaled amount passed doesn't match bookkeeping expectations (e.g., due to interim accrual/index changes between reading `curr-scaled` for the target debt asset and re-fetching indexes for the other debt assets in the list — the cache refresh step (`map-set index-cache ... (unwrap! (vault-accrue asset-id) ...)`) mutates per-block index state as a side effect of the fold itself, which other debt-asset entries in the same fold then read from).

### Impact Explanation
A borrower whose position has multiple debt assets and zero remaining collateral cannot be liquidated at all if socialization of any single one of those debt assets reliably fails (e.g., a legitimately zero/degenerate scaled amount for one asset, or an inconsistency introduced by the in-fold index-cache mutation). Because the liquidator cannot repay debt or seize collateral in that same atomic call (it all reverts), the position becomes stuck: unrecoverable bad debt sits on the books indefinitely, the vaults never get the corresponding write-down, and liquidators/protocol are permanently unable to close out the position. This is a temporary/permanent freezing of protocol funds and directly threatens solvency accounting for the affected vaults (the debt is never written off, so vault accounting continues to reflect assets that don't exist) — matching the in-scope "protocol insolvency" / "permanent freezing of funds" impact classes.

### Likelihood Explanation
Likelihood is moderate: multi-debt-asset borrowers are a normal, expected usage pattern (Zest explicitly supports cross-asset egroups), and the socialization path is only exercised in the already-rare "no collateral left, bad debt" branch — meaning any latent failure mode in one of the chained vault calls (as opposed to being purely theoretical) is difficult to test/observe until it actually occurs on a real under-collateralized multi-asset position, at which point it permanently blocks liquidation with no recovery path (no retry succeeds, since the same fold executes the same calls again).

### Recommendation
Do not let a single failing debt-asset socialization abort the whole liquidation. Mirror the fix pattern the report references for Atlas (`reconcile()`/blocking-after-call) by isolating each debt-asset socialization attempt: continue folding over the remaining debt entries even if one fails, and only revert (or better, retain the un-socialized entry in the position's debt list for a later retry) for the specific asset that failed, rather than asserting global `success` and unwinding the entire `liquidate()` call including the already-successful debt repayment and collateral seizure. This is analogous to how `liquidate-multi` already correctly isolates failures per position via `map` instead of `fold`+`assert!`.

### Proof of Concept
Conceptual PoC (cannot be executed without deployment/test access, so this is a reasoning-level PoC based on code paths above):
1. Set up a borrower with debt in two assets, e.g. debt-asset A (the one being liquidated) and debt-asset B (a leftover residual position).
2. Ensure debt-asset B's stored scaled-debt entry is degenerate (e.g., driven to `u0` scaled units through prior partial repayments/interest-index rounding, while `market-vault`'s debt list for the borrower still contains an entry `{ aid: B, scaled: u0 }` that hasn't been pruned).
3. Trigger a liquidation of debt-asset A that fully drains the borrower's only collateral (`no-collateral-left` becomes true), forcing `fresh-debt-list` to include both A's leftover debt (if any) and B's `{ aid: B, scaled: u0 }` entry.
4. The `fold socialize-debt-asset` reaches B's entry, calls `vault-socialize-debt` for vault B with `scaled-amount = u0`, which hits `(asserts! (> scaled-amount u0) ERR-AMOUNT-ZERO)` in the vault's `socialize-debt` and fails: [5](#0-4) 
5. `socialize-debt-asset` returns `{ success: false }`, `liquidate()`'s `asserts! (get success socialization-result) ERR-BAD-DEBT-SOCIALIZATION-FAILED` fires, and the entire liquidation (including the already-performed debt repay and collateral removal for asset A) reverts.
6. Every subsequent attempt to liquidate this borrower's position hits the exact same code path and reverts identically — the position is permanently stuck with bad debt that can never be socialized/liquidated through the normal `liquidate()` entry point.

Note: I was unable to fully confirm within the tool-call budget whether a zero-scaled residual debt entry can actually persist in `market-vault`'s per-borrower debt list under normal operation (this would require reading `v0-market-vault.clar`'s debt-list maintenance functions, which I could not retrieve before the iteration limit). The root-cause mechanism (fold+assert reverting the whole `liquidate()` call on any single per-asset socialization failure) is confirmed directly from the code cited above; the exact triggering precondition for a per-asset failure needs further verification against `v0-market-vault.clar`.

```text
(define-private (socialize-debt-asset
                (debt-entry { aid: uint, scaled: uint })
                (acc { borrower: principal, success: bool }))
  ;; Early return if previous socialization failed
  (if (not (get success acc))
      acc
      (let ((borrower (get borrower acc))
            (failed-status { borrower: borrower, success: false })
            (asset-id (get aid debt-entry))
            (scaled-debt (get scaled debt-entry)))

            ;; Socialize in vault - pass scaled directly to avoid rounding
            (unwrap! (vault-socialize-debt asset-id scaled-debt) failed-status)
            ;; Refresh cache with new indexes post-write-down (lindex decreased)
            (map-set index-cache
                     { timestamp: stacks-block-time, aid: asset-id }
                     (unwrap! (vault-accrue asset-id) failed-status))
            ;; Remove from obligation
            (unwrap! (contract-call? .v0-market-vault
                                      debt-remove-scaled
                                      borrower
                                      scaled-debt
                                      asset-id) failed-status)
          acc)
        ))
```
