### Title
Per-IP QUIC connection rate limiting keyed by raw `IpAddr` can be bypassed via IPv6 address churn to unfairly capture unstaked TPU connection capacity - ([File: streamer/src/nonblocking/connection_rate_limiter.rs])

### Summary
`ConnectionRateLimiter::register_connection` and `is_allowed` key the per-source token bucket strictly by the literal `IpAddr` of the QUIC peer, with no normalization or aggregation by network prefix (e.g. IPv6 /64). An unprivileged, unstaked attacker who owns a routable IPv6 /64 block (trivially obtainable from many cloud/VPS providers) can present a distinct source address for every connection attempt, so each connection is seen as a "fresh" key that has never consumed tokens, defeating the intended per-source cap of `DEFAULT_MAX_CONNECTIONS_PER_IPADDR_PER_MINUTE`.

### Finding Description
`ConnectionRateLimiter` wraps a `KeyedRateLimiter<IpAddr>` [1](#0-0) . `register_connection` calls `self.limiter.consume_tokens(*ip, 1)`, and `is_allowed` calls `self.limiter.current_tokens(ip)`; both treat any `IpAddr` never seen before as having a full bucket (`None => true`) [2](#0-1) . The keying is a raw `IpAddr` equality/hash lookup in the underlying `DashMap<K, TokenBucket>` inside `KeyedRateLimiter` [3](#0-2) , with no logic anywhere in the codebase (confirmed via search) that normalizes or buckets IPv6 addresses by a /64 or any other prefix before use as the key.

In `streamer/src/nonblocking/quic.rs`, this is exactly the enforcement path for unstaked connection admission: `is_allowed` is checked before handshake completes and `register_connection` is checked immediately after handshake completion, both keyed on `incoming.remote_address().ip()` / `from.ip()` [4](#0-3) [5](#0-4) . Because an attacker can complete a QUIC handshake from a new IPv6 address in the same /64 for every connection attempt (IPv6 /64 gives 2^64 addresses, trivially assignable on a single NIC/host under `ip -6 addr add`), each attempt is a distinct DashMap key with a fresh `TokenBucket`, so the per-IP cap (`DEFAULT_MAX_CONNECTIONS_PER_IPADDR_PER_MINUTE = 8`, configurable via `max_connections_per_ipaddr_per_min`) [6](#0-5)  is never actually enforced against this attacker.

The only remaining backstop is the global `overall_connection_rate_limiter` (a single shared `TokenBucket`, not keyed by source) checked in `quic.rs` both pre-handshake and post-handshake [7](#0-6) [8](#0-7) . This limiter caps *total* connection throughput cluster-wide but provides no per-source fairness — an attacker with IP diversity can consume a disproportionate share of this shared global budget while legitimate single-IP unstaked senders are throttled by both the (ineffective-for-attacker) per-IP limiter and the same shared global budget, in effect being crowded out.

### Impact Explanation
This is a QoS/fairness evasion, not a crash or consensus bug: an unstaked attacker who churns IPv6 source addresses can consume a disproportionate share of the leader's unstaked QUIC connection admission budget (bounded by the global `overall_connection_rate_limiter` and `DEFAULT_MAX_UNSTAKED_CONNECTIONS`), starving legitimate unstaked senders who present a single, stable source IP and are correctly per-IP throttled. This matches the "unstaked connection/stream/per-IP QoS limits bypass leading to unfair TPU capacity capture" bounty category referenced in the question. It does not enable unbounded resource growth beyond the existing global caps, node panics, or consensus violations, since `DEFAULT_MAX_UNSTAKED_CONNECTIONS` and `overall_connection_rate_limiter` still bound total admitted connections.

### Likelihood Explanation
High feasibility for an attacker with routable IPv6 connectivity: no stake, no identity, and no special privilege is required — only the ability to bind many source addresses within an owned /64 block (a standard feature on most cloud providers and readily available IPv6 transit). The attack is trivially repeatable and requires no timing precision beyond completing enough QUIC handshakes within the observation window (a minute, per the token bucket's refill rate). The codebase shows no IPv6-prefix aggregation logic anywhere (confirmed by search for `/64`, `Ipv6Addr`, `to_canonical`, `prefix` in the relevant streamer/net-utils code), so the bypass is unconditional for any attacker with IPv6 address diversity.

### Recommendation
Normalize the rate-limiter key for IPv6 addresses to a fixed prefix (e.g., the /64 network, matching common ISP/cloud allocation granularity) before insertion into `KeyedRateLimiter<IpAddr>` in `ConnectionRateLimiter::register_connection` and `is_allowed`, so all addresses within an attacker-controlled subnet share a single token bucket. Consider introducing a second key type (e.g., `IpNet`/prefix) or masking the low 64 bits of IPv6 addresses via `Ipv6Addr::to_bits() & !0u64` (or equivalent) prior to calling `consume_tokens`/`current_tokens`, while leaving IPv4 keyed as-is (since IPv4 spoofing is already bounded by address scarcity and NAT considerations).

### Proof of Concept
```rust
// streamer/src/nonblocking/connection_rate_limiter.rs (new test)
#[tokio::test]
async fn test_connection_rate_limiter_ipv6_prefix_churn_bypass() {
    use std::net::Ipv6Addr;
    // limit_per_minute=3, burst=3: mirrors DEFAULT_MAX_CONNECTIONS_PER_IPADDR_PER_MINUTE-style config
    let limiter = ConnectionRateLimiter::new(3, 3, 4);

    // Simulate a single attacker /64 block: 2001:db8:1234:5678::/64
    // Generate 100 distinct addresses within the same /64 (only low 64 bits vary).
    let base: u128 = 0x2001_0db8_1234_5678_0000_0000_0000_0000;
    let mut allowed_count = 0;
    for i in 0..100u128 {
        let ip = IpAddr::V6(Ipv6Addr::from(base | i));
        if limiter.register_connection(&ip) {
            allowed_count += 1;
        }
    }

    // Current behavior: every distinct address is treated as unseen, so all
    // 100 "connections" are admitted despite sharing a single /64 attacker prefix,
    // demonstrating the per-source cap (3/min) is bypassed via address churn.
    assert_eq!(
        allowed_count, 100,
        "expected all connections admitted under current unprefixed IpAddr keying, \
         demonstrating bypass of per-IP rate limit via IPv6 /64 address churn"
    );

    // Expected behavior after fix (prefix-aware keying): only ~3 (limit_per_minute)
    // of the 100 attempts from the same /64 should be admitted.
}
```

    pub fn is_allowed(&self, ip: &IpAddr) -> bool {
        // Check if we have records in the rate limiter for the given IP address
        match self.limiter.current_tokens(ip) {
            Some(r) => r > 0, // we have a record, and rate is not exceeded
            None => true,     // if we have not seen IP, allow connection request
        }
    }

    pub fn register_connection(&self, ip: &IpAddr) -> bool {
        if self.limiter.consume_tokens(*ip, 1).is_ok() {
            debug!("Request from IP {ip:?} allowed");
            true // Request allowed
        } else {
            debug!("Request from IP {ip:?} blocked");
            false // Request blocked
        }
    }
