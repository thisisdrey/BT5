## Analog Vulnerability Found

### Title
QUIC connection stake classification is cached at handshake and never revalidated, letting an actor whose stake is later reduced/removed keep elevated stake-weighted QoS for the life of the connection - ([File: streamer/src/nonblocking/swqos.rs])

### Summary
The Covalent report describes a "check-once, exploit-forever" pattern: a restrictive state change (`freeze`) is checked at every entry point *except* the completion step of an already-started, time-delayed action (`transferUnstakedOut`/`recoverUnstaking`), so an actor who begins the action before the restriction lands keeps enjoying pre-restriction privileges for the whole subsequent window. Agave's stake-weighted QUIC QoS (`SwQos`) has the identical structural bug: a peer's stake is snapshotted once when a QUIC connection is admitted, and that snapshot is used for the *entire lifetime* of the connection for admission limits, per-connection stream caps, and per-stream throttling, with no re-check against the live, periodically-updated `StakedNodes` state.

### Finding Description
`SwQos::build_connection_context` looks up the peer's current stake exactly once, at connection-establishment time, via `get_connection_stake`, and bakes the result into a `ConnectionPeerType` (`Staked(stake)` or `Unstaked`) stored in `SwQosConnectionContext`: [1](#0-0) 

That cached `peer_type`/`total_stake` is then reused for the connection's entire lifetime:
- Admission and eviction/pruning weight in `try_add_connection` (staked table capacity, `prune_random(..., stake)`): [2](#0-1) 
- Per-connection max concurrent uni-streams computed once in `cache_new_connection`: [3](#0-2) 
- Per-stream throttling allowance recomputed on *every new stream* but still keyed off the stale cached `peer_type`/`total_stake` rather than a fresh stake lookup, via `max_streams_per_throttling_interval` → `on_new_stream`: [4](#0-3) [5](#0-4) 

The underlying `staked_nodes: Arc<RwLock<StakedNodes>>` is a live, shared, periodically-refreshed view of current cluster stake (populated from bank state), and `get_connection_stake` correctly reads it fresh: [6](#0-5) 

But there is no code path anywhere in `swqos.rs` that re-queries `staked_nodes` for an already-open connection's `SwQosConnectionContext`. Once a connection is classified `Staked(stake)`, it keeps that classification — and the throughput budget derived from it — until the connection is closed, regardless of subsequent stake decreases (deactivation, unstaking, delegation withdrawal, or removal from the epoch's staked-nodes set).

### Impact Explanation
This is the "QoS evasion" analog explicitly in scope: an actor can lock in a favorable `ConnectionPeerType::Staked(stake)` classification by opening (or keeping open) a QUIC TPU connection while stake is high, and then continue consuming a disproportionate share of the stake-weighted stream/connection budget — via `compute_max_allowed_uni_streams_with_rtt` and `StakedStreamLoadEMA::available_load_capacity_in_throttling_duration` — even after their stake is reduced or removed on-chain. Because staked capacity is a shared, limited resource (`QUIC_TOTAL_STAKED_CONCURRENT_STREAMS`, `max_staked_connections`, per-throttle-interval stream budgets), this degrades fairness for legitimately still-staked peers and undermines the entire purpose of stake-weighted QoS, which is to continuously prioritize traffic in proportion to *current* stake.

### Likelihood Explanation
Any client maintaining a long-lived QUIC connection (which is the normal, encouraged usage pattern for TPU clients via `ConnectionCache`/`tpu-client-next`) will retain its stake classification across epoch boundaries or stake-change events, since nothing in the connection lifecycle forces a re-lookup. No special validator/operator privilege is needed to trigger it beyond having been staked at some point and then having stake reduced while an existing connection stays open — this is reachable by any unprivileged QUIC/TPU client.

### Recommendation
Periodically re-evaluate `peer_type`/`total_stake` for open connections against the current `staked_nodes` snapshot (e.g., on each `on_new_stream`/`on_stream_accepted` call, or via a periodic background sweep of the connection tables), and downgrade/evict connections whose backing stake has dropped, mirroring how `transferUnstakedOut`/`recoverUnstaking` were fixed by adding a live frozen-state check instead of relying on a stale precondition.

### Proof of Concept
1. Attacker's identity key has significant stake in the current epoch's `StakedNodes`.
2. Attacker opens a QUIC connection to a validator's TPU; `build_connection_context` snapshots `ConnectionPeerType::Staked(large_stake)` and `total_stake` into `SwQosConnectionContext` (`streamer/src/nonblocking/swqos.rs:302-341`).
3. Attacker's stake is subsequently reduced to near-zero or removed (deactivation/unstake), and `staked_nodes` is updated to reflect this on the next refresh.
4. Attacker keeps the original QUIC connection open (no reconnect). Every subsequent `on_new_stream` call still computes `max_streams_per_throttling_interval` from the stale cached `peer_type`/`total_stake` (`swqos.rs:292-298`, `496-516`), so the attacker continues sending at the original high-stake throughput/stream-count allowance, evading the intended reduced QoS.

                stream_counter: None,
                last_update: Arc::new(AtomicU64::new(timing::timestamp())),

            |(pubkey, stake, total_stake)| {
                // The heuristic is that the stake should be large enough to have 1 stream pass through within one throttle
                // interval during which we allow max (MAX_STREAMS_PER_MS * STREAM_THROTTLING_INTERVAL_MS) streams.

                let peer_type = {
                    let max_streams_per_ms = self.staked_stream_load_ema.max_streams_per_ms();
                    let min_stake_ratio =
                        1_f64 / (max_streams_per_ms * STREAM_THROTTLING_INTERVAL_MS) as f64;
                    let stake_ratio = stake as f64 / total_stake as f64;

                    in_staked_table: false,
