### Title
Incomplete Duplicate-Signer Comparison Lets a Single Key Multiply Its Weight in ValidateMultiSign Precompile - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `ValidateMultiSign` TVM precompile (address `0x66`) is meant to let a smart contract verify that a threshold of *distinct* account-permission keys have signed a given hash. Its de-duplication check for "has this signer already been counted" compares the **full signature bytes** (`address ++ signature`) instead of comparing on the **signer address alone**. Because an ECDSA signature over the same hash is not unique per key (different nonces / signature malleability produce different byte strings for the same signer), an attacker can submit two syntactically different signatures produced by the *same* private key and have both counted toward `totalWeight`, defeating the multi-signature threshold check.

### Finding Description
`ValidateMultiSign.execute` iterates over the caller-supplied signature array and tracks which signers have already contributed weight using `executedSignList`, a flat list alternating `merge(recoveredAddr, sign)` entries and `recoveredAddr` entries: [1](#0-0) 

The relevant logic is:
```
if (ByteArray.matrixContains(executedSignList, recoveredAddr)) {
  if (ByteArray.matrixContains(executedSignList, sign)) {
    continue;
  }
  MUtil.checkCPUTime();
}
long weight = TransactionCapsule.getWeight(permission, recoveredAddr);
...
totalWeight += weight;
executedSignList.add(sign);
executedSignList.add(recoveredAddr);
```
When `recoveredAddr` has already appeared, the code only skips (`continue`) the weight addition if the **exact merged signature bytes** (`sign`) also match a prior entry. If the same address recovers again but with a *different* signature byte string (which is trivial to produce for the same private key/hash — different `k` nonce, or by flipping `s` to `n-s`, or ASN.1/DER re-encoding depending on `SignUtils` acceptance), the "already contains recoveredAddr" branch falls through instead of being rejected, and `totalWeight += weight` executes again for the same signer.

This is a textbook "incomplete comparison with missing factor" bug (CWE-697): the correct invariant to enforce is "this **address** has already been counted", but the code additionally requires the **raw signature bytes** to match before treating it as a duplicate, so it fails to reject a duplicate signer with a different valid signature.

Contrast this with the canonical, correct implementation in `TransactionCapsule.checkWeight`, which de-duplicates strictly by address (`addMap.containsKey(base64)` keyed on the recovered/encoded address) and throws `"has signed twice!"` regardless of the raw signature bytes: [2](#0-1) 

`ValidateMultiSign` does not apply this same address-only dedup rule, which is the root cause.

### Impact Explanation
`ValidateMultiSign` is a public precompile reachable by any smart contract on TVM (any TriggerSmartContract caller, i.e. an unprivileged transaction broadcaster / contract deployer). Contracts (custodial wallets, DAOs, bridges, escrow contracts, etc.) commonly rely on this precompile to gate privileged operations behind an on-chain multisig-threshold check without re-implementing signature aggregation themselves. Because a single controlled key can be counted multiple times by supplying multiple distinct valid signatures over the same hash, an attacker who controls just one key in the permission (with weight below the threshold) can forge a "passing" `ValidateMultiSign` result, causing any depending contract logic (fund release, permission change, order execution, etc.) to authorize actions that should have required independent approval from multiple distinct key holders. This is a concrete unauthorized-account-operation / theft-of-funds primitive for any application built on top of this precompile.

### Likelihood Explanation
High. No special privileges are required — only the ability to deploy or call a contract that invokes the `ValidateMultiSign` precompile with attacker-controlled signature array data, and knowledge of one private key already present (with nonzero weight) in the target account's permission. Producing two distinct valid ECDSA signatures for the same message with the same key is trivial (different random nonce `k`, or `s → n − s` malleable variant, depending on what `SignUtils`/`recoverAddrBySign` accepts).

### Recommendation
Change the duplicate-signer check in `ValidateMultiSign.execute` to key strictly on `recoveredAddr` (not on the combined `sign` bytes), mirroring `TransactionCapsule.checkWeight`'s address-only `addMap` dedup: if `recoveredAddr` has already been counted, skip/reject regardless of whether the exact signature bytes differ. This closes the "missing factor" gap by ensuring the check enforces "one weight contribution per distinct address" rather than "one weight contribution per distinct signature."

### Proof of Concept
1. Create an account whose Active permission has one key `K` with weight `W < threshold`, plus other unrelated keys.
2. Compute `hash = sha256(address ++ permissionId ++ data)` as done inside the precompile.
3. Using only the private key for `K`, produce two different valid signatures `sig1` and `sig2` over `hash` (e.g., by resigning to get a different nonce, or flipping `s` to `n - s` for signature malleability).
4. Deploy/call a contract that invokes the `ValidateMultiSign` precompile with `signatures = [sig1, sig2]`.
5. Inside `execute`, both signatures recover to the same `recoveredAddr` for key `K`. The first iteration adds weight `W`. On the second iteration, `matrixContains(executedSignList, recoveredAddr)` is true, but `matrixContains(executedSignList, sign)` is false (different signature bytes), so the code does **not** `continue` — it proceeds to add `W` again, making `totalWeight = 2W`, which can now reach or exceed `threshold` even though only a single distinct signer participated.
6. The precompile returns "true" (`dataOne()`), and the calling contract treats the multisig check as satisfied despite only one real signer being involved. [3](#0-2)
