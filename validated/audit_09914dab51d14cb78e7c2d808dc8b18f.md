### Title
Rounding drift in `MarketSellAssetActuator` order matching can mint/burn tokens across trades - (File: `actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java`)

### Summary
The external USSD report describes unauthorized minting/burning of tokens because balance-changing functions were reachable without proper authorization/accounting checks. The closest analogous, actually-reachable issue in java-tron via a single signed transaction is in the on-chain exchange order matching in `MarketSellAssetActuator`, where amounts credited to the maker and taker are computed independently with separate, non-reciprocal integer-division roundings (`MarketUtils.multiplyAndDivide`), rather than deriving one side's credit directly from the other side's debit. This can create a persistent mismatch between the tokens deducted from the seller side and tokens credited to the buyer side across repeated small-order matches, effectively minting or burning fractions of TRC10/TRX balances that are not backed by any corresponding deduction, unlike a normal swap where credited amount must equal debited amount.

### Finding Description
`MarketSellAssetActuator.matchSingleOrder` computes, in the "taker > maker" and "taker == maker" branches, `makerBuyTokenQuantityReceive` via `MarketUtils.multiplyAndDivide(makerSellRemainQuantity, makerBuyQuantity, makerSellQuantity, ...)` [1](#0-0) , while the corresponding `takerBuyTokenQuantityReceive` in the same block is set directly to `makerOrderCapsule.getSellTokenQuantityRemain()` (a different value with no matching division) [2](#0-1) . In the "taker < maker" branch, `takerBuyTokenQuantityReceive` is taken from `takerBuyTokenQuantityRemain` (computed earlier via `multiplyAndDivide`), while `makerBuyTokenQuantityReceive` is set to `takerOrderCapsule.getSellTokenQuantityRemain()` directly [3](#0-2) . These two credited values (`takerBuyTokenQuantityReceive` and `makerBuyTokenQuantityReceive`) are each independently added to the counter-party balances via `addTrxOrToken` [4](#0-3) , with no cross-check that the total minted across the trade equals the total token/TRX debited from the corresponding sell-side quantity that was reduced when the order was originally created (`transferBalanceOrToken` / `reduceAssetAmountV2`) [5](#0-4) .

`MarketUtils.multiplyAndDivide` performs plain floor integer division with no remainder tracking or carry-forward mechanism [6](#0-5) , so each match event can round in favor of either the maker or the taker. Because a single transaction (`MarketSellAssetContract`, reachable by any account via `MarketSellAssetActuator.execute`) can trigger up to `MAX_MATCH_NUM` (20) matches in a loop `matchOrder` [7](#0-6) , and an attacker fully controls both the sell/buy quantities of new orders they place (subject only to balance and quantity-limit checks in `validate()`) [8](#0-7) , an attacker can deliberately construct sequences of small, adversarially-chosen sell/buy quantities and self-trade (place both maker and taker orders from accounts they control) to repeatedly bias the rounding in the same direction, accumulating token or TRX balance that was never deducted from any account (or losing none while removing balance from a victim) across many transactions.

### Impact Explanation
This differs from the reported "onlyBalancer" issue in mechanism (no missing access-control modifier exists here — anyone is legitimately allowed to trade), but it produces the same class of impact: creation of unbacked balance / permanent value leakage in a monetary primitive that other protocol logic (`collateralFactor`-equivalent invariants such as total asset/TRX conservation) implicitly assumes holds. If exploitable at scale, an attacker can create free TRX or TRC10 tokens (inflating total circulating supply beyond what was actually deposited/frozen), or drain counter-parties' balances through systematic rounding loss, both of which are High-severity, since they directly cause unbacked balance / theft of funds in a component reachable by any unprivileged transaction sender.

### Likelihood Explanation
Likelihood depends on the actual magnitude of the rounding drift per match, which requires deeper numerical analysis (e.g., simulating specific ratios of `sellTokenQuantity`/`buyTokenQuantity` across chained self-trades) that could not be completed within the available tool budget. The code path is reachable by any account with no special privilege, and the loop allows up to 20 matches per transaction, and an attacker can send unlimited transactions, so if any non-zero, directionally-biased rounding drift exists, it is fully attacker-controlled and repeatable indefinitely.

### Recommendation
Ensure that in every match, the amount credited to one party is derived directly (and exactly) from the amount debited from the other party — i.e., compute only one "receive" quantity per pairwise transfer via `multiplyAndDivide` and use that same value (or its exact complement) for both sides of the transfer, rather than independently computing/rounding both `takerBuyTokenQuantityReceive` and `makerBuyTokenQuantityReceive`. Add invariant checks/tests asserting that the sum of all token amounts added to accounts during a match equals the sum of all token amounts removed from the corresponding sell-side quantities, and add fuzz/property tests across many small quantity ratios and repeated self-trades to confirm no persistent unbacked balance can accumulate.

### Proof of Concept
Conceptual PoC (not fully simulated due to tool constraints):
1. Attacker controls two accounts, A and B, each holding some TRC10 token X and TRX.
2. Account B places a maker sell order for token X priced such that `makerSellQuantity`/`makerBuyQuantity` has no exact GCD-aligned ratio with the eventual taker order (e.g., sell 7 X for 3 TRX).
3. Account A (taker) repeatedly places small `MarketSellAssetContract` orders (`MarketSellAssetActuator`) against B's resting order, each sized so that `multiplyAndDivide` rounds down on B's `makerBuyTokenQuantityReceive` in `matchSingleOrder` while A's `takerBuyTokenQuantityReceive` is taken from the maker's full remaining sell quantity (not re-divided) [9](#0-8) .
4. After N matches, sum the total TRX/token credited to A and B via `addTrxOrToken` and compare against the total debited via `transferBalanceOrToken`/`reduceAssetAmountV2` for the orders consumed; a persistent positive delta indicates unbacked token creation.

Because verifying the exact numeric conditions under which the rounding is directionally exploitable (rather than merely lossy/neutral) requires running the arithmetic across many ratios — which could not be completed here — this should be treated as a finding requiring numerical verification/fuzzing before remediation prioritization, but the code pattern (independent, non-reciprocal integer-division rounding on both sides of a value transfer inside a market-matching loop reachable by arbitrary transactions) is a legitimate root cause matching the "unbacked balance creation" impact class of the reported bug.

  public static long multiplyAndDivide(long a, long b, long c, boolean disableMath) {
    try {
      long tmp = multiplyExact(a, b, disableMath);
      return floorDiv(tmp, c, disableMath);
    } catch (ArithmeticException ex) {
      // do nothing here, because we will use BigInteger to compute again
    }

    BigInteger aBig = BigInteger.valueOf(a);
    BigInteger bBig = BigInteger.valueOf(b);
    BigInteger cBig = BigInteger.valueOf(c);

    return aBig.multiply(bBig).divide(cBig).longValue();
  }
