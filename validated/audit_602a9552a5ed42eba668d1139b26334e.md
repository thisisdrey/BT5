### Title
Unvalidated `git_object_directory`/`git_alternate_object_directories` request fields allow path traversal when spawning Git commands - (File: internal/git/alternates/alternates.go)

### Summary
Gitaly's `Repository` protobuf message carries two client-controllable fields, `git_object_directory` and `git_alternate_object_directories` [1](#0-0) , which are meant to point Git at a quarantine directory during pushes. When Gitaly resolves a repository's *object directory path* for user-facing size/introspection RPCs, it validates that this path stays within the repository/storage boundary via `ObjectDirectoryPath()` [2](#0-1) . However, the lower-level function that actually injects these same fields into every spawned Git subprocess's environment, `alternates.Env`, performs no such validation at all [3](#0-2) , and is called directly from `ExecCommandFactory.newCommand` with the raw, unvalidated repository fields [4](#0-3) .

### Finding Description
`ObjectDirectoryPath()` in `internal/git/localrepo/paths.go` is a “read-checking” path: before returning an object directory location (used e.g. by `GetObjectDirectorySize`), it calls `storage.ValidateRelativePath` to ensure the path is inside the storage root, and additionally verifies that non-standard (quarantine-style) object directories carry the expected repository-specific `QuarantineDirectoryPrefix` [5](#0-4) . This is the equivalent of `claimRewards`'s "already-claimed" check in the original report — a defensive check that exists on one code path.

The equivalent “write/exec” path — `ExecCommandFactory.newCommand`, which is invoked for essentially every Git subprocess Gitaly spawns for any RPC — builds the process environment via `alternates.Env(repoPath, repo.GetGitObjectDirectory(), repo.GetGitAlternateObjectDirectories())` [4](#0-3) . `alternates.Env` simply does `filepath.Join(repoPath, objectDirectory)` for `GIT_OBJECT_DIRECTORY` and the same for each alternate, with **no bounds checking, no `ValidateRelativePath` call, and no quarantine-prefix verification** [3](#0-2) . This mirrors the report’s core defect: a check present on one path (`getRewardsAmount`/`ObjectDirectoryPath`) is missing on the equivalent operational path (`claimRewards`/`newCommand`+`alternates.Env`) that actually matters most, since it is used for command execution rather than just introspection.

Other call sites reinforce that these two fields are treated as free-form, repository-relative paths and are joined onto `repoPath` without validation elsewhere too, e.g. custom hook environment construction `customHooksEnv` also does a bare `filepath.Join(repoPath, alternateObjectDirectory)` [6](#0-5) , and `quarantine.Apply` sets `GitAlternateObjectDirectories` from the caller-controlled `repo.GetGitObjectDirectory()` value without re-validating it [7](#0-6) .

### Impact Explanation
If a value such as `../../../../some/other/storage-or-path` is supplied in `git_object_directory` or `git_alternate_object_directories` on a `Repository` message passed to any RPC, `alternates.Env` will happily construct `GIT_OBJECT_DIRECTORY=/var/gitlab/storage/../../../../some/other/path` and `GIT_ALTERNATE_OBJECT_DIRECTORIES=...` and inject them into every Git subprocess spawned for that RPC. Since `GIT_ALTERNATE_OBJECT_DIRECTORIES` causes Git to search for and read objects from that path, and `GIT_OBJECT_DIRECTORY` causes new objects (e.g., from `commit-tree`, `receive-pack`, `merge`, `cherry-pick`) to be **written** there, this can result in:
- Cross-repository object disclosure by pointing `GIT_ALTERNATE_OBJECT_DIRECTORIES` at another repository's `objects` directory (bypassing the isolation that `ObjectDirectoryPath`/quarantine-prefix checks are meant to provide elsewhere), and
- Writing/leaking Git objects to arbitrary filesystem locations outside the intended storage root via `GIT_OBJECT_DIRECTORY` traversal.

This falls squarely within the "cross-repository object access" and "object-pool and alternates isolation" categories called out as valid analogs.

### Likelihood Explanation
`git_object_directory` / `git_alternate_object_directories` are legitimate, documented fields of the `Repository` message that GitLab Rails/gitlab-shell populate during ordinary push flows (object quarantine) and pass back to Gitaly on subsequent RPCs during access checks [8](#0-7) . Because the value is round-tripped through an external system (Rails) and ultimately supplied back to Gitaly as part of a normal RPC field, any component in that chain capable of influencing this field (or a malformed/compromised intermediate) can reach `alternates.Env` on essentially any Git-invoking RPC. I was not able to fully confirm, within the available tool budget, whether `s.locator.ValidateRepository()` (used as a general RPC-entry guard in handlers such as `GetObjectDirectorySize`/`RepositorySize`, see `internal/gitaly/config/locator.go`) independently sanitizes these two specific fields before the repository message reaches `ExecCommandFactory.newCommand` for other RPCs; this is a gap in my verification that should be checked against `ValidateRepository`'s implementation.

### Recommendation
Route `git_object_directory` and `git_alternate_object_directories` through the same validation used by `ObjectDirectoryPath` (i.e., `storage.ValidateRelativePath` plus the quarantine-prefix check) before they are used in `alternates.Env`, ideally centralizing this validation in `ExecCommandFactory.newCommand` (and in `customHooksEnv`) rather than leaving it only in the read-only `ObjectDirectoryPath` helper.

### Proof of Concept
1. Send any RPC that operates on a repository and accepts a `Repository` message with attacker/caller-influenced `git_object_directory` set to a relative path containing `../` sequences that resolve outside the repository's/storage's boundary, e.g. `git_object_directory: "../../../other-repo/objects"`.
2. `ExecCommandFactory.newCommand` calls `alternates.Env(repoPath, "../../../other-repo/objects", nil)` [4](#0-3) , producing `GIT_OBJECT_DIRECTORY=<repoPath>/../../../other-repo/objects` with no boundary check [3](#0-2) .
3. Any Git subprocess spawned for that RPC (e.g., `commit-tree`, `receive-pack`) will read/write objects at the traversed path instead of the intended repository's object directory, in contrast to what `ObjectDirectoryPath()` would have rejected with `structerr.NewInvalidArgument` had the same value been passed to it [5](#0-4) .

func (repo *Repo) ObjectDirectoryPath(ctx context.Context) (string, error) {
	repoPath, err := repo.Path(ctx)
	if err != nil {
		return "", err
	}

	objectDirectoryPath := repo.GetGitObjectDirectory()
	if objectDirectoryPath == "" {
		return "", structerr.NewInvalidArgument("object directory path is not set")
	}

	storagePath, err := repo.locator.GetStorageByName(ctx, repo.GetStorageName())
	if err != nil {
		return "", fmt.Errorf("get storage by name: %w", err)
	}

	// Ensure the path points somewhere in the storage.
	relativeObjectDirectoryPath, err := storage.ValidateRelativePath(storagePath, filepath.Join(repoPath, objectDirectoryPath))
	if err != nil {
		return "", structerr.NewInvalidArgument("validate relative path: %w", err)
	}

	parentDir := filepath.Base(filepath.Dir(relativeObjectDirectoryPath))
	baseDir := filepath.Base(relativeObjectDirectoryPath)
	isTransactionQuarantineDir := (baseDir == "quarantine") || ((parentDir == "quarantine") && strings.HasPrefix(baseDir, "tmp_objdir"))

	// Transactions quarantine a repository by pointing the object directory to a 'quarantine' named
	// directory in the transaction's temporary directory. If the base directory is `quarantine`,
	// Git push may apply an additional layer of quarantine such as `/quarantine/tmp_objdir-incoming-Gbc29N`
	// so we don't assert the `/quarantine` being the last element of the path. We thus also check for
	// whether the parent directory is in `quarantine` and whether the base directory has the expected
	// `tmp_objdir` suffix.
	if !isTransactionQuarantineDir {
		// We need to check whether the relative object directory as given by the repository is
		// a valid path. This may either be a path in the Git repository itself, where it may either
		// point to the main object directory storage or to an object quarantine directory as
		// created by git-receive-pack(1). Alternatively, if that is not the case, then it may be a
		// manual object quarantine directory located in the storage's temporary directory. These
		// have a repository-specific prefix which we must check in order to determine whether the
		// quarantine directory does in fact belong to the repo at hand.
		if _, origError := storage.ValidateRelativePath(repoPath, objectDirectoryPath); origError != nil {
			tempDir, err := repo.locator.TempDir(repo.GetStorageName())
			if err != nil {
				return "", structerr.NewInvalidArgument("getting storage's temporary directory: %w", err)
			}

			expectedQuarantinePrefix := filepath.Join(tempDir, storage.QuarantineDirectoryPrefix(repo))
			absoluteObjectDirectoryPath := filepath.Join(repoPath, objectDirectoryPath)

			// The relative path is outside of the repository
			if !strings.HasPrefix(absoluteObjectDirectoryPath, expectedQuarantinePrefix) {
				return "", structerr.NewInvalidArgument("not a valid relative path: %w", origError)
			}
		}
	}

// Env returns the alternate object directory environment variables.
func Env(repoPath, objectDirectory string, alternateObjectDirectories []string) []string {
	var env []string
	if objectDirectory != "" {
		env = append(env, fmt.Sprintf("GIT_OBJECT_DIRECTORY=%s", filepath.Join(repoPath, objectDirectory)))
	}

	if len(alternateObjectDirectories) > 0 {
		var dirsList []string

		for _, dir := range alternateObjectDirectories {
			dirsList = append(dirsList, filepath.Join(repoPath, dir))
		}

		env = append(env, fmt.Sprintf("GIT_ALTERNATE_OBJECT_DIRECTORIES=%s", strings.Join(dirsList, ":")))
	}

	return env
}

// Apply applies the quarantine on the repository. This is done by setting the quarantineDirectory
// as the repository's object directory, and configuring the repository's object directory as an alternate.
func Apply(repoPath string, repo *gitalypb.Repository, quarantineDir string) (*gitalypb.Repository, error) {
	relativePath, err := filepath.Rel(repoPath, quarantineDir)
	if err != nil {
		return nil, fmt.Errorf("creating quarantine: %w", err)
	}

	// All paths are relative to the repository root.
	objectDir := repo.GetGitObjectDirectory()
	if objectDir == "" {
		// Set the default object directory as an alternate if the repository didn't
		// have the object directory overwritten yet.
		objectDir = "objects"
	}

	alternateObjectDirs := make([]string, 0, len(repo.GetGitAlternateObjectDirectories())+1)
	alternateObjectDirs = append(alternateObjectDirs, objectDir)
	alternateObjectDirs = append(alternateObjectDirs, repo.GetGitAlternateObjectDirectories()...)

	quarantinedRepo := proto.Clone(repo).(*gitalypb.Repository)
	quarantinedRepo.GitObjectDirectory = relativePath
	quarantinedRepo.GitAlternateObjectDirectories = alternateObjectDirs

	return quarantinedRepo, nil
}

### How GitLab passes the object quarantine information around

To overcome this problem, the GitLab `pre-receive` hook
[reads the object directory configuration from its environment](https://gitlab.com/gitlab-org/gitaly/-/blob/71d527f4f16c1f0e76793f055def0299b375cc7d/internal/gitlabshell/env.go#L9).

On the Rails side, we then
[put the object directory information in the "request store"](https://gitlab.com/gitlab-org/gitlab/-/blob/master/lib/api/internal/base.rb#L43)
(i.e., request-scoped thread-local storage). And then during that
Rails request, when Rails makes Gitaly requests on this repo, we send back the quarantine information
[in the Gitaly `Repository` struct](https://gitlab.com/gitlab-org/gitlab/-/blob/f81f30c29a0edce20f6737fdccc3315c8baab9d1/lib/gitlab/gitaly_client/util.rb#L8-17).

that were present on the `pre-receive` hook, so that we can see the
quarantined objects.
