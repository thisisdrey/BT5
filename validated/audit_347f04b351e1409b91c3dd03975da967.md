### Title
Unauthenticated `RecvError` packets allow remote attackers to force-close established tunnels without any certificate or cryptographic proof - ([File: outside.go])

### Summary
`header.RecvError` packets are dispatched in `readOutsidePackets` before any decryption or certificate verification takes place, and `handleRecvError` tears down an existing, fully-authenticated tunnel based only on a 32-bit index and a source-address comparison — neither of which is cryptographically authenticated. This lets an attacker who holds no CA-signed Nebula certificate forge tunnel-teardown packets, forcing legitimate peers' tunnels to be destroyed at will.

### Finding Description
In `outside.go`, `readOutsidePackets` parses the header and, for unencrypted message types, dispatches immediately without any peer/cert validation: [1](#0-0) 

```go
switch h.Type {
case header.Handshake:
    f.handshakeManager.HandleIncoming(via, packet, h)
    return

case header.RecvError:
    f.handleRecvError(via.UdpAddr, h)
    return
}
```

`handleRecvError` then does this: [2](#0-1) 

The only gates are:
1. `f.acceptRecvErrorConfig.ShouldRecvError(addr)` — a local policy/rate-limiting check, not a cryptographic authentication mechanism.
2. `hr.IsValid() && hr != addr` — a comparison against the currently known UDP source address of the hostinfo.

Neither check involves any certificate, MAC, or encrypted payload. `h.RemoteIndex` (the index used to look up the hostinfo via `f.hostMap.QueryReverseIndex`) is sent in cleartext in the header of *every* packet a tunnel exchanges — it is not a secret, and any attacker capable of eavesdropping on the path, or of guessing/observing it, can supply this value to target a specific, already-established tunnel. The `addr` value is the packet's UDP source address, which is trivially spoofable at the UDP/IP layer by an attacker with no relationship to the Nebula overlay whatsoever, or forgeable outright by an on-path attacker.

If the attacker can deliver a UDP packet whose source address matches (or is spoofed to match) the hostinfo's current remote address, and set the header type to `RecvError` with the correct `RemoteIndex`, the receiver immediately calls:

```go
f.closeTunnel(hostinfo)
f.handshakeManager.DeleteHostInfo(hostinfo)
```

This tears down a live, mutually-authenticated tunnel between two legitimate, CA-signed peers, with zero contribution of a valid certificate or successful handshake by the attacker.

### Impact Explanation
This is a remote state-poisoning / denial-of-service primitive reachable by an attacker who possesses no CA-signed certificate at all — it is handled entirely at the pre-authentication, header-parsing stage of the packet pipeline, exactly analogous to the referenced report's theme: an unauthorized/uninvolved party is able to force disruption of a resource (there: reward distribution and farm-closure; here: an established, authenticated VPN tunnel) that legitimate, properly-authorized parties depend on, using a code path that lacks the verification the rest of the system relies on. Repeated forged `RecvError` packets let an attacker persistently sever tunnels between arbitrary pairs of legitimate Nebula peers, defeating the confidentiality/availability guarantees the mesh is meant to provide, without ever presenting a valid certificate.

### Likelihood Explanation
Likelihood is dependent on the attacker's position:
- An on-path (MITM) or same-broadcast-domain attacker can trivially forge the exact source address and observe the `RemoteIndex` in cleartext traffic, making exploitation straightforward.
- A pure off-path attacker would need to either guess/spoof the correct source `AddrPort` (UDP source spoofing is possible on networks/paths that don't filter it) and learn/guess the 32-bit `RemoteIndex`, which is somewhat harder but not cryptographically infeasible over long-lived tunnels or on networks where indices/addresses can be observed via other means (e.g., prior traffic capture, NAT device logs, or a previously-revoked/removed member of the mesh who still has a stale-but-valid index/address pairing they observed while a member).

Because the exact strength of `ShouldRecvError`'s default policy (rate limiting vs. allow-list) could not be fully confirmed from the available index (the definition of `acceptRecvErrorConfig`/`ShouldRecvError` lives in `interface.go`, which the tool budget did not allow me to fully inspect), I cannot state with certainty whether a default configuration meaningfully restricts this attack surface. This is a caveat on likelihood, not on the root-cause finding, which is confirmed directly from `outside.go`.

### Recommendation
Do not act on `RecvError` (or any other pre-decryption/pre-auth signal) to tear down a tunnel based solely on an index+source-address match. At minimum:
- Require some proof of possession of the tunnel's active key material (e.g., only honor `RecvError`-driven teardown if corroborated by a subsequent failed post-handshake exchange, or authenticate `RecvError` similarly to other in-tunnel control messages).
- Rate-limit and require multiple independent confirmations (e.g., several consecutive send failures) before tearing down a tunnel from `handleRecvError`, rather than a single unauthenticated packet.
- Consider binding `RecvError` handling more strictly, e.g. requiring it be tied to an actual send failure recently observed locally (already partially done via `ShouldRecvError`), and never trusting the source-address comparison alone as a substitute for authentication, since UDP source addresses are not a security boundary.

### Proof of Concept
1. Attacker observes (via any vantage point capable of seeing the UDP traffic, e.g., on-path, shared network segment, or prior capture) a live Nebula tunnel between hosts A and B, noting the underlay `AddrPort` of B as seen by A, and the `RemoteIndex` A uses to address B (visible in the cleartext header of every packet A sends to B).
2. Attacker crafts a raw UDP packet with header `Type = header.RecvError`, `RemoteIndex = <observed index>`, and sends it to A's underlay address, spoofing (or, if on-path, naturally having) a source address equal to B's `AddrPort`.
3. A's `readOutsidePackets` dispatches directly to `handleRecvError` without any decryption or certificate check.
4. `f.hostMap.QueryReverseIndex(h.RemoteIndex)` finds the hostinfo for B; `hr == addr` passes because the source address matches B's known remote.
5. A calls `f.closeTunnel(hostinfo)` and `f.handshakeManager.DeleteHostInfo(hostinfo)`, destroying the tunnel to B — accomplished entirely by an attacker holding no CA-signed Nebula certificate.

```go
func (f *Interface) handleRecvError(addr netip.AddrPort, h *header.H) {
	if !f.acceptRecvErrorConfig.ShouldRecvError(addr) {
		f.l.Debug("Recv error received, ignoring",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
		return
	}

	if f.l.Enabled(context.Background(), slog.LevelDebug) {
		f.l.Debug("Recv error received",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
	}

	hostinfo := f.hostMap.QueryReverseIndex(h.RemoteIndex)
	if hostinfo == nil {
		f.l.Debug("Did not find remote index in main hostmap", "remoteIndex", h.RemoteIndex)
		return
	}

	hr := hostinfo.GetRemote()
	if hr.IsValid() && hr != addr {
		f.l.Info("Someone spoofing recv_errors?",
			"addr", addr,
			"hostinfoRemote", hr,
		)
		return
	}

	f.closeTunnel(hostinfo)
	// We also delete it from pending hostmap to allow for fast reconnect.
	f.handshakeManager.DeleteHostInfo(hostinfo)
}
```
