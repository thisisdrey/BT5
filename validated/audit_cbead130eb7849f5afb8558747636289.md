### Title
Unverified attacker-controlled content accepted and permanently written to AtlasDB via unauthenticated `AttachmentRequest` response - ([File: stackslib/src/net/atlas/download.rs])

### Summary
When resolving an `AttachmentRequest`, `AttachmentsBatchStateContext::extend_with_attachments` accepts whatever `Attachment` payload a peer returns and inserts it into `self.attachments` without ever checking that its content hash matches the `content_hash` that was actually requested. The `Done`-state handler in `AttachmentsDownloader::run` then unconditionally calls `atlasdb.insert_instantiated_attachment(&attachment)`, permanently persisting attacker-chosen bytes keyed by their own (self-consistent but uncommitted) Hash160, even when no on-chain `AttachmentInstance` ever asked for that content.

### Finding Description
`AttachmentsBatchStateContext::extend_with_attachments` (`stackslib/src/net/atlas/download.rs:530-558`) processes successful `AttachmentRequest` HTTP responses:
```rust
if let Ok(response) = response.decode_atlas_get_attachment() {
    self.attachments.insert(response.attachment);
    report.bump_successful_requests();
```
The `request` object (which carries the intended `content_hash`, `stackslib/src/net/atlas/download.rs:404-478`, `AttachmentRequest.content_hash`) is discarded — the decoded `response.attachment` is trusted as-is and never compared against `request.content_hash`.

In `AttachmentsDownloader::run` (`stackslib/src/net/atlas/download.rs:153-169`), when the state machine reaches `Done`:
```rust
for attachment in context.attachments.drain() {
    let attachments_instances = network.atlasdb.find_all_attachment_instances(&attachment.hash())?;
    network.atlasdb.insert_instantiated_attachment(&attachment)?;
    for attachment_instance in attachments_instances.into_iter() { ... }
    context.attachments_batch.resolve_attachment(&attachment.hash())
}
```
`insert_instantiated_attachment` is called unconditionally, regardless of whether `find_all_attachment_instances(&attachment.hash())` found any matching, on-chain-committed `AttachmentInstance`. Because `attachment.hash()` is computed from the attacker's own bytes, it is internally self-consistent (the `attachments.hash` column always equals Hash160 of `attachments.content`), but there is no requirement anywhere in this path that this hash equal the `content_hash` field of the `AttachmentRequest` that solicited the response, nor that any real `AttachmentInstance` with that hash exists. The equality `stored_attachment_count == attachments_actually_committed_on_chain` is broken: a responding peer can return arbitrary content for a request and have it written into the persistent `attachments` table with `was_instantiated = 1` (`stackslib/src/net/atlas/db.rs:66-71`), a state from which `evict_expired_uninstantiated_attachments` (which only targets uninstantiated rows) will not clean it up.

Because the real content_hash was never resolved by the bogus response, `resolve_attachment` will not mark the original outstanding attachment as resolved, so the batch is retried (bounded by `connection_options.max_attachment_retry_count`, `stackslib/src/net/atlas/download.rs:188-205`) — each retry with a different garbage payload adds another distinct row to the `attachments` table.

### Impact Explanation
A remote peer chosen as an attachment-inventory source can cause the requesting node to write attacker-chosen bytes into its local `AtlasDB` (`attachments` table) under a hash that has no corresponding on-chain commitment. This is an unauthenticated write to persistent node state. Repeated across retries (bounded by `max_attachment_retry_count`) and across the many distinct pending attachment instances a node processes over its lifetime, this can accumulate unbounded amounts of unrelated, attacker-chosen data in the node's storage, none of which is evicted since it's flagged `was_instantiated`. This matches the Critical category "unauthenticated write to state" via a peer with no privileged role.

### Likelihood Explanation
The attacker needs no privileges beyond being selectable as a data-serving peer for an outbound Atlas sync (an ordinary P2P/RPC peer with an advertised data URL) and must be included in the `sources` map for at least one queued `AttachmentRequest` (`stackslib/src/net/atlas/download.rs:454-474`), which happens naturally once the peer's inventory response claims to have the attachment. The attacker's cost is a single crafted HTTP response per request; it is repeatable across every attachment fetch cycle the node performs, and no signature, hash, or content-length check gates the accepted content against the requested `content_hash`.

### Recommendation
In `AttachmentsBatchStateContext::extend_with_attachments`, after decoding `response.attachment`, verify `response.attachment.hash() == request.content_hash` before inserting into `self.attachments`; drop/penalize the peer (`report.bump_failed_requests()`) on mismatch instead of accepting the payload. Additionally, in `AttachmentsDownloader::run`, only call `insert_instantiated_attachment` when `find_all_attachment_instances(&attachment.hash())` is non-empty (i.e., the attachment was actually solicited by a real, on-chain-committed `AttachmentInstance`); otherwise discard the payload.

### Proof of Concept
```rust
// stackslib/src/net/atlas/tests.rs (illustrative)
#[test]
fn test_unverified_attachment_content_written_to_db() {
    let mut atlasdb = AtlasDB::connect_memory().unwrap();
    let peer_url: UrlString = "http://peer.example".try_into().unwrap();
    let mut ctx = AttachmentsBatchStateContext::new(
        AttachmentsBatch::new(),
        HashMap::from([(peer_url.clone(), ReliabilityReport::empty())]),
        &ConnectionOptions::default(),
    );

    // Attacker fabricates N distinct payloads for content_hash values
    // that were never queued as AttachmentInstance in atlasdb.
    let mut results = BatchedRequestsResult::new(HashMap::new());
    for i in 0..N {
        let fake_content = format!("attacker-garbage-{}", i).into_bytes();
        let fake_attachment = Attachment::new(fake_content);
        let request = AttachmentRequest {
            sources: HashMap::from([(peer_url.clone(), ReliabilityReport::empty())]),
            content_hash: Hash160::from_data(b"legit-content-never-sent-by-attacker"),
            stacks_block_height: 1,
            canonical_stacks_tip_height: None,
        };
        // simulate a decoded HTTP 200 response carrying fake_attachment
        results.succeeded.insert(request, Some(fake_response_with(fake_attachment)));
    }

    ctx = ctx.extend_with_attachments(&mut results);

    // Assert: all N distinct attacker payloads end up written via
    // insert_instantiated_attachment despite none matching any queued
    // AttachmentInstance.content_hash.
    for attachment in ctx.attachments.iter() {
        atlasdb.insert_instantiated_attachment(attachment).unwrap();
        assert!(atlasdb.find_attachment(&attachment.hash()).unwrap().is_some());
        // No AttachmentInstance ever referenced this hash:
        assert!(atlasdb.find_all_attachment_instances(&attachment.hash()).unwrap().is_empty());
    }
    assert_eq!(ctx.attachments.len(), N);
}
```
This demonstrates that `insert_instantiated_attachment` is invoked for content whose hash was never checked against the requested `content_hash` and has no corresponding `AttachmentInstance`, confirming the write-path gap.
