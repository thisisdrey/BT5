### Title
Unvalidated protobuf enum value in `FindLocalBranchesRequest.SortBy` reaches `panic("never reached")` - ([File: internal/gitaly/service/ref/find_local_branches.go])

### Summary
The `FindLocalBranches` RPC parses the client-supplied `SortBy` enum field with a `switch` statement that only handles the three known enum values and falls through to an explicit `panic("never reached")` for anything else. Because protobuf enums are transmitted as raw `int32` values, an unprivileged client can send any out-of-range integer for this field and directly trigger the panic, aborting the goroutine (and, depending on panic-recovery configuration, the whole `gitaly` process) — the same bug class as the reported Fuel Network GraphQL crash, where an unreachable/panic branch was reachable purely through unvalidated client input.

### Finding Description
`FindLocalBranches` calls `s.findLocalBranches`, which computes the git `--sort=` flag via `parseSortKey(in.GetSortBy())`: [1](#0-0) 

`parseSortKey` is implemented as an exhaustive-looking switch over the three defined `FindLocalBranchesRequest_SortBy` enum constants, but any other value — which is fully valid in protobuf's wire format since enums are unconstrained `int32`s — falls through to an explicit panic: [2](#0-1) 

The request handler `FindLocalBranches` performs input validation only on `Repository` and `ExcludePatterns`; it never validates `SortBy` before it reaches `parseSortKey`: [3](#0-2) 

This mirrors the Fuel Network report's root cause exactly: an enum/field combination that "shouldn't" occur according to the author's mental model of valid inputs is treated as truly unreachable and guarded with a panic macro, when in fact the wire protocol (GraphQL input validation in the original report; protobuf enum encoding here) allows an ordinary, unauthenticated/unprivileged caller to produce that "impossible" value.

### Impact Explanation
Any client capable of issuing a `FindLocalBranches` gRPC call (a standard, frequently-used, unprivileged read RPC exposed to ordinary git clients/GitLab callers) can crash the handling goroutine by simply setting `SortBy` to an enum value outside `{0,1,2}` (e.g. `3`). Depending on whether Gitaly's gRPC panic-recovery interceptor treats this as a per-request recoverable panic or allows it to escalate, this results in at minimum a crashed RPC (DoS of the handler) and at worst — consistent with the original report's full process crash — termination of the `gitaly` server process, which would take down all repositories served by that node.

### Likelihood Explanation
Likelihood is high: the RPC requires no special permissions beyond ordinary access already granted for reading branches, the payload construction requires only setting a single integer field to a value outside the three known constants, and no client-side SDK enforcement prevents this because protobuf enums are just integers on the wire.

### Recommendation
Replace the `panic("never reached")` fallback in `parseSortKey` with proper input validation that returns a `structerr.NewInvalidArgument` error for unrecognized `SortBy` values, and validate `in.GetSortBy()` explicitly in `FindLocalBranches` before use, consistent with how `Repository` and `ExcludePatterns` are already validated. Audit other RPCs for similar `switch`-with-`panic`/`unreachable` patterns keyed on client-controlled protobuf enum or oneof fields.

### Proof of Concept
Issue a `FindLocalBranches` gRPC request with `SortBy` set to an integer not matching any defined enum constant (i.e., not `NAME` (0/unset... note zero-value semantics should be checked), `UPDATED_ASC`, or `UPDATED_DESC` — e.g., raw enum value `99`):
```
grpcurl -plaintext -d '{
  "repository": {"storage_name": "default", "relative_path": "path/to/repo.git"},
  "sort_by": {"key": 99}
}' localhost:9999 gitaly.RefService/FindLocalBranches
```
This drives execution into `parseSortKey`'s default fallthrough at `internal/gitaly/service/ref/find_local_branches.go:120`, invoking `panic("never reached")` and crashing the handling goroutine/process, analogous to the `unreachable!()` panic reachable via the `after`/`before`-without-`first`/`last` GraphQL query in the original report.

func (s *server) FindLocalBranches(in *gitalypb.FindLocalBranchesRequest, stream gitalypb.RefService_FindLocalBranchesServer) error {
	if err := s.locator.ValidateRepository(stream.Context(), in.GetRepository()); err != nil {
		return structerr.NewInvalidArgument("%w", err)
	}

	for _, pattern := range in.GetExcludePatterns() {
		p := string(pattern)
		if p == "" {
			return structerr.NewInvalidArgument("empty exclude pattern")
		}
		if strings.ContainsRune(p, 0) {
			return structerr.NewInvalidArgument("exclude pattern contains null byte: %q", p)
		}
		if !strings.HasPrefix(p, "refs/heads/") {
			return structerr.NewInvalidArgument("exclude pattern must start with %q: %q", "refs/heads/", p)
		}
	}

	if err := s.findLocalBranches(in, stream); err != nil {
		return err
	}

	return nil
}

func parseSortKey(sortKey gitalypb.FindLocalBranchesRequest_SortBy) string {
	switch sortKey {
	case gitalypb.FindLocalBranchesRequest_NAME:
		return "refname"
	case gitalypb.FindLocalBranchesRequest_UPDATED_ASC:
		return "committerdate"
	case gitalypb.FindLocalBranchesRequest_UPDATED_DESC:
		return "-committerdate"
	}

}
