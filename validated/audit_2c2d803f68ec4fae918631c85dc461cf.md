### Title
Module-extension `facts` in `MODULE.bazel.lock` are trusted as verified/immutable data with no cryptographic binding to the content they describe, allowing lockfile-only tampering to bypass integrity checks — ([File: src/test/py/bazel/bzlmod/bazel_lockfile_test.py])

### Summary
Bazel's `module_ctx.facts` / `extension_metadata(facts=...)` mechanism is the closest analog in this repo to the LiquidityWindow storage-layout issue: like V1/V2 storage slots, `facts` is a persisted, schema-versioned blob (`factsVersion`) that is reused across extension-implementation changes, and Bazel explicitly warns that stale-schema reinterpretation is possible unless the extension author remembers to bump `facts_version`. But unlike the LiquidityWindow bug, this one is directly attacker-reachable: `facts` are stored in `MODULE.bazel.lock`, a file that (per Bazel's own best practices) is checked into version control and consumed by every CI build off any branch, and the docs recommend using `facts` to record “the download URL and checksum” of network-fetched artifacts specifically to *skip* the checksum-guarded download path on subsequent runs.

### Finding Description
`extension_metadata(facts=...)` lets a non-reproducible module extension persist arbitrary JSON-like data into `MODULE.bazel.lock` under `facts` / `factsVersions`, keyed by extension ID [1](#0-0) . The documentation is explicit that this is meant for “effectively immutable data obtained from outside the build, most commonly from the network, but you don't have a checksum available to guard the download” such as “the download URL and checksum” for an SDK version [2](#0-1) , and that on subsequent evaluations the extension is expected to use the value from `facts` instead of re-fetching/re-verifying it [3](#0-2) .

Validation of `facts` before feeding it back into `ctx.facts` is governed only by (a) `lockFileVersion` matching, (b) `factsVersion` per-extension matching, and — for non-reproducible extensions — Bazel does not require the extension to re-run at all as long as its recorded inputs (`bzlTransitiveDigest`, `usagesDigest`) haven't changed; it just reuses the lockfile's `facts` value verbatim. This is demonstrated by `testDeletedFactsRegeneratedByUpdateMode`, where facts are silently restored (from a machine-local cache) or otherwise consumed [4](#0-3) , and `_addFactToLockfile`, whose own comment describes exactly the attacker-controlled channel: "Simulates the workspace lockfile changing underneath a warm output base, e.g. due to a branch switch or pull that brings in facts produced by an evaluation of the extension on a different machine." [5](#0-4) . `testExternallyUpdatedFactsRegenerateReproducibleExtension` and `testDeletedFactsDetectedByErrorModeForReproducibleExtension` show that only *reproducible* extensions get their facts checked against a re-evaluation for consistency [6](#0-5) ; for non-reproducible extensions (the ones the docs specifically recommend `facts` for, since they can't produce a checksum), there is no such re-verification — the value from the lockfile is simply trusted as ground truth going forward, exactly like `ctx.facts` "may have been created by a different version of the extension, which may have used a different schema" [7](#0-6) .

The merge tooling (`bazel-lockfile-merge.jq`, used to combine concurrently-updated lockfiles, e.g. in CI or git-merge-driver workflows) further confirms `facts` entries are merged shallowly per-key based only on `factsVersion` equality, with no content/hash validation of the merged values themselves [8](#0-7) , and its own tests show facts values freely substituted across merges as long as `factsVersion` matches [9](#0-8) .

### Impact Explanation
Because `MODULE.bazel.lock` is meant to be committed to version control (per Bazel's own best practices) [10](#0-9) , an attacker who can get content merged into a branch that CI builds on (an "untrusted branch CI builds" scenario, per the threat model) can directly edit the `facts` blob for any non-reproducible extension used by the build. If that extension's author followed the documented pattern of storing a "download URL and checksum" pair in `facts` to skip a checksum-guarded fetch, the attacker can substitute an arbitrary sha256/URL pair. Because the extension trusts `ctx.facts` as verified/immutable, this bypasses the very checksum-guard mechanism the `facts` API exists to avoid re-running, letting the attacker redirect a "trusted, immutable" artifact reference to attacker-controlled content without tripping Bazel's usual `sha256`/`integrity` checks on `http_archive`/`http_file`, since the download would proceed using the (attacker-supplied) checksum from `facts` rather than one pinned by a human reviewer in `MODULE.bazel`.

### Likelihood Explanation
This requires: (1) a module extension in the dependency graph that uses `facts` to cache checksum/URL-like metadata for otherwise-unverified downloads (an explicitly documented, encouraged pattern), and (2) the ability to modify `MODULE.bazel.lock` on a branch/PR that is built by CI without a human noticing the JSON diff in the `facts` section (which is easy to overlook compared to `MODULE.bazel` itself, and can also arrive via the lockfile git-merge-driver / `bazel-lockfile-merge.jq` tooling). Given `lockfile_mode=update` is the default and does not re-verify non-reproducible facts against a fresh evaluation, this is plausible wherever such extensions are used, though it depends on third-party extension authors adopting this specific pattern rather than being a universal Bazel-core vulnerability.

### Recommendation
- Require or default to `reproducible = True`-style verification for any extension using `facts` to store checksum/URL pairs, so that a mismatch between committed `facts` and freshly fetched data is detected (as already happens for reproducible extensions).
- Consider warning or requiring an explicit opt-in when `facts` values resemble a checksum/URL pair that bypasses a checksum-guarded fetch, since these are the values whose tampering has integrity consequences.
- Document more prominently in `bazel mod` / lockfile review tooling that `facts` entries are unauthenticated and should be reviewed with the same scrutiny as `sha256`/`integrity` attributes in `MODULE.bazel`.

### Proof of Concept
A JUnit/`BazelLockfileTest`-style reproduction, extending the existing `_addFactToLockfile` helper pattern [5](#0-4) :
1. Define a non-reproducible module extension whose implementation, on first run, "fetches" (simulated) a `{url, sha256}` pair for an artifact and stores it via `extension_metadata(facts={...})`, then uses `ctx.download(url=facts_url, sha256=facts_sha256)` on subsequent runs to skip re-fetching.
2. Run once to populate `MODULE.bazel.lock` with legitimate `facts`.
3. Simulate the attacker branch: directly edit `facts[<ext_id>]` in `MODULE.bazel.lock` to point `url`/`sha256` at attacker-controlled content, mirroring `_addFactToLockfile`.
4. Re-run `bazel build` with default `--lockfile_mode=update`: observe that the extension is not re-evaluated (inputs unchanged) and `ctx.facts` returns the tampered values, which are used directly in the (previously) checksum-guarded download step — demonstrating that `facts` tampering flows unchecked into a step meant to be integrity-protected.

Note: I could not verify the exact Java-side implementation (`LockFileModuleExtension`/`SingleExtensionEvalFunction`, `BazelLockFileFunction`) that handles `facts`/`factsVersion` validation, since no matches for these fields were found under `src/main/java/**/*.java` in the indexed content — this may be due to index size limits excluding some file contents. A Devin session with full repository access would be needed to confirm the precise validation logic (e.g., whether any additional binding between `facts` values and content hashes exists that isn't visible in the docs/tests reviewed here) before treating this as a fully confirmed vulnerability rather than a design-level integrity gap inferred from documentation and test behavior.

  def _addFactToLockfile(self, extension_id, fact_key, fact_value):
    """Adds a facts entry to the workspace lockfile."""
    # Simulates the workspace lockfile changing underneath a warm output base,
    # e.g. due to a branch switch or pull that brings in facts produced by an
    # evaluation of the extension on a different machine.
    with open(self.Path('MODULE.bazel.lock'), 'r') as f:
      lockfile = json.loads(f.read().strip())
    lockfile['facts'][extension_id][fact_key] = fact_value
    with open(self.Path('MODULE.bazel.lock'), 'w') as f:
      json.dump(lockfile, f, indent=2)

  def testDeletedFactsRegeneratedByUpdateMode(self):
    """Facts deleted from the workspace lockfile are restored by UPDATE mode.

    Regression test for https://github.com/bazelbuild/bazel/issues/29161. For a
    non-reproducible extension, the deleted facts are restored from the hidden
    lockfile's copy without rerunning the extension: its cached result is
    locked in the workspace lockfile, so a cold machine would not rerun it
    either.
    """
    extension_id = self._setUpExtensionWithFacts(reproducible=False)
    self._dropFactsFromLockfile(extension_id)

    _, _, stderr = self.RunBazel(
        ['build', '@hello//:all', '--lockfile_mode=update']
    )
    self.assertNotIn('lockfile_ext is being evaluated', '\n'.join(stderr))

    with open(self.Path('MODULE.bazel.lock'), 'r') as f:
      lockfile = json.loads(f.read().strip())
    self.assertEqual(
        lockfile['facts'][extension_id],
        {'1.25.0': {'hash': 'olleh'}, '1.26.1': {'hash': 'hello'}},
    )

  def testExternallyUpdatedFactsRegenerateReproducibleExtension(self):
    """UPDATE mode reruns a reproducible extension on changed facts.

    A reproducible extension's facts can only legitimately change together
    with its inputs, so facts that differ from the record of its most recent
    evaluation despite unchanged inputs indicate an edited workspace lockfile
    and the extension is rerun to regenerate them. This is safe: a reproducible
    extension's result is only ever cached in the machine-local hidden
    lockfile, so a cold machine would rerun it anyway.
    """
    extension_id = self._setUpExtensionWithFacts(reproducible=True)
    self._addFactToLockfile(extension_id, '1.27.0', {'hash': 'hola'})

    _, _, stderr = self.RunBazel(
        ['build', '@hello//:all', '--lockfile_mode=update']
    )
    self.assertIn('lockfile_ext is being evaluated', '\n'.join(stderr))

    with open(self.Path('MODULE.bazel.lock'), 'r') as f:
      lockfile = json.loads(f.read().strip())
    self.assertEqual(
        lockfile['facts'][extension_id],
        {'1.25.0': {'hash': 'olleh'}, '1.26.1': {'hash': 'hello'}},
    )

  def testDeletedFactsDetectedByErrorModeForReproducibleExtension(self):
    """ERROR mode reruns a reproducible extension on edited facts and fails.

    Regression test for https://github.com/bazelbuild/bazel/issues/29161
    """
    extension_id = self._setUpExtensionWithFacts(reproducible=True)
    self._dropFactsFromLockfile(extension_id, fact_key='1.25.0')

    exit_code, stdout, stderr = self.RunBazel(
        ['build', '@hello//:all', '--lockfile_mode=error'], allow_failure=True
    )
    stderr = ''.join(stderr)
    self.AssertExitCode(exit_code, 48, stderr, stdout)
    self.assertIn('has changed its facts', stderr)

def shallow_merge(f):
  map(f) | stable_unique | add | to_entries | sort_by(.key | split(":")) | from_entries;

(
    # Ignore all MODULE.bazel.lock files that do not have the maximum
    # lockFileVersion.
    (map(.lockFileVersion) | max) as $maxVersion
    | map(select(.lockFileVersion == $maxVersion))
    # Compute the maximum factsVersion observed across lockfiles per extension
    # ID. Missing entries default to 0.
    | (
        map(.factsVersions // {} | to_entries) | flatten
        | if length > 0 then
            group_by(.key)
            | map({key: .[0].key, value: (map(.value) | max)})
            | from_entries
          else {} end
      ) as $maxFactsVersions
    # Within each lockfile, drop facts entries whose own factsVersion does not
    # match the global maximum: those are at an outdated schema and cannot be
    # merged with newer-schema entries.
    | map(
        if has("facts") then
          (.factsVersions // {}) as $fv
          | .facts |= with_entries(
              .key as $k
              | select((($fv[$k]) // 0) == (($maxFactsVersions[$k]) // 0))
            )
        else . end
      )
    | {
        lockFileVersion: $maxVersion,
        registryFileHashes: shallow_merge(.registryFileHashes),
        selectedYankedVersions: shallow_merge(.selectedYankedVersions),
        # Group extension results by extension ID across all lockfiles with
        # shallowly merged factors map, then shallowly merge the results.
        moduleExtensions:  (map(.moduleExtensions | to_entries)
                           | flatten
                           | if length > 0 then group_by(.key) | shallow_merge({(.[0].key): shallow_merge(.value)}) else {} end),
        # Group facts by extension ID across all lockfiles (already filtered to
        # the latest factsVersion above) and shallowly merge their dicts.
        facts: (if any(has("facts")) then
                  map(.facts // {} | to_entries) | flatten |
                  if length > 0 then group_by(.key) | shallow_merge({(.[0].key): shallow_merge(.value)}) else {} end

# When two lockfiles have facts at different schema versions (tracked in the
# parallel factsVersions map), only the entries at the highest version survive
# for each extension: facts at a lower version would be misinterpreted under
# the new schema.
function test_merge_facts_with_mismatched_versions() {
  cat > base <<'EOF'
{
  "lockFileVersion": 28,
  "registryFileHashes": {},
  "selectedYankedVersions": {},
  "moduleExtensions": {}
}
EOF
  cat > left <<'EOF'
{
  "lockFileVersion": 28,
  "registryFileHashes": {},
  "selectedYankedVersions": {},
  "moduleExtensions": {},
  "facts": {
    "@@rules_foo+//:foo_deps.bzl%foo_deps": {
      "old_key": "old_value"
    }
  },
  "factsVersions": {
    "@@rules_foo+//:foo_deps.bzl%foo_deps": 1
  }
}
EOF
  cat > right <<'EOF'
{
  "lockFileVersion": 28,
  "registryFileHashes": {},
  "selectedYankedVersions": {},
  "moduleExtensions": {},
  "facts": {
    "@@rules_foo+//:foo_deps.bzl%foo_deps": {
      "new_key": "new_value"
    }
  },
  "factsVersions": {
    "@@rules_foo+//:foo_deps.bzl%foo_deps": 2
  }
}
EOF
  cat > expected <<'EOF'
{
  "lockFileVersion": 28,
  "registryFileHashes": {},
  "selectedYankedVersions": {},
  "moduleExtensions": {},
  "facts": {
    "@@rules_foo+//:foo_deps.bzl%foo_deps": {
      "new_key": "new_value"
    }
  },
  "factsVersions": {
    "@@rules_foo+//:foo_deps.bzl%foo_deps": 2
  }
}
EOF

  do_merge base left right
  diff -u expected left || fail "output differs"
}

## Best Practices {#best-practices}

To maximize the benefits of the lockfile feature, consider the following best
practices:

*   Regularly update the lockfile to reflect changes in project dependencies or
    configuration. This ensures that subsequent builds are based on the most
    up-to-date and accurate set of dependencies. To lock down all extensions
    at once, run `bazel mod deps --lockfile_mode=update`.

*   Include the lockfile in version control to facilitate collaboration and
    ensure that all team members have access to the same lockfile, promoting
    consistent development environments across the project.

*   Use [`bazelisk`](/install/bazelisk) to run Bazel, and include a
    `.bazelversion` file in version control that specifies the Bazel version
    corresponding to the lockfile. Because Bazel itself is a dependency of
    your build, the lockfile is specific to the Bazel version, and will
    change even between [backwards compatible](/release/backward-compatibility)
    Bazel releases. Using `bazelisk` ensures that all developers are using
    a Bazel version that matches the lockfile.
