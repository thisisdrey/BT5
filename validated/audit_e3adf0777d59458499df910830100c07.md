No vulnerability found for this question.

**Reasoning:** The premise conflates two unrelated metering dimensions. `main_storage_proof_size_soft_limit` throttles chunk processing based on the size of the **trie/storage proof** recorded by `TrieRecorder` during receipt execution — i.e., actual trie node reads/writes tracked via `TrieRecorder::record`/`record_key_removal`/`record_code_len` and checked via `check_proof_size_limit_exceed()`. [1](#0-0) 

This is checked per-chunk in `process_receipts`, which increments `CHUNK_RECEIPTS_LIMITED_BY` with `storage_proof_size_limit` only when `state_update.trie.check_proof_size_limit_exceed()` is true. [2](#0-1) 

`bls12381_g1_multiexp` (via `g1_multiexp`/`blst_p1_mult`) is a pure host-function computation over WASM guest memory and register output; it does not perform any trie/storage reads or writes. Its cost model (`bls12381_g1_multiexp_base + bls12381_g1_multiexp_element * num_elements`, plus register write costs) is entirely a **gas/compute** cost, unrelated to storage proof accounting. [3](#0-2) 

Since the function contributes zero bytes to the trie storage proof regardless of its input size, output size, or gas cost, there is no mechanism by which its "gas-to-output-size asymmetry" could cause storage-proof-soft-limit bypass — the two costs (compute gas vs. storage proof bytes) are tracked independently, and `check_proof_size_limit_exceed` is wired only to trie recording, not to VM logic gas costs or register/output sizes. The existing test `test_main_storage_proof_size_soft_limit` and `test_storage_proof_size_limit` integration test confirm the throttling is driven by actual storage reads, not by compute-heavy or output-size-mismatched host calls. [4](#0-3) [5](#0-4) 

Additionally, view calls never produce receipts (they are stateless RPC queries with no chunk/witness involvement), so "submitting a view call and then separately as a receipt" doesn't compound any effect — each receipt is independently gas-metered and storage-proof-accounted, with no cross-call amortization that would let compute-heavy/storage-light calls escape the soft limit differently than any other function call. There is no reachable path by which this creates a concrete freezing/loss-of-funds, consensus divergence, or shard-halting impact.
