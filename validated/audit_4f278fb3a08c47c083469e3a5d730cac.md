### Title
Attacker can brick `withdraw`/`liquidate` by filling `feeCollector`'s token list to `MAX_TOKENS_PER_USER`, causing a revert inside `seize`/`_transfer` — (File: contracts/Pool.sol / contracts/DepositToken.sol)

### Summary
The reported bug class is: *a revert in a code path that must not revert bricks a core operation (position stuck / funds frozen), because the code assumes an invariant — "a recipient can always accept the token" — that does not hold.* The same class exists in Metronome: every deposit-token transfer that creates a new balance for the recipient calls `Pool.addToDepositTokensOfAccount`, which reverts with `UserReachedMaxTokens` once the recipient's combined deposit+debt token list reaches `MAX_TOKENS_PER_USER`. Because `DepositToken._withdraw` sends the withdrawal fee to the fixed `feeCollector` address, and `Pool.liquidate` seizes the protocol fee to the same `feeCollector`, an unprivileged attacker can grief the protocol by dust-filling `feeCollector`'s token list, making all future fee-bearing withdrawals and liquidations revert.

### Finding Description

`Pool` enforces a per-account cap on the number of tracked tokens:

```solidity
// contracts/Pool.sol
modifier onlyIfAdditionWillNotReachMaxTokens(address account_) {
    if (debtTokensOfAccount.length(account_) + depositTokensOfAccount.length(account_) >= MAX_TOKENS_PER_USER) {
        revert UserReachedMaxTokens();
    }
    _;
}

function addToDepositTokensOfAccount(address account_) external onlyIfAdditionWillNotReachMaxTokens(account_) { ... }
```

Every `DepositToken._transfer` that gives a recipient its first balance of that token pushes it into the recipient's list:

```solidity
// contracts/DepositToken.sol ~L517-520
if (_recipientBalanceBefore == 0 && amount_ > 0) {
    pool.addToDepositTokensOfAccount(recipient_);
}
```

Critically, both fee-charging paths send tokens to the *fixed* `feeCollector` address:

- `DepositToken._withdraw`: `if (_fee > 0) { _transfer(account_, _pool.feeCollector(), _fee); }` (~L546-548)
- `Pool.liquidate`: `depositToken_.seize(account_, _poolRegistry.feeCollector(), _fee);` (L591-593)

Attack path (unprivileged, no privileged role needed):
1. Attacker deposits dust of each deposit token into the pool (or transfers existing `msdX`), then calls `depositToken.transfer(feeCollector, 1)` for `MAX_TOKENS_PER_USER` distinct deposit tokens. Each dust transfer adds a new entry to `feeCollector`'s list via `addToDepositTokensOfAccount`. Once the list is full, the cap check reverts for any *further new* token.
2. From then on, for any deposit token `feeCollector` does not yet hold:
   - `DepositToken.withdraw(...)` reverts inside `_transfer` when paying `_fee`, so users cannot withdraw that collateral at all.
   - `Pool.liquidate(...)` reverts inside `seize` when paying `_fee`, so no liquidator can liquidate positions collateralized by that token.

This is structurally identical to the Notional finding: an unconditional `require`/`revert` (`require(hasRequest)` there, `UserReachedMaxTokens` here) sits inside a function that every critical operation depends on, and the broken invariant ("the fee recipient can always accept one more token") is attacker-breakable. ### Impact Explanation
- **Freezing of user funds**: any user holding a deposit token absent from `feeCollector`'s (now-full) list cannot withdraw while `withdrawFee > 0`.
- **Liquidation DoS → protocol insolvency**: unhealthy positions backed by such tokens cannot be liquidated while `protocolLiquidationFee > 0`, so bad debt accrues — liveness/liquidation-bounds invariant broken.
- A slot only frees if `feeCollector`'s balance of some token goes fully to zero, so the DoS is long-lived/possibly indefinite.

### Likelihood Explanation
Requires (a) the pool to list more deposit tokens than `MAX_TOKENS_PER_USER` slots the `feeCollector` still has free, and (b) nonzero withdraw/liquidation fees. The attack costs only dust deposits and gas; no privileged action, oracle manipulation, or governance involvement is needed. (I could not verify the exact `MAX_TOKENS_PER_USER` value or the body of `seize` within the available context — `seize` presumably routes through `_transfer`/`_mint`-style accounting that calls `addToDepositTokensOfAccount`, which the grep results for `DepositToken.sol` are consistent with; this should be confirmed in a session.)

### Recommendation
- Exempt `feeCollector` (or fee transfers) from the per-account token-list bookkeeping, or treat fee accrual via a separate accounting variable instead of a real transfer.
- Alternatively, in `addToDepositTokensOfAccount`, silently skip adding (rather than reverting) when the recipient is a protocol address at capacity — the list is used for `depositOf`/health computation, which is meaningless for `feeCollector` anyway.
- More generally, fee-paying transfers should never revert on recipient-side bookkeeping.

### Proof of Concept
Foundry sketch (to be run against a deployment where the pool has > `MAX_TOKENS_PER_USER` deposit tokens, or a test with several tokens):

```solidity
// attacker fills feeCollector's list
address feeCollector = poolRegistry.feeCollector();
uint256 max = pool.MAX_TOKENS_PER_USER();
for (uint256 i; i < max; ++i) {
    IDepositToken dt = IDepositToken(pool.depositTokens().at(i)); // distinct tokens
    deal(address(dt), attacker, 1);                                // or deposit dust
    dt.transfer(feeCollector, 1);                                  // adds to feeCollector list
}
// now liquidating an account whose collateral token feeCollector lacks:
vm.expectRevert(Pool.UserReachedMaxTokens.selector);
pool.liquidate(msEth, victim, amountToRepay, newDepositToken);     // reverts in seize -> _transfer

// and withdrawals of that token revert too:
vm.expectRevert(Pool.UserReachedMaxTokens.selector);
newDepositToken.withdraw(victimAmount);
```

Note: the same `UserReachedMaxTokens` revert via dust transfers to a *victim* (blocking them from receiving new collateral types) is a related but weaker variant; the `feeCollector` path is the strongest analog because it reverts inside a system-critical operation for all users.
