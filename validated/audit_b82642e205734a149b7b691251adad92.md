### Title
Heap buffer over-read parsing attacker-supplied Zip64 extra fields in central directory - ([File: third_party/ijar/zip.cc])

### Summary
`InputZipFile::ProcessCentralDirEntry` in `third_party/ijar/zip.cc` decodes central-directory-record length fields and Zip64 extra-field data taken directly from an untrusted jar/zip file, and advances read pointers and dereferences memory based on those attacker-controlled lengths without any bounds check against the actual mapped file size.

### Finding Description
`ProcessCentralDirEntry` reads `file_name_length`, `extra_field_length`, and `file_comment_length` as raw `u2` values from the central directory record and immediately advances the cursor `p` by these amounts with no validation that the mapped input buffer actually contains that many bytes: [1](#0-0) 

It then walks the "extra field" bytes in a loop, reading a 2-byte `header_id` and 2-byte `data_size` per record and, when `header_id == ZIP64_EXTRA_FIELD_TAG`, unconditionally calls `get_u8le(extra)` up to three times to read 8-byte fields from `extra` — without ever checking that `data_size >= 8` or that `extra + 8` stays inside the extra-field region or the mapped file: [2](#0-1) 

This is the same bug class as the HDF5 `H5F_addr_decode_len` issue: a length/size field decoded from untrusted input is trusted to determine how many further bytes to read, with no check that those bytes actually exist in the buffer, producing a heap/mmap buffer over-read.

Contrast this with `ProcessLocalFileEntry`, in the same file, which explicitly calls `EnsureRemaining()` before trusting `file_name_length_`/`extra_field_length_` to advance `p`: [3](#0-2) 
and with `EnsureRemaining` itself, which is the only bounds-check primitive defined in this class: [4](#0-3) 

`ProcessCentralDirEntry` never calls `EnsureRemaining`. Its governing comment asserts safety on the theory that "the central directory is always followed by another data structure that has a signature", but that assumption only bounds the *outer* central-directory-record walk (`ProcessNext`/`CalculateOutputLength` loop) — it says nothing about the *inner* extra-field loop, where `data_size` is a fully attacker-controlled 16-bit value read from inside the record and used to jump `extra_p` forward, and `get_u8le(extra)` reads 8 bytes from `extra` regardless of whether `data_size` was actually ≥ 8 or whether the extra field region itself was truncated by a crafted `extra_field_length`.

By contrast, Bazel's other in-tree zip parser, `singlejar`'s `zip_headers.h`/`ExtraField::find`, explicitly bounds-checks each extra field against the declared region and calls `diag_errx` on malformed data (proven by the `MalformedExtraField` death test), showing the project is aware of and mitigates this exact class of bug elsewhere — but not in `third_party/ijar/zip.cc`: [5](#0-4) [6](#0-5) 

### Impact Explanation
`ijar` is a core Bazel toolchain binary invoked during ordinary Java builds to generate interface jars from arbitrary input jars, including third-party jars fetched from Maven/http_jar with a pinned sha256. A sha256/integrity check only guarantees the bytes match what the attacker chose to publish — it does not validate internal Zip structural sanity. An attacker who controls the content served at a dependency URL (and whose hash is what gets pinned, e.g. on first fetch, in a lockfile update, or via a malicious registry entry) can craft a jar whose central directory contains a Zip64 extra field with `data_size` smaller than 8 (or `extra_field_length`/`file_name_length` values that run past the end of the mapped file), causing `get_u8le`/pointer arithmetic in `ProcessCentralDirEntry` to read outside the mmap'd input file. This is a memory-safety violation (heap/mmap buffer over-read) in a Bazel-shipped native tool triggered purely by untrusted, integrity-pinned build input content — matching CWE-125 out-of-bounds read, the same class as the cited HDF5 CVE.

### Likelihood Explanation
High for triggering the over-read (any build that runs `ijar` over a crafted jar reaches this code unconditionally; no opt-in flag is required since ijar interface-jar generation is a standard part of the Java build action graph), though the practical consequence is bounded by the fact that the read happens inside a `mmap`'d region, whose over-read may land in adjacent mapped pages (leaking or crashing) rather than reliably corrupting control flow.

### Recommendation
Add bounds checking in `ProcessCentralDirEntry` analogous to `EnsureRemaining`/`ExtraField::find`: validate `file_name_length`, `extra_field_length`, and `file_comment_length` against the remaining bytes in the central directory buffer before advancing `p`, and validate `data_size` (and that `data_size >= 8` where 8-byte Zip64 fields are read) against the bounds of the extra-field region before calling `get_u8le`/`get_u4le` on `extra`. On violation, fail with a diagnostic (as `singlejar` does via `diag_errx`) instead of reading past the buffer.

### Proof of Concept
A reproducible test can be added under `third_party/ijar/test/` (paralleling the pattern in `src/tools/singlejar/output_jar_simple_test.cc`'s `MalformedExtraField`/`CreateZipWithMalformedExtraField`): construct a minimal zip file whose Central Directory Header declares `uncompressed_size32 = 0xFFFFFFFF` (marking Zip64) and an extra field with `header_id = 0x0001` (`ZIP64_EXTRA_FIELD_TAG`) and `data_size` set to `0` or `1` (less than the 8 bytes required), positioned so the extra field ends at (or the declared `extra_field_length` exceeds) the true end of the mmap'd input buffer; then invoke `ijar`/`InputZipFile::ProcessNext()` (or `CalculateOutputLength()`) on that file and run under ASan to observe the heap/mmap-buffer-overflow-read triggered by `get_u8le(extra)` in `third_party/ijar/zip.cc:533-539`.

class ExtraField {
 public:
  static const ExtraField* find(uint16_t tag, const uint8_t* start,
                                const uint8_t* end) {
    while (start < end) {
      if (ziph::byte_ptr(start) + sizeof(ExtraField) > ziph::byte_ptr(end)) {
        break;
      }
      auto extra_field = reinterpret_cast<const ExtraField*>(start);
      if (ziph::byte_ptr(start) + extra_field->size() > ziph::byte_ptr(end)) {
        break;
      }
      if (extra_field->is(tag)) {
        return extra_field;
      }
      start = ziph::byte_ptr(start) + extra_field->size();
    }
    return nullptr;
  }
