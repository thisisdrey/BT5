### Title
Slow-client lock starvation via unbounded `stream.Recv()` in `SetCustomHooks`/`RestoreCustomHooks` blocking hook updates - ([File: internal/gitaly/repoutil/custom_hooks.go])

### Summary
`SetCustomHooks`/`RestoreCustomHooks` acquire an exclusive `hooksLock` on the repository's `custom_hooks` directory *before* the tar payload is fully read from the client stream, and the payload read (`ExtractHooks`, driven by `streamio.NewReader`'s closure calling `stream.Recv()`) has no independent deadline. A client that sends the first request and then stalls or trickles data can hold the lock for the life of the gRPC stream, blocking any other `SetCustomHooks`/`RestoreCustomHooks` call for the same repository.

### Finding Description
In `internal/gitaly/service/repository/set_custom_hooks.go`, `SetCustomHooks` receives the first request, validates the repository, then builds a `streamio.NewReader` whose read function calls `stream.Recv()` on demand [1](#0-0) . This reader is passed into `repoutil.SetCustomHooks`, which acquires `hooksLock.Lock()` on `<repoPath>/custom_hooks` *before* calling `ExtractHooks(ctx, logger, reader, tmpDir.Path(), false)`, which is the point at which the client-driven `stream.Recv()` loop actually consumes data [2](#0-1) . `ExtractHooks` pipes the reader directly as stdin to a spawned `tar` subprocess and blocks on `cmd.Wait()`, so as long as the client trickles or withholds bytes, the goroutine sits inside `stream.Recv()`/`tar` while holding the directory lock [3](#0-2) .

The server-side gRPC configuration only sets `KeepaliveEnforcementPolicy`/`KeepaliveParams` (`Time: 5m`), which governs HTTP/2 PING keepalives, not idle/read timeouts for stalled application-level stream data; there is no `MaxConnectionIdle`, `Timeout` on `KeepaliveParams`, or an explicit gRPC deadline enforced independent of the client's own context [4](#0-3) . HTTP/2 keepalive PING/PONG is handled transparently by the transport and doesn't require the application to send any data, so a client that responds to transport-level pings but never sends further `DATA` frames for the RPC message stream can keep the call open indefinitely without the server enforcing any timeout tied to the RPC's own deadline. The `hooksLock` is released only in a deferred `Unlock()` after `SetCustomHooks` returns, so the lock is held for the entire duration of the stalled `Recv()`/`tar` operation [5](#0-4) .

### Impact Explanation
While the held lock is scoped to a single repository's `custom_hooks` directory, it blocks all subsequent `SetCustomHooks`/`RestoreCustomHooks` calls for that same repository (e.g., legitimate hook restores/updates triggered by GitLab Rails during imports, project transfers, or hook management) for as long as the attacker keeps the stream open. This matches a scoped "denial of service of an RPC handler" impact class — it is not a full-server DoS, but a repo-scoped resource/lock starvation that a single unprivileged client can trigger and sustain.

### Likelihood Explanation
Whether this is exploitable by a fully unprivileged, external user depends on whether `SetCustomHooks`/`RestoreCustomHooks` are reachable through a path an ordinary GitLab user controls (e.g., via project import/fork flows that invoke custom hook restoration) versus being an operator/admin-only or internal-only RPC invoked exclusively by trusted GitLab Rails/Gitaly-internal code paths. I could not fully confirm from the available proto/ACL annotations in this index whether these RPCs are exposed to unprivileged users or are restricted to administrative/internal callers; the proto file shows the RPC definitions but not a clear ACL scope in what I retrieved. If it is only reachable by GitLab Rails on behalf of the system (not directly attacker-controlled per the "unprivileged user" threat model), the described precondition ("attacker opens a SetCustomHooksServer stream") may not be satisfiable from an unprivileged user's normal capabilities (push/fetch/fork/import), which would make this **out of scope** for the given attacker model.

### Recommendation
- Enforce a bounded read/idle timeout on the streaming payload independent of the client's keepalive behavior, e.g., wrap the `stream.Context()` with a `context.WithTimeout` for hook extraction, or use `grpc.KeepaliveParams{Timeout: ...}` combined with periodic reads that fail fast if no data arrives within a bounded window.
- Acquire `hooksLock` only after the tar payload has been fully buffered/received (or use a read timeout on the underlying `io.Reader` passed to `ExtractHooks`) so an idle/stalled client cannot hold the lock indefinitely.
- Add a maximum RPC duration enforced server-side (e.g., via a deadline-setting interceptor) for `SetCustomHooks`/`RestoreCustomHooks` so no single stream can hold the lock beyond a bounded period.

### Proof of Concept
Because I could not confirm from the indexed code whether this RPC is reachable by an unprivileged GitLab user (versus being an internal/administrative-only call), I cannot fully validate the "Preconditions: attacker can open a long-lived...gRPC call" as satisfying the stated unprivileged-attacker threat model. A concrete Go test would:
1. Start a `SetCustomHooksServer` stream, send the first request with a valid `Repository`.
2. Send zero or partial `DATA` chunks and pause indefinitely (or for a long duration) without closing the stream.
3. Concurrently issue a second `SetCustomHooks`/`RestoreCustomHooks` call for the same repository and assert it either succeeds within a bounded time or fails with `DeadlineExceeded` rather than blocking indefinitely — the current code would keep this second call blocked on `hooksLock.Lock()` for as long as the first stream is stalled, since `internal/gitaly/repoutil/custom_hooks.go` has no lock-acquisition timeout [6](#0-5) .

Given the uncertainty about attacker reachability/privilege for this specific RPC, and that I was unable to verify the ACL/exposure of `SetCustomHooks`/`RestoreCustomHooks` to fully unprivileged users within the available index, I flag this finding with **reduced confidence** rather than asserting definitive exploitability under the stated unprivileged-attacker constraints.

func ExtractHooks(ctx context.Context, logger log.Logger, reader io.Reader, path string, stripPrefix bool) error {
	// GNU tar does not accept an empty file as a valid tar archive and produces
	// an error. Since an empty hooks tar is symbolic of a repository having no
	// hooks, the reader is peeked to check if there is any data present.
	buf := bufio.NewReader(reader)
	if _, err := buf.Peek(1); errors.Is(err, io.EOF) {
		return nil
	}

	stripComponents := "0"
	if stripPrefix {
		stripComponents = "1"
	}

	cmdArgs := []string{"-xf", "-", "-C", path, "--strip-components", stripComponents, CustomHooksDir}

	var stderrBuilder strings.Builder
	cmd, err := command.New(ctx, logger, append([]string{"tar"}, cmdArgs...),
		command.WithStdin(buf),
		command.WithStderr(&stderrBuilder))
	if err != nil {
		return fmt.Errorf("executing tar command: %w", err)
	}

	if err := cmd.Wait(); err != nil {
		stderr := stderrBuilder.String()

		// GNU and BSD tar versions have differing errors when attempting to
		// extract specified members from a valid tar archive. If the tar
		// archive is valid the errors for GNU and BSD tar should have the
		// same prefix, which can be checked to validate whether the expected
		// content is present in the archive for extraction.
		if strings.HasPrefix(stderr, "tar: custom_hooks: Not found in archive") {
			return nil
		}

		return structerr.New("waiting for tar command completion: %w", err).WithMetadata("stderr", stderr)
	}

	return nil
