### Title
Stale `PromiseYieldReceipt`/`PromiseYieldStatus` entries survive `DeleteAccount`, letting an old account's yield-callback actions execute against a recreated account of the same name - (File: core/store/src/utils/mod.rs)

### Summary
`remove_account` only purges the `Account`, `ContractCode`, `AccessKey`/gas-key, and `ContractData` trie entries for a deleted account, but never removes `PromiseYieldReceipt`, `PromiseYieldStatus`, `YieldIdToDataId`, or `DataIdToYieldId` rows, even though these are explicitly listed as account-scoped columns (`COLUMNS_WITH_ACCOUNT_ID_IN_KEY`). A pending yield's `PromiseYieldTimeout` queue entry (which is *not* account-scoped by key) survives independently and, on expiry, is delivered to whatever account currently owns that name - including a brand-new account created after the original was deleted.

### Finding Description
`remove_account` (`core/store/src/utils/mod.rs:504-575`) removes exactly four categories of state for `account_id`: `Account`, `ContractCode`, access/gas keys (lines 515-553), and `ContractData` (lines 555-573). [1](#0-0) 

However, the `col` module documents that `PROMISE_YIELD_RECEIPT`, `PROMISE_YIELD_STATUS`, `YIELD_ID_TO_DATA_ID`, and `DATA_ID_TO_YIELD_ID` are all account-scoped columns (they key on `receiver_id`/`account_id`), grouped in `COLUMNS_WITH_ACCOUNT_ID_IN_KEY`: [2](#0-1) 

None of these four columns are touched by `remove_account`, so a pending yield (stored by `set_promise_yield_receipt`, keyed `TrieKey::PromiseYieldReceipt { receiver_id, data_id }`) is left in the trie after `DeleteAccount` executes on the account. Meanwhile the corresponding timeout entry lives in a separate, non-account-scoped structure - `TrieKey::PromiseYieldTimeout { index }` - which only carries `account_id` inside its value, not its key: [3](#0-2) 

When the queue is drained in `resolve_promise_yield_timeouts`, the runtime only checks whether the `expires_at` height has passed and whether a `PromiseYieldReceipt` still exists at `(queue_entry.account_id, queue_entry.data_id)` - it does not verify that this is the *same* account instance that created the yield: [4](#0-3) 

If found, it synthesizes a `PromiseResume` receipt destined for `queue_entry.account_id` and forwards it: [5](#0-4) 

On delivery, the `PromiseResume` handler fetches the stale `PromiseYieldReceipt` via `get_promise_yield_receipt(state_update, account_id, data_id)` and unconditionally executes it with `apply_action_receipt` against the account's *current* trie state: [6](#0-5) 

Exploit flow:
1. Attacker controls account `A`, deploys a contract, and calls a method that invokes `promise_yield_create`, producing an attacker-chosen action list (predecessor = receiver = `A`, so it is a self-authorized receipt requiring no separate permission check) to run as the yield callback. This is stored via `set_promise_yield_receipt`, and a `PromiseYieldTimeout{account_id: A, data_id, expires_at}` is enqueued via `enqueue_promise_yield_timeout` (`runtime/runtime/src/function_call.rs:160-169`).
2. Attacker submits `DeleteAccount(A)`, invoking `action_delete_account` → `remove_account`, which deletes the `Account`/keys/code/data rows but leaves the `PromiseYieldReceipt`/`PromiseYieldStatus` rows and the independent `PromiseYieldTimeout` queue entry intact.
3. Some third party (the "new owner") later submits `CreateAccount(A)`, funds it, and deploys their own contract - `action_create_account` never inspects or clears residual trie rows outside the ones it directly writes.
4. Once `expires_at` block height passes, `resolve_promise_yield_timeouts` finds the stale `PromiseYieldReceipt` still present (never cleaned up) and emits/forwards a `PromiseResume` receipt to `A`.
5. The `PromiseResume` handler at `runtime/runtime/src/lib.rs:1511-1562` finds the yield receipt and executes it against the new `A`'s account/contract/balance, using an action list the new owner never approved and that was authorized purely by the attacker's earlier self-call.

None of the existing checks (signature/nonce verification, access-key permission, `check_actor_permissions`) apply here because this is an internally generated system receipt (`PromiseResume`/the parked `PromiseYieldReceipt` itself), not a directly signed transaction, and the runtime treats "receiver_id matches" as sufficient without any check that the account identity/state generation matches the one that created the yield.

### Impact Explanation
This is an authorization-escalation bug across accounts: an action list authored and authorized under the *old* account `A`'s context (chosen entirely by the attacker who deleted `A`) executes against the *new* `A`'s state/balance/contract after recreation, without the new owner's consent. Depending on what actions the attacker embeds in the yield callback (e.g., `FunctionCall` on itself, `Transfer`, `DeleteKey`, `DeployContract` etc., all self-authorized because predecessor==receiver==A), this can mutate or drain the new account's state/balance - matching the "authorization escalation across accounts or promises" and potential "theft or freezing of user funds" bounty categories.

### Likelihood Explanation
Preconditions are fully within an unprivileged attacker's control: creating an account, deploying a contract that calls `promise_yield_create`, then deleting the account are ordinary, low-cost transactions. The main uncertainty is timing/coordination - the attacker needs the account name to be reused by someone else (or reuses it themselves) before the timeout height is reached; `yield_timeout_length_in_blocks` is a bounded, known runtime config value, and the attacker fully controls when `DeleteAccount` is submitted relative to `promise_yield_create`, so they can set up the timing precisely. This is repeatable (each attempt costs only standard account-creation/deletion/contract-call gas).

### Recommendation
`remove_account` (`core/store/src/utils/mod.rs`) should also iterate and remove all `PromiseYieldReceipt`, `PromiseYieldStatus`, `YieldIdToDataId`, and `DataIdToYieldId` rows scoped to the deleted `account_id` (consistent with the `COLUMNS_WITH_ACCOUNT_ID_IN_KEY` list), and/or `resolve_promise_yield_timeouts` should validate that the resolved `PromiseYieldReceipt` genuinely corresponds to the account instance that created it (e.g., invalidate/skip timeout entries whose account no longer exists or has been recreated) before synthesizing/executing a `PromiseResume`.

### Proof of Concept
Test-loop integration test plan (mirroring existing tests in `test-loop-tests/src/tests/yield_timeouts.rs`):
1. Deploy a yield-capable test contract to account `A`; call a method invoking `promise_yield_create` with a distinctive, attacker-chosen callback action (e.g., a self `FunctionCall` that writes a sentinel value or transfers balance) and record `data_id`/`yield_timeout_height`.
2. Before the timeout height, submit `DeleteAccount(A)`.
3. Submit `CreateAccount(A)` (simulating a new owner) with a fresh contract/state, and fund it.
4. Advance the chain to `yield_timeout_height`.
5. Assert that a `PromiseResume` receipt targeting `A` is produced and that, once applied, the attacker's original callback action executes against the *new* `A` (e.g., the sentinel value appears in the new account's state, or its balance changes) - proving action execution across the account-recreation boundary without the new owner's authorization. Also assert that `state_update.contains_key(TrieKey::PromiseYieldReceipt{...})` is `true` immediately after `DeleteAccount`, demonstrating the leaked row.
