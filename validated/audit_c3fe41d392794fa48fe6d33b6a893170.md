## Finding: Token-Name Front-Running in `AssetIssueActuator` Permanently Squats Desired Asset Names

### Title
Front-Running of Asset Name Reservation in `AssetIssueActuator.validate()`/`execute()` — ([File: actuator/src/main/java/org/tron/core/actuator/AssetIssueActuator.java])

### Summary
`AssetIssueActuator` lets any account broadcast an `AssetIssueContract` to claim a globally-unique token `name` as a permanent identifier, exactly analogous to `enrollCourier()`'s `courierId` claim in the external report. When same-token-name mode is disabled, the actuator rejects any request whose `name` already exists in the `AssetIssueStore`, and once claimed the name can never be reused. An attacker who observes a pending `AssetIssueContract` transaction in the mempool can front-run it with an identical `name` and higher fee/priority, causing the legitimate issuer's transaction to fail permanently with "Token exists," permanently denying them their intended token identity.

### Finding Description
In `validate()`, the sole gate against reuse of a `name` is a lookup keyed by the caller-chosen `name` field: [1](#0-0) 

There is no reservation, commit-reveal, or address-binding mechanism preventing a third party from submitting the exact same `name` in their own `AssetIssueContract` transaction. In `execute()`, the first transaction to be included in a block persists that `name` permanently into `assetIssueStore`, keyed by the name itself: [2](#0-1) 

Because `name` is fully attacker-controlled and requires no prior relationship to the true issuer, an attacker monitoring the transaction pool for a target's `AssetIssueContract` can copy the `name` field, sign their own `AssetIssueContract` with a competitive fee/energy bid, and get it packed into an earlier position within the same or an earlier block. The victim's original transaction then fails validation with `"Token exists"` since the check at line 210-214 executes against actuator state that has already been mutated by the attacker's transaction. This is architecturally identical to the reported `enrollCourier()` bug: a "first writer wins" unique key derived directly from user input, with no anti-squatting protection, fee scaling, or off-chain reservation step.

### Impact Explanation
The affected asset name is permanently and irrevocably consumed once written, since the actuator's execute path treats `assetIssueStore.get(name)` as authoritative and does not allow re-issuing or overwriting an existing name. This causes:
- Denial of Service against the legitimate issuer's specific business intent (they can never issue their intended token name again).
- Loss of any pre-arranged value tied to that specific token identity (partners, exchange listings, or off-chain commitments referencing a specific asset name), mirroring the "Loss of Incentives" impact accepted as Medium in the original report.
- The account also permanently loses its asset-issuance fee (`getAssetIssueFee()`) is deducted only on success, but wasted transaction fees/energy are still consumed attempting the failed transaction, and — more importantly — the account's one-time issuance slot logic (`accountCapsule.getAssetIssuedName().isEmpty()` check) is untouched by the failed attempt, so the direct financial loss is fee/gas plus opportunity loss of the specific name, not fund theft.

### Likelihood Explanation
Any unprivileged account holder with a funded address and the asset-issue fee can execute this attack merely by observing pending transactions and resubmitting with an identical `name` field and higher energy/fee priority — no special privileges, witness/SR role, or protocol-level access is required. The attack is cheap and repeatable against any desired token name.

### Recommendation
Do not let a raw user-supplied `name` act as the sole collision key for an irrevocable state mutation. Options:
- Bind the reservation to `(ownerAddress, name)` with a delayed-reveal/commit scheme so front-runners cannot copy an observed name before the true issuer's commitment is finalized.
- Allow the true owner to reclaim/override a squatted name via a signed pre-commitment (e.g., hash-committed name commitment transaction followed by a reveal), similar to ENS-style commit/reveal.
- Alternatively, since `getAllowSameTokenName() == 0` is a legacy mode already superseded by the `id`-based V2 asset store (auto-incremented `tokenIdNum`, not user-chosen), consider fully retiring the name-keyed `AssetIssueStore` collision path.

### Proof of Concept
1. Victim signs and broadcasts `AssetIssueContract` with `name = "MYTOKEN"`, `ownerAddress = V`.
2. Attacker observes this transaction in the mempool, immediately constructs and signs an `AssetIssueContract` with the same `name = "MYTOKEN"`, `ownerAddress = A`, and a higher energy/fee bid.
3. The attacker's transaction is packed first (same block or earlier block); `AssetIssueActuator.execute()` writes `assetIssueStore.put(nameKey, ...)` for `A`, per [2](#0-1) .
4. Victim's transaction is then processed; `validate()` finds `assetIssueStore.get("MYTOKEN") != null` and throws `"Token exists"`, per [1](#0-0) , confirmed by the existing regression test asserting this exact failure mode: [3](#0-2) .
5. `"MYTOKEN"` is now permanently owned by attacker `A`; victim `V` can never issue that name again.
