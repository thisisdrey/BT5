### Title
StackerDB chunk signature omits contract identity, enabling cross-lane replay of signer writes - (File: libstackerdb/src/libstackerdb.rs)

### Summary
`SlotMetadata::sign`/`verify` bind a chunk write only to `(slot_id, slot_version, data_hash)`, never to the StackerDB smart-contract identity. Because the same signer key controls the identical `slot_id` across multiple sibling `signers-{set}-{message_id}` contracts, a signature and chunk legitimately produced for one lane's StackerDB can be resubmitted verbatim as a write to a different lane's StackerDB, as long as the target lane's version/size checks and payload-type filter happen to accept it.

### Finding Description
`StackerDBChunkData::sign`/`verify` and `SlotMetadata::auth_digest` compute the signed digest from `slot_id`, `slot_version`, and `data_hash` only [5](#0-4) . The node-side write path (`PeerNetwork::validate_received_chunk` and `StackerDBTx::try_replace_chunk`) authorizes the write purely by looking up the *local, target* contract's registered slot owner via `get_slot_signer(smart_contract_id, slot_id)` and checking `slot_metadata.verify(&addr)` [6](#0-5) . The HTTP POST endpoint (`RPCPostStackerDBChunkRequestHandler`) accepts a `contract_identifier` from the request path and an independently-supplied `StackerDBChunkData` body, then calls `try_replace_chunk` against whatever contract the URL names [7](#0-6) .

Because sibling `signers-N-1`, `signers-N-2`, `signers-N-3` contracts for the same reward cycle assign identical `(slot_id → signer address)` mappings (all derived from the same `.signers` state) [2](#0-1) , a chunk `(slot_id, slot_version, data, sig)` that was validly signed and stored for lane A's contract also produces a valid `slot_metadata.verify(addr)` result for lane B's contract, since the digest never encodes which contract it was intended for. An attacker who observes a broadcast/posted chunk for lane A can re-POST the identical bytes to lane B's `/v2/stackerdb/{addr}/{signers-N-B}/chunks` endpoint (or replay it over the p2p `StackerDBPushChunk`/`StackerDBGetChunk` paths), and it will pass the equality check `slot_metadata.verify(&addr)` because the contract identity is never part of what was signed.

The only mitigating control is `signer_message_payload_matches_lane`, applied later in `libsigner` when interpreting chunks as `SignerMessage`s, which filters by the payload's leading type-prefix byte to match the lane's expected `message_id` [8](#0-7) . This is an application-layer filter on the *already-stored* chunk, not a cryptographic binding — the malicious/cross-lane write still lands in the target StackerDB's slot storage and is replicated to peers before that filter is ever applied, and it will succeed outright whenever the two message types happen to share a compatible prefix or whenever a bug/extension causes the mapping to be non-injective.

### Impact Explanation
This breaks the "signed vs. contract-authorized" equality relied on by StackerDB's authorization model: `try_replace_chunk`/`validate_received_chunk` treat a signature verifying against the local slot's registered signer as sufficient proof of the write's authenticity and intent for that specific contract instance, but the signature space is shared across every sibling contract with the same slot assignment. This is an unauthenticated write to state, matching the "unauthenticated/unauthorized write to state or StackerDB" Critical impact bucket: an attacker can force acceptance and network-wide propagation of a chunk into a StackerDB slot it was never intended for, without needing the signer's private key, the node's secret, or an admin role — only observation of one legitimately-broadcast chunk for the reward cycle.

### Likelihood Explanation
Likelihood is moderate-to-high: any relay-capable network peer, or any client with access to the public StackerDB HTTP GET/POST endpoints, can capture a legitimately signed chunk from any signer-message lane and resubmit it to another lane's contract for the same reward cycle. No privileged access, node secret, or additional cryptography is required — only that (a) the target lane's `slot_version`/`chunk_size`/`max_writes` gates are also satisfied (attacker controls `slot_version` freely up to `max_writes = u32::MAX`, per `signers.clar`) [9](#0-8) , which is trivially arrangeable.

### Recommendation
Bind the StackerDB contract identity (and/or reward cycle) into the signed digest, e.g. include a hash/identifier of `smart_contract_id` in `SlotMetadata::auth_digest`, mirroring how the AtomWallet fix bound `validUntil`/`validAfter` into the signed payload rather than leaving it as unauthenticated appended metadata. Alternatively, require slot-owner assignment across sibling `signers-N-*` contracts to be intentionally domain-separated (e.g. per-contract salts) so a signature cannot be replayed cross-contract even when the signer set and slot indices coincide.

### Proof of Concept
1. During reward cycle `N`, signer `S` owns `slot_id = k` in both `signers-N-1` (BlockResponse) and `signers-N-3` (BlockPreCommit), per the shared `stackerdb-get-signer-slots-page` mapping.
2. `S` legitimately signs and posts a chunk `(slot_id=k, slot_version=v, data=D, sig)` to `signers-N-1` via `POST /v2/stackerdb/{S}/signers-N-1/chunks`; it is accepted and gossiped.
3. An observing attacker captures this exact `StackerDBChunkData` JSON body and resubmits it unmodified to `POST /v2/stackerdb/{S}/signers-N-3/chunks` (choosing/adjusting `slot_version` on the target lane to satisfy its own freshness check — trivial since `max_writes = u32::MAX`).
4. `try_replace_chunk` for `signers-N-3` calls `slot_metadata.verify(&addr)` using `auth_digest()`, which only depends on `(k, v, hash(D))` — all attacker-controlled/replayable — and the check succeeds despite the chunk never having been signed for `signers-N-3`.
5. The chunk is stored and re-broadcast as if it were an authentic message for the `signers-N-3` lane.

    fn auth_digest(&self) -> Sha512Trunc256Sum {
        let mut hasher = Sha512_256::new();
        hasher.update(self.slot_id.to_be_bytes());
        hasher.update(self.slot_version.to_be_bytes());
        hasher.update(self.data_hash.0);
        Sha512Trunc256Sum::from_hasher(hasher)
    }

    /// Sign this slot metadata, committing to slot_id, slot_version, and
    /// data_hash.  Sets self.signature to the signature.
    /// Fails if the underlying crypto library fails
    pub fn sign(&mut self, privkey: &StacksPrivateKey) -> Result<(), Error> {
        let auth_digest = self.auth_digest();
        let sig = privkey
            .sign(&auth_digest.0)
            .map_err(|se| Error::SigningError(se.to_string()))?;

        self.signature = sig;
        Ok(())
    }

    /// Verify that a given principal signed this chunk metadata.
    /// Note that the address version is ignored.
    pub fn verify(&self, principal: &StacksAddress) -> Result<bool, Error> {
        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )
        .map_err(|ve| Error::VerifyingError(ve.to_string()))?;

        let pubkh = Hash160::from_node_public_key(&pubk);
        Ok(pubkh == *principal.bytes())
    }
