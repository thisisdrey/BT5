### Title
Signature-malleability weight double-counting bypasses multisig threshold in `ValidateMultiSign` precompile - ([File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java])

### Summary
The TVM precompiled contract `ValidateMultiSign` aggregates signer weights across a batch of signatures supplied in a single call. Its within-request de-duplication logic keys off the exact signature bytes concatenated with the recovered address, rather than the recovered address alone. Because ECDSA signatures are malleable (the same key/message pair admits multiple distinct valid `(r, s, v)` encodings), an attacker can submit two differently-encoded but cryptographically equivalent signatures from the *same* private key and have the weight for that address counted twice, letting a caller reach a permission's signing `threshold` without the required number of distinct authorized signers — directly analogous to OpenFGA's list-value cache-key collision (GHSA-jwvj-g8pc-cx45), where an incomplete/partial dedup key over a batch of near-identical items produced an incorrect authorization decision.

### Finding Description
`ValidateMultiSign.execute` iterates over the `signatures` array supplied in the precompile call data and accumulates `totalWeight` for each recovered signer against an account `Permission`: [1](#0-0) 

For each entry it recovers the address, builds `sign = merge(recoveredAddr, sign)`, and only skips accumulating weight if the *exact* `sign` byte-array (address||raw-signature-bytes) was already seen:

```
byte[] recoveredAddr = recoverAddrBySign(sign, hash);
sign = merge(recoveredAddr, sign);
if (ByteArray.matrixContains(executedSignList, recoveredAddr)) {
  if (ByteArray.matrixContains(executedSignList, sign)) {
    continue;
  }
  MUtil.checkCPUTime();
}
long weight = TransactionCapsule.getWeight(permission, recoveredAddr);
...
totalWeight += weight;
executedSignList.add(sign);
executedSignList.add(recoveredAddr);
``` [2](#0-1) 

The dedup check correctly detects a byte-for-byte duplicate signature (`sign` already in `executedSignList`) and skips it, but it does **not** stop processing when `recoveredAddr` is already present with a *different* raw signature encoding — it only inserts a CPU-time check (`MUtil.checkCPUTime()`) and then falls through to add `weight` again. Since ECDSA signatures over a fixed message/key are malleable (e.g. `(r, s, v)` vs `(r, n-s, 1-v)`, or any other alternate valid encoding recoverable to the same address), an attacker holding a single private key that is one of the permission's authorized keys can submit two (or more) distinct-byte, same-key signatures in the `signatures` array. Each is treated as a "different" entry because the concatenated `sign` byte value differs, so `TransactionCapsule.getWeight(permission, recoveredAddr)` is added to `totalWeight` multiple times for what is really a single authorized key.

This lets the caller reach `permission.getThreshold()` with fewer *distinct* authorized signers than the permission actually requires — a direct authorization-logic error (CWE-863) caused by a batch de-duplication key (`address||raw-sig-bytes`) that fails to fully identify "the same signer," exactly mirroring the OpenFGA advisory's root cause of a within-request dedup key that didn't fully capture identity/context, producing an incorrect authorization decision.

### Impact Explanation
`ValidateMultiSign` is invoked by any smart contract via the TVM precompile dispatch, reachable from an ordinary `TriggerSmartContract`/`TriggerConstantContract` call by any unprivileged account. A contract relying on `ValidateMultiSign` to gate privileged actions (e.g., custodial/multisig wallet logic, DeFi vaults, bridge contracts) can be tricked into approving an operation that should require multiple distinct co-signers, using signatures effectively controlled by a single key holder. This is an unauthorized-account-operation / permission-bypass primitive that can lead to theft of funds or unauthorized state changes gated by TVM-level multisig checks.

### Likelihood Explanation
The precondition is narrow but realistic: the attacker must control one signer whose weight, when doubled (or multiplied), reaches the threshold, and must be able to produce a second, differently-encoded but valid signature over the same `hash` from the same key — which is a well-known, low-effort ECDSA malleability transform (flipping `s` to `n-s` and the recovery bit). No special node privileges are required; this is purely a contract-level call using standard signature crafting. The main damage class (multisig-threshold bypass) requires the deployed smart contract to genuinely rely on this precompile for weight thresholds, which does limit blast radius to consumers of `ValidateMultiSign`, but the vulnerability is squarely inside `java-tron`'s own precompile implementation.

### Recommendation
Change the de-duplication key in `ValidateMultiSign.execute` to be based solely on `recoveredAddr` (i.e., once an address has contributed weight, skip it entirely regardless of the specific signature bytes), rather than on the combination of address and raw signature bytes. This mirrors the correct fix pattern for the OpenFGA analog: the cache/dedup key must capture the full identity that determines the result (the signer address) rather than a value (raw signature bytes) that can vary while representing the same signer.

### Proof of Concept
1. Deploy/invoke a contract that calls the `ValidateMultiSign` precompile with an account `permission` requiring, e.g., 2 signers with weight 1 each (threshold 2), where the attacker only controls key `K1` (weight 1) and is missing a second authorized signer.
2. Attacker signs `hash = sha256(address || permissionId || data)` once with `K1` to get `sig1 = (r, s, v)`.
3. Attacker derives a second, differently-encoded, still-valid signature from the same key over the same `hash` via the standard ECDSA malleability transform `sig2 = (r, n-s, 1-v)`.
4. Attacker submits `signatures = [sig1, sig2]` to `ValidateMultiSign`.
5. In the loop at [2](#0-1) , both entries recover to the same `recoveredAddr` (K1's address) but produce different `sign` byte arrays, so neither is skipped by the `matrixContains(executedSignList, sign)` check; `weight` for K1 is added twice, making `totalWeight = 2 >= threshold(2)`, and the call returns `dataOne()` (success) even though only one distinct authorized signer participated.
