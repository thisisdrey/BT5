## Analysis

The report describes a cross-chain-replay class: a merkle-tree-based "anyone can call withdraw()" function whose authorization data is signed without any chain-specific domain separator, so the exact same calldata can be rebroadcast on a forked chain to redirect/duplicate funds.

The closest reachable analog in java-tron is the **ShieldedTRC20 privacy pool**, whose mint/transfer/burn operations are executed through the permissionless `VerifyMintProof` / `VerifyTransferProof` / `VerifyBurnProof` precompiled contracts [1](#0-0) , invoked by any `TriggerSmartContract` transaction. The data that gets signed to authorize these shielded operations (`dataHashToBeSigned`, used for both the spend-authority signature and the Sapling binding signature) is built purely from application-level bytes — the shielded contract address plus the spend/receive descriptions — with no transaction-level or chain-specific binding at all: [2](#0-1) 

By contrast, the native L1 `ShieldedTransferContract` path (`ShieldedTransferActuator`) derives its `signHash` from `getShieldTransactionHashIgnoreTypeException(tx.getInstance())`, i.e. from the full enclosing transaction, which is bound to `ref_block_hash`/`ref_block_bytes`/`expiration` and therefore to a specific point on a specific chain: [3](#0-2) 

The ShieldedTRC20 pool has no equivalent binding — the signed hash and the resulting `TriggerSmartContract` calldata (`getTriggerContractInput`) are self-contained and chain-agnostic [4](#0-3) , and the trigger-input construction helper (`Wallet.getTriggerInputForShieldedTRC20Contract`) only adds an anti-replay nonce for the `BURN` case, at the client/RPC layer, not inside the on-chain precompiled verification itself: [5](#0-4) 

### Title
Missing chain-binding in ShieldedTRC20 signed authorization data enables cross-chain replay of mint/transfer/burn - (File: `framework/src/main/java/org/tron/core/zen/ShieldedTRC20ParametersBuilder.java`)

### Summary
The ShieldedTRC20 pool's spend-authority signature and Sapling binding signature are computed over `dataHashToBeSigned = Sha256Hash.of(shieldedTRC20Address || spend/receive descriptions ...)`, which contains no reference to a specific TRON network/chain (no `ref_block_hash`, no expiration, no chain id / genesis binding). Since mint/transfer/burn operations are executed via the permissionless `VerifyMintProof`/`VerifyTransferProof`/`VerifyBurnProof` precompiled contracts callable by any `TriggerSmartContract`, the exact calldata produced for one chain remains fully valid on any other chain that shares the same shielded pool state (e.g., after a chain fork/split, or a network that redeploys the same shielded contract with identical pre-fork Merkle tree state).

### Finding Description
`ShieldedTRC20ParametersBuilder.build()` constructs `mergedBytes` from only the contract address and the descriptions of the specific operation, then hashes it to get the value that is both signed (`createSpendAuth`) and embedded as `messageHash`/used for `bindingSig` [6](#0-5) . Nothing in this hash ties the authorization to a specific chain instance, unlike the native `ShieldedTransferContract`, whose `signHash` is derived from the whole `Transaction`, which is bound to `ref_block_hash`/`expiration` and thus effectively chain-specific [7](#0-6) .

Because the resulting proof + signatures are packaged into ABI-encoded trigger input that anyone can resubmit as a `TriggerSmartContract` (the verification precompiles do not check `msg.sender`, only the zk-proof math) [8](#0-7) , an attacker who observes such a transaction on one network can rebroadcast identical calldata on a sibling/forked network that shares the pre-fork nullifier set and Merkle tree state. The nullifier check that prevents double-spend is purely local per-chain state (`NullifierStore`), so it does not detect that the note was already spent on a *different* chain.

### Impact Explanation
A successful replay lets an attacker duplicate a shielded mint, transfer, or burn on a second chain that was never intended by the original signer — for burn operations in particular this authorizes disbursement of transparent TRC20 tokens to the `transparentToAddress` a second time on the other chain, i.e., unauthorized creation of an unbacked balance / duplicate withdrawal of funds, which is a Medium-severity funds-integrity issue on any network that forks from or mirrors java-tron's mainnet state (e.g., private chains, test networks, or a contentious hard fork).

### Likelihood Explanation
Exploitation requires only observing a public, already-broadcast trigger-contract transaction (all shielded pool inputs and signatures are on-chain/public calldata) and resubmitting it verbatim on a second chain instance that shares the same shielded-pool deployment address and pre-fork state — no private key or privileged role is needed, matching the original report's "anyone may call this function for anyone else" pattern.

### Recommendation
Bind the ShieldedTRC20 `dataHashToBeSigned` (and therefore the spend-authority/binding signatures) to chain-specific context — e.g. include a network/genesis identifier, the shielded contract's deployment-chain fingerprint, or the referencing transaction's `ref_block_hash`/expiration — analogous to the domain separation already relied upon implicitly by the native `ShieldedTransferContract` path, so that valid proofs/signatures cannot be replayed verbatim across distinct chain instances.

### Proof of Concept
1. Build a valid ShieldedTRC20 `BURN` (or `TRANSFER`/`MINT`) parameter set and its trigger-contract input using `ShieldedTRC20ParametersBuilder`/`Wallet.getTriggerInputForShieldedTRC20Contract` as shown in the test flow [9](#0-8) .
2. Broadcast the resulting `TriggerSmartContract` transaction on chain A; it succeeds because `VerifyBurnProof`/`VerifyTransferProof` only validate the zk-SNARK math and signatures, not `msg.sender` or chain-specific data.
3. Capture the identical calldata and rebroadcast it as a new `TriggerSmartContract` transaction on chain B (a fork/mirror sharing the same shielded pool contract address and pre-fork nullifier/Merkle state); since `dataHashToBeSigned` contains no chain-specific binding, the same proofs/signatures verify successfully again, duplicating the transfer/burn on chain B.
