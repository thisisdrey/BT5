### Title
StackerDB inventory response advertises an unpersisted chunk version as stored - ([File: stackslib/src/net/stackerdb/mod.rs])

### Summary
`PeerNetwork::handle_unsolicited_StackerDBPushChunk()` builds the `StackerDBChunkInv` reply that tells a remote peer "we now have slot X at version Y" by patching the in-memory inventory vector as soon as a pushed chunk passes `validate_received_chunk()` — before the chunk has actually been written to the StackerDB store. The real write happens later, out-of-band, when the message is forwarded to the relayer and processed by `Relayer::process_stacker_db_chunks()` via `StackerDBTx::try_replace_chunk()`. This breaks the equality "advertised inventory version == persisted slot version," the same class of bug as the audited report, where a value sent to another party (raw collateral vs. net-of-borrow capacity) did not reflect the true, up-to-date state.

### Finding Description
`make_StackerDBChunksInv_or_Nack()` fetches the *current* slot versions from the DB [1](#0-0) . Immediately afterward, in `handle_unsolicited_StackerDBPushChunk()`, once `validate_received_chunk()` passes (signature, size, staleness, max-writes checks against the *pre-write* state) [2](#0-1) , the code optimistically overwrites the corresponding entry in that inventory vector with the version from the *incoming, not-yet-stored* chunk and sends this patched inventory back to the peer as the truth: [3](#0-2) .

The actual persistence of the chunk (`tx.try_replace_chunk`) happens separately and later, in `Relayer::process_stacker_db_chunks()`, which re-validates against the DB state at commit time and can fail (e.g. `StaleChunk`) if another chunk for the same slot was committed first; on failure it is simply logged and dropped — no corrective NACK or inventory retraction is sent to the peer that was already told the chunk was accepted: [4](#0-3) .

Because `validate_received_chunk()` only checks the DB's state *at the moment the message arrived*, not atomically with the store operation performed later by the relayer, and because chunk delivery/validation and chunk storage are two decoupled steps (validate in `stackerdb/mod.rs`, commit in `relay.rs`), a remote peer can be told that a specific slot/version is stored on this node when, in fact, the corresponding write can still fail and be dropped. The peer's own StackerDB replica sync logic in `sync.rs` uses the received `StackerDBChunkInv` to decide it need not re-fetch that slot, so the network's shared inventory can end up diverging from the local (real) contents of the StackerDB store.

### Impact Explanation
This matches the "serving non-canonical state as canonical" category. A node's advertised StackerDB chunk inventory can claim persistence of a chunk that never actually lands in the store, causing peers to believe replication succeeded and skip re-fetching that slot/version, leaving a permanent gap in that StackerDB's global replication for the affected slot until an unrelated later write bumps the version again. Since StackerDB is used for signer messaging/state (e.g., signer signature and state-machine updates carried over StackerDB, per `libstackerdb`), an inventory hole can cause certain signer messages to never propagate to some nodes, degrading availability of signer coordination data without any consensus-level compromise.

### Likelihood Explanation
Reaching this requires no special privileges — any connected peer can push a validly-signed `StackerDBPushChunk` message to a node's `PeerNetwork`, which unconditionally enters this optimistic-inventory-patch code path via `handle_unsolicited_StackerDBPushChunk()`. Triggering the actual persistence *failure* after the optimistic ack requires a race — e.g. two connections receiving different valid pushes for the same slot in a narrow window before the relayer batch-commits them — which is plausible in a busy StackerDB but not trivially forced by a single remote actor; it is more of a design gap (decoupled validate/ack vs. commit) than a deterministic single-message exploit. I was unable to fully verify the threading/ordering guarantees of the p2p event loop (whether unsolicited-message handling and the later `process_stacker_db_chunks()` call are strictly serialized per network tick), which affects how easily the race can be forced; this should be checked further with the actual node event-loop code before treating likelihood as more than "possible under specific timing."

### Recommendation
Do not patch/send the inventory update until the chunk has actually been committed via `try_replace_chunk()`. Either (a) perform the DB write synchronously inside `handle_unsolicited_StackerDBPushChunk()` before constructing the ack, or (b) defer sending the `StackerDBChunkInv` reply until after the relayer's `process_stacker_db_chunks()` has confirmed the write succeeded, and send a corrective NACK/updated inventory if the deferred commit fails.
