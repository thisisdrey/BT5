### Title
Attacker fills victim's `depositTokensOfAccount` via dust `DepositToken.transfer`, permanently blocking deposits of new collateral types (`UserReachedMaxTokens`) - ([File: contracts/Pool.sol](contracts/Pool.sol) / [contracts/DepositToken.sol](contracts/DepositToken.sol))

### Summary
CVE-2019-18281 is a DoS where a resource-constrained container (the Qt text engine's run list) is overfilled with attacker-controlled items until processing crashes. The Metronome analog is the bounded per-account token list in `Pool`: `MAX_TOKENS_PER_USER = 30` (`Pool.sol:79`). `DepositToken._transfer` adds the token to the *recipient's* list whenever their balance goes from 0 → positive (`DepositToken.sol:518-520`), with no consent required. An attacker can dust-transfer all registered deposit tokens to a victim, fill the combined 30-slot limit, and cause every subsequent first-time receipt or `deposit` for that account to revert via `onlyIfAdditionWillNotReachMaxTokens` (`Pool.sol:143-148`).

### Finding Description
- `Pool.addToDepositTokensOfAccount(account_)` is callable only by a registered `DepositToken`, but the trigger is the permissionless ERC20 `transfer`/`transferFrom` path.
- In `DepositToken._transfer` (`DepositToken.sol:498-526`), after updating balances it calls `pool.addToDepositTokensOfAccount(recipient_)` whenever `_recipientBalanceBefore == 0 && amount_ > 0`.
- `Pool.sol:144` reverts with `UserReachedMaxTokens` when `debtTokensOfAccount.length(account_) + depositTokensOfAccount.length(account_) >= 30`. The count is shared between deposit and debt tokens.
- Attack: for each registered deposit token `d[i]`, attacker deposits a small amount themselves (or acquires dust), then calls `d[i].transfer(victim, 1 wei)`. Each call grows `depositTokensOfAccount[victim]`. After enough transfers (max 30 across deposit+debt lists; pools typically have far fewer deposit tokens, but the attacker can spread across multiple pools' tokens and combine with `DebtToken` positions the victim opens), the list hits the cap.
- Once at cap, any `deposit(amount, victim)` into a deposit token the victim does not already hold reverts inside `_mint` → `addToDepositTokensOfAccount` (`DepositToken.sol:486-488`), and any `transfer`/`seize` to the victim of a new token reverts identically.
- Victim recovery requires manually transferring dust out of the tokens they never wanted (each `transfer` with full balance calls `removeFromDepositTokensOfAccount`), or waiting; there is no "leave list" or "reject" function — `removeFromDepositTokensOfAccount` is callable only by the token itself (`Pool.sol` `_revertIfSenderIsNotDepositToken`), i.e., only by zeroing the balance.

### Impact Explanation
Temporary freezing / denial of service of the victim's collateral operations: while at the cap, the victim cannot deposit a *new* collateral type, cannot receive deposit tokens via transfer, and — critically — cannot top up with a different asset to repair an unhealthy position before `Pool.liquidate` executes against them. Their existing-token deposits and withdrawals still work, so it is a partial, time-bounded freeze rather than permanent loss, matching the "temporary freezing of funds" impact tier.

### Likelihood Explanation
Fully reachable by an unprivileged EOA: `DepositToken.transfer` is public, requires no role, and the only cost is dust amounts of each collateral plus gas. The 30-slot cap is shared, so the number of transfers needed is bounded and small on pools with few listed collaterals. No privileged actor, oracle manipulation, or governance action is required. No modifier (`whenNotPaused`, `nonReentrant`, `_revertIfLocked`) prevents the inbound dusting; `_revertIfLocked` only constrains the *sender's* balance, which the attacker controls. The attack is strongest when timed against a victim whose position is deteriorating and who needs to add a different collateral type.

### Recommendation
Do not add tokens to a recipient's account list on inbound transfers; only track tokens the account actively `deposit()`ed, or make `addToDepositTokensOfAccount` failure non-fatal on transfer (skip list addition rather than revert) and re-derive collateral values from an allow-list. Alternatively, add a per-account opt-out/`leaveTokenList(account, token)` that lets any user remove entries without zeroing balances.

### Proof of Concept
```ts
// Hardhat, forked deployment context
// Assume pool has registered deposit tokens msdA, msdB, ... and victim is an EOA.

it("fills victim's token list, blocking new-collateral deposits", async () => {
  const depositTokens = await pool.getDepositTokens(); // registered DepositToken[]

  // Attacker deposits dust in each token and transfers it to the victim
  for (const d of depositTokens) {
    const dt = await ethers.getContractAt("DepositToken", d);
    const underlying = await ethers.getContractAt("IERC20", await dt.underlying());
    await underlying.connect(attacker).approve(dt.address, 2);
    await dt.connect(attacker).deposit(2, attacker.address); // balance 0 -> >0 for attacker
    await dt.connect(attacker).transfer(victim.address, 1);  // victim balance 0 -> 1, list += 1
  }

  // Repeat across pools / combined with victim's debt tokens until:
  // debtTokensOfAccount.length(victim) + depositTokensOfAccount.length(victim) == 30
  expect(
    (await pool.getDepositTokensOfAccount(victim.address)).length +
    (await pool.getDebtTokensOfAccount(victim.address)).length
  ).to.eq(30);

  // Victim (or anyone on their behalf) tries to deposit a collateral type they don't yet hold
  const newDt = depositTokenNotHeldByVictim;
  const underlying = await ethers.getContractAt("IERC20", await newDt.underlying());
  await underlying.connect(victim).approve(newDt.address, 1000);
  await expect(
    newDt.connect(victim).deposit(1000, victim.address)
  ).to.be.revertedWithCustomError(pool, "UserReachedMaxTokens");

  // Direct transfers of new tokens to the victim also revert
  await expect(
    newDt.connect(attacker).transfer(victim.address, 1)
  ).to.be.revertedWithCustomError(pool, "UserReachedMaxTokens");
});
```
