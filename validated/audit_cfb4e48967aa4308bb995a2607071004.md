Audit Report

## Title
`CREATE1` contract address derivation uses stale nonce in dry-run/RPC simulation, producing an address that diverges from the actual on-chain deployment address - (File: `substrate/frame/revive/src/exec.rs`)

## Summary
`Stack::new_frame` computes the `CREATE1` deployment address via `address::create1(&deployer, account_nonce.saturating_sub(1))` whenever `origin_is_caller` is true, without checking whether the current execution is a real dispatched transaction (where `CheckNonce` has already bumped the nonce pre-dispatch) or a dry-run/RPC simulation (where no such increment occurs). This causes `eth_estimateGas`/`eth_call`/`dry_run_eth_transact`-style simulations to report a `CREATE1` contract address one nonce lower than the address actually produced when the real transaction executes.

## Finding Description
In `FrameArgs::Instantiate` handling, the address for a salt-less (`CREATE1`) instantiation is derived as: [1](#0-0) 

The subtraction of 1 from `account_nonce` is only correct when `CheckNonce` has already incremented the stored nonce pre-dispatch, i.e., for a genuine signed extrinsic. The code gates this solely on `origin_is_caller`, with no check against the execution context (dry-run vs. real transaction). I confirmed via `grep_search` that `ExecContext` — the type introduced by the referenced fix (`prdoc/stable2506/pr_8504.prdoc`) to gate this subtraction — does not appear anywhere in `exec.rs` in this repository snapshot; it only exists in the prdoc description of the upstream fix. The `ExecConfig` struct does carry an `is_dry_run: Option<DryRunConfigurations<MomentOf<T>>>` field, and separately a `bump_nonce: bool` field explicitly documented as controlling nonce-increment behavior for Ethereum-originated transactions, but neither of these is consulted in the `create1` nonce computation shown above.

This matches the exact pre-fix logic described in `prdoc/stable2506/pr_8504.prdoc`, confirming the vulnerable code path is what ships in this snapshot.

## Impact Explanation
Any wallet, deployment tool, or contract relying on dry-run simulation (`eth_estimateGas`, `eth_call` for contract creation, `dry_run_eth_transact`) to predict a `CREATE1` contract's address will receive an address computed for `nonce - 1` rather than the actual deployment nonce, since the stored nonce is not incremented pre-dispatch during simulation. Funds or approvals pre-committed against the simulated (wrong) address — a common Ethereum tooling pattern for counterfactual deployments — would be sent to an account that never becomes the intended contract, resulting in a permanent fund lock. This aligns with the "permanent user-fund lock" impact category in the Polkadot SDK impact gate.

## Likelihood Explanation
The bug is reachable by any unprivileged user through standard public RPC/dry-run entrypoints exposed by `pallet-revive`'s Ethereum-compatibility layer, with no special permissions or privileged actor required. It is deterministic and reproducible on every `CREATE1` (no-salt) dry-run simulation where `origin_is_caller` is true, not a race condition.

## Recommendation
Gate the `saturating_sub(1)` nonce adjustment on the actual execution context rather than solely on `origin_is_caller` — e.g., use `exec_config.is_dry_run.is_none()` (or an equivalent execution-context marker) to determine whether the nonce has genuinely been pre-incremented, matching the shape of the upstream `ExecContext::Transaction` gate. Add a regression test asserting dry-run and actual-transaction `CREATE1` deployments compute identical addresses for the same nonce.

## Proof of Concept
1. Fund an account and note its on-chain nonce `N`.
2. Call `dry_run_eth_transact` (or `eth_estimateGas`/`eth_call`) with `to = None` and contract-creation bytecode (no salt), hitting `FrameArgs::Instantiate` with `salt = None`, `origin_is_caller = true`.
3. Observe returned address computed via `address::create1(&deployer, N - 1)`.
4. Submit the real signed extrinsic for the same deployment; `CheckNonce` increments stored nonce to `N + 1` pre-dispatch, and `new_frame` computes `address::create1(&deployer, N)`.
5. The two addresses differ by one nonce value, confirming the dry-run result is unreliable relative to the actual deployment address.
