### Title
Out-of-bounds read / segmentation fault parsing malicious central-directory entries in `ijar`'s zip parser - (File: `third_party/ijar/zip.cc`)

### Summary
`InputZipFile::ProcessCentralDirEntry` in `third_party/ijar/zip.cc` decodes central-directory records from an mmap'd, attacker-controlled zip/jar file without any bounds checking of the length fields it reads, unlike the sibling local-file-header parser which performs `EnsureRemaining()` checks before every advance. A malformed jar consumed by `ijar` (Bazel's interface-jar stripping tool, and the same core code path used by `singlejar`) can drive the cursor `p` past the end of the mapped buffer, causing an out-of-bounds read / SIGSEGV — the same bug class as CVE-2022-43039 (GPAC's `gf_isom_meta_restore_items_ref` segfault from unchecked, attacker-controlled offsets/lengths while restoring item references from a malformed box).

### Finding Description
`ProcessCentralDirEntry` reads `file_name_length`, `extra_field_length`, and `file_comment_length` directly from attacker-supplied bytes and advances the cursor `p` by these values with no check that the resulting pointer stays within `[zipdata_in_, zipdata_in_ + input_file_->Length())`: [1](#0-0) [2](#0-1) 

The code comment explicitly assumes the input is well-formed ("the central directory is always followed by another data structure that has a signature, so parsing it this way is safe"), which is not a validated invariant for hostile input: [3](#0-2) 

By contrast, `InputZipFile::ProcessLocalFileEntry` (parsing the *local* file header) does call `EnsureRemaining()` before every pointer advance: [4](#0-3) 

`FindZipCentralDirectory` only validates that `central_dir_offset + central_dir_size <= in_length` — it does not validate the internal structure or lengths of individual entries inside that region: [5](#0-4) 

The buffer itself is a plain `mmap` of the file with no guard page (unlike the *output* mapped file, which intentionally over-allocates a guard page to turn overflow-writes into crashes, an unrelated write-side mitigation): [6](#0-5) 

A crafted `filename_length`/`extra_field_length`/`file_comment_length` combination (e.g., values that push `p` far beyond `in_length` while `central_dir_offset + central_dir_size <= in_length` still holds for the outer check, or a corrupted last entry near the very end of the mapped region) causes subsequent `get_u4le(p)`/`get_u2le(p)` calls or the `memcpy` of the filename to dereference memory outside the mapped page range, producing a wild read and SIGSEGV.

### Impact Explanation
An attacker who supplies a malicious jar/zip (e.g., as a Bazel dependency artifact fetched via `http_archive`/`http_jar`, a Maven artifact, or any archive later processed by `ijar` to generate an interface jar) can crash the build process with a segmentation fault when Bazel invokes `ijar` on the file. This is a denial-of-service against the local build (crash, not code execution or data corruption), matching the severity profile of the referenced GPAC CVE (Medium, `AV:L`, `A:H`/no C or I impact).

### Likelihood Explanation
Likelihood is moderate-to-high in a threat model where dependency archives are attacker-influenced: no MITM or credential compromise is needed, just publishing a byte pattern that reaches `ijar`'s central-directory parser. The `EnsureRemaining` protections that exist for local headers were evidently considered necessary there but were not applied symmetrically to the central-directory parsing path, suggesting this is an overlooked gap rather than a deliberately accepted risk.

### Recommendation
Add explicit length/bounds validation in `InputZipFile::ProcessCentralDirEntry` mirroring `EnsureRemaining()` in `ProcessLocalFileEntry`: before reading `file_name_length`, `extra_field_length`, `file_comment_length`, and before each `p += length` advance, verify the remaining distance to `zipdata_in_ + input_file_->Length()` is sufficient, and fail gracefully (returning an error) rather than trusting the "safe by construction" assumption.

### Proof of Concept
A `BuildIntegrationTestCase`/`src/test/shell` style repro: build a crafted zip whose End-Of-Central-Directory/central-directory size satisfies `FindZipCentralDirectory`'s outer bound check, but whose last central-directory entry declares `file_name_length`/`extra_field_length`/`file_comment_length` values that, when summed, place the cursor `p` beyond `zipdata_in_ + Length()`. Feed this file to the `ijar` binary (`third_party/ijar/ijar.cc` / `zip_main.cc`) as the input jar and observe a SIGSEGV instead of a clean parse error — analogous to the `input_jar_scan_entries_test.h` fixtures used for legitimate zip64 parsing tests, but with deliberately malicious length fields instead of valid ones. // Note that the central directory is always followed by another data structure
// that has a signature, so parsing it this way is safe.
bool InputZipFile::ProcessCentralDirEntry(const u1 *&p, u8 *compressed_size,
                                          u8 *uncompressed_size, char *filename,
                                          size_t filename_size, u4 *attr,
                                          u8 *offset) {
  u4 signature = get_u4le(p);

  if (signature != CENTRAL_FILE_HEADER_SIGNATURE) {
    if (signature != DIGITAL_SIGNATURE && signature != EOCD_SIGNATURE &&
        signature != ZIP64_EOCD_SIGNATURE) {
      error("invalid central file header signature: 0x%x\n", signature);
    }
    return false;
  }

  p += 16;  // skip to 'compressed size' field
  *compressed_size = get_u4le(p);
  *uncompressed_size = get_u4le(p);
  u2 file_name_length = get_u2le(p);
  u2 extra_field_length = get_u2le(p);
  u2 file_comment_length = get_u2le(p);
  p += 4;  // skip to external file attributes field
  *attr = get_u4le(p);
  *offset = get_u4le(p);
  {
    size_t len = (file_name_length < filename_size)
      ? file_name_length
      : (filename_size - 1);
    memcpy(reinterpret_cast<void*>(filename), p, len);
    filename[len] = 0;
  }
  p += file_name_length;
  const u1 *extra_p = p;
  p += extra_field_length;
  while (extra_p != p) {
    const u2 header_id = get_u2le(extra_p);
    const u2 data_size = get_u2le(extra_p);
    const u1 *extra = extra_p;
    extra_p += data_size;
    if (header_id == ZIP64_EXTRA_FIELD_TAG) {
      if (*uncompressed_size == U4_MAX) {
        *uncompressed_size = get_u8le(extra);
      }
      if (*compressed_size == U4_MAX) {
        *compressed_size = get_u8le(extra);
      }
      if (*offset == U4_MAX) {
        *offset = get_u8le(extra);
      }
    }
  }
  p += file_comment_length;
  return true;
}
