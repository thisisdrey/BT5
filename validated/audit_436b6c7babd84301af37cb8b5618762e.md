### Title
`isExchangeTransaction` gate is fully disabled once `ALLOW_HARDEN_EXCHANGE_CALCULATION` is on, silently removing the intended block on `ExchangeTransactionContract` - (File: `framework/src/main/java/org/tron/core/db/Manager.java`)

### Summary
`Manager.isExchangeTransaction()` short-circuits to `false` for *every* transaction (regardless of its actual contract type) whenever the committee-controlled dynamic property `allowHardenExchangeCalculation` is enabled. This is structurally the same bug pattern as the `ExpiringMarket.isClosed()` always returning `false`: a gate/guard boolean that is supposed to conditionally block a class of operations is neutralized by an unrelated flag, so downstream `require`/`throw` checks that depend on it never fire.

### Finding Description
`isExchangeTransaction` is used as a gate in three places to reject/skip the legacy, precision-sensitive `ExchangeTransactionContract` path: [1](#0-0) 

```java
private boolean isExchangeTransaction(Transaction transaction) {
    if (getDynamicPropertiesStore().allowHardenExchangeCalculation()) {
      return false;
    }
    Contract contract = transaction.getRawData().getContract(0);
    switch (contract.getType()) {
      case ExchangeTransactionContract: {
        return true;
      }
      default:
        return false;
    }
}
```

This helper feeds:
1. `pushTransaction` — rejects incoming `ExchangeTransactionContract` transactions outright: [2](#0-1) 
2. `generateBlock` — skips packing exchange transactions from the pending/repush queues: [3](#0-2) 
3. `rejectExchangeTransaction`, called for every transaction inside `processBlock` while applying a received block: [4](#0-3) 

Because `isExchangeTransaction` returns `false` unconditionally the moment `allowHardenExchangeCalculation` is `1` — with no per-transaction contract-type check being reached at all — every one of these three enforcement points becomes a no-op for `ExchangeTransactionContract`, exactly mirroring the report's root cause: a boolean gate (`isClosed()` / `isExchangeTransaction()`) that always evaluates to the "allow" branch once a certain state is set, defeating the `require`/`throw` guard built on top of it.

The critical difference from the external report's "acknowledged, no real-world impact" framing is that here the flag (`allowHardenExchangeCalculation`) is a **committee-governed chain parameter** set via `ProposalUtil`/`ProposalService`, not something under attacker control, and its correctness is unverifiable from the code alone: turning it on is supposed to mean "the hardened, overflow/precision-safe math paths in `ExchangeTransactionActuator`, `ExchangeCapsule.transaction`, `ExchangeWithdrawActuator`, etc. are now safe to use again," and as a consequence the deprecation gate for `ExchangeTransactionContract` is fully lifted for **every actuator and every code path simultaneously** with a single boolean, rather than being scoped to only the specific hardened calculation. Any transaction type match bug or edge case not covered by "hardened" math (e.g. asset-decimal edge cases, `TRX_SYMBOL_BYTES` handling, or interactions with `AllowSameTokenName`) would silently re-enable the previously-blocked, precision-sensitive `ExchangeTransactionContract` flow with no independent contract-type re-validation, since the check collapses to a constant `false` rather than "check the fix is in effect AND this is not an exchange contract that still needs rejecting."

### Impact Explanation
If the hardened math fix does not fully close the original precision/overflow issue that justified rejecting `ExchangeTransactionContract` post-fork (`VERSION_4_8_0_1`), enabling `allowHardenExchangeCalculation` would resurrect the exploit path across all three enforcement points at once (transaction admission, block packing, and block validation), potentially enabling unbacked-balance creation or fund loss through the reopened exchange trading path. Given `ExchangeTransactionActuator.execute`/`validate` directly mutate account balances and `ExchangeCapsule` reserves, a residual precision bug would be a direct path to loss/creation of funds. [5](#0-4) 

### Likelihood Explanation
Likelihood is low-to-moderate: `allowHardenExchangeCalculation` can only be flipped by a passed committee proposal, not by an arbitrary transaction sender, so it is not directly attacker-triggerable. However, once the committee enables it (which is the intended eventual outcome of this feature), the gate collapse is unconditional and irreversible in effect for as long as the flag stays on, and there is no secondary contract-type check retained as defense in depth.

### Recommendation
Do not let `isExchangeTransaction` collapse to a blanket `false`. Keep the contract-type check independent of the `allowHardenExchangeCalculation` flag, e.g.:
```java
private boolean isExchangeTransaction(Transaction transaction) {
  Contract contract = transaction.getRawData().getContract(0);
  boolean isExchangeType = contract.getType() == ContractType.ExchangeTransactionContract;
  if (!isExchangeType) {
    return false;
  }
  return !getDynamicPropertiesStore().allowHardenExchangeCalculation();
}
```
This preserves the same intended behavior (harden-on disables the reject/skip logic) while ensuring the contract-type detection itself is never silently bypassed, and makes it easier to reason about/extend if additional conditions (e.g. still rejecting specific malformed exchange transactions even when hardened math is active) are needed later.

### Proof of Concept
1. Committee passes a proposal enabling `ALLOW_HARDEN_EXCHANGE_CALCULATION` (`ProposalUtil`/`ProposalService`), setting `allowHardenExchangeCalculation() == true` in `DynamicPropertiesStore`.
2. A user broadcasts an `ExchangeTransactionContract` transaction via the standard tx-submission path (`Wallet` -> `Manager.pushTransaction`).
3. `isExchangeTransaction(trx.getInstance())` returns `false` immediately due to the flag check, before even inspecting the contract type, so the `"ExchangeTransactionContract is rejected"` `ContractValidateException` is never thrown. [2](#0-1) 
4. The transaction is queued, packed into a block by `generateBlock` (skip check also bypassed), and accepted by peers during `processBlock` (rejection check also bypassed) — reactivating full `ExchangeTransactionContract` semantics network-wide via a single dynamic property, with no additional per-transaction validation retained to catch cases the harden fix may not cover.

  public boolean execute(Object object) throws ContractExeException {
    TransactionResultCapsule ret = (TransactionResultCapsule) object;

    }

    long fee = calcFee();
    AccountStore accountStore = chainBaseManager.getAccountStore();
    DynamicPropertiesStore dynamicStore = chainBaseManager.getDynamicPropertiesStore();
    ExchangeStore exchangeStore = chainBaseManager.getExchangeStore();
    ExchangeV2Store exchangeV2Store = chainBaseManager.getExchangeV2Store();
    AssetIssueStore assetIssueStore = chainBaseManager.getAssetIssueStore();
    try {
      final ExchangeTransactionContract exchangeTransactionContract = this.any
          .unpack(ExchangeTransactionContract.class);
      AccountCapsule accountCapsule = accountStore
          .get(exchangeTransactionContract.getOwnerAddress().toByteArray());

      ExchangeCapsule exchangeCapsule = Commons
          .getExchangeStoreFinal(dynamicStore, exchangeStore, exchangeV2Store)
          .get(ByteArray.fromLong(exchangeTransactionContract.getExchangeId()));

      byte[] firstTokenID = exchangeCapsule.getFirstTokenId();
      byte[] secondTokenID = exchangeCapsule.getSecondTokenId();

      byte[] tokenID = exchangeTransactionContract.getTokenId().toByteArray();
      long tokenQuant = exchangeTransactionContract.getQuant();

      byte[] anotherTokenID;
      long anotherTokenQuant = exchangeCapsule.transaction(tokenID, tokenQuant,
          dynamicStore.allowStrictMath(), allowHarden());

      if (Arrays.equals(tokenID, firstTokenID)) {
        anotherTokenID = secondTokenID;
      } else {
        anotherTokenID = firstTokenID;
      }

      long newBalance = subtractExact(accountCapsule.getBalance(), calcFee());
      accountCapsule.setBalance(newBalance);

      if (Arrays.equals(tokenID, TRX_SYMBOL_BYTES)) {
        accountCapsule.setBalance(subtractExact(newBalance, tokenQuant));
      } else {
        accountCapsule.reduceAssetAmountV2(tokenID, tokenQuant, dynamicStore, assetIssueStore);
      }

      if (Arrays.equals(anotherTokenID, TRX_SYMBOL_BYTES)) {
        accountCapsule.setBalance(addExact(newBalance, anotherTokenQuant));
      } else {
        accountCapsule
            .addAssetAmountV2(anotherTokenID, anotherTokenQuant, dynamicStore, assetIssueStore);
      }

      accountStore.put(accountCapsule.createDbKey(), accountCapsule);

      Commons.putExchangeCapsule(exchangeCapsule, dynamicStore, exchangeStore, exchangeV2Store,
          assetIssueStore);

      ret.setExchangeReceivedAmount(anotherTokenQuant);
      ret.setStatus(fee, code.SUCESS);
    } catch (ItemNotFoundException | InvalidProtocolBufferException
        | ContractValidateException | ArithmeticException e) {
      logger.debug(e.getMessage(), e);
      ret.setStatus(fee, code.FAILED);
      throw new ContractExeException(e.getMessage());
    }
    return true;
  }
