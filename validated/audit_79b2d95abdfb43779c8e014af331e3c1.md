### Title
Attacker can fill a victim's per-account token list to `MAX_TOKENS_PER_USER` via dust `DepositToken` transfers, permanently blocking new deposits and debt minting - ([File: contracts/Pool.sol])

### Summary
Analogous to the wallet that "accepts" an 18-word mnemonic but only supports tracking/displaying 12 words, `Pool` lets any `DepositToken` transfer or mint arbitrarily append entries to a victim's `depositTokensOfAccount` list, while the account-level bookkeeping only supports `MAX_TOKENS_PER_USER = 30` combined deposit + debt tokens. Once the cap is reached, every subsequent `addToDepositTokensOfAccount` / `addToDebtTokensOfAccount` reverts with `UserReachedMaxTokens`, which DoS-es the victim's ability to deposit new collateral types or mint new debt positions — including while their existing position is becoming liquidatable.

### Finding Description
`Pool` maintains a per-account `MappedEnumerableSet.AddressSet` for `depositTokensOfAccount` and `debtTokensOfAccount`, guarded by `onlyIfAdditionWillNotReachMaxTokens` (reverts when `debtTokens + depositTokens >= 30`) [1](#0-0) .

The key issue is *who* can add entries. `DepositToken._transfer` unconditionally calls `pool.addToDepositTokensOfAccount(recipient_)` whenever the recipient's balance goes from 0 to >0 [2](#0-1) . There is no opt-in, no minimum amount, and no consent check: any holder of an msdTOKEN can `transfer(victim, 1 wei)` and permanently occupy a slot in the victim's list. The same happens on `DepositToken._mint` [3](#0-2) .

Debt tokens are non-transferable (`transfer`/`transferFrom` revert with `TransferNotSupported`) [4](#0-3) , so an attacker can only push deposit-token entries. However, on pools with a sufficient number of registered deposit tokens (the list is capped only by the pool's `ReachedMaxDepositTokens` offerings, not per user), an attacker holding dust amounts of each deposit token fills the victim's list to 30.

Once saturated:
- `DepositToken.deposit`/`mint` for any *new* collateral reverts inside `_mint` → `addToDepositTokensOfAccount` → `UserReachedMaxTokens`.
- `DebtToken.issue`/`mint` for any *new* synthetic debt reverts inside `_mint` → `addToDebtTokensOfAccount` [5](#0-4) .
- `SmartFarmingManager.leverage`/`flashRepay` paths that touch new tokens revert.

Cleanup is possible only if the victim can transfer the dust tokens back out (which zeroes the balance and triggers `removeFromDepositTokensOfAccount`). However, `DepositToken._transfer` is gated by `_revertIfLocked` on the sender side for accounts with outstanding debt — a victim whose collateral is locked by open debt positions may be unable to send the attacker-dusted tokens away, because *any* transfer-out requires the unlocked-balance check to pass for the *sender*, i.e. the victim. In that state the victim cannot add new collateral to restore health, cannot mint new debt to refinance, and can be pushed into liquidation — an unrecoverable-by-UI mismatch directly mirroring the mnemonic truncation bug (system state supports more entries than the accounting structure can handle, and the excess is silently irreversible through normal user flows).

### Impact Explanation
Temporary-to-permanent freezing of the victim's ability to manage their position: the victim cannot deposit additional collateral of a new type to de-lever or avoid liquidation. If the market moves against them while saturated, they are liquidated when they otherwise could have topped up collateral — direct economic loss forced by an unprivileged attacker spending only dust amounts of pool deposit tokens.

### Likelihood Explanation
Cost to the attacker is trivial: acquire 1 wei of each distinct `DepositToken` (they are freely transferable ERC-20s) and transfer to the victim. Reachability depends on the deployed pool having enough distinct deposit tokens to fill remaining slots (up to 30). Uncertainty: I could not fully verify the number of registered deposit tokens per deployed pool or the exact `_revertIfLocked` semantics that determine whether the victim can self-clean the list; if the pool has few deposit tokens, the cap may be unreachable and the finding reduces to low-severity griefing.

### Recommendation
Mirror the report's fix — validate input length *before* accepting it, or remove the hard cap. Concretely:
- Only add a token to `depositTokensOfAccount` on explicit user actions (`deposit`/`mint` by the account itself via `SynthContext._msgSender()`), not on permissionless `transfer` to an arbitrary recipient; or require the recipient's balance to exceed a meaningful threshold.
- Alternatively, make `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` a no-op (skip tracking) instead of reverting when at cap, and iterate position data differently — matching the "fully support a variable word count" recommendation.

### Proof of Concept
```solidity
// Foundry fork test (pseudo-implementation against deployed Pool/DepositTokens)
function test_FillTokenListGriefing() public {
    IPool pool = IPool(POOL_MAINNET);
    address victim = makeAddr("victim");

    // Attacker acquires 1 wei of each registered deposit token
    address[] memory dts = pool.getDepositTokens();
    uint256 fill = 30; // MAX_TOKENS_PER_USER
    for (uint256 i; i < fill && i < dts.length; ++i) {
        deal(dts[i], attacker, 1);
        IERC20(dts[i]).transfer(victim, 1); // adds entry to victim's list
    }

    // Victim now cannot deposit a NEW collateral type
    vm.expectRevert(Pool.UserReachedMaxTokens.selector);
    vm.prank(victim);
    IDepositToken(dts[0]).deposit(amount); // reverts if dts[0] not already tracked

    // Victim cannot mint a new synthetic debt either:
    vm.expectRevert(Pool.UserReachedMaxTokens.selector);
    vm.prank(victim);
    IDebtToken(newDebtToken).issue(1e18, victim);
}
```
Steps: fork mainnet/optimism, enumerate `pool.getDepositTokens()`, dust-transfer each to the victim until `debtTokensOfAccount + depositTokensOfAccount == 30`, then show `issue`/`deposit` revert with `UserReachedMaxTokens` and that a worsening oracle price makes the victim liquidatable while top-up is blocked.
