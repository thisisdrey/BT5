### Title
Unrestricted `deposit(onBehalfOf_)` and dust `transfer` let any user fill a victim's deposit-token list to the `MAX_TOKENS_PER_USER` cap, DoS-ing their deposits - (File: contracts/DepositToken.sol)

### Summary
`DepositToken.deposit(uint256, address onBehalfOf_)` mints deposit tokens to an arbitrary beneficiary chosen by the caller, and `transfer`/`transferFrom` deliver tokens to any recipient. Both paths call `Pool.addToDepositTokensOfAccount(recipient)` whenever the recipient's balance transitions from zero. That list is bounded by `MAX_TOKENS_PER_USER`; once full, any further first-touch mint/transfer reverts. An unprivileged attacker can therefore deposit/transfer dust of every registered deposit token to a target account, permanently (until the victim empties one) blocking the victim's deposits of new collateral types — mirroring the BookStack bug class of unauthenticated public forms causing targeted DoS on arbitrary users.

### Finding Description
- `DepositToken.deposit` accepts an unrestricted `onBehalfOf_` parameter and mints to it (DepositToken.sol:211-237). There is no consent, allowlist, or self-only check.
- `DepositToken.transfer`/`transferFrom` only check the *sender's* unlocked balance (`_revertIfLocked` on sender), never the recipient (DepositToken.sol:348-376).
- `_mint` and `_transfer` call `pool.addToDepositTokensOfAccount(account)` when the recipient's balance was zero (DepositToken.sol:486-488, 518-520).
- In `Pool.sol`, `addToDepositTokensOfAccount` reverts once `depositTokensOfAccount[account]` reaches `MAX_TOKENS_PER_USER`, so the enclosing deposit/transfer/seize reverts.

Attack path:
1. Attacker obtains dust amounts of each underlying and calls `pool`-registered `DepositToken.deposit(1, victim)` (or `transfer(victim, 1)`) for every deposit token the victim doesn't hold.
2. Victim's `depositTokensOfAccount` set is filled to `MAX_TOKENS_PER_USER` with attacker-chosen tokens.
3. Any subsequent `deposit(amount, victim)` or `transfer`/`seize` crediting a *new* deposit token to the victim reverts.

### Impact Explanation
Targeted denial of service against a chosen account: the victim cannot receive deposits (including deposits made by themselves via `deposit(amount_, victim)`), cannot receive transfers of new deposit tokens, and — critically — cannot be credited with seized collateral if a liquidator routes `to_` = a new token to them; more importantly it blocks the victim adding new collateral types, which is their main defense against liquidation when positions deteriorate. Attacker cost is dust token amounts plus gas; no privileged role required. Severity is griefing/temporary freezing of user functionality rather than direct theft.

### Likelihood Explanation
Fully permissionless: any EOA can call `deposit`/`transfer`. Requires the victim to currently hold fewer than `MAX_TOKENS_PER_USER` distinct deposit tokens and the pool to have enough registered deposit tokens to fill the list. Cost scales with token count but each entry needs only 1 wei of underlying. The victim can mitigate by fully emptying one position (transferring/burning a deposit token to zero), so the DoS is temporary once the victim pays gas to clear an entry — but each `deposit` attempt reverts until then.

### Recommendation
- Restrict `deposit`'s `onBehalfOf_` to the caller (i.e., drop the parameter or require `onBehalfOf_ == _msgSender()`), and/or
- Track per-account deposit-token membership separately from balance-based list insertion — e.g., do not revert in `addToDepositTokensOfAccount` on cap reached (ignore the add), or allow removals to be triggered so forced dust entries can be evicted cheaply, or
- Revert on transfers to recipients whose set is full but keep `deposit` self-only so attackers cannot populate the list via mint.

### Proof of Concept
Foundry-style sketch:

```solidity
// Assume pool has N registered DepositTokens and victim holds 0 of them.
// MAX_TOKENS_PER_USER = 10 (illustrative).
function test_fillVictimList() public {
    address victim = address(0xBEEF);
    for (uint i; i < depositTokens.length; ++i) {
        IERC20 underlying = depositTokens[i].underlying();
        deal(address(underlying), attacker, 1);
        vm.startPrank(attacker);
        underlying.approve(address(depositTokens[i]), 1);
        depositTokens[i].deposit(1, victim); // adds token to victim's list
        vm.stopPrank();
    }
    assertEq(pool.depositTokensOfAccount(victim).length, MAX_TOKENS_PER_USER);

    // Victim (or anyone) depositing a token the victim doesn't yet hold reverts:
    vm.expectRevert(); // MaxTokensPerUserReached in addToDepositTokensOfAccount
    someNewDepositToken.deposit(1 ether, victim);
}
```

Note: I could not fully verify the exact revert name/`MAX_TOKENS_PER_USER` constant value inside `Pool.addToDepositTokensOfAccount` (grep confirmed the function exists in `contracts/Pool.sol` but the truncated body wasn't shown); the mechanism described follows from `DepositToken.sol` calling it unconditionally on first-touch mint/transfer.
