## Title
Malicious maker order causes uncaught `ArithmeticException` to abort entire batch match in `MarketSellAssetActuator.execute()`, permanently blocking the order book - (File: `actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java`)

### Summary
`MarketSellAssetActuator.execute()` processes a taker's sell order by matching it against up to `MAX_MATCH_NUM` (20) independent, unrelated maker orders resting in the order book within a single atomic transaction [1](#0-0) . If crediting any single maker in that batch fails with an uncaught `ArithmeticException`, the whole batch — including matches already computed against other, unrelated makers — is discarded, exactly mirroring the "one failing operation reverts the whole batch" pattern from the external report.

### Finding Description
The taker's `execute()` calls `matchOrder()`, which iterates through the maker order book at the best price(s) and calls `matchSingleOrder()` for each maker, up to `MAX_MATCH_NUM` matches, all within one execute call [2](#0-1) . For each successful match, tokens are credited to the maker via `addTrxOrToken(makerOrderCapsule, makerBuyTokenQuantityReceive)` [3](#0-2) , which calls `AccountCapsule.addAssetAmountV2()` [4](#0-3) .

`addAssetAmountV2()` uses `addExact(currentAmount, amount, disableJavaLangMath)`, which throws an unchecked `ArithmeticException` on `long` overflow [5](#0-4) . Critically, `execute()`'s catch clause only handles `ItemNotFoundException`, `InvalidProtocolBufferException`, `BalanceInsufficientException`, and `ContractValidateException` — `ArithmeticException` is **not** caught [6](#0-5) . Other actuators in the codebase (`ParticipateAssetIssueActuator`, `ExchangeInjectActuator`) explicitly catch `ArithmeticException` for this exact overflow scenario, confirming this is a known-relevant failure mode that was simply omitted from `MarketSellAssetActuator`'s catch list.

An unprivileged order placer can pre-load their own account's asset balance to near `Long.MAX_VALUE` for a specific token (via repeated legitimate `TransferAsset`/self-trades) and then post a resting sell order (maker) for that token pair at the best price. Any subsequent unrelated taker whose `MarketSellAssetContract` matches against this poisoned maker order will trigger the overflow in `addAssetAmountV2()`, throwing an uncaught `ArithmeticException` that unwinds out of `execute()`, aborting the *entire* transaction — including all matches against other unrelated, healthy makers that were already computed in the same `matchOrder()` loop, and the order/price-book state updates (removal of consumed maker orders, `pairPriceToOrderStore` updates) that were pending in that same in-memory pass.

### Impact Explanation
Because the transaction fully reverts, the poisoned maker order is never removed from the order book (removal only happens on the success path, in the same call that fails). If this poisoned order sits at or ahead of the best price for its pair, it can permanently block matching for any taker attempting to trade at or through that price level, denying service to all legitimate participants trying to trade that asset pair on the decentralized exchange feature — a form of permanent freezing/denial of trading liquidity reachable by any unprivileged asset holder who places orders (an explicitly in-scope "order placer" role).

### Likelihood Explanation
Likelihood is Medium-High: any account can accumulate a large TRC10 asset balance (assets can be self-issued and freely transferred/traded to inflate one address's holdings near `Long.MAX_VALUE`), and posting a maker order costs only the standard `MarketSellFee` [7](#0-6) . No special privilege, witness/SR access, or off-chain component is required — only the market feature being enabled (`supportAllowMarketTransaction`).

### Recommendation
In `MarketSellAssetActuator.execute()`, add `ArithmeticException` (and any other unchecked exceptions from balance/asset arithmetic) to the caught exception types so a single overflowing maker credit fails only that specific match/transaction cleanly with `ContractExeException`, rather than allowing an uncaught runtime exception to propagate. Additionally, consider validating maker/taker post-match balances against overflow *before* committing state changes, or isolating maker updates so a bad maker order can be skipped/removed rather than blocking the entire order book.

### Proof of Concept
1. Attacker account A repeatedly transfers/self-issues TRC10 token X into its own balance until it holds a value close to `Long.MAX_VALUE`.
2. Attacker A places a `MarketSellAssetContract` maker order selling token Y for token X at the best available price, resting in the order book (`addOrder`/`createAndSaveOrder`).
3. Any unrelated user B submits a `MarketSellAssetContract` to sell token X for token Y that matches A's resting order.
4. During `matchOrder()` → `matchSingleOrder()` → `addTrxOrToken(makerOrderCapsule, ...)` → `AccountCapsule.addAssetAmountV2()`, crediting token X to A's already near-max balance triggers `addExact()` overflow, throwing `ArithmeticException` [8](#0-7) .
5. `execute()`'s catch block does not catch `ArithmeticException` [6](#0-5) , so B's entire transaction reverts, and any other unrelated makers B's order would have matched against in the same call are also rolled back. A's poisoned order remains in the book, indefinitely blocking future takers at that price.

**Note on uncertainty:** I was not able to fully trace, within the available context, exactly how the top-level `Manager`/actuator dispatch loop handles an uncaught `RuntimeException` (e.g., whether it is caught generically as a transaction failure or has broader effects on block processing); this would benefit from further verification via a Devin session with full repository access if a more precise characterization of the propagation is needed.

  @Override
  public boolean execute(Object object) throws ContractExeException {
    initStores();

    TransactionResultCapsule ret = (TransactionResultCapsule) object;
    if (Objects.isNull(ret)) {
      throw new RuntimeException(TX_RESULT_NULL);
    }

    long fee = calcFee();

    try {
      final MarketSellAssetContract contract = this.any
          .unpack(MarketSellAssetContract.class);

      AccountCapsule accountCapsule = accountStore
          .get(contract.getOwnerAddress().toByteArray());

      sellTokenID = contract.getSellTokenId().toByteArray();
      buyTokenID = contract.getBuyTokenId().toByteArray();
      sellTokenQuantity = contract.getSellTokenQuantity();
      buyTokenQuantity = contract.getBuyTokenQuantity();
      MarketPrice takerPrice = MarketPrice.newBuilder()
          .setSellTokenQuantity(sellTokenQuantity)
          .setBuyTokenQuantity(buyTokenQuantity).build();

      // fee
      accountCapsule.setBalance(accountCapsule.getBalance() - fee);
      // add to blackhole address
      if (dynamicStore.supportBlackHoleOptimization()) {
        dynamicStore.burnTrx(fee);
      } else {
        adjustBalance(accountStore, accountStore.getBlackhole(), fee);
      }
      // 1. transfer of balance
      transferBalanceOrToken(accountCapsule);

      // 2. create and save order
      MarketOrderCapsule orderCapsule = createAndSaveOrder(accountCapsule, contract);

      // 3. match order
      matchOrder(orderCapsule, takerPrice, ret, accountCapsule);

      // 4. save remain order into order book
      if (orderCapsule.getSellTokenQuantityRemain() != 0) {
        saveRemainOrder(orderCapsule);
      }

      orderStore.put(orderCapsule.getID().toByteArray(), orderCapsule);
      accountStore.put(accountCapsule.createDbKey(), accountCapsule);

      ret.setOrderId(orderCapsule.getID());
      ret.setStatus(fee, code.SUCESS);
    } catch (ItemNotFoundException
        | InvalidProtocolBufferException
        | BalanceInsufficientException
        | ContractValidateException e) {
      logger.debug(e.getMessage(), e);
      ret.setStatus(fee, code.FAILED);
      throw new ContractExeException(e.getMessage());
    }

    return true;
  }

    while (takerCapsule.getSellTokenQuantityRemain() != 0) {

  public boolean addAssetAmountV2(byte[] key, long amount,
      DynamicPropertiesStore dynamicPropertiesStore, AssetIssueStore assetIssueStore) {
    importAsset(key);
    boolean disableJavaLangMath = dynamicPropertiesStore.disableJavaLangMath();
    //key is token name
    if (dynamicPropertiesStore.getAllowSameTokenName() == 0) {
      Map<String, Long> assetMap = this.account.getAssetMap();
      AssetIssueCapsule assetIssueCapsule = assetIssueStore.get(key);
      String tokenID = assetIssueCapsule.getId();
      String nameKey = ByteArray.toStr(key);
      Long currentAmount = assetMap.get(nameKey);
      if (currentAmount == null) {
        currentAmount = 0L;
      }
      this.account = this.account.toBuilder()
          .putAsset(nameKey, addExact(currentAmount, amount, disableJavaLangMath))
          .putAssetV2(tokenID, addExact(currentAmount, amount, disableJavaLangMath))
          .build();
    }
    //key is token id
    if (dynamicPropertiesStore.getAllowSameTokenName() == 1) {
      String tokenIDStr = ByteArray.toStr(key);
      Map<String, Long> assetMapV2 = this.account.getAssetV2Map();
      Long currentAmount = assetMapV2.get(tokenIDStr);
      if (currentAmount == null) {
        currentAmount = 0L;
      }
      this.account = this.account.toBuilder()
          .putAssetV2(tokenIDStr, addExact(currentAmount, amount, disableJavaLangMath))
          .build();
    }
    return true;
  }
