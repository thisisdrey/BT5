### Title
Underwater positions can never be fully liquidated — `AmountIsTooHigh` / `RemainingDebtIsLowerThanTheFloor` leave permanent bad debt — (File: contracts/Pool.sol)

### Summary
In Exactly, a max-repay→principal conversion rounded down and left dust that blocked `clearBadDebt()`. The same bug class exists in Metronome with different mechanics: `Pool.liquidate` reverts with `AmountIsTooHigh` whenever the collateral to seize exceeds the account's `DepositToken` balance, and reverts with `RemainingDebtIsLowerThanTheFloor` whenever the residual debt lands in `(0, debtFloorInUsd)`. Combined with the `maxLiquidable` cap and `wadMul`-rounded seize quotes, there is a reachable state where no `amountToRepay_` value succeeds while debt remains > 0. Metronome has no `clearBadDebt`-equivalent at all, so the residual debt — and the unbacked synthetic supply it notionally collateralizes — stays on the books permanently.

### Finding Description
`Pool.liquidate` (contracts/Pool.sol:537-596) enforces three conditions that compose badly:

1. `amountToRepay_.wadDiv(_debtTokenBalance) > maxLiquidable` → `AmountGreaterThanMaxLiquidable` (line 567). If `maxLiquidable < 1e18`, a single call can never repay 100% of the debt.
2. If `debtFloorInUsd > 0`, a repayment leaving `_newDebtInUsd` in `(0, debtFloorInUsd)` reverts (lines 571-578). Partial liquidation must therefore either fully zero the debt or leave at least the floor.
3. `(_totalSeized, ...) = quoteLiquidateOut(...)` then `if (_totalSeized > depositToken_.balanceOf(account_)) revert AmountIsTooHigh()` (lines 581-585). The seize amount includes the liquidator incentive, so once a position is underwater the USD value that must be seized exceeds the collateral value; the liquidator can only repay an amount whose rounded seize fits inside the remaining balance.

Because `quoteLiquidateOut` computes `_totalSeized` via `wadMul`-rounded oracle quotes scaled by `(1 + liquidatorIncentive + fee)`, the mapping `amountToRepay_ → _totalSeized` is stepwise: for an arbitrary collateral balance there is generally no `amountToRepay_` making `_totalSeized == balance` exactly, and full repayment of the debt always requires seizing *more* than the balance (incentive margin). The liquidator therefore repays the largest amount whose seize fits, draining the collateral to dust (or zero) while leaving residual debt. Every subsequent `liquidate` call then reverts: any nonzero `amountToRepay_` yields `_totalSeized > remainingBalance` (`AmountIsTooHigh`), and any partial repay that would fit leaves `_newDebtInUsd < debtFloorInUsd` (`RemainingDebtIsLowerThanTheFloor`). There is no socialization or `clearBadDebt` path — `IDebtToken.burn` for the residual amount is only callable via `liquidate`/`repay` flows that all fail.

### Impact Explanation
Permanent protocol insolvency accounting: once a position goes underwater (interest accrual via `DebtToken.accrueInterest` and/or collateral price decline — both reachable without any privileged action), its collateral is fully drained but residual `DebtToken` balance can never be extinguished. The corresponding `SyntheticToken` supply remains outstanding with no backing, i.e. bad debt is locked into the protocol's solvency invariant `collateralValue ≥ debtValue` forever. Unlike Exactly, there is not even a governance escape hatch — the debt simply cannot be removed by anyone.

### Likelihood Explanation
Requires only ordinary market conditions: a borrower whose collateral underperforms the synthetic asset or who lets interest accrue past the collateral value. No attacker action is needed beyond opening a normal leveraged/borrow position via public `DepositToken.deposit` + `SyntheticToken` minting and waiting; any unprivileged liquidator then hits the wall. The probability scales with how close `debtFloorInUsd` and `maxLiquidable` are configured and how volatile collateral is; with `debtFloorInUsd == 0` and `maxLiquidable == 1e18` the residual shrinks to rounding dust but the `AmountIsTooHigh` block still prevents zeroing the debt once collateral is exhausted.

### Recommendation
In `liquidate`, cap `_totalSeized`/`amountToRepay_` at the account's available collateral instead of reverting on `AmountIsTooHigh` when the position is underwater, or add a `clearBadDebt`-style path that burns residual `DebtToken` when the account's total collateral is zero (or below a dust threshold), accepting the rounding loss explicitly rather than reverting.

### Proof of Concept
Foundry fork (mainnet), against deployed `Pool`:

```solidity
function test_BadDebtStuckAfterCollateralDrained() external {
    // 1. BOB deposits vaUSDC-like DepositToken and mints msUSD near max LTV
    depositToken.deposit(BOB_COLLATERAL);           // public
    pool.mint(msUSD, borrowAmount);                 // public, healthy at t0

    // 2. Time passes / collateral price falls so debtUSD > collateralUSD
    vm.warp(block.timestamp + 365 days);            // interest accrual
    // (or mock MasterOracle price drop on fork)

    // 3. Liquidator approves msUSD and attempts full repay
    uint256 debt = debtToken.balanceOf(BOB);
    vm.expectRevert(Pool.AmountIsTooHigh.selector);
    pool.liquidate(msUSD, BOB, debt, depositToken); // seize > balance

    // 4. Liquidator repays max amount whose seize fits -> drains collateral
    uint256 repayMax = _binarySearchMaxRepay();     // largest repay with _totalSeized <= balance
    pool.liquidate(msUSD, BOB, repayMax, depositToken);
    assertEq(depositToken.balanceOf(BOB), 0);
    assertGt(debtToken.balanceOf(BOB), 0);          // residual bad debt

    // 5. No further liquidation can succeed — bad debt is permanent
    vm.expectRevert();                              // AmountIsTooHigh or RemainingDebtIsLowerThanTheFloor
    pool.liquidate(msUSD, BOB, debtToken.balanceOf(BOB), depositToken);
}
```

Caveat: I verified `liquidate`'s guard logic directly (contracts/Pool.sol:553-593), but did not fully read `quoteLiquidateOut`; the argument assumes it computes `_totalSeized = oracleQuote(amountToRepay_).wadMul(1 + incentive + fee)` — consistent with the quote naming and the seize-fee split at lines 589-593. Deployed `debtFloorInUsd`/`maxLiquidable` values per chain were not confirmed; with `debtFloorInUsd > 0` the stuck region is larger, but the `AmountIsTooHigh` revert on exhausted collateral holds regardless.
