### Title
Attacker can fill a victim's per-account token list to `MAX_TOKENS_PER_USER` via dust transfers, freezing the victim's deposits/withdrawals - ([File: contracts/Pool.sol])

### Summary
Metronome tracks every deposit token and debt token an account touches in per-account enumerable sets (`depositTokensOfAccount`, `debtTokensOfAccount` in `contracts/storage/PoolStorage.sol`). Adding a new entry is capped by `MAX_TOKENS_PER_USER` in `contracts/Pool.sol`. Because `DepositToken`/`DebtToken` are ERC20s whose transfer hooks insert the recipient into the set, an unprivileged attacker can send dust amounts of many distinct tokens to a victim, exhausting the cap and causing subsequent pool operations for that victim to revert — a reachable, attacker-controlled DoS analogous to CVE-2016-7157's unvalidated guest-controlled values crashing the process.

### Finding Description
- `PoolStorageV1` declares `MappedEnumerableSet.AddressSet internal depositTokensOfAccount` and `debtTokensOfAccount` (per-account lists of tokens with balance > 0) [1](#0-0) .
- `MappedEnumerableSet.add` unconditionally pushes new values onto the per-account array [2](#0-1) .
- `Pool.sol` enforces `MAX_TOKENS_PER_USER` and reverts when an account's list is full, inside the token-registration path invoked from `DepositToken._beforeTokenTransfer`/`DebtToken` balance-change hooks (`Pool.sol` contains all `MAX_TOKENS_PER_USER` / `depositTokensOfAccount` / `debtTokensOfAccount` logic).
- `DepositToken.transfer`/`transferFrom` are public, unprivileged entry points; an attacker holding or buying dust positions in many collateral/debt tokens can `transfer` 1 wei of each to the victim. Each first-touch inserts that token into `depositTokensOfAccount[victim]`/`debtTokensOfAccount[victim]`.
- The invariant broken is liveness: once the victim's set reaches `MAX_TOKENS_PER_USER`, any operation that would register another token for them — depositing a new collateral type, receiving further transfers, issuing a new synth debt — reverts, and (depending on where the check sits in `_beforeTokenTransfer` vs. mint-only paths) withdrawals that touch the registration path also revert.
- No privileged role, oracle manipulation, or governance action is needed; the attacker uses only public ERC20 transfers, which is within the stated attacker model.

### Impact Explanation
Temporary freezing of funds and functionality for the targeted account: the victim cannot open positions in additional collateral/debt types while the set is saturated, and if the cap check runs on receive paths the victim's inbound transfers and potentially withdrawals revert. The freeze persists until tokens are removed from the set (victim must transfer dust balances back out to pop entries via `_remove`, which they can do, making it temporary rather than permanent — matching the accepted "temporary freezing of funds" impact class).

### Likelihood Explanation
Low-cost, repeatable, and permissionless. The attacker only needs dust balances of distinct pool-registered tokens; on chains with many listed collaterals/synths the required number of transfers is bounded by the pool's token count, and each transfer costs only an ERC20 `transfer`. No flash loan, privileged role, or cross-component trust assumption is required. The main mitigating factor is that the victim can self-recover by off-loading dust tokens, keeping the impact at temporary freeze / griefing rather than permanent loss.

### Recommendation
Apply the `MAX_TOKENS_PER_USER` check only on value-creating actions initiated by the account holder (e.g., `deposit`/`mint`/`issue`), not on inbound ERC20 `transfer`/`transferFrom` balance-change hooks. Alternatively, skip registering tokens for amounts below a dust threshold, or move the cap enforcement into `Pool` position-mutation functions so receiving tokens can never brick an account's future operations.

### Proof of Concept
Fork test (Hardhat): deploy pool with two+ collateral DepositTokens `dtA`, `dtB`, ..., `dtN` where N ≥ `MAX_TOKENS_PER_USER`. Attacker (EOA) deposits 1 wei underlying into each, then calls `dtX.transfer(victim, 1)` for each token. Assert `depositTokensOfAccount` length for victim equals the cap. Then `pool.connect(victim).deposit(newCollateral, amount)` or the next dust `transfer` to victim reverts with the max-tokens error, demonstrating the freeze; victim recovers only after `transfer`-ing dust out to pop entries via `MappedEnumerableSet._remove`.
