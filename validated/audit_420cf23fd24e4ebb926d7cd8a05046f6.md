### Title
`RewardsDistributor._calculateTokenDelta` accrues rewards equal to the full token balance for pre-existing holders because it uses `>` instead of `>=` when back-filling the account index - (contracts/RewardsDistributor.sol:225)

### Summary
The external report's bug class is a boundary check that wrongly treats a legitimate "zero/baseline" value as "undefined," skipping logic that should run. The Metronome analog lives in `RewardsDistributor._calculateTokenDelta`. When a reward token starts being tracked, `tokenStates[token_].index` is initialized to `INITIAL_INDEX` (`1e18`). The code back-fills `accountIndexOf` only when `_tokenIndex > INITIAL_INDEX`; when the index equals `INITIAL_INDEX` exactly (i.e., the token was just activated and no rewards have accrued yet), an account with `accountIndexOf == 0` keeps index `0`, producing `_deltaIndex = 1e18` and `tokensDelta = balance * 1` — the account's entire token balance booked as claimable reward.

### Finding Description
In `_calculateTokenDelta` (contracts/RewardsDistributor.sol:217-231):

```solidity
uint256 _accountIndex = accountIndexOf[token_][account_];

if (_accountIndex == 0 && _tokenIndex > INITIAL_INDEX) {
    _accountIndex = INITIAL_INDEX;
}

uint256 _deltaIndex = _tokenIndex - _accountIndex;
_tokensDelta = token_.balanceOf(account_).wadMul(_deltaIndex);
```

A token's index is set to `INITIAL_INDEX` the first time a non-zero speed is configured in `_updateTokenSpeed` (lines 296-299). At that moment every existing holder has `accountIndexOf[token_][account] == 0`, because `updateBeforeMintOrBurn`/`updateBeforeTransfer`/`claimRewards` all skip accrual while `tokenStates[token_].index == 0` (lines 156, 176, 187). When accrual is first evaluated for such an account, `_tokenIndex == INITIAL_INDEX`, so the guard `_tokenIndex > INITIAL_INDEX` fails, `_accountIndex` remains `0`, `_deltaIndex = 1e18`, and `_tokensDelta = balanceOf(account).wadMul(1e18) = balanceOf(account)`.

The same flaw is reachable on every later claim for any account whose stored index is still `0` while the token index sits exactly at `INITIAL_INDEX` (e.g., reward speed set but no time elapsed / supply zero rounding), and more generally the comparison should cover the "index is initialized" case, not only "index has moved past initial."

### Impact Explanation
Unprivileged theft of unclaimed yield. An attacker can:
1. Deposit into a pool so they hold `DepositToken` balance while its `RewardsDistributor` tracking is off (index 0 → all `updateBefore*` hooks are no-ops).
2. Wait for (or front-run) the governor/keeper calling `updateTokenSpeed`/`syncTokenSpeed`, which sets `tokenStates.index = INITIAL_INDEX`.
3. Call `claimRewards(attacker, [depositToken])` — a public function accepting arbitrary accounts — which runs `_updateTokensAccruedOf` and books `tokensAccruedOf[attacker] += balance`, then `_transferRewardIfEnoughTokens` pays out real reward tokens.

The attacker receives reward tokens equal to their full deposit balance for zero elapsed time. Repeating across accounts and each newly activated reward token drains the distributor's reward-token balance, stealing yield meant for honest suppliers/borrowers.

### Likelihood Explanation
Likelihood is medium-high. The trigger conditions are ordinary protocol states: a distributor begins tracking a token that already has holders (speed set on an existing DepositToken, or a distributor registered after deposits exist), or an attacker front-runs the speed-setting transaction with a deposit. `syncTokenSpeed` (called by a permissionless-gated keeper path) and `updateTokenSpeeds` both hit `_updateTokenSpeed`, which sets `index = INITIAL_INDEX` without touching `accountIndexOf` of existing holders. No privileged attacker is needed: `claimRewards(address[], IERC20[])` is public and iterates arbitrary accounts. The only prerequisite is that `accountIndexOf` be `0` for an account holding a non-zero balance at the moment the token index equals `INITIAL_INDEX` — which is guaranteed for all pre-existing holders by construction.

### Recommendation
In `_calculateTokenDelta`, back-fill the account index whenever the token index is initialized, not only when it has advanced past the initial value:

```solidity
if (_accountIndex == 0 && _tokenIndex >= INITIAL_INDEX) {
    _accountIndex = _tokenIndex; // or INITIAL_INDEX, with >= on _tokenIndex
}
```

Equivalently, initialize `accountIndexOf[token][account]` to the current token index at activation time for all existing holders (impractical), or record a per-account "initialized" flag instead of relying on `0`/`INITIAL_INDEX` boundary comparisons. The core fix mirrors the report: do not treat the boundary value (`index == INITIAL_INDEX`, analog of "tick == 0") as "not yet defined."

### Proof of Concept
Foundry-style reproduction (no fork of external state needed; uses repo mocks):

```solidity
// Setup: Pool, DepositToken (msUSD-style), RewardsDistributor registered on pool.
// 1. Attacker deposits underlying -> receives depositToken balance B.
//    tokenStates[depositToken].index == 0, so updateBeforeMintOrBurn no-ops;
//    accountIndexOf[depositToken][attacker] == 0.
// 2. Governor calls distributor.updateTokenSpeed(depositToken, speed > 0)
//    -> tokenStates[depositToken] = {index: 1e18, timestamp: now}.
// 3. Attacker calls distributor.claimRewards(attacker, [depositToken]).
//    _updateTokenIndex: deltaTimestamps == 0 -> index stays 1e18.
//    _updateTokensAccruedOf -> _calculateTokenDelta:
//      _accountIndex = 0; _tokenIndex = 1e18;
//      guard (0 == 0 && 1e18 > 1e18) is false -> _accountIndex stays 0;
//      _deltaIndex = 1e18; _tokensDelta = B.wadMul(1e18) = B.
//    tokensAccruedOf[attacker] = B; distributor transfers min(B, rewardBalance)
//    reward tokens to attacker.
// Assert: attacker received ~B reward tokens with zero seconds of accrual.
```

Variant without governance timing: attacker deposits, an existing-tracked token's index is exactly `INITIAL_INDEX` in the same block its speed was set (e.g., `syncTokenSpeed` followed by a same-block `claimRewards`), producing the identical `_tokenIndex == INITIAL_INDEX && _accountIndex == 0` path.

Note: I was unable to fully verify whether any deposit/mint path forces `accountIndexOf` initialization for pre-existing balances (the hooks are all gated on `index > 0`, so they do not), and I could not inspect test files for coverage of this scenario; the code trace above is nonetheless self-contained in `RewardsDistributor.sol`.
