## Title
Neighbor-of-neighbor and pingback HandshakeAccept processing stores an attacker-chosen `addrbytes`/`port` into the PeerDB frontier without checking it against the address actually dialed - ([File: stackslib/src/net/neighbors/db.rs])

### Summary
`add_or_schedule_replace_neighbor` keys the PeerDB record entirely off the self-reported `handshake.addrbytes`/`handshake.port` fields (via `Neighbor::load_and_update` → `NeighborKey::from_handshake`), which are inside the signed payload but are never checked against the address our node actually connected to (`na`/`naddr`) when it is invoked from `handle_neighbor_handshake_accept` (`stackslib/src/net/neighbors/walk.rs:1092-1124`) and `pingback_handshakes_try_finish` (`stackslib/src/net/neighbors/walk.rs:1683-1725`). Only the direct-cur_neighbor handshake path (`handle_handshake_accept`, `walk.rs:676-715`) enforces `neighbor_from_handshake.addr == self.cur_neighbor.addr`; the neighbor-of-neighbor and pingback paths lack this equality check.

### Finding Description
The equality the question is really about is: *the address written to PeerDB (`NeighborKey::from_handshake` → `addrbytes`/`port` from `HandshakeData`) must equal the address of the socket we actually validated the signature over/connected to*. A valid `secp256k1` signature over a `HandshakeAccept` only proves that the keyholder authored that exact byte sequence — it says nothing about whether the `addrbytes`/`port` field inside it corresponds to the TCP peer we dialed. That check has to be done explicitly by the caller.

`neighbor_handshakes_begin` (`walk.rs:979-1069`) takes `NeighborAddress` entries (`na`) reported by `cur_neighbor` via `GetNeighbors`, and calls `self.comms.neighbor_session_begin(network, &na)`, which dials `na.addrbytes:na.port` directly (`comms.rs: neighbor_session_begin_only`, using `na.public_key_hash` only for the pubkey-collision check, not address). Whatever server answers at that address can freely set `HandshakeData.addrbytes`/`port` to *any* value (e.g. a victim's real IP:port) while signing with its own private key over its own self-chosen payload — the signature is self-consistent and passes `validate_handshake`/`verify_secp256k1` in `chat.rs:1047-1127`.

`neighbor_handshakes_try_finish` → `handle_neighbor_handshake_accept` (`walk.rs:1092-1124`) then calls `add_or_schedule_replace_neighbor` (`db.rs:368-426`) with that `HandshakeData` directly, with **no check that `data.handshake.addrbytes`/`port` matches `na`/`naddr`**. Inside, `Neighbor::load_and_update` (`chat.rs:475-516`) computes `let addr = NeighborKey::from_handshake(peer_version, network_id, handshake_data);` from the attacker-controlled fields, and the resulting `Neighbor` is unconditionally `save`d/`save_update`d into PeerDB (`db.rs:387-408`), inserting/updating a frontier row keyed at the attacker-chosen address.

The same gap exists in `pingback_handshakes_try_finish` (`walk.rs:1683-1725`): `check_handshake_pubkey_hash` (`walk.rs:1664-1680`) only verifies the reported public key hash matches the expected `naddr.public_key_hash`; it never compares `data.handshake.addrbytes`/`port` to `naddr.addrbytes`/`port` before calling `add_or_schedule_replace_neighbor`.

By contrast, the direct cur_neighbor handshake path (`handle_handshake_accept`, `walk.rs:676-715`) does have the guard: `if self.walk_outbound && neighbor_from_handshake.addr != self.cur_neighbor.addr { return Err(...) }`. This shows the codebase is aware such a check is necessary, but it was not applied uniformly to the neighbor-of-neighbor/pingback code paths that also call `add_or_schedule_replace_neighbor`.

### Impact Explanation
An attacker who runs one node that gets referenced as a "neighbor" (either by legitimately being a listed neighbor of some node being crawled, or by being pinged back after connecting inbound) can, upon receiving our Handshake, reply with a `HandshakeAccept`/`StackerDBHandshakeAccept` whose `HandshakeData.addrbytes`/`port` point at an arbitrary third-party IP:port while `node_public_key` is the attacker's own key. This gets written into our PeerDB frontier as if that third-party address had been contacted and cryptographically validated. Because frontier/PeerDB entries are later served to other peers via `GetNeighbors`/`Neighbors` responses (self-reported `addrbytes`/pubkey), this forged (address, pubkey) binding can propagate to other nodes in the gossip network, matching the "unauthenticated/unauthorized write to state" and "network-wide propagation of forged data" Critical categories. It is repeatable per handshake round and costs the attacker only a single reachable node.

### Likelihood Explanation
No privileged role or secret is required — the attacker just needs to (a) be discoverable as a neighbor-of-a-neighbor (trivial: gossip protocol invites this by design, or become a pingback target by connecting in) and (b) answer with a validly self-signed `HandshakeAccept` containing arbitrary `addrbytes`/`port`. Reachability of the P2P port is a stated precondition and is satisfied. This is straightforward and cheap to trigger repeatedly during normal neighbor-walk operation.

### Recommendation
In `handle_neighbor_handshake_accept` (`walk.rs:1092`) and in `pingback_handshakes_try_finish` (`walk.rs:1683`), before calling `add_or_schedule_replace_neighbor`/`check_handshake_pubkey_hash`, add an explicit equality check comparable to the one in `handle_handshake_accept`: verify `data.handshake.addrbytes == naddr.addrbytes && data.handshake.port == naddr.port` (allowing the same private/anynet address substitution logic already used elsewhere), and reject/drop the reply otherwise instead of persisting it to PeerDB.

### Proof of Concept
Rust test plan in `stackslib::net::neighbors::db` / `walk.rs` test harness:
1. Set up `peer_1` (victim node under test) and two additional `TestPeer`s: `attacker` and `third_party` (the address we want forged into peer_1's PeerDB, never actually contacted by peer_1).
2. Configure `cur_neighbor` for peer_1's walk such that `attacker` is discoverable as a "neighbor of cur_neighbor" (i.e., its `NeighborAddress` shows up in `pending_neighbor_addrs` feeding `neighbor_handshakes_begin`).
3. Have `attacker`'s conversation, when replying to peer_1's `Handshake`, construct and sign a `HandshakeAccept`/`HandshakeData` with `addrbytes`/`port` set to `third_party`'s address/port but `node_public_key` set to attacker's own key (a validly self-signed message).
4. Drive `peer_1.network`'s walk through `neighbor_handshakes_begin`/`neighbor_handshakes_try_finish` (or directly call `PeerDBNeighborWalk::add_or_schedule_replace_neighbor` with the crafted `Preamble`/`HandshakeData`).
5. Assert: `PeerDB::get_peer(peer_1_dbconn, network_id, &third_party_addrbytes, third_party_port)` returns `Some(..)` with `public_key == attacker_pubkey`, even though peer_1 never dialed `third_party`'s address — confirming the forged frontier entry.
