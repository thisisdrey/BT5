This confirms the analog: `f.listenOut` is launched across `f.routines` goroutines (multiple concurrent readers of the same UDP socket), each calling `readOutsidePackets` → `ConnectionState.Decrypt` for the same `hostinfo.ConnectionState` concurrently. That directly parallels the "check vs. act" TOCTOU class in the external report — a value validated in one step (`Check`) can become stale before the state-changing step (`Update`) commits, because a concurrent goroutine can interleave and win the race on the same resource (there, IPT balance; here, the anti-replay window slot).### Title
Anti-replay window Check/Update race allows replayed packet acceptance - (File: connection_state.go)

### Summary
`ConnectionState.Decrypt` and `ConnectionState.VerifyRelay` split the anti-replay window's "may I accept counter *i*?" check (`Bits.Check`) and "commit counter *i* as seen" mutation (`Bits.Update`) into two separate lock/unlock sections, with the AEAD decryption happening in between while the lock is released. This is the same check-then-act (TOCTOU) pattern as the reported `getPoints()`/`takeFrom()` bug: a value is validated against shared state, the lock is released, an unrelated operation runs, and only afterward is the shared state updated — allowing a concurrent caller to interleave and invalidate the assumption the first caller relied on.

### Finding Description
`Decrypt` (and identically `VerifyRelay`) does:
1. Lock, `window.Check(messageCounter)`, unlock.
2. Run `DecryptDanger` (no lock held).
3. Lock, `window.Update(messageCounter)`, unlock. [1](#0-0) 

`Bits.Check` only inspects whether counter `i` has already been marked as received; it does not mark it itself. `Bits.Update` is what actually flips the bit for `i`. [2](#0-1) [3](#0-2) 

If two packets carrying the same `messageCounter` for the same `hostinfo.ConnectionState` are processed concurrently (e.g. by two of the `f.routines` UDP listener goroutines spun up in `Interface.run`/`listenOut`, both calling `readOutsidePackets` → `ConnectionState.Decrypt` on the same `hostinfo.ConnectionState`), both can execute step 1 (`Check`) before either has executed step 3 (`Update`). Since the bit for that counter has not yet been set by either goroutine, `Check` returns "not yet seen" to both, and both proceed to successfully decrypt and pass the packet up the stack, only serializing on `Update` afterward (where the second `Update` call will correctly report a duplicate, but only after the plaintext has already been delivered to the application/tun device once — actually twice, since each goroutine independently completes `Decrypt` and returns the plaintext to its caller in `readOutsidePackets`). [4](#0-3) [5](#0-4) 

This mirrors the report's root cause precisely: the "amount available" (whether counter *i* is still unclaimed) is validated once, an unlocked/asynchronous operation is performed, and the shared resource is only debited/marked afterward — letting a racing second request slip through on stale validation.

### Impact Explanation
A successful race lets an attacker who can duplicate/replay a captured packet twice in quick succession (e.g., via a NIC/OS-level packet duplication, a malicious upstream router, or by sending the same UDP datagram twice such that two listener goroutines pick it up nearly simultaneously) get the payload accepted and processed twice by the tunnel's data plane, defeating the intent of the anti-replay window described at the top of `bits.go` ("Bits is a sliding-window anti-replay tracker"). Depending on the packet type this results in double-delivery of application traffic to the tun device or duplicate control-plane processing (e.g., duplicate `handleOutsideMessagePacket`/`lhf.HandleRequest` invocations), i.e., a traffic/replay integrity violation reachable by a remote, unauthenticated network attacker who does not hold a CA-signed certificate — they merely need to get two copies of a legitimately-captured ciphertext frame to the victim's UDP socket.

### Likelihood Explanation
Exploitability depends on the interface being configured with multiple listener routines (`listen.routines` / `tun.routines` style multi-queue configuration, which nebula supports and documents) so that concurrent goroutines can process packets for the same `ConnectionState` at the same time, or on any other concurrent-caller path reaching `Decrypt`/`VerifyRelay` for the same peer. I was not able to fully confirm, within the available tool budget, that two independent listener goroutines can in practice receive and dispatch the *same* replayed ciphertext for the *same* `hostinfo` concurrently under nebula's socket/queue architecture (e.g., SO_REUSEPORT queue hashing may or may not route duplicate packets to different queues) — this needs to be verified with a proof-of-concept before treating it as a fully proven remote impact.

### Recommendation
Hold `decryptLock` across the entire "check → decrypt → update" sequence in both `Decrypt` and `VerifyRelay`, so that a single atomic critical section performs the replay check, decryption, and window commit, eliminating the interleaving window between `Check` and `Update`.

### Proof of Concept
Conceptual PoC (not verified end-to-end due to tool limitations):
1. Configure a nebula node with `listen.routines` (or equivalent multi-queue setting) > 1 so multiple goroutines call `listenOut`/`readOutsidePackets` concurrently.
2. Capture one legitimate encrypted data packet destined for that node from a peer.
3. Replay the exact same UDP datagram twice in immediate succession (e.g., from two sockets or via packet duplication) so both copies are picked up by different listener goroutines before either completes `ConnectionState.Decrypt`.
4. Observe both goroutines pass `Bits.Check` (since neither has called `Bits.Update` yet), both successfully `DecryptDanger`, and both deliver the plaintext to `handleOutsideMessagePacket`/tun device — i.e., the same message is processed twice despite the anti-replay window. [1](#0-0) [2](#0-1)

func (b *Bits) Update(l *slog.Logger, i uint64) bool {
	// Fast path: i is the next expected counter. Split out so the function
	// stays small and avoids paying for the slow paths' slog argument-build
	// stack frame on every call. The bit read/test/write is inlined to
	// touch the backing word once.
	if i == b.current+1 {
		pos := i & b.lengthMask
		word := pos >> 6
		mask := uint64(1) << (pos & 63)
		w := b.bits[word]
		if i > b.length && w&mask == 0 {
			b.lostCounter.Inc(1)
		}
		b.bits[word] = w | mask
		b.current = i
		return true
	}
	return b.updateSlow(l, i)
}

	var li udp.Conn
	if i > 0 {
		li = f.writers[i]
	} else {
		li = f.outside
	}

	ctCache := firewall.NewConntrackCacheTicker(f.ctx, f.l, f.conntrackCacheTimeout)
	lhh := f.lightHouse.NewRequestHandler()
	plaintext := make([]byte, udp.MTU)
	h := &header.H{}
	fwPacket := &firewall.Packet{}
	nb := make([]byte, 12, 12)

	err := li.ListenOut(func(fromUdpAddr netip.AddrPort, payload []byte) {
		f.readOutsidePackets(ViaSender{UdpAddr: fromUdpAddr}, plaintext[:0], payload, h, fwPacket, lhh, nb, i, ctCache.Get())
	})

	// An error after teardown began is shutdown noise, the closed flag covers resources
	// Close releases itself and the cancelled ctx covers ones torn down by their owners
	// reacting to it, like the user device pipes
	if err != nil && !f.closed.Load() && f.ctx.Err() == nil {
		f.l.Error("Error while reading inbound packet, closing", "error", err)
		f.onFatal(err)
	}

	f.l.Debug("underlay reader is done", "reader", i)
}
