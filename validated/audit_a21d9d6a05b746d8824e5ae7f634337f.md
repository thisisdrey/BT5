Checking `DebtToken` for stale-index behavior before minting, and how `accrueInterest` is enforced.### Title
Rewards index accrues at a stale `tokenSpeed` until keeper calls `syncTokenSpeed`, letting users over-accrued rewards drain the distributor's balance - ([File: contracts/RewardsDistributor.sol](contracts/RewardsDistributor.sol))

### Summary
`RewardsDistributor` prices its reward accrual from a locally-stored `tokenSpeeds[token_]` value that only reflects the real, external reward rate (Vesper `poolRewards().rewardRates`) when the privileged `tokenSpeedKeeper` calls `syncTokenSpeed`. There is no flag or freshness check forcing that sync before the index is advanced or rewards are claimed — the exact analog of Lido's "deposit allowed before stuck-validator update is finalized." After the upstream reward rate drops (or the period ends), the contract keeps accruing index growth at the stale, higher speed. Any unprivileged user can call `claimRewards` (or just `deposit`/`mint`/`transfer`, which trigger `updateBeforeMintOrBurn`) during the gap and crystallize an index that over-allocates reward tokens, paying out more than the external pool actually streamed.

### Finding Description
The analog to `_getDepositsAllocation` reading stale `availableValidatorsCount` is `_calculateTokenIndex` reading stale `tokenSpeeds[token_]`:

- `tokenSpeeds[token_]` is only synced to the real rate inside `syncTokenSpeed`, gated by `if (_msgSender() != tokenSpeedKeeper) revert NotTokenSpeedKeeper()` [1](#0-0) 
- The index accrues purely from stored speed and elapsed time: `_tokensAccrued = _deltaTimestamps * _speed; _ratio = _tokensAccrued.wadDiv(_totalSupply)` [2](#0-1) 
- `claimRewards` is permissionless and advances the index at whatever speed is stored, then transfers `tokensAccruedOf[account_]` [3](#0-2) 
- `_transferRewardIfEnoughTokens` pays the full accrued amount as long as the distributor's `rewardToken` balance covers it — there is no cap tying payouts to rewards actually earned upstream [4](#0-3) 

Like the Lido report, the system permits the action (claim/mint/deposit) in the window between "external state changed" (Vesper `rewardRates` dropped / `periodFinish` passed, which would make `_speed = 0` in `syncTokenSpeed`) and "internal status finalized" (keeper sync). `syncTokenSpeed` itself computes `_speed = 0` when `block.timestamp >= periodFinish`, confirming that a stale positive speed over-accrues after the real stream ends [5](#0-4) .

### Impact Explanation
The invariant broken is reward-accrual conservation: cumulative `tokensAccruedOf` must equal rewards actually streamed from Vesper. During the sync gap, the index grows at the old speed, so accounts' accrued balances exceed the real reward inflow. Early claimers — including the attacker who simply calls `claimRewards(attacker)` in the gap — withdraw real `rewardToken` balance that belongs to later claimers' unclaimed yield. This is theft of unclaimed yield: the first claimers are overpaid and later claimers' accrued amounts become unpayable (the transfer silently no-ops when balance is insufficient, so their rewards are permanently lost). No admin key, malicious oracle, or privileged role is needed by the attacker; the keeper is honest, just not instantaneous.

### Likelihood Explanation
`syncTokenSpeed` is an explicitly marked "temporary fix" driven by an external keeper, so synchronization lag between Vesper reward changes and `tokenSpeeds` updates is expected in normal operation — including the deterministic window right after `periodFinish` when the true speed is zero. Every deposit, mint, withdraw, transfer, or claim in that window finalizes accrued amounts at the wrong speed. The attacker's required action is a single public `claimRewards` call (optionally front-run/scheduled around known `periodFinish` timestamps), making this reachable by any EOA.

### Recommendation
Mirror the suggested fix from the report: prevent state-changing accrual until the external rate is reconciled. Concretely:
- Call the upstream freshness check inside `claimRewards`, `updateBeforeMintOrBurn`, and `updateBeforeTransfer` — i.e., recompute `_speed` from `IVPool.poolRewards().rewardRates`/`periodFinish` (or revert if `block.timestamp` is past `periodFinish` and `tokenSpeeds` hasn't been synced since), before advancing the index.
- Alternatively store a `lastSyncedPeriodFinish`/`rateTimestamp` and revert claims when `block.timestamp` crossed `periodFinish` without a sync, so no accrual happens on stale speed.
- In `syncTokenSpeed`, accrue the index at the old speed only up to `periodFinish` and zero afterward, rather than letting the stale rate run until the keeper call lands.

### Proof of Concept
Hardhat fork (mainnet, deployed `RewardsDistributor` for a Vesper-backed `DepositToken`):

```ts
// Setup: distributor has tokenSpeed S > 0 for msdX, rewardToken balance funded,
//        alice and attacker hold msdX.
// 1. Warp to just past Vesper IPoolRewards.periodFinish(rewardToken)
//    -> true upstream rate is now 0, but tokenSpeeds[msdX] is still S.
await time.increaseTo(periodFinish + 1 days);

// 2. Attacker claims during the unsynced window.
//    _calculateTokenIndex uses stale S for the whole day after periodFinish.
await rewardsDistributor.connect(attacker).claimRewards(attacker.address);

// 3. Keeper eventually calls syncTokenSpeed -> _speed becomes 0,
//    but the inflated index was already persisted.
await rewardsDistributor.connect(keeper).syncTokenSpeed(msdX.address);

// Assertions:
// - attacker's payout > their pro-rata share of rewards actually streamed
//   (Vesper rewardRates * treasury balance / totalSupply integrated to periodFinish).
// - sum(tokensAccruedOf) of remaining holders exceeds distributor's
//   rewardToken.balanceOf -> their claimRewards() silently pays 0
//   (_transferRewardIfEnoughTokens), i.e., yield stolen by early claimer.
```

Key checks for the PoC: `tokenSpeeds[msdX]` is unchanged until `syncTokenSpeed` runs [6](#0-5) , the index delta between `periodFinish` and the claim time is computed with the stale speed [7](#0-6) , and the payout is uncapped relative to real upstream accrual [8](#0-7) .

    function syncTokenSpeed(IDepositToken depositToken_) external {
        if (_msgSender() != tokenSpeedKeeper) revert NotTokenSpeedKeeper();

        IVPool _vPool = IVPool(address(depositToken_.underlying()));
        IPoolRewardsExt _rewards = IPoolRewardsExt(_vPool.poolRewards());

        uint256 _speed;

        if (block.timestamp < _rewards.periodFinish(address(rewardToken))) {
            _speed =
                (_rewards.rewardRates(address(rewardToken)) * _vPool.balanceOf(address(pool.treasury()))) /
                _vPool.totalSupply();
        }

        _updateTokenSpeed(IERC20(address(depositToken_)), _speed);
    }
