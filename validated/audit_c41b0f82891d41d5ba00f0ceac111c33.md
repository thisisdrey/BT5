`SlotMetadata`/`StackerDBChunkData` signatures omit the target StackerDB contract, enabling cross-contract chunk replay - ([File: libstackerdb/src/libstackerdb.rs])

### Summary
The Merkle-proof bug reported for `PerAddressTrancheVestingMerkleDistributor` boils down to a checked digest omitting a field (`tranches`) that a different, correctly-implemented sibling contract does include, so a value that should bind data to a specific context does not. The same class of fault exists in Stacks' StackerDB signature scheme: the digest that authenticates a chunk write binds only `slot_id`, `slot_version`, and `data_hash` — never the target `QualifiedContractIdentifier` (i.e. which StackerDB the chunk belongs to). Because slot assignment (`signer -> slot_id`) is frequently shared across multiple StackerDB contracts (e.g. all `signers-N-<message-id>` contracts for a given signer set), a validly-signed chunk that was broadcast for one contract can be replayed, by any remote unprivileged observer, into a *different* StackerDB contract where it still passes signature verification.

### Finding Description
`SlotMetadata::auth_digest` computes the signed/verified digest as: [1](#0-0) 

This hashes only `slot_id`, `slot_version`, and `data_hash`. It never includes the smart contract identifier of the StackerDB the chunk is destined for. `sign`/`verify` operate purely on this digest: [2](#0-1) 

The contract identifier (`smart_contract`) is passed as a separate, out-of-band argument to the storage/validation routines and is never mixed into what is actually authenticated: [3](#0-2) [4](#0-3) 

Slot ownership (which principal owns which `slot_id`) is derived from a sorted list of signer principals that is shared across *all* per-message-type contracts for a signer set. The `.signers` boot contract stores exactly one slot list per signer-set parity (`stackerdb-signer-slots-0`/`-1`) and every `signers-<set>-<message-id>` contract reads from the same shared page: [5](#0-4) 

and the test confirms the same slot assignment (sorted by signer public key) is returned identically for every `message_id` within a signer set: [6](#0-5) 

Because a signer's `slot_id` is identical across e.g. `signers-0-<BlockResponse>` and `signers-0-<StateMachineUpdate>` contracts, a signature produced by that signer for a chunk written into one of those contracts is *also* a valid signature for a chunk with the same `slot_id`/`slot_version`/`data_hash` written into the other contract — the verifying code (`SlotMetadata::verify`, used in `try_replace_chunk` and `validate_received_chunk`) has no way to distinguish the two, since the contract identity is never part of the signed material. The same applies across reward cycles that share signer-set parity (`reward_cycle % 2`), since the same `signers-<set>-*` contracts are reused for every reward cycle of that parity.

This exactly mirrors the reported bug class: an equality check (auth_digest vs. stored/expected value) silently omits a binding component that the design requires for correctness, so data legitimately signed for context A satisfies the check when replayed into context B.

### Impact Explanation
StackerDB chunk data is broadcast/gossiped in the clear over the P2P network (`StackerDBPushChunkData`, `StackerDBChunkInv`), so any unprivileged network observer can capture a validly-signed chunk. Because the signature never binds to the destination contract, that same signed bytes-tuple `(slot_id, slot_version, data_hash)` plus signature can be POSTed (via the `POST /v2/stackerdb/.../chunks` RPC, or gossiped `StackerDBPushChunkData`) against a *different* StackerDB contract in which the same signer occupies the same slot, and it will pass `try_replace_chunk`'s `slot_desc.verify(&slot_validation.signer)` check: [7](#0-6) 

This is an unauthenticated cross-contract write: an attacker (who need not be a signer or possess any private key) can inject/replay data that was authenticated for one application-level channel (e.g. a `BlockResponse` message) into a slot of a different channel (e.g. `StateMachineUpdate` or a different reward cycle's signer contract), as long as `slot_version` satisfies the strictly-increasing check. Depending on which chunk types are cross-compatible in framing, this can corrupt/forge state read by the signer or miner coordination logic that consumes these StackerDBs, which matches "unauthenticated/unauthorized write to state or StackerDB" / "network-wide propagation of forged data."

### Likelihood Explanation
The precondition — same signer occupying the same `slot_id` across multiple contracts — is not a rare coincidence but the deterministic, documented behavior of the `.signers` boot contract's shared slot-list design. Any network participant that can observe StackerDB gossip (which is by design widely replicated) can carry out the replay without needing any private key or elevated privilege, only the ability to re-POST/re-gossip previously-seen bytes with a chosen destination contract ID.

### Recommendation
Include the destination `QualifiedContractIdentifier` (and, ideally, protocol/message-type context) inside `SlotMetadata::auth_digest`, mirroring how `PerAddressTrancheVestingMerkle` binds `tranches` into its Merkle-proof digest. Concretely, add the contract identifier (encoded canonically) to the hasher in `auth_digest()` and ensure both `sign()` and `verify()` receive/require it explicitly (as `try_replace_chunk`/`validate_received_chunk` already receive `smart_contract`), so a chunk signed for one StackerDB contract can never validate against another.

### Proof of Concept
1. Let signer `S` (private key `sk`) legitimately own `slot_id = 3` in both `signers-0-<BlockResponse>` and `signers-0-<StateMachineUpdate>` (guaranteed by the shared `stackerdb-signer-slots-0` list read by every `signers-0-*` contract, per `signers.clar`).
2. `S` signs and posts a `StackerDBChunkData { slot_id: 3, slot_version: 5, data: <BlockResponse bytes> }` to `signers-0-<BlockResponse>`; this chunk (with its signature) is broadcast over gossip and observed by any peer.
3. An unprivileged attacker who captured this chunk re-submits the identical `(slot_id, slot_version, sig, data)` tuple as a POST to `signers-0-<StateMachineUpdate>` (a different contract, no key needed).
4. `try_replace_chunk` calls `slot_desc.verify(&slot_validation.signer)`, which recomputes `auth_digest()` from only `slot_id/slot_version/data_hash` — identical to step 2 — and recovers the same signer `S`, so verification succeeds and the (wrong-context) chunk is accepted into `signers-0-<StateMachineUpdate>`'s slot 3, provided its stored version there is `< 5`.

    /// Fails if the underlying crypto library fails
    pub fn sign(&mut self, privkey: &StacksPrivateKey) -> Result<(), Error> {
        let auth_digest = self.auth_digest();
        let sig = privkey
            .sign(&auth_digest.0)
            .map_err(|se| Error::SigningError(se.to_string()))?;

        self.signature = sig;
        Ok(())
    }

    /// Verify that a given principal signed this chunk metadata.
    /// Note that the address version is ignored.
    pub fn verify(&self, principal: &StacksAddress) -> Result<bool, Error> {
        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )
        .map_err(|ve| Error::VerifyingError(ve.to_string()))?;

        let pubkh = Hash160::from_node_public_key(&pubk);
        Ok(pubkh == *principal.bytes())
    }
