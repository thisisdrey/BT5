### Title
Priority-floor drop filter is computed from unverified packet bytes, letting spoofed packets defeat sigverify-stage QoS/load-shedding - (File: core/src/sigverify.rs)

### Summary
`SigVerifyWorkerPool::run_transaction_task` applies a "priority floor" load-shedding check to incoming TPU packets *before* signatures are verified, using a priority value computed straight from unauthenticated wire bytes. Because the priority value used to decide whether to drop a packet is derived from fields (e.g. compute-unit-price / prioritization instructions) that are not yet checked for a valid signature, an attacker can trivially fabricate packets that always compute an "above-floor" priority, bypassing the load-shedding mechanism that is specifically designed to protect the sigverify stage under saturation.

### Finding Description
In `core/src/sigverify.rs::run_transaction_task`, the packet processing order is: dedup → priority-floor filter → actual `ed25519_verify_serial` signature verification. [1](#0-0) 

The priority-floor filter is implemented in `apply_priority_floor_to_batch`, which calls `calculate_priority_from_bytes(bank, data)` on the raw, unverified packet bytes to decide whether the packet should be discarded: [2](#0-1) 

`calculate_priority_from_bytes` parses the transaction from the raw bytes and derives a priority strictly from message-level fields (compute-unit price / prioritization fee) without any check that the accompanying signature is valid or that the claimed fee payer actually exists/has funds: [3](#0-2) 

The struct-level comment on `SigVerifyWorkerState::priority_floor` explicitly documents that this check is meant to run "ahead of signature verification": [4](#0-3) 

Actual signature verification only happens afterward: [5](#0-4) 

This is structurally the same class of defect as the referenced EIP-4337 report: a gating/validation decision (there: `validateUserOp`'s pass/fail and aggregator/time-range semantics; here: the load-shedding "floor" decision) is made using data that has not been authenticated/verified, allowing the intended protocol invariant (only real, validly-priced, validly-signed transactions influence admission decisions) to be trivially violated by an adversary who controls the unauthenticated fields.

### Impact Explanation
The priority floor exists specifically to shed load during saturation, dropping cheap/low-priority packets *before* the CPU-expensive `ed25519_verify_serial` step runs, so that the sigverify stage can keep up under attack/flood conditions. Because the priority used for this decision is computed from unverified bytes, any unprivileged network client can set an arbitrarily large fake compute-unit-price on garbage/invalid-signature packets so they are never classified as "below floor." This defeats the entire purpose of the floor mechanism for exactly the population of packets it should be most effective against (spam with no real economic backing), forcing the validator to spend full signature-verification effort on it. Under saturation, this amplifies the attacker's ability to keep the sigverify workers loaded, working against the anti-saturation control that `update_scheduler_priority_floor` in `scheduler_controller.rs` is meant to enable — a QoS-evasion outcome.

### Likelihood Explanation
This is reachable by any unprivileged UDP/QUIC client sending TPU packets, requires no special stake or privileges, and needs only a crafted compute-budget instruction with a high price field in an otherwise garbage/unsigned packet — a trivial, cheap-to-construct input for an attacker specifically during the saturation window when the floor is non-zero (i.e., exactly when the defense matters most).

### Recommendation
Do not use claimed-but-unverified fee/priority fields as the sole basis for the priority-floor admission decision. Options: perform (or gate this check behind) a cheap authenticity/existence check on the fee payer before trusting the computed priority, verify signatures first (accepting the extra CPU cost) before applying floor logic to packets that claim high priority, or otherwise bound/discount the trust placed in unauthenticated-priority to prevent it from unconditionally exempting a packet from the floor.

### Proof of Concept
1. During saturation, the scheduler publishes a non-zero `scheduler_priority_floor` (`core/src/banking_stage/transaction_scheduler/scheduler_controller.rs`, `update_scheduler_priority_floor`).
2. An attacker sends a flood of TPU packets containing a syntactically valid `SanitizedTransactionView` with a `ComputeBudgetInstruction::set_compute_unit_price` set to a very large value, but with an invalid/garbage signature (no valid keypair needed).
3. In `apply_priority_floor_to_batch`, `calculate_priority_from_bytes` successfully parses these bytes and returns a high `priority` value (since it only reads instruction data, not signatures), so `priority <= floor` is false and the packet is kept (`any_kept = true`), never being dropped by the floor.
4. All such packets proceed to `ed25519_verify_serial`, consuming full verification CPU cost, and only fail there — but by then the load-shedding step the code relies on to protect the verifier under saturation has already been bypassed.

fn apply_priority_floor_to_batch(
    batch: &mut PacketBatch,
    floor: u64,
    bank: &Bank,
) -> (usize, bool) {
    let mut dropped: usize = 0;
    let mut any_kept = false;
    for mut packet in batch.iter_mut() {
        if packet.meta().discard() {
            continue;
        }
        let Some(data) = packet.data(..) else {
            // Zero-length or otherwise unreadable: leave to downstream
            // stages to reject.
            any_kept = true;
            continue;
        };
        // Unparseable packets are kept and left for downstream rejection.
        match calculate_priority_from_bytes(bank, data) {
            Some(priority) if priority <= floor => {
                packet.meta_mut().set_discard(true);
                dropped = dropped.saturating_add(1);
            }
            _ => any_kept = true,
        }
    }
    (dropped, !any_kept)

    let view = SanitizedTransactionView::try_new_sanitized(data, &sanitize_config()).ok()?;
    let runtime_tx = RuntimeTransaction::<SanitizedTransactionView<_>>::try_new(
        view,
        MessageHash::Compute,
        None,
    )
    .ok()?;
    let transaction_configuration = runtime_tx
        .transaction_configuration(&bank.feature_set)
        .ok()?;
    let (priority, _cost) =
        calculate_priority_and_cost(bank, &runtime_tx, &transaction_configuration);

    Some(priority)
}
