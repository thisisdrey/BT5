### Title
Dust-transfer griefing: attacker fills a victim's `depositTokensOfAccount` set to `MAX_TOKENS_PER_USER`, DoS-ing new deposits and debt issuance - ([File: contracts/Pool.sol])

### Summary
`Pool` tracks each account's deposit/debt tokens in bounded enumerable sets capped at `MAX_TOKENS_PER_USER = 30` (`contracts/Pool.sol:79`). Any addition reverts once the combined length reaches the cap via `onlyIfAdditionWillNotReachMaxTokens` (`contracts/Pool.sol:143-148`). Because `DepositToken._transfer` unconditionally calls `pool.addToDepositTokensOfAccount(recipient_)` whenever a recipient's balance moves from zero (`contracts/DepositToken.sol:517-520`), an unprivileged attacker can deposit dust into every registered `DepositToken` and `transfer`/`transferFrom` 1 wei of each `msdToken` to a victim, filling the victim's set. From then on, any deposit or mint of a collateral/debt token not already in the victim's list reverts with `UserReachedMaxTokens`, and the victim cannot add new collateral to defend a position against liquidation.

### Finding Description
- `addToDepositTokensOfAccount` / `addToDebtTokensOfAccount` revert when `debtTokensOfAccount.length + depositTokensOfAccount.length >= 30` (`contracts/Pool.sol:204-220`).
- `DepositToken._transfer` forces the recipient into the set on first receipt (`contracts/DepositToken.sol:498-526`); the recipient has no opt-out, and `_revertIfLocked` only gates the *sender's* balance (`contracts/DepositToken.sol:348-353`).
- The same forced-add happens on `seize` (`contracts/DepositToken.sol:343-345`) and on `deposit(..., onBehalfOf_)` → `_mint` (`contracts/DepositToken.sol:211-237`, `469-489`), so a liquidator seizing to a fresh address or a third-party `deposit` on behalf of the victim also consumes a slot.
- Once saturated: `DepositToken.deposit` for any token not yet in the victim's list reverts inside `_mint` → `addToDepositTokensOfAccount`; `DebtToken` issuance of a synth the victim doesn't yet hold reverts identically through `addToDebtTokensOfAccount`. A user with an unhealthy position who needs to deposit a *different* collateral type is therefore blocked and can be liquidated.
- `addDepositToken` itself is also capped at 30 deposit tokens (`contracts/Pool.sol:703`), so the attack requires a pool with enough registered deposit tokens (victim's pre-existing entries plus registered deposit tokens must reach 30). This is the Aave-style "max tokens dust" DoS class, matching the authenticated-user → denial-of-service pattern of CVE-2023-22840.

### Impact Explanation
Temporary freezing of funds / forced liquidations: the victim cannot onboard new collateral types or issue new synth debt until they manually burn the dust positions via `withdraw`, costing gas and being front-runnable/repeatable. If the victim is near the liquidation threshold and the needed collateral type isn't already in their set, the block directly enables liquidation of an otherwise salvageable position.

### Likelihood Explanation
Fully permissionless path: `deposit` (any amount ≥ 1 wei post-fee), `transfer`, and `transferFrom` are public with no allowlist. Cost is dust principal across all registered deposit tokens plus gas. Feasibility depends on the deployed pool having enough deposit tokens to reach the 30-entry cap; pools with few collaterals reduce or eliminate the impact.

### Recommendation
Let recipients keep a clean set: skip `addToDepositTokensOfAccount` for amounts below a minimum, or make the cap apply only to tokens with non-dust balances; alternatively allow removals (`removeFromDepositTokensOfAccount` is already callable on balance→0) and document that receiving dust does not consensually consume slots, or raise/decouple the per-account cap from the pool-level `addDepositToken` cap.

### Proof of Concept
```solidity
// SPDX-License-Identifier: MIT
pragma solidity 0.8.24;

import "forge-std/Test.sol";
import {Pool} from "../contracts/Pool.sol";
import {IDepositToken} from "../contracts/interfaces/IDepositToken.sol";
import {IERC20} from "../contracts/dependencies/openzeppelin/token/ERC20/IERC20.sol";

contract MaxTokensGriefingTest is Test {
    Pool pool;            // deployed Pool proxy (fork)
    address attacker;
    address victim;

    function test_fillVictimTokenList() public {
        address[] memory dts = pool.getDepositTokens();
        uint256 n = dts.length;

        // 1. Attacker deposits dust into every deposit token and sends 1 wei of each msdTOKEN to victim
        for (uint256 i; i < n; ++i) {
            IDepositToken dt = IDepositToken(dts[i]);
            IERC20 underlying = dt.underlying();
            deal(address(underlying), attacker, 1e6);
            vm.startPrank(attacker);
            underlying.approve(address(dt), 1e6);
            dt.deposit(1e6, attacker);
            dt.transfer(victim, 1); // adds dt to victim's depositTokensOfAccount
            vm.stopPrank();
        }

        uint256 slots = pool.getDepositTokensOfAccount(victim).length
                      + pool.getDebtTokensOfAccount(victim).length;
        // Combined with victim's own pre-existing entries, slots == 30 when pool has enough tokens
        assertEq(slots, pool.MAX_TOKENS_PER_USER());

        // 2. Victim tries to deposit a collateral type not yet in their list -> DoS
        IDepositToken newDt = IDepositToken(dts[0]); // any token victim's balance is 0 in
        vm.startPrank(victim);
        IERC20 newDt.underlying().approve(address(newDt), 1e6);
        vm.expectRevert(Pool.UserReachedMaxTokens.selector);
        newDt.deposit(1e6, victim); // reverts inside _mint -> addToDepositTokensOfAccount
        vm.stopPrank();

        // 3. Same revert hits DebtToken.issue for a synth the victim doesn't hold,
        //    blocking new borrowing / SmartFarmingManager leverage flows.
    }
}
```
Run as a Hardhat/Foundry fork against a chain whose pool has enough registered deposit tokens for the victim's combined set to hit 30 (e.g., `forge test --fork-url <rpc>`), which reproduces the `UserReachedMaxTokens` denial of service.

Caveat I could not fully verify within the index: the exact number of registered `DepositToken`s per deployed pool (from `deployments/*/Pool.json`) and whether `DebtToken` permits any attacker-initiated path to add entries to a victim's debt set. If every production pool has far fewer than 30 deposit tokens and the victim's own usage can't bridge the gap, the impact shrinks accordingly — that deployment-specific count should be confirmed before final severity assignment.
