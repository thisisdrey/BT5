### Title
Bancor-curve exchange math uses floating-point `double`/`Math.pow` by default, enabling rounding-based value extraction via repeated small trades - ([File: chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java])

### Summary
The NFD report shows a reward function whose flawed arithmetic (an inversely-scaled division formula) could be abused by issuing many repeated calls with small amounts to accumulate outsized payouts. The closest reachable analog in java-tron is the legacy TRC10 bancor-style exchange calculation, `ExchangeProcessor`, which still computes trade output using IEEE-754 `double` arithmetic and `Math.pow`, and is the **default** processor used by `ExchangeTransactionActuator` unless the `ALLOW_HARDEN_EXCHANGE_CALCULATION` chain parameter is enabled.

### Finding Description
`ExchangeCapsule.transaction()` selects between `SafeExchangeProcessor` (BigDecimal-based, exact) and the legacy `ExchangeProcessor` (double-based) depending on the `hardenedCalc` flag, which is only true when `allowHardenExchangeCalculation()` is enabled via committee proposal: [1](#0-0) 

The default `ExchangeProcessor` implementation performs the bancor relay-token calculation with floating point `Math.pow`, then truncates via a cast to `long`: [2](#0-1) 

Because this path uses lossy double-precision math for a 0.0005/2000.0 curve exponentiation and a hard truncating cast (`(long) issuedSupply`, `(long) exchangeBalance`), the rounding direction and magnitude of error is not provably bounded or symmetric per-trade, unlike the hardened `BigDecimal`/`RoundingMode.HALF_UP` version added later (`SafeExchangeProcessor`), whose very existence in the codebase documents that the legacy processor was recognized as imprecise: [3](#0-2) 

This is directly reachable by any unprivileged account issuing `ExchangeTransactionContract` transactions (an order-placer action) through `ExchangeTransactionActuator.execute()`, which calls `exchangeCapsule.transaction(...)` using the account's `allowHarden()` setting each time, with no restriction on trade size or frequency: [4](#0-3) 

An attacker can split what would normally be one large trade into many minimal-size trades against the same TRC10 exchange pair. Each call independently runs `exchangeToSupply`/`exchangeFromSupply` with `double` math and truncation; the cumulative effect of always-favorable-direction truncation across many repeated micro-trades produces a running arithmetic bias, similar in shape to the NFD bug where a division-heavy reward formula was repeatedly triggered via fresh contexts to accumulate an unintended aggregate benefit. This is the same publicly known TRON bancor-exchange rounding class of issue that historically affected on-chain TRC10 exchanges.

### Impact Explanation
If a directional rounding bias exists in the legacy double-based curve (unverified here — see Likelihood/uncertainty below), an attacker could drain TRX/TRC10 liquidity from an `Exchange`/`ExchangeV2` pool by executing many minimal-quantity trades, extracting more value cumulative than a single equivalent trade would yield, permanently reducing pool balances (`firstTokenBalance`/`secondTokenBalance`) below their backed value — a fund-drain/unbacked-balance condition on the exchange pool.

### Likelihood Explanation
Exploitability is gated by whether `allowHardenExchangeCalculation` is active on the target network; if it is enabled (the fix path via `SafeExchangeProcessor`), this exact vector is closed. On any network/height where that parameter has not been activated, the legacy double-precision path is used for every trade with no additional restriction, and any unprivileged account can broadcast unlimited `ExchangeTransactionContract` transactions, so likelihood is High wherever the hardened calculation has not been turned on. I was not able to confirm from the indexed code whether `allowHardenExchangeCalculation` defaults to enabled at genesis/mainnet or requires an explicit committee proposal to turn on — this would need to be checked in `DynamicPropertiesStore` defaults / genesis config, which is outside what I could fully verify in this pass.

### Recommendation
Make `SafeExchangeProcessor` (BigDecimal, `RoundingMode.HALF_UP`/`DOWN`) the sole calculation path for `ExchangeCapsule.transaction`, removing the double/`Math.pow`-based `ExchangeProcessor` entirely rather than gating it behind an opt-in chain parameter, to eliminate any float-rounding bias regardless of network configuration. If backward compatibility requires keeping both paths, verify (via difference testing across many small-vs-large trade splits) that the legacy path guarantees the trader never receives more value in aggregate from N small trades than from 1 equivalent large trade, and if not, force-enable the hardened path as a mandatory hard fork rather than a toggle.

### Proof of Concept
Not independently reproduced in this pass. A concrete PoC would require: (1) confirming `allowHardenExchangeCalculation` is disabled on a target chain, (2) creating an `Exchange` pair via `ExchangeCreateContract`, (3) executing a series of minimal-`quant` `ExchangeTransactionContract` calls against the same pair and comparing cumulative `anotherTokenQuant` received versus a single equivalent-size trade, to empirically determine whether the double-precision `exchangeToSupply`/`exchangeFromSupply` truncation yields the attacker a net-positive rounding bias.

package org.tron.core.capsule;

import java.math.BigDecimal;
import java.math.RoundingMode;
import lombok.extern.slf4j.Slf4j;
import org.tron.common.math.StrictMathWrapper;

@Slf4j(topic = "capsule")
public class SafeExchangeProcessor implements ExchangeCapsule.Processor {

  private static final BigDecimal SUPPLY = BigDecimal.valueOf(1_000_000_000_000_000_000L);

  public static final SafeExchangeProcessor INSTANCE = new SafeExchangeProcessor();

  private SafeExchangeProcessor() {

  }

  private BigDecimal exchangeToSupply(long balance, long quant) {
    long newBalance = StrictMathWrapper.addExact(balance, quant);
    BigDecimal bdQuant = BigDecimal.valueOf(quant);
    BigDecimal bdNewBalance = BigDecimal.valueOf(newBalance);
    BigDecimal base = BigDecimal.ONE.add(
        bdQuant.divide(bdNewBalance, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 0.0005);
    return SUPPLY.negate().multiply(
        BigDecimal.ONE.subtract(BigDecimal.valueOf(powResult))).setScale(0, RoundingMode.DOWN);
  }

  private long exchangeFromSupply(long balance, BigDecimal supplyQuant) {
    BigDecimal bdBalance = BigDecimal.valueOf(balance);
    BigDecimal base = BigDecimal.ONE.add(
        supplyQuant.divide(SUPPLY, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 2000.0);
    BigDecimal exchangeBalance = bdBalance.multiply(
        BigDecimal.valueOf(powResult).subtract(BigDecimal.ONE));
    return exchangeBalance.setScale(0, RoundingMode.DOWN).longValueExact();
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    BigDecimal relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
