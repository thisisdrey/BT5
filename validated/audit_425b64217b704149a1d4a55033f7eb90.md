### Title
`git_repository`'s submodule update forcibly re-enables `file://` protocol, permitting arbitrary local file/repo disclosure via an attacker-controlled `.gitmodules` - (File: `tools/build_defs/repo/git_worker.bzl`)

### Summary
`git_repository` (and `new_git_repository`, now removed but still backing the same worker) supports `init_submodules`/`recursive_init_submodules`. When enabled, Bazel runs `git submodule update --init [--recursive] --checkout --force` with `-c protocol.file.allow=always` unconditionally. [1](#0-0)  This flag was specifically the mitigation Git shipped to close CVE-2022-39253, an arbitrary local file read where a malicious repository's `.gitmodules` points a submodule URL at a local `file://` path (or an ext:: helper). Git's default (`protocol.file.allow=user` and disabling submodule recursion into local paths without an explicit opt-in) exists precisely to stop a repository the victim doesn't fully trust from being able to clone arbitrary paths on the victim's own filesystem into the checkout. Bazel's worker script overrides that default globally for every `git_repository` submodule update, regardless of how trusted the remote's *content* (as opposed to its URL) is.

### Finding Description
`git_repo`/`_update` in `git_worker.bzl` clone the attacker-designated `remote` at a `tag`/`branch`/`commit` and then, if the rule author set `init_submodules` or `recursive_init_submodules` (a normal, common option for consuming repos with submodules), call `update_submodules`, which runs:
```
_git_maybe_shallow(ctx, git_repo, "-c", "protocol.file.allow=always", "submodule", "update", "--init", "--recursive", "--checkout", "--force")
``` [1](#0-0) 

The attacker who controls the content served at the pinned `tag`/`branch` (e.g., a hostile mirror, a compromised branch that CI builds, or a repo the victim pulls by branch/tag without a content hash — `git_repository` has no checksum/integrity pinning at all, unlike `http_archive`) fully controls the tree, including `.gitmodules`. Because `protocol.file.allow=always` is forced, Git will honor a submodule entry such as:
```
[submodule "leak"]
    path = leak
    url = file:///home/victim/secrets_repo
```
and clone whatever local git repository (or, depending on git version/behavior, any path reachable via `file://`/relative paths) is on the victim's machine directly into the checkout directory that then becomes part of the fetched external repository — i.e., content the victim's own `BUILD` files, `genrule`s, or downstream build steps can read, embed into outputs, or otherwise leak. This breaks the "untrusted content stays data" / containment invariant: bytes from an attacker's published git ref are used to pull *host filesystem content* outside the intended repository into the build tree, exactly the class of bug described in the go-getter advisory (arbitrary file reads via crafted content/URLs during git operations).

Unlike `http_archive`'s extraction path (`ZipDecompressor`/`zip_main.cc`), which explicitly guards against zip-slip by normalizing and checking the target path stays under `output_root_` before writing, [2](#0-1)  there is no equivalent containment check in `git_worker.bzl` for submodule URLs — the code trusts Git's own protocol restrictions to provide containment, and then explicitly disables that restriction.

### Impact Explanation
Any Bazel workspace that uses `git_repository(..., init_submodules = True)` (or `recursive_init_submodules = True`) against a remote whose branch/tag content isn't cryptographically pinned (which is the norm for `git_repository`, since it has no checksum attribute the way `http_archive` does) is exposed: a malicious/compromised upstream can, via `.gitmodules` alone, cause the victim's Bazel invocation to read arbitrary local paths on the build machine and stage their contents inside the external repository, where they can be picked up by build rules, embedded in build outputs, or exfiltrated by any subsequent build step that processes the repo's files. This is a confidentiality (CWE-200) impact matching the advisory's C:H rating.

### Likelihood Explanation
Requires the rule author to opt into `init_submodules`/`recursive_init_submodules`, which is a common, unremarkable configuration for repositories that use git submodules, and requires the attacker to control (or compromise) the branch/tag content that the victim's `git_repository` rule fetches — squarely within the threat model of "content a victim's build consumes" from an untrusted branch/mirror. No credentials, sandbox escape, or local machine access are needed beyond normal `bazel fetch`/`bazel build`.

### Recommendation
- Do not force `protocol.file.allow=always` unconditionally; scope it or drop it, and instead validate/allowlist submodule URLs (reject `file://`, `ext::`, and other local-transport schemes) before invoking `git submodule update`.
- Add a containment check after submodule checkout analogous to the zip-slip guard in `zip_main.cc`, verifying no submodule path or content originated from outside the intended checkout directory.
- Consider requiring an explicit `allow_file_submodules`-style opt-in with a loud warning, rather than silently overriding Git's own security default.

### Proof of Concept
Add a shell test alongside `src/test/shell/bazel/starlark_git_repository_test.sh` (which already exercises submodule scenarios) [3](#0-2) :

1. Create a local "victim secret" git repo `secret_repo` containing a file `SECRET.txt` with sensitive content, outside any workspace directory.
2. Create the "malicious" remote repo `evil_repo` with a `.gitmodules` entry: `url = file:///abs/path/to/secret_repo`, `path = leaked`.
3. In the test workspace's `MODULE.bazel`, declare:
```
git_repository(
    name = "evil",
    remote = "<path-to-evil_repo>",
    branch = "main",
    recursive_init_submodules = True,
)
```
4. Run `bazel fetch --noshow_progress @evil` and assert that `$(bazel info output_base)/external/+git_repository+evil/leaked/SECRET.txt` exists and its contents match the victim secret — demonstrating that content from outside any trusted checkout boundary (the local `secret_repo`) was pulled into the build tree solely because `evil_repo`'s attacker-controlled `.gitmodules` specified a `file://` URL, enabled only because `-c protocol.file.allow=always` is unconditionally passed by `update_submodules` in `tools/build_defs/repo/git_worker.bzl`. def update_submodules(ctx, git_repo, recursive = False):
    if recursive:
        # "protocol.file.allow=always" allows the submodule command clone from a local directory.
        # It's necessary for Git 2.38.1 and assoicated backport versions.
        # See https://github.com/bazelbuild/bazel/issues/17040
        _git_maybe_shallow(ctx, git_repo, "-c", "protocol.file.allow=always", "submodule", "update", "--init", "--recursive", "--checkout", "--force")
    else:
        _git_maybe_shallow(ctx, git_repo, "-c", "protocol.file.allow=always", "submodule", "update", "--init", "--checkout", "--force")
