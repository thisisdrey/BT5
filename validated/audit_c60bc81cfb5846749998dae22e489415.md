### Title
Floating-point precision manipulation in TRC10/TRX Bancor-style exchange pools allows fund extraction - (File: `chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java`)

### Summary
The Texture incident involved an attacker exploiting flawed vault accounting logic to extract funds disproportionate to their deposit. The closest reachable analog in java-tron is the TRX/TRC10 AMM-style exchange pool math in `ExchangeProcessor`, which by default performs the core bonding-curve calculation using `double`-precision floating point arithmetic (`Math.pow`) rather than exact integer/BigDecimal math. This is reachable by any unprivileged account issuing `ExchangeTransactionContract` or `MarketSellAssetContract`-adjacent transactions against a `ExchangeCapsule` pool.

### Finding Description
`ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply` [1](#0-0)  compute the Bancor-formula supply/balance conversion using `double issuedSupply = -supply * (1.0 - Maths.pow(...))` and casts the result to `long`, which truncates and accumulates floating-point rounding error on every trade. This routine is invoked from `ExchangeCapsule.transaction()` [2](#0-1) , which is the core execution path for `ExchangeTransactionActuator.execute()` — a fully unprivileged, single-signed-transaction entry point that lets any account trade against a TRX/TRC10 exchange pool.

Critically, the safer, overflow-checked/precision-hardened path (`SafeExchangeProcessor`) is only used when `hardenedCalc` is true, which is gated by the dynamic property `getAllowHardenExchangeCalculation()` set via `ExchangeTransactionActuator` [3](#0-2) . This is a committee-controlled feature flag (default off unless explicitly enabled by chain governance), meaning the legacy double-precision math path remains the default on most deployments. Repeated small trades against a shallow/near-balanced pool can exploit rounding bias in the `double`-based formula to extract more value than deposited, incrementally draining the pool's `firstTokenBalance`/`secondTokenBalance` reserves — analogous to how the Texture attacker manipulated vault share/asset accounting to siphon deposited funds.

### Impact Explanation
An attacker who repeatedly trades small quantities against an `ExchangeCapsule` pool can accumulate rounding-favorable outcomes from the floating-point Bancor formula, extracting TRX/TRC10 tokens deposited by other liquidity participants without providing equivalent value — a direct theft of user funds analogous to the vault drain in the Texture incident. This qualifies as concrete unauthorized extraction/theft of funds from a shared on-chain pool.

### Likelihood Explanation
Exploitation requires only broadcasting many `ExchangeTransactionContract` transactions (or the `MarketSellAssetActuator` order-matching path, which uses similar `multiplyAndDivide` integer math with less risk, but the `ExchangeProcessor` legacy path is a pure `double` computation) against any existing exchange pool — no special privileges, and no reliance on SR/witness/peer misbehavior. It only requires the hardened calculation flag to remain disabled, which is the default and requires a committee proposal to change.

### Recommendation
Enable `SafeExchangeProcessor`/hardened calculation unconditionally (remove the opt-in dynamic-property gate) for all exchange trade execution, replacing the `double`-based Bancor computation with the existing overflow-checked, precision-safe implementation. Additionally, add invariant checks post-trade (e.g., constant-product/constant-supply verification with a strict integer/BigDecimal tolerance) inside `ExchangeCapsule.transaction()` to reject trades that would violate pool solvency bounds.

### Proof of Concept
Conceptual PoC (cannot be executed without a live chain, but the code path is directly traceable):
1. Deploy or use an existing `ExchangeCapsule` pool with balances `firstTokenBalance`/`secondTokenBalance` via `ExchangeCreateActuator`.
2. Repeatedly submit `ExchangeTransactionContract` transactions with `quant=1` (minimum tradable unit) alternating sell direction, while `AllowHardenExchangeCalculation` is disabled (default).
3. Each call routes through `ExchangeCapsule.transaction()` → `new ExchangeProcessor(...)` (not `SafeExchangeProcessor`) [4](#0-3) , performing the `double`-based `exchangeToSupply`/`exchangeFromSupply` math shown above.
4. Over many iterations, the `(long) issuedSupply` truncation/rounding consistently favors the attacker's direction of trade, incrementally shifting reserve balances (`newFirstTokenBalance`/`newSecondTokenBalance`) away from parity with the true value contributed, draining the pool over time — mirroring the accounting-manipulation root cause of the referenced Texture incident.

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
