### Title
Unbounded attacker-controlled array length in `ValidateMultiSign` precompile leads to uncaught `OutOfMemoryError`/`ArrayIndexOutOfBoundsException` during TVM execution - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The Samba CVE describes an integer-overflow in a length-prefixed parser (`ndr_pull_dnsp_name`) that lets any authenticated writer corrupt memory. The closest analog reachable by an unprivileged java-tron actor is the length-prefixed array decoding used by the `ValidateMultiSign` precompiled contract (address `0x...a`), invoked by any contract `CALL`/`STATICCALL`. The helper `extractBytesArray`/`extractSigArray` trusts an attacker-supplied 32-byte "array length" word taken directly from calldata to size a Java array, with no upper bound check on that code path, and the call site is not wrapped in a catch-all.

### Finding Description
`extractBytesArray` and `extractSigArray` read the declared array length straight from the calldata word array and allocate a Java array of that size before any validation: [1](#0-0) 

In `ValidateMultiSign.execute`, the size check (`sigArraySize > MAX_SIZE`) is only performed when `VMConfig.allowTvmSelfdestructRestriction()` is enabled; on the non-restricted branch (and pre‑`allowTvmOsaka`, `isValidAbiEncoding` is also skipped) `extractBytesArray`/`extractSigArray` is invoked directly with the raw, unchecked length: [2](#0-1) 

Crucially, this extraction call is *outside* the `try { ... } catch (Throwable t)` block, which only wraps the later permission-processing loop: [3](#0-2) 

Because `words[offset].intValueSafe()` can be an attacker-chosen value up to `Integer.MAX_VALUE`, `new byte[len][]` inside `extractBytesArray`/`extractBytes32Array` can attempt to allocate a multi-gigabyte reference array, throwing `OutOfMemoryError` (an `Error`, not an `Exception`), or the subsequent `words[offset + i + 1]` index accesses can throw `ArrayIndexOutOfBoundsException` when the declared length exceeds the actual word array populated by `DataWord.parseArray`. Neither is caught anywhere in `ValidateMultiSign.execute`, unlike `BatchValidateSign`, which wraps its entire `doExecute` call in a `catch (Throwable t)`: [4](#0-3) 

This asymmetry (BatchValidateSign is hardened, ValidateMultiSign is not) is the root cause.

### Impact Explanation
An uncaught `OutOfMemoryError`/`Error` escaping precompile execution during block application can destabilize or crash the JVM process executing the transaction, since generic `catch (Exception e)` handlers elsewhere in the VM/transaction-trace pipeline will not catch `java.lang.Error`. This matches the accepted "node crash or halt" impact class. It is reachable from a single unprivileged contract call with no special permissions, matching the "unprivileged contract deployer/caller" threat model requested.

### Likelihood Explanation
Likelihood is high for the code path itself (a plain `CALL` to address `0x...a` with crafted calldata containing a huge length word triggers it whenever `allowTvmSelfdestructRestriction` is not enabled, and pre‑`allowTvmOsaka` there is also no ABI-shape validation). I was not able to fully trace, within this session, how far up the call stack an `Error` (as opposed to `Exception`) propagates before being caught by `Program`/`Runtime`/`TransactionTrace` — i.e., whether it is contained to the single transaction or destabilizes the whole node process. This is the main open uncertainty; verifying it would require inspecting `Program.callToPrecompiledAddress`, `Runtime.execute`, and `TransactionTrace.exec` exception-handling layers, which were not retrieved in this investigation.

### Recommendation
- Bound-check the declared array length in `extractBytesArray`/`extractSigArray`/`extractBytes32Array` against `MAX_SIZE` (and against `words.length`) before allocating, symmetric with the `BatchValidateSign` `MAX_SIZE` gating, regardless of `allowTvmSelfdestructRestriction`/`allowTvmOsaka` flags.
- Wrap the entire `ValidateMultiSign.execute` body (not just the permission loop) in a `catch (Throwable t)` as is already done in `BatchValidateSign.execute`, so malformed calldata degrades to `DATA_FALSE` instead of throwing.

### Proof of Concept
Craft calldata for `validatemultisign(address,uint256,bytes32,bytes[])` where the encoded `bytes[]` array's length word (the word at the offset pointed to by the 4th head word) is set to a very large value (e.g. `0x7fffffff`) while the actual calldata is short, and `VMConfig.allowTvmSelfdestructRestriction()`/`allowTvmOsaka()` are not active (default/older network parameters). Calling this from any account via `CALL` to `PrecompiledContracts` address `0x...a` drives execution into `extractBytesArray` with `len = 0x7fffffff`, attempting `new byte[0x7fffffff][]`, which throws `OutOfMemoryError` uncaught by `ValidateMultiSign.execute`. This is directly analogous to `BatchValidateSignContractTest.testTip854RejectsMalformedCalldata`, which exercises the corresponding *guarded* case for `BatchValidateSign` but has no equivalent unguarded-length stress test for `ValidateMultiSign`.     }
