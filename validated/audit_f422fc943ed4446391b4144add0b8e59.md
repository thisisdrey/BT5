### Title
Dust `DepositToken.transfer` griefing permanently fills a victim's per-account token list, DoS-ing deposits, issuances and swaps - ([File: contracts/Pool.sol](contracts/Pool.sol), [File: contracts/DepositToken.sol](contracts/DepositToken.sol))

### Summary
`Pool` enforces `MAX_TOKENS_PER_USER = 30` via `onlyIfAdditionWillNotReachMaxTokens`, which counts `debtTokensOfAccount + depositTokensOfAccount` [1](#0-0) . Any ERC20 transfer of a `DepositToken` to a first-time holder calls `addToDepositTokensOfAccount(recipient)`, which enforces the cap on the *recipient* [2](#0-1) . Since `DepositToken` implements permissionless `transfer`/`transferFrom` guarded only by the sender's unlocked balance [3](#0-2) , an attacker can push 1-wei balances of every registered deposit token into a victim, permanently filling the list with no victim interaction.

### Finding Description
- Attacker deposits dust (e.g., 1 wei of underlying) into each of the pool's ~N registered `DepositToken`s (or buys dust on the market), keeping zero debt so `_revertIfLocked` passes.
- For each token, attacker calls `depositToken.transfer(victim, 1)`. `_transfer` sets `balanceOf[victim] = 1` and, because the recipient balance was 0, calls `pool.addToDepositTokensOfAccount(victim)` [2](#0-1) , which adds to `depositTokensOfAccount[victim]` [4](#0-3) .
- Once `debtTokens + depositTokens` reaches 30, every subsequent `addTo*TokensOfAccount` reverts `UserReachedMaxTokens`. This DoSes:
  - `DepositToken.deposit` / `_mint` into any collateral the victim doesn't already hold (`_balanceBefore == 0` path) [5](#0-4)  — victim cannot top up *new* collateral types to restore health as price moves.
  - `DebtToken` mint paths (`issue`, `SmartFarmingManager.leverage`, `Pool.swap` into a new synth) which call `addToDebtTokensOfAccount` [6](#0-5) .
- Removal only happens when the victim's balance of that token returns to exactly 0 [7](#0-6) . The victim can transfer each dust token out, but the attacker can front-run/re-add dust repeatedly, and on an unhealthy account the victim's *own* `transfer` is gated by `_revertIfLocked`, so dust sent to an account whose collateral is fully locked cannot be transferred out at all — the griefer's dust is permanently wedged while the position is distressed.

### Impact Explanation
Unprivileged availability attack analogous to the CVE's unauthorized DoS: the victim is blocked from depositing new collateral types and from issuing/receiving new synthetic debt, i.e., temporary-to-permanent freezing of their ability to manage the position. For a victim already at the cap with fully locked collateral, the dust entries cannot be removed (`_revertIfLocked` blocks outbound transfer of even the dust token since it contributes to `depositOf`), so the only exits are liquidation or repaying all debt — the position cannot be re-collateralized into a different asset even if that would save it.

### Likelihood Explanation
Requires only an EOA with dust amounts of registered underlyings; no privileged role, no oracle manipulation, no flash loan needed. Cost is N dust deposits + N transfers. Front-running the victim's cleanup transfers keeps the DoS alive indefinitely. Caveat: the victim can clear entries while healthy by transferring dust out, so sustained impact requires either repeated griefing or targeting a near-cap/locked account.

### Recommendation
- Do not run `addToDepositTokensOfAccount` (or the cap check) on unsolicited transfers below a minimum threshold; or exempt `seize`/mint from the cap and only enforce it on user-initiated `deposit`/`issue`.
- Alternatively track deposit/debt tokens for position accounting but enforce the cap only when the account deliberately opens a position, and allow anyone to "sweep" dust entries (balance below a floor) out of a victim's set.

### Proof of Concept
Hardhat-style sketch (reproducible on a fork/test fixture with `N` deposit tokens registered):

```ts
// attacker: no debt, dust balances of every deposit token
for (const dt of depositTokens) {
  await underlying[dt].connect(attacker).approve(dt.address, 1)
  await dt.connect(attacker).deposit(1, attacker.address) // mints 1 wei msdX
}

// grief: fill victim's depositTokensOfAccount up to MAX_TOKENS_PER_USER
for (const dt of depositTokens) {
  await dt.connect(attacker).transfer(victim.address, 1) // _transfer -> addToDepositTokensOfAccount
}

const count = (await pool.getDepositTokensOfAccount(victim.address)).length
          + (await pool.getDebtTokensOfAccount(victim.address)).length
expect(count).to.eq(30)

// victim cannot deposit a collateral type they don't already hold
await expect(msdNewToken.connect(victim).deposit(amount, victim.address))
  .revertedWithCustomError(pool, 'UserReachedMaxTokens')

// victim cannot issue a synth whose debt token they don't hold
await expect(msUsdDebtToken.connect(victim).issue(1, victim.address))
  .revertedWithCustomError(pool, 'UserReachedMaxTokens')
```

Key detail for permanence: if `unlockedBalanceOf(victim) == 0` for the dusted tokens (debt fully locks collateral), `victim`'s own `transfer`/`withdraw` reverts on `_revertIfLocked` [8](#0-7) , so the dust cannot be evicted and the cap remains saturated until liquidation or full repayment.
