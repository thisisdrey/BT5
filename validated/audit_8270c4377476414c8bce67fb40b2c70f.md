### Title
Fixed-size-based `dispatch_weight` estimate lets XCM bridge messages under-declare actual execution cost, enabling block-weight exhaustion - (File: `bridges/modules/xcm-bridge-hub/src/dispatcher.rs`)

### Summary
`pallet_bridge_messages::receive_messages_proof` gates message dispatch on a relayer-declared `dispatch_weight` argument, checked per message against `T::MessageDispatch::dispatch_weight(&mut message)` before calling `dispatch()`. For the XCM bridge hub, this bound is computed by `XcmBlobMessageDispatch::dispatch_weight` solely from the **encoded byte size** of the payload via a benchmarked linear function (`message_dispatch_weight(payload_size)`), completely independent of the actual number/kind of XCM instructions packed into that payload.

### Finding Description [1](#0-0) 
computes the dispatch weight bound from `payload.encoded_size()` alone, feeding it through `MessagesPalletWeights::<T, I>::message_dispatch_weight`, itself defined as a difference of two benchmarks parameterized only by message size in bytes: [2](#0-1) 

The actual `dispatch()` call then forwards the whole decoded XCM blob straight into `T::BlobDispatcher::dispatch_blob(payload)` without any weight metering of the XCM instruction execution, and always reports `unspent_weight: Weight::zero()`: [3](#0-2) 

The `MessageDispatch` trait's own contract requires `dispatch_weight` to be a "correct upper bound of dispatch weight" matching the message-details API used by relayers/fee estimation: [4](#0-3) 

Because an XCM program's real execution cost is dominated by the *number and kind* of instructions (e.g. many `Transact`, `DepositAsset`, `QueryPending`, or nested `SetAppendix`/`ClearOrigin` instructions), not by the raw byte length of its SCALE encoding, an attacker can craft a payload that is small in bytes (cheap `dispatch_weight` estimate, easily fits under the relayer's declared `dispatch_weight_left` counter in `receive_messages_proof`) yet expands into a very large XCM execution weight once dispatched into the destination chain's XCM executor/queue. This is the on-chain analog of the reported `finalizeBlocks` issue: the "declared cost" used to gate acceptance (`dispatch_weight`) is decoupled from the true computational cost of processing the submitted data, and the gap is attacker-controlled by choosing dense-but-small-encoded XCM programs.

### Impact Explanation
`receive_messages_proof` uses `dispatch_weight_left` to decide, before actually executing anything, whether it *can* dispatch the next message on the lane: [5](#0-4) 
Since this check is bounded only by `message_dispatch_weight(payload_size)` and not by the true weight the destination-side XCM executor will spend when the blob is finally processed (in `dispatch_blob` → HRMP/XCMP queue → `on_initialize` processing by `pallet-message-queue`), a relayer can submit proofs that pass the pre-dispatch weight check under-priced relative to what the destination parachain's block will actually have to spend to execute the forwarded XCM. Repeated across many lanes/messages in the same block this can inflate real per-block XCM processing cost beyond what was accounted for at admission time, degrading block production or stalling the receiving chain's message queue — the "public underpriced work that degrades block production or stalls bridge processing" impact class explicitly in scope.

### Likelihood Explanation
Any signed account can act as a relayer and submit `receive_messages_proof` with a valid storage proof for messages that were legitimately queued on the source chain — no malicious validator, collator, or governance actor is required, only crafting of the XCM payload content (which any parachain team or user with cross-chain interaction rights controls when originating the bridge message). The gap between byte-size-based weight and instruction-based weight is inherent to `dispatch_weight`'s size-only formula, so this is systematically exploitable rather than a one-off edge case.

### Recommendation
Compute `dispatch_weight` for XCM blob messages using the XCM `Weigher`/`WeighMultiAssets`-style analysis of the decoded instructions (as done for locally-originated XCM in `pallet-xcm`/`xcm-executor`), not merely the payload's encoded byte length. Additionally, actually meter weight consumption inside `XcmBlobMessageDispatch::dispatch()` (or in `DispatchBlob::dispatch_blob`) and return the real `unspent_weight` instead of hardcoding `Weight::zero()`, so that the pallet's post-dispatch refund/weight-limit machinery reflects true cost and can reject/postpone messages whose real weight exceeds the declared bound — mirroring the "benchmark the cost per block and enforce limits" recommendation from the external report.

### Proof of Concept
1. Craft an XCM program with many cheap-to-encode but expensive-to-execute instructions (e.g., a long chain of nested `SetAppendix`/`Transact`/`DepositAsset` items using compact indices/short call data) such that `payload.encoded_size()` stays small.
2. Submit it as a bridge message on the source chain lane so it becomes queued in `OutboundLanes`.
3. As a relayer, build a storage proof and call `receive_messages_proof` with `dispatch_weight` set to the small value returned by `message_dispatch_weight(payload_size)` — the check at `bridges/modules/messages/src/lib.rs:293-304` passes because it only compares against this byte-size-derived figure.
4. `dispatch()` forwards the payload to `T::BlobDispatcher::dispatch_blob`, which enqueues/executes the XCM program on the destination side with real weight far exceeding what was declared/charged for the `receive_messages_proof` extrinsic.
5. Repeating this with multiple such messages inflates the destination chain's actual per-block XCM processing weight without the pre-dispatch accounting having reserved for it, evidenced by `unspent_weight` always being `Weight::zero()` in `bridges/modules/xcm-bridge-hub/src/dispatcher.rs:107-128` regardless of actual instruction cost.
