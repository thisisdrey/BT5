Confirmed: there is no rate limiting anywhere in nebula's incoming-handshake path. `HandshakeManager.HandleIncoming` at `handshake_manager.go:151-194` performs only cheap header checks (subtype allow-list and a zero-`RemoteIndex` check for stage-1) before calling `beginHandshake` for *every* well-formed stage-1 packet from *any* unauthenticated source, and the wire format's only planned anti-DoS field (`Cookie`) is explicitly documented as "reserved... but never implemented" in `handshake/handshake.proto:21-24`.

### Title
Unrated remote CPU-exhaustion DoS via unthrottled Noise handshake processing in `beginHandshake` - (File: `handshake_manager.go`)

### Summary
Any unauthenticated attacker who can reach a nebula node's UDP listener can force it to perform expensive asymmetric (Curve25519 Diffie-Hellman/Noise) cryptographic operations for every spoofed stage-1 handshake packet it sends, with no per-source rate limiting, cookie challenge, or connection-attempt cap anywhere in the incoming-handshake path.

### Finding Description
`HandshakeManager.HandleIncoming` [1](#0-0)  is the single entry point for handshake packets. For any packet with `MessageCounter == 1` and `RemoteIndex == 0` (i.e., every syntactically valid stage-1 packet, which an attacker can trivially craft since the initiator index/cert fields are entirely attacker-controlled), it unconditionally calls `beginHandshake` — no rate limit, no per-IP quota, no proof-of-work/cookie challenge is applied first.

`beginHandshake` [2](#0-1)  then constructs a brand-new `handshake.Machine` via `handshake.NewMachine` and calls `machine.ProcessPacket`, which internally invokes noise's `ReadMessage` — this performs the responder-side Diffie-Hellman computation (`hs.ReadMessage`) as shown in `handshake/machine.go:228` [3](#0-2) . This scalar-multiplication work happens *before* any certificate is validated (`validatePeerCert` runs only after `ProcessPacket` succeeds), so the attacker never needs a CA-signed certificate to trigger it — a single UDP datagram with a plausible header and payload shape is enough to force a full Noise IX message-1 processing cycle.

The wire format's own documentation admits there is no anti-DoS mechanism: the `Cookie` field in `NebulaHandshakeDetails` was "reserved for an anti-DoS mechanism that was never implemented. No released version of nebula has ever populated it" [4](#0-3) . A repo-wide search for rate-limiting primitives (`RateLimit`, `Limiter`, token bucket, etc.) in the production code returns no hits, confirming no other layer compensates for this gap.

This is a direct analog of the reported disperser bug class: an externally reachable RPC/packet-processing entry point that does non-trivial per-request work (holding mutexes / consuming CPU) with no throttling, allowing an attacker to exhaust a shared resource (here, CPU cycles and heap allocations for `Machine` objects) purely by flooding requests.

### Impact Explanation
An attacker with only network reachability to the UDP port (no valid certificate, no prior trust relationship) can flood spoofed or real stage-1 handshake packets from many source addresses/ports. Each packet forces the responder to allocate a `handshake.Machine`, build Noise state, and perform an ECDH operation — asymmetric crypto is orders of magnitude more expensive than the packet-drop path. At sufficient volume this saturates CPU on the receiving node, degrading or denying handshake/service availability for legitimate peers (remote crash/DoS-class impact, consistent with the “no impact” exclusion not applying here since availability of the whole tunnel is affected).

### Likelihood Explanation
High reachability, low attacker cost: the attacker needs no certificate, no prior handshake, and no non-default configuration — only the ability to send UDP packets to the listener with a valid header/`MessageCounter==1`/`RemoteIndex==0` combination, all of which are directly attacker-controlled per `HandleIncoming`'s dispatch logic.

### Recommendation
Add per-source-address rate limiting (or a stateless cookie/proof-of-work challenge, as originally envisioned by the now-dead `Cookie` field) in `HandshakeManager.HandleIncoming`/`beginHandshake` before any Noise/`ProcessPacket` work is performed, so that an unauthenticated peer cannot trigger unbounded expensive cryptographic work per packet.

### Proof of Concept
1. Stand up a nebula node with a valid CA and its own certificate (standard config), listening on UDP.
2. From an unauthenticated host, craft and send UDP datagrams matching nebula's header format: `Type=Handshake`, `Subtype=HandshakeIXPSK0`, `MessageCounter=1`, `RemoteIndex=0`, followed by an arbitrary/garbage Noise message-1 payload of the correct minimum length (or a captured legitimate msg1 replayed with a fresh ephemeral key each time to avoid any replay-window matching).
3. Repeat at high rate from a single or many source IP/ports.
4. Observe that each packet reaches `HandshakeManager.beginHandshake` → `handshake.NewMachine` → `machine.ProcessPacket` → `hs.ReadMessage`, performing a fresh ECDH computation per packet, with CPU usage scaling directly with attacker-controlled packet rate and no rejection/throttling occurring until the process is resource-starved.

func (hm *HandshakeManager) HandleIncoming(via ViaSender, packet []byte, h *header.H) {
	// Gate on known handshake subtypes. Unknown subtypes (or future ones we
	// don't yet support) are dropped here rather than silently routed through
	// the IX path. Add a case when introducing a new pattern.
	switch h.Subtype {
	case header.HandshakeIXPSK0:
		// supported
	default:
		hm.l.Debug("dropping handshake with unsupported subtype",
			"from", via, "subtype", h.Subtype)
		return
	}

	// First remote allow list check before we know the vpnIp
	if !via.IsRelayed {
		if !hm.lightHouse.GetRemoteAllowList().AllowUnknownVpnAddr(via.UdpAddr.Addr()) {
			hm.l.Debug("lighthouse.remote_allow_list denied incoming handshake", "from", via)
			return
		}
	}

	// First message of a new handshake. The wire format requires RemoteIndex
	// to be zero here (the initiator has no responder index to fill in yet),
	// and generateIndex never allocates 0, so any non-zero RemoteIndex on a
	// stage-1 packet is malformed or someone probing for an index collision.
	// Drop without paying the cost of running noise on a pending Machine.
	if h.MessageCounter == 1 {
		if h.RemoteIndex != 0 {
			hm.l.Debug("dropping stage-1 handshake with non-zero RemoteIndex",
				"from", via, "remoteIndex", h.RemoteIndex)
			return
		}
		hm.beginHandshake(via, packet, h)
		return
	}

	// Continuation message must match a pending handshake by index.
	// Anything else is an orphaned packet (e.g., late retransmit after
	// timeout) and is dropped.
	if hh := hm.queryIndex(h.RemoteIndex); hh != nil {
		hm.continueHandshake(via, hh, packet)
		return
	}
}

func (hm *HandshakeManager) beginHandshake(via ViaSender, packet []byte, h *header.H) {
	f := hm.f
	cs := f.pki.getCertState()

	v := cs.DefaultVersion()
	if cs.GetCredential(v) == nil {
		f.l.Error("Unable to handshake with host because no certificate is available",
			"from", via, "certVersion", v)
		return
	}

	machine, err := handshake.NewMachine(
		v, cs.GetCredential,
		hm.certVerifier(), func() (uint32, error) { return generateIndex(f.l) },
		false, header.HandshakeIXPSK0,
	)
	if err != nil {
		f.l.Error("Failed to create handshake machine", "from", via, "error", err)
		return
	}

	response, result, err := machine.ProcessPacket(nil, packet)
	if err != nil {
		f.l.Error("Failed to process handshake packet", "from", via, "error", err)
		return
	}
