## Finding

### Title
Unbounded growth of per-account `DelegatedResourceAccountIndex` entries enables DoS of the `getDelegatedResourceAccountIndexV2` query API - (File: chainbase/src/main/java/org/tron/core/store/DelegatedResourceAccountIndexStore.java)

### Summary
`DelegateResourceActuator`/`DelegateResourceProcessor` let any account delegate as little as 1 TRX of frozen bandwidth/energy to an unlimited number of distinct receiver addresses, with **no cap** on how many delegation relationships a single account can hold. Each delegation creates a new, permanent key-value pair under a `V2_FROM_PREFIX`/`V2_TO_PREFIX` prefix in `DelegatedResourceAccountIndexStore`. The full set of relationships for an address is later reconstructed on demand by `getWithPrefix()`, which performs an **unbounded `prefixQuery`** over all matching keys, sorts them, and materializes the full list in memory. This reconstruction is reachable directly from the public `getDelegatedResourceAccountIndexV2` gRPC/HTTP query, mirroring the reported `activeProtectionIndexes` pattern: an attacker-controlled, unboundedly-growing collection that is fully iterated/loaded in a single externally triggerable operation.

### Finding Description
`DelegateResourceActuator.validate()` only checks that `delegateBalance >= 1 TRX` and that the receiver account exists; it places no limit on the number of distinct receivers a single owner can delegate to. [1](#0-0) 

Each successful delegation writes a brand-new index entry via `delegatedResourceAccountIndexStore.delegateV2(...)`, keyed by `V2_FROM_PREFIX + owner + receiver` and `V2_TO_PREFIX + receiver + owner`: [2](#0-1) [3](#0-2) 

Nothing prevents an attacker from repeating this with distinct receiver addresses (each just needs to be a pre-existing, non-contract account) indefinitely, growing the number of DB entries sharing the same prefix for a given owner without bound.

The full reconstruction of an account's delegation index is done by `getWithPrefix()`, which scans **all** entries under the prefix, sorts them by timestamp, and builds `List<ByteString>` for both directions: [4](#0-3) 

This method is invoked by `getV2Index()`, which backs the public `getDelegatedResourceAccountIndexV2` API exposed via gRPC (`RpcApiService`) and HTTP (`GetDelegatedResourceAccountIndexV2Servlet`)/`Wallet`: [5](#0-4) 

Because the number of entries scanned by `prefixQuery` is entirely attacker-controlled (bounded only by how many transactions/TRX the attacker is willing to spend), a single unprivileged query against this API can be made arbitrarily expensive in CPU and memory — the same DoS structure as the referenced `activeProtectionIndexes` issue where an unbounded, attacker-grown collection is fully iterated in one call.

### Impact Explanation
An attacker can cheaply inflate a single account's delegation index to a very large size (each entry only costs ~1 TRX frozen balance plus a normal transaction fee, and receivers can be attacker-owned accounts). Once inflated, every call to `getDelegatedResourceAccountIndexV2` (or `getDelegatedResourceAccountIndex` via the legacy path with similar `getIndex`/`getWithPrefix` fallback) for that address forces the serving node to perform a full-prefix DB scan, sort, and build a potentially huge response object. This can degrade or hang the node's API-serving threads, denying legitimate `Wallet`/gRPC/HTTP query service — a concrete "API the node can no longer serve" condition.

### Likelihood Explanation
Reachable by any unprivileged account: `DelegateResourceContract` is a standard broadcastable transaction with no special permission requirements, and repeatedly calling it against many receiver addresses is straightforward and inexpensive (minimum 1 TRX per relationship, receivers can be self-controlled newly created accounts). The query endpoint itself requires no authentication and is part of the standard Wallet/gRPC/HTTP surface.

### Recommendation
Enforce a maximum number of concurrent delegation relationships (`toAccounts`/`fromAccounts`) per address in `DelegateResourceActuator`/`DelegateResourceProcessor` validation, and/or paginate `getWithPrefix()`/`prefixQuery` results instead of materializing and sorting the entire prefix range in a single call.

### Proof of Concept
1. Create N funded, non-contract accounts A1..AN.
2. From account O, freeze 1 TRX increments (`FreezeBalanceV2`) and call `DelegateResourceContract` N times, delegating 1 TRX of bandwidth to each Ai — each call succeeds independently since `validate()` never limits the count of distinct receivers.
3. This creates N persistent entries with keys `V2_FROM_PREFIX+O+Ai` and `V2_TO_PREFIX+Ai+O`.
4. Any client calls `getDelegatedResourceAccountIndexV2(O)` via gRPC/HTTP; the node executes `getWithPrefix()` which runs `prefixQuery` over all N entries, sorts them, and builds/serializes the full response — with N chosen large enough (e.g., hundreds of thousands), this single query consumes disproportionate CPU/memory on the serving node.

  public DelegatedResourceAccountIndexCapsule getV2Index(byte[] address) {

  private DelegatedResourceAccountIndexCapsule getWithPrefix(byte[] fromPrefix, byte[] toPrefix, byte[] address) {
    DelegatedResourceAccountIndexCapsule tmpIndexCapsule =
        new DelegatedResourceAccountIndexCapsule(ByteString.copyFrom(address));

    byte[] key = Bytes.concat(fromPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpToList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpToList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    List<ByteString> list = tmpToList.stream()
        .map(DelegatedResourceAccountIndexCapsule::getAccount).collect(Collectors.toList());
    tmpIndexCapsule.setAllToAccounts(list);

    key = Bytes.concat(toPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpFromList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpFromList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    list = tmpFromList.stream().map(DelegatedResourceAccountIndexCapsule::getAccount).collect(
        Collectors.toList());
    tmpIndexCapsule.setAllFromAccounts(list);
    return tmpIndexCapsule;
