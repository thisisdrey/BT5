### Title
StackerDB chunk signatures omit the contract identifier, allowing cross-StackerDB replay of previously-published chunks — ([File: libstackerdb/src/libstackerdb.rs])

### Summary
The Shardus `UnjoinRequest` report describes a signed message whose signed payload is missing a contextual/anti-replay field, letting a valid signature be replayed outside its original context. The Stacks `StackerDB` chunk-signing scheme has the same structural weakness: the signature only commits to `(slot_id, slot_version, data_hash)` and never binds to the owning smart-contract (`contract_id`). Any chunk legitimately published to one StackerDB replica can therefore be re-submitted verbatim to a *different* StackerDB contract in which the same signer address happens to own the same `slot_id`, as long as the target's expected version check is satisfied.

### Finding Description
`SlotMetadata::auth_digest` — the exact bytes that get signed/verified for every StackerDB chunk — is built only from `slot_id`, `slot_version`, and `data_hash`: [1](#0-0) 

The struct doc comment confirms the intended scope of the signature: "signature from the stacker over (slot id, slot version, chunk sha512/256)" — with no `contract_id`, network ID, or reward-cycle context: [2](#0-1) 

Server-side acceptance in `StackerDBs::validate_received_chunk` looks up the expected signer address *per contract* (`get_slot_signer(smart_contract_id, slot_id)`), but the cryptographic check itself, `slot_metadata.verify(&addr)`, only re-derives `auth_digest()` from the three fields above — it never checks that the chunk was intended for `smart_contract_id`: [3](#0-2) 

The only "freshness" gates are per-contract slot version (`data.slot_version < *expected_version` ⇒ stale) and `max_writes` — neither of which involve the contract identity: [4](#0-3) 

Because slot ownership (`(StacksAddress, num_slots)` list) for each StackerDB is derived independently per contract from `stackerdb-get-signer-slots`, and multiple StackerDB contracts (e.g., separate message-type replicas belonging to the same reward-cycle signer set) commonly reuse the *same ordered signer list*, the same address frequently owns slot `N` in more than one contract simultaneously: [5](#0-4) 

This means a signature produced for contract A, slot N, version V, chunk data D is also a valid signature for contract B's slot N as long as B's owner-at-slot-N is the same address and B's expected version for slot N is ≤ V. An attacker does not need any private key: chunks (including `sig` and raw `data`) are broadcast/gossiped in the clear via `StackerDBChunk`/`StackerDBPushChunk` messages and the `POST /v2/stackerdb/.../chunks` HTTP endpoint, so the attacker only has to capture a previously valid `(slot_id, slot_version, sig, data)` tuple and resubmit it against a different contract ID.

### Impact Explanation
This is an unauthenticated write to network state / propagation of forged data: an attacker can plant attacker-selected (but previously legitimately signed) chunk content into a StackerDB contract other than the one it was intended for, attributed to a victim signer, without ever obtaining the victim's private key. Depending on which contracts share signer-slot layouts, this could corrupt signer message replicas (e.g., inject a stale/foreign `BlockResponse` or transaction payload from one signer-message contract into another), confusing block/nakamoto-inv consumers that trust `StackerDBChunkData::verify()` as proof of authorship for that particular contract. This matches the "unauthenticated/unauthorized write to state or StackerDB" / "network-wide propagation of forged data" High/Critical impact categories.

### Likelihood Explanation
Exploitation requires: (1) capturing a validly-signed chunk from the wire (trivial — chunks and signatures are broadcast openly), and (2) a target contract in which the signing address also owns the same `slot_id` with an acceptable (non-stale) version. Because Nakamoto/signer StackerDB contracts for the same reward cycle are frequently provisioned with identical or overlapping signer-to-slot assignments (multiple message-type replicas per cycle), condition (2) is plausible in real deployments, though it depends on deployment-specific contract slot layouts, which I could not fully verify from the indexed StackerDB contract-generation code (e.g., `stackerdb-get-signer-slots` bodies for the signer contracts themselves were not available in the index). This uncertainty affects likelihood but not the root-cause finding: the signature scheme itself provides no cryptographic binding to contract identity.

### Recommendation
Include the `contract_id` (and ideally the network ID / reward cycle) as part of `SlotMetadata::auth_digest()` so that a chunk signature is only valid for the specific StackerDB replica it was produced for. This closes the cross-contract replay path without weakening any other validation logic already in `validate_received_chunk`.

### Proof of Concept
Conceptual/code-level PoC (no private key needed):
1. Observe a legitimately published chunk for StackerDB contract `A`: `StackerDBChunkData { slot_id: N, slot_version: V, sig, data }`, signed by signer `S`.
2. Identify (or wait for) StackerDB contract `B` whose `stackerdb-get-signer-slots` assigns slot `N` to the same address `S`, and whose current version for slot `N` is `< V`.
3. Submit the identical `(slot_id: N, slot_version: V, sig, data)` tuple to contract `B` via `POST /v2/stackerdb/{B}/chunks` or by gossiping a `StackerDBPushChunk` for `B`.
4. `StackerDBs::validate_received_chunk` for contract `B` calls `slot_metadata.verify(&addr_B_slot_N)`, which succeeds because the digest only covers `(slot_id, slot_version, data_hash)` — identical to what was signed for `A` — and the stale-version check passes. [3](#0-2) 

This demonstrates the chunk from contract `A` is accepted as authentic for contract `B`, i.e., a replay across an unintended context — directly analogous to the reported `UnjoinRequest` replay bug in Shardus.

    /// Get the digest to sign that authenticates this chunk data and metadata
    fn auth_digest(&self) -> Sha512Trunc256Sum {
        let mut hasher = Sha512_256::new();
        hasher.update(self.slot_id.to_be_bytes());
        hasher.update(self.slot_version.to_be_bytes());
        hasher.update(self.data_hash.0);
        Sha512Trunc256Sum::from_hasher(hasher)
    }

    /// Sign this slot metadata, committing to slot_id, slot_version, and
    /// data_hash.  Sets self.signature to the signature.
    /// Fails if the underlying crypto library fails
    pub fn sign(&mut self, privkey: &StacksPrivateKey) -> Result<(), Error> {
        let auth_digest = self.auth_digest();
        let sig = privkey
            .sign(&auth_digest.0)
            .map_err(|se| Error::SigningError(se.to_string()))?;

        self.signature = sig;
        Ok(())
    }

    /// Verify that a given principal signed this chunk metadata.
    /// Note that the address version is ignored.
    pub fn verify(&self, principal: &StacksAddress) -> Result<bool, Error> {
        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )
        .map_err(|ve| Error::VerifyingError(ve.to_string()))?;

        let pubkh = Hash160::from_node_public_key(&pubk);
        Ok(pubkh == *principal.bytes())
    }

    fn eval_signer_slots(
        chainstate: &mut StacksChainState,
        burn_dbconn: &dyn BurnStateDB,
        contract_id: &QualifiedContractIdentifier,
        tip: &StacksBlockId,
    ) -> Result<Vec<(StacksAddress, u32)>, NetError> {
        let value = chainstate.eval_read_only(
            burn_dbconn,
            tip,
            contract_id,
            &format!("({STACKERDB_SLOTS_FUNCTION})"),
        )?;

        let result = value.expect_result()?;
        let slot_list = match result {
            Err(err_val) => {
                let err_code = err_val.expect_u128()?;
                let reason = format!(
                    "Contract {} failed to run `stackerdb-get-signer-slots`: error u{}",
                    contract_id, &err_code
                );
                warn!("{}", &reason);
                return Err(NetError::InvalidStackerDBContract(
                    contract_id.clone(),
                    reason,
                ));
            }
            Ok(ok_val) => ok_val.expect_list()?,
        };

        let mut total_num_slots = 0u32;
        let mut ret = vec![];
        for slot_value in slot_list.into_iter() {
            let (addr, num_slots) =
                Self::parse_slot_entry(slot_value, contract_id).map_err(|e| {
                    warn!("Failed to parse StackerDB slot entry: {}", &e);
                    NetError::InvalidStackerDBContract(contract_id.clone(), e)
                })?;

            if num_slots > STACKERDB_INV_MAX {
                let reason = format!(
                    "Contract {} stipulated more than maximum number of slots for one signer ({})",
                    contract_id, STACKERDB_INV_MAX
                );
                warn!("{}", &reason);
                return Err(NetError::InvalidStackerDBContract(
                    contract_id.clone(),
                    reason,
                ));
            }

            total_num_slots =
                total_num_slots
                    .checked_add(num_slots)
                    .ok_or(NetError::OverflowError(format!(
                        "Contract {} stipulates more than u32::MAX slots",
                        &contract_id
                    )))?;

            if total_num_slots > STACKERDB_INV_MAX {
                let reason = format!(
                    "Contract {contract_id} stipulated more than the maximum number of slots"
                );
                warn!("{reason}");
                return Err(NetError::InvalidStackerDBContract(
                    contract_id.clone(),
                    reason,
                ));
            }

            ret.push((addr, num_slots));
        }
        Ok(ret)
    }
