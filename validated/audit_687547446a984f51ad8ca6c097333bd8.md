### Title
Unbounded blocking read on attacker-declared Content-Length hangs the signer's single event-processing thread - (File: libsigner/src/events.rs -> process_event)

### Summary
`process_event` calls `request.as_reader().read_to_string(&mut body)` with no timeout and no cap on the number of bytes it will wait for, so a POST to `/stackerdb_chunks` (or `/proposal_response`, `/new_burn_block`, `/new_block`) that declares a large `Content-Length` but withholds/trickles the body will block that read indefinitely. Because `next_event`/`main_loop` processes requests synchronously on a single thread [1](#0-0) , this stalls the whole event receiver, preventing the signer from ever observing legitimate stackerdb chunks, block proposals, or burn-block events for as long as the attacker keeps the connection open.

### Finding Description
`process_event` reads the full body before doing any JSON/size validation: [2](#0-1) . `HttpRequest::as_reader()` (tiny_http) only limits total bytes read to the declared `Content-Length`; it does not require them to arrive within any time bound, and no `read_timeout` is ever set on the underlying socket in `bind()` [3](#0-2) . There is also no authentication check anywhere in this path — `next_event` dispatches directly to `process_event` for `/stackerdb_chunks` etc. with no token/secret verification [4](#0-3) . The sample signer config binds this listener to `0.0.0.0`, i.e., all interfaces [5](#0-4) .

`HttpServer::recv()` and the subsequent body read both happen synchronously inside the single `main_loop`/`next_event` call [6](#0-5) . An attacker sends `POST /stackerdb_chunks HTTP/1.1\r\nContent-Length: 999999999\r\n\r\n` followed by little or no body data, then leaves the connection open. `read_to_string` blocks waiting for the declared byte count to arrive (or EOF), and since the receiver is single-threaded, this hangs all future event processing — the signer stops receiving real stackerdb chunks and block proposals from the node until the attacker's connection is closed or times out at the OS/TCP layer (which is not bounded by any application-level timeout in this code).

Note: unlike the framing in the question, this is not primarily an "unbounded memory allocation" bug — tiny_http's reader only buffers bytes as they actually arrive on the wire, so `body` grows proportionally to bytes received, not to the declared `Content-Length`. The real, confirmed fault is the **unbounded blocking hang** with no read timeout and no `Content-Length` sanity cap (e.g., against `MAX_MESSAGE_LEN`) before/while reading.

### Impact Explanation
A single crafted, cheap TCP connection from an unprivileged remote party who can reach the signer's event port can hang the signer's sole event-processing thread indefinitely, blocking ingestion of all subsequent StackerDB chunks, block proposals, and burn-block notifications from the node. This is a single-message, unauthenticated availability attack against the signer process — matching the "Critical: remote crash/unauthenticated DoS from few messages" category, provided the event listener is reachable (which the sample configuration's `0.0.0.0` bind allows).

### Likelihood Explanation
No secret/token is checked before the vulnerable read, so the only precondition is TCP reachability to the configured event-receiver port. If operators bind the listener to `127.0.0.1` (as some other sample docs show) rather than `0.0.0.0`, the port is not remotely reachable and the issue is local-only; reachability therefore depends entirely on deployment configuration, which varies across the provided sample files (`0.0.0.0:30000` in `mainnet-signer-conf.toml` vs. `127.0.0.1:30000` in `docs/follower.md`/`docs/signing.md`/`testnet-signer.toml`). Attacker cost is a single TCP connection with a crafted header and no need to actually send the declared payload, and the attack is trivially repeatable.

### Recommendation
Enforce a maximum acceptable `Content-Length` (e.g., bounded by `MAX_MESSAGE_LEN`) before reading, reject requests exceeding it with `MalformedRequest`, and set an explicit read/idle timeout on the accepted socket (or use `Read::take` with a byte cap plus a timeout) so `read_to_string` cannot block indefinitely regardless of what `Content-Length` claims or how slowly bytes arrive. Consider also moving body reads onto their own bounded-duration task/thread so a stalled peer cannot stall the whole event-receiver loop, and add basic authentication/shared-secret verification for the event-POST endpoints.
