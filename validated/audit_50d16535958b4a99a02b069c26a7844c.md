A voter's transaction is applied instantly to `AccountCapsule.votesList` and `VotesStore` [1](#0-0) , but the effect on a witness's total `voteCount` (the value used to compute the per-cycle reward index `Vi`) is only realized once per maintenance cycle via `countVote()`/`updateWitnessValue()` in `MaintenanceManager.doMaintenance()` [2](#0-1) . ### Title
Vote-reward `Vi` accrual is not time-weighted, allowing last-block voters to capture a full cycle's reward - (File: consensus/src/main/java/org/tron/consensus/dpos/MaintenanceManager.java, chainbase/src/main/java/org/tron/core/store/DelegationStore.java)

### Summary
java-tron's DPoS voting reward mechanism accrues rewards per maintenance cycle using a global per-vote reward index (`Vi`) that is updated once per cycle boundary using the witness's *instantaneous* vote count, rather than a time-weighted average of votes held during the cycle. This mirrors the reported JOJO Perpetual funding-rate flaw where a discretely-updated rate is applied uniformly regardless of how long a position (here, a vote) was actually held within the period.

### Finding Description
Votes cast via `VoteWitnessActuator.countVoteAccount()` (or the TVM equivalent `VoteWitnessProcessor.execute()`) are recorded immediately into `AccountCapsule.votesList` and the account's `VotesCapsule.newVotes`, but they only affect `WitnessCapsule.voteCount` when `MaintenanceManager.doMaintenance()` runs `countVote(votesStore)` and `updateWitnessValue()` [4](#0-3) .

Immediately before that vote-count update, `doMaintenance()` calls `delegationStore.accumulateWitnessVi(curCycle, witness.createDbKey(), witness.getVoteCount())` for every witness, using the witness's vote count *as of that block* to compute the reward-per-vote delta for the entire cycle that just ended [5](#0-4) . `accumulateWitnessVi` computes `deltaVi = reward * DECIMAL_OF_VI_REWARD / voteCount` and stores it as the cumulative `Vi` for that cycle [3](#0-2) .

Any voter's eventual reward is `deltaVi (endVi - beginVi) * userVoteCount / DECIMAL`, computed in `MortgageService.computeReward()` / `VoteRewardUtil.computeReward()`, purely as a function of the vote count recorded at the account-vote snapshot for that cycle range, with no adjustment for when within the cycle the vote was cast or changed [6](#0-5) .

Because a new `VoteWitnessContract` transaction is applied to `AccountCapsule.votesList` synchronously (same block), and only the once-per-cycle `doMaintenance()` folds those pending votes into the witness's `voteCount` used for `Vi` calculation, a vote submitted in the very last block before maintenance is credited the exact same per-vote reward for that entire finished cycle as a vote that was held for the whole ~6-hour cycle window.

### Impact Explanation
An attacker (or any unprivileged account with sufficient frozen TRX for TRON Power) can vote for a witness only in the final block(s) before a maintenance cycle transition, receive full-cycle `Vi`-based rewards from that witness's block/transaction-fee pool at `MortgageService.withdrawReward()`/`queryReward()` time, and then immediately unvote or move votes elsewhere in the next cycle. This dilutes the reward legitimately earned by voters who held their vote for the full cycle, effectively redistributing reward-pool funds away from long-term voters toward voters who briefly "snipe" the cycle boundary — a concrete misappropriation of funds within the reward-distribution mechanism, reachable purely via signed `VoteWitnessContract` transactions.

### Likelihood Explanation
Cycle boundary timing (`getCurrentCycleNumber()`, maintenance interval) is public/deterministic, and any account can submit a `VoteWitnessContract` transaction (or call the TVM vote precompile via `VoteWitnessProcessor`) at will. No special privilege is required, making the interaction reliably repeatable every cycle.

### Recommendation
Weight `Vi` accrual (or the vote count fed into `accumulateWitnessVi`) by the amount of time/blocks a vote was actually outstanding during the cycle, e.g. by tracking vote-weighted-time similar to a TWAP, instead of using the single end-of-cycle snapshot vote count for the whole cycle's reward distribution.

### Proof of Concept
1. Note the current maintenance cycle number via `getCurrentCycleNumber()` and estimate the next maintenance block.
2. In the last block before maintenance, submit a large `VoteWitnessContract` transaction for witness `W` (`VoteWitnessActuator.countVoteAccount()` records votes into `AccountCapsule`/`VotesStore` immediately) [7](#0-6) .
3. When `doMaintenance()` runs, `countVote()` folds this vote into `WitnessCapsule.voteCount`, and `accumulateWitnessVi` computes the cycle's `deltaVi` using that inflated vote count against the reward accumulated over the whole finished cycle [8](#0-7) .
4. Immediately after the cycle rolls over, call `withdrawReward()`; the attacker's account receives `deltaVi * userVoteCount` — the same reward-per-vote as accounts that held the vote the entire prior cycle [6](#0-5) .
5. Unvote/move the stake away in the new cycle, repeating each cycle boundary to continually extract disproportionate reward relative to actual holding duration.

  public void accumulateWitnessVi(long cycle, byte[] address, long voteCount) {
    BigInteger preVi = getWitnessVi(cycle - 1, address);
    long reward = getReward(cycle, address);
    if (reward == 0 || voteCount == 0) { // Just forward pre vi
      if (!BigInteger.ZERO.equals(preVi)) { // Zero vi will not be record
        setWitnessVi(cycle, address, preVi);
      }
    } else { // Accumulate delta vi
      BigInteger deltaVi = BigInteger.valueOf(reward)
          .multiply(DECIMAL_OF_VI_REWARD)
          .divide(BigInteger.valueOf(voteCount));
      setWitnessVi(cycle, address, preVi.add(deltaVi));
    }

  private long computeReward(long beginCycle, long endCycle, AccountCapsule accountCapsule) {
    if (beginCycle >= endCycle) {
      return 0;
    }

    long reward = 0;
    long newAlgorithmCycle = dynamicPropertiesStore.getNewRewardAlgorithmEffectiveCycle();
    List<Pair<byte[], Long>> srAddresses = accountCapsule.getVotesList().stream()
        .map(vote -> new Pair<>(vote.getVoteAddress().toByteArray(), vote.getVoteCount()))
        .collect(Collectors.toList());
    if (beginCycle < newAlgorithmCycle) {
      long oldEndCycle = min(endCycle, newAlgorithmCycle,
          dynamicPropertiesStore.disableJavaLangMath());
      reward = getOldReward(beginCycle, oldEndCycle, srAddresses);
      beginCycle = oldEndCycle;
    }
    if (beginCycle < endCycle) {
      for (Pair<byte[], Long>  vote : srAddresses) {
        byte[] srAddress = vote.getKey();
        BigInteger beginVi = delegationStore.getWitnessVi(beginCycle - 1, srAddress);
        BigInteger endVi = delegationStore.getWitnessVi(endCycle - 1, srAddress);
        BigInteger deltaVi = endVi.subtract(beginVi);
        if (deltaVi.signum() <= 0) {
          continue;
        }
        long userVote = vote.getValue();
        reward += deltaVi.multiply(BigInteger.valueOf(userVote))
            .divide(DelegationStore.DECIMAL_OF_VI_REWARD).longValue();
      }
    }
    return reward;
