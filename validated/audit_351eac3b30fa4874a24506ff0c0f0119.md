## Analysis Result

I found a strong analog: `MarketSellAssetActuator.matchSingleOrder` contains a code path where an order's terminal state (`INACTIVE`) is applied in memory and removed from the owner's active-order index, but the corresponding order-book record is **never persisted**, leaving the on-chain `MarketOrder` record stuck as `ACTIVE` while its collateral has already been returned to the owner and the order removed from the owner's tracking list — the same "state divergence between what actually happened and what the authoritative store reflects" pattern as the Teller report.

### Title
Maker order left persisted as `ACTIVE` with a stale quantity after early-return branch skips `orderStore.put` in `MarketSellAssetActuator` - (File: `actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java`)

### Summary
In `matchSingleOrder`, the "taker > maker" branch first marks the maker order `INACTIVE` via `MarketUtils.updateOrderState(makerOrderCapsule, State.INACTIVE, marketAccountStore)` [1](#0-0) . Immediately after, if `makerBuyTokenQuantityReceive == 0`, the code returns the maker's remaining sell tokens and `return`s early [2](#0-1) , **before** reaching the `orderStore.put(makerOrderCapsule.getID().toByteArray(), makerOrderCapsule)` call at line 486 [3](#0-2) .

### Finding Description
`MarketUtils.updateOrderState` mutates the in-memory `orderCapsule.setState(state)` and, for `INACTIVE`/`CANCELED`, removes the order from `MarketAccountOrderCapsule` (persisted immediately to `marketAccountStore`) [4](#0-3) . However, the mutated `makerOrderCapsule` object (state=INACTIVE, tokens returned) is only ever written back to `MarketOrderStore` at line 486 of the actuator. In the early-return branch this `orderStore.put` call is skipped, so the on-disk `MarketOrderCapsule` for that order id retains its prior persisted state — which can be `ACTIVE` with a nonzero `sell_token_quantity_remain` — even though: (a) the account's remaining sell-token balance has already been credited back to the owner via `returnSellTokenRemain`, and (b) the order has already been de-indexed from the owner's `MarketAccountOrderCapsule` active list.

This is the same root-cause shape as the Teller report: one code path (`updateOrderState` + fund movement) completes a "closure"/fund-release action on the entity, while the authoritative persisted record for that entity is not updated to reflect the closure, because the mutation and the persistence (`orderStore.put`) are two separate, independently-skippable steps.

### Impact Explanation
Because the persisted `MarketOrderCapsule` can retain `State.ACTIVE` and a stale `sell_token_quantity_remain` while its backing collateral has already been paid out to the owner, a subsequent `MarketCancelOrderContract` or match against that same `orderId` (if still reachable through `orderStore.get(orderId)`, e.g. via a stale reference in `pairPriceToOrderStore`/`MarketOrderIdListCapsule`, or a resubmitted cancel by an owner who observed the order as active) could attempt to `returnSellTokenRemain` a second time or otherwise operate on funds that no longer back the order, since `MarketCancelOrderActuator.validate()` only checks `marketOrderCapsule.isActive()` (i.e., the persisted state) [5](#0-4)  without any additional consistency check against the fact that the order was already de-indexed from the owner's account-order list. This could allow double-crediting of sell tokens (unbacked balance creation), which is a fund-integrity issue.

### Likelihood Explanation
Reaching this branch requires the exact arithmetic condition `makerBuyTokenQuantityReceive == 0` in the "taker > maker" branch of order matching — a condition the code's own comment states "it would not happen here" given normal market-order math [6](#0-5) . I could not fully verify within the available exploration whether an attacker can craft `sellTokenQuantity`/`buyTokenQuantity` pairs (both of which are validated only for `>0` and an upper bound in `validate()`) to force `multiplyAndDivide(makerSellRemainQuantity, makerBuyQuantity, makerSellQuantity, ...)` to floor to `0` while `makerSellRemainQuantity > 0`, nor whether `pairPriceToOrderStore`/`MarketOrderIdListCapsule` retain a dangling reference to the order id after `orderIdListCapsule.removeOrder(...)` is called by the caller (`matchOrder`, guarded on `makerOrderCapsule.getSellTokenQuantityRemain() == 0`, which is **not** updated to 0 in the early-return branch since `setSellTokenQuantityRemain(0)` only happens in the other branches). This uncertainty affects confidence in exploitability and should be confirmed via a Devin session tracing exact integer values and store consistency end-to-end, since the reachability and exact BigInteger/long-division edge case go beyond static index inspection.

### Recommendation
Move `orderStore.put(makerOrderCapsule...)` to execute unconditionally on every exit path of `matchSingleOrder` (or persist immediately after each `MarketUtils.updateOrderState` call), and/or set `makerOrderCapsule.setSellTokenQuantityRemain(0)` before the early return so that any downstream matching logic relying on the in-memory quantity treats the order as fully consumed regardless of whether the early-return path is taken.

### Proof of Concept
Not independently reproducible from the index alone; the arithmetic precondition (`makerBuyTokenQuantityReceive == 0` while `makerSellRemainQuantity > 0`) needs to be confirmed against `MarketUtils.multiplyAndDivide`'s BigInteger fallback and the market's quantity limits in `DynamicPropertiesStore.getMarketQuantityLimit()`. A Devin session with a running node/test harness (e.g. extending `MarketSellAssetActuatorTest`) would be needed to construct concrete `sellTokenQuantity`/`buyTokenQuantity` values that hit this branch and verify whether the resulting order record is actually re-readable as `ACTIVE` for a second cancel/match.

  public static void updateOrderState(MarketOrderCapsule orderCapsule,
      State state, MarketAccountStore marketAccountStore) throws ItemNotFoundException {
    orderCapsule.setState(state);

    // remove from account order list
    if (state == State.INACTIVE || state == State.CANCELED) {
      MarketAccountOrderCapsule accountOrderCapsule = marketAccountStore
          .get(orderCapsule.getOwnerAddress().toByteArray());
      accountOrderCapsule.removeOrder(orderCapsule.getID());
      marketAccountStore.put(accountOrderCapsule.createDbKey(), accountOrderCapsule);
    }
  }
