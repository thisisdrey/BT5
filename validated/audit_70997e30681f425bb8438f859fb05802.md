### Title
Unauthenticated remote shutdown of the signer's `SignerEventReceiver` HTTP listener via `POST /shutdown` - (File: `libsigner/src/events.rs`)

### Summary
The signer's HTTP event-receiver server, which the Stacks node uses to push StackerDB chunks, block-validation responses, and burn/stacks-block notifications to a running `stacks-signer` process, exposes a `/shutdown` route that terminates the receiver loop for *any* caller who can reach the socket, with no authentication, signature check, or source-address restriction.

### Finding Description
`SignerEventReceiver::next_event()` dispatches on the raw HTTP request URL. Most routes (`/stackerdb_chunks`, `/proposal_response`, `/new_burn_block`, `/new_block`) route to `process_event`, which at least requires a JSON body that deserializes into an expected event type. But the `/shutdown` route unconditionally sets the stop flag and returns `EventError::Terminated`: [1](#0-0) 

```
} else if request.url() == "/shutdown" {
    event_receiver.stop_signal.store(true, Ordering::SeqCst);
    Err(EventError::Terminated)
```

There is no comparison against a shared secret, no check that the request originated from the local Stacks node process, and no signature/MAC validation of the request body — unlike every other data-bearing endpoint, which at least requires the body to parse into a `StackerDBChunksEvent`/`BlockValidateResponse`/etc. This mirrors the internal, *intentional* mechanism `SignerStopSignaler::send()` uses to wake and stop the receiver from within the same process: [2](#0-1) 

That internal mechanism connects to `self.local_addr` and POSTs `/shutdown` — but the HTTP endpoint itself makes no distinction between this legitimate local caller and an arbitrary remote TCP client that sends the same three lines of HTTP. `EventError::Terminated` propagates out of `next_event()` and is treated as a clean exit condition in `main_loop()`: [3](#0-2) 

```
Err(EventError::Terminated) => {
    // we're done
    info!("Caught termination signal");
    break;
}
```

Once `main_loop` breaks, the event-receiver thread exits, and `RunningSigner::stop()`/`join()` in `libsigner/src/runloop.rs` will subsequently unblock the runloop; the effect is that the signer's ability to receive block proposals, StackerDB chunk pushes, and burn-block notifications from the node is permanently disabled until the operator restarts the process.

This is a direct structural analog to the `nltk.app.wordnet_app` bug: a plaintext HTTP GET/POST to a specific well-known path (`SHUTDOWN THE SERVER` vs `/shutdown`) causes an unauthenticated, unconditional termination of a network-facing service listener — CWE-306 (Missing Authentication for Critical Function).

### Impact Explanation
Any party who can reach the signer's bound event-receiver port can silently and permanently stop that signer's connectivity to the node with a single HTTP request (`POST /shutdown` with any body). For a Stacks signer, this is a denial-of-service on the signer's ability to receive proposals and StackerDB pushes from its node, which can degrade the signer's participation in signing rounds and — if this affects a large fraction of signers simultaneously — impact block signing liveness. This matches the "Critical — remote crash / unauthenticated DoS from a few messages" impact bucket used for `wordnet_app`'s analog: an unauthenticated request that unconditionally shuts down a listening service. Whether the socket is reachable beyond localhost depends on the deployed `endpoint` bind address in the signer's TOML config (`stacks-signer/src/config.rs`) — if an operator binds to `0.0.0.0` or a LAN-reachable interface (a supported and plausible operational configuration, since the field is a general `SocketAddr`), the vulnerability is remotely exploitable by any host that can reach that address/port.

### Likelihood Explanation
High for any deployment where the event-receiver's `endpoint` is not strictly bound to `127.0.0.1`/loopback-only and firewalled: the attack requires a single unauthenticated HTTP request with no cryptographic material, no valid StackerDB signature, and no knowledge of any secret. It is trivially automatable, exactly as demonstrated in the referenced advisory's PoC against `wordnet_app`.

### Recommendation
Require an authentication token or restrict the `/shutdown` route to loopback-only origins. Concretely: (1) generate a random per-process shared secret at signer startup, include it as a header/query parameter on `SignerStopSignaler::send()`'s outgoing POST, and require the `next_event()` handler to check it before honoring `/shutdown`; and/or (2) verify the request's peer address is loopback before acting on `/shutdown`, rejecting all other sources with a 403/ignoring the message (similar in spirit to the `authorization` header checks already used for the node's `/v3/*` RPC endpoints, e.g. `stackslib/src/net/api/postblock_proposal.rs`).

### Proof of Concept
1. Start a `stacks-signer` process (or the `SignerEventReceiver` harness) bound to a reachable address, e.g. `endpoint = "0.0.0.0:30000"`.
2. From any remote host that can reach the port, send:
```
printf 'POST /shutdown HTTP/1.1\r\nHost: target:30000\r\nConnection: close\r\nContent-Length: 0\r\n\r\n' | nc target 30000
```
3. Observe the signer's event-receiver thread log `"Caught termination signal"` and exit its main loop, per `libsigner/src/events.rs:296-300`, ending the signer's ability to receive further node-pushed events without any authentication having been presented.
