### Title
`transfer_to_new_account` / `transfer_to_new_account_pda` allow migrating to `new_authority = Pubkey::default()`, permanently locking the migrated account and its positions - ([File: programs/marginfi/src/instructions/marginfi_account/transfer_account.rs])

### Summary
The Nouns `delegateBySig` bug allowed a user to set their voting delegate to `address(0)` because, unlike `delegate()`, it had no zero-address guard, permanently corrupting vote accounting and blocking future transfers/burns. The marginfi `transfer_to_new_account` and `transfer_to_new_account_pda` instructions have the analogous flaw: `new_authority` is an `UncheckedAccount` explicitly documented as "completely unchecked," with no on-chain guard preventing `new_authority == Pubkey::default()`. Because the old account is atomically disabled and stripped of its `lending_account` state as part of the same instruction, setting `new_authority` to the zero pubkey permanently locks the migrated deposits/borrows, since no signer can ever produce a valid signature for the all-zero `Pubkey`.

### Finding Description
Both migration instructions accept `new_authority` as a raw, unchecked account and use it directly as the new account's `authority`: [1](#0-0) [2](#0-1) 

The `Accounts` struct explicitly flags this as unchecked: [3](#0-2) 

In the same instruction call, `finalize_migrated_old_account` disables the old account and zeroes its `lending_account` (moving the balances to the new account), and this happens unconditionally regardless of what `new_authority` is: [4](#0-3) 

The only guard against re-migration checks `migrated_to == Pubkey::default()`, not `new_authority`: [5](#0-4) 

Root cause: exactly like `delegate()` in the Nouns contract normalizing `delegatee == address(0)` to `msg.sender` while `delegateBySig()` omitted the same check, marginfi's off-chain CLI helper (`marginfi_account_transfer` in `p0-cli`) added a client-side guard against the zero pubkey, but the on-chain instruction itself — the actual security boundary — has no equivalent check: [6](#0-5) 

Since a user (or any caller constructing the raw instruction directly, bypassing the CLI) fully controls all accounts passed into `TransferToNewAccount`/`TransferToNewAccountPda`, they can pass `Pubkey::default()` (or any other pubkey with no known private key) as `new_authority`. Because `Pubkey::default()` is the all-zero pubkey with no corresponding keypair, no future transaction can ever satisfy the `Signer<'info>` requirement for `authority` on the new account (`is_signer_authorized` checks `authority.key()` against `MarginfiAccount.authority`, which would be permanently unreachable).

### Impact Explanation
Once migrated, the old account is disabled and its `lending_account` (all deposit/borrow positions) is zeroed and moved to the new account, whose `authority` is now unclaimable. This permanently locks/freezes all funds tracked by that account — the user can never sign for the new account, and the old account is intentionally disabled (`ACCOUNT_DISABLED`) as part of the design, so there is no recovery path without a privileged admin/upgrade intervention (which does not exist for regular user accounts by default). This matches the reachable "permanent lock/freeze" impact category via an ordinary user-initiated, unprivileged transaction.

### Likelihood Explanation
Likelihood is low from a self-inflicted-mistake standpoint (a rational user gains nothing by burning their own account), but the flaw is trivially reachable by anyone constructing the instruction directly (no CLI enforcement is required on-chain), and could also be leveraged as a griefing/social-engineering vector (e.g., a malicious dApp/integrator building a "migrate account" flow that quietly passes the zero pubkey, or third-party CPI callers who don't reimplement the client-side check) since the PDA variant is explicitly designed for third-party/CPI usage via `third_party_id`.

### Recommendation
Add an on-chain constraint in both `TransferToNewAccount` and `TransferToNewAccountPda` account structs (or at the start of `transfer_to_new_account`/`transfer_to_new_account_pda`) requiring `new_authority.key() != Pubkey::default()`, mirroring the fix recommended for the Nouns `delegateBySig` bug (reject the zero address rather than relying on an off-chain/client-only check).

### Proof of Concept
1. Create a marginfi account and deposit collateral via `MarginfiAccountInitialize` + `LendingAccountDeposit`.
2. Call `transfer_to_new_account` (or `transfer_to_new_account_pda`) directly via a raw `Instruction` (bypassing `p0-cli`'s `marginfi_account_transfer`, which is only a client-side check as shown at [7](#0-6) ), passing `new_authority = Pubkey::default()`.
3. The instruction succeeds: `initialize_migrated_account` sets `new_account.authority = Pubkey::default()` while copying over `old_account.lending_account` [8](#0-7) , and `finalize_migrated_old_account` disables the old account and zeroes its lending state [4](#0-3) .
4. Any subsequent instruction requiring `authority` as `Signer<'info>` matching `new_account.authority` (e.g., withdraw, repay, close) can never be signed, since no private key exists for the all-zero `Pubkey`. The funds represented by `lending_account` in the new account are permanently locked.

fn finalize_migrated_old_account(
    old_account: &mut MarginfiAccount,
    new_account_key: Pubkey,
    current_timestamp: u64,
) {
    old_account.migrated_to = new_account_key;
    old_account.last_update = current_timestamp;
    old_account.lending_account = LendingAccount::zeroed();
    old_account.set_flag(ACCOUNT_DISABLED, true);
    old_account.sync_indexer_flags();
}
