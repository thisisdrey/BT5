### Title
Floating-point precision loss in the TRC10 Exchange AMM pricing formula enables value extraction analogous to Usual Protocol's rate-discrepancy arbitrage - ([File: chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java])

### Summary
The Usual Protocol incident exploited a mismatch between an internally computed, imprecise exchange rate and the "correct" market-consistent rate to extract value from a vault. Java-tron's built-in TRC10 `Exchange` feature has an analogous internal pricing engine, `ExchangeProcessor`, which — unless the hardened math flag is enabled — computes the Bancor-style relay/exchange formula using Java `double` arithmetic rather than exact arithmetic, and is directly reachable by any account via a signed `ExchangeTransactionContract`.

### Finding Description
`ExchangeCapsule.transaction()` selects between two pricing engines based on `dynamicStore.allowStrictMath()`/`allowHarden()`: the legacy `ExchangeProcessor` (double-precision `Maths.pow`) or the newer `SafeExchangeProcessor` (BigDecimal, only used when `allowHardenExchangeCalculation` is on). [1](#0-0) 

`ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply` perform the core rate math with `double` division and `Math.pow`, then truncate to `long` via a naive cast, which discards fractional precision non-deterministically depending on operand magnitude and order: [2](#0-1) 

This is the code path invoked by `ExchangeTransactionActuator.execute()`, which is reached directly from a broadcast `ExchangeTransactionContract` — no special privilege required, only a valid signed transaction and sufficient balance of the sell token: [3](#0-2) 

The validation step only checks that the computed `anotherTokenQuant` is `>= expected` (a user-supplied slippage floor), not that it matches an economically exact AMM curve value: [4](#0-3) 

Because the double-based formula's rounding error is a function of pool balance ratios and trade size (and is not bounded the same way the strict `SafeExchangeProcessor` guarantees non-negative balances via `StrictMathWrapper`), an attacker who structures a specific sequence of `ExchangeInjectContract` / `ExchangeTransactionContract` calls (choosing balances/quantities that maximize the divergence between the true curve output and the double-computed output) can repeatedly extract slightly more of the counter-asset than the pool should yield per the intended invariant — the same "internal fixed/approximate rate diverges from the correct exchange rate" root cause described in the Usual Protocol report, just implemented as a floating-point AMM instead of a hardcoded 1:1 peg. Over many iterations this can drain real TRX/TRC10 balances from the exchange pool, i.e., unbacked value extraction from other participants' deposited liquidity.

### Impact Explanation
If exploitable, an attacker can extract TRC10 tokens or TRX from an `Exchange` pool beyond what the intended bonding-curve invariant allows, effectively stealing liquidity contributed by the pool creator/other traders — a concrete unauthorized transfer/theft of funds reachable purely through the public `ExchangeTransactionContract`/`ExchangeInjectContract` APIs (`Wallet`/`TronJsonRpcImpl` broadcast paths). This maps to "theft of funds" impact criteria.

### Likelihood Explanation
Medium: this requires the non-hardened path to still be active (`allowHardenExchangeCalculation` disabled) and requires the attacker to find pool-balance/trade-size combinations where the double-precision truncation systematically favors them over many repeated trades — this is a known class of bug in floating-point-based AMMs, and the codebase's own introduction of `SafeExchangeProcessor` as a "hardened" alternative (with a dedicated `allowHardenExchangeCalculation` feature flag, `StrictMathWrapper` overflow checks, and non-negative balance assertions) is a strong internal signal that the floating-point implementation was recognized as an at-risk implementation needing replacement. I was unable to verify from the index whether `allowHardenExchangeCalculation` defaults to enabled on mainnet or is still a pending/optional proposal; this bounds confidence on real-world reachability.

### Recommendation
- Confirm and, if not already done, force `allowHardenExchangeCalculation` (and `SafeExchangeProcessor`) on by default for all networks, removing the legacy `ExchangeProcessor` double-precision code path entirely rather than leaving it selectable.
- Add strict property-based/invariant tests verifying the constant-product-style invariant holds exactly (within defined integer rounding rules) for `ExchangeProcessor`-computed trades across a wide range of pool balances and trade sizes, specifically targeting the boundary cases where the double `Math.pow` truncation diverges most from the BigDecimal computation.
- Consider disallowing/deprecating any legacy `ExchangeStore`/`ExchangeV2Store` entries still relying on the non-hardened processor.

### Proof of Concept
Not independently reproducible from the indexed code alone; the existing test suite already demonstrates both the double-precision (`ExchangeCapsuleTest.testExchange`, first call) and hardened (`SafeExchangeProcessor`, second call in the same test) code paths returning different results for the same nominal trade parameters, which is the mechanism supporting this analog: [5](#0-4)

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
