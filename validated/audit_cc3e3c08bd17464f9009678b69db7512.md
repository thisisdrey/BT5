### Title
Integer overflow in TVM precompile offset/length arithmetic causes uncaught exception in `ValidateMultiSign` - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
`PrecompiledContracts.extractBytesArray()` / `extractSigArray()` compute byte offsets from attacker-controlled ABI words using plain `int` arithmetic without overflow checking, mirroring the integer-overflow bug class from ALPINE-CVE-2022-24963 (`apr_encode` writing past buffer bounds due to unchecked length arithmetic). In java-tron, the equivalent primitive is `(bytesOffset + offset + 2) * WORD_SIZE`, which can wrap around for attacker-supplied "offset" words, and the resulting value is fed straight into `Arrays.copyOfRange` with no bounds validation beforehand.

### Finding Description
`extractBytesArray` and `extractSigArray` derive `bytesOffset` directly from calldata words via `DataWord.intValueSafe()`: [1](#0-0) 

`intValueSafe()` clamps out-of-range values to `Integer.MAX_VALUE` rather than rejecting them: [2](#0-1) 

The expression `(bytesOffset + offset + 2) * WORD_SIZE` (line 408/422) is ordinary `int` multiplication with no `Math.multiplyExact`/`Math.addExact` guard — unlike other places in the same file that explicitly use `multiplyExact`/`subtractExact` for the same class of computation, e.g. `isValidAbiEncoding`: [3](#0-2) 

Because `bytesOffset` can be as large as `Integer.MAX_VALUE / WORD_SIZE`, the multiplication `(bytesOffset + offset + 2) * WORD_SIZE` overflows 32-bit signed range and wraps to an arbitrary (possibly negative) `int`. That wrapped value is passed unchecked as the `from` argument to `Arrays.copyOfRange`: [4](#0-3) 

`isValidAbiEncoding`, the TIP-854 guard added to reject malformed calldata, only validates the *overall* calldata length against the expected header/item word shape — it does **not** validate the internal offset/length words used by `extractBytesArray`/`extractSigArray`, so a well-shaped (length-valid) payload with a maliciously large inner offset word still reaches the vulnerable arithmetic: [5](#0-4) 

Critically, `ValidateMultiSign.execute()` calls `extractSigArray`/`extractBytesArray` **outside** any `try/catch` block — only the later permission/weight-calculation logic is wrapped in `try (Throwable t)`: [6](#0-5) 

This is unlike `BatchValidateSign.execute()`, which wraps its entire `doExecute()` call in `try/catch(Throwable)` specifically to contain such faults: [7](#0-6) 

Consequently, an `ArrayIndexOutOfBoundsException` or `NegativeArraySizeException` thrown from the overflowed offset/length computation in `ValidateMultiSign` propagates uncaught out of the precompile, unlike `BatchValidateSign` which was hardened to swallow such faults and return a safe default.

### Impact Explanation
Any account can trigger this by calling a contract that invokes the `validatemultisign` precompiled contract (address `0x...a`) with crafted calldata: total length matching the expected ABI shape (bypassing `isValidAbiEncoding`), but with an inner sub-array offset/length word engineered to overflow the `(bytesOffset + offset + 2) * WORD_SIZE` computation. This produces an uncaught Java exception inside transaction/contract execution. Because the containment fix (TIP-854 outer-frame test) was applied to both `ValidateMultiSign` and `BatchValidateSign` only for the *head-length* malformed-calldata case, and `ValidateMultiSign.execute()` still lacks a blanket `try/catch` around the offset-extraction call, this specific overflow path is not covered by the existing containment test: [8](#0-7) 

At minimum this causes the transaction to fail with an unexpected runtime exception instead of a controlled revert; if this exception is not fully caught by the outer VM/`Program`/`VMActuator` machinery during block application, it can disrupt transaction processing for every node applying that block (a chain-wide DoS during block application in `Manager`), since all full nodes execute the same TVM call deterministically.

I was not able to fully trace whether `Program.callToPrecompiledAddress` or the higher-level `VMActuator`/`Runtime` layer generically catches arbitrary `RuntimeException` (as opposed to the VM's own `Program.Exception` hierarchy) for precompile calls — this determines whether the practical outcome is "transaction revert only" or a more severe "node halt/inconsistent processing." This should be verified directly against `Program.java`/`VMActuator.java` call sites.

### Likelihood Explanation
High — the precompile is directly reachable by any unprivileged account through a normal contract `CALL` to a fixed address, requires only crafting standard ABI-encoded calldata, and needs no special privileges, matching the "TVM opcodes/precompiles" in-scope category.

### Recommendation
- Use `Math.addExact`/`Math.multiplyExact` (or the project's existing `StrictMathWrapper`) for all offset/length arithmetic in `extractBytesArray`, `extractSigArray`, and `extractBytes32Array`, matching the pattern already used in `isValidAbiEncoding`.
- Validate `bytesOffset`, `bytesLen`, and the derived byte range against `data.length` *before* calling `extractBytes`, returning a safe failure (e.g., `DATA_FALSE`) rather than allowing an exception to propagate.
- Wrap the offset-extraction calls in `ValidateMultiSign.execute()` in the same defensive `try/catch(Throwable)` pattern already used by `BatchValidateSign.execute()`.
- Extend `isValidAbiEncoding` (or add a companion check) to validate inner offset/length words against the actual calldata bounds, not just the aggregate length shape.

### Proof of Concept

2. Craft `rawData` so that:
   - Total length satisfies `isValidAbiEncoding(rawData, 5, 5)` (word-aligned, valid header/item shape).
   - `words[3]` (offset to the signature array) points to a slot whose declared sub-array length/offset word, once divided by `WORD_SIZE` and added to `offset+2`, multiplied by `WORD_SIZE`, overflows `int` range (e.g., an offset word close to `Integer.MAX_VALUE`).
3. Invoke the precompile; `extractSigArray`/`extractBytesArray` computes a wrapped (possibly negative) `from` index and calls `Arrays.copyOfRange(data, from, from+len)` at `PrecompiledContracts.java:428-430`, throwing `ArrayIndexOutOfBoundsException`/`NegativeArraySizeException` uncaught out of `ValidateMultiSign.execute()`.
4. Observe whether the enclosing `Program`/`VMActuator` machinery contains this exception as a normal revert, or whether it propagates further and disrupts transaction/block processing — this final propagation step needs confirmation via test execution in the repository, which was not verifiable within this read-only session.

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }

  private static boolean isValidAbiEncoding(byte[] data, int headerWords, int itemWords) {
    if (data == null || data.length % WORD_SIZE != 0) {
      return false;
    }
    long tail = subtractExact(data.length, multiplyExact(headerWords, WORD_SIZE));
    return tail > 0 && tail % multiplyExact(itemWords, WORD_SIZE) == 0;
  }

  @Test
  public void testTip854OuterFrameContainment() throws ContractValidateException {

    DecodeUtil.addressPreFixByte = Constant.ADD_PRE_FIX_BYTE_MAINNET;
    VMConfig.initAllowTvmOsaka(1);

      for (PrecompiledContracts.PrecompiledContract contract :
          new PrecompiledContracts.PrecompiledContract[]{

              new PrecompiledContracts.BatchValidateSign()}) {
        invoke = new ProgramInvokeMockImpl();
        InternalTransaction interTrx = new InternalTransaction(
            Protocol.Transaction.getDefaultInstance(),
            InternalTransaction.TrxType.TRX_UNKNOWN_TYPE);
        program = new Program(new byte[0], new byte[0], invoke, interTrx);
        // inDataSize=0 ⇒ data=[] ⇒ fewer than H=5 head words ⇒ guard rejects.
        MessageCall messageCall = new MessageCall(
            Op.CALL, new DataWord(10000),
            DataWord.ZERO(), DataWord.ZERO(),
            DataWord.ZERO(), DataWord.ZERO(),
            DataWord.ZERO(), DataWord.ZERO(),
            DataWord.ZERO(), false);

            DataWord.ZERO(), program.getStack().pop());

        program.stackPush(new DataWord(1));
        Assert.assertEquals(new DataWord(1), program.getStack().pop());
      }

      VMConfig.initAllowTvmOsaka(0);
