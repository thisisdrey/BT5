### Title
Zip64 attribute index computed from 32-bit sentinel flags is not bounds-checked against the extra field's actual `attr_count`, causing an out-of-bounds heap read when singlejar parses an attacker-supplied jar/zip - (`File: src/tools/singlejar/zip_headers.h`)

### Summary

### Finding Description
`CDH::compressed_file_size()` and `CDH::local_header_offset()` derive the index into the parsed `Zip64ExtraField`'s `attr_[]` array purely from which 32-bit fields in the *fixed* part of the Central Directory Header equal the sentinel `0xFFFFFFFF`, without ever checking that value against the Zip64 field's own declared `attr_count()`: [1](#0-0) 

```
uint64_t local_header_offset() const {
    uint32_t size32 = local_header_offset32();
    if (ziph::zfield_has_ext64(size32)) {
      const Zip64ExtraField* z64 = zip64_extra_field();
      int attr_no = ziph::zfield_has_ext64(uncompressed_file_size32());
      if (ziph::zfield_has_ext64(compressed_file_size32())) {
        ++attr_no;
      }
      return z64 == nullptr ? 0xFFFFFFFF : z64->attr64(attr_no);
    }
    return size32;
}
```

Per the ZIP spec, the Zip64 extra field only stores attributes for the fields that are actually flagged 64-bit in the CDH, in order (uncompressed, compressed, offset), and the field's `payload_size` (hence `attr_count()`) reflects exactly that count. `CDH::compressed_file_size()` (`src/tools/singlejar/zip_headers.h:406-415`) has the same pattern, using `zfield_has_ext64(uncompressed_file_size32())` as a boolean index. Both call `Zip64ExtraField::attr64(index)`: [2](#0-1) 

which does raw, unchecked indexing (`attr_[index]`) into a flexible array member — there is no verification that `index < attr_count()`.

This is a structural analog of ALPINE-CVE-2017-15192: the Wireshark BT ATT dissector assumed a consistent "encapsulation" (that all packets carried the same wrapping structure) and crashed when that assumption didn't hold across packets. Here, singlejar's CDH parser assumes the 32-bit sentinel flags in the header always match the number of 64-bit attributes actually present in the accompanying Zip64 extra field — an attacker who crafts a CDH can set all three fixed 32-bit fields to `0xFFFFFFFF` while attaching a Zip64 extra field with `attr_count() == 1` (or 0), causing `attr_no` to reach 1 or 2 while `attr_[]` only holds 1 element (or none), reading past the field's own payload into adjacent heap bytes (other extra fields, or, if the Zip64 field is the last thing in the mapped file/buffer, past the mapped region).

`ExtraField::find`/`Zip64ExtraField::find` (`src/tools/singlejar/zip_headers.h:99-115`) only bounds-check the field's own declared `size()` against the caller-supplied `[start, end)` extra-fields window — they never validate that a *specific attribute index* used later by `compressed_file_size()`/`local_header_offset()` is within that declared payload. This is a distinct, unguarded code path from the one added for `payload_size` overflow (see `AppendToDirectoryBuffer`'s explicit bounds check at `src/tools/singlejar/output_jar.cc:936-940` and the existing `MalformedExtraField` regression test), which only guards iteration over the extra-field chain, not this index-derivation logic.

This is reachable whenever singlejar (used by `java_library`/`java_binary`/`deploy_jar` merging, and other jar-combining actions) opens an attacker-influenced jar via `InputJar::Open` → `LocateCentralDirectory` (`src/tools/singlejar/input_jar.cc:23-168`), which locates the Central Directory and hands `CDH*` pointers to the rest of singlejar without validating Zip64 attribute counts. Such a jar could originate from an `http_archive`/`http_jar` dependency served by a hostile origin, a genrule/action output built from an untrusted branch, or any jar consumed as a `srcs`/dep — none of which are validated for internal Zip64 self-consistency beyond the signature/size sanity checks already present in `LocateCentralDirectory`.

### Impact Explanation
The out-of-bounds `attr64()` read returns attacker-uncontrolled adjacent heap memory that is then used internally as `local_header_offset()` or `compressed_file_size()`. Because `local_header_offset()` is subsequently used to compute a pointer into the memory-mapped input jar to locate the entry's Local Header, a corrupted offset can drive further pointer arithmetic and reads to arbitrary offsets relative to the mapped file, which can manifest as a crash (out-of-bounds read/SIGSEGV) of the singlejar build tool. This is an integrity failure of the CDH/Zip64 parsing invariant (index totality is not enforced), not merely a resource-exhaustion issue — it is a genuine out-of-bounds memory read triggered by fully attacker-controlled archive bytes with no checksum/lockfile mechanism protecting the *internal structure* of the archive (sha256/integrity only protects the archive's bytes as a whole, not that its Zip64 extra fields are internally consistent).

### Likelihood Explanation
Any build that merges or repacks a jar via singlejar (extremely common in Bazel Java rule implementations) processes the Central Directory of every input jar. An attacker who can supply or influence the bytes of one such input jar (e.g., a `http_jar`/`http_archive` dependency, or a checked-in/generated jar on an untrusted branch that CI builds) can trivially craft a CDH whose 32-bit size/offset fields are all `0xFFFFFFFF` paired with a truncated Zip64 extra field, deterministically triggering the bug on every build that processes the file. No special privileges beyond publishing/serving the archive content are required.

### Recommendation
In `Zip64ExtraField::attr64(int index)` (or in the callers `CDH::compressed_file_size()`, `CDH::uncompressed_file_size()`, `CDH::local_header_offset()`, and the equivalent `LH` methods), validate `index < attr_count()` before dereferencing, and treat a mismatch between the CDH's 32-bit sentinel flags and the Zip64 extra field's actual `attr_count()` as a malformed-archive error (`diag_errx`), consistent with the existing "malformed extra field" handling in `output_jar.cc`.

### Proof of Concept
Construct a malformed jar/zip similar to the existing `CreateZipWithMalformedExtraField` helper in `src/tools/singlejar/output_jar_simple_test.cc:1179-1225`, but instead of an oversized `payload_size`, craft a CDH where:
- `compressed_file_size32 = uncompressed_file_size32 = local_header_offset32 = 0xFFFFFFFF`
- an attached Zip64 extra field (`tag=1`) with `payload_size = 8` (i.e. `attr_count() == 1`)

Then run singlejar (`OutputJar::Doit()`) with `--sources` pointing at this crafted jar, as in the existing `MalformedExtraField` test (`src/tools/singlejar/output_jar_simple_test.cc:1227-1236`), and observe an out-of-bounds read when `CDH::local_header_offset()`/`compressed_file_size()` computes `attr_no >= 1` and calls `z64->attr64(attr_no)`, exceeding the single declared attribute — verifiable via ASan (`heap-buffer-overflow` on read) as a new `BuildIntegrationTestCase`/gtest analogous to the existing `MalformedExtraField` test.
