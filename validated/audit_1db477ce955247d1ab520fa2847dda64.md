### Title
Dust deposit-token griefing fills an account's per-pool token list to `MAX_TOKENS_PER_USER`, permanently reverting borrows, deposits, and liquidations for that account - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
`Pool` tracks each account's deposit and debt tokens in `depositTokensOfAccount` / `debtTokensOfAccount` (`MappedEnumerableSet`) and caps the combined length at `MAX_TOKENS_PER_USER = 30` via `onlyIfAdditionWillNotReachMaxTokens`. `DepositToken._transfer` and `DepositToken._mint` call `pool.addToDepositTokensOfAccount(recipient_)` whenever the recipient's balance was zero, and `deposit()` accepts an arbitrary `onBehalfOf_` beneficiary. An unprivileged attacker can therefore push dust-sized deposit-token balances onto any victim until the victim's list hits 30, after which every flow that would add a new token to that account reverts with `UserReachedMaxTokens`.

### Finding Description
- `Pool.addToDepositTokensOfAccount` / `addToDebtTokensOfAccount` revert once `debtTokensOfAccount.length + depositTokensOfAccount.length >= 30` (`contracts/Pool.sol:143-148`, `204-220`).
- `DepositToken._transfer` adds the token to the recipient's list on first receipt (`contracts/DepositToken.sol:517-520`), and `deposit(..., onBehalfOf_)` mints directly to an arbitrary beneficiary (`contracts/DepositToken.sol:211-237`, `469-489`). Neither requires the recipient's consent.
- The attacker deposits a dust amount of each listed collateral with `onBehalfOf_ = victim`, or dust-transfers shares, filling the victim's list to 30.
- Consequences for the victim:
  - Any `DebtToken` issue/mint/flashIssue for a synthetic the victim doesn't already hold reverts inside `addToDebtTokensOfAccount`, so the victim cannot open new borrows.
  - Any deposit of a collateral type the victim doesn't already hold reverts (`_mint` → `addToDepositTokensOfAccount`), so the victim cannot top up a declining position with a different collateral asset.
  - `Pool.liquidate` → `DepositToken.seize` → `_transfer` → `addToDepositTokensOfAccount(to_)` reverts when the seized-collateral recipient (the liquidator) does not already hold that deposit token and is at the cap. The same dust-griefing applied to known liquidator/searcher addresses makes `liquidate` revert for them, delaying liquidation while the position drifts into bad debt.
- Victim self-help (transferring dust out) is bounded by `unlockedBalanceOf`/`_revertIfLocked` (`DepositToken.sol:180-182`, `348-354`), and requires up to ~30 separate transactions; meanwhile a cross-collateral rescue deposit or borrow remains impossible.
- Nothing in `SynthContext`, `nonReentrant`, `whenNotPaused`, or supply caps prevents this: `deposit`/`transfer` are public entry points and `addToDepositTokensOfAccount` is legitimately callable by any registered `DepositToken`.

### Impact Explanation
Denial of service analogous to the CVE class (availability): affected accounts cannot borrow, cannot add new collateral types, and — when applied to liquidator addresses — liquidations of underwater positions revert, allowing bad debt to accumulate and threatening protocol solvency. Funds are effectively frozen for accounts that need a new collateral type to avoid liquidation.

### Likelihood Explanation
The cost is only dust amounts of each whitelisted underlying plus gas (~30 cheap deposits/transfers). No privileged role, oracle manipulation, or governance action is required; any EOA can execute it against any account or known liquidator address. It is limited by the number of registered deposit/debt tokens available to fill the list and by the victim's ability to eventually clear slots with unlocked dust.

### Recommendation
- Do not add tokens to the per-account list on plain `transfer`/receipt; only track tokens actually used as collateral in `deposit`/`seize` flows, or
- Make `addToDepositTokensOfAccount` best-effort (skip rather than revert on cap) and handle unlisted tokens in `depositOf`/`debtPositionOf`, or
- Raise/decouple `MAX_TOKENS_PER_USER` from deposit-token receipt, or add a pull-based claim so dust cannot be forced on recipients.

### Proof of Concept
Hardhat fork sketch:

```ts
// pool, depositTokens[] = all registered DepositTokens, victim = EOA w/ existing position
for (const dt of depositTokens) {
  const underlying = await ethers.getContractAt('IERC20', await dt.underlying());
  await underlying.approve(dt.address, DUST);
  // deposit() mints to victim and calls pool.addToDepositTokensOfAccount(victim)
  await dt.deposit(DUST, victim.address);
}
expect(await pool.getDepositTokensOfAccount(victim.address)).to.have.lengthOf(30);

// victim cannot deposit a new collateral type
await expect(newDepositToken.connect(victim).deposit(1e6, victim.address))
  .to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');

// victim cannot mint a new synthetic
await expect(debtToken.connect(victim).issue(1e18))
  .to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');

// liquidation reverting for a grieved liquidator
await expect(pool.connect(liquidator).liquidate(syntheticToken, victim.address, amount, depositToken.address))
  .to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');
```

Uncertainty: I could not re-read `Pool.liquidate`'s seize-recipient wiring or `DebtToken`'s list-add path within the iteration budget; the core revert chain (`_mint`/`_transfer` → `addTo*TokensOfAccount` → `UserReachedMaxTokens`) is verified in `DepositToken.sol:486-488,517-520` and `Pool.sol:143-148,204-220`.
