### Title
Unprivileged dust-transfer griefing of `MAX_TOKENS_PER_USER` blocks deposits, transfers and liquidations - (File: contracts/Pool.sol)

### Summary
The per-account token registries `depositTokensOfAccount` / `debtTokensOfAccount` are capped at `MAX_TOKENS_PER_USER = 30`, enforced by `onlyIfAdditionWillNotReachMaxTokens` in `Pool.addToDepositTokensOfAccount` / `Pool.addToDebtTokensOfAccount` (contracts/Pool.sol:143-148, 204-220). Any holder of a `DepositToken` can `transfer()` an arbitrarily small dust amount (1 wei) to a victim; `DepositToken._transfer` then calls `pool.addToDepositTokensOfAccount(recipient_)` whenever the recipient's prior balance was zero (contracts/DepositToken.sol:517-520). An attacker can fill a victim's list with all whitelisted deposit tokens, after which every action that would add a *new* token to the victim's account reverts with `UserReachedMaxTokens`. This is the Metronome analog of the reported DoS class (unauthorized availability impact): an unprivileged account degrades protocol liveness for a targeted account with no privileged role.

### Finding Description
- `DepositToken._transfer` adds the token to the recipient's per-account list on any first receipt (contracts/DepositToken.sol:498-526). There is no minimum amount and no opt-in; the sender only needs `unlockedBalanceOf(sender) >= amount_` (contracts/DepositToken.sol:350, 383-398), which is the full balance when the sender has no debt.
- `Pool.addToDepositTokensOfAccount` reverts via `onlyIfAdditionWillNotReachMaxTokens` once `debtTokensOfAccount.length + depositTokensOfAccount.length >= 30` (contracts/Pool.sol:143-148, 216-220). The same modifier guards `addToDebtTokensOfAccount` (contracts/Pool.sol:204-208).
- Once the victim's list is full:
  - `DepositToken.deposit(amount, victim)` reverts at `_mint` → `addToDepositTokensOfAccount` for any token the victim does not yet hold (contracts/DepositToken.sol:234, 486-488).
  - Any `transfer`/`transferFrom`/`seize` sending a new token to the victim reverts (contracts/DepositToken.sol:518-519).
  - `Pool.liquidate(...)` targeting any account reverts whenever `depositToken_.seize(account_, liquidator, _toLiquidator)` would add a new token to a liquidator whose list was dust-filled, or when `seize(account_, feeCollector, _fee)` would add a new token to the fee collector's list (contracts/Pool.sol:589-592). Note the fee-collector seize path executes for every liquidation that charges a fee, so filling the fee collector's list reverts all fee-charging liquidations of collateral types it does not already hold.
- Nothing in the modifiers stops this: `transfer` is `nonReentrant`-free, requires no pool flag beyond the token existing, and works while the pool is only paused. `SynthContext._msgSender` resolution does not change reachability — the attack works directly as an EOA.

Invariant broken: liveness/availability — liquidations, deposits and settlement transfers can be made to revert at the attacker's discretion for chosen accounts.

### Impact Explanation
- Targeted users can be prevented from receiving any new deposit token type (blocking them from posting additional collateral to heal a position, blocking donations/`onBehalfOf_` deposits, and blocking OTC settlement into their account).
- More severe for shared/systemic recipients: dust-filling the `feeCollector`'s or a known liquidator bot's token list makes every liquidation that would add a new collateral token to that recipient revert (contracts/Pool.sol:592). Since the `PositionIsHealthy` check passes, the revert happens after state reads, wasting the liquidator's gas each attempt and delaying liquidation of unhealthy positions — which is precisely how bad debt accrues in fast markets. This matches the CVE's availability-impact profile (hang/repeatable crash of the service).
- Recovery is possible (victim transfers dust back out to drop entries via `removeFromDepositTokensOfAccount`, contracts/DepositToken.sol:523-524), but the attacker can re-dust in front of each retry, and unaware keepers/liquidators simply see reverts. Impact is temporary freezing / griefing of protocol operations rather than permanent loss.

### Likelihood Explanation
- Cost: the attacker needs 1 wei of each of up to ~30 deposit tokens, i.e. dust deposits in each pool collateral. `MAX_TOKENS_PER_USER` is a hard constant (contracts/Pool.sol:79), so no governance parameter needs to be adversarial.
- Preconditions: the pool must have enough whitelisted deposit tokens to fill the cap — check `getDepositTokens()` count on the deployed pools (Base/OP/BSC) versus 30 minus the victim's current entries. If the deployed pool has fewer than ~30 collaterals, the attack still works partially (blocks every token the victim doesn't already hold).
- Constraints: the attacker cannot block transfers of tokens the victim already holds (no list insertion), and cannot directly steal funds — impact is availability only, consistent with the source advisory's C:N/I:N/A:H profile.

### Recommendation
- Make list insertion non-blocking for recipients: catch/ignore `UserReachedMaxTokens` for accounting purposes, or replace the per-account enumerable cap with a mechanism that does not revert the underlying balance update (e.g., cap iterations in `debtPositionOf`/`unlockedBalanceOf` instead of reverting transfers).
- Alternatively, require a minimum (non-dust) amount for first-time list insertion, or skip `addToDepositTokensOfAccount` when `amount_` is below a threshold.
- Exempt the `feeCollector` seize path in `Pool.liquidate` from list-accounting failures (contracts/Pool.sol:591-593) so liquidation liveness cannot be tied to a recipient's list state.

### Proof of Concept
Hardhat (existing fixture style in test/Pool.test.ts):

```ts
// assumes: pool, deposit tokens [msdA ... msdN], attacker EOA funded with 1 wei of each
// 1) Attacker deposits 1 wei of underlying into every whitelisted DepositToken
// 2) For each deposit token the victim does NOT yet hold:
//    await msdX.connect(attacker).transfer(victim.address, 1)
//    // each first receipt calls pool.addToDepositTokensOfAccount(victim)
//    // until debtTokensOfAccount.length + depositTokensOfAccount.length == 30
// 3) Grief victim:
await expect(msdNew.connect(thirdParty).deposit(amt, victim.address))
  .revertedWithCustomError(pool, 'UserReachedMaxTokens');
await expect(msdNew.connect(anyone).transfer(victim.address, 1))
  .revertedWithCustomError(pool, 'UserReachedMaxTokens');
// 4) Grief liquidations via feeCollector:
//    repeat step 2 targeting poolRegistry.feeCollector() until its list hits 30,
//    then liquidate any unhealthy account with a depositToken not yet in its list:
await expect(pool.connect(liquidator)
  .liquidate(msEth.address, alice.address, amountToRepay, msdNew.address))
  .revertedWithCustomError(pool, 'UserReachedMaxTokens'); // reverts at fee seize
```

To verify on a fork, enumerate `pool.getDepositTokens()`, compute `30 - (debt + deposit tokens already held by target)`, and confirm the attacker only needs to dust that many tokens; repeat calls succeed deterministically and the target remains unable to receive new collateral types or be liquidated-through until it manually empties the dust entries.
