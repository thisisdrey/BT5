Audit Report

## Title
Reward payout marks era/page as claimed before the transfer succeeds, permanently losing staker rewards on transfer failure - (File: substrate/frame/staking-async/src/pallet/impls.rs)

## Summary
`do_payout_stakers_by_page` calls `Eras::<T>::set_rewards_as_claimed(era, &stash, page)` before performing the actual reward transfer via `payout_from_provider` → `make_payout_from_provider`. If the underlying `T::Currency::transfer` fails, the failure is caught and swallowed (logged, `None` returned) rather than propagated as a `DispatchError`. Since the dispatchable does not error out, the earlier `set_rewards_as_claimed` write is not rolled back, permanently marking the era/page reward as paid even though the transfer never happened.

## Finding Description
`do_payout_stakers_by_page` ensures the reward for `(era, stash, page)` hasn't already been claimed, then immediately commits `Eras::<T>::set_rewards_as_claimed(era, &stash, page)` at line 386, with the comment "Input data seems good, no errors allowed after this point" confirming this is treated as an irrevocable checkpoint.

The subsequent payout path, when `use_dap_payout` is active, calls `Self::payout_from_provider`, which for each beneficiary calls `Self::make_payout_from_provider`. If `T::Currency::transfer(&staker_rewards_pot, &payout_account, amount, Preservation::Expendable)` fails, the code logs the error and `return None;` — the caller `payout_from_provider` simply skips depositing a `Rewarded` event for that beneficiary and moves on; the overall `do_payout_stakers_by_page` function still returns `Ok(...)`. The identical swallow-and-log pattern exists in `transfer_validator_incentive` for the validator's own incentive payout, which returns unit and only logs/deposits an `Unexpected` event on failure.

Because the dispatchable returns `Ok`, FRAME's per-extrinsic transactional wrapper does not roll back any storage writes made earlier in the call, including `set_rewards_as_claimed`. Only an `amount.is_zero()` check exists prior to the transfer attempt in `make_payout_from_provider` — there is no check that the destination account can actually receive the transfer (e.g., ED satisfaction for non-existent accounts), no retry mechanism, and no propagation of the underlying `DispatchError` back up to the caller.

## Impact Explanation
This is a real fund-loss path: once `Eras::<T>::set_rewards_as_claimed` is set for `(era, stash, page)`, `payout_stakers`/`payout_stakers_by_page` refuses to run again for that page (the `AlreadyClaimed` check). If the transfer to a nominator, staker, or validator fails for any legitimate on-chain reason (e.g., the reward amount being below the existential deposit for a non-existent destination account, or the reward pot's liquidity being insufficient at that instant), that beneficiary's reward for that era/page is permanently lost — it can never be reclaimed, since the "claimed" flag is already set and irreversible. This matches the "permanent user-fund lock" / "duplicate or skipped settlement" impact category, since the payout-state marker advances despite settlement never completing.

## Likelihood Explanation
This does not require a malicious peer, validator, governance actor, or leaked key — it is an unprivileged, permissionless dispatchable path (`payout_stakers` / `payout_stakers_by_page`) that any account can trigger for any validator/era/page combination. The failure condition (a reward transfer to a small/dust or otherwise transfer-rejecting destination account) is a normal, achievable on-chain condition rather than a contrived edge case, making this a realistic, repeatable scenario rather than purely theoretical.

## Recommendation
Move `Eras::<T>::set_rewards_as_claimed(era, &stash, page)` to occur only after all payout transfers for that page have been attempted and confirmed successful, or make `make_payout_from_provider`/`transfer_validator_incentive` propagate transfer failures as a hard `Err` from `do_payout_stakers_by_page` so the entire extrinsic (including the "claimed" marker) is rolled back atomically when any payout fails. Alternatively, retain a per-beneficiary retry/pending-payout mechanism instead of unconditionally marking the whole page as claimed regardless of individual transfer outcomes.

## Proof of Concept
1. Configure a nominator's `RewardDestination::Account(x)` where account `x` does not yet exist on-chain and the nominator's computed reward for a given `(era, page)` is smaller than the chain's existential deposit.
2. Call `payout_stakers_by_page(validator_stash, era, page)` (or `payout_stakers`) as any signed account.
3. Observe: `set_rewards_as_claimed(era, &stash, page)` is committed before the transfer attempt; inside `make_payout_from_provider`, `T::Currency::transfer(..., Preservation::Expendable)` fails (destination cannot be created below ED), the error is logged via `log!(error, ...)`, and `None` is returned — no `Rewarded` event is emitted for that nominator.
4. The extrinsic completes with `Ok(...)`. Re-invoking `payout_stakers_by_page` for the same `(era, stash, page)` returns `Error::<T>::AlreadyClaimed`, confirming the nominator's reward is permanently unclaimable and the funds were never delivered.
