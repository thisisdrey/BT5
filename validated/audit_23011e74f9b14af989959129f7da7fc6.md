### Title
Missing flashloan-reentrancy guard on `vault.redeem` lets an attacker withdraw against stale liquidity accounting during a flashloan callback - ([File: mainnet/contracts/vault/v0-vault-stx.clar])

### Summary
Across all six vault contracts (`v0-vault-stx.clar`, `v0-vault-sbtc.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`, and their `local-testing` counterparts), the `deposit` function is explicitly protected against being invoked while a flashloan callback is executing, but the sibling state-mutating function `redeem` is not. This is the same class of asymmetric-guard bug as the H-16 report: one entry point (`withdrawETH`/`deposit`) is reentrancy-protected while a related function that mutates the same shared accounting (`claimRewards`/`redeem`) is not, letting it be invoked mid-transaction while shared state is in a transient, inconsistent condition.

### Finding Description
In `deposit`, the guard is present: [1](#0-0) 

In `redeem`, this same check is absent — only pause/amount/slippage/liquidity checks are performed: [2](#0-1) 

`redeem` burns shares, then sends the underlying out, and only afterward decrements the internal `assets` ledger variable: [3](#0-2) 

The reentrancy window is created by `flashloan`, which explicitly invokes an attacker-supplied callback contract *after* sending the borrowed funds out and *before* pulling them back, while a reentrancy flag `in-flashloan` is set true: [4](#0-3) 

`deposit` checks `in-flashloan` to prevent being called during this window, but `redeem` does not. This means a flashloan borrower's callback contract (which at that point in execution actually holds the borrowed underlying tokens, since `send-underlying` already ran) can call back into `redeem` on the same vault. At that moment:
- the vault's real token balance has already been reduced by the outstanding flashloan amount (`send-underlying amount funds-receiver-resolved` already executed),
- but the vault's internal accounting variable `assets` (used to compute `available-assets`/`current-assets` inside `redeem`) has not been adjusted for the flashloan, since flashloan-in-progress state is not reflected in `assets` until repayment.

This is structurally identical to the H-16 root cause: a state variable (`idleETH`/`assets`) is decremented at a different point in the call sequence than when the real transfer happens, and a second function without the reentrancy guard (`claimRewards`/`redeem`) is invoked in that gap, computing results from the stale/inconsistent state.

### Impact Explanation
Because `redeem`'s liquidity/solvency checks (`current-assets`, `available-assets`) are derived from the ledger variable that hasn't been synchronized with the vault's real token custody during an in-flight flashloan, a reentrant `redeem` call executed from the flashloan callback can pass checks that should fail (or succeed on liquidity that has, in reality, already left the contract). The subsequent `send-underlying inkind recipient` call in `redeem` competes with the flashloan's own outstanding obligation for the same pool of real tokens. This can result in over-withdrawal relative to actual vault liquidity, corrupting the `assets`/share accounting relationship for all remaining LPs and creating a shortfall other depositors cannot recover — i.e., theft of user funds at rest / protocol insolvency for the affected vault.

### Likelihood Explanation
The precondition is being an approved flashloan borrower (`can-flashloan` permission) supplying a malicious `flash-callback` contract, and holding/acquiring `zft` vault shares to redeem during the callback. Flashloan whitelisting is a deliberate access control the DAO manages, but once a principal is whitelisted for flashloans (a normal, expected operational state, not a compromise), nothing in `redeem` stops them from reentering during their own callback. This is a straightforward, single-transaction attack requiring no oracle manipulation, DAO compromise, or third-party dependency — only calling `redeem` from within the flashloan callback.

### Recommendation
Add the same `(asserts! (not (var-get in-flashloan)) ERR-REENTRANCY)` guard to `redeem` (and audit `system-borrow`/`system-repay` and any other state-mutating public functions in the vault for the same omission) so that no accounting-mutating entry point can be invoked while a flashloan callback is in flight, mirroring the guard already applied to `deposit`.

### Proof of Concept
1. Attacker (or an account they control) is whitelisted with `can-flashloan: true` on a vault (e.g. `v0-vault-stx.clar`).
2. Attacker holds `zft` shares in that vault (via normal `deposit`).
3. Attacker calls `flashloan` with a malicious `flash-callback` contract as `fc`.
4. Inside `flashloan`, after `in-flashloan` is set `true` and `send-underlying amount funds-receiver-resolved` has already transferred real tokens out of the vault, the vault calls `(contract-call? fc callback amount fee data)`.
5. The malicious callback re-enters the same vault's `redeem` function with the attacker's `zft` shares. Since `redeem` never checks `in-flashloan`, it proceeds, computing `available-assets`/`current-assets` from the stale `assets` var that has not been reduced for the in-flight flashloan, and transfers additional real underlying tokens to the attacker via `send-underlying`.
6. The callback returns; `flashloan` then attempts `receive-underlying (+ amount fee) funds-provider`, pulling back the flashloaned principal+fee — but the vault's real balance has now been depleted twice (once for the flashloan payout, once for the reentrant redeem), corrupting the relationship between outstanding `zft` supply and actual backing assets.

Note: I was not able to fully verify the exact implementation of `get-available-assets` (i.e., whether it reads the `assets` ledger variable or queries the real on-chain token balance directly) before running out of tool iterations; this detail determines whether the attack succeeds on the first reentrant call or requires a specific vault-balance/flashloan-size ratio. The core finding — that `redeem` lacks the `in-flashloan` reentrancy guard present on `deposit` — is directly confirmed by reading the contract source across all six vault files.
