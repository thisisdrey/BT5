### Title
Uninitialized `accountIndexOf` is read as zero instead of `INITIAL_INDEX`, letting a depositor claim reward tokens equal to their full balance - ([File: contracts/RewardsDistributor.sol](contracts/RewardsDistributor.sol))

### Summary
`RewardsDistributor._calculateTokenDelta` reads `accountIndexOf[token_][account_]`, which is uninitialized (`0`) for any account that has never been indexed. A guard exists to substitute `INITIAL_INDEX` (1e18) in that case, but it only fires when the token index is *strictly greater* than `INITIAL_INDEX`. While the token index sits exactly at `INITIAL_INDEX` (speed newly set, or accrued ratio truncating to zero), the zero value is used as-is, producing a delta index of 1e18 and crediting the account rewards equal to its entire token balance.

### Finding Description
In `_calculateTokenDelta` (contracts/RewardsDistributor.sol:217-231):

```solidity
uint256 _accountIndex = accountIndexOf[token_][account_];

if (_accountIndex == 0 && _tokenIndex > INITIAL_INDEX) {
    _accountIndex = INITIAL_INDEX;
}

uint256 _deltaIndex = _tokenIndex - _accountIndex;
_tokensDelta = token_.balanceOf(account_).wadMul(_deltaIndex);
```

The intent is clear: a never-seen account should be treated as if it entered at `INITIAL_INDEX`, so its delta is zero until rewards actually accrue. The strict `>` comparison defeats this when `tokenStates[token_].index == INITIAL_INDEX`, which happens:

- right after `_updateTokenSpeed` initializes `tokenStates[token_] = TokenState({index: INITIAL_INDEX, ...})` (line 298), and
- whenever `_tokensAccrued.wadDiv(_totalSupply)` truncates to `0` in `_calculateTokenIndex` (line 206), so the index never advances past 1e18 even though `tokenSpeeds` is nonzero — a persistent state for a large-supply DepositToken/DebtToken with a small speed.

In that window `_deltaIndex = 1e18 - 0 = 1e18`, so `_tokensDelta = balanceOf(account).wadMul(1e18) = balanceOf(account)`. This path is reached by any caller via the public, `nonReentrant` `claimRewards(accounts_, tokens_)` (line 150) → `_updateTokensAccruedOf` (line 261) → `_calculateTokenDelta`, or via `updateBeforeMintOrBurn`/`updateBeforeTransfer`. `_transferRewardIfEnoughTokens` (line 248) then pays out as long as the distributor holds enough reward tokens.

This mirrors the CVE-2024-7526 bug class — a parameter/slot that was never initialized is read and its raw default value flows into a sensitive computation — here an uninitialized storage slot rather than uninitialized GPU memory.

### Impact Explanation
An attacker deposits into the affected DepositToken (or borrows on the DebtToken), immediately calls `claimRewards([attacker], [token])`, and receives reward tokens equal to their deposit balance, bounded only by the distributor's reward-token balance. This drains the reward pool — tokens earmarked for all users' accrued yield — i.e., direct theft of unclaimed yield. It is repeatable across fresh attacker EOAs (each uninitialized account index is independently exploitable) and across each token whose index is still at `INITIAL_INDEX`.

### Likelihood Explanation
Likelihood is condition-dependent but realistically reachable: it triggers whenever a reward token's index has not yet grown past `INITIAL_INDEX`, which includes the whole period where the per-block accrual ratio truncates to zero (large `totalSupply`, small `speed`, short elapsed time — common right after `updateTokenSpeeds` for a new distribution). The attacker needs no privileged role; `claimRewards` is permissionless and `nonReentrant` does not block it. Existing holders' indexes may already be initialized, but any new account is eligible. The main constraint is that the distributor must hold reward tokens, which is the normal funded state.

### Recommendation
Change the guard in `_calculateTokenDelta` to apply the fallback whenever the account index is unset, i.e. `if (_accountIndex == 0) { _accountIndex = INITIAL_INDEX; }` — or, more generally, `_accountIndex = _accountIndex == 0 ? _tokenIndex < INITIAL_INDEX ? _tokenIndex : INITIAL_INDEX : _accountIndex` semantics that ensure a first-time account can never claim rewards accrued before its first observed index. Alternatively, set `accountIndexOf` to the current index at first interaction and skip the delta entirely when it was `0`.

### Proof of Concept
Hardhat (fork) outline:

```ts
// Preconditions: pool, depositToken (e.g. msUSD/vaUSD deposit token) and
// rewardsDistributor deployed; governor sets speed so
// tokenStates[depositToken].index == INITIAL_INDEX and the accrued
// wadDiv ratio is 0 (call claimRewards in the same block as the
// speed update, or use a speed so small that delta*speed*1e18 < totalSupply).

await depositToken.connect(attacker).deposit(attacker.address, depositAmount);
// attacker has never interacted -> accountIndexOf[depositToken][attacker] == 0

const distBal = await rewardToken.balanceOf(distributor.address);
await distributor.connect(attacker).claimRewards(
  [attacker.address],
  [depositToken.address]
);
// tokensDelta = depositAmount (wadMul by 1e18) -> tokensAccruedOf == depositAmount
// _transferRewardIfEnoughTokens pays min(depositAmount, distBal)

expect(await rewardToken.balanceOf(attacker.address)).to.eq(
  BigNumber.from(depositAmount).lte(distBal) ? depositAmount : distBal
);
```

Uncertainty note: this relies on the deployed state where `tokenStates[token_].index == INITIAL_INDEX` is reachable with `index > 0` (set) — true immediately after speed initialization and whenever the accrual ratio truncates to zero; a fork PoC should pin a block right after a `updateTokenSpeeds` call or simulate a low-speed/high-supply token to keep the index pinned at `INITIAL_INDEX`.
