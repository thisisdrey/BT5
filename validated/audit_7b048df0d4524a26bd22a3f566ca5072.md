### Title
StackerDB write-policy cache falls back to an unbounded `noop()` config on any contract-config load failure, silently disabling the on-chain `max-writes` cap - (File: stackslib/src/net/stackerdb/mod.rs)

### Summary
`PeerNetwork::refresh_stacker_db_configs` reloads each replica's `StackerDBConfig` from its controlling smart contract every time the burnchain view changes, and the freshly loaded config is used immediately for all subsequent chunk-write validation without any check that the load actually succeeded and reflects canonical, up-to-date contract state.

### Finding Description
`create_or_reconfigure_stackerdbs` iterates every configured StackerDB contract and tries to reload its policy with `StackerDBConfig::from_smart_contract`. If that call fails for any reason (DB error, unreadable contract analysis, transient Clarity read failure, etc.), the code falls back to `StackerDBConfig::noop()`: [1](#0-0) 

`noop()` sets `max_writes: u32::MAX` and `write_freq: 0`, i.e. it removes the write-count cap and the per-slot write-frequency throttle entirely: [2](#0-1) 

Crucially, this fallback config is unconditionally inserted into the returned map that becomes the node's new in-memory `stacker_db_configs`, regardless of whether the previous (good) config existed: [3](#0-2) 

The comment on `noop()` explicitly acknowledges this class of risk for `chunk_size` (capping it at `STACKERDB_MAX_CHUNK_SIZE` to avoid it ever being "looser" than intended when it "transiently overwrite[s] a good in-memory config on a failed refresh"), but no equivalent mitigation is applied to `max_writes`/`write_freq`: [4](#0-3) 

This stale/overwritten config is then used, unchecked, in the write-acceptance path. Both the HTTP write handler and the P2P push-chunk handler validate `slot_version` against `config.max_writes` before persisting a chunk: [5](#0-4) [6](#0-5) 

Neither `try_handle_request` in the RPC handler nor `handle_unsolicited_StackerDBPushChunk`/`validate_received_chunk` verify that the `StackerDBConfig` currently in `self.stacker_db_configs` actually reflects the canonical, successfully-loaded on-chain policy before using it to gate writes. There is no analog of the "cache is synced" guard the referenced report recommends: any signer that already owns a valid slot in that StackerDB can exploit a window where a contract-config reload failed (and thus `max_writes` collapsed to `u32::MAX`) to submit unlimited version-bumped, validly-signed chunks that would otherwise have been rejected as `TooManySlotWrites` under the real, contract-defined cap.

### Impact Explanation
This degrades an explicit on-chain policy (`max-writes`, `write-freq`) — enforced identically to a StackerDB "auth/quota gate" — into a fail-open state. A legitimate slot owner (any registered signer for that StackerDB) can flood the DB with unbounded chunk writes/version bumps whenever the node's cached config has silently fallen back to `noop()`, bypassing the intended write-count ceiling and disabling the write-frequency throttle across the whole StackerDB replica set (since `slot_versions`/inventories propagate the accepted writes to peers). This is a policy/quota bypass reachable by any already-authorized StackerDB writer, not requiring privileged/administrative access, and can materially increase per-slot storage churn and downstream sync/bandwidth cost across the network.

### Likelihood Explanation
The reload path runs automatically on every burnchain-tip change via `refresh_burnchain_view` → `refresh_stacker_db_configs` → `create_or_reconfigure_stackerdbs`, so any transient failure to read/evaluate the StackerDB-controlling contract (e.g., a Clarity read hiccup, or a contract that is temporarily unparsable/invalid per `is_contract_valid`) causes the fallback and gets silently written back into the live config map used by every write path, with no explicit distinction between "genuinely reconfigured to noop by design" and "failed to load, defaulted to noop by accident."

### Recommendation
Do not let a failed `StackerDBConfig::from_smart_contract` call silently replace a previously-good in-memory config with `noop()`. On failure, retain the last-known-good config (as is effectively done for `chunk_size`, but should be generalized to `max_writes`/`write_freq`/`signers`), or explicitly mark the StackerDB config as "unsynced" and reject/queue writes until a successful reload occurs — mirroring the reported fix's approach of gating operator-dependent operations on a verified "cache is synced" state before allowing writes.

### Proof of Concept
1. Configure a StackerDB whose controlling contract has a strict `max-writes` value.
2. Force `StackerDBConfig::from_smart_contract` to error for one reload cycle (e.g., transient Clarity DB read error or a contract analysis hiccup) while a burnchain-tip change triggers `refresh_stacker_db_configs`.
3. Observe `create_or_reconfigure_stackerdbs` catches the error and substitutes `StackerDBConfig::noop()` (`max_writes: u32::MAX`), inserting it into `stacker_db_configs` (`stackslib/src/net/stackerdb/mod.rs:388-405`, `429-434`).
4. As a legitimate slot owner, submit chunks with monotonically increasing `slot_version` well beyond the contract's real `max-writes` cap via `POST /v2/stackerdb/.../chunks` — `try_replace_chunk`'s `TooManySlotWrites` check now compares against `u32::MAX` and never rejects (`stackslib/src/net/stackerdb/db.rs:430-436`).
5. These writes propagate to peers via normal StackerDB gossip/sync since they pass `validate_received_chunk` against the same degraded config (`stackslib/src/net/stackerdb/mod.rs:709-715`).

impl StackerDBConfig {
    /// Config that does nothing
    pub fn noop() -> StackerDBConfig {
        StackerDBConfig {
            // Cap the chunk size at the protocol-wide maximum rather than u64::MAX.
            // `noop()` is used as a fallback whenever a replica's real config can't be
            // loaded (see `create_or_reconfigure_stackerdbs`), and it can transiently
            // overwrite a good in-memory config on a failed refresh. Since the DB slots
            // persist independently of the config, writes can still land on existing
            // slots while `noop()` is active, so its chunk-size limit must never be
            // looser than `STACKERDB_MAX_CHUNK_SIZE`.
            chunk_size: STACKERDB_MAX_CHUNK_SIZE as u64,
            write_freq: 0,
            max_writes: u32::MAX,
            hint_replicas: vec![],
            max_neighbors: 8,
            signers: vec![],
        }
    }
