### Title
Unverified attacker-supplied content permanently persisted as `was_instantiated=1` via `AtlasDB::insert_instantiated_attachment` - (File: `stackslib/src/net/atlas/download.rs`, `stackslib/src/net/atlas/db.rs`)

### Summary
`AttachmentsBatchStateContext::extend_with_attachments` accepts and stores any `Attachment` returned in an `AttachmentRequest` HTTP response into `context.attachments` without checking that the received content's hash equals the `content_hash` that was actually requested. When the batch state machine reaches `Done`, every attachment in that set is unconditionally written via `AtlasDB::insert_instantiated_attachment` with `was_instantiated=1`, a status class that is never touched by either eviction routine, which only delete `was_instantiated=0` rows.

### Finding Description
The claimed equality — "bytes stored with `was_instantiated=1` == bytes committed by a confirmed name operation" — is broken by the following path:

1. `AttachmentsBatchStateContext::extend_with_attachments` iterates `results.succeeded` and does `self.attachments.insert(response.attachment)` with no comparison against `request.content_hash`: [1](#0-0) 
2. In the `Done` state of `AttachmentsDownloader::run`, every attachment drained from `context.attachments` is unconditionally passed to `network.atlasdb.insert_instantiated_attachment(&attachment)`, regardless of whether `find_all_attachment_instances(&attachment.hash())` found any matching row: [2](#0-1) 
3. `AtlasDB::insert_instantiated_attachment` performs an unconditional `INSERT OR REPLACE INTO attachments (... was_instantiated=1 ...)` keyed by `attachment.hash()` (a hash computed from the attacker-supplied content itself, not the originally requested `content_hash`): [3](#0-2) 
4. Both eviction routines only ever delete `was_instantiated = 0` rows, so nothing ever reclaims rows inserted through this path: [4](#0-3) 

Because the stored row is keyed by the hash of the attacker's own bytes (not the hash the node actually asked for), a malicious peer that is a source for a legitimately-pending `AttachmentRequest` can return arbitrary content (up to the `attachments_max_size` bound enforced during HTTP decoding) instead of the real attachment. That content will never correspond to any `attachment_instances.content_hash` row, yet it is written with `was_instantiated=1` and is permanently retained.

### Impact Explanation
A remote peer that is included as a source for a real, currently-outstanding `AttachmentRequest` (i.e., the node is legitimately trying to sync a BNS attachment referenced by a confirmed name operation) can substitute unrelated attacker-chosen bytes in its HTTP response. Each such response permanently persists up to `attachments_max_size` bytes of garbage in the node's `attachments` table under a status that is exempt from all eviction, unlike normal unresolved/uninstantiated attachments. Because each fake response is content-addressed by the attacker's own chosen bytes, repeating this across many distinct outstanding requests (or many hashes if the attacker also controls what content_hash values appear achievable, e.g. by being the sole/one source across multiple missing-attachment entries in a batch) causes unbounded disk growth that is never reclaimed — a mismatch between committed BNS state and durable attachment storage (an attachment/BNS mismatch class of impact).

### Likelihood Explanation
Preconditions: the attacker must run a peer that (a) is included in the node's outbound sync peer set, and (b) advertises (via `GetAttachmentsInv`) that it has the attachment for a content hash the node is actually trying to resolve for a legitimately confirmed name operation, so that the node issues it a real `AttachmentRequest`. No secret, admin role, or privileged access is required — only normal P2P/RPC reachability and running a peer that participates in Atlas attachment inventory/sync, both attacker-achievable as an unprivileged remote party. This is repeatable per resolved batch/attachment request cycle.

### Recommendation
In `AttachmentsBatchStateContext::extend_with_attachments` (`stackslib/src/net/atlas/download.rs`), verify that `response.attachment.hash() == request.content_hash` before inserting into `self.attachments`; discard and penalize (bump failed requests / mark peer faulty) responses that don't match. Additionally, in the `Done` handler, only call `insert_instantiated_attachment` when `find_all_attachment_instances` returns a non-empty result for that hash (i.e., there is an actual `attachment_instances` row awaiting it), so unsolicited/mismatched content is never persisted as `was_instantiated=1`.

### Proof of Concept
Rust net test in `stackslib/src/net/atlas/download.rs` tests (or `tests.rs`):
1. Seed `AtlasDB` with an `AttachmentInstance` row (status `Checked`) for a known `content_hash` H, simulating a confirmed name operation referencing an unresolved attachment.
2. Drive `AttachmentsBatchStateMachine` through `DownloadingAttachment` with a mocked HTTP peer that, when asked for `content_hash = H`, returns a `GetAttachmentResponse` containing `Attachment{ content: <attacker bytes>, ... }` whose `hash()` is some `H' != H`.
3. Call `AttachmentsDownloader::run` to reach `Done`, then assert:
   - `SELECT SUM(LENGTH(content)) FROM attachments WHERE was_instantiated=1` includes the attacker bytes under hash `H'`.
   - `SELECT * FROM attachment_instances WHERE content_hash = H'` is empty (no confirmed name operation ever referenced `H'`).
   - Repeated calls to `evict_k_oldest_uninstantiated_attachments` / `evict_expired_uninstantiated_attachments` do not reduce the row for `H'`, confirming permanent, unbounded retention of unverified content.

    pub fn evict_k_oldest_uninstantiated_attachments(&mut self, k: u32) -> Result<(), db_error> {
        let tx = self.tx_begin()?;
        let res = tx.execute(
            "DELETE FROM attachments WHERE hash IN (SELECT hash FROM attachments WHERE was_instantiated = 0 ORDER BY created_at ASC LIMIT ?)",
            params![k],
        );
        res.map_err(db_error::SqliteError)?;
        tx.commit().map_err(db_error::SqliteError)?;
        Ok(())
    }

    pub fn evict_expired_uninstantiated_attachments(&mut self) -> Result<(), db_error> {
        let now = util::get_epoch_time_secs() as i64;
        let cut_off = now - self.atlas_config.uninstantiated_attachments_expire_after as i64;
        let tx = self.tx_begin()?;
        let res = tx.execute(
            "DELETE FROM attachments WHERE was_instantiated = 0 AND created_at < ?",
            params![cut_off],
        );
        res.map_err(db_error::SqliteError)?;
        tx.commit().map_err(db_error::SqliteError)?;
        Ok(())
    }

    pub fn insert_instantiated_attachment(
        &mut self,
        attachment: &Attachment,
    ) -> Result<(), db_error> {
        let now = util::get_epoch_time_secs() as i64;
        let tx = self.tx_begin()?;
        tx.execute(
            "INSERT OR REPLACE INTO attachments (hash, content, was_instantiated, created_at) VALUES (?, ?, 1, ?)",
            params![attachment.hash(), attachment.content, now],
        )?;
        tx.execute(
            "UPDATE attachment_instances SET is_available = 1 WHERE content_hash = ?1 AND status = ?2",
            params![attachment.hash(), AttachmentInstanceStatus::Checked],
        )?;
        tx.commit()?;
        Ok(())
    }
