### Title
Unbounded array allocation from attacker-controlled length in TVM precompiled contracts `ValidateMultiSign`/`BatchValidateSign` causes node OutOfMemoryError DoS - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The CVE describes a DoS in `qst_vec_set_copy` where a crafted SQL statement causes an unchecked vector-copy allocation to blow memory. The equivalent bug class in java-tron is present in the byte-array-extraction helpers used by the `ValidateMultiSign` (address `0x66`) and `BatchValidateSign` (address `0x67`) precompiled contracts: an array is allocated (`new byte[len][]`) using a length value taken directly from attacker-controlled call data, before any upper-bound is enforced, when the legacy (non-`allowTvmSelfdestructRestriction`) code path is exercised.

### Finding Description
`extractBytesArray` and `extractBytes32Array` read a 32-byte word from the raw calldata and use it, without any range validation, as the size of a new Java array of byte-array references: [1](#0-0) 

`extractBytes32Array` in particular has no offset bound check at all and directly does `new byte[len][]` with `len = words[offset].intValueSafe()`, which an attacker fully controls.

In `ValidateMultiSign.execute`, the `MAX_SIZE` bound (`sigArraySize > MAX_SIZE`) is only checked **before** allocation when `VMConfig.allowTvmSelfdestructRestriction()` is enabled, and only for the `extractSigArray` path; the legacy `extractBytesArray` branch (used when the flag is disabled) performs the length check only **after** the array has already been allocated: [2](#0-1) 

`BatchValidateSign.doExecute` has the same pattern, and additionally calls `extractBytes32Array` for `addresses` unconditionally, with its `MAX_SIZE` guard only applied inside the `allowTvmSelfdestructRestriction()` branch: [3](#0-2) 

Because `getEnergyForData` computes the energy charge from `data.length / WORD_SIZE`, not from the embedded length word, an attacker can submit a small `data` payload (cheap to pay for) that encodes a huge `len` value (up to `Integer.MAX_VALUE`) at the offset read by `extractBytesArray`/`extractBytes32Array`. The resulting `new byte[len][]` allocation (8 bytes per reference on a 64-bit JVM, before any element is populated) can request gigabytes of heap for a length in the hundreds of millions, triggering an `OutOfMemoryError` in the node process executing the contract call.

### Impact Explanation
An `OutOfMemoryError` thrown while executing a TVM precompile during transaction/block processing can crash or destabilize the executing node (validator or full node), or force JVM-wide GC thrashing that halts servicing of further requests — a concrete "node crash / node can no longer serve" DoS condition triggered by a single, cheaply-priced signed transaction (`TriggerSmartContract` calling address `0x66` or `0x67`), reachable by any unprivileged transaction broadcaster.

### Likelihood Explanation
The attack requires only crafting calldata for a `CALL` to a known precompile address, computable off-chain and broadcastable as a normal transaction; no special privileges are needed. Reachability is conditioned on the `allowTvmSelfdestructRestriction()` hard-fork parameter being disabled for the code path being executed (e.g. on private/consortium chains, older/historic block replay, or any network where this feature switch has not been activated); on networks where it is enabled, only `ValidateMultiSign`'s `extractBytesArray` legacy branch and `BatchValidateSign`'s unconditional `extractBytes32Array` call for `addresses` remain exposed since the pre-checks (`sigArraySize`, `addrArraySize`) do not cover every allocation performed. I was not able to confirm from the indexed code whether `allowTvmSelfdestructRestriction()` is unconditionally forced "on" for all currently-running mainnet nodes; this should be verified against the live chain parameters.

### Recommendation
Enforce a `MAX_SIZE` bound check on the length word immediately after reading it inside `extractBytesArray` and `extractBytes32Array` themselves (defense in depth), before allocating the array, regardless of the `allowTvmSelfdestructRestriction()` flag or the calling precompile's own external check. Also validate `offset` bounds in `extractBytes32Array` as is already done in `extractBytesArray`.

### Proof of Concept
1. Craft calldata for a `CALL` to precompile address `0x67` (`BatchValidateSign`) such that `words[2]` (the address-array offset pointer) resolves to a word encoding a large `len` (e.g. `0x7FFFFFFF`), while keeping the total `data.length` small so `getEnergyForData` charges minimal energy.
2. Ensure `allowTvmSelfdestructRestriction()` is not active for the executing path (e.g., a private/test network or historical block execution before hard-fork activation).
3. Submit a `TriggerSmartContract` transaction invoking this precompile call from a deployed contract.
4. During execution, `extractBytes32Array` executes `new byte[len][]`, attempting a multi-gigabyte allocation and raising `OutOfMemoryError`, destabilizing the node executing/validating the transaction.

  private static byte[][] extractBytes32Array(DataWord[] words, int offset) {
    int len = words[offset].intValueSafe();
    byte[][] bytes32Array = new byte[len][];
    for (int i = 0; i < len; i++) {
      bytes32Array[i] = words[offset + i + 1].getData();
    }
    return bytes32Array;
  }

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
