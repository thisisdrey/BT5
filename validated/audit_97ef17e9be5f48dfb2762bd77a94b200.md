### Title
StackerDB write-frequency policy (`write-freq`) is never enforced on chunk writes, allowing unbounded rapid overwrites and forged-chunk propagation - (File: `stackslib/src/net/stackerdb/db.rs`, `stackslib/src/net/stackerdb/mod.rs`)

### Summary
The external report describes a scheme where an actor holding a legitimate stake (the challenger's collateral) exploits a missing rate/cost control to repeatedly trigger a state-changing action (`restrictMinting`) with effectively no real cost, because the protocol enforces some checks (bid ≥ price) but omits the one control (a cost on repeated false challenges) that would prevent abuse. The same class of bug — a declared throttle that is never actually checked at the enforcement point — exists in this repo's StackerDB chunk-write path: the smart-contract-declared `write-freq` policy is loaded into `StackerDBConfig` but is never consulted when a chunk write is validated or committed.

### Finding Description
A StackerDB smart contract declares a `write-freq` value as part of its control interface, intended to bound how often a given slot may be rewritten [1](#0-0) . This value is parsed and stored into `StackerDBConfig.write_freq` [2](#0-1) .

However, the actual chunk-acceptance logic never reads or enforces `config.write_freq`:
- The RPC write path `try_replace_chunk` in `db.rs` checks chunk size, slot existence, signature validity, staleness (monotonic version), and `max_writes`, but performs no wall-clock/write-frequency check at all [3](#0-2) .
- `PeerNetwork::validate_received_chunk`, which gates both pulled and pushed/gossiped chunks, likewise checks size, signer, staleness and `max_writes`, but never references `write_freq` — its own doc comment explicitly notes "does not check write frequency, since the caller has different ways of doing this" [4](#0-3) .
- The HTTP `POST /stackerdb` handler (`RPCPostStackerDBChunkRequestHandler::try_handle_request`) forwards straight into `try_replace_chunk`, with no separate throttle check before storing the chunk [5](#0-4) .

Grepping the codebase confirms `write_freq` is only referenced in `sync.rs` (used purely to pace this node's own *pull* scheduling when acting as a sync client) and in `config.rs`/tests — it is never used as a gate in the *storage write* path (`db.rs`) or in the *validation* path applied to unsolicited pushes (`mod.rs`). This breaks the equality between "declared write policy (write-freq)" and "actually enforced write policy": the smart contract's stated throttle is silently non-canonical at the enforcement point, while callers/downstream code (and application authors relying on `write-freq` for cost control) treat it as if it were canonical.

### Impact Explanation
Any legitimate slot signer (an application/user who holds a valid slot per the controlling smart contract, analogous to the "challenger" in the original report who legitimately puts up collateral) can bump a slot's version and rewrite/broadcast a chunk as fast as the network allows, up to `max_writes` times, completely ignoring the `write-freq` throttle the contract author intended. Because each valid write is re-broadcast to peers via StackerDB replication (store-and-forward gossip) [6](#0-5) , this allows a signer to force repeated network-wide propagation of new "valid" data far faster than the smart contract's policy permits, exhausting the `max_writes` budget instantly and generating outsized p2p/storage/bandwidth load across all replicating nodes for that DB — a violation of the smart contract's write-rate policy that the protocol claims to enforce.

### Likelihood Explanation
Any actor with a legitimately assigned slot (no special node secret or admin privilege required — only a StackerDB slot signer key, which is application-specific and can be broadly distributed, e.g. signer sets) can trivially trigger this by issuing rapid consecutive `POST /stackerdb` requests or unsolicited `StackerDBPushChunk` messages with incrementing versions. No collusion or race condition is needed; the check is simply absent.

### Recommendation
Enforce `config.write_freq` as a wall-clock gate in `try_replace_chunk` (using the persisted `write_time` from `SlotValidation`, already tracked in `insert_chunk`) before allowing a version bump, and likewise enforce it in `PeerNetwork::validate_received_chunk` for pushed/gossiped chunks, returning a dedicated error/ack code (e.g. `TooFrequentWrites`) analogous to `TooManySlotWrites`.

### Proof of Concept
1. Deploy/observe a StackerDB contract with `write-freq: u3600` (intended: at most one write per hour per slot) and `max-writes: u4096`.
2. As the registered signer for slot `N`, sign and `POST` a chunk with `slot_version = 1`; it is accepted by `try_replace_chunk` [7](#0-6) .
3. Immediately sign and `POST` another chunk with `slot_version = 2`, then `3`, `4`, ... up to `max_writes`, all within the same second. None of these are rejected by a frequency check, because none exists — they are only checked for size, signature, monotonic version, and the `max_writes` ceiling.
4. Each accepted write is relayed to peer nodes replicating this DB, producing network-wide propagation and storage churn far exceeding the contract-declared `write-freq` policy.

    /// Otherwise, this errors out with Error::StaleChunk
    pub fn try_replace_chunk(
        &self,
        smart_contract: &QualifiedContractIdentifier,
        slot_desc: &SlotMetadata,
        chunk: &[u8],
    ) -> Result<(), net_error> {
        // Check per-replica chunk-size cap.
        if (chunk.len() as u64) > self.config.chunk_size {
            return Err(net_error::StackerDBChunkTooBig(chunk.len()));
        }

        let slot_validation = self
            .get_slot_validation(smart_contract, slot_desc.slot_id)?
            .ok_or(net_error::NoSuchSlot(
                smart_contract.clone(),
                slot_desc.slot_id,
            ))?;

        if !slot_desc.verify(&slot_validation.signer)? {
            return Err(net_error::BadSlotSigner(
                slot_validation.signer,
                slot_desc.slot_id,
            ));
        }
        if slot_desc.slot_version <= slot_validation.version {
            return Err(net_error::StaleChunk {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
            });
        }
        if slot_desc.slot_version > self.config.max_writes {
            return Err(net_error::TooManySlotWrites {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
                max_writes: self.config.max_writes,
            });
        }
        self.insert_chunk(smart_contract, slot_desc, chunk)
    }

    /// Validate chunk data either downloaded (with [`StackerDBSync::validate_downloaded_chunk`]), or
    /// pushed to us (with [`PeerNetwork::handle_unsolicited_StackerDBPushChunk`])
    ///
    /// NOTE: does not check write frequency, since the caller has different ways of doing this.
    /// Returns:
    /// - Ok(true) if the chunk is valid
    /// - Ok(false) if the chunk is invalid
    /// - Err(..) on DB error
    pub fn validate_received_chunk(
        &self,
        smart_contract_id: &QualifiedContractIdentifier,
        config: &StackerDBConfig,
        data: &StackerDBChunkData,
        expected_versions: &[u32],
    ) -> Result<bool, net_error> {
        // validate -- must not exceed this replica's configured chunk size.
        if (data.data.len() as u64) > config.chunk_size {
            info!(
                "Received StackerDBChunk for {} ID {}, which is oversized: {} bytes (max {} bytes)",
                smart_contract_id,
                data.slot_id,
                data.data.len(),
                config.chunk_size
            );
            return Ok(false);
        }

        // validate -- must be a valid chunk
        let Some(expected_version) = expected_versions.get(data.slot_id as usize) else {
            info!(
                "Received StackerDBChunk for {} ID {}, which is too big ({})",
                smart_contract_id,
                data.slot_id,
                expected_versions.len()
            );
            return Ok(false);
        };

        // validate -- must be signed by the expected author
        let addr = match self
            .stackerdbs
            .get_slot_signer(smart_contract_id, data.slot_id)?
        {
            Some(addr) => addr,
            None => {
                return Ok(false);
            }
        };

        let slot_metadata = data.get_slot_metadata();
        if !slot_metadata.verify(&addr)? {
            info!(
                "StackerDBChunk for {} ID {} is not signed by {}",
                smart_contract_id, data.slot_id, &addr
            );
            return Ok(false);
        }

        // validate -- must be the current or newer version
        if data.slot_version < *expected_version {
            info!(
                "Received StackerDBChunk for {} ID {} version {}, which is stale (expected {})",
                smart_contract_id, data.slot_id, data.slot_version, *expected_version
            );
            return Ok(false);
        }

        // validate -- must not exceed max writes
        if data.slot_version > config.max_writes {
            info!(
                "Write count exceeded for StackerDBChunk for {} ID {} version {} (max is {})",
                smart_contract_id, data.slot_id, data.slot_version, config.max_writes
            );
            return Ok(false);
        }

        Ok(true)
    }
