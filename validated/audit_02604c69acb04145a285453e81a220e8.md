### Title
Protocol trading fee is entirely bypassable by settling trustless swaps via `Transfer` intents instead of `TokenDiff` intents - (File: contracts/defuse/core/src/intents/tokens.rs)

### Summary
The Golom bug allowed a maker/taker pair to guarantee a trustless trade while hiding the true value from the fee-computation path, so the marketplace's fee logic never saw the real trade amount. The `defuse` Verifier has a structurally identical fee-bypass surface: its protocol fee is computed and collected *only* inside `TokenDiff::execute_intent`, while `Transfer::execute_intent` moves balances between two different signers with zero fee logic at all. Two counterparties can achieve the exact same trustless, atomic swap semantics that `TokenDiff` is meant to provide — just by each signing a `Transfer` intent to the other and having a relayer submit both `MultiPayload`s in one `execute_intents` call — and pay zero protocol fee.

### Finding Description
`TokenDiff::execute_intent` is the only code path in `defuse-core` that reads `engine.state.fee()` and collects `fees_collected` into the `fee_collector` account [3](#0-2) . This is the mechanism the protocol relies on to monetize "trustless P2P trades" as advertised: two parties who don't trust each other sign complementary `TokenDiff` deltas and have them settled atomically, with the protocol taking a cut on the negative (token-in) side [4](#0-3) .

However, the exact same trust-minimized, atomic, all-or-nothing settlement semantics can be achieved using `Transfer` intents instead. `Transfer::execute_intent` only checks that `sender_id != receiver_id` and that `tokens` is non-empty, then calls `internal_sub_balance`/`internal_add_balance` directly — no fee is computed, no `fee()` lookup occurs anywhere in this path [5](#0-4) .

Because `execute_intents` / `execute_signed_intents` iterates over an arbitrary `Vec<MultiPayload>` and executes each signed intent set in sequence within one contract call, and any error anywhere causes the whole call to panic/revert (no partial execution is persisted) [6](#0-5) [7](#0-6) , two independent, mutually-distrusting parties (Alice, Bob) can each sign a `Transfer` intent — Alice: "send 1000 USDT to Bob", Bob: "send 1000 USDC to Alice" — and submit both `MultiPayload`s together via a single `execute_intents([alice_transfer, bob_transfer])` call. Either both transfers land or neither does, exactly the atomicity guarantee that `TokenDiff` provides, but with `fee = 0` because the `Transfer` code path never consults `Pips`/`fee()` at all.

This directly parallels the Golom root cause: the fee-bearing code path (`o.totalAmt`/`TokenDiff.diff`) is not the only path capable of moving the same economic value between two willing counterparties; an alternate, fee-blind path (`AvoidsFeesContract`/`Transfer`) provides equivalent settlement guarantees and is fully reachable by any unprivileged user with no special permissions, roles, or contract deployment ignoring documented config — `Transfer` is a first-class, always-enabled intent type in the public `Intent` enum [2](#0-1) .

### Impact Explanation
This crosses the "fees owed versus fees collected" custody binding: the protocol fee model implicitly assumes `fees_collected(trade_value) = fee_rate × trade_value` for every P2P trade settled by the Verifier, but for trades routed through paired `Transfer` intents, `fees_collected = 0` regardless of `trade_value`. Any two users (solvers, market makers, or the general public) can permanently avoid the protocol's designed fee-take on volume that would otherwise be settled as a `TokenDiff` swap, directly reducing protocol revenue at scale ("fees bypassed" — listed as a Critical-severity impact category). Because there is no cap or detection distinguishing "legitimate transfer" traffic from "disguised fee-free trade" traffic, this can be systematically exploited by relayers/solvers who route all counterparty-matched swaps as `Transfer` pairs instead of `TokenDiff`, defeating the fee mechanism entirely and undermining the "network effects" monetization model in the same way the Golom `AvoidsFeesContract` did.

### Likelihood Explanation
Likelihood is high: no special role, deployment misconfiguration, or trusted party is required — any two signer accounts with valid public keys registered on the Verifier can construct this today using only documented, publicly-exposed functionality (`Transfer` intent + `execute_intents` batching), which is exactly how the test suite already demonstrates atomic multi-payload submission is supported (`defuse_simulate_and_execute_intents`/`execute_intents(signed: Vec<MultiPayload>)`) [7](#0-6) . Relayers or solvers have direct financial incentive to always prefer the fee-free `Transfer` path whenever both sides' desired amounts are known in advance (which is the normal RFQ/solver flow shown in the repository's own tests) [8](#0-7) .

### Recommendation
Either (a) compute and collect protocol fees generically at the `Engine`/`Deltas` finalize layer based on net-negative balance deltas per signer across *all* intent types (not only `TokenDiff`), so `Transfer`-based swaps are taxed identically to `TokenDiff`-based swaps, or (b) restrict `Transfer` to same-owner/self-custody movements (e.g., require `receiver_id` to be an account controlled by the same signer, or disallow using `Transfer` as a substitute for atomic multi-party swaps by charging a fee whenever a `Transfer`'s `sender_id`/`receiver_id` pair appears in a reciprocal pattern within the same `execute_intents` batch). Auditing at the `finalize()` invariant-checking layer (`contracts/defuse/core/src/engine/mod.rs:113-118`) for aggregate volume moved between two accounts within one call, and taxing it consistently with `TokenDiff`'s fee model, closes the gap.

### Proof of Concept
1. Alice deposits 1000 USDT into the Verifier; Bob deposits 1000 USDC.
2. Alice signs a `Transfer` intent: `{ receiver_id: Bob, tokens: {USDT: 1000} }` via `sign_defuse_payload_default`, producing `MultiPayload` `A`.
3. Bob signs a `Transfer` intent: `{ receiver_id: Alice, tokens: {USDC: 1000} }`, producing `MultiPayload` `B`.
4. Any relayer calls `execute_intents([A, B])` (or `defuse_execute_intents`) in a single transaction, mirroring the pattern already exercised in `tests/src/tests/defuse/intents/transfer.rs:35-106` and `crates/testing/sandbox/src/extensions/defuse/mod.rs:532-546`.
5. Because `Transfer::execute_intent` never calls `state.fee()` (confirmed by grep: `fee()` only appears in `token_diff.rs`, `deltas.rs`, and `cached.rs` internals, never in `tokens.rs`), the swap completes atomically with `fees_collected = 0`, whereas the equivalent `TokenDiff` trade of the same value would have collected `protocol_fee × amount` into `fee_collector` per `TokenDiff::execute_intent` lines 56-77 [3](#0-2) .
6. Repeat at scale: any solver network can route 100% of matched counterparty flow through paired `Transfer` intents, permanently avoiding the protocol fee that `TokenDiff` was designed to collect.

    pub fn execute_signed_intents(
        mut self,
        signed: impl IntoIterator<Item = MultiPayload>,
    ) -> Result<Transfers> {
        for signed in signed {
            self.execute_signed_intent(signed)?;
        }
        self.finalize()
    }

    fn execute_signed_intent(&mut self, signed: MultiPayload) -> Result<()> {
        // verify signed payload and get public key
        let public_key = signed.verify().ok_or(DefuseError::InvalidSignature)?;

        // calculate intent hash
        let hash = signed.hash();

        // extract NEP-413 payload
        let DefusePayload::<DefuseIntents> {
            signer_id,
            verifying_contract,
            deadline,
            nonce,
            message: intents,
        } = signed.extract_defuse_payload()?;

        // check recipient
        if verifying_contract != *self.state.verifying_contract() {
            return Err(DefuseError::WrongVerifyingContract);
        }

        self.inspector.on_deadline(deadline);

        // make sure message is still valid
        if deadline < Timestamp::now() {
            return Err(DefuseError::DeadlineExpired);
        }

        // make sure the account has this public key
        if !self.state.has_public_key(&signer_id, &public_key) {
            return Err(DefuseError::PublicKeyNotExist(signer_id, public_key));
        }

        // commit nonce
        self.verify_intent_nonce(nonce, deadline)?;
        self.state.commit_nonce(signer_id.clone(), nonce)?;

        intents.execute_intent(&signer_id, self, hash)?;
        self.inspector.on_intent_executed(&signer_id, hash, nonce);

        Ok(())
    }
