### Title
StackerDB chunk signatures omit the contract ID, enabling cross-contract signed-chunk replay - (File: `libstackerdb/src/libstackerdb.rs`)

### Summary
`SlotMetadata::auth_digest()` computes the signed digest from only `slot_id`, `slot_version`, and `data_hash` [1](#0-0) . It does not bind the signature to the specific StackerDB smart-contract instance the chunk is destined for. Because many Stacks signer StackerDB contracts (e.g. `signers-1-1`, `signers-1-2`, `signers-1-3` for message types `BlockResponse`, `StateMachineUpdate`, `BlockPreCommit`) assign the *same* signer address to the *same* `slot_id` within a signer set — since all of them read the identical slot-id ordering from `.signers`' `stackerdb-get-signer-slots-page` [2](#0-1)  and `stacks-core--008: stackslib/src/chainstate/stacks/boot/signers-1-xxx.clar` [3](#0-2)  — a chunk signed by a signer for one contract can be replayed verbatim into another sibling contract that assigns the same signer the same slot, and the signature will still validate, since the verifier only checks the recovered address against the destination contract's per-slot signer, never checking which contract the signature was made for.

### Finding Description
`StackerDBChunkData::verify()` / `SlotMetadata::verify()` recover a public key strictly from the `auth_digest` (slot_id||slot_version||data_hash) and compare its hash to the expected address stored per-slot for the *target* contract [4](#0-3) . This is exactly the "affiliate key reuse" pattern from the external report: a signature intended for context A (contract A) is accepted verbatim in context B (contract B) because the signed payload never commits to the context/contract identifier.

Both the node-side `PeerNetwork::validate_received_chunk` (gossip/download path) [5](#0-4)  and `StackerDBTx::try_replace_chunk` (HTTP POST-write path, used by `/v2/stackerdb/:principal/:contract/chunks` [6](#0-5) ) look up the expected signer using the destination `smart_contract_id` and `slot_id`, then call `SlotMetadata::verify(&addr)`, which is contract-agnostic. Neither path re-derives or checks that the signature was produced with the destination contract in mind.

Because signer-slot assignment for a signer set is computed once from `.signers` and shared across all per-message-type sibling contracts (`signers-{0|1}-{1,2,3}`) [7](#0-6) , the same signer address occupies the same `slot_id` in every sibling contract for a given signer set. StackerDB chunk contents (including signatures) are broadcast and readable by anyone via the p2p StackerDB protocol and HTTP GET endpoints, so any remote, unprivileged party can observe a legitimately-signed `StackerDBChunkData` for one message-type contract and re-POST the identical bytes (`slot_id`, `slot_version`, `sig`, `data`) to a different sibling contract, where it will pass `BadSigner`/`BadSlotSigner` checks and get written and gossiped as if it were an authentic message of the second type.

### Impact Explanation
This allows an unauthenticated third party to forge/relay data into a StackerDB slot of one message type using a signature that was only ever produced for a different message type — an unauthenticated write to state / network-wide propagation of forged data, since accepted chunks are re-gossiped to peers by the StackerDB sync logic. This matches the "Critical" bar for "unauthenticated/unauthorized write to state or StackerDB, network-wide propagation of forged data."

The practical severity depends on whether the replayed bytes deserialize into a valid message of the target contract's expected type (e.g. `SignerMessage` variant) — a `BlockResponse` chunk's raw bytes are unlikely to parse as a valid `StateMachineUpdate`. However, the vulnerability itself is a real authentication-boundary break: the signature commits to *nothing* that ties it to the destination contract, which is a structural flaw regardless of whether every payload cross-decodes today. Any future addition of sibling StackerDB contracts sharing slot assignments and compatible/overlapping payload schemas would be immediately exploitable for state confusion/DoS on signer coordination.

### Likelihood Explanation
Reaching the bug requires no privileged access: an attacker only needs to observe one legitimately-broadcast chunk (chunks are not secret — they are propagated in the clear over p2p and served over the public `GET /v2/stackerdb/...` API) and re-POST it to a sibling contract's `chunks` endpoint. The slot-id-per-signer overlap across sibling contracts is a structural property of the current signer-set/StackerDB layout [7](#0-6) , not an unusual configuration.

### Recommendation
Include the StackerDB contract identifier (`QualifiedContractIdentifier`) in `SlotMetadata::auth_digest()` so that a signature is only valid for the specific StackerDB instance it was produced for, analogous to the AffiliateValidator fix that folded the contract address into the signed key hash. This requires a wire/protocol version bump since it changes what is signed by all StackerDB writers.

### Proof of Concept
1. Identify two sibling StackerDB contracts for the same signer set that assign an attacker-controlled or victim signer the same `slot_id` (e.g. `signers-1-1` and `signers-1-2`), confirmed via `.signers`' `stackerdb-get-signer-slots-page` returning identical `slot_id` ordering for both [8](#0-7) .
2. Passively observe (via p2p gossip or `GET /v2/stackerdb/.../{slot_id}`) a legitimately-signed `StackerDBChunkData { slot_id, slot_version, sig, data }` written to `signers-1-1`.
3. Re-POST the identical `StackerDBChunkData` bytes to `POST /v2/stackerdb/<addr>/signers-1-2/chunks` (adjusting `slot_version` upward if needed to beat the current stored version for that slot in contract 2).
4. Observe that `StackerDBTx::try_replace_chunk` accepts the write — `SlotMetadata::verify()` succeeds because it never checked which contract the signature was meant for [4](#0-3)  — even though the signer never authorized a write to `signers-1-2`.
