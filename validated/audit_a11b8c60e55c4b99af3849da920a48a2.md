### Title
`AddressRegistrar::register` does not refund excess attached deposit on successful registration - (File: `runtime/near-wallet-contract/implementation/address-registrar/src/lib.rs`)

### Summary
The `register` method of the `AddressRegistrar` contract (part of the eth-implicit Wallet Contract system) checks only that the attached deposit is *at least* the storage cost (`given_deposit < required_deposit` → panic), but never refunds the excess when `given_deposit > required_deposit` and the entry is newly inserted. Any amount attached beyond the exact storage cost is silently kept by the contract with no way for the caller to reclaim it.

### Finding Description
`register` computes the exact `required_deposit` for storing the `address -> account_id` mapping and requires `given_deposit >= required_deposit`: [1](#0-0) 

When the entry is `Vacant` (the normal, successful path), the mapping is inserted and the address returned, but `given_deposit` is never compared against `required_deposit` again, and no transfer back of the difference is issued: [2](#0-1) 

Contrast this with the `Occupied` branch (address collision, no storage written), where the *entire* `given_deposit` is refunded via a transfer promise: [3](#0-2) 

This is the same bug class as the referenced Sherlock finding: a check that only enforces `attached >= required` instead of `attached == required` (or explicitly refunding the delta), meaning excess funds attached by the caller are absorbed by the contract instead of returned. There is no other method in `AddressRegistrar` (`lookup`, `get_address`, `new`) that allows withdrawing this excess balance, so any amount attached above the exact storage cost is permanently stuck in the contract.

The register call is reached from the Wallet Contract's ERC-20/base-token relayer flow (`inner_rlp_execute` / `parse_rlp_tx_to_action` in `runtime/near-wallet-contract/implementation/wallet-contract/src/internal.rs` and `lib.rs`), where relayers or callers can attach NEAR deposits when invoking `register` on behalf of a user account.

### Impact Explanation
Any caller (a relayer, a user, or an automated integration) that over-estimates the storage deposit and attaches more than the exact `required_deposit` when calling `register` on a successful (non-colliding) registration permanently loses the difference — the funds remain locked in the `AddressRegistrar` contract's balance with no method exposed to withdraw or reclaim them. This is a permanent loss-of-funds bug for the caller, matching the "concrete theft or permanent freezing of funds" acceptance criterion. It's a self-contained contract bug (not a protocol runtime bug), but it lives in the in-scope eth-implicit wallet-contract ecosystem code, exploitable by any ordinary, unprivileged caller.

### Likelihood Explanation
Likelihood is moderate: it requires a caller (or misconfigured relayer script) to intentionally or mistakenly attach more than the exact computed storage byte cost. Since `NearToken`/attached-deposit amounts are commonly rounded up (e.g., to whole NEAR or milliNEAR units, or set with a safety margin) by integrators unfamiliar with the exact per-byte storage price, over-attachment is a realistic and easy-to-trigger scenario, especially given there is no incentive check preventing it and the function is `#[payable]` with no upper bound enforced.

### Recommendation
Refund the difference between `given_deposit` and `required_deposit` in the `Vacant` branch, mirroring the refund logic already present in the `Occupied` branch:
```rust
Entry::Vacant(entry) => {
    let address_str = format!("0x{}", hex::encode(address));
    entry.insert(account_id);
    let excess = given_deposit.saturating_sub(required_deposit);
    if excess > NearToken::from_yoctonear(0) {
        let refund_promise = env::promise_batch_create(&env::predecessor_account_id());
        env::promise_batch_action_transfer(refund_promise, excess);
    }
    Some(address_str)
}
```
Alternatively, require `given_deposit == required_deposit` exactly and panic otherwise (as in the referenced report's suggested fix), though refunding the excess is friendlier to callers.

### Proof of Concept
1. A relayer or user calls `AddressRegistrar::register(account_id)` attaching, e.g., `2 * required_deposit` NEAR (rounding up because the exact per-byte storage cost is hard to compute off-chain).
2. Since `account_id`'s derived address is not yet registered, the `Entry::Vacant` branch executes: the mapping is inserted and `Some(address)` is returned.
3. `given_deposit - required_deposit` (the excess) is never transferred back to the caller; it remains part of the `AddressRegistrar` contract's account balance.
4. There is no method in the contract (`lookup`, `get_address`, or any owner-only withdrawal function) that lets the caller or anyone recover this excess — the funds are permanently unspendable by the original depositor.

Note: I was unable to find any owner/admin withdrawal function elsewhere in the `address-registrar` crate (only `lib.rs` exists in that crate), which confirms the excess deposit has no recovery path within the current codebase as indexed.
