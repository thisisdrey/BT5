### Title
Active-permission key can unilaterally rewrite the Owner permission via `AccountPermissionUpdateContract`, enabling account takeover — (File: `actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java`)

### Summary
`AccountPermissionUpdateActuator` allows any transaction signer whose *Active* permission's operation bitmap includes the `AccountPermissionUpdateContract` type to completely replace an account's Owner, Witness, and Active permissions in a single transaction, with no check that ties the new permission set to the previously-authorized signer's privilege level. This mirrors the ShenYu bug class (CVE-2022-37435): a lower-privileged credential is able to overwrite the highest-privileged credential due to an authorization gap between "is this operation type allowed" and "is this specific privileged change allowed."

### Finding Description
Transaction-level authorization for a non-default permission is gated only by `WalletUtil.checkPermissionOperations`, which checks a single bit in the signer's `Permission.operations` bitmap corresponding to the contract type being submitted: [1](#0-0) 

This check is invoked from `TransactionCapsule.checkPermission`, used both when signing (`addSign`) and when validating a submitted transaction (`validateSignature`): [2](#0-1) [3](#0-2) 

If an Active permission's `operations` bitmap has the `AccountPermissionUpdateContract` bit set (which the validator only checks is a *valid* contract type, not that it's an appropriately-scoped one — see the bit-validation loop against `dynamicStore.getAvailableContractType()`): [4](#0-3) 

then that Active-key holder can submit an `AccountPermissionUpdateContract` with permissionId pointing to their own Active permission. `AccountPermissionUpdateActuator.validate()` only validates the *shape* of the new permissions (key counts, weights, threshold sums, distinctness, operations size) — it never compares the new `Owner`/`Witness`/`Active` permission sets against the old ones, and never requires that the change be co-signed by the current Owner permission itself: [5](#0-4) 

`execute()` then unconditionally overwrites all permissions on the account: [6](#0-5) 

The result: a signer holding only an Active-level key (intended to be scoped to specific operations such as transfers) can, if that Active permission's operations bitmap happens to include `AccountPermissionUpdateContract`, replace the account's Owner permission with keys/thresholds entirely of their choosing — removing the legitimate high-privilege owner and/or granting themselves Owner-level control. This is structurally identical to the ShenYu flaw: a lower-privileged principal is permitted to overwrite a higher-privileged principal's credentials because the authorization model checks "is this contract type allowed" rather than "is this specific privileged mutation allowed by someone with sufficient standing."

### Impact Explanation
Successful exploitation allows unauthorized full account takeover: the attacker (holding only an Active key) can set the Owner permission's keys to their own address(es) with a low threshold, lock out or delete all of the legitimate owner's and other active signers' keys, and/or grant themselves an Active permission scoped to move funds (`TransferContract`, `TransferAssetContract`) or perform other high-value ContractTypes. This is a concrete unauthorized account operation and a path to theft/permanent freezing of funds for the legitimate account holder.

### Likelihood Explanation
Exploitability depends on whether an account's Active permission has been configured (by the owner, potentially unintentionally, since permission templates commonly grant broad operation coverage) to include the `AccountPermissionUpdateContract` bit in its `operations` bitmap. Once that precondition holds — which is plausible for any multisig/permission setup that uses a broadly-scoped Active key rather than a narrowly restricted one — exploitation requires nothing more than a single signed transaction from that Active key; no additional privilege or timing is needed.

### Recommendation
Require that `AccountPermissionUpdateContract` transactions can only be authorized by the account's Owner permission (permissionId == 0), or, if delegation via Active permission is intentionally supported, add an explicit safeguard in `AccountPermissionUpdateActuator.validate()` that the new Owner permission must be co-signed/authorized by the current Owner permission (or otherwise verify that an Active-permission signer cannot elevate its own privileges beyond its granted scope, e.g., disallow inclusion of `AccountPermissionUpdateContract` in any but Owner-authorized flows).

### Proof of Concept
1. Account `A` has Owner permission `{ownerKey}` (threshold 1) and an Active permission (id=2) `{activeKey}` whose `operations` bitmap includes `AccountPermissionUpdateContract` (the default active permission covers the full available-contract-type bitmap, as validated in `checkPermission`, `actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java:137-144`).
2. Attacker who controls `activeKey` (but not `ownerKey`) constructs an `AccountPermissionUpdateContract` for account `A`, setting `contract.getPermissionId() = 2` (the Active permission id) and defining a brand new Owner permission `{attackerKey}` with threshold 1, dropping `ownerKey` entirely.
3. Attacker signs the transaction with `activeKey`. `TransactionCapsule.checkPermission` passes because `checkPermissionOperations` only verifies the `AccountPermissionUpdateContract` bit is set on the Active permission (`chainbase/src/main/java/org/tron/common/utils/WalletUtil.java:27-37`).
4. `AccountPermissionUpdateActuator.validate()` accepts the new Owner permission since it only checks structural validity (`actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java:71-146`), not any relationship to the prior owner.
5. `execute()` overwrites the account's permissions (`actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java:49-51`), giving the attacker sole Owner control of account `A` and locking out the legitimate owner.

  public static boolean checkPermissionOperations(Permission permission, Contract contract)
      throws PermissionException {
    ByteString operations = permission.getOperations();
    if (operations.size() != 32) {
      throw new PermissionException(String.format("operations size must 32, actual: %d",
          operations.size()));
    }
    int contractType = contract.getTypeValue();
    boolean b = (operations.byteAt(contractType / 8) & (1 << (contractType % 8))) != 0;
    return b;
  }

  @Override
  public boolean validate() throws ContractValidateException {

    if (chainBaseManager == null) {
      throw new ContractValidateException(ActuatorConstant.STORE_NOT_EXIST);
    }

    if (this.any == null) {
      throw new ContractValidateException(ActuatorConstant.CONTRACT_NOT_EXIST);
    }

    AccountStore accountStore = chainBaseManager.getAccountStore();
    DynamicPropertiesStore dynamicStore = chainBaseManager.getDynamicPropertiesStore();

    if (dynamicStore.getAllowMultiSign() != 1) {
      throw new ContractValidateException("multi sign is not allowed, "
          + "need to be opened by the committee");
    }
    if (!this.any.is(AccountPermissionUpdateContract.class)) {
      throw new ContractValidateException(
          "contract type error,expected type [AccountPermissionUpdateContract],real type["
              + any.getClass() + "]");
    }
    final AccountPermissionUpdateContract accountPermissionUpdateContract;
    try {
      accountPermissionUpdateContract = any.unpack(AccountPermissionUpdateContract.class);
    } catch (InvalidProtocolBufferException e) {
      logger.debug(e.getMessage(), e);
      throw new ContractValidateException(e.getMessage());
    }
    byte[] ownerAddress = accountPermissionUpdateContract.getOwnerAddress().toByteArray();
    if (!DecodeUtil.addressValid(ownerAddress)) {
      throw new ContractValidateException("invalidate ownerAddress");
    }
    AccountCapsule accountCapsule = accountStore.get(ownerAddress);
    if (accountCapsule == null) {
      throw new ContractValidateException("ownerAddress account does not exist");
    }

    if (!accountPermissionUpdateContract.hasOwner()) {
      throw new ContractValidateException("owner permission is missed");
    }

    if (accountCapsule.getIsWitness()) {
      if (!accountPermissionUpdateContract.hasWitness()) {
        throw new ContractValidateException("witness permission is missed");
      }
    } else {
      if (accountPermissionUpdateContract.hasWitness()) {
        throw new ContractValidateException("account isn't witness can't set witness permission");
      }
    }

    if (accountPermissionUpdateContract.getActivesCount() == 0) {
      throw new ContractValidateException("active permission is missed");
    }
    if (accountPermissionUpdateContract.getActivesCount() > 8) {
      throw new ContractValidateException("active permission is too many");
    }

    Permission owner = accountPermissionUpdateContract.getOwner();
    Permission witness = accountPermissionUpdateContract.getWitness();
    List<Permission> actives = accountPermissionUpdateContract.getActivesList();

    if (owner.getType() != PermissionType.Owner) {
      throw new ContractValidateException("owner permission type is error");
    }
    checkPermission(owner);
    if (accountCapsule.getIsWitness()) {
      if (witness.getType() != PermissionType.Witness) {
        throw new ContractValidateException("witness permission type is error");
      }
      checkPermission(witness);
    }
    for (Permission permission : actives) {
      if (permission.getType() != PermissionType.Active) {
        throw new ContractValidateException("active permission type is error");
      }
      checkPermission(permission);
    }
    return true;
  }
