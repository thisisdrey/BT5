### Title
Byte-accounting mismatch in `Parser.prunePatch` allows resource-limit bypass in `CommitDiff` diff parsing - (File: internal/gitaly/diff/diff.go)

### Summary
`Parser.prunePatch()` decrements `bytesProcessed` by `len(parser.currentDiff.Patch)`, but `bytesProcessed` was only ever incremented by `parser.currentDiff.byteCount` (a narrower count that excludes hunk-header lines and any patch data appended outside of "stat-updating" chunk consumption). This asymmetric add/subtract accounting is directly analogous to the reported Solidity bug class, where a value is decremented by an amount that was never actually added to it, silently driving a running counter far below its true value. Because Gitaly uses signed Go `int`, this doesn't "wrap" like a `uint256` would, but it produces the same functional defect: the tracked resource counter becomes permanently and increasingly negative/understated, disabling the very safety checks it exists to enforce.

### Finding Description
In `internal/gitaly/diff/diff.go`, each call to `Parser.Parse()` updates counters after reading a diff: [1](#0-0) 

`byteCount` is only accumulated in `consumeChunkLine` when `updateStats` is `true` (content lines prefixed with `-`, `+`, ` `, `\`, `~\n`) — hunk header lines (`@@ ... @@`) are explicitly excluded from stats even though their bytes are still appended to `diff.Patch`: [2](#0-1) [3](#0-2) 

When the parser decides to collapse a diff (`CollapseDiffs` + over safe limits) or when a single patch exceeds `MaxPatchBytes`, it calls `prunePatch()`, which subtracts the **full** `len(patch)` (including all hunk-header bytes that were never added to `bytesProcessed`) rather than the previously-added `byteCount`: [4](#0-3) 

Net effect per pruned diff: `bytesProcessed` decreases by `(byteCount_added - len(Patch)_subtracted)`, which is negative whenever the diff contains hunk headers — i.e., essentially always for real diffs with multiple hunks. Every subsequent collapse/prune event drives `bytesProcessed` further below its true cumulative value. The same mismatch model also applies conceptually to `linesProcessed`/`lineCount`, though that pair is more consistently tracked; the byte pair is the concrete divergent case.

`bytesProcessed` (and `linesProcessed`) directly gate both:
- `isOverSafeLimits()` used to trigger `CollapseDiffs`: [5](#0-4) 
- The hard `EnforceLimits` stop condition: [6](#0-5) 

Once `bytesProcessed` is driven sufficiently negative by repeated pruning, both the soft (`SafeMaxBytes`) collapse mechanism and the hard (`MaxBytes`) enforcement stop mechanism become ineffective for a large number of subsequent files, since the counter must first climb back above zero and then above the configured limit before either check fires again.

### Impact Explanation
This is directly reachable by any ordinary caller of the `CommitDiff` RPC, whose limits (`MaxBytes`, `SafeMaxBytes`, `MaxPatchBytes`, `CollapseDiffs`, `EnforceLimits`) are all client-supplied request fields, and whose diff content is produced from repository data that an attacker fully controls (their own commits/pushes): [7](#0-6) [8](#0-7) 

By crafting a repository whose commits generate diffs with many small hunks (maximizing hunk-header byte count relative to counted content bytes) and triggering an initial prune/collapse, an attacker can suppress the effectiveness of `SafeMaxBytes`/`MaxBytes` accounting for a large number of subsequent files in the same `CommitDiff` response, causing Gitaly to buffer and stream far more patch data than the caller's own limits intend. This is a resource-limit bypass in an RPC handler that can amplify memory/CPU consumption and gRPC response size beyond configured bounds — a DoS-class issue on the Gitaly node, exactly the kind of "RPC-handler resource limits" defect called for in scope.

### Likelihood Explanation
Likelihood is high for triggering the accounting defect itself (it fires on any diff with hunk headers plus any collapse/prune event, which is common), but the *severity* of the bypass is proportional to how much hunk-header overhead an attacker can accumulate relative to `SafeMaxBytes`/`MaxBytes` — this requires deliberately crafting many small hunks across many files, which is straightforward for an attacker who controls repository content and RPC parameters (both true for `CommitDiff`, an ACCESSOR RPC available to any client authorized to read the repository).

### Recommendation
Make the increment/decrement of `bytesProcessed` (and ideally `linesProcessed`) symmetric: either subtract exactly what was added (track and subtract `currentDiff.byteCount`, not `len(currentDiff.Patch)`), or count hunk-header bytes into `byteCount` at accumulation time so both operations touch the same quantity. E.g. in `prunePatch`, replace `parser.bytesProcessed -= len(parser.currentDiff.Patch)` with `parser.bytesProcessed -= parser.currentDiff.byteCount`.

### Proof of Concept
1. Send a `CommitDiff` RPC request with `EnforceLimits: true`, `CollapseDiffs: true`, and small `SafeMaxBytes`/`MaxBytes` values, against a repository containing several files each with many small hunks (e.g., dozens of `@@ -n,1 +n,1 @@` single-line hunks per file, so hunk-header bytes dominate over the 1-2 content bytes counted per hunk).
2. The first file(s) exceed `SafeMaxBytes` and get collapsed via `prunePatch()`, subtracting `len(Patch)` (large, includes all hunk headers) while only `byteCount` (small, content-line bytes only) was ever added.
3. `bytesProcessed` goes deeply negative.
4. Subsequent files, even if individually large, no longer trigger `isOverSafeLimits()` / `maxBytesExceeded` checks until `bytesProcessed` climbs back above the configured thresholds, allowing much more patch data to be streamed/buffered than the caller's limits should permit.

Note: I was unable to run this PoC against a live Gitaly instance in this environment; the analysis is based on static code review of `internal/gitaly/diff/diff.go` and its test suite (`internal/gitaly/diff/diff_test.go`), which confirms the `byteCount` vs `len(Patch)` distinction via existing test fixtures (e.g. `TestDiffParserWithLargeDiffWithFalseCollapseDiffsFlag` shows `byteCount: 12500000` vs `PatchSize: 12500021`, an 21-byte discrepancy from a single hunk header in that test case). A background Devin session with repository access could construct and run the full PoC to empirically confirm the magnitude of the bypass.

```go
func consumeChunkLine(reader *bufio.Reader, diff *Diff, skipPatch, updateStats bool) error {
	// The code that follows would be much simpler if we used
	// bufio.Reader.ReadBytes, but that allocates an intermediate copy of
	// each line which adds up to a lot of allocations. By using ReadSlice we
	// can copy bytes into currentDiff.Patch without intermediate
	// allocations.
	var byteCount int
	for done := false; !done; {
		line, err := reader.ReadSlice('\n')
		if updateStats && byteCount == 0 && len(line) > 0 {
			if line[0] == '+' {
				diff.LinesAdded++
			} else if line[0] == '-' {
				diff.LinesRemoved++
			}
		}
		byteCount += len(line)

		switch {
		case errors.Is(err, bufio.ErrBufferFull):
			// long line: keep reading
		case err != nil && !errors.Is(err, io.EOF):
			return fmt.Errorf("read chunk line: %w", err)
		default:
			done = true
		}

		if !skipPatch {
			diff.Patch = append(diff.Patch, line...)
		}
	}

	if updateStats {
		diff.byteCount += byteCount
		diff.lineCount++
	}

	return nil
```
