### Title
RewardsDistributor._calculateTokenIndex() advances the timestamp without accruing rewards when a rewarded token's totalSupply is zero, permanently losing emissions - (File: contracts/RewardsDistributor.sol)

### Summary
`RewardsDistributor` streams `rewardToken` at `tokenSpeeds[token]` per second, accruing via a supply index. In `_calculateTokenIndex`, when `token_.totalSupply() == 0` the accrual `_ratio` is forced to `0`, but `_newTimestamp` is still set to `block.timestamp` and `_updateTokenIndex` persists it. The elapsed zero-supply window is therefore consumed without any index growth — the corresponding emissions (`_deltaTimestamps * _speed`) are never accounted to anyone and can never be recovered, mirroring the `rewardPerTokenStored`/`lastUpdateTime` desync in the reference report.

### Finding Description
In `contracts/RewardsDistributor.sol`, `_calculateTokenIndex` computes:

```solidity
uint256 _totalSupply = token_.totalSupply();
uint256 _tokensAccrued = _deltaTimestamps * _speed;
uint256 _ratio = _totalSupply > 0 ? _tokensAccrued.wadDiv(_totalSupply) : 0;
_newIndex = (_supplyState.index + _ratio).toUint224();
_newTimestamp = block.timestamp.toUint32();
```

When `_totalSupply == 0`, `_ratio` is `0` so `_newIndex` equals the stored index, but `_newTimestamp = block.timestamp` is still returned. `_updateTokenIndex` then executes the `else if (_newTimestamp > 0)` branch and writes `tokenStates[token_].timestamp = block.timestamp` (lines 271–282). The next update measures `_deltaTimestamps` from this new timestamp, so the entire zero-supply interval's emissions are skipped. There is no `remainingReward`/carryover variable — unlike a Synthetix-style `notifyRewardAmount` that recycles leftover rewards into `rewardRate`, Metronome's fixed `tokenSpeeds` means the skipped emissions are simply never minted to the index. The accrued `rewardToken` balance stays locked in the contract with no withdrawal path (`_transferRewardIfEnoughTokens` only pays out accrued amounts).

The trigger is permissionless: `updateBeforeMintOrBurn` is callable by anyone (it is also invoked by `DepositToken`/`DebtToken` on mint/burn) and only requires `tokenStates[token_].index > 0`. The zero-supply state is reached naturally when all holders burn/withdraw, or an attacker holding the full supply can burn their entire position, wait, call `updateBeforeMintOrBurn(token, attacker)` to checkpoint the timestamp, then re-mint.

### Impact Explanation
Every second a rewarded `DepositToken`/`DebtToken` sits at `totalSupply == 0` with `tokenSpeeds > 0`, `speed` worth of `rewardToken` emissions are permanently forfeited. The tokens remain in the `RewardsDistributor` balance but are unreachable by any user, since claims only pay out index-derived `tokensAccruedOf`. This is permanent freezing/loss of unclaimed yield proportional to the zero-supply duration. On deployments where `syncTokenSpeed` keeps speed in sync with an external Vesper `IPoolRewards` rate, the externally-funded reward stream continues paying into a vacuum during these windows.

### Likelihood Explanation
Likelihood is moderate. Zero `totalSupply` is an edge case but is reachable: a reward token with an active speed whose pool is fully exited (all deposits withdrawn, or debt fully repaid for a `DebtToken`), or a newly configured token before its first deposit (speed set while supply is still 0 — emissions from `tokenStates` initialization until first mint are partially lost via the same path). No privileged action by the attacker is required to advance the timestamp since `updateBeforeMintOrBurn` is public; it only depends on the natural or induced zero-supply condition. Impact scales with `tokenSpeeds` and the duration of the zero-supply window.

### Recommendation
Track undistributed emissions during zero-supply periods instead of discarding them. Options: (1) do not advance `tokenStates[token_].timestamp` when `totalSupply == 0` so the accrued amount is distributed to the next depositors once supply returns; or (2) introduce a `pendingRewards`/carryover state per token that accumulates `_deltaTimestamps * _speed` while supply is zero and is folded into the index when supply becomes nonzero. Add tests covering speed changes and index updates across zero-supply intervals.

### Proof of Concept
Hardhat-style (matching the repo's existing test harness in `test/RewardDistributor.test.ts`):

```typescript
it('loses emissions accrued while totalSupply is zero', async function () {
  const speed = parseEther('1') // 1 rewardToken per second
  await rewardDistributor.updateTokenSpeed(msdTOKEN1.address, speed)

  // token at zero supply; advance timestamp via public updateBeforeMintOrBurn
  msdTOKEN1.totalSupply.returns(0)
  msdTOKEN1.balanceOf.returns(0)
  await increaseTimeOfNextBlock(100)
  await rewardDistributor.updateBeforeMintOrBurn(msdTOKEN1.address, alice.address)
  // 100 * speed emissions elapsed; tokenStates.timestamp was advanced, index unchanged

  // supply returns; alice holds everything
  msdTOKEN1.totalSupply.returns(parseEther('100'))
  msdTOKEN1.balanceOf.returns(parseEther('100'))
  await increaseTimeOfNextBlock(10)

  const claimable = await rewardDistributor['claimable(address)'](alice.address)
  // Alice only receives ~10 rewards for the post-supply window.
  // The 100 rewards emitted during the zero-supply window are unclaimable forever.
  expect(claimable).eq(parseEther('10')) // expected 110 if accounting were correct
})
```

Run on a mainnet fork by forking at the deployed `RewardsDistributor` and impersonating `governor` only for the initial `updateTokenSpeed` setup (configuration, not the exploit step); the loss itself is triggered by the permissionless `updateBeforeMintOrBurn` call while `DepositToken.totalSupply() == 0`.
