### Title
Unchecked SIP-010 `transfer` boolean return in `collateral-add()` credits collateral even when token transfer silently fails - (File: mainnet/contracts/market/v0-market-vault.clar)

### Summary
`collateral-add()` in `v0-market-vault.clar` uses `(try! (receive-tokens ft amount account))` to pull the collateral token from the user, but `try!` in Clarity only aborts on `(err ...)` responses — it does not validate that an `(ok true)` response actually reflects a successful transfer. If the collateral `<ft-trait>` implementation returns `(ok false)` on a failed transfer (a valid SIP-010 pattern deviation analogous to ERC20 `transfer`/`transferFrom` returning `false` instead of reverting), the vault's internal accounting is still updated as if tokens were received.

### Finding Description
`receive-tokens` simply forwards the trait call without inspecting the boolean payload: [1](#0-0) 

`collateral-add()` calls it via `try!` and then unconditionally proceeds to update the user's collateral accounting (`add-user-collateral`, already computed in the `let` bindings) and `insert`s the refreshed obligation entry: [2](#0-1) 

Per the SIP-010 standard referenced in this repo, a compliant `transfer` should abort on insufficient balance, but the standard's error-code table is only a recommendation — non-compliant or buggy fungible-token implementations can legally implement the trait while returning `(ok false)` instead of erroring: [3](#0-2) 

Because `try!` only unwraps `(ok x)` -> `x` and only aborts on `(err ...)`, a `(ok false)` return is treated as success. The market-vault then records `amount` as collateral for `account` even though zero tokens actually moved into the vault contract. This is the direct Clarity analog of the Visor Finance `timeLockERC20()` bug: an unhandled/unchecked boolean success indicator from a token transfer leads to accounting that diverges from actual token custody.

### Impact Explanation
This lands in the "collateral-remove" / accounting invariant surface explicitly named as in-scope ("position mask and collateral/debt accounting"). The mismatch lets a user record phantom collateral in `collateral` map without the market-vault actually holding the underlying tokens. That inflated collateral can then be used to pass health checks in the market contract (e.g., `is-healthy` checks in `v0-4-market.clar`) to borrow against non-existent collateral, or to later `collateral-remove` value that was never truly deposited — draining real assets deposited by other users of the shared vault. This is a path to insolvency / theft of user funds at rest, matching the Critical impact class.

### Likelihood Explanation
Exploitability depends on whether an asset onboarded via the DAO's asset registry implements `<ft-trait>` in a non-standard way (returning `(ok false)` on failure rather than aborting). Since asset onboarding is DAO-controlled and out of scope per the rules (DAO registry updates are excluded), the practical trigger requires either (a) a currently-listed token whose implementation can be coerced into returning `(ok false)` under some caller-controlled condition, or (b) reliance purely on the code path itself, independent of any specific token's behavior, since the vulnerability is in the vault's failure to validate the return value regardless of which token exhibits the behavior. The root-cause defect — missing boolean-result validation after `try!` — is present in the code today and reachable by any ordinary principal calling into the market's `supply-collateral-add` / `collateral-add` flow with a token that can return `false`.

### Recommendation
After unwrapping the `transfer` call result in `receive-tokens` (and analogous `send-tokens`), explicitly assert the boolean payload is `true` rather than only using `try!`, e.g.:
```clarity
(define-private (receive-tokens (asset <ft-trait>) (amount uint) (account principal))
  (let ((ok? (try! (contract-call? asset transfer amount account current-contract none))))
    (asserts! ok? ERR-COLLATERAL-TRANSFER-FAILED)
    (ok ok?)))
```
Apply the same explicit boolean check to every other `token transfer` call site that currently only wraps the call in `try!` (vault `receive-underlying`/`send-underlying` helpers, `supply-collateral-add`, `dao-treasury withdraw`, etc.), since all of them share the same unchecked-return pattern.

### Proof of Concept
1. DAO (or existing) asset `X` implements `<ft-trait>` such that `transfer` returns `(ok false)` when the sender lacks sufficient balance (a legal, if non-compliant, SIP-010 implementation, distinct from the compliant abort-on-failure recommended in the SIP-010 spec: `local-testing/references/sip-010-fungible-token-standard.md:60-67`).
2. Attacker calls the market entry point that leads to `collateral-add(account, amount, X, asset-id)` in `v0-market-vault.clar:374-404`, e.g. via `market.clar`'s `supply-collateral-add`/`collateral-add` flow, while holding zero balance of `X`.
3. `receive-tokens` (`v0-market-vault.clar:256-257`) calls `contract-call? X transfer amount account current-contract none`; `X` returns `(ok false)` instead of erring.
4. `try!` unwraps `(ok false)` to `false` without aborting; `collateral-add` proceeds to `add-user-collateral` and `insert`, recording `amount` of `X` as collateral for `account` even though the vault received nothing.
5. Attacker's position now shows phantom collateral of asset `X`, which can be used to pass `is-healthy` checks in the market contract to borrow real assets, or be later withdrawn via `collateral-remove`, causing real-asset loss to the protocol/other depositors.

When returning an error in this function, the error codes should follow the same patterns as the built-in `ft-transfer?` and `stx-transfer?` functions.

| u2         | `sender` and `recipient` are the same principal |
