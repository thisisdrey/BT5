### Title
Exchange liquidity inject/withdraw lack minimum/maximum "another token" bound, letting front-run trades force unexpected token amounts - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`, `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
`ExchangeInjectContract` and `ExchangeWithdrawContract` compute the paired ("another") token amount from the exchange pool's *live* `firstTokenBalance`/`secondTokenBalance` ratio at the moment the transaction is validated/executed, exactly analogous to the Mellow `LPIssuer.deposit` "balanced amounts" calculation flagged in the external report. Unlike `ExchangeTransactionContract`, which carries an `expected` field enforced by a `token required must greater than expected` check [1](#0-0) , neither `ExchangeInjectContract` nor `ExchangeWithdrawContract` expose any minimum/maximum bound parameter for the calculated `anotherTokenQuant`.

### Finding Description
In `ExchangeInjectActuator.execute`/`doValidate`, `anotherTokenQuant` is derived at execution time as `secondTokenBalance * tokenQuant / firstTokenBalance` (or the symmetric case), using whatever `firstTokenBalance`/`secondTokenBalance` the exchange capsule holds when the transaction is packed into a block [2](#0-1) . The same live-ratio computation and lack of a bound parameter exists in `ExchangeWithdrawActuator.doValidate` [3](#0-2) .

Any unprivileged account can broadcast an `ExchangeTransactionContract` (a normal token swap against the same exchange pool) via `ExchangeTransactionActuator.execute`, which mutates `firstTokenBalance`/`secondTokenBalance` through `ExchangeCapsule.transaction` [4](#0-3) . Because block producers order transactions and an attacker can get their swap included immediately before the victim's already-signed/broadcast `ExchangeInjectContract` or `ExchangeWithdrawContract`, the pool ratio used to compute `anotherTokenQuant` can be arbitrarily different from the ratio the victim observed when they signed their transaction — with no slippage/bound check anywhere in the actuator's `execute`/`doValidate` to reject the transaction if the resulting amount deviates from what the victim expected.

### Impact Explanation
For `ExchangeInjectActuator`, the victim (exchange creator injecting liquidity) can be forced to debit a far larger (or smaller) amount of the paired token than intended, since `anotherTokenQuant` is deducted directly from their account balance in `execute` with no upper bound check [5](#0-4) . For `ExchangeWithdrawActuator`, the victim can receive a far smaller amount of the paired token than expected when withdrawing liquidity, with no minimum bound enforced. This causes concrete, unauthorized loss of user funds through a mispriced state transition, unlike `ExchangeTransactionContract` which is already protected via its `expected` parameter.

### Likelihood Explanation
This requires only a normal signed `ExchangeTransactionContract` transaction from any account with tokens/TRX on that exchange pair, and relies on ordinary transaction-ordering within a block — no malicious SR/witness/peer behavior is needed (any user, or even the exchange creator's own subsequent inject/withdraw call, can be sandwiched by ordinary trades). The precondition (an actively traded exchange pair with a pending inject/withdraw) is realistic and does not require special privileges.

### Recommendation
Add a user-supplied minimum/maximum bound field to `ExchangeInjectContract` and `ExchangeWithdrawContract` (analogous to `ExchangeTransactionContract.expected`), and enforce it in `ExchangeInjectActuator.doValidate`/`execute` and `ExchangeWithdrawActuator.doValidate`/`execute` by rejecting the transaction if the computed `anotherTokenQuant` falls outside the caller-specified bound.

### Proof of Concept
1. Exchange pool holds `firstTokenBalance = 1000`, `secondTokenBalance = 1000`.
2. Creator broadcasts `ExchangeInjectContract{tokenId=first, quant=100}`, expecting `anotherTokenQuant = 100` (i.e., a 1:1 ratio, based on pool state observed at signing time).
3. Before this transaction is packed, any account broadcasts an `ExchangeTransactionContract` trade that shifts the pool to `firstTokenBalance = 500`, `secondTokenBalance = 2000` (via `ExchangeCapsule.transaction`).
4. When the inject transaction executes, `anotherTokenQuant = secondTokenBalance * tokenQuant / firstTokenBalance = 2000 * 100 / 500 = 400`, four times what the creator expected, silently debited from their account with no check to reject it [6](#0-5) .

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
