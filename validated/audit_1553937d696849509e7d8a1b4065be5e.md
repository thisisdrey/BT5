### Title
Active-permission key can self-escalate to full Owner control via `AccountPermissionUpdateContract` - (File: `actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java`)

### Summary
The BuddyPress bug let a group "Moderator" role invoke the group member-role-update endpoint and set its own role to "Administrator" because the endpoint only checked that the caller was *a* privileged group member, not that the caller held sufficient rights to grant the *specific target role* being assigned. The same class of flaw exists in java-tron's multi-signature permission model: any account that grants an `Active` permission the bit for `AccountPermissionUpdateContract` in its `operations` bitmap allows the holder of that (lower-privileged) `Active` key to unilaterally rewrite the account's `Owner` permission — including replacing the owner key set entirely — with no check that the signer actually held Owner-level authority.

### Finding Description
Transaction-level authorization for any contract is done generically in `TransactionCapsule.checkPermission()`/`validateSignature()` [1](#0-0) . For a non-owner (`permissionId != 0`), it only verifies the permission is of type `Active` and that the `operations` bitmap for that `Active` permission has the bit for the invoked `ContractType` set — nothing more: [2](#0-1) 

`AccountPermissionUpdateActuator.execute()` then unconditionally applies the new `Owner`, `Witness`, and `Active` permissions supplied in the contract payload to the account, with no re-check of which permission authorized the transaction versus which permission is being overwritten: [3](#0-2) 

`validate()` only checks structural correctness of the new `Owner`/`Witness`/`Active` permissions (key counts, thresholds, address validity, valid operation bits), never that the signer's own permission level is sufficient to modify the `Owner` permission: [4](#0-3) 

`AccountCapsule.updatePermissions()` blindly overwrites `ownerPermission` with whatever `Permission` object is supplied in the contract, regardless of which permission signed the transaction: [5](#0-4) 

Consequently, once an owner grants any `Active` permission the `AccountPermissionUpdateContract` bit (e.g., intending to allow that key only to, say, rotate its own active keys or perform routine account maintenance), the holder of that Active key can send a single `AccountPermissionUpdateContract` transaction that replaces the account's `Owner` permission with keys entirely of the attacker's choosing (and removes the original owner's key), and additionally rewrite every other `Active` permission — achieving full permanent takeover of the account, exactly analogous to the BuddyPress moderator promoting itself to administrator by crafting a privileged-role-change request that the endpoint fails to scope-check.

### Impact Explanation
An attacker holding only a scoped `Active` key (intended for limited operations) can seize full, permanent control of the account by rewriting its `Owner` permission, then use owner authority to move funds, revoke original owner access, or perform any owner-only action (e.g., freezing/unfreezing TRX, voting, asset issuance) — an unauthorized account takeover leading to theft or permanent loss of control of funds, matching the "concrete unauthorized account operation" bar for Medium/High severity.

### Likelihood Explanation
This requires that the account owner has previously granted an `Active` permission the `AccountPermissionUpdateContract` operation bit — a configuration that is not prevented or specially warned against anywhere in `checkPermission()` of `AccountPermissionUpdateActuator`, which validates the operations bitmap purely against `getAvailableContractType()` without excluding `AccountPermissionUpdateContract` itself (unlike `ClearABIContract`/`UpdateBrokerageContract`, which are excluded from the available-type bitmap). Since this is a routinely available and unrestricted configuration path in production (via `AccountPermissionUpdateContract` itself, reachable by any account holder), and requires only one subsequently signed transaction from the Active key, likelihood is realistic wherever multi-sig delegation to lower-trust Active keys is used with broad operation grants.

### Recommendation
In `AccountPermissionUpdateActuator.validate()`/`execute()`, require that any transaction attempting to modify the `Owner` permission (or add/broaden operations bits, or the `Witness` permission) must itself be signed under `permissionId == 0` (Owner). Alternatively, exclude `AccountPermissionUpdateContract` from the bits that may legally be granted to `Active` permissions (mirroring the existing exclusion pattern used for `ClearABIContract`/`UpdateBrokerageContract`), preventing delegation of self-permission-rewriting capability to non-owner keys.

### Proof of Concept
1. Owner account `A` sets up multi-sig via `AccountPermissionUpdateContract`, creating an `Active` permission (id ≥ 2) that includes key `B` and sets the `AccountPermissionUpdateContract` bit in `operations` (a legal configuration per `checkPermission()`).
2. Attacker, controlling private key `B`, crafts a new `AccountPermissionUpdateContract` transaction for owner address `A`, with `contract.permission_id` set to `B`'s Active permission id, and supplies a new `Owner` permission containing only `B`'s key with threshold 1 (replacing `A`'s original owner key), while leaving/adjusting `Active`/`Witness` as required by `validate()`.
3. `B` signs the transaction with its own key satisfying the Active permission's threshold; `TransactionCapsule.validateSignature`/`checkPermission` passes because the bit for `AccountPermissionUpdateContract` is set for that Active permission.
4. `AccountPermissionUpdateActuator.execute()` calls `account.updatePermissions(...)`, overwriting `A`'s `ownerPermission` with the attacker-controlled permission.
5. `B` now fully controls account `A` as sole owner and can transfer all funds, revoke `A`'s remaining permissions, etc.

  public static boolean validateSignature(Transaction transaction,
      byte[] hash, AccountStore accountStore, DynamicPropertiesStore dynamicPropertiesStore)
      throws PermissionException, SignatureException, SignatureFormatException {

    int permissionId = contract.getPermissionId();
    byte[] owner = getOwner(contract);
    AccountCapsule account = accountStore.get(owner);
    Permission permission = null;
    if (account == null) {
      if (permissionId == 0) {
        permission = AccountCapsule.getDefaultPermission(ByteString.copyFrom(owner));
      }
      if (permissionId == 2) {
        permission = AccountCapsule
            .createDefaultActivePermission(ByteString.copyFrom(owner), dynamicPropertiesStore);
      }
    } else {
      permission = account.getPermissionById(permissionId);
    }
    if (permission == null) {
      throw new PermissionException("permission isn't exit");
    }
    checkPermission(permissionId, permission, contract);
    long weight = checkWeight(permission, transaction.getSignatureList(), hash, null);
    if (weight >= permission.getThreshold()) {
      return true;
    }
    return false;
  }

  public void updatePermissions(Permission owner, Permission witness, List<Permission> actives) {
    Builder builder = this.account.toBuilder();

    owner = owner.toBuilder().setId(0).build();
    builder.setOwnerPermission(owner);
    if (witness != null && builder.getIsWitness()) {
      witness = witness.toBuilder().setId(1).build();
      builder.setWitnessPermission(witness);
    }

    builder.clearActivePermission();
    if (actives != null) {
      for (int i = 0; i < actives.size(); i++) {
        Permission permission = actives.get(i).toBuilder().setId(i + 2).build();
        builder.addActivePermission(permission);
      }
    }

    this.account = builder.build();
  }
