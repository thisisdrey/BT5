### Title
Internal DB error details (`{:?}` debug-formatted `db_error`/rusqlite errors) leaked to remote StackerDB writers in HTTP 500 responses - (File: stackslib/src/net/api/poststackerdbchunk.rs)

### Summary
The `POST /v2/stackerdb/:principal/:contract_name/chunks` handler returns raw, debug-formatted internal error values (`{:?}` on `NetError`/`db_error`, which wraps `rusqlite::Error`) directly in the HTTP response body whenever an unclassified error occurs while replacing a chunk or re-reading its slot metadata. This is the same bug class as CVE-2007-2353 (Apache Axis returning internal exception detail, including filesystem paths, to a remote unauthenticated caller who merely sends a malformed/edge-case request).

### Finding Description
In `RPCPostStackerDBChunkRequestHandler::try_handle_request`, any storage error from `tx.try_replace_chunk(...)` that doesn't match the known/classified variants (`StaleChunk`, `NoSuchSlot`, `BadSlotSigner`/`VerifyingError`, `StackerDBChunkTooBig`, `TooManySlotWrites`) falls into the catch-all branch: [1](#0-0) 
which builds `HttpServerError::new(format!("Failed to store StackerDB chunk for {}: {:?}", &contract_identifier, &e))` and sends it as the response payload. The same pattern appears when re-reading slot metadata fails after a rejected write: [2](#0-1) 

`HttpServerError` stores this string verbatim as `HttpResponsePayload::Text`, which is serialized into the actual bytes sent back over the wire: [3](#0-2) [4](#0-3) 

The wrapped error type ultimately originates from `crate::util_lib::db::Error`, which is a thin wrapper around `rusqlite::Error` (SQLite driver errors commonly include the on-disk DB path, and in some rusqlite error variants, other internal detail) as seen from the imports in the StackerDB storage layer: [5](#0-4) 

This breaks the "authenticated/internal detail vs. externally-servable message" equality: whatever `Debug` happens to produce for the underlying SQLite/db error — potentially including the sqlite file path, table/column identifiers, or other internal state — is served verbatim to any remote peer capable of reaching this RPC endpoint, exactly analogous to Axis leaking its installation path via an exception message triggered by a non-existent WSDL request.

### Impact Explanation
This is an information-disclosure vulnerability reachable by any remote peer that can send a StackerDB chunk POST (no special privilege beyond being able to reach the RPC endpoint; StackerDB writes are gated only by signature verification on the *chunk contents*, not by any restriction on who may attempt the request and observe the resulting error). By crafting inputs that trigger DB-layer failures (e.g., concurrent write races, corrupted or edge-case slot state, or induced SQLite contention), an attacker can harvest internal error text that may include local filesystem paths or other implementation details useful for further reconnaissance or fingerprinting of the node's deployment. This matches CWE-200 (Exposure of Sensitive Information to an Unauthorized Actor) and is the closest legitimate analog to the reported Axis path-disclosure bug within the in-scope surface.

### Likelihood Explanation
Likelihood is limited by the difficulty of deterministically forcing the unclassified-error branch (most common failure modes are already mapped to specific classified codes), so this is not trivially triggerable, unlike the trivial Axis case (`request a non-existent WSDL`). It requires provoking a DB error along a race/edge condition rather than a single crafted request. Given the reviewed scope, this is the most credible remaining analog, but its practical exploitability for extracting sensitive detail depends on what `Debug` actually renders for the specific `rusqlite`/`db_error` variant encountered, which could not be fully confirmed from the available index.

### Recommendation
Do not embed `{:?}`-formatted internal error values (from `db_error`/`rusqlite::Error` or any other internal error type) directly into HTTP response bodies returned to remote peers. Log the detailed error server-side (as is already done via `error!`) and return only a generic, non-identifying message (e.g., "Internal server error while storing StackerDB chunk") in the HTTP 500 response body.

### Proof of Concept
1. Set up a node with an active StackerDB configuration and a registered signer.
2. Trigger a state where `tx.try_replace_chunk` or the subsequent `tx.get_slot_metadata` call fails with an error variant not covered by the classified match arms in `poststackerdbchunk.rs` lines 214–223 (e.g., forcing a SQLite-level failure through concurrent/conflicting writes or a corrupted slot row).
3. Observe the HTTP 500 response body returned to the remote caller; it contains the full `{:?}` debug rendering of the underlying `NetError`/`db_error`, which may include internal state such as SQL error text or file-path-bearing SQLite error messages. [6](#0-5)

/// HTTP 500
pub struct HttpServerError {
    error_text: String,
}

impl HttpServerError {
    pub fn new(error_text: String) -> Self {
        Self { error_text }
    }
}

impl HttpErrorResponse for HttpServerError {
    fn code(&self) -> u16 {
        500
    }
    fn payload(&self) -> HttpResponsePayload {
        HttpResponsePayload::Text(self.error_text.clone())
    }
    fn try_parse_response(
        &self,
        preamble: &HttpResponsePreamble,
        body: &[u8],
    ) -> Result<HttpResponsePayload, Error> {
        try_parse_error_response(preamble.status_code, preamble.content_type, body)
    }
}

    /// Make a new HTTP error response with additional headers, in reaction to a request
    pub fn new_error_with_headers(
        preamble: &HttpRequestPreamble,
        error: &dyn HttpErrorResponse,
        extra_headers: Vec<(String, String)>,
    ) -> StacksHttpResponse {
        let payload = error.payload();
        let content_type = match &payload {
            HttpResponsePayload::Empty => HttpContentType::Bytes,
            HttpResponsePayload::Bytes(..) => HttpContentType::Bytes,
            HttpResponsePayload::Text(..) => HttpContentType::Text,
            HttpResponsePayload::JSON(..) => HttpContentType::JSON,
        };
        let content_length = payload.try_content_length();
        let mut resp_preamble = HttpResponsePreamble::from_http_request_preamble(
            preamble,
            error.code(),
            http_reason(error.code()),
            content_length,
            content_type,
        );
        for (key, value) in extra_headers {
            resp_preamble.add_header(key, value);
        }
        StacksHttpResponse::new(resp_preamble, payload)
    }
