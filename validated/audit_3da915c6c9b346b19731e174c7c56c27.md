### Title
Unbounded Reference-Update Streams Enable Resource-Exhaustion DoS in `UpdateReferences` and Push-Time Hook Processing - ([File: internal/gitaly/service/ref/update_references.go])

### Summary
The `UpdateReferences` RPC, and the equivalent internal reference-update path exercised during `git-receive-pack`, accept an effectively unbounded number of individual reference updates from an ordinary client. Every update is buffered in memory (as a queued update in the `updateref.Updater`, and again as a `git.ReferenceUpdates` map in the transaction manager and hook layer) with no cap on the total count, mirroring the Compound `allMarkets`/`maxAssets` issue where an unbounded, user-influenced list is fully materialized and iterated without any enforced ceiling, risking resource exhaustion of the handler.

### Finding Description
`UpdateReferences` is a client-streaming RPC. The server loop receives requests and, for each one, iterates `request.GetUpdates()` and calls `updater.Update(...)` for every entry with no limit on the number of `Update` messages that can be sent across the stream: [1](#0-0) 

There is no configured `MaxRecvMsgSize`/`MaxCallRecvMsgSize` override found in the codebase, and even if per-message size were bounded by gRPC's default, the loop accepts an arbitrary number of *messages* in the stream, so the total number of updates queued in the `updateref.Updater` is unbounded.

This same "list of all reference changes" pattern is what feeds Gitaly's push-time hooks. When a push (or an internal `UpdateReference` call via `UpdaterWithHooks`) occurs, the full set of changes is serialized into a single blob and handed to the pre-receive hook, which reads it entirely into memory with `io.ReadAll(stdin)`: [2](#0-1) 

That same `changes` blob is forwarded as a string to the Rails `/internal/allowed` API and to any custom hooks, and is also fed to `parseChanges`/`isForceDeletionsOnly` in the reference-transaction hook, which fully scans and builds a map (`git.ReferenceUpdates`) keyed by every reference name in the transaction: [3](#0-2) 

Downstream, the partition transaction manager iterates the entire `updates` map again to compute final states for the commit: [4](#0-3) 

None of these layers impose a maximum on the number of references that may be updated within a single RPC/push, analogous to the audited Compound code where `allMarkets`/`accountAssets` are iterated without honoring the `maxAssets` cap. Because gitaly serves ordinary user actions (an authorized push or a direct `UpdateReferences` call), a large-enough batch of updates can drive proportionally large CPU/memory consumption (buffering, string building, hashing for the vote, map construction, JSON/HTTP payload to Rails) inside a single request-handling goroutine.

### Impact Explanation
An authenticated user with write access to a repository (an "ordinary user's push" per the validation criteria) can submit a very large number of reference updates in one RPC call/push. This causes:
- Large memory buffering of the entire changes blob (`io.ReadAll` with no size cap) that is also duplicated into HTTP request bodies sent to Rails.
- O(n) map construction and voting-hash computation over all references in the reference-transaction hook, run synchronously per hook invocation on the primary node.
- Increased holding time of internal locks/transaction state during `Commit()`, which could degrade concurrent access to the same repository and consume the handler's goroutine/memory budget.

This is a resource-exhaustion (DoS) risk against a single Gitaly node/handler rather than data corruption or privilege escalation, consistent with "DoS of a handler" as an accepted analog class.

### Likelihood Explanation
Likelihood is moderate: the attacker only needs standard write/push access (no special privilege, no malicious peer, no MITM), and the RPC/protocol places no explicit limit on the number of `Update` entries across a stream or the number of ref changes in a single push. The main mitigating factor is that produced pack/ref data must still be plausible to Git itself and other request-level timeouts/concurrency limiters may eventually bound impact, but no update-count-specific limit was found in the reviewed code paths.

### Recommendation
- Enforce an explicit maximum on the number of reference updates accepted per `UpdateReferences` stream (and per push-derived hook invocation), rejecting requests that exceed a configurable threshold (analogous to enforcing `maxAssets`/`maxSup` in the referenced report).
- Stream-process pre-receive/reference-transaction hook input incrementally (avoid `io.ReadAll` of the full changes blob) or place a hard byte/count cap on it before buffering.
- Perform load/stress testing to determine safe upper bounds for reference-update batch size and configure `MaxRecvMsgSize`/application-level counters accordingly, then enforce them consistently across `UpdateReferences`, `ReferenceTransactionHook`, and `UpdaterWithHooks`.

### Proof of Concept
Not independently executed; based on static analysis of the request/handler code paths. A conceptual PoC:
1. As a client with push/write access, open a client-streaming `UpdateReferences` call.
2. Send an extremely large number of small `Update` messages (e.g., millions of distinct new branch refs) across the stream, keeping each individual message under any default gRPC message-size limit.
3. Observe the server (`internal/gitaly/service/ref/update_references.go`) queuing all updates into the `updateref.Updater` and, on `Commit()`, generating a correspondingly large in-memory changes blob that is passed whole to `io.ReadAll` in `internal/gitaly/hook/prereceive.go` and parsed entirely in `internal/gitaly/hook/referencetransaction.go`, measuring CPU/memory growth and handler latency as update count increases.

Full verification of enforced caps (e.g. whether `MaxRecvMsgSize` or a request-level update-count limit exists elsewhere in configuration not covered by the indexed search) was not completed due to index coverage limits; a Devin session with full repository access would be needed to confirm no such cap exists elsewhere in the codebase.

func parseChanges(objectHash git.ObjectHash, changes io.Reader) (git.ReferenceUpdates, error) {
	scanner := bufio.NewScanner(changes)

	updates := git.ReferenceUpdates{}
	for scanner.Scan() {
		line := scanner.Text()
		components := strings.Split(line, " ")
		if len(components) != 3 {
			return nil, fmt.Errorf("unexpected change line: %q", line)
		}

		reference := git.ReferenceName(components[2])

		// We only track updates made in the 'refs/' directory.
		// An exception to this is when HEAD is updated.
		if !strings.HasPrefix(reference.String(), "refs/") && reference.String() != "HEAD" {
			continue
		}

		update := git.ReferenceUpdate{}

		var err error

		if _, target, ok := strings.Cut(components[0], "ref:"); ok {
			update.OldTarget = git.ReferenceName(target)
		} else {
			update.OldOID, err = objectHash.FromHex(components[0])
			if err != nil {
				return nil, fmt.Errorf("parse old: %w", err)
			}
		}

		if _, target, ok := strings.Cut(components[1], "ref:"); ok {
			update.NewTarget = git.ReferenceName(target)
		} else {
			update.NewOID, err = objectHash.FromHex(components[1])
			if err != nil {
				return nil, fmt.Errorf("parse new: %w", err)
			}
		}

		// Only capture default branch changes and ignore all other symbolic reference updates.
		if reference.String() != "HEAD" && (update.NewTarget != "" || update.OldTarget != "") {
			continue
		}

		// If the default branch is being deleted, we ignore updating HEAD
		//
		// TODO: This can be removed once the bug in Git itself is fixed
		// https://gitlab.com/gitlab-org/git/-/issues/348
		if reference.String() == "HEAD" && update.NewTarget == "" {
			continue
		}

		updates[reference] = update
	}

	return updates, nil
}

func (txn *Transaction) UpdateReferences(ctx context.Context, updates git.ReferenceUpdates) error {
	u := git.ReferenceUpdates{}

	for reference, update := range updates {
		// Transactions should only stage references with valid names as otherwise Git would already
		// fail when they try to stage them against their snapshot. `update-ref` happily accepts references
		// outside of `refs` directory so such references could theoretically arrive here. We thus sanity
		// check that all references modified are within the refs directory.
		//
		// HEAD is a special case and refers to a default branch update.
		if !strings.HasPrefix(reference.String(), "refs/") && reference != "HEAD" {
			return InvalidReferenceFormatError{ReferenceName: reference}
		}

		oldOID := update.OldOID
		oldTarget := update.OldTarget

		if initialValue, ok := txn.initialReferenceValues[reference]; ok {
			if !initialValue.IsSymbolic {
				oldOID = git.ObjectID(initialValue.Target)
			} else {
				oldTarget = git.ReferenceName(initialValue.Target)
			}
		}

		if oldOID == update.NewOID && oldTarget == update.NewTarget {
			// This was a no-op.
			continue
		}

		for _, updates := range txn.referenceUpdates {
			if txUpdate, ok := updates[reference]; ok {
				if txUpdate.NewOID != "" {
					oldOID = txUpdate.NewOID
				}

				if txUpdate.NewTarget != "" {
					oldTarget = txUpdate.NewTarget
				}
			}
		}

		u[reference] = git.ReferenceUpdate{
			OldOID:    oldOID,
			NewOID:    update.NewOID,
			OldTarget: oldTarget,
			NewTarget: update.NewTarget,
		}
	}
