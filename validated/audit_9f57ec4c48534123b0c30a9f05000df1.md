Audit Report

## Title
Per-account HOP submit rate limiter (`RateLimiter::check`) is enforced only inside `HopDataPool::insert`, after `hop_submit` has already performed two runtime-API calls and a full signature verification - (File: `substrate/client/hop/src/rpc.rs`)

## Summary
`HopRpcServer::submit` in `substrate/client/hop/src/rpc.rs` performs a `max_promotion_size` runtime-API call, a `can_account_promote` runtime-API call (a state-trie read), and a full `MultiSignature::verify` before ever calling `self.pool.insert(...)`, and the per-account token-bucket `RateLimiter::check` is invoked only deep inside `HopDataPool::insert` as effectively the last gate. Any account that satisfies the runtime-defined, non-privileged `can_account_promote` authorization can therefore call `hop_submit` at a rate far above the configured `submit_rate_per_min`/`submit_burst`, forcing the node to repeatedly perform the two runtime-API dispatches and a cryptographic signature verification per rejected call, defeating the stated purpose of the rate limiter.

## Finding Description
`HopRpcServer::submit` executes, in order: SCALE-decoding, `runtime_api::max_promotion_size` [1](#0-0) , `runtime_api::can_account_promote` (explicitly documented as happening "before verifying the signature" to avoid *one* DoS pattern) [2](#0-1) , `multi_sig.verify(...)` [3](#0-2) , and only afterward `self.pool.insert(...)` [4](#0-3) . The rate limiter is invoked inside `insert`, after the caller has already absorbed the entire cost of the request: [5](#0-4) . `RateLimiter::check` itself is a straightforward per-`SenderId` token bucket for requests and bandwidth [6](#0-5) , whose documented purpose is exactly to bound how often one account can hit this expensive path [7](#0-6) . Because the check sits inside `insert` rather than at the top of `submit`, the ordering asymmetry is real: the code explicitly protects against unauthorized-account floods forcing signature verification, but does not protect against an authorized account forcing unlimited authorization-checks-plus-signature-verifications, since the admission-control primitive (the token bucket) runs last. `can_account_promote` is a runtime-defined, non-privileged authorization policy — per the module's own README it can be "any other policy" the runtime chooses, including reuse of a broadly-granted existing on-chain authorization [8](#0-7) .

## Impact Explanation
`sc-hop` is a node-level service that runs inside Substrate collator processes; `hop_submit` is exposed over public JSON-RPC and marked `blocking` [9](#0-8) . An account authorized under `can_account_promote` can drive the node to perform unbounded state-trie reads and CPU-bound signature verifications at a rate the configured `--hop-submit-rate-per-min`/`--hop-submit-burst` values are supposed to prevent, since those checks execute before the token bucket ever gets a chance to reject the call. This is public, underpriced work reachable with no admin, governance, or validator privilege — only one ordinary account the runtime happens to authorize — and lines up with the "public underpriced work that degrades block production" impact category for node-adjacent resource exhaustion.

## Likelihood Explanation
High for triggering the ordering flaw deterministically on every call: no race condition or timing window is required, and the code path is unconditional. The only precondition is possession of a keypair the runtime's `can_account_promote` policy accepts, which per the crate's own documentation may be a broadly granted, non-privileged authorization rather than an admin-only one.

## Recommendation
Move the `RateLimiter::check` call to the first admission-control step in `HopRpcServer::submit`, before the `max_promotion_size` and `can_account_promote` runtime-API calls and before signature verification, keyed on the sender identity derived from the decoded `signer`. If establishing the sender identity itself needs to remain cheap, ensure the reordering keeps the check as the very first cost gate so an authorized account cannot force runtime-API dispatches or cryptographic verification beyond its configured token-bucket budget.

## Proof of Concept
1. Configure a node with HOP enabled and a runtime whose `can_account_promote` authorizes account `A` under a non-privileged, broadly granted policy.
2. Using `A`'s keypair, send `hop_submit` requests over JSON-RPC at a rate above `--hop-submit-rate-per-min`/`--hop-submit-burst` (e.g., 300 req/min), each with a distinct payload and valid signature.
3. Observe that every request incurs a `HopRuntimeApi_max_promotion_size` call, a `HopRuntimeApi_can_account_promote` state read, and a full `MultiSignature::verify` in `HopRpcServer::submit` (`substrate/client/hop/src/rpc.rs:182-214`) before `RateLimiter::check` (`substrate/client/hop/src/pool.rs:374-376`, `substrate/client/hop/src/rate_limit.rs:147-171`) is ever reached, confirming the token bucket only limits stored entries, not the per-request CPU/state-read cost imposed on the node.

**File:** substrate/client/hop/src/rate_limit.rs (L143-171)
```rust
	/// Check whether this account may submit `data_len` bytes right now.
	///
	/// Returns `Ok(())` on admission (tokens consumed) or `Err(retry_after_secs)`
	/// when either bucket is empty.
	pub fn check(&self, sender_id: &SenderId, data_len: u64) -> Result<(), u64> {
		if !self.cfg.enabled {
			return Ok(());
		}

		let now = Instant::now();
		let state = self.get_or_create(sender_id, now);
		let mut state = state.lock();
		state.last_touch = now;

		let req_wait = state.requests.try_consume(1.0, now).err();
		if let Some(wait) = req_wait {
			return Err(wait.as_secs().max(1));
		}

		// If the bandwidth bucket is exhausted, reject immediately and refund the request
		// token so both buckets stay consistent.
		if let Err(wait) = state.bandwidth.try_consume(data_len as f64, now) {
			// Refund the request token we just took so the two buckets stay consistent.
			state.requests.tokens = (state.requests.tokens + 1.0).min(state.requests.capacity);
			return Err(wait.as_secs().max(1));
		}

		Ok(())
	}
```
