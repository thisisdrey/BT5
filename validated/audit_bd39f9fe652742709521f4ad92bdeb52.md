## Analysis: Static fixed-size thread pool exhaustion in `VerifyTransferProof` precompile

The CVE describes SAXParser pool exhaustion from crafted input files causing long hangs. The closest and strongest reachable analog in java-tron is the small, static, JVM-global thread pools backing the Sapling `VerifyTransferProof` TVM precompile, which any unprivileged account can drive via a smart-contract call (including read-only `triggerconstantcontract`/`triggersmartcontract` RPC/HTTP calls). ### Title
Node-wide DoS via static fixed-size worker pool exhaustion in `VerifyTransferProof` shielded-transfer precompile - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
`PrecompiledContracts.VerifyTransferProof` maintains two `static` `ExecutorService` pools, each fixed at only 5 threads, shared across the entire JVM for every constant call and every non-constant (broadcast) TVM execution that reaches this precompile: [3](#0-2) . Every invocation submits up to `spendCount + receiveCount + 1` (max 5) expensive native zk-SNARK verification tasks (`librustzcashSaplingCheckSpendNew`, `librustzcashSaplingCheckOutputNew`, binding-sig check) to the shared pool: [4](#0-3) [5](#0-4) .

### Finding Description
Because `workersInConstantCall` / `workersInNonConstantCall` are `static` (JVM-global, not per-request or per-block), any external client can flood `triggerconstantcontract` (which runs on `isConstantCall()==true` and uses `workersInConstantCall`) with concurrent calls into a shielded contract that invokes this precompile. Each call alone can occupy all 5 constant-call threads (max spend=2, receive=2, plus binding-sig task = 5 tasks). A handful of concurrent requests is enough to fully saturate the pool for every other client using constant calls at the same time, since `ExecutorServiceManager.newFixedThreadPool` backs it with an unbounded `LinkedBlockingQueue`, so excess tasks just queue instead of being rejected: [6](#0-5) .

Critically, when the caller times out waiting on `countDownLatch.await(getCPUTimeLeftInNanoSecond(), ...)`, the already-submitted `Future`s are never cancelled: [7](#0-6) . The native zk-SNARK verification tasks keep running to completion in the shared pool regardless of the caller giving up, so a burst of crafted/expensive calls keeps all 5 threads (and the growing unbounded queue) occupied well beyond any single request's CPU-time budget — directly mirroring the "SAXParser pool exhaustion → long hangs" bug class in the CVE, but for native crypto verification threads instead of XML parsers.

### Impact Explanation
Because the pools are static/JVM-global rather than scoped per request, a modest number of concurrent malicious `triggerconstantcontract` calls (well within normal API rate limits, since these are legitimate read-only calls) can starve the 5-thread `workersInConstantCall` pool, causing all *other* users' concurrent constant calls (an important externally-facing query path, analogous to `eth_call`) that traverse this same precompile to hang or fail with `notEnoughTime`/timeout errors. This is a denial-of-service of an externally reachable node API ("API the node can no longer serve"), and because tasks are not cancelled on timeout, the exhaustion outlives each individual attacker request's CPU-time budget, amplifying the effect over sustained request bursts.

### Likelihood Explanation
The precompile is reachable by any account calling a shielded-token smart contract without special privileges, via the standard `triggerconstantcontract`/`triggersmartcontract` Wallet/gRPC/HTTP paths [8](#0-7) . Input validation only bounds `spendCount`/`receiveCount` to 1–2 per call [9](#0-8) , it does not bound concurrency across independent requests against the shared static pool. No authentication or elevated permission is required, so likelihood is moderate-to-high for an attacker willing to script several concurrent contract calls.

### Recommendation
- Avoid `static` global pools for precompile execution; scope worker pools (or apply a bounded semaphore/backpressure) so a single client cannot monopolize node-wide capacity.
- Cancel outstanding `Future`s (`future.cancel(true)`) when `countDownLatch.await` times out so abandoned native verification work doesn't keep occupying threads.
- Use a bounded queue with rejection (`ThreadPoolExecutor` + `RejectedExecutionException` handling) instead of the unbounded `LinkedBlockingQueue` from `ExecutorServiceManager.newFixedThreadPool`, so bursts fail fast rather than queuing indefinitely.
- Consider per-connection/per-account rate limiting specifically for precompile-heavy constant calls.

### Proof of Concept
1. Deploy or use an existing shielded TRC-20-style contract that calls the `VerifyTransferProof` precompile.
2. From several concurrent clients, repeatedly call `triggerconstantcontract` with crafted (but format-valid) shielded transfer proof data (`spendCount`/`receiveCount` = 2, valid `SIZE` per `Arrays.asList(SIZE).contains(data.length)`), so each call submits 5 tasks to `workersInConstantCall`.
3. Issue enough concurrent calls (a handful is sufficient given the pool size of 5) to keep the static pool and its unbounded queue continuously saturated.
4. Observe that concurrent, legitimate `triggerconstantcontract` calls from other clients that also traverse `VerifyTransferProof` (or share the pool) hang/time out, demonstrating denial of service on this API path.
