## Analog Finding

### Title
Unchecked integer-overflow sentinel in prioritization-fee calculation allows priority-queue eviction of legitimate transactions - ([File: compute-budget/src/compute_budget_limits.rs])

### Summary
`get_prioritization_fee()` silently returns `u64::MAX` when the micro-lamport prioritization-fee computation overflows, instead of signaling an error. This sentinel value is never checked by any caller and flows directly into transaction "priority" scoring used by the banking/forwarding stage to admit or evict buffered transactions, mirroring the reported bug class where `price()` returns an unchecked sentinel `(0, FIX_MAX)` that corrupts a downstream shortfall calculation.

### Finding Description
`get_prioritization_fee` computes `compute_unit_price * compute_unit_limit`, converts to lamports, and falls back to `u64::MAX` if the conversion overflows `u64`: [1](#0-0) 

The function's own test explicitly documents this saturating-to-sentinel behavior for adversarial-looking inputs: [2](#0-1) 

Crucially, `compute_unit_price` is taken directly, unbounded, from a user-supplied `SetComputeUnitPrice` instruction, while `compute_unit_limit` is only capped to `MAX_COMPUTE_UNIT_LIMIT` (not zeroed): [3](#0-2) 

An attacker fully controls `compute_unit_price` (up to `u64::MAX`), so `compute_unit_price * compute_unit_limit` (with `compute_unit_limit` near `MAX_COMPUTE_UNIT_LIMIT`, ~1.4M) easily overflows u64 after the microlamport→lamport conversion, causing `get_prioritization_fee()` to return `u64::MAX` unconditionally, with no error propagated to any caller.

This sentinel becomes `TransactionConfiguration.priority_fee_lamports`: [4](#0-3) 

which is then fed, unchecked, into the reward/priority formula used to rank packets in the forwarding stage's buffering/eviction logic: [5](#0-4) [6](#0-5) 

That artificially inflated priority is used directly to decide whether to evict an already-buffered (legitimate) packet when the forwarding container is full: [7](#0-6) 

No code path validates that the returned prioritization fee is a "real" value rather than the overflow sentinel — exactly analogous to the reported issue where `price()`'s sentinel `(0, FIX_MAX)` is used by `collateralShortfall()` without a validity check.

### Impact Explanation
An unprivileged network participant can craft a cheap, syntactically valid transaction containing `ComputeBudgetInstruction::set_compute_unit_price(u64::MAX)` (or another overflow-inducing value) plus a large `set_compute_unit_limit`. This transaction will always fail during actual fee-payer/balance checks in the bank (since it can never actually pay `u64::MAX` lamports), so it costs the attacker nothing to produce and never lands in a block or consumes real compute. However, before that rejection, its computed "priority" (driven by the saturated `u64::MAX` prioritization fee) becomes maximal, letting it evict genuinely fee-paying, low-cost transactions from the forwarding stage's bounded packet container. This is a low-cost QoS-evasion / DoS vector against the transaction-forwarding pipeline: garbage, guaranteed-to-fail transactions can displace legitimate ones purely due to an unchecked overflow sentinel.

### Likelihood Explanation
Likelihood is moderate-to-high for the specific vector demonstrated (forwarding-stage buffer eviction): the input (`compute_unit_price`) is fully attacker-controlled, requires no stake or special privilege, and the overflow condition is trivially reachable (single `SetComputeUnitPrice` instruction with a large value). The blast radius depends on how many other code paths besides `forwarding_stage.rs`/`transaction_priority.rs` consume unchecked `priority_fee_lamports`; this was the portion I could concretely verify from the available index.

### Recommendation
`get_prioritization_fee()` (and its `ComputeBudgetLimits::get_prioritization_fee` wrapper) should return a `Result`/`Option` on overflow instead of silently returning `u64::MAX`, and `try_into_config` in `runtime-transaction/src/transaction_meta.rs` should propagate that as a `TransactionError` (e.g. rejecting the transaction with an invalid-compute-budget-style error) rather than allowing an overflowed sentinel to be treated as a legitimate priority-fee value anywhere downstream (forwarding-stage priority calculation, banking-stage priority/reward calculation, prioritization-fee cache).

### Proof of Concept
1. Build a transaction whose instructions include `ComputeBudgetInstruction::set_compute_unit_limit(MAX_COMPUTE_UNIT_LIMIT)` and `ComputeBudgetInstruction::set_compute_unit_price(u64::MAX)` plus a no-op/system instruction, signed with an arbitrary (even unfunded) keypair.
2. Send this packet (and enough copies to fill the forwarding container) to a validator's TPU.
3. In `forwarding_stage.rs::buffer_packet_batches`, `calculate_priority()` computes `priority_fee_lamports = u64::MAX` via the code path shown above, producing a maximal `priority` score for a transaction that can never actually pay this fee.
4. Because the container is capacity-bounded and evicts the lowest-priority buffered packet when full (`core/src/forwarding_stage.rs` lines 316–331), these zero-cost garbage transactions can displace legitimate, fee-paying transactions from the forward buffer before ultimately failing fee-payer checks at execution time — the existing unit test `test_new_with_compute_unit_price` in `compute-budget/src/compute_budget_limits.rs` confirms the exact `u64::MAX` saturation behavior exploited here.

fn get_prioritization_fee(compute_unit_price: u64, compute_unit_limit: u64) -> u64 {
    let micro_lamport_fee: MicroLamports =
        (compute_unit_price as u128).saturating_mul(compute_unit_limit as u128);
    micro_lamport_fee
        .saturating_add(MICRO_LAMPORTS_PER_LAMPORT.saturating_sub(1) as u128)
        .checked_div(MICRO_LAMPORTS_PER_LAMPORT as u128)
        .and_then(|fee| u64::try_from(fee).ok())
        .unwrap_or(u64::MAX)
}

fn calculate_priority(
    transaction: &RuntimeTransaction<SanitizedTransactionView<&[u8]>>,
    bank: &Bank,
) -> Option<u64> {
    let transaction_configuration = transaction
        .transaction_configuration(&bank.feature_set)
        .ok()?;

    // Manually estimate fee here since currently interface doesn't allow a on SVM type.
    // Doesn't need to be 100% accurate so long as close and consistent.
    let prioritization_fee = transaction_configuration.priority_fee_lamports;
    let signature_details = transaction.signature_details();
    let signature_fee = signature_details
        .total_signatures()
        .saturating_mul(bank.fee_structure().lamports_per_signature);
    let fee_details = FeeDetails::new(signature_fee, prioritization_fee);

    let reward = bank
        .calculate_reward_and_burn_fee_details(&CollectorFeeDetails::from(fee_details))
        .get_deposit();

    let cost = CostModel::estimate_cost(
        transaction,
        transaction.program_instructions_iter(),
        transaction.num_requested_write_locks(),
        &bank.feature_set,
    );

    // We need a multiplier here to avoid rounding down too aggressively.
    // For many transactions, the cost will be greater than the fees in terms of raw lamports.
    // For the purposes of calculating prioritization, we multiply the fees by a large number so that
    // the cost is a small fraction.
    // An offset of 1 is used in the denominator to explicitly avoid division by zero.
    const MULTIPLIER: u64 = 1_000_000;
    Some(
        MULTIPLIER
            .saturating_mul(reward)
            .wrapping_div(cost.sum().saturating_add(1)),
    )
}

pub(crate) fn calculate_priority_and_cost<Tx: TransactionMeta + SVMStaticMessage>(
    bank: &Bank,
    transaction: &Tx,
    transaction_configuration: &TransactionConfiguration,
) -> (u64, u64) {
    let cost = CostModel::calculate_cost_for_executed_transaction(
        transaction,
        u64::from(transaction_configuration.compute_unit_limit),
        transaction_configuration.loaded_accounts_data_size_limit,
        &bank.feature_set,
    )
    .sum();
    let fee_details = solana_fee::calculate_fee_details(
        transaction,
        bank.fee_structure().lamports_per_signature,
        transaction_configuration.priority_fee_lamports,
        bank.fee_features(),
    );
    let reward = bank
        .calculate_reward_and_burn_fee_details(&CollectorFeeDetails::from(fee_details))
        .get_deposit();

    // We need a multiplier here to avoid rounding down too aggressively.
    // For many transactions, the cost will be greater than the fees in terms of raw lamports.
    // For the purposes of calculating prioritization, we multiply the fees by a large number so that
    // the cost is a small fraction.
    // An offset of 1 is used in the denominator to explicitly avoid division by zero.
    const MULTIPLIER: u64 = 1_000_000;
    (
        reward
            .saturating_mul(MULTIPLIER)
            .saturating_div(cost.saturating_add(1)),
        cost,
    )
}
