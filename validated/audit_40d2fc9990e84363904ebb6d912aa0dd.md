### Title
StackerDB chunk signatures omit the contract/message-type identity, enabling cross-context chunk replay across `.signers-N-X` contracts - (File: `libstackerdb/src/libstackerdb.rs`)

### Summary
`SlotMetadata::auth_digest()` computes the signed digest as `sha512/256(slot_id || slot_version || data_hash)` [1](#0-0) , and this is the only data a stacker/signer commits to when authorizing a StackerDB chunk write via `SlotMetadata::sign`/`verify` [2](#0-1) . The smart-contract identity of the target StackerDB (i.e., which `MessageSlotID`/message type the chunk belongs to) is never part of the signed payload — it is only used afterward to look up which signer address is authorized for that particular `(contract, slot_id)` pair [3](#0-2) . Because the same reward-cycle signer set is deployed with an identical, deterministic signer→slot_id ordering across every per-message-type contract (`signers-{0|1}-1` for `BlockResponse`, `signers-{0|1}-2` for `StateMachineUpdate`, `signers-{0|1}-3` for `BlockPreCommit`) [4](#0-3) , verified by the `signers_db_get_slots` test which shows every message-id contract for a signer set returns the same signer-slot list [5](#0-4) , a chunk validly signed by a signer for one message-type contract also verifies against that same signer's slot in a completely different message-type contract.

### Finding Description
StackerDB writes and inter-node gossip are publicly observable (any peer can request/receive `StackerDBChunkData` for any replicated DB), and `PeerNetwork::validate_received_chunk` accepts a pushed/downloaded chunk purely by (a) size, (b) `get_slot_signer(contract, slot_id)` lookup, (c) `SlotMetadata::verify(&addr)`, and (d) freshness/`max_writes` — none of which binds the signature to the specific contract it was created for [6](#0-5) . The same equality gap exists in the on-disk write path, `StackerDBTx::try_replace_chunk`, which resolves `slot_validation.signer` from `(smart_contract, slot_id)` and then calls `slot_desc.verify(&slot_validation.signer)` — again, the contract identity is used only for the signer *lookup*, not as part of what was actually signed [7](#0-6) .

Since signer slot assignment is identical across all `MessageSlotID` contracts for the same reward-cycle parity, an attacker who observes any legitimately-broadcast, validly-signed chunk from signer S for slot K in contract A (e.g., `BlockResponse`) can resubmit the exact same `(slot_id=K, slot_version, sig, data)` tuple to contract B (e.g., `StateMachineUpdate` or `BlockPreCommit`) at the same `slot_id=K`, provided only that the submitted `slot_version` is fresher than what's currently stored in B for that slot (trivial, since a new StackerDB instance/slot starts at version 0) and does not exceed `max_writes`. `try_replace_chunk`/`validate_received_chunk` will accept it because the signature check only ever verifies `(slot_id, slot_version, data_hash)` against the signer address that happens to own slot K in the target contract — the type/context this data was actually intended for is never checked. This is a direct structural analog of H-29: the discriminating "type" (here, message/contract context) is left out of the signed payload, so data legitimately signed for context A can be smuggled in as valid for context B whenever the underlying authorization key coincides across contexts.

### Impact Explanation
This allows an unauthenticated third party (anyone who observed the original broadcast, which is by design public) to force acceptance of a chunk into a StackerDB context (message type) that the signer never intended, and have it stored and further gossiped by the node/replica as if it were a legitimate `BlockPreCommit`/`StateMachineUpdate`/etc. message from that signer. Downstream consumers (e.g., `StackerDBListener`/`GlobalStateEvaluator`, which deserializes chunk bytes as `SignerMessageV0::StateMachineUpdate` per address, and the block-response/pre-commit vote tallying logic) trust that a chunk stored under a given slot in a given contract was authored by the corresponding signer for that exact message type. Feeding cross-context bytes (e.g., raw `BlockResponse` payload bytes replayed into the `StateMachineUpdate` slot) causes the consumer to attempt to parse foreign-shaped data as its own expected schema; depending on serialization overlap this can either be silently dropped (deserialize failure) or, if the byte layouts partially coincide, misinterpreted as a legitimate state/vote update, corrupting the network's view of that signer's state or vote and propagating forged, non-canonical StackerDB data across the network as if canonical.

### Likelihood Explanation
Exploitation requires no privileged access: capturing any publicly broadcast, validly-signed chunk and replaying it via the standard `POST /v2/stackerdb/{contract}/chunks` endpoint or via P2P `StackerDBPushChunk` to a *different* target contract using the identical signer/slot mapping. The only constraint is that the target slot's stored version in that other contract is behind the replayed `slot_version`, which is essentially always true for freshly-provisioned per-cycle contracts and easily satisfiable otherwise. No cryptographic forgery is needed — only observation and resubmission of previously-seen legitimate signatures.

### Recommendation
Bind the signed digest to the specific StackerDB context: include the `smart_contract_id` (or equivalently the `MessageSlotID`) inside `SlotMetadata::auth_digest()` alongside `slot_id`, `slot_version`, and `data_hash`, and require both signer and verifier to supply/check it. This mirrors the H-29 recommendation of folding the "type" discriminator into the signed payload so that a valid signature for one context can never be replayed as valid for another.

### Proof of Concept
1. Reward cycle `N`, signer `S` with private key `sk` is assigned `slot_id=3` in both `.signers-0-1` (`BlockResponse`) and `.signers-0-2` (`StateMachineUpdate`) contracts, per the deterministic, identical slot ordering shown in `signers_db_get_slots` [8](#0-7) .
2. `S` legitimately signs and broadcasts a `BlockResponse` chunk: `chunk = StackerDBChunkData{slot_id:3, slot_version:5, data: block_response_bytes}`, `chunk.sign(sk)` [9](#0-8) . Any peer/observer receives this via normal StackerDB replication.
3. An attacker (not possessing `sk`) resubmits the identical `(slot_id, slot_version, sig, data)` to `.signers-0-2` (`StateMachineUpdate`) via `POST /v2/stackerdb/{signers-0-2}/chunks`.
4. `try_replace_chunk` looks up the `StateMachineUpdate` contract's slot-3 signer (also `S`), calls `slot_desc.verify(&S)` which succeeds because the digest never referenced which contract it was for [7](#0-6) , and the chunk (raw `BlockResponse` bytes) is accepted and stored as slot 3's data in the `StateMachineUpdate` StackerDB, then gossiped to other peers as legitimate.

            sigh.as_bytes(),
