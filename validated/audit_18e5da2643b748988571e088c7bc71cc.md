### Title
Git submodule fetch forces `protocol.file.allow=always`, re-enabling arbitrary local-path submodule cloning (CVE-2022-39253 class) - (`tools/build_defs/repo/git_worker.bzl`)

### Summary
`git_repository`'s submodule handling unconditionally passes `-c protocol.file.allow=always` to `git submodule update`, which re-enables Git's `file://` submodule protocol that upstream Git disabled by default specifically to fix CVE-2022-39253 (arbitrary local file/directory disclosure via malicious `.gitmodules`). A hostile git remote (an untrusted branch/tag/mirror a victim's build fetches) can ship a `.gitmodules` file with a submodule URL pointing at an arbitrary local filesystem path; because Bazel forces the protocol back on, `git submodule update --init` will happily "clone" that local path into the checked-out repository, disclosing its contents into the build tree.

### Finding Description
`update_submodules()` in [1](#0-0)  runs:
```
_git_maybe_shallow(ctx, git_repo, "-c", "protocol.file.allow=always", "submodule", "update", "--init", ...)
```
for both the recursive and non-recursive submodule-init paths, whenever `init_submodules`/`recursive_init_submodules` is set on a `git_repository`/`new_git_repository` rule. The inline comment even documents the intent: *"protocol.file.allow=always" allows the submodule command clone from a local directory*, referencing bazel issue #17040. This directly undoes the upstream Git hardening (Git ≥2.38.1 disabled `file://` for submodules by default) that was introduced to close CVE-2022-39253.

The submodule *URLs* themselves come from `.gitmodules`, which is ordinary file content fetched from the remote (`fetch`/`reset`/`clean` in the same file, e.g. [2](#0-1) ). For `git_repository` invocations pinned only by `branch` or `tag` (no `commit`), that content is not cryptographically bound to anything the root module specified — the remote server fully controls it on every fetch, matching the "hostile origin server" fetch-and-integrity threat model (analogous to the checksum-less path for `http_archive`, but here there is no integrity mechanism available at all for git refs). Even with `commit` pinned, an attacker who controls the initial ref resolution before a lockfile/commit is first recorded, or who serves a matching object via a MITM-free hostile mirror under an as-yet-unpinned branch, can supply the malicious `.gitmodules` blob.

Because `protocol.file.allow=always` is forced globally for the `submodule update` invocation, any submodule URL of the form `file:///absolute/local/path` (or a `../`-relative local path) is honored, letting `git` clone/read directories from the local machine (attacker-chosen paths on the build host, e.g. other output_base repos, `$HOME`, cache directories) into the external repository's checkout. This bypasses the containment invariant that "untrusted repository content stays inside the repository directory and originates only from the declared remote."

### Impact Explanation
This is a read-outside-the-repository-directory primitive: an attacker who controls (or can influence, e.g. via an untrusted branch/tag/mirror) the content fetched by `git_repository` can smuggle arbitrary local filesystem content into the fetched repository tree, where it becomes readable by subsequent build steps, potentially leaking secrets or code residing elsewhere on the build machine/output base into build artifacts or logs.

### Likelihood Explanation
Requires a `git_repository`/`new_git_repository` usage with `init_submodules = True` (or `recursive_init_submodules = True`) fetching from an attacker-influenced remote/branch/tag/mirror — a realistic and common configuration for external Git dependencies, since submodule support is a documented, supported feature of this rule.

### Recommendation
Do not force `protocol.file.allow=always` for submodule updates. Only enable `file://` protocol narrowly, if at all, and only for genuinely local/trusted submodule sources; otherwise leave Git's upstream default (which blocks `file://` submodule URLs) intact, or explicitly validate/deny submodule URLs using `file://` or local absolute paths before invoking `git submodule update`.

### Proof of Concept
1. Set up a "hostile" git remote whose HEAD/tag/branch contains a `.gitmodules` such as:
   ```
   [submodule "leak"]
       path = leak
       url = file:///etc
   ```
2. In `MODULE.bazel`, declare:
   ```
   git_repository = use_repo_rule("@bazel_tools//tools/build_defs/repo:git.bzl", "git_repository")
   git_repository(
       name = "evil",
       remote = "<hostile-remote-url>",
       branch = "main",
       init_submodules = True,
   )
   ```
3. Run `bazel fetch @evil//...`. Observe that `git submodule update --init` (invoked with `-c protocol.file.allow=always` per [3](#0-2) ) successfully clones `/etc` into the `leak` subdirectory of the external repository instead of failing with Git's normal `fatal: transport 'file' not allowed` error.
4. This can be turned into a `src/test/shell/bazel/external_git_test.sh`-style shell integration test that creates a local git repo acting as the "hostile" origin with a `.gitmodules` pointing to a local path outside the workspace, and asserts the forbidden content appears in the fetched repository.

def fetch(ctx, git_repo):
    args = ["fetch", "origin"]

    sparse_checkout_patterns_or_file = \
        getattr(ctx.attr, "sparse_checkout_patterns", None) or \
        getattr(ctx.attr, "sparse_checkout_file", None)
    if sparse_checkout_patterns_or_file:
        if _git_sparse_checkout_config(ctx, git_repo):
            # Use filter to disable downloading file contents until we set the `sparse-checkout` patterns.
            args.append("--filter=blob:none")
        else:
            print("WARNING: Sparse checkout is not supported. Doing a full checkout.")
            sparse_checkout_patterns_or_file = None

    args.extend(["--", git_repo.fetch_ref])
    st = _git_maybe_shallow(ctx, git_repo, *args)

    if sparse_checkout_patterns_or_file:
        _git_sparse_checkout(ctx, git_repo, sparse_checkout_patterns_or_file)

    if st.return_code == 0:
        return
    if ctx.attr.commit:
        # Perhaps uploadpack.allowReachableSHA1InWant or similar is not enabled on the server;
        # fall back to fetching all branches, tags, and history.
        # The semantics of --tags flag of git-fetch have changed in Git 1.9, from 1.9 it means
        # "everything that is already specified and all tags"; before 1.9, it used to mean
        # "ignore what is specified and fetch all tags".
        # The arguments below work correctly for both before 1.9 and after 1.9,
        # as we directly specify the list of references to fetch.
        _report_progress(ctx, git_repo, shallow_failed = True)
        _git(
            ctx,
            git_repo,
            "fetch",
            "origin",
            "--",
            "refs/heads/*:refs/remotes/origin/*",
            "refs/tags/*:refs/tags/*",
        )
    else:
        _error(ctx.name, ["git"] + args, st.stderr)

def reset(ctx, git_repo):
    _git(ctx, git_repo, "reset", "--hard", git_repo.reset_ref)

def update_submodules(ctx, git_repo, recursive = False):
    if recursive:
        # "protocol.file.allow=always" allows the submodule command clone from a local directory.
        # It's necessary for Git 2.38.1 and assoicated backport versions.
        # See https://github.com/bazelbuild/bazel/issues/17040
        _git_maybe_shallow(ctx, git_repo, "-c", "protocol.file.allow=always", "submodule", "update", "--init", "--recursive", "--checkout", "--force")
    else:
        _git_maybe_shallow(ctx, git_repo, "-c", "protocol.file.allow=always", "submodule", "update", "--init", "--checkout", "--force")
