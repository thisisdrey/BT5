### Title
Unchecked boolean return value of `addAssetAmountV2` in `ExchangeWithdrawActuator.execute()` can silently drop TRC10 asset credits - (File: actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java)

### Summary
`AccountCapsule.addAssetAmountV2` returns a `boolean` indicating whether the asset amount was actually applied to the account, but `ExchangeWithdrawActuator.execute()` (and its sibling `ExchangeInjectActuator.execute()`) discard this return value when crediting `tokenID`/`anotherTokenID` back to the user account.

### Finding Description
`AccountCapsule.addAssetAmountV2` is declared to return `boolean` and can return `false` in certain code paths (e.g. when `getAllowSameTokenName()==0` and the asset is not found the same way `addAsset`/`addAssetV2` explicitly return `false` on conflicting entries, per the sibling methods at [2](#0-1) ). The method contract clearly implies a caller must check for failure — this is exactly how `Commons.adjustAssetBalanceV2` treats it, throwing `BalanceInsufficientException` if the call returns `false`: [3](#0-2) 

However, in `ExchangeWithdrawActuator.execute()`, the two calls that credit the withdrawn token and "another token" amounts back to the user's account ignore the boolean result entirely: [4](#0-3) 

The same unchecked pattern exists in `ExchangeInjectActuator.execute()`: [5](#0-4) 

In both actuators, the exchange pool balance (`ExchangeCapsule`) is unconditionally updated via `exchangeCapsule.setBalance(...)` regardless of whether the corresponding account-side asset credit actually succeeded. If `addAssetAmountV2` were ever to fail silently (return `false`) for the credit side while the debit/pool-side accounting has already proceeded, the transaction would still be marked `SUCESS`, and TRX/TRC10 value would be removed from the exchange pool's balance bookkeping without the equivalent asset being credited to the user's account — a direct value-loss condition analogous to the reported "success not checked" oracle bug, where ignoring a boolean success flag allows stale/incorrect state to be treated as if the operation succeeded.

### Impact Explanation
If the unchecked `addAssetAmountV2` call ever returns `false` in a reachable state, the actuator proceeds to commit the transaction as successful and persists the exchange pool's reduced balance via `Commons.putExchangeCapsule`, while the user's account is never credited with the corresponding asset — a permanent loss of value for the user with no on-chain sign of failure (`ret.setStatus(fee, code.SUCESS)` is always set on this path). Any unprivileged account holder invoking `ExchangeWithdrawContract` or `ExchangeInjectContract` (both broadcastable, unprivileged transaction types) can trigger this actuator path.

### Likelihood Explanation
`ExchangeWithdrawActuator`/`ExchangeInjectActuator` are actuators for ordinary user-broadcastable transactions (`ExchangeWithdrawContract`/`ExchangeInjectContract`), reachable by any account without special permission via `validate()`+`execute()`. The current `addAssetAmountV2` implementation for `AllowSameTokenName==1` (the active path in modern java-tron) always returns `true` after `importAsset`, so the guaranteed conditions for the return value to become `false` in this call site are not evident from current code, keeping practical exploitability uncertain absent further state (e.g. legacy `AllowSameTokenName==0` path interacting with `importAsset`/asset-not-found edge cases). This is a defensive/robustness gap rather than a demonstrated exploit today.

### Recommendation
Check the boolean return values of both `addAssetAmountV2` calls in `ExchangeWithdrawActuator.execute()` and `ExchangeInjectActuator.execute()`, mirroring the pattern already used in `Commons.adjustAssetBalanceV2` and `TransferAssetActuator.execute()` (which does check `reduceAssetAmountV2`'s return and throws `ContractExeException` on failure). Throw `ContractExeException` on `false` before persisting the exchange pool state, to guarantee atomicity between pool debit/credit and account-side asset changes.

### Proof of Concept
Not independently reproducible from the current call graph, since `addAssetAmountV2` returns `true` unconditionally on the `AllowSameTokenName==1` path in the current source, per [6](#0-5) . The finding documents a code-hygiene/defense-in-depth gap: the unchecked return value pattern is structurally identical to the reported class of bug and violates the contract implied by `addAssetAmountV2`'s boolean signature and by the checked-usage pattern elsewhere in the codebase (`Commons.adjustAssetBalanceV2`, `TransferAssetActuator`).

  public boolean addAssetAmountV2(byte[] key, long amount,
      DynamicPropertiesStore dynamicPropertiesStore, AssetIssueStore assetIssueStore) {
    importAsset(key);
    boolean disableJavaLangMath = dynamicPropertiesStore.disableJavaLangMath();
    //key is token name
    if (dynamicPropertiesStore.getAllowSameTokenName() == 0) {
      Map<String, Long> assetMap = this.account.getAssetMap();
      AssetIssueCapsule assetIssueCapsule = assetIssueStore.get(key);
      String tokenID = assetIssueCapsule.getId();
      String nameKey = ByteArray.toStr(key);
      Long currentAmount = assetMap.get(nameKey);
      if (currentAmount == null) {
        currentAmount = 0L;
      }
      this.account = this.account.toBuilder()
          .putAsset(nameKey, addExact(currentAmount, amount, disableJavaLangMath))
          .putAssetV2(tokenID, addExact(currentAmount, amount, disableJavaLangMath))
          .build();
    }
    //key is token id
    if (dynamicPropertiesStore.getAllowSameTokenName() == 1) {
      String tokenIDStr = ByteArray.toStr(key);
      Map<String, Long> assetMapV2 = this.account.getAssetV2Map();
      Long currentAmount = assetMapV2.get(tokenIDStr);
      if (currentAmount == null) {
        currentAmount = 0L;
      }
      this.account = this.account.toBuilder()
          .putAssetV2(tokenIDStr, addExact(currentAmount, amount, disableJavaLangMath))
          .build();
    }
    return true;
  }

  public boolean addAsset(byte[] key, long value) {
    Map<String, Long> assetMap = this.account.getAssetMap();
    String nameKey = ByteArray.toStr(key);
    if (!assetMap.isEmpty() && assetMap.containsKey(nameKey)) {
      return false;
    }
    this.account = this.account.toBuilder().putAsset(nameKey, value).build();
    return true;
  }

  public boolean addAssetV2(byte[] key, long value) {
    if (AssetUtil.hasAssetV2(this.account, key)) {
      return false;
    }

    this.account = this.account.toBuilder()
        .putAssetV2(ByteArray.toStr(key), value)
        .build();
    return true;
  }
