### Title
Path-containment bypass in ijar `unzip` allows zip entries to escape the extraction root via "same prefix, different sibling directory" - (File: third_party/ijar/zip_main.cc)

### Summary
The `unzip`/`zip` command-line tool (`third_party/ijar/zip_main.cc`), which is embedded as `tools/zip/zipper` and used by Bazel's build/test tooling (`src/package_zip.bzl`, `src/builtins_zip.bzl`, embedded tools list) to extract zip archives, validates that an extracted entry stays within `output_root_` using a raw string-prefix comparison rather than a proper path/segment-boundary check.

### Finding Description
In `UnzipProcessor::Process`, the containment check is:
```
std::string normalized_root = normalize_path(output_root_);
std::string normalized = normalize_path(path);
if (normalized.compare(0, normalized_root.size(), normalized_root) != 0) {
  fprintf(stderr, "paths in the zip may not end up outside of the output directory...");
  abort();
}
``` [1](#0-0) 

This is exactly the bug class described in CVE-2017-0360 ("same root name but with a suffix" attack): `std::string::compare(0, len, prefix)` only checks that the first `len` characters of `normalized` equal `normalized_root` — it does **not** verify that the next character (if any) is a path separator. So if `output_root_` normalizes to `/out`, an entry whose resolved path normalizes to `/output_evil/passwd` also satisfies `normalized.compare(0, 4, "/out") == 0`, because `"/output_evil"` shares the 4-character prefix `"/out"`. The entry is written to a sibling directory (`/output_evil/...`) that is outside the intended `output_root_`, bypassing the containment check entirely.

Contrast this with the correct pattern used elsewhere in the same codebase, e.g. `paths.bzl`'s `_starts_with`, which explicitly checks `norm_a[len(norm_b)] == "/"` after the prefix match [2](#0-1) , and `git.bzl`'s strip_prefix escape check, which requires `str(strip_prefix_path).startswith(str(checkout_realpath) + "/")` [3](#0-2) . The ijar unzip tool lacks this trailing-separator check.

### Impact Explanation
An attacker who controls the contents of a zip archive that gets extracted by this `unzip` tool (e.g., an `http_archive`/`http_file`-downloaded archive without a matching checksum enforcement point in this particular code path, a build-time genrule/action that unpacks an untrusted zip, or any consumer that shells out to `zipper`/`unzip_bin`) can craft an entry whose combined path (`output_root_` + entry name, normalized) shares only a string-level prefix with the legitimate output root but actually resolves into a sibling filesystem location. This allows writing files outside the intended extraction directory, a form of path-traversal / arbitrary-file-write, analogous to Tryton's `file_open` "same root name but suffix" flaw.

### Likelihood Explanation
Exploitability depends on how a specific caller of `zipper`/`unzip_bin` selects `output_root_` (e.g., whether it is guaranteed to end without a name collision with a sibling directory) and whether the entry name/attacker-controlled content is fully attacker chosen. Because this tool is a generic zip/unzip binary invoked from various Bazel build rules and packaging scripts, and the check is purely string-based, this is a realistic containment-check weakness, though I could not fully trace every call site (e.g., whether `sha256`/`integrity` verification always precedes extraction for repository-fetch use, versus build-time packaging rule use where no checksum applies) within the available indexed context.

### Recommendation
Fix the containment check in `UnzipProcessor::Process` to require a path-separator boundary after the prefix match, e.g.:
```cpp
if (normalized.compare(0, normalized_root.size(), normalized_root) != 0 ||
    (normalized.size() > normalized_root.size() &&
     normalized[normalized_root.size()] != '/')) {
  ...
}
```
This mirrors the correct boundary-aware checks already used in `paths.bzl` (`_starts_with`) and `git.bzl` (`add_prefix`/`strip_prefix` escape checks) elsewhere in the codebase.

### Proof of Concept
Not fully reproducible from the available indexed context — I was unable to confirm all call sites and whether an attacker-controlled archive can reach this code path without also being subject to a `sha256`/`integrity` check upstream (e.g., in `http_archive` extraction vs. direct `zipper`/`unzip_bin` invocations in build actions). A concrete PoC would need a `third_party/ijar/test` shell test that creates a zip with an entry name causing `output_root_ + entry` to normalize into a sibling directory sharing a string prefix (e.g., `output_root_ = "out"`, entry resolving to `../out_evil/pwned`), then invokes the `unzip_bin` with that archive and asserts the file lands outside `out/`. This should be validated with a background agent that can build and run `third_party/ijar/test/zip_test.sh`-style tests against the actual binary.
