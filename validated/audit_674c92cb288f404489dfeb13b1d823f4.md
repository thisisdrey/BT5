### No vulnerability found for this question.

**Reasoning:** The scenario requires a `Request` containing `WalletOp::AddExtension{account_id: attacker.near}` followed by `WalletOp::SetSignatureMode{enable:false}` to be executed via `execute_signed` or `execute_extension`, both of which require either a valid signature from the wallet's own key over that exact `RequestMessage` (`S::verify_request_msg`) [1](#0-0)  or the caller already being an enabled extension with equivalent full control (`check_extension_enabled`) [2](#0-1) . An unprivileged attacker holding no victim private key and not already an enabled extension cannot construct or forge such a `Request`; they can only relay whatever the owner actually signed, and `verify_request_msg` binds the signature to the exact `msg.request` content, so a relayer cannot inject `AddExtension{attacker.near}` into a payload the owner never signed [3](#0-2) .

`check_lockout` is only designed to prevent total lockout (no signature AND no extensions), not to prevent an owner from intentionally delegating full control to a new extension while disabling their own signature in the same authorized batch [4](#0-3) [5](#0-4) . This exact sequential-ops pattern (`AddExtension` then disable signature within one signed request) is the documented, intended "key rotation" flow, where extensions are explicitly described as having "the same full power over the wallet-contract instance as the original signer" [6](#0-5) , and is demonstrated in the SDK test `rotate` which performs precisely this two-step disable-signature-after-add-extension pattern as legitimate functionality [7](#0-6) .

Since the attacker cannot get such a `Request` signed or authorized without already holding the victim's key or already being a trusted extension, the described "self-lockout into attacker control" requires the victim to voluntarily sign a malicious payload naming the attacker's account — a social-engineering precondition explicitly out of scope. There is no path where an unprivileged attacker (per the given profile) can inject this op sequence into an authorized `Request` without owner cooperation, so the claimed broken binding does not hold under the stated attacker capabilities.

    fn execute_signed(&mut self, msg: RequestMessage, proof: &str) -> Result<()> {
        if !self.0.is_signature_allowed() {
            return Err(Error::SignatureDisabled);
        }

        // TODO: change to the following when External Contract Calls land:
        // if !msg.pay_for_gas && env::is_external() {
        //     return Err(Error::UnauthorizedGasPayment);
        // }
        if msg.pay_for_gas {
            env::panic_str("`pay_for_gas` is not currently supported");
        }

        // check chain_id
        if msg.chain_id != env::chain_id() {
            return Err(Error::InvalidChainId);
        }

        // check signer_id
        if msg.signer_id != env::current_account_id() {
            return Err(Error::InvalidSignerId(msg.signer_id));
        }

        // commit the nonce
        self.0
            .nonces
            .commit(msg.nonce, msg.created_at, msg.timeout)?;

        // verify signature
        if !S::verify_request_msg(&self.0.public_key, &msg, proof) {
            return Err(Error::InvalidSignature);
        }

        let hash = msg.hash();
        WalletEvent::SignedRequest { hash }.emit();

        self.execute_request(msg.request, &Actor::SignedRequest(hash))
    }

    fn execute_extension(&mut self, request: Request) -> Result<()> {
        if env::attached_deposit().is_zero() {
            return Err(Error::InsufficientDeposit);
        }

        // check whether extension is enabled
        let extension_id = env::predecessor_account_id();
        self.check_extension_enabled(&extension_id)?;

        // maybe cleanup nonces from the storage as best-effort to make it
        // available for further applying wallet-ops below
        self.0.nonces.check_cleanup();

        self.execute_request(request, &Actor::Extension(extension_id.into()))
    }

    fn set_signature_mode(&mut self, enable: bool, actor: Actor<'_>) -> Result<()> {
        if self.0.signature_enabled == enable {
            return Err(Error::ThisSignatureModeAlreadySet);
        }
        self.0.signature_enabled = enable;
        self.check_lockout()?;

        WalletEvent::SignatureModeSet {
            enabled: enable,
            by: actor,
        }
        .emit();

        Ok(())
    }

Extensions are **separate** third-party accounts/contracts on Near that can
execute arbitrary requests on behalf of the wallet and have the same full power
over the wallet-contract instance as the original signer does. Extensions can be
added or removed by the signer or other installed extensions.

Extensions is an *open ecosystem* which enable patterns like 2FA, social
recovery, spending limits, session keys, etc.

#### Lockout protection

The contract prevents disabling all authentication methods at once: if signature
is disabled, then at least one extensions must remain enabled. Otherwise, the
whole request fails.
