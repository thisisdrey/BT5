The Go standard library's `net/http` transfer-length logic already implements the RFC 9112 §6.3 mitigations that address exactly the smuggling primitive described in the Jetty advisory (dual Content-Length headers / Content-Length vs. chunked Transfer-Encoding confusion). Specifically:

- `readTransfer` in `src/net/http/transfer.go:500` computes framing via `determineBodyLength`, which explicitly enumerates the RFC 9112 rules.
- If both `Content-Length` and `Transfer-Encoding` are present, Content-Length is discarded and the connection is forced closed rather than silently trusting a smuggled length: [1](#0-0) 
- Multiple/duplicate `Transfer-Encoding` values, or any value other than exactly `"chunked"`, are rejected outright as errors (`errTooManyTransferEncodings`, `errUnsupportedTransferEncoding`), rather than being ambiguously interpreted: [2](#0-1) 
- The server-side test suite explicitly encodes the RFC 9112 §6.3 matrix (duplicate Content-Length, comma-separated duplicate values, invalid CL, duplicate/garbled TE) and asserts either rejection (400/501 + connection close) or safe single-value handling: [3](#0-2) 
- At the `conn.serve` level, unsupported Transfer-Encoding errors are converted into a `501` response and the connection is not reused, closing off any smuggling window: [4](#0-3) 

This is the opposite of the Jetty flaw: Jetty's bug was *ignoring* Content-Length when both headers were present without also closing the connection, letting an intermediary's "leftover" bytes be reinterpreted as a pipelined request. Go's `transfer.go` deliberately sets `t.Close = true` in the ambiguous dual-header case (`src/net/http/transfer.go:724`), which is the standard smuggling-prevention pattern that Jetty itself later adopted. I did not find `parseContentLength`'s exact body in the available index snippets (only its call sites), but the enclosing logic and the dedicated regression tests (`TestServerRequestBodyLength` and `readrequest_test.go`) confirm strict, single-value-only Content-Length handling with rejection on conflicting values [5](#0-4) .

No code path in the reachable production HTTP request-parsing flow (`readRequest` → `readTransfer` → `determineBodyLength`) reproduces the Jetty CVE-2017-7658 primitive of silently trusting an inconsistent length while keeping the connection alive. Given the rules in the prompt (must show a concrete, currently-reachable, unfixed bypass; reject already-fixed/duplicate findings), this does not qualify as a valid analog finding.
