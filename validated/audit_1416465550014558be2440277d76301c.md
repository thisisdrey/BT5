### Title
Attacker can permanently occupy a victim's `MAX_TOKENS_PER_USER` slots via dust `DepositToken` transfers, DoS-ing borrowing and incoming deposits — ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
Analogous to a memory leak (a resource allocated and never released), an attacker can fill the victim's `depositTokensOfAccount` enumerable set — capped at `MAX_TOKENS_PER_USER = 30` — by transferring 1 wei of each `DepositToken` to the victim. The victim's slot budget is consumed by worthless dust positions they never asked for. Because `Pool.addToDebtTokensOfAccount`/`addToDepositTokensOfAccount` revert once the combined count reaches 30, the victim can no longer mint debt (`DebtToken` issue/mint path), receive a new collateral type, or receive a `deposit` made `onBehalfOf_` them — every such call reverts with `UserReachedMaxTokens`.

### Finding Description
- `Pool` tracks per-account tokens in `debtTokensOfAccount`/`depositTokensOfAccount` (`MappedEnumerableSet`) and enforces `onlyIfAdditionWillNotReachMaxTokens` (`Pool.sol:143-148`).
- `DepositToken._transfer` adds the token to the recipient's set whenever `balanceOf[recipient] == 0`, with no opt-in from the recipient (`DepositToken.sol:517-520`). Removal only happens when a balance goes back to exactly 0 (`DepositToken.sol:523-525`).
- `DepositToken.deposit` lets anyone mint dust shares on any collateral, and `transfer`/`transferFrom` let the attacker push those shares to the victim.
- On deployments where 30 deposit tokens exist (the governor-side cap `addDepositToken` uses the same `MAX_TOKENS_PER_USER`), the attacker deposits dust into each collateral, then transfers 1 wei of each `DepositToken` to the victim. The victim's combined set size hits 30.
- Consequences while slots are saturated:
  - `DebtToken` issuance calls `pool.addToDebtTokensOfAccount(account)` → reverts → victim cannot borrow/mint (denial of a core protocol function for that account).
  - Any `deposit(amount, onBehalfOf_ = victim)` of a collateral the victim doesn't already hold reverts.
  - Any transfer of a new `DepositToken` to the victim reverts, which also griefs third parties (e.g., liquidators/integrations sending tokens to the victim).
- Recovery is possible only by the victim explicitly transferring out each dust balance to zero (30+ transactions), after which the attacker can simply re-fill the slots — a repeatable griefing loop with asymmetric cost, and it blocks leverage/flash-repay flows through `SmartFarmingManager` that mint into the account in the same tx.

### Impact Explanation
Liveness/denial-of-service on a per-account basis: borrowing, new-collateral deposits, and receipt of new deposit tokens all revert for the targeted account. The victim's existing collateral remains withdrawable only after manually shedding dust entries; integrations that batch mint+deposit (SmartFarmingManager `leverage`) revert atomically, so leveraged positions for the account are frozen. This is a "temporary freezing of funds / protocol functions" class impact and is indefinitely repeatable.

### Likelihood Explanation
Requires only that the pool supports enough distinct deposit tokens to saturate the victim's remaining slots (up to 30) and that the attacker can acquire dust shares of each — both achievable by an unprivileged EOA through the public `deposit`/`transfer` entry points. No privileged role, oracle manipulation, or honest-victim cooperation is needed. If a deployment has few deposit tokens, impact shrinks (victim may still have free slots), so severity scales with the number of registered deposit tokens.

### Recommendation
- Do not add tokens to a recipient's set on plain `transfer`; only add on `deposit`-originated mints, or require `recipient == msg.sender`/opt-in.
- Alternatively, don't revert on `UserReachedMaxTokens` for recipient-side set additions during `seize`/transfers to fee collector/liquidator, or raise/remove the cap by making `depositOf`/`debtOf` iterate over the pool's global token lists filtered by nonzero balance.

### Proof of Concept
Hardhat fork/mainnet test sketch:

```ts
// For each DepositToken dt in pool.getDepositTokens():
// 1. attacker approves underlying and calls dt.deposit(1 wei-of-underlying, attacker)
// 2. attacker calls dt.transfer(victim, 1)
// After N transfers, pool.depositTokensOfAccount(victim) + debtTokensOfAccount(victim).length == 30

// 3. victim (or anyone via deposit onBehalfOf) tries:
await expect(
  debtToken.connect(victim).issue(amount) // -> Pool.addToDebtTokensOfAccount
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');

await expect(
  someNewDepositToken.connect(bob).deposit(amount, victim) // onBehalfOf victim
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');
```

Steps verified against `Pool.onlyIfAdditionWillNotReachMaxTokens` (`Pool.sol:143`), `addToDepositTokensOfAccount` (`Pool.sol:216`), and the recipient-side set insertion in `DepositToken._transfer` (`DepositToken.sol:517-520`). The exact revert inside `DebtToken.issue`/`mint` and the SmartFarmingManager batching path were not fully read in this pass, but they route through the same `addToDebtTokensOfAccount`/`_mint` calls and will revert identically.
