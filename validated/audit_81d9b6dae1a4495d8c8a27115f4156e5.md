### Title
Unprivileged attacker can fill a victim's `depositTokensOfAccount`/`debtTokensOfAccount` list to `MAX_TOKENS_PER_USER` via dust `deposit(onBehalfOf_)` / `transfer`, permanently DoS-ing the victim's ability to deposit new collateral types or mint new synths while debt exists - (File: contracts/DepositToken.sol)

### Summary
The analog of CVE-2016-5436 (a remote availability/DoS bug) in Metronome is a per-account token-list saturation attack. `DepositToken.deposit(amount_, onBehalfOf_)` mints `msdTOKEN` to an arbitrary beneficiary, and both `_mint` and `_transfer` unconditionally call `pool.addToDepositTokensOfAccount(account_)` whenever the recipient's balance moves from 0 to non-zero (`DepositToken.sol:485-488`, `DepositToken.sol:517-520`). `addToDepositTokensOfAccount` is gated by `onlyIfAdditionWillNotReachMaxTokens` and reverts `UserReachedMaxTokens` once the account's combined deposit+debt token list reaches `MAX_TOKENS_PER_USER` (`Pool.sol:204-208`, `Pool.sol:216-220`; the same cap applies to `addToDebtTokensOfAccount`). An unprivileged attacker can therefore spam dust deposits (or `transfer` dust, which calls `_revertIfLocked` on the *sender*, not the recipient) to a victim for every registered `DepositToken`, forcing the victim's list to the cap without any consent.

### Finding Description
1. `DepositToken.deposit(uint256 amount_, address onBehalfOf_)` is public, `whenNotPaused`, and credits `msdTOKEN` to `onBehalfOf_` — there is no opt-in or allowance check on the beneficiary (`DepositToken.sol:211-237`).
2. On a 0→>0 balance transition, `_mint`/`_transfer` call `pool.addToDepositTokensOfAccount` (`DepositToken.sol:486-488`, `DepositToken.sol:518-520`).
3. `Pool.addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` revert `UserReachedMaxTokens` when the set would exceed `MAX_TOKENS_PER_USER` (`Pool.sol:204`, `Pool.sol:216`).
4. Because `DebtToken._mint` also calls `pool.addToDebtTokensOfAccount(account_)` on first borrow (`DebtToken.sol:597-600`), and it shares the same per-account cap, a saturated victim cannot mint *any new* `DebtToken` type — `DebtToken.issue` reverts inside `_mint` — and cannot deposit *any new* `DepositToken` type or receive new msd-tokens via transfer.
5. Recovery is asymmetric: the victim can only remove entries by reducing their balance of that token to zero, but if they carry debt, `unlockedBalanceOf` may be 0 for the dust tokens (`DepositToken.sol:383-398` returns 0 when `_issuableInUsd == 0`), so the dust slots are locked and cannot be shed until the debt is repaid — while being unable to add a different collateral type to cure an unhealthy position.

### Impact Explanation
Broken invariant: liveness. The victim suffers (a) inability to deposit any collateral type they don't already hold — blocking top-ups to escape liquidation with a different asset; (b) inability to mint any synth type they haven't already borrowed (`issue`, `SmartFarmingManager.leverage` paths revert); (c) inability to receive new `msd` tokens via `transfer`. For an account whose positions became unhealthy because its single existing collateral dropped, the attacker pre-saturating the list means the victim cannot add a healthier collateral and cannot expand issuance — their collateral is effectively temporarily frozen / force-liquidated, and the dust entries cannot be removed while locked. Attacker cost is dust amounts of each registered underlying (recoverable later by withdrawing from their own position, or simply by `transfer`-ing dust they already hold).

### Likelihood Explanation
Fully reachable by any unprivileged EOA through the public `deposit(amount_, victim)` entry point or `transfer(victim, dust)` — no privileged role, oracle manipulation, or special state is required. The number of attacker transactions needed equals the number of registered `DepositToken`s (bounded by `MAX_TOKENS_PER_USER`, which the code and `test/Pool.test.ts:1491-1521` show is enforced as a small constant combined across deposit+debt tokens). The pool just needs ≥ a few registered deposit tokens and the victim to have debt with low issuance headroom for the freeze to stick. Attack is detectable and griefing-style (no direct profit), which lowers real-world frequency but does not remove the loss-of-availability for victims racing to cure positions.

### Recommendation
- Make token-list additions consent-based or lazy: e.g., only add to `depositTokensOfAccount` on self-serve paths (`deposit(amount_, _msgSender)`-equivalent), and for `transfer`/`onBehalfOf` credit balances without registering the token in the victim's list (track a user's tokens via an enumerable list updated on explicit action).
- Alternatively, treat `UserReachedMaxTokens` as a no-op skip rather than a revert when the recipient didn't initiate the operation — i.e., in `_transfer`, wrap `pool.addToDepositTokensOfAccount(recipient_)` so saturation can't brick the recipient (the recipient simply won't get oracle value counted for that dust, which is desirable anyway).
- Consider a per-account removal path that lets users purge dust entries (e.g., a `sweepDust` that force-removes a token whose balance is below a threshold and isn't needed as collateral).

### Proof of Concept
```solidity
// Foundry, fork/deployed config with Pool, DepositToken[] and DebtToken[] registered.
function test_accountListSaturationDoS() public {
    address victim = makeAddr("victim");
    address attacker = makeAddr("attacker");

    // Victim opens a normal position: deposit MET, mint msETH
    uint256 dep = 10 ether;
    deal(address(met), victim, dep);
    vm.startPrank(victim);
    met.approve(address(msdMET), dep);
    msdMET.deposit(dep, victim);
    msEthDebtToken.issue(1 ether, victim); // victim now owes debt -> dust may be locked
    vm.stopPrank();

    // Attacker fills victim's depositTokensOfAccount up to MAX_TOKENS_PER_USER
    uint256 cap = pool.MAX_TOKENS_PER_USER();
    address[] memory dTokens = pool.getDepositTokens();
    for (uint256 i; i < dTokens.length; ++i) {
        IDepositToken dt = IDepositToken(dTokens[i]);
        IERC20 und = dt.underlying();
        deal(address(und), attacker, 1);          // 1 wei of underlying
        vm.startPrank(attacker);
        und.approve(address(dt), 1);
        dt.deposit(1, victim);                    // adds token to victim's list
        vm.stopPrank();
        if (pool.getDepositTokensOfAccount(victim).length
              + pool.getDebtTokensOfAccount(victim).length >= cap) break;
    }
    assertEq(pool.getDepositTokensOfAccount(victim).length
             + pool.getDebtTokensOfAccount(victim).length, cap);

    // 1) Victim cannot deposit a collateral type they don't already hold
    vm.startPrank(victim);
    IDepositToken newCol = IDepositToken(notYetHeldToken);
    deal(address(newCol.underlying()), victim, 1 ether);
    newCol.underlying().approve(address(newCol), 1 ether);
    vm.expectRevert(IPool.UserReachedMaxTokens.selector);
    newCol.deposit(1 ether, victim);              // reverts

    // 2) Victim cannot mint a new synth type (debt token not yet held)
    vm.expectRevert(IPool.UserReachedMaxTokens.selector);
    msDogeDebtToken.issue(1, victim);             // reverts inside _mint
    vm.stopPrank();
}
```
Note: the exact value of `MAX_TOKENS_PER_USER` and the count of registered deposit/debt tokens on each deployment determine attacker cost; on chains where the number of registered `DepositToken`s is already ≥ the cap, the victim is saturated by enumeration of existing tokens alone, with no extra deployments required. If the underlying of some deposit token is scarce, the attacker can instead `transfer` dust `msdTOKEN` they mint to themselves — `_revertIfLocked` only checks the sender.
