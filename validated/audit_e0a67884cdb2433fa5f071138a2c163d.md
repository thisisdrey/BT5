### Title
Direct transfer of underlying token to a Zest vault is permanently unaccounted and unrecoverable - ([File: mainnet/contracts/vault/v0-vault-stx.clar])

### Summary
Zest's tokenized vaults (`v0-vault-stx`, `v0-vault-sbtc`, `v0-vault-ststx`, `v0-vault-usdc`, `v0-vault-usdh`, `v0-vault-ststxbtc`) track the underlying asset amount they hold via an internal accounting variable `assets`, which is only mutated inside `deposit`/`redeem`/borrow-repay flows. This is analogous to the reported Lido issue where `stETH` sent directly to `WstETH.sol` (bypassing `wrap()`) is not reflected in the shares accounting and becomes permanently stuck, since the contract has no function to sweep/reconcile the excess balance against the internally tracked share/asset accounting.

### Finding Description
Each vault holds its accounting state in a `(define-data-var assets uint)` variable, updated only by `deposit` and `redeem` (and lending flows): [1](#0-0) 

The actual on-chain SIP-010 balance held by the vault contract is queried separately via `ubalance`, which simply calls `get-balance current-contract` on the underlying token contract: [2](#0-1) 

If a user (or any other contract) transfers the underlying token (e.g. `wstx`, `sbtc-token`, `ststx-token`, `usdcx`, `usdh-token-v1`, `ststxbtc-token-v2`) directly to the vault's contract principal — outside of `deposit` — the token contract's balance for the vault increases, but the vault's internal `assets` var is never incremented, because that only happens inside `deposit`: [3](#0-2) 

`redeem`, `total-assets`, and `convert-to-assets/shares` all key off `(var-get assets)` plus computed interest, never off the live `ubalance`: [4](#0-3) 

There is no DAO or user-callable function anywhere in these vault contracts (searched for "sweep", "skim", "rescue", "donate", "recover") that reconciles `ubalance` against `assets` or allows withdrawal of the untracked excess. The extra underlying tokens sit in the vault's SIP-010 balance forever, invisible to share price math and unclaimable by anyone, exactly mirroring the referenced Lido `WstETH` root cause: assets received outside the designed wrap/deposit path are not reflected in the internal share/asset ledger and have no recovery path.

### Impact Explanation
Any principal (a normal user, or a contract accidentally routing a transfer to the vault address instead of calling `deposit`) that sends the underlying token directly to a Zest vault contract permanently loses those funds — they are not reflected in `assets`, do not increase redeemable value for any zToken holder, and there is no function to reclaim or redistribute them. This is a permanent freezing of funds, matching the in-scope "High" impact category (permanent freezing of funds), since the underlying tokens become permanently unreachable to their original owner and unusable by the protocol.

### Likelihood Explanation
Likelihood is non-trivial: any wallet or integrating contract that mistakenly uses `transfer` to the vault's contract address (a plausible mistake, since the vault address is a well-known, publicly documented principal per asset) instead of calling `deposit`, or any protocol/DAO logic that assumes `send-to-vault == deposit`, will trigger permanent loss with no recovery, requiring only a single SIP-010 `transfer` call to any of the six vault contracts.

### Recommendation
Add a permissionless or DAO-gated "sync"/"skim" function that computes the delta between `ubalance` (actual token balance) and `(var-get assets)`, and either (a) mints proportional shares to a specified recipient for the excess (mirroring a `deposit`), or (b) increments `assets` and mints treasury shares so the excess is captured and can be redeemed rather than permanently lost, similar to `donate`/`sync` patterns used in standard ERC-4626 implementations.

### Proof of Concept
1. A user calls `(contract-call? .wstx transfer u1000000 tx-sender .v0-vault-stx none)` directly (SIP-010 `transfer`) instead of `(contract-call? .v0-vault-stx deposit u1000000 u0 tx-sender)`.
2. `wstx`'s `get-balance` for `.v0-vault-stx` increases by `1000000`, but `(var-get assets)` in `v0-vault-stx` is unchanged (only `deposit`/`redeem` mutate it).
3. `total-assets`, `convert-to-shares-preview`, and `convert-to-assets-preview` all continue to use the stale `assets` var, so no zSTX shares are minted and no existing holder's redeemable amount increases.
4. There is no function in `v0-vault-stx.clar` (or any sibling vault) that lets the sender, the DAO, or anyone else claim or reconcile that extra `1000000` wstx; it is permanently stuck in the vault contract's token balance.
