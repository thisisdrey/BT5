### Title
Unprivileged clients can front-run and mis-steer the LoadShedder into cancelling a legitimate high-cost RPC instead of the actual offending one, causing DoS of unrelated requests - ([File: internal/burdenmonitor/load_shedder.go])

### Summary
The `MuteBond` report describes an attacker exploiting a shared, globally-mutated state (`epochStart`) that decays over time/usage, letting the attacker front-run a victim's transaction and steer the outcome against them. Gitaly's `BurdenMonitor`/`LoadShedder` load-management subsystem contains an analogous shared, globally-ranked mutable state: the top-N CPU/memory ranking of in-flight RPCs used to decide which RPC gets force-cancelled with `RESOURCE_EXHAUSTED` when the node is under critical pressure.

### Finding Description
`LoadShedder.shed` reacts to a critical `loadmonitor` condition by querying `BurdenMonitor.GetTopNEntries(shedTopN, SortByCPU)` and cancelling whichever in-flight RPCs currently rank highest by cumulative CPU time, regardless of which RPC actually caused the pressure spike or which repository/user it belongs to: [1](#0-0) 

The ranking itself is produced by `entriesSortedBy`, which sorts *all* currently tracked RPC entries system-wide by `TotalCPUTime()`/`TotalMemory()`, with no per-user, per-repository, or per-tenant isolation: [2](#0-1) 

Because this ranking is a single global data structure keyed only by RPC start time and resource consumption, an unprivileged client can influence which RPC gets shed by racing the timing of its own requests relative to a victim's legitimate long-running RPC (e.g. a large clone or push):
1. Attacker spawns several CPU-light-but-long-duration or CPU-heavy operations that push the node into a "Backoff"/"Critical" pressure state (as described in `doc/load-management-architecture.md`, lines 150–164).
2. Simultaneously, a legitimate user's normal (but large) fetch/push/clone runs a CPU-intensive `git` subprocess tracked via the same `RegisterRPC` call: [3](#0-2) .
3. When `LoadShedder.run` fires on the next critical `loadmonitor.Event`, `GetTopNEntries` returns whichever RPCs currently have the highest accumulated CPU time in the whole node — this can include the victim's legitimate RPC even though the attacker caused the pressure event, because the ranking has no correlation to the actual triggering condition or actor. `shedInterval` further concentrates the effect: after one shed, no new shed can occur for 15 seconds, so an attacker can time bursts to land right as a victim's RPC crosses a high CPU-time threshold: [4](#0-3) .
4. The victim's RPC is unilaterally cancelled with `RESOURCE_EXHAUSTED`, even though it was not the cause of the pressure and even though the attacker's own cheaper/shorter-lived requests survive: [5](#0-4) .

This mirrors the bond front-running bug class: a shared, time/usage-decaying, globally-ranked resource (bond price / RPC "shed" ranking) is manipulated by an attacker's cheap, adversarially-timed actions to make a legitimate actor bear an unexpected, worse outcome (lower payout / RPC cancellation) — with no per-actor isolation or "expected outcome" check before the irreversible action (payout transfer / RPC cancellation) is executed.

### Impact Explanation
An unauthenticated or low-privilege attacker who can issue RPCs against a Gitaly node (e.g., via a repository they have push/fetch access to) can influence global node-level backpressure and cause the `LoadShedder` to cancel unrelated, legitimate, and potentially far more important operations (e.g., a large push in progress) instead of the attacker's own requests. This is a resource-limit/DoS-of-handler issue: legitimate work is aborted mid-flight with `RESOURCE_EXHAUSTED`, wasting the resources already spent and forcing costly retries, while the actual offending client can avoid selection simply by keeping its own tracked CPU time lower than the victim's (e.g., splitting work across many short requests). Because ranking is global across the entire node (not scoped per repository or per client), one tenant can repeatedly cause pressure events that always spare its own traffic and target co-located tenants' long-running jobs.

### Likelihood Explanation
Reaching this path requires only the ability to send ordinary Gitaly RPCs (e.g., `PostReceivePack`/`PostUploadPackWithSidechannel`/any RPC that spawns Git subprocesses tracked by `BurdenMonitor`, gated by `featureflag.BurdenMonitorTrackCommands`) concurrently with a victim on the same node — a realistic scenario on shared/multi-tenant Gitaly nodes. The load-shedding path is only engaged when the node is under genuine critical pressure (PSI/OOM thresholds), so the attacker must also be able to generate that pressure, which raises the bar somewhat but is plausible via resource-intensive but individually-cheap-looking operations (e.g., many concurrent small commands with short bursts of high CPU) is a nontrivial DoS objective.

### Recommendation
- Scope shedding decisions or add fairness bounds so that an actor cannot repeatedly avoid being shed while causing pressure that harms others (e.g., per-repository/per-client attribution and weighting, not just a raw global top-N by CPU/memory).
- Correlate the shed decision with the actual RPC(s)/commands that contributed to the triggering `loadmonitor.Event` (e.g., condition resource + recent CPU delta window) rather than lifetime cumulative CPU/memory of all in-flight RPCs.
- Consider excluding or down-weighting RPCs that are close to completion or have already consumed the bulk of legitimate, expected resources for their operation type, to avoid wasting near-complete work.
- Add metrics/audit logging correlating attacker-identifiable request bursts with sheds of unrelated RPCs, to detect this abuse pattern in production.

### Proof of Concept
Conceptual (this is a design-level race, not a memory-safety bug, so no single crafted payload is decisive):
1. Attacker opens N concurrent RPCs to the target Gitaly node that spawn Git subprocesses (e.g., many `git blame`/`git log -p` on a large repo they have access to) tuned to push CPU/PSI over the critical threshold defined in `condition_psi.go`, while keeping each individual RPC's own tracked CPU time below the victim's.
2. Victim issues a legitimate, resource-intensive push/clone at/around the same time; its `RPCEntry.TotalCPUTime()` accumulates and eventually exceeds the attacker's individual entries.
3. Once `loadmonitor` emits a critical event, `LoadShedder.shed` calls `bm.GetTopNEntries(shedTopN, SortByCPU)` and cancels the top 10 by CPU time — which, depending on timing, includes the victim's RPC (cancelled with `RESOURCE_EXHAUSTED`) while sparing the attacker's shorter, numerous requests that collectively caused the pressure.

func (ls *LoadShedder) shed(ctx context.Context, event loadmonitor.Event) {
	entries := ls.bm.GetTopNEntries(shedTopN, SortByCPU)
	reason := SortByCPU.reason()

	for _, entry := range entries {
		ls.cancel(entry, reason)
	}

	ls.logger.WithFields(log.Fields{
		"condition":    event.ConditionName,
		"reason":       event.Description,
		"sniped_count": len(entries),
	}).WarnContext(ctx, "load shedder cancelled in-flight RPCs")
}

func (ls *LoadShedder) cancel(entry *RPCEntry, reason string) {
	err := structerr.NewResourceExhausted(
		"RPC cancelled by load shedder: %s", reason).
		WithDetail(&gitalypb.LimitError{ErrorMessage: reason})

	entry.Cancel(err)

	rpcsShedTotal.WithLabelValues(entry.ServiceName, entry.MethodName, reason).Inc()

	ls.logger.WithFields(log.Fields{
		"rpc_id":         entry.ID,
		"correlation_id": entry.CorrelationID,
		"repository":     entry.Repository,
		"reason":         reason,
		"cpu_time_ms":    entry.TotalCPUTime().Milliseconds(),
		"memory_bytes":   entry.TotalMemory(),
		"active_cmds":    entry.ActiveCommandCount(),
	}).WarnContext(entry.Context, "load shedder cancelled RPC")
}

// RegisterRPC adds an RPC entry to the burden monitor's tracking.
func (bm *BurdenMonitor) RegisterRPC(ctx context.Context, fullMethod string) (context.Context, *RPCEntry) {
	ctx, cancel := context.WithCancelCause(ctx)

	serviceName, methodName := protoregistry.SplitMethodName(fullMethod)

	var repository string
	if info := requestinfohandler.Extract(ctx); info != nil {
		repository = info.Repository.GetRelativePath()
	}

	entry := &RPCEntry{
		ID:            uuid.NewString(),
		ServiceName:   serviceName,
		MethodName:    methodName,
		StartTime:     time.Now(),
		Context:       ctx,
		Cancel:        cancel,
		CorrelationID: correlation.ExtractFromContext(ctx),
		Repository:    repository,
		Commands:      make(map[int]*CommandStats),
	}

	bm.mu.Lock()
	defer bm.mu.Unlock()

	bm.entries[entry.ID] = entry
	activeRPCsGauge.Inc()

	return contextWithRPCEntry(ctx, entry), entry
}

// EntriesSortedBy returns all tracked RPC entries sorted by the specified field.
// The returned entries are sorted in descending order (highest resource usage first).
func (bm *BurdenMonitor) entriesSortedBy(sortBy SortBy) []*RPCEntry {
	entries := bm.Entries()

	switch sortBy {
	case SortByCPU:
		sort.Slice(entries, func(i, j int) bool {
			return entries[i].TotalCPUTime() > entries[j].TotalCPUTime()
		})
	case SortByMemory:
		sort.Slice(entries, func(i, j int) bool {
			return entries[i].TotalMemory() > entries[j].TotalMemory()
		})
	case SortByDuration:
		sort.Slice(entries, func(i, j int) bool {
			return entries[i].StartTime.Before(entries[j].StartTime)
		})
	}

	return entries
}
