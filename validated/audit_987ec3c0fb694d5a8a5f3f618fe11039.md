Audit Report

## Title
`submit_delivery_receipt`/`process_delivery_receipt` pays relayer reward without checking the Ethereum-side `success` flag - ([File: bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs])

## Summary
The `DeliveryReceipt` type decoded from the Ethereum `InboundMessageDispatched` event carries an explicit `success: bool` field, but `Pallet::process_delivery_receipt` in the outbound-queue-v2 pallet never reads it. Reward eligibility is gated solely on `order.fee > 0` and the existence of a `PendingOrders` entry for the nonce, so a relayer is paid in full even when the proven event reports `success = false`.

## Finding Description
`DeliveryReceipt` is decoded in `bridges/snowbridge/primitives/outbound-queue/src/v2/delivery_receipt.rs` (lines 14-51), explicitly capturing `event.success` from the ABI-decoded `InboundMessageDispatched` log: [1](#0-0) 

`submit_delivery_receipt` verifies the proof and decodes the receipt, then forwards it to `process_delivery_receipt` without inspecting `success`: [2](#0-1) 

`process_delivery_receipt` checks only `receipt.gateway`, `receipt.reward_address`, and `receipt.nonce` — `receipt.success` is never referenced anywhere in the function body. The reward is registered purely based on `order.fee > 0`, and the `PendingOrders` entry is unconditionally removed with `Event::MessageDelivered` emitted regardless of the decoded outcome: [3](#0-2) 

The existing guard (`T::Verifier::verify` plus `GatewayAddress` check) only establishes that a genuine event was emitted by the correct contract for the correct nonce — it does not, and cannot, establish that the underlying command dispatch succeeded, since the field distinguishing that outcome (`success`) is decoded but discarded before the payout decision.

## Impact Explanation
This violates the required invariant that bridge receipts and payout state must only advance after execution succeeds — here, settlement (`PendingOrders` removal) and reward payout both proceed identically whether `success` is `true` or `false`. Because the check is a pure omission of an already-decoded field (not a proof-forgery or route-binding issue), it constitutes public underpriced/unbacked work: fee funds can be paid out for deliveries that the Ethereum side itself recorded as unsuccessful, with no distinguishing event or reduced payout path, degrading the bridge's economic assumption that reward corresponds to successful delivery.

## Likelihood Explanation
`submit_delivery_receipt` is a permissionless, publicly reachable extrinsic gated only by `ensure_signed(origin)`, requiring nothing beyond a valid Merkle/log proof for a real `InboundMessageDispatched` event — no privileged or governance relationship, and no assumption of a "malicious" relayer beyond ordinary permissionless usage of the exposed extrinsic. Any relayer whose relayed message dispatch fails on Ethereum (for reasons within or outside their control) can submit that same valid, truthful proof and still be paid, since the local logic never consults `success`.

## Recommendation
Gate reward payment on `receipt.success`. When `success == false`, withhold the reward payout (or route it through a materially reduced compensation path), still remove the `PendingOrders` entry to prevent resubmission, and emit a distinct event (e.g., `MessageDispatchFailed`) instead of unconditionally emitting `Event::MessageDelivered`.

## Proof of Concept
1. A message is submitted through `do_process_message`, creating `PendingOrders[nonce]` with `fee > 0` (`bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs` lines 426-436).
2. The corresponding Ethereum-side dispatch fails at the command level; the Gateway still emits `InboundMessageDispatched(nonce, topic, success=false, reward_address)`.
3. A relayer submits this genuine, cryptographically valid event log via `submit_delivery_receipt`; `T::Verifier::verify` succeeds and `DeliveryReceipt::try_from` decodes `success = false`.
4. `process_delivery_receipt` reaches `if order.fee > 0 { T::RewardPayment::register_reward(...) }` — this branch does not reference `receipt.success`, so the reward is registered as if the dispatch had succeeded, and `Event::MessageDelivered` is emitted (`bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs` lines 466-477).
5. A unit test asserting `receipt.success == false` still results in `RewardPayment::register_reward` being invoked confirms the missing check.

		) -> DispatchResult

		/// Process a delivery receipt from a relayer, to allocate the relayer reward.
		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}
