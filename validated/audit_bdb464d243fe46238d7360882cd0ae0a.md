## Title
Division-by-zero / underflow panic in `accrue()` treasury-LP minting when reserve accrual exceeds previewed total assets - (File: `mainnet/contracts/vault/v0-vault-stx.clar` and equivalent vault contracts)

## Summary
This is the same bug class as the FactoryDAO `SpeedBumpPriceGate.addGate()` finding: an unvalidated value can reach a divisor used later in the code, causing the transaction to trap/revert. In Zest's vaults, the `accrue()` function computes a treasury LP-minting amount by dividing by `(- (total-assets-preview) reserve-inc)`, a value that is not validated to stay non-zero/non-negative before being used as a divisor.

## Finding Description
Every vault (`v0-vault-stx.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`, `v0-vault-ststxbtc.clar`, and their `local-testing` equivalents) implements `accrue()` as follows: [1](#0-0) 

specifically the treasury-lp computation: [2](#0-1) 

`treasury-lp` is computed as `mul-div-down reserve-inc (total-supply) (- (total-assets-preview) reserve-inc)`. The divisor is `(total-assets-preview) - reserve-inc`. Neither `total-assets-preview` nor `reserve-inc` is validated to guarantee this subtraction is positive before being used as a divisor — analogous to `priceIncreaseDenominator` never being checked to be `> 0` before being used in `SpeedBumpPriceGate.passThruGate()`.

`reserve-inc` is derived from `debt-delta` (newly accrued interest since last update) scaled by `fee-reserve/BPS`: [3](#0-2) 

`accrue()` is called at the start of essentially every user-facing vault entry point (`system-borrow`, `system-repay`, deposit/redeem paths, etc.), so this code path is reached by ordinary, unprivileged principals via normal market operations, not just DAO calls: [4](#0-3) 

If `reserve-inc` ever equals or exceeds `total-assets-preview` (e.g., after a large socialized-debt write-down that reduces `assets`/`total-assets-preview` disproportionately relative to outstanding scaled debt, or after long periods of unaccrued interest combined with elevated `fee-reserve`), the subtraction underflows a `uint`, which traps in Clarity — reverting the entire transaction, including the user's own borrow/repay/deposit/withdraw action that triggered `accrue()`.

## Impact Explanation
This lands in the "temporary freezing of funds" category: because `accrue()` is invoked as a precondition in every deposit, withdraw, borrow, and repay call, a persistent underflow condition in the treasury-LP divisor would cause every subsequent vault operation to revert, freezing all user funds in that vault (deposits cannot be withdrawn, debt cannot be repaid) until the underlying state (e.g., `total-assets-preview` vs. accrued reserve) is fixed — mirroring the FactoryDAO report's "functionality interrupted until fixed" conclusion, but with a more severe result here since the vault becomes fully unusable for all callers, not just one gate.

## Likelihood Explanation
Likelihood is moderate to low under normal operation, since `fee-reserve` and typical interest accrual rates keep `reserve-inc` far below `total-assets-preview` in steady state. However, the code contains no explicit invariant/assertion guaranteeing `total-assets-preview >= reserve-inc` before the subtraction, unlike other setters in the codebase (e.g., `set-fee-flash`, `set-fee-reserve`) that do bound their inputs. The lack of an explicit guard on this specific arithmetic path — reachable purely through normal interest accrual triggered by any unprivileged caller — is exactly the same class of omission flagged in the original report: a downstream divide operation is not defensively protected against the upstream value reaching zero (or, here, underflowing).

## Recommendation
Add an explicit guard in `accrue()` before computing `treasury-lp`: assert that `(total-assets-preview) > reserve-inc` (or clamp `reserve-inc` to `(total-assets-preview) - u1`) so that the subtraction/division can never trap. This mirrors the FactoryDAO recommendation to validate the divisor at the point where it is set/derived rather than allowing it to reach the division unguarded.

## Proof of Concept
1. Observe that `treasury-lp` in `accrue()` is computed as `(mul-div-down reserve-inc (total-supply) (- (total-assets-preview) reserve-inc))` with no prior assertion that `(total-assets-preview) > reserve-inc`.
2. `accrue()` is invoked unconditionally at the top of `system-borrow`/`system-repay` and other lending entry points, so any ordinary user's call to borrow/repay/deposit/withdraw executes this arithmetic.
3. If a scenario arises (e.g., following `socialize-debt` reducing `assets`/`total-assets-preview`, combined with continued interest accrual) where `reserve-inc >= (total-assets-preview)`, the subtraction underflows and Clarity traps, reverting the calling transaction.
4. Because every subsequent user operation on the vault also calls `accrue()` first, the vault becomes unusable (funds temporarily frozen) until the state causing the underflow is remediated.

Note: I was unable to fully verify the exact numeric bounds of `total-assets-preview()` and `fee-reserve` limits within the available context (the search iteration budget was exhausted before I could pull the full definitions of `total-assets-preview`, `total-supply`, and the `set-fee-reserve` bound-check), so the precise conditions required to trigger the underflow in practice remain unconfirmed and should be verified by a full read of `mainnet/contracts/vault/v0-vault-stx.clar` (definitions of `total-assets-preview`, `total-assets`, `total-supply`, and the reserve-fee setter).
