### Title
Precompiled-Contract Calls with `msg.value` Permanently Strand TRX/TRC10 at Virtual Precompile Addresses - (File: actuator/src/main/java/org/tron/core/vm/program/Program.java)

### Summary
`Program.callToPrecompiledAddress` unconditionally transfers `msg.value` (TRX via `MUtil.transfer`, or TRC10 via `deposit.addTokenBalance`) from the caller to the precompiled contract's virtual address *before* invoking `contract.execute(data)`, regardless of whether the specific precompiled contract logic (vote, freeze, signature verification, zk-SNARK, etc.) ever reads, refunds, or otherwise accounts for that endowment. [1](#0-0) 

### Finding Description
Precompiled contract addresses (e.g. `0x1000001`–`0x1000015`, ecRecover, sha256, altBN128, etc.) are virtual — they have no private key, no user-controlled code, and none of the `PrecompiledContract` implementations in `PrecompiledContracts.java` are shown here to sweep or return an accidental TRX/TRC10 endowment sent alongside a `CALL`. Yet `Program.callToPrecompiledAddress` performs the value transfer as a side effect of any `CALL`/`CALLCODE` opcode targeting such an address whenever `endowment > 0`:

```java
if (!ArrayUtils.isEmpty(senderAddress) && !ArrayUtils.isEmpty(contextAddress)
    && senderAddress != contextAddress && msg.getEndowment().value().longValueExact() > 0) {
  if (!isTokenTransfer) {
    try {
      MUtil.transfer(deposit, senderAddress, contextAddress,
          msg.getEndowment().value().longValueExact());
    } catch (ContractValidateException e) {
      throw new BytecodeExecutionException("transfer failure");
    }
  } else {
    ...
    deposit.addTokenBalance(senderAddress, tokenId, -endowment);
    deposit.addTokenBalance(contextAddress, tokenId, endowment);
  }
}
``` [1](#0-0) 

This mirrors the SoftVault bug class exactly: an asset transfer is performed to an address whose "contract" (here, a virtual precompile) has no logic to withdraw or forward the asset back out. Once TRX or TRC10 balance is credited to a precompile address, there is no actuator, opcode path, or precompile implementation that lets anyone move it back out — `AccountCapsule` balances at these addresses become unreachable because the address is not a normal EOA (no private key controls it) and is not a deployed smart contract (no code to execute a withdrawal). Any contract that mistakenly (or via a bug/exploit in an intermediary contract) issues a value-bearing `CALL` to a precompiled address — for example a reentrant/forwarding proxy contract, or a contract using `address(precompile).call{value: x}(data)` — permanently burns that value with no recovery path, distinct from and unprotected by the `ForbidTransferToContract`/`validateForSmartContract` checks that exist for normal contract addresses in `TransferAssetActuator` and `VMUtils.validateForSmartContract`. [2](#0-1) 

By contrast, `callToAddress` (calls to normal deployed contracts) goes through `createAccountIfNotExist` + `VMUtils.validateForSmartContract`, and normal contracts at least have the opportunity to implement `receive`/`fallback`/withdraw logic; precompiled addresses categorically cannot. [3](#0-2) 

### Impact Explanation
Any TRX or TRC10 tokens transferred via `CALL` with nonzero value to a precompiled contract address become permanently and unrecoverably locked, since there is no actuator or opcode path enabling withdrawal from those addresses. This is a permanent freezing-of-funds condition, reachable by any contract caller (deployer or triggerer of a smart contract) issuing a value-bearing internal call to a precompiled address, whether intentionally or by accident/via vulnerable intermediary contracts.

### Likelihood Explanation
Reachable directly by any unprivileged account via a `TriggerSmartContract` that causes the executing contract to perform a `CALL`/`CALLCODE` with nonzero `value` to one of the well-known low-address precompile IDs (`0x1`–`0x9`, `0x100`, `0x1000001`–`0x1000015`, etc.). No special privilege, SR/witness status, or malicious node behavior is required — only a standard smart-contract call.

### Recommendation
In `Program.callToPrecompiledAddress`, reject (or explicitly refund) any nonzero `msg.value`/token endowment directed at a precompiled address unless the specific precompile is designed to consume it (and if so, that precompile must itself account for and be able to release the value, e.g., via its own withdrawal/refund mechanism). At minimum, disallow value-bearing calls to precompile addresses that have no such accounting logic, mirroring how `forbidTransferToContract`/`validateForSmartContract` protect normal contract transfers.

### Proof of Concept
1. Deploy a helper contract with a function such as:
```solidity
function sendToPrecompile(address payable target) public payable {
    target.call{value: msg.value}("");
}
```
2. Call `sendToPrecompile` with `target = 0x0000000000000000000000000000000000010001` (the vote-contract precompile address) and some TRX value, using a standard `TriggerSmartContract`.
3. `Program.callToPrecompiledAddress` executes `MUtil.transfer(deposit, senderAddress, contextAddress, endowment)`, crediting the precompile's virtual `AccountCapsule` with the TRX before `contract.execute(data)` runs. [4](#0-3) 
4. There is no actuator, TVM opcode, or `Wallet`/HTTP API that allows withdrawing balance from a precompile address (unlike a deployed contract, which could implement a withdrawal function); the TRX is permanently stranded.
