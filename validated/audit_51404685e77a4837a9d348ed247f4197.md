### Title
Unbounded array allocation from attacker-controlled length word in TVM precompiles `ValidateMultiSign`/`BatchValidateSign` causes node OOM crash - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The `extractBytesArray`, `extractSigArray`, and `extractBytes32Array` helper functions in `PrecompiledContracts.java` read a 32-byte length word directly from attacker-supplied precompile calldata and pass it unchecked into `new byte[len][]` before validating it against the amount of data actually available. This is the same bug class as CVE-2026-42189: a decoded count is used for `Vec::with_capacity`/array allocation before being bounded by the remaining input size, letting a remote, unauthenticated (here: unprivileged, fee-paying) caller trigger a multi-gigabyte allocation attempt with a single, cheap transaction.

### Finding Description
`extractBytesArray` / `extractSigArray` / `extractBytes32Array`: [1](#0-0) 

Each function does `int len = words[offset].intValueSafe();` and immediately allocates `new byte[len][]` (or `new byte[len][32]` in the bytes32 variant) with no upper bound check on `len` relative to `words.length` or `data.length`. `DataWord.intValueSafe()` returns the raw parsed int (up to `Integer.MAX_VALUE`) whenever the value fits in 4 bytes and is non-negative: [2](#0-1) 

`ValidateMultiSign.execute()` calls `extractBytesArray` on this attacker-controlled `len` with **no bound check whatsoever** whenever `VMConfig.allowTvmSelfdestructRestriction()` is false — the `sigArraySize`/`MAX_SIZE` guard only executes when that chain parameter is enabled, and the resulting call is entirely outside any `try/catch`: [3](#0-2) 

`BatchValidateSign.doExecute()` has the analogous unconditional call to `extractBytes32Array` for building the `addresses` array, and calls `extractBytesArray` for `signatures` whenever the same restriction flag is disabled: [4](#0-3) 

This precisely mirrors the russh flaw: a length field decoded straight from untrusted input is used to size an allocation (`Vec::with_capacity(n)` ↔ `new byte[len][]`) before it is validated against the amount of data actually present, so a single crafted call can request an allocation far larger than the input could legitimately encode.

### Impact Explanation
Any account can invoke the `ValidateMultiSign`/`BatchValidateSign` precompiled contracts (via `TriggerSmartContract` or a `CALL` from any contract) with crafted calldata that sets the relevant length word to a large positive 4-byte value (up to `0x7FFFFFFF`). The node attempts to allocate an array of that many object references (`new byte[len][]`), which for `len` near `Integer.MAX_VALUE` requires several gigabytes just for the reference array, independent of whether the underlying data actually contains that many entries. In `ValidateMultiSign` this allocation happens outside any exception handler in `execute()`, so a resulting `OutOfMemoryError` propagates up through TVM execution — this is a node-crash / halt vector (CWE-770/CWE-789), reachable pre-permission-check by any fee-paying caller. This satisfies the "node crash or halt" bar for a High severity finding.

### Likelihood Explanation
This path is reachable purely on the condition that `VMConfig.allowTvmSelfdestructRestriction()` is disabled — i.e., on any java-tron network (private chain, testnet, or a mainnet-like chain) where the corresponding committee proposal has not yet been activated (the default/pre-activation state for a chain parameter). No special privileges, staking, or prior transactions are required; a single `TriggerSmartContract` transaction targeting the precompile address with crafted calldata is sufficient, and the caller does not even need the signatures to validate — only the length words need to be crafted.

### Recommendation
Bound `len` in `extractBytesArray`, `extractSigArray`, and `extractBytes32Array` by the number of remaining `words` (or bytes of `data`) before allocating, e.g. `len = Math.min(len, words.length - offset - 1)`, and reject if the computed length is inconsistent with the actual calldata size — mirroring the `MAX_SIZE`/ABI-encoding checks already applied under the `allowTvmSelfdestructRestriction`/Osaka guards, but unconditionally rather than only when those (optional, governance-gated) hardfork flags are active. Additionally, wrap the extraction calls in `ValidateMultiSign.execute()` with the same defensive `try/catch(Throwable)` pattern already used in `BatchValidateSign.execute()`.

### Proof of Concept
1. Craft calldata for `validateMultiSign(address,uint256,bytes32,bytes[])` (or `batchValidateSign`) where the ABI offset word for the `bytes[]`/`address[]` array points to a length word set to `0x000000000000000000000000000000000000000000000000000000007FFFFFFF` (a large but 4-byte-representable positive value).
2. On a node/chain where `ALLOW_TVM_SELFDESTRUCT_RESTRICTION` has not been activated, send a `TriggerSmartContract` transaction whose calldata is delivered to the `ValidateMultiSign` precompiled contract address with this crafted payload.
3. `DataWord.intValueSafe()` returns `0x7FFFFFFF` for `len`; `extractBytesArray` immediately executes `new byte[0x7FFFFFFF][]`, attempting to allocate ~8-16GB of reference-array memory on the node processing the transaction, which is not guarded by any try/catch in `ValidateMultiSign.execute()`, producing an uncaught `OutOfMemoryError` during transaction execution.

  private static byte[][] extractBytes32Array(DataWord[] words, int offset) {
    int len = words[offset].intValueSafe();
    byte[][] bytes32Array = new byte[len][];
    for (int i = 0; i < len; i++) {
      bytes32Array[i] = words[offset + i + 1].getData();
    }
    return bytes32Array;
  }

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }

  private static byte[][] extractSigArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          SIG_LENGTH);
    }
    return bytesArray;
  }
