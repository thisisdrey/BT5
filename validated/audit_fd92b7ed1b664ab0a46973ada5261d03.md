### Title
Boundary off-by-one locks claimed MET into esMET for an extra minimum lock period at the exact unlock timestamp - (File: contracts/MetAirdrop.sol)

### Summary
The external report describes an off-by-one on a time-window boundary (`<` where `<=` is intended), which wrongly treats the final valid timestamp as outside the window. Metronome has the same boundary pattern in `MetAirdrop._transferReward` at contracts/MetAirdrop.sol:32-37 [1](#0-0) . When a user calls `RecurringAirdrop.claim` at exactly `block.timestamp == updatedAt + lockPeriod` (the moment the lock period ends), the check `_end < block.timestamp` is false, so instead of receiving freely transferable MET the user's reward is pushed into `ESMET.lockFor`.

### Finding Description
`claim` in `RecurringAirdrop` verifies a Merkle proof and calls the overridden `_transferReward` [2](#0-1) . In `MetAirdrop._transferReward`, `_end = updatedAt + lockPeriod`; the free-transfer branch requires `_end < block.timestamp` [1](#0-0) . At the exact boundary timestamp, `_end - block.timestamp` is `0`, which is then clamped by `Math.max(..., _min)` to `ESMET.MINIMUM_LOCK_PERIOD() + 1` [3](#0-2) . The user is therefore locked for the minimum esMET lock period despite the configured `lockPeriod` having fully elapsed — the same "boundary instant excluded from the intended regime" defect class as the HardVault `<`/`<=` report.

### Impact Explanation
A user claiming at `block.timestamp == updatedAt + lockPeriod` has their MET locked into an esMET position for `MINIMUM_LOCK_PERIOD + 1` seconds instead of receiving liquid MET. This is a temporary freezing of user funds caused by the strict-inequality boundary. The impact is bounded (the extra lock is only the esMET minimum lock duration, and only for claims landing exactly on the boundary second), so severity is low.

### Likelihood Explanation
Any unprivileged user can trigger it simply by calling `claim` at the boundary timestamp; no privileged role, oracle manipulation, or special configuration is required. However, hitting the exact second is unlikely on its own and requires deliberate timing (e.g., broadcasting in the block whose timestamp equals `_end`), which is trivially achievable by a miner/attacker-controlled timing or just a user who claims the moment the UI says the lock has ended.

### Recommendation
Decide the intended inclusivity of the boundary. If `lockPeriod` should be fully elapsed at `updatedAt + lockPeriod`, change the condition to `_end <= block.timestamp` so the boundary claim transfers liquid MET. Alternatively, document that the lock is exclusive of the end timestamp. The same fix class applies: use `<=` instead of `<` at contracts/MetAirdrop.sol:34.

At `block.timestamp == updatedAt + lockPeriod`, the current code routes through the `ESMET.lockFor` path with `_remainLockPeriod = MINIMUM_LOCK_PERIOD + 1` instead of the `safeTransfer` path [4](#0-3) , demonstrating the same off-by-one window-boundary defect.

Note on uncertainty: whether `_end` is intended to be inclusive is a spec question (the NatSpec says the lock "starts from" `updatedAt` but does not define inclusivity). If the intended semantics are exclusive, this is not a bug. No other production code in the repo uses a timestamp-window comparison that gates a withdraw/claim path, so this is the only reachable surface for this bug class.

    function claim(uint256 amount_, bytes32[] calldata proof_) external nonReentrant {
        if (merkleRoot == bytes32(0)) revert NothingToClaim();

        bytes32 _leaf = keccak256(abi.encodePacked(msg.sender, amount_));
        if (!MerkleProof.verify(proof_, merkleRoot, _leaf)) revert InvalidProof();

        uint256 _claimable = amount_ - claimed[msg.sender];
        if (_claimable == 0) revert NothingToClaim();

        claimed[msg.sender] += _claimable;

        _transferReward(msg.sender, _claimable);
