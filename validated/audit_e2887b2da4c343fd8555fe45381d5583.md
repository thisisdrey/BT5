### Title
Single failing/stale per-asset price resolution reverts entire `price-multi-resolve`, causing DoS on `repay`/`collateral-remove` (risk-reducing actions) - ([File: mainnet/contracts/market/v0-4-market.clar])

### Summary
`price-multi-resolve` aggregates prices for every asset (collateral + debt) held by a position via a `fold`. If the resolution of **any single** asset in that list fails (stale price, low confidence, or an external oracle call reverting), the whole fold is marked invalid and the entire function aborts with `ERR-ORACLE-MULTI`. Since this helper backs the health-check path used by essentially all position-mutating entry points, one bad/stale oracle for one of the user's holdings blocks every operation on that position — including debt repayment and collateral withdrawal, i.e., the very actions a user needs to de-risk. This is the same underlying bug class as the referenced report: optimistic dependence on the success of a batch of external-facing checks/calls, where a single failure aborts the whole transaction.

### Finding Description
`price-multi-resolve` folds `iter-price-multi` over the oracle-config list for a position's enabled assets: [1](#0-0) 

Each iteration calls `price-resolve`, which enforces both a positivity check and a staleness/monotonicity check (`oracle-price-legal`, `oracle-timestamp-fresh`) and can also fail via `try!` through `resolve-price-feed` (external `pyth-storage-v4`/`dia-oracle` calls) or `resolve-callcode` (e.g., `resolve-ststx` calling an external ratio provider): [2](#0-1) 

`get-assets` builds the asset list for a specific account from its held collateral+debt bitmap (`user-safe-mask`) and always resolves prices for **all** of them together via a single `price-multi-resolve` call: [3](#0-2) 

Because `iter-price-multi` short-circuits on the first failure but the outer `price-multi-resolve` only checks `valid` after the fold and then `asserts!`s on it, a single failing entry anywhere in the list aborts price resolution for the *entire* position, not just for the problematic asset: [4](#0-3) 

Users can partially mitigate staleness for Pyth-sourced feeds by supplying up to 3 fresh price-feed buffers via `write-feeds`/`write-feed`, but this is capped at 3 feeds per call and only applies to Pyth-type assets: [5](#0-4) 
Assets whose oracle `type` is DIA, or whose price fails due to a hard external-call revert (`ERR-ORACLE-PYTH`/`ERR-ORACLE-DIA`) or confidence check, or whose held-asset count exceeds the 3-feed refresh limit, have no user-controlled remediation.

### Impact Explanation
Any function that needs the account's notional collateral/debt (health checks for borrow, collateral-add/remove, repay, liquidation math) routes through `get-assets`/`price-multi-resolve` for the full set of assets the account holds — not just the asset being acted on. If one held asset's oracle is stale beyond its configured `max-staleness`, has confidence above `max-confidence-ratio`, or its upstream oracle contract call reverts, the position becomes globally stuck: the borrower cannot `repay` debt or `collateral-remove` (withdraw) even though those are risk-reducing operations that logically shouldn't require pricing of unrelated assets, or even of the specific asset being withdrawn/repaid at all in a strict sense. This is a temporary freezing of the user's funds/position for as long as the problematic feed stays broken/stale, matching the in-scope "temporary freezing of funds" impact class.

### Likelihood Explanation
Likelihood is non-trivial: any account holding multiple collateral/debt assets is exposed to the single worst-behaving oracle among all of them. Oracle staleness/outages, `pyth-storage-v4` or `dia-oracle` external call failures, and confidence-ratio breaches are realistic external conditions outside the market contract's control, and DIA-sourced assets have no user-side refresh path at all (unlike Pyth assets, which can partially self-heal via `write-feeds`, subject to the 3-feed cap).

### Recommendation
Decouple health-check/notional pricing so that risk-reducing operations (`repay`, `collateral-remove` when resulting position is safer) do not require successful price resolution of assets unrelated to the specific action, or at minimum do not require re-resolving assets whose price is not needed to prove the action is risk-reducing. Alternatively, allow `price-multi-resolve`/`iter-price-multi` to return partial results (skip/flag the failed asset) instead of aborting the whole fold via `asserts! valid`, and let callers decide whether the missing price actually blocks their specific safety determination.

### Proof of Concept
1. Account A holds collateral in assets X and Y, and debt in asset Y.
2. Asset X's oracle feed goes stale beyond its `max-staleness` (or the underlying Pyth/DIA contract call starts reverting, or confidence spikes above `max-confidence-ratio`).
3. Account A calls `repay` (or `collateral-remove` on asset Y) to reduce risk.
4. The health-check path calls `get-assets`, which calls `price-multi-resolve` over the full safe-mask including asset X. [3](#0-2) 
5. `iter-price-multi` fails resolving asset X's price and marks `valid: false`; `price-multi-resolve` then hits `(asserts! (get valid response) ERR-ORACLE-MULTI)` and the entire `repay`/`collateral-remove` transaction reverts. [6](#0-5) 
6. Account A cannot repay debt or withdraw collateral on asset Y until asset X's oracle recovers, even though the action does not need asset X's price to be judged safe.

(define-private (price-resolve
  (data { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint }))
  (let ((type (get type data))
        (ident (get ident data))
        (key { type: type, ident: ident })
        (resolution (try! (resolve-price-feed type ident)))
        (price (get value resolution))
        (callcode (get callcode data))
        (final-price (try! (resolve-callcode price callcode)))
        (last-update-time (oracle-last-update key))
        (timestamp (get timestamp resolution))
        (max-staleness (get max-staleness data)))

    ;; validate price and timestamp using max-staleness from oracle data
    (asserts! (and (oracle-price-legal final-price) (oracle-timestamp-fresh timestamp last-update-time max-staleness))
              ERR-ORACLE-INVARIANT)

    ;; update timestamp if newer
    (if (> timestamp last-update-time)
        (map-set last-update key timestamp)
        false)

    (ok final-price)))

(define-private (price-multi-resolve
  (data (list 64 { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint }))
  (aids (list 64 uint)))
  (let ((init { output: (list), valid: true, aids: aids, idx: u0 })
        (response (fold iter-price-multi data init)))
    (asserts! (get valid response) ERR-ORACLE-MULTI)
    (ok (get output response))))

(define-private (iter-price-multi
  (oracle-data { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint })
  (acc { output: (list 64 uint), valid: bool, aids: (list 64 uint), idx: uint }))
  (let ((valid (get valid acc))
        (skip? (asserts! valid acc))
        (asset-ids (get aids acc))
        (idx (get idx acc))
        ;; resolve price - will use cache for ztokens
        (price (unwrap! (price-resolve oracle-data) (merge acc { valid: false })))
        (next (unwrap-panic (as-max-len? (append (get output acc) price) u64))))
    { output: next,
      valid: true,
      aids: asset-ids,
      idx: (+ idx u1) }))

(define-private (user-safe-mask (mask-user uint) (mask-enabled uint))
  (let ((enabled-collateral (bit-and mask-enabled MAX-U64))
        (user-collateral (bit-and mask-user MAX-U64))
        (user-debt (/ (bit-and mask-user DEBT-MASK) (pow u2 DEBT-OFFSET)))
        (collateral-match (bit-and user-collateral enabled-collateral)))
    (bit-or collateral-match user-debt)))
