### Title
Non-atomic check-then-decrypt-then-update in `ConnectionState.Decrypt` allows a duplicated/replayed ciphertext to bypass anti-replay protection - (File: `connection_state.go`)

### Summary
### Finding Description
`ConnectionState.Decrypt` implements Nebula's anti-replay protection using a three-step sequence that separates the "check" from the "effect" with an expensive interaction (AEAD decryption) in between, and only the check and the effect are individually mutex-protected, not the whole operation: [1](#0-0) 

The sequence is:
1. Lock `decryptLock`, call `cs.window.Check(l, messageCounter)` to test whether the counter has already been seen, unlock.
2. Call `cs.dKey.DecryptDanger(...)` — the AEAD decrypt — **without holding the lock**.
3. Lock `decryptLock` again, call `cs.window.Update(l, messageCounter)` to actually mark the counter as seen, unlock.

This is structurally the same class of bug as the reported ERC20 issue: a state check is performed, an "interaction" (here, the costly decrypt operation) is performed, and only afterward is the state mutated to reflect that the operation happened — instead of checking and marking the counter as consumed atomically before the interaction. `outside.go`'s `listenOut` is invoked once per UDP reader/socket (`listenOut(i int)`), and each reader independently calls `f.readOutsidePackets` → `hostinfo.ConnectionState.Decrypt` concurrently for packets belonging to the same `ConnectionState`: [2](#0-1) [3](#0-2) 

Because `Check` and `Update` are two separate critical sections rather than one atomic check-and-mark, two goroutines racing on the exact same captured/duplicated ciphertext (same `messageCounter`) can both pass `Check` before either has called `Update`. Both then proceed to decrypt and process the packet: one increments/records the message counter in `f.connectionManager.In(hostinfo)`, and both are handed to `handleOutsideMessagePacket`/`lhf.HandleRequest`, which can write the same payload to the tun device or firewall path twice.

### Impact Explanation
This defeats the purpose of the replay window: an attacker who is on-path and can capture and re-inject a single legitimate ciphertext packet (a classic replay, requiring no valid certificate or CA trust — this is exactly the "packet/nonce/replay handling" class called out as in-scope) can, by sending two copies of the packet in quick succession so they land on different reader goroutines, cause the same authenticated plaintext to be delivered/processed twice instead of the second copy being dropped as "already seen." Depending on payload this can duplicate tun-delivered traffic, double-invoke lighthouse/control message handling, or duplicate firewall conntrack state changes — a remote state-poisoning/replay impact reachable by an attacker without any valid certificate.

### Likelihood Explanation
Exploitability requires only capturing one legitimate ciphertext (observable to any network-path attacker who can also inject UDP packets to the target) and firing two near-simultaneous copies of it — no cryptographic material or certificate is needed since replay does not require forging anything, only duplicating an already-valid packet. The race window is the time between the `Check` unlock and the subsequent `Update` lock, which spans an entire AEAD decrypt; multiple UDP reader goroutines (`listenOut(i)`) make it plausible for two racing packets to interleave in that window. This is a genuine, if narrow, TOCTOU race rather than a deterministic bypass, so likelihood is moderate rather than certain.

### Recommendation
Collapse the check-and-mark into a single atomic operation performed under one critical section before decryption is attempted, e.g. have a single locked call that checks the window and immediately reserves/marks the counter (returning failure if already reserved or out of window), and only roll back the reservation if decryption subsequently fails. This mirrors the checks-effects-interactions fix recommended in the original report: perform the state-mutating "effect" (marking the counter consumed) before the "interaction" (the decrypt), not after, so a racing duplicate cannot slip through between check and mark.

### Proof of Concept
1. Establish a tunnel between two Nebula nodes so a `ConnectionState` with an active replay window exists.
2. Capture one legitimate encrypted `header.Message` packet destined for a node configured with multiple UDP listeners/readers (`listen.routines > 1`, driving multiple `listenOut(i)` goroutines as shown in `interface.go`).
3. Re-inject two copies of the exact same captured packet at the same time.
4. Observe both `Decrypt` calls pass `cs.window.Check` before either completes `cs.window.Update` (verified structurally by the code path in `connection_state.go:61-82`), causing the payload to be processed twice (e.g., duplicate tun writes/firewall conntrack updates) rather than the second copy being rejected with `ErrAlreadySeen`.

Note: I was not able to run a live concurrency test against the actual binary to empirically confirm the race triggers under realistic network timing (this would require running the full Nebula binary/tests, which is outside available tooling); the finding is based on static analysis of the check/decrypt/update ordering and the confirmed presence of multiple concurrent UDP reader goroutines feeding the same code path.

func (cs *ConnectionState) Decrypt(l *slog.Logger, messageCounter uint64, out []byte, packet []byte, nb []byte) ([]byte, error) {
	var err error
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}

	out, err = cs.dKey.DecryptDanger(out, packet[:header.Len], packet[header.Len:], messageCounter, nb)
	if err != nil {
		return nil, err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}
	return out, nil
}
