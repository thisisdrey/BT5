Audit Report

## Title
Inbound Queue V2 `add_tip` Accepts Tips For Any Unverified Nonce, Permanently Locking Burned Bridge Funds - (File: bridges/snowbridge/pallets/inbound-queue-v2/src/lib.rs)

## Summary
`Pallet::<T>::add_tip` in `snowbridge-pallet-inbound-queue-v2` accepts a tip for any `nonce` as long as `NonceBitmap` has not marked it consumed, with no check that a message with that nonce is a real, currently pending/deliverable message from Ethereum. This diverges from the sibling `outbound-queue-v2::add_tip`, which validates against an actual `PendingOrders` entry, and results in tips (backed by real burned/teleported Ether) being permanently and unrecoverably locked in storage if the targeted nonce is never delivered.

## Finding Description
The inbound queue's `add_tip` is: [1](#0-0) 

Its only guard is `!Nonce::<T>::get(nonce)`, i.e., the nonce bit is unset in `NonceBitmap`. This is true for every unprocessed nonce, including arbitrary or unreachable ones, because the bitmap only tracks "already processed" vs "not yet processed" — it has no concept of "will ever be delivered." [2](#0-1) 

By contrast, `outbound-queue-v2::add_tip` requires the nonce to correspond to a currently pending order and explicitly returns `AddTipError::UnknownMessage` otherwise: [3](#0-2) 

The tip is only ever released when a message with the matching `nonce` is actually decoded and dispatched via `process_message`: [4](#0-3) 

There is no code path to reclaim a tip in `Tips::<T>` if the targeted nonce is never delivered. The public entry point is `snowbridge-pallet-system-v2::Pallet::add_tip`, gated only by `T::FrontendOrigin` (satisfied by an ordinary signed AssetHub user via XCM): [5](#0-4) 

Because `add_tip` unconditionally returns `Ok(())` for any unconsumed nonce instead of an error, the `system-v2::add_tip` handler treats it as fully successful and does not record the amount into `LostTips`, so there is no visibility or accounting of the loss either. Meanwhile the tip asset is already swapped to Ether and burned for teleportation on AssetHub before this call executes, per `system-frontend::swap_and_burn`. The confirmed absence of any nonce-range or pending-message validation in the inbound pallet (no `InboundNonce`/expected-nonce tracking mechanism exists in this pallet) demonstrates the guard is insufficient to prevent tipping an unreachable/incorrect nonce.

## Impact Explanation
This matches the "permanent user-fund or bridge-state lock" impact category: real, already-burned/teleported Ether value (recorded in `Tips::<T>` keyed by an arbitrary nonce) can become permanently unclaimable if that nonce is never reached by a genuine inbound message, with no refund or `LostTips` tracking, and no dispatchable path to reclaim it.

## Likelihood Explanation
High. The flaw is triggered by ordinary user error (mistakenly targeting a wrong or future nonce) or intentional misuse, requires no privileged actor, relayer collusion, or race condition, and is reachable purely through the standard public `SnowbridgeSystemFrontend::add_tip` XCM flow from AssetHub, which is exercised by the repository's own integration test `add_tip_from_asset_hub_user_origin`.

## Recommendation
Align `snowbridge-pallet-inbound-queue-v2::add_tip` with the outbound-queue-v2 pattern: validate the nonce against a real, currently-known pending/expected inbound message context before accepting a tip, and return `AddTipError::UnknownMessage` for any nonce that cannot be validated, so that `system-v2::add_tip` correctly records the amount into `LostTips` and/or the transfer can be prevented/reverted upstream.

## Proof of Concept
1. On AssetHub, an unprivileged user calls `SnowbridgeSystemFrontend::add_tip` with `MessageId::Inbound(nonce)` where `nonce` is chosen far beyond (or otherwise divergent from) any nonce the Ethereum Gateway will ever emit.
2. `system-frontend::swap_and_burn` swaps the tip asset to Ether and burns it for teleportation to BridgeHub.
3. On BridgeHub, `EthereumSystemV2::add_tip` forwards to `InboundQueue::add_tip(nonce, amount)`.
4. Since `Nonce::<T>::get(nonce)` is `false` for this arbitrary nonce, `add_tip` returns `Ok(())` and stores `amount` in `Tips::<T>[nonce]`.
5. No message with this `nonce` is ever relayed from Ethereum, so `Tips::<T>::take(nonce)` in `process_message` is never invoked; the tip amount remains permanently locked and unclaimable, confirmed by the divergence from the `UnknownMessage`-checked behavior in `outbound-queue-v2::add_tip`.

	impl<T: Config> Pallet<T> {
		pub fn process_message(relayer: T::AccountId, message: Message) -> DispatchResult {
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == message.gateway, Error::<T>::InvalidGateway);

			let (nonce, relayer_fee) = (message.nonce, message.relayer_fee);

			// Verify the message has not been processed
			ensure!(!Nonce::<T>::get(nonce), Error::<T>::InvalidNonce);

			// Mark message as received
			Nonce::<T>::set(nonce);

			let message_id = T::MessageProcessor::process_message(relayer.clone(), message)
				.map_err(|e| match e {
					MessageProcessorError::ProcessMessage(e) => e,
					MessageProcessorError::ConvertMessage(e) => Error::<T>::from(e).into(),
					MessageProcessorError::SendMessage(e) => Error::<T>::from(e).into(),
				})?;

			// Pay relayer reward
			let tip = Tips::<T>::take(nonce).unwrap_or_default();
			let total_tip = relayer_fee.saturating_add(tip);
			if total_tip > 0 {
				T::RewardPayment::register_reward(&relayer, T::DefaultRewardKind::get(), total_tip);
			}

			// Emit event with the message_id
			Self::deposit_event(Event::MessageReceived { nonce, message_id });

			Ok(())
		}

		fn add_tip(nonce: u64, amount: u128) -> Result<(), AddTipError> {
			ensure!(amount > 0, AddTipError::AmountZero);
			// If the nonce is already processed, return an error
			ensure!(!Nonce::<T>::get(nonce.into()), AddTipError::NonceConsumed);
			// Otherwise add the tip.

	impl<T: Config> AddTip for Pallet<T> {
		fn add_tip(nonce: u64, amount: u128) -> Result<(), AddTipError> {
			ensure!(amount > 0, AddTipError::AmountZero);
			PendingOrders::<T>::try_mutate_exists(nonce, |maybe_order| -> Result<(), AddTipError> {
				match maybe_order {
					Some(order) => {
						order.fee = order.fee.saturating_add(amount);
						Ok(())
					},
					None => Err(AddTipError::UnknownMessage),
				}
			})
		}
	}
