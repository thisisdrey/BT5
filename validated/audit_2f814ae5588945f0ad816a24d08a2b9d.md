### Title
Griefing via `MAX_TOKENS_PER_USER` dust deposits DoS withdrawals and liquidations that pay the `feeCollector` — (File: contracts/Pool.sol)

### Summary
Every `DepositToken` balance change from zero calls `Pool.addToDepositTokensOfAccount(account)`, which reverts with `UserReachedMaxTokens` once the account's combined deposit+debt token count reaches `MAX_TOKENS_PER_USER = 30`. The check is enforced on the *recipient*, and `DepositToken.deposit(amount_, onBehalfOf_)`/`transfer` let any unprivileged attacker add entries to an arbitrary account's list. By dust-filling the `feeCollector`'s list, the attacker permanently reverts every `withdraw` charging `withdrawFee` and every `liquidate` charging `protocolLiquidationFee`, since both paths `seize`/`_transfer` deposit tokens *to* `feeCollector` — an address that cannot clear slots without governor `sweep`.

### Finding Description
- `Pool.addToDepositTokensOfAccount` / `addToDebtTokensOfAccount` revert once `debtTokensOfAccount.length + depositTokensOfAccount.length >= MAX_TOKENS_PER_USER` (30) for the *account being added to*, not the sender [1](#0-0) [2](#0-1) 
- `DepositToken._transfer` adds the token to `recipient_`'s list whenever `balanceOf[recipient_] == 0 && amount_ > 0` [3](#0-2) 
- `DepositToken.seize` (called by `Pool.liquidate`) is the same `_transfer`, so `depositToken_.seize(account_, feeCollector, _fee)` reverts if `feeCollector`'s list is full and it doesn't already hold that token [4](#0-3) [5](#0-4) 
- `DepositToken._withdraw` routes the withdrawal fee through `_transfer(account_, feeCollector, _fee)`, so it reverts identically — and the whole withdraw (user exit) rolls back [6](#0-5) 
- The attacker seeds the slots cheaply: `deposit(1 wei, feeCollector)` or `transfer(feeCollector, 1 wei)` per registered deposit token. `feeCollector` is a fixed protocol address; its entries can only be removed if its balance hits zero, which requires a `transfer`/`sweep` the contract has no unprivileged path to perform (`_requireCanSweep` is `onlyGovernor`) [7](#0-6) 

### Impact Explanation
Liveness break on core flows:
- `Pool.liquidate` reverts on any liquidation where `protocolLiquidationFee > 0` and `feeCollector` lacks that deposit token — unhealthy positions cannot be liquidated, enabling bad-debt accrual / protocol insolvency.
- `DepositToken.withdraw` reverts whenever `withdrawFee > 0` for tokens not already in `feeCollector`'s list — user collateral is frozen until governance sweeps `feeCollector` (temporary freezing of funds requiring privileged recovery).

### Likelihood Explanation
Attack cost is dust collateral plus gas for at most 30 calls; the attacker only needs unprivileged `deposit`/`transfer`. Pre-conditions that bound likelihood:
- The pool must list enough distinct deposit tokens (combined with any debt tokens already on `feeCollector`'s list) to reach 30 entries. If a deployment has few collateral types, the cap is unreachable — this must be checked per deployment.
- `withdrawFee`/`protocolLiquidationFee` must be > 0 in `FeeProvider` for the DoS to trigger (fee==0 paths skip the transfer).
- A victim-user variant (filling a target account's list to block their deposits/liquidation-receives) also works but is weaker: the victim can transfer dust entries out to free slots, so it is only a temporary per-account grief. The `feeCollector` variant is the impactful one because that account cannot self-recover.

### Recommendation
Do not couple recipient-side accounting to a global cap: in `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount`, skip (rather than revert) when the account is at the cap, or exempt `feeCollector`/`seize` paths; alternatively cap only entries that contribute to `debtPositionOf` iteration cost, or allow `feeCollector` a dedicated fee balance outside `MappedEnumerableSet`. At minimum, let `feeCollector` freely transfer/sweep deposit tokens.

### Proof of Concept
Hardhat (pool unit-test style):

```ts
it('fills feeCollector list and DoSes withdraw and liquidate', async function () {
  const feeCollector = await poolRegistryMock.feeCollector()

  // 1. Attacker dusts feeCollector with every deposit token it doesn't already hold
  for (const dt of depositTokens) {                       // up to MAX_TOKENS_PER_USER slots
    await underlying.approve(dt.address, 1)
    await dt.deposit(1, feeCollector)                     // adds dt to feeCollector's list
  }
  const len = (await pool.getDepositTokensOfAccount(feeCollector)).length
            + (await pool.getDebtTokensOfAccount(feeCollector)).length
  expect(len).to.eq(await pool.MAX_TOKENS_PER_USER())

  // 2. Any withdraw paying a fee in a token feeCollector hasn't held reverts
  await expect(newDepositToken.connect(alice).withdraw(amount))
    .revertedWithCustomError(pool, 'UserReachedMaxTokens')

  // 3. Any liquidation with protocolLiquidationFee > 0 reverts at the fee seize
  await expect(pool.connect(bob).liquidate(msEth.address, alice.address, amount, newDepositToken.address))
    .revertedWithCustomError(pool, 'UserReachedMaxTokens')
})
```

Uncertainty: I did not verify the deployed per-chain token counts or current `withdrawFee`/`protocolLiquidationFee` values; the attack requires enough listed tokens to reach the 30-entry cap and non-zero fees.
