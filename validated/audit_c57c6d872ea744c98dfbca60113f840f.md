### Title
Dust-transfer griefing permanently fills a victim's per-account collateral list, blocking all deposits of new collateral types - (File: contracts/DepositToken.sol)

### Summary
The AMF advisory is a remotely triggered denial of service: a crafted message breaks a core component's liveness. The reachable Metronome analog is the per-account `depositTokensOfAccount` list in `Pool`, capped by `MAX_TOKENS_PER_USER`. Any ERC-20-style `transfer` of a `DepositToken` (msdTOKEN) to a first-time holder appends that token to the recipient's list via `pool.addToDepositTokensOfAccount(recipient_)` in `DepositToken._transfer` (contracts/DepositToken.sol:517-520). An unprivileged attacker can deposit dust amounts of every registered collateral, then transfer 1 wei of each distinct `DepositToken` to a victim until `addToDepositTokensOfAccount` reverts with `UserReachedMaxTokens` (contracts/Pool.sol, `addToDepositTokensOfAccount`). From then on, any action that would add a *new* deposit token to the victim's list reverts.

### Finding Description
- `DepositToken._transfer` unconditionally calls `pool.addToDepositTokensOfAccount(recipient_)` whenever the recipient's prior balance of that token is zero. The same hook runs on `_mint` (contracts/DepositToken.sol:485-488), so `deposit`, `DepositToken.seize` in liquidations, and `SmartFarmingManager` leverage deposits all go through the same capped `MappedEnumerableSet` add.
- `Pool.addToDepositTokensOfAccount` enforces a combined cap (`MAX_TOKENS_PER_USER` across deposit + debt tokens) and reverts with `UserReachedMaxTokens` once full (test/Pool.test.ts:1386-1416 demonstrates the cap behavior).
- `DepositToken.transfer` only checks `_revertIfLocked(_msgSender, amount_)` on the sender; there is no check that the recipient opted in, no minimum amount, and no way for a recipient to refuse entries.
- Attack path: attacker calls `DepositToken.deposit` (or deposits then `transfer`s dust) for each registered collateral, then calls `transfer(victim, 1)` on each `DepositToken`. Each dust transfer permanently occupies a slot in `depositTokensOfAccount[victim]` until the victim's balance of that token returns to zero.
- Consequence: once the list is full, the victim's `deposit`/`leverage`/receipt of *any* deposit token they don't already hold reverts in `_mint` → `addToDepositTokensOfAccount`. If the victim has open debt, their seized/liquidation routing and `withdraw`-adjacent flows on new tokens are also impaired; critically, `liquidate`/`seize` transfers to a liquidator whose list is full also revert, degrading liquidation liveness for positions whose collateral token isn't in the liquidator's set.

### Impact Explanation
Temporary freezing of funds / degraded liveness: the victim cannot deposit, leverage, or receive new collateral token types, and liquidators cannot seize a token into an account whose list is saturated (seize uses `_transfer`, which hits the same add). Victims with existing debt may be unable to add the collateral needed to restore health, pushing them into liquidation. Recovery requires zeroing out a dusted balance, which is blocked if the token's balance is locked by debt (`_revertIfLocked` / `unlockedBalanceOf`), so the freeze can persist as long as the account is collateralized.

### Likelihood Explanation
Fully unprivileged and cheap: the attacker needs only dust deposits of existing collateral types (recovered afterwards by withdrawing their own balance, minus small fees) plus gas for N transfers. No privileged role, oracle manipulation, or malicious LayerZero component is required; the only prerequisite is that the pool has multiple registered `DepositToken`s, which is the deployed configuration.

### Recommendation
Do not mutate the per-account collateral set inside plain ERC-20 `transfer`/`transferFrom`. Track an account's collateral set only on protocol-relevant flows (`deposit`, `seize`, leverage mints) or treat zero/dust balances as absent (e.g., add only when the post-transfer balance exceeds a dust threshold, or maintain the set lazily during `debtPositionOf` iteration over registered tokens instead of a per-account list).

### Proof of Concept
Hardhat sketch (fork or local deployment):

```ts
// victim starts with no deposit tokens
for (const dt of allDepositTokens) {
  // attacker deposits dust of dt.underlying
  await underlying.connect(attacker).approve(dt.address, 1);
  await dt.connect(attacker).deposit(1);           // mints 1 wei msdTOKEN to attacker
  await dt.connect(attacker).transfer(victim.address, 1); // adds dt to victim's list
}
// repeat across enough tokens until:
await expect(
  newDepositToken.connect(victim).deposit(parseEther('1'))
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');
// also: liquidator with full list cannot seize
await expect(
  pool.connect(liquidator).liquidate(.../* collateral = newDepositToken */...)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');
```

The revert originates in `DepositToken._mint` → `Pool.addToDepositTokensOfAccount` once `depositTokensOfAccount[victim]` reaches `MAX_TOKENS_PER_USER`.
