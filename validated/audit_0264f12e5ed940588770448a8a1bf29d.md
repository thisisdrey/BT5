### Title
Strict equality check on CPI-returned Drift withdraw amount can revert legitimate liquidations, blocking bad-debt cleanup - (File: `programs/marginfi/src/instructions/drift/withdraw.rs`)

### Summary
`drift_withdraw` pre-computes an expected token amount and expected scaled-balance decrement *before* calling into the Drift program via CPI, then asserts strict equality against the values actually observed after the CPI returns. This mirrors the Superposition `swap_2_internal` bug class: an intermediate/expected value computed locally is required to exactly equal the value produced by an external call, with no tolerance for legitimate deviation (e.g., reduce-only clamping, rounding, or state drift between computation and CPI execution).

### Finding Description
In `drift_withdraw`, the non-`withdraw_all` path computes `token_amount` and `expected_scaled_balance_change` from the user's requested `amount` via `integration_acc_1.get_scaled_balance_decrement`/`get_withdraw_token_amount` [1](#0-0) . After the CPI to Drift's `withdraw` (called with `reduce_only = true`, i.e. Drift is permitted to internally cap the withdrawal) [2](#0-1) [3](#0-2) , the code measures `actual_amount_received` (vault balance delta) and `actual_scaled_balance_change` (Drift-side scaled balance delta), and then enforces:

```rust
require_eq!(
    actual_amount_received,
    token_amount,
    MarginfiError::DriftWithdrawFailed
);
require_eq!(
    actual_scaled_balance_change,
    expected_scaled_balance_change,
    MarginfiError::DriftScaledBalanceMismatch
);
``` [4](#0-3) 

Just like `interim_usdc_out == interim_usdc_in` in the Superposition report — where a value computed in step 1 is required to exactly match the value observed after step 2's external execution — this check assumes the external protocol (Drift) will always return precisely the value marginfi pre-computed off-chain-ish math, with zero tolerance. `reduce_only = true` explicitly signals to Drift that it may cap the withdrawal below the requested `amount` if the user's Drift-side position cannot fully satisfy it (e.g., rounding of Drift's internal scaled-balance representation, dust, or a spot balance that is fractionally smaller than marginfi's locally computed `token_amount`/`scaled_decrement`). The `withdraw_all` branch already anticipates and defensively handles a very similar off-by-one/rounding class of discrepancy (see the comment and the `-1` adjustment) [5](#0-4) , but the non-`withdraw_all` branch has no equivalent tolerance before hitting the exact-equality assertion.

### Impact Explanation
`drift_withdraw` is not merely a user convenience path — it is used directly inside the marginfi liquidation and receivership flow to seize/liquidate a Drift-backed asset position, as shown in the liquidation test flows (`makeDriftWithdrawIx` invoked between `startLiquidationIx` and `repayIx`/`endLiquidationIx`) [6](#0-5) . If Drift's CPI legitimately returns a token amount or scaled-balance delta that differs by even one unit from marginfi's pre-computed expectation (a realistic scenario any time Drift applies `reduce_only` clamping, internal rounding, or the position balance is marginally smaller than assumed), the `require_eq!` checks will revert the entire instruction — and since this ix is embedded inside the atomic start/withdraw/repay/end liquidation transaction, the whole liquidation attempt fails. This creates a Denial-of-Service on liquidating Drift-collateralized unhealthy accounts: liquidators cannot complete the liquidation, which for a sufficiently underwater position can allow bad debt to grow uncontrolled or force reliance on the more disruptive bankruptcy/receivership socialization path instead of a clean liquidation, directly bearing on protocol insolvency risk.

### Likelihood Explanation
Likelihood is data-dependent: it triggers only when Drift's actual withdrawal execution diverges from marginfi's locally pre-computed `token_amount`/`expected_scaled_balance_change`, which is plausible under `reduce_only` semantics and rounding edge cases (the same category of "not all requested value is realized in the second leg" issue as the original report), but does not manifest on every call. This matches the "medium — causes a subset of transactions to fail with no additional harm beyond DoS" characterization from the original finding, escalated here because the affected instruction sits on the liquidation critical path rather than a standalone swap route.

### Recommendation
Relax the strict equality checks in `drift_withdraw` to tolerant/bounded checks (e.g., `require_gte!`/`require_lte!` with a defined rounding tolerance, or explicitly recompute downstream state from the CPI-returned actual values instead of asserting them against the pre-computed expectation), mirroring the defensive rounding-adjustment logic already present in the `withdraw_all` branch. At minimum, treat `actual_amount_received <= token_amount` and `actual_scaled_balance_change <= expected_scaled_balance_change` as valid outcomes and propagate the actual values downstream, rather than reverting the entire liquidation transaction on exact mismatch.

### Proof of Concept
Concrete on-chain reproduction was not runnable in this analysis (no code execution/test environment available); the report is grounded in static analysis of the cited assertion and the CPI's `reduce_only = true` flag. To empirically confirm, a Devin session with build/test access could: (1) construct a Drift spot position where marginfi's locally computed `token_amount`/`scaled_decrement` is 1 unit larger than what Drift will actually transfer under `reduce_only` (e.g., via interest-accrual/rounding edge cases similar to the existing `withdraw_all` handling), (2) invoke `drift_withdraw` inside a liquidation transaction, and (3) observe the transaction revert with `DriftWithdrawFailed`/`DriftScaledBalanceMismatch`, blocking liquidation of an otherwise-liquidatable unhealthy account.
