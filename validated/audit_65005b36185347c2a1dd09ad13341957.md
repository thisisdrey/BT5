### Title
Unbounded JSON nesting depth in `parse_json` causes remote stack-overflow crash of the RPC node - ([File: stackslib/src/net/http/common.rs])

### Summary
`parse_json` (stackslib/src/net/http/common.rs:88-107) calls `serde_json::from_slice(body)` directly on an attacker-supplied HTTP request body that is only bounded by `Content-Length`/`MAX_PAYLOAD_LEN` (a byte-size cap), with no check on JSON nesting depth. `serde_json`'s value/array/object parser is a recursive-descent parser with no built-in depth limit, so a body consisting of tens of thousands of nested `[` characters (which trivially fits under any reasonable `MAX_PAYLOAD_LEN`) drives the parser to recurse until the OS thread stack is exhausted, aborting the entire process — not just the handling thread — since Rust stack overflows are not catchable panics.

### Finding Description
The claimed invariant — "a bounded-length body cannot cause unbounded stack depth" — is false. `MAX_PAYLOAD_LEN` and `Content-Length` validation only bound the number of *bytes* in the body; they say nothing about the JSON structural depth of those bytes. `serde_json::from_slice` at stackslib/src/net/http/common.rs:99 parses arrays/objects via mutual recursion in its `Deserializer`, consuming one stack frame per nesting level, with no depth guard. A body of N `[` characters (1 byte per nesting level) reaches N levels of recursion for only N bytes of payload, so an attacker can craft a body of ~100,000–1,000,000 nested brackets that is far below any of the `MAX_PAYLOAD_LEN`/`MAX_MESSAGE_LEN` byte caps enforced upstream in `stackslib/src/net/httpcore.rs` and `stacks-common/src/codec/mod.rs`, yet is deep enough to overflow the thread stack during parsing.

`parse_json` is invoked from multiple JSON-content-type RPC handlers (e.g. `postblock_proposal.rs`, `txsimulate.rs`, `blocksimulate.rs`, `postfeerate.rs`), reachable over the node's RPC port by any remote, unauthenticated party who can send an HTTP request with `Content-Type: application/json` and a crafted deeply-nested body. None of the existing guards — Content-Length validation, `MAX_PAYLOAD_LEN`/`MAX_MESSAGE_LEN` size caps, or content-type checks — inspect or bound structural nesting depth, so they do not prevent this.

### Impact Explanation
A single crafted HTTP request causes a stack overflow inside the RPC-handling thread. In Rust, stack overflow triggers an immediate process abort (SIGSEGV/SIGABRT) that cannot be caught by `catch_unwind` or any error-handling logic, crashing the entire node process, not merely the connection/thread. This is a remote, unauthenticated, single-message crash of the whole node — matching the Critical severity category ("remote crash/unauthenticated DoS from few messages"). It is trivially repeatable against any reachable RPC endpoint that accepts JSON bodies via `parse_json`.

### Likelihood Explanation
No privileged role, secret, or prior handshake is required — only network reachability to the node's RPC port and the ability to send one HTTP POST with a JSON content-type header and a deeply-nested body under the byte-size cap. The attacker cost is negligible (a single request, generated by a trivial script), and the exploit is fully repeatable against any and all nodes exposing an affected JSON RPC endpoint.

### Recommendation
Configure `serde_json`'s deserializer with a bounded recursion/nesting depth (e.g., use `serde_json::Deserializer::from_slice(body).into_iter()` variants combined with a depth-limited deserializer wrapper, or use `serde_stacker`/manual depth tracking to fail fast with a controlled `Error::DecodeError` once nesting exceeds a safe threshold, e.g., 64–128 levels) before falling back to full deserialization in `parse_json`.

### Proof of Concept
Add a test in `stackslib/src/net/http` (or a new test module under `stackslib/src/net/http/common.rs`) that:
1. Builds a `HttpResponsePreamble` with `content_type = HttpContentType::JSON`.
2. Builds `body: Vec<u8>` = `b"[".repeat(100_000)` (well under `MAX_PAYLOAD_LEN`).
3. Calls `parse_json::<serde_json::Value>(&preamble, &body)`.
4. Asserts the call returns `Err(_)` rather than aborting the test process with a stack overflow (run under `cargo test` and observe the process aborts with `SIGSEGV`/"stack overflow" rather than returning a `Result`, confirming the crash).
