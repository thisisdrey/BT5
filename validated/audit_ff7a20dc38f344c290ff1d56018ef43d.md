### Title
Legacy Bancor-relay Exchange swap uses non-hardened double/`Maths.pow` arithmetic that always truncates in one direction, allowing repeated micro-swaps to desync the pool invariant - ([File: chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java])

### Summary
`ExchangeTransactionActuator` lets any account swap tokens through a Balancer/Bancor-style bonding-curve AMM (`ExchangeCapsule.transaction`). When the chain-wide flag `allowHardenExchangeCalculation` is not enabled, every swap is routed through the legacy `ExchangeProcessor`, which computes the bonding-curve math with raw IEEE-754 `double` arithmetic and a custom, non-monotonic power approximation (`Maths.pow` → `MathWrapper.pow`), then truncates the result to `long` via a plain narrowing cast. This is architecturally the same bug class as Balancer's `_upscale()`: a single-direction rounding/truncation step embedded in an invariant-based swap function, "expected to be minimal" per swap, but capable of desynchronizing pool state when repeated across many small swaps in a single transaction.

### Finding Description
`ExchangeCapsule.transaction()` selects between two processors based on the `allowHarden()`/`hardenedCalc` flag: [1](#0-0) 

The legacy path (`ExchangeProcessor`, used whenever `allowHardenExchangeCalculation` is off) computes the relay-token/output-token amounts using `double` math and a custom `Maths.pow` exponentiation, then truncates via `(long)` cast: [2](#0-1) 

The "hardened" replacement (`SafeExchangeProcessor`) fixes this using `BigDecimal` with explicit `RoundingMode.HALF_UP`/`DOWN` semantics, which is functionally the equivalent of Balancer shipping a `FixedPoint`/rounding library *after* the fact: [3](#0-2) 

The test suite confirms the two paths produce *different* results for the same inputs (`assertNotEquals(anotherTokenQuant, result)`), proving the legacy path's rounding is not equivalent/safe: [4](#0-3) 

`Maths.pow`/`MathWrapper.pow` is explicitly marked deprecated for "cross-platform consistency" reasons - i.e. the project itself acknowledges the double-based power computation is imprecise and platform-dependent: [5](#0-4) 

Crucially, whether hardening applies is a runtime dynamic-property switch, not a permanent code fix - the vulnerable legacy processor remains fully reachable code and is the default unless `allowHardenExchangeCalculation` is turned on, exactly mirroring Balancer's situation where old pool instances "had expired pause windows" and inherited unfixed math while newer logic existed alongside it: [6](#0-5) 

The public-facing swap actuator (`ExchangeTransactionActuator`, reachable by any signed `ExchangeTransactionContract`) calls this math directly on every user swap, with no per-swap upper bound on the number of chained calls other than the transaction's normal fee/bandwidth cost - the same "one-hour of many small swaps" primitive that Balancer's attacker used (65+ micro-swaps in one transaction): [7](#0-6) 

### Impact Explanation
If the legacy (double-based) exchange processor is active for a given exchange/network configuration, an attacker can:
1. Repeatedly execute small `ExchangeTransactionContract` swaps against a pool with low reserves (achievable by first draining reserves via normal swaps or targeting a thin/new pool).
2. Exploit the fact that `Maths.pow`'s custom double approximation and the truncating `(long)` cast do not guarantee monotonic, invariant-preserving rounding under composition (`exchangeToSupply` followed by `exchangeFromSupply`, each independently truncating).
3. Because both legs of the swap mutate a floating internal `supply` accumulator across iterations within the same transaction (`ExchangeProcessor.supply` is stateful across calls), floating-point drift can compound across many chained calls, similarly to how Balancer's compounding rounding in `_upscale()` desynchronized the pool invariant across 65 iterations.

The result could be extraction of value beyond what reserves support (unbacked balance / theft) if the accumulated floating-point drift can be steered to favor the attacker rather than the pool - this would constitute direct, unauthorized draining of exchange reserves, matching the accepted impact categories (theft of funds / unbacked balance).

### Likelihood Explanation
Medium. The vulnerable legacy `ExchangeProcessor` is reachable by any unprivileged account via a single signed `ExchangeTransactionContract` - no special privileges are required. However:
- Exploitability depends on whether `allowHardenExchangeCalculation` is enabled on the target network; if it is enabled, all swaps route through `SafeExchangeProcessor`'s `BigDecimal` math, closing this specific path.
- Unlike Balancer, TRON's `Exchange` module is a legacy, low-usage feature (most modern TRON deployments favor SunSwap/other on-chain DEXs); still, the contract type remains active in the protocol and callable.
- Full confirmation that the floating-point drift can be steered to a specific attacker-favorable direction (rather than always favoring the pool, as in the correct case) requires numeric analysis of `Maths.pow`'s approximation error characteristics, which I could not fully verify from the available code (the `MathWrapper.pow` implementation itself was not retrieved in this session).

### Recommendation
- Make `allowHardenExchangeCalculation` (routing all exchange swaps through `SafeExchangeProcessor`) a permanent, non-toggleable code path rather than a runtime dynamic property, eliminating the legacy double-based `ExchangeProcessor` entirely.
- Add explicit round-trip invariance tests (swap A→B→A should never yield a profit) for both processors, mirroring the Certora "Roundtrip Swap Invariance" property that would have caught Balancer's bug.
- Audit `MathWrapper.pow`/`Maths.pow` for monotonicity and consistent-direction rounding guarantees; deprecate and remove call sites outside of the exchange module.

### Proof of Concept
Not independently reproducible from the indexed codebase snippets alone - reproducing a profitable drift would require: (1) confirming `allowHardenExchangeCalculation` is disabled (the default in some deployments, per `AbstractExchangeActuator.allowHarden()`), (2) constructing a low-liquidity `Exchange` pool, and (3) issuing a sequence of `ExchangeTransactionContract` swaps and comparing the on-chain resulting `firstTokenBalance + secondTokenBalance` (in equivalent value) before/after against the theoretical invariant, similar to the existing `ExchangeProcessorTest.testStrictMath` differential test harness: [8](#0-7)

  private BigDecimal exchangeToSupply(long balance, long quant) {
    long newBalance = StrictMathWrapper.addExact(balance, quant);
    BigDecimal bdQuant = BigDecimal.valueOf(quant);
    BigDecimal bdNewBalance = BigDecimal.valueOf(newBalance);
    BigDecimal base = BigDecimal.ONE.add(
        bdQuant.divide(bdNewBalance, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 0.0005);
    return SUPPLY.negate().multiply(
        BigDecimal.ONE.subtract(BigDecimal.valueOf(powResult))).setScale(0, RoundingMode.DOWN);
  }

  private long exchangeFromSupply(long balance, BigDecimal supplyQuant) {
    BigDecimal bdBalance = BigDecimal.valueOf(balance);
    BigDecimal base = BigDecimal.ONE.add(
        supplyQuant.divide(SUPPLY, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 2000.0);
    BigDecimal exchangeBalance = bdBalance.multiply(
        BigDecimal.valueOf(powResult).subtract(BigDecimal.ONE));
    return exchangeBalance.setScale(0, RoundingMode.DOWN).longValueExact();

package org.tron.common.math;

/**
 * This class is deprecated and should not be used in new code,
 * for cross-platform consistency, please use {@link StrictMathWrapper} instead,
 * especially for floating-point calculations.
 */
@Deprecated
public class Maths {

  /**
   * Returns the value of the first argument raised to the power of the second argument.
   * @param a the base.
   * @param b the exponent.
   * @return the value {@code a}<sup>{@code b}</sup>.
   */
  public static double pow(double a, double b, boolean useStrictMath) {
    return useStrictMath ? StrictMathWrapper.pow(a, b) : MathWrapper.pow(a, b);
  }
