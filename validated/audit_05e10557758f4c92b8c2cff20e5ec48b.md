### Title
Central-directory-trusted ZIP entry sizes are not validated against actual local-header/data-descriptor boundaries during `ijar`/`singlejar` re-packaging, allowing hidden/extra bytes to be smuggled into build outputs - (File: `third_party/ijar/zip.cc`, `src/tools/singlejar/transient_bytes.h`, `src/tools/singlejar/output_jar.cc`)

### Summary
The Sherlock finding is that `VotingStrategy.vote()` trusts `msg.value` without validating it equals the sum of the individually declared `_amount` fields, letting an attacker exploit the gap between "declared total" and "actual total" to steal funds. The closest structural analog in Bazel is in the ZIP/JAR-processing code used when Bazel repackages/copies entries from an *attacker-supplied archive* (e.g. an `http_archive`/`http_jar` downloaded via `ctx.download_and_extract`, or any dependency zip consumed by `ijar`/`singlejar`): the code trusts one authoritative field (the Central Directory's declared entry size) as "the whole" when `no_size_in_local_header()` is true, but otherwise blindly trusts the Local File Header's size field and copies exactly that many bytes as "the entry", without cross-checking it against the actual amount of data delimited by the next entry / real content boundary.

### Finding Description
In `third_party/ijar/zip.cc`, `InputZipFile::ProcessLocalFileEntry()` reads `compressed_size`/`uncompressed_size` from the Central Directory Entry (CDH) and separately reads size fields out of the Local File Header (LH). It only performs a consistency check when the LH fields are non-zero and non-`U4_MAX`: [1](#0-0) 
If the LH field is `0` or `U4_MAX` (which is exactly what a compressed entry legitimately looks like, and also what a crafted entry can set), the code unconditionally substitutes the CDH-declared size as ground truth with no re-validation against the number of bytes actually available/consumed for that entry, then proceeds to read exactly that many bytes as the entry payload: [2](#0-1) 

The analogous pattern exists in `src/tools/singlejar/transient_bytes.h`'s `ReadEntryContents`/`DecompressEntryContents`, and in `src/tools/singlejar/output_jar.cc`'s `AddJar`, all of which pick between "trust the Central Directory" (`no_size_in_local_header()`) or "trust the Local Header" declared size, but never validate that the resulting byte range for one entry doesn't overlap into a different declared entry's declared data, i.e. there is no check that "sum of the bytes-per-entry, as delimited by size fields we trust" equals the byte range that is actually structurally reserved for the entries in the archive (analogous to `msg.value == sum(amount)` never being enforced). [3](#0-2) [4](#0-3) 

Because the Central Directory offset for the *next* entry is used to relocate the read pointer (`p = zipdata_in_ + in_offset_ + offset;` in `ProcessNext`), and the size used to read *this* entry's payload comes from a different, independently-controlled field, a hostile zip served at a download URL (or checked into an untrusted branch that CI later re-packages with `ijar`) can construct a Local/Central Header pair where the declared size for entry N is smaller/larger than the actual span reserved for it before entry N+1's local header, causing bytes that "look like" they belong to another entry (or that are outside any entry's true content) to be silently included in — or excluded from — the repackaged (`ijar`-stripped or singlejar-merged) output.

### Impact Explanation
An attacker who controls the content served at a URL a victim's `http_jar`/`http_archive` fetches (or a dependency zip merged by `singlejar`/interface-jar-generated by `ijar` during the build) can smuggle extra bytes past the declared entry boundary into the final packaged jar consumed by the build, without breaking the archive-level sha256/integrity check (which validates the whole file, not per-entry consistency). This is a concrete integrity bypass of the entry-level "declared size" invariant that the ZIP reader is relying on to decide what bytes constitute one file's content versus another's — directly mirroring the source bug's "declared total not checked against actual total" class.

### Likelihood Explanation
Requires the attacker to control content at a URL/registry entry a victim's build fetches with `download_and_extract`/`http_jar`/`http_archive` (in-scope, unprivileged outsider serving hostile content), and the archive-level checksum does nothing to prevent this since it validates the outer file, not the internal entry boundary consistency that `ijar`/`singlejar` rely upon when repackaging.

### Recommendation
When `no_size_in_local_header()` is false, cross-validate the LH-declared size against the actual byte distance to the next entry's Central-Directory-declared `local_header_offset` (or the End-Of-Central-Directory boundary for the last entry), and reject the archive if they disagree, rather than trusting either field in isolation.

### Proof of Concept
A `BuildIntegrationTestCase`/`src/test/shell/bazel` test would need to: (1) hand-craft a zip where a middle entry's Local File Header declares an uncompressed/compressed size shorter than the actual bytes up to the next entry's Central-Directory-declared offset, embedding attacker payload bytes in the gap; (2) serve it via `http_archive`/`http_jar` with a correct sha256 for the whole archive; (3) show that `ijar`/`singlejar` (invoked as part of a `java_library`/`java_import` build) either silently drops or silently appends the gap bytes into the output artifact, demonstrating the entry-boundary invariant is not enforced despite the outer checksum passing — analogous to the existing `InputJarPreambledTest`/`InputJarScanEntries` smog-check assertions in `src/tools/singlejar/input_jar_scan_entries_test.h` and `input_jar_preambled_test.cc`, which currently only assert LH/CDH agreement when both are present and non-sentinel, but do not test the divergent-size-with-gap-bytes case.
