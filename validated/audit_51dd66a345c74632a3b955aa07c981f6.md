### Title
Account-scoped PromiseYield trie state survives `remove_account`, enabling potential post-recreation authorization escalation - (File: core/store/src/utils/mod.rs)

### Summary
`remove_account` enumerates and deletes only `Account`, `ContractCode`, `AccessKey`/`GasKeyNonce`, and `ContractData` trie rows for a deleted account, but does not clear `PromiseYieldReceipt`, `PromiseYieldTimeout`, `YieldIdToDataId`, or `DataIdToYieldId` rows scoped to that account name. This is a confirmed cleanup asymmetry between account-scoped state writers and the deletion path.

### Finding Description
`remove_account` explicitly removes `TrieKey::Account`, `TrieKey::ContractCode`, then iterates and removes access-key/gas-key-nonce rows, then removes `ContractData` rows. [2](#0-1) 
No code path in this function references `PromiseYieldReceipt`, `PromiseYieldTimeout`, `YieldIdToDataId`, or `DataIdToYieldId`, all of which exist as account-scoped `TrieKey` variants elsewhere in the codebase (`core/primitives/src/trie_key.rs`). If a `promise_yield_create` call leaves one of these rows behind for an account, and that account is subsequently deleted via `DeleteAccount`, the row remains in the trie under that account-name prefix. Because NEAR's trie key namespace is keyed by account *name* string rather than by an account-creation generation/nonce, a later `CreateAccount` reusing the same name inherits any un-cleared rows tied to that name.

### Impact Explanation
If the surviving row is later resolved (via `PromiseResume` delivered by the original creator or an automatic `PromiseYieldTimeout`), and if `apply_action_receipt`/`check_actor_permissions` treat a self-targeted receipt (`predecessor_id == receiver_id`) as carrying owner-level authority, an `AddKey(FullAccess)` action queued against the old incarnation could be admitted against the new tenant's account — this would constitute authorization escalation / account takeover, matching NEAR's "authorization escalation across accounts" bounty category. I was unable to fully verify this second half of the chain in this session.

### Likelihood Explanation
The precondition (root-cause cleanup gap in `remove_account`) is confirmed and requires no privileged access — any account holder can call `promise_yield_create` and `DeleteAccount` on their own subaccount. However, whether this gap is actually reachable to produce owner-privilege escalation depends on unverified downstream logic (`actor_id` derivation, `check_actor_permissions`, and `PromiseYieldTimeout` scheduling independence from account liveness), which I could not confirm with the tools available in this session.

### Recommendation
Audit `remove_account` against the full enumeration of account-scoped `TrieKey` variants in `core/primitives/src/trie_key.rs`, and add explicit removal (via prefix iteration, similar to the `ContractData`/access-key handling already present) for `PromiseYieldReceipt`, `PromiseYieldTimeout`, `YieldIdToDataId`, and `DataIdToYieldId` rows before an account is deleted, or reject `DeleteAccount` while such pending rows exist for the account.

### Proof of Concept
Given the incomplete verification of the resolve/actor_id path, a definitive PoC could not be fully constructed in this session. A verification test should: (1) create account A, call `promise_yield_create` with `receiver_id == current_account_id` and a pending `AddKey(FullAccess)` callback, (2) call `DeleteAccount` on A, (3) inspect trie state directly to confirm the `PromiseYieldReceipt`/`YieldIdToDataId` rows for A still exist post-deletion, (4) recreate account A, (5) deliver the surviving `data_id`'s `PromiseResume` (or trigger `PromiseYieldTimeout`), and (6) assert whether the new A's access-key set gained the `AddKey` from the stale callback — this last assertion is the unverified part requiring further tracing of `apply_action_receipt`/`check_actor_permissions`.
