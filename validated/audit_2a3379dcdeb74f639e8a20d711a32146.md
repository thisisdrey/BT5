### Title
Unbounded HTTP body read causes single-request memory-exhaustion DoS in signer event receiver - (File: libsigner/src/events.rs)

### Summary
`process_event<T,E>` reads the entire POST body via `request.as_reader().read_to_string(&mut body)` with no size cap before handing it to `serde_json::from_slice`, unlike the P2P HTTP body path in `libsigner/src/http.rs` which enforces `MAX_MESSAGE_LEN` on chunked bodies. Because `SignerEventReceiver::bind` is commonly configured to listen on `0.0.0.0` (per the shipped `sample/conf/signer/mainnet-signer-conf.toml` and `stacks-signer/src/config.rs`), any unauthenticated remote party that can open a TCP connection to this port can send one POST with a huge `Content-Length` to force unbounded memory allocation.

### Finding Description
`SignerEventReceiver::next_event` dispatches all POSTs to `/stackerdb_chunks`, `/proposal_response`, `/new_burn_block`, `/new_block` into `process_event::<T, E>` [1](#0-0) . `process_event` then does:

```rust
let mut body = String::new();
if let Err(e) = request.as_reader().read_to_string(&mut body) { ... }
``` [2](#0-1) 

There is no cap comparable to `MAX_MESSAGE_LEN` applied to this read, whereas the analogous body-decoding path used for the node<->signer HTTP protocol in `decode_http_body` explicitly bounds chunked reads with `HttpChunkedTransferReader::from_reader(ptr, MAX_MESSAGE_LEN.into())` [3](#0-2) . `SignerEventReceiver::bind` simply constructs a `tiny_http::Server` with no request-body-size configuration [4](#0-3) , and the event listener performs no authentication check before reading and buffering the body.

The listening endpoint is documented and shipped to be bound broadly (`endpoint = "0.0.0.0:30000"` in `sample/conf/signer/mainnet-signer-conf.toml`), and `stacks-signer/src/config.rs`'s `GlobalConfig`/`RawConfigFile` accept and use this address as-is with no enforced-loopback restriction [5](#0-4) . Consequently, any remote party who can reach that port can send `POST /stackerdb_chunks HTTP/1.1` with an arbitrarily large `Content-Length` and body, and the signer process will buffer the entire body into a `String` in memory before any JSON validation or size check occurs.

### Impact Explanation
A single crafted POST can force the signer process to allocate memory proportional to the attacker-supplied body size before any validation happens, causing memory exhaustion / process termination (OOM) on the signer node. This is an unauthenticated, single-request DoS against a component (`stacks-signer`) that participates in block signing, so a successful DoS can degrade or halt the signer's participation in consensus signing — matching the "remote crash/unauthenticated DoS from few messages" Critical category.

### Likelihood Explanation
- No authentication or signature check gates the event-receiver HTTP endpoint before the body is read.
- The bind address is commonly `0.0.0.0` per the shipped sample configs, making the port remotely reachable without any privileged role, secret, or prior handshake.
- The attacker only needs to open a TCP connection and send one HTTP POST with a large `Content-Length` — trivially repeatable at will.

### Recommendation
Apply a hard cap (e.g., `MAX_MESSAGE_LEN`-style limit, consistent with `libsigner/src/http.rs`'s `decode_http_body`) to the number of bytes read in `process_event` before or during `request.as_reader().read_to_string`, e.g. by wrapping the reader in a bounded `Read` (`Read::take(MAX_MESSAGE_LEN)`) or checking the `Content-Length` header up front and rejecting oversized requests with a `413`-equivalent response. Additionally consider binding the event-receiver default to loopback and warning operators against exposing it publicly.

### Proof of Concept
1. Start a `SignerEventReceiver` via `bind()` on a test port (as done in existing integration tests for the signer).
2. From a separate thread/process, open a `TcpStream` to that port and send:
   ```
   POST /stackerdb_chunks HTTP/1.1\r\nHost: 127.0.0.1\r\nContent-Length: 2000000000\r\nContent-Type: application/json\r\n\r\n
   ```
   followed by streaming large amounts of non-JSON filler bytes (or simply a very large legitimate-looking byte stream) up to the declared length.
3. Observe the signer process's memory usage grow unboundedly in `process_event`'s `body: String` buffer at `libsigner/src/events.rs:524-526`, with no early rejection based on size, before the `serde_json::from_slice` call at line 536 is even reached — confirming the missing size cap relative to the `MAX_MESSAGE_LEN` guard used elsewhere in `libsigner/src/http.rs:207`.

fn process_event<T, E>(mut request: HttpRequest) -> Result<SignerEvent<T>, EventError>
where
    T: SignerEventTrait,
    E: serde::de::DeserializeOwned + TryInto<SignerEvent<T>, Error = EventError>,
{
    let mut body = String::new();

    if let Err(e) = request.as_reader().read_to_string(&mut body) {
        error!("Failed to read body: {:?}", &e);
        ack_dispatcher(request);
        return Err(EventError::MalformedRequest(format!(
            "Failed to read body: {:?}",
            e
        )));
    }
    // Regardless of whether we successfully deserialize, we should ack the dispatcher so they don't keep resending it
    ack_dispatcher(request);
    let json_event: E = serde_json::from_slice(body.as_bytes())
        .map_err(|e| EventError::Deserialize(format!("Could not decode body to JSON: {:?}", e)))?;
