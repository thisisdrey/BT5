### Title
Missing Zero-Address Validation in Staking/Delegation Operator and Beneficiary Setters Allows Permanent Loss of APT Commission Rewards — (`stake.move`, `staking_contract.move`, `delegation_pool.move`, `vesting.move`)

---

### Summary

Multiple public entry functions in the Aptos staking framework accept critical `address` parameters — operator, voter, and beneficiary — without any zero-address (`@0x0`) guard. An operator or owner who passes `@0x0` (e.g., due to a front-end bug or uninitialized variable) can redirect commission rewards to the null address, permanently burning APT, or can strip a stake pool of its operator, blocking validator operations until a corrective transaction is submitted.

---

### Finding Description

The following production entry functions accept an `address` parameter and write it directly into on-chain state with no `assert!(addr != @0x0, ...)` guard:

| Module | Function | Unguarded parameter |
|---|---|---|
| `stake` | `set_operator` / `set_operator_with_cap` | `new_operator` |
| `stake` | `set_delegated_voter` / `set_delegated_voter_with_cap` | `new_voter` |
| `staking_contract` | `set_beneficiary_for_operator` | `new_beneficiary` |
| `delegation_pool` | `set_beneficiary_for_operator` | `new_beneficiary` |
| `vesting` | `update_operator` | `new_operator` |
| `vesting` | `update_voter` | `new_voter` |

**`stake::set_operator_with_cap`** writes `new_operator` directly:

```move
stake_pool.operator_address = new_operator;   // no zero check
```

**`staking_contract::set_beneficiary_for_operator`** writes `new_beneficiary` directly:

```move
borrow_global_mut<BeneficiaryForOperator>(operator_addr).beneficiary_for_operator =
    new_beneficiary;   // no zero check
```

**`delegation_pool::set_beneficiary_for_operator`** does the same:

```move
borrow_global_mut<BeneficiaryForOperator>(operator_addr).beneficiary_for_operator = new_beneficiary;
// no zero check
```

The downstream `distribute_internal` in `staking_contract` then routes commission to whatever address is stored:

```move
if (recipient == operator) {
    recipient = beneficiary_for_operator(operator);   // could be @0x0
};
aptos_account::deposit_coins(
    recipient, coin::extract(&mut coins, amount_to_distribute)
);
```

By contrast, `vesting::create_vesting_contract` **does** validate its address parameter:

```move
assert!(
    !system_addresses::is_reserved_address(withdrawal_address),
    error::invalid_argument(EINVALID_WITHDRAWAL_ADDRESS),
);
```

This inconsistency shows the framework is aware of the risk but has not applied the guard uniformly.

---

### Impact Explanation

**Beneficiary set to `@0x0`:** When `distribute_internal` runs, it calls `aptos_account::deposit_coins(@0x0, coins)`. If `@0x0` has no `CoinStore`, the distribution transaction aborts and all commission payouts are permanently blocked until the operator corrects the beneficiary — effectively freezing earned APT rewards. If `aptos_account::deposit_coins` auto-creates the account (as it does for normal addresses), the APT is sent to an address no one controls and is permanently burned.

**Operator set to `@0x0`:** The stake pool's `operator_address` becomes `@0x0`. No one can sign as the operator, so consensus-key rotation, validator-set join/leave, and commission requests are all blocked. The owner can recover by calling `set_operator` again, but any epoch during which the validator cannot rotate keys or respond to slashing conditions is a real operational risk.

**Vesting operator set to `@0x0`:** `vesting::update_operator` calls `staking_contract::switch_operator` with `new_operator = @0x0`, keying the staking contract by `@0x0`. All subsequent vesting reward flows depend on the operator key, so vest/distribute calls may fail until the admin corrects the operator.

---

### Likelihood Explanation

These are all unprivileged user-initiated entry functions (operator or owner role, not governance). A front-end bug that passes an uninitialized variable — exactly the scenario described in the external report — is a realistic trigger. The Aptos CLI and SDK builder expose these as direct transaction payloads with no client-side zero check either. The probability is low in normal operation but non-negligible given the number of validators and the history of front-end bugs in staking UIs.

---

### Recommendation

Add a zero-address assertion at the top of each affected function, mirroring the pattern already used in `vesting::create_vesting_contract`:

```move
// In stake::set_operator_with_cap
assert!(new_operator != @0x0, error::invalid_argument(EINVALID_OPERATOR));

// In staking_contract::set_beneficiary_for_operator
assert!(new_beneficiary != @0x0, error::invalid_argument(EINVALID_BENEFICIARY));

// In delegation_pool::set_beneficiary_for_operator
assert!(new_beneficiary != @0x0, error::invalid_argument(EINVALID_BENEFICIARY));

// In vesting::update_operator / update_voter
assert!(new_operator != @0x0, error::invalid_argument(EINVALID_OPERATOR));
assert!(new_voter != @0x0, error::invalid_argument(EINVALID_VOTER));
```

Optionally, reuse `system_addresses::is_reserved_address` to also block `@vm_reserved` and other special addresses, consistent with the existing `withdrawal_address` validation.

---

### Proof of Concept

1. Operator calls `staking_contract::set_beneficiary_for_operator(operator_signer, @0x0)`.
   - No assertion fires; `BeneficiaryForOperator.beneficiary_for_operator` is written as `@0x0`. [1](#0-0) 

2. Anyone calls `staking_contract::distribute(staker, operator)`.
   - `distribute_internal` resolves `recipient = beneficiary_for_operator(operator)` → `@0x0`. [2](#0-1) 

3. `aptos_account::deposit_coins(@0x0, commission_coins)` either:
   - **Aborts** → all future commission distributions are permanently blocked until the operator corrects the beneficiary (freezing earned APT rewards), or
   - **Succeeds** → commission APT is sent to `@0x0` and permanently burned.

4. The same flow applies to `delegation_pool::set_beneficiary_for_operator`. [3](#0-2) 

5. For `stake::set_operator(@0x0)`, the stake pool's operator becomes `@0x0`, blocking all operator-signed actions (consensus-key rotation, validator-set management) until the owner submits a corrective transaction. [4](#0-3) 

6. The inconsistency is confirmed by the existing guard in `vesting::create_vesting_contract` that the setter functions lack: [5](#0-4)

    public entry fun set_beneficiary_for_operator(

        // The beneficiay address of an operator is stored under the operator's address.

            );
        };

                new_beneficiary
            }
        );
    }
