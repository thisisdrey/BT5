### Title
Unrestricted remote URL scheme allows Git `ext::`/`file://` transport-helper abuse in Gitaly's clone/fetch RPCs - (File: internal/gitaly/service/repository/create_repository_from_url.go, internal/gitaly/service/repository/fetch_remote.go, internal/gitaly/service/remote/update_remote_mirror.go)

### Summary
Gitaly exposes several RPCs (`CreateRepositoryFromURL`, `FetchRemote`, `UpdateRemoteMirror`, `FindRemoteRootRef`, `FindRemoteRepository`) that accept a caller-supplied remote URL string and pass it, largely unvalidated, directly as a positional argument to `git clone`/`git fetch`/`git ls-remote`/`git push` subprocesses. None of the request validators restrict the URL's *scheme* — they only check for an empty string.

### Finding Description
`validateCreateRepositoryFromURLRequest` only checks `req.GetUrl() == ""` [1](#0-0) , and the parsed URL is handed straight to `git clone` as a positional argument with no scheme allow-list [2](#0-1) . Likewise, `validateFetchRemoteRequest` only checks for a blank URL before it is placed into `remote.inmemory.url` git config and fetched [3](#0-2) [4](#0-3) , and `validateUpdateRemoteMirrorRequest` behaves the same way [5](#0-4) .

The only scheme-aware code path, `GetURLAndResolveConfig`, is opt-in (only triggered when `resolved_address` is set) and even there the SCP-style/`default` branch accepts arbitrary strings without rejecting dangerous schemes such as `ext::` or `file://` — it merely tries to split on `:` and falls through to SCP-style handling for anything not matching `http(s)://`, `git://`, or `ssh://` [6](#0-5) . When `resolved_address` is not provided, no scheme validation happens at all before the raw URL reaches `git`.

Git's `ext::` transport helper is well known to execute an arbitrary shell command supplied as the "host" part of the URL (e.g. `ext::sh -c "id > /tmp/pwn"`), and `file://` can be used to read/clone from arbitrary local paths on the Gitaly host, bypassing storage boundaries. Because Gitaly does not set `GIT_ALLOW_PROTOCOL`/`protocol.*.allow` to restrict the transports usable by the invoked `git` binary, and does not reject non-`http(s)/git/ssh` schemes in the RPC validators, any caller who can supply the `url` field of `CreateRepositoryFromURL`, `FetchRemote.RemoteParams.url`, `UpdateRemoteMirror.remote.url`, or `FindRemoteRootRef.remote_url` can force Gitaly's `git` subprocess to execute an "undesired external call" analogous to the Controller/`callee` issue in the source report — the RPC acts as a generic gateway that blindly hands attacker-controlled data to an external interpreter (git's transport-helper dispatch) without checking that the target is a recognized/whitelisted transport.

### Impact Explanation
If reachable with an attacker/tenant-controlled URL (e.g., a GitLab "import project by URL" or "pull mirror" feature relaying user input into these RPC fields), this allows remote code execution on the Gitaly host via `ext::`, or arbitrary local file/repo disclosure via `file://`, which is a full compromise of the Gitaly node and, in a Praefect/multi-tenant deployment, potentially other repositories on the same storage.

### Likelihood Explanation
Likelihood depends on whether the higher-level caller (GitLab Rails / gitlab-shell) already sanitizes URL schemes before invoking these RPCs — I could not verify that from the Gitaly codebase alone since the RPCs are typically called by a trusted Rails backend rather than directly by an anonymous end-user. However, within Gitaly itself there is no defense-in-depth: these validators and command constructors provide zero scheme allow-listing, so if any caller path (project import by URL, repository mirroring, pull mirrors configured by ordinary project maintainers) forwards user-supplied URLs unmodified, the Gitaly layer offers no protection.

### Recommendation
Add scheme validation to `validateCreateRepositoryFromURLRequest`, `validateFetchRemoteRequest`, and `validateUpdateRemoteMirrorRequest` (and the `FindRemoteRootRef`/`FindRemoteRepository` handlers) that rejects any URL whose scheme is not in an explicit allow-list (`http`, `https`, `git`, `ssh`, and SCP-style `user@host:path`). Additionally, set `GIT_ALLOW_PROTOCOL=http:https:git:ssh` (or equivalent `protocol.*.allow=never` defaults with explicit allows) as an environment variable on every git subprocess spawned for these remote-URL flows as defense in depth, matching the intent already shown by `GetURLAndResolveConfig`'s scheme switch but enforcing it unconditionally rather than only when `resolved_address` is set.

### Proof of Concept
A request such as:
```
CreateRepositoryFromURLRequest{
  Repository: <target>,
  Url: "ext::sh -c 'touch /tmp/pwned'",
}
```
would be parsed by `url.Parse` (schemeless URLs are parsed leniently) and passed as `Args: []string{urlString, repositoryFullPath}` to `git clone` [7](#0-6) . Since `git` recognizes the `ext::` transport helper by default and Gitaly does not restrict `GIT_ALLOW_PROTOCOL`, the embedded shell command would execute in the context of the Gitaly process. I was not able to run this against a live Gitaly instance to fully confirm exploitation (no filesystem/terminal access in this environment), so this should be validated empirically by a Devin session with repository access before treating it as confirmed-exploitable, and by tracing exactly which upstream (Rails/gitlab-shell) caller paths pass through unsanitized user input into these RPC URL fields.

		config = append(config, resolveConfig...)

func GetURLAndResolveConfig(remoteURL string, resolvedAddress string) (string, []ConfigPair, error) {
	if remoteURL == "" {
		return "", nil, fmt.Errorf("URL is empty")
	}

	if resolvedAddress == "" {
		return "", nil, fmt.Errorf("resolved address is empty")
	}

	resolvedIP := net.ParseIP(resolvedAddress)
	if resolvedIP == nil {
		return "", nil, fmt.Errorf("resolved address has invalid IPv4/IPv6 address")
	}

	switch {
	case strings.HasPrefix(remoteURL, "http://"), strings.HasPrefix(remoteURL, "https://"), strings.HasPrefix(remoteURL, "git://"):
		return getURLAndResolveConfigForURL(remoteURL, resolvedAddress)
	case strings.HasPrefix(remoteURL, "ssh://"):
		return getURLAndResolveConfigForSSH(remoteURL, resolvedAddress)
	default:
		return getURLAndResolveConfigForSCP(remoteURL, resolvedAddress)
	}
