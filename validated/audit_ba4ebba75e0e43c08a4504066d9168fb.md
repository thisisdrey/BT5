### Title
Protocol fee bypass on NEP-245/IMT token transfers via unit-fragmentation of `TokenDiff` intents - ([File: contracts/defuse/core/src/intents/token_diff.rs])

### Summary
`TokenDiff::token_fee` returns `Pips::ZERO` whenever a negative delta on a `TokenIdType::Nep245`/`TokenIdType::Imt`/`TokenIdType::Nep171` token has `amount <= 1`, and this exemption is evaluated independently per `TokenDiff` intent rather than on the aggregate value transferred in a batch. Because NEP-245/IMT-wrapped tokens can represent fungible-equivalent balances with fine-grained (1-unit) increments, a transfer of any size can be fragmented into many unit-sized `TokenDiff` pairs, each of which nets to zero without invoking `closure_delta`/`closure_supply_delta` fee-adjustment, allowing the full nominal amount to move with zero fee collected.

### Finding Description
The binding that should hold is: `fee_collector` balance increase for a transfer of `N` units of a fee-bearing NEP-245/IMT token == `Self::token_fee(token_id, N, protocol_fee).fee_ceil(N)`, regardless of how the transfer is split across intents in a batch.

In `execute_intent` [1](#0-0) , each `(token_id, delta)` pair in a `TokenDiff` independently computes its fee via `Self::token_fee(token_id, delta.unsigned_abs(), protocol_fee).fee_ceil(amount)` only when `delta < 0`, and `token_fee` short-circuits to `Pips::ZERO` for `Nep171`/`Nep245`/`Imt` whenever `amount <= 1` [2](#0-1) .

For a normal fee-bearing swap between two parties, the counterparty's compensating delta must be computed via `closure_delta`/`closure_supply_delta`, which explicitly bakes in the fee so that the sum of all deltas in the batch (including the amount later credited to `fee_collector`) still nets to zero [3](#0-2) . However, a plain "gift" transfer of the *same* `TokenId` between two accounts does not require any closure adjustment at all — the invariant is trivially satisfied by `A: -k` and `B: +k` on the same token, with no `fee_collector` contribution needed for the batch to net to zero.

If `k` is chosen as a single amount greater than 1 (e.g. `A: -1000`, `B: +1000`), `token_fee` returns `protocol_fee` (not zero, since `amount=1000 > 1`), so the batch would need `B`'s delta reduced to `1000 - fee` (via closure) to keep the Verifier's custodied balance conserved, and `fee_collector` collects `fee`. But if the same net transfer of `1000` units is instead executed as `1000` separate `TokenDiff` intents, each with `delta = -1` (signed by `A`) and `delta = +1` (signed by `B`) on the identical `TokenId::Nep245`, every individual intent hits the `amount <= 1` branch and returns `Pips::ZERO`. Each unit-pair trivially nets to zero without touching `fee_collector`, so `B` ends up with the full `1000` units and `fee_collector`'s balance is unchanged — a strictly better outcome for the colluding pair than executing the same value transfer as one (or few) larger `TokenDiff`s.

No existing guard catches this: `MaybeLegacyNonces::commit`, `MultiPayload::verify`, and `Deltas`/`TransferMatcher::finalize` [4](#0-3)  only enforce that the aggregate deltas across the batch net to zero (custody conservation); they do not aggregate or evaluate `amount` per token across multiple intents for fee purposes. The `amount<=1` exemption is a purely local, per-`TokenDiff`, per-token-id check with no memory of prior/other intents in the same batch.

### Impact Explanation
The fee that would normally accrue to `fee_collector` (a protocol-level revenue mechanism) is bypassed entirely for any NEP-245/IMT-wrapped value transfer, by an attacker/solver splitting the transfer into unit-sized `TokenDiff` intents. This directly matches the Critical impact category "protocol fees bypassed" — value that should have been credited to `fee_collector` never is, while the full nominal value still moves between the two colluding/cooperating accounts. It is repeatable for any amount and any Nep245/Imt token, and scales linearly with the number of fragments (N intents to move N units fee-free). This does not violate the Verifier's overall balance invariant (deltas still net to zero within each unit-pair), so no under-custodied state results, but it is a genuine loss of protocol fee revenue.

### Likelihood Explanation
Preconditions: `fee != Pips::ZERO`; attacker controls two accounts holding/receiving a NEP-245 (or IMT) token with a `TokenId` supporting >1 unit increments and can sign/submit `N` `TokenDiff` intents in one or more `execute_intents`/`simulate_intents` batches. This requires no special privilege — any unprivileged NEAR account that can sign `DefusePayload`s and call `execute_intents` can perform it. The only friction is gas/storage/transaction cost for issuing `N` intents (explicitly acknowledged as a batch-size precondition in the question and out of scope as a blocking factor per the rules, since gas exhaustion itself is not the claimed impact). This is fully reproducible on unit tests without needing near-workspaces sandbox limits to be exceeded for reasonably small `N` (e.g., tens to hundreds of units), and scales for any Nep245/Imt token the attacker controls.

### Recommendation
Change the fee exemption to be based on intrinsic token semantics rather than the per-intent delta magnitude: e.g., only exempt `TokenIdType::Nep171` (true NFTs, which are inherently non-fungible and always have `|delta|==1`), and always apply `protocol_fee` to `Nep245`/`Imt` deltas regardless of magnitude (since these types can represent fungible-equivalent balances). Alternatively, track and aggregate per-`TokenId` negative deltas across the whole intents batch before applying the `amount<=1` exemption, so fragmentation across multiple `TokenDiff` intents in the same execution cannot evade the aggregate fee schedule.

    /// Returns total supply delta from token delta
    #[inline]
    fn supply_delta(token_id: &TokenId, delta: i128, fee: Pips) -> Option<i128> {
        if delta < 0 {
            // fee is taken only on negative deltas (i.e. token_in)
            delta.checked_mul_div_ceil(
                Self::token_fee(token_id, delta.unsigned_abs(), fee)
                    .invert()
                    .as_pips()
                    .into(),
                Pips::MAX.as_pips().into(),
            )
        } else {
            // token_out
            Some(delta)
        }
    }
