### Title
Missing length validation when parsing untrusted ZIP central-directory entries allows out-of-bounds read / crash in ijar's zip parser - (`third_party/ijar/zip.cc`)

### Summary
`InputZipFile::ProcessCentralDirEntry` in `third_party/ijar/zip.cc` reads attacker-controlled 16/32-bit length fields (`file_name_length`, `extra_field_length`, `file_comment_length`, ZIP64 extra-field `data_size`) directly from a memory-mapped, untrusted ZIP/JAR file and advances the read cursor and does a `memcpy` based on those lengths **without ever calling the `EnsureRemaining()` bounds check** that the sibling function `InputZipFile::ProcessLocalFileEntry` (same file) consistently uses before every read. [1](#0-0) [2](#0-1) 

### Finding Description
`ProcessLocalFileEntry` protects every read with `EnsureRemaining(n, state)`, which checks `n` bytes remain before the cursor is advanced, e.g. for `file_name_length` and `extra_field_length`: [3](#0-2) 

By contrast, `ProcessCentralDirEntry` — used while walking the central directory — reads the corresponding fields and unconditionally does:
```
p += file_name_length;
...
extra_p += data_size;   // inside a ZIP64 extra-field parsing loop
...
p += file_comment_length;
```
with no call to `EnsureRemaining()` anywhere in the function. [4](#0-3) 

Specifically:
1. `file_name_length`, `extra_field_length`, `file_comment_length` are read as raw `u2` values straight from the mapped file with no upper bound check against the remaining mapped length. [5](#0-4) 
2. `memcpy(filename, p, len)` is executed with `len` derived from the unchecked `file_name_length`, before verifying that `p + len` is within the mapped region — this is a direct out-of-bounds read into `filename`. [6](#0-5) 
3. The ZIP64 extra-field walking loop increments `extra_p += data_size` using an attacker-controlled 16-bit `data_size` with no bound on `extra_p` staying inside the buffer, and then dereferences `get_u8le(extra)` to read 8 bytes past that unchecked offset when the `ZIP64_EXTRA_FIELD_TAG` is seen. [7](#0-6) 

This function is invoked from `ProcessNext()`/`CalculateOutputLength()` while iterating the central directory of a ZIP/JAR file that is only backed by a fixed-length `mmap`, so reading past the computed cursor position walks off the end of the mapped region. [8](#0-7) [9](#0-8) 

This is a direct structural analog of CVE-2017-12187: a length field taken from untrusted, attacker-supplied binary input is used to advance a cursor / compute a copy size with no bounds validation, permitting an out-of-bounds read that can crash the process (mapped page beyond file end is unmapped → SIGSEGV) or leak adjacent heap/mapping bytes into the `filename` buffer that is later used to decide whether to `Accept()`/process a file.

### Impact Explanation
`ijar` (and the `InputZipFile` class here) parses ZIP/JAR files as part of Bazel's `ijar` interface-jar generator and other zip-processing tools built on this shared `zip.cc`. Any JAR/ZIP whose bytes were authored by an attacker — e.g. an artifact published at a URL that a `http_jar`/`http_archive` rule downloads — reaches this parser once it is used as an input to jar-processing tooling. Because sha256/integrity pinning only guarantees the *bytes* match what was recorded, not that the ZIP structure is well-formed, an attacker who controls the origin can craft a byte-for-byte reproducible malicious central directory (with e.g. `extra_field_length`/`data_size` values that walk the cursor past the mapped region) that still satisfies any checksum the victim later pins. The result is a crash (denial of build) or, if the out-of-bounds bytes happen to be readable heap/mapping content, disclosure of adjacent memory content copied into `filename` and used in subsequent decision logic.

### Likelihood Explanation
Central-directory-entry length fields are fully attacker controlled in any ZIP/JAR the attacker authors, and `ProcessCentralDirEntry` is called for every entry while iterating the whole central directory (`ProcessNext`, `CalculateOutputLength`), so the vulnerable code path is reached on every use of this parser against untrusted archive content, with no additional preconditions beyond the archive being processed by ijar's zip reader.

### Recommendation
Add `EnsureRemaining()` (or equivalent bounds checks against `input_file_->Length()` from `zipdata_in_`/`p`) before reading `file_name_length`, `extra_field_length`, `file_comment_length`, and before every `memcpy`/pointer advance and ZIP64 extra-field `data_size`-driven read in `InputZipFile::ProcessCentralDirEntry`, mirroring the checks already present in `ProcessLocalFileEntry`.

### Proof of Concept
I was not able to fully trace how far `ijar`'s zip reader is reachable from a `http_archive`/`http_jar`-fetched artifact within the remaining investigation budget (I could not confirm the exact call path from Bazel's Java-side repository/download machinery into this specific C++ `zip.cc` reader, nor locate/verify an existing JUnit/shell test harness that exercises `ProcessCentralDirEntry` with a crafted central directory). A reproducible PoC would need to be built as a `third_party/ijar/zip_test` style test (see `third_party/ijar/test/zip_test.sh`) that constructs a minimal ZIP whose central-directory entry declares `extra_field_length`/`file_comment_length` values exceeding the remaining mapped file length, and confirms `InputZipFile::ProcessNext`/`CalculateOutputLength` reads out of bounds (e.g., under ASan) instead of failing cleanly with an `error(...)` message as `ProcessLocalFileEntry` does for analogous fields. This should be validated/confirmed by a Devin session with code-execution access before treating this as fully confirmed.

```text
bool InputZipFile::ProcessCentralDirEntry(const u1 *&p, u8 *compressed_size,
                                          u8 *uncompressed_size, char *filename,
                                          size_t filename_size, u4 *attr,
                                          u8 *offset) {
  u4 signature = get_u4le(p);

  if (signature != CENTRAL_FILE_HEADER_SIGNATURE) {
    if (signature != DIGITAL_SIGNATURE && signature != EOCD_SIGNATURE &&
        signature != ZIP64_EOCD_SIGNATURE) {
      error("invalid central file header signature: 0x%x\n", signature);
    }
    return false;
  }

  p += 16;  // skip to 'compressed size' field
  *compressed_size = get_u4le(p);
  *uncompressed_size = get_u4le(p);
  u2 file_name_length = get_u2le(p);
  u2 extra_field_length = get_u2le(p);
  u2 file_comment_length = get_u2le(p);
  p += 4;  // skip to external file attributes field
  *attr = get_u4le(p);
  *offset = get_u4le(p);
  {
    size_t len = (file_name_length < filename_size)
      ? file_name_length
      : (filename_size - 1);
    memcpy(reinterpret_cast<void*>(filename), p, len);
    filename[len] = 0;
  }
  p += file_name_length;
  const u1 *extra_p = p;
  p += extra_field_length;
  while (extra_p != p) {
    const u2 header_id = get_u2le(extra_p);
    const u2 data_size = get_u2le(extra_p);
    const u1 *extra = extra_p;
    extra_p += data_size;
    if (header_id == ZIP64_EXTRA_FIELD_TAG) {
      if (*uncompressed_size == U4_MAX) {
        *uncompressed_size = get_u8le(extra);
      }
      if (*compressed_size == U4_MAX) {
        *compressed_size = get_u8le(extra);
      }
      if (*offset == U4_MAX) {
        *offset = get_u8le(extra);
      }
    }
  }
  p += file_comment_length;
  return true;
}
```

u8 InputZipFile::CalculateOutputLength() {
  const u1* current = central_dir_;

  u8 compressed_size = 0;
  u8 uncompressed_size = 0;
  u8 skipped_compressed_size = 0;
  u4 attr;
  u8 offset;
  char filename[PATH_MAX];

  while (true) {
    u8 file_compressed, file_uncompressed;
    if (!ProcessCentralDirEntry(current,
                                &file_compressed, &file_uncompressed,
                                filename, PATH_MAX, &attr, &offset)) {
      break;
    }

    if (processor->Accept(filename, attr)) {
      compressed_size += (u8) file_compressed;
      uncompressed_size += (u8) file_uncompressed;
    } else {
      skipped_compressed_size += file_compressed;
    }
  }

  // The worst case is when the output is simply the input uncompressed. The
  // metadata in the zip file will stay the same, so the file will grow by the
  // difference between the compressed and uncompressed sizes.
  return (u8) input_file_->Length() - skipped_compressed_size
      + (uncompressed_size - compressed_size);
}
