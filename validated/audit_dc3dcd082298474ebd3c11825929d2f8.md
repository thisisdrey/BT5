### Title
Unstaked peer can inflate observed QUIC RTT to gain up to 7x more concurrent uni-streams via BDP scaling in `compute_max_allowed_uni_streams_with_rtt` - (File: streamer/src/nonblocking/swqos.rs)

### Finding Description
`compute_max_allowed_uni_streams_with_rtt` scales the base per-connection concurrent-uni-stream cap by `rtt_millis.clamp(REFERENCE_RTT_MS, MAX_RTT_MS) / REFERENCE_RTT_MS`, where `REFERENCE_RTT_MS = 50` and `MAX_RTT_MS = 350` [1](#0-0) . For `ConnectionPeerType::Unstaked` the base is `QUIC_MAX_UNSTAKED_CONCURRENT_STREAMS = 128`, and the final result is `streams * rtt_millis / REFERENCE_RTT_MS`, meaning at `MAX_RTT_MS` the multiplier reaches `350/50 = 7x`, i.e. up to `896` concurrent uni-streams instead of `128` [2](#0-1) . This value is fed directly into `connection.set_max_concurrent_uni_streams(max_uni_streams)` at connection-cache time via `SwQos::cache_new_connection`, using `connection.rtt()` clamped only at the upper bound (`rtt_millis = connection.rtt().as_millis().min(MAX_RTT_MS as u128)`) [3](#0-2) .

`connection.rtt()` (quinn) is derived from the QUIC RTT estimator, which is computed from ACK timing reported by the peer — an unprivileged remote client fully controls when/how it ACKs packets sent by the server. By deliberately delaying its ACKs (e.g., holding off sending ACK frames for received server data, or exploiting the self-reported `ACK Delay` field), a remote unstaked client can inflate the RTT sample the server-side connection observes, without any actual added network latency. This is a client-controlled input with no independent verification on the server side — there is no cross-check against network topology, GeoIP, or historical measurements. There is no `MIN_RTT`-style clamp in the `SwQos` path (unlike `simple_qos.rs`'s `cache_new_connection`, which does `connection.rtt().clamp(MIN_RTT, MAX_RTT)` — but that only clamps up to a lower bound and still permits upper-bound inflation) [4](#0-3) .

However, the effect is limited: `set_max_concurrent_uni_streams` only widens the transport-level flow-control window (how many streams can be *simultaneously open* at once), it does not increase the actual rate of *new* accepted streams per unit time, which is separately governed by `throttle_stream` / `StakedStreamLoadEMA::available_load_capacity_in_throttling_duration`, capped at `max_unstaked_load_in_throttling_window = MAX_UNSTAKED_TPS * STREAM_THROTTLING_INTERVAL_MS / 1000` (independent of RTT) [5](#0-4) [6](#0-5) . This throughput-limiting gate is unaffected by RTT manipulation and applies per-connection independent of the `max_concurrent_uni_streams` cap. Additionally, the actual test in the repo already documents this scaling as intentional design ("Max streams should scale with BDP in high-RTT connections") [7](#0-6) .

### Impact Explanation
The concrete effect of RTT inflation is that an attacker's connection is allowed more *concurrently open* streams (up to 7x, 896 vs 128), which can let it hold more transaction-carrying streams open at once and consume more per-connection receive-window/memory resources on the server, and potentially allow bursts of stream creation ahead of throttling being applied per-stream. However, since new-stream acceptance rate for unstaked peers is separately hard-capped by `max_unstaked_load_in_throttling_window` regardless of RTT, the sustained throughput advantage over legitimate low-RTT unstaked senders is bounded — this is primarily a resource-consumption/fairness concern (more open streams => more receive-window state per connection) rather than an unbounded QoS-bypass or DoS. This is a low/medium severity QoS-fairness issue, not a node panic, deadlock, unbounded memory, verification bypass, or invalid block.

### Likelihood Explanation
Feasible without special privileges: any unstaked client opening a QUIC connection to the public TPU port controls its own ACK timing and can artificially delay ACKs to inflate the server-observed RTT up to `MAX_RTT_MS` (350ms). No staking, gossip, or validator control is required, only client-side control over the QUIC handshake/ACK cadence, which is fully attacker-controlled and repeatable across connections.

### Recommendation
Do not scale unstaked (or staked) stream limits based on unauthenticated, self-influenceable RTT samples without additional safeguards. Options:
- Cap the BDP multiplier more conservatively for unstaked peers, or disable RTT-based upscaling entirely for `ConnectionPeerType::Unstaked` (only apply BDP scaling to staked/verified peers where misbehavior has reputational/stake cost).
- Cross-validate RTT against a smoothed/minimum-seen RTT over the connection lifetime (min-RTT filtering, as used in BBR) rather than trusting the latest sample, to reduce the ability to inflate on demand.
- Ensure the concurrent-stream cap increase can never let an attacker exceed the throughput cap already enforced by `StakedStreamLoadEMA`, e.g., decouple the "resource/memory" cap from being attacker-adjustable at all for unstaked connections.

fn test_unstaked_rtt_inflation_grants_up_to_7x_streams() {
    // Baseline: low/reference RTT -> baseline stream count
    let baseline = compute_max_allowed_uni_streams_with_rtt(
        REFERENCE_RTT_MS,
        ConnectionPeerType::Unstaked,
        10_000,
    );
    assert_eq!(baseline, QUIC_MAX_UNSTAKED_CONCURRENT_STREAMS);

    // Attacker inflates RTT (e.g. via delayed ACKs) up to MAX_RTT_MS
    let inflated = compute_max_allowed_uni_streams_with_rtt(
        MAX_RTT_MS,
        ConnectionPeerType::Unstaked,
        10_000,
    );

    // Demonstrates unstaked peer can obtain up to 7x more concurrent streams
    // than a legitimate low-RTT peer, purely via self-reported/observed RTT.
    assert_eq!(inflated, baseline * (MAX_RTT_MS / REFERENCE_RTT_MS));
    assert!(inflated > baseline, "RTT-only manipulation increases unstaked stream cap");

    // independent of RTT, e.g. capped at baseline regardless of rtt_millis.
    // assert_eq!(inflated, baseline);
}

fn compute_max_allowed_uni_streams_with_rtt(
    rtt_millis: u32,
    peer_type: ConnectionPeerType,
    total_stake: u64,
) -> u32 {
    let streams = match peer_type {
        ConnectionPeerType::Staked(peer_stake) => {
            // No checked math for f64 type. So let's explicitly check for 0 here
            if total_stake == 0 || peer_stake > total_stake {
                warn!(
                    "Invalid stake values: peer_stake: {peer_stake:?}, total_stake: \
                     {total_stake:?}"
                );

                QUIC_MIN_STAKED_CONCURRENT_STREAMS
            } else {
                let delta = (QUIC_TOTAL_STAKED_CONCURRENT_STREAMS
                    - QUIC_MIN_STAKED_CONCURRENT_STREAMS) as f64;

                (((peer_stake as f64 / total_stake as f64) * delta) as u32
                    + QUIC_MIN_STAKED_CONCURRENT_STREAMS)
                    .clamp(
                        QUIC_MIN_STAKED_CONCURRENT_STREAMS,
                        QUIC_MAX_STAKED_CONCURRENT_STREAMS,
                    )
            }
        }
        ConnectionPeerType::Unstaked => QUIC_MAX_UNSTAKED_CONCURRENT_STREAMS,
    };
    // scale amount of streams based on RTT if RTT is larger than REFERENCE_RTT_MS
    // multiply first then divide to avoid rounding errors.
    (streams.saturating_mul(rtt_millis.clamp(REFERENCE_RTT_MS, MAX_RTT_MS))) / REFERENCE_RTT_MS
}

    pub(crate) fn available_load_capacity_in_throttling_duration(
        &self,
        peer_type: ConnectionPeerType,
        total_stake: u64,
    ) -> u64 {
        match peer_type {
            ConnectionPeerType::Unstaked => self.max_unstaked_load_in_throttling_window,
            ConnectionPeerType::Staked(stake) => {
                if self.staked_throttling_enabled.load(Ordering::Relaxed) {
                    // 1 is added to `max_unstaked_load_in_throttling_window` to guarantee that staked
                    // clients get at least 1 more number of streams than unstaked connections.
                    self.max_staked_load_in_throttling_window
                        .saturating_mul(stake)
                        .checked_div(total_stake)
                        .unwrap_or(self.max_unstaked_load_in_throttling_window + 1)
                        .max(self.max_unstaked_load_in_throttling_window + 1)
                } else {
                    self.max_staked_load_in_throttling_window
                }
            }
        }
    }
