### Title
Unbounded per-account token list lets an attacker dust-fill a victim's `depositTokensOfAccount`/`debtTokensOfAccount` slots and DoS new deposits, borrows, and collateral additions - (File: contracts/Pool.sol)

### Summary
`Pool` maintains a bounded per-account set (`depositTokensOfAccount` + `debtTokensOfAccount`) capped by `MAX_TOKENS_PER_USER`. Entry into the set is triggered not by the account owner but by *any* `DepositToken`/`DebtToken` balance change from zero — including inbound `transfer`s the victim never requested. An unprivileged attacker can deposit dust into every whitelisted deposit token and `transfer` it to a victim, filling all available slots. Every subsequent first-time deposit, `issue`/`mint` of a new synthetic, or receipt of a new collateral type reverts with `UserReachedMaxTokens`, a denial of service analogous to the open62541 "unlimited received chunks" bug: state grows on behalf of a victim without their consent until a hard limit permanently rejects further work.

### Finding Description
In `DepositToken._transfer` (contracts/DepositToken.sol:517-520), when the recipient's balance is zero the token calls `pool.addToDepositTokensOfAccount(recipient_)` unconditionally — the recipient cannot opt out. The same happens in `_mint` (contracts/DepositToken.sol:485-488) on deposit.

`Pool.addToDepositTokensOfAccount` (contracts/Pool.sol:216-220) and `addToDebtTokensOfAccount` (contracts/Pool.sol:204-208) are gated by `onlyIfAdditionWillNotReachMaxTokens(account_)`, which reverts `UserReachedMaxTokens` once the combined deposit+debt token count reaches `MAX_TOKENS_PER_USER`. Because the revert propagates through `_transfer`/`_mint`, the *entire* transaction reverts:

- `DepositToken.deposit(amount, onBehalfOf)` → `_mint` → `addToDepositTokensOfAccount` → revert. The victim cannot receive a new collateral type, including deposits made on their behalf.
- `DebtToken.issue`/`mint`/`flashIssue` of any synthetic the victim has never held → `addToDebtTokensOfAccount` → revert. The victim is locked out of opening new debt positions.
- `DepositToken.transfer`/`transferFrom`/`seize` to the victim of any token not already in their set → revert. Liquidators cannot send the victim new collateral types either.

Recovery is asymmetric: the victim can only purge a slot by transferring the dust out, which requires the dust to be *unlocked* — `_transfer` is guarded by `_revertIfLocked`/`unlockedBalanceOf`. If the victim's collateral is fully locked by an existing debt position, the attacker-planted entries cannot be removed, so the victim cannot deposit any *new* collateral type to improve health (only top up types already held), and cannot repay-and-exit into a new synthetic. The attack costs the attacker only dust amounts; with N whitelisted deposit tokens and M synthetic debt tokens, ~`MAX_TOKENS_PER_USER` cheap transfers fully saturate the victim.

### Impact Explanation
Temporary-to-permanent freezing of position-management functionality: the victim loses the ability to (a) onboard new collateral types, (b) issue any new synthetic asset, and (c) receive any token not already in their set. For an account whose collateral is entirely locked, the dust entries cannot be evicted by the victim, making the block persistent until positions change. This also blocks rescue-deposits of new collateral on an unhealthy account (only pre-held token types can be topped up), indirectly exposing the victim to liquidation they could otherwise avoid.

### Likelihood Explanation
Fully permissionless: only requires public `deposit` and `transfer` on whitelisted `DepositToken`s, plus dust capital. No privileged roles, no oracle manipulation, no timing dependence. The only prerequisites are that the pool has whitelisted tokens (always true in deployed configs) and that the victim has headroom below `MAX_TOKENS_PER_USER`.

### Recommendation
- Do not add tokens to `depositTokensOfAccount`/`debtTokensOfAccount` on plain `transfer`s; only add on `deposit`/`issue` initiated (or authorized) by the account, or add an opt-in/registry toggle per account.
- Alternatively, let `addToDepositTokensOfAccount` fail-soft (skip the add instead of reverting) and have `depositOf`/`debtOf` iterate a lazily maintained list, so an unsolicited transfer can never brick the victim's flows.
- As a mitigation, allow accounts to forcibly remove dust entries (e.g., a `purgeToken(account, token)` ignoring the locked-balance check for balances below a threshold).

### Proof of Concept
Hardhat (fork or local, against deployed Pool/DepositTokens):

```ts
// Attacker fills victim's account token set with dust.
const MAX = (await pool.MAX_TOKENS_PER_USER()).toNumber();
const depositTokens = await pool.getDepositTokens(); // whitelisted DepositTokens

for (const dt of depositTokens.slice(0, MAX)) {
  const depositToken = await ethers.getContractAt('DepositToken', dt);
  const underlying = await ethers.getContractAt('ERC20', await depositToken.underlying());
  await underlying.approve(dt, ethers.constants.MaxUint256);
  // deposit 1 wei of underlying, transfer dust to victim -> adds token to victim's set
  await depositToken.deposit(1, attacker.address);
  await depositToken.transfer(victim.address, 1);
}
// Optionally fill remaining slots with DebtToken dust via issue() + transfer if DebtToken transfers are allowed,
// or rely on combined deposit+debt cap by repeating with each debt token.

// Victim is now saturated:
const token = await ethers.getContractAt('ERC20', underlyingOfSomeTokenVictimNeverHeld);
await token.approve(newDepositToken.address, amount);
await expect(newDepositToken.deposit(amount, victim.address))
  .to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');

// Same for issuing any synthetic not previously held:
await expect(newDebtToken.issue(amount, victim.address))
  .to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');
```

The test in `test/Pool.test.ts:1386-1416` already demonstrates the revert path (`UserReachedMaxTokens`); the PoC shows the entries can be planted by a third party via unsolicited `DepositToken.transfer`s, which the victim cannot prevent and may not be able to remove while collateral is locked.
