### Title
Unauthenticated integer-overflow panic in `estimate_tx_fee_from_cost_and_length` via attacker-controlled `estimated_len` - ([File: stackslib/src/net/api/postfeerate.rs])

### Summary
The `POST /v2/fees/transaction` handler takes the caller-supplied `estimated_len` field verbatim (bounded only below by the actual payload length, never above) and multiplies it by `MINIMUM_TX_FEE_RATE_PER_BYTE` with a plain `u64 * u64` operation and no `checked_mul`/`saturating_mul`. A remote, unauthenticated caller can set `estimated_len` to a value close to `u64::MAX`, causing this multiplication to overflow.

### Finding Description
In `try_parse_request` [1](#0-0) , `estimated_len` is computed as `max(body.estimated_len.unwrap_or(0), payload_data.len() as u64)` — the caller-supplied `body.estimated_len` is a free-form JSON `u64` with no upper bound check (the only size restriction, `content_len < MAX_PAYLOAD_LEN`, bounds the JSON *body* size in bytes, not the numeric value of an integer field, which can encode `18446744073709551615` in 20 ASCII bytes trivially within that limit).

This attacker-controlled `estimated_len` then flows unmodified into `estimate_tx_fee_from_cost_and_length`, where:
```
let minimum_fee = estimated_len * MINIMUM_TX_FEE_RATE_PER_BYTE;
``` [2](#0-1) 
is a raw multiplication with no overflow guard. Because `MINIMUM_TX_FEE_RATE_PER_BYTE` is a fixed positive constant `>1` [3](#0-2) , choosing `estimated_len = u64::MAX` (or any value near it) makes the product exceed `u64::MAX`, triggering arithmetic overflow. No downstream check (auth gate, `MAX_PAYLOAD_LEN`, `will_admit_mempool_tx`, canonical-tip resolution) intercepts this value before the multiplication — the request only needs a syntactically valid small transaction payload to pass `TransactionPayload::consensus_deserialize` at line 179.

This is reachable via a single unauthenticated `POST /v2/fees/transaction` request containing a well-formed small `transaction_payload` hex string and `"estimated_len": 18446744073709551615`.

### Impact Explanation
In a debug build (overflow-checks enabled, which is the default for `debug_assertions`), this multiplication panics, crashing the thread handling the RPC request. Whether this results in full node crash or just a single dropped connection depends on how the HTTP server isolates panics per-connection; if unwinding is caught per-request the impact is a benign error, but if not caught it can bring down the node process — this is a remotely triggerable, repeatable DoS primitive requiring only one HTTP POST to an RPC endpoint that requires no secret/auth. In an optimized release build without `overflow-checks = true`, the multiplication silently wraps, producing an incorrect (typically much smaller) `minimum_fee`, which is a correctness bug but not a crash.

### Likelihood Explanation
No privileged role, secret, or specific chain state is required — only network reachability to the node's RPC port and the ability to send a valid JSON POST body with a well-formed transaction payload, which is trivial. The attack is a single request and fully repeatable.

### Recommendation
Bound `estimated_len` to a sane maximum (e.g., `MAX_PAYLOAD_LEN` or a defined maximum tx size) when parsing the request body, and replace the raw multiplication with `checked_mul`/`saturating_mul`, returning an HTTP 400 on overflow instead of allowing an unchecked computation.

### Proof of Concept
Add a test in `stackslib/src/net/api/tests/postfeerate.rs` that constructs a `FeeRateEstimateRequestBody { estimated_len: Some(u64::MAX), transaction_payload: <valid small tx hex> }`, serializes it, and drives it through `RPCPostFeeRateRequestHandler::try_parse_request` followed by `estimate_tx_fee_from_cost_and_length`, asserting the call either returns an `Err` gracefully (expected fix) or currently panics/wraps at `estimated_len * MINIMUM_TX_FEE_RATE_PER_BYTE` (current behavior), run with `cargo test` in debug mode where overflow checks are enabled by default to observe the panic.
