Audit Report

## Title
Snowbridge outbound-queue `calculate_fee` truncates the ETH-denominated remote fee to zero via chained division, letting messages be charged and queued for Ethereum delivery with an unbacked (zero) relayer/execution fee - ([File: bridges/snowbridge/pallets/outbound-queue/src/lib.rs])

## Summary
`Pallet::<T>::calculate_fee` computes the ETH-denominated `remote` fee by chaining a `saturating_mul`/`checked_div` against `exchange_rate` and then feeding the result into `convert_from_ether_decimals`, which performs a second plain integer division by `10^(ETHER_DECIMALS - T::Decimals)`. With realistic, individually-valid `PricingParameters` (small `fee_per_gas`/`reward` relative to the ~10^6–10^8 scaling divisor for DOT/KSM-like chains), this floors a non-zero wei-scale fee down to `0`, as directly demonstrated by the pallet's own test.

## Finding Description
`calculate_fee` at [1](#0-0)  computes `fee = fee_per_gas * gas_used + reward` (wei), scales it by `multiplier / exchange_rate` via `FixedU128`, and then calls `convert_from_ether_decimals`, which performs `value.checked_div(denom)` where `denom = 10^(18 - T::Decimals)` [2](#0-1) . For chains like DOT (10 decimals) or KSM (12 decimals), `denom` is `10^8` or `10^6` respectively; any intermediate value smaller than `denom` truncates to exactly `0` via integer flooring division, with no ceiling/rounding-up and no minimum-fee floor.

This is exercised by the pallet's own test `test_calculate_fees_with_valid_exchange_rate_but_remote_fee_calculated_as_zero`, which uses individually non-zero, `validate()`-passing parameters (`exchange_rate = 1`, `fee_per_gas = 1`, `rewards.remote = 1`, `multiplier = 1`) and asserts `fee.remote == 0`, with an inline comment acknowledging the fee is "invalid which should be avoided" [3](#0-2) .

`PricingParameters::validate` only checks that each individual input field is non-zero — `exchange_rate`, `fee_per_gas`, `rewards.local`, `rewards.remote`, `multiplier` — and never simulates or checks the composed output of `calculate_fee` [4](#0-3) . This is the guard that fails to catch the truncation.

`SendMessage::validate` calls `calculate_fee` to compute the `Fee` charged to the user before queuing a message via `deliver` [5](#0-4) . Separately, `do_process_message`/commit logic unconditionally sets `reward: pricing_params.rewards.remote` and `max_fee_per_gas` into the `CommittedMessage` regardless of the (possibly zero) `Fee.remote` computed for the user-facing charge [6](#0-5) .

## Impact Explanation
Because `remote` is meant to fully back the relayer/execution cost on Ethereum but can be truncated to `0` for currently-valid pricing parameters, a caller can be charged an incorrect (zero) fee for the Ethereum-side cost of message execution while the message is still accepted and queued. This is "public underpriced work" reachable via ordinary message submission (e.g., asset transfers through the bridge exporter/router), matching the allowed impact category of underpriced work that can degrade bridge economics/processing, without any privileged actor or off-repo assumption required — it is a pure, deterministic arithmetic consequence of the documented divisor relationship between `ETHER_DECIMALS` and typical `T::Decimals` configurations.

## Likelihood Explanation
No privileged actor, governance action, or compromised relayer is needed. Any legitimately configured, individually-valid `PricingParameters` (which is the norm for realistic small `fee_per_gas`/`reward` values relative to the `10^6`–`10^8` divisor gap between wei and DOT/KSM decimals) reproducibly triggers this truncation, as already proven by the repository's own unit test with concrete inputs.

## Recommendation
- Change `convert_from_ether_decimals` to use ceiling division instead of flooring, and/or
- Enforce a minimum non-zero floor on the final composed `Fee.remote` after all divisions, rejecting configurations that would yield zero for supported commands, and
- Extend `PricingParameters::validate` to simulate `calculate_fee` for the cheapest supported `Command` and reject parameter sets that produce a zero composed `remote` fee.

## Proof of Concept
The existing repository test directly reproduces the issue: with `exchange_rate = FixedU128::from_rational(1,1)`, `fee_per_gas = 1`, `rewards = {local:1, remote:1}`, `multiplier = FixedU128::from_rational(1,1)`, and `gas_used = 250000`, `OutboundQueue::calculate_fee` returns `fee.remote == 0` despite all `PricingParameters::validate()` checks passing [3](#0-2) .

		pub(crate) fn calculate_fee(
			gas_used_at_most: u64,
			params: PricingParameters<T::Balance>,
		) -> Fee<T::Balance> {
			// Remote fee in ether
			let fee = Self::calculate_remote_fee(
				gas_used_at_most,
				params.fee_per_gas,
				params.rewards.remote,
			);

			// downcast to u128
			let fee: u128 = fee.try_into().defensive_unwrap_or(u128::MAX);

			// multiply by multiplier and convert to local currency
			let fee = FixedU128::from_inner(fee)
				.saturating_mul(params.multiplier)
				.checked_div(&params.exchange_rate)
				.expect("exchange rate is not zero; qed")
				.into_inner();

			// adjust fixed point to match local currency
			let fee = Self::convert_from_ether_decimals(fee);

			Fee::from((Self::calculate_local_fee(), fee))
		}

		let message_id: H256 = message
