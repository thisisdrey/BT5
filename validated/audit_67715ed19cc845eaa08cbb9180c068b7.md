### Title
Unbounded array allocation from attacker-controlled length field in `PrecompiledContracts.extractBytesArray` / `extractBytes32Array` / `extractSigArray` enables memory-exhaustion DoS - ([File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java])

### Summary
The TVM precompiled contracts `ValidateMultiSign` and `BatchValidateSign` decode a dynamic-array length directly from attacker-supplied call data and allocate a `byte[len][]` array of that size **before** any bound check is applied, whenever the `allowTvmSelfdestructRestriction` feature flag is not active. This mirrors the reported `quick-xml` `NsReader` bug class: an internal length-driven allocation happens inside the library/runtime before the caller's own size checks have a chance to reject the input.

### Finding Description
`extractBytesArray`, `extractBytes32Array`, and `extractSigArray` read the array length straight from the ABI-encoded input and immediately allocate an array of that size: [1](#0-0) 

Both call sites gate the *bound check* behind `VMConfig.allowTvmSelfdestructRestriction()`, but the extraction (and therefore the allocation) itself is unconditional:

- In `ValidateMultiSign.execute`, the `MAX_SIZE` (5) check on `sigArraySize` only happens `if (VMConfig.allowTvmSelfdestructRestriction())`; otherwise `extractBytesArray(words, words[3].intValueSafe() / WORD_SIZE, rawData)` is called directly with the raw attacker-controlled length, and the `signatures.length > MAX_SIZE` check only runs *after* the array has already been allocated: [2](#0-1) 

- In `BatchValidateSign.doExecute`, the same pattern occurs for `signatures`, and critically `addresses = extractBytes32Array(words, words[2].intValueSafe() / WORD_SIZE)` is called with **no** preceding bound check regardless of the feature flag state for that particular array (the `addrArraySize` check inside the `if (VMConfig.allowTvmSelfdestructRestriction())` block reads the same length value used later, but `extractBytes32Array` itself performs the allocation `new byte[len][]` with an unvalidated `len` from `words[offset].intValueSafe()`): [3](#0-2) 

The `len` value is an arbitrary attacker-supplied 256-bit word truncated to an `int` (`intValueSafe()`), independent of the real size of the call data. Because the bound check (`MAX_SIZE`, i.e. 5 or 16) is only enforced *after* the array is already allocated (or not at all, when the fork/feature flag is inactive), a small transaction can drive an allocation of up to `Integer.MAX_VALUE` array slots.

### Impact Explanation
A single, unauthenticated smart-contract call to one of the precompiled addresses backing `ValidateMultiSign` or `BatchValidateSign` can force the node to attempt to allocate an oversized `byte[][]` (each element being an 8-byte reference on 64-bit JVMs, so a length near `Integer.MAX_VALUE` requests ~16 GB) before any of the contract's own bound checks execute. This can throw `OutOfMemoryError` or otherwise exhaust heap on the executing node, causing the transaction-processing thread/node to crash or become unresponsive — a node crash/halt DoS reachable from any contract call, matching the "node crash or halt" acceptance criterion.

### Likelihood Explanation
The precompiles are reachable from any TVM contract call (`CALL`/`STATICCALL` to the fixed precompile address) by any unprivileged account; no special privileges are required. The energy charged for these precompiles (`getEnergyForData`) is computed from `data.length`, which is unrelated to the internal length field read from the payload, so the cost of triggering the huge allocation is not properly bounded by energy metering. The vulnerable path is only closed when `VMConfig.allowTvmSelfdestructRestriction()` is active for the *sig* array (and never fully closed for the `addresses` array extraction in `BatchValidateSign`, since `extractBytes32Array` has no bound check at all before allocating).

### Recommendation
Validate the decoded array length against the precompile's `MAX_SIZE` (and against the actual remaining size of `words`) inside `extractBytesArray`, `extractBytes32Array`, and `extractSigArray` themselves, *before* allocating the destination array — unconditionally, not gated behind a feature flag. Alternatively, pass a `maxLen` parameter to these helper methods and reject (return `false`) immediately if `len` exceeds it or exceeds what the input buffer can actually contain, mirroring the remediation approach in the referenced `quick-xml` fix (reject before allocating, with a hard cap).

### Proof of Concept
1. Craft a TVM contract call to the `BatchValidateSign` precompile address (or `ValidateMultiSign`) with a minimal `data` payload.
2. Set the word at the address-array length offset (`words[words[2].intValueSafe()/WORD_SIZE]`) to a large value close to `Integer.MAX_VALUE / 8` (or any value large enough to trigger an outsized allocation, e.g. `0x1FFFFFFF`).
3. Ensure `VMConfig.allowTvmSelfdestructRestriction()` is not active (default/older fork state) so no pre-check occurs for `extractBytes32Array`.
4. Call `execute(data)`; `extractBytes32Array` executes `byte[][] bytes32Array = new byte[len][];` with the attacker-supplied `len`, immediately attempting a multi-gigabyte allocation and risking `OutOfMemoryError` on the node processing the transaction, before the subsequent `cnt > MAX_SIZE` check ever runs.

  private static byte[][] extractBytes32Array(DataWord[] words, int offset) {
    int len = words[offset].intValueSafe();
    byte[][] bytes32Array = new byte[len][];
    for (int i = 0; i < len; i++) {
      bytes32Array[i] = words[offset + i + 1].getData();
    }
    return bytes32Array;
  }

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
