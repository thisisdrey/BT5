## Analysis

The LiFi bug's core invariant: **an external call's boolean success return is trusted as proof that value was actually moved, without verifying the actual balance change.** The strongest local analog is in `cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs`, which implements `TransactAsset` for `ERC20Transactor` — a live component wired into `asset-hub-westend`'s `AssetTransactors` tuple.

### Title
Unbacked XCM asset credit from trusting arbitrary ERC20 `transfer()` return value without balance verification - (File: `cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs`)

### Summary
`ERC20Transactor::withdraw_asset_with_surplus` treats any Solidity contract address embedded in an XCM `Asset` location as a valid ERC-20 "asset id" via `ERC20Matcher` [1](#0-0) , with no allow-list of trusted token contracts. When executing a `WithdrawAsset`, it calls the arbitrary contract's `transfer()` and, upon a decoded `true` return, unconditionally credits the XCM holding register with the claimed `amount` via `AssetsInHolding::new_from_fungible_credit` [2](#0-1)  — without ever checking that the checking account's actual on-chain ERC20 balance increased by that amount.

### Finding Description
`withdraw_asset_with_surplus` builds an ERC20 `transfer` call to move `amount` from `who` to the checking account, executes it via `pallet_revive::Pallet::<T>::bare_call`, and only inspects the ABI-decoded boolean return value: [3](#0-2) 

If the decoded return is `true`, the code immediately mints an `Erc20Credit(amount)` into the XCM holding register — the `amount` value used comes from the XCM message itself (via `Matcher::matches_fungibles`), not from any observed balance delta on the contract. This is structurally identical to the LiFi `GenericSwapFacet`/`LibSwap::swap()` flaw: the call's return code is trusted as a proxy for "tokens were actually moved," with no `before/after` balance check.

Because `ERC20Matcher` accepts *any* local `AccountKey20` location as a valid asset id [4](#0-3) , an attacker can:
1. Deploy a malicious "ERC20" contract via `pallet-revive` whose `transfer()` function always ABI-encodes and returns `true` but performs no real balance debit (or debits a decoy shadow balance instead of the real supply).
2. Submit an XCM program (e.g. via `pallet-xcm::execute`, reachable by any signed account) with `WithdrawAsset` referencing this contract address as the asset location and an attacker-chosen `amount`.
3. `withdraw_asset_with_surplus` calls `transfer()`, gets `true`, and credits the XCM holding register with the full `amount` — value that was never actually removed from any real balance.
4. The attacker's XCM program then uses `DepositAsset`/`TransferAsset`/`BuyExecution` to move that credited holding to any beneficiary (including cross-chain via HRMP/UMP, or to pay fees), converting a phantom "withdrawal" into spendable value elsewhere.

The symmetric `deposit_asset_with_surplus` has the analogous weakness in reverse: it also trusts `transfer()`'s `true` return as sufficient evidence a deposit succeeded.

### Impact Explanation
This breaks the "message queues, bridge markers, receipts, and payout state must only advance after decode, dispatch, execution, and settlement succeed atomically" invariant, and the value-conservation requirement for "contract-held value must conserve value and settle exactly once." An attacker can conjure XCM-recognized value backed by nothing, enabling theft/unbacked mint style impact: value appears in the holding register and can be relocated to any beneficiary or cross-chain destination without any real asset ever leaving circulation on the source side.

### Likelihood Explanation
This requires only an unprivileged account able to (a) deploy a contract through `pallet-revive` (already permitted broadly via `UploadOrigin`/`InstantiateOrigin: EnsureSigned` in the asset-hub-westend runtime config [5](#0-4) ) and (b) submit an XCM program referencing that contract as an asset. No validator, relayer, governance, or leaked key is needed — this is a pure public-entrypoint path.

### Recommendation
Do not trust the ERC20 `transfer()` boolean return alone. Read the checking account's (or recipient's) balance via `balanceOf` before and after the call and require the delta to equal `amount` before crediting/decrementing the XCM holding register, mirroring the LiFi fix of requiring a verified balance-based check rather than trusting the call's return status.

### Proof of Concept
1. Deploy a Solidity contract `FakeERC20` whose `transfer(address,uint256)` always returns `abi.encode(true)` and performs no storage mutation (or mutates an unrelated variable).
2. Register/represent this contract's address as `AccountKey20` in an XCM `Asset` location.
3. From a signed account, call `pallet_xcm::execute` (or construct a remote XCM) containing:
   ```
   WithdrawAsset(Asset { id: AssetId(Location::new(0, [AccountKey20 { network: None, key: FAKE_ERC20_ADDR }])), fun: Fungible(LARGE_AMOUNT) })
   DepositAsset { assets: All, beneficiary: <attacker-controlled account> }
   ```
4. `ERC20Transactor::withdraw_asset_with_surplus` calls `FakeERC20.transfer(checking_account, LARGE_AMOUNT)`, receives `true`, and credits `LARGE_AMOUNT` of `Erc20Credit` to the holding register despite no real balance movement having occurred.
5. `deposit_asset_with_surplus` then transfers this phantom credited amount out via the checking account's ERC20 `transfer` call to the beneficiary address — again trusting a boolean return from the same attacker-controlled contract, completing the unbacked value creation and delivery. [6](#0-5)

/// `Contains<Location>` implementation that matches locations with no parents,
/// a `PalletInstance` and an `AccountKey20` junction.
pub struct IsLocalAccountKey20;
impl Contains<Location> for IsLocalAccountKey20 {
	fn contains(location: &Location) -> bool {
		matches!(location.unpack(), (0, [AccountKey20 { .. }]))
	}
}

/// Fallible converter from a location to a `H160` that matches any location ending with
/// an `AccountKey20` junction.
pub struct AccountKey20ToH160;
impl MaybeEquivalence<Location, H160> for AccountKey20ToH160 {
	fn convert(location: &Location) -> Option<H160> {
		match location.unpack() {
			(0, [AccountKey20 { key, .. }]) => Some((*key).into()),
			_ => None,
		}
	}

	fn convert_back(key: &H160) -> Option<Location> {
		Some(Location::new(0, [AccountKey20 { key: (*key).into(), network: None }]))
	}
}
