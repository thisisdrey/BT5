### Title
NAV mid-computation state can be corrupted by an unguarded external interleaving in `PortfolioVault.updateNav` - (File: `contracts/PortfolioVault.sol`)

### Summary
The Hyperdrive report flags `checkpoint()` as a state-mutating function lacking a reentrancy guard, which lets an in-flight, multi-step operation (`_calculateOpenShort` → `_applyOpenShort`) be interleaved with a state change that invalidates the assumption that the underlying curve `C` stays fixed between the two calls, producing a corrupted post-condition (solvency drift). The same root cause — a multi-step, stateful computation that assumes its inputs (the loan set backing NAV) stay fixed across sub-calls, but has no lock preventing another path from mutating that exact state mid-computation — exists in `PortfolioVault.updateNav`, which is already documented as an unresolved finding in this repo's own audit report.

### Finding Description
`updateNav(uint256 batchSize)` paginates NAV computation across possibly many transactions (`navCursor`, `pendingNav`, `navStart`), accumulating per-loan valuations from the curated `_navLoanIds` list [1](#0-0) . It is guarded only by `whenNotPaused` and a manager role check, not by any lock that prevents the vault's own loan holdings from changing between batches through a path that does not funnel through the vault. `createSaleOffer` on `LoansExchange` does not require `_requireIdleNav`, and a named buyer can settle that offer directly via `LoansExchange.acceptOffer`, transferring the listed loan NFT out of the vault without any callback into `PortfolioVault` [2](#0-1) . If this settlement happens between two `updateNav` batches (after the loan has already been folded into `pendingNav` but before finalization), the loan's discounted value remains counted in `pendingNav` while the sale proceeds simultaneously land in `assetToken.balanceOf(vault)`, which is also added at finalization — double counting the same economic value and inflating `lastNav` [3](#0-2) . This is documented as an open, unfixed finding: the current `updateNav` implementation still lacks the recommended snapshot-and-verify mechanism (`navSnapshot`), confirming the fix has not been applied [4](#0-3) .

This mirrors the Hyperdrive pattern precisely: a "checkpoint"-like accumulator (`pendingNav`/`navCursor`) is trusted to represent a consistent snapshot across multiple external interactions, but no atomicity/lock mechanism stops an unprivileged actor (the offer's designated buyer) from mutating the very state (`loansNFT` ownership of a vault-held loan) that the computation depends on, mid-cycle.

### Impact Explanation
An inflated `lastNav` directly feeds `approveDeposit`/`approveRedemption` share pricing: `shares = (assets * totalSupply) / lastNav` [5](#0-4) . An inflated NAV mints fewer shares to new depositors than fair value (favoring the vault) or, more critically once diluted, could let existing/redeeming shareholders redeem against an inflated NAV, extracting more USDC than backed by real assets — an unfair mint/redeem and underbacked-claims scenario, which is explicitly an allowed impact under "Material corruption of ... vault NAV ... that produces real value loss, unfair mint or redeem, or underbacked claims."

### Likelihood Explanation
Triggering requires only that a sale offer's designated buyer (an ordinary registered investor, not a privileged role) call `LoansExchange.acceptOffer` while a manager's `updateNav` cycle is mid-flight and has already processed the listed loan's batch — a timing condition dependent on batch size and portfolio size but not otherwise gated. Since `createSaleOffer` is intentionally exempt from `_requireIdleNav`, no on-chain guard prevents this interleaving, and the repo's own audit already rates this at confidence 85 with 3 independent agent confirmations.

### Recommendation
Snapshot the vault's loan-ID set at `navStart` and verify at finalization that the snapshot still matches live ownership (reverting/restarting on mismatch) as already recommended in the repo's audit report, rather than relying on the currently updated live list plus in-loop self-healing, which cannot detect an NFT that leaves after being counted.

### Proof of Concept
1. Vault holds loan `L` valued at par, included in `_navLoanIds`.
2. Manager calls `updateNav(batchSize)` with `batchSize` small enough that `L` is processed and folded into `pendingNav` in the first batch, but the cycle spans multiple transactions before finalization.
3. Before the manager calls the next `updateNav` batch, the seller (vault, via portfolio manager) had earlier called `createSaleOffer` listing `L`; the named buyer now calls `LoansExchange.acceptOffer`, paying USDC directly to the vault and receiving `L`'s NFT — this does not touch `PortfolioVault` state at all.
4. Manager resumes `updateNav`; because `L` was already counted in `pendingNav` from step 2, and the sale proceeds are now sitting in `assetToken.balanceOf(vault)`, both values are additively combined at finalization: `lastNav = balanceOf(vault) + pendingNav - ... ` — `L`'s value is counted twice.
5. `lastNav` is now inflated by `L`'s value; subsequent `approveDeposit`/`approveRedemption` mint/redeem shares off this corrupted NAV. [3](#0-2)

  function updateNav(uint256 batchSize) external whenNotPaused {
    _requireManagerRole();
    require(batchSize > 0, ZeroAmount());

    ILoansNFT loansNFT_ = loansNFT;
    INavCalculator calculator_ = calculator;
    ILoans loans_ = loans;

    uint256 currentNonce = loansNFT_.ownershipNonce(address(this));
    uint256 currentConfigurationVersion = calculator_.configurationVersion();
    if (navStart == 0) {
      navStart = block.timestamp;
      lastOwnershipNonce = currentNonce;
      lastCalculatorConfigurationVersion = currentConfigurationVersion;
      emit NavComputationStarted(block.timestamp);
    } else if (
      currentNonce != lastOwnershipNonce ||
      currentConfigurationVersion != lastCalculatorConfigurationVersion ||
      block.timestamp - navStart > maxNavComputationTime
    ) {
      // Restart if the vault's NFT holdings changed mid-cycle, calculator
      // factors changed, or the previous computation took too long. The in-loop
      // ownership check below self-heals the list as it walks.
      navStart = block.timestamp;
      navCursor = 0;
      pendingNav = 0;
      lastOwnershipNonce = currentNonce;
      lastCalculatorConfigurationVersion = currentConfigurationVersion;
      emit NavComputationStarted(block.timestamp);
    }

    uint256 cursor = navCursor;
    uint64[] memory owned = new uint64[](batchSize);
    uint256 ownedCount;

    for (uint256 i; i < batchSize; ++i) {
      if (cursor >= _navLoanIds.length) break;
      uint64 loanId = _navLoanIds[cursor];
      // Treat a reverting `ownerOf` (e.g. burned token) the same as a foreign
      // owner so the list self-heals instead of bricking NAV computation.
      bool owns;
      try loansNFT_.ownerOf(uint256(loanId)) returns (address owner) {
        owns = owner == address(this);
      } catch {
        owns = false;
      }
      if (owns) {
        owned[ownedCount++] = loanId;
        unchecked {
          ++cursor;
        }
      } else {
        // Drop stale entry; swap-and-pop places a new entry at `cursor`, so do
        // not advance — the next iteration re-scans this slot.
        _removeLoanFromNav(loanId);
      }
    }

    if (ownedCount > 0) {
      // Trim the memory array to its used length before passing to the calculator.
      assembly {
        mstore(owned, ownedCount)
      }
      pendingNav += calculator_.getLoansValue(loans_, owned);
    }

    navCursor = cursor;

    // Finalize if we've processed all loans
    if (cursor >= _navLoanIds.length) {
      lastNav =
        assetToken.balanceOf(address(this)) +
        calculator_.applyPortfolioAdjustment(pendingNav) -
        totalPendingDepositAssets -
        totalClaimableRedeemAssets;
      lastNavUpdate = block.timestamp;
      navCursor = 0;
      pendingNav = 0;
      navStart = 0;
      emit NavUpdated(lastNav, block.timestamp);
    }
  }

[85] **1. NAV double-count when sale offer is accepted mid-batch updateNav**

`PortfolioVault.updateNav` · Confidence: 85 · [agents: 3]

**Description**
`createSaleOffer` lacks `_requireIdleNav()`, and the resulting offer can be settled by the buyer directly on `LoansExchange.acceptOffer` without any callback into the vault, so a vault-listed loan NFT can be transferred out of the vault while `updateNav` is partway through batched accumulation — `pendingNav` then double-counts the loan's discounted face value alongside the sale proceeds that are already sitting in `assetToken.balanceOf(vault)` at finalization, inflating `lastNav` and mispricing the next `approveDeposit` / `approveRedemption`.

**Fix**

Snapshot the vault's loan IDs at `navStart`, iterate the snapshot instead of re-reading `tokenOfOwnerByIndex` per batch, and verify at finalize that the snapshot still matches the live set; if anything moved in or out, revert and require the manager to restart with a fresh snapshot.
