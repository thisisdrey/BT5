### Title
Unguarded attacker-controlled array index in `ValidateMultiSign` precompile causes uncaught `ArrayIndexOutOfBoundsException` - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `ValidateMultiSign` precompiled contract parses the raw call data supplied by any TVM contract into a `DataWord[]` and then uses an **offset value taken directly from that same attacker-controlled data** (`words[3]`) to compute an index into the very array it was parsed from, before any bounds check is applied. This mirrors the Cedrus CVE-2026-68229 pattern: an index taken from untrusted, structured input is used to look up a fixed/finite array without first validating that the index is in range. [1](#0-0) 

### Finding Description
`ValidateMultiSign.execute()` parses caller-controlled bytes into `words = DataWord.parseArray(rawData)` and then does:

```java
int sigArraySize = words[words[3].intValueSafe() / WORD_SIZE].intValueSafe();
``` [2](#0-1) 

`words[3]` is fully attacker-controlled (it is the raw `abi.encode`d offset field for the signature array, supplied via a `TriggerSmartContract` call to any contract that invokes this precompile, e.g. via `staticcall`/`call` to the `ValidateMultiSign` address). `intValueSafe()` returns an `int` derived from a 256-bit value truncated/clamped, so it can be made arbitrarily large (or a value that, divided by `WORD_SIZE` (32), still exceeds `words.length`). There is no check that `words[3].intValueSafe() / WORD_SIZE < words.length` before this index is used to read `words[...]`.

This is the exact bug class described in the report: an index derived from untrusted structured data (H.264 `ref_pic_list` entries in Cedrus vs. ABI-offset words here) is used to index a fixed-size backing array (`decode->dpb[]` in Cedrus vs. `words[]` here) without validating the index is in range, causing an out-of-bounds access.

Notably, the sibling precompile `BatchValidateSign` performs the identical unsafe pattern (`words[words[1].intValueSafe() / WORD_SIZE]`), but its `execute()` wraps the whole body in `try { return doExecute(data); } catch (Throwable t) { ... return Pair.of(true, new byte[WORD_SIZE]); }`, silently catching any `ArrayIndexOutOfBoundsException` and returning a safe dummy result. [3](#0-2) 

`ValidateMultiSign.execute()` has no such outer guard — its only `try/catch` is scoped inside the `account != null` block, well *after* the vulnerable indexing at line 1067, and it only catches exceptions thrown while iterating recovered signatures, not the earlier array lookup. [4](#0-3) 

An `ArrayIndexOutOfBoundsException` thrown here is therefore an unhandled `RuntimeException` that propagates out of the precompile, through TVM opcode dispatch and `VMActuator`, up into transaction execution during block application.

### Impact Explanation
If this exception is not caught somewhere generically higher up the call stack (VM opcode execution loop / `VMActuator.execute`), it will propagate as an unexpected runtime exception during `Manager` block application for any node processing a block containing such a transaction, causing that node to fail to apply the block — a denial-of-service / potential chain-halt condition reachable by any account that can deploy or call a contract invoking `ValidateMultiSign` with a crafted offset. This is only reachable when `VMConfig.allowTvmSelfdestructRestriction()` is enabled (a chain-parameter-gated feature), so the exploitability is contingent on that flag being active on the target network.

### Likelihood Explanation
Reaching this code path requires only a single `TriggerSmartContract` transaction from an unprivileged account calling (or deploying and calling) a contract that invokes the `ValidateMultiSign` precompiled contract address with a malformed 4th-word offset — no special privileges, signatures, or witness/SR status are needed. The precondition is that `allowTvmSelfdestructRestriction` is enabled on the chain, which I could not verify is default-on or off from the available context.

### Recommendation
Add an explicit bounds check before using an attacker-supplied offset to index into `words[]`, mirroring the Cedrus fix: validate `words[3].intValueSafe() / WORD_SIZE < words.length` (and `>= 0`) prior to the lookup at line 1067, returning `Pair.of(true, DATA_FALSE)` on failure instead of performing the raw array access. Apply the same fix to `extractSigArray`/`extractBytesArray`/`extractBytes32Array` call sites and consider wrapping `ValidateMultiSign.execute()` in the same defensive `try/catch(Throwable)` pattern already used in `BatchValidateSign.execute()`.

### Proof of Concept
1. Deploy a contract whose bytecode performs a raw `staticcall`/`call` to the `ValidateMultiSign` precompiled contract address, passing calldata equivalent to:
   - `words[0]` = target address
   - `words[1]` = permissionId
   - `words[2]` = data
   - `words[3]` = a large value (e.g., `0xFFFFFFFF`) intended as the byte-offset to the signature array
2. Invoke the contract via a normal `TriggerSmartContract` transaction from any funded account.
3. With `allowTvmSelfdestructRestriction` enabled, execution reaches `words[words[3].intValueSafe() / WORD_SIZE]` [5](#0-4)  with an index far beyond `words.length`, throwing `ArrayIndexOutOfBoundsException` that is not caught locally, unlike the equivalent path in `BatchValidateSign`.

Note: I was unable to confirm within the indexed codebase whether `VMActuator`/opcode dispatch has a generic `catch (Throwable/RuntimeException)` wrapper that would convert this into a normal transaction revert rather than an unhandled crash; this affects the final severity/likelihood assessment. If such a generic catch exists elsewhere in the call chain, the impact would be limited to the calling transaction failing rather than a node crash.
