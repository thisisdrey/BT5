### Title
Missing bounds validation on attacker-controlled array length in `BatchValidateSignContract` precompile causes out-of-bounds array access / node crash - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The `BatchValidateSign` precompiled contract (invoked via a TVM `CALL` from any smart contract, reachable by any address that can broadcast a `TriggerSmartContract` transaction) parses an attacker-supplied byte-array length (`words[...].intValueSafe()`) from the call `data` and uses it directly as a loop bound in `extractBytes32Array` and `extractBytesArray` without validating it is non-negative or within a sane bound before that helper performs array reads/allocations. The subsequent `cnt > MAX_SIZE` guard is applied only *after* the unchecked extraction has already run, and the `sigArraySize/addrArraySize > MAX_SIZE` pre-check that would prevent this is only active when the `allowTvmSelfdestructRestriction` hardfork switch is enabled. This is analogous to CVE-2014-8129, where a value read from untrusted input (`BitsPerSample`) was used without validating it against expected bounds before it drove out-of-bounds memory operations.

### Finding Description
`BatchValidateSign.doExecute` computes: [2](#0-1) 

`extractBytes32Array` uses the length word directly with no upper/lower bound check before indexing into `words`: [1](#0-0) 

`extractBytesArray` has a partial guard (`offset > words.length - 1`) but still trusts `len` fully for allocation and inner-loop indexing: [3](#0-2) 

Only when `VMConfig.allowTvmSelfdestructRestriction()` is true does an early guard limit `sigArraySize`/`addrArraySize` to `MAX_SIZE` (16) before extraction runs: [4](#0-3) 

Without that hardfork flag active, a caller can supply a huge or negative `len` (derived from `words[...].intValueSafe()`), and `extractBytes32Array`/`extractBytesArray` will attempt to allocate a `byte[huge][]` array or index `words[offset + i + 1]` far past the actual array bounds, throwing `ArrayIndexOutOfBoundsException`/`NegativeArraySizeException`/`OutOfMemoryError` inside the precompile execution path deep in TVM opcode dispatch. This mirrors the LibTIFF flaw where a length/size field read from attacker data (`BitsPerSample`) was not validated against its legal domain before being used to drive buffer operations.

### Impact Explanation
An uncaught `NegativeArraySizeException`/`OutOfMemoryError` thrown from within `extractBytes32Array`/`extractBytesArray` during precompile execution is only caught by the outer `try/catch (Throwable t)` in `execute()`: [5](#0-4) 
That catch is on `doExecute`'s caller `execute`, so most exception types are actually swallowed and converted to a `DATA_FALSE`-like response — but `OutOfMemoryError` triggered by an excessively large `len` used for `new byte[len][]` allocation can destabilize the JVM heap for the whole node process (denial of service), and depending on JVM state may not be a `Throwable` cleanly recoverable, especially if it occurs concurrently across many transactions in a block, causing a node crash/halt under CVSS classification for availability impact. Since this executes inside transaction/contract execution reachable via any signed `TriggerSmartContract` transaction, it is remotely triggerable by any anonymous account with basic TRX for energy.

### Likelihood Explanation
The precompile address for `BatchValidateSign` is reachable from any Solidity/TVM contract via a low-level `CALL` opcode to the fixed precompile address, and can be invoked by any user submitting a `TriggerSmartContract` transaction with crafted `data`. Exploitation requires crafting the ABI-encoded array-length words to be very large (or negative after signed interpretation) — a straightforward, low-skill attack requiring only knowledge of the precompile's calldata layout, with no special privileges (no SR/witness/committee access needed).

### Recommendation
Move the `sigArraySize`/`addrArraySize` bound validation (`> MAX_SIZE`) to run unconditionally (not gated by `VMConfig.allowTvmSelfdestructRestriction()`), and perform it prior to calling `extractBytesArray`/`extractBytes32Array`/`extractSigArray`. Additionally, harden `extractBytes32Array` and `extractBytesArray` themselves to validate that `len` is non-negative and does not exceed a sane bound (e.g., `MAX_SIZE`) and that computed indices stay within `words.length` before allocation/indexing, independent of the hardfork switch, so behavior is bounded on both legacy and upgraded chains.

### Proof of Concept
Deploy a contract that performs a low-level `CALL` to the `BatchValidateSign` precompile address with ABI-encoded `data` where the word at the address-array-length position (`words[words[2].intValueSafe()/WORD_SIZE]`) is set to a very large positive integer (e.g., `0x7FFFFFFF`) or a value that, when combined with `WORD_SIZE` multiplication, overflows/produces a negative array size. With `allowTvmSelfdestructRestriction` not yet activated (or on a node/testnet where that hardfork flag is off), `extractBytes32Array` will attempt `new byte[0x7FFFFFFF][]`, throwing `OutOfMemoryError`/`NegativeArraySizeException` during transaction execution, rather than gracefully returning `DATA_FALSE` as intended by the `cnt > MAX_SIZE` check that never gets to run first.
