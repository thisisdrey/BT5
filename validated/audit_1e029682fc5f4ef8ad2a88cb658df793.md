### Title
Replay-window bypass via lock release between `Bits.Check` and `Bits.Update` allows duplicate packet delivery - (File: connection_state.go)

### Summary
### Finding Description
`ConnectionState.Decrypt` (and `VerifyRelay`) implement anti-replay protection with a **check-then-act** pattern that is not atomic: the mutex protecting the replay window is released between the "check" and the "commit" step, and the expensive decrypt operation happens in between while the mutex is not held. [1](#0-0) 

The sequence is:
1. `cs.decryptLock.Lock(); cs.window.Check(...); cs.decryptLock.Unlock()` — checks whether `messageCounter` is unseen, then immediately releases the lock.
2. `cs.dKey.DecryptDanger(...)` — the actual AEAD decrypt runs with **no lock held**.
3. `cs.decryptLock.Lock(); cs.window.Update(...); cs.decryptLock.Unlock()` — only now is the counter actually marked as seen.

This mirrors the reNFT bug class exactly: a state-changing/side-effecting operation (here, decrypting and — critically — allowing the caller to proceed to deliver the packet to the firewall/TUN) is performed using a validity check that was true only at a *prior* point in time, and the actual "commit" of that validity (marking the nonce as consumed / marking the order as existing) happens only afterward. Because the lock is dropped for the duration of `DecryptDanger`, two goroutines processing the *same* duplicated ciphertext (nebula runs multiple UDP-read queues, so packets for the same tunnel legitimately execute `readOutsidePackets`/`Decrypt` concurrently) can both pass `Check` before either has called `Update`, exactly analogous to the attacker creating the rental order inside the callback window before `STORE.removeRentals` runs.

### Impact Explanation
If two copies of the same encrypted data-plane packet are received (attacker-supplied duplicate, or a duplicate that arises naturally in transit and gets processed by two reader goroutines before the first `Update` lands), both can pass `window.Check`, both successfully decrypt (the nonce being reused for decryption does not fail, unlike encryption misuse), and both get delivered to `f.firewall.Drop` and the TUN device / relay-forward path in `outside.go`. This is a replay-protection bypass: the same authenticated packet can be processed twice, defeating the guarantee the replay window is meant to provide (`ReplayWindow`/`Bits` docstring explicitly frames this as anti-replay). Depending on the payload this can cause duplicate delivery of application data, or in the relay path (`VerifyRelay`) duplicate forwarding of relayed traffic through `SendVia`.

### Likelihood Explanation
Nebula's `Interface` reads inbound UDP packets across multiple queues/goroutines (`readOutsidePackets` is invoked with a `q` queue index), so packets destined to the same `hostinfo`/tunnel are not serialized before reaching `ConnectionState.Decrypt`. An attacker with no CA-signed certificate, who is only capable of observing/duplicating an already-established tunnel's ciphertext on the wire (a standard on-path/duplicate-UDP capability, not requiring any cryptographic material), can send the same UDP datagram twice in close succession to trigger the race window. Because `decryptLock` is dropped exactly around the costly `DecryptDanger` call, the race window is non-trivial and reproducible under load or with a duplicated small burst.

### Recommendation
Perform the "reserve the slot" step before decrypting and finalize/rollback under a single critical section, rather than doing a separate speculative `Check` and a later, unlocked `Update`:
- Hold `decryptLock` across the entire `Check → Decrypt → Update` sequence for the same connection (serializing decrypt attempts per `ConnectionState`), or
- Atomically "claim" the counter bit (equivalent to `Update`) before decrypting, and only decrypt after the claim succeeds, rolling back the claim if decryption subsequently fails.
This removes the window in which two concurrent decrypt attempts for the same counter can both be judged valid.

### Proof of Concept
Not executable in ask-only mode without filesystem/terminal access. Conceptually: run two goroutines that both call `hostinfo.ConnectionState.Decrypt` with the same `messageCounter` and same ciphertext, delaying the second `Lock()` call inside `Check` just long enough (e.g. by injecting a hook/sleep in `DecryptDanger`) to let the first goroutine's `Check` complete and `Unlock` before the second goroutine's `Check` runs; both `Check` calls will return `true`, and both decrypts will succeed, demonstrating the double-acceptance of a single (duplicated) message counter. Confirming this in a live environment requires a Devin session with access to run the Go test suite / write a targeted concurrency test against `connection_state.go` and `bits.go`.

	var err error
