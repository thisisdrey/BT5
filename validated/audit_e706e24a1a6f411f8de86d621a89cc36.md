### Title
Unchecked `new_authority` in account-transfer instructions allows permanent self-lock of a MarginfiAccount and its funds - (File: `programs/marginfi/src/instructions/marginfi_account/transfer_account.rs`)

### Summary
The `transfer_to_new_account` and `transfer_to_new_account_pda` instruction handlers accept a `new_authority` account parameter and write it directly into the new `MarginfiAccount.authority` field with no validation that it is a non-default (non-zero) `Pubkey`. This mirrors the reported bug class: an address-type input parameter is stored without a zero-value check, and the resulting mis-set field has no other on-chain remediation path.

### Finding Description
`TransferToNewAccount`/`TransferToNewAccountPda` declare `new_authority` as a completely unvalidated account: [1](#0-0) [2](#0-1) 

The value is used unchecked to initialize the new account's authority: [3](#0-2) [4](#0-3) [5](#0-4) 

Neither handler checks `new_authority.key() != Pubkey::default()` (or any other invalid/burn value) before finalizing the migration and permanently disabling the old account: [6](#0-5) 

Notably, the off-chain CLI tooling (`p0-cli`) *does* perform this check client-side, confirming that the project itself recognizes zero-authority as an invalid/dangerous state that must be rejected, but this guard is absent from the on-chain program: [7](#0-6) 

Once `transfer_to_new_account`/`transfer_to_new_account_pda` completes, the old account is disabled and its position data (lending balances, everything) is moved into the new account: [6](#0-5) 
If `new_authority` was `Pubkey::default()` (or any other key nobody controls), no private key exists that can ever sign for that new `MarginfiAccount`. There is no admin-level or user-level instruction elsewhere in the codebase that can re-point `MarginfiAccount.authority` for the new account, other than another `transfer_to_new_account*` call, which itself requires a signature from the very `authority` that is now unrecoverable.

### Impact Explanation
This results in a **permanent, unrecoverable freeze/lock of user funds**: all collateral/position value in the account (deposits, LP shares, etc.) becomes permanently inaccessible, since the account's `authority` signer can never be produced. This meets the "permanent lock/freeze" impact bar allowed by the validation rules. It affects the standard user-facing account-lifecycle path (`transfer_to_new_account`/`transfer_to_new_account_pda`), which is fully reachable by any unprivileged account authority — no admin/privileged access is required to trigger it.

### Likelihood Explanation
The bug is trivially triggerable: any account authority calling `transfer_to_new_account` (or the PDA variant) with `new_authority = Pubkey::default()` (or any other key with an unknown/unrecoverable private key, e.g. a burn address) immediately and irreversibly locks their own account's funds. Because this is purely a self-directed action (the old account's `authority` must already sign, per `is_signer_authorized`), it cannot be used to attack another user's account directly — it can only lock the caller's own account. This lowers exploit value as a griefing vector against third parties, but it remains a real permanent-fund-loss bug: e.g. a compromised or malicious front-end, a buggy integrator, or a user's own transaction-building mistake (typos, misconfigured `new_authority` derivation) can permanently destroy funds with no recovery path, which is exactly the class of defect the reported issue describes (unchecked address input with no redeployment/remediation option).

### Recommendation
Add an explicit check in both `transfer_to_new_account` and `transfer_to_new_account_pda` that rejects `ctx.accounts.new_authority.key() == Pubkey::default()` (and ideally any well-known burn/system addresses) before finalizing the migration, matching the guard already present in the `p0-cli` client: [8](#0-7) 

### Proof of Concept
1. User creates a `MarginfiAccount` and deposits funds into a bank.
2. User (or a malicious/compromised client) calls `transfer_to_new_account` with `new_authority = Pubkey::default()`: [9](#0-8) 
3. The instruction succeeds: `new_account.authority` is set to `Pubkey::default()`, `old_account` is flagged `ACCOUNT_DISABLED` and its `lending_account` zeroed out, with all balances now only referenced from the new account: [6](#0-5) 
4. No instruction in the program can ever authorize actions on the new `MarginfiAccount` because no signer can produce the `Pubkey::default()` signature — all deposited funds tied to that account are permanently frozen.
