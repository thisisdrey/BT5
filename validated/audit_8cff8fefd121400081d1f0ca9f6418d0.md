### Title
Dust-transfer griefing fills a victim's `depositTokensOfAccount`/`debtTokensOfAccount` list to `MAX_TOKENS_PER_USER`, DoS-ing deposits, borrows, and receives - ([File: contracts/Pool.sol])

### Summary
CVE-2018-3144 is an unauthenticated availability bug: a remote attacker with no privileges can crash/hang the service. The Metronome analog is a liveness/DoS flaw in the per-account token-list bookkeeping. `Pool` caps `debtTokensOfAccount + depositTokensOfAccount` at `MAX_TOKENS_PER_USER = 30` and reverts with `UserReachedMaxTokens` once the cap is hit (`onlyIfAdditionWillNotReachMaxTokens`, Pool.sol:143-148). Entries are added to a victim's list by *anyone*, because `DepositToken._transfer` calls `pool.addToDepositTokensOfAccount(recipient_)` whenever the recipient's balance moves from 0 (DepositToken.sol:517-520). An unprivileged attacker can therefore push 1-wei dust amounts of every listed deposit token to a target account, permanently reverts on that victim's `deposit()`, `DebtToken.issue()/mint()`, and any inbound `transfer`/`seize` of a new token type — a repeatable crash of the victim's core protocol operations.

### Finding Description
`DepositToken._transfer` (DepositToken.sol:511-525) adds the deposit token to `recipient_`'s list whenever `_recipientBalanceBefore == 0 && amount_ > 0`, and removes it from the sender's list when the sender's balance hits 0. `Pool.addToDepositTokensOfAccount` (Pool.sol:216-220) enforces `onlyIfAdditionWillNotReachMaxTokens`, which reverts if `debtTokensOfAccount.length + depositTokensOfAccount.length >= 30` (Pool.sol:144-146). The same check gates `addToDebtTokensOfAccount` (Pool.sol:204-208), which `DebtToken` calls when an account's debt balance goes from 0 to non-zero on `issue`/`mint`/`flashIssue`.

`addDepositToken` allows up to `MAX_TOKENS_PER_USER` (30) deposit tokens in `depositTokens` (Pool.sol:703), so on a fully populated pool the attacker has enough distinct tokens to fill the victim's list entirely.

Attack trace (all calls public, no roles needed):
1. Attacker deposits dust amounts of each underlying into each listed `DepositToken` via `deposit(amount_, attacker)` (DepositToken.sol:211-237) to obtain small msdTOKEN balances.
2. Attacker calls `transfer(victim, 1)` on every deposit token the victim doesn't hold. `transfer` only checks `_revertIfLocked(msg.sender, amount)` on the *sender* (DepositToken.sol:348-354); nothing checks or throttles the recipient side. Each call adds one entry to `depositTokensOfAccount[victim]` until it reaches 30.
3. Now: `victim.deposit(...)` on any new collateral reverts in `_mint`'s downstream `addToDepositTokensOfAccount`; `victim` cannot `issue`/`mint` a new synthetic (`addToDebtTokensOfAccount` reverts); `onBehalfOf_` deposits to the victim revert; liquidations and inbound transfers that would add a new token to the victim also revert.

Checks that do *not* stop it: `transfer`/`transferFrom` have no recipient opt-in and no minimum-amount (dust) guard; `nonReentrant`/`whenNotPaused` are irrelevant; SynthContext/`_msgSender` paths don't change the accounting.

### Impact Explanation
Temporary freezing of funds / liveness failure for the victim. While the list is saturated, the victim cannot open positions in new collateral types, cannot mint/issue any new synthetic debt, and cannot even receive new deposit tokens (inbound transfers revert). If the victim's position is deteriorating, they are blocked from adding a *different* collateral to restore health, and a liquidator seizing a token type the liquidator already maxed out can also be forced to fail. This mirrors the CVE class exactly: an unauthenticated, unprivileged remote actor causes repeatable denial of service of core operations.

Severity is bounded: the victim can recover by transferring each dust balance out in full (balance → 0 triggers `removeFromDepositTokensOfAccount`, DepositToken.sol:522-525), so funds aren't permanently locked — hence a Medium-style DoS, not critical.

### Likelihood Explanation
- Attacker requirements: none beyond gas and dust amounts of each listed underlying (attacker may use flash loans/donations to acquire msdTOKENs, or even `transferFrom` with victim-innocent approval — not needed though).
- Preconditions: pool must have enough listed deposit tokens to reach the cap; deployed pools support up to 30, and even partial filling combines with the victim's existing entries.
- Cost: one `transfer` per entry plus collateral dust; fully repeatable against any account, including contracts that can't easily send tokens back (e.g., SmartFarmingManager-held or smart-wallet accounts), making the freeze effectively longer for non-EOA victims.

### Recommendation
- Move the cap check off the recipient path: do not revert in `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` when a *transfer/seize* is the trigger; instead enforce `MAX_TOKENS_PER_USER` only on user-initiated actions (`deposit`, `issue`/`mint`), or remove the cap and bound iteration via pagination in `debtPositionOf`/`depositOf`/`debtOf`.
- Alternatively, auto-remove on receipt: if the recipient list is full, either reject only genuinely new positions initiated by the victim, or allow the pool to merge/ignore dust below a minimum-balance threshold so spam entries can't be created.
- Add a minimum first-deposit amount per deposit token to raise the dust-spam cost.

### Proof of Concept
Foundry fork test (pool with N ≥ enough listed deposit tokens to push victim past 30 combined entries):

```solidity
// SPDX-License-Identifier: MIT
pragma solidity 0.8.24;

import "forge-std/Test.sol";
import {Pool} from "../contracts/Pool.sol";
import {IDepositToken} from "../contracts/interfaces/IDepositToken.sol";
import {IERC20} from "../contracts/dependencies/openzeppelin/token/ERC20/IERC20.sol";

contract MaxTokensGriefingTest is Test {
    Pool pool;                       // deployed Pool proxy
    address victim = address(0xVIC);
    address attacker = address(0xATT);

    function test_dustFillsVictimList_blocksDepositAndIssue() public {
        address[] memory dts = pool.getDepositTokens();
        // need enough tokens so that victim's (debt + deposit) entries hit 30
        uint256 needed = pool.MAX_TOKENS_PER_USER()
            - pool.getDebtTokensOfAccount(victim).length
            - pool.getDepositTokensOfAccount(victim).length;
        require(dts.length >= needed, "not enough listed collaterals");

        for (uint256 i; i < needed; ++i) {
            IDepositToken dt = IDepositToken(dts[i]);
            IERC20 underlying = dt.underlying();
            deal(address(underlying), attacker, 1);
            vm.startPrank(attacker);
            underlying.approve(address(dt), 1);
            dt.deposit(1, attacker);        // mint ~1 wei of msdTOKEN to attacker
            dt.transfer(victim, 1);         // adds dts[i] to victim's list — no consent
            vm.stopPrank();
        }

        assertEq(
            pool.getDebtTokensOfAccount(victim).length
                + pool.getDepositTokensOfAccount(victim).length,
            pool.MAX_TOKENS_PER_USER()
        );

        // victim can no longer deposit a new collateral type
        IDepositToken newDt = IDepositToken(dts[needed]); // a token victim doesn't hold
        IERC20 newUnder = newDt.underlying();
        deal(address(newUnder), victim, 1e18);
        vm.startPrank(victim);
        newUnder.approve(address(newDt), 1e18);
        vm.expectRevert(Pool.UserReachedMaxTokens.selector);
        newDt.deposit(1e18, victim);
        vm.stopPrank();

        // victim cannot mint a new synthetic either (addToDebtTokensOfAccount reverts)
        // debtToken.issue(...) -> UserReachedMaxTokens
    }
}
```

Recovery path (shows why it's temporary, not permanent): victim calls `transfer(attacker, dustBalance)` on each spam token until balance is 0, which triggers `removeFromDepositTokensOfAccount` and frees the slots — at the cost of gas and, for contract-based victims, possibly no practical path at all.
