## Finding

### Title
Missing slippage protection in `ExchangeInjectContract`/`ExchangeWithdrawContract` enables sandwich attacks on TRX/TRC10 liquidity pools - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`)

### Summary
The Bancor-style exchange pools in java-tron support three operations on a token pair: swap (`ExchangeTransactionContract`), add liquidity (`ExchangeInjectContract`), and remove liquidity (`ExchangeWithdrawContract`). The swap path correctly implements a caller-supplied slippage bound (`expected`), but the add/remove-liquidity paths compute counterparty amounts purely from the live pool ratio with no caller-supplied bound at all — the exact "unused slippage params" bug class described in the report, except here the parameter is entirely absent rather than merely ignored.

### Finding Description
`ExchangeInjectContract` only carries `owner_address`, `exchange_id`, `token_id`, and `quant`; [1](#0-0)  there is no minimum/maximum bound field. In `ExchangeInjectActuator.execute`, the counterpart token amount the caller must also deposit is derived solely from the current on-chain pool ratio at execution time: `anotherTokenQuant = floorDiv(multiplyExact(secondTokenBalance, tokenQuant), firstTokenBalance)` (or the symmetric case), and the account is unconditionally debited that computed amount. [2](#0-1) 

Compare this to `ExchangeTransactionActuator` (swap), where the contract carries an explicit `expected` field [3](#0-2)  and `doValidate()` explicitly rejects the transaction if the computed output falls below it: `if (anotherTokenQuant < tokenExpected) { throw new ContractValidateException("token required must greater than expected"); }`. [4](#0-3) 

`ExchangeWithdrawContract` has the identical structure/limitation as `ExchangeInjectContract` (`owner_address`, `exchange_id`, `token_id`, `quant`, no bound field), [5](#0-4)  confirmed by the absence of any `expected`-like field in `ExchangeWithdrawActuator.java`.

Because Inject/Withdraw math is deterministic on the pool ratio at execution time and no bound is enforced, an attacker who observes a pending `ExchangeInjectContract` (or `ExchangeWithdrawContract`) transaction in the mempool can:
1. Front-run it with an `ExchangeTransactionContract` swap that shifts the first/second token ratio in the pool.
2. Let the victim's inject transaction execute against the manipulated ratio, forcing the victim to deposit a distorted (larger than fair-value) amount of the counterpart token, or receive a distorted (smaller than fair-value) amount when withdrawing.
3. Back-run with a reverse swap to restore the ratio and pocket the difference, extracted from the victim's deposit/withdrawal.

### Impact Explanation
This is a classic sandwich/MEV attack vector reachable by any unprivileged transaction broadcaster who can observe the mempool and submit their own signed `ExchangeTransactionContract` swaps immediately before and after a victim's `ExchangeInjectContract`/`ExchangeWithdrawContract`. It results in unauthorized value extraction from liquidity providers using TRON's built-in TRX/TRC10 exchange feature — a concrete theft-of-funds impact for any account using `wallet/exchangeinject` or `wallet/exchangewithdraw`.

### Likelihood Explanation
Likelihood is high for any observer with mempool visibility and enough capital to move the pool ratio meaningfully within one or two blocks: SR block production ordering and the low cost of TRX/TRC10 swaps make this economically feasible, and no special privilege (SR/witness/committee) is required — only a signed swap transaction.

### Recommendation
Add slippage-bound fields (e.g., `min_expected_amount`/`max_expected_amount`) to `ExchangeInjectContract` and `ExchangeWithdrawContract`, mirroring the `expected` pattern already used in `ExchangeTransactionContract`, and enforce them in `ExchangeInjectActuator`/`ExchangeWithdrawActuator`'s `doValidate()`/`execute()` before committing balance changes.

### Proof of Concept
1. Attacker observes a pending `ExchangeInjectContract` from victim depositing `tokenQuant` of `firstToken`.
2. Attacker submits an `ExchangeTransactionContract` swap that shifts `firstTokenBalance`/`secondTokenBalance` in the pool, executed before the victim's tx (e.g. via higher energy/fee or timing).
3. Victim's inject executes with the manipulated ratio: `anotherTokenQuant = floorDiv(multiplyExact(secondTokenBalance, tokenQuant), firstTokenBalance)` [6](#0-5)  now computes an inflated `anotherTokenQuant`, debited unconditionally from the victim's account without any check against a caller-supplied minimum/maximum.
4. Attacker submits a reverse swap restoring the ratio, realizing the value difference extracted from the victim's deposit.
