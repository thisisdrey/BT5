### Title
Legacy `pallet-staking::withdraw_unbonded` lets stakers withdraw unbonding chunks before pending offences are processed, evading slashes that `pallet-staking-async` now blocks - (File: `substrate/frame/staking/src/pallet/mod.rs`)

### Summary
The C4 report's core broken invariant is: a withdrawal path uses a weaker/looser liability check (`bareCollateral`) than the check the protocol actually relies on to determine whether a position is still liable (`weightedCollateral` used in liquidation), letting an account withdraw funds it should still be exposed to. The Polkadot SDK analog is the divergence between `pallet-staking` (legacy) and `pallet-staking-async` on `withdraw_unbonded`: the async pallet was hardened specifically to prevent withdrawing unbonded funds while slashes from unprocessed offences are still outstanding, but the legacy `pallet-staking` pallet, which is still present and used in this repository, has no equivalent guard.

### Finding Description
`prdoc/stable2509/pr_9079.prdoc` documents a fix titled "Prevent withdrawals while processing offences" for `pallet-staking-async` [1](#0-0) . It explicitly states the pre-fix behavior was dangerous: "Withdrawals are blocked if there are unapplied slashes from the previous era" and "withdrawals are restricted to the minimum of the active era and the last fully processed offence era" — a defensive measure "to maintain slashing guarantees ... even in extreme edge cases" [2](#0-1) .

`substrate/frame/staking-async/src/lib.rs` documents this new withdrawal-era calculation as `earliest_era_to_withdraw = min(active_era, last_fully_processed_offence_era + BondingDuration)`, i.e. withdrawal eligibility is bound to the same slashing-liability accounting (`OffenceQueue`, `UnappliedSlashes`) used for actually applying slashes [3](#0-2) . The corresponding guard strings `UnappliedSlashesInPreviousEra`, `earliest_era_to_withdraw`, and `OffenceTooOld` only exist in `substrate/frame/staking-async/src/pallet/impls.rs`, `substrate/frame/staking-async/src/pallet/mod.rs`, `substrate/frame/staking-async/src/lib.rs`, and the staking-async test suite — they do not appear anywhere in `substrate/frame/staking` (the legacy pallet). This confirms that the legacy `pallet-staking::withdraw_unbonded` extrinsic (declared at `substrate/frame/staking/src/pallet/mod.rs`) still uses only era-elapsed unlocking-chunk logic without checking whether there are unprocessed/unapplied offences that could still slash the unlocking funds — exactly the "different collateral check for withdrawal vs. the check used to determine real liability" pattern from the original report.

Both `pallet-staking::StakingLedger::slash` and `pallet-staking-async::StakingLedger::slash` implement proportional slashing across `active` and `unlocking` chunks based on which era the offence occurred in [4](#0-3) [5](#0-4) . In `pallet-staking-async`, `pr_11999.prdoc` further shows the team explicitly fixed a bug where "the ledger... uses the offence era (not the slash application era) to decide which unlocking chunks are still in range" because using the wrong era caused a "disproportionate" slash split [6](#0-5) , and a regression test `apply_slash_paths_agree_on_unbonding_chunk_at_offence_era` was added to keep the two slash-application code paths consistent [7](#0-6) . None of this offence-era-aware accounting, nor the withdrawal-blocking guard, exists in the legacy `pallet-staking`.

### Impact Explanation
A validator/nominator whose misbehavior (offence) has occurred but whose slash has not yet been fully processed (queued, deferred, or delayed beyond the normal per-era processing window) can call `withdraw_unbonded` on legacy `pallet-staking` once the nominal unlock era has elapsed, withdrawing the full unlocking-chunk balance from their stash before the pending slash is applied to that chunk. This is a direct value-theft/underpayment-to-the-protocol analog to the report: funds that should still back a liability (the pending slash) are removed from exposure, permanently reducing the amount the protocol can recover — the same "withdraw before liability check catches up" primitive as withdrawing uncollateralized deposits while a position is liquidable.

### Likelihood Explanation
This requires only a normal unprivileged staker/nominator interaction (calling `unbond` then `withdraw_unbonded` once the standard bonding duration passes) combined with the pre-existing, permissionless, defensively-documented possibility that offence/slash processing can lag behind (explicitly acknowledged in `pr_9079.prdoc` as occurring when "all unapplied slashes for an era could not be applied within one era worth of blocks"). No malicious validator, relayer, or governance action is needed — an attacker only needs an offence to exist against them and race the withdrawal against slash processing, which is exactly the scenario `pallet-staking-async` was hardened against.

### Recommendation
Port the same defensive restriction that was added to `pallet-staking-async` (`UnappliedSlashesInPreviousEra` guard and the `earliest_era_to_withdraw = min(active_era, last_fully_processed_offence_era + BondingDuration)` logic) into legacy `pallet-staking::withdraw_unbonded`, so that unbonding chunks cannot be withdrawn while offences that could still slash them remain unprocessed, matching the invariant the report demands: the withdrawal-path liability check must be at least as strict as the check used when the liability is actually realized (slash application).

### Proof of Concept
1. Bond stake in `pallet-staking` (legacy) as a validator/nominator; call `unbond` to create an unlocking chunk maturing at era `E`.
2. Have an offence reported against the account close to era `E` such that its slash is deferred/queued and not yet applied by the time `E` is reached (this is an acknowledged possible delay per `pr_9079.prdoc`).
3. At era `E`, call `withdraw_unbonded`; because legacy `pallet-staking` has no `UnappliedSlashesInPreviousEra`/`earliest_era_to_withdraw` guard (confirmed absent via search — these identifiers exist only in `pallet-staking-async`), the withdrawal succeeds and the unlocking chunk balance leaves the stash.
4. When the deferred slash is later applied, it can no longer act on the withdrawn balance, so the protocol recovers less than intended — mirroring the original report's "withdraw uncollateralized deposit while position is liquidable" outcome.

	///
	/// This implements a proportional slashing system, whereby we set our preference to slash as
	/// such:
	///
	/// - If any unlocking chunks exist that are scheduled to be unlocked at `slash_era +
	///   bonding_duration` and onwards, the slash is divided equally between the active ledger and
	///   the unlocking chunks.
	/// - If no such chunks exist, then only the active balance is slashed.
	///
	/// Note that the above is only a *preference*. If for any reason the active ledger, with or
	/// without some portion of the unlocking chunks that are more justified to be slashed are not
	/// enough, then the slashing will continue and will consume as much of the active and unlocking
	/// chunks as needed.
	///
	/// This will never slash more than the given amount. If any of the chunks become dusted, the
	/// last chunk is slashed slightly less to compensate. Returns the amount of funds actually
	/// slashed.
	///
	/// `slash_era` is the era in which the slash (which is being enacted now) actually happened.
	///
	/// This calls `Config::OnStakingUpdate::on_slash` with information as to how the slash was
	/// applied.
	pub fn slash(
		&mut self,
		slash_amount: BalanceOf<T>,
		minimum_balance: BalanceOf<T>,
		slash_era: EraIndex,
	) -> BalanceOf<T> {
		if slash_amount.is_zero() {
			return Zero::zero();
		}

		use sp_runtime::PerThing as _;
		let mut remaining_slash = slash_amount;
		let pre_slash_total = self.total;

		// for a `slash_era = x`, any chunk that is scheduled to be unlocked at era `x + 28`
		// (assuming 28 is the bonding duration) onwards should be slashed.
		let slashable_chunks_start = slash_era.saturating_add(T::BondingDuration::get());

		// `Some(ratio)` if this is proportional, with `ratio`, `None` otherwise. In both cases, we
		// slash first the active chunk, and then `slash_chunks_priority`.
		let (maybe_proportional, slash_chunks_priority) = {
			if let Some(first_slashable_index) =
				self.unlocking.iter().position(|c| c.era >= slashable_chunks_start)
			{
				// If there exists a chunk who's after the first_slashable_start, then this is a
				// proportional slash, because we want to slash active and these chunks
				// proportionally.

				// The indices of the first chunk after the slash up through the most recent chunk.
				// (The most recent chunk is at greatest from this era)
				let affected_indices = first_slashable_index..self.unlocking.len();
				let unbonding_affected_balance =
					affected_indices.clone().fold(BalanceOf::<T>::zero(), |sum, i| {
						if let Some(chunk) = self.unlocking.get(i).defensive() {
							sum.saturating_add(chunk.value)
						} else {
							sum
						}
					});
				let affected_balance = self.active.saturating_add(unbonding_affected_balance);
				let ratio = Perquintill::from_rational_with_rounding(
					slash_amount,
					affected_balance,
					Rounding::Up,
				)
				.unwrap_or_else(|_| Perquintill::one());
				(
					Some(ratio),
					affected_indices.chain((0..first_slashable_index).rev()).collect::<Vec<_>>(),
				)
			} else {
				// We just slash from the last chunk to the most recent one, if need be.
				(None, (0..self.unlocking.len()).rev().collect::<Vec<_>>())
			}
		};
