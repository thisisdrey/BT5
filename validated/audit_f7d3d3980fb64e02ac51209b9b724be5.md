### Title
`write-freq` StackerDB throttle is enforced only in the sync scheduler, not at the actual chunk-write gate — remote signer can flood writes via the HTTP POST endpoint - (File: `stackslib/src/net/stackerdb/db.rs`)

### Summary
`StackerDBConfig.write_freq` is documented and loaded from the controlling smart contract as the minimum interval between writes to a slot, but the only function that actually commits a chunk to storage, `StackerDBTx::try_replace_chunk`, never checks it. The check exists solely inside the peer-to-peer sync scheduler (`stackslib/src/net/stackerdb/sync.rs`), which decides how often *this node* proactively re-fetches a chunk from other peers. Any remote party who holds a valid slot signing key can bypass that scheduler entirely by hitting the unauthenticated-except-for-signature HTTP endpoint (`POST /v2/stackerdb/.../chunks`, `stackslib/src/net/api/poststackerdbchunk.rs`) or by pushing an unsolicited P2P `StackerDBPushChunk`, both of which call `try_replace_chunk` directly and are throttled only by `max_writes`/`slot_version` monotonicity — not by `write_freq`.

### Finding Description
`try_replace_chunk` is the single write gate used by every chunk-storage path (HTTP POST handler, unsolicited P2P push via `relay.rs::process_stacker_db_chunks`, and sync-driven downloads): [1](#0-0) 

It validates: chunk size cap, signer authenticity, version monotonicity (`StaleChunk`), and `max_writes` — but there is no check against `write_freq`/`write_time` (the `write_time` column is written unconditionally on every accepted chunk): [2](#0-1) 

Meanwhile, `PeerNetwork::validate_received_chunk` — the validation routine used by the sync engine — explicitly documents that it does *not* check write frequency because "the caller has different ways of doing this": [3](#0-2) 

That "different way" only exists in the sync-scheduling logic (`stackslib/src/net/stackerdb/sync.rs`), which uses `write_freq` to decide when *this node* should re-download a chunk from a neighbor — it has no bearing on writes accepted directly from an authenticated signer via the HTTP API or via P2P push: [4](#0-3) 

The HTTP write path confirms this directly — it calls `tx.try_replace_chunk` with no separate write-frequency check before it: [5](#0-4) 

Similarly the P2P unsolicited-push/sync-result storage path in `relay.rs::process_stacker_db_chunks` calls `tx.try_replace_chunk` directly, with no write-frequency gate: [6](#0-5) 

This is structurally identical to the reported bug class: a pause/throttle control (`write_freq`, analogous to SpiritFactory's lock) is implemented in one component (the sync scheduler) but the actual state-mutating entry point (`try_replace_chunk`, analogous to `PancakePair.swap()`) has unrestricted access and never consults it.

### Impact Explanation
A signer authorized for a given slot (which, per the StackerDB trust model, is any principal listed in the smart contract's `stackerdb-get-signer-slots`, not a privileged node operator) can write new chunk versions as fast as `max_writes` allows, completely ignoring the smart contract's configured `write-freq`. Each accepted write triggers a network-wide broadcast (`StackerDBPushChunk`) to all replicating neighbors: [7](#0-6) 

This lets an authorized-but-malicious signer generate write/broadcast amplification across the whole StackerDB replica set at a rate the protocol's own economic/anti-spam parameter (`write-freq`) was specifically designed to prevent, causing a bounded compute/bandwidth DoS on all replicating nodes.

### Likelihood Explanation
High for any node operating a StackerDB with a nonzero `write-freq` in its contract. Exploitation requires only a valid signing key for one slot (no node secret, no admin role) and a normal HTTP POST or P2P push, both of which are supported, unauthenticated-at-the-transport-layer entry points reachable by any peer.

### Recommendation
Enforce `write_freq` inside `StackerDBTx::try_replace_chunk` (or equivalently in `insert_chunk`) by comparing the current time against the previously stored `write_time` for that slot, rejecting/erroring (e.g., a new `TooFrequentWrite` error) if the elapsed time is less than `config.write_freq`. This ensures the rate limit is enforced at the single authoritative write gate rather than only in the best-effort sync scheduler.

### Proof of Concept
1. Deploy or use a StackerDB contract with `write-freq` set to a large value (e.g., 3600 seconds).
2. Obtain a valid private key for a signer with an assigned slot.
3. Repeatedly call `POST /v2/stackerdb/<contract>/chunks` with strictly increasing `slot_version` and a valid signature, in a tight loop (bounded only by `max_writes`).
4. Observe that every request succeeds and triggers `try_replace_chunk` → `insert_chunk` → P2P broadcast, with no delay enforced, despite `write-freq` mandating a minimum interval between writes.

    /// Add or replace a chunk for a given reward cycle, if it is valid
    /// Otherwise, this errors out with Error::StaleChunk
    pub fn try_replace_chunk(
        &self,
        smart_contract: &QualifiedContractIdentifier,
        slot_desc: &SlotMetadata,
        chunk: &[u8],
    ) -> Result<(), net_error> {
        // Check per-replica chunk-size cap.
        if (chunk.len() as u64) > self.config.chunk_size {
            return Err(net_error::StackerDBChunkTooBig(chunk.len()));
        }

        let slot_validation = self
            .get_slot_validation(smart_contract, slot_desc.slot_id)?
            .ok_or(net_error::NoSuchSlot(
                smart_contract.clone(),
                slot_desc.slot_id,
            ))?;

        if !slot_desc.verify(&slot_validation.signer)? {
            return Err(net_error::BadSlotSigner(
                slot_validation.signer,
                slot_desc.slot_id,
            ));
        }
        if slot_desc.slot_version <= slot_validation.version {
            return Err(net_error::StaleChunk {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
            });
        }
        if slot_desc.slot_version > self.config.max_writes {
            return Err(net_error::TooManySlotWrites {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
                max_writes: self.config.max_writes,
            });
        }
        self.insert_chunk(smart_contract, slot_desc, chunk)
    }
