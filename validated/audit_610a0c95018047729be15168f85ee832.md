### Title
Permissionless `deposit(onBehalfOf)`/`transfer` lets an attacker fill a victim's token-list slots so new collateral deposits and new debt mints revert — combined with locked dust it can block position rescue and force liquidation - (File: contracts/Pool.sol)

### Summary
The Teller bug is "anyone can push arbitrary collateral into a victim's bid, breaking the action that iterates over that collateral." Metronome has the same shape: the per-account sets `depositTokensOfAccount`/`debtTokensOfAccount` are populated by `DepositToken._mint`/`_transfer` and `DebtToken` issuance with no consent check on the recipient side, and every `Pool` operation that would add a new entry reverts once the combined list reaches `MAX_TOKENS_PER_USER = 30` (`onlyIfAdditionWillNotReachMaxTokens`, `Pool.sol:143-148`). An unprivileged attacker can dust-fill all 30 slots of any victim.

### Finding Description
- `DepositToken._mint` adds the token to `depositTokensOfAccount[account_]` whenever the recipient's balance goes 0→>0 (`DepositToken.sol:486-488`), and `deposit(amount_, onBehalfOf_)` accepts any `onBehalfOf_` (`DepositToken.sol:211-237`) — so `deposit(1 wei, victim)` inserts an entry the victim never asked for. `transfer`/`transferFrom`/`seize` do the same via `_transfer` (`DepositToken.sol:517-520`).
- `addToDepositTokensOfAccount` and `addToDebtTokensOfAccount` both guard with `onlyIfAdditionWillNotReachMaxTokens` (`Pool.sol:204-220`), which reverts `UserReachedMaxTokens` at 30 combined entries.
- Once full, every subsequent victim call that would create a 0→>0 balance in a *new* deposit token (i.e. `deposit` of a collateral they don't hold) or mint a new `DebtToken` reverts inside `_mint`/`issue`.
- Removal requires the victim's balance of that token to reach 0 (`_transfer`/`_burn`, `DepositToken.sol:460-462, 523-525`), and transfers are gated by `_revertIfLocked` → `unlockedBalanceOf` (`DepositToken.sol:348-354, 383-398`). If the victim has outstanding debt, their transferable balance is capped at the excess-issuance equivalent, so dust entries may be impossible to clear without repaying debt — the exact loop the attacker is blocking them from escaping by depositing a fresh collateral type.

### Impact Explanation
An attacker can permanently DoS a targeted account's ability to (a) deposit a collateral type not already in its list and (b) issue a new synthetic asset, by spending dust amounts of each whitelisted underlying. For a victim whose existing collateral is falling in value, blocking the *new* deposit path prevents position rescue and makes liquidation by third parties inevitable — a liveness break / temporary freezing of funds delivered entirely through public entry points, mirroring the Teller report's DoS-on-acceptance impact.

### Likelihood Explanation
Medium-low likelihood of severe impact: the attacker must spend real underlying in up to `depositTokens.length()` (≤30) dust deposits, and the victim can still top up collateral types already in their list, repay debt, or clear dust slots if they have unlocked balance. Front-running a victim's first-ever deposit of a specific asset is cheap and reliable; weaponizing it against a distressed position requires the victim to need a new collateral type or new debt token.

### Recommendation
- Restrict `DepositToken.deposit`'s `onBehalfOf_` path (and/or the 0→>0 list insertion on `transfer`) so entries are only added when the recipient is the caller or has opted in — analogous to the report's "verify caller is TellerV2 or the borrower" fix.
- Alternatively, exempt dust-removal transfers from `_revertIfLocked`, or decouple `MAX_TOKENS_PER_USER` enforcement so a victim can always evict unwanted entries (e.g. a `sweepDust`/forced-remove callable by the account owner for tokens they never deposited).

### Proof of Concept
Reproducible in the existing Hardhat suite (pattern from `test/Pool.test.ts:1386-1416`):

```ts
// victim already holds one collateral with open debt (unlockedBalance ~0)
for (const dt of allDepositTokens) {
  if (dt === victimExistingCollateral) continue
  // attacker dusts the victim's account list
  await dt.connect(attacker).deposit(1n, victim.address)   // or transfer dust
}
// list is now at MAX_TOKENS_PER_USER
await expect(
  newDepositToken.connect(victim).deposit(amount, victim.address)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens')
await expect(
  newDebtToken.connect(victim).issue(amount, victim.address)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens')
// victim cannot clear dust slots while underwater:
await expect(dustToken.connect(victim).transfer(attacker.address, 1n))
  .to.be.revertedWithCustomError(dustToken, 'NotEnoughFreeBalance')
```

Uncertainty note: I did not fully enumerate `DebtToken.issue`/`mint`'s exact call chain to `addToDebtTokensOfAccount` within the iteration limit, but `Pool.sol:204-208` and the test at `test/Pool.test.ts:1491-1521` confirm minting a first balance in any debt token hits the same 30-entry cap.
