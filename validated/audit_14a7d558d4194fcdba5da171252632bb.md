### Title
Reward index skips accrual during zero-supply periods, permanently freezing emissions - (File: contracts/RewardsDistributor.sol)

### Summary
Analogous to Napier's `maxscale` high-water mark that stops updating while the underlying scale keeps growing, `RewardsDistributor._calculateTokenIndex` advances `TokenState.timestamp` while leaving `index` unchanged whenever the tracked token's `totalSupply()` is zero. The reward emissions for the entire zero-supply window are discarded permanently — no account can ever claim them — even though `tokenSpeeds[token_]` kept emitting rewards during that window.

### Finding Description
In `contracts/RewardsDistributor.sol`, `_calculateTokenIndex` computes:

```solidity
uint256 _totalSupply = token_.totalSupply();
uint256 _tokensAccrued = _deltaTimestamps * _speed;
uint256 _ratio = _totalSupply > 0 ? _tokensAccrued.wadDiv(_totalSupply) : 0;
_newIndex = (_supplyState.index + _ratio).toUint224();
_newTimestamp = block.timestamp.toUint32();
```

When `_totalSupply == 0`, `_ratio` is forced to 0 but `_newTimestamp` is still set to `block.timestamp`. `_updateTokenIndex` then stores `_newTimestamp`, so the whole elapsed interval (`_deltaTimestamps * _speed` reward tokens) is skipped and can never be re-accrued later — the accrual window is "settled" with a stale index, exactly like `maxScale` freezing at maturity while `cscale` moves on.

This is reachable from public entry points without any privileged action:

- `RewardsDistributor.updateBeforeMintOrBurn` / `updateBeforeTransfer` / `claimRewards` all call `_updateTokenIndex`, which permanently consumes the elapsed timestamp.
- Any user fully withdrawing/burning the tracked `DepositToken` (or repaying all `DebtToken` debt) drives `totalSupply()` to zero while `tokenSpeeds` remains > 0. Subsequent calls to any of the above functions by anyone burn the emissions accrued during the zero-supply period.
- Even the first depositor after the gap cannot recover them, because their `accountIndexOf` is initialized to `INITIAL_INDEX`/`_tokenIndex` via `_calculateTokenDelta`, and the skipped window's tokens were never added to the index.

Unlike the DebtToken path — where `issue`, `repay`, `repayAll`, `mint`, and `flashIssue` all call `accrueInterest()` first so `debtIndex` is refreshed before any accounting uses it — the distributor has no mechanism to credit the skipped emissions to anyone. The reward tokens remain locked in the distributor contract forever (`_transferRewardIfEnoughTokens` only pays out `tokensAccruedOf` balances, which can never include the skipped amount).

### Impact Explanation
All reward tokens emitted at rate `tokenSpeeds[token_]` for the duration of every zero-supply window are permanently frozen inside the `RewardsDistributor` contract. This is a permanent freezing/loss of unclaimed yield. For a `DebtToken` reward (borrow incentives) where supply frequently drops to zero, or a `DepositToken` fully exited during a market event, entire emission periods are destroyed. `claimable`/`claimRewards` under-report relative to `speed × elapsed`, and there is no recovery path — governor cannot redistribute them either.

### Likelihood Explanation
Likelihood is moderate-to-high depending on configuration, but requires no attacker privilege:

- The condition needs only `tokenSpeeds[token_] > 0` while `token_.totalSupply() == 0` for some period. Speeds are set per DepositToken/DebtToken via `updateTokenSpeed`/`updateTokenSpeeds`/`syncTokenSpeed`; zero supply occurs naturally (first token before initial deposit, debt tokens with zero open borrows, or full withdrawal events triggered by any user).
- A single user performing the last withdrawal, plus any later call to `updateBeforeMintOrBurn`/`claimRewards` (callable by anyone, including the next depositor's own mint hook), finalizes the loss.
- No modifiers block it: `nonReentrant`, `onlyIfTokenExists`, and `onlyIfDistributorExists` do not apply to the accrual math itself.

### Recommendation
Do not advance the stored timestamp past periods where the index cannot be updated, or defer reward accrual when supply is zero. Concretely, in `_calculateTokenIndex`, when `_totalSupply == 0` either:

- keep `_newTimestamp` at `_supplyState.timestamp` for the index math and carry the unallocated emissions forward (e.g., track a `pendingRewards` bucket credited on the next non-zero-supply update), or
- at minimum, document and bound the loss by forcing `tokenSpeeds` to 0 before supply can reach 0 — though on-chain enforcement (skipping timestamp advance) is safer.

### Proof of Concept
Foundry/Hardhat-style reproduction against `contracts/RewardsDistributor.sol`:

```solidity
// Setup: pool with DepositToken msdX and RewardsDistributor rd,
// governor sets rd.updateTokenSpeed(msdX, speed) with speed > 0.

// 1. user deposits D, mints supply: msdX.deposit(D, user)  -> totalSupply = D
// 2. warp T1 seconds: index accrues normally.
// 3. user withdraws everything: msdX.withdraw(D, user, user) -> totalSupply = 0
//    (withdraw triggers updateBeforeMintOrBurn -> index + timestamp saved)
// 4. warp T2 seconds while supply == 0.
// 5. anyone calls rd.updateBeforeMintOrBurn(msdX, user) or a new deposit happens.
//    _calculateTokenIndex: delta = T2, speed > 0, totalSupply = 0
//    -> _ratio = 0, index unchanged, but timestamp := now.
// 6. user2 deposits D' and waits T3. user2's claimable =
//    D' * (index growth over T3 only). The speed * T2 emissions
//    are nowhere in the index and unclaimable by anyone.
// assert rd.balance < expectedEmissions(T1 + T2 + T3) and
//        no sequence of claimRewards calls can recover the T2 amount.
```

The assertion `rewardToken.balanceOf(rd) == speed*(T1+T2+T3)` with total claimed + `tokensAccruedOf` sum equal to only `speed*(T1+T3)` proves permanent freezing of `speed*T2` reward tokens.
