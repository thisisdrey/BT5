### Title
Unbounded stderr capture during `git-pack-objects` execution allows memory-exhaustion DoS via crafted fetch/clone - (File: internal/gitaly/service/hook/pack_objects.go)

### Summary
Gitaly's built-in subprocess wrapper (`internal/command/command.go`) only enforces a bounded, 10KB `stderrBuffer` when a caller does **not** supply its own stderr writer. Numerous call sites across the codebase bypass this protection by passing an explicit `bytes.Buffer{}` for `stderr`, which has no size limit at all. This mirrors the external-report's root cause — an external process's output being captured without a size cap, allowing memory/resource exhaustion — except here it's a Git subprocess invoked as part of an ordinary, unprivileged client operation (a fetch/clone) rather than a low-level `.call()`.

### Finding Description
`command.New` only installs a bounded `stderrBuffer` (`maxStderrBytes = 10000`, `maxStderrLineLength = 4096`) when the caller leaves `cfg.stderr` unset: [1](#0-0) [2](#0-1) 

If the caller passes its own writer for stderr, that bound is never applied — the writer receives everything the subprocess emits. In `internal/gitaly/service/hook/pack_objects.go`, `runPackObjects` (which backs the `PackObjectsHookWithSidechannel` RPC that services every `git fetch`/`clone`/`upload-pack` operation via `uploadpack.packObjectsHook`) captures `git-pack-objects` stderr into an explicit, unbounded `bytes.Buffer`: [3](#0-2) 

`git-pack-objects` can be induced to emit large volumes of stderr output — for example, progress/statistics reporting, or one warning line per broken/missing/unreachable object encountered while packing a requested set of objects (e.g. via `--shallow`, filtered/partial clone parameters, or a repository containing many corrupt/missing objects reachable from requested refs). Because `stderrBuf` here has no cap, an attacker who can trigger many or large stderr lines from `git-pack-objects` (via ordinary fetch/clone request parameters that reach `PackObjectsHookWithSidechannelRequest.Args`, processed in `parsePackObjectsArgs`) causes Gitaly to buffer that data entirely in memory per request: [4](#0-3) 

This same unbounded-buffer pattern recurs at other reachable call sites (e.g. `internal/git/localrepo/config.go` `GetConfig`/`GetConfigValues`, `internal/git/localrepo/bundle.go` `CloneBundle`), all of which pass explicit `bytes.Buffer{}` for stdout/stderr and thus skip the 10KB guard — but `pack_objects.go` is the strongest analog because it sits directly in the unauthenticated/low-privilege fetch/clone hot path reachable by any client that can read a repository.

### Impact Explanation
Each concurrent fetch/clone request that triggers a pathological amount of `git-pack-objects` stderr output consumes unbounded server memory proportional to attacker-influenced input (number of objects requested, filter options, repository corruption state), with no per-request cap analogous to the 10KB default. Multiple concurrent such requests can drive Gitaly's process to memory exhaustion/OOM, denying service to all repositories on the node — consistent with the report's DoS classification.

### Likelihood Explanation
Likelihood is moderate: reaching this path requires only an ordinary fetch/clone against a repository that exercises `git-pack-objects` with heavy stderr output (e.g. large/partial/shallow clones against repositories with many unreachable/missing objects, or crafted `--filter`/`--shallow-file` combinations passed through `parsePackObjectsArgs`). No special privileges beyond normal fetch access are needed, matching the "ordinary user's fetch" trigger class required by the validation rules. Precisely engineering the largest possible stderr volume from `git-pack-objects` may require some experimentation, which slightly lowers ease of exploitation compared to a single crafted contract call.

### Recommendation
- Short term: Replace the raw `bytes.Buffer{}` used for `stderr` (and any other explicit stdout/stderr buffers used for subprocess output that isn't already streamed) in `runPackObjects`/`runPackObjectsLimited` with a bounded writer equivalent to `command`'s internal `stderrBuffer` (10KB/4096-byte line cap), or route stderr through the package's existing `newStderrBuffer` helper instead of `&bytes.Buffer{}`.
- Long term: Audit all callers across the codebase that pass explicit `io.Writer`/`bytes.Buffer` for `command.WithStdout`/`command.WithStderr` and standardize on a shared, size-bounded buffer type by default, only allowing unbounded capture where the volume is already known to be small and not attacker-influenced.

### Proof of Concept
1. Set up a Gitaly-backed repository reachable via `git fetch`/`clone`, with the pack-objects cache/hook path enabled (`uploadpack.packObjectsHook` configured, as done for `PostUploadPackWithSidechannel`).
2. Craft a repository/ref set such that a client-initiated `git fetch`/`clone` (using e.g. `--filter`, `--shallow-since`, or deep history against corrupted/missing objects) causes the server-side `git-pack-objects` invocation in `runPackObjects` to emit a very large amount of stderr (e.g. many "unable to read" / progress lines).
3. Observe that `stderrBuf := &bytes.Buffer{}` in `runPackObjects` ( [5](#0-4) ) grows unbounded, and repeat the request concurrently to exhaust Gitaly server memory, unlike stderr captured through the default `command` path which is capped at 10KB.

func parsePackObjectsArgs(args []string) (*packObjectsArgs, error) {
	result := &packObjectsArgs{}

	// Check for special argument used with shallow clone:
	// https://gitlab.com/gitlab-org/git/-/blob/v2.30.0/upload-pack.c#L287-290
	if len(args) >= 2 && args[0] == "--shallow-file" && args[1] == "" {
		result.shallowFile = true
		args = args[2:]
	}

	if len(args) < 1 || args[0] != "pack-objects" {
		return nil, errNoPackObjects
	}
	args = args[1:]

	// There should always be "--stdout" somewhere. Git-pack-objects can
	// write to a file too but we don't want that in this RPC.
	// https://gitlab.com/gitlab-org/git/-/blob/v2.30.0/upload-pack.c#L296
	seenStdout := false
	for _, a := range args {
		if !strings.HasPrefix(a, "-") {
			return nil, errNonFlagArg
		}
		if a == "--stdout" {
			seenStdout = true
		} else {
			result.flags = append(result.flags, a)
		}
	}

	if !seenStdout {
		return nil, errNoStdout
	}

	return result, nil
}
