### Title
`repayAll()` burns an unbounded amount of the payer's synthetic tokens — attacker can front-run with `issue()` to inflate the debt being repaid - ([File: contracts/DebtToken.sol](contracts/DebtToken.sol))

### Summary
`DebtToken.repayAll(address onBehalfOf_)` lets any payer burn their own synthetic tokens to clear another account's entire debt, but it resolves `balanceOf(onBehalfOf_)` at execution time with no `maxAmount`/`expectedDebt` bound. The referenced debt ("the empire" of the planet in the bug class — the mutable attribute behind a user-supplied identifier) can change between transaction submission and execution: the borrower can front-run with `issue()` to inflate their own debt, forcing the payer to burn more synth than intended.

### Finding Description
`repayAll` computes the amount to burn dynamically:

```solidity
// contracts/DebtToken.sol
_repaid = balanceOf(onBehalfOf_);          // line 478 — resolved at execution time
...
(_amount, _fee) = quoteRepayIn(_repaid);   // line 485 — gross + fee derived from _repaid
_syntheticToken.seize(_msgSender, pool.feeCollector(), _fee);   // line 488
_syntheticToken.burn(_msgSender, _repaid); // line 491 — payer pays whatever balanceOf says now
_burn(onBehalfOf_, _repaid);
```

Meanwhile `issue(uint256 amount_, address to_)` is a public function that lets the borrower mint new debt on their own account (`_mint(_pool, _masterOracle, _msgSender, amount_)`, line 262) backed by their deposited collateral.

Attack path (unprivileged EOA only):
1. Victim intends to repay borrower's full debt `D` (quoted via `quoteRepayIn(balanceOf(borrower))` off-chain) and submits `repayAll(borrower)` expecting to burn ~`D + fee` of synth.
2. Borrower (attacker) front-runs with `deposit()`/`issue(x, attacker)`, raising `balanceOf(borrower)` to `D + x` and receiving `x` fresh synth.
3. Victim's `repayAll` executes and burns `D + x + fee` of the victim's synth instead of `D + fee`.

The attacker ends with their full (now larger) debt paid off by the victim while keeping their collateral and the newly minted synth. Profit ≈ `x` (bounded by the victim's synth balance and the attacker's collateralization headroom). There is no parameter to cap the spend — unlike `repay(onBehalfOf_, amount_)`, which is explicitly bounded (line 418).

The same class applies weakly to `Pool.liquidate` (the liquidator names `depositToken_` explicitly, so identity is fixed — no analog there), but `repayAll` is the direct analog: a user-supplied identifier (`onBehalfOf_`) whose mutable state is not verified against the payer's expectation.

### Impact Explanation
Direct theft of user funds: the payer burns more synthetic tokens than they intended, with the difference accruing to the attacker as forgiven debt. Loss is bounded by the payer's synth balance and how much debt the attacker can `issue` under `maxTotalSupply` and their collateral factor.

### Likelihood Explanation
- Requires a user to voluntarily call `repayAll` on another account — less common than repaying own debt, but supported by design (`_msgSender()` is the payer, `onBehalfOf_` the beneficiary, per the NatSpec at line 460).
- Front-running is straightforward on public mempools (mainnet/Base/Optimism deployments); attacker needs collateral and the victim to hold sufficient synth.
- No privileged role, oracle manipulation, or governance action needed. `whenNotShutdown`, `nonReentrant`, `onlyIfSyntheticTokenExists` do not block it.

### Recommendation
Add a caller-specified bound, e.g. `repayAll(address onBehalfOf_, uint256 maxAmountToRepay_)`, and revert if `balanceOf(onBehalfOf_) > maxAmountToRepay_` (or the quoted gross `_amount > maxAmount_`). This mirrors the fix in the source report: verify the mutable state the user's calldata implicitly depends on.

### Proof of Concept
Hardhat-style sketch (repo's existing `Pool.test.ts` fixtures apply):

```ts
// setup: borrower deposits MET via msdMET, issues msEth debt of D
// victim holds >= D + x msEth and wants to repay borrower's full debt
const debtBefore = await msEthDebtToken.balanceOf(borrower.address);
const quote = await msEthDebtToken.quoteRepayIn(debtBefore); // victim expects ~this much

// attacker (borrower) sees victim's repayAll(borrower) in mempool, front-runs:
await msEthDebtToken.connect(borrower).issue(extraDebt, borrower.address); // +x debt, mints x msETH to borrower

// victim tx lands
await msEthDebtToken.connect(victim).repayAll(borrower.address);

// assert: victim burned debtBefore + x + fee, not quote[0]
// attacker keeps collateral + x msETH, fully debt-free
expect(await msEthDebtToken.balanceOf(borrower.address)).eq(0);
expect(await msEth.balanceOf(victim.address)).lt(victimBefore.sub(quote._amount));
```

Note: `issue` reverts `NotEnoughCollateral` if the attacker lacks issuable headroom, so the PoC must deposit extra collateral to the attacker first; impact scales with that headroom.
