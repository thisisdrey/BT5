### Title
Unauthenticated pre-handshake QUIC connections evade both connection-rate limiters and exhaust the shared `max_concurrent_connections` slot pool - ([File: streamer/src/nonblocking/quic.rs])

### Summary
The QUIC ingress loop only *peeks* the global `overall_connection_rate_limiter` and only checks the per-IP `rate_limiter` against pre-existing records before allocating a `ClientConnectionTracker` slot; both limiters are actually populated/consumed only *after* the TLS handshake completes. An attacker who opens QUIC connections and never finishes the handshake therefore never gets rate-limited, and can hold `ClientConnectionTracker` slots (counted against the shared `qos.max_concurrent_connections()` cap) for up to `QUIC_CONNECTION_HANDSHAKE_TIMEOUT` per connection, exhausting the pool shared by staked and unstaked peers.

### Finding Description
In the QUIC accept loop, before a `ClientConnectionTracker` is created, two checks run: a global burst check and a per-IP check: [1](#0-0) 

- The overall limiter check `overall_connection_rate_limiter.current_tokens() == 0` at line 347 is a non-mutating peek; the token bucket is only actually decremented via `consume_tokens(1)` later in `setup_connection`, *after* the handshake succeeds (line 495 of the excerpt below). If handshakes never complete, tokens are never consumed, so this limiter never trips regardless of connection volume.
- The per-IP check `rate_limiter.is_allowed(&incoming.remote_address().ip())` only inspects an existing record; the code and its own comment state "we assume that only IPs with actual confirmed connections are stored in it" — a record is only created via `register_connection`, which (like the global bucket) is only called after the handshake completes: [2](#0-1) [3](#0-2) 

Once both (non-blocking) checks pass, `ClientConnectionTracker::new` increments `stats.open_connections` and compares it against `qos.max_concurrent_connections()`, which is shared across staked and unstaked traffic: [4](#0-3) [5](#0-4) 

The tracker is then held for the duration of the handshake attempt, bounded only by `QUIC_CONNECTION_HANDSHAKE_TIMEOUT`, and only released (via `Drop`, decrementing `open_connections`) when the timeout fires or the handshake resolves: [6](#0-5) [7](#0-6) 

The code's own comment acknowledges the design tradeoff — rate-limiting by IP before the peer has "asserted control over their ip address" would allow ip-spoofing attacks against the limiter itself — and states the mitigation is meant to be "bound resource consumption" via the handshake timeout plus the global rate limiter. But because the global limiter is a peek-not-consume check that is never decremented for stalled handshakes, it provides no actual bound on the *volume* of concurrent in-flight (never-completing) handshake attempts; the only real ceiling is `qos.max_concurrent_connections()` itself, i.e. `(max_staked_connections + max_unstaked_connections) * 5 / 4`. An attacker opening connections from many ephemeral ports/IPs and abandoning them after the first packet can therefore fill and continuously refill this shared pool for as long as they sustain connection churn within the handshake timeout window, denying tracker slots (and thus TPU ingress) to legitimate staked and unstaked senders.

### Impact Explanation
This is a QoS-evasion / denial-of-service against TPU ingress: unstaked, unprivileged connection churn from an attacker fully starves the shared connection slot pool that both staked and unstaked legitimate peers rely on, causing `stats.refused_connections_too_many_open_connections` to climb and legitimate transactions to fail to reach the leader's TPU (`incoming.refuse()` at line 377). Because the cap is shared between staked and unstaked tables (`max_concurrent_connections` combines both), even staked validators/RPCs sending transactions can be denied service by a purely unstaked attacker — this is a resource-exhaustion/availability bug affecting the leader's transaction ingestion path.

### Likelihood Explanation
This requires no stake, no identity, no gossip/peer control — only the ability to open raw UDP/QUIC packets to the leader's public TPU QUIC port and then stop responding, which is exactly within the stated unprivileged-attacker capability. It is fully repeatable and only bounded by the attacker's ability to churn ephemeral source ports/addresses faster than `QUIC_CONNECTION_HANDSHAKE_TIMEOUT` reclaims slots, which is a modest bandwidth/packet-rate requirement, not a sophisticated exploit.

### Recommendation
Bound the number of *in-flight, unauthenticated* handshake attempts independently of the post-handshake rate limiters — e.g., consume a token from the global `overall_connection_rate_limiter` (or a dedicated pre-handshake bucket) at accept time rather than only after a successful handshake, and/or maintain a separate, smaller cap dedicated to "outstanding_incoming_connection_attempts" that is enforced before `ClientConnectionTracker::new` is invoked (the code already tracks `stats.outstanding_incoming_connection_attempts`, but does not gate on it). Consider also lowering `QUIC_CONNECTION_HANDSHAKE_TIMEOUT` or applying quinn's stateless-retry validation to force IP ownership proof before allocating a tracked connection slot.

### Proof of Concept
Integration test plan (extending existing `setup_quic_server` test harness in `streamer/src/nonblocking/quic.rs`):
1. Spin up the QUIC server with `max_staked_connections`/`max_unstaked_connections` set small (e.g., 4 total → `max_concurrent_connections() == 5`).
2. Spawn `N > max_concurrent_connections()` raw UDP sockets that each send a single QUIC Initial packet to the server (constructing minimal valid Initial packets, or using `quinn::Endpoint::connect` but immediately dropping/blackholing the client-side socket after the first flight so the handshake never completes), each from a distinct ephemeral source port.
3. Concurrently, have one legitimate `make_client_endpoint` attempt a normal full handshake and send a transaction stream.
4. Assert:
   - `stats.refused_connections_too_many_open_connections.load(Ordering::Relaxed) > 0`.
   - `stats.open_connections.load(Ordering::Relaxed)` reaches `max_concurrent_connections()` while the stalled handshakes are outstanding.
   - The legitimate client's connection attempt is refused/times out despite being well under `max_staked_connections`/`max_unstaked_connections` individually.
   - After `QUIC_CONNECTION_HANDSHAKE_TIMEOUT` elapses, `stats.connection_setup_timeout` increments and slots free up, confirming the hold duration matches the handshake timeout rather than any rate-limit rejection.

impl ClientConnectionTracker {
    /// Check the max_concurrent_connections limit and if it is within the limit
    /// create ClientConnectionTracker and increment open connection count. Otherwise returns Err
    fn new(stats: Arc<StreamerStats>, max_concurrent_connections: usize) -> Result<Self, ()> {
        let open_connections = stats.open_connections.fetch_add(1, Ordering::Relaxed);
        if open_connections >= max_concurrent_connections {
            stats.open_connections.fetch_sub(1, Ordering::Relaxed);
            debug!(
                "There are too many concurrent connections opened already: open: \
                 {open_connections}, max: {max_concurrent_connections}"
            );
            return Err(());
        }

        Ok(Self { stats })
    }

    /// Check if the connection from the said `ip` is allowed.
    /// Here we assume that only IPs with actual confirmed connections are stored in it,
    /// since we should only modify server state once source IP is verified
    pub fn is_allowed(&self, ip: &IpAddr) -> bool {
        // Check if we have records in the rate limiter for the given IP address
        match self.limiter.current_tokens(ip) {
            Some(r) => r > 0, // we have a record, and rate is not exceeded
            None => true,     // if we have not seen IP, allow connection request
        }
    }

    pub fn register_connection(&self, ip: &IpAddr) -> bool {
        if self.limiter.consume_tokens(*ip, 1).is_ok() {
            debug!("Request from IP {ip:?} allowed");
            true // Request allowed
        } else {
            debug!("Request from IP {ip:?} blocked");
            false // Request blocked
        }
    }
