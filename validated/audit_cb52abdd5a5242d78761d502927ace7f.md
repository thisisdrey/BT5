### Title
Unprivileged attacker can exhaust a victim's `MAX_TOKENS_PER_USER` slots via dust `DepositToken.transfer`, blocking the victim from depositing/borrowing new collateral types - ([File: contracts/DepositToken.sol](contracts/DepositToken.sol))

### Summary
The Werkzeug advisory describes a configured resource limit (`max_form_memory_size`) being bypassed so an attacker consumes more resources than intended. The Metronome analog is `Pool.MAX_TOKENS_PER_USER` (30), a hard cap on the combined `debtTokensOfAccount` + `depositTokensOfAccount` lists. `DepositToken._transfer` unconditionally calls `pool.addToDepositTokensOfAccount(recipient_)` for any first-time recipient, and `Pool.addToDepositTokensOfAccount` reverts with `UserReachedMaxTokens` once the cap is hit. Anyone can send 1 wei of a deposit receipt token to a victim, consuming one of the victim's slots without consent.

### Finding Description
- `DepositToken.transfer`/`transferFrom` only check the *sender's* unlocked balance (`_revertIfLocked(_msgSender, amount_)`, `DepositToken.sol:348-376`). There is no minimum amount and no opt-in on the recipient side.
- `_transfer` calls `pool.addToDepositTokensOfAccount(recipient_)` whenever the recipient's prior balance is zero (`DepositToken.sol:517-520`).
- `Pool.addToDepositTokensOfAccount` is guarded by `onlyIfAdditionWillNotReachMaxTokens`, which reverts `UserReachedMaxTokens` when `debtTokensOfAccount.length + depositTokensOfAccount.length >= 30` (`Pool.sol:143-148`).
- The same cap applies to `DebtToken._mint` → `pool.addToDebtTokensOfAccount` (`DebtToken.sol:598-600`), so once a victim's combined list is full, the victim cannot `deposit()` into a collateral they don't already hold, cannot receive any new deposit token, and cannot `issue()` a new synthetic asset — all those paths revert.
- The attacker only needs to buy negligible (1 wei) amounts of each underlying, deposit them, and transfer the dust receipt tokens to the target. Repeatable via multiple attacker accounts so the attacker never loses list space themselves (each attacker's own slots are per-account, and the dust leaves their balance at zero, which also removes the entry from *their* list via `removeFromDepositTokensOfAccount` — actually making the attack self-cleaning for the attacker while permanently occupying the victim's slots).

### Impact Explanation
Temporary freezing of funds / protocol-feature DoS against a targeted account. The victim's existing positions remain withdrawable (`withdraw`/`_burn` removes a token from the list when the balance hits zero, freeing a slot), but while the list is saturated the victim cannot open positions in new collateral or synthetic assets, and any `transfer`/`transferFrom`/`deposit(onBehalfOf=victim)` of a token they don't already hold reverts. An attacker can continuously re-fill slots (each dusting costs ~1 wei) to keep the victim locked out indefinitely, forcing the victim to fully exit a position (paying withdraw fees) to free a single slot — and even then the slot can be immediately re-consumed by the attacker. This is a per-account resource exhaustion that bypasses the intended protection `MAX_TOKENS_PER_USER` was designed to give (it protects *loops*, but assumes entries are user-initiated).

### Likelihood Explanation
- Attack cost is negligible: minimum-denomination deposits of each whitelisted collateral plus gas.
- Feasibility depends on the deployed configuration: the attack can only force entries equal to the number of whitelisted `DepositToken`s in the pool (capped at 30 by `addDepositToken`, `Pool.sol:703`). Attacker-controlled debt tokens cannot be pushed onto the victim since `issue` mints to the caller. If the pool has `N` deposit tokens and the victim already uses `M` slots, the victim is fully blocked only if `M + N >= 30`; otherwise their usable capacity is merely reduced to `30 - N - M` free slots. Pools with few collaterals make full lockout impossible but still reduce headroom.
- No privileged role, oracle manipulation, or malicious endpoint is required — `transfer` is a public entry point reachable by any EOA or via `Operator.execute`/gateways.
- Reentrancy guards, pause flags, `SynthContext` checks, and supply caps do not mitigate this; `whenNotPaused`/`nonReentrant` on `deposit` don't stop the dust-transfer vector.

### Recommendation
Bound additions by value, not just presence — e.g., only call `addToDepositTokensOfAccount` when the incoming amount exceeds a per-token dust threshold, or allow accounts to remove unwanted entries themselves (a public `removeFromDepositTokensOfAccountSelf`/`cleanse` path or make recipient-side additions lazy/permissioned). Alternatively track "list membership" separately from zero-balance transfers so unsolicited dust cannot consume capped slots.

### Proof of Concept (Hardhat sketch)
```ts
// Setup: pool with N whitelisted deposit tokens msd1..msdN; victim holds M positions.
// Attacker:
for (const dt of depositTokens) {
  // 1. acquire dust of underlying, approve
  await underlying.approve(dt.address, 1);
  // 2. deposit minimal amount to self → gets msdTOKEN balance
  await dt.deposit(1, attacker.address);        // mints ~1 wei to attacker
  // 3. force onto victim — fills one victim slot
  await dt.transfer(victim.address, 1);          // addToDepositTokensOfAccount(victim)
}
// Once debtTokens + depositTokens of victim == MAX_TOKENS_PER_USER (30):
await expect(dtNew.deposit(amount, victim.address))
  .to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');
await expect(debtTokenNew.issue(amount, victim.address /* via onBehalf path */))
  .to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');
// Attacker re-fills freed slots at ~0 cost after each victim withdrawal.
```

Caveat: I verified the modifier logic and revert path from the contract source and `test/Pool.test.ts` (lines 1386–1416, 1491–1521), but I could not confirm the exact whitelisted deposit-token count per deployed pool from the index, so the "full lockout" precondition (`victim slots + pool deposit tokens >= 30`) should be validated per deployment.
