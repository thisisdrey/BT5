### Title
Relayer fee refund is paid out immediately for `EOABaseTokenTransfer` even when nonce advance is deferred pending the address‑registrar check, allowing unlimited replay of a single signed transaction to drain wallet funds - ([File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs])

### Summary
In `inner_rlp_execute`, when the parsed transaction kind is `EthEmulationKind::EOABaseTokenTransfer { address_check: Some(_), fee }`, the nonce increment is deliberately skipped (deferred until `address_check_callback` resolves the registrar lookup), but the relayer-fee refund promise is created unconditionally in the same function, without regard to `address_check`. If the registrar lookup later reveals the target address is actually a registered named account (i.e., the relayer's `target` was invalid), `address_check_callback` returns an error without incrementing the nonce and without banning the relayer (unless the relayer used the wallet's own access key). This decouples relayer payment from nonce consumption, letting the same signed RLP transaction be resubmitted indefinitely to repeatedly extract the fee from the wallet contract's balance.

### Finding Description
The relevant logic is in `inner_rlp_execute` [1](#0-0) :

- Nonce advance is conditionally skipped only for `EOABaseTokenTransfer { address_check: Some(_), .. }`, because the transaction's validity (whether `target` is really an unregistered EOA-style address) can only be confirmed asynchronously via the address registrar lookup [2](#0-1) .
- Immediately after, a **second, independent** `if let` matches `EOABaseTokenTransfer { fee, .. } | ERC20Transfer { fee, .. }` (ignoring `address_check`) and unconditionally creates a transfer promise refunding `fee` to `context.predecessor_account_id` via `env::promise_batch_create` [3](#0-2) . This batch promise executes independently of the main action's outcome and independently of whether the nonce was actually incremented.
- When the registrar lookup later resolves in `address_check_callback` and finds `maybe_account_id.is_some()` (target address is a real registered account, i.e. the relayer supplied an invalid target), the code explicitly documents that the nonce is *not* incremented ("we intentionally do not increment the nonce in this case because the error is caused by a faulty relayer") and the relayer is only banned if `env::signer_account_id() == current_account_id` (i.e., only if the relayer used the wallet's own access key) [4](#0-3) .
- If the relayer instead calls `rlp_execute` directly with its own account as `predecessor_account_id`/`signer_account_id` (a normal, unprivileged NEAR account acting as relayer — no access key of the wallet is used), no ban occurs, no nonce is consumed, and `has_in_flight_tx` is reset to `false` once `address_check_callback` runs [5](#0-4) .
- Consequently, `validate_tx_relayer_data`'s nonce check (`nonce != expected_nonce`) in `internal.rs` [6](#0-5)  will pass again on the exact same RLP bytes, because `expected_nonce` (the contract's stored `nonce`) was never advanced. `target` classification comes from `parse_target`, which relies on `extract_address`/`account_id_to_address` to determine `TargetKind::EthImplicit` vs `OtherNearAccount` [7](#0-6) , and this classification is exactly what routes execution into the `address_check: Some(_)` branch.
- Result: the attacker (any unprivileged account holding a copy of a validly-signed RLP transaction from the wallet owner — as would routinely happen when a user broadcasts a meta-transaction to relayer services) can call `rlp_execute` with the identical `tx_bytes_b64`/`target` repeatedly. Each call passes the signature check (`tx.address == current_address`), the chain-id check (`tx.chain_id == CHAIN_ID`), and the (never-advancing) nonce check, triggers a fee payout from the wallet's own NEAR balance to the caller, then fails in `address_check_callback` without consuming the nonce or banning the caller.

The chain-id check (`tx.chain_id != Some(CHAIN_ID)` in `validate_tx_relayer_data`) does not block this: the attacker needs a transaction that is validly signed for chain id `CHAIN_ID` (mainnet=397) to begin with, which is satisfied by any real user-signed transaction intended for a relayer on this network; a foreign-chain-id transaction is simply rejected earlier and is not part of the exploit path.

### Impact Explanation
This breaks the documented invariant that "relayer compensation happens only alongside a nonce advance" and results in direct, repeatable theft of the wallet contract's own NEAR balance by any unprivileged account that has obtained one qualifying user-signed RLP transaction (which is inherent to how relayer/meta-transaction flows work — the signed payload is handed to relayer(s) for broadcast). This matches "High – Direct theft of user funds via access-key / meta-transaction / wallet-contract authorization bypass," since the wallet pays out repeatedly without the underlying state (nonce) advancing, i.e., unbounded fee extraction until the wallet's balance is exhausted.

### Likelihood Explanation
- Precondition: attacker must possess a validly ECDSA-signed RLP Ethereum-style transaction from the wallet owner whose `parse_tx_data`/`parse_target` resolves to `TargetKind::EthImplicit` with the ambiguous/unparsable-payload or emulated-EOA-transfer branch, and whose target address is (or later becomes) registered in the address registrar, and whose fee (`max_fee_per_gas * gas_limit`) is non-zero.
- Attacker cost: only gas for calling `rlp_execute` repeatedly (as a normal, non-privileged predecessor account) plus possession of the one signed blob; no access key of the victim wallet is required, and no signature forgery is needed.
- Repeatability: unlimited — every call is a legitimate constant-nonce RLP transaction that reproducibly reaches the same failing branch, so this can be looped until the wallet balance / relayer fee amount is exhausted.
- This is straightforward to trigger for any relayer-facing signed transaction targeting an eth-implicit address that is/becomes registrar-registered; there is no fuzzing or race condition required.

### Recommendation
In `inner_rlp_execute`, gate the relayer-fee-refund promise creation on the same condition used for nonce advancement: only pay the fee immediately when the nonce is also being advanced in this call (i.e., skip the immediate refund for `EOABaseTokenTransfer { address_check: Some(_), .. }` and instead move the fee-refund logic into `address_check_callback`, executing it only in the `None` (unregistered) branch that actually advances the nonce). This restores the invariant that relayer compensation and nonce advance are atomic/coupled.

### Proof of Concept
Unit/integration test plan (using the existing `wallet-contract` test scaffolding under `runtime/near-wallet-contract/implementation/wallet-contract/src/tests`):
1. Construct an `ExecutionContext` for a wallet contract account and a `target` `AccountId` that is an eth-implicit-looking address not equal to `current_address`.
2. Craft/mock a normalized Ethereum transaction whose calldata is not parseable as a Near action (or is a supported ERC-20/base-token emulation) so that `parse_tx_data`/`parse_rlp_tx_to_action` yields `TransactionKind::EthEmulation(EthEmulationKind::EOABaseTokenTransfer { address_check: Some(address), fee })` with `fee` non-zero.
3. Call `inner_rlp_execute` with `predecessor_account_id` set to an arbitrary unprivileged account (not the wallet's own account) and assert (a) a refund promise/transfer batch action for `fee` is generated targeting `predecessor_account_id`, and (b) `*nonce` is unchanged after the call.
4. Simulate the registrar callback (`address_check_callback`) with `promise_result(0)` returning `Some(some_registered_account_id)`, and `env::signer_account_id() != current_account_id`; assert the resulting `ExecuteResponse` is an error, `self.nonce` is unchanged, and no ban/delete-key promise is issued.
5. Repeat steps 2–4 twice with the identical `tx_bytes_b64`/`target` and confirm both calls pass the nonce check in `validate_tx_relayer_data` (since `nonce == expected_nonce` both times) and both generate a fee-refund promise — demonstrating unbounded repeat drain.
Expected assertion for the fix: after applying the recommendation, no fee-refund promise/transfer action should be generated when `address_check` is `Some(_)` until the registrar confirms the address is unregistered, at which point the fee refund and nonce increment must both occur atomically in `address_check_callback`.
