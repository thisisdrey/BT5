### Title
Unauthenticated sandwich manipulation of `pallet-asset-conversion` spot reserves forces overpayment of transaction fees paid via `SwapAssetAdapter` - (File: `substrate/frame/transaction-payment/asset-conversion-tx-payment/src/payment.rs`)

### Summary
`SwapAssetAdapter::withdraw_fee` and `SwapAssetAdapter::correct_and_deposit_fee` (the `OnChargeAssetTransaction` implementation used by `ChargeAssetTxPayment`) price a user's non-native-asset fee payment by calling `quote_price_tokens_for_exact_tokens` / `quote_price_exact_tokens_for_tokens`, which read the AMM pool's *live, spot* reserves via `pallet_asset_conversion::Pallet::get_reserves`. This is the direct on-chain analog of the reported Uniswap `slot0` spot-price bug: there is no TWAP, no price-impact bound, and — unlike normal user-initiated swaps which carry attacker/user-supplied `amount_out_min`/`amount_in_max` slippage guards — the fee-quoting path has *no slippage protection at all*, because the quoted amount is computed and consumed atomically inside the extension with no user-chosen bound. An attacker who can place transactions immediately before and after a victim's transaction in the same block (ordinary public mempool sandwiching, no validator/collator privilege required) can move the pool's spot reserves to inflate the fee-asset price the victim is charged, then reverse the trade to capture the extracted value.

### Finding Description
`get_reserves` reads the pool account's current on-chain balances directly with no historical averaging: [1](#0-0) 

`quote_price_tokens_for_exact_tokens` / `quote_price_exact_tokens_for_tokens` derive the fee-asset amount purely from these instantaneous reserves via the constant-product formula (`get_amount_in`/`get_amount_out`): [2](#0-1) [3](#0-2) 

`SwapAssetAdapter::withdraw_fee` calls this quote at pre-dispatch time and immediately executes the swap for exactly that quoted amount, with zero tolerance/slippage parameter exposed to the user: [4](#0-3) 

`correct_and_deposit_fee` repeats the same pattern at post-dispatch time when refunding overpaid fees, again quoting off the pool's spot reserves at that instant: [5](#0-4) 

Because `ChargeAssetTxPayment::validate_and_prepare` and `post_dispatch_details` run inline with normal extrinsic execution in a block, an attacker can submit `swap_exact_tokens_for_tokens`/`swap_tokens_for_exact_tokens` transactions on the same pool immediately before the victim's fee-paying transaction (skewing reserves to raise the price of the victim's fee asset relative to the target fee asset `A`), let the victim's `withdraw_fee` execute at the skewed price, and then submit a reversing swap afterward to restore the pool and capture the spread. This is functionally identical to the reported Uniswap `slot0`/sandwich pattern — the guard that would normally stop this (a TWAP oracle or a caller-supplied price-impact/slippage bound) is absent from the fee-quoting call path, even though it exists for ordinary user swaps (`amount_out_min`/`amount_in_max` in `swap_exact_tokens_for_tokens`/`swap_tokens_for_exact_tokens`).

### Impact Explanation
Any chain configuring `pallet-asset-conversion-tx-payment`'s `SwapAssetAdapter` to let users pay fees in non-native assets is exposed: victims can be forced to pay a fee-asset amount above fair market value, or receive a smaller-than-fair refund, with the difference extracted by the sandwiching attacker. This is value loss from an unprivileged, ordinary user's balance — falling under "public underpriced work" / value-conservation violations for balances and asset accounting, without requiring any admin, governance, relayer, validator, or collator role.

### Likelihood Explanation
The only precondition is the ability to get two of the attacker's own transactions ordered around the victim's transaction touching the same asset-conversion pool — an ordinary MEV/sandwich capability available to any public-mempool participant with sufficient tip/priority, not a validator/collator/relayer privilege. Any runtime that enables asset-fee payment through `pallet-asset-conversion` (e.g. Asset Hub style configurations) is affected whenever the underlying pool has usable depth for a sandwich, which is the normal operating condition of a fee-payment pool.

### Recommendation
Do not price mandatory fee-asset conversions purely off instantaneous `get_reserves()` spot balances. Options:
- Use a time-weighted or multi-block-averaged price source (TWAP) for fee-asset quoting instead of raw spot reserves.
- Bound the acceptable price movement between quote and settlement (e.g. cap `asset_fee`/`refund_asset_amount` deviation against a recent reference price, failing the transaction rather than accepting an arbitrarily skewed price).
- Consider restricting/monitoring same-block reserve deltas for pools used for fee payment, or requiring minimum liquidity depth relative to fee sizes to bound sandwich profitability.

### Proof of Concept
1. Attacker identifies a pending transaction from victim `V` that will pay fees in asset `X` via `ChargeAssetTxPayment` against pool `(X, A)` (native fee asset `A`).
2. Attacker submits tx1: a large `swap_exact_tokens_for_tokens` trading `A` into `X` (or vice versa) in the pool, shifting `get_reserves(X, A)` so that `quote_price_tokens_for_exact_tokens(X, A, fee, true)` (called inside `SwapAssetAdapter::withdraw_fee`, `substrate/frame/transaction-payment/asset-conversion-tx-payment/src/payment.rs:142-146`) now returns an inflated `asset_fee`.
3. Victim `V`'s transaction executes; `withdraw_fee` withdraws the inflated `asset_fee` amount of `X` from `V` and swaps it for the required native fee `fee`, per `substrate/frame/transaction-payment/asset-conversion-tx-payment/src/payment.rs:148-170`.
4. Attacker submits tx2 immediately after, reversing tx1's swap, restoring the pool to its original state and capturing the price difference extracted from `V`'s overpaid fee (or shorted refund via `correct_and_deposit_fee`, `substrate/frame/transaction-payment/asset-conversion-tx-payment/src/payment.rs:262-277`).
5. No `TransactionValidityError` is raised anywhere in this path because the quote functions always succeed as long as liquidity exists (`quote_price_tokens_for_exact_tokens`/`quote_price_exact_tokens_for_tokens` only return `None` on zero liquidity or amount, not on price deviation), so the sandwiched fee is accepted as valid.

		/// Gets a quote for swapping an exact amount of `asset1` for `asset2`.
		///
		/// If `include_fee` is true, the quote will include the liquidity provider fee.
		/// If the pool does not exist or has no liquidity, `None` is returned.
		/// Note that the price may have changed by the time the transaction is executed.
		/// (Use `amount_out_min` to control slippage.)
		/// Returns `Some(quoted_amount)` on success.
		pub fn quote_price_exact_tokens_for_tokens(
			asset1: T::AssetKind,
			asset2: T::AssetKind,
			amount: T::Balance,
			include_fee: bool,
		) -> Option<T::Balance> {
			// Swaps reject zero amounts, match that behavior.
			if amount.is_zero() {
				return None;
			}

			let pool_account = T::PoolLocator::pool_address(&asset1, &asset2).ok()?;

			let (balance1, balance2) = Self::get_reserves(asset1.clone(), asset2.clone()).ok()?;

			if balance1.is_zero() {
				return None;
			}

			let amount_out = if include_fee {
				let fee = Self::pool_fee_for(&asset1, &asset2).ok()?;
				Self::get_amount_out(fee, &amount, &balance1, &balance2).ok()?
			} else {
				Self::quote(&amount, &balance1, &balance2).ok()?
			};

			// Small inputs can round output to zero due to integer division.
			if amount_out.is_zero() {
				return None;
			}

			// Swap withdrawals from pools use `keep_alive=true` (Preserve). Use the same
			// preservation level to determine the actual withdrawable amount.
			let max_output = T::Assets::reducible_balance(asset2, &pool_account, Preserve, Polite);
			if amount_out > max_output {
				return None;
			}

			Some(amount_out)
		}

	fn withdraw_fee(
		who: &T::AccountId,
		_call: &T::RuntimeCall,
		_dispatch_info: &DispatchInfoOf<<T>::RuntimeCall>,
		asset_id: Self::AssetId,
		fee: Self::Balance,
		_tip: Self::Balance,
	) -> Result<Self::LiquidityInfo, TransactionValidityError> {
		if asset_id == A::get() {
			// The `asset_id` is the target asset, we do not need to swap.
			let fee_credit = F::withdraw(
				asset_id.clone(),
				who,
				fee,
				Precision::Exact,
				Preservation::Preserve,
				Fortitude::Polite,
			)
			.map_err(|_| InvalidTransaction::Payment)?;

			return Ok((fee_credit, fee));
		}

		// Quote the amount of the `asset_id` needed to pay the fee in the asset `A`.
		let asset_fee =
			S::quote_price_tokens_for_exact_tokens(asset_id.clone(), A::get(), fee, true)
				.filter(|asset_fee| !asset_fee.is_zero())
				.ok_or(InvalidTransaction::Payment)?;

		// Withdraw the `asset_id` credit for the swap.
		let asset_fee_credit = F::withdraw(
			asset_id.clone(),
			who,
			asset_fee,
			Precision::Exact,
			Preservation::Preserve,
			Fortitude::Polite,
		)
		.map_err(|_| InvalidTransaction::Payment)?;

		let (fee_credit, change) = match S::swap_tokens_for_exact_tokens(
			vec![asset_id, A::get()],
			asset_fee_credit,
			fee,
		) {
			Ok((fee_credit, change)) => (fee_credit, change),
			Err((credit_in, _)) => {
				defensive!("Fee swap should pass for the quoted amount");
				let _ = F::resolve(who, credit_in).defensive_proof("Should resolve the credit");
				return Err(InvalidTransaction::Payment.into());
			},
		};

		// Since the exact price for `fee` has been quoted, the change should be zero.
		ensure!(change.peek().is_zero(), InvalidTransaction::Payment);

		Ok((fee_credit, asset_fee))
	}
