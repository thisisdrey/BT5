### Title
Potential division-by-zero panic in `PohTiming::report` if `num_ticks` is 0 - (File: `poh/src/poh_service.rs`)

### Summary
`PohTiming::report` computes `us_per_slot` using an unchecked integer division by `self.num_ticks`: [1](#0-0) 

```
fn report(&mut self, ticks_per_slot: u64) {
    if self.last_metric.elapsed().as_millis() > 1000 {
        let elapsed_us = self.last_metric.elapsed().as_micros() as u64;
        let us_per_slot = (elapsed_us * ticks_per_slot) / self.num_ticks;
```

Unlike the ERC-4626 `maxRedeem` bug (a "MUST NOT revert" division-by-zero in a view function), this is a native Rust integer division, so `self.num_ticks == 0` would cause an immediate thread panic rather than a revert. PoH is recorded/ticked on a dedicated validator thread (`solPohTickProd` style loop) that this metrics struct tracks.

### Finding Description
`num_ticks` is only incremented when a tick actually occurs, and `report()` is called on a time-based cadence (elapsed > 1000ms) rather than being gated on `num_ticks > 0`. I was not able to fully confirm, within the available tool calls, all code paths that call `report()` to determine whether there is a guaranteed prior increment of `num_ticks` before every call in every producer variant (e.g., low-power tick producer vs. hot/busy tick producer), particularly around startup, PoH resets, or leader-slot transitions where a `report()` call could occur without an intervening tick.

### Impact Explanation
If reachable with `num_ticks == 0`, this is an unconditional Rust integer division by zero, which panics the thread computing PoH ticks — a core validator liveness path. A panic here is a full node crash/liveness failure, not merely a metrics-reporting glitch.

### Likelihood Explanation
Unconfirmed. This requires demonstrating a real code path where `report()` executes with zero recorded ticks since the last metrics reset (e.g., immediately after `last_metric` reset if a long stall happens with no ticks recorded, or a race between reset and tick). I could not trace this fully due to running out of investigation iterations, so I cannot state with confidence this is reachable in production versus always guarded elsewhere.

### Recommendation
If confirmed reachable, guard the division: `self.num_ticks.checked_div(...)` / early-return when `self.num_ticks == 0`, analogous to the `maxRedeem` fix pattern of handling `totalAssets == 0` explicitly before dividing.

### Proof of Concept
Not established — would require constructing/tracing a scenario where `PohTiming::report` is invoked with `num_ticks == 0`, which I was unable to confirm or refute with the remaining tool budget.

**Caveat:** Because I could not complete verification of the call sites feeding into `report()`, I cannot assert this as a confirmed vulnerability with certainty — this should be treated as a lead requiring further investigation (reading the full `poh_service.rs` tick-producer loops and reset logic) rather than a proven finding.
