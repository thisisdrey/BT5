### Title
Single external `stSTX` ratio contract reverting breaks oracle price resolution and DoS's all market operations for any position holding `stSTX`/`zststx` - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
The market's oracle callcode transformation for `stSTX` (`CALLCODE-STSTX`) depends on an unconditional external call to a single, third-party contract (`block-info-nakamoto-ststx-ratio-v2`, deployed by a different party at `SP4SZE494VC2YC5JYG7AYFQ44F5Q4PYV7DVMDPBG`). If that call reverts or returns an error for any reason, price resolution for `stSTX` (and derivative `zststx`) fails, which - because prices are resolved in a batch via `price-multi-resolve` - causes the **entire position's** price resolution to fail with `ERR-ORACLE-MULTI`, blocking borrow, repay, collateral-add/remove, and liquidation for the whole account, not just the `stSTX` leg. This mirrors the C4 finding [M-14] where a single failing external `SponsorVault` call caused the whole `execute` transaction (and thus all cross-chain messaging for the domain) to revert.

### Finding Description
The oracle callcode transform chain is:
- `resolve-callcode` dispatches `CALLCODE-STSTX` (and `CALLCODE-ZSTSTX`, which nests it) to `resolve-ststx`: [1](#0-0) 

- `resolve-ststx` performs an `unwrap!` on `call-ststx-ratio`, converting any error into `ERR-ORACLE-CALLCODE`: [2](#0-1) 

- `call-ststx-ratio` is a public function that performs a direct, unguarded `contract-call?` to a hardcoded third-party contract with no try/catch/fallback: [3](#0-2) 

- `price-resolve` propagates this failure via `try!`: [4](#0-3) 

- `price-multi-resolve`/`iter-price-multi` resolve prices for an entire asset list (a user's whole position mask) in one fold; a single failed `price-resolve` call sets `valid: false` for the whole batch, and `price-multi-resolve` then asserts and reverts the entire evaluation with `ERR-ORACLE-MULTI`: [5](#0-4) 

- `get-assets`, which is called from every core market entry point (`borrow`, `repay`, `liquidate`, `collateral-add`, `collateral-remove`, etc. via `get-notional-evaluation`), calls `price-multi-resolve` over the caller's asset list: [6](#0-5) 

Because `stSTX`/`zststx` is unconditionally resolved for any position that includes it as collateral or debt, and one failure aborts price resolution for the *entire* asset list of that call (not just the `stSTX` entry), an outage, pause, upgrade, or bug in the third-party `block-info-nakamoto-ststx-ratio-v2` contract makes `get-assets` revert unconditionally for every affected account - even when the operation targeted a completely different asset in the same position (e.g., repaying a `USDC` debt while also holding `stSTX` collateral).

### Impact Explanation
This is a temporary freezing of funds: while the third-party ratio contract is broken/reverting, any account holding `stSTX` or `zststx` cannot borrow, repay, add/remove collateral, or be liquidated for **any** asset in their position, since price resolution for the whole mask fails atomically. Unlike the disabled-collateral liquidation exclusion (an intended design decision), this is an unintended systemic dependency on an unmonitored, unwhitelisted third-party contract's continued availability with no on-chain fallback or graceful degradation path - directly matching the impact class of the referenced report (temporary freezing of funds due to a single external dependency failure cascading into a full-flow revert).

### Likelihood Explanation
Likelihood is non-trivial: the ratio contract is an external, third-party dependency (a different deploying principal), and any of its own pauses, upgrades, reverts (e.g., internal staleness checks, admin pause, contract redeployment/migration) or being temporarily unavailable will trip this. This requires no attacker action - it is purely a resilience/DoS defect - and it affects every user holding `stSTX`/`zststx`, an actively supported collateral/debt asset in the protocol.

### Recommendation
Wrap the `call-ststx-ratio` external call (and other single third-party oracle dependencies) with error containment so a revert does not cascade into aborting price resolution for the caller's entire asset list. At minimum, decouple `stSTX`-price resolution failures from unrelated assets in `iter-price-multi`/`price-multi-resolve` (e.g., only fail the operation if the specific failing asset is actually part of the requested notional calculation), or add a fallback/cached-ratio mechanism so a temporarily unavailable third-party contract cannot completely block borrow/repay/liquidation across the whole position.

### Proof of Concept
1. User A supplies `stSTX` as collateral and separately borrows `USDC`.
2. The third-party `block-info-nakamoto-ststx-ratio-v2` contract reverts (e.g., due to its own pause, migration, or internal error) when `get-ststx-ratio-v3` is called.
3. User A calls `repay` on their `USDC` debt (unrelated to `stSTX`). `repay` → `get-position`/notional evaluation → `get-assets` → `price-multi-resolve` iterates the position's asset list, which includes `stSTX`; `price-resolve` for `stSTX` calls `resolve-callcode` → `resolve-ststx` → `call-ststx-ratio`, which reverts.
4. `iter-price-multi` marks the whole batch invalid; `price-multi-resolve` returns `ERR-ORACLE-MULTI`; the entire `repay` transaction (and equally `borrow`, `collateral-add`, `collateral-remove`, `liquidate`) reverts.
5. All of User A's market operations are blocked until the third-party contract recovers, even though the operation itself did not require an `stSTX` price.

(define-private (price-resolve
  (data { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint }))
  (let ((type (get type data))
        (ident (get ident data))
        (key { type: type, ident: ident })
        (resolution (try! (resolve-price-feed type ident)))
        (price (get value resolution))
        (callcode (get callcode data))
        (final-price (try! (resolve-callcode price callcode)))
        (last-update-time (oracle-last-update key))
        (timestamp (get timestamp resolution))
        (max-staleness (get max-staleness data)))

    ;; validate price and timestamp using max-staleness from oracle data
    (asserts! (and (oracle-price-legal final-price) (oracle-timestamp-fresh timestamp last-update-time max-staleness))
              ERR-ORACLE-INVARIANT)

    ;; update timestamp if newer
    (if (> timestamp last-update-time)
        (map-set last-update key timestamp)
        false)

    (ok final-price)))

(define-private (price-multi-resolve
  (data (list 64 { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint }))
  (aids (list 64 uint)))
  (let ((init { output: (list), valid: true, aids: aids, idx: u0 })
        (response (fold iter-price-multi data init)))
    (asserts! (get valid response) ERR-ORACLE-MULTI)
    (ok (get output response))))

(define-private (iter-price-multi
  (oracle-data { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint })
  (acc { output: (list 64 uint), valid: bool, aids: (list 64 uint), idx: uint }))
  (let ((valid (get valid acc))
        (skip? (asserts! valid acc))
        (asset-ids (get aids acc))
        (idx (get idx acc))
        ;; resolve price - will use cache for ztokens
        (price (unwrap! (price-resolve oracle-data) (merge acc { valid: false })))
        (next (unwrap-panic (as-max-len? (append (get output acc) price) u64))))
    { output: next,
      valid: true,
      aids: asset-ids,
      idx: (+ idx u1) }))
