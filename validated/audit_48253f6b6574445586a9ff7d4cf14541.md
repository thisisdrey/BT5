### Title
Stale partition assignment allows a repository to be silently rejoined to a previously deleted repository's partition, causing cross-repository object/state leakage - (File: internal/gitaly/storage/storagemgr/partition_assigner.go)

### Summary
Gitaly's transactional storage backend maps every repository's relative path to a `storage.PartitionID` via `partitionAssignmentTable`, persisted in the storage's embedded key-value store. This mapping is created lazily on first access and is **never removed**, even when the repository at that relative path is deleted. If a new, unrelated repository is later created at the same relative path (e.g. after a project delete+recreate, an import, or a fork/rename cycle that frees and reuses a path), Gitaly's partition assigner will find the stale `(relativePath, partitionID)` record and silently attach the new repository to the old partition instead of allocating a fresh one — exactly analogous to the reported bug class where stale approval/lock data tied to an object identity is never cleared and is later misapplied when the same identity is reused.

### Finding Description
`partitionAssignmentTable` only exposes `getPartitionID` and `setPartitionID`; there is no delete/removal path: [1](#0-0) 

The lookup/assignment logic in `getPartitionIDRecursive` looks up the assignment purely by `relativePath` string — it has no way to distinguish "this relative path belongs to the repository that originally got this ID" from "this relative path is now occupied by a brand-new, unrelated repository": [2](#0-1) 

The project's own documentation explicitly acknowledges this: "The assignments are created before the repository is even created, and assignments are not deleted even if the repository is deleted." [3](#0-2) 

Partitions are not 1:1 with a single repository — an object pool and *all* repositories connected to it are deliberately colocated in the *same* partition so that pool/member transactions can be ordered together: [4](#0-3) 

This means the impact of reusing a stale partition assignment is not merely "wasted partition ID": if the deleted repository at that relative path was previously a pool member (or a pool), the stale assignment routes the *new* repository into the very partition that stores the write-ahead log, key-value entries, and potentially still-linked alternate-object state for the old pool/members. This is the direct structural analog of the reported vault bug — an approval/permission record keyed by an identifier (`nftContract`+`tokenID` there, `relativePath` here) is left dangling after the underlying object is moved out (`transferERC721`/repository deletion), and is later misapplied when a new, unrelated occupant reuses that same identifier (a different NFT placed in the vault / a different repository created at the same path), producing an incorrect trust/data relationship that a legitimate actor cannot resolve without special knowledge of the stale record.

### Impact Explanation
- A newly created repository can be transactionally routed into a partition that was previously used by a deleted repository/object pool, inheriting whatever WAL/KV/partition-scoped state persists there.
- Because pools and members must share a partition for consistency guarantees, this can re-establish an implicit relationship between the new repository and the old pool's remaining members/alternates without any explicit `LinkRepositoryToObjectPool` call, undermining the repository isolation the partitioning/transaction model is designed to guarantee (`doc/transactions.md` describes partitioning precisely as the isolation boundary for transactional guarantees).
- At minimum this is a storage-path resolution / partition-assignment integrity bug leading to state confusion between logically unrelated repositories; in the worst case (pool partition reuse) it is a cross-repository object/data exposure primitive, reachable purely through ordinary repository lifecycle operations (delete + recreate at the same relative path), no privileged actor required.

### Likelihood Explanation
Relative-path reuse after deletion is a normal, user-triggerable event (e.g., project deletion followed by recreation/import at the same disk path, or Praefect-driven repository state reconciliation). The assignment table has no cleanup hook anywhere in the codebase (confirmed by the absence of any delete/remove method on `partitionAssignmentTable`), so every such reuse deterministically hits the stale-assignment path once the relative path collides.

### Recommendation
Delete the partition assignment record for a relative path as part of repository deletion (and any other operation that frees a relative path for reuse), or otherwise invalidate/version the assignment so a freshly created repository at a reused path is guaranteed a new partition rather than inheriting the previous occupant's. This mirrors the recommended fix in the source report: explicitly clear the stale keyed record (`delete timelockERC721s[...]` there; delete the `partition_assignment/<relativePath>` key here) at the point where the underlying resource is removed from its container, rather than leaving it to be misinterpreted the next time that identifier is reused.

### Proof of Concept
1. Create repository `A` at relative path `p`; it is lazily assigned partition ID `N` via `getPartitionIDRecursive` (`internal/gitaly/storage/storagemgr/partition_assigner.go:234`).
2. Link `A` to an object pool `Pool`, which is also placed in partition `N` per the pool/member colocation rule.
3. Delete repository `A` from disk. The `partition_assignment/p → N` KV record is not removed (no such deletion codepath exists in `partitionAssignmentTable`).
4. Create a brand-new, unrelated repository `B` at the same relative path `p` (e.g., recreate project at the same hashed path).
5. On first transactional access to `B`, `getPartitionIDRecursive(ctx, "p", ...)` finds the pre-existing assignment and returns `N` instead of allocating a new partition — `B` is now transactionally colocated with the residual state of `Pool`/`A`'s old partition, without any explicit linking RPC ever being issued for `B`.

// partitionAssignmentTable records which partitions repositories are assigned into.
type partitionAssignmentTable struct{ db keyvalue.Store }

func newPartitionAssignmentTable(db keyvalue.Store) *partitionAssignmentTable {
	return &partitionAssignmentTable{db: db}
}

func (pt *partitionAssignmentTable) key(relativePath string) []byte {
	return []byte(fmt.Sprintf("%s%s", PrefixPartitionAssignment, relativePath))
}

func (pt *partitionAssignmentTable) getPartitionID(relativePath string) (storage.PartitionID, error) {
	var id storage.PartitionID

	if err := pt.db.View(func(txn keyvalue.ReadWriter) error {
		item, err := txn.Get(pt.key(relativePath))
		if err != nil {
			if errors.Is(err, badger.ErrKeyNotFound) {
				return storage.ErrPartitionAssignmentNotFound
			}

			return fmt.Errorf("get: %w", err)
		}

		return item.Value(func(value []byte) error {
			id.UnmarshalBinary(value)
			return nil
		})
	}); err != nil {
		return 0, fmt.Errorf("view: %w", err)
	}

	return id, nil
}

func (pt *partitionAssignmentTable) setPartitionID(relativePath string, id storage.PartitionID) error {
	wb := pt.db.NewWriteBatch()
	if err := wb.Set(pt.key(relativePath), id.MarshalBinary()); err != nil {
		return fmt.Errorf("set: %w", err)
	}

	if err := wb.Flush(); err != nil {
		return fmt.Errorf("flush: %w", err)
	}

	return nil

func (pa *partitionAssigner) getPartitionIDRecursive(ctx context.Context, relativePath string, recursiveCall bool, partitionHint storage.PartitionID, isRepositoryCreation bool) (storage.PartitionID, error) {
	// Check first whether the repository is already assigned into a partition. If so, just return the assignment.
	ptnID, err := pa.partitionAssignmentTable.getPartitionID(relativePath)
	if err != nil {
		if !errors.Is(err, storage.ErrPartitionAssignmentNotFound) {
			return 0, fmt.Errorf("get partition: %w", err)
		}

		// Repository wasn't yet assigned into a partition. This is the slow path. Requests attempting
		// to get or assign a partition ID concurrently are serialized.

		releaseLock, err := pa.acquireRepositoryLock(ctx, relativePath)
		if err != nil {
			return 0, fmt.Errorf("acquire repository lock: %w", err)
		}

		defer releaseLock()

		// With the repository locked, check first whether someone else assigned it into a partition
		// while we weren't holding the lock between the first failed attempt getting the assignment
		// and locking the repository.
		ptnID, err = pa.partitionAssignmentTable.getPartitionID(relativePath)
		if !errors.Is(err, storage.ErrPartitionAssignmentNotFound) {
			if err != nil {
				return 0, fmt.Errorf("recheck partition: %w", err)
			}

			// Some other goroutine assigned a partition between the failed attempt and locking the
			// repository.
			return ptnID, nil

**File:** doc/transactions.md (L56-60)
```markdown
Gitaly automatically assigns repositories to partitions when they are first accessed:

- Object pools and all repositories connected to the object pool are placed in the same partition. Repositories that are about to be connected to an object pool, such as newly created forks, are also placed in the same partition with the object pool they are about to be connected.
  - Assigning pools and their connected repositories into the same partition ensures transactions can guarantee consistency between them. If pools were in different partitions, transaction ordering could cause issues, for example updating a reference in a fork before the objects are written into the pool.
- Repositories that are not connected (nor about to be connected) to an object pool are placed in their own partitions.
```
