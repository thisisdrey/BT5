### Title
RewardsDistributor grants a windfall equal to the account's full balance when `accountIndexOf == 0` coincides with `tokenStates.index == INITIAL_INDEX` - ([File: contracts/RewardsDistributor.sol](contracts/RewardsDistributor.sol))

### Summary
`RewardsDistributor._calculateTokenDelta()` contains a special-case shortcut for accounts with no recorded index: it backfills `accountIndex` with `INITIAL_INDEX` **only when the global index is strictly greater than `INITIAL_INDEX`** (`_tokenIndex > INITIAL_INDEX`). This shortcut is sound in the common case (index already advanced), but wrong in the exact-block case where the index is still equal to `INITIAL_INDEX`: `accountIndex` stays `0`, producing `_deltaIndex = 1e18` and `_tokensDelta = balanceOf(account) * 1e18 / 1e18 = balanceOf(account)`. This is the same bug class as the upstream report: a shared helper assumes a result that holds for one branch (index already advanced) and silently produces a wrong state for the other branch (index still at initial value) — analogous to assuming `0 | K == 0` because `0 & K == 0`.

### Finding Description
In `contracts/RewardsDistributor.sol:217-231`:

```solidity
function _calculateTokenDelta(...) private view returns (uint256 _tokenIndex, uint256 _tokensDelta) {
    _tokenIndex = _tokenState.index;
    uint256 _accountIndex = accountIndexOf[token_][account_];

    if (_accountIndex == 0 && _tokenIndex > INITIAL_INDEX) {
        _accountIndex = INITIAL_INDEX;
    }

    uint256 _deltaIndex = _tokenIndex - _accountIndex;
    _tokensDelta = token_.balanceOf(account_).wadMul(_deltaIndex);
}
```

When a governor first activates a reward speed for a token via `updateTokenSpeed`/`updateTokenSpeeds`, `_updateTokenSpeed()` stores `tokenStates[token_] = TokenState({index: INITIAL_INDEX, timestamp: block.timestamp})` (lines 296-299). In that same block, any account holding a balance of that DepositToken/DebtToken that touches `_updateTokensAccruedOf` — via `claimRewards` (line 159), `updateBeforeMintOrBurn` (line 178), or `updateBeforeTransfer` (line 190) — hits `_calculateTokenDelta` with:

- `_accountIndex = 0` (never recorded)
- `_tokenIndex = 1e18` — not `> INITIAL_INDEX`, so the backfill is skipped
- `_deltaIndex = 1e18`
- `_tokensDelta = balanceOf(account_)` interpreted as reward-token units

`accountIndexOf` is then set to `1e18` and `tokensAccruedOf` credits this windfall. `_updateTokenIndex` does not advance the index when `_deltaTimestamps == 0` (lines 203-211), so the window is the same block/timestamp as the speed activation — reachable by an unprivileged attacker front-running/back-running the governance `updateTokenSpeed` transaction (e.g., via `Operator.execute` batching a `claimRewards` call, or simply being the next transaction in the same block timestamp on L2s where timestamps are shared).

Note the asymmetry with the intended invariant: an account first recorded when `index == INITIAL_INDEX` should accrue `0`, exactly as an account recorded later does. The `>` versus `>=`-equivalent boundary is what makes the shortcut unsound for this one case.

### Impact Explanation
Theft of unclaimed yield / direct reward-token drain. The attacker's `tokensAccruedOf` is credited an amount equal to their DepositToken (or DebtToken) balance, denominated in the reward token, with zero time elapsed and zero speed accrued. `claimRewards` then pays out up to the distributor's full `rewardToken` balance (`_transferRewardIfEnoughTokens`, lines 248-256). An attacker can scale the payout by maximizing their deposit balance at the moment of activation (e.g., a large deposit just before, or leverage via `SmartFarmingManager` to inflate a DebtToken balance). The yield stolen belongs to all legitimate suppliers/borrowers; the distributor's reserve is drained to whoever reaches the windfall first.

### Likelihood Explanation
Requirements: a `RewardsDistributor` registered on the pool, a reward token funded in it, and a fresh `updateTokenSpeed(s)` activation for a token the attacker holds. Activation is a routine governance operation (also reachable via the keeper-driven `syncTokenSpeed` for Vesper-backed collaterals), not a malicious action — the attacker only needs to hold a balance and land an accrual-touching call in the same timestamp. On L2 deployments (Base/Hemi per `deployments/`), multiple transactions per timestamp are normal, making same-block inclusion trivial. No flash loan is needed for the DebtToken variant since debt balances count directly. The bug is deterministic once the timing condition is met.

### Recommendation
Change the fallback condition in `_calculateTokenDelta` to cover the equality case, i.e. treat any zero `accountIndex` as initialized at the current index rather than `INITIAL_INDEX` only:

```solidity
if (_accountIndex == 0) {
    _accountIndex = _tokenIndex > INITIAL_INDEX ? INITIAL_INDEX : _tokenIndex;
}
```

(or equivalently, set `accountIndexOf` for all existing holders' first touch to `max(_tokenIndex, INITIAL_INDEX)`). Additionally, when `_updateTokenSpeed` activates a new token, the stored index could be set such that `accountIndex` backfill is unambiguous. Add a regression test: activate a speed, update an existing holder in the same block, and assert `_tokensDelta == 0`.

### Proof of Concept
Hardhat fork/ unit PoC (against `test/Pool.test.ts` fixtures):

```ts
// 1. Alice holds msdToken balance (already deposited).
const aliceBalance = await msdEth.balanceOf(alice.address);

// 2. Governor activates a reward speed on the deposit token.
await rewardsDistributor.connect(governor).updateTokenSpeed(msdEth.address, parseEther('0.01'));
//    tokenStates[msdEth].index == 1e18, timestamp == now.

// 3. In the SAME block/timestamp, Alice claims (batch via automine off or
//    Operator.execute, or rely on shared L2 timestamps).
await network.provider.send('evm_setAutomine', [false]);
await rewardsDistributor.connect(alice).claimRewards(alice.address);
// ... mine ...
// Expected (fixed): tokensAccruedOf == 0
// Actual (buggy):   tokensAccruedOf == aliceBalance

// 4. Fund distributor and observe drain.
const rewardBal = await met.balanceOf(rewardsDistributor.address);
await rewardsDistributor.claimRewards(alice.address);
const gained = await met.balanceOf(alice.address);
// gained == min(aliceBalance, rewardBal) > 0 despite zero elapsed accrual
```

Key assertion: `_deltaIndex` should be `0` when a speed was just activated; instead it is `1e18`, minting `balanceOf(alice)` worth of claimable reward out of thin air.

*Caveat: I was able to fully verify the accrual path (`_calculateTokenDelta`, `_updateTokenSpeed`, `claimRewards`, `updateBeforeMintOrBurn/Transfer`) but did not exhaustively rule out every deployed-configuration factor (e.g., whether all speeds were activated long ago on every live deployment); the bug re-triggers on any new token-speed activation or re-activation after a zeroed index.*
