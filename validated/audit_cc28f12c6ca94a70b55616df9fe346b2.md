Confirmed: `run_ijar` in Bazel's `java_common` API runs the `ijar` tool on a jar file provided by the rule (`jar` parameter), which can be an arbitrary jar supplied through `java_import`/`JavaInfo#compile_jar` pipelines — i.e., attacker-influenced content fetched via `http_archive`/`http_jar`/Maven-style rules and consumed by the build, not just Bazel-produced output jars.

### Title
ijar's `ProcessCentralDirEntry` walks off the end of a jar's extra-field / central-directory records - (File: `third_party/ijar/zip.cc`)

### Summary
`InputZipFile::ProcessCentralDirEntry` in [1](#0-0)  parses each Central Directory Header of an mmap'd jar/zip file entirely without ever calling the `EnsureRemaining` bounds check that every other reader in the same class uses (e.g. `ProcessLocalFileEntry`, `SkipFile`, `ProcessFile`) via [2](#0-1)  and [3](#0-2) .

### Finding Description
The extra-field sub-record loop:
```
const u1 *extra_p = p;
p += extra_field_length;
while (extra_p != p) {
  const u2 header_id = get_u2le(extra_p);
  const u2 data_size = get_u2le(extra_p);
  const u1 *extra = extra_p;
  extra_p += data_size;
  ...
}
``` [4](#0-3)  is structurally identical to the JFS `ealist` bug class: it walks a list of variable-length attribute-like records (`header_id`/`data_size` pairs) bounded only by an attacker-controlled outer length (`extra_field_length`, itself read straight from the file with `get_u2le(p)` at line 511), and it never validates that each record's declared `data_size` keeps `extra_p` within `p` (the computed end of the extra-field region) before dereferencing `extra_p` for the next `header_id`/`data_size` read. If a crafted jar declares a `data_size` that overshoots `p` (or wraps past it), `extra_p` never equals `p`, so the `while (extra_p != p)` loop keeps dereferencing memory beyond the extra-field boundary, and beyond the end of the memory-mapped input file itself, reading arbitrary heap/adjacent-mapping bytes.

The wider function has the same defect at a higher level: unlike `ProcessLocalFileEntry`, none of the reads in `ProcessCentralDirEntry` — signature, sizes, `file_name_length`, `extra_field_length`, `file_comment_length`, `attr`, `offset`, `memcpy(filename, p, len)` — are preceded by any `EnsureRemaining`/bounds check against `input_file_->Length()`. A truncated or maliciously sized central directory record can push `p` past the mmap'd region entirely.

### Impact Explanation
This is an out-of-bounds read in a native (C++) tool that runs as part of ordinary Bazel Java builds whenever `java_common.run_ijar` is invoked (used to build interface/compile jars, including from prebuilt jars ingested via `java_import`, which are frequently sourced from `http_archive`/`http_jar`/external Maven-style repositories). A hostile origin serving a crafted jar can crash the ijar worker (SIGSEGV) or, worse, leak adjacent heap memory into the derived interface jar's filename/attribute fields, which can then be observed indirectly through build outputs. There is no checksum/content check inside ijar itself that would stop malformed central-directory sub-records once the outer file's own checksum (if any) has already been verified — the corruption is internal structure, not the whole-file bytes, so a valid sha256 for the archive does not protect against internal ealist-style corruption in the archive's zip metadata.

### Likelihood Explanation
Moderate-to-high: any build that runs ijar over an externally-sourced jar (a very common pattern for `java_import`/prebuilt dependencies) is exposed. The attacker only needs to control the bytes of one dependency jar; no privileged access is required. The bug is a straightforward missing-bounds-check in a hand-written binary parser with no fuzzing-hardening comparable to `EnsureRemaining` guards elsewhere in the same file.

### Recommendation
Add bounds checks in `ProcessCentralDirEntry` before every field read/advance (mirroring `EnsureRemaining` used in `ProcessLocalFileEntry`), and in the extra-field loop validate that `extra_p + 4 <= p` before reading `header_id`/`data_size`, and that `extra_p + data_size <= p` before advancing, aborting with an error instead of continuing to iterate when the record would overrun the extra-field/file boundary.

### Proof of Concept
A `BuildIntegrationTestCase`/native unit test can construct a minimal ZIP whose Central Directory Header declares `extra_field_length` covering a single crafted sub-record with `data_size` set to a value causing `extra_p` to skip past the computed `p` (e.g., `data_size = 0xFFFF` while only a few bytes remain in `extra_field_length`), then feed it to the `ijar` binary (or directly to `InputZipFile::ProcessCentralDirEntry`/`ProcessNext`) and observe the process reading/crashing past the mapped file bounds under ASan, analogous to `input_jar_scan_ziptool_test.cc`'s existing entry-scanning tests [5](#0-4) , but targeting `third_party/ijar` instead of `singlejar`.

I was not able to trace the exact BUILD-graph wiring that invokes the native `ijar` binary from `run_ijar`/`java_import` in this index (only documentation pages for `java_common.run_ijar` were indexed, not the Java implementation that constructs the ijar `SpawnAction`), so the precise action wiring should be confirmed in a full checkout before finalizing a fix; the vulnerable parsing code itself, however, is directly confirmed in `third_party/ijar/zip.cc`.

  // abort with an error message.  "state" is the name of the field
  // we're about to read, for diagnostics.
  int EnsureRemaining(size_t n, const char *state) {
    size_t in_offset = p - zipdata_in_;
    size_t remaining = input_file_->Length() - in_offset;
    if (n > remaining) {
      return error("Premature end of file (at offset %zd, state=%s); "
                   "expected %zd more bytes but found %zd.\n",
                   in_offset, state, n, remaining);
    }
    return 0;
  }

bool InputZipFile::ProcessCentralDirEntry(const u1 *&p, u8 *compressed_size,
                                          u8 *uncompressed_size, char *filename,
                                          size_t filename_size, u4 *attr,
                                          u8 *offset) {
  u4 signature = get_u4le(p);

  if (signature != CENTRAL_FILE_HEADER_SIGNATURE) {
    if (signature != DIGITAL_SIGNATURE && signature != EOCD_SIGNATURE &&
        signature != ZIP64_EOCD_SIGNATURE) {
      error("invalid central file header signature: 0x%x\n", signature);
    }
    return false;
  }

  p += 16;  // skip to 'compressed size' field
  *compressed_size = get_u4le(p);
  *uncompressed_size = get_u4le(p);
  u2 file_name_length = get_u2le(p);
  u2 extra_field_length = get_u2le(p);
  u2 file_comment_length = get_u2le(p);
  p += 4;  // skip to external file attributes field
  *attr = get_u4le(p);
  *offset = get_u4le(p);
  {
    size_t len = (file_name_length < filename_size)
      ? file_name_length
      : (filename_size - 1);
    memcpy(reinterpret_cast<void*>(filename), p, len);
    filename[len] = 0;
  }
  p += file_name_length;
  const u1 *extra_p = p;
  p += extra_field_length;
  while (extra_p != p) {
    const u2 header_id = get_u2le(extra_p);
    const u2 data_size = get_u2le(extra_p);
    const u1 *extra = extra_p;
    extra_p += data_size;
    if (header_id == ZIP64_EXTRA_FIELD_TAG) {
      if (*uncompressed_size == U4_MAX) {
        *uncompressed_size = get_u8le(extra);
      }
      if (*compressed_size == U4_MAX) {
        *compressed_size = get_u8le(extra);
      }
      if (*offset == U4_MAX) {
        *offset = get_u8le(extra);
      }
    }
  }
  p += file_comment_length;
  return true;
}
