Based on my research, I found a genuine local analog to the EIP-2929 cold/warm gas discrepancy bug: `pallet-revive`'s recently introduced EIP-2929-style cold/hot storage access pricing.

### Title
Weight metering discrepancy from per-transaction warm/cold storage access list can cause gas-estimation vs. execution divergence in `pallet-revive` - (File: `substrate/frame/revive/src/vm/runtime_costs.rs`)

### Summary
`pallet-revive` recently added EIP-2929-style cold/hot storage pricing, tracked by a per-transaction `AccessList` [1](#0-0) . Warmth of a `(contract, slot)` pair depends entirely on prior touches within the same top-level transaction/call-stack, and the first touch is billed strictly more (cold) than a later touch to the same slot (hot) [2](#0-1) . This is the exact same primitive as the EIP-2929 issue in the report: cost of an access depends on whether it was previously "warmed" in the same execution context, and this can diverge between an isolated pre-flight simulation (e.g. `eth_estimateGas`/dry-run) and the actual atomic execution, or between different call orderings of the same contract logic within a call stack.

### Finding Description
The weight for `GetStorage`/`SetStorage`/etc. is computed via `weight_for_storage_access`, branching on `Warmth::Cold`/`Warmth::Hot` [3](#0-2) . A contract's validation-style logic (e.g. a precompile-gated check, or a guard that reads a storage slot and reverts if the remaining weight/gas is insufficient) can be crafted to succeed when the slot is charged as "cold" in isolation but the gas/weight budget check is tuned to a narrow margin such that a different warm/cold sequencing (e.g. induced by an attacker calling into the same contract from a different frame position, or the dry-run/estimate API computing weight with a different access-list state than the actual execution) causes the same call to run out of weight during real dispatch. The code's own comment on `AccessList` explicitly documents the danger of this asymmetry: "an out-of-gas at the cold charge after the touch would leave the slot warm without the cold charge being paid, and a later access would then be billed hot" [4](#0-3) . This shows the authors are aware that touch-then-charge ordering combined with rollback semantics is safety-critical; correctness relies on every caller strictly following "touch before charge, and always roll back on revert" — an invariant not enforced by the type system, only by convention/comment.

### Impact Explanation
If gas/weight estimation (used off-chain to set a transaction's declared weight limit, analogous to the individual "simulation" in the ERC-4337 report) computes cost using a warm/cold state that differs from the state seen during actual on-chain dispatch (e.g., because dry-run estimation and final execution build the `AccessList` differently, or because a contract's internal call ordering differs from what was estimated), a transaction that was estimated to succeed can run out of weight during actual dispatch, and vice versa a contract can be built to exploit warm-state assumptions to pass a guard cheaply that should have been priced as cold. This maps to the "public underpriced work that degrades block production" and "runtime bugs that compromise intended behavior" impact categories, since it can cause legitimate transactions to unexpectedly fail on-chain (denial of service for users) or allow specially crafted contracts to under-price storage-heavy operations relative to their true resource cost.

### Likelihood Explanation
This is a newly introduced feature (`pr_12104`, `pr_12599` in the repo's `prdoc` history) [5](#0-4) [6](#0-5) , and I could not fully trace, within the available indexed content, the exact call site in `substrate/frame/revive/src/exec.rs` where `touch_storage_access` is invoked relative to `charge_storage`/weight metering to confirm whether the "touch before charge, roll back on failure" invariant is actually violated on any concrete path, or whether the gas-estimation RPC path (`eth_estimateGas`/dry-run) constructs its `AccessList` identically to real dispatch. The trait definition in `exec.rs` documents the invariant conceptually [7](#0-6)  but the grep for actual call sites in `exec.rs` returned matches I was not able to fully inspect before running out of iterations. This limits confidence that a concrete, exploitable divergence exists versus the mitigations already documented (bounded access list, differential benchmarking, worst-case-cold pricing for fee/weight limit purposes).

	fn weight_for_storage_access<T: Config>(
		kind: StorageAccessKind,
		cold: impl FnOnce() -> Weight,
		hot: impl FnOnce() -> Weight,
		transient: impl FnOnce() -> Weight,
	) -> Weight {
		match kind {
			StorageAccessKind::Persistent(Warmth::Cold { revertible }) => {
				let cost = cold()
					.saturating_add(T::WeightInfo::access_list_touch_cold_full())
					.saturating_sub(T::WeightInfo::access_list_touch_cold_empty());
				if revertible {
					cost.saturating_add(T::WeightInfo::access_list_rollback_amortization())
				} else {
					cost
				}
			},
			StorageAccessKind::Persistent(Warmth::Hot) => hot()
				.saturating_add(Self::hot_storage_overlay_overhead::<T>())
				.saturating_add(T::WeightInfo::access_list_touch_hot_full())
				.saturating_sub(T::WeightInfo::access_list_touch_hot_single_element()),
			StorageAccessKind::Transient => transient(),
		}
	}

title: 'pallet-revive: per-transaction cold/hot storage access pricing'
doc:
- audience: Runtime Dev
  description: |-
    ### Summary
    EIP-2929-style cold/hot(warm) pricing for persistent storage access in pallet-revive. The first non-reverted access to a `(contract, slot)` pair within a transaction is billed "cold" (higher weight); any later access to the same slot is "hot" (cheaper).

    ### Description
    #### Covered operations
    Cold/hot pricing applies to persistent storage:
    - the EVM `SLOAD` / `SSTORE` opcodes,
    - the PVM storage host functions,
    - the storage precompile (`containsStorage` warms the slot like an `SLOAD`).

    #### Access list and rollback
    Hot/cold state is tracked by a new per-transaction access list, whose layout mirrors `TransientStorage`: a current-state set plus a journal and per-frame checkpoints.
    - Nested frames open a checkpoint, so a reverted frame drops the slots it warmed; the top-level frame is never rolled back.
    - A cold touch that journals inside a nested frame also pre-pays a small rollback weight, to cover the cost of a potential revert (which charges no gas).

    #### Memory bound
    The access list is capped at a fixed number of entries per transaction; once full, further new slots are billed cold without being tracked.
    Short slots are held inline (Fix at 32 bytes, VarInline up to MAX_INLINE_KEY_LEN); longer ones (VarLong, up to STORAGE_KEY_BYTES) use a heap-allocated bounded vector.

    #### Benchmarks
    New benchmarks cover the hot storage ops (`seal_set_storage_hot`, `clear_storage_hot`, `contains_storage_hot`, `seal_get_storage_hot`, `take_storage_hot`) and the access-list overhead (`access_list_touch_cold_*`, `access_list_touch_hot_*`, `access_list_rollback_amortization`)
