### Title
Permanent freeze of ETH-implicit accounts via un-resettable `has_in_flight_tx` flag on callback failure - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The Wallet Contract that backs every ETH-implicit account gates all mutating entry points behind an in-memory invariant flag, `has_in_flight_tx`, which is only ever cleared to `false` as the first statement of a handful of promise-callback methods. Because NEAR receipts are atomic and rolled back entirely on failure, any circumstance that causes one of those callback receipts to fail (panic / out-of-gas / unexpected data from an untrusted cross-contract call) discards the `has_in_flight_tx = false` write along with everything else, leaving the flag permanently `true`. Since `rlp_execute` — the *only* way to operate an ETH-implicit account — unconditionally refuses to do anything while the flag is `true`, the account becomes permanently unusable. This mirrors the external report's root cause: an internal balance/invariant flag is silently corrupted by the outcome of an external call that the code does not defensively account for, permanently locking user funds.

### Finding Description
`WalletContract` tracks in-flight execution with a single boolean: [1](#0-0) 

`rlp_execute` is the sole entry point for an ETH-implicit account and short-circuits immediately (returning a `Value`, not spawning any receipt) whenever the flag is set: [2](#0-1) 

The flag is only ever cleared back to `false` inside the private callback methods (`address_check_callback`, `nep_141_storage_balance_callback`, `rlp_execute_callback`, `ban_relayer`), and always as the very first statement of the function body: [3](#0-2) [4](#0-3) [5](#0-4) 

However, nearcore's runtime guarantees per-receipt atomicity: if a receipt's execution result is `Err` (panic, out-of-gas, or any host error), *all* state changes it made — including the `has_in_flight_tx = false` write that happened as its first line — are discarded via `state_update.rollback()`: [6](#0-5) 

So the *only* mechanism that ever resets the invariant is itself vulnerable to being undone by the very receipt that was supposed to reset it. The callback receipts process attacker/counterparty-controlled data before it is safe to assume success: e.g. `nep_141_storage_balance_callback` deserializes and branches on the JSON payload returned by an arbitrary (attacker-chosen or malicious) NEP-141-style `target` contract from the ERC-20 emulation path: [7](#0-6) [8](#0-7) 

The static gas budget attached to this whole callback chain is a small fixed constant computed from `NEP_141_STORAGE_BALANCE_CALLBACK_GAS`/`ADDRESS_CHECK_CALLBACK_GAS` plus the user's requested action gas — not sized defensively against an oversized or pathological `promise_result` payload returned by an untrusted counterparty contract: [9](#0-8) 

If the callback receipt fails for any reason — out-of-gas while copying/deserializing an oversized `promise_result` blob returned by a target/token contract, a panic triggered by unexpected data, or any other host-level error inside the callback body after the flag would have been reset — the entire callback receipt (including the flag reset) rolls back, leaving `has_in_flight_tx == true` in the persisted account state forever.

Because an ETH-implicit account can *only* be controlled through the Wallet Contract's methods (it cannot receive a full access key nor be deleted), this permanently disables the account: [10](#0-9) 

### Impact Explanation
Once `has_in_flight_tx` is stuck at `true`, every subsequent call to `rlp_execute` is rejected at the very first check before any promise is even created, so the owner can never again transfer NEAR, transfer NEP-141 tokens, add a relayer key, or otherwise recover the account. Since ETH-implicit accounts cannot be deleted and cannot receive a full access key by any other means, all NEAR and fungible-token balances held by that account become permanently frozen — a direct, unprivileged-reachable "permanent freezing of funds" outcome. The trigger does not require any special privilege: the victim (or a relayer acting on their behalf) simply has to submit an ERC-20-emulated transfer (or any target contract that returns attacker-controlled data on the callback path) whose target/token contract behaves adversarially or the callback runs low on gas.

### Likelihood Explanation
Reaching the vulnerable code path only requires an ordinary user (or relayer) to interact with the Wallet Contract's ERC-20 emulation, sending an `rlp_execute` transaction targeting a contract that is either malicious or simply returns larger-than-expected `storage_balance_of`/other results, or where gas becomes tight relative to the fixed callback gas constants. No node-level, validator-level, or protocol-level privilege is needed — this is entirely reachable from a normal client transaction and a normal (or attacker-deployed) NEP-141-style contract.

### Recommendation
- Do not rely on a callback's own execution succeeding to restore a safety invariant. Instead, ensure `has_in_flight_tx` (or an equivalent guard) can be reset even when the associated callback fails, e.g. by wrapping fallible/attacker-influenced logic so that any error path still commits the flag reset before doing anything that could panic or run out of gas, or by using a two-phase pattern where the flag reset is the very first *and only* unconditionally-committed state change in a receipt that cannot fail.
- Bound/validate the size and shape of any `promise_result` payload from an untrusted target/token contract before deserializing it, and allocate gas budgets for these callbacks defensively (independent from attacker-controlled response sizes) so cross-contract calls to arbitrary/malicious contracts cannot induce out-of-gas failures inside the reset-critical callback.
- Add a recovery path (e.g., an idempotent, permissionless "unstick" method gated by a timeout) that can clear `has_in_flight_tx` if no callback resolves within an expected window, similar in spirit to using an allow-list/SafeERC20-style defensive wrapper recommended in the original report.

### Proof of Concept
1. Deploy an ETH-implicit account and fund it (creates the Wallet Contract global-contract instance for that account), per `test_eth_implicit_account_creation`.
2. Deploy a non-standard "NEP-141-like" contract whose `storage_balance_of` view method returns a very large or malformed JSON-encodable blob (still fitting the 5 Tgas budget for that specific call, since NEAR limits compute, not necessarily output size cheaply).
3. Have the account's owner (via `rlp_execute`) sign an ERC-20 "transfer" transaction targeting that malicious contract, following the same flow exercised in `test_erc20_emulation`.
4. The resulting cross-contract call resolves into `nep_141_storage_balance_callback`; the oversized/attacker-crafted payload increases the gas cost of processing (`serde_json::from_slice` + follow-on promise construction) inside a callback receipt funded only by the fixed `NEP_141_STORAGE_BALANCE_CALLBACK_GAS` budget, causing the receipt to fail with `FunctionCallError`/`GasExceeded`.
5. Because the receipt failed, per `runtime/runtime/src/lib.rs`'s failed-receipt rollback semantics, the `self.has_in_flight_tx = false;` write made at the top of `nep_141_storage_balance_callback` is discarded.
6. Any subsequent call to `rlp_execute` now immediately returns `"Error: transaction already in progress, please try again later."` for that account, permanently, since `has_in_flight_tx` remains `true` in persisted state and there is no other entry point (no full access key, no deletion) to recover the account.
