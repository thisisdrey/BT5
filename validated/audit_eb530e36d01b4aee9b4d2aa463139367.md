## Analysis

I traced the equality claim directly. On the read side, `RPCGetAttachmentRequestHandler::try_parse_request` validates the path with the regex `^/v2/attachments/(?P<attachment_hash>[0-9a-f]{40})$` and decodes it via `Hash160::from_hex`, storing it in `self.attachment_hash` [1](#0-0) . `try_handle_request` then calls `network.get_atlasdb().find_attachment(&attachment_hash)`, returning `HttpNotFound` unless a row is found [2](#0-1) . `find_attachment`'s underlying storage is keyed by `hash` in the `attachments` table, and `insert_instantiated_attachment`/`insert_uninstantiated_attachment` always write rows keyed on `attachment.hash()` (i.e., `Hash160::from_data(&content)`), never on an attacker-supplied or externally claimed hash [3](#0-2) [4](#0-3) . Because every row's `hash` column is derived from the content's own hash at write time, and the RPC lookup filters `WHERE hash = ?1`, the served bytes' hash and the requested hash are equal by construction — there is no way to store content under a hash that doesn't match its own `Hash160::from_data`. This confirms the serve-side equality holds and the RPC endpoint is not the vulnerable point.

On the write/ingestion side, `AttachmentsBatchStateContext::extend_with_attachments` decodes each peer's HTTP response via `decode_atlas_get_attachment()` and inserts `response.attachment` into `self.attachments` — a `HashSet<Attachment>` — without ever comparing the attachment's own hash against the hash that was requested in the corresponding `AttachmentRequest` [5](#0-4) . Later, in `AttachmentsDownloader::run`, for each attachment drained from this set, the code looks up `find_all_attachment_instances(&attachment.hash())` and calls `insert_instantiated_attachment(&attachment)` [6](#0-5) . Note that `attachment.hash()` here is recomputed from the *content actually received*, not the hash that was originally requested (`AttachmentRequest`'s target `content_hash`), so a malicious/misbehaving peer can respond to a request for hash `H1` with arbitrary content `C2` whose real hash is `H2`; `extend_with_attachments` accepts it unconditionally, and the downloader stores `C2` under `H2` — resolving whatever attachment instances point to `H2`, not `H1`. Since `find_all_attachment_instances` is used to resolve attachment *instances*, not to validate that the requested hash matches, any BNS/attachment instance genuinely waiting on `H2` (from some other, unrelated on-chain event) gets falsely resolved with content that a random peer supplied, and the batch for `H1` is marked incomplete/retried rather than rejected as a peer misbehavior. This is a genuine mismatch: the code that issues `AttachmentRequest` for a specific `content_hash` never verifies, on response, that `Hash160::from_data(&content) == requested_content_hash` before admitting the attachment into local storage and marking associated attachment instances as resolved.

This validates the premise of the question: the read/serve path (`getattachment.rs` + `find_attachment`) is safe because storage itself enforces hash==content at write time via `attachment.hash()`, whereas the download/ingestion path (`extend_with_attachments` in `download.rs`) is exactly where an untrusted peer's claimed pairing between "attachment I asked for" and "attachment I received" is never re-validated against `Hash160::from_data`, before that content becomes canonically resolvable at whatever hash it actually hashes to.

### Title
Missing peer-response hash verification in `extend_with_attachments` allows attachment/BNS mismatch - ([File: stackslib/src/net/atlas/download.rs])

### Summary
`AttachmentsBatchStateContext::extend_with_attachments` accepts any `Attachment` content returned by a peer for an `AttachmentRequest` without checking that `Hash160::from_data(&content)` equals the `content_hash` that was originally requested. This lets a malicious sync peer supply substitute content that gets stored and paired with whatever attachment instances happen to reference its actual (different) hash, serving non-canonical BNS attachment data as canonical.

### Finding Description
The RPC serve path is sound: `getattachment.rs`'s regex/`Hash160::from_hex` validate the hash format, and `AtlasDB::find_attachment` filters `WHERE hash = ?1 AND was_instantiated = 1` against rows whose `hash` column is always set from the content's own `attachment.hash()` at insert time (`insert_instantiated_attachment`, `insert_uninstantiated_attachment`) — so served bytes always hash-match the requested hash [4](#0-3) [3](#0-2) .

The fault is on ingestion: `extend_with_attachments` drains `results.succeeded`, decodes each `GetAttachmentResponse` via `decode_atlas_get_attachment()`, and inserts `response.attachment` directly into the batch's `attachments: HashSet<Attachment>` — with no comparison to the `content_hash` targeted by the originating `AttachmentRequest` [5](#0-4) . `AttachmentsDownloader::run` then, for each such attachment, resolves it against `find_all_attachment_instances(&attachment.hash())` (hash of the *received* content) and calls `insert_instantiated_attachment`, marking matching attachment instances as available [6](#0-5) . A remote peer that legitimately answers an `AttachmentsInventoryRequest`/`AttachmentRequest` (reachable by any node configured as an outbound sync peer — no privilege required) can respond with arbitrary content of its choosing instead of the content matching the requested hash; that content is admitted, stored keyed by its own (different) hash, and used to resolve any attachment instance elsewhere in the system that happens to reference that hash.

### Impact Explanation
An unprivileged remote peer serving attachment content can cause a node to accept and store attacker-chosen bytes, and to mark unrelated attachment instances (BNS name/zonefile bindings) as resolved/available using this attacker-supplied content, rather than the content whose hash was actually requested — i.e., non-canonical content served/treated as canonical for whichever attachment instance happens to share that hash. This matches the "attachment/BNS mismatch" High-impact category in scope.

### Likelihood Explanation
Precondition: the victim node must be actively downloading attachments (an unresolved `AttachmentInstance` exists) and the attacker must be one of the node's outbound sync peers responding to `/v2/attachments/<hash>` GET requests issued by the victim — no secret, no privileged role, and no special peer relationship beyond being a configured/connected peer is required. This is a single crafted HTTP response per attachment request and is repeatable for every subsequent request the victim issues.

### Recommendation
In `extend_with_attachments` (or in `decode_atlas_get_attachment`/before insertion), verify `Hash160::from_data(&response.attachment.content) == request.content_hash` (the hash targeted by the corresponding `AttachmentRequest`) before inserting into `self.attachments`; otherwise, treat the response as failed (bump `report.bump_failed_requests()` and skip), mirroring the equality check already implicitly enforced by the write paths in `AtlasDB`.

### Proof of Concept
1. In `stackslib/src/net/atlas/tests.rs` (or a new test module for `download.rs`), construct an `AttachmentsBatchStateContext` with a pending `AttachmentRequest` targeting `content_hash = H1`.
2. Simulate a `BatchedRequestsResult` where the peer's response contains an `Attachment` whose content hashes to `H2 != H1` (e.g., `Attachment::new(b"malicious".to_vec())`).
3. Call `extend_with_attachments` and assert that `context.attachments` contains the `H2` attachment despite the request being for `H1` — demonstrating the missing equality check (contrast with `getattachment.rs`, where a control test requesting `/v2/attachments/<H1>` for content pre-inserted at `H2` correctly returns `HttpNotFound`, proving the RPC serve side never returns bytes for the wrong hash).
4. Extend to `AttachmentsDownloader::run` with a real `AtlasDB` and an `AttachmentInstance` for `H2` pending resolution; assert that after processing, the instance for `H2` is marked available/resolved using content that was fetched in response to a request for `H1`, confirming cross-hash resolution.

    pub fn extend_with_attachments(
        mut self,
        results: &mut BatchedRequestsResult<AttachmentRequest>,
    ) -> AttachmentsBatchStateContext {
        for (request, response) in results.succeeded.drain() {
            let report = self
                .peers
                .get_mut(request.get_url())
                .expect("Atlas: unable to retrieve reliability report for peer");

            let response = if let Some(r) = response {
                r
            } else {
                report.bump_failed_requests();
                continue;
            };

            if let Ok(response) = response.decode_atlas_get_attachment() {
                self.attachments.insert(response.attachment);
                report.bump_successful_requests();
            } else {
                report.bump_failed_requests();
            }
        }
        let mut events_ids = results.faulty_peers.keys().copied().collect::<Vec<usize>>();
        self.events_to_deregister.append(&mut events_ids);

        self
    }
