### Title
Unbounded delegation-index growth via repeated minimal `DelegateResourceContract` calls causes unbounded-cost prefix scan in `GetDelegatedResourceAccountIndexV2` query path - (File: chainbase/src/main/java/org/tron/core/store/DelegatedResourceAccountIndexStore.java)

### Summary
`DelegateResourceActuator` allows any account to delegate resources to an unlimited number of distinct receiver addresses with only a minimal `1 TRX` per call, no cap on repetitions, and full reversibility via `UnDelegateResourceActuator`. Each such call adds a new persistent key-value entry keyed by `(owner, receiver)` in `DelegatedResourceAccountIndexStore` (V2 model). The read path (`getV2Index` → `getWithPrefix`) performs an unbounded `prefixQuery` over all entries for a given address and sorts them in memory on every single API call, with no pagination or size limit — mirroring the reported bug class where cheap, repeated deposit/withdraw-style calls inflate an array that is later iterated/aggregated in full by a downstream function.

### Finding Description
`DelegateResourceActuator.validate()` only requires `delegateBalance >= TRX_PRECISION` (1 TRX) and that the receiver account exists; it places no limit on how many distinct receivers a single owner can delegate to, nor any delay/cooldown between delegate/undelegate cycles: [1](#0-0) 

Each successful delegation writes a new entry into `DelegatedResourceAccountIndexStore` under `V2_FROM_PREFIX`/`V2_TO_PREFIX` keyed by `owner+receiver` (one distinct DB key per receiver, so no de-duplication/cap on count for a given owner): [2](#0-1) [3](#0-2) 

The corresponding query path used to serve `GetDelegatedResourceAccountIndexV2` (exposed via HTTP/gRPC on FullNode, SolidityNode, and PBFT node) performs an unbounded `prefixQuery` for both the "from" and "to" prefixes of the address, collects **all** matching entries into a list, and sorts them by timestamp on every request: [4](#0-3) 

There is no limit, pagination, or cap on the number of entries returned/scanned in this path, unlike the write-side `1 TRX` minimum which does nothing to bound the *number* of relations an attacker can create. Because `UnDelegateResourceActuator` allows reclaiming the delegated balance and removing the index entry once the delegation is no longer locked, the attacker's capital is only tied up for the delegate/undelegate cycle (transaction fees plus 1 TRX momentarily locked per receiver), letting the attacker cheaply and repeatedly grow the number of relation records associated with their own address — analogous to the CrabNetting `deposits`/`withdraws` array growth via minimal repeated `depositUSDC`/`withdrawUSDC` calls, where `depositAuction`/`withdrawAuction` later iterate the full array.

### Impact Explanation
`getV2Index` is on the read path invoked by `Wallet` for the `GetDelegatedResourceAccountIndexV2` HTTP/gRPC/JSON-RPC-adjacent endpoints (also exposed on Solidity and PBFT nodes): [5](#0-4) 

If an attacker inflates the number of distinct delegation relations for a chosen address to a very large number, every subsequent request to this query (which any anonymous API client can issue for any address, including the attacker's own) triggers a full prefix scan of potentially very many DB entries plus an in-memory sort, with no page/limit parameter to bound the work. This can materially degrade full node, solidity node, and PBFT node query-serving capacity (CPU/IO amplification per request), i.e., "an API the node can no longer serve" as tolerated by scope. Because each relation is a first-class capsule (own key, own protobuf serialization/deserialization overhead), the per-call cost of the endpoint scales with attacker-controlled state, unlike bandwidth/energy metering, which only limits the write-side transaction cost, not the aggregate query-side cost incurred later by all callers.

### Likelihood Explanation
The only prerequisites are: (1) sufficient TRX/bandwidth to submit many low-cost `DelegateResourceContract` transactions (1 TRX momentarily locked, reversible via `UnDelegateResourceContract`), and (2) existing receiver accounts (trivially created via ordinary transfers). No special privilege, SR/witness status, or novel primitive is required — this is reachable purely through signed transactions from an ordinary account, matching the "unprivileged transaction broadcaster" reachability required by scope. The attack is inexpensive relative to potential query-serving disruption it can later cause.

### Recommendation
- Add pagination (offset/limit) to `getV2Index`/`getWithPrefix` and to the corresponding servlet/gRPC handlers so a single query cannot force scanning/sorting an unbounded number of entries.
- Consider capping the number of distinct delegation relations (`toAccounts`/`fromAccounts`) an account can hold, or introducing a minimum delegation size/cooldown to make repeated minimal delegate/undelegate cycles economically costly, similar to the report's suggested delay-based mitigation.
- Alternatively, precompute/maintain a bounded summary rather than performing full prefix scans and sorts on every read request.

### Proof of Concept
1. Attacker account `A` creates `N` fresh receiver accounts `R1..RN` via ordinary TRX transfers (any minimal transfer activates a new account).
2. `A` freezes TRX for BANDWIDTH/ENERGY (`FreezeBalanceV2Contract`), then issues `N` `DelegateResourceContract` transactions, each delegating the minimum `1 TRX` of bandwidth to a distinct `Ri`, each creating a new `DelegatedResourceAccountIndexCapsule` entry keyed by `(A, Ri)` per `DelegateResourceProcessor.delegateResource` [2](#0-1) .
3. Optionally, `A` issues `UnDelegateResourceContract` transactions to reclaim the frozen TRX and repeats step 2 with new receiver addresses, cheaply multiplying the number of ever-created relation records tied to `A`'s address if the store/index doesn't fully purge historical entries, or simply keeps them delegated permanently since capital is not the limiting cost, only fee/gas is.
4. Any client calls `GetDelegatedResourceAccountIndexV2` for address `A` [6](#0-5) , which triggers `getV2Index(A)` → `getWithPrefix` performing two unbounded `prefixQuery` scans and a full sort over all `N` relations [7](#0-6) , consuming CPU/IO proportional to attacker-chosen `N` on every single request, degrading the node's ability to serve this (and potentially other) queries as `N` grows.

A full Devin session with complete repository access could confirm this wiring precisely.*

  public DelegatedResourceAccountIndexCapsule getV2Index(byte[] address) {
    return getWithPrefix(V2_FROM_PREFIX, V2_TO_PREFIX, address);
  }

  private DelegatedResourceAccountIndexCapsule getWithPrefix(byte[] fromPrefix, byte[] toPrefix, byte[] address) {
    DelegatedResourceAccountIndexCapsule tmpIndexCapsule =
        new DelegatedResourceAccountIndexCapsule(ByteString.copyFrom(address));

    byte[] key = Bytes.concat(fromPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpToList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpToList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    List<ByteString> list = tmpToList.stream()
        .map(DelegatedResourceAccountIndexCapsule::getAccount).collect(Collectors.toList());
    tmpIndexCapsule.setAllToAccounts(list);

    key = Bytes.concat(toPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpFromList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpFromList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    list = tmpFromList.stream().map(DelegatedResourceAccountIndexCapsule::getAccount).collect(
        Collectors.toList());
    tmpIndexCapsule.setAllFromAccounts(list);
    return tmpIndexCapsule;
  }
