### Title
Permanent freeze of ETH-implicit wallet funds via stuck `has_in_flight_tx` flag when an oversized promise return value exhausts fixed callback gas - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The `WalletContract` that backs every ETH-implicit account (the only way such an account can be used, since it can never hold a full-access key or be deleted) gates all user actions behind a single boolean, `has_in_flight_tx`. This flag is set to `true` before a cross-contract promise is dispatched and is only reset to `false` as the very first statement of the corresponding `#[private]` callback (`rlp_execute_callback`, `address_check_callback`, `nep_141_storage_balance_callback`, `ban_relayer`). If that callback receipt itself fails/panics (e.g. runs out of its fixed gas budget), the entire receipt — including the `has_in_flight_tx = false` write — is rolled back per NEAR's failed-receipt atomicity guarantee, leaving the flag stuck at `true` forever with no privileged or alternate path to reset it.

### Finding Description
`rlp_execute` refuses to do anything once `has_in_flight_tx` is true: [1](#0-0) 

The flag is set `true` right after a promise is successfully created, and the *only* place it is ever reset is inside the private callbacks, as their first line: [2](#0-1) [3](#0-2) 

Each callback is scheduled with a fixed, hard-coded gas budget (`RLP_EXECUTE_CALLBACK_GAS = 5 Tgas`, similarly for `ADDRESS_CHECK_CALLBACK_GAS`/`NEP_141_STORAGE_BALANCE_CALLBACK_GAS`): [4](#0-3) 

`rlp_execute_callback` reads the promise result and, on success, wraps the returned bytes into `ExecuteResponse.success_value` for JSON serialization back to the caller: [5](#0-4) 

The action that produces this promise result is a `FunctionCall` chosen by the *user's* signed Ethereum transaction and dispatched to an *arbitrary* `target` account (`action_to_promise`): [6](#0-5) 

Because `target` and the called method are attacker/user-controlled, the callee contract can return an arbitrarily large byte value (up to the protocol-level return-value/register size limits) as its success value. Serializing and returning that oversized value inside `rlp_execute_callback` consumes WASM gas proportional to its size; if it exceeds the fixed `RLP_EXECUTE_CALLBACK_GAS` budget, the callback receipt fails with a gas-exceeded error before it even reaches (or completes) the `self.has_in_flight_tx = false` mutation region of committed state.

Per the runtime's documented invariant, a failing receipt causes a full rollback of all state changes made during that receipt: [7](#0-6) 

Since `has_in_flight_tx` was already committed as `true` in the *prior* (successful) receipt that dispatched the promise, and the callback receipt that was supposed to flip it back to `false` never durably commits due to running out of gas, the flag remains permanently `true`. From that point on, every future call to `rlp_execute` is short-circuited at the very first check and returns the "transaction already in progress" error, without ever creating a new promise or attempting a new balance-affecting action.

Because ETH-implicit accounts:
- cannot have a full-access key added (`AddFullAccessKey` is explicitly rejected by `action_to_promise`), and
- cannot be deleted (per the NEP-518 wallet-contract design; there is no `DeleteAccount` path exposed through `rlp_execute`),

there is no way — privileged or otherwise — to reset `has_in_flight_tx` or otherwise regain control of the account once it is stuck. All NEAR (and any other assets reachable only through this account, e.g. tokens requiring an `ft_transfer` initiated from it) become permanently inaccessible.

This is the direct analog of the reported bug class: a single boolean "in-progress/pause" gate that blocks the user's only legitimate path to move their own funds, with no recovery mechanism, but here the "unpause" that failed to happen is not an operator's function call but a gas-metering roll-back — making the freeze permanent rather than merely inconvenient.

### Impact Explanation
If triggered, this results in **permanent freezing of all funds held by the affected ETH-implicit account**, matching the "permanent freezing of funds" impact category. There is no admin, guard, or governance key that can reset the flag (unlike the original Solidity report where a guard could eventually unpause); the NEAR account itself has no full-access key and cannot be deleted, so the freeze is irrecoverable through the protocol layer.

### Likelihood Explanation
Reachability requires only an ordinary user transaction: an ETH-implicit account owner (or a relayer acting on their signed instructions) issuing an `rlp_execute` call whose decoded action is a `FunctionCall` to a `target` contract that returns an oversized value on success. This can happen either (a) accidentally, if the target contract's success return value happens to be large (e.g., an NFT/token contract returning verbose JSON, or a contract with unusually large method output), or (b) if a malicious/compromised relayer or contract deliberately crafts such a call to grief a specific ETH-implicit account it doesn't like, or to grief itself/others as a denial-of-funds attack. No special privileges are needed to reach any of these paths — the `target`, method name, and by-extension the size of the returned value are all attacker/user-influenced inputs to `rlp_execute`.

### Recommendation
- Ensure `RLP_EXECUTE_CALLBACK_GAS` (and the other fixed callback gas constants) reserve enough headroom to always safely truncate or bound the returned `success_value` regardless of the callee's output size, rather than relying on a fixed constant sized for the "happy path."
- Alternatively, avoid echoing the raw promise-result bytes back through `ExecuteResponse` when they exceed a safe size; truncate or drop oversized payloads before serialization so the callback's gas cost is bounded independent of the callee's behavior.
- More fundamentally, decouple the "in-flight" guard from a single unconditional boolean with no timeout/reset path: consider giving the wallet owner (verified via their Secp256k1 signature, the same trust root used for `rlp_execute`) a way to force-clear a stuck `has_in_flight_tx` flag (e.g., after some cooldown of blocks/gas-exhaustion evidence), so a stuck callback cannot permanently strand the account.

### Proof of Concept
1. Deploy the Wallet Contract as the global contract for ETH-implicit accounts, and fund an ETH-implicit account `A` (as in `test_wallet_contract_interaction`, `runtime/near-wallet-contract/implementation/wallet-contract/src/tests/...`).
2. Deploy an attacker-controlled contract `Evil` whose method `big_output()` returns a large byte blob close to the protocol's maximum return-value/register size.
3. Have the owner of `A` (or a relayer on their behalf) sign an Ethereum-style transaction whose decoded NEAR action is `FunctionCall { receiver: Evil, method_name: "big_output", gas: <small>, deposit: 0 }`, and submit it via `rlp_execute(target = Evil, tx_bytes_b64 = ...)`.
4. `inner_rlp_execute` dispatches the `FunctionCall` to `Evil` via `action_to_promise`, chained to `.then(ext.rlp_execute_callback(...))` with only `RLP_EXECUTE_CALLBACK_GAS` (5 Tgas) reserved for the callback; `has_in_flight_tx` is set `true` and this receipt commits successfully.
5. `Evil::big_output()` succeeds and returns its large payload. The scheduled `rlp_execute_callback` receipt begins executing, attempts to construct/serialize `ExecuteResponse { success_value: Some(<huge bytes>), .. }`, and exceeds its 5 Tgas allocation, causing the receipt to fail with a gas-exceeded error.
6. Per receipt-failure atomicity, the state changes of this callback receipt (including the intended `self.has_in_flight_tx = false`) are rolled back; `has_in_flight_tx` remains `true` as committed by step 4.
7. Any subsequent `rlp_execute` call against account `A` now immediately returns `"Error: transaction already in progress, please try again later."` forever — the account, and all NEAR/tokens it holds, become permanently inaccessible.

Note: I was not able to fully verify from the indexed code the exact numeric register/return-value size limit enforced elsewhere in `near-vm-runner` (the config parameter controlling maximum returned-data size), nor the precise per-byte JSON-serialization gas cost inside near-sdk's generated callback wrapper, both of which determine the exact payload size needed to exceed 5 Tgas. Confirming the precise threshold would require inspecting `near-vm-runner`'s host-function cost table and near-sdk's serialization code paths, which were not fully retrievable through the available index.

## Invariants & failure modes

- **Gas ordering**: `merge` asserts `gas_burnt_for_function_call <= gas_burnt <= gas_used` per action (`runtime/runtime/src/lib.rs:440`).
- **Failed receipt atomicity**: a receipt whose result is `Err` triggers `state_update.rollback()`, so no state changes persist except the outcome/gas accounting (`runtime/runtime/src/lib.rs:967`). `set_error` additionally clears queued receipts, proposals, and burnt/subsidized amounts (`runtime/runtime/src/lib.rs:487`).
- **Staking invariant**: `update_validator_accounts` returns a fatal `StorageInconsistentState` if `locked < max_of_stakes` (`runtime/runtime/src/lib.rs:1617`).
- **Invalid txs make progress, not failure**: a chunk with invalid transactions is not rejected; the offending txs are skipped during conversion, polluting the chain with junk but keeping the shard live (`runtime/runtime/src/lib.rs:1706` doc; skip sites at `:1994`, `:2199`).
- **Refund receipts are free**: system-predecessor receipts burn zero gas; a failed refund burns its deposit into `other_burnt_amount` rather than refunding (`runtime/runtime/src/lib.rs:929`, `:972`).
- **Delayed receipts must stay valid**: a delayed receipt that fails `validate_receipt` on dequeue is treated as `StorageInconsistentState` (`runtime/runtime/src/lib.rs:2500`).
