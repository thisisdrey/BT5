Based on my research, the closest legitimate analog to the reported bug class (an on-chain, attacker-influenceable "baseline" value used as a pass/fail gate, causing perpetual denial of the operation) in this Gitaly codebase is the checksum-consistency check in `RewriteHistory`.

### Title
`RewriteHistory` checksum-consistency gate can be kept permanently failing by concurrent repository writes, causing persistent denial of service - (File: internal/gitaly/service/cleanup/rewrite_history.go)

### Summary
`RewriteHistory` computes a repository "checksum" before and after running `git-filter-repo`, and aborts the whole (potentially expensive) operation if the two checksums differ, on the theory that the repository was mutated concurrently and the rewrite result is now stale. Because the "before" and "after" checksums are computed on-the-fly from live repository state rather than being pinned to a fixed pre-agreed baseline, any actor with ordinary push access to the repository can keep the repository's checksum changing throughout the (potentially long) `git-filter-repo` run, causing the post-rewrite validation to fail every time and denying the `RewriteHistory` RPC from ever completing successfully — directly mirroring the reported pattern of an unstable, attacker-influenceable "expected" value gating an operation.

### Finding Description
`rewriteHistory()` captures `initialChecksum` before invoking `s.runFilterRepo(...)`, then recomputes `validationChecksum` after the (long-running) filter-repo pass completes, and hard-fails the RPC if the two differ: [1](#0-0) 

This is structurally identical to the reported pattern: an on-the-fly computed "expected" value (`calcImpact`'s `baselineAmount` there, `checksumRepo(ctx, repo)` here) is compared against a live/actual outcome, and any mismatch aborts the whole operation with an error (`WorseRate` there, `structerr.NewAborted("source repository checksum altered")` here): [2](#0-1) 

Because `git-filter-repo` on a large repository can run for an extended period, an ordinary user with write access to the same repository (a legitimate, unprivileged push actor — not a malicious peer, MITM, or privileged operator) can push arbitrary trivial commits/refs repeatedly during that window. Each push changes the live repository state, so `checksumRepo` computed after the rewrite will practically always disagree with the value captured before the rewrite began, causing the abort branch to trigger on essentially every invocation for an actively-used repository.

I was not able to view the exact implementation of `checksumRepo` (its definition lives outside the range I could inspect within the given tool budget), so I cannot confirm precisely which git state it hashes (e.g., all refs, all objects, etc.); however, the control-flow logic that turns any observed drift into an unconditional abort is fully confirmed at the cited lines.

### Impact Explanation
For any repository that receives even light, ordinary push traffic during the (long) `git-filter-repo` execution window, `RewriteHistory` — a feature specifically intended for redacting sensitive blobs/text (e.g., leaked credentials) from history — becomes unusable: the RPC will reliably abort with "source repository checksum altered" instead of completing the rewrite. This is a denial of service of a specific RPC handler, and because the check re-triggers deterministically as long as pushes continue, an unprivileged writer to the repository can indefinitely block a legitimate cleanup/redaction operation from ever succeeding.

### Likelihood Explanation
Likelihood is moderate-to-high for actively used repositories: no attacker sophistication is required beyond having ordinary push access and issuing routine commits during the operation window; `git-filter-repo` runs can be lengthy for larger histories, widening the race window naturally without any need for precise timing or flash-loan-style manipulation.

### Recommendation
Do not treat "any state drift during the rewrite" as an unconditional hard failure of the whole operation. Instead, either (a) exclude and quarantine writes to the repository for the duration of the rewrite (e.g., via a lock/reference-transaction hook) so the baseline cannot be invalidated by ordinary concurrent activity, or (b) compute the "changed" determination against a narrower, well-defined baseline (e.g., only the refs that filter-repo is expected to rewrite) rather than a whole-repository checksum that any unrelated push can perturb, and retry/reconcile instead of unconditionally aborting.

### Proof of Concept
1. Start a `RewriteHistory` RPC against a repository with a non-trivial history (long enough for `git-filter-repo` to run for a noticeable duration).
2. As an ordinary user with push access to that same repository, issue a trivial push (e.g., an empty commit) shortly after step 1 begins, before `rewriteHistory` reaches its post-rewrite checksum recomputation.
3. Observe that `validationChecksum` computed at [3](#0-2)  differs from `initialChecksum`, causing the RPC to abort at [2](#0-1) .
4. Repeat step 2 on every subsequent `RewriteHistory` attempt to keep the operation permanently failing for that repository.

	initialChecksum, err := checksumRepo(ctx, repo)
	if err != nil {
		return fmt.Errorf("calculate initial checksum: %w", err)
	}

	if err := s.runFilterRepo(ctx, repo, stagingRepo, blobsToRemove, redactions); err != nil {
		return fmt.Errorf("rewriting repository history: %w", err)
	}

	// Recheck repository state to confirm no changes occurred while filter-repo ran. The
	// repository may not be fully rewritten if it was modified after git-fast-export(1)
	// completed.
	validationChecksum, err := checksumRepo(ctx, repo)
	if err != nil {
		return fmt.Errorf("recalculate checksum: %w", err)
	}

	if initialChecksum != validationChecksum {
		return structerr.NewAborted("source repository checksum altered").WithMetadataItems(
			structerr.MetadataItem{Key: "initial checksum", Value: initialChecksum},
			structerr.MetadataItem{Key: "validation checksum", Value: validationChecksum},
		)
	}
