## Title
Unconditional witness-Vi advance in `DelegationStore.accumulateWitnessVi` causes permanent loss of voter rewards when a witness's vote count is zero for a cycle — (File: `chainbase/src/main/java/org/tron/core/store/DelegationStore.java`)

### Summary
`DelegationStore.accumulateWitnessVi` is the java-tron analog of `RangePool.sync`: it is a per-cycle "accumulator advance" function that is called unconditionally every maintenance cycle for every witness, regardless of whether that witness actually had any active votes ("liquidity") during the cycle. Just like `RangePool.sync` always moves `lastUpdated` forward and silently drops the per-token reward amount when `liquidity == 0`, `accumulateWitnessVi` always "forwards" the previous Vi checkpoint and drops the cycle's already-recorded reward amount when `voteCount == 0`, permanently orphaning that reward.

### Finding Description
Block/standby rewards are recorded independent of a witness's vote count. `MortgageService.payReward` unconditionally does `delegationStore.addReward(cycle, witnessAddress, value)` for every reward paid to a witness in the current cycle, with no check on how many votes that witness has: [1](#0-0) 

At the start of every maintenance cycle, `MaintenanceManager.doMaintenance` unconditionally calls `accumulateWitnessVi` for the *current* cycle for every witness before that cycle's votes are finalized: [2](#0-1) 

`DelegationStore.accumulateWitnessVi` is the reward-per-vote accumulator (the direct analog of `RangePool`'s rewards-per-liquidity accumulator). When `voteCount == 0` for that cycle, it does **not** increase Vi — it just "forwards" the previous value and returns, exactly like `RangePool.sync` skipping `_accumulateToken` when `liquidity == 0`: [3](#0-2) 

The critical defect is that the reward already stored via `addReward(cycle, witnessAddress, value)` for that cycle is never retried or carried forward once `voteCount` becomes non-zero in a later cycle. `computeReward` in `MortgageService` only ever looks at the delta between two Vi checkpoints (`endVi - beginVi`) to compute a voter's share: [4](#0-3)  and the older per-cycle path explicitly `continue`s (skips) any cycle whose recorded `totalVote == 0`: [5](#0-4) 

Because the cycle pointer (`curCycle`) always advances at the end of `doMaintenance` regardless of whether the reward was actually converted into claimable Vi units, the reward amount recorded for that specific cycle is silently and permanently orphaned — it was already deducted/accounted for as "paid" to the witness's reward bucket, but no voter (past, present, or future) can ever claim it, since the Vi accumulator that all downstream reward computations key off of never reflects it. This mirrors the reported BMX root cause precisely: an unconditional state-advance (`lastUpdated` / cycle-Vi checkpoint) that consumes an already-computed reward window even though the "active stake" (`liquidity` / `voteCount`) was zero, with no mechanism to replay or preserve that window once stake reappears.

### Impact Explanation
This is a stake/delegation/reward-math correctness bug reachable through the normal, unprivileged consensus reward flow (any account can freeze TRX for TRON Power and vote for a witness via the standard `VoteWitnessContract`/actuator path, or a witness can simply have zero votes transiently). Reward TRX that is already recorded as earned by a witness for a given cycle becomes permanently unclaimable by any voter once that cycle's `voteCount` was zero, while the accounting continues to treat it as paid. This is a denial-of-reward / permanent-loss-of-funds correctness issue matching the Medium/High severity bar of the source finding (funds intended for distribution become unbacked/unreachable, not stolen but permanently frozen from any legitimate claimant).

### Likelihood Explanation
This requires no attacker action beyond normal protocol usage: any witness that temporarily has zero votes (e.g., a newly registered witness, or a witness whose voters have not yet voted in a given cycle window) while still receiving standby/block rewards will trigger this path every maintenance cycle. Given `useNewRewardAlgorithm` is the modern default reward path, this is a realistically reachable condition, not a contrived edge case.

### Recommendation
Do not treat a cycle's reward as "consumed" by advancing the Vi checkpoint when `voteCount == 0`. Instead of dropping the reward amount recorded via `addReward` for that cycle, either (a) roll the un-distributed reward amount forward into the next cycle's reward bucket for that witness so it eventually gets folded into a Vi computation once votes exist, or (b) prevent `payReward`/`addReward` from crediting a cycle's reward pool for a witness with zero votes in the first place, redirecting it elsewhere (e.g., back to the general incentive pool) rather than silently discarding the claim path.

### Proof of Concept
1. Register a new witness `W` with `voteCount == 0` in `witness.getVoteCount()`.
2. Have `payStandbyWitness`/`payBlockReward` credit `W` a reward for `curCycle` via `delegationStore.addReward(curCycle, W, value)` (`MortgageService.java:79-87`).
3. At `doMaintenance`, `accumulateWitnessVi(curCycle, W, 0)` runs before votes are tallied for the cycle (`MaintenanceManager.java:96-100`); since `voteCount == 0`, Vi is not incremented for `curCycle` (`DelegationStore.java:133-146`).
4. In a later cycle, a voter votes for `W` and `voteCount` becomes non-zero; `computeReward` only ever diffs Vi between the voter's `beginCycle` and `endCycle`, so the `curCycle` reward recorded in step 2 never contributes to any voter's `deltaVi` (`MortgageService.java:215-229`).
5. The reward TRX credited to `W`'s bucket for `curCycle` is now unclaimable by any account, while system-wide accounting had already treated it as paid out of the incentive pool.

  private long computeReward(long cycle, List<Pair<byte[], Long>> votes) {
    long reward = 0;
    for (Pair<byte[], Long> vote : votes) {
      byte[] srAddress = vote.getKey();
      long totalReward = delegationStore.getReward(cycle, srAddress);
      if (totalReward <= 0) {
        continue;
      }
      long totalVote = delegationStore.getWitnessVote(cycle, srAddress);
      if (totalVote == DelegationStore.REMARK || totalVote == 0) {
        continue;
      }
      long userVote = vote.getValue();
      double voteRate = (double) userVote / totalVote;
      reward += voteRate * totalReward;
    }
    return reward;
  }

  public void accumulateWitnessVi(long cycle, byte[] address, long voteCount) {
    BigInteger preVi = getWitnessVi(cycle - 1, address);
    long reward = getReward(cycle, address);
    if (reward == 0 || voteCount == 0) { // Just forward pre vi
      if (!BigInteger.ZERO.equals(preVi)) { // Zero vi will not be record
        setWitnessVi(cycle, address, preVi);
      }
    } else { // Accumulate delta vi
      BigInteger deltaVi = BigInteger.valueOf(reward)
          .multiply(DECIMAL_OF_VI_REWARD)
          .divide(BigInteger.valueOf(voteCount));
      setWitnessVi(cycle, address, preVi.add(deltaVi));
    }
  }
