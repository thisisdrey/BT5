## Analog Vulnerability: Order-book griefing DoS via `MAX_MATCH_NUM` revert in `MarketSellAssetActuator`

### Title
Denial-of-service griefing on Market (DEX) matching — attacker floods a price level with dust orders to force victim sell transactions to revert - (File: `actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java`)

### Summary
The external report describes an attacker keeping a "state" artificially active (via minimal partial swaps) so that a size/state check inside a shared code path (`swapActive`/`poke`) always reverts, blocking legitimate users while the attacker benefits from favorable pricing over time. The closest reachable analog in java-tron's on-chain, permissionless order-matching logic is the hard-coded `MAX_MATCH_NUM` cap inside `MarketSellAssetActuator.matchOrder`. Any unprivileged account can place many small "dust" maker orders at the best price for a trading pair; when a legitimate taker's `MarketSellAssetContract` needs to match against more than `MAX_MATCH_NUM` (20) resting orders at that price, the actuator throws `ContractValidateException("Too many matches...")`, which is converted to `ContractExeException` and causes the whole transaction to fail [1](#0-0) , while the victim's bandwidth/energy fee is still consumed because resource accounting happens before actuator execution in `Manager.processTransaction` [2](#0-1) .

### Finding Description
`MarketSellAssetActuator` matches a taker's sell order against maker orders resting in the order book, walking the linked list of orders at the best price level and incrementing `matchOrderCount` for every match. If more than `MAX_MATCH_NUM` (20) matches are required to fill or partially fill a taker order at a single price level, the method throws `ContractValidateException`, which propagates out of `execute()` as `ContractExeException`, failing the whole transaction [3](#0-2) .

Any account can create up to `MAX_ACTIVE_ORDER_NUM` (100) simultaneous active orders [4](#0-3) , so an attacker can place 21+ minimal-size orders at the single best price for a given token pair. Any subsequent, unrelated user attempting to sell into that price level — where their order size would naturally consume more than 20 of these dust orders — will have their transaction unconditionally revert with "Too many matches", regardless of how much liquidity is actually available in the book beyond those 20 orders.

Crucially, transaction resource consumption (bandwidth/energy) happens in `Manager.processTransaction` via `consumeBandwidth`/`consumeMultiSignFee`/`consumeMemoFee` before the actuator (`trace.exec()`) runs [2](#0-1) , meaning the victim pays real fees for a transaction that is guaranteed to fail as long as the attacker maintains ≥21 dust orders at that price. The attacker can trivially refill orders that get consumed (each order, even 1 unit, still occupies a matching slot per `matchOrder`'s `matchOrderCount` increment), keeping the griefing state persistent at negligible cost (only the per-order `MarketSellFee`), and can withdraw/cancel them at will via `MarketCancelOrderActuator` once done extracting value [5](#0-4) .

This mirrors the reported bug class precisely: a state (order-book depth at the best price) that is cheap for an attacker to keep in a specific configuration, causing a fixed, protocol-level limit (`MAX_MATCH_NUM`, analogous to the `sync`/`poke` check) to unconditionally block legitimate operations (other users' sell orders) for as long as the attacker chooses to maintain it.

### Impact Explanation
- Legitimate market participants attempting to sell against the best price of a pair can have their transactions repeatedly and predictably fail ("Too many matches"), wasting bandwidth/energy fees each attempt — a direct, repeatable resource-griefing DoS reachable by any address holding TRX/tokens, matching the "unauthorized... theft... node crash/halt... API the node can no longer serve" bar loosely via forced fee loss and guaranteed transaction failure for arbitrary victims.
- Because the attacker fully controls when to cancel their dust orders, this can also be leveraged to manipulate the effective depth/availability of a trading pair, denying other users the ability to trade at a given price while the attacker's own orders sit ahead of them in the queue — a market-manipulation-adjacent DoS, directly analogous to the Dutch-auction price-manipulation incentive in the original report.

### Likelihood Explanation
Likelihood is high: it requires only standard `MarketSellAssetContract` calls (already reachable by any signed transaction from an unprivileged account, once `supportAllowMarketTransaction` is enabled by committee), no special privileges, and the cost to the attacker is bounded by `MarketSellFee` times number of dust orders (≥21), which is cheap relative to the guaranteed fee loss inflicted on every victim transaction that attempts to cross that price level.

### Recommendation
- Do not hard-fail the whole transaction when `MAX_MATCH_NUM` is exceeded; instead, partially fill up to the limit and leave the remainder of the taker order resting in the book (similar to how partial fills are already handled elsewhere in `matchSingleOrder`), so legitimate takers are not forced to pay fees for a doomed transaction.
- Consider a minimum order size (dust threshold) for `MarketSellAssetContract`/order creation to prevent cheap flooding of a single price level with many tiny orders.
- Consider charging a fee proportional to the number of orders an account maintains at the same price level, or capping the number of *orders per price level* (not just per account) to reduce the ease of monopolizing/blocking a specific price point.

### Proof of Concept
1. Attacker (address A) enables market trading is already on (committee flag `supportAllowMarketTransaction`).
2. Attacker submits 25 `MarketSellAssetContract` transactions, each a minimal-size sell order for pair (X, Y) at the best (lowest) price, all resting via `saveRemainOrder` [6](#0-5) . This is well within `MAX_ACTIVE_ORDER_NUM=100` per account.
3. Victim (address B) submits a `MarketSellAssetContract` for pair (Y, X) with a size that requires matching more than `MAX_MATCH_NUM=20` of A's dust orders to fill.
4. `matchOrder` walks the order list, incrementing `matchOrderCount`; once it exceeds 20, it throws `ContractValidateException("Too many matches...")`, causing B's transaction to fail with `ContractExeException`, while B's bandwidth/energy was already consumed by `Manager.processTransaction` prior to execution [7](#0-6) .
5. Attacker repeats replenishing dust orders as they get consumed by partial matches from other victims, keeping the price level permanently blocked for large sell attempts at negligible cost, as confirmed by the existing test `exceedMaxMatchNumLimit` which reproduces the exact revert condition [8](#0-7) .

      TransactionResultCapsule ret, AccountCapsule takerAccountCapsule)
      throws ItemNotFoundException, ContractValidateException {

    byte[] makerSellTokenID = buyTokenID;
    byte[] makerBuyTokenID = sellTokenID;
    byte[] makerPair = MarketUtils.createPairKey(makerSellTokenID, makerBuyTokenID);

    // makerPair not exists
    long makerPriceNumber = pairToPriceStore.getPriceNum(makerPair);
    if (makerPriceNumber == 0) {
      return;
    }
    long remainCount = makerPriceNumber;

    // get maker price list
    List<byte[]> priceKeysList = pairPriceToOrderStore
        .getPriceKeysList(MarketUtils.getPairPriceHeadKey(makerSellTokenID, makerBuyTokenID),
            (long) (MAX_MATCH_NUM + 1), makerPriceNumber, true);

    int matchOrderCount = 0;
    // match different price
    while (takerCapsule.getSellTokenQuantityRemain() != 0) {
      // get lowest ordersList
      MarketPrice makerPrice = hasMatch(priceKeysList, takerPrice);
      if (makerPrice == null) {
        return;
      }

      byte[] pairPriceKey = priceKeysList.get(0);

      // if not exists
      MarketOrderIdListCapsule orderIdListCapsule = pairPriceToOrderStore.get(pairPriceKey);

      // match different orders which have the same price
      while (takerCapsule.getSellTokenQuantityRemain() != 0
          && !orderIdListCapsule.isOrderEmpty()) {
        byte[] orderId = orderIdListCapsule.getHead();
        MarketOrderCapsule makerOrderCapsule = orderStore.get(orderId);

        matchSingleOrder(takerCapsule, makerOrderCapsule, ret, takerAccountCapsule);

        // remove order
        if (makerOrderCapsule.getSellTokenQuantityRemain() == 0) {
          // remove from market order list
          orderIdListCapsule.removeOrder(makerOrderCapsule, orderStore,
              pairPriceKey, pairPriceToOrderStore);
        }

        matchOrderCount++;
        if (matchOrderCount > MAX_MATCH_NUM) {
          throw new ContractValidateException("Too many matches. MAX_MATCH_NUM = " + MAX_MATCH_NUM);
        }

  private void saveRemainOrder(MarketOrderCapsule orderCapsule)
      throws ItemNotFoundException {
    // add order into orderList

        sellTokenID,
        buyTokenID,
        sellTokenQuantity,
        buyTokenQuantity
    );

    MarketOrderIdListCapsule orderIdListCapsule = pairPriceToOrderStore.getUnchecked(pairPriceKey);
    if (orderIdListCapsule == null) {
      orderIdListCapsule = new MarketOrderIdListCapsule();

      // pairPriceKey not exists, increase price count:
      // if pair not exits, add token pair, set count = 1, add headKey to pairPriceToOrderStore
      // if pair exists, increase count
      pairToPriceStore.addNewPriceKey(sellTokenID, buyTokenID, pairPriceToOrderStore);
    }

    orderIdListCapsule.addOrder(orderCapsule, orderStore);
    pairPriceToOrderStore.put(pairPriceKey, orderIdListCapsule);
  }

  @Test
  public void exceedMaxMatchNumLimit() throws Exception {

    InitAsset();

    int start = 10;
    int limit = MarketSellAssetActuator.getMAX_MATCH_NUM();
    int step = 1;
    int end = start + step * limit;

    //(sell id_1  and buy id_2)
    String sellTokenId = TOKEN_ID_ONE;
    String buyTokenId = TOKEN_ID_TWO;
    long buyTokenQuant = 400L;
    long sellTokenQuant = buyTokenQuant * (end / start + 1);

    byte[] ownerAddress = ByteArray.fromHexString(OWNER_ADDRESS_FIRST);
    AccountCapsule accountCapsule = dbManager.getAccountStore().get(ownerAddress);
    accountCapsule.addAssetAmountV2(sellTokenId.getBytes(), sellTokenQuant,
        dbManager.getDynamicPropertiesStore(), dbManager.getAssetIssueStore());
    dbManager.getAccountStore().put(ownerAddress, accountCapsule);
    Assert.assertEquals(sellTokenQuant,
            (long) accountCapsule.getAssetV2MapForTest().get(sellTokenId));

    // Initialize the order book

    // at least limit+1 times
    for (int i = start; i <= end; i += step) {
      addOrder(buyTokenId, (long) start, sellTokenId, i, OWNER_ADDRESS_SECOND);
    }

    // this order(taker) need to match 21 times
    MarketSellAssetActuator actuator = new MarketSellAssetActuator();
    actuator.setChainBaseManager(dbManager.getChainBaseManager()).setAny(getContract(
        OWNER_ADDRESS_FIRST, sellTokenId, sellTokenQuant, buyTokenId, buyTokenQuant));

    String errorMessage =
        "Too many matches. MAX_MATCH_NUM = " + MarketSellAssetActuator.getMAX_MATCH_NUM();
    try {
      TransactionResultCapsule ret = new TransactionResultCapsule();
      actuator.validate();
      actuator.execute(ret);
      fail(errorMessage);
    } catch (ContractExeException e) {
      Assert.assertEquals(errorMessage, e.getMessage());
    } catch (Exception e) {
      Assert.assertTrue(false);
    }
  }
