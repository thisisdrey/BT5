### Title
Uncaught IndexOutOfBoundsException from unbounded `ContractType` value crashes multisig signature verification - (File: `chainbase/src/main/java/org/tron/common/utils/WalletUtil.java`)

### Summary
This is a plausible analog to the Aptos "harden ingress validation against DoS" bug class: an attacker-controlled index derived from network input is used to index into a fixed-size buffer without a bounds check, and the resulting `IndexOutOfBoundsException` is not caught by the surrounding exception handling, crashing the code path instead of returning a typed validation error — exactly the pattern the Aptos fix eliminated for `get_virtual_player`/`get_player_weight`.

### Finding Description
`WalletUtil.checkPermissionOperations` (and its duplicate in `TransactionUtil.checkPermissionOperations`) computes a byte-index into the 32-byte `operations` bitmap using the contract's raw enum wire value: [1](#0-0) 

```java
public static boolean checkPermissionOperations(Permission permission, Contract contract)
    throws PermissionException {
  ByteString operations = permission.getOperations();
  if (operations.size() != 32) {
    throw new PermissionException(...);
  }
  int contractType = contract.getTypeValue();
  boolean b = (operations.byteAt(contractType / 8) & (1 << (contractType % 8))) != 0;
  return b;
}
```

`Contract.type` is a protobuf enum field. Protobuf-Java treats enum fields as "open": an out-of-range wire value for `type` does not get rejected — `contract.getType()` returns `UNRECOGNIZED` but `contract.getTypeValue()` still returns the raw attacker-supplied `int32`, which can be arbitrarily large or negative. There is no validation anywhere that `contractType` is within `[0, 255]` (the bit-range covered by the 32-byte `operations` field) before it's used to index `operations.byteAt(contractType / 8)`. `ByteString.byteAt()` throws `IndexOutOfBoundsException` for any index outside `[0, 31]`.

This function is invoked from `TransactionCapsule.checkPermission`, which is called from `TransactionCapsule.validateSignature` (used during `validatePubSignature`) whenever a transaction's `permissionId != 0`: [2](#0-1) [3](#0-2) 

`validatePubSignature` only catches `SignatureException | PermissionException | SignatureFormatException`: [4](#0-3) 

`IndexOutOfBoundsException` is a `RuntimeException`, not caught here, so it will propagate up through whatever caller invoked signature validation (transaction broadcast/pushTransaction path or block application), rather than being converted into a rejection response.

An attacker can craft a raw transaction with:
- an Active-type permission set on the target account with `operations` bitmap of exactly 32 bytes (a normal, valid configuration),
- `Contract.type` field encoded with an out-of-range varint (e.g., 100000), producing `getTypeValue()` far outside `[0,255]`,
- `permission_id` set to a non-zero (Active) permission id,

and submit it via the standard broadcast API. When the node performs signature/permission validation, `checkPermissionOperations` computes `contractType/8` far beyond index 31 and throws an uncaught `IndexOutOfBoundsException`.

### Impact Explanation
An uncaught runtime exception during transaction signature/permission validation, triggered by a single malformed but otherwise well-formed (non-malicious-node) broadcast transaction, can crash or destabilize the processing thread handling incoming transactions (mempool ingestion or block validation), denying service to the node. This matches the "node crash or halt" impact category the scan is instructed to accept.

### Likelihood Explanation
Reachable by any unprivileged transaction broadcaster: it requires only (1) an account with a valid Active permission whose owner has authorized use of `permission_id`, and (2) a hand-crafted `Contract.type` field value outside the defined enum range, which any client capable of constructing raw protobuf bytes can produce (bypassing normal SDK constraints since gRPC/protobuf enum fields accept arbitrary int32 wire values). No validator collusion or privileged access is required.

### Recommendation
Bound-check `contractType` before indexing: reject (throw `PermissionException`) if `contractType < 0 || contractType >= operations.size() * 8` in both `WalletUtil.checkPermissionOperations` and `TransactionUtil.checkPermissionOperations`, mirroring how `AccountPermissionUpdateActuator.checkPermission` already validates each of the 256 possible bit positions against `dynamicStore.getAvailableContractType()` at permission-update time. This prevents any out-of-range enum value from reaching `ByteString.byteAt()`.

### Proof of Concept
1. Create/target an account with a valid Active permission (`operations` = 32-byte bitmap, e.g. default active permission).
2. Hand-construct (not via SDK, but directly via protobuf wire encoding) a `Transaction` whose `raw_data.contract[0]` has:
   - `type` field encoded as a varint value such as `100000` (outside the ~60 defined `ContractType` values),
   - `Permission_id` set to `2` (Active),
   - `parameter` containing any `Any`-packed payload matching some real contract type so downstream unpack logic doesn't reject it earlier.
3. Sign the transaction with a key that satisfies the account's Active permission threshold.
4. Broadcast the transaction to the node.
5. During validation, `TransactionCapsule.validateSignature` → `checkPermission` → `WalletUtil.checkPermissionOperations` computes `contractType / 8 = 12500`, calling `operations.byteAt(12500)` on a 32-byte `ByteString`, throwing an uncaught `IndexOutOfBoundsException` that is not caught by `validatePubSignature`'s catch clauses.
