### Title
Unprivileged dust-transfer griefing fills the 30-slot per-account token list, permanently reverting any new DepositToken receipt and DoS-ing `liquidate()` for affected recipients - (contracts/Pool.sol)

### Summary
`Pool` enforces `MAX_TOKENS_PER_USER = 30` across `debtTokensOfAccount` + `depositTokensOfAccount` (`contracts/Pool.sol:79`). The guard `onlyIfAdditionWillNotReachMaxTokens` (`contracts/Pool.sol:143-148`) reverts whenever the combined list length is already 30 — *before* checking whether the token being added is already tracked. Because `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` (`contracts/Pool.sol:204-220`) are invoked by `DepositToken`/`DebtToken` whenever an account balance goes 0 → positive, an unprivileged attacker can force-fill any victim's list to 30 by dust-transferring or depositing-on-behalf every listed deposit token (and synth debt where feasible). From that point on, **any** transfer of a deposit token the victim does not already hold reverts — including `DepositToken.seize` inside `Pool.liquidate` (`contracts/Pool.sol:589-593`), which sends seized collateral to the liquidator and the fee to `PoolRegistry.feeCollector()`.

### Finding Description
- `addToDepositTokensOfAccount(account_)` is public, gated only by "caller is a registered deposit token" (`contracts/Pool.sol:216-220`).
- The cap modifier counts `debtTokensOfAccount.length + depositTokensOfAccount.length >= 30` and reverts with `UserReachedMaxTokens` (`contracts/Pool.sol:143-148`).
- `DepositToken` calls this hook on `deposit(amount, onBehalfOf)`, `transfer`, `transferFrom`, and `seize` paths whenever the recipient's balance of that token was previously zero (the hook exists precisely for the "balance changes from 0" case, per the NatSpec at `contracts/Pool.sol:210-214`).
- Attack: for each registered deposit token `d_i`, attacker calls `d_i.deposit(1 wei, victim)` (or `transfer(victim, 1)` after self-depositing). After 30 distinct tokens, `depositTokensOfAccount.length(victim) == 30`. Attacker keeps slots occupied by re-dusting whenever the victim empties one (removal only occurs when a balance returns to 0 via `removeFromDepositTokensOfAccount`, `contracts/Pool.sol:630-634`).
- Once capped, any call that would add a *new* token reverts, so: (a) the victim cannot receive, deposit, or be seized into any collateral type it doesn't already hold; (b) more critically, if the victim is `feeCollector` or a major liquidation bot, `Pool.liquidate` reverts at `depositToken_.seize(account_, feeCollector, _fee)` / `seize(account_, liquidator, _toLiquidator)` whenever that token isn't already in the recipient's set — the whole `liquidate` transaction reverts (`contracts/Pool.sol:581-595`), blocking liquidation of that collateral class entirely while the cap is maintained.

### Impact Explanation
- Temporary, attacker-renewable freezing of funds/flows: victims cannot receive new deposit-token types, and liquidation proceeds reverting means unhealthy positions backed by a collateral the recipient doesn't track cannot be liquidated from/to that recipient. If `feeCollector`'s set is saturated, every `liquidate` call that would pay a protocol fee in a new collateral token reverts, stalling liquidations and exposing the pool to bad debt accrual during the window (partial DoS, matching the advisory's availability-impact class).
- No privileged role needed: only standard public entry points (`DepositToken.deposit`, `ERC20.transfer`) with dust amounts.

### Likelihood Explanation
- Cost is bounded: at most 30 dust deposits/transfers of already-listed tokens; attacker can withdraw/recycle the dust afterward on most paths. No governance, oracle manipulation, or malicious endpoint required. The blocker is purely the hard-coded `MAX_TOKENS_PER_USER` combined with the revert-before-membership-check ordering.

### Recommendation
- In `onlyIfAdditionWillNotReachMaxTokens`, only revert when the token is *new* to the account's set (i.e., check `!depositTokensOfAccount.contains(account_, token)` / debt equivalent before enforcing the cap), so transfers of already-held tokens and repeat additions cannot be forced to revert.
- Alternatively, make the per-account list add failure non-fatal on `seize`/transfer paths (skip accounting rather than revert), or accept deposits made `onBehalfOf` without auto-registering the token until the holder opts in.
