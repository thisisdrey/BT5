### Title
Missing zero-amount check in `MarketSellAssetActuator.matchSingleOrder` "taker == maker" branch allows rounding-to-zero fund extraction - (File: `actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java`)

### Summary
`MarketSellAssetActuator.matchSingleOrder` computes the amount a maker receives in a trade using integer (floor) division via `MarketUtils.multiplyAndDivide`. In two of the three match branches ("taker < maker fully consumed" and "taker > maker consumed") the code explicitly checks whether the computed amount rounds down to `0` and handles it safely. The third branch — the exact-match case ("taker == maker") — computes `makerBuyTokenQuantityReceive` with the same rounding-prone formula but has **no zero check**, so when it rounds to `0` the maker's full remaining sell-side balance is still transferred to the taker for free, exactly mirroring the report's "calculated pull amount rounds to 0 but credit is still issued" bug class.

### Finding Description
In `matchSingleOrder`, when a taker order exactly consumes a maker order's remaining quantity (`takerBuyTokenQuantityRemain == makerOrderCapsule.getSellTokenQuantityRemain()`): [1](#0-0) 

`makerBuyTokenQuantityReceive` is computed via `MarketUtils.multiplyAndDivide(makerSellRemainQuantity, makerBuyQuantity, makerSellQuantity, ...)`, which uses floor division: [2](#0-1) 

Unlike the other two branches of the same method, which explicitly guard against a `0` result:
- The "taker fully consumed, quantity too small" case is guarded: `if (takerBuyTokenQuantityRemain == 0) { ... return sellToken to user ... }` [3](#0-2) 
- The "taker > maker" case is guarded: `if (makerBuyTokenQuantityReceive == 0) { ... return the remain of sellToken to maker ... }` [4](#0-3) 

...the "taker == maker" branch performs no such check before crediting the taker with `takerBuyTokenQuantityReceive = makerOrderCapsule.getSellTokenQuantityRemain()` (the maker's entire remaining balance) and reducing the taker's own remaining sell balance only by `makerBuyTokenQuantityReceive`: [5](#0-4) 

If `makerBuyTokenQuantityReceive` computes to `0` (which happens whenever `makerSellRemainQuantity` is smaller than a full/unfilled order and the price ratio truncates), the taker's remaining sell-side balance is left unchanged (`takerSellTokenLeft = remain - 0 = remain`) while it still fully receives the maker's leftover assets via `addTrxOrToken`: [6](#0-5) 

This is functionally identical to the reported bug class: the amount to be "pulled"/paid from one party rounds to zero via integer division, yet the credit (the other party's assets) is fully transferred.

### Impact Explanation
An unprivileged market participant (order placer) can extract another user's or their own colluding account's remaining order balance without paying the proportional counter-asset, since the payment leg silently becomes `0` due to floor division while the receipt leg still executes in full. This is a direct theft-of-funds / unbacked-balance vector reachable purely through standard `MarketSellAssetContract` transactions (no special privileges needed), matching the "exchange and market order handling" reachable surface.

### Likelihood Explanation
Any maker order whose remaining quantity has been partially reduced by prior trades (a normal, common occurrence in the order book) can end up with a small remainder. An attacker (or an attacker acting as both maker and taker across two accounts/transactions) can engineer a final matching taker order whose computed `takerBuyTokenQuantityRemain` exactly equals that remainder, deterministically forcing execution into the unguarded "taker == maker" branch. Because the check present in the sibling branches (lines 406 and 466) is provably absent here, this is a straightforward, repeatable exploitation path requiring only two ordinary `MarketSellAssetContract` broadcasts, not a rare edge case.

### Recommendation
Add the same `== 0` safety check used in the other two branches to the "taker == maker" branch: if `makerBuyTokenQuantityReceive` computes to `0`, either reject/return the maker's remaining sell tokens to the maker instead of transferring them to the taker, or correspondingly reduce `takerBuyTokenQuantityReceive`/enforce a minimum receivable amount so that no assets are transferred without a matching payment. Additionally, consider proactively requiring `makerBuyTokenQuantityReceive > 0` before crediting `takerBuyTokenQuantityReceive` in all match branches, and apply the pattern consistently as `Commons`/`ExchangeInjectActuator` already does (`"the calculated token quant must be greater than 0"` check) for the `Exchange*` actuators.

### Proof of Concept
1. Account M places a `MarketSellAssetContract`: sell `TokenA` quantity `S`, buy `TRX` quantity `B` (`S > B`), creating a maker order with `sellTokenQuantityRemain = S`.
2. Account T1 (attacker) places a taker order that partially fills M's order via the "taker < maker" branch (`actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java:440-452`), reducing `makerOrderCapsule.getSellTokenQuantityRemain()` to a small remainder `R` where `0 < R < S`.
3. Account T2 (attacker, same or different account) places a taker order whose computed `takerBuyTokenQuantityRemain` (via `MarketUtils.multiplyAndDivide`) exactly equals `R`, driving execution into the "taker == maker" branch.
4. Because `R * B / S` (floor division) truncates to `0` for sufficiently small `R` relative to `S`/`B`, `makerBuyTokenQuantityReceive == 0`.
5. The unguarded branch still sets `takerBuyTokenQuantityReceive = R` (maker's full leftover `TokenA`) and only reduces T2's remaining sell balance by `0`, so T2 receives `R` units of `TokenA` from M for free while M's order is closed (`sellTokenQuantityRemain = 0`) with no compensating TRX ever credited to M.

This mirrors the existing regression tests in `framework/src/test/java/org/tron/core/actuator/MarketSellAssetActuatorTest.java` (e.g. `partMatchMakerLeftNotEnoughBuyOrders1`) which already exercise near-identical "accuracy problem" scenarios for other branches, confirming the rounding scenario is realistically reachable through normal contract usage.

  public static long multiplyAndDivide(long a, long b, long c, boolean disableMath) {
    try {
      long tmp = multiplyExact(a, b, disableMath);
      return floorDiv(tmp, c, disableMath);
    } catch (ArithmeticException ex) {
      // do nothing here, because we will use BigInteger to compute again
    }

    BigInteger aBig = BigInteger.valueOf(a);
    BigInteger bBig = BigInteger.valueOf(b);
    BigInteger cBig = BigInteger.valueOf(c);

    return aBig.multiply(bBig).divide(cBig).longValue();
  }
