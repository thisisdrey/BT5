### Title
Shared object-pool disk usage is silently attributed to every fork's reported repository size, letting an unprivileged fork owner inflate another fork's size and trigger DoS of size-limited operations - (File: internal/gitaly/service/repository/repository_info.go)

### Summary
`RepositoryInfo` (and `RepositorySize`) compute a repository's reported size by walking the repository directory and, whenever the repository is linked to an object pool, adding the pool directory's disk usage on top [1](#0-0) . This mirrors the report's root cause: a security-relevant numeric check (`aEthValue`) is derived from *live, externally influenceable state* (`_geth.balanceOf(address(this))`) rather than from a value the caller committed to, so a third party can cheaply manipulate that live state to break another actor's otherwise-valid operation.

### Finding Description
An object pool is a single shared object store linked via the Git alternates mechanism to every member of a fork network [2](#0-1) . Its size grows whenever any pool member pushes new objects and they get pulled into the pool through `FetchIntoObjectPool` [3](#0-2) .

`RepositoryInfo` computes the "size" it reports for a given repository by summing the repo's own directory size with the pool directory's size: [4](#0-3) 

The same pattern exists in the size test, confirming the pool's size is added to every member's reported size: `expectedResponse.Size = repoSize + poolSize` [5](#0-4) , and `RepositorySize` performs the equivalent disk walk directly on the repo path with no accounting for which fork actually contributed which bytes [6](#0-5) .

Because the pool is shared, this size figure is not attributable to a single actor's committed contribution — it is a live, mutable aggregate that any pool member with ordinary push access can inflate (by pushing large blobs into their own fork, which get deduplicated into the shared pool on the next `FetchIntoObjectPool`/housekeeping run). This is structurally identical to the reported bug: a check meant to reflect "how much did *this* actor commit" (`dEthValue_` vs. `aEthValue` in the report; a fork's own contribution here) is instead computed from a live, shared value that any unprivileged party can cheaply move (`_geth.balanceOf` vs. pool directory size), enabling that party to force a downstream security check to fail for someone else.

### Impact Explanation
GitLab's product layer (and any consumer relying on `RepositoryInfo`/`RepositorySize`) uses these size figures to enforce per-repository storage quotas and to decide whether pushes should be accepted. Because the object pool's size is transparently folded into *every* member repository's reported size, an ordinary user who merely has push access to any fork sharing the pool (e.g., any public fork of a project) can inflate the pool's disk footprint and thereby inflate the reported size of every sibling fork, including ones they do not own or control. This can push an unrelated repository over its configured size limit, causing legitimate pushes from other users to that repository to be rejected — a denial of service that requires no special privilege on the victim's repository at all.

### Likelihood Explanation
Any authenticated user with push access to one fork in a fork network can trigger this: pushing large, reachable blobs and having them absorbed into the shared pool via normal housekeeping/`FetchIntoObjectPool` flows is part of ordinary repository operation, not a privileged or exotic action. The only "cost" to the attacker is the storage of the objects they push into their own fork (which the pool will hold regardless), so the attack is cheap relative to the disruption caused to sibling forks. This is a realistic, low-effort griefing vector reachable purely from an ordinary user's push/fork workflow.

### Recommendation
Do not let disk usage of a shared object pool be transparently and fully attributed to every linked fork's "size" figure without accounting for actual ownership/contribution. Consider either: (1) computing a fork's own "committed" size as the deduplicated delta it actually owns rather than adding the entire pool size to every member, (2) tracking and enforcing size limits at the pool level (attributable to the fork-network/root) rather than per-member, or (3) requiring any consumer that gates security-relevant decisions (e.g., quota enforcement blocking pushes) to use a size measure that cannot be inflated by unrelated pool members' actions.

### Proof of Concept
Not independently reproduced against a live GitLab quota-enforcement flow (that logic lives outside this repository, in GitLab Rails); the analog is demonstrated purely from the code paths above:
1. Fork network `P` has pool `Pool` and forks `A` (attacker) and `V` (victim), both linked to `Pool` via `internal/git/objectpool/link.go`.
2. Attacker pushes large blobs to fork `A`; a subsequent `FetchIntoObjectPool` pulls them into `Pool`, growing `Pool`'s on-disk size.
3. A call to `RepositoryInfo`/`RepositorySize` for `V` now returns `repoSize(V) + poolSize(Pool)` per `internal/gitaly/service/repository/repository_info.go:73-79`, inflated purely by attacker-controlled data that `V`'s owner never pushed.
4. Any downstream consumer that rejects operations (e.g., pushes) on `V` once its reported size exceeds a quota will now reject legitimate operations on `V`, at a cost to the attacker limited to the objects they chose to push into their own fork.

// RepositorySize returns the size of the specified repository in kibibytes. By default, this
// calculation is performed using the disk usage command.
func (s *server) RepositorySize(ctx context.Context, in *gitalypb.RepositorySizeRequest) (*gitalypb.RepositorySizeResponse, error) {
	repository := in.GetRepository()
	if err := s.locator.ValidateRepository(ctx, repository); err != nil {
		return nil, structerr.NewInvalidArgument("%w", err)
	}
	repo := s.localRepoFactory.Build(repository)

	path, err := repo.Path(ctx)
	if err != nil {
		return nil, err
	}

	filter := snapshot.NewDefaultFilter(ctx)
	sizeInBytes, err := dirSizeInBytes(path, filter)
	if err != nil {
		return nil, fmt.Errorf("calculating directory size: %w", err)
	}

	return &gitalypb.RepositorySizeResponse{Size: sizeInBytes / 1024}, nil
}
