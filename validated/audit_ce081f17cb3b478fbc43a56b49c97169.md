### Title
Cross-lane StackerDB chunk replay due to missing contract/message-id binding in the signed digest - (File: `libstackerdb/src/libstackerdb.rs`)

### Summary

### Finding Description
`SlotMetadata::auth_digest()` computes the bytes that are signed (and later verified) for every StackerDB chunk as `hash(slot_id || slot_version || data_hash)` only: [1](#0-0) 

Neither the smart-contract identifier (`QualifiedContractIdentifier`) nor any other value that identifies *which* StackerDB/message lane the chunk belongs to is included in the signed payload. `SlotMetadata::verify()`/`StackerDBChunkData::verify()` likewise only check `slot_id`, `slot_version`, `data_hash`, and the recovered signer address: [2](#0-1) 

For the Nakamoto signer StackerDBs, a single reward-cycle "page" of signers (`stackerdb-get-signer-slots-page`) is shared by **three sibling contracts** — `signers-<set>-1` (BlockResponse), `signers-<set>-2` (StateMachineUpdate), `signers-<set>-3` (BlockPreCommit) — each simply reading the same signer list for the same signer_set/page: [3](#0-2) [4](#0-3) 

Because `StackerDBTx::create_stackerdb` assigns `slot_id` deterministically in list order for each `(signer, num_slots)` entry: [5](#0-4) 

the address → `slot_id` mapping is **identical** across `signers-<set>-1`, `signers-<set>-2`, and `signers-<set>-3` for the same reward cycle/set. Consequently, a legitimately-signed chunk broadcast for one lane (e.g. a `BlockResponse` on `signers-0-1`) carries a signature over `(slot_id, slot_version, data_hash)` that is *also valid* for the sibling lanes `signers-0-2` / `signers-0-3`, since the digest never bound the message to its intended contract.

Both write paths accept chunks purely on this incomplete authentication:
- The P2P/gossip validator `PeerNetwork::validate_received_chunk` only checks size, expected version, the (context-blind) signature, and version bounds — never the contract identity encoded in the signature: [6](#0-5) 
- The persistence layer `StackerDBTx::try_replace_chunk` re-checks signature/staleness/max-writes the same way, again with no binding to contract identity beyond looking up the expected signer address for *that* `stackerdb_id`, which is the same signer for the sibling lanes: [7](#0-6) 
- The public, unauthenticated HTTP write endpoint `POST /v2/stackerdb/.../chunks` calls the same `try_replace_chunk`: [8](#0-7) 

The only place a mismatch is ever detected is much later, in the *consumer* (`libsigner`), which filters chunks by inspecting the leading type-prefix byte of the payload against the expected lane: [9](#0-8) [10](#0-9) 

This is a downstream, best-effort filter — it does not prevent the chunk from being accepted and persisted into the *wrong* StackerDB slot in the first place, and it only helps when message type-prefix bytes happen to differ between lanes.

### Impact Explanation
An unprivileged remote peer that observes (via gossip or HTTP) a validly-signed chunk broadcast for one signer message lane (e.g. `signers-0-1`) can replay the exact same `(slot_id, slot_version-or-higher, data, signature)` tuple into a sibling lane contract for the same signer_set (e.g. `signers-0-2` or `signers-0-3`) as long as the target slot's stored version is lower. Because `try_replace_chunk` only requires `slot_version` to strictly exceed the stored version and the signature to recover to the address on record for that `stackerdb_id`, the replayed chunk is accepted as an **authenticated write** even though it was never actually signed for that lane/contract. This is an unauthenticated/unauthorized overwrite of a specific signer's stored `StateMachineUpdate` or `BlockPreCommit` slot with foreign, mis-contextualized data (its own valid, once-broadcast content) — corrupting or hiding a targeted signer's genuine contribution to that lane once it is fetched and skipped by the type-prefix filter as unrecognized. This matches the "unauthenticated/unauthorized write to state or StackerDB" class.

### Likelihood Explanation
Moderate-to-high: it requires no secret key, no elevated role, and no special timing — only observing one already-broadcast, publicly-visible signed chunk (chunks are gossiped/pushed network-wide and are also queryable) and resubmitting it (with an incremented version if needed) against a different, predictable sibling contract name for the same signer_set. The attacker needs no private key of their own; they only replay bytes that were already validly signed by the legitimate signer for a different lane.

### Recommendation
Bind the digest signed in `SlotMetadata::auth_digest()` to the full context of the chunk, not just `(slot_id, slot_version, data_hash)` — include the `QualifiedContractIdentifier` (or equivalently, the `message_id`/lane and signer_set/reward_cycle) of the StackerDB the chunk is destined for. Update `sign()`/`verify()` call sites in `libstackerdb/src/libstackerdb.rs`, and thread the contract identifier through `StackerDBChunkData`, `try_replace_chunk`, and `validate_received_chunk` so that a signature computed for one contract can never validate against another.

### Proof of Concept
1. During a reward cycle, observe (via P2P gossip or `GET /v2/stackerdb/<contract>/<slot>/<version>`) a validly signed `BlockResponse` chunk for signer S, e.g. `signers-0-1`, at `slot_id = k`, `slot_version = v`, with signature `sig` and `data`.
2. Confirm (via `stackerdb-get-signer-slots-page`) that signer S also owns `slot_id = k` in `signers-0-2` (guaranteed, since both contracts read the same page-0 signer list — see `signers.clar`/`signers-0-xxx.clar`).
3. Construct a `StackerDBChunkData { slot_id: k, slot_version: v' > current_version_in(signers-0-2), sig, data }` (same `sig`/`data` as captured, bump `slot_version` if the target slot's stored version already ≥ v).
4. Submit it via `POST /v2/stackerdb/signers-0-2/chunks` (`poststackerdbchunk.rs`) or push it as an unsolicited `StackerDBPushChunk` P2P message.
5. `try_replace_chunk`/`validate_received_chunk` accept it: `slot_metadata.verify(&addr)` succeeds because the digest never encoded which contract it was for, and the version/size/max-writes checks pass independently — the chunk is stored, overwriting whatever `StateMachineUpdate` slot content the legitimate signer had placed at `signers-0-2` slot `k`.

    pub fn try_replace_chunk(
        &self,
        smart_contract: &QualifiedContractIdentifier,
        slot_desc: &SlotMetadata,
        chunk: &[u8],
    ) -> Result<(), net_error> {
        // Check per-replica chunk-size cap.
        if (chunk.len() as u64) > self.config.chunk_size {
            return Err(net_error::StackerDBChunkTooBig(chunk.len()));
        }

        let slot_validation = self
            .get_slot_validation(smart_contract, slot_desc.slot_id)?
            .ok_or(net_error::NoSuchSlot(
                smart_contract.clone(),
                slot_desc.slot_id,
            ))?;

        if !slot_desc.verify(&slot_validation.signer)? {
            return Err(net_error::BadSlotSigner(
                slot_validation.signer,
                slot_desc.slot_id,
            ));
        }
        if slot_desc.slot_version <= slot_validation.version {
            return Err(net_error::StaleChunk {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
            });
        }
        if slot_desc.slot_version > self.config.max_writes {
            return Err(net_error::TooManySlotWrites {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
                max_writes: self.config.max_writes,
            });
        }
        self.insert_chunk(smart_contract, slot_desc, chunk)
    }
