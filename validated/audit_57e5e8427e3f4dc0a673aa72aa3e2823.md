Audit Report

## Title
Bounty and child-bounty payout transfers rely on `debug_assert!` instead of checked results, allowing state to advance to "Claimed"/removed even when the payout transfer silently fails - ([File: substrate/frame/child-bounties/src/lib.rs])

## Summary
`claim_child_bounty()` in `pallet-child-bounties` and `claim_bounty()` in `pallet-bounties` perform the curator-fee and beneficiary payout transfers via `T::Currency::transfer(...)`, but only check the resulting `DispatchResult` with `debug_assert!`, which is compiled to a no-op in release builds. A transfer can genuinely fail with standard `pallet-balances` semantics when the destination account does not yet exist and the computed payout/fee amount is below the `ExistentialDeposit`, in which case the extrinsic still proceeds to emit the "Claimed" event and permanently delete the bounty record, stranding funds in the now-orphaned sovereign bounty account.

## Finding Description
In `claim_child_bounty()`, the curator-fee and beneficiary transfers are checked only via `debug_assert!(fee_transfer_result.is_ok())` and `debug_assert!(payout_transfer_result.is_ok())`: [1](#0-0) 
Regardless of the transfer outcome, the function unconditionally emits `Event::Claimed`, decrements `ParentChildBounties`, removes the description, and sets `*maybe_child_bounty = None`: [2](#0-1) 

The identical pattern exists in `claim_bounty()` in the parent pallet, where `res.is_ok()` for both the fee and payout transfers is checked only via `debug_assert!` before `*maybe_bounty = None` deletes the bounty record: [3](#0-2) 

Crucially, this is not merely a theoretical risk requiring a non-standard `Currency` implementation. The repository's own `pallet-balances` test suite confirms that a `transfer_allow_death` (which underlies the `AllowDeath`-requirement `Currency::transfer` used here) to a **non-existent** destination account with a value **below the `ExistentialDeposit`** fails with `TokenError::BelowMinimum`: [4](#0-3) 

Both `claim_bounty` and `claim_child_bounty` compute `payout`/`curator_fee` from the *current* free balance of the bounty sub-account (`balance.saturating_sub(fee)` / `child_bounty.fee.min(balance)`), so the transferred amount can legitimately be a small, dust-level value if the bounty account's balance has been partially depleted (e.g., via `slash`, an earlier partial payout, or a small originally-funded value combined with a nonzero fee) and the beneficiary or curator account has never been funded/does not exist on-chain. In that scenario `T::Currency::transfer(..., AllowDeath)` returns `Err(TokenError::BelowMinimum)`, `debug_assert!` in a release build is a no-op, and the function proceeds exactly as if the transfer succeeded.

Existing guards are insufficient: the `curator_fee = child_bounty.fee.min(balance)` / `fee = bounty.fee.min(balance)` clamping only prevents the transfer amount from exceeding the account's balance — it does nothing to prevent the amount from being below the destination's `ExistentialDeposit` when the destination does not exist. There is no `ensure!`/`?`-based check anywhere in either function that would abort the `try_mutate_exists` closure on transfer failure.

## Impact Explanation
If the transfer fails after the guard checks pass, the payout/fee amount remains stuck in the `child_bounty_account_id`/`bounty_account_id` sovereign account, which is disassociated from any pallet storage the moment the bounty record is deleted (`*maybe_child_bounty = None` / `*maybe_bounty = None`), with no remaining index to retry or recover the funds. Meanwhile, the chain state and events (`Event::Claimed` / `Event::BountyClaimed`) report the bounty as successfully paid to the beneficiary, so this is a duplicate/incorrect settlement in which state advances to "paid" without actual value transfer — a permanent fund lock combined with an incorrect settlement record, matching the required impact categories for duplicate settlement / permanent user-fund lock.

## Likelihood Explanation
Likelihood is Low-to-Medium: the failure condition (destination account non-existent and amount below `ExistentialDeposit`) is a standard, well-known `pallet-balances` behavior — not a contrived custom-`Currency` assumption — and can arise from ordinary bounty lifecycle interactions (e.g., a bounty account partially slashed/drained, or a small residual fee/payout after most funds were already distributed via a prior partial-transfer scenario) combined with a beneficiary/curator account that has not been otherwise funded. No privileged actor is required to trigger `claim_bounty`/`claim_child_bounty`, since both are permissionless signed extrinsics; the precondition (dust-level payout to a non-existent account) can plausibly occur without any malicious governance or validator behavior.

## Recommendation
Replace `debug_assert!(result.is_ok())` with proper error propagation (`?` or `ensure!`) for the curator-fee and beneficiary transfers in both `claim_bounty()` (`substrate/frame/bounties/src/lib.rs`) and `claim_child_bounty()` (`substrate/frame/child-bounties/src/lib.rs`), so a failed transfer aborts the `try_mutate_exists` closure instead of allowing the bounty record to be marked claimed/removed. Alternatively/additionally, ensure computed `curator_fee`/`payout` amounts are validated against the destination's `ExistentialDeposit` before attempting the transfer when the destination may not exist.

## Proof of Concept
1. Configure a runtime built without `debug_assertions` (standard release profile).
2. Create and fund a bounty/child-bounty, progress it to `PendingPayout` with a beneficiary account that has never been funded (does not exist on-chain), and arrange for the bounty sub-account's balance at claim time to leave a `payout` (or `curator_fee`) amount below `T::Currency::minimum_balance()` (e.g., via a prior partial slash of the bounty account, or a bounty value/fee combination that yields a small remainder).
3. Wait for `unlock_at`, then call `claim_bounty`/`claim_child_bounty` as any signed account.
4. `T::Currency::transfer(&bounty_account, &beneficiary, payout, AllowDeath)` returns `Err(TokenError::BelowMinimum)` per the confirmed behavior in `substrate/frame/balances/src/tests/dispatchable_tests.rs::default_indexing_on_new_accounts_should_not_work2`, but since `debug_assertions` is disabled, `debug_assert!(payout_transfer_result.is_ok())` is a no-op.
5. Observe: `Event::Claimed`/`Event::BountyClaimed` is emitted, the bounty record is deleted, yet the beneficiary received nothing and the `payout` remains stranded in the now-orphaned bounty sub-account with no remaining storage entry to recover it.
