### Title
Unbounded array-length parameter in `BatchValidateSign` precompile causes unbounded heap allocation / OOM DoS - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `BatchValidateSign` precompiled contract (reachable from any TVM contract via `STATICCALL`/`CALL`) decodes attacker-controlled ABI words to determine the size of internal arrays. The address-array extraction path, `extractBytes32Array`, uses an unvalidated length taken directly from calldata to allocate a Java array, with no upper bound check unless a specific hard-fork flag (`allowTvmSelfdestructRestriction`) is active. This mirrors the reported TensorFlow `Dequantize` bug class (CWE-1284/CWE-20 — missing validation of an attacker-supplied size/index used to compute array dimensions before use).

### Finding Description
`extractBytes32Array` reads a length word from the decoded call data and immediately uses it to size a new array, without any bounds check: [1](#0-0) 

This differs from the sibling helpers `extractBytesArray` and `extractSigArray`, which at least guard against `offset` running past the input (`if (offset > words.length - 1) return new byte[0][];`), but none of the three actually caps the decoded `len` value itself: [2](#0-1) 

In `BatchValidateSign.doExecute`, the `MAX_SIZE` (16) guard on the address-array size is only applied when the `allowTvmSelfdestructRestriction` hard-fork flag is enabled: [3](#0-2) 

When that flag is off (its default state must be confirmed against the live chain parameters; I could not verify the current mainnet activation status of `allowTvmSelfdestructRestriction` within the available tool budget), `words[2].intValueSafe()` (address-array offset) and the length word it points to are fully attacker-controlled and unbounded, and `extractBytes32Array` will execute `new byte[len][]` with `len` up to `Integer.MAX_VALUE` — an allocation of tens of gigabytes of array-header memory alone, well before any signature-count sanity check (`cnt == 0 || cnt > MAX_SIZE`) is reached.

### Impact Explanation
An uncontrolled large allocation is a classic denial-of-service vector: it can trigger `OutOfMemoryError` inside the JVM. While `BatchValidateSign.execute` wraps `doExecute` in `catch (Throwable t)`: [4](#0-3) 
catching the `Throwable` after the allocation has already stressed/exhausted the heap does not prevent the underlying memory pressure from destabilizing the entire node process — other concurrently executing transactions, database/RocksDB operations, and unrelated threads can fail with their own `OutOfMemoryError`s, potentially crashing or hanging the full node. This satisfies the "node crash or halt" impact bar for a Medium-severity finding reachable by any contract caller.

### Likelihood Explanation
The precompile is invoked purely via a `CALL`/`STATICCALL` from any TVM contract to the `BatchValidateSign` precompile address — no special privilege, signer role, or witness/committee status is required. The only gating factor is whether the `allowTvmSelfdestructRestriction` feature is active on the target chain/fork; on any chain (including private/enterprise or lagging Tron-compatible chains) where this flag has not yet been turned on, the path is fully exploitable by a single crafted transaction.

### Recommendation
Apply an unconditional upper bound (e.g., `MAX_SIZE`) check on the decoded `len` inside `extractBytes32Array`, `extractBytesArray`, and `extractSigArray` themselves — independent of the `allowTvmSelfdestructRestriction` flag — before allocating any array, and reject with `Pair.of(false, EMPTY_BYTE_ARRAY)` (or `DATA_FALSE`) if `len` is negative or exceeds the maximum expected batch size.

### Proof of Concept
1. Deploy a simple contract that performs a low-level `call` to the `BatchValidateSign` precompiled contract address.
2. Craft calldata such that `words[2]` (the address-array offset field) points to a word whose value is a very large positive integer (e.g., `0x7FFFFFFF`).
3. Ensure the chain/fork under test has `allowTvmSelfdestructRestriction` inactive (default/older configuration), so the `MAX_SIZE` guard in `doExecute` (lines 1165–1171) is skipped.
4. Invoke the contract; `extractBytes32Array` (lines 390–397) executes `new byte[Integer.MAX_VALUE][]`, causing a massive heap allocation attempt / `OutOfMemoryError` inside the node's TVM execution thread, exhausting heap and impacting other concurrently running node operations.

*Note: I was unable to confirm within the available investigation budget whether `allowTvmSelfdestructRestriction` is enabled by default on the target production chain configuration; this materially affects real-world exploitability and should be verified before treating this as immediately actionable on mainnet.*
