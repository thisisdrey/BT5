### Title
Stale scheduled-replacement race lets an attacker's replacement clobber a freshly re-handshaked peer's frontier slot - ([File: stackslib/src/net/neighbors/db.rs])

### Summary
`PeerDBNeighborWalk::replace_neighbors` overwrites a peer-DB slot using only a denial check on the *replacement's* address, without re-verifying that the slot's *current* occupant is still the one that was originally scheduled to be evicted or that it is still alive. The liveness-ping step (`ping_existing_neighbors_begin`) pings the *new candidate's* own address, not the slot's actual incumbent, so a legitimate peer that re-handshakes and refreshes its own row is never protected from being silently overwritten by a stale, previously-scheduled replacement.

### Finding Description
`NeighborReplacements::add_neighbor` is populated in `add_or_schedule_replace_neighbor` (stackslib/src/net/neighbors/db.rs:400-420) with `naddr = NeighborAddress::from_neighbor(&neighbor_from_handshake)` (the *new*, attacker-controlled peer `A`) and `slot = find_replaced_neighbor_slot(&tx, &neighbor_from_handshake.addr)`. `find_replaced_neighbor_slot` (db.rs:287-302) merely computes `A`'s own deterministic hash-based candidate slots via `PeerDB::peer_slots` and picks one at random — it never inspects, locks, or records who currently occupies that slot (`C`).

Later, `ping_existing_neighbors_begin` (walk.rs:1746-1784) sends a fresh `Handshake` to `naddr` taken from `neighbor_replacements.iter_slots()` — but that `naddr` is `A`'s own address, not `C`'s. If `A` answers, `handle_handshake_accept_from_ping` (walk.rs:1788-1811) removes `A` from `neighbor_replacements` (self-cancellation); if `A` simply does not respond (attacker's choice), the stale scheduled entry for slot `S` survives untouched. Crucially, the real occupant `C` of slot `S` is never pinged or re-verified by this mechanism at all.

Meanwhile `C` can legitimately re-handshake through any normal path (e.g. as `cur_neighbor`, or via `save_neighbor_from_handshake`/`update_neighbor`), refreshing its own frontier row for slot `S` in the interim.

When the walk finally calls `replace_neighbors` (db.rs:463-505):
```
let replaced_opt = PeerDB::get_peer_at(&tx, network_id, *slot)?;
if let Some(replaced) = replaced_opt {
    if PeerDB::is_address_denied(&tx, &replacement.addr.addrbytes)? { continue; }
    PeerDB::insert_or_replace_peer(&tx, replacement, *slot)?;
    ...
}
```
`get_peer_at` does pick up `C`'s fresh row, but the only gate before unconditional overwrite is a denial check on `replacement.addr.addrbytes` (i.e. `A`'s address) — there is no check that `C` is still the intended eviction target, no freshness/liveness check on `C`, and no compare-and-swap against `C`'s current row. `insert_or_replace_peer` (db.rs:1091-1133) then overwrites the row and, because `old_peer.addr != neighbor.addr`, calls `PeerDB::drop_stacker_dbs(tx, slot)`, wiping `C`'s StackerDB peer associations for that slot.

### Impact Explanation
An unauthenticated remote peer (`A`) that gets scheduled as a stale replacement candidate for slot `S` can, simply by not responding to the (misdirected) liveness ping, force `replace_neighbors` to silently overwrite the freshly-updated, legitimately-active peer `C`'s frontier row at slot `S` with `A`'s own stale data — evicting `C` from the frontier and dropping `C`'s StackerDB peer-slot associations (`drop_stacker_dbs`). This is an unauthenticated write to peer-DB/StackerDB state that discards a peer's just-authenticated identity and replication metadata without any check tying eviction eligibility to `C`'s current liveness, matching the "unauthenticated write to state / StackerDB" Critical category. It is repeatable across walk cycles and any slot the attacker manages to get scheduled against.

### Likelihood Explanation
Preconditions: the node's frontier must be near capacity such that an attacker-controlled address's deterministic hash slots (`PeerDB::peer_slots`, 8 candidates keyed by the node's private nonce) are all occupied, causing `save()` to fail and a replacement to be scheduled; this is plausible for a long-running, well-populated node and an attacker who can cheaply enumerate many low-cost Sybil identities/ports to find a colliding address. Once scheduled, the attacker's only required action is to not answer the ping sent to its own address — trivial and fully under attacker control. The race requires the true incumbent `C` to re-handshake during the walk's window, which is a routine, frequent event, not something the attacker needs to engineer. No secret, privileged role, or local access is needed; only P2P reachability.

### Recommendation
In `replace_neighbors`, before overwriting a slot, re-validate that the current occupant (`PeerDB::get_peer_at`) still matches the neighbor that was originally recorded/pinged for eviction (e.g., store the incumbent's `NeighborKey`/public key alongside the scheduled slot in `NeighborReplacements` and compare-and-swap against it), and fix `ping_existing_neighbors_begin`/`handle_handshake_accept_from_ping` to actually ping the slot's *incumbent* rather than the new candidate, cancelling the replacement if the incumbent proves alive/fresh (e.g. `last_contact_time` updated) since scheduling.

### Proof of Concept
Rust test plan (in `stackslib/src/net/neighbors/db.rs` or a walk-level integration test):
1. Set up a `PeerDB` with `NUM_SLOTS` candidate slots for address `A` all occupied, one of them (slot `S`) by neighbor `C`.
2. Call `PeerDBNeighborWalk.add_or_schedule_replace_neighbor` with a crafted `Preamble`/`HandshakeData` for `A`, confirming `neighbor_replacements.get_slot(&naddr_A) == Some(S)`.
3. Concurrently (before calling `replace_neighbors`), call `PeerDB::update_peer`/`insert_or_replace_peer` (simulating `C`'s legitimate re-handshake `update_neighbor`) to refresh `C`'s row at slot `S` with a new `last_contact_time`.
4. Call `PeerDBNeighborWalk.replace_neighbors(&mut network, &neighbor_replacements, &mut result)`.
5. Assert `PeerDB::get_peer_at(&tx, network_id, S)` now equals `A`'s neighbor record (not `C`'s freshly-updated one), and that `result.replaced_neighbors` contains `C`'s key — demonstrating the fresh occupant was clobbered by the stale scheduled replacement.
