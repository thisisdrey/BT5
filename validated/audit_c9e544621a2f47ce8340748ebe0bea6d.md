## Analysis

The Sherlock bug class here is: *native/token funds attached to a call to cover fees are silently frozen on a contract's balance when a particular execution branch skips the refund logic that exists elsewhere in the same contract.* Searching nearcore's protocol-level refund machinery, the base runtime does not have this bug class — `refund_unspent_gas_and_deposits` (`runtime/runtime/src/lib.rs:1230`) unconditionally refunds every unused attached deposit and unused gas via `Receipt::new_balance_refund`/`Receipt::new_gas_refund` regardless of code path, this is enforced by the protocol itself, not by manually-written contract logic.

However, the exact analog exists in the **eth-implicit wallet contract** (`runtime/near-wallet-contract`), which *is* ordinary user-writable/deployed contract logic with manual refund bookkeeping via `CallerDeposit`, structurally identical to the Solidity pattern in the report (fee attached by an external caller, refunded only on some conditional branches, dropped on others).

### Title
Attached deposit from an external caller is permanently lost when the wallet contract's `address_check_callback` or `nep_141_storage_balance_callback` short-circuits with an error - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The eth-implicit wallet contract tracks an external caller's `attached_deposit` in a `CallerDeposit` struct so it can be refunded if the relayed Ethereum-emulated transaction ultimately fails. The refund is only actually sent from the terminal `rlp_execute_callback` on `PromiseResult::Failed`. Several earlier bail-out branches in `address_check_callback` and `nep_141_storage_balance_callback` return `PromiseOrValue::Value(ExecuteResponse{success:false, ...})` directly, without forwarding to `rlp_execute_callback` and without ever issuing the `promise_batch_action_transfer` refund. In these cases, the caller's attached NEAR (already credited to the wallet contract's balance per NEAR's attached-deposit semantics) is never returned.

### Finding Description
`CallerDeposit::new` records the predecessor's attached deposit whenever the caller is external (`predecessor_account_id != current_account_id`): [1](#0-0) 

This value is threaded through `inner_rlp_execute` and the multi-step promise chains (`address_check_callback`, `nep_141_storage_balance_callback`, `rlp_execute_callback`) so that it can be refunded if the underlying action ultimately fails: [2](#0-1) 

The refund is only implemented in this final `rlp_execute_callback` when `PromiseResult::Failed`. But `address_check_callback` has three exit points that discard `caller_deposit` entirely instead of forwarding to that refund logic:

1. Registrar call failed: [3](#0-2) 

2. Unparseable registrar response: [4](#0-3) 

3. Target resolves to an existing named account and the caller isn't the contract itself (so `ban_relayer` isn't used): [5](#0-4) 

The same pattern repeats in `nep_141_storage_balance_callback`:

1. `storage_balance_of` call failed: [6](#0-5) 

2. Unparseable `storage_balance_of` response: [7](#0-6) 

3. Action mismatch guard (defensive branch, but still drops `caller_deposit`): [8](#0-7) 

In every one of these branches, `caller_deposit` is a local parameter that is simply never used to build a refund `Promise`; the function returns `PromiseOrValue::Value(...)` directly. Since NEAR credits `attached_deposit` to the receiving account's balance immediately upon receipt processing (per the Economics API — "attached_deposit ... will be immediately deposited before the contract execution starts"), the funds are already on the wallet contract's account balance and there is no other code path that later returns them. This is the same failure mode as the reported Solidity bug: a fee/deposit provided by the caller is used in the "happy path" via the promise chain, but on an alternate conditional branch the developer forgot to reproduce the refund logic, and the funds stay frozen on the contract balance permanently.

The `test_caller_refunds` test only exercises the direct-promise-failure path (`PromiseResult::Failed` in `rlp_execute_callback`), which is the one path that *is* correctly refunded, so it does not cover the vulnerable branches: [9](#0-8) 

### Impact Explanation
Any external account can send an eth-implicit wallet contract an RLP-encoded transaction with `rlp_execute` and attach NEAR tokens that are recorded as a `CallerDeposit`. If the target address requires the address-registrar lookup path (`EOABaseTokenTransfer` with `address_check`) or the ERC-20 transfer path (which queries `storage_balance_of`), and the auxiliary cross-contract call fails, returns unparseable data, or reveals the target is an existing named account while the caller isn't the wallet itself, the caller's attached deposit is permanently and irrecoverably retained by the wallet contract — a genuine "permanent freezing of funds" for the depositing account. This requires no malicious relayer collusion; a benign network hiccup causing the address-registrar or token contract's cross-contract call to fail is sufficient to trigger the loss.

### Likelihood Explanation
Reaching these branches only requires an ordinary signed transaction calling the deployed, permissionless `rlp_execute` method with a nonzero attached deposit while targeting an eth-implicit address (forcing the `address_check` sub-call) or an unregistered ERC-20 receiver (forcing the `storage_balance_of` sub-call). Both sub-calls are cross-contract calls to accounts outside the caller's/wallet's control (the address registrar, or an arbitrary NEP-141 token contract), so any transient failure, malformed response, or intentionally malicious target contract can trigger the fund-losing branch. This does not require validator, network, or epoch-manager privileges — only an ordinary externally-owned relayer/caller interacting with a deployed wallet contract instance.

### Recommendation
In each of the identified early-return branches in `address_check_callback` and `nep_141_storage_balance_callback`, mirror the refund logic used in `rlp_execute_callback`: if `caller_deposit` is `Some`, issue a `promise_batch_create`/`promise_batch_action_transfer` back to `caller_deposit.account_id` for `caller_deposit.yocto_near` before returning the `ExecuteResponse::success = false` value. Consider factoring this into a shared helper (e.g. `refund_caller_deposit(caller_deposit)`) invoked from every failure exit point in the promise chain, so future branches cannot omit it.

### Proof of Concept
1. Deploy the wallet contract for an eth-implicit account `W`.
2. An external caller `C` (≠ `W`) calls `W.rlp_execute(target, tx_bytes_b64)` with `deposit > 0` NEAR attached, where the RLP-encoded transaction is a base-token transfer to an address that is not already registered in the address registrar (`EOABaseTokenTransfer { address_check: Some(address), .. }`), so `inner_rlp_execute` builds `caller_deposit = Some(CallerDeposit { account_id: C, yocto_near: deposit })` (`types.rs:180-191`) and dispatches the `address_registrar.lookup(...).then(address_check_callback(target, action, caller_deposit))` promise (`lib.rs:419-431`).
3. Cause the `address_registrar.lookup` cross-contract call to fail (e.g., the registrar contract runs out of gas, panics, or is temporarily unavailable) or return a malformed/unexpected payload.
4. `address_check_callback` hits `PromiseResult::Failed` (`lib.rs:142-148`) or the JSON-parse error branch (`lib.rs:151-157`) and returns `PromiseOrValue::Value(ExecuteResponse{success:false,...})` immediately, never constructing a refund promise for `caller_deposit`.
5. Query `C`'s balance versus `W`'s balance: `deposit` yoctoNEAR remains on `W`'s account permanently, with no subsequent code path capable of returning it to `C`.

// An external caller gets its deposit back if the cross-contract call fails.
#[tokio::test]
async fn test_caller_refunds() -> anyhow::Result<()> {
    let TestContext { worker, wallet_contract, wallet_sk, address_registrar, .. } =
        TestContext::new().await?;

    let caller = worker.root_account()?;
    let deposit_amount = NearToken::from_near(3);
    let create_tx = |receiver_id: &AccountId, nonce: u64| {
        let method = "register";
        let args = br#"{"account_id": "birchmd.near"}"#;
        let action = Action::FunctionCall {
            receiver_id: receiver_id.to_string(),
            method_name: method.into(),
            args: args.to_vec(),
            gas: Gas::from_tgas(10).as_gas(),
            yocto_near: 0,
        };
        utils::create_signed_transaction(
            nonce,
            receiver_id,
            Wei::new_u128(deposit_amount.as_yoctonear() / (MAX_YOCTO_NEAR as u128)),
            action,
            &wallet_sk,
        )
    };

    // External caller gets a refund when the cross-contract call fails
    let pre_tx_account_balance = caller.view_account().await?.balance;
    let receiver_id: AccountId = "fake.near".parse()?;
    let result = wallet_contract
        .rlp_execute_from(
            &caller,
            receiver_id.as_str(),
            &create_tx(&receiver_id, 0),
            deposit_amount,
        )
        .await?;
    assert!(!result.success);
    let post_tx_account_balance = caller.view_account().await?.balance;
    assert!(
        pre_tx_account_balance.as_yoctonear() - post_tx_account_balance.as_yoctonear()
            < deposit_amount.as_yoctonear()
    );

    // External caller does not get a refund when their tokens are spent
    let pre_tx_account_balance = post_tx_account_balance;
    let receiver_id = address_registrar.id();
    let result = wallet_contract
        .rlp_execute_from(&caller, receiver_id.as_str(), &create_tx(receiver_id, 1), deposit_amount)
        .await?;
    assert!(result.success);
    let post_tx_account_balance = caller.view_account().await?.balance;
    assert!(
        pre_tx_account_balance.as_yoctonear() - post_tx_account_balance.as_yoctonear()
            >= deposit_amount.as_yoctonear()
    );

    Ok(())
}
