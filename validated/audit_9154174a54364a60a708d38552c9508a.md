### Title
Unstaked QUIC connections can inflate `max_concurrent_uni_streams` up to 7x the intended cap via RTT manipulation - ([File: streamer/src/nonblocking/swqos.rs])

### Summary
`compute_max_allowed_uni_streams_with_rtt` applies BDP-based scaling to the concurrent uni-stream grant using `rtt_millis`, which is derived directly from `connection.rtt()` and is not clamped from below at `REFERENCE_RTT_MS` for the *unstaked* base value before scaling. An unstaked attacker who inflates its measured RTT (e.g., by deliberately delaying QUIC ACKs) can cause the server to grant it up to `QUIC_MAX_UNSTAKED_CONCURRENT_STREAMS * (MAX_RTT_MS / REFERENCE_RTT_MS)` = `128 * 350 / 50` = 896 concurrent uni streams instead of the intended cap of 128.

### Finding Description
In `streamer/src/nonblocking/swqos.rs`, `SwQos::cache_new_connection` computes the RTT-based cap and applies it via `connection.set_max_concurrent_uni_streams`: [1](#0-0) 

The scaling function is: [2](#0-1) 

For `ConnectionPeerType::Unstaked`, `streams = QUIC_MAX_UNSTAKED_CONCURRENT_STREAMS = 128` [3](#0-2) , and this base value is then multiplied by `rtt_millis.clamp(REFERENCE_RTT_MS, MAX_RTT_MS) / REFERENCE_RTT_MS` with `REFERENCE_RTT_MS = 50` and `MAX_RTT_MS = 350` [4](#0-3) . The comment "Above this RTT we stop scaling for BDP" only limits the *upper* bound; it does not prevent the unstaked cap from being scaled *above* `QUIC_MAX_UNSTAKED_CONCURRENT_STREAMS` in the first place, since any `rtt_millis > REFERENCE_RTT_MS` multiplies the base 128 upward with no ceiling at 128 itself.

`connection.rtt()` reflects the QUIC-measured round-trip time, which is influenced by when the remote peer transmits ACKs. A client can artificially delay its acknowledgments (while still remaining within idle-timeout bounds) to inflate the server-measured smoothed RTT toward `MAX_RTT_MS` (350 ms), which is explicitly documented as "Enough to cover any non-malicious link on Earth" — i.e., attacker-reachable without real network distance. This is corroborated by the crate's own test, which documents (and accepts) that "Max streams should scale with BDP in high-RTT connections" for the unstaked case, producing a stream grant of `QUIC_MAX_UNSTAKED_CONCURRENT_STREAMS + QUIC_MAX_UNSTAKED_CONCURRENT_STREAMS / 2` for a moderately elevated RTT: [5](#0-4) 

No other guard clamps the unstaked concurrent-uni-stream cap back down to 128 after BDP scaling; the separate `StakedStreamLoadEMA`/`throttle_stream` mechanism limits new-stream *acceptance rate* per 100ms window (fixed at `MAX_UNSTAKED_TPS` for unstaked peers, independent of RTT) but does not bound the number of concurrently *open* (not-yet-finished) uni streams that QUIC-level flow control allows via `set_max_concurrent_uni_streams`. Thus the concurrent-open-stream ceiling itself — a distinct resource axis from stream throughput — is evadable via RTT manipulation.

### Impact Explanation
An unstaked, unprivileged attacker can obtain up to ~7x (896 vs. 128) the intended maximum number of simultaneously open, unfinished uni streams on a single QUIC connection by inflating the connection's measured RTT toward `MAX_RTT_MS`. Because the open-stream count is what QUIC flow control (and associated per-stream buffering/state in `quinn`) tracks independently of the stream-acceptance-rate throttle, this allows one unstaked connection to hold more concurrent partial-stream state than the unstaked quota intends, disproportionately consuming stream/connection-table capacity relative to `QUIC_MAX_UNSTAKED_CONCURRENT_STREAMS`. This is a QoS-limit evasion for unstaked connections, falling under the "unstaked connection/stream limits enforced per source... cannot be evaded" invariant category.

### Likelihood Explanation
Feasible with a single unprivileged unstaked client: it only requires establishing a QUIC connection to the leader's TPU port and delaying ACK transmission to inflate the server-observed RTT before/while streams are being counted. No staked identity, gossip presence, or validator control is needed. The behavior is deterministic given `rtt_millis`, as shown directly by the existing unit test in the same file that documents streams scaling above the unstaked baseline for elevated RTT.

### Recommendation
Cap the RTT-scaled unstaked grant to never exceed `QUIC_MAX_UNSTAKED_CONCURRENT_STREAMS`, e.g., clamp the final unstaked result with `.min(QUIC_MAX_UNSTAKED_CONCURRENT_STREAMS)`, or restrict BDP scaling to staked peers only (where `QUIC_MAX_STAKED_CONCURRENT_STREAMS` already serves as an explicit upper clamp). Also consider bounding RTT-based scaling using a source of RTT that is harder to manipulate (e.g., a floor derived from `min_rtt` sampled over multiple independent probes) rather than the live smoothed RTT alone.

fn compute_max_allowed_uni_streams_with_rtt(
    rtt_millis: u32,
    peer_type: ConnectionPeerType,
    total_stake: u64,
) -> u32 {
    let streams = match peer_type {
        ConnectionPeerType::Staked(peer_stake) => {
            // No checked math for f64 type. So let's explicitly check for 0 here
            if total_stake == 0 || peer_stake > total_stake {
                warn!(
                    "Invalid stake values: peer_stake: {peer_stake:?}, total_stake: \
                     {total_stake:?}"
                );

                QUIC_MIN_STAKED_CONCURRENT_STREAMS
            } else {
                let delta = (QUIC_TOTAL_STAKED_CONCURRENT_STREAMS
                    - QUIC_MIN_STAKED_CONCURRENT_STREAMS) as f64;

                (((peer_stake as f64 / total_stake as f64) * delta) as u32
                    + QUIC_MIN_STAKED_CONCURRENT_STREAMS)
                    .clamp(
                        QUIC_MIN_STAKED_CONCURRENT_STREAMS,
                        QUIC_MAX_STAKED_CONCURRENT_STREAMS,
                    )
            }
        }
        ConnectionPeerType::Unstaked => QUIC_MAX_UNSTAKED_CONCURRENT_STREAMS,
    };
    // scale amount of streams based on RTT if RTT is larger than REFERENCE_RTT_MS
    // multiply first then divide to avoid rounding errors.
    (streams.saturating_mul(rtt_millis.clamp(REFERENCE_RTT_MS, MAX_RTT_MS))) / REFERENCE_RTT_MS
}
