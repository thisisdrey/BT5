### No vulnerability found for this question.

**Analysis:**

The behavior described is explicitly documented and intentional, not an unforeseen flaw. The `NativeWithdraw` intent doc comment states directly: *"the `wNEAR` will not be refunded in case of fail (e.g. `receiver_id` account does not exist)"* [1](#0-0) .

Tracing the path: `Contract::native_withdraw` first commits `self.withdraw(...)` synchronously (debiting the signer's wNEAR balance in the Verifier), then fires an async, detached promise chain (`near_withdraw` → `do_native_withdraw`) [2](#0-1) . `do_native_withdraw` checks only that `near_withdraw` succeeded before calling `Promise::new(withdraw.receiver_id).transfer(withdraw.amount)`; it has no re-credit/resolve callback to restore the signer's balance if the final NEAR transfer fails [3](#0-2) .

This means if `receiver_id` doesn't exist, the transfer fails and the NEAR is returned to the Defuse contract itself (per NEAR protocol semantics for failed transfers to non-existent accounts), while the signer's Verifier-tracked wNEAR balance was already debited and is not refunded — exactly as the code comment warns.

Why this doesn't qualify as a valid finding under the rules:
- The attacker signs the intent **for their own account** (`owner_id == signer_id`) and specifies their own choice of `receiver_id`. Any loss is self-inflicted by the signer's own mistake, not an unauthorized movement of another party's funds.
- No value is extracted by the attacker; the wNEAR is simply stuck/lost with no attacker profit, which falls under "griefing with no attacker profit," explicitly out of scope.
- The behavior is documented in-code as an accepted design tradeoff, not a hidden divergence from a security-critical invariant that the codebase claims to enforce elsewhere (e.g., there's no `checked_*`/refund guard promised for this path, unlike `ft_withdraw`'s resolve-based refund pattern used elsewhere for storage/refunds).

Since the impact is confined to the signer's own funds via their own signed action, with no unauthorized third-party fund movement, this does not meet the Critical/High impact bar defined in the rules. [2](#0-1) [4](#0-3) [5](#0-4)

pub struct NativeWithdraw {

    pub amount: NearToken,

                .as_slice(),

    }

    fn native_withdraw(&mut self, owner_id: &AccountIdRef, withdraw: NativeWithdraw) -> Result<()> {
        self.withdraw(
            owner_id,
            [(
                Nep141TokenId::new(self.wnear_id().into_owned()).into(),
                withdraw.amount.as_yoctonear(),
            )],
            Some("withdraw"),
            false,
        )?;

        ext_wnear::ext(self.wnear_id.clone())
            .with_attached_deposit(NearToken::from_yoctonear(1))
            .with_static_gas(NEAR_WITHDRAW_GAS)
            // do not distribute remaining gas here
            .with_unused_gas_weight(0)
            .near_withdraw(U128(withdraw.amount.as_yoctonear()))
            .then(
                // do_native_withdraw only after unwrapping NEAR
                Self::ext(env::current_account_id())
                    .with_static_gas(Self::DO_NATIVE_WITHDRAW_GAS)
                    // do not distribute remaining gas here
                    .with_unused_gas_weight(0)
                    .do_native_withdraw(withdraw),
            )
            .detach();

        Ok(())
    }

use defuse_core::intents::tokens::NativeWithdraw;
use defuse_near_utils::promise_result_checked_void;
use near_sdk::{Gas, Promise, near, require};

use crate::contract::{Contract, ContractExt};

#[near]
impl Contract {
    pub(crate) const DO_NATIVE_WITHDRAW_GAS: Gas = Gas::from_tgas(12);

    #[private]
    pub fn do_native_withdraw(withdraw: NativeWithdraw) -> Promise {
        require!(
            promise_result_checked_void(0).is_ok(),
            "near_withdraw failed",
        );

        Promise::new(withdraw.receiver_id).transfer(withdraw.amount)
    }
