### Title
Unbounded array-length allocation in TVM `validatemultisign`/`batchvalidatesign` precompiles causes OOM/DoS - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The `ValidateMultiSign` and `BatchValidateSign` precompiled contracts decode an attacker-controlled "array length" word from the raw calldata and immediately use it to allocate a `byte[len][]` array, before any bound check is guaranteed to run. This mirrors the GraphicsMagick Utah-RLE bug class in CVE-2016-7448, where a length value taken from untrusted header data is used to size a memory allocation without first validating it against the actual available payload, allowing an attacker to force excessive CPU/memory consumption.

### Finding Description
`extractBytesArray`, `extractBytes32Array`, and `extractSigArray` all read a length field directly from the caller-supplied `words` array and allocate accordingly with no upper bound: [1](#0-0) 

These helpers are invoked from `ValidateMultiSign.execute` and `BatchValidateSign.doExecute`. A size guard (`MAX_SIZE = 16`) is only applied when `VMConfig.allowTvmSelfdestructRestriction()` is enabled: [2](#0-1) [3](#0-2) 

When that hard-fork flag is not active (e.g. on private/consortium chains that have not enabled this later feature, or any deployment pinned to a config before it), the legacy branch calls `extractBytesArray`/`extractSigArray`/`extractBytes32Array` directly with `len = words[offset].intValueSafe()` fully attacker-controlled up to `Integer.MAX_VALUE`, and `new byte[len][]` is allocated **before** the post-hoc `signatures.length > MAX_SIZE` check can reject it. This is the same root-cause pattern as CVE-2016-7448: a size value taken from untrusted "header" data drives a memory allocation without validating it is within the bounds of the actual supplied data.

### Impact Explanation
Any contract can invoke the `validatemultisign` or `batchvalidatesign` precompiled contract address with crafted calldata containing a huge length word. This triggers an unbounded array allocation attempt, which can throw `OutOfMemoryError` inside the node's TVM execution thread, exhaust heap, and crash or stall the node — a remotely triggerable denial of service reachable by any unprivileged transaction/contract call, consistent with the "node crash/halt" impact criteria.

### Likelihood Explanation
Any account can deploy a trivial contract that calls the precompile address with an oversized length word, or any account can directly craft a TVM call/triggercontract into the precompile. The vulnerable code path is only closed by the `allowTvmSelfdestructRestriction` config flag; on any node/network where that flag is not yet enabled, the unbounded-allocation path is live and directly reachable from an ordinary contract call.

### Recommendation
Move the `MAX_SIZE` (or a hard cap tied to `rawData.length`) bound check ahead of `extractBytesArray`/`extractBytes32Array`/`extractSigArray` unconditionally (not gated behind `allowTvmSelfdestructRestriction`), and validate that the declared `len`/`bytesLen` values are consistent with the actual remaining `data.length` before allocating, similar to `verifyLength` pattern used elsewhere in the RLP decoder.

### Proof of Concept
Craft ABI-encoded calldata for `validatemultisign(address,uint256,bytes32,bytes[])` (or `batchvalidatesign`) where the dynamic array's length word is set to a very large value (e.g. `0x7fffffff`) while the actual payload is small. Invoke this from a deployed contract via a normal `TriggerSmartContract` transaction on a node/network where `allowTvmSelfdestructRestriction` is not enabled. `extractBytesArray`/`extractSigArray` will execute `new byte[len][]` with `len` ≈ 2^31, causing an `OutOfMemoryError` in the executing node thread.
