### Title
Unclaimed rewards in a removed `RewardsDistributor` can be stolen via balance transfers to fresh accounts - ([File: contracts/RewardsDistributor.sol])

### Summary
Metronome's `Pool` maintains a list of `RewardsDistributor` contracts (`pool.getRewardsDistributors()`), and `DepositToken`/`DebtToken` notify each registered distributor on every balance change via `updateBeforeMintOrBurn`/`updateBeforeTransfer`. When a distributor is removed from that list, it stops receiving balance-change callbacks, but its `claimRewards`/`updateBeforeMintOrBurn` entry points remain callable and its accrual math still reads the token's *live* `balanceOf(account_)`. An unprivileged attacker can therefore move deposit/debt token balances to fresh accounts and drain the removed distributor's remaining reward tokens, claiming the full historical index against a balance that never accrued those rewards.

### Finding Description
Two facts combine to create the bug:

1. Accrual uses live balance with a stale per-account index. In `_calculateTokenDelta`, the reward delta is `token_.balanceOf(account_).wadMul(_tokenIndex - _accountIndex)`, where `_accountIndex` falls back to `INITIAL_INDEX` (1e18) if the account was never touched. So a fresh account that receives balance *after* the distributor stops being updated will be credited `(finalIndex - 1e18) * newBalance` — i.e., the entire reward history of the token, computed against a balance it just acquired.
   - `contracts/RewardsDistributor.sol:217-231` (`_calculateTokenDelta`, `accountIndexOf` fallback at lines 225-227)
   - `contracts/RewardsDistributor.sol:261-266` (`_updateTokensAccruedOf`)

2. The claim path on a removed distributor is unguarded. `claimRewards` (lines 134-168) and `updateBeforeMintOrBurn` (lines 175-180) have no `onlyIfDistributorExists` check — only `updateTokenSpeed` (`_updateTokenSpeed`, line 290) is gated. `_transferRewardIfEnoughTokens` (lines 248-256) pays out from whatever `rewardToken` balance the distributor still holds.

Once a distributor holding unclaimed `rewardToken` is removed from `pool.getRewardsDistributors()`, `DepositToken.transfer`/`mint`/`burn` and `DebtToken.issue`/`repay` no longer call `updateBeforeTransfer`/`updateBeforeMintOrBurn` on it, so `accountIndexOf[token][newAccount]` stays 0 while the actual balance moves freely.

### Impact Explanation
Direct theft of unclaimed yield: every reward token left in the removed distributor can be siphoned by an EOA that cycles deposit-token (or debt-token-share) balances through fresh accounts. The accrued amount per account is `balance * (index - INITIAL_INDEX)`, which can far exceed any legitimate accrual. This is the same loss category as the TOKE-8 finding (theft of unclaimed rewards from a decommissioned rewarder).

### Likelihood Explanation
Requires the governor to remove a rewards distributor while it still holds a `rewardToken` balance — a privileged trigger identical in class to TOKE-8's `removeExtraRewards` (which also required a privileged `rewardRole`). Given that precondition, exploitation is fully unprivileged: no health checks, supply caps, reentrancy guard, `SynthContext`, or pause flag applies to `claimRewards`/`updateBeforeMintOrBurn`, and `nonReentrant` does not prevent the multi-account replay. `_transferRewardIfEnoughTokens` even silently caps at the contract balance, so the drain is monotonic and repeatable until empty.

Note: I was unable to read the exact `Pool` removal function name in this pass (grep confirmed `Pool.sol` contains ~25 rewards-distributor references including `getRewardsDistributors` and add/remove management), but `onlyIfDistributorExists` iterating `pool.getRewardsDistributors()` confirms distributors are dynamically added/removed.

### Recommendation
Mirror the TOKE-8 remediation: never remove a `RewardsDistributor` from the pool while it may hold unclaimed rewards; alternatively gate `claimRewards`/`updateBeforeMintOrBurn`/`updateBeforeTransfer` with `onlyIfDistributorExists` so a removed distributor can no longer pay out, or sweep `rewardToken` balances on removal.

### Proof of Concept
Hardhat (fork or fixture with Pool, DepositToken `msdX`, DebtToken, distributor `D` with speed > 0 and rewardToken balance):

```ts
// 1. Rewards run for a while; index grows to I >> INITIAL_INDEX.
//    Attacker account A holds 0 msdX (or had index snapshotted at 0 balance).
// 2. Governor removes D from pool.getRewardsDistributors().
// 3. Attacker (unprivileged):
const B = freshEOA(); // accountIndexOf[msdX][B] == 0
await depositToken.connect(A).transfer(B.address, amount); // D not notified
// B's stored index is 0 -> _calculateTokenDelta uses INITIAL_INDEX fallback
await distributor.connect(B).updateBeforeMintOrBurn(msdX.address, B.address);
await distributor.connect(B)['claimRewards(address)'](B.address);
// B receives amount * (I - 1e18) rewardTokens — rewards for a period it never held.
// 4. Repeat: transfer msdX to C, claim from C, ... until distributor is empty.
```

`msdX.transfer` invokes `updateBeforeTransfer` only on distributors still in `pool.getRewardsDistributors()`, so `D` never snapshots B/C's index — each fresh account claims the full historical delta.
