### Title
ValidateMultiSign precompile is vulnerable to ECDSA signature malleability, allowing multisig threshold bypass with a single signing key - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The `validatemultisign` TVM precompile (`ValidateMultiSign.execute`) is meant to let smart contracts verify that an on-chain account's multisig **weight threshold** has genuinely been met before authorizing a privileged action (fund release, custody approval, governance action, etc.) — conceptually the exact same trust primitive whose real-world compromise let the Humanity Protocol attacker cross a signing threshold with fewer independent keys than intended. In java-tron's implementation, the "already-signed" de-duplication check keys off the exact signature bytes rather than the recovered signer address, so a single ECDSA key's signature weight can be **counted twice** by supplying its canonical and its mathematically-equivalent malleable variant, letting one real key satisfy a threshold that should require multiple independent signers.

### Finding Description
`ValidateMultiSign.execute` computes, per submitted signature, the recovered address and its permission weight, then de-duplicates using: [1](#0-0) 

The check is:
```
if (ByteArray.matrixContains(executedSignList, recoveredAddr)) {
  if (ByteArray.matrixContains(executedSignList, sign)) {
    continue;
  }
  MUtil.checkCPUTime();
}
long weight = TransactionCapsule.getWeight(permission, recoveredAddr);
...
totalWeight += weight;
executedSignList.add(sign);
executedSignList.add(recoveredAddr);
```
If the same `recoveredAddr` reappears but with **different signature bytes**, the code does not skip it — it only runs a CPU-time guard and then adds the weight again. Because ECDSA (secp256k1) signatures are malleable, any valid signature `(r, s, v)` has a second, distinct, publicly-derivable valid signature `(r, n-s, 1-v)` for the *same* message hash that recovers to the *same* address — this second signature can be computed by anyone from the first, without the private key. Submitting both to `validatemultisign` therefore doubles the counted weight of a single signer.

Contrast with the correctly-implemented equivalent in `TransactionCapsule.checkWeight`, which is used for top-level transaction signature verification and keys its "already signed" map off the **recovered address**, not the raw signature bytes: [2](#0-1) 

That logic throws `"... has signed twice!"` if the same address appears twice, correctly preventing double counting regardless of signature malleability. The precompile's re-implementation of the same concept in `PrecompiledContracts.java` diverges from this safe pattern and is broken.

The `ValidateMultiSign` precompile is reachable from any TVM contract via `validatemultisign(...)`, which any unprivileged account can trigger through a normal `TriggerSmartContract` call against any deployed contract that uses this precompile for authorization logic (e.g., custodial/treasury/escrow contracts implementing on-chain multisig approval), as exercised in the test suite: [3](#0-2) 

### Impact Explanation
Any smart contract that relies on `validatemultisign` to gate a privileged operation (fund transfer, withdrawal approval, admin action) behind an account's Active/Owner permission threshold can have that threshold satisfied by a single compromised or malicious signer, because the weight of one key can be duplicated via signature malleability to synthetically reach the threshold. This is a direct "unauthorized account operation" / theft-of-funds primitive for any dependent contract logic, mirroring the real-world impact of the Humanity Protocol incident where fewer genuinely independent signers than the nominal threshold were sufficient to seize control — except here the flaw is a code-level verification bug rather than a key-custody failure.

### Likelihood Explanation
High. No private key theft or insider access is required: the second (malleable) signature can be derived purely mathematically from any one valid signature over the target hash, by any unprivileged contract caller. The attack only requires access to one weight-bearing key on the target account/permission and the ability to call a contract that invokes `validatemultisign` — both are attacker-controlled preconditions with no special privilege, consistent with the "unprivileged contract deployer/caller" reachability required by scope.

### Recommendation
In `ValidateMultiSign.execute`, de-duplicate strictly by `recoveredAddr` (as `TransactionCapsule.checkWeight` already does), not by the raw signature bytes, i.e. skip/reject as soon as `recoveredAddr` has been seen once, regardless of whether the exact signature bytes differ. Additionally, enforce canonical (low-`s`) signature form on input to reject malleable variants outright, consistent with standard ECDSA anti-malleability practice.

### Proof of Concept
1. Create an account with an Active permission of threshold `2`, containing key `K` with weight `1` and key `K2` with weight `1` (as in `ValidateMultiSignContractTest.testDifferentCase`).
2. Have only key `K` sign the target hash once, producing signature `S1 = (r, s, v)`.
3. Derive the malleable counterpart `S2 = (r, n-s, 1-v)` — purely arithmetic, no private key needed, `n` being the secp256k1 curve order.
4. Call `validatemultisign(address, permissionId, data, [S1, S2])`.
5. Both `S1` and `S2` recover to `K`'s address; per the flawed loop, `recoveredAddr` for `S2` is already in `executedSignList` but the raw `sign` bytes differ, so the `continue` is skipped, `checkCPUTime()` runs, and `K`'s weight (`1`) is added a second time, yielding `totalWeight = 2 >= threshold(2)`, returning `dataOne()` (success) — with only one real signer.
