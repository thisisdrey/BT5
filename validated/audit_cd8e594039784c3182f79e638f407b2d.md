### Title
`ValidateMultiSign` precompile builds its authorization digest without chain/network domain separation - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `ValidateMultiSign` TVM precompiled contract (TIP-171, address-permission signature verification exposed to any Solidity contract) recomputes the digest that off-chain co-signers sign as `sha256(address || permissionId || data)`, with no chain identifier, genesis hash, or verifying-contract binding folded in. Because TRON account addresses are derived purely from secp256k1 keys and are identical across every TRON-based network (Mainnet, Nile/Shasta testnets, private/forked chains), a valid multisig authorization produced for one network can be replayed verbatim on any other network where the same account/permission set exists, exactly mirroring the "signed digest lacks a domain separator" bug class described in the external report.

### Finding Description
`ValidateMultiSign.execute` decodes the caller-supplied `address`, `permissionId`, and `data`, then derives the hash that must be co-signed by the account's permission keys purely from those three fields: [1](#0-0) 

This hash is then checked against each supplied signature via `recoverAddrBySign`, and weights are summed against the on-chain `Permission` threshold: [2](#0-1) 

Unlike native transaction signing — where `TransactionCapsule.validateSignature` hashes the raw transaction (which is bound to a specific chain because it references `ref_block_hash`/TAPOS data unique to that chain's block history) — this precompile's digest is fully decoupled from any chain-identifying data: [3](#0-2) 

There is no `chainid`, genesis block hash, or precompile/contract identity mixed into the `combine` buffer. Any dApp built on top of `ValidateMultiSign` to implement off-chain "permit"-style authorizations (custodial withdrawal approvals, order signing, meta-transactions, etc.) inherits this gap: the digest depends only on `(address, permissionId, data)`, none of which vary between networks that share the same account keys and permission configuration.

### Impact Explanation
An unprivileged actor who observes a valid `(address, permissionId, data, signatures[])` tuple used to satisfy `ValidateMultiSign` on one TRON network (e.g., a testnet used for staging, or a forked/private chain sharing the same genesis account set) can resubmit the identical `data`/signature bundle via a `TriggerSmartContract` call to the same precompile on another network where the signer's account and permission configuration are identical. Because the digest carries no domain separator, verification succeeds and the contract on the second network executes the authorized action (e.g., releasing funds, approving a withdrawal, executing a governance action) without the signer's actual intent for that network — resulting in unauthorized account operations / theft of funds on the replay target.

### Likelihood Explanation
Exploitation requires that the same address and multisig `Permission` configuration exist and are reachable on more than one network the attacker can broadcast to (common in TRON given shared genesis/private-chain forks and staging-then-production key reuse patterns), and that the calling contract's `data` payload does not itself already encode a chain-specific value. Given that `ValidateMultiSign` is a generic, widely reusable primitive (any TVM contract can call it) and its digest construction gives callers no built-in protection, the precondition is plausible for real deployments that reuse keys/permissions across environments, making this a realistic Medium-severity issue rather than a purely theoretical one.

### Recommendation
Fold a domain separator into the digest computed by `ValidateMultiSign` (and any similarly-shaped verification precompiles such as `BatchValidateSign`), e.g. include the chain ID (`DynamicPropertiesStore` chain identifier used for `CHAINID` opcode) and/or the precompile's fixed address in the `combine` buffer before hashing: [4](#0-3) 
so that signatures produced for one chain cannot be replayed as valid on another.

### Proof of Concept
1. Deploy identical contract code (or reuse the same custodial account address) on two TRON-compatible networks that share the same account keypair and an `Active` `Permission` with the same `permissionId`/threshold/keys (realistic for private/forked chains or staging environments cloned from mainnet state).
2. On Network A, have the required co-signers produce `data`, compute `hash = sha256(address || permissionId || data)`, and sign it, then call the contract that invokes `ValidateMultiSign(address, permissionId, data, signatures)` to authorize an action (e.g., a withdrawal).
3. Capture the `(address, permissionId, data, signatures[])` tuple used in that transaction.
4. Submit a `TriggerSmartContract` transaction with the identical tuple to the equivalent contract on Network B.
5. `ValidateMultiSign.execute` recomputes the same `hash` (no chain binding), `recoverAddrBySign` returns the same signer addresses, weight threshold is met, and the precompile returns `true`/`DATA_TRUE`, authorizing the action on Network B without any signer intent for that network.

    if (account == null) {

        permission = AccountCapsule
            .createDefaultActivePermission(ByteString.copyFrom(owner), dynamicPropertiesStore);
      }
    } else {
      permission = account.getPermissionById(permissionId);
    }
    if (permission == null) {
      throw new PermissionException("permission isn't exit");
    }
