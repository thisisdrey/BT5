### Title
Inconsistent tronPower calculation between `VoteWitnessActuator` and TVM `VoteWitnessProcessor` allows validation-limit mismatch when casting votes - (File: actuator/src/main/java/org/tron/core/vm/nativecontract/VoteWitnessProcessor.java)

### Summary
The regular vote-casting path and the TVM smart-contract vote-casting path compute the voter's maximum allowed "tron power" using two different, non-equivalent conditions, mirroring the reported Balancer bug class where the code "wrongly assumes" a single computation method applies to all cases when in fact there are two valid variants that must be chosen consistently.

### Finding Description
`VoteWitnessActuator.validate()`, the path used by a normal signed `VoteWitnessContract` transaction, decides which tron-power accessor to use based on a single flag: [1](#0-0) 

```
long tronPower;
DynamicPropertiesStore dynamicStore = chainBaseManager.getDynamicPropertiesStore();
if (dynamicStore.supportAllowNewResourceModel()) {
  tronPower = accountCapsule.getAllTronPower();
} else {
  tronPower = accountCapsule.getTronPower();
}
```

By contrast, `VoteWitnessProcessor.execute()`, which is the native-contract implementation reachable by any TVM smart contract that invokes the vote precompile (i.e. by an unprivileged contract deployer/caller from a broadcast transaction), gates the same decision on the conjunction of **two** flags instead of one: [2](#0-1) 

```
long tronPower;
if (repo.getDynamicPropertiesStore().supportUnfreezeDelay()
    && repo.getDynamicPropertiesStore().supportAllowNewResourceModel()) {
  tronPower = accountCapsule.getAllTronPower();
} else {
  tronPower = accountCapsule.getTronPower();
}
```

`getTronPower()` and `getAllTronPower()` are not simple equivalent representations of the same quantity — they sum different underlying fields depending on the account's `oldTronPower` migration state: [3](#0-2) 

```
public long getTronPower() {
  long tp = 0;
  for (int i = 0; i < account.getFrozenCount(); ++i) {
    tp += account.getFrozen(i).getFrozenBalance();
  }
  tp += account.getAccountResource().getFrozenBalanceForEnergy().getFrozenBalance();
  tp += account.getDelegatedFrozenBalanceForBandwidth();
  tp += account.getAccountResource().getDelegatedFrozenBalanceForEnergy();
  tp += getFrozenV2List().stream().filter(o -> o.getType() != TRON_POWER)
          .mapToLong(FreezeV2::getAmount).sum();
  tp += account.getDelegatedFrozenV2BalanceForBandwidth();
  tp += account.getAccountResource().getDelegatedFrozenV2BalanceForEnergy();
  return tp;
}

public long getAllTronPower() {
  if (account.getOldTronPower() == -1) {
    return getTronPowerFrozenBalance() + getTronPowerFrozenV2Balance();
  } else if (account.getOldTronPower() == 0) {
    return getTronPower() + getTronPowerFrozenBalance() + getTronPowerFrozenV2Balance();
  } else {
    return account.getOldTronPower() + getTronPowerFrozenBalance()
        + getTronPowerFrozenV2Balance();
  }
}
```

`getTronPower()` sums bandwidth/energy-type frozen balances (old-style and V2, excluding `TRON_POWER`-type entries), while `getAllTronPower()` branches on `account.getOldTronPower()`:
- When it equals `-1` (meaning old-style frozen balances have been invalidated/migrated), `getAllTronPower()` returns **only** `TRON_POWER`-typed frozen balances (old + V2), completely excluding bandwidth/energy frozen amounts that `getTronPower()` still counts.
- When it equals `0`, `getAllTronPower()` returns `getTronPower() + TRON_POWER-type balances` (strictly larger than `getTronPower()`).

Because the two vote-processing code paths pick between these functions using different flag conditions (`supportAllowNewResourceModel()` alone vs. `supportAllowNewResourceModel() && supportUnfreezeDelay()`), there exists a reachable chain state — specifically when `AllowNewResourceModel` is activated but `UnfreezeDelay` is not (these are independent, separately-activatable committee proposals tracked in `DynamicPropertiesStore`) — where the normal actuator path enforces one power ceiling while the TVM native-contract path enforces a different one for the exact same account state. This is the same root-cause pattern as the reported Balancer issue: code hard-codes an assumption about which variant applies without verifying that both call sites make the decision the same way.

### Impact Explanation
If `getTronPower()` (used by the TVM path in the diverging state) yields a larger permitted value than `getAllTronPower()` (used by the actuator path) for the same account — e.g. an account whose `oldTronPower == -1` has significant old-style/V2 bandwidth or energy frozen balance but little/no `TRON_POWER`-typed frozen balance — a smart contract invoking the vote precompile can cast/validate votes up to a higher `tronPower` ceiling than the direct `VoteWitnessContract` transaction path would allow for the identical account state. This inflates the votes recorded for one or more witnesses beyond what the account's true governance-eligible stake should permit under the new resource model, corrupting SR (Super Representative) election results, block-production rights, and the standby-witness/committee reward distribution that depends on `WitnessCapsule.getVoteCount()` (consumed in `MortgageService`, `IncentiveManager`, and `MaintenanceManager`). This is an unauthorized/incorrect account-operation impact on core consensus governance, satisfying a Medium/High-severity analog.

### Likelihood Explanation
The divergence is only exploitable while the chain has `AllowNewResourceModel` active and `UnfreezeDelay` inactive — both are proposal-gated hard-fork flags in `DynamicPropertiesStore`, so the window depends on chain configuration/rollout sequencing rather than attacker control. Once triggered, however, the exploit path itself (deploying/calling a contract that invokes the vote precompile) is trivially reachable by any anonymous account with no special privilege, matching the "unprivileged contract deployer/caller" reachability requirement.

### Recommendation
Unify the tron-power selection logic into a single shared helper (e.g., a method on `AccountCapsule` or a shared utility) that both `VoteWitnessActuator.validate()` and `VoteWitnessProcessor.execute()` call, using one canonical condition (matching whichever gating flags are actually intended, likely `supportUnfreezeDelay() && supportAllowNewResourceModel()`, or documenting precisely why the two paths should legitimately differ). Add regression tests asserting that the actuator and native-contract paths compute identical `tronPower` ceilings for the same account state across all `oldTronPower` migration states (`-1`, `0`, and positive).

### Proof of Concept
Conceptual reproduction (not fully verified end-to-end due to index limitations on precompile dispatch wiring):
1. Activate `AllowNewResourceModel` via committee proposal, while keeping `UnfreezeDelay` inactive.
2. Create an account that has undergone the unfreeze-v2 migration such that `account.getOldTronPower() == -1`, and freeze a large amount for BANDWIDTH/ENERGY (V2), with zero or minimal TRON_POWER-type frozen balance.
3. Call `VoteWitnessActuator.validate()` directly with a vote contract: it computes `tronPower = accountCapsule.getAllTronPower()`, which under `oldTronPower == -1` returns only the TRON_POWER-typed balance (near zero) — the vote is rejected as exceeding tronPower.
4. Deploy a contract that calls the TVM vote precompile with the same voter address and vote amount, triggering `VoteWitnessProcessor.execute()`; since `supportUnfreezeDelay()` is false, it falls to `tronPower = accountCapsule.getTronPower()`, which includes the large BANDWIDTH/ENERGY frozen balance — the same vote that was rejected via path (3) is now accepted via the TVM path, inflating the witness's recorded vote count beyond what the "new resource model" ceiling should allow.

This PoC could not be executed against a running node in this analysis; the discrepancy is demonstrated purely via static code comparison of the two validation branches and the differing semantics of `getTronPower()` vs `getAllTronPower()`. A Devin session with repository build/test access would be needed to construct and run the actual on-chain reproduction (freeze/migrate account state, toggle the two proposals independently, and compare actuator vs. TVM precompile vote acceptance).
