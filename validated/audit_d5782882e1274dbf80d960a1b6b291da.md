Based on the code review, this describes expected/inherent behavior of Solana's parallel account-locking design, not an exploitable bypass.

**Analysis:**

`ThreadAwareAccountLocks::write_schedulable_threads` (via `schedulable_threads::<true>`) is *designed* to restrict a writable, already-locked account to the single thread currently holding its write lock — this is a correctness mechanism to prevent concurrent conflicting writes, not a fairness/QoS control. [1](#0-0) 

When `try_lock_accounts` finds conflicting locks on multiple threads it returns `TryLockError::MultipleConflicts`, which `GreedyScheduler::try_schedule_transaction` converts into `TransactionSchedulingError::UnschedulableConflicts`; the transaction is pushed back into `unschedulables` and retried on subsequent scheduling passes rather than dropped. [2](#0-1) [3](#0-2) 

This behavior is identical for legitimate and attacker traffic — any burst of transactions writing the same hot account (e.g., a popular AMM pool) will naturally serialize onto one thread, because Solana's execution model requires exclusive write access per account. This is a documented, intentional consequence of parallel account-locked scheduling, not a QoS bypass. Crucially:

- Only the single thread holding the contended account's lock is affected; the other `num_threads - 1` threads continue processing unrelated, non-conflicting transactions from other senders normally — `schedulable_threads` bitmask shrinking to one thread only affects transactions requiring that specific account, not global TPU capacity.
- Per-thread CU budget (`target_scheduled_cus / num_threads`) caps how much of that one thread's capacity is consumable, and the scheduler's priority-ordered container (`container.pop()`) still lets higher-fee transactions (including from legitimate senders on the same hot account) win priority over low-fee spam.
- No unstaked/staked QoS limit is being bypassed: the QQuic per-IP/connection stream quotas mentioned in the invariant still gate how many transactions the attacker can inject in the first place; nothing in `ThreadAwareAccountLocks` or `GreedyScheduler` grants unstaked senders extra throughput or evades those caps — it merely reflects the pre-existing contention behavior applicable to all senders equally.

The proof-of-concept described (`test_try_lock_accounts_multiple`, `test_schedule_single_threaded_conflict`, `test_schedule_scan_past_highest_priority`) already exists in the codebase as expected-behavior unit tests confirming that same-account conflicts serialize to one thread — this is documented, tested, intended design, not a bug.     /// If there are no locks, then all threads are schedulable.
    /// If only write-locked, then only the thread holding the write lock is schedulable.
    /// If a mix of locks, then only the write thread is schedulable.
    /// If only read-locked, the only write-schedulable thread is if a single thread
    ///   holds all read locks. Otherwise, no threads are write-schedulable.
    /// If only read-locked, all threads are read-schedulable.
    fn schedulable_threads<const WRITE: bool>(&self, account: &Pubkey) -> ThreadSet {
