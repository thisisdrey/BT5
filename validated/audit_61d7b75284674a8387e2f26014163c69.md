## Analog Found

### Title
Inconsistent-model precision check in `ExchangeWithdrawActuator` incorrectly rejects legitimate withdrawals — ([File: actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java])

### Summary
Just like GoodEntry's `addDust` used one price model (oracle-derived scaling) to guard a value that is actually produced by a different model (Uniswap tick math) — causing the "safety margin" to be systematically wrong and to spuriously revert — `ExchangeWithdrawActuator.doValidate()` computes the TRC10 exchange withdrawal's `anotherTokenQuant` using integer floor division, but then "sanity-checks" that same value against a *different* computation (a `BigDecimal` division rounded to 4 decimal places) and reverts the transaction if the two diverge by more than an arbitrary 0.01% relative threshold. Because the two computations are fundamentally different (exact truncating integer division vs. a fixed 4-decimal approximation), the check does not actually validate what it claims to, and ordinary, perfectly valid withdrawals are rejected whenever the pool ratio isn't an exact multiple of the requested quantity.

### Finding Description
In `doValidate()`, `anotherTokenQuant` is always computed via exact truncating division: [1](#0-0) 

When the `ALLOW_HARDEN_EXCHANGE_CALCULATION` chain parameter is enabled (via `allowHarden()`/`AbstractExchangeActuator.allowHarden`), a second, unrelated computation is performed to "verify" the first one: [2](#0-1) 

This second computation rounds the ratio to 4 decimal places with `RoundingMode.HALF_UP` and compares it against the exact truncated integer result, rejecting the transaction with `"Not precise enough"` if the discrepancy (which is *inherent* to comparing a rounded decimal approximation against exact integer floor division) exceeds 0.01% of the computed quantity. This mirrors the GoodEntry root cause precisely: the value used to actually execute the operation (exact floor division) is computed by one method, while the guard/sanity check that decides whether the operation is allowed to proceed is computed by an unrelated method (decimal rounding to a fixed scale). The two are not reconcilable in general, so the check does not achieve its intended goal — it doesn't detect a genuine precision problem, it just fails whenever the ratio isn't a "clean" multiple.

The identical unrelated-model check exists symmetrically for the other token branch: [3](#0-2) 

The dynamic property gating this behavior is a standard committee-controlled chain parameter: [4](#0-3) [5](#0-4) 

The repo's own test confirms the flaw: a perfectly legitimate withdraw of `9991` units against a 100M/200M pool (`anotherTokenQuant = 4995`, true ratio `4995.5`) is rejected outright as `"Not precise enough"` purely because it does not happen to be an exact multiple of the pool ratio: [6](#0-5) 

### Impact Explanation
Once `ALLOW_HARDEN_EXCHANGE_CALCULATION` is enabled, `ExchangeWithdrawContract` (reachable by any account that created a TRC10 exchange and is withdrawing its own liquidity — a fully unprivileged, ordinary signed transaction) will revert for the overwhelming majority of withdrawal quantities, since exact-multiple ratios are the exception rather than the rule for realistic pool balances. This effectively freezes the creator's ability to withdraw liquidity from the exchange pool — a permanent/near-permanent freezing-of-funds condition for legitimate operations, exactly analogous to how GoodEntry's dust mechanism could make `addDust`'s safety goal unreachable and cause spurious reverts.

### Likelihood Explanation
The precondition is a single chain-parameter proposal (`ALLOW_HARDEN_EXCHANGE_CALCULATION = 1`), which is a normal, expected governance action (the flag exists specifically to be turned on). Once active, every `ExchangeWithdrawContract` transaction is affected — no attacker action beyond sending a standard withdraw transaction with a non-"clean" quantity is required, which is the common case, not an edge case.

### Recommendation
Remove the redundant decimal-based "precision" check, or replace it with a check that is mathematically consistent with the actual computation path (e.g., verify the exact integer division itself and its true remainder rather than comparing against a different, decimal-rounded approximation). The check should validate the real transformation used to derive `anotherTokenQuant`, not an unrelated approximate model.

### Proof of Concept
Using the existing repository test as the reproduction: [7](#0-6) 
With `ALLOW_HARDEN_EXCHANGE_CALCULATION` enabled and a 100,000,000 / 200,000,000 pool, withdrawing `9991` units of the second token computes `anotherTokenQuant = 4995` (exact truncating division), yet the decimal-approximation check computes a "remainder" of `0.5`, which exceeds the `0.0001 * 4995 = 0.4995` threshold, causing the actuator to throw `ContractValidateException("Not precise enough")` even though `4995` is the correct, intended withdrawal amount.
