Based on the code, I found a valid analog to the Jimbo's Protocol vulnerability class in java-tron's on-chain bancor-style `Exchange` (TRX/TRC10 liquidity pool) actuators.

### Title
Missing slippage/price-bound protection in `ExchangeInjectActuator`/`ExchangeWithdrawActuator` allows sandwich extraction of pool-owned liquidity - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`)

### Summary
The `Exchange` module implements an on-chain bancor-style liquidity pool (`ExchangeCapsule`) for TRX/TRC10 pairs. Liquidity providers add/remove liquidity via `ExchangeInjectContract`/`ExchangeWithdrawContract`, which compute the counter-asset amount proportionally to the pool's *current* balances at execution time. Unlike the swap contract (`ExchangeTransactionContract`, which carries an `expected` minimum-output field), neither the inject nor withdraw contract carries any user-specified bound/tolerance on the resulting ratio or counter-asset amount. This is structurally identical to the Jimbo's Protocol root cause: "lack of slippage control on the liquidity transfer operation," which let an attacker skew the pool price immediately before/after the liquidity operation and profit from reverse swaps.

### Finding Description
`ExchangeInjectActuator.execute` pulls the pool's live balances and computes the counter-token amount purely from the ratio present at block-application time: [1](#0-0) 

The validate path performs the identical ratio computation for its checks, but again with no caller-supplied bound — only that the derived quantity is `> 0` and within the global `balanceLimit`: [2](#0-1) 

The protobuf contract itself confirms `ExchangeInjectContract`/`ExchangeWithdrawContract` only carry `exchange_id`, `token_id`, and `quant` — no minimum/maximum counter-quantity or expected-ratio field — whereas `ExchangeTransactionContract` explicitly has an `expected` field for exactly this purpose: [3](#0-2) 

`ExchangeWithdrawActuator` mirrors this: it computes `anotherTokenQuant` from the live pool ratio with only a rounding/"precision" tolerance check (`"Not precise enough"`), not a price/slippage tolerance: [4](#0-3) 

The underlying pool math (`ExchangeCapsule.transaction` via `ExchangeProcessor`) is a continuous bancor-relay formula, so any swap (`ExchangeTransactionContract`) immediately before an inject/withdraw shifts `firstTokenBalance`/`secondTokenBalance`, and thus shifts the ratio used by the next inject/withdraw in the same or an adjacent block: [5](#0-4) 

Because only the exchange's original creator may call inject/withdraw (`"is not creator"` check), this role is directly analogous to a protocol's own liquidity manager (Jimbo's Protocol's owned liquidity) — an ordinary, unprivileged, self-registered account (anyone can become an exchange creator via `ExchangeCreateContract`) whose liquidity moves are still fully exposed to unprotected pool-ratio manipulation from any other unprivileged trader: [6](#0-5) 

### Impact Explanation
An attacker who observes a pending `ExchangeInjectContract` (or `ExchangeWithdrawContract`) transaction can broadcast an `ExchangeTransactionContract` swap immediately before it to skew the pool's `firstTokenBalance`/`secondTokenBalance` ratio away from fair market value, then broadcast a second swap immediately after the inject/withdraw executes to restore the ratio and capture the arbitrage. Because the inject/withdraw actuators compute the counter-asset amount strictly from the manipulated live ratio with no minimum/maximum bound, the liquidity provider is forced to inject (or receive on withdraw) at the skewed, attacker-chosen ratio, transferring value to the attacker — the same mechanism as the $7.5M Jimbo's Protocol loss. This results in direct, unauthorized transfer of value (theft of funds) from any exchange creator/liquidity provider on the java-tron `Exchange` market.

### Likelihood Explanation
Any account can create an exchange pool (via `ExchangeCreateContract`) and act as its own liquidity provider, and any other unprivileged account can freely submit `ExchangeTransactionContract` swap transactions against that same pool with no cooldown or price-impact cap beyond the global `balanceLimit`. Transaction ordering within a block is attacker-influenceable (front-run/back-run via standard broadcast timing), making the sandwich pattern practically executable by any unprivileged transaction broadcaster targeting known/whale exchange pools, mirroring the real-world Jimbo's Protocol exploit conditions.

### Recommendation
Add a caller-specified slippage bound to `ExchangeInjectContract` and `ExchangeWithdrawContract` (e.g., `expected_another_token_quant_min`/`max`, analogous to the `expected` field already present in `ExchangeTransactionContract`), and enforce it in `ExchangeInjectActuator.execute`/`ExchangeWithdrawActuator.execute` before committing the balance changes, rejecting the operation if the computed counter-asset amount falls outside the caller's tolerance.

### Proof of Concept
1. Attacker monitors the mempool for a pending `ExchangeInjectContract` from exchange creator `C` on exchange `E` (pair A/B, current balances `balA`, `balB`).
2. Attacker submits `ExchangeTransactionContract` selling a large amount of `A` for `B` on `E`, shifting the ratio so `balA` rises and `balB` falls sharply (per `ExchangeProcessor.exchange`, `chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java:41-45`).
3. `C`'s inject transaction executes against the now-skewed ratio: `ExchangeInjectActuator` computes `anotherTokenQuant = secondTokenBalance * tokenQuant / firstTokenBalance` using the manipulated `secondTokenBalance`/`firstTokenBalance`, forcing `C` to supply an inflated amount of `B` relative to fair value (`actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java:71-83`).
4. Attacker submits a second `ExchangeTransactionContract` reversing the initial swap, restoring the ratio and extracting the excess `B` value that `C` was forced to inject at the skewed rate, net profit to the attacker at `C`'s expense.

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
  }
