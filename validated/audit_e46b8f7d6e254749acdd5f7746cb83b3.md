### Title
Attachment content is inserted into the Atlas batch without verifying it matches the requested `content_hash` - (File: stackslib/src/net/atlas/download.rs)

### Summary
`AttachmentsBatchStateContext::extend_with_attachments` decodes a peer's `GET /v2/attachments/{content_hash}` response and inserts `response.attachment` into `self.attachments` without ever comparing `response.attachment.hash()` to the `AttachmentRequest.content_hash` that was queued. A malicious download-source peer can therefore return arbitrary attachment bytes for any requested hash, and those bytes are accepted as if they matched.

### Finding Description
The request is built from `AttachmentRequest::content_hash` via `Requestable::make_request_type`, which forms the URL `/v2/attachments/{content_hash}` [1](#0-0) . The `AttachmentRequest` struct carries this `content_hash` field that is expected to bind the response to a specific attachment [2](#0-1) .

When the batched request completes, `extend_with_attachments` iterates `results.succeeded`, decodes the HTTP body with `response.decode_atlas_get_attachment()`, and directly calls `self.attachments.insert(response.attachment)` — the `request` value (which holds `content_hash`) is available in scope but is never used to validate the returned attachment's hash: [3](#0-2) 

No comparison such as `Attachment::hash(&response.attachment.content) == request.content_hash` exists anywhere in this function or in the surrounding `AttachmentsBatchStateContext`/`AttachmentsBatchStateMachine` code that was inspected. The only checks performed are: (1) whether an HTTP response was received at all (`report.bump_failed_requests()` on `None`), and (2) whether `decode_atlas_get_attachment()` succeeds structurally (i.e., the body deserializes). Neither check validates content integrity against the requested hash.

Because `sources: HashMap<UrlString, ReliabilityReport>` in `AttachmentRequest` can include any peer registered as a download source, and the URL used for the request is chosen via `get_most_reliable_source` [4](#0-3) , a remote, unprivileged peer serving that URL fully controls the bytes returned in the `GetAttachmentResponse` body. It can return well-formed attachment content that decodes successfully but whose actual hash differs from `content_hash`.

### Impact Explanation
An attacker-controlled attachment (differing from the one identified by the canonical `content_hash` committed via a BNS/name operation) is inserted into `self.attachments` and subsequently flows into `AtlasDB::insert_instantiated_attachment`, storing forged attachment content in the node's local Atlas database keyed to a hash it never actually matches. Any RPC clients or BNS resolution logic reading resolved attachments from this node will be served attacker-supplied data as if it were the canonical committed attachment, while the true attachment for that hash can never be considered "resolved" (since the local store now believes it already has it). This matches the "attachment/BNS mismatch" High-severity category: canonical name/zonefile data is silently replaced by attacker data with no cryptographic binding enforced client-side.

### Likelihood Explanation
Any peer that a node has picked as an attachment download source (an unprivileged position — simply being connected and offering to serve the URL) can trigger this on every attachment request it services. No secrets, signatures, or special roles are required; the attacker just needs to be selected as (or be) the queried source URL and return a mismatched but well-formed `GetAttachmentResponse` body. This is fully repeatable per request/attachment.

### Recommendation
In `extend_with_attachments`, after a successful decode, verify the returned attachment's hash against the request before inserting:
```rust
if let Ok(response) = response.decode_atlas_get_attachment() {
    if Attachment::hash(&response.attachment.content) == request.content_hash {
        self.attachments.insert(response.attachment);
        report.bump_successful_requests();
    } else {
        report.bump_failed_requests();
    }
} else {
    report.bump_failed_requests();
}
```
Also consider penalizing/deregistering peers that return mismatched content as if they were faulty.

### Proof of Concept
Add a unit test in `stackslib/src/net/atlas/download.rs`'s test module:
1. Construct an `AttachmentRequest` with a known `content_hash` (e.g. hash of `b"correct"`).
2. Construct a `GetAttachmentResponse`-decoding `StacksHttpResponse` whose body attachment content is `b"malicious"` (a different hash).
3. Build a `BatchedRequestsResult<AttachmentRequest>` with `succeeded = {(request, Some(response))}`.
4. Call `AttachmentsBatchStateContext::extend_with_attachments(context, &mut results)`.
5. Assert `context.attachments` contains the attachment with content `b"malicious"` even though `Attachment::hash(b"malicious") != request.content_hash`, proving the mismatched attachment was accepted despite the hash inequality.

    pub fn extend_with_attachments(
        mut self,
        results: &mut BatchedRequestsResult<AttachmentRequest>,
    ) -> AttachmentsBatchStateContext {
        for (request, response) in results.succeeded.drain() {
            let report = self
                .peers
                .get_mut(request.get_url())
                .expect("Atlas: unable to retrieve reliability report for peer");

            let response = if let Some(r) = response {
                r
            } else {
                report.bump_failed_requests();
                continue;
            };

            if let Ok(response) = response.decode_atlas_get_attachment() {
                self.attachments.insert(response.attachment);
                report.bump_successful_requests();
            } else {
                report.bump_failed_requests();
            }
        }
        let mut events_ids = results.faulty_peers.keys().copied().collect::<Vec<usize>>();
        self.events_to_deregister.append(&mut events_ids);

        self
    }
