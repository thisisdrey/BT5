### Title
Missing reward checkpoint before resource undelegation can allow stale vote-based reward accrual - (File: `actuator/src/main/java/org/tron/core/actuator/UnDelegateResourceActuator.java`)

### Summary
The external report describes a case where a fund-removal operation (`ParentFundingPool#removeCollateral`) fails to update a monotonic "high-water" accounting checkpoint (`valueHighPoint`) before returning value to the caller, so future fee/gain calculations are computed against stale state. The same bug class — a state-mutating operation that changes an account's stake/weight without first checkpointing the reward-accrual bookkeeping — is reachable in java-tron's resource-delegation actuators.

### Finding Description
java-tron tracks voting rewards using a per-account checkpoint (`beginCycle`/`endCycle`, and a snapshotted vote list) maintained by `MortgageService.withdrawReward()` [1](#0-0) . Any actuator that changes an account's stake/weight or vote eligibility is expected to call `mortgageService.withdrawReward(ownerAddress)` first, so that reward accrual is correctly settled against the account's state *before* the mutation. This pattern is followed by `UnfreezeBalanceActuator` [2](#0-1) , `UnfreezeBalanceV2Actuator` [3](#0-2) , and `VoteWitnessActuator`.

However, `UnDelegateResourceActuator.execute()` mutates the owner's frozen/delegated resource balances (`addDelegatedFrozenV2BalanceForBandwidth`, `addFrozenBalanceForBandwidthV2`, similarly for energy) and the receiver's acquired balances, without ever calling `mortgageService.withdrawReward()` for either account [4](#0-3) . This is analogous to the reported bug: a withdrawal-class operation ("returning" delegated TRX back to the owner as unlocked frozen balance) changes the stake/weight that reward computation depends on (`ownedTronPower` vs. total votes, as used in `UnfreezeBalanceV2Actuator.updateVote` / `UnfreezeBalanceV2Processor.updateVote` [5](#0-4) ) without first settling/checkpointing the reward accounting the way its sibling actuators do.

### Impact Explanation
Because `withdrawReward` is what advances `beginCycle`/`endCycle` and snapshots the vote list used to compute `deltaVi`-based rewards in `computeReward` [6](#0-5) , skipping this checkpoint on `UnDelegateResourceActuator` can leave the checkpoint stale relative to the account's now-changed resource/weight state. This is the same class of issue as the `valueHighPoint` bug: an accounting baseline that should be advanced on a "removal" event is not advanced, so subsequent reward computations can be performed against an inconsistent baseline. In the worst case this could result in incorrect (excess or deficient) reward crediting relative to actual stake — a value-accounting bug in the DPoS reward pool rather than a direct fund-theft primitive.

### Likelihood Explanation
`UnDelegateResourceContract` is a normal, permissionless, broadcastable transaction type usable by any account that has previously delegated resources, so the path is reachable by any unprivileged transaction broadcaster. I was not able to fully trace, within the available tool budget, whether the omission actually produces an observable reward miscalculation end-to-end (e.g., whether `computeReward`'s vote-based delta-Vi math is actually affected by resource undelegation independent of vote changes, since votes themselves are only mutated in the freeze/unfreeze paths, not in delegate/undelegate). This uncertainty should be treated as unresolved — a deeper trace of `computeReward`'s dependency on `DelegatedResourceCapsule`/tron power (versus purely vote count) is required before this can be confirmed as a Medium/High severity, concretely-exploitable analog rather than a purely defensive-coding inconsistency.

### Recommendation
Given the incomplete verification above, I recommend that a Devin session (or manual review) trace whether `UnDelegateResourceActuator`'s resource/weight mutation can, via `TronPower` changes, cause `MortgageService.computeReward` or `VoteRewardUtil.computeReward` to use stale vote/cycle checkpoints in a way that changes reward outcomes. If confirmed, add a `mortgageService.withdrawReward(ownerAddress)` (and for the receiver, if applicable) call at the start of `UnDelegateResourceActuator.execute()`, mirroring `UnfreezeBalanceActuator` and `UnfreezeBalanceV2Actuator`.

### Proof of Concept
Not constructible with certainty from static analysis alone within the current investigation — a full PoC requires confirming that undelegation-induced tron-power changes feed into the reward-checkpoint logic (`beginCycle`/`endCycle`/`accountVote` snapshot) used by `MortgageService`/`VoteRewardUtil`, which was not conclusively established in this pass. A background Devin session with test-harness access (e.g., extending `UnDelegateResourceActuatorTest` / `DelegationServiceTest`) would be needed to construct and validate a concrete PoC transaction sequence (delegate → vote → undelegate → advance cycle → withdraw reward) and observe whether the paid-out reward diverges from the expected amount.

  public void withdrawReward(byte[] address) {
    if (!dynamicPropertiesStore.allowChangeDelegation()) {
      return;
    }
    AccountCapsule accountCapsule = accountStore.get(address);
    long beginCycle = delegationStore.getBeginCycle(address);
    long endCycle = delegationStore.getEndCycle(address);
    long currentCycle = dynamicPropertiesStore.getCurrentCycleNumber();
    long reward = 0;
    if (beginCycle > currentCycle || accountCapsule == null) {
      return;
    }
    if (beginCycle == currentCycle) {
      AccountCapsule account = delegationStore.getAccountVote(beginCycle, address);
      if (account != null) {
        return;
      }
    }
    //withdraw the latest cycle reward
    if (beginCycle + 1 == endCycle && beginCycle < currentCycle) {
      AccountCapsule account = delegationStore.getAccountVote(beginCycle, address);
      if (account != null) {
        reward = computeReward(beginCycle, endCycle, account);
        adjustAllowance(address, reward);
        reward = 0;
        logger.info("Latest cycle reward {}, {}.", beginCycle, account.getVotesList());
      }
      beginCycle += 1;
    }
    //
    endCycle = currentCycle;
    if (CollectionUtils.isEmpty(accountCapsule.getVotesList())) {
      delegationStore.setBeginCycle(address, endCycle + 1);
      return;
    }
    if (beginCycle < endCycle) {
      reward += computeReward(beginCycle, endCycle, accountCapsule);
      adjustAllowance(address, reward);
    }
    delegationStore.setBeginCycle(address, endCycle);
    delegationStore.setEndCycle(address, endCycle + 1);
    delegationStore.setAccountVote(endCycle, address, accountCapsule);
    logger.info("Adjust {} allowance {}, now currentCycle {}, beginCycle {}, endCycle {}, "
            + "account vote {}.", Hex.toHexString(address), reward, currentCycle,
        beginCycle, endCycle, accountCapsule.getVotesList());
  }

  private long computeReward(long beginCycle, long endCycle, AccountCapsule accountCapsule) {
    if (beginCycle >= endCycle) {
      return 0;
    }

    long reward = 0;
    long newAlgorithmCycle = dynamicPropertiesStore.getNewRewardAlgorithmEffectiveCycle();
    List<Pair<byte[], Long>> srAddresses = accountCapsule.getVotesList().stream()
        .map(vote -> new Pair<>(vote.getVoteAddress().toByteArray(), vote.getVoteCount()))
        .collect(Collectors.toList());
    if (beginCycle < newAlgorithmCycle) {
      long oldEndCycle = min(endCycle, newAlgorithmCycle,
          dynamicPropertiesStore.disableJavaLangMath());
      reward = getOldReward(beginCycle, oldEndCycle, srAddresses);
      beginCycle = oldEndCycle;
    }
    if (beginCycle < endCycle) {
      for (Pair<byte[], Long>  vote : srAddresses) {
        byte[] srAddress = vote.getKey();
        BigInteger beginVi = delegationStore.getWitnessVi(beginCycle - 1, srAddress);
        BigInteger endVi = delegationStore.getWitnessVi(endCycle - 1, srAddress);
        BigInteger deltaVi = endVi.subtract(beginVi);
        if (deltaVi.signum() <= 0) {
          continue;
        }
        long userVote = vote.getValue();
        reward += deltaVi.multiply(BigInteger.valueOf(userVote))
            .divide(DelegationStore.DECIMAL_OF_VI_REWARD).longValue();
      }
    }
    return reward;
  }
