### Title
Non-atomic Check-then-Decrypt-then-Update anti-replay window permits packet replay under concurrent processing - (File: connection_state.go)

### Summary
`ConnectionState.Decrypt` in `connection_state.go` validates and records a message counter in the anti-replay `Bits` window using two separate, non-atomic critical sections (`Check` then, after the AEAD decrypt work is done outside any lock, `Update`). Because the "value that should be recomputed on every state-changing event" (the replay window) is not updated atomically with the check that gates processing, a duplicated/replayed packet delivered to two concurrent handling paths for the same tunnel can both pass the `Check` gate before either commits its `Update`, exactly mirroring the reported bug class: a security-relevant decision is made against a stale snapshot of state instead of a value that is updated transactionally with the operation it gates.

### Finding Description
`Decrypt` performs:
1. Lock, `cs.window.Check(l, messageCounter)`, unlock [1](#0-0) 
2. AEAD decrypt (`DecryptDanger`) performed **without holding the lock** [2](#0-1) 
3. Lock, `cs.window.Update(l, messageCounter)`, unlock [3](#0-2) 

The same pattern is repeated in `VerifyRelay` [4](#0-3) .

`Bits.Check` only inspects existing state (read-only) and `Bits.Update` is the only call that actually marks the counter as seen [5](#0-4) . Since `Check` and `Update` are split across two separate lock acquisitions with the (potentially slow) AEAD decrypt sandwiched in between, the anti-replay window's committed state does not reflect an in-flight decrypt. This is structurally identical to the reported bug class: a value ("has this counter been consumed") is validated against the current/stale snapshot rather than being updated as part of the same atomic operation, so a second concurrent evaluation of the same input can pass the check before the first evaluation's effect is recorded.

Nebula's UDP layer supports multiple reader routines/queues (`f.routines`, `SO_REUSEPORT`) that independently call into `readOutsidePackets` and ultimately `ConnectionState.Decrypt` for inbound packets [6](#0-5) [7](#0-6) . There is nothing pinning all traffic for a given tunnel/`ConnectionState` to a single queue at the Nebula application layer, so it is at least architecturally possible for the same encrypted packet (or a captured, retransmitted duplicate) to reach `Decrypt` twice near-simultaneously.

### Impact Explanation
If two decrypt calls for the same `messageCounter` race, both can pass `Check` (since neither has yet called `Update`), both successfully decrypt the same valid ciphertext, and only afterward do their `Update` calls run (one recording success, one then correctly rejecting as duplicate — but too late, since the plaintext has already been delivered/processed once by each caller). This allows a captured/duplicated tunnel packet to be processed twice, which is a traffic replay outcome — the same category of impact called out for "nonce/replay handling" attacker paths. This is a genuine window for replay/duplicate-processing rather than a purely cosmetic accounting bug (unlike the original fee-miscalculation report, which is a financial accounting error with no security/authentication content, but the pattern of "commit state must happen atomically with the state-gated action" root cause is directly analogous).

### Likelihood Explanation
Exploitability depends on: (1) an attacker capturing and replaying a genuine encrypted UDP packet on the wire within the narrow race window between two decrypt attempts, and (2) the specific packet being routed to two different reader goroutines concurrently (requires multi-queue mode, `routines > 1`). This is a race condition, not a deterministic bypass, so likelihood is lower than a straightforward logic bug, but it is reachable purely by a network-adjacent attacker replaying observed ciphertext — no valid CA-signed certificate is needed to trigger the race (the attacker only needs to duplicate an already-observed packet on the wire).

### Recommendation
Make the "check gate the operation" and "commit the result" a single atomic operation with respect to the replay window: hold `decryptLock` for the entire Check→Decrypt→Update sequence (or use a single combined "reserve-then-confirm" primitive on `Bits`) so that no second caller can observe the counter as unconsumed while a first caller is still processing it. Alternatively, perform an atomic "check-and-mark" as the very first step (before decrypting), and only roll back the mark if decryption subsequently fails.

### Proof of Concept
Not executed (would require constructing two concurrent `ConnectionState.Decrypt` calls with the same `messageCounter` and observing both return successfully); the race is demonstrated purely from code inspection of the lock scopes in `connection_state.go`, lines 61-82, combined with the multi-queue dispatch path in `interface.go`, lines 273-337. Confirming the practical severity would require validating the actual queue/connection affinity behavior on each platform's UDP implementation, which was not fully explored here.

func (cs *ConnectionState) VerifyRelay(l *slog.Logger, messageCounter uint64, packet []byte, nb []byte) error {
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	signedPayload := packet[:len(packet)-cs.dKey.Overhead()]
	signatureValue := packet[len(packet)-cs.dKey.Overhead():]
	_, err := cs.dKey.DecryptDanger(nil, signedPayload, signatureValue, messageCounter, nb)
	if err != nil {
		return err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	return nil

// Check returns true if i is within (or way out in front of) the window, and not a replay
func (b *Bits) Check(l *slog.Logger, i uint64) bool {
	// If i is the next number, return true.
	if i > b.current {
		return true
	}

	if b.strictlyWithinWindow(i) {
		return !b.get(i)
	}

	// Not within the window
	if l.Enabled(context.Background(), slog.LevelDebug) {
		l.Debug("rejected a packet (top)", "current", b.current, "incoming", i)
	}
	return false
}

// Update has three branches:
//   - i == b.current+1: fast path; advance the cursor by one and lose-count
//     the slot we just stomped (only past warmup; see the i > b.length guard
//     below).
//   - i  >  b.current+1: jump path; clear all slots between current and i
//     (or up to a full window's worth, whichever is smaller) via clearRange,
//     then mark i. Two arms here: a warmup arm that handles the very first
//     window before the cursor has slid, and a steady-state arm that treats
//     every cleared empty slot as a lost packet.
//   - i  <= b.current: in-window check for duplicates; out-of-window otherwise.
//
// NewBits seeds bits[0]=1 so counter 0 looks "received" — Update never
// clears that marker during warmup (clearRange skips position 0 when
// startPos=1), and once b.current >= b.length the marker is no longer
// consulted. The marker prevents a fictitious "lost" hit on the first real
// counter.
func (b *Bits) Update(l *slog.Logger, i uint64) bool {
	// Fast path: i is the next expected counter. Split out so the function
	// stays small and avoids paying for the slow paths' slog argument-build
	// stack frame on every call. The bit read/test/write is inlined to
	// touch the backing word once.
	if i == b.current+1 {
		pos := i & b.lengthMask
		word := pos >> 6
		mask := uint64(1) << (pos & 63)
		w := b.bits[word]
		if i > b.length && w&mask == 0 {
			b.lostCounter.Inc(1)
		}
		b.bits[word] = w | mask
		b.current = i
		return true
	}
	return b.updateSlow(l, i)
}

func (f *Interface) listenOut(i int) {
	var li udp.Conn
	if i > 0 {
		li = f.writers[i]
	} else {
		li = f.outside
	}

	ctCache := firewall.NewConntrackCacheTicker(f.ctx, f.l, f.conntrackCacheTimeout)
	lhh := f.lightHouse.NewRequestHandler()
	plaintext := make([]byte, udp.MTU)
	h := &header.H{}
	fwPacket := &firewall.Packet{}
	nb := make([]byte, 12, 12)

	err := li.ListenOut(func(fromUdpAddr netip.AddrPort, payload []byte) {
		f.readOutsidePackets(ViaSender{UdpAddr: fromUdpAddr}, plaintext[:0], payload, h, fwPacket, lhh, nb, i, ctCache.Get())
	})

	// An error after teardown began is shutdown noise, the closed flag covers resources
	// Close releases itself and the cancelled ctx covers ones torn down by their owners
	// reacting to it, like the user device pipes
	if err != nil && !f.closed.Load() && f.ctx.Err() == nil {
		f.l.Error("Error while reading inbound packet, closing", "error", err)
		f.onFatal(err)
	}

	f.l.Debug("underlay reader is done", "reader", i)
}
