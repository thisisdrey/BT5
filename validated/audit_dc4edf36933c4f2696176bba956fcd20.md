### Title
Multi-signature weight double-counting via malleable signatures in `ValidateMultiSign` precompile - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `ValidateMultiSign` TVM precompile (`PrecompiledContracts.java:1036-1122`) is reachable by any contract that calls the precompiled address, and is used by smart contracts (e.g. multisig wallets) to check whether a set of signatures meets an account's permission threshold. Its de-duplication logic only rejects an *exact* duplicate `(address, signature)` pair, not a duplicate *signer address* backed by a different signature. Because ECDSA signatures are malleable, a single private key can produce two distinct valid signatures over the same hash that both recover to the same address, letting one key contribute its weight twice and satisfy a multisig threshold designed to require multiple independent signers.

### Finding Description
`ValidateMultiSign.execute()` iterates over the supplied signature array and, for each signature, recovers the signer address and adds up weights from the target account's `Permission`: [1](#0-0) 

The dedup check is:
```
if (ByteArray.matrixContains(executedSignList, recoveredAddr)) {
  if (ByteArray.matrixContains(executedSignList, sign)) {
    continue;
  }
  MUtil.checkCPUTime();
}
long weight = TransactionCapsule.getWeight(permission, recoveredAddr);
...
totalWeight += weight;
executedSignList.add(sign);
executedSignList.add(recoveredAddr);
```
If `recoveredAddr` was already seen but the exact `sign` bytes were *not* seen before (i.e., a different, still-valid signature that happens to recover to the same address), the code does **not** `continue` — it falls through and adds the same key's `weight` to `totalWeight` again. This differs from the transaction-level multisig check, `TransactionCapsule.checkWeight()`, which explicitly rejects a second signature from the same recovered address with `"... has signed twice!"`: [2](#0-1) 

ECDSA signatures are inherently malleable: for a valid `(r, s, v)` signature, `(r, n-s, v')` (with the recovery id flipped) is also a valid signature over the same message hash and recovers to the same address, unless the verifier enforces canonical/low-S signatures. The precompile's `recoverAddrBySign`/signature-recovery path was not confirmed (within the available search budget) to reject non-canonical (high-S) signatures before recovery, so an attacker holding a single active key can likely submit two malleable variants of their own signature to `ValidateMultiSign` and have their weight counted twice.

### Impact Explanation
If an account's `Active` permission is configured with multiple keys each carrying partial weight (e.g., two keys with weight 1 and threshold 2, requiring both signers' cooperation), a single key holder could use this precompile weakness to independently satisfy the multisig threshold by submitting two malleable signatures of their own key, bypassing the intended requirement for a second independent signer. Any smart contract (e.g., a custom multisig wallet, escrow, or governance contract) relying on this precompile for authorization would treat the transaction as fully approved by the required weight, enabling unauthorized asset movement/approval by a single key — a concrete "unauthorized account operation" consistent with the reported incident's bug class (a wallet drain caused by insufficient/erroneous signature-authorization enforcement).

### Likelihood Explanation
Exploitation requires: (1) a smart contract that uses `ValidateMultiSign` to gate a sensitive operation with a weighted multisig permission, and (2) the ability to construct a malleable counterpart of one's own signature (a standard, well-known ECDSA property, not a cryptographic break). Both are within reach of any external, unprivileged contract caller with a single valid key in the permission set. The main uncertainty is whether the signature-recovery/verification path already rejects non-canonical S values before reaching this weight-accumulation code — this could not be confirmed with the available tools and should be verified by the implementing engineer.

### Recommendation
- In `ValidateMultiSign.execute()`, deduplicate strictly by `recoveredAddr`, not by the `(recoveredAddr, signature)` pair: once an address has contributed weight, skip any further signature that recovers to the same address, mirroring `TransactionCapsule.checkWeight()`'s "signed twice" rejection.
- Alternatively/additionally, enforce canonical (low-S) signature form during recovery in this precompile, consistent with standard ECDSA malleability mitigations, so that a single key cannot generate two distinct accepted signatures for the same hash.
- Add regression tests asserting that two malleable signatures from the same key are not both counted toward `totalWeight`.

### Proof of Concept
1. Create an account with an `Active` permission containing two keys `K1` (weight 1) and `K2` (weight 1), threshold 2 — i.e., both signers must approve.
2. Deploy/call a contract that invokes the `ValidateMultiSign` precompile with the account address, permission id, and a signature array.
3. Using only `K1`'s private key, sign the data hash to get `(r, s, v)`. Derive the malleable counterpart `(r, n-s, v')` which also recovers to `K1`'s address.
4. Submit both signatures (`sig1`, `sig2`) as the two entries in the precompile call's signature array.
5. Observe: `executedSignList` does not contain the exact bytes of `sig2` (it differs from `sig1`), so the `continue` is skipped; `TransactionCapsule.getWeight` is called twice for the same address, and `totalWeight` reaches 2, meeting the threshold — even though `K2` never signed.

Note: This PoC depends on confirming that the signature-recovery path used inside `ValidateMultiSign` (`recoverAddrBySign`) does not itself reject non-canonical/high-S signatures; that specific check could not be located within the available search scope and should be verified directly in the code before treating this as fully confirmed.
