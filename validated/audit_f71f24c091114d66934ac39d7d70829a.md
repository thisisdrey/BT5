Audit Report

## Title
`submit_delivery_receipt` pays relayer reward and clears the pending order regardless of the `DeliveryReceipt.success` flag - (File: bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs)

## Summary
The public, unprivileged `submit_delivery_receipt` extrinsic verifies an Ethereum execution proof and decodes a `DeliveryReceipt` containing a `success: bool` field sourced from the Gateway's `InboundMessageDispatched` event, but `process_delivery_receipt` never inspects `receipt.success` before paying the relayer reward and removing the `PendingOrders` entry. Any relayer holding a genuine proof for a message whose on-chain commands reverted (`success = false`) is paid in full exactly as if delivery succeeded.

## Finding Description
`submit_delivery_receipt` calls `T::Verifier::verify` to authenticate the event log/proof, then `DeliveryReceipt::try_from` decodes `gateway`, `nonce`, `topic`, `success`, and `reward_address` directly from the Ethereum event [3](#0-2) . It then calls `Self::process_delivery_receipt(relayer, receipt)` [2](#0-1) .

`process_delivery_receipt` only checks that `receipt.gateway` matches `T::GatewayAddress::get()` and that a `PendingOrders` entry exists for `receipt.nonce`; it then unconditionally invokes `T::RewardPayment::register_reward(&reward_account, T::DefaultRewardKind::get(), order.fee)` and calls `<PendingOrders<T>>::remove(nonce)`, emitting `MessageDelivered` — all without ever reading `receipt.success` [1](#0-0) . `Verifier::verify` only attests that the log is an authentic Ethereum event; it says nothing about whether the dispatched commands succeeded. Consequently, a receipt with `success = false` is processed identically to one with `success = true`.

## Impact Explanation
This is duplicate/incorrect settlement of bridge reward state: the pending order (created in `do_process_message` with a non-zero `fee` [4](#0-3) ) is finalized and the fee paid even though the underlying message execution failed on Ethereum. This violates the required invariant that payout state must only advance after dispatch and execution succeed atomically, and permanently forecloses any accounting path for the failed message since `PendingOrders` is removed unconditionally.

## Likelihood Explanation
Any relayer already participating in the normal `submit_delivery_receipt` flow can trigger this simply by relaying a message whose Ethereum-side commands revert (a plausible occurrence for `CallContract`, `Upgrade`, or asset-mint commands under gas or target-revert conditions). No forged proof, colluding validator, or privileged action is required — only a legitimately obtained proof for a failed dispatch, which is an unprivileged, publicly reachable action via `ensure_signed`.

## Recommendation
In `process_delivery_receipt`, branch on `receipt.success`: on `true`, retain current behavior; on `false`, withhold (or reduce per protocol design) the reward and either retain the `PendingOrders` entry for retry/refund handling or transition it to an explicit failure state/event (e.g., `MessageDispatchFailed { nonce }`) instead of treating it identically to success.

## Proof of Concept
1. `do_process_message` enqueues a message, inserting `PendingOrders[nonce]` with `fee > 0`.
2. On Ethereum, the Gateway executes the message's commands, they fail/revert, and the Gateway emits `InboundMessageDispatched(nonce, topic, success=false, reward_address)`.
3. A relayer obtains a genuine proof for this event and calls `submit_delivery_receipt(origin, event)`.
4. `Verifier::verify` succeeds (proof is authentic); `DeliveryReceipt::try_from` decodes `success = false`; `process_delivery_receipt` ignores this field, calls `register_reward` with `order.fee`, and removes `PendingOrders[nonce]`.
5. The relayer is rewarded identically to a successful delivery despite the on-chain execution failure, and the failed order's accounting is permanently erased.
